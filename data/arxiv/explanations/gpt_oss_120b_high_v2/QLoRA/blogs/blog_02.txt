# Inside NF4: The 4‑bit NormalFloat Data Type That Saves Memory and Boosts Accuracy  

Large language models (LLMs) have become the workhorse of modern NLP, but their sheer size makes **finetuning** a costly operation. A 65 billion‑parameter model traditionally needs more than 780 GB of GPU memory when trained in standard 16‑bit precision—far beyond what most researchers can afford.  

Quantization—compressing model weights to fewer bits—offers a tempting way out, yet most low‑bit formats either sacrifice performance or break down when gradients have to flow through them during training. The recent **QLoRA** framework shows that a carefully crafted 4‑bit format, **NormalFloat (NF4)**, can break this trade‑off. In this post we unpack the statistical ideas behind NF4, see how it differs from the everyday *int4* and *float4* formats, and understand why it is “information‑theoretically optimal” for the normally‑distributed weights of LLMs.

---

## 1. Why Standard 4‑bit Formats Struggle  

Before diving into NF4, let’s recall what a typical block‑wise k‑bit quantizer does. A full‑precision weight tensor $\mathbf{W}\in\mathbb{R}^{b\times h}$ is split into small blocks (e.g., 64 elements each). For each block we compute a *scale* $c$ and map the real numbers onto an integer range:

\[
\mathbf{W}^{\text{int8}} = \operatorname{round}\!\Bigl( c \,\mathbf{W} \Bigr),\qquad 
c = \frac{\text{absmax}(\mathbf{W})}{2^{b_{\text{bits}}}-1}.
\]

During **dequantization** we divide back by $c$. This works well for inference, but two problems surface when training:

1. **Outliers dominate the scale** – a single large weight forces $c$ to be small, wasting many integer codes on empty bins.  
2. **Gradient flow through discrete codes** – backpropagation needs an accurate reconstruction of $\mathbf{W}$; any systematic bias introduced by poor quantization hurts learning.

Both int (plain integers) and float (including “float‑type” 4‑bit representations) suffer from these issues because they assume *uniform* allocation of codes across a fixed range rather than matching the actual data distribution.

---

## 2. The Hidden Normal Distribution of LLM Weights  

Empirical studies of pretrained transformer weights reveal a striking regularity: after per‑layer scaling, weight values are **approximately zero‑centered Gaussian** (normal) variables:

\[
\mathbf{W}_{\ell} \;\approx\; \mathcal{N}(0,\sigma_{\ell}^{2}) .
\]

The key observation is that *the shape* of this distribution is stable across layers; only its variance $\sigma_{\ell}^{2}$ changes. If we could align our quantizer’s bins with the true **quantiles** of a normal distribution, each code would be used equally often—precisely what information theory tells us maximizes representational efficiency.

---

## 3. Building NormalFloat (NFk)  

### 3.1 From Quantiles to Codewords  

For a $k$‑bit datatype we have $2^{k}$ distinct codes. Let $Q_{X}(\cdot)$ be the quantile function (inverse CDF) of $\mathcal{N}(0,1)$. The optimal code values $q_{i}$ are chosen so that each interval between successive codes contains exactly the same probability mass:

\[
q_{i} = \frac{1}{2}\Bigl(
Q_{X}\!\bigl(\tfrac{i}{2^{k}+1}\bigr)
+ Q_{X}\!\bigl(\tfrac{i+1}{2^{k}+1}\bigr)
\Bigr),\quad i=0,\dots,2^{k}-1 .
\tag{1}
\]

These $q_i$ define a **k‑bit NormalFloat** (NFk) data type whose bins are perfectly aligned with a standard normal distribution.

### 3.2 Zero‑Point & Symmetry  

A naïve symmetric coding would lack an exact representation for zero—a problem because many tensors contain exact zeros (e.g., padding). To enforce a discrete zero while still using all $2^{k}$ codes:

* Allocate $2^{k-1}$ negative values and $2^{k-1}+1$ positive values,
* Merge the duplicate zero entries,
* Keep the remaining $2^{k}$ values as in Eq.(1).

The result is an *asymmetric* but still balanced code set that guarantees an exact zero point—crucial for stable training.

### 3​.​3 Putting Real Weights onto NFk  

Given a weight block $\mathbf{w}$ with empirical standard deviation $\sigma$, we first **normalize** it into the fixed range $[-1,1]$:

\[
\tilde{\mathbf{w}} = \frac{\mathbf{w}}{\max|\mathbf{w}|}\;\in[-1,1].
\]

Because NFk’s underlying quantiles were also scaled to $[-1,1]$, this simple rescaling aligns the block’s distribution with the codebook defined by Eq.(1). Dequantization simply looks up the nearest code value and rescales back to BF16 precision during computation.

---

## 4. Why NF4 Beats int4 and float4  

| Aspect | int4 / float4 | NormalFloat (NF4) |
|--------|---------------|-------------------|
| **Code allocation** | Uniform over fixed interval | Equal probability mass under $\mathcal N(0,\sigma^2)$ |
| **Zero representation** | May be approximated poorly | Exact discrete zeropoint |
| **Outlier handling** | Large outliers shrink scale → many empty bins | Scale matches true variance → all bins utilized |
| **Empirical performance** | Higher perplexity & lower downstream accuracy | Consistently lower perplexity across OPT/LLaMA/BLOOM/Pythia (see Table 5 in QLoRA) |

In practice, experiments with QLoRA show that *NF4 + double quantization* recovers full 16‑bit performance on benchmarks ranging from GLUE to MMLU, while plain FP4 lags by roughly one percentage point in accuracy. The memory savings are also tangible: double quantizing the per‑block scaling constants trims ≈0.37 bits per parameter—about 3 GB for a 65 B model.

---

## 5. Double Quantization: Squeezing Out Every Bit  

A blockwise 4‑bit scheme needs a *scale* per block (the $c$ constant). If stored as full‐precision float32 these scales add ≈0.5 bits per parameter overhead. **Double Quantization (DQ)** treats those scales themselves as another quantizable tensor:

* First level: original weights → NF4 with per‑block scale $c_{2}^{\text{FP32}}$.
* Second level: compress $c_{2}^{\text{FP32}}$ → FP8 ($c_{2}^{\text{FP8}}$) using a larger blocksize (e.g., 256).  
* A tiny set of FP32 meta‑scales ($c_{1}^{\text{FP32}}$) restores full precision during dequantization.

The result reduces average scale storage from $0.5$ bits → $0.127$ bits per weight while preserving numerical fidelity—exactly what enables finetuning a 65 B model inside a single 48 GB GPU.

---

## 6. Integrating NF4 into QLoRA  

QLoRA’s training pipeline distinguishes two data types:

| Role | Storage datatype | Computation datatype |
|------|------------------|----------------------|
| Base model weights | **NF4** (or other k‑bit) | BF16 (Brain Float16) |
| LoRA adapters | BF16 | BF16 |

During forward & backward passes each weight block is *dequantized on‐the‐fly* from NF4 to BF16 before participating in matrix multiplications. Crucially, gradients are never computed w.r.t. the frozen base weights—only w.r.t. the LoRA parameters—so backpropagation stays entirely in high precision while keeping the base model in ultra‐compact form.

This design yields two practical breakthroughs:

* **Memory reduction:** A LLaMA 65B model goes from >780 GB (full BF16 finetuning) down to <48 GB using NF4 + DQ + paged optimizers.
* **Performance parity:** Across >1000 finetuning runs from 80M up to 65B parameters, QLoRA matches or exceeds baseline BF16 LoRA performance on GLUE, Super-NaturalInstructions, MMLU, and Vicuna chat benchmarks.

---

## 7. Bottom Line & Outlook  

NormalFloat (NF4) brings together three ideas that feel almost inevitable once you look at them together:

1️⃣ **Statistical matching:** By aligning code boundaries with Gaussian quantiles we guarantee an even utilization of every bit pattern—exactly what information theory predicts for optimal compression of normally distributed data.

2️⃣ **Zero fidelity:** An explicit discrete zero point removes systematic bias on padded or sparsely active tensors—a subtle bug that can explode during gradient propagation.

3️⃣ **Hardware friendliness:** Because NF4 uses only four bits per weight plus an efficiently stored scale (thanks to double quantization), it fits comfortably into modern GPU memory hierarchies without exotic kernels beyond standard dequantize‐and‐multiply operations.

The payoff is dramatic: state‑of‑the‑art chatbots such as **Guanaco** can be finetuned on commodity hardware while staying within <48 GB GPU memory and still achieving ≈99 % of ChatGPT’s Vicuna benchmark score—a gap previously thought unreachable without massive clusters or proprietary data pipelines.

### What’s Next?

* **Even lower precisions:** With gradients already flowing through high‑precision adapters, research could explore aggressive base model compressions like *3‑bit* or *binary* encodings.
* **Alternative PEFT methods:** LoRA works beautifully here, but prompt tuning or IA³ might pair even better with NFk under certain tasks.
* **Broader evaluation:** Extending beyond Vicuna/MMLU—to BigBench or HELM—will reveal how far “distributional optimality” helps on truly diverse downstream workloads.

In short, NF4 shows that clever statistics can turn what looked like an unavoidable tradeoff between memory and accuracy into a non‑issue—opening doors for anyone who wants to push large language models without waiting for multi‑GPU supercomputers. Happy finetuning!
