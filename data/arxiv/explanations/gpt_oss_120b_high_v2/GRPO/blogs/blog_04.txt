\title{Blogs about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

# From Code to Calculus – How Pretraining on Code Improves Mathematical Thinking  

*What happens when a language model learns to program before it learns mathematics? The DeepSeekMath experiments show that a solid dose of coding can make a huge difference—not only when the model calls a calculator or a Python library, but also when it reasoned step‑by‑step with plain text.*

---

## The “hard” part of mathematics for language models  

Mathematical problem solving combines three things that are traditionally tricky for large language models (LLMs):  

1. **Symbolic manipulation** – you have to keep track of variables, equations, and algebraic identities without losing any term.  
2. **Multi‑step planning** – most problems require a chain of logical deductions before you can write down the final answer.  
3. **Precision** – a single stray sign or an off‑by‑one mistake makes an otherwise correct solution invalid.

Large‑scale LLMs have tackled these challenges by ingesting billions of math tokens or by post‑hoc reinforcement learning (RL). Yet many open‑source models still lag far behind closed systems such as GPT‑4 or Gemini‑Ultra. The DeepSeekMath team asked a very concrete question: *Can exposing an LLM early on to programming languages give it an edge on pure mathematical reasoning?*

---

## Why code might be a good warm‑up  

Programming languages are essentially **structured symbolic systems**—variables, functions, loops, and conditionals are all explicit symbols whose meaning depends on context rather than on natural language nuances. When a model learns to generate syntactically correct Python (or any other language), it simultaneously learns:

* **How to keep track of symbols across many lines** – just like you would hold an algebraic expression in mind while performing transformations.
* **How to break a problem into reusable subroutines** – analogous to writing “first compute X, then plug X into Y” which mirrors chain‑of‑thought (CoT) reasoning.
* **How to call external tools safely** – generating `sympy` calls teaches the model the pattern “solve → verify → return”.

If these habits transfer beyond coding, we would expect measurable improvements on standard mathematics benchmarks—both when the model is allowed to run Python (“tool‐assisted” mode) and when it must produce a self‐contained textual solution (“pure” mode).

---

## Experiment design – two ways of feeding code and math  

The authors built several training pipelines around **DeepSeek‑LLM 1.3 B**, which later served as the backbone for the 7 B DeepSeekMath series. All pipelines used exactly the same total amount of data; only the order and mixing differed.

| Pipeline | First phase | Second phase | Tokens |
|----------|------------|--------------|--------|
| **Two‑stage (code → math)** | 400 B tokens of *pure* programming data (mostly GitHub + StackOverflow) | 150 B tokens of *pure* mathematical web text | 550 B total |
| **Two‑stage (general → math)** | 400 B tokens of generic natural‑language data (no code) | 150 B tokens of mathematical web text | 550 B total |
| **One‑stage mixed** | A single pass over a *mixture* of 400 B code tokens *and* 150 B math tokens | — | 550 B total |

All runs used the same optimizer settings as DeepSeek’s standard pre‑training recipe (AdamW, multi‑step learning rate schedule, 4 K context length). After pre‑training they evaluated three families of tasks:

* **Pure CoT** – solving GSM8K or MATH problems directly in text.
* **Program‑of‑Thought (PoT)** – writing a short Python script that uses `math` or `sympy`, then executing it.
* **General language/coding benchmarks** – HumanEval / MBPP for programming fidelity.

---

## What the numbers say  

Even without exact percentages printed in the paper, all three evaluation suites pointed in the same direction:

* **Code first → Math second beats “general first → Math”.**  
  The model that spent its first 400 B tokens learning Python consistently outperformed its counterpart that saw generic English data first—even though *both* received exactly the same amount of subsequent math data.

* **Program‐aided solving gets a noticeable lift after any amount of code pre‑training.**  
  On GSM8K and MATH when prompted to write a Python solver, the “code→math” model solved more problems correctly than either baseline without code exposure or than a model trained only on math tokens.

* **Pure textual reasoning also improves after code pre‑training**, albeit less dramatically than PoT performance. The chain‐of‐thought scores rose above those achieved by models that never saw programming data.

* **Mixing code & math in one stage mitigates catastrophic forgetting.**  
  When researchers continued training *only* on math after heavy code exposure, they observed some decline in raw coding ability (the usual “catastrophic forgetting”). By interleaving code tokens during this second stage, the mixed pipeline preserved most of its original coding scores while still gaining almost all of the mathematical boost seen in the strict two–stage version.

In short, **code pretraining is beneficial for both tool‐integrated reasoning and plain symbolic thinking**, and careful curriculum design can keep those gains while protecting earlier abilities.

---

## Peeking under the hood – why does programming help?  

1. **Symbolic discipline** – Writing correct Python forces the model to treat variable names as *ontologically distinct objects*. This habit translates directly into handling algebraic symbols (`x`, `y`, `θ`) without confusing them during transformations.

2. **Explicit step ordering** – A typical PoT solution looks like:
   ```python
   import sympy as sp
   x = sp.symbols('x')
   expr = sp.solve(sp.Eq(x**2 - 5*x + 6, 0), x)
   print(expr)
   ```
   Each line corresponds to an inference step (“introduce x”, “form equation”, “solve”). When asked to reason without executing any code, the model has already internalized this linear decomposition pattern from millions of examples—a perfect primer for CoT prompting.

3. **Error checking via execution feedback** – During pretraining on public repositories many examples include *tests* (`assert` statements) or comments describing expected outputs (“# returns 42”). This exposure teaches LLMs how *verification* fits into problem solving—a skill that carries over when they must double-check arithmetic mentally rather than by running an interpreter.

4. **Tool–use mindset** – If you’ve spent billions of tokens learning when it’s appropriate to call external libraries (`numpy`, `sympy`, `math`), you develop an intuition about “what can be outsourced”. Even without actual execution at inference time, that intuition nudges the model toward more structured decompositions rather than vague monologues.

---

## Catastrophic forgetting – how mixing saves both worlds  

Standard continual learning experience tells us that fine‐tuning heavily on one domain often erodes knowledge from earlier domains—a phenomenon especially acute when parameters are limited (as with a 1.3 B backbone). In practice:

* After finishing the second stage of pure math training, token‐level accuracy on HumanEval dropped compared with the checkpoint taken right after code pretraining.
* By reintroducing a modest fraction (~10–20 %) of raw code samples into each subsequent mini‐batch (“mixed” schedule), those drops were largely eliminated while still achieving comparable gains on GSM8K/MATH CoT metrics.

The tradeoff is subtle: if you overload a *small* model with too much mixed data at once, its capacity may not suffice to represent both styles optimally, leading to slight dip in pure CoT scores. In larger models (>7 B) this tension eases—their higher capacity can absorb heterogeneous streams more comfortably.

---

## Practical takeaways for building mathematically strong LLMs  

- **Start from a coder foundation**  
  Even if your end goal is pure mathematics, initializing from a strong coding checkpoint such as DeepSeek‑Coder gives you immediate symbol handling abilities that plain language models lack.

- **Use a curriculum:**  
  - Phase 1 → heavy exposure to high-quality programming corpora (Python/JavaScript/SQL).  
  - Phase 2 → targeted mathematical web text (the DeepSeekMath Corpus shows excellent quality).  
  - Optional Phase 3 → interleave small fractions of code throughout Phase 2 if you want long‐term coding competence.

- **Monitor both sides**  
  Keep separate validation suites: PoT benchmark (e.g., GSM8K/Python) *and* CoT benchmark (e.g., MATH). If one metric starts sliding while another climbs, adjust mixing ratio accordingly.

- **Don’t overvalue arXiv alone**  
  The authors found that massive arXiv collections contributed little—or even hurt—performance on quantitative benchmarks despite being popular in prior work. Focus instead on diverse web sources filtered specifically for mathematical discourse (Common Crawl + fastText classifier proved effective).

- **Scale matters—but isn’t everything**  
  The two–stage “code→math” route allowed a modest 7 B model (**DeepSeekMath‑Base**) to rival far larger closed models such as Minerva 540 B on competition­level MATH tests—a clear indicator that data quality + curriculum outweigh sheer parameter count at these sizes.

---

## Closing thoughts  

The DeepSeekMath study offers concrete evidence that learning how *to program* trains large language models in ways directly useful for mathematics:

* Symbolic handling becomes second nature because programs demand it relentlessly.
* Multi-step planning emerges naturally when models learn how humans break down computational tasks into functions.
* A well–designed curriculum prevents mental “rust”—the loss of earlier skills—by keeping programming examples sprinkled throughout later training phases.

As open source communities continue building increasingly capable LLMs, embedding a solid coding phase early on looks like an inexpensive yet high‑payoff investment—not just for tool‐augmented problem solving but also for bare‐bones logical deduction across languages and domains. Future work will test whether this benefit scales further up (e.g., beyond 70 B parameters) and how reinforcement learning tricks such as Group Relative Policy Optimization can amplify it even more—but even today we already see that moving from “code” straight into “calculus” is more logical than trying to jump straight into calculus alone.
