# Transformer Decoder Architecture Recap  

Modern large language models (LLMs) employed throughout this work adopt a **decoder‑only transformer** design \citep{gpt4,deeps​ek‑coder}. In such an architecture each token is processed sequentially: at time step \(t\) the model receives all previously generated tokens \(x_{<t}\) and predicts the distribution over the next token \(x_{t}\). This prediction relies on a stack of self‑attention layers followed by feed‑forward networks \citep{transformer}. Self‑attention allows every position to attend to every earlier position while respecting causality—the model never sees future tokens during training or generation. By stacking many identical blocks one obtains a deep network capable of capturing long‑range dependencies required for sophisticated reasoning tasks such as mathematics \citep{deepseek‑coder}. The parameters are shared across all layers and positions, enabling efficient scaling up to billions of weights while preserving a uniform computational pattern that maps cleanly onto modern hardware accelerators.



# Pre‑training Objectives (Causal Language Modeling)  

The core learning signal during pre‑training follows the **causal language modeling** objective. Concretely, for each position \(t\) the model maximizes the log‑likelihood  

\[
\log p_{\theta}(x_{t}\mid x_{<t}),
\]  

where \(p_{\theta}\) denotes the conditional distribution defined by the transformer decoder with parameters \(\theta\). By summing this term over all positions in a document we obtain an overall loss that encourages the network to predict the next word given its left context. This formulation respects causality because only past tokens influence future predictions—a property shared by all decoder‑only LLMs \citep{deepseek‑coder}.  

In DeepSeekMath development this objective was applied repeatedly over massive corpora. The base model **DeepSeekMath‑Base 7B** continued pre‑training from *DeepSeek‑Coder‑Base‑v1.5 7B* \citep{deepseek‑coder} for an additional 500 B tokens, of which 56 % originated from a newly constructed web‐mined mathematics corpus (the DeepSeekMath Corpus), while remaining tokens comprised code snippets, arXiv papers, and natural language text in English and Chinese. Because the same causal loss was used throughout both stages—the initial coder‑oriented phase and later mathematics‑focused phase—the model retained its generative abilities while gradually specializing toward mathematical reasoning.



# Fine‑tuning Paradigms: Supervised vs Reinforcement Learning  

After establishing strong generic capabilities through extensive causal pre‑training, two complementary fine‑tuning strategies were explored.  

## Supervised Instruction Tuning  

Supervised fine‑tuning (SFT) aligns a pretrained LLM with human‐written task demonstrations \citep{sft}. For DeepSeekMath this stage assembled **776 K** examples covering diverse mathematical domains in both English and Chinese. Each example paired a problem statement with a solution expressed either as chain‑of‑thought reasoning (“CoT”), program‑of‑thought reasoning (“PoT”) where Python code solves intermediate subproblems \citep{pot,pal}, or tool–integrated formats that combine natural language steps with calls to external libraries \citep{tora}. Training proceeded by concatenating examples up to a context length of 4 K tokens and performing standard next‑token prediction over 500 gradient steps using a constant learning rate \(5\times10^{-5}\). The resulting **DeepSeekMath‑Instruct 7B** demonstrated dramatic gains over its base counterpart across multiple benchmarks when tool use was disallowed, attaining competition‑level performance on MATH without auxiliary systems.



## Reinforcement Learning Fine‑tuning  

Reinforcement learning (RL) further refines SFT models by encouraging actions—here token generations—that receive high scores from an external reward signal \citep{ouyang2022training}. In this work an **outcome-supervision** reward model \(r_{\varphi}\) judges whether a generated answer solves a problem correctly; additionally a **process–supervision** variant evaluates each intermediate reasoning step separately \citep{wang2023math}. The classic RL algorithm applied previously to LLMs is **Proximal Policy Optimization (PPO)** \citep{schulman2017proximal}. Its surrogate objective reads  

\[
\mathcal{J}_{\mathrm{PPO}}(\theta)=
\E_{q\sim P(Q),\, o\sim \pi_{\theta_{\!old}}(\cdot|q)} 
    \Biggl[\frac1{|o|}
    \sum_{t=1}^{|o|}
    \min
    \Bigl(
        r_t(\theta)\,
        \operatorname{clip}\bigl(r_t(\theta),\,1-\varepsilon,\,
            1+\varepsilon\bigr)
    \Bigr)
    \Biggr],
\]  

with  

\(r_t(\theta)=
   \dfrac{\pi_{\theta}(o_t|q,o_{<t})}
         {\pi_{\theta_{\!old}}(o_t|q,o_{<t})}\)
the probability ratio between current and old policies,
\(A_t\) denoting an **advantage** estimated via Generalized Advantage Estimation using a learned value function \(V_{\psi}\),
and \(\varepsilon>0\) controlling clipping stability.
PPO additionally penalizes divergence from an immutable reference policy via a per‐token KL term  

\(r_t = r_{\varphi}(q,o_{\le t})
      - \beta\, 
      \log\dfrac{\pi_{\theta}(o_t|q,o_{<t})}
                {\pi_{\mathrm{ref}}(o_t|q,o_{<t})},
`
where \(\beta>0\) balances fidelity versus exploration (Equation (2) in the source).

Because evaluating \(V_{\psi}\) requires an extra large neural network comparable in size to the policy itself, memory consumption during PPO becomes substantial—a practical bottleneck when scaling RL for multi–billion parameter models.



# The Role of Code Data in Improving Logical Inference  

A central hypothesis tested throughout this study is whether exposure to source code before mathematics confers reasoning benefits—a question historically debated yet rarely quantified empirically under controlled conditions [see discussion §6.1]. Two families of experiments were conducted using a 1.3 B parameter “DeepSeek–LLM” backbone:

* In a **two–stage pipeline**, first 400 B tokens comprised purely of programming examples were consumed (“code pretraining”), followed by 150 B tokens drawn exclusively from mathematics webpages (“math finetuning”).  
* As baselines, either 400 B general natural‐language tokens preceded math finetuning or math alone was presented without any preceding phase.

The outcomes consistently favored **code first** training:
* Even before encountering any mathematical material, the coder‐pretrained checkpoint exhibited improved ability to generate correct Python programs for GSM8K and MATH problems—a clear programme‐aided advantage noted in Table 2 of the source.
* Subsequent math finetuning built upon this foundation yielding further gains; performance after both stages surpassed that achieved by directly feeding mathematics after generic language exposure.
* When code tokens were interleaved with mathematics during a single unified stage (“mixed” training), catastrophic forgetting observed after pure two–stage schedules was mitigated while preserving strong program‐aided performance.
* Notably, improvements were also recorded on pure chain‐of‐thought tasks that forbid tool usage, demonstrating that exposure to syntactic structures and algorithmic patterns typical of source code sharpens logical inference pathways even when no actual execution occurs later.
  
These observations support an intuition that **code embodies precise compositional semantics**, compelling models to learn disciplined variable binding, control flow constructs, and stepwise computation—all traits beneficial for formal mathematical deduction [see §6.1]. Consequently DeepSeekMath’s designers deliberately initialized their high–capacity Math models from *DeepSeek‑Coder‑Base* rather than generic LLM checkpoints.



# Brief Introduction to Proximal Policy Optimization (PPO)  

PPO belongs to the family of actor–critic methods wherein two neural networks interact: an **actor** (\(\pi_\theta\)) that proposes token sequences given a question \(q\), and a **critic** (\(V_\psi\)) estimating expected future reward (“value”) under this policy. Training proceeds iteratively:
1. Sample several responses \(o=\left(o_1,\dots,o_T\right)\) from the current actor policy.
2. Compute scalar rewards at terminal steps using either rule–based correctness checks or learned reward models \(r_\varphi(q,o)\).
3. Propagate these rewards backwards through time via Generalized Advantage Estimation,
   yielding per­token advantages \(A_t = r(q,O)-V_\psi(q,O_{<t}) + (\ldots)\).
4. Formulate the surrogate loss \(\mathcal J_{\rm PPO}(\theta)\) shown above; clipping restricts updates so that successive policies stay close,
   thereby avoiding destructive policy swings.
5. An auxiliary loss enforces proximity between actor updates and an immutable reference policy \(\pi_{\rm ref}\), typically the SFT checkpoint,
   via a KL penalty parameterized by coefficient \(\beta.\)

While effective across numerous domains—including mathematical reasoning tasks such as GSM8K when paired with process supervision [see §5]—the necessity for an auxiliary value network dramatically increases GPU memory footprints during fine‐tuning [see §5]. This insight motivated devising **Group Relative Policy Optimization (GRPO)** later in this work,
which discards an explicit critic entirely.
Instead GRPO samples *groups* of candidate outputs per question,
computes their raw scores via \(r_\varphi,\)
and uses groupwise averages as implicit baselines.
The resultant objective mirrors PPO’s clipped ratio term but replaces individual advantages \(A_t\) with *group-relative* advantages
\( \hat A_{i,t}\),
thereby eliminating any extra value‐function parameters while still achieving comparable—or superior—performance at far reduced memory cost.
