# Why Attention Slows Down Large Language Models – A Simple Explanation

Large language models (LLMs) have become the workhorse behind chatbots, code assistants, and many other AI products. Yet anyone who has tried to scale these models quickly discovers a recurring roadblock: **the attention layer**. In this post we’ll walk through what attention does, why its cost explodes as models grow, how that limits “long‑context” use cases (reading whole documents or codebases), and finally how the newest FlashAttention‑3 algorithm squeezes out significant speedups on modern GPUs.

---

## What is Attention?

At its core, a Transformer layer computes three matrices from the input token embeddings:

* **Queries** $\mathbf{Q}\in\mathbb{R}^{N\times d}$
* **Keys**    $\mathbf{K}\in\mathbb{R}^{N\times d}$
* **Values**  $\mathbf{V}\in\mathbb{R}^{N\times d}$  

where $N$ is the sequence length (how many tokens we process) and $d$ is the head dimension (the size of each “attention head”).

The attention output $\mathbf{O}$ is obtained by three steps:

\[
\mathbf{S}= \frac{1}{\sqrt{d}}\,\mathbf{Q}\mathbf{K}^{\!\top}\quad
\mathbf{P}= \operatorname{softmax}(\mathbf{S}) \quad
\mathbf{O}= \mathbf{P}\,\mathbf{V}.
\]

* $\mathbf{S}$ holds pairwise similarity scores between every query and every key.
* $\operatorname{softmax}$ converts each row of $\mathbf{S}$ into a probability distribution.
* Finally each probability row weights the values $\mathbf{V}$ to form the new representation $\mathbf{O}$.

All of this looks simple on paper, but hidden inside is an operation that scales **quadratically** with $N$—the size of $\mathbf{S}$ is $N\times N$!

---

## Why Does Attention Become a Bottleneck?

### 1️⃣ Quadratic Scaling

The matrix multiplication $\mathbf{Q}\mathbf{K}^{\!\top}$ requires $N^{2}d$ multiply‑adds. Likewise the softmax and the second multiplication $\mathbf{P}\mathbf{V}$ also touch $N^{2}$ entries. As $N$ grows from a few hundred tokens (typical for short prompts) to tens of thousands (whole documents or codebases), the number of operations climbs by orders of magnitude:

\[
\text{FLOPs}_{\text{forward}} = 4\, N^{2}\, d\, n_{\text{heads}}.
\]

A modest increase from $N=1\,024$ to $N=16\,384$ multiplies the compute by $256\times$, even though the model size stays unchanged.

### 2️⃣ Memory Traffic

Standard implementations materialize both $\mathbf{S}$ and $\mathbf{P}$ in GPU global memory (HBM). That means two extra reads/writes of an $N\times N$ matrix per head—an enormous bandwidth burden that dwarfs raw compute on modern GPUs.

### 3️⃣ Hardware Mismatch

GPUs excel at dense matrix multiplication (GEMM) thanks to specialized Tensor Cores. But they are comparatively slow at element‑wise ops like exponentials needed for softmax. On an NVIDIA H100 GPU the peak FP16 GEMM throughput is roughly **989 TFLOPs**, while special‑function units can only deliver about **4 TFLOPs** for exponentials—a factor of more than two hundred difference! If attention spends too much time on softmax or on moving data around, overall utilization falls dramatically.

These three factors combine into a classic “attention bottleneck”: even though GPUs have huge raw horsepower, they can’t keep it busy when attention has to shuffle massive $N\times N$ matrices back and forth.

---

## Real‑World Impact: Long‑Context Limits

Because attention scales quadratically, most production LLMs truncate inputs to a few thousand tokens. That restriction hurts many applications:

| Application | Desired Context | Typical Truncation |
|-------------|-----------------|-------------------|
| Whole‑document QA | > 10 k tokens | ~ 2 k tokens |
| Codebase navigation | > 20 k tokens | ~ 4 k tokens |
| High‑resolution vision (e.g., $1024\times1024$ patches) | > 30 k patches | ~ 6 k patches |

When you can’t feed all relevant data at once, you need workarounds like retrieval‑augmented generation or chunked processing—both add latency and complexity. Faster attention would directly unlock “read‑the‑entire‑document” capabilities without sacrificing speed.

---

## Cutting Through the Bottleneck: Faster Attention with FlashAttention‑3

The original *FlashAttention* algorithm showed that you can avoid storing $\mathbf{S}$ and $\mathbf{P}$ by fusing all operations into a single kernel that streams blocks of data through shared memory. That reduced memory traffic dramatically but still left two major inefficiencies on newer hardware like NVIDIA’s Hopper H100:

* **Low utilization:** FlashAttention‑2 only reaches ~35 % Tensor‑Core utilization on H100, far below the 80–90 % seen for pure GEMM kernels.
* **No low‑precision path:** The algorithm was designed for FP16/BF16 only, missing out on the higher throughput promised by FP8 Tensor Cores.

*FlashAttention‑3* addresses both gaps with three synergistic ideas:

### 1️⃣ Producer–Consumer Asynchrony via Warp Specialization

GPU warps are groups of 32 threads that execute in lockstep. In *FlashAttention‑3*, some warps (“producers”) focus exclusively on loading data from global memory into shared memory using the Tensor Memory Accelerator (TMA). Other warps (“consumers”) immediately start computing GEMMs as soon as data appear. Because TMA transfers are asynchronous, producers never stall consumers—memory movement and computation overlap perfectly.

### 2️⃣ Overlap Softmax with Block‑wise GEMMs

Recall that softmax is much slower than GEMM. *FlashAttention‑3* interleaves these two stages across blocks:

1️⃣ Compute $\mathbf{Q}\,\mathbf{K}_j^{\!\top}$ for block $j$ → start softmax on that block.  
2️⃣ While softmax runs, immediately launch the GEMM for block $j+1$ (`WGMMA` – Tensor Core instruction).  

A “ping‑pong” schedule emerges where one warpgroup does softmax while another runs Tensor Core matmuls. This hides the low‑throughput exponential work behind high‐throughput matrix multiplication, boosting overall utilization from ~57 % to > 70 % in practice.

### 3️⃣ Hardware‑Accelerated FP8 GEMM + Block Quantization

Hopper’s Tensor Cores support **FP8** (`e4m3`) format—a roughly 2× speedup over FP16 if you can tolerate reduced precision. However there are two challenges:

* **Layout constraints:** FP8 `WGMMA` only accepts k‑major operand layout (contiguous along the inner dimension). *FlashAttention‑3* solves this by performing an *in‑kernel transpose* using `ldmatrix`/`stmatrix` instructions while loading tiles of $\mathbf V$.
* **Numerical error from outliers:** LLMs often contain occasional very large activations (“outliers”). A naïve per‑tensor scaling would clip these aggressively and degrade quality.

To keep accuracy high while staying in FP8, *FlashAttention‑3* employs:
- **Block quantization:** each tile (e.g., $B_r\times d$) gets its own scale factor rather than one global scale per tensor.
- **Incoherent processing:** before quantizing we multiply $\mathbf Q$ and $\mathbf K$ by a random orthogonal matrix (a signed Hadamard transform). This spreads out outlier values across entries so they become less harmful after quantization—yet because the transform is orthogonal it leaves attention mathematically unchanged.

Together these tricks deliver **2.6× lower RMSE** compared to a baseline FP8 implementation that uses per‑tensor scaling alone.

## Real Performance Gains

Benchmarks on an H100 SXM5 GPU confirm that *FlashAttention‑3* translates its clever design into tangible speedups:

| Precision | Speedup vs FlashAttention‑2 | Peak TFLOPs/s | Utilization |
|-----------|---------------------------|---------------|-------------|
| FP16      | 1.5–2.0× (forward)        | ~740          | ~75 % |
| FP8       | ≈1× (baseline already fast) but peaks at **~1.2 PFLOPs/s** thanks to double Tensor Core throughput | — | — |
| Backward (FP16) | 1.5–1.75×                | —             | — |

For typical long-sequence settings (e.g., $N=8192$, head dimension = 128), forward TFLOPs rise from ~570 TFLOPs (FlashAttention‑2) to ~620–640 TFLOPs when adding softmax‐overlap alone; full *FlashAttention‑3* reaches ~740 TFLOPs—the closest real-world kernel gets to H100’s theoretical peak.

In addition to raw speed:

* **Memory savings:** Still avoids materializing $\mathbf S$/$\mathbf P$, keeping global memory traffic minimal.
* **Accuracy:** FP16 version matches prior exact‐attention implementations; FP8 version remains within acceptable error margins even with aggressive quantization.
* **Scalability:** The algorithm works for any batch size or number of heads because each CTA processes its own query tile independently—perfectly suited for multi‐GPU training pipelines.

---

## How These Improvements Enable Longer Contexts

If you can attend over twice as many tokens in the same wall-clock time, you effectively double your context window without needing extra hardware or sacrificing latency. Concretely:

* A model that previously managed $4\,\text{k}$ tokens at 100 ms per forward pass can now handle roughly $7$–$8\,\text{k}$ tokens within the same budget.
* For inference APIs this means fewer round trips when answering questions about big documents—no need for complex chunking or retrieval pipelines.
* During training, longer context windows improve gradient quality for tasks like document summarisation or code completion across many files.

Thus *FlashAttention‑3* not only makes existing deployments faster; it expands what is feasible today—paving the way toward truly “whole‐document” LLMs without prohibitive compute costs.

---

## Takeaways

1️⃣ **Quadratic scaling** makes attention inherently expensive as sequence length grows—both compute (`$\mathcal O(N^2)$`) and memory traffic blow up.

2️⃣ **Hardware realities matter:** On modern GPUs most cycles are spent moving data or doing low‐throughput softmax work rather than pure matrix multiply.

3️⃣ **FlashAttention‑3 shows how to bridge this gap** by:
   - Splitting data movement & computation across dedicated warp groups,
   - Overlapping cheap softmax ops with heavyweight Tensor Core GEMMs,
   - Exploiting fast FP8 Tensor Cores while mitigating their numerical pitfalls through block quantization and incoherent orthogonal transforms.

4️⃣ The result is **up to 2× faster exact attention**, near‐peak GPU utilization (≈75 %), and substantially lower error even at ultra‐low precision—directly unlocking longer context windows for LLMs and related modalities.

As LLMs continue scaling in both parameters and application domains, being able to squeeze every ounce of performance out of attention will be essential. *FlashAttention‑3* offers a concrete step toward that goal—and its core ideas—producer/consumer pipelining, softmax‐GEMM overlap, and smart low‐precision handling—are likely to inspire further optimizations across future GPU architectures beyond Hopper as well.
