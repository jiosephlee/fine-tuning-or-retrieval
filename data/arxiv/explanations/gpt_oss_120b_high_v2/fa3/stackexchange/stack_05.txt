\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### How is block quantization applied when converting Q, K, V tensors to FP8?
Question:
Section 4 describes block quantization where each tile gets its own scaling factor before casting to FP8. I am unsure how these per‑tile scales are stored during execution, whether they are kept in registers or SMEM, and exactly where the scale multiplication takes place before feeding operands into WGMMA.
Answer:
**Answer**

In FlashAttention‑3 the tensors $Q,K,V$ are first split into the same rectangular tiles that the attention kernel already processes (a query tile $Q_i∈{\mathbb R}^{B_r\times d}$, a key/value tile $K_j,V_j∈{\mathbb R}^{B_c\times d}$).  
Block‑quantisation means that **each tile gets its own floating‑point scale** $s^{Q}_i,\;s^{K}_j,\;s^{V}_j$; *the elements are multiplied by this factor* **before** they are rounded‑to‑FP8 and written to shared memory (SMEM). The purpose is exactly what the paper calls “block quantisation”: outlier values are confined inside a single small region rather than contaminating an entire tensor‑wide dynamic range.

---

### Where are the per‑tile scales kept?

The kernel already contains a circular SMEM buffer that holds up‑to $s$ pending tiles (`stage = j % s`).  
Because only $s$ tiles can be alive at any moment, holding one extra 32‑bit float per pending operand costs at most a few hundred bytes, far less than&nbsp;the bandwidth budget.  

* **During production**  
&nbsp;&nbsp;&nbsp;&nbsp;The producer warpgroup loads a tile with TMA, runs an intra​warp reduction to obtain  

​$$
a_{\max}= \max_{(r,c)}|\,{\text{tile}}_{rc}\,},
$$  

&nbsp;&nbsp;&nbsp;&nbsp;and computes  

​$$
s=\frac{{{\text{FP8}}_{\max}}}{a_{\max}}\,. 
$$  

This scalar lives initially in a register (`float curScale`).  
Immediately afterwards every element belonging to this tile is multiplied by $s$
and casted to FP8; ...

```cuda
__shared__ float qScale[s];
__shared__ float kScale[s];
__shared__ float vScale[s];

// producer writes
qScale[stage] = curScale;
```

* **During consumption**  
&nbsp;&nbsp;&nbsp;&nbsp;The consumer warpgroup reads the three scalars belonging to *the pair* $(i,j)$ right before issuing WGMMA:

```cuda
float qs = qScale[stage];   // scale of current Q‑tile
float ks = kScale[stage];   // scale of current K‑tile
```

For $Q_i$, this value does not change while we sweep over all key blocks,
therefore after it has been read once it can be hoisted into a register that lives
for *the whole inner loop* (`float qsReg`).  
The key–scale $k_s$ changes every iteration and is therefore fetched from SMEM
at each step (the latency is hidden because loading happens concurrently with other work).

In principle nothing forces us to use SMEM – if $s=1$ or if enough registers are left,
the two scalars can stay purely in registers. The reference implementation chooses SMEM
simply because it already synchronises producer–consumer stages anyway,
so attaching one extra word incurs zero additional synchronisation cost.



### When does ...

WGMMA on Hopper **does not support an operand‒wise multiplier**; it treats its inputs as raw FP8 bits and produces an FP32 accumulator $\mathbf A_{ij}$. Consequently we have two distinct places where scaling enters:

1\. *Before WGMMA* – … Every element written into SMEM has been multiplied by its own block scale.  

2\. *After WGMMA* – once $\mathbf A_{ij}∈{\mathbb R}^{B_r\times B_c}$ appears,
we must re insert …  

​$$
\mathbf S_{ij}= s^{Q}_i\, s^{K}_j\, \mathbf A_{ij},
$$  

… This rescaling is just … :

```cuda
float combinedScale = qsReg * ks;
A_reg *= combinedScale;          // elementwise multiply entire tile
```

A completely analogous step follows *the second GEMM* ($P\,V^\top$): after obtaining 
the FP32 output tile we multiply it by $s^{V}_j$.  

Thus all heavy work—matrix multiplication—is performed entirely on unscaled FP8 data,
while only light FP32 work incurs *the* extra multiplications.



### Why does ...

*The algorithm already processes one query tile against many key/value tiles.*  
Hence only *one query scale* ($s^{Q}_i$) needs permanent storage during an inner loop,
while *key/value scales* appear exactly once per iteration …

Because these scalars occupy only four bytes each,
keeping them alongside every staged tile adds < 1 KB of shared memory overhead even for $s=4$. …

Finally, performing *the rescaling after* WGMMA preserves numerical accuracy:
the product $s^{Q}_i s^{K}_j$ is applied once on an FP32 accumulator rather than being folded 
into low−precision arithmetic which would otherwise amplify rounding errors.
