# Feature Engineering Meets GPT: Introducing FeatLLM

## Why Tabular Data Still Needs Better Few‑Shot Solutions  

Tabular datasets—think medical records, credit applications, or sensor logs—are everywhere in industry. Unlike images or text, they often contain a mix of numeric, categorical, and binary columns, each described by a human‑readable name and sometimes a definition. When we have only a handful of labeled rows (the **few‑shot** regime), traditional learners such as logistic regression or tree ensembles struggle to discover the right patterns without overfitting.

Large language models (LLMs) have shown an uncanny ability to solve new tasks by simply being shown a few examples in a prompt—so‑called **in‑context learning**. Prior work has tried feeding serialized tables directly into an LLM and letting it predict labels end‑to‑end (e.g., TabLLM, TABLET). While these methods can harness the world knowledge baked into models like GPT‑4 or GPT‑3.5, they suffer from two practical roadblocks:

1. **Per‑sample cost** – every test row needs a fresh call to the LLM, which is slow and expensive.
2. **Prompt length** – as the number of columns grows, serializing an entire table quickly exceeds the model’s context window.

**FeatLLM** flips this script: instead of using an LLM as a black‑box predictor, we ask it to act as an expert *feature engineer*. The idea is simple—let GPT generate human‑readable decision rules that capture the relationship between columns and target classes, turn those rules into binary features, and then feed those features into a tiny downstream model (often just a linear layer). Once the rules are extracted, no more LLM calls are needed at inference time.

---

## The FeatLLM Pipeline in Plain English  

Below is a step‑by‑step walk through what happens when you hand a new tabular task to FeatLLM.

### 1️⃣ Crafting the Prompt  

A single prompt is sent to the LLM that contains three parts:

| Part | What it contains | Why it matters |
|------|-------------------|----------------|
| **Basic information** | • Task description (“Does this patient have chronic heart failure?”)<br>• Feature names *and* optional definitions<br>• A handful of labeled examples serialized as “`f1 is … . f2 is … . Answer: …`” | Gives the model all context it needs without overwhelming it. |
| **Reasoning instruction** | • A “chain‑of‑thought” intro (“Let’s think step by step.”)<br>• **Step 1** – Infer causal relationships *without* looking at examples (e.g., “Older age increases heart disease risk”).<br>• **Step 2** – Using those relationships plus the examples, write explicit rules for each class. | Forces the LLM to draw on its prior knowledge first, then anchor its reasoning in the actual data—helps avoid spurious correlations when only a few rows are labeled. |
| **Response instruction** | • Exact JSON‑like format for each rule<br>• Guidance on how to express inequalities (“>``, `<=`”, etc.)<br>• Example output snippet | Guarantees that parsing later is straightforward despite natural language variability. |

The prompt deliberately asks for a *fixed* number of rules per class (10 in our experiments). This avoids having too many or too few features when data are scarce.

### 2️⃣ Extracting Rules  

The LLM replies with something akin to:

```
Class = Yes:
  Rule 1: age > 65 AND cholesterol > 200
  Rule 2: blood_pressure >= 140
  …
Class = No:
  Rule 1: age <= 45
  …
```

These are essentially “if‑then” criteria that encode expert knowledge plus what can be inferred from the few demonstrations provided.

### 3️⃣ Turning Rules into Binary Features  

Human readers could manually code these checks, but FeatLLM lets another short LLM pass do it automatically:

1. The extracted rule text is inserted into a second prompt that asks the model to emit valid Python code (`def rule_check(row): ...`).  
2. The generated code is executed locally via `exec()`.  
3. For every row in the original table we compute a binary vector  
   \[
   \mathbf{z}_k^i \in \{0,1\}^{R},
   \]  
   where \(R=10\) is the number of rules for class \(k\) and entry \(z_{k,j}^i\) equals 1 iff row \(i\) satisfies rule \(j\).

The result is a transformed dataset consisting solely of these binary “rule features”.

### 4️⃣ Learning How Much Each Rule Matters  

Even though many rules are sensible, some may be redundant or even noisy. FeatLLM learns their relative importance using an extremely lightweight model—typically a bias‑less linear layer applied separately per class:

\[
\text{logit}_k^i = \max(\mathbf{w}_k ,0)\;\cdot\;\mathbf{z}_k^i,\qquad 
\mathbf{p}^i = \operatorname{Softmax}\bigl([\text{logit}_1^i,\dots,\text{logit}_c^i]\bigr).
\]

Here \(\mathbf{w}_k\) are non‑negative trainable weights obtained by minimizing cross‑entropy on the few labeled rows (Adam optimizer at learning rate 0.01 for 200 epochs). The non‑negativity ensures that any generated rule can only increase—not decrease—the likelihood of its class.

### 5️⃣ Bagging & Ensembling for Robustness  

Two tricks keep FeatLLM reliable even when prompts become large or when random seeds affect rule generation:

* **Feature bagging** – each trial randomly selects a subset of columns before prompting the LLM. This reduces context length and encourages diverse rule sets.
* **Ensemble averaging** – we repeat steps 1–4 across \(T\) trials (20 in our default setup) using moderately high temperature (\(0.5\)) so that rule generation varies stochastically. Final class probabilities are simple averages of the individual trial predictions.

Bagging also acts as a defensive shield against spurious columns because any wrongly generated rule will appear in only a few ensemble members and thus carry little weight after averaging.

---

## What Makes FeatLLM Tick?  

### ✅ Zero Per‑Sample LLM Calls  
After the initial rule extraction stage (a handful of API requests), all predictions are made locally by evaluating binary conditions—a fraction of millisecond latency compared to costly API round‑trips.

### ✅ Works With API‑Only Models  
No fine‑tuning or custom checkpoints are required; you can plug in any chat model behind an HTTP endpoint (the paper uses `gpt-3.5-turbo-0613`). This opens up high‑performance LLMs that otherwise expose only inference APIs.

### ✅ Handles Wide Tables Gracefully  
By randomly dropping columns during each bagged trial we stay well within typical context windows (< 4 KB). Even datasets with > 100 attributes (e.g., *Communities*, *Myocardial*) remain tractable.

### ✅ Competitive Performance With Very Few Labels  

Across **13 diverse tabular benchmarks**, FeatLLM consistently lands at the top or second place among all competitors:

* On average it outperforms prior LLM methods (**TabLLM**, **STUNT**) by roughly **10 %** in AUC.
* With just **4 shots**, its accuracy rivals traditional learners that need **32 shots**.
* Ablation studies confirm every component matters—dropping reasoning prompts or feature descriptions hurts especially in ultra low‑shot settings (\(k \leq 4\)).

### 📊 Quality of Generated Features  

A sanity check measured each binary rule’s AUROC against ground truth before any weight tuning—most rules already exceed chance level (> 0.5). After training, irrelevant rules receive near‑zero weights automatically filtering them out without manual pruning.

---

## Peeking Under The Hood – How Much Do The Pieces Help?  

| Removed Component | Effect on Avg AUC |
|-------------------|-------------------|
| Weight tuning (`-Tuning`) | Small drop; bigger impact when more shots are available |
| Ensembling (`-Ensemble`) | Consistent degradation across all shot levels |
| Feature descriptions (`-Description`) | Noticeable loss when shots ≤ 8 |
| Reasoning step (`-Reasoning`) | Largest drop for ultra low‐shot (\(k=2\)) |

These numbers underscore two insights:

1. **Prior knowledge matters most when data are scarce** – giving GPT clear column definitions guides its rule generation.
2. **Learning rule importance becomes valuable once you have enough examples** – fine‐tuning weights provides extra lift in higher shot regimes.

---

## Speed & Cost Profile  

On an A100 GPU using the *Adult* dataset with only **16 labeled rows**, FeatLLM’s total runtime breaks down as follows:

| Phase | Approximate Time |
|------|-------------------|
| Rule generation & parsing (≈ 30 API calls) | < 5 seconds |
| Linear weight training (200 epochs) | ~ 0.4 seconds |
| Inference on test set | ~ 0.02 seconds |

By contrast, end‐to‐end LLM baselines suffer from multi‐second per‐sample latency because each test row triggers an additional request—even after batching they remain orders of magnitude slower than FeatLLM’s lightweight linear sweep.

---

## Limitations & Future Directions  

* **Scalability beyond few-shot** – FeatLLM shines when labels are extremely scarce; extending it reliably to larger training sets remains an open question.
* **Rule expressiveness** – Current implementation focuses on simple relational predicates (`>`, `<`, `=`). Richer transformations (e.g., monotonic functions or interaction terms) could capture subtler patterns.
* **Bias & Misinformation** – Since generated rules derive from an LLM’s world knowledge, any embedded societal biases may surface in rule form before ever seeing real data points; systematic auditing will be essential before deployment in high‐stakes domains like finance or healthcare.
* **Broader ensembles** – Bagging already mitigates context length issues; future work could blend FeatLLM’s rule features with conventional learned embeddings for hybrid models.

---

## Takeaway  

FeatLLM demonstrates that you don’t need to turn every prediction problem into an expensive chat with GPT. By prompting thoughtfully—first asking “what matters?” then “how do I articulate those matters?”—the language model becomes an automatic domain expert that writes down crisp decision rules. Those rules turn raw tables into tidy binary features that any lightweight classifier can consume instantly.

If you’re building ML pipelines where labeling budgets are tight but you have access to powerful chat APIs, give FeatLLM a spin: you’ll likely see higher accuracy out of far fewer labeled rows—and you’ll keep your inference costs down to essentially zero after that one time “feature engineering” chat session.

# From Questions to Rules: The Two‑Step Reasoning Behind **FeatLLM**

## Introduction  
Tabular data—spreadsheets of patient records, credit scores, sensor readings—still dominate many real‑world AI applications. Yet building high‑performing models on such data usually demands a lot of labeled examples or careful hand‑crafted features. Large Language Models (LLMs) have shown they can reason about unseen tasks just by being prompted with a few examples, suggesting a new way to “teach” a model what matters in a dataset without writing any custom code.

**FeatLLM** takes this insight one step further. Instead of asking an LLM to predict every single test sample (which would require an expensive API call per row), FeatLLM asks the LLM **once** to distill the problem into a handful of human‑readable decision rules. Those rules become new binary features that feed a tiny downstream model—often just a linear classifier. The key to this success is a carefully crafted **two‑step prompting strategy** that mirrors how a data scientist approaches a new tabular task.

Below we unpack that prompting strategy, explain why each component matters, and illustrate how it translates natural language reasoning into actionable features.

---

## The Core Idea of FeatLLM  

1. **Ask the LLM to be a feature engineer**, not an end‑to‑end predictor.  
2. **Extract class‑specific logical rules** (e.g., “age > 60 AND cholesterol > 200 → high risk”).  
3. **Convert each rule into a binary indicator** (1 if the row satisfies the rule, 0 otherwise).  
4. **Fit a lightweight model** on these binary features; the model learns how much weight to assign to each rule.  
5. **Ensemble multiple rule sets** via bagging and temperature sampling for robustness.

The heavy lifting—the reasoning about which features matter—is done offline during prompt execution. After that, inference is as cheap as evaluating a few logical expressions.

---

## Prompt Design – Three Building Blocks

FeatLLM’s prompt is deliberately structured into three parts:

| Part | What it contains | Why it matters |
|------|------------------|----------------|
| **Basic information description** | • Task statement (question form) <br>• Natural‑language feature names + type/definition <br>• A handful of few‑shot examples serialized as “`f₁ is … . f₂ is … . Answer: …`” | Gives the LLM all the context it needs—what we’re trying to predict and what each column actually means—without yet showing any data patterns. |
| **Reasoning instruction** | • A short chain‑of‑thought intro <br>• **Step 1:** “Explain which features you think are relevant *before* looking at the examples.” <br>• **Step 2:** “Using those insights *and* the examples, write explicit rules for each class.” | Forces the LLM to first draw on its *prior knowledge* (e.g., “older people have higher heart disease risk”) instead of blindly fitting spurious correlations present in just a few rows. |
| **Response instruction** | • Exact JSON‑like template for the answer <br>• Syntax guidelines for each rule (e.g., use `>` or `<=` when appropriate) | Guarantees machine‑readable output so that downstream parsing can be automated without fragile string fiddling.|

### 1️⃣ Basic Information Description

Even before any reasoning begins, the LLM must understand *what* it’s being asked about:

- **Task description** is phrased as a question such as  
  “*Does this patient’s record indicate chronic heart failure? Yes or no.*”
- **Feature definitions** are supplied verbatim from the dataset metadata (“`age` – integer years”, “`smoking_status` – categorical {never, former, current}”).  
- **Few‑shot demonstrations** are serialized exactly as prior work does:
  \[
  \text{Serialize}(x^i,y^i,F)=\text{``}f_1\text{ is }x^i_1.\dots f_d\text{ is }x^i_d.\ \text{Answer:}\ y^i\text{''}
  \]
  This anchors the LLM in the concrete format it will need to emit later.

### 2️⃣ Reasoning Instruction – The Two‑Step Dance

#### Step 1 – *Domain Understanding*  
The prompt says something like:

> “First, think about which features are likely related to chronic heart failure based on general medical knowledge.”

Crucially, *no example rows are referenced yet.* This pushes the LLM to surface its internal knowledge base (“age and hypertension are risk factors”) rather than latching onto accidental patterns in only four training points.

#### Step 2 – *Rule Extraction from Data*  
After summarizing its intuition, the LLM is told:

> “Now look at the given examples and combine them with your intuition to write ten decision rules for each class.”

By separating these steps:

- The model avoids over‑fitting trivial coincidences (e.g., discovering that `patient_id = 123` predicts “yes” merely because that ID appears in all positive demos).  
- It can incorporate domain expertise that may not be represented in such low‑shot data (e.g., “smoking_status = current → higher risk”).

The number of rules per class is fixed (10 by default) to keep prompts short and keep downstream models manageable.

### 3️⃣ Response Instruction – Making Parsing Easy

The final part tells the LLM exactly how its answer should look:

```json
{
  "class_A": [
    "age > 65",
    "cholesterol >= 200 AND smoker = yes",
    ...
  ],
  "class_B": [
    "age <= 45",
    "blood_pressure < 120"
    ...
  ]
}
```

A strict template prevents variations such as swapping “greater than” for `>` or introducing ambiguous punctuation—issues that would otherwise break simple parsers.

---

## From Natural Language Rules to Binary Features

Even with disciplined formatting there can be minor syntactic noise (“greater than” instead of `>`). FeatLLM solves this by **leveraging the LLM itself as a code generator**:

1. Feed each rule set back into an LLM prompt asking it to emit Python code that implements those logical checks (`def check_rule(row): return row["age"] > 65`).  
2. Execute the generated code with Python’s `exec()` function on every row of the original table.  
3. For each rule we obtain one binary column (`z_k^i ∈ {0,1}^R`) where `R` is the number of rules per class and `k` indexes classes.

Thus every sample turns into a sparse vector of rule satisfactions ready for learning.

---

## Learning from Rules – A Tiny Linear Model

Once we have binary rule features we fit an ultra‑lightweight classifier:

\[
\begin{aligned}
\text{logit}_k^i &= \max(\mathbf{w}_k ,0)\cdot \mathbf{z}_k^i ,\\[4pt]
\mathbf{p}^i &= \operatorname{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big),
\end{aligned}
\]

where:
- $\mathbf{w}_k$ are non‑negative trainable weights learned via cross‑entropy on the few labeled rows,
- $\mathbf{p}^i$ yields class probabilities at inference time.

Because $\mathbf{z}_k^i$ already encode high‐level domain knowledge, even with only $k=4$–$8$ shots this linear model attains performance comparable to fully trained tree ensembles on many benchmarks.

---

## Ensembling & Bagging – Guarding Against Variability

Two sources of randomness make each rule set slightly different:

1. **Temperature sampling** when querying the LLM (default $T=0.5$). Higher temperature yields diverse rule proposals.
2. **Permutation of few‑shot examples**, which can subtly swing the LLM’s inference.

To capitalize on this diversity FeatLLM repeats the entire pipeline $T$ times (often $T=20$) and averages predicted probabilities across trials—a classic ensemble technique akin to random forests but operating at the *rule generation* level instead of tree construction.

Additionally, **feature bagging** randomly selects subsets of columns when building prompts—this keeps prompt length within model limits even for datasets with hundreds of attributes and further decorrelates individual learners.

---

## Why Two-Step Reasoning Works Better Than Direct Prediction

Existing LLM‐based tabular methods typically feed every test row through an LLM (“Here’s my record; what’s the label?”). This approach suffers from three practical issues:

| Issue | Direct Prediction | FeatLLM’s Two‑Step Approach |
|-------|-------------------|------------------------------|
| **Latency** | One API call per row → seconds per thousand rows | Only dozens of calls total during feature engineering |
| **Prompt Length** | Full row serialization plus task description may exceed context window | Prompt only contains meta‐information + few examples; no per‐row data |
| **Spurious Correlation Risk** | Model can latch onto accidental patterns in tiny training sets | Step 1 forces reliance on prior knowledge before seeing data; reduces overfitting |

Empirically, FeatLLM outperforms baselines such as TabLLM and STUNT by roughly $10\%$ AUC on average across 13 diverse datasets—particularly shining on high‐dimensional tables where prompt overflow previously crippled end‐to‐end methods.

---

## A Walkthrough Example

Imagine we want to predict whether a hospital patient will develop chronic heart failure (`CHF`). The dataset includes columns `age`, `blood_pressure`, `smoker`, and `ejection_fraction`.  

### Prompt Skeleton

```
Task: Does this patient's record indicate chronic heart failure? Yes or No.
Features:
 - age: integer years
 - blood_pressure: integer mmHg
 - smoker: {yes,no}
 - ejection_fraction: integer percentage
Examples:
 age is 72 . blood_pressure is 150 . smoker is yes . ejection_fraction is 30 . Answer: Yes
 age is 45 . blood_pressure is 120 . smoker is no . ejection_fraction is 60 . Answer: No
...
Reasoning:
 Step1: Identify which features you think matter based on medical knowledge.
 Step2: Using those insights plus above examples, write ten rules for each class.
Response format:
{
 "Yes": ["<rule1>", "<rule2>", ...],
 "No": ["<rule1>", "<rule2>", ...]
}
```

### Step 1 Output (generated by LLM)

> “Age and reduced ejection fraction are strong risk factors for CHF; high blood pressure also contributes.”

### Step 2 Output (rules)

```json
{
 "Yes": [
   "age > 65",
   "ejection_fraction < 35",
   "blood_pressure >= 140 AND smoker = yes",
   "...(7 more rules)..."
 ],
 "No": [
   "age <= 50",
   "ejection_fraction >= 55",
   "...(8 more rules)..."
 ]
}
```

The second pass transforms these strings into Python functions (`def r1(row): return row["age"] > 65`) which are executed over every patient record yielding binary columns like `r_yes_1`, `r_no_3`, etc. Finally we train $\mathbf{w}$ on our four labeled patients; perhaps we discover `ejection_fraction < 35` carries most weight while `blood_pressure >=140 AND smoker=yes` adds modest importance.

At inference time predicting CHF for thousands of patients simply means evaluating these logical conditions—a handful of cheap operations per row—and applying learned weights—a dot product followed by softmax.

---

## Takeaways

- **Two-step prompting mimics expert reasoning:** first build *domain intuition*, then *translate* that intuition plus concrete examples into actionable decision rules.
- **Rule extraction sidesteps costly per‑sample LLM calls** while still harvesting rich prior knowledge from massive language models.
- **Simple downstream models suffice:** once you have high-quality binary features, even linear regression reaches state-of-the-art few-shot performance.
- **Ensembling via temperature & bagging yields robustness** without exploding API costs or violating context windows.
- **Interpretability comes free:** each binary feature corresponds directly to an English rule that a practitioner can inspect and validate.

FeatLLM shows that large language models need not remain opaque black boxes; with thoughtfully engineered prompts they can act as *knowledgeable feature engineers*, turning natural language insight into machine learning-ready representations—all in just a couple of API calls.

# Turning Natural‑Language Rules into Machine‑Ready Features  

**How FeatLLM translates LLM‑generated textual rules into executable Python code, builds binary indicators for every record, and why this makes downstream models both simple and powerful.**  

---  

## The motivation: From “black‑box” predictions to “feature engineering”

Most recent methods that apply Large Language Models (LLMs) to tabular data feed every test sample through the LLM at inference time.  
While this can work, it is costly—each prediction requires a separate API call—and it quickly hits prompt‑size limits when tables have many columns.  

FeatLLM takes a different path. It asks the LLM **once** (or a handful of times) to **explain** what makes an example belong to each class. The output is a set of human‑readable “rules”, e.g.,  

> *If age > 60 **and** cholesterol > 200 then predict heart disease.*  

Once those rules are available we can treat them as **new features**: a binary flag tells us whether a given row satisfies each rule. A downstream model can then operate on this compact representation without ever calling the LLM again.  

---

## Step 1 – Prompting the LLM for textual rules  

The prompt is split into three logical blocks:

1. **Basic information** – task description, feature names/types, and a few labeled examples serialized as  
   ```
   f1 is <value>. … f_d is <value>. Answer: <label>
   ```  
2. **Reasoning instruction** – coaxing the model first to think about causal relationships between features and the target (using its world knowledge), then to derive concrete decision rules from the given examples.  
3. **Response instruction** – specifying an exact format for each rule (e.g., “IF <feature> > <threshold> THEN …”) so that later parsing is feasible.  

The prompt forces the model to output a *fixed* number of rules per class (10 in the paper) which balances informativeness against prompt length.  

---

## Step 2 – Turning natural language into executable code  

### Why parsing by hand is hard  

Even with strict response instructions, LLMs may vary their syntax:

* “>” may appear as “greater than”,  
* numeric literals may be spelled out (“one hundred”),  
* logical connectors can be written as “AND”, “and”, or even “&”.  

A handcrafted regex parser would quickly break on such variations.

### Using the LLM as a parser  

FeatLLM solves this by *re‑prompting* the same model with a **code‑generation request**:

```
You are given a list of decision rules:
1) Age greater than 60 AND Cholesterol > 200
2) ...
Write a Python function `check_rule(sample)` that returns 1 if the
sample satisfies the rule and 0 otherwise.
```

The request includes:

* The function signature (`def check_rule(sample):`),
* A description of `sample` (a dictionary mapping feature names → values),
* The list of rules extracted in Step 1.

The LLM returns ready‑to‑run Python code that explicitly compares feature values using ordinary operators (`>`, `<`, `==`, etc.). The returned string is fed to Python’s `exec()` function, which defines the function in the current runtime environment. This approach leverages the LLM’s own knowledge of programming syntax and makes it tolerant to linguistic variations in its own output.

---

## Step 3 – Generating binary features for every record  

For each class \(k\) we obtain a set of \(R\) rules \(\{r_{k,1},\dots,r_{k,R}\}\).  
Given a data point \(\mathbf{x}^i\), we evaluate every rule with the compiled functions:

\[
z_{k,r}^i = 
\begin{cases}
1 & \text{if } r_{k,r}\text{ is satisfied by }\mathbf{x}^i ,\\[4pt]
0 & \text{otherwise}.
\end{cases}
\]

Collecting all \(R\) outcomes yields a binary feature vector  
\(\mathbf{z}_k^i \in \{0,1\}^{R}\).  
Repeating this for all classes creates a concise representation that captures both **domain knowledge** (the rule logic) and **data‐driven insight** (the particular thresholds discovered from the few-shot examples).

---

## Step 4 – A tiny linear model does the heavy lifting  

With these engineered features in hand we only need a lightweight classifier. FeatLLM adopts a bias‑free linear model whose logit for class \(k\) is

\[
\text{logit}_k^{\,i}= \max(\mathbf{w}_{k},0)\cdot \mathbf{z}_{k}^{\,i},
\]

where \(\mathbf{w}_{k}\in\mathbb{R}^{R}\) are trainable non‑negative weights learned by minimizing cross‑entropy on the few labeled samples.  
The final class probabilities are obtained by softmax:

\[
\mathbf{p}^i = \operatorname{Softmax}\bigl([\text{logit}_1^{\,i},\dots,\text{logit}_c^{\,i}]\bigr).
\]

Because there are only \(c\times R\) parameters (often under one hundred), training converges within seconds even with just 4–8 labeled instances. Inference reduces to a handful of dot products—orders of magnitude faster than contacting an LLM per sample.

---

## Robustness tricks: Ensemble + bagging  

A single set of generated rules can still contain occasional noise or miss some informative patterns. FeatLLM mitigates this by:

* **Temperature sampling:** generating diverse rule sets across multiple runs,
* **Random demo ordering:** shuffling few-shot examples before each query,
* **Feature/instance bagging:** each trial sees only a random subset of columns or rows, which keeps prompts short enough for large tables,
* **Ensembling:** averaging softmax outputs from \(T\) independent trials (the paper uses \(T=20\)).  

This ensemble behaves like classic bagged decision stumps—weak learners compensate each other—while preserving FeatLLM’s low inference cost because all heavy lifting happens *once* per trial at training time.

---

## Why this step matters

| Aspect | Traditional end‑to‑end LLM inference | FeatLLM’s rule‑to‑feature pipeline |
|---|---|---|
| **API calls at test time** | One call per sample → high latency & cost | Zero calls after feature extraction |
| **Prompt length constraints** | Serialized rows quickly exceed token limits | Rules are generated once; bagging controls size |
| **Model complexity** | Large transformer needed for accurate predictions | Simple linear weights suffice |
| **Interpretability** | Hard to extract why a prediction was made | Each binary feature corresponds directly to an English rule |
| **Performance in few‑shot regime** | Often unstable or outperformed by classic models | Consistently improves AUC by ~10 % over TabLLM/STUNT |

Empirically, across 13 benchmarks ranging from classic UCI datasets (Adult, Credit-g) to newly released tables never seen during pretraining (Cultivars, NHANES), FeatLLM matches or exceeds strong baselines while requiring only 4–8 labeled points—equivalent performance that traditional methods need 32 shots to achieve.

---

## Takeaways

1️⃣ **LLMs excel at reasoning**, not at raw number crunching. By asking them *why* rather than *what*, we harvest high‑level decision logic that can be reused indefinitely.  

2️⃣ **Parsing those textual insights with another LLM call avoids brittle hand‑crafted parsers**, ensuring robustness against linguistic variation while keeping implementation simple (`exec()` on generated code).  

3️⃣ **Binary rule indicators transform any tabular dataset into an interpretable feature space**, enabling ultra‑lightweight downstream models that train in seconds and predict instantly.  

4️⃣ **Ensemble + bagging neutralizes occasional mistakes**, turning many weak “rule learners” into a strong collective predictor—mirroring classic ensemble theory but applied at the level of language–generated features.  

In short, FeatLLM shows how you can turn natural‐language explanations from an LLM into machine‐ready features, achieving state‑of‑the‑art few‑shot performance without sacrificing speed or interpretability. The approach bridges massive pretrained knowledge with decades­‑old linear modeling tricks—making advanced AI accessible even when data and compute budgets are tight.



# Why FeatLLM Slashes Inference Costs Compared to Traditional LLM Pipelines  

*Large language models are powerful knowledge bases, but calling them for every row in a table can be prohibitively expensive. FeatLLM flips the script: it asks the LLM **once** to engineer useful features, then lets a tiny linear model do all the heavy lifting at prediction time.*

---  

## The hidden price tag of “end‑to‑end” LLM tabular pipelines  

Recent work such as **In‑context learning**, **TABLET**, and **TabLLM** treats an LLM as the predictor itself:

1. Serialize a single data row together with a task description and column names into a prompt.  
2. Send that prompt to the model through an API call (or an on‑premise GPU).  
3. Parse the answer back into a class label or probability.  

Because step 2 happens *for every test sample*, the runtime grows linearly with the size of the deployment set. Even a modestly cheap model such as GPT‑3.5 costs several cents per thousand tokens; when you need millions of predictions this quickly dwarfs any budget allocated for training data collection. Moreover, each call adds network latency (often tens‐to‐hundreds of milliseconds) which makes real‑time use cases—fraud detection, clinical triage, ad bidding—essentially impossible.

The fundamental bottleneck is **per‑sample reliance on the LLM** rather than exploiting its knowledge *once* up front.



## FeatLLM’s alternative view: “Feature engineering + tiny predictor”

FeatLLM treats the LLM purely as an *expert feature engineer*. The workflow splits into two clearly separated phases:

| Phase | What happens | Who does it? |
|------|--------------|--------------|
| **Feature generation** | The model receives a *single* prompt describing the task, column definitions, and a handful of labeled examples (< k shots). It returns **rules**—human‑readable conditions that characterize each class (e.g., “`Age > 65 AND BloodPressure ≥ 140`”). | Large Language Model (e.g., GPT‑3.5) |
| **Prediction** | Each rule is turned into a binary indicator (`1` if the row satisfies it, else `0`). A lightweight linear model consumes these indicators and produces class probabilities via a single matrix multiply & softmax operation. | Conventional ML code (no LLM needed) |

Because step 1 runs **once per problem**—not once per row—there are no additional API calls during deployment.



## Inside FeatLLM’s feature generation  

### Prompt design  
A carefully crafted prompt guides the LLM through two reasoning stages:

1. **Problem understanding** – The model draws on its world knowledge (“older patients tend to have higher cardiovascular risk”) without looking at any training rows.
2. **Rule deduction** – Using the few labeled rows supplied as demonstrations, it writes down *ten* explicit rules per class.

The prompt also enforces a structured response format so that downstream parsing is deterministic even when the model varies its wording (“greater than” vs “>”).

### From natural language rules to binary columns  
The raw textual rules contain variations (“≥”, “greater than”, “is older than”). Rather than hand‐crafting parsers for every possible glitch, FeatLLM asks the same or another LLM *once more* to emit short Python functions that implement each rule safely (`exec()` runs them). This step automatically normalizes noisy phrasing into executable Boolean expressions.



## Training the tiny downstream model  

Let  

* $\mathbf{z}_k^i \in \{0,1\}^R$ be the binary vector for sample $i$ indicating whether it satisfies each of the $R$ rules belonging to class $k$,  
* $\mathbf{w}_k \in \mathbb{R}^R$ be trainable non‑negative weights learned from the $k$‑shot data.

The logit for class $k$ is

\[
\text{logit}_k^i = \max(\mathbf w_k ,0)\;\cdot\;\mathbf z_k^i,
\]

and probabilities are obtained via softmax

\[
\mathbf p^i = \operatorname{Softmax}\bigl([\text{logit}_1^i,\dots,\text{logit}_c^i]\bigr).
\]

Training simply minimizes cross‑entropy over the few labeled rows—no backpropagation through the massive LLM is required.


## Why this design shaves off inference cost  

| Aspect | Traditional LLM pipeline | FeatLLM |
|-------|--------------------------|---------|
| **Number of API calls** | One call **per test instance** → $O(N)$ | One batch call for rule extraction plus one optional call for code generation → `≈30` calls total regardless of $N$ |
| **Runtime per prediction** | Hundreds of ms (network + model compute) × $N$ | < 1 ms after binary features are ready (just vector dot product & softmax) |
| **Memory / Prompt length** | Must fit full serialized row + all column names → often exceeds context window on wide tables | Uses *bagging*: randomly subsamples columns/features before each generation step so prompts stay comfortably within limits |
| **Scalability** | Limited by rate limits & latency of external APIs | Scales linearly with hardware resources once features are materialized |

Empirically, on the Adult dataset with only 16 labeled rows (`k=4` shots repeated four times), **FeatLLM’s total inference time was comparable to plain logistic regression**, while classic in‑context methods took several seconds—a difference orders of magnitude larger when $N$ reaches thousands.



## Ensemble & bagging keep performance high without hurting cost  

FeatLLM does not rely on a single rule set:

* It runs the whole pipeline $T$ times (`T=20` in experiments) using higher temperature sampling — different random seeds yield diverse rules.
* Each trial may also bag a random subset of columns or training rows before prompting.
* Final probabilities are averaged across trials (`self-consistency`).

Because all $T$ rule sets are generated **offline**, ensembling adds virtually no extra latency during serving.


## Bottom line: cheap inference without sacrificing accuracy  

*Average performance*: Across 13 heterogeneous tabular benchmarks,
- FeatLLM achieved **~10 % higher AUC** than strong baselines such as TabLLM and STUNT,
- while requiring only **few-shot training** (`k=4–8`) and **no per-sample LLM calls**.

Thus you get *both* superior predictive quality *and* dramatically lower serving costs—a rare win in machine learning.


## Takeaways  

1. **Separate knowledge extraction from prediction** – let an LLM write human‐readable rules once; let conventional ML handle fast scoring thereafter.
2. **Feature engineering becomes an API call budget item**, not an ongoing expense.
3. **Bagging & ensembling offset prompt length limits** without reintroducing per-instance latency.
4. Practically you go from “pay‐per‐prediction” pricing models (often cents per thousand rows) down to negligible compute costs – enabling real‐time tabular AI in finance, healthcare, ad tech, etc.

FeatLLM demonstrates that large language models are most valuable when used as *knowledge distillers*, not as brute-force predictors every time you need an answer.

# Bagging and Ensembling to Beat Prompt Length Limits

*How FeatLLM squeezes high‑dimensional tables into tiny prompts while still harvesting the full predictive signal.*

---

## Why Prompt Length Matters for Tabular Learning

Large language models (LLMs) such as GPT‑3.5 can act as knowledge‑rich “feature engineers”: given a description of a classification task they can articulate rules like “age > 60 **and** blood‑pressure > 140 predicts heart disease”.  
The usual workflow is to serialize **all** columns of a table into a textual prompt and let the LLM produce a prediction for each sample.  

Unfortunately:

* The context window of current APIs is limited (≈ 4 K tokens for GPT‑3.5‑turbo).  
* Datasets with dozens or hundreds of attributes easily exceed that budget—especially when we also need a task description, feature definitions, and a few exemplars.  
* Running an LLM inference **per sample** inflates latency and cost dramatically.

FeatLLM sidesteps both issues by treating the LLM **once** as a rule generator instead of an end‑to‑end predictor, and it does so through **feature bagging** plus **ensemble averaging**.

---

## From Table to Rules – The Core FeatLLM Pipeline

1. **Prompt construction** – The prompt has three parts:  
   *Basic information*: task statement, natural‐language feature names & definitions, and a handful of serialized examples (`f₁ is 23 … f_d is “yes”. Answer: Yes`).  
   *Reasoning instruction*: a two‑step chain–of‑thought that first asks the model to infer causal tendencies between features and the target (using only prior knowledge), then to deduce concrete decision rules using the few examples.  
   *Response instruction*: explicit formatting guidelines so that each rule appears as a simple logical condition (`feature > value`, `category == “X”`, etc.).
2. **Rule extraction** – The LLM returns **R = 10** class‑specific rules (the same number for every class).  
3. **Parsing & feature creation** – A secondary call parses those natural‐language conditions into executable Python code (`exec`). Each rule becomes a binary indicator \(z_{k}^{i} \in \{0,1\}\) telling whether sample \(i\) satisfies rule \(k\).  
4. **Linear scoring** – For each class we learn non‑negative weights \(\mathbf{w}_{k}\) in a tiny linear model:  

   \[
   \text{logit}_{k}^{i}= \max(\mathbf{w}_{k},0)\cdot\mathbf{z}_{k}^{i},\qquad 
   \mathbf{p}^{i}= \text{Softmax}\big([\text{logit}_{1}^{i},\dots,\text{logit}_{c}^{i}]\big)
   \]

   The weights are fitted on the available \(k\)-shot training set (e.g., \(k=4\)) via cross‑entropy loss.

So far this already eliminates per‑sample LLM calls: after rule generation we only need cheap linear inference.

---

## The Prompt Bottleneck Reappears When Tables Are Huge

If we feed *all* \(d\) columns into step 1 above, even with compact serialization the token count can blow past the context window—particularly on datasets like **Communities** or **Myocardial**, which have more than 100 attributes. Simply truncating columns would discard useful signal.

**Enter feature bagging:** randomly sample a manageable subset of columns for each LLM query while keeping every query under the token limit.

### How Feature Bagging Works

| Step | What We Do |
|------|------------|
| **(a) Column sampling** | Choose \(m < d\) columns uniformly at random (or via importance heuristics). |
| **(b) Prompt building** | Assemble the basic information part *only* with those \(m\) columns plus the fixed task description and few‐shot examples. |
| **(c) Rule generation** | Ask the LLM to produce \(R\) rules per class based on this reduced view of the data. |
| **(d) Binary features** | Parse the returned rules back into binary indicators that involve only the sampled columns.|

Because each mini‑prompt fits comfortably inside the API’s context window, we can run many such queries across different column subsets without hitting any size ceiling.

### Why Bagging Helps Beyond Token Savings

* **Noise reduction:** irrelevant or highly noisy columns are often omitted from any single bag, decreasing their chance of contaminating rule generation.  
* **Coverage:** Over many bags (`T` repetitions), every original column gets represented in at least one query, ensuring that no useful predictor is permanently ignored.  
* **Robustness:** Rules derived from distinct column subsets act like weak learners; their errors tend not to correlate, which sets us up nicely for ensembling.

---

## Ensemble Averaging – Reconstructing the Whole Signal

After we repeat the whole bag–generate–parse cycle `T` times (the paper uses `T = 20`), we end up with `T` independent linear scorers:

\[
\mathbf{p}^{i[t]} = \text{Softmax}\big([\text{logit}_{1}^{i[t]},\dots,\text{logit}_{c}^{i[t]}]\big),
\qquad t = 1,\dots,T .
\]

The final prediction is simply the average:

\[
\boxed{\;\hat{\mathbf{p}}^{i}= \frac{1}{T}\sum_{t=1}^{T}\mathbf{p}^{i[t]}\;}
\]

Ensemble averaging provides two crucial benefits:

1. **Self‑consistency amplification:** Rules that appear across many trials are likely correct; averaging boosts their impact while diluting idiosyncratic mistakes from any single bag.\*
2. **Full–dimensional recovery:** Even though each trial sees only \(m\) columns, aggregating over `T` bags yields predictions that effectively incorporate information from all \(d\) original features—without ever exceeding token limits in any single call.*

> *The authors observed that increasing `T` improves performance up to about 20 trials; beyond that gains plateau while API cost rises.*

---

## Empirical Evidence That Bagging + Ensembling Works

| Dataset            | Avg AUC (FeatLLM) | Avg AUC (Next Best) |
|--------------------|-------------------|----------------------|
| Adult              | 0.92 ± 0.01       | 0.86 ± 0.02 (XGBoost)|
| Blood              | 0.84 ± 0.03       | 0.73 ± 0.04 (TabLLM)|
| Communities        | 0.78 ± 0.04       | 0.66 ± 0.05 (STUNT) |
| Myocardial         | 0.81 ± 0.02       | 0.70 ± 0.03 (In‑context)|

*Results are averaged over three random splits with \(k=4\) shots.*

Key observations from the paper’s ablation study:

* Removing **bagging** (-Bagging) drops AUC by ≈ 2–3 points across datasets because fewer columns are ever seen by any trial.
* Dropping **ensembling** (-Ensemble) reduces AUC similarly—single-bag models become brittle.
* When both are omitted together, performance collapses close to baseline logistic regression trained on raw features alone.

In addition, an experiment that spiked irrelevant Adult columns into the Heart dataset showed that FeatLLM’s AUC fell far less than competing methods—evidence that bags naturally shield against spurious correlations.

---

## Practical Guidelines for Replicating Bagged FeatLLM

* **Choose `m` wisely:** Ensure `m × avg_token_per_column + overhead ≤ context_limit`. For GPT‑3.5 you typically stay under 800 tokens total; this often translates to `m ≈ 30–40` when column names/descriptions are brief.
* **Set `R = 10` rules per class:** This number balances expressive power against prompt bloat; experiments showed diminishing returns beyond ten.
* **Use moderate temperature (`τ = 0.5`)**: High enough for diverse rule sets but low enough to keep syntax parsable.
* **Randomize few‑shot order every trial:** Small changes in demonstration ordering noticeably affect which rules surface—a cheap source of diversity.
* **Ensemble size around `T = 20`:** Gives near‑optimal performance without exploding API usage; you can monitor validation AUC while adding more trials if budget allows.
* **Post‑training filter:** After learning weights \(\mathbf{w}_k^{[t]}\), discard any rule whose weight falls below a small threshold (e.g., `0.1`). This cleans up noisy rules automatically.

All these knobs are adjustable via simple configuration files; there is no need for gradient updates inside the LLM itself—only standard Adam updates on a tiny linear classifier.

---

## Bringing It All Together

FeatLLM demonstrates that you don’t have to sacrifice high dimensionality just because your LLM has a limited context window:

1️⃣ **Feature bagging** shrinks each prompt enough for today’s APIs while still exposing the LLM to varied slices of the data space.  
2️⃣ **Ensemble averaging** stitches those slices back together, letting us reap information from every original column without ever loading them all at once.<br>
3️⃣ The result is a lightweight downstream model—a nonnegative linear scorer—that runs at inference speeds comparable to classic logistic regression but enjoys an AUC boost of roughly *10 %* over existing few‑shot baselines.

The approach works even when you only have four labeled examples—an attractive regime for domains like finance or healthcare where labeling is expensive yet prior knowledge lives abundantly inside modern LLMs.

If you’re curious to try it yourself, an anonymized implementation is available at:

```
https://github.com/Sungwon-Han/FeatLLM
```

Feel free to experiment with different column sampling strategies (e.g., stratified by type), adjust temperature for greater diversity, or replace GPT‑3.5 with another code-capable model—all without changing the core bagged‐ensemble recipe.

---

### Bottom Line

Prompt length limits no longer have to be showstoppers for LLM‐augmented tabular learning. By combining *feature bagging* with *ensemble averaging*, FeatLLM extracts compact yet powerful rule‐based features from an LLM once per dataset—and then makes lightning‐fast predictions thereafter—while faithfully preserving signal from high‑dimensional tables.

Give it a spin on your next low‐shot classification problem; you might find that fewer tokens translate into better performance!



# Few‑Shot Tabular Learning: How FeatLLM Outperforms Classic Methods

## Setting the Stage

Tabular data—think spreadsheets of medical records, credit‑card logs, or sensor readings—still power most real‑world analytics. Yet training a high‑performing model on a **handful** of labeled rows is notoriously hard. Classical learners such as logistic regression or XGBoost need dozens (or hundreds) of examples to avoid chasing spurious patterns, while recent approaches that call large language models (LLMs) for every sample quickly become computationally prohibitive.

Enter **FeatLLM**. Instead of asking an LLM “what is the label for this row?” it asks the LLM “what **rules** would decide the label?” The LLM spits out human‑readable conditions (e.g., “age > 65 AND cholesterol > 200”), which are then turned into binary features. A tiny linear model learns how much each rule should count. The whole pipeline requires only a few API calls at training time and none at inference time.

## What Was Tested?

The authors put FeatLLM head‑to‑head with a battery of baselines on **13** publicly available tabular datasets spanning finance, healthcare, agriculture, and synthetic tasks. The key competitors were:

| Category | Methods |
|----------|---------|
| Conventional ML | Logistic Regression (LogReg), XGBoost, Random Forest |
| Unlabeled‑data tricks | SCARF, STUNT |
| LLM‑centric | In‑context learning, TABLET, TabLLM |
| Synthetic pre‑training | TabPFN |

All experiments were done in a **few‑shot regime**: either $2$, $4$, $8$, or $32$ labeled examples per class. For fairness each method received exactly the same few-shot slices. Performance was measured with the area under the ROC curve (AUC).

## Bottom‑Line Results

### 1. FeatLLM is consistently on top

- Across all 13 datasets FeatLLM ranked **first or second** in terms of AUC.
- On average it beat the strongest LLM baseline (TabLLM) by roughly **10 % absolute AUC**.
- Even when competing against well‑tuned XGBoost or Random Forest trained on $32$ shots, FeatLLM using only **$4$ shots** achieved comparable scores.

### 2. Classic baselines need far more data

| Shots per class | LogReg AUC (avg.) | XGBoost AUC (avg.) | FeatLLM AUC (avg.) |
|-----------------|-------------------|--------------------|---------------------|
| 2               | 0.71              | 0.74               | **0.80**            |
| 4               | 0.73              | 0.77               | **0.83**            |
| 8               | 0.75              | 0.79               | **0.85**            |
| 32              | 0.78              | 0.82               | **0.86**            |

*Numbers are illustrative averages taken from the paper’s tables; exact values vary per dataset.*  
The takeaway: **FeatLLM extracts enough signal from a handful of rows that conventional learners would need almost an order of magnitude more labels to catch up.**

### 3. LLM‑centric baselines struggle with many features

Methods that feed the whole table into an LLM at inference time—plain in‑context learning, TABLET, TabLLM—saw sharp drops on datasets with more than ~30 columns (e.g., *Communities* with 100+ attributes). Their prompts exceed context windows or force the model to consider irrelevant columns, leading to degraded accuracy.

By contrast, FeatLLM’s use of **feature bagging** caps prompt size: each LLM query sees only a random subset of columns and examples. The ensemble of many weak rule generators compensates for any missing information.

## Why Does FeatLLM Win? Insights from Ablations

The authors stripped away components to see what mattered most:

| Removed component | Impact on AUC (average Δ) |
|-------------------|---------------------------|
| No linear‐weight tuning (`-Tuning`) | −2–3 % |
| No ensemble (`-Ensemble`)          | −4–5 % |
| No feature descriptions (`-Description`) | −3–6 % (especially at $2$–$4$ shots) |
| No two‑step reasoning (`-Reasoning`)   | −5–7 % |

- **Weight tuning** matters more when we have *more* shots, because the linear model can better learn which rules truly help.
- **Reasoning instructions** and **feature descriptions** are critical when data are scarce—they guide the LLM to draw on its world knowledge rather than latch onto random noise.
- The **ensemble** consistently lifts performance regardless of shot count by averaging out occasional bad rules and expanding coverage across columns.

## Speed & Cost: Not Just Accuracy

Inference latency is where many LLM pipelines choke:

| Method        | Training API calls* | Inference time per row |
|---------------|----------------------|------------------------|
| FeatLLM       | ~30 calls total      | ~1 ms (linear dot product) |
| In‑context    | —                    | ~150 ms (full LLM pass) |
| TABLET        | —                    | ~180 ms |
| TabLLM        | —                    + fine‑tuning on GPU | >200 ms |

\*Each call corresponds to one rule‐generation request to GPT‑3.5; they can be parallelized across models/GPUs.

Because FeatLLM’s downstream predictor is just a tiny linear model, prediction is as cheap as traditional tabular methods while still leveraging sophisticated LLM reasoning for feature creation.

## A Quick FAQ

1. **Do I need any fine‑tuning?**  
   No. All you need is API access to an LLM (the authors used GPT‑3.5). The only trainable part is a small linear layer solved with standard gradient descent.

2. **What if my table has hundreds of columns?**  
   The built‑in bagging randomly selects subsets of columns for each rule generation round, keeping prompts within context limits while still covering most attributes across ensembles.

3. **Is interpretability a side effect?**  
   Absolutely—each binary feature corresponds to a natural‐language rule (“blood pressure > 140”). You can inspect which rules carry high learned weight and gain insight into the model’s decision logic.

## Bottom Line

FeatLLM demonstrates that an LLM can be far more efficient than a black‑box predictor if we ask it to act as a *feature engineer* instead of an end‑to‑end classifier. By extracting compact rule‑based features from just a few labeled examples and then feeding them into a trivial linear model, FeatLLM:

- Beats classic learners even when they see many more labels,
- Outperforms other LLM‐based methods across a wide variety of domains,
- Keeps inference cheap enough for production,
- Offers interpretable rules that bridge data science and domain expertise.

For anyone wrestling with sparse labels on structured data—whether in finance, healthcare, or any industry where every annotation costs money—FeatLLM provides a practical and powerful shortcut: let the language model do the heavy lifting up front, then let a simple model reap the benefits at lightning speed.



# Real‑World Impact: Using FeatLLM in Finance and Healthcare Without Massive Labels  

Large language models (LLMs) have become surprisingly good at reasoning about problems they have never seen before. The recent **FeatLLM** framework shows that we can turn this reasoning power into a practical feature‑engineering assistant for tabular data—especially when only a handful of labeled examples are available. Below we walk through how FeatLLM works and why it matters for two high‑impact domains: finance and healthcare.

## Why Feature Engineering Still Bottlenecks Tabular Learning  

Most real‑world predictive systems—credit‑risk scores, disease classifiers, churn detectors—rely on carefully crafted features. Traditionally this step demands domain experts or extensive trial‑and‑error with algorithms such as gradient boosting. In low‑shot settings (e.g., only a dozen annotated loan applications or patient records), standard models either overfit or simply cannot learn meaningful patterns.

Enter LLMs. Because they have been trained on massive corpora that include medical literature, financial regulations, and countless other sources of structured knowledge, an LLM already “knows” that **age**, **blood pressure**, or **debt‑to‑income ratio** are often predictive of health or credit outcomes. FeatLLM extracts exactly that knowledge as human‑readable rules and converts them into new binary features—without ever having to fine‑tune the LLM or send each test sample through it at inference time.

## A Bird’s‑Eye View of FeatLLM  

1. **Prompt the LLM with context**  
   - The prompt contains three parts:  
     *a.* A concise task description (e.g., “Predict whether a loan applicant will default”).  
     *b.* Natural‑language definitions of each column (“`age` is the applicant’s age in years”).  
     *c.* A few annotated examples serialized as “`age is 45 … Answer: No`”.  

2. **Two‑step reasoning**  
   - **Step 1:** The model draws on its prior knowledge to infer which columns are causally related to the target (“older applicants tend to default more”).  
   - **Step 2:** Using the few examples as anchors, the model formulates a fixed number of decision rules per class (the paper uses ten rules per class). An example rule might be “`age > 60 AND credit_score < 600`”.

3. **Parse rules into code**  
   - Even though the raw text can be noisy (“greater than” vs “>”), FeatLLM asks the same LLM to generate a short Python function that evaluates each rule on a row. The function is executed with `exec()` to produce **binary features** (`1` if a rule fires, `0` otherwise).

4. **Train a tiny downstream model**  
   - The binary feature vector \( \mathbf{z}_k \) for class \(k\) is fed into a non‑negative linear model:  
     \[
     \text{logit}_k = \max(\mathbf{w}_k ,0)\cdot \mathbf{z}_k ,\qquad 
     \mathbf{p} = \operatorname{softmax}([\text{logit}_1,\dots,\text{logit}_c]).
     \]  
   - Only a few gradient steps are needed because there are at most \(10\times c\) weights.

5. **Ensemble via bagging**  
   - The whole pipeline is repeated many times (the authors use \(T=20\) ensembles) with random subsets of features and shuffled example orders. Final predictions are obtained by averaging softmax outputs across ensembles—greatly reducing variance and handling datasets that exceed the LLM’s context window.

The result? A model that **requires only API access to an LLM**, runs inference without any additional LLM calls, and sidesteps prompt‑length limits through bagging.

## Finance – Building Credit Models with a Handful of Labels  

Imagine a regional bank launching a new micro‑loan product for gig workers. Collecting hundreds of labeled defaults would take months and cost thousands of dollars in manual review. Here’s how FeatLLM can cut that overhead:

| Step | What the bank does |
|------|-------------------|
| 1️⃣ | Write a short task description (“Will this applicant repay within 12 months?”) and provide plain English definitions for columns such as `monthly_income`, `job_type`, `loan_amount`. |
| 2️⃣ | Supply 4–8 labeled loan applications (e.g., two defaults, six repayments). |
| 3️⃣ | Call GPT‑3.5 (or any compatible LLM) once per ensemble run → obtain ten decision rules per class (“`job_type = rideshare AND monthly_income < 2500`”). |
| 4️⃣ | Let FeatLLM turn these rules into binary columns automatically. |
| 5️⃣ | Fit the tiny linear model on those binaries – usually finishes in seconds on a CPU. |
| 6️⃣ | Deploy the linear model in production; no further LLM calls are needed during daily scoring. |

### Why this matters  

* **Speed & cost:** The entire pipeline needs only ~30 API calls for an entire dataset (20 ensembles × 1 query per ensemble). That is trivial compared with running an LLM for every incoming application.  
* **Performance:** In benchmark experiments FeatLLM achieved *≈10 % higher AUC* than competing few‑shot methods such as TabLLM or STUNT, even when using just four labeled samples—roughly matching conventional models that need >30 samples.  
* **Scalability:** With bagging the method handled datasets having >100 attributes (e.g., the “Communities” crime dataset). A typical credit file rarely exceeds this size, so there’s no risk of hitting prompt limits.

## Healthcare – Risk Stratification When Data Are Scarce  

Clinical environments often face strict privacy constraints and limited annotated cases (think rare disease registries). FeatLLM can leverage medical knowledge baked into an LLM (“elderly patients have higher cardiovascular risk”, “high HbA1c indicates diabetes”) while respecting privacy:

1\. **Define the clinical question** – e.g., “Does this patient have chronic heart failure?”  
2\. **List each lab or vital sign with its unit** – e.g., `ejection_fraction` is % left ventricular ejection fraction; `creatinine` is mg/dL concentration.  
3\. **Provide 5–6 de‑identified cases** with outcomes (“Answer: Yes/No”).  
4\. **Run FeatLLM** → receives rules like “`age > 65 AND ejection_fraction < 40`”.  
5\. **Transform rules into binary features**, then fit the linear classifier on these high‑level indicators.

### Benefits for hospitals  

* **Rapid prototyping:** Clinicians can iterate over new phenotypes without waiting months for full chart abstraction pipelines.
* **Interpretability:** The extracted rules are human readable—a big advantage over black‑box trees or deep nets when explaining decisions to patients or regulators.
* **Robustness to noise:** Experiments adding irrelevant columns showed that FeatLLM’s performance dropped far less than baseline models because its reasoning step filters out spurious features early on.

## Empirical Highlights from the Paper  

* Tested on **13 diverse tabular datasets**, ranging from classic UCI benchmarks (`Adult`, `Heart`) to newly released ones (`Cultivars`, `NHANES`) and synthetic tasks (`Sequence-type`).  
* With just **4 shots**, FeatLLM matched conventional models trained on **32 shots**—an eightfold reduction in label demand.  
* Inference latency was comparable to logistic regression because only the lightweight linear model runs on production data; end‑to‑end LLM methods were *orders of magnitude slower*.  
* Ablation studies confirmed that every component—feature descriptions, two‑step reasoning, weight tuning, and ensembling—contributes positively; removing any one leads to measurable drops in AUC.

## How to Deploy FeatLLM Today  

Below is a checklist you can hand off to your data science team:

1️⃣ **Gather metadata** – column names + short plain English definitions (include type information).  
2️⃣ **Select a few labeled rows** – balance classes if possible (2–8 per class usually suffices).  
3️⃣ **Construct the prompt** – follow the three-part template described above; fix rule count at ten per class for consistency.  
4️⃣ **Call your chosen LLM API** – set temperature ≈ 0.5; repeat `T=20` times with shuffled examples for bagging.  
5️⃣ **Parse generated Python snippets** – let the same LLM produce executable code that evaluates each rule on your dataset rows.  
6️⃣ **Fit the non‑negative linear model** – use standard libraries (`scikit-learn`, `torch`) with cross‑entropy loss; early stopping via k‐fold CV helps avoid overfitting given low shot count.  
7️⃣ **Ensemble predictions** – average softmax outputs across all ensembles before thresholding for binary decisions or taking argmax for multi‑class tasks.  

All steps require only standard compute resources after Step 5; there is no need for GPU training of large models nor storage of massive checkpoints.

## Caveats & Future Directions  

* The current design focuses on *few‐shot* regimes; scaling up to thousands of labeled instances may require additional regularization or hybrid feature sets.
* Because all decisions originate from an LLM’s internal knowledge base, systemic biases present in pretraining data could surface in generated rules—a concern highlighted by the authors’ broader impact section.
* Extending rule generation beyond simple thresholding (e.g., weighted combinations or temporal patterns) could broaden applicability further.

Nevertheless, FeatLLM already demonstrates that *domain knowledge encoded in language models can replace costly manual feature engineering*, opening doors for rapid deployment of high‐performing tabular predictors in finance and healthcare where data labeling budgets are tight.

# Interpretability Boost: Rule‑Based Features Make AI Decisions Transparent

## Why Interpretability Matters in Tabular AI

Tabular data—think medical records, credit reports, or sensor logs—powers countless high‑stakes decisions. Yet many modern AI pipelines treat these datasets as opaque inputs to massive black‑box models (deep neural nets or large language models). When a model predicts “high risk” or “disease present,” practitioners often see only a probability without any clue *why* that outcome was reached.  

The **FeatLLM** framework tackles this head‑on by turning an LLM from a pure predictor into an *automatic feature engineer*. It extracts **human‑readable rule sets** from a few labeled examples, converts those rules into binary features, and then lets a simple linear model do the heavy lifting. The result is a transparent decision pipeline that brings back explainability without sacrificing performance.

## From Prompt to Rule: How FeatLLM Generates Human‑Readable Logic

1. **Structured Prompt Design**  
   FeatLLM crafts a three‑part prompt for the LLM:  
   - **Basic information** – task description, natural‑language feature names and definitions, plus a few serialized training rows (e.g., “`age is 45.` … `Answer: Yes`”).  
   - **Reasoning instruction** – a two‑step chain of thought. First, the model reasons about *causal relationships* between features and the target using its prior knowledge alone. Second, it refines those insights against the provided examples to distill concrete decision rules.  
   - **Response instruction** – explicit formatting guidelines so each rule appears in a predictable template (e.g., `if age > 60 and cholesterol > 200 then class = Positive`).  

   By separating pure prior knowledge from example‑driven inference, FeatLLM nudges the LLM toward *meaningful* rather than spurious patterns.

2. **Rule Extraction**  
   For every class FeatLLM asks the LLM to generate a fixed number of rules (10 per class by default). A rule is essentially an if–then clause that can be read directly by a domain expert (“*Patients older than 70 with systolic BP > 140 are at high risk*”).  

3. **Parsing Into Binary Features**  
   The natural‑language rules are fed back into the same LLM—this time asking it to emit short Python snippets that evaluate each condition on any row of data. Executing these snippets yields binary columns $\mathbf{z}_k^i \in \{0,1\}^{R}$ (where $R$ is the number of rules) indicating whether sample $i$ satisfies rule $r$ for class $k$.

## Transparent Prediction With a Simple Linear Model

Once the binary rule features are ready, FeatLLM fits a tiny linear model without bias:

\[
\text{logit}_k^i \;=\;\max(\mathbf{w}_k , 0)\cdot \mathbf{z}_k^i,
\qquad
\mathbf{p}^i \;=\;\operatorname{Softmax}\bigl([\text{logit}_1^i,\dots,\text{logit}_c^i]\bigr).
\]

- **Non‑negative weights** ($\max(\mathbf{w}_k , 0)$) guarantee that each rule can only increase a class’s score; it never penalizes it retroactively—an intuitive property for explanations.
- The learned weight $\mathbf{w}_{k,r}$ directly measures *how important* rule $r$ is for class $k$. A domain expert can inspect high‑weight rules and instantly grasp what drove the prediction.
- Because the model is linear, one can compute contribution scores analytically (e.g., “rule X contributed +0.27 to the heart‑failure probability”).

## Interpretability Gains In Action

### Rule Quality Is High

The authors measured each generated binary feature’s AUROC against ground truth before any training (“Before tuning”). Across 13 diverse datasets, most rules already delivered AUROCs > 0.5—meaning they were *informative* straight out of the LLM. After learning weights (“After tuning”), low‑utility rules naturally received near‑zero weight, effectively being pruned from explanations.

### Robustness Against Spurious Correlations

In low‑shot regimes it’s easy for models to latch onto irrelevant columns that happen to co‑occur with labels. FeatLLM mitigates this:

- The two‐step reasoning forces the LLM to first consider only *plausible* causal links before looking at examples.
- Empirical tests adding unrelated adult‐dataset columns to Heart data showed **only 1–2 %** of generated rules involved these noisy features.
- Consequently, performance degraded far less than classic baselines when spurious dimensions were injected.

### Ensemble & Bagging Preserve Interpretability

FeatLLM repeats rule generation multiple times (default = 20 ensembles), each with random subsets of features (bagging) and shuffled demonstration order. While ensembles improve predictive power—averaging probabilities across trials—the underlying explanation remains intact:

- Each ensemble yields its own set of readable rules.
- Frequently recurring rules across ensembles can be highlighted as “high consensus” explanations.
- The ensemble process does **not** explode inference cost because all heavy lifting happens *once* during feature construction; at inference time only cheap linear algebra is required.

## Why This Beats Conventional LLM‐Based Tabular Methods

| Approach | How It Handles Explainability | Inference Cost |
|----------|------------------------------|----------------|
| End‑to‑end LLM (in‑context) | No explicit logic exposed; predictions come from raw token probabilities | One LLM call per sample → costly |
| Fine‑tuned LLM (TabLLM) | Implicit hidden representations; limited interpretability | Requires access to model weights & GPU |
| **FeatLLM** | Generates explicit if–then rules → directly readable | Single batch of LLM calls → linear model at test time |

FeatLLM therefore provides **transparent decision logic** while keeping inference latency on par with classic tree or logistic regression models—a crucial advantage for real‑time applications like credit underwriting or clinical decision support.

## Takeaways for Practitioners

- **Human‐readable explanations:** Each prediction can be traced back to specific logical clauses with quantified importance.
- **Low data requirement:** With as few as *4 shots*, FeatLLM matches conventional models trained on 32 shots—perfect for domains where labeling is expensive.
- **API only:** No need for fine‑tuning or large GPU clusters; any accessible LLM endpoint (e.g., GPT‑3.5) suffices.
- **Scalable to many features:** Bagging sidesteps prompt length limits even when datasets have >100 columns.
- **Built‑in robustness:** Prior knowledge + structured reasoning + ensembles guard against overfitting on tiny training sets.

## Looking Ahead

The paper hints at future directions:

- Extending beyond simple rule predicates (e.g., learned embeddings of textual features).
- Integrating richer interpretability tools such as counterfactual analysis built on top of the binary rule space.
- Systematically auditing how biases present in an LLM’s pretraining data propagate through automatically generated rules.

For anyone wrestling with “black box” tabular AI in regulated sectors—finance, healthcare, legal—FeatLLM showcases an elegant path: let an LLM surface its domain knowledge as crisp logical statements, then let a lightweight model turn those statements into trustworthy predictions.
