# From Questions to Rules: The Two‑Step Reasoning Behind **FeatLLM**

## Introduction  
Tabular data—spreadsheets of patient records, credit scores, sensor readings—still dominate many real‑world AI applications. Yet building high‑performing models on such data usually demands a lot of labeled examples or careful hand‑crafted features. Large Language Models (LLMs) have shown they can reason about unseen tasks just by being prompted with a few examples, suggesting a new way to “teach” a model what matters in a dataset without writing any custom code.

**FeatLLM** takes this insight one step further. Instead of asking an LLM to predict every single test sample (which would require an expensive API call per row), FeatLLM asks the LLM **once** to distill the problem into a handful of human‑readable decision rules. Those rules become new binary features that feed a tiny downstream model—often just a linear classifier. The key to this success is a carefully crafted **two‑step prompting strategy** that mirrors how a data scientist approaches a new tabular task.

Below we unpack that prompting strategy, explain why each component matters, and illustrate how it translates natural language reasoning into actionable features.

---

## The Core Idea of FeatLLM  

1. **Ask the LLM to be a feature engineer**, not an end‑to‑end predictor.  
2. **Extract class‑specific logical rules** (e.g., “age > 60 AND cholesterol > 200 → high risk”).  
3. **Convert each rule into a binary indicator** (1 if the row satisfies the rule, 0 otherwise).  
4. **Fit a lightweight model** on these binary features; the model learns how much weight to assign to each rule.  
5. **Ensemble multiple rule sets** via bagging and temperature sampling for robustness.

The heavy lifting—the reasoning about which features matter—is done offline during prompt execution. After that, inference is as cheap as evaluating a few logical expressions.

---

## Prompt Design – Three Building Blocks

FeatLLM’s prompt is deliberately structured into three parts:

| Part | What it contains | Why it matters |
|------|------------------|----------------|
| **Basic information description** | • Task statement (question form) <br>• Natural‑language feature names + type/definition <br>• A handful of few‑shot examples serialized as “`f₁ is … . f₂ is … . Answer: …`” | Gives the LLM all the context it needs—what we’re trying to predict and what each column actually means—without yet showing any data patterns. |
| **Reasoning instruction** | • A short chain‑of‑thought intro <br>• **Step 1:** “Explain which features you think are relevant *before* looking at the examples.” <br>• **Step 2:** “Using those insights *and* the examples, write explicit rules for each class.” | Forces the LLM to first draw on its *prior knowledge* (e.g., “older people have higher heart disease risk”) instead of blindly fitting spurious correlations present in just a few rows. |
| **Response instruction** | • Exact JSON‑like template for the answer <br>• Syntax guidelines for each rule (e.g., use `>` or `<=` when appropriate) | Guarantees machine‑readable output so that downstream parsing can be automated without fragile string fiddling.|

### 1️⃣ Basic Information Description

Even before any reasoning begins, the LLM must understand *what* it’s being asked about:

- **Task description** is phrased as a question such as  
  “*Does this patient’s record indicate chronic heart failure? Yes or no.*”
- **Feature definitions** are supplied verbatim from the dataset metadata (“`age` – integer years”, “`smoking_status` – categorical {never, former, current}”).  
- **Few‑shot demonstrations** are serialized exactly as prior work does:
  \[
  \text{Serialize}(x^i,y^i,F)=\text{``}f_1\text{ is }x^i_1.\dots f_d\text{ is }x^i_d.\ \text{Answer:}\ y^i\text{''}
  \]
  This anchors the LLM in the concrete format it will need to emit later.

### 2️⃣ Reasoning Instruction – The Two‑Step Dance

#### Step 1 – *Domain Understanding*  
The prompt says something like:

> “First, think about which features are likely related to chronic heart failure based on general medical knowledge.”

Crucially, *no example rows are referenced yet.* This pushes the LLM to surface its internal knowledge base (“age and hypertension are risk factors”) rather than latching onto accidental patterns in only four training points.

#### Step 2 – *Rule Extraction from Data*  
After summarizing its intuition, the LLM is told:

> “Now look at the given examples and combine them with your intuition to write ten decision rules for each class.”

By separating these steps:

- The model avoids over‑fitting trivial coincidences (e.g., discovering that `patient_id = 123` predicts “yes” merely because that ID appears in all positive demos).  
- It can incorporate domain expertise that may not be represented in such low‑shot data (e.g., “smoking_status = current → higher risk”).

The number of rules per class is fixed (10 by default) to keep prompts short and keep downstream models manageable.

### 3️⃣ Response Instruction – Making Parsing Easy

The final part tells the LLM exactly how its answer should look:

```json
{
  "class_A": [
    "age > 65",
    "cholesterol >= 200 AND smoker = yes",
    ...
  ],
  "class_B": [
    "age <= 45",
    "blood_pressure < 120"
    ...
  ]
}
```

A strict template prevents variations such as swapping “greater than” for `>` or introducing ambiguous punctuation—issues that would otherwise break simple parsers.

---

## From Natural Language Rules to Binary Features

Even with disciplined formatting there can be minor syntactic noise (“greater than” instead of `>`). FeatLLM solves this by **leveraging the LLM itself as a code generator**:

1. Feed each rule set back into an LLM prompt asking it to emit Python code that implements those logical checks (`def check_rule(row): return row["age"] > 65`).  
2. Execute the generated code with Python’s `exec()` function on every row of the original table.  
3. For each rule we obtain one binary column (`z_k^i ∈ {0,1}^R`) where `R` is the number of rules per class and `k` indexes classes.

Thus every sample turns into a sparse vector of rule satisfactions ready for learning.

---

## Learning from Rules – A Tiny Linear Model

Once we have binary rule features we fit an ultra‑lightweight classifier:

\[
\begin{aligned}
\text{logit}_k^i &= \max(\mathbf{w}_k ,0)\cdot \mathbf{z}_k^i ,\\[4pt]
\mathbf{p}^i &= \operatorname{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big),
\end{aligned}
\]

where:
- $\mathbf{w}_k$ are non‑negative trainable weights learned via cross‑entropy on the few labeled rows,
- $\mathbf{p}^i$ yields class probabilities at inference time.

Because $\mathbf{z}_k^i$ already encode high‐level domain knowledge, even with only $k=4$–$8$ shots this linear model attains performance comparable to fully trained tree ensembles on many benchmarks.

---

## Ensembling & Bagging – Guarding Against Variability

Two sources of randomness make each rule set slightly different:

1. **Temperature sampling** when querying the LLM (default $T=0.5$). Higher temperature yields diverse rule proposals.
2. **Permutation of few‑shot examples**, which can subtly swing the LLM’s inference.

To capitalize on this diversity FeatLLM repeats the entire pipeline $T$ times (often $T=20$) and averages predicted probabilities across trials—a classic ensemble technique akin to random forests but operating at the *rule generation* level instead of tree construction.

Additionally, **feature bagging** randomly selects subsets of columns when building prompts—this keeps prompt length within model limits even for datasets with hundreds of attributes and further decorrelates individual learners.

---

## Why Two-Step Reasoning Works Better Than Direct Prediction

Existing LLM‐based tabular methods typically feed every test row through an LLM (“Here’s my record; what’s the label?”). This approach suffers from three practical issues:

| Issue | Direct Prediction | FeatLLM’s Two‑Step Approach |
|-------|-------------------|------------------------------|
| **Latency** | One API call per row → seconds per thousand rows | Only dozens of calls total during feature engineering |
| **Prompt Length** | Full row serialization plus task description may exceed context window | Prompt only contains meta‐information + few examples; no per‐row data |
| **Spurious Correlation Risk** | Model can latch onto accidental patterns in tiny training sets | Step 1 forces reliance on prior knowledge before seeing data; reduces overfitting |

Empirically, FeatLLM outperforms baselines such as TabLLM and STUNT by roughly $10\%$ AUC on average across 13 diverse datasets—particularly shining on high‐dimensional tables where prompt overflow previously crippled end‐to‐end methods.

## A Walkthrough Example

Imagine we want to predict whether a hospital patient will develop chronic heart failure (`CHF`). The dataset includes columns `age`, `blood_pressure`, `smoker`, and `ejection_fraction`.  

### Prompt Skeleton

```
Task: Does this patient's record indicate chronic heart failure? Yes or No.
Features:
 - age: integer years
 - blood_pressure: integer mmHg
 - smoker: {yes,no}
 - ejection_fraction: integer percentage
Examples:
 age is 72 . blood_pressure is 150 . smoker is yes . ejection_fraction is 30 . Answer: Yes
 age is 45 . blood_pressure is 120 . smoker is no . ejection_fraction is 60 . Answer: No
...
Reasoning:
 Step1: Identify which features you think matter based on medical knowledge.
 Step2: Using those insights plus above examples, write ten rules for each class.
Response format:
{
 "Yes": ["<rule1>", "<rule2>", ...],
 "No": ["<rule1>", "<rule2>", ...]
}
```

### Step 1 Output (generated by LLM)

> “Age and reduced ejection fraction are strong risk factors for CHF; high blood pressure also contributes.”

### Step 2 Output (rules)

```json
{
 "Yes": [
   "age > 65",
   "ejection_fraction < 35",
   "blood_pressure >= 140 AND smoker = yes",
   "...(7 more rules)..."
 ],
 "No": [
   "age <= 50",
   "ejection_fraction >= 55",
   "...(8 more rules)..."
 ]
}
```

The second pass transforms these strings into Python functions (`def r1(row): return row["age"] > 65`) which are executed over every patient record yielding binary columns like `r_yes_1`, `r_no_3`, etc. Finally we train $\mathbf{w}$ on our four labeled patients; perhaps we discover `ejection_fraction < 35` carries most weight while `blood_pressure >=140 AND smoker=yes` adds modest importance.

At inference time predicting CHF for thousands of patients simply means evaluating these logical conditions—a handful of cheap operations per row—and applying learned weights—a dot product followed by softmax.

---

## Takeaways

- **Two-step prompting mimics expert reasoning:** first build *domain intuition*, then *translate* that intuition plus concrete examples into actionable decision rules.
- **Rule extraction sidesteps costly per‑sample LLM calls** while still harvesting rich prior knowledge from massive language models.
- **Simple downstream models suffice:** once you have high-quality binary features, even linear regression reaches state-of-the-art few-shot performance.
- **Ensembling via temperature & bagging yields robustness** without exploding API costs or violating context windows.
- **Interpretability comes free:** each binary feature corresponds directly to an English rule that a practitioner can inspect and validate.

FeatLLM shows that large language models need not remain opaque black boxes; with thoughtfully engineered prompts they can act as *knowledgeable feature engineers*, turning natural language insight into machine learning-ready representations—all in just a couple of API calls.
