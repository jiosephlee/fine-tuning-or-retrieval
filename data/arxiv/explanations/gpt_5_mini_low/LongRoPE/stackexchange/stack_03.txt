\title{Stack Exchange of the Paper: "LongRoPE: Extending LLM Context Window Beyond 2 Million Tokens"}

### What guarantees symmetry between queries and keys under LongRoPE’s non-uniform scaling per dimension?
Question:
RoPE rotates both queries and keys so that their dot products encode relative positions. If LongRoPE applies per-dimension rescale factors $\lambda_i$ and a position threshold $\hat n$, is the exact same transformation applied to both queries and keys for the same head? Are there any corner cases where Q and K could end up misaligned (e.g., due to caching, chunking, or dynamic switching of $\hat n$) that would break the relative position property?
Answer:
Short answer: yes — LongRoPE applies the same per-dimension rescaling to the RoPE angles that are used for both queries and keys in the same head, so the intended $Q\cdot K$ relative-position behavior is preserved — provided the same rescale choice is applied consistently to both $Q$ and $K$ for the same token positions. The paper expresses the modification as a change to the RoPE rotary angles (Eq. (1)/(unified form) and Eq. (problem)): for each RoPE dimension $i$ and token position $n$ the angle becomes either the original $n/\beta^i$ (when $n < \hat n$) or scaled by $1/\lambda_i$ (when $n \ge \hat n$). Because RoPE is a rotation applied at embedding/attention time ($\cos$, $\sin$ of that angle), that same rotated representation is used to form both $Q$ and $K$ for that token, so $Q$ and $K$ remain symmetric under the transform.

Important caveats / corner cases (what can break the symmetry in practice)
1) Changing rescale factors mid-inference (dynamic switching): the paper explicitly states that during inference the model “dynamically adjusts the corresponding RoPE rescale factors” (shorter-context recovery). If you change the $\lambda_i$ or $\hat n$ policy after some keys have already been computed and cached, those cached $K$ (and $V$) were produced with the old angles. New queries produced with a different set of angles will no longer share the exact rotational relationship expected by RoPE, so $Q\cdot K$ will not encode the intended relative positions. In other words: switching $\lambda_i$ or $\hat n$ without either (a) recomputing cached $K/V$ or (b) ensuring the choice of scale is a deterministic function of the absolute token index used to compute both $Q$ and $K$ will break symmetry.

2) Chunking / incremental decoding with caching: when you process tokens in chunks you must ensure the same mapping from absolute position $n \to$ angle (i.e., whether you use original angle or the scaled angle for that $n$, and which $\lambda_i$) is used consistently at the time you compute $Q$ and $K$. If chunk boundaries or a chunked implementation accidentally re-index positions (e.g., per-chunk local indices instead of global absolute indices) or apply different $\lambda$ policies per chunk, $Q/K$ misalignment occurs. The paper’s formulation uses absolute token index $n$ in the indicator $\mathbb{I}(\hat\lambda_i,\hat n)$, so the correct implementation is to base the rescale decision on global position $n$.

3) Mixed policies across heads/layers: the method searches $\lambda_i$ per RoPE dimension (across the model) and then applies these rescale factors. The intended behavior is to use the same RoPE angles wherever that RoPE embedding is used. If an implementation were to (incorrectly) apply different $\lambda$ choices to $Q$ versus $K$ within the same head, the relative-position property would be lost. The paper does not propose different transforms for $Q$ vs $K$, so this would be an implementation bug, not a method feature.

Practical implementation guidance (to preserve $Q$–$K$ symmetry)
- Make $\lambda_i$ and $\hat n$ deterministic functions of the absolute position index (and of the model/head configuration) and compute $\cos/\sin$(angle) once per token position that will be used for both $Q$ and $K$ (and cache those rotated embeddings if you cache $K/V$). This guarantees $Q$ and $K$ for the same position share the same rotation.
- If you need to change $\lambda_i$ or $\hat n$ at runtime (for example switching to a “short-context recovery” set of factors), either (a) do that only at a sequence boundary and recompute prior keys (or invalidate cache), or (b) avoid changing the mapping for positions already consumed (i.e., ensure the mapping is a pure function of absolute $n$ so already-computed keys remain valid).
- When chunking, use global position indices, not per-chunk offsets, to decide whether $n < \hat n$ and which $\lambda_i$ to apply.

Bottom line: the LongRoPE paper modifies the RoPE angles (same $\cos/\sin$ expression used for $Q$ and $K$) and therefore preserves the $Q$/$K$ rotational symmetry when implemented as specified. The only practical pitfalls are engineering ones (changing rescale factors mid-stream, using local indexing, or applying different transforms to $Q$ vs $K$), and those must be avoided by making the rescaling decision depend deterministically on absolute position and by keeping cached $K/V$ consistent with the angle choices used to produce them.
