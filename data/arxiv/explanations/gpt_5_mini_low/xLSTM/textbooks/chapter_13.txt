\title{A Textbook about the Paper: "xLSTM: Extended Long Short-Term Memory"}

Chapter 13: Implementation Guidelines and Practical Tips

# LayerNorm placement and projections (pre/post up-projection choices)
The xLSTM paper prescribes two residual block backbones and matches them to the two main memory variants. For reproducible results, follow the advised mapping:

- For mLSTM blocks use a pre up-projection backbone: first linearly project the input into a higher-dimensional space, then apply the mLSTM non-linearity (the matrix-memory update and retrieval), and finally project back to the model dimension. The motivation given in the paper is that the matrix memory benefits from operating in the higher-dimensional space (larger coding dimension increases memory capacity).
- For sLSTM blocks use a post up-projection backbone: first apply the sLSTM non-linearity in the original model dimension, then up-project to a high-dimensional intermediate, apply the intermediate non-linearity, and down-project. This mirrors the Transformer-style post up-projection residual block used in the paper for sLSTM-containing blocks.

Layer normalization is used in a pre-LayerNorm residual backbone throughout the xLSTM architectures (see Section 2.4). Concretely, apply LayerNorm to the block inputs before the linear projections and before feeding them to the memory cell computations. This matches the "pre-LayerNorm" design used in modern large models and in the experiments. Keeping LayerNorm pre-projection stabilizes the statistics entering the LSTM gates and the key/query/value projections (important for the covariance update and gate numerics discussed below).

# Gate initialization, especially forget gate care
Gate initialization matters. The paper highlights that the forget gate initialization must be chosen carefully (Limitations, point (iv)). Practical recommendations consistent with the paper’s design:

- Input gate: because the input gate uses an exponential activation $i_t = \exp(\tilde{i}_t)$, initialize $\tilde{i}$ so that $i_t$ is small but not vanishing. A standard practice compatible with the paper is to initialize the bias $b_i$ slightly negative so the initial effective learning-rate-like input gate is modest. Avoid large positive bias because $\exp(\cdot)$ can grow quickly.
- Forget gate: because the forget gate acts like a decay factor for memory ($f_t$ multiplies previous memory), initialize $\tilde{f}$ so that $f_t$ is close to but slightly below 1 (for $\sigma$-activated forget) or suitably close to 1 for an exponential forget gate. For example, if using the sigmoid variant $f_t=\sigma(\tilde{f}_t)$, set $b_f$ so $\sigma(b_f)\approx 0.9\text{--}0.99$ to encourage long retention at start. If using exponential forget ($f_t=\exp(\tilde{f}_t)$), set $b_f$ near zero but slightly negative so the effective decay per step is small. The paper notes careful selection is needed because the gate controls decay of stored information.
- Output gate: standard small bias (e.g., zero) is acceptable; the output gate is sigmoid in all variants.
- When gates depend on inputs and/or hidden state, initialize recurrent weights smaller than input projection weights to avoid unstable recurrent contributions early in training.

Because exponential gates can produce large magnitudes, proper initialization (biases and small weight scales) is crucial to keep initial dynamics stable and avoid overflow in the stabilization terms described below.

# Stabilization: normalizer state, m_t, denominator clamping in mLSTM
xLSTM introduces several stabilization constructs. Reproduce them exactly to ensure numerically-stable training and equivalence of stabilized forms.

- Normalizer state: both sLSTM and mLSTM maintain a normalizer $n_t$ that accumulates the gate strengths:
  - sLSTM scalar normalizer: $n_t = f_t\ n_{t-1} + i_t$.
  - mLSTM vector normalizer: $\mathbf{n}_t = f_t\ \mathbf{n}_{t-1} + i_t\ \mathbf{k}_t$.
  Always compute and carry $n_t$ (or $\mathbf{n}_t$) in the forward pass; it is used to divide the retrieved memory representation so that retrieved values are normalized by the total effective stored mass (see Equations (3) and (9) in the paper).
- Stabilizer state $m_t$ for exponential gates: when using exponential gates, the paper uses the log-space stabilizer trick to avoid overflow:
  - $m_t = \max(\log(f_t) + m_{t-1}, \log(i_t))$,
  - then stabilized gates become
    $i'_t = \exp(\log(i_t) - m_t)$ and
    $f'_t = \exp(\log(f_t) + m_{t-1} - m_t)$.
  Implement these stabilized forms in place of direct exponentiation. The paper proves the stabilized transformations leave outputs and parameter gradients unchanged while preventing numerical overflow.
- Denominator clamping in mLSTM retrieval: for mLSTM retrieval the paper divides the matrix-vector product $\mathbf{C}_t \mathbf{q}_t$ by the (absolute) dot product between normalizer and query, lower-bounded by 1:
  $\tilde{\mathbf{h}}_t = \dfrac{\mathbf{C}_t \mathbf{q}_t}{\max\{|\mathbf{n}_t^\top \mathbf{q}_t|,\,1\}}$.
  Implement this exact lower bounding. This avoids division by near-zero denominators (the paper mentions the dot product can be close to zero) and ensures stable magnitudes for the retrieved vector.
- Practical float handling: keep these stabilizers in FP32 (or at least the accumulator state $m_t$ and $\mathbf{n}_t$ in FP32) if you intend to use mixed precision—this reduces the risk of underflow/overflow in exponentiation and accumulation steps.

# Key scaling and zero-mean assumptions for covariance updates
The mLSTM derives its matrix-memory update from the covariance (outer-product) rule. To match the theoretical assumptions and maximize signal/noise:

- LayerNorm before key/value projections: the paper assumes a layer-norm before projecting inputs to keys and values so that keys (and in effect values) have zero mean. This is critical because the covariance update $\mathbf{C}_t \leftarrow \mathbf{C}_{t-1} + \mathbf{v}_t \mathbf{k}_t^\top$ aims to capture associative correlations; zero-mean inputs make the covariance-based memory optimal for separability (as discussed in Section 2.3).
- Key scaling: the paper uses a $\frac{1}{\sqrt{d}}$ scaling for the key projection:
  $\mathbf{k}_t = \frac{1}{\sqrt{d}}\mathbf{W}_k \mathbf{x}_t + \mathbf{b}_k$.
  Implement this scaling to keep dot-product magnitudes in a sensible range for both the outer-product update and the denominator $\mathbf{n}_t^\top \mathbf{q}_t$. Matching this scaling is important for stable signal-to-noise characteristics of the matrix memory (the paper explicitly shows this scaling in Equation (9)).
- Bias handling: because layer-norm makes mean approximately zero, keep the key bias $\mathbf{b}_k$ small or zero if you apply LayerNorm strictly before projection; otherwise non-zero bias alters the zero-mean assumption.

# Precision and mixed-precision training considerations
The paper used mixed precision for many experiments but also points out precision sensitivities. Follow these pragmatic rules:

- Keep accumulation and stabilizer variables in FP32: states such as the matrix memory $\mathbf{C}_t$, normalizer $\mathbf{n}_t$, and stabilizer $m_t$ should be maintained in full precision (FP32) to prevent numerical issues. The matrix memory involves many add/multiply operations; storing it in lower precision invites noise accumulation.
- Gate computations: computing $\tilde{i}_t$, $\tilde{f}_t$, and the subsequent exponentials/sigmoids is sensitive to precision. Compute the exponentials and logs (used in stabilization) in FP32.
- Mixed-precision for weight matrices and activations: forward activations and parameter multiplications can often be done in FP16/BFloat16 for speed, provided you cast back to FP32 for the memory accumulators (as above) and for any reduction-heavy operations.
- Automatic mixed-precision caveat: the paper notes that for some RNN variants (e.g., RWKV-5/6, GLA, HGRN2) the automated AMP tooling needed special handling and some trainings did not use standard PyTorch AMP. For reproducibility, if using AMP, monitor numerics carefully, and be prepared to force FP32 on the memory and stabilizer paths while using AMP for feedforward/projection branches.

# CUDA/Kernel notes: sLSTM custom kernels; potential mLSTM optimization paths
The paper reports engineering realities and guidance for optimized implementations:

- sLSTM custom kernels: sLSTM uses memory mixing (hidden-to-hidden recurrent connections), so it cannot be trivially parallelized across timesteps. The authors wrote a custom CUDA implementation with register-level memory optimizations which achieves runtime typically less than two times slower than their parallel mLSTM implementation. If you intend to use sLSTM in practice:
  - Implement a fused recurrent kernel that computes the gates, updates the scalar cell(s), normalizer, stabilizer, and output in a single kernel launch to minimize kernel overhead.
  - Use register- and shared-memory buffering for per-thread temporal state to reduce global-memory traffic.
  - Fuse LayerNorm and projections where possible to reduce memory transfers.
- mLSTM optimization paths: mLSTM is fully parallelizable because it removes hidden-hidden memory mixing, but it has heavy $d\times d$ matrix memory updates and retrievals which can be costly.
  - The matrix-memory updates are parameter-free (no learnable parameters in $\mathbf{C}_t$), so they are pure linear algebra operations. These can be implemented as batched outer-product updates and batched matrix-vector products, which are highly optimized on modern GPUs.
  - The authors note their mLSTM kernels are not fully optimized and are currently about 4× slower than FlashAttention or the scan used in Mamba. Potential optimizations include:
    - Use fused batched GEMM and batched outer-product primitives where hardware accelerators can exploit tensor cores.
    - Implement a FlashAttention-like memory layout and blocking strategy for the $\mathbf{C}_t \mathbf{q}_t$ retrieval to reduce memory traffic and increase arithmetic intensity.
    - Consider tiling $\mathbf{C}_t$ updates and retrievals to fit GPU shared memory and tensor core tile sizes.
    - If deploying at inference for very long contexts, take advantage of the constant-size memory $\mathbf{C}_t$ to avoid caching large key/value histories; you can keep $\mathbf{C}_t$ resident and perform only the incremental outer-product updates.
  - Where possible, keep $\mathbf{C}_t$ in FP32 even if other activations are in FP16 to avoid accumulation noise.
- Profiling: carefully profile both memory-bound and compute-bound regimes. The paper reports that despite heavier per-step compute, wall-clock overhead is minor because operations parallelize well. Nonetheless, a production-grade implementation should implement the optimizations above.

# Selecting xLSTM[a:b] ratios by task (capacity vs. state tracking)
xLSTM permits mixing mLSTM- and sLSTM-based blocks. The paper uses the notation xLSTM[a:b] to denote the ratio of mLSTM-based to sLSTM-based blocks. Practical selection guidance based on the empirical findings and the properties of the two variants:

- If your task emphasizes large associative memory capacity (many distinct key-value pairs, rich content-addressed recall, rare token modeling across long contexts), favor mLSTM-heavy configurations. The paper finds xLSTM[1:0] (only mLSTM) and variants with high mLSTM ratios perform best on many language-modeling tasks (see experiments on SlimPajama and PALOMA).
- If your task requires state tracking, sequential algorithmic behavior, or structured state updates that benefit from recurrent memory mixing, include sLSTM blocks. sLSTM supports memory mixing and the exponential gating that enables revising storage decisions; the paper shows sLSTM is superior when memory-mixing capacity is required (for formal language/state-tracking tasks).
- A mixed architecture like xLSTM[7:1] (mostly mLSTM blocks with a minority of sLSTM blocks) often provides a practical balance: the majority of high-capacity associative storage and efficient parallelism comes from mLSTM blocks, while the small number of sLSTM blocks gives state-tracking and memory-mixing capability that helps on tasks needing sequence-sensitive updates. The paper used xLSTM[7:1] in many experiments and showed strong overall results.
- If inference latency or throughput is the primary constraint and the task is mostly associative (e.g., large-context language modeling without heavy sequential state dependencies), favor pure mLSTM (xLSTM[1:0]) because it is parallelizable and gives higher throughput.
- If the application is in reinforcement learning or program evaluation where state tracking is critical, include a nontrivial proportion of sLSTM blocks to access memory mixing and stateful updates.

# Additional engineering notes consistent with the paper
- Memory vs. compute trade-off of mLSTM: the mLSTM’s matrix memory increases memory capacity but at a $d\times d$ computational cost per cell. The paper notes the memory itself does not add parameters, but costs compute. In practice you can trade off the internal d (the memory dimension) and the number of mLSTM blocks to fit your hardware budget.
- Sequence length and memory load: because the matrix memory is independent of sequence length, very long contexts may overload the fixed-size $\mathbf{C}_t$ if the model is asked to store too much diverse information. The paper observed good extrapolation up to 16k contexts with 1.3B models, but keep this consideration in mind for extreme context lengths; you may need to increase the internal memory dimension $d$ or adjust forget/input gate priors.
- Reproducibility tips: follow the same residual stacking, pre-LayerNorm setup, and the block projection choices the paper used. For benchmarking, match the training tokenization, data mixture, and prefill/context lengths as closely as possible to achieve comparable perplexity and scaling behaviors.
- Hyperparameter tuning: the paper indicates that not all architectures were fully optimized and that further tuning (especially at large scale) can improve performance. Key knobs to tune include gate bias initializations (especially $b_f$), key scaling, memory dimension $d$, and the xLSTM[a:b] ratio.

Following these guidelines will reproduce the numerics and engineering trade-offs discussed in the paper: use pre-LayerNorm residual backbones, map sLSTM to post up-projection and mLSTM to pre up-projection, stabilize exponential gates via $m_t$ and stabilized $i'_t,f'_t$, clamp mLSTM denominators by $\max\{|\mathbf{n}_t^\top \mathbf{q}_t|,1\}$, keep memory accumulators in FP32 when using mixed precision, and design CUDA kernels to fuse recurrent-state updates (sLSTM) or to exploit batched GEMM/tensor core tiling (mLSTM). Choosing the xLSTM[a:b] ratio should be driven by whether your task needs high associative capacity (favor mLSTM) or state-tracking/memory-mixing (include sLSTM).
