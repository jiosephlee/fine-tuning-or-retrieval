\title{A Textbook about the Paper: "xLSTM: Extended Long Short-Term Memory"}

Chapter 7: Computation, Memory, and Parallelization

# Complexity vs. sequence length: linear compute, constant memory

One of the central computational advantages emphasized for xLSTM in the paper is its behavior with respect to the sequence length. Both sLSTM and mLSTM operate in a recurrent (or recurrence-derived parallel) fashion such that the amount of work and the working memory that depend on sequence length grow only linearly for compute and remain constant for model memory use. Concretely, for a sequence of length $T$, the number of elementary update steps is proportional to $T$: each time step performs a fixed set of operations (gate computations, projections, and a memory update and/or retrieval), so the total arithmetic work is $O(T \cdot W)$ where $W$ denotes the per-step work proportional to layer width and any internal matrix sizes. This linearity in $T$ contrasts with full dense self-attention in standard Transformers, whose naive implementation incurs $O(T^2)$ compute and $O(T^2)$ intermediate memory for attention scores.

The "constant memory" claim refers to the fact that model-internal state that must be kept across the time dimension (for generation or streaming) does not grow with $T$. For both xLSTM variants, the cell state is a fixed-size object independent of how many time steps have been processed: a scalar (or vector of scalars) per cell for sLSTM, or a matrix $\mathbf{C}\in\mathbb{R}^{d\times d}$ (and associated normalizer state) for mLSTM. Thus the active working memory required to continue generation online or to maintain the model state for future inputs is a constant size per layer, not a cache of all past token keys and values. This allows xLSTM models to process arbitrarily long sequences without the memory blow-up encountered when storing keys and values for every past token as done in vanilla Transformer decoding without compression.

This compute and memory profile makes xLSTM particularly well-suited for streaming and long-context scenarios and explains why the paper highlights xLSTM's linear computation and constant memory complexity in the sequence length. It is important to note that linear compute does not imply small absolute latency or low wall-clock time — the per-token work $W$ and operator types (e.g., matrix--matrix products) determine runtime — but it guarantees scalability in contexts where $T$ grows very large.

# mLSTM compute cost: d×d updates and retrievals, no parameter cost

mLSTM augments the scalar LSTM memory by replacing the scalar cell with a matrix memory $\mathbf{C}_t\in\mathbb{R}^{d\times d}$. The update rule adopted is a covariance (outer-product) style update:
\[
\mathbf{C}_t \;=\; f_t \, \mathbf{C}_{t-1} \;+\; i_t \, \mathbf{v}_t \, \mathbf{k}_t^\top,
\]
where $\mathbf{k}_t,\mathbf{v}_t,\mathbf{q}_t\in\mathbb{R}^d$ are key, value, and query vectors and the hidden output is computed via a matrix--vector product and normalization:
\[
\tilde{\mathbf{h}}_t \;=\; \frac{\mathbf{C}_t \mathbf{q}_t}{\max\{|\mathbf{n}_t^\top \mathbf{q}_t|,1\}},
\qquad
\mathbf{h}_t \;=\; \mathbf{o}_t \odot \tilde{\mathbf{h}}_t,
\]
with $\mathbf{n}_t$ the normalizer state updated analogously to $\mathbf{C}_t$.

These formulas make the computational cost per time step explicit: the rank-one outer-product update $i_t \, \mathbf{v}_t \, \mathbf{k}_t^\top$ is a $d\times d$ matrix that must be added to the scaled previous memory $f_t \mathbf{C}_{t-1}$. The retrieval step requires multiplying the stored matrix $\mathbf{C}_t$ by the query vector $\mathbf{q}_t$, i.e., a $d\times d$ times $d$ vector product. Therefore, per time step the dominant arithmetic costs scale as $O(d^2)$ for both the update and the retrieval. Unlike a parameter matrix multiplication, these costs come from manipulating the content of the memory rather than learned weight parameters — the memory matrices themselves are not parameters tuned by optimization; they are ephemeral state that accumulates information from the sequence. Hence the paper emphasizes that the matrix memory imposes computation costs (quadratic in $d$) but not parameter costs.

The quadratic-in-$d$ cost is the trade-off for substantially increased storage capacity relative to scalar cell states. The covariance update can store pairwise (outer-product) associations between key and value components, enabling retrieval via inner products with queries. This expanded capacity is what allows mLSTM blocks to improve performance on rare-token prediction and associative-recall-type tasks. Practitioners must therefore balance desired memory capacity (larger $d$) against the $O(d^2)$ compute per step.

# GPU parallelism: why wall clock overhead can be modest

Although mLSTM's arithmetic complexity per time step is $O(d^2)$, there are reasons the wall-clock overhead can be moderate in practice. First, the expensive operations (rank-one outer product formation, scaled matrix addition, and matrix--vector multiply) are regular linear-algebraic operations that map well to GPU hardware: they can be implemented as batched matrix--matrix and matrix--vector kernels and thus exploit the high throughput of modern GPUs. In particular, the rank-one update can be implemented efficiently by expanding $\mathbf{v}_t$ and $\mathbf{k}_t$ into outer-product kernels or by using optimized level-3 BLAS routines when accumulating updates across heads or minibatch elements. The matrix--vector retrieval $\mathbf{C}_t \mathbf{q}_t$ is also a standard high arithmetic-intensity operation.

Second, because the memory is not tied to sequence length, mLSTM allows computation to be organized so that many tensor operations across the batch and heads execute in parallel. Where possible, multiple heads, minibatch items, and multiple memory cells can be batched into larger GEMM calls to improve hardware utilization. The paper explicitly notes that such computations "can be done in parallel on GPUs," and therefore despite $d\times d$ operations the wall clock time overhead compared to other architectures is relatively small.

Finally, mLSTM's parallel reformulation removes sequential hidden–hidden mixing (see below), enabling efficient parallel kernels similar in spirit to parallelized attention implementations. This makes mLSTM comparable to other linear-time attention-like methods that are amenable to high-throughput GPU execution, and the paper reports that mLSTM's parallelizable operations result in modest wall-clock overhead in practice.

# sLSTM non-parallelizability due to memory mixing

sLSTM retains memory-mixing through recurrent hidden–hidden connections: gates and cell inputs depend on the previous hidden state $h_{t-1}$ via recurrent weight matrices (or vectors in the scalar case). This creates a sequential dependency across time steps that precludes a straightforward parallel reformulation analogous to mLSTM. Concretely, when gate pre-activations and the new cell input $\tilde{z}_t$ are functions of $h_{t-1}$, each time step must be evaluated in order because $h_{t-1}$ is produced only after finishing the previous step. That sequential dependency is exactly what prevents batching the entire sequence into a single giant matrix multiplication that replaces per-step recurrence.

This inability to parallelize over time is a classical limitation of RNN-like models, and sLSTM inherits it because its design intentionally preserves memory mixing to enable state-tracking behaviors that rely on interactions between memory cells across time. The paper motivates this design choice: memory mixing enables the sLSTM to perform tasks that require revising stored decisions and tracking complex internal state (for example, certain formal-language state-tracking tasks). The trade-off is that sLSTM cannot leverage the same large-scale time-parallel kernels that are available for fully parallelizable blocks.

# CUDA implementation notes: sLSTM kernels and mLSTM optimization gap

Given that sLSTM is inherently sequential across time due to memory mixing, the authors implemented a specialized CUDA kernel for it to mitigate the sequential performance penalty. The paper reports a fast CUDA implementation for sLSTM with "GPU memory optimizations to the register level" that makes sLSTM typically less than two times slower than mLSTM in practice. This indicates that well-engineered low-level kernels can substantially reduce the overhead of sequential recurrence by maximizing per-step efficiency: minimizing global memory traffic, exploiting registers and shared memory, fusing elementwise operations (gate computations, normalization, stabilizers), and reducing kernel launch overheads. Those engineering efforts partially compensate for the lack of time parallelism.

On the other hand, the authors note that the mLSTM CUDA kernels are not yet fully optimized. The current mLSTM implementation is about four times slower than highly optimized attention implementations such as FlashAttention or the sequence-scan used in Mamba. There is thus an optimization gap: while mLSTM is parallelizable and its operations are conceptually well-suited for GPUs, absence of equivalent low-level optimizations (e.g., fused $d\times d$ update kernels, memory layout tuning, and kernel fusion across updates and retrievals) increases runtime in the present implementation. The authors suggest that further optimization — in the spirit of FlashAttention — could significantly shrink this gap, and their results indicate that even the current, not-yet-fully-optimized mLSTM has acceptable wall-clock performance because GPUs parallelize the $d^2$ work efficiently.

These remarks highlight two practical realities: (1) algorithmic complexity gives an upper bound on work, but real runtime depends heavily on kernel quality and hardware utilization; (2) recurrent but memory-mixing models can partly close the runtime gap through hand-tuned sequential kernels, while parallelizable matrix-memory models benefit most from investing in fused, high-throughput GPU kernels.

# Throughput implications vs. Transformers with KV cache

Transformer decoders used for autoregressive generation typically store keys and values for every context position in a KV cache, so that each subsequent token generation can reuse those cached key and value matrices rather than recomputing attention against the entire prefix. While this cache avoids redoing the forward pass over past tokens, it still grows in memory as $O(T)$ (and attention with cached keys/values still requires $O(T)$ memory accesses per new token for the attention score computations unless special approximations are used). This leads to practical limits on batch sizes and possible throughput bottlenecks: larger prefill (longer context) reduces available memory for batching and lowers the maximal throughput achievable during decoding.

Because xLSTM maintains a fixed-size internal state (scalar/vector per cell for sLSTM or $d\times d$ matrix for mLSTM) independent of $T$, it avoids the linear memory blow-up of stored per-token keys/values. The paper demonstrates that this has strong throughput implications. In the experiments reported, xLSTM (and other recurrent models like Mamba and RWKV) show linear scaling of generation time with context length as opposed to the quadratic or cache-limited behavior for Transformers. Moreover, the constant memory profile allows xLSTM to use much larger batch sizes during decoding: the paper's benchmarking found that xLSTM achieves higher maximal throughput than Llama because it can scale batch sizes without hitting KV-cache memory limits.

This advantage is most pronounced when the Transformer decoder must keep a large KV cache for long prefill lengths: the KV cache consumes memory proportional to both sequence length and model width, constraining batch sizes and thus throughput. In contrast, xLSTM's constant-state approach means that even with long precursors (large prefill), it can maintain high batch sizes and therefore deliver higher tokens-per-second throughput in many settings. The paper reports that xLSTM achieves the highest throughput among compared models in their decoding throughput experiments, underlining that algorithmic linearity and constant memory translate into practical throughput gains.

Finally, it is worth noting the generation-time trade-offs: while Transformers can be optimized with fused KV cache access and attention kernels (e.g., FlashAttention) to be extremely fast per token for moderately sized contexts, their memory scaling limits ultimate batch sizes and memory-constrained throughput. Conversely, xLSTM’s per-step $O(d^2)$ cost (for mLSTM) or sequential overhead (for sLSTM) can make its per-token latency larger at small contexts and without specific kernel optimizations, but its throughput remains more robust as context length increases and at large batch sizes. The net effect — as demonstrated in the paper — is that xLSTM attains competitive or superior throughput in many practical decoding regimes, especially when large contexts or large batch sizes are necessary.
