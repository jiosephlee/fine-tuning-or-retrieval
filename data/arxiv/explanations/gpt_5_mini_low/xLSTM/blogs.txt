# xLSTM in Plain English: Why LSTMs Are Making a Comeback

LSTMs were once the go-to architecture for sequence modeling. They solved the vanishing gradient problem by introducing a guarded, additive memory (the "constant error carousel") and gating to control reads and writes. Then Transformers arrived with parallel self-attention and steamrolled LSTMs for many language tasks. The xLSTM paper asks a simple, practical question: what happens if we modernize and scale LSTMs with the best of recent ideas? The surprising answer: with a few well-chosen changes, LSTM-style models can be competitive with state-of-the-art Transformers and State Space Models at language modeling — and they bring some distinct trade-offs.

This post gives a concise, non-mathematical tour of what xLSTM changes and why those changes matter.

## Quick background: what LSTMs get right (and where they fall short)

An LSTM keeps a scalar cell state \(c_t\) and updates it additively using gates:
\(c_t = f_t \, c_{t-1} + i_t \, z_t\),
with an output \(h_t = o_t \, \psi(c_t)\). That additive update is what prevents vanishing gradients, and the gates (input, forget, output) let the model decide what to store, keep, and emit.

Strengths:
- Good at stateful problems and explicit state tracking (e.g., parsing, program evaluation).
- Compact memory that can retain information across long spans.

Weaknesses highlighted by the authors:
- Limited ability to "revise" past storage decisions: once a value is stored, it can be hard to overwrite it if a later, better candidate appears.
- Limited storage capacity per cell: scalar cells compress a lot of information.
- Poor parallelizability when full recurrent connections (hidden-to-hidden mixes) are used, which slows training and inference for very long contexts.

xLSTM targets these limitations with two core ideas: exponential gating (to allow revising storage decisions) and richer memory structures (for more capacity and parallelism).

## The two xLSTM variants: sLSTM and mLSTM (and what they add)

xLSTM is a family built around two main extensions of the LSTM cell.

1. sLSTM — scalar memory, exponential gates, new mixing
- Like a traditional LSTM, sLSTM keeps scalar memory cells, but it changes the gating nonlinearity: the input gate (and optionally the forget gate) can use an exponential activation instead of a sigmoid.
- To avoid runaway numerical issues with exponentials, sLSTM keeps two auxiliary states:
  - A normalizer \(n_t\) that tracks the cumulative strength of writes (the product/sum of input gate times future forget gates). This is used to normalize the effective memory contribution, so outputs remain well-scaled.
  - A stabilizer \(m_t\) that keeps the exponentials numerically stable (effectively subtracting a running maximum before exponentiating), which preserves exact outputs and gradients while avoiding overflow.
- Multiple scalar cells and "heads" are possible. Crucially, sLSTM keeps memory mixing via recurrent connections between hidden state and gates, which makes it expressive for state-tracking problems (things Transformers and SSMs without recurrence can struggle with).

Why exponential gates? Intuitively they let the model weight writes multiplicatively across time so that later writes can exponentially dominate or diminish earlier ones. That makes it easier to revise stored content when a better candidate appears later in the sequence.

2. mLSTM — matrix memory with covariance (outer-product) updates
- Instead of a scalar \(c_t\), mLSTM stores a matrix \(\mathbf{C}_t \in \mathbb{R}^{d \times d}\). Each time step stores a key \(\mathbf{k}_t\) and value \(\mathbf{v}_t\) and updates the matrix using a covariance (outer-product) rule:
  \(\mathbf{C}_t = f_t \, \mathbf{C}_{t-1} + i_t \, \mathbf{v}_t \mathbf{k}_t^\top\).
- Retrieval is a matrix-vector product: given a query \(\mathbf{q}_t\), the read is \(\tilde{\mathbf{h}}_t = \mathbf{C}_t \mathbf{q}_t\), normalized by a measure derived from a normalizer state \(\mathbf{n}_t\) (the accumulated, gate-weighted sum of keys) to keep the signal-to-noise reasonable.
- Gates here also use exponentials (with the same stabilizer trick) so the input gate acts like a learned write learning-rate and the forget gate like a decay factor.

Why a matrix memory? The outer-product update stores pairwise associations between keys and values compactly and allows richer, higher-capacity retrieval than scalar cells. It resembles "fast weights" and some linear-attention ideas but is integrated into an LSTM-style gated framework. Importantly, because mLSTM drops hidden-to-hidden mixing (no recurrent matrix mixing in the same way), it can be implemented in a parallel, scan-friendly fashion — making it computationally competitive at scale.

## Stabilizers and normalizers — the small but crucial engineering fixes

Exponentials can blow up numerically. xLSTM adds a stabilizer \(m_t\) that subtracts a running max log of gate values before exponentiating; this preserves the exact model outputs and gradients but avoids overflow. The normalizer states \(n_t\) (scalar for sLSTM, vector for mLSTM) track the cumulative effective write strength to allow dividing the accumulated memory by the total write mass — this keeps reads well-conditioned even when many writes accumulated.

These mechanisms are important: they make the exponential gating practical and stable while retaining the desired algebraic properties.

## How xLSTM is assembled: residual xLSTM blocks and stacked architectures

xLSTM cells are placed inside familiar residual block backbones (pre-LayerNorm residual stacks like modern LLMs). Two block variants are used:

- For sLSTM blocks: a "post up-projection" design (nonlinear summarization in original space, then up-project, activate, down-project).
- For mLSTM blocks: a "pre up-projection" design (up-project first into a high-dimensional space, then run the memory cell there).

These blocks are residually stacked into deep xLSTM architectures, which aligns with contemporary LLM construction patterns and helps scale to many parameters.

The paper explores hybrids: xLSTM[a:b] denotes the ratio of mLSTM-based to sLSTM-based blocks (e.g., xLSTM[7:1] has many mLSTM blocks and a few sLSTM blocks). The best-performing models often mix both variants.

## Why this matters: trade-offs vs Transformers and SSMs

- Expressiveness / state tracking: Because sLSTM retains recurrence and explicit memory mixing, xLSTM can handle state-tracking tasks that Transformers and some SSMs find fundamentally hard. The paper shows synthetic tasks where this matters (e.g., formal languages and parity-like problems).
- Memory capacity: mLSTM's matrix memory gives a larger, associative memory than scalar LSTM cells, improving performance on associative recall tasks where many key–value pairs must be stored and retrieved.
- Complexity vs parallelism:
  - mLSTM can be parallelized and has linear time in sequence length (like SSMs and many efficient attention variants).
  - sLSTM with recurrent mixing is less parallel but still practical with a custom CUDA kernel (authors report it can be less than 2× slower than mLSTM in their implementation).
  - mLSTM has heavier per-step compute (\(d \times d\) matrix updates), whereas Transformers pay quadratic cost in sequence length (attention). So xLSTM offers a different complexity trade-off: constant memory in sequence length and linear compute in sequence length, but potentially larger constant factors due to the matrix memory.

## Empirical takeaways (concise)

The paper trains and evaluates xLSTM variants on language modeling and synthetic tasks. Highlights:

- On synthetic state-tracking/formal language tasks, models that retain memory mixing (sLSTM) solve problems that Transformers and many SSMs cannot.
- On associative recall tasks with many key-value pairs, hybrid xLSTM models (mix of mLSTM and sLSTM) perform best among non-Transformer methods; mLSTM boosts storage capacity.
- On language modeling (trained on SlimPajama subsets, e.g., 15B and 300B-token regimes), xLSTM variants achieve validation perplexities competitive with — and often better than — a range of Transformer and SSM baselines (the paper compares to Llama, Mamba, RWKV, H3, etc.).
- xLSTM extrapolates better to longer contexts (tested up to 16k tokens in the paper) in some setups.
- In generation speed and memory: recurrent xLSTM variants scale linearly with context length (so generation is faster than a Transformer for very long contexts), and mLSTM enables high throughput thanks to constant memory usage with sequence length. Transformers, by contrast, face quadratic memory growth with context length.

## Limitations the authors note

The paper is careful about limitations:

- sLSTM's memory mixing prevents easy parallelization; that makes sLSTM inherently sequential and slower to run unless specialized kernels are used.
- mLSTM has heavier compute (quadratic in the coding dimension \(d\)) because of \(d \times d\) matrix operations, which raises runtime and FLOP budgets even though memory does not depend on sequence length.
- CUDA kernels for mLSTM and sLSTM in the paper are not fully optimized; the reported runtimes could improve with engineering effort.
- Initialization of forget gates and capacity saturation for very long contexts are practical concerns the authors mention.
- Hyperparameter and architecture search at very large scale remain to be fully explored.

## Bottom line

xLSTM shows that LSTM ideas are not obsolete — they can be modernized. Two relatively small but powerful changes are the keys:

- Exponential gating (with stabilizers and normalizers) lets the model revise and weight writes in a way that improves state updates and retrieval dynamics.
- Matrix memory (covariance/outer-product updates) gives associative, higher-capacity storage that integrates naturally with gated recurrent dynamics.

When wrapped into residual blocks and scaled, these ideas let xLSTM models compete with modern Transformers and State Space Models on language modeling, while offering different trade-offs in expressiveness, memory behavior, and computational structure. For practitioners, xLSTM is an intriguing option if you need strong state tracking, constant memory with sequence length, or want a model family that combines recurrent inductive biases with scalable architectures.

Code and implementation details are available in the authors' repository: https://github.com/NX-AI/xlstm — useful if you want to experiment with the stabilizer tricks, mLSTM matrix memory, or their hybrid block stacks.



# Exponential Gating, Explained: How xLSTM Learns to Revise Its Memory

xLSTM introduces a deceptively small change to the classic LSTM that fixes a long-standing behavioral limitation: the original LSTM struggles to reliably *revise* previously stored content when later inputs should take priority. The key idea is exponential gating paired with two bookkeeping states — a stabilizer and a normalizer — that together let the network treat its cell as a weighted (and re-weightable) accumulator rather than an accumulating-but-immutable sum.

This post breaks down the mechanism, the math, and the intuition behind why exponential gates + stabilizer + normalizer let xLSTM (specifically the sLSTM variant) revise memory, and why that matters for tasks like parity, nearest-neighbor search, and other state-tracking problems.

## The problem: LSTMs and non-revisable storage

A vanilla LSTM cell updates its scalar memory with the constant-error-carousel rule:
c_t = f_t * c_{t-1} + i_t * z_t,
and produces h_t via an output gate. The gates f_t and i_t are sigmoid outputs in (0,1), so the forget gate attenuates past content and the input gate scales new content. This design prevents vanishing gradients, but it gives two important limitations:

- The input and forget gates are bounded in (0,1), so once content is written and then partially forgotten, future writes have limited ability to "dominate" or strongly re-weight the total content.
- Information in c_t is a scalar (or a low-dimensional vector) compressed via additive accumulation, which makes fine-grained selective retrieval or aggressive revision harder.

Consequence: when later inputs should override earlier stored values (for example, finding the most similar vector in a sequence, or toggling a parity bit), standard LSTM gating can be too conservative — the past still leaks into the memory and distorts retrieval.

xLSTM’s sLSTM addresses this by changing how gates behave and how the cell output is formed.

## sLSTM: exponential gates, normalizer, stabilizer — the forward pass

sLSTM keeps the LSTM-style additive cell but replaces the usual sigmoid input gate with an exponential activation and introduces two auxiliary states: a normalizer n_t and a stabilizer m_t. The core forward equations (scalar form) are:

c_t = f_t * c_{t-1} + i_t * z_t
n_t = f_t * n_{t-1} + i_t
h_t = o_t * \tilde{h}_t ,    \tilde{h}_t = c_t / n_t

where
- z_t is the (squashed) cell input,
- i_t = exp( \tilde{i}_t ) is the input gate (exponential),
- f_t = sigma( \tilde{f}_t ) or optionally exp( \tilde{f}_t ) is the forget gate,
- o_t is an output gate as usual.

So instead of letting i_t be in (0,1), we let i_t be strictly positive and potentially large. The normalizer n_t accumulates the same gating weights that scale stored z's: it tracks the total "weight mass" contributed to the cell across time (each input's contribution multiplied by all subsequent forget factors). The hidden pre-output \tilde{h}_t is the normalized ratio c_t / n_t, i.e., a weighted average of stored z's where each z is weighted by its effective contribution.

This is the central operational change: the network no longer treats c_t as an unnormalized sum, but as a numerator that is explicitly divided by the sum of weights. That shift is what enables effective revision.

## Intuition: weighted average and revisability

Write out c_t and n_t unrolled:

c_t = sum_{s <= t} ( i_s * z_s * prod_{u=s+1..t} f_u )
n_t = sum_{s <= t} ( i_s * prod_{u=s+1..t} f_u )

Then
\tilde{h}_t = c_t / n_t = (sum_s w_s z_s) / (sum_s w_s)
with w_s = i_s * prod_{u=s+1..t} f_u.

So the cell output is a weighted average of the past z_s with weights w_s that depend multiplicatively on input gates i_s and future forget gates f_u. Two implications follow:

1. A later input can dominate the weighted average if its i_t (or the combination of i_t and subsequent f's) is large relative to prior weights. Using an exponential activation for i_t removes an arbitrary cap on how strongly a write can influence the averaged state. This allows the network to *revise* memory by assigning a much larger weight to a later item, effectively overriding prior stored content.

2. The normalizer n_t ensures scale doesn't explode: even if some i_t are large, dividing by the sum of weights yields a stable averaged representation. So the cell can represent a dominant new value without blowing up magnitude-wise.

In contrast, a standard LSTM with i_t in (0,1) cannot assign arbitrarily large relative weight to a late item: late contributions are always bounded by the gate range, which can prevent proper revision when a later input should be prioritized strongly.

## The stabilizer m_t: numerical safety for exponentials

Exponentials can overflow in floating point if you let their arguments grow unchecked. xLSTM uses a stabilizer state m_t (drawn from ideas in prior work) that keeps the exponentials numerically stable without changing the mathematical result. The stabilized gates are computed via log-space max-trick:

m_t = max( log(f_t) + m_{t-1}, log(i_t) )

Then define stabilized (scaled) gates

i'_t = exp( log(i_t) - m_t ) = exp( \tilde{i}_t - m_t )
f'_t = exp( log(f_t) + m_{t-1} - m_t )

Replacing i_t and f_t by i'_t and f'_t in the recurrence does not change the network outputs nor the gradients; it only rescales the internal bookkeeping so the exponentials remain in a safe numeric range. This is the same numerical trick that stabilizes softmax-like accumulations and makes the exponential gating practically usable in training.

Put simply, m_t tracks a running log-scale so we normalize the gate magnitudes around a manageable exponent.

## How this enables concrete algorithmic abilities

Two examples illustrate why revisability matters and how exponential gating + normalizer helps.

Nearest-neighbor search (sequence setting). Suppose we stream vectors x_1, x_2, ..., x_T paired with labels, and at the end we want to return the label of the vector most similar to a fixed reference vector r that was given at the start. The correct behavior is: whenever a vector more similar to r is seen, the model should update the stored best-match so that at the end the label of the most similar vector is returned.

- Standard LSTM: earlier stored candidates leave residual influence due to bounded gates; later, even if a better candidate appears, its bounded i_t might not sufficiently outweigh accumulated prior mass, so the memory average remains polluted and retrieval fails.

- sLSTM: when the model detects a much better candidate at time s, it can set i_s to a very large value (via exponential gating) and let f for subsequent steps be permissive, so the new candidate's weight dominates the normalizer n_t and thus drives \tilde{h} toward that candidate. The model can therefore aggressively revise which item counts most.

Parity and formal-language tasks (state tracking). Some tasks require toggling internal state (e.g., flipping a bit for parity) or precise bookkeeping across long spans. Memory mixing (recurrent connections across cells) combined with exponential gating gives the network the ability to reassign global weight mass quickly and reliably. Where standard gating only slowly attenuates old contributions, exponential gates can sharply shift the normalized average to reflect transient or late-arriving signals.

Empirically in the xLSTM paper, sLSTM variants solve parity and other formal languages that Transformers and many SSMs fail on, because these tasks need expressive state tracking and the ability to revise or overwrite stored information.

## A few practical notes and caveats

- Forget gate options: f_t can be kept sigmoid (in (0,1)) or also be exponential. Using an exponential forget gives even more flexible multiplicative control but increases the demand for stabilization and careful initialization.

- Initialization matters: the paper notes forget-gate initialization must be chosen carefully; bad initialization can make the normalizer dynamics problematic or make the stabilizer roll poorly early in training.

- Numeric invariance: the stabilizer m_t (log-space normalization) does not alter the functional behavior of the cell — it is a numerics trick. The normalizer n_t, however, is a core algorithmic addition: it changes the semantics of c_t from an unnormalized sum to an explicit weighted average denominator.

- sLSTM vs mLSTM: this post focused on sLSTM (scalar memory + exponential gates + normalizer), which adds memory mixing (recurrent hidden-to-gates connections). The paper also introduces an mLSTM with matrix memory and covariance updates to increase capacity; mLSTM uses the same stabilizer/normalizer philosophy but in matrix form. Both variants leverage exponential gating to improve revisability and retrieval.

## Bottom line

Exponential gating turns the input (and optionally forget) gates into positive multiplicative weights without the tight upper bound of sigmoids. When combined with the normalizer state n_t that tracks the sum of effective weights, the cell output becomes a stable weighted average of past inputs. This lets the network choose to make a late input overwhelmingly influential (i.e., revise memory) while avoiding numerical blowup via the stabilizer m_t. The result is an LSTM-like recurrent unit that can both track state (via memory mixing) and aggressively revise stored content when the task requires it — a capability that standard LSTMs lacked and that many non-recurrent architectures (Transformers, many SSMs) do not offer without extra machinery.

If you want to see the exact sLSTM equations again, here they are compactly:

c_t = f_t c_{t-1} + i_t z_t  
n_t = f_t n_{t-1} + i_t  
\tilde{h}_t = c_t / n_t  
h_t = o_t \tilde{h}_t  

with i_t = exp(\tilde{i}_t), optional f_t = exp(\tilde{f}_t), and stabilizer

m_t = max( log(f_t) + m_{t-1}, log(i_t) ),

together with the normalized gates i'_t, f'_t computed from m_t to avoid overflow.

This simple structural change has outsized algorithmic consequences: it gives xLSTM the ability to revise its memory decisively, and that translates to strong empirical gains on tasks requiring stateful revision and associative recall.



# From Scalars to Matrices: The mLSTM Memory That Remembers More

The classic LSTM stores information in scalar cell states and updates them with gated additions. That design—the constant error carousel—solved vanishing gradients and powered many sequence models, but it has limits: scalar cells compress information heavily, they are not naturally parallelizable when recurrent mixing is present, and they can struggle to revise or represent many items (e.g., rare tokens or long associative memories). The mLSTM from "xLSTM: Extended Long Short-Term Memory" addresses those limits by replacing scalar cells with a matrix memory and using a covariance (outer-product) update rule. This post pulls the key ideas apart, explains how the matrix memory works, how retrieval and normalization are handled, and why this design improves capacity and long-range associations while keeping parallelism.

## The core idea: matrix memory with covariance updates

Instead of a scalar cell \(c_t \in \mathbb{R}\), mLSTM maintains a matrix memory \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\). At each time step the model computes three vectors from the current input \(\mathbf{x}_t\): a key \(\mathbf{k}_t\), a value \(\mathbf{v}_t\), and a query \(\mathbf{q}_t\). The memory update is a covariance-style outer product of value and key:

\[
\mathbf{C}_t = f_t \, \mathbf{C}_{t-1} \;+\; i_t \, \mathbf{v}_t \mathbf{k}_t^\top,
\]

where \(i_t\) (input gate) controls how strongly the new outer product is written, and \(f_t\) (forget gate) decays the previous memory. This is the same family of updates used in Fast Weight Programmers and earlier associative memory models: store associations via rank-1 outer products that bind keys to values.

Why an outer product? Because the matrix \(\mathbf{C}\) naturally implements a linear associative mapping: later, given a query \(\mathbf{q}\), you retrieve (a proxy for) the value associated with keys aligned to that query by multiplying

\[
\tilde{\mathbf{h}}_t = \mathbf{C}_t \mathbf{q}_t.
\]

If the keys stored earlier are (approximately) orthogonal and \(\mathbf{q}_t\) aligns to a stored key \(\mathbf{k}_\tau\), then \(\mathbf{C}_t \mathbf{q}_t\) will contain a strong component along \(\mathbf{v}_\tau\). In short: keys write directions into the matrix, values are recovered via matrix-vector product with a query.

## Normalization and stabilization: making retrieval robust

A practical problem with this scheme is that the strength of retrieved signals depends on how strongly keys have been written and on future forget gates. The paper addresses this with a normalizer state \(\mathbf{n}_t\) that accumulates weighted keys:

\[
\mathbf{n}_t = f_t \, \mathbf{n}_{t-1} \;+\; i_t \, \mathbf{k}_t.
\]

When retrieving, the raw vector \(\mathbf{C}_t \mathbf{q}_t\) is scaled by the magnitude of the dot product between \(\mathbf{n}_t\) and the query to normalize for accumulated gate strength:

\[
\tilde{\mathbf{h}}_t = \frac{\mathbf{C}_t \mathbf{q}_t}{\max\{|\mathbf{n}_t^\top \mathbf{q}_t|, 1\}}.
\]

The absolute value and lower threshold avoid divisions by tiny numbers; the authors note they typically use threshold 1.0 as in prior work. Finally, an output gate \(\mathbf{o}_t\) (sigmoid) elementwise scales the retrieved \(\tilde{\mathbf{h}}_t\) to produce the hidden state \(\mathbf{h}_t = \mathbf{o}_t \odot \tilde{\mathbf{h}}_t\).

Additionally, mLSTM uses exponential activation for the input gate (\(i_t = \exp(\tilde{i}_t)\)) and either sigmoid or exponential for forget gates, with a stabilization trick (tracking a scalar log-scale state) so exponentials don't overflow. These choices let gates represent multiplicative write/decay factors more flexibly than bounded sigmoids.

## How this compares to attention and fast weights

At a high level, the mLSTM memory behaves like a form of linear attention or fast weights:

- Attention performs weighted sums of value vectors where weights depend on dot products between queries and stored keys. Standard (softmax) attention uses normalized pairwise interactions between all tokens and needs \(O(L^2)\) time or explicit approximations for linearity.
- Fast weight or outer-product memories store associations as outer products and retrieve with matrix-vector products. The mLSTM uses exactly this outer-product (covariance) storage, but embeds it in a gated recurrent update (write learning rate \(i_t\) and decay \(f_t\)) and adds normalization via \(\mathbf{n}_t\).

Key differences and relationships highlighted in the paper:

- The covariance update \(\mathbf{C} \leftarrow \mathbf{C} + \mathbf{v}\mathbf{k}^\top\) is equivalent in spirit to Fast Weight Programmers and to certain linear-attention formulations that can be written as incremental outer-product accumulations.
- Unlike full softmax attention, \(\mathbf{C}\) accumulates across time into a single matrix, so the memory size is independent of sequence length (constant memory per layer), and retrieval is \(O(d^2)\) per step rather than \(O(Ld^2)\) or quadratic in \(L\).
- Because mLSTM drops hidden-hidden mixing (no recurrent dependence on previous hidden state for key/value/gate projections), the recurrence on \(\mathbf{C}\) can be reformulated and implemented in parallel across tokens, making the design parallelizable similarly to modern attention approximations.

So mLSTM sits between classic attention and RNN fast-weights: it has associative outer-product storage like fast weights, an explicit normalizer for robust retrieval, and gates that control learning and decay.

## Why this boosts capacity for rare tokens and long-range associations

There are several reasons the matrix memory helps where scalar LSTMs struggle:

1. Larger representational degrees of freedom. A scalar cell compresses all stored information into one number per dimension; a matrix \(\mathbf{C}\) can store many pairwise associations across its \(d^2\) entries, enabling more orthogonalized representations of many items. That makes it easier to store rare or infrequent items without collapsing them into shared scalars.

2. Direct key–value binding. Outer products explicitly bind keys to values. When keys are well-structured (for example, after a layer norm and scaled projection as the paper uses), queries that match those keys retrieve the corresponding values with relatively high signal-to-noise. This is more effective for associative recall tasks than trying to cram associations into scalar cells.

3. Gate-controlled writing and decay. The input gate \(i_t\) acts like a learned write-strength (learning rate) and forget gate \(f_t\) like a decay. That allows the model to modulate how long particular associations persist, which is useful when some items (e.g., rare tokens) should be retained strongly.

4. Normalization reduces interference. The normalizer \(\mathbf{n}_t\) captures the cumulative key magnitude so that retrieval is scaled by expected total write strength along the query direction, reducing variance and improving robustness across different write histories.

Empirically (as reported in the paper), mLSTM-backed architectures (xLSTM variants with matrix memory) perform much better on associative recall tasks and improve perplexity particularly on rare token partitions compared to scalar LSTM baselines. In a synthetic multi-query associative recall benchmark, xLSTM variants outperform other non-Transformer models and the sLSTM head augments capacity further when combined appropriately.

## Parallelizability and computational trade-offs

A major practical advantage is that mLSTM can be implemented in a parallel fashion because its key/value/gate projections do not rely on the previous hidden state (no hidden-hidden mixing). That allows batched, parallel computation across sequence positions similar to how Transformer layers are batched—unlike sLSTM which retains recurrent mixing and thus is sequential.

But there is a trade-off: the matrix memory requires \(d\times d\) storage for \(\mathbf{C}\) and the update/retrieval are \(O(d^2)\) operations. This is heavier than a scalar LSTM per dimension but lighter than full quadratic-in-sequence-length attention when considered with long contexts, because \(\mathbf{C}\) does not grow with sequence length. The authors note that the matrix update uses no extra learned parameters (the keys/values/queries are linear projections), so the parameter count remains manageable. In practice, these matrix operations map well to GPU linear algebra, and the authors report that mLSTM computations can be parallelized and that wall-clock overheads are reasonable, though current CUDA kernels are not as optimized as FlashAttention and can be improved.

## Practical stabilizations

Because mLSTM uses exponential activations for writes (to allow unbounded positive write strengths), the authors include a stabilization technique that tracks log-scales and rescales gates to avoid overflow while leaving outputs and gradients unchanged. They also lower-bound the normalizer-based denominator to avoid divisions by small numbers. These engineering details make the method numerically stable in long sequences.

## Where mLSTM shines (and where it costs)

According to the experiments in the paper:

- Associative recall and synthetic memory tasks: mLSTM (and mixed xLSTM variants that include mLSTM blocks) performs significantly better than scalar-memory baselines and many other non-Transformer models, especially as the number of key–value pairs and context lengths grow.
- Rare token prediction: matrix memory increases capacity so the models better model rare tokens, yielding lower perplexities on rare-token partitions of Wikitext-103.
- Long context extrapolation: xLSTM variants with mLSTM maintain good perplexity when evaluated at longer contexts than those seen during training.
- Parallel inference: mLSTM can be parallelized and, because memory usage is constant in sequence length, it supports larger batch sizes and higher throughput at decoding compared to Transformers whose KV caches grow with sequence length.

Costs and limitations include the \(O(d^2)\) compute for the matrix operations and current lack of highly optimized kernels; careful initialization of forget gates; and the possibility of memory "overload" if extremely long contexts accumulate too many associations into a fixed-size \(\mathbf{C}\) (though the paper reports good performance up to 16k context length in their tests).

## Takeaway

mLSTM injects an explicit, gated matrix associative memory into the LSTM framework. By writing outer products of value and key vectors into a persistent matrix, normalizing retrieval, and using gated write/decay, it provides higher storage capacity and more robust associative recall than scalar LSTM cells. It bridges ideas from fast weights, linear attention, and classical associative memories, while keeping the model parallelizable and practical for large-scale sequence modeling. Empirically, that design improves rare-token modeling, associative recall accuracy, and long-range extrapolation relative to scalar-memory baselines, making mLSTM a compelling building block for memory-intensive sequence tasks.



# sLSTM vs mLSTM: When to Mix Memory and When to Parallelize

## Overview

xLSTM extends classical LSTM along two orthogonal axes: how memory is structured, and how gates are formed. The two concrete variants introduced in the paper — sLSTM and mLSTM — trade expressivity, memory capacity, and parallelizability in complementary ways. This post explains their design differences, the role of heads and cells, and the practical considerations captured by the xLSTM[$a$:$b$] notation (ratio of mLSTM- to sLSTM-based blocks) so you can reason about where to place each variant in an architecture.

## Core distinctions

At a high level:

- sLSTM = scalar memory per cell + exponential gating + memory mixing (recurrent hidden–hidden connections). It's an RNN-style cell that preserves the original LSTM ability to mix memory across time and across cells, but upgrades gating to exponential activations with normalization and stabilization.
- mLSTM = matrix memory + covariance (outer-product) update + exponential gating. It stores key–value pairs into a matrix \(\mathbf{C}\in\mathbb{R}^{d\times d}\), is retrieval-by-multiplication, and removes hidden–hidden recurrence to enable full parallelization across time steps.

Those differences imply different strengths and weaknesses which I summarize next.

## sLSTM: memory mixing and state tracking

What sLSTM keeps and adds

- Retains scalar cell state \(c_t\) per memory unit with additive "constant error carousel" style update: \(c_t = f_t c_{t-1} + i_t z_t\).
- Replaces (or augments) sigmoid gates by exponential gates for the input gate (and optionally the forget gate): \(i_t = \exp(\tilde{i}_t)\). Exponential gating gives the model the ability to sharply revise stored content.
- Adds a normalizer state \(n_t\) that tracks the effective strength of stored components through the future forget gates: \(n_t = f_t n_{t-1} + i_t\). The hidden output is normalized by dividing cell state by this normalizer: \(\tilde{h}_t = c_t/n_t\).
- Uses stabilization trick with a max-logger state \(m_t\) so exponentials do not overflow. The stabilized gates \(i'_t, f'_t\) are mathematically equivalent to the unstabilized equations but numerically safe.

Why this matters

- Memory mixing: sLSTM supports recurrent weight matrices from the previous hidden state into gate and input projections. That allows different memory cells to interact across time; this is crucial for state-tracking tasks (for example, regular language recognition or long-term sequence state maintenance). Models without memory mixing (standard Transformers/SSMs with no recurrence) can be fundamentally weaker at these tasks.
- Revision capability: exponential gating plus the normalizer enables revising past storage decisions effectively. In experiments, sLSTM outperforms vanilla LSTM on tasks where previously stored content must be revised or overwritten later in the sequence.

Tradeoffs

- Not parallelizable across time because of hidden–hidden recurrence (memory mixing). This makes wall-clock training/inference slower than fully parallelizable variants, though the authors implemented an optimized CUDA kernel that narrows the gap.
- Memory per cell remains scalar, so raw storage capacity is limited compared to matrix memories.

## mLSTM: matrix memory for capacity and parallelism

What mLSTM changes

- Memory becomes a matrix \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\). At each step a key \(\mathbf{k}_t\) and value \(\mathbf{v}_t\) are derived from the input and the matrix is updated by a covariance (outer-product) rule:
  \(\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \, \mathbf{v}_t \mathbf{k}_t^\top\).
- Retrieval uses matrix-vector multiplication with a query \(\mathbf{q}_t\): \(\tilde{\mathbf{h}}_t = \mathbf{C}_t \mathbf{q}_t / \max\{|\mathbf{n}_t^\top \mathbf{q}_t|, 1\}\), where \(\mathbf{n}_t\) is a normalizer that accumulates weighted keys similarly to sLSTM.
- Gates use exponential activation for input (and optionally for forget) and the same stabilization machinery as sLSTM.
- Importantly, mLSTM removes hidden–hidden recurrent connections (no memory mixing). That makes the recurrence expressible in a form that can be implemented in parallel across time steps (analogous to many linear-attention or fast-weight approaches).

Why this matters

- Much larger storage capacity: because memory is a matrix, the model can encode many key–value associations with retrieval density that scales with \(d^2\) operations even though no extra parameters are needed for the memory itself.
- Parallelizability: without hidden–hidden recurrence, the entire recurrent forward pass can be reformulated into a parallel algorithm (the paper provides a parallel version). This makes mLSTM suitable for large-scale training and fast inference where sequence-parallel operations are important.
- Good at associative memory tasks: covariance update rule is closely related to Fast Weights and associative memory paradigms and performs well on multi-query associative recall and long-context retrieval tasks.

Tradeoffs

- Computational cost: updating and multiplying \(d\times d\) matrices is more expensive (compute and memory) than scalar-cell updates. The matrix memory increases per-step FLOPs, though it does not require additional trainable parameters and can be parallelized on modern accelerators.
- No memory mixing: removing hidden–hidden recurrence reduces expressivity in tasks that require interacting state across cells in a recurrent way (state tracking). Some formal languages and stateful computations are harder without recurrence.

## Heads, cells, and the xLSTM[$a$:$b$] stacking strategy

Heads vs. cells

- Multiple cells: both sLSTM and mLSTM can be extended to multiple memory cells. In sLSTM multiple scalar cells can be mixed via recurrent matrices; in mLSTM multiple cells are equivalent to multiple heads (since there is no mixing).
- Multiple heads in sLSTM: sLSTM can be organized into multiple heads where each head has its own set of cells. Important nuance: sLSTM allows memory mixing within a head but not across heads. This gives a structured way to partition memory and interactions.
- For mLSTM, "multiple heads" and "multiple cells" are essentially the same concept because each head/cell maintains its own matrix memory and there is no cross-head recurrent mixing.

xLSTM[$a$:$b$] ratio and what it expresses

- The paper uses xLSTM[$a$:$b$] to denote the ratio of mLSTM-based blocks to sLSTM-based blocks in a stacked residual architecture. For example, xLSTM[7:1] with 8 blocks means 7 blocks are mLSTM-based and 1 block is sLSTM-based.
- This gives a practical knob to balance the tradeoffs:
  - Increasing the proportion of mLSTM blocks (larger \(a\)) biases the model toward higher memory capacity and parallelism.
  - Increasing the proportion of sLSTM blocks (larger \(b\)) injects memory mixing and stronger state-tracking capability.

Why mix them?

- Expressivity vs. throughput: some tasks (state-tracking, formal languages, code evaluation) require the recurrent mixing that sLSTM provides. Other tasks (large-scale language modeling with long contexts, associative recall) benefit from mLSTM’s matrix memory and parallelism. Combining them lets the model retain state-tracking where needed while exploiting parallelizable, high-capacity memory for bulk storage and retrieval.
- In experiments, mixed stacks like xLSTM[7:1] (mostly mLSTM with a sprinkling of sLSTM) performed very well: they preserved much of the parallel efficiency and capacity of mLSTM while leveraging sLSTM’s recurrent mixing to improve expressivity on tasks that need it.

## Practical guidance: when to use which

- Use sLSTM when:
  - The task requires complex state tracking, compositional reasoning over long spans, or operations that benefit from recurrent interactions between memory cells.
  - You can afford sequential processing or have optimized custom kernels (the paper’s CUDA sLSTM kernel reduced the gap significantly).
  - You need the model to be able to revise or reweight stored scalar content dynamically with strong gating behavior.

- Use mLSTM when:
  - You need large storage capacity per time step (associative recall, value-rich contexts).
  - Parallelization across sequence positions is critical for training throughput or inference latency.
  - You want a compressive memory that scales in practice even for long contexts, and you can tolerate higher per-step FLOPs for matrix updates.

- Use a mix (xLSTM[$a$:$b$]) when:
  - You want the best of both worlds: mostly parallel, high-capacity memory plus a smaller number of recurrent-mixing blocks to handle stateful computations.
  - A typical configuration might heavily favor mLSTM blocks (e.g., xLSTM[7:1] or xLSTM[1:0] for purely mLSTM), but include some sLSTM blocks to enable state tracking where needed. The paper’s experiments show that mixed architectures outperform purely recurrent or purely parallel models on many language tasks.

## Engineering and performance notes

- Stabilization: both variants use the same stabilization trick to make exponential gates numerically safe (the \(m_t\) max-logger and the derived stabilized gates). This is crucial when using exponentials in practice.
- Normalizer state: both sLSTM and mLSTM track a normalizer that sums input-gate-weighted future forget gates; dividing by this normalizer makes retrieved outputs comparable and prevents uncontrolled growth.
- Complexity: mLSTM has higher per-step compute due to \(d\times d\) matrix updates and multiplications but is parallelizable across time. sLSTM is lighter per-step but sequential due to recurrence.
- Memory vs. sequence length: xLSTM (both variants) has linear compute and constant memory with respect to sequence length, in contrast to the quadratic memory of dense Transformers. That constant-memory property allows mLSTM/xLSTM to scale to longer contexts in practice.

## Takeaway

sLSTM and mLSTM implement two complementary ways of extending LSTM ideas:

- sLSTM = exponential gating + scalar cell + memory mixing → best for expressive stateful computations and tasks needing recurrence.
- mLSTM = exponential gating + matrix memory + covariance update → best for capacity and parallelism (associative memory, long contexts).

Stacking them (xLSTM[$a$:$b$]) is a principled way to tune the tradeoff between expressivity and throughput. The paper shows that a predominantly mLSTM architecture augmented by some sLSTM blocks captures much of the power of both approaches: it achieves strong language-modeling performance, preserves long-context capabilities, and keeps the door open for efficient parallel training and inference.



# Inside the xLSTM Block: Residual Backbones That Scale Like LLMs

xLSTM reimagines the LSTM cell for modern large-scale language modeling by combining two innovations: exponential gating (to fix reviseability and stability issues) and richer memory structures (scalar and matrix memories). But the building block that makes these ideas practical at scale is the xLSTM block — a residual backbone that embeds either an sLSTM or an mLSTM into a pre/post up-projection pattern with pre-LayerNorm. This post explains the xLSTM block design choices, why we sometimes project up before the recurrent operation and sometimes after, where LayerNorm lives, and how non-linear summarization in higher-dimensional spaces (invoking Cover’s Theorem) improves separability of histories. Finally, we sketch how stacking these blocks produces full xLSTM architectures that scale like modern LLMs.

## What an xLSTM block must do

At its core, an xLSTM block needs to non-linearly summarize the entire past context into a representation that helps predict the next token. Two practical constraints guide the block design:

- The block must fit into a residual-stack architecture (the same scaffolding used by contemporary LLMs).
- The recurrent/memory operation (sLSTM or mLSTM) should operate in the space where it is most effective: sometimes the original embedding space suffices, sometimes a higher-dimensional space is better for memory capacity.

This leads to two complementary residual block patterns used in xLSTM: post up-projection and pre up-projection.

## Pre- vs. post-up-projection: the intuitive difference

- Post up-projection block (used with sLSTM): The block first summarizes the past using the sLSTM in the original embedding dimension, then projects the result up into a higher-dimensional space, applies a non-linearity, and projects back down. Intuitively, sLSTM’s scalar memory and its memory-mixing recurrent connections operate effectively in the model’s base embedding space; the up-projection after the recurrent step gives the block extra expressive power for the residual path while keeping the recurrent dynamics compact.

- Pre up-projection block (used with mLSTM): The block first linearly maps inputs into a higher-dimensional space, runs the mLSTM recurrence there, then projects back down. This is because mLSTM’s matrix memory $\mathbf{C}\in\mathbb{R}^{d\times d}$ benefits from operating in a higher-dimensional coding space: larger $d$ increases storage capacity and retrieval separability for key--value updates (the mLSTM update is $\mathbf{C}_t = f_t\,\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t \mathbf{k}_t^\top$). Running the matrix memory in the up-projected space maximizes the benefit of the covariance-style updates and the larger associative memory.

So: choose post up-projection for sLSTM (scalar memory + memory mixing), and pre up-projection for mLSTM (matrix memory + parallelizable covariance updates).

## Where LayerNorm goes: pre-LayerNorm for stability in deep stacks

xLSTM blocks are placed inside a residual stacking scheme with pre-LayerNorm (LayerNorm applied before the block’s main operations). Concretely, each residual branch receives a normalized input and then performs the up/down projections and the recurrent/memory operation. Using pre-LayerNorm follows the modern LLM convention: it stabilizes training in very deep stacked architectures and improves optimizer behavior when residuals are summed across many layers.

For mLSTM blocks the paper assumes a layer-norm before the projections to keys/values/queries, which also justifies treating keys and values as zero-mean when using covariance updates. For sLSTM (with memory mixing), pre-LayerNorm likewise improves stability when hidden-hidden mixing and gating interact across many stacked layers.

## Why summarize non-linearly in a higher-dimensional space? (Cover’s Theorem intuition)

Cover’s Theorem provides the intuition behind the up-projection choice: a complex decision boundary that is not linearly separable in low dimensions can often be made linearly separable after a non-linear mapping into a higher-dimensional space. In the language-modeling setting, the “classes” to separate are different past histories or contexts that require different next-token predictions. By embedding histories into a higher-dimensional nonlinear feature space inside an xLSTM block, the model makes those histories easier to distinguish downstream with linear (or shallow) operations.

Mechanically this is realized by the up-projection + nonlinearity (or the nonlinearity inside the recurrent cell in the up-projected space). For mLSTM this means the matrix memory operates on more expressive, higher-dimensional key/value/query vectors; for sLSTM it means the residual path can enrich the signal the scalar memories provide.

## How exponential gating and normalizers fit into the block

Exponential gating (using $\exp(\cdot)$ for input and optionally forget gates) is introduced to help revise storage decisions and to implement gating dynamics that behave multiplicatively across many time steps. Because raw exponentials can overflow and produce unstable magnitudes, xLSTM blocks include stabilizers: an auxiliary state $m_t$ that normalizes gate magnitudes so that replacing $i_t$ and $f_t$ by stabilized equivalents does not change network outputs or gradients.

Both sLSTM and mLSTM maintain a normalizer state $n_t$ that accumulates weighted contributions of inputs and gates (for sLSTM scalar normalizer, for mLSTM a vector of summed keys). The block’s read-out divides the raw accumulated memory by this normalizer (or a bounded scalar derived from it) so that retrieved signals are scale-aware and numerically well behaved.

Putting this inside the residual block with pre-LayerNorm means the block’s projections see normalized inputs and the gating/stabilization interaction remains well-conditioned across layers.

## Putting many blocks together: residually stacked xLSTM architectures

An xLSTM architecture is created by residually stacking many xLSTM blocks (pre-LayerNorm residual backbone). Each block performs:

1. Pre-LayerNorm on the input.
2. A projection schedule (pre or post up-projection depending on whether the block contains an mLSTM or sLSTM).
3. The recurrent/memory operation (mLSTM matrix-memory updates in parallelizable form, or sLSTM scalar-memory with memory mixing).
4. Optional non-linearity and down-projection back to base dimension.
5. Residual add to the input.

Stacking dozens of such blocks yields deep models that mimic the architectural pattern that made Transformers effective (residual + pre-LayerNorm) while replacing attention with recurrent/memory primitives better suited to linear-in-sequence complexity and compressive long-term storage.

The paper explores mixed stacks: e.g., xLSTM[7:1] meaning 7 mLSTM-based blocks and 1 sLSTM-based block out of 8, showing that combining both block types in a residual stack can provide both high memory capacity and memory-mixing expressivity.

## Practical trade-offs inside a block

- Computational cost: mLSTM blocks operate on $d\times d$ matrix memories, which increases compute compared to scalar memories but yields much larger storage capacity. Because those operations are parameter-free updates and can be parallelized, they integrate well into GPU pipelines (though optimized CUDA kernels could further improve wall-clock times).
- Parallelism: mLSTM can be implemented in a parallel fashion (no hidden-hidden mixing), which is favorable for throughput. sLSTM uses memory mixing (recurrent hidden-hidden weights), so it is inherently sequential; in practice the authors implemented an efficient CUDA kernel to make sLSTM only modestly slower than the parallel mLSTM.
- Numerical stability: exponential gates and covariance updates require normalization and stabilizers; these are included in-block to avoid overflow and to ensure gradient correctness.

## Bottom line

The xLSTM block is not a single monolithic recurrent unit but a small residual module that places the recurrent/memory primitive in the space where it is most effective:

- Use pre up-projection when you want to maximize associative memory capacity (mLSTM).
- Use post up-projection when you rely on scalar memories with memory mixing and want compact recurrence (sLSTM).
- Always use pre-LayerNorm in the residual backbone for stable deep stacking.
- Normalize and stabilize exponential gates and memory normalizers inside the block to keep training numerically robust.

Stack a lot of these blocks, mixing sLSTM and mLSTM blocks as needed, and you get an xLSTM architecture that preserves the residual/depth advantages of modern LLMs while offering linear-in-context complexity, richer memory primitives, and the ability to revise stored information. The result, as shown in the paper, is competitive scaling behavior and strong language-modeling performance against Transformers and state-space competitors.



# Performance Report: xLSTM vs Transformers, SSMs, and RWKV

This post summarizes the experimental evaluation from "xLSTM: Extended Long Short-Term Memory", focusing on language modeling and memory tasks. The paper introduces two LSTM extensions—sLSTM (scalar memory with exponential gating and memory mixing) and mLSTM (matrix memory with covariance updates and parallelizable recurrence)—and integrates them into residually stacked xLSTM architectures. Below I highlight the empirical claims and where xLSTM stands relative to Transformers, State Space Models (SSMs), and RWKV-style RNNs.

## Quick reminder: what changed in xLSTM
- Exponential gating: input (and optionally forget) gates use an exponential activation with a stabilizer to allow non-saturating, revisable writes.
- sLSTM: scalar cell with a normalizer state and new memory-mixing patterns (including multi-heads within sLSTM).
- mLSTM: matrix memory \(\mathbf{C}\in\mathbb{R}^{d\times d}\) updated by a covariance rule \(\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \mathbf{v}_t \mathbf{k}_t^\top\); retrieval is by multiplication with a query and normalization by a normalizer state.
- xLSTM architectures stack residual blocks that contain either sLSTM (post up-projection blocks) or mLSTM (pre up-projection blocks), trading off memory capacity and parallelizability.

All experimental comparisons below were done within the paper's described setup (same autoregressive training on SlimPajama subsets, comparable model sizes and residual block counts).

## Highlights from the experiments

Overall finding: xLSTM variants (combinations of mLSTM and sLSTM blocks) perform favorably against state-of-the-art Transformer and SSM baselines, and outperform several recent RNN-based approaches in both language modeling and memory-oriented tasks.

### 15B-token training (SlimPajama, validation perplexity)
- Models trained on 15B tokens were evaluated by validation perplexity. xLSTM outperformed the other methods in this setting, beating representatives from:
  - Transformers (e.g., GPT-3, Llama),
  - State Space Models (e.g., H3, Mamba),
  - RNN / linear-attention families (e.g., RWKV variants, GLA, HGRN/HGRN2, RetNet, Hyena).
- Ablations attribute the gains to both exponential gating and the matrix memory: adding exponential gating and then the matrix memory incrementally improved perplexity over a vanilla LSTM baseline integrated into residual blocks.

(Exact numeric perplexities are reported in the paper tables; the qualitative outcome is that xLSTM had the lowest validation perplexity among the compared models trained on the same 15B-token corpus.)

### Associative recall / memory capacity (Multi-Query Associative Recall)
- Task: memorize many random key-value pairs (up to 256 pairs) and later retrieve values given keys; contexts extended up to length 2048.
- xLSTM[1:1] (mixed mLSTM+sLSTM blocks) performed best among all non-Transformer models and remained competitive overall. Transformers retain an advantage where memory scales exponentially with coding dimension, but xLSTM narrowed the gap significantly.
- Notably, including sLSTM blocks did not harm memory capacity; sLSTM appeared to leverage mLSTM capacity, improving performance at the hardest settings.

### Long-context extrapolation (trained with context 2048, tested up to 16384)
- For 1.3B models trained on 300B tokens (see below), xLSTM maintained low perplexities when evaluated at longer contexts (up to 16k), whereas the other models (RWKV-4, Llama, Mamba) degraded more rapidly.
- This indicates stronger extrapolation/stability of xLSTM to longer sequence lengths under the tested setups.

### Large-scale language modeling (300B-token training)
- Models trained on 300B tokens were compared across several axes: validation perplexity, downstream common-sense reasoning tasks, domain-wise perplexity over PALOMA, and scaling behavior.
- Validation & downstream tasks: Across model sizes (125M, 350M, 760M, 1.3B), xLSTM variants (both xLSTM[1:0] and xLSTM[7:1]) achieved the best validation perplexities and were the top performers on the majority of downstream tasks. The one exception noted was ARC where Mamba sometimes performed better.
- PALOMA benchmark (571 domains): xLSTM[1:0] showed strong, consistent gains:
  - Lower perplexity than Mamba in 568/571 domains (99.5%),
  - Lower perplexity than Llama in 486/571 domains (85.1%),
  - Lower perplexity than RWKV-4 in 570/571 domains (99.8%).
  These results suggest xLSTM generalizes well across many textual domains.

### Scaling laws
- When fitting power-law scaling curves (loss vs model size), xLSTM shares similar slopes with the other methods but with a favorable offset. That is, xLSTM models achieve lower loss/perplexity at the same sizes, and projection suggests xLSTM will remain competitive at larger scales.

### Inference / throughput observations
- xLSTM (being recurrent with compressed state) has linear compute and constant memory in sequence length, which enables higher batch sizes and greater decoding throughput than Transformers in practice. The paper reports:
  - Linear generation-time scaling for recurrent models (xLSTM, RWKV, Mamba) vs quadratic for the tested Transformer implementation (Llama).
  - xLSTM attained the highest maximal throughput among the compared models due to lower memory footprint for long contexts and higher usable batch sizes.
- Implementation caveats: current CUDA kernels are not fully optimized; mLSTM implementation is slower than optimized FlashAttention Transformer kernels but is parallelizable and expected to improve with optimized kernels.

## Synthetic / formal-language benchmarks and LRA
- Formal language tasks that require state tracking (e.g., parity, other regular grammars) show that models lacking memory-mixing (many Transformers and SSMs) cannot solve certain tasks, while xLSTM variants with memory mixing (sLSTM) succeed.
- On the Long Range Arena benchmarks, xLSTM demonstrated strong, consistent performance across tasks designed to stress long-context processing.

## Limits and caveats called out by the authors
- sLSTM memory mixing prevents straightforward parallelization; their custom CUDA kernel makes sLSTM reasonably fast (within ~2x of mLSTM), but further optimization would help.
- mLSTM carries \(d\times d\) matrix updates which are computationally heavy; current kernels are not fully optimized and are slower than FlashAttention in the reported codebase.
- The matrix memory, while independent of sequence length, could be overloaded if sequence content exceeds capacity for very long contexts; empirical tests up to 16k did not show a problem in the experiments.
- Initialization of forget gates and careful hyperparameter tuning are important; the experiments did not exhaustively optimize xLSTM hyperparameters for largest-scale regimes.

## Takeaway
xLSTM—by combining exponential gating (for revisable writes and stabilized large gates), scalar memory with new mixing (sLSTM), and a large matrix memory with covariance updates (mLSTM)—demonstrates that an updated LSTM family can be scaled to compete with modern Transformers and SSMs. Empirically, xLSTM variants achieved the best validation perplexities among compared methods at 15B-token training, generalized strongly across 571 PALOMA domains, extrapolated better to much longer contexts, and showed robust associative recall behavior. Scaling behavior suggests xLSTM will remain competitive at larger sizes, and throughput advantages (constant memory in context length) make it an attractive option for long-context decoding and memory-constrained deployments.

For implementation details, model hyperparameters, and the full numeric results and ablations, refer to the paper and the provided code repository: https://github.com/NX-AI/xlstm.



# Efficiency at Scale: Linear Compute, Constant Memory, and Throughput

Modern large language models are dominated by Transformers, whose self-attention gives excellent performance but comes with a well-known cost: generation at runtime scales quadratically in the context length and requires cache memory proportional to context length. xLSTM revisits recurrent designs (LSTM-derived) and demonstrates a different trade-off: linear-time generation with constant memory in context length, enabling larger batch sizes and higher throughput in practice. This post walks through why that happens, the practical implementations in xLSTM, and the latency vs. throughput trade-offs you should expect.

## Why recurrent xLSTM gives linear time and constant memory

The core difference is how state is represented and advanced across tokens.

- Transformers perform per-token attention over all past tokens; a single decode step requires combining the current query with an ever-growing set of keys and values. This yields O(L^2) compute during full self-attention prefill or O(L) compute per new token with an O(L) cache (where L is context length). Memory for cached keys/values grows with L.

- xLSTM keeps a compressed recurrent state (the memory) that summarizes history into a fixed-size object independent of context length. Two memory variants in xLSTM are central to this:
  - sLSTM: scalar (or small-vector) cells with gating and memory mixing (hidden–hidden recurrences).
  - mLSTM: a matrix memory C_t ∈ ℝ^{d×d} updated by a covariance (outer-product) rule C_t = f_t C_{t-1} + i_t v_t k_t^T.

Because both variants advance a fixed-size memory per step, compute per new token is constant in L and memory usage does not grow with context length. Thus generation time scales linearly with the number of generated tokens (O(L) total) and per-step compute/working memory are constant wrt context length.

## Practical throughput advantages

Constant memory per sequence gives two practical effects in decoding:

1. You can sustain much larger batch sizes before exhausting GPU memory. Unlike Transformers, whose KV cache quickly consumes memory when L grows, xLSTM’s fixed-size state lets you increase batch size to improve hardware utilization and overall tokens-per-second throughput.

2. Decoding time scales linearly with sequence length. In the experiments reported, xLSTM and other recurrent models show linear generation time versus context length, while Llama (Transformer) shows the quadratic wall-clock effect from attention. Measured throughput at 1.3B scale indicates xLSTM achieves higher maximal throughput than a comparable Transformer when batching aggressively because it isn’t limited by cache memory.

The paper quantifies this: xLSTM outperforms Llama and RWKV-4 on decoding throughput measurements (higher throughput for larger batch sizes and longer contexts), and 99.5–99.8% of 571 PALOMA domains had lower perplexity for xLSTM compared to some baselines, indicating that the efficiency gains do not come at the cost of modeling quality.

## Parallel mLSTM vs. non-parallel sLSTM: implementation trade-offs

xLSTM includes two variants with different parallelization properties and cost profiles.

- mLSTM (matrix memory)
  - Parallelizable: Because mLSTM abandons hidden–hidden recurrent mixing, its recurrence can be reformulated into a parallel implementation (similar in spirit to other linear-time mechanisms). The matrix update uses outer products and a decay/input gating: C_t = f_t C_{t-1} + i_t v_t k_t^T.
  - Constant memory and linear compute in context length remain true here.
  - Computational overhead: mLSTM maintains a d×d matrix and performs d×d updates and d×d multiplies for retrieval (C_t q_t). This is computationally heavier than scalar recurrent cells, and the paper notes the current CUDA kernels are not yet optimized; the implementation used was about 4× slower than FlashAttention or the scan used in Mamba. However, these operations are parameter-free and map well to parallel matrix kernels, so optimized GPU kernels could substantially reduce the wall-clock gap.

- sLSTM (scalar memory with memory mixing)
  - Not parallelizable across time due to recurrent hidden–hidden connections (memory mixing), meaning it must be scanned sequentially in time.
  - Highly optimized custom CUDA: The authors developed a specialized CUDA kernel with register-level optimizations that achieves performance competitive with mLSTM. In practice their optimized sLSTM kernel is typically less than 2× slower than the parallel mLSTM implementation. So although sLSTM cannot be parallelized in the same way, careful low-level engineering closes much of the runtime gap.

In short: mLSTM gives algorithmic parallelism and constant memory with straightforward batching advantages, while sLSTM offers stronger expressivity via memory mixing but requires custom sequential kernels to be efficient.

## Latency vs. throughput — practical trade-offs

When choosing a model for generation you often balance single-request latency and overall throughput.

- Latency (time to produce the next token for a single stream): xLSTM models have per-step work that is independent of L, so single-stream latency grows slowly with context (linearly with steps generated, but each step has fixed work). In practice, latency will be dominated by the cost of the matrix operations (for mLSTM) or the sequential kernel (for sLSTM). An optimized mLSTM kernel can yield low latency comparable to attention-based decode with an efficient KV cache; sLSTM sequential kernels are slightly slower per-step but within a small constant factor (the paper reports <2× for their optimized sLSTM vs. mLSTM).

- Throughput (tokens/sec across many parallel streams): xLSTM wins here. Because the working memory per stream is fixed, you can batch many streams to amortize kernel overhead and fully utilize the GPU. Transformers hit an early memory ceiling from KV caches, limiting batch sizes and thus peak throughput. The experiments show xLSTM achieves higher maximal throughput than Llama by using much larger batch sizes.

Practical guidance:
- If your priority is maximizing tokens/sec on many concurrent requests (e.g., high-throughput inference), xLSTM’s constant-memory design allows much larger batching and higher throughput than Transformer baselines.
- If you need the absolute lowest single-stream latency and have access to extremely optimized FlashAttention-like Transformer decoders with a small context, Transformers can be competitive. But as contexts grow and multi-request batching is required, xLSTM’s scaling becomes increasingly favorable.
- Choose mLSTM when you want a fully parallelizable pipeline and are prepared to invest in optimized d×d kernels. Choose sLSTM when you need the memory-mixing expressivity and can accept sequential kernels; the paper’s custom CUDA implementation shows the sequential cost can be kept small.

## Costs and limitations to keep in mind

xLSTM’s efficiency advantages are not free:

- mLSTM’s matrix memory requires O(d^2) computation per update and retrieval. This can be costly for large d, and current public implementations in the paper were about 4× slower than optimized attention kernels. The d×d memory does not add trainable parameters, but it does add compute.
- sLSTM’s memory mixing prevents the straightforward time-parallel implementations available to mLSTM; achieving competitive runtimes requires careful low-level CUDA engineering (the authors report <2× slowdown compared to their mLSTM implementation).
- The matrix memory is finite and compressive; extremely long contexts could in principle overload the matrix unless gating/forget initializations are chosen carefully. Empirically xLSTM handled contexts up to 16k in their experiments.
- The paper did not exhaustively optimize CUDA kernels and hyperparameters for the largest architectures; further engineering effort could improve both latency and throughput.

## Takeaway

xLSTM shows that revisiting recurrent ideas with modern twists—exponential gates, matrix memory updates, and careful residual backbones—delivers a compelling trade-off: linear-time generation and constant memory in context length. That enables much larger batch sizes and higher decoding throughput than Transformers in practice, at comparable or better modeling performance in the reported language modeling experiments. The key engineering work is in efficient implementations: mLSTM benefits from optimized d×d matrix kernels, while sLSTM benefits from carefully tuned sequential CUDA kernels. If your use case needs high throughput across many concurrent streams or very long contexts without exploding KV caches, xLSTM-style recurrent designs are worth evaluating.



# Limitations and What’s Next: Faster Kernels, Longer Contexts, Better Inits

xLSTM extends classical LSTM ideas with two main innovations: exponential gating (to enable revisable storage and stronger gating dynamics) and enlarged memory structures (sLSTM with enhanced scalar-cell mixing, and mLSTM with a matrix memory updated by an outer-product / covariance rule). The paper shows these changes yield strong language-modeling performance and favorable scaling behavior versus Transformers and State Space Models. That said, xLSTM is not without concrete bottlenecks. This post gives an honest, focused look at the current limitations reported in the paper, why they matter, and practical directions to address them. I only summarize findings and recommendations that are grounded in the paper.

## Short list of current bottlenecks

- sLSTM non-parallelism. Memory mixing via hidden–hidden recurrent connections prevents an efficient fully-parallel implementation. The team implemented a fast CUDA kernel that brings sLSTM runtime down, but it remains not fully parallel and currently about up to 2× slower than the parallel mLSTM implementation.

- mLSTM d×d complexity. The matrix memory in mLSTM is a dense \(\mathbb{R}^{d\times d}\) structure with outer-product updates (\(\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \,\mathbf{v}_t \mathbf{k}_t^\top\)). This delivers large storage capacity, but computing and updating \(d\times d\) matrices is computationally heavy.

- Kernel maturity and implementation gaps. The mLSTM CUDA kernels are not yet optimized; in the current implementation mLSTM is about 4× slower than highly optimized attention kernels (e.g., FlashAttention), meaning wall-clock runtimes could be materially improved with better kernels.

- Forget/gate initialization sensitivity. The paper notes that the initialization of forget gates must be chosen carefully. Improper initialization can hinder learning/stability when using exponential gating and matrix memory.

- Potential memory overload at very long contexts. Although xLSTM’s memory is sequence-length independent (it compresses past context), the matrix memory accumulates contributions over time; in principle, extremely long contexts could “overload” the capacity of a fixed-size \(\mathbf{C}\). Empirically, contexts up to 16k did not show practical limits in experiments, but the risk is noted.

- Hyperparameter and architecture tuning unfinished. Large-scale xLSTM models reported in the paper were not exhaustively optimized; achieving maximal performance likely requires more extensive hyperparameter and architecture search.

## Why these matter (brief)

- Parallelism and kernel efficiency translate directly into throughput for training and generation. If sLSTM cannot be accelerated to the same level as parallel modules, its usage at scale is constrained.

- The \(d\times d\) cost limits attainable model width for a given compute budget. Dense outer-product updates also raise peak memory bandwidth requirements even if final memory usage is constant with respect to sequence length.

- Initialization sensitivity is especially important for exponential gates: exponential activations can grow or vanish quickly; stable training depends on careful bias/scale choices and the stabilizer state introduced in the paper.

- Although compressive memory is attractive (constant memory vs sequence length), any fixed-capacity memory implies a tradeoff between context length and fidelity of retrieval; for some tasks the matrix memory may require scaling or structural changes to avoid saturation.

## Concrete paths to improvement (aligned with the paper)

1. Kernel engineering and compilers
   - Implement FlashAttention-style optimizations for the mLSTM matrix updates and retrievals. The paper points out that mLSTM computations can be parallelized like FlashAttention; adopting similar tiling, fused kernels, and attention-like memory layouts should reduce the current ~4× slowdown.
   - Produce highly optimized CUDA kernels for sLSTM recurrent components. The authors already provided a CUDA kernel that narrows the gap (sLSTM currently <2× slower than mLSTM); continuing kernel-level optimizations (register tiling, warp-level primitives, fused elementwise ops) can close the gap further.
   - Explore backend compilation strategies (e.g., TVM, Triton, torch.compile) to generate device-optimized kernels for outer-product updates and stabilizer math.

2. Algorithmic reductions of d×d cost
   - Low-rank approximations: represent \(\mathbf{C}\) in factorized form (e.g., \(\mathbf{C}\approx U V^\top\)) and update factors instead of full dense matrices, reducing compute/storage from \(O(d^2)\) to \(O(dk)\) for rank \(k\).
   - Structured matrices: use block-diagonal, banded, or other structured parameterizations to trade capacity for compute.
   - Sparse or product-key sparsity: selectively update and read sub-blocks of \(\mathbf{C}\) based on gate-driven attention-like scores.
   - Mixed-precision and quantization-aware updates: exploit lower precision or accumulation formats for parts of the matrix to reduce memory bandwidth and cache pressure.

3. Memory management and hierarchical strategies
   - Multi-resolution or hierarchical memories: keep a compact global matrix and additional local / chunked matrices that capture recent context with higher fidelity.
   - Resetting or decay schedules: besides learned forget gates \(f_t\), schedule or adapt decay diagnostics to avoid over-accumulation over extremely long sequences.
   - Capacity-aware gating: make input gate magnitudes \(i_t\) dependent on a learned “memory fullness” signal to throttle updates when capacity nears saturation.

4. Better initialization and stabilization heuristics
   - Systematic studies of forget-bias initialization for exponential gates. The paper emphasizes careful initialization; a small set of recommended defaults (learned or data-dependent) would make training more robust.
   - Use the stabilizer state \(m_t\) (as in the paper) consistently and test variants (e.g., soft thresholds) to control numerical range from exponentials.
   - Warmup schedules and gradient clipping tuned for gates with exponential activations.

5. Extensive hyperparameter and architecture search
   - Explore varying the ratio of mLSTM to sLSTM blocks (e.g., xLSTM[$a$:$b$]) to trade memory capacity and parallelism for a target workload.
   - Tune widths \(d\) versus number of blocks to find Pareto-efficient points given \(d\times d\) cost.
   - Optimize layer-normalization, residual scales, and gating parameterizations jointly at large scale.

6. Hybrid and approximate parallelization approaches
   - For sLSTM, investigate semi-parallel schemes that process chunks in parallel with synchronized memory mixing across chunk boundaries, improving utilization while preserving some memory-mixing expressivity.
   - Investigate approximating hidden–hidden mixing using blockwise or restricted recurrent matrices that permit more parallelism.

## Practical short-term wins

- Prioritize implementing FlashAttention-like GPU kernels for the mLSTM outer-product updates and retrievals. The paper makes it clear these operations are parallelizable and would benefit greatly from kernel-level optimization.

- Release tuned initialization defaults (forget-bias, gate scales) and example recipes for stable training with exponential gates and stabilizer \(m_t\).

- Provide low-rank or block-matrix variants of mLSTM as drop-in alternatives for practitioners constrained by compute.

## Longer-term research directions

- The matrix memory idea combined with exponential gating opens a path toward richer, compressive associative memories that can be trained end-to-end. There is room to explore theoretical capacity limits, tradeoffs between size and robustness, and compression schemes that preserve retrieval SNR.

- Integrating xLSTM-style compressive memory into RL agents or continuous control stacks where persistent state and long-term credit assignment matter could be impactful. The paper highlights RL as a promising application because LSTMs historically shine in such domains.

- Time-series forecasting and physical system modeling (where constant-memory, linear-in-context complexity is essential on edge devices) are natural domains for optimized xLSTM variants. The compressive memory and constant memory footprint are attractive properties.

## Takeaway

xLSTM demonstrates that carefully modernized LSTM ideas—exponential gating plus richer memory structures—can compete with Transformers and SSMs in language modeling and scaling. The remaining obstacles are mostly engineering and algorithmic: faster, FlashAttention-like kernels for mLSTM; further optimizations for sLSTM’s recurrent kernel; strategies to reduce or structure the \(d\times d\) cost; and robust initialization recipes for exponential gates.

Tackling these bottlenecks should be straightforward in principle and would unlock faster training and inference, broader adoption, and more confident deployment in RL, time series, and physical modeling tasks where LSTM-style recurrence and compressive memories have distinct advantages. The paper already points to these directions and provides initial implementations and empirical guidance; the path forward is clear and actionable.
