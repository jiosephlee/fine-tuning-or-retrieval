# QLoRA in Plain English: How 4-Bit Finetuning Put Giant LLMs on a Single GPU

## TL;DR
QLoRA is a practical trick that lets you finetune very large language models (up to 65B parameters) on a single 48 GB GPU without losing the accuracy of standard 16-bit finetuning. The core idea is simple and powerful: keep the pretrained model weights frozen and stored in an extremely memory-efficient 4-bit format, add a small set of trainable low-rank adapters (LoRA), and run backpropagation through the quantized weights by dequantizing to a higher-precision compute type. Two quantization innovations (NF4 and Double Quantization) plus a memory-management technique (Paged Optimizers) make this work in practice. The result: state-of-the-art open models (Guanaco family) that rival ChatGPT on common chat benchmarks, trained on a single GPU in hours.

## The problem QLoRA solves
Finetuning a large pretrained model normally requires holding:
- model weights,
- optimizer states,
- activation gradients,

all in GPU memory. For a 65B model that easily exceeds hundreds of gigabytes, so researchers long needed multi-GPU servers. Existing low-bit quantization methods made large models cheap at inference time, but they break down for training because backprop needs more precise math and intermediate values.

QLoRA changes that picture: it reduces the storage footprint of the pretrained weights to 4 bits while preserving full-precision behavior during training, by never updating those weights and only training small adapter modules. This slashes memory needs so dramatically that a 65B model can be finetuned on a single 48 GB GPU.

## The big idea — three ingredients
QLoRA combines three mutually supporting ideas.

1) Freeze the base model and use LoRA adapters for learning
- Instead of updating the huge weight matrices, QLoRA inserts low-rank adapters (LoRA) into the network. A standard linear projection XW is augmented with a low-rank term s X L1 L2. Only L1 and L2 are trainable; W stays frozen.
- Because adapters are small, the number of trainable parameters is tiny and optimizer state is cheap. But gradients still flow through the frozen weights during backprop so the adapters learn to correct model outputs.

2) Store the base model in 4-bit (NF4) and compute in 16-bit
- Weights are stored in a 4-bit data type called NormalFloat4 (NF4). NF4 is designed to be information-theoretically optimal for zero-centered normal distributions (a good fit for pretrained weights). It distributes quantization bins according to normal quantiles so bins are used efficiently and outliers are handled better than naive 4-bit float or integer schemes.
- At runtime each 4-bit block is dequantized into a 16-bit compute type (BFloat16) to do forward and backward passes. Only the adapters have actual gradients computed and updated; base weights remain stored in 4-bit.

3) Reduce metadata and manage memory spikes
- Double Quantization: the small per-block quantization constants (scales) themselves are further quantized (e.g., to 8-bit floats) so the extra memory per parameter for scales is much smaller. This reduces overhead that would otherwise make small block sizes costly.
- Paged Optimizers: optimizer states (which are still needed for adapters) are allocated in pageable memory using NVIDIA unified memory. When the GPU peaks during a long sequence, states are automatically paged out to CPU RAM and paged back when needed, preventing out-of-memory failures.

Putting it together: during a layer's computation QLoRA double-dequantizes the stored 4-bit weights to BF16, computes with adapters in BF16, and only updates adapter gradients. This yields effective 16-bit training behavior while the base model stays in ultra-low precision storage.

## A bit more detail (without getting too deep)
- Block-wise quantization is used: weights are split into contiguous blocks and each block gets its own quantization constant. Small blocks give better fidelity but more metadata overhead; Double Quantization keeps that overhead low.
- NormalFloat (NFk) is built by taking the quantiles of a standard normal \(N(0,1)\), mapping them to the \([-1,1]\) range, and using those bin centers as the k-bit data type values. For 4-bit, this is called NF4.
- The forward pass for one layer looks like:
  \[
    Y^{\text{BF16}} = X^{\text{BF16}} \cdot \text{doubleDequant}(c_1, c_2, W^{\text{NF4}}) \;+\; X^{\text{BF16}} L_1^{\text{BF16}} L_2^{\text{BF16}},
  \]
  where doubleDequant reconstructs the BF16 weights from the NF4 storage and quantized constants. Backprop computes derivatives through the dequantized path but only updates the LoRA parameters.

## Why this matches full finetuning performance
Three practical observations from the QLoRA experiments:
- Adapter placement matters. Applying LoRA only to attention matrices (the common default) was insufficient to match full finetuning. QLoRA applies adapters more broadly—essentially at every linear layer—and this recovers the full-performance behavior.
- NF4 beats simple 4-bit float or integer formats. Empirically, NF4 yields lower quantization error and better downstream performance.
- Double Quantization reduces memory of scales with no measurable accuracy hit.

Overall, experiments show 4-bit QLoRA (with NF4 + Double Quantization + paged optimizers) recovers 16-bit finetuning and 16-bit LoRA performance across tasks and model sizes (7B up to 65B for adapter finetuning experiments). That is, you don't lose predictive performance compared to standard finetuning.

## What this enables (results you can expect)
- Memory: QLoRA reduces the average GPU memory requirement for finetuning a 65B LLaMA model from over 780 GB (16-bit full finetuning) to under 48 GB.
- Speed and accessibility: The authors finetuned their best Guanaco models in roughly 12–24 hours on a single consumer/professional GPU. The Guanaco family (finetuned with QLoRA on OASST1) reached state-of-the-art among open models on Vicuna, with the 65B model hitting 99.3% of ChatGPT’s performance on that benchmark.
- Practical footprints: their smallest Guanaco model (7B) runs in about 5 GB of memory at inference time and still outperforms larger open models finetuned without QLoRA.

## Limitations & cautions
- QLoRA freezes base weights. The method is designed for adapter-style finetuning; it does not perform full weight updates. The paper demonstrates parity to full finetuning in many settings, but it did not exhaustively prove exact equivalence for every dataset and training regime at the largest scales.
- Evaluation caveats: chatbot benchmarks (Vicuna, OA) and automated raters (GPT-4) have biases and variance. The authors used human raters and Elo-style pairwise comparisons to get more reliable comparisons, but evaluation of dialogue models remains imperfect.
- Engineering complexity: NF4 and Double Quantization require custom CUDA kernels and careful memory management (the project releases code and kernels, but using them requires some engineering).

## Practical impact
QLoRA greatly lowers the resource barrier for high-quality finetuning. Researchers and practitioners with a single 24–48 GB GPU can now:
- finetune 33B models in ~12 hours,
- finetune 65B models in ~24 hours (on a 48 GB pro GPU),
- experiment with many datasets and adapter variants without renting large clusters.

This democratizes experimentation: more groups can iterate on instruction tuning, safety tuning, domain adaptation, and rapid prototyping of chatbots.

## Where to look next
The paper includes code, CUDA kernels, and many trained adapters and models (Guanaco family). If you want to reproduce or build on this work, the repositories linked in the paper provide the implementation of NF4, Double Quantization, paged optimizers, and QLoRA training scripts.

If you care about pushing beyond this work, open questions include: how far can quantization be pushed (3-bit?), how other adapter approaches compare, and more systematic evaluation across diverse benchmarks and safety metrics.

## Final thought
QLoRA is a practical, well-engineered win: it combines a principled quantization format (NF4), an efficiency trick (Double Quantization), robust adapter finetuning (LoRA applied widely), and memory paging to make large-model finetuning feasible on widely available hardware—without paying an accuracy tax. For anyone blocked by GPU memory limits, QLoRA is worth trying.



# Meet Guanaco: An Open-Source Chatbot That Nearly Matches ChatGPT

## TL;DR
Guanaco is a family of open-source chatbots finetuned with QLoRA — a memory-efficient 4-bit finetuning method. Using QLoRA, the authors finetuned a 65B-parameter LLaMA model on a single 48 GB GPU and produced Guanaco 65B, which reaches 99.3% of ChatGPT’s performance on the Vicuna benchmark (evaluated relative to ChatGPT). A 33B Guanaco hits similarly strong levels and can be finetuned in about 12 hours on a 24 GB consumer GPU. QLoRA makes these results accessible by reducing finetuning memory from hundreds of gigabytes to a single modest GPU.

## What QLoRA actually does (short)
QLoRA is a practical recipe that combines three engineering ideas to enable large-scale finetuning without updating the full model:

- Store the pretrained weights in a 4-bit quantized format designed for normally distributed weights (NF4), but perform computations in a higher-precision format (BFloat16). During forward/backward passes the quantized weights are dequantized into the computation dtype.
- Use Low-Rank Adapters (LoRA): only a small set of additional adapter weights are trained; the large base model weights remain frozen. Gradients are backpropagated through the dequantized base weights into the adapters.
- Reduce quantization meta-overhead with Double Quantization (quantize the quantization scales) and avoid optimizer memory spikes with Paged Optimizers that use unified CPU/GPU memory when needed.

Together this reduces the memory footprint enough to finetune 33B and 65B models on a single GPU while matching 16-bit finetuning performance on standard benchmarks.

## Guanaco — how it was trained
- Base models: LLaMA models at 7B / 13B / 33B / 65B scales.
- Finetuning method: QLoRA with NF4 + Double Quantization + LoRA adapters applied broadly (adapters in all linear layers).
- Training data: variants of the OpenAssistant (OASST1) conversational dataset were key for the top Guanaco models. The authors found small, high-quality datasets can outperform much larger but lower-quality instruction collections.
- Objective: supervised cross-entropy finetuning (no RLHF was used in these models).
- Compute: Guanaco 33B was trained in ~12 hours on a single 24 GB consumer GPU; Guanaco 65B was trained in ~24 hours on a single 48 GB GPU (the combination of QLoRA and paged optimizers enabled this).

## Performance highlights
- On the Vicuna benchmark (the commonly used 80-prompt set comparing responses to ChatGPT), Guanaco 65B achieves 99.3% of ChatGPT’s score in the paper’s GPT-4-based automated evaluation.
- Guanaco 33B and 65B rank near the top of open-source models in Elo-style tournaments using both human raters and GPT-4 pairwise comparisons; Guanaco 65B is the best open-source chatbot in their evaluations.
- Smaller Guanaco models are competitive too: Guanaco 7B fits in ~5 GB and outperforms larger earlier open models like Alpaca on Vicuna prompts.

The paper also shows that, across tasks, QLoRA (4-bit storage with NF4 + LoRA) matches the performance of 16-bit full finetuning and 16-bit LoRA finetuning on academic benchmarks such as MMLU and GLUE for a variety of model sizes.

## What this means for the community
QLoRA + Guanaco changes the accessibility equation for instruction tuning and chatbot development. Before this work, finetuning a multi-billion-parameter model typically required many GPUs and hundreds of GB of memory. Now researchers and smaller teams can:

- Finetune much larger models on a single GPU (e.g., 33B on a 24 GB card, 65B on a 48 GB card).
- Iterate quickly on finetuning datasets and adapter configurations without renting expensive multi-node clusters.
- Produce very strong open-source chatbots without needing proprietary datasets or RLHF (though RLHF remains a complementary approach).

This lowers the barrier for experimenting with instruction datasets, safety interventions, domain specialization, and deployment-ready finetuning for privacy-sensitive applications.

## Where Guanaco still struggles (qualitative failure modes)
The paper includes a thoughtful qualitative analysis. Guanaco is strong in many conversational settings but has clear, reproducible weaknesses:

- Factuality and hallucinations: for common facts it is reliable, but for obscure facts it can be confidently wrong.
- Mathematics: it often fails on arithmetic and factorization unless the question is decomposed into explicit step-by-step reasoning; symbolic/math errors were a common failure mode.
- Inconsistent refusals / instruction following: the model sometimes refuses simple transformations for unclear reasons, and adversarial prompting can override secret-keeping or instruction constraints.
- Theory-of-mind and pragmatic inference: the model can reason about beliefs and intentions, but its inferences are sometimes based on unjustified assumptions and thus unreliable.
- Evaluation instability: automated evaluators (e.g., GPT-4) and humans only moderately agree on pairwise preferences; GPT-4 exhibits ordering bias (prefers the response shown first) and tends to rate its own outputs higher.

These limitations are important to keep in mind for deployments, and the authors emphasize the need for better evaluation protocols (Elo-style pairwise comparisons help) and further safety analysis.

## Caveats and limitations called out by the authors
- The paper shows QLoRA matches 16-bit performance on many benchmarks, but the comparison to fully finetuning 33B/65B models on 16-bit hardware is not exhaustively proven (full 16-bit finetuning at that scale is expensive).
- Guanaco was trained via supervised finetuning only (no RLHF). Differences between supervised finetuning and RLHF in behavior and safety are left for further work.
- Human and automated evaluations show only moderate agreement, so claims based on a single evaluation protocol should be interpreted with care.
- The analysis of biases and harms is limited; more responsible-AI evaluations are required before deployment in high-stakes settings.

## Bottom line
Guanaco is a practical demonstration that efficient quantized finetuning can produce very strong open-source chatbots. QLoRA reduces memory costs dramatically and recovers 16-bit finetuning quality, enabling strong models like Guanaco 33B and 65B to be trained on a single GPU in hours to a day. Guanaco 65B approaches ChatGPT on common conversational benchmarks, while still showing the usual LLM failure modes (hallucinations, math mistakes, inconsistent instruction following). The combination of lower compute barriers and open releases makes it a meaningful step toward wider reproducibility, experimentation, and scrutiny in chatbot research.



# The Magic of NF4: Why a New 4-Bit Data Type Keeps Big Models Smart

Quantizing large language models to 4-bit storage while keeping their performance close to full 16-bit finetuning feels almost like magic. In QLoRA, one of the key spells in that trick is a new 4-bit data type called NormalFloat 4 (NF4). This post unpacks what NF4 is, why it makes sense for pretrained model weights, how it is constructed, and why it empirically beats simpler 4-bit formats like FP4 and Int4 — enabling robust 4-bit finetuning of models up to 65B parameters.

## The problem: quantization vs. information loss

Quantization reduces storage by mapping high-precision values (e.g., FP32) to a small discrete set (e.g., 4-bit). A naive uniform mapping (e.g., Int4) or a small float format (FP4) can be efficient, but they may not use the available discrete levels in an information-preserving way. Two common practical issues are:

- Outliers: If a tensor has a few large values, uniform rescaling wastes many representable levels on a long tail and loses precision where most values actually lie.
- Distribution mismatch: The optimal placement of discrete levels depends on the distribution of the values being quantized.

QLoRA's observation: pretrained neural network weights are typically approximately zero-centered and close to normally distributed. That suggests we can design a quantization data type tailored to a normal distribution and get better use of the limited 4-bit bins.

## NF4 in one sentence

NF4 is a 4-bit quantization data type whose representable values are the quantiles of a standard normal distribution (appropriately scaled), so each quantization bin has equal expected probability mass under a normal weight distribution. That makes NF4 information-theoretically optimal for zero-mean normal weights and gives better empirical precision than FP4 or Int4 when quantizing LLM weights.

## How NF4 is constructed (conceptually)

The construction uses the idea of quantile (or histogram-equalizing) quantization applied to a theoretical normal distribution:

1. Start from the standard normal distribution \(N(0,1)\).
2. Compute the quantile function values needed to define \(2^k\) bins for a \(k\)-bit data type. Concretely, for a k-bit symmetric scheme you estimate midpoints
   \[
   q_i = \frac{1}{2}\left( Q\!\left(\frac{i}{2^k+1}\right) + Q\!\left(\frac{i+1}{2^k+1}\right)\right)
   \]
   where \(Q(\cdot)\) is the quantile function of \(N(0,1)\) and \(i\) indexes bins.
3. Normalize these \(q_i\) values into the target range (e.g., \([-1,1]\)) so they can be used as the discrete set of representable values.
4. Account for zero: a symmetric k-bit quantization often lacks an exact zero codepoint, which is undesirable because many weights (and paddings) are exactly zero. NF4 resolves this by creating an asymmetric pairing of negative and positive quantiles (with one explicit zero) so that zero is exactly representable while preserving near-equal expected counts across bins.

The resulting quantized alphabet is therefore non-uniformly spaced: bins are denser around zero (matching the mass of a normal), and sparser in the tails, which is exactly what you want if most weights follow a normal distribution.

## Why NF4 is information-theoretically sensible

Under the assumption that weights in pretrained networks are approximately Gaussian with mean zero, quantile-based bins give an equal expected number of values per bin. This matches the idea of minimizing expected quantization error when the data distribution is known: allocate more representable levels where the distribution has higher density. NF4 approximates the optimal (rate-distortion) allocation for a normal distribution in the discrete, low-bit setting.

In contrast:

- Int4/linear uniform formats waste many levels if the weight distribution is concentrated near zero.
- Small float formats (FP4 variants) keep an exponent/mantissa structure that is not matched to the specific normal-shaped distribution of weights and therefore do not allocate levels optimally.

## How NF4 is used inside QLoRA (practical pipeline)

QLoRA uses NF4 as the storage format for the large pretrained weight tensors. Key practical details:

- Block-wise quantization: weights are chunked into small blocks (e.g., blocksize = 64) and each block is rescaled independently by an "absolute max" scale constant before mapping to NF4. This reduces outlier problems at the block level.
- Dequantization for computation: when performing forward/backward passes, the stored NF4 weights are dequantized to a higher-precision computation type (BFloat16) and matrix multiplications are done in 16-bit precision. QLoRA only updates LoRA adapter parameters; it does not need to store gradients for the 4-bit base weights.
- Zero representability: NF4 explicitly includes a discrete zero code, which avoids any special-casing for common zero elements (padding, sparse patterns).

## Double Quantization and memory tuning

One overhead of block-wise k-bit schemes is the extra storage for per-block quantization constants (scales). QLoRA reduces that overhead via Double Quantization: the per-block FP32 scales themselves are quantized (e.g., to FP8 with a larger blocksize) and stored compactly, recovering a few tenths of bits per parameter on average. Importantly, QLoRA reports that this secondary quantization does not degrade performance.

Combined with NF4’s improved representational efficiency, double quantization trims memory use further while keeping the quantized weight reconstruction accurate enough for training the adapters.

## Empirical effects: NF4 > FP4 and Int4; NF4 enables 4-bit finetuning parity

The QLoRA paper evaluates NF4 against FP4 and Int4 on a wide range of models (OPT, LLaMA, BLOOM, Pythia) and sizes (125M to 13B) and reports:

- NF4 consistently yields better perplexity and zero-shot accuracy after quantization than FP4 and Int4.
- When NF4 is combined with QLoRA (i.e., finetuning LoRA adapters with gradients propagated through dequantized NF4 base weights), the method recovers the performance of 16-bit full-model finetuning and 16-bit LoRA finetuning across benchmarks like GLUE, Super-NaturalInstructions, and MMLU.
- Specifically, NF4 with double quantization and the full QLoRA pipeline matches 16-bit LoRA MMLU performance for LLaMA models from 7B up to 65B, while FP4 lags by about ~1 percentage point in some MMLU evaluations.

These results show that the precision advantage NF4 provides at quantization time translates into real gains after adapter finetuning: the quantization-induced information loss is sufficiently small (and correctly targeted) that adapters can recover 16-bit-level task performance.

## Practical design choices you should know

- Blocksize: QLoRA uses small blocksize (e.g., 64) for weight NF4 quantization to handle per-block outliers, and a larger blocksize (e.g., 256) when double-quantizing the scales. This trades off quantization fidelity against memory for scale storage.
- Computation type: storage = NF4; compute = BFloat16. NF4 is only for storage; dequantize to BF16 for all computations.
- Zero codepoint: NF4's asymmetric construction ensures exact zero representation, reducing errors on padded positions or exact zeros.
- LoRA placement: to match full finetuning performance, QLoRA applies LoRA adapters to all linear layers (not just attention Q/K/V) — this is important because adapter coverage matters more than aggressive adapter compression when recovering full performance.

## Takeaway

NF4 is an elegant, distribution-aware 4-bit data type tailored to the empirical fact that pretrained neural network weights are approximately zero-centered and normally distributed. By placing quantization levels where weights actually lie (dense near zero, sparse in tail), NF4 uses the scarce 4-bit budget far more effectively than uniform integers or small float formats. In practice, NF4 (with double quantization and the rest of QLoRA) enables faithful 4-bit storage of huge models and, importantly, lets adapter finetuning recover the performance of full 16-bit finetuning — even at 65B scale.

If you're interested in efficient finetuning, NF4 is a small-but-critical piece that makes 4-bit training not just possible, but practically competitive.



# Double Quantization Explained: Squeezing Memory Without Squeezing Performance

Quantizing large language models (LLMs) to 4-bit storage dramatically reduces model size, but it comes with an extra, often-overlooked memory cost: the per-block quantization constants (scales). Double Quantization—quantizing the quantizers—compresses those constants further, trimming about 0.373 bits per parameter (roughly 3 GB for a 65B model) while preserving downstream performance. This post explains the idea, the math, and why it works in practice based on the QLoRA paper.

## The memory cost you might miss: quantization constants

Block-wise k-bit quantization stores each weight block in low-bit form (e.g., 4 bits) and also saves a floating-point quantization constant (scale) per block to allow dequantization. For a blocksize of \(B\) and 32-bit quantization constants, the average metadata cost is

- per-parameter overhead = \( \frac{32}{B} \) bits.

Example: with \(B=64\), the constants alone add \(32/64 = 0.5\) bits per parameter. For huge models this becomes non-trivial.

Double Quantization tackles this by applying a second, coarser quantization step to the first-level quantization constants themselves.

## What double quantization does (step-by-step)

1. First-level quantization (usual flow)
   - Partition a weight matrix into blocks of size \(B\) (e.g., 64).
   - For each block, compute a 32-bit floating-point scale \(c_2^{\text{FP32}}\) and quantize the block's weights into k-bit integers (or NFk values).
   - Store both the k-bit weights and the 32-bit per-block scale.

2. Second-level quantization (the new step)
   - Treat the array of first-level scales \(\{c_2^{\text{FP32}}\}\) as a tensor to be quantized again.
   - Subtract the mean from \(c_2\) (centering) because the first-level scales are positive; centering lets us use symmetric quantization.
   - Quantize the centered scales into an 8-bit floating-point format (FP8) with a larger blocksize (e.g., \(B_2=256\)), producing:
     - quantized quantization constants \(c_2^{\text{FP8}}\), and
     - a second-level 32-bit scale \(c_1^{\text{FP32}}\) used to dequantize the FP8 values when needed.

3. Dequantization on demand
   - When the weight block is needed for computation, double-dequantize:
     - dequantize the FP8 \(c_2\) back to FP32 using \(c_1^{\text{FP32}}\),
     - then dequantize the k-bit weights with the recovered \(c_2\) to the computation dtype (e.g., BF16).

So the model stores:
- k-bit weights (primary low-bit storage),
- FP8 quantized copies of the first-level scales (much smaller than FP32),
- occasional second-level FP32 scales to reconstruct the FP8 values.

## Why this saves memory (the numbers)

Using the QLoRA defaults (k = 4 bits, first blocksize \(B = 64\), second-level blocksize \(B_2 = 256\)):

- Original per-parameter scale cost: \( \frac{32}{64} = 0.5 \) bits.
- After double quantization:
  - FP8 scales cost: \( \frac{8}{64} = 0.125 \) bits per parameter (since we still have one FP8 per weight-block of 64).
  - Plus the amortized cost of the second-level FP32 scale: there is one FP32 per \(B_2 = 256\) FP8 scales, and each FP8 scale corresponds to a block of 64 weights, so the amortized cost is \( \frac{32}{64 \times 256} \) bits per weight.
  - Sum: \( \frac{8}{64} + \frac{32}{64 \cdot 256} = 0.125 + 0.002 = 0.127 \) bits per parameter.

Reduction = \(0.5 - 0.127 = 0.373\) bits per parameter.

For a 65B-parameter model:
- 0.373 bits/param × 65B params ≈ 3.03 GB saved.

These are the numbers reported in QLoRA.

## Why performance doesn't degrade

Double Quantization might sound risky—you're compressing the very scales used to reconstruct weights—but there are three practical reasons it works without harming accuracy:

1. Quantization constants are smooth and low-entropy. The per-block scales vary much more slowly and are well-approximated at lower precision (FP8) than raw weights are. That makes them robust to a second round of lossy encoding.

2. Larger second-level blocksize amortizes the remaining FP32 overhead. Using a larger blocksize for the FP8->FP32 quantization (e.g., 256) keeps the extra FP32 costs negligible while still enabling faithful reconstruction of the FP8 scales.

3. Empirical confirmation in QLoRA. The paper reports that double quantization reduces the memory footprint without degrading performance in downstream tasks. Combined with the use of the NF4 data type and adapter finetuning, the method recovers full 16-bit finetuning results in practice.

Additional implementation detail used by QLoRA: because the first-level scales are all positive, QLoRA subtracts the mean before symmetric quantization of the scales—this centering improves representational efficiency when quantizing their distribution into FP8.

## Practical tradeoffs and pointers

- Blocksize choices matter. Smaller first-level blocks (e.g., 64) yield better weight quantization accuracy but increase the relative metadata cost—making double quantization more beneficial. The second-level blocksize should be larger (e.g., 256) to amortize the FP32 overhead of reconstructing FP8 scales.
- Compute pipeline: double dequantization adds a tiny extra step during runtime (dequantize FP8 scales to FP32; then dequantize k-bit weights to BF16) but QLoRA’s kernels and workflow hide this overhead and retain computational correctness.
- Double Quantization is complementary to other quantization innovations (e.g., the NF4 k-bit format) and to adapter-based finetuning (LoRA). In QLoRA it is one of multiple memory-saving elements that together make 65B finetuning on a single 48GB GPU feasible.

## Bottom line

Double Quantization is a small, high-leverage optimization: by quantizing the per-block quantization constants themselves (FP32 -> FP8 plus a higher-level FP32 scale), you cut roughly 0.373 bits per parameter (about 3 GB on a 65B model with the QLoRA configuration) without hurting downstream performance. Because the scales are low-entropy and smoothly varying, they compress well—and the empirical results in QLoRA confirm this works at scale.

If you are implementing or using block-wise quantization for large models, double quantization is a straightforward and cost-effective way to reclaim memory that would otherwise be eaten by per-block scales.



# Paged Optimizers: The Safety Net That Stops Out-of-Memory Crashes

## Overview

When finetuning very large language models on a single GPU, one of the hardest practical problems is occasional out-of-memory (OOM) spikes. These spikes typically happen during backpropagation with long sequences or large mini-batches (for example when using gradient checkpointing), and they can abort a run even when average memory use comfortably fits on the device. The QLoRA paper introduces "Paged Optimizers" as a pragmatic, low-friction safety net that leverages NVIDIA unified memory to avoid such crashes. This post explains what paged optimizers are, when paging happens, why training speed often stays intact, and how the technique unlocks longer sequences and larger effective batches on limited-GPU setups.

## What paged optimizers are

Paged Optimizers use NVIDIA's unified memory (a system for automatic CPU↔GPU page transfers) as backing storage for optimizer state. Instead of pinning optimizer state permanently on the GPU, paged optimizers allocate those tensors in unified/paged memory. When the GPU needs more memory for a forward/backward pass, the CUDA runtime can evict pages of optimizer state to host RAM; when the optimizer update step runs, pages are automatically brought back to the device.

In short: optimizer state is kept in paged (unified) memory so the system can transparently move those pages to CPU RAM when the GPU hits a peak memory demand, and bring them back when updates are needed.

## Why this matters: activation/gradient spikes

Two facts combine to make paged optimizers useful:

- For large models, most of the training memory is consumed by activation gradients during the backward pass, not by the optimizer state or the small adapter parameters used in PEFT methods like LoRA.
- Gradient checkpointing reduces the steady-state activation memory but creates transient spikes during recomputation/backward passes. Those spikes can exceed GPU memory even if the long-term average fits.

Paged optimizers mitigate these transient spikes. When the GPU would otherwise OOM during a spike, unified memory allows optimizer state pages to be evicted, freeing enough device memory to complete the expensive recomputation/backward step. After the backward pass finishes, the optimizer step brings back the pages to perform parameter updates.

## When paging kicks in

Paging is not part of the normal fast-path; it happens only when the GPU cannot allocate enough device memory for some transient requirement (for example during a recomputation step with a long input sequence or unusually large micro-batch). In QLoRA's setup:

- The base model weights are stored quantized (4-bit NF4) and dequantized to a 16-bit compute type when needed.
- LoRA adapter parameters and their gradients live in device memory, as usual.
- Optimizer states (which can be sizable for large models) are allocated in unified memory so they can be paged out when the device hits a transient peak.

So paging will typically occur only on rare, high-water-mark operations (long sequences, big batches, or particular attention patterns where recomputation causes large temporary memory demands).

## Why training speed often stays intact

Paging sounds expensive, but in practice QLoRA reports that paging rarely affects throughput significantly. Important points from the paper:

- Paging is conditional: it happens only on spikes, not every step. Most steps proceed without page transfers.
- In their measurements for a 65B model on a 48GB GPU, with a batch size of 16, paged optimizers provided the same training speed as regular (non-paged) optimizers. That indicates the runtime overhead of the occasional page-ins/outs did not measurably slow down the run in that configuration.
- The optimization step (when optimizer state must be resident) can be overlapped or amortized over many examples; the transient cost of bringing pages back is only paid when necessary.

The paper cautions that paging behavior depends on workload characteristics (sequence length distribution, batch size, checkpointing schedule) and the system environment (PCIe/NVLink bandwidth and host RAM). They note that future work should more precisely characterize when and how much paging slows down training.

## Practical benefits

Using paged optimizers unlocks several practical gains when working with large models on single GPUs:

- Avoid hard OOM failures caused by rare activation spikes, making long runs more robust.
- Make it feasible to use longer sequence lengths or larger mini-batches that would otherwise cause transient OOMs.
- Reduce the need to over-provision GPU memory or to manually finetune checkpointing schedules just to dodge rare spikes.
- Combine naturally with other QLoRA memory reductions (4-bit NF4, double quantization, LoRA adapters) to enable finetuning models that previously required many GPUs.

## Caveats and open questions

The QLoRA paper explicitly notes some limitations you should keep in mind:

- Paging only occurs when the GPU would otherwise run out of memory. It is not a substitute for overall memory reduction when the steady-state footprint truly exceeds device capacity.
- The runtime impact of paging is workload-dependent. In QLoRA's experiments paging did not slow training for the tested configuration, but slower page transfers could matter with different hardware (lower PCIe/NVLink bandwidth) or different batching/sequence patterns.
- The authors did not provide exhaustive performance characterizations of paged optimizers across all conditions and recommend future work to measure and characterize when paging introduces noticeable slowdowns.

## Takeaway

Paged Optimizers are a pragmatic engineering lever: allocate optimizer state in unified (paged) memory so rare activation/gradient spikes can be handled without crashing the run. In the QLoRA experiments this safety net allowed single-GPU finetuning of very large models with minimal or no throughput penalty in typical settings, and it makes longer sequences and larger effective batches more usable on constrained hardware. If your training jobs fail due to intermittent spikes rather than sustained memory pressure, paged optimizers are an effective strategy to try before sacrificing sequence length, batch size, or model scale.



# From Lab to Laptop: A Practical Guide to Finetuning LLMs with QLoRA

QLoRA makes finetuning very large language models (LLMs) feasible on modest hardware by storing the pretrained weights in 4-bit form and training only small adapter (LoRA) parameters. This guide summarizes the practical choices and recipes from the QLoRA paper so you can reproduce their results or use the approach for your own models. I keep this concise and actionable while explaining the key design decisions that let QLoRA match 16-bit finetuning performance even on 7B–65B models.

## What QLoRA gives you (short summary)
- Finetune a 65B-parameter model on a single 48 GB GPU (paper reports <48 GB memory use vs >780 GB for naïve 16-bit finetuning).
- Finetune a 33B model on a single 24 GB consumer GPU (paper: <12 hours).
- Finetune 7B models that can fit into ~5 GB for inference/deployment (paper: Guanaco 7B ~5 GB).
- Match 16-bit full finetuning and 16-bit-LoRA performance on standard benchmarks when using the recommended settings.

## Core components you must use
QLoRA is a combination of three main ideas. Use them together:

1. 4-bit NormalFloat (NF4) weights for storage
   - NF4 is a k-bit quantization data type optimized for approximately normal (zero-centered) weight distributions. It uses quantiles of a standard normal to place representable values so bins are used evenly for normally-distributed weights.
   - Store model weight tensors in NF4 (block-wise quantized).

2. Double Quantization (DQ)
   - The per-block quantization scales/Constants from the first quantization are themselves quantized (e.g., to 8-bit floats) so you reduce overhead from having many block scales. This saves ~0.37 bits/parameter on typical block sizes.
   - The paper uses 8-bit floats (FP8) for the second-level quantization constants.

3. Low-Rank Adapters (LoRA) on a frozen, quantized base model
   - Keep the base pretrained weights frozen (stored in NF4). Insert and train LoRA adapters; gradients are backpropagated through dequantized weights into those adapters.
   - Dequantize blocks to BF16 for compute (forward/backward) and only update the LoRA parameters in BF16.

Additionally, QLoRA uses paged optimizers that leverage NVIDIA unified memory to avoid out-of-memory spikes caused by long sequence-length batches. This allows training large models on a single GPU without failure due to occasional memory peaks.

## Practical recipe — step by step

1. Pick your base model
   - Any large pretrained decoder/encoder-decoder model used in the paper: LLaMA, T5, RoBERTa, etc.
   - Note: QLoRA experiments in the paper span 7B–65B.

2. Quantize the model weights to NF4 (block-wise)
   - Use a block size of 64 for the main weight tensors (paper choice: blocksize = 64 gives high quantization precision).
   - Produce block-wise NF4 weights and the first-level quantization constants (c2 in the paper).

3. Apply Double Quantization to quantization constants
   - Quantize the per-block constants c2 using an 8-bit float representation with block size 256 to save memory (paper used FP8 for c2 and blocksize 256).
   - Store the top-level constants (c1) in FP32 as needed for dequantization.

4. Install LoRA adapters at every linear layer you want to adapt
   - Critical design choice from the paper: applying LoRA only to a subset (e.g., query/value projections) often does not match full finetuning performance for larger base models.
   - The paper finds that putting LoRA on all linear projection layers inside transformer blocks is required to recover 16-bit full-finetuning performance robustly.

5. Use BF16/BFloat16 for compute
   - Whenever a quantized weight block is used, dequantize to BF16 for matrix multiplication and gradient computation.
   - LoRA parameters are stored and updated in BF16.

6. Use paged optimizers for optimizer state
   - Allocate optimizer states in paged (unified) memory so that GPU-CPU paging happens automatically if spikes occur. This prevents OOM during the occasional long-sequence batches.

7. Training objective and data
   - The paper used supervised cross-entropy finetuning (no RLHF) for instruction/chatbot experiments.
   - For multiple-response tree-structured datasets (OASST1, HH-RLHF), they selected top responses and finetuned on full conversations including instructions.

8. Generation / evaluation defaults used in the paper
   - Nucleus sampling (top-p) with p = 0.9 and temperature = 0.7 for chat-style output generation in evaluations.

## Recommended hyperparameters and heuristics from the paper

- LoRA placement: apply adapters at all linear layers (every transformer block linear projection), not only query/value. This is the most important PEFT choice the paper found for matching full finetuning.
- LoRA projection dimension r: the paper states this did not materially affect performance in their ablations. Use the standard LoRA settings you normally use, but prioritize adapter placement first.
- Learning rate and batch size search range used for baselines: the paper searched learning rates from 1e-6 to 5e-5 and batch sizes 8 to 128 to tune robust baselines.
- Scaling for larger models:
  - For 33B and 65B, the paper reports halving the learning rate and doubling the batch size relative to settings found at 7B.
  - Number of epochs found at 7B generalized to larger models in their experiments, except for the adjustments above to LR and batch size.
- Storage/computation types:
  - Storage: NF4 for weights, FP8 for second-level scale constants, FP32 for top-level scale constants.
  - Compute: BF16 (Brain Float 16) for dequantized weights and LoRA computations.
- Block sizes:
  - Weight quantization: block size = 64 (better quantization precision).
  - c2 (quantization constants) quantization: block size = 256 (reduce memory overhead).

## Memory and runtime expectations (as reported)
- 65B model: QLoRA reduces memory requirement from >780 GB (16-bit full finetuning) to <48 GB so a single 48 GB GPU can perform finetuning.
- 33B model: trainable on a single 24 GB consumer GPU; the paper reports a 33B model finetuned in under 12 hours on a single consumer GPU.
- 7B model: inference footprint about 5 GB (fits on modern phones for deployment).
- Paged optimizers: normally give the same training speed as regular optimizers when batch sizes are reasonable (paper noted no runtime penalty in their 65B/48GB tests with batch size 16).

## Tips and pitfalls
- Do not expect LoRA on just Q and V to be sufficient for large models: the paper found that adapter coverage across layers is essential to match full finetuning.
- NF4 is better than FP4 or Int4 empirically for these models; if you use 4-bit quantization, prefer NF4 as in the paper.
- Double Quantization reduces memory footprint of quantization constants with no measurable performance hit in their experiments—use it to save a few GB on large models.
- Evaluation variability: chatbot-style human evaluations can have substantial variance and scale/bias effects. The paper found that GPT-4 judgments correlate moderately with humans but also have biases (for example, ordering effects). Use careful evaluation protocols.
- Data quality matters more than quantity for instruction finetuning: in their experiments small high-quality datasets (e.g., OASST1) outperformed larger lower-quality alternatives for chatbot behavior.

## What you can expect to match (from the paper)
- With the combination of NF4 + Double Quantization + LoRA on all linear layers + paged optimizers, QLoRA finetuning matched 16-bit full finetuning and 16-bit LoRA baselines across many benchmarks (GLUE, Super-NaturalInstructions, MMLU) and across model scales from 125M up to 65B in the experiments reported.
- Using this approach the paper produced the Guanaco models (7B, 13B, 33B, 65B) that were state-of-the-art among openly released chatbots on the Vicuna benchmark, with Guanaco-65B achieving 99.3% of ChatGPT's performance on that benchmark.

## Minimal implementation checklist
- [ ] Quantize base model weights to NF4, blocksize = 64.
- [ ] Double-quantize quantization constants to FP8 with blocksize = 256.
- [ ] Insert LoRA adapters at every linear projection layer; store adapter params in BF16.
- [ ] Dequantize blocks to BF16 at runtime for forward/backward.
- [ ] Use paged optimizer allocation for optimizer state (unified memory).
- [ ] Train with supervised cross-entropy (no RLHF) unless you plan to add RL later.
- [ ] Tune LR and batch size; for 33B/65B halve LR and double batch size compared to 7B-tuned settings.

## Where to look next (resources from the paper)
- The authors released code, CUDA kernels for 4-bit training, and finetuned adapters (Guanaco family). See the QLoRA and bitsandbytes repositories cited in the paper for implementation details and kernels.
- If you want to reproduce the exact experiments, follow the repo examples for NF4 quantization, Double Quantization, LoRA insertion, and using the paged optimizer setup.

# Small but Mighty Data: Why Quality Beats Quantity in Instruction Tuning

The QLoRA paper gave us more than a way to finetune massive models on a single GPU — it also produced a surprisingly clear data-centric lesson: a small, high-quality instruction dataset can outperform a much larger but less well-matched dataset when the target is chatbot performance.

Here I summarize the evidence from QLoRA, unpack why dataset-task fit matters, and give practical guidance for anyone building instruction-tuned chatbots.

## The headline: 9k beats 450k (for chatbots)

In the QLoRA experiments, models finetuned on a small, high-quality dataset (the authors call out OASST1, roughly 9k selected examples in their use) outperformed models finetuned on a much larger dataset that had been subsampled to 450k examples (FLAN v2) when the evaluation target was chatbot behavior (Vicuna and OA-style chat prompts).

At the same time, the opposite trend appeared on the MMLU benchmark: FLAN v2 gave stronger results on MMLU while OASST1-finetuned models did worse there. In short: the dataset that made the model better at MMLU was not the one that made it better at realistic multi-turn chat.

This is not an accident. It is an illustration of dataset-task fit: large scale alone does not guarantee better downstream behavior if the data’s content, format, and quality do not align with the target application.

## Why quality and fit win for chatbots

Several factors explain why a smaller, higher-quality dataset like OASST1 can beat a much larger one for chatty assistants.

- Multi-turn and conversational structure. Chatbots need to handle turn-taking, context preservation, role indicators, and realistic user intents. Datasets designed as multi-turn assistant dialogues (or curated from real multi-turn conversations) teach the model those mechanics directly. Generic instruction datasets or synthetic single-turn instructions may lack these structural cues.

- Natural assistant responses vs. task-centric outputs. Chat behavior emphasizes tone, refusal strategies, follow-up questions, and safe/guarded responses. High-quality datasets often contain carefully written assistant responses that encode these behaviors; generic training corpora might optimize for correctness in short tasks rather than conversational appropriateness.

- Noise and label quality. Large scraped or auto-generated corpora can contain bad examples, inconsistent styles, and distilled artifacts from the teacher models. A smaller but cleaner dataset reduces contradictory signals and helps the model learn robust conversational policies.

- Domain and style alignment. If your evaluation or production inputs resemble the small dataset’s prompt distribution (e.g., user queries, instruction phrasing, multilingual queries, or safety constraints), finetuning on that data transfers much better than using unrelated large corpora.

- Human-curated signal for subtle behavior. Some conversational behaviors (refusal, secret-keeping, system instruction adherence) require careful human annotation and curation. Quantity alone rarely encodes these subtleties.

QLoRA’s empirical finding — that models finetuned on OASST1 excelled at the Vicuna/OA-style chat evaluation but not necessarily at MMLU — is exactly what you would predict if dataset format and quality are the dominant factors for chatbot skill.

## MMLU strength ≠ chatbot strength

Massive Multitask Language Understanding (MMLU) is a broad multiple-choice knowledge benchmark. It rewards factual knowledge and exam-style reasoning. Good performance on MMLU indicates strong knowledge and few-shot reasoning ability, but it does not directly measure:

- Multi-turn coherence or memory across a conversation
- Appropriateness of assistant tone or safety-oriented refusals
- Response fluency, follow-up-questioning, or preferences handling
- Robustness to adversarial user prompts or instruction-following edge-cases

Hence, a dataset optimized for improving MMLU-style tasks (for example, FLAN v2 or other task-diverse, instruction-supervised collections) will help on MMLU but might miss or even degrade conversational qualities that are best taught with multi-turn chat examples and careful human-crafted assistant responses.

QLoRA shows this empirically: the same finetuning recipe yields different downstream strengths depending on which dataset is chosen. The takeaway is simple: evaluate models on the target behavior you actually care about, and prioritize datasets that mirror that behavior.

## Evaluation nuances: human vs model-based raters

The authors used both human annotators and GPT-4 to evaluate chat outputs, aggregated via pairwise comparisons and Elo scores. A few cautionary points emerged:

- GPT-4 ratings broadly agreed with human rankings at the system level but showed notable divergences at the example level, and displayed ordering biases (preferring the response shown earlier in the prompt).
- Human annotations also had moderate inter-annotator agreement, especially for close-quality responses.
- These evaluation realities amplify the need for datasets that match the desired behavior: if evaluation is noisy or biased, it becomes harder to identify the real effect of more data.

In practice, this means you should not rely solely on a single benchmark (e.g., MMLU) to claim chatbot quality. Use pairwise human/Elo-style comparisons on representative chat prompts when optimizing for conversational behavior.

## Practical recommendations for dataset design and selection

If your goal is to build a capable chatbot, the QLoRA results suggest the following pragmatic rules:

1. Match format to task. Prioritize multi-turn dialogues and real assistant-style responses when training chatbots. Single-turn instruction-response pairs are insufficient to teach conversational dynamics.

2. Prioritize curation over raw scale. Remove noisy, contradictory, or low-quality examples even if that reduces dataset size drastically. Cleaner signal helps more for nuanced behaviors.

3. Preserve role/context tokens. Include the system, user, and assistant markers, and train on sequences that include previous turns so the model learns context retention and role-aware response generation.

4. Include safety and refusal examples. High-quality assistant datasets explicitly show when to refuse or ask clarifying questions. Teach those behaviors explicitly.

5. Evaluate on representative dialogs. Use human pairwise judgments and Elo aggregation on the kinds of prompts you expect in production. Supplement with model-based ratings for scale but treat them as approximations.

6. Consider multilingual and domain coverage intentionally. If you need multilingual chat, use multilingual examples rather than assuming a large monolingual dataset will generalize.

7. Small targeted fine-tuning cycles are cheap and effective. QLoRA itself shows that finetuning even 33B/65B models is accessible and fast; that lowers the cost of iterating with curated small datasets.

## Final thoughts

The QLoRA experiments highlight a simple but powerful truth: for instruction-tuned chatbots, more data is not always better. Data that matches the task and is curated for conversational quality can produce larger gains than bulkier, more diverse collections geared at other evaluation objectives.

If you are building assistant models, choose your training data with intention. Treat dataset design as a first-class engineering decision — often a small, well-chosen dataset will make your chatbot noticeably better than a larger, unfocused one.



# Can GPT-4 Judge Other Models? What Human vs. AI Evaluations Reveal

Evaluating generative models—especially chatbots—is hard. The QLoRA paper (training the Guanaco models) ran a careful set of comparisons between human raters and GPT-4 to see whether an AI can be used as a cheap proxy for humans. Here I summarize the evaluation setup they used, the main findings about agreement and biases, and practical takeaways for anyone planning to use model-based evaluation.

## How the evaluation was set up

Two complementary evaluation styles were used:

- Absolute scoring against a reference (ChatGPT). Given a prompt and two responses (ChatGPT and a candidate model), GPT-4 was asked to assign a score out of 10 to each response and explain. The paper found a strong ordering effect in this setup (see below), so they recommend averaging scores over both presentation orders.

- Pairwise comparisons (head-to-head). For each prompt, two system responses are compared and the judge (human or GPT-4) picks the better response or declares a tie. This was simplified to a three-class decision: A wins / B wins / tie.

Pairwise results were aggregated into tournament-style Elo ratings to obtain a stable ranking. Details:
- Elo starts at 1000, uses K = 32.
- The sampling/recalculation is repeated 10,000 times with different random seeds to reduce ordering and sampling noise.
- Pairwise comparisons were collected for both the Vicuna prompts (80 items) and a larger OpenAssistant validation set (953 user queries).

This combination lets the authors produce both relative percent-of-ChatGPT scores and Elo-based model rankings.

## Key empirical findings

1. GPT-4 largely agrees with humans at the system-ranking level, but only moderately.
   - System-level agreement between GPT-4 and human raters had Kendall Tau τ = 0.43 and Spearman rank correlation r = 0.55. That is moderate agreement, not perfect alignment.

2. Sample-level agreement is weaker.
   - At the individual example level, agreement between GPT-4 and majority human vote had Fleiss' κ = 0.25 (weak agreement).
   - Human annotators themselves had moderate inter-annotator agreement for the task reported as Fleiss' κ = 0.42.

3. GPT-4 shows measurable biases.
   - A pronounced ordering effect: GPT-4 tends to give higher scores to the response that appears first in the prompt. This biases absolute-score comparisons unless order is controlled.
   - GPT-4 appears to favor its own outputs compared to human ratings: GPT-4's Elo for its own outputs is higher (reported as 1348) vs. human-derived Elo (1176), corresponding to about a ~20% higher win probability against an opponent.

4. Automated evaluation can be a reasonable cheap proxy — with caution.
   - GPT-4 and humans often agree on broad rankings (useful for coarse comparisons), but disagree meaningfully on many individual examples and show different biases. The authors conclude that GPT-4 evaluations are "a cheap and reasonable alternative to human evaluation" but note important uncertainties and recommend treating AI evaluations as imperfect.

## Why these findings matter

- Absolute scoring (e.g., 0–10 ratings) is fragile. The ordering effect alone can change perceived model quality. That creates variance that is not due to the models’ outputs but to presentation choices.
- Pairwise judgments aggregated into Elo are empirically more robust to scaling and anchoring issues. Elo translates pairwise win/loss/tie data into a stable skill-like ranking across many models.
- Model-based evaluation introduces systematic biases (e.g., self-favoritism, order bias). These biases can distort conclusions, especially when comparing models that have similar quality.

## Practical recommendations

If you want to use GPT-4 (or another strong model) to evaluate model outputs, follow these best practices drawn from the paper’s methodology and observations:

1. Prefer pairwise comparisons + Elo over absolute scoring. Pairwise judgments reduce anchoring/scale issues and Elo aggregates match outcomes into a stable ranking.

2. Randomize and control ordering. Always present responses in both orders (A then B and B then A) and either balance presentations or average over both orders to mitigate ordering effects.

3. Repeat sampling and aggregate. Resample pairings and recompute Elo multiple times (the paper used 10,000 seeds) to smooth sampling variance.

4. Complement model-based evaluation with a human subset. Use human raters to (a) validate that the model-based ranking is not systematically biased in your domain, and (b) compute inter-annotator agreement (e.g., Fleiss' κ) so you know the human noise floor.

5. Watch for model-specific biases. If you’re evaluating GPT-derived outputs with GPT-based judges, be wary of potential self-preference. Where possible, include a judge that is different from the evaluated model family.

6. Report agreement statistics. Publish Kendall Tau / Spearman correlations between judges and Fleiss’ κ at the example level so readers can judge reliability.

7. Use three-way labels to capture ties. Allowing ties reduces forced decisions and reflects real ambiguity.

## When is AI-based evaluation a reasonable proxy?

- Reasonable to use when you need large-scale, low-cost, comparative rankings across many systems and want a quick sanity check on relative performance, provided you follow the mitigations above (pairwise + order control + human spot checks).
- Risky to rely on as the sole evaluation when fine-grained decisions matter (e.g., deployment safety, critical factual correctness, legal or medical contexts) because GPT-4 and humans disagree substantially on individual examples and GPT-4 exhibits systematic biases.

## Bottom line

GPT-4 can replicate many human judgments and produce useful, low-cost evaluations, especially for system-level ranking. But it is not a drop-in replacement for humans. The QLoRA study shows moderate agreement between GPT-4 and human raters, noticeable ordering and self-favoring biases in GPT-4, and weaker agreement at the example level. If you use AI-based evaluation, adopt pairwise Elo-style aggregation, control presentation order, validate with humans, and report agreement metrics so readers can judge how much weight to place on your automated evaluations.



# Why 4-Bit Training Works: Recovering 16-Bit Performance with Adapters

Modern large language models (LLMs) are powerful but finetuning them remains expensive: full 16-bit finetuning of a 65B model can require hundreds of gigabytes of GPU memory. QLoRA shows a practical alternative: store the base model in 4-bit while backpropagating through its (frozen) quantized weights into a small set of trainable Low-Rank Adapters (LoRA). The result: match 16-bit finetuning performance on a range of tasks and architectures, while cutting memory enough to finetune 65B models on a single 48GB GPU.

This post focuses on the key concepts that make this possible and why the specific choices in QLoRA (NF4, Double Quantization, and LoRA placement) matter. I’ll simplify the ideas but keep the math and mechanisms intact.

## The big idea in one sentence

Store the pretrained weights in a carefully designed 4-bit format, dequantize to high precision at runtime, and train only small extra adapter weights (LoRA) by backpropagating through the dequantization. Because the heavy parameter updates are restricted to adapters (in full precision) and the dequantization is precise enough, the finetuned model recovers the 16-bit accuracy of full finetuning.

## Why quantize at all, and why 4-bit?

Quantization reduces the memory footprint by storing each parameter with fewer bits. A standard quantization pipeline rescales tensor values and maps them into fewer discrete bins. For example, an 8-bit integer quantization is often written as

$X^{\text{Int8}} = \text{round}\!\left(c \cdot X^{\text{FP32}}\right)$,

with dequantization

$\text{dequant}(c, X^{\text{Int8}}) = X^{\text{Int8}} / c$.

Block-wise quantization (chunking tensors, each with its own scale $c$) reduces the effect of outliers by letting each block use the available quantization bins more effectively.

Going from 16-bit to 4-bit reduces storage dramatically, but naive 4-bit quantization hurts model performance. QLoRA narrows that gap by two core ideas: an information-theoretically better 4-bit data type tuned to weight distributions (NF4) and finetuning only low-rank adapters while keeping the quantized base frozen.

## NormalFloat 4 (NF4): match the quantization to weight statistics

Pretrained network weights are typically close to zero-centered Gaussians (empirical observation). QLoRA exploits that: instead of using uniform FP4 or Int4 bins, it designs the 4-bit data type so that each quantization bin has equal expected mass under a standard normal distribution. Concretely:

1. Compute the theoretical quantiles of \(N(0,1)\) to obtain boundary points for the \(2^k\) bins.
2. Normalize the bin centers into the range \([-1, 1]\).
3. For any real tensor, rescale by its absolute max (or equivalently its standard deviation) so its range matches \([-1,1]\), then quantize into those NF4 bins.

The resulting NFk data type (NF4 when \(k=4\)) is information-theoretically optimal for zero-mean normal data: each bin is used equally in expectation, which reduces quantization error for the common case of normally distributed weights. NF4 empirically outperforms FP4 and Int4 on post-quantization zero-shot tasks and perplexity (across many model families and scales).

Two practical details:
- NF4 uses an asymmetric construction so that zero can be represented exactly (important for padding/zeros).
- Block-wise quantization is still used (e.g., blocksize 64) to handle outliers at the local level.

## Double Quantization: make the quantization metadata smaller

Block-wise quantization requires storing a scale constant per block. For small block sizes, these constants add noticeable overhead. QLoRA reduces that overhead by quantizing the quantization constants themselves: quantize the per-block FP32 scales into an 8-bit float representation (FP8) with a larger blocksize. This "double quantization" reduces the average bits per parameter used by scale metadata without hurting performance.

Roughly: instead of storing 32 bits per scale for every block of 64 parameters (0.5 bits/parameter), storing FP8 scales with a larger blocksize reduces this to about 0.127 bits/parameter — a worthwhile saving for huge models.

## Backpropagation through quantized weights into LoRA adapters

This is the key training mechanism. The base weights \(W\) are quantized and frozen in storage, say as NF4. At runtime they are dequantized to a higher-precision computation format (BFloat16), and forward and backward passes use the dequantized values. LoRA inserts small trainable matrices \(\mathbf{L}_1, \mathbf{L}_2\) and modifies a linear projection

\(\mathbf{Y} = \mathbf{XW} + s \mathbf{X} \mathbf{L}_1 \mathbf{L}_2.\)

During finetuning QLoRA:
- Only the LoRA parameters \(\mathbf{L}_1, \mathbf{L}_2\) are updated (kept in BF16).
- Gradients must flow through the dequantization of \(W\) to compute the necessary derivatives to update adapters. That is, we compute gradients like \(\partial E / \partial \mathbf{L}_i\) while treating \(\mathbf{W}\) as a constant in the optimizer (though we do backpropagate through the operations that used the dequantized \(\mathbf{W}\)).
- In practice, the storage data type is NF4 (4-bit) and the computation data type is BF16. The pipeline is: dequantize NF4 -> BF16 compute -> compute gradients for adapters (BF16) -> update adapters.

Because the adapters are small and stored/updated in high precision, they can learn to compensate for the information lost during quantization. Empirically, with this setup, QLoRA recovers the performances of both full 16-bit finetuning and 16-bit LoRA finetuning across architectures (encoder, encoder-decoder, decoder-only) and tasks.

## LoRA placement and scale matter

A practical take-away from QLoRA: it is not enough to add LoRA only to the attention query/value matrices (a common practice). To reach parity with full finetuning, LoRA adapters need to be applied to all linear layers in the transformer blocks. The number of adapters is the most important LoRA hyperparameter for matching 16-bit performance. Other LoRA hyperparameters (e.g., rank \(r\)) are less critical.

Because the LoRA parameters are small relative to activation gradients and the quantized base model, adding adapters to every layer is memory-feasible and important for accuracy.

## Paged Optimizers: avoid memory spikes

Activation gradients are the principal memory consumer during training, and batch processing of long sequences can cause transient memory spikes. QLoRA uses "Paged Optimizers" leveraging NVIDIA Unified Memory to automatically page optimizer states to CPU memory when the GPU runs out of memory, preventing OOMs during occasional spikes without a performance hit in typical settings.

## Empirical results that matter

- QLoRA (NF4 + Double Quantization + LoRA everywhere) matches 16-bit full finetuning and 16-bit LoRA finetuning across GLUE, Super-NaturalInstructions, and 5-shot MMLU (models from 125M up to 65B in various experiments).
- NF4 substantially outperforms FP4 and Int4 in post-quantization zero-shot accuracy and perplexity across many model families and sizes.
- Double Quantization reduces storage of scales without measurable performance loss.
- Applying LoRA to all linear layers (not just attention projections) is necessary to match full finetuning.
- Using QLoRA, the authors finetuned Guanaco models (up to 65B) that reach near-ChatGPT performance on the Vicuna benchmark while being trainable in 24 hours on a single 48GB GPU.

## Where FP4 falls short compared to NF4

FP4 is a straightforward 4-bit floating representation (typically a very narrow exponent/mantissa format). Because pretrained weights closely follow normal distributions whose quantiles are not uniformly aligned with FP4 bins, FP4 assigns bits suboptimally, especially around high-density regions near zero and for the tails. NF4, by designing bins that match the quantiles of \(N(0,1)\), reduces quantization error where the mass is concentrated and improves representation of typical weight values. Empirically NF4 gives better perplexity and downstream task accuracy than FP4 in the same experimental setups.

## Practical implications and caveats

- QLoRA makes large-scale finetuning accessible: 33B models can be finetuned on 24GB consumer GPUs and 65B on a single 48GB pro GPU.
- The method recovers 16-bit accuracy on a wide set of benchmarks and architectures, but the authors note they did not fully prove parity at all scales for full 16-bit finetuning across every metric—some large-scale full-finetuning comparisons remain for future work.
- Evaluation of chatbots and instruction-tuning is nuanced: dataset suitability matters a lot (small high-quality datasets can beat much larger low-quality ones), and automated evaluators like GPT-4 show biases (e.g., order effects) relative to humans. These are orthogonal issues but important when judging "state-of-the-art" conversational performance.

## Takeaway

QLoRA shows a practical and well-justified path to 4-bit finetuning without sacrificing 16-bit accuracy: use a quantization format matched to weight statistics (NF4), compress metadata (Double Quantization), allow gradients to flow through accurate dequantization, and concentrate updates in full-precision LoRA adapters placed across all linear layers. The combination recovers the fidelity of full 16-bit finetuning while dramatically lowering memory usage, opening up large-model finetuning to much more modest hardware.

If you want to experiment: the authors released code, CUDA kernels for 4-bit training, and many pretrained adapters — so these ideas are reproducible and ready for practical use.



# The Bigger Picture: How QLoRA Democratizes LLM Finetuning

## Intro — why QLoRA matters

Finetuning large language models (LLMs) has traditionally been an expensive, multi‑GPU operation. The QLoRA paper demonstrates a practical change: by quantizing a pretrained model to 4 bits and training small low-rank adapters (LoRA) while keeping the main weights frozen, you can finetune models up to 65B parameters on a single professional GPU (48GB) and 33B on a single consumer GPU (24GB) without measurable loss compared to 16‑bit finetuning. That reduction in memory and compute opens pathways for researchers, small teams, and even device‑level workflows that were previously infeasible.

Below I summarize the technical enablers, the concrete outcomes the paper demonstrates (including the Guanaco models), and the broader implications—both positive and cautionary.

## What makes QLoRA efficient (the short technical tour)

QLoRA combines three core engineering/algorithmic ideas to enable high‑quality finetuning with minimal GPU memory:

- 4‑bit NormalFloat (NF4): a 4‑bit quantization data type that is designed to be information‑theoretically optimal for zero‑mean normally distributed weights. Instead of uniform integer bins or naive 4‑bit floats, NF4 uses quantiles of a standard normal to define the representable values, then rescales per block. This improves quantization fidelity compared to FP4 or Int4 for typical pretrained weight distributions.

- Double Quantization: the paper reduces the memory cost of per‑block quantization constants by quantizing those constants themselves (i.e., quantize the quantization scale). Practically, they store the first‑level quantization constants in a compact format (FP8 with a larger blocksize) and keep a small FP32 backup constant. This cuts the per‑parameter overhead from about 0.5 bits down to ~0.127 bits on average for their chosen block sizes, shaving several GB for large models.

- Paged Optimizers: to avoid out‑of‑memory spikes during gradient checkpointing, optimizer state is allocated in pageable memory (using NVIDIA unified memory) so pages can be moved between CPU and GPU as needed. This makes large single‑GPU runs stable without needing many‑GPU memory pooling.

Key operational point: QLoRA stores the base weights in NF4, dequantizes them to a 16‑bit compute format (BFloat16/BrainFloat) for forward/backward, and only computes and stores gradients for the LoRA adapter parameters (which remain full‑precision). In short: low storage precision, high compute precision, and tiny learnable adapters.

## Does this actually match full finetuning quality?

The paper reports extensive experiments showing that 4‑bit QLoRA with NF4 + Double Quantization recovers the performance of 16‑bit finetuning and 16‑bit LoRA finetuning across multiple architectures, datasets, and model sizes (125M up to 65B in some settings). Specific takeaways:

- NF4 empirically outperforms FP4 and Int4 in post‑quantization zero‑shot accuracy and perplexity across evaluated models.
- 4‑bit QLoRA matches 16‑bit baselines on GLUE, Super‑NaturalInstructions, and MMLU (5‑shot) in their reported setups.
- The authors emphasize that to reproduce full‑finetuning performance you typically need LoRA adapters placed broadly (not just on query/value matrices) and appropriately tuned LoRA hyperparameters.

So, QLoRA is not only a memory trick—it preserves task performance when combined with the right adapter strategy.

## Real outcome: Guanaco — a state‑of‑the‑art open model example

Using QLoRA, the authors trained the Guanaco family (7B/33B/65B) and report that Guanaco 65B reaches 99.3% of ChatGPT performance on the Vicuna benchmark (using GPT‑4 based scoring relative to ChatGPT). Guanaco 33B and 7B also show strong results: the 33B model can be trained on 24GB consumer GPUs in under 12 hours, and the 7B fits into ~5GB when deployed. These outcomes highlight two practical points:

- Large, competitive chatbots can be produced with modest hardware and relatively short wall clock time.
- Model size and precision tradeoffs matter: increasing parameter count while lowering precision can be an effective use of a fixed resource budget.

The paper also releases code and CUDA kernels (NF4 kernels and related tooling) to make these techniques available to the community.

## Practical implications: accessibility, privacy, and mobile finetuning

QLoRA materially lowers the entry barrier for high‑quality finetuning. Important implications include:

- Research accessibility: single‑GPU finetuning for 33B/65B models lets smaller labs and independent researchers experiment with model scales that used to require racks of GPUs, enabling broader participation in LLM research and auditing.

- Faster iteration: shorter finetuning runs on a single device speed up experimentation cycles, which helps reproducibility and democratizes model development (more people can iterate on models and datasets).

- On‑device or near‑device personalization: the paper argues that QLoRA makes device‑level finetuning plausible. They estimate that with a modern phone (example: iPhone 12 Plus) one could finetune on the order of millions of tokens overnight while charging. That points toward privacy‑preserving personalization workflows where data never leaves the user’s device.

- Open tooling and kernels: by releasing CUDA kernels, Double Quantization tooling, and integration with popular stacks (Hugging Face Transformers), the authors lower friction for adoption beyond the original group.

All of the above are grounded in the paper’s experiments and stated estimates.

## Evaluation caveats and what the results do not say

The paper is careful to point out limitations and caveats that matter when interpreting the new accessibility:

- Benchmarks are not perfect proxies for real‑world behavior. The authors find mismatches across benchmarks (e.g., MMLU vs. Vicuna chatbot performance) and note that dataset suitability often matters more than sheer size.

- Automated evaluators (GPT‑4 used for scoring) correlate moderately with human judgments but have biases (e.g., an order effect favoring the first response). Human and GPT‑4 rankings correlate but not perfectly; sample‑level agreement is limited.

- The authors did not exhaustively show that QLoRA exactly matches full finetuning for every setting at 33B/65B; some aspects (e.g., full 16‑bit equivalence at the very largest scales under all conditions) remain to be explored.

In short: QLoRA makes large‑scale finetuning feasible, but evaluation of final model behavior—factuality, safety, bias, calibration—still requires careful, often human, vetting.

## Dual‑use, safety, and ethical considerations

Lowering the resource bar is broadly beneficial, but it also amplifies dual‑use concerns:

- Easier finetuning means harmful applications (misinformation generation, personalized disinformation, automated abuse tools) could be developed with fewer resources. The paper acknowledges this explicitly.

- Open release of kernels and adapters accelerates both beneficial and potentially harmful reuse. That tradeoff is a societal one: democratization promotes independent audits, transparency, and innovation, but also increases availability for malicious actors.

The authors recommend and demonstrate partial mitigations (e.g., reporting results on bias checks, analyzing refusal behavior), but they emphasize that more evaluation and governance work is needed as model finetuning becomes pervasive.

## Bottom line

QLoRA is a practical, well‑engineered approach that reduces memory requirements enough to finetune very large LLMs on single GPUs while retaining performance. That changes the playing field: researchers and practitioners with modest hardware can now experiment at scales previously reserved for large labs. The implications are wide: faster iteration, more open research, potential for local/private personalization, and broader auditability. At the same time, the same accessibility heightens dual‑use risks and makes careful evaluation, responsible release practices, and continued study of model safety and benchmark validity more important than ever.

If you plan to adopt QLoRA, the paper’s code, NF4 kernels, and the released Guanaco adapters are a good place to start. And if you’re thinking about deploying finetuned models, invest early in robust human evaluation, bias analysis, and guardrails—because the technical barrier is no longer the only limiting factor.
