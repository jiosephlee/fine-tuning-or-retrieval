\title{A Textbook about the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

Chapter 6: QLoRA Mechanics: Storage vs Compute Types and Training Flow

# Storage in 4-bit NF4, compute in BF16
A central design decision in QLoRA is the separation between the storage data type used for the pretrained base model weights and the computation data type used during forward and backward passes. The base model weights are stored in a highly compact 4-bit representation termed NF4 (4-bit NormalFloat). NF4 is a quantization data type specifically designed to be information-theoretically optimal for zero-centered normally distributed tensors (as typical for pretrained network weights). Practically, this means each block of stored weights holds only 4 bits per value plus small per-block quantization constants; the combination preserves much of the statistical structure of the original floating-point weights while reducing memory usage dramatically.

Although the weights are stored in NF4, QLoRA never performs arithmetic directly in that 4-bit domain. Instead, whenever a stored weight tensor is needed for computation, it is dequantized into a higher-precision computation type. The computation data type used in QLoRA is typically BFloat16 (BF16, called BrainFloat16 in the paper), which offers a 16-bit floating-point format with large dynamic range and sufficient precision for matrix multiply and gradient computations in this setup. In short: storage = NF4 (4-bit), compute = BF16 (16-bit). This split permits storing very large models compactly on scarce GPU memory while still operating with adequate numeric precision at runtime.

# Double dequantization at use-time
QLoRA introduces a small multi-stage dequantization pipeline because storage is not just the 4-bit NF4 tensor: block-wise quantization requires per-block quantization constants, and QLoRA applies a further compression called Double Quantization to those constants. Concretely, a stored linear weight tensor in QLoRA is represented by (i) the k-bit NF4 integers representing quantized values per block, (ii) second-level quantization of the per-block constants stored in an 8-bit float form, and (iii) a small set of 32-bit scaling constants used at the outer level. At use-time these pieces are combined via a double dequantization operation that recovers a BF16 approximation of the original full-precision weights.

Formally, if we denote the NF4 stored tensor by $\mathbf{W}^{\text{NF4}}$, the k-bit representation of the second-level constants by $c_2^{\text{k-bit}}$, and the final-level FP32 constants by $c_1^{\text{FP32}}$, the double dequantization function is written as:

\[
\text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{NF4}}) \;=\; \text{dequant}\big(\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}),\; \mathbf{W}^{\text{NF4}}\big) \;=\; \mathbf{W}^{\text{BF16}}.
\]

In words: first dequantize the quantized constants into FP32 to reconstruct per-block scales, then use those scales to dequantize the NF4 integer bins into BF16 values ready for matrix operations. This double dequantization recovers a BF16 tensor suitable for both forward activations and the backward propagation of derivatives needed by adapters.

# Forward pass: dequantized W plus LoRA low-rank update
During the forward pass through a linear layer, QLoRA composes two contributions to the layer output: (1) the dequantized base-model linear projection computed from the NF4-stored weights, and (2) the low-rank LoRA adapter correction, which is a small learnable rank-$r$ factorization added to the projection. Let $\mathbf{X}^{\text{BF16}}$ denote the input activations in BF16, and for a linear layer with original weight $\mathbf{W}$ the standard projection is $\mathbf{X}\mathbf{W}$. In QLoRA we compute:

\[
\mathbf{Y}^{\text{BF16}} \;=\; \mathbf{X}^{\text{BF16}}\; \text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{NF4}})\; +\; \mathbf{X}^{\text{BF16}}\mathbf{L}_1^{\text{BF16}}\mathbf{L}_2^{\text{BF16}}.
\]

The first term is the dequantized base projection, now in BF16. The second term is the LoRA update with adapter matrices $\mathbf{L}_1\in\mathbb{R}^{h\times r}$ and $\mathbf{L}_2\in\mathbb{R}^{r\times o}$ stored and computed in BF16. A scalar multiplier $s$ used in LoRA formulations can be absorbed into $\mathbf{L}_2$ or applied explicitly; in all cases the adapter computations are performed at BF16 precision. Because LoRA parameters are small relative to the base model, computing them in BF16 and storing their gradients at BF16 constitutes a negligible memory cost compared to the base model, while enabling high-fidelity learning in the low-rank subspace.

This forward composition has two practical implications. First, it keeps the large base model frozen: the NF4 weights are not updated and are only read and dequantized when needed. Second, it provides the expressivity to adapt model behavior through the small LoRA matrices without changing the stored base weights.

# Backward pass: gradients only for LoRA parameters
A key memory-saving feature of QLoRA is that gradients are computed only for the LoRA adapter parameters; gradients with respect to the quantized base-model weights are not computed or stored. During backpropagation we still need to compute derivatives that flow through the frozen linear projection because the LoRA parameters depend on the activations that in turn depend on the base weights. Concretely, to compute gradients of the loss $E$ with respect to the LoRA parameters, we must compute quantities such as $\partial E/\partial \mathbf{L}_i$, which depend on the forward pathway that used the dequantized base weight $\mathbf{W}^{\text{BF16}}$.

Because the dequantized weight tensor is available at BF16 precision during the forward pass, the backward pass can compute the necessary Jacobian-vector products and activation gradients using BF16 arithmetic. But the algorithm does not compute $\partial E/\partial \mathbf{W}$ to update the base weights. Omitting base weight gradients removes the need to reserve optimizer state memory (moment estimates, second moments, etc.) and greatly reduces overall memory consumption. The only gradients that need to be stored and used by the optimizer are those associated with the LoRA factors $\mathbf{L}_1$ and $\mathbf{L}_2$, which are small.

In practice, while gradients are not taken with respect to the stored NF4 integers, the backward computation does involve the dequantized BF16 tensor because the chain rule applies through the dequantization operation. The important distinction is that the base tensor is treated as a fixed function (a constant w.r.t. optimization) rather than an optimizable parameter, so no parameter-update step for base weights is performed.

# Why backprop through dequantized W is sufficient
Why is it sufficient to backpropagate through the dequantized BF16 representation of the NF4-stored base weights rather than through high-precision stored weights or through the NF4 integers themselves? There are several interlocking reasons grounded in QLoRA's design.

First, the LoRA adapters are the only trainable parameters; the base weights are intentionally frozen. Training the adapters requires gradients that measure how changes in adapter parameters affect the loss. Those gradients are computed using the forward computation that depends on the current (frozen) base projection. Computing these gradients only requires the numerical value of the base projection and its effect on subsequent activations; it does not require computing or applying gradients to the base weights themselves. The dequantized BF16 tensor accurately represents the base projection for the purpose of computing these activation derivatives.

Second, BF16 arithmetic provides sufficient precision for the matrix-multiply and accumulation operations used in these gradient computations. Because the adapter gradients are comparatively small and because the dequantized tensor restores most of the base-model numerical content, the chain-rule computations that yield $\partial E/\partial \mathbf{L}_i$ are reliable when performed at BF16. The empirical results reported in the paper show that this approach recovers full 16-bit finetuning accuracy (when NF4 and Double Quantization are used as described), indicating the numerical path through BF16 dequantized weights is adequate for the optimization of adapters.

Third, treating the quantization-dequantization pipeline as a read-only deterministic transform means the backward computation need only treat dequantization as part of the computational graph for derivative propagation. Since we do not need to update quantization parameters during adapter training, doing the full dequantization to BF16 at use-time and then backpropagating through those BF16 values is both conceptually simple and memory efficient.

# Precision choices and their practical implications
The precision choices in QLoRA—NF4 for storage and BF16 for compute—are a careful balance between memory efficiency and numerical reliability. Storing weights in NF4 yields a roughly 8x reduction in raw weight storage compared to FP32 and an approximate 4x reduction compared to BF16, enabling very large models to fit into single GPUs. However, low-bit storage by itself is too lossy for training unless the computation uses a higher-precision representation. Hence the dequantization to BF16 for computation.

Using BF16 as the computation type has practical advantages. BF16 has the wide dynamic range of FP32 but reduced mantissa bits; this often maintains stability for matrix multiplications and gradient computations in large models while halving memory for intermediate activations and certain optimizer states relative to FP32. Because only the small LoRA parameters are updated and maintained in BF16, the additional BF16 memory burden is modest.

Double Quantization further reduces the memory overhead of storing per-block quantization constants by quantizing those constants themselves (e.g., to FP8 for the second level). This reduces the average bits per parameter used by constants without degrading empirical performance. Together, NF4 plus Double Quantization and BF16 computation enable finetuning of extremely large models (e.g., 65B parameters) on hardware with limited GPU memory (e.g., a single 48GB GPU) while achieving task performance that matches full-precision finetuning baselines.

Finally, practical runtime considerations motivate additional mechanisms such as Paged Optimizers (noting that optimizer states for adapter parameters can be paged to CPU memory to avoid transient GPU OOM spikes). But at the core, the combination of 4-bit storage with BF16 compute and adapter-only updates is what gives QLoRA its favorable tradeoff: drastically reduced storage with high-fidelity training behavior because the compute path operates in a sufficiently precise numeric regime.
