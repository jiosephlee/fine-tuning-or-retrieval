Chapter 5: Paged Optimizers: Engineering Around Memory Spikes

# The problem: transient spikes from long sequences with checkpointing

When training very large language models, the dominant memory consumer is often not the model parameters themselves but the intermediate activations and their gradients. To reduce peak activation memory, practitioners commonly use activation (gradient) checkpointing: recompute activations on the backward pass instead of storing them during the forward pass. Checkpointing trades extra compute for lower steady-state memory usage, but it does not eliminate all memory variability. In particular, real workloads contain examples with widely varying sequence lengths. A minibatch that contains one or more unusually long sequences can create a transient but large spike in activation memory during the forward or backward pass. If that spike exceeds the GPU's available DRAM, training aborts with an out-of-memory (OOM) error even though the model would fit the GPU memory for the average-case input length.

This transient-OOM problem becomes especially acute for very large models (tens of billions of parameters) where there is little headroom in device memory. The standard remedies—reducing batch size, clipping sequence length, or reconfiguring checkpointing—work but are blunt: they reduce throughput, change the training distribution, or require careful per-run tuning. For researchers who wish to finetune very large models on a single GPU (e.g., finetuning a 65B parameter model on a 48 GB GPU), the problem of occasional long-sequence spikes is a practical blocker. Paged optimizers are an engineering approach designed to tolerate those transient memory spikes without changing model microstructure or average throughput.

# Unified Memory paging between CPU and GPU

Modern NVIDIA platforms expose Unified Memory, a system that makes a region of CPU-addressable memory appear as a single virtual memory space usable by both the CPU and the GPU. Under the hood, the CUDA driver can migrate pages between host RAM and device DRAM on demand. The migration is automatic: when the GPU tries to access a page that currently resides in host memory, the runtime faults, copies the page onto the device, and resumes execution. Conversely, pages that are not frequently accessed can be evicted back to host memory to free device DRAM.

This automatic page-level transfer mechanism behaves like OS-level paging but between host RAM and GPU DRAM. The important property for finetuning is that large tensors allocated in Unified Memory do not permanently occupy device DRAM; instead, they can be resident on the CPU and only migrate to the GPU when actively accessed. If accesses are infrequent or concentrated in short critical phases, Unified Memory can reduce the peak DRAM footprint visible to the GPU at any instant, helping avoid OOMs caused by transient activation spikes.

# Allocating optimizer states in pageable memory

Paged optimizers exploit Unified Memory by placing the optimizer state tensors (momentum buffers, second-moment accumulators, or other per-parameter states) into pageable Unified Memory instead of conventional GPU-only allocations. The optimizer state for large models can be substantial in size; keeping those states resident on the GPU increases the baseline memory footprint and leaves little room for transient activation spikes. By allocating optimizer state in Unified Memory, the runtime can automatically evict those optimizer pages to host memory when the GPU needs space for activations, and bring them back just in time when the optimizer update step runs and requires access.

The QLoRA paper describes this strategy succinctly: use NVIDIA Unified Memory to allocate paged memory for the optimizer states so they "are then automatically evicted to CPU RAM when the GPU runs out-of-memory and paged back into GPU memory when the memory is needed in the optimizer update step." In practice, this means that during the forward and backward passes—when activations are being produced and recomputed—the optimizer pages can remain on the host, freeing GPU DRAM for activations. Later, during the optimizer step (parameter updates), the required pages are migrated back to device DRAM for the update computation.

This approach needs minimal changes to the optimizer logic: from a programmer's point of view, the optimizer still reads and writes the same tensors; the differences are in how those tensors are allocated (in Unified/Pageable memory rather than device-only memory) and in the performance characteristics, which now depend on page movement patterns.

# Observed runtime behavior at 65B on 48GB GPUs

The QLoRA work applied paged optimizers to enable finetuning of extremely large models on single GPUs with limited DRAM (e.g., a 65B parameter model on a 48 GB GPU). Although paging introduces the potential for extra data movement, the authors report that paging mostly occurs only in rare circumstances—specifically when processing minibatches containing long sequence lengths that produce spikey memory patterns. In their measurements for a 65B model on a 48 GB GPU with batch size 16, the authors find that paged optimizers provide the same training speed as regular (device-resident) optimizers. That is, for the settings they evaluated, the automatic page transfers did not introduce a measurable runtime slowdown, while they avoided OOM failures caused by transient activation spikes.

Two aspects explain why paging did not slow training in their reported setting. First, optimizer states are typically touched only during the optimizer update step (once per minibatch): during the forward/backward passes many optimizer pages can remain untouched and therefore resident on the host without incurring migration. Second, pager activity is sparse: long-sequence-induced spikes are uncommon, so most minibatches never cause eviction or migration. When page migrations are infrequent relative to computation, the amortized cost of migrating optimizer pages is small compared to the total compute cost of a training step on a large model.

# When paging can cause slowdowns and open questions

Although the reported measurements are encouraging, Unified Memory paging is not cost-free and can cause slowdowns in some situations. The QLoRA paper acknowledges that paging only occurs when processing minibatches with long sequence lengths and therefore provides the same training speed "in the scenario" tested, but it also points out that future work should measure and characterize under what circumstances slow-downs occur from the paging process. From the mechanisms of Unified Memory and practical experience, several potential slowdowns and unanswered questions emerge:

- Frequency of migrations: If optimizer pages must be migrated to the GPU every step (for example, because the optimizer frequently reads or updates many pages during intermediate phases or because activation access patterns force frequent evictions), the page transfer bandwidth can become a bottleneck. Page migrations move data over the PCIe (or NVLink) interconnect, which is far slower than on-device DRAM bandwidth. In the worst case, frequent migrations can significantly reduce training throughput.

- Page granularity and fragmentation: Unified Memory migrates at page granularity (commonly 4 KB or larger). If optimizer data access patterns are fragmented across many pages, the total volume of migrated data could exceed the useful working set, increasing transfer overhead. The distribution of optimizer tensor touches and the alignment of tensors to page boundaries can therefore influence performance.

- Overlap of migration and compute: The CUDA runtime may be able to overlap some page transfers with computation, but effective overlap depends on where and when pages are accessed relative to compute kernels. If migrations stall kernels (because a kernel immediately accesses pages that are still on the host), the GPU can be idle while waiting for transfers.

- Host memory pressure and OS interference: Unified Memory moves pages to host RAM when evicting from GPU. If the host system is memory constrained or other processes compete for RAM, eviction and migration responsiveness can degrade. Moreover, kernel-level interference (e.g., other processes triggering page faults) could increase unpredictability.

- Interactions with other memory-management strategies: Systems that already use memory partitioning, memory pools, or custom allocators may interact with Unified Memory in complex ways. Ensuring deterministic performance in such combined systems can be challenging.

- Variability across hardware and drivers: Different GPUs, interconnects (PCIe vs NVLink), and driver/runtime versions influence the latency and bandwidth of migrations and the sophistication of migration heuristics. Results observed on one platform (e.g., a 48 GB GPU with a particular driver) may not generalize.

These points define a short list of open engineering and research questions. The QLoRA paper explicitly defers a detailed measurement study, noting that "future work should measure and characterize under what circumstances slow-downs occur from the paging process." Practical investigations could systematically vary sequence-length distributions, batch sizes, optimizer state sizes, and hardware interconnects to chart a performance envelope for paged optimizers.

# Practical guidance and takeaway

Paged optimizers are a pragmatic engineering lever to avoid catastrophic transient OOMs without globally lowering model throughput or changing the training objective. The core idea—put large but infrequently accessed optimizer state into pageable Unified Memory so it is evicted during activation peaks and brought back for updates—lets developers trade predictable but rare cross-device data movement for robustness on resource-constrained GPUs.

From the QLoRA study the immediate practical takeaways are:

- For very large-model finetuning on a single GPU (e.g., 33B or 65B models on 24–48 GB devices), allocating optimizer states in Unified/Pageable memory can prevent rare sequence-length-induced OOMs that would otherwise abort training.

- In the specific measurements reported, with a 65B model on a 48 GB GPU and a batch size of 16, paged optimizers achieved the same training speed as regular optimizers, indicating that page migrations were sufficiently infrequent or well-overlapped to be negligible in that setting.

- Because paging behavior depends on workload distribution and hardware, engineers should treat Unified Memory as a performance knob: test representative minibatch distributions (including rare long sequences), profile page migrations, and validate that the amortized overhead is acceptable on their target hardware.

- There remain open questions about worst-case degraded throughput under heavy paging, and about how paging interacts with different interconnects, OS memory pressure, and optimizer algorithms. These warrant systematic future measurement and possible tooling (for example, heuristics to prefetch optimizer pages just before updates, or selective pinning of hot optimizer tensors).

Paged optimizers are therefore a valuable technique in the toolbox for enabling large-model training on limited hardware. They provide an engineering path around transient memory spikes that would otherwise force either smaller models or onerous dataset preprocessing, while leaving room for follow-up work to more precisely characterize and optimize paging behavior.
