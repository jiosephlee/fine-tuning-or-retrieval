\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### What exactly is stored in memory during QLoRA training, and where are the savings coming from?
Question:
In the Memory Requirement section, the paper says the 4-bit base model is about 5,048 MB for LLaMA-7B and that LoRA gradients can dominate memory without gradient checkpointing. Could someone provide a precise breakdown for a single transformer layer during training with QLoRA? Specifically: 1) storage for quantized weights $\mathbf{W}^{\text{NF4}}$, 2) storage for quantization constants with double quantization ($c_1$, $c_2$), 3) dequantized temporary BF16 weights during forward/backward, 4) activations and activation gradients with gradient checkpointing, 5) optimizer states for LoRA (paged) vs. full-model? Which of these scale with sequence length vs. parameter count?
Answer:
Short answer: QLoRA stores the base model weights compressed on‑device as $4$‑bit $\mathrm{NF4}$ plus small per‑block quantization constants (with double quantization), and it dequantizes those to a $\mathrm{BF16}$ buffer on the fly for compute. During training you also store (a) activations (and activation gradients), (b) the small LoRA parameters and their optimizer state, and (c) temporary dequantized $\mathrm{BF16}$ weight tensors needed for forward/backward. The big memory savings come from (1) replacing full‑precision storage of the entire base model with $4$‑bit storage + tiny quant constants, (2) only keeping optimizer state for the much smaller LoRA adapters (not the full model), and (3) paging optimizer state to CPU and using gradient checkpointing so activations, not parameter state, dominate GPU peak. Below I give a concise per‑transformer‑layer breakdown, with formulas showing what scales with sequence length versus parameter count.

Notation: let the layer be a linear projection $W$ with shape $h\times o$ (so it has $P = h\cdot o$ parameters). Let blocksize for $W$ quantization be $B$ (paper uses $B = 64$). Let the LoRA rank be $r$ so LoRA adds $L_1 \in \mathbb{R}^{h\times r}$ and $L_2 \in \mathbb{R}^{r\times o}$. Let batch size be $b$ and sequence length be $L$ (tokens). $\mathrm{BF16}$ is $16$ bits, $\mathrm{NF4}$ is $4$ bits, $\mathrm{FP32}$ is $32$ bits, $\mathrm{FP8}$ used for second quantization of constants.

1) Storage for quantized weights $W^{\mathrm{NF4}}$ (persistent on GPU)
You store the base weight values in $4$ bits each. Memory = $P\cdot 4\ \text{bits} = P\cdot 0.5\ \text{bytes}$. This scales with parameter count $P$ (not with sequence length). Example: a $7\text{B}$ model total weights $\sim 7\times 10^{9}$ parameters; per layer it is proportional to $P$.

2) Storage for quantization constants with double quantization ($c_2, c_1$)
With blockwise quantization you need one quantization constant per block of size $B$. If there are $n = P / B$ blocks, the original single quantization would store $c_2^{\mathrm{FP32}}$ per block ($32$ bits each) giving $32\cdot n$ bits $= (32/B)$ bits per parameter $= 32/B\ \text{bits/param}$. The paper points out that with $B=64$ this is $32/64 = 0.5\ \text{bits/param}$. Double Quantization treats the $c_2$ values as a tensor and quantizes them to an $8$‑bit format ($\mathrm{FP8}$) with a second‑level $c_1^{\mathrm{FP32}}$ used to dequantize. With the paper's choices ($W$ blocksize $64$, $c_2$ blocksize $256$) the amortized cost becomes approximately $8/64 + 32/(64\cdot 256) = 0.127$ bits per parameter (paper’s calculation), i.e. a reduction of $\sim 0.373$ bits/param. So the constants cost scales with parameter count (because number of blocks $\propto P$), but it is much smaller than storing full $\mathrm{FP32}$ per parameter. Note both $c_2^{k\text{-bit}}$ and the small $c_1^{\mathrm{FP32}}$ are stored; $c_1$ is per (larger) block of $c_2$, so extremely small overhead.

3) Dequantized temporary $\mathrm{BF16}$ weights during forward/backward
For compute the layer dequantizes $W^{\mathrm{NF4}}$ to $\mathrm{BF16}$ (the computation data type). The dequantized $\mathrm{BF16}$ copy size is $P\cdot 16\ \text{bits} = P\cdot 2\ \text{bytes}$. This is a temporary/computation buffer used to run matmuls during forward and to compute $\partial X/\partial W$ during backward (the paper states they dequantize into $\mathrm{BF16}$ to compute derivatives even though they do not update $W$). Whether you need a full separate $\mathrm{BF16}$ copy simultaneously depends on implementation: typically a dequantized tile or the whole layer is dequantized at once and held in $\mathrm{BF16}$ for the forward+backward of that chunk; thus the GPU peak may briefly include this $\mathrm{BF16}$ copy. This term scales with parameter count $P$, not with sequence length $L$. Because $\mathrm{BF16}$ is $4\times$ larger than $\mathrm{NF4}$ storage, dequantization is the single largest per‑layer transient memory cost if you dequantize whole tensors at once.

4) Activations and activation gradients with gradient checkpointing
Activations (hidden states) for this layer have shape $(b, L, h)$ (or $(b\cdot L, h)$ if flattened). Stored in $\mathrm{BF16}$ they cost $b\cdot L\cdot h\cdot 16\ \text{bits}$. Activation gradients produced during backward have similar scale. These terms scale with sequence length $L$ and batch $b$ (and with hidden size $h$, which ties to parameter counts but are not the same as $P$). The paper emphasizes activations dominate memory in finetuning and that gradient checkpointing reduces stored activations by recomputing forward parts as needed: with checkpointing you store fewer intermediate activations and recompute during backward, trading GPU compute for much lower memory. The paper gives an example: for a $7\text{B}$ LLaMA model with batch size $1$ and typical LoRA setup, LoRA input gradients were $567\ \text{MB}$ without checkpointing and average $18\ \text{MB}$ per sequence with checkpointing — showing activation/activation‑gradient terms depend strongly on $L$ and checkpoint strategy. So activation memory $\propto b\cdot L$ (sequence‑length dependent), whereas most parameter storage is sequence‑length independent.

5) Optimizer states for LoRA (paged) vs. full‑model optimizer states
If you were to full‑finetune the entire model you would need optimizer state (e.g., Adam has two moment accumulators) for all $P$ parameters, typically stored in $16$ or $32$‑bit (two or more tensors of size $P$). That would scale as $O(P)$ and be very large. QLoRA only trains the LoRA adapter parameters (size $P_{\mathrm{LoRA}} = h\cdot r + r\cdot o \approx r\cdot(h+o)$), which is tiny relative to $P$. So optimizer state stored on GPU is only for the LoRA params (and possibly small extra state for other trainable modules). The paper uses Paged Optimizers: optimizer state can be allocated in unified memory and paged to CPU when not needed, avoiding GPU OOM spikes. Thus optimizer state for LoRA still scales with LoRA parameter count, not with full $P$, and can be paged off GPU to reduce GPU footprint further. In short, optimizer state cost with QLoRA is $O(P_{\mathrm{LoRA}})$ on GPU (and $O(P_{\mathrm{LoRA}})$ overall if paged to CPU), whereas full finetuning would be $O(P)$ and dominate memory.

Additional important points and interactions
- Which quantities scale with sequence length $L$: activations and activation gradients ($b\cdot L\cdot h$), and the temporary activation‑related gradients used to compute LoRA gradients (so LoRA gradient memory depends on activations too). Also some per‑token caches depending on implementation (attention caches for generation), but those are separate from training when you train with causal LM cross‑entropy.
- Which quantities scale with parameter count $P$: stored $4$‑bit $W^{\mathrm{NF4}}$ ($P\cdot 4\ \text{bits}$), quantization constants and their second quantization ($\approx P\cdot 0.127\ \text{bits}$ after DQ for the paper’s choices), temporary dequantized $\mathrm{BF16}$ copy ($P\cdot 16\ \text{bits}$ if dequantized fully at once), and full‑model optimizer states (if doing full finetuning).
- LoRA gradients memory depends on activations: computing gradients for LoRA requires inner products of per‑token inputs $X$ (size $b\cdot L\cdot h$) and output gradients, so LoRA gradient buffers and input gradients scale with $b\cdot L$ and $r$; the paper’s example shows LoRA input gradients dominated memory unless checkpointing was used.
- Savings summary: primary savings come from storing the huge base model at $4$ bits instead of $\mathrm{BF16}/\mathrm{FP32}$ (roughly $4\times$–$8\times$ reduction vs $\mathrm{BF16}/\mathrm{FP32}$ depending on base dtype), plus Double Quantization reduces the quantization‑constant overhead, and by only optimizing LoRA adapters you avoid having $O(P)$ optimizer state. The remaining dominant memory cost becomes activations (sequence dependent), which QLoRA mitigates by gradient checkpointing and Paged Optimizers to keep optimizer state off‑GPU when possible.

Concrete per‑layer formulas (compact):
- NF4 storage (persistent): $S_W = P\cdot 4\ \text{bits}$.
- Quant constants (after DQ, amortized): $S_c \approx P\cdot 0.127\ \text{bits}$ (paper’s numbers for $B=64$ and chosen second level).
- Dequantized compute weights (temporary $\mathrm{BF16}$): $S_{\mathrm{deq}} = P\cdot 16\ \text{bits}$ (may be done per‑chunk).
- Activations stored ($\mathrm{BF16}$) during forward: $S_{\mathrm{act}} = b\cdot L\cdot h\cdot 16\ \text{bits}$ (and activation gradients similar scale).
- LoRA params ($\mathrm{BF16}$): $S_{\mathrm{LoRA}} = (h\cdot r + r\cdot o)\cdot 16\ \text{bits}$ and LoRA optimizer states (e.g., $2\times$ moments) $\approx 2\cdot S_{\mathrm{LoRA}}$ (or more depending on optimizer), which can be paged.
- LoRA gradient/input gradient peak: scales $\propto b\cdot L\cdot h\cdot r$ (paper reported e.g. $567\ \text{MB}$ for $7\text{B}$ without checkpointing vs $18\ \text{MB}$ with checkpointing).

Practical implications
Implementations exploit the fact that you can dequantize per‑block or per‑tile so you often do not need to have the entire $P\cdot 16$ bits resident at once; instead you dequantize a chunk, multiply, and discard, further reducing peak memory. The paper’s CUDA kernels and the use of paging make the transient dequantized cost manageable. But conceptually, the dequantized $\mathrm{BF16}$ buffer is the compute representation and is the reason you cannot entirely avoid higher precision during training.

Conclusion
So, for a single transformer linear layer you keep a tiny $\mathrm{NF4}$ persistent store ($P\cdot 4\ \text{bits}$) plus tiny per‑block quantization constants (very small amortized bits/param after double quantization), you transiently dequantize to $\mathrm{BF16}$ for compute ($P\cdot 16\ \text{bits}$ if you materialize whole tensor, or less if tiled), you keep activations/activation gradients which scale with batch·seq_len, and you only maintain optimizer/gradient state for the small LoRA adapters (paged to CPU if needed). The memory savings come mainly from compressing the base model to $4$ bits and from avoiding full‑model optimizer states; the remaining peak is dominated by activations unless checkpointing and paging are used.
