\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### How do LoRA rank and scaling hyperparameters interact with placing adapters in every layer?
Question:
The paper states that the projection rank $r$ did not matter much, while putting LoRA in more places did. Is there a known regime where increasing $r$ within a layer materially helps once adapters are in every linear submodule? Conversely, can we reduce $r$ and still match 16-bit if we keep full coverage across layers? Any guidance on the trade-off curve between number of adapter locations and per-adapter rank to keep memory roughly constant?
Answer:
Short answer: The paper’s experiments show that covering more linear submodules with LoRA matters far more than increasing the per-adapter rank $r$. In practice you should first expand adapter coverage (put LoRA in every linear projection in each transformer block) and only increase $r$ if you still need capacity for a specific task or you can afford the extra memory. If you must hold total memory roughly constant, trade-offs are simple and roughly linear: doubling the number of adapter locations allows halving $r$ (and vice‑versa) because adapter parameter count scales linearly with both.

Why the paper reaches this conclusion (intuitive + technical)
The QLoRA paper reports that using LoRA only on the usual Q/V projections failed to recover full $16$-bit finetuning performance for large models, whereas adding adapters to every linear layer recovered performance. The intuitive reason is that different submodules (attention projections, feed‑forward projections, output projections, etc.) each provide distinct degrees of freedom the model uses to adapt; spreading small low‑rank updates across those different functional places is more effective than concentrating capacity in only a few places. Technically, a LoRA adapter for a linear map $XW$ uses an additive term $s X L_1 L_2$ where $L_1 \in \mathbb{R}^{h\times r},\ L_2 \in \mathbb{R}^{r\times o}$. The total extra parameters are proportional to $r$ times $(h+o)$ per adapter. So adding many adapters increases representational reach across the network, while increasing $r$ increases per‑location expressivity but cannot reassign capacity to locations where the model needs it.

When increasing $r$ still helps
There are regimes where raising $r$ inside each adapter can still be useful:

- If coverage is already full (adapters in all linear submodules) and the task requires richer per‑layer transformations (e.g., large domain shift, heavy structural changes, or tasks that need many new degrees of freedom), increasing $r$ can help. The paper’s core point is that for the instruction‑finetuning tasks they tried, coverage mattered more and modest $r$ values were enough to match $16$-bit.
- If you are operating under a strict limit on the number of adapter locations (for implementation or inference reasons) then increasing $r$ at those few locations is the only way to add capacity — then larger $r$ will matter.
- For much smaller models or very small layers (where activation gradient memory is small), the tradeoffs can change and per‑adapter $r$ could be more beneficial.

Can you reduce $r$ and still match $16$-bit if you keep full coverage?
Yes — that is exactly what the paper found in their experiments. Because the bulk of finetuning memory is activation gradients and not the LoRA parameter storage, you can afford many adapter locations with small $r$ and still hit the same memory envelope. In the QLoRA experiments, modest ranks (often small $r$) with adapters in every linear module recovered $16$-bit finetuning performance. The implication is that you often can reduce $r$ and keep full coverage without degrading performance for typical instruction‑tuning tasks.

Simple tradeoff bookkeeping (how to keep memory roughly constant)
Adapter parameter count scales approximately as $(\text{num\_locations}) \times r \times \text{hidden\_size}$ (ignoring small constants and output dims). So if you want to keep total adapter params approximately constant, you can set

$r_{\text{new}} = r_{\text{old}} \times \left(\dfrac{\text{num\_old\_locations}}{\text{num\_new\_locations}}\right).$

Example: if you ran with LoRA on only Q and V ( $\text{num\_old\_locations} = 2$ per block) with $r=32$, and now want adapters on every linear (say $\text{num\_new\_locations} = 8$ per block), then $r_{\text{new}} \approx 32 \times (2/8) = 8$ to keep the adapter parameter footprint similar. This linear relationship is the practical tradeoff the paper suggests: increase number of adapter sites first, then increase $r$ if needed.

Practical tuning guidance derived from QLoRA
1. Prioritize coverage: add adapters to all linear submodules in each transformer block before increasing $r$. The paper shows this is the most important hyperparameter for matching full finetuning.
2. Use modest $r$ values by default (e.g., $r \in \{4, 8, 16, 32\}$ depending on hidden size). In the authors’ experiments, increasing $r$ beyond typical small values had little effect once coverage was full.
3. Tune the scalar $s$ (the LoRA scaling) along with $r$. If you must reduce $r$, sometimes increasing $s$ can partially compensate (it scales the adapter contribution), so try $s$ in a small sweep (e.g., $0.1, 0.3, 1.0$) while keeping $r$ small.
4. If memory is the constraint, remember that LoRA parameter storage is small relative to activation gradients (the paper quantifies this). That means you can usually afford full coverage without blowing your memory budget; so don’t trim locations prematurely.
5. Only increase $r$ if (a) coverage is already full, (b) the task still underfits (validation loss or generation quality degrades), or (c) you cannot put adapters in more locations for some reason. Otherwise concentrate on coverage and simple tuning of learning rate and $s$.

Broader connection
This behavior mirrors a general ML principle: it is often better to distribute small amounts of adaptable capacity across many places in a deep model (so the network can reconfigure different computations) than to concentrate capacity in a few locations. QLoRA shows this concretely for LoRA on quantized large models: breadth (coverage) wins over depth (per‑adapter rank) for the instruction‑tuning workloads they studied.
