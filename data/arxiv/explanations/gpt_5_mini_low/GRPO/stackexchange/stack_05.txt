\title{Stack Exchange of the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

### What is the memory and compute trade-off when sampling G=64 outputs per prompt in GRPO?
Question:
You report using \(G=64\) samples per question with max length 1024 and a batch size of 1024 during RL. Could you detail the actual memory footprint compared to PPO with a separate value model of the same size? For example, is the total GPU memory lower when using GRPO at \(G=64\) versus PPO with \(G\) much smaller plus a critic? Also, do you reuse KV caches across the \(G\) samples for the same prompt, or otherwise amortize attention computation in practice?
Answer:
Short answer: GRPO trades off extra sampling compute/temporary activations (you pay $O(G)$ generation cost per prompt) for removing the separate value network (you save the memory and compute of an entire critic model). In practice that means GRPO with $G=64$ usually uses less steady-state GPU memory than PPO that keeps a same‑size critic, but it requires more total inference work (and transient KV/activation storage) unless you amortize generation over the shared prompt prefix. The paper does not publish exact per‑GPU bytes, nor does it state whether prompt KV caches were reused; below I explain the sources of memory and compute and what to expect.

Why GRPO is lower-memory than PPO
- The paper’s core point is that PPO typically trains a value function $V_\psi$ of comparable size to the policy (policy $\approx 7\text{B}$; typical value heads have comparable backbone), so PPO requires storing another large model’s parameters and its optimizer state and activations during training. That is a large, persistent memory cost. GRPO “foregoes the critic model” and instead uses the group average reward as the baseline, so you avoid storing the critic’s weights, optimizer buffers, and its activations — a big win for GPU memory footprint and for the peak memory needed while computing advantages and backpropagating through the value network.
- So for the same policy model size, GRPO removes the steady-state memory associated with the critic. In other words, peak memory for model parameters (policy + critic) in PPO > peak memory for policy-only GRPO.

Why GRPO costs more compute / transient memory with $G=64$
- GRPO samples $G$ outputs per prompt and scores them with the reward model. Generating $G$ continuations increases inference compute roughly linearly in $G$ (generation FLOPs), and increases transient memory used for (a) activations/logits for each generated sequence if you keep them in memory for later optimization steps, and (b) KV caches during autoregressive decoding while a sequence is being generated.
- The paper reports: $G=64$, max length $1024$, training batch size $1024$. That implies many generated sequences per training batch. If you naively generate all $G$ continuations for all batch prompts in parallel and keep everything resident, transient memory (KV caches + activation buffers + reward scores) can be very large. The paper’s claim is that GRPO “significantly reducing training resources compared to PPO” comes from eliminating the critic, but the authors do not publish the precise memory breakdown or peak numbers in bytes.

KV-cache reuse / amortization: what the paper says (and what it doesn’t)
- The paper does not explicitly state whether KV caches of the shared prompt prefix are reused across the $G$ samples for the same prompt. It only states that they sample $64$ outputs per question (section “Training and Evaluating DeepSeekMath-RL”) and reports batch size and max length.
- Reuse is a standard and important optimization in practice: when you generate multiple continuations for the same prompt, you can compute the prompt’s KV cache once and reuse it for each continuation, so you avoid re-computing attention over the prefix $G$ times. That reduces both compute and memory footprint significantly (you still need separate KV caches for the generated suffix tokens, but you amortize the prefix cost). The paper does not confirm whether they applied this optimization, so we cannot claim they did.

Putting it together: expected practical trade-offs
- Memory (steady-state): GRPO typically uses less steady GPU memory than PPO with a same-size critic because you remove another model’s parameters + optimizer states. That is the main “memory win” emphasized in the paper.
- Memory (transient/peak): GRPO can increase peak transient memory depending on how sampling is scheduled. If you generate many continuations concurrently and store all KV caches/activations, transient peak memory could approach or exceed PPO’s peak. But if you (a) reuse prompt KV caches, (b) generate continuations sequentially or in smaller inner micro‑batches, and (c) only keep minimal tensors required for computing losses (e.g., store logits and rewards but free activations), the transient peak can be controlled and remain below PPO+critic memory.
- Compute (total FLOPs): GRPO with $G=64$ multiplies generation work by $\approx 64$ relative to a single-sample policy. PPO with a smaller $G$ plus a critic pays the compute to run the critic (forward and backward) and to compute advantages using $G$ (if $G>1$), but typically GRPO’s total generation FLOPs will be larger when $G$ is large. The paper implicitly accepts this cost to avoid the critic memory cost and to exploit group‑based baseline estimation that matches reward-model comparisons.
- Training dynamics: The paper argues GRPO’s group baseline aligns well with comparative reward models and yields good sample efficiency for improving Maj@K, so the extra generation compute is compensated by more stable / effective updates in their experiments.

Practical recommendations (consistent with the paper)
- If your constraint is GPU memory (cannot fit a second model), GRPO ($G$ large) is attractive: you trade wall‑clock generation cost for substantially lower model‑parameter memory.
- If your constraint is total GPU time / throughput, you must measure whether the $G=64$ sampling overhead (including reward-model scoring and any stored activations) outweighs the cost of running a critic. In many setups the critic’s forward/backward cost is smaller than generating $64$ long continuations, so $G$ should be tuned with operational constraints.
- Implement prompt‑KV reuse: compute the prefix KV cache once per prompt and reuse it for each of the $G$ continuations. This is a standard, high‑impact optimization that reduces both compute and memory for GRPO sampling. Because the paper does not state whether they used it, if you reproduce their setup you should enable KV reuse and evaluate the peak memory and throughput.
- If transient memory becomes a bottleneck, generate continuations in micro‑batches (e.g., generate $4$–$8$ continuations at a time per prompt), free intermediate activations promptly, and store only what you need (logits/rewards) for the GRPO loss.

Summary
The paper’s practical message is: GRPO ($G=64$) reduces the persistent GPU memory cost relative to PPO with a separate value model by removing the critic, at the expense of increased generation work and potentially larger transient memory during sampling. Whether total GPU memory is “lower” in your setup depends on implementation details (especially whether you reuse prompt KV caches and whether you generate continuations concurrently). The paper does not specify KV-cache reuse, so you should assume they did not report that optimization and plan to apply it when reproducing/optimizing GRPO.
