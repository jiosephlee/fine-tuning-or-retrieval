\title{Stack Exchange of the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

### What evaluation protocol ensures fair comparisons on MATH with and without tools, including decoding settings?
Question:
Across Base, Instruct, and RL models, and against baselines, what exact decoding parameters (temperature, top-p, max tokens, stop criteria) and prompt formats were used for: (1) CoT without tools, (2) PoT with Python and libraries like sympy, and (3) self-consistency or vote count where applicable? For self-consistency, you report 64 samples for DeepSeekMath-7B; are the same sampling hyperparameters applied uniformly across models to avoid conflating model quality with decoding differences?
Answer:
Short answer: the paper evaluates MATH under two distinct prompting modes (chain-of-thought (CoT) without tools; program-of-thought (PoT) / tool-integrated with Python+libraries) and it uses sampling-based decoding for self-consistency / RL data collection. The paper gives some explicit decoding choices for the RL/sampling stage and otherwise describes the prompt formats and evaluation procedures, but it does not give a full, line-by-line list of temperature / top-p / stop-token settings for every evaluation. To make comparisons fair (and to avoid conflating model quality with decoding differences) you must therefore follow the explicit choices the paper gives and otherwise apply a single, uniform decoding protocol across all models and conditions.

What the paper states (explicitly and reproducibly)
- Prompt formats: evaluations use few-shot prompts in the corresponding style. For non-tool evaluation they use few-shot chain-of-thought (CoT) prompts; for tool evaluation they use few-shot program-of-thought (PoT) / tool-integrated prompts where the model is asked to produce a Python program and libraries like math and sympy are allowed. The program is executed and the execution result is taken as the final answer. These few-shot prompts are drawn from the SFT / PoT datasets used in training (see SFT Data Curation).
- Self-consistency and sampling used in RL/data collection: for GRPO training the paper samples $G = 64$ outputs per question, uses nucleus (top-p) sampling described as “a naive nucleus sampling”, sets the max generation length to $1024$ tokens during sampling, and the policy samples $64$ outputs per question for reward-model scoring. The RL training batch size and learning rates are reported alongside these sampling choices.
- Scoring / final-answer decision: for PoT with program execution the execution result is treated as the answer (so correctness is decided by running the generated code). For CoT (no tools) evaluation correctness is judged by parsing the model’s numeric/expressed answer. For self-consistency they report $\mathrm{Maj}@K$ / $\mathrm{Pass}@K$ style aggregate statistics (majority voting / top-k pass counts are discussed in the RL analysis).
- Important methodological point in the paper: the authors emphasize that RL (GRPO) used the same sampling strategy ($64$ samples, top-p nucleus sampling, max length $1024$) during its exploration phase; they attribute improvements in part to making the output distribution more robust (improved $\mathrm{Maj}@K$), so sampling hyperparameters materially affect measured accuracy.

What the paper does not fully specify (and therefore you should fix when re-running or comparing)
- Exact temperature and explicit top-p value used for the published CoT / PoT evaluations on benchmarks is not reported in the main text. The phrase “naive nucleus sampling” is used for RL exploration but no numeric top-p or temperature are listed for final benchmark decoding.
- Explicit stop tokens or fine-grained decoding cutoffs used when generating CoT reasoning traces for final evaluation (e.g., whether generation is stopped when an “Answer:” line appears) are not enumerated in the write-up.

Practical recommendation (to ensure fair comparisons and avoid conflation of model and decoding effects)
1) Use the prompt style reported in the paper exactly: few-shot CoT templates for no-tool runs; PoT / tool-integrated templates for program runs. Use the same few-shot exemplars across all models under test.
2) Use the paper’s explicit sampling choices where given: for sampling-based procedures (self-consistency, RL-like evaluations, reward sampling) sample $G = 64$ outputs per question, use nucleus (top-p) sampling, and set max generation length = $1024$ as done in the RL experiments. Apply those same choices uniformly to all models when you compare self-consistency / voting results.
3) If the paper does not specify temperature or the numeric top-p, pick and fix a single reasonable set of decoding hyperparameters and apply them to every model and condition. A minimal fair-protocol example consistent with the paper’s descriptions is: nucleus sampling (top-p), same top-p and temperature for all models, max tokens = $1024$ for sampling-based aggregation (and a smaller sensible max for deterministic eval if you prefer), and identical stop criteria (e.g., stop on a canonical “Answer:” delimiter or when the model emits a designated terminator). Crucially, whatever exact temperature/top-p you choose must be identical across models and evaluation modes when you compare aggregate metrics.
4) For PoT/tool evaluation, execute the generated Python and use the numerical execution output as the canonical answer; use identical execution environment (Python version and same library versions, e.g., sympy) across evaluations.
5) For self-consistency / majority-vote reporting, use the same number of samples per question and the same sampling hyperparameters for all models. The paper reports that DeepSeekMath-7B used $64$ samples for its “self-consistency” result; to avoid confounding you should apply $64$ samples to every model you compare (or run ablations that show accuracy vs. number of samples).

Why these choices matter (intuitive explanation)
Decoding knobs (temperature, top-p, number of samples, max tokens, stop logic) change the model’s output distribution and therefore both the diversity of generated reasoning traces and the majority-vote outcome. Self-consistency benefits from sampling diversity, so a larger sample count or higher-temperature / higher top-p can inflate $\mathrm{Maj}@K$ performance. Conversely, deterministic greedy decoding or low-temperature sampling reduces diversity and can reduce the measured benefit of voting. Thus fairness requires fixing decoding hyperparameters across all evaluated systems; the paper follows this principle for its RL sampling (explicitly $G=64$, nucleus sampling, max length $1024$) and stresses that RL’s gains show up most in $\mathrm{Maj}@K$ rather than $\mathrm{Pass}@K$, demonstrating the importance of consistent sampling.

If you need a concrete, fully reproducible protocol to implement now (recommended)
Adopt the paper’s prompt formats (CoT for no-tools; PoT for tool runs), and for all models use nucleus sampling with the same parameters and sample count. Specifically, for parity with the paper’s reported self-consistency run, use $G = 64$ sampled outputs per question, nucleus sampling, max gen length = $1024$, and the same fixed temperature/top-p pair for every model (e.g., $\text{temperature} = 0.7$, $\text{top-}p = 0.95$). Execute any generated Python with identical runtime/libraries and derive the final answer from execution output. Use majority voting to produce the self-consistency answer. Document these exact decoding hyperparameters alongside reported scores so readers can disambiguate model improvements from decoding differences.

Summary: the paper explicitly documents prompt formats (CoT vs PoT), that PoT answers are judged by executing generated Python (math, sympy allowed), and that GRPO/RL sampling used $64$ samples, nucleus sampling, and max length $1024$. It does not publish a complete set of numeric decoding hyperparameters for the benchmark evaluations, so to ensure fair comparisons you must fix and apply a uniform decoding protocol (same temperature, same top-p, same sample count, same max tokens, same stop rules) across all models and conditions; using $G = 64$, nucleus sampling, max length = $1024$ is directly grounded in the paper and is the safest choice for reproducing their self-consistency-style results.
