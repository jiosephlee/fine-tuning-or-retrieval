\title{A Textbook about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

Chapter 6: Producer–Consumer Asynchrony: Warp-Specialization and Ping-Pong Scheduling

# CTA view: tiles of Q (rows) and streaming K/V (columns) with circular SMEM buffer

At the level of a cooperative thread array (CTA), FlashAttention-3 partitions the computation so that each CTA is responsible for computing the attention output corresponding to a tile of query rows. Concretely, let the input query, key, and value matrices for a single head be $\mathbf{Q}, \mathbf{K}, \mathbf{V} \in \mathbb{R}^{N \times d}$, where $N$ is the sequence length and $d$ is the head dimension. We divide $\mathbf{Q}$ into $T_r = \lceil N / B_r \rceil$ row blocks $\{\mathbf{Q}_i\}_{i=1}^{T_r}$ of size $B_r \times d$. Each CTA operates on one such query block $\mathbf{Q}_i$ and produces the corresponding output block $\mathbf{O}_i \in \mathbb{R}^{B_r \times d}$.

Keys and values are processed streaming-wise in column blocks of size $B_c \times d$, yielding $T_c = \lceil N / B_c \rceil$ key/value tiles $\{\mathbf{K}_j, \mathbf{V}_j\}_{j=0}^{T_c-1}$. To avoid repeatedly reading and writing these tiles to high-latency global memory (HBM), FlashAttention-3 uses a circular shared-memory (SMEM) buffer with $s$ stages. The buffer provides a small number of stages that the producer warps fill with successive $\mathbf{K}_j$ and $\mathbf{V}_j$ tiles and that consumer warps drain as they compute partial contributions to $\mathbf{O}_i$ for the current $\mathbf{Q}_i$ block. The circularity of the buffer lets producer and consumer proceed in a pipelined fashion: while consumers are computing on stage $t$ of the buffer, producers can be filling stage $t+s$, subject to synchronization that ensures data races do not occur.

This CTA-level tiling aligns naturally with the mathematical structure of attention, which can be written as the two-stage computation $\mathbf{S} = \alpha \mathbf{Q}\mathbf{K}^\top$, $\mathbf{P}=\mathrm{softmax}(\mathbf{S})$, and $\mathbf{O}=\mathbf{P}\mathbf{V}$. Each consumer CTA iterates over the streamed key/value tiles and accumulates contributions to $\mathbf{O}_i$ by computing blockwise matrix multiplications between its local $\mathbf{Q}_i$ and the resident $\mathbf{K}_j$ or $\mathbf{V}_j$ tiles in SMEM. The circular SMEM buffer decouples the rate at which tiles are loaded from global memory from the rate at which they are consumed, permitting overlap between copy and compute when the hardware supports asynchronous memory movement.

# Producer warpgroup: TMA loads for Q, then pipelined K/V blocks

Within the CTA, FlashAttention-3 divides warps into producer and consumer warpgroups. Producer warps are specialized to move data from global memory into shared memory and to perform any necessary in-kernel layout transforms (for FP8, for example). The key hardware primitive used for producer warps is the Tensor Memory Accelerator (TMA), which performs asynchronous, high-throughput transfers between HBM and SMEM. Producers first issue a TMA load for the CTA's $\mathbf{Q}_i$ tile; once that load is committed, they pipeline TMA loads of successive $\mathbf{K}_j$ and $\mathbf{V}_j$ tiles, placing each pair into the next stage of the circular SMEM buffer.

Because TMA is asynchronous, producer warpgroups do not have to wait for a transfer to complete before issuing the next TMA for another tile. Instead, the producer uses barrier-like commit notifications: after a TMA completes for a stage, it "commits" that stage to signal consumers that the tile is ready. The circular buffer has the invariant that producers wait for a stage's consumption before overwriting it, ensuring correctness. This ping-pong of filling and releasing stages avoids redundant global memory accesses and keeps SMEM contents localized to the working set of the CTA.

The producer warps are also register-light relative to consumer warps, so FlashAttention-3 reassigns register budget between producer and consumer groups using the architecture's ability to reallocate registers (e.g., via setmaxnreg). This lets the producer warps execute TMA and potential transpose kernels (for FP8 layout conformance) using minimal registers while giving consumer warps larger register files for compute-intensive work on Tensor Cores.

# Consumer warpgroup: WGMMA for QK^T and PV with local softmax rescaling

Consumer warpgroups are specialized for compute: they perform the blockwise matrix multiplications using the asynchronous warpgroup-wide MMA instruction (WGMMA) to leverage Tensor Cores. The consumer main loop operates over $j=0,\dots,T_c-1$ and for each stage performs two kinds of GEMM-like work: first, the "SS-GEMM" computing $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^\top$ (where SS indicates the source placement of operands, typically shared memory and registers), and second, the "RS-GEMM" accumulating the partial output $\mathbf{O}_i \mathrel{+}= \widetilde{\mathbf{P}}_i^{(j)} \mathbf{V}_j$ after computing the local softmax block $\widetilde{\mathbf{P}}_i^{(j)}$.

To avoid materializing full $N\times N$ intermediate matrices, FlashAttention-3 maintains the softmax reduction locally following the fused local-softmax idea from FlashAttention. Each consumer initializes running per-row quantities $m_i$ and $\ell_i$ that track the rowwise maximum and the running sum of exponentials in a numerically stable manner. After computing $\mathbf{S}_i^{(j)}$, the consumer computes the per-row maximum of $\mathbf{S}_i^{(j)}$, updates $m_i$ (taking the maximum across the accumulated and current block maxima), and forms the scaled exponentials $\widetilde{\mathbf{P}}_i^{(j)} = \exp(\mathbf{S}_i^{(j)} - m_i)$, updating $\ell_i$ accordingly. These operations include non-GEMM instructions such as exponentials and row-wise reductions.

Once $\widetilde{\mathbf{P}}_i^{(j)}$ is available, the consumer issues another WGMMA to multiply it with $\mathbf{V}_j$ and accumulate into the register-resident $\mathbf{O}_i$. Crucially, FlashAttention-3 keeps the rescaling of partial outputs consistent with the numerically stable recurrence: after updating $m_i$, previously accumulated $\mathbf{O}_i$ is rescaled appropriately before adding the new contribution. Both GEMMs are implemented with WGMMA, exposing them as asynchronous compute operations relative to other CTA activity.

By maintaining these running reductions and embracing per-block processing, the consumer warps avoid expensive global memory reads/writes of $\mathbf{S}$ and $\mathbf{P}$, keeping most activity on-chip in registers and SMEM and using WGMMA to achieve high Tensor Core throughput.

# Ping-pong scheduling with barriers: staggering GEMM0 and GEMM1 across warpgroups

A central mechanism in FlashAttention-3 for exploiting asynchrony is ping-pong scheduling across multiple consumer warpgroups. The observation is that the softmax-related operations (rowwise maxima, exponentials, and reductions) are relatively slow on the multi-function units (MFUs) compared to the very high throughput of Tensor Core GEMMs. To hide the latency of softmax, FlashAttention-3 staggers GEMM invocations across two (or more) consumer warpgroups so that while one group is executing softmax on its current block, another group is performing Tensor Core GEMMs on the next block.

The implementation uses explicit synchronization barriers (e.g., bar.sync) to orchestrate this staggering. The barriers enforce an interleaving such that GEMM0 (the $\mathbf{Q}\mathbf{K}^\top$ WGMMA for block $j$) and GEMM1 (the $\widetilde{\mathbf{P}}\mathbf{V}$ WGMMA for block $j-1$) from different warpgroups are ordered so that the Tensor Core engines see a steady stream of GEMM work. This is the ping-pong: warpgroup A issues GEMM0 and GEMM1 for its iteration, then performs softmax; concurrently, warpgroup B, having been released by the barrier, issues its GEMM0 and GEMM1 for the next iteration while A's softmax executes. The two warpgroups then swap roles on the next iteration.

Because WGMMA and TMA are asynchronous, producers and consumers can overlap copying and compute across the circular buffer stages, and ping-pong scheduling leverages this to keep Tensor Cores busy even when some warpgroups are executing MFU-bound code. The barriers ensure correctness by serializing the minimal required dependencies while permitting the desired overlap. Practically, this scheme improves measured Tensor Core utilization, e.g., raising forward-pass FP16 throughput from around 570 TFLOPs to the 620–640 TFLOPs range in the paper's experiments for certain parameter settings.

# Throughput intuition: MFU exponentials vs Tensor Cores and why overlap helps

Understanding why ping-pong scheduling yields performance gains comes from contrasting the relative throughputs of the hardware units responsible for the different parts of attention. Tensor Cores provide enormous throughput for matrix multiply-accumulate operations: on Hopper H100, Tensor Cores support very high TFLOPs rates in FP16 and even higher in FP8. In contrast, special-function units that compute exponentials, division, and other non-GEMM primitives operate at orders-of-magnitude lower arithmetic throughput.

A single attention iteration comprises a mixture of these operation types. For head dimension and block sizes typical in practice, the total number of floating-point operations performed by GEMMs dwarfs the FLOP count of exponentials and reductions. However, because exponentials are handled by a distinct, lower-throughput unit, they can become a bottleneck unless their latency is masked. If a single warpgroup performed all operations in strict sequence, the Tensor Cores would be idle during the time the MFU spends on exponentials and reductions. The ping-pong approach avoids that idle time by deliberately scheduling different warpgroups such that MFU-bound operations run concurrently with Tensor Core GEMMs from other warpgroups.

From a resources perspective, ping-pong scheduling aims to convert otherwise serial dependency chains into overlapped pipelines that exploit hardware parallelism. The circular SMEM buffer and asynchronous TMA allow the producer to keep supplying tiles, and reassigning registers among warpgroups gives consumer warps the register headroom to launch large WGMMA ops. Together, these ensure that the faster Tensor Cores have a sustained supply of GEMM work even when some warpgroups execute softmax-related instructions that would otherwise stall progress.

# Applying to MQA/GQA by indexing without duplicating K/V

FlashAttention-3's CTA-tiling and streaming approach extends naturally to multi-query attention (MQA) and grouped-query attention (GQA) variants without duplicating the global key and value tensors in memory. In MQA and GQA, queries may be partitioned or grouped differently across heads relative to keys and values, but the key observation is that $\mathbf{K}$ and $\mathbf{V}$ are shared structures that can be streamed through the same circular SMEM buffer and consumed by multiple CTAs.

Practically, FlashAttention-3 handles these variants by adjusting tensor indexing when issuing TMA loads and when selecting tiles for the WGMMA computations. Rather than materializing separate copies of $\mathbf{K}$ and $\mathbf{V}$ per query group, the producer warps load the canonical $\mathbf{K}_j$ and $\mathbf{V}_j$ tiles into SMEM, and consumer warps use logical indexing offsets to pick the appropriate rows/columns corresponding to their particular query grouping. Because the algorithm works blockwise and relies on local softmax rescaling, these index adjustments are sufficient to preserve correctness and avoid memory duplication. The same ping-pong and warp-specialization machinery operates unchanged: producers stream shared $\mathbf{K}/\mathbf{V}$ tiles, and consumers (specialized per CTA/query block) perform WGMMA and softmax reductions with local bookkeeping.

In summary, by structuring attention as a CTA-local computation on $\mathbf{Q}$ tiles with streamed $\mathbf{K}/\mathbf{V}$ tiles in a circular SMEM buffer, and by assigning producer and consumer roles to distinct warpgroups that exploit TMA and WGMMA asynchronously, FlashAttention-3 achieves a pipelined execution that overlaps slow softmax work with fast Tensor Core GEMMs. Ping-pong scheduling across warpgroups ensures Tensor Core utilization remains high, while the architectural choices for buffer stages and register allocation make the scheme practical and compatible with MQA/GQA indexing patterns.
