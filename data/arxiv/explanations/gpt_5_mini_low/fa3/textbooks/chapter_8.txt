\title{A Textbook about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

Chapter 8: FP8 FlashAttention-3: Layouts, Transposes, and Operand Conformance

# FP8 WGMMA k-major constraint vs typical head-major tensors
When targeting the FP8 Tensor Cores via the WGMMA instruction on Hopper, attention implementations encounter an important constraint: FP8 WGMMA accepts only k-major formatted input operands in shared memory. Concretely, if we consider a GEMM of the form $A \times B^\top$ where $A$ is $M\times K$ and $B$ is $N\times K$, an operand is called k-major when it is contiguous along the inner, $K$ dimension. For FP16 WGMMA the hardware accepts either mn-major or k-major layouts in SMEM; for FP8 WGMMA only k-major SMEM operands are supported. This difference has practical consequences for attention, because the typical memory layout used by Transformer implementations stores token-major (sequence length) or head-major contiguous strides rather than the k-major stride assumption required by FP8 WGMMA.

In the attention forward pass we commonly multiply $\mathbf{P}\in\mathbb{R}^{B_r\times B_c}$ (a block of softmax scores) by $\mathbf{V}_j\in\mathbb{R}^{B_c\times d}$ to accumulate into an output tile of shape $B_r\times d$. When invoking FP8 WGMMA for this RS-GEMM, the hardware expects the operand corresponding to $B$ (here, the $\mathbf{V}_j$ tile) loaded in SMEM to be laid out k-major: contiguous across the $K$ dimension that WGMMA interprets as the reduction dimension. Typical attention tensors, however, are contiguous in the head (feature) dimension $d$ (so within each token the features are contiguous), which makes tiles of $\mathbf{V}$ contiguous along the token (sequence) axis after standard loading. This mismatch means a straightforward copy of $\mathbf{V}$ into SMEM via TMA will not produce the k-major layout FP8 WGMMA requires.

Because WGMMA is the high-throughput primitive we want to use to obtain the 2x throughput benefit of FP8 on Hopper, the layout constraint cannot be ignored. Any FP8-aware attention algorithm must therefore ensure that the tiles provided to FP8 WGMMA are in k-major order in SMEM. The rest of the chapter explains why naive remedies are undesirable and how FlashAttention-3 addresses this with in-kernel transposes and register-level accumulator reformatting while keeping the fused kernel and high arithmetic intensity.

# Why pre-transpose in GMEM is undesirable for bandwidth-limited workloads
A natural approach to resolving the layout mismatch would be to transpose the global-memory (GMEM) representation of $\mathbf{V}$ ahead of the attention kernel so that TMA loads will already fetch k-major tiles. While conceptually simple, pre-transposing $\mathbf{V}$ in GMEM is problematic for the workloads that motivate FlashAttention-3 because these workloads are memory-bandwidth-limited at the edges.

There are two ways to do pre-transpose in GMEM: (1) fuse the transpose into a preceding operation (for example, fuse the transpose into the epilogue of rotary embedding), or (2) run an explicit, standalone transpose kernel as a preprocessing step. Both have downsides in practice. Fusing the transpose into an earlier operation (1) is hard to adopt in general-purpose libraries: it requires modifying upstream kernels or the model graph to emit data in a different stride layout, which complicates integration with standard frameworks and existing fused kernels. Running a separate transpose kernel (2) moves data in global memory and adds an extra global memory write and read for $\mathbf{V}$. In memory-bound scenarios (inference or long-context attention where the data movement is already the bottleneck), adding extra GMEM traffic is expensive and can dominate runtime. Even optimized transpose kernels that approach the device bandwidth still cost a full extra pass over the data, which we want to avoid.

FlashAttention-3 therefore avoids pre-transposing $\mathbf{V}$ in GMEM. Instead, it performs a transpose in-kernel after the TMA load and before feeding the FP8 WGMMA. This keeps the number of GMEM reads and writes minimal (the attention kernel continues to be a single fused kernel with no extra global writes), and uses on-chip resources and lower-latency instructions to implement the necessary layout change. The remainder of the chapter describes the concrete instructions and scheduling that enable an efficient in-kernel transpose with minimal register pressure and hidden latency.

# In-kernel transpose of V tiles using LDSM/STSM (ldmatrix/stmatrix) with packed bytes
To implement an in-kernel transpose of $\mathbf{V}$ tiles efficiently, FlashAttention-3 uses the LDSM and STSM primitives (exposed as PTX ldmatrix and stmatrix). These instructions move data between shared memory (SMEM) and the register file (RMEM) at a fine-grained tile granularity (the PTX documentation describes them as copying $8\times 8$ matrices of 16-bit entries), and they are register-efficient: a warp of threads cooperatively executes them to load or store small tiles.

For FP8, entries are 8-bit. FlashAttention-3 packs pairs of FP8 bytes into the 16-bit lanes that LDSM/STSM expect, allowing these instructions to be reused for an 8-bit transpose operation. The high-level pattern is: after TMA loads a $\mathbf{V}$ tile into SMEM in the natural head-major layout, a producer warpgroup issues a sequence of LDSM operations to pull packed 16-bit words into RMEM, then performs the necessary register-level reorganization and finally issues STSM operations to write the transposed tile back into SMEM in the k-major layout expected by the subsequent FP8 WGMMA. Because LDSM and STSM are warp-cooperative and operate on 128-byte chunks, they are efficient and compact in register usage.

There are a couple of practical details to note. First, LDSM/STSM as documented cannot split the packed 8-bit entries inside a 16-bit lane when performing the transpose; this necessitates small register manipulations between LDSM and STSM to permute bytes appropriately. Second, the packing implies that the planner must ensure correct alignment and tile sizes so that the LDSM/STSM semantics line up with the logical $B_c\times d$ tile shapes used by the attention loop. Nevertheless, these limitations are manageable and the approach avoids additional GMEM traffic while producing the k-major SMEM layout required by FP8 WGMMA.

# Scheduling the V transpose under GEMM shadow to hide its cost
Although LDSM/STSM and the small register permutations are inexpensive relative to global memory accesses, they still consume cycles and some on-chip resources. To minimize their impact on throughput, FlashAttention-3 schedules the in-kernel $\mathbf{V}$ transpose to run in the latency shadow of high-throughput GEMMs: while one warpgroup executes WGMMA instructions, another warpgroup issues the LDSM/STSM sequence to transpose the upcoming $\mathbf{V}$ tile.

Warp-specialization combined with the TMA/WGMMA asynchrony makes this possible. The algorithm splits the CTAs into producer and consumer warpgroups and uses the circular SMEM buffer to stage tiles. After the producer issues a TMA load that places a naturally laid-out $\mathbf{V}_j$ tile into its SMEM staging slot, the producer warpgroup executes the LDSM/STSM-based transpose of that tile, writing the k-major result into a different stage of SMEM. This transpose can be scheduled so that it overlaps with the consumer warpgroup's WGMMA operations: because WGMMA and TMA are asynchronous, the warp that performs the transpose need not wait for the consumer's GEMM to complete and vice versa. In practice, FlashAttention-3 arranges for the transpose of the next $\mathbf{V}$ tile to be executed “in the shadow” of the two WGMMAs that use the preceding $\mathbf{V}$ and the current $\mathbf{K}$ tile.

This shadow scheduling hides most of the transpose latency. The result is that the attention kernel remains effectively fused from the perspective of GMEM traffic (no extra global writes), and the additional on-chip data movement and register permutations do not materially reduce WGMMA utilization when the schedule is balanced. The circular buffer and synchronization (barriers and commit notifications) guarantee correctness: producers commit that a stage is available only after the transpose has finished, and consumers wait for that commit before invoking FP8 WGMMA on the transposed tile.

# FP8 accumulator vs operand layout mismatch and byte-permute solution
Another practical complication arises from the difference in how FP8 WGMMA expects the layout of its FP32 accumulator versus how the previous FP8 WGMMA's accumulator is organized when held in registers. When chaining back-to-back WGMMAs inside a fused kernel—common in attention where we first compute score blocks and then multiply the produced $\widetilde{\mathbf{P}}$ tiles by $\mathbf{V}$—the logical register order produced by the first WGMMA's FP32 accumulator does not always match the operand layout the second WGMMA expects for its input held in registers.

FlashAttention-3 resolves this mismatch with targeted byte-permute register operations that reorder the accumulator contents into the layout acceptable for the subsequent WGMMA. The paper gives a concrete example: one changes the register-level byte order within 8-byte groups from the original sequence to the permuted sequence
\{ d0 d1 d4 d5 d2 d3 d6 d7 \} (replicated over every 8 bytes). This permutation effectively remaps column positions of the logically stored $\mathbf{P}$ tile. Implementing such a permutation uses compact byte-permute instructions available on the hardware and is register-efficient compared to rewriting data through shared memory or performing cross-thread shuffles.

By applying this byte-permute to the FP32 accumulator registers after the first WGMMA, we obtain a register layout that the second FP8 WGMMA will interpret correctly as its operand A or B (depending on the chaining direction). This avoids expensive shared-memory transposes or inter-thread communication. Importantly, because the byte-permute is local to registers, it can be executed quickly and scheduled to overlap with other producer-side activities, preserving the kernel's high arithmetic throughput.

# Coordinating P-tile column permutation with V-tile row permutation for correctness
The register-level permutation applied to make the first WGMMA's accumulator compatible with the second WGMMA has logical implications on the arrangement of matrix indices: permuting the bytes in the accumulator is equivalent to permuting columns of the logical $\mathbf{P}$ tile. For the chained GEMM to produce mathematically correct results, any column permutation applied to the $\mathbf{P}$ tile must be matched by a corresponding row permutation of the $\mathbf{V}$ tile passed into the second GEMM. In other words, if the accumulator permutation reorders $\mathbf{P}$'s columns, the transpose or in-kernel re-layout of $\mathbf{V}$ must produce a row permutation that mirrors that column permutation so that the matrix product $\mathbf{P}\mathbf{V}$ remains correct.

FlashAttention-3 coordinates these two permutations explicitly. The in-kernel transpose of $\mathbf{V}$ using LDSM/STSM is implemented so that the written k-major $\mathbf{V}$ tile not only changes the contiguous stride, but also applies the row permutation that matches the earlier register byte-permute of the $\mathbf{P}$ accumulator. The flexibility afforded by performing the $\mathbf{V}$ transpose in-kernel (rather than relying on global pre-transpose) permits this alignment: the producer warpgroup can place bytes into SMEM in the permuted row order required by the consumer warpgroup's register permutation.

This coordination eliminates the need for shuffles across threads or additional correction steps in the matmul sequence. In aggregate, the approach ensures correctness of the numerical computation while enabling the use of FP8 WGMMA with its k-major requirement and the fused, high-throughput execution model of FlashAttention-3. The synchronization primitives around the circular SMEM buffer ensure that the consumer only triggers the FP8 WGMMA once both the $\mathbf{V}$ tile has been transposed into the correct k-major plus row-permuted layout and the producer has committed that the stage is ready.

Taken together, these engineering choices—preferring in-kernel transpose over GMEM preprocessing, implementing tiled LDSM/STSM-based transposes with packed bytes, hiding transpose latency under WGMMA shadow execution, applying register-level byte-permute accumulator reformatting, and coordinating the complementary $\mathbf{P}$ column and $\mathbf{V}$ row permutations—allow FlashAttention-3 to exploit FP8 Tensor Cores without breaking the fused attention kernel. The net effect in practice is a large increase in measured TFLOPs/s for FP8 (approaching the H100 FP8 throughput ceiling) while keeping numerical correctness and enabling the additional accuracy mitigations (block quantization and incoherent processing) described elsewhere in the paper.
