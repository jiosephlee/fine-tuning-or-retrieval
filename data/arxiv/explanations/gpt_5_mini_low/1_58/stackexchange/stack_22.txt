\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### What are the implications for MoE routing and communication with 1.58-bit weights?
Question:
The paper argues MoE becomes more deployable due to reduced memory and activation transfer costs. In a concrete MoE setup (e.g., top-2 gating with N experts), how would you quantize and transmit activations and expert weights? Are gating logits/dispatch indices also quantized, and does quantization affect load balancing or expert specialization?
Answer:
Short answer: use the paper’s $1.58$-bit recipe for expert weights (ternary $\{-1,0,1\}$) and $8$-bit per-token activations as the default on-the-wire representation; keep gating computation either in slightly higher precision ($FP16/BF16$) or carefully quantized ($int8$ with scale) so top-2 decisions stay stable; send compact dispatch indices (small integers/bitmasks) and per-token scale factors alongside the $int8$ activations. With these choices you get large communication savings and usually only mild effects on load balancing or specialization — but you should treat gating logits with care because quantization noise can flip near-ties and so shift expert loads or specialization patterns.

Why — intuition and practical pipeline
The paper’s core quantization choices are: weights are ternary $\{-1,0,1\}$ and activations are $8$-bit, scaled per token to a symmetric range $[-Q_b, Q_b]$. That immediately implies two useful properties for MoE: expert weight storage is very small and activations to be routed are tiny compared to $FP16$, so the dominant network cost (sending token activations from router to selected experts) is reduced by roughly the ratio of bit-widths.

A practical MoE dispatch pipeline consistent with the paper is:

1. Gating: compute gating logits from the (possibly quantized) pre-attention token representation. To avoid destabilizing top-2 selection, compute gating in $FP16/BF16$ if possible. If you must quantize gating, do it as $int8$ with a known scale per token (or per batch) and perform softmax in higher precision (or with dequantized accumulation). The reason is that top-2 selection is sensitive to small differences in logits: quantization noise can change who wins when logits are close.

2. Top-2 selection & indices: select two experts per token using the gating logits. Transmit compact dispatch metadata: an expert ID pair and small integer slots (capacity index) per token. These are naturally small ($\log_2(N)$ bits per expert ID plus some bits for capacity slot) and should be sent in integer form (no need for FP).

3. Activation transmission: send the token activation vectors to the selected experts as $8$-bit signed integers (the paper’s activation scheme: per-token symmetric scaling to $[-Q_b, Q_b]$). Also send the per-token scale factor (a small $FP16$ or even $FP8$ scalar) so the receiving expert can dequantize or compute in integer arithmetic using that scale. Because each token goes to two experts in top-2 routing, you either send two copies or use a multicast if network supports it.

4. Expert computation: experts hold ternary weights $\{-1,0,1\}$ so matrix multiplies can be implemented as additions/subtractions and masked accumulations. Experts can multiply the $int8$ activations by ternary weights in integer arithmetic; if you preserve the per-token scale, you can carry out integer accumulation and then multiply by the scale at the end (or keep everything quantized through activation outputs if downstream supports it).

5. Return/merge: experts return their outputs as $8$-bit activations plus scales (or accumulate locally and send back a dequantized $FP16$ result if merging requires higher precision). The router merges the two expert responses (weighted by gating probabilities) — merging is safer if done in $FP16/BF16$ or using dequantized accumulators to avoid precision loss when combining many tokens/experts.

Does one quantize gating logits / dispatch indices?
Dispatch indices are integer by nature and should be transmitted as small integers or bitmasks; there is no benefit to representing them in FP. Gating logits, however, are sensitive and benefit from higher precision. The paper does not explicitly prescribe gating precision for MoE, but given it keeps activations at $8$-bit while weights are ternary, the conservative and practical choice is to compute gating logits in $FP16/BF16$ (or compute in $int8$ but do softmax in $FP16$ after dequantizing). This avoids flipping top-2 selections due to quantization noise.

How quantization affects load balancing and expert specialization
Quantization can affect routing in two ways. First, it changes the inputs the gate sees (if gating uses quantized activations), and second, it can introduce numerical noise in the softmax/logit comparisons. In practice:

- If gating is computed in $FP16/BF16$ and only the routed activations are quantized to $int8$ for transmission, load balancing is almost unchanged: the gate makes the same expert choices and expert specialization is preserved because experts still see essentially the same logical input (dequantized or scaled $int8$).

- If gating itself is aggressively quantized (e.g., low-bit logits without careful scaling), small differences near decision boundaries can flip top-2 winners. That will change the empirical expert load balance and can gradually alter expert specialization during any online or continual learning scenario. Even in pure inference, repeated flips change which data each expert sees and so could change how the system behaves from run to run (if random tie-breaking differs).

Mitigations and practical tips
If you want maximal communication savings while keeping routing stable, the simplest reliable recipe is: keep gating in $FP16/BF16$; transmit activations as $int8$ with a per-token symmetric scale; keep weights ternary on the expert side; return outputs as $int8$ (with scale) and perform the weighted merge in $FP16$ after dequantizing or with integer accumulation plus scaling. If you need to quantize gating too (for extreme edge deployments), calibrate the gating quantization scales on representative data, increase the softmax temperature slightly to reduce sensitivity to tiny numeric perturbations, and add or retain a small load-balancing regularizer (capacity factor or auxiliary loss) so that noisy flips don’t create pathological imbalances.

Bandwidth and memory impact (back-of-envelope)
Replacing $FP16$ activations with $8$-bit activations cuts activation bandwidth by ~2x. Replacing expert weights with ternary storage gives an even larger drop in DRAM bandwidth and device memory. For a top-2 router you still send two activation vectors per token, so per-token network bytes = $2 \times D \times 8$ bits (plus scale and indices), where $D$ is token hidden dimension. If you can compress scales to $FP16$ and indices to a few bits, the additional overhead is negligible compared to the activations themselves.

In short: the paper’s $1.58$-bit design naturally translates to MoE by keeping expert weights ternary and routed activations as $8$-bit (with per-token scales). Treat gating with higher precision or carefully quantized $int8$ with calibration to avoid destabilizing top-2 choices. Doing so yields large reductions in memory and communication with only modest risk to load balancing and specialization, and any residual risks can be addressed by calibration, temperature tuning, or lightweight load-balancing regularizers.
