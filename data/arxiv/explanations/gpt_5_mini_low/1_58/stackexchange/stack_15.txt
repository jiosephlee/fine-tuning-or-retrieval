\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### Throughput results on two A100s: what parallelism and KV-cache sharding were used?
Question:
For the 70B throughput experiment on two 80GB A100 GPUs, you mention pipeline parallelism. Were tensor-parallel or sequence-parallel techniques also used? How was the KV cache partitioned across devices? Since b1.58 supports much larger batch sizes, is the 8.9× throughput gain limited by interconnect bandwidth, kernel launch overheads, or compute? More details would help understand bottlenecks.
Answer:
Short answer: the paper states only pipeline parallelism was used for the $70\text{B}$ / two‑A100 throughput experiment; it does not report using tensor‑parallel (TP) or sequence‑parallel (SP) techniques, nor does it give an explicit scheme for KV cache sharding. The reported $8.9\times$ throughput advantage is attributed in the paper to the much smaller weight/activation footprint (and the optimized $2$-bit / $\text{INT}$ kernels) which allow much larger batch sizes; whether the residual limit is interconnect, kernel overhead, or compute is not measured in the paper, but I will explain the likely contributors and how you would verify them.

What the paper explicitly says and implies
The text in the Throughput paragraph says: “we compare ... on two $80\text{GB}$ A100 cards, using pipeline parallelism so that LLaMA LLM $70\text{B}$ could be run on the devices. We increased the batch size until the GPU memory limit was reached, with sequence length $512$.” They also state they measured latency with FasterTransformer and used a $2$-bit kernel for BitNet b1.58. From that text you can reliably conclude they used pipeline parallelism only, and that the throughput test exploited BitNet’s much smaller memory footprint to raise batch size (they explicitly say BitNet supports up to $11\times$ the batch size of the $\text{FP16}$ baseline, yielding $8.9\times$ throughput).

What the paper does not report
The paper does not say it used tensor parallelism, sequence parallelism, or any explicit KV‑cache sharding strategy. It also does not present microprofiling (e.g., device utilization, NVLink traffic, kernel timelines) to identify whether the final bottleneck for the $8.9\times$ gain is interconnect bandwidth, kernel launch overheads, or raw compute.

Why BitNet b1.58 gets large gains (intuitive + technical)
The dominant effects described in the paper are (1) much smaller weight and activation memory (weights are ternary, activations quantized to $8$-bit in their setup and measured with a $2$-bit kernel) and (2) lower arithmetic cost for the heavy nn.Linear ops ($\text{INT}$ additions rather than $\text{FP16}$ multiply‑adds). These two facts let you increase batch size until GPU memory is the limiting factor; larger batch size raises arithmetic intensity and amortizes kernel launch/overhead, so end‑to‑end throughput climbs steeply. The paper explicitly ties throughput gains to the reduced nn.Linear cost as model size grows.

Which resource is likely limiting in that two‑A100 experiment
With only the information in the paper, the most plausible explanation is that the speedup is primarily due to reduced memory footprint and cheaper compute (so the run is more compute‑efficient and allows larger batches). For two GPUs with pipeline parallelism:

- If the test is memory‑bound (they increased batch until memory limit), then BitNet’s smaller activation/weight memory is the key enabler of larger batch sizes and thus higher throughput. That is what they report.
- If communication (NVLink) were the bottleneck, you would expect increasing batch size to provide diminishing returns because pipeline stage swaps would still push activation/KV across the link each step; the paper’s claim that batch size scaled by $11\times$ and throughput by $8.9\times$ suggests communications did not dominate to the point of negating the benefit. But the paper does not measure NVLink traffic, so this is an inference, not a measured fact.
- Kernel launch overheads matter for small batches and short sequences. Because they explicitly increased batch to fill memory, the runs that produced the reported throughput are likely in the regime where kernel overheads are amortized; thus kernel launch overhead is unlikely the main limiter for the reported $8.9\times$ number.
- Compute cost (per token FLOP / type of arithmetic) certainly helps BitNet. FasterTransformer + $2$-bit kernels and $\text{INT}$ arithmetic reduce wall‑clock for matrix multiplies, so compute reduction is a real contributor. The paper emphasizes that nn.Linear time grows with model size and BitNet reduces that cost.

What you would need to prove which bottleneck dominates
To move from plausible reasoning to a firm attribution (interconnect vs kernel overhead vs compute) you need microprofiling that the paper doesn’t provide: GPU utilization, per‑kernel timing and occupancy, NVLink PCIe/NVSwitch traffic and stalls, and a breakdown of time spent in communication versus GEMM kernels. Suggested experiments: run the same model with pinned batch sizes while collecting Nsight Compute timelines or nvprof traces; compare single‑GPU (if possible) versus two‑GPU pipeline runs; measure NVLink bandwidth usage and per‑stage idle times; and try disabling the $2$-bit kernel (or replacing with a $\text{FP16}$ baseline kernel) to isolate kernel speedup from memory effects.

Short practical summary
From the paper: they used only pipeline parallelism; no explicit TP/SP or KV sharding is reported. The $8.9\times$ gain is presented as arising from (a) much smaller memory footprint allowing much larger batch sizes, and (b) faster low‑bit kernels and cheaper arithmetic in nn.Linear. The paper does not provide low‑level profiling, so it does not pin down whether remaining limits are interconnect bandwidth, kernel launch overheads, or compute; the most likely dominant factors are memory footprint enablement and cheaper compute, with communication and kernel launch overheads secondary in the reported (large‑batch) experiments.
