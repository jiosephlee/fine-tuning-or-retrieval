\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### What evaluation settings were used for latency per output token?
Question:
The paper reports time per output token using FasterTransformer. Could you specify the full inference configuration: batch size(s), context length, use of KV cache, attention implementation, GPU model and clock settings, tensor parallelism, and whether pinned memory/async prefetch was used? Since time/token depends heavily on these, a detailed setup would help reproduce the reported 2.4–4.1× speedups.
Answer:
Short answer: the paper only specifies a few pieces of the inference setup explicitly (FasterTransformer, the Ladder $2$-bit kernel, and that throughput for the $70$B run used two $80$GB A100s with pipeline parallelism and sequence length $512$). It does not list the complete per‑token latency configuration (batch sizes for the reported time/token numbers, exact context lengths used for latency measurement, whether KV cache was enabled, GPU clock settings, tensor parallelism for non‑$70$B runs, pinned host memory or async prefetch, or the exact attention kernel used). Because those missing details strongly affect measured time/token, I summarize what is stated in the paper, point out what is unspecified, and give a concise, reproducible recommended configuration that matches the paper’s intent and typical FasterTransformer practice.

What the paper explicitly states
- Inference codebase: NVIDIA FasterTransformer (with the Ladder $2$-bit kernel integrated for BitNet b1.58).
- Time metric reported: time per output token (this is the reported latency metric).
- Throughput experiment ($70$B): run on two $80$GB A100 GPUs using pipeline parallelism; sequence length (context) for throughput runs was $512$ and batch size was increased until GPU memory was saturated.
- Latency/memory/energy trends and the $2.4$–$4.1\times$ speedups are reported across model sizes; all latency and memory numbers were measured using the $2$-bit kernel.

What the paper does NOT specify (and so cannot be assumed)
- Batch size used for the reported time per output token (e.g., batch size $1$ vs larger).
- Exact context length(s) used for the latency-per-token numbers (latency depends on past context length when generating autoregressively).
- Whether the KV cache was enabled during the latency measurements (it almost certainly was for autoregressive generation, but the paper does not explicitly say).
- Whether attention used FasterTransformer’s fused causal self‑attention kernels or some other implementation (paper only references FasterTransformer generally).
- Exact GPU model and clock settings for the latency experiments beyond the $70$B throughput mention of A100 $80$GB (no info about boost clocks, power limits, or driver/CUDA/cuDNN versions).
- Whether tensor parallelism (TP) or model parallelism was used for non‑$70$B runs; only pipeline parallelism was explicitly mentioned for the $70$B throughput test.
- Whether pinned host memory, async weight/IO prefetching, CUDA streams or other host/GPU transfer optimizations were used.

Why these missing items matter
Time per generated token depends heavily on: (1) batch size (amortization across tokens), (2) KV cache and context length (longer past context increases attention/KV read cost), (3) exact attention kernel (fused kernels are much faster), (4) whether weights are streamed from host or fully resident on GPU, (5) tensor/pipe parallelism (cross‑GPU comm costs), and (6) GPU clocks and driver/runtime. Without those, a $2.4$–$4.1\times$ speedup is not reproducible.

A concise, practical reproduction configuration (matches the paper’s tools and typical FasterTransformer practice)
To reproduce the reported time/token as faithfully as possible, use this explicit setup (treat unspecified paper choices as these standard, high‑performance options):

- GPUs: NVIDIA A100 $80$GB (same device as the paper’s throughput mention). Use default boost clocks (or report the exact clock/power limit you set). Driver: recent NVIDIA driver and CUDA/cuBLAS/cuDNN versions compatible with FasterTransformer release used.
- Binary/kernel: FasterTransformer inference build with Ladder $2$-bit kernel integrated (same commit/branch if available).
- Batch size for latency (time per output token): batch size = $1$ (single‑stream autoregressive generation). Time/token is typically reported for batch=$1$; if paper used another batch, latency scales accordingly.
- Context length for latency: measure at several context lengths (e.g., $1$, $32$, $128$, $512$) and report the steady state when generating many tokens; if you must pick one, report both the empty‑context startup and a realistic warmed KV cache length (paper reports throughput at sequence length $512$ for throughput experiments).
- KV cache: enabled (typical autoregressive generation uses KV cache and FasterTransformer supports cached decoding; disabling it inflates time/token).
- Attention implementation: use FasterTransformer’s fused causal self‑attention kernels / decoder kernels (the fastest option in FT), not a naïve PyTorch loop. If you use a different attention kernel, report it explicitly.
- Parallelism: for models that fit on a single GPU (up to the memory limit with quantized weights), run with no tensor parallelism and no pipeline parallelism to measure single‑device latency; for $70$B the paper used pipeline parallelism across two A100s — reproduce the same pipeline partitioning if comparing the throughput numbers.
- Memory/weights residency: load all model weights into GPU memory (no streaming from host) for single‑GPU latency runs. For multi‑GPU pipeline runs, ensure weights for each stage are resident on the appropriate GPU.
- Host/GPU transfers: enable pinned host memory and asynchronous prefetch/overlap of H2D transfers if you must stream weights; for steady single‑GPU latency with resident weights this is unnecessary. If you do use streaming (e.g., for very large models), report pinned-memory + async prefetch settings explicitly.
- Measurement protocol: run a warmup of several hundred tokens (or generate a few sequences) to let kernels JIT/initialize, then measure wall‑clock time for generating $N$ tokens ($N$ large, e.g., $1000$) and report average time per output token = $\text{total\_time} / N$. Disable logging and host synchronizations that break batching or add overhead.
- Reproducibility notes: report CUDA version, FasterTransformer commit, Ladder $2$-bit kernel commit, driver version, and exact compilation flags so others can reproduce.

If you contact the authors or check supplementary material / code repo
Ask them to confirm (or supply) these explicit items: batch size used for time/token, context length(s) for latency curves, whether the KV cache was used and how it was warmed, exact FasterTransformer commit and config (which attention kernels and whether fused kernels were enabled), GPU clock/power settings, and parallelism settings for each model size. With those they should be able to provide an exact recipe replicating the $2.4$–$4.1\times$ numbers.

Summary
The paper documents the high‑level software stack (FasterTransformer + Ladder $2$-bit kernel) and reports throughput details for the $70$B two‑A100 case, but it omits many low‑level inference settings that materially affect time per output token. To reproduce the reported speedups you need to run with the Ladder $2$-bit kernel in FasterTransformer, use pinned GPU‑resident weights, enable KV cache and fused FT decoder kernels, measure after warmup with batch=$1$ (or the batch used in the paper if they can confirm it), and match the GPU and parallelism setup ($70$B used two A100s + pipeline). If you’d like, I can draft an explicit commandline/config (FasterTransformer flags, partitioning, and a short timing script) that implements the recommendation above.
