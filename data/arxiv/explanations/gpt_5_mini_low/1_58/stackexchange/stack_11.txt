\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### How was memory usage measured and what remains in full precision?
Question:
For the reported 3.3–3.6× memory reductions, what is included: model weights, optimizer states (for training?), KV cache, activation buffers, and temporary workspace? Given embeddings may remain FP16 and KV caches are 8-bit per the paper, can you provide a per-component memory breakdown for a representative model (e.g., 7B) at a given batch size and sequence length?
Answer:
Short answer: the $3.3\text{–}3.6\times$ memory reductions reported in the paper refer to inference (runtime GPU) memory measured with FasterTransformer using the deployed kernels. That measurement includes model parameter storage (weights), the KV cache, activation buffers and the GPU workspace used by the kernels. It does not include optimizer state (those are training-specific and were not part of the reported inference memory numbers). Per the paper, some components remain in full precision (or higher-precision) on purpose: token embeddings and similar LLaMA-style components are kept FP16/BF16, while the bulk of linear weight matrices are ternary 1.58-bit and activations / KV caches are stored in low precision (the paper used 8-bit activations / 8-bit KV and a 2-bit kernel for weight compute). The latency and memory numbers were produced by running FasterTransformer (so temporary workspace used by that library is implicitly included).

I’ll make this concrete with a representative, self-contained breakdown for a LLaMA-like 7B model at batch size 1 and sequence length 512 so you can see how the savings arise. I use the paper’s stated precisions and common LLaMA-7B architecture hyperparameters ($d_{model} = 4096$, $n_{layers} = 32$, $n_{heads} = 32$, $head\_dim = 128$). Treat the following as an illustrative, paper-grounded example (the paper does not publish an itemized table of every byte), and I call out assumptions and caveats at the end.

Representative assumptions (typical LLaMA-7B-style):
- Total params $\approx 7\times10^{9}$ parameters.
- Embeddings and any normalization/embedding-related tensors remain FP16 (2 bytes per element) per the paper.
- Weights (linear layers) are stored as 1.58-bit ternary ($\sim 1.58\ \text{bits} \approx 1.58/8 = 0.1975\ \text{bytes per parameter}$) as in BitNet b1.58.
- Activations and KV caches are stored as 8-bit (1 byte per element) in the BitNet runtime (paper: “activations 8-bit” and “KV caches ... 8-bit”).
- Baseline (FP16 LLaMA): parameters, embeddings, KV, activations are FP16 (2 bytes per element).
- Measurements are for inference; optimizer states (training) are excluded.

Compute sizes (approximate):

1) Model weights
- FP16 baseline: $7\times10^{9}\ \text{params} \times 2\ \text{bytes} \approx 14.0\ \text{GB}$.
- BitNet b1.58 weights: $7\times10^{9} \times 0.1975\ \text{bytes} \approx 1.38\ \text{GB}$.

2) Token embeddings (kept FP16 in the paper)
- Embedding size roughly vocab × $d_{model}$. For a 32k vocab: $32{,}000 \times 4096 \approx 131\times10^{6}$ elements.
- FP16 embedding size $\approx 131\times10^{6} \times 2\ \text{bytes} \approx 262\ \text{MB}$. (This is part of the 14 GB FP16 param above; for BitNet embeddings remain in FP16 so they are not reduced proportionally.)

3) KV cache (inference context memory)
The KV cache stores keys and values for every token, layer and head. Element count (K+V) = batch × seq_len × n_layers × n_heads × head_dim × 2.
With batch = 1, seq_len = 512, $n_{layers} = 32$, $n_{heads} = 32$, $head\_dim = 128$:
- Elements $= 1 \times 512 \times 32 \times 32 \times 128 \times 2 = 134{,}217{,}728$ elements.
- FP16 baseline KV size: $\times 2\ \text{bytes} \approx 268.4\ \text{MB}$.
- BitNet KV at 8-bit: $\times 1\ \text{byte} \approx 134.2\ \text{MB}$.

4) Activation / intermediate buffers
The paper states activations are 8-bit for BitNet (vs FP16 for baseline). The total activation buffer depends on implementation and overlap, but a typical order-of-magnitude for a 7B model with these dimensions is a few hundred MB. For an illustrative estimate assume activation working set (all intermediate activations that need to be kept per token during the forward pass) $\sim 300\ \text{MB}$ FP16 baseline $\rightarrow$ becomes $\sim 150\ \text{MB}$ at 8-bit in BitNet.

5) Kernel temporary workspace and other runtime overhead
FasterTransformer and the 2-bit/2-bit-ish kernels require some extra GPU workspace (scratch buffers, fused-kernel temporary arrays). That is implementation-dependent; for a single model + sequence this is commonly tens of MBs to low hundreds of MBs. The paper’s memory/latency numbers are measured with FasterTransformer, so such workspace is included implicitly in their quoted reductions.

Putting these up (approximate totals) for batch=1, seq=512:

Baseline FP16 totals (rough sum)
- Weights: $14.0\ \text{GB}$
- Embeddings (already in weights but highlighted): $\sim 0.26\ \text{GB}$
- KV cache: $\sim 0.27\ \text{GB}$
- Activations: $\sim 0.30\ \text{GB}$ (estimate)
- Workspace/overhead: $\sim 0.05\ \text{GB}$ (example)
Total $\approx 14.9\ \text{GB}$ (dominant term is FP16 weights)

BitNet b1.58 totals (approx sum)
- Weights (1.58-bit): $\approx 1.38\ \text{GB}$
- Embeddings (FP16): $\approx 0.26\ \text{GB}$
- KV cache (8-bit): $\approx 0.13\ \text{GB}$
- Activations (8-bit): $\approx 0.15\ \text{GB}$
- Workspace/overhead (FasterTransformer + kernels): $\approx 0.05\ \text{GB}$
Total $\approx 1.97\ \text{GB}$

Ratio baseline / BitNet $\approx 14.9 / 1.97 \approx 7.6\times$ memory reduction in this very simplified accounting. The paper reports $3.3\text{–}3.6\times$ reductions in their chosen measurement setups; the larger ratio above comes from (a) counting all parameters as reduced—real implementations may keep weight copies, quantization metadata, scaling factors, or use 2-bit kernels that bring additional buffers; (b) embeddings and small FP16 pieces reduce the effective saving; and (c) the paper’s figures are measured end-to-end with specific kernels and realistic runtime allocations (and they report memory for a range of models and batch sizes). The paper’s $3.3\text{–}3.6\times$ numbers are therefore the realistic, measured outcome for their FasterTransformer/inference configs. My breakdown shows where most of the savings come from: the big weight matrices going from $14\ \text{GB} \rightarrow \sim 1.4\ \text{GB}$, and the KV/activation precision reduction cutting hundreds of MBs.

Important caveats and clarifications tied to the paper
- The reported reductions are for inference memory measured with FasterTransformer kernels; optimizer states for training (which can triple memory because of optimizer + fp32 master copies) are not part of those numbers. Training memory will therefore show different (smaller) proportional reductions unless optimizer states and gradients are also quantized or otherwise reduced.
- The paper explicitly keeps embeddings and LLaMA-like components in FP16/BF16. That is a key reason why memory savings are not simply $16/1.58 \approx 10\times$ across the board. Embeddings, certain normalization parameters and some small arrays remain higher precision.
- The quoted KV and activation precisions in the paper are 8-bit, and the inference runs used a 2-bit kernel from Ladder in FasterTransformer. Kernel implementation details (e.g., whether the kernel needs dequantized temporary copies, whether per-matrix scales are stored) affect real-world memory use; the paper’s measured $3.3\text{–}3.6\times$ reflects those practicalities.
- If you care about training memory, optimizer states (Adam / AdamW states, fp32 master weights) typically dominate during training; the paper’s memory numbers do not include those and so do not directly translate to training memory reduction without additional scheme-specific treatment.

Conclusion
The paper’s $3.3\text{–}3.6\times$ reductions are inference measurements that include weights, activations, KV cache and kernel workspace measured with FasterTransformer. Embeddings and other small LLaMA-style tensors remain FP16/BF16, and optimizer states are excluded (i.e., training memory was not the basis of those reported numbers). The majority of the savings come from shrinking the large linear weight matrices (FP16 $\rightarrow$ 1.58-bit) and lowering KV/activation precision (FP16 $\rightarrow$ 8-bit). The short worked example above (with explicit calculations for a LLaMA-like 7B architecture) shows the relative sizes and where reductions appear; use it as an illustrative guideline and rely on the paper’s measured numbers for final claims because implementation/kernel details and quantization metadata materially affect the end-to-end measured reduction.
