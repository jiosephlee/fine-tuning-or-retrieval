\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### Reconciling 2-bit kernels with ternary weights: how are codes mapped?
Question:
Since weights are in \{-1,0,1\}, a 2-bit code can represent 3 values plus one unused. Which code mapping is used, and does the kernel exploit the unused code for any optimization (e.g., run-lengths or block sparsity)? Also, does the kernel handle mixed signed activations, or are activations also recoded for faster addition?
Answer:
Short answer: the paper does not spell out a concrete $2$-bit bitpattern $\to$ value mapping or any special use of the fourth code, and it does not describe recoding activations into a special form. It states only that weights are quantized to the ternary set $\{-1,0,+1\}$ (via the absmean RoundClip quantizer), that inference runs with an existing 2‑bit kernel from Ladder integrated into FasterTransformer, and that activations are kept as signed 8‑bit values scaled per token to the range $[-Q_b, Q_b]$. From those statements you can infer that the implementation uses a 2‑bit storage kernel that represents three logical values and leaves one bit pattern unused (or implementation-defined), and that the compute path works with signed integer additions on 8‑bit activations rather than requiring extra recoding.

Why this is the case (intuitive + technical): the paper’s quantizer maps full‑precision weights to the set $\{-1,0,1\}$ before inference. Storing three possible values in 2 bits is natural, but the document doesn’t commit to a particular bit-pattern assignment (e.g. $00 \to -1$, $01 \to 0$, $10 \to +1$ or any other mapping). They rely on an off‑the‑shelf 2‑bit kernel (Ladder) for the actual packed storage and compute; such kernels typically pick a mapping internally and implement the arithmetic primitives to interpret the packed 2‑bit codes as signed integers during the matmul replacement. Because activations are explicitly kept as signed 8‑bit values (scaled per token to $[-Q_b, Q_b]$), the forward computation is described as integer additions (INT8 adds) rather than a mixture of signless encodings that would need special unpack/recoding. In short, the paper emphasizes the algorithmic quantization and that a 2‑bit kernel is used, but it does not alter activation representation to avoid signedness, nor does it claim using the spare bit pattern for metadata.

What the paper does not claim (and where to look if you need details): the manuscript does not describe using the unused 2‑bit code for run‑length encoding, block‑sparsity flags, or other side‑channel encodings; it simply reports using the Ladder 2‑bit kernel integrated into FasterTransformer for latency/memory measurements. If you need the exact bit assignment or any kernel‑level tricks (packing order, use of the spare code, SIMD-friendly layout, whether Ladder compresses runs or encodes blocks), you should inspect the Ladder kernel source or the FasterTransformer integration used in their experiments—those implementation repositories will show the precise mapping and any micro‑optimizations.

Practical takeaway: functionally, treat weights as ternary values stored with a 2‑bit kernel whose internal mapping is implementation detail. The compute path uses signed INT8 activations (no special recoding reported) and the kernel performs integer additions accordingly. If you want to exploit the unused code pattern (e.g., for run‑lengths or block flags), that would be an independent engineering choice not covered in the paper and would require modifying/confirming the kernel implementation.
