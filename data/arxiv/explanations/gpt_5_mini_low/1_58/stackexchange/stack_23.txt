\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### Storage vs compute precision: what precision is used on disk, in RAM, and in the kernel?
Question:
To deploy b1.58, models might be stored in compressed formats on disk, unpacked into GPU memory, and then processed by specialized kernels. Could you specify the precisions at each stage (disk, host RAM, device global memory, shared memory/registers) and the associated bandwidth/compression strategies? This would clarify practical gains vs theoretical 1.58 bits/weight.
Answer:
Short answer: the paper’s weights are conceptually 1.58 bits/weight (ternary $\{-1,0,+1\}$), activations are 8‑bit; but the end‑to‑end precisions and bandwidth seen in a real system depend on how you pack and which kernel you run. The paper does not mandate a single on‑disk / in‑RAM layout, but it describes the algorithmic choices (ternary weights, per‑token activation scaling to $[-Q_b,Q_b]$, and use of a 2‑bit kernel from Ladder). Below I summarize the plausible, paper‑consistent precisions and common system choices at each stage, the compression/packing strategies that realize the 1.58‑bit claim in practice, and where practical losses vs the ideal occur.

Disk (persistent storage)
The model semantic format is ternary weights (values in $\{-1,0,1\}$) plus a per‑tensor scale $\gamma$ (absmean). To approach 1.58 bits/weight on disk you must pack many ternary values into bytes and optionally compress further:
- Minimal representation: bit‑pack two bits per weight ($00,01,10$ for the 3 values; one unused code) → 2 bits/weight raw. This is what the paper’s use of a “2‑bit kernel” implies is supported.
- To approach 1.58 effective bits/weight you can exploit the extra structure (sparsity of zeros and entropy of symbol frequencies) with run‑length encoding, bitmap + indices for zeros, or entropy coding (e.g., arithmetic or Huffman). Those give stored sizes closer to the theoretical 1.58 bits/weight if symbol distribution and sparsity are favorable.
The paper does not prescribe an exact disk format; it only requires saving the quantized ternary matrix and its $\gamma$ (and any per‑block metadata if you use block scaling).

Host RAM (process memory before GPU upload)
There are two common choices consistent with the paper:
1) Keep weights packed in the host process (2‑bit packed, or compressed) and transfer the packed bytes to the device (preferred for bandwidth).
2) Unpack to a byte‑aligned integer representation (e.g., int8 per weight with values -1,0,1) for simpler CPU-side ops or for a driver that expects byte elements.
The paper’s memory/latency advantages assume keeping the footprint compact (packed) across host memory and into device memory whenever the kernel supports it. Activations and embeddings: activations are stored as 8‑bit integers (per the paper: “8‑bit activations”), while embeddings are kept full precision (FP16/BF16), as stated.

Device global memory (GPU DRAM)
The paper reports experiments using a “2‑bit kernel from Ladder” integrated into FasterTransformer. That implies device global memory typically stores weights in a packed 2‑bit layout (one byte contains $4$ weights) or a blockwise 2‑bit layout compatible with the kernel. Practically:
- Weights: packed 2‑bit (or a block‑packed + per‑block scale $\gamma$), or in some implementations unpacked to int8 for simpler kernels. The paper’s memory reductions (e.g., 3.55× less GPU memory) assume packed/low‑bit storage and kernels that consume it directly.
- Activations/KV caches: 8‑bit int (paper explicitly: 8‑bit activations). The paper also notes activations can be losslessly further compressed to 4 bits in future work, but experiments use 8‑bit.
- Embeddings / any components kept full precision: FP16/BF16 in global memory (paper: “embedding remains full precision”).

On‑chip (shared memory / registers / compute)
At kernel runtime the layout depends on the kernel implementation:
- Ladder / specialized 2‑bit kernels typically read packed 2‑bit weights and perform bitwise/unpacking operations into registers or use vectorized integer arithmetic. The arithmetic is mostly additions of integer values (paper: “matrix multiplication of BitNet only involves integer addition”).
- Common practical implementation: weights may be unpacked into int8 lanes in registers or shared memory and then summed/accumulated into int32 accumulators, followed by scaling by $\gamma$ (and possibly conversion to FP16/BF16 for following layers). So compute precision often is int8 (or bit‑ops) for weight×activation, accumulation in int32, then cast to FP16.
- Activations are 8‑bit inputs to these kernels; accumulators and final outputs may be int32 → FP16/FP32 depending on the kernel and whether downstream ops expect floating point.

Bandwidth and compression strategies (how practical gains are realized)
The paper’s claims hinge on reducing both capacity and bandwidth costs. The system techniques consistent with the paper are:
- Bit‑packing: store weights at 2 bits/weight in bytes (4 weights/byte). This cuts raw transfer size by 8× relative to FP16 (16 bits → 2 bits).
- Blockwise scaling: store a small per‑block float scale $\gamma$ (e.g., one FP16/FP32 scale per $256$ or $1024$ weights). That overhead is tiny and already included in the paper’s cost accounting.
- Sparsity exploitation: since ternary includes zeros, store a bitmap or run‑length code for zeros to reduce further toward 1.58 bits/weight. This is optional in the paper but explicitly enabled by the ternary design.
- Kernel‑native consume: keep the packed layout when uploading to GPU and call a kernel (the Ladder 2‑bit kernel referenced) that consumes packed data directly, avoiding unpack→pack overheads.
- Activation scaling: activations are quantized per token to $[-Q_b,Q_b]$, eliminating zero‑points and simplifying kernel math and memory layout (paper statement).

Where the theoretical 1.58 bits vs practical differ
The paper’s “1.58 bits/weight” is an information/representation figure for ternary weights with observed sparsity / symbol frequencies. Practical system costs deviate for these reasons:
- If you use a simple 2‑bit packed layout everywhere, you pay 2 bits/weight rather than 1.58. Getting to 1.58 requires entropy or sparsity compression which adds CPU/GPU decompression cost.
- If the GPU kernel cannot operate on packed 2‑bit data, you must unpack to int8 on upload, temporarily using 8 bits/weight in device memory/bandwidth and incurring unpack cost; the paper’s reported speed and memory savings assume kernels that can handle low‑bit packed formats (they used a 2‑bit Ladder kernel).
- Per‑block scales and metadata increase overhead slightly; for large blocks this is negligible.
- Activations/KV caches: the paper reduces them to 8 bits → halves memory relative to 16‑bit FP. If you keep KV caches at FP16, the end‑to‑end memory gains are smaller than the pure weight compression number.

Practical recommended pipeline consistent with the paper to realize near‑claimed gains
Store weights on disk packed (2‑bit) and optionally entropy‑compress for archival. Keep them packed in host RAM and DMA to GPU as packed blocks. Use a kernel that consumes packed 2‑bit weights (like the Ladder 2‑bit kernel used in the paper) and 8‑bit activations, accumulate in int32 and rescale with stored $\gamma$ before casting to FP16 for downstream ops. Keep embeddings FP16. If you can exploit zero sparsity (bitmap + packed nonzeros), you can reduce stored bits toward 1.58 at little extra runtime cost if the kernel supports sparse decode.

Final practical note
The paper documents training and inference results using a 2‑bit kernel and 8‑bit activations and reports memory/latency/energy reductions under those choices. It does not give one mandatory on‑disk encoding; the exact bits/weight seen by a deployed system equals the chosen packing and whether the kernel directly consumes packed data. The theoretical 1.58 bits/weight is achievable as an average compressed storage number, but the real runtime bandwidth equals the on‑wire format the kernel expects (commonly 2 bits/weight for the experiments in the paper).
