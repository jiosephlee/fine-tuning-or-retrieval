\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### How does 1.58 bits arise from ternary weights {−1, 0, 1}?
Question:
The paper claims each weight is in {−1, 0, 1} and calls the model "1.58-bit". I assume this is because there are 3 states and log2(3) ≈ 1.585 bits. Is this just a naming convention (information-theoretic) or does the implementation actually use packed encodings close to 1.58 bits/weight at runtime? If the kernel uses 2-bit packing (as mentioned via Ladder), then the effective storage is 2 bits/weight, not 1.58. Can the authors clarify what is 1.58 vs 2 bits in practice (storage on disk, in-memory, wire, and compute representation)?
Answer:
Short answer: “$1.58$-bit” in the paper is an information‑theoretic descriptor ($\log_2(3) \approx 1.585$) for ternary weights $\{-1,0,+1\}$. In practice the implementation uses an available $2$-bit kernel (Ladder) for compute and storage on GPU, so the working representation on device is effectively $2$ physical bits per weight (or often one byte per weight depending on packing/driver). The paper distinguishes the theoretical entropy of a ternary-valued weight from the concrete low‑level packing/compute choices used today.

Why the “1.58” label
The model constrains each scalar weight to exactly three values: $-1$, $0$, $+1$. The number of distinct states is $3$, so the information content per weight (if all three states are equally likely) is $\log_2(3) \approx 1.585$ bits. Calling the model “$1.58$-bit” is therefore shorthand: it describes the discrete alphabet size of the parameter set, not the byte/bit layout in memory or the kernel implementation.

What happens in the implementation (storage, memory, wire, compute)
The paper is explicit that inference/latency/memory measurements were made with a $2$-bit kernel from Ladder integrated into FasterTransformer. That implies:

- Compute representation: the runtime kernel consumes a $2$-bit encoded representation (Ladder’s $2$-bit path) and performs the int additions described for BitNet b$1.58$. So during inference the device executes on a $2$-bit packing/decoder and arithmetic pipeline (not a hypothetical $1.585$-bit ALU).
- In‑memory and on‑device storage: for the experiments reported (latency, GPU memory), weights are represented as $2$-bit packed values (or via the kernel’s internal packed layout). Two physical bits are used per weight on the wire between DRAM and accelerator (subject to alignment/transport semantics), which is what drives the measured memory and bandwidth improvements.
- On‑disk or offline storage: the paper does not detail a specific compressed file format. You can store ternary parameters as $2$-bit packed arrays (fast, simple) or compress further offline. If you apply an entropy coder (arithmetic coding, Huffman) tuned to the empirical distribution of $\{-1,0,1\}$ and include any required metadata (scales, block gamma values), you can approach the information‑theoretic lower bound ($\approx 1.585$ bits/weight). That requires extra CPU/GPU work at load/decode time and bookkeeping for blockwise scaling factors (the paper uses an absmean scale $\gamma$ per weight matrix/block), so practical storage size will be a bit larger than the pure entropy limit.
- Metadata and alignment overheads: whatever compressed scheme you choose, you must store scaling factors ($\gamma$) per block/matrix, any block shapes, and potentially padding/alignment for fast decoding. Those overheads make the real per‑weight bytes slightly larger than $\log_2(3)$.

When can you actually reach $\approx 1.585$ bits/weight?
You can only approach $\approx 1.585$ bits/weight if:
1) the empirical distribution of the three states is close to the entropy‑maximizing one (equal probabilities) or you use an entropy coder matched to the actual distribution, and
2) you accept the decoding/encoding overhead (compute + implementation complexity) and store the scaling metadata efficiently. For on‑the‑fly inference on GPUs in the paper’s experiments, the pragmatic choice was to use a $2$-bit kernel instead of a computationally expensive entropy codec.

Takeaway
“$1.58$-bit” is a descriptive name referencing the ternary alphabet size ($\log_2(3)$). The practical system used in the paper uses a $2$-bit runtime kernel (Ladder) for compute and memory/bandwidth measurements. If you need minimal bytes on disk or wire, you can further compress to approach $\approx 1.585$ bits/weight with entropy coding, but that is a separate engineering tradeoff (decode cost, metadata, alignment) the paper does not claim to have implemented for the runtime measurements.

### Where does the scaling factor go after absmean quantization of weights?
Question:
The quantization is defined as \(\widetilde{W} = \mathrm{RoundClip}(W/(\gamma+\epsilon), -1, 1)\) with \(\gamma = \frac{1}{nm}\sum_{ij} |W_{ij}|\). After rounding, are the ternary weights used as-is (\{-1,0,1\}) or is there an implicit multiplication by \(\gamma\) somewhere (e.g., folding \(\gamma\) into activations or a layerwise scaling)? If \(\gamma\) is thrown away, how is dynamic range preserved? If it is kept, where is it applied at inference so that matrix multiplies remain multiplication-free?
Answer:
Short answer: The paper’s absmean scale $\gamma$ is not discarded — it is a per-weight-matrix (layerwise) scale that must be kept and applied to recover the original dynamic range. In practice you quantize to ternaries $\widetilde W\in\{-1,0,1\}$ and then treat the real-valued weight matrix as $W\approx (\gamma+\epsilon)\,\widetilde W$. During inference the integer (ternary) matrix–vector products produce integer accumulators which are then multiplied by the scalar $\gamma+\epsilon$ (or have that scalar folded into some neighbouring scale), so you do not lose dynamic range.

Why this is the correct reading and how it is used. The paper defines
$\widetilde W=\mathrm{RoundClip}\big(W/(\gamma+\epsilon),-1,1\big)$
with $\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|$. That formula normalizes by $\gamma$ to decide the ternary sign/zero; it is therefore the natural inverse factor to restore the approximate magnitude of $W$. If you threw away $\gamma$ you would reduce every retained $\pm1$ to exactly unit magnitude and lose the per-matrix scale information — the model would lose dynamic range and accuracy.

How it is implemented efficiently so matrix multiplies remain mostly multiplication-free. The usual practical ways to handle the scale are: keep a single scalar $\gamma$ per quantized weight matrix and apply it after the integer (here ternary) accumulation, or fold that scalar into the next operation’s scale (for example into an activation quantization scale, a succeeding layer’s weight scale, or the post-linear-layer bias/normalization scaling). Concretely, if activations are $A$ and you compute $Y = W A$, you actually compute
$Y \approx (\gamma+\epsilon)\,(\widetilde W A)$.
The inner product $\widetilde W A$ can be done with integer additions (and sign flips for $-1$) and yields integer accumulators; only after accumulation do you multiply those accumulators by the scalar $\gamma+\epsilon$. Folding $\gamma$ into the next layer’s input scale means that scalar multiplication can be merged with that layer’s existing rescaling (so it does not add a dense per-element multiply inside the heavy GEMM inner loop). That’s why the paper states “almost no multiplication operations” — the expensive MACs are replaced by integer add/sign operations, and only a comparatively cheap scalar rescale remains per channel/tensor block or is absorbed into existing quantization/normalization.

Relation to the paper’s activation quantization comment. The paper quantizes activations per-token to a fixed range and avoids zero-point; that per-token activation scale is another place where the weight $\gamma$ can be folded: either multiply the ternary accumulation by $\gamma$ then by the activation scale, or combine $\gamma$ with the activation scale so the thin scalar that remains is applied outside the core integer accumulation.

Practical summary: keep $\gamma$ (one scalar per weight matrix), perform the ternary integer accumulation $\widetilde W A$ with addition-only primitives, and apply $\gamma+\epsilon$ as a cheap scalar rescale afterwards or fold it into adjacent quantization/normalization operations. This preserves dynamic range while keeping the heavy inner loops multiplication-free, which is consistent with the system and hardware claims in the paper.

### How are gradients computed through the RoundClip operator during training?
Question:
The paper says BitNet b1.58 is trained from scratch with 1.58-bit weights, implying quantization is present throughout training. What surrogate gradient is used for \(\mathrm{round}(\cdot)\) and clipping (e.g., straight-through estimator with clip-aware gradient)? Is there any gradient scaling by \(\gamma\)? Also, is \(\gamma\) treated as a constant per weight matrix (frozen per step) or differentiated through?
Answer:
Short answer: the paper does not explicitly state the surrogate gradient used. It only gives the forward quantization math
$$
\widetilde W = \mathrm{RoundClip}\!\left(\frac{W}{\gamma+\epsilon},-1,1\right),\qquad
\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|.
$$
So you must infer an implementation from common practice. Below I explain the likely choices, why they are used, and the practical decision points the paper leaves unspecified.

What the paper says (forward only)
The text defines $\mathrm{RoundClip}(x,a,b)=\max(a,\min(b,\mathrm{round}(x)))$ and a per-matrix scale $\gamma$ equal to the mean absolute weight. That fully specifies the forward pass: divide $W$ by $\gamma$, round and clip to $\{-1,0,1\}$, then use $\widetilde W$ for the linear ops. The paper does not describe backward/surrogate gradients, nor whether $\gamma$ is treated as differentiable.

Typical, practical choice (and why)
Practically, most quantized-training works adopt a Straight-Through Estimator (STE) for non-differentiable ops like round and hard clip: during backward you pretend the quantizer is identity (or use a clipped identity) so gradients flow to the underlying full-precision $W$. Concretely, one common implementation is
$$
\frac{\partial \widetilde W}{\partial W}\approx \mathbf{1}_{|W/\gamma|\le C}
$$
or simply treat $\mathrm{round}(\cdot)$ as identity (pass-through) and let clipping backprop either pass gradient inside the clip range and zero outside (clip-aware STE) or pass everything (naive STE). The intuitive reason is stability: STE lets the optimizer move the latent $W$ so that its rounded/ clipped value changes when desirable, and it has a long history of working for quantization.

What to do with $\gamma$
There are two sensible choices: treat $\gamma$ as a deterministic scalar computed from $W$ each forward and stop-gradient it (i.e., do not backprop through the mean-abs computation), or allow gradients to flow through $\gamma$. Most papers that use scale-by-statistics (mean/absmean) either detach the statistic or explicitly reparameterize to avoid noisy gradients through reduction ops, because backpropagating through a global per-matrix average can introduce undesirable coupling and instability. So the conservative/typical practice is to compute $\gamma$ from $W$ in the forward pass and treat it as a constant for the backward pass (detach).

Is there extra gradient scaling by $\gamma$?
The forward divides by $\gamma$. If you detach $\gamma$ then no extra gradient-scaling term from $\gamma$ appears in backprop beyond the explicit division in the forward. If you do differentiate through $\gamma$, gradients on $W$ will include additional terms coming from $\partial\gamma/\partial W$ (a global coupling). The paper does not report any special gradient-rescaling factor applied beyond the forward scaling, so there is no evidence that they used an extra manual gradient multiplier.

Recommended/likely implementation consistent with the paper
Given the paper’s silence, the most straightforward and commonly used implementation consistent with their description is:
compute $\gamma=\frac{1}{nm}\sum|W_{ij}|$ each forward, detach it (no gradient through $\gamma$), compute $X=W/(\gamma+\epsilon)$, set $\widetilde W=\mathrm{RoundClip}(X,-1,1)$ for the forward, and use an STE in the backward that treats $\mathrm{round}()$ as identity and uses clip-aware pass-through (i.e., pass gradient for inputs inside the clipping interval, zero outside or simply pass-through everywhere). This is simple, stable, and matches standard quantized-training practice.

Why this matters (intuition)
Allowing gradients through round/clip only via STE gives a usable training signal to the latent full-precision $W$ so the optimizer can nudge weights across rounding thresholds. Detaching $\gamma$ avoids global coupling noise and spurious gradient contributions from the reduction over the whole matrix, which otherwise can slow or destabilize training. If one instead backpropagates through $\gamma$, the optimizer will update $W$ partly to change the normalization statistic itself, which can be harder to control.

If you need reproducibility
Because the paper does not specify, if you implement this yourself and want to reproduce results exactly, try the STE + detach-gamma variant first (it is the most common and the one I would expect the authors used). If results differ, try enabling gradient through $\gamma$ or using clip-aware vs naive STE and report the difference; papers that omit these details often found them not crucial but they can affect stability for some scales.

Summary
The paper specifies the forward RoundClip and $\gamma$ but does not state the surrogate gradient. The standard, likely choice is an STE for round/clip and treating $\gamma$ as a frozen per-matrix scalar in the backward (detach). There is no reported explicit gradient-scaling factor beyond the forward division by $\gamma$.

### What exactly is meant by “no multiplication operations” in matrix multiplication?
Question:
With weights in \{-1,0,1\}, a dot product with 8-bit activations can be implemented as additions and sign flips (and skips for zeros). But the paper also mentions using a 2-bit kernel from Ladder. Does the actual kernel use any multiplications (e.g., bit-serial popcount tricks or table lookups) or is it strictly addition/subtraction and shift? Can you detail the primitive operations used per MAC and how that translates to the claimed energy savings?
Answer:
Short answer: When the paper says “almost no multiplication operations” it means that the heavy inner-loop floating-point multiplications of a conventional $\text{FP16}$ MAC are replaced by much cheaper integer operations — conditional adds/subtracts, bitwise ops and population counts — not by general FP multipliers. For the ternary weights $\{-1,0,1\}$ a multiply with an $8$‑bit activation reduces to “add the activation” (for $+1$), “subtract the activation” (for $-1$), or “skip” (for $0$). The $2$‑bit Ladder kernel the paper integrates is implemented with bitwise/bitpacked integer primitives (e.g. XNOR/AND + popcount or small LUTs) and integer accumulation, not full-precision multiplies.

Why that is true (intuitive + technical):
- A conventional MAC for $\text{FP16}$ does: output += $(\text{FP16 weight}) \times (\text{FP16 activation})$. That uses a floating-point multiply and a floating-point add for every weight–activation pair.
- If weights are constrained to $\{-1,0,1\}$ and activations are integers ($8$‑bit in the paper), then weight $\times$ activation is exactly one of three outcomes: activation, $0$, or $-$activation. So the multiply operation is logically replaced by a simple selection and sign: output += sign $\times$ activation or skip if zero. On hardware this is implemented as an integer add/subtract (accumulate the $8$‑bit activation into a wider integer accumulator), plus a branchless sign flip (negation) or two’s‑complement subtraction. No FP multiply units are needed in the inner loop.
- For kernels that pack many low-bit weights (the Ladder $2$‑bit kernel or other bitpacked kernels), the low-bit multiplies are implemented via bitwise operations and a population count (popcount) rather than arithmetic multiply. Example approaches:
  - For binary weights $\{-1,+1\}$ one can pack bits and compute XNOR (or XOR)+popcount over activations to obtain dot-products; the final dot-product is reconstructed from popcount results and simple integer arithmetic.
  - For $2$‑bit weights, implementations typically decompose the $2$‑bit multiply into a small number of bitwise ANDs/XNORs and popcounts (or use a tiny lookup table per packed word) and then combine the popcounts with integer adds/subs and shifts. These are integer/bitwise primitives, not FP multipliers.
- The Ladder kernel referenced in the paper is integrated to implement $2$‑bit/low-bit GEMM efficiently; the paper does not claim Ladder uses FP multipliers — the usual Ladder-style kernels use bitpacking + popcount/lookup + integer accumulation.

Primitive operations counted per MAC (conceptually)
- $\text{FP16}$ MAC (baseline): $1$ $\text{FP16}$ multiply + $1$ $\text{FP16}$ add (plus normalization/accumulation overhead).
- Ternary weight + $\text{INT8}$ activation MAC (BitNet idea): for each nonzero weight, one $\text{INT8}$ add or subtract into an accumulator (often widening to int32). Zero weights skip work. In packed implementations you amortize many such logical MACs into a few bitwise + popcount + integer adds.
- Packed $2$‑bit kernel (Ladder-like): a small number of bitwise ops (AND/XNOR/XOR), $1$ popcount per packed word, and a handful of integer adds/shifts to turn popcounts into partial sums. These are integer/bitwise primitives.

Where multiplications may still appear (practical caveats)
The inner GEMM can avoid FP multiplies, but some scalar multiplications remain in the system: scaling factors (the paper’s $\gamma$ or per-tensor scales), dequantization to $\text{FP}$ for downstream layers or output, and some activation scaling or normalization may use FP or integer multiplies. But these are far less frequent than the per-weight multiplies that dominate FP MAC cost. Also, an implementation on commodity GPUs may use integer multiply instructions in microkernels for packing/unpacking or for scale application, but the dominant bulk multiply engine (FP multipliers) is not used for the inner dot products.

How that maps to the claimed energy savings
Energy models in the paper (citing prior work like “energycost” and “pokebnn”) show that an FP multiply (and FP MAC) costs orders of magnitude more energy than integer adds or bitwise ops on modern process nodes. Replacing FP multiplies by $\text{INT8}$ adds, popcounts and bitwise ops reduces arithmetic energy significantly for the MAC-dominated portion of LLM inference. The paper reports an estimated $71.4\times$ reduction in arithmetic operation energy for matrix multiplication on a $7\ \mathrm{nm}$ process. Intuitively this comes from (a) eliminating the expensive $\text{FP16}$ multiply and (b) using very compact integer/bitwise kernels that do more logical MACs per hardware instruction (bitpacking amortizes many logical multiplies into one popcount). The presence of many zeros (sparsity from ternary quantization) further reduces operations because skipped weights eliminate adds entirely.

Bottom line
“Almost no multiplications” in the paper means you no longer execute a FP multiply for each weight–activation pair during the main GEMM. Instead you use integer additions/subtractions for ternary weights and bitwise+popcount + integer arithmetic for bitpacked $2$‑bit kernels (Ladder). That substitution is what drives the large per-MAC energy reduction reported, though a few scalar multiplies for scaling/dequantization still exist outside the inner loop.

### Are all Transformer parameters ternary, or are some layers left in higher precision?
Question:
The paper says "every parameter (or weight) of the LLM is ternary" but elsewhere notes that the embedding "remains full precision" in scaling analyses. Which components are ternary versus higher precision at inference: token embeddings, positional/rotary embedding parameters, attention projection matrices (Q/K/V/O), MLP (SwiGLU) matrices, layer norm/RMSNorm parameters, and output softmax head? If some remain FP16/BF16, how does that affect the reported memory and speed numbers?
Answer:
Short answer: in the paper the bulk of model weights (all linear layers used in the Transformer) are ternary, while a few small parameter groups are treated in higher precision in the measurements. Concretely, attention projection matrices (Q/K/V/O), the MLP (SwiGLU) weight matrices, and the output (softmax) projection are trained/represented as ternary weights in BitNet b$1.58$. Activations are $8$-bit. By the paper's statement about memory proportions, token embeddings (and, in practice, small normalization or embedding-like parameters) are kept in full precision for the reported memory/latency numbers.

Why this is the case and what it changes for the reported results
The paper emphasizes “every parameter (or weight) of the LLM is ternary” as the design goal of BitNet b$1.58$, and the model is built by replacing nn.Linear with BitLinear and training from scratch with ternary weights. That wording refers to the model’s main weight matrices: attention and feed‑forward (MLP) matrices and the output projection. However, when reporting runtime memory and latency the authors explicitly call out that “the embedding remains full precision and its memory proportion is smaller for larger models.” That tells us that, in their runtime/counts, token embeddings were left as $ \mathrm{FP16}/\mathrm{BF16}$ (full precision) while the main linear layers used the $1.58$-bit ternary representation (and the inference kernels used a $2$-bit implementation from Ladder for execution). RMSNorm and similar tiny parameter vectors (scale / norm statistics) are extremely small, and the paper treats them as part of the non-dominant $ \mathrm{FP16}$ component in the memory breakdown; practically they remain negligible in cost whether $ \mathrm{FP16}$ or quantized.

Practical consequences on memory, latency and energy numbers
Because embeddings can be large for small models (and proportionally smaller for very large models), leaving them $ \mathrm{FP16}$ makes the reported memory savings slightly conservative compared to a hypothetical fully-ternarized model including embeddings. For example, the paper reports that BitNet b$1.58$ is $3.55\times$ lower GPU memory at $3$B and that this improvement increases with model size; that trend is explained by the fixed $ \mathrm{FP16}$ cost of embeddings becoming a smaller fraction of total parameters for bigger models. Similarly, latency/speed numbers reflect two things: (1) compute kernels for matrix multiplies are run on low-bit ($2$-bit/ternary) kernels for the bulk of nn.Linear ops, giving large speedups; (2) any remaining $ \mathrm{FP16}$ copies (embeddings, tiny norm params) must be moved/used in $ \mathrm{FP16}$, so they slightly reduce the theoretical maximum speedup. The authors measured with a $2$-bit kernel for the ternary weights and left embeddings $ \mathrm{FP16}$, so reported speed/memory/energy are the real measured end-to-end numbers under that mixed-precision runtime.

Intuition and broader context
Embeddings sit at the interface between discrete tokens and continuous networks and are relatively easy to keep full precision: doing so avoids some engineering complications (e.g., token-table lookups with very low bitwidth and preserving representation capacity for rare tokens). But matrix multiplies (attention and MLP) are the dominant FLOPs and bandwidth consumers; quantizing those yields the big wins in latency, energy and memory. Thus the pragmatic mixed choice (ternary for the big linear layers, $ \mathrm{FP16}$ for embeddings and tiny normative params) gives most of the system benefit while keeping a few convenient components in higher precision. For very small models the embedding share is larger, so fully-ternary embeddings would yield noticeably higher relative memory savings; for large models the embedding $ \mathrm{FP16}$ overhead is marginal.

Short practical takeaway
- Ternary in the paper = attention projection matrices, MLP matrices, and output projection are ternary (BitLinear). Activations are $8$-bit.  
- Token embeddings (and effectively small norm/gain vectors) were left full precision in the reported measurements.  
- The reported memory/latency/energy numbers were measured with this mixed-precision setup (ternary bulk weights + $ \mathrm{FP16}$ embeddings), so they are slightly conservative compared to an all-ternary-weights measurement; the difference matters most for smaller models where embeddings are a larger fraction of total memory.

### Why are biases removed, and how does that interact with ternary constraints?
Question:
The model removes all biases and uses RMSNorm and SwiGLU (LLaMA-like). Is bias removal primarily for numerical stability/quantization compatibility, for simplicity, or to match LLaMA configs? In ternary networks, biases can help shift activation distributions. Did keeping biases degrade training stability or performance here, or was removal just for reproducibility with LLaMA?
Answer:
Short answer: in this paper bias removal is mainly a pragmatic design choice to match the “LLaMA‑alike” configuration (RMSNorm, SwiGLU, rotary, toolchain compatibility) and to simplify integration with open-source runtimes. A useful side effect is that it simplifies the ternary quantization pipeline (scaling/rounding around zero) and avoids subtle bias-related interactions with the absmean quantizer, so it also helps implementation- and quantization‑robustness. The authors do not report that keeping biases improved performance, and their results show BitNet b1.58 matches FP16 from 3B up, so removing biases did not hurt their empirical outcome.

Why that makes sense (intuitively + technically)
1) Matching LLaMA and ecosystem compatibility. The paper explicitly says the model “adopts the LLaMA‑alike components” and “removes all biases” so BitNet b1.58 can be dropped into popular open‑source software (HuggingFace, vLLM, llama.cpp) with minimal effort. That is a concrete engineering motivation: many LLaMA forks omit biases and the toolchain expects that structure.

2) Simpler quantization and scaling. BitNet b1.58 enforces ternary weights via an absmean scale and a round/clip to $\{-1,0,1\}$. When you quantize around zero it is simpler if there are no per-neuron/per-output additive terms to account for. Biases introduce constant offsets in pre-activations which (a) must be quantized themselves or folded into other ops, (b) can shift means away from zero and thus change the effective sparsity (frequency of zeros) after rounding. Removing biases makes the absmean normalization and the RoundClip step conceptually and numerically cleaner.

3) Interaction with normalization. The architecture uses RMSNorm (which, unlike LayerNorm, typically has no learned bias term). If normalization layers are already normalizing and providing affine scaling, learned linear-layer biases become less critical for representational power. In many transformer variants the combination of pre/post‑norm and gating nonlinearities can absorb the function of biases, so removing them causes little functional loss.

4) Ternary-specific considerations. In ternary/1.58‑bit networks biases can have outsized effects because small constant offsets get quantized to nonzero discrete values and persist across signals. That can (depending on scale) either force more nonzero weights (reducing sparsity advantage of the added $0$ state) or create systematic activation shifts that the model must compensate for elsewhere. By removing biases you avoid these brittle interactions and keep the weight distribution centred for the absmean scaler to produce sensible quantization thresholds.

Did leaving biases hurt stability or performance? The paper does not present an explicit ablation where biases were retained vs removed, so we cannot claim they empirically failed. However, the authors emphasize reproducibility with the LLaMA config and report that BitNet b1.58 matches FP16 baselines (from 3B up) after using the biasless design. That implies removing biases did not degrade final performance in their training regime; pragmatically it simplified the quantization recipe and integration with existing implementations.

What to test if you worry biases matter
If you want a definitive answer for your own experiments, run a small ablation: train (or fine‑tune) identical BitNet models with and without biases and measure (a) training stability (loss curves, gradients), (b) resulting sparsity / fraction of zeros in ternary weights, and (c) validation perplexity and downstream tasks. That will show whether biases improve representational efficiency, merely duplicate capacity already provided by RMSNorm/SwiGLU, or cause quantization brittleness.

Takeaway
Removing biases in this paper is primarily an engineering and compatibility choice aligned with the LLaMA design, which also makes the ternary quantization pipeline cleaner (less shifting of activation/weight means, more predictable sparsity). The authors’ results indicate this choice did not prevent the ternary model from matching FP16 baselines at scale, but a direct bias ablation (not reported) would be needed to quantify any small gains or losses from keeping biases.

### Clarifying activation quantization: per-token scaling to [−Q_b, Q_b] without zero-point
Question:
The paper states activations are 8-bit and scaled per token to \([-Q_b, Q_b]\), removing zero-point. 1) How is the per-token scale determined (max-abs, EMA, percentile)? 2) Is scaling applied before or after attention softmax, and how is numerical stability ensured for attention scores and softmax? 3) Does per-token scaling break any invariances or cause sequence-position-dependent artifacts compared to per-channel or per-tensor schemes? 4) Why was the previous BitNet activation scaling to \([0, Q_b]\) dropped—did it hurt performance or complicate kernels?
Answer:
Short answer: the paper does not give a single hard formula, but the design and wording make clear the practical choices and trade‑offs. The activations are quantized per token into a symmetric range $[-Q_b, Q_b]$ (no zero point) for implementation simplicity and negligible measured loss. In practice that implies using a per‑token scalar (most commonly max‑abs or a robust variant) applied to the token's activation vector; the symmetric scale is applied to the activations (so that quantized $Q/K/V$/hidden activations are centered about zero); numerical stability for softmax is preserved by computing attention logits/softmax in higher precision (or by dequantizing before softmax) and by keeping relative magnitudes through the chosen scaling; and per‑token scaling does not meaningfully harm model invariances in this architecture because components like RMSNorm and the linear layers absorb or cancel a per‑token scalar, which matches the paper's observation of negligible effect. Finally, the old BitNet choice to scale to $[0, Q_b]$ was dropped because a symmetric, zero‑centered range removes the zero‑point complexity and simplifies kernels and system integration—again with negligible performance impact.

Expanded explanation and technical grounding from the paper

1) How is the per‑token scale determined?
The paper only states that activations are “scaled to $[-Q_b, Q_b]$ per token” and does not give an explicit estimator. In quantization practice there are three common, reasonable choices:

- Max‑absolute per token: choose scale = $\max_i |x_i|$ for the token so the largest magnitude maps to $Q_b$. This is simple and exactly enforces the dynamic range.
- Robust (percentile) clipping: choose a high percentile (e.g. $99.9$th) of $|x|$ across the token to reduce outlier sensitivity, then clip and scale. This reduces quantization noise when outliers exist.
- EMA or running statistics: keep a running estimate of typical token magnitude (useful in streaming or pipelined systems), then use that per token (or per microbatch) to be stable across steps.

Which one the authors used is not specified; the paper emphasizes simplicity and system convenience, so max‑abs or a simple percentile/clipping scheme is the most likely. Any of these yields a single scalar per token that maps the token’s continuous activation vector into the symmetric $8$‑bit range.

2) Is scaling applied before/after attention softmax, and how is softmax stability kept?
The paper phrases scaling as “the activations are all scaled to $[-Q_b, Q_b]$ per token,” i.e. the activation tensors used throughout inference are quantized in this symmetric range. In a Transformer the relevant places are: (a) the hidden activations that feed the linear layers which produce queries/keys/values, and (b) the attention score computation $\text{softmax}(QK^{T} / \sqrt{d})$. Two practical points follow and are standard in quantized LLM implementations:

- The quantized activations (after per‑token scaling) are used as inputs to the int8/low‑bit linear kernels, but attention logits (the $QK^{T}$) and the softmax are typically computed with higher precision accumulation. That is, $Q$ and $K$ may be represented in low precision for storage/compute but their dot products should be accumulated in $\mathrm{FP16}/\mathrm{FP32}$ (or dequantized to FP prior to dot product) so logits have enough dynamic range and precision for a stable softmax.
- Numerical stability of softmax is preserved by the usual logit shifting (subtract max) and by using higher precision for accumulation and exponentiation. If $Q/K$ are stored quantized, kernels either compute integer dot products with FP accumulation or first dequantize to FP before softmax. The paper integrates with standard optimized runtimes (FasterTransformer, Ladder kernels) which provide these numerically stable ops.

In short: the symmetric per‑token scaling is applied to activations as stored and passed through linear layers, but the softmax internals are handled in sufficiently high precision (or by dequantization) so stability is unchanged compared to FP16 implementations.

3) Does per‑token scaling break invariances or cause position‑dependent artifacts?
A per‑token scalar multiplies the entire token vector; mathematically this is equivalent to a scalar factor applied to all channels of that token. Two important observations make this benign in the BitNet b1.58 design:

- Normalization: BitNet b1.58 uses RMSNorm (a per‑token normalization) and other LLaMA‑alike components. RMSNorm normalizes a token’s vector magnitude, so a global scalar per token is largely removed by the normalization that follows (or is equivalently absorbed into learned affine parameters). Thus many layerwise invariances cancel a pure scalar multiplier.
- Linear layers: a global scalar on activations can be absorbed by the next linear layer’s weights (or simply scale the resulting activations), so it does not change the direction of token vectors, only their amplitude, which is often handled by downstream normalization and nonlinearity.

So per‑token scaling can introduce a token‑dependent amplitude, but because Transformer blocks include per‑token normalization and learned linear mappings, this does not produce systematic sequence‑position artifacts in practice. The paper explicitly reports “negligible effects to the performance in our experiments,” which supports that no measurable degrading artifacts were observed. That said, compared to per‑channel or per‑tensor schemes, per‑token scaling is a different inductive choice: per‑token is more flexible (adapts to token‑by‑token amplitude variation) while per‑channel/per‑tensor enforces consistent scaling across tokens. If you worry about subtle position‑dependent behavior you can validate with controlled ablations (e.g., check logits/attention patterns vs. FP16 or run synthetic tests), but the architecture choices (RMSNorm, removal of biases) were made to make per‑token scaling safe.

4) Why was the earlier BitNet scaling to $[0, Q_b]$ dropped?
The paper states that they “do not scale the activations before the non‑linear functions to the range $[0, Q_b]$. Instead, the activations are all scaled to $[-Q_b, Q_b]$ per token to get rid of the zero‑point quantization. This is more convenient and simple for both implementation and system‑level optimization, while introduces negligible effects to the performance in our experiments.” Concretely, scaling to $[0,Q_b]$ requires a zero point (an offset) in integer representation, which complicates quantized kernels and memory layout; symmetric quantization around zero removes the need for a zero‑point and simplifies integer arithmetic (signed ints, symmetric clipping). Symmetric quantization also better matches activations centered on zero (post‑RMSNorm and common nonlinearities), avoids separately handling negative values, and makes bit‑wise/adder‑based kernels simpler and faster. The reason given in the paper is primarily engineering and system simplicity, not a large accuracy gain; they report negligible effect on performance while making implementation and system‑level optimization easier.

Summary
The paper chooses per‑token symmetric scaling primarily for engineering simplicity (zero‑point removal) and reports negligible impact on performance. The scale is a single scalar per token (likely max‑abs or a robust variant), softmax stability is preserved by performing logits/softmax in higher precision or with dequantization and standard numerically stable softmax tricks, and per‑token scaling is harmless in this architecture because normalization and linear layers absorb the scalar. If you need to reproduce or tweak the approach, start with per‑token max‑abs scaling and test percentile clipping or EMA for robustness; ensure attention dot‑products and softmax run with FP accumulation or dequantize $Q/K$ before softmax.

### Energy model assumptions behind the 71.4× arithmetic savings
Question:
Figure references claim 71.4× energy savings in matrix multiplication arithmetic on 7nm. Which per-operation energy costs were assumed for FP16 multiply/add versus INT8 add? A concrete equation or table with the constants used would clarify the derivation.
Answer:

The $71.4\times$ “arithmetic operations” saving is quoted with the citation pair [energycost, pokebnn], and the text and figure make clear that the $71.4\times$ is an arithmetic (ALU) energy comparison for matrix multiplication on a 7 nm process (i.e., it compares compute energy per op, not a full system energy number). The paper therefore treats arithmetic energy separately from memory/control costs; end‑to‑end energy claims are derived by combining that arithmetic saving with the relative share of time/energy spent in $nn.Linear$ (matrix multiplies) versus other blocks. Below I explain the assumptions implicit in that workflow, give the exact algebra the authors must have used, and show how to reproduce the $71.4\times$ and a full end‑to‑end estimate if you plug in constants from the cited energy models.

What the paper actually says and implies
- The $71.4\times$ factor is introduced in the “Energy” paragraph immediately after the latency/memory discussion and is attributed to the energy model in the cited works (those two refs are the source of the per‑operation numbers). The paper states “We focus mainly on the calculation for matrix multiplication … According to the energy model in [energycost, pokebnn], BitNet b1.58 saves $71.4$ times arithmetic operations energy consumption for matrix multiplication on 7nm chips.” That wording and the figure make it clear the comparison is arithmetic (ALU) energy for the matrix multiply kernel itself (FP16 multiply+add vs INT8 add), not a complete DRAM+SRAM+control energy accounting in that $71.4\times$ number.

Algebra / equation used to produce the arithmetic saving
Let $N$ be the number of scalar multiply–accumulate (MAC) operations required by the FP16 matmul. Typical matmul cost per element is one multiply + one add per MAC; for ternary/1‑bit schemes the computation can reduce to integer additions and sign operations. Define the per‑operation energies:

$E_{\text{fp16\_mul}} = $ energy per FP16 multiply  
$E_{\text{fp16\_add}} = $ energy per FP16 add  
$E_{\text{int8\_add}} = $ energy per INT8 add

Total FP16 arithmetic energy for the matmul (counting multiplies and adds):
$$E_{\text{FP16\_total}} = N \cdot (E_{\text{fp16\_mul}} + E_{\text{fp16\_add}})$$

Total BitNet arithmetic energy (assuming multiplication largely removed and replaced by INT8 additions; use $N'$ for the number of integer additions required by the ternary scheme — often $N' \approx N$ but could be lower if sparsity/packing is used):
$$E_{\text{INT8\_total}} = N' \cdot E_{\text{int8\_add}}$$

Arithmetic saving $S_{\text{arith}}$ is then
$$S_{\text{arith}} = \frac{E_{\text{FP16\_total}}}{E_{\text{INT8\_total}}} = \frac{N\cdot (E_{\text{fp16\_mul}} + E_{\text{fp16\_add}})}{N' \cdot E_{\text{int8\_add}}}.$$

If $N' = N$ (1:1 replacement of MAC by one INT8 add), this simplifies to
$$S_{\text{arith}} = \frac{E_{\text{fp16\_mul}} + E_{\text{fp16\_add}}}{E_{\text{int8\_add}}}.$$

This is the formula you should use to reproduce the $71.4\times$ number. The paper’s citation implies they used values from [energycost, pokebnn] for those $E_{\cdot}$ constants to get $S_{\text{arith}} \approx 71.4$ on a 7 nm process.

Why memory/control are excluded from the $71.4\times$ and how the paper handles end‑to‑end energy
The $71.4\times$ is explicitly for arithmetic energy only. Memory transfer (SRAM/DRAM), activation storage, caches, control flow, and other fixed costs are not included in that number. The paper does present “end‑to‑end energy cost for models with 512 tokens” elsewhere: those end‑to‑end numbers are formed by combining the arithmetic energy (with the $71.4\times$ reduction for the matmul portion) with other model components’ energy shares. Concretely the end‑to‑end energy $E_{\text{total\_model}}$ is:

$$E_{\text{total\_model}} = E_{\text{matmul}} + E_{\text{other}} = E_{\text{matmul\_arith}} + E_{\text{matmul\_mem}} + E_{\text{other\_arith}} + E_{\text{other\_mem}} + E_{\text{control}}.$$

In the paper they reduce $E_{\text{matmul\_arith}}$ by the $71.4\times$ factor for BitNet and leave the other terms either unchanged or scaled by bit‑width changes (for example, activations become 8‑bit so activation memory and activation arithmetic change accordingly). The dominant modelling assumption used in the paper is that matrix multiplies ($nn.Linear$) dominate overall energy as model size grows, so cutting matmul arithmetic energy by $71.4\times$ yields a large end‑to‑end reduction; but the precise end‑to‑end factor depends on the fraction $f$ of total energy that matmul arithmetic represented in the FP16 baseline. If in the baseline $ \text{matmul\_arith}$ is fraction $f$ of total energy, then

$$E_{\text{total\_bitnet}} = E_{\text{total\_fp16}} - f \cdot E_{\text{total\_fp16}} \cdot (1 - 1/S_{\text{arith}}) + \text{adjustments\_for\_activation\_and\_memory\_reduction}$$

so the end‑to‑end speedup $< S_{\text{arith}}$ and approaches $S_{\text{arith}}$ only if $f \to 1$.

Because the paper cites external energy models rather than listing constants, the correct way to reproduce the $71.4\times$ is to pull the per‑op constants from the cited refs and plug them into the formula above. Typical referenced quantities used in the community (Horowitz 2014 style numbers and later adjusted for 7 nm) give the following order‑of‑magnitude numbers (these are examples commonly used in papers; see the cited refs for the actual values the authors used):

- DRAM access (per 64‑bit word) $\sim O(100)\ \text{pJ}$  
- SRAM access (per 64‑bit word) $\sim O(5)\ \text{pJ}$  
- 32‑bit floating add/mul $\sim$ a few pJ  
- 16‑bit floating multiply/add $\sim 0.5$–$1\ \text{pJ}$ each (process dependent)  
- 8‑bit integer add $\sim 0.01$–$0.05\ \text{pJ}$ (much lower than FP ops)

If you use numbers of that order in the formula $S_{\text{arith}} = (E_{\text{fp16\_mul}} + E_{\text{fp16\_add}})/E_{\text{int8\_add}}$ you can easily get a multi‑order reduction. For instance, if $(E_{\text{fp16\_mul}} + E_{\text{fp16\_add}}) \approx 2.0\ \text{pJ}$ and $E_{\text{int8\_add}} \approx 0.028\ \text{pJ}$, then $S_{\text{arith}} \approx 71.4$. That shows why the ratio can be large: FP multiply cost is relatively expensive while simple integer adds at 8‑bit logic are very cheap on modern processes. But note these example constants are illustrative; the exact constants and the $71.4\times$ value should be checked against the two cited energy‑model papers the authors reference.

### Why does BitNet b1.58 match FP16 perplexity only from 3B and up?
Question:
Results suggest parity begins at around 3B parameters. Is there a known capacity or expressivity threshold for ternary-weight Transformers that causes underperformance at smaller scales? Did you attempt architectural tweaks (e.g., wider MLPs, more heads) at smaller sizes to recover performance, or is the gap mostly due to quantization noise being amortized at scale?
Answer:
Short answer: There is no mysterious single “ternary expressivity threshold” proved in the paper; the most plausible explanation the authors give (and that matches known quantization/overparameterization principles) is that quantization noise and representational loss from ternary weights are amortized only once the model is large enough and sufficiently redundant. The paper reports that with the same LLaMA-like configuration, training recipe and $100\ \text{B}$ tokens, BitNet b1.58 matches FP16 starting at $\approx 3\ \text{B}$ parameters; they do not report architecture-level redesigns (wider MLPs, more heads, etc.) to recover smaller-scale performance.

Why this happens (intuitively and technically)
- Quantization noise vs. model capacity. Ternary weights restrict each parameter to $\{-1,0,1\}$. For small models that are close to the minimum capacity needed for the task, that restriction removes degrees of freedom that were critical for representing fine-grained feature combinations. Larger models are overparameterized; they have redundancy so that many parameter configurations implement similar functions. That redundancy lets them “absorb” the coarse-grained quantization without as much hurt to loss or downstream metrics.
- Signal-to-quantization ratio improves with scale. As models grow, per-weight magnitudes and aggregated contributions to activations concentrate (by concentration-of-measure / law-of-large-numbers intuition). The scaling/absmean quantizer used in BitNet b1.58 (paper: divide by $\gamma = \text{mean}\,|W|$ before rounding) tends to preserve the dominant directions in large matrices better than in small ones, so quantization error becomes relatively smaller in larger layers.
- Effective expressivity: the ternary constraint is a hard nonlinearity on parameter space. Small networks have less capacity to reconfigure around that constraint, while large networks can reallocate representational burden (wider MLPs, more heads, or deeper layers implicitly) so the net function remains close to the FP16 baseline.
- The paper also keeps some elements full/higher precision (e.g., embeddings are full precision, activations are $8$-bit). Those design choices interact with size: the relative contribution of the full-precision parts is larger in small models, so the fractional effect of quantizing the linear layers is different by scale.
- Empirical scaling-law behavior. The authors claim a new scaling relationship where b1.58 becomes increasingly efficient and closer in performance to FP16 as size grows; this is consistent with other findings that aggressive quantization or pruning harms small models far more than large, overparameterized ones.

What the paper did and did not try
The paper trains BitNet b1.58 from scratch with LLaMA-like components (RMSNorm, SwiGLU, RoPE) and the absmean ternary quantizer, and compares models trained with the same config and token budget. It reports that parity with FP16 appears at $\approx 3\ \text{B}$, and that the gap narrows as size increases ($3.9\ \text{B}$ b1.58 even outperforms LLaMA $3\ \text{B}$). The paper does not describe experiments that specifically change micro-architecture at small sizes (e.g., increasing MLP width, increasing attention heads, or layerwise mixed precision) to close the small-model gap. So there is no reported evidence in this work that architectural tweaks were (or were not) effective at small scales.

Practical hypotheses and simple experiments you could try
If you want to probe whether the deficit is strictly capacity vs. an artifact of the quantizer/recipe, try these controlled experiments: (1) keep depth fixed but expand MLP hidden width for a $1$–$3\ \text{B}$ model (see if extra flop-budget recovers FP16 performance), (2) allow a small fraction of layers or parameters to remain higher precision (per-channel mixed precision) to localize critical capacity, (3) try per-row or per-channel learned scales instead of global abs-mean scaling, and (4) increase training tokens or apply distillation from the FP16 teacher. If gains appear from (1) or (2), that supports a capacity/expressivity explanation; if not, it suggests the quantizer or optimization dynamics at small scale are the main issue.

Broader connection
This phenomenon sits at the intersection of quantization theory and the modern overparameterization view: model robustness to aggressive compression (quantization/pruning) grows with size because large networks have many near-equivalent parameterizations. Similar effects have been observed for pruning and low-bit quantization in CNNs and Transformers: compression hurts small networks strongly, but large networks degrade gracefully.

Summary
The paper attributes parity beginning around $3\ \text{B}$ to the ability of larger models to accommodate the ternary constraint under the same training recipe; it does not report architectural interventions to rescue smaller models. The likely causes are quantization-induced information loss being cheaper to hide in overparameterized models and the specifics of the absmean ternary quantizer interacting more favorably with large-layer statistics. If you need to recover small-scale performance, try increasing effective capacity (wider MLPs), per-channel/learned scaling, hybrid precision, or teacher distillation—these are standard remedies consistent with the paper’s setup.

### How is rotary embedding handled with 8-bit activations and ternary weights?
Question:
Rotary positional embeddings are multiplicative/rotational transforms on Q/K. Given 8-bit activations and ternary weights, are rotary operations performed in higher precision (e.g., FP16) before re-quantization, or directly in INT8? If done in FP16, does this materially affect the claim of near-multiplication-free compute? What precision is used for attention score computation and softmax?
Answer:
Short answer: The paper does not explicitly specify every operator’s micro-precision, but the only implementation consistent with the paper’s claims and with common practice is a mixed-precision pipeline: the rotary rotation and the softmax/attention-scaling are done in higher precision (FP16/BF16 or FP32 accumulators) on dequantized activations, while the bulk matrix multiplies (the expensive nn.Linear-like work) are performed with the ternary/INT8 compute kernels. Doing the few FP multiplies for rotary and softmax is negligible compared to the cost saved by replacing the dense weight multiplications with addition-based ternary/INT8 kernels, so it does not materially break the “near-multiplication-free” claim for the dominant cost.

Why this is the most plausible reading from the paper
The paper states weights are ternary $\{-1,0,1\}$ and activations are 8-bit, and it repeatedly attributes most of the energy/latency savings to converting the heavy matrix multiplications into INT8 additions (and specialized 2-bit kernels). It also names rotary embeddings, softmax, RMSNorm and attention as part of the LLaMA-like components it keeps. But it does not claim every scalar op (rotary, softmax, scaling) is executed in integer arithmetic. Practically, most quantized LLM implementations (and the FasterTransformer codebase the authors used) keep a small set of ops in floating (FP16/BF16 or FP32 accumulators) for numerical stability and simplicity while moving the large-cost GEMMs to the quantized kernel. That matches the paper’s energy breakdown: “The majority of BitNet b1.58 is INT8 addition calculation,” i.e., the heavy FLOP reductions are in the big matmuls, not in tiny pointwise ops.

What typically happens to rotary in a quantized model
Rotary applies a small, elementwise linear rotation to $Q$ and $K$ (multiplication by sines/cosines or a $2\times2$ rotation). Two practical ways to implement this with 8-bit activations are (1) dequantize the 8-bit activation to FP16/BF16, apply the rotary (FP multiplies), then continue (re-quantize if needed) or (2) pre-scale the 8-bit representation and perform the small rotations in integer arithmetic (more complex, uncommon). The paper’s design choices (ease of integration with existing toolchains like FasterTransformer/llama.cpp and removing zero-point) favor option (1): perform rotary in FP16/BF16, then feed the rotated $Q$/$K$ to the attention path.

Why doing rotary in FP16 does not defeat the “near-multiplication-free” claim
Rotary and other pointwise ops are cheap relative to the cost of the big matrix multiplies. The paper’s performance and energy claims hinge on reducing the dominant cost (many-large-GEMMs) from FP16 multiply–adds to largely integer additions. A handful of FP16 multiplications per token position (the rotary rotations, layernorm scaling, the softmax and scaling by $\sqrt{d}$) are a negligible fraction of total arithmetic and memory traffic for large models, so the overall conclusion about large savings remains valid.

Precision for attention score computation and softmax
Attention score computation (the $QK^T$ dot-products) is another place where mixed precision is normally used. In quantized inference pipelines you often see:

- The linear projection producing $Q$ and $K$ can be computed by the quantized kernel, but the outputs are typically dequantized to FP16 or accumulated into a higher-precision accumulator (FP16/BF16 or int32 accumulators then converted to FP16) before computing $Q K^T$.
- The $QK^T$ matmul itself is done in a precision that preserves dynamic range: either FP16/BF16 or using int8 kernels with wider integer accumulators (e.g., int32) and then converted to FP16 for softmax.
- The softmax and the subsequent weighted sum (attention * $V$) are normally performed in FP16/BF16 (or FP32 if extreme stability is required).

The paper’s references to FasterTransformer and standard practice imply attention scores and softmax are computed in floating point (FP16/BF16) or use integer accumulators converted to FP16 for the softmax. Softmax is numerically sensitive (requires exponentials and normalization), so it’s overwhelmingly common to compute softmax in FP16/BF16 or FP32 rather than trying to do it directly in INT8.

Recommendation / how to verify
The paper integrates FasterTransformer and a 2-bit kernel from Ladder. Inspecting the actual inference kernels (their FasterTransformer config, ladder kernel, or the repo they integrated) will show whether rotary and softmax are done in FP16. If you need a strict “no FP multiplies ever” guarantee, that is not what this paper claims; instead it claims the dominant matmul work is converted to low-bit integer arithmetic, and a few pointwise FP ops remain.

Summary
The most consistent implementation is mixed precision: rotate $Q$/$K$ and compute softmax in FP16/BF16 (or use int accumulators converted to FP16), while the heavy linear layers are handled by ternary/INT8 kernels. This keeps numerical stability and integration simple and does not materially undermine the large computational and energy savings reported for BitNet b1.58.

### KV cache quantization: how do you maintain accuracy with 8-bit (and proposed 4-bit) caches?
Question:
The paper claims that reducing activations from 16 to 8 bits allows doubling context length, and even "lossless" compression to 4 bits for 1.58-bit LLMs is suggested as future work. 1) How are K and V cached quantization scales selected and updated across time steps? 2) What error control ensures negligible degradation at long contexts? 3) On what basis is 4-bit "lossless" considered feasible—do you rely on constrained dynamic ranges from ternary weights, and is there empirical evidence?
Answer:
Short answer: the paper uses per-token activation scaling before quantization and stores $8$-bit $K$/$V$ (with their per-token scales) so each timestep’s $K$ and $V$ are quantized using that token’s scale. This keeps quantization error local and bounded, which combined with the model’s redundancy and the modest precision reduction ($16\to8$ bits) yields negligible accuracy loss across long contexts. The suggestion of “lossless” $4$-bit caches is presented as future work and is plausible in principle (because BitNet’s ternary weights and constrained activation ranges reduce entropy), but the paper gives no empirical $4$-bit results — it’s a hypothesis that would require additional techniques (per-block scaling, entropy coding, or learned quantizers) and experiments to verify.

Detailed explanation and intuition, tied to the paper

1) How $K$ and $V$ quantization scales are selected and updated across time steps
BitNet b1.58 quantizes activations by scaling each token’s activation vector to a symmetric range. Concretely, before non-linearities activations are scaled per token to lie in $[-Q_b, Q_b]$ (the paper’s change from BitNet). That per-token scale is the normalization factor used to map floating activations into the integer range used for quantization. When a token is processed at time $t$, its computed key $K_t$ and value $V_t$ are quantized using the scale computed for that token and then written into the $K$/$V$ cache in quantized ($8$-bit) form. The scale (or equivalently the inverse scale) for that token must be stored alongside the quantized vectors so that, at later decoding steps, the dequantization back to the approximate floating-point representation is possible. In short: scale is computed per token at the time the token is produced, saved with its quantized $K$/$V$, and reused when those cached $K$/$V$ are read.

This per-token scaling is explicitly described in the paper’s activation quantization paragraph: activations are scaled to $[-Q_b,Q_b]$ per token, avoiding zero-points and simplifying implementation. The same idea applies to the $K$/$V$ that get cached.

2) What error control ensures negligible degradation at long contexts
There are three closely related reasons the paper reports negligible degradation when using $8$-bit cached $K$/$V$ over long contexts.

First, per-token scaling keeps the dynamic range of each cached vector small and well-adapted to that token. Quantization error is then a bounded, mostly zero-mean perturbation relative to that token’s magnitude, rather than being amplified by global range mismatch across many timesteps.

Second, attention uses inner products between queries and (dequantized) keys and then a weighted sum with values. If quantization introduces small additive noise in $K$ or $V$, the downstream effect is a (roughly) linear perturbation of logits and outputs. LLMs are empirically robust to small additive noise because their representations are highly redundant; small per-element errors average out in inner products and in the softmax. The paper demonstrates empirically (through perplexity and end-task evaluations) that reducing activations to $8$ bits — and caching those $8$-bit $K$/$V$ — produces negligible degradation when compared to $FP16$.

Third, the model design itself ($1.58$-bit ternary weights, RMSNorm, SwiGLU, etc.) and training from scratch with these quantization-aware choices helps preserve representation stability and makes the network less sensitive to activation quantization.

Operationally, error control relies on: (a) per-token scale computation and storage so dequantization is accurate for each cached item, (b) using an $8$-bit resolution which already provides sufficient fidelity for keys/values in modern LLMs, and (c) the model’s inherent robustness and the authors’ empirical validation over long contexts (they report doubled context lengths with the same memory budget and no meaningful performance loss).

3) Why $4$-bit “lossless” is considered feasible and what evidence exists
The paper says $8$-bit activations allow doubling the context and that this can “be further losslessly compressed to $4$ bits or even lower for $1.58$-bit LLMs,” but this is presented as future work rather than a demonstrated result. The argument for plausibility rests on two observations in the paper: BitNet’s ternary weights and per-token activation scaling substantially constrain the activation statistics (smaller effective dynamic ranges, sparser or low-entropy distributions), and the current experiments already show strong robustness at $8$ bits. Those facts make more aggressive compression conceivable.

However, the paper does not provide empirical $4$-bit $K$/$V$-cache results nor a concrete method that achieves “lossless” $4$-bit caching. In general, making $4$-bit caching effectively lossless would likely require additional techniques beyond naive uniform quantization: block- or channel-wise scaling, mixed precision (store some tokens or components at higher precision), learned quantizers, entropy coding, or run-length / variable-bit packing of low-entropy representations. ### How do SwiGLU activations behave under per-token 8-bit scaling?
Question:
SwiGLU involves elementwise products and nonlinearity. With per-token 8-bit quantization, how do you prevent saturation or information loss at the gates? Are intermediate products computed in higher precision and then requantized? Any calibration or learned scale parameters per channel to stabilize training/inference?
Answer:
Short answer: BitNet b1.58 prevents catastrophic saturation of SwiGLU gates mainly by using per-token symmetric 8-bit activation scaling (no zero point) and by training the network from scratch with the quantized recipe, rather than relying on a brittle post-hoc quantization. The paper does not introduce learned per-channel activation scales for SwiGLU nor does it explicitly state that the elementwise product is computed in higher precision; however, standard and practical implementations that match the paper’s description typically either perform the nonlinearity/multiplication in a higher precision accumulator (INT32/FP16) and then requantize, or dequantize to FP16/FP32 for the activation/GELU/SwiGLU step and requantize afterwards. Below I explain the intuition and how this connects to the paper.

Why per-token symmetric scaling helps
The paper explicitly says activations are scaled per token to the symmetric range $[-Q_b, Q_b]$ (no zero point). That means each token’s activation vector is linearly rescaled by a single per-token factor so the dynamic range of the activation that enters SwiGLU fits the representable $8$-bit symmetric range. Intuitively, this avoids two common failure modes: (1) a global/static scale that is too small will underflow and destroy gate contrast; (2) a global scale that is too large will saturate the clipping/rounding. Per-token scaling adapts the scale to the instantaneous activation magnitude, preserving relative contrasts across the two SwiGLU branches (the gating and the transformed branch) and reducing saturation at the inputs to the nonlinearity and the elementwise product.

SwiGLU structure and potential failure modes
SwiGLU does elementwise multiplication between a gated branch (usually a sigmoid-like gate) and a transformed branch (Swish/GELU applied to another linear projection). If both branches are low-precision, two problems can happen: the nonlinearity can lose its smooth shape when inputs are coarsely quantized, and the elementwise product can underflow/overflow. The per-token symmetric scaling directly addresses the quantization dynamic range for both branches simultaneously, so the gate retains usable resolution and the product still carries useful information.

What the paper states about intermediates and training
The paper reports training from scratch with $1.58$-bit weights and $8$-bit activations and describes the per-token symmetric activation scaling. It does not report learned per-channel activation scales, nor does it state explicitly that intermediate elementwise products in SwiGLU are computed in higher precision. Instead, the design choices they emphasize are: (a) absmean-based weight quantization to $\{-1,0,1\}$; (b) per-token symmetric activation scaling (no zero point); and (c) training the quantized model end-to-end so the model can learn to operate within the quantized dynamic ranges.

Practical and hardware-aware implementations (consistent with the paper)
Although not spelled out in the paper, there are two common and compatible implementation patterns you should assume when reasoning about SwiGLU in an $8$-bit-activation system like BitNet:

1) Compute linear matmuls in low-bit kernels (their $2$-bit/INT8 kernels), accumulate in higher-bit integer (INT32) or FP16, then apply the nonlinearity and elementwise product in that higher precision before requantizing. This approach preserves the shape of the nonlinearity and avoids catastrophic rounding in the product, and it is consistent with the paper’s usage of optimized low-bit kernels together with overall $8$-bit activations.

2) Alternatively, dequantize the two SwiGLU branches to FP16/FP32, apply the activation (GELU/Swish) and elementwise product there, then requantize the result back to $8$-bit for downstream layers. This is slightly more expensive but keeps the nonlinear and multiplicative math accurate; it is compatible with the paper’s claim of $8$-bit activations while recognizing that some intermediate higher-precision compute is a practical necessity on current hardware.

Both choices are consistent with the paper’s statement that the model uses $8$-bit activations (scaled per-token) and highly quantized weights while leveraging optimized low-bit inference kernels. The paper’s performance numbers imply that either the network learned to be robust under these quantization choices or that the implementation used higher-precision intermediates where it matters.

About calibration or learned scales
The paper uses absmean-based scaling for weights (a global-ish scale computed from the weight matrix) and per-token scaling for activations. It does not report per-channel learned activation scales or explicit calibration steps for activations entering SwiGLU. Instead, the combination of per-token activation scaling and training-from-scratch appears to be their stabilization mechanism. This is a different design point from many post-training quantization works that rely on per-channel scales or learned scale/zero-point parameters.

Takeaway and broader context
Per-token symmetric scaling is the core stabilization mechanism described in the paper for $8$-bit activations feeding nonlinearities like SwiGLU. In practice, to avoid final precision loss you normally compute the nonlinearities and elementwise products in a higher accumulator precision (or dequantize to FP16/FP32), then requantize the outputs; the paper doesn’t contradict that approach. Finally, training the model end-to-end with the quantized weight/activation recipe lets the network adapt its internal statistics and avoid pathological saturations that would plague naive post-training quantization.

### Does ternary quantization encourage structured sparsity that kernels can exploit?
Question:
With \{−1, 0, 1\} weights, zeros may appear frequently. Do your trained models exhibit significant block or channel-level sparsity that could be exploited by sparse kernels to further reduce compute/memory bandwidth? If so, what sparsity patterns and densities are observed across layers and model sizes?
Answer:
Short answer: The paper does not claim or report meaningful block- or channel-level sparsity that sparse kernels could exploit. The ternary design (weights in $\{-1,0,1\}$) produces many zeros, but those zeros are produced per-weight by a simple round-and-clip quantizer and are therefore largely unstructured by construction. The authors use dense 2-bit kernels (e.g., Ladder) for speed/memory gains rather than sparse-block kernels.

Why this is the case (intuitive + technical): BitNet b1.58 quantizes each weight matrix by scaling with the matrix mean absolute value
$$
\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|
$$
and then applying
$$
\widetilde W = \mathrm{RoundClip}\!\big(\tfrac{W}{\gamma+\epsilon},-1,1\big).
$$
This is a per-matrix scalar thresholding and rounding operation: each weight that after scaling lies near 0 is mapped to 0, otherwise to $\pm 1$. That process creates sparsity at the individual-weight level (i.e., unstructured zeros where small weights are rounded to 0), but it does not include any mechanism that encourages contiguous blocks, entire channels/rows/columns, or structured groups of weights to go to zero. In other words, zeros are the byproduct of magnitude-based rounding, not the result of a structured pruning objective.

What the paper reports and what it does not: The paper emphasizes that adding the 0 value helps “feature filtering” and improves modeling capability, and it shows system-level gains by using low-bit representations and a 2-bit kernel; but it does not give layer-wise or block-wise zero rates, nor does it present statistics about channel/block sparsity patterns or densities across layers and model sizes. The reported runtime/memory/throughput/energy gains come from bit-width reduction and optimized dense low-bit kernels, not from exploiting structured sparsity.

Practical implications for sparse kernels: Because the zeros are created independently per weight by rounding, they will typically be randomly distributed across the matrix, which is difficult for sparse-block or channel-sparse kernels to exploit efficiently. Sparse inference engines gain most when sparsity is structured (e.g., entire rows/columns, blocks, or channels zeroed) so the compute/communication patterns can be simplified; unstructured sparsity usually requires irregular sparse kernels with lower hardware efficiency. Therefore, out-of-the-box BitNet b1.58 models are unlikely to yield large additional speedups from structured sparse kernels unless you explicitly train or fine-tune to induce structure.

If you want structured sparsity that kernels can exploit: use targeted methods during training or fine-tuning. Examples that are consistent with the paper’s setup would be (a) adding group-L1 or block-sparsity regularizers, (b) applying structured pruning (channel/row/column pruning) and then re-quantizing/finetuning in the ternary regime, or (c) using sparsity-aware distillation where student weights are encouraged to zero out whole channels/blocks. After such training you should report per-layer metrics such as per-channel zero-rate, block-zero-rate for chosen block sizes, and the distribution of nonzero counts to judge kernel applicability.

How to measure this for your models (recommended checks): compute for each weight matrix and each candidate block size (e.g., $4\times4$, $8\times8$) the fraction of blocks that are entirely zeros, the fraction of zeroed channels/rows/columns, and plot histogram of per-row/column sparsity. Also compare these statistics across layer types (attention projections vs. MLP weights) and model sizes (3B/7B/13B/70B) to see trends. If you find high whole-block or whole-channel zero rates, then sparse-block kernels may be worthwhile.

Conclusion: BitNet b1.58 does introduce many zeros because of ternary rounding, but the paper does not demonstrate structured sparsity exploitable by sparse kernels. The zeros are primarily unstructured per-weight zeros; to get hardware-friendly structured sparsity you would need to add structure-inducing training (pruning/regularization/distillation) and then measure the per-layer/block/channel sparsity statistics.

### What are the implications for MoE routing and communication with 1.58-bit weights?
Question:
The paper argues MoE becomes more deployable due to reduced memory and activation transfer costs. In a concrete MoE setup (e.g., top-2 gating with N experts), how would you quantize and transmit activations and expert weights? Are gating logits/dispatch indices also quantized, and does quantization affect load balancing or expert specialization?
Answer:
Short answer: use the paper’s $1.58$-bit recipe for expert weights (ternary $\{-1,0,1\}$) and $8$-bit per-token activations as the default on-the-wire representation; keep gating computation either in slightly higher precision ($FP16/BF16$) or carefully quantized ($int8$ with scale) so top-2 decisions stay stable; send compact dispatch indices (small integers/bitmasks) and per-token scale factors alongside the $int8$ activations. With these choices you get large communication savings and usually only mild effects on load balancing or specialization — but you should treat gating logits with care because quantization noise can flip near-ties and so shift expert loads or specialization patterns.

Why — intuition and practical pipeline
The paper’s core quantization choices are: weights are ternary $\{-1,0,1\}$ and activations are $8$-bit, scaled per token to a symmetric range $[-Q_b, Q_b]$. That immediately implies two useful properties for MoE: expert weight storage is very small and activations to be routed are tiny compared to $FP16$, so the dominant network cost (sending token activations from router to selected experts) is reduced by roughly the ratio of bit-widths.

A practical MoE dispatch pipeline consistent with the paper is:

1. Gating: compute gating logits from the (possibly quantized) pre-attention token representation. To avoid destabilizing top-2 selection, compute gating in $FP16/BF16$ if possible. If you must quantize gating, do it as $int8$ with a known scale per token (or per batch) and perform softmax in higher precision (or with dequantized accumulation). The reason is that top-2 selection is sensitive to small differences in logits: quantization noise can change who wins when logits are close.

2. Top-2 selection & indices: select two experts per token using the gating logits. Transmit compact dispatch metadata: an expert ID pair and small integer slots (capacity index) per token. These are naturally small ($\log_2(N)$ bits per expert ID plus some bits for capacity slot) and should be sent in integer form (no need for FP).

3. Activation transmission: send the token activation vectors to the selected experts as $8$-bit signed integers (the paper’s activation scheme: per-token symmetric scaling to $[-Q_b, Q_b]$). Also send the per-token scale factor (a small $FP16$ or even $FP8$ scalar) so the receiving expert can dequantize or compute in integer arithmetic using that scale. Because each token goes to two experts in top-2 routing, you either send two copies or use a multicast if network supports it.

4. Expert computation: experts hold ternary weights $\{-1,0,1\}$ so matrix multiplies can be implemented as additions/subtractions and masked accumulations. Experts can multiply the $int8$ activations by ternary weights in integer arithmetic; if you preserve the per-token scale, you can carry out integer accumulation and then multiply by the scale at the end (or keep everything quantized through activation outputs if downstream supports it).

5. Return/merge: experts return their outputs as $8$-bit activations plus scales (or accumulate locally and send back a dequantized $FP16$ result if merging requires higher precision). The router merges the two expert responses (weighted by gating probabilities) — merging is safer if done in $FP16/BF16$ or using dequantized accumulators to avoid precision loss when combining many tokens/experts.

Does one quantize gating logits / dispatch indices?
Dispatch indices are integer by nature and should be transmitted as small integers or bitmasks; there is no benefit to representing them in FP. Gating logits, however, are sensitive and benefit from higher precision. The paper does not explicitly prescribe gating precision for MoE, but given it keeps activations at $8$-bit while weights are ternary, the conservative and practical choice is to compute gating logits in $FP16/BF16$ (or compute in $int8$ but do softmax in $FP16$ after dequantizing). This avoids flipping top-2 selections due to quantization noise.

How quantization affects load balancing and expert specialization
Quantization can affect routing in two ways. First, it changes the inputs the gate sees (if gating uses quantized activations), and second, it can introduce numerical noise in the softmax/logit comparisons. In practice:

- If gating is computed in $FP16/BF16$ and only the routed activations are quantized to $int8$ for transmission, load balancing is almost unchanged: the gate makes the same expert choices and expert specialization is preserved because experts still see essentially the same logical input (dequantized or scaled $int8$).

- If gating itself is aggressively quantized (e.g., low-bit logits without careful scaling), small differences near decision boundaries can flip top-2 winners. That will change the empirical expert load balance and can gradually alter expert specialization during any online or continual learning scenario. Even in pure inference, repeated flips change which data each expert sees and so could change how the system behaves from run to run (if random tie-breaking differs).

Mitigations and practical tips
If you want maximal communication savings while keeping routing stable, the simplest reliable recipe is: keep gating in $FP16/BF16$; transmit activations as $int8$ with a per-token symmetric scale; keep weights ternary on the expert side; return outputs as $int8$ (with scale) and perform the weighted merge in $FP16$ after dequantizing or with integer accumulation plus scaling. If you need to quantize gating too (for extreme edge deployments), calibrate the gating quantization scales on representative data, increase the softmax temperature slightly to reduce sensitivity to tiny numeric perturbations, and add or retain a small load-balancing regularizer (capacity factor or auxiliary loss) so that noisy flips don’t create pathological imbalances.

Bandwidth and memory impact (back-of-envelope)
Replacing $FP16$ activations with $8$-bit activations cuts activation bandwidth by ~2x. Replacing expert weights with ternary storage gives an even larger drop in DRAM bandwidth and device memory. For a top-2 router you still send two activation vectors per token, so per-token network bytes = $2 \times D \times 8$ bits (plus scale and indices), where $D$ is token hidden dimension. If you can compress scales to $FP16$ and indices to a few bits, the additional overhead is negligible compared to the activations themselves.

In short: the paper’s $1.58$-bit design naturally translates to MoE by keeping expert weights ternary and routed activations as $8$-bit (with per-token scales). Treat gating with higher precision or carefully quantized $int8$ with calibration to avoid destabilizing top-2 choices. Doing so yields large reductions in memory and communication with only modest risk to load balancing and specialization, and any residual risks can be addressed by calibration, temperature tuning, or lightweight load-balancing regularizers.

### Storage vs compute precision: what precision is used on disk, in RAM, and in the kernel?
Question:
To deploy b1.58, models might be stored in compressed formats on disk, unpacked into GPU memory, and then processed by specialized kernels. Could you specify the precisions at each stage (disk, host RAM, device global memory, shared memory/registers) and the associated bandwidth/compression strategies? This would clarify practical gains vs theoretical 1.58 bits/weight.
Answer:
Short answer: the paper’s weights are conceptually 1.58 bits/weight (ternary $\{-1,0,+1\}$), activations are 8‑bit; but the end‑to‑end precisions and bandwidth seen in a real system depend on how you pack and which kernel you run. The paper does not mandate a single on‑disk / in‑RAM layout, but it describes the algorithmic choices (ternary weights, per‑token activation scaling to $[-Q_b,Q_b]$, and use of a 2‑bit kernel from Ladder). Below I summarize the plausible, paper‑consistent precisions and common system choices at each stage, the compression/packing strategies that realize the 1.58‑bit claim in practice, and where practical losses vs the ideal occur.

Disk (persistent storage)
The model semantic format is ternary weights (values in $\{-1,0,1\}$) plus a per‑tensor scale $\gamma$ (absmean). To approach 1.58 bits/weight on disk you must pack many ternary values into bytes and optionally compress further:
- Minimal representation: bit‑pack two bits per weight ($00,01,10$ for the 3 values; one unused code) → 2 bits/weight raw. This is what the paper’s use of a “2‑bit kernel” implies is supported.
- To approach 1.58 effective bits/weight you can exploit the extra structure (sparsity of zeros and entropy of symbol frequencies) with run‑length encoding, bitmap + indices for zeros, or entropy coding (e.g., arithmetic or Huffman). Those give stored sizes closer to the theoretical 1.58 bits/weight if symbol distribution and sparsity are favorable.
The paper does not prescribe an exact disk format; it only requires saving the quantized ternary matrix and its $\gamma$ (and any per‑block metadata if you use block scaling).

Host RAM (process memory before GPU upload)
There are two common choices consistent with the paper:
1) Keep weights packed in the host process (2‑bit packed, or compressed) and transfer the packed bytes to the device (preferred for bandwidth).
2) Unpack to a byte‑aligned integer representation (e.g., int8 per weight with values -1,0,1) for simpler CPU-side ops or for a driver that expects byte elements.
The paper’s memory/latency advantages assume keeping the footprint compact (packed) across host memory and into device memory whenever the kernel supports it. Activations and embeddings: activations are stored as 8‑bit integers (per the paper: “8‑bit activations”), while embeddings are kept full precision (FP16/BF16), as stated.

Device global memory (GPU DRAM)
The paper reports experiments using a “2‑bit kernel from Ladder” integrated into FasterTransformer. That implies device global memory typically stores weights in a packed 2‑bit layout (one byte contains $4$ weights) or a blockwise 2‑bit layout compatible with the kernel. Practically:
- Weights: packed 2‑bit (or a block‑packed + per‑block scale $\gamma$), or in some implementations unpacked to int8 for simpler kernels. The paper’s memory reductions (e.g., 3.55× less GPU memory) assume packed/low‑bit storage and kernels that consume it directly.
- Activations/KV caches: 8‑bit int (paper explicitly: 8‑bit activations). The paper also notes activations can be losslessly further compressed to 4 bits in future work, but experiments use 8‑bit.
- Embeddings / any components kept full precision: FP16/BF16 in global memory (paper: “embedding remains full precision”).

On‑chip (shared memory / registers / compute)
At kernel runtime the layout depends on the kernel implementation:
- Ladder / specialized 2‑bit kernels typically read packed 2‑bit weights and perform bitwise/unpacking operations into registers or use vectorized integer arithmetic. The arithmetic is mostly additions of integer values (paper: “matrix multiplication of BitNet only involves integer addition”).
- Common practical implementation: weights may be unpacked into int8 lanes in registers or shared memory and then summed/accumulated into int32 accumulators, followed by scaling by $\gamma$ (and possibly conversion to FP16/BF16 for following layers). So compute precision often is int8 (or bit‑ops) for weight×activation, accumulation in int32, then cast to FP16.
- Activations are 8‑bit inputs to these kernels; accumulators and final outputs may be int32 → FP16/FP32 depending on the kernel and whether downstream ops expect floating point.

Bandwidth and compression strategies (how practical gains are realized)
The paper’s claims hinge on reducing both capacity and bandwidth costs. The system techniques consistent with the paper are:
- Bit‑packing: store weights at 2 bits/weight in bytes (4 weights/byte). This cuts raw transfer size by 8× relative to FP16 (16 bits → 2 bits).
- Blockwise scaling: store a small per‑block float scale $\gamma$ (e.g., one FP16/FP32 scale per $256$ or $1024$ weights). That overhead is tiny and already included in the paper’s cost accounting.
- Sparsity exploitation: since ternary includes zeros, store a bitmap or run‑length code for zeros to reduce further toward 1.58 bits/weight. This is optional in the paper but explicitly enabled by the ternary design.
- Kernel‑native consume: keep the packed layout when uploading to GPU and call a kernel (the Ladder 2‑bit kernel referenced) that consumes packed data directly, avoiding unpack→pack overheads.
- Activation scaling: activations are quantized per token to $[-Q_b,Q_b]$, eliminating zero‑points and simplifying kernel math and memory layout (paper statement).

Where the theoretical 1.58 bits vs practical differ
The paper’s “1.58 bits/weight” is an information/representation figure for ternary weights with observed sparsity / symbol frequencies. Practical system costs deviate for these reasons:
- If you use a simple 2‑bit packed layout everywhere, you pay 2 bits/weight rather than 1.58. Getting to 1.58 requires entropy or sparsity compression which adds CPU/GPU decompression cost.
- If the GPU kernel cannot operate on packed 2‑bit data, you must unpack to int8 on upload, temporarily using 8 bits/weight in device memory/bandwidth and incurring unpack cost; the paper’s reported speed and memory savings assume kernels that can handle low‑bit packed formats (they used a 2‑bit Ladder kernel).
- Per‑block scales and metadata increase overhead slightly; for large blocks this is negligible.
- Activations/KV caches: the paper reduces them to 8 bits → halves memory relative to 16‑bit FP. If you keep KV caches at FP16, the end‑to‑end memory gains are smaller than the pure weight compression number.

Practical recommended pipeline consistent with the paper to realize near‑claimed gains
Store weights on disk packed (2‑bit) and optionally entropy‑compress for archival. Keep them packed in host RAM and DMA to GPU as packed blocks. Use a kernel that consumes packed 2‑bit weights (like the Ladder 2‑bit kernel used in the paper) and 8‑bit activations, accumulate in int32 and rescale with stored $\gamma$ before casting to FP16 for downstream ops. Keep embeddings FP16. If you can exploit zero sparsity (bitmap + packed nonzeros), you can reduce stored bits toward 1.58 at little extra runtime cost if the kernel supports sparse decode.

Final practical note
The paper documents training and inference results using a 2‑bit kernel and 8‑bit activations and reports memory/latency/energy reductions under those choices. It does not give one mandatory on‑disk encoding; the exact bits/weight seen by a deployed system equals the chosen packing and whether the kernel directly consumes packed data. The theoretical 1.58 bits/weight is achievable as an average compressed storage number, but the real runtime bandwidth equals the on‑wire format the kernel expects (commonly 2 bits/weight for the experiments in the paper).

### How does adding the 0 state compare to scaled binary weights (±α) in practice?
Question:
Some 1-bit methods use binary weights with a learned or estimated per-channel/per-tensor scale \(\alpha\) to recover dynamic range. Your approach uses ternary \{-1,0,1\} with an absmean normalization. Did you compare against binary-with-scale baselines of similar complexity? Where does ternary help most (e.g., attention vs MLP), and is the gain mainly from induced sparsity or better approximation of small-magnitude weights?
Answer:
Short answer: the paper does not report a direct head-to-head with a binary-with-scale ($( \pm \alpha)$) baseline of matched complexity; instead it argues and demonstrates that adding a zero state with a simple absmean normalization (ternary $\{-1,0,1\}$) produces practical gains that let BitNet b1.58 match FP16 at scale. Intuitively, the benefit of the zero state is twofold: it explicitly filters small-magnitude weights (improving approximation where many weights should be near zero) and induces sparsity that can be exploited by hardware/software (reduced effective compute and noise). Both effects help, and which dominates depends on the layer type and distribution of weights.

Why the paper chose ternary absmean rather than $\pm \alpha$-binary
The paper’s quantizer scales each weight matrix by its average absolute value
$$
\gamma = \frac{1}{nm}\sum_{ij}|W_{ij}|
$$
and then rounds/clips to $\{-1,0,+1\}$. This is a single, simple per-matrix normalization (no learned per-channel scale). The rationale shown in the text is pragmatic: it’s simple to implement, avoids per-channel learned parameters and zero-point complications in activations, and enables an explicit $0$ state for feature filtering. The results (matching FP16 from 3B and large runtime/memory/energy wins) are presented as evidence that this simple ternary scheme is sufficient at scale.

How that compares, conceptually, to $\pm \alpha$ binary
A $\pm \alpha$ binary quantizer represents weights as $\alpha\cdot\operatorname{sign}(W)$ (with $\alpha$ learned or estimated per tensor/channel). That recovers dynamic range but forces every weight to be nonzero; small weights are mapped to $\pm \alpha$ rather than $0$. The main trade-offs are:
- Approximation: $\pm \alpha$ can preserve magnitude via $\alpha$, but it cannot represent that a true optimal weight should be essentially zero. Ternary can approximate small weights better by mapping them to $0$, reducing bias for parameters that should be suppressed.
- Sparsity: ternary produces literal zeros, which can be exploited by sparse computation or by reduced noise in aggregated dot-products; $\pm \alpha$ gives no sparsity.
- Complexity: per-channel learned $\alpha$ adds parameters and optimization complexity; the paper’s absmean is cheaper (no extra learned $\alpha$) and stable in training.

Where ternary helps most (attention vs MLP)
The paper does not include layerwise ablations, but you can reason from how weights behave in transformers. MLP (feedforward) layers often have many small-magnitude parameters that act as fine-grained feature selectors; inserting a zero state helps these layers by letting truly small weights vanish rather than being forced to a uniform $\pm$ scale. Attention projection matrices (Q/K/V/O) can be more sensitive to precise scaling because they directly shape attention scores; there the per-tensor scale of $\pm \alpha$ can help preserve relative magnitudes. Empirically in many quantization studies (and consistent with the paper’s design choices emphasizing feature filtering), adding a zero state tends to favor MLPs and projection matrices where sparsity/thresholding reduces noise, while scaled-binary can be competitive where preserving global scale matters most. The paper’s overall success (matching FP16 from 3B) suggests ternary with absmean is sufficient across the network at their scale and training recipe.

Is the gain mainly from induced sparsity or better approximation of small weights?
Both mechanisms contribute. The absmean + rounding explicitly thresholds small weights to $0$, so part of the gain is improved approximation of the true weight distribution (many weights should be near zero). The resultant sparsity also reduces the effective interference/noise in matrix products and can be exploited by system kernels (the paper reports large latency/memory/energy benefits). The paper emphasizes “explicit support for feature filtering” as an advantage of having $0$ in the alphabet, which highlights the modeling/approximation benefit; the runtime/energy sections highlight the systems benefit of sparsity.

What’s missing / recommended ablations
Because the paper does not present a matched $\pm \alpha$ baseline, a fair experimental comparison you could run is: (a) binary-with-per-matrix or per-channel learned $\alpha$ trained from scratch with the same architecture and training tokens, (b) the paper’s ternary absmean, and (c) hybrid variants like per-channel absmean or learned ternary thresholds. Important diagnostics are validation perplexity, per-layer nonzero density, distribution of quantization error, and a layerwise swap experiment (ternary in MLPs vs attention only). Measuring where the nonzeros concentrate (MLP vs attention, early vs late layers) will show whether gains come from sparsity patterns or better magnitude approximation.

Practical takeaway
The paper shows that a very simple ternary quantizer (absmean + RoundClip to $\{-1,0,1\}$) is enough to reach FP16 parity at scale and to unlock major system-level savings. Conceptually, ternary is superior to plain $\pm \alpha$ when many true weights are near zero or when explicit sparsity can be exploited; $\pm \alpha$ keeps magnitude but cannot suppress small unrelated weights. For a definitive claim about relative performance one should run the matched $\pm \alpha$ baselines the paper didn’t report and do layerwise ablations to isolate sparsity vs approximation effects.

### Do residual connections accumulate quantization error, and how is it controlled?
Question:
In Transformers, residual connections can amplify quantization noise across layers. With 8-bit activations and ternary weights, do you observe drift or instability in deep stacks? Are there normalization tweaks (e.g., post-norm RMSNorm parameters in higher precision) or periodic rescaling to keep residual streams within safe dynamic ranges?
Answer:
Short answer: Yes, in principle residual connections can accumulate quantization noise, but BitNet b1.58 controls that in several concrete ways so that you do not observe problematic drift or instability in deep stacks (empirically it matches FP16 baselines from 3B up). The paper does not report adding ad‑hoc “periodic rescaling” or higher‑precision norm parameters — instead stability is obtained by the quantization recipe plus architecture / training choices.

Why accumulation is a concern (intuitive). Each residual add injects whatever rounding/quantization error is present in the layer outputs; if those errors are biased or the residual stream grows in magnitude layer by layer, errors can amplify and the activations can leave the dynamic range of the low‑bit format, causing drift or divergence in very deep networks.

How BitNet b1.58 prevents that (technical, from the paper). First, weights are constrained to $\{-1,0,1\}$ after an explicit scaling step: each weight matrix is divided by its mean absolute value $\gamma = \frac{1}{nm}\sum_{i,j}|W_{ij}|$ then rounded/clipped. That absmean scaling keeps the effective weight scale predictable and prevents uncontrolled per‑layer gain that would amplify residuals. Second, activations are represented in 8 bits but are explicitly scaled per token to the symmetric range $[-Q_b, Q_b]$ (no zero‑point). Per‑token symmetric scaling reduces dynamic‑range mismatches across tokens and layers, so the residual stream stays within the representable range layer to layer. Third, the model uses RMSNorm (the LLaMA‑alike components) and removes biases; RMSNorm is scale‑stabilizing and bias‑free layers remove a persistent additive offset that could otherwise accumulate. Finally, the model is trained from scratch under these quantized constraints, so the optimizer and training dynamics adapt the learned magnitudes and activations to be compatible with ternary weights + 8‑bit activations rather than relying on post‑hoc quantization of an FP16 trained net.

Empirical evidence in the paper. The authors report matching perplexity and downstream performance starting at 3B, and successful scaling to 70B models with large speed/memory/energy gains. These empirical results indicate no practical drift/instability across deep stacks under their recipe.

What the paper does not do (and practical notes). The paper does not state that they used higher‑precision RMSNorm parameters, nor that they inserted periodic rescaling/renormalization hooks in the residual stream. Those are reasonable additional controls in other low‑precision work, but here they were unnecessary given: (1) absmean weight scaling, (2) symmetric per‑token activation scaling, (3) RMSNorm and bias removal, and (4) training from scratch under the quantized scheme.

If you are experimenting beyond the paper. If you still worry about residual accumulation in other settings (e.g., post‑training quantization of a pretrained FP16 model, or more aggressive activation quantization), common remedies are: keep normalization layers in full or higher precision, apply per‑layer learnable scaling factors (layer scale) initialized small, periodically renormalize residual norms, or fine‑tune under quantization so weights learn to avoid gain buildup. The paper’s empirical approach shows those extra measures were not required for their $1.58$-bit training recipe.

Summary: accumulation is a real theoretical risk, but BitNet b1.58 prevents it through absmean weight scaling, symmetric per‑token activation scaling, RMSNorm + bias removal, and training-from-scratch in the quantized regime — and the reported results show no instability or drift in deep models.

### Is there any calibration or post-training fine-tuning after from-scratch quantized training?
Question:
After training from scratch with 1.58-bit weights, did you run any short calibration or post-finetuning pass (e.g., collecting activation ranges, adjusting per-layer scales, or distillation on a held-out set) to improve final inference performance? If not, would such a step further narrow any remaining gaps at sub-3B scales?
Answer:
Short answer: No — the paper reports training BitNet b1.58 entirely from scratch with the ternary weight quantization (the absmean RoundClip scheme) and 8-bit activations, and does not describe any separate post-training calibration, activation-range collection, per-layer re-scaling pass, or distillation-based fine-tuning after the main pretraining. The activation handling they mention (per-token scaling to $[-Q_b,Q_b]$ and avoiding a zero-point) is part of the training/inference quantization design, not a separate calibration/fine-tune step.

Why that matters and what you could try
Intuitively, the authors built the quantization into the training loop so the model learned to operate with ternary weights and 8-bit activations throughout pretraining. That typically reduces the benefit you’d get from a later calibration pass, because the network has already adapted its internal representations to the constrained weight/activation formats. For the sizes they report, the trained 1.58-bit models already match FP16 baselines from roughly 3B up, which suggests the from-scratch quantized training is sufficient at those scales.

That said, for sub-3B regimes (where the paper admits gaps exist) a short post-training intervention could plausibly help. Practical techniques that are consistent with the paper’s setup and that you could try are:

- Activation-range calibration: run a small held-out batch through the model in inference mode to collect per-layer (or per-channel) activation statistics and set quantization scales. This is cheap and sometimes closes small gaps when activations at inference differ from training-time statistics.
- Per-layer/per-channel scale adjustment or bias correction: learn tiny multiplicative scales (or additive corrections) for weights/activations on a small calibration set (e.g., a few hundred to few thousand examples) while keeping the main weights frozen. This is low-cost and often stabilizes layer outputs after quantization.
- Short quantization-aware fine-tuning: perform 1–5 epochs of LM fine-tuning (very low learning rate, frozen or lightly regularized embeddings) with the quantized operators in the loop. This lets the model re-adapt any remaining mismatches.
- Distillation from an FP16 teacher: run a brief distillation pass (student is the quantized model) with a teacher loss (logits/MSE) on a modest dataset; distillation often helps smaller models and can correct systematic output shifts.
- Techniques from post-training quant methods (AdaRound, GPTQ-style rounding tweaks, LSQ-like learned scales) adapted to ternary weights: instead of hard rounding, optimize rounding decisions/scales on a small calibration set to reduce reconstruction error.

Expected effect sizes and trade-offs
A calibration-only pass (collecting ranges and setting scales) is nearly-free and can give small but reliable improvements when activations shift between training and inference. Short fine-tuning or distillation will typically give larger gains, especially for smaller models (<3B) that have less overcapacity to absorb quantization noise. The trade-off is compute/time: a few epochs of low-LR fine-tuning or a distillation pass costs more than calibration but is still far cheaper than full pretraining.

Practical recipe to try
If you want to experimentally test this on a sub-3B BitNet b1.58 model, a pragmatic path is: (1) run activation-range calibration with a few thousand in-distribution tokens to set per-layer scales; (2) if gaps remain, run 1–3 epochs of quantization-aware fine-tuning on the same held-out corpus with a small LR (e.g., $1\times10^{-5}$–$5\times10^{-5}$) and monitor perplexity and downstream zero-shot metrics; (3) if further improvement is needed, add a short distillation loss from the FP16 teacher.

Summary
The paper did not report any post-training calibration or fine-tuning beyond the built-in quantized training and the activation scaling scheme described. Nevertheless, for smaller models where a residual gap remains, light-weight calibration, learned-scale adjustment, short QAT fine-tuning, or distillation are all plausible, low-cost ways to further narrow performance gaps.
