# What Is a 1.58-bit LLM? A Friendly Guide to Ternary Weights

Large language models (LLMs) have typically used 16-bit floating point (FP16 / BF16) weights and activations. That precision gives models a lot of numeric flexibility, but it also makes them heavy: large memory footprint, lots of power-hungry multiply–accumulate operations, and higher latency. BitNet b1.58 introduces a very different trade-off: every weight is constrained to one of three values, \{-1, 0, +1\}. That ternary representation yields an average of about 1.58 bits per weight, and it turns out you can preserve model quality while drastically cutting compute, memory, and energy cost. This post explains how that works, why the extra value 0 matters, and what BitNet b1.58 does to make it practical.

## The idea in plain language: from FP16 to ternary weights

FP16 models store each parameter as a 16-bit floating point number. BitNet b1.58 replaces those floats with ternary weights that can only be -1, 0, or +1. The key effects are:

- Multiplications become much cheaper. Multiplying by +1 or -1 is just copying and (optionally) flipping sign; multiplying by 0 is trivial. This massively reduces the need for floating-point multipliers in matrix multiplies.
- Memory per weight drops dramatically. Storing a ternary weight uses far fewer bits than 16 bits. The paper refers to this as an average of 1.58 bits per weight, because a ternary alphabet of size 3 corresponds to log2(3) ≈ 1.585 bits.
- Because the weight values are so simple, the dominant work becomes integer additions and sign flips rather than FP16 multiply–accumulate, which is much cheaper in energy and hardware complexity.

BitNet b1.58 keeps activations at 8 bits (instead of 16), and uses ternary weights throughout the model (trained from scratch). Architecturally it follows modern LLaMA-like choices (RMSNorm, SwiGLU, rotary embeddings) so it slots into existing LLM toolchains easily.

## How ternary weights are produced (the quantization function)

To get weights into \{-1, 0, +1\}, BitNet b1.58 uses a simple scale-and-round procedure based on the mean absolute value of the weight matrix. Concretely:

- Compute the average absolute magnitude of the weight matrix
  \[
  \gamma = \frac{1}{nm}\sum_{i,j} |W_{ij}|.
  \]
- Scale each weight by \(\gamma\) and round/clip to \{-1, 0, +1\}:
  \[
  \widetilde{W} = \mathrm{RoundClip}\!\left(\frac{W}{\gamma + \epsilon}, -1, 1\right),
  \]
  where
  \[
  \mathrm{RoundClip}(x,a,b) = \max(a, \min(b, \mathrm{round}(x))).
  \]

This "absmean" scaling makes the rounding stable across matrices with different scales and yields a sparse-ish ternary matrix where many entries can be zero.

Activations are quantized differently: they are scaled per-token to the symmetric range \([-Q_b, Q_b]\) (no zero-point), which simplifies implementation and system-level optimization while keeping performance stable.

## Why adding zero matters: explicit feature filtering

A pure 1-bit scheme with values \{-1, +1\} can only scale and flip signals. Adding 0 makes a qualitative difference: it allows the model to entirely suppress some connections. That enables explicit feature filtering — a weight of 0 effectively removes that feature from contributing to the next layer.

Concretely, having zero weights provides:

- Sparsity: computation and storage can skip zero-weight contributions.
- Selectivity: the model can route signals more cleanly, shutting off noisy or irrelevant features.
- Improved modeling flexibility: the network can represent linear functions that require selective gating, not just sign flips and uniform scaling.

The paper reports that the ternary variant (adding 0) strengthens modeling capability relative to strict \{-1,+1\} BitNet, helping BitNet b1.58 match full-precision quality from a certain model size upward.

## Maintaining quality: comparable perplexity and end-task performance

BitNet b1.58 was trained from scratch (not post-training quantized) on the same token budget and datasets used for the FP16 LLaMA baselines in the experiments. Key empirical findings summarized in the paper:

- Starting at around 3B parameters, BitNet b1.58 matches FP16 LLaMA models in validation perplexity and a suite of zero-shot downstream tasks (ARC, HellaSwag, Winogrande, PIQA, OpenBookQA, BoolQ, etc.).
- A 3.9B ternary model outperforms a 3B FP16 model while using significantly less memory and delivering lower latency.
- As model size grows (7B, 13B, 70B), the speedups and memory savings increase and BitNet b1.58 continues to be more efficient while maintaining competitive performance.

The take-away: with the right architecture and training recipe, constraining weights to ternary values need not mean degraded quality at practical scales.

## Practical wins: latency, memory, energy, and throughput

Because matrix multiplication is the dominant cost in transformer layers, switching the arithmetic profile from FP16 multiply–accumulate to cheap integer adds and sign operations yields real system benefits:

- Latency: BitNet b1.58 shows multi-fold speedups. For example, at 3B scale it was ~2.7× faster; at 70B the speedup reported goes up to ~4.1× versus the FP16 LLaMA baseline in their measurements.
- Memory: The ternary model uses substantially less GPU memory (e.g., ~3.3–3.5× less for some model sizes in reported results), which also enables larger batch sizes or longer contexts.
- Energy: Focusing on the arithmetic cost of matrix multiplies, BitNet b1.58 shifts most work to INT8 additions and sign handling. Using the energy model cited in the paper, this results in large reductions in arithmetic energy—for 7nm chips the paper reports around 71.4× lower arithmetic energy for matrix multiplies alone.
- Throughput: With the reduced memory footprint, a 70B BitNet b1.58 model can support much larger batch sizes on the same hardware; the paper reports roughly 8.9× higher throughput in an example setup.

Two implementation notes: the experiments used an optimized inference stack (FasterTransformer) and a 2-bit kernel for some operations was integrated, meaning there is still room for further kernel-level and hardware optimization.

## Where ternary LLMs help the most

Some specific use cases that benefit from the lower-bit regime:

- Large-scale inference where latency and energy matter (e.g., cloud serving, high-throughput applications).
- Long-context inference: lowering activations from 16 to 8 bits (and potentially compressing KV caches further) makes it cheaper to store long key/value caches, enabling longer effective context windows for the same memory budget.
- Mixture-of-Experts (MoE) and other models where memory and inter-chip bandwidth are bottlenecks: a smaller memory footprint reduces device count and network overhead.
- Edge and mobile: ternary weights (and integer-friendly compute) make it more practical to run larger models on constrained devices and CPUs.

## What about hardware?

BitNet b1.58 changes the dominant primitive from FP16 multiplications to integer additions and sign operations. That opens opportunities for specialized hardware that can exploit ternary arithmetic and sparse integer flows. The paper argues that designing chips or accelerators with native support for this computation paradigm could further amplify the efficiency gains.

## Limitations and practical caveats

Keep in mind the following, based on what the paper reports:

- BitNet b1.58 is trained from scratch with the ternary constraint. It is not a post-training quantization of an FP16 model; the training recipe matters.
- Some parts of the model (like embeddings) remain full precision in the reported experiments, so end-to-end savings depend on implementation choices.
- The activations are still 8-bit, so the model is not fully ternary/1-bit everywhere. The combination (1.58-bit weights, 8-bit activations) is what the paper explores and validates.
- Kernel- and hardware-level support matters. The paper used optimized kernels and reports that further gains are plausible with better low-bit kernels or custom hardware.

## Bottom line

BitNet b1.58 shows that moving from 16-bit floating weights to ternary weights \{-1, 0, +1\} can preserve model quality (from ~3B parameters upward) while delivering significant wins in latency, memory, throughput, and energy. The inclusion of 0 is more than a tiny extra symbol: it provides explicit feature filtering and sparsity that improve modeling flexibility. For practitioners and hardware designers, ternary LLMs open a promising path to more efficient, deployable large models without throwing away performance.
