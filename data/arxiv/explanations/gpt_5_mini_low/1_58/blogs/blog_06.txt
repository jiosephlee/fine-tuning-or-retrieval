# Throughput Wins at Scale: What 70B Models Teach Us

Large models are great — until you try to serve many users from a single node. The BitNet b1.58 results give a clear and practical answer: if your goal is throughput at scale, low-bit models win. In the 70B comparison reported in the paper, a BitNet b1.58 model running on two 80GB A100 GPUs supports up to 11× larger batch sizes and achieves 8.9× higher throughput than the FP16 LLaMA baseline using the same devices. Here’s why that matters and how it works.

## The setup in one sentence

The 70B comparison was measured on two 80GB A100 GPUs using pipeline parallelism; batch size was increased until GPU memory was exhausted (sequence length 512), and the result was that BitNet b1.58 could hold 11× the batch size and deliver 8.9× the throughput of the FP16 baseline.

## Why batch size and throughput matter in practice

Throughput (tokens/sec or requests/sec) directly determines how many concurrent users a server can handle. Larger batch sizes amortize per-request overhead and increase arithmetic efficiency. If one node can sustain 8.9× the throughput, you need far fewer nodes to serve the same traffic — lowering capital costs, power draw, and system complexity.

Two metrics to keep in mind:
- Batch size capacity: how many sequences you can fit in device memory at once.
- Throughput: real tokens processed per second at that batch size.

BitNet b1.58 improves both.

## What pipeline parallelism is (simple explanation)

Pipeline parallelism splits a model's layers across multiple devices. Think of the model as a long assembly line: device A does the first set of layers, passes intermediate activations to device B, which does the next set, and so on. While device A is processing the next batch, device B can work on the previous batch's later layers — enabling concurrency across micro-batches.

Key points:
- Pipeline parallelism lets very large models (like 70B) run on multiple GPUs by partitioning layers.
- Memory usage per device depends both on the portion of the model hosted there and on per-request activation storage (the KV cache and intermediate tensors).
- The maximum batch size is constrained by the total memory footprint across devices, so reducing per-token memory lets you increase batch size and thus throughput.

## Why 1.58-bit models enable much larger batch sizes

BitNet b1.58 reduces memory and compute pressure in several structural ways that directly increase batch capacity and throughput:

1. Weight footprint is tiny. Weights are ternary \{-1, 0, +1\} — effectively 1.58 bits per parameter — versus 16 bits in FP16. That slashes the model parameter storage and the DRAM/SRM bandwidth needed to stream weights into on-chip memory during inference.

2. Cheaper core ops. Dense linear layers (nn.Linear) in BitNet become largely integer-add operations (INT8 additions) rather than FP16 multiplies and adds. Arithmetic energy and latency per operation go down substantially, so the same device can process more tokens per second.

3. Smaller activations and KV caches. BitNet uses 8-bit activations (and can compress caches further in future work). For long contexts and large batch sizes, KV cache memory is a dominant consumer. Cutting activation precision reduces per-token memory and allows the KV cache to hold more sequences for the same memory budget.

4. Less memory bandwidth pressure. Both weight transfers and activation transfers consume memory bandwidth. Lower-precision data moves less volume, which means GPUs reach memory capacity limits later (i.e., at larger batch sizes).

All of these combine to increase the maximum batch size the system can hold, hence the reported 11× larger batch capacity and 8.9× throughput.

## Why throughput scales superlinearly with memory reduction

Throughput is not a linear function of model size or memory footprint because several system bottlenecks interact:
- When the model is memory-bound (moving weights and activations), reducing size often yields a large jump in usable batch size before compute becomes the limiting factor.
- Reducing weight/activation precision reduces both on-device memory usage and DRAM/SRAM transfer time, improving both latency per token and the ability to pipeline more micro-batches simultaneously.

In the 70B case, the system moved from being constrained by memory bandwidth and storage to being less constrained — this multiplicative effect is why an ~16× reduction in weight precision (16-bit → ~1.58-bit) can produce near an order-of-magnitude throughput increase once the whole system stacks up favorably.

## Practical implications for serving LLMs

- Cost per served token drops. Higher throughput per GPU translates directly to fewer GPUs needed for the same traffic, lowering cloud or datacenter costs.
- Fewer GPUs reduces cross-device communication complexity. With smaller activations and weights, more of the model or more KV cache can fit on-device, lowering the network overhead in distributed setups.
- Better latency under load. Larger batch capacity means the system can absorb bursts of traffic with less queuing and fewer scale-outs.
- Enables edge and single-node large models. Lower memory and compute requirements make it conceivable to run much larger models on more modest hardware.

## Caveats and where this shines

The 8.9× throughput comes from a specific measurement: 70B models on two 80GB A100s with pipeline parallelism and sequence length 512, using highly optimized inference kernels (FasterTransformer with a 2-bit kernel integration). Results will vary with hardware, kernel optimizations, sequence length, and workload characteristics (e.g., interactive low-latency queries vs. large-batch generation). But the core takeaway is robust: reducing precision and switching to compute-friendly integer ops can unlock large practical gains in serving throughput.

## Bottom line

When serving large LLMs, memory and bandwidth are often the true constraints — not just raw FLOPs. BitNet b1.58 demonstrates that by shaving precision and using arithmetic-friendly representations, you can dramatically increase the number of users served per node. The 70B two-GPU results — 11× larger batch capacity and 8.9× higher throughput — are a concrete illustration: throughput wins at scale when you make models cheaper to store, move, and compute on.
