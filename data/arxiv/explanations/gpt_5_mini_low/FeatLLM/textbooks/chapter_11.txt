\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 11: Practical Guide to Using FeatLLM

# Preparing feature metadata: names, types, and optional descriptions
FeatLLM relies on clear, human-readable feature metadata because the LLM uses this information both to invoke prior knowledge and to avoid type errors when generating rules. At minimum provide each column's name in natural language (for example, "age", "cholesterol_mg/dL", or "smoking_status") together with its data type: numerical (continuous or integer), categorical (with listed categories if possible), boolean, or text. The paper shows that including feature descriptions improves the LLM's ability to generate relevant rules, particularly in low-shot regimes, so add short natural-language definitions when available: one sentence describing the meaning of the column, units if applicable, and typical value ranges or categories.

Organize the metadata so it can be serialized into the prompt automatically; FeatLLM places the feature names and their types/descriptions into the "Basic information description" block of the prompt. For categorical variables, supplying the possible categories (or a representative subset) reduces the chance the LLM invents impossible categories. For numerical features, indicating units and typical ranges helps the LLM propose realistic thresholds (e.g., "age: integer, range 18–90, years"). Keep descriptions concise: the LLM benefits from focused context but the overall prompt length should remain manageable.

Finally, make sure feature names are stable and human-friendly. FeatLLM depends on natural-language reasoning: cryptic internal column keys or abbreviated names (e.g., "f_12") reduce the model's ability to connect features to domain concepts. If your dataset already has terse column keys, prepare a mapping to readable names and use that mapping when composing prompts.

# Authoring effective task questions and example serialization
FeatLLM frames the prediction objective as a natural-language question, which guides the LLM to infer causal tendencies and to generate rules for each target class. Write the task description as a clear question that directly asks what you want predicted, including the possible answer set when helpful. For binary classification use yes/no phrasing ("Does this patient's record indicate chronic heart failure? Yes or No?"). For multiclass tasks, list the classes explicitly in the question so the LLM is aware of the output space.

Example demonstrations are serialized in the "Serialize" format used in the paper:
"f_1 is x_1. ... f_d is x_d. Answer: y"
Automate this serialization so each example in the few-shot support set becomes a small textual case in the prompt. Because FeatLLM is designed for few-shot settings, you will include only k examples (e.g., k=4 or k=8) in each rule-generation query. The paper finds that demonstration order can affect LLM outputs; therefore randomizing order across ensemble trials produces diversity in extracted rules.

When choosing which examples to include, prefer exemplars that highlight discriminative patterns: examples where feature conditions correspond clearly to the target class. If you have class imbalance, ensure examples represent each class to allow the LLM to infer rules for all classes. Keep the examples compact and consistent with the feature metadata to reduce parsing ambiguity.

# Crafting the two-step reasoning instruction and response format
The FeatLLM prompt structure deliberately uses a two-step reasoning instruction to separate general prior knowledge from data-driven rule induction. Implement the same structure in your prompt.

Step 1 instruction (prior-knowledge inference): ask the LLM to infer, without looking at examples, which features are likely to be causally or strongly associated with each label based on general knowledge. Phrase it explicitly: "First, based on common knowledge about the domain and the feature definitions above, list how each feature tends to relate to the label (e.g., 'higher age increases risk'). Do not use the examples here." This primes the model to surface domain priors that avoid spurious correlations driven solely by the few examples.

Step 2 instruction (example-based rule derivation): then instruct the LLM to use the prior-step output plus the few-shot example cases to generate concrete, parseable rules for each class. Specify a fixed number of rules per class (the paper uses 10 per class) to balance expressivity and prompt size. For instance: "Using the prior knowledge and the examples, produce up to 10 rules that, if true for a sample, indicate membership in each class." Constraining the number helps control downstream binary feature dimensionality and avoids excessively long parsing/validation steps.

Response formatting guidance: to make parsing reliable, require a strict, minimal structure for the LLM's responses. For example, instruct the model to output:

Class: <class-name>
1. <rule-expression-1>
2. <rule-expression-2>
...
End

And require each rule to reference feature names exactly as provided and to use comparisons appropriate to the feature type. Provide short examples of acceptable rule formats for each type: numeric (e.g., "age > 65"), categorical (e.g., "smoking_status == 'current'"), boolean (e.g., "has_diabetes is True"), and combinations using AND/OR when needed. This response instruction reduces syntactic variability and makes later parsing simpler.

# Rule parsing implementation: LLM prompt for code generation, validation tests
Even with constrained formatting, LLM outputs can vary syntactically. FeatLLM solves parsing by using the same LLM to translate the natural-language rules into executable code (Python). Implement a two-step parser:

1) Prompt-to-code generation: create a second prompt that contains (a) a short function signature and I/O description (for example, "def rule_to_bool(row: dict) -> List[bool]: # returns list of booleans, one per rule"), (b) the serialized rules produced earlier, and (c) a strict request: "Return only valid Python code that evaluates each rule on a row dictionary using the provided feature names." Ask the LLM to map phrases like "greater than" to ">" and to map categorical equality to Python string equality. Because the LLM has been trained heavily on code, it reliably emits short code blocks when asked in this constrained way.

2) Execution and validation: execute the returned code with Python's exec() in a sandboxed environment and apply it to a small validation set. The paper executes such generated code to convert the dataset into binary features for each rule. To ensure safety and correctness, run validation tests on a handful of synthetic or real rows that exercise edge cases: missing values, out-of-range values, categorical labels not seen in rules, and type mismatches. Flag failures (exceptions or unexpected outputs such as non-binary values). If a failure occurs, re-run the code-generation prompt with appended error messages and request corrections, or fall back to a conservative parser that recognizes simple patterns (e.g., "<", ">", "==") for well-formed rules.

Because the paper constrains response structure and then uses the LLM to produce Python code, this two-phase approach reduces efforts building hand-coded parsers and leverages the LLM's code-generation strengths while keeping parsing robust via simple validation tests.

# Choosing ensemble size and bagging ratios under context limits
FeatLLM uses an ensemble of repeated rule-generation trials combined with bagging to increase robustness and to handle prompt size limits when datasets have many features or when support size is large. The paper used T=20 ensemble trials with R=10 rules per class as a practical choice; this produced diminishing returns beyond roughly 20 trials.

When selecting ensemble size T, balance improved robustness against API cost and latency. Useful practical guidance from the paper: performance typically improves with T, but gains converge (often around T ≈ 20). For very strict cost/latency constraints, T can be reduced; for critical-accuracy scenarios you can increase T until you observe diminishing returns on validation.

Bagging strategy: in each ensemble trial randomly sample a subset of features and/or a subset of support examples to include in the prompt. This reduces prompt length per query, allowing datasets with many features to be handled without exceeding context limits. Tune bagging ratios based on context capacity: if the LLM's token budget constrains you, reduce the number of features per trial; the ensemble idea compensates by aggregating rule-sets across different feature subsets. The paper reports that bagging both features and instances reduces per-query prompt size and increases rule diversity. When you have a reasonable context window, you can include more features per trial; otherwise prioritize the most semantically relevant or high-variance features in each sampled subset.

Also randomize example order within the prompt across trials to exploit in-context-order sensitivity, increasing diversity in generated rule-sets. The paper found that randomness in order and a moderately high sampling temperature (e.g., 0.5) helps produce varied but useful rules for the ensemble.

# Selecting and training the downstream linear model
After parsing rules into binary features, FeatLLM fits a simple linear model to learn each rule's importance. For a classification problem with c classes and R rules per class (binary features), denote the binary feature vector for class k from sample i as $\mathbf{z}_k^i \in \{0,1\}^R$. The paper uses a linear logit model without bias where, for sample i and class k:

logit_k^i = max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\mathbf{p}^i = \text{Softmax}([ \text{logit}_1^i, ..., \text{logit}_c^i ]).

Constrain weights to be non-negative by applying elementwise $\max(\mathbf{w}_k, 0)$; this prevents generated features from reducing a class's likelihood during learning. Trainable parameters are the weight vectors $\mathbf{w}_k$. Optimize the cross-entropy loss on the few-shot labeled examples. The paper used the Adam optimizer with learning rate 0.01 and trained for ~200 epochs, selecting epochs via k-fold cross-validation; these hyperparameters are sensible starting points.

If you prefer a regularized alternative, you can employ L2 or L1 penalties to avoid overfitting when many rules are present, but FeatLLM's design purposefully limits per-trial rule counts (e.g., 10 rules per class) and uses ensembling to reduce overfitting. The paper shows that learning weights (i.e., tuning) improves performance versus naive counting of satisfied rules, particularly as shot count increases, so training this simple model is important.

After training, you can prune rules with near-zero learned weights (the paper suggests a threshold such as 0.1 chosen from the empirical weight histogram) to simplify the final model and remove uninformative or noisy rules.

# Common pitfalls: overly general rules, type mismatches, and how to refine prompts
Overly general rules: LLMs sometimes output very broad rules (e.g., "age > 0" or "has_any_symptom is True") that are trivially true or unhelpful. These produce uninformative binary features and waste capacity. Mitigation: in the response instruction require rules to be "decisive" and actionable. Provide examples of both good and bad rules in the prompt: show that "age > 65" is acceptable, while "age > 0" is not. The two-step reasoning (first ask for priors, then for decisive rules using examples) reduces generation of trivial rules.

Type mismatches: a generated rule might use an inequality on a categorical feature or compare a string to a number. Two defenses reduce this issue. First, include feature type annotations in the "Basic information description" and remind the LLM in reasoning instructions to use comparisons appropriate for each type. Second, validate generated code using the parsing-and-execution step on a small validation set: type errors will surface as exceptions or as logically impossible comparisons. When errors are detected, resend the rule parsing request to the LLM with explicit error output and ask for corrected code.

Ambiguous wording and syntactic variability: although response format constraints help, LLMs may phrase comparisons in words like "greater than" or "less than or equal to." Because the paper uses the LLM to translate rules into code, this is manageable—ensure your parsing prompt explicitly requests normalization of such phrases to canonical Python symbols. If the LLM still produces ambiguous rules, you can post-process rules with regex heuristics before code generation to canonicalize common phrases.

Spurious correlations: with very few examples, the LLM can latch onto accidental correlations. The paper demonstrates that the explicit step to list prior knowledge and the use of multiple trials plus bagging reduces extraction of noisy rules; still, monitor the proportion of generated rules that reference obviously irrelevant features. If you find many spurious rules, add more domain guidance in step 1, or restrict the set of features sampled per trial to those likely relevant.

# Deployment: low-latency inference without LLM calls
One of FeatLLM's main operational benefits is that after the rule-generation phase and downstream weight training are complete, inference does not require any LLM calls. Deployment proceeds as follows.

1. Store the final set of parsed rules as executable code (or a compiled form) that maps each raw input row to the binary rule-feature vector. Use the validated Python implementation generated during the parsing stage or manually convert it into a safe production routine.

2. Save the trained weight vectors $\{\mathbf{w}_k\}$ (or pruned subset). At inference time, for each new sample compute the binary vector outputs for the rules, compute the logits via the linear model
logit_k = max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k,
and produce class probabilities with softmax. This is a simple dot product and softmax computation (O(number_of_rules)), which is very fast.

3. Because the inference requires no LLM, latency is comparable to standard linear models and is much lower than approaches that evaluate each sample via the LLM. The paper's runtime comparison shows that FeatLLM's inference time is similar to conventional methods like logistic regression and far faster than per-sample LLM inference alternatives.

For safety and maintainability, keep a versioned artifact bundle containing (a) the rule code, (b) the trained weight vectors, and (c) metadata about how each rule maps to features and which ensemble trial produced it. This supports interpretability and debugging after deployment.

# Final practical checklist
- Prepare readable feature metadata with explicit types and short descriptions.
- Write a clear natural-language task question that enumerates classes.
- Serialize k-shot examples in the standard format and keep them representative.
- Implement the two-step reasoning prompt: (1) prior-knowledge inference, (2) example-based rule generation; constrain rule count (e.g., 10 rules/class).
- Constrain response format strictly and include rule-format examples for each feature type.
- Use the LLM to translate rules to executable code; validate this code on test rows and iterate if errors occur.
- Choose ensemble size T (start at 20) and bagging ratios to respect context limits; randomize demo order and use moderate temperature (e.g., 0.5) for diversity.
- Train non-negative-weight linear models per class with cross-entropy and simple optimizers (Adam, lr 0.01), prune low-weight rules.
- Bundle the rule code and learned weights for inference; no LLM calls required at runtime.

Following the paper's method and these practical steps should let you implement FeatLLM effectively: extracting interpretable, high-quality rule features with an LLM during a limited set of queries, and achieving fast, LLM-free inference with a simple downstream model.
