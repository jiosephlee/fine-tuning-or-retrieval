\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 5: Prompting for Rule Extraction

# Basic information description: task question, labels, feature types/descriptions, serialized few-shot examples
The first component of FeatLLM's prompt provides the LLM with all essential, grounded information required to reason about the tabular prediction task. This section is written to look and behave like the problem statement an expert analyst would read: a concise task question, explicit label definitions, and clear descriptions of each column (feature). The task question is expressed in natural language as a concrete yes/no or multiclass question (for example, "Does this patient's myocardial infarction complications data indicate chronic heart failure? Yes or no?") so the model has a target-oriented framing for downstream rule extraction. The label definitions enumerate the possible classes and, when helpful, short clarifications of what each label means in the task context.

Feature descriptions are equally explicit. For every column we give (a) the feature name as natural language text, (b) the feature type (numeric, categorical, boolean, etc.), and (c) optionally a short definition or allowed category values for categorical features. The presence of type information is important: it constrains which syntactic forms of rules the LLM should produce (for example, inequalities for numeric features and membership tests for categorical ones), and it reduces the risk of creating syntactically invalid or semantically meaningless conditions. In datasets with many possible categories, listing representative categories or the full domain (when feasible) prevents the model from inventing categories that do not exist.

This basic information block also contains the few-shot example demonstrations. Each demonstration is a serialized training sample paired with its ground-truth label; demonstrations are chosen from the available k-shot training set. These examples expose the LLM to concrete input-output mappings and let it ground its general priors in the specific statistical patterns present in the target dataset. The basic-information block is therefore a hybrid: it supplies general task semantics and detailed feature typing, and it injects a small number of concrete examples so the LLM can coordinate prior knowledge with observed instances.

# Serialization format for examples and labels
FeatLLM employs a simple, uniform serialization format to convert a tabular sample and its label into text for the prompt. For a d-dimensional input vector \mathbf{x}^i and corresponding label \mathbf{y}^i, the serialization is defined in the paper as:

"\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = 
\ ``\ f_1\ \text{is}\ \mathbf{x}^i_1.\ ... \ f_d\  \text{is}\  \mathbf{x}^i_d.\ \ \text{Answer:}\  \mathbf{y}^i\ ”"

This format lists every feature name f_j followed by the observed value \mathbf{x}^i_j, ending with "Answer: <label>". The serial form mirrors prior LLM-tabular work and is deliberately simple to keep prompts predictable. Importantly, this serialization retains the feature names F = \{f_j\}_{j=1}^{d} in natural language, which links the numeric or categorical values to semantic descriptions the LLM can exploit from its pretraining. Using a consistent serialized example format aids both the LLM's pattern recognition and subsequent automatic parsing of the LLM's recommendations.

When constructing the few-shot block, FeatLLM typically includes k examples where k is small (e.g., k=4 or k=8) to match the low-shot learning regime. The example order is randomized across ensemble trials because example ordering can influence LLM outputs; this randomness is later used to generate diverse rule sets for ensembling.

# Reasoning instruction: two-step process
To guide the LLM toward producing causally meaningful, parsable rules rather than superficial correlations, the prompt includes an explicit reasoning instruction that splits the inference into two sequential steps. The intention is to mimic an expert analyst's workflow: first surface relevant domain priors and tendencies without being anchored to specific examples, then reconcile those priors with the observed few-shot cases to produce concrete, decisive rules.

The reasoning instruction begins with an opening that encourages chain-of-thought style reasoning, prompting the LLM to consider causal tendencies and feature relevance explicitly. The two-step structure is enforced in the prompt text so the LLM is told to separate its answers into a Step 1 and Step 2. By dividing the process, FeatLLM reduces the risk that the model will latch onto spurious correlations visible only in the few-shot examples and instead promotes the reuse of broad, transferable domain knowledge.

Concretely, the first step asks the LLM to reflect on general associations between the task and features given their descriptions—without consulting the example demonstrations. The second step then asks the LLM to propose concrete rules that use both the priors surfaced in Step 1 and the few-shot exemplars. This sequencing biases the LLM to favor features that a priori make sense for the task, and then to convert those into rules consistent with the small in-context dataset.

# Step 1: Prior-knowledge reasoning without examples to surface domain priors
Step 1 is: "Given only the task description and the feature definitions (do not look at the examples), what features do you expect to be related to the label, and in which direction or manner?" The LLM is explicitly prohibited from consulting the serialized examples at this stage. This prohibition is purposeful: it forces the model to retrieve and articulate priors stored in its pretraining—medical knowledge, domain correlations, monotonic tendencies, and so on—rather than overfitting to idiosyncratic patterns present in the few examples.

By surfacing these priors first, the LLM creates a shortlist of promising feature candidates and expected relationships (for instance, "age likely increases disease risk", or "high blood-glucose is associated with diabetes"). These surfaced tendencies serve two functions. First, they anchor Step 2 so that the LLM will search for rules that align with domain-relevant features rather than arbitrary correlates. Second, they provide a natural filter: features not mentioned in Step 1 are implicitly deemphasized in Step 2, reducing the chance of producing rules derived purely from noise or spurious correlations present only in the few-shot examples.

This approach leverages one of the strengths of LLMs: stored world knowledge and commonsense associations learned during pretraining. Because Step 1 is run inside the same prompt, the LLM can integrate those priors smoothly into the next stage without any external model components.

# Step 2: Rule deduction using examples plus priors to avoid spurious features
Step 2 instructs the LLM to use both the priors identified in Step 1 and the serialized few-shot examples to deduce decisive, testable rules for each class. In this phase the model is allowed and expected to examine the examples: to find concrete value ranges, category memberships, or combinations that match the target labels while being consistent with the domain priors. The two-step separation leads to rules that are both interpretable (derived from priors) and empirically grounded (consistent with examples).

The Step 2 instruction explicitly asks for rules that are concise and decisive: they should be conditions that can be applied to a new sample and yield a binary outcome of rule satisfaction. For numerical features, the LLM is guided to produce inequalities or value ranges; for categorical features, membership tests or specific categorical values; for boolean flags, direct checks. The LLM is guided to prefer single-feature conditions where possible and to combine features with logical operators like AND/OR only when necessary to produce a decisive rule.

The combination of priors and examples helps prevent the LLM from extracting spurious features. If a feature shows an accidental correlation in the examples but contradicts the high-level domain prior from Step 1, the LLM is encouraged to treat that correlation with caution and avoid making it a standalone rule. Conversely, when a prior suggests a relationship and the examples corroborate it, Step 2 will concretize that into an explicit condition.

# Response instruction: constrained output format and rule templates
To ensure that the rules the LLM emits are parsable and directly usable, the prompt includes a structured response instruction that specifies a precise output format and rule templates. The response instruction prescribes how many rules to generate per class, how to enumerate them, and the syntactic shape each rule should take. The goal is to make the LLM produce output that can be reliably parsed (or, when small syntactic variation occurs, re-parsed by a subsequent LLM-assisted parser) into executable checks.

The response format enforces a short header per class and then a numbered list of rules. Each rule is requested to follow a template according to the feature type. For example:
- Numeric rule template: "<feature> is <comparison> <value>" or "<feature> in [<low>, <high>]"
- Categorical rule template: "<feature> == <category>" or "<feature> in {<cat1>,<cat2>}"
- Boolean rule template: "<feature> is True" or "<feature> is False"

In practice the LLM will sometimes use synonyms (e.g., "greater than" instead of the symbol ">"). The response instruction therefore also requests syntactic consistency, but FeatLLM anticipates minor variants and remedies them at parsing time (see paper's parsing stage). Crucially, the response instruction sets a strict, machine-friendly structure: numbered rules, class headings, and rule templates. This constrained form drastically reduces the difficulty of converting the natural language rules into binary features indicating rule satisfaction.

# Choosing the number of rules per class (default 10) and trade-offs
FeatLLM fixes the number of rules per class to a modest, predefined number; the paper uses a default R=10 rules per class. This limit is a pragmatic trade-off between expressiveness and tractability. On one hand, asking the LLM to produce many rules per class increases the probability of covering diverse patterns and capturing complex decision boundaries; it also increases the dimensionality of the rule-based feature space, which may be beneficial if the downstream learner can exploit many weak signals. On the other hand, too many rules inflate the prompt length (if rules are also shown or validated in subsequent steps), raise the chance of including low-quality or redundant rules, and enlarge the input dimensionality for the downstream tuning process, which in few-shot regimes may promote overfitting.

Constraining to R=10 is a design point the paper found to balance these concerns: it provides enough capacity for expressivity while keeping prompts and the resulting binary feature set manageable. Empirically, the paper's hyper-parameter analysis indicated no statistically significant gains from substantially increasing R beyond 10 in low-shot scenarios; instead, adding more rules tended to increase input dimensionality without reliable performance improvements. The fixed-count design also simplifies ensembling and bagging: every trial produces a predictable number of candidate features per class, facilitating consistent weight training and aggregation.

Practically, one should view the number of rules per class as a tunable hyper-parameter. In extremely low-dimensional problems or when domain knowledge suggests simple thresholds suffice, a smaller R may be adequate. In heterogeneous tasks where several independent signals exist, a somewhat larger R can help, but the downstream weight-tuning and ensembling stages are the primary guards against overfitting.

# Preventing type mismatches and promoting concise, decisive conditions
Several mechanisms in the prompt design reduce the chance the LLM will produce rules that are type-incoherent or syntactically unusable. First, the basic information block explicitly states the feature type for each column. The reasoning and response instructions then refer back to those types: the LLM is told to prefer inequality-based templates for numeric features, membership tests for categorical features, and boolean checks for binary flags. This reference constrains the forms the LLM should employ and reduces mismatches like asking whether "age is 'male'" for a numeric "age" feature.

Second, the response templates reinforce type-appropriate syntax. By supplying example rule templates in the prompt, the LLM is more likely to follow them, producing rules that can be directly parsed into code or into a structured representation. If the LLM uses synonyms or differing punctuation (e.g., "greater than" vs. ">"), the subsequent parsing stage in FeatLLM is designed to handle those predictable variants. The parsing uses the LLM again to translate natural-language rules into executable code snippets, leveraging the LLM's robustness to linguistic variability rather than building brittle hand-written parsers.

Third, the prompt emphasizes concision and decisiveness. Rules are requested to be as simple as possible: single-feature thresholds or categorical membership checks unless a multi-feature combination is truly necessary. This preference for simplicity increases interpretability, keeps the generated binary features meaningful, and makes the downstream linear weight-tuning step more effective given few training examples. Concise rules are easier to validate across ensemble trials: rules that recur across runs are more likely to be genuine signals.

Finally, the prompt caps the number of rules per class and asks for exactly that many, which avoids ambiguous open-ended outputs that could mix explanatory text with rules. Combined, these measures reduce type errors, encourage machine-parsable output, and promote production of concise, decisive conditions that can be reliably applied to new samples without any per-sample LLM inference.

# Summary
FeatLLM's prompt architecture intentionally scaffolds LLM reasoning to extract high-quality, parsable rules. The basic information block supplies a focused task question, label definitions, and typed feature descriptions alongside serialized few-shot examples. A two-step reasoning instruction forces the model to first articulate prior knowledge without examples and then to derive concrete rules grounded in both priors and exemplars. A constrained response instruction, with type-specific templates and a fixed number of rules per class (default R=10), yields concise rules that are amenable to parsing into executable checks. These design choices collectively balance the need for expressive, causally relevant features with the practical constraints of prompt length, parseability, and few-shot robustness.
