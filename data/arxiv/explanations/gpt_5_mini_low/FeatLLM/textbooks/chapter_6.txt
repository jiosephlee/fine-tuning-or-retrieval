\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 6: From Natural Language Rules to Computable Features

# Parsing challenges: syntax variability and ambiguity in natural language
When an LLM is prompted to produce decision criteria or "rules" in natural language, the output can be rich in semantics but inconsistent in syntax. The FeatLLM paper highlights concrete examples of this variability: an LLM may express the same comparison as the symbol "$>$" or as the phrase "greater than," it may reorder clauses, or it may include optional clarifying text. Even with constrained response formats, subtle syntactic noise remains common. This variability creates two core parsing challenges.

First, syntactic variability undermines deterministic string-based parsers. A parser that expects an exact lexical form (for example, the precise token "$>$") will fail when the LLM writes "greater than" or "is larger than". Natural language allows optional articles, parentheses, units, and synonyms that change the token stream while preserving meaning. Second, ambiguity arises when a generated rule mixes concepts, uses implicit references (e.g., "this value" without an explicit feature name), or uses logical combinations (AND/OR) in nested forms. Such ambiguity makes it difficult to map rule text unambiguously to a simple predicate that can be evaluated on a tabular row.

These difficulties are particularly important in the FeatLLM setting because the downstream pipeline relies on automatically converting rules into binary features. Parsing failures produce malformed predicates that either crash a conversion step or, worse, silently produce incorrect features. The paper therefore treats parsing as a crucial step: instead of attempting to predefine brittle grammatical patterns, FeatLLM accepts that LLM outputs will contain syntactic variation and builds the parsing stage to be robust to it.

# LLM-assisted code generation for parsing: function signatures, I/O specs, and safety checks
FeatLLM addresses parsing variability by delegating much of the parsing burden back to an LLM that is itself good at interpreting semantically equivalent phrasings. Rather than hand-coding a complex natural language parser that must enumerate lexical variations, the pipeline prompts an LLM to produce executable code that implements the intended predicate evaluations.

Concretely, the prompt for the parsing step contains (1) a function name, (2) explicit descriptions of the function's inputs and outputs, and (3) the list of inferred natural-language rules. By supplying this minimal API-level specification, the LLM is guided to emit code that takes structured inputs (for example, a dictionary or a row vector and feature metadata) and returns a deterministic output (for example, a list or array of binary indicators). Because the prompt enforces an input/output (I/O) contract, the LLM is steered toward producing code that can be executed programmatically.

Two practical design choices in this approach are worth emphasizing. First, the I/O contract reduces ambiguity: the LLM must map natural language rules into expressions that use the provided feature names and data types. When the prompt includes feature types (categorical, continuous) and canonical names, the LLM is less likely to generate type-mismatched expressions. Second, providing the desired return shape (for example, an array of length $R$ for $R$ rules) reduces the chance that the LLM will emit prose instead of code. The FeatLLM authors found that leveraging the LLM to generate simple code is effective because the model is already trained on code and can translate variable natural-language phrasings into logically equivalent programmatic tests.

In addition to function signatures and I/O, the prompt can include minimal safety checks and parsing guidance: request that the generated function validate input types, handle common synonyms (e.g., map "greater than" to the "$>$" operator), and return clear error codes or default values when a rule cannot be interpreted. These requirements make the generated code itself more robust to irregular outputs from the rule-generating stage.

# Executing generated code securely (e.g., sandbox considerations) and verifying outputs
The FeatLLM paper implements the execution of generated parsing code using Python's exec() function. This is an effective, lightweight mechanism to materialize and run code created by an LLM. However, executing arbitrary generated code carries obvious risks: syntactic errors can raise exceptions, and malicious or simply mistaken code could have unintended side effects if executed in an unrestricted environment.

In the FeatLLM implementation the generated code is executed to perform the data conversion from rules into binary features. Because the paper focuses on practicality and shows that this approach works across many datasets, the authors emphasize programmatic verification of the outputs after execution. Two verification steps are implied by the paper's methodology:

1) Syntax and runtime validation. After running the generated function, the pipeline checks that the function returned the expected output shape (for example, an array of length $R$ with values in $\{0,1\}$ for $R$ rules). If execution raises syntax or runtime errors, that trial is either retried (possibly with a different LLM sample) or discarded as malformed.

2) Semantic sanity checks. The pipeline inspects the generated binary features for basic statistical sanity: features should be binary, should not be constant across the dataset (all zeros or all ones), and should have some nontrivial association with the target across the few labeled samples. The FeatLLM paper uses downstream model tuning and thresholding (see the Quality Control section) which further rejects irrelevant or spurious features.

While the paper describes using exec() directly, it also implicitly motivates careful runtime checks before accepting generated code outputs. In practice one would run generated code in an isolated or restricted environment, validate its outputs, and only then allow these features into the training pipeline. The FeatLLM results show that this approach—generate code with an LLM, execute it, then validate outputs—is sufficient to extract high-quality features for few-shot tabular learning when combined with downstream filtering and ensembling.

# Binary feature construction per class: rule satisfaction indicators
Once parsing succeeds, each rule is converted into a deterministic predicate that can be evaluated on every sample in the dataset. FeatLLM constructs binary features from these predicates: for class $k$ and rule $r$ the generated feature for sample $i$ is a bit indicating whether sample $\mathbf{x}^i$ satisfies rule $r$ associated with class $k$. The paper denotes the per-class rule feature vector for sample $i$ as $\mathbf{z}_k^i \in \{0,1\}^R$, where $R$ is the number of rules per class.

These binary indicators are the only features used by the downstream, low-complexity predictive model. The choice of binary features has several advantages in the FeatLLM design. First, they are interpretable: each active bit corresponds to a concrete, human-readable rule. Second, they are model-agnostic: once produced, any classical ML method can be applied, but FeatLLM focuses on a simple linear model (without bias) to estimate class logits. The linear model computes a logit for class $k$ as a weighted sum of its binary rule indicators:

logit_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,

and then class probabilities are obtained with a softmax across classes:

\mathbf{p}^i = \text{Softmax}([ \text{logit}_1^i, \dots, \text{logit}_c^i ]).

The projection $\max(\mathbf{w}_k, 0)$ enforces non-negativity on the learned weights, ensuring that satisfying a rule does not reduce the likelihood of the associated class. Learning the weights $\mathbf{w}_k$ on the few labeled samples lets the pipeline calibrate which rules are predictive and how strongly they should influence class likelihood. This step converts the set of potentially noisy and overlapping rule indicators into a compact, weighted signal suitable for few-shot training.

# Quality control: detecting malformed rules and fallback strategies
The FeatLLM paper adopts several strategies to detect and mitigate malformed or unhelpful rules and to ensure robustness of the generated features.

First, constraining the rule-generation prompt reduces gross malformations. The prompt enforces a fixed response format, requests a fixed number of rules per class (the authors typically use $R=10$), and supplies feature type information so the LLM is less likely to produce type errors. Even with these constraints, some rules remain noisy; the paper acknowledges that syntactic changes and variation still occur.

Second, the pipeline uses the LLM itself to parse natural language rules into code, letting a model trained on code normalize common linguistic variants. This two-stage LLM usage—one LLM to propose rules, another to translate them into executable predicates—reduces parsing failures relative to a handcrafted parser.

Third, FeatLLM employs downstream statistical filtering during the weight-tuning phase. After generating the binary rule features and fitting the linear model with cross-entropy loss, the learned non-negative weights $\mathbf{w}_k$ implicitly rank features by usefulness. The authors report computing histograms of learned weights and applying a small threshold (they use 0.1 in experiments) to identify and effectively discard rules that receive negligible weight. Table analyses in the paper show that the fraction of rule-features with AUROC $>0.5$ increases after tuning, indicating that tuning functions as an effective filter.

Fourth, ensembling with bagging provides a robust fallback when individual trials generate malformed or unhelpful rules. FeatLLM repeats the entire rule-generation, parsing, and tuning pipeline $T$ times (the paper uses $T=20$), randomizing few-shot example order and performing feature/instance bagging across trials. Because the ensemble averages class probabilities produced by each trial, trials with many malformed rules have limited influence on the final prediction. Moreover, rules that are repeatedly inferred across trials receive consistent positive weights and thus have greater net influence; this self-consistency property helps prioritize correct rules.

Finally, pragmatic runtime safeguards are used during code execution: the pipeline validates the function's return shape and that outputs are binary. If produced code fails these checks (exceptions, wrong shapes, non-binary outputs), the trial can be retried or excluded from the ensemble. While the paper does not enumerate every possible fallback, it demonstrates a pragmatic set of checks and a post-parsing filtering mechanism (weight thresholding plus ensembling) that together make the system robust to malformed rules.

# Summary
FeatLLM converts LLM-generated natural-language rules into reliable, computable binary features by recognizing and addressing parsing variability, employing the LLM itself to generate parsing code under clear function/I/O constraints, executing and validating that code (using exec() in the implementation), and then constructing per-class binary rule indicators $\mathbf{z}_k^i$ for downstream prediction. Quality control is enforced via prompt constraints, post-parsing validation, weight-based filtering after tuning (e.g., thresholding learned non-negative weights), and ensembling with bagging to dilute the impact of malformed trials. Together these design choices enable FeatLLM to turn informal, variable natural-language rules into robust, interpretable features suitable for few-shot tabular learning.
