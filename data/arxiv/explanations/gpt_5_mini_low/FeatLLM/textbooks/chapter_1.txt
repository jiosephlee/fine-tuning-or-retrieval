\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 1: Why LLMs for Few-Shot Tabular Learning?

# The challenge of few-shot learning on tabular data
Few-shot learning for tabular data is fundamentally difficult because tabular datasets are heterogeneous, often small, and lack the kind of spatial or sequential structure that makes transfer and augmentation straightforward. In a typical supervised setup we have a labeled dataset $\mathcal{D}=\{(\mathbf{x}^i,\mathbf{y}^i)\}_{i=1}^N$ where each input $\mathbf{x}^i\in\mathbb{R}^d$ (or a mixed-type vector with categorical and numeric columns) and $d$ can vary greatly across problems. In the few-shot regime we are restricted to only $k \ll N$ labeled examples for training. With so few labels it is easy for a learned model to latch onto spurious correlations in the available features, and standard regularization, data augmentation, or self-supervised pretraining approaches are often insufficient because (1) tabular features are heterogeneous so designing universally effective augmentations is hard, and (2) when $k$ is small there is simply not enough signal to reliably estimate complex relationships.

Traditional tabular learning methods—logistic regression, tree ensembles like RandomForest or XGBoost—work well when there is sufficient labeled data or when carefully engineered features are available. But in many real-world domains (medical records, finance, small scientific studies) labeled data are costly and domain expertise for feature engineering may not be available. Few-shot methods attempt to bridge that gap: some use synthetic pretraining across many datasets, some exploit unlabeled data, and others adapt large models via parameter-efficient fine-tuning. Each has practical limitations. The key problem remains: how do we obtain informative, low-dimensional, and interpretable features that capture the true predictive criteria of the task when only a handful of labeled examples exist?

# LLMs’ prior knowledge and reasoning as a substitute for domain expertise
Large Language Models (LLMs) are trained on massive corpora of text that contain not just language patterns but also embodied domain knowledge—medical, financial, scientific, and everyday causal regularities. This prior knowledge allows LLMs to make reasonable inferences about relationships between concepts even when provided only a small number of examples. Concretely, an LLM can read a task description and the natural-language names and definitions of columns $F=\{f_j\}_{j=1}^d$, then draw on its background knowledge to hypothesize which features are likely to matter or how feature values map to outcomes.

Beyond stored facts, modern LLMs exhibit emergent reasoning behaviors when prompted appropriately: by providing a task description and a few demonstrations, the model can produce chain-of-thought style reasoning that reveals why a particular label follows from certain feature patterns. In the context of tabular tasks this means the LLM can not only guess labels for examples, but also propose human-interpretable decision criteria—rules such as ``if age $>$ 65 and blood pressure $>$ 140 then high risk''. Those rules are precisely the sort of domain-guided, high-signal features that a few-shot classifier desperately needs: they distill prior knowledge into conditions that partition the input space in ways relevant to the target.

Using LLMs as a source of such rules turns the model into an automated domain expert: it leverages broad textual training to suggest plausible causal tendencies and concrete feature conditions that go far beyond what can be inferred from a handful of labeled points alone.

# Limitations of end-to-end LLM inference: latency, cost, API-only access, and prompt length
While LLMs can be applied in an end-to-end manner—serialize a row of tabular data into natural language, include the task description and few-shot examples in a prompt, and ask the LLM to predict the label—this approach has several practical drawbacks that restrict adoption in real-world systems.

Latency and cost: End-to-end use typically requires one LLM inference per sample at prediction time. For moderate to large test sets this becomes expensive and slow, especially when using commercial API-backed LLMs where each call has a monetary cost and throughput limits. For production systems that must score many rows with low latency, per-sample LLM calls are often unacceptable.

API-only access and lack of fine-tuning: Many high-quality LLMs are offered only as inference APIs without access to weights or fine-tuning hooks. Methods that require parameter-efficient tuning or training the LLM (to adapt to task-specific patterns) become infeasible in those cases. Even parameter-efficient fine-tuning approaches presuppose some ability to run or modify the model, which is not guaranteed for API-only models.

Prompt size limits: Classic serialization approaches concatenate feature descriptions, feature values, and examples into a prompt. When $d$ is large or example sets are long, the prompt length can exceed the model’s context window, or the model’s performance can degrade because important information is truncated. This is especially problematic for datasets with dozens or hundreds of columns where one would like the LLM to consider many features jointly.

These limitations motivate a different use of LLMs: instead of relying on them at inference time or requiring fine-tuning, can we use their strengths once to produce reusable artifacts that enable cheap downstream inference?

# From predictions to feature engineering: reframing the role of LLMs
The central idea is to reframe LLMs from label predictors to feature engineers. Rather than asking an LLM to label each new sample, we ask it once (or a limited number of times) to describe the predictive criteria for each class in human-readable rule form. These rules are then parsed into deterministic binary features that can be applied cheaply to all samples. Concretely, a rule might be of the form ``age $>$ 65 and cholesterol $>$ 240'', and we convert it into a binary feature that is 1 when that condition holds and 0 otherwise. Once a set of rules is produced, a simple downstream model—e.g., a linear model with non-negative weights—can be trained on the few labeled examples to combine these rule-based features into class probabilities.

This reframing has several practical advantages. First, inference no longer requires any LLM calls: the generated features are standard deterministic transformations of input columns, so scoring a new row is as cheap as evaluating the rules and applying a linear dot product. That eliminates per-sample latency and API cost. Second, since rule generation can be done with only API-level access and a bounded number of queries (for instance, tens of prompts rather than one per test sample), the approach is compatible with LLMs that do not permit fine-tuning. Third, by having the LLM produce concise, human-readable rules, we gain interpretability—each learned feature has an explicit semantic meaning relating to the task—and enable straightforward debugging and human oversight. Finally, because rules are discrete programmatic checks, they do not require the entire dataset to be serialized into a single prompt, mitigating the prompt-length problem: rule extraction can be done via multiple queries with feature bagging or ensembling strategies so that each prompt fits within the context window.

This feature-engineering role leverages the LLM’s best qualities—prior knowledge and reasoning—while avoiding its weaknesses for large-scale, low-latency deployment.

# High-level overview of FeatLLM and its contributions
FeatLLM operationalizes the idea above into a practical framework for few-shot tabular learning. At a high level it performs the following steps: (1) prompt an LLM to infer and output a fixed number of rules per class using a carefully structured prompt that provides the task description, feature definitions, and a small set of demonstrations; (2) parse the LLM’s natural-language rules into executable code that creates binary features indicating whether each rule holds for a given sample; (3) train a simple downstream model (e.g., a linear model with non-negative weights) on the few-shot labeled data to learn the importance of each rule-derived feature; and (4) repeat the rule-generation and training steps multiple times with randomization (bagging of features or examples, high sampling temperature, and varied demonstration order) to produce an ensemble whose averaged probabilities improve robustness.

FeatLLM’s design choices reflect several concrete contributions and practical benefits. First, the prompt design separates reasoning into two phases: (A) infer general tendencies or causal relationships between features and the task from the model’s prior (without looking at examples), and (B) use those tendencies plus the few-shot demonstrations to deduce explicit rules for each class. This two-step instruction encourages the LLM to leverage prior knowledge rather than overfitting to idiosyncrasies in a small example set. Second, the framework deliberately constrains the format and number of rules (e.g., a fixed number $R$ of rules per class) so that the feature dimensionality remains tractable for downstream learning and for ensemble aggregation. Third, FeatLLM uses the LLM itself to parse noisy natural-language rules into executable code rather than writing brittle hand-coded parsers; this reduces engineering effort and exploits the LLM’s strong capabilities in understanding and generating structured code. Fourth, by projecting the linear weights into the non-negative subspace (using $\max(\mathbf{w}_k,0)$ during inference) FeatLLM ensures rule features cannot negatively flip a class likelihood—this matches the intuition that a rule for a class should only increase evidence for that class, while tuning allows the model to downweight unhelpful rules.

Empirically, FeatLLM demonstrates that LLM-generated rule features are highly informative: a large fraction of generated rules show positive predictive signal (AUROC $>$ 0.5) before any tuning, and tuning plus ensembling further filters and amplifies useful rules. Because FeatLLM creates reusable features, the inference cost matches that of conventional methods while delivering strong few-shot performance, often outperforming other LLM-based baselines that require per-sample inference or finetuning. Importantly, FeatLLM is compatible with API-only LLMs, avoids prompt-length limitations via bagging and ensembling, and produces interpretable, inspectable rule features that can aid practitioners in domains where transparency matters.

In sum, FeatLLM reframes the role of LLMs from expensive per-sample predictors to one-time (or limited) feature engineers that inject prior knowledge and structured reasoning into few-shot tabular learning. This reframing addresses practical deployment constraints—latency, cost, API access, and prompt length—while delivering interpretable, high-quality features that enable simple downstream models to achieve strong performance with very few labeled examples.
