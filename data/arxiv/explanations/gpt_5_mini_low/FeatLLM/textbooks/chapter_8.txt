\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 8: Ensembling and Bagging for Robustness and Scalability

# Generating diverse rule sets: LLM temperature and example order randomization
A central ingredient of FeatLLM's robustness is that it does not rely on a single deterministic set of rules produced by the LLM. Instead, it intentionally induces variability in the rule-generation process so that multiple, slightly different rule sets can be produced and then combined. Two simple but effective sources of randomness are used to create this diversity.

The first is the LLM sampling temperature. When the LLM is queried to produce rules, setting a higher temperature increases the model's entropy: it is more willing to produce alternative phrasings, choose different thresholds, and combine features in different ways. In FeatLLM experiments the temperature is set to a non-zero value (for example 0.5) during ensemble runs so that each call can yield a different collection of candidate rules even when the prompt structure is held constant. This diversity in candidate rules helps the pipeline explore multiple plausible heuristics that connect features to labels.

The second source of randomness is the order of few-shot demonstrations included in the prompt. The LLM’s in-context behavior is sensitive to the sequence of examples; changing that order can alter which aspects of the examples the model attends to and thus which rules it proposes. FeatLLM exploits this sensitivity by randomizing demonstration order across trials. Together with temperature sampling, randomizing example order produces a rich set of rule outputs that vary in both content and emphasis, giving the later ensemble multiple independent views of how features may relate to the target.

# Instance and feature bagging to reduce prompt length and variance
Tabular datasets can have many columns and, in low-shot settings, feeding all columns and all few-shot examples into an LLM can exceed prompt size limits or degrade performance. FeatLLM addresses this by applying a bagging strategy to the inputs to each rule-generation trial. Two complementary bagging schemes are used: instance bagging and feature bagging.

Feature bagging selects a subset of columns (features) to include in the prompt for a given trial. By restricting the prompt to a smaller random subset, each LLM call remains compact and within token constraints, enabling FeatLLM to scale to tables with dozens or hundreds of attributes. Feature bagging also has a variance-reduction benefit: each trial effectively searches for rules in a different subspace of the original feature space, making it less likely that a single, spurious column will dominate the full system. Over many trials the ensemble covers the column space more broadly than any single prompt could without breaking token limits.

Instance bagging chooses a random subset of the available few-shot examples to serialize into the prompt for that trial. This reduces prompt length and introduces additional randomness — each trial sees different exemplars and therefore may favor different rule patterns. Instance bagging also stabilizes the downstream learned weights because training each trial's linear model on a slightly different view helps prevent overfitting to idiosyncrasies of particular examples.

Because each trial uses a smaller prompt (fewer features and/or fewer instances), FeatLLM avoids the practical constraint of long prompts while building an ensemble whose aggregate coverage approximates a larger, infeasible single-prompt exploration. The bagging approach thus simultaneously addresses scalability (prompt size limits) and variance (reducing sensitivity to spurious correlations present in any single small prompt).

# Averaging class probabilities across trials
Once each trial has produced a set of parsed rules and those rules are converted into binary features, FeatLLM fits a simple, non-negative-weight linear model per class to map the rule features to class logits. Let the trained weight vector for trial $t$ and class $k$ be $\mathbf{w}_k[t]$ and let the binary rule-feature vector for sample $i$ be $\mathbf{z}_k^i[t]$. The trial-specific logit is computed as

\[
\text{logit}_{k}^i[t] = \max(\mathbf{w}_k[t],0)\cdot \mathbf{z}_k^i[t],
\]

and the corresponding trial-level class probabilities use the softmax over classes. FeatLLM forms the final prediction by averaging these trial-level probabilities across $T$ independently generated trials. Concretely, for sample $i$ and class $k$,

\[
\mathbf{p}_k^i = \frac{1}{T}\sum_{t=1}^T \text{Softmax}_k\big(\{\text{logit}_{j}^i[t]\}_{j=1}^c\big).
\]

Averaging probabilities (rather than averaging logits or voting) is a simple, well-behaved aggregation: each trial contributes a calibrated soft estimate of class likelihood. Because each trial is trained independently on its own generated features, averaging reduces the influence of trials that produced poor or noisy rule sets and amplifies consensus among trials that consistently place probability mass on the same class.

# Self-consistency intuition: common rules across trials likely being reliable
The ensemble construction in FeatLLM leverages a self-consistency intuition: when an LLM is asked multiple times (with different random seeds and example orders) about the same task, rules or patterns that recur across many trials are more likely to be meaningful and germane to the true input–label relationship. Conversely, idiosyncratic rules that appear only in a few trials are more likely to reflect sampling noise, prompt artifacts, or spurious correlations in the few-shot exemplars.

Practically, self-consistency manifests in two ways inside FeatLLM. First, when the same or similar rule is proposed across many trials, that binary feature will be present in multiple trials and thus have repeated opportunities to be weighted highly by the corresponding linear models. In the averaging step, these consistent signals contribute coherently to the final probability. Second, trials that produce many low-quality rules will tend to assign low weights to those features during the per-trial tuning step; when these trials are averaged together with higher-quality trials, their negative impact is diluted.

This self-consistency effect is closely tied to the ensemble size: as more independent trials are sampled, recurring, true rules are more likely to appear multiple times by chance, while spurious rules remain rare. Thus the ensemble filters noisy LLM outputs implicitly without requiring a separate rule-validation mechanism.

# Trade-offs: ensemble size vs computation and diminishing returns
While ensembling and bagging bring concrete benefits in robustness, they introduce computation and API-query cost trade-offs that must be balanced. Each additional trial requires at least one LLM query to generate rules and a small amount of downstream computation to parse rules and fit the lightweight linear models. In FeatLLM experiments the authors used on the order of $T=20$ trials and observed that performance improves with $T$ but begins to plateau: accuracy gains diminish beyond a certain ensemble size. This empirical diminishing-return behavior is common in ensemble methods and reflects the fact that once most reliable rules have been discovered in multiple trials, additional trials primarily re-discover existing rules rather than adding new informative ones.

From a systems perspective, the ensemble size should be chosen to balance desired performance versus API and runtime budget. Smaller $T$ reduces cost and latency but risks missing some helpful rules or leaving more variance in the final predictor. Larger $T$ increases robustness and coverage of the feature space but yields greater query and parsing overhead. The bagging strategy partly mitigates this: by varying feature subsets and example subsets per trial, FeatLLM can achieve broad coverage even with a modest $T$, because each trial contributes a different slice of the column and instance space.

Finally, there is a trade-off in the number of rules extracted per trial. Asking the LLM for too many rules increases prompt complexity and downstream feature dimensionality, which in very low-shot regimes can lead to overfitting; asking for too few may under-express the predictive patterns. Empirically FeatLLM fixed a moderate number (e.g., 10 rules per class) as a practical compromise between prompt length and representation capacity.

In summary, ensembling with randomized LLM sampling and bagging of features and instances provides FeatLLM with a practical mechanism to scale to long tables, reduce sensitivity to spurious correlations, and amplify reliable heuristics via self-consistency. The practitioner must, however, tune ensemble size and per-trial prompt scope to trade off numerical performance against API cost and latency, mindful that beyond a moderate number of trials returns tend to diminish.
