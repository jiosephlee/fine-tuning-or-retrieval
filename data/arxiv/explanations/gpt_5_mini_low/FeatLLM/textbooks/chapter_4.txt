\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 4: FeatLLM: System Overview

# Design principle: LLM as rule/feature generator, not predictor
FeatLLM is built on a clear design principle: treat the large language model (LLM) as an expert feature engineer that produces human-interpretable rules, instead of using the LLM as a per-sample end-to-end predictor. The motivation for this design is twofold. First, LLMs encode broad prior knowledge and commonsense relationships that can be brought to bear on tabular prediction tasks; by asking the LLM to surface those relationships as rules, we explicitly capture that knowledge in a form that downstream models can use. Second, direct end-to-end prediction with LLMs requires passing every input sample through the model at inference time, which is costly, slow, and often infeasible when only API-level access is available. FeatLLM flips this pattern: the LLM is queried a limited number of times to produce rule-based features, and thereafter inference uses a lightweight model that reads only those generated features.

Conceptually, this design separates "knowledge extraction" from "statistical fitting." The LLM supplies rule templates and conditional statements that map raw input columns to binary indicators relevant to each class; these indicators are features that summarize the LLM's prior knowledge and any tendencies detectable from few-shot examples. The downstream learner then treats those binary features as inputs and estimates their importance from the labeled training samples. This separation has important practical consequences: it reduces dependence on the LLM at inference time, enables use of powerful closed-source LLM APIs (no fine-tuning required), and yields features that are interpretable and amenable to conventional ML machinery.

# Two-stage workflow: rule extraction then lightweight model fitting
FeatLLM operates in two clear stages. The first stage is rule extraction: using an in-context prompt, the LLM is asked to (a) infer how features generally relate to the target (leveraging prior knowledge), and then (b) synthesize a fixed number of decisive rules per class based on that prior knowledge plus the few-shot examples provided in the prompt. The prompt is structured into three parts: a basic information description (task description, feature names and types, and serialized few-shot examples), a reasoning instruction that splits the LLM's thought process into a prior-knowledge step and a data-driven rule derivation step, and response instructions that constrain the output format so the rules are parseable. This two-step reasoning—first general tendencies, then concrete rules—helps avoid overfitting to spurious correlations in a very small sample set by grounding rule generation in broader knowledge.

The second stage is lightweight model fitting. Once rules are generated, they are parsed and applied to the training samples to create binary rule-satisfaction features. FeatLLM trains a simple per-class linear model (without bias) over these binary features to compute class logits and probabilities. Specifically, for class $k$ and sample $i$, the LLM-derived binary feature vector is denoted $\mathbf{z}_k^i \in \{0,1\}^R$ where $R$ is the number of rules per class. The logit for class $k$ is computed as
\[
\text{logit}_k^i = \max(\mathbf{w}_k,0) \cdot \mathbf{z}_k^i,
\]
and class probabilities are obtained via softmax:
\[
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big).
\]
Only the linear weights $\{\mathbf{w}_k\}$ are trained (via cross-entropy loss and a small number of epochs with an optimizer such as Adam). Projecting weights into the non-negative subspace ensures that satisfying a rule cannot decrease a class's logit, reflecting the intuition that generated rules mark positive evidence for a class.

This two-stage pipeline has practical advantages: rule extraction relies on LLM reasoning, but the fitted model controls how much each rule matters on the observed few-shot data, enabling the system to discount rules that are irrelevant to the current dataset.

# Binary feature construction per class from rules
Rules returned by the LLM are expressed as conditional criteria that link original columns to target classes (for example, "age > 60 and chest pain = 'typical' implies higher risk"). FeatLLM transforms each such rule into a binary feature that indicates whether a given sample satisfies the rule. For a task with $c$ classes and $R$ rules per class (the paper fixes $R=10$ in experiments), the derived feature space effectively contains $c\times R$ binary features.

Because the LLM output is in natural language and can contain syntactic variation (for example, "greater than" vs. "$>$", or slight rephrasing), FeatLLM implements a parsing step to convert textual rules into executable code that evaluates the rule on tabular rows. Rather than building a brittle handcrafted parser, FeatLLM reutilizes the LLM for parsing: it supplies the inferred rules and a small function specification to the LLM and asks it to produce a simple parsing program (e.g., a Python function) that returns 0/1 for each rule when applied to a sample. The generated code is then executed (e.g., via Python's exec()) to obtain the binary feature values for all samples. This pragmatic use of the LLM leverages its strength at interpreting varied natural-language predicates without requiring fragile rule-engine construction.

Once the binary features are constructed, they serve as the sole inputs to the downstream lightweight model. A simple aggregation—counting how many rules of a class are satisfied—could be used as a logit proxy, but FeatLLM improves upon that by learning weights for each rule, so features are combined with learned importance rather than equal weighting.

# No training of the LLM; only API-level usage
A central practical constraint driving FeatLLM's design is the limited access to many highquality LLMs: some state-of-the-art models provide only inference APIs and do not permit parameter-efficient fine-tuning or access to training code. FeatLLM is explicitly designed to work under those constraints. The system treats the LLM as a black-box oracle for in-context generation and parsing; it never fine-tunes the LLM parameters.

This API-only approach means rule extraction and parsing require only a small number of LLM queries. In the experimental setup reported, each ensemble trial used a single query to generate rules and another to parse rules into code, and across trials the total API usage remains modest (e.g., the paper reports around 30 API queries in total). Because the LLM is not re-trained or adapted, FeatLLM retains portability across different models and avoids the engineering and cost burden associated with parameter-efficient tuning. It also means FeatLLM can be immediately applied to closed-source, high-performance LLMs that only expose inference endpoints.

# Decoupling inference from the LLM to lower latency and cost
One of FeatLLM's most important operational benefits is that, after rule extraction and parsing, no LLM calls are required for per-sample inference. Predictions on new samples are made by evaluating the parsed rule-logic (which is plain program code operating on tabular values) to produce binary features and then running the lightweight trained model (a linear layer and softmax). This decoupling reduces both latency and monetary cost relative to approaches that require an LLM to process each test example through a long serialized prompt.

In practice, the heavy-cost operations (LLM queries) are front-loaded and can be executed offline or in batch. The final deployed predictor is a simple deterministic program plus a small linear model; its inference time is comparable to standard tabular methods such as logistic regression or gradient-boosted trees. The paper's experiments confirm this: FeatLLM has low inference time similar to conventional learners, while other LLM-based baselines that run the LLM per-sample have substantially higher inference latency and cost. This architectural choice therefore makes FeatLLM suitable for real-world scenarios where rapid, repeated predictions are required and where LLM API calls per sample are impractical.

# Mitigating prompt-size issues via bagging and ensembling
LLMs have finite context windows, and when tabular datasets contain many features or when many few-shot examples must be serialized, prompt length can become a limiting factor. FeatLLM addresses this in two complementary ways: feature/instance bagging and ensembling.

In each trial of the ensemble, FeatLLM performs rule extraction using only a random subset of the dataset's features and/or training instances. This bagging reduces the prompt size per LLM query, allowing the system to operate even when the full dataset description would exceed the LLM's input limits. The LLM is therefore only asked to consider a manageable subset of features at a time, and it generates rules that are targeted to that subset.

Because each trial only sees a portion of the feature space, FeatLLM repeats the process multiple times (the paper uses on the order of $T=20$ trials) with randomized temperature and shuffled demonstration order to encourage diversity of the generated rule sets. Each trial produces a weight vector $\mathbf{w}[t]$ after fitting the lightweight model on its generated features. Final predictions are formed by averaging the class probability vectors across the ensemble:
\[
\overline{\mathbf{p}}^i = \frac{1}{T}\sum_{t=1}^T \mathbf{p}^i(\mathbf{w}[t]).
\]
This ensembling strategy accomplishes three goals simultaneously. First, it aggregates complementary pieces of information that individual trials capture, improving robustness and overall predictive performance. Second, it mitigates the risk that any single trial's LLM output contains incorrect or spurious rules—errors are diluted when many trials are averaged. Third, it ensures that the system scales to high-dimensional tabular problems by partitioning feature attention across trials, rather than overwhelming the LLM's prompt with all columns at once.

Together, bagging and ensembling let FeatLLM balance the LLM's prompt-size constraints against the need to cover a large or heterogeneous set of attributes, while preserving the low inference cost advantage by only requiring the LLM during the ensemble's generation stage (not per-sample prediction).
