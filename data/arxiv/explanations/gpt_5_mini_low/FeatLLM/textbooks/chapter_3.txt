\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 3: Problem Formulation and Setup

# Dataset notation: samples, features, labels, and feature metadata
We consider a tabular dataset used for supervised classification. The dataset is denoted by
\[
\mathcal{D} = \{(\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^{N},
\]
where $N$ is the total number of labeled samples. Each input sample $\mathbf{x}^i$ is a $d$-dimensional vector of feature values,
\[
\mathbf{x}^i = (x^i_1, x^i_2, \dots, x^i_d) \in \mathbb{R}^d \ \text{(or categorical encodings as appropriate)}.
\]
The dataset contains $d$ columns (attributes) and each column has a human-readable name. We denote the set of feature names by
\[
F = \{f_j\}_{j=1}^{d},
\]
where $f_j$ is the natural-language name for column $j$. In addition to the name, each feature may come with an optional textual description that explains its meaning or value type (for example, whether it is numerical or categorical, and, for categorical features, the possible categories). These descriptions are treated as metadata and are used by FeatLLM to guide rule generation.

The label for sample $i$ is denoted by $\mathbf{y}^i$. In the classification tasks considered, each $\mathbf{y}^i$ is a membership in a finite set of classes. If there are $c$ classes, labels can be represented as integers in $\{1,\dots,c\}$ or as one-hot vectors depending on the downstream loss formulation.

The FeatLLM pipeline operates in three conceptual stages: (1) it queries a large language model (LLM) to extract human-readable rules that relate features to classes, (2) it parses and applies those rules to the samples to produce engineered binary features, and (3) it fits a simple downstream model that maps those engineered features to class likelihoods. The notation above describes the original tabular input and its metadata, which are the starting point for the rule extraction and feature engineering steps.

# Few-shot regime definition (k-shot)
The work focuses on the few-shot learning regime, commonly described as $k$-shot learning. In this setup a small number, $k$, of labeled samples from the full dataset are used for training the downstream model (and for providing demonstration examples to the LLM). Formally, given the full dataset $\mathcal{D}$, a training subset of size $k$ is sampled:
\[
\mathcal{D}_{\text{train}} = \{(\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^{k},\quad k \ll N.
\]
The remainder of the data may be used for validation and testing. Typical values of $k$ in the experiments include very small counts such as 4, 8, 16, and up to 32; the design of the FeatLLM framework is intended to be particularly effective for small $k$.

In FeatLLM the same $k$ labeled examples serve two roles: they provide few-shot demonstrations inside the prompts to the LLM (so the model can leverage in-context learning) and they are used to learn the weights of the simple downstream predictor that maps rule-based features to class likelihoods. Because $k$ is small, the method is careful to leverage prior knowledge from the LLM and to keep the downstream model simple (low capacity) so that it can be reliably trained from few examples.

# Target: class likelihood estimation from engineered features
The ultimate prediction target is an estimate of the class likelihoods (class probabilities) for each input sample. FeatLLM transforms the original feature space into a set of binary features derived from the rules produced by the LLM. For each class $k\in\{1,\dots,c\}$ the LLM is prompted to produce $R$ rules (the paper uses a fixed number, e.g., $R=10$) that characterize conditions under which a sample would belong to that class. Each rule is a logical condition on one or more original features (for example, "$\text{age} > 60$ and \text{cholesterol} > 240$" or "$\text{marital\_status}$ in \{\text{single},\text{divorced}\}$").

After parsing and applying these rules to a sample $\mathbf{x}^i$, FeatLLM obtains for class $k$ a binary vector of rule-satisfaction indicators:
\[
\mathbf{z}_k^i \in \{0,1\}^R,
\]
where the $r$-th entry of $\mathbf{z}_k^i$ is 1 if and only if sample $i$ satisfies rule $r$ for class $k$.

To convert these engineered features into class probability estimates, the framework fits a simple linear model (no bias term) per class. Let $\mathbf{w}_k\in\mathbb{R}^R$ denote the trainable weight vector for class $k$. The logit for class $k$ on sample $i$ is computed as
\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,
\]
where $\max(\mathbf{w}_k, 0)$ denotes element-wise maximum to project the learned weights into a non-negative subspace. Projecting to non-negative weights enforces that satisfying a rule cannot decrease the logit for the class (i.e., features do not have negative contributions to class likelihood). The logits for all classes are combined with a softmax to produce class probabilities:
\[
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big).
\]
The model parameters $\{\mathbf{w}_k\}_{k=1}^c$ are learned by minimizing the cross-entropy loss on the available $k$ training examples (or via cross-validation within the small training set to select epochs). Because the downstream model is low capacity (linear, non-negative weights), it reduces the risk of overfitting in the few-shot regime while allowing the data to tune the relative importance of the LLM-derived rules.

The FeatLLM pipeline also employs ensemble techniques: the entire rule-generation → parsing → weighting cycle is repeated $T$ times with randomized LLM sampling (e.g., higher temperature and different example orders) and bagging (random subsets of features or instances) to produce $T$ models. The final class probability for a sample is the average of the probabilities predicted by the $T$ models, which stabilizes predictions and mitigates noisy or incorrect rules produced in individual trials.

# Assumptions: feature names and optional feature descriptions
FeatLLM assumes that each column in the tabular dataset has an associated natural-language name $f_j$ and, optionally, a textual description that clarifies the feature's meaning and type. The presence of such metadata is central to how the LLM is prompted: the prompt contains the task description, the feature names and descriptions (including value types and possible categories for categorical features), and serialized example demonstrations.

These assumptions are explicit in the prompt design. The feature descriptions help the LLM avoid type mismatches when it formulates rules (for example, it can avoid writing a rule that compares a categorical variable with a numeric threshold). When the dataset does not include detailed feature descriptions, FeatLLM still proceeds but ablation experiments in the paper show that including feature descriptions improves performance, especially in very small $k$ regimes, because the LLM can better leverage prior knowledge when the features are well described.

Another practical assumption is that the LLM is available via API-level access for inference. FeatLLM is designed to work without fine-tuning the LLM; it relies only on a modest number of API queries (one query per rule-generation trial plus queries to parse rules into executable code) rather than requiring per-sample LLM inferences at prediction time. This design choice reduces inference cost and makes the approach compatible with large LLMs that expose only inference APIs.

# Evaluation metrics overview (AUC/AUROC) and cross-validation usage
The primary evaluation metric used in the FeatLLM experiments is the area under the receiver operating characteristic curve (AUC or AUROC). AUC is a standard metric for binary (and can be adapted for multiclass via one-vs-rest averaging) classification tasks, measuring the ability of the model to rank positive instances higher than negative ones across all possible classification thresholds. In low-shot settings AUC is often preferred because it is threshold-agnostic and robust to class imbalance.

Empirical results reported in the paper present mean AUC scores (and standard deviations) across repeated trials with different random splits of training and test data. For model selection and hyper-parameter choices (for example, the number of training epochs for the linear weight tuning), the paper uses $k$-fold cross-validation on the available small training set, where $k$ is chosen (in the experimental setup) so that each fold still contains at least one example of every class. This cross-validation serves to reduce overfitting arising from running gradient-based optimization on very small datasets and to select a stopping epoch or other small-sample hyper-parameters reliably.

When reporting final results, the experiments repeat the entire process multiple times (for example, three repetitions with different training/test splits) and report the average AUC and its standard deviation to quantify variability due to sampling in the few-shot regime.

# Summary
To summarize, the problem setup treats tabular classification under few-shot constraints: a dataset with $N$ samples, $d$ named features (with optional descriptions), and $c$ classes. A small $k$-sized labeled training set is used both to demonstrate examples to an LLM and to train a low-capacity downstream model. The LLM is tasked with producing human-readable rules per class; those rules are parsed into binary rule-satisfaction features $\mathbf{z}_k^i$, and a non-negative-weight linear mapping converts those features to logits and class probabilities via softmax. Performance is measured primarily by AUROC, with cross-validation used within small training sets to mitigate overfitting and to select tuning hyper-parameters. The design choices—using feature metadata, enforcing low-capacity downstream models, and applying ensembling with bagging—are motivated by the need to be effective and robust in the $k$-shot regime while remaining compatible with LLMs accessible only through inference APIs.
