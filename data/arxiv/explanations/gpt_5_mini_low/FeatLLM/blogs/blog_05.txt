\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Beating the Context Window: Bagging and Ensembling for Scalable Few-Shot Tables

LLMs are great at reasoning from text, but naively serializing wide tabular datasets into prompts quickly runs into a hard limit: the context window. FeatLLM takes a different route. Instead of asking the LLM to predict each sample end-to-end, it asks the LLM to act as a feature engineer: generate human-readable rules, convert those rules into binary features, and train a lightweight downstream model. The trick that makes this strategy scale to wide tables and remain robust in few-shot regimes is an ensemble built from three simple sources of randomness: randomizing demonstration order, bagging features/instances, and using higher-temperature sampling to diversify rules. This post unpacks why that ensemble works and how it solves the context window and robustness problems in practice.

## The core idea in one line
Use an LLM to produce rule-based features (not per-sample predictions), parse those rules into binary features, fit a simple model (a non-negative linear scoring layer), and repeat this pipeline many times with randomized prompts and data subsets. Average the resulting class probabilities for a final, efficient predictor.

## How FeatLLM generates features
At each trial, FeatLLM prompts the LLM with:
- A short problem description and feature metadata (types, optional definitions).
- A few k-shot examples serialized as text (e.g., "age is 55. cholesterol is 240. Answer: yes").
- Reasoning guidance split into two steps: (1) infer general tendencies from feature descriptions (prior knowledge), (2) combine prior knowledge and the examples to produce class-specific rules.
- A strict response format for rules so they can be parsed.

The LLM returns a fixed number of rules per class (in the paper, R = 10), each rule expressed in natural language (e.g., "age > 50 and cholesterol > 200"). Those rules are parsed into executable code (the paper uses the LLM itself to generate parsing code) and applied to every sample to produce binary feature vectors z_k^i ∈ {0,1}^R for class k and sample i.

A simple linear scoring model maps those binary features to logits:
logit_k^i = max(w_k, 0) · z_k^i
and probabilities are produced with softmax across classes. The weights w_k are learned from the few-shot labeled data (cross-entropy), and projecting weights into the non-negative space ensures rules don't actively decrease a class score.

This pipeline already buys efficiency: once rules are generated and the linear model is trained, inference for new samples never touches the LLM.

## Where ensembling and bagging come in
A single LLM prompt may miss relevant rules, include noisy/spurious rules, or be limited by prompt length when the table has many columns. FeatLLM addresses this by repeating the whole rule-generation → parsing → feature-construction → linear-fit pipeline T times and averaging the class probabilities. The diversity of ensemble members comes from three controlled sources:

1. Randomizing demonstration order
   - In-context learning is sensitive to example order. FeatLLM randomly permutes the k-shot example order between trials to induce variation in the LLM's reasoning path and resulting rules.

2. Bagging features and instances
   - For each trial, FeatLLM selects a random subset of columns (features) and/or a subset of the few-shot instances. This reduces prompt length per trial (mitigating the context-window constraint) and lets different trials cover different parts of the original feature set. Aggregating many trials stitches together a broader coverage of the table without ever exceeding prompt limits.

3. Higher-temperature sampling
   - Setting a higher temperature (the paper refers abstractly to "sufficiently high" temperature for ensemble diversity) makes the LLM produce a wider range of plausible rules across trials, which increases the chance that some trials find high-quality, generalizable rules. In implementation the paper used GPT-3.5 with temperature = 0.5 during experiments, but notes raising temperature for ensemble diversity.

These three mechanisms create multiple "weak feature engineers": each trial produces a different set of rule-derived binary features. Averaging the probabilities from these trained linear scorers yields a robust final predictor.

## Why this improves robustness and scalability

- Mitigates prompt-size constraints: bagging columns/instances per trial keeps each prompt short. You never need to serialize hundreds of columns in a single prompt; instead, different trials cover different subsets and the ensemble aggregates information.
- Reduces sensitivity to spurious correlations: the LLM is guided with a two-step reasoning prompt (infer general tendencies, then derive rules using examples), which already lowers spuriously correlated rules. The ensemble further dilutes rules that appear only rarely (likely noisy) while reinforcing rules that appear consistently.
- Efficient inference: after feature generation and linear-weight tuning (done once per ensemble member), inference is a simple evaluation of binary features and a dot product with learned non-negative weights — no per-sample LLM calls.
- Works in few-shot settings: learning the importance of each rule via the simple linear model allows the system to filter unhelpful rules (weights near zero) even with very few labeled examples.

## Practical choices and observed behavior
- Number of rules per class: the paper fixes 10 rules per class per trial as a tradeoff between prompt length and expressivity. Too many rules increase dimensionality and risk overfitting in low-shot regimes.
- Number of ensembles T: performance improves with T but saturates; experiments showed gains converging around T ≈ 20.
- Weight tuning matters: summing raw binary features (no tuning) performs worse than fitting the non-negative linear weights; the benefit of tuning grows with more shots.
- Parsing noisy rule text: rather than hand-crafting brittle parsers, FeatLLM prompts the LLM to output simple parsing code (e.g., Python) and executes it to convert rules into binary features. This leverages the LLM's strength in interpreting permissive natural-language variants.
- API cost and runtime: FeatLLM needs only a modest number of LLM API queries (e.g., 30 in the paper’s reported runs) to build the ensemble. Training the small linear models and inference are inexpensive compared to per-sample LLM inference used by end-to-end LLM baselines.

## Empirical evidence (high level)
The paper evaluates FeatLLM across 13 tabular datasets (including UCI classics and synthetic tasks designed not to be memorized by LLMs). Key empirical observations:
- FeatLLM consistently ranked first or second across datasets in AUC, outperforming other few-shot approaches (LLM-based and classical).
- With as few as 4 shots, FeatLLM reached performance comparable to conventional methods trained with 32 shots.
- When irrelevant columns were appended to test robustness (spurious correlations experiment), FeatLLM degraded the least compared to baselines — indicating the ensemble+reasoning prompt helps avoid brittle rules.
- The ensemble approach allowed FeatLLM to handle datasets with many features despite LLM prompt limits, an area where other LLM-based baselines failed or became infeasible.

## When to use this pattern
- You have a tabular prediction task with very few labeled samples and meaningful natural-language feature names/descriptions.
- The table has many columns that cannot fit in a single prompt, or you want to avoid per-sample LLM inference for latency/cost reasons.
- You would like interpretable, rule-like features for downstream use or auditing.

## Limitations and caveats
- FeatLLM focuses on low-shot regimes; scaling to large labeled datasets may require different considerations.
- LLM priors can introduce biases; rules induced from prior knowledge may dominate when labeled data are scarce, so fairness and bias analyses are needed for sensitive domains.
- Diversity hyperparameters (temperature, bag size, T) and rule count require tuning; excessively high diversity can also produce many low-quality rules that the linear tuning step must filter.

## Takeaway
Bagging and ensembling turn an LLM’s rule-generation capability from a single brittle attempt into a scalable, robust feature-engineering pipeline. By randomizing demonstration order, bagging features/instances to stay within prompt limits, and promoting rule diversity via sampling temperature, FeatLLM constructs many complementary rule-sets and stitches them into a low-latency, accurate few-shot predictor. If you need LLM-powered induction over wide tables without per-sample API calls, this pattern is worth trying.
