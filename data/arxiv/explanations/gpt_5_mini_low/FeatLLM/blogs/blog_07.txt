\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Trust the Rules: Interpretability, Spurious Correlations, and Rule Quality

## Why rules?
FeatLLM reframes the use of Large Language Models (LLMs) for tabular, few-shot learning: instead of asking an LLM to predict each sample at inference time, it asks the LLM to act as a feature engineer that outputs human-readable rules. Those rules are parsed into binary features (does sample satisfy rule or not) and a lightweight downstream model uses them to estimate class probabilities. That change of role buys three practical benefits simultaneously: interpretability, low inference cost, and robustness in low-shot settings.

This post walks through why those rule-based features are interpretable and informative, how simple weight tuning filters weak or noisy rules, and why FeatLLM resists spurious columns better than baselines — with pointers to the quantitative analyses reported in the paper.

## How FeatLLM generates interpretable features
FeatLLM designs a prompt that explicitly asks the LLM to (1) reason about which features are plausibly related to the target (draw on prior knowledge), and then (2) produce a fixed number of decisive rules per class (the paper uses 10 rules/class per trial). Rules are constrained to a parseable format and then converted into executable code (via the LLM) to produce binary features z_k^i ∈ {0,1}^R for sample i and class k.

Because each generated feature corresponds to a named, human-readable rule (e.g., "if age > 65 and cholesterol > X then …"), a practitioner can inspect, interpret, and—if desired—edit or reject specific rules. That contrasts with opaque latent features learned by many representation methods.

## Weight tuning as an automatic filter for weak rules
Not all rules generated from a few examples are equally useful. FeatLLM addresses this by fitting a very simple downstream model that learns a non-negative importance for each rule:

logit_k^i = max(w_k, 0) · z_k^i
p^i = Softmax([logit_1^i, ..., logit_c^i])

The weight vector w_k is trained with cross-entropy on the available k-shot labeled data. Two key points make this step powerful:

- Non-negativity: projecting weights into a positive subspace (via max(w_k, 0)) prevents a generated rule from actively decreasing the likelihood of its associated class, which keeps learning stable when rules are noisy.
- Sparsifying effect in low-shot regimes: with few labeled examples, the learned weights naturally downweight rules that don't correlate with the labels. Empirically, the paper uses a small threshold (0.1) on learned weights to identify and effectively filter out low-importance rules.

Because the downstream model is linear and low-capacity, tuning is cheap and interpretable: the learned weight directly indicates the rule's usefulness.

## AUROC-of-features analysis — rule quality before and after tuning
To quantify how informative the generated rules are, the authors measured the average AUROC of each binary rule against the target label, and reported the fraction of rules with AUROC > 0.5. The main findings:

- Before tuning: the majority of generated rules already have AUROC > 0.5, showing that the LLM's prior knowledge plus few-shot examples produce many individually informative signals.
- After tuning: many of the low-AUROC (weak) rules become downweighted or effectively ignored by the learned weights; the tuning step increases the fraction of "useful" features that contribute to prediction.

In short, the LLM supplies a broad set of plausible, interpretable candidate features and the simple linear tuning stage selects and weights the genuinely predictive ones. This two-stage design leverages both prior knowledge (rule generation) and observed data (weight tuning) efficiently.

## Why FeatLLM is robust to spurious columns
The paper evaluates robustness to spurious covariates by attaching unrelated columns (drawn from another dataset) to a target dataset (Heart) while keeping the same few-shot training regime. Compared with conventional baselines and several LLM-based approaches, FeatLLM showed the smallest performance degradation as the number of unrelated columns increased.

There are several reasons for this robustness:

1. Guided reasoning prompt: FeatLLM's two-step prompt asks the LLM first to reason about which features *should* relate to the target (leveraging common-sense or domain priors) before extracting rules from the examples. This discourages inventing rules on obviously irrelevant columns.
2. Rule-format constraints and parsing: requiring parseable rules and converting them into explicit binary features reduces the likelihood of unpredictable, dataset-specific transformations that overfit noise.
3. Weight tuning and ensembling: the downstream weight learning filters out rules that do not correlate with labels in the few shots, and the ensemble with bagging dilutes the influence of occasional bad rule sets from any single LLM sample.
4. Empirical observation: across trials, only about 1–2% of generated rules came from noisy/unrelated columns in the reported experiment, and ensemble averaging further mitigated their effect.

Taken together, FeatLLM effectively combines human-interpretable priors (via LLM reasoning) with data-driven filtering (via weight tuning and ensembling), which is precisely the combination that combats spurious correlations in low-shot settings.

## Practical takeaways
- Interpretability is built in: every feature corresponds to an explicit rule you can read and audit. That helps debugging, fairness checks, and domain validation.
- Lightweight tuning is crucial: the simple non-negative linear model both improves accuracy and serves as an automatic filter for weak rules. In practice the paper uses cross-entropy training on the few labeled examples to learn weights.
- Ensemble + bagging matters: repeating rule generation with randomized demonstrations and subsets reduces sensitivity to prompt order and to prompt-size limits, and it converges in performance by around 20 ensembles in the experiments.
- Low inference cost: after the rule-generation and tuning stage (which requires only a modest number of LLM API queries — the paper reports about 30 API calls for their setting), predictions use only the learned linear weights on binary features, so per-sample inference is inexpensive and does not require further LLM calls.
- Robustness to spurious features is empirical, not absolute: FeatLLM degrades less than baselines in the tested setup, but the authors note it can still learn spurious correlations if related-but-misleading columns are present.

## Closing
FeatLLM illustrates an attractive middle ground: use an LLM not as a prediction black box for every sample, but as a generator of human-readable candidate features; then let a lightweight, interpretable tuner pick which candidates matter. That pipeline preserves much of the LLM's prior knowledge while giving practitioners inspectable rules and resilience to spurious noise — a pragmatic recipe for many low-shot tabular problems.
