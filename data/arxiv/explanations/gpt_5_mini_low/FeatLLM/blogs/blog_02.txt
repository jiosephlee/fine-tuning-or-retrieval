\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Why Current LLM-Tabular Methods Struggle—and How FeatLLM Fixes It

Large Language Models (LLMs) have obvious appeal for tabular problems: they carry broad prior knowledge, can reason in natural language, and—crucially—can often generalize from only a few examples. But the naive ways people have tried to apply LLMs to tabular data run into three practical roadblocks that make them hard to use in real systems: (1) high per-sample inference cost, (2) reliance on fine-tuning or restricted model access, and (3) prompt/context-window limitations when tables get wide. FeatLLM reframes the role of the LLM and, in doing so, addresses all three problems simultaneously. Below I summarize the pain points, the key idea behind FeatLLM, and why this design is better suited for real-world, few-shot tabular learning.

## The three practical pain points with current LLM–tabular methods

1. Per-sample LLM calls (inference latency and cost)
   - Many approaches serialize a row (or row + context) and send it to the LLM to get a prediction for that single sample. That means one LLM API call per prediction. This is expensive, slow, and often unacceptable for production systems where thousands or millions of rows must be scored.

2. Fine-tuning requirements and limited model access
   - Some successful methods rely on parameter-efficient fine-tuning (LoRA, IA3, etc.) of the LLM. Fine-tuning gives higher accuracy but assumes you have model weights and a training interface. Many top-tier LLMs are available only via inference APIs (no fine-tune access), making these approaches impractical for real deployments.

3. Prompt length / context-window limits
   - Tabular datasets can have many columns. Serializing many features (and many examples) produces very long prompts. LLMs have finite context windows, and performance often degrades when you approach or exceed them. That prevents straightforward scaling to wide tables or using large numbers of demonstrations.

In practice these three issues often interact: per-sample calls amplify cost, fine-tuning isn’t possible on API-only models, and long serialized prompts either hit hard limits or cause the LLM to perform worse.

## The core insight of FeatLLM

Instead of using the LLM as a black-box predictor for each row, FeatLLM uses the LLM as an expert feature engineer: ask the LLM to *explain* the mapping from features to labels in the form of human-readable rules, convert those rules into programmatic features, and then use a cheap downstream model for prediction.

High-level pipeline:
- Use in-context prompts (few-shot examples + feature descriptions + guided reasoning) to ask the LLM to produce a fixed set of rules per class. Each rule is a condition over original features (e.g., "age > 60 and cholesterol > 240").
- Parse the rules into executable code (FeatLLM actually asks the LLM to generate the small parsing / transformation function), and run that code to convert each row into new binary features: a feature is 1 if the rule applies to the row, 0 otherwise.
- Fit a simple downstream model (a linear model per class) on the new binary features. The model constrains weights to be non-negative and computes class logits as
  - logit_k^i = max(w_k, 0) · z_k^i
  - p^i = Softmax([logit_1^i, ..., logit_c^i])
  where z_k^i is the R-dimensional binary vector of rule-satisfaction for class k.
- Repeat feature generation with bagging/ensembling to increase robustness and to reduce effective prompt size per trial.

This design turns the LLM's knowledge into a compact, reusable feature set. After rules are generated and converted to code, inference for any number of rows is cheap and does not require further LLM calls.

## How FeatLLM solves the three pain points

1. Eliminates per-sample LLM calls
   - The LLM is queried only during the feature-engineering step (a modest number of queries, e.g., 20 ensemble trials in the paper). Once rules are parsed into executable code and the linear model is trained, scoring new rows does not call the LLM. This yields inference costs comparable to conventional tabular models and dramatically lower than per-sample LLM scoring.

2. Works with API-only LLM access (no fine-tuning required)
   - FeatLLM uses in-context learning and a small number of API queries to extract rules. It does not require weights or any fine-tuning capability. That makes it compatible with modern closed-source LLMs that only provide inference APIs.

3. Overcomes context-window limits via bagging and ensembling
   - Instead of trying to encode all features and many examples in a single, huge prompt, FeatLLM uses feature bagging: each trial samples a subset of features or examples and asks the LLM to produce rules for that subset. Across many trials, the ensemble aggregates diverse rules that together cover the dataset. This reduces per-prompt length and avoids hitting the LLM’s context window while still leveraging a large feature space.

Additional benefits:
- Interpretability: the learned features are explicit rules, often human-readable, which helps auditing and debugging.
- Data efficiency: FeatLLM is designed for few-shot regimes. In experiments, it performs strongly with only a handful of labeled examples (the paper reports that with 4 shots FeatLLM matches or approaches the performance of conventional models trained with 32 shots on many datasets).
- Noise/spurious-correlation resistance: the prompt design asks the LLM to first reason about which features are conceptually related to the task (step 1) and then use examples (step 2) to produce concrete rules. Empirically this reduces the generation of rules that rely on irrelevant columns; experiments adding unrelated columns showed FeatLLM degrades less than baselines.

## Important implementation details that make this practical

- Guided prompt structure: FeatLLM's prompt has three parts—(a) task & feature descriptions and serialized demonstrations, (b) reasoning instruction that enforces a two-step process (infer general tendencies, then derive rules using examples), and (c) response instruction that standardizes the rule format. This reduces spurious or ill-formed rules.
- Fixed rule budget per class: to avoid exploding prompt length and overfitting, FeatLLM extracts a fixed number of rules per class (the authors set 10 rules per class in experiments).
- Parsing via the LLM: because natural-language rule text can vary syntactically (e.g., ">" vs "greater than"), FeatLLM prompts the LLM to output the small parsing function/code that implements the rule checks. That code is executed (e.g., via Python exec) to produce binary features. Using the LLM to generate parsing code simplifies robust extraction without writing brittle parsers.
- Simple downstream model and weight projection: the linear model uses non-negative projected weights (max(w, 0)) so generated features cannot subtract from a class' logit, simplifying optimization and interpretation.
- Ensemble + randomization: the system uses multiple trials with high sampling temperature and randomized demonstration order to induce diverse rule sets; combining them reduces sensitivity to any single noisy rule set.

## Empirical takeaways (from the paper)

- FeatLLM was evaluated on 13 datasets spanning real-world and synthetic tasks (including Adult, Credit-g, Heart, Myocardial, and several newer or synthetic datasets not in LLM pretraining).
- It consistently ranked first or second across datasets in low-shot settings, and in aggregate outperformed recent LLM-based baselines like TabLLM and STUNT by a notable margin (the paper reports roughly a 10% average improvement over alternatives such as TabLLM and STUNT).
- With only 4 labeled examples, FeatLLM often matched the performance of conventional tabular models trained on 32 examples.
- Inference time is comparable to traditional models and far lower than per-sample LLM-based approaches. Training (rule generation) requires only a small number of API queries (e.g., 30 in their configuration), so the LLM usage cost is modest and parallelizable.

## Limitations and caveats

FeatLLM focuses on the few-shot regime. When large labeled datasets are available, traditional supervised learning can (and often will) outperform few-shot rule-based features. Also, LLM prior knowledge can carry societal biases or incorrect domain assumptions; FeatLLM can reflect those biases in generated rules. The authors note the importance of bias analysis and auditing when using LLM-generated rules in sensitive domains (healthcare, finance).

Finally, while bagging and ensembling mitigate context-size issues, there is a trade-off between the number of trials, prompt complexity, and the final feature set dimensionality—too many generated rules can overfit in very-low-shot regimes, so the paper uses a practical rule count (10 per class) and ensembles around 20 trials.

## Bottom line

If you want to use an API-only LLM to improve tabular predictions in a few-shot setting, don’t treat the LLM as a per-row predictor. Let the LLM be a feature engineer: have it generate rules, convert those rules to binary features, learn a lightweight model on top, and ensemble with bagging. That simple change in the role of the LLM addresses the three core deployment problems—latency/cost, fine-tuning access, and prompt-size limits—while delivering strong few-shot performance and interpretable features. FeatLLM is a clean, practical blueprint for making LLMs useful for real-world tabular tasks.
