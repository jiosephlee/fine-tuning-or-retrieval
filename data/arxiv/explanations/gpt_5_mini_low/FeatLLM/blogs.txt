# From Black Box to Feature Engineer: How FeatLLM Reimagines LLMs for Tabular AI

Large Language Models (LLMs) have been used as end-to-end predictors for many modalities, including tabular data. But running an LLM at inference for every row of a dataset is slow, expensive, and often impractical (especially when you only have API-level access and can't fine-tune the model). FeatLLM takes a different approach: treat the LLM as an automated feature engineer that writes human-readable, executable rules. Those rules become binary features fed into a small, fast downstream model. The result: most of the LLM work happens once up front, inference is cheap, and you avoid prompt-length and fine-tuning constraints.

Below I unpack the core ideas, the how, and the why FeatLLM works well for few-shot tabular learning.

## The core idea in one sentence

Instead of asking an LLM to predict labels for each sample, ask it to generate rule-based criteria (e.g., "if age > 50 and cholesterol > 240 then class = positive") for each class. Convert those rules into binary features, and learn a lightweight classifier on top of them.

## Why this shift matters

- Lower inference cost: Once you have the rule set, prediction for a new sample is just computing a few boolean conditions and evaluating a small model (a linear model in FeatLLM). You no longer need to query the LLM per sample.
- No fine-tuning required: FeatLLM uses in-context learning to extract rules. It only needs API-level access to the LLM; it does not require access to the model weights or tuning APIs (important when best-performing LLMs are only exposed via inference endpoints).
- Prompt-length handling: Serializing large tables into a single prompt quickly hits context-window limits. FeatLLM uses bagging and ensembling to split the problem across many smaller prompts, circumventing those limits while preserving robustness.

## How FeatLLM works — the pipeline

1. Prompt the LLM to extract rules
   - The prompt has three parts: (1) basic info (task description, feature names and types, and a few serialized examples), (2) reasoning instruction that guides the LLM through two steps (a general prior-knowledge step and then an example-grounded rule-derivation step), and (3) a response-format instruction so outputs are parseable and structured.
   - FeatLLM asks the LLM to produce a fixed number of rules per class (e.g., 10), which keeps outputs consistent and limits prompt growth.

2. Parse rules into executable code and generate binary features
   - The LLM outputs rules in natural language. Instead of hand-writing a brittle parser, FeatLLM asks the LLM itself to emit simple Python code that implements those rules.
   - Executing that code yields binary features: for class \(k\) and sample \(i\), a vector \(\mathbf{z}_k^i \in \{0,1\}^R\) indicating which of the \(R\) rules for class \(k\) are satisfied.

3. Train a small downstream model
   - FeatLLM fits a simple linear model (without bias) per class that maps rule-features to logits:
     \[
     \text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,
     \qquad
     \mathbf{p}^i = \text{Softmax}([\text{logit}_1^i,\dots,\text{logit}_c^i]).
     \]
   - The \(\max(\mathbf{w}_k,0)\) projection enforces non-negative weights so that each discovered rule can only increase class likelihood (interpretable and avoids rules that actively penalize a class).
   - Weights \(\mathbf{w}_k\) are learned from the few available labeled examples (few-shot regime) using cross-entropy.

4. Ensemble with bagging
   - To improve robustness and avoid prompt-size issues, FeatLLM repeats the whole rule-extraction process multiple times (with random subsets of features and examples), producing multiple rule sets and trained weight vectors \(\{\mathbf{w}[t]\}_{t=1}^T\).
   - Final prediction averages the softmax probabilities across the ensemble.
   - Randomness in the LLM calls (temperature) and ordering of examples adds diversity; bagging reduces per-prompt size.

## Why the LLM is a good feature engineer

LLMs carry broad prior knowledge and common-sense associations (e.g., "older patients are more likely to have certain conditions"). By designing prompts that first elicit prior knowledge (step 1) and then ask the model to ground that knowledge in a few examples (step 2), FeatLLM encourages discovery of meaningful, human-readable rules rather than brittle spurious correlations.

Two practical benefits follow:
- Interpretability: Rules are explicit and inspectable, making it easier to audit and debug behavior.
- Noise filtering: The reasoning step helps avoid rules built on irrelevant columns; empirical results show only a small fraction of extracted rules correspond to noisy features even when random unrelated columns are attached.

## Results highlights (what the paper found)

- FeatLLM was evaluated on 13 tabular datasets spanning domains and difficulties, including some datasets unlikely to be in the LLM pretraining data (recent UCI additions and synthetic datasets).
- In the few-shot regime, FeatLLM consistently ranked first or second versus baselines that included standard ML (logistic regression, XGBoost, RandomForest), semi-supervised or synthetic pretraining methods (SCARF, STUNT, TabPFN), and LLM-based baselines (in-context LLM, TABLET, TabLLM).
- With as few as 4 labeled examples, FeatLLM achieved performance comparable to conventional methods trained with 32 examples on several datasets.
- The generated rule-features were informative: a majority had AUROC > 0.5 with respect to the target, and the downstream tuning step filtered out low-importance rules automatically by assigning them small weights.
- Computational profile: FeatLLM incurs minimal inference cost (comparable to classic ML models) because inference does not call the LLM. Training requires a modest number of LLM API calls (e.g., tens of queries) that can be parallelized.

## Practical considerations and limitations

- Designed for low-shot settings: The framework is explicitly targeted at few-shot regimes. Extending to large-sample regimes is future work.
- Rule quantity and ensemble size are hyperparameters: The authors used 10 rules per class and ~20 ensemble members as pragmatic defaults; performance saturates beyond a point.
- LLM noise and parsing: Outputs can have syntactic variability. FeatLLM mitigates this by instructing the LLM to emit executable code for the rules, which is then executed to generate features.
- Prior knowledge bias: Since the LLM's priors influence extracted features, biases and misinformation encoded in the LLM can affect downstream predictions. The paper highlights this as an important direction for future analysis.

## When to use FeatLLM

FeatLLM is a good fit when you have:
- A tabular problem with few labeled examples.
- A need to minimize per-sample inference cost (e.g., real-time or large-scale scoring).
- Only inference/API access to an LLM (no fine-tuning).
- A desire for interpretable, rule-based features that can be audited.

## Final thoughts

FeatLLM reframes the role of LLMs from black-box predictors to intelligent feature engineers. That change is small in concept but large in practical impact: it preserves the LLM's ability to inject prior knowledge and perform reasoning, while avoiding high per-sample inference cost, fine-tuning requirements, and prompt-length constraints. The produced rule-features are human-interpretable and, when combined with a simple downstream learner and ensemble bagging, produce robust few-shot performance across diverse tabular tasks.

If you work on low-data tabular tasks and have access to an LLM API, FeatLLM is worth exploring: it's fast at inference, economical with API usage, and produces explainable features you can read, test, and refine.



# Why Current LLM-Tabular Methods Struggle—and How FeatLLM Fixes It

Large Language Models (LLMs) have obvious appeal for tabular problems: they carry broad prior knowledge, can reason in natural language, and—crucially—can often generalize from only a few examples. But the naive ways people have tried to apply LLMs to tabular data run into three practical roadblocks that make them hard to use in real systems: (1) high per-sample inference cost, (2) reliance on fine-tuning or restricted model access, and (3) prompt/context-window limitations when tables get wide. FeatLLM reframes the role of the LLM and, in doing so, addresses all three problems simultaneously. Below I summarize the pain points, the key idea behind FeatLLM, and why this design is better suited for real-world, few-shot tabular learning.

## The three practical pain points with current LLM–tabular methods

1. Per-sample LLM calls (inference latency and cost)
   - Many approaches serialize a row (or row + context) and send it to the LLM to get a prediction for that single sample. That means one LLM API call per prediction. This is expensive, slow, and often unacceptable for production systems where thousands or millions of rows must be scored.

2. Fine-tuning requirements and limited model access
   - Some successful methods rely on parameter-efficient fine-tuning (LoRA, IA3, etc.) of the LLM. Fine-tuning gives higher accuracy but assumes you have model weights and a training interface. Many top-tier LLMs are available only via inference APIs (no fine-tune access), making these approaches impractical for real deployments.

3. Prompt length / context-window limits
   - Tabular datasets can have many columns. Serializing many features (and many examples) produces very long prompts. LLMs have finite context windows, and performance often degrades when you approach or exceed them. That prevents straightforward scaling to wide tables or using large numbers of demonstrations.

In practice these three issues often interact: per-sample calls amplify cost, fine-tuning isn’t possible on API-only models, and long serialized prompts either hit hard limits or cause the LLM to perform worse.

## The core insight of FeatLLM

Instead of using the LLM as a black-box predictor for each row, FeatLLM uses the LLM as an expert feature engineer: ask the LLM to *explain* the mapping from features to labels in the form of human-readable rules, convert those rules into programmatic features, and then use a cheap downstream model for prediction.

High-level pipeline:
- Use in-context prompts (few-shot examples + feature descriptions + guided reasoning) to ask the LLM to produce a fixed set of rules per class. Each rule is a condition over original features (e.g., "age > 60 and cholesterol > 240").
- Parse the rules into executable code (FeatLLM actually asks the LLM to generate the small parsing / transformation function), and run that code to convert each row into new binary features: a feature is 1 if the rule applies to the row, 0 otherwise.
- Fit a simple downstream model (a linear model per class) on the new binary features. The model constrains weights to be non-negative and computes class logits as
  - logit_k^i = max(w_k, 0) · z_k^i
  - p^i = Softmax([logit_1^i, ..., logit_c^i])
  where z_k^i is the R-dimensional binary vector of rule-satisfaction for class k.
- Repeat feature generation with bagging/ensembling to increase robustness and to reduce effective prompt size per trial.

This design turns the LLM's knowledge into a compact, reusable feature set. After rules are generated and converted to code, inference for any number of rows is cheap and does not require further LLM calls.

## How FeatLLM solves the three pain points

1. Eliminates per-sample LLM calls
   - The LLM is queried only during the feature-engineering step (a modest number of queries, e.g., 20 ensemble trials in the paper). Once rules are parsed into executable code and the linear model is trained, scoring new rows does not call the LLM. This yields inference costs comparable to conventional tabular models and dramatically lower than per-sample LLM scoring.

2. Works with API-only LLM access (no fine-tuning required)
   - FeatLLM uses in-context learning and a small number of API queries to extract rules. It does not require weights or any fine-tuning capability. That makes it compatible with modern closed-source LLMs that only provide inference APIs.

3. Overcomes context-window limits via bagging and ensembling
   - Instead of trying to encode all features and many examples in a single, huge prompt, FeatLLM uses feature bagging: each trial samples a subset of features or examples and asks the LLM to produce rules for that subset. Across many trials, the ensemble aggregates diverse rules that together cover the dataset. This reduces per-prompt length and avoids hitting the LLM’s context window while still leveraging a large feature space.

Additional benefits:
- Interpretability: the learned features are explicit rules, often human-readable, which helps auditing and debugging.
- Data efficiency: FeatLLM is designed for few-shot regimes. In experiments, it performs strongly with only a handful of labeled examples (the paper reports that with 4 shots FeatLLM matches or approaches the performance of conventional models trained with 32 shots on many datasets).
- Noise/spurious-correlation resistance: the prompt design asks the LLM to first reason about which features are conceptually related to the task (step 1) and then use examples (step 2) to produce concrete rules. Empirically this reduces the generation of rules that rely on irrelevant columns; experiments adding unrelated columns showed FeatLLM degrades less than baselines.

## Important implementation details that make this practical

- Guided prompt structure: FeatLLM's prompt has three parts—(a) task & feature descriptions and serialized demonstrations, (b) reasoning instruction that enforces a two-step process (infer general tendencies, then derive rules using examples), and (c) response instruction that standardizes the rule format. This reduces spurious or ill-formed rules.
- Fixed rule budget per class: to avoid exploding prompt length and overfitting, FeatLLM extracts a fixed number of rules per class (the authors set 10 rules per class in experiments).
- Parsing via the LLM: because natural-language rule text can vary syntactically (e.g., ">" vs "greater than"), FeatLLM prompts the LLM to output the small parsing function/code that implements the rule checks. That code is executed (e.g., via Python exec) to produce binary features. Using the LLM to generate parsing code simplifies robust extraction without writing brittle parsers.
- Simple downstream model and weight projection: the linear model uses non-negative projected weights (max(w, 0)) so generated features cannot subtract from a class' logit, simplifying optimization and interpretation.
- Ensemble + randomization: the system uses multiple trials with high sampling temperature and randomized demonstration order to induce diverse rule sets; combining them reduces sensitivity to any single noisy rule set.

## Empirical takeaways (from the paper)

- FeatLLM was evaluated on 13 datasets spanning real-world and synthetic tasks (including Adult, Credit-g, Heart, Myocardial, and several newer or synthetic datasets not in LLM pretraining).
- It consistently ranked first or second across datasets in low-shot settings, and in aggregate outperformed recent LLM-based baselines like TabLLM and STUNT by a notable margin (the paper reports roughly a 10% average improvement over alternatives such as TabLLM and STUNT).
- With only 4 labeled examples, FeatLLM often matched the performance of conventional tabular models trained on 32 examples.
- Inference time is comparable to traditional models and far lower than per-sample LLM-based approaches. Training (rule generation) requires only a small number of API queries (e.g., 30 in their configuration), so the LLM usage cost is modest and parallelizable.

## Limitations and caveats

FeatLLM focuses on the few-shot regime. When large labeled datasets are available, traditional supervised learning can (and often will) outperform few-shot rule-based features. Also, LLM prior knowledge can carry societal biases or incorrect domain assumptions; FeatLLM can reflect those biases in generated rules. The authors note the importance of bias analysis and auditing when using LLM-generated rules in sensitive domains (healthcare, finance).

Finally, while bagging and ensembling mitigate context-size issues, there is a trade-off between the number of trials, prompt complexity, and the final feature set dimensionality—too many generated rules can overfit in very-low-shot regimes, so the paper uses a practical rule count (10 per class) and ensembles around 20 trials.

## Bottom line

If you want to use an API-only LLM to improve tabular predictions in a few-shot setting, don’t treat the LLM as a per-row predictor. Let the LLM be a feature engineer: have it generate rules, convert those rules to binary features, learn a lightweight model on top, and ensemble with bagging. That simple change in the role of the LLM addresses the three core deployment problems—latency/cost, fine-tuning access, and prompt-size limits—while delivering strong few-shot performance and interpretable features. FeatLLM is a clean, practical blueprint for making LLMs useful for real-world tabular tasks.



# Prompting for Power: The Two-Step Reasoning Recipe Behind FeatLLM’s Rules

## Overview

FeatLLM reframes how we use Large Language Models (LLMs) for tabular, few-shot learning: instead of using an LLM as a per-sample predictor, it asks the LLM to be a feature engineer. The LLM outputs human-readable "rules" that are parsed into binary features, and a simple downstream model (a linear classifier with non-negative weights) is trained on those features. The core trick that makes these rule features reliable is a two-step reasoning prompt design: first elicit general prior knowledge about feature–label relationships, then use a small set of labeled examples to extract concrete rules. This blog explains that two-step recipe, why it helps filter spurious patterns, and how it enforces type consistency and downstream robustness.

## The prompt structure at a glance

FeatLLM builds prompts from three components:

- Basic information: task description, feature names/types/definitions, and a few serialized example demonstrations.
- Reasoning instruction: an explicit two-step guide for the model to follow when generating rules.
- Response instruction: a strict output format specification so generated rules can be parsed into executable conditions.

The heart of the design is the "Reasoning instruction" block, which divides the LLM’s reasoning into:

1. Step 1 — Prior-knowledge reasoning: infer general tendencies or causal directions between features and the target without looking at the few-shot examples.
2. Step 2 — Example-driven rule extraction: combine the insights from Step 1 with the few-shot demonstrations to produce concrete rules for each class.

FeatLLM fixes the number of rules per class (e.g., 10) to avoid both trivial undercoverage and exploding prompts.

## Why split reasoning into two steps?

There are three practical benefits to separating general knowledge from example-specific rule extraction.

1. Leverage LLM priors explicitly. LLMs encode broad factual and commonsense knowledge (e.g., "age is correlated with disease risk" or "higher credit utilization correlates with default risk"). Step 1 encourages the model to surface that background knowledge first. When the LLM later formulates rules, it does so informed by that prior, improving the chance the rules reflect domain-relevant signals rather than noise.

2. Reduce overfitting to tiny samples. If the LLM were allowed to go straight from a few noisy examples to rules, it could latch onto spurious correlations present in those examples. By separating out Step 1, the model is nudged to prefer rules that align with general tendencies before fitting specifics. That bias toward plausible, prior-consistent explanations reduces the likelihood of inventing brittle, dataset-specific rules.

3. Focus attention on informative features. Step 1 helps the LLM rank or identify which features are likely relevant to the label. Step 2 then concentrates rule-extraction on those candidate features rather than scanning all columns equally. In experiments this results in only ~1–2% of rules relying on obviously irrelevant (noisy) columns when unrelated features are injected.

## How the two steps are implemented in the prompt

Practically, the prompt includes:

- A short chain-of-thought-like intro encouraging structured reasoning.
- Step 1 instruction: “Without using the examples, describe likely relationships or causal tendencies between each feature and the target.” This asks the model to reason from general knowledge and feature definitions (the prompt supplies feature types and optional definitions).
- Step 2 instruction: “Using the few-shot examples and your Step 1 conclusions, generate up to R rules per class that decide class membership.” The prompt also constrains rule count and asks the LLM to obey feature types when forming conditions.

These instructions are explicit: the LLM produces a textual answer that first lists its general tendencies and then lists rules in a parsable template.

## Enforcing type-consistent rules

FeatLLM provides feature descriptions (value types, possible categories, and optional definitions) in the basic information block. When the LLM is told the feature types and asked in Step 2 to produce rules, it is guided to pick operators and comparisons appropriate to each feature type: numeric features get inequalities, categorical features get membership checks, textual features get substring-like conditions, etc.

This explicit typing minimizes syntactic and semantic mismatches (e.g., comparing a string to a numeric threshold). Still, the LLM output can vary in phrasing (">" vs "greater than"), so FeatLLM uses a secondary parsing step: it asks the LLM to translate each natural-language rule into simple executable code (e.g., a short Python condition). That generated code is executed (via Python's exec) to create binary rule-features automatically.

## From rules to features to predictions

Once rules are parsed into code, FeatLLM applies them to every sample to produce binary vectors. For class k, each sample gets a vector z_k ∈ {0,1}^R indicating which of the R rules for class k are satisfied.

The downstream likelihood estimation is intentionally simple: a linear logit per class computed as

logit_k = max(w_k, 0) · z_k,

followed by a softmax over classes to get probabilities. The non-negativity projection (max(w_k, 0)) forces rule activations to contribute positively to class evidence, reflecting the intuition that a generated rule should increase belief in its target class rather than actively reduce it. The linear weights w_k are learned from the few-shot training samples (cross-entropy loss), which also filters out weak or irrelevant rules by assigning them small weights.

## Robustness via bagging and ensembling

Two additional mechanisms strengthen the approach:

- Feature/instance bagging: each generation trial samples subsets of features and examples, keeping prompt size manageable and forcing diversity in the rule sets.
- Ensembling: run the entire generation → parse → train pipeline T times (with high sampling temperature and randomized demonstration orders) and average predicted probabilities across trials.

Because LLM outputs are stochastic and can sometimes produce imperfect rules, the ensemble averages out bad trials and yields a more stable predictor. This is crucial for datasets with many features where a single prompt cannot include everything without exceeding context limits.

## Why this filter spurious patterns better than naive in-context prompts

- A plain in-context prompt that only serializes examples into the LLM can directly mirror spurious coincidences present in the few examples. FeatLLM’s Step 1 creates a prior-anchored scaffold that resists such coincidences.
- Type-aware instructions reduce syntactic mistakes and illogical comparisons, increasing the fraction of rules that are actually executable and meaningful.
- Learning non-negative weights and tuning on the few-shot data filters out rules that are not predictive in practice, which helps discard remaining noisy rules.

Empirically (as reported in the paper), this combination produces a majority of useful features (measured by AUROC against the target) even before tuning, and tuning further removes irrelevant ones.

## Practical notes and limitations

- The method is designed for few-shot regimes; the approach fixes a relatively small number of rules per class (e.g., 10) to balance expressiveness and prompt length.
- The LLM needs only API-level access for rule generation; FeatLLM avoids per-sample LLM inference at test time because the final predictor uses only the generated features and a lightweight trained model.
- Parsing relies on the LLM’s ability to translate noisy natural-language rules into correct code; this is handled by a focused parsing prompt, but it can still fail occasionally and is mitigated by ensembling.

## Takeaway

The two-step reasoning prompt in FeatLLM is a practical template for converting LLM priors into structured, type-safe, and parsable rules: first extract general relationships from prior knowledge, then use few-shot examples to ground those relationships into concrete rules. Combined with type guidance, LLM-driven parsing, non-negative linear tuning, and ensemble bagging, this recipe yields robust, high-quality rule-features that make LLM-powered few-shot tabular learning both efficient and interpretable.



# From Text to Toggles: Turning LLM Rules into Binary Features and Predictions

## Overview

FeatLLM takes a different approach to using large language models (LLMs) for tabular prediction. Instead of asking an LLM to output a prediction for every sample at inference time, it asks the LLM to explain the decision boundary: produce human-readable rules (e.g., "age > 50 AND smoker = yes") that capture conditions indicative of each class. Those natural-language rules are then parsed into executable code, applied across the dataset to produce binary features (toggles), and fed into a very simple predictive model: a non-negative linear model whose outputs are converted into class probabilities via softmax.

This post walks through that pipeline: how rule text becomes code, how toggles are constructed, how the linear model computes class likelihoods, and why learning per-rule weights is crucial—especially in few-shot settings.

## 1) Generating rules with an LLM

Given a small labeled training set and natural-language feature descriptions, FeatLLM prompts an LLM to output a fixed number of rules per class (the paper uses 10 per class). The prompt is structured in three parts:

- Basic information: task description, feature names/types/definitions, and serialized few-shot examples.
- Reasoning instruction: a two-step nudge that first asks the LLM to reason from prior knowledge (relationships between features and labels) and then to use the few-shot examples to derive concrete rules. This reduces spurious correlations.
- Response instruction: a constrained output format so downstream parsing is easier.

The LLM returns rules in text. In practise the LLM may vary syntax (e.g., "greater than" vs. ">"), and can introduce small formatting noise. Rather than building a brittle hand-written parser, FeatLLM again leverages the LLM to turn the textual rules into simple, executable code.

## 2) Parsing text rules into executable code

Parsing is handled by asking the LLM to output a small function (e.g., Python) that implements the rules. The prompt provided to the LLM contains the inferred rules, a function signature, and input/output expectations. The LLM then generates code that evaluates each rule for a given row and returns a set of binary indicators.

The generated code is executed (the paper uses Python’s exec()), producing for each sample a binary vector per class:
- For class \(k\), the rule-derived feature vector for sample \(i\) is \(\mathbf{z}_k^i \in \{0,1\}^R\), where \(R\) is the number of rules per class.

This approach sidesteps fragile text parsing and uses the LLM’s strengths at semantic interpretation and code generation. It also produces deterministic, fast evaluation of rules at inference time: once the code is generated and executed, making predictions on new samples does not require any more LLM calls.

## 3) From toggles to class likelihoods: a non-negative linear model

Having turned each rule into a binary toggle, FeatLLM computes class logits using a separate linear weight vector per class. For class \(k\) and sample \(i\), the logit is:

logit_k^i = max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,

and the class probabilities are

\mathbf{p}^i = \text{Softmax}([ \text{logit}_1^i, \dots, \text{logit}_c^i ]).

Key implementation details from the paper:

- The model is linear, with no bias term in the described formulation.
- The weights are constrained to be non-negative by applying an elementwise projection \(\max(\mathbf{w}_k, 0)\). This enforces that satisfying a rule cannot *decrease* the likelihood of its associated class.
- The model is trained with cross-entropy loss on the few-shot labeled set. Training is lightweight: typically a small number of epochs with a simple optimizer (the paper uses Adam with learning rate 0.01 and 200 epochs, chosen by cross-validation).

Why a simple linear model? Because once the LLM has provided a set of informative, interpretable binary features, a complex model is often unnecessary—especially in low-shot regimes where heavy models easily overfit.

## 4) Why per-rule weights matter (especially in few-shot)

You might wonder: if rules are already informative, why not just count satisfied rules per class and pick the class with the highest count? There are three reasons FeatLLM learns per-rule weights:

1. Different rules carry different degrees of evidence. A rule like "age > 80" may be much stronger for a medical outcome than "systolic_bp > 120". Learning weights lets the model up-weight strong rules and down-weight weak ones.

2. Rules can be correlated and overlapping. A naive count treats correlated rules as independent votes, which can exaggerate their combined effect. Learned weights can compensate for redundancy.

3. Robustness in few-shot learning. With only a handful of labeled examples, some generated rules may be spurious or irrelevant to the specific data distribution. Training learns to assign low weights to such rules, effectively filtering noise. The paper shows that after tuning, many rules with little empirical relevance get down-weighted or pruned (weights below a threshold), improving predictive performance.

Ablation in the paper confirms that removing weight tuning (i.e., using raw rule counts) degrades performance, and the benefit of tuning grows with more shots (because importance estimation becomes more reliable as labeled data increases).

## 5) Ensemble + bagging: dealing with prompt limits and uncertainty

FeatLLM repeats the whole rule-generation + parsing + linear tuning process multiple times (the paper uses \(T=20\) ensembles). Each trial randomizes aspects of the LLM call (higher sampling temperature, different order of few-shot examples) and uses bagging (sampling subsets of features or instances) to produce diverse rule sets. The resulting predictions are averaged across ensembles.

This ensemble strategy provides two wins:

- Robustness: incorrect rules from some trials are compensated by correct rules from others (self-consistency).
- Prompt-size mitigation: since each trial may only ask the LLM to consider a subset of features, the approach scales better to wide tables where a single prompt would be too long.

Importantly, ensembles are only used during the offline rule-generation and training phase. At inference time, prediction uses the generated binary features and the trained (or ensembled) linear weights—no per-sample LLM calls are required.

## 6) Practical implications and takeaways

- Turning natural-language rules into executable toggles leverages LLM strengths (reasoning + code generation) while avoiding expensive per-sample LLM inference.
- A lightweight non-negative linear model on top of LLM-generated toggles is effective and interpretable. The projection \(\max(\mathbf{w},0)\) ensures rules only add positive evidence.
- Learning per-rule weights is critical in few-shot regimes to filter spurious rules, handle correlation, and assign proper importance.
- Ensemble + bagging adds robustness and helps scale to wide feature sets without exploding prompt size.

FeatLLM demonstrates that LLMs can act as high-quality feature engineers: they translate prior knowledge into concrete, executable criteria, and a simple learned aggregation can turn those criteria into accurate class likelihoods in low-shot tabular tasks.



# Beating the Context Window: Bagging and Ensembling for Scalable Few-Shot Tables

LLMs are great at reasoning from text, but naively serializing wide tabular datasets into prompts quickly runs into a hard limit: the context window. FeatLLM takes a different route. Instead of asking the LLM to predict each sample end-to-end, it asks the LLM to act as a feature engineer: generate human-readable rules, convert those rules into binary features, and train a lightweight downstream model. The trick that makes this strategy scale to wide tables and remain robust in few-shot regimes is an ensemble built from three simple sources of randomness: randomizing demonstration order, bagging features/instances, and using higher-temperature sampling to diversify rules. This post unpacks why that ensemble works and how it solves the context window and robustness problems in practice.

## The core idea in one line
Use an LLM to produce rule-based features (not per-sample predictions), parse those rules into binary features, fit a simple model (a non-negative linear scoring layer), and repeat this pipeline many times with randomized prompts and data subsets. Average the resulting class probabilities for a final, efficient predictor.

## How FeatLLM generates features
At each trial, FeatLLM prompts the LLM with:
- A short problem description and feature metadata (types, optional definitions).
- A few k-shot examples serialized as text (e.g., "age is 55. cholesterol is 240. Answer: yes").
- Reasoning guidance split into two steps: (1) infer general tendencies from feature descriptions (prior knowledge), (2) combine prior knowledge and the examples to produce class-specific rules.
- A strict response format for rules so they can be parsed.

The LLM returns a fixed number of rules per class (in the paper, R = 10), each rule expressed in natural language (e.g., "age > 50 and cholesterol > 200"). Those rules are parsed into executable code (the paper uses the LLM itself to generate parsing code) and applied to every sample to produce binary feature vectors z_k^i ∈ {0,1}^R for class k and sample i.

A simple linear scoring model maps those binary features to logits:
logit_k^i = max(w_k, 0) · z_k^i
and probabilities are produced with softmax across classes. The weights w_k are learned from the few-shot labeled data (cross-entropy), and projecting weights into the non-negative space ensures rules don't actively decrease a class score.

This pipeline already buys efficiency: once rules are generated and the linear model is trained, inference for new samples never touches the LLM.

## Where ensembling and bagging come in
A single LLM prompt may miss relevant rules, include noisy/spurious rules, or be limited by prompt length when the table has many columns. FeatLLM addresses this by repeating the whole rule-generation → parsing → feature-construction → linear-fit pipeline T times and averaging the class probabilities. The diversity of ensemble members comes from three controlled sources:

1. Randomizing demonstration order
   - In-context learning is sensitive to example order. FeatLLM randomly permutes the k-shot example order between trials to induce variation in the LLM's reasoning path and resulting rules.

2. Bagging features and instances
   - For each trial, FeatLLM selects a random subset of columns (features) and/or a subset of the few-shot instances. This reduces prompt length per trial (mitigating the context-window constraint) and lets different trials cover different parts of the original feature set. Aggregating many trials stitches together a broader coverage of the table without ever exceeding prompt limits.

3. Higher-temperature sampling
   - Setting a higher temperature (the paper refers abstractly to "sufficiently high" temperature for ensemble diversity) makes the LLM produce a wider range of plausible rules across trials, which increases the chance that some trials find high-quality, generalizable rules. In implementation the paper used GPT-3.5 with temperature = 0.5 during experiments, but notes raising temperature for ensemble diversity.

These three mechanisms create multiple "weak feature engineers": each trial produces a different set of rule-derived binary features. Averaging the probabilities from these trained linear scorers yields a robust final predictor.

## Why this improves robustness and scalability

- Mitigates prompt-size constraints: bagging columns/instances per trial keeps each prompt short. You never need to serialize hundreds of columns in a single prompt; instead, different trials cover different subsets and the ensemble aggregates information.
- Reduces sensitivity to spurious correlations: the LLM is guided with a two-step reasoning prompt (infer general tendencies, then derive rules using examples), which already lowers spuriously correlated rules. The ensemble further dilutes rules that appear only rarely (likely noisy) while reinforcing rules that appear consistently.
- Efficient inference: after feature generation and linear-weight tuning (done once per ensemble member), inference is a simple evaluation of binary features and a dot product with learned non-negative weights — no per-sample LLM calls.
- Works in few-shot settings: learning the importance of each rule via the simple linear model allows the system to filter unhelpful rules (weights near zero) even with very few labeled examples.

## Practical choices and observed behavior
- Number of rules per class: the paper fixes 10 rules per class per trial as a tradeoff between prompt length and expressivity. Too many rules increase dimensionality and risk overfitting in low-shot regimes.
- Number of ensembles T: performance improves with T but saturates; experiments showed gains converging around T ≈ 20.
- Weight tuning matters: summing raw binary features (no tuning) performs worse than fitting the non-negative linear weights; the benefit of tuning grows with more shots.
- Parsing noisy rule text: rather than hand-crafting brittle parsers, FeatLLM prompts the LLM to output simple parsing code (e.g., Python) and executes it to convert rules into binary features. This leverages the LLM's strength in interpreting permissive natural-language variants.
- API cost and runtime: FeatLLM needs only a modest number of LLM API queries (e.g., 30 in the paper’s reported runs) to build the ensemble. Training the small linear models and inference are inexpensive compared to per-sample LLM inference used by end-to-end LLM baselines.

## Empirical evidence (high level)
The paper evaluates FeatLLM across 13 tabular datasets (including UCI classics and synthetic tasks designed not to be memorized by LLMs). Key empirical observations:
- FeatLLM consistently ranked first or second across datasets in AUC, outperforming other few-shot approaches (LLM-based and classical).
- With as few as 4 shots, FeatLLM reached performance comparable to conventional methods trained with 32 shots.
- When irrelevant columns were appended to test robustness (spurious correlations experiment), FeatLLM degraded the least compared to baselines — indicating the ensemble+reasoning prompt helps avoid brittle rules.
- The ensemble approach allowed FeatLLM to handle datasets with many features despite LLM prompt limits, an area where other LLM-based baselines failed or became infeasible.

## When to use this pattern
- You have a tabular prediction task with very few labeled samples and meaningful natural-language feature names/descriptions.
- The table has many columns that cannot fit in a single prompt, or you want to avoid per-sample LLM inference for latency/cost reasons.
- You would like interpretable, rule-like features for downstream use or auditing.

## Limitations and caveats
- FeatLLM focuses on low-shot regimes; scaling to large labeled datasets may require different considerations.
- LLM priors can introduce biases; rules induced from prior knowledge may dominate when labeled data are scarce, so fairness and bias analyses are needed for sensitive domains.
- Diversity hyperparameters (temperature, bag size, T) and rule count require tuning; excessively high diversity can also produce many low-quality rules that the linear tuning step must filter.

## Takeaway
Bagging and ensembling turn an LLM’s rule-generation capability from a single brittle attempt into a scalable, robust feature-engineering pipeline. By randomizing demonstration order, bagging features/instances to stay within prompt limits, and promoting rule diversity via sampling temperature, FeatLLM constructs many complementary rule-sets and stitches them into a low-latency, accurate few-shot predictor. If you need LLM-powered induction over wide tables without per-sample API calls, this pattern is worth trying.



# Show Me the Numbers: FeatLLM’s Performance and Cost vs. Popular Baselines

## TL;DR
FeatLLM uses an LLM as a feature engineer (producing rule-based binary features) and then trains a lightweight downstream model. Across 13 tabular datasets in few-shot regimes, FeatLLM delivers substantially better predictive performance—about a 10% average improvement over LLM-based baselines like TabLLM and STUNT—while keeping inference costs close to classic ML models. In ultra-low-shot settings (e.g., 4 shots) FeatLLM attains AUROC comparable to conventional methods trained with many more examples (e.g., 32 shots). Training requires only a small number of LLM API calls (the paper reports ~30), and no LLM calls are needed at per-sample inference time.

## Short recap of how FeatLLM works (one-paragraph)
FeatLLM prompts an LLM to extract human-readable “rules” (conditions that indicate class membership) from a task description, feature definitions, and a few labeled examples. The LLM’s textual rules are parsed (again via the LLM) into executable code that produces binary features for each sample (one binary per rule). A simple parametric model (a non-negative-weight linear model per class) is trained on those binary features to produce class probabilities. To improve robustness and handle prompt-size limits, the whole process is repeated with bagging and ensembling (the authors use 20 trials and 10 rules per class in their main experiments).

## What was evaluated
- 13 datasets spanning healthcare, finance, public datasets, and synthetic problems (e.g., Adult, Bank, Heart, Myocardial, Cultivars, NHANES, Sequence-type, Solution-mix).
- Few-shot regimes (k-shot experiments with k small — examples discussed include 4 and 16 shots).
- Baselines: classic ML (Logistic Regression, XGBoost, RandomForest), data-augmentation/semi-supervised methods (SCARF, STUNT), synthetic-prior methods (TabPFN), and other LLM-based methods (in-context prompting, TABLET, TabLLM).

## Key quantitative findings

Performance
- Across the 13 datasets, FeatLLM consistently ranks first or second among baselines. The paper reports an average improvement of roughly 10% (AUC/AUROC) over LLM-based competitors such as TabLLM and STUNT.
- In ultra-low-shot settings (example: 4-shot), FeatLLM achieves performance comparable to conventional tabular methods trained with far more labeled examples (example: similar AUROC to methods using 32 shots). This highlights strong data efficiency from LLM-driven feature extraction.
- Feature quality checks in the paper show that a large fraction of generated rule-features are informative (many rules yield AUROC > 0.5 with respect to the label before tuning), and tuning the downstream weights filters out weak/noisy rules.

Robustness to spurious features
- When random irrelevant columns (from another dataset) are attached to a target dataset, FeatLLM suffers less performance degradation than the baselines. The framework’s explicit reasoning step (asking the LLM to infer which features matter, then derive rules) reduces the fraction of rules based on noisy columns (the paper notes only ~1–2% of rules came from noisy columns in their test).

Hyperparameters and ensemble
- Main hyperparameters: number of ensemble trials (improves up to ~20 and then saturates) and rules-per-class (the authors use 10 rules per class as a practical trade-off between prompt length and feature expressiveness).

## Training and inference cost — the important numbers
- LLM API usage: FeatLLM requires only a small number of LLM queries per trained model. The paper reports around 30 API queries to generate rule sets across ensemble trials (these calls can be parallelized).
- No per-sample LLM calls at inference time. The inference pipeline uses only the generated code and a trained lightweight model (binary feature extraction + linear model), so per-sample inference cost is comparable to classic ML methods (LogReg/XGBoost/RandomForest).
- Runtime comparisons (Adult dataset, 16-shot example): FeatLLM shows low inference time comparable to conventional methods. In contrast, other LLM-based approaches that perform end-to-end LLM inference per sample (in-context, TABLET, TabLLM) have much higher inference latency and compute cost.
- Training-time perspective: FeatLLM’s overall training time (including LLM querying + linear model fitting) is comparable to other LLM-based methods in the paper. Crucially, because FeatLLM does not fine-tune a large LLM, it avoids the GPU-heavy costs of fine-tuning. Note: TabLLM’s experiments required model-parallel hardware (TabLLM used four A100 GPUs), while FeatLLM uses only API calls for the LLM backbone (GPT-3.5 in the paper) and a small downstream optimization run on a single GPU or CPU.

Why this matters in practice
- Low inference overhead: In settings where hundreds or millions of predictions are needed, per-sample LLM inference is impractical. FeatLLM’s zero-LLM-at-inference design makes it feasible for production deployment.
- API-only friendly: FeatLLM works with LLMs accessible only via API (no fine-tuning required). That broadens applicability to top-performing LLMs that expose only inference endpoints.
- Data efficiency: Achieving near high-shot performance from only a few labeled examples reduces labeling costs, which is crucial in domains like healthcare and finance.

## Practical configuration used in the paper (so you can reproduce)
- LLM backbone: GPT-3.5 (the approach is LLM-agnostic).
- Ensemble trials: 20.
- Rules per class per trial: 10.
- LLM generation temperature: 0.5 (top-p = 1).
- Downstream optimizer: Adam, learning rate 0.01, 200 epochs; k-fold cross-validation used for epoch selection.
- Parsing: LLM-assisted generation of simple code from rules; code executed to produce binary features.

## Limitations to keep in mind
- FeatLLM focuses on low-shot regimes; its advantages may shrink when large labeled datasets are available and conventional ML can be fully trained.
- The quality of engineered features depends on the LLM’s prior knowledge and reasoning; biases or misinformation in the LLM could influence the generated rules (the paper flags this as an area for future study).
- While parsing is robustified by using the LLM to generate code, occasional noisy outputs still require careful prompt constraints and validation.

## Bottom line
If you need strong few-shot performance on tabular data without incurring per-sample LLM inference costs or fine-tuning large models, FeatLLM gives a practical and effective compromise: it capitalizes on LLM priors to build concise, interpretable rule-features, trains a tiny downstream model, and yields about a 10% average AUC improvement over competing LLM-based methods while keeping inference cost on par with classic ML.



# Trust the Rules: Interpretability, Spurious Correlations, and Rule Quality

## Why rules?
FeatLLM reframes the use of Large Language Models (LLMs) for tabular, few-shot learning: instead of asking an LLM to predict each sample at inference time, it asks the LLM to act as a feature engineer that outputs human-readable rules. Those rules are parsed into binary features (does sample satisfy rule or not) and a lightweight downstream model uses them to estimate class probabilities. That change of role buys three practical benefits simultaneously: interpretability, low inference cost, and robustness in low-shot settings.

This post walks through why those rule-based features are interpretable and informative, how simple weight tuning filters weak or noisy rules, and why FeatLLM resists spurious columns better than baselines — with pointers to the quantitative analyses reported in the paper.

## How FeatLLM generates interpretable features
FeatLLM designs a prompt that explicitly asks the LLM to (1) reason about which features are plausibly related to the target (draw on prior knowledge), and then (2) produce a fixed number of decisive rules per class (the paper uses 10 rules/class per trial). Rules are constrained to a parseable format and then converted into executable code (via the LLM) to produce binary features z_k^i ∈ {0,1}^R for sample i and class k.

Because each generated feature corresponds to a named, human-readable rule (e.g., "if age > 65 and cholesterol > X then …"), a practitioner can inspect, interpret, and—if desired—edit or reject specific rules. That contrasts with opaque latent features learned by many representation methods.

## Weight tuning as an automatic filter for weak rules
Not all rules generated from a few examples are equally useful. FeatLLM addresses this by fitting a very simple downstream model that learns a non-negative importance for each rule:

logit_k^i = max(w_k, 0) · z_k^i
p^i = Softmax([logit_1^i, ..., logit_c^i])

The weight vector w_k is trained with cross-entropy on the available k-shot labeled data. Two key points make this step powerful:

- Non-negativity: projecting weights into a positive subspace (via max(w_k, 0)) prevents a generated rule from actively decreasing the likelihood of its associated class, which keeps learning stable when rules are noisy.
- Sparsifying effect in low-shot regimes: with few labeled examples, the learned weights naturally downweight rules that don't correlate with the labels. Empirically, the paper uses a small threshold (0.1) on learned weights to identify and effectively filter out low-importance rules.

Because the downstream model is linear and low-capacity, tuning is cheap and interpretable: the learned weight directly indicates the rule's usefulness.

## AUROC-of-features analysis — rule quality before and after tuning
To quantify how informative the generated rules are, the authors measured the average AUROC of each binary rule against the target label, and reported the fraction of rules with AUROC > 0.5. The main findings:

- Before tuning: the majority of generated rules already have AUROC > 0.5, showing that the LLM's prior knowledge plus few-shot examples produce many individually informative signals.
- After tuning: many of the low-AUROC (weak) rules become downweighted or effectively ignored by the learned weights; the tuning step increases the fraction of "useful" features that contribute to prediction.

In short, the LLM supplies a broad set of plausible, interpretable candidate features and the simple linear tuning stage selects and weights the genuinely predictive ones. This two-stage design leverages both prior knowledge (rule generation) and observed data (weight tuning) efficiently.

## Why FeatLLM is robust to spurious columns
The paper evaluates robustness to spurious covariates by attaching unrelated columns (drawn from another dataset) to a target dataset (Heart) while keeping the same few-shot training regime. Compared with conventional baselines and several LLM-based approaches, FeatLLM showed the smallest performance degradation as the number of unrelated columns increased.

There are several reasons for this robustness:

1. Guided reasoning prompt: FeatLLM's two-step prompt asks the LLM first to reason about which features *should* relate to the target (leveraging common-sense or domain priors) before extracting rules from the examples. This discourages inventing rules on obviously irrelevant columns.
2. Rule-format constraints and parsing: requiring parseable rules and converting them into explicit binary features reduces the likelihood of unpredictable, dataset-specific transformations that overfit noise.
3. Weight tuning and ensembling: the downstream weight learning filters out rules that do not correlate with labels in the few shots, and the ensemble with bagging dilutes the influence of occasional bad rule sets from any single LLM sample.
4. Empirical observation: across trials, only about 1–2% of generated rules came from noisy/unrelated columns in the reported experiment, and ensemble averaging further mitigated their effect.

Taken together, FeatLLM effectively combines human-interpretable priors (via LLM reasoning) with data-driven filtering (via weight tuning and ensembling), which is precisely the combination that combats spurious correlations in low-shot settings.

## Practical takeaways
- Interpretability is built in: every feature corresponds to an explicit rule you can read and audit. That helps debugging, fairness checks, and domain validation.
- Lightweight tuning is crucial: the simple non-negative linear model both improves accuracy and serves as an automatic filter for weak rules. In practice the paper uses cross-entropy training on the few labeled examples to learn weights.
- Ensemble + bagging matters: repeating rule generation with randomized demonstrations and subsets reduces sensitivity to prompt order and to prompt-size limits, and it converges in performance by around 20 ensembles in the experiments.
- Low inference cost: after the rule-generation and tuning stage (which requires only a modest number of LLM API queries — the paper reports about 30 API calls for their setting), predictions use only the learned linear weights on binary features, so per-sample inference is inexpensive and does not require further LLM calls.
- Robustness to spurious features is empirical, not absolute: FeatLLM degrades less than baselines in the tested setup, but the authors note it can still learn spurious correlations if related-but-misleading columns are present.

## Closing
FeatLLM illustrates an attractive middle ground: use an LLM not as a prediction black box for every sample, but as a generator of human-readable candidate features; then let a lightweight, interpretable tuner pick which candidates matter. That pipeline preserves much of the LLM's prior knowledge while giving practitioners inspectable rules and resilience to spurious noise — a pragmatic recipe for many low-shot tabular problems.



# Getting Started with FeatLLM: Practical Tips, Edge Cases, and Extensions

FeatLLM reframes how you use Large Language Models (LLMs) for tabular problems: instead of asking an LLM to make a prediction for every sample, you ask it to act as a feature engineer — to generate human-readable rules that get converted into binary features. A lightweight downstream model (a non-negative linear layer + softmax in the paper) is trained on those binary features for inference. This reduces per-sample inference cost, avoids requiring LLM fine-tuning, and scales better to wide tables by using bagging and ensembling.

Below I summarize practical tips for practitioners, things to watch out for, and sensible extensions that follow directly from the FeatLLM approach.

## Quick recap of the FeatLLM pipeline (practical viewpoint)
1. Prepare the dataset: small labeled set (k-shot), feature names and short descriptions (if available).
2. Build a prompt that contains: (a) basic information (task, feature descriptions, a few serialized examples), (b) a two-step reasoning instruction, and (c) response formatting constraints for rules.
3. Query the LLM (the paper uses GPT-3.5) to produce rule sets for each class. Repeat trials with randomization (temperature, demo order) to get diverse rule sets.
4. Parse the LLM’s natural-language rules into executable code (the paper uses the LLM itself to output Python snippets, then runs them with exec()) to create binary rule-features z ∈ {0,1} per rule.
5. Fit a small trainable model: for class k with rule-features z_k, compute logit via logit_k = max(w_k, 0) · z_k and apply softmax across classes to get probabilities. Learn w by minimizing cross-entropy with the few-shot labels.
6. Ensemble multiple such models (bagged trials) by averaging predicted probabilities.

Now the practical guidance.

## Curating feature descriptions and task statements

Why it matters
- FeatLLM leverages both prior knowledge from the LLM and the information present in your few-shot examples. Clear feature names and descriptions help the LLM avoid type mismatches and identify meaningful relationships, which is especially important in the low-shot regime.

What to include in feature descriptions
- Feature name (short): the canonical column label.
- Type: numeric / categorical / boolean / ordinal.
- Short semantics (one or two sentences) if the name is ambiguous (e.g., “BP” → “blood pressure in mmHg”).
- For categorical columns: list possible categories or representative examples if the set is small.

How to craft task statements
- Phrase the task as a clear yes/no or classification question (the paper used explicit question forms, e.g., “Does this patient have chronic heart failure? Yes or no?”).
- If classes are ordered or have specific semantics, enumerate them in the prompt.
- Keep the task description concise but explicit about what counts as a positive vs. negative outcome.

Practical tip: when you have many short features, prefer a single-line description for each (type + one-sentence meaning). The paper’s ablation study shows that removing feature descriptions degrades performance, particularly in very-low-shot settings.

## Prompt design: the three parts that work
FeatLLM’s prompts deliberately decompose the problem to improve rule generation:

1. Basic information description: task, feature definitions, and a few serialized examples.
   - Serialize examples as “f1 is x1. ... fd is xd. Answer: label” — that format worked well in experiments.

2. Reasoning instruction (two-step):
   - Step 1: ask the LLM to infer general tendencies/causal relationships between features and the target using common sense and domain priors (no examples used here).
   - Step 2: ask it to use the few-shot examples plus Step 1 insights to generate concrete rules per class.
   - This two-step structure reduces generation of spurious correlations and focuses attention on features likely to be relevant.

3. Response instruction:
   - Force a strict, parseable rule format and fixed number of rules per class (the paper used 10).
   - Guide the LLM to choose operators consistent with the declared feature types.

Practical tip: explicitly remind the LLM of each feature’s type inside the prompt so generated rules are syntactically compatible with parsing.

## Choosing rule counts, ensemble size, and LLM settings

Rule count per class
- Paper default: 10 rules per class.
- Why: trade-off between additional informative features and input dimensionality/overfitting in low-shot settings. Empirically, 10 was a practical sweet spot in their experiments.

Number of ensemble trials
- Paper default: 20 ensemble trials.
- Why: ensembling improves robustness by aggregating diverse rule-sets; gains saturate around ~20 trials in their ablations.

LLM inference settings
- Temperature: the paper used 0.5 (higher temp introduces more diversity for ensembling).
- Top-p: default 1 in the experiments.

Practical rules of thumb
- If you have extremely few shots (k < 8), keep rule counts modest (≈ 5–10). Increase ensemble size to compensate for variability.
- If prompt length becomes a constraint (many features), prefer increasing ensembles with bagging (see next section) rather than increasing rules per trial.

## Handling many columns: bagging and prompt-size management

Problem: long feature lists and many serialized examples can exceed the LLM context window or make prompts unwieldy.

FeatLLM strategy
- Apply feature bagging: in each ensemble trial, sample a subset of columns and/or a subset of training examples to include in the prompt.
- Generate rule-sets for those subsets. Repeating this across trials allows coverage of the full feature set without a single enormous prompt.

Why it works
- Ensemble + bagging reduces prompt length per query and creates diverse weak learners whose aggregation compensates for missing columns in individual trials.
- The paper found that bagging helps maintain performance on datasets with hundreds of columns and mitigates prompt size constraints.

Practical tip
- If your table has dozens or hundreds of columns, set a bag size that keeps your prompt comfortably under your LLM’s context limit. Then increase ensembles until performance stabilizes (paper observed convergence around 20 trials).

## Parsing rules into executable features

Two main approaches considered in the paper
- Classic parser: build hand-coded parsing logic to convert rule text into predicates. This is brittle because LLM outputs vary in syntax.
- LLM-assisted parsing (used in FeatLLM): include the inferred rules and a function spec in a follow-up LLM prompt, ask the LLM to emit simple Python code that implements the rules, and execute the code (e.g., via exec()) to convert raw rows into binary features.

Practical safety note
- Executing generated code has security implications. In production, sanitize and sandbox any generated code, or implement a conservative parser that supports the expected rule grammar.

Practical tip
- Ask the LLM to produce minimal, well-structured functions (no imports, simple comparisons), and validate the generated code on a small sample before applying broadly.

## Training the downstream model

Model form used in the paper
- Binary rule-features z_k^i ∈ {0,1} for each class k and rule r.
- Compute logit_k^i = max(w_k, 0) · z_k^i to enforce non-negativity of rule contributions.
- Convert logits to probabilities via softmax and train w via cross-entropy.
- Optimizer: Adam, learning rate 0.01, up to 200 epochs with k-fold cross-validation for early stopping (the paper used these settings).

Why non-negativity?
- Ensures that rules can only increase class likelihoods, reflecting the design choice that rules indicate positive evidence for a class. In practice this also stabilizes learning with very few examples.

Practical tip
- With very few shots, L2 regularization or early stopping via cross-validation can reduce overfitting to noisy generated rules.

## Edge cases and failure modes

Spurious correlations
- When unrelated columns are present, unconstrained rule generation can still pick up spurious cues. FeatLLM mitigates this by: (a) the two-step reasoning instruction encouraging reliance on domain priors, and (b) ensembling so that spurious rules in a few trials are diluted.
- The paper’s experiments with added irrelevant columns showed FeatLLM degrades less than baselines, but it is not immune to confounding.

Prompt-length limits and very wide tables
- Use bagging: sample columns per trial so each prompt fits. Expect to need more ensemble trials for complete coverage.

Low-shot-only regime
- FeatLLM is designed for few-shot settings. The paper explicitly focuses on small labeled sets; behavior and advantages in very large-sample regimes were not explored and are an open direction.

Interpretable but imperfect rules
- Generated rules are interpretable, but the LLM can still produce incorrect or overly-general rules. Tuning the linear model will downweight irrelevant rules, but you should inspect common rules across trials for sanity checks.

Safety and code execution
- Using the LLM to generate parsing code is convenient but carries execution risk. Sanitize and run in a controlled environment.

## Integration with existing ML stacks

Where FeatLLM fits
- FeatLLM produces a fixed-length binary feature vector per sample (number of classes × rules per class × ensembles or you can average per-ensemble probabilities). These features can be:
  - Used directly by a simple linear classifier as in the paper.
  - Appended to your existing feature set and fed into downstream models (tree-based models, gradient boosters).
  - Logged and exposed to human analysts for rule inspection and validation.

Practical integration tips
- Workflow: run the LLM-based rule-generation offline to produce a rule library, parse them into functions that transform raw rows into features, then store these feature extraction functions as part of your feature engineering pipeline.
- For realtime inference: once the rule functions are implemented, per-sample inference is cheap — no LLM queries required.
- Monitoring: log which rules fire most frequently and whether weights learned in training remain stable as new data arrive. Drift detection on rule activations can be an early signal of dataset shift.
- Auditability: since rules are text and executable predicates, they are easier to inspect and potentially to hand-correct than opaque model internals.

## Practical checklist before running FeatLLM
- Provide succinct, accurate feature descriptions and types.
- Craft a clear task statement and enumerate classes.
- Start with rule count = 10 and ensemble = 20 (paper defaults). Adjust: reduce rules if overfitting; increase ensembles for wider tables.
- Use a conservative sandbox to execute generated parsing code; validate parsing outputs on small data subsets.
- Train the non-negative linear weights with regularization and cross-validation for early stopping.
- Inspect top rules that receive non-trivial learned weight; discard or revise obviously wrong ones.

## Extensions and future directions (from the paper)
The paper mentions several natural directions that are aligned with practical needs:

- Richer feature types. FeatLLM currently focuses on rule-based (binary) features. Extending to numeric engineered features, aggregated features, or higher-order interactions would broaden applicability.
- Large-sample regimes. The method was designed for few-shot learning; adapting FeatLLM principles (e.g., rule generation as prior, then larger-scale statistical refinement) to settings with many labeled samples is an open direction.
- Interpretability & debiasing. Since LLM priors can embed societal biases, systematic analysis of bias and mechanisms to correct or constrain generated rules are important future work.
- Better parsing protocols. Safer, robust rule grammars or constrained code-generation templates could remove the need to exec arbitrary code.
- Hybrid flows. Use FeatLLM’s rule-features as inputs to more complex models (e.g., gradient-boosted trees) trained on larger datasets, combining LLM priors and data-driven learning.

## Closing notes
FeatLLM is a practical approach to inject LLM prior knowledge into tabular models without per-sample LLM inference or LLM fine-tuning. It is especially well-suited to low-shot settings and settings where inference latency and API costs matter. If you adopt it, focus on precise prompt construction (feature types, two-step reasoning), conservative parsing/execution practices, and ensemble/bagging strategies to manage wide tables and noisy outputs. The generated rules give you both a performant low-cost predictor and a set of interpretable predicates you can inspect and evolve over time.
