\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How are continuous feature thresholds chosen when LLMs generate rules in FeatLLM?
Question:
In FeatLLM, the LLM produces human-readable rules that often look like inequalities (e.g., "age > 60"). With only few-shot examples, how does the LLM decide specific threshold values for continuous features? Are these thresholds inferred purely from prior knowledge, from the provided few-shot examples, or both? If both, what prevents overfitting to arbitrary cut points suggested by tiny k-shot samples? Do you post-process or discretize continuous features before prompting to stabilize the learned thresholds?
Answer:
Short answer: FeatLLM lets the LLM propose numeric cutpoints using both its pretraining (prior knowledge) and the few-shot examples, then prevents overfitting to arbitrary k-shot thresholds by turning those cutpoints into binary features and learning non‑negative weights on many generated rules with ensembling and bagging. There is no separate pre-discretization step; instead stability comes from downstream weight learning, rule filtering, and ensemble regularization.

Explanation grounded in the paper (how thresholds are chosen and why they don’t overfit):

1) How thresholds are produced by the LLM
FeatLLM’s prompt explicitly asks the LLM to (a) first reason from general/commonsense knowledge about which features matter (Step 1) and then (b) combine that prior knowledge with the provided few-shot serialized examples to “deduce rules” (Step 2). Because of this two-step instruction the numeric thresholds (e.g., “$\text{age} > 60$”) that appear in generated rules arise from a mixture of the model’s pretrained knowledge (typical clinical or domain cutpoints it has seen) and the few examples you show it. The paper emphasizes this separation to encourage the LLM to use prior knowledge rather than simply memorizing tiny-sample idiosyncrasies.

2) Rules are converted to binary features (no pre-discretization)
Rather than discretizing the dataset before prompting, FeatLLM parses the LLM’s natural-language rules (using the LLM itself to generate parseable code) and applies those rules to the raw numeric columns to create binary indicator features “$\text{rule satisfied} = 1/0$.” So the continuous value is not binned by a fixed global discretizer beforehand; instead each candidate threshold from the LLM becomes a binary feature.

3) Why these thresholds don’t cause severe overfitting
Several mechanisms in the pipeline reduce overfitting to noisy thresholds suggested by a tiny k-shot set:

- Learnable non-negative weights: The binary rule-features are fed to a simple linear model where the logit for class $k$ is computed as $ \text{logit}_k^i = \max(\mathbf{w}_k,0) \cdot \mathbf{z}_k^i,$ and the model is trained (cross-entropy) on the few labeled samples. Learning these weights lets the model downweight or ignore rules that do not generalize from the examples. Projecting weights into the positive subspace prevents a generated feature from actively hurting the class logit and behaves like a one-sided regularizer.

- Rule filtering via learned weights: The paper reports computing AUROC of generated rule-features vs. label and then filtering by weight; empirically they use a threshold (paper mentions $0.1$ was used in analysis) to remove features judged uninformative after tuning.

- Ensembling + bagging: FeatLLM repeats rule generation $T=20$ times (the paper used $T=20$), with high LLM temperature and randomization of few-shot demo order, producing diverse rule-sets. Predictions average probabilities over these ensembles. Bagging (random subsets of features/instances per trial) both limits prompt size and adds robustness: bad thresholds from a single trial are diluted across the ensemble.

- Fixed budget of rules and prompt guidance: The method enforces a fixed number of rules per class (paper used $R=10$) and gives instructions (feature types, formats, Step‑1 reasoning) to reduce wild/irrelevant cutpoints. The ablation study shows the Step‑1 prior-knowledge reasoning and feature descriptions materially help performance in low-shot regimes, consistent with reducing spurious arbitrary thresholds.

- Low-capacity downstream model & regularization effect: By converting thresholds into binary features and using a low-capacity linear model trained on few examples, the approach avoids fitting a high-complexity function of continuous inputs directly from few samples, which is a typical source of overfitting.

4) Practical details from the paper that stabilize thresholds
The implementation choices reported in the paper that affect threshold stability include using GPT‑3.5 with temperature $0.5$ for generation, extracting $R=10$ rules per class, ensembling over $T=20$ trials, and training the linear weights with Adam (LR=$0.01$) for $200$ epochs with cross-validation to pick epochs. The parsing step uses the LLM to produce executable code that applies the natural-language thresholds to raw feature values, rather than relying on brittle regex-only parsing.

Broader conceptual view
Intuitively this is a form of “prior + data” hybridization: the LLM supplies potentially useful hypothesis cuts (prior-informed inductive bias), the few examples $n$udge which cuts are plausible for this dataset, and a downstream statistical learner (low-capacity, regularized by non-negativity, thresholding and ensembling) performs selection and smoothing. That pipeline shifts the risk of overfitting from the LLM’s raw textual thresholds into a controllable ML stage where standard regularization and ensembling reduce variance.

What the paper does not do
FeatLLM does not pre-discretize continuous features globally before prompting, nor does it hard-constrain thresholds to bins derived from the data (e.g., quantiles). Thresholds are proposed by the LLM and then evaluated/tuned downstream. If you want even stronger protection against idiosyncratic cutpoints, you could augment the pipeline (not in the paper) by: (a) adding candidate thresholds derived from data quantiles into the prompt, (b) increasing ensemble size, or (c) adding explicit weight regularization (L1/L2) when training the linear model.

Takeaway
Thresholds in FeatLLM come from both LLM prior knowledge and the few-shot examples (by design). Overfitting is mitigated by turning thresholds into many binary features, learning non-negative feature weights, filtering low-weight features, and averaging over multiple randomized rule generations via bagging/ensemble. These elements together make the learned cutpoints stable and useful even in the few-shot regime.

### Why constrain rule weights to be non-negative in the linear model?
Question:
Section 3.2 defines logits per class as \(\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i\), forcing non-negative contributions from rule activations. Conceptually, this prevents a rule that fires from ever decreasing a class's logit. But some rules might indicate negative evidence for a class (e.g., "no chest pain" might reduce the likelihood of heart disease). Why prohibit negative weights? Is the intent that negative evidence is represented as positive evidence for some other class, making explicit negatives unnecessary? Did you empirically compare against an unconstrained linear/logistic model with signed weights?
Answer:
Short answer: the paper enforces non-negative weights so that every LLM-generated rule (a binary “this condition holds” feature) can only increase the logit for the class it was written for. The stated motivations are interpretability, robustness in the low-shot regime, and an inductive bias that fits how the rules are produced (rules are written as positive signals for a class). The paper does not report a direct comparison to an unconstrained linear/logistic model with signed weights.

Why non-negativity makes sense here (intuitively and technically)
The LLM in FeatLLM is asked to produce rules that are intended as evidence for a particular class (e.g., “$\text{age} > 65$ indicates higher risk of disease X”). Treating each rule as a positive indicator and restricting its learned weight to be non-negative enforces that semantics: when a rule fires it will not reduce the class’s logit. This has several practical consequences that matter especially in few-shot settings.

First, it preserves interpretability and trust: positive rule weight = supportive evidence, near-zero weight = irrelevant/filtered rule. If weights could go negative, a rule the LLM produced as a “support” could end up being used as a learned negative signal after noisy few-shot fitting, which undermines the intended human-readable mapping from rules $\to$ evidence.

Second, it acts as a useful inductive bias / regularizer in the extremely low-data regime. With very few labeled examples, unconstrained fitting can easily assign spurious signed weights (positive or negative) to explain noise. Enforcing non-negativity prevents a model from explaining everything by flipping the sign of weak/noisy binary features, which stabilizes learning and reduces overfitting.

Third, model structure and competition between classes: FeatLLM builds per-class rule sets and computes logits per class (then applies softmax). Negative evidence for class A can be represented implicitly by positive evidence for other class(es). In a softmax, increasing another class’s logit decreases class A’s posterior probability even if A’s own rules only add positive mass. Thus one can represent “negative evidence for A” either by a rule directly for A with negative weight, or by rules for other classes with positive weights. FeatLLM chooses the latter implicitly by construction, which keeps the semantics of each rule aligned with the class it was generated for.

What the paper actually reports empirically
The paper reports an ablation that removes the weight tuning step: instead of learning non-negative weights they simply sum the binary features per class (i.e., equal positive weights). That ablation (“-Tuning”) degrades performance, showing that learning per-rule importance is helpful. However, the paper does not present an explicit experiment comparing the chosen projected-nonnegative-weight model against a fully unconstrained signed-weight linear model. So there is no reported direct empirical test in the paper that answers “would signed weights help?” The authors claim the positive projection “ensures that the features generated by the LLM do not reduce the likelihood of a class during learning,” and motivate this by robustness and interpretability rather than by an empirical signed-vs-non-signed sweep.

Practical implications and a suggested experiment
If you suspect many rules are legitimately negative indicators (e.g., “no chest pain” reduces heart disease risk) you can represent that in FeatLLM either by (a) asking the LLM to generate negative-signal rules as positive rules for the complement class (or a “not-disease” class), or (b) allow signed weights and learn them. The paper favors (a)/(implicit) because it keeps rules aligned with class semantics and gives stability in low-shot fitting.

If you want to evaluate this empirically, the natural experiment is straightforward: train two versions on the same rule-derived binary features — one with the paper’s projection to non-negative weights, the other with unconstrained signed weights (same optimization, same regularization). Measure few-shot performance and inspect what fraction of rules get negative weights in the unconstrained run. My expectation (consistent with the paper’s motivations) is that in very-low-shot settings the unconstrained model will assign unstable/sign-flipping weights and may overfit more, while in higher-shot regimes signed weights could help if there are genuine negative indicators that are not captured as positive evidence for other classes.

Bottom line: the non-negativity constraint is a design choice that favors interpretability and robustness in few-shot learning by enforcing that LLM-generated rules remain positive evidence for their target class. The paper demonstrates benefits of learning per-rule importances versus uniform weights but does not report an explicit signed-vs-non-signed weight comparison — that would be a reasonable empirical follow-up.

### How are contradictory or overlapping rules handled during training and inference?
Question:
FeatLLM extracts a fixed number (e.g., 10) of rules per class. What happens if two rules for the same class are logically overlapping or contradictory (e.g., "age > 65" and "age > 70", or "smoker == yes" vs. a composite rule that implies "smoker == no")? During training, will both rules just receive weights based on usefulness, or is there any deduplication/logic simplification step? Does the LLM get guidance to avoid redundant rules, and how do you ensure stability when overlapping rules correlate strongly, potentially causing multicollinearity in the binary feature space?
Answer:
Short answer: FeatLLM does not perform an explicit logical deduplication/simplification pass over the rule set. Instead it relies on (1) controlled prompt design and parsing to reduce trivial syntactic noise, (2) learning non-negative weights per rule so the downstream learner can downweight or ignore redundant/irrelevant rules, and (3) ensemble + bagging across many LLM trials to dilute the effect of any single bad/redundant rule. These mechanisms are what the paper uses to handle overlapping or contradictory rules and to keep the binary feature space stable.

Explanation grounded in the paper

1) Rule generation and parsing: The prompt forces a fixed number of rules per class (the authors use 10) and constrains response formats and rule structure. That reduces some kinds of trivial redundancy (e.g., different syntactic renderings of the same comparison). In addition, the paper uses the LLM itself to parse the natural-language rules into program code, which tends to canonicalize many syntactic variants (for example turning “greater than seventy” into “age $> 70$”). However, there is no claim in the paper of a formal logic-simplifier that detects and removes logically subsumed or contradictory rules (e.g., “age $> 65$” vs. “age $> 70$”) before feature creation.

2) Learning importance (the main filter): After rules are parsed into binary features $z_{k}^{i}$ (one feature per rule per class), FeatLLM fits a simple linear model per class with trainable weights $w_k$ and a projection into the positive orthant: $\text{logit}_{k}^{i} = \max(w_k, 0)\cdot z_{k}^{i}$. Because the model learns these weights from the few-shot examples (cross-entropy loss, optimized with Adam), rules that are not useful for predicting the label receive near-zero weights. The paper explicitly reports that tuning filters out many uninformative rules (they even show the fraction of useful rules “before tuning” vs “after tuning” using an empirical threshold). Intuitively, overlapping rules that do not add extra predictive signal will get low weight; contradictory rules that do not co-occur with the label will likewise be downweighted.

3) Non-negativity constraint and its consequences: Projecting weights to be non-negative prevents a rule from actively decreasing a class’s score (the model assumes rules are evidence for a class). That design choice simplifies interpretation and avoids the model using negative weights to cancel out correlated features, but it also changes how redundancy is resolved: rather than subtracting one rule’s vote with another, the model can assign near-zero weights to redundant rules. This reduces one form of instability (opposite-signed coefficients cancelling) but means contradictory evidence must be handled by selecting other class logits (softmax across classes) rather than negative weights on rules.

4) Ensemble + bagging to reduce instability from correlated rules: The framework repeats the whole LLM-rule-generation + linear-weight-fitting procedure $T$ times with randomization (higher LLM temperature, random demonstration order, and feature/instance bagging). Averaging predicted probabilities across these trials reduces the influence of any single trial’s idiosyncratic or highly correlated rule-set. The authors argue (and show empirically) that ensemble/bagging improves robustness, compensating when some trials produce redundant or erroneous rules.

What about multicollinearity in the binary feature matrix? The paper does not introduce an explicit de-correlation or regularization scheme beyond the above. In practice, correlated binary features (e.g., “age $> 65$” and “age $> 70$”) can make the learned weights less stable when data are very scarce. FeatLLM mitigates this empirically by (a) learning weights so uninformative/redundant rules go to low values, (b) projecting to non-negative weights (avoids sign-based cancellations), and (c) averaging across ensembles to stabilize predictions. The ablation study in the paper shows that the weight-tuning step materially improves performance compared to simply summing binary features, especially with more shots, which implies that learning weights is the intended mechanism to handle redundancy and correlated features.

Limitations and implicit trade-offs (as described/implicit in the paper)
Because FeatLLM fixes the number of rules per class and delegates redundancy handling to the downstream learner and to ensembling, it does not guarantee minimal logical rule-sets or provable lack of redundancy. In very low-shot regimes, highly correlated rules could still lead to variance in learned weights; the ensemble reduces but does not eliminate that variance. Also, the non-negativity constraint prevents the model from using negative evidence on a class via a rule, which is a design choice that trades expressivity for interpretability and stability.

If you need stronger guarantees
The paper does not implement these, but if you want to extend FeatLLM for settings where logical deduplication or multicollinearity control is critical, standard alternatives (not claimed in the paper) would be to post-process parsed rules to canonicalize/simplify them (e.g., detect subsumption like “age $>70$” implies “age $>65$” and keep only the tighter rule), add regularization ($L_1$/$L_2$) when fitting weights, perform feature clustering and collapse near-duplicates, or allow signed weights with careful regularization. Those are natural follow-ups consistent with the paper’s framework but are outside the described method.

Bottom line: FeatLLM handles overlapping/contradictory rules primarily by learning non-negative weights that downweight irrelevant or redundant rules, plus ensembling/bagging and parsing normalization via the LLM. There is no explicit logical deduplication step; stability relies on weight tuning and ensemble averaging, which the paper demonstrates empirically to be effective in the few-shot tabular settings studied.

### How is multi-class classification formulated with per-class rule sets and softmax?
Question:
For multi-class tasks, you build R binary rule features per class and then compute per-class logits before applying softmax. Suppose a sample satisfies many rules for multiple classes. Does the softmax inherently resolve competition, or do you normalize rule counts/weights across classes to handle class-specific differences in the number or "generality" of rules? Also, what happens when a sample satisfies none of the rules for any class—do all logits become zero, leading to a uniform softmax output?
Answer:
Short answer: softmax does resolve the competition across classes at prediction time, but it does not by itself correct for class‑specific differences in the number or generality of rules. In FeatLLM those differences are handled by learning nonnegative per‑rule weights per class (so more and/or stronger rules increase a class logit more), and if a sample satisfies no rules for any class the model (as implemented in the paper) produces equal logits and hence a uniform softmax.

Explanation grounded in the paper. FeatLLM converts the LLM‑generated rules into binary features per class: for class $k$ the feature vector for sample $i$ is $\mathbf{z}_k^i\in\{0,1\}^R$ (one entry per rule). The model computes per‑class logits and then applies a softmax over classes, specifically (Eq. (2) in the paper)

$$
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,\qquad
\mathbf{p}^i = \mathrm{Softmax}([\text{logit}_1^i,\dots,\text{logit}_c^i]).
$$

Intuition about competition and normalization. Softmax turns the class logits into a categorical distribution and therefore enforces competition: a larger logit for class $k$ reduces the relative probability of other classes. However, softmax only reacts to the logits it is given; it does not automatically compensate if some classes have many weak rules while others have few strong rules.

How FeatLLM handles unequal rule counts/generality. The paper addresses class‑specific imbalance by learning the weights $\mathbf{w}_k$ for each class and projecting them to the nonnegative orthant (the $\max(\mathbf{w}_k,0)$ operator). Those learned weights scale each class’s binary rule features: rules that are general but uninformative will receive small learned weights during tuning, whereas informative rules will get larger weights. Thus normalization or reweighting is done via learning rather than by explicit normalizing counts across classes. The ablation study also shows this tuning step improves performance, especially with more shots, which supports that the learned weights correct for per‑class differences in rule usefulness.

What happens if no rule fires for any class. If for sample $i$ we have $\mathbf{z}_k^i=\mathbf{0}$ for every class $k$, then $\text{logit}_k^i=0$ for all $k$ (given the model has no bias term as described). Softmax on the zero vector yields a uniform distribution over classes, so the model is maximally uncertain. In practice FeatLLM mitigates this in two ways: (1) ensembles with bagging produce many different rule sets across trials, so it’s less likely that every trial produces all‑zero logits for a sample; and (2) tuning tends to produce some low‑weight but nonzero structure when rules partially match the data. The paper does not include class biases or offsets in the linear model, so uniform outputs are the direct implication when no rules match.

Practical notes / how you might alter this behavior. If you want the model to prefer certain classes when rules are absent (e.g., incorporate class prior or avoid uniform guesses), you would add class biases or prior log odds, use a temperature on softmax, or normalize per‑class rule sums before weighting. These are not part of FeatLLM as presented, which deliberately uses a simple nonnegative linear readout and trusts learned weights plus ensembling to handle class imbalance and generality of rules.

Summary: softmax enforces competition but does not automatically correct imbalances in rule counts or rule generality; FeatLLM relies on learned per‑rule, per‑class nonnegative weights (and ensembling) to do that. If no rules fire, all logits are zero and the softmax is uniform.

### What specific bagging scheme is used for samples and features in FeatLLM?
Question:
The paper says you use feature bagging and instance bagging to control prompt size and induce diversity, but the exact sampling scheme is not specified. Do you sample without replacement from features and examples for each LLM call? What are the typical fractions for features and examples retained per trial, and how are they tuned? Are the same subsets used for both the rule-generation prompt and the subsequent weight training, or is there a risk of distribution shift between the prompt subset and the training subset?
Answer:
Short answer: the paper does not spell out a precise sampling protocol (e.g., with vs. without replacement or fixed fractions) for the feature/instance bagging. What it does state is that FeatLLM uses bagging to select a subset of features or instances per trial to (1) reduce prompt size and (2) induce diversity across an ensemble of trials. The only concrete bagging-related hyperparameters reported are the number of ensemble trials ($T = 20$) and the number of rules extracted per class per trial ($R = 10$). The paper leaves the precise sampling fractions and the replacement policy unspecified and treats those as tuning choices (see the discussion in the Methods and Hyper-parameter analysis sections and Appendix references).

What that means in practice and why it matters
- The method repeatedly runs the full pipeline (prompt → rule generation → parsing → feature construction → fit simple model) $T$ times and averages the predicted class probabilities. Bagging is the source of randomness across trials (together with LLM sampling temperature and order of demonstrations).
- Because the paper emphasizes controlling prompt size, the intended use of bagging is to pick only a subset of the full feature set (or a subset of instances) to include in each prompt so that each LLM query stays within token limits.
- The paper does not claim a sophisticated sampling scheme; it treats the number/size of subsets as a hyperparameter that trades prompt length, diversity, and coverage.

On whether the same subset is used for rule-generation and weight training (and distribution-shift risk)
- Though the paper does not explicitly write a line like “we use the same subset for prompt and training in each trial,” the described pipeline implies that each trial generates rules from the prompt (which contains the subset of features/instances) and then those generated rule-features are parsed and applied to data and a linear model is trained on the available $k$-shot training samples. In other words, the rules generated in a given trial are used to create binary features that are then fit with weights (Eq. $1$) in that same trial, and the ensemble averages models from all trials.
- If one were to use different subsets for the rule-generation prompt versus the later weight-training step, that would create a distribution shift: the rules the LLM produced were based on a particular view of features/instances and might not align with the data used to learn weights. The paper’s described flow (generate rules → parse → construct binary features → learn weights) strongly suggests the intended and sensible practice is to use the rules from the prompt and then train the downstream model on the binary features produced from the same rule set (applied to whatever training samples you have). This avoids the obvious mismatch between rule semantics and training data.

Recommended practical choices (consistent with the paper’s stated design and experiments)
- Use per-trial subsets consistently: for each ensemble trial, pick the subset (features and/or instances), build the prompt from that subset, generate rules, parse them, apply those rules to your dataset to produce binary features, and then train the weights for that trial on the available $k$-shot examples (or the subset of instances if you intentionally bag instances). This follows the pipeline in the paper and avoids distribution-shift between prompt and training.
- Use the paper’s reported defaults as starting points: $T \approx 20$ ensembles, $R = 10$ rules per class, LLM temp = $0.5$. The paper reports these gave stable performance and that performance gains saturate around $20$ ensembles.
- Treat the fraction/size of features or instances included per prompt as a tunable hyperparameter. The paper frames this as an explicit tradeoff: smaller subsets reduce prompt size (and make LLM calls feasible) and increase ensemble diversity, while larger subsets give each trial a more complete view of the table. Tune the subset size by validation (or by checking performance vs. prompt length), respecting your LLM token limits.

Summary
The paper uses feature/instance bagging to create diverse prompts across an ensemble, but it does not specify whether sampling is with/without replacement nor give fixed fractions for retained features/instances; those choices are treated as hyperparameters. The pipeline implies rules generated in a trial are the ones used to create features and train that trial’s weights (so you should avoid using different subsets for prompting vs. training to prevent distribution shift). Use the paper’s recommended ensemble size ($T = 20$) and rules-per-class ($R = 10$) as defaults and tune the subset size to balance prompt length and coverage.

### How are categorical features and multi-valued categories represented in rules and parsing?
Question:
For categorical columns with many levels (e.g., dozens or hundreds), how does the LLM express rules—single-category equality, sets of categories, or regex-like patterns? Does the response template explicitly allow OR-clauses over categories, and can the parser robustly translate natural language descriptions of sets into code (e.g., {"A", "B", "C"})? How do you handle high-cardinality categories where enumerations inflate prompt length or lead to brittle parsing?
Answer:
Short answer: The paper handles categorical and multi-valued categories by (1) instructing the LLM to produce rules using simple logical forms (it explicitly allows $AND/OR$ combinations), (2) constraining the response format for easier parsing, and (3) parsing the (noisy) natural-language rules back to executable code by asking the LLM itself to emit small Python code snippets which are then executed. For high‑cardinality categories the framework avoids always enumerating everything by giving the LLM category examples in the prompt, using bagging/ensembling to avoid gigantic prompts, and relying on the downstream weight‑tuning and ensembling to filter brittle or spurious enumerations.

Why and how this works (intuitive + concrete):

The paper’s design has three pieces that determine how categorical conditions appear and are translated to code.

1) Prompt + response format guides the LLM to produce rule forms you can parse. In Section 3.1 the authors say the prompt contains feature descriptions (including type and optionally “examples of the possible categories”), reasoning instructions, and a response instruction that specifies the required format for rules. The prompt explicitly permits the LLM to combine conditions with logical operators ($AND/OR$) and to choose a format appropriate to the feature type. So you should expect rules like “feature X equals $\text{'A'}$” or “feature Y is in $\{A, B, C\}$” or compound conditions joined with $OR/AND$. That explicit formatting guidance is what lets the system extract structured rule-like text instead of arbitrary prose.

2) Parsing is done by asking the LLM to generate small code snippets rather than writing a brittle hand-coded parser. The authors point out that the LLM’s outputs can have syntactic variability (e.g., “$>$” vs “greater than”), so instead of building a complex parser they feed the inferred rules + a function signature back into the LLM and ask it to produce Python code that implements those rules. That generated code is executed via Python’s exec(). This leverages the LLM’s tolerance for surface variation and its ability to emit code that captures the semantics of “category in $\{\dots\}$”, equality tests, prefix checks, numeric comparisons, etc. The paper emphasizes this approach as more robust than naive string parsing because the LLM maps noisy natural-language rule text into executable logic.

3) Handling high-cardinality categories and avoiding prompt bloat. The paper acknowledges (Section 1 and Prompt Design) that long prompts and big enumerations are a problem. They mitigate this in two concrete ways: (a) when describing features you can provide a few example categories rather than listing hundreds, and (b) they use feature bagging + ensembling: each trial asks the LLM about a subset of features (and randomizes demonstrations) so you never have to encode all columns and every category in a single prompt. Bagging thus keeps prompt size manageable and creates diverse, smaller rule sets whose ensemble compensates for partial coverage. Practically, this means the LLM will often propose grouped/set rules (e.g., “in $\{A,B,C\}$” or “categories starting with 'NY'”) rather than raw full enumerations, and even if it enumerates too much the tuning stage (learning non-negative weights on boolean rule-features) downweights brittle or unhelpful rules.

Practical implications and recommendations consistent with the paper

- Use the response-instruction slot to force canonical, parseable forms (e.g., require that set membership be written as "in $\{A, B, C\}$" or equality as $\text{== 'A'}$). The paper shows this is what they do to ease downstream parsing.
- Provide a short representative list of categories in the feature description instead of a full dump when cardinality is large; that cues the LLM toward typical values or sensible groupings.
- Encourage the LLM to produce grouped rules (e.g., “is one of $\{\dots\}$”, “starts with”, “contains”) instead of raw enumerations; the paper allows logical operators and type-based formatting so this is compatible with FeatLLM’s design.
- Rely on bagging/ensembling to avoid putting every categorical level into one prompt; the paper explicitly uses bagging to reduce prompt size and then ensembles multiple trials.
- Expect the tuning step (learning weights for rule-features) to filter out brittle enumerations: rules that don't help the held‑out few shots get near-zero weights and have minimal effect on final predictions.

Limitations called out by the paper

The authors explicitly note that LLM outputs can vary syntactically and that parsing remains a challenge; that is precisely why they use the LLM to emit parsing code. They also set a fixed number of rules per class (10 in their experiments) to avoid exploding the feature set, which is a pragmatic constraint when categories are many. Finally, although FeatLLM reduces the need to enumerate everything, if the underlying task truly requires treating every level of a high-cardinality categorical variable distinctly the method will need either more sophisticated grouping heuristics or more training examples to learn importance — a point the authors flag under future work.

In short: the framework expects categorical rules to appear as equality tests or set-membership and allows $AND/OR$ combinations; it constrains response format to make parsing feasible and, instead of brittle hand-parsing, uses the LLM again to turn rules into executable code. For high-cardinality categories the paper recommends (and implements) giving example values, asking the LLM for grouped/set-style rules, and using bagging/ensembling and weight tuning to avoid prompt bloat and brittle enumerations.

### How robust is the rule-to-code parsing when LLMs vary syntax (e.g., "<" vs. "less than")?
Question:
You mention leveraging the LLM itself to generate Python code from natural-language rules to mitigate noisy syntax. What safeguards exist if the generated code is syntactically valid but semantically incorrect (e.g., off-by-one thresholds, inclusive vs. exclusive bounds)? Do you run any unit checks on toy inputs to validate rule behavior against the natural-language description? Also, how do you handle missing values in code generation (e.g., null-safe comparisons) to avoid runtime errors?
Answer:
Short answer: The paper relies on three built-in, paper-described mechanisms for robustness (structured prompt constraints, using the LLM as a parser, and ensemble + weight tuning), but it does not claim a full formal verifier or an extensive battery of unit-tests. Practical safeguards you should expect or add in an implementation are (1) constrain the rule format and feature types in the prompt so the LLM produces well-typed code, (2) parse/generate the runnable Python via an LLM prompt that includes function signature and I/O descriptions (as the paper does), (3) execute the generated code and discard or downweight rules that fail or do not correlate with labels (the paper uses ensembling + learns non-negative weights to filter irrelevant/incorrect rules). The paper does not describe an explicit, systematic unit-testing protocol or a detailed null-handling policy, so I’ll explain what the paper provides and then give compact, practical checks you can add.

What the paper actually does (grounded in text)
The paper explicitly addresses noisy syntax and parsing by constraining the rule response format and by asking the LLM to produce simple Python code: the prompt contains the function name, input/output descriptions, the inferred rules, and guidance on formats. Because LLM outputs vary in phrasing (e.g., “less than” vs “$<$”), they avoid brittle handcrafted parsers and instead use the LLM itself to translate the natural-language rules into executable Python. The generated code is then executed with Python’s exec() to perform data conversion. Robustness to bad rules is handled at the model level via ensembling/bagging (multiple independently-generated rule sets) and by learning non-negative linear weights on the binary rule-features: rules that are not predictive get near-zero weights and thus are effectively filtered out during training. The ablation and feature-quality sections show that many rules are informative and that tuning removes irrelevant ones.

Where semantic mistakes (off-by-one, inclusive/exclusive, null handling) can still happen
The paper acknowledges “noisy syntactic changes” and type mismatches and mitigates them by including feature type descriptions in the prompt so the LLM can choose appropriate formats. However, it does not claim automatic detection of subtle semantic bugs (off-by-one errors, whether “less than” means strict or inclusive, unexpected units, or handling of missing/null values). Those are not described as explicitly tested in the manuscript.

Practical safeguards you should add (recommended, concise)
1) Validation run on a small set of synthetic / edge-case inputs. After the LLM generates the parsing function, run it on a tiny suite of toy inputs that exercise boundary cases: exactly-at-threshold, threshold $\pm \epsilon$, NaN/null, negative/empty strings, unseen categories. If the function raises an exception, returns inconsistent types, or produces results that contradict an obvious interpretation (e.g., “age $> 18$” returning True for $\text{age}=18$), mark the rule as faulty and discard it for that trial.

2) Explicit instruction for inclusivity/exclusivity and null-safety in the parser prompt. When you ask the LLM to emit Python, include an instruction such as “use inclusive bounds when the rule says ‘at least’ or ‘$\ge$’; use strict bounds when it says ‘greater than’ or ‘$>$’. Treat missing values as not satisfying the rule unless explicitly stated.” The paper already uses the pattern of giving the LLM function signatures and I/O descriptions—extending those to include these conventions reduces ambiguous semantics.

3) Runtime exception handling and filtering. Execute the generated code inside a try/except wrapper. If a rule’s function raises exceptions on realistic inputs, catch the exception, log it, and exclude that rule from the feature set for that trial. The paper executes generated code via exec(); adding a safe execution wrapper is a minimal, practical extension consistent with the paper’s approach.

4) Statistical sanity checks and weight-based filtering (what the paper already does). After turning rules into binary features, the paper trains a small linear model with non-negative weights. Use the learned weights and simple univariate checks (correlation or AUROC between a rule-feature and the label) to automatically discard rules that are non-predictive or that appear to be anticorrelated in a way that contradicts the rule’s natural-language intention. The paper demonstrates this: many rules with low learned weight are effectively removed.

5) Lightweight unit tests for semantics. For threshold rules, automatically create three test values: just below the boundary, exactly at the boundary, and just above. Verify that outputs align with the textual rule’s natural reading or with an explicitly-stated convention. If the rule’s text is ambiguous (e.g., “older than $65$”), you can standardize a convention in the prompt (e.g., “interpret ‘older than $65$’ as strictly greater”) and check adherence.

6) Ensemble robustness (already in paper). Because the system repeats rule generation with randomness and ensembles the resulting models, a few semantically incorrect rules in some trials tend not to dominate the final prediction. This is an intended robustness mechanism in the paper.

Putting this together in a minimal workflow consistent with the paper
Prompt the LLM for rules (constrained format + feature types), ask the LLM to produce a Python parser function (include precise conventions for bounds and nulls in that prompt), exec the generated code inside a guarded environment, run the function over a small battery of toy/edge-case inputs and the actual k-shot training samples, discard any rules that raise exceptions or fail boundary tests, convert surviving rules to binary features, fit the non-negative linear model, and finally ensemble across trials. The paper covers the central steps of LLM-based parsing, exec(), weight tuning, and ensembling; adding the toy-input validations and runtime guards addresses the specific semantic error modes you listed.

Short summary
The paper’s explicit safeguards are constrained response formats, feature-type guidance in prompts, LLM-based parsing into executable Python, and robustness via ensemble + learned non-negative weights that filter unhelpful rules. It does not describe an explicit unit-test suite or a detailed null-handling policy; those are sensible, minimal augmentations you can add (toy-input boundary tests, explicit inclusivity/null conventions in the parser prompt, try/except execution and dropping faulty rules) and they integrate naturally with the paper’s described pipeline.

### Security implications of using exec() for generated code in FeatLLM?
Question:
The method executes LLM-generated code via Python's exec(). What sandboxing measures are in place to prevent file system or network access, arbitrary imports, or long-running loops? Do you restrict the available builtins/modules or run the code in a containerized environment? Given industrial deployment is a stated goal, can you detail the threat model and mitigations you applied when executing model-generated code?
Answer:
Short answer: the paper explicitly says it uses Python’s exec() to run LLM-produced code for parsing/applying rules, but it does not describe any sandboxing, builtin/module restrictions, timeouts, or containerization. That means as written the paper does not present an explicit threat model or concrete mitigations for executing model‑generated code — so you should treat the implementation in the paper as functionally correct but not production‑secure.

Why this matters (intuitive + technical): executing arbitrary text with exec() hands the LLM full dynamic Python capability. Even if the LLM’s intended output is a small rule function, a generated snippet can (accidentally or maliciously)

- read or overwrite files, e.g., open("/etc/passwd").read(), os.remove(...)  
- make network I/O (sockets, requests) and exfiltrate data or fetch payloads  
- import dangerous modules (os, subprocess, ctypes) and spawn processes or run shell commands  
- run long or infinite loops and exhaust CPU; allocate large objects and exhaust RAM  
- manipulate the environment, delete logs, or modify downstream model artifacts  
- perform prompt‑injection style attacks to change future prompts or reveal sensitive prompt contents

These attack vectors are well known when running untrusted code; the paper mentions only that the LLM is used to generate code and that code is executed via exec() for data conversion, without further safety guarantees.

If you want to deploy FeatLLM in an industrial setting, here are concrete mitigations (practical, ordered by how commonly they are used) that align with the paper’s goal of parsing rules but remove dangerous capabilities. The paper does not claim any of these, so they are suggestions you should add to a production implementation.

1) Avoid running raw Python from the LLM at all. Replace exec() with a deterministic parser/DSL for rules. For example, restrict rule grammar to comparisons, membership and boolean ops and write a small parser that outputs a safe predicate function. This is the simplest and strongest control: you only accept syntactic forms you understand.

2) If you must run generated code, parse and validate the code first. Use Python’s ast module to parse the returned string and reject ASTs that contain imports, attribute access (e.g., __), calls to suspicious functions, comprehensions that could be used to construct large objects, or nodes beyond a white‑list (Compare, Name, BoolOp, Constant, IfExp). AST validation lets you enforce a known‑safe subset.

3) Restrict builtins and globals passed to exec(). Use a minimal globals dict (e.g., {"__builtins__": None}) and provide only explicit safe functions (e.g., numeric operators, safe comparators). Note this is brittle: many bypasses exist if the LLM can produce attribute access or exploit type objects, so combine with AST checks.

4) Run code in a separate, isolated process with strict resource caps. Spawn a helper process (or worker) that runs the code with:
   - no network namespace (or network disabled)  
   - chroot / unprivileged user  
   - cgroups limiting CPU and memory  
   - RLIMITs for address space, open files, process count, and CPU time  
   - enforced wallclock timeout (kill the process after $N$ ms)  
This containment prevents host compromise and limits damage from infinite loops or memory bombs.

5) Use OS‑level sandboxing / containers / VMs for stronger isolation. For high assurance, run each parse/evaluate job in an ephemeral container or micro‑VM (Firecracker, gVisor) that is destroyed after use and has no host mounts. This adds latency/cost but greatly reduces risk.

6) Use syscall filtering (seccomp) on the helper process to block execve, open, socket, ptrace, etc. Combined with cgroups, this prevents file and network access even if code tries lower‑level calls.

7) Deny imports or provide a whitelisted safe helper library. If certain utilities are needed (e.g., date parsing), expose an explicit, vetted helper API rather than permitting imports. For example, pass a functions dictionary into exec containing only safe parsers.

8) Apply static and dynamic behavioral checks. Have a static analyzer for suspicious tokens/strings and at runtime monitor syscalls, file accesses and outbound connections. Log and alert on anything unexpected.

9) Use RestrictedPython or other sandboxing frameworks carefully. RestrictedPython and similar projects offer higher‑level sandboxes for some use cases, but they are not bulletproof and require careful configuration and ongoing maintenance.

10) Test adversarially. Use red‑team inputs and LLM prompting variants to probe failure modes: can the LLM produce a malicious payload that bypasses AST checks, or create rules that leak the training data? Add negative tests to the CI.

11) Adopt least privilege and data minimization. Ensure the worker process only sees the minimum data necessary to generate or run the rule. Never give it production secrets, private dataset parts, or API keys. Use synthetic or redacted examples when possible.

12) Auditing, monitoring, and human‑in‑the‑loop. Persist generated rules and their code in logs and require human review for new rule templates or when the LLM output deviates from expected structure. Track which rules were used in production decisions to support forensics.

13) Consider deterministic extraction instead of executing LLM code: the paper already constrains the LLM output format. Tighten the output formatting requirements and perform string→AST→predicate mapping yourself rather than running the produced code.

Threat model you should document (example to add to paper/engineering plan): assume the LLM may produce arbitrary text (benign mistakes, hallucinations, or adversarially crafted prompts). The attacker goal can be data exfiltration, host compromise, or denial of service. Your mitigations should assume an attacker can influence prompts (via corrupted training examples or an adversarial user providing inputs) and that the LLM can generate syntactically valid but semantically malicious Python unless checked. The minimal secure posture therefore is “never run untrusted code in the host interpreter; parse into a restricted grammar or execute inside a strongly isolated runtime with resource and syscall limits.”

To summarize: the paper states exec() is used but does not describe sandboxing or a threat model. For industrial deployment you must not rely on exec() alone. Use a restricted grammar or AST validation, run code in a constrained separate process or container with cgroups/seccomp/timeouts, whitelist helpers instead of allowing imports, log/audit outputs, and run adversarial tests. These measures align with the paper’s architecture (LLM generates parsable rules that then create binary features) but add the necessary operational security to execute model‑generated logic safely.

### How is k-fold cross-validation used with very small k-shot training sets?
Question:
You select epochs using k-fold cross-validation to avoid overfitting in the linear model trained on rule features. In very low-shot scenarios (e.g., 4 or 8 shots), how do you define folds without collapsing class coverage? The paper says k is 2 or 4, ensuring each fold has at least one example per class. Does this procedure become unstable for multi-class datasets with class imbalance? Did you compare against leave-one-out or stratified repeated holdouts to reduce variance in model selection?
Answer:
Short answer: With $4$–$8$ shot regimes you must choose folds so each validation split still contains every class (the paper enforces this by using $k=2$ or $4$ so each fold has at least one example per class). That approach is simple and practical, but it is higher-variance and can become unstable for multi-class, highly imbalanced settings. The paper does not report explicit comparisons to leave‑one‑out or repeated stratified holdouts; instead it relies on (1) small $k$ ($2$ or $4$) with stratification to preserve class coverage and (2) bagging/ensembling and multiple random train/test draws to reduce variance.

Why the paper uses $k=2$ or $4$ (intuition grounded in the text)
The model inside FeatLLM is very low‑shot ($k$ much smaller than dataset size). The authors state they set $k$ to small values ($2$ or $4$) “guaranteeing that the training set includes at least one example of each class.” With only a few labeled points, larger $k$ can make some validation folds lack examples of certain classes, breaking both metric computation and model fitting for class‑specific weights. Hence the conservative choice of small $k$.

Why that can be unstable for multi‑class, imbalanced data
When classes are many or strongly imbalanced, even a fold with “at least one example” per class is a weak estimate: the validation result depends heavily on that one or two examples and therefore has high variance. Model selection (selecting epoch) based on such a noisy validation curve can flip between epochs, causing instability. This is unavoidable in extreme few‑shot regimes: the smaller the validation set per class, the less reliable the error estimate.

Alternatives and tradeoffs (what you can do)
- Stratified $k$-fold (what the paper effectively uses): always prefer stratified folds so class proportions are preserved as much as possible. For tiny $k$, stratification simply enforces each fold has at least one example per class (what the authors did).  
- Repeated stratified holdout (Monte‑Carlo CV): repeat many random stratified train/val splits and average validation metrics. This lowers variance relative to a single small $k$-fold at the cost of more evaluations. It is a practical alternative when LLM queries aren’t needed at every split (FeatLLM only needs few LLM calls up front, so repeated light-weight tuning/eval is often feasible). The paper does not report this comparison, but it is a sensible option.  
- Leave‑one‑out (LOO): LOO can reduce bias of the validation estimate but in few‑shot multi‑class problems it is often unusable because some classes may not appear if you leave one out of an already tiny class, and LOO has high variance when classes are rare. Also LOO is expensive if you must retrain model for each held out sample — for FeatLLM the downstream linear weight tuning is cheap, so LOO is computationally possible, but the estimate will still be noisy when classes are rare. The paper does not compare against LOO.  
- Nested or pooled validation across ensemble trials: because FeatLLM creates many rule/feature sets via ensemble/bagging, you can pool validation outcomes across ensemble members or use ensemble‑level validation to stabilize epoch selection. The paper’s ensemble/bagging design implicitly reduces sensitivity to one unstable epoch choice.  
- Regularization and conservative early stopping: with tiny validation sets it helps to reduce model capacity, use stronger regularization, or choose fewer training epochs ($200$ epochs with cross‑validation for epoch selection is what the paper uses, but in practice you may prefer smaller max epochs and early stopping thresholds to avoid reacting to noisy validation fluctuations).

What the paper actually did and what it did not
The paper explicitly used $k = 2$ or $4$ so that each fold contains at least one example per class, and it used $k$-fold cross‑validation for epoch selection in the linear model. It does not report experiments comparing this procedure to leave‑one‑out or to repeated/stratified holdout schemes. To control variance across the whole evaluation, the authors repeated the entire experiment multiple times with different random choices of train/test splits ($3$ repetitions) and used ensembling/bagging across rule generations to increase robustness.

Practical recommendation
If you face a multi‑class, imbalanced few‑shot problem, start with stratified $k$-fold with the largest $k$ that still guarantees at least one example per class (as the paper did). If instability remains, try repeated stratified holdouts (average several repeats) or pool validation metrics across the FeatLLM ensemble trials. If computational budget permits, try LOO for the downstream linear tuning as a sanity check, but expect noisy estimates when classes are rare. Finally, favor stronger regularization and rely on FeatLLM’s ensemble/bagging (which the paper shows helps) to reduce the risk of unstable model selection.

In short: the paper’s $k=2$ or $4$ stratified choice is a pragmatic compromise for few‑shot settings; it is susceptible to high variance in imbalanced multi‑class cases, and the paper mitigates this via ensembling and multiple experiment repeats rather than reporting comparisons to LOO or repeated stratified holdouts.

### How are few-shot examples chosen for the prompt, and does example order bias results?
Question:
You mention randomizing the order of few-shot demonstrations because order affects LLM responses. How are the specific examples selected from the k-shot pool—randomly, or with some coverage heuristic (e.g., class balance, feature diversity)? Given that different orders and selections induce different rules, did you evaluate strategies for selecting exemplars that reduce variance or improve performance (e.g., clustering-based prototypes or informative selection), versus pure random choice?
Answer:
Short answer: for the experiments in the paper the $k$-shot demonstrations are drawn randomly (subject to basic class-presence constraints used for cross‑validation), and the only deliberate non‑random choices made to control variance are (1) randomizing the order of those examples in the prompt and (2) using bagging + ensembling across many LLM trials. The paper does not evaluate exemplar‑selection heuristics such as class‑balanced sampling, clustering/prototype selection, or information‑theoretic exemplar picking.

Why that matters and what the paper does about it
LLMs are sensitive to both which exemplars are shown and the order in which they are shown. Intuitively, different exemplars emphasize different local regularities or spurious correlations in a tiny $k$-shot set, and a different order can nudge the LLM’s chain‑of‑thought toward different reasoning paths. The paper addresses those sources of variance in two practical ways. First, it explicitly randomizes the order of few‑shot demonstrations (citing known prompt‑order effects) so that any one ordering does not systematically bias results. Second, it runs the whole rule‑generation pipeline multiple times with bagging (random subsets of features/instances) and a nonzero temperature for LLM decoding, producing diverse rule sets, and then ensembles them (they used $T = 20$ trials and extract $R = 10$ rules per class in the reported setting). This ensemble/bagging strategy is the paper’s main mechanism to reduce variance and improve robustness: incorrect or spurious rules in some trials are averaged out while common, stable rules survive across trials.

Concrete statements from the paper you can rely on
- Sampling: “For the $k$-shot learning experiments, only $k$ ($< N$) labeled samples are randomly sampled to train the model.” The cross‑validation setup also ensures the training fold contains at least one example of each class.  
- Order: the prompt construction “randomize[s] the order of few‑shot demonstrations based on the observation that the order can impact the query outcome of LLM.”  
- Variance control: they use bagging + ensembling, set LLM temperature to $0.5$, and report that ensemble consistently improves performance (ablation shows removing ensemble degrades AUC). The Appendix contains additional analysis on rule diversity across trials.

What the paper does not do (and reasonable next steps)
The paper does not compare different exemplar selection strategies such as class‑balanced sampling, diversity/coverage heuristics, clustering‑based prototype selection, influence‑score or gradient‑based informative sampling, or optimized ordering (e.g., retrieval of nearest neighbours, representative exemplars, or ordering by difficulty). It also does not report experiments that directly contrast e.g. random exemplars versus prototype exemplars or tuned selections. Exploring such strategies is a natural future direction: one could test class‑aware sampling, $k$-means prototypes on feature space, Max‑Min diversity selection, or exemplar selection based on model uncertainty, and measure (i) mean performance, (ii) variance across trials, and (iii) rule stability (fraction of rules reproduced across trials). Given the paper’s finding that ensembling saturates around $T \approx 20$, a promising experiment would be to test whether smarter exemplar selection reduces required $T$ for the same performance/variance.

Practical takeaway
If you’re reproducing or extending FeatLLM, use random $k$-shot sampling and randomize prompt order as the paper does, and rely on bagging+ensemble to stabilize outputs. If you want to reduce API calls or variance further, trying class‑balanced or prototype exemplar selection is a sensible next experiment—but the paper itself reports only the random sampling + bagging/ensembling approach, not comparisons with sophisticated exemplar selection methods.

### What prevents label leakage through feature names or descriptions?
Question:
Because FeatLLM includes detailed feature names and descriptions in the prompt, and some tabular datasets contain columns that are proxies for the label (or include subtle task hints), how do you ensure there is no leakage (e.g., a feature named "disease_present")? Do you sanitize feature names/descriptions or mask obviously label-correlated strings? In the synthetic datasets, was any care taken to avoid textual cues that trivially reveal the target?
Answer:
Short answer: the paper does not perform explicit sanitization or masking of feature names/descriptions. Instead, FeatLLM relies on its prompt design, two-step reasoning, ensemble/bagging, and the downstream weight-tuning to reduce the impact of trivial label proxies; the experimental setup also uses datasets chosen to avoid memorization (including recent UCI additions and synthetic tasks). The authors report empirical evidence (spurious-column experiments and feature-quality analyses) that show the pipeline largely avoids trivial leakage in their evaluated datasets, but they do not claim a formal guarantee against a column that literally names the label.

Explanation (intuitive + technical, tied to the paper)

1) No explicit name-mangling in the method
The Methods and Experiments sections describe that each dataset comes with natural-language feature names and optional definitions and that those are included in the “basic information” part of the prompt. There is no step in the paper that says the authors systematically rename, mask, or remove features that are string-identical to the label (for example converting "disease_present" to "feature_12"). Thus FeatLLM purposely uses the human-readable metadata as input to the LLM rather than sanitizing it.

2) Why that does not automatically imply trivial leakage in their experiments
The paper uses several defenses implicit in the design that reduce the chance that an obviously label-correlated string (or other spurious textual cue) will trivially make the task trivial or leak labels into rule generation:

- Two-step reasoning instruction. The prompt forces the LLM to first infer general relationships between features and the task without looking at the few-shot examples, and only then use examples to derive rules. This encourages rules grounded in prior knowledge and causal tendencies, not mere rote pattern-matching from example serialization that could exploit a literal label-name column.

- Rule format + parsing + downstream fitting. The LLM generates explicit rules which are parsed to binary features. Those binary rule-features are then passed to a simple linear model with non-negative weights $\text{Eq. (1)}$. The model is trained from the held-out few-shot examples to learn per-rule importance; rules that are not predictive in the few-shot data get small weights (and the paper thresholds weights to filter weak rules in the feature-quality analysis). That tuning step filters out many spurious or noisy rules even if they appear in the generated set.

- Ensemble + bagging. FeatLLM repeats rule generation with randomized prompts (temperature, demonstration order) and bagging. That means a single accidental or memorized label-proxy rule from one trial is unlikely to dominate the ensemble. The paper shows that performance improves and stabilizes with $\sim 20$ ensembles, suggesting robustness to occasional noisy rules.

3) Datasets choice and synthetic tasks
The paper explicitly states that two datasets were recently added to UCI after Sept 2023 and two datasets are synthetic, so they were not in the LLM pretraining corpus used (gpt-3.5-turbo-0613). This reduces the chance that the LLM already memorized a mapping. The synthetic datasets were constructed so they could not have been memorized and thus trivial textual memorization is not an evaluation concern for those tasks. The experimental “effect of adding spurious correlations” shows that when unrelated columns are attached, FeatLLM experienced the least performance degradation relative to baselines and that only about $1$--$2\%$ of generated rules used noisy columns—evidence that the method does not trivially latch onto irrelevant textual cues in practice on their benchmarks.

4) What remains a practical concern and recommended safeguards
The paper admits (and the experiments imply) that FeatLLM can still learn spurious correlations in some settings (see the appendix note that attaching closely related columns can cause misunderstanding). Concretely, if a dataset really contains a column whose name or description literally states the label (e.g., "disease_present", "target_flag") or contains near-deterministic proxies, then any method that ingests names could find that as an easy rule. The paper does not claim to guard against that class of leakage.

If you are replicating or applying the method and worry about leakage, reasonable practical safeguards (not claimed in the paper but consistent with its spirit) are: remove or obfuscate obviously label-named columns, withhold explicit label-descriptive text from the feature descriptions during rule-generation, run a quick check for near-deterministic columns (correlation / mutual information with the label) and optionally drop them or mask their names, and examine generated rules for exact-name matching. The paper’s downstream tuning and ensemble will help, but explicit name-sanitization is the most direct protection against trivial label leakage.

Summary
The paper does not sanitize feature names; instead it depends on LLM prompt design (two-step reasoning), parsing + downstream weight tuning, and ensembling/bagging to avoid generating and relying on trivial label-proxy rules, and it uses datasets (including recent and synthetic ones) chosen to reduce memorization risk. Empirically this appears effective on their benchmarks, but there is no formal guarantee—if your dataset contains an explicit label-name feature, you should sanitize or validate it before running FeatLLM.

### Why fix the number of rules per class (e.g., 10), and how sensitive is performance?
Question:
The paper fixes the number of rules per class to 10 and shows minimal sensitivity, yet acknowledges trade-offs with prompt length and overfitting. Conceptually, some tasks may need fewer, more general rules, while others may benefit from many specialized rules. Did you try adaptive stopping criteria (e.g., based on validation improvement or rule novelty)? Also, do you allow nested logic or only flat conjunctions/disjunctions per rule, and how does expressivity trade off against interpretability and stability?
Answer:
Short answer: we fixed $10$ rules per class mainly for practical trade-offs (prompt length, parsing reliability, and overfitting) and because our hyper-parameter sweeps showed little sensitivity around that choice. The paper does allow simple combinations (AND / OR) in rule text and relies on the LLM to parse rules to executable code, but it does not attempt deep nested logical programs. Allowing richer nesting would increase expressivity but also make parsing, stability, and interpretability worse; the paper instead uses weighting + ensembling to control capacity and prune irrelevant rules.

Why “$10$ rules per class” and how sensitive is performance
The Methods and Hyper-parameter Analysis sections explain the reasoning. We fix a constant number of rules per class to avoid two practical failure modes: overly long prompts (LLM input limits and cost) and generating so many features that the downstream few-shot learner overfits. Empirically (Fig. $8$ / Appendix hyper-parameter plots) changing the number of rules did not yield statistically significant gains, so the authors picked $10$ as a sensible operating point that balances (1) adding enough candidate conditions to capture different informative patterns and (2) keeping prompt size and downstream feature dimensionality modest. They explicitly state performance “improves with more ensembles” but that rule-count gains converge and “more rules enlarge input dimensionality … yet also result in overfitting in the low-shot regime.” So sensitivity was measured and found minimal around the chosen value; the choice is pragmatic rather than theoretically optimal.

Did the paper try adaptive stopping (validation improvement or novelty)?
The paper does not report using an adaptive stopping rule for “generate until no improvement” or “stop when rules are novel.” Instead, the design choices to control rule quality are: (a) constrain the prompt and response formatting so the LLM produces a fixed set per class, (b) parse LLM-produced rules into binary features, and (c) learn non-negative linear weights on those binary features (Eq. $1$) so training can down-weight or effectively ignore irrelevant rules. In addition, ensembling with bagging and randomness in prompts helps robustness: useful rules tend to recur across trials, while spurious ones are diluted.

If you want an adaptive approach (not in the paper) that remains consistent with the framework, reasonable options are: use a small validation set and add rules iteratively while monitoring validation AUC, stop when marginal gain falls below a threshold, or accept only rules whose parsed binary feature has minimum support/confidence with the label. Another practical method compatible with the paper’s parsing step is to generate a larger candidate pool in a few LLM calls and then select a subset via forward selection (greedy) or L1 regularization on the linear weights. These were not reported in the paper but would be straightforward extensions.

Nested logic vs. flat conjunctions/disjunctions, and expressivity vs. interpretability/stability
The paper’s response instructions allow the LLM to combine atomic conditions with logical operators (the authors note “Without additional guidance, the LLM can combine multiple rules using logical operators like AND or OR”), and the parsing step uses the LLM itself to generate executable code from the textual rules. Practically, that means rules can express simple conjunctions/disjunctions (e.g., “if age > 60 and cholesterol > X then ...”) but the paper does not pursue or demonstrate deep, nested logical programs (long chains of if/else, nested exceptions, recursion, etc.). The reasons are:

- Parsing reliability: deeper nesting increases syntactic variability in LLM output and parsing becomes fragile. The paper mitigates parsing noise by prompting the LLM to output parseable code and executing it, but complex nested logic would raise parsing risk and execution errors.
- Interpretability: simple rules (single conditions or short conjunctions/disjunctions) remain human-readable and actionable. As soon as you allow arbitrarily nested logic the feature semantics become harder to inspect and trust, which undercuts one of the paper’s stated benefits (interpretable rule-features for downstream models).
- Statistical stability: with small $k$-shot training sets, high-capacity logical structures easily overfit. The paper addresses this by learning non-negative linear weights to down-weight weak rules and using ensembling to average out spurious rule sets. Richer logic would increase the number of effective parameters / feature combinations and worsen overfitting unless you substantially increase data or add strong regularization.

How expressivity trades off against interpretability and stability in this setup
There is the standard bias–variance/interpretability trade-off: more expressive rule languages can capture complex decision boundaries with fewer rules, but they hurt interpretability, are harder to parse robustly from free-form LLM output, and are unstable under few-shot sampling. The authors choose a middle ground: allow useful compositionality (AND/OR) but keep rules short and fix count per class to control dimensionality. Then they rely on three mechanisms to keep expressivity useful but not harmful: (1) LLM-guided rule generation that uses prior knowledge to focus on likely informative features, (2) learning positive weights that prune irrelevant rules, and (3) ensembling/bagging to reduce variance from occasional bad rule-sets.

Practical suggestions consistent with the paper
If you want to experiment beyond the paper’s setup while staying close to its philosophy, try one of these low-effort extensions: generate a bigger candidate pool (e.g., $30$ rules per class in a few calls), then prune using validation AUC or an L1-regularized positive-weight linear model; enforce simple syntactic templates for nesting depth (limit to $2$ clauses) to get more expressivity while keeping parsing stable; or use rule-support / confidence thresholds (as in association-rule mining) as an acceptance criterion for rules. The paper’s framework already supports these interventions because parsing yields executable binary features and the downstream learning step is modular.

Summary
The fixed $10$-rule choice is a pragmatic, empirically validated compromise: it gave reliable performance without bloating prompts or feature space and avoided overfitting in low-shot regimes. The paper did not implement adaptive stopping or deep nested logic; instead it focuses on short compositional rules, LLM-based parsing into code, weight tuning to filter rules, and ensemble bagging for robustness. Adaptive rule-selection and constrained nesting are natural, compatible extensions to try next, but each increases implementation complexity and must be balanced against parsing reliability and low-shot stability.

### How does FeatLLM handle samples that match zero rules or all rules?
Question:
Since features are binary per rule, edge cases can occur. If a sample activates zero rules for all classes, logits become zero and softmax is uniform—do you treat this as an abstention or low-confidence prediction? Conversely, if the sample activates almost all rules for multiple classes, do you cap contributions or regularize weights to avoid overconfident predictions? Is there any calibration step applied after ensembling to improve probability quality?
Answer:
Short answer: FeatLLM handles the zero-rules / all-rules edge cases implicitly via its linear logit model and ensembling; a sample that activates no rules for any class produces zero logits and therefore a uniform (low‑confidence) softmax prediction (the paper does not treat that as a formal “abstention”). Conversely, there is no explicit hard cap on the contribution of many active rules — class logits are the (nonnegative) weighted sum of active rule features, so many active rules can produce large logits and a confident prediction, but the learned weights, positive projection, tuning procedure, and ensembling are used to limit pathological overconfidence in practice. The paper does not report any additional post‑hoc calibration step after ensembling.

Explanation grounded in the paper
The model in FeatLLM converts each LLM-generated rule into a binary feature and for class $k$ computes
$\text{logit}_{k}^{i} = \max(w_{k}, 0)\cdot z_{k}^{i}$,
then $p^{i} = \text{Softmax}([\text{logit}_{1}^{i}, \dots, \text{logit}_{c}^{i}])$ (Eq. $(1)$ in the paper). A few direct consequences follow.

1) Zero‑rules activated for a sample:
If for a given sample all binary rule vectors $z_{k}^{i}$ are zero (no rules matched for any class), every class logit is $0$. After softmax this yields a uniform distribution across classes. The paper treats this outcome as a (naturally) low‑confidence prediction rather than a special abstention mechanism; there is no separate abstention policy described. Intuitively, the model is saying “none of the learned rule‑features apply, so I have no evidence to prefer any class.”

2) Many/all rules activated:
If a sample activates many rules, the logit is the sum of the corresponding (projected) nonnegative weights. There is no explicit clipping of logits or a hard cap on a rule’s contribution in the published method. Instead, the approach relies on the training dynamics and architectural choices to avoid pathological behavior: weights are learned by minimizing cross‑entropy on the few-shot training samples, weights are projected to the nonnegative subspace (so features can only increase class logit), and ensembling with randomized rule generation / bagging is used. Together these reduce the chance that noisy or spurious rule sets produce consistently overconfident wrong predictions. In analysis the authors also demonstrate that tuning learns to downweight irrelevant rules (they report filtering rules with learned weights below a threshold like $0.1$ when inspecting feature quality).

3) Regularization / capping:
The paper does not describe any explicit $L_{2}$/$L_{1}$ regularizer, explicit weight clipping, or a hard cap on summed contributions. Regularization is therefore implicit via the few‑shot training procedure, the positive projection, and early/ cross‑validated epoch selection (they use Adam, learning rate $0.01$, train up to $200$ epochs and pick epoch by k‑fold CV). The ensemble/bagging design is also an implicit regularizer: averaging probabilistic outputs from multiple randomized rule sets smooths predictions and mitigates single‑trial overconfidence.

4) Calibration after ensembling:
No dedicated calibration step (for example temperature scaling or Platt scaling) is reported in the paper. The final prediction is the average of probabilities produced by each ensemble trial. Averaging probabilities across diverse trials tends to improve calibration compared to single deterministic models, but the paper does not perform or report any additional post‑hoc calibration experiments.

Practical implications / what to do if you need different behavior
If you need explicit abstention for zero‑rule samples, add a simple rule: if all logits equal zero (or max probability below a threshold), return abstain. If overconfidence from many active rules becomes a problem in your domain, you can add $L_{2}$ regularization on weights, apply a softmax temperature on logits, clip logits, or run a post‑hoc calibration method (temperature scaling / isotonic regression) on a held‑out calibration set. These are standard remedies; FeatLLM’s paper did not apply them but the model structure admits them naturally.

Summary
FeatLLM defaults to uniform (low‑confidence) predictions when no rules fire, and relies on learned nonnegative weights, cross‑entropy tuning, and ensembling to prevent spurious high confidence when many rules fire. There is no explicit abstention mechanism, weight capping, or post‑hoc calibration reported in the paper, although the authors do inspect and filter low‑weight rules in analysis and rely on ensemble averaging to improve robustness.

### Details on ensembling: averaging probabilities vs. logits and calibration effects
Question:
The paper states that final predictions average class probabilities \(\mathbf{p}^i\) across T trials. Did you compare against averaging logits or stacking (e.g., training a meta-learner on the ensemble outputs)? Averaging probabilities can under- or over-calibrate depending on diversity. Did you measure calibration metrics (e.g., ECE, Brier score) and try temperature scaling or Dirichlet calibration on top of the ensemble?
Answer:
Short answer: the paper only reports averaging class probabilities across the $T$ ensemble trials (it states “the prediction is made by averaging the probability for each class $\mathbf{p}^i$ computed with each weight $\mathbf{w}[t]$”). It does not report experiments that compare averaging logits vs. averaging probabilities, nor does it report stacking/meta‑learners or calibration evaluations (ECE, Brier) or post‑hoc calibration (temperature scaling, Dirichlet).  

Why this matters (intuitively and technically). Averaging probabilities and averaging logits are not the same. Averaging logits corresponds to taking the mean of pre‑softmax scores and then applying softmax, which is equivalent to a geometric‑like averaging in probability space and can preserve stronger relative class preferences from individual members. Averaging probabilities is an arithmetic mean of class likelihoods; if the ensemble members are over‑ or under‑confident in different ways, probability averaging can under‑ or over‑calibrate the final output. Stacking (training a small meta‑learner on the $T$ outputs) can learn to correct systematic biases and reweight models based on validation performance; post‑hoc calibration (temperature scaling or Dirichlet calibration) directly optimizes calibration on a held‑out set and typically improves ECE/Brier without changing ranking.

Specific considerations tied to FeatLLM’s design that affect calibration choices. FeatLLM trains per‑trial linear weights and forms per‑trial logits as
$\text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot\mathbf{z}_k^i$,
so logits are non‑negative and then converted with softmax. Two consequences follow. First, forcing non‑negative weights biases logits upward and removes the ability of any rule to *decrease* a class score; that structural bias can skew confidences and interact with ensemble averaging. Second, because each trial’s logit baseline is constrained, the scale and spread of logits across trials may be limited, which changes how averaging logits vs. probabilities behaves. Both observations make calibration particularly relevant: a calibration layer can correct global over/under‑confidence introduced by the non‑negativity and the limited shot regime.

Practical experiments I would recommend (concise recipe you can run on the paper’s setup)
1. Compute calibration metrics for the current probability‑averaged ensemble: Expected Calibration Error (ECE, with reasonable binning like 15–20 bins) and Brier score on a held‑out validation fold used in the paper’s $k$‑fold process. Report reliability diagrams.  
2. Compare three simple aggregation strategies: (A) average probabilities (current), (B) average logits then softmax, (C) majority‑vote (for hard labels) as a baseline. Evaluate accuracy/AUC plus ECE/Brier.  
3. Try stacking: use a small validation set to train a logistic regression (or a shallow neural net) that takes either per‑trial logits or per‑trial probabilities as features and outputs calibrated probabilities. Evaluate generalization on test folds. Stacking often outperforms naive averaging when ensemble members have complementary strengths.  
4. Apply temperature scaling to the final logits (fit a single scalar temperature on the validation set minimizing negative log likelihood); this is simple and low‑risk. For multiclass, fit temperature on the vector of logits before softmax. Evaluate ECE/Brier after scaling.  
5. Try Dirichlet calibration if multiclass calibration is still poor: Dirichlet calibration fits a richer mapping from logits to probabilities and often beats scalar temperature for multiclass problems. Use the validation set for fitting.  
6. Optionally, calibrate each trial separately (fit temperatures per trial) and then average resulting probabilities; or average logits (possibly after per‑trial scaling) before softmax. Compare these variants.

Which aggregation + calibration I expect to help for FeatLLM. Because per‑trial logits are non‑negative and of limited dynamic range, averaging logits may restore sharper class differences if trials consistently favor the same class; however if some trials are strongly miscalibrated (overconfident), averaging probabilities can dilute that effect. In practice stacking or temperature/Dirichlet calibration on top of the ensemble is the most reliable fix for calibration problems: temperature scaling is cheap and often yields immediate ECE/Brier improvements; Dirichlet or a small meta‑learner will further help when different trials have systematic, class‑dependent biases.

A few implementation notes tied to the paper’s constraints. FeatLLM is designed for low‑shot regimes where validation data is scarce; calibration needs a held‑out set, so use $k$‑fold splits (as the paper already does) or use cross‑validated temperature fitting to avoid losing too many training shots. Also report both discrimination (AUC/accuracy) and calibration (ECE/Brier) because a method can keep AUC but improve expected calibration. Finally, because the LLM temperature was already changed to increase rule diversity, you may find trial diversity helpful for ensemble calibration but also creating heteroskedastic confidences — another reason to fit a calibration layer.

Summary: the paper only averages probabilities and does not report comparisons with logit averaging, stacking, or calibration metrics. Given FeatLLM’s non‑negativity constraint on weights and low‑shot setting, evaluating ECE/Brier and trying simple fixes (temperature scaling, Dirichlet calibration, or stacking on logits) is a compact, practical next step that I would expect to improve calibration without harming discrimination. If you want, I can write a short experiment plan with code snippets to run the comparisons on one of the paper’s datasets.

### What is the exact objective and regularization used for weight tuning on binary rule features?
Question:
The linear model is trained with cross-entropy over softmaxed per-class logits. Are there any regularizers (e.g., L1 to encourage sparsity over rules, L2 for stability) applied to \(\mathbf{w}_k\)? Given potentially noisy or redundant rules, did you study the effect of L1 on pruning spurious rules vs. relying solely on weight magnitudes? Also, why 200 epochs with Adam and LR 0.01—did you perform sensitivity analysis to avoid overfitting in the tiny-sample regime?
Answer:
Short answer: the downstream linear model is trained with a standard cross-entropy objective on softmaxed logits, with no explicit $L_1$/$L_2$ penalty reported in the paper. The only modeling constraints / implicit regularizers are (1) a non-negativity projection of weights via \(\max(\mathbf{w}_k,0)\), (2) selection of training length via $k$-fold cross-validation (early‑stopping style), and (3) post hoc pruning by thresholding small learned weights (they report using $0.1$). Training uses Adam with learning rate $0.01$ for $200$ epochs; they say they choose epochs with $k$-fold CV and report hyperparameter sensitivity for ensemble size and number-of-rules in the appendix.

Explanation and grounding to the paper: Equation (1) in Section 3.2 defines the logits and probabilities
\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,\qquad
\mathbf{p}^i=\text{Softmax}([\text{logit}_1^i,\dots,\text{logit}_c^i]),
\]
and they state explicitly “We optimize the cross-entropy loss to learn the weight \(\mathbf{w}_k\) using a few-shot training samples.” The paper does not introduce an explicit $L_1$ or $L_2$ regularizer in the loss; instead they enforce non-negativity by projecting weights into the positive subspace (via the \(\max(\cdot,0)\) operation). This both encodes a modeling assumption (rules should not *decrease* class likelihood) and acts like a simple constraint that reduces the effective hypothesis space.

Why no explicit $L_1$/$L_2$ and how they combat overfitting/noisy rules: the authors rely on several mechanisms rather than explicit penalties. First, the linear model is extremely low-complexity (no bias term and binary inputs), which already reduces overfitting risk in few-shot regimes. Second, they run $k$-fold cross-validation to select training length (they say “We employ $k$-fold cross-validation for optimal epoch selection”), which functions like early stopping. Third, the ensemble with bagging across multiple LLM-generated rule-sets reduces sensitivity to any one noisy rule-set. Fourth, they remove unimportant rules after training by thresholding learned weights (they report using $0.1$ chosen from the weight histogram), which is a pragmatic sparsification step. The ablation (Section 4.2) shows the benefit of tuning weights, and the “Quality of features” experiment shows that many rules are informative before tuning and tuning removes weak ones.

On the optimizer / epochs / learning rate: they set Adam with $LR=0.01$ and train for $200$ epochs; the paper states they used $k$-fold CV to choose the optimal epoch (so the fixed “200 epochs” is an upper bound and CV determines the stopping point). The hyperparameter analyses included in Appendix (and Figure references in the main text) analyze the effect of ensemble size and number of rules; the paper does not present a detailed ablation sweeping $L_1$/$L_2$ penalties. So while $200$ epochs and $LR=0.01$ are the reported defaults, the authors mitigate overfitting via CV-based epoch selection and ensembling rather than via explicit weight decay.

Did they study $L_1$ for pruning vs relying on magnitudes? The paper does not report experiments comparing explicit $L_1$ regularization to their magnitude-threshold pruning. Their reported sparsification is done post-training by thresholding learned weights (threshold $0.1$) and by counting how many rule-features have $AUROC > 0.5$ before and after tuning. They therefore rely on learned magnitude + thresholding and ensemble robustness rather than an $L_1$ penalty.

Practical implications / suggested follow-ups: given the few-shot setting and binary features, an explicit sparsity regularizer such as $L_1$ (or $L_1$ with cross‑validated strength) would be a natural additional experiment; it might give more principled pruning (and potentially faster convergence) than thresholding. Similarly, adding an $L_2$ weight decay would be useful to test stability if one expects noisier rule outputs. But note that the paper’s combination of non-negativity, low model capacity, CV-based epoch selection, and bagged ensembling is their chosen strategy to avoid overfitting in tiny-sample regimes.

### How do you measure and filter "useful" rules before and after tuning?
Question:
The paper reports the fraction of rules with AUROC > 0.5 against the target ("Before tuning") and then filters rules with learned weights below 0.1 ("After tuning"). Why AUROC > 0.5 as the usefulness threshold and 0.1 for weights—are these data-dependent? Also, AUROC on very low-shot data can be high-variance; did you use any cross-validated or bootstrapped estimate to assess rule usefulness robustly before final filtering?
Answer:
Short answer: $\mathrm{AUROC} > 0.5$ and $\text{weight} > 0.1$ are heuristics rather than theoretically fixed cutoffs. In the paper the $\mathrm{AUROC} > 0.5$ cutoff is used as the intuitive “better than random” test for a binary (rule vs. target) relationship, and the $0.1$ weight threshold was chosen empirically after inspecting the histogram of learned weights. The authors did not report a dedicated cross‑validated or bootstrapped per‑rule $\mathrm{AUROC}$ procedure in the paper; instead they reduce variance and improve robustness by ensembling/bagging, repeating experiments with different train/test splits, and using $k$-fold CV to select epochs for training the linear model.

More detail and interpretation grounded in the paper
- Why $\mathrm{AUROC} > 0.5$? $\mathrm{AUROC}$ is a natural way to measure how well a binary feature (a rule firing or not) ranks positive vs. negative cases. A value of $0.5$ is the value of a random classifier, so counting rules with $\mathrm{AUROC} > 0.5$ is a simple “useful vs. not-useful” heuristic: rules that do no better than random are unlikely to help. This choice is explicitly what the paper reports (“ratio of useful features with an $\mathrm{AUROC}$ higher than $0.5$”). It is a coarse, interpretable threshold rather than a statistical test; it is therefore a pragmatic, not a hard, theoretically optimal choice.

- Why weight threshold $0.1$? After the LLM generates binary rule features the paper trains a linear model with non‑negative weights (Eq. (1)). The authors state that the threshold of $0.1$ was set “taking into consideration the overall histogram of weights.” That is, $0.1$ is an empirical cutoff derived by inspecting the distribution of learned weights across experiments and choosing a value that separates near‑zero (uninformative) weights from ones that contribute meaningfully. So this cutoff is data/experiment dependent in practice — it’s a practical rule of thumb motivated by the observed weight distribution in their runs.

- Are these choices data‑dependent? Yes. $\mathrm{AUROC} > 0.5$ is a generic baseline (and thus minimally data‑dependent), but how useful that threshold is will depend on class balance, noise, and the low‑shot regime. The $0.1$ weight cutoff is explicitly empirical and depends on the learned weight histogram for the datasets and shot levels in the paper. The paper does not claim these thresholds are universal; they were chosen for interpretability and shown to work across the evaluated datasets.

- What about $\mathrm{AUROC}$ variance in very low‑shot settings? The paper acknowledges low‑shot instability and addresses robustness in several ways: rules are generated multiple times with bagging and LLM temperature randomness, an ensemble averages across $T=20$ trials (they use $T=20$), experiments are repeated three times with different train/test splits and averages/stds are reported, and $k$-fold cross‑validation is used to pick training epochs for the linear model. However, the paper does not report using per‑rule cross‑validated $\mathrm{AUROC}$ estimates, bootstrap confidence intervals, or permutation tests to quantify $\mathrm{AUROC}$ uncertainty for individual rules. In short, the authors rely on ensemble/stability and aggregate reporting rather than explicit per‑rule bootstrapped uncertainty estimates.

Practical implications and recommendations (if you want more robust filtering)
If you are concerned about noisy $\mathrm{AUROC}$ estimates in your low‑shot setting, consider these simple extensions (all consistent with the paper’s pipeline):
- Estimate per‑rule $\mathrm{AUROC}$ with cross‑validation or bootstrap to get confidence intervals and only mark a rule “useful” if its lower CI bound exceeds $0.5$ (or another calibrated threshold).
- Use permutation testing (shuffle labels) to get an empirical null distribution of rule $\mathrm{AUROC}$ and compute $p$-values or FDR corrections to control false discoveries among many rules.
- Replace a hard weight cutoff with a stability criterion: keep rules that are repeatedly assigned non‑negligible weight across ensemble trials (frequency threshold), which leverages the paper’s bagging/ensembling mechanism.
- Regularize the linear model (L1 or group sparsity) so that irrelevant rules are shrunk toward zero more aggressively; choose regularization strength by CV even in low‑shot (nested CV or Bayesian priors can help).
- Use rank‑based filtering (e.g., top-$k$ rules by median weight or median $\mathrm{AUROC}$ across bootstrap samples) rather than absolute thresholds if weight scales vary across datasets.

Summary
The $\mathrm{AUROC} > 0.5$ and $\text{weight} > 0.1$ cutoffs in the paper are practical, interpretable heuristics: $\mathrm{AUROC} > 0.5$ tests “better than random,” while $0.1$ is an empirical weight threshold set after inspecting the weight histogram. The paper mitigates low‑shot variance through ensembling, bagging, repeated trials, and $k$-fold CV for training, but it does not report bootstrapped or cross‑validated per‑rule $\mathrm{AUROC}$ estimates — adding those would be a sensible way to make the “useful rule” filtering more statistically robust.
