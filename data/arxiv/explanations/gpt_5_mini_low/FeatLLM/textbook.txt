\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Why LLMs for Few-Shot Tabular Learning?

# The challenge of few-shot learning on tabular data
Few-shot learning for tabular data is fundamentally difficult because tabular datasets are heterogeneous, often small, and lack the kind of spatial or sequential structure that makes transfer and augmentation straightforward. In a typical supervised setup we have a labeled dataset $\mathcal{D}=\{(\mathbf{x}^i,\mathbf{y}^i)\}_{i=1}^N$ where each input $\mathbf{x}^i\in\mathbb{R}^d$ (or a mixed-type vector with categorical and numeric columns) and $d$ can vary greatly across problems. In the few-shot regime we are restricted to only $k \ll N$ labeled examples for training. With so few labels it is easy for a learned model to latch onto spurious correlations in the available features, and standard regularization, data augmentation, or self-supervised pretraining approaches are often insufficient because (1) tabular features are heterogeneous so designing universally effective augmentations is hard, and (2) when $k$ is small there is simply not enough signal to reliably estimate complex relationships.

Traditional tabular learning methods—logistic regression, tree ensembles like RandomForest or XGBoost—work well when there is sufficient labeled data or when carefully engineered features are available. But in many real-world domains (medical records, finance, small scientific studies) labeled data are costly and domain expertise for feature engineering may not be available. Few-shot methods attempt to bridge that gap: some use synthetic pretraining across many datasets, some exploit unlabeled data, and others adapt large models via parameter-efficient fine-tuning. Each has practical limitations. The key problem remains: how do we obtain informative, low-dimensional, and interpretable features that capture the true predictive criteria of the task when only a handful of labeled examples exist?

# LLMs’ prior knowledge and reasoning as a substitute for domain expertise
Large Language Models (LLMs) are trained on massive corpora of text that contain not just language patterns but also embodied domain knowledge—medical, financial, scientific, and everyday causal regularities. This prior knowledge allows LLMs to make reasonable inferences about relationships between concepts even when provided only a small number of examples. Concretely, an LLM can read a task description and the natural-language names and definitions of columns $F=\{f_j\}_{j=1}^d$, then draw on its background knowledge to hypothesize which features are likely to matter or how feature values map to outcomes.

Beyond stored facts, modern LLMs exhibit emergent reasoning behaviors when prompted appropriately: by providing a task description and a few demonstrations, the model can produce chain-of-thought style reasoning that reveals why a particular label follows from certain feature patterns. In the context of tabular tasks this means the LLM can not only guess labels for examples, but also propose human-interpretable decision criteria—rules such as ``if age $>$ 65 and blood pressure $>$ 140 then high risk''. Those rules are precisely the sort of domain-guided, high-signal features that a few-shot classifier desperately needs: they distill prior knowledge into conditions that partition the input space in ways relevant to the target.

Using LLMs as a source of such rules turns the model into an automated domain expert: it leverages broad textual training to suggest plausible causal tendencies and concrete feature conditions that go far beyond what can be inferred from a handful of labeled points alone.

# Limitations of end-to-end LLM inference: latency, cost, API-only access, and prompt length
While LLMs can be applied in an end-to-end manner—serialize a row of tabular data into natural language, include the task description and few-shot examples in a prompt, and ask the LLM to predict the label—this approach has several practical drawbacks that restrict adoption in real-world systems.

Latency and cost: End-to-end use typically requires one LLM inference per sample at prediction time. For moderate to large test sets this becomes expensive and slow, especially when using commercial API-backed LLMs where each call has a monetary cost and throughput limits. For production systems that must score many rows with low latency, per-sample LLM calls are often unacceptable.

API-only access and lack of fine-tuning: Many high-quality LLMs are offered only as inference APIs without access to weights or fine-tuning hooks. Methods that require parameter-efficient tuning or training the LLM (to adapt to task-specific patterns) become infeasible in those cases. Even parameter-efficient fine-tuning approaches presuppose some ability to run or modify the model, which is not guaranteed for API-only models.

Prompt size limits: Classic serialization approaches concatenate feature descriptions, feature values, and examples into a prompt. When $d$ is large or example sets are long, the prompt length can exceed the model’s context window, or the model’s performance can degrade because important information is truncated. This is especially problematic for datasets with dozens or hundreds of columns where one would like the LLM to consider many features jointly.

These limitations motivate a different use of LLMs: instead of relying on them at inference time or requiring fine-tuning, can we use their strengths once to produce reusable artifacts that enable cheap downstream inference?

# From predictions to feature engineering: reframing the role of LLMs
The central idea is to reframe LLMs from label predictors to feature engineers. Rather than asking an LLM to label each new sample, we ask it once (or a limited number of times) to describe the predictive criteria for each class in human-readable rule form. These rules are then parsed into deterministic binary features that can be applied cheaply to all samples. Concretely, a rule might be of the form ``age $>$ 65 and cholesterol $>$ 240'', and we convert it into a binary feature that is 1 when that condition holds and 0 otherwise. Once a set of rules is produced, a simple downstream model—e.g., a linear model with non-negative weights—can be trained on the few labeled examples to combine these rule-based features into class probabilities.

This reframing has several practical advantages. First, inference no longer requires any LLM calls: the generated features are standard deterministic transformations of input columns, so scoring a new row is as cheap as evaluating the rules and applying a linear dot product. That eliminates per-sample latency and API cost. Second, since rule generation can be done with only API-level access and a bounded number of queries (for instance, tens of prompts rather than one per test sample), the approach is compatible with LLMs that do not permit fine-tuning. Third, by having the LLM produce concise, human-readable rules, we gain interpretability—each learned feature has an explicit semantic meaning relating to the task—and enable straightforward debugging and human oversight. Finally, because rules are discrete programmatic checks, they do not require the entire dataset to be serialized into a single prompt, mitigating the prompt-length problem: rule extraction can be done via multiple queries with feature bagging or ensembling strategies so that each prompt fits within the context window.

This feature-engineering role leverages the LLM’s best qualities—prior knowledge and reasoning—while avoiding its weaknesses for large-scale, low-latency deployment.

# High-level overview of FeatLLM and its contributions
FeatLLM operationalizes the idea above into a practical framework for few-shot tabular learning. At a high level it performs the following steps: (1) prompt an LLM to infer and output a fixed number of rules per class using a carefully structured prompt that provides the task description, feature definitions, and a small set of demonstrations; (2) parse the LLM’s natural-language rules into executable code that creates binary features indicating whether each rule holds for a given sample; (3) train a simple downstream model (e.g., a linear model with non-negative weights) on the few-shot labeled data to learn the importance of each rule-derived feature; and (4) repeat the rule-generation and training steps multiple times with randomization (bagging of features or examples, high sampling temperature, and varied demonstration order) to produce an ensemble whose averaged probabilities improve robustness.

FeatLLM’s design choices reflect several concrete contributions and practical benefits. First, the prompt design separates reasoning into two phases: (A) infer general tendencies or causal relationships between features and the task from the model’s prior (without looking at examples), and (B) use those tendencies plus the few-shot demonstrations to deduce explicit rules for each class. This two-step instruction encourages the LLM to leverage prior knowledge rather than overfitting to idiosyncrasies in a small example set. Second, the framework deliberately constrains the format and number of rules (e.g., a fixed number $R$ of rules per class) so that the feature dimensionality remains tractable for downstream learning and for ensemble aggregation. Third, FeatLLM uses the LLM itself to parse noisy natural-language rules into executable code rather than writing brittle hand-coded parsers; this reduces engineering effort and exploits the LLM’s strong capabilities in understanding and generating structured code. Fourth, by projecting the linear weights into the non-negative subspace (using $\max(\mathbf{w}_k,0)$ during inference) FeatLLM ensures rule features cannot negatively flip a class likelihood—this matches the intuition that a rule for a class should only increase evidence for that class, while tuning allows the model to downweight unhelpful rules.

Empirically, FeatLLM demonstrates that LLM-generated rule features are highly informative: a large fraction of generated rules show positive predictive signal (AUROC $>$ 0.5) before any tuning, and tuning plus ensembling further filters and amplifies useful rules. Because FeatLLM creates reusable features, the inference cost matches that of conventional methods while delivering strong few-shot performance, often outperforming other LLM-based baselines that require per-sample inference or finetuning. Importantly, FeatLLM is compatible with API-only LLMs, avoids prompt-length limitations via bagging and ensembling, and produces interpretable, inspectable rule features that can aid practitioners in domains where transparency matters.

In sum, FeatLLM reframes the role of LLMs from expensive per-sample predictors to one-time (or limited) feature engineers that inject prior knowledge and structured reasoning into few-shot tabular learning. This reframing addresses practical deployment constraints—latency, cost, API access, and prompt length—while delivering interpretable, high-quality features that enable simple downstream models to achieve strong performance with very few labeled examples.

Background: Few-Shot Tabular Learning and Language-Interfaced Methods

# Few-shot learning in tabular domains: risks of overfitting and spurious correlations
Few-shot learning addresses the scenario where only a very small number of labeled examples are available for a target task. In tabular domains this problem is acute because tabular datasets are often heterogeneous (continuous, categorical, ordinal features), and signal can be subtle or distributed across many columns. When training standard supervised models with only a handful of labeled examples, those models easily fit idiosyncratic patterns in the small training set that do not generalize. In other words, overfitting is a primary risk: with few examples, complex models can pick up noise and incidental associations that are not causal or reliable for future data.

A related and particularly important failure mode in low-shot tabular learning is learning spurious correlations. Spurious correlations are associations present in the limited training data that arise from sampling noise, dataset collection artifacts, or coincidental covariation between some columns and the target. Because tabular data may include many columns, some unrelated columns will by chance correlate with the label in a tiny sample. A learner that treats all correlations as equally informative can produce predictions that rely heavily on these spurious signals and therefore degrade dramatically when tested on new data or when irrelevant columns are added. The paper emphasizes this risk and motivates methods that can inject stronger inductive biases or external knowledge so that the learner focuses on plausible, semantically meaningful relationships rather than accidental patterns.

In summary, few-shot tabular learning must contend with two intertwined dangers: (1) overfitting due to limited labeled data, and (2) exploitation of spurious correlations when irrelevant features appear predictive in a small sample. Any successful few-shot solution for tabular data needs mechanisms to mitigate these risks—either by adding appropriate priors, leveraging external or auxiliary data, or constraining model complexity so that only robust, explainable relations are used for prediction.

# Classical strategies: semi-supervision, self-supervision, and transfer learning
Classical approaches to reduce overfitting and improve generalization in low-data regimes introduce additional sources of information or change the training objectives to create more robust inductive biases. Three major directions discussed in the paper are semi-supervision, self-supervision, and transfer learning.

Semi-supervised approaches aim to exploit large amounts of unlabeled data that are often easier to collect than labeled examples. In the tabular setting this can mean using an unlabeled corpus from the same domain together with a small labeled subset, often combined with carefully designed augmentations to encourage the model to learn stable structure. Although semi-supervised methods can provide extra signal and improve performance, the heterogeneous nature of tabular data makes it hard to design universally effective augmentations. The paper notes that such strategies have not consistently yielded large gains in very low-shot settings for tabular data.

Self-supervised (or unsupervised pretext) objectives offer another route: create learning tasks from the data itself (for example masking or corruption and reconstruction) so that the model learns useful representations before fine-tuning on the small labeled set. Examples include masking columns and training the model to reconstruct them, or contrastive objectives that encourage invariance under suitable data transformations. Self-supervision can produce a representation that transfers to downstream low-shot tasks, but again the diversity and structure of tabular features limit how generally applicable these pretext tasks are.

Transfer learning tackles the problem by pre-training a model on many tasks or datasets so that it acquires broadly useful inductive biases. Once pretrained, the model can be adapted to a new target task with few labeled samples. In tabular learning this has taken two forms: (a) training on a broad range of tabular datasets to learn cross-table semantic relationships (for example, methods that use column names and values to learn column semantics), and (b) large-scale synthetic pretraining in which a model is exposed to many artificially generated distributions to develop a flexible prior. The advantage of these approaches is that they can encode priors about likely data generating processes which then guide learning on new small datasets.

Each of these classical strategies imposes different requirements. Semi-supervision demands access to unlabeled data from the same domain. Self-supervision requires a pretext task that actually captures transferable structure. Transfer learning requires pretraining resources and datasets (or synthetic data generators) that encompass the kinds of patterns one will encounter at test time. The paper positions these classical techniques as effective but imperfect, which motivates exploring alternative sources of prior knowledge—specifically, knowledge embedded in Large Language Models (LLMs).

# Representative systems: TransTab, TabPFN, SCARF, STUNT
The literature contains concrete representative systems that embody the classical directions described above. The paper discusses several notable methods that target few-shot tabular learning.

TransTab (referred to as TransTab in the paper) is an example of transfer learning for tabular data that leverages column names and their semantics. It trains transformer-based models across many tables to capture semantic relationships between columns, not just the raw values. By learning how column names and values relate across diverse datasets, TransTab gains the ability to generalize to new tabular tasks in a zero-shot or few-shot way: the learned representations let the model make better use of limited labeled examples at test time.

TabPFN takes a different transfer route: it pretrains a Bayesian neural network on a large mixture of synthetic distributions. The key idea is to expose the model during pretraining to many plausible data-generating processes so that, at inference time, it can act as a strong prior over classifiers for small datasets. TabPFN’s synthetic pretraining enables it to perform inference by ingesting both training and test samples of the target task without further gradient-based learning, which is a valuable property in extreme low-shot settings.

SCARF and STUNT are methods that exploit additional unlabeled data or synthetic augmentation in order to boost few-shot performance. SCARF uses large amounts of unlabeled data together with task-specific augmentations, while STUNT develops strategies for leveraging unlabeled samples to improve robustness in low-shot regimes. These approaches can be powerful when suitable unlabeled corpora exist, but the paper points out that collecting such unlabeled data is not always feasible in real-world applications, limiting their practical applicability.

Taken together, these representative systems illustrate different trade-offs: TransTab and TabPFN invest in pretraining over multiple tasks or synthetic distributions to produce strong priors; SCARF and STUNT exploit extra unlabeled data; each brings advantages but also practical constraints (availability of pretraining data, synthetic distribution design, or unlabeled datasets). The FeatLLM approach proposed in the paper is presented as an alternative that leverages the knowledge embedded in LLMs without requiring large unlabeled corpora, custom pretraining, or model fine-tuning.

# Language-interfaced tabular learning: data serialization and prompting
Language-interfaced tabular learning methods treat tabular prediction as a natural language reasoning problem by serializing structured rows into textual prompts that are then processed by LLMs. The serialization encodes each feature and its value into simple textual statements. For a single example with features F = \{f_1, ..., f_d\} and values \mathbf{x}^i = (x^i_1, ..., x^i_d), the typical serialization used in the paper takes the form:

"f_1 is x^i_1. ... f_d is x^i_d. Answer: y^i"

This serialized text—optionally augmented with feature descriptions, the task description, and some few-shot demonstrations—is then fed to an LLM which produces a prediction or an explanation. The LLM’s pretraining on massive text corpora provides priors about the world (for instance, medical knowledge about age and disease risk), and the prompt can combine that prior knowledge with the few labeled examples to guide inference.

Prompt design is central in this style of approach. A good prompt must supply the task description (what to predict), feature descriptions (types, definitions, possible categorical values), and a small set of demonstrations to encourage the LLM to use the supplied features correctly. The paper highlights that careful prompt construction can make LLMs act, effectively, as a domain expert: they can infer causal tendencies between features and target labels (e.g., "older age increases risk for X") and use that prior knowledge in few-shot classification.

However, serializing many features or many examples can create very long prompts. Because LLMs have finite context windows, long serializations can either exceed the model’s length limits or degrade performance when the prompt becomes too long. This creates a practical limitation: language-interfaced approaches must balance the amount of serialized information against the LLM’s context capacity. The FeatLLM paper uses this insight to motivate a design where the LLM is used to generate compact, reusable artifacts (rules/features) rather than to produce per-sample predictions based on long serializations.

# In-context learning vs parameter-efficient fine-tuning (LoRA, IA3)
Two primary paradigms for using LLMs in downstream tasks are in-context learning and parameter-efficient fine-tuning.

In-context learning supplies the LLM with a textual prompt that includes a description of the task and a small number of example input–label pairs; the LLM produces predictions for new inputs without any weight updates. This approach is appealing because it requires no gradient-based training and can leverage black-box API models like GPT-3.5 or GPT-4. In the tabular setting, in-context learning means serializing a handful of training examples with their labels in the prompt and asking the model to predict the label of a new serialized example. The paper notes that in-context learning demonstrates the LLM’s ability to generalize from few examples by leveraging prior knowledge encoded during pretraining.

Parameter-efficient fine-tuning methods, such as LoRA and IA3, take another route: they update only a small number of additional parameters or low-rank adapters while keeping the bulk of the LLM fixed. This allows adapting a large model to a new task with limited computation and relatively small labeled datasets. In the tabular literature cited by the paper, approaches like TabLLM use IA3-style tuning so the model can better calibrate to the specific statistical patterns of a tabular dataset. Parameter-efficient tuning typically yields higher accuracy than pure in-context learning when the tuning procedure and model access are available.

Each strategy has tradeoffs. In-context learning requires only API access and no training but can be sensitive to prompt length and the order of demonstrations. Parameter-efficient tuning can improve performance but needs the ability to update model weights (which may not be possible for commercial LLMs that only expose inference APIs) and can be costly when large models are involved. The FeatLLM paper emphasizes this practical constraint: many top-performing LLMs offer only inference API access, making fine-tuning infeasible. That motivates FeatLLM’s design goal of using LLMs via prompts to engineer features while keeping downstream inference lightweight and independent of the LLM.

# Known issues: context window limits, per-sample LLM inference costs, and generalization
When applying LLM-based methods to tabular learning, practitioners must confront several well-known practical limitations. First is the context window limit: LLMs can only accept prompts up to a maximum token length. For tabular datasets with many features, serializing entire rows plus many demonstrations can easily hit that limit, or at least force truncation that loses important information. Even when the prompt fits, very long prompts can degrade in-context performance because the model must attend to a large amount of text and may not prioritize the right pieces of information.

Second, many language-interfaced approaches perform at inference time by passing every test sample through the LLM. That is, per-sample LLM inference is required to produce predictions. This is computationally expensive and slow compared to running a conventional lightweight classifier, and it can be infeasible in production due to latency or API cost constraints. The paper calls this out as a key drawback of end-to-end LLM prediction methods.

Third, generalization concerns remain. Even though LLMs carry rich prior knowledge, their use as black-box predictors risks over-reliance on spurious patterns present in the few demonstration examples or on the accidental phrasing in prompts. The order of demonstrations can affect outcomes, and the LLM may infer rules that work on the prompt examples but do not generalize. Furthermore, where LLMs are used for per-sample inference, robustness can be undermined by variability in model outputs and temperature-driven randomness.

The FeatLLM approach addresses these practical issues by changing how the LLM is used: rather than running the LLM on every test sample, the LLM is queried a limited number of times to generate human-readable rules that become binary features. Once these features are generated and parsed into code, downstream inference uses a simple parametric model (e.g., a linear model) that runs efficiently without calling the LLM. This design reduces per-sample LLM inference cost, avoids extensive fine-tuning requirements, and mitigates context window problems by using bagging and ensembling to limit prompt size per query. It also aims to improve generalization by instructing the LLM to first reason about causal tendencies (leveraging prior knowledge) and then formulate class-specific rules, thereby helping avoid rules that exploit spurious correlations in the small labeled set.

# Concluding perspective
This chapter reviewed the foundational ideas behind few-shot tabular learning and the recent trend of language-interfaced methods that serialize tabular inputs into text for LLMs. Classical strategies—semi-supervision, self-supervision, and transfer learning—provide various avenues to supply additional inductive bias, but each has practical limitations. Language-interfaced methods offer a powerful source of prior knowledge through LLMs, yet they face concrete issues: prompt length limits, the computational cost of per-sample LLM inference, and sensitivity to demonstration ordering and spurious correlations.

FeatLLM (as described in the paper) sits at the intersection of these observations: it leverages LLMs’ world knowledge and reasoning not to make end-to-end predictions for every sample but to act as a feature engineer that extracts rules. These rules are parsed into binary features and combined with a simple downstream learner. This architecture is motivated directly by the practical and methodological concerns reviewed in this chapter and seeks to retain the strengths of language-interfaced approaches while ameliorating their principal limitations.

Problem Formulation and Setup

# Dataset notation: samples, features, labels, and feature metadata
We consider a tabular dataset used for supervised classification. The dataset is denoted by
\[
\mathcal{D} = \{(\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^{N},
\]
where $N$ is the total number of labeled samples. Each input sample $\mathbf{x}^i$ is a $d$-dimensional vector of feature values,
\[
\mathbf{x}^i = (x^i_1, x^i_2, \dots, x^i_d) \in \mathbb{R}^d \ \text{(or categorical encodings as appropriate)}.
\]
The dataset contains $d$ columns (attributes) and each column has a human-readable name. We denote the set of feature names by
\[
F = \{f_j\}_{j=1}^{d},
\]
where $f_j$ is the natural-language name for column $j$. In addition to the name, each feature may come with an optional textual description that explains its meaning or value type (for example, whether it is numerical or categorical, and, for categorical features, the possible categories). These descriptions are treated as metadata and are used by FeatLLM to guide rule generation.

The label for sample $i$ is denoted by $\mathbf{y}^i$. In the classification tasks considered, each $\mathbf{y}^i$ is a membership in a finite set of classes. If there are $c$ classes, labels can be represented as integers in $\{1,\dots,c\}$ or as one-hot vectors depending on the downstream loss formulation.

The FeatLLM pipeline operates in three conceptual stages: (1) it queries a large language model (LLM) to extract human-readable rules that relate features to classes, (2) it parses and applies those rules to the samples to produce engineered binary features, and (3) it fits a simple downstream model that maps those engineered features to class likelihoods. The notation above describes the original tabular input and its metadata, which are the starting point for the rule extraction and feature engineering steps.

# Few-shot regime definition (k-shot)
The work focuses on the few-shot learning regime, commonly described as $k$-shot learning. In this setup a small number, $k$, of labeled samples from the full dataset are used for training the downstream model (and for providing demonstration examples to the LLM). Formally, given the full dataset $\mathcal{D}$, a training subset of size $k$ is sampled:
\[
\mathcal{D}_{\text{train}} = \{(\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^{k},\quad k \ll N.
\]
The remainder of the data may be used for validation and testing. Typical values of $k$ in the experiments include very small counts such as 4, 8, 16, and up to 32; the design of the FeatLLM framework is intended to be particularly effective for small $k$.

In FeatLLM the same $k$ labeled examples serve two roles: they provide few-shot demonstrations inside the prompts to the LLM (so the model can leverage in-context learning) and they are used to learn the weights of the simple downstream predictor that maps rule-based features to class likelihoods. Because $k$ is small, the method is careful to leverage prior knowledge from the LLM and to keep the downstream model simple (low capacity) so that it can be reliably trained from few examples.

# Target: class likelihood estimation from engineered features
The ultimate prediction target is an estimate of the class likelihoods (class probabilities) for each input sample. FeatLLM transforms the original feature space into a set of binary features derived from the rules produced by the LLM. For each class $k\in\{1,\dots,c\}$ the LLM is prompted to produce $R$ rules (the paper uses a fixed number, e.g., $R=10$) that characterize conditions under which a sample would belong to that class. Each rule is a logical condition on one or more original features (for example, "$\text{age} > 60$ and \text{cholesterol} > 240$" or "$\text{marital\_status}$ in \{\text{single},\text{divorced}\}$").

After parsing and applying these rules to a sample $\mathbf{x}^i$, FeatLLM obtains for class $k$ a binary vector of rule-satisfaction indicators:
\[
\mathbf{z}_k^i \in \{0,1\}^R,
\]
where the $r$-th entry of $\mathbf{z}_k^i$ is 1 if and only if sample $i$ satisfies rule $r$ for class $k$.

To convert these engineered features into class probability estimates, the framework fits a simple linear model (no bias term) per class. Let $\mathbf{w}_k\in\mathbb{R}^R$ denote the trainable weight vector for class $k$. The logit for class $k$ on sample $i$ is computed as
\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,
\]
where $\max(\mathbf{w}_k, 0)$ denotes element-wise maximum to project the learned weights into a non-negative subspace. Projecting to non-negative weights enforces that satisfying a rule cannot decrease the logit for the class (i.e., features do not have negative contributions to class likelihood). The logits for all classes are combined with a softmax to produce class probabilities:
\[
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big).
\]
The model parameters $\{\mathbf{w}_k\}_{k=1}^c$ are learned by minimizing the cross-entropy loss on the available $k$ training examples (or via cross-validation within the small training set to select epochs). Because the downstream model is low capacity (linear, non-negative weights), it reduces the risk of overfitting in the few-shot regime while allowing the data to tune the relative importance of the LLM-derived rules.

The FeatLLM pipeline also employs ensemble techniques: the entire rule-generation → parsing → weighting cycle is repeated $T$ times with randomized LLM sampling (e.g., higher temperature and different example orders) and bagging (random subsets of features or instances) to produce $T$ models. The final class probability for a sample is the average of the probabilities predicted by the $T$ models, which stabilizes predictions and mitigates noisy or incorrect rules produced in individual trials.

# Assumptions: feature names and optional feature descriptions
FeatLLM assumes that each column in the tabular dataset has an associated natural-language name $f_j$ and, optionally, a textual description that clarifies the feature's meaning and type. The presence of such metadata is central to how the LLM is prompted: the prompt contains the task description, the feature names and descriptions (including value types and possible categories for categorical features), and serialized example demonstrations.

These assumptions are explicit in the prompt design. The feature descriptions help the LLM avoid type mismatches when it formulates rules (for example, it can avoid writing a rule that compares a categorical variable with a numeric threshold). When the dataset does not include detailed feature descriptions, FeatLLM still proceeds but ablation experiments in the paper show that including feature descriptions improves performance, especially in very small $k$ regimes, because the LLM can better leverage prior knowledge when the features are well described.

Another practical assumption is that the LLM is available via API-level access for inference. FeatLLM is designed to work without fine-tuning the LLM; it relies only on a modest number of API queries (one query per rule-generation trial plus queries to parse rules into executable code) rather than requiring per-sample LLM inferences at prediction time. This design choice reduces inference cost and makes the approach compatible with large LLMs that expose only inference APIs.

# Evaluation metrics overview (AUC/AUROC) and cross-validation usage
The primary evaluation metric used in the FeatLLM experiments is the area under the receiver operating characteristic curve (AUC or AUROC). AUC is a standard metric for binary (and can be adapted for multiclass via one-vs-rest averaging) classification tasks, measuring the ability of the model to rank positive instances higher than negative ones across all possible classification thresholds. In low-shot settings AUC is often preferred because it is threshold-agnostic and robust to class imbalance.

Empirical results reported in the paper present mean AUC scores (and standard deviations) across repeated trials with different random splits of training and test data. For model selection and hyper-parameter choices (for example, the number of training epochs for the linear weight tuning), the paper uses $k$-fold cross-validation on the available small training set, where $k$ is chosen (in the experimental setup) so that each fold still contains at least one example of every class. This cross-validation serves to reduce overfitting arising from running gradient-based optimization on very small datasets and to select a stopping epoch or other small-sample hyper-parameters reliably.

When reporting final results, the experiments repeat the entire process multiple times (for example, three repetitions with different training/test splits) and report the average AUC and its standard deviation to quantify variability due to sampling in the few-shot regime.

# Summary
To summarize, the problem setup treats tabular classification under few-shot constraints: a dataset with $N$ samples, $d$ named features (with optional descriptions), and $c$ classes. A small $k$-sized labeled training set is used both to demonstrate examples to an LLM and to train a low-capacity downstream model. The LLM is tasked with producing human-readable rules per class; those rules are parsed into binary rule-satisfaction features $\mathbf{z}_k^i$, and a non-negative-weight linear mapping converts those features to logits and class probabilities via softmax. Performance is measured primarily by AUROC, with cross-validation used within small training sets to mitigate overfitting and to select tuning hyper-parameters. The design choices—using feature metadata, enforcing low-capacity downstream models, and applying ensembling with bagging—are motivated by the need to be effective and robust in the $k$-shot regime while remaining compatible with LLMs accessible only through inference APIs.

FeatLLM: System Overview

# Design principle: LLM as rule/feature generator, not predictor
FeatLLM is built on a clear design principle: treat the large language model (LLM) as an expert feature engineer that produces human-interpretable rules, instead of using the LLM as a per-sample end-to-end predictor. The motivation for this design is twofold. First, LLMs encode broad prior knowledge and commonsense relationships that can be brought to bear on tabular prediction tasks; by asking the LLM to surface those relationships as rules, we explicitly capture that knowledge in a form that downstream models can use. Second, direct end-to-end prediction with LLMs requires passing every input sample through the model at inference time, which is costly, slow, and often infeasible when only API-level access is available. FeatLLM flips this pattern: the LLM is queried a limited number of times to produce rule-based features, and thereafter inference uses a lightweight model that reads only those generated features.

Conceptually, this design separates "knowledge extraction" from "statistical fitting." The LLM supplies rule templates and conditional statements that map raw input columns to binary indicators relevant to each class; these indicators are features that summarize the LLM's prior knowledge and any tendencies detectable from few-shot examples. The downstream learner then treats those binary features as inputs and estimates their importance from the labeled training samples. This separation has important practical consequences: it reduces dependence on the LLM at inference time, enables use of powerful closed-source LLM APIs (no fine-tuning required), and yields features that are interpretable and amenable to conventional ML machinery.

# Two-stage workflow: rule extraction then lightweight model fitting
FeatLLM operates in two clear stages. The first stage is rule extraction: using an in-context prompt, the LLM is asked to (a) infer how features generally relate to the target (leveraging prior knowledge), and then (b) synthesize a fixed number of decisive rules per class based on that prior knowledge plus the few-shot examples provided in the prompt. The prompt is structured into three parts: a basic information description (task description, feature names and types, and serialized few-shot examples), a reasoning instruction that splits the LLM's thought process into a prior-knowledge step and a data-driven rule derivation step, and response instructions that constrain the output format so the rules are parseable. This two-step reasoning—first general tendencies, then concrete rules—helps avoid overfitting to spurious correlations in a very small sample set by grounding rule generation in broader knowledge.

The second stage is lightweight model fitting. Once rules are generated, they are parsed and applied to the training samples to create binary rule-satisfaction features. FeatLLM trains a simple per-class linear model (without bias) over these binary features to compute class logits and probabilities. Specifically, for class $k$ and sample $i$, the LLM-derived binary feature vector is denoted $\mathbf{z}_k^i \in \{0,1\}^R$ where $R$ is the number of rules per class. The logit for class $k$ is computed as
\[
\text{logit}_k^i = \max(\mathbf{w}_k,0) \cdot \mathbf{z}_k^i,
\]
and class probabilities are obtained via softmax:
\[
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big).
\]
Only the linear weights $\{\mathbf{w}_k\}$ are trained (via cross-entropy loss and a small number of epochs with an optimizer such as Adam). Projecting weights into the non-negative subspace ensures that satisfying a rule cannot decrease a class's logit, reflecting the intuition that generated rules mark positive evidence for a class.

This two-stage pipeline has practical advantages: rule extraction relies on LLM reasoning, but the fitted model controls how much each rule matters on the observed few-shot data, enabling the system to discount rules that are irrelevant to the current dataset.

# Binary feature construction per class from rules
Rules returned by the LLM are expressed as conditional criteria that link original columns to target classes (for example, "age > 60 and chest pain = 'typical' implies higher risk"). FeatLLM transforms each such rule into a binary feature that indicates whether a given sample satisfies the rule. For a task with $c$ classes and $R$ rules per class (the paper fixes $R=10$ in experiments), the derived feature space effectively contains $c\times R$ binary features.

Because the LLM output is in natural language and can contain syntactic variation (for example, "greater than" vs. "$>$", or slight rephrasing), FeatLLM implements a parsing step to convert textual rules into executable code that evaluates the rule on tabular rows. Rather than building a brittle handcrafted parser, FeatLLM reutilizes the LLM for parsing: it supplies the inferred rules and a small function specification to the LLM and asks it to produce a simple parsing program (e.g., a Python function) that returns 0/1 for each rule when applied to a sample. The generated code is then executed (e.g., via Python's exec()) to obtain the binary feature values for all samples. This pragmatic use of the LLM leverages its strength at interpreting varied natural-language predicates without requiring fragile rule-engine construction.

Once the binary features are constructed, they serve as the sole inputs to the downstream lightweight model. A simple aggregation—counting how many rules of a class are satisfied—could be used as a logit proxy, but FeatLLM improves upon that by learning weights for each rule, so features are combined with learned importance rather than equal weighting.

# No training of the LLM; only API-level usage
A central practical constraint driving FeatLLM's design is the limited access to many highquality LLMs: some state-of-the-art models provide only inference APIs and do not permit parameter-efficient fine-tuning or access to training code. FeatLLM is explicitly designed to work under those constraints. The system treats the LLM as a black-box oracle for in-context generation and parsing; it never fine-tunes the LLM parameters.

This API-only approach means rule extraction and parsing require only a small number of LLM queries. In the experimental setup reported, each ensemble trial used a single query to generate rules and another to parse rules into code, and across trials the total API usage remains modest (e.g., the paper reports around 30 API queries in total). Because the LLM is not re-trained or adapted, FeatLLM retains portability across different models and avoids the engineering and cost burden associated with parameter-efficient tuning. It also means FeatLLM can be immediately applied to closed-source, high-performance LLMs that only expose inference endpoints.

# Decoupling inference from the LLM to lower latency and cost
One of FeatLLM's most important operational benefits is that, after rule extraction and parsing, no LLM calls are required for per-sample inference. Predictions on new samples are made by evaluating the parsed rule-logic (which is plain program code operating on tabular values) to produce binary features and then running the lightweight trained model (a linear layer and softmax). This decoupling reduces both latency and monetary cost relative to approaches that require an LLM to process each test example through a long serialized prompt.

In practice, the heavy-cost operations (LLM queries) are front-loaded and can be executed offline or in batch. The final deployed predictor is a simple deterministic program plus a small linear model; its inference time is comparable to standard tabular methods such as logistic regression or gradient-boosted trees. The paper's experiments confirm this: FeatLLM has low inference time similar to conventional learners, while other LLM-based baselines that run the LLM per-sample have substantially higher inference latency and cost. This architectural choice therefore makes FeatLLM suitable for real-world scenarios where rapid, repeated predictions are required and where LLM API calls per sample are impractical.

# Mitigating prompt-size issues via bagging and ensembling
LLMs have finite context windows, and when tabular datasets contain many features or when many few-shot examples must be serialized, prompt length can become a limiting factor. FeatLLM addresses this in two complementary ways: feature/instance bagging and ensembling.

In each trial of the ensemble, FeatLLM performs rule extraction using only a random subset of the dataset's features and/or training instances. This bagging reduces the prompt size per LLM query, allowing the system to operate even when the full dataset description would exceed the LLM's input limits. The LLM is therefore only asked to consider a manageable subset of features at a time, and it generates rules that are targeted to that subset.

Because each trial only sees a portion of the feature space, FeatLLM repeats the process multiple times (the paper uses on the order of $T=20$ trials) with randomized temperature and shuffled demonstration order to encourage diversity of the generated rule sets. Each trial produces a weight vector $\mathbf{w}[t]$ after fitting the lightweight model on its generated features. Final predictions are formed by averaging the class probability vectors across the ensemble:
\[
\overline{\mathbf{p}}^i = \frac{1}{T}\sum_{t=1}^T \mathbf{p}^i(\mathbf{w}[t]).
\]
This ensembling strategy accomplishes three goals simultaneously. First, it aggregates complementary pieces of information that individual trials capture, improving robustness and overall predictive performance. Second, it mitigates the risk that any single trial's LLM output contains incorrect or spurious rules—errors are diluted when many trials are averaged. Third, it ensures that the system scales to high-dimensional tabular problems by partitioning feature attention across trials, rather than overwhelming the LLM's prompt with all columns at once.

Together, bagging and ensembling let FeatLLM balance the LLM's prompt-size constraints against the need to cover a large or heterogeneous set of attributes, while preserving the low inference cost advantage by only requiring the LLM during the ensemble's generation stage (not per-sample prediction).

Prompting for Rule Extraction

# Basic information description: task question, labels, feature types/descriptions, serialized few-shot examples
The first component of FeatLLM's prompt provides the LLM with all essential, grounded information required to reason about the tabular prediction task. This section is written to look and behave like the problem statement an expert analyst would read: a concise task question, explicit label definitions, and clear descriptions of each column (feature). The task question is expressed in natural language as a concrete yes/no or multiclass question (for example, "Does this patient's myocardial infarction complications data indicate chronic heart failure? Yes or no?") so the model has a target-oriented framing for downstream rule extraction. The label definitions enumerate the possible classes and, when helpful, short clarifications of what each label means in the task context.

Feature descriptions are equally explicit. For every column we give (a) the feature name as natural language text, (b) the feature type (numeric, categorical, boolean, etc.), and (c) optionally a short definition or allowed category values for categorical features. The presence of type information is important: it constrains which syntactic forms of rules the LLM should produce (for example, inequalities for numeric features and membership tests for categorical ones), and it reduces the risk of creating syntactically invalid or semantically meaningless conditions. In datasets with many possible categories, listing representative categories or the full domain (when feasible) prevents the model from inventing categories that do not exist.

This basic information block also contains the few-shot example demonstrations. Each demonstration is a serialized training sample paired with its ground-truth label; demonstrations are chosen from the available k-shot training set. These examples expose the LLM to concrete input-output mappings and let it ground its general priors in the specific statistical patterns present in the target dataset. The basic-information block is therefore a hybrid: it supplies general task semantics and detailed feature typing, and it injects a small number of concrete examples so the LLM can coordinate prior knowledge with observed instances.

# Serialization format for examples and labels
FeatLLM employs a simple, uniform serialization format to convert a tabular sample and its label into text for the prompt. For a d-dimensional input vector \mathbf{x}^i and corresponding label \mathbf{y}^i, the serialization is defined in the paper as:

"\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = 
\ ``\ f_1\ \text{is}\ \mathbf{x}^i_1.\ ... \ f_d\  \text{is}\  \mathbf{x}^i_d.\ \ \text{Answer:}\  \mathbf{y}^i\ ”"

This format lists every feature name f_j followed by the observed value \mathbf{x}^i_j, ending with "Answer: <label>". The serial form mirrors prior LLM-tabular work and is deliberately simple to keep prompts predictable. Importantly, this serialization retains the feature names F = \{f_j\}_{j=1}^{d} in natural language, which links the numeric or categorical values to semantic descriptions the LLM can exploit from its pretraining. Using a consistent serialized example format aids both the LLM's pattern recognition and subsequent automatic parsing of the LLM's recommendations.

When constructing the few-shot block, FeatLLM typically includes k examples where k is small (e.g., k=4 or k=8) to match the low-shot learning regime. The example order is randomized across ensemble trials because example ordering can influence LLM outputs; this randomness is later used to generate diverse rule sets for ensembling.

# Reasoning instruction: two-step process
To guide the LLM toward producing causally meaningful, parsable rules rather than superficial correlations, the prompt includes an explicit reasoning instruction that splits the inference into two sequential steps. The intention is to mimic an expert analyst's workflow: first surface relevant domain priors and tendencies without being anchored to specific examples, then reconcile those priors with the observed few-shot cases to produce concrete, decisive rules.

The reasoning instruction begins with an opening that encourages chain-of-thought style reasoning, prompting the LLM to consider causal tendencies and feature relevance explicitly. The two-step structure is enforced in the prompt text so the LLM is told to separate its answers into a Step 1 and Step 2. By dividing the process, FeatLLM reduces the risk that the model will latch onto spurious correlations visible only in the few-shot examples and instead promotes the reuse of broad, transferable domain knowledge.

Concretely, the first step asks the LLM to reflect on general associations between the task and features given their descriptions—without consulting the example demonstrations. The second step then asks the LLM to propose concrete rules that use both the priors surfaced in Step 1 and the few-shot exemplars. This sequencing biases the LLM to favor features that a priori make sense for the task, and then to convert those into rules consistent with the small in-context dataset.

# Step 1: Prior-knowledge reasoning without examples to surface domain priors
Step 1 is: "Given only the task description and the feature definitions (do not look at the examples), what features do you expect to be related to the label, and in which direction or manner?" The LLM is explicitly prohibited from consulting the serialized examples at this stage. This prohibition is purposeful: it forces the model to retrieve and articulate priors stored in its pretraining—medical knowledge, domain correlations, monotonic tendencies, and so on—rather than overfitting to idiosyncratic patterns present in the few examples.

By surfacing these priors first, the LLM creates a shortlist of promising feature candidates and expected relationships (for instance, "age likely increases disease risk", or "high blood-glucose is associated with diabetes"). These surfaced tendencies serve two functions. First, they anchor Step 2 so that the LLM will search for rules that align with domain-relevant features rather than arbitrary correlates. Second, they provide a natural filter: features not mentioned in Step 1 are implicitly deemphasized in Step 2, reducing the chance of producing rules derived purely from noise or spurious correlations present only in the few-shot examples.

This approach leverages one of the strengths of LLMs: stored world knowledge and commonsense associations learned during pretraining. Because Step 1 is run inside the same prompt, the LLM can integrate those priors smoothly into the next stage without any external model components.

# Step 2: Rule deduction using examples plus priors to avoid spurious features
Step 2 instructs the LLM to use both the priors identified in Step 1 and the serialized few-shot examples to deduce decisive, testable rules for each class. In this phase the model is allowed and expected to examine the examples: to find concrete value ranges, category memberships, or combinations that match the target labels while being consistent with the domain priors. The two-step separation leads to rules that are both interpretable (derived from priors) and empirically grounded (consistent with examples).

The Step 2 instruction explicitly asks for rules that are concise and decisive: they should be conditions that can be applied to a new sample and yield a binary outcome of rule satisfaction. For numerical features, the LLM is guided to produce inequalities or value ranges; for categorical features, membership tests or specific categorical values; for boolean flags, direct checks. The LLM is guided to prefer single-feature conditions where possible and to combine features with logical operators like AND/OR only when necessary to produce a decisive rule.

The combination of priors and examples helps prevent the LLM from extracting spurious features. If a feature shows an accidental correlation in the examples but contradicts the high-level domain prior from Step 1, the LLM is encouraged to treat that correlation with caution and avoid making it a standalone rule. Conversely, when a prior suggests a relationship and the examples corroborate it, Step 2 will concretize that into an explicit condition.

# Response instruction: constrained output format and rule templates
To ensure that the rules the LLM emits are parsable and directly usable, the prompt includes a structured response instruction that specifies a precise output format and rule templates. The response instruction prescribes how many rules to generate per class, how to enumerate them, and the syntactic shape each rule should take. The goal is to make the LLM produce output that can be reliably parsed (or, when small syntactic variation occurs, re-parsed by a subsequent LLM-assisted parser) into executable checks.

The response format enforces a short header per class and then a numbered list of rules. Each rule is requested to follow a template according to the feature type. For example:
- Numeric rule template: "<feature> is <comparison> <value>" or "<feature> in [<low>, <high>]"
- Categorical rule template: "<feature> == <category>" or "<feature> in {<cat1>,<cat2>}"
- Boolean rule template: "<feature> is True" or "<feature> is False"

In practice the LLM will sometimes use synonyms (e.g., "greater than" instead of the symbol ">"). The response instruction therefore also requests syntactic consistency, but FeatLLM anticipates minor variants and remedies them at parsing time (see paper's parsing stage). Crucially, the response instruction sets a strict, machine-friendly structure: numbered rules, class headings, and rule templates. This constrained form drastically reduces the difficulty of converting the natural language rules into binary features indicating rule satisfaction.

# Choosing the number of rules per class (default 10) and trade-offs
FeatLLM fixes the number of rules per class to a modest, predefined number; the paper uses a default R=10 rules per class. This limit is a pragmatic trade-off between expressiveness and tractability. On one hand, asking the LLM to produce many rules per class increases the probability of covering diverse patterns and capturing complex decision boundaries; it also increases the dimensionality of the rule-based feature space, which may be beneficial if the downstream learner can exploit many weak signals. On the other hand, too many rules inflate the prompt length (if rules are also shown or validated in subsequent steps), raise the chance of including low-quality or redundant rules, and enlarge the input dimensionality for the downstream tuning process, which in few-shot regimes may promote overfitting.

Constraining to R=10 is a design point the paper found to balance these concerns: it provides enough capacity for expressivity while keeping prompts and the resulting binary feature set manageable. Empirically, the paper's hyper-parameter analysis indicated no statistically significant gains from substantially increasing R beyond 10 in low-shot scenarios; instead, adding more rules tended to increase input dimensionality without reliable performance improvements. The fixed-count design also simplifies ensembling and bagging: every trial produces a predictable number of candidate features per class, facilitating consistent weight training and aggregation.

Practically, one should view the number of rules per class as a tunable hyper-parameter. In extremely low-dimensional problems or when domain knowledge suggests simple thresholds suffice, a smaller R may be adequate. In heterogeneous tasks where several independent signals exist, a somewhat larger R can help, but the downstream weight-tuning and ensembling stages are the primary guards against overfitting.

# Preventing type mismatches and promoting concise, decisive conditions
Several mechanisms in the prompt design reduce the chance the LLM will produce rules that are type-incoherent or syntactically unusable. First, the basic information block explicitly states the feature type for each column. The reasoning and response instructions then refer back to those types: the LLM is told to prefer inequality-based templates for numeric features, membership tests for categorical features, and boolean checks for binary flags. This reference constrains the forms the LLM should employ and reduces mismatches like asking whether "age is 'male'" for a numeric "age" feature.

Second, the response templates reinforce type-appropriate syntax. By supplying example rule templates in the prompt, the LLM is more likely to follow them, producing rules that can be directly parsed into code or into a structured representation. If the LLM uses synonyms or differing punctuation (e.g., "greater than" vs. ">"), the subsequent parsing stage in FeatLLM is designed to handle those predictable variants. The parsing uses the LLM again to translate natural-language rules into executable code snippets, leveraging the LLM's robustness to linguistic variability rather than building brittle hand-written parsers.

Third, the prompt emphasizes concision and decisiveness. Rules are requested to be as simple as possible: single-feature thresholds or categorical membership checks unless a multi-feature combination is truly necessary. This preference for simplicity increases interpretability, keeps the generated binary features meaningful, and makes the downstream linear weight-tuning step more effective given few training examples. Concise rules are easier to validate across ensemble trials: rules that recur across runs are more likely to be genuine signals.

Finally, the prompt caps the number of rules per class and asks for exactly that many, which avoids ambiguous open-ended outputs that could mix explanatory text with rules. Combined, these measures reduce type errors, encourage machine-parsable output, and promote production of concise, decisive conditions that can be reliably applied to new samples without any per-sample LLM inference.

# Summary
FeatLLM's prompt architecture intentionally scaffolds LLM reasoning to extract high-quality, parsable rules. The basic information block supplies a focused task question, label definitions, and typed feature descriptions alongside serialized few-shot examples. A two-step reasoning instruction forces the model to first articulate prior knowledge without examples and then to derive concrete rules grounded in both priors and exemplars. A constrained response instruction, with type-specific templates and a fixed number of rules per class (default R=10), yields concise rules that are amenable to parsing into executable checks. These design choices collectively balance the need for expressive, causally relevant features with the practical constraints of prompt length, parseability, and few-shot robustness.

From Natural Language Rules to Computable Features

# Parsing challenges: syntax variability and ambiguity in natural language
When an LLM is prompted to produce decision criteria or "rules" in natural language, the output can be rich in semantics but inconsistent in syntax. The FeatLLM paper highlights concrete examples of this variability: an LLM may express the same comparison as the symbol "$>$" or as the phrase "greater than," it may reorder clauses, or it may include optional clarifying text. Even with constrained response formats, subtle syntactic noise remains common. This variability creates two core parsing challenges.

First, syntactic variability undermines deterministic string-based parsers. A parser that expects an exact lexical form (for example, the precise token "$>$") will fail when the LLM writes "greater than" or "is larger than". Natural language allows optional articles, parentheses, units, and synonyms that change the token stream while preserving meaning. Second, ambiguity arises when a generated rule mixes concepts, uses implicit references (e.g., "this value" without an explicit feature name), or uses logical combinations (AND/OR) in nested forms. Such ambiguity makes it difficult to map rule text unambiguously to a simple predicate that can be evaluated on a tabular row.

These difficulties are particularly important in the FeatLLM setting because the downstream pipeline relies on automatically converting rules into binary features. Parsing failures produce malformed predicates that either crash a conversion step or, worse, silently produce incorrect features. The paper therefore treats parsing as a crucial step: instead of attempting to predefine brittle grammatical patterns, FeatLLM accepts that LLM outputs will contain syntactic variation and builds the parsing stage to be robust to it.

# LLM-assisted code generation for parsing: function signatures, I/O specs, and safety checks
FeatLLM addresses parsing variability by delegating much of the parsing burden back to an LLM that is itself good at interpreting semantically equivalent phrasings. Rather than hand-coding a complex natural language parser that must enumerate lexical variations, the pipeline prompts an LLM to produce executable code that implements the intended predicate evaluations.

Concretely, the prompt for the parsing step contains (1) a function name, (2) explicit descriptions of the function's inputs and outputs, and (3) the list of inferred natural-language rules. By supplying this minimal API-level specification, the LLM is guided to emit code that takes structured inputs (for example, a dictionary or a row vector and feature metadata) and returns a deterministic output (for example, a list or array of binary indicators). Because the prompt enforces an input/output (I/O) contract, the LLM is steered toward producing code that can be executed programmatically.

Two practical design choices in this approach are worth emphasizing. First, the I/O contract reduces ambiguity: the LLM must map natural language rules into expressions that use the provided feature names and data types. When the prompt includes feature types (categorical, continuous) and canonical names, the LLM is less likely to generate type-mismatched expressions. Second, providing the desired return shape (for example, an array of length $R$ for $R$ rules) reduces the chance that the LLM will emit prose instead of code. The FeatLLM authors found that leveraging the LLM to generate simple code is effective because the model is already trained on code and can translate variable natural-language phrasings into logically equivalent programmatic tests.

In addition to function signatures and I/O, the prompt can include minimal safety checks and parsing guidance: request that the generated function validate input types, handle common synonyms (e.g., map "greater than" to the "$>$" operator), and return clear error codes or default values when a rule cannot be interpreted. These requirements make the generated code itself more robust to irregular outputs from the rule-generating stage.

# Executing generated code securely (e.g., sandbox considerations) and verifying outputs
The FeatLLM paper implements the execution of generated parsing code using Python's exec() function. This is an effective, lightweight mechanism to materialize and run code created by an LLM. However, executing arbitrary generated code carries obvious risks: syntactic errors can raise exceptions, and malicious or simply mistaken code could have unintended side effects if executed in an unrestricted environment.

In the FeatLLM implementation the generated code is executed to perform the data conversion from rules into binary features. Because the paper focuses on practicality and shows that this approach works across many datasets, the authors emphasize programmatic verification of the outputs after execution. Two verification steps are implied by the paper's methodology:

1) Syntax and runtime validation. After running the generated function, the pipeline checks that the function returned the expected output shape (for example, an array of length $R$ with values in $\{0,1\}$ for $R$ rules). If execution raises syntax or runtime errors, that trial is either retried (possibly with a different LLM sample) or discarded as malformed.

2) Semantic sanity checks. The pipeline inspects the generated binary features for basic statistical sanity: features should be binary, should not be constant across the dataset (all zeros or all ones), and should have some nontrivial association with the target across the few labeled samples. The FeatLLM paper uses downstream model tuning and thresholding (see the Quality Control section) which further rejects irrelevant or spurious features.

While the paper describes using exec() directly, it also implicitly motivates careful runtime checks before accepting generated code outputs. In practice one would run generated code in an isolated or restricted environment, validate its outputs, and only then allow these features into the training pipeline. The FeatLLM results show that this approach—generate code with an LLM, execute it, then validate outputs—is sufficient to extract high-quality features for few-shot tabular learning when combined with downstream filtering and ensembling.

# Binary feature construction per class: rule satisfaction indicators
Once parsing succeeds, each rule is converted into a deterministic predicate that can be evaluated on every sample in the dataset. FeatLLM constructs binary features from these predicates: for class $k$ and rule $r$ the generated feature for sample $i$ is a bit indicating whether sample $\mathbf{x}^i$ satisfies rule $r$ associated with class $k$. The paper denotes the per-class rule feature vector for sample $i$ as $\mathbf{z}_k^i \in \{0,1\}^R$, where $R$ is the number of rules per class.

These binary indicators are the only features used by the downstream, low-complexity predictive model. The choice of binary features has several advantages in the FeatLLM design. First, they are interpretable: each active bit corresponds to a concrete, human-readable rule. Second, they are model-agnostic: once produced, any classical ML method can be applied, but FeatLLM focuses on a simple linear model (without bias) to estimate class logits. The linear model computes a logit for class $k$ as a weighted sum of its binary rule indicators:

logit_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,

and then class probabilities are obtained with a softmax across classes:

\mathbf{p}^i = \text{Softmax}([ \text{logit}_1^i, \dots, \text{logit}_c^i ]).

The projection $\max(\mathbf{w}_k, 0)$ enforces non-negativity on the learned weights, ensuring that satisfying a rule does not reduce the likelihood of the associated class. Learning the weights $\mathbf{w}_k$ on the few labeled samples lets the pipeline calibrate which rules are predictive and how strongly they should influence class likelihood. This step converts the set of potentially noisy and overlapping rule indicators into a compact, weighted signal suitable for few-shot training.

# Quality control: detecting malformed rules and fallback strategies
The FeatLLM paper adopts several strategies to detect and mitigate malformed or unhelpful rules and to ensure robustness of the generated features.

First, constraining the rule-generation prompt reduces gross malformations. The prompt enforces a fixed response format, requests a fixed number of rules per class (the authors typically use $R=10$), and supplies feature type information so the LLM is less likely to produce type errors. Even with these constraints, some rules remain noisy; the paper acknowledges that syntactic changes and variation still occur.

Second, the pipeline uses the LLM itself to parse natural language rules into code, letting a model trained on code normalize common linguistic variants. This two-stage LLM usage—one LLM to propose rules, another to translate them into executable predicates—reduces parsing failures relative to a handcrafted parser.

Third, FeatLLM employs downstream statistical filtering during the weight-tuning phase. After generating the binary rule features and fitting the linear model with cross-entropy loss, the learned non-negative weights $\mathbf{w}_k$ implicitly rank features by usefulness. The authors report computing histograms of learned weights and applying a small threshold (they use 0.1 in experiments) to identify and effectively discard rules that receive negligible weight. Table analyses in the paper show that the fraction of rule-features with AUROC $>0.5$ increases after tuning, indicating that tuning functions as an effective filter.

Fourth, ensembling with bagging provides a robust fallback when individual trials generate malformed or unhelpful rules. FeatLLM repeats the entire rule-generation, parsing, and tuning pipeline $T$ times (the paper uses $T=20$), randomizing few-shot example order and performing feature/instance bagging across trials. Because the ensemble averages class probabilities produced by each trial, trials with many malformed rules have limited influence on the final prediction. Moreover, rules that are repeatedly inferred across trials receive consistent positive weights and thus have greater net influence; this self-consistency property helps prioritize correct rules.

Finally, pragmatic runtime safeguards are used during code execution: the pipeline validates the function's return shape and that outputs are binary. If produced code fails these checks (exceptions, wrong shapes, non-binary outputs), the trial can be retried or excluded from the ensemble. While the paper does not enumerate every possible fallback, it demonstrates a pragmatic set of checks and a post-parsing filtering mechanism (weight thresholding plus ensembling) that together make the system robust to malformed rules.

# Summary
FeatLLM converts LLM-generated natural-language rules into reliable, computable binary features by recognizing and addressing parsing variability, employing the LLM itself to generate parsing code under clear function/I/O constraints, executing and validating that code (using exec() in the implementation), and then constructing per-class binary rule indicators $\mathbf{z}_k^i$ for downstream prediction. Quality control is enforced via prompt constraints, post-parsing validation, weight-based filtering after tuning (e.g., thresholding learned non-negative weights), and ensembling with bagging to dilute the impact of malformed trials. Together these design choices enable FeatLLM to turn informal, variable natural-language rules into robust, interpretable features suitable for few-shot tabular learning.

Estimating Class Likelihoods with Simple Models

# Feature representation: z_k as binary indicators for class k
In the FeatLLM framework, the raw tabular inputs are transformed into a set of rule-based binary features that are designed to capture whether a sample satisfies certain class-specific criteria inferred by a large language model (LLM). For a particular class $k$, the new feature vector for sample $i$ is denoted as $\mathbf{z}_k^i \in \{0,1\}^R$, where $R$ is the fixed number of rules generated per class. Each coordinate of $\mathbf{z}_k^i$ corresponds to one rule for class $k$ and takes the value $1$ if the sample satisfies that rule and $0$ otherwise.

This representation has two useful properties. First, it is highly interpretable: each dimension can be read as a human-understandable condition (a rule) that the LLM proposed as indicative of class $k$. Second, binarization simplifies downstream modeling because we can reason directly about counts and combinations of satisfied rules. In practice, rules are parsed (via an auxiliary LLM prompt that outputs simple executable code) and applied to the tabular dataset to produce these binary indicators automatically. The binary vectors $\{\mathbf{z}_k^i\}$ for all classes become the input features used by the simple downstream model to estimate class likelihoods.

# Linear logits with non-negative weights: interpretability and monotonicity rationale
To convert these binary rule indicators into a score (logit) for each class, FeatLLM uses a linear model per class. Let $\mathbf{w}_k \in \mathbb{R}^R$ be the trainable weight vector associated with the $R$ rules for class $k$. The model computes the class logit for sample $i$ by taking a non-negative projection of the weights and forming an inner product with the binary indicators:
\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i.
\]
The $\max(\cdot,0)$ operation is applied elementwise and ensures all effective weights used in the dot product are non-negative.

There are two key motivations behind forcing weights into the non-negative subspace. First, interpretability: a non-negative weight indicates how strongly satisfying a given rule increases the logit (and thus the probability) for class $k$. Positive weights are directly readable as rule importance scores; zero weights mean a rule has no positive contribution. Second, a monotonicity rationale: because rules were generated by an LLM as criteria suggestive of a class, it is natural to treat satisfaction of such a rule as evidence in favor of that class. Forcing weights to be non-negative prevents the learned model from treating an LLM-proposed rule as negatively indicative of the same class, which aligns model behavior with the intended semantics of the extracted rules.

# Softmax over class logits and cross-entropy training
After computing logits for each class, the model converts logits into probabilities using the softmax function across classes. For a sample $i$ with class logits $\{\text{logit}_{1}^i,\dots,\text{logit}_{c}^i\}$, the class probability vector $\mathbf{p}^i$ is given by
\[
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_{1}^i, \dots, \text{logit}_{c}^i]\big),
\]
so that $p_k^i = \frac{\exp(\text{logit}_k^i)}{\sum_{j=1}^c \exp(\text{logit}_j^i)}$.

Learning proceeds by minimizing the standard cross-entropy loss between these predicted probabilities and the one-hot encoded ground-truth labels over the available few-shot training samples. Because the downstream classifier is linear in the binary rule features (after the non-negativity projection), optimization is simple and efficient. Minimizing cross-entropy adjusts the weight magnitudes so that combinations of rules better align predicted probabilities with the observed labels in the few-shot set.

# Why weight tuning matters vs simple rule counts
A naive way to combine binary rule indicators into a score is simply to count the number of satisfied rules for each class and use those counts as logits. That corresponds to treating each rule as equally informative (unit weight) and ignoring any differences in rule quality. While this approach can work as a rough indicator, FeatLLM shows that learning weights from data yields substantial improvements, especially as more labeled examples become available.

Tuning the weights allows the model to modulate the contribution of each rule: strongly predictive rules receive higher weights, while noisy or irrelevant rules receive near-zero weights and are effectively ignored. The paper's ablation study demonstrates that omitting the tuning step (i.e., using raw counts) degrades performance, and the benefit of tuning increases with the number of shots. This is because with more labeled examples the learner can estimate rule importance more reliably; conversely, in very low-shot settings, prior knowledge embedded in the rules is already valuable, but learned weighting still helps filter or emphasize rules consistent with the observed labels.

# Training details: optimizer choice, learning rate, epochs, and early stopping via k-fold CV
The downstream linear models in FeatLLM are trained with straightforward settings suitable for few-shot learning. The reported implementation uses the Adam optimizer with a learning rate of $0.01$. Training runs for a fixed number of epochs (200 epochs in the experiments). To avoid overfitting and to select an appropriate stopping point in the few-shot regime, k-fold cross-validation is used to determine the optimal epoch. Concretely, k-fold cross-validation is applied over the few-shot training set: the training process is monitored across folds and the epoch that generalizes best on validation folds is selected. This procedure provides an implicit early-stopping mechanism tailored to the extremely limited-data setting.

Because the downstream model is small and convex in the weights before the non-negativity projection, training is computationally light. The paper notes that these training runs are cheap relative to per-sample LLM inferences, and only a modest number of LLM queries (e.g., one per ensemble trial) are required during the overall FeatLLM procedure.

# Interpreting learned weights as rule importance
Once trained, the learned (non-negative) weights $\max(\mathbf{w}_k,0)$ serve as direct measures of each rule's importance for predicting class $k$. A higher weight for a particular rule means that when that rule is satisfied for a sample, it has a larger positive impact on the logit and therefore increases the predicted probability of class $k$ more strongly. Weights near zero indicate rules that the learning process found uninformative or inconsistent with the labeled examples; such rules can effectively be treated as filtered-out or pruned.

This interpretability enables several practical uses. First, practitioners can inspect which LLM-generated rules are actually being trusted by the data-driven learner and which are being downweighted. The paper uses a threshold (e.g., weight threshold 0.1 in the analysis) to quantify how many rules remain useful after tuning. Second, because weights are non-negative and additive in the logit space, the model provides a monotone, easily explainable mapping from satisfied rules to class evidence. Finally, in the ensemble setting FeatLLM repeats rule generation and weight learning across multiple randomized trials; rules that consistently receive high weights across trials are more likely to be genuinely informative, and the ensemble averaging of probabilities further stabilizes predictions.

Together, these design choices—binary, rule-based features, non-negative linear aggregation, softmax normalization, and cross-entropy training with simple optimization and validation—yield a lean, interpretable, and effective mechanism for converting LLM-extracted rules into calibrated class likelihoods in few-shot tabular learning.

Ensembling and Bagging for Robustness and Scalability

# Generating diverse rule sets: LLM temperature and example order randomization
A central ingredient of FeatLLM's robustness is that it does not rely on a single deterministic set of rules produced by the LLM. Instead, it intentionally induces variability in the rule-generation process so that multiple, slightly different rule sets can be produced and then combined. Two simple but effective sources of randomness are used to create this diversity.

The first is the LLM sampling temperature. When the LLM is queried to produce rules, setting a higher temperature increases the model's entropy: it is more willing to produce alternative phrasings, choose different thresholds, and combine features in different ways. In FeatLLM experiments the temperature is set to a non-zero value (for example 0.5) during ensemble runs so that each call can yield a different collection of candidate rules even when the prompt structure is held constant. This diversity in candidate rules helps the pipeline explore multiple plausible heuristics that connect features to labels.

The second source of randomness is the order of few-shot demonstrations included in the prompt. The LLM’s in-context behavior is sensitive to the sequence of examples; changing that order can alter which aspects of the examples the model attends to and thus which rules it proposes. FeatLLM exploits this sensitivity by randomizing demonstration order across trials. Together with temperature sampling, randomizing example order produces a rich set of rule outputs that vary in both content and emphasis, giving the later ensemble multiple independent views of how features may relate to the target.

# Instance and feature bagging to reduce prompt length and variance
Tabular datasets can have many columns and, in low-shot settings, feeding all columns and all few-shot examples into an LLM can exceed prompt size limits or degrade performance. FeatLLM addresses this by applying a bagging strategy to the inputs to each rule-generation trial. Two complementary bagging schemes are used: instance bagging and feature bagging.

Feature bagging selects a subset of columns (features) to include in the prompt for a given trial. By restricting the prompt to a smaller random subset, each LLM call remains compact and within token constraints, enabling FeatLLM to scale to tables with dozens or hundreds of attributes. Feature bagging also has a variance-reduction benefit: each trial effectively searches for rules in a different subspace of the original feature space, making it less likely that a single, spurious column will dominate the full system. Over many trials the ensemble covers the column space more broadly than any single prompt could without breaking token limits.

Instance bagging chooses a random subset of the available few-shot examples to serialize into the prompt for that trial. This reduces prompt length and introduces additional randomness — each trial sees different exemplars and therefore may favor different rule patterns. Instance bagging also stabilizes the downstream learned weights because training each trial's linear model on a slightly different view helps prevent overfitting to idiosyncrasies of particular examples.

Because each trial uses a smaller prompt (fewer features and/or fewer instances), FeatLLM avoids the practical constraint of long prompts while building an ensemble whose aggregate coverage approximates a larger, infeasible single-prompt exploration. The bagging approach thus simultaneously addresses scalability (prompt size limits) and variance (reducing sensitivity to spurious correlations present in any single small prompt).

# Averaging class probabilities across trials
Once each trial has produced a set of parsed rules and those rules are converted into binary features, FeatLLM fits a simple, non-negative-weight linear model per class to map the rule features to class logits. Let the trained weight vector for trial $t$ and class $k$ be $\mathbf{w}_k[t]$ and let the binary rule-feature vector for sample $i$ be $\mathbf{z}_k^i[t]$. The trial-specific logit is computed as

\[
\text{logit}_{k}^i[t] = \max(\mathbf{w}_k[t],0)\cdot \mathbf{z}_k^i[t],
\]

and the corresponding trial-level class probabilities use the softmax over classes. FeatLLM forms the final prediction by averaging these trial-level probabilities across $T$ independently generated trials. Concretely, for sample $i$ and class $k$,

\[
\mathbf{p}_k^i = \frac{1}{T}\sum_{t=1}^T \text{Softmax}_k\big(\{\text{logit}_{j}^i[t]\}_{j=1}^c\big).
\]

Averaging probabilities (rather than averaging logits or voting) is a simple, well-behaved aggregation: each trial contributes a calibrated soft estimate of class likelihood. Because each trial is trained independently on its own generated features, averaging reduces the influence of trials that produced poor or noisy rule sets and amplifies consensus among trials that consistently place probability mass on the same class.

# Self-consistency intuition: common rules across trials likely being reliable
The ensemble construction in FeatLLM leverages a self-consistency intuition: when an LLM is asked multiple times (with different random seeds and example orders) about the same task, rules or patterns that recur across many trials are more likely to be meaningful and germane to the true input–label relationship. Conversely, idiosyncratic rules that appear only in a few trials are more likely to reflect sampling noise, prompt artifacts, or spurious correlations in the few-shot exemplars.

Practically, self-consistency manifests in two ways inside FeatLLM. First, when the same or similar rule is proposed across many trials, that binary feature will be present in multiple trials and thus have repeated opportunities to be weighted highly by the corresponding linear models. In the averaging step, these consistent signals contribute coherently to the final probability. Second, trials that produce many low-quality rules will tend to assign low weights to those features during the per-trial tuning step; when these trials are averaged together with higher-quality trials, their negative impact is diluted.

This self-consistency effect is closely tied to the ensemble size: as more independent trials are sampled, recurring, true rules are more likely to appear multiple times by chance, while spurious rules remain rare. Thus the ensemble filters noisy LLM outputs implicitly without requiring a separate rule-validation mechanism.

# Trade-offs: ensemble size vs computation and diminishing returns
While ensembling and bagging bring concrete benefits in robustness, they introduce computation and API-query cost trade-offs that must be balanced. Each additional trial requires at least one LLM query to generate rules and a small amount of downstream computation to parse rules and fit the lightweight linear models. In FeatLLM experiments the authors used on the order of $T=20$ trials and observed that performance improves with $T$ but begins to plateau: accuracy gains diminish beyond a certain ensemble size. This empirical diminishing-return behavior is common in ensemble methods and reflects the fact that once most reliable rules have been discovered in multiple trials, additional trials primarily re-discover existing rules rather than adding new informative ones.

From a systems perspective, the ensemble size should be chosen to balance desired performance versus API and runtime budget. Smaller $T$ reduces cost and latency but risks missing some helpful rules or leaving more variance in the final predictor. Larger $T$ increases robustness and coverage of the feature space but yields greater query and parsing overhead. The bagging strategy partly mitigates this: by varying feature subsets and example subsets per trial, FeatLLM can achieve broad coverage even with a modest $T$, because each trial contributes a different slice of the column and instance space.

Finally, there is a trade-off in the number of rules extracted per trial. Asking the LLM for too many rules increases prompt complexity and downstream feature dimensionality, which in very low-shot regimes can lead to overfitting; asking for too few may under-express the predictive patterns. Empirically FeatLLM fixed a moderate number (e.g., 10 rules per class) as a practical compromise between prompt length and representation capacity.

In summary, ensembling with randomized LLM sampling and bagging of features and instances provides FeatLLM with a practical mechanism to scale to long tables, reduce sensitivity to spurious correlations, and amplify reliable heuristics via self-consistency. The practitioner must, however, tune ensemble size and per-trial prompt scope to trade off numerical performance against API cost and latency, mindful that beyond a moderate number of trials returns tend to diminish.

Experimental Setup

# Datasets
The evaluation of FeatLLM covers a diverse collection of thirteen tabular datasets chosen to represent a range of domains, difficulty levels, feature dimensionalities, and likelihoods of being seen during LLM pretraining. The datasets fall into four groups.

First, a set of commonly used UCI and benchmark tabular datasets (referred to below as “UCI classics”) are included: Adult (predict whether an individual earns over \$50,000), Bank (predict whether a customer will subscribe to a term deposit), Blood (predict whether donors will return), Car (predict car quality), Communities (predict crime rate in a region), and Credit-g (predict whether an individual is a good or bad credit risk). These datasets vary in the number of features and complexity; some such as Communities have over 100 attributes and thus stress prompt-size limitations.

Second, a group of health-focused datasets is used to evaluate performance in sensitive, real-world prediction problems: Diabetes (predict presence of diabetes), Heart (predict occurrence of coronary artery disease), and Myocardial (predict chronic heart failure). These datasets were selected both for domain relevance and because clinical prior knowledge encoded in LLMs can be especially useful for few-shot learning.

Third, two more recent UCI datasets—Cultivars (predict grain-yield level of a soybean cultivar) and NHANES (predict age group from a person’s record)—are included. These datasets were donated to the UCI repository after September 2023 and are explicitly chosen to reduce the likelihood that their data or attributes were included during LLM pretraining.

Finally, two synthetic datasets were constructed to further guard against memorization by the LLM backbone: Sequence-type, which classifies a sequence as arithmetic, geometric, Fibonacci, or Collatz; and Solution-mix, which predicts whether the concentration percentage of a mixture from four solutions exceeds 0.5. Because these synthetic datasets are generated algorithmically and do not correspond to natural texts, they are unlikely to have been part of the LLM’s pretraining data.

Across these thirteen datasets the paper evaluates FeatLLM in low-shot regimes (e.g., $k$-shot settings with $k \ll N$). Each dataset provides natural language names and definitions for attributes; these feature descriptions are leveraged by FeatLLM when constructing prompts and extracting rules. The experimental write-up reports per-dataset statistics (size, number of attributes, task type) in the main paper (Table references) and uses this variety to stress-test FeatLLM’s robustness to different feature counts and domains.

# Rationale for including recent and synthetic datasets
A central design choice in the evaluation is to include datasets that the LLM backbone is unlikely to have seen in pretraining. The two recent UCI datasets (Cultivars and NHANES) were added after the LLM’s cutoff date for public data availability, and the two synthetic datasets (Sequence-type and Solution-mix) are algorithmically constructed. This selection reduces the chance that high performance is due to memorization of table contents or dataset-specific heuristics learned during pretraining. By evaluating FeatLLM on these datasets alongside standard benchmarks and health datasets, the experiments aim to demonstrate that the method extracts task-relevant rules from few-shot examples and LLM prior knowledge, not merely recalling examples seen during LLM training.

# Baselines
The experiments compare FeatLLM to nine baselines spanning conventional machine learning methods, semi-supervised / transfer methods that assume access to unlabeled data or multi-task pretraining, and recent LLM-based approaches for tabular learning. These baselines are:

- Logistic regression (LogReg): a linear classifier commonly used as a simple parametric baseline.
- XGBoost: a gradient-boosted tree ensemble that is a strong off-the-shelf tabular learner.
- RandomForest: a bagged tree ensemble that serves as a robust nonparametric baseline.
- SCARF: a semi-supervised method that leverages unlabeled data for augmentation and training.
- STUNT: a few-shot method that assumes access to a large unlabeled dataset for augmentation or pretraining.
- TabPFN: a pretrained Bayesian neural network for tabular tasks that uses synthetic training distributions to provide few-shot inference without task-specific training.
- In-context learning: direct in-context prompting of the LLM by serializing few-shot examples into the prompt and obtaining predictions without parameter tuning.
- TABLET: a method that augments LLM in-context prompts with additional hints derived from an external classifier (rule-sets and prototypes) to improve inference quality.
- TabLLM: an LLM-based approach that uses parameter-efficient tuning (IA3 in the referenced study) to adapt a language model to tabular tasks.

These baselines provide a spectrum of comparisons: classical supervised learners (LogReg, XGBoost, RandomForest), methods that exploit additional unlabeled data or synthetic pretraining (SCARF, STUNT, TabPFN), and LLM-based strategies that either use in-context inference directly or require tuning (In-context, TABLET, TabLLM). It is worth noting that some baselines, such as SCARF and STUNT, assume access to large unlabeled datasets and therefore are not directly comparable in settings where such data are unavailable; the paper excludes those baselines from comparisons when the experimental condition forbids unlabeled data.

# LLM backbone and API settings
FeatLLM is designed to be LLM-agnostic, but the experiments reported in the paper use GPT-3.5 (specifically the gpt-3.5-turbo-0613 API) as the backbone LLM for rule generation and for parsing LLM outputs into executable code. The chosen API settings in the reported experiments are a temperature of 0.5 and top-p (nucleus sampling) set to the default value of 1. These settings introduce controlled randomness: temperature provides stochasticity to encourage diverse rule generation across ensemble trials, while top-p left at 1 means nucleus sampling is not further restricted. The paper notes that FeatLLM requires only API-level inference access (no fine-tuning), which makes it applicable to modern LLMs that do not expose training checkpoints or tuning APIs.

Although GPT-3.5 is used in the primary experiments, FeatLLM’s architecture (extract rules once, convert to binary features, then use a small downstream model at inference time) is intentionally method-agnostic so alternative LLM backbones can be substituted. Additional experiments with different LLM backbones are discussed in the Appendix of the paper.

# Hyperparameters: rules per class, ensemble size, and training details
Two hyperparameters are highlighted as most influential to FeatLLM’s performance: the number of rules extracted per class per LLM query and the number of ensemble trials (bagged models) combined at prediction time.

- Number of rules per class: In the reported experiments FeatLLM extracts $R=10$ rules for each class in a single LLM query. The paper fixes this number to avoid both underfitting (too few rules) and overly large prompts (too many rules), striking a balance appropriate for low-shot settings. Hyper-parameter sensitivity experiments reported in the Appendix show performance is relatively stable around this choice, and $R=10$ was selected as a practical trade-off between prompt length and predictive information.

- Ensemble size (number of trials): FeatLLM repeats the rule-extraction, parsing, binary-feature construction, and downstream weight training process $T$ times and ensembles the resulting models by averaging predicted probabilities. In the main experiments $T=20$ trials are used. Increasing $T$ improves performance up to a point; the paper reports diminishing returns beyond approximately 20 trials. The ensemble uses two sources of randomness to increase diversity across trials: sampling feature/instance subsets (bagging) and setting a non-zero LLM temperature so the LLM produces diverse rule sets.

Training details for the downstream model are deliberately lightweight. After binary features are produced, FeatLLM fits a simple linear model (one per class) without bias to convert the rule indicators into logits. Formally, for class $k$ the binary-rule feature vector for sample $i$ is $\mathbf{z}_k^i \in \{0,1\}^R$, and the model maintains a trainable weight vector $\mathbf{w}_k$. The logit for class $k$ is computed as

logit_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,

and probabilities are obtained by applying a Softmax over the class logits:

\mathbf{p}^i = \text{Softmax}([\,\text{logit}_1^i, \ldots, \text{logit}_c^i\,]).

Projecting $\mathbf{w}_k$ into the non-negative orthant via $\max(\mathbf{w}_k,0)$ ensures features cannot reduce a class likelihood. The model optimizes the cross-entropy loss on the few-shot training samples. Implementation details reported in the paper specify training the linear model with the Adam optimizer at a learning rate of 0.01 for 200 epochs, using $k$-fold cross-validation to select the optimal epoch (see next section). The number of API calls required for FeatLLM is small: typical experimental settings use on the order of 30 LLM queries per full training run, making the approach practical under API access limits.

# Cross-validation and early stopping for hyperparameter and epoch selection
To avoid overfitting in the few-shot regime and to choose training hyperparameters (notably the number of training epochs for the downstream linear model), FeatLLM uses $k$-fold cross-validation on the available few-shot training set. The value of $k$ is chosen so that each fold maintains at least one example of every class; in practice $k$ is set to either 2 or 4 depending on dataset size and the shot count. During training of the linear model, FeatLLM records performance on cross-validation folds to determine the appropriate stopping epoch (early stopping). This cross-validation procedure also guides hyperparameter selection such as the exact number of epochs and any dataset-specific choices when fitting the downstream model.

Beyond model-fitting, cross-validation is used to evaluate variance due to training/test splits: the main reported metrics (e.g., AUC) are averaged over three experimental runs with different random splits of training and testing data, and standard deviations are reported to capture variability.

# Additional implementation notes
Several practical choices are reported in the experiments. Prompt engineering for rule extraction comprises three structured parts—basic information (task and feature descriptions plus serialized demonstrations), a two-step reasoning instruction (prior-knowledge inference followed by data-conditioned rule generation), and strict response formatting instructions to make subsequent parsing robust. Parsing of the natural-language rules into executable code is itself performed via the LLM: the inferred rules and a function specification are provided to the LLM, which outputs Python code that is then executed (via Python’s exec()) to create the binary features. The paper emphasizes that this two-stage use of the LLM—first to propose rules, then to produce parsing code—reduces brittle hand-written parsers and exploits the LLM’s strength at interpreting noisy natural language.

Temperature for rule generation is set to 0.5 in the main experiments to balance determinism and diversity across ensemble trials. The bagging strategy subsamples features or instances in each trial to address prompt-size limitations (datasets with many features) and to increase ensemble diversity. The final prediction is the average of predicted class probabilities across the $T$ trained trials.

Taken together, these experimental choices—dataset selection (including recent and synthetic datasets), a broad and representative set of baselines, a clear LLM backbone and API configuration, controlled hyperparameter settings ($R=10$, $T=20$ in main results), and cross-validation for epoch selection—constitute the evaluation protocol used to validate FeatLLM’s ability to extract informative, generalizable rule-based features for few-shot tabular learning.

Results and Analyses

# Main results: AUC performance across datasets and shots; FeatLLM vs baselines
The core empirical finding of the paper is that FeatLLM consistently achieves top-tier predictive performance across a diverse collection of tabular datasets in few-shot settings. The evaluation covers 13 datasets spanning conventional UCI tasks (e.g., Adult, Bank, Credit-g, Diabetes, Heart, Myocardial), recent additions to repositories (e.g., Cultivars, NHANES), and intentionally synthetic tasks (Sequence-type, Solution-mix). Performance is reported in terms of area under the ROC curve (AUC), averaged over three random train/test splits, with standard deviations reported.

Across these datasets and experimental conditions, FeatLLM either ranks first or second among all compared methods. The baselines include classical supervised models (Logistic Regression, XGBoost, RandomForest), few-shot / semi-supervised approaches (SCARF, STUNT), pretraining-based methods (TabPFN), and other LLM-based strategies (in-context prompting, TABLET, TabLLM). Notably, LLM-based baselines that operate end-to-end on each sample (in-context, TABLET, TabLLM) frequently fail on datasets with many features because of prompt length limitations; FeatLLM, by contrast, uses bagging and ensembling to remain effective even when the number of attributes is large.

Quantitatively, the paper reports that FeatLLM improves over competing LLM-based methods and other baselines, with an average lift of approximately 10% compared to alternatives like TabLLM and STUNT in the reported experiments. These results demonstrate that converting LLM outputs into engineered binary features, and then fitting a simple downstream model, yields not just interpretable rule-like features but also high predictive accuracy in low-shot regimes.

# Data efficiency: competitive with 4 shots relative to 32-shot classical baselines
One of the most striking results concerns data efficiency. In the experiments, FeatLLM trained with as few as $k=4$ labeled examples often attains accuracy comparable to classical tabular models trained with $k=32$ labeled samples. This demonstrates that the combination of LLM priors and rule-based feature generation can compensate for dramatically fewer labeled instances. The mechanism behind this data efficiency is twofold: first, the LLM supplies strong prior knowledge about which features or feature relationships matter for the target task; second, FeatLLM translates that prior knowledge into concrete binary features that concentrate signal, making it easier for the downstream simple model to learn from limited labeled data.

This result is particularly relevant for domains where labels are costly to obtain (for instance, in healthcare or finance). Instead of relying solely on labeled examples to discover predictive structure, FeatLLM leverages the semantic knowledge embedded in the LLM to propose plausible decision rules, which significantly accelerates learning from small labeled sets.

# Runtime comparison: training and inference costs versus LLM-inference methods
The paper reports both training and inference time comparisons, using the Adult dataset with 16-shot training as an example. FeatLLM requires relatively modest training-time interaction with the LLM: around 30 API queries per ensemble trial setup, which can be parallelized and is designed to be inexpensive compared to full fine-tuning. The heavy LLM interaction is limited to the rule-generation and parsing phases; inference on new samples does not require additional LLM calls because the learned rules are parsed into executable code and the downstream model is a lightweight linear (or similar) predictor.

In terms of inference latency, FeatLLM matches conventional methods: once rules are produced and the linear model is trained, prediction is a low-cost forward pass (binary-feature extraction and a dot product with learned weights). This contrasts with other LLM-based approaches (in-context prompting, TABLET, TabLLM) that perform at least one LLM call per test sample and therefore have substantially higher inference time. TabLLM, which involves parameter-efficient tuning, also has heavy training-time and inference resource requirements (for example, TabLLM experiments used multiple A100 GPUs for model parallelism), while FeatLLM needs only API-level access without fine-tuning.

Thus FeatLLM achieves a favorable trade-off: it concentrates LLM use at training time to extract reusable features, keeping per-sample inference costs low and comparable to classical models.

# Ablations: effect of weight tuning, ensembling, feature descriptions, prior-knowledge reasoning
The paper includes an ablation study that isolates the contributions of major components to overall performance. Four ablations are considered:

1. -Tuning: omit learning of the linear model weights; instead simply sum the binary rule features per class to obtain logits.
2. -Ensemble: remove the ensemble (bagging + multiple trials) and rely on a single rule-generation run.
3. -Description: exclude feature descriptions from the prompt that explains feature types and definitions.
4. -Reasoning: remove the Step-1 reasoning instruction (the prior-knowledge step) that asks the LLM to think about feature–label tendencies before inspecting examples.

Averaged AUC changes indicate that each component contributes positively: removing any of these elements reduces performance across datasets. Two qualitative patterns emerge from the ablations. First, weight tuning provides increasing benefit as the number of shots grows: when more training data are available, the downstream linear model can more accurately estimate the relative importances of rules, and tuning yields larger improvements. Second, when shots are few, the inclusion of feature descriptions and the prior-knowledge reasoning step materially affects performance. In other words, the LLM's use of prior knowledge and the structured two-step reasoning are especially valuable in the extremely low-shot regime, helping the model avoid spurious correlations and focus rule generation on semantically relevant attributes. Finally, ensemble techniques consistently improve performance by aggregating multiple LLM-generated rule sets and mitigating noisy or incorrect rules from individual trials.

# Feature quality analysis: proportion of informative rules before/after tuning
FeatLLM explicitly evaluates the quality of the generated rule-based features by measuring the AUROC of each binary rule feature against the target label. For each dataset, the paper reports the average AUROC of rule features and the proportion of rules with AUROC above 0.5 (i.e., informative features). Two stages are contrasted: "Before tuning" (directly examining LLM-generated rule features) and "After tuning" (examining which rules are retained as important after the downstream model learns weights).

The analysis shows that a majority of generated rules are relevant to the prediction target: many rule features attain AUROC greater than 0.5 prior to any tuning. Moreover, the tuning phase serves as an automatic filter: after fitting the linear model, rules with negligible learned weights (below a threshold such as 0.1) are effectively discarded, increasing the fraction of retained features that are genuinely informative. This two-step process—LLM generation followed by data-driven weight estimation—both harnesses LLM prior knowledge and uses empirical evidence to remove spurious or weak rules. The result is a compact and informative set of binary features that drive prediction.

# Robustness to spurious features: appending unrelated columns and measuring degradation
Robustness to irrelevant or spurious features is explicitly tested via an experiment on the Heart dataset. The experimental protocol appends randomly chosen columns from the Adult dataset (which are unrelated to predicting heart disease) and measures AUC degradation as the number of such noisy columns grows. All models are trained in an 8-shot setting, and methods that require large unlabeled corpora are excluded for fairness.

FeatLLM shows the least performance degradation compared to baselines as spurious columns are added. The core reason is the prompt design and the two-step reasoning instruction: before generating rules, the LLM is prompted to reason about which features are plausibly related to the target task (Step 1). This encourages the LLM to avoid crafting rules from obviously irrelevant columns, so only a small fraction (about 1–2%) of generated rules originate from noisy columns in practice. That said, the paper also notes that FeatLLM is not immune to learning spurious correlations entirely—if strongly related but incorrectly attached columns exist, the LLM can still generate misleading rules. But overall, the combination of prior-knowledge reasoning and tuning makes FeatLLM substantially more robust than models that rely purely on pattern-matching from a few examples.

# Hyperparameter sensitivity: ensemble size and number of rules per class
FeatLLM depends primarily on two hyperparameters: the number of ensemble trials $T$ and the number of rules per class $R$ generated in each LLM query. Empirical exploration reveals the following:

- Ensemble size $T$: Increasing $T$ improves performance because additional trials produce diverse rule sets, enabling ensembling to average out errors and to amplify consistent, correct rules. Performance gains, however, saturate: in the experiments, benefits converge around $T \approx 20$. Thus $T=20$ is a pragmatic choice balancing accuracy and LLM-query budget.

- Rules per class $R$: While more rules can increase representational capacity by covering more candidate decision boundaries, it also increases input dimensionality and the chance of overfitting in low-shot regimes. The experiments found no statistically significant advantage to very large $R$, and a setting of $R=10$ provides a practical trade-off between prompt length, downstream model complexity, and performance.

These observations imply that modest ensemble sizes and a moderate number of rules per class suffice to capture most of the performance gains, keeping both LLM-query cost and downstream model complexity manageable.

# Scalability to many features via bagging and ensemble
One practical limitation of direct LLM-based tabular approaches is the input prompt length: very wide tables (many columns) can exceed model context windows or produce unwieldy prompts. FeatLLM addresses scalability to many features through a bagging-and-ensemble strategy. Concretely, each ensemble trial performs rule generation from a subset of features or training instances, thereby keeping prompt length modest. The final prediction aggregates across trials; collectively, these trials cover more of the original feature space without ever requiring a single oversized prompt.

This approach supplies two complementary benefits. First, it enables application to datasets with many attributes that would otherwise be infeasible for single-shot LLM prompts. Second, it injects diversity into the ensemble: different trials produce different candidate rules because they see different feature subsets and randomized demonstrations. This diversity is crucial to robustness: incorrect rules in some trials are attenuated by correct rules from others when probabilities are averaged. Hence the bagging-plus-ensemble design is both a practical scalability mechanism and a means to enhance stability and predictive performance.

Taken together, the experimental analyses show that FeatLLM leverages LLM prior knowledge to generate high-quality, interpretable binary features; uses a simple learnable aggregator to ground those features to task-specific evidence; and employs ensemble strategies to manage prompt size, increase robustness, and produce competitive few-shot performance with low inference cost.

Practical Guide to Using FeatLLM

# Preparing feature metadata: names, types, and optional descriptions
FeatLLM relies on clear, human-readable feature metadata because the LLM uses this information both to invoke prior knowledge and to avoid type errors when generating rules. At minimum provide each column's name in natural language (for example, "age", "cholesterol_mg/dL", or "smoking_status") together with its data type: numerical (continuous or integer), categorical (with listed categories if possible), boolean, or text. The paper shows that including feature descriptions improves the LLM's ability to generate relevant rules, particularly in low-shot regimes, so add short natural-language definitions when available: one sentence describing the meaning of the column, units if applicable, and typical value ranges or categories.

Organize the metadata so it can be serialized into the prompt automatically; FeatLLM places the feature names and their types/descriptions into the "Basic information description" block of the prompt. For categorical variables, supplying the possible categories (or a representative subset) reduces the chance the LLM invents impossible categories. For numerical features, indicating units and typical ranges helps the LLM propose realistic thresholds (e.g., "age: integer, range 18–90, years"). Keep descriptions concise: the LLM benefits from focused context but the overall prompt length should remain manageable.

Finally, make sure feature names are stable and human-friendly. FeatLLM depends on natural-language reasoning: cryptic internal column keys or abbreviated names (e.g., "f_12") reduce the model's ability to connect features to domain concepts. If your dataset already has terse column keys, prepare a mapping to readable names and use that mapping when composing prompts.

# Authoring effective task questions and example serialization
FeatLLM frames the prediction objective as a natural-language question, which guides the LLM to infer causal tendencies and to generate rules for each target class. Write the task description as a clear question that directly asks what you want predicted, including the possible answer set when helpful. For binary classification use yes/no phrasing ("Does this patient's record indicate chronic heart failure? Yes or No?"). For multiclass tasks, list the classes explicitly in the question so the LLM is aware of the output space.

Example demonstrations are serialized in the "Serialize" format used in the paper:
"f_1 is x_1. ... f_d is x_d. Answer: y"
Automate this serialization so each example in the few-shot support set becomes a small textual case in the prompt. Because FeatLLM is designed for few-shot settings, you will include only k examples (e.g., k=4 or k=8) in each rule-generation query. The paper finds that demonstration order can affect LLM outputs; therefore randomizing order across ensemble trials produces diversity in extracted rules.

When choosing which examples to include, prefer exemplars that highlight discriminative patterns: examples where feature conditions correspond clearly to the target class. If you have class imbalance, ensure examples represent each class to allow the LLM to infer rules for all classes. Keep the examples compact and consistent with the feature metadata to reduce parsing ambiguity.

# Crafting the two-step reasoning instruction and response format
The FeatLLM prompt structure deliberately uses a two-step reasoning instruction to separate general prior knowledge from data-driven rule induction. Implement the same structure in your prompt.

Step 1 instruction (prior-knowledge inference): ask the LLM to infer, without looking at examples, which features are likely to be causally or strongly associated with each label based on general knowledge. Phrase it explicitly: "First, based on common knowledge about the domain and the feature definitions above, list how each feature tends to relate to the label (e.g., 'higher age increases risk'). Do not use the examples here." This primes the model to surface domain priors that avoid spurious correlations driven solely by the few examples.

Step 2 instruction (example-based rule derivation): then instruct the LLM to use the prior-step output plus the few-shot example cases to generate concrete, parseable rules for each class. Specify a fixed number of rules per class (the paper uses 10 per class) to balance expressivity and prompt size. For instance: "Using the prior knowledge and the examples, produce up to 10 rules that, if true for a sample, indicate membership in each class." Constraining the number helps control downstream binary feature dimensionality and avoids excessively long parsing/validation steps.

Response formatting guidance: to make parsing reliable, require a strict, minimal structure for the LLM's responses. For example, instruct the model to output:

Class: <class-name>
1. <rule-expression-1>
2. <rule-expression-2>
...
End

And require each rule to reference feature names exactly as provided and to use comparisons appropriate to the feature type. Provide short examples of acceptable rule formats for each type: numeric (e.g., "age > 65"), categorical (e.g., "smoking_status == 'current'"), boolean (e.g., "has_diabetes is True"), and combinations using AND/OR when needed. This response instruction reduces syntactic variability and makes later parsing simpler.

# Rule parsing implementation: LLM prompt for code generation, validation tests
Even with constrained formatting, LLM outputs can vary syntactically. FeatLLM solves parsing by using the same LLM to translate the natural-language rules into executable code (Python). Implement a two-step parser:

1) Prompt-to-code generation: create a second prompt that contains (a) a short function signature and I/O description (for example, "def rule_to_bool(row: dict) -> List[bool]: # returns list of booleans, one per rule"), (b) the serialized rules produced earlier, and (c) a strict request: "Return only valid Python code that evaluates each rule on a row dictionary using the provided feature names." Ask the LLM to map phrases like "greater than" to ">" and to map categorical equality to Python string equality. Because the LLM has been trained heavily on code, it reliably emits short code blocks when asked in this constrained way.

2) Execution and validation: execute the returned code with Python's exec() in a sandboxed environment and apply it to a small validation set. The paper executes such generated code to convert the dataset into binary features for each rule. To ensure safety and correctness, run validation tests on a handful of synthetic or real rows that exercise edge cases: missing values, out-of-range values, categorical labels not seen in rules, and type mismatches. Flag failures (exceptions or unexpected outputs such as non-binary values). If a failure occurs, re-run the code-generation prompt with appended error messages and request corrections, or fall back to a conservative parser that recognizes simple patterns (e.g., "<", ">", "==") for well-formed rules.

Because the paper constrains response structure and then uses the LLM to produce Python code, this two-phase approach reduces efforts building hand-coded parsers and leverages the LLM's code-generation strengths while keeping parsing robust via simple validation tests.

# Choosing ensemble size and bagging ratios under context limits
FeatLLM uses an ensemble of repeated rule-generation trials combined with bagging to increase robustness and to handle prompt size limits when datasets have many features or when support size is large. The paper used T=20 ensemble trials with R=10 rules per class as a practical choice; this produced diminishing returns beyond roughly 20 trials.

When selecting ensemble size T, balance improved robustness against API cost and latency. Useful practical guidance from the paper: performance typically improves with T, but gains converge (often around T ≈ 20). For very strict cost/latency constraints, T can be reduced; for critical-accuracy scenarios you can increase T until you observe diminishing returns on validation.

Bagging strategy: in each ensemble trial randomly sample a subset of features and/or a subset of support examples to include in the prompt. This reduces prompt length per query, allowing datasets with many features to be handled without exceeding context limits. Tune bagging ratios based on context capacity: if the LLM's token budget constrains you, reduce the number of features per trial; the ensemble idea compensates by aggregating rule-sets across different feature subsets. The paper reports that bagging both features and instances reduces per-query prompt size and increases rule diversity. When you have a reasonable context window, you can include more features per trial; otherwise prioritize the most semantically relevant or high-variance features in each sampled subset.

Also randomize example order within the prompt across trials to exploit in-context-order sensitivity, increasing diversity in generated rule-sets. The paper found that randomness in order and a moderately high sampling temperature (e.g., 0.5) helps produce varied but useful rules for the ensemble.

# Selecting and training the downstream linear model
After parsing rules into binary features, FeatLLM fits a simple linear model to learn each rule's importance. For a classification problem with c classes and R rules per class (binary features), denote the binary feature vector for class k from sample i as $\mathbf{z}_k^i \in \{0,1\}^R$. The paper uses a linear logit model without bias where, for sample i and class k:

logit_k^i = max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\mathbf{p}^i = \text{Softmax}([ \text{logit}_1^i, ..., \text{logit}_c^i ]).

Constrain weights to be non-negative by applying elementwise $\max(\mathbf{w}_k, 0)$; this prevents generated features from reducing a class's likelihood during learning. Trainable parameters are the weight vectors $\mathbf{w}_k$. Optimize the cross-entropy loss on the few-shot labeled examples. The paper used the Adam optimizer with learning rate 0.01 and trained for ~200 epochs, selecting epochs via k-fold cross-validation; these hyperparameters are sensible starting points.

If you prefer a regularized alternative, you can employ L2 or L1 penalties to avoid overfitting when many rules are present, but FeatLLM's design purposefully limits per-trial rule counts (e.g., 10 rules per class) and uses ensembling to reduce overfitting. The paper shows that learning weights (i.e., tuning) improves performance versus naive counting of satisfied rules, particularly as shot count increases, so training this simple model is important.

After training, you can prune rules with near-zero learned weights (the paper suggests a threshold such as 0.1 chosen from the empirical weight histogram) to simplify the final model and remove uninformative or noisy rules.

# Common pitfalls: overly general rules, type mismatches, and how to refine prompts
Overly general rules: LLMs sometimes output very broad rules (e.g., "age > 0" or "has_any_symptom is True") that are trivially true or unhelpful. These produce uninformative binary features and waste capacity. Mitigation: in the response instruction require rules to be "decisive" and actionable. Provide examples of both good and bad rules in the prompt: show that "age > 65" is acceptable, while "age > 0" is not. The two-step reasoning (first ask for priors, then for decisive rules using examples) reduces generation of trivial rules.

Type mismatches: a generated rule might use an inequality on a categorical feature or compare a string to a number. Two defenses reduce this issue. First, include feature type annotations in the "Basic information description" and remind the LLM in reasoning instructions to use comparisons appropriate for each type. Second, validate generated code using the parsing-and-execution step on a small validation set: type errors will surface as exceptions or as logically impossible comparisons. When errors are detected, resend the rule parsing request to the LLM with explicit error output and ask for corrected code.

Ambiguous wording and syntactic variability: although response format constraints help, LLMs may phrase comparisons in words like "greater than" or "less than or equal to." Because the paper uses the LLM to translate rules into code, this is manageable—ensure your parsing prompt explicitly requests normalization of such phrases to canonical Python symbols. If the LLM still produces ambiguous rules, you can post-process rules with regex heuristics before code generation to canonicalize common phrases.

Spurious correlations: with very few examples, the LLM can latch onto accidental correlations. The paper demonstrates that the explicit step to list prior knowledge and the use of multiple trials plus bagging reduces extraction of noisy rules; still, monitor the proportion of generated rules that reference obviously irrelevant features. If you find many spurious rules, add more domain guidance in step 1, or restrict the set of features sampled per trial to those likely relevant.

# Deployment: low-latency inference without LLM calls
One of FeatLLM's main operational benefits is that after the rule-generation phase and downstream weight training are complete, inference does not require any LLM calls. Deployment proceeds as follows.

1. Store the final set of parsed rules as executable code (or a compiled form) that maps each raw input row to the binary rule-feature vector. Use the validated Python implementation generated during the parsing stage or manually convert it into a safe production routine.

2. Save the trained weight vectors $\{\mathbf{w}_k\}$ (or pruned subset). At inference time, for each new sample compute the binary vector outputs for the rules, compute the logits via the linear model
logit_k = max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k,
and produce class probabilities with softmax. This is a simple dot product and softmax computation (O(number_of_rules)), which is very fast.

3. Because the inference requires no LLM, latency is comparable to standard linear models and is much lower than approaches that evaluate each sample via the LLM. The paper's runtime comparison shows that FeatLLM's inference time is similar to conventional methods like logistic regression and far faster than per-sample LLM inference alternatives.

For safety and maintainability, keep a versioned artifact bundle containing (a) the rule code, (b) the trained weight vectors, and (c) metadata about how each rule maps to features and which ensemble trial produced it. This supports interpretability and debugging after deployment.

# Final practical checklist
- Prepare readable feature metadata with explicit types and short descriptions.
- Write a clear natural-language task question that enumerates classes.
- Serialize k-shot examples in the standard format and keep them representative.
- Implement the two-step reasoning prompt: (1) prior-knowledge inference, (2) example-based rule generation; constrain rule count (e.g., 10 rules/class).
- Constrain response format strictly and include rule-format examples for each feature type.
- Use the LLM to translate rules to executable code; validate this code on test rows and iterate if errors occur.
- Choose ensemble size T (start at 20) and bagging ratios to respect context limits; randomize demo order and use moderate temperature (e.g., 0.5) for diversity.
- Train non-negative-weight linear models per class with cross-entropy and simple optimizers (Adam, lr 0.01), prune low-weight rules.
- Bundle the rule code and learned weights for inference; no LLM calls required at runtime.

Following the paper's method and these practical steps should let you implement FeatLLM effectively: extracting interpretable, high-quality rule features with an LLM during a limited set of queries, and achieving fast, LLM-free inference with a simple downstream model.

Limitations, Extensions, and Broader Impact

# Scope: designed for low-shot regimes; potential extensions to larger datasets
FeatLLM is explicitly developed and evaluated for the few-shot (low-shot) learning regime. The core design choices—relying on LLM in-context reasoning to generate a modest set of human-interpretable rules, converting those rules to binary features, and learning a simple downstream model from only a handful of labeled examples—are tailored to settings where labeled data are scarce. Empirically, the paper shows that with as few as 4 shots FeatLLM can reach performance comparable to conventional tabular learners trained on many more samples, and the ablation studies indicate that components that exploit LLM prior knowledge (feature descriptions, two-step reasoning) are particularly valuable when shots are small. The ensemble-with-bagging strategy further helps stabilize rule generation and cope with prompt-size constraints in low-shot settings.

Because FeatLLM depends on learning importance weights for generated binary rule-features from the available labeled examples, its current formulation is not optimized for very large labeled datasets. The linear model used to combine rule features (trained with cross-entropy on the few labeled samples) is simple by design; when labeled data grow large, more expressive downstream learners or different regularization regimes may become preferable. The paper notes this in the conclusion and in analysis: the benefit of weight tuning becomes larger as the number of shots increases, suggesting that FeatLLM can benefit from more data but may require changes (e.g., different model capacity, different regularizers, or alternate training protocols) to fully exploit abundant labels.

Potential extensions toward larger datasets are natural: one could increase the complexity of the downstream learner, adapt the number of generated rules, or transition from rule-only features to richer feature representations (discussed below). However, these are directions identified by the authors as future work rather than established in the experiments. Practically, the parts of FeatLLM that leverage LLMs (rule extraction, rule parsing into executable code) are already designed to be API-friendly and prompt-size aware (through ensemble bagging), so scaling to larger labeled regimes would primarily involve adjusting the downstream training stage and possibly rethinking how many distinct rule-sets are needed to cover a large, diverse dataset.

# Beyond rules: exploring richer feature types and hybrid symbolic-numeric features
The published FeatLLM framework focuses on extracting explicit rules—conditions tied to each class—and turning them into binary features that indicate whether each rule holds for a sample. This rule-centric design has clear advantages: rules are human-readable, easy to parse into simple executable checks, and naturally yield sparse, interpretable binary features that work well with a low-shot linear combiner.

Nonetheless, the paper acknowledges that rules are only one type of feature the LLM could produce. The conclusion highlights future work to expand the kinds of features FeatLLM crafts, beyond rule-based features, to address a broader set of tasks and datasets. Richer feature types could include numeric scoring functions (continuous features derived from expressions among columns), embedding-like semantic features (e.g., encoding free-text attribute descriptions or derived interactions), or hybrid symbolic-numeric features that mix conditional logic with computed values. Such hybrids could capture subtler relationships that a pure rule (binary) feature cannot; for instance, a rule that thresholds a laboratory measurement is useful, but a normalized continuous transformation might better capture dose–response patterns when more labeled data are available.

Moving to richer feature types raises practical and safety considerations already touched on in the methods: FeatLLM currently relies on constrained rule formats and a parsing step whereby the LLM itself produces small executable code that implements the rule checks; that code is then run (the paper uses Python’s exec()). Extending to arbitrary numeric transformations or learned embeddings would require more careful parsing and validation, more sophisticated execution sandboxing, and possibly new training objectives for the downstream model to handle continuous or high-dimensional features. The paper’s ensemble and bagging techniques for rule diversity and prompt-size management would remain relevant: if richer features are more expensive to generate or represent, bagging subsets of features or instances per trial can still mitigate prompt length and promote diversity.

# Bias and misinformation risks from LLM priors and mitigation strategies
One of the central motivations for FeatLLM is to exploit LLMs’ broad prior knowledge to compensate for limited labeled data. This is a double-edged sword: while such priors can supply valuable domain insight (e.g., clinically plausible relationships or common-sense associations), they may also encode societal biases, outdated knowledge, or outright misinformation. The paper explicitly raises this concern in the Broader Impact section: since FeatLLM’s rule generation can “dominate” the sparse labeled evidence, predictions may reflect the LLM’s priors more than the observed data. In sensitive application domains such as finance or healthcare, this can lead to unfair or harmful outcomes.

Mitigation strategies discussed in the paper and that naturally follow from its architecture include the following. First, the downstream learning stage serves as a data-driven filter: the linear model learns non-negative weights for each generated feature and, through tuning, down-weights rules that are not supported by the labeled samples. The feature-quality analysis in the experiments demonstrates that many generated rules are informative and that tuning reduces the contribution of unhelpful rules. Second, the ensemble-with-bagging procedure reduces reliance on any single LLM-generated rule set; rules that consistently appear across diverse trials are more likely to be meaningful, while idiosyncratic, possibly biased rules may be averaged out. Third, practitioners can supply accurate and careful feature descriptions and task descriptions in the prompt; the ablation studies show that including feature descriptions and a two-step reasoning instruction improves robustness in few-shot settings by steering the LLM toward relevant prior knowledge rather than spurious correlations.

Beyond these measures, the paper suggests further work: analyzing the societal biases and misinformation embedded in LLM priors is an important future direction. In practice, additional safeguards would be advisable before deployment: human review of generated rules (made feasible by their interpretable form), domain-specific prompt templates that limit problematic inferences, and the inclusion of debiasing constraints or counterfactual examples in the prompt to counter known stereotypes or erroneous assumptions baked into the LLM.

# Interpretable ML benefits: human-readable rules and weight importances
A key advantage of FeatLLM is the interpretability of its outputs. The LLM produces explicit, human-readable rules for each class; these rules are then parsed into checks and become binary features. The downstream linear model assigns non-negative weights to each rule-feature, and the learned weights quantify each rule’s contribution to the class logit via the positive-projection operation used in the paper: for class $k$ and sample $i$ the logit is

logit_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,

where $\mathbf{z}_k^i \in \{0,1\}^R$ is the vector of R rule-feature indicators for class $k$. Because the model projects weights into the non-negative orthant, each nonzero weight has a straightforward interpretation as how strongly satisfying that rule increases the class logit. This combination (readable rules + non-negative importance weights) yields an especially transparent predictive mechanism compared to end-to-end LLM or complex black-box models.

The interpretability serves multiple purposes. From a scientific or operational standpoint, stakeholders can inspect rules to validate whether they reflect domain knowledge, detect spurious correlations, or uncover surprising but plausible patterns. From the safety perspective, interpretability supports auditing and bias detection: if certain generated rules reflect stereotypes or incorrect causal assumptions, they can be removed or corrected before deployment. Finally, the rule-weight pairing helps feature selection in practice: low-weighted or zeroed rules can be pruned, reducing model size and simplifying explanations.

# Security and safety: executing generated code responsibly
FeatLLM’s parsing stage converts LLM-produced rule descriptions into executable code, leveraging the LLM itself to generate small Python snippets implementing the rules, and then running the code with Python’s exec() to create the binary features. While this approach exploits the LLM’s ability to normalize diverse textual rule formulations into code, it brings an important safety dimension: executing code generated by an LLM (even if expected to be simple checks) poses risks if not properly sandboxed. The paper documents this implementation choice but does not delve into operational safety mechanisms; it therefore implicitly acknowledges the need for responsible execution.

Responsible deployment requires multiple safeguards. At minimum, the execution environment should be sandboxed: limit available builtins, disallow filesystem and network access, and enforce strict resource and time limits to prevent runaway processes. Generated code should be parsed and statically inspected when possible; restricted grammar templates and constrained code generation prompts reduce the risk surface by channeling outputs into a tightly-defined subset of safe operations (comparisons, arithmetic, categorical checks). Human review of a sample of generated code snippets is another pragmatic check, particularly in high-stakes applications. Finally, logging and monitoring should capture generated rules and execution traces so any anomalous or malicious behavior can be diagnosed post hoc.

The paper’s design already reduces some risks by constraining rule formats during generation (see the response-instruction component), and by using the LLM again to normalize rules into code rather than trying to parse arbitrary natural language with brittle heuristics. Nonetheless, practitioners should treat the code-execution step as a critical operational point and instrument it accordingly.

# Future directions: adaptive rule counts, active sample selection, domain-specific templates
The paper outlines several future directions that would extend FeatLLM’s capabilities and address current limitations. Adaptive rule counts are one natural extension. In the published system, the number of rules per class was fixed (ten rules per class in the experiments), chosen as a trade-off between prompt length and expressivity; hyper-parameter analysis found ten to be practical. However, different tasks and datasets likely benefit from different numbers of candidate rules. Adaptive schemes—where the LLM or a downstream controller proposes a dynamic number of rules conditional on task complexity or initial validation performance—could improve efficiency and performance.

Active sample selection is another promising direction. Because FeatLLM leverages few labeled examples to tune feature weights and to ground rule extraction, intelligently choosing which samples to label (or which samples to include in the few-shot demonstrations sent to the LLM) could substantially improve rule quality and model performance. The paper already randomizes demonstration order to induce diversity in ensemble trials; extending that to informed selection strategies (e.g., uncertainty-based acquisition, diversity sampling) would fit naturally in the framework and could be especially beneficial when labeling cost is high.

Finally, domain-specific prompt templates and task descriptions can increase robustness. The paper’s ablations show that feature descriptions and the two-step reasoning instruction materially improve rule relevance in low-shot conditions. Creating curated templates for particular domains (medicine, finance, manufacturing) that encode common valid rule idioms, unit conventions, and verification checks would likely reduce spurious rule generation and make parsing simpler. Such templates also support compliance requirements in regulated domains by enforcing that generated rules conform to known constraints (e.g., physical ranges for measurements).

More speculative but aligned directions include hybridizing rule-based features with learned numeric transforms, integrating unlabeled data or synthetic pretraining of the downstream combiner (while preserving FeatLLM’s main advantage of minimal per-sample LLM inference), and developing automated audits that compare generated rules to known domain ontologies to detect misalignments.

# Concluding remarks
FeatLLM demonstrates a compelling approach: leveraging LLMs as feature engineers—explicitly producing human-readable rules that are converted into binary features and combined with a small trainable model—can deliver strong few-shot tabular performance while reducing per-sample LLM inference cost and improving interpretability. The architecture’s strengths are most pronounced in low-shot regimes and in contexts where human inspection of generated rules can be applied. At the same time, the approach carries limitations and risks intrinsic to using LLM priors: possible bias or misinformation, and the operational hazards of executing LLM-generated code. The paper discusses these points and proposes practical mitigations (weight tuning, ensembling, constrained prompts), while pointing to concrete future work (richer feature types, bias analysis, adaptive processes) to broaden FeatLLM’s applicability and safety.
