\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### What specific bagging scheme is used for samples and features in FeatLLM?
Question:
The paper says you use feature bagging and instance bagging to control prompt size and induce diversity, but the exact sampling scheme is not specified. Do you sample without replacement from features and examples for each LLM call? What are the typical fractions for features and examples retained per trial, and how are they tuned? Are the same subsets used for both the rule-generation prompt and the subsequent weight training, or is there a risk of distribution shift between the prompt subset and the training subset?
Answer:
Short answer: the paper does not spell out a precise sampling protocol (e.g., with vs. without replacement or fixed fractions) for the feature/instance bagging. What it does state is that FeatLLM uses bagging to select a subset of features or instances per trial to (1) reduce prompt size and (2) induce diversity across an ensemble of trials. The only concrete bagging-related hyperparameters reported are the number of ensemble trials ($T = 20$) and the number of rules extracted per class per trial ($R = 10$). The paper leaves the precise sampling fractions and the replacement policy unspecified and treats those as tuning choices (see the discussion in the Methods and Hyper-parameter analysis sections and Appendix references).

What that means in practice and why it matters
- The method repeatedly runs the full pipeline (prompt → rule generation → parsing → feature construction → fit simple model) $T$ times and averages the predicted class probabilities. Bagging is the source of randomness across trials (together with LLM sampling temperature and order of demonstrations).
- Because the paper emphasizes controlling prompt size, the intended use of bagging is to pick only a subset of the full feature set (or a subset of instances) to include in each prompt so that each LLM query stays within token limits.
- The paper does not claim a sophisticated sampling scheme; it treats the number/size of subsets as a hyperparameter that trades prompt length, diversity, and coverage.

On whether the same subset is used for rule-generation and weight training (and distribution-shift risk)
- Though the paper does not explicitly write a line like “we use the same subset for prompt and training in each trial,” the described pipeline implies that each trial generates rules from the prompt (which contains the subset of features/instances) and then those generated rule-features are parsed and applied to data and a linear model is trained on the available $k$-shot training samples. In other words, the rules generated in a given trial are used to create binary features that are then fit with weights (Eq. $1$) in that same trial, and the ensemble averages models from all trials.
- If one were to use different subsets for the rule-generation prompt versus the later weight-training step, that would create a distribution shift: the rules the LLM produced were based on a particular view of features/instances and might not align with the data used to learn weights. The paper’s described flow (generate rules → parse → construct binary features → learn weights) strongly suggests the intended and sensible practice is to use the rules from the prompt and then train the downstream model on the binary features produced from the same rule set (applied to whatever training samples you have). This avoids the obvious mismatch between rule semantics and training data.

Recommended practical choices (consistent with the paper’s stated design and experiments)
- Use per-trial subsets consistently: for each ensemble trial, pick the subset (features and/or instances), build the prompt from that subset, generate rules, parse them, apply those rules to your dataset to produce binary features, and then train the weights for that trial on the available $k$-shot examples (or the subset of instances if you intentionally bag instances). This follows the pipeline in the paper and avoids distribution-shift between prompt and training.
- Use the paper’s reported defaults as starting points: $T \approx 20$ ensembles, $R = 10$ rules per class, LLM temp = $0.5$. The paper reports these gave stable performance and that performance gains saturate around $20$ ensembles.
- Treat the fraction/size of features or instances included per prompt as a tunable hyperparameter. The paper frames this as an explicit tradeoff: smaller subsets reduce prompt size (and make LLM calls feasible) and increase ensemble diversity, while larger subsets give each trial a more complete view of the table. Tune the subset size by validation (or by checking performance vs. prompt length), respecting your LLM token limits.

Summary
The paper uses feature/instance bagging to create diverse prompts across an ensemble, but it does not specify whether sampling is with/without replacement nor give fixed fractions for retained features/instances; those choices are treated as hyperparameters. The pipeline implies rules generated in a trial are the ones used to create features and train that trial’s weights (so you should avoid using different subsets for prompting vs. training to prevent distribution shift). Use the paper’s recommended ensemble size ($T = 20$) and rules-per-class ($R = 10$) as defaults and tune the subset size to balance prompt length and coverage.
