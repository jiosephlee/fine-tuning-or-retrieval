\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How are continuous feature thresholds chosen when LLMs generate rules in FeatLLM?
Question:
In FeatLLM, the LLM produces human-readable rules that often look like inequalities (e.g., "age > 60"). With only few-shot examples, how does the LLM decide specific threshold values for continuous features? Are these thresholds inferred purely from prior knowledge, from the provided few-shot examples, or both? If both, what prevents overfitting to arbitrary cut points suggested by tiny k-shot samples? Do you post-process or discretize continuous features before prompting to stabilize the learned thresholds?
Answer:
Short answer: FeatLLM lets the LLM propose numeric cutpoints using both its pretraining (prior knowledge) and the few-shot examples, then prevents overfitting to arbitrary k-shot thresholds by turning those cutpoints into binary features and learning non‑negative weights on many generated rules with ensembling and bagging. There is no separate pre-discretization step; instead stability comes from downstream weight learning, rule filtering, and ensemble regularization.

Explanation grounded in the paper (how thresholds are chosen and why they don’t overfit):

1) How thresholds are produced by the LLM
FeatLLM’s prompt explicitly asks the LLM to (a) first reason from general/commonsense knowledge about which features matter (Step 1) and then (b) combine that prior knowledge with the provided few-shot serialized examples to “deduce rules” (Step 2). Because of this two-step instruction the numeric thresholds (e.g., “$\text{age} > 60$”) that appear in generated rules arise from a mixture of the model’s pretrained knowledge (typical clinical or domain cutpoints it has seen) and the few examples you show it. The paper emphasizes this separation to encourage the LLM to use prior knowledge rather than simply memorizing tiny-sample idiosyncrasies.

2) Rules are converted to binary features (no pre-discretization)
Rather than discretizing the dataset before prompting, FeatLLM parses the LLM’s natural-language rules (using the LLM itself to generate parseable code) and applies those rules to the raw numeric columns to create binary indicator features “$\text{rule satisfied} = 1/0$.” So the continuous value is not binned by a fixed global discretizer beforehand; instead each candidate threshold from the LLM becomes a binary feature.

3) Why these thresholds don’t cause severe overfitting
Several mechanisms in the pipeline reduce overfitting to noisy thresholds suggested by a tiny k-shot set:

- Learnable non-negative weights: The binary rule-features are fed to a simple linear model where the logit for class $k$ is computed as $ \text{logit}_k^i = \max(\mathbf{w}_k,0) \cdot \mathbf{z}_k^i,$ and the model is trained (cross-entropy) on the few labeled samples. Learning these weights lets the model downweight or ignore rules that do not generalize from the examples. Projecting weights into the positive subspace prevents a generated feature from actively hurting the class logit and behaves like a one-sided regularizer.

- Rule filtering via learned weights: The paper reports computing AUROC of generated rule-features vs. label and then filtering by weight; empirically they use a threshold (paper mentions $0.1$ was used in analysis) to remove features judged uninformative after tuning.

- Ensembling + bagging: FeatLLM repeats rule generation $T=20$ times (the paper used $T=20$), with high LLM temperature and randomization of few-shot demo order, producing diverse rule-sets. Predictions average probabilities over these ensembles. Bagging (random subsets of features/instances per trial) both limits prompt size and adds robustness: bad thresholds from a single trial are diluted across the ensemble.

- Fixed budget of rules and prompt guidance: The method enforces a fixed number of rules per class (paper used $R=10$) and gives instructions (feature types, formats, Step‑1 reasoning) to reduce wild/irrelevant cutpoints. The ablation study shows the Step‑1 prior-knowledge reasoning and feature descriptions materially help performance in low-shot regimes, consistent with reducing spurious arbitrary thresholds.

- Low-capacity downstream model & regularization effect: By converting thresholds into binary features and using a low-capacity linear model trained on few examples, the approach avoids fitting a high-complexity function of continuous inputs directly from few samples, which is a typical source of overfitting.

4) Practical details from the paper that stabilize thresholds
The implementation choices reported in the paper that affect threshold stability include using GPT‑3.5 with temperature $0.5$ for generation, extracting $R=10$ rules per class, ensembling over $T=20$ trials, and training the linear weights with Adam (LR=$0.01$) for $200$ epochs with cross-validation to pick epochs. The parsing step uses the LLM to produce executable code that applies the natural-language thresholds to raw feature values, rather than relying on brittle regex-only parsing.

Broader conceptual view
Intuitively this is a form of “prior + data” hybridization: the LLM supplies potentially useful hypothesis cuts (prior-informed inductive bias), the few examples $n$udge which cuts are plausible for this dataset, and a downstream statistical learner (low-capacity, regularized by non-negativity, thresholding and ensembling) performs selection and smoothing. That pipeline shifts the risk of overfitting from the LLM’s raw textual thresholds into a controllable ML stage where standard regularization and ensembling reduce variance.

What the paper does not do
FeatLLM does not pre-discretize continuous features globally before prompting, nor does it hard-constrain thresholds to bins derived from the data (e.g., quantiles). Thresholds are proposed by the LLM and then evaluated/tuned downstream. If you want even stronger protection against idiosyncratic cutpoints, you could augment the pipeline (not in the paper) by: (a) adding candidate thresholds derived from data quantiles into the prompt, (b) increasing ensemble size, or (c) adding explicit weight regularization (L1/L2) when training the linear model.

Takeaway
Thresholds in FeatLLM come from both LLM prior knowledge and the few-shot examples (by design). Overfitting is mitigated by turning thresholds into many binary features, learning non-negative feature weights, filtering low-weight features, and averaging over multiple randomized rule generations via bagging/ensemble. These elements together make the learned cutpoints stable and useful even in the few-shot regime.
