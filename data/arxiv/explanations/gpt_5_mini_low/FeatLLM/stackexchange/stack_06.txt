\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How are categorical features and multi-valued categories represented in rules and parsing?
Question:
For categorical columns with many levels (e.g., dozens or hundreds), how does the LLM express rules—single-category equality, sets of categories, or regex-like patterns? Does the response template explicitly allow OR-clauses over categories, and can the parser robustly translate natural language descriptions of sets into code (e.g., {"A", "B", "C"})? How do you handle high-cardinality categories where enumerations inflate prompt length or lead to brittle parsing?
Answer:
Short answer: The paper handles categorical and multi-valued categories by (1) instructing the LLM to produce rules using simple logical forms (it explicitly allows $AND/OR$ combinations), (2) constraining the response format for easier parsing, and (3) parsing the (noisy) natural-language rules back to executable code by asking the LLM itself to emit small Python code snippets which are then executed. For high‑cardinality categories the framework avoids always enumerating everything by giving the LLM category examples in the prompt, using bagging/ensembling to avoid gigantic prompts, and relying on the downstream weight‑tuning and ensembling to filter brittle or spurious enumerations.

Why and how this works (intuitive + concrete):

The paper’s design has three pieces that determine how categorical conditions appear and are translated to code.

1) Prompt + response format guides the LLM to produce rule forms you can parse. In Section 3.1 the authors say the prompt contains feature descriptions (including type and optionally “examples of the possible categories”), reasoning instructions, and a response instruction that specifies the required format for rules. The prompt explicitly permits the LLM to combine conditions with logical operators ($AND/OR$) and to choose a format appropriate to the feature type. So you should expect rules like “feature X equals $\text{'A'}$” or “feature Y is in $\{A, B, C\}$” or compound conditions joined with $OR/AND$. That explicit formatting guidance is what lets the system extract structured rule-like text instead of arbitrary prose.

2) Parsing is done by asking the LLM to generate small code snippets rather than writing a brittle hand-coded parser. The authors point out that the LLM’s outputs can have syntactic variability (e.g., “$>$” vs “greater than”), so instead of building a complex parser they feed the inferred rules + a function signature back into the LLM and ask it to produce Python code that implements those rules. That generated code is executed via Python’s exec(). This leverages the LLM’s tolerance for surface variation and its ability to emit code that captures the semantics of “category in $\{\dots\}$”, equality tests, prefix checks, numeric comparisons, etc. The paper emphasizes this approach as more robust than naive string parsing because the LLM maps noisy natural-language rule text into executable logic.

3) Handling high-cardinality categories and avoiding prompt bloat. The paper acknowledges (Section 1 and Prompt Design) that long prompts and big enumerations are a problem. They mitigate this in two concrete ways: (a) when describing features you can provide a few example categories rather than listing hundreds, and (b) they use feature bagging + ensembling: each trial asks the LLM about a subset of features (and randomizes demonstrations) so you never have to encode all columns and every category in a single prompt. Bagging thus keeps prompt size manageable and creates diverse, smaller rule sets whose ensemble compensates for partial coverage. Practically, this means the LLM will often propose grouped/set rules (e.g., “in $\{A,B,C\}$” or “categories starting with 'NY'”) rather than raw full enumerations, and even if it enumerates too much the tuning stage (learning non-negative weights on boolean rule-features) downweights brittle or unhelpful rules.

Practical implications and recommendations consistent with the paper

- Use the response-instruction slot to force canonical, parseable forms (e.g., require that set membership be written as "in $\{A, B, C\}$" or equality as $\text{== 'A'}$). The paper shows this is what they do to ease downstream parsing.
- Provide a short representative list of categories in the feature description instead of a full dump when cardinality is large; that cues the LLM toward typical values or sensible groupings.
- Encourage the LLM to produce grouped rules (e.g., “is one of $\{\dots\}$”, “starts with”, “contains”) instead of raw enumerations; the paper allows logical operators and type-based formatting so this is compatible with FeatLLM’s design.
- Rely on bagging/ensembling to avoid putting every categorical level into one prompt; the paper explicitly uses bagging to reduce prompt size and then ensembles multiple trials.
- Expect the tuning step (learning weights for rule-features) to filter out brittle enumerations: rules that don't help the held‑out few shots get near-zero weights and have minimal effect on final predictions.

Limitations called out by the paper

The authors explicitly note that LLM outputs can vary syntactically and that parsing remains a challenge; that is precisely why they use the LLM to emit parsing code. They also set a fixed number of rules per class (10 in their experiments) to avoid exploding the feature set, which is a pragmatic constraint when categories are many. Finally, although FeatLLM reduces the need to enumerate everything, if the underlying task truly requires treating every level of a high-cardinality categorical variable distinctly the method will need either more sophisticated grouping heuristics or more training examples to learn importance — a point the authors flag under future work.

In short: the framework expects categorical rules to appear as equality tests or set-membership and allows $AND/OR$ combinations; it constrains response format to make parsing feasible and, instead of brittle hand-parsing, uses the LLM again to turn rules into executable code. For high-cardinality categories the paper recommends (and implements) giving example values, asking the LLM for grouped/set-style rules, and using bagging/ensembling and weight tuning to avoid prompt bloat and brittle enumerations.
