\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Why fix the number of rules per class (e.g., 10), and how sensitive is performance?
Question:
The paper fixes the number of rules per class to 10 and shows minimal sensitivity, yet acknowledges trade-offs with prompt length and overfitting. Conceptually, some tasks may need fewer, more general rules, while others may benefit from many specialized rules. Did you try adaptive stopping criteria (e.g., based on validation improvement or rule novelty)? Also, do you allow nested logic or only flat conjunctions/disjunctions per rule, and how does expressivity trade off against interpretability and stability?
Answer:
Short answer: we fixed $10$ rules per class mainly for practical trade-offs (prompt length, parsing reliability, and overfitting) and because our hyper-parameter sweeps showed little sensitivity around that choice. The paper does allow simple combinations (AND / OR) in rule text and relies on the LLM to parse rules to executable code, but it does not attempt deep nested logical programs. Allowing richer nesting would increase expressivity but also make parsing, stability, and interpretability worse; the paper instead uses weighting + ensembling to control capacity and prune irrelevant rules.

Why “$10$ rules per class” and how sensitive is performance
The Methods and Hyper-parameter Analysis sections explain the reasoning. We fix a constant number of rules per class to avoid two practical failure modes: overly long prompts (LLM input limits and cost) and generating so many features that the downstream few-shot learner overfits. Empirically (Fig. $8$ / Appendix hyper-parameter plots) changing the number of rules did not yield statistically significant gains, so the authors picked $10$ as a sensible operating point that balances (1) adding enough candidate conditions to capture different informative patterns and (2) keeping prompt size and downstream feature dimensionality modest. They explicitly state performance “improves with more ensembles” but that rule-count gains converge and “more rules enlarge input dimensionality … yet also result in overfitting in the low-shot regime.” So sensitivity was measured and found minimal around the chosen value; the choice is pragmatic rather than theoretically optimal.

Did the paper try adaptive stopping (validation improvement or novelty)?
The paper does not report using an adaptive stopping rule for “generate until no improvement” or “stop when rules are novel.” Instead, the design choices to control rule quality are: (a) constrain the prompt and response formatting so the LLM produces a fixed set per class, (b) parse LLM-produced rules into binary features, and (c) learn non-negative linear weights on those binary features (Eq. $1$) so training can down-weight or effectively ignore irrelevant rules. In addition, ensembling with bagging and randomness in prompts helps robustness: useful rules tend to recur across trials, while spurious ones are diluted.

If you want an adaptive approach (not in the paper) that remains consistent with the framework, reasonable options are: use a small validation set and add rules iteratively while monitoring validation AUC, stop when marginal gain falls below a threshold, or accept only rules whose parsed binary feature has minimum support/confidence with the label. Another practical method compatible with the paper’s parsing step is to generate a larger candidate pool in a few LLM calls and then select a subset via forward selection (greedy) or L1 regularization on the linear weights. These were not reported in the paper but would be straightforward extensions.

Nested logic vs. flat conjunctions/disjunctions, and expressivity vs. interpretability/stability
The paper’s response instructions allow the LLM to combine atomic conditions with logical operators (the authors note “Without additional guidance, the LLM can combine multiple rules using logical operators like AND or OR”), and the parsing step uses the LLM itself to generate executable code from the textual rules. Practically, that means rules can express simple conjunctions/disjunctions (e.g., “if age > 60 and cholesterol > X then ...”) but the paper does not pursue or demonstrate deep, nested logical programs (long chains of if/else, nested exceptions, recursion, etc.). The reasons are:

- Parsing reliability: deeper nesting increases syntactic variability in LLM output and parsing becomes fragile. The paper mitigates parsing noise by prompting the LLM to output parseable code and executing it, but complex nested logic would raise parsing risk and execution errors.
- Interpretability: simple rules (single conditions or short conjunctions/disjunctions) remain human-readable and actionable. As soon as you allow arbitrarily nested logic the feature semantics become harder to inspect and trust, which undercuts one of the paper’s stated benefits (interpretable rule-features for downstream models).
- Statistical stability: with small $k$-shot training sets, high-capacity logical structures easily overfit. The paper addresses this by learning non-negative linear weights to down-weight weak rules and using ensembling to average out spurious rule sets. Richer logic would increase the number of effective parameters / feature combinations and worsen overfitting unless you substantially increase data or add strong regularization.

How expressivity trades off against interpretability and stability in this setup
There is the standard bias–variance/interpretability trade-off: more expressive rule languages can capture complex decision boundaries with fewer rules, but they hurt interpretability, are harder to parse robustly from free-form LLM output, and are unstable under few-shot sampling. The authors choose a middle ground: allow useful compositionality (AND/OR) but keep rules short and fix count per class to control dimensionality. Then they rely on three mechanisms to keep expressivity useful but not harmful: (1) LLM-guided rule generation that uses prior knowledge to focus on likely informative features, (2) learning positive weights that prune irrelevant rules, and (3) ensembling/bagging to reduce variance from occasional bad rule-sets.

Practical suggestions consistent with the paper
If you want to experiment beyond the paper’s setup while staying close to its philosophy, try one of these low-effort extensions: generate a bigger candidate pool (e.g., $30$ rules per class in a few calls), then prune using validation AUC or an L1-regularized positive-weight linear model; enforce simple syntactic templates for nesting depth (limit to $2$ clauses) to get more expressivity while keeping parsing stable; or use rule-support / confidence thresholds (as in association-rule mining) as an acceptance criterion for rules. The paper’s framework already supports these interventions because parsing yields executable binary features and the downstream learning step is modular.

Summary
The fixed $10$-rule choice is a pragmatic, empirically validated compromise: it gave reliable performance without bloating prompts or feature space and avoided overfitting in low-shot regimes. The paper did not implement adaptive stopping or deep nested logic; instead it focuses on short compositional rules, LLM-based parsing into code, weight tuning to filter rules, and ensemble bagging for robustness. Adaptive rule-selection and constrained nesting are natural, compatible extensions to try next, but each increases implementation complexity and must be balanced against parsing reliability and low-shot stability.
