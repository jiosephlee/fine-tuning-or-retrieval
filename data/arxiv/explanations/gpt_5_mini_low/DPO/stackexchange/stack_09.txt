\title{Stack Exchange of the Paper: "Direct Preference Optimization: Your Language Model is Secretly a Reward Model"}

### How do we avoid backpropagating through $\pi_{\text{ref}}$ in practice, and does its parameterization matter?
Question:
Eq. (8) contains $\log \frac{\pi_{\theta}(y\mid x)}{\pi_{\text{ref}}(y\mid x)}$. My understanding is that $\pi_{\text{ref}}$ is a frozen model used only to compute the denominator’s log-prob. In implementation, do we detach $\pi_{\text{ref}}$ entirely (no gradients)? Also, does it matter if $\pi_{\text{ref}}$ shares the same tokenizer or architecture as $\pi_\theta$? If not, how do we ensure sequence log-probs are comparable (e.g., consistent handling of BOS/EOS, tokenization differences)?
Answer:
Short answer: Yes — treat $\pi_{\text{ref}}$ as fixed (no gradients) in practice, and yes, the choice/implementation of $\pi_{\text{ref}}$ matters for numerical comparability (tokenization, BOS/EOS, length handling) but not for the theory beyond being a reference distribution close to the data-generating policy. Concretely: detach or keep a separate frozen copy of $\pi_{\text{ref}}$; compute sequence log-probabilities under the same tokenization and prefix/termination conventions used for $\pi_{\theta}$ (or precompute/store the reference log-probs), and initialize $\pi_{\text{ref}}$ to the SFT model used to sample the preference data (or fit a likelihood model on preferred completions if SFT is unavailable), as recommended in the paper.

Explanation and practical checklist grounded in the paper
1) Backpropagation: the paper treats $\pi_{\text{ref}}$ as the fixed reference policy in the KL-regularized objective (Eq. (3) / Eq. (RL) and then in the DPO loss Eq. (11)). In implementation you should not backpropagate through $\pi_{\text{ref}}$. That means either (a) keep $\pi_{\text{ref}}$ as a frozen model (parameters not updated), or (b) if $\pi_{\text{ref}}$ is implemented from the same underlying parameters as $\pi_{\theta}$ at initialization, you must explicitly detach the computations that produce $\log \pi_{\text{ref}}(y\mid x)$ so gradients do not flow into that copy. The DPO gradient (see the paper) only contains gradients of $\log \pi_{\theta}$ and treats $\pi_{\text{ref}}$ as a constant in the term
$\hat r_{\theta}(x,y) = \beta \log \frac{\pi_{\theta}(y\mid x)}{\pi_{\text{ref}}(y\mid x)}$.

2) Why freeze $\pi_{\text{ref}}$? Conceptually $\pi_{\text{ref}}$ is the baseline/reference distribution that defines the KL constraint. If you allow gradients into $\pi_{\text{ref}}$ you change the optimization problem: the denominator is no longer a fixed reference and the theoretical derivation that maps preferences \rightarrow policy (the reparameterization in Eq. (10) and the DPO objective Eq. (11)) no longer holds. Practically, updating $\pi_{\text{ref}}$ risks collapsing the KL-term and destabilizing training.

3) Does parameterization / architecture / tokenizer of $\pi_{\text{ref}}$ matter? The theory (Theorem 1) only requires some reference distribution $\pi_{\text{ref}}$ and shows reward classes can be represented via $\beta \log(\pi/\pi_{\text{ref}})$. But for correct, stable, and meaningful training you must ensure that the sequence log-probabilities you plug into the DPO loss are comparable across $\pi_{\theta}$ and $\pi_{\text{ref}}$. In practice that implies the following must be consistent:

- Tokenization and vocabulary: $\pi_{\theta}$ and $\pi_{\text{ref}}$ should use the same tokenizer and vocabulary so that the same sequence $y$ is decomposed into the same token sequence and the same per-token probabilities are comparable. If tokenization differs, $\log \pi(y\mid x)$ values are not directly comparable because the factorization (and number of tokens) changes.

- BOS/EOS and prefix handling: include the same BOS token (if any) and the same EOS handling when computing sequence log-probabilities. The DPO objective and the KL are sequence-level sums of per-token log-probs (the paper refers to sequence-level KL). If one model includes or omits an EOS/BOS in its probability, the ratio will be inconsistent.

- Padding and attention masks: when computing per-token log-probs for variable-length generations, use identical padding/length-masking conventions so that sums over timesteps match.

- Numerical normalization: both models must compute true (normalized) token probabilities (softmax over the same vocabulary). If $\pi_{\text{ref}}$ is an unnormalized score or uses a different normalization trick, results will be invalid.

If you cannot make $\pi_{\text{ref}}$ share tokenizer/arch with $\pi_{\theta}$, you must at minimum compute and store the sequence log-probabilities for the dataset under the reference model (precompute $\log \pi_{\text{ref}}(y\mid x)$ as scalars) and then use those frozen numbers in the DPO loss. Precomputing removes the need for runtime tokenization parity, but you must be careful that the stored log-probs were computed under the same tokenization convention that you will use when evaluating/comparing.

4) Practical recommendations from the paper and implementation notes
- Use $\pi_{\text{ref}} = \pi^{\text{SFT}}$ when available, because the preference dataset was sampled from that model in the usual RLHF pipeline; the paper explicitly recommends initializing $\pi_{\text{ref}}$ to $\pi^{\text{SFT}}$. If you do not have that SFT model, fit $\pi_{\text{ref}}$ by maximizing likelihood of the preferred completions (the paper says: $\pi_{\text{ref}} = \arg\max_{\pi}\ \mathbb{E}_{x,y_w\sim\mathcal{D}} \log \pi(y_w\mid x)$), which produces a reference distribution that is closer to the data distribution used to collect preferences and reduces distribution shift.

- Freeze $\pi_{\text{ref}}$ during DPO training. Either keep a separate model instance that is not updated, or detach its outputs (e.g., compute log-probs with torch.no_grad / jax.stop_gradient and treat them as constants).

- If both models share the same implementation and weight initialization (common when you start $\pi_{\theta}$ from $\pi^{\text{SFT}}$), keep two model objects: one frozen reference copy and one trainable policy copy. This avoids accidental shared-parameter updates.

- If you precompute $\log \pi_{\text{ref}}(y\mid x)$ for the dataset, store the full sequence log-prob (sum of token log-probs including EOS) and use that scalar in the DPO loss. This is often convenient and eliminates runtime cost and gradient concerns.

- When evaluating KL or frontier metrics (as in the experiments), compute the same sequence-level log-probs for both models using the same tokenization and termination rules; sequence-level KL is the sum over token-level KLs according to the paper's evaluation.

5) Edge cases and pitfalls
- Different tokenization lengths change the additive sequence log-prob. A longer tokenization (more tokens) tends to produce more negative log-probs; comparing two models with different tokenizations can spuriously favor one model in the DPO ratio. Always align tokenization.

- Sampling/decoding differences do not affect the training loss if you compute exact likelihoods under the models. But if the preference dataset was created with sampling procedures that rely on different decoding (e.g., nucleus sampling vs. greedy), the empirical distribution of $y$ may differ; that’s why the paper recommends $\pi_{\text{ref}}$ approximate the sampler that produced the dataset (use $\pi^{\text{SFT}}$).

- If you must use a different tokenizer/arch for operational reasons (e.g., a smaller reference model), precompute the reference log-probs under that model and use them as frozen scalars; but interpret results cautiously—DPO’s theoretical guarantees assume the reference distribution in the denominator matches the one used in the derivation.

Summary
Treat $\pi_{\text{ref}}$ as a frozen reference (no gradients) and make sure sequence log-probabilities are computed consistently for $\pi_{\theta}$ and $\pi_{\text{ref}}$ (same tokenizer, BOS/EOS, masking, and normalization). The paper explicitly recommends initializing $\pi_{\text{ref}}$ to the SFT model that produced samples used to collect preferences, or fitting a maximum-likelihood reference when SFT is unavailable, and using that frozen reference in the DPO loss.
