\title{Blogs about the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

# Why AI Might Stop Using Tokens: Inside the Byte Latent Transformer

Large language models have been built around a simple trick: before the model sees text, a tokenizer chops it into tokens. Those tokens are usually subword chunks, and the model predicts the next token rather than the next character or byte.

That design has worked extremely well. But it also creates a hidden constraint: the model does not learn directly from raw text. It learns from a compressed, preprocessed version of text whose boundaries are fixed ahead of time. The Byte Latent Transformer, or BLT, is a new architecture that challenges that assumption.

The core idea is straightforward: instead of forcing text into a fixed vocabulary of tokens, BLT reads raw bytes and groups them into dynamic patches. Those patches are not chosen from a predefined list. They are formed on the fly, based on how predictable the next bytes are. In other words, BLT spends more compute where the text is hard and less where it is easy.

## Why tokenization is a problem

Tokenization is often treated as a boring implementation detail. In practice, it shapes how the model sees language.

A tokenizer decides which byte sequences become units of computation. That can be useful, but it also introduces bias. A word may be split one way in one context and differently in another. Text with unusual spelling, noisy formatting, or non-English scripts can be awkward for a fixed vocabulary. The paper points out several consequences: sensitivity to input noise, weaker orthographic knowledge, and inequities across languages.

There is also an efficiency issue. Standard token-based models process every token with roughly the same amount of compute, even though some predictions are much easier than others. Predicting the last few letters of a common word is not the same problem as choosing the first word in a sentence, yet traditional architectures often treat them similarly.

## From tokens to bytes to patches

BLT removes tokenization entirely. It starts from raw bytes, which are the basic building blocks of text encoding. But processing bytes one by one is expensive, because sequences become much longer.

The trick is to group bytes into patches. A patch is just a contiguous chunk of bytes that BLT treats as a unit for part of the computation. The important part is that patches are dynamic. BLT does not use a fixed patch size everywhere. Instead, it segments text based on the entropy of the next-byte prediction.

Entropy here is a measure of uncertainty. If the model is very unsure about what byte comes next, that region is considered more complex and deserves more compute. If the next bytes are easy to predict, BLT can use a larger patch and move through the sequence more cheaply.

That gives BLT a built-in form of adaptive computation. It is not trying to think equally hard about every byte.

## The architecture in plain English

BLT has three main parts.

First, there is a small local encoder that reads bytes and turns them into patch representations. This local encoder is lightweight, so it can process byte sequences efficiently.

Second, there is a large global transformer that operates on the patches. This is where most of the model’s capacity lives. Because it runs on patches rather than every byte, it does not need to do full heavy computation at every position.

Third, there is a local decoder that turns the patch-level representations back into bytes for generation.

The paper also adds a few important ingredients to make byte modeling work well in practice. One is hash-based $n$-gram embeddings, which give the model information about short byte sequences like 3-grams through 8-grams. Another is cross-attention between bytes and patches, which helps the local and global parts exchange information.

So BLT is not “just bytes.” It is a carefully designed system that lets byte-level modeling scale.

## Why dynamic patches matter

A fixed patch size would already reduce the cost of processing bytes, but it would still be rigid. BLT goes further by making patch size depend on the input.

This matters because not all text has the same structure. Some spans are repetitive and easy to compress. Others are information-dense, such as math, code, or the beginning of a new sentence. BLT can allocate more transformer steps to the hard parts and fewer to the easy ones.

The paper compares several patching strategies:

- fixed-size patches,
- whitespace-based patches,
- entropy-based patches.

Whitespace patching already helps by treating words as natural units. But entropy patching is more flexible. It does not rely on a hand-built rule about spaces. Instead, it uses a small byte-level language model to estimate uncertainty and choose boundaries.

That is the main architectural move behind BLT: use data-dependent patching to allocate compute where it matters.

## What the experiments show

The headline result is that BLT matches tokenization-based models at scale.

The paper reports a flop-controlled scaling study up to 8B parameters and 4T training bytes. Under those controlled comparisons, BLT matches the performance trends of Llama 3 while using up to 50% fewer inference flops in some settings. That is a significant result, because earlier byte-level models tended to fall behind at scale.

The study also shows something else interesting: patches can scale better than tokens. Because longer patches reduce the number of times the global transformer has to run, compute can be “reinvested” into making that global transformer larger. This creates a new scaling dimension that token-based systems do not have in the same way. With BLT, you can increase both model size and patch size while keeping inference cost fixed.

In the paper’s fixed-inference scaling experiments, this leads to better scaling trends than tokenization-based architectures. In practical terms, that means BLT can sometimes trade one kind of compute for another and come out ahead.

## Better robustness, especially on messy text

One of the strongest advantages of byte-level modeling is robustness.

Since BLT operates directly on bytes, it is less fragile when text is noisy or unusual. The paper evaluates this by adding character-level noise such as random casing, dropped characters, repeated characters, and uppercase transformations. BLT is more robust than tokenizer-based models on these corrupted inputs.

That makes intuitive sense. If a model only sees tokenized chunks, then odd spelling or formatting can break familiar token boundaries. A byte-level model is less dependent on those boundaries.

The paper also finds strong results on character-aware tasks. BLT does well on grapheme-to-phoneme conversion, orthographic reasoning, and a benchmark called CUTE that tests understanding of spelling and character manipulation. It also performs well on low-resource machine translation, especially for language pairs with less training data or more diverse scripts.

These are all areas where direct access to bytes seems to help.

## Can BLT start from a token model?

The paper explores an interesting hybrid path: initializing BLT from a pretrained Llama 3.1 model.

This is described as “byte-ifying” a tokenizer-based model. The idea is to reuse the global transformer weights from the pretrained token model and then train the byte-level parts around it. In their experiments, this setup improves training convergence and can outperform baseline BLT models trained from scratch under the same flop budget.

This suggests a possible migration path from token-based systems to byte-based ones. Instead of throwing away existing pretrained models, you can adapt them into a tokenizer-free architecture.

## Why this matters

BLT is important because it shows that tokenization is not required for large-scale language modeling.

For years, tokenization was the default because it made training tractable. Raw bytes were too expensive. BLT changes that equation by introducing dynamic patching and a split architecture that concentrates compute where it is most useful.

The result is a model that:

- reads raw bytes instead of fixed tokens,
- adapts its compute to the complexity of the input,
- matches token-based models at scale,
- improves robustness to noise,
- and opens up a new scaling strategy based on patch size.

That does not mean tokenizers are disappearing tomorrow. The paper itself notes limitations, including the need for further optimization and better scaling laws specific to BLT. But it does show that the field has a credible alternative to fixed-vocabulary text processing.

If tokenization was the compromise that made large language models possible, BLT is a strong argument that the compromise may no longer be necessary.
