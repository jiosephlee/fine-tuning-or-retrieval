# Why AI Might Stop Using Tokens: Inside the Byte Latent Transformer

Large language models have been built around a simple trick: before the model sees text, a tokenizer chops it into tokens. Those tokens are usually subword chunks, and the model predicts the next token rather than the next character or byte.

That design has worked extremely well. But it also creates a hidden constraint: the model does not learn directly from raw text. It learns from a compressed, preprocessed version of text whose boundaries are fixed ahead of time. The Byte Latent Transformer, or BLT, is a new architecture that challenges that assumption.

The core idea is straightforward: instead of forcing text into a fixed vocabulary of tokens, BLT reads raw bytes and groups them into dynamic patches. Those patches are not chosen from a predefined list. They are formed on the fly, based on how predictable the next bytes are. In other words, BLT spends more compute where the text is hard and less where it is easy.

## Why tokenization is a problem

Tokenization is often treated as a boring implementation detail. In practice, it shapes how the model sees language.

A tokenizer decides which byte sequences become units of computation. That can be useful, but it also introduces bias. A word may be split one way in one context and differently in another. Text with unusual spelling, noisy formatting, or non-English scripts can be awkward for a fixed vocabulary. The paper points out several consequences: sensitivity to input noise, weaker orthographic knowledge, and inequities across languages.

There is also an efficiency issue. Standard token-based models process every token with roughly the same amount of compute, even though some predictions are much easier than others. Predicting the last few letters of a common word is not the same problem as choosing the first word in a sentence, yet traditional architectures often treat them similarly.

## From tokens to bytes to patches

BLT removes tokenization entirely. It starts from raw bytes, which are the basic building blocks of text encoding. But processing bytes one by one is expensive, because sequences become much longer.

The trick is to group bytes into patches. A patch is just a contiguous chunk of bytes that BLT treats as a unit for part of the computation. The important part is that patches are dynamic. BLT does not use a fixed patch size everywhere. Instead, it segments text based on the entropy of the next-byte prediction.

Entropy here is a measure of uncertainty. If the model is very unsure about what byte comes next, that region is considered more complex and deserves more compute. If the next bytes are easy to predict, BLT can use a larger patch and move through the sequence more cheaply.

That gives BLT a built-in form of adaptive computation. It is not trying to think equally hard about every byte.

## The architecture in plain English

BLT has three main parts.

First, there is a small local encoder that reads bytes and turns them into patch representations. This local encoder is lightweight, so it can process byte sequences efficiently.

Second, there is a large global transformer that operates on the patches. This is where most of the model’s capacity lives. Because it runs on patches rather than every byte, it does not need to do full heavy computation at every position.

Third, there is a local decoder that turns the patch-level representations back into bytes for generation.

The paper also adds a few important ingredients to make byte modeling work well in practice. One is hash-based $n$-gram embeddings, which give the model information about short byte sequences like 3-grams through 8-grams. Another is cross-attention between bytes and patches, which helps the local and global parts exchange information.

So BLT is not “just bytes.” It is a carefully designed system that lets byte-level modeling scale.

## Why dynamic patches matter

A fixed patch size would already reduce the cost of processing bytes, but it would still be rigid. BLT goes further by making patch size depend on the input.

This matters because not all text has the same structure. Some spans are repetitive and easy to compress. Others are information-dense, such as math, code, or the beginning of a new sentence. BLT can allocate more transformer steps to the hard parts and fewer to the easy ones.

The paper compares several patching strategies:

- fixed-size patches,
- whitespace-based patches,
- entropy-based patches.

Whitespace patching already helps by treating words as natural units. But entropy patching is more flexible. It does not rely on a hand-built rule about spaces. Instead, it uses a small byte-level language model to estimate uncertainty and choose boundaries.

That is the main architectural move behind BLT: use data-dependent patching to allocate compute where it matters.

## What the experiments show

The headline result is that BLT matches tokenization-based models at scale.

The paper reports a flop-controlled scaling study up to 8B parameters and 4T training bytes. Under those controlled comparisons, BLT matches the performance trends of Llama 3 while using up to 50% fewer inference flops in some settings. That is a significant result, because earlier byte-level models tended to fall behind at scale.

The study also shows something else interesting: patches can scale better than tokens. Because longer patches reduce the number of times the global transformer has to run, compute can be “reinvested” into making that global transformer larger. This creates a new scaling dimension that token-based systems do not have in the same way. With BLT, you can increase both model size and patch size while keeping inference cost fixed.

In the paper’s fixed-inference scaling experiments, this leads to better scaling trends than tokenization-based architectures. In practical terms, that means BLT can sometimes trade one kind of compute for another and come out ahead.

## Better robustness, especially on messy text

One of the strongest advantages of byte-level modeling is robustness.

Since BLT operates directly on bytes, it is less fragile when text is noisy or unusual. The paper evaluates this by adding character-level noise such as random casing, dropped characters, repeated characters, and uppercase transformations. BLT is more robust than tokenizer-based models on these corrupted inputs.

That makes intuitive sense. If a model only sees tokenized chunks, then odd spelling or formatting can break familiar token boundaries. A byte-level model is less dependent on those boundaries.

The paper also finds strong results on character-aware tasks. BLT does well on grapheme-to-phoneme conversion, orthographic reasoning, and a benchmark called CUTE that tests understanding of spelling and character manipulation. It also performs well on low-resource machine translation, especially for language pairs with less training data or more diverse scripts.

These are all areas where direct access to bytes seems to help.

## Can BLT start from a token model?

The paper explores an interesting hybrid path: initializing BLT from a pretrained Llama 3.1 model.

This is described as “byte-ifying” a tokenizer-based model. The idea is to reuse the global transformer weights from the pretrained token model and then train the byte-level parts around it. In their experiments, this setup improves training convergence and can outperform baseline BLT models trained from scratch under the same flop budget.

This suggests a possible migration path from token-based systems to byte-based ones. Instead of throwing away existing pretrained models, you can adapt them into a tokenizer-free architecture.

## Why this matters

BLT is important because it shows that tokenization is not required for large-scale language modeling.

For years, tokenization was the default because it made training tractable. Raw bytes were too expensive. BLT changes that equation by introducing dynamic patching and a split architecture that concentrates compute where it is most useful.

The result is a model that:

- reads raw bytes instead of fixed tokens,
- adapts its compute to the complexity of the input,
- matches token-based models at scale,
- improves robustness to noise,
- and opens up a new scaling strategy based on patch size.

That does not mean tokenizers are disappearing tomorrow. The paper itself notes limitations, including the need for further optimization and better scaling laws specific to BLT. But it does show that the field has a credible alternative to fixed-vocabulary text processing.

If tokenization was the compromise that made large language models possible, BLT is a strong argument that the compromise may no longer be necessary.



# Patches, Not Tokens: How BLT Learns to Spend Compute Where It Matters

Large language models usually rely on tokenization: text is broken into a fixed vocabulary of subword pieces, and the model processes one token at a time. That works well, but it also forces every token to get the same amount of compute, even when some parts of the text are easy to predict and others are genuinely hard.

The Byte Latent Transformer, or BLT, takes a different approach. Instead of starting from a fixed vocabulary, it works directly on raw bytes and groups them into dynamic patches. The key idea is simple: predictable text should be compressed into larger patches, while uncertain text should be split into smaller ones. That lets BLT spend more of its compute where the next-byte prediction is harder.

## Why fixed tokens waste compute

Tokenization is a convenient heuristic, but it is not always aligned with prediction difficulty. A tokenizer may compress common words into single tokens and rare or messy text into smaller pieces, but the result is still a fixed segmentation scheme. The model then applies roughly the same amount of processing to every token.

BLT argues that this is not the best use of compute. Consider two examples. Completing the word “Mozart” after “Who composed the Magic Flute?” is relatively easy once the model sees the beginning of the answer. By contrast, deciding the first byte of the answer is much harder. These two situations have very different uncertainty, but a token-based model gives them the same basic treatment.

BLT’s solution is to make patch boundaries depend on the data itself.

## Dynamic patching with next-byte entropy

BLT creates patches using a small byte-level language model that estimates the entropy of the next byte at each position. In simple terms, entropy here measures uncertainty: high entropy means the model is less sure what byte comes next, while low entropy means the next byte is easy to guess.

BLT uses these entropy estimates to decide where a new patch should begin. The intuition is that patch boundaries should appear around harder-to-predict regions. When the next-byte distribution is uncertain, BLT cuts the sequence into a new patch. When the text is predictable, it keeps bytes together in a longer patch.

This creates a form of adaptive compression. Easy stretches of text become fewer, larger patches, which means fewer expensive steps in the main transformer. Harder regions are broken up more finely, so the model can devote more capacity to them.

## A smarter way to allocate compute

The architecture behind BLT is built around this idea of variable compute. It has three main pieces: a small local encoder, a large global latent transformer, and a small local decoder.

The local encoder reads bytes and turns them into patch representations. The global transformer operates on those patches and does most of the heavy lifting. The local decoder then turns the patch-level outputs back into bytes. Since the global transformer is the expensive part, running it on fewer patches saves compute. That is the whole point of dynamic patching.

The nice part is that BLT does not just choose a single patch size for the whole model. It can use longer patches where text is predictable and shorter patches where it is not. In other words, it allocates more transformer steps only when the input actually deserves them.

## Why entropy-based patching matters

The paper compares several patching strategies, including fixed-size patches and whitespace-based patches. Those are useful baselines, but entropy-based patching is the most flexible because it is driven by the actual difficulty of prediction rather than a hand-written rule.

Whitespace patching already gives a hint of the idea: words often make a natural unit, and the beginning of a word is often harder to predict than the rest. Entropy patching generalizes that intuition. It does not assume that word boundaries are always the right place to split. Instead, it uses a learned estimate of uncertainty to decide where compute should be spent.

That matters because text is not uniform. Code, math, multilingual text, and noisy inputs all have different structure. A fixed segmentation scheme cannot adapt to those differences, but entropy-based patching can.

## The result: longer patches when text is easy

The paper shows that BLT can scale with average patch sizes larger than the average byte count per token used by tokenizer-based models. In the experiments, larger patches reduce inference flops because the global transformer runs less often. Those saved flops can be used to grow the model itself, which creates a new scaling tradeoff.

This is the core insight behind “patches scale better than tokens.” Tokens are constrained by a fixed vocabulary, so increasing token size quickly runs into tradeoffs in the embedding and output layers. BLT avoids that bottleneck because patches are not drawn from a fixed vocabulary. Their size can vary dynamically, and the model can keep getting more efficient as patch size grows.

## Why this helps in practice

The paper reports two broad benefits from direct byte modeling with dynamic patches.

First, BLT is more robust to noisy inputs. Because it sees raw bytes, it is less brittle when text includes unusual capitalization, dropped characters, or other perturbations that can confuse tokenizers.

Second, BLT shows stronger character-level understanding. That includes spelling-sensitive tasks, grapheme-to-phoneme conversion, and low-resource machine translation. These are all areas where byte-level information matters more than a tokenizer’s predefined units.

So the advantage is not just theoretical efficiency. Better patching also seems to improve how the model handles the long tail of text.

## The big picture

BLT’s main innovation is not simply “remove tokenization.” It is to replace fixed token boundaries with dynamic patch boundaries chosen from next-byte entropy. That allows the model to compress easy regions aggressively and spend extra compute on difficult ones.

This is a more adaptive way to run a language model. Instead of treating every token as equally important, BLT asks a better question: where is the text hard enough to justify more computation?

That question leads to patches, not tokens.



# Can Byte-Level AI Be Faster Too? The Efficiency Story Behind BLT

Large language models usually rely on tokenizers: they split text into a fixed vocabulary of subword pieces, and the model predicts one token at a time. That setup has a nice practical benefit: it shortens sequences, which keeps computation manageable. But it also bakes in a rigid unit of computation. Every token gets roughly the same amount of model effort, even when some parts of the text are easy and others are much harder.

The Byte Latent Transformer, or BLT, takes a different route. It works directly on raw bytes, but it does not process every byte with the same amount of heavy transformer computation. Instead, it groups bytes into dynamic patches. Easy regions get larger patches, while information-dense regions get smaller ones. That is the core idea behind BLT’s efficiency story: spend more compute where the prediction problem is complex, and less where it is predictable.

## Why byte-level models were considered expensive

A byte-level model sounds attractive in principle. Bytes avoid tokenization artifacts, work across languages and scripts, and preserve exact character-level information. But they also create much longer sequences than subword tokenizers do. If you naively run a transformer over every byte, the cost can become prohibitive.

Earlier byte-level systems tried to deal with this by improving attention efficiency or using alternative architectures. BLT’s paper argues that this helps at small scale, but at large scale the main cost is not attention alone. The feed-forward layers in the transformer dominate the FLOPs, and those layers still run on every step. So the real question is not just how to make byte models possible, but how to make them compute-efficient.

BLT answers that with patching.

## The basic trick: fewer heavy steps

BLT introduces a three-part design:

- a small local encoder that reads bytes,
- a large global latent transformer that operates on patches,
- and a small local decoder that turns patch outputs back into bytes.

The heavy transformer is only applied at patch boundaries, not for every byte. If a patch contains 8 bytes on average, then the global model runs about one-eighth as often as it would on a byte-by-byte sequence. That is where the inference savings come from.

The paper reports that BLT can match the flop-controlled performance of Llama 3 while using up to 50% fewer inference FLOPs. That is a big claim, and it comes from this basic idea: make the expensive part of the model work on fewer, smarter units.

## Why patches are better than fixed tokens

Tokenizers also compress text, but they do it with a fixed vocabulary chosen before training. BLT’s patches are different. They are not predefined symbols; they are dynamically formed groups of bytes.

This matters because tokenization is a one-size-fits-all compression scheme. It does not know whether a region of text is easy to predict or not. BLT tries to align compute with uncertainty instead.

The paper gives a simple intuition: predicting the last letters of a word is often easy once the beginning is known, but predicting the first word after a prompt or a new sentence can be much harder. BLT’s patching scheme tries to reflect that. When the next-byte entropy is low, it can group bytes into longer patches. When entropy rises, it creates new boundaries and gives the global model more chances to reason.

## How BLT decides where to patch

BLT explores several patching strategies. Fixed-size patches are the simplest: every $k$ bytes, start a new patch. That is easy to implement, but it wastes compute on predictable regions and may under-allocate compute to complex ones.

It also tries whitespace-based patching, which starts new patches around spaces and similar boundaries. That is more natural for language, because words often form sensible units. But it still cannot adapt patch size based on how hard the next prediction is.

The most interesting option is entropy patching. BLT trains a small byte-level language model and uses its next-byte entropy estimates to find where uncertainty rises. Those points become patch boundaries. In other words, the model uses a lightweight predictor to decide where the expensive model should step in.

This makes patch size a controllable knob for efficiency. Larger patches mean fewer latent transformer steps, which lowers inference FLOPs. Smaller patches mean more compute and more fine-grained modeling.

## The architecture behind the efficiency gains

The efficiency story only works because BLT separates concerns.

The local encoder is lightweight. It processes bytes and builds patch representations using a small amount of computation. The global latent transformer is the main reasoning engine, but it runs on patch representations rather than raw bytes. The local decoder then maps the patch outputs back to byte sequences.

Two details help make those patch representations more useful. First, the encoder includes hash-based $n$-gram embeddings, which inject information about byte sequences of lengths 3 through 8. Second, the encoder and decoder use cross-attention so that patches can summarize and expand byte-level information efficiently.

The important point is that the heavy transformer is reserved for the places where it is most needed. That is what lets BLT reduce FLOPs without collapsing in quality.

## Larger patches, cheaper inference

One of the paper’s more interesting findings is that patch size itself becomes a new scaling dimension.

With tokenizer-based models, you can increase vocabulary size to reduce sequence length, but that has limits and comes with trade-offs in embedding and output layers. BLT does not have a fixed vocabulary, so it can simply choose larger average patches. Larger patches mean fewer global transformer invocations, which lowers inference cost.

In the paper’s scaling experiments, BLT shows that you can trade that saved compute for a larger global latent transformer. So instead of choosing between “small model with many steps” and “large model with fewer steps,” BLT opens up a third option: a larger model that takes fewer, smarter steps.

That is why the paper’s title is not just about bytes versus tokens. It is about patches scaling better than tokens. With fixed inference cost, BLT can improve as both model size and patch size increase.

## The quality trade-off is surprisingly mild

Efficiency is only useful if the model stays competitive. According to the paper, BLT does.

On compute-controlled training runs, BLT matches or outperforms BPE-based baselines across scaling trends. On downstream tasks, the entropy-patched version outperforms the Llama 3 tokenizer-based model on 4 out of 7 benchmark tasks, while being trained on the same number of bytes and under the same FLOP budget.

The space-patching version is even cheaper at inference, but it gives up more quality. That makes BLT’s main design lesson clear: longer patches can buy you real savings, but dynamic patching is what keeps the quality drop under control.

This is also why entropy patching matters so much. It is not just a compression trick. It is a way to decide when the model should think harder.

## Why this matters for real deployments

For many applications, inference cost matters more than raw training cost. Training a model once is expensive, but serving it repeatedly is where compute bills accumulate.

BLT’s results suggest a practical deployment strategy: spend a bit more flexibility during training and patch selection, then save substantially at inference time. The paper’s fixed-inference scaling study shows that BLT can outperform tokenizer-based architectures under the same inference FLOP budget, especially once training budgets move beyond the compute-optimal regime.

That is a valuable result because it changes the usual assumption that byte-level modeling is automatically too expensive. BLT shows that byte-level inputs do not have to imply byte-level compute everywhere.

## The bigger picture

BLT does not eliminate the need for good engineering, and the paper is clear about limitations. Its entropy model is trained separately, and the implementation may not yet match tokenizer-based systems in wall-clock efficiency. But conceptually, it demonstrates something important: raw-byte modeling can be made scalable if compute is allocated dynamically.

The main efficiency insight is simple but powerful. Don’t force the model to spend the same amount of effort on every byte. Use small local models to understand the raw stream, use patching to identify how much information each region contains, and reserve the large transformer for the places where it actually helps.

That is how BLT makes byte-level AI not just more robust, but potentially faster too.



# Why Byte-Level Models Are Better at Messy Text, Misspellings, and Rare Languages

Large language models usually do not read text as raw characters. They first break it into tokens using a fixed tokenizer, and the model learns over those tokens. That works well in practice, but it also introduces a hidden assumption: the tokenizer decides what the basic units of language are.

The Byte Latent Transformer, or BLT, takes a different approach. It operates directly on bytes and groups them into dynamic patches instead of fixed vocabulary tokens. That design matters more than it might seem at first. In the paper, one of the clearest benefits of BLT is robustness: it handles noisy text, spelling-level transformations, phonology, and low-resource languages better than token-based models in several settings.

## Why bytes help

Tokenizers compress text using a fixed vocabulary, but the resulting units are not always aligned with the structure of the input. A misspelling, odd casing, character repetition, or an unusual script can change how text gets split into tokens. Once that happens, the model is working with a representation that may be brittle or inconsistent.

BLT avoids that problem by keeping direct access to raw bytes. It still compresses computation through patches, but it does not lose the underlying byte sequence. That gives it a more faithful view of spelling, punctuation, subword structure, and character-level variation. The paper argues that this helps especially on long-tail inputs, where tokenizers can be a poor fit.

## Robustness to noisy text

One of the paper’s main robustness tests corrupts benchmark prompts using character-level noise. The authors evaluate five noise patterns:

- converting text to uppercase and spacing out characters,
- randomly dropping 10% of characters,
- randomly changing character case,
- repeating 20% of characters up to four times,
- converting all characters to uppercase.

They apply these changes to the prompt, the completion, or both, and compare BLT to tokenizer-based models.

The result is clear: BLT is more robust across the board. On noisy HellaSwag, the paper reports that BLT outperforms tokenizer-based models by an average of 8 points, even beating a larger Llama 3.1 model trained on much more data. That is a strong sign that raw-byte modeling helps when the input is messy or slightly corrupted.

This makes intuitive sense. A tokenizer can be thrown off by a small formatting change, especially if that change affects how text is segmented into tokens. A byte-level model sees the text more directly, so it is less dependent on brittle preprocessing boundaries.

## Better at spelling and character manipulation

BLT also does much better on tasks that require explicit character-level understanding. The paper evaluates it on the CUTE benchmark, which includes tasks such as:

- understanding composition,
- recognizing orthographic similarity,
- manipulating character sequences.

These tasks are a good stress test for token-based models, because success often depends on knowing how words are spelled, not just what they mean. The paper notes that tokenizer-based models often seem aware of token spellings but struggle to use that information for manipulation.

BLT-Entropy performs especially well here, beating the two Llama 3 tokenizer-based baselines by more than 25 points overall. On spelling tasks, it reaches 99.9%. That is a very strong result, and it suggests that direct byte access gives the model a much better internal handle on letters, substrings, and word structure.

There are a couple of exceptions. Word deletion and insertion are the two tasks where the BPE-based model does better. But the paper frames the gap as narrow, and overall the byte-level model is much stronger on character manipulation.

## Phonology: grapheme to phoneme

Another place where bytes matter is pronunciation. The paper evaluates BLT on grapheme-to-phoneme translation, using the Phonology Bench in a 5-shot setting. Here the task is to map written words to their pronunciations.

BLT outperforms the baseline Llama 3 tokenizer-based model on this task. Again, that is not surprising once you think about the input. Grapheme-to-phoneme mapping is a character-level problem. The model has to reason about spelling patterns, letter combinations, and how written forms map to sounds. A tokenizer may hide useful internal structure, while a byte-level model can work with it directly.

## Low-resource translation and long-tail languages

BLT’s robustness is not limited to English spelling or noisy prompts. The paper also evaluates translation on FLORES-101 across six language families and 21 lower-resource languages with different scripts.

The results show that BLT outperforms the Llama 3 tokenizer-based model overall:

- by 2 points when translating into English,
- by 0.5 points when translating from English.

The gains are especially noticeable on lower-resource language pairs. That is important, because rare languages and non-Latin scripts are exactly where tokenizers tend to struggle most. If a tokenizer does not have a good representation for a script or morphology pattern, the model has to learn on top of a segmentation scheme that may already be suboptimal.

BLT sidesteps that by modeling bytes directly. It still has to learn the language, of course, but it is not forced into a fixed vocabulary that may underrepresent the structure of the input. The paper’s results suggest that this is especially helpful in the long tail, where training data is sparse and orthographic variation is high.

## Why this matters

The key takeaway is not just that BLT is a byte-level model. It is that byte-level access changes what kinds of errors the model can recover from and what kinds of structure it can learn.

In practice, that means better behavior on:

- misspellings and casing changes,
- noisy or corrupted text,
- spelling-aware reasoning,
- pronunciation-related tasks,
- low-resource and multilingual translation.

These are exactly the kinds of cases where tokenization can become a liability. Fixed vocabularies are efficient, but they can hide the character-level information that matters for robust generalization.

BLT shows that you do not necessarily need to give up scale to get these benefits. The paper’s broader result is that a byte-level model can match tokenization-based performance at scale, while being more robust to messy inputs and more sensitive to subword structure.

## The bigger picture

For years, byte-level models were seen as too expensive to scale. BLT changes that by using dynamically sized patches to reduce compute while keeping the model close to raw bytes. That architectural shift is what makes the robustness gains practical rather than just theoretical.

So if you care about noisy real-world text, spelling-sensitive tasks, or translation in underrepresented languages, BLT is an important signal. It suggests that tokenization may not be the only path to strong language modeling. Sometimes, reading text more directly is simply the better choice.



# A New Scaling Law for LLMs? How BLT Changes the Tradeoff Between Model Size and Inference Cost

Large language models have traditionally been scaled along two main axes: more parameters and more training data. But there has always been a third constraint sitting in the background: inference cost. If you want a model that is cheaper to run, you usually have to give up performance, shrink the model, or accept a more constrained tokenizer.

The Byte Latent Transformer, or BLT, proposes a different way to think about this tradeoff. Instead of processing text as a fixed sequence of tokens, it starts from raw bytes and groups them into dynamically sized patches. The key idea is simple but powerful: not every byte needs the same amount of compute. Easy regions of text can be grouped into larger patches, while harder, more unpredictable regions can be split more finely. That lets the model spend its capacity where it matters most.

The result is a scaling story that looks different from the standard tokenizer-based one. In BLT, you can increase patch size and model size at the same time while keeping inference cost fixed. The paper argues that this is one reason “patches scale better than tokens.”

## Why tokenization becomes a bottleneck

Most LLMs rely on a tokenizer that turns bytes into a fixed vocabulary of tokens before the model ever sees the text. That works well, but it also hard-codes a compression scheme. Every token gets the same amount of model compute, even though some tokens are much easier to predict than others.

The paper points out several drawbacks of this approach. Tokenization can be sensitive to domain, input noise, spelling, and language. It also creates a mismatch between how the data is compressed and how much reasoning effort the model actually needs. For example, predicting the rest of a common word is usually much easier than predicting the first word in a new sentence, but a token-based model still spends the same amount of compute on both.

BLT is designed to remove that rigid boundary. It works directly on bytes and only groups them into patches when the model decides it makes sense.

## What BLT changes: compute follows uncertainty

The central innovation in BLT is dynamic patching. Instead of using a fixed stride or a static tokenizer, BLT forms patches based on the entropy of the next-byte prediction from a small byte-level language model.

In practice, this means the model looks at where the next byte is easy to predict and where it is uncertain. Low-entropy regions tend to become larger patches. High-entropy regions get smaller ones. This gives the architecture a way to allocate compute adaptively across the sequence.

That matters because the expensive part of the model is the global transformer operating on patches. Fewer patches mean fewer transformer steps. So if a sequence is predictable, BLT can compress it more aggressively and save compute. Those savings can then be “spent” on a larger global model.

This is the core idea behind the paper’s scaling result: longer patches reduce inference cost, and that cost reduction can be used to scale up the model itself.

## The architecture in one sentence

BLT has three main pieces: a lightweight local encoder that turns bytes into patch representations, a large global transformer that does most of the reasoning over patches, and a lightweight local decoder that turns the patch outputs back into bytes.

The paper also adds hash-based n-gram embeddings and cross-attention between bytes and patches to preserve byte-level information. Those details matter because raw bytes are a much lower-level representation than tokens, and the model needs mechanisms to recover structure efficiently.

But the broad design is straightforward: keep the heavy compute at the patch level, and make patching adaptive.

## The scaling study: up to 8B parameters and 4T training bytes

The paper’s main scaling result is not just that BLT works, but that it scales well.

The authors present a flop-controlled scaling study of byte-level models up to 8 billion parameters and 4 trillion training bytes. They compare BLT to tokenizer-based baselines, including Llama 3-style models, under matched training compute. The headline result is that BLT matches compute-controlled performance at scale, while also improving inference efficiency.

A few points stand out:

- BLT reaches parity with tokenization-based models in compute-controlled training runs.
- It can use larger patch sizes, which lowers inference cost.
- With a patch size of 8 bytes, the paper reports nearly 50% inference flop savings.
- Bigger patch sizes do not just reduce cost; they can also support better scaling as model size increases.

This last point is especially important. The authors show that BLT can simultaneously increase patch size and model size while keeping the same inference budget. That is a different kind of scaling law from the one most LLM work has focused on.

## Why “patches scale better than tokens”

Tokenizers impose a fixed vocabulary. If you want larger units, you usually need a larger vocabulary, which increases the size of the embedding and output layers. That tradeoff limits how far token size can be pushed without making the model expensive in other ways.

BLT avoids that constraint. Its patches do not come from a fixed vocabulary. They are dynamically formed groups of bytes, so patch size can grow without requiring a bigger token table. That creates a new degree of freedom: you can use longer patches to reduce the number of expensive latent transformer steps, then reallocate that compute to a larger model.

The paper’s inference-flop-controlled experiments test exactly this idea. For fixed inference budgets, BLT models with larger patches show better scaling trends than token-based architectures. In other words, once you hold inference cost constant, the extra efficiency from bigger patches can be turned into extra model capacity.

That is why the authors frame this as a new scaling direction. It is not just “make the model bigger.” It is “make the patches bigger too, and use the savings to support a larger model.”

## What the benchmarks say

The paper does not stop at language modeling loss. It also evaluates downstream tasks.

On an 8B model trained on the BLT-1T dataset, BLT-Entropy outperforms the Llama 3 tokenizer-based model on 4 of 7 tasks, including common sense reasoning, world knowledge, and code generation benchmarks such as ARC-Easy, ARC-Challenge, HellaSwag, PIQA, MMLU, MBPP, and HumanEval.

The paper also compares a space-patching version of BLT. That version achieves a larger average patch size and lower inference cost, but it is weaker on most benchmark tasks. The entropy-based version performs better overall, which supports the idea that patching should be data-driven rather than purely rule-based.

This is a recurring theme in the paper: dynamic patching is what closes the gap with tokenizer-based models.

## Why bytes help with robustness

Another major result is robustness. Because BLT works directly with bytes, it is less brittle to changes in spelling, casing, spacing, and noisy input.

The authors test this with several character-level perturbations, including random case changes, character dropping, repetition, and uppercasing. They also evaluate on tasks that require strong character-level knowledge, such as grapheme-to-phoneme conversion, orthographic manipulation, and low-resource machine translation.

BLT does particularly well on these tests. The most striking result is on the CUTE benchmark, where BLT-Entropy outperforms Llama 3 tokenizer-based models by more than 25 points, and reaches 99.9% accuracy on spelling tasks. It also improves on low-resource machine translation, especially for language pairs with less common scripts.

This matters for scaling because better handling of the long tail of language can translate into better generalization, not just better robustness.

## What this means for future LLM design

The biggest implication of BLT is not just that bytes can compete with tokens. It is that the unit of computation itself can become dynamic.

In standard LLMs, tokenization is a one-time preprocessing step. After that, every token gets equal treatment. BLT replaces that with a learned, adaptive scheme where the amount of computation depends on the input. That opens up a new way to think about efficiency: instead of only scaling model size, we can also scale the granularity of representation.

For practical deployment, this is attractive because inference cost is often the real constraint. If a model can maintain performance while reducing the number of expensive transformer steps, that can make larger models usable in settings where token-based architectures would be too costly.

The paper is careful not to overclaim. It notes that wall-clock performance still depends on implementation details, and that the scaling laws used to choose model sizes were originally derived for tokenizer-based transformers. Still, the evidence suggests that BLT changes the shape of the tradeoff.

## The bottom line

BLT makes a strong case that fixed-vocabulary tokenization is not the only viable way to scale LLMs.

By working directly on bytes, grouping them into dynamic patches, and using patch size as a compute knob, BLT shows that you can:

- match tokenizer-based performance at scale,
- reduce inference FLOPs,
- improve robustness to noise and character-level variation,
- and, most importantly, grow both patch size and model size under a fixed inference budget.

That last point is what makes the paper feel like more than just another architecture tweak. It suggests a different scaling path for future LLMs: one where efficiency gains are not simply used to make models cheaper, but to make them larger in the places that matter.

If tokenization defined the last generation of LLM scaling, BLT is an argument that patches may define the next one.
