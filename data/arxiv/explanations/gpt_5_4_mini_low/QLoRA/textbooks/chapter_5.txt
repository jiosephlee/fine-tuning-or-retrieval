\title{A Textbook about the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

Chapter 5: 5. Double Quantization and Paged Optimizers: Eliminating Hidden Memory Costs

# Why quantization constants create nontrivial memory overhead

QLoRA is built around the idea that reducing the precision of the base model can make large-model finetuning practical. But the paper emphasizes that quantizing the weights alone is not enough to fully solve the memory problem. When a weight tensor is quantized in blocks, each block needs its own quantization constant, also called a scale. These constants are necessary because the tensor is rescaled so that the low-bit representation can use its range effectively.

This creates an often overlooked source of memory use. Even if each weight is stored in only a few bits, the scale values themselves are typically stored in a much higher precision, such as $32$-bit floating point. As a result, the overhead from these constants can become substantial when many small blocks are used. In QLoRA, small blocks are desirable because they improve quantization precision, but small blocks also mean more scale constants per parameter. Thus, there is a tension between accuracy and memory efficiency that QLoRA resolves with an additional compression step.

# Memory cost of per-block scales in low-bit quantization

The paper gives a concrete example to show why scale overhead matters. If a tensor is quantized with blocksize $64$ and each block uses a $32$-bit constant, then the constants alone add $32/64 = 0.5$ bits per parameter on average. That may sound small, but across billions of parameters it becomes a major memory burden. For a very large model, this overhead can translate into several gigabytes.

This overhead is especially important in QLoRA because the method is designed to push finetuning to models such as $33$B and $65$B parameters on a single GPU. At those scales, every fraction of a bit per parameter matters. The paper therefore treats the scale constants not as a minor implementation detail, but as a core target for compression. This is the motivation for Double Quantization.

# The idea of Double Quantization: quantizing the quantization constants

Double Quantization is QLoRA’s second memory-saving idea. The basic idea is simple: if the first quantization step produces scale constants, then those constants can themselves be quantized. In other words, QLoRA applies quantization twice. The first level quantizes the weight tensor, and the second level quantizes the constants used by the first level.

The paper describes the second-stage constants as inputs to another quantization procedure. Instead of storing the first-stage constants in full precision, QLoRA stores them in a lower-precision form. This reduces the average memory footprint while still retaining enough information to reconstruct the effective scale used during computation. The important point is that the model does not need the constants in full precision at all times; it only needs them accurately enough to support dequantization into the computation datatype.

# First-level and second-level quantization in QLoRA

In the notation of the paper, the weight tensor is first quantized using a blockwise method. This produces a low-bit representation $\mathbf{W}^{\text{k-bit}}$ and a set of first-level quantization constants, which the paper denotes as $c_2^{\text{FP32}}$. These are the constants directly associated with the weight blocks.

Double Quantization then treats those first-level constants as data to be quantized again. That produces second-level quantized constants $c_2^{\text{FP8}}$ and a second set of constants $c_1^{\text{FP32}}$ needed to dequantize them. The process is therefore nested: one quantization for the weights, and another quantization for the scales of those weights.

This nesting is what allows QLoRA to reduce overhead without changing the basic structure of blockwise quantization. The weight tensor remains blockwise quantized, but the scale metadata is compressed as well. In effect, QLoRA applies compression to both the model parameters and the bookkeeping needed to decode them.

# Using FP8 for quantized scale constants

The paper chooses $8$-bit floating point for the second-stage quantization of the constants. This is based on the observation, consistent with prior work cited in the paper, that $8$-bit quantization does not cause a performance degradation in this setting. Since the second-level values are just scale constants, storing them in FP8 gives a large reduction in memory use while still preserving the information needed for reconstruction.

The use of FP8 is a compromise between compression and recoverability. The constants must remain accurate enough that the first-stage dequantization behaves properly, but they do not need the same precision as the full model weights. By selecting FP8, QLoRA substantially reduces storage cost while keeping the quantization pipeline simple and efficient.

# Centering positive scale values before second-stage quantization

The paper notes that the first-level scale constants $c_2^{\text{FP32}}$ are positive. This matters because symmetric quantization is generally most natural around zero, but a set of strictly positive values is not centered there. To address this, QLoRA subtracts the mean from the scale constants before quantizing them in the second stage. This recenters the values around zero and allows symmetric quantization to be used more effectively.

This centering step is important because it makes the second-stage quantization more suitable for the distribution of scale values. Without centering, the quantizer would be wasting representational capacity on an asymmetric range. By shifting the constants first, QLoRA uses the available bits more efficiently.

# Deriving the memory savings per parameter

The paper provides a straightforward memory calculation to show why Double Quantization matters. With blocksize $64$, storing a $32$-bit scale per block costs $32/64 = 0.5$ bits per parameter on average. After Double Quantization, those scale constants are themselves stored in $8$ bits, and the second-level constants add a much smaller overhead. The paper gives the resulting average as

$$
8/64 + 32/(64 \cdot 256) = 0.127
$$

bits per parameter.

This means Double Quantization reduces the scale overhead by about $0.373$ bits per parameter. The paper translates this to approximately $3$ GB saved for a $65$B model. This is a large reduction, and it is one reason QLoRA can fit very large finetuning workloads into the memory limits of a single GPU.

# Why Double Quantization preserves performance empirically

A central claim of the paper is that these savings do not come at the cost of accuracy. In the experiments comparing quantized data types, the authors report that Double Quantization reduces memory footprint without degrading performance. In other words, the extra compression applied to the scale constants does not materially hurt the model’s ability to match the performance of higher-precision baselines.

This result is crucial because it shows that the quantization constants are overparameterized relative to the needs of finetuning. Storing them in full precision is unnecessary for preserving task performance. QLoRA’s contribution is not just to compress more aggressively, but to do so in a way that retains the finetuning quality of the original model.

# What memory spikes are during gradient checkpointing and long-sequence training

The paper’s third major engineering contribution, Paged Optimizers, addresses a different kind of memory problem. Even if the average memory footprint fits within a GPU, training can still fail when temporary memory usage spikes. The paper specifically points to gradient checkpointing with long sequence lengths as a situation where this can happen.

Gradient checkpointing reduces activation memory by recomputing some values during backpropagation rather than storing everything. But this comes with a tradeoff: during some steps, the memory demand can momentarily spike. These spikes may push the system over the GPU memory limit, causing an out-of-memory failure even if the average memory usage would otherwise be acceptable. The paper treats this as a practical obstacle to single-GPU finetuning of large models.

# Unified memory and the idea behind Paged Optimizers

Paged Optimizers use NVIDIA unified memory to handle these spikes. Unified memory allows automatic page-to-page transfers between CPU and GPU. In the paper’s description, this works like ordinary memory paging, where data can be moved out when it is not immediately needed and brought back when required.

The optimizer states are allocated in paged memory. If the GPU runs out of memory during a peak, the system automatically evicts some optimizer state to CPU RAM. Later, when the optimizer update step needs that state again, it is paged back into GPU memory. This makes training more robust by allowing the system to survive temporary memory overflows rather than crashing.

# Moving optimizer states between CPU and GPU automatically

The key advantage of Paged Optimizers is that the movement of optimizer state is automatic. The user does not need to manually manage memory transfers or redesign the training loop. Instead, unified memory handles the paging behind the scenes. This makes it possible to keep training going even in scenarios where the memory footprint is temporarily larger than the available GPU memory.

In the paper’s framing, this does not change the mathematical optimization procedure. It changes the memory management around the optimizer states. That distinction matters: QLoRA is not introducing a new optimizer rule, but a way of storing optimizer state so that training remains feasible under tight memory constraints.

# Why paged optimization helps avoid out-of-memory failures

The role of Paged Optimizers is not primarily to make training faster; it is to make training possible. The paper says that paging is critical for tuning $33$B and $65$B models on single $24$GB or $48$GB GPUs because it prevents the transient memory spikes that would otherwise cause out-of-memory errors. In practice, that means training can continue through long-sequence mini-batches that would have been too memory-intensive for standard optimization.

The authors also note that in their measurements, paged optimizers provide the same training speed as regular optimizers for a batch size of $16$ on $65$B models on $48$GB GPUs, and that paging mainly occurs in the rarer long-sequence cases. The main takeaway is that Paged Optimizers provide a practical safety mechanism. They do not change the model’s learned behavior, but they help ensure that training completes successfully under extreme memory pressure.

Together, Double Quantization and Paged Optimizers address the “hidden” costs of large-scale finetuning. One compresses the metadata required by low-bit storage, and the other protects training from transient memory spikes. In the paper’s overall system, these two contributions are what make QLoRA workable at the largest scales studied.
