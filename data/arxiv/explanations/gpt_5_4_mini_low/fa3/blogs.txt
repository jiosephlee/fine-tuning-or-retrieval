# Why Attention Is Still the Slowest Part of AI—and How FlashAttention-3 Fixes It

Attention is one of the most important parts of the Transformer architecture, but it is also one of the main reasons large models are slow. That matters even more as models move toward longer context windows, where they need to process thousands or even tens of thousands of tokens at once. In that regime, attention does not just get more expensive — it grows quadratically with sequence length, which quickly makes it the bottleneck.

The FlashAttention line of work was designed to attack that problem directly. Instead of changing the math of attention, it changes how attention is executed on GPUs. FlashAttention-3 continues that idea, but takes a more hardware-aware approach than earlier versions. On NVIDIA Hopper GPUs, it uses asynchrony and low-precision execution to push attention much closer to the hardware limits.

## Why attention becomes the bottleneck

For a single attention head, the core computation is:

\[
\mathbf{S} = \alpha \mathbf{Q}\mathbf{K}^\top,\quad
\mathbf{P} = \mathrm{softmax}(\mathbf{S}),\quad
\mathbf{O} = \mathbf{P}\mathbf{V}.
\]

The problem is the middle matrix, \(\mathbf{S}\). If the sequence length is \(N\), then \(\mathbf{S}\) is \(N \times N\), so the cost grows like \(N^2\). That is fine for short sequences, but it becomes very expensive for long-context workloads.

This is not just a training issue. Long context is increasingly useful for:

- reasoning over long documents,
- code understanding over large repositories,
- multimodal models for images, audio, and video,
- user-facing systems that need to remember long histories,
- agent workflows with long horizons.

So there is a real need for attention implementations that are exact, fast, and scalable.

## What earlier FlashAttention versions did

The original FlashAttention made a simple but powerful observation: attention does not need to materialize the intermediate matrices \(\mathbf{S}\) and \(\mathbf{P}\) in global memory. Those reads and writes are expensive. Instead, FlashAttention fuses the attention computation into a single GPU kernel and keeps intermediate values on chip as much as possible.

FlashAttention-2 pushed that further by restructuring the computation to better parallelize work across the sequence dimension and improve occupancy. That helped a lot, but the paper reports that on Hopper H100 GPUs, FlashAttention-2 still only reaches about 35% utilization, while optimized matrix-multiplication kernels can get much closer to the hardware ceiling.

FlashAttention-3 is built to close that gap.

## What FlashAttention-3 changes

FlashAttention-3 introduces three main ideas.

First, it uses warp specialization to separate producer and consumer work. On Hopper, memory movement and matrix multiplication can happen asynchronously through hardware units like TMA and WGMMA. FlashAttention-3 exploits that by splitting the warps in a threadblock into roles: some warps load data, while others compute. That lets the kernel overlap data movement with computation instead of waiting on it.

Second, it overlaps softmax with GEMM work. In earlier designs, the softmax step and the matrix multiplications were more serialized. FlashAttention-3 reworks the execution so that while one part of the kernel is handling softmax for one block, another part can already be launching the next matrix multiplication. This “pingpong” style scheduling helps hide the relatively slow softmax operations behind faster Tensor Core work.

Third, it adapts the algorithm to FP8 on Hopper. FP8 can roughly double throughput compared to FP16 or BF16, but it comes with extra layout constraints and more numerical risk. FlashAttention-3 handles both issues with in-kernel layout transformations and two accuracy techniques: block quantization and incoherent processing.

## Why Hopper matters here

FlashAttention-3 is specifically designed around Hopper’s execution model.

Hopper has:

- Tensor Cores that support asynchronous WGMMA instructions,
- TMA for asynchronous data movement from global memory to shared memory,
- support for dynamic register reallocation across warpgroups,
- hardware support for FP8.

These features make it possible to redesign the kernel around overlapping work, rather than simply making the old kernel a little faster. That distinction matters. FlashAttention-3 is not just a tuned implementation of the same synchronous algorithm — it is an algorithm that explicitly exploits Hopper’s asynchronous hardware.

## How much faster is it?

The paper reports substantial speedups on an H100 SXM5 GPU:

- FP16 FlashAttention-3 reaches up to 740 TFLOPs/s, about 75% utilization.
- It is 1.5–2.0\times faster than FlashAttention-2 in the forward pass.
- It is 1.5–1.75\times faster in the backward pass.
- FP8 FlashAttention-3 reaches close to 1.2 PFLOPs/s.

That is a meaningful jump. In practice, a 1.5–2.0\times speedup on attention is a big deal because attention is one of the dominant costs in Transformer models. If attention gets faster, then longer context, larger batches, and more efficient multimodal processing all become more feasible.

The authors also compare against standard attention implementations and a cuDNN implementation optimized for Hopper. For medium and long sequences, FlashAttention-3 can outperform cuDNN as well.

## Why FP8 is both promising and tricky

FP8 is attractive because it can significantly increase throughput. But lower precision also means more numerical error, and attention is especially sensitive to that because it includes softmax and can be affected by outlier values in model activations.

FlashAttention-3 addresses this in two ways.

With block quantization, each block of \(\mathbf{Q}\), \(\mathbf{K}\), and \(\mathbf{V}\) gets its own scaling factor instead of using one scale for the entire tensor. That gives finer control over quantization error.

With incoherent processing, the model multiplies \(\mathbf{Q}\) and \(\mathbf{K}\) by a random orthogonal transform before quantization. Because the transform is orthogonal, it does not change the attention scores:

\[
(\mathbf{Q}\mathbf{M})(\mathbf{K}\mathbf{M})^\top = \mathbf{Q}\mathbf{K}^\top.
\]

What it does do is spread out outliers, which makes quantization easier.

In the paper’s evaluation, FP8 FlashAttention-3 is 2.6\times more accurate than a baseline FP8 attention method using per-tensor quantization in the tested outlier-heavy setting.

## Why this is more than just a benchmark win

This kind of optimization matters because attention is not an isolated kernel. It sits in the middle of almost every Transformer-based system. If you speed it up, you improve:

- training throughput,
- inference latency,
- long-context reasoning,
- multimodal pipelines,
- memory efficiency.

That is especially important as models grow larger and context windows expand. The broader the context, the more attention costs dominate. So even a relatively small improvement at the kernel level can translate into a major system-level gain.

FlashAttention-3 is also a good example of a broader trend in ML systems: the best performance gains often come from matching algorithms to hardware features instead of treating hardware as generic compute.

## The takeaway

FlashAttention-3 does not approximate attention or change the underlying math. Instead, it rethinks how exact attention is scheduled on Hopper GPUs. By using asynchronous execution, warp specialization, GEMM-softmax overlap, and FP8-aware design, it pushes attention much closer to the hardware limits.

The result is a 1.5–2.0\times speedup over FlashAttention-2 on H100 GPUs, along with strong FP8 performance and improved FP8 numerical accuracy. For long-context LLMs, multimodal models, and document-scale reasoning, that is exactly the kind of improvement that can make the difference between a theoretical capability and a practical one.



# Teaching GPUs to Multitask: The Asynchrony Trick Behind FlashAttention-3

Attention is one of the most important parts of Transformer models, but it is also one of the most expensive. As sequence lengths grow, the cost of computing attention grows quickly too. That is why the FlashAttention line of work has been so influential: it turns attention from a memory-heavy operation into a carefully tiled GPU kernel that avoids writing large intermediate results back to slow global memory.

FlashAttention-3 pushes that idea further, but the main story is not just “make the math faster.” The paper’s biggest systems insight is that modern Hopper GPUs can do more than one thing at once, and the attention kernel should be redesigned around that fact.

In short: FlashAttention-3 teaches the GPU to multitask.

## Why attention is hard to speed up

A standard attention computation has three main steps. First, it computes the score matrix $\mathbf{S} = \alpha \mathbf{Q}\mathbf{K}^\top$. Then it applies row-wise softmax to get probabilities $\mathbf{P}$. Finally, it multiplies by $\mathbf{V}$ to produce the output $\mathbf{O} = \mathbf{P}\mathbf{V}$.

On paper, those are just a couple of matrix multiplications and a softmax. On a GPU, though, the challenge is that these steps are not independent. The softmax needs the score matrix before it can run, and the final multiplication needs the softmax output. If you execute them naively, the GPU spends too much time waiting for one stage to finish before the next can begin.

FlashAttention already improved this by fusing the whole computation into one kernel and avoiding extra reads and writes. FlashAttention-3 goes a step further by exploiting the fact that Hopper GPUs can overlap data movement and computation in a more fine-grained way than earlier designs assumed.

## The key hardware idea: different GPU parts can work in parallel

A Hopper GPU does not behave like one single giant processor. It has specialized units for different jobs.

Tensor Cores are optimized for matrix multiplication. The Tensor Memory Accelerator, or TMA, is a dedicated engine for moving data between global memory and shared memory. Meanwhile, the regular CUDA cores handle logic, arithmetic, and other control-heavy work.

That matters because these units can run asynchronously. In other words, the GPU does not need to stop everything while one piece finishes. If the kernel is structured correctly, data can be moving in one part of the chip while matrix multiplication is happening in another, and while softmax is being computed somewhere else.

FlashAttention-3 is designed around this idea.

## Warp-specialization: splitting the team into producers and consumers

The first major trick in FlashAttention-3 is warp-specialization.

A warp is a group of 32 threads, and a warpgroup is a larger unit made of four warps. Instead of making every warp do every task, FlashAttention-3 divides the work into roles:

- **Producer warps** handle data movement.
- **Consumer warps** handle computation.

The producer side uses TMA to load tiles of $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$ from global memory into shared memory. The consumer side reads those tiles from shared memory and runs the matrix multiplications and softmax logic.

This is a producer-consumer pipeline. The producer keeps filling the next slot in a circular shared-memory buffer, while the consumer works through the current slot. Because the loads are asynchronous, the producer does not have to block on every compute step, and the consumer does not have to wait for the entire next chunk of data to be ready before starting.

That is the basic multitasking pattern: one part of the GPU is always preparing the next tile while another part is finishing the current one.

## Ping-pong scheduling: overlapping softmax with matmul

Warp-specialization alone helps, but FlashAttention-3 goes further. The paper’s second major idea is to overlap softmax with matrix multiplication.

Why is this useful? Because matrix multiplication is extremely fast on Tensor Cores, while softmax involves operations like exponentials and reductions that are much slower. On Hopper, the mismatch is especially large: the paper notes that FP16 matmul throughput is far higher than the throughput for special functions such as exponential.

If the GPU waits for softmax to finish before starting the next matrix multiplication, the Tensor Cores sit idle. FlashAttention-3 instead tries to keep the Tensor Cores busy while softmax runs in parallel on other hardware.

The mechanism is a kind of “ping-pong” schedule between two warpgroups. While one warpgroup is doing the softmax and output update for the current block, the other warpgroup is already launching the next $\mathbf{Q}\mathbf{K}^\top$ multiplication. Then they swap roles.

So the execution looks roughly like this:

- Warpgroup A computes softmax for block $j$.
- Warpgroup B computes matrix multiplication for block $j+1$.
- Then they switch.

This is the heart of the asynchrony trick. Instead of a strict sequence of “matmul, then softmax, then next matmul,” FlashAttention-3 turns the kernel into a pipeline where different stages overlap.

## Why this matters: better hardware utilization

This design is not just elegant; it shows up in the numbers.

The paper reports that on an H100 SXM5 GPU, FlashAttention-3 reaches up to 740 TFLOPs/s in FP16, which is about 75% utilization of the GPU’s theoretical maximum for that setting. It is about 1.5–2.0$\times$ faster than FlashAttention-2 in the forward pass, and 1.5–1.75$\times$ faster in the backward pass.

That performance gain is not from changing the math. It comes from keeping more of the machine busy at the same time.

A good mental model is a factory with specialized stations. If one station is fast but keeps waiting for the next station to finish, the factory is underused. FlashAttention-3 rearranges the line so that loading materials, processing them, and packaging outputs can happen in parallel whenever possible.

## The practical complication: dependencies still exist

Of course, the GPU cannot literally do everything at once. Softmax depends on the output of the first matrix multiplication, and the second matrix multiplication depends on the softmax result. FlashAttention-3 does not remove those dependencies. Instead, it reorganizes the kernel so that dependencies for one block are hidden behind useful work on another block.

That is why the paper uses buffer staging and careful synchronization. It also explains why the implementation is more complex than the earlier FlashAttention versions. You need enough shared-memory staging, enough registers, and the right ordering of events so that the pipeline stays full without corrupting data.

The important point is that the design treats latency as something to hide, not something to eliminate.

## A note on FP8: the same philosophy, even harder

The paper also extends the idea to FP8. That part introduces a separate set of challenges around layout and numerical accuracy, especially because Hopper’s FP8 Tensor Cores have stricter operand layout requirements than FP16.

But the underlying pattern is the same: use the hardware more efficiently by structuring the computation to fit the machine’s strengths. For FP8, FlashAttention-3 combines asynchrony with block quantization and incoherent processing to reduce error while still gaining performance. The paper reports that this FP8 version reaches close to 1.2 PFLOPs/s and is 2.6$\times$ more accurate than a baseline FP8 attention setup with per-tensor quantization in the tested outlier-heavy setting.

## What to take away

FlashAttention-3 is a good example of modern GPU algorithm design. The fastest kernel is not necessarily the one with the fewest operations. It is often the one that understands how the hardware actually moves data and schedules work.

The main lesson from the paper is simple:

If the GPU has separate engines for memory movement, matrix multiplication, and other arithmetic, then the best attention kernel should let those engines work at the same time.

That is what FlashAttention-3 does with warp-specialization, TMA, Tensor Cores, and ping-pong execution. Instead of making the GPU wait at every stage, it turns attention into a pipeline. And on Hopper, that makes a big difference.



# FP8 Without the Accuracy Nightmare: How FlashAttention-3 Makes Low-Precision Work

FP8 is attractive for the same reason every low-precision format is attractive: it can make attention faster and more efficient. On Hopper GPUs, FlashAttention-3 shows that this is not just a theoretical benefit. By targeting FP8 Tensor Cores, it reaches close to 1.2 PFLOPs/s.

But there is a catch. Lower precision usually means higher numerical error, and attention is especially sensitive to that. Large language models often contain outlier values, which are much larger than the rest of the activations. Those outliers make naive quantization harder, because a single large value can force the scale to stretch too far and reduce effective precision for everything else.

FlashAttention-3 addresses that problem with two ideas: block quantization and incoherent processing. Together, they make FP8 attention substantially more accurate than a baseline FP8 approach, while still preserving the performance gains of low precision.

## Why FP8 is appealing

The hardware motivation is straightforward. Hopper GPUs have FP8 Tensor Cores, and those Tensor Cores can deliver roughly 2x the throughput of FP16 or BF16. For attention, that matters a lot, because attention is already a major bottleneck in transformer models.

FlashAttention-3 uses that hardware to push attention much further than previous versions. In the paper’s measurements, FP8 FlashAttention-3 gets close to 1.2 PFLOPs/s on H100. That is an enormous amount of throughput for a kernel that sits in the inner loop of transformer workloads.

The problem is that speed is only useful if the results are still reliable.

## Why low precision is risky for attention

FP8 uses only 8 bits, with just 3 bits for the mantissa and 4 bits for the exponent in the e4m3 format used here. That gives much less representational range and precision than FP16 or BF16.

In attention, this is not a minor detail. The computation depends on dot products, softmax, and repeated rescaling across blocks. Small numerical errors can accumulate. And if the model has outlier features, the issue gets worse.

The paper points out that large models often have outliers in $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$. Those rare but large values can dominate tensor ranges and make per-tensor scaling too coarse. If one scale is shared across an entire tensor, a few extreme entries can reduce precision everywhere else.

That is why baseline FP8 attention can be fragile.

## Block quantization: scale smaller pieces, not the whole tensor

FlashAttention-3 reduces quantization error by moving from per-tensor scaling to block quantization.

Instead of using one scale for all of $\mathbf{Q}$, $\mathbf{K}$, or $\mathbf{V}$, the tensor is split into smaller blocks, and each block gets its own scale. In the paper, those blocks are sized to match the algorithm’s tile structure, such as $B_r \times d$ or $B_c \times d$ blocks.

This helps because each block is more locally homogeneous. A few outliers in one region no longer force the entire tensor to use the same conservative scale. The result is better use of FP8’s limited dynamic range.

Another advantage is that FlashAttention-3 already operates on blocks internally, so the quantization fits naturally into the algorithm. The paper also notes that block quantization can be fused with a preceding operation such as rotary embedding, so it does not add extra slowdown.

## Incoherent processing: spread out the outliers

Block quantization helps, but it does not completely solve the outlier problem. FlashAttention-3 adds a second technique called incoherent processing.

The idea is to multiply both $\mathbf{Q}$ and $\mathbf{K}$ by the same random orthogonal matrix $\mathbf{M}$ before quantization. Since $\mathbf{M}\mathbf{M}^\top = I$, this transformation does not change the attention scores:

$$
(\mathbf{Q}\mathbf{M})(\mathbf{K}\mathbf{M})^\top = \mathbf{Q}\mathbf{K}^\top.
$$

So the math stays the same, but the distribution of values changes. The transformation mixes the entries, which tends to “spread out” outliers instead of letting them remain concentrated in a few coordinates. That makes quantization easier and reduces error.

In practice, the paper follows prior work and uses $\mathbf{M}$ as a product of random diagonal $\pm 1$ matrices and a Hadamard matrix. This keeps the transformation efficient, since it can be applied in $O(d \log d)$ time rather than $O(d^2)$.

The key point is that this is not an approximation to attention. It is a reparameterization that preserves the exact attention output in real arithmetic, while making the low-precision path behave better.

## Why the implementation details matter

FP8 is not just a matter of changing the datatype. The paper also explains that Hopper’s FP8 WGMMA instructions have stricter layout requirements than FP16.

In particular, FP8 WGMMA expects certain operands to be laid out in k-major format. That creates a problem for attention, where the usual tensor layouts are not always compatible with the desired compute path. FlashAttention-3 solves this with an in-kernel transpose using LDSM and STSM instructions, so the data can be rearranged without costly extra passes over memory.

There is also a layout mismatch between the FP32 accumulator produced by one WGMMA and the operand layout expected by the next one. The implementation uses byte permutation instructions to bridge that gap. These are the kinds of low-level details that determine whether FP8 is practical in a real fused attention kernel.

## What the paper shows experimentally

The paper evaluates FP8 FlashAttention-3 on an H100 SXM5 GPU. The headline result is that FP8 reaches close to 1.2 PFLOPs/s.

On the accuracy side, the paper compares FP8 FlashAttention-3 against a baseline FP8 attention method that uses per-tensor scaling. To make the test realistic, it simulates outlier-like values using a mixture distribution with rare large-magnitude entries.

Under those conditions, block quantization plus incoherent processing reduces numerical error by 2.6x compared to the baseline FP8 approach.

That is the important takeaway: FlashAttention-3 does not trade accuracy away blindly in exchange for speed. It shows that with the right algorithmic and hardware-aware choices, FP8 attention can be both fast and noticeably more stable.

## The bigger lesson

FlashAttention-3 is a good example of how low precision should be approached in modern accelerators. The answer is not “use fewer bits and hope for the best.” The answer is to redesign the algorithm around the hardware and around the numerical structure of the problem.

For FP8 attention, that means:

- exploiting the GPU’s FP8 Tensor Cores,
- limiting the damage from outliers with block quantization,
- smoothing the value distribution with incoherent processing,
- and integrating all of this into a fused attention kernel rather than a slow, memory-heavy implementation.

The result is a kernel that is both faster and more accurate than a naive FP8 baseline. That combination is exactly what makes FP8 practical instead of risky.

FlashAttention-3 is not just showing that FP8 can be fast. It is showing how FP8 can be made usable for attention without turning numerical stability into an afterthought.



# From 35% to 75% GPU Utilization: What FlashAttention-3 Teaches Us About Modern AI Hardware

Attention is one of those operations that looks simple on paper and becomes painfully expensive at scale. In Transformers, it is also the main bottleneck for long sequences because the core computation scales quadratically with context length. That is why the FlashAttention line of work has been so influential: instead of treating attention like a generic matrix problem, it reshapes the algorithm around how GPUs actually move data and execute work.

FlashAttention-3 pushes that idea further. The paper’s main message is not just “make attention faster,” but “modern GPUs have new hardware features, and the algorithm should explicitly use them.” On NVIDIA’s Hopper H100, that matters a lot. FlashAttention-2 reaches only about 35% utilization on H100, while FlashAttention-3 gets up to 75% utilization, reaching up to 740 TFLOPs/s in FP16 and nearly 1.2 PFLOPs/s in FP8.

## Why FlashAttention-2 Left Performance on the Table

FlashAttention-2 already made a major improvement over standard attention by avoiding the expensive intermediate matrices $\mathbf{S}$ and $\mathbf{P}$ in high-bandwidth memory. Instead of materializing those matrices, it fuses the whole attention computation into a single kernel and keeps the intermediate results on chip as much as possible.

That was a big step, but Hopper changed the rules. The H100 GPU has hardware features that FlashAttention-2 does not fully exploit:

- **Asynchronous Tensor Cores**, exposed through WGMMA instructions.
- **The Tensor Memory Accelerator (TMA)**, which can move data between global memory and shared memory asynchronously.
- **FP8 Tensor Core support**, which can roughly double throughput relative to FP16 or BF16.

FlashAttention-2 was designed around a more synchronous execution model. It does not explicitly overlap as much computation and data movement as Hopper allows, and it does not treat low precision as part of the algorithm design. FlashAttention-3 is built around those assumptions instead.

## The Hardware Reality: Memory, Registers, and Specialized Units

To understand the paper, it helps to think of a GPU as a set of specialized layers.

Global memory is large but slow. Shared memory is much smaller but fast and programmer-managed. Registers are even faster, but extremely limited. Hopper also adds hardware units that do very specific jobs well: Tensor Cores for matrix multiplication and TMA for memory movement.

The key point is that a high-performance attention kernel is really a scheduling problem across these layers. The question is not just “how many FLOPs does attention require?” It is also:

- How do we keep Tensor Cores busy?
- How do we hide memory latency?
- How do we avoid storing unnecessary intermediates in global memory?
- How do we fit the algorithm into the limited register file and shared memory?
- How do we use FP8 without losing too much numerical accuracy?

FlashAttention-3 answers those questions by redesigning the kernel around Hopper’s execution model.

## Three Ideas That Make FlashAttention-3 Faster

The paper’s improvements fall into three main categories.

### 1. Producer-consumer asynchrony with warp-specialization

One of the big Hopper features is that data movement and computation can happen asynchronously. FlashAttention-3 takes advantage of that by splitting the warps in a CTA into producer and consumer roles.

The producer warps mainly handle loading data into shared memory. The consumer warps perform the matrix multiplications and softmax work. This warp-specialized design makes it easier to overlap data movement with compute, instead of forcing the whole kernel to move in lockstep.

The paper also uses **register reallocation** via `setmaxnreg`, which lets the compute-heavy warps get more registers than the load-only warps. That matters because registers are one of the main limits on kernel occupancy and tile size.

### 2. Overlapping softmax with asynchronous GEMMs

Attention is often described as two matrix multiplications with a softmax in between:

\[
\mathbf{S} = \alpha \mathbf{Q}\mathbf{K}^\top,\quad
\mathbf{P} = \mathrm{softmax}(\mathbf{S}),\quad
\mathbf{O} = \mathbf{P}\mathbf{V}
\]

In a naive implementation, those steps are serialized. FlashAttention-3 tries to break that dependency chain by pipelining across iterations.

The clever part is that the paper overlaps the relatively slow softmax operations with the asynchronous GEMMs. While one block is going through softmax, the Tensor Cores can already be computing the next block. The paper calls this kind of interleaving “pingpong” scheduling when it is extended across warpgroups.

This is a good example of hardware-aware algorithm design: the GPU is not treated as one homogeneous engine. Different parts of the chip are used at the same time for different stages of the computation.

### 3. FP8 support with block quantization and layout fixes

Hopper’s FP8 support is a major opportunity, but it comes with complications. FP8 gives higher throughput, but it is less forgiving numerically and has stricter layout requirements for WGMMA.

FlashAttention-3 handles this in two ways.

First, it uses **block quantization** instead of per-tensor quantization. Rather than assigning one scale factor to an entire tensor, it uses one scale per block. Because FlashAttention already works in blocks, this can be integrated naturally.

Second, it uses **incoherent processing**. The idea is to multiply $\mathbf{Q}$ and $\mathbf{K}$ by the same random orthogonal matrix before quantization. Since the matrix is orthogonal, attention itself does not change:

\[
(\mathbf{Q}\mathbf{M})(\mathbf{K}\mathbf{M})^\top = \mathbf{Q}\mathbf{K}^\top
\]

But the values become more evenly distributed, which reduces the impact of outliers and improves quantization accuracy. The paper uses structured orthogonal transforms based on random diagonal matrices and Hadamard matrices.

These two techniques make FP8 attention both fast and more numerically stable than a naive FP8 baseline.

## Why Layout Matters More Than You Think

A recurring theme in the paper is that performance depends on physical layout, not just math.

For FP8 WGMMA on Hopper, the second GEMM in attention wants its operand in a k-major format. But the natural layout of the value matrix $\mathbf{V}$ is not always compatible with that. FlashAttention-3 resolves this with an in-kernel transpose using `ldmatrix` and `stmatrix`, and by carefully matching register layouts between the accumulator of one GEMM and the operands of the next.

This sounds like a low-level implementation detail, but it is actually central to the whole story. On modern accelerators, the algorithm is only “simple” if it matches the hardware’s preferred layout. If the layouts do not line up, the kernel pays a hidden tax in extra copies, shuffles, or register pressure.

In other words, modern attention optimization is not just about math. It is about making the math fit the machine.

## What the Results Show

The empirical results back up the hardware-software co-design story.

On an H100 SXM5 GPU, FlashAttention-3:

- Achieves **1.5-2.0x speedup** over FlashAttention-2 in the forward pass.
- Achieves **1.5-1.75x speedup** in the backward pass.
- Reaches up to **740 TFLOPs/s**, which is about **75% utilization** of the H100’s theoretical maximum.
- In FP8, reaches close to **1.2 PFLOPs/s**.
- Produces FP8 results that are **2.6x more accurate** than a baseline FP8 attention method with per-tensor quantization.

The paper also shows that the warp-specialization and pipelining ideas matter on their own. In one ablation, the FP16 forward pass improves from 570 TFLOPs/s to 661 TFLOPs/s when those ideas are added.

## The Broader Lesson

FlashAttention-3 is a strong example of how GPU progress changes software design. When hardware adds asynchrony, specialized memory movement, and lower-precision arithmetic, the best algorithms are the ones that assume those features will be used directly.

That is why the paper is interesting beyond attention itself. It shows a pattern that keeps repeating in systems work on ML accelerators:

- Memory hierarchy shapes the kernel.
- Register pressure shapes the tile sizes.
- Specialized compute units shape the scheduling.
- Low precision shapes the numerics.
- The best performance comes from making these constraints part of the algorithm, not treating them as after-the-fact implementation issues.

FlashAttention-3 is not just a faster attention kernel. It is a demonstration that algorithm design for AI hardware has to evolve with the hardware itself.

## Closing Thoughts

Attention is still one of the most important bottlenecks in large language models and long-context systems. FlashAttention-3 shows that there is still substantial headroom left if we stop thinking about GPU kernels as generic math routines and start thinking about them as carefully staged workflows across memory, registers, and specialized execution units.

That is the real takeaway from the jump from 35% to 75% utilization: the hardware was capable all along, but only if the software was redesigned to meet it where it is.



# The Hidden Engineering of Faster Transformers: Inside FlashAttention-3’s Pipeline

Attention is still one of the biggest bottlenecks in Transformer models, especially as context lengths grow. FlashAttention already showed that you can speed it up dramatically by avoiding expensive reads and writes to global memory. FlashAttention-3 takes the next step: instead of only reducing memory traffic, it restructures the attention loop itself to better match how modern Hopper GPUs actually run.

The short version is that FlashAttention-3 treats attention as a pipeline. It overlaps data movement, matrix multiplications, and softmax work across blocks, and it does so using Hopper-specific features like asynchronous Tensor Cores, TMA loads, and FP8 support. The result is a measurable jump in throughput: up to 1.5-2.0$\times$ faster than FlashAttention-2 in FP16, with FP16 forward pass performance reaching up to 740 TFLOPs/s on H100, and FP8 reaching close to 1.2 PFLOPs/s.

## Why FlashAttention-2 Was Not Enough

FlashAttention-2 improved on the original FlashAttention by parallelizing more of the work and restructuring the inner loop over key/value blocks. That made it a strong implementation on older hardware.

But on Hopper, the paper observes a gap: FlashAttention-2 reaches only about 35% utilization on H100, while optimized GEMM kernels can hit 80-90%. The issue is not just raw algorithmic efficiency. It is also that FlashAttention-2 was still designed around a mostly synchronous execution model. Hopper, by contrast, gives you new tools for asynchrony:

- TMA for asynchronous memory transfers from global memory to shared memory.
- WGMMA for asynchronous matrix multiplication on Tensor Cores.
- Separate hardware paths for matrix math and memory movement.

FlashAttention-3 is built to exploit those features directly.

## The Core Idea: Turn Attention Into a Pipeline

At a high level, attention does three things over and over for each block of keys and values:

1. Compute scores with a GEMM: $\mathbf{Q}\mathbf{K}^\top$
2. Apply softmax
3. Multiply by values with another GEMM: $\mathbf{P}\mathbf{V}$

In a naive implementation, these steps serialize. Softmax waits for the score matrix, and the value GEMM waits for softmax. FlashAttention-3 breaks that strict dependency chain by pipelining work across blocks.

Instead of thinking about one block at a time, it keeps multiple stages in flight:

- While one warpgroup is doing softmax on block $j$,
- another warpgroup can already be running GEMMs for block $j+1$,
- and TMA can be loading the next key/value tiles in the background.

This is the main engineering shift: attention is no longer a simple loop of dependent steps. It becomes an overlapped producer-consumer pipeline.

## Warp-Specialization: Separate the Loaders from the Compute

One of the first optimizations in FlashAttention-3 is warp-specialization. Rather than having all warps do everything, the CTA is split into producer and consumer roles.

The producer warps handle data movement. They use TMA to load $\mathbf{Q}$ and then stream $\mathbf{K}$ and $\mathbf{V}$ tiles into shared memory. The consumer warps handle the math. They wait for the right tiles to arrive and then execute the two GEMMs and the softmax updates.

This matters because Hopper can overlap these roles more effectively than a uniform kernel can. The paper also uses `setmaxnreg` to dynamically reallocate registers between these roles. Consumer warps doing the Tensor Core work can get more registers, while producer warps need fewer. That is a practical way to reduce pressure on the register file and improve scheduling.

The implementation uses a circular shared-memory buffer, so while one stage is being consumed, another can already be filled. This is the foundation that makes the rest of the pipeline work.

## Hiding Softmax Under GEMM

The next step is more interesting: even inside the consumer path, FlashAttention-3 overlaps softmax with GEMM.

In the standard flow, softmax depends on the output of $\mathbf{Q}\mathbf{K}^\top$, and the value GEMM depends on softmax output. That seems sequential. The trick in FlashAttention-3 is to pipeline across iterations, so that the second GEMM from one block can run while the softmax for the next block is being computed.

The paper’s 2-stage version does this by keeping intermediate state in registers:

- One stage computes the next score block $\mathbf{S}_{\mathrm{next}} = \mathbf{Q}_i \mathbf{K}_j^\top$.
- At the same time, the previous softmax result is used to compute $\mathbf{O}_i = \mathbf{O}_i + \tilde{\mathbf{P}}_{\mathrm{cur}} \mathbf{V}_{j-1}$.
- Then the kernel waits for the next score block, runs softmax, and advances.

This reordering lets the GPU’s Tensor Cores stay busy while the slower special-function work for exponentials and reductions is happening elsewhere. The paper notes that special functions are much lower throughput than matmul on H100, so hiding them under GEMM is a real win.

This is also why the authors use “pingpong” scheduling across warpgroups. One warpgroup is in the GEMM-heavy part of the pipeline while another is in the softmax-heavy part, then they swap roles. In practice, this improved FP16 forward performance from about 570 TFLOPs/s to 620-640 TFLOPs/s in the paper’s example setup.

## Why the Compiler Becomes Part of the Problem

Once you start writing highly scheduled asynchronous code, the compiler stops being a passive detail. The paper explicitly calls out compiler reordering as a practical risk.

The pseudocode describes a carefully choreographed sequence. But NVCC may rearrange instructions for its own optimization goals, which can break the intended overlap. So the authors inspect the generated SASS to make sure the pipeline is actually preserved.

This is a recurring theme in GPU kernel work: performance is not just about the algorithm on paper. It is about whether the emitted machine code respects the timing assumptions that the algorithm depends on.

Another issue is register pressure. The 2-stage pipeline needs extra registers to hold intermediate score blocks and to bridge one stage to the next. That can conflict with using larger block sizes, which also consume registers. So the implementation has to balance:

- deeper pipelining,
- larger tiles,
- and the available register budget.

The paper even discusses a 3-stage variant, which could expose more overlap but raises the register pressure further. In other words, more pipelining is not automatically better.

## Why FP8 Needs More Than Just Lower Precision

FlashAttention-3 also targets Hopper’s FP8 Tensor Cores. This is not just a matter of changing dtypes and getting more throughput. FP8 introduces both layout constraints and accuracy issues.

On the layout side, FP8 WGMMA is stricter than FP16 WGMMA. In particular, some operand layouts must be k-major, which clashes with how attention data is normally laid out. For FlashAttention, that means the value tiles need to be transformed so they fit what the hardware expects.

The paper’s solution is an in-kernel transpose using `ldmatrix` and `stmatrix`, rather than a separate preprocessing transpose. That choice avoids an extra memory-bound kernel and keeps the dataflow inside the attention kernel itself.

There is also a layout mismatch between the FP32 accumulator produced by the first FP8 WGMMA and the operand layout expected by the second WGMMA. The authors solve this with byte permutation instructions and a matching row permutation in the transposed value tile. The result is a pipeline that can still run fully on the FP8 path.

## Accuracy: Block Quantization and Incoherent Processing

The other challenge with FP8 is numerical error, especially when activations contain outliers. The paper evaluates this with synthetic data that includes rare large-magnitude values, which is meant to reflect the kind of outlier behavior seen in large models.

Two techniques are used to reduce error:

Block quantization means using one scale per block rather than one scale per whole tensor. Since FlashAttention already works on blocks, this fits naturally into the kernel and can be fused with nearby operations.

Incoherent processing means multiplying $\mathbf{Q}$ and $\mathbf{K}$ by a random orthogonal matrix before quantization. Because the same transform is applied to both sides, the attention scores do not change, but the outliers get spread out, which reduces quantization error. The paper uses a structure based on random diagonal matrices and Hadamard matrices to make this efficient.

With these techniques, FP8 FlashAttention-3 is reported to be 2.6$\times$ more accurate than a baseline FP8 attention method using per-tensor quantization.

## What This Means in Practice

The most useful thing about FlashAttention-3 is that it shows where the extra performance comes from. It is not a single magical optimization. It is a combination of several low-level changes that each remove a different source of idle time:

- warp-specialization keeps data movement and compute moving in parallel,
- asynchronous WGMMA lets softmax and GEMM overlap,
- FP8 support doubles Tensor Core throughput,
- block quantization and incoherent processing recover much of the lost accuracy.

That combination is why the gains are substantial both for training-oriented workloads and for longer-context inference-style runs. In the paper’s benchmarks on H100 SXM5, FlashAttention-3 is up to 2.0$\times$ faster than FlashAttention-2 in the forward pass and 1.5-1.75$\times$ faster in the backward pass, while also beating standard attention by a wide margin.

For engineers, the key takeaway is that modern GPU performance often comes from reorganizing the computation around hardware concurrency, not just reducing arithmetic or memory use. FlashAttention-3 is a good example of that mindset: it treats the GPU as an asynchronous system and reshapes attention to keep its specialized units busy.

## Closing Thoughts

FlashAttention-3 is a strong reminder that kernel engineering still matters a lot, especially for Transformers. The algorithm is still exact attention, but the way it is scheduled is very different from earlier versions. By overlapping GEMM, softmax, and data movement, and by adapting to Hopper’s FP8 path, the paper pushes attention much closer to the hardware limits.

The implementation is intricate, but the payoff is clear: higher throughput, better utilization, and a practical path toward faster long-context models.
