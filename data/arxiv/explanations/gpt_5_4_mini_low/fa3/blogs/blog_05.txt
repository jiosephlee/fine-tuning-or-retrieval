\title{Blogs about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

# The Hidden Engineering of Faster Transformers: Inside FlashAttention-3’s Pipeline

Attention is still one of the biggest bottlenecks in Transformer models, especially as context lengths grow. FlashAttention already showed that you can speed it up dramatically by avoiding expensive reads and writes to global memory. FlashAttention-3 takes the next step: instead of only reducing memory traffic, it restructures the attention loop itself to better match how modern Hopper GPUs actually run.

The short version is that FlashAttention-3 treats attention as a pipeline. It overlaps data movement, matrix multiplications, and softmax work across blocks, and it does so using Hopper-specific features like asynchronous Tensor Cores, TMA loads, and FP8 support. The result is a measurable jump in throughput: up to 1.5-2.0$\times$ faster than FlashAttention-2 in FP16, with FP16 forward pass performance reaching up to 740 TFLOPs/s on H100, and FP8 reaching close to 1.2 PFLOPs/s.

## Why FlashAttention-2 Was Not Enough

FlashAttention-2 improved on the original FlashAttention by parallelizing more of the work and restructuring the inner loop over key/value blocks. That made it a strong implementation on older hardware.

But on Hopper, the paper observes a gap: FlashAttention-2 reaches only about 35% utilization on H100, while optimized GEMM kernels can hit 80-90%. The issue is not just raw algorithmic efficiency. It is also that FlashAttention-2 was still designed around a mostly synchronous execution model. Hopper, by contrast, gives you new tools for asynchrony:

- TMA for asynchronous memory transfers from global memory to shared memory.
- WGMMA for asynchronous matrix multiplication on Tensor Cores.
- Separate hardware paths for matrix math and memory movement.

FlashAttention-3 is built to exploit those features directly.

## The Core Idea: Turn Attention Into a Pipeline

At a high level, attention does three things over and over for each block of keys and values:

1. Compute scores with a GEMM: $\mathbf{Q}\mathbf{K}^\top$
2. Apply softmax
3. Multiply by values with another GEMM: $\mathbf{P}\mathbf{V}$

In a naive implementation, these steps serialize. Softmax waits for the score matrix, and the value GEMM waits for softmax. FlashAttention-3 breaks that strict dependency chain by pipelining work across blocks.

Instead of thinking about one block at a time, it keeps multiple stages in flight:

- While one warpgroup is doing softmax on block $j$,
- another warpgroup can already be running GEMMs for block $j+1$,
- and TMA can be loading the next key/value tiles in the background.

This is the main engineering shift: attention is no longer a simple loop of dependent steps. It becomes an overlapped producer-consumer pipeline.

## Warp-Specialization: Separate the Loaders from the Compute

One of the first optimizations in FlashAttention-3 is warp-specialization. Rather than having all warps do everything, the CTA is split into producer and consumer roles.

The producer warps handle data movement. They use TMA to load $\mathbf{Q}$ and then stream $\mathbf{K}$ and $\mathbf{V}$ tiles into shared memory. The consumer warps handle the math. They wait for the right tiles to arrive and then execute the two GEMMs and the softmax updates.

This matters because Hopper can overlap these roles more effectively than a uniform kernel can. The paper also uses `setmaxnreg` to dynamically reallocate registers between these roles. Consumer warps doing the Tensor Core work can get more registers, while producer warps need fewer. That is a practical way to reduce pressure on the register file and improve scheduling.

The implementation uses a circular shared-memory buffer, so while one stage is being consumed, another can already be filled. This is the foundation that makes the rest of the pipeline work.

## Hiding Softmax Under GEMM

The next step is more interesting: even inside the consumer path, FlashAttention-3 overlaps softmax with GEMM.

In the standard flow, softmax depends on the output of $\mathbf{Q}\mathbf{K}^\top$, and the value GEMM depends on softmax output. That seems sequential. The trick in FlashAttention-3 is to pipeline across iterations, so that the second GEMM from one block can run while the softmax for the next block is being computed.

The paper’s 2-stage version does this by keeping intermediate state in registers:

- One stage computes the next score block $\mathbf{S}_{\mathrm{next}} = \mathbf{Q}_i \mathbf{K}_j^\top$.
- At the same time, the previous softmax result is used to compute $\mathbf{O}_i = \mathbf{O}_i + \tilde{\mathbf{P}}_{\mathrm{cur}} \mathbf{V}_{j-1}$.
- Then the kernel waits for the next score block, runs softmax, and advances.

This reordering lets the GPU’s Tensor Cores stay busy while the slower special-function work for exponentials and reductions is happening elsewhere. The paper notes that special functions are much lower throughput than matmul on H100, so hiding them under GEMM is a real win.

This is also why the authors use “pingpong” scheduling across warpgroups. One warpgroup is in the GEMM-heavy part of the pipeline while another is in the softmax-heavy part, then they swap roles. In practice, this improved FP16 forward performance from about 570 TFLOPs/s to 620-640 TFLOPs/s in the paper’s example setup.

## Why the Compiler Becomes Part of the Problem

Once you start writing highly scheduled asynchronous code, the compiler stops being a passive detail. The paper explicitly calls out compiler reordering as a practical risk.

The pseudocode describes a carefully choreographed sequence. But NVCC may rearrange instructions for its own optimization goals, which can break the intended overlap. So the authors inspect the generated SASS to make sure the pipeline is actually preserved.

This is a recurring theme in GPU kernel work: performance is not just about the algorithm on paper. It is about whether the emitted machine code respects the timing assumptions that the algorithm depends on.

Another issue is register pressure. The 2-stage pipeline needs extra registers to hold intermediate score blocks and to bridge one stage to the next. That can conflict with using larger block sizes, which also consume registers. So the implementation has to balance:

- deeper pipelining,
- larger tiles,
- and the available register budget.

The paper even discusses a 3-stage variant, which could expose more overlap but raises the register pressure further. In other words, more pipelining is not automatically better.

## Why FP8 Needs More Than Just Lower Precision

FlashAttention-3 also targets Hopper’s FP8 Tensor Cores. This is not just a matter of changing dtypes and getting more throughput. FP8 introduces both layout constraints and accuracy issues.

On the layout side, FP8 WGMMA is stricter than FP16 WGMMA. In particular, some operand layouts must be k-major, which clashes with how attention data is normally laid out. For FlashAttention, that means the value tiles need to be transformed so they fit what the hardware expects.

The paper’s solution is an in-kernel transpose using `ldmatrix` and `stmatrix`, rather than a separate preprocessing transpose. That choice avoids an extra memory-bound kernel and keeps the dataflow inside the attention kernel itself.

There is also a layout mismatch between the FP32 accumulator produced by the first FP8 WGMMA and the operand layout expected by the second WGMMA. The authors solve this with byte permutation instructions and a matching row permutation in the transposed value tile. The result is a pipeline that can still run fully on the FP8 path.

## Accuracy: Block Quantization and Incoherent Processing

The other challenge with FP8 is numerical error, especially when activations contain outliers. The paper evaluates this with synthetic data that includes rare large-magnitude values, which is meant to reflect the kind of outlier behavior seen in large models.

Two techniques are used to reduce error:

Block quantization means using one scale per block rather than one scale per whole tensor. Since FlashAttention already works on blocks, this fits naturally into the kernel and can be fused with nearby operations.

Incoherent processing means multiplying $\mathbf{Q}$ and $\mathbf{K}$ by a random orthogonal matrix before quantization. Because the same transform is applied to both sides, the attention scores do not change, but the outliers get spread out, which reduces quantization error. The paper uses a structure based on random diagonal matrices and Hadamard matrices to make this efficient.

With these techniques, FP8 FlashAttention-3 is reported to be 2.6$\times$ more accurate than a baseline FP8 attention method using per-tensor quantization.

## What This Means in Practice

The most useful thing about FlashAttention-3 is that it shows where the extra performance comes from. It is not a single magical optimization. It is a combination of several low-level changes that each remove a different source of idle time:

- warp-specialization keeps data movement and compute moving in parallel,
- asynchronous WGMMA lets softmax and GEMM overlap,
- FP8 support doubles Tensor Core throughput,
- block quantization and incoherent processing recover much of the lost accuracy.

That combination is why the gains are substantial both for training-oriented workloads and for longer-context inference-style runs. In the paper’s benchmarks on H100 SXM5, FlashAttention-3 is up to 2.0$\times$ faster than FlashAttention-2 in the forward pass and 1.5-1.75$\times$ faster in the backward pass, while also beating standard attention by a wide margin.

For engineers, the key takeaway is that modern GPU performance often comes from reorganizing the computation around hardware concurrency, not just reducing arithmetic or memory use. FlashAttention-3 is a good example of that mindset: it treats the GPU as an asynchronous system and reshapes attention to keep its specialized units busy.

## Closing Thoughts

FlashAttention-3 is a strong reminder that kernel engineering still matters a lot, especially for Transformers. The algorithm is still exact attention, but the way it is scheduled is very different from earlier versions. By overlapping GEMM, softmax, and data movement, and by adapting to Hopper’s FP8 path, the paper pushes attention much closer to the hardware limits.

The implementation is intricate, but the payoff is clear: higher throughput, better utilization, and a practical path toward faster long-context models.
