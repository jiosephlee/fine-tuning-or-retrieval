\title{A Textbook about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

Chapter 3: 3. GPU Architecture for Attention Kernels

# GPU memory hierarchy: HBM/global memory, L2 cache, shared memory, and registers

FlashAttention-3 is designed around a simple but crucial fact about GPUs: different kinds of data live at different “distances” from the compute units, and those distances matter enormously for performance. The paper describes the GPU memory system as a hierarchy of data locales, each with different capacity and bandwidth. At the farthest and largest level is global memory, also called HBM. This off-chip DRAM is accessible to all streaming multiprocessors, but it is much slower than on-chip storage. Data from global memory is transparently cached into an on-chip L2 cache, which sits between HBM and the compute units. Closer still is shared memory, which is a small, programmer-managed, highly banked on-chip cache local to each streaming multiprocessor. Finally, each thread has access to its own register file, which is the closest and fastest storage but also the most limited.

This hierarchy is central to understanding why attention kernels are hard to optimize. Attention involves large matrix operations and repeated movement of query, key, and value tiles. If intermediate results are written out to HBM and later read back, performance is dominated by memory traffic rather than arithmetic. FlashAttention’s original insight, and FlashAttention-3’s continuation of it, is to keep intermediate data on chip whenever possible. In the paper’s algorithmic description, query, key, and value tiles are moved into shared memory, then consumed there by the compute steps. The outputs and normalization statistics are maintained on chip until the end of the block computation, and only the final results are written back to HBM.

The register file is especially important because some parts of the algorithm need to preserve intermediate state across iterations. In the consumer portion of the kernel, the algorithm maintains quantities such as the output accumulator $\mathbf{O}_i$, the running maximum $m_i$, and the running normalizer $\ell_i$. These are held in registers so that they can be updated efficiently across many small operations. The paper also uses register buffers to enable pipelining: when overlapping one operation with another, extra register space is needed to hold intermediate matrices such as $\mathbf{S}_{\mathrm{next}}$ while the current work is still in flight. Thus, shared memory and registers are not just passive storage locations; they actively constrain how the kernel is structured.

# Bandwidth versus capacity across the memory hierarchy

A key organizing principle in the paper is that capacity and bandwidth move in opposite directions. The largest memory, HBM, has the greatest capacity but the lowest bandwidth relative to on-chip storage. Shared memory and registers are much smaller, but they are far faster to access. The paper explicitly notes that the memory hierarchy is organized so that capacity is inversely related to bandwidth. This is why attention kernels must be carefully tiled: the full matrices are too large to keep in the fastest memory levels, so the computation is broken into blocks that fit into shared memory and registers.

For attention, this tradeoff is particularly consequential because the score matrix $\mathbf{S} = \alpha \mathbf{Q}\mathbf{K}^\top$ is $N \times N$, which grows quadratically in the sequence length. Materializing $\mathbf{S}$ and the softmax probabilities $\mathbf{P}$ in HBM, as in standard attention, creates a large bandwidth burden. The FlashAttention family avoids that by performing local softmax updates on blocks of the score matrix and by never storing the full intermediate matrices in global memory. Instead, it processes blocks of queries, keys, and values so that the working set stays within the fast on-chip memory hierarchy.

The paper’s implementation details reflect this bandwidth-capacity balance very directly. Query blocks are loaded into shared memory, key and value blocks are streamed through a circular shared-memory buffer, and partial outputs are accumulated on chip. The use of a staged buffer is a way of matching the flow of data to the finite capacity of shared memory. Because only a limited number of blocks can be resident at a time, the kernel must carefully coordinate when a stage is filled, consumed, and released. This interplay between movement and reuse is a defining feature of the architecture-aware design.

# GPU thread hierarchy: threads, warps, warpgroups, CTAs, clusters, and grids

The paper also emphasizes that GPU execution is organized through a hierarchy of thread groupings. From smallest to largest, these are threads, warps, warpgroups, threadblocks or CTAs, threadblock clusters, and grids. A warp contains $32$ threads. A warpgroup, in the Hopper model used in the paper, is a group of $4$ contiguous warps. CTAs are the workhorse unit of scheduling, and CTAs in the same cluster are co-scheduled on the same GPC in Hopper.

This hierarchy is more than a bookkeeping device; it determines how work is distributed in FlashAttention-3. The algorithm is parallel across batch elements, heads, and query blocks, so a CTA-level view is enough to understand one unit of work. Each CTA is responsible for a tile $\mathbf{Q}_i$ of the query matrix and computes the corresponding tile $\mathbf{O}_i$ of the output. Within that CTA, the work is further divided across warps and warpgroups depending on whether they are producing data, consuming data, or performing asynchronous computation. The paper’s warp-specialized design is built on this hierarchy.

The hierarchy also shapes what kinds of data can be shared efficiently. Shared memory is directly addressable by all threads in a CTA, which makes it ideal for blockwise reuse across warps in the same CTA. Registers, by contrast, are private to each thread and therefore best suited for per-thread fragments and local intermediate values. This distinction is why the kernel uses shared memory for tiles of $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$, but keeps certain intermediate accumulators and pipeline state in registers. Understanding the hierarchy is therefore essential to understanding why the algorithm is arranged in stages and why some data movement is done cooperatively while other data is kept private.

# How shared memory and registers shape kernel design

In FlashAttention-3, shared memory and registers do not merely store data; they determine the structure of the kernel itself. Shared memory is used as a circular buffer for query, key, and value tiles. The producer warpgroup loads tiles from HBM into shared memory, and consumer warpgroups read them back for computation. Because shared memory is programmer-managed, the kernel must explicitly coordinate when a buffer stage is available, when it is being filled, and when it can be reused. The paper’s pseudocode reflects this through wait and release steps, as well as through a pipeline object used to manage barrier synchronization.

Registers are equally important because the consumer side of the algorithm maintains running state across many blocks. In the standard FlashAttention update, each block contributes to a running maximum and a running normalizer for the softmax. These quantities are stored in registers so that the algorithm can rescale intermediate outputs without repeatedly moving data between memory levels. The paper also points out that additional pipeline stages require additional register space. For example, the two-stage overlapped algorithm keeps an extra matrix such as $\mathbf{S}_{\mathrm{next}}$ in registers, which increases register pressure. This matters because register spilling would reduce performance, so the design must trade off deeper pipelining against available register capacity.

This is one reason the paper pays attention to dynamic register reallocation. If some warps are only issuing data movement, they do not need many registers, while warps performing matrix multiply operations need more. By rebalancing register usage according to role, the kernel can make better use of the available on-chip resources. The underlying lesson is that high performance on GPUs is not just about arithmetic throughput; it is about fitting the kernel’s live working set into the right level of the memory hierarchy and assigning resources to the right execution units.

# Tensor Memory Accelerator (TMA) for asynchronous memory movement

A major hardware feature exploited by FlashAttention-3 on Hopper is the Tensor Memory Accelerator, or TMA. The paper describes TMA as a dedicated hardware unit for asynchronous memory copies between global memory and shared memory. This matters because moving blocks of $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$ into shared memory is a recurring task in the attention kernel, and if those copies were done synchronously they would stall the compute pipeline.

TMA changes the design space because memory movement can proceed independently of other operations. In the paper’s warp-specialized kernel, producer warps issue TMA loads of the query, key, and value tiles, while consumer warps perform computation. Since TMA is asynchronous, issuing a load does not require the producer to wait for the corresponding copy to complete before continuing to plan the next one. This is what makes a circular shared-memory buffer useful: while one stage is being consumed, another stage can be filled in the background.

The paper stresses that this hardware capability is what enables the producer-consumer execution model. Instead of having one warpgroup do everything in lockstep, the kernel splits responsibilities so that data movement can be hidden behind computation. In the pseudocode, the producer warpgroup loads $\mathbf{Q}_i$, then repeatedly loads $\mathbf{K}_j$ and $\mathbf{V}_j$ into successive buffer stages. Meanwhile, the consumer warpgroup waits only when necessary and otherwise keeps the pipeline moving. The architectural insight is that memory copies are not merely preparatory work; on Hopper they can be scheduled as an active, overlapping part of the computation.

# Tensor Cores and asynchronous WGMMA on Hopper

FlashAttention-3 also exploits Hopper’s Tensor Cores through the warpgroup-wide WGMMA instruction. The paper highlights an important difference from prior architectures such as Ampere: on Hopper, WGMMA is asynchronous and can source inputs directly from shared memory. This makes it especially well suited to a kernel that continuously streams tiles through shared memory while computing on them.

The asynchronous nature of WGMMA is crucial. In a synchronous design, a warp would issue a matrix multiply and stall until it completed before moving on. In the Hopper model used by FlashAttention-3, a warpgroup can commit a WGMMA and continue with other work while the operation is still in flight. This allows the kernel to overlap arithmetic with other arithmetic or with memory movement. The paper uses WGMMA as a metonym for asynchronous GEMM, because the actual implementation is built around sequences of such matrix multiplications.

This capability is used in two places. First, the kernel uses WGMMA to perform the score computation $\mathbf{Q}_i \mathbf{K}_j^\top$. Second, it uses WGMMA again to apply the softmax probabilities to the value tile, computing $\widetilde{\mathbf{P}}_i^{(j)} \mathbf{V}_j$. Because both operations are substantial matrix multiplies, Hopper’s Tensor Cores are the natural units to execute them. The key design problem is to schedule them so that they can overlap with the softmax work and with the data movement handled by TMA. The paper’s answer is to combine WGMMA with warp specialization and pipelining.

# Warp specialization and producer-consumer execution models

Warp specialization is one of the paper’s central architectural ideas. The basic concept is to divide the warps of a CTA into distinct roles so that some warps act as producers, handling data movement, while others act as consumers, handling computation. This fits Hopper particularly well because TMA handles memory movement asynchronously and WGMMA handles matrix multiplications asynchronously. By separating the duties, the kernel can keep both kinds of hardware units busy.

The producer-consumer split also helps the compiler generate better instruction schedules. The paper notes that warp specialization generally improves the compiler’s ability to produce optimal instruction sequences. In the FlashAttention-3 kernel, producer warps issue loads into shared memory, while consumer warpgroups perform the GEMMs and softmax-related updates. This role separation is especially useful because different roles need different amounts of register space and have different latency-hiding responsibilities.

The paper goes further and combines warp specialization with “pingpong” scheduling. In that scheme, one warpgroup performs the softmax while another warpgroup is executing GEMMs, and then the roles swap. The motivation is that softmax involves much lower-throughput operations than matrix multiplication, especially exponential calculations. By moving these two kinds of work onto different warpgroups, the kernel can overlap them more effectively. This is a concrete example of how a hardware-aware execution model shapes the structure of the algorithm: the computation is not simply parallelized, but partitioned by hardware role and latency profile.

# Dynamic register reallocation with setmaxnreg

Hopper introduces another mechanism that FlashAttention-3 exploits: dynamic reallocation of registers between warpgroups using $\verb|setmaxnreg|$. The paper explains that this matters because the warps performing matrix multiplications need more register space than the warps that are only issuing TMA loads. In a warp-specialized kernel, not every warp has the same register demand, so a static equal split would be wasteful.

By using $\verb|setmaxnreg|$, the kernel can deallocate some registers from the producer-side warps and reallocate them to the consumer-side warps. This is particularly valuable because the consumer warps store intermediate values, maintain softmax statistics, and may hold extra buffers for pipelining. Meanwhile, the producer side, which mostly orchestrates memory copies, can operate with a smaller register budget. The paper describes this as a way of allowing the warps doing MMAs to obtain a larger share of register memory than those just issuing TMA.

This detail may sound implementation-specific, but it captures an important broader theme of the paper: modern GPU efficiency comes from matching resource allocation to functional role. Instead of treating all threads the same, FlashAttention-3 adapts register usage to the needs of each part of the pipeline. That flexibility is part of what lets the algorithm achieve better utilization on Hopper than the earlier FlashAttention designs.

# Low-precision formats on modern GPUs: FP16, BF16, FP8, and the trend toward lower precision

The paper places Hopper’s low-precision support in a broader historical trend. GPUs have steadily added specialized hardware for lower-precision arithmetic, moving from FP16 on Pascal in 2017 to BF16 on Ampere in 2020 and then FP8 on Hopper. The reason is straightforward: lower precision can deliver more throughput for the same power and chip area. The paper mentions that the FP8 Tensor Cores on Hopper can provide roughly twice the throughput per SM compared with FP16 or BF16.

However, lower precision is not just a performance opportunity; it is also a design constraint. FlashAttention-3 has to preserve numerical accuracy while taking advantage of FP8 throughput. The paper emphasizes that this is especially challenging in the presence of outlier features, which are common in large language models and can be much larger in magnitude than typical values. Quantization becomes difficult when a few large values dominate the scale of an entire tensor. That is why the paper does not simply “switch to FP8” but instead adapts the algorithm with block quantization and incoherent processing.

Another important low-precision detail in the paper is that precision affects layout requirements as well as numerical behavior. FP8 WGMMA on Hopper imposes stricter layout constraints than FP16 WGMMA, such as requiring k-major input operands for certain cases. This means that the move to lower precision is not only a matter of arithmetic format; it also changes how tiles must be arranged in shared memory and how the kernel must prepare operands for the Tensor Cores. Thus, the trend toward lower precision is tightly coupled to the hardware execution model and to the memory hierarchy described earlier.

Taken together, the paper’s treatment of low precision shows why attention kernels must be co-designed with hardware. Throughput gains from FP8 are real, but they come with layout restrictions and accuracy challenges. FlashAttention-3 addresses both by aligning its tile-based algorithm with Hopper’s execution units and by introducing quantization strategies that preserve the quality of the attention computation.
