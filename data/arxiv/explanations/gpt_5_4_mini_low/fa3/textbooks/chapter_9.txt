\title{A Textbook about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

Chapter 9: 9. FP8 Attention on Hopper: Layout Constraints and Kernel Design

# Why FP8 promises major throughput gains

One of the central motivations for moving attention to FP8 is that modern GPU hardware has specialized support for low-precision arithmetic. In the paper, FP8 is presented as part of a continuing trend in GPU number formats: FP16 on Pascal, BF16 on Ampere, and FP8 on Hopper. The key promise is simple: if the hardware can do the same kind of matrix multiplication using fewer bits, then it can achieve higher throughput for the same power and chip area. For attention, this matters because the attention mechanism is already the main bottleneck in Transformer models, and improving its throughput directly improves the performance of large language models and long-context applications.

The paper emphasizes that Hopper’s FP8 support is not just a minor numerical format change. It is tied to a hardware path that can nearly double the measured TFLOPs/s compared to FP16. In the paper’s empirical results, FP8 FlashAttention-3 reaches close to $1.2$ PFLOPs/s, which shows how large the performance upside can be when the kernel is adapted correctly to the hardware. At the same time, the paper is careful to note that FP8 introduces accuracy challenges, especially in the presence of outlier features, so the performance benefit comes with design constraints that the kernel must handle explicitly.

# Hopper FP8 WGMMA versus FP16 WGMMA

The paper’s discussion of Hopper centers on WGMMA, the warpgroup-wide matrix-multiply instruction. For FP16 WGMMA, the hardware is comparatively flexible: it accepts both mn-major and k-major input operands when the data lives in shared memory. That flexibility makes FP16 easier to integrate into fused attention kernels, because the kernel can more readily reuse layouts that naturally arise from standard tensor storage and intermediate computations.

FP8 WGMMA is different. The paper states that on Hopper, FP8 WGMMA only supports k-major input operands. This means that, unlike FP16, the operand layout must be arranged so that the data is contiguous in the inner $K$ dimension rather than the outer $M$ or $N$ dimension. This difference is not merely an implementation detail. It affects how attention must move data between global memory, shared memory, registers, and the Tensor Cores, because the kernel must present each operand in a layout that the FP8 instruction expects.

The consequence is that a fused attention kernel can no longer treat the GEMM stages as layout-agnostic. The paper’s FP8 design has to account for the exact layout conformance rules of WGMMA. In other words, the kernel must be redesigned not only for arithmetic precision but also for how the data is physically organized at the moment the Tensor Core consumes it.

# mn-major and k-major operand layouts

To describe the layout requirements of WGMMA, the paper uses the terms mn-major and k-major. In a GEMM call that multiplies $A \times B^\top$, where $A$ is an $M \times K$ matrix and $B$ is an $N \times K$ matrix, an operand is mn-major if it is contiguous in the outer $M$ or $N$ dimension. It is k-major if it is contiguous in the inner $K$ dimension. This distinction captures whether the data is laid out so that adjacent memory locations correspond to rows or columns of the logical matrix.

The point of introducing this vocabulary is that the correct layout depends on the specific WGMMA variant. For FP16, the kernel can work with either format in shared memory. For FP8, the operand must be k-major. That requirement becomes especially important in attention, because attention is not a single GEMM but a composition of GEMMs and softmax, and the intermediate results must be arranged so that the next operation can consume them without a costly rearrangement.

This is why the paper frames layout as a hardware constraint rather than a superficial storage preference. The layout of a tensor affects whether it can be fed efficiently into FP8 WGMMA at all. In FP8 FlashAttention-3, the design must therefore coordinate the layout of the key, value, and accumulator fragments so that the sequence of GEMMs remains executable on the FP8 Tensor Cores.

# Why FP8 WGMMA requires k-major operands in shared memory

The paper’s FP8 constraint is specifically about operands in shared memory. The text explains that for FP8 WGMMA, only the k-major format is supported for inputs in shared memory. This matters because FlashAttention-style kernels keep tiles in shared memory to avoid repeated movement through global memory. If the shared-memory tile is not laid out in the format the Tensor Core expects, the kernel cannot directly invoke the instruction on that tile.

This is particularly important in attention because the kernel is built around block processing. Each block of $K$ and $V$ must be loaded into shared memory, used by WGMMA, and then released so that the next block can be processed. If the layout in shared memory is wrong, the kernel either has to transform the data or abandon the ability to use FP8 WGMMA efficiently. So the layout restriction is not an incidental inconvenience; it directly shapes the kernel structure.

The paper also notes that the problem becomes harder when one wants to fuse back-to-back GEMMs in a single kernel. In such a fused design, the output of one GEMM becomes the input of the next. If the output is stored in one layout and the next instruction expects a different one, the kernel must bridge that mismatch somehow. That is exactly what happens in FP8 FlashAttention-3, and it is the reason the paper devotes substantial attention to transpose and register-layout transformations.

# The challenge of back-to-back GEMMs in fused attention kernels

Attention is not just a matrix multiplication; it is a sequence of operations. In the forward pass, the kernel computes scores with $\mathbf{Q}\mathbf{K}^\top$, applies softmax, and then multiplies by $\mathbf{V}$. In a fused kernel, these stages are kept on-chip as much as possible so that intermediate matrices do not have to be written to global memory. This is the core FlashAttention idea, and FlashAttention-3 builds on it.

The challenge in FP8 is that the output of the first GEMM and the operand requirements of the second GEMM do not naturally align. In the paper’s discussion, the accumulator layout produced by the first FP8 WGMMA does not match the operand layout expected by the second FP8 WGMMA when that operand is held in registers. This means that even if the attention computation is mathematically straightforward, the hardware-level data representation is not. The kernel has to convert between representations while preserving the performance advantage of fusion.

This creates a tension that is central to the FP8 design. On one hand, the kernel wants to keep everything fused so that attention stays memory efficient. On the other hand, the hardware’s layout constraints mean that the intermediate representations must sometimes be transformed before the next WGMMA can run. FlashAttention-3 resolves this tension by combining layout-aware transpose work with careful register permutation.

# Why V must be transformed for the second GEMM

In the FP8 forward pass, the paper identifies $\mathbf{V}$ as the key tensor that must be transformed for the second GEMM. The reason is that the second GEMM in attention multiplies the softmax probabilities by the value matrix, and FP8 WGMMA requires the operand to be in k-major format. However, tensors such as $\mathbf{V}$ are typically laid out contiguous in the head dimension, which is not the layout needed by the FP8 instruction when the tile is in shared memory.

The paper explains that because the TMA load itself cannot change the contiguous dimension, simply loading $\mathbf{V}$ from global memory does not solve the problem. The tile must either be transposed before it reaches shared memory or transposed after it has been loaded there. Without this transformation, the second GEMM cannot be executed in the desired FP8 format.

This is an especially important point in fused attention, because the second GEMM depends on the softmax output from the first stage. If the kernel has to pause and move data inefficiently, the benefits of low precision are reduced. FlashAttention-3 therefore treats the transformation of $\mathbf{V}$ as a first-class part of the kernel design rather than as a separate preprocessing step.

# Options for meeting layout constraints: preprocessing transpose versus in-kernel transpose

The paper considers two broad ways to satisfy the FP8 layout requirement for $\mathbf{V}$. The first is to transpose $\mathbf{V}$ ahead of time in global memory. This could be done either by fusing the transpose into the epilogue of a preceding step, such as rotary embedding, or by running a standalone preprocessing transpose kernel. The second is to perform the transpose inside the attention kernel, after loading tiles of $\mathbf{V}$ into shared memory.

The paper explains why the first approach is awkward. Fusing the transpose into an earlier operation is difficult to integrate into a standard library workflow, and a standalone transpose kernel is unattractive in a memory-bound setting. Since attention, especially in inference, is often limited by memory traffic, adding an extra global-memory pass just to rearrange $\mathbf{V}$ would waste bandwidth and undermine the efficiency gains of the fused kernel.

Because of this, FlashAttention-3 chooses the second approach: in-kernel transpose. This decision keeps the transformation on-chip and avoids introducing a separate global-memory-intensive preprocessing phase. The kernel can then reorganize the data exactly where and when it is needed, which aligns with the overall FlashAttention philosophy of minimizing slow memory traffic.

# Why standalone transposes are unattractive for memory-bound inference

The paper’s reasoning against a standalone transpose is rooted in memory bandwidth. An optimized transpose kernel can run near device bandwidth, but that is precisely the problem: if the system is already memory-bound, then spending bandwidth on a separate transpose is expensive. In inference, where the goal is often to maximize throughput and minimize latency, such extra traffic can erase much of the benefit of moving the actual attention computation to FP8.

The issue is not that transpose kernels are slow in an absolute sense. Rather, they consume a significant amount of the same scarce resource that attention is trying to save: memory bandwidth. FlashAttention-3 is designed to reduce reads and writes to global memory, so introducing a separate kernel that does little besides rearranging bytes would go against the central design principle.

This is why the paper treats in-kernel transposition as the more suitable choice. By keeping the transformation local to the attention kernel, the method preserves the fused execution model and reduces the chance that layout adaptation becomes a bottleneck in its own right.

# Using LDSM/ldmatrix and STSM/stmatrix for in-kernel transpose

To perform the in-kernel transpose, the paper uses LDSM and STSM instructions, exposed as $ldmatrix$ and $stmatrix$. These instructions let a warp collectively load data from shared memory into registers and then store data back from registers to shared memory at a granularity of 128 bytes. The paper notes that although the PTX documentation describes these as copying $8 \times 8$ matrices with 16-bit entries, the same machinery can be adapted to packed 8-bit data, which is the relevant case for FP8.

The important property of these instructions is that they are register efficient and naturally suited to warp-level cooperation. That makes them a good fit for the producer side of the FlashAttention-3 kernel. By using LDSM to pull a tile into registers, rearranging the register contents as needed, and then using STSM to write the data back in a transposed form, the kernel can convert the layout without leaving the chip. This avoids the cost of moving the tile through global memory just to change its orientation.

The paper also notes a subtlety: the transpose versions of LDSM/STSM cannot split packed 8-bit entries, so the kernel needs certain register movements between the load and store to actually accomplish the tile-wise transpose. The paper does not detail every low-level step, but the high-level takeaway is clear: the transpose is implemented as a carefully orchestrated on-chip register-and-shared-memory transformation.

# Performing transpose work in the producer warpgroup

In FlashAttention-3, the transpose is performed in the producer warpgroup. This is a natural place for it because the producer is already responsible for data movement. The paper’s warp-specialized design divides work into producer and consumer warpgroups, with the producer handling loading and buffer management and the consumer handling the matmul-heavy computation. Since the transpose belongs to the data-movement side of the kernel, it can be assigned to the producer without interfering with the consumer’s computation.

This choice also fits the asynchronous execution model of Hopper. The producer can execute the transpose work while the consumer is busy with GEMMs and softmax-related computation. In this way, the transpose becomes part of the data-flow pipeline instead of a separate serial step. The kernel can continue feeding data to the consumer while the producer prepares the next $\mathbf{V}$ tile in the correct layout.

The paper stresses that this placement makes the transpose much more practical. A producer warpgroup is already the locus of TMA loads and buffer staging, so adding transpose logic there preserves the division of labor that warp-specialization is designed to achieve. The producer becomes responsible not only for fetching data but also for shaping it into the exact form needed by FP8 WGMMA.

# Overlapping V-tile transpose with prior GEMMs

The final refinement in the paper’s FP8 design is that the transpose of the next $\mathbf{V}$ tile can be overlapped with the two WGMMA operations that involve the preceding $\mathbf{V}$ tile and the current $\mathbf{K}$ tile. This is one of the reasons the in-kernel approach is effective: the transpose does not have to appear as a standalone phase that stalls the kernel. Instead, after the first iteration, the kernel can hide the transpose behind ongoing GEMM work.

This overlap is consistent with the paper’s broader strategy of exploiting asynchrony. Hopper’s Tensor Cores and TMA permit data movement and computation to proceed independently enough that the kernel can interleave them. In the FP8 case, the producer can prepare the next transposed $\mathbf{V}$ tile while the consumer is still processing the current attention block. That means the layout conversion is amortized across useful work rather than paid as a visible pause.

Seen together, these design choices explain how FlashAttention-3 makes FP8 practical on Hopper. The kernel does not merely “use FP8”; it adapts the layout of the data, the placement of work across warpgroups, and the timing of the transpose so that the hardware can actually execute the fused attention pipeline efficiently.
