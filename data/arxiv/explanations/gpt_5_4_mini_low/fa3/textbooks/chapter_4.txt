\title{A Textbook about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

Chapter 4: 4. From Standard Attention to FlashAttention and FlashAttention-2

# Standard attention and the cost of materializing $S$ and $P$ in global memory

To understand why the FlashAttention line of work exists, it helps to start from the standard formulation of attention. For a single head, we have query, key, and value matrices $\mathbf{Q}, \mathbf{K}, \mathbf{V} \in \mathbb{R}^{N \times d}$, where $N$ is the sequence length and $d$ is the head dimension. The attention output is computed by first forming the score matrix $\mathbf{S} = \alpha \mathbf{Q}\mathbf{K}^\top$, then applying row-wise softmax to obtain $\mathbf{P} = \mathrm{softmax}(\mathbf{S})$, and finally multiplying by the values to get $\mathbf{O} = \mathbf{P}\mathbf{V}$. Usually $\alpha = 1/\sqrt{d}$, and in practice one subtracts the row maximum of $\mathbf{S}$ before applying the exponential to improve numerical stability.

The key issue is that $\mathbf{S}$ and $\mathbf{P}$ are both $N \times N$ matrices. As sequence length grows, these intermediate matrices become very large. If a GPU implementation materializes them in global memory, then it must write them out and later read them back, which is expensive because global memory is the slowest and most bandwidth-limited level of the GPU memory hierarchy discussed in the paper. In other words, the naive implementation does not just perform a lot of arithmetic; it also performs a large amount of memory traffic on the very intermediates that are only needed transiently.

This is exactly why the paper describes standard attention as an implementation that materializes the intermediate matrices $\mathbf{S}$ and $\mathbf{P}$ to HBM. The problem is not only that these tensors are large, but also that they are not needed as standalone outputs of the layer. They are merely temporary quantities required to compute $\mathbf{O}$. From the perspective of performance, storing them in global memory is wasted work.

# The IO-aware design principle behind FlashAttention

FlashAttention was introduced to address this memory-traffic bottleneck directly. The paper describes it as an IO-aware approach: instead of treating attention as a purely algebraic expression, the algorithm is designed with the GPU memory hierarchy in mind. The central goal is to minimize reads and writes to slow global memory by keeping intermediate results on-chip whenever possible.

The intuition is simple but powerful. If an intermediate quantity is only useful for the next few instructions, then it should ideally live in shared memory or registers rather than being written out to HBM. FlashAttention reorganizes the computation so that the full score matrix $\mathbf{S}$ and probability matrix $\mathbf{P}$ never need to be stored in global memory. Instead, the algorithm processes attention in tiles, computes local partial results, and combines them in a way that reproduces the exact output.

This is what the paper means by integrating knowledge of the GPU execution model into the algorithmic design. Rather than computing the entire attention matrix at once, FlashAttention computes it in pieces that fit into on-chip storage. That change matters because the GPU is much faster when the working set stays on-chip and when the algorithm avoids unnecessary global-memory traffic. In the paper’s framing, FlashAttention is not an approximation; it is an exact attention algorithm that is reorganized to better match the hardware.

# Local softmax and fused-kernel execution

A central ingredient of FlashAttention is the local softmax reduction. Standard softmax over a row of scores requires knowing the row maximum for numerical stability, and then normalizing by the sum of exponentials. If the whole row is not stored in memory, one cannot simply compute softmax in the usual “all at once” way. FlashAttention solves this by maintaining running summaries as it processes blocks.

The paper explains that local softmax corresponds to the consumer-side operations in the FlashAttention-3 pseudocode, together with rescalings of blocks of $\mathbf{O}$. The idea is that each tile of scores contributes to the final output, but the algorithm keeps track of the row-wise maximum and the normalization factor incrementally. This allows the output to be assembled block by block while remaining mathematically equivalent to standard attention.

This local treatment of softmax is closely tied to kernel fusion. Instead of splitting attention into separate GPU kernels for matrix multiplication, softmax, and the final multiplication by $\mathbf{V}$, FlashAttention fuses these operations into a single kernel. That fusion is important because it removes the need to write intermediate matrices to HBM between stages. It also means the algorithm can keep intermediate quantities on chip and immediately reuse them, which is precisely what gives FlashAttention its efficiency advantage over standard attention.

# Tiling attention to avoid expensive intermediate reads and writes

The paper emphasizes that FlashAttention’s performance comes from a tiling strategy. Rather than computing attention over the full $N \times N$ score matrix, the algorithm splits the query sequence into blocks and processes each query tile against blocks of keys and values. This lets the implementation work with smaller subproblems that fit into shared memory and register storage.

The tiled computation changes how the algorithm is scheduled on the GPU. A block of queries can be paired with successive blocks of keys and values, and the algorithm maintains running state for the output tile $\mathbf{O}_i$ along with the softmax statistics $\ell_i$ and $m_i$. The paper’s pseudocode shows how each block of scores is used to update these values, and then how the partial output is rescaled and accumulated. This makes it possible to compute exact attention without ever materializing the full matrices $\mathbf{S}$ and $\mathbf{P}$ in HBM.

This tiling strategy is not just a coding trick; it changes the fundamental cost profile of attention. The paper presents FlashAttention as a way to replace slow global-memory traffic with much cheaper on-chip computation and synchronization. The result is that the algorithm becomes far more suitable for long-sequence workloads, where the size of the score matrix would otherwise dominate the cost of the layer.

# FlashAttention-2: improved work partitioning and parallelization over sequence length

FlashAttention-2 built on FlashAttention by restructuring the algorithm to better use the GPU. According to the paper, FlashAttention-2 parallelizes over the sequence-length dimension and performs the inner loop of the forward pass over blocks of the key and value matrices. This improves occupancy and distributes work more effectively across the GPU.

This is an important step forward because FlashAttention-1 already reduced memory traffic, but it did not fully exploit the parallelism available in modern hardware. FlashAttention-2 addresses that by changing the organization of the computation so that more work can be carried out concurrently. The paper describes this as a reworking of the algorithm to improve the occupancy and distribution of work on the GPU. In other words, more of the hardware is kept busy.

However, FlashAttention-2 still uses a simplified synchronous model. It does not explicitly design around asynchrony or low-precision hardware features. That is why, even though it is more efficient than standard attention, the paper observes that it still falls short of what newer GPU architectures can do. FlashAttention-2 is a major improvement, but it is not the final step.

# Why FlashAttention-2 underutilizes Hopper GPUs

The paper’s central motivation for FlashAttention-3 is that FlashAttention-2 underutilizes Hopper GPUs relative to optimized GEMM kernels. On the H100 GPU, FlashAttention-2 achieves only about $35\%$ utilization, while optimized matrix-multiplication kernels can reach about $80$--$90\%$. This gap is large enough that it cannot be dismissed as a minor implementation detail.

Part of the issue is implementation-level: FlashAttention-2 did not use Hopper-specific instructions where they would have helped. The paper notes that newer work and libraries have shown that Hopper-specific instructions and tile-based abstractions can improve attention performance and simplify implementation. But the deeper issue is algorithmic. FlashAttention-2 is built around a synchronous execution model that does not explicitly exploit the fact that Hopper separates data movement and matrix multiplication into specialized asynchronous hardware units.

In the paper’s view, this is the key limitation. FlashAttention-2 improves the organization of the work, but it still assumes a more conventional execution model than Hopper actually provides. As a result, it does not fully hide memory and instruction latencies, and it does not make full use of the Tensor Cores and TMA in the way a Hopper-native algorithm can.

# Measured utilization gap between attention kernels and optimized GEMM kernels

The paper repeatedly compares FlashAttention-2 to optimized GEMM kernels because GEMM is the kind of workload that modern GPUs handle especially well. On H100, optimized matrix-multiplication kernels can achieve very high utilization, while FlashAttention-2 remains far lower. The paper gives the specific comparison of $35\%$ utilization for FlashAttention-2 versus roughly $80$--$90\%$ for optimized GEMM kernels.

This comparison is important because it tells us that the bottleneck is not simply “attention is hard.” Rather, it reveals that attention, as implemented in FlashAttention-2, is not yet aligned with the hardware’s best execution paths. Since the GPU is built to accelerate matrix multiplication extremely efficiently, an attention kernel that leaves that capability underused is effectively leaving performance on the table.

The paper’s later results reinforce this point. FlashAttention-3 reaches up to $740$ TFLOPs/s on H100, corresponding to about $75\%$ utilization, and FP8 performance approaches $1.2$ PFLOPs/s. These numbers show that much more of the GPU can be used when the algorithm is redesigned to better match the architecture. The fact that FlashAttention-2 sits far below these levels is exactly what motivates the new design.

# Why new hardware features require a redesign rather than a simple port

A natural question is why one cannot simply port FlashAttention-2 to Hopper and expect large gains. The paper’s answer is that Hopper introduces hardware features that change what a good algorithm looks like. In particular, Hopper provides asynchronous Tensor Cores via WGMMA and a Tensor Memory Accelerator for asynchronous data movement. It also supports low-precision FP8 computation. These are not just faster versions of old operations; they introduce new possibilities and new constraints.

Asynchrony changes the structure of the computation. If matrix multiplication and memory movement can proceed asynchronously, then the algorithm can overlap them rather than waiting for each stage to finish before starting the next. But to exploit this, the algorithm must be reorganized so that data producers and consumers can be separated, and so that the software can pipeline different parts of the work. That is a design problem, not a simple replacement of one instruction with another.

Low precision also requires redesign. FP8 can provide roughly double the throughput of FP16 or BF16 on Hopper, but it comes with reduced numeric range and precision. In attention, this matters because the computation can be sensitive to outliers in the input features. The paper therefore uses block quantization and incoherent processing to control error. None of this is handled by the original FlashAttention-2 design, which was not built to target FP8 Tensor Cores or to manage the layout restrictions they impose.

So the paper’s larger point is that Hopper is not merely “faster hardware.” It is hardware with new capabilities that require the algorithm to be rethought around asynchrony, specialized memory movement, and low-precision execution. FlashAttention-2 was a major step forward, but FlashAttention-3 is needed to fully exploit those features.
