\title{A Textbook about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

Chapter 12: 12. Pre-Training Lessons: Code Helps, arXiv Does Not Always

# The Hypothesis that Code Training Improves Reasoning

A common idea in language-model research is that training on code may improve reasoning. The paper treats this as an important but not fully settled hypothesis and uses mathematical reasoning as a test case. The authors do not claim that code training magically creates general intelligence. Instead, they present evidence that code training does help models reason about mathematics, both when the model is allowed to use tools and when it must solve problems in natural language alone.

The intuition behind this result, as reflected in the paper’s experiments, is that code training exposes a model to structured, executable, stepwise patterns that are closer to the discipline required in mathematical problem solving than ordinary text is. The paper’s main point is not simply that code is useful, but that code can serve as a strong intermediate training stage before math training, improving the eventual mathematical reasoning performance of the model.

# Two-Stage Training: Code Then Math vs. General Then Math

To examine the role of code more carefully, the authors compare two-stage training setups. In one setting, DeepSeek-LLM 1.3B is first trained on 400B code tokens and then on 150B math tokens. In the control setting, the first stage uses 400B general tokens sampled from a large-scale general corpus instead of code tokens, followed again by 150B math tokens. This comparison is designed to isolate whether code provides something qualitatively better than ordinary text when used as the initial training domain.

The results show that code training is more beneficial than general training for later mathematical reasoning. Under the two-stage setup, the code-first model already improves significantly after the code stage, and the later math stage improves it further. By contrast, starting from general data does not provide the same advantage. The paper’s interpretation is that code tokens provide a more useful pre-training foundation for later math learning than generic text tokens do.

This is an important lesson because it suggests that not all auxiliary pre-training data are equally useful for a target reasoning domain. The value of a first training stage depends on how well that stage prepares the model for the structure of the downstream task.

# One-Stage Training: Math Only vs. Mixed Code and Math

The authors also test one-stage training, where code and math are mixed together instead of being learned sequentially. One comparison is math-only training for 150B tokens. Another is a mixture of 400B code tokens and 150B math tokens in a single training stage. This setup probes whether code still helps when it is not used as a separate precursor stage.

The paper finds that mixing code and math in one stage has a more complicated effect. On the one hand, it helps preserve coding ability while also supporting program-aided mathematical reasoning. On the other hand, for mathematical reasoning without tools, this mixed one-stage approach is not as strong as the two-stage code-then-math pipeline. The authors suggest that the smaller model may not have enough capacity to fully absorb both domains at once when they are trained jointly, even though the mixture can still be useful in some respects.

So the chapter-level lesson is subtle: code is beneficial, but the training schedule matters. Sequential learning and mixed learning do not behave identically, and the best arrangement depends on the kind of reasoning one wants to strengthen.

# Effects on Tool-Free Mathematical Reasoning

The paper distinguishes between solving mathematics in plain natural language and solving it with external tools. For tool-free reasoning, the two-stage code-first strategy is especially helpful. The authors report that code training alone already produces moderate gains, and the later math stage leverages that foundation to achieve the best performance.

This means that code training is not only useful for tasks that explicitly involve writing programs. It also improves the model’s ability to reason through mathematical problems without tool use. In other words, the benefit of code is not confined to direct program generation; it appears to transfer into the internal structure of mathematical reasoning itself.

At the same time, the paper shows that mixing code and math in a single stage can compromise tool-free reasoning. This reinforces the idea that the benefit of code is not simply a matter of adding more tokens from another structured domain. The training dynamics matter, and the model’s capacity to integrate multiple domains simultaneously is limited.

# Effects on Program-Aided Mathematical Reasoning

The benefit of code becomes even clearer when the model is allowed to use programs as part of its solution process. The paper evaluates program-aided reasoning using Python-based solutions for mathematical problems, where the program output is taken as the answer. In this setting, code training provides a strong advantage.

Under the two-stage setup, code training alone already substantially improves the model’s ability to solve GSM8K and MATH using Python. Then math training in the second stage yields further gains. The paper interprets this as evidence that code tokens are directly aligned with the format and logic needed for tool-assisted reasoning.

The one-stage mixed setup is also favorable for program-aided reasoning. In fact, the paper notes that mixing code and math can synergize coding and program-aided mathematical reasoning. This is a useful contrast with the tool-free case: the same mixed training strategy that weakens pure mathematical reasoning can still be helpful for tasks where code execution is part of the solution process.

# Catastrophic Forgetting and How Mixed Training Can Mitigate It

A key phenomenon discussed in this section is catastrophic forgetting. In the two-stage setting, if the model is trained on code first and then on math, its coding performance can degrade during the math stage. The paper investigates whether training with a mixture of code and math can reduce this problem.

The answer is yes. When code tokens and math tokens are combined in a one-stage training regime, the model avoids some of the forgetting that appears in the sequential setup. This mixed approach helps preserve coding capability while still supporting mathematical reasoning, especially program-aided reasoning. The paper frames this as a tradeoff: mixing the domains can be beneficial for retention and for certain reasoning modes, even if it is not always optimal for pure tool-free mathematical performance.

This result is practically important because it shows that the order and composition of training data can determine whether one capability is maintained while another is learned. The paper therefore treats catastrophic forgetting not as a side note, but as a major factor in designing multi-domain pre-training recipes.

# Interaction Between Model Size and Multi-Domain Learning

The paper offers a conjecture about why mixed training can hurt tool-free math reasoning in the one-stage setting. The authors suggest that DeepSeek-LLM 1.3B may simply be too small to fully absorb both code and mathematics at the same time. This is not presented as a proven law, but as a plausible explanation grounded in their results.

The broader implication is that model size interacts with training composition. A smaller model may benefit more from staged learning, where one domain prepares the model for another, rather than from simultaneous exposure to several specialized domains. The paper’s results do not say that multi-domain training is bad in general. Rather, they show that the benefit depends on whether the model has enough capacity to integrate the domains without interference.

This is one of the most important practical lessons in the chapter: corpus design cannot be separated from model scale. The same data mixture may behave differently in a smaller model than in a larger one.

# The Widespread Use of arXiv in Math Pre-Training

The paper turns next to arXiv papers, which are widely used in mathematical pre-training corpora. This usage has become common in the field, often under the assumption that scientific and mathematical papers should naturally help mathematical reasoning. The authors explicitly question this assumption.

Rather than treating arXiv as obviously beneficial, they test it empirically. Their discussion notes that arXiv is frequently included in math pre-training corpora such as MathPile and Proof-Pile-2, but the detailed effect of arXiv on reasoning ability has not always been carefully examined. The paper therefore uses arXiv-focused experiments to ask whether a large quantity of academic text actually helps models solve mathematical problems better.

# Experiments with MathPile and ArXiv-RedPajama

The paper studies two arXiv-based corpora. The first is MathPile, an $8.9$B-token corpus where over $85\%$ of the data comes from scientific arXiv papers. The second is ArXiv-RedPajama, which contains the full arXiv LaTeX files after removing preambles, comments, macros, and bibliographies, totaling $28.0$B tokens.

To test their effect, the authors train DeepSeek-LLM 1.3B for $150$B tokens and DeepSeek-Coder-Base-v1.5 7B for $40$B tokens on these corpora. They then evaluate the models on a range of mathematical benchmarks, including quantitative reasoning tasks such as GSM8K and MATH, multiple-choice tasks such as MMLU-STEM, and formal mathematics tasks such as miniF2F.

The conclusion is surprisingly negative. Across these benchmarks, arXiv-only training does not produce meaningful improvements, and in some cases performance worsens. This result holds despite the strong reputation of arXiv as a source of technical content.

# Why arXiv-Only Training Showed Little or Negative Benefit in This Study

The paper’s empirical finding is that arXiv papers appear ineffective for improving mathematical reasoning in the setups tested. That conclusion is based on the observation that both a general model and a code model showed no notable gains, or even deterioration, after arXiv-only training. In other words, the presence of mathematical or scientific exposition in arXiv was not enough, by itself, to make the model better at the benchmarks considered in the paper.

The paper does not overinterpret this result as proving that arXiv is useless in all settings. Instead, it presents the finding as evidence that arXiv may not be as helpful as many researchers assume, at least when used alone and under the particular experimental conditions studied here. The broader message is that not all academically themed text automatically translates into better mathematical reasoning.

# Caveats and Limits of the arXiv Conclusion

The authors are careful to limit the scope of their conclusion. They explicitly say the result should be taken with a grain of salt. In particular, they have not studied whether arXiv helps with tasks not included in their benchmark suite, such as informalization of theorems. They also have not tested whether arXiv might become useful when combined with other types of training data. Finally, they note that the effect of arXiv at much larger model scales remains open.

These caveats matter because they keep the conclusion grounded in the experiments actually performed. The paper is not claiming that arXiv can never help. It is claiming that, in the tested settings, arXiv-only training did not provide the expected benefit for the mathematical reasoning benchmarks they used.

# What These Findings Imply for Future Domain-Specific Corpus Design

The paper’s broader lesson is that corpus design should be empirical rather than assumption-driven. Code clearly has value for mathematical reasoning, but the way code is introduced matters. Sequential code-then-math training can be especially effective, while mixed training has tradeoffs and may depend on model size. arXiv, despite its popularity, is not guaranteed to improve reasoning and may even be unhelpful if used in isolation.

Taken together, these findings suggest that building a domain-specific corpus is not just a matter of collecting any text related to the field. The data must be selected and organized according to how it will shape reasoning behavior. The DeepSeekMath paper argues that carefully engineered web-scale mining can outperform more conventional assumptions about what counts as “useful” mathematical text.

For future work, the implication is clear: researchers should test the actual effects of data sources, not just their intuitive appeal. A good corpus is not defined by prestige or familiarity, but by whether it measurably improves the model’s intended capabilities.
