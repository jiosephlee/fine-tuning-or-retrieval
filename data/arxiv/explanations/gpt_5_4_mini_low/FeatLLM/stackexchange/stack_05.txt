\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Why does FeatLLM need a separate parsing prompt instead of enforcing a stricter rule syntax from the start?
Question:
One thing that surprised me is that the paper uses the LLM twice: first to generate natural-language rules, and then again to convert those rules into executable Python code.

I would have expected the authors to ask the LLM to directly output a machine-readable format such as JSON, Python conditionals, or a small domain-specific language. Instead, they generate rules in text and then do another LLM call for parsing.

Why is this second step necessary? Is the claim that LLMs produce better rules when they are allowed to write them somewhat naturally, rather than under a strict syntax constraint? Or is it mainly a robustness issue because even "formatted" outputs can be noisy?

I'm trying to understand whether this design is principled or just a practical workaround.
Answer:
The second LLM call is not there because the authors believe a natural-language rule representation is inherently better than a machine-readable one; it is there because, in this paper’s design, the first call is optimized for *rule discovery*, while the second is optimized for *robust conversion* of those rules into executable features.

The key idea in \textsf{FeatLLM} is that rule generation and rule parsing are two different problems. In the first stage, they want the model to reason like an expert and produce useful class-specific criteria. The paper explicitly says the prompt is designed to encourage a two-step reasoning process: first infer the relationship between features and the task using prior knowledge, then derive decisive rules from the examples. This is meant to improve the quality of the rules, especially in few-shot settings, and to avoid forcing the model into a rigid syntax too early, which could distract from the reasoning.

But once the rules are generated, they need to be turned into binary features for every sample. At that point, the issue is no longer reasoning quality but *machine executability*. The paper says that even with formatting instructions, the LLM output can still contain noisy syntactic variations, such as writing “greater than” instead of $>$ or “less than” instead of $<$. So a hard-coded parser would be brittle: it would work only if the output matched the exact expected syntax. That is why they use the LLM again for parsing. Since the model is good at understanding semantics despite surface-level variation, they let it translate the natural-language rules into simple Python code.

So the design is mainly a robustness workaround, not a claim that strict formats are impossible. In fact, the paper already tries to constrain the output format during rule generation, but it still finds that “formatted” text can be noisy. The second prompt is their way of absorbing that noise without building a complicated manual parser. This is especially consistent with the paper’s overall goal of being practical under API-only access: they avoid training a custom parser or requiring access to the model internals.

In short, the first prompt is for better rule generation, and the second is for robust semantic parsing. They could have asked for JSON or DSL output from the start, but the paper’s argument is that in low-shot LLM prompting, stricter syntax often trades away some reasoning flexibility and still does not fully eliminate formatting errors. The two-stage setup is therefore a pragmatic choice to get both good rules and reliable execution.
