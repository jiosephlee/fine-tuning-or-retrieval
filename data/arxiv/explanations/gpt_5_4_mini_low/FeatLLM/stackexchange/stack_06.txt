\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Does using Python's \texttt{exec()} on LLM-generated code create a reliability problem for the method?
Question:
The paper says that the generated code is executed using Python's \texttt{exec()} function to perform data conversion.

From a systems and reproducibility perspective, this seems risky to me. Even ignoring security issues, what happens if the generated parser code is logically wrong, inconsistent across runs, or silently interprets a rule incorrectly?

For example, if the LLM misreads a categorical feature as numeric, or translates "greater than or equal to" incorrectly, the downstream binary features could be wrong without being obvious.

Did I miss any validation step that checks whether the parsed code matches the intended rule semantics? If not, how should I think about the trustworthiness of the feature engineering stage?
Answer:
Yes, that is a real reliability concern, and the paper does not describe a formal semantic validation step that would guarantee the parsed code exactly matches the intended rule.

What the paper actually does is use the LLM in two stages: first, it generates rules in natural language; then, to turn those rules into features, the authors ask the LLM to produce code and execute that code with Python’s `exec()`. The reason they give is that LLM outputs can be noisy syntactically, so instead of writing a brittle hand parser, they let the LLM itself translate the rule into executable code. In other words, `exec()` is just the mechanism for applying the generated program to the table; it is not, by itself, a validation step.

So your concern is well founded: if the LLM misreads a feature type, flips an inequality, or otherwise encodes the wrong condition, the downstream binary feature will be wrong and that error could be silent. The paper does not claim to eliminate that risk. What it claims instead is a more probabilistic kind of robustness. They try to reduce mistakes by including feature-type descriptions in the prompt, constraining the response format, and extracting a fixed number of rules. Then, crucially, they rely on repetition and ensembling with bagging: multiple independent rule-generation runs are performed, and the final prediction averages over those trials. The authors explicitly say that even if some trials generate incorrect rules, correct rules from other trials can compensate, and that rules repeatedly inferred across trials are more likely to be accurate.

There is also an empirical check, but it is not the same as semantic verification. In the analysis section, they measure whether the generated rules are informative by looking at the AUROC of the generated features against the labels, and they show that many rules are useful before tuning and that the linear model tends to downweight weak rules afterward. That is evidence that the pipeline can produce helpful features on average, not proof that each individual parsed rule is semantically correct.

So the right way to think about trustworthiness here is: FeatLLM is a heuristic, ensemble-based feature-engineering method that tolerates some imperfect rule translations, rather than a system that guarantees exact rule semantics. The downstream linear model and the ensemble provide some error absorption, but they do not make the feature engineering stage fully reliable or formally verified. If exact correctness of every rule matters, the method as described in the paper would indeed be too weakly validated for that use case.
