\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Instead of Making Predictions, This AI Learns the Rules First

Large language models are often used like black boxes: you give them a table, a prompt, and a question, and they return a prediction. That works, but it has real drawbacks for tabular learning. It can be expensive, slow at inference time, and awkward when the table has many columns or when you only have API access to the model.

The paper on **FeatLLM** takes a different approach. Instead of asking the LLM to directly predict the label for every new row, it asks the model to do something more like feature engineering: **learn the decision rules first**. Those rules are then converted into new binary features, and a simple classifier makes the final prediction.

## The core shift: from predictor to rule maker

The key idea is to treat the LLM as an expert assistant that can infer useful patterns from a few labeled examples. For a task like predicting whether a patient has a disease, the model is prompted to reason about which conditions tend to indicate the positive class and which conditions point to the negative class.

So rather than outputting “yes” or “no” directly for each test sample, the LLM produces rules such as:

- if a certain feature is above a threshold,
- if a categorical value matches a specific condition,
- or if a combination of values suggests one class over another.

These rules are meant to capture the criteria behind the prediction.

That is the conceptual change FeatLLM makes: **the LLM is no longer the final predictor. It becomes the rule generator.**

## How FeatLLM works

FeatLLM has three main stages.

First, it prompts the LLM with basic information about the task. This includes the task description, feature names, feature definitions, and a few labeled examples. The prompt is designed to encourage the model to think like a human expert solving the problem.

Second, the LLM generates class-specific rules. The paper describes a two-step reasoning setup. In the first step, the model infers the relationship between features and the target using general knowledge. In the second step, it uses the few examples to refine those ideas into concrete rules for each class. The authors also constrain the output format so the rules are easier to parse.

Third, those rules are converted into binary features. For each rule, a sample gets a value of 1 if it satisfies the rule and 0 otherwise. These binary rule features are then passed to a lightweight downstream model, such as a linear classifier, which learns how important each rule is.

In equation form, the model computes class logits from the rule features and then applies a softmax to obtain class probabilities. The important part is that the classifier is simple: once the rules are generated, inference no longer requires querying the LLM.

## Why this is useful

This setup addresses several practical problems with LLM-based tabular prediction.

The biggest one is inference cost. In many LLM tabular systems, every test sample must be sent through the LLM. FeatLLM avoids that by doing the expensive reasoning only during the rule-generation stage. After that, prediction is handled by a small model.

It also helps with prompt length limits. Tabular datasets can have many columns, and serializing all of them into a prompt can become unwieldy. FeatLLM reduces that burden by using the LLM to extract only the most relevant rules. The paper also uses bagging to select subsets of features or samples during different runs, which helps manage prompt size.

Another advantage is that FeatLLM only needs **API-level access** to the LLM. It does not require fine-tuning the model, which matters when you are using a closed model that does not expose training code or parameter updates.

## Why rules can work well in few-shot tabular learning

Few-shot tabular learning is hard because with only a handful of labeled rows, standard models can easily latch onto noise. The LLM helps here because it brings in prior knowledge from pretraining. In medical datasets, for example, it may already know that age, certain lab values, or risk factors tend to matter.

FeatLLM uses that prior knowledge to propose candidate rules, then lets the small labeled dataset determine which rules are actually useful. This is an important balance: the LLM provides broad reasoning, and the downstream classifier filters and weights the results based on the data.

The paper also reports that the generated rules are often informative even before tuning, and that weight learning further removes weak or irrelevant rules.

## Ensemble and bagging make it more robust

The authors do not rely on just one set of rules. Instead, they repeat the process multiple times with different random seeds, different demonstration orders, and different subsets of data or features. This creates an ensemble of rule-based models.

That matters because LLM outputs can vary. Some generated rules may be good, others may be noisy. By aggregating multiple trials, FeatLLM benefits from the rules that recur consistently, while reducing the impact of bad ones. The paper links this to the idea of self-consistency: rules that keep appearing across runs are more likely to be correct.

Bagging also helps when prompts would otherwise become too long. If a dataset has many columns, sampling subsets keeps each prompt manageable.

## What the experiments show

The paper evaluates FeatLLM on 13 tabular datasets across binary and multi-class tasks, including standard benchmarks like Adult, Bank, Heart, and Diabetes, as well as newer and synthetic datasets.

Across these datasets, FeatLLM performs strongly in low-shot settings. According to the paper, it often ranks first or second among the compared methods and improves by about 10% on average over alternatives such as TabLLM and STUNT.

It is also notable that FeatLLM remains usable on datasets with many columns, where direct prompt-based LLM methods can struggle.

An ablation study in the paper shows that several pieces matter:

- tuning the linear weights matters,
- the ensemble helps consistently,
- feature descriptions improve performance,
- and the step-by-step reasoning prompt is important, especially in very small-shot regimes.

## The bigger idea

FeatLLM is not just a new model; it is a different way to think about using LLMs on structured data.

The usual approach is: “Let the LLM predict the answer.”

FeatLLM’s approach is: “Let the LLM discover the rules, then let a simple model do the prediction.”

That shift has a few nice properties. It lowers inference cost, reduces dependence on full model access, handles large tables better, and makes the LLM’s contribution more explicit. Instead of hiding everything inside a prompt-to-answer pipeline, the model’s knowledge is turned into something more concrete: rules that can be inspected, parsed, and reused.

## A practical takeaway

If you are working with tabular data and only have a few labeled examples, FeatLLM suggests a useful pattern: do not necessarily ask the LLM to solve the task end-to-end. Ask it to help you **engineer better features**.

That is a smaller job, but in this paper it turns out to be a very effective one.



# Why LLMs Struggle With Tables—and How FeatLLM Gets Around It

Large language models have become surprisingly good at many tasks that were never part of their original design. They can answer questions, write code, summarize text, and even help with prediction problems. But tabular data is a different beast.

Tables are common in real applications: healthcare records, financial profiles, customer logs, and many other structured datasets. Yet most LLM-based tabular methods run into practical issues fast. The paper *Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning* introduces a different approach called **FeatLLM** that tries to keep the strengths of LLMs while avoiding the expensive parts.

## Why tabular learning is hard for LLMs

The standard way to use an LLM on tabular data is to serialize the table into text, put feature names and a few labeled examples into the prompt, and ask the model to predict the label. This can work in few-shot settings, especially when the LLM’s pretrained knowledge is relevant to the domain.

But there are three major bottlenecks.

First, **inference is expensive**. If the model must make one prediction per sample by calling the LLM each time, deployment gets costly and slow. That is a serious problem if you need to score many rows.

Second, **fine-tuning is often required for best performance**. Some methods rely on parameter-efficient tuning or training access that is not always available. This limits usefulness when you only have API access to a model.

Third, **prompts get too long**. Tabular data can have many columns, and serialized text grows quickly. Once the prompt becomes too large, the method either becomes infeasible or loses performance.

These issues matter less in toy experiments and much more in real systems.

## The key idea behind FeatLLM

FeatLLM changes the role of the LLM. Instead of asking it to directly predict each sample, the method uses the LLM as a **feature engineer**.

The LLM is asked to generate rules that capture the conditions associated with each class. Those rules are then converted into binary features, such as whether a sample satisfies a certain condition or not. After that, a simple downstream model learns how to combine those features into class probabilities.

In other words, the LLM is used once to discover useful structure in the data. Prediction itself is then handled by a lightweight model, not by the LLM.

That design has an important deployment advantage: **the LLM is not needed at inference time**. Once the rules are extracted and turned into features, the final predictor is just a small machine learning model.

## How the pipeline works

FeatLLM breaks the process into a few stages.

The first stage is **rule extraction**. The prompt contains task information, feature descriptions, and a few labeled examples. The model is also guided with a two-step reasoning instruction. In the first step, it is asked to infer the relationship between features and the target using general knowledge. In the second step, it uses the examples to derive rules for each class.

This structure is meant to help the model focus on meaningful features rather than noisy ones. The paper also fixes the number of rules extracted per class to keep the prompt manageable.

The second stage is **parsing the rules into executable code**. Since the LLM produces natural language, the system needs a way to convert those rules into binary indicators automatically. Rather than writing a brittle parser, the paper uses the LLM itself to generate simple code from the inferred rules. That code is then executed with Python to transform the data.

The third stage is **learning class likelihoods from the generated features**. The paper uses a linear model without bias. For each class, it computes a logit from the binary rule features and then applies a softmax across classes. The trainable weights tell the model which rules matter most.

The final stage is **ensembling with bagging**. The entire rule-generation-and-training process is repeated multiple times with randomness introduced through the prompt order, temperature, and feature or instance bagging. The predictions are then averaged.

## Why this is better for deployment

The biggest benefit of FeatLLM is that it moves the expensive LLM step out of the prediction path.

That matters because many LLM-based tabular methods require a fresh LLM call for every sample at inference time. FeatLLM does not. Once the rule-based features are created, the downstream model can score new samples directly.

This makes the method much more practical for real use cases where latency and cost matter. It also means FeatLLM can work with API-only access to LLMs, which is important because many top-performing models do not expose training code or fine-tuning interfaces.

Another advantage is that FeatLLM is more robust to long tables. Because it uses feature bagging and ensembles, it can work around prompt size limitations by splitting the problem into smaller pieces across multiple trials.

## What the experiments show

The paper evaluates FeatLLM on 13 tabular datasets from a wide range of domains, including adult income prediction, credit risk, diabetes, heart disease, and several more recent or synthetic datasets.

The baselines include:

- standard models like logistic regression, XGBoost, and RandomForest,
- tabular methods that rely on unlabeled data or pretraining,
- and LLM-based methods such as in-context learning, TABLET, and TabLLM.

Across these experiments, FeatLLM is consistently one of the best-performing methods. The paper reports that it outperforms alternatives like TabLLM and STUNT by about 10% on average.

One notable result is that FeatLLM with only 4-shot training can reach performance comparable to conventional tabular methods that use 32 shots. That is exactly the kind of efficiency gain that matters in low-label settings.

The method also remains usable on datasets with many features, where other LLM-based approaches often struggle because the prompt becomes too long.

## Why the rules matter

A natural question is whether the LLM is really generating useful structure, or just producing noise.

The paper directly checks this by measuring how informative the generated rule features are. Many of the created features have meaningful association with the target labels before tuning. After the linear model is trained, low-value rules are effectively filtered out by their weights.

This is a good sign: the LLM is not just spitting out arbitrary conditions. It is often extracting rules that are relevant to the task, and the downstream model learns which ones are actually useful.

The authors also test robustness to spurious correlations by attaching irrelevant columns from another dataset. FeatLLM shows less performance degradation than the baselines, suggesting that its rule-generation process helps avoid some noisy features. That said, the paper also notes that if the added columns are closely related, the model can still learn misleading correlations.

## The trade-off: LLM intelligence, but only where it helps

FeatLLM is not trying to replace machine learning with an LLM. It is trying to use the LLM where it is strongest: connecting domain knowledge to structured features and generating candidate rules from very limited data.

Then it hands off the actual prediction task to a simple and efficient model.

That trade-off is what makes the approach interesting. It keeps the benefits of LLM prior knowledge while avoiding the most expensive deployment pattern, which is end-to-end LLM inference for every prediction.

## Takeaway

If you want to use LLMs on tabular data, the obvious approach is not always the best one. Direct prediction with prompts can be slow, costly, hard to scale, and sensitive to prompt length. Fine-tuning can help, but it adds another layer of complexity and may not even be possible with API-only models.

FeatLLM offers a cleaner alternative: use the LLM once to engineer rules, turn those rules into features, and let a lightweight model handle inference.

For low-shot tabular learning, that design is both practical and effective. It shows that sometimes the best way to use an LLM is not to ask it to make every prediction, but to ask it to build a better input representation first.



# Few Examples, Strong Results: How FeatLLM Boosts Low-Data Machine Learning

Tabular machine learning is everywhere: credit scoring, disease prediction, customer modeling, scientific classification, and more. But these settings often share one painful constraint: labeled data is scarce. In many real-world workflows, getting just a few trusted examples can be much easier than labeling hundreds or thousands.

That is exactly the setting targeted by the paper on **FeatLLM**, a framework that uses a large language model not to make end-to-end predictions for each row, but to **engineer features** from a tiny labeled set. The result is a surprisingly practical idea: let the LLM discover rules, convert those rules into binary features, and then train a simple downstream model on top.

The key question is whether this actually works when data is limited. The paper’s experiments suggest that it does.

## Why few-shot tabular learning is hard

In low-shot tabular learning, standard models are often forced to learn from too few examples to reliably separate signal from noise. That makes them vulnerable to spurious patterns, especially when the feature space is wide and heterogeneous.

LLM-based approaches promise to help by injecting prior knowledge. But most of those methods still have drawbacks. They often require an LLM inference step for every test example, which is expensive. Some require fine-tuning. Others struggle when the tabular input has many features and the prompt becomes too long.

FeatLLM takes a different route. Instead of asking the LLM to directly predict the label, it asks the model to extract **rules** like “if feature A is high and feature B is low, then class 1 is likely.” Those rules become features that a small linear model can use efficiently.

## What FeatLLM actually does

The pipeline is simple in concept:

1. Provide the LLM with the task description, feature definitions, and a few labeled examples.
2. Ask it to infer class-specific rules.
3. Parse those rules into executable code.
4. Turn each rule into a binary feature indicating whether a sample satisfies it.
5. Train a lightweight linear model to estimate class probabilities.
6. Repeat this process multiple times with bagging and ensemble the results.

This matters because it moves the heavy reasoning into an offline feature discovery stage. At inference time, FeatLLM does **not** need to query the LLM for each sample. That makes it much cheaper than many other LLM-based methods.

## The benchmark story: few examples, strong performance

The paper evaluates FeatLLM on **13 tabular datasets** spanning binary and multiclass classification. These include familiar benchmark tasks like Adult, Bank, Blood, Credit-g, Diabetes, Heart, and Myocardial, as well as newer and synthetic datasets designed to test whether the model is really learning or just memorizing common patterns.

Across these tasks, FeatLLM is reported to be consistently competitive, often ranking at the top or near the top compared with a range of baselines. The comparison includes:

- conventional tabular methods such as logistic regression, XGBoost, and RandomForest,
- low-shot methods that use unlabeled data like SCARF and STUNT,
- a pretrained tabular model, TabPFN,
- and several LLM-based approaches, including in-context learning, TABLET, and TabLLM.

The headline result is that FeatLLM **outperforms alternatives by about 10% on average** over the evaluated settings, and it does so in the low-shot regime that the paper targets.

## Why the results matter in practical terms

The real significance of these results is not just that FeatLLM wins benchmarks. It is that it does so in the exact kind of environment where machine learning often struggles most.

In healthcare, for example, labeled outcomes may be expensive to obtain or require expert review. A model that can learn useful rules from only a handful of patient records could help bootstrap decision support systems faster.

In finance, teams often need to build models from sparse, high-stakes historical data. A method that can extract meaningful patterns from limited examples while keeping inference cheap is attractive for fraud detection, credit risk, and customer analytics.

In scientific applications, labeled datasets are frequently small by nature. If an LLM can help synthesize domain knowledge into features, researchers may be able to get useful models sooner, even before large curated datasets exist.

In all of these cases, the appeal is the same: FeatLLM tries to turn the LLM’s knowledge into something that is **reusable**, **efficient**, and **less dependent on large training sets**.

## Performance with very few shots

One of the most interesting findings in the paper is that FeatLLM can match conventional tabular baselines with far fewer labeled examples. The authors report that with only **4 shots**, FeatLLM achieves performance comparable to standard methods that need **32 shots** in some settings.

That is a strong signal that the framework is extracting genuinely useful structure from the limited data, rather than merely fitting the few examples directly.

The paper also shows that the method remains effective on datasets with many attributes, where prompt length becomes a real challenge for direct LLM-based approaches. This is where the feature-engineering framing helps: once rules are extracted, the downstream model can work with compact binary features instead of long serialized tables.

## Why the ensemble step helps

Few-shot settings are noisy by nature, and a single set of generated rules can miss important details. FeatLLM addresses this by repeatedly generating rules with different prompt orderings, randomized subsets of features or samples, and a higher sampling temperature.

This creates diverse rule sets, which are then combined through ensembling. The paper reports that this consistently improves performance. In other words, even if some trials produce imperfect rules, the better ones can compensate.

This is a practical design choice. It also helps with prompt size limitations, since bagging can reduce how much of the table needs to be included in any single LLM call.

## The model is also less brittle to noisy columns

The authors include an analysis where irrelevant columns from another dataset are added to a task. In that experiment, FeatLLM shows the smallest performance drop among the compared methods.

That suggests the two-step prompting design is doing something useful: first infer the broad relationship between task and features, then extract class-specific rules. This helps the system focus on relevant columns and avoid being distracted by noise.

The paper also notes an important caveat: if the added columns are closely related to the target task, FeatLLM can still learn spurious correlations. So this is not a magic bullet. But it does appear more robust than many alternatives in the low-shot regime.

## What FeatLLM changes about LLM use in tabular learning

The most important conceptual shift is that FeatLLM does not treat the LLM as the final predictor. It treats the LLM as a **feature engineer**.

That matters because it makes the overall system easier to deploy. The LLM is used to discover rules once, not to process every sample forever. After that, a simple model handles inference. The paper reports that this gives FeatLLM relatively low inference time compared with other LLM-based methods, while keeping training manageable through API-only access.

This is especially relevant in practical environments where:
- access to model training code may be limited,
- prompt length is constrained,
- latency matters,
- and repeated per-sample LLM calls are too expensive.

## Takeaway

FeatLLM shows that large language models can be useful in tabular learning without being used as end-to-end classifiers. By converting a few labeled examples into interpretable rules and then into binary features, it finds a middle ground between raw LLM prompting and conventional machine learning.

The result is a method that works well in the exact setting where many organizations struggle: **small labeled datasets, high stakes, and limited room for expensive model tuning**.

For healthcare, finance, and scientific applications, that is a meaningful direction. If labeling is costly, the ability to get strong results from just a few examples can change what is feasible. FeatLLM is not the final answer to low-data machine learning, but it is a compelling demonstration that LLMs may be most valuable not only as predictors, but as automated feature engineers.



# From Natural Language Rules to Machine Learning Features

Large language models are often used as end-to-end predictors: you serialize a table into text, send it to the model, and ask for a label. The FeatLLM paper takes a different path. Instead of asking the LLM to make the final prediction for every sample, it uses the LLM as a feature engineer.

That shift matters. Once the model has extracted useful rules from a few examples, those rules can be turned into binary features and handed off to a simple classifier. The result is a pipeline that is cheaper at inference time, easier to deploy with API-only access, and better suited to tabular datasets with many columns.

## The Core Idea

FeatLLM treats tabular prediction as a two-stage process.

First, the LLM reads a small set of labeled examples, feature descriptions, and a task description, then generates rules that separate the classes. These rules are written in natural language, but they are meant to capture structured conditions such as “if age is above a threshold and another condition holds, then the positive class is likely.”

Second, those rules are converted into executable code that can check whether each sample satisfies them. Each rule becomes a binary feature: $1$ if the sample matches the rule, $0$ otherwise.

A lightweight downstream model, such as a linear model, then learns how to combine those binary features into class probabilities.

This means the LLM is used where it is strongest: reasoning from a few examples and bringing in prior knowledge. The actual prediction step is pushed into a simple model that is fast and cheap to run.

## Why Not Just Predict Directly with the LLM?

The paper points out several limitations of existing LLM-based tabular methods.

If the LLM has to make a prediction for every test sample, inference becomes expensive. If the method relies on fine-tuning, then it also depends on having training access, which is not always available with modern API-only models. And when tables have many columns, the serialized prompt can become too large.

FeatLLM avoids these issues by using the LLM only during feature discovery. After that, inference no longer requires the LLM. The discovered rules are reused by a standard classifier.

## Prompt Design: Getting the LLM to Think Like a Feature Engineer

The paper’s prompt design is carefully structured. It has three parts: basic information, reasoning instruction, and response instruction.

The basic information section gives the model the task description, feature names and definitions, and a few labeled examples. The examples are serialized in a tabular-to-text format like:

$$
\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = `` f_1\ \text{is}\ \mathbf{x}^i_1.\ ...\ f_d\ \text{is}\ \mathbf{x}^i_d.\ \ \text{Answer:}\ \mathbf{y}^i "
$$

This gives the LLM enough context to connect raw columns to the target label.

The reasoning instruction is where the method becomes more interesting. FeatLLM breaks inference into two steps. In the first step, the model is asked to infer the general relationship between the features and the task, using prior knowledge and common sense. In the second step, it uses that understanding plus the few-shot examples to derive rules for each class.

This two-step setup is important because it pushes the LLM to separate general causal or semantic reasoning from example-specific pattern matching. The paper argues that this helps the model ignore uninformative columns and focus on more meaningful features.

The response instruction then constrains the output format so the rules can be parsed more easily later. The paper also fixes the number of rules per class at 10 to avoid generating too few rules or inflating the prompt too much.

## From Rules to Binary Features

Once the LLM outputs rules, FeatLLM turns them into code.

This step is necessary because the rules are written in natural language, and natural language is messy. The model may output variants like “greater than” instead of $>$, or make small syntactic changes that break naive parsing.

Rather than building a brittle parser, FeatLLM uses the LLM again to generate a small piece of code from the inferred rules. The prompt includes the function name, input/output descriptions, and the rule text. The generated code is then executed with Python’s `exec()` function.

The output is a set of binary features. For each class, each rule becomes a flag indicating whether a sample satisfies that rule. If there are $R$ rules per class, then each sample gets a binary vector $\mathbf{z}_k^i \in \{0,1\}^R$ for class $k$.

This is the key transformation: the LLM’s textual reasoning is converted into machine-readable signals.

## A Simple Model Does the Final Prediction

After feature generation, FeatLLM does not need a deep model. It uses a low-complexity predictor, such as a linear model without bias, to estimate class likelihoods.

For class $k$, the model computes:

$$
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i
$$

and then applies a softmax over all class logits:

$$
\mathbf{p}^i = \text{Softmax}([\text{logit}_1^i, ..., \text{logit}_c^i])
$$

The weights $\mathbf{w}_k$ represent the importance of each rule. The positive constraint, $\max(\mathbf{w}_k, 0)$, ensures that a rule cannot reduce the likelihood of its class during learning.

The model is trained with cross-entropy loss on the few labeled examples. In other words, the LLM creates the features, and the small downstream model learns how much to trust each one.

## Why This Works Better Than Just Counting Rules

A simple alternative would be to count how many rules each sample satisfies. FeatLLM does something slightly more flexible: it learns which rules matter more.

That matters because not all extracted rules are equally useful. Some may be strong indicators, while others may be noisy or weakly related to the label. The linear model learns to weight them accordingly.

The paper also shows that low-quality rules can be downweighted automatically during training. This gives the system a built-in filtering mechanism without needing a separate feature-selection stage.

## Bagging and Ensembling for Robustness

Because LLM outputs can vary across prompts, FeatLLM repeats the whole rule-generation-and-training process multiple times and averages the results.

This ensemble setup serves two purposes.

First, it improves robustness. If one trial produces a bad rule, other trials may produce better ones, and averaging helps smooth out the errors.

Second, it helps with prompt length limits. For large tables, not all features can fit comfortably into one prompt. FeatLLM uses feature bagging or instance bagging to reduce the amount of information passed in each trial, making the method more scalable to wider tables.

The paper also randomizes the order of the few-shot demonstrations and uses a nonzero temperature during LLM inference to encourage diversity across trials.

## What Happens in Practice?

On the benchmark datasets studied in the paper, this pipeline produces useful rules that often outperform or match existing baselines in low-shot settings. The authors also test whether the generated rules are actually informative by measuring how well they align with the target labels. Most of the generated features are relevant before tuning, and the linear model can further suppress weak ones during training.

An interesting result is that FeatLLM is relatively resilient to spurious columns. When unrelated features are attached to a dataset, performance degrades less than with several baselines. The reason seems to be that the prompt design pushes the LLM to reason about the task-feature relationship before generating rules, which reduces the chance that irrelevant columns dominate the output.

## The Takeaway

FeatLLM is a good example of rethinking where an LLM should sit in a machine learning pipeline.

Instead of treating the model as the predictor, the paper uses it as a rule generator and feature engineer. Those rules are then converted into binary features and passed to a simple classifier. This makes inference cheaper, avoids per-sample LLM calls, and works with API-only access.

For technical readers, the main lesson is straightforward: sometimes the best use of an LLM is not to replace the downstream model, but to create better inputs for it. In tabular learning, that can mean turning a phrase like “older age increases risk” into an explicit feature the model can actually learn from.



# Can AI Be a Better Feature Engineer Than Humans?

Large language models are usually discussed as prediction engines: give them a table, ask for an answer, and let them infer the label directly. The FeatLLM paper takes a different view. Instead of asking an LLM to make every prediction itself, it asks the model to do something more familiar to data scientists: engineer features.

That shift matters. In low-shot tabular learning, where only a handful of labeled examples are available, the main challenge is not just fitting a classifier. It is finding useful structure in messy, heterogeneous columns. FeatLLM treats the LLM as a knowledge-driven assistant that can propose decision rules from a small set of examples and feature descriptions. Those rules are then turned into binary features, and a simple downstream model handles the actual prediction.

## From end-to-end prediction to feature engineering

Most prior LLM-based tabular methods serialize a row into text and send it through the model at inference time. That works, but it has two practical costs. First, you need an LLM call for every sample you want to predict. Second, the prompt can become unwieldy as the number of features grows.

FeatLLM avoids both issues by moving the LLM to the feature construction stage. The model is prompted to extract rules such as conditions that indicate one class versus another. Those rules are then applied to each row to produce binary indicators: does this sample satisfy the rule or not?

Once those indicators exist, prediction becomes a standard machine learning problem. In the paper, the authors use a linear model with non-negative weights and softmax to estimate class probabilities. The LLM is no longer in the loop during inference, which keeps latency low and makes the approach more practical when API-only access is available.

## Why the rules are more than just text

A natural concern is whether the LLM is just generating plausible-sounding rules that do not actually help. The experiments suggest that this is not the case. The paper evaluates FeatLLM on 13 tabular datasets across domains such as healthcare, finance, and synthetic classification tasks. Across these datasets, the generated rules are often genuinely informative: the authors measure the average AUROC of the rule-based features and find that many exceed random usefulness, with a substantial fraction remaining useful even before weight tuning.

This is important because it supports the paper’s core claim: an LLM can act as a feature engineer, not just a classifier. In other words, the model is not merely memorizing labels from the prompt. It is extracting patterns that translate into features with predictive value.

## Why a simple model can work so well

Once the rules are turned into features, FeatLLM uses a low-complexity classifier instead of a heavy LLM. That may sound like a downgrade, but it is actually one of the method’s strengths.

The downstream model learns which rules matter most. In the paper’s linear setup, each rule gets a learned weight, and those weights are constrained to be non-negative. This design prevents the model from learning that a rule should actively reduce the likelihood of a class, which fits the intended interpretation of the rules as supporting evidence.

This also adds a layer of interpretability. Instead of a black-box score from an LLM, you get explicit rules and learned weights that tell you which conditions the model found useful. For many tabular tasks, that is a much more actionable output.

## Ensembling helps separate signal from bad rules

No LLM will generate perfect rules every time. FeatLLM addresses this with bagging and ensembling. The idea is to run the rule-generation process multiple times, using randomness in prompt order and sampling subsets of features or examples. Each run produces a slightly different set of rules, and the final prediction averages across the resulting models.

This does two things at once. It improves robustness, and it helps with prompt-length limits. If a table has many columns, not all of them can fit comfortably into one prompt. Bagging lets the method work on subsets, so the LLM sees only part of the problem at a time.

The paper’s ablation study shows that ensembling matters consistently. Removing it hurts performance across settings, which suggests that diversity across rule sets is useful rather than just noise. Bad rules from one trial can be offset by better rules from another, and repeated extraction helps the method converge toward more stable signals.

## Where the method is most convincing

One of the stronger pieces of evidence in the paper is the experiment with spurious correlations. The authors take the Heart dataset and attach unrelated columns from the Adult dataset, then gradually increase the amount of irrelevant information. Many methods degrade as the noise grows. FeatLLM is comparatively more stable.

Why? Because the prompt structure explicitly encourages the LLM to think about the relationship between the task and the features before it extracts rules. That makes it less likely to latch onto random columns. In the experiment, rules based on noisy columns account for only a small fraction of the total.

This is encouraging, but it is not a guarantee. The paper also notes that FeatLLM can still learn spurious correlations if the added columns are closely related to the target task. So the method is more robust than naive prompting, but it is not immune to misleading context.

## The limits of LLM-driven feature engineering

FeatLLM is promising, but its limitations are worth taking seriously.

First, it still inherits the biases and prior assumptions of the LLM. If the model’s prior knowledge is wrong or skewed, those mistakes can shape the rules it generates. In a sensitive domain such as healthcare or finance, that is not a minor issue.

Second, the method is designed for low-shot learning. The paper does not claim it is the best choice for large, richly labeled datasets. Its value comes from situations where labels are scarce and expert-derived feature engineering would otherwise be expensive.

Third, while the rules are interpretable, they are not necessarily causal. A rule can be predictive without being a true explanation. That distinction matters when the output will influence downstream decisions.

Finally, the approach depends on the quality of the prompt construction and the feature descriptions. If the dataset metadata are poor, incomplete, or ambiguous, the LLM has less to work with.

## What this means for data science workflows

FeatLLM points toward a broader shift in how we might use LLMs for structured data. Instead of thinking of them as end-to-end predictors that replace traditional models, we can think of them as knowledge tools that support the parts of the workflow where humans usually spend the most effort: feature design, rule discovery, and hypothesis generation.

That is a more realistic and, arguably, more useful role.

For practitioners, the appeal is clear. You get:

- no need to fine-tune the LLM,
- no per-sample LLM inference at test time,
- a simpler and faster downstream model,
- and a more interpretable set of rule-based features.

For researchers, the deeper implication is that LLMs may be better at providing structured priors than final answers. They can inject domain knowledge into low-data problems, then let a lightweight model do the rest.

## The bottom line

Can AI be a better feature engineer than humans? FeatLLM suggests that, in some low-shot tabular settings, the answer may be yes or at least “sometimes, and in a useful way.”

The paper shows that LLMs can generate rules that are often informative, that ensembling can filter out bad ones, and that a simple model on top of these features can outperform several strong baselines. At the same time, it also shows why we should be cautious: the method can still absorb bias, learn spurious patterns, and depend heavily on prompt quality.

So the most compelling takeaway is not that LLMs should replace human feature engineering entirely. It is that they can become powerful collaborators in the workflow, especially when labels are scarce and domain knowledge matters. In that sense, FeatLLM is less about replacing data science and more about expanding what data science tools can do.
