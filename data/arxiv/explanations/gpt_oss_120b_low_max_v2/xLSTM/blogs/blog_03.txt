# Parallel vs. Sequential: Understanding sLSTM’s Memory Mixing and Its Trade‑offs  

## Introduction  

Long Short‑Term Memory (LSTM) networks have been the backbone of many sequence‑modeling breakthroughs for three decades. Their success stems from two simple ingredients introduced in the original paper: a constant‑error carousel that preserves gradients over long time spans, and a set of sigmoid gates that control how information is written to and read from a scalar cell state.  

The new **xLSTM** family pushes these ideas further. It adds **exponential gating** and, most importantly for this post, a **memory‑mixing mechanism** in the scalar variant called **sLSTM**. Memory mixing gives sLSTM the ability to *track state* across a sequence—a property that traditional Transformers and many State‑Space Models (SSMs) lack. The flip side is that mixing introduces *sequential dependencies* that dramatically limit parallel execution. In this article we unpack what memory mixing does, why it forces a sequential workflow, and what this means for speed, hardware, and real‑world use cases.

## What is memory mixing in sLSTM?  

In a vanilla LSTM each time step updates a single scalar cell $c_t$ according to  

\[
c_t = f_t \, c_{t-1} + i_t \, z_t,
\]

where $f_t$ (forget) and $i_t$ (input) are sigmoid gates. The hidden state $h_t$ is then emitted via an output gate $o_t$.  

sLSTM keeps the same basic recurrence but introduces two crucial changes:

1. **Exponential gates** – the input gate $i_t$ (and optionally the forget gate $f_t$) are exponentiated instead of passed through a sigmoid:
   \[
   i_t = \exp(\tilde{i}_t), \qquad
   f_t = \sigma(\tilde{f}_t)\ \text{or}\  \exp(\tilde{f}_t).
   \]
   This allows the network to *revise* earlier storage decisions more aggressively.

2. **Normaliser state $n_t$** – alongside $c_t$, a second running sum tracks how much “mass’’ the gates have contributed:
   \[
   n_t = f_t n_{t-1} + i_t.
   \]
   The hidden output uses the ratio $\tilde{h}_t = c_t / n_t$, which normalises the cell by the accumulated gate strength.

When we extend sLSTM to **multiple cells**, we obtain a vector of states $\mathbf{c}_t \in \mathbb{R}^{d}$. Here *memory mixing* enters: each hidden vector $\mathbf{h}_{t-1}$ can be linearly transformed and fed back into **all** gates and the cell input through recurrent weight matrices
\[
\mathbf{R}_z,\;\mathbf{R}_i,\;\mathbf{R}_f,\;\mathbf{R}_o,
\]
exactly as in the original LSTM vector‑cell formulation. The key difference is that exponential gating now amplifies or attenuates these recurrent contributions, enabling the network to *override* or *reinforce* earlier stored values as new evidence arrives.

### Why does this help with state tracking?  

State tracking problems—think of keeping count of nested parentheses or updating a “nearest neighbor’’ record when a better match appears later—require the model to **revise** a previously stored piece of information. Traditional LSTMs with sigmoid gates tend to be conservative: once a value is written with a large forget gate close to 1, decreasing it later is costly because $f_t$ can only slowly decay information.

Exponential gating removes this bottleneck. Since $i_t$ can grow arbitrarily large (and we stabilise it with the log–max trick), the network can *overwrite* an earlier entry in one step. Coupled with memory mixing—where each hidden step can influence every gate—sLSTM can propagate an updated decision through all cells instantly, achieving perfect state tracking on synthetic formal‑language benchmarks (parity, copy‑with‑delay, etc.). This capability is absent in pure attention models or SSMs that lack recurrent hidden‑to‑hidden pathways.

## The cost: loss of parallelism  

The recurrent connections that enable memory mixing also create a **temporal dependency chain**: computing $\mathbf{h}_t$ requires $\mathbf{h}_{t-1}$, which itself needs $\mathbf{h}_{t-2}$, and so on. In contrast, modern Transformers compute attention scores for all positions simultaneously because each token’s representation depends only on *static* key/value projections of other tokens.

Because of this chain:

- **GPU kernels cannot be vectorised across time steps**; they must perform a scan operation (prefix sum) where each iteration waits for the previous one.
- The computational complexity remains *linear* in sequence length (good for memory), but the wall‑clock time grows *linearly* as well, without any of the constant‑time tricks employed by FlashAttention or other fast attention kernels.
- Parallel hardware such as Tensor Processing Units (TPUs) or GPUs benefit less from their massive matrix‑multiply throughput because at any given moment only one time step’s matrix multiplies are active.

The authors mitigated this slowdown with a custom CUDA kernel that stores intermediate states in registers and streams data efficiently; even then sLSTM runs roughly **1–2× slower** than its parallel cousin mLSTM (which eliminates hidden‑to‑hidden connections).

## Practical implications  

### Speed vs. expressivity  

| Property | sLSTM (memory mixing) | mLSTM (no mixing) |
|----------|----------------------|-------------------|
| State tracking (ability to revise past decisions) | ✅ Strong – proven on formal languages | ❌ Weak – relies on additive updates only |
| Parallel execution across timesteps | ❌ Sequential scan required | ✅ Fully parallelisable |
| Compute per token | ~1.5× LSTM baseline (due to extra normaliser) | ~2× LSTM baseline (matrix ops) |
| Memory footprint | O(1) per token (scalar cells) | O($d^2$) per token for matrix $\mathbf{C}$ |
| Ideal hardware | GPU with fast per‑step kernels; low latency inference | GPU/TPU with large matrix multiply pipelines |

If your application demands **precise state tracking**—e.g., code execution verification, long‑range entity resolution, or online reinforcement learning where decisions must be corrected on the fly—sLSTM’s sequential nature may be worthwhile despite slower throughput.

Conversely, for tasks where raw throughput matters more than exact revision abilities—large‐scale language modeling with billions of tokens—**mLSTM** (or other linear transformers) typically wins because they can exploit parallel hardware and achieve higher FLOPs per second.

### Hardware considerations  

- **GPU memory:** sLSTM’s scalar cells keep memory usage modest; you can run very deep stacks without blowing memory even on modest GPUs.
- **Cache locality:** The custom CUDA kernel keeps recurrent states in registers, reducing global memory traffic—a design choice critical for maintaining acceptable latency.
- **Batch size:** Since each sequence step must be processed sequentially, increasing batch size does not hide latency as effectively as in Transformers; you’ll see diminishing returns after modest batch sizes (~8–16).
- **Edge devices:** The low per‑token parameter count makes sLSTM attractive for edge inference where static RAM is limited, provided real‑time latency requirements are relaxed.

### Real‑world scenarios  

1. **Reinforcement learning agents:** Agents like AlphaStar rely on precise temporal credit assignment; revisiting past decisions quickly is valuable. A sequential model like sLSTM can directly encode “last good move” logic without auxiliary replay buffers.
2. **Time series anomaly detection:** When an anomalous event appears later in a stream and should overwrite earlier tentative predictions, exponential gating ensures rapid correction.
3. **Interactive language assistants:** For dialogues longer than 4–8 k tokens where context needs constant updating (e.g., correcting user-provided facts), sLSTM can maintain an up‑to‑date internal knowledge base without re‑encoding the entire conversation.

In contrast, for production text generation services that serve millions of requests per second, sLSTM’s slower per‑token speed may be prohibitive; developers would likely opt for mLSTM or optimized Transformers instead.

## Takeaways  

- **Memory mixing** in sLSTM equips recurrent models with genuine *state tracking*: they can revise earlier stored values instantly via exponential gating.
- This power comes at the cost of **sequential execution**, preventing the massive parallelism that modern attention mechanisms exploit.
- Whether you choose sLSTM or its parallel sibling mLSTM depends on your priority: *expressivity & exact revision* vs. *speed & hardware efficiency*.
- For niche domains requiring reliable online updates—reinforcement learning, real‑time monitoring, long dialogue management—sLSTM offers a compelling trade‑off despite slower wall‑clock times.

As research continues to optimise CUDA kernels and explore hybrid architectures that blend parallel matrix memories with selective sequential mixing, we may soon see models that enjoy both worlds: fast inference *and* robust state tracking. Until then, understanding the fundamental trade‑offs outlined above helps practitioners pick the right tool for their specific sequential modelling challenge.
