\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### What is the role of the n‑gram hash embeddings and how are they combined with byte embeddings?
Question:
Section 4.1.1 introduces hash‑based embeddings for byte n‑grams (n=3…8) which are added to the byte embedding and then normalized. I am confused about several points: (1) why use a hash function rather than a learned lookup table for each n‑gram? (2) How is the normalization performed – is it simply dividing by the number of n‑gram contributions plus one? (3) Do these hash embeddings get updated during training like regular parameters, and how large are the hash tables in practice?
Answer:
The encoder of BLT has to turn a raw byte $b_i$ into a vector that already contains some notion of the surrounding context, because the local transformer only sees a relatively short window of bytes (the “local block‑causal” window).  
The authors therefore augment every byte‑embedding $x_i$ with a set of **hash‑based n‑gram embeddings** that represent the 3‑ to 8‑byte sequences ending at position $i$.

### 1. Why a hash function instead of a learned table for each n‑gram?

A literal lookup table for all possible n‑grams would quickly become infeasible.  
For an alphabet of 256 possible byte values, the number of distinct 8‑grams is  

$$
256^{8}\approx 2^{64}\;,
$$

far larger than any memory budget.  By applying a **deterministic rolling polynomial hash** (RollPolyHash) and then taking the result modulo the size of a *fixed* embedding matrix $E^{\text{hash}}_{n}$, every n‑gram is mapped to one of a modest number of slots (the paper uses 500 k slots per n‑gram size).  

The hash therefore provides two crucial properties:

* **Compactness** – the embedding tables stay at a constant, manageable size (hundreds of thousands of vectors rather than billions).
* **Speed** – computing the hash is an O(1) operation that can be performed on‑the‑fly while loading data, avoiding the need for a separate preprocessing pass that would be required for a learned vocabulary.

Because the hash function is deterministic, identical n‑grams always hit the same slot, and collisions are tolerated: they simply share the same embedding vector. Empirically the authors find that this limited amount of collision does not harm performance; on the contrary, it acts as a form of regularisation and keeps the parameter count low.

### 2. How is the normalization carried out?

For each byte position $i$ the augmented embedding is

$$
e_i \;=\; x_i \;+\;\sum_{n=3}^{8} E^{\text{hash}}_{n}\!\bigl(\text{Hash}(g_{i,n})\bigr),
$$

where $g_{i,n}$ denotes the $n$-gram ending at $i$.  
After summation the paper says “we normalize by the number of n‑gram sizes plus one”.  
In practice this means dividing by $1+N$ where $N=6$ (the six n‑gram lengths). Thus

$$
\tilde e_i = \frac{e_i}{7}.
$$

This simple averaging prevents the magnitude of $\tilde e_i$ from growing with the number of added terms and keeps it comparable to the raw byte embedding scale, which is important for stable training of the downstream transformer layers.

### 3. Are these hash embeddings learned and how large are they?

Yes. Each table $E^{\text{hash}}_{n}\in \mathbb{R}^{|E^{\text{hash}}_{n}|\times h_{\mathcal{E}}}$ contains trainable parameters (the paper uses $h_{\mathcal{E}}$ equal to the hidden dimension of the local encoder). During back‑propagation gradients flow through the selected rows exactly as they would for an ordinary embedding lookup, so the vectors are updated just like any other model parameter.

The concrete sizes used in all experiments are:

* **Number of slots per n‑gram size:** 500 000 (≈ 0.5 M).  
* **Embedding dimension:** equal to the local encoder hidden size (e.g., 768 for a 1 B model, 1024 for larger models).

Thus each hash‑embedding table holds roughly $5\times10^{5}\times h_{\mathcal{E}}$ parameters; across six n‑gram lengths this amounts to about $3\,\text{M–5\,M}$ additional weights, which is negligible compared with billions of parameters in the global transformer.

---

**In summary**, hash‑based n‑gram embeddings let BLT inject cheap, contextual information into each byte without exploding memory, are averaged with the raw byte embedding to keep feature scales stable, and are fully learnable parameters updated during training. This design contributes noticeably to BLT’s ability to match token‐based LLMs while operating directly on bytes.
