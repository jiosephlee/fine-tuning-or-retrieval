\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### Why does the cross‑attention module in the encoder pool only over bytes belonging to a single patch?
Question:
The encoder cross‑attention (Section 4.1) uses queries for each patch that attend only to keys/values from bytes inside that patch. Intuitively, one might think allowing a query to attend to a larger window of surrounding bytes could give richer context before forming the latent representation. What is the justification for this strict per‑patch attention mask? Does it limit the ability of the latent transformer to capture dependencies that span across patch boundaries, or are those handled solely by the global transformer’s block‑causal attention?
Answer:
In the encoder a *patch* is meant to be a compact latent summary of **exactly the bytes that belong to that patch**.  
The cross‑attention layer is therefore built as a “pooling” operation: each query $Q_{j}$ is created for patch $p_{j}$ and is allowed to attend only to the keys and values that come from the byte embeddings $\{h_{l,i}\}$ that lie inside the same patch.  

There are three intertwined reasons for this design choice, all of which are mentioned in the paper:

1. **Preserve the semantics of a patch**  
   A patch is defined by the dynamic segmentation function $f_{p}$. Its boundaries are chosen precisely because the bytes inside have roughly homogeneous information density (low‑entropy continuation after a high‑entropy boundary). If a query were allowed to look at bytes outside its own patch, the resulting representation would no longer be an *intrinsic* description of that segment; it would already contain context that belongs to a different segment. This would blur the meaning of “patch = local context” and would make it harder for the downstream latent transformer to know where one logical unit ends and another begins.

2. **Separate concerns between local ↔ global processing**  
   The architecture contains two distinct stages:

   * **Local encoder (and its cross‑attention)** – cheap, shallow layers that turn raw bytes into a *per‑patch* latent vector. Its job is to extract enough information from the bytes so that the following stage can treat each patch as an atomic token.
   * **Global latent transformer** – a deep autoregressive model that operates on the sequence of patch embeddings $\{p_{j}\}$. It uses **block‑causal attention**, which already lets each patch attend to all *earlier* patches while staying causal with respect to the document.

   Because the global model can already see any earlier patch, giving each encoder query access to bytes from neighbouring patches would be redundant. All dependencies that cross a patch boundary are deliberately handled by the global block‑causal attention, which is far more expressive (it can attend across arbitrarily many patches) and much cheaper than letting every encoder layer repeatedly scan overlapping windows.

3. **Efficiency and memory constraints**  
   The cross‑attention in the encoder is executed on every transformer layer of $\mathcal{E}$. By restricting the attention mask to “bytes‑in‑the‑same‑patch”, the attention matrix for each layer is block‑diagonal with blocks of size equal to the current patch length. Consequently its computational cost is linear in the number of bytes rather than quadratic in the full sequence length. If queries were allowed to attend beyond their own patch, we would have to compute dense or large sliding‑window attention, dramatically increasing FLOPs without a corresponding gain in modelling power—because those longer‑range interactions are already captured later by $\mathcal{G}$.

Putting these points together, the per‑patch mask is not an arbitrary limitation; it is a deliberate architectural decision that enforces a clean hierarchy: **local encoder = intra‑patch summarisation**, **global transformer = inter‑patch reasoning**. The global block‑causal attention fully handles dependencies that span across patch boundaries, while the encoder cross‑attention stays tightly focused on its own bytes, keeping both computation and representation semantics efficient. This design mirrors classic hierarchical models (e.g., hierarchical RNNs, Perceiver) where a cheap bottom‑up stage builds local latents and an expensive top‑down stage reasons over them. The paper’s experiments confirm that this separation does not hurt performance—in fact, it enables the model to scale to 8 B parameters with byte‑level inputs while matching tokeniser‑based baselines.
