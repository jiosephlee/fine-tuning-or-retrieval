# Deploying FeatLLM with API‑Only Access – A Practical Guide  

*How to turn a single LLM inference pass into a full‑featured few‑shot tabular learner.*

---

## Introduction  

Large language models (LLMs) are great at reasoning over text, yet calling them for every row of a table quickly becomes prohibitively expensive. **FeatLLM** sidesteps this bottleneck by using the LLM **once** (or a few dozen times) to *engineer* a set of binary features—human‑readable “rules” that capture the relationship between columns and the target label. After the rules are extracted, prediction is performed by a tiny linear model that runs locally on your machine, requiring **no further API calls**.

In this tutorial we walk through a complete deployment pipeline that works **with API‑only access** (e.g., OpenAI’s `gpt‑3.5‑turbo`). You’ll learn how to:

1️⃣ Craft a single batch of rule‑generation prompts for an entire dataset  
2️⃣ Persist the generated Python code locally  
3️⃣ Train the lightweight linear weight model on the binary rule features  
4️⃣ Tune temperature and ensemble size for robustness  
5️⃣ Roughly estimate API costs per run  
6️⃣ Scale the approach to high‑dimensional tables  

All steps are grounded in the **FeatLLM** methodology described in the paper *Large Language Models Can Automatically Engineer Features for Few‑Shot Tabular Learning*.

---

## Overview of FeatLLM’s Workflow  

| Stage | What Happens | Why It Matters |
|-------|--------------|----------------|
| **Rule extraction** | A prompt containing task description, feature definitions, and a few labeled examples is sent to an LLM → The model returns *R* logical rules per class (e.g., “age > 60 && cholesterol ≤ 200”). | Captures prior knowledge and causal intuition without any training of the LLM itself. |
| **Feature generation** | Each rule is parsed into executable Python code that evaluates whether a row satisfies it → Binary feature vector $\mathbf{z}_k^i \in \{0,1\}^{R}$ for class $k$ is produced for every sample $i$. | Turns natural‐language reasoning into mathematically tractable inputs for downstream learning. |
| **Lightweight training** | Train a non‑negative linear model $\mathbf{w}_k \ge 0$ on the binary vectors using standard cross‑entropy loss (Eq. 2 in the paper). | Only a few gradient steps are needed; training is negligible compared with any fine‑tuning of an LLM. |
| **Ensembling & bagging** | Repeat rule extraction $T$ times with different random seeds/feature subsets → obtain $T$ independent weight vectors $\{\mathbf{w}[t]\}_{t=1}^{T}$. Final prediction = average softmax scores across ensembles. | Improves robustness against occasional noisy rules and mitigates context‑window limits on large tables.|

After step 1 you never talk to the LLM again—every subsequent operation runs locally.

## Step‑by‑Step Implementation  

Below is a concrete recipe you can copy–paste into a notebook or script.

### 1️⃣ Prepare Your Tabular Data  

You need three pieces:

| Item | Required format |
|------|----------------|
| Feature names | List `F = ["age", "cholesterol", …]` |
| Feature definitions *(optional but highly recommended)* | Dictionary `def_f = {"age": "numeric age in years", "cholesterol": "serum cholesterol in mg/dL", …}` |
| Few‑shot examples | `k` labeled rows (`k` as low as 4 works well). Serialize each row as:

```
age is 55.
cholesterol is 210.
...
Answer: Positive
```

The column descriptions help the LLM focus on the right variables during rule extraction (see Sec 3 of the paper).

### 2️⃣ Build the Prompt  

The prompt follows three logical blocks:

```text
[Basic Information]
Task: Does this patient have chronic heart failure? Yes/No.
Feature Descriptions:
- age: numeric age in years.
- cholesterol: serum cholesterol level.
...
Few-shot demonstrations:
<serialize k examples>

[Reasoning Instruction]
Step 1: Based solely on general medical knowledge infer which features are likely related to heart failure.
Step 2: Using both Step 1 insight and the few-shot examples derive exactly R (=10) decision rules for each class ("Yes" and "No").

[Response Instruction]
Please return your rules in JSON format:
{
  "Yes": ["age > 60 && cholesterol <= 200", ...],
  "No": ["age <= 60 && cholesterol > 200", ...]
}
```

Key points:

* **Two‑step reasoning** forces the model first to exploit its prior knowledge before looking at noisy few‑shot data—this reduces spurious rule generation.
* **Fixed number of rules** (`R = 10`) keeps prompts short enough for most APIs while still giving expressive power.
* **JSON response format** simplifies downstream parsing dramatically.

### 3️⃣ Issue Rule‑Generation Queries  

For most datasets you’ll run **\(T\)** independent queries (default \(T = 20\)). Each query returns a set of rules for all classes in one call—so you need only \(T\) API requests total.

```python
import openai, json, tqdm

def get_rules(prompt):
    resp = openai.ChatCompletion.create(
        model="gpt-3.5-turbo",
        messages=[{"role":"user","content":prompt}],
        temperature=0.5,
        max_tokens=800   # enough space for JSON output
    )
    return json.loads(resp["choices"][0]["message"]["content"])
```

If your table has hundreds of columns (>~150), you may exceed the model’s context window (~4 k tokens). In that case **feature bagging** solves it:

* Randomly sample a subset `F_subset ⊂ F` (e.g., √|F| columns) for each trial.
* Include only those columns in “Basic Information.”
* Across \(T\) trials most columns will appear at least once, giving you a comprehensive rule set after ensembling.

#### Cost estimate  

A typical prompt + answer pair uses roughly **2 500 tokens** (≈ 1 000 tokens for feature descriptions + few‐shot rows + instructions). At OpenAI’s public rate (\$0.002 / 1k tokens), one call costs ≈ \$0.005​\. With \(T = 20\), total expense ≈ **\$0.<sup>10</sup>–\$0.<sup>15</sup>**, well under a dollar even for large tables—far cheaper than repeatedly invoking an LLM during inference.

### 4️⃣ Parse Rules into Executable Code  

Even though you asked for JSON strings, natural language variations (“greater than”, “>”, “is above”) still appear inside each rule expression. The simplest way is to ask **the same LLM** once more to translate each textual condition into valid Python code:

```python
def translate_rule(rule_text):
    prompt = f"Convert this human readable condition into valid Python boolean expression:\n{rule_text}"
    # reuse same model parameters; low temperature encourages consistency.
    resp = openai.ChatCompletion.create(
        model="gpt-3.5-turbo",
        messages=[{"role":"user","content":prompt}],
        temperature=0,
        max_tokens=64,
    )
    return resp["choices"][0]["message"]["content"].strip()
```

Run this over all rules once and store the resulting functions locally (`rules_{trial_id}.py`). Because translation happens only **once**, it adds negligible extra cost (< \$0.01).

Alternatively you can implement simple string replacements (`">"` ↔ `" > "` etc.) if you prefer pure Python parsing—but delegating it to an LLM preserves robustness across diverse phrasing patterns reported in Section 4 of the paper.

### 5️⃣ Compute Binary Rule Features  

Load all generated functions and apply them vectorially:

```python
import pandas as pd
import numpy as np
import importlib.util

def load_rules(file_path):
    spec = importlib.util.spec_from_file_location("rules", file_path)
    mod = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(mod)
    return mod.RULES   # assume RULES is a dict {class_label: [func1,...]}

def evaluate_rules(df, rules):
    # output shape : N x C x R   where C = #classes , R = #rules/class
    N = len(df)
    C = len(rules)
    R = len(next(iter(rules.values())))
    Z = np.zeros((N,C,R), dtype=int)
    
    for c_idx,(cls,rlist) in enumerate(rules.items()):
        for r_idx,f in enumerate(rlist):
            Z[:,c_idx,r_idx] = df.apply(f, axis=1).astype(int)
    return Z.reshape(N,C,R)
```

The resulting tensor `Z[i,k,:] = \mathbf{z}_k^i` feeds directly into our linear predictor.

### 6️⃣ Train the Lightweight Linear Model  

Only **\(R \times C\)** trainable scalars are needed—a truly tiny model even when \(R=10\) and \(C=5\):

```python
import torch, torch.nn.functional as F

class RuleLinear(torch.nn.Module):
    def __init__(self, C,R):
        super().__init__()
        self.w = torch.nn.Parameter(torch.randn(C,R))   # unconstrained
    
    def forward(self, Z):   # Z shape: batch x C x R
        w_pos = torch.relu(self.w)                     # enforce w >= 0
        logits = torch.sum(w_pos * Z, dim=2)           # dot product per class
        probs = F.softmax(logits, dim=1)
        return probs

```

A small validation split or early stopping decided via `k`‑fold CV prevents overfitting—a technique employed by FeatLLM’s authors (see Sec 4).

#### Positive weight projection  

The ReLU (`torch.relu`) implements Eq.(2)’s `max(\mathbf{w},0)` constraint without extra bookkeeping and guarantees that every selected rule can only increase its class probability rather than suppress it—a design choice highlighted in Fig 2 of the paper.

### 7️⃣ Ensemble Predictions  

Repeat steps 2–6 across all \(T\) trials producing weight matrices `{w[t]}` and their corresponding binary tensors `{Z[t]}`:

```python
probs_ensemble = sum(model_t(Z_test_t) for model_t,Z_test_t in zip(models,Z_tests)) / T
preds = probs_ensemble.argmax(dim=1)
```

Averaging softmax scores implements exactly what FeatLLM describes in Eq.(3). Empirically this reduces variance substantially; performance plateaued around \(T=20\) according to Figure 7 in Appendix A of the paper.

## Hyperparameter Cheat Sheet  

| Hyperparameter | Recommended default | Effect |
|----------------|---------------------|--------|
| `temperature` (LLM) | **0.5** | Balances diversity vs deterministic output; higher values give more varied rules → better ensembles but larger variance across trials |
| `T` (ensemble size) | **20** | Improves AUC up to ≈ +2% beyond \(T=10\); diminishing returns after ≈ 20 |
| `R` (rules per class) | **10** | Sufficient expressive power while keeping prompt length modest |
| `feature_bag_size` | `min(√d , max_features_allowed_by_context)` | Controls prompt overflow when d ≫ 100; larger bags give richer individual rule sets but increase token budget |

When working under strict latency constraints you can cut `T` down to 10 or even 5 at modest accuracy loss—feel free to experiment based on your budget sheet!

## Scaling Guidance  

### Parallelizing API Calls  
OpenAI permits concurrent requests up to several hundred per minute depending on your plan. Dispatch all \(T\) prompts asynchronously (`asyncio`, `concurrent.futures`) and wait for completion—overall wall‐clock time drops from minutes to seconds even when \(T=20\).
