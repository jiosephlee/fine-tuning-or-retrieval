# Why Simpler Models Win: How **FeatLLM** Slashes Inference Costs Without Losing Accuracy

## The Problem with “LLM‑as‑Predictor” for Tables  

Large language models (LLMs) have become the go‑to tool for *few‑shot* learning because a short prompt can turn them into a generic reasoner.  
When researchers apply this ability to tabular data they usually do one of two things:

1. **Serialize the whole table** (feature names + values) into a prompt and let the LLM output a label for each row.  
2. **Fine‑tune or LoRA‑adapt** the LLM on a handful of rows and then run it repeatedly at inference time.

Both strategies share a hidden cost: **every test sample triggers an LLM call**.  
Even with a modest API latency of ≈ 0.5 s per request, a production pipeline that needs thousands of predictions per minute quickly becomes impractical—and incurs a non‑trivial monetary bill.

## What FeatLLM Does Differently

Instead of asking the LLM to *predict* directly, FeatLLM asks it to **engineer features** once, offline. The resulting features are binary “rule satisfaction” flags that can be consumed by an ultra‑lightweight model such as linear regression or logistic regression.

### Step‑by‑Step Overview

| Stage | What Happens? | Why It Matters |
|------|----------------|----------------|
| **1️⃣ Prompt Design** | A carefully crafted prompt supplies (a) a natural‑language task description, (b) concise feature definitions, and (c) a few labeled examples.<br>Two reasoning steps are enforced:<br>• **Step 1:** Infer causal tendencies between features and the target using general knowledge.<br>• **Step 2:** Derive concrete decision rules for each class from the examples.<br>Exactly 10 rules per class are requested to keep the prompt manageable. | The two‑step chain-of‑thought separates *domain knowledge* from *sample‐specific evidence*, reducing spurious correlations that often appear in low‑shot settings. |
| **2️⃣ Rule Extraction** | The LLM outputs rules in a fixed textual format (e.g., “`age > 55 AND cholesterol > 200`”). A second lightweight prompting step asks the same model to translate each rule into executable Python code that returns `1` if the rule holds and `0` otherwise. | Using the LLM itself as a parser sidesteps brittle hand‑crafted regexes—any phrasing variation (“greater than”, “>”) is correctly interpreted. |
| **3️⃣ Feature Generation** | For every row we evaluate all extracted rules, yielding a binary vector \(\mathbf{z}_k \in \{0,1\}^{R}\) for class \(k\) (with \(R=10\)). | These high‑level predicates already encode complex interactions among raw columns, so the downstream model does not need to discover them again. |
| **4️⃣ Light Model Training** | A simple linear model without bias is fitted on the few labeled rows:<br>\[\text{logit}_k = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k,\qquad \mathbf{p}= \text{Softmax}([\text{logit}_1,\dots,\text{logit}_c])\] <br>The weights \(\mathbf{w}_k\) are learned by minimizing cross‑entropy loss. The non‑negative projection guarantees that any rule can only increase its class’s score. | Training involves just tens of parameters; even with 4–8 shots it converges quickly while still allowing each rule’s importance to be tuned. |
| **5️⃣ Bagging + Ensembling** | The whole pipeline is repeated \(T\) times with random subsets of features/rows and a higher temperature sampling from the LLM.<br>The final prediction is the average of all softmax outputs. | Diversity mitigates both prompt length limits (large tables are split across bags) and occasional erroneous rules—correct rules dominate across trials (self‑consistency). |

## Accuracy That Matches or Beats Heavyweight Baselines  

FeatLLM was evaluated on **13 diverse tabular datasets** ranging from classic UCI benchmarks (Adult, Credit‐g) to very recent releases (Cultivars, NHANES) and synthetic tasks where memorization is impossible. All experiments used only *k* shots with \(k\in\{2,4,8\}\).

* **Performance:** Across all datasets FeatLLM either topped the leaderboard or placed second behind conventional tree ensembles trained on many more examples. On average it improves AUC by roughly **10 %** over recent LLM baselines such as TabLLM and STUNT.
* **Data efficiency:** With just **4 shots**, FeatLLM reaches performance comparable to XGBoost or Random Forest trained on **32 shots**, highlighting how much prior knowledge is harvested from the LLM during feature creation.

These results show that once high‑quality rules are obtained, a linear combiner can capture most of the predictive signal—no deep networks needed.

## Latency & Cost Where Simpler Wins

Below is a qualitative summary of inference timings reported on the Adult dataset (16 shots):

| Method | Typical per‑sample latency* | Approximate API calls needed |
|--------|----------------------------|------------------------------|
| In‑context learning (full table each query) | ~0.6 s | 1 call per test sample |
| TABLET | ~0.8 s | ≥1 call per test sample |
| TabLLM (parameter efficient fine‑tuning) | ~0.7 s + GPU warmup overhead | Continuous GPU inference |
| **FeatLLM** (linear model) | **≈ 0.02 s** (CPU) | ~30 API calls total (offline feature generation) |

\*Numbers reflect wall‐clock time on an Nvidia A100 server; CPU inference times are similar on modest hardware because only matrix–vector products over binary vectors are required.

The contrast is stark:

* **No per‐sample LLM call** → latency drops by two orders of magnitude.
* **Only dozens of cheap API queries** → negligible cloud cost compared with thousands of calls needed by end‑to‑end approaches.
* The linear model’s memory footprint is < 1 KB per class—ideal for edge deployment or batch scoring pipelines.

## Why Rule‑Based Binary Features Work So Well

1. **Compression of Knowledge** – An LLM can embed decades of domain facts in one rule (“`age > 60` ⇒ high risk”). The binary flag instantly conveys that insight without requiring any learned representation.
2. **Interpretability** – Each feature corresponds to an understandable predicate that domain experts can validate or edit.
3. **Monotonic Contribution** – By constraining weights to be non‑negative we guarantee that satisfying an additional rule never hurts class likelihood—a property natural in many risk scoring systems.
4. **Robustness Through Ensembling** – Even if some generated rules are noisy, averaging over many bagged models dilutes their effect while reinforcing consistently useful rules—a practical form of “self consistency”.

Ablation studies in the paper confirm these intuitions:

* Removing weight tuning drops performance noticeably once more than a handful of shots become available—highlighting that learning rule importance matters when data increase.
* Omitting feature descriptions or the first reasoning step hurts low‑shot performance substantially because without prior knowledge the LLM falls back on spurious correlations.
* Turning off ensembling uniformly degrades results across all shot regimes.

## Real‑World Implications

For industries where labeling is expensive—healthcare risk stratification, credit underwriting, or fraud detection—FeatLLM offers:

* **Data efficiency:** Leverage existing domain literature encoded in an LLM instead of collecting thousands of labeled rows.
* **Operational simplicity:** Deploy a tiny linear scorer behind existing data pipelines; no GPU required at inference time.
* **Predictable costs:** Fixed upfront expense for API calls versus unpredictable per‐prediction billing.

The approach also eases compliance concerns: because final decisions rest on explicit logical rules rather than opaque neural activations, audits become feasible without sacrificing accuracy.

## TL;DR

* Traditional few‑shot tabular methods that treat an LLM as an end‑to‑end predictor pay huge latency and cost penalties because they query the model for every new row.
* FeatLLM flips this paradigm—use the LLM once to synthesize high‑quality logical rules from a handful of examples and domain descriptions.
* Those rules become binary features that feed a cheap linear model; thanks to bagging + ensembling they stay robust even when prompts must be trimmed.
* Empirically FeatLLM matches or surpasses state‐of‐the‐art few‐shot tabular learners while cutting inference time by two orders of magnitude and reducing API usage dramatically.

In short, *simplicity wins*: by letting powerful language models do what they excel at—reasoning about concepts—and then handing off prediction to lean models, we get both accuracy and efficiency in one package.

### Quick Takeaways

- **Feature engineering via LLMs = high‐level knowledge extraction once**, not per prediction.
- **Binary rule features + linear classifier = near SOTA AUC** on dozens of heterogeneous datasets.
- **Inference latency ≈ linear regression**, dramatically lower than any full‐LLM pipeline.
- **Cost = ~30 API calls**, independent of test set size—ideal for production environments.

If you’re building low‑shot tabular solutions today, give FeatLLM a try—it may just let you retire heavyweight inference servers while keeping your predictions razor sharp.
