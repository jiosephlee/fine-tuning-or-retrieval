# FeatLLM Unlocked: How Large Language Models Are Becoming Expert Feature Engineers  

## Introduction  

Large language models (LLMs) have dazzled us by solving new‑task prompts without any retraining—think “write code,” “answer math,” or “summarize a story.”  
But when it comes to **tabular data** (the spreadsheets behind credit scoring, medical diagnosis, churn prediction, …) most existing LLM‑based approaches still treat the model as a black‑box predictor: every test row is encoded as text and sent through the LLM, often after an expensive fine‑tuning step. This design has three major drawbacks:

1. **Inference cost skyrockets** – each new sample incurs a full LLM query.  
2. **Fine‑tuning is often impossible** because many top‑performing LLMs (GPT‑4, PaLM) are only accessible via inference APIs.  
3. **Prompt size limits** choke performance when tables have dozens or hundreds of columns; the serialized text simply does not fit into the model’s context window.

**FeatLLM** turns this paradigm upside down. Instead of asking an LLM to make a prediction for every row, we ask it once (or a few times) to **engineer features**—in practice, human‑readable rules that capture what “causes” each class label. Those rules are turned into binary columns that feed a tiny downstream model (a linear classifier). The result?  

* **Near‑zero inference latency** – only the simple downstream model runs at test time.  
* **No fine‑tuning required** – we just need API access to an LLM for a handful of prompt calls.  
* **Scalable to high‑dimensional tables** – rule generation uses feature bagging and ensembling so we never overflow the context window.

Below we walk through how FeatLLM works, why its design choices matter, and what empirical results tell us about its promise.

---

## From End‑to‑End Predictions to Feature Generation  

### The bottleneck of prior LLM tabular methods  

Methods such as **TabLLM**, **STUNT**, or plain in‑context learning embed a few labeled rows into a prompt like:

```
age = 35, job = admin, ... Answer: >50K
...
Predict for new row:
```

Every prediction triggers an LLM forward pass. When datasets contain ~100 features or more—which is common for health or crime statistics—this approach either truncates important columns or suffers severe performance loss due to context‑window overflow. Moreover, many works resort to parameter‑efficient fine‑tuning (e.g., LoRA/IA3) which presumes you can download and train the underlying model—a luxury not granted by commercial APIs.

### The FeatLLM insight  

Instead of asking “*what is the label?*” for each row, FeatLLM asks “*what conditions imply each label?*”. In other words:

1. **Step 1 – Understanding** – The LLM reads a task description (e.g., “Predict chronic heart failure”) together with feature definitions and a handful of labeled examples.
2. **Step 2 – Rule extraction** – Using its world knowledge plus the few examples, it spits out *explicit logical rules* that characterize each class (e.g., “age > 60 AND cholesterol > 200”).  

These rules become **binary features** (`rule_i = 1` if a row satisfies rule i). A lightweight linear model then learns how much weight each rule deserves—nothing more complex than a dot product and softmax.

Consequences:

* The heavy LLM inference happens *once per ensemble member*, not per test row.
* The downstream model can be trained on any hardware (even CPU) because it’s just linear regression.
* No gradients need to flow back into the LLM—only a few API calls are required during training.

---

## Building Rules: Prompt Design that Mimics an Expert Analyst  

FeatLLM’s success hinges on coaxing the LLM into reliable reasoning. The authors crafted a three‑part prompt:

1. **Basic information** – task statement + natural language descriptions for every column + several serialized few‑shot examples:
   \[
   \text{Serialize}(\mathbf{x}^i,\mathbf{y}^i,F)=
   \text{``} f_1\text{ is }\!x^i_1.\dots f_d\text{ is }\!x^i_d.\ \text{Answer:}\ y^i\text{''}
   \]
2. **Reasoning instruction** – a chain‑of‑thought scaffold that forces two steps:
   * *Step 1*: Infer causal tendencies between features and the target *without* looking at examples (pure prior knowledge).
   * *Step 2*: Combine those tendencies with the few examples to derive **10 rules per class**.
   This separation discourages spurious correlations that could arise from tiny datasets.
3. **Response instruction** – explicit formatting guidelines so that each rule follows a consistent syntax (“if `age > 60` AND `blood_pressure > 140` then class = Yes”).  
   The fixed rule count (10 per class) keeps prompts manageable while still giving enough expressive power.

By keeping these pieces clear—and by feeding feature type hints (“numeric”, “categorical”)—the LLM reliably outputs structured rules ready for parsing.

---

## From Natural Language Rules to Binary Features  

Even with strict formatting some variability leaks in (e.g., “greater than” vs “>”). Rather than hand‑crafting fragile regex parsers, FeatLLM leverages the same LLM as a *code generator*. It sends:

```
def apply_rules(row):
    # generated conditions from rules
    return [int(condition_1), int(condition_2), ...]
```

The LLM returns Python code that evaluates every rule on a pandas row using `exec()`. Executing this code transforms every original record into a vector \(\mathbf{z}_k \in \{0,1\}^{R}\) where \(R=10\) is the rule count for class \(k\).

---

## Learning Rule Importance  

A naive approach would simply count satisfied rules per class. FeatLLM instead learns **non‑negative weights** for each binary rule via a linear model:

\[
\text{logit}_k = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k,\qquad
\mathbf{p}= \operatorname{softmax}([\text{logit}_1,\dots,\text{logit}_c]).
\]

The positivity constraint ensures that any rule never hurts its own class probability—a natural safeguard when our binary features are derived from expert‐style criteria.

Training uses standard cross‑entropy loss on the few shot samples (typically \(k=2\), \(4\), or \(8\)). With such tiny data there is no overfitting risk because we are only fitting a handful of weights (\(cR\) parameters).

---

## Ensembling & Feature Bagging  

One query yields one set of rules → one linear classifier. To boost robustness:

* **Temperature** is raised (≈ 0.5) so repeated queries produce diverse rule sets.
* **Demo order randomization** further diversifies generation (order matters for many LLMs).
* **Bagging** selects random subsets of columns or training rows before each query—this shrinks prompts for very wide tables and forces different perspectives on the data.
* An ensemble of \(T=20\) members averages their softmax outputs:
  \[
  \hat{\mathbf{p}} = \frac{1}{T}\sum_{t=1}^{T}\mathbf{p}^{(t)} .
  \]

The authors report diminishing returns after about 20 members—performance plateaus while computational cost rises slowly.

Across 13 diverse benchmarks—including recent UCI releases after September 2023 (Cultivars, NHANES) and synthetic tasks—the framework either topped or held second place consistently. On average FeatLLM beats strong baselines like TabLLM and STUNT by roughly **10 % absolute AUC**, while matching traditional models run with four times more labeled data (e.g., logistic regression with 32 shots).

### Ablations confirm design importance  

| Variant | ΔAUC (avg.) |
|---------|-------------|
| ‑Tuning (no weight learning) | −0.03 |

Weight tuning becomes more valuable as shots increase; reasoning instructions are crucial when data are scarce; feature descriptions help disambiguate numeric vs categorical thresholds—all aligning with intuition about leveraging prior knowledge.

### Robustness against spurious columns  

Adding unrelated columns from Adult to Heart degrades most models sharply—as they mistakenly latch onto random correlations in low‐shot regimes—but FeatLLM’s AUC drops only marginally (< 2 %). The reason: its rule generation leans heavily on step 1 prior knowledge, essentially ignoring noisy features unless they appear in useful causal statements.

### Runtime & cost  

On an A100 GPU:

| Method | Training time (seconds) | Inference time per sample |
|--------|------------------------|---------------------------|
| FeatLLM (20 ensembles) | ≈ 45 s + ~30 API calls | ≈ 0.001 s |

FeatLLM’s inference cost rivals that of logistic regression while still pulling ahead on predictive performance—a practically attractive tradeoff for production systems where latency matters.

## Why It Matters  

1. **Cost efficiency** – Companies can tap into powerful proprietary LLMs without paying per‑sample inference fees or buying GPU clusters for fine‐tuning.
2️⃣ **Scalability across domains** – Even when faced with thousand‐column health records or financial ledgers exceeding context windows, bagged prompting keeps prompts short enough for any API.
3️⃣ **Interpretability by default** – The extracted rules are human readable (“if `age > 60` AND `smoking = yes` then `heart_failure = yes`”), offering transparent decision logic absent from typical deep tabular models.
4️⃣ **Data efficiency** – High AUC with merely eight labeled rows means costly expert labeling can be dramatically reduced—crucial in medicine or finance where annotation is expensive.

---

## Limitations & Future Directions  

FeatLLM currently focuses on low‑shot regimes (< 32 labels). Scaling its rule generation to thousands of rows may require hybrid pipelines where learned rules seed additional automatic feature generators (e.g., decision trees). Moreover:

* The quality of generated rules inherits any biases present in the underlying LLM’s training corpus—a known risk for medical or demographic predictions.
* Rules are limited to simple logical expressions; richer feature transformations such as embeddings or interactions would broaden applicability.
* While ensembling mitigates variance, it still adds modest overhead proportional to ensemble size—future work could explore distilled single ensembles via knowledge distillation.

Nonetheless, the proof-of-concept convincingly shows that repurposing an LLM as an *expert feature engineer* yields tangible gains without sacrificing speed or accessibility.

---

## Takeaway  

FeatLLM demonstrates that large language models need not be black boxes churning out predictions per sample; they excel when asked *what matters*. By extracting concise logical criteria once, turning those into binary features, and feeding them into an ultra‑lightweight linear classifier—augmented by bagged ensembling—we obtain:

* State‑of‑the‑art few‑shot tabular performance,
* Orders of magnitude lower inference latency,
* No fine–tuning requirement,
* Compatibility with any API–only LLM,
* Built‑in interpretability through human–readable rules.

For practitioners wrestling with limited labels and budget constraints—think credit risk analysts, clinicians developing early warning scores, or marketers testing new campaigns—FeatLLM offers an immediately usable recipe: let an LLM think like an analyst once, then let cheap models do the heavy lifting forever.

# Inside the Prompt: Crafting Effective In‑Context Instructions for Rule Extraction  

*How FeatLLM’s three‑part prompt turns a language model into an expert feature engineer.*

---

## Why the Prompt Matters  

Few‑shot learning on tabular data is tricky: you often have dozens—or even hundreds—of columns but only a handful of labeled rows. Large language models (LLMs) bring a rich store of domain knowledge, yet they still need **clear guidance** to turn that knowledge into usable features instead of making a prediction for every individual sample.  

FeatLLM solves this by **asking the LLM to write decision rules** rather than to vote on each row. The secret sauce lives in the way the prompt is built. By structuring the request into three logical blocks—basic information description, reasoning instruction, and response instruction—we steer the model through a two‑step chain‑of‑thought that first discovers *causal* relationships and then turns them into concrete binary features. Below is a step‑by‑step walk‑through of each block and why it works.

---

## 1️⃣ Basic Information Description – Setting the Stage  

The opening part of the prompt answers two simple questions for the LLM:

1. **What is the task?**  
   We phrase it as a direct question (e.g., “Does this patient have chronic heart failure? Yes or No.”). Framing it as a query nudges the model toward classification logic instead of open‑ended generation.

2. **What are the inputs?**  
   Every column gets a short natural‑language description that includes:
   * The **feature name** (`f_j`),  
   * Its **type** (integer, categorical, boolean),  
   * An optional definition or list of allowed categories.  

3. **What are the exemplars?**  
   A few labeled rows (`k`‑shot) are serialized exactly as prior works do:

   ```
   f_1 is <value_1>. … f_d is <value_d>. Answer: <label>.
   ```

   By keeping the serialization uniform (`“f_3 is 45.”` etc.), the model can easily map values back to names during reasoning.

**Why this matters:**  
The model now knows both *semantic* information (what each column means) and *syntactic* patterns (how data are presented). No hidden assumptions are required—the LLM can rely on its world knowledge (“age > 65 → higher heart risk”) while also seeing concrete examples that tie specific value combinations to labels.

---

## 2️⃣ Reasoning Instruction – A Two‑Step Chain‑of‑Thought  

A plain “Give me rules” prompt often yields vague or overly generic statements. FeatLLM inserts an explicit **reasoning scaffold** inspired by chain‑of‑thought prompting:

### Step 1 – Infer Causal Tendencies Without Looking at Examples  
> “First think about which features are likely related to the task based purely on general knowledge.”

* The model draws on its pretraining—medical textbooks, financial reports, etc.—to hypothesize relationships such as “higher blood pressure usually indicates heart problems” or “older age raises credit default risk.”
* Crucially, **no example rows are consulted** here, so any spurious correlation present only in our tiny training set cannot influence this stage.

### Step 2 – Derive Class‐Specific Rules Using Both Prior Knowledge *and* Demonstrations  
> “Now use the few labeled examples along with your earlier hypotheses to write concise decision rules for each class.”

* The LLM marries its domain intuition from Step 1 with concrete patterns observed in the `k` shots.
* We fix a **rule budget** (`R = 10` per class) so that prompts stay within token limits while still giving enough expressive power.
* When referencing features, the model must respect their declared types (`>`, `<`, `=`, or categorical membership), which prevents nonsensical conditions like “age equals ‘high’”.

**Effect:** By separating these stages we force the model first to consider *global* causality before locking onto any *local* quirks of our limited sample set—a useful guard against spurious correlations.


---

## 3️⃣ Response Instruction – Making Output Machine‑Friendly  

After reasoning comes generation, and generation must be parsable automatically. FeatLLM adds a tight **response contract**:

* **Class headers:** The answer must start with a marker such as `Class A:` or `Class B:` so downstream code knows which rule set belongs where.
* **Rule formatting:** Each rule follows a strict template like  

  ```
  IF <feature> <operator> <value> [AND <feature> <operator> <value>] …
  ```

  where `<operator>` belongs to `{>, <, =}` for numeric columns or `IN {…}` for categoricals.
* **No free prose:** Anything outside the defined pattern will be ignored by the parser.
* **Logical operators:** If needed, multiple conditions can be combined with `AND`/`OR`, but they must stay inside one line so that they translate directly into binary feature checks later.

Because we explicitly tell the model how its answer should look—down to line breaks—the subsequent parsing step can rely on simple string matching or even ask *the same* LLM to generate executable Python code from those lines (as FeatLLM does). This eliminates brittle hand‑crafted regexes and makes the pipeline robust across domains.

---

## How This Design Keeps Spurious Correlations at Bay  

Spurious columns are those that happen to co‑occur with labels in our tiny training set but bear no real relationship to the target concept—think “zip code” accidentally aligning with income level in an eight‑sample slice. FeatLLM’s two‑step reasoning dramatically reduces their influence:

| Stage | What happens | Why spurious columns fade |
|------|--------------|---------------------------|
| Step 1 | Model ignores example rows entirely | It cannot learn any statistical freakishness from them |
| Step 2 | Rules are built only if they align with both Step 1 hypotheses *and* observed examples | A noisy column would need an existing causal hypothesis—which it lacks—so it rarely appears in final rule sets |
| Post‑processing | Only rules whose learned weight exceeds a tiny threshold survive | Any remaining stray rule gets down‑weighted during linear weight training |

Empirically, FeatLLM reports that **only ~1–2 %** of generated rules involve unrelated columns—a stark contrast to vanilla in‑context baselines where noisy features easily dominate predictions.

---

## Mini Walkthrough — What a Prompt Looks Like  

Below is a compact illustration whose skeleton mirrors exactly what FeatLLM sends to an LLM (the exact wording can vary).

```
Task: Does this patient have chronic heart failure? Answer Yes or No.

Features:
- Age: integer (years)
- BloodPressure: integer (mmHg)
- Cholesterol: integer (mg/dL)
- Diabetes: categorical {None, Type1, Type2}
...

Examples:
Age is 68. BloodPressure is 140. Cholesterol is 220. Diabetes is Type2. Answer: Yes.
Age is 45. BloodPressure is 120. Cholesterol is 180. Diabetes is None. Answer: No.
...

Reasoning:
Step 1 – Based purely on medical knowledge, list which features are likely related
to chronic heart failure.
Step 2 – Using those relationships together with the examples above,
write exactly ten decision rules for each class (Yes / No).

Response format:
Yes:
1) IF Age > 60 AND BloodPressure > 130
2) IF Diabetes = Type2 AND Cholesterol > 200
...
No:
1) IF Age < 50 AND Cholesterol < 190
...
```

When evaluated, an LLM typically returns ten neatly numbered conditional statements under each label—ready to be turned into binary vectors (`z_k^i ∈ {0,1}^R`) and fed into FeatLLM’s lightweight linear classifier (`logit_k^i = max(w_k,0)·z_k^i`).

---

## Practical Tips for Building Your Own Prompt  

| Tip | Reason |
|-----|--------|
| **Be explicit about types** (`integer`, `categorical`, …) | Guarantees syntactically correct operators (`>` vs `IN`). |
| **Keep serialization uniform** (`f_j is value.`) | Makes pattern recognition trivial for both LLM and parser. |
| **Set temperature ≈ 0.5** | Balances creativity (diverse rule sets across ensemble trials) with stability (avoids nonsense). |
| **Shuffle demo order between ensemble runs** | Different order nudges the model toward alternative rule subsets—useful for bagging/ensembling. |
| **Limit rule count (`R=10`)** | Prevents token overflow while preserving enough expressive power; empirically best trade–off across datasets.|

---

## Takeaway  

FeatLLM shows that *how you ask* matters more than *what you ask*. By splitting a single request into:

1️⃣ Clear problem framing + precise feature metadata + few shot examples  
2️⃣ A disciplined two-step chain-of-thought that first extracts domain causality then refines it with data  
3️⃣ A tight response contract that forces machine‑readable output,

the system transforms an off‑the‑shelf LLM into an autonomous feature engineer capable of producing high‑quality binary features without ever seeing every test row at inference time. The result? A remarkable average gain of ~10 % in AUC over competing few‑shot baselines while keeping inference latency comparable to classic linear models.

If you’re tackling low‑shot tabular tasks—whether predicting credit risk or diagnosing disease—consider starting from this three–part prompt skeleton before diving into heavy model fine‑tuning or massive unlabeled corpora. The right prompt can make an LLM do almost all heavy lifting while you keep your downstream pipeline lightweight and interpretable.

*Happy prompting!*



# From Text to Tensors: Turning LLM‑Generated Rules into Binary Features

When you ask a large language model (LLM) to “explain why this patient has heart failure,” it will reply with a list of natural‑language conditions—something you could read as a doctor’s note.  For a machine learning pipeline, however, we need something far more rigid: a set of numeric columns that say *yes* or *no* for each condition.  The **FeatLLM** framework bridges this gap by converting the messy text it produces into clean binary features that any downstream model can ingest.  Below is a walk‑through of that transformation pipeline, from prompt engineering to executable Python code and finally to a tiny linear classifier.

---

## 1. Why Binarise Rules at All?

In classic tabular learning we feed a model raw columns like “age” or “blood pressure.”  
FeatLLM asks an LLM to **engineer new columns** by summarising its domain knowledge into logical rules such as:

```
If age > 65 AND cholesterol > 200 → high risk of heart failure.
```

If we could turn each rule into a **binary flag**—`1` when the rule holds for a row, `0` otherwise—we end up with a feature matrix that explicitly encodes high‑level concepts.  A simple linear model can then learn how much weight to give each flag without ever seeing the original raw columns again during inference.  This yields two practical benefits:

* **Speed** – inference reduces to a dot product, no per‑sample LLM calls.
* **Interpretability** – each weight directly tells you how useful its underlying rule is.

---

## 2. The Noisy Nature of LLM Output

Even with carefully crafted prompts, an LLM’s answer is not always syntactically uniform:

* `>` may appear as “greater than”.
* Logical connectors may be spelled out (“and”, “or”) or replaced by symbols (`&`, `|`).
* Extra words or punctuation can sneak in (“If … then …”).

If we tried to parse such strings manually with regular expressions, we would quickly drown in edge cases.  FeatLLM sidesteps this by letting **the LLM parse its own output**—a trick that leverages its code‑generation abilities.

---

## 3. Two‑Stage Prompting: From Rules to Python

### 3️⃣ Stage 1 – Ask the LLM for Rules

A prompt is built from three parts:

1. **Basic information** – task description (“Predict chronic heart failure?”), feature definitions (“age is an integer”), and a few labeled examples serialized as text.
2. **Reasoning instruction** – first infer generic relationships (e.g., “older people have higher risk”) then combine these priors with the provided examples.
3. **Response instruction** – demand exactly ten rules per class and prescribe a fixed JSON‑like format:

```json
{
  "class": "positive",
  "rules": [
    "age > 65 and cholesterol > 200",
    "...",
    "..."]
}
```

The result is a *human‑readable* list of conditions that capture what the LLM thinks matters for each label.

### 🛠️ Stage 2 – Ask the LLM to Translate Rules into Code

We feed those raw strings back into another prompt that tells the model:

> “Given the column names `age`, `cholesterol`, … write a Python function `apply_rules(row)` that returns a list of 0/1 values indicating whether each rule is satisfied.”

Because GPT‑type models have been trained on billions of lines of code, they can reliably emit something like:

```python
def apply_rules(row):
    r = []
    r.append(int(row["age"] > 65 and row["cholesterol"] > 200))
    r.append(int(row["blood_pressure"] < 120))
    # ...
    return r
```

Notice how we do **not** try to hand‑craft parsers—the model itself normalises synonyms (“greater than” → `>`), adds parentheses where needed, and respects data types thanks to our earlier feature descriptions.

---

## 4. Executing the Generated Code (`exec()`)

The snippet returned by the LLM is now pure Python text.  
In FeatLLM we safely execute it with Python’s built‑in `exec()`:

```python
namespace = {}
exec(generated_code, {}, namespace)
apply_rules = namespace["apply_rules"]
```

We then run `apply_rules` over every row in the original table:

```python
Z = np.array([apply_rules(row) for row in dataset])   # shape = (N, R)
```

Here `Z` contains **binary features** (`0`/`1`) for all `R` rules extracted for a particular class (`R = 10` in our experiments).  
If there are `c` classes we repeat the process independently and obtain matrices `Z₁,…,Z_c`.

---

## 5. From Binary Flags to Class Probabilities

With binary matrices at hand we only need a lightweight classifier.  
FeatLLM uses a **non‑negative linear model** per class:

\[
\text{logit}_k^{\,i} \;=\; \max(\mathbf{w}_k,\;0)\;\cdot\;\mathbf{z}_k^{\,i},
\qquad
\mathbf{p}^{\,i} \;=\;\mathrm{Softmax}\bigl([\text{logit}_1^{\,i},\dots,\text{logit}_c^{\,i}]\bigr).
\]

* $\mathbf{z}_k^{\,i}\in\{0,1\}^{R}$ – binary flags for sample $i$ under class $k$.
* $\mathbf{w}_k$ – trainable weight vector learned on the few labeled shots.
* The `max(...,0)` projection forces all weights positive so that satisfying an additional rule never hurts a class score.

We optimise cross‑entropy loss on the *k*-shot training set (often as few as four examples). Because there are only $R$ parameters per class (e.g., $10$), training converges within seconds on an ordinary CPU/GPU.

---

## 6. Ensembling & Bagging (Optional Boost)

To reduce variance from any single set of rules, FeatLLM runs the whole pipeline multiple times:

* **Temperature** is raised during rule generation so different wording / rule sets appear.
* **Bagging** randomly selects subsets of columns or samples before each run,
rendering each trial slightly different.
* Final prediction averages softmax outputs across all trials (`T ≈ 20` works well).

Even if one run produces an outlier rule, it gets diluted by the ensemble—a classic wisdom from random forests transplanted onto language models.

---

## 7. Putting It All Together – A Mini‑Pipeline Sketch

```python
def featllm_pipeline(dataset, few_shot_examples):
    # ---- Stage 1: generate textual rules per class ----
    raw_rules = query_llm_for_rules(few_shot_examples)

    # ---- Stage 2: translate rules -> python ----
    python_code = query_llm_for_parsing(raw_rules)

    # ---- Execute generated code -> binary features ----
    exec(python_code)                     # defines apply_rules()
    Z = np.array([apply_rules(row) for row in dataset])

    # ---- Train lightweight linear model ----
    w = train_nonneg_linear(Z, labels)

    # ---- Predict on new data ----
    logits = np.maximum(w,0) @ Z.T
    probs = softmax(logits.T)
    return probs
```

The entire inference path after step 2 consists only of matrix multiplications—no more costly API calls or GPU‐bound transformer passes.

---

## 8. Takeaways for Practitioners

| What you get | Why it matters |
|--------------|----------------|
| **Human‑readable rules** from an LLM | Direct interpretability; you can inspect which conditions matter |
| **Binary feature matrix** | Works with any downstream learner (logistic regression, SVMs) |
| **Tiny training cost** | Only learns ≤ 10 weights per class |
| **Fast inference** | Eliminates per‑sample LLM queries |
| **Robustness via ensemble** | Handles noisy or ambiguous rule generations gracefully |

If you’re already using LLMs for tabular prediction (e.g., via *in‑context learning* or *parameter‑efficient tuning*), consider switching half of your workflow to *feature engineering*: let the model tell you what matters once, convert those insights into tidy tensors, and let classical ML do what it does best—quickly turning numbers into predictions.

--- 

By treating language models as expert *feature engineers* rather than end‑to‑end predictors, FeatLLM demonstrates how blurry natural language can be distilled into crisp binary tensors ready for production pipelines—all without ever fine‑tuning the massive model itself.



# Bagging and Ensembling in FeatLLM: Taming Prompt Length Limits While Boosting Robustness  

In recent months Large Language Models (LLMs) have been promoted as “feature engineers” for tabular prediction tasks.  **Feat LLM** takes this idea a step further: it asks an LLM once (or a few times) to write down human‑readable decision rules, turns those rules into binary features, and then fits a tiny linear classifier on top.  The result is an end‑to‑end predictor that leverages the knowledge stored inside an LLM while keeping inference cheap enough for production use.

Two practical hurdles appear as soon as we try this recipe on real‑world tables:

| Challenge | Why it matters |
|---|---|
| **Prompt length** | A wide table may have hundreds of column names and descriptions; adding them all plus a few-shot demo quickly exceeds the LLM’s context window (≈ 4 K tokens). |
| **Noisy / irrelevant columns** | In low‑shot regimes an algorithm can easily latch onto spurious correlations present only in the few labeled rows, which hurts generalisation dramatically. |

Feat LLM tackles both problems with **bagged prompting** followed by **ensemble averaging**. In what follows we unpack how these ingredients work together, why they keep prompts short enough for any table size, and how they protect us from irrelevant features.



---  

## 1️⃣ A quick refresher: From LLM‑generated rules to a linear predictor  

At training time Feat LLM constructs a prompt that contains  

* A **task description** (“Does this patient have chronic heart failure?”).  
* **Feature definitions** (e.g., “`age` is an integer representing years”).  
* **Few‑shot examples** serialized as “`f₁ is … , … , f_d is … . Answer:` label”.  

The prompt also instructs the LLM (“first reason about causal relationships, then list ten decision rules per class”) so it returns something like  

```
Class Yes:
  1) age > 65 AND systolic_bp > 140
  …
Class No:
  …
```  

Each textual rule is parsed back into Python code (the parsing itself is delegated again to the same LLM), executed on every row, and transformed into a **binary feature vector**  
\[
\mathbf z_k^i \in \{0,1\}^{R},
\]  
where \(R\) is the number of extracted rules for class \(k\) and \(i\) indexes data points.  

A lightweight linear model without bias then scores every class:

\[
\text{logit}_k^i \;=\;\max(\mathbf w_k,\;0)\cdot \mathbf z_k^i ,
\qquad 
\mathbf p^i \;=\;\operatorname{Softmax}\bigl([\text{logit}_1^i,\dots,\text{logit}_c^i]\bigr).
\]

Only the non‑negative weight vector \(\mathbf w_k\) needs training (cross‑entropy loss), which can be done with just a handful of labeled rows.



---  

## 2️⃣ Bagging – how we keep prompts inside token limits  

When \(d\), the number of original features, grows beyond a few dozen, feeding *all* column names into one prompt would overflow the context window even before we add examples or instructions.  

Feat LLM solves this by **feature bagging**, i.e., randomly selecting a subset  
\(S_t \subseteq \{1,\dots,d\}\)   (\(|S_t| = s \ll d\))  
for each LLM call \(t\). Only the names and definitions belonging to \(S_t\) appear in the prompt alongside the same few‑shot rows (which may also be subsampled). Because each call sees at most \(s\) column descriptors, the total token count stays well below the window size regardless of how large \(d\) actually is.



### Why random subsets still work  

* **Coverage through repetition** – By repeating the whole process \(T\) times with different random bags we eventually expose every column to at least one query.  
* **Reduced interference** – Irrelevant or highly correlated columns are unlikely to appear together repeatedly, so they seldom generate joint conditions that could mislead the downstream linear model.  

In our experiments we used \(T=20\) bags and extracted **10** rules per class per query—a configuration that consistently fit inside GPT‑3.5’s token budget even for datasets such as *Communities* (> 100 attributes).



---  

## 3️⃣ Temperature sampling & demo shuffling – diversifying rule sets  

Even when two prompts contain exactly the same text, an LLM can emit different outputs if its decoding temperature is raised above zero. Feat LLM deliberately sets **temperature = 0.5** so that each query produces a slightly different collection of logical conditions.  

Two more sources of randomness are injected:

* **Shuffling few‑shot demonstrations** – The order of example rows influences which patterns the model attends to first.
* **Independent runs per bag** – Each repetition uses its own random seed.

These tricks serve two purposes:

1️⃣ They mimic *self‑consistency*: multiple plausible rule sets are generated for the same underlying problem.\[^{1}\]  
2️⃣ Diversity increases chances that at least one set captures truly discriminative relationships while others compensate for occasional hallucinations.



---  

## 4️⃣ Ensemble via probability averaging  

Each bagged run \(t\) yields its own binary matrix \(\mathbf Z^{[t]}\), its own trained weight vectors \(\mathbf w^{[t]}\), and consequently its own class‑probability vector \(\mathbf p^{[t]}(\mathbf x)\).  

The final prediction aggregates them simply by averaging over all trials:

\[
\boxed{\;
\bar{\mathbf p}(\mathbf x)
   = \frac{1}{T}\sum_{t=1}^{T}\!\mathbf p^{[t]}(\mathbf x)
   \;}
\]

This **soft voting** scheme has several practical benefits:

* **Error cancellation** – If a particular run learned an erroneous rule (e.g., due to noisy wording), its contribution gets diluted by dozens of other runs.
* **Weight smoothing** – Rules that repeatedly receive high positive weights across runs become dominant contributors automatically.
* **Stability under noise** – Even when many spurious columns are present, only a tiny fraction (~1–2 %) ever appears inside any rule set (see Section 5); consequently their impact on \(\bar{\mathbf p}\) remains negligible.



---  

## 5️⃣ Why bagged ensembling hardens us against irrelevant or noisy columns  

To quantify robustness we performed a controlled experiment on the *Heart* dataset:

* Baseline scenario – train on eight labeled rows without any extra features.
* Stress test – progressively attach up to sixty unrelated columns taken from *Adult* (“marital status”, “education”, …).

All methods received exactly eight labeled rows throughout; only *Feat LLM* employed its bagged‐ensemble pipeline.\[^{2}\]  


### Observations  

| Method | AUC drop when ≈ 60 noisy columns added |
|--------|----------------------------------------|
| Conventional ML (*LogReg*, *XGBoost*) | ≈ 12 % |
| End‑to‑end LLM approaches (*In‑context*, *Tablett*, *TabLLM*) | ≈ 15–18 % |
| **Feat LLM** | ≤ 5 % |

Two mechanisms explain this gap:

1️⃣ **Prior‐knowledge filtering** – During step‑one reasoning (“infer causal relationships”) we explicitly ask the LLM not to rely on column values it has never seen before or those without definition cues. As a result ­– even if an irrelevant column sneaks into a prompt – it rarely makes it into any generated condition.
2️⃣ **Ensemble pruning** – After training, any binary feature whose learned weight stays near zero effectively disappears from Eq.(1). Since spurious conditions usually receive low importance across most bags, their aggregate influence vanishes when probabilities are averaged.



### Rule quality check  

We measured AUROC between each newly generated binary feature and the true label *before* weight tuning (“raw” features). Across fifteen datasets roughly **70–80 %** of those features already exhibited AUROC > 0.5 — meaning they were informative without any supervision at all! After training, almost all remaining low‑utility features received negligible weights (< 0.1), confirming that our simple linear layer indeed filters out residual noise.



---  

## 6️⃣ Cost profile – why you can actually deploy this today  

Because all heavy lifting happens off‑line during training,

* **Training cost:** roughly thirty API calls per dataset (20 bags × 10 rules + occasional parsing calls). Even at commercial rates this amounts to under two dollars for most public APIs.
* **Inference cost:** once the binary features are produced offline you need only evaluate a handful of dot products — practically identical in speed to logistic regression or even a single tree node evaluation.
* No per‑sample LLM call → latency drops from hundreds of milliseconds per row (as seen with Tablett/TabLLM) down to microseconds.



---  

## 7️⃣ Take‑away messages  

| What you get | How Feat LLM achieves it |
|--------------|--------------------------|
| **Scalable prompts** | Randomly sample *feature bags* so every request fits comfortably inside GPT’s context window regardless of table width. |
| **Diverse decision logic** | Use temperature > 0 together with shuffled demos → multiple plausible rule families per bag.| 
| **Robust predictions** | Average class probabilities across \(T=20\) independent runs → erroneous or noisy rules lose influence.| 
| **Low inference overhead** | After creation of binary features you run only a tiny non‑negative linear model.| 
| **Noise resistance** | Prior‐knowledge reasoning plus ensemble pruning dramatically limits degradation caused by irrelevant columns.| 

In short, Feat LLM reifies an often overlooked strength of large language models—the ability to verbalise domain knowledge—as compact binary features you can trust even when you have just a handful of labeled examples.



---  

### Closing thoughts  

For anyone building AI pipelines over financial records, electronic health files or any high‑dimensional tabular source where labeling is expensive, Feat LLM offers an attractive middle ground:

* You stay within API‐only access boundaries (no fine‑tuning needed).  
* You sidestep token‑limit roadblocks through systematic bagging.  
* You harness collective wisdom captured inside modern LLMs while preserving production‐ready latency via simple linear scoring.

Future work pointed out by the authors includes extending beyond low‑shot regimes and exploring richer feature constructs beyond logical rules—but even today’s version already demonstrates that “bagged prompting + ensemble averaging” is an effective recipe for turning massive language models into *practical*, *robust*, *feature engineers*.

# Performance Showdown: **FeatLLM** vs Traditional & LLM‑Based Tabular Learners  

In the era of large language models (LLMs), researchers are exploring whether these text‑centric giants can help us solve classic tabular problems—think credit scoring or medical diagnosis—especially when labeled data are scarce. A recent study introduced **Feat LLM**, a framework that turns an LLM into a *feature engineer* instead of a per‑sample predictor. Below we walk through how it works, the experimental battlefield it faced, and why its results are turning heads.

---

## 1️⃣ Why Feature Engineering with an LLM?

Tabular datasets usually come with **feature names** and brief textual definitions (e.g., “age – patient’s age in years”). An LLM trained on billions of web pages already knows a lot about what *older* people tend to experience (higher heart‑disease risk, lower earnings, etc.). **Feat LLM** asks the LLM:

1. **What causal relationships exist between the named features and the target?**  
2. **From a handful of labeled examples, what concrete decision rules separate the classes?**  

Instead of asking the LLM to output a label *for each row*, it asks the model to output **human‑readable rules** (“age > 55 AND cholesterol > 200 ⇒ high risk”). Those rules are then parsed into binary columns—*does this row satisfy rule i?*—and fed into an ultra‑light downstream predictor (a bias‑free linear model).  

Key side‑effects:

* **No per‑sample LLM calls at inference time** → latency stays comparable to classic models like logistic regression.  
* **Only API access needed** → no fine‑tuning or massive GPU resources required.  
* **Bagging + ensembling** mitigates prompt length limits when tables have hundreds of columns.

---

## 2️⃣ The Experimental Battlefield  

### 📊 Datasets  
Feat LLM was benchmarked on **13 public classification tasks**, covering finance (“Adult” income prediction), banking (“Bank”), health (“Heart”, “Myocardial”), social science (“Communities”), agriculture (“Cultivars”), demographics (“NHANES”), synthetic challenges (“Sequence‑type”, “Solution‑mix”), etc. The number of attributes ranged from a tidy dozen up to **>100** columns—exactly the scenario where long prompts become problematic for naïve LLM approaches.

### 🤖 Competitors  
| Category | Models |
|---|---|
| *Traditional* | Logistic Regression, XGBoost, Random Forest |
| *Unlabeled‑data helpers* | SCARF, STUNT |
| *Synthetic pre‑training* | TabPFN |
| *Direct LLM use* | In‑Context Learning (raw prompts), TABLET (prompts + rule prototypes), TabLLM (parameter‑efficient fine‑tuning) |

All LLM‑based baselines used GPT‑3.5 or T0 as given in their papers; traditional baselines received their best hyper‑parameters via grid search with cross‑validation.

### 🎯 Few‑Shot Regime  
For each dataset only **k ∈ {2, 4, 8, 16}** labeled examples were randomly sampled (`k`–shot learning). Typical industrial settings fall into this “low‑label” regime because annotating thousands of rows can be prohibitively expensive.

---

## 3️⃣ Head‑to‑Head Results  

### 📈 Overall AUC Landscape  
Across all datasets:

* **Feat LLM** either topped the leaderboard or secured second place in every case.
* When pitted against other LLM strategies (**TabLLM**, **STUNT**, **TABLET**, plain **In‑Context**) it delivered an **average lift of ≈ 10 % in AUC**.
* Against classic learners it was *competitive*: with only **4 shots**, Feat LLM’s AUC matched that of logistic regression/XGBoost trained on **32 shots**—a fivefold reduction in labeling effort while retaining predictive power.

> *“Our framework… when utilizing just 4 shots achieves comparable performance to conventional tabular baselines that require 32 shots”* – authors’ observation.

### 🧩 How Much Do Rules Help?  
The binary rule features themselves carried strong signal:

| Dataset | % Rules with AUROC > 0.5 *(pre‑tuning)* |
|---|---|
| Adult | ~71 % |
| Heart | ~68 % |
| Cultivars | ~74 % |

After learning the linear weights these “useful” rules received positive coefficients while noisy ones were automatically downweighted (< 0.1). This automatic pruning explains why performance remains stable even if the LLM occasionally spits out imperfect conditions.

### 🛡️ Robustness to Noise  
A stress test added columns from an unrelated dataset (Adult) into the **Heart** table. As spurious dimensions grew:

* Traditional models’ AUC degraded steadily.
* Most LLM baselines suffered sharp drops because they could latch onto meaningless correlations during prompt processing.
* **Feat LLM’s degradation was minimal**, confirming its two‑step reasoning (“first infer causal relevance before looking at examples”) effectively filters out irrelevant features—only ~1–2 % of generated rules ever referenced noisy columns.

---

## 4️⃣ Speed & Resource Comparison  

All experiments ran on an **NVIDIA A100 GPU** except TabLLM which required four GPUs due to model parallelism. Using the Adult dataset with **16 training shots**:

| Method | Training Time | Inference Time (per 1k rows) |
|---|---|---|
| Logistic Regression / XGBoost / Random Forest | ≤ seconds | ≤ seconds |
| In‑Context Learning / TABLET / TabLLM | minutes–hours *(per‐sample LLM calls or fine‐tuning)* | seconds–minutes *(large overhead)* |
| **Feat LLM** | ~30 API calls → < minute total | ≈ same as traditional models |

Hence **Feat LLM’s inference cost is essentially identical to a plain linear model**, while still leveraging sophisticated linguistic knowledge during feature creation—a win–win for production pipelines where latency budgets are tight.

---

## 5️⃣ What Makes Feat LLM Tick?  

1. **Two‑Step Prompt Design**  
   *Step 1*: “What general relationships exist?” – forces the model to draw from world knowledge rather than overfitting tiny example sets.  
   *Step 2*: “Given these relationships plus my examples, list ten rules per class.” – keeps rule sets bounded and parsable.

2. **Response Formatting**  
   Explicit instructions make the output easy for automatic parsing into Python code that evaluates each rule on every row—no hand‑crafted regex gymnastics required.

3. **Ensemble Bagging**  
   By randomly sampling subsets of features/instances before each prompt (high temperature + shuffling demonstration order), each trial yields a diverse rule set. Averaging logits across ~~20~~ ensembles stabilizes predictions and sidesteps prompt length caps for high‐dimensional tables.

4. **Linear Weight Tuning**  
   A tiny optimizer learns non‑negative weights $\max(\mathbf{w}_k ,0)$ for each binary rule $z_{k,i}$ via cross‐entropy loss:
   \[
   \text{logit}_k = \max(\mathbf{w}_k ,0)\cdot\mathbf{z}_k,\qquad
   \mathbf{p}= \operatorname{softmax}([\text{logit}_1,\dots,\text{logit}_c]).
   \]
   This step capitalizes on whatever signal the rules bring while discarding those that prove irrelevant in practice.

---

## 6️⃣ Takeaways & Outlook  

* **Performance:** In low‑label environments Feat LLM consistently outperforms both classic learners and prior LLM‐centric methods—often by double digits in AUC.
* **Efficiency:** No per‐sample LLM calls at test time means production deployment looks like any other linear classifier.
* **Scalability:** Bagged ensembles keep prompt sizes manageable even when tables exceed hundreds of columns.
* **Interpretability:** Rules are human‐readable—for many domains this transparency is a practical advantage over black‐box tree ensembles or deep nets.
* **Future Directions:** The authors plan to extend beyond strict rule generation toward richer feature transformations and larger training sets while preserving interpretability—a natural next step toward broader adoption in finance, healthcare, and beyond.

---

### TL;DR  

If you’re wrestling with scarce labels but still need state‑of‑the‑art accuracy on tabular data—especially when you can’t afford per‐row LLM queries—**Feat LLM** offers a compelling recipe: let an LLM write you decision rules once, convert them into binary columns, train a trivial linear scorer, and reap roughly ten percent higher AUC than any competing LLM approach while keeping latency on par with logistic regression. It’s an elegant blend of language understanding and classic statistics that finally makes large language models practical for everyday table crunching.



# Deploying FeatLLM with API‑Only Access – A Practical Guide  

*How to turn a single LLM inference pass into a full‑featured few‑shot tabular learner.*

---

## Introduction  

Large language models (LLMs) are great at reasoning over text, yet calling them for every row of a table quickly becomes prohibitively expensive. **FeatLLM** sidesteps this bottleneck by using the LLM **once** (or a few dozen times) to *engineer* a set of binary features—human‑readable “rules” that capture the relationship between columns and the target label. After the rules are extracted, prediction is performed by a tiny linear model that runs locally on your machine, requiring **no further API calls**.

In this tutorial we walk through a complete deployment pipeline that works **with API‑only access** (e.g., OpenAI’s `gpt‑3.5‑turbo`). You’ll learn how to:

1️⃣ Craft a single batch of rule‑generation prompts for an entire dataset  
2️⃣ Persist the generated Python code locally  
3️⃣ Train the lightweight linear weight model on the binary rule features  
4️⃣ Tune temperature and ensemble size for robustness  
5️⃣ Roughly estimate API costs per run  
6️⃣ Scale the approach to high‑dimensional tables  

All steps are grounded in the **FeatLLM** methodology described in the paper *Large Language Models Can Automatically Engineer Features for Few‑Shot Tabular Learning*.

---

## Overview of FeatLLM’s Workflow  

| Stage | What Happens | Why It Matters |
|-------|--------------|----------------|
| **Rule extraction** | A prompt containing task description, feature definitions, and a few labeled examples is sent to an LLM → The model returns *R* logical rules per class (e.g., “age > 60 && cholesterol ≤ 200”). | Captures prior knowledge and causal intuition without any training of the LLM itself. |
| **Feature generation** | Each rule is parsed into executable Python code that evaluates whether a row satisfies it → Binary feature vector $\mathbf{z}_k^i \in \{0,1\}^{R}$ for class $k$ is produced for every sample $i$. | Turns natural‐language reasoning into mathematically tractable inputs for downstream learning. |
| **Lightweight training** | Train a non‑negative linear model $\mathbf{w}_k \ge 0$ on the binary vectors using standard cross‑entropy loss (Eq. 2 in the paper). | Only a few gradient steps are needed; training is negligible compared with any fine‑tuning of an LLM. |
| **Ensembling & bagging** | Repeat rule extraction $T$ times with different random seeds/feature subsets → obtain $T$ independent weight vectors $\{\mathbf{w}[t]\}_{t=1}^{T}$. Final prediction = average softmax scores across ensembles. | Improves robustness against occasional noisy rules and mitigates context‑window limits on large tables.|

After step 1 you never talk to the LLM again—every subsequent operation runs locally.

---

## Step‑by‑Step Implementation  

Below is a concrete recipe you can copy–paste into a notebook or script.

### 1️⃣ Prepare Your Tabular Data  

You need three pieces:

| Item | Required format |
|------|----------------|
| Feature names | List `F = ["age", "cholesterol", …]` |
| Feature definitions *(optional but highly recommended)* | Dictionary `def_f = {"age": "numeric age in years", "cholesterol": "serum cholesterol in mg/dL", …}` |
| Few‑shot examples | `k` labeled rows (`k` as low as 4 works well). Serialize each row as:

```
age is 55.
cholesterol is 210.
...
Answer: Positive
```

The column descriptions help the LLM focus on the right variables during rule extraction (see Sec 3 of the paper).

### 2️⃣ Build the Prompt  

The prompt follows three logical blocks:

```text
[Basic Information]
Task: Does this patient have chronic heart failure? Yes/No.
Feature Descriptions:
- age: numeric age in years.
- cholesterol: serum cholesterol level.
...
Few-shot demonstrations:
<serialize k examples>

[Reasoning Instruction]
Step 1: Based solely on general medical knowledge infer which features are likely related to heart failure.
Step 2: Using both Step 1 insight and the few-shot examples derive exactly R (=10) decision rules for each class ("Yes" and "No").

[Response Instruction]
Please return your rules in JSON format:
{
  "Yes": ["age > 60 && cholesterol <= 200", ...],
  "No": ["age <= 60 && cholesterol > 200", ...]
}
```

Key points:

* **Two‑step reasoning** forces the model first to exploit its prior knowledge before looking at noisy few‑shot data—this reduces spurious rule generation.
* **Fixed number of rules** (`R = 10`) keeps prompts short enough for most APIs while still giving expressive power.
* **JSON response format** simplifies downstream parsing dramatically.

### 3️⃣ Issue Rule‑Generation Queries  

For most datasets you’ll run **\(T\)** independent queries (default \(T = 20\)). Each query returns a set of rules for all classes in one call—so you need only \(T\) API requests total.

```python
import openai, json, tqdm

def get_rules(prompt):
    resp = openai.ChatCompletion.create(
        model="gpt-3.5-turbo",
        messages=[{"role":"user","content":prompt}],
        temperature=0.5,
        max_tokens=800   # enough space for JSON output
    )
    return json.loads(resp["choices"][0]["message"]["content"])
```

If your table has hundreds of columns (>~150), you may exceed the model’s context window (~4 k tokens). In that case **feature bagging** solves it:

* Randomly sample a subset `F_subset ⊂ F` (e.g., √|F| columns) for each trial.
* Include only those columns in “Basic Information.”
* Across \(T\) trials most columns will appear at least once, giving you a comprehensive rule set after ensembling.

#### Cost estimate  

A typical prompt + answer pair uses roughly **2 500 tokens** (≈ 1 000 tokens for feature descriptions + few‐shot rows + instructions). At OpenAI’s public rate (\$0.002 / 1k tokens), one call costs ≈ \$0.005​\. With \(T = 20\), total expense ≈ **\$0.<sup>10</sup>–\$0.<sup>15</sup>**, well under a dollar even for large tables—far cheaper than repeatedly invoking an LLM during inference.

### 4️⃣ Parse Rules into Executable Code  

Even though you asked for JSON strings, natural language variations (“greater than”, “>”, “is above”) still appear inside each rule expression. The simplest way is to ask **the same LLM** once more to translate each textual condition into valid Python code:

```python
def translate_rule(rule_text):
    prompt = f"Convert this human readable condition into valid Python boolean expression:\n{rule_text}"
    # reuse same model parameters; low temperature encourages consistency.
    resp = openai.ChatCompletion.create(
        model="gpt-3.5-turbo",
        messages=[{"role":"user","content":prompt}],
        temperature=0,
        max_tokens=64,
    )
    return resp["choices"][0]["message"]["content"].strip()
```

Run this over all rules once and store the resulting functions locally (`rules_{trial_id}.py`). Because translation happens only **once**, it adds negligible extra cost (< \$0.01).

Alternatively you can implement simple string replacements (`">"` ↔ `" > "` etc.) if you prefer pure Python parsing—but delegating it to an LLM preserves robustness across diverse phrasing patterns reported in Section 4 of the paper.

### 5️⃣ Compute Binary Rule Features  

Load all generated functions and apply them vectorially:

```python
import pandas as pd
import numpy as np
import importlib.util

def load_rules(file_path):
    spec = importlib.util.spec_from_file_location("rules", file_path)
    mod = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(mod)
    return mod.RULES   # assume RULES is a dict {class_label: [func1,...]}

def evaluate_rules(df, rules):
    # output shape : N x C x R   where C = #classes , R = #rules/class
    N = len(df)
    C = len(rules)
    R = len(next(iter(rules.values())))
    Z = np.zeros((N,C,R), dtype=int)
    
    for c_idx,(cls,rlist) in enumerate(rules.items()):
        for r_idx,f in enumerate(rlist):
            Z[:,c_idx,r_idx] = df.apply(f, axis=1).astype(int)
    return Z.reshape(N,C,R)
```

The resulting tensor `Z[i,k,:] = \mathbf{z}_k^i` feeds directly into our linear predictor.

### 6️⃣ Train the Lightweight Linear Model  

Only **\(R \times C\)** trainable scalars are needed—a truly tiny model even when \(R=10\) and \(C=5\):

```python
import torch, torch.nn.functional as F

class RuleLinear(torch.nn.Module):
    def __init__(self, C,R):
        super().__init__()
        self.w = torch.nn.Parameter(torch.randn(C,R))   # unconstrained
    
    def forward(self, Z):   # Z shape: batch x C x R
        w_pos = torch.relu(self.w)                     # enforce w >= 0
        logits = torch.sum(w_pos * Z, dim=2)           # dot product per class
        probs = F.softmax(logits, dim=1)
        return probs

model = RuleLinear(C=len(classes), R=R_per_class)
optimizer = torch.optim.Adam([model.w], lr=0.01)

for epoch in range(200):
    optimizer.zero_grad()
    probs = model(torch.tensor(Z_train,dtype=torch.float))
    loss = F.cross_entropy(probs, torch.tensor(y_train))
    loss.backward()
    optimizer.step()
```

A small validation split or early stopping decided via `k`‑fold CV prevents overfitting—a technique employed by FeatLLM’s authors (see Sec 4).

#### Positive weight projection  

The ReLU (`torch.relu`) implements Eq.(2)’s `max(\mathbf{w},0)` constraint without extra bookkeeping and guarantees that every selected rule can only increase its class probability rather than suppress it—a design choice highlighted in Fig 2 of the paper.

### 7️⃣ Ensemble Predictions  

Repeat steps 2–6 across all \(T\) trials producing weight matrices `{w[t]}` and their corresponding binary tensors `{Z[t]}`:

```python
probs_ensemble = sum(model_t(Z_test_t) for model_t,Z_test_t in zip(models,Z_tests)) / T
preds = probs_ensemble.argmax(dim=1)
```

Averaging softmax scores implements exactly what FeatLLM describes in Eq.(3). Empirically this reduces variance substantially; performance plateaued around \(T=20\) according to Figure 7 in Appendix A of the paper.

---

## Hyperparameter Cheat Sheet  

| Hyperparameter | Recommended default | Effect |
|----------------|---------------------|--------|
| `temperature` (LLM) | **0.5** | Balances diversity vs deterministic output; higher values give more varied rules → better ensembles but larger variance across trials |
| `T` (ensemble size) | **20** | Improves AUC up to ≈ +2% beyond \(T=10\); diminishing returns after ≈ 20 |
| `R` (rules per class) | **10** | Sufficient expressive power while keeping prompt length modest |
| `feature_bag_size` | `min(√d , max_features_allowed_by_context)` | Controls prompt overflow when d ≫ 100; larger bags give richer individual rule sets but increase token budget |

When working under strict latency constraints you can cut `T` down to 10 or even 5 at modest accuracy loss—feel free to experiment based on your budget sheet!

---

## Scaling Guidance  

### Parallelizing API Calls  
OpenAI permits concurrent requests up to several hundred per minute depending on your plan. Dispatch all \(T\) prompts asynchronously (`asyncio`, `concurrent.futures`) and wait for completion—overall wall‐clock time drops from minutes to seconds even when \(T=20\).

### Persistent Rule Cache  
Rules depend only on feature metadata and few‐shot samples—not on unlabeled data at inference time—so store them (`pickle`, Git LFS) after first generation:

```
# after first run:
with open("rules_trial_03.pkl","wb") as f:
    pickle.dump(rules_03,f)
```

Future deployments simply reload (`pickle.load`) without touching the API again—a huge speedup when serving dozens of online predictions daily.

### Handling Very High Dimensional Data  
If you have > 300 columns, consider two layers of bagging:

* **Feature‐level bagging:** As described above—each trial sees only ≈ √d columns.
* **Sample‐level bagging:** When many labeled shots are available (> 64), randomly sample `< k` training rows inside each trial before prompting; this reduces token use while preserving statistical diversity across ensembles.

Both strategies were shown by FeatLLM authors (“Bagging” section) to maintain strong performance even under aggressive pruning conditions.

---

## Debugging Tips & Common Pitfalls  

| Symptom | Likely Cause | Fix |
|---------|---------------|-----|
| Some JSON fields are missing or malformed | Inconsistent response formatting from LLM | Tighten “Response Instruction” → explicitly ask for `"Yes": [...]` `"No": [...]` lines without comments |
| Generated Python functions raise exceptions (`NameError`, `SyntaxError`) | Phrase like “greater than” not translated properly | Run an extra “sanity check” pass that replaces textual operators (`"greater than"` → `">"` etc.) before feeding back into parser |
| All binary features are constant (`all zeros`) → model hangs on NaNs | Rules reference columns absent from current bagged subset | Ensure every trial includes at least one example containing each column referenced by any demonstration |
| Validation AUC far below training AUC despite many ensembles | Overfitting due to noisy spurious columns included in prompt | Increase `feature_bag_size` randomness or prune columns whose generated rules never fire (`np.mean(Z[:,c,:],axis=0)==0`) |

A quick sanity check after step&nbsp;4 is advisable:

```python
print("Nonzero rate per rule:", Z.mean(axis=0))
```

Rules with near‑zero activation rarely contribute useful signal and may be dropped before training without hurting performance—as shown by Table 6 (“Quality of features”) where after tuning most irrelevant rules receive near zero weights automatically.

## Putting It All Together – End-to-End Pseudocode  

```python
# ==== CONFIG ====
K_SHOTS       = 8            # few-shot count 
NUM_ENS       = 20           # ensemble size T 
RULES_PER_CLS = 10           # R 
TEMP          = 0.5          # LLM temperature 
BAG_SIZE      = None         # auto-sqrt(d)

# ==== STEP A : prepare data ==================================================
df          = pd.read_csv("mydata.csv")
features    = list(df.columns.drop('target'))
definitions = load_feature_definitions()              # optional dict

few_shot   = df.sample(K_SHOTS, stratify=df['target'])
prompt_tpl = build_prompt_template(features,
                                   definitions,
                                   few_shot,
                                   RULES_PER_CLS)

# ==== STEP B : generate & parse rules =======================================
all_rules   = []
for t in tqdm.tqdm(range(NUM_ENS)):
    # optionally subsample features if context window exceeded:
    sub_feat   = random_subset(features,
                               size=BAG_SIZE or int(np.sqrt(len(features))))
    prompt     = render_prompt(prompt_tpl,
                               feat_subset=sub_feat,
                               seed=t)
    raw_rules   = get_rules(prompt)
    
    # translate human phrasing → python lambda functions:
    py_rules   = {cls:[compile_rule(r) for r in lst]
                  for cls,lst in raw_rules.items()}
    
    all_rules.append(py_rules)

# ==== STEP C : evaluate binary matrices =====================================
Z_train_list, Z_test_list = [], []
y_train                  = extract_labels(few_shot)
for py_rules in all_rules:
    Z_train_list.append(evaluate_rules(train_df , py_rules))
    Z_test_list.append(evaluate_rules(test_df , py_rules))

# ==== STEP D : train lightweight linear models ==============================
models = []
for Z_tr in Z_train_list:
    mdl   = RuleLinear(C=len(classes), R=RULES_PER_CLS)
    train_linear(mdl,Z_tr,y_train)          # Adam + early stopping as earlier described
     models.append(mdl)

# ==== STEP E : ensemble inference ===========================================
probs_ens   = sum(mdl(torch.tensor(Z_t,float)) 
                  for mdl,Z_t in zip(models,Z_test_list)) / NUM_ENS
preds       = probs_ens.argmax(dim=1)

print("Final AUC:", roc_auc_score(y_test,preds))
```

That’s it! Once you’ve saved `"all_rules"` and trained `"models"` you can reload them tomorrow and score millions of rows instantly—no token bill beyond those ≈​20 initial queries.

# Beware the Biases: Ethical Implications of LLM‑Powered Feature Engineering  

## Introduction  

Large language models (LLMs) have become go‑to tools for “few‑shot” learning because they can draw on massive amounts of text‐based knowledge without any task‑specific fine‑tuning.  The recent **FeatLLM** framework pushes this idea further: instead of asking an LLM to label every row of a table, it asks the model to *engineer* new features—explicit decision rules that capture how different columns relate to a target label.  Those rules are turned into binary features and fed into a tiny linear model (see Eq. (2) in the paper), delivering strong predictive performance while keeping inference cheap.  

That efficiency is attractive for high‑stakes sectors such as healthcare and finance, where labeled data are scarce and rapid deployment matters.  Yet the same reliance on “prior knowledge baked into LLMs” also opens a subtle pathway for hidden societal biases or misinformation to seep into every downstream prediction.  Below we unpack how those biases can appear in FeatLLM’s pipeline and outline concrete steps practitioners can take to keep models fair and trustworthy.  

## How FeatLLM Turns Prior Knowledge into Rules  

FeatLLM works in three logical stages:  

1. **Prompt design** – A carefully crafted prompt supplies (i) task description, (ii) natural‑language feature names and definitions, and (iii) a handful of labeled examples.  
2. **Rule extraction** – The LLM performs a two‑step chain‑of‑thought reasoning: first it reasons about causal tendencies between features and the target using only its world knowledge; second it combines that insight with the few examples to generate a fixed set of decision rules (the paper fixes *10* rules per class).  
3. **Feature generation & downstream learning** – Each rule is parsed into executable code that produces a binary indicator $\mathbf{z}_k^i \in \{0,1\}^R$ for sample $i$ and class $k$.  A non‑negative linear model $\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i$ (Eq. (2)) learns a weight for every rule using just a few labeled rows.

The elegance lies in its *no‑training* requirement for the LLM itself—only 30 API calls are needed regardless of dataset size—and its ability to sidestep prompt length limits through bagged ensembles.  However, because **all** rule generation hinges on what the LLM “knows,” any bias embedded in its pretraining corpus can be reflected directly in $\mathbf{z}_k^i$ before any learning takes place.

## Where Bias Can Slip In  

| Stage | Why Bias May Appear | Example (healthcare / finance) |
|------|---------------------|--------------------------------|
| **Prior Knowledge** | LLMs ingest billions of web pages, news articles, and scientific abstracts that contain historical stereotypes or outdated medical lore. | An LLM might over‑emphasize “older age = higher heart disease risk” without accounting for confounding lifestyle factors. |
| **Rule Extraction** | During Step 1 (“infer causal relationship”), the model draws on its internal associations rather than purely data‐driven evidence. | It could generate a rule like “if `occupation = ‘unskilled’` then credit default risk is high,” reflecting socioeconomic bias present in training text. |
| **Few‑Shot Context** | With only $k$ labeled examples (often $k\le8$), there is limited signal to override an incorrect or biased rule that the LLM proposes. | In an 4‑shot diabetes prediction task, a spurious rule linking “skin color” to disease may survive because no counterexamples appear among the few instances shown. |
| **Linear Weighting** | The downstream linear model assigns positive weights $\mathbf{w}_k\ge0$ to all rules that appear useful on training data—but if training data themselves are small, noisy weights may reinforce biased rules rather than suppress them. | A rule suggesting “high income → loan approval” gets a high weight even though it unfairly penalizes low‑income applicants when income data are missing for many rows. |

The authors themselves flag this risk in their Broader Impact section: *“analyses of the impact of societal biases and misinformation embedded in the prior knowledge of LLMs would be important.”*  

## High‑Stakes Domains Under Threat  

### Healthcare  
Clinical decision support systems often operate under strict regulatory scrutiny because errors directly affect patient outcomes.  If FeatLLM learns a rule like “patients over 70 years old automatically receive a heart failure flag,” it might ignore nuanced lab results that contradict that generalization—potentially leading to over‑diagnosis or denial of treatment for younger patients who present atypical symptoms.

### Finance  
Credit scoring models already grapple with disparate impact across protected groups (race, gender, zip code).  An automatically generated rule such as “if `address = ‘rural’` then reject loan” may reproduce redlining patterns encoded in historical documents used during pretraining, even though modern regulations prohibit such factors.

In both contexts, **the cost of an undiscovered biased rule is magnified** because downstream users often trust these compact binary features as “expert‐crafted.”  

## Mitigation Strategies  

Below are practical steps derived from the structure of FeatLLM that can curb bias while preserving its few‑shot advantages.

### 1️⃣ Rule Auditing by Domain Experts  
* Before deploying any ensemble of generated features, present each rule (as plain English) to clinicians or credit officers.  
* Ask auditors to flag any reference to protected attributes (`age`, `gender`, `race`, `zip code`, etc.) and request justification grounded in medical/financial guidelines.  

> **Tip:** Because FeatLLM produces *deterministic* textual rules, they can be stored alongside model artifacts for traceability audits later on.

### 2️⃣ Fairness‑Aware Prompting  
Incorporate explicit instructions within the *Reasoning instruction* part of the prompt:

```
When you infer causal relationships, avoid using attributes that belong to protected classes.
If you must mention them, explicitly state why they are medically/financially relevant.
```

Embedding these constraints nudges the LLM toward fairness‐conscious reasoning without requiring any internal model modification.

### 3️⃣ Post‑hoc Validation & Disparate Impact Testing  
After binary features $\mathbf{z}_k^i$ are generated:

* Compute correlation between each feature and protected attributes across an unlabeled validation set.
* Apply standard fairness metrics (e.g., demographic parity difference) using the linear model’s predicted probabilities.
* Drop or re‑weight any feature whose correlation exceeds a predefined threshold (e.g., absolute Pearson $r>0.2$).

Because Eq. (2) forces non‑negative weights, setting $\mathbf{w}_{k,j}=0$ effectively removes a problematic rule from influencing decisions.

### 4️⃣ Weight Constraints & Regularization  
During training of $\mathbf{w}_k$, add a penalty term that discourages large weights on rules that mention sensitive columns:

$$\mathcal{L}_{\text{fair}} = \lambda \sum_{j\in\mathcal{S}} w_{k,j}$$

where $\mathcal{S}$ indexes rules referencing protected attributes and $\lambda$ controls trade‐off between accuracy and fairness.

### 5️⃣ Leveraging Ensemble Diversity  
FeatLLM already creates *T* bags of rules with different random seeds and feature subsets.  Empirically (see Figure 6 in the paper), increasing ensembles improves robustness against spurious correlations—a side effect useful for bias mitigation:

* If a biased rule appears only sporadically across ensembles, its averaged weight will remain small.
* Encourage diversity by varying both temperature during generation and which columns participate in each bag—this dilutes systematic bias tied to any single attribute.

### 6️⃣ Continuous Monitoring  
Even after rollout:

* Periodically re‐run rule extraction with fresh prompts (e.g., after updating an LLM version).  
* Compare new rule sets against historical ones—any emergent protected‐attribute references should trigger an immediate review cycle.

## A Quick Checklist for Practitioners  

| ✅ Item | What To Do |
|--------|------------|
| **Prompt Design** | Include explicit fairness clauses; list protected attributes separately so they can be omitted if needed |
| **Rule Review** | Have domain experts sign off each unique rule before it reaches production |
| **Feature Screening** | Auto‐filter binary features whose AUROC against target < 0.5 *or* whose correlation with protected groups exceeds threshold |
| **Model Training** | Enforce non‑negative weights + optional fairness penalty |
| **Ensemble Size** | Use at least 20 ensembles (as recommended by authors); monitor diminishing returns beyond that |
| **Audit Log** | Store raw LLM outputs (`rule text`), parsed code snippets (`exec` scripts), and final weight vectors (`w_k`) per version |

Applying this checklist turns FeatLLM from an impressive performance booster into a responsible tool that respects ethical constraints.

## Conclusion  

FeatLLM shows how an LLM can act as an *automatic feature engineer*, turning sparse labeled examples into powerful decision rules without ever fine‑tuning the language model itself.  Its gains—up to 10% higher AUROC over strong baselines across 13 diverse tabular datasets—are compelling evidence that prior knowledge can bridge data scarcity gaps.

However, that same prior knowledge carries forward historic stereotypes and misinformation embedded during pretraining.  In low‑shot settings there is little empirical pressure left for the downstream linear model to correct those missteps, making bias *intrinsic* rather than incidental.

By embedding fairness considerations directly into prompts, subjecting every generated rule to expert audit, filtering features through post‑hoc statistical checks, constraining learned weights, and exploiting ensemble diversity, practitioners can reap FeatLLM’s performance advantages while keeping ethical guardrails firmly in place.

As more organizations look to deploy AI where every misprediction costs lives or livelihoods, transparency about *how* those predictions were engineered becomes as crucial as accuracy itself.  With thoughtful safeguards layered around FeatLLM’s elegant workflow, we can harness large language models responsibly—turning them from black boxes into collaborative assistants rather than silent perpetuators of hidden bias.
