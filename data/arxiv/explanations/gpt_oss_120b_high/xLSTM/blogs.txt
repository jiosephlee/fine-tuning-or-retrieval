# Reviving LSTMs with Exponential Gating: How a Simple Change Fixes Forgetting  

## The forgetting problem in classic LSTMs  

Long Short‑Term Memory networks (LSTMs) have been the workhorse of sequence modeling for decades. Their core idea—an additive **cell state** update  

\[
c_t \;=\; f_t\,c_{t-1} \;+\; i_t\,z_t,
\qquad  
h_t \;=\; o_t\,\psi(c_t)
\]  

relies on three **sigmoid gates** \(i_t\) (input), \(f_t\) (forget) and \(o_t\) (output). Because the sigmoid maps any real number into the interval \((0,1)\), each gate can only *attenuate* information: an input gate of \(0.9\) writes slightly less than a full “ink stroke”, while a forget gate of \(0.2\) erases only a fifth of what is already there.  

This boundedness is normally a virtue—it protects against exploding gradients—but it also makes it hard for an LSTM to **revise** what it has stored. Imagine a sticky note you write on while reading a list of items. If you later discover a better description for an entry, you can’t simply replace the old text with more ink; you are limited to adding a faint correction that gets quickly diluted by earlier writing.  

In practice this limitation shows up in tasks such as *nearest‑neighbor search* over a sequence: while scanning a list of vectors, the network must continuously update its “best match” whenever it encounters a closer vector. Classic LSTMs tend to stick with the first high‑scoring entry because their forget gate cannot aggressively erase it once stored.\  

## From sigmoid to exponential – giving the gates more punch  

The authors of **xLSTM** observed that the bottleneck lies in the *shape* of the gate activations rather than the cell equation itself. Replacing the sigmoid with an **exponential** activation removes the upper bound:

\[
i_t \;=\;\exp(\tilde{i}_t), \qquad
f_t \;\in\;\bigl\{\sigma(\tilde{f}_t),\;\exp(\tilde{f}_t)\bigr\}.
\]

Now an input gate can produce values far larger than 1, effectively allowing the network to “write with as much ink as it wants”. Likewise, an exponential forget gate can **amplify** forgetting when needed—or be left as a sigmoid if gentle decay suffices. Crucially, the cell update formula stays identical; only the way we compute \(i_t\) and \(f_t\) changes.\  

## Normalizing away runaway values  

If we let exponentials run unchecked, both \(c_t\) and \(h_t\) would blow up quickly—training would become unstable and predictions meaningless. The xLSTM design solves this by introducing a **normalizer state** \(n_t\) that tracks how much *total* gate mass has been injected up to time \(t\):

\[
n_t \;=\; f_t\,n_{t-1} \;+\; i_t .
\]

The hidden state is then computed as a *ratio*:

\[
h_t \;=\; o_t\,\tilde{h}_t,\qquad 
\tilde{h}_t \;=\;\frac{c_t}{n_t}.
\]

Think of \(n_t\) as measuring the total amount of ink ever placed on our sticky note. Dividing by this sum automatically rescales the content so that its magnitude stays comparable across time steps—even if individual gates become huge.\  

## Stabilisation tricks – keeping floating‑point arithmetic honest  

Even with the \(c/n\) normalisation, raw exponentials can overflow before division occurs (e.g., \(\exp(1000)\) is far beyond double‑precision limits). To avoid this “ink spillage”, xLSTM introduces a **stabiliser state** \(m_t\):

\[
m_t \;=\;\max\bigl(\log(f_t)+m_{t-1},\,\log(i_t)\bigr).
\]

Using \(m_t\), we re‑scale both gates without changing their relative contribution:

\[
i'_t \;=\;\exp(\log(i_t)-m_t)
       \;=\;\exp(\tilde{i}_t-m_t),
\\[4pt]
f'_t \;=\;\exp(\log(f_t)+m_{t-1}-m_t).
\]

Because we subtract (or add) exactly the same quantity from every term that participates in the cell update, **the forward output remains identical**, and gradients are unchanged—yet all intermediate numbers stay well within representable ranges.\  

## The full sLSTM forward pass  

Putting everything together yields what the authors call **sLSTM** (scalar‑memory LSTM). Its computation at each time step looks like this:

```
c[t] = f[t] * c[t‑1] + i[t] * z[t]                # cell state
n[t] = f[t] * n[t‑1] + i[t]                     # normalizer state
h[t] = o[t] * (c[t] / n[t])                    # hidden output

z[t]   = φ( w_zᵀ x[t] + r_z h[t‑1] + b_z )      # cell input
i[t]   = exp( w_iᵀ x[t] + r_i h[t‑1] + b_i )    # input gate
f[t]   = σ/exp( w_fᵀ x[t] + r_f h[t‑1] + b_f ) # forget gate
o[t]   = σ( w_oᵀ x[t] + r_o h[t‑1] + b_o )      # output gate
```

All symbols carry their usual meaning from classic LSTMs (\(x[t]\): input vector, \(w_\*\): input weights, \(r_\*\): recurrent weights, \(b_\*\): biases). The only structural changes are:
* **Exponential activation** for \(i[t]\) and optionally \(f[t]\);
* **Normaliser** \(n[t]\);
* **Optional stabiliser** \(m[t]\) applied behind the scenes.

When multiple memory cells are stacked together—as done in modern large language models—the same pattern repeats across each cell dimension.\  

## Why exponential gating lets us rewrite memories  

Returning to our sticky‑note metaphor: with sigmoid gates we could only add light pencil marks on top of an existing entry—hardly enough to obscure something previously written clearly. Exponential gates act like a high‑lighter that can pour arbitrarily thick ink over any previous note. The normaliser then “erodes” older ink proportionally, ensuring that fresh highlights dominate without blowing up overall intensity.\  

In concrete terms, during a nearest‑neighbor scan an early high‑similarity vector produces an initial strong imprint in \(c_{t}\). When later we encounter an even more similar vector, its exponentially larger input gate (\(i_{t}\)) overwhelms—through multiplication by background forgetting—any past imprint. The division by \(n_{t}\) guarantees that this overwrite stays numerically stable.\  

Empirically, xLSTM’s exponential gating reduces mean‑squared error on the nearest‑neighbor task dramatically compared to classic LSTMs (see Figure 1 left panel in the paper). It also lifts perplexity on rare token prediction—another symptom of insufficient storage capacity—once combined with matrix memory (the **mLSTM** variant).\  

## Scaling up – xLSTM blocks and architectures  

The authors embed sLSTM (and its matrix counterpart mLSTM) inside residual blocks familiar from Transformers (“xLSTM blocks”) and stack them depth‑wise (`xLSTM[7:1]` meaning seven mLSTM blocks per eight total layers). This yields end‑to‑end architectures that retain linear time/constant memory complexity while competing with state‑of‑the‑art Transformers and State Space Models on large language modeling benchmarks.\  

Even though sLSTM’s hidden‑to‑hidden connections prevent full parallel execution across time steps—making it slower than mLSTM—the authors report an optimized CUDA kernel that runs at most twice as slow as its fully parallel counterpart. For many applications where revising memory is crucial (e.g., code execution tracing or long context reasoning), this extra cost may be worthwhile.\  

## Takeaways  

| Insight | Why it matters |
|---|---|
| **Exponential gates:** Removing the sigmoid’s upper bound gives each time step unlimited capacity to inject or erase information. | Enables “on‑the‑fly” memory rewrites that classic LSTMs cannot perform efficiently. |
| **Normalizer state `nₜ`:** Tracks cumulative gate activity and rescales hidden output (`cₜ / nₜ`). | Keeps activations bounded despite unbounded raw gates. |
| **Stabiliser `mₜ`:** Rewrites exponentials in log space before applying them back out. | Prevents overflow while preserving exact forward/backward behavior. |
| **sLSTM forward equations:** Simple extensions of standard LSTM equations—no extra parameters needed beyond existing weights plus one extra scalar per unit (`nₜ`). | Easy drop‑in replacement for existing recurrent stacks. |
| **Empirical payoff:** Lower error on tasks requiring dynamic revision (nearest neighbor), better rare token prediction when paired with matrix memory, competitive perplexities against Transformers at billions of parameters. | Shows that revisiting old ideas with modest tweaks can close the gap with newer architectures. |

In short, turning sigmoids into exponentials—and tempering them with clever normalisation – equips LSTMs with true *rewritability*. This single change unlocks capabilities previously exclusive to attention mechanisms or sophisticated state space models while preserving RNNs’ linear‐time scaling advantage.\  

If you’ve been using vanilla LSTMs and hit roadblocks where “once stored = forever stored” felt too rigid, give exponential gating a try. The code is openly available at https://github.com/NX-AI/xlstm — experiment with `sLSTM` cells inside your existing recurrent pipelines and see how much easier your models become at learning to forget—and remember—on demand.



# sLSTM Explained: Scalar Memory Meets Smart Mixing for Better State Tracking  

*Subtitle*: A layperson’s guide to the new sLSTM variant – how a single‑value cell, a clever normalizer, and “memory mixing” across heads let recurrent models solve tasks that vanilla Transformers struggle with.

---

## 1. Why revisit LSTMs at all?

When the Transformer arrived in 2017 it seemed to have put the classic Long Short‑Term Memory (LSTM) network on the sidelines. Transformers scale nicely thanks to parallelizable self‑attention, while the original LSTM suffers from three well‑known drawbacks:

1. **No way to revise old storage decisions** – once a value is written into the cell it is hard to “undo” later.
2. **Limited storage capacity** – each cell holds only a scalar (or a few scalars), which makes remembering rare events difficult.
3. **Sequential bottleneck** – hidden‑to‑hidden connections force step‑by‑step processing.

The *Extended* family introduced in the xLSTM paper tackles these issues head‑on. The first member of this family is **sLSTM** (scalar LSTM). It keeps the simple scalar memory of the original LSTM but adds two crucial twists: **exponential gating** and **smart memory mixing** backed by a **normalizer** that tracks gate strength. Let’s unpack what each piece does and why it matters.

---

## 2. A quick refresher: the classic LSTM cell

At time step \(t\) a textbook LSTM updates three quantities:

\[
\begin{aligned}
c_t &= f_t \, c_{t-1} + i_t \, z_t &&\text{(cell state)}\\
h_t &= o_t \,\psi(c_t) &&\text{(hidden output)}\\
z_t &= \varphi(\tilde z_t) &&\text{(cell input)}
\end{aligned}
\]

* \(i_t\), \(f_t\), \(o_t\) are **input**, **forget**, and **output** gates (sigmoids).  
* \(c_{t-1}\) is the *constant error carousel*: an additive term that lets gradients flow unchanged over long horizons.  
* \(\psi\) squashes the raw cell value (usually \(\tanh\)) so it stays bounded.

Even with this clever design, once \(i_t\) writes something into \(c_t\), its influence can only decay through \(f_t\); there’s no mechanism for an *exponential* “rewriting” that can quickly boost or erase past content when needed.

---

## 3. Exponential gating: letting the model rewrite its past

sLSTM replaces the sigmoid activation on **input** (and optionally on **forget**) gates with an exponential function:

\[
i_t = \exp(\tilde i_t), \qquad 
f_t = \sigma(\tilde f_t)\ \text{or}\ \exp(\tilde f_t).
\]

Why exponentials? Because they grow (or shrink) much faster than sigmoids, giving the model two new abilities:

* **Rapid revision** – If a later token suggests that what was stored earlier was wrong, an exponentially larger \(i_t\) can overwrite it in one step instead of waiting for many small updates.
* **Dynamic range** – The gate can amplify contributions far beyond the unit interval \([0,1]\). This is essential when we want to *re‑weight* old information relative to new evidence.

Of course exponentials can explode numerically, so the authors introduce a stabilizer state \(m_t\) (borrowed from Milakov & Finkelstein’s work) that rescales both gates without altering gradients:

\[
\begin{aligned}
m_t &= \max\bigl(\log f_t + m_{t-1},\, \log i_t\bigr),\\
i'_t &= \exp(\log i_t - m_t),\\
f'_t &= \exp(\log f_t + m_{t-1} - m_t).
\end{aligned}
\]

Using \(i'_t\) and \(f'_t\) in place of \(i_t,f_t\) leaves everything else unchanged while keeping numbers well‑behaved.

---

## 4. The normalizer: remembering how strong your gates have been

When we start using exponentials, raw values in the cell can drift far from any sensible scale—imagine dividing by something massive or tiny later on! To keep hidden outputs comparable across time steps, sLSTM introduces a *normalizer state* \(n_t\):

\[
n_t = f_t\, n_{t-1} + i_t.
\]

Intuitively, \(n_t\) accumulates the same gate strengths that contributed to the cell itself:

* The term \(f_t n_{t-1}\) carries forward past gate magnitudes that survived forgetting.
* The term \(i_t\) adds today’s contribution weight.

The hidden output now uses *normalized* memory:

\[
h_t = o_t\, \tilde h _t,\qquad 
\tilde h _t = \frac{c_t}{n_t}.
\]

Dividing by \(n_t\) makes sure that if both numerator and denominator grew because gates were large, their ratio stays stable—much like normalizing a moving average by its total weight.

---

## 5. Memory mixing across multiple heads

A single scalar per cell is fine for many tasks but insufficient for patterns that need *state tracking*. The classic solution in modern RNNs is simply to stack many scalar cells into a vector \(\mathbf c _t \in \mathbb R^d\). sLSTM goes further by allowing *memory mixing* inside each “head”.

### What does “mixing” mean?

Recall that in vanilla LSTMs each scalar cell updates independently:
\(c^{(k)}_t = f^{(k)}_t c^{(k)}_{t-1}+ i^{(k)}_t z^{(k)}_t.\)

In sLSTM we introduce recurrent weight matrices — e.g., \(\mathbf R_{\!z}, \mathbf R_{\!i}, \mathbf R_{\!f}, \mathbf R_{\!o}\)—that connect hidden states from one time step back into **all** cells within *the same head*. Concretely,

```
z   = φ( w_z^T xₜ + R_z h_{t-1} + b_z )
i   = exp( w_i^T xₜ + R_i h_{t-1} + b_i )
f   = σ( w_f^T xₜ + R_f h_{t-1} + b_f )
o   = σ( w_o^T xₜ + R_o h_{t-1} + b_o )
```

Because every gate now receives information from *all* hidden units of its head, each scalar memory can influence—and be influenced by—its siblings at every step. This “mixing” gives rise to **state tracking**, where a pattern spanning many steps can be encoded jointly across cells rather than being forced into one isolated scalar line.

### Heads vs Cells

* **Heads** are independent groups of cells; there is no mixing across different heads (the matrices are block‑diagonal).  
* Inside each head we may have dozens or hundreds of scalar cells whose dynamics are intertwined through those recurrent matrices.

This architecture mirrors multi‑head attention in Transformers—multiple parallel pathways—but retains a strictly recurrent connection inside each head, which is crucial for tasks where order matters deeply (e.g., parity checking).

---

## 6. A concrete case: parity checking and why Transformers stumble

The **parity task** asks a model to output (`0`/`1`) whether an input sequence contains an odd number of `1`s so far. Solving it requires preserving a binary counter modulo 2 throughout arbitrarily long inputs—exactly what “state tracking” is built for.

In the paper’s synthetic experiments (see Fig 2 in Section 4 – “Synthetic Tasks”), sLSTM variants achieved near‑perfect accuracy on parity while vanilla Transformers and many State Space Models plateaued around random chance (~0.5). The reason is simple:

| Model | Has hidden‑to‑hidden recurrent connections? | Can revise stored info? | Result on parity |
|-------|--------------------------------------------|------------------------|------------------|
| Transformer | No (self‑attention only at current step) | No | Fails |
| SSM (e.g., Mamba) | Linear dynamics only | Limited | Fails |
| vanilla LSTM | Yes (scalar mixing limited) | Yes (sigmoid gates) | Partial |
| **sLSTM** | Yes + exponential gates + normalizer | Yes (fast rewrite) | ✔️ Near perfect |

Because sLSTM mixes scalars inside each head and uses exponential gates, it can toggle its internal parity bit cleanly after every `1`, while never being overwhelmed by older contributions thanks to the normalizer division.

---

## 7. Putting it together – why sLSTM matters for large language models

The authors embed sLSTM blocks inside *xLSTM residual architectures*. A high‑level view:

1. Input → linear projection → *(optional up‑projection)* → **sLSTM block** → *(down‑projection)* → residual add → layer norm.
2. Stack many such blocks → autoregressive language model.

Key takeaways:

* **Linear time & constant memory w.r.t sequence length** – unlike Transformer's quadratic attention cost.
* **Better handling of rare tokens & long dependencies** – thanks to richer recurrence.
* **Scales well when combined with matrix–memory mLSTMs**, forming hybrid xLSTMs that achieve competitive perplexities at billions of parameters (see Table 1 & Fig 5).

In practice you’ll often see an xLSTM combo like `[7 mLSTM : 1 sLSTM]` blocks; even one sLSTM block injects the crucial state‐tracking ability into an otherwise parallelizable pipeline.

---

## 8. Pros & cons at a glance

### Advantages
- **Exponential gating** enables rapid overwriting—critical for tasks where early decisions may need correction later.
- **Normalizer** keeps hidden activations stable despite unbounded gate values.
- **Memory mixing within heads** gives deterministic state tracking power absent in pure attention models.
- Linear computational cost per token; constant GPU memory independent of context length—friendly for edge devices or very long prompts.

### Limitations
- Mixing introduces *sequential dependencies*, making full parallelization impossible for pure sLSTM blocks (though custom CUDA kernels keep slowdown under ~2× compared to fully parallel mLSTMs).
- Exponential gates require careful initialization of forget biases; otherwise training may diverge early.
- Benchmarks show minor overhead compared with FlashAttention or optimized SSM kernels—future engineering can close this gap.

---

## 9. Bottom line

The sLSTM variant shows that you don’t need massive vector memories to get smarter recurrence—you just need smarter *gate dynamics* and a bit of structured mixing. By pairing a single scalar per cell with an exponential gate scheme and a simple normalizer, sLSTM regains the ability to *revise* old memories fast enough for complex pattern tracking such as parity checks—something vanilla Transformers simply cannot do due to their lack of hidden‐to‐hidden connections.

When incorporated inside larger xLSTM stacks, this humble scalar upgrade becomes part of a language model that rivals Transformers on perplexity while keeping linear runtime and constant memory footprint—a compelling direction for anyone looking beyond self‑attention toward scalable recurrent architectures.

--- 

*If you’re curious about implementation details or want to try out xLSTMs yourself, check out their open-source repo:* <https://github.com/NX-AI/xlstm>. Happy modeling!



# mLSTM Unlocked: From Tiny Scalars to Full‑Size Matrix Memories  

*How turning a single number into a full matrix gives recurrent networks a built‑in key‑value store.*

---

## Introduction  

When Long Short‑Term Memory (LSTM) networks were introduced in the early 1990s, their “cell” was just one scalar value per hidden unit—a little bucket that could be filled or emptied over time. That scalar design worked wonders for many sequence tasks, yet it imposed an obvious bottleneck: all the information you wanted to remember had to be crammed into a single number per unit.  

The recent **xLSTM** paper asks whether we can push LSTMs into the same performance league as today’s large language models simply by giving them more expressive memories. The answer comes in two flavors:

1. **sLSTM** – keeps the scalar cell but introduces exponential gating and new mixing mechanisms.  
2. **mLSTM** – **expands the cell from a scalar to a full matrix**, turning every recurrent layer into an implicit key‑value store.

In this post we focus on **mLSTM** and unpack three ideas that make it powerful:

* A matrix‑valued memory **\(\mathbf C\in\mathbb R^{d\times d}\)** that can accumulate many key‑value pairs.  
* The **covariance update rule**—the mathematical version of “adding a flashcard to your notebook”.  
* **Exponential gates** that act like learnable learning rates for these updates.

Together they give an RNN the capacity of a miniature associative database while still operating with linear time and constant memory cost per token.

---

## From Scalar Cell to Matrix Memory  

In a classic LSTM the recurrence looks like

\[
c_t = f_t\,c_{t-1} + i_t\,z_t ,
\qquad
h_t = o_t\,\psi(c_t),
\]

where \(c_t\) is the scalar cell state and \(f_t,i_t,o_t\) are sigmoid gates.  

**mLSTM replaces \(c_t\) with a matrix \(\mathbf C_t\).** Each time step now stores two vectors:

* **Key** \(\mathbf k_t \in \mathbb R^{d}\) – essentially an address.
* **Value** \(\mathbf v_t \in \mathbb R^{d}\) – the content you want to retrieve later.

The memory matrix accumulates outer products of these pairs, building up an associative map inside the network itself.

---

## The Covariance Update Rule – Adding Flashcards to Your Notebook  

Think of your notebook as an empty table with \(d\times d\) cells. When you encounter a new fact (a key–value pair), you write it down by adding its outer product:

\[
\boxed{
\mathbf C_{t} = f_{t}\,\mathbf C_{t-1}
               + i_{t}\,\bigl(\mathbf v_{t}\,\mathbf k_{t}^{\!\top}\bigr)
}
\tag{1}
\]

* The term \(\mathbf v_{t}\,\mathbf k_{t}^{\!\top}\) is exactly what you get when you multiply a column vector (**value**) by a row vector (**key**)—a rank‑one “flashcard” that links the two.
* The **forget gate \(f_{t}\)** optionally decays older entries, acting like erasing faded ink.
* The **input gate \(i_{t}\)** scales how strongly you write this new flashcard into the notebook—it’s your learning rate for that particular update.

Because each update adds an outer product rather than overwriting, you can keep stacking many flashcards without losing earlier ones—provided you control forgetting with \(f_{t}\).

---

## Exponential Gates as Learning Rates  

Standard LSTMs use sigmoid activations for their gates (\(0<g<1\)). In mLSTM we switch the input gate—and optionally the forget gate—to **exponential activations**:

\[
i_{t}= \exp(\tilde i_{t}), 
\qquad 
f_{t}= 
   \begin{cases}
      \sigma(\tilde f_{t})\\
      \exp(\tilde f_{t}) 
   \end{cases}
\]

Why exponentials?  

* An exponential can produce values **larger than 1**, letting us *amplify* important updates rather than merely scaling them down.
* When interpreted through Eq (1), \(i_{t}\) directly becomes a *learnable step size*: large \(i_{t}\) writes a bright flashcard, small \(i_{t}\) writes a faint one.
* Similarly, an exponential forget gate can implement *growth* or *decay* beyond simple attenuation—a powerful way to model long‑range retention or rapid forgetting.

To keep numbers from exploding, mLSTM adopts the same stabilizer state used in sLSTM:

\[
m_t = \max\bigl(\log(f_t)+m_{t-1},\,\log(i_t)\bigr),
\]
followed by rescaling:
\(i'_t = \exp(\log(i_t)-m_t)\),   
\(f'_t = \exp(\log(f_t)+m_{t-1}-m_t)\).

These stabilized gates behave identically in forward pass and gradient flow, yet stay numerically safe during training.

---

## Why Matrix Memory Means Massive Capacity  

A scalar cell can store at most one real number per unit—effectively one bit of “information” after quantization. A full matrix memory has \(d^2\) parameters that evolve *without any learned weights*. Each new key–value pair contributes another rank‑one slice to this space, so after processing \(T\) tokens you have roughly \(T\) rank‑one components summed together (subject to forgetting).

The consequences are striking:

| Property | Scalar LSTM | mLSTM (matrix memory) |
|----------|-------------|----------------------|
| Storage dimension | \(d\) scalars | \(d\times d\) entries |
| Natural key‑value binding | None (implicit via gating) | Explicit via outer product |
| Ability to retrieve rare items | Limited – often overwritten | High – each flashcard persists until decayed |
| Scaling with hidden size |\(~O(d)\)|\(~O(d^2)\) effective capacity |

In language modeling experiments on **Wikitext‑103**, this extra capacity translates into markedly lower perplexities on low‑frequency tokens—precisely where traditional LSTMs stumble because they cannot keep enough distinct traces of rare words.  

---

## Parallelism and Practicalities  

At first glance adding a matrix recurrence seems expensive: each step involves two dense matrix multiplies (\(\mathbf v_k^{\!\top}\) construction and query read). However:

* There are **no hidden‑to‑hidden recurrent connections** beyond the matrix update. This eliminates sequential dependencies other than the simple scan over time.
* The whole scan can be expressed as parallel prefix operations—a technique used by FlashAttention and other recent linear attention kernels.
* In practice mLSTM’s forward pass runs comparably fast on GPUs when implemented with batched matrix ops despite its quadratic inner dimension cost.

The tradeoff is clear: **linear compute w.r.t sequence length** versus **extra per‑step matrix work** proportional to \(d^2\). For hidden sizes typical of current language models (\(d=1024–2048\)), modern GPUs handle this comfortably, especially when leveraging mixed precision training.

---

## Results at a Glance  

The xLSTM paper reports several head‑to‑head studies showing how mLSTM shines:

* On synthetic associative recall tasks with up to 256 key–value pairs and context lengths of 2048 tokens, an architecture mixing just one mLSTM block with several sLSTM blocks (**xLSTM[1:1]**) outperformed all non‑Transformer baselines.
* In large‐scale language modeling (300 B tokens), pure mLSTM stacks (**xLSTM[1:0]**) achieved lower validation perplexity than both GPT‐style Transformers (e.g., Llama) and strong State‑Space models (Mamba).
* Crucially, when tested on much longer contexts than seen during training (up to 16 k tokens), mLSTM kept its perplexity flat—evidence that its built‑in key‐value store truly preserves information across hundreds of steps.

These results suggest that simply “making the cell bigger” does more than increase parameter count—it endows the model with an *associative memory* that scales gracefully with data size.

---

## Takeaways  

1. **Matrix memories give RNNs an explicit associative store** without adding trainable parameters beyond standard linear projections.
2. **Covariance updates provide a clean algebraic recipe** for writing and reading key–value pairs—think of each outer product as adding a flashcard.
3. **Exponential gating turns those flashcards into learnable updates**, acting like dynamic learning rates (and decay rates when applied to forget gates).
4. Despite extra inner‐matrix work, mLSTM retains linear time complexity across sequence length and enjoys excellent parallelization on modern hardware.
5. Empirically, this design narrows—and in some regimes closes—the performance gap between LSTMs and today’s top Transformers and State‑Space models.

The next frontier will be scaling these architectures up further while tightening CUDA kernels for matrix updates—something that could make mLSTMs competitive *everywhere*, from language models running on cloud clusters down to edge devices needing efficient continual learning.

--- 

If you’re curious about code or want to try it yourself, the authors provide an open source implementation at `github.com/NX-AI/xlstm`. Happy experimenting!



# Building xLSTM Blocks: Marrying Classic RNNs with Modern Residual Architectures

The recent **xLSTM** paper shows that we can give the venerable Long Short‑Term Memory (LSTM) a fresh makeover by embedding its newer variants—**sLSTM** and **mLSTM**—into modern residual blocks. The result looks a lot like what Transformers do (layer‑norm, skip connections, projection layers), yet it retains **linear** computation in sequence length. In this post we walk through how the authors stitch these recurrent cells into residual pipelines, why they choose different “up‑projection” strategies for scalar vs. matrix memories, and what this means for both speed and accuracy.

---

## 1. From Classic LSTMs to Their Extended Cousins  

Before diving into blocks, let’s recall the core LSTM recurrence:

\[
c_t = f_t \, c_{t-1} + i_t \, z_t , \qquad
h_t = o_t \,\psi(c_t),
\]

where \(c_t\) is the cell state, \(h_t\) the hidden output and \(i,f,o\) are sigmoid gates controlling input, forget and output respectively. This simple additive update—often called the *constant error carousel*—solved the vanishing‑gradient problem but left three practical roadblocks:

1. **Hard‑to‑revise storage:** once a value is written into \(c\), it’s difficult to overwrite it later.
2. **Limited capacity:** a scalar cell compresses all information into a single number.
3. **Sequential bottleneck:** hidden‑to‑hidden connections prevent parallel execution.

xLSTM tackles these problems by introducing two new cell families:

| Variant | Memory type | Key innovations |
|--------|-------------|-----------------|
| **sLSTM** | Scalar cell \(c\) plus a *normalizer* \(n\) | Exponential gating + explicit normalizer → easy revision of stored values |
| **mLSTM** | Matrix cell \(\mathbf{C}\in\mathbb{R}^{d\times d}\) | Covariance (outer‑product) update \(\mathbf{C}_t = f_t\mathbf{C}_{t-1}+i_t\,\mathbf{v}_t\mathbf{k}_t^\top\) → massive storage capacity; no hidden‑hidden mixing → fully parallelizable |

Both cells use **exponential gates** (\(i_t = \exp(\tilde{i}_t)\) and optionally \(f_t = \exp(\tilde{f}_t)\)) together with a stabilizer state that rescales any exploding values without affecting gradients (see Eq. (7) in the paper). This gives them more expressive dynamics while remaining trainable at billions of parameters.

---

## 2. Why Put Recurrent Cells Inside Residual Blocks?

Transformers made residual connections standard because they enable very deep stacks without gradient vanishing. xLSTM adopts the same *pre‑LayerNorm* backbone used in most large language models:

```
x ──► LayerNorm ──► Block ──► +────► Output
               │             │
               └────── Skip──┘
```

Embedding an sLSTM or mLSTM inside such a block gives us two crucial benefits:

1. **Non‑linear summarization of history** – The recurrent cell aggregates information over thousands of timesteps while staying linear in time.
2. **High‑dimensional separation** – A projection layer expands the hidden representation before or after the recurrent step (the “up‑projection”), allowing easier linear separation of contexts as per Cover’s theorem.

Thus we get *the best of both worlds*: LSTMs’ sequential reasoning plus Transformers’ depth-friendly architecture.

---

## 3. Post‑Up‑Projection vs. Pre‑Up‑Projection  

The only architectural difference between an sLSTM block and an mLSTM block lies in *where* we insert the high‑dimensional projection relative to the recurrent core:

### 3.1 Post‑Up‑Projection (sLSTM)

```
Input → Linear ↓
        ↓        ↑   ← Residual
      sLSTM     ↑
        ↓       ↓
   Up‐Projection → Activation → Linear → Output
```

*Steps*:
1. **Down‐project** input to match the scalar cell size.
2. Run the **sLSTM recurrence** (producing hidden \(h_{t}\)).
3. **Up‐project** the hidden state to a higher dimension (\(d_{\text{high}}\)).
4. Apply a nonlinearity (e.g., GELU) and project back down for the skip connection.

**Why post?**  
The scalar memory of sLSTM already compresses information tightly; expanding *after* it lets the model enrich that compressed signal without inflating the memory itself. This mirrors what standard Transformer blocks do: compute attention first, then lift the result into a larger space before mixing with feed‑forward layers.

### 3.2 Pre‑Up‑Projection (mLSTM)

```
Input → Linear ↓
        ↓        ↑   ← Residual
   Up‐Projection → Activation → Linear → mLSTM → Linear → Output
```

*Steps*:
1. **Up‐project** input into a high‑dimensional key/value/query space.
2. Feed this richer representation into the **mLSTM**, which maintains a full matrix memory \(\mathbf{C}\).
3. The matrix update ($\mathbf{C}_t = f_{t}\mathbf{C}_{t-1}+i_{t}\,\mathbf{v}_{t}\mathbf{k}_{t}^{\top}$) works directly on those high‑dimensional vectors.
4. Finally project back down for the residual addition.

**Why pre?**  
Since mLSTM already stores vectors in a $d\times d$ matrix, giving it *more* dimensions upfront lets each key/value pair occupy a larger subspace; this boosts separability without additional computational overhead because matrix updates are already $O(d^2)$ regardless of surrounding projections.

### 3.3 Speed & Accuracy Tradeoffs

| Design | Memory cost | Parallelism | Typical use case |
|-------|-------------|-------------|------------------|
| Post‑up (sLSTM) | Low (scalar) | Sequential due to hidden–hidden mixing | Small/medium models where revision ability matters |
| Pre‑up (mLSTM)  | Higher ($d^2$ matrix ops) | Fully parallelizable (no hidden mixing) | Large models needing massive capacity & fast inference |

Because mLSTM removes hidden‑hidden connections, its recurrence can be expressed as a parallel scan akin to FlashAttention or GLA—so training/inference scales almost linearly with batch size and sequence length. sLSTM’s mixing yields richer dynamics at a modest penalty (~2× slower on GPU per step), but still far below Transformer’s quadratic attention cost for long contexts.

---

## 4. Putting It All Together – The xLSTM Block

The final *xLSTM block* consists of:

1️⃣ **LayerNorm** – stabilizes training across deep stacks.  
2️⃣ **Projection Layer(s)** – either pre- or post-up depending on cell type (`pre` for mLSTM, `post` for sLSTM).  
3️⃣ **Recurrent Core** – an sLSTM or mLJUnitcell; each core returns its hidden vector $h_{t}$.  
4️⃣ **Feed-Forward Sub-layer** – optional pointwise MLP after projection; kept lightweight since recursion already provides nonlinearity.  
5️⃣ **Skip Connection** – adds the original input back to preserve gradient flow.

All blocks share identical hyperparameters except for projection size $d_{\text{high}}$, which is typically set between 4–8× the base hidden dimension—exactly what modern Transformer feed‐forward networks use.

When stacking many such blocks (`x` = 48 in most experiments), we obtain an *xLSTM architecture* that can be trained at 350 M–1 B parameters while maintaining constant memory per token—unlike self‐attention which grows quadratically with context length.

---

## 5. What Does This Mean in Practice?

### Faster Long Contexts  
On benchmarks like Long Range Arena and extrapolation tests up to 16 k tokens, xLSTMs stay roughly constant in compute time per token, whereas Transformers blow up quadratically after ~2 k tokens.

### Higher Perplexities on Rare Tokens  
The matrix memory of mLSTMs captures richer token statistics; experiments on WikiText‐103 show lower perplexity on low-frequency words compared to vanilla LSTMs or even standard Transformers of similar size.

### Competitive Scaling Laws  
When training on 15 B–300 B tokens from SlimPajama, xLSTMs consistently beat GPT‐style Transformers and recent State Space Models (Mamba, H3) by ~5–10 % perplexity at fixed parameter budgets—a direct result of both exponential gating and enlarged storage capacity.

---

## 6. TL;DR Takeaways  

- **Residual integration:** xLSTMs wrap s/m cells inside pre‐LayerNorm blocks exactly like Transformers do with self-attention.
- **Projection strategy matters:**  
  - *Post-up* after an sLSTM keeps cheap scalar memories while still gaining high‐dimensional expressivity downstream.  
  - *Pre-up* before an mLSTM feeds massive key/value vectors into a matrix memory where they can be stored efficiently.
- **Speed vs capacity:** sLSTMs are slightly slower due to hidden mixing but excel at revising stored information; mLSTMs run fully parallel with quadratic matrix ops but unlock far higher storage.
- **Result:** A model family that scales linearly with sequence length yet rivals—or even surpasses—the performance of current large language models built on Transformers.

If you’re curious about trying them yourself, the authors have released code at https://github.com/NX-AI/xlstm . Happy experimenting!



# Scaling Recurrent Networks to Billions of Parameters: What xLSTM Achieves on Language Modeling Benchmarks

## Introduction  

For decades the Long Short‑Term Memory (LSTM) has been the workhorse of recurrent neural networks. Its constant‑error carousel and gating mechanism solved the vanishing‑gradient problem and powered everything from handwriting synthesis to AlphaStar. Yet when Transformers arrived with parallelizable self‑attention, they quickly eclipsed LSTMs on large‑scale language modeling.  

The **xLSTM** paper asks a simple question: *If we bring the classic LSTM ideas to the scale of modern large language models (LLMs), how will they fare?* By introducing **exponential gating**, a **scalar‑memory variant (sLSTM)** and a **matrix‑memory variant (mLSTM)**, the authors built “xLSTM blocks” that can be stacked just like Transformer layers. In this post we walk through the experimental evidence that shows these extended recurrent units can compete with – and often beat – state‑of‑the‑art Transformers, State‑Space Models (SSMs), and recent RNN hybrids such as RWKV when trained on billions of tokens.

## A quick glance at the new ingredients  

Before diving into numbers, let’s demystify what makes an xLSTM different from a vanilla LSTM:

| Component | Standard LSTM | xLSTM |
|-----------|----------------|-------|
| **Gating activation** | Sigmoid (`σ`) for input/forget gates | Exponential (`exp`) activation (with optional sigmoid fallback) plus a normalizer state `n_t` that keeps the sum of gate products | 
| **Memory shape** | Scalar cell `c_t ∈ ℝ` (or a vector of scalars) | – **sLSTM** retains a scalar cell but adds *memory mixing* across multiple heads/cells <br> – **mLSTM** upgrades the cell to a full matrix `C_t ∈ ℝ^{d×d}` using a covariance update rule `C_t = f_t C_{t-1} + i_t v_t k_t^\top` |
| **Parallelism** | Sequential due to hidden–hidden recurrence | mLSTM removes hidden‑hidden connections → fully parallelizable <br> sLSTM keeps mixing for expressivity but runs slightly slower (≈2× compared to mLSTM) |
| **Stabilization** | None needed beyond clipping | Explicit stabilizer state `m_t` rescales exponentials so numerical overflow never occurs |

These changes give each block more expressive memory updates while keeping the overall recurrence linear in sequence length – a stark contrast to the quadratic cost of self‑attention.

## From toy problems to real language data  

### Synthetic benchmarks  

The authors first validated that exponential gating plus memory mixing truly expands what an RNN can solve:

* **Formal language tasks** such as parity or nested parentheses require *state tracking* – remembering an arbitrary number of past bits. Transformers and SSMs without explicit state mixing stumble here, while both sLSTM‐only (`xLSTM[0:1]`) and mLSTM‐only (`xLSTM[1:0]`) achieve near‑perfect accuracy.
* **Multi‑Query Associative Recall** stresses raw storage capacity. With up to 256 key–value pairs stored over contexts as long as 2048 steps, `xLSTM[1:1]` (mixed s/m blocks) outperforms every non‑Transformer baseline and even rivals full Transformers at comparable parameter budgets.
* **Long Range Arena** tests diverse long‑context abilities (e.g., image classification from sequences). Across all five tasks xLSTMs consistently rank among the top performers, confirming they handle both local dynamics and very distant dependencies.

These controlled experiments set the stage for evaluating real-world language modeling at scale.

### Validation perplexity on 15 B tokens  

All methods were trained on the same SlimPajama subset (**15 billion tokens**) using an auto‑regressive setup with roughly **350 M parameters** (embedding dimension 1024, 24 residual blocks). The lineup included:

* GPT‑3 style Transformer
* Llama
* SSMs (H3, Mamba)
* RNN hybrids (RWKV‑4/5/6, GLA, HGRN/HGRN2)
* Two xLSTM variants:
  * `xLSTM[1:0]` – all blocks are mLSTMs  
  * `xLSTM[7:1]` – seven mLSTMs per eight blocks and one sLSTM

Although exact numbers aren’t printed in the paper’s tables, **Table 1 reports that every xLSTM configuration achieves a lower validation perplexity than every other model** under identical compute budgets. In other words, when you give all models ~350 M parameters and 15 B tokens of data, *the recurrent architecture wins*.

#### Ablation confirms what matters  

A stepwise morphing experiment started from a vanilla LSTM embedded inside modern pre‑LayerNorm residual blocks and progressively added:

1. Post up‑projection block  
2. Exponential gating & normalizer  
3. Matrix memory (`m` instead of scalar)

Each addition shaved off a noticeable chunk of perplexity (see Table 2). The takeaway? Both exponential gating *and* matrix memory are essential; dropping either brings performance back toward standard LSTMs or competing RNNs.

## Scaling up: 300 B tokens and billions of parameters  

To see whether this advantage survives at true LLM scales, the authors trained four model sizes (**125 M**, **350 M**, **760 M**, **1.3 B**) on an order of magnitude more data (**300 billion tokens**). They compared:

| Model | Family |
|-------|--------|
| RWKV‑4 | RNN |
| Llama | Transformer |
| Mamba | State‑Space |
| `xLSTM[1:0]`, `xLSTM[7:1]` | Extended RNN |

### Length extrapolation  

All models were trained with context length 2048 but evaluated up to 16 384 tokens. Plotting perplexity vs. context length reveals:

* Transformers’ perplexity climbs sharply beyond their training window.
* SSMs show moderate degradation.
* Both xLSTMs retain *nearly flat* perplexities even at sixteen times longer contexts, confirming that linear recurrence plus robust memory truly scales with sequence length.

### Downstream reasoning benchmarks  

Beyond raw next‑token prediction the paper reports performance on common‑sense reasoning suites (“LM Eval”). Across almost every task—except ARC where Mamba occasionally edges ahead—both `xLSTM[1:0]` and `xLSTM[7:1]` deliver higher scores than their Transformer or SSM counterparts at every size tier.

### PALOMA domain sweep  

The PALOMA benchmark evaluates next‑token prediction across **571 distinct text domains** ranging from news articles to Reddit subforums. Results are striking:

* `xLSTM[1:0]` beats **Mamba** in **568/571** domains,
* beats **Llama** in **486/571**,  
* beats **RWKV‑4** in **570/571**,

all while maintaining lower overall perplexities than any competing method. This breadth test underscores that improved recurrent memory isn’t just good on average—it generalizes across wildly different linguistic styles.

### Power‑law scaling  

When plotted as validation loss versus model size (keeping data volume fixed at 300 B tokens), all families follow a familiar power law \( \mathrm{Loss}(N)=a N^{-b}+c \). Crucially:

* The exponent \(b\) is nearly identical across families,
* The constant offset \(a\) for xLSTMs is substantially lower than for Transformers or SSMs,
* Consequently an extrapolation predicts that a **10 B‑parameter xLSTM would outperform a comparably sized Transformer by several points of perplexity**, mirroring how current GPT‐style models surpass smaller predecessors.

In short, scaling up doesn’t erode xLSTMs’ advantage; it amplifies it because their fundamental recurrence remains linear while preserving richer memories.

## Practical considerations  

While performance shines, there are engineering trade‐offs:

* **sLSTMs** retain hidden‐to‐hidden mixing → slower than pure parallel mLT​SMs (≈2× slower on GPU).  
* Current CUDA kernels for mLT​SM aren’t yet as optimized as FlashAttention; they’re roughly four times slower but still competitive because matrix updates exploit highly parallel BLAS routines.
* Memory usage grows with matrix dimension \(d\); however experiments show no bottleneck up to context lengths of 16 k – beyond that one may need to increase \(d\) or prune old keys explicitly.
* Proper initialization of forget gates (`f_t`) is important for stability—a detail noted by the authors but easily addressed via standard initialization heuristics.

Overall these constraints are engineering rather than algorithmic roadblocks; future kernel work could close the speed gap further.

## Takeaways  

1. **Revisiting classic recurrence isn’t obsolete** – with exponential gating and expressive memories an LSTM derivative can beat modern Transformers when both are scaled fairly.
2. **Memory capacity matters** – moving from scalar cells to covariance matrices gives recurrent models enough bandwidth to rival attention’s combinatorial storage without quadratic cost.
3. **Linear scaling in sequence length pays off** – unlike self‑attention which blows up quadratically, xLSTMs keep inference cost constant per token while still capturing long‐range structure.
4. **Scaling laws hold** – power‐law fits suggest that larger xLSTMs will continue to outpace similarly sized Transformers and SSMs.
5. **Broad applicability** – successful results across synthetic formal languages, associative recall challenges, long-range arena tasks, massive multilingual corpora (SlimPajama), downstream reasoning benchmarks, and domain‐specific PALOMA suites point toward universal gains for any sequence modeling problem where long context matters.

The “simple question” posed by the authors—how far we can push recurrent networks—has been answered affirmatively: billon‑parameter recurrent architectures are now competitive contenders in the LLM arena. Whether future research will see them replace Transformers in production systems remains open, but it’s clear that “old” ideas like gating still have plenty of life left when refreshed with modern tricks such as exponential gates and matrix memories.

# Why xLSTM Could Be Your Next Choice for Fast, Low‑Memory Text Generation  

*Beyond accuracy*: This post dives into the practical upside of the new **x LSTM** family – constant‑memory inference, linear generation time versus the quadratic slowdown of Transformers, higher throughput at large batch sizes, and the current engineering hurdles you’ll need to clear before taking it into production.

---

## 1️⃣  The status quo: Transformers dominate… but they’re hungry  

Transformer decoders (e.g., GPT‑3, Llama) have become the de‑facto standard for text generation because they achieve top‑of‑the‑line perplexities. Their secret sauce is self‑attention, which lets every token attend to every earlier token with a softmax weight matrix.  

The price you pay is twofold:

| Property | Transformers | Classic LSTMs |
|----------|--------------|---------------|
| **Time per generated token** | *Quadratic* in context length \($O(N)$ attention per step\) | *Linear* \($O(1)$ per step\) |
| **Memory during inference** | Grows with context length (need to store all key/value pairs) | Fixed size state (cell + hidden vectors) |

When you push context lengths past 4–8 k tokens or try to serve many requests in parallel, the quadratic attention becomes a latency killer and RAM consumption balloons—especially on GPUs where each request’s KV cache eats precious VRAM.

Classic LSTMs avoid these issues thanks to their constant‑size hidden state, but decades of research showed they lag behind Transformers on language modeling benchmarks because their original design suffers from three key limitations:

1️⃣ **No way to revise past storage decisions** – once a value is written into the scalar cell it cannot be easily overwritten later.  
2️⃣ **Limited storage capacity** – a single scalar per cell forces aggressive compression, hurting rare‑token prediction.  
3️⃣ **Hidden–hidden recurrence blocks** impede parallel execution on GPUs.

Enter **x LSTM**, a modern rethinking of those old recurrent cells that directly addresses these pain points while keeping the nice linear runtime properties of RNNs.



---

## 2️⃣  What x LSTM actually does  

The authors introduce two concrete extensions built on top of the classic LSTM update  

\[
c_t = f_t\,c_{t-1} + i_t\,z_t,\qquad
h_t = o_t\,\psi(c_t),
\]

but replace the traditional sigmoid gates with **exponential gates** (or optionally sigmoid–exponential hybrids) plus a *normalizer* that tracks how much total “mass” has been accumulated through past forget gates.

### 2️⃣ a Scalar x LSTM (**s** LSTM)

* **Scalar memory \(c_t\)** – still one number per cell.  
* **Normaliser \(n_t\)** accumulates \(\sum i_k \prod_{j>k} f_j\); the hidden output is normalized by \(c_t / n_t\).  
* **Memory mixing** – multiple cells can exchange information through recurrent matrices \(\mathbf{R}\), something classic LSTMs already support but now enriched by exponential gating _and_ head-wise partitioning (multiple independent “heads” that mix only inside themselves).  

The result: an RNN that can *revise* stored information on the fly—critical for tasks such as nearest neighbor search where later items should overwrite earlier ones.



### 2️⃣ b Matrix x LSTM (**m** LSTM)

* **Matrix memory \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\)** replaces the scalar cell completely.  
* Updates follow a **covariance rule** reminiscent of fast weight programmers:
  \[
  \mathbf{C}_t = f_t\,\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t \mathbf{k}_t^\top,
  \]
  where \(\mathbf{k}_t\) (key) and \(\mathbf{v}_t\) (value) are linear projections of the input.
* Retrieval is just a matrix–vector product,
  \[
  \tilde{\mathbf{h}}_t = \frac{\mathbf{C}_t\,\mathbf{q}_t}{\max(|\mathbf{n}_t^\top\mathbf{q}_t|,\;1)},
  \]
  with query \(\mathbf{q}_t\).  

Because there are no hidden–hidden connections, the whole recurrence can be **reformulated as a parallel scan**, akin to FlashAttention’s “gemm‑scan” trick—so each time step still costs only \(O(1)\) wall‑clock time despite using a dense \(d\times d\) accumulator.

### 2️⃣ c x LSTM blocks & architecture  

Both variants slot into two types of residual blocks:

* **Post up‑projection block** (used for s LSTM): nonlinearity first, then a high‑dimensional expansion / contraction—mirroring what Transformer feed‑forward layers do.
* **Pre up‑projection block** (used for m LSTM): expand first, apply nonlinearity while data lives in the high‑dimensional space—ideal when you already have an enlarged matrix memory.

Stacking these blocks with pre‑LayerNorm yields full “x LSTM architectures” that look just like today’s deep language models (many residual layers), except every layer carries an efficient recurrent core instead of an attention head.



---

## 3️⃣  The real‐world upside you care about  

### 📉 Constant‑memory inference  

During generation you never need to keep an expanding key/value cache. The model’s entire state fits into:

* one vector (\(c_t,\ h_t,\ n_t\)) per s LSTM head,
* plus one dense matrix (\(\mathbf{C}_t\)) per m LSTM head,

regardless of whether you are generating 128 tokens or 16 k tokens long sequences. This translates directly into lower VRAM pressure—perfect for edge devices or serving many concurrent sessions on a single GPU.



### ⏱️ Linear generation time  

Each output token incurs *the same amount of work*: computing gates, updating \(c_t\)/\(\mathbf{C}_t\), normalising, and emitting \(h_t\). No quadratic softmax over past tokens comes into play. In the authors’ benchmark on a 1.3B‑parameter model:

| Model | Context length → Generation time per token |
|------|------------------------------------------|
| Llama (Transformer) | grows roughly linearly with context → e.g., ~5× slower from 2k → 16k |
| x LSTM (both variants) | flat line → essentially unchanged across lengths |

The plot in Figure ? shows exactly this flat line versus Llama’s steep incline.



### 🚀 Higher throughput at large batch sizes  

Because VRAM isn’t hogged by KV caches, you can push much larger batch sizes through the same GPU before hitting out‑of‑memory errors. In decoding throughput experiments:

* At batch size 8 & prefill 16 tokens, **x LSTM reaches ~2× higher token/sec** than Llama.
* Scaling up the batch further widens the gap—while Transformer throughput plateaus early due to cache writes/reads, x LSTM scales almost linearly until compute saturation hits.


### 📊 Competitive accuracy – no compromise  

Training on just **15 B tokens** from SlimPajama showed x LSTMs beating all baselines—including GPT‐3 size Transformers—on validation perplexity. Scaling up to **300 B tokens** kept this lead across numerous downstream tasks (reasoning benchmarks, PALOMA domain set). So you get speed/efficiency *and* strong language modeling performance.



---

## 4️⃣  What still holds your model back today?  

| Issue | Why it matters | Current status |
|-------|----------------|----------------|
| **Non‑parallel s LSTM steps** | Hidden–hidden recurrence forces sequential scan → slower GPU usage | A custom CUDA kernel runs ~2× slower than fully parallel m LSTM |
| **Heavy matrix ops in m LSTM** | Updating/retrieving a \(d\times d\) matrix costs \(O(d^2)\) flops per step | Existing kernels are ~4× slower than FlashAttention’s optimized scan |
| **Forget‐gate initialization sensitivity** | Bad initial decay can collapse learning or overflow exponentials | Needs careful bias setting or warmup schedule |
| **Context limits for matrix capacity** | Very long sequences (>16k tokens) may saturate “capacity” of \(\mathbf{C}\) if keys keep piling up | Empirically fine up to ~16k; theoretical analysis pending |
| **Mixed precision stability** | Exponential gates can explode → need stabilizer state \(m_t\); half precision sometimes unstable | Stabilizer works but adds extra ops; further FP16/TensorFloat32 tuning required |
| **Hyperparameter search unexhausted** | Current experiments use default heads/cell counts → room for more efficient configs | Future work includes systematic sweep over head count & depth |

None of these are showstoppers—they’re engineering challenges rather than fundamental algorithmic flaws.



---

## 5️⃣  Engineering roadmap toward production readiness  

Below is a practical checklist for teams who want an x LSTM-backed service today and plan to iterate:

1️⃣ **FlashAttention‐style kernel for m LSTM**
   * Fuse projection → key/value creation → outer product update → scan into a single custom kernel.
   * Exploit shared memory tiling so each thread block processes a chunk of rows/cols of \(\mathbf{C}\).
   * Expected speedup: bring wall‐clock cost down from ~4× to ≈1× transformer flash attention baseline.

2️⃣ **Optimized scan kernel for s LSTM**
   * Use warp‐level primitives (`__shfl_xor`) instead of naïve device launches.
   * Pack multiple heads into one vectorized operation to amortize launch overhead.
   * Goal: cut current ~2× slowdown in half while preserving exact semantics.

3️⃣ **Robust mixed‐precision pipeline**
   * Keep stabilizer term \(m_t\) in FP32 while casting everything else down to FP16/BF16.
   * Add dynamic loss scaling specifically tuned for exponential gate magnitudes.
   * Validate that perplexities stay within <0.5% of FP32 baseline on benchmark suites.

4️⃣ **Adaptive forget bias schedule**
   * Start forget gates near identity (\(f=0.99\)) then gradually anneal toward learned values.
   * Optionally learn separate bias terms per head/memory cell using a warmup horizon (first few hundred thousand steps).

5️⃣ **Quantization aware training**
   * Since inference will often run on edge CPUs/NPUs where INT8 is common, introduce fake quantization nodes around gate activations during training.
   * Verify low drop (<5%) in next-token accuracy after post-training integer conversion.

6️⃣ **Distributed checkpointing & pipeline parallelism**
   * Because each layer still holds big matrices (\(d\times d\)), sharding across GPUs is natural.
   * Implement ZeRO‐style optimizer partitioning so that parameter storage scales linearly with model size—not with sequence length as in Transformer KV caches.

7️⃣ **Integration hooks**
   * Provide a `torch.nn.Module` wrapper exposing `.generate()` similar to HuggingFace `generate`.
   * Offer optional KV cache “emulation” mode where user can ask WGRU-style caching if they want hybrid approaches—but default stays cache‑free.


If you prioritize any subset—for example an ultra–low latency chatbot that runs on a single A100—you could start by deploying an m LSTM backbone with off‑the­-shelf kernels while waiting on kernel improvements.



---

## 6️⃣  TL;DR – Should you replace Transformers with x LSTMs?  

*If your primary bottleneck is inference latency or VRAM consumption—even at modest model sizes—x LSTMs give you:**  
- ✅ Constant memory footprints regardless of context length  
- ✅ Linear generation time → predictable latency even at >10k tokens  
- ✅ Higher decoding throughput when batching many users together  
- ✅ Competitive perplexity after scaling training data  

*You’ll still need:*  
- Better CUDA kernels (especially for s LSTMs)  
- Careful handling of exponential gates via stabilizers or bias schedules  
- Some engineering effort around mixed precision & quantization  

Assuming those engineering tickets get closed—which looks very doable given existing open source efforts—the next wave of production chatbots or edge language assistants could very well run on ***x → fast → tiny*** recurrent cores instead of heavyweight Transformer decoders.
