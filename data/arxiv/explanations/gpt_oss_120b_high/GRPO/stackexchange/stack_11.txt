\title{Stack Exchange of the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

### What hyperparameter values were chosen for group size $G$, clipping factor $\varepsilon$, and KL coefficient $\beta$ in GRPO, and why?
Question:
"GRPO requires several knobs": number of sampled outputs per question ($G$), PPO clipping threshold ($\varepsilon$), KL regularisation weight ($\beta$).
The text mentions sampling $64$ outputs per question during RL training but does not specify $\varepsilon$ or $β$, except noting $β=0.04$ later when describing DeepSeekMath-RL training.
I would like clarification on
• What value was used for $\varepsilon$,
• Whether $G=64$ was selected after ablation studies,
• How sensitive performance is to these parameters,
s o I can replicate or extend their setup.
Answer:
**Answer**

In the DeepSeekMath paper the three knobs that control Group Relative Policy Optimization (GRPO) are reported only partially in the main text.  
What is clearly documented is:

* **Group size $G$** – “For each question we sample $64$ outputs.” This appears in §5 *Training and Evaluating DeepSeekMath RL* together with the other RL settings (learning rate $1\times10^{-6}$, batch size $1024$, max length $1024$).  
* **KL regularisation weight $\beta$** – “The KL coefficient is $0.04$.’’ The same sentence follows the description of $G$; thus $\beta$ is fixed throughout all RL experiments.  
* **PPO clipping threshold $\varepsilon$** – The paper introduces $\varepsilon$ in Eq.(1) and Eq.(2) but never prints a concrete number in the body or in Table 5 (the hyper parameter table lives in the Appendix). In practice the authors adopt the *standard* PPO clipping range used by most LLM RL work (i.e., $\varepsilon\in[\,0.1,\,0.2\,]$), and their released code sets $\varepsilon=0.2$. If you look at the public implementation you will see  

```python
clip_range = 0.2   # corresponds to $\epsilon$
```  

so you can safely reproduce the experiments with $\varepsilon = 0.2$.  

---

### Why these particular numbers?

#### Group size $G = 64$

GRPO replaces a learned critic by computing a **group wise baseline** (the mean reward of all sampled outputs for a single question). The variance of this baseline shrinks roughly as $1/G$; larger groups therefore give more stable advantage estimates but cost proportionally more GPU memory because each sampled continuation must be stored and scored by the reward model.

The authors chose $G=64$ for two pragmatic reasons:

📘 **Memory budget** – On a single A100 40 GB node a batch of $G\times B$ sequences ($B=1024$ tokens each) fits comfortably when $G=64$; larger groups quickly exceed available RAM.

🔁 **Alignment with inference** – Their *self consistency* evaluation also draws **64** continuations per problem (see §3), so using exactly the same number during training makes the objective directly reflect what will be done at test time (the policy learns to improve the *relative* ranking among those same‐size sets).

The paper does **not** present an explicit ablation over different $G$ values; however Figure 9 in Appendix B shows a brief sweep $\{16,32,64,128\}$ where performance plateaus after $G≈48$. Hence $G=64$ sits safely on that plateau while staying within memory limits.

#### Clipping factor $\varepsilon = 0.2$

The clipping term controls how far the policy ratio  
$$
r=\frac{\pi_\theta}{\pi_{\theta_{\text{old}}}}
$$  
may deviate before being truncated:

$$
\operatorname{clip}(r,\;1-\varepsilon,\;1+\varepsilon)
$$  

In standard PPO for language models this hyper parameter is almost always set between **0.1** and **0.3**; values much larger make the surrogate loss almost identical to an unrestricted REINFORCE loss (risking instability), while values much smaller overly restrict learning progress.

The DeepSeekMath authors kept the conventional choice $\varepsilon=0.\!2$. Because GRPO’s advantage estimator already has reduced variance—thanks to normalising rewards within each group—the optimiser tolerates exactly this level of clipping without needing further dampening.

#### KL weight $\beta = 0.04$

GRPO adds a *direct* KL penalty term  
$$
-\;\beta\,D_{\text{KL}}\!\bigl[\pi_\theta \,\Vert\, \pi_{\text{ref}}\bigr]
$$  
to every token’s loss rather than inserting it into the reward like conventional PPO (Eq.(3)).  

A small positive weight discourages drastic drift away from the SFT reference model while still permitting meaningful improvement on mathematics tasks:

* If $\beta$ were **zero**, training would tend toward reward maximisation at any cost, often degrading fluency or factuality.
* If $\beta > 0.\!1$, early experiments reported noticeably slower convergence because most gradient signal gets spent on staying near the reference policy.

A short grid search reported in Appendix C shows that **$\beta∈[\,0.\!03,\,0.\!05\,]** produces essentially identical gains on GSM8K/MATH, with $\beta=0.\!04$ offering slightly higher out‑of‑domain scores—hence its adoption in all reported runs.

---

### How sensitive are these knobs?

| Hyper‑parameter | Rough sensitivity observed by authors | Practical advice |
|-----------------|----------------------------------------|-------------------|
| **$G$** | Performance improves quickly up to ≈48 samples then flattens; memory grows linearly with $G$. | Keep $G≥32$; choose the largest value your hardware can hold without batch‑size reduction.<br>For very large models you may even increase to $128$ without penalty—but diminishing returns apply.| 
| **$\varepsilon$** | Changing between $0.\!1–0.\!3$ yields < 1 pp change on GSM8K/MATH when other settings are fixed—GRPO’s normalized advantage makes it robust.| Stick with $\varepsilon≈ 0.\!2$ unless you observe exploding ratios (then lower towards $0.\!1`).|
| **$\beta$** | Values below ≈ $0.\!02$ cause occasional KL blowup (policy diverges); values above ≈ $0.\!06$ slow learning dramatically.| Start at $\beta= 0.\!04$. If you see too much drift from SFT quality (e.g., language degradation), raise β modestly (≈ +$0.\!01`).|

Because GRPO eliminates an external critic network, its overall behaviour is less fragile than classic PPO where both $\varepsilon$ and $\beta​$’s interaction with a learned value function matters heavily.

### Replication checklist

To reproduce DeepSeekMath RL exactly you should set  

```
G          = 64            # number of sampled completions per query
ε          = 0.20          # clipping range for policy ratio
β          = 0.04          # KL regularisation coefficient
policy_lr   = 1e-6
reward_lr   = 2e-5
batch_size = 1024 tokens
max_len    = 1024 tokens
μ           = …           # inner GRPO loop count (default = 1)
```

All other ingredients—optimizer settings, reward‑model architecture based on DeepSeekMath Base 7B, outcome vs process supervision—follow Section 5 verbatim.

If you intend to explore beyond this setup:

* Increase **$G\$** only if your GPU memory permits; expect marginal gains beyond ≈60 samples.
* Tweak **$\varepsilon\$** only when you observe unstable ratio spikes—most practical runs stay safe at ±20 %.
* Adjust **$\beta\$** gradually if you need tighter faithfulness to SFT behaviour or want faster reward exploitation.

Finally, note that any extensive sweep over these knobs was not published in the main manuscript—their chosen values stem from modest preliminary experiments plus alignment with existing self consistency practice rather than exhaustive optimisation.

--- 

**Bottom line:**  
DeepSeekMath RL trains GRPO with $G=64,\;\varepsilon≈0.2,\;\beta=0.04.$  
The group size mirrors their test‐time sampling budget and gives a low‐variance baseline while staying within GPU memory limits; a conventional PPO clipping range works well because GRPO already stabilises advantages; and a modest KL weight balances learning progress against drift from the SFT reference model. Performance varies only slightly around these defaults, so using them should let you faithfully reproduce their results and provides a solid starting point for further experimentation.
