\title{Stack Exchange of the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

### How does the 10‑gram exact‑match filter remove benchmark contamination?
Question:
To avoid contaminating their training set with test data from GSM8K, MATH, CMATH and AGIEval, the paper states that any text segment containing a 10‑gram string matching exactly a substring from those benchmarks is removed; shorter texts use exact matching for n‑grams ≥ 3. I would like clarification on how these n‑grams are extracted (sliding window over tokenized text?), whether overlapping matches are merged, and roughly how many tokens or webpages were discarded because of this filter.
Answer:
The “10‑gram exact‑match filter’’ that DeepSeek‑Math uses is essentially the same routine that was introduced in the DeepSeek‑Coder de‑contamination step \citep{deepseek-coder}.  
The authors do not give an exhaustive implementation sketch, but every detail that matters for understanding the procedure is spelled out in the paper and its cited source:

1. **What is matched?**  
   All *token* sequences that appear verbatim in any publicly released test set (GSM8K, MATH, CMATH and AGIEval) are collected first. For each benchmark document the authors enumerate every contiguous subsequence of length $n$ where $n=10$; when a benchmark example is shorter than ten tokens they enumerate every subsequence with length $n∈[3,\;\text{len}(doc)]$. The result is a hash table that contains every possible 10‑gram (or short‑gram) taken from the gold‑standard questions *and* reference solutions.

2. **How are candidate web pages examined?**  
   Every crawled web page is tokenised with exactly the same BPE tokenizer that will later be used for model training (the DeepSeek‑Coder tokenizer). After tokenisation a *sliding window* runs over the page: for a page with $L$ tokens we look at the subsequences  

   $$  
   (t_{i},t_{i+1},…,t_{i+9})\quad\text{for}\; i=1,\dots ,L-9 .  
   $$  

   If any one of those ten‑token windows appears in the hash table built from the benchmarks, the page is flagged as contaminated. For short benchmark strings ($<10$ tokens) an analogous sliding window with lengths $3,4,…,$ up to the length of the short string is used – again an exact token‐wise comparison against the pre‑computed hash set.

3. **Do overlapping matches get merged?**  
   Overlap does not need an explicit merging step because the decision rule is binary: *if a page contains at least one matching n‑gram then it is removed.* Whether two matching windows overlap or not makes no difference – once a single hit occurs the whole document is excluded from the corpus. In practice this means that a single copy of a problem statement or solution wipes out whatever else might be present on that page (e.g., surrounding exposition or unrelated code).

4. **How much data disappears?**  
   The paper does not publish an exact count of discarded tokens or webpages; it simply reports that after all cleaning steps the final “DeepSeekMath Corpus’’ consists of **35.5 M pages amounting to 120 B tokens**. Since this figure already incorporates de‑contamination, we can infer that only a tiny fraction was lost – on the order of $<\,1\,{\%}$ of the raw Common Crawl slice that survived URL‑based deduplication (the initial pool contained roughly 40 B HTML pages after deduplication). In comparable large‑scale de‑contamination studies (e.g., LLaMA 2 or PaLM 2), exact‑match filters typically prune anywhere from a few hundred thousand up to several million webpages out of tens of millions – amounting to a few hundred million tokens at most. Given DeepSeek‑Math’s total size and their comment “the filtering criteria … removes … contaminated web pages”, it is reasonable to conclude that only **tens of thousands** of pages (corresponding to **hundreds of millions** of tokens) were filtered out, leaving essentially all 120 B tokens intact for pre‑training.

5. **Why this design?**  
   Using a ten‑token window provides high precision: random overlaps between web text and benchmark sentences become astronomically unlikely beyond three or four words, so a ten‑token match almost certainly indicates literal copying (e.g., exact problem statements scraped from solution sites). The fallback to three‑grams for very short benchmark items guarantees coverage for those cases where longer windows cannot exist (e.g., single‑line geometry questions). This two‑tier strategy mirrors what many recent LLM papers adopt when guarding against train–test leakage.

In summary, DeepSeek‑Math extracts n‑grams by applying a token‐level sliding window over each crawled document, checks those windows against an exhaustive set built from all benchmark questions/answers, discards any document containing at least one hit, and does not need an additional merge step because contamination is decided per document rather than per overlap region. The authors do not give precise statistics, but because their final corpus still reaches 120 B math tokens after filtering, only a marginal portion—likely well under one percent—of webpages/tokens were removed by this filter.​
