\title{Blogs about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

# From Code to Calculus: Why Starting with a Coder Model Supercharges Math Reasoning  

Mathematical reasoning has long been a stumbling block for open‑source large language models (LLMs). While closed‑source giants such as GPT‑4 or Gemini‑Ultra dominate the leaderboard, recent work on **DeepSeekMath** shows that a modest $7$ B‑parameter model can close the gap—*if you start from a coder‑oriented foundation*.  

In this post we unpack the surprising boost that **pre‑training on source code** gives to pure math problem solving. We walk through the experiments that compare a “code‑first” pipeline against a generic language pipeline, discuss why algorithmic thinking transfers into step‑by‑step reasoning, and illustrate how this foundation powers both **self‑contained** solutions and **tool‑assisted** calculations.

---

## 1. The Core Idea: Build Math on Top of Code  

DeepSeekMath‑Base $7$B is initialized from **DeepSeek‑Coder‑Base‑v1.5 $7$B**, a model already trained extensively on programming data (GitHub repositories, code snippets, etc.). The authors then continue pre‑training on a *massive* math corpus—**$120$ B** tokens harvested from Common Crawl—while still blending in natural language and coding data.  

Why does this matter?  

- **Code training forces deterministic, stepwise generation.** Writing correct code requires adhering to precise syntax, managing variables consistently, and ordering operations logically—exactly the discipline needed for rigorous mathematical proofs or chain‑of‑thought solutions.  
- **Programming habits give models a ready “toolbox.”** A model that already knows how to emit executable Python (e.g., using `math` or `sympy`) can more easily adopt *Program‑of‑Thought* (PoT) prompting where it writes a short script then executes it for the final answer.  

---

## 2. Experimental Setup: Code vs. General Pre‑Training  

The authors performed four controlled training regimes on a $1.3$ B base model (DeepSeek‑LLM $1.3$B) before scaling up:

| Regime | First Phase (Tokens) | Second Phase (Tokens) | Goal |
|--------|----------------------|-----------------------|------|
| **Code → Math** | $400\,$B *code* tokens | $150\,$B *math* tokens | Test if code pretraining helps later math learning |
| **General → Math** | $400\,$B *general* language tokens | $150\,$B *math* tokens | Baseline without code exposure |
| **Pure Math** | — | $150\,$B *math* tokens only | Pure math pretraining |
| **Mixed Code+Math** | $400\,$B *code* + $150\,$B *math* mixed in one stage | — | Examine if simultaneous exposure avoids catastrophic forgetting |

All phases used identical optimization settings (AdamW, batch size ≈ 4 M tokens, context length 4 K) so differences can be attributed purely to data composition.

---

## 3. What the Numbers Tell Us  

While the paper only reports tables for brevity, the narrative highlights clear trends:

### 3.1 Program‑Aided Reasoning Benefits  
- **Two‑stage Code → Math** already outperforms General → Math on *Python‐based* benchmarks such as GSM8K and MATH when models are asked to generate executable scripts.  
- Adding the second math phase yields an additional lift—meaning that **code pretraining gives an early advantage**, which further math exposure amplifies.

### 3.2 Step‑by‑Step Reasoning Improves Even Without Tools  
- After just the initial code phase (no math yet), models show moderate gains on plain chain‑of‑thought (CoT) tasks compared to General → Math equivalents—demonstrating that **algorithmic discipline transfers directly to textual reasoning**.
- The full two‐stage pipeline (code then math) achieves the *best* scores across both CoT and PoT evaluations, surpassing even larger models that lack any coding background.

### 3.3 Mixing Code & Math Mitigates Forgetting  
- When data are mixed in one stage (`400` B code + `150` B math), catastrophic forgetting of coding ability is reduced compared to a naïve two–stage approach where coding performance decays after heavy math fine‐tuning.
- However, at this model scale (`1.3` B), fully mastering both domains simultaneously remains challenging; the two–stage approach still yields higher pure‐math scores.

> **Bottom line:** Starting from a coder model consistently beats starting from a generic language model—both when we later specialize in mathematics and when we want the model to retain its coding chops.

---

## 4. Why Does “Code First” Translate Into Better Math?  

### 4.1 Structured Generation Mirrors Logical Proofs  
When you write a function:
```python
def solve(a,b):
    return a + b
```
the model must keep track of variable names (`a`, `b`), maintain correct indentation, and guarantee that each line contributes toward a correct output. This mirrors how one constructs a proof:
1️⃣ Declare symbols  
2️⃣ Apply definitions or lemmas  
3️⃣ Derive intermediate results  

The internal representation learned during code training therefore aligns naturally with *stepwise logical inference*, making it easier for the LLM to emit coherent CoT explanations.

### 4.2 Familiarity With Numerical APIs Reduces “Tool Friction”  
A coder model already knows how to call `math.sqrt`, manipulate `sympy` expressions, or loop over ranges—actions essential for solving many quantitative problems that would otherwise require cumbersome manual arithmetic in plain text. Consequently:
- Prompted with PoT instructions (“solve using Python”), the model produces syntactically correct scripts almost out of the box.
- The downstream execution engine returns accurate numerical answers, feeding back into self‑consistency methods that boost performance further (e.g., self-consistency raises DeepSeekMath’s MATH score from ≈ 51% → 60%).

### 4? Extra Bonus: Transfer To General Reasoning  
The paper observes that **math pretraining also lifts MMLU and BBH scores**, suggesting that algorithmic fluency learned from coding spills over into broader reasoning tasks—not just arithmetic but logical deduction across domains.

---

## 5. Putting It All Together: A Simple Recipe  

If you’re building an open‐source math LLM today, consider this three‑step pipeline:

1️⃣ **Start From A Strong Coder Base** – Choose an existing code‐focused LLM (e.g., DeepSeek‑Coder or CodeLlama). Its token-level knowledge about syntax and algorithmic patterns provides a solid scaffold.
2️⃣ **Continue Pretraining On High‑Quality Math Corpus** – Use web‐mined math data (the DeepSeekMath Corpus gives us $120$ B tokens) while retaining some coding token proportion (~10–20%). This “math” phase refines domain knowledge without erasing programming habits.
3️⃣ **Instruction Tune + Light RL** – Fine‐tune on chain‐of‐thought / program‐of‐thought instruction data; optionally apply GRPO reinforcement learning for a final edge (the authors see jumps of ~5% absolute on GSM8K).

Following this recipe yields a $7$ B model that **rivals closed models on competition‐level benchmarks**, all while staying fully open source.

---

## 6. Takeaways  

- **Code pretraining ≠ just better at coding; it’s a catalyst for mathematical thinking** because both tasks demand disciplined sequential generation.
- A two–stage “code first → math later” schedule consistently outperforms “general language first → math later,” especially for tool–integrated tasks.
- Mixing code & math can preserve coding ability but may slightly compromise pure mathematical depth at current scales; future research may explore larger models or curriculum strategies.
- The synergy between code and math extends beyond arithmetic—it improves general reasoning benchmarks too, hinting at deeper representational benefits.

In short, if you want your next open-source LLM to excel at calculus as well as at compiling C++, give it plenty of *code* before you feed it equations. The path from **coder** to **calculist** looks increasingly short—and remarkably effective. 🚀
