# How to Plug LongRoPE Into Your Own LLaMA or Mistral Model  

*Extend a pre‑trained RoPE‑based LLM from its native ~4 K window to a **2 048 K** context with only ~1 K fine‑tuning steps.*  

---

## TL;DR  

1. **Clone & install** the official LongRoPE repo.  
2. **Prepare** a modest‑size long‑text dataset (≈256 K tokens per chunk) for the first fine‑tuning stage.  
3. **Run** the evolutionary RoPE‑rescaling search twice – once before any fine‑tuning (128 K / 256 K) and once after you’ve fine‑tuned to 256 K (target = 2 048 K).  
4. **Fine‑tune** the model for ~1 000 steps (400 + 600) while injecting the searched scaling factors.  
5. **Optional:** run a second “recovery” search to get separate scaling factors for short windows (≤8 K).  
6. **Inference:** swap the scaling tables on‑the‑fly depending on input length – you get a single checkpoint that works anywhere from 4 K up to 2 048 K tokens.

Below you’ll find each step in detail, together with ready‑to‑run command snippets derived from the LongRoPE paper.

---

## 1️⃣ Prerequisites  

| Item | Recommended |
|------|--------------|
| **GPU** | ≥1× A100 40 GB (for 256 K fine‑tune) – multiple GPUs accelerate training via DeepSpeed or FSDP. |
| **Python** | ≥3.9 |
| **Framework** | PyTorch ≥2.0 |
| **Extras** | FlashAttention / xFormers (optional but strongly advised for >128 K context). |

> **Why these choices?**  
LongRoPE does **not** alter the LLM architecture – it only changes the rotary positional embedding matrix. Consequently you can keep all existing speed‑ups (kv‑cache compression, fused kernels) unchanged; you only need enough memory to hold a longer KV cache during training/inference.

---

## 2️⃣ Clone the LongRoPE Repository  

```bash
git clone https://github.com/microsoft/LongRoPE.git
cd LongRoPE
pip install -e .            # installs longrope + dependencies
```

The repo ships three useful entry points:

| Script | Purpose |
|--------|---------|
| `search_rope.py` | Evolutionary optimization of per‑dimension scaling factors (`λ_i`) and early‑token cutoff (`\hat n`). |
| `finetune_long.py` | Simple trainer that plugs in custom RoPE before running fast‑step SGD on your data. |
| `inference.py` | Demonstrates dynamic switching of scaling tables at runtime. |

All three accept a common config file (`config.yaml`) – see `configs/example_lLaMA2.yaml` for a working baseline on LLaMA‑2 7B.

## 3️⃣ Dataset Prep for the First Fine‑Tuning Stage  

You only need **shorter** long documents (≈256 K tokens). The paper used RedPajama chunks of size 128 K → 256 K; you can follow the same pipeline:

```python
import json
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-2-7b-hf")
MAX_LEN = 256_000                     # target length for fine‑tune
CHUNK_OVERLAP = 0                     # no overlap needed

def chunk_text(text):
    tokens = tokenizer.encode(text)
    chunks = [tokens[i:i+MAX_LEN] for i in range(0, len(tokens), MAX_LEN)]
    return chunks

# Example: building a tiny dataset from public books
with open("books.txt", "r", encoding="utf-8") as f:
    raw = f.read()
chunks = chunk_text(raw)

# Save as JSONL where each line is one token list (already integer IDs)
with open("data/256k_chunks.jsonl", "w") as out:
    for c in chunks:
        out.write(json.dumps({"input_ids": c}) + "\n")
```

*Tips*  

- Keep about **32–64 GB** of shuffled text on disk – enough for ~1 000 training steps at batch size 32 without exhausting GPU memory.  
- The same data can be reused for both the 128 K and 256 K stages—just truncate at runtime.

---

## 4️⃣ Evolutionary Search: From 4 K → 128 K / 256 K  

### What is being searched?  

For each rotary dimension *i* we learn a rescale factor `λ_i`. The angle used in Eq.(2) becomes  

\[
\cos\!\Bigl(\frac{n}{\lambda_i\,\beta^{i}}\Bigr),\qquad
\sin\!\Bigl(\frac{n}{\lambda_i\,\beta^{i}}\Bigr)
\]

If token index `n < \hat n` we leave it untouched (`λ_i = 1`).  
The evolutionary algorithm explores a huge combinatorial space:

- `λ_i ∈ [1.0,\; s·1.25]` with step size `0.01` (`s` = target ratio).  
- `\hat n ∈ {0,1,2,4,8,…,256}` tokens.

### Running the search  

```bash
python -m longrope.search_rope \
    --model meta-llama/Llama-2-7b-hf \
    --target_len 128000 \          # switch to 256000 for second round
    --pop_size 64 \
    --mut_size 16 \
    --cross_size 16 \
    --max_iter 40 \
    --mut_prob 0.3 \
    --samples pg19_val.jsonl      # five short PG19 samples as in paper
```

Outputs:

- `best_lambdas.npy` – vector of length *d/2* containing optimal `λ_i`.  
- `best_n_hat.json` – scalar `\hat n`.  

The script also logs the *perplexity* achieved on your validation samples so you can compare against PI / NTK / YaRN baselines directly.

> **Why evolution?**  
Even with modest hyper‐parameters (`P=64`, `T=40`) the algorithm finds solutions that beat static PI and YaRN by >10 % perplexity on an 8 K test (see Table 1 of the paper). The monotonic constraint (`λ_i ≤ λ_{i+1}`) dramatically cuts down useless evaluations while preserving NTK‐motivated ordering of frequencies.

---

## 5️⃣ Fine‑Tuning with LongRoPE  

Now we inject those factors into LLaMA/Mistral’s rotary module and do a *tiny* amount of training:

```bash
python -m longrope.finetune_long \
    --model meta-llama/Llama-2-7b-hf \
    --train_data data/256k_chunks.jsonl \
    --batch_size 32 \
    --lr 2e-5 \                  # use 1e-6 for Mistral per paper
    --steps 400 \
    --target_len 128000 \
    --rope_scale_file best_lambdas_128k.npy \
    --rope_n_hat best_n_hat_128k.json
```

When the checkpoint finishes, **swap** to the next set of scaling factors:

```bash
python -m longrope.finetune_long \
    --model_path ./ckpt_128k \   # output folder of previous run
    --train_data data/256k_chunks.jsonl \
    --batch_size 32 \
    --lr 2e-5 \
    --steps 600 \
    --target_len 256000 \
    --rope_scale_file best_lambdas_256k.npy \
    --rope_n_hat best_n_hat_256k.json
```

Result: `ckpt_256k` containing an LLM that already *understands* <256 K tokens (the “progressive extension” from Fig. 3 of the paper). No additional data collection is required beyond what we already have—just re‑using those same ~200M tokens works remarkably well thanks to LongRoPE’s better initialization.

---

## 6️⃣ Second Search: Jump From 256 K → 2 048 K  

With the model now comfortable at middle lengths we repeat the evolutionary search **once more**, this time probing extreme lengths:

```bash
python -m longrope.search_rope \
    --model_path ./ckpt_256k \
    --target_len 2048000 \        # two million forty‑eight thousand tokens
    --pop_size 32 \               # smaller pop since space explodes
    --mut_size 8 \
    --cross_size 8 \
    --max_iter 30 \
    --mut_prob 0.3 \
    --samples books3_val.jsonl   # few very long samples (>2M tokens)
```

You’ll obtain `best_lambdas_2048k.npy` & `best_n_hat_2048k.json`. Plug them into any downstream inference script – no extra fine‑tuning needed! This is precisely how LongRoPE achieves an *8×* non‑fine‑tuned jump followed by an *8×* fine‑tuned jump (overall ×512).

---

## 7️⃣ Short‐Context Recovery (Optional but Recommended)  

Empirically—see Table 5 of the paper—the massive stretch makes positions inside *the original* window overly crowded, harming accuracy on standard benchmarks. A quick extra search restores performance:

```bash
python -m longrope.search_rope \
    --model_path ./ckpt_2048k \
    --target_len 8000 \          # or simply use two runs: one @4K and one @8K
    --max_lambda_factor 1.25 \   # limit λ_i ≤ s·1.25 where s ≈2 here
    ...                         # same hyper‑params as before
```

Store these “short” tables (`short_lambdas.npy`, `short_n_hat.json`). At inference time you will dynamically select either:

| Input length ≤ | Scaling table |
|----------------|--------------|
| **8 000** tokens | *short* table |
| > **8 000** tokens | *full* table (`best_lambdas_2048k`) |

## 8️⃣ Inference – Switching On The Fly  

Below is a minimal “plug-and-play” snippet that demonstrates runtime swapping:

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from longrope.rotary import ScaledRotaryEmbedding

# --- load model ---------------------------------------------------------
model_name = "meta-llama/Llama-2-7b-hf"
tokenizer = AutoTokenizer.from_pretrained(model_name)

model = AutoModelForCausalLM.from_pretrained(
        model_name,
        device_map="auto",
        torch_dtype=torch.float16,
)

# --- load scaling tables -------------------------------------------------
full_scale   = torch.from_numpy(np.load("best_lambdas_2048k.npy"))
full_nhat   = json.load(open("best_n_hat_2048k.json"))
short_scale = torch.from_numpy(np.load("short_lambdas.npy"))
short_nhat = json.load(open("short_n_hat.json"))

def apply_rope(scale_vec, nhat):
    """Monkey patch attention layers' rotary embeddings."""
    
    def _new_rotary(self, position_ids):
        # position_ids shape -> [batch, seq_len]
        # compute default angles then multiply by per-dim scale.
        angles = self.compute_angles(position_ids)   # existing method from HF impl.
        scale = scale_vec.unsqueeze(0).unsqueeze(0)   # [1,1,d/2]
        angles = angles / scale                       # Eq.(2)
        if nhat > 0:
            mask = (position_ids >= nhat).float()
            angles = angles * mask + angles.detach() * (1-mask)
        return angles
    
    # replace every attention block's rotary embedder:
    for blk in model.model.layers:
        blk.self_attn.rotary_emb.forward = _new_rotary.__get__(blk.self_attn.rotary_emb)

# -----------------------------------------------------------------------
def generate(prompt: str):
    input_ids = tokenizer(prompt, return_tensors="pt").input_ids.to(model.device)
    
    seq_len = input_ids.shape[1]
    
    if seq_len <= 8000:
        apply_rope(short_scale.to(model.device), short_nhat)
        max_len = seq_len + short_nhat   # ensure KV cache covers both parts.
    else:
        apply_rope(full_scale.to(model.device), full_nhat)
    
    output = model.generate(
        input_ids,
        max_new_tokens=200,
        do_sample=False,
        eos_token_id=tokenizer.eos_token_id,
        pad_token_id=tokenizer.pad_token_id,
        use_cache=True,
        attention_mask=torch.ones_like(input_ids),
        )    
    
    return tokenizer.decode(output[0], skip_special_tokens=True)

# Example:
print(generate("Summarize this novel:\n" + very_long_text))
```

*What happens under the hood?*  
Whenever you call `apply_rope`, we overwrite each layer’s `rotary_emb.forward` method so that future forward passes use our custom scaling factors exactly as described in Eq.(2) of LongRoPE. Because we do this only once per inference batch there is essentially zero overhead compared to native RoPE.

## 🎉 Recap of the Full Pipeline  

| Stage | Action | Typical Settings |
|------|--------|------------------|
| **0** | Clone repo & install deps | ✅ |
| **1** | Prepare ~256 K token chunks | RedPajama / Mistral data |
| **2a** | Evolutionary search @128 K | Pop=64, Iter=40 → `λ_i`, `\hat n` |
| **2b** | Fine‐tune @128 K | LR=2e−5 → 400 steps |
| **3a** | Evolutionary search @256 K | Same hyper‐params |
| **3b** | Fine‐tune @256 K (add’l 600 steps) | Same LR |
| **4a** | Evolutionary search @2 048 K | Pop≈32 → fastest convergence |
| **4b** *(optional)* | Recovery search @4–8 K | Tight λ bound |
| **5**   | Deploy single checkpoint & toggle tables at runtime | See inference snippet |

All three “search” phases take only a few minutes on one A100 when evaluating on five PG19 samples – thanks to their heavy reliance on perplexity rather than full backpropagation.

## 🛠️ Common Pitfalls & How to Fix Them  

| Symptom | Likely Cause | Fix |
|--------|--------------|-----|
| Out‑of‑memory error at ≥512 K during fine-tuning. | KV cache too large for single GPU memory. | Enable FlashAttention (`export FLASH_ATTENTION=True`) or switch to ZeRO Stage 3 via DeepSpeed (`--deepspeed ds_config.json`). |
| Perplexity spikes after extending beyond ~32 K even though you used LongRoPE’s rescaling factors.| You accidentally fed *both* short and full tables simultaneously. Ensure only one call to `apply_rope()` precedes generation.| Use prints/logs inside `apply_rope()` to verify which table is active. |
| Search stagnates at λ_i ≈ s·1.25 across dimensions—no improvement over PI.| Population too small / mutation probability too low.| Raise `pop_size` or increase `mut_prob`. Also check that your validation samples contain enough tokens (> target length). |

## 👀 What’s Next?  

LongRoPE leaves several avenues open for experimentation:

- **Different base θ values:** The original RoPE uses θ=10⁴; tweaking it before searching could push extensions beyond ≈4× without any fine-tuning.
- **Hybrid attention tricks:** Pairing LongRoPE with sparse attention masks (e.g., Blockwise Hierarchical Transformers) may reduce KV memory while preserving ultra-long reasoning.
- **Domain-specific corpora:** The progressive scheme works even if your downstream documents are legal contracts or scientific articles—just ensure those texts appear in your short dataset so periodic attention patterns are learned early on.

---

### 🎉 Wrap Up  

By following this guide you should be able to turn any RoPE-based LLaMA or Mistral checkpoint into a genuinely *multi‑million token* language model—all while keeping hardware demands modest and preserving performance on classic benchmark tasks (<4 K context). The core idea is simple yet powerful: make positional interpolation respect both frequency non-uniformities *(different λ_i)* and token importance *(early tokens left untouched)*, then let an evolutionary procedure discover exactly how much scaling each dimension needs.

Happy coding—and enjoy seeing your LLM remember an entire novel verbatim! 🚀
