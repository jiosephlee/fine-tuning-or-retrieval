Chapter 3: GPU Architecture Fundamentals for High‑Performance Computing  

# Memory hierarchy  

Modern GPUs are built around a deep memory hierarchy whose design reflects a fundamental trade‑off between capacity and bandwidth. At the top of the hierarchy sits **global memory** (often HBM), an off‑chip DRAM pool that is physically large enough to hold all tensors required by a deep‑learning workload—queries $\mathbf{Q}$, keys $\mathbf{K}$, values $\mathbf{V}$, intermediate scores $\mathbf{S}$, etc.—and is reachable by all streaming multiprocessors (SMs). Because every access must traverse the package pinout and board‑level interconnects, global memory has relatively modest bandwidth and high latency compared with on‑chip structures.  

Directly beneath global memory lies an **L2 cache** that sits on the GPU die but remains shared among all SMs. The L2 cache smoothes repeated reads from global memory but still offers less bandwidth than any private storage attached to an individual SM because it must arbitrate among many concurrent requests.  

Every SM contains a privately addressable **shared memory** region (SMEM). This region is physically located inside the silicon of each SM and is organized as a multi‑banked SRAM array capable of delivering up to 128 bytes per clock cycle per SM \citep{luo2024benchmarking}. Consequently, when one converts an algorithm so that it repeatedly reuses data resident in SMEM—as FlashAttention does by tiling $\mathbf{Q}$, $\mathbf{K}$, $\mathbf{V}$ into blocks—memory traffic can be reduced dramatically relative­ly to a design that streams every element directly from global memory.  

At the finest granularity are the **register files** (RMEM) within each SM. A single thread can hold up to 256 scalar registers at any moment, giving these values effectively zero latency access because they never leave the pipeline stage where arithmetic executes. Registers are therefore reserved for transient values such as partial dot‑products or intermediate softmax scalars that must be accessed every cycle by floating‑point units.  

Understanding this ladder—global → L2 → shared → register—reveals why attention kernels that materialize intermediate matrices $\mathbf{S}$ or $\mathbf{P}$ in global memory become bottlenecks: each write incurs a costly round trip through DRAM whereas keeping those matrices alive only inside SMEM or registers eliminates thousands of expensive transactions without sacrificing correctness.



# Thread hierarchy  

The programming model exposed by CUDA maps compute onto several nested logical groups whose sizes are fixed by hardware design:

* **Thread** – the smallest unit of execution that runs its own instruction stream.
* **Warp** – a collection of exactly $32$ threads that execute in lockstep under a single instruction word.
* **Warpgroup** – introduced with NVIDIA’s Hopper microarchitecture, this groups together four consecutive warps ($4\times 32 = 128$ threads). Warpgroups enjoy special coordination capabilities because they share most low‑level resources such as load/store queues and scheduling slots.
* **Cooperative Thread Array (CTA)** – also called a *threadblock*, it comprises one or more warpgroups that are scheduled onto one SM simultaneously.
* **Cluster** – Hopper adds an additional level called a *threadblock cluster*, which aggregates several CTAs within one graphics processing cluster (GPC) so they can cooperate through inter‑CTA synchronisation primitives.
* **Grid** – the top‑level collection of all CTAs launched by a kernel call across the entire GPU device.

Because every CTA resides entirely on a single SM, its constituent warps can freely exchange data through shared memory without incurring inter‑SM traffic. Moreover, SCATTERED launch configurations naturally map batch size ($B$), number of heads ($H$), and query blocks ($\lceil N/B_r\rceil$) onto distinct CTAs so that computation proceeds independently across these dimensions—a strategy leveraged throughout FlashAttention‑3’s design.



# Asynchrony  

A crucial observation about modern GPUs is that many functional units operate **asynchronously**, i.e., they can start work without waiting for preceding instructions to finish fully before issuing new ones. Two units exemplify this property:

1. **Tensor Memory Accelerator (TMA)** – This dedicated engine handles bulk copies between global memory and shared memory without occupying CUDA core pipelines. A thread may issue an asynchronous `tma_load` operation specifying source address in HBM and destination address in SMEM; control returns immediately while TMA streams data behind the scenes.
2. **Tensor Cores** – Exposed via CUDA’s warpgroup-wide matrix‑multiply‑accumulate instruction `WGMMA`, Tensor Cores accept operands directly from shared memory or registers and launch a matrix multiplication (`GEMM`) operation whose completion may span many cycles. Importantly, once `WGMMA` has been dispatched, subsequent non‑Tensor‑Core instructions issued by other warps may execute concurrently because Tensor Core execution proceeds independently.

When combined together inside a single CTA one can overlap **producer** work—loading tiles $\mathbf{K}_j$, $\mathbf{V}_j$, $\mathbf{Q}_i$ into SMEM—with **consumer** work—executing $\mathbf{Q}_i\mathbf{K}_j^\top$ then applying softmax before multiplying by $\mathbf{V}_j$. The overlap hides both data‑movement latency (because TMA runs while previous GEMMs are still computing) and compute latency (because softmax’s relatively low throughput arithmetic runs while later GEMMs execute). This producer–consumer pipeline lies at the heart of FlashAttention‑3’s performance gain over its predecessor.



# Warp specialization  

If all warps within a CTA performed identical duties—loading data *and* performing GEMM—the scheduler would have difficulty allocating sufficient registers and would suffer unnecessary contention for TMA queues versus Tensor Core pipelines. Instead FlashAttention‑3 adopts **warp specialization**, deliberately assigning distinct functional roles:

* **Producer warps** concentrate exclusively on issuing `tma_load` commands for upcoming tiles of $\mathbf{K}$ or $\mathbf{V}$. Because loading requires almost no arithmetic state, producers may release most of their register budget (`setmaxnreg`) back to other warps after initializing their few control variables.
* **Consumer warps** devote themselves solely to matrix multiplications (`WGMMA`), softmax exponentials (`exp`), reductions (`rowmax`, `rowsum`), and accumulation into output tiles $\mathbf{O}_i$. These operations are register hungry—especially when employing pipelined two‑stage GEMM–softmax overlap—and thus benefit from having access to more RMEM.

The specialization yields two practical advantages:
1. **Instruction‐schedule clarity:** The compiler sees long stretches of homogeneous instructions per warpgroup rather than interleaved load/store / arithmetic mixes, allowing better static scheduling decisions.
2. **Resource partitioning:** By invoking NVIDIA’s `setmaxnreg` directive at kernel launch time one can shrink producer warp’s register quota while inflating consumer warp’s quota dynamically, reducing register spilling without sacrificing occupancy.



# Low‑precision formats  

Deep learning has steadily migrated toward narrower floating‑point formats because they cut both storage traffic and arithmetic cost while preserving enough numeric fidelity for training or inference:

* **FP16** (“half” precision) entered GPUs with Pascal (2017). It halves main‑memory traffic relative to single precision yet retains 10 mantissa bits.
* **BF16** appeared on Ampere (2020). It keeps the same exponent width as FP32 (allowing large dynamic range) while truncating mantissa bits further—ideal when most model activations lie near zero.
* **FP8** arrives with Hopper (2022) in two popular encodings; FlashAttention‑3 uses *e4m3*, which allocates $4$ exponent bits and $3$ mantissa bits (\texttt{e4m3}). By targeting native FP8 Tensor Cores one obtains roughly twice the throughput compared with FP16/Tensor Core paths because both multiplier arrays are duplicated internally.

The reduced mantissa inevitably amplifies quantization error—especially when models contain *outlier* features whose magnitude dwarfs typical activations (\citet{dettmers2208llm}, \citet{sun2024massive}). To mitigate this loss FlashAttention‑3 employs two complementary mechanisms described later (§ “Low‑precision with FP8”):

1. **Block quantization**, which scales each tile individually rather than applying one scalar scale globally.
2. **Incoherent processing**, which randomly orthogonalizes $\mathbf{Q}$ and $\mathbf{K}$ before quantization so outlier energy spreads evenly across elements (“Hadamard mixing”).

Both techniques preserve exactness after dequantization because they exploit linearity properties (\(\mathbf M\mathbf M^\top = I\)).



# Hopper specific instructions  

Hopper introduces two pivotal ISA extensions that enable FlashAttention‑3’s aggressive overlap:

* **WGMMA** (`warpgroup matrix multiply accumulate`) executes at warpgroup granularity rather than individual warp scope used previously (`wmma`). A single `WGMMA` instruction launches an entire blockwise GEMM whose operands may live either:
  * In *registers* (`RS` prefix)—useful when one operand remains resident after an earlier multiplication—or
  * In *shared memory* (`SS` prefix)—ideal when loading fresh tiles via TMA.
  
  Crucially `WGMMA` is asynchronous: after issuing it returns control immediately while hardware core begins processing on tensor cores.
  
* ***Layout constraints*** differ between precisions:
   - For FP16/ BF16 operands either “mn-major” layout (contiguous along outer dimension \(M\) or \(N\)) or “k-major” layout (contiguous along inner reduction dimension \(K\)) are accepted.
   - For FP8 only “k-major” layout is permitted due both to hardware routing logic inside Tensor Cores and optimal utilization of their packing units.
  
Because attention requires two consecutive GEMMs—the query–key product producing scores $\mathbf S$, then weighted value aggregation producing outputs $\mathbf O$—FlashAttention‑3 must respect these restrictions carefully when switching between precisions.



# Dynamic register allocation  

A CUDA kernel’s performance hinges upon how efficiently it uses an SM’s finite pool of registers (typically thousands per SM). The `setmaxnreg` directive empowers developers to reconfigure this pool at launch time:

```cuda
nvcc ... -Xptxas -setmaxnreg=<value>
```

When used alongside Warp Specialization,
* Producer warps assign themselves a very modest maximum (`setmaxnreg=16`) because after loading their tile they only store pointers/counters.
* Consumer warps request far larger limits (`setmaxnreg=96` or higher) so they can keep intermediate fragments such as partial dot products `$ \mathbf S_{\text{cur}} $`, scaling factors `$m_i$, `$ \ell_i $`, or temporary exponentiated values `$ \widetilde{\mathbf P}_{i}^{(j)} $` resident entirely in registers throughout an iteration loop.

By reallocating register quota dynamically between producer/consumer groups—not statically fixing it for all threads—the kernel avoids costly spills into shared memory while preserving high occupancy across different block sizes $(B_r,B_c)$. This flexibility becomes especially important when scaling down tile dimensions so that more blocks fit simultaneously into an SM’s shared buffer.



## Bringing it together  

All six concepts described above intertwine compactly within FlashAttention‑3’s forward pass:

1️⃣ A CTA receives one query tile $\mathbf Q_i$ loaded asynchronously by producer warps via TMA into SMEM.\  
2️⃣ Consumer warps immediately launch `WGMMA` (“SS”) on `(Q_i , K_j)` while producer continues loading `(K_{j+1}, V_{j+1})`.  
3️⃣ As soon as `WGMMA` finishes producing score block $\mathbf S_i^{(j)}$, softmax reduction runs using fast special-function units (`exp`). Meanwhile consumers already dispatch another `WGMMA` for `(Q_i , K_{j+1})`.  
4️⃣ When softmax supplies `$ \widetilde{\mathbf P}_{i}^{(j)} $`, consumer warps issue another `WGMMA` (“RS”) multiplying this block with value tile `$V_j$`. All three steps overlap thanks to asynchronous Tensor Core launches.\  
5️⃣ If operating in FP8 mode, before feeding tiles into `WGMMA` producers perform an intra-kernel transpose (`ldmatrix / stmatrix`) so operands meet k-major layout requirements without extra DRAM round trips.\  
6️⃣ Throughout those overlapped phases producers free most registers back via `setmaxnreg`, letting consumers keep extensive temporary state wholly in RMEM.\  

By comprehending each building block—the layered memories, hierarchical threading model, intrinsic asynchrony between TMA & Tensor Cores, split‐role warp specialization, low‐precision pathways within Hopper’s ISA, and dynamic register budgeting—students gain an intuition not merely for how FlashAttention‑3 achieves “1½–2× speedups” but also why classic naïve implementations squander cycles simply by ignoring these hardware realities.
