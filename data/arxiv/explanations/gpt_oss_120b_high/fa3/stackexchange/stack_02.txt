\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### How does the “ping‑pong scheduling” overlap softmax computation with Tensor‑Core GEMMs?
Question:
The authors claim that by using two warp groups alternating roles, softmax (exponential + row‑wise scaling) can be performed while the other warp group is executing a GEMM. 

- What are the exact dependencies that would normally serialize softmax after the first GEMM?
- How does inserting a `bar.sync` instruction break this dependency?
- Is there any risk that numerical results differ because softmax operates on partially computed scores?

I would appreciate a step‑by‑step illustration of one iteration of this ping‑pong scheme.

Answer:
**Answer**

The “ping‑pong” trick used in FlashAttention‑3 is nothing more than a software pipeline that lets two warp‑groups work on different parts of the same attention tile at the same time.  
The key idea is that on Hopper the Tensor‑Core instruction **WGMMA** (the asynchronous matrix‑multiply) starts a GEMM and returns control to the warp immediately – the actual arithmetic continues inside the Tensor Core while the warp can go on issuing other instructions.  The same asynchrony exists for the TMA load that brings \(Q\), \(K\) and \(V\) tiles from HBM into shared memory.  By assigning one warp‑group to be a *producer* (loading tiles) and the other to be a *consumer* (doing the arithmetic), we can keep both units busy most of the time.

Below I first describe which data dependences force a naïve implementation to serialize softmax after the first GEMM, then explain how a ``bar.sync`` barrier together with asynchronous WGMMA breaks those dependences, and finally walk through one iteration of the ping‑pong schedule showing why it does **not** change the numerical result.



--------------------------------------------------------------------

### 1.   Dependencies that force a sequential schedule

In a single‑block attention tile (size \(B_r\times B_c\)) the forward loop consists of three logical steps:

1. **SS‑GEMM** – compute  
   $$  
   S^{(j)} = Q_i\,K_j^{\top}\;\in\;\mathbb{R}^{B_r\times B_c},  
   $$  

2. **Local soft‑max** – from \(S^{(j)}\) obtain  
   $$  
   m_i = \operatorname{rowmax}\!\bigl(S^{(j)}\bigr), \qquad   
   \tilde P^{(j)} = \exp!\bigl(S^{(j)} - m_i\bigr), \qquad   
   \ell_i = 
      {\ell}_i^{\,\text{old}}\,
      e^{\,m_i^{\,\text{old}}-m_i}
      + 
      \operatorname{rowsum}\!\bigl(\tilde P^{(j)}\bigr)\,.  
   $$  

3. **RS‑GEMM** – accumulate the output  
   $$  
   O_i 
      \;\gets\;
      e^{-\,(\,m_i^{\,\text{old}}-m_i\,)}
      O_i 
      + 
      {\widetilde P}_{\,\text{cur}}\;V_j .
   $$  

Because step 2 consumes every element of \(S^{(j)}\) and step 3 consumes every element of~\(\tilde P^{(j)}\), a naïve kernel inserts a **wait** after each WGMMA:

```c++
// SS‑GEMM
WGMMA(Qi, KjT) -> Scur ;  // commit & wait
// soft‑max
softmax(Scur);
```

The ``wait`` guarantees that all multiplications have finished before we read ``Scur``. Consequently no other work can be issued while this waiting takes place – all Tensor‑Core cycles are idle while the elementwise exponential and reduction run on CUDA cores (which are ≈100× slower per FLOP).

--------------------------------------------------------------------

### 2.   How ``bar.sync`` enables overlap

Instead of waiting for **the current** SS‑GEMM to finish before launching **the next** SS‑GEMM, FlashAttention‑3 lets two iterations be *in flight* at once:

* Warp‑group A holds the results of iteration \(j\) (`Scur`) and performs its soft‑max.
* Warp‑group B already issued the SS‑GEMM for iteration \(j+1\)
  $$
  S_{\text{next}} = Q_i\,K_{\,j+1}^{\top},
  $$
  and will only read it after it finishes.

The only true dependency between those two warps is that they must not overwrite each other’s shared–memory tiles (`K_j`, `V_j`). This is enforced by a **stage‑wise circular buffer** protected by a ``bar.sync``.

The barrier works like this:

* After loading a key/value tile into stage~\(s\) of shared memory, the producer warps execute  
  ``bar.sync s`` to announce “stage \(s\) is ready”.
* The consumer warps issue ``bar.wait s`` before reading from stage~\(s\).

The barrier therefore **does not wait for any arithmetic result**, it only guarantees correct memory ordering. Because WGMMA is already asynchronous, once ``WGMMA(Qi,K_{\,j+1}^{T})`` has been issued there is no stall – the warp can immediately go on to execute non‑matrix instructions (the exponential etc.) belonging to iteration \(j\).

In practice this looks like:

```c++
// ---- consumer warpgroup -------------------------------------------------
// Compute SS‑GEMM for block j            <-- already finished earlier
// ----------------------------------------
// Soft‑max on S_cur                      <-- uses fully produced data
// ----------------------------------------
// Issue RS‑GEMM with $\widetilde P_{\textrm{cur}}\!V_{\,j-1}$
//    (asynchronous – do not wait)
// ----------------------------------------
// Issue SS‑GEMM for next block j+1      <-- starts now, overlaps with above
// ----------------------------------------
// bar.wait(s) for K/V tiles j+1          <-- ensure they are loaded
```

Because each warpgroup alternates between “softmax + RS‑GEMM” and “SS‑GEMM + load”, we obtain a **ping–pong** pattern: while A is busy with its elementwise work, B keeps the Tensor Cores occupied with the next matrix multiply; next iteration they swap roles.

--------------------------------------------------------------------

### 3.   No loss of numerical correctness

The only values used by soft‑max are elements of ``Scur``, which are guaranteed to be completely produced before step 2 starts – this guarantee comes from two sources:

1. **WGMMA hazard detection:** even though we do not issue an explicit ``wait``, the hardware records when all lanes have written their partial sums into registers; later reads of those registers cannot proceed until the accumulation finishes.
2. **Program order enforced by ``bar.sync``:** we never start using another key/value tile until its predecessor has been consumed (`bar.wait`).

Thus every row’s maximum \(m_{i}\) is computed from exactly the same numbers as in a fully sequential implementation, and subsequently every exponential receives exactly \(S^{(j)} - m_{i}\). The floating–point rounding behavior therefore matches what would happen if we had performed “SS‑GEMM → wait → softmax → wait → RS‑GEMM” inside one tile, because all arithmetic inside a tile still occurs in a fixed order.

The only possible source of deviation would be if different tiles were processed in a different order across runs, which could change rounding when reductions are performed across tiles rather than within a single tile. FlashAttention‑3’s design keeps reductions **tile local** (`rowmax` and `rowsum` are performed per block), so exchanging tiles does not affect any cross‑tile accumulation – only an overall scaling factor \(L=m+\log(\ell)\) changes at the very end, exactly as in FlashAttention‑2.

Consequently there is no measurable numerical drift; experiments reported in §5 confirm identical FP16 error relative to FlashAttention‑2 and much lower error than naïve kernels.



--------------------------------------------------------------------

### 4.   Step–by–step illustration of one ping–pong iteration

Consider two warp groups ― WG₀ (consumer now) and WG₁ (producer now).  
Assume we are about to process key/value block \(j\). The shared memory contains three stages; stage~\(s=j\bmod s_{\textrm{buf}}\) holds \(K_j,V_j.\)

| Cycle | WG₀ (consumer) | WG₁ (producer) |
|------|----------------|----------------|
| **A** | Wait until ``bar.wait(s)`` confirms \(K_j,V_j\) loaded.<br>Issue ``WGMMA(Q_i , K_j^T)`` → produces $S_{\textrm{cur}}$. *No wait*. | Load next tiles \(K_{\,j+1},V_{\,j+1}\) into stage~\(s+1;\)$ after copy finishes execute ``bar.sync(s+1)`` to publish them. |
| **B** | While hardware completes SS‑GEMM for $S_{\textrm{cur}}$, continue execution.<br>When hardware signals completion, compute ``rowmax(S_cur)`` → update running maximum $m_i$.<br>Compute $\widetilde P_{\textrm{cur}} = \exp(S_{\textrm{cur}} - m_i)$.<br>Update scaling sum $\ell_i$. | Nothing else yet – just waiting for WMMA finish or loading more blocks. |
| **C** | Issue RS‑GEMM ``WGMMA(\widetilde P_{\textrm{cur}}, V_{\,j-1})`` → adds contribution from previous value block.<br>*Again do not wait*. | Issue SS‑GEMM for next block (`WGMMA(Q_i , K_{\,j+1}^{T})`); this runs concurrently with WG₀’s RS‑GEMM because both use disjoint Tensor Core resources via separate warp groups. |
| **D** | After RS‑GEMM finishes, apply diagonal rescaling<br>\(O_i \gets e^{-({m}_{i}^{\,\text{old}}-m_{i})}O_{i}\).<br>Now all work concerning block \(j\) is done; release stage~\(s$: ``bar.sync(s)`` so producer may overwrite it.| When SS‑GEMM for block \(j+1\) finishes, move its result from registers into ``S_cur`` buffer for WG₀’s upcoming soft‐max step (the “next” iteration). |
| **E** | Loop back: treat $S_{\textrm{next}}$ as new ``Scur``, go again at step A with index \(j+1).\ | Continue loading further blocks or finish when all keys/values have been consumed.|

Notice how steps **B–C** are interleaved between two different warp groups: while WG₀ spends cycles evaluating exponentials—a operation whose throughput is tiny compared with Tensor Core matmul—WG₁ already keeps those cores busy on the *following* matrix multiply. The only synchronisation points are those required by shared‐memory discipline (`bar.sync / bar.wait`).  

Because every piece of data needed by an operation has already been produced when that operation begins, there is no point at which a soft‐max works on partially computed scores – hence no deviation from exact attention.



--------------------------------------------------------------------

### Summary

* In a non‐overlapped implementation each iteration must finish SS‐GEMM → wait → full softmax → wait → RS‐GEMM before starting work on the next key/value block.
* On Hopper WGMMA launches an asynchronous matrix multiply; inserting ``bar.sync`` only synchronises memory stages, not arithmetic results.
* By assigning two warp groups opposite roles and letting one launch SS‐GEMM for block \(j+1\) while the other performs softmax/RS‐GEMM for block \(j\), we hide essentially all tensor‐core latency behind cheap elementwise work – this is described as “ping–pong scheduling”.
* Because each softmax operates on a completely materialised score tile (`Scur`) and all barriers guarantee correct ordering of shared–memory accesses, numerical results are identical to those obtained by a strictly serial schedule – experiments confirm bit‐identical FP16 output compared with FlashAttention‑2.



I hope this clarifies how ping–pong scheduling removes an otherwise dominant serialization bottleneck without compromising correctness.)
