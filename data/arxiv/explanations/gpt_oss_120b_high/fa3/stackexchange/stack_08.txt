\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### How does the two‑stage pipeline in Algorithm 3 avoid sequential dependencies between softmax and GEMMs?
Question:
Algorithm 3 shows that after computing $S_{\text{next}} = Q_i K_j^\top$, the kernel immediately launches a second WGMMA for $O_i += \tilde P_{\text{cur}} V_{j-1}$ without waiting for softmax on $S_{\text{next}}$. 

- Which registers/buffers hold intermediate data to allow this overlap?
- What guarantees that data needed by softmax is ready when its turn arrives?
- Are there any corner cases where latency of previous WGMMA could cause incorrect results?

A detailed explanation of data flow across stages would be useful.

Answer:
**Short answer**

Algorithm 3 hides the data–dependency between the first GEMM ($Q\!\cdot\!K^{\top}$) – which produces the scores that feed the soft–max – and the second GEMM ($P\!\cdot\!V$) – which produces the output contribution – by keeping two *register tiles* alive across loop iterations.  
One tile stores the **next score block** $S_{\text{next}}=Q_{i}\,K_{j}^{\top}$ while a second tile stores the **current probability block** $\tilde{P}_{\text{cur}}=\exp\!\bigl(S_{\text{cur}}-m_{i}\bigr)$ (the row–wise–scaled soft–max). The kernel launches both WGMMAs asynchronously, issues a wait only after it has started useful work from the next iteration, and finally synchronises on each token just before the value is consumed by either soft–max or the accumulator update. Because all waits happen *after* at least one independent instruction has been issued, the latency of a WGMMA can be completely hidden as long as there is another block to process; when there is no further block (the last iteration) an explicit epilogue wait guarantees correctness.

Below I detail how the registers/buffers are organised, why the data are ready when needed, and what pathological cases could break the hiding.

---

### 1. Where do the intermediate results live?

The core of Algorithm 3 is a *two–stage pipeline* inside a single warpgroup (the consumer). At each loop step **j** ($\,1 \leq j < T_{c}-1\,)$ it performs  

1\. $S_{\text{next}}=Q_{i}\,K_{j}^{\top}$        *$WGMA_{0}$* – launched **asynchronously**  

2\. $O_{i}\;\leftarrow\;O_{i}+ \tilde{P}_{\text{cur}}\,V_{\,j-1}$ *$WGMA_{1}$* – launched **asynchronously**

Both intermediate tiles are kept **in registers**:

* $S_{\text{next}}$ occupies a register array sized $B_{r}\!\times\! B_{c}$ (the current query block times the next key block).  
* $\tilde{P}_{\text{cur}}$ occupies an identically shaped register array holding $\exp(S_{\text{cur}}-m_{i})$ after row–max subtraction.

Because each thread in a warp works on a fixed sub–tile of these matrices, no shared–memory traffic is needed between iterations – only a *register copy* ($S_{\text{next}}\rightarrow S_{\text{cur}}$) at line 22 moves the freshly computed scores into the slot that will become $S_{\text{cur}}$ on the next pass.

The **circular shared–memory buffer** described in §3.1 supplies fresh key/value tiles ($K_{j},\,V_{j}$) while it is being recycled; it does not store any score or probability data. Its role is only to decouple memory movement from computation.

---

### 2. How does the kernel know that soft–max can start?

After issuing *WGMA$_0$* ($S_{\text{next}}=Q_{i}K_{j}^{\top}$) the code executes  

```c
// line “Commit but do not wait”
wmma.commit_group();
```  

which returns an opaque *completion token*. The next instruction that touches $S_{\text{next}}$ – namely  

```c
// line “Wait for the WGMMA Q·Kᴛ”
wmma.wait_group(token);
```  

appears **after** two other independent actions have been scheduled:

* loading $V_{\,j-1}$ from shared memory,
* launching *WGMA$_1$* ($\tilde{P}_{\text{cur}}\,V_{\,j-1}$).

Thus while Tensor Cores are busy finishing *WGMA$_0*$, CUDA cores are already executing  

* special–function operations for row–wise max/subtraction,
* exponential arithmetic that builds $\tilde{P}_{\text{next}}$,  
* bookkeeping for normalisation factor $\ell_{i}$.

The same pattern follows *WGMA$_1*$: it is also committed without an immediate wait; later, just before its result is added into $O_{i}$, we issue  

```c
wmma.wait_group(token_PV);
```  

Only at those two points does control actually pause – exactly when a consumer thread needs a value produced by an earlier producer WGMA. Because every wait follows at least one full “useful” instruction stream, all latencies are absorbed unless there are fewer than two blocks left to process.

The algorithm therefore guarantees readiness simply by construction:

* The **soft‑max** reads $S_{\text{next}}$ only after an explicit ``wait_group`` , which cannot fire until Tensor Cores have written back those registers.  
* The **output accumulation** reads $\tilde{P}_{\text{cur}}$ only after its own preceding WGMA has signalled completion.

No race condition can arise because both producers and consumers are bound by those tokens.

---

### 3. Could lingering latencies corrupt results?

In theory an extreme latency—for example if a WGMA takes longer than the work scheduled between its launch and its wait—would make later instructions stall, but it would never produce wrong numbers:

* The **data path** itself never proceeds without confirming completion (``wait_group``).  
* The **control flow** ensures that every producer–consumer pair respects this ordering.

What *does* change performance is pipeline occupancy:  

* When there are fewer than two key/value blocks ($T_{c}<2$) there simply isn’t any “next’’ iteration to hide latency; the kernel falls back to a simple serial schedule (the epilogue in lines 30–31 handles this case).  
* When register pressure forces spills into shared memory or local memory, extra traffic can increase overall runtime but still preserves correctness because all loads/stores are still guarded by their respective barriers (``bar.sync`` in §3.1).

Therefore corner cases where “latency could cause incorrect results’’ do not exist under correct compilation; only performance degradation may appear if either  

​    (i) block size makes each WGMA unusually long relative to soft‑max work, or  
​    (ii) extreme resource constraints trigger register spilling.

---

### 4. End‑to‑end data flow

Putting it together, one full loop looks like this:

| Step | Action |
|------|--------|
| 1 | **Load** $K_{j}$ into SMEM → issue WGMA$_0$ producing $S_{\text{next}}$. |
| 2 | **Load** $V_{\,j-1}$ into SMEM → issue WGMA$_1$ using already available $\tilde{P}_{\text{cur}}$. |
| 3 | **Wait** on WGMA$_0$ → execute soft‑max on $S_{\text{next}}$, producing new probability tile $\tilde{P}_{\text{next}}$, updating row max $m_{i}$ and normalisation factor $\ell_{i}$. |
| 4 | **Wait** on WGMA$_1$ → add its product into output accumulator $O_{i}$, apply rescaling by $\exp(m^{\text{old}}_i-m_i)$. |
| 5 | **Swap** pointers/registers so that today’s $S_{\text{next}}$ becomes tomorrow’s $S_{\text{cur}}$, today’s $\tilde{P}_{\text{next}}$ becomes tomorrow’s $\tilde{P}_{\text{cur}}$. |

Because steps 2–4 run in parallel across different hardware units—Tensor Cores for both WGMMAs, CUDA cores for exponential/max/sum—the total wall‑clock time per block approaches that of a single GEMM while preserving exact attention semantics.

---

### TL;DR  

Algorithm 3 uses two per‑warp register tiles ($S_{\text{next}}$ and $\tilde{P}_{\text{cur}}$) to keep score and probability data alive across iterations. Each WGMA is launched with an asynchronous commit token; explicit waits are placed only when that tile is actually needed (soft‑max or output accumulation). This simple producer/consumer token scheme guarantees that every piece of data has finished computing before it is read, while allowing all other work in between to hide its latency. The only situation where we cannot hide latency is when there are fewer than two blocks left to process—the kernel then reverts to a serial tail—but correctness never suffers; only possible idle cycles appear if hardware latency exceeds overlapping work or if register spilling occurs. This is precisely how FlashAttention‑3 removes sequential dependencies between softmax and GEMMs without sacrificing numerical accuracy.
