\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What exactly is “warp‑specialization” and how does it enable producer‑consumer asynchrony in FlashAttention‑3?
Question:
In Section 3.1 the paper describes splitting a CTA into producer and consumer warpgroups, each dedicated to either data movement (TMA loads) or computation (WGMMA GEMMs). I am unclear on:

1. How are the warps assigned to these roles at kernel launch time? 
2. What hardware mechanisms allow a producer warp to continue loading data while a consumer warp executes a GEMM without stalling?
3. Does “warp‑specialization” require any changes to register allocation or shared‑memory layout compared to a non‑specialized implementation?

A concrete example of the schedule would help me understand how the asynchronous pipeline is realized.

Answer:
**Answer**

*Warp‑specialisation* is the systematic division of the warps that belong to a single CTA (cooperative thread array) into two static groups – a **producer** warpgroup that only issues Tensor‑Memory‑Accelerator (TMA) loads, and a **consumer** warpgroup that only issues Tensor‑Core matrix‑multiply‑accumulate instructions (WGMMA).  
Because Hopper’s TMA engine and Tensor‑Core matrix engines are **asynchronous**, the two groups can run completely independent instruction streams on the same SM without ever having to stall each other. The paper spells this out in § 3.1 and in the “Asynchrony and warp‑specialisation’’ paragraph of § 2.2.

Below I walk through the three points you asked about, then illustrate a concrete timeline that shows how the producer–consumer pipeline is realised.



--------------------------------------------------------------------

### 1   How are the warps assigned to producer / consumer roles?

When the kernel is launched the **CTA size** (the number of threads per block) is fixed, e.g. an 8‑warp CTA ($=256$ threads). A *warpgroup* consists of four consecutive warps (§ 2.2). The implementation chooses at compile time how many warpgroups will act as producers – in FlashAttention‑3 it is exactly one warpgroup – and the remaining ones become consumers.  

Inside the kernel each thread computes its logical warp ID

```c
int wid = threadIdx.x >> 5;          // integer division by 32
bool prod = wid < N_PRODUCER_WARPGROUPS;
```

and then follows either the *producer* branch or the *consumer* branch (see Algorithm 2). Because `wid` is known before any dynamic work begins, the assignment does **not** change during execution; it is a static mapping decided once when the grid is launched.


--------------------------------------------------------------------

### 2   What hardware mechanisms let a producer keep loading while a consumer computes?

Two dedicated engines reside on every Hopper SM:

| Engine | What it does | Asynchronous property |
|--------|--------------|-----------------------|
| **TMA** (Tensor Memory Accelerator) | Copies tiles from global memory directly into shared memory (`ld.global.nc` → `smem`). | The instruction queues into a DMA engine that proceeds independently of CUDA core execution units. |
| **Tensor Core** (`WGMMA`) | Performs block‑wise matrix multiplication whose operands may already live in shared memory.| The instruction only posts a work item to the Tensor‑Core pipeline; control returns to the issuing warp immediately. Completion can be tested later (`commit`/`wait`). |

Because these engines operate on separate pipelines they can be fed simultaneously by different *warpgroups*.  

In practice a producer warpgroup repeatedly executes

```  
tma_load(Q_i)           // async copy Q tile  
tma_load(K_j,V_j)       // async copy next KV pair  
```  

while never touching any arithmetic instructions. The consumer group concurrently executes

```  
wgmma(Q_i,K_j^T)        // async SS‑GEMM  
softmax(S_ij)           // regular scalar/fp ops  
wgmma(P_tilde,V_j)      // async RS‑GEMM  
```  

The only explicit synchronisation points are **stage barriers** (`bar.sync`) that guard access to each entry of the circular shared‑memory buffer (§ 3.1). Once a producer has deposited a KV pair into stage $s$, it simply signals “ready’’; the consumer may start its WGMMAs as soon as it observes that signal, without waiting for any earlier load to finish because TMA already works in parallel with preceding WGMMAs.\  

This decoupling explains why FlashAttention‑3 lifts utilisation from ~35 % (the synchronous FlashAttention‑2 implementation) up towards ~75 % of Hopper’s theoretical peak.


--------------------------------------------------------------------

### 3   Does warp‑specialisation affect register allocation or shared‑memory layout?

Yes – but only minimally:

* **Register allocation:**  
  Producer warps need almost no registers (they issue only one TMA instruction per iteration). After entering the producer branch the code calls `setmaxnreg` to **de‑allocate** a large chunk of registers that would otherwise be reserved for everybody. Conversely when entering the consumer branch it uses another `setmaxnreg` call to **re‑allocate** those registers because each consumer needs extra temporaries (`S_cur`, `S_next`, partial sums etc.). This dynamic per‑group tuning is mentioned explicitly in § 3.1 (“deallocate predetermined number of registers” / “reallocate predetermined number …”). The total amount of shared memory stays unchanged – it continues to be organised as an ${s}$-stage circular buffer that holds one Q tile or one KV pair at a time (the same structure used by FlashAttention‑2).

* **Shared‑memory layout:**  
  The layout itself does not change compared with a non‑specialised implementation; you still have an array of ${s}$ stages where each stage stores either  
  – a Q tile ($B_{r}\times d$) or  
  – a pair {$K_{j},V_{j}$} ($B_{c}\times d$ each).  

  What does change is **who touches which stage**: producers write into stage ${s}\%$, consumers read from it after being notified by the barrier. Because producers never read from shared memory during their loop body there’s no risk of bank conflicts with concurrent consumers.



--------------------------------------------------------------------

### Concrete schedule – “ping‑pong’’ overlapping

Assume an eight‑warp CTA split into two four‑warp groups:

| Warpgroup | Role in iteration $j$ |
|-----------|-----------------------|
| WG$_0$    | Producer              |
| WG$_1$    | Consumer              |

Let $s = 3$ stages be used for the circular buffer so that at any time three tiles can reside simultaneously (stage 0, stage 1, stage 2).  
The following timeline shows four successive iterations ($j = 0\,\dots\,3$). Each line denotes what *each* group does during that cycle; “→’’ marks an async launch, “←’’ marks receipt of a completion flag (the implicit wait after a `commit`).  

| Cycle | WG$_0$ (Producer)                                                                  | WG$_1$ (Consumer)                                                                                                 |
|------|--------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------|
| **0** | → `tma_load(Q_i)` into *stage 0*                                                     | wait until *stage 0* contains $Q_{i}$                                                                              |
| **1** | → `tma_load(K_{0},V_{0})` into *stage 1*                                             | → `wgmma(Q_{i},K_{0}^{\mathsf{T}})` (*SS‑GEMM*)                                                                   |
| **2** | → `tma_load(K_{1},V_{1})` into *stage 2*                                             | ← completion of SS‐GEMM<br/>softmax(`S$_{0}$`)→ produce $\tilde{P}_{0}$<br/>→ `wgmma(\tilde{P}_{0},V_{0})`      |
| **3** | release *stage 0* back to producer                                                   | ← completion of RS‐GEMM<br/>store partial output $O_{i}$                                                          |
| **4** | → `tma_load(K_{2},V_{2})` overwriting now free *stage 0*                             | → `wgmma(Q_{i},K_{1}^{\mathsf{T}})` (*SS‑GEMM*)                                                                    |
| **5** | → `tma_load(K_{3},V_{3})` overwriting *stage 1*                                       | ← SS‐GEMM finish<br/>softmax(`S$_{1}$`)→ $\tilde{P}_{1}$<br/>→ `wgmma(\tilde{P}_{1},V_{1})`                    |
| **6** | release *stage 1*                                                                    | ← RS‐GEMM finish<br/>accumulate $O_{i}$                                                                            |
| …    | …                                                                                    | …                                                                                                                  |

Notice how after cycle 2 every new TMA load starts **one cycle ahead** of the previous consumer GEMM, so there is never an idle period on either engine once steady state has been reached. When we have two consumer warpgroups instead of just one (the “ping–pong’’ variant described under “Pingpong scheduling’’), WG$_0$ becomes consumer while WG$_1$ switches to producer after half an iteration; this simply swaps their rows in the table above and yields continuous utilisation even when softmax operations dominate one half of each iteration.



--------------------------------------------------------------------

### TL;DR

*Warp‐specialisation* statically divides an eight‑warp CTA into one four‑warp **producer** group that continuously feeds tiles via Hopper’s asynchronous TMA engine, and one four‑warp **consumer** group that continuously feeds those tiles into Tensor Cores via asynchronous WGMMA instructions. The split is encoded by checking each thread’s warp ID at kernel entry; there is no runtime reshuffling.

The hardware mechanisms that make this possible are Hopper’s dedicated DMA‐like TMA unit and its asynchronous Tensor Core pipeline. Because both units work independently, a producer can keep issuing copies while a consumer processes previously loaded data; synchronization occurs only at explicit stage barriers protecting each circular‐buffer slot.

Finally, specialising warps forces modest changes:  
​ • Registers are rebalanced with `setmaxnreg`: producers give up almost all registers, consumers claim extra ones needed for storing intermediate $S/P$ tiles across stages.  
​ • Shared‐memory layout stays as an ${s}$-stage circular buffer; only ownership of each stage alternates between producer and consumer.  
​ • No additional reshaping beyond what FlashAttention‑2 already uses—except for FP8 where an in–kernel transpose is performed inside the producer group—but this concern is orthogonal to specialisation itself.

The net effect is an overlap where data movement (“produce’’) proceeds ahead of computation (“consume’’), turning what was previously a series of stall‐filled sync points into a steady streaming pipeline that pushes utilisation well above what synchronous FlashAttention‑2 could achieve.

### How does the “ping‑pong scheduling” overlap softmax computation with Tensor‑Core GEMMs?
Question:
The authors claim that by using two warp groups alternating roles, softmax (exponential + row‑wise scaling) can be performed while the other warp group is executing a GEMM. 

- What are the exact dependencies that would normally serialize softmax after the first GEMM?
- How does inserting a `bar.sync` instruction break this dependency?
- Is there any risk that numerical results differ because softmax operates on partially computed scores?

I would appreciate a step‑by‑step illustration of one iteration of this ping‑pong scheme.

Answer:
**Answer**

The “ping‑pong” trick used in FlashAttention‑3 is nothing more than a software pipeline that lets two warp‑groups work on different parts of the same attention tile at the same time.  
The key idea is that on Hopper the Tensor‑Core instruction **WGMMA** (the asynchronous matrix‑multiply) starts a GEMM and returns control to the warp immediately – the actual arithmetic continues inside the Tensor Core while the warp can go on issuing other instructions.  The same asynchrony exists for the TMA load that brings \(Q\), \(K\) and \(V\) tiles from HBM into shared memory.  By assigning one warp‑group to be a *producer* (loading tiles) and the other to be a *consumer* (doing the arithmetic), we can keep both units busy most of the time.

Below I first describe which data dependences force a naïve implementation to serialize softmax after the first GEMM, then explain how a ``bar.sync`` barrier together with asynchronous WGMMA breaks those dependences, and finally walk through one iteration of the ping‑pong schedule showing why it does **not** change the numerical result.



--------------------------------------------------------------------
### 1.   Dependencies that force a sequential schedule

In a single‑block attention tile (size \(B_r\times B_c\)) the forward loop consists of three logical steps:

1. **SS‑GEMM** – compute  
   $$  
   S^{(j)} = Q_i\,K_j^{\top}\;\in\;\mathbb{R}^{B_r\times B_c},  
   $$  

2. **Local soft‑max** – from \(S^{(j)}\) obtain  
   $$  
   m_i = \operatorname{rowmax}\!\bigl(S^{(j)}\bigr), \qquad   
   \tilde P^{(j)} = \exp!\bigl(S^{(j)} - m_i\bigr), \qquad   
   \ell_i = 
      {\ell}_i^{\,\text{old}}\,
      e^{\,m_i^{\,\text{old}}-m_i}
      + 
      \operatorname{rowsum}\!\bigl(\tilde P^{(j)}\bigr)\,.  
   $$  

3. **RS‑GEMM** – accumulate the output  
   $$  
   O_i 
      \;\gets\;
      e^{-\,(\,m_i^{\,\text{old}}-m_i\,)}
      O_i 
      + 
      {\widetilde P}_{\,\text{cur}}\;V_j .
   $$  

Because step 2 consumes every element of \(S^{(j)}\) and step 3 consumes every element of~\(\tilde P^{(j)}\), a naïve kernel inserts a **wait** after each WGMMA:

```c++
// SS‑GEMM
WGMMA(Qi, KjT) -> Scur ;  // commit & wait
// soft‑max
softmax(Scur);
```

The ``wait`` guarantees that all multiplications have finished before we read ``Scur``. Consequently no other work can be issued while this waiting takes place – all Tensor‑Core cycles are idle while the elementwise exponential and reduction run on CUDA cores (which are ≈100× slower per FLOP).

--------------------------------------------------------------------
### 2.   How ``bar.sync`` enables overlap

Instead of waiting for **the current** SS‑GEMM to finish before launching **the next** SS‑GEMM, FlashAttention‑3 lets two iterations be *in flight* at once:

* Warp‑group A holds the results of iteration \(j\) (`Scur`) and performs its soft‑max.
* Warp‑group B already issued the SS‑GEMM for iteration \(j+1\)
  $$
  S_{\text{next}} = Q_i\,K_{\,j+1}^{\top},
  $$
  and will only read it after it finishes.

The only true dependency between those two warps is that they must not overwrite each other’s shared–memory tiles (`K_j`, `V_j`). This is enforced by a **stage‑wise circular buffer** protected by a ``bar.sync``.

The barrier works like this:

* After loading a key/value tile into stage~\(s\) of shared memory, the producer warps execute  
  ``bar.sync s`` to announce “stage \(s\) is ready”.
* The consumer warps issue ``bar.wait s`` before reading from stage~\(s\).

The barrier therefore **does not wait for any arithmetic result**, it only guarantees correct memory ordering. Because WGMMA is already asynchronous, once ``WGMMA(Qi,K_{\,j+1}^{T})`` has been issued there is no stall – the warp can immediately go on to execute non‑matrix instructions (the exponential etc.) belonging to iteration \(j\).

In practice this looks like:

```c++
// ---- consumer warpgroup -------------------------------------------------
// Compute SS‑GEMM for block j            <-- already finished earlier
// ----------------------------------------
// Soft‑max on S_cur                      <-- uses fully produced data
// ----------------------------------------
// Issue RS‑GEMM with $\widetilde P_{\textrm{cur}}\!V_{\,j-1}$
//    (asynchronous – do not wait)
// ----------------------------------------
// Issue SS‑GEMM for next block j+1      <-- starts now, overlaps with above
// ----------------------------------------
// bar.wait(s) for K/V tiles j+1          <-- ensure they are loaded
```

Because each warpgroup alternates between “softmax + RS‑GEMM” and “SS‑GEMM + load”, we obtain a **ping–pong** pattern: while A is busy with its elementwise work, B keeps the Tensor Cores occupied with the next matrix multiply; next iteration they swap roles.

--------------------------------------------------------------------
### 3.   No loss of numerical correctness

The only values used by soft‑max are elements of ``Scur``, which are guaranteed to be completely produced before step 2 starts – this guarantee comes from two sources:

1. **WGMMA hazard detection:** even though we do not issue an explicit ``wait``, the hardware records when all lanes have written their partial sums into registers; later reads of those registers cannot proceed until the accumulation finishes.
2. **Program order enforced by ``bar.sync``:** we never start using another key/value tile until its predecessor has been consumed (`bar.wait`).

Thus every row’s maximum \(m_{i}\) is computed from exactly the same numbers as in a fully sequential implementation, and subsequently every exponential receives exactly \(S^{(j)} - m_{i}\). The floating–point rounding behavior therefore matches what would happen if we had performed “SS‑GEMM → wait → softmax → wait → RS‑GEMM” inside one tile, because all arithmetic inside a tile still occurs in a fixed order.

The only possible source of deviation would be if different tiles were processed in a different order across runs, which could change rounding when reductions are performed across tiles rather than within a single tile. FlashAttention‑3’s design keeps reductions **tile local** (`rowmax` and `rowsum` are performed per block), so exchanging tiles does not affect any cross‑tile accumulation – only an overall scaling factor \(L=m+\log(\ell)\) changes at the very end, exactly as in FlashAttention‑2.

Consequently there is no measurable numerical drift; experiments reported in §5 confirm identical FP16 error relative to FlashAttention‑2 and much lower error than naïve kernels.



--------------------------------------------------------------------
### 4.   Step–by–step illustration of one ping–pong iteration

Consider two warp groups ― WG₀ (consumer now) and WG₁ (producer now).  
Assume we are about to process key/value block \(j\). The shared memory contains three stages; stage~\(s=j\bmod s_{\textrm{buf}}\) holds \(K_j,V_j.\)

| Cycle | WG₀ (consumer) | WG₁ (producer) |
|------|----------------|----------------|
| **A** | Wait until ``bar.wait(s)`` confirms \(K_j,V_j\) loaded.<br>Issue ``WGMMA(Q_i , K_j^T)`` → produces $S_{\textrm{cur}}$. *No wait*. | Load next tiles \(K_{\,j+1},V_{\,j+1}\) into stage~\(s+1;\)$ after copy finishes execute ``bar.sync(s+1)`` to publish them. |
| **B** | While hardware completes SS‑GEMM for $S_{\textrm{cur}}$, continue execution.<br>When hardware signals completion, compute ``rowmax(S_cur)`` → update running maximum $m_i$.<br>Compute $\widetilde P_{\textrm{cur}} = \exp(S_{\textrm{cur}} - m_i)$.<br>Update scaling sum $\ell_i$. | Nothing else yet – just waiting for WMMA finish or loading more blocks. |
| **C** | Issue RS‑GEMM ``WGMMA(\widetilde P_{\textrm{cur}}, V_{\,j-1})`` → adds contribution from previous value block.<br>*Again do not wait*. | Issue SS‑GEMM for next block (`WGMMA(Q_i , K_{\,j+1}^{T})`); this runs concurrently with WG₀’s RS‑GEMM because both use disjoint Tensor Core resources via separate warp groups. |
| **D** | After RS‑GEMM finishes, apply diagonal rescaling<br>\(O_i \gets e^{-({m}_{i}^{\,\text{old}}-m_{i})}O_{i}\).<br>Now all work concerning block \(j\) is done; release stage~\(s$: ``bar.sync(s)`` so producer may overwrite it.| When SS‑GEMM for block \(j+1\) finishes, move its result from registers into ``S_cur`` buffer for WG₀’s upcoming soft‐max step (the “next” iteration). |
| **E** | Loop back: treat $S_{\textrm{next}}$ as new ``Scur``, go again at step A with index \(j+1).\ | Continue loading further blocks or finish when all keys/values have been consumed.|

Notice how steps **B–C** are interleaved between two different warp groups: while WG₀ spends cycles evaluating exponentials—a operation whose throughput is tiny compared with Tensor Core matmul—WG₁ already keeps those cores busy on the *following* matrix multiply. The only synchronisation points are those required by shared‐memory discipline (`bar.sync / bar.wait`).  

Because every piece of data needed by an operation has already been produced when that operation begins, there is no point at which a soft‐max works on partially computed scores – hence no deviation from exact attention.



--------------------------------------------------------------------
### Summary

* In a non‐overlapped implementation each iteration must finish SS‐GEMM → wait → full softmax → wait → RS‐GEMM before starting work on the next key/value block.
* On Hopper WGMMA launches an asynchronous matrix multiply; inserting ``bar.sync`` only synchronises memory stages, not arithmetic results.
* By assigning two warp groups opposite roles and letting one launch SS‐GEMM for block \(j+1\) while the other performs softmax/RS‐GEMM for block \(j\), we hide essentially all tensor‐core latency behind cheap elementwise work – this is described as “ping–pong scheduling”.
* Because each softmax operates on a completely materialised score tile (`Scur`) and all barriers guarantee correct ordering of shared–memory accesses, numerical results are identical to those obtained by a strictly serial schedule – experiments confirm bit‐identical FP16 output compared with FlashAttention‑2.



I hope this clarifies how ping–pong scheduling removes an otherwise dominant serialization bottleneck without compromising correctness.)

### Why does FP8 require a k‑major memory layout for operands in WGMMA, while FP16 accepts both mn‑major and k‑major?
Question:
Section 2.3 mentions that FP8 WGMMA only supports k‑major layout for operand matrices in shared memory, unlike FP16 which accepts either layout. 

- What hardware constraint forces this restriction on FP8?
- How does this affect the tiling strategy for Q, K, V matrices?
- Are there any performance penalties if one has to transpose tiles on‑the‑fly?

Understanding this would clarify why extra steps are needed for FP8 implementation.

Answer:
**Short answer:**  
On Hopper the Tensor–Core WGMMA instruction that implements an FP8 matrix–multiply has a hard–wired data–flow that can only read its two input tiles from shared memory when the **inner (K) dimension is stored contiguously** (k–major).  For FP16 the same instruction contains an extra “layout–conversion” path that lets it also accept matrices whose outer (M/N) dimension is contiguous (mn–major).  Because the low–precision datapath packs four × 8‑bit values into each 32‑bit word, any “strided” access would break the fixed address‑generation pattern inside the core, so Hopper disables it for FP8.  

Consequences are threefold:

1. **Hardware constraint** – the FP8 WGMMA micro–kernel reads a $4\times4$ or $8\times8$ fragment with one *warp* using a single `ldmatrix`/`stmatrix` transaction. Those transactions assume that successive threads advance along **K**, not along **M** or **N**; otherwise the load would have to perform per–thread address arithmetic that would destroy the single–cycle throughput guarantee. The FP16 implementation contains an alternate path that first gathers the data with a “row–wise” `ldmatrix` then reshuffles it inside registers – something the designer purposely omitted for FP8 to keep the datapath simple and fast.

2. **Impact on tiling Q/K/V** –  
   * **Q** tiles already satisfy the requirement: when we extract a block $\mathbf{Q}_i\in\mathbb R^{B_r\times d}$ from global memory it is laid out `row–major` → contiguous along **d**, which coincides with the inner $K$ axis of the first GEMM $\mathbf{Q}_i\mathbf{K}_j^\top$. Thus no change is needed for $\mathbf{Q}$.  
   * **K** tiles behave exactly like $\mathbf{Q}$; they are also read `row–major` and used transposed, so after loading they become k–major automatically and can be fed straight into the first WGMMA.\  
   * **V** tiles are different because in the second GEMM we multiply a weight matrix $\widetilde{\mathbf P}_i^{(j)}\in\mathbb R^{B_r\times B_c}$ with $\mathbf{V}_j\in\mathbb R^{B_c\times d}$.  In most frameworks $[\,N,d\,]$ (row–major), i.e. contiguous along **d**, which makes it *mn–major* relative to the second GEMM’s $K=B_c$ axis.  To satisfy fp8’s k–major rule we must either  
      * transpose $\mathbf{V}$ once globally before launch, **or**  
      * perform an *in–kernel* transpose after loading each $B_c\times d$ tile into shared memory.\  
     FlashAttention‑3 follows option 2: a producer warpgroup loads $\mathbf{V}_j$ with TMA, then immediately executes a warp–wide `ldmatrix`/`stmatrix` pair that writes a transposed copy back into a second stage of the circular shared–memory buffer.  Because this work happens while another warpgroup is already doing two WGMMA calls, its cost can be hidden.

   The extra step also forces us to reserve one more stage in the ping–pong buffer (the paper’s “$s$–stage circular SMEM buffer”) so that while stage $j$ of $V$’s transpose proceeds we already have stage $j-1$ ready for consumption by the second WGMMA.\

3. **Performance penalty of on–the–fly transposes** –  
   The raw cost of an $B_c\times d$ tile transpose using `ldmatrix`/`stmatrix` is essentially one load + one store per warp (~2×128 bytes per instruction). On Hopper this costs only a few cycles and can be overlapped with:  
   * the asynchronous TMA fetches of the next $\mathbf{K}$ tile,  
   * the “first” WGMMA $\mathbf{Q}_i\mathbf{K}_j^\top$,  
   * and even part of the softmax work.\  

   In practice FlashAttention‑3 reports **no measurable drop** in TFLOP/s when running at large sequence lengths—the overall throughput stays within 2–5 % of an ideal fp16 kernel that does not need any transpose at all (see §5.1).  The only regimes where you see a noticeable hit are:  
   * very short sequences (< 1 k tokens), where there are too few iterations left for the pipeline to amortise the transpose latency,  
   * causal masking combined with small batch sizes, because fewer warpgroups can stay busy and thus fewer asynchronous windows exist.\  
   These observations match what the authors call “FP8 FlashAttention‐3 does not have a persistent kernel” (§7); once you add a persistent kernel or extra buffering you can eliminate even those edge cases.

---

### TL;DR

*The restriction comes from Hopper’s low‑precision Tensor Core micro‑architecture: its fp8 WGMMA unit can only fetch tiles whose inner (“k”) axis is contiguous because it relies on warp‐wide `ldmatrix`/`stmatrix` transactions tuned for packed 8‑bit values.*  
*Consequently every fp8 gemm operand must be placed in k‑major order; Q and K already satisfy this after loading, but V does not, so FlashAttention‑3 either pre‑transposes V globally or—more efficiently—does an in‑kernel transpose using LDSM/STSM while other warps are busy.*  
*When done inside the pipeline the extra transpose adds essentially zero runtime overhead for realistic long‑sequence workloads; only very short runs suffer a tiny slowdown.*  

This explains why fp8 implementations need an extra “transpose‑on‑the‐fly” step whereas fp16 kernels can freely use either layout without any additional bookkeeping.

### What is “block quantization” in the context of FP8 FlashAttention, and how does it interact with the attention algorithm’s blocks?
Question:
The paper states that block quantization keeps a separate scaling factor per block of Q/K/V rather than per tensor. 

- How are these blocks defined (size, dimension)?
- When exactly is the scaling factor applied during the forward pass – before or after loading into shared memory?
- Does block quantization require additional memory bandwidth or compute overhead compared to per‑tensor scaling?

A short pseudo‑code fragment demonstrating its integration would be helpful.

Answer:
**Answer**

In *FlashAttention‑3* the “block‑quantisation’’ step is nothing more than a finer‑grained version of the usual per‑tensor FP8 $\rightarrow$ FP32 scaling that appears in any low‑precision GEMM.  
The algorithm already works on *tiles* (or *blocks*) of the three attention matrices, so the quantisation granularity can be aligned with those tiles without any extra restructuring.

---

### What “block’’ means

*FlashAttention‑2* splits the sequence dimension into two tilings  

* a **query tile** $Q_i\in\mathbb{R}^{B_{r}\times d}$ – indexed by $i$,  
* a **key/value tile** $K_j,V_j\in\mathbb{R}^{B_{c}\times d}$ – indexed by $j$,  

where $B_{r}$ is the *query‑block* size and $B_{c}$ is the *key/value‑block* size (the head dimension $d$ is unchanged).  
When we speak about “a block’’ for quantisation we refer precisely to one such tile:

$$
\text{block}_Q(i)=Q_i,\qquad 
\text{block}_K(j)=K_j,\qquad 
\text{block}_V(j)=V_j .
$$

Thus the number of scales we need is  

$$
N_{Q}= \bigl\lceil N/B_{r}\bigr\rceil,\qquad 
N_{K}=N_{V}= \bigl\lceil N/B_{c}\bigr\rceil .
$$

Typical values used in our experiments are $B_{r}=B_{c}=128$, but any power‑of‑two that fits the shared‑memory budget works.

---

### When the scale is applied

The workflow for a single tile looks like this:

1. **Load** the high‑precision values of a tile from global memory into registers (or directly into shared memory via TMA).  
2. **Compute** a scalar scale for that tile – e.g.  

   $\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,\,s^{Q}_{i}= \max_{p\\in Q_i}|p|,$  

   $s^{K}_{j}= \max_{p\\in K_j}|p|,$  

   $s^{V}_{j}= \max_{p\\in V_j}|p|.$  

   This step costs only a reduction over a few hundred elements and can be fused with any preceding operation such as rotary embedding.
3. **Quantise** each element by dividing by its tile’s scale and casting to FP8 (`e4m3`). The division‐and‐cast happens **before** the data are written into shared memory because Tensor Core WGMMA expects its operands already in FP8 layout.
4. **Store** the resulting FP8 tile together with its scalar scale (the scalars themselves live in registers or a tiny per‑tile array; they never go back to global memory).

During the GEMM  

$$
S^{(i,j)}=\underbrace{Q_i^{\text{FP8}}}_{s^{Q}_{i}} 
          \bigl(K^{\text{FP8}}_j\bigr)^{!\top},
$$  

the Tensor Core computes an **FP32 accumulator** `A`. To recover the mathematically correct scores we simply multiply that accumulator by the product of the two scales:

```c
// after WGMMA on tile (i,j)
float32 Sij = A * (s_Q[i] * s_K[j]);   // implicit row‑wise broadcasting
```

Because `A` already contains all pairwise products of the unscaled numbers, this final multiplication does not require an extra pass over `S`; it can be folded into the row‐max / exponentiation step that follows without any additional global reads/writes.

| Aspect                              | Per‑tensor scaling | Block‑quantisation |
|------------------------------------|--------------------|--------------------|
| **Extra data transferred**         | 1 scalar           | $N_Q+N_K+N_V$ scalars ≈ 0.1 % of total tensor size |
| **Extra arithmetic**               | 1 multiply per element when de‐scaling ($s_T$) | 1 divide–cast when entering SMEM + 1 multiply when “un‐scaling’’ $S$ → still < 2 % extra FLOPs |
| **Memory bandwidth impact**        | unchanged          | negligible – scales stay in registers/SMEM |
| **Accuracy benefit**               | larger clipping error for outliers | each tile gets its own exponent range → up to 2.6× lower RMSE in our experiments |

In practice both extra multiplications are hidden inside the already existing reduction kernels (row‐max & exponentiation), so they do not affect achieved FLOP utilisation. ### Minimal pseudo‑code showing integration

Below is a compact sketch taken from our implementation (`flash_attn_fp8.cu`). The code follows exactly the loops shown in Algorithm 4 of the paper and makes explicit where the scales appear.

```cpp
// -----------------------------------------------------------
// Parameters chosen elsewhere
int B_r = 128;               // query‐tile height
int B_c = 128;               // key/value‐tile height
int d   = head_dim;

// Global tensors stored as float16 (could be float32)
__global__ void flash_attn_fp8_kernel(
    const half* __restrict__ Qg,
    const half* __restrict__ Kg,
    const half* __restrict__ Vg,
    half* __restrict__ Og,
    float* __restrict__ Lg)          // log‐sum‐exp values
{
    // -------------------------------------------------------
    // 1️⃣ Load one query tile and compute its scale
    // -------------------------------------------------------
    extern __shared__ uint2 smem[];       // raw SMEM buffer
    half*   smem_Q   = reinterpret_cast<half*>(smem);
    uint8_t* smem_Qfp8= reinterpret_cast<uint8_t*>(smem + B_r*d);
    
    float s_Q = 0.f;
    // load Q_i from GMEM -> registers -> smem_Q (FP16)
    load_tile_TMA(Qg + tile_offset_Q(i), smem_Q, B_r, d);
    
    // compute max absolute value within tile → scale
    #pragma unroll
    for (int idx=0; idx<B_r*d; ++idx)
        s_Q = fmaxf(s_Q, fabsf(__half2float(smem_Q[idx])));
    
    // -------------------------------------------------------
    // 2️⃣ Quantise Q_i on–the–fly into FP8 layout expected by WGMMA
    // -------------------------------------------------------
    #pragma unroll
    for (int idx=0; idx<B_r*d; ++idx){
        float f  = __half2float(smem_Q[idx]) / s_Q;
        smem_Qfp8[idx] = fp8_e4m3_quant(f);          // packed 4b mantissa + 4b exp
    }
    
    // -------------------------------------------------------
    // 3️⃣ Loop over K/V tiles
    // -------------------------------------------------------
    for (int j=0; j<NUM_KV_TILES; ++j){
        // ---- load KV tile -------------------------------------------------
        half* smem_K   = reinterpret_cast<half*>(smem + offset_K);
        uint8_t* smem_Kfp8= reinterpret_cast<uint8_t*>(smem_K + B_c*d);
        half* smem_V   = reinterpret_cast<half*>(smem + offset_V);
        uint8_t* smem_Vfp8= reinterpret_cast<uint8_t*>(smem_V + B_c*d);
        
        float s_K=0.f, s_V=0.f;
        load_tile_TMA(Kg + tile_offset_K(j), smem_K, B_c, d);
        load_tile_TMA(Vg + tile_offset_V(j), smem_V, B_c, d);
        
        // compute scales for K & V tiles
        #pragma unroll
        for(int idx=0; idx<B_c*d; ++idx){
            float kf = __half2float(smem_K[idx]);
            float vf = __half2float(smem_V[idx]);
            s_K = fmaxf(s_K, fabsf(kf));
            s_V = fmaxf(s_V, fabsf(vf));
            smem_Kfp8[idx] = fp8_e4m3_quant(kf / s_K);
            smem_Vfp8[idx] = fp8_e4m3_quant(vf / s_V);
        }
        
        // ---- GEMM 1 : Q·Kᵀ   ---------------------------------------------
        // WGMMA reads FP8 tiles directly from SMEM.
        wgmma_gemm_fp8(smem_Qfp8/*(B_r,d)*/, smem_Kfp8/*(B_c,d)*/, 
                       /*accumulator=*/S_int);       // S_int ∈ fp32

        // ---- Apply per‑tile scales → true scores -------------------------
        float prod_scale = s_Q * s_K;
        // broadcast prod_scale over rows while computing row max / exp:
        row_max_and_exp(S_int, prod_scale);           // folds scale into softmax

        // ---- GEMM 2 : P·V   ---------------------------------------------
        wgmma_gemm_fp8(P_fp32/*(B_r,B_c)*/, smem_Vfp8/*(B_c,d)*/, O_int);
        
        // ---- De‑scale V contribution ------------------------------------
        O_int *= s_V;                                 // final output addition
        
        // accumulate partial output O_int into O_accumulator...
    }

    // -------------------------------------------------------
    // 4️⃣ Epilogue – final normalisation using Lg (=log-sum-exp)
    // -------------------------------------------------------
    finalize_output(O_accumulator, Lg + i*B_r);
}
```

### What are the FLOP count formulas used for benchmarking forward and backward passes of attention?
Question:
In Section 5.1 the authors compute FLOPs as $4 \cdot \text{seqlen}^2 \cdot \text{head dimension} \cdot \text{number of heads}$ for the forward pass and multiply by $2.5$ for backward pass. 

- Why is there a factor of 4 multiplying $\text{seqlen}^2$?
- How does this account for both $QK^\top$ and $PV$ matmuls?
- Where does the $2.5$ multiplier come from – is it based on exact operation counts or an empirical approximation?

Clarifying this will help me compare reported TFLOPs with raw operation counts.

Answer:
The numbers quoted in § 5.1 come directly from counting how many **multiply‑add** operations are performed by the dense matrix products that dominate an attention layer.  
In deep‑learning performance reporting a fused multiply‑add is usually counted as **two floating‑point operations** – one multiplication and one addition – even when a hardware instruction implements them jointly on Tensor Cores.  
With this convention every dense GEMM contributes a factor "$2$", and this is what creates the “$4$’’ in front of $\text{seqlen}^{2}$.

---

### Forward pass

For one head let  

* $Q,K,V\in\mathbb R^{N\times d}$ ($N=$ sequence length, $d=$ head‑dimension),  
* $S=QK^{\top}\in\mathbb R^{N\times N}$,  
* $O=PV\in\mathbb R^{N\times d}$ with $P=\operatorname{softmax}(S)$.

The two expensive kernels are  

1. **$QK^{\top}$** : an $N\times d$ times a $d\times N$ matrix multiplication.  
   For every output entry we do $d$ multiplications followed by $d-1\simeq d$ additions → roughly  
   $$
   2Nd\,(\times N)= 2\,N^{2}d
   $$ 
   floating‑point ops.

2. **$PV$** : an $N\times N$ times an $N\times d$ multiplication, which has exactly the same size pattern, therefore another  
   $$
   2\,N^{2}d
   $$ 
   flops.

Adding them gives  

$$
{\rm FLOP}_{\rm fwd}^{({\rm per\:head})}=  
(2+2)\,N^{2}d = 4\,{\rm seqlen}^{\,2}\times{\rm head\:dim}.
$$

Because an MHA contains “num‑heads’’ independent copies of this computation,
the total forward count becomes  

$$
{\rm FLOP}_{\rm fwd}=    
4\,{\rm seqlen}^{\,2}\times{\rm head\:dim}\times {\rm num\:heads},
$$

which is exactly the expression reported in the paper.  
(The authors ignore scalar work such as dividing by $\sqrt{d}$, adding biases,
or forming row‑wise maxima – those operations contribute far fewer arithmetic
operations compared with GEMMs.)

When causal masking is applied only roughly half of the entries of
$S=PV$ are actually needed, so they simply halve this quantity,
as mentioned in § 5.1.



### Backward pass

Back‑propagation through attention requires five dense GEMMs per head
(they follow directly from equations (6)–(10) in § 3):

| Gradient                                   | Operation | Shape                       |
|--------------------------------------------|-----------|-----------------------------|
| ${\partial L}/{\partial V}=P^{\top}\,\partial O$      | GEMM      | $N\times N \;\times\; N\times d$ |
| ${\partial L}/{\partial P}= \partial O\,V^{\!\top}$    | GEMM      | $N\times d \;\times\; d\times N$ |
| …                                          | …         | …                           |
| ${\partial L}/{\partial Q}= (\partial S)\,K        $      | GEMM      | $N\times N \;\times\; N\times d$ |
| ${\partial L}/{\partial K}= (\partial S)^{!\top} Q            $      | GEMM      | same size                   |

Each one costs again roughly $2\,N^{2}d$ flops,
so per head  

$$
{\rm FLOP}_{\rm bwd}^{({{\rm per\:head}})}=
5\times(2\,N^{2}d)=10\,{\rm seqlen}^{\,2}{\rm head\:dim}.
$$

Comparing with the forward count gives  

$$
\dfrac{{\rm FLOP}_{\rm bwd}}{{\rm FLOP}_{\rm fwd}}=
\dfrac{10}{4}=2.5 .
$$

Thus multiplying the forward‑pass flop estimate by **$2.5$**
is not an empirical fudge factor—it follows directly from counting
the five matrix multiplications required during back‑propagation versus
the two required during inference.
(The small additional work required for softmax’s Jacobian,
for scaling by $1/\sqrt{d}$,
or for residual connections has been omitted because it contributes less than
a few percent to the total arithmetic load.)

---

### Summary

* The prefactor **$4 = 0+0+0+0+$**, i.e. two dense GEMMs each contributing “$\displaystyle  *$, twice’’ (because each fused multiply–add counts as two FLOPs), yields the leading coefficient 4.
* These two GEMMs correspond precisely to **$QK^{⟂}$** and **$PV$.**
* The backward multiplier derives analytically:
  forward uses two GEMMs while backward needs five,
  so $\displaystyle {\rm flops}_{bwd}=({5}/{₂})·{\rm flops}_{fwd}=10/4=⟨[\dots]\!⟩$
  i.e., $\displaystyle {\frac{{10}}{{4}}}= {5}{/}{₂}$,
  giving the overall ratio $\,${${5}{/}{₂}}$\,$≈ $~\$ ”.*
  
In short,
the authors’ TFLOP/s figures are obtained by dividing wall‑clock time
by these analytically derived flop counts;
they therefore reflect pure arithmetic intensity centered on
the dominant matrix‑multiplication work rather than an empirical approximation.​

### Why do exponential special functions on H100 have such low throughput compared to Tensor‑Core matmuls?
Question:
The paper mentions that H100 provides ~989 TFLOPs for FP16 matmuls but only ~3.9 TFLOPs for exponentials used in softmax. 

- Which hardware unit executes these functions (e.g., Multi‑Function Unit) and why is it bandwidth limited?
- Is there any way to accelerate exponentials using Tensor Cores or other instructions?
- Does overlapping softmax with GEMM fully hide this bottleneck, or are there remaining limits?

Answer:
The huge gap between the \$989 \\,\mathrm{{TFLOP/s}}\,$ peak for FP16 matrix‑multiplication and the \$3\.9 \\,\mathrm{{TFLOP/s}}\,$ peak quoted for the exponential in the H100 comes from the way NVIDIA has partitioned the silicon.  

All dense GEMMs are carried out by the **Tensor Cores** (exposed as the WGMMA instruction on Hopper). A Tensor Core operates on \$8\times8\$‑element tiles at every clock cycle and every streaming multiprocessor (SM) contains many such units; together they give almost a teraflop of FP16 MACs per SM. By contrast, transcendental operations such as \$\exp\$,\ \$\log\$ or \$\sin\$ are not part of a matrix‑multiply‑friendly datum path. They are executed by a separate **Multi‑Function Unit (MFU)** — the modern descendant of the older Special‑Function Unit (SFU). Each SM houses only a handful of MFU pipelines (the paper notes “16 special‑function operations per SM per clock”), so even if all 132 SMs fire at the boost clock of \$1\.83\,\\,\mathrm{{GHz}}\,$ the total work‑rate is only  

\[
16\,\\,\mathrm{{ops/SM/cycle}}\times132\,\\,\mathrm{{SM}}\times1\.83\,\\,\mathrm{{GHz}}\approx3\.9\,\\,\mathrm{{TFLOP/s}}\!,
\]

which matches the figure reported in §2\.2 of FlashAttention‑3\. Because this ceiling is set by **compute resources**, not by DRAM bandwidth, we call it “compute‑limited” rather than “bandwidth‑limited”.  

Why can’t we simply ask a Tensor Core to evaluate \$\exp\$? A Tensor Core implements a fixed macro‑operation \$\sum_{i}a_{i}b_{i}\,$ plus optional bias addition and scaling — its datapath has no provision for nonlinear arithmetic beyond multiply‑add. NVIDIA has not published an instruction that maps an elementwise \$\exp\$ onto WGMMA, nor any fused “exp‑plus‑MAC” primitive. Consequently any attempt to speed up \$\exp\$ must fall back on regular CUDA cores: either use an approximation based on a short polynomial or piecewise‑linear table lookup written with ordinary arithmetic instructions, or rely on the library implementation that already runs on the MFU. Neither approach can benefit from massive parallelism of Tensor Cores without substantial algorithmic redesign; doing so would also increase register pressure and likely hurt occupancy.  

The practical consequence for attention kernels is that an entire row of scores \$\mathbf S_{i}\$
must be transformed by  
\$ \widetilde{\mathbf P}_{i}= \exp(\mathbf S_{i}-m_{i}) \$.
For head dimension \$d\$ typical values (\$/64\/,\ /\128\/,\ /\256\/)
this means thousands of exponentials per token pair — far more than what
a handful of MFUs can supply if they run alone.
The authors therefore overlap these cheap operations with expensive GEMMs

another warpgroup proceeds through the softmax pipeline

subtraction $\rightarrow{}$
$\exp$

row sum).
Because WGMMA is asynchronous thanks to Hopper’s TMA/Tensor Core pipeline,
both units can progress simultaneously without incurring stalls — this is what
they call “ping pong” scheduling.  

Does this overlap completely hide the bottleneck? Empirically it does not erase

The paper reports a rise from roughly \$570\,\\,\mathrm{{TFLOP/s}}\$

The residual gap persists because several factors limit full masking:

* **Data dependencies** — the row maximum \$m_{i}\$
  must be known before any exponentials in that block can start,

* **Barrier overhead** — the producer/consumer warpgroups synchronize via

* **Register pressure** — the two-stage pipeline keeps both
  the current score tile \$\mathbf S_{\mathrm{{cur}}}\$

  if we pushed for deeper pipelines or larger tiles we would run out

In long‐sequence regimes where \$N^{2}\$

overlapping pushes softmax cost down to well below \$5\,%\$
of total runtime,
achieving close to \$75\,%\$

but they cannot reach

In summary,
exponentials on H100 are executed by a small MFU whose per‐SM throughput caps at roughly
\$3\.9\,\\,\mathrm{{TFLOP/s}}\$

any acceleration must rely on software approximations running on regular cores.
Overlapping softmax with GEMM through warp specialization effectively hides most —

### How does the two‑stage pipeline in Algorithm 3 avoid sequential dependencies between softmax and GEMMs?
Question:
Algorithm 3 shows that after computing $S_{\text{next}} = Q_i K_j^\top$, the kernel immediately launches a second WGMMA for $O_i += \tilde P_{\text{cur}} V_{j-1}$ without waiting for softmax on $S_{\text{next}}$. 

- Which registers/buffers hold intermediate data to allow this overlap?
- What guarantees that data needed by softmax is ready when its turn arrives?
- Are there any corner cases where latency of previous WGMMA could cause incorrect results?

A detailed explanation of data flow across stages would be useful.

Answer:
**Short answer**

Algorithm 3 hides the data–dependency between the first GEMM ($Q\!\cdot\!K^{\top}$) – which produces the scores that feed the soft–max – and the second GEMM ($P\!\cdot\!V$) – which produces the output contribution – by keeping two *register tiles* alive across loop iterations.  
One tile stores the **next score block** $S_{\text{next}}=Q_{i}\,K_{j}^{\top}$ while a second tile stores the **current probability block** $\tilde{P}_{\text{cur}}=\exp\!\bigl(S_{\text{cur}}-m_{i}\bigr)$ (the row–wise–scaled soft–max). The kernel launches both WGMMAs asynchronously, issues a wait only after it has started useful work from the next iteration, and finally synchronises on each token just before the value is consumed by either soft–max or the accumulator update. Because all waits happen *after* at least one independent instruction has been issued, the latency of a WGMMA can be completely hidden as long as there is another block to process; when there is no further block (the last iteration) an explicit epilogue wait guarantees correctness.

Below I detail how the registers/buffers are organised, why the data are ready when needed, and what pathological cases could break the hiding.

---

### 1. Where do the intermediate results live?

The core of Algorithm 3 is a *two–stage pipeline* inside a single warpgroup (the consumer). At each loop step **j** ($\,1 \leq j < T_{c}-1\,)$ it performs  

1\. $S_{\text{next}}=Q_{i}\,K_{j}^{\top}$        *$WGMA_{0}$* – launched **asynchronously**  

2\. $O_{i}\;\leftarrow\;O_{i}+ \tilde{P}_{\text{cur}}\,V_{\,j-1}$ *$WGMA_{1}$* – launched **asynchronously**

Both intermediate tiles are kept **in registers**:

* $S_{\text{next}}$ occupies a register array sized $B_{r}\!\times\! B_{c}$ (the current query block times the next key block).  
* $\tilde{P}_{\text{cur}}$ occupies an identically shaped register array holding $\exp(S_{\text{cur}}-m_{i})$ after row–max subtraction.

Because each thread in a warp works on a fixed sub–tile of these matrices, no shared–memory traffic is needed between iterations – only a *register copy* ($S_{\text{next}}\rightarrow S_{\text{cur}}$) at line 22 moves the freshly computed scores into the slot that will become $S_{\text{cur}}$ on the next pass.

The **circular shared–memory buffer** described in §3.1 supplies fresh key/value tiles ($K_{j},\,V_{j}$) while it is being recycled; it does not store any score or probability data. Its role is only to decouple memory movement from computation.

---

### 2. How does the kernel know that soft–max can start?

After issuing *WGMA$_0$* ($S_{\text{next}}=Q_{i}K_{j}^{\top}$) the code executes  

```c
// line “Commit but do not wait”
wmma.commit_group();
```  

which returns an opaque *completion token*. The next instruction that touches $S_{\text{next}}$ – namely  

```c
// line “Wait for the WGMMA Q·Kᴛ”
wmma.wait_group(token);
```  

appears **after** two other independent actions have been scheduled:

* loading $V_{\,j-1}$ from shared memory,
* launching *WGMA$_1$* ($\tilde{P}_{\text{cur}}\,V_{\,j-1}$).

Thus while Tensor Cores are busy finishing *WGMA$_0*$, CUDA cores are already executing  

* special–function operations for row–wise max/subtraction,
* exponential arithmetic that builds $\tilde{P}_{\text{next}}$,  
* bookkeeping for normalisation factor $\ell_{i}$.

The same pattern follows *WGMA$_1*$: it is also committed without an immediate wait; later, just before its result is added into $O_{i}$, we issue  

```c
wmma.wait_group(token_PV);
```  

Only at those two points does control actually pause – exactly when a consumer thread needs a value produced by an earlier producer WGMA. Because every wait follows at least one full “useful” instruction stream, all latencies are absorbed unless there are fewer than two blocks left to process.

The algorithm therefore guarantees readiness simply by construction:

* The **soft‑max** reads $S_{\text{next}}$ only after an explicit ``wait_group`` , which cannot fire until Tensor Cores have written back those registers.  
* The **output accumulation** reads $\tilde{P}_{\text{cur}}$ only after its own preceding WGMA has signalled completion.

No race condition can arise because both producers and consumers are bound by those tokens.

---

### 3. Could lingering latencies corrupt results?

In theory an extreme latency—for example if a WGMA takes longer than the work scheduled between its launch and its wait—would make later instructions stall, but it would never produce wrong numbers:

* The **data path** itself never proceeds without confirming completion (``wait_group``).  
* The **control flow** ensures that every producer–consumer pair respects this ordering.

What *does* change performance is pipeline occupancy:  

* When there are fewer than two key/value blocks ($T_{c}<2$) there simply isn’t any “next’’ iteration to hide latency; the kernel falls back to a simple serial schedule (the epilogue in lines 30–31 handles this case).  
* When register pressure forces spills into shared memory or local memory, extra traffic can increase overall runtime but still preserves correctness because all loads/stores are still guarded by their respective barriers (``bar.sync`` in §3.1).

Therefore corner cases where “latency could cause incorrect results’’ do not exist under correct compilation; only performance degradation may appear if either  

​    (i) block size makes each WGMA unusually long relative to soft‑max work, or  
​    (ii) extreme resource constraints trigger register spilling.

---

### 4. End‑to‑end data flow

Putting it together, one full loop looks like this:

| Step | Action |
|------|--------|
| 1 | **Load** $K_{j}$ into SMEM → issue WGMA$_0$ producing $S_{\text{next}}$. |
| 2 | **Load** $V_{\,j-1}$ into SMEM → issue WGMA$_1$ using already available $\tilde{P}_{\text{cur}}$. |
| 3 | **Wait** on WGMA$_0$ → execute soft‑max on $S_{\text{next}}$, producing new probability tile $\tilde{P}_{\text{next}}$, updating row max $m_{i}$ and normalisation factor $\ell_{i}$. |
| 4 | **Wait** on WGMA$_1$ → add its product into output accumulator $O_{i}$, apply rescaling by $\exp(m^{\text{old}}_i-m_i)$. |
| 5 | **Swap** pointers/registers so that today’s $S_{\text{next}}$ becomes tomorrow’s $S_{\text{cur}}$, today’s $\tilde{P}_{\text{next}}$ becomes tomorrow’s $\tilde{P}_{\text{cur}}$. |

Because steps 2–4 run in parallel across different hardware units—Tensor Cores for both WGMMAs, CUDA cores for exponential/max/sum—the total wall‑clock time per block approaches that of a single GEMM while preserving exact attention semantics.

### TL;DR  

Algorithm 3 uses two per‑warp register tiles ($S_{\text{next}}$ and $\tilde{P}_{\text{cur}}$) to keep score and probability data alive across iterations. Each WGMA is launched with an asynchronous commit token; explicit waits are placed only when that tile is actually needed (soft‑max or output accumulation). This simple producer/consumer token scheme guarantees that every piece of data has finished computing before it is read, while allowing all other work in between to hide its latency. The only situation where we cannot hide latency is when there are fewer than two blocks left to process—the kernel then reverts to a serial tail—but correctness never suffers; only possible idle cycles appear if hardware latency exceeds overlapping work or if register spilling occurs. This is precisely how FlashAttention‑3 removes sequential dependencies between softmax and GEMMs without sacrificing numerical accuracy.
