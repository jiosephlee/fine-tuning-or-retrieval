\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### Why are hash n‑gram embeddings used instead of learned n‑gram embeddings in the encoder?
Question:
Section 4.2.1 introduces hash embeddings for byte n‑grams of size 3–8 using a RollPolyHash function. The authors mention frequency‑based n‑gram embeddings as an alternative explored in an appendix. What are the advantages of hash embeddings (e.g., memory efficiency, collision handling) over directly learning an embedding table for all possible n‑grams? Also, how sensitive is model performance to the hash table size (e.g., 100K vs 500K entries) according to their ablations?
Answer:
The encoder in BLT has to enrich the representation of every byte with a short‑range context – i.e.\@with the byte‑ngrams that end at that position.  
If we were to allocate a conventional learnable table for all possible byte‑ngrams of length 3‒8 we would need  

\[
\sum_{n=3}^{8}256^{\,n}\;\approx\;2\times10^{19}
\]

entries. Even if we kept only the *observed* n‑grams in the training corpus this would still be tens or hundreds of millions of distinct strings, each requiring a vector of size \(h_{\mathcal{E}}\) (typically \(64\!-\!256\)). The resulting matrix would easily exceed several hundred gigabytes – far beyond what fits on a GPU or a single server node, and it would also make the optimizer updates prohibitively expensive.

A frequency‑based alternative (described in Appendix B) therefore keeps only the most frequent n‑grams and treats everything else as “unknown”. This solves the memory problem but introduces two new drawbacks:

1\. **Coverage bias** – rare n‑grams are precisely those that often carry useful orthographic or domain‑specific clues (e.g., uncommon Unicode characters or code symbols). By discarding them we lose information that is otherwise available for free at test time.  
2\. **OOV handling** – every unseen n‑gram collapses onto a single “unknown” vector, which forces the model to treat very different patterns identically.

The authors therefore adopt **hash n‑gram embeddings**, i.e., the classic feature‑hashing trick applied at the level of byte strings. For each gram \(g_{i,n}\) they compute  

\[
\text{idx}= \text{RollPolyHash}(g_{i,n}) \bmod |E_n^{\text{hash}}|
\]

and look up a dense vector from a *fixed‑size* table \(E_n^{\text{hash}}\). The advantages are:

* **Memory efficiency** – the size of every table can be chosen arbitrarily (e.g., 100 k or 500 k entries), independent of the astronomical number of possible grams. Even with six tables (one per gram length) the total extra parameters amount to only a few megabytes compared with billions in the global transformer.
* **Uniform coverage** – every possible gram maps somewhere into the table, so even extremely rare patterns receive an embedding rather than being lumped into a generic OOV bucket.
* **Implicit regularisation through collisions** – when two different grams hit the same index they share parameters, which acts like a form of smoothing: unrelated patterns that happen rarely together do not overfit separate vectors while frequent ones still dominate their buckets.
* **Simple computation** – RollPolyHash is an integer rolling polynomial that can be evaluated in \(\mathcal{O}(1)\) per gram using only integer arithmetic and a modulo operation, adding negligible overhead during data loading.
* **Deterministic incremental patching** – because hashing depends only on the current bytes (no future context) it satisfies the incremental patching property required by BLT’s preprocessing pipeline.

### How much does the hash‑table size matter?

Table 10 (reproduced in § 4\.2\.1) reports ablations with four settings:

| Table size per gram | Bits‑per‑byte change vs.\@no hash |
|---------------------|------------------------------------|
| 0 (kill hash)      | baseline                           |
| 100 k               | $-0.03\,\mathrm{BPB}$ on Wikipedia, $-0.02\,\mathrm{BPB}$ on GitHub |
| 200 k               | additional $\approx -0.01\,\mathrm{BPB}$            |
| 400 k               | additional $\approx -0.005\,\mathrm{BPB}$           |
| 500 k (default)    | $\approx -0.04\,\mathrm{BPB}$ overall improvement over baseline |

The key observations are:

* Adding any hash table already yields a noticeable gain (\(\!\approx\nobreakspace 0.\!\!03{-}0.\!\!04~{\rm BPB}\)), especially on corpora where character patterns matter most.
* Doubling the capacity from 100 k → 200 k reduces BPB by another \(\!\approx\nobreakspace 0.\!\!01~{\rm BPB}\), confirming that fewer collisions help.
* Going beyond roughly three hundred thousand entries brings diminishing returns: moving from 300 k → 500 k improves BPB by only \(\!\approx\nobreakspace 10^{-3}~{\rm BPB}\) after fifteen thousand training steps at the eight‑billion‑parameter scale.
* Across all scales (400 M up to 8 \( {\rm B}\) parameters) this trend holds – performance plateaus once collisions become rare enough that most useful grams have dedicated rows.

Thus BLT’s authors chose a default budget of **500 000 hashes per gram length**, which adds \< 1 % extra parameters relative to an eight‑billion‑parameter model while essentially eliminating any measurable performance gap caused by collisions.

### Intuition

From a broader perspective this design mirrors *feature hashing* used in large‑scale linear models and recommender systems: you map an extremely high‑cardinality categorical space into a modest dense space with random projections, preserving inner products in expectation while keeping memory constant. In BLT the hashed gram vectors play exactly this role – they inject sub‑byte locality into each byte’s embedding without blowing up storage or requiring handcrafted frequency cutoffs.

In short, hash n‑gram embeddings give BLT **full coverage**, **tiny memory footprint**, **fast lookup**, and **robustness through controlled collision sharing**; empirical ablations show that even a modest table $(\approx 100~{\rm k}\,\text{entries})$ already recovers most of the benefit, while increasing it up to half a million entries yields marginal but consistent improvements—beyond that point performance saturates. This explains why learned full vocabularies or pure frequency tables are abandoned in favor of hashed embeddings in the encoder.&nbsp;
