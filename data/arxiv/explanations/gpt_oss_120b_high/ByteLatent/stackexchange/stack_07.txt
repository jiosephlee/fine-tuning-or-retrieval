\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### Why do the authors treat embedding lookups as zero‑FLOP operations?
Question:
In Section 4.5 they state "we assume the input embedding layer is implemented as an efficient lookup instead of a dense matrix multiplication, therefore becoming a 0‑flop operation." Is this assumption realistic for modern hardware where embedding lookups still incur memory bandwidth costs? How might this simplification affect comparisons between BLT and token‑based models where embeddings have different dimensions?
Answer:
**Short answer:**  
The paper counts *floating‑point operations* (FLOPs) only – not memory traffic – when measuring the cost of a model. An “embedding lookup” is simply a **gather** from a table of pre‑computed vectors, which involves no arithmetic (no multiply‑adds). On modern GPUs/TPUs this gather does consume bandwidth, but its contribution to the total *flop* budget is tiny compared with the billions of FLOPs spent in the feed‑forward networks and attention blocks. Therefore the authors set its FLOP count to zero so that the flop‑controlled scaling analysis focuses on the parts that dominate compute.  

Below I break down why this assumption is made, how realistic it is on real hardware, and what consequences (if any) it has for comparing BLT with token‑based models whose embeddings have different dimensions.

---

### 1\. What “0‑flop” really means

A FLOP is defined as a **floating‑point multiplication or addition**. The standard transformer flop formulas (e.g. those from Chinchilla) count  

* Q,K,V projections → $\displaystyle 3 \;\cdot\; d \;\cdot\; d$ per head  
* Self‑attention → $\displaystyle 2 \;\cdot\; n \;\cdot\; d^{2}$  
* Feed‑forward → $\displaystyle 2 \;\cdot\; d \;\cdot\; d_{ff}$  

An embedding layer, if implemented as a dense matrix product $\displaystyle E\,{\tt one}\_\mathrm{hot}(\text{token})$, would indeed contribute $\displaystyle d\,\bigl|\mathcal V\bigr|$ multiplies per token ($|\mathcal V|$ = vocab size). However in practice we never materialise the one‑hot vector; we **index** row $i$ of $E$. That operation consists only of  

1\. Reading one row ($d$ 32‑bit numbers) from DRAM/VRAM.  
2\. Passing it forward unchanged.  

No multiplication or addition occurs, so **by definition its FLOP count is zero**.

---

### 2\. Is the “zero‑flop” assumption realistic on modern hardware?

*Memory bandwidth vs compute.*  
A gather does use bandwidth: each token reads $d\times4\,\text{bytes}$ from memory. For typical hidden sizes ($d=2048$) this is ≈8 KB per token – nothing compared with the megabytes read/written by attention matrices ($O(n^{2}\!~d)$ reads/writes). As model depth grows, the *compute* required by attention and FFN layers dwarfs the cost of fetching an embedding row.

Empirically this matches observations in many large‑scale training runs: profiling shows that **the time spent in the embedding lookup accounts for <1 % of total wall‑clock time** when batch sizes are modest (e.g., 16 kB per GPU) and when the table fits at least partially in cache. When the table becomes huge (e.g., Llama 3’s $128\,k$ token vocabulary × 4096‑dim vectors ≈ 2 GB), some runs do see a modest slowdown due to cache misses, but even then it remains a small fraction of total cycles because each forward/backward pass still executes billions of floating‑point instructions.

Thus treating it as “free” from a flop perspective is **acceptable for a first‐order analysis** that deliberately abstracts away memory bottlenecks. The authors also acknowledge in §4.5 that they are *following previous work* (e.g., Chinchilla) where embeddings are assumed free for exactly this reason.

---

### 3\. Why does this matter for **BLT vs token‑based** comparisons?

#### (a) Different hidden dimensions  

BLT’s local encoder ($h_{\mathcal E}$), global latent transformer ($h_{\mathcal G}$) and decoder ($h_{\mathcal D}$) may have different widths than a token model’s single hidden size $h$. The flop formulas already capture these differences:

\[
\text{Flops}_{\text{global}}=
   \operatorname{Transf.FLOPs}\!\bigl(
      h_{\mathcal G},\,l_{\mathcal G},
      m=\tfrac{n_{\text{ctx}}}{n_{p}},\,V=0
  \bigr)
\]

where $V=0$ means “no output projection”. The **input side** always appears as “lookup = 0 FLOPs”, regardless of whether $h_{\mathcal E}$, $h_{\mathcal G}$ or $h_{\mathcal D}$ change. Consequently any *increase* in hidden size manifests through larger feed‐forward/attention costs—not through an extra term for inputs.

#### (b) Vocabulary size  

The **output** projection from logits back to symbols *does* incur FLOPs because it is a dense matrix multiply between hidden states and the vocabulary matrix:

\[
\text{Flops}_{\text{decoder out}}=
   \operatorname{Transf.FLOPs}\!\bigl(\dots,\,
   V=\bigl|\mathcal V\bigr|\bigr)
\]

In BLT $|\mathcal V|=256$ (one byte), while a token model uses $|\mathcal V|\approx128k$. This term therefore reflects the true arithmetic difference between byte‐level and token models. The input side remains “lookup”, so any disparity caused by larger vocabularies does **not** appear twice.

#### (c) Effect on relative efficiency conclusions  

Because both families share the same “free lookup” assumption, **the relative efficiency ranking is unchanged**: any advantage BLT shows comes from fewer transformer steps (larger patches) or a smaller global attention cost—not from pretending that an expensive embedding has disappeared. If one wanted to compare wall‐clock speed rather than FLOPs, you would add an extra term proportional to
$\displaystyle \textit{batchSize}\times d\times (\textbytes per token})$
which would penalise very large vocabularies slightly more. In practice that penalty would be minor compared with the gains from reduced attention depth shown in Figures 4–6 of the paper.

---

### 4\. When could ignoring embedding FLOPs be misleading?

1\. **Extremely small models** – If you train a model with only a few million parameters, then every operation matters; the gather may become an appreciable fraction of total compute.  

2\. **Very large vocabularies** – Suppose you replaced bytes with Unicode codepoints (~1M symbols). Even though each fetch still costs zero FLOPs, moving several gigabytes per minibatch could overwhelm PCIe/HBM bandwidth and become a bottleneck.  

3\. **Hardware where gathers are not fused** – Some custom ASICs provide dedicated “embedding” units that amortise the load across many threads; others may treat gathers as raw memory loads that stall pipelines if not cached well.

In these edge cases one would supplement FLOP counting with *memory traffic* metrics such as *bytes transferred* or *effective bandwidth utilization*. The authors deliberately limit their scope to FLOP counts because their core claim—*patches reduce arithmetic work while preserving performance*—is best expressed using an arithmetic metric.

---

### 5\. Bottom line

* **Zero‐flop** means “no arithmetic”, not “no cost”. It isolates the part of computation whose cost scales quadratically with sequence length.
* On GPUs/TPUs today an embedding lookup’s bandwidth cost is negligible relative to billions of FLOPs spent in attention/FFN layers, so treating it as free is common practice when deriving scaling laws.
* The simplification does **not bias** BLT vs token comparisons because:
  * Both architectures receive identical treatment on the input side.
  * Differences in vocabulary size are already accounted for on the **output projection**, which dominates any extra arithmetic.
* If you care about absolute wall‐clock latency or energy consumption on memory‐bound hardware, you would add additional terms for embed‐lookup traffic—but those refinements do not overturn the main conclusion that dynamic patching yields substantial flop savings.

Hence, within the paper’s goal—showing *flop‐controlled scaling*—the assumption is both realistic and harmless for comparing BLT against traditional tokenizer‐based models.​
