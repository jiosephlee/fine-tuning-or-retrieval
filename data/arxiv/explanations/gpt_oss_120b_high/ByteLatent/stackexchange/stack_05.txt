\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### How does average patch size affect both training context length and inference FLOPs?
Question:
The paper claims that larger average patch sizes reduce inference FLOPs because the Latent Transformer runs fewer steps, yet they also keep "the number of bytes in each batch constant in expectation" when changing patch size. I'm confused about how increasing patch size simultaneously reduces compute per token while preserving context length. Does changing the average patch size implicitly shorten the sequence length fed to the Global Transformer? How is this accounted for in their FLOP estimation formula (Equation 5)?
Answer:
**Short answer:**  
When the *average* patch size $\displaystyle \bar{s}$ grows, the *number of patches* that appear in a fixed‑byte context shrinks (because  
$\displaystyle n_{\mathrm{patch}}=n_{\mathrm{bytes}}/\bar{s}$). The Latent Global Transformer therefore receives a shorter sequence—it executes fewer autoregressive steps—while the **total amount of raw byte data** seen by the model stays the same. In the flop bookkeeping (Eq.\,$\,5)$ this appears as $\,n_{p}\,$ (the number of patches) in the denominator of every term that belongs to the Global transformer or its cross‑attention layers. Since $\,n_{p}\,$ drops linearly with $\displaystyle \bar{s}$, the global‑transformer contribution to FLOPs per byte drops roughly as $\displaystyle 1/\bar{s}$, which is exactly what the paper reports as “larger patches save inference FLOPs”.

Below I walk through why this does **not** mean that we are secretly shortening the *byte* context, how it influences training versus inference, and how Eq.\,$\,5)$ captures the effect mathematically.



---

### 1\. What “keeping the number of bytes in each batch constant’’ really means  

The authors fix an *expected* batch size measured in **bytes**, e.g.~$\displaystyle 8\,\mathrm{kB}$ on Llama‑2 data or $\displaystyle 16\,\mathrm{kB}$ on BLT‑1T data (§ 4.3).  
During data loading they first segment each document into patches using whatever rule (strided, whitespace, entropy), then **pack** batches so that every batch contains roughly the same *byte* count:

\[
\mathbb E[\!\,\text{bytes per batch}\!] = B_{\mathrm target}.
\]

If $\displaystyle \bar{s}$ is large, fewer patches are needed to reach $B_{\mathrm target}$, so a batch will contain *fewer* tokens for the Global model but exactly the same amount of raw text. No extra information is lost—we simply live with a shorter **patch sequence** $\mathbf p$ while preserving a full‑byte context for the local encoder/decoder.

Thus “constant batch bytes’’ does **not** imply a constant *patch* length; it deliberately allows $\,n_{p}\,$ to vary as $\displaystyle \bar{s}\,$ varies.



---

### 2\. How a larger $\displaystyle \bar{s}\,$ reduces FLOPs  

The Global transformer operates on  

\[
\mathbf p=\bigl\{\,p_j\bigr\}_{j=1}^{\,n_{p}},
\]

and its cost follows standard transformer scaling:

\[
\operatorname{Transf.\!FL}(h,l,m)=
2\,l\,h^{2}m   \;\;\!\!\!\!\!\!\!\!\!\!\!\,\bigl(\!\mathrm{:FFN}\bigr)\;
+\;
4\,l\,h^{2}m   \;\;\!\!\!\!\!\!\!\!\!\!\!\,\bigl(\!\mathrm{:QKV+O}\bigr).
\]

Here $m$ is the attention window length (for full causal attention $m=n_{p}$).  
In Eq.\,$\,5)$ the authors divide this cost by $\,n_{p}\,$ because FLOPs are reported **per byte**:

\[
\dfrac{\operatorname{
Transf.\!FL}\bigl(h _{\mathcal G},
                 l _{\mathcal G},
                 m=n_{p},
                 V=0\bigr)}{
      n_{p}}
=
      \Theta\bigr(\tfrac1{\displaystyle \bar{s}}\bigr).
\]

Since  

\[
n_{p}= \dfrac { n _ {\mathrm {ctx}} } {\displaystyle \bar{s}},
\]

every factor that contains $\,n_{p}\,$ becomes inversely proportional to $\displaystyle \bar{s}$.  
The cross‑attention terms contain an extra ratio $\displaystyle k/n_{p}$ (where $k$ is a fixed splitting factor), which again scales like $1/\displaystyle \bar{s}$.

All other components – the Local encoder ($h _{\mathcal E}, l _{\mathcal E}$) and Local decoder ($h _{\mathcal D}, l _{\mathcal D}$) – act on **bytes** directly ($m = w _{\mathsymbol{"211D}}, V=0$, i.e.~$\displaystyle m=w _{\symbol{"211D}}$, or simply {$m=w_\({E/D})${}). Their FLOPs therefore do **not** depend on $\displaystyle \bar{s}$. Consequently, as $\displaystyle \bar{s}$ grows  

| Effect | Description |
|--------|-------------|
| **Global cost** | Falls roughly linearly with $\displaystyle 1/\bar{s}$. |
| **Local cost** | Stays flat. |
| **Total FLOPs/byte** | Shrink until the Global part becomes comparable to—or smaller than—the Local part, at which point further increase in $\displaystyle \bar{s}$ yields diminishing returns.|

This exact dependence produces Fig.\,$0.$4 (fixed‑inference scaling): doubling $\displaystyle \bar{s}$ almost halves inference FLOPs while allowing us to re‑allocate saved compute to a bigger Global transformer if desired.



---

### 3\. Training vs.~inference  

During training all bytes in a context are processed at once; both Local encoder and Global transformer run on every step of an input segment because teacher forcing supplies all target bytes simultaneously. The reduction in Global steps therefore appears directly as a lower forward/backward FLOP count for each training minibatch—exactly what Eq.\,$\,5)$ captures.

During autoregressive **generation**, however, only when a new patch starts does the model invoke the Global transformer again (§ 3). Inside a long patch all subsequent bytes are produced solely by the Local decoder (plus cheap cross‑attention), so each generated byte after the first one costs only “decoder‑only’’ FLOPs.  

If $\displaystyle \bar{s}=8~$\!bytes/patch then roughly one eighth of generated bytes trigger a costly Global call; if $\displaystyle \bar{s}=4~$\!bytes/patch only one fourth do. Hence inference FLOPs per generated token drop ≈ proportionally to $1/\displaystyle \bar{s}$, matching precisely “larger patches → fewer steps → lower inference FLOPs’’.



---

### 4\. Does increasing $\displaystyle \bar{s}\,$ implicitly shorten *the* context seen by the model?  

Yes—it shortens **the token/prefix length fed into the Global transformer**, because that module only sees one element per patch:

\[
L _ {\mathrm {global}} = n _ { p } =
\dfrac { L _ {\mathrm {bytes }} } {\displaystyle \bar{s}}\!.
\]

But notice that $L _ {\mathrm {bytes }}$(the actual textual span) stays unchanged across experiments thanks to constant‑byte batching (§ 4.3). In other words we give every model exactly the same raw‐text window; we merely present it at different granularities to its two sub‑networks.

Because any information that would have been captured by an extra Global step now lives inside a longer *local* region, there is no loss of total context—it is simply represented more compactly inside an individual patch representation rather than spread across many Global states.



---

All terms containing ``\( n_{ p }\!)'' scale with ``\(1/\overline{s}\!)'' because $n_p=L_\textrm{{bytes}}/\overline{s}$. The first term already carries an explicit division by~$ n_p $, converting total Global FLOPs into *per‑byte* units.
Both cross‑attention terms carry either ``\(k/n_p)\,$'' or ``\(1/n_p)\,$'', i.e.~they shrink when patches become larger.
Only middle three terms are independent of~$\displaystyle n_p$, thus forming an asymptotic floor for FLOPs/byte once~$\overline{s}$ grows enough.



---

### TL;DR  

* Keeping “bytes per batch constant’’ means we always feed exactly the same raw‐text window.
* Raising average patch size reduces **how many patches** represent that window ($\: n_p = L_\textrm{{bytes}}/\overline{s}\:$), so both training and generation use fewer steps of the expensive Global transformer.
* Eq.\,$0.$5 reflects this through every occurrence of~$\: n_p\:;$ those factors become inversely proportional to~$\overline{s}\,$.
* The remaining three terms ($>$ encoder, decoder, local operations) do not depend on~$\overline{s}\,$ and therefore constitute an asymptotic compute floor.
* Consequently larger patches save inference FLOPs without cheating on context length—they merely compress more bytes into each latent step while preserving full‐byte coverage.
