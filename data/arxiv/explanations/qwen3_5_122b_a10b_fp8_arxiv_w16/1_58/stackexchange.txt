\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### How exactly does adding '0' to the {-1, 1} set result in 1.58 bits per parameter?
Question:
The abstract and introduction repeatedly refer to the model as '1.58-bit'. I understand that the weights are ternary {-1, 0, 1}, but I am confused about the math behind the name. If a standard bit is binary (2 states), and we have 3 states, shouldn't the information content be $rac{	ext{log}_2(3)}{	ext{log}_2(2)} 	imes 	ext{bits}$? Does $1.58$ come from calculating $	ext{log}_2(3)$? If so, why is this referred to as '1-bit' in other contexts (like BitNet) versus '1.58-bit' here, and does this imply a compression ratio rather than just storage size?
Answer:
The value of **1.58** arises directly from the information theory definition of entropy applied to a uniform distribution over three distinct states. When you add the value `0` to the traditional binary set $\{-1, 1\}$ found in BitNet, you expand the parameter space from two possibilities ($N=2$) to three possibilities ($N=3$, i.e., $\{-1, 0, 1\}$). In information theory, the minimum number of bits required to represent one symbol chosen uniformly from $N$ options is calculated as $\log_2(N)$. Therefore, for a ternary system where $N=3$, the theoretical information content per parameter is exactly $\log_2(3) \approx 1.58496$ bits. The authors explicitly state in Section 1 that they "added an additional value of 0... resulting in 1.58 bits," confirming that this figure represents the theoretical storage efficiency gain relative to a base-2 system.

This naming convention distinguishes **BitNet b1.58** from the original **BitNet**, which strictly utilizes a binary set $\{-1, 1\}$. Since $\log_2(2) = 1$, the original architecture is correctly termed "1-bit." By introducing the third state (`0`), the model gains "feature filtering" capabilities—allowing weights to effectively deactivate connections—which improves modeling performance without reverting to higher-precision formats like FP16 or INT4. Consequently, while both models offer massive compression compared to standard floating-point weights (which use 16 or 32 bits), BitNet b1.58 sits mathematically between pure binary and low-bit integer quantization schemes (like 2-bit or 4-bit).

It is important to note that this "1.58-bit" label refers to the **information density** or theoretical lower bound of storage per parameter assuming an optimal encoding scheme (such as Huffman coding or arithmetic coding) across large batches of weights. In practical hardware implementations described in the paper, such as those using NVIDIA's FasterTransformer or custom kernels, individual parameters might still be stored in fixed-width registers (e.g., packed into integers) rather than fractional bit streams. However, because every parameter takes one of only three values, the *effective* memory footprint and energy cost scale according to this logarithmic ratio rather than linear byte allocation. Thus, calling it "1.58-bit" accurately reflects its position on the spectrum between strict binarization and higher-precision quantization, highlighting that it achieves near-binary efficiency while retaining significantly greater expressivity through sparsity (the zero state).

### Does the absmean quantization function allow gradients to flow through the rounding operation during backpropagation?
Question:
In Section 2 under 'Quantization Function', Equation 1 defines $	ilde{W} = 	ext{RoundClip}(rac{W}{eta + 	au}, -1, 1)$. Since the $	ext{RoundClip}$ operation is non-differentiable (the derivative is zero everywhere except undefined points), how does the model train effectively? Are they using Straight-Through Estimator (STE) approximations for the gradient of the rounding function? The paper mentions training from scratch but doesn't explicitly detail how gradients pass through this hard constraint.
Answer:
Yes, the model trains effectively despite the non-differentiable nature of the `RoundClip` operation because the authors implicitly rely on the **Straight-Through Estimator (STE)**, a standard technique in quantization-aware training that is consistent with the methods used in their predecessor, BitNet. Although the paper titled *The Era of 1-bit LLMs* does not explicitly define the STE equation in Section 2, it states that BitNet b1.58 is built upon the BitNet architecture and trained from scratch using a specific quantization function. In the original BitNet framework and virtually all modern quantization literature, when a discrete operation like $\mathrm{Round}$ appears inside a computational graph during backpropagation, its gradient is defined as 1 within a certain clipping range (typically $[-1, 1]$) and 0 outside, effectively bypassing the discontinuity.

Intuitively, this works because during forward propagation, the weights $W$ are indeed clamped to the set $\{-1, 0, 1\}$ via Equation 1: $\widetilde{W} = \mathrm{RoundClip}\left(\frac{W}{\gamma + \epsilon}, -1, 1\right)$, ensuring the model operates with ternary weights. However, during backward propagation, treating the derivative of $\mathrm{RoundClip}$ as zero would prevent any learning signal from reaching the underlying full-precision weights $W$, causing training to stall. By applying STE, we approximate $\frac{\partial \widetilde{W}}{\partial W} \approx 1$ whenever $\left|\frac{W}{\gamma + \epsilon}\right| < 1$. This allows gradients to flow through the "hard" rounding operation as if it were an identity function locally, updating $W$ toward values that minimize loss while keeping the actual stored weights ternary.

This approach connects to broader concepts in deep learning where we optimize a continuous relaxation of a discrete problem. The scaling factor $\gamma$, defined as $\gamma = \frac{1}{nm}\sum_{ij} |W_{ij}|$, acts as a learnable or dynamic threshold that adapts to the distribution of weights. Without STE (or a similar approximation like Gumbel-Softmax), there would be no mechanism for $W$ to evolve toward regions where rounding yields optimal ternary configurations ($\pm 1$ or $0$). Therefore, while Equation 2 describes a non-differentiable mapping for inference and forward passes, successful training necessitates this gradient approximation strategy to bridge the gap between continuous optimization and discrete constraints.

### If weights are strictly ternary {-1, 0, 1}, how does matrix multiplication avoid floating point multiplication entirely?
Question:
The paper claims that BitNet b1.58's matrix multiplication 'requires almost no multiplication operations.' Mathematically, if $Y = XW$, and elements of $W$ are only -1, 0, or 1, then computing a dot product seems to involve only additions ($+X_i$), subtractions ($-X_i$), or skips ($0$). However, activations $X$ are stated to be 8-bit integers in Section 2. How does the hardware actually execute this without converting back to float? Specifically, if an activation is an integer like $45$, multiplying by $-1$ is just negation, but isn't there still a need for accumulation logic that might differ from standard GEMM units? How does this translate to 'integer addition' specifically?
Answer:
Your intuition regarding the replacement of multiplication with conditional addition and subtraction is exactly correct, and this is precisely what allows BitNet b1.58 to claim it "requires almost no multiplication operations." The key lies in understanding that while the *mathematical* operation $y = \sum x_i w_i$ remains a dot product, the *computational realization* changes fundamentally when $w_i \in \{-1, 0, 1\}$ and $x_i$ are integers.

When performing standard General Matrix Multiplication (GEMM) with floating-point numbers, the hardware must execute a Multiply-Accumulate (MAC) instruction for every pair of operands. This involves complex circuitry to align exponents and multiply mantissas, which is energy-intensive. However, in BitNet b1.58, since the weights $\widetilde{W}_{ij}$ are restricted to the set $\{-1, 0, 1\}$, the term $x_j \cdot \widetilde{W}_{ij}$ simplifies logically: if $\widetilde{W}_{ij} = 1$, the result is simply $+x_j$; if $\widetilde{W}_{ij} = -1$, the result is $-x_j$ (which is equivalent to bitwise negation plus one in two's complement representation); and if $\widetilde{W}_{ij} = 0$, the contribution is skipped entirely. Consequently, the inner loop of the matrix multiplication transforms from a series of multiplications followed by additions into a series of conditional additions and subtractions accumulated into an integer register.

You correctly noted that activations $X$ are 8-bit integers. This choice is critical because it ensures that the accumulation logic operates purely within the integer domain. Standard Integer Adders (INT_ADD) are significantly simpler circuits than Floating-Point Multipliers (FP_MUL). In modern silicon technology (such as the 7nm process mentioned in the paper), an integer addition consumes roughly 2% to 4% of the energy required for a floating-point multiplication. By eliminating the multiplier stage entirely for weights, BitNet b1.58 shifts the dominant energy cost from FP-MAC operations to INT-ADD operations. The paper explicitly states in Section 2 that "the matrix multiplication of BitNet only involves integer addition," and Section Results confirms this by noting that "the majority of BitNet b1.58 is INT8 addition calculation."

Regarding your concern about whether this requires special hardware conversion back to float: it does not happen during the core linear layer computation. The entire forward pass through `BitLinear` layers occurs in fixed-point integer arithmetic ($Y = XW$ where $X$ is int8 and $W$ is ternary). The accumulation happens in wider integer registers (typically int32 or int64) to prevent overflow during summation, but no floating-point unit (FPU) involvement is needed until potentially after activation functions or normalization steps if those require higher precision scaling (though even these can often be handled via fixed-point approximations or lookup tables). The "conversion" you might imagine—where an integer like 45 multiplied by -1 becomes -45—is not performed via a generic multiplication instruction; instead, it is implemented via a simple sign flip or subtraction logic controlled by a bit flag derived from the ternary weight storage format.

This distinction explains why the paper highlights such massive efficiency gains: they are leveraging specialized kernels (like the integrated Ladder 2-bit kernel mentioned in Section Results) that pack multiple ternary weights into bits and use vectorized add/subtract instructions rather than generic MAC units. This effectively turns what was historically a bottleneck of expensive floating-point multiplies into a stream of cheap integer adds, enabling speedups of up to $4.1\times$ and energy reductions of $\sim71\times$ as observed in their benchmarks against FP16 LLaMA baselines.

### Why does removing bias terms matter specifically for ternary weight models compared to FP16 models?
Question:
Section 2 mentions that BitNet b1.58 'removes all biases' to align with LLaMA-like components. In standard Transformers, biases help shift activations away from zero or correct systematic errors. With weights restricted to {-1, 0, 1}, isn't there a risk that the lack of bias limits the model's ability to represent certain distributions or offsets in the data? Or does the RMSNorm layer implicitly handle what biases usually do? I'm struggling to see why bias removal is highlighted as a specific architectural choice for *this* quantization scheme rather than just general efficiency.
Answer:
Your intuition regarding the necessity of bias terms to shift activation distributions is correct for standard floating-point architectures, but the situation changes fundamentally when moving to ternary weights ($\{-1, 0, 1\}$) combined with RMSNorm. In the context of BitNet b1.58, the removal of biases is not merely an arbitrary alignment with LLaMA for compatibility; it is a structural necessity driven by how normalization layers interact with quantized linear transformations.

In a standard Transformer block using LayerNorm or BatchNorm, these normalization techniques explicitly center the activations around zero (subtracting the mean) and rescale them. If you were to add a learnable bias term after such a normalization layer, you would effectively re-introduce a constant offset that the subsequent non-linearity must overcome or adapt to, which can sometimes lead to instability or redundancy. However, BitNet b1.58 specifically employs **RMSNorm** (Root Mean Square Layer Normalization), as noted in Section 2 under "LLaMA-alike Components." Unlike traditional LayerNorm, RMSNorm normalizes inputs solely based on their root mean square without subtracting a mean term: $\text{RMSNorm}(x)_i = x_i / \sqrt{\frac{1}{n}\sum_j x_j^2 + \epsilon} \cdot w_i$, where $w_i$ represents learnable scaling factors (often denoted as gain). Crucially, RMSNorm inherently assumes and enforces that the input distribution is centered near zero before applying the learned scaling.

When weights are restricted to the discrete set $\{-1, 0, 1\}$ via the `absmean` quantization function described in Equation (1), the linear transformation $y = Wx$ produces outputs that are naturally symmetric around zero if the input $x$ is zero-centered. The quantization process itself divides weights by their average absolute value $\gamma$, which acts as a dynamic scaling factor ensuring that the magnitude of weights adapts to the data distribution. If you were to include a bias term $b$ in this equation ($y = Wx + b$), you would force the output distribution away from zero. Since RMSNorm expects zero-centered inputs to function optimally (specifically because it lacks a subtraction step for centering), adding a bias would require RMSNorm's learned scale parameters $w_i$ to compensate aggressively for this offset. This creates an ill-conditioned optimization landscape where the model wastes capacity learning to counteract its own additive constants rather than learning meaningful feature representations.

Furthermore, from an expressivity standpoint within BitNet b1.58, the inclusion of **0** in the ternary weight set provides a mechanism that partially supersedes the need for bias-driven shifts in feature selection. As highlighted in Section 2 ("The Era of 1-bit LLMs"), BitNet b1.58 gains "explicit support for feature filtering" because weights can be exactly zero. This sparsity allows individual neurons to effectively turn off specific pathways without needing a negative bias to push activations below a threshold or positive bias to lift them above noise floors; instead, they simply do not contribute to the sum at all ($0 \cdot x = 0$). The combination of sparse connectivity (via zeros) and adaptive scaling (via RMSNorm's gain parameters and weight scaling $\gamma$) allows the model to represent complex distributions and offsets purely through multiplicative interactions and channel-wise scaling, rendering additive biases redundant and potentially detrimental to convergence stability in this specific quantization regime. Thus, removing biases simplifies the architecture while preserving representational power tailored to integer-only arithmetic and norm-based constraints.

### What explains the discrepancy between theoretical storage reduction and actual memory savings mentioned in Table 1?
Question:
Theoretically, moving from FP16 (16 bits) to Ternary (effectively ~2 bits if packed naively or ~log_2(3) bits theoretically) should yield massive memory savings. However, Table 1 shows BitNet b1.58 uses roughly half the memory of FP16 at small scales (e.g., 3B vs FP16), but not an order of magnitude less as pure bit-width suggests. The text notes that 'embedding remains full precision.' Could someone break down how much of the total memory footprint is actually occupied by embeddings versus linear layers? If embeddings are large and remain FP32/FP16, wouldn't they dominate memory usage at smaller model sizes (like 3B), thereby limiting the observed speedup/memory reduction compared to larger models where linear layers dominate?
Answer:
The discrepancy you observe between the theoretical $\sim 8\times$--$16\times$ reduction in weight storage (moving from 16-bit FP16 to effectively $\approx 1.58$ bits) and the actual $\approx 2\times$--$3.5\times$ memory reduction shown in Table 1 arises primarily because **not all parameters in the model are quantized**, and the relative contribution of unquantized components changes with model scale.

As explicitly stated in the "Memory and Latency" section of the paper, **"the embedding remains full precision."** In a standard Transformer architecture like LLaMA (which BitNet b1.58 mimics), the total parameter count is dominated by the feed-forward network ($\mathrm{FFN}$) and attention projection matrices ($\mathrm{nn.Linear}$ layers), which are converted to ternary values $\{-1, 0, 1\}$. However, the embedding layer maps discrete tokens to continuous vectors and typically retains FP16 precision to preserve fine-grained semantic distinctions at initialization and during early training stages. Since the embedding matrix size is proportional to $(V \times d)$, where $V$ is vocabulary size and $d$ is hidden dimension, it constitutes a fixed overhead that does not shrink with quantization.

At smaller model scales (e.g., 3B parameters), the ratio of embedding parameters to linear layer parameters is significantly higher than in larger models. Consequently, the unquantized FP16 embedding layer occupies a much larger fraction of the total memory footprint for a 3B model compared to a 70B model. This dilutes the overall memory savings; while the massive linear layers shrink by nearly an order of magnitude, they cannot compensate fully for the static size of the full-precision embeddings in smaller configurations. As noted in the paper's discussion on scaling trends, "the memory consumption follows a similar trend [to latency], as ... its memory proportion is smaller for larger models." This explains why the efficiency gap widens as you scale up: in a 70B model, the ternary linear layers overwhelmingly dominate the parameter count, making the fixed-cost FP16 embedding negligible by comparison, whereas in a 3B model, that fixed cost is substantial enough to limit the observed speedup to roughly $3.5\times$ rather than the theoretical maximum derived solely from weight bit-width reduction.
