\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Confusion regarding the 'no training' claim vs. the linear model optimization in FeatLLM
Question:
The abstract and introduction repeatedly emphasize that FeatLLM 'eliminates the need to send queries to the LLM for each sample at inference time' and is 'free from training constraints.' However, in Section 3.2 ('Inferring Class Likelihood via Rules'), the authors explicitly describe optimizing trainable weights $\mathbf{w}_k$ for a linear model using cross-entropy loss on the few-shot training samples. Does 'free from training constraints' strictly mean we don't need to *fine-tune* the massive LLM parameters (like in TabLLM), or am I misunderstanding that there is actually a standard supervised learning phase (gradient descent) happening on the downstream linear layer? If so, why isn't this considered 'training' in the context of their claims?
Answer:
Your confusion stems from a distinction in terminology common in modern deep learning literature, specifically the separation between **model fine-tuning** (updating the parameters of the foundation model) and **downstream head training** (optimizing a lightweight classifier). When the authors state that FeatLLM is "free from training constraints," they are explicitly contrasting their approach against methods like TabLLM, which require parameter-efficient fine-tuning (e.g., using LoRA or IA3) of the massive LLM itself. In TabLLM, "training" implies updating billions of parameters or even adapter layers attached to the LLM, which necessitates access to the model's internal architecture and gradients, often prohibiting the use of closed-source API-only models like GPT-3.5 or GPT-4.

In contrast, FeatLLM treats the LLM solely as a static feature generator that operates purely via in-context learning. The "training" phase you identified in Section 3.2 involves optimizing only the weights $w_k$ of a simple linear model defined by $\text{logit}_k^i = \max(w_k, 0) \cdot z_k^i$. Here, $z_k^i$ represents binary features derived from rules parsed from the LLM's output, and $w_k$ are scalar weights representing the importance of each rule. Optimizing these weights via gradient descent on cross-entropy loss is indeed standard supervised learning; however, because this optimization occurs on a tiny linear layer with negligible parameter counts (typically tens or hundreds of weights depending on the number of rules), it does not constitute "training" in the context of LLM deployment constraints. This linear layer can be trained instantly on a CPU without requiring GPU acceleration or specialized hardware access to an LLM's training pipeline.

Therefore, the claim holds true because FeatLLM decouples the heavy lifting from the LLM entirely. Once the few-shot rules are generated via API calls (which happens only once during feature engineering), no further interaction with the LLM is required for inference or for fitting the final predictor. The "training" mentioned in Section 3.2 is merely fitting a logistic regression-style classifier to transformed data, a process that imposes no restrictions on API access and avoids the prohibitive computational costs associated with fine-tuning large language models. This design allows FeatLLM to leverage powerful proprietary LLMs while maintaining an inference cost comparable to traditional tabular methods like Logistic Regression or XGBoost.

### How does the ensemble mechanism mathematically resolve conflicting rules generated by different LLM calls?
Question:
In Section 3.2, under 'Ensembling with bagging,' the paper states that predictions are made by averaging the probabilities $\mathbf{p}^i$ computed with each weight vector $\mathbf{w}[t]$ from $T$ trials. Since each trial involves a fresh LLM call with randomized temperature and demonstration ordering, Trial A might generate Rule Set X (which says 'Age > 50 implies Disease') while Trial B generates Rule Set Y (which says 'Age < 30 implies Disease'). When we average the final probabilities, how does the model reconcile these contradictory logical conditions? Are we assuming that valid rules will appear consistently across trials while noise averages out, or is there a specific aggregation logic for the binary features themselves before probability calculation?
Answer:
Your intuition regarding the nature of the ensemble is largely correct: the FeatLLM framework relies on the statistical principle that **valid, semantically meaningful rules tend to emerge consistently across stochastic trials**, while spurious or noisy rules appear inconsistently and thus average out. There is no explicit logical reconciliation engine that resolves contradictions like "Age > 50" versus "Age < 30" at the rule level before probability calculation; instead, the resolution happens implicitly through the weighted voting mechanism of the downstream linear model.

When Trial A generates a rule implying "Age > 50" and Trial B generates "Age < 30," these are treated as distinct binary features in their respective trials. During the ensemble phase described in Section 3.2, the system computes a probability vector $\mathbf{p}^i[t]$ for each trial $t$ independently using Equation (2): $\text{logit}_k^i = \max(\mathbf{w}_k[t], 0) \cdot \mathbf{z}_k^i[t]$. Here, $\mathbf{z}_k^i[t]$ represents the binary satisfaction of rules *specific to that trial*, and $\mathbf{w}_k[t]$ represents the weights learned for those specific rules. If a rule is genuinely predictive (e.g., "Age > 50"), it will likely appear in many trials with a positive weight, contributing constructively to the logit. Conversely, if a rule is an artifact of noise or a contradiction (e.g., "Age < 30" appearing rarely or only in trials where it correlates poorly with the label), its associated weight will be small or zero after optimization on the few-shot data, or its contribution will be diluted when averaged across $T$ trials.

The final prediction is simply the arithmetic mean of these probabilities: $\bar{\mathbf{p}}^i = \frac{1}{T} \sum_{t=1}^T \mathbf{p}^i[t]$. This process leverages what the authors describe as **self-consistency** (referencing Wang et al., 2022); rules that are robust and aligned with true causal relationships will stabilize across different random seeds, temperatures, and demonstration orderings, accumulating higher aggregate probability mass. Inconsistent rules act as variance-reducing noise. Therefore, the "reconciliation" is not a symbolic logic operation but a probabilistic consensus where signal dominates noise through repetition and weighting.

### Clarification on why projecting weights into a positive subspace ($\max(\mathbf{w}_k, 0)$) is necessary
Question:
Equation (2) defines the logit as $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$. The text explains this ensures features 'do not reduce the likelihood of a class.' I understand this prevents negative weights from lowering the score of a class when a rule is met ($\mathbf{z}=1$). However, doesn't this constraint prevent the model from learning that satisfying a specific rule should actually *decrease* confidence in a class (e.g., if Rule A is 'Patient has healthy blood pressure', meeting this rule should lower the probability of having hypertension)? By forcing all weights to be non-negative, aren't we losing expressivity and potentially hurting performance if some rules are inversely correlated with their target class?
Answer:
Your intuition regarding the loss of expressivity is well-founded in standard linear models, where negative weights are essential for representing inverse correlations (e.g., high blood pressure reducing the likelihood of being healthy). However, in the specific architecture of **FeatLLM** described in the paper, the constraint $\max(\mathbf{w}_k, 0)$ is not a limitation on the model's ability to learn that a rule should decrease a class's probability; rather, it is a design choice driven by how the rules themselves are constructed and interpreted.

The key lies in the semantics of the features $\mathbf{z}_k^i$ generated by the LLM. As stated in Section 3 ("Inferring Class Likelihood via Rules"), these binary features indicate whether a sample satisfies a rule derived specifically for class $k$. The authors explicitly frame this as "deducing decisive rules to distinguish classes." Consequently, if a condition logically implies that a sample does *not* belong to class $k$ (e.g., "healthy blood pressure" implying "no hypertension"), the LLM is instructed to generate that rule under the target class where it applies (e.g., the "No Hypertension" class), or simply not generate it for the "Hypertension" class. The framework relies on the LLM's prior knowledge to ensure that every generated rule $\mathbf{r}$ for class $k$ represents evidence *supporting* membership in $k$. Therefore, activating such a rule ($\mathbf{z}=1$) should inherently increase or maintain confidence in class $k$, never decrease it.

By enforcing non-negative weights $\mathbf{w}_k \geq 0$, the model treats every activated rule as additive evidence toward its associated class. If a specific feature condition were truly negatively correlated with class $k$, FeatLLM's prompting strategy expects the LLM to either formulate that condition as a supporting rule for a competing class or exclude it entirely from the set of rules for class $k$. The "expressivity" lost by forbidding negative weights is compensated by the richness of the rule generation process itself. If we allowed negative weights, we would risk interpreting noise or spurious correlations as deliberate negations within a single class's logic, potentially destabilizing learning in low-shot regimes where data scarcity makes distinguishing true signal from noise difficult.

Furthermore, Equation (2) operates within an ensemble framework involving bagging (Section 3.2). Even if an individual trial generates a slightly imperfect rule set, averaging probabilities across multiple trials smooths out inconsistencies. The primary mechanism for handling inverse relationships is not flipping signs within a single linear projection but rather assigning contradictory evidence to different classes via distinct rule sets. Thus, while mathematically restrictive compared to unconstrained logistic regression, this constraint aligns with the paper's core premise: leveraging LLMs to act as expert feature engineers who pre-filter and semantically orient features so that their mere existence supports their designated hypothesis.

### Does using $exec()$ on LLM-generated code pose security risks or reliability issues with variable scoping?
Question:
In Section 3.1 ('Parsing rules for feature generation'), the authors mention leveraging an LLM to generate Python code which is then executed using Python's `exec()` function to convert raw data into binary features based on natural language rules. Given that LLM outputs can contain syntax errors or unexpected variable names (even with formatting instructions), how does `exec()` handle cases where a generated rule references a column name that doesn't exist in the current dataframe slice during execution? Also, since `exec()` runs arbitrary code strings, how do they ensure safety against potential injection attacks if they ever apply this to user-submitted data descriptions?
Answer:
Based on the methodology described in Section 3.1 ("Parsing rules for feature generation") of the FeatLLM paper, the system handles potential execution errors and security concerns primarily through a combination of LLM-driven code generation, strict prompting constraints, and a statistical ensemble approach rather than low-level sandboxing or exception handling logic.

Regarding your question about variable scoping and missing columns, the paper does not describe implementing explicit error handling (like try-except blocks) within the `exec()` call to catch `NameError` exceptions when a generated rule references a non-existent column. Instead, the framework relies on the LLM's reasoning capabilities guided by specific prompt instructions to prevent such errors from occurring in the first place. As noted in Section 3.1, the prompt explicitly instructs the LLM to "refer to the type of each feature in the basic information description part to avoid type mismatches," and the initial reasoning phase encourages the model to infer causal relationships before generating rules. This design aims to ensure that only valid feature names present in the input dataframe are referenced in the generated Python code. If an invalid reference were to slip through due to LLM hallucination, the resulting `exec()` call would raise a runtime error; however, the paper's experimental setup implies that these failures are rare enough or managed implicitly because they do not report manual error recovery mechanisms. The robustness against occasional incorrect rules is instead achieved later in the pipeline through **ensembling**. As detailed in Section 3.2 ("Ensembling with bagging"), if an LLM generates an incorrect or nonsensical rule (which might fail execution or simply not correlate with the target), this "noise" is treated as a weak learner. Since FeatLLM repeats the process $T$ times (set to 20 in experiments) with randomized sampling and high temperature settings, correct rules generated in other trials compensate for erroneous ones, effectively diluting their impact on the final averaged prediction probabilities $\mathbf{p}^i$.

Concerning security risks such as code injection via user-submitted data descriptions, the paper does not explicitly discuss deploying sandboxed environments or restricting `exec()` permissions. The safety assumption appears to rest on two pillars: first, that `exec()` is invoked only on code strings generated by a trusted LLM API (GPT-3.5) based on controlled prompts containing schema definitions and few-shot examples; second, that the scope of execution is strictly limited to transforming tabular data into binary features for internal model training, rather than executing arbitrary commands on user infrastructure. The "user-submitted" aspect mentioned in your question refers to natural language descriptions of features provided as part of the prompt context (the "Basic information description" section), not executable payloads injected directly into code slots. The framework assumes that by constraining the output format via "Response instruction" sections—forcing specific Python syntax patterns—the risk of malicious payload generation is minimized by design. Ultimately, FeatLLM prioritizes data efficiency and performance over rigorous security auditing of generated code, relying on the fact that downstream models are simple linear regressors trained on binary features derived from this process, which limits any potential damage even if a rogue rule executes successfully (e.g., producing a constant feature vector).

### Is there an upper bound on feature dimensionality imposed by the fixed number of rules per class?
Question:
The paper mentions handling datasets with over 100 attributes by using bagging to fit within prompt limits. However, Equation (2) and Section 3.2 imply that for every class $c$, we generate exactly $R$ rules (where $R=10$ according to Section 3.1). If we have a multi-class problem with $C=5$ classes, does this mean our final feature vector size is strictly capped at $5 \times 10 = 50$ dimensions regardless of whether we have 10 or 100 original input features? If so, how does reducing hundreds of original features down to just dozens of derived binary rules affect information retention compared to methods like TabPFN that might preserve more granular interactions?
Answer:
Your interpretation of the dimensional cap is partially correct regarding the *fixed* output of a single rule-generation trial, but it misses the critical role of **bagging** and **ensembling** described in Section 3.2, which allows the framework to scale beyond this limit and retain information from high-dimensional inputs.

While it is true that Equation (2) defines the intermediate feature vector $\mathbf{z}_k^i$ for a single trial as having a dimensionality of $R$ (where $R=10$ rules per class), this represents only one "weak learner" in an ensemble. The paper explicitly states in Section 3.1 and Section 3.2 that for datasets with over 100 attributes (like "Communities" or "Myocardial"), the authors employ **feature bagging**. In this process, the LLM is prompted with a *subset* of the original features rather than all of them simultaneously. By repeating this process $T$ times (the paper uses $T=20$ ensembles), each trial generates a distinct set of 10 rules based on different subsets of the original $d$ features. Consequently, while any single model instance operates on roughly 50 dimensions ($C \times R = 5 \times 10$), the full ensemble aggregates predictions from these multiple trials, effectively covering a much larger portion of the original feature space across the aggregate system.

Regarding information retention compared to methods like TabPFN, FeatLLM does not attempt to preserve every granular interaction in a dense vector representation; instead, it relies on **prior knowledge filtering**. As noted in Section 3.2 ("Reasoning instruction"), the LLM is guided to infer causal relationships before generating rules, which inherently filters out uninformative or spurious features. The paper argues in Section 4.2 that this mechanism makes FeatLLM robust against noise; when spurious correlations were artificially added to datasets, FeatLLM suffered minimal performance degradation because the LLM rarely generated rules based on irrelevant columns (only $1\text{--}2\%$). Therefore, rather than losing information by compressing hundreds of features into dozens of binary flags, FeatLLM discards low-signal noise early in the pipeline, transforming raw data into high-confidence binary indicators that are weighted by a downstream linear model (Eq. 2). This approach trades exhaustive feature preservation for high signal-to-noise ratio features derived from the LLM's internal knowledge base, which proves particularly effective in few-shot regimes where preserving every interaction might lead to overfitting rather than better generalization.

### Why did FeatLLM fail on spurious correlations when columns came from closely related datasets?
Question:
In Section 4.2 ('Effect of adding spurious correlations'), Figure X shows that FeatLLM handles random noise columns well but degrades when columns are taken from 'closely related data' (specifically mixing Adult and Heart datasets). The authors suggest this happens because FeatLLM relies on prior knowledge which might misinterpret causal relationships between semantically similar but task-irrelevant columns. Could someone elaborate on why an LLM's prior knowledge would lead it to confidently generate false-positive rules for these specific cases? Wouldn't few-shot examples usually override prior knowledge if they clearly contradict it?
Answer:
The degradation of FeatLLM when columns are drawn from closely related datasets (like mixing Adult and Heart data) stems from the inherent tension between the model's reliance on **semantic priors** versus **statistical evidence** in low-shot regimes. Unlike random noise, which lacks semantic meaning and is easily dismissed as irrelevant by an LLM's world knowledge, columns from related datasets possess plausible semantic connections to the target task. For instance, features like "Age," "Income," or "Cholesterol" exist in both the Adult and Heart datasets with similar names and definitions. When the LLM performs its first reasoning step—inferring causal relationships based solely on prior knowledge—it retrieves associations that are generally true in the real world (e.g., "older age correlates with health issues") but may be spurious or misleading for the specific dataset configuration at hand.

The core issue is that few-shot examples alone cannot always override these strong priors when the signal-to-noise ratio is low or when the spurious correlation mimics a genuine causal mechanism. In a standard few-shot setting with only $k$ samples (where $k$ is small, e.g., 4 to 8), statistical patterns derived from the data are weak and prone to variance. If an LLM generates a rule like "If Age > 50 then predict Positive," this rule aligns perfectly with its pre-trained medical knowledge *and* happens to correlate slightly with the target variable in the limited training set due to chance or dataset overlap. Consequently, the LLM confidently generates this rule because it satisfies both its internal knowledge base and the sparse empirical evidence, failing to distinguish between a true causal driver and a coincidental correlation amplified by shared semantics.

Furthermore, FeatLLM's architecture explicitly prioritizes prior knowledge in its two-step prompting design. The first step asks the LLM to reason about feature-task relationships *without* looking at examples, establishing a strong hypothesis based on semantics before seeing any data. When columns are semantically similar but task-irrelevant, this initial hypothesis acts as a powerful attractor for attention mechanisms within the model's latent space. The subsequent few-shot examples serve more to refine or confirm these pre-existing hypotheses rather than correct them, especially if the examples happen to support the spurious trend (which is highly probable when mixing related datasets). Therefore, unlike random noise which breaks semantic coherence and triggers rejection by the LLM's safety filters or logic checks, semantically coherent spurious features reinforce false positives because they appear "reasonable" to both the prior knowledge engine and the limited statistical evidence provided by few-shot learning. This highlights a known limitation where inductive biases derived from massive pre-training can become detrimental when they conflict with specific domain nuances not captured in general text corpora.
