# FP8 Transformers Made Practical – Block Quantisation + Random Orthogonalisation Yields Petaflop Speed & Accuracy

## What problem does this solve?

Modern transformers still find themselves stuck behind attention – it needs every token pair in a sequence, so those quadratic cost tensors grow rapidly when you add context length or widen model width. On today’s GPUs the compute pattern is dominated by two ideas that can be optimised yet are easy to overlook:

* **Data movement** – most prior work keeps intermediate matrices (`S`, `P`) in global memory.
* **Precision** – Hardware now offers *FP 8* Matrix‑Multiply units that roughly double the raw GOPS over former *FP 16* units, but naïve quantisation simply explodes your numerical errors when a handful of huge values appear (“outliers”) ❤

If you could get rid of the intermediate reads/writes *and* harness duplicated arithmetic power without losing accuracy, you would get a real boost both upfront FLOP count and downstream quality.


## The FlashAttention‑3 idea stack

FlashAttention‑3 integrates several layers of GPU‑specific optimisation drawn straight from Hopper’s new feature set:


| Layer | Idea | Benefit |
|-------|------|---------|
| Memory | Using *Tensor Memory Accelerator* (TMA) loads directly into shared memories while masking latency – swapping producer warps (the loaders) against consumer warps (the matmuls)+softmax logic through warp‑specialisation | Keeps SM emotes idle time hidden without extra copy passes |
| Compute | Overlap a GEMM stage (`Q × Kᵀ`) with softmax computation on the *next* batch thanks to asynchronous WGMMA execution | Each token row spends fewer cycles idle |
| Precision | Run everything through WGMMA’s *FP 8 target*, supplied two additional adaptations |
|   | • **Block quantisation** – each `Q`, `K`, `V` tile gets its own scaling factor |
|   | • **Incoherent processing** – pre‑multiply both `Q` & `K` by a cheap random orthogonal matrix before quantising |

And all together you plate an algorithm that runs straight through one persistent kernel that does *no materialise* intermediate matrices – what once took PBreads time can finish almost instantly.


## Big picture bandwidth savings

Typical transformer heads need two matrix multiplies per query row (`Q×Kᵀ` → scores ; scores × `V`). In flash form those two multiplies happen fully fused *inside shared memory*, removing any read/write cycle back-to-back across GDRAM.



Instead you see something along these lines (*run your head alive*) :

```
load Q[i]         → // async TMA
load K[j], V[j]   → // async TMA
WGMMA(Q[i], K[j]ᵀ)   // async matmul → scores
// -- while scores hidden in reg/
softmax(scores + reduce⍈ // simple rowwise normalising
WGMMA(softmax_scores × V[j]) // next matmul → partial output    
// repeat until key blocks exhausted
final rescale           // divide accumulated sums
write output O[i]
```

Notice how every kernel launch never touches global mem twice.



## Why Block Quantisation matters

Up‐to‑date manifolds treat data uniformly – one scalar stores how the whole head should map int↔fp… When your head contains just a handful of absurdly huge activations (*≈10× larger than most entries*), one single scale tears everyone apart : massive rounding offsets leak later into softmax exponentials → wrong probabilities → wrong gradients.


Block‑by‑block scalars let each tile adapt itself:


```math
S_{block} = Q_{block}\cdot K_{block}^{T}\\[4pt]
scale(Q)   = \frac{q_{\max}}{127},    % per block \\
scale(K)   = \frac{k_{\max}}{127}
```

Quantising thereafter needs almost none extra bandwidth—because flash already loads tiles incrementally—the tiny scale array costs nothing compared against most praxis.



## Incoherent processing dispels outliers

How does a bright dagger fix it *without changing linear algebra*? Put simply,

```math
Q' = Q\,M ,   K'= K\,M .
```

Selecting an orthogonal matrix `M` preserves dot products due directly depening from maths


```math
Q'\,(K')^{T}=QM\,M^{T}\!K^{T}=QK^{T}.
```

Therefore final self-attention remains untouched while composition marks allow every element inside `Q·Kᵀ` roam more uniformly among bits — so fewer amplitudes hit extreme mantissa limits when forced into f∈[−128,+127].  
Blend‑in cost comes almost for free ‑ it’s just an inexpensive Hadamard transform (O(d log d) operations), easily fused into any rotary embedding or projection routine.
