# Crafting Rules With Language Models  
## The Two–Step Reasoning Process  

Large language models have been shown capable of answering surprising questions without ever being trained directly on that task.  
A recent line of work has turned this ability into *feature engineering* for low‑shot tabular problems—calling it **FeatLLM**—and it hinges on a single idea that seems simple but is surprisingly powerful: *first ask an LLM what it knows about how columns relate to one another, then let it use a handful of labeled rows to turn those ideas into concrete decision rules.*

Below I unpack how FeatLLM builds this two‑step chain‑of‑thought prompt and why it matters when you only have a handful of samples.



--------------------------------------------------------------------

## Why Turn an LLM Into a Human‑Like Rule Writer?

Imagine you’re given a small patient record dataset and asked “Does this person probably suffer from chronic heart failure?”  
Without many labeled examples you risk inventing *spurious correlations*—for example you might mistakenly think “if blood glucose > 150 mg/dL → yes” purely because one lucky row had both high glucose and heart failure even though glucose isn’t related clinically.



The trick behind FeatLLM is **separating prior knowledge from data‑driven evidence**:

| Prior Knowledge | Few‑Shot Data |
|-----------------|---------------|
| What doctors believe about risk factors | Concrete rows we hand‑label |
| How numerical thresholds normally behave | Which thresholds actually work here |

If an LLM first thinks aloud about **generic causal links** among columns based only on what it has read during pre‑training—and *doesn’t* look at any examples yet—it will naturally ignore irrelevant features.  
Later, when you give it just eight rows expressed in natural language, it can refine those links into *explicit logical conditions* that distinguish each class.



--------------------------------------------------------------------

## Prompt Design – Three Blocks That Work Together  

In practice FeatLLM structures its query into three self‑contained blocks so that every step stays clear enough for the model *and* easy enough later to turn back into executable code.



### 1) Basic Information Description  

This is what you always give an LLM before asking any question:\n\n
- **Task statement** formulated as a clear yes/no question.\n\n
- **Column catalogue** – each feature name followed by its type (numeric versus categorical) and optionally its definition.\n\n
- **Serialized examples** – chosen few labeled rows written out word‑for‑word so the model sees exactly what constitutes “an answer.”  
For instance:

```
Age is 65., Smoker is Yes., HeartRate is 110., Answer: Yes
Age is 30., Smoker is No., HeartRate is 72., Answer: No
```



### 2) Reasoning Instruction – The Two–Step Chain  

A *chain‑of‑thought* style cue tells the model how **to think before talking**:\n\n  

**Step 1 – Prior Knowledge Check:**  
> “Think normally about how each feature relates to heart failure before looking at any training rows.”

This forces the model’s first draft answer onto *generic causality* (“high age tends towards failure”, “smoking increases risk”), ignoring random overlaps in our limited data.



**Step 2 – Data‑Guided Refinement:**  
> “Now look at these eight rows together with your prior thoughts and write ten logical rules that would tell whether the answer should be ‘Yes’ or ‘No’.”

Two things happen here immediately:\n\n - Existing patterns become anchored by concrete evidence.\n - Because only ten rules are requested per class, everything has room for meaning while keeping later prompts short.



### 3) Response Instruction – Enforce Parseable Form  

The last block tells the model exactly **how much grammar matters**:\n\n  

```text
Class Yes:
    Rule 1 = …
    Rule 2 = …
    …
Class No:
    Rule 1 = …
```

By giving exact wording (“Class …”, “Rule … =”), FeatLLM ensures people who implement downstream parsers won’t deal with special cases where apostrophes or pluralities change rendering.



--------------------------------------------------------------------

## From Natural Language Rules To Binary Features  

Once you receive those neat rule lists you cannot just paste them straight into code—humans who read midway often miss subtle modifiers (“greater than” vs “more than”).  
Instead FeatLLM forwards *the text back* into another request whose sole purpose is code generation:\n\n
```python
def check_rules(row):
    #Parsed booleans below follow pattern produced earlier.
    return (
        row["Age"] >70 and row["Smoker"]=="Yes",   # Rule 1 (“Yes”)
        row["HeartRate"] >120                      # Rule 2 (“Yes”)
        ...
    )
```

Executing those tiny snippets produces a matrix `Z` where `Z[i,k]` equals `1` if row *i* satisfies any rule assigned to class *k*. In computational terms this becomes a very small linear classifier whose trainable weights are forced nonnegative, meaning “satisfied → more likely”.

Because all parsing happens through automatic code generation fed back into GPT itself, there’s almost no manual transcription error.



--------------------------------------------------------------------

## Why This Two–Step Route Is Superior  

1. **Fewer Spurious Rules** – By asking the model first what it knows globally you force it *away* from randomly correlated columns present among your few samples.\n\n2. **Tight Prompt Size** – Fixing exactly ten rules per class keeps inputs shorter than many other approaches which serialise all original columns.\n\n3. **Robustness Through Bagging** – FeatLLM repeats the whole process several times using different random shuffles and temperatures, creating distinct sets of rules which then get ensembled normally (probabilities averaged). This encourages consistency (“rule writes itself across trials”), much like how humans double‑check calculations.\n\n4. **Low Inference Cost** – After these offline queries you’re left with a tiny linear model running locally everywhere. No ARI’s shine every time you read a new record!\n\nSeveral ablation studies in their work showed dropping either Step 1 or Step 2 degrades scores noticeably—exactly what you'd expect if either the global perspective or data grounding was missing.

## Putting It All Together – A Quick Walkthrough  

Below’s an outline you’d send via GPT‑3.5 API (pseudo‑text cleanly showing tone used in FeatLLM):

```
Task:
“Does this patient's record indicate chronic heart failure? Yes or No?”

Feature descriptions:
• Age – numeric
• Smoker – categorical {Yes, No}
• HeartRate – numeric
• BloodGlucose – numeric
…

Examples (8 shots):
• Age is 68., Smoker is Yes., HeartRate was 117..., Answer: Yes.
…
(7 more lines)

Reasoning instruction:
First think generally about these features' relation with heart failure without looking at any examples.
Then look at these eight rows together with your thoughts above,
and write exactly ten logical conditions under Class Yes,
and ten under Class No,

Response instruction:
For each class write Class Yes:, Class No:. Then list Rule # = condition...
Make sure conditions match syntax accepted by Python parser.
```

When GPT finishes you’ll see something like:

```
Class Yes:
Rule 1 = Age > 65 AND Smoker == "Yes"
Rule 2 = HeartRate > 110 AND BloodGlucose > 140
...
Class No:
Rule 1 = Age < 50 OR Smoker == "No"
...
```

Those entries are now fed back through another prompt asking GPT to translate them into an `if …:` Python function—a reliable executor.


--------------------------------------------------------------------

## Takeaways For Practitioners  

* If your budget allows only surface‐level access (`API`s) without gigantic training runs, turn your LLM into an *expert linguist* who writes human interpretable decision logic instead of acting as black box predictor.*

* Keep your prompts modular: basic definition block → reasoning instruction → response formatting.*

* Even though ten rules seemed arbitrary at first glance—you’ll find validating them shows little loss while keeping everything well within token limits.*

* Finally remember variable keeping across runs leads to ensemble improvements without needing another forward pass through GPT per new data point.*

With these points ironed out work begins quickly—the rest consists mainly stylistically polishing code functions generated by GPT.”
