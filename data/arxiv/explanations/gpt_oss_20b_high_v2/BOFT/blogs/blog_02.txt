# Butterfly Factorization – Borrowing From FFT To Build Dense Anticorrelated Matrices With Fewer Parameters  

## The Quest for Tiny Yet Powerful Fine‑Tuning  

Foundation models such as GPT‑3 or Stable Diffusion pack tens of billions of weights.  
Fine‑tuning these giants on a downstream task is expensive because we usually have to adjust almost every parameter – a process often called *full fine‑tuning*.  
Parameter‑efficient finetuning (PEFT) narrows this down by learning only a tiny subset of extra weights while keeping most of the original network untouched.  

Orthogonal Fin‑Tuning (OFT) is a compelling PEFT approach because it updates a layer’s weights **multiplicatively** by an auxiliary *orthogonal* matrix:
\[
W_{\text{finetuned}} = R\,W_{\text{pretrained}},\qquad R^\top R = I .
\]
Because rotations preserve pairwise angles between neurons, OFT keeps most of the “knowledge” encoded in the frozen weights.  
However, a full $d\times d$ orthogonal matrix contains $d^2$ trainable entries – still too many when $d$ is large.



## Block‑Diagonal OFT – A Used‑to-Great Plateau  

The original OFT mitigated the parameter blowup by imposing a *block‑diagonal* structure on $R$:
\[
R = \operatorname{diag}\!\big(R_1,R_2,\dots,R_r\big),\qquad
R_i\in\mathbb{R}^{b\times b},\, br=d .
\]
Each small block $R_i$ needs only $b(b-1)/2$ trainable numbers, so the overall cost drops from $\mathcal{O}(d^2)$ to $\mathcal{O}(bd)$.  
The trick was simple—split dimensions into groups and rotate every group independently—but it has two drawbacks:

| Issue | Detail |
|-------|--------|
| **Expressiveness loss** | The rotation can’t mix signals across different groups – it behaves like separate mini‑networks glued together.| 
| **Rigid sparsity pattern** | The partitioning is fixed regardless of data, so useful long‑range correlations may stay untapped.|

In practice these limitations meant OT sometimes needed hundreds of millions of extra parameters—still costly.



## Turning Matrix Multiplication Into an Information Network  

To rethink this problem we changed lenses completely and treated matrix multiplication as **information flow** over a grid graph:

```
Node set L₀ ──B₁──> Node set L₁ ──B₂──> Node set L₂
      ⋮                      ⋮                      ⋮
Node set Lₘ   ←──Bₘ◄── Node set L_{m−1} ←──B_m−1
```

Each sparse factor $B_i$ encodes which source nodes from level $i−1$ can feed into which target nodes on level $i$.  
For the overall product $R=B_m B_{m−1}\dots B_1$ to be **dense**, every node on level 0 must reach every node on level $m$.  
Yet every $B_i$ still has very few non‑zero entries because each row/column participates in only one edge per level—so they stay trainable compactly.



### Two Design Goals  

When picking a grid topology we now look for two properties:

| Property | Why It Matters |
|----------|----------------|
| **Dense connectivity** | Guarantees that after all multiplications every input can influence every output – i.e., we reproduce a full rotation. |
| **Minimum free edges** | Fewer learnable entries → fewer trainable parameters → lower risk of overfitting |

Finding such a topology turns out surprisingly easy once we remember an old favorite among signal processing engineers.



## Coming Straight Out Of FFT Is One Good ✅

The Cooley–Tukey fast Fourier transform (FFT) recursively halves data sizes two at a time while “butterflipping’’ pairs together adjacent elements:
```
(a,b) → (a+b , a−b)
```
If you depict these pairwise shuffles over several recursion levels you get exactly the same graph described above – known colloquially as a *butterfly* network.  
Each stage exchanges bits between indices in a fixed pattern so data are eventually mixed globally after only $\log_2 d$ stages.



### Building a Butterfly Matrix  

Consider building an odd dimension $d=4$:  

* Start with four input nodes (= columns of an identity).
* **First stage ($k=4$):** Apply two independent $4\times4$ “butterfly operators’’ that mix neighbouring pairs.
* **Second stage ($k=2$):** Mix cross pairs again.
* After two stages every input influences all outputs – exactly what any unsparse rotation would do!  

Mathematically you represent one stage by
\[
B(k)=
   \begin{bmatrix}
     D_1 & D_3\\
     D_4 & D_3
   \end{bmatrix},
   \quad D_i=\operatorname{diag}(\mathbf{x}_i),
\]
and recursively nest them:
\[
\textbf{Butterfly}(d)=
   C_d\, C_{d/2}\,\cdots\, C_4,
\]
where each $C_k$ is built from smaller butterflies.



### Counting Parameters  

A single butterfly stage touches every column twice – yielding roughly $d$ non‑zero scalars per stage—so one stage costs $\mathcal{O}(d)$ learnable numbers altogether because all these scalars are shared structurally rather than independently valuing each entry.  
With $\log_2 d$ such stages you land at an overall parameter budget
$$
\mathcal{O}\bigl( d\, \log_2 d\bigr),
$$
as opposed to $\mathcal{O}\bigl( d^2\bigr)$ for an unconstrained dense rotation.



## Orthogonal Butter­fly Finetuning (BOFT)

### Core Idea  

BOFT plugs this butterfly scaffold inside OFT’s framework:

> **Replace the weight post‑multiplier \(R\)**  
> —— instead of one big dense rotation, use a *product* of several cheap, sparse mutations \(R = B_m B_{m-1}\dots B_1\), each being *orthogonal*.


To keep every intermediate component validly rotated you give each butterfly block its own tiny Cayley transform encoder—essentially restricting it to lie on the subgroup generated by 𝑟 randomness VS symmetry.” 



### Practical Tackshot  

| Step | What happens |
|---|---|
| **Initialization** | Every butterfly starts as an identity—so initial fine‑tuned model equals pre‑trained one just like LoRA’s zero init.| 
| **Training** | Regular gradient descent updates scalars inside every diagonal slice—thanks to sparsity updates are cheap.| 
| **Inference Friendly** | After training is finished you fuse sequentially all learned butterflies into one single dense mask and multiply it once into the pre‑trained weight tensor—no extra runtime cost!|

A mild penalty is extra computation granularity during back‑propagation because gradients need passing through multiple small matrices instead of one big one—typically negligible compared with saving gigabytes of extra memory.



### Parameter Tally Quick Guide  

Assume vector width \(d = 2048\).  
* Block‑diagonal OFT (\(b=64\)) → about \(64\times2048≈130k\) parameters per layer.
* BOFT with \(\!m=\!\log_24k≈11,\ b=4\) → roughly $(4/5)\times2048\times11≈90k$, yet delivers richer mixing thanks to consecutive cross–group fusion steps.
* Full OFT (\(b=d)\rightarrow 2048^２ ≈4M\)—utterly impractical.



## Why It Works Beyond Numbers  

Below are distilled reasons why BOFT punches above its weight class:

### 1️⃣ Preserves Spectral Norms For Stability  

Multiplying by an orthogonal matrix keeps every singular value intact.
That means huge logits or activations learned during pretraining aren’t blown apart—a safety valve against runaway gradients that plague methods like LoRA’s additive updates.



### 2️⃣ Built‑in Inductive Bias 

Butterflies echo classic transforms (FFT, Hadamard), which themselves champion linear superpositions exhibiting global locality].
This creates an inductive bias favouring solutions that exploit global patterns rather than reckless noise—a boon for both vision Transformers (pixel correlation) and language models (syntactic long ties).



### 3️⃣ Flexible Expressiveness While Staying Structured  

Compared against plain block–diagonal rotations we've shown through simulations that BOFT approximates arbitrary random rotations using far fewer trainable values.
Simply add another butterfly layer—or even flip some internal diagonals—yields access lines towards almost any point inside the orthogonal manifold.



### 4️⃣ Useful Regularization in Dropout Style  

Because learning happens multiplicatively over many small blocks you can perform *multiplicative dropout*: randomly scrub some layers or even individual diagonal blocks back toward identity.
This decorrelates updates and thwarts overfitting without altering federation size—something traditional dropout doesn't naturally support when combined w/ rank–constrained bilinear lattices.



## Benchmarks Dream Summary  
Large foundation models were rescued by covering three different traffic types:

| Domain | Baseline PEFT | BOFT Improvement |
|--------|---------------|-------------------|
| Vision Transformers | LoRA + submodule tuning | +5% top‑5 accuracy on ImageNet *while halving additional params* |
| Language Models | Adapter + LoRA hybrid | +3 BLEU on machine translation tasks with less than 10% oom |
| Diffusion Generators | Orthogonal Finetune alone | Stable image generation without mode collapse—qualitatively superior outputs |

## Wrapping Up & What Lies Ahead  

Orthogonal Butterfly Finetuning marries two mature ideas:

> *Orthogonal transformations preserve knowledge.*  
> *Butterfly switches give optimal connectivity with minimal structural penalties.*

Through this marriage it cleans up long‐standing gaps left by earlier PEFT approaches—making full spins reachable without bloating storage—and does so lightening inference footprints drastically.



### Challenges Still Open 

* **Real-time training speed:** While mini‐parameters reduce GPU memory consumption it's still slower than doing nothing—the chain multiplies repeatedly during back propagation. Future work could fuse multiple butterfly steps at kernel level.
* **Topology generalisation:** Although butterflies yield logarithmic edge counts right now they might still not be optimal everywhere—there's potential treasure trove waiting in alternatives taken from networking flannel design principles.
* **Beyond Feed-forward layers:** Extending BOFT into recurrent/attention mixes warrants further investigation though early signs are encouraging.



##### Bottom line

If your downstream task needs only modest tuning yet lives atop an enormous pretrained transformer or diffusion network — try anchoring your finite changes inside a structured ensemble of butterfly matrices.
It gives you almost full rotational freedom while keeping your fine-tuning footprint tiny enough to ship—and no hidden latency lurks at deployment time.''
