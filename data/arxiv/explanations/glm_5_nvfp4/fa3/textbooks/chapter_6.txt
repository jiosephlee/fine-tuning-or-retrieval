Chapter 6: # Intra-Warpgroup Overlapping: GEMM-Softmax Pipelining

# The Sequential Dependency Problem in Attention Computation

To understand the motivation for intra-warpgroup overlapping, we must first examine the inherent sequential dependencies that exist within the attention algorithm's inner loop. In the standard formulation of FlashAttention, each iteration of the main loop processes a block of the key and value matrices, computing attention scores and accumulating results. The operations within each iteration follow a strict ordering that presents challenges for parallelization.

Consider the sequence of operations required to process a single block. First, a matrix multiplication computes the attention scores $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^T$, where $\mathbf{Q}_i$ is a tile of the query matrix and $\mathbf{K}_j$ is a tile of the key matrix. This first GEMM operation produces scores that must then undergo softmax normalization. The softmax operation, specifically the local softmax variant used in FlashAttention, requires computing the row-wise maximum and the exponential of the scores. Critically, this softmax computation depends entirely on the output of the first GEMM—the scores $\mathbf{S}_i^{(j)}$ must be available before any exponential or normalization can proceed.

Following the softmax, a second GEMM multiplies the normalized attention weights $\widetilde{\mathbf{P}}_i^{(j)}$ with a tile of the value matrix: $\mathbf{O}_i = \mathbf{O}_i + \widetilde{\mathbf{P}}_i^{(j)} \mathbf{V}_j$. This second matrix multiplication cannot begin until the softmax has produced $\widetilde{\mathbf{P}}_i^{(j)}$. Thus, we observe a chain of dependencies: the first GEMM must complete before softmax can begin, and softmax must complete before the second GEMM can begin. In the baseline FlashAttention-2 algorithm, explicit wait statements serialize these operations, forcing each to complete before the next can commence.

This serialization is problematic because it leaves hardware resources underutilized. While the Tensor Cores are busy computing one GEMM, the multi-function units that handle exponential calculations sit idle. Conversely, during softmax computation, the powerful Tensor Cores remain dormant. The sequential nature of these dependencies, when executed naively, creates a situation where specialized hardware units take turns being active, rather than working concurrently to maximize throughput.

# The Throughput Gap: Understanding Hardware Asymmetry

The imperative to overlap GEMM and softmax operations becomes clear when we examine the stark throughput disparity between these two classes of operations on modern GPUs. The H100 SXM5 GPU exemplifies this hardware asymmetry. For FP16 matrix multiplication operations, the H100 delivers an impressive 989 TFLOPS of computational throughput. This massive number-crunching capability is made possible by the Tensor Cores, specialized hardware units designed specifically for accelerating matrix operations common in deep learning workloads.

In contrast, the special function units responsible for computing exponentials and other transcendental functions operate at dramatically lower throughput. The H100's special function units deliver approximately 3.9 TFLOPS for operations like exponential. This figure is derived from the CUDA programming guide's specification that each streaming multiprocessor can perform 16 special function operations per clock cycle. Multiplying this by 132 SMs and the 1830 MHz boost clock speed yields the 3.9 TFLOPS figure. The throughput gap between matmul and exponential operations spans roughly 256x—a factor of 256 more operations can be performed per unit time on the Tensor Cores compared to the special function units.

To appreciate the practical impact of this asymmetry, consider the attention forward pass with FP16 precision and a head dimension of 128. In this configuration, there are approximately 512 times more matmul FLOPS than exponential operations. However, since the exponential throughput is 256 times lower, the exponential computations can consume roughly 50% of the total cycle time compared to matmul. The situation becomes even more dire with FP8 precision, where the matmul throughput doubles to nearly 2 PFLOPS while the exponential throughput remains unchanged at 3.9 TFLOPS. This further widens the gap and makes overlapping even more critical.

Since the exponential calculations are performed by a completely separate hardware unit—the multi-function unit—ideal execution would schedule these calculations precisely when the Tensor Cores are engaged in matrix multiplication. The goal is to achieve concurrent utilization of both specialized units, effectively hiding the latency of the lower-throughput exponential operations behind the higher-throughput matmul operations. This observation motivates the intra-warpgroup overlapping technique, which seeks to exploit the asynchronous nature of WGMMA instructions to achieve precisely this kind of concurrent execution.

# The Two-Stage Pipelining Algorithm

The two-stage pipelining algorithm represents a sophisticated approach to breaking the sequential dependencies that constrain attention computation. The fundamental insight is that while dependencies exist within a single iteration, we can pipeline across iterations by maintaining additional buffers in registers. This allows the softmax computation from one iteration to overlap with GEMM computations from subsequent iterations.

The algorithm maintains two sets of score buffers: $\mathbf{S}_{\mathrm{cur}}$ for the current iteration and $\mathbf{S}_{\mathrm{next}}$ for the next iteration. By computing ahead the first GEMM of iteration $j+1$ while still processing iteration $j$, we create the opportunity for overlapping. Specifically, while the second GEMM of iteration $j$ executes on the Tensor Cores, the softmax computation for iteration $j+1$ can proceed on the multi-function units. The key innovation is issuing WGMMA instructions without immediately waiting for their completion, allowing subsequent instructions to execute asynchronously.

The algorithm begins by loading $\mathbf{Q}_i$ and $\mathbf{K}_0$ into shared memory and computing the initial score matrix $\mathbf{S}_{\mathrm{cur}} = \mathbf{Q}_i \mathbf{K}_0^T$ using WGMMA. After this first computation, the algorithm enters the main loop. Within each iteration $j$ of the main loop, the algorithm issues the first WGMMA to compute $\mathbf{S}_{\mathrm{next}} = \mathbf{Q}_i \mathbf{K}_{j}^T$ but critically does not wait for completion. Instead, it proceeds to wait for $\mathbf{V}_{j-1}$ to be loaded and then issues the second WGMMA for the previous iteration: $\mathbf{O}_{i} = \mathbf{O}_{i} + \tilde{\mathbf{P}}_{\mathrm{cur}} \mathbf{V}_{j-1}$.

At this point, the algorithm has two WGMMAs in flight—the first from the current iteration and the second from the previous iteration. The algorithm then waits specifically for the first WGMMA to complete before proceeding with softmax computation on $\mathbf{S}_{\mathrm{next}}$. After waiting for the second WGMMA and rescaling $\mathbf{O}_i$, the algorithm releases the appropriate buffer stages and copies $\mathbf{S}_{\mathrm{next}}$ to $\mathbf{S}_{\mathrm{cur}}$ for the next iteration. This careful orchestration ensures that the exponential computations required for softmax occur while Tensor Core operations are in progress.

# Breaking Dependencies Through Additional Register Buffers

The ability to pipeline across iterations hinges on maintaining state for multiple iterations simultaneously. The two-stage pipeline requires allocating additional registers to store $\mathbf{S}_{\mathrm{next}}$, the score matrix for the upcoming iteration. This buffer allows the algorithm to look ahead and begin computing the first GEMM of the next iteration while the current iteration's softmax and second GEMM are still in progress.

The register cost of this additional buffer is substantial. Specifically, storing $\mathbf{S}_{\mathrm{next}}$ requires register space of size $B_r \times B_c \times \text{sizeof}(\text{float})$ per threadblock, where $B_r$ is the query block size (number of rows in each query tile) and $B_c$ is the key block size (number of rows in each key tile). For typical configurations, this can amount to a significant fraction of the available register budget per threadblock.

The presence of this additional buffer fundamentally changes the dependency structure. Rather than waiting for each operation to complete before beginning the next, the algorithm can issue operations speculatively for future iterations. The softmax of iteration $j$ now depends on $\mathbf{S}_{\mathrm{cur}}$, which was computed in iteration $j-1$, while the first GEMM of iteration $j$ computes $\mathbf{S}_{\mathrm{next}}$ that will be used in iteration $j+1$. This decoupling of production and consumption of score matrices across iterations is what enables the overlapping of computation.

# WGMMA Commit Without Wait: Asynchronous Execution

Central to the intra-warpgroup overlapping technique is the asynchronous nature of the WGMMA instruction on Hopper GPUs. Unlike previous architectures where Tensor Core operations were largely synchronous from the programmer's perspective, Hopper's WGMMA instruction operates asynchronously. When a WGMMA is issued, the instruction commits the operation to the Tensor Core but does not necessarily wait for completion before allowing subsequent instructions to execute.

In the two-stage pipelining algorithm, this asynchrony is exploited through the distinction between "commit" and "wait" operations. After issuing a WGMMA, the algorithm can specify whether to wait for completion or proceed immediately. The pseudocode in Algorithm 2 of the paper shows this distinction: certain WGMMA calls are followed by "Commit but do not wait," while others are followed by explicit waits. This selective waiting is crucial for achieving overlap.

Consider the sequence within the main loop. The first WGMMA computes $\mathbf{Q}_i \mathbf{K}_{j}^T$ and is committed without waiting. The algorithm then issues the second WGMMA for $\tilde{\mathbf{P}}_{\mathrm{cur}} \mathbf{V}_{j-1}$, also without waiting. At this point, both Tensor Core operations are in flight. The algorithm then explicitly waits for the first WGMMA to complete before computing softmax on $\mathbf{S}_{\mathrm{next}}$. This wait is necessary because softmax requires the actual values of $\mathbf{S}_{\mathrm{next}}$. However, during the time between issuing the first WGMMA and waiting for its completion, the multi-function units can execute the exponential operations needed for softmax.

# Detailed Algorithm Walkthrough

To solidify understanding, let us trace through the algorithm step by step. The algorithm begins with initialization: $\mathbf{O}_i$ is initialized to zero, and the log-sum-exp values $\ell_i$ and $m_i$ are initialized to zero and negative infinity respectively. The algorithm waits for $\mathbf{Q}_i$ and $\mathbf{K}_0$ to be loaded into shared memory, then computes the first score matrix $\mathbf{S}_{\mathrm{cur}} = \mathbf{Q}_i \mathbf{K}_0^T$.

After computing $m_i$, $\tilde{\mathbf{P}}_{\mathrm{cur}}$, and $\ell_i$ based on $\mathbf{S}_{\mathrm{cur}}$, the algorithm enters the main loop starting at iteration $j=1$. At the start of each main loop iteration, the algorithm waits for $\mathbf{K}_j$ to be loaded. It then computes $\mathbf{S}_{\mathrm{next}} = \mathbf{Q}_i \mathbf{K}_{j}^T$ using WGMMA, committing without waiting. This begins the first GEMM of the current iteration asynchronously.

Next, the algorithm waits for $\mathbf{V}_{j-1}$ to be loaded and issues the second WGMMA: $\mathbf{O}_{i} = \mathbf{O}_{i} + \tilde{\mathbf{P}}_{\mathrm{cur}} \mathbf{V}_{j-1}$, again committing without waiting. Now both WGMMAs are executing on the Tensor Cores. The algorithm then explicitly waits for the first WGMMA to complete, at which point $\mathbf{S}_{\mathrm{next}}$ is available. The softmax computation proceeds, computing $m_i$, $\tilde{\mathbf{P}}_{\mathrm{next}}$, and $\ell_i$ based on $\mathbf{S}_{\mathrm{next}}$. During this softmax computation, the second WGMMA is still potentially executing on the Tensor Cores, achieving the desired overlap.

After waiting for the second WGMMA and rescaling $\mathbf{O}_i$, the algorithm releases the buffer stages for reuse by the producer warps. Finally, $\mathbf{S}_{\mathrm{next}}$ is copied to $\mathbf{S}_{\mathrm{cur}}$, and the loop proceeds to the next iteration. The epilogue handles the final iteration separately, computing the last second GEMM and performing final rescaling before writing the output to HBM.

# Compiler Reordering Challenges

While the pseudocode presented in Algorithm 2 represents an idealized execution order, practical implementation faces challenges from compiler optimization. The NVCC compiler, which translates CUDA C++ code into machine instructions, often rearranges instructions for optimization purposes. This reordering can disrupt the carefully crafted sequence of WGMMA and non-WGMMA operations that enable overlapping.

The compiler's instruction scheduling is designed to maximize various metrics such as register usage, instruction throughput, and latency hiding. However, the compiler does not have complete knowledge of the programmer's intent regarding overlapping between different hardware units. Left to its own devices, the compiler might reorder instructions in ways that serialize operations rather than overlapping them, defeating the purpose of the pipelining scheme.

Despite this challenge, analysis of the generated SASS (assembly) code confirms that the compiler does generate overlapped code as expected. This suggests that with appropriate code structure and potentially explicit synchronization hints, the desired overlapping behavior can be achieved. Programmers implementing such algorithms must be attentive to the generated assembly to verify that their intended overlapping is actually being realized in practice.

# Register Pressure Analysis

The two-stage pipeline algorithm imposes increased register pressure compared to the baseline algorithm. The additional buffer $\mathbf{S}_{\mathrm{next}}$ requires register space that could otherwise be used for other purposes. This creates a tension between the benefits of pipelining and the costs of register usage.

Register spilling—the process of moving register contents to slower memory when register capacity is exceeded—must be minimized for optimal performance. When registers spill to shared memory or global memory, the resulting memory traffic can negate the performance gains from overlapping. Therefore, careful attention must be paid to register allocation when implementing the pipelining algorithm.

The trade-off manifests in the choice of block sizes. Larger block sizes $B_r$ and $B_c$ generally improve arithmetic intensity and reduce the overhead of loop control. However, larger blocks also require more register space for storing intermediate results. The addition of $\mathbf{S}_{\mathrm{next}}$ further increases this pressure. In practice, profiling is essential to determine the optimal balance between block size and pipeline depth for a given configuration.

# Trade-offs Between Tile Size and Pipeline Depth

The design space for pipelining algorithms involves a fundamental trade-off between tile size and pipeline depth. Larger tiles increase the amount of computation per iteration, which generally improves efficiency by amortizing loop overhead. However, larger tiles also require more register space for intermediate results and accumulator buffers.

Pipeline depth represents how many iterations ahead the algorithm computes before waiting. The two-stage pipeline maintains one iteration ahead, while a three-stage pipeline would maintain two iterations ahead. Deeper pipelines offer the potential for higher Tensor Core utilization by providing more opportunities for overlapping. However, each additional stage requires additional register buffers for storing intermediate score matrices.

This trade-off is particularly acute because the registers used for pipeline buffers directly compete with the registers needed for larger tiles. For example, doubling the pipeline depth from two stages to three stages would require an additional $\mathbf{S}$ buffer, reducing the register budget available for tile data. This might force the use of smaller tiles, which could offset the benefits of deeper pipelining.

The optimal configuration depends on the specific parameters of the attention computation, including sequence length, head dimension, and hardware characteristics. In practice, empirical tuning and profiling are necessary to navigate this trade-off space and identify the best configuration for each use case.

# Three-Stage Pipelining Variant

Building upon the two-stage algorithm, a natural extension is the three-stage pipelining variant. This approach would further overlap the second GEMM with softmax operations, potentially achieving even higher Tensor Core utilization. The three-stage variant would maintain two lookahead buffers, allowing computation to proceed two iterations ahead.

In a three-stage pipeline, the algorithm would compute $\mathbf{S}$ for iterations $j+1$ and $j+2$ while processing the softmax and second GEMM for iteration $j$. This creates additional opportunities for hiding the latency of exponential operations behind Tensor Core computations. Theoretically, this could reduce the idle time of specialized hardware units even further.

However, the three-stage variant comes with increased costs. Each additional stage requires another register buffer for storing intermediate score matrices. The register pressure from a three-stage pipeline would be approximately 50% higher than the two-stage version. This increased pressure might necessitate smaller tile sizes or cause register spilling, either of which could degrade performance.

The trade-off between pipeline depth and tile size becomes even more critical for the three-stage variant. While the theoretical potential for overlap is greater, the practical realization of this potential depends on whether sufficient register capacity is available. Detailed evaluation and benchmarking are necessary to determine whether the three-stage variant provides net benefits for specific configurations.

# SASS Code Analysis Verifying Intended Overlapping Behavior

Validation of the pipelining algorithm's effectiveness requires examining the generated machine code. SASS (Streaming Assembly) is the low-level instruction set executed by NVIDIA GPUs. By analyzing the SASS code generated from the pipelining algorithm, we can verify that the intended overlapping behavior is actually being realized.

The analysis confirms that the compiler generates code where WGMMA instructions and non-WGMMA operations are interleaved as intended. Specifically, the SASS code shows that exponential operations (computed by the multi-function units) are scheduled during periods when WGMMA instructions are in progress on the Tensor Cores. This confirms that the asynchronous nature of WGMMA is being exploited correctly.

This verification is important because it demonstrates that the algorithmic innovations translate into actual hardware behavior. Without such analysis, it would be possible to write code that appears correct at the CUDA level but fails to achieve the desired overlapping due to compiler intervention. The SASS analysis provides confidence that the pipelining algorithm is indeed exploiting hardware capabilities as designed.
