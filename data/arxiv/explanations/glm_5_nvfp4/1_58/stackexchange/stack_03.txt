\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### Why does adding 0 to the weights enable "feature filtering"?
Question:
The paper claims that BitNet b1.58 has stronger modeling capability because the inclusion of 0 in the weights enables "explicit support for feature filtering." It states this "can significantly improve the performance of 1-bit LLMs."

I understand that weights of 0 would zero out certain activations, but isn't that what ReLU and other activation functions already do? Why is having explicit 0 weights particularly beneficial compared to just having small magnitude weights that approximate zero? And why couldn't the original 1-bit BitNet (with weights in \{-1, 1\}) learn to approximate zero through its remaining parameters?
Answer:
The distinction between zero weights and activation functions like ReLU is more fundamental than it might first appear. Let me explain why explicit zero weights in BitNet b1.58 provide genuinely different capabilities.

**The key difference: where the "zeroing" happens in the computation.**

When ReLU zeros out an activation, it does so *after* the weighted sum has been computed—every input feature has already contributed its weighted influence. In contrast, a zero weight zeros out an input feature's contribution *before* it enters the weighted sum. Mathematically, for an input vector $x$ and weight vector $w$:

- With ReLU: $\text{ReLU}(w^T x) = \max(0, \sum_i w_i x_i)$ — all features contribute first, then we threshold
- With zero weights: $\sum_i w_i x_i$ where $w_i = 0$ means feature $i$ is *explicitly ignored*

This matters because zero weights enable the model to implement *feature selection* at the connection level, not just output-level thresholding.

**Why can't small magnitude weights approximate this?**

In a 1-bit quantization framework like the original BitNet, there are no "small magnitude weights"—weights can only be exactly $\{-1, 1\}$. Every single connection either adds or subtracts the input activation with full strength. There's no continuous spectrum of weight magnitudes that could "approximately" ignore a feature.

The original BitNet would need to rely on indirect strategies to diminish a feature's importance, such as having multiple paths that cancel out, or relying on the attention mechanism to downweight certain inputs. These are less direct and less parameter-efficient than simply having a weight that says "ignore this connection."

**What "feature filtering" actually means in practice.**

The paper's concept of feature filtering refers to the model's ability to *selectively route information*. With ternary weights $\{-1, 0, 1\}$, each neuron can explicitly choose which input features to respond to positively, which to respond to negatively, and which to ignore entirely. This creates a sparser, more interpretable connectivity pattern.

Consider a neuron processing word representations: with binary weights, every semantic dimension must either be amplified or suppressed. With ternary weights, the neuron can genuinely "not care" about certain dimensions, which is particularly valuable in high-dimensional embedding spaces where many features may be irrelevant to any given computation.

The empirical results support this intuition—BitNet b1.58 matches FP16 LLaMA performance starting at 3B parameters, while the original BitNet (without explicit zeros) showed a larger performance gap. The inclusion of zero weights provides expressivity that proves essential for closing this gap.
