\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does FeatLLM parse natural language rules into executable code?
Question:
The paper mentions that the LLM generates rules in natural language, and then these rules are parsed into program code to create binary features. However, it also mentions that the LLM output can include 'noisy syntactic changes' like substituting '>' with 'greater than'.

I'm confused about how the parsing actually works. Does the paper use a second LLM call to convert rules to code? And if so, how does it ensure the parsed code correctly reflects the original rule's semantics?
Answer:
The paper does indeed use a second LLM call to convert natural language rules into executable code, and this is a key design decision in FeatLLM's architecture.

The parsing challenge arises because even though FeatLLM constrains the output format during rule generation (through response instructions in the prompt), the LLM can still produce "noisy syntactic changes." For example, it might substitute "$>$" or "$<$" with phrases like "greater than" or "less than," making rule-based parsing unreliable.

Rather than building a complex parser to handle all these variations, FeatLLM leverages the LLM itself for the parsing task. The approach is elegant: the LLM, having been trained on code corpora, can understand the semantic meaning of rules despite syntactic variations and generate appropriate executable code. The prompt for this second LLM call includes:
- The function name
- Input and output descriptions  
- The inferred rules from the first step

The generated code is then executed using Python's `exec()` function to perform the actual data transformation.

Regarding semantic correctness, the paper doesn't use explicit validation of the parsed code. Instead, robustness is achieved through two mechanisms:

1. **Ensembling with bagging**: The entire rule generation and parsing process is repeated multiple times ($T=20$ trials by default). Even if incorrect rules or parsing errors occur in some trials, correct rules from other trials can compensate.

2. **Self-consistency**: Rules commonly inferred across multiple trials are more likely to be accurate, and this redundancy helps filter out parsing errors or spurious rules.

3. **Weight tuning**: After generating binary features, a linear model learns weights for each rule. Rules with low learned weights (below a threshold of $0.1$) are effectively filtered out during training, as they have little relevance to the target.

This design choice—using the LLM for both generation and parsing—exemplifies how FeatLLM exploits LLM capabilities while keeping the downstream inference simple and efficient. The parsing code generation happens only once during feature engineering, not at inference time, so the computational cost is contained.
