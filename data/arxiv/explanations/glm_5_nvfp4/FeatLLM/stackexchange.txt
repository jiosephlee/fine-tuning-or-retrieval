\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Why does FeatLLM use a linear model instead of the LLM for final predictions?
Question:
I'm reading the FeatLLM paper and I understand that it uses LLMs to generate rules/features, but I'm confused about why it then uses a simple linear model for the final predictions instead of continuing to use the LLM. The paper mentions that this 'improves inference latency' but couldn't the LLM also make predictions directly from the rules it generated? What's the specific advantage of switching to a linear model?
Answer:
The design choice to use a linear model for final predictions rather than the LLM itself is central to FeatLLM's architecture, and the paper provides several compelling reasons for this approach.

**Inference Efficiency.** The primary motivation is computational efficiency at deployment time. As the paper states, "Current LLM-based tabular learning methods have some limitations. For end-to-end predictions, at least one LLM inference per sample is required, making it computationally expensive." By extracting rules once using the LLM and then deploying a lightweight linear model, FeatLLM "eliminates the need to send queries to the LLM for each sample at inference time." This dramatically reduces both latency and API costs when the model is deployed.

**Learning Feature Importance.** While you could theoretically use the LLM's rules directly for prediction (e.g., counting how many rules each sample satisfies), the paper notes that "not all rules and features carry the same importance, necessitating learning their significance from training samples." The linear model with trainable weights $\mathbf{w}_k$ learns which rules are most predictive, effectively filtering out less useful rules. The ablation study confirms this: omitting weight tuning ("-Tuning") causes performance degradation, with the benefit being "higher when the number of shots increases" since more data allows better estimation of rule importance.

**Practical Deployment.** The paper emphasizes that FeatLLM "merely requires API-level access to LLMs" and is "free from training constraints." Once the rules are generated and parsed into executable code, the downstream model can operate independently without requiring LLM access. This is particularly valuable in industrial settings where "the requirement to always pass inference through the LLM poses challenges."

**Quantified Benefits.** Table 4 in the paper shows that FeatLLM's inference time is comparable to conventional ML methods, while other LLM-based approaches (In-context learning, TABLET, TabLLM) have "much higher inference time."

The key insight is that the LLM's strength lies in its prior knowledge for *feature engineering*—understanding which patterns might be predictive—not in performing the final classification itself. Once meaningful features are extracted, a simple linear model suffices for the prediction task.

### What is the purpose of max($\mathbf{w}_k$, 0) in the logit computation?
Question:
In Section 3.2, the paper computes the logit as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

Why is the max operation applied to the weights? The paper mentions 'projecting these weights into a positive subspace' but I don't understand why this is necessary. Couldn't we just let the weights be positive or negative based on what the data tells us? If a rule actually decreases the likelihood of a class, shouldn't the weight be negative?
Answer:
The `$\max(\mathbf{w}_k, 0)$` operation ensures that satisfying a rule can only *increase* (or have no effect on) the likelihood of a class, never decrease it. This design choice stems from how the rules are generated.

The key insight is that the LLM is explicitly prompted to generate rules that are *positively associated* with each class. For class $k$, the LLM produces rules like "age $>$ 65" or "blood pressure $>$ 140" that should indicate membership in that class. These rules are extracted from the LLM's prior knowledge about what conditions are relevant to the target class.

If you allowed negative weights, a sample satisfying a rule for class $k$ could actually *decrease* the logit for class $k$. This would contradict the semantic meaning of the rules themselves—the LLM was asked to generate conditions that indicate class membership, not conditions that indicate non-membership.

But what if a generated rule is uninformative or even counterproductive? The learning process handles this gracefully: if a rule is irrelevant, gradient descent will push its weight toward zero (or even negative), and the `$\max$` operation then clips it to exactly zero. This effectively "turns off" unhelpful rules without inverting their intended meaning.

This is analogous to how attention mechanisms work in neural networks—weights are often constrained to be non-negative to maintain interpretability and prevent counterintuitive behavior. In the ablation study (Table 4), the paper shows that removing weight tuning entirely ("$-$Tuning") degrades performance, confirming that learning which rules matter is important—but the positive constraint ensures the learned weights respect the semantics of the rule generation process.

### How does FeatLLM parse natural language rules into executable code?
Question:
The paper mentions that the LLM generates rules in natural language, and then these rules are parsed into program code to create binary features. However, it also mentions that the LLM output can include 'noisy syntactic changes' like substituting '>' with 'greater than'.

I'm confused about how the parsing actually works. Does the paper use a second LLM call to convert rules to code? And if so, how does it ensure the parsed code correctly reflects the original rule's semantics?
Answer:
The paper does indeed use a second LLM call to convert natural language rules into executable code, and this is a key design decision in FeatLLM's architecture.

The parsing challenge arises because even though FeatLLM constrains the output format during rule generation (through response instructions in the prompt), the LLM can still produce "noisy syntactic changes." For example, it might substitute "$>$" or "$<$" with phrases like "greater than" or "less than," making rule-based parsing unreliable.

Rather than building a complex parser to handle all these variations, FeatLLM leverages the LLM itself for the parsing task. The approach is elegant: the LLM, having been trained on code corpora, can understand the semantic meaning of rules despite syntactic variations and generate appropriate executable code. The prompt for this second LLM call includes:
- The function name
- Input and output descriptions  
- The inferred rules from the first step

The generated code is then executed using Python's `exec()` function to perform the actual data transformation.

Regarding semantic correctness, the paper doesn't use explicit validation of the parsed code. Instead, robustness is achieved through two mechanisms:

1. **Ensembling with bagging**: The entire rule generation and parsing process is repeated multiple times ($T=20$ trials by default). Even if incorrect rules or parsing errors occur in some trials, correct rules from other trials can compensate.

2. **Self-consistency**: Rules commonly inferred across multiple trials are more likely to be accurate, and this redundancy helps filter out parsing errors or spurious rules.

3. **Weight tuning**: After generating binary features, a linear model learns weights for each rule. Rules with low learned weights (below a threshold of $0.1$) are effectively filtered out during training, as they have little relevance to the target.

This design choice—using the LLM for both generation and parsing—exemplifies how FeatLLM exploits LLM capabilities while keeping the downstream inference simple and efficient. The parsing code generation happens only once during feature engineering, not at inference time, so the computational cost is contained.

### Why does the two-step reasoning process help filter out uninformative features?
Question:
In Section 3.1, the paper describes a two-step reasoning instruction where Step 1 infers causal relationships without looking at examples, and Step 2 uses examples to deduce rules. The paper claims this 'prevents the model from identifying spurious correlations in irrelevant columns.'

I don't quite follow why separating these steps helps. If the LLM has prior knowledge about which features are relevant, why can't it just generate rules directly? And how does looking at examples first lead to spurious correlations?
Answer:
The two-step reasoning process works by establishing a "prior filter" before the model ever sees the data samples. Here's why this matters:

**The problem with looking at examples first:** In few-shot settings (e.g., 4-16 samples), there's a high risk that random coincidences in those few examples appear meaningful. If the LLM examines examples immediately, it might latch onto spurious patterns—for instance, noticing that 3 out of 4 patients with heart disease in your examples happen to share an unrelated feature (like a particular occupation or zip code). Without first consulting its prior knowledge about what features are *plausibly* relevant to heart disease, the model has no basis to reject this as noise.

**How Step 1 helps:** By first asking the LLM to infer causal relationships based solely on task and feature descriptions—*without* seeing any examples—the model must rely entirely on its world knowledge. For a heart disease prediction task, it might reason: "Age, blood pressure, and cholesterol are known risk factors for heart disease, while occupation is not typically causally related." This step extracts the LLM's prior beliefs about which features are mechanistically relevant.

**How Step 2 uses this:** When the LLM then examines examples to derive specific rules, it's already primed to focus on features identified as causally relevant. The spurious correlation in that zip code column won't be encoded into rules because Step 1 already established it's not a meaningful feature for this task.

The paper provides empirical support in Section 4.2: when irrelevant columns from the Adult dataset were added to the Heart dataset, FeatLLM showed the least performance degradation among baselines, with rules based on noisy columns accounting for only 1-2\% of total rules generated. The ablation study also confirms that removing Step 1 (the "$\textsf{-Reasoning}$" condition) causes significant performance drops, especially in low-shot regimes where spurious correlations are most likely to mislead.

### How does bagging solve the prompt size limitation?
Question:
The paper claims that bagging helps 'mitigate the challenge of excessive prompt size' when dealing with datasets that have many features. I understand bagging typically involves sampling subsets of data, but how exactly does this reduce the prompt size? Does the paper sample features or samples for each trial? And wouldn't using subsets mean some important features are missed in individual trials?
Answer:
The paper uses **feature bagging** (sampling subsets of features) rather than just sample bagging to address the prompt size limitation. Here's how it works:

When a tabular dataset has many features—such as the 'Communities' or 'Myocardial' datasets with over 100 attributes—serializing all feature descriptions and their values into a single prompt can exceed the LLM's context window or cause performance degradation due to the "lost in the middle" phenomenon.

The solution is straightforward: for each trial, the framework randomly selects a **subset of features** (and optionally instances) to include in the prompt. This directly reduces the serialized text length, making each individual query feasible within prompt size constraints.

Regarding your concern about missing important features: the paper addresses this through **ensembling across multiple trials**. Each trial uses a different random subset of features, so while any single trial may miss some important features, the ensemble collectively captures relationships across the full feature space. The paper states:

> "While a single rule set might not capture the relationships of all features, the ensemble of various weak learners created across multiple trials can nullify the impact of incomplete feature/instance coverage in individual trials."

This connects to the broader concept of **self-consistency** in LLMs—rules that appear consistently across multiple trials are more likely to be correct, while spurious or missing rules from individual trials average out in the ensemble.

The experimental results demonstrate effectiveness: other LLM-based approaches like TabLLM and in-context learning "failed to infer on tabular datasets with a large number of features," while FeatLLM maintained strong performance even on high-dimensional datasets precisely because the bagging mechanism kept each prompt within manageable size limits.

### What happens when the LLM generates incorrect or nonsensical rules?
Question:
Since FeatLLM relies on the LLM generating meaningful rules, what happens when the LLM outputs something that doesn't make sense? For example, what if it generates a rule like 'if age is greater than Tuesday' or creates a rule based on a feature that doesn't exist in the data? How does the framework handle such failures?
Answer:
The FeatLLM framework handles incorrect or nonsensical rules through several robust mechanisms, making it resilient to occasional LLM failures.

**Ensemble approach provides fault tolerance.** The most important safeguard is that FeatLLM generates rules multiple times (default: 20 trials) with bagging and combines predictions through ensembling. As the paper states, "even if the LLM generates incorrect rules in some trials, the correct rules from other trials can compensate, enhancing the overall robustness of the framework." This connects to the self-consistency principle—rules commonly inferred across multiple trials are more likely to be accurate.

**Weight tuning filters out unhelpful rules.** After generating binary features from rules, FeatLLM learns a linear model with non-negative weights ($\mathbf{w}_k \geq 0$) to estimate each rule's importance. Rules that don't correlate with the target will receive low weights, effectively neutralizing their impact. The paper confirms this in Table 6: "during the process of tuning the linear model with data, rules that have little relevance to the data (i.e., rules with learned weights below the threshold) are automatically filtered out."

**Type-aware prompt design prevents nonsensical rules.** The reasoning instruction explicitly guides the LLM to "refer to the type of each feature in the basic information description part to avoid type mismatches in rules." By providing feature descriptions including value types, the LLM is less likely to generate rules like "if age is greater than Tuesday."

**LLM-assisted parsing handles syntactic variations.** When the LLM produces rules with inconsistent syntax (e.g., using "greater than" instead of "$>$"), the framework leverages the LLM itself to parse these into executable code, as the LLM excels at understanding semantic meaning despite syntactic noise.

In summary, while FeatLLM doesn't prevent every bad rule, its ensemble strategy and learned weighting scheme ensure that a few nonsensical rules won't significantly degrade overall performance.

### Why set the number of rules to exactly 10 per class?
Question:
The paper mentions setting a fixed number of rules (10) to be extracted for each class to avoid underfitting or creating too large a prompt. However, this seems arbitrary. Some classes might need more rules to capture their characteristics, while others might need fewer. Does the paper explain why 10 is chosen, or provide analysis on how this number affects performance?
Answer:
The paper does address this question, though you need to connect a few pieces.

First, the motivation for fixing the number of rules is stated in Section 3.1: the constraint prevents extracting "too few or too many rules, potentially leading to either underfitting or creating an excessively large prompt."

More importantly, the paper provides an empirical analysis of this hyperparameter. In Section 4.2 under "Hyper-parameter analysis," the authors report that they "conducted experiments to investigate the impact of these hyper-parameters on performance." Their finding was that "while there wasn't a statistically significant difference" across different numbers of rules, "$10$ is the most appropriate number considering the trade-off between prompt length and performance."

The reasoning here is subtle but important: since FeatLLM operates in a **few-shot regime** (e.g., $4$ to $32$ labeled samples), increasing the number of rules directly increases the dimensionality of the binary feature vector fed to the downstream linear model. The authors speculate that "more rules enlarging input dimensionality, leading to an increase in information, yet also resulting in overfitting within the low-shot regime."

So $10$ isn't claiming to be optimal for every class—it's a practical default that balances competing concerns:
1. **Prompt size**: More rules mean longer prompts, which can hit context length limits
2. **Feature quality**: Too few rules risks underfitting; the LLM's knowledge isn't fully utilized
3. **Overfitting risk**: In few-shot settings, high-dimensional feature spaces (many rules) relative to few training samples leads to overfitting

The ensemble mechanism (Section 3.2) also mitigates any single choice being problematic. By running $20$ trials with different random subsets and aggregating, the framework naturally explores a larger effective rule space without any single prompt becoming unwieldy.

### How does FeatLLM differ from simply using chain-of-thought prompting?
Question:
The paper mentions using a 'chain-of-thought' style reasoning instruction. I'm wondering: how is FeatLLM's approach fundamentally different from just using CoT prompting with an LLM for tabular prediction? In both cases, the LLM reasons about the task. Is the main difference just that FeatLLM extracts explicit rules rather than giving predictions?
Answer:
The fundamental difference between FeatLLM and chain-of-thought (CoT) prompting lies in **what the LLM is asked to produce** and **how inference is performed**.

## Key Distinctions

**1. Output Type: Rules vs. Predictions**

In standard CoT prompting for tabular prediction, the LLM reasons through each sample and outputs a prediction (e.g., "This patient is at high risk because..."). In FeatLLM, the LLM never outputs predictions for individual samples. Instead, it outputs **explicit rules** in natural language form, such as:
- "If age is greater than 60 AND blood pressure exceeds 140, then high risk"
- "If glucose level is between 120-200, then moderate risk"

These rules are then parsed into executable code and converted into binary features.

**2. Inference Mechanism**

This is the most practical difference. With CoT, **every test sample requires an LLM query**. FeatLLM, by contrast, queries the LLM only during the feature engineering phase. At inference time, the paper uses a simple linear model:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

where $\mathbf{z}_k^i$ represents the binary features indicating whether each rule is satisfied. This eliminates LLM inference entirely at prediction time, resulting in dramatically lower computational cost.

**3. Structured Two-Step Reasoning**

FeatLLM's prompt design goes beyond CoT by structuring reasoning into two explicit steps:
- **Step 1**: Infer causal relationships using prior knowledge *without* looking at examples
- **Step 2**: Deduce rules by combining prior knowledge with few-shot examples

The paper shows this prevents the LLM from latching onto spurious correlations in irrelevant columns—a problem that standard CoT approaches don't explicitly address.

**4. Scalability to Many Features**

When tabular datasets have many features (e.g., the Myocardial dataset with 100+ attributes), standard CoT hits prompt length limits. FeatLLM handles this through feature bagging—sampling subsets of features across multiple ensemble trials—while still producing coherent rules for each subset.

## Why This Matters

The paper emphasizes that FeatLLM "eliminates the need to send queries to the LLM for each sample at inference time" and "merely requires API-level access to LLMs." This makes it feasible for real-world applications where inference cost and latency matter, while still leveraging the LLM's prior knowledge during feature engineering.

### Why does the ablation show feature descriptions are more important with fewer shots?
Question:
In the ablation study (Section 4.2), removing feature descriptions causes performance degradation, and this effect is 'high when the number of shot is small.' The paper says this suggests 'efficient utilization of the prior knowledge of LLM becomes crucial.'

I'm confused about this reasoning. If we have fewer shots, shouldn't we rely more on the few examples we do have, rather than feature descriptions? Why would feature descriptions (prior knowledge) become more important when we have less data?
Answer:
The intuition you're suggesting actually works in the opposite direction. When you have fewer shots, the examples themselves are often insufficient to learn meaningful patterns—this is precisely why prior knowledge becomes *more* critical, not less.

Let me explain the reasoning:

**With few shots, data is unreliable.** When you only have 4 or 8 examples, those samples might be unrepresentative, noisy, or contain spurious correlations. Learning purely from such limited data risks overfitting to noise rather than discovering true signal. The paper explicitly notes this challenge in the Related Work section: "Learning from a small number of labeled samples presents the risk of learning spurious correlations."

**Feature descriptions activate the LLM's prior knowledge.** The feature descriptions tell the LLM what each column means semantically (e.g., that a column represents "age" or "blood pressure"). Without these descriptions, the LLM sees only abstract column names and cannot apply its domain knowledge. With descriptions, the LLM can leverage its pre-training—which includes knowledge like "older patients are at higher risk for certain diseases"—to generate meaningful rules.

**This aligns with the paper's reasoning structure.** Notice that in Section 3.1, the prompt design separates the reasoning into two steps: first, inferring causal relationships "without referring to example demonstrations, relying instead on general knowledge," and only then incorporating the few-shot examples. This design ensures prior knowledge guides the process before the sparse data is considered.

**The broader principle:** This connects to the bias-variance tradeoff in machine learning. With limited data (high variance), you need stronger inductive biases—or prior knowledge—to constrain the hypothesis space and prevent overfitting. Feature descriptions provide exactly this: they inject domain knowledge that guides the model toward plausible hypotheses rather than letting it learn arbitrary patterns from a handful of examples.

So the ablation result confirms that FeatLLM's strength lies in combining LLM prior knowledge with data-efficient learning, and this combination is most valuable precisely when the data signal is weakest.

### Can FeatLLM handle continuous target variables for regression?
Question:
The paper focuses on classification tasks with discrete class labels. The rules generated by the LLM are used to create binary features indicating whether samples satisfy each rule. I'm wondering: can this framework be extended to regression problems where the target is continuous? Would the rule extraction process work the same way, or would a fundamentally different approach be needed?
Answer:
Yes, FeatLLM is specifically designed for classification tasks and cannot directly handle continuous target variables for regression without fundamental modifications.

The framework makes several assumptions that inherently require discrete class labels. First, the rule extraction process prompts the LLM to generate rules "for each class" — the paper states in the problem formulation that "Assuming the classification setup, the label $\mathbf{y}^i$ is defined as one of the predefined set of classes." The LLM is instructed to "deduce rules for each class" based on the few-shot examples, which requires the target to be a finite set of categories.

Second, the binary feature generation is class-dependent. The generated features $\mathbf{z}_k^i \in \{0, 1\}^R$ indicate whether sample $\mathbf{x}^i$ satisfies rules associated with class $k$. This structure inherently assumes a discrete number of classes $c$, as these features are created "for each class."

Third, the downstream model uses softmax normalization over class logits:
$$\mathbf{p}^i = \text{Softmax}({[\text{logit}_{1}^i, ..., \text{logit}_{c}^i]})$$

This produces a probability distribution over $c$ classes, which doesn't apply to continuous targets.

To adapt FeatLLM for regression, you would need a fundamentally different approach. One possibility is discretizing the continuous target into bins and treating each bin as a class, though this loses information and introduces arbitrary boundaries. Alternatively, you could redesign the rule extraction to generate rules predicting value ranges or threshold conditions, and replace the softmax-based downstream model with a regression model. However, the paper does not explore these extensions, and such modifications would require rethinking how rules map to continuous predictions.

The authors explicitly note in the conclusion that "FeatLLM is designed to focus on low-shot learning regime only" with future work exploring "various feature types beyond rules," suggesting the current framework's scope is intentionally limited to classification.
