Chapter 5: # From Natural Language to Binary Features: Rule Parsing and Application

## The Challenge of Parsing Noisy LLM Outputs

When Large Language Models generate rules in natural language, these outputs are inherently flexible and varied. This flexibility, while useful for human comprehension, presents a significant technical challenge when we attempt to systematically apply these rules to tabular data. The core problem lies in the syntactic variations that LLMs introduce into their outputs. Even when given explicit formatting instructions, an LLM might substitute symbolic operators like "$>$" or "$<$" with their textual equivalents such as "greater than" or "less than." Similarly, logical operators might appear as "AND," "and," "&&," or even spelled out as "and also."

Consider a rule that the LLM generates for identifying high-risk credit applicants. In one trial, the model might output "income $<$ 30000 AND debt_ratio $>$ 0.5," while in another trial, the semantically equivalent rule might appear as "income is less than 30000 and debt_ratio exceeds 0.5." A human reader would immediately recognize these as expressing the same condition, but a traditional parser built on rigid pattern matching would struggle to handle such variability. The challenge is compounded by the fact that these variations are not merely cosmetic—they can affect the structure of the output in ways that break predetermined parsing templates.

This noise in LLM outputs stems from the fundamental nature of language models. LLMs are trained to generate human-like text, and human language is characterized by its flexibility and redundancy. Multiple phrasings can express identical meanings, and the LLM has learned to navigate this space of linguistic equivalence. While this property is valuable for general language tasks, it becomes a hurdle when we need to convert natural language rules into executable code that can be systematically applied to data.

The variability in outputs also extends to how the LLM structures its logical reasoning. It might combine multiple conditions using different logical connectives, nest conditions in various ways, or introduce parenthetical clarifications. Each of these variations requires the parsing system to be robust enough to handle edge cases that may not have been anticipated during system design. Building a rule-based parser with hard-coded patterns to handle all these variations would be impractical and brittle, as it would fail to generalize to new patterns that the LLM might produce.

## Leveraging the LLM to Write Its Own Parsing Code

Rather than attempting to build an increasingly complex parser to handle the noisy and variable outputs from the LLM, the FeatLLM framework adopts an elegant solution: it leverages the LLM itself to perform the parsing. This approach recognizes that the LLM, having generated the rules, is uniquely positioned to understand their semantic meaning. The same model that produced "greater than" instead of "$>$" can understand that these expressions are equivalent and translate them into appropriate code.

The key insight here is that LLMs possess two complementary capabilities. First, they excel at understanding semantic meaning even when syntactic expressions vary. The model that generated a rule with unconventional phrasing can still parse that rule correctly because it understands the underlying logical structure. Second, LLMs trained on code corpora have acquired the ability to generate functional program code when given clear instructions. By combining these capabilities, we can ask the LLM to translate its own natural language rules into executable Python code.

The process begins after the LLM has generated its rules. The framework constructs a new prompt that includes the function name, input and output descriptions, and the inferred rules themselves. This prompt asks the LLM to generate Python code that implements the logical conditions specified in the rules. The generated code takes a data sample as input and returns a binary indicator for whether each rule is satisfied.

Consider how this works in practice. Suppose the LLM has generated a rule stating that a patient is at high risk for heart disease if "age is greater than 60 and blood pressure exceeds 140." When we feed this rule back to the LLM with a request to generate parsing code, the model produces Python code that checks whether a given sample's age value is greater than 60 and whether its blood pressure value is greater than 140. The code handles any necessary type conversions and comparisons, abstracting away the specific phrasing used in the original rule.

The generated code is then executed using Python's built-in \texttt{exec()} function, which allows dynamic execution of code stored as strings. This enables the system to automatically transform new data samples based on the rules without requiring human intervention or manual coding. The entire pipeline—from rule generation to code generation to execution—is automated, making it feasible to apply this approach across multiple trials and datasets.

This approach to parsing exemplifies a broader principle in working with LLMs: when faced with challenges arising from model behavior, it is often more effective to leverage the model's strengths rather than to build external systems that fight against its tendencies. By asking the LLM to translate its own outputs, we sidestep the need to anticipate and handle every possible syntactic variation.

## Feature Generation: Transforming Samples into Binary Vectors

Once the parsing code has been generated, the next step is to apply this code to transform data samples into new feature representations. This transformation converts each sample from its original representation—typically a vector of continuous and categorical values—into a binary feature vector based on rule satisfaction.

For each class in the classification task, the LLM generates a set of rules that characterize when a sample belongs to that class. When these rules are applied to a sample, they produce a binary vector where each element indicates whether the sample satisfies a particular rule. If a sample meets the conditions specified in a rule, the corresponding feature is set to 1; otherwise, it is set to 0. This creates a sparse, interpretable representation of the sample based on how it aligns with the LLM's reasoning.

To formalize this process, consider a classification problem with $c$ classes. For each class $k$, the LLM generates $R$ rules based on the few-shot examples and its prior knowledge. Given a sample $\mathbf{x}^i$, the generated parsing code evaluates each of these $R$ rules against the sample's feature values. The result is a binary vector $\mathbf{z}_k^i \in \{0, 1\}^R$ for each class $k$, where each component $z_{k,j}^i$ indicates whether sample $i$ satisfies rule $j$ for class $k$.

This transformation has several important properties. First, it abstracts away the specific feature values and instead focuses on whether samples satisfy certain logical conditions. This can be particularly valuable when the relationship between features and labels is not linear or when interactions between features are important. Second, the binary representation is highly interpretable—each feature corresponds directly to a human-readable rule, making it possible to understand exactly why a particular classification decision was made.

The number of rules $R$ per class is a design choice that balances several factors. With too few rules, the representation may be too coarse to capture important distinctions between samples. With too many rules, the feature dimensionality becomes large relative to the number of training samples, potentially leading to overfitting in the low-shot regime. The FeatLLM framework uses $R = 10$ rules per class as a default, which provides sufficient representational capacity while remaining tractable for few-shot learning.

An important consideration is that not all rules generated by the LLM will be equally informative. Some rules may capture genuine relationships between features and labels, while others may reflect spurious correlations or irrelevant reasoning. The transformation to binary features preserves all rules equally initially, and the subsequent learning process must identify which rules are most useful for the task at hand.

## Inferring Class Likelihood: A Linear Model Approach

With the binary feature representation in hand, the next step is to use these features to predict class membership. While many approaches could be used, the FeatLLM framework employs a simple linear model for this purpose. This choice is deliberate—by using a model with low complexity, the framework maintains its efficiency and interpretability while still achieving strong predictive performance.

The rationale for a linear model becomes clear when we consider the nature of the binary features. Each feature directly represents whether a sample satisfies a particular rule, and each rule was designed by the LLM to be relevant for identifying members of a particular class. The question then becomes: how important is each rule for making accurate predictions? A linear model directly answers this question by learning a weight for each feature that quantifies its contribution to the prediction.

A naive approach would be to simply count how many rules each sample satisfies for each class—summing the binary features—and use these counts as scores. However, this approach assumes that all rules are equally important, which is unlikely to be true in practice. Some rules may be highly diagnostic, strongly indicating class membership when satisfied. Other rules may be weaker signals, providing only marginal evidence. The linear model allows us to learn these relative importances from the few-shot training data.

The simplicity of the linear model also aligns with the constraints of few-shot learning. With only a small number of labeled samples available for training, complex models with many parameters would be prone to overfitting, memorizing the training examples rather than learning generalizable patterns. A linear model, with its limited parameter count, provides appropriate inductive bias for the low-data regime. The model can still achieve high performance because the heavy lifting—identifying relevant features and their relationships to classes—has already been done by the LLM during rule generation.

Furthermore, using a linear model enables efficient inference. Once the model weights have been learned, predictions for new samples require only simple matrix operations: a dot product between the weights and the binary features, followed by a softmax transformation. This computational efficiency stands in stark contrast to approaches that require LLM inference for each sample, where each prediction requires a potentially expensive API call.

## Mathematical Formulation of the Linear Model

The mathematical formulation of the classification model is designed to be both simple and effective. Let $\mathbf{z}_k^i \in \{0, 1\}^R$ denote the binary feature vector generated from sample $\mathbf{x}^i$ for class $k$, where $R$ is the number of rules per class. For each class, we learn a weight vector $\mathbf{w}_k \in \mathbb{R}^R$ that represents the importance of each rule for predicting membership in that class.

The first step in computing the class likelihood is to calculate a logit score for each class. This is done using a dot product between the weight vector and the binary feature vector:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

The $\max(\mathbf{w}_k, 0)$ operation projects the weights onto the positive subspace, ensuring that all weights are non-negative. This projection is a crucial design choice with an important rationale: the rules were generated by the LLM to identify samples belonging to class $k$. If a sample satisfies a rule for class $k$, this should never decrease its likelihood of belonging to that class. By constraining weights to be non-negative, we ensure that the features generated by the LLM can only increase the class likelihood, never reduce it.

Without this constraint, the learning process might assign negative weights to some rules, effectively treating them as evidence against class membership. But this would contradict the semantic meaning of the rules, which were explicitly designed to identify members of each class. The positive weight projection maintains consistency between the LLM's rule generation and the downstream learning process.

After computing logits for each class, the final step is to convert these scores into proper probability distributions using the softmax function:

$$\mathbf{p}^i = \text{Softmax}\left([\text{logit}_{1}^i, \text{logit}_{2}^i, ..., \text{logit}_{c}^i]\right)$$

The softmax function normalizes the logit scores so that they sum to one and are all positive, yielding a valid probability distribution over the $c$ classes. For each sample, the predicted class is the one with the highest probability.

This formulation elegantly combines the LLM's knowledge—encoded in the rules—with data-driven learning—encoded in the weights. The LLM identifies potentially relevant features, and the learning process determines which of those features are actually useful for the specific dataset at hand.

## Training the Downstream Model: Optimizing Weights to Learn Rule Importance

The training process for the linear model involves learning the weight vectors $\mathbf{w}_k$ for each class using the few-shot training samples. The objective is to assign higher weights to rules that are more predictive of class membership and lower weights to rules that are less informative or potentially misleading.

The weights are learned by optimizing the cross-entropy loss, which measures the discrepancy between the predicted probability distribution and the true class labels. For a dataset with $N$ labeled samples, the cross-entropy loss is:

$$\mathcal{L} = -\sum_{i=1}^{N} \log p_{y^i}^i$$

where $y^i$ is the true class label for sample $i$ and $p_{y^i}^i$ is the predicted probability for that class. Minimizing this loss encourages the model to assign high probability to the correct class for each training sample.

The optimization is performed using standard gradient-based methods, such as the Adam optimizer. Given the small number of parameters—the weight vectors for each class—and the limited number of training samples, the optimization converges quickly. The FeatLLM framework uses a learning rate of 0.01 and trains for up to 200 epochs, selecting the optimal epoch using $k$-fold cross-validation.

An important empirical finding from the research is that the benefit of weight tuning increases with the number of training samples. When only a handful of samples are available, there is limited information to estimate rule importance accurately, and the simple sum of binary features may perform nearly as well as the weighted approach. However, as more labeled samples become available, the weighted model can leverage this additional information to learn more nuanced rule importances, leading to significant performance improvements.

The training process also provides a form of automatic filtering for irrelevant rules. Rules that have little relationship to the target label will tend to receive low weights during optimization. In practice, the researchers found that setting a threshold of 0.1 on the learned weights effectively filters out rules with little relevance to the data, with the majority of rules receiving weights above this threshold confirming their informativeness. This demonstrates that the LLM generates high-quality rules that are genuinely useful for the prediction task.

The combination of LLM-based rule generation and data-driven weight learning creates a powerful synergy. The LLM contributes its vast prior knowledge and reasoning capabilities, identifying features that a human expert might specify. The learning process then adapts these features to the specific characteristics of the dataset at hand, learning which rules are most important and effectively discarding irrelevant ones. This division of labor allows each component to do what it does best, resulting in a system that achieves strong performance in few-shot tabular learning scenarios.
