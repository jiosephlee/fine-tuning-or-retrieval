\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 4: # Engineering the Prompt: Extracting Knowledge from LLMs

The design of prompts for Large Language Models (LLMs) represents a critical intersection between human intent and machine reasoning. When we task an LLM with feature engineering for tabular learning, the prompt becomes more than a simple request—it becomes a structured mechanism for knowledge extraction. This chapter explores how FeatLLM approaches prompt engineering as a systematic process, transforming the LLM into an effective feature engineer capable of generating high-quality, interpretable rules from limited data.

The FeatLLM framework structures its input prompt into three distinct components, each serving a specific purpose in guiding the LLM toward accurate rule generation. This structured approach mimics how an expert human might approach a tabular learning task, breaking down complex reasoning into manageable steps. By understanding each component and its role in the overall process, we gain insight into how to effectively leverage LLMs for feature engineering tasks.

#

## Component 1: Basic Information Description

The foundation of any effective prompt lies in providing the LLM with sufficient context to understand the problem at hand. In FeatLLM, the basic information description serves as this foundational layer, equipping the LLM with essential information for solving the classification task. This component comprises three critical elements: the task description, feature descriptions, and example demonstrations.

The task description provides the LLM with a clear understanding of what problem it needs to solve. In FeatLLM, task descriptions are formulated as questions, which naturally prompts the LLM to reason toward an answer. For instance, when predicting medical outcomes, the task description might take the form: "Does this patient's myocardial infarction complications data indicate chronic heart failure? Yes or no?" This question-based format serves a dual purpose: it clearly defines the prediction objective while also framing the problem in a way that encourages the LLM to identify the factors that influence the answer. The task description implicitly communicates what features should be examined and what kind of reasoning would be appropriate for the domain.

Feature descriptions provide the LLM with detailed information about each variable in the dataset. For each feature, the description indicates its value type and optionally includes its definition, providing semantic context that goes beyond mere column names. For categorical variables, examples of the possible categories can be provided, helping the LLM understand the range of values it might encounter. This level of detail is crucial because tabular data often contains features with names that may be ambiguous or domain-specific. By including definitions and value type information, the prompt ensures that the LLM can properly interpret each feature's meaning and significance. For example, a feature named "cp" in a heart disease dataset might be cryptic on its own, but when described as "chest pain type" with possible values of "typical angina," "atypical angina," "non-anginal pain," and "asymptomatic," the LLM can draw upon its medical knowledge to understand how this feature relates to cardiac outcomes.

### Data Serialization Techniques: Converting Tabular Rows into Natural Language

Example demonstrations constitute the third element of the basic information description, and they require careful serialization to transform tabular data into a format the LLM can process. Since LLMs operate on natural language text, tabular data must be converted into textual representations—a process known as serialization. FeatLLM follows serialization formats established in prior research, converting each data sample into a coherent natural language statement.

The serialization process follows a specific formula that combines feature names with their corresponding values. Given a sample $\mathbf{x}^i$ with feature names $F = \{f_j\}_{j=1}^{d}$, the serialized representation takes the form:

$$\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = ``f_1\ \text{is}\ \mathbf{x}^i_1.\ ...\ f_d\ \text{is}\ \mathbf{x}^i_d.\ \ \text{Answer:}\ \mathbf{y}^i"$$

This serialization approach creates a natural language description where each feature name is paired with its value using the connecting phrase "is." For example, a patient record might be serialized as: "age is 45. sex is male. chest_pain_type is asymptomatic. resting_blood_pressure is 130. Answer: heart_disease." This format provides several advantages. First, it maintains semantic coherence, allowing the LLM to process the data as it would any other natural language text. Second, it explicitly associates feature names with values, ensuring the LLM understands which measurement corresponds to which attribute. Third, by including the answer (label) at the end, it establishes a clear connection between the input features and the target variable, enabling the LLM to learn from these examples during the reasoning process.

The choice of how many examples to include in the prompt relates to the few-shot learning paradigm. In FeatLLM, these examples serve as demonstrations from which the LLM can infer patterns and relationships. The serialization must balance comprehensiveness—providing enough information for the LLM to identify patterns—with conciseness, as prompt length constraints remain a practical consideration. When dealing with datasets containing many features, careful attention must be paid to serialization efficiency to ensure that relevant information can fit within the LLM's context window.

## Component 2: Reasoning Instructions and the Two-Step Inference Process

The second major component of the FeatLLM prompt design focuses on reasoning instructions. This component plays a pivotal role in guiding the LLM through a logical thought process, ensuring that the generated rules are grounded in meaningful relationships rather than superficial patterns. The reasoning instruction begins with an introductory sentence similar to the chain-of-thought approach, which has been shown to improve LLM performance on complex reasoning tasks by encouraging step-by-step problem decomposition.

What distinguishes FeatLLM's approach is the division of the LLM's inference process into two distinct steps. This structured reasoning approach serves a crucial purpose: it separates the LLM's prior knowledge application from its data-driven learning, allowing each source of information to contribute appropriately to rule generation. By explicitly structuring the reasoning process, FeatLLM guides the LLM toward more thoughtful and reliable feature engineering.

### Step 1: Inferring Causal Relationships Using Prior Knowledge Without Examples

The first step of the reasoning process encourages the LLM to infer causal relationships or tendencies between features and the task outcome without referring to example demonstrations. This step relies entirely on the LLM's general knowledge and common sense, allowing it to fully extract and apply its prior knowledge about the problem domain. By explicitly instructing the LLM to reason before examining examples, FeatLLM ensures that the model's inherent understanding of the domain contributes to rule formation.

Consider a medical diagnosis task. Before examining any patient data, the LLM might reason about factors that influence heart disease risk based on its training on medical literature. It could identify that factors such as advanced age, elevated blood pressure, high cholesterol, and certain chest pain types are generally associated with increased cardiac risk. This reasoning draws upon the vast corpus of medical information encoded in the LLM's parameters during pre-training. The LLM might articulate relationships like: "older individuals typically face higher cardiovascular risk" or "asymptomatic chest pain in diabetic patients often indicates silent ischemia."

This step is crucial because it allows domain knowledge to inform feature engineering before the model becomes influenced by the particularities of the limited examples. In few-shot learning scenarios, where only a handful of labeled examples are available, relying solely on these examples could lead to identifying spurious correlations that happen to exist in the small sample but do not reflect true relationships. By having the LLM first reason from prior knowledge, FeatLLM establishes a foundation of domain-appropriate relationships that can be refined—rather than determined—by the example demonstrations.

### Step 2: Deduce Decisive Rules Using Few-Shot Demonstrations

After establishing the prior knowledge foundation, the second step instructs the LLM to use both the example demonstrations and the information from the first step to deduce specific rules for each class. This step bridges general knowledge with specific data patterns, allowing the LLM to generate concrete, actionable rules that can be applied to new samples.

The reasoning instruction explicitly guides the LLM to examine the serialized examples and identify distinguishing characteristics between classes. For instance, given examples of patients with and without heart disease, the LLM might notice that patients with the positive label tend to have specific combinations of feature values. It then formulates rules that capture these distinguishing patterns. A rule might be: "IF age is greater than 60 AND chest_pain_type is asymptomatic, THEN predict high risk of heart disease."

This two-step reasoning process prevents the model from identifying spurious correlations in irrelevant columns. When an LLM is presented with many features and only a few examples, there is a risk that random variations in the data could be mistaken for meaningful patterns. By first establishing what relationships should exist based on domain knowledge, the model is better equipped to focus on features that plausibly relate to the target variable. The LLM can filter out uninformative features during rule extraction, concentrating its attention on features that both its prior knowledge and the example data suggest are important.

To ensure consistent and useful output, FeatLLM sets a fixed number of rules—specifically, ten—to be extracted for each class. This constraint addresses potential issues with both underfitting (too few rules) and prompt bloat (too many rules). The fixed number also provides predictability in downstream processing, as the system knows exactly how many binary features to generate per class. Additionally, when formulating rules, the LLM is instructed to refer to the type of each feature from the basic information description, avoiding type mismatches such as applying numerical comparisons to categorical variables.

## Component 3: Response Instructions for Structured and Parsable Outputs

The third component of the prompt design addresses a practical challenge inherent in working with LLMs: how to transform their free-form text outputs into structured data that can be programmatically processed. Response instructions guide the LLM on how to structure its outputs, ensuring that the generated rules can be reliably parsed and converted into executable code.

The response instructions specify two formatting requirements: the overall format for the response and the structure each individual rule should follow. These instructions serve a critical function in bridging the gap between natural language generation and automated feature engineering. Without structured response instructions, LLMs might produce rules in varying formats, using different syntactic conventions, making automated parsing unreliable or impossible.

The instructions specify that responses should be organized by answer class, with rules for each class presented in a clear, consistent format. For each rule, the LLM is guided to use appropriate comparison operators and logical connectives based on the feature type. For numerical features, rules might employ operators such as greater than ($>$), less than ($<$), or equality ($=$). For categorical features, rules might specify membership in a particular category. The instructions also allow the LLM to combine multiple conditions using logical operators like AND or OR, enabling the expression of more complex decision boundaries.

Consider an example where the LLM generates rules for predicting heart disease. A properly formatted rule might appear as: "Rule 1: age > 50 AND sex = 'male' AND chest_pain_type IN ['typical angina', 'atypical angina']." This structured format clearly specifies the feature, the comparison operator, and the threshold or category, enabling straightforward parsing into executable code.

The importance of response formatting becomes apparent when considering the downstream processing of these rules. FeatLLM must convert natural language rules into program code that can be executed to generate binary features. Even with formatting constraints, LLM output can include noisy syntactic variations. For example, the LLM might substitute "$>$" with phrases like "greater than" or "exceeds." Such variations, while semantically equivalent, pose challenges for automated parsing. FeatLLM addresses this by leveraging the LLM itself as a parser: the rules are fed back into the LLM with instructions to generate equivalent Python code. The LLM's ability to understand semantic meaning despite syntactic variations makes it well-suited for this translation task. The generated code is then executed using Python's `exec()` function to perform the actual data transformation, converting each sample into binary features indicating whether each rule is satisfied.

## Mitigating Spurious Correlations Through Structured Reasoning

A fundamental challenge in few-shot learning is the risk of learning spurious correlations—patterns that appear in the limited training data but do not reflect true underlying relationships. With only a handful of examples, random variations can be mistaken for meaningful signals, leading to models that perform well on training data but fail to generalize. FeatLLM's structured reasoning approach directly addresses this challenge through multiple mechanisms working in concert.

The two-step reasoning process serves as the primary defense against spurious correlations. By first asking the LLM to reason about causal relationships based on prior knowledge, independently of the examples, the framework establishes which feature-target relationships are plausible from a domain perspective. This prior knowledge acts as a filter, preventing the LLM from becoming overly influenced by chance patterns in the few-shot examples. When the LLM subsequently examines the examples in Step 2, it does so with the context of what relationships make sense, rather than freely fitting to whatever patterns happen to exist in the small sample.

Empirical evidence supports the effectiveness of this approach. In experiments where spurious correlations were artificially introduced by attaching irrelevant columns from unrelated datasets, FeatLLM demonstrated remarkable robustness. When columns from the Adult dataset (containing features like occupation and work class) were randomly attached to the Heart dataset (predicting coronary artery disease), FeatLLM showed the least performance degradation compared to baseline methods. Analysis revealed that rules based on these noisy columns accounted for only 1-2% of the total generated rules, indicating that the LLM successfully identified them as irrelevant and excluded them from meaningful rule generation.

The ablation studies in the FeatLLM paper further illuminate the importance of structured reasoning. When the reasoning instruction's first step—which elicits prior knowledge—was removed, performance degraded significantly, particularly in low-shot settings. This finding underscores that the prior knowledge component becomes increasingly crucial when fewer examples are available. With only four shots, there is simply not enough data to reliably distinguish signal from noise; domain knowledge must fill this gap. Conversely, as the number of shots increases, the relative contribution of prior knowledge decreases, though it remains beneficial.

It is worth noting that FeatLLM's approach is not foolproof. The framework can learn spurious correlations and misunderstand causal relationships when columns from closely related datasets are attached—situations where prior knowledge might actually reinforce incorrect associations. This limitation highlights an important consideration: the quality of feature engineering depends not only on the reasoning process but also on the relevance and quality of the features provided. The LLM's prior knowledge, while generally beneficial, may occasionally reinforce biases or incorrect assumptions present in its training data.

The ensemble approach employed by FeatLLM provides an additional layer of protection against spurious correlations. By generating rules multiple times with different random seeds, demonstration orderings, and feature subsets, the framework reduces the impact of any single erroneous rule. Rules that appear consistently across multiple trials are more likely to capture genuine relationships, following the principle of self-consistency in LLM reasoning. This ensemble strategy transforms the potential weakness of any single LLM query into a strength through aggregation, producing more robust feature sets for downstream prediction.
