Chapter 3: # The FeatLLM Methodology: An Architectural Overview

# Problem Formulation: Defining Datasets, Feature Names, and Labels for K-Shot Learning

To understand the FeatLLM framework, we must first establish the formal problem setting in which it operates. The framework addresses the challenge of tabular learning, a fundamental task in machine learning where data is organized in a structured format with rows representing individual samples and columns representing features or attributes. This stands in contrast to unstructured data like images or raw text, and tabular learning remains vital for many real-world applications in finance, healthcare, and business analytics.

Consider a tabular dataset comprising $N$ labeled samples, which we denote as $\mathcal{D} = \{(\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^{N}$. Each sample consists of an input feature vector $\mathbf{x}^i$ that is $d$-dimensional, meaning it contains $d$ distinct features or attributes. The label $\mathbf{y}^i$ represents the target variable we wish to predict, and in the classification setup that FeatLLM addresses, this label belongs to a predefined set of classes. The framework assumes a classification task where the goal is to assign each input sample to one of several possible categories.

What distinguishes tabular data from other data modalities, and what FeatLLM leverages, is the semantic meaning carried by feature names. The dataset comes with natural language feature names, denoted by $F = \{f_j\}_{j=1}^{d}$, along with their definitions provided separately. For instance, in a medical dataset, feature names might include "age," "blood pressure," or "cholesterol level," each carrying semantic meaning that a language model can interpret and reason about. This semantic richness is crucial because it allows the LLM to apply its pre-existing knowledge about relationships between features and outcomes.

The k-shot learning paradigm introduces an additional constraint that makes the problem particularly challenging. Rather than having access to all $N$ labeled samples for training, only $k$ samples are randomly sampled, where $k < N$ and typically $k$ is quite small. This setting, known as few-shot learning, presents the risk of learning spurious correlations—patterns that appear meaningful in the small training set but do not generalize to the broader population. The constraint reflects real-world scenarios where obtaining labeled data is expensive, time-consuming, or requires expert annotation, such as in medical diagnosis or financial risk assessment.

In the experiments conducted by the authors, the value of $k$ ranges from as few as 2 to 32 shots, demonstrating the framework's capability to perform meaningful learning even with extremely limited supervision. This regime is where conventional machine learning methods often struggle, as they typically require substantial amounts of labeled data to learn accurate models without overfitting. The few-shot setting demands that the learning system incorporate prior knowledge or inductive biases that compensate for the scarcity of labeled examples.

# The Core Philosophy: Extracting Rules Instead of Direct Predictions

The central innovation of FeatLLM lies in reconceptualizing the role that large language models play in the prediction pipeline. Rather than treating LLMs as end-to-end predictors that directly output answers for each input sample, FeatLLM assigns them the role of feature engineers. This philosophical shift has profound implications for both the efficiency and interpretability of the resulting system.

When an LLM is asked to make a prediction directly, it must process each sample through its entire computational graph at inference time. For a tabular dataset with millions of samples, this means invoking the LLM millions of times, incurring substantial computational costs and latency. Moreover, this black-box approach provides little insight into why particular predictions are made, making it difficult to debug, validate, or trust the system's outputs. The LLM becomes an inscrutable oracle whose reasoning remains hidden.

FeatLLM takes a fundamentally different approach. Instead of asking "what is the prediction for this sample?", it asks "what criteria determine whether a sample belongs to a particular class?" This shift from instance-level prediction to rule extraction represents a more sophisticated use of the LLM's capabilities. The LLM is tasked with understanding and articulating the underlying logic that connects features to outcomes. For example, when predicting heart disease, the LLM might generate rules such as "if age is greater than 60 AND blood pressure exceeds 140, then high risk" or "if cholesterol level is above 240 AND family history is positive, then high risk."

These rules, which the paper refers to as the "criteria" underlying predictions, serve as the foundation for feature engineering. By converting the LLM's knowledge into explicit, interpretable rules, FeatLLM creates a transparent representation of the reasoning process. Each rule can be examined, validated, and modified by domain experts, fostering trust and enabling collaboration between human experts and machine learning systems. This interpretability is particularly valuable in high-stakes domains like healthcare, where understanding the basis for predictions is essential for clinical decision-making.

The extraction of rules also enables a clean separation between the knowledge-intensive reasoning process and the statistical learning process. The LLM contributes its vast prior knowledge—gleaned from training on extensive text corpora spanning diverse domains—to propose plausible relationships between features and outcomes. A simple downstream machine learning model then learns the relative importance of these rules from the limited labeled data. This division of labor allows each component to do what it does best: the LLM provides domain knowledge and reasoning capabilities, while the statistical model provides data-driven calibration.

Furthermore, this approach addresses a fundamental limitation of LLM-based tabular learning methods. Current approaches require at least one LLM inference per sample for end-to-end predictions, making them computationally expensive for real-world deployment. By extracting rules once and reusing them for all samples, FeatLLM reduces the LLM's role to a preprocessing step, dramatically reducing inference costs while still benefiting from the LLM's knowledge.

# Pipeline Overview: From Prompting to Model Training

The FeatLLM pipeline consists of several interconnected stages that transform raw tabular data into accurate predictions. Understanding this end-to-end workflow is essential for appreciating how the framework achieves its goals of efficiency, interpretability, and strong performance in few-shot settings.

The first stage involves carefully designing prompts that guide the LLM toward extracting meaningful rules. The prompt comprises three main components: basic information description, reasoning instruction, and response instruction. The basic information description provides essential context for solving the problem, including a description of the task formulated as a question (such as "Does this patient's myocardial infarction complications data indicate chronic heart failure?"), descriptions of each feature including value types and optional definitions, and example demonstrations where few training samples are serialized into text along with their ground-truth labels.

The serialization of training samples follows a consistent format: $``\ f_1\ \text{is}\ \mathbf{x}^i_1.\ ... \ f_d\  \text{is}\  \mathbf{x}^i_d.\ \ \text{Answer:}\  \mathbf{y}^i\ ''$. This format presents each feature name and its corresponding value in natural language, followed by the correct answer. For example, a sample might be serialized as "age is 65. blood_pressure is 150. cholesterol is 280. Answer: positive." This serialization enables the LLM to process tabular data using its natural language understanding capabilities.

The reasoning instruction guides the LLM through a structured two-step reasoning process. In the first step, the LLM is encouraged to infer causal relationships or tendencies between features and the target variable without referring to the example demonstrations. This step relies on the LLM's general knowledge and common sense, allowing it to fully extract prior knowledge about the problem domain. In the second step, the LLM uses both the information from the first step and the example demonstrations to deduce specific rules for each class. This structured approach prevents the model from identifying spurious correlations in irrelevant columns and helps focus attention on more significant features.

The response instruction ensures that the LLM's output is structured in a way that facilitates automated parsing. The prompt specifies the format for responses and the structure each rule should follow, allowing the LLM to select appropriate formats based on feature types (numeric or categorical). Without such guidance, the LLM might produce rules in various formats that would be difficult to parse programmatically.

Once the LLM generates rules in natural language, the next stage involves parsing these rules into executable code. This is achieved by leveraging the LLM itself to generate Python code that implements the rules. The function name, input and output descriptions, and inferred rules are included in a prompt that asks the LLM to generate the corresponding code. This generated code is then executed using Python's $\texttt{exec()}$ function to perform the actual data transformation. This approach handles the challenge of parsing noisy text, as the LLM can understand semantic meaning despite syntactic variations in the rules.

The feature generation stage applies the parsed rules to create new binary features. For each class, binary features indicate whether a sample satisfies the rules associated with that class. If we denote the generated binary feature from sample $\mathbf{x}^i$ for class $k$ as $\mathbf{z}_k^i \in \{0, 1\}^R$, where $R$ is the number of rules per class and $c$ is the number of classes, each feature takes a value of 1 if the sample satisfies the corresponding rule and 0 otherwise.

The final stage involves training a simple machine learning model on these binary features to estimate class probabilities. The framework uses a linear model without bias, where the probability for each class $\mathbf{p}^i$ is computed as follows:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,$$

$$\mathbf{p}^i = \text{Softmax}({[\text{logit}_{1}^i, ..., \text{logit}_{c}^i]}).$$

Here, $\mathbf{w}_k$ represents trainable weights that signify the importance of each feature for predicting class $k$. By projecting weights into a positive subspace through the $\max$ operation, the framework ensures that features generated by the LLM do not reduce the likelihood of a class during learning. The model is trained by optimizing cross-entropy loss using the few-shot training samples.

# Advantages of Decoupling Feature Engineering from the Inference Model

The architectural decision to separate feature engineering from the inference model yields several significant advantages that address fundamental challenges in applying LLMs to tabular learning tasks.

The most immediate benefit is the dramatic reduction in inference cost. Since the LLM is only consulted during the feature engineering phase, which occurs once before model training, the framework eliminates the need to send queries to the LLM for each sample at inference time. In contrast, approaches that use LLMs for end-to-end predictions must invoke the model for every single test sample, leading to substantial computational overhead and latency. FeatLLM's inference cost is comparable to conventional machine learning methods, making it practical for deployment in real-world systems with large datasets or real-time prediction requirements.

A second advantage concerns accessibility to state-of-the-art LLMs. Many of the most powerful recent LLMs, such as GPT-4 and PaLM, only permit limited access via inference APIs without providing access to training codebases or fine-tuning APIs. This restriction poses a fundamental challenge for approaches that require fine-tuning the LLM for high accuracy. FeatLLM circumvents this limitation by only requiring API-level access to the LLM for inference during the feature engineering phase. The framework is model-agnostic and can work with any LLM that can process prompts and generate text outputs.

The decoupled architecture also addresses the challenge of prompt size limitations. LLMs have finite context windows that limit the amount of text they can process in a single query. When tabular data has many features, the serialized text length can exceed these limits, rendering the approach infeasible or causing performance degradation. FeatLLM employs ensemble methods with feature bagging to mitigate this challenge. By selecting subsets of features for different ensemble members, the framework ensures that each individual prompt remains within acceptable size limits while still covering the full feature set across the ensemble.

The ensemble approach, inspired by techniques from ensemble methods, offers additional benefits for robustness. Even if the LLM generates incorrect rules in some trials, correct rules from other trials can compensate, enhancing overall prediction quality. This relates to the concept of self-consistency in LLMs—rules commonly inferred across multiple trials are more likely to be accurate. The framework sets a sufficiently high temperature for LLM inference and randomizes the order of few-shot demonstrations to introduce diversity in rule generation, ensuring that the ensemble captures a broad range of potentially useful rules.

Finally, the separation enables interpretability. Each generated rule can be examined as a human-readable statement about the relationship between features and outcomes. The learned weights indicate which rules the data suggests are most important. This transparency stands in stark contrast to end-to-end LLM predictions, where the reasoning process remains opaque. In domains where understanding the basis for predictions is critical for trust and accountability, this interpretability provides substantial value.

# Visualizing the Workflow: From Raw Tabular Samples to Binary Features

Understanding how raw tabular data transforms through the FeatLLM pipeline provides concrete insight into the framework's operation. Let us trace the journey of a single sample through this transformation process.

Consider a sample from a medical dataset attempting to predict chronic heart failure. The raw input might consist of numerical and categorical values: age equals 65, blood pressure equals 150, cholesterol equals 280, and so forth through all $d$ features. This sample, along with $k-1$ other labeled samples and the feature descriptions, enters the prompt construction phase.

The LLM receives this structured prompt and generates rules through its two-step reasoning process. For the positive class (chronic heart failure present), it might produce rules such as: "age is greater than 60," "blood pressure exceeds 140," or "cholesterol level is greater than 240 AND previous heart condition is present." For the negative class, it might generate complementary rules. Each rule represents a condition that the LLM believes distinguishes samples of that class.

The parsing stage converts these natural language rules into executable Python code. The LLM, when prompted with the rules and appropriate function signatures, generates code that checks each condition. For example, a rule "age is greater than 60" becomes a function that returns 1 if the age feature exceeds 60 and 0 otherwise. This automated code generation handles the variability in how the LLM might express rules, such as substituting mathematical symbols with phrases like "greater than."

With the parsed code, feature generation proceeds by applying each rule to each sample. The original sample $\mathbf{x}^i$ with its $d$ original features transforms into a new representation $\mathbf{z}_k^i$ containing $R$ binary features for each class $k$. If $R$ rules are extracted for each of $c$ classes, the total number of new binary features equals $R \times c$. Each binary feature indicates whether the sample satisfies a particular rule associated with a particular class.

This transformation from continuous and categorical original features to binary rule-based features fundamentally changes the nature of the learning problem. The downstream linear model no longer needs to discover complex relationships between features and outcomes; instead, it simply learns which rules, among those proposed by the LLM, are most predictive. The heavy lifting of reasoning about feature-target relationships has already been accomplished by the LLM's prior knowledge.

The ensemble approach adds another dimension to this workflow. Multiple independent trials of rule generation and model training occur, each potentially producing different rules due to the randomized prompt construction and LLM temperature settings. The final prediction aggregates the probability estimates from all ensemble members, combining diverse perspectives into a more robust prediction. This aggregation ensures that the system does not rely too heavily on any single set of rules, providing resilience against occasional poor rule generation.

The complete journey—from raw tabular samples with semantic feature names, through LLM-guided rule extraction, to binary features processed by a simple linear model—represents a thoughtful integration of large language model capabilities with traditional machine learning principles. Each stage builds upon the previous, transforming data in ways that preserve semantic meaning while enabling efficient computation.
