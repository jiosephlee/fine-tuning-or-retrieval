\title{Stack Exchange of the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

### How does iterative GRPO work with reference model updates?
Question:
I'm reading about the iterative RL process in DeepSeekMath's GRPO algorithm (Algorithm 1). The paper mentions:

1. Set reference model $\pi_{ref} \leftarrow \pi_{\theta}$ at the beginning of each iteration
2. Continually train the reward model using a replay mechanism with 10% historical data

I'm confused about several things:

Why does the reference model need to be updated to the current policy? I thought the reference model was supposed to stay fixed (like in standard PPO with KL penalty) to prevent the policy from drifting too far from the original?

What is the purpose of the replay mechanism for the reward model? And why 10% specifically?

The algorithm shows they run multiple iterations, but I don't understand the intuition behind updating both the reference model and reward model this way.
Answer:
The iterative GRPO design addresses a fundamental challenge in reinforcement learning for LLMs: as the policy improves, the training distribution shifts, and both the reference point and reward model need to adapt.

**Reference Model Update**

In standard single-run PPO, the reference model stays fixed to the initial policy, and the KL penalty prevents deviation from it. However, in iterative RL, this creates a problem: after significant training, the policy has legitimately improved, and anchoring to the *original* reference model becomes overly restrictive. The KL penalty would essentially constrain the policy to stay near its initial, less-capable state rather than allowing continued exploration.

By setting $\pi_{ref} \leftarrow \pi_\theta$ at the start of each iteration, DeepSeekMath effectively "resets the anchor" to the current improved policy. This allows the next iteration to explore from the new baseline while still maintaining stability within each iteration through the KL regularization. The key insight is that in iterative RL, you want to prevent *excessive* drift *within* an iteration (hence keeping the reference fixed during the inner loop), but you *want* progress across iterations (hence updating the reference between iterations).

**Replay Mechanism for Reward Model**

As the policy evolves, it generates outputs with different characteristics—potentially exploring reasoning patterns the original reward model never saw during training. The reward model must be continuously updated to properly evaluate these new samples.

The replay mechanism with 10% historical data prevents *catastrophic forgetting*. If you trained the reward model only on new samples from the improved policy, it would quickly lose its ability to evaluate earlier output patterns and could overfit to the narrow distribution of current samples. The 10% ratio is an empirical balance: enough historical data to maintain evaluation stability across output distributions, but not so much that it dilutes the signal from current, more relevant samples.

Together, these mechanisms enable the iterative loop to work properly: the reference model allows legitimate policy improvement across iterations, while the replay mechanism ensures the reward model remains a reliable judge of the evolving output distribution.
