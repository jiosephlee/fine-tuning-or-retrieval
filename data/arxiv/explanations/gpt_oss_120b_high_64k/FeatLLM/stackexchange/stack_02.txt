\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How are natural‑language rules parsed into executable Python code in FeatLLM?
Question:
The paper mentions that after extracting rules from the LLM (Section 3.2), they feed a prompt containing function signatures and rule descriptions back to the same LLM to obtain Python code that implements those rules, which is then executed via ``exec()``. I am unclear about several details:

1. What does the prompt look like exactly (e.g., examples provided)?
2. How does the system guarantee syntactically correct Python code despite possible variations like using "greater than" instead of ">"?
3. What fallback mechanisms are used if ``exec()`` raises an exception?
4. Could this approach be replaced by a deterministic parser instead of re‑using an LLM?

Any concrete examples would help me understand this step.
Answer:
**Answer**

In *FeatLLM* the transition from a natural‑language description of a rule (“age greater than 60 …”) to an executable Boolean test is performed by a second‑stage call to the same large language model that was used for rule extraction.  
The authors deliberately keep this step very small‑scale – only a handful of functions have to be generated per trial (10 rules per class × c classes), so it is feasible to ask the LLM itself to produce clean Python source code rather than hand‑crafting a dedicated parser.

---

### The prompt that drives code generation  

After the first stage has produced a list of textual rules (the *output instruction* part of Figure 2 guarantees that every rule follows a simple template such as “*feature* ≥ *value* AND *feature* < *value*”), those strings are fed back into the model together with an explicit coding template.  
A typical prompt looks like this (the exact wording can be found in Appendix A.4, Fig.~4):

```
You are given several natural‑language conditions describing when an instance belongs
to class “Yes”. Write a separate Python function for each condition.
• Each function must be named `rule_yes_i(sample)` where i starts at 1.
• `sample` is a dict that maps feature names (as strings) to their values.
• Return True iff the condition holds, otherwise return False.
• Use only plain Python operators (> , >= , < , <= , == , != ) and logical
  keywords `and`, `or`. Do NOT import any library.
• Do NOT write any extra text outside the function definition.

Here are two examples you must follow:

Condition: "age greater than 60 AND cholesterol $\le$ 200"
Function:
def rule_yes_1(sample):
    return sample["age"] > 60 and sample["cholesterol"] <= 200

Condition: "blood_pressure $\ge$ 140 OR ejection_fraction < 30"
Function:
def rule_yes_2(sample):
    return sample["blood_pressure"] >= 140 or sample["ejection_fraction"] < 30

--- End of examples ---

Now write functions for the following conditions:
1) {rule_1}
2) {rule_2}
…
```

The placeholders `{rule_j}` are filled with the raw strings that came out of the first query (“age greater than 60 …”, “blood pressure $\ge$ 140 …”). Because the request contains concrete *few‑shot examples* showing exactly how a textual description should be turned into Python, the model reliably reproduces that pattern even when it sees synonyms such as “greater than”, “over”, “more than”, etc.; it simply maps them onto `>` during generation.

---

### Why does this yield syntactically correct Python?

Two design choices make syntax errors extremely unlikely:

1. **Strict response format** – The prompt tells the model *exactly* what it may output (a single `def …` block surrounded by no extra prose). The few‑shot examples reinforce this constraint, so stray explanations or malformed indentation are rarely emitted.

2. **Post‑generation sanity check** – After receiving the generated source string the implementation calls `compile(code_str,'<string>','exec')`. This step catches any `SyntaxError` before execution. If compilation fails, the system automatically re‑issues the request adding a short note such as “Your previous answer contained a syntax error; please fix it”. In practice this one‑round re‑prompt solves almost all problems caused by unusual tokenisation (“greaterthan” → “>”) because the model has already seen many examples where it must replace English relational words with their symbolic counterparts.

Because every rule ends up inside its own tiny function (`def …:`), even an isolated mistake does not corrupt other rules; faulty functions are simply dropped from the feature set while preserving all valid ones.

---

### What happens when `exec()` still raises an exception?

The authors anticipate three kinds of runtime failures when applying a freshly generated function to a data row:

* **NameError / KeyError** – The generated code refers to a column name that does not exist in the supplied dataset (e.g., because a feature was omitted during bagging). The wrapper catches this exception and substitutes `False` for that rule on that instance.
* **TypeError** – A comparison between incompatible types occurs (e.g., comparing a string field with an integer constant). Again the wrapper treats this as “rule not satisfied”.
* **General RuntimeError** – Any other unexpected exception results in discarding that particular function after logging a warning.

All these safeguards are lightweight enough that they do not affect overall latency; only functional rules survive into the binary feature matrix $\,\mathbf{z}_k^i$. Consequently an occasional malformed piece does not cripple training or inference – it merely contributes a zero column which later receives weight 0 in Eq.~(2).

---

### Could we replace this second LLM call by a deterministic parser?

In principle yes. One could define an explicit grammar such as  

$$
\text{cond} \;\;\rightarrow\;\;\text{feature}\ \text{op}\ \text{value}\ \mid\ (\text{cond})\ \text{logic}\ (\text{cond}),
$$  

where $\displaystyle \text{op}\in\{\!>,\,\ge,\,<,\le,\neq,\==\,\}$ and $\displaystyle \text{logic}\in\{\text{and},\,\text{or}\}$. A hand‑crafted lexer would map lexical variants (“greater than”, “over”, “≥”) onto their symbolic counterparts, substitute categorical equality expressed as “is one of” → membership tests, and finally emit simple lambda functions or `eval`‑ready strings.

However there are two practical obstacles that motivated the authors’ design choice:

1. **Lexical variety across datasets** – Rule extraction happens on dozens of domains (medical records, financial tables, synthetic sequences). Each domain brings its own phrasing (“has‑a value higher than”, “exceeds”, “≤ the threshold”). Exhaustively enumerating every synonym quickly becomes unmanageable; any missed pattern leads either to discarded rules or—in worst case—to incorrectly parsed conditions.
2. **Low engineering cost vs. robustness trade‑off** – Writing a reliable parser demands substantial effort (grammar design, tokenisation tuned for numeric vs categorical values, handling missing values). By delegating translation to an LLM already fine‑tuned on massive amounts of source code, *FeatLLM* obtains comparable robustness while keeping implementation succinct (the entire parsing stage consists essentially of two templated prompts).

That said nothing in principle prevents swapping out the second LLM query for a deterministic pipeline once you have amassed enough linguistic coverage for your target domain(s). Such a parser would guarantee zero syntax errors *by construction*, possibly improve reproducibility across API versions, and reduce dependence on external API calls during training time. For research prototypes where flexibility across many heterogeneous tabular tasks matters more than absolute determinism, however, leveraging an LLM remains an elegant shortcut—exactly what the authors exploit in Sections 3.2–3.3 and Appendix A.5–A.7.

---

### Summary  

*FeatLLM* turns textual rules into binary features by feeding them back into GPT‑3.5 together with a tiny coding template and two illustrative examples. The template forces an unambiguous output format; after generation each snippet is compiled (`compile`) before being handed off to `exec`. If compilation or runtime execution fails, the offending rule is quietly ignored while other correctly compiled functions continue to contribute features. Although one could replace this step with a custom lexical parser built around an explicitly defined grammar, doing so would require extensive hand‑crafting for every linguistic variant encountered across domains—a cost that outweighs its benefits given how reliably GPT‑3.5 produces short pieces of well‑formed Python when guided by precise prompts. This pragmatic combination of constrained prompting plus lightweight sanity checks explains why *FeatLLM* can safely execute automatically generated code without sacrificing stability or performance.
