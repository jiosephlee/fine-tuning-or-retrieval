\title{Blogs about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

# Why Teaching LLMs to Code Helps Them Solve Math Problems

Mathematical reasoning has become one of the flagship capabilities of large language models (LLMs). Recent closed‑source models such as GPT‑4 or Gemini‑Ultra achieve impressively high scores on benchmarks like **MATH**, yet they are out of reach for most researchers.  
The new open‑source contender **DeepSeekMath** narrows that gap dramatically—scoring over 50 % on the competition‑level MATH benchmark—by taking a somewhat unconventional route: heavy pre‑training on **code** before exposing the model to massive amounts of web‑extracted mathematics data.

In this post we unpack the experiments behind this claim, demystify terms such as *catastrophic forgetting*, and explain why learning to program makes an LLM a better mathematician—both when it must reason entirely in text and when it can invoke Python as an external “calculator”.

---

## 1. From Code to Calculus – The Idea

The authors start from **DeepSeek‑Coder‑Base‑v1.5**, a 7 B parameter model already fine‑tuned on billions of source‑code tokens. The intuition is simple:

> Programming forces a model to think in **stepwise, deterministic transformations**—exactly the kind of discipline required for rigorous mathematical proofs or multi‑step problem solving.

If this intuition holds, then adding a dedicated mathematics corpus should amplify those algorithmic habits rather than overwrite them.

---

## 2. Training Strategies Tested

The researchers compared four concrete pipelines (all run on a 1.3 B “mini” backbone before scaling up to 7 B). The setups differ along two axes:

| Pipeline | First Phase | Second Phase |
|----------|-------------|--------------|
| **Two‑stage A** | *Code* – 400 B tokens | *Math* – 150 B tokens |
| **Two‑stage B** | *General* text – 400 B tokens | *Math* – 150 B tokens |
| **One‑stage C** | *Pure Math* – 150 B tokens (no preceding phase) |
| **One‑stage D** | *Mixed* – 400 B code + 150 B math (simultaneous) |

All “math” phases use the same carefully curated **DeepSeekMath Corpus** (≈ 120 B tokens drawn from Common Crawl with a fastText classifier).  
The “general” baseline mixes ordinary web text without any programming bias, providing a control against which we can assess the special contribution of coding data.

---

## 3. What Did the Numbers Say?

Although the paper reports only aggregate results in tables, the narrative makes clear several robust trends:

* **Program‑aided solving improves drastically after any amount of code pre‑training.**  
  In both two‑stage settings A & B, models that saw code before math already outperformed those that only saw general text when asked to generate Python programs for GSM8K or MATH problems (“program‐of‐thought” prompting).

* **Subsequent math training builds on this foundation.**  
  Adding the math phase yields further gains across all metrics—suggesting that code knowledge does not “crowd out” later mathematical learning but rather provides a scaffold for it.

* **When code and math are mixed from the start (one‑stage D), catastrophic forgetting is mitigated.**  
  Pure two‑stage training suffers a drop in raw coding ability after the long math fine‐tune (the model “forgets” how to write clean APIs). By interleaving both domains during the same phase, model performance on both coding benchmarks *and* program‐aided mathematics stays high—a classic case of preventing catastrophic forgetting.

* **Tool‑free reasoning also benefits—but only under the two‑stage regime with an initial coding phase.**  
  In pure one‑stage training (C) where math is presented without any prior programming exposure, gains on standard chain‐of‐thought benchmarks are modest compared with A or B. This hints that algorithmic habits cultivated during code exposure transfer to textual reasoning as well.

In short, **code pre‐training acts as a catalyst**, especially when followed by dedicated math exposure; mixing both from day one preserves the best of both worlds.

---

## 4. Catastrophic Forgetting – A Quick Primer

*Catastrophic forgetting* describes how neural networks quickly lose performance on earlier tasks once they start learning new data—a problem especially acute when fine‐tuning large language models sequentially.

In our context:

1. **Stage A:** The model learns syntactic patterns of Python (`def`, `for`, `import sympy`) and develops an internal sense of *deterministic computation*.  
2️⃣ **Stage B:** When we switch exclusively to mathematics text (no more code examples), gradient updates start pushing parameters toward optimal representations for natural language explanations rather than programming constructs. If we stop providing any coding signal, the network’s “code head” gradually drifts away—that’s forgetting.

The remedy explored here is straightforward:
- **Interleaved training** (one‐stage D) keeps a steady stream of programming examples alongside mathematical ones, anchoring those parameters and preventing drift.
- Alternatively, one can perform a short *replay* phase after math fine‐tuning where a tiny amount of coding data is reintroduced—a strategy common in continual learning research but not needed once you mix domains from scratch.

---

## 5. Why Does Knowing Code Help With Pure Math?

Three complementary mechanisms appear at play:

### 5.1 Structured Thinking via Algorithmic Templates

When generating Python, the model implicitly learns templates such as “loop over integers”, “solve linear equations with `sympy.solve`”, or “evaluate an integral using `sympy.integrate`”. Even if we later forbid tool usage, those templates translate into textual analogues (“first isolate x, then substitute…”) because the underlying logical flow has already been internalized during coding pre‐training.

### 5.2 Access to Precise Computational Primitives

Libraries like `math` or `sympy` provide exact arithmetic (`Fraction`) and symbolic manipulation (`simplify`). By seeing countless examples where a problem’s answer hinges on calling `sympy.expand` or `math.gcd`, the LLM picks up *semantic associations*: “to factor this polynomial I should call `factor`.” Consequently it can reason about which operation would be appropriate even before actually executing any Python snippet—a subtle yet powerful boost for step‑by‑step explanations.

### 5 ​**Self‐Supervision Through Execution Results**

During instruction tuning (“program‐of‐thought” data), each generated script is executed and its output verified against the ground truth answer. The resulting feedback loop teaches the model that *correctness equals executable consistency*. This reinforces careful token ordering—something beneficial for pure chain‑of‑thought where each intermediate sentence must be logically sound despite lacking an external executor.

### 5️⃣ Conditioning on Code Improves Token Prediction

From a purely statistical viewpoint, source–code corpora contain dense blocks of highly predictable syntax (`:` after `def`, parentheses pairing). Learning these regularities sharpens next token prediction overall, which translates into tighter language modeling—one reason why deep language models often see modest gains across unrelated downstream tasks after extensive code pretraining (the classic “pretraining transfer”).

---

## 6. How DeepSeekMath Leverages Both Worlds

Putting everything together, DeepSeekMath proceeds as follows:

1. **Initialize** from DeepSeek-Coder-Base-v1.5 → already proficient at writing syntactically correct Python.
2. **Continual pre‑training** on the massive DeepSeekMath Corpus (≈ 120 B tokens) while retaining ≈ 20 % coding tokens throughout training—this preserves algorithmic habits.
3. **Instruction tuning** with chain–of–thought (CoT) *and* program–of–thought (PoT) examples so that the model learns when to write pure prose versus when to embed executable snippets.
4. **Reinforcement learning via GRPO**, further sharpening its preference for high‐quality solutions without destroying earlier abilities.

The outcome is striking:
- On GSM8K (“grade school maths”) DeepSeekMath reaches **88 % accuracy**, comparable with much larger proprietary systems.
- On MATH (“competition level”) it hits **51–52 %**, surpassing every other open source contender at comparable size.
- In *tool integrated* settings it attains roughly **60 %**, showing that its internalized programming knowledge translates into robust Python generation that actually executes correctly.

Importantly, these results reflect gains both in *tool–free* CoT reasoning and in *tool–enabled* PoT solving—a direct testament that early exposure to code helped the model learn generalizable problem–solving schemas.

---

## 7. Takeaways for Researchers and Practitioners

| Lesson | Practical Implication |
|--------|-----------------------|
| **Code = Structured Reasoning** | When building new domain experts (e.g., chemistry or physics), consider seeding them with heavy programming data first; algorithmic discipline tends to transfer across domains that require multi-step deduction. |
| **Mix Early & Often** | To avoid catastrophic forgetting when your pipeline involves multiple specialized corpora, interleave them rather than stacking them sequentially—or allocate a small replay budget after each stage. |
| **Program-of-Thought Data Matters** | Provide paired examples where a problem is solved by generating runnable code; execution feedback supplies a strong self-consistency signal absent from pure text supervision. |
| **Scale Is Not Everything** | The paper shows a 7 B model rivaling a closed 540 B system simply by curating better data and leveraging code pretraining—smart data pipelines can outweigh raw parameter counts.|

---

## 8. Looking Ahead

The authors acknowledge remaining gaps: geometry problems still lag behind closed models; larger scale may further amplify benefits; improving reward models for reinforcement learning could make RL phases even more efficient than GRPO’s current group-relative baseline estimation.

Nonetheless, DeepSeekMath demonstrates a clear principle: teaching an LLM *how* to program teaches it *how* to think stepwise—a skill set that transfers powerfully into pure mathematical reasoning.

If you’re interested in reproducing these findings or extending them to other domains (e.g., chemistry notebooks or legal contract drafting), start by building a high-quality language–code corpus using fastText classifiers or similar filters—then follow up with mixed continual training rather than sequential fine-tuning alone.

Happy modeling!
