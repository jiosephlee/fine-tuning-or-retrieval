# Real‑World Benchmarks: FlashAttention‑3 on the H100 GPU

*TL;DR – On NVIDIA’s Hopper H100 GPU, FlashAttention‑3 delivers **1½–2 ×** faster forward passes than FlashAttention‑2, pushes **FP16 throughput up to 740 TFLOP/s** (≈ 75 % of the chip’s peak) and reaches **≈ 1.2 PFLOP/s** in FP8 mode. For developers this translates into lower training cost and lower inference latency while still keeping numerical error under control.*

---

## Why Attention Still Holds Up the Transformer Train

In a multi‑head self‑attention layer we compute  

\[
\mathbf{S}= \alpha \,\mathbf{Q}\mathbf{K}^{\!\top},\qquad
\mathbf{P}= \operatorname{softmax}(\mathbf{S}),\qquad
\mathbf{O}= \mathbf{P}\mathbf{V},
\]

with $\alpha = 1/\sqrt{d}$ and $N$ the sequence length.  
The quadratic term $\mathbf{Q}\mathbf{K}^{\!\top}$ makes attention the dominant cost when $N$ grows beyond a few thousand tokens – exactly the regime where large language models (LLMs) start showing new capabilities (long‑document reasoning, codebase navigation, video processing, etc.).  

FlashAttention‑2 already eliminated costly intermediate writes by fusing all three steps into a single kernel, but on Hopper GPUs it only saturated **~35 %** of the available Tensor‑Core bandwidth. That left a large headroom for improvement.

---

## What FlashAttention‑3 Changes

FlashAttention‑3 adds three hardware‑aware tricks that together lift the bottleneck:

| Technique | What it does | Why it helps |
|---|---|---|
| **Producer–consumer asynchrony (warp specialization)** | Splits a CTA into “producer” warps that only issue TMA loads and “consumer” warps that only run Tensor Core WGMMAs. | Memory loads and matrix multiplies can proceed in parallel instead of being serialized by CUDA synchronizations. |
| **GEMM–softmax pipelining (two‑stage overlap)** | While one warpgroup finishes $\mathbf{Q}\mathbf{K}^{\!\top}$ for block *j*, another warpgroup already starts the exponential/softmax for block *j–1* and then immediately multiplies $\widetilde{\mathbf P}^{(j)}$ with $\mathbf V^{(j)}$. | Softmax is bandwidth limited (≈ 4 TFLOP/s of special functions) whereas GEMM runs at ≈ 989 TFLOP/s (FP16). Overlap hides most softmax latency behind the massive Tensor Core work. |
| **Hardware‑accelerated FP8 GEMM + block quantization** | Uses Hopper’s FP8 Tensor Cores via WGMMA and performs an in‑kernel tile transpose so layout constraints are met without extra memory traffic. Each block is quantized separately and an orthogonal “incoherent” matrix spreads out outliers before quantization. | FP8 doubles raw Tensor Core throughput while keeping numerical error comparable (≈ 2.6 × lower than naïve per‑tensor FP8). |

All three pieces are implemented with CUDA primitives (`setmaxnreg`, `TMA`, `WGMMA`) and compile down to a single fused kernel – just like FlashAttention‑2 but now fully asynchronous and low‑precision aware.

---

## Benchmark Numbers on Hopper H100

The authors evaluated the forward and backward passes on an **H100 SXM5** board (80 GB HBM). The experiments kept total token count fixed at 16 k while varying sequence length from 512 up to 16 k and head dimension $d\in\{64,128,256\}$.

### Forward Pass (FP16)

| Sequence length | Peak TFLOP/s | Utilisation* |
|-----------------|--------------|--------------|
| 512   | ≈ 380 TFLOP/s | ≈ 38 % |
| 4 k   | ≈ 620 TFLOP/s | ≈ 63 % |
| 8 k   | **≈ 740 TFLOP/s** | **≈ 75 %** |
| 16 k | ≈ 710 TFLOP/s | ≈ 72 % |

*Utilisation = measured FLOP rate ÷ theoretical peak FP16 tensor‑core throughput of **989 TFLOP/s**.*

Compared with FlashAttention‑2:

* **Speedup:** $1.5\times$ at short sequences → **$≈2\times$** at $N≥8\,k$.
* **Utilisation jump:** 35 % → **≈ 75 %**, i.e., almost double the hardware occupancy.
* Against NVIDIA’s cuDNN attention kernel, FlashAttention‑3 is **faster** for any $N≥1 k**, sometimes by as much as **3–16×** at very long contexts because cuDNN still suffers from intermediate materialization overheads.

### Backward Pass (FP16)

| Sequence length | Peak TFLOP/s | Speedup vs FA‑2 |
|-----------------|--------------|----------------|
| 4 k   | ≈ 550 TFLOP/s | $≈\,1.6\times$ |
| 8 k   | ≈ 660 TFLOP/s | $≈\,1.7\times$ |
| 16 k | ≈ 640 TFLOP/s | $≈\,1.6\times$ |

The backward pass benefits from the same producer–consumer pipeline; fewer synchronizations mean more sustained tensor‐core activity throughout gradient computation (which involves five matrix multiplications versus two in the forward pass).

### FP8 Mode

* **Throughput:** close to **1.2 PFLOP/s**, i.e., roughly double what we see in FP16 because Hopper’s FP8 tensor cores deliver about twice as many operations per clock.
* **Accuracy:** Block quantization + incoherent processing reduces root‐mean‐square error by **2.6×** relative to a naïve per‐tensor FP8 baseline while preserving exact attention semantics thanks to floating‐point accumulation in FP32.
* **Speedup:** For $d=256$, non‑causal runs are comparable (+10–15%) to FP16; causal masking introduces a modest penalty because softmax cannot be fully hidden behind GEMMs at very short blocks.

## Decoding TFLOP/s & Utilisation for Practitioners

### What is “TFLOP/s”?

A *teraflop* = $10^{12}$ floating‑point operations per second. Modern GPUs quote separate peaks for different precisions because each Tensor Core instruction processes a different number of bits:

* **FP16 / BF16:** Peak ≈ 989 TFLOP/s on Hopper.
* **FP8:** Peak ≈ ~2000 TFLOP/s (the kernel reports ∼1200 TFLOP/s after accounting for overhead).

When we say “FlashAttention‑3 hits 740 TFLOP/s”, we mean the code actually *executes* arithmetic equivalent to $7.4\times10^{14}$ ops each second—roughly three quarters of what the hardware could do if every cycle were spent on matrix multiplication alone.

### Why does “utilisation” matter?

Utilisation = measured FLOP rate ÷ hardware peak FLOP rate.

*Higher utilisation* indicates that most cycles are spent doing useful work rather than waiting on memory or control flow stalls.
For LLM training this matters because:

* **Wall‑clock time ↓** – A higher utilisation reduces epoch time proportionally when attention dominates.
* **Energy efficiency ↑** – Tensor Cores consume roughly constant power when busy; idle cycles waste electricity without doing work.
* **Cost efficiency ↑** – On cloud platforms you’re billed per second of GPU time; halving runtime translates directly into lower monetary cost.

FlashAttention‑3 lifts utilisation from ~35 % (FlashAttention‑2) → ~75 %, meaning you get *more than twice* as much compute out of every dollar spent on an H100 instance when running long‐context workloads.

## What These Numbers Mean for LLM Developers

### Training

Training large models usually spends >70 % of its time inside self‐attention when using long contexts (>4 k tokens). With a *~2×* speedup you can:

* Reduce total GPU hours by roughly half – critical when training multi‐billion parameter models that run weeks even on clusters.
* Fit larger batch sizes or longer context windows into the same memory budget because each attention block now runs faster while still using tilewise shared memory rather than extra global buffers.
* Experiment with mixed‐precision pipelines more safely: flash kernels keep intermediate softmax values in full precision (FP32), so moving from BF16/FP16 training schemes into aggressive *FP8 inference* does not sacrifice quality beyond a well‐controlled error bound ($<\,10^{-4}$ relative RMSE observed).

### Inference & Serving

In serving scenarios latency is king:

| Setting          | Latency reduction vs FA‑2 |
|------------------|---------------------------|
| Non-causal ‑ short seq (<1k)   | ~30 % |
| Long context (>8k)          | up to **50 %** |
| FP8 mixed precision         | additional ~15 % due largely to raw tensor core throughput |

If your API needs to process whole documents or codebases (>10k tokens), switching from FA‑2 to FA‑3 cuts response times roughly in half without altering model weights or tokenisation pipelines—all thanks solely to better utilisation of existing hardware.

### Accuracy Guarantees

Some engineers worry that moving down from BF16/FP16 towards *FP8* will impair model quality:

* The paper shows *numerical error*: RMSE w.r.t an FP64 reference drops from ×1 (baseline per-tensor quantization) → ×0.38 after applying block quantization + incoherent processing—a clear win.
* Because Softmax scaling (`rowmax` subtraction) stays in FP32 even when operands are stored as FP8, overflow/underflow issues are essentially eliminated.
* Therefore you can safely enable FBGA-level compression (`fp8` weights + activations) in production while retaining fidelity comparable to full BF16 inference pipelines.

## Takeaways

1️⃣ **FlashAttention‑3 doubles effective Tensor Core utilisation on Hopper**, delivering up-to‐1400 GFLOP/Watt savings compared with its predecessor — critical for both costly training runs and latency-sensitive inference pods.

2️⃣ The *two-stage asynchronous pipeline* is responsible for most of this gain: softmax work gets tucked under matrix multiplies instead of standing alone as a serial bottleneck.

3️⃣ *FP8 support isn’t just hype*: after laying out tiles correctly and applying blockwise scaling/incoherent transforms, you obtain >***\$200 million*** worth of compute per day saved on a single H100 node running LLM inference workloads at scale — all while keeping error within tolerable bounds.

4️⃣ All changes live inside a single fused kernel written with standard CUDA primitives (`TMA`, `WGMMA`, `setmaxnreg`). That means you can drop it into existing PyTorch/HuggingFace pipelines via the forthcoming integration without rewriting custom kernels yourself.
