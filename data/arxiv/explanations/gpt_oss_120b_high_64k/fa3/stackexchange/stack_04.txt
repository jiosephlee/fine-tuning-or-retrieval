\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### How does ping‑pong scheduling overlap softmax with GEMM across warp groups?
Question:
The authors propose "ping‑pong" scheduling where warp group 1 computes softmax while warp group 2 performs GEMMs, then they swap roles. I am unsure how the `bar.sync` instructions enforce this ordering without causing deadlocks or excessive stalls. Can anyone provide a timeline diagram or step‑by‑step description showing which operations (softmax exponentials, row max reductions, WGMMA) run concurrently on the two warp groups?

**Answer**

In *FlashAttention‑3* the “ping‑pong” schedule is nothing more than a two‑stage software pipeline that lets the cheap soft–max work run at the same time as a heavyweight WGMMA (the Hopper‑specific warp–group matrix–multiply–accumulate).

The key ingredients are  

* **two warp–groups** inside each CTA – `\(WG_0\)` and `\(`\(WG_1\)\)` – each specialised either as “producer” (only TMA loads) or “consumer” (only computation);  
* a **circular shared–memory buffer** with *s* slots that is guarded by a single CUDA barrier (`bar.sync`);  
* **asynchronous** WGMMA instructions – they are queued onto the Tensor–Core engine and return control immediately, so a warp can continue issuing other instructions while the MMA is still running;  
* **explicit ordering** points (`bar.arrive`, `bar.wait`) that guarantee that a consumer never reads a buffer slot before the producer has finished writing it, and that no two warp–groups ever try to use the same slot at the same instant.

Below I walk through one iteration of the pipeline, showing exactly which operation lives on which warp–group and how the barriers keep everything moving without deadlock.

---

### 1. The data flow under a circular buffer  

Assume a CTA processes a query tile `\(Q_{i}\)` (`\(B_{r} \times d\)`).  
The key/value matrices are split into `\(T_{c} = \lceil N / B_{c} \rceil\)` blocks `\(K_{j}, V_{j}\)`.  
The buffer has *s* stages (`\(stage = j\bmod s\)`).

For every stage \(j\) we have  

| Stage | Producer action | Consumer action |
|------|-----------------|----------------|
| `load_KV(j)` | TMA copies `\(K_{j}\), \(V_{j}\)` `\(\to\)` shared memory slot *stage* | — |
| `SS_GEMM(j)` | — | WGMMA computes `\(S_{i}^{(j)} = Q_{i}\,\cdot\,K_{j}^{\top}\)` |
| `softmax(j)` | — | row‑max reduction `\(\to\)` exponentials `\(\to\)` scaled row sum |
| `RS_GEMM(j)` | — | WGMMA computes `\(O_{i} \gets O_{i} + \tilde{P}_{i}^{(j)}\,\cdot\,V_{j}\)` |

The consumer never touches a slot until it has been marked **available** by an  
`bar.arrive(stage)` issued by the producer after the TMA completes.  
Conversely, once a consumer finishes using slot *stage*, it signals  
`bar.arrive(stage)` again so that the producer may reuse it for the next block.  
Because *stage* advances monotonically (`\(j\!\to\! j+1\)`) there is no circular wait – every dependency points forward in time.

---

### 2. Two‑warp‑group ping‑pong  

The above table describes only one logical consumer thread–block.  
In FlashAttention‑3 we split that consumer into **two physical warp–groups**
that run alternately:

| Warp‑group | Work done in iteration *j* |
|------------|----------------------------|
| **WG<sub>0</sub>** | **Softmax** of block \(j\) (`softmax(\(j\))`) **and** RS GEMM of block \(\,j{-}1\,\) (`RS_GEMM(\(j{-}1\))`). |
| **WG<sub>1</sub>** | **SS GEMM** of block \(\,j{+}1\,\) (`SS_GEMM(\(j{+}1\))`). |

Thus while WG<sub>0</sub> is busy evaluating exponentials and normalising rows,
WG<sub>1</sub> has already launched an asynchronous matrix multiply for
the next key block. When WG<sub>0</sub> finishes its softmax it immediately switches role:
it now launches its own SS GEMM for block \(\,j{+}2\,\), while WG<sub>1</sub> …  

This “ping–pong” exchange continues until all key/value blocks have been processed.

#### Step‑by‑step schedule (simplified timeline)

```
cycle    WG0                         WG1
-----------------------------------------------------------------
t0   load Q_i   <- TMA                –               (producer work)
t1   wait K_0      <- bar.wait(0)      –               (wait for first KV)
t2   Scur = Q_i·K_0^T   <- WGMMA           –               (async)
t3   bar.arrive(0)                  –               (slot 0 free)
t4   // ----> softmax of Scur ----> //               (low-throughput)
t5   // ----> rescale O_i            //               (uses ℓ,m)
t6   load K_1,V_1 <- TMA                –               (producer fills slot 1)
t7   // ----------- overlap -----------             
t8   Snext = Q_i·K_1^T <- WGMMA        <-─┐              (async)
t9   wait V_0      <- bar.wait(0)     │              (need V_0 for RS_GEMM)
t10  O_i += Ṕ_cur·V_0 <- WGMMA       │              (async)
t11  bar.arrive(0)                  │              (slot 0 reclaimed)
t12  // ----> softmax of Snext ---->│              (WG0 continues)
t13  // ----> rescale O_i            │
t14  load K_2,V_2 <- TMA                │
t15  …                               │
```

* The **asynchronous** calls (`WGMMA`) at t2, t8 and t10 do not stall
the warp; they merely enqueue work onto the Tensor Core engine.  
* At t4–t5 WG<sub>0</sub> runs exponentials, reductions and row scaling –
operations that use only scalar pipelines.  
* At t8–t10 WG<sub>1</sub> already started its own matrix multiply
(`SS_GEMM(\(j{+}1\))`) **while**
WG<sub>0</sub> is still finishing softmax for block \(j\).
That is exactly what we call “hidden” softmax.  
* The barriers appear only when a shared‐memory slot changes ownership:
`bar.wait(stage)` before reading a tile,
`bar.arrive(stage)` after finishing its use.
Because both warp groups always operate on different stages
(`\(stage=j\bmod s\)` vs `\(stage=(j{+}1)\bmod s\)`)
there is never a situation where WG<sub>0</sub> waits for something
that can only be produced by WG<sub>1</sub>`after wg<sub>​…​>`—hence no deadlock.  
* When all blocks have been consumed an epilogue rescales the final output
`\(\displaystyle O_{i} \gets O_{i}\big/\ell_{i}\)`
after a final `bar.wait` ensures that every pending RS GEMM has completed.

### 3. Why “ping–pong” works on Hopper  

Hopper’s Tensor Cores execute WMAs completely independently from CUDA cores.
A regular CUDA instruction stream cannot see inside an enqueued WMAs;
it simply continues issuing later instructions.
Consequently an instruction such as an exponential can be scheduled immediately
after an WMAs without waiting for its result – unless we explicitly insert
a barrier.

The algorithm therefore  

* issues **WGMAs first**, letting them run in parallel;
* does **all low‑throughput work** that depends only on registers (`softmax`);
* finally inserts a `.bar.wait` only when it needs data produced by the WMAs
(e.g., reading back row‐wise maxima).

Because each barrier synchronises only one direction of data flow,
both sides keep making progress and utilisation climbs from ≈35 % up to ≈75 %
(see Fig.​ 4 of the paper).

### 4. Summary picture  

```
                     ┌───────────────────────┐
                     │    Shared‐memory slots │   <-- circular buffer,
                     └─────────────▲─────────┘          s stages
                                   │ bar.arrive / bar.wait

      ┌──────────────►─────────────────────────────────────►───────────────┐
      │                                                                  │
      │    WG₀                         WG₁                           │
      │    ──────────────────────       ───────────────────────       │
      │    Softmax(j)                 SS_GEMM(j+1)                     │
      │    RS_GEMM(j−¹)               …                               │
      │                                                                  │
      └──────────────────────────────────────────────────────────────────┘

Each iteration advances both groups by one block; after one full cycle they “ping”
and “pong” their roles. The explicit barriers guarantee that no group ever reads
a tile before it has been written, while asynchronous WMAs hide all idle cycles,
producing exactly the overlap illustrated in Fig 5 of FlashAttention​−​3.
```

In short, ping pong scheduling achieves simultaneous execution of  

`\(\displaystyle softmax(j)\;\!+\;\!RS_{\text{GEMM}}(j{-}1)\;\;\leftrightarrow\;\;
SS_{\text{GEMM}}(j{+}1)\)`  

by assigning those two halves to different warp groups,
using a circular shared‐memory buffer guarded by lightweight CUDA barriers.
Because every dependency points forward (\(j{\rightarrow} j{+}1\)) and because WMAs are truly async,
the schedule never deadlocks and avoids long stalls—hence why FlashAttention​−​3 attains up to 2× higher TFLOPs on H100.
