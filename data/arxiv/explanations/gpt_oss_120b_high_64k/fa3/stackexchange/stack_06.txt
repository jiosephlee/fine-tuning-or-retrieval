\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What are WGMMA instructions and how do they differ from earlier HMMA/Tensor Core calls?
Question:
"WGMMA" stands for warp‑group‑wide matrix multiply‑accumulate introduced in Hopper. How does its programming model differ from the older `hmma`/`mma` intrinsics used on Ampere? In particular, what changes are required in kernel code to switch from HMMA to WGMMA, and how does WGMMA enable asynchronous execution?
Answer:
**Short answer** – WGMMA is a new Tensor‑Core instruction introduced with NVIDIA’s Hopper architecture that lets a *warp‑group* (four contiguous warps) issue a single matrix‑multiply‑accumulate operation. It differs from the older HMMA/​MMA intrinsics of Ampere in three important ways:

1. **Scope of the operation** – HMMA works per‑warp; every warp independently multiplies a $64\times 64$ (or $128\times 64$) tile that lives entirely in its own registers/shared memory. WGMMA aggregates the registers of four warps and computes a larger tile (e.g.\ $128\times 128$ or $256\times 256$) in one instruction, so fewer instructions are needed and the hardware can keep more Tensor‑Core lanes busy.

2. **Asynchronous execution** – On Hopper the Tensor‑Core pipeline is decoupled from the normal CUDA‑core pipeline. A WGMMA instruction returns control to the issuing warp‑group immediately; the actual multiply‑accumulate proceeds in parallel with any subsequent instructions (e.g.\ loads through the Tensor Memory Accelerator or soft‑max exponentials). With HMMA the compiler inserts an implicit “wait” after every call because the legacy Tensor‑Core pipeline blocks the issuing warp.

3. **Layout constraints & low‑precision support** – WGMMA supports FP8 directly but imposes a stricter “k‑major” layout on its operands, whereas HMMA accepted both mn‑major and k‑major layouts for FP16/BF16. Consequently a kernel that switches to WGMMA must reshape one of its matrices (normally V) before it reaches shared memory or perform an in‑kernel transpose using LDSM/STSM.



### What you have to change in kernel code

When you port an existing Ampere kernel that uses `hmma`/`mma` intrinsics to Hopper’s `wgmma`, the transformation is essentially a change of *thread‑group organization* plus a few architectural‐specific calls:

1. **Split the CTA into producer/consumer warp‑groups**  
   In FlashAttention‑3 the CTA is divided into two warp‑groups: one set of warps only performs TMA loads (`producer`) while the other set only issues WGMMAs (`consumer`). This split can be expressed with PTX’s `setmaxnreg` directive which temporarily reduces register count for producer warps so that more registers become available for consumer warps that need them for matrix fragments.

2. **Replace every HMMA call with a WGMMA call**  
   In user code this means swapping something like  

   ```cpp
   // Ampere
   __hmma16816(...);      // implicit wait after it
   ```  

   with  

   ```cpp
   // Hopper
   wgmma_m64n64k64_fp16(...);   // async – no implicit wait
   ```  

   The exact name depends on datatype and tile size (`wgmma_m128n128k64_fp8`, etc.). If you use CUTLASS / cuTensorCore abstractions you simply change the template arguments from `<tHmma>` to `<tWgmma>`; CUTLASS automatically emits the proper PTX.



3. **Adjust operand layout**  
   For FP8 you must ensure that both A and B operands are stored *k‑major* in shared memory (contiguous in K). A common way, as described in § 4\.2 of FlashAttention‑3, is to let the producer warp‑group transpose V on‑the‐fly after loading it into SMEM using `ldmatrix`/`stmatrix`. For FP16 you can keep either layout, but keeping everything k\-major eases code reuse across precisions.



4. **Remove stale synchronisation**  
   Because WGMMA does not block, any `__syncthreads()` placed immediately after an HMMA becomes unnecessary and actually harms performance. Instead insert explicit barriers only where data movement between producer/consumer groups must be ordered, e.g.:

   ```cpp
   // After loading Q/K/V into SMEM
   bar.sync [0];          // tell consumer group data is ready
   // Consumer group:
   wgmma(...);            // launch async GEMM
   // … continue issuing TMA loads for next tiles …
   ```



5. **Add explicit “wait” when you really need results**  
   The consumer eventually needs the accumulator before it can apply softmax scaling or write out O. At those points you insert either a `bar.sync` that synchronises on the same buffer stage used by producers, or leverage CUDA’s “asynchronous collective” API (`cuda::pipeline`). In FlashAttention‑3 this appears as “Commit and wait” after each WGMMAs which really maps to a fence that ensures prior WGMMAs have completed before using their output.



### How asynchrony translates into speed

In AMPERE’s synchronous model each iteration of attention’s inner loop looked roughly like  

```
load K_j,V_j → __syncthreads()
S = Q_i · K_j^T        // hmma
softmax(S)
O += P·V_j            // hmma
```

Every `hmma` stalled the warp until its result was ready, so while the second GEMM was running no other work could be issued by that CTA – even though the GPU had idle tensor‐core pipelines waiting for new data.



With WGMMA these steps become  

```
load K_j,V_j → async TMA               // producer warps keep loading
S_next = Q_i · K_{j+1}^T ← wgmma async // consumer issues next GEMM early
softmax(S_cur)                         // runs while previous wgmma finishes
O += P_cur·V_j ← wgmma async           // overlaps with softmax of next block
```

Because each WGMMAs lives in its own hardware queue, a CUDA core can start exponentials (`expf`) as soon as it has received `S_cur`, while another set of Tensor Cores already works on `S_next`. The paper reports an improvement from ~570 TFLOP/s (HMMA path) to ~620–640 TFLOP/s when merely adding this ping–pong scheduling; full two–stage pipelining pushes utilization up to ~740 TFLOP/s (≈75 % of H100’s peak).

In practice this means:

* **Higher occupancy:** Four warps jointly feed one Tensor Core instruction, so register pressure per thread declines compared with allocating an entire fragment per warp.
* **Better latency hiding:** While one WGMMAs stalls waiting for its inputs, another independent WGMMAs already runs; softmax—previously a bottleneck because its throughput is roughly two orders of magnitude lower than Tensor Cores—gets overlapped almost completely.
* **Cleaner code path:** Producer/consumer split mirrors classic CPU producer–consumer pipelines but at CUDA‐warp granularity; no explicit double buffering of shared memory beyond what already existed for HMMA, just an extra circular buffer stage advertised by `setmaxnreg`.



### Putting it together

To convert an existing Ampere‐based attention kernel:

1. Refactor CTA layout into two logical warp groups.
2. Replace every `hmma` intrinsic with its matching `wgmma` variant (CUTLASS makes this almost one line change).
3. Adjust tensor storage so that all GEMM operands respect WG​M​M​A’s k\-major constraint—typically by adding an LDSM/STSM based transpose inside the producer group.
4. Remove hidden synchronisation after each matmul and introduce explicit barriers only where inter‑group data dependencies exist.
5. If targeting FP8, also add block quantization / incoherent processing as described in § 4\.2, because WG​M​M​A only accepts k\-major FP8 tiles.



The net effect is an attention kernel whose matrix multiply stage runs asynchronously with both data movement (via TMA) and non‑matmul work (softmax), achieving up to twice the utilization observed with older HMMA based kernels on H100 GPUs—as demonstrated by FlashAttention‑3’s experimental results.​
