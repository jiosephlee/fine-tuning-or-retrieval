\title{Stack Exchange of the Paper: "LongRoPE: Extending LLM Context Window Beyond 2 Million Tokens"}

### What exactly does the RoPE embedding formula in Equation (1) represent?
Question:
The paper defines the RoPE encoding for a token at position $n$ as a vector $[\cos(n\theta_0), \sin(n\theta_0), \cos(n\theta_1), \dots , \sin(n\theta_{d/2-1})]$ (Eq. 1). I am confused about how this simplified form relates to the full rotary positional embedding used in practice. Specifically:
* How are the frequencies $\theta_i=\theta^{-2i/d}$ derived from a base $\theta$?
* Why are cosine and sine interleaved per dimension rather than having separate sinusoid channels?
* Does this formulation assume any particular ordering or reshaping of query/key vectors before multiplication?
Any clarification on how Eq. (1) maps onto the standard implementation of RoPE would help me understand the rest of the paper.
Answer:
**Answer**

Equation (1) is a compact way of writing the scalars that later appear inside the 2‑D rotation matrices applied to the query‑ and key‑vectors in Rotary Position Embedding (RoPE).  
In practice one never builds an explicit “positional vector’’ of the form  

$$
[\cos (n\,\theta_{0}),\;\sin (n\,\theta_{0}),\;\cos (n\,\theta_{1}),\;\sin (n\,\theta_{1}),\,dots]
$$  

and adds it to the token embedding.  
Instead those scalars are used to **rotate** pairs of hidden‑state dimensions, which is why the cosine and sine terms are interleaved.



---------------------------------------------------------------------

### Where do the frequencies $\boldsymbol{\theta_i=\!\theta^{-2i/d}}$ come from?

The original sinusoidal encoding introduced by Vaswani *et al.* assigns a distinct angular frequency to every “half‑dimension’’:

$$
{\rm freq}_i=\frac{1}{10000^{\,2i/d}}\qquad i=0,\dots,\frac d2-1 .
$$

If we denote the base value by a generic symbol $\theta$ (the paper uses $\displaystyle \theta = 10\,000$), then  

$$
{\rm freq}_i=\frac{1}{\;\!\displaystyle \theta^{\,2i/d}} .
$$

The **rotary angle** for a token at absolute position $n$ is simply  

$$
n\,{\rm freq}_i=n\,\theta^{-2i/d}= 
        \frac{n}{(\,\theta^{\,2/d})^{\,i}} ,
$$

or more compactly  

$$
n\,\theta_i,\qquad 
    {\rm with }\;
    \displaystyle \theta_i=\!\:\!\theta^{-2i/d}.
$$

Thus Equation (1) is nothing more than a listing of those angles after applying cosine and sine once:

*low‑index* dimensions ($i=0,1,\dots$) receive **high​‑frequency** angles because $\displaystyle \theta^{-2i/d}$ is close to one,
while high indices receive **low​‑frequency** angles because the exponent makes the value much smaller.  
This geometric progression ensures that short‑range relative positions are captured by many fast‑oscillating components and long‑range relations are captured by slowly varying components—a principle identical to the classic sinusoidal PE.



---------------------------------------------------------------------

### Why are cosine and sine interleaved?

A single RoPE operation works on a **pair** of numbers considered as a point in a two–dimensional plane:

$$
%
\begin{pmatrix}x\\y\end{pmatrix}
\xrightarrow{\text{rotate } \phi}
R(\phi)\begin{pmatrix}x\\y\end{pmatrix},
   \qquad
R(\phi)=
   \begin{pmatrix}
      \cos \phi & -\,\sin \phi \\[4pt]
      \sin \phi &   \phantom{-}\!\cos \phi
   \\end{pmatrix}.
%
$$

If we store a hidden vector whose first half contains all $x_k$’s and whose second half contains all $y_k$’s, we would have to remember which entry belongs to which coordinate when we form $R(\phi)$.  
Interleaving solves this bookkeeping problem: every **even** index together with its **next odd** index already forms a natural pair  

```
[ x₀ , y₀ , x₁ , y₁ , … ]
      ^        ^    ^
   cos φ₀   sin φ₀ …
```

Consequently the same scalar $n\,\theta_i$ can be turned into two numbers – its cosine and sine – and placed next to each other.  
When we later reshape the tensor into shape `(..., d//2, 2)` we obtain exactly those planes on which a single rotation matrix acts.



---------------------------------------------------------------------

### From Eq.\,(1) to the code that multiplies queries/keys

Assume a model with hidden size $d_{\textit{model}}$, multi‑head attention with $h$ heads,
and each head has dimension $d_{\textit{head}}$.  
Only a subset of each head – usually all $d_{\textit{head}}$ or some prefix – participates in RoPE.
Let us call this rotary sub‑dimension $d_{\textit{rot}}=d_{\textit{head}}$ (it must be even).

A typical implementation follows these steps:

| step | description |
|------|-------------|
| **(a)** | Compute an array ``inv_freq`` of length ``d_rot/2``:<br/>$$ {\rm invfreq}_i=\frac{1}{\,!\displaystyle \theta^{\,2 i / d_{\rm rot}}}. $$ |
| **(b)** | For every absolute position $n=0,\dots,L-1$ form the outer product ``positions[:,None] * inv_freq[None,:]``.<br/>The result has shape ``[L, d_rot/2]`` and contains all angles $n\,\theta_i$. |
| **(c)** | Take element‑wise ``cos`` and ``sin`` → tensors ``cosine`` and ``sine``, both ``[L,d_rot/2]``. |
| **(d)** | Reshape queries ($Q$) and keys ($K$) so that their last dimension becomes ``[d_rot/2, 2]``.<br/>In PyTorch this looks like ``Q = Q.view(..., d_rot//2, 2)`` . |
| **(e)** | Apply the rotation without ever materialising an explicit vector like Eq.\,(1):<br/><br/>```python<br/># Q[..., 0] are x components,<br/># Q[..., 1] are y components.<br/>Q_rot   = Q[..., 0] * cosine[..., None] - Q[..., 1] * sine[..., None]<br/>Q_rot_y = Q[..., 0] * sine[..., None] + Q[..., 1] * cosine[..., None]<br/>Q_out   = torch.stack([Q_rot, Q_rot_y], dim=-1)<br/>```<br/>The same operation is performed on ``K``. |
| **(f)** | Finally flatten back (`view`) so that shape becomes ``[batch, heads, seq_len, d_head]``. |

Notice three facts that match Eq.\,(1):

* The scalar values ``cosine[n,i]=cos(n\,\!\theta_i)`` and ``sine[n,i]=sin(n\,\!\theta_i)`` are exactly those appearing in Eq.\,(1).
* Because we paired every even index with its following odd index before stepping into step (d), no additional permutation is required – **the ordering assumed by Eq.\,(1)** is simply “even–odd alternating”.
* The rotation is applied element‑wise across all heads and batch items; no extra “positional channel’’ exists beyond these two tensors.



---------------------------------------------------------------------

### Summary – how Eq.\,(1) maps onto “standard’’ RoPE

* Equation (​1​) lists the scalar trigonometric values generated from an underlying geometric series of frequencies,
  given a base value $\displaystyle \theta = 10000$.
* Those values are not concatenated as an extra embedding vector;
  they serve as parameters of a set of independent planar rotations — one rotation per frequency index $i.$
* Interleaving cosine with sine guarantees that each planar rotation sees its two coordinates side‑by‑side,
  allowing an efficient implementation that merely reshapes queries/keys into “pairs’’ (`(..., d/2 , 2)`),
  multiplies by ``cos`` on one component,
  adds/subtracts ``sin`` times the swapped component,
  then reshapes back.
* Consequently any correct RoPE implementation implicitly assumes exactly this alternating ordering;
  if one were to rearrange dimensions arbitrarily one would have to permute them back before applying step (e).

Thus Eq.\,(​1​) should be read not as a stand‑alone positional vector but as a compact prescription of **which cosine/sine scalars belong together when rotating each hidden‑state pair**—the exact recipe used by all mainstream RoPE codebases. This viewpoint also clarifies why later sections of the paper talk about “rescaling’’ each angle separately ($$\lambda_i^{-1}$$): they simply replace $n\,\!\theta_i → n\,\!\theta_i/\lambda_i,$ which changes the rotation speed per dimension while preserving the same interleaved structure required for efficient computation.
