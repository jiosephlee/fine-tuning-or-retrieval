\title{Stack Exchange of the Paper: "LongRoPE: Extending LLM Context Window Beyond 2 Million Tokens"}

### How are multiple sets of RoPE rescale factors applied dynamically at inference time?
Question:
After extending a model to 2048 k tokens, LongRoPE "adjusts" rescale factors again for short context windows (e.g., ≤8 k). The paper says "During inference, if the sequence length is less than 8k, we update RoPE with the searched rescale factors." I wonder:
* Is this implemented by swapping out an entire positional embedding table depending on input length,
or by computing per-token angles on-the‑fly using conditional logic?
* Does this dynamic switching introduce any latency overhead compared with static embeddings?
* Are there any pitfalls when mixing multiple factor sets within one batch containing sequences of different lengths?
Clarifying implementation details would aid developers who want to adopt LongRoPE.
Answer:
**Short answer:**  
At inference LongRoPE does **not** keep several whole “positional‑embedding tables” in memory.  
Instead it stores **one vector of per‑dimension rescale factors** $\lambda_i$ for each target window (e.g. a “256 k” set and an “8 k” set) and plugs the appropriate vector into the ordinary RoPE formula (Eq.~3 of the paper).  
When a batch is processed the code checks whether the effective sequence length $\displaystyle N$ is below the trigger (8 k); if so it uses the short‑window vector $\lambda^{(8k)}$, otherwise it uses the long‑window vector $\lambda^{(256k)}$ (or the final 2 048 k set).  
The change amounts to a few element‑wise divisions/multiplications before calling ``torch.sin``/``torch.cos``, so there is virtually no additional latency compared with a static RoPE implementation.  

Below I explain why this works, what the implementation looks like in practice, and what you need to watch out for when you mix different factor sets inside a single batch.

---

### 1\. How the “switch’’ is implemented  

RoPE encodes a token at position $n$ in dimension $i$ by  

$$
\bigl[\cos(\tfrac{n}{\beta^{i}}),\,\sin(\tfrac{n}{\beta^{i}})\bigr],
\qquad
\beta=\theta^{2/d},
$$

where $\theta=10\,000$ in most LLMs.  

LongRoPE replaces $\displaystyle\tfrac{1}{\beta^{i}}$ with  

$$
\frac{1}{\beta^{i}}\;\mathbb I(\hat{\lambda}_{i},\,\hat n)
=
{
    \begin{cases}
        \tfrac{1}{\beta^{i}}                         & n<\hat n\\[4pt]
        \tfrac{1}{\beta^{i}\,\lambda_{i}}           & n\ge \hat n,
    \end{cases}
}
$$

as described in Section 3 (“Shorter context window recovery”).  
All that changes at inference time is the **vector**

$$
r_i=\frac{1}{\beta^{i}\,\lambda_{i}},
$$

which multiplies every position index $n \ge \hat n$. The pipeline therefore remains

```python
# base inverse frequencies from the pretrained model
inv_freq = theta ** (-2 * torch.arange(d // 2) / d)

# pick which scaling vector we need
if seq_len <= 8192:
    scale = lambda_short      # list/torch.tensor of shape [d//2]
else:
    scale = lambda_long

# apply the scaling only after position hat_n
inv_freq_scaled = inv_freq / scale          # broadcast over dimensions
pos = torch.arange(seq_len, device=device).unsqueeze(-1)
freqs = pos * inv_freq_scaled                # shape [seq_len, d//2]

# usual sin/cos + rotary multiplication
sin, cos = freqs.sin(), freqs.cos()
...
```

There is **no separate lookup table** that has been pre‑computed for every possible $n$; everything is derived analytically from ``inv_freq_scaled``. Because ``torch.arange`` and a single element‑wise division are $O({seq_len}\cdot d)$, the extra work compared with vanilla RoPE is just an additional multiplication/division by ``scale``, which costs far less than the quadratic attention that follows.

---

### 2\. Latency impact  

* **Computation:**  
  - A vanilla RoPE call already computes two sinusoid tensors (`sin`, `cos`). Adding a division by ``scale`` is a constant‑time operation per dimension and does not increase asymptotic complexity.
* **Memory:**  
  - Only one extra float tensor of size $d/2$ needs to be kept (the chosen scaling vector). Even for a 7 B‑parameter model ($d≈4096$) this is < 16 KB.
* **Cache friendliness:**  
  - The same code path is used whether we are in “short’’ or “long’’ mode; existing kernels such as FlashAttention can still reuse KV‑caches because all keys/queries are rotated with *the same* frequency vector throughout a generation run.
* **Empirical numbers** reported by the authors’ open‑source implementation (see their GitHub repo) show an increase of ≤ 0.5 ms per forward pass on an A100 when toggling between factor sets—well within measurement noise.

Hence dynamic switching does **not** introduce any noticeable slowdown compared with static embeddings.

---

### 3\. Mixing several factor sets inside one batch  

Transformers normally process a minibatch where **all sequences share identical rotary parameters**, because:

1\. The sinusoid matrix (`freqs`) is built once per forward call and broadcast over the whole batch.<br>
2\. KV‑caches used during autoregressive generation store keys/queries already multiplied by those sin/cos values; changing them partway through would corrupt cached states.<br>

If your batch contains both short (< 8 k) and long (> 8 k) inputs you have two practical options:

| Strategy | How it works | Pros | Cons |
|----------|--------------|------|------|
| **Split into sub‑batches** | Separate inputs into “short’’ and “long’’ groups, run two forward passes with their own ``scale`` vector, then concatenate results. | Exact use of optimal factors for each group; no cache invalidation issues. | Slightly higher wall‑time due to two passes (often offset by better accuracy). |
| **Pad everything to longest length & use long factors everywhere** | Pad short sequences up to max length in batch and always apply ``lambda_long``.| Simpler code path; single pass.| Short inputs suffer unnecessary interpolation → higher perplexity on those examples.|

A third “dynamic mask’’ approach—building a per–position mask so that positions $<\,\hat n$ use $\lambda=1$ while later ones use $\lambda_{i}$—is feasible but only works when *all* samples share the same $\lambda_i$. It cannot accommodate two completely different vectors ($$\lambda_{\text{short}}$$ vs $$\lambda_{\text{long}}$$) inside one tensor without custom kernels because each head’s attention kernel expects a single set of rotation coefficients.

Therefore most implementations adopt **sub‑batching** when mixed lengths appear during training or evaluation. In generation pipelines where each request typically runs independently there’s no mixing problem at all: just inspect ``len(prompt)+len(completion)`` once and pick the appropriate scaling vector before constructing rotary embeddings.

---

### 4\. Summary of best practices  

* Store only the per‑dimension scaling vectors (`$\lambda_i$`) for each target window (e.g., `[\,λ^{(8k)}\,]`, `[\,λ^{(256k)}\,]`, `[\,λ^{(2048k)}\,]`).  
* At inference start,
    ```python
    scale = select_scale(seq_len)
    inv_freq_scaled = base_inv_freq / scale
    ```
   where ``select_scale`` implements ``if seq_len < 8192 ⇒ short‐scale else long‐scale``.
* Recompute sin/cos tensors **once per forward pass**; there is no need for pre‑materialised large lookup tables.
* Expect **negligible extra latency** (< 1% of total GPU time).
* When processing a heterogeneous minibatch,
    - either split into homogeneous sub‑batches,
    - or accept that all entries will use whichever scale corresponds to the longest sequence,
    - never mix two distinct scale vectors inside a single kernel call unless you modify low‐level attention kernels.
* Remember that KV‑cache entries become tied to whatever scale was used when they were created; changing scales mid‐generation forces cache invalidation (a simple ``model.reset_cache()`` call).

With these points in mind you can safely integrate LongRoPE’s multiple rescaling regimes into existing PyTorch/Transformers pipelines without sacrificing speed or stability, while preserving the improved perplexity that motivated the method in Section 3 of the paper.
