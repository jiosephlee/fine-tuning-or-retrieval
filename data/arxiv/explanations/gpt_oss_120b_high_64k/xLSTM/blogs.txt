# Why LSTMs Are Making a Comeback: From 1990s Roots to Billion‑Parameter Models  

## The LSTM’s Golden Era  

When Hochreiter and Schmidhuber introduced the **Long Short‑Term Memory** (LSTM) network in the early 1990s, they tackled the notorious *vanishing gradient* problem of recurrent neural networks. Their key insight was the **constant error carousel**—an additive update of a hidden cell state—combined with three sigmoid gates (input $i_t$, forget $f_t$, output $o_t$):

\[
c_t = f_t\,c_{t-1} + i_t\,z_t ,\qquad 
h_t = o_t\,\psi(c_t) .
\]

This simple machinery let LSTMs retain information over long time horizons. Over the next two decades they powered everything from handwriting synthesis to game‑playing agents such as AlphaStar and OpenAI Five. Linguistic “neurons” emerged inside their cells, capturing syntax, sentiment, even number concepts—proof that recurrent networks can learn deep abstractions.

## Why Transformers Superseded LSTMs  

Around 2017 the **Transformer** arrived with **self‑attention**, offering two decisive advantages:

1. **Parallelism** – attention can be computed across all positions at once, while classic LSTMs require sequential processing.  
2. **Scalability** – stacking many attention layers produced huge language models (GPT‑3, Llama) that outperformed recurrent models on virtually every benchmark.

Consequently most research shifted toward Transformer‑based large language models (LLMs), and LSTMs fell out of the spotlight despite their elegant recurrence logic.

## Core Limitations That Held Classic LSTMs Back  

Even though powerful, vanilla LSTMs suffer from three practical drawbacks:

| Limitation | What It Means |
|------------|---------------|
| **Irreversible storage** | Once a value is written into the scalar cell $c_t$, revising it later is hard. This hurts tasks like nearest‑neighbor search where you may need to replace a stored entry with a better match. |
| **Scalar memory bottleneck** | Each cell stores only one number, limiting capacity especially for rare token prediction where richer representations are needed. |
| **Sequential bottleneck** | Hidden‑to‑hidden connections enforce strict step‑by‑step computation, preventing the massive parallelism that makes Transformers fast on GPUs. |

These gaps gave attention‐based models a decisive edge.

## Reviving Recurrence – What *xLSTM* Brings to the Table  

The recent **xLSTM** paper revisits these old ideas *and* equips them with modern tricks borrowed from today's LLM toolbox. The result is an extended family of recurrent cells that scale to billions of parameters while addressing each classic limitation.

### 1. Exponential Gating + Stabilization  

Instead of limiting gates to sigmoid outputs $\sigma(\cdot)\in(0,1)$, xLSTM allows **exponential gates** $\exp(\tilde{i}_t)$ and optionally $\exp(\tilde{f}_t)$. This lets the network amplify or suppress signals far beyond the sigmoid’s narrow range—critical for *revising* stored information quickly.  

Because exponentials can explode numerically, xLSTM introduces a *stabilizer state* $m_t$ that tracks the log‑scale of gates:

\[
m_t = \max\!\bigl(\log f_t + m_{t-1}, \ \log i_t\bigr),
\]
\[
i'_t = \exp(\log i_t - m_t), \qquad 
f'_t = \exp(\log f_t + m_{t-1} - m_t).
\]

These normalized gates preserve exact outputs and gradients while keeping values within a safe range.

### 2. sLSTM – Scalar Memory With Mixing  

The **sLSTM** keeps a *scalar* cell $c_t$ (like classic LSTMs) but adds two new ingredients:

* A **normalizer state** $n_t$ that accumulates gate products so that hidden output becomes $h_t = o_t\, c_t / n_t$, effectively “renormalizing’’ the cell each step.
* **Memory mixing across multiple heads/cells**, enabled by exponential gating. This gives each head its own internal recurrence while allowing controlled interaction among heads—something vanilla LSTMs lack.

Thus sLSTM solves the irreversible‑storage issue while still being lightweight for tasks where scalar memory suffices.

### 3. mLSTM – Matrix Memory With Covariance Updates  

To overcome the scalar bottleneck, **mLSTM** expands the cell into a full matrix $\mathbf{C}_t\in\mathbb{R}^{d\times d}$. Storing a *key–value* pair becomes an outer‑product update akin to a *covariance rule*:

\[
\mathbf{C}_t = f_t\,\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t\,\mathbf{k}_t^\top .
\]

Here $\mathbf{k}_t$ encodes a *key*, $\mathbf{v}_t$ encodes its *value*, and $\mathbf{q}_t$ (the query) retrieves information via $\tilde{\mathbf{h}}_t = \mathbf{C}_t \mathbf{q}_t / \max\!\bigl(|\mathbf{n}_t^\top \mathbf{q}_t|,\ 1\bigr)$. This mechanism mirrors fast weight programmers and associative memories, giving each cell an effectively *infinite* capacity for storing paired vectors.

Because there is no hidden‑to‑hidden recurrence in mLSTM (**no memory mixing**), its computations can be expressed as matrix operations that run in parallel across timesteps—a crucial factor for large‐scale training.

### 4. From Cells to Architectures – xLSTM Blocks  

Both sLSTM and mLSTM are wrapped inside residual blocks inspired by modern Transformer backbones:

* **Post up‑projection block** (used for sLSTM) first processes the recurrence in its native space, then linearly upsamples before applying a nonlinearity.
* **Pre up‑projection block** (used for mLSTM) projects inputs into a high‐dimensional space first; recurrence then happens there, maximizing storage utility.

Stacking many such blocks with pre‑LayerNorm yields deep **xLSTM architectures** that inherit all benefits of residual learning while preserving linear compute cost ($O(T)$) and constant memory footprint ($O(1)$ w.r.t.\ sequence length).

## Scaling Up – From Hundreds of Millions to Billions of Parameters  

### Synthetic Benchmarks  

On formal‐language tasks that require explicit state tracking (e.g., parity or balanced parentheses), only models equipped with *memory mixing*—like sLSTM—reach perfect accuracy. Traditional Transformers or pure State Space Models struggle because they cannot maintain an explicit internal state across arbitrary lengths.

On *Multi‑Query Associative Recall*—a test of raw storage capacity—mLSTM‐based xLSTMs outperform all non‑Transformer baselines even when handling up to 256 key–value pairs over sequences of length 2048. The matrix memory’s associative retrieval shines here.

### Language Modeling on Real Data  

Training on **15 B tokens** from SlimPajama (the same data used for GPT‑3 scale experiments), xLSTMs achieved lower validation perplexity than:

* Classic Transformers (GPT‑3/Llama)
* State Space Models (Mamba, H3)
* Linear/Hybrid RNNs (RWKV, HGRN2)

Ablation studies confirmed that both exponential gating *and* matrix memory contribute significantly—the performance drops when either component is removed.

When scaling further to **300 B tokens**, xLSTMs maintained their edge across multiple model sizes (125 M–1.3 B parameters). Notably:

* **Long‑context extrapolation:** Models trained with context length 2048 preserved low perplexity up to 16 k tokens—a regime where Transformers’ quadratic cost blows up.
* **Downstream reasoning benchmarks:** Across diverse tasks (common sense reasoning, ARC), xLSTMs consistently ranked highest except for isolated cases where Mamba edged out slightly.
* **Domain‐wise perplexity:** On the PALOMA suite covering 571 text domains, xLSTMs outperformed Llama and RWKV on > 99 % of domains.
* **Scaling laws:** When plotting loss versus model size × data size on log–log axes, xLSTMs follow the same power‐law trend as Transformers but sit on a lower loss curve—implying better performance at any scale given comparable compute budget.

### Compute & Memory Footprint  

Because recurrent updates are linear in sequence length and require only constant extra state per layer:

* Training memory grows linearly with batch size rather than quadratically with context length—as is typical for self‑attention.
* Inference speed scales linearly too; benchmarks show wall‑clock generation times comparable to other RNNs and far better than vanilla Transformers at long contexts.
* The matrix updates in mLSTM are computationally heavier ($d\times d$ ops), yet they map efficiently onto GPUs’ dense linear algebra kernels. Preliminary CUDA kernels achieve near–optimal throughput despite being unoptimized relative to FlashAttention implementations.

## Limits & Open Challenges  

While promising, xLSTMs still face practical hurdles:

| Issue | Current Status |
|-------|----------------|
| **Parallelism of sLSTM** | Memory mixing forces sequential dependencies; custom CUDA kernels make it only ~2× slower than fully parallel mLSTM. |
| **Matrix cost in mLSTM** | $d^2$ operations dominate compute; optimized kernels could close this gap further. |
| **Gate initialization** | Forget gate biases need careful tuning to avoid runaway decay or explosion. |
| **Longer contexts beyond ~16 k** | Matrix memory remains finite; extremely long sequences could overflow capacity unless adaptive strategies are added. |
| **Full hyperparameter search** | Large‐scale experiments used default settings; dedicated tuning may unlock even higher performance gains. |

Future work might combine sLSTM’s expressive mixing with mLSTM’s parallelism via hybrid blocks or explore hierarchical memory schemes that retain constant cost while expanding capacity further.

## Takeaway  

The story comes full circle:  
*From pioneering ideas about constant error carousels in the ’90s,*  
to being eclipse­d by attention over two decades later,
and now back into relevance through clever engineering (*exponential gating*, *matrix memories*, *residual block design*) that let recurrent networks scale to billions of parameters while retaining their unique strengths—namely explicit state tracking and linear compute cost.

If you’re building systems where long-range dependencies must be revised on the fly—think code execution traces, interactive agents, or edge devices with tight memory budgets—xLSTMs offer a compelling alternative to pure Transformer stacks. Their resurgence reminds us that old ideas can be revitalized with fresh perspective—and that “the next big thing” may sometimes be an upgraded version of what we already had under our hands.



# Exponential Gating Explained: Letting Recurrent Networks Rewrite Their Past

Recurrent neural networks have been around for decades, but the Long Short‑Term Memory (LSTM) architecture still enjoys a special place because it solved the classic *vanishing‑gradient* problem with its “constant error carousel” and three sigmoid gates.  
Despite its great track record—think language generation before Transformers and countless applications in reinforcement learning—plain LSTMs hit a hard wall when it comes to **revising past decisions**. Once a piece of information is written into the cell state, the bounded sigmoid forget gate can only *decrease* its influence; it can never *amplify* a forgotten value later on.

The recent **xLSTM** family tackles this exact limitation by swapping the classic sigmoid gates for **exponential gates** and adding a lightweight **normalization + stabilization** machinery. The result is an LSTM that can *rewrite* what it stored earlier—hence “exponential gating”. Below we break down how this works, why it matters, and what the experiments say.

---

## 1. The problem with classic gating

In a vanilla LSTM the core recurrence is  

\[
c_t = f_t \, c_{t-1} + i_t \, z_t ,
\qquad
h_t = o_t \,\psi(c_t),
\]

where all three gates \((i_t,f_t,o_t)\) are produced by a sigmoid activation,
\(\sigma(x)=1/(1+e^{-x})\).  
Because \(\sigma(\cdot) \in (0,1)\), the forget gate \(f_t\) can *only* shrink the previous cell value \(c_{t-1}\); it can never increase it again later. Consequently:

* **No revision:** If a more relevant piece of information appears later in the sequence, the network cannot “bring back” a previously forgotten value.
* **Limited capacity:** Important details that are stored early get continuously damped as more timesteps pass.

These issues surface in tasks such as *nearest‑neighbor search*—where you must overwrite an earlier candidate if a closer match appears later—and other state‑tracking problems.

---

## 2. Enter exponential gates

The key idea of xLSTM’s **sLSTM** variant is simple but powerful: replace the sigmoid (or keep it optional) with an **exponential activation** for at least the input gate—and optionally also for the forget gate:

\[
\begin{aligned}
i_t &= \exp\!\big(\tilde{i}_t\big),\\
f_t &= \sigma\!\big(\tilde{f}_t\big)\quad\text{or}\quad \exp\!\big(\tilde{f}_t\big).
\end{aligned}
\]

Since \(\exp(\cdot) > 0\) has **unbounded range**, both gates can now take values **greater than 1**. The consequences are immediate:

* **Amplification possible:** The input gate can write an update \(i_t z_t\) that is larger than any preceding contribution.
* **Re‑increase of forgotten memory:** If \(f_t>1\), past values get *boosted* rather than merely decayed—a direct way to rewrite earlier storage decisions.

In practice we keep one gate sigmoid‑based (usually the output gate \(o_t\)) to retain a bounded output while allowing flexible internal dynamics.

---

## 3. Keeping the explosion in check – Normalizer state

Unbounded gates sound risky—without control they could blow up numeric values and destabilize training. xLSTM solves this with a cheap yet elegant **normalizer state** \(n_t\) that tracks how much “gate mass” has been accumulated over time:

\[
n_t = f_t\, n_{t-1} + i_t .
\]

Intuitively, \(n_t\) sums all past input‑gate contributions after they have been scaled by every subsequent forget gate.  
When producing the hidden output we *divide* the raw cell state by this normalizer:

\[
\tilde{h}_t = \frac{c_t}{n_t}, \qquad
h_t = o_t\, \tilde{h}_t .
\]

Because both numerator and denominator receive **the same multiplicative factors**, their ratio stays well‑behaved even when individual gates become large. The network therefore learns *how much* to amplify or attenuate without ever leaving the stable range needed for back‑propagation.

---

## 4. Stabilization via logarithmic tracking

Exponentials can still create overflow in floating‑point arithmetic when their arguments become large (e.g., \(\exp(1000)\)). xLSTM adopts a classic trick from earlier recurrent work: keep a running **log‑scale tracker** \(m_t\),

\[
m_t = \max\!\Big(\log(f_t)+m_{t-1},\, \log(i_t)\Big),
\]

and then renormalize each gate before using it:

\[
\begin{aligned}
i'_t &= \exp\!\big(\log(i_t) - m_t\big),\\
f'_t &= \exp\!\big(\log(f_t) + m_{t-1} - m_t\big).
\end{aligned}
\]

Because we subtract the same offset \(m_t\) from both log‑gates, their product remains unchanged:
\(i'_t f'_t = i_tf_t.\)  
Thus mathematically nothing changes, but numerically we avoid catastrophic overflow or underflow.

---

## 5. Why does this matter? Empirical highlights

The paper evaluates exponential gating on several benchmarks that explicitly test revision capabilities:

| Task | Classic LSTM | xLSTM (sLSTM) |
|------|--------------|---------------|
| Nearest‑Neighbor Search (need to overwrite old match) | High MSE – fails to replace stored vector | Low MSE – correctly revises storage |
| Rare token prediction on WikiText‑103 | Perplexity deteriorates for low‑frequency tokens | Consistently lower perplexity across all frequency bins |

Beyond these synthetic tasks, full language models built from sLSTM blocks (**xLSTM architectures**) achieve **lower validation perplexities** than GPT‑3‑scale Transformers and State Space Models when trained on 15 B tokens of SlimPajama data.

The key takeaway is that **exponential gating restores the ability to edit memories**, which translates into better handling of long‑range dependencies and rare events—both critical for modern language modeling.

---

## 6. Putting it together – The sLSTM forward pass

For quick reference, here is the full forward computation of an sLSTM cell with exponential gating (as presented in the paper):

```
c_t = f_t * c_{t-1} + i_t * z_t               # cell update
n_t = f_t * n_{t-1} + i_t                     # normalizer update
h̃_t = c_t / n_t                              # normalized hidden
h_t   = o_t * h̃_t                             # output gated

z   = φ( w_z^T x + r_z h_{t-1} + b_z )        # cell input
i   = exp( w_i^T x + r_i h_{t-1} + b_i )      # input gate (exp)
f   = σ( w_f^T x + r_f h_{t-1} + b_f )        # forget gate (sigmoid or exp)
o   = σ( w_o^T x + r_o h_{t-1} + b_o )        # output gate
```

All weights (\(w_*, r_*\)) & biases (\(b_*\)) are learned exactly as in a regular LSTM; only two activation functions differ.

---

## 7. What stays unchanged?

It is worth emphasizing that introducing exponential gates does **not** alter any fundamental property of backpropagation:

* The gradients flow through the same additive cell update.
* The stabilizer state guarantees that derivatives remain finite.
* Normalization provides scale invariance without hurting expressivity.

Thus existing training pipelines—mixed precision, AdamW optimizer schedules, etc.—can be re-used unchanged.

---

## 8. Final thoughts

Exponential gating may look like just swapping a sigmoid for an `exp`, but in practice it adds three tightly coupled components:

1. **Unbounded gates** → give the network power to amplify or resurrect past information.
2. **Normalizer state** → balances those amplifications so hidden activations stay in range.
3. **Log‑scale stabilizer** → prevents numerical overflow while preserving exact dynamics.

Together they let recurrent models “rewrite their past”—a capability that plain LSTMs fundamentally lack. In the extensive experiments of the xLSTM paper, this simple change leads to measurable gains on synthetic revision tasks and real-world language modeling at billions of parameters.

If you’ve been skeptical about RNNs’ relevance in today’s Transformer‑dominated world, exponential gating shows there’s still room for clever recurrent designs—especially when scaling memory and parallelism become non‑trivial concerns for extremely long contexts or edge deployment.

Ready to try it yourself? The authors have released an implementation at <https://github.com/NX-AI/xlstm>. Feel free to experiment with sLSTM blocks inside your own sequence models and see how well your networks can *remember—and un‑remember* what matters most.



# sLSTM vs mLSTM: Two New Flavors of Memory for Recurrent Networks

## Introduction

Long Short‑Term Memory (LSTM) networks have been the workhorse of sequence modeling for three decades. Their hallmark – an additive “constant error carousel” protected by input, forget and output gates – solved the vanishing‑gradient problem that plagued early recurrent neural networks (RNNs). Yet modern language models have largely outpaced vanilla LSTMs because classic LSTMs still suffer from three practical limits:

1. **Irreversible storage decisions** – once a value is written into the cell it is hard to overwrite without losing earlier information.
2. **Scalar memory bottleneck** – each cell stores a single real number, making it difficult to retain many distinct facts (e.g., rare tokens).
3. **Sequential processing** – hidden‑to‑hidden recurrence forces strict step‑by‑step computation, limiting parallelism.

The recent **xLSTM** family tackles these problems by extending the classic cell in two orthogonal directions:

* **sLSTM** – a scalar‑memory variant that adds *memory mixing* across cells.
* **mLSTM** – a matrix‑memory variant that stores *key–value pairs* with a covariance update rule.

Both share a common ingredient: **exponential gating** (instead of the usual sigmoid) together with careful normalization and stabilization. Below we unpack each design, then compare them in terms of memory capacity and parallelism.

---

## A Quick Refresher: The Classic LSTM Update

At every time step $t$ an LSTM updates its cell state $c_t$ and hidden output $h_t$ as  

\[
c_t \;=\; f_t\,c_{t-1} \;+\; i_t\,z_t,
\qquad
h_t \;=\; o_t\,\psi(c_t),
\]

where $i_t$, $f_t$ and $o_t$ are sigmoid gates ($\sigma(\cdot)$), $z_t$ is the transformed input, and $\psi(\cdot)$ is typically $\tanh$. The cell state $c_t$ is a *scalar* (or a vector of scalars) that accumulates information linearly over time.

---

## sLSTM: Scalar Memory with Mixing Across Cells

### How It Works

The **sLSTM** keeps the familiar scalar cell but replaces the input gate with an exponential activation ($\exp(\cdot)$) and optionally allows the forget gate to be exponential as well. Because exponentials can blow up quickly, sLSTM introduces two stabilizing mechanisms:

1. **Normalizer state** $n_t$ that aggregates the product of past forget gates with the current input gate:
   \[
   n_t = f_t\,n_{t-1} + i_t.
   \]
2. **Stabilizer state** $m_t$ that tracks the logarithmic magnitude of gates:
   \[
   m_t = \max\bigl(\log f_t + m_{t-1},\;\log i_t\bigr).
   \]
   Normalized gates $i'_t$ and $f'_t$ are obtained by subtracting $m_t$, guaranteeing numerically stable values.

The hidden output now reads  
\[
h_t = o_t\,\frac{c_t}{n_t},
\]
which effectively divides the raw cell by its accumulated “mass” $n_t$, preventing unbounded growth.

### Memory Mixing

Where classic LSTMs treat each cell independently (except for optional recurrent weight matrices), **sLSTM introduces explicit mixing across cells**:

* Multiple scalar cells can interact via learned recurrent matrices $\mathbf{R}_{z},\mathbf{R}_{i},\mathbf{R}_{f},\mathbf{R}_{o}$.
* The *mixing* happens *within* each head but not across heads – a design reminiscent of multi‑head attention but applied to recurrent states.
* This structure enables *state tracking*: the network can revise earlier storage decisions by routing information through other cells in subsequent steps.

### Strengths & Weaknesses

| Aspect | Advantage | Limitation |
|--------|-----------|------------|
| **Capacity** | Still scalar per cell → limited raw storage per unit | May require many cells for complex facts |
| **Expressivity** | Memory mixing gives richer dynamics than plain LSTMs | Sequential recurrence prevents full parallel execution |
| **Parallelism** | Requires scan‑like operations across time → GPU kernels slower than pure matrix ops | Custom CUDA kernel achieves < 2× slowdown compared to fully parallel mLSTM |

Empirically, sLSTM shines on formal language tasks that demand *revision* of stored symbols (e.g., parity or nearest‑neighbor search). The mixing enables it to update forgotten information without discarding everything else—a capability missing in vanilla Transformers or State Space Models.

---

## mLSTM: Matrix Memory via Covariance Updates

### How It Works

The **mLSTM** upgrades each scalar cell into a full matrix $\mathbf{C}_t\in\mathbb{R}^{d\times d}$ acting as an *associative memory*. At each step we compute three vectors from the input $\mathbf{x}_t$:

* **Key** $\mathbf{k}_t = \frac{1}{\sqrt d}\,\mathbf{W}_k\mathbf{x}_t + \mathbf{b}_k$
* **Value** $\mathbf{v}_t = \mathbf{W}_v\mathbf{x}_t + \mathbf{b}_v$
* **Query** $\mathbf{q}_t = \mathbf{W}_q\mathbf{x}_t + \mathbf{b}_q$

The core update follows the classic *covariance rule* (also known from Fast Weight Programmers):

\[
\mathbf{C}_t = f_t\,\mathbf{C}_{t-1} \;+\; i_t\,\underbrace{\bigl(\mathbf{v}_t\,\mathbf{k}_t^{\!\top}\bigr)}_{\text{outer product}}.
\]

Here:
* $i_t = \exp(\tilde{i}_t)$ is an exponential *learning rate* controlling how much of $(\mathbf{v}\,\mathbf{k}^\top)$ we write.
* $f_t = \sigma(\tilde{f}_t)$ or $\exp(\tilde{f}_t)$ acts as a *decay factor* on the old memory.
* A normalizer vector $\mathbf{n}_t = f_t\,\mathbf{n}_{t-1} + i_t\,\mathbf{k}_t$ tracks total key mass for stable division.

Retrieval is simply a matrix‑vector product followed by normalization:

\[
\tilde{\mathbf h}_t = 
   \frac{\mathbf C_t\,\mathbf q_t}
        {\max\bigl(|\mathbf n^\top_{t}\!\,\mathbf q_{t}|,\,1\bigr)},
\qquad 
h_{t}=o_{t}\odot \tilde{\mathbf h}_{t},
\]

with elementwise output gating $o_{t}= \sigma(\tilde{\mathbf o}_{t})$.

### Parallelism

Because there is no hidden‑to‑hidden recurrence (no “memory mixing”), every time step can be expressed as independent matrix updates followed by a parallel reduction across timesteps—exactly what modern libraries excel at:

* The outer product $\mathbf v\,\mathbf k^\top$ is a batched rank‑1 update.
* Decay via $f_t$ multiplies all entries uniformly.
* The whole recurrence can be implemented with prefix‑sum style scans that run in $O(\log T)$ depth on GPUs (similar to FlashAttention’s kernel design).

Hence **mLSTM scales linearly with sequence length in both compute and memory**, just like Transformers after linearization tricks—but without quadratic pairwise interactions.

### Capacity & Expressivity

| Aspect | Advantage | Limitation |
|--------|-----------|------------|
| **Capacity** | A full matrix can hold up to $d^2$ pairwise associations → dramatically higher than scalar cells | Updating a $d\times d$ matrix costs $O(d^2)$ flops per step |
| **Associative Retrieval** | Exact key–value binding using outer products → natural fit for tasks like associative recall or rare token prediction | No explicit mixing among distinct “heads”; mixing only via overlapping keys |
| **Parallelism** | Fully amenable to parallel scans → comparable wall‑clock time to linear Transformers despite heavier arithmetic | Current CUDA kernels are ~4× slower than FlashAttention but still scale well |
| **Stability** | Shares same exponential gating stabilizer as sLSTM (log‐max trick) → prevents overflow |

Empirically, mLSTM dominates on *large‐capacity* benchmarks such as Multi‑Query Associative Recall, where it retains thousands of key–value pairs far better than any scalar‐based model. In language modeling it also improves perplexity on rare token subsets because those tokens can be stored explicitly in separate dimensions of $\mathbf C$.

---

## Capacity vs Parallelism Trade‑off

Both variants address different pain points of classic LSTMs:

| Feature               | sLSTM                                                | mLSTM                                                   |
|-----------------------|------------------------------------------------------|----------------------------------------------------------|
| **Memory type**       | Scalar per cell (+ mixing)                           | Full matrix ${d\times d}$ storing many key–value pairs    |
| **Revisability**      | High – memory mixing lets later cells overwrite earlier ones without erasing everything | Moderate – decay gate controls forgetting globally        |
| **Raw storage size**  | Limited by number of cells ($\sim d$ scalars)        | Quadratic in hidden dimension ($d^2$ entries)           |
| **Parallel execution**| Requires sequential scan → slower GPU kernels        | Fully parallelizable prefix sum / scan → linear time     |
| **Best suited for**   | Tasks requiring fine‐grained *state tracking*, e.g., formal grammars or dynamic nearest‑neighbor search                  | Tasks needing massive associative memory such as rare token prediction or long‑range retrieval |
| **Implementation overhead** | Custom CUDA kernel (~2× slower than pure matmul)  | Straightforward batched matmul/outer product (~4× slower than FlashAttention but still linear) |

In practice you can think of them as two ends of a spectrum:

* Move left toward **sLSTM** when you care more about *expressive dynamics* and being able to “rewrite” what you stored.
* Move right toward **mLSTM** when you want *massive storage capacity* without sacrificing speed on very long sequences.

The original xLSTM architecture cleverly blends both by stacking residual blocks where some contain sLSTM layers (for state tracking) and most contain mLSTM layers (for bulk storage). Experiments show that even a modest mixture such as xLSTM[7:1] (seven mLSTMs per eight blocks) outperforms pure Transformers on large language modeling benchmarks while retaining good extrapolation ability.

---

## Practical Guidance

If you’re building a new recurrent backbone for language models or any long‐sequence task:

1. **Identify bottlenecks:**  
   - If your data exhibits frequent revisions (e.g., keeping track of dynamic entities), allocate more sLSTM blocks.
   - If you’re mostly memorizing a large set of facts or rare symbols, favor mLSTM blocks.
2. **Dimension choice:**  
   - For mLSTM pick hidden size $d$ such that $d^2$ fits comfortably in GPU memory at your target batch size.  
   - For sLSTM you can increase the number of cells instead because each contributes only one scalar.
3. **Stabilization matters:** Always apply the log‐max stabilizer ($m_t$) when using exponential gates—otherwise training may diverge due to overflow.
4. **Hybrid stacking:** Empirical results suggest that a small proportion (< 20 %) of sLSTM blocks yields most of its revisability benefits without harming throughput dramatically.
5. **Software tip:** Use the provided CUDA kernels from the authors’ repository (`github.com/NX-AI/xlstm`). They already implement fast scans for both variants and integrate seamlessly with PyTorch’s `nn.Module`.

---

## Conclusion

The introduction of **sLSTM** and **mLSTM** expands the classic LSTM’s toolbox in complementary ways:

- ***sLSTM*** brings *memory mixing*, letting recurrent networks revise past decisions through inter‑cell communication—crucial for precise state tracking at the cost of sequential processing.
- ***mLSTM*** equips recurrent networks with an *associative matrix memory*, dramatically boosting raw storage capacity while preserving linear-time inference through full parallelism.

Together they form the core building blocks of the x​​​​​​​​​​​​​​​​​​​​​​​​​​​XL™ architecture—a modern recurrent family that competes head‑to‑head with Transformers and State Space Models on large‐scale language modeling while retaining RNN’s hallmark efficiency in sequence length scaling. As hardware accelerators continue improving their matrix multiplication throughput, we expect matrix‐memory models like mLSTM to become ever more attractive for long‑context applications ranging from code generation to reinforcement learning agents operating over massive histories. 

If you’re curious about trying them out yourself, head over to the open‐source implementation linked in the paper—there’s no better way to feel the difference between scalar mixing and matrix binding than by running your own benchmark!



# From Cells to Blocks: Building xLSTM Architectures with Residual Stacking  

*How scalar‑ and matrix‑based LSTM cells become modern building blocks that can be stacked just like Transformer layers.*

---

## Why a New Kind of Block?

Classic LSTMs excel at tracking long‑range dependencies because their **constant‑error carousel** keeps gradients flowing through time. Yet they hit three practical roadblocks:

1. **Irrevocable storage decisions** – once a value is written it’s hard to overwrite it later.  
2. **Limited memory bandwidth** – a scalar cell can only hold so much information, hurting rare‑token prediction.  
3. **Sequential bottleneck** – hidden‑to‑hidden connections force strictly step‑by‑step processing.

The *xLSTM* family (Section 2 of the paper) solves these issues by introducing two new cell families:

| Cell | Core Idea | Memory |
|------|-----------|--------|
| **sLSTM** (scalar LSTM) | *Exponential gating* + a **normalizer state** that lets the network revise what it stored | A single scalar \(c_t\) (plus a normalizer \(n_t\)) |
| **mLSTM** (matrix LSTM) | Same exponential gates but **matrix memory** \(\mathbf{C}_t\in\mathbb{R}^{d\times d}\) updated by a covariance rule | A full matrix that stores key–value pairs |

Both cells keep the familiar LSTM recurrence,
\[
c_t = f_t\,c_{t-1}+i_t\,z_t,\qquad 
h_t = o_t\,\psi(c_t),
\]
but replace the sigmoid input/forget gates with \(\exp(\cdot)\) (or optionally \(\sigma(\cdot)\)), and they add a *stabilizer* \(m_t\) (Eq. (6)) so that huge exponentials never overflow.

Now we have powerful cells, but raw recurrent units cannot be dropped into a large language model without further engineering. The solution is to embed them inside **residual blocks**, exactly the way Transformer layers are built.

---

## Residual Blocks 101

A residual block does three things:

1. **Normalize** its input (pre‑LayerNorm) so that each layer sees roughly zero‑mean activations—this is crucial when gradients travel through many layers.
2. **Non‑linearly summarize the past** using the recurrent cell.
3. **Project up to a high‑dimensional space**, apply a cheap nonlinearity, then project back down and finally add the input (“skip connection”).

Why project up? According to **Cover’s Theorem**, mapping data into a higher‑dimensional space makes it far easier to linearly separate different histories—a key ingredient for next‑token prediction in language modeling.

The crucial design choice is *where* we place the projection relative to the recurrent cell:

* For **sLSTM**, we first run the recurrent computation in its native space, then lift its output into a larger vector space (**post up‑projection**). This mirrors standard Transformer blocks where self‑attention works on the original hidden dimension before an expansion.
* For **mLSTM**, we flip the order (**pre up‑projection**) because the matrix memory already lives in a high‑dimensional “key–value” space; performing mixing there maximises its capacity.

Both schemes are illustrated in Figure 3 of the paper, but let’s walk through them step by step.

---

## 1️⃣ Post Up‑Projection Block – sLSTM  

### Data Flow

```
x_t  ──► LayerNorm ──► Linear (project) ──► sLSTM cell ──► Linear (expand) ──► GELU ──► Linear (shrink)
                                                                                               │
                                                                                               ▼
                ────────────────────────────────────────────────────────────────────────►  Add (skip)
```

1️⃣ **LayerNorm** ensures stable statistics across depth.  

2️⃣ The *project* layer is an identity mapping for sLSTM blocks (`d → d`), because we keep everything at the “native” size while the recurrent unit runs.  

3️⃣ Inside the **sLSTM cell**, Eq. (5) computes
   \[
   c_t = f_t c_{t-1}+i_t z_t,\quad
   n_t = f_t n_{t-1}+i_t,\quad
   h_t = o_t \frac{c_t}{n_t},
   \]
   where \(i_t = \exp(\tilde{i}_t)\), \(f_t = \sigma(\tilde{f}_t)\) or \(\exp(\tilde{f}_t)\).  
   The normalizer \(n_t\) tracks accumulated gate strength so that division by \(n_t\) yields a well‑scaled hidden state even when exponentials grow large.

4️⃣ After the cell finishes, we *expand* (`up‑projection`) from dimension \(d\) to \(d_{\text{ff}}\) (typically 4× larger). A cheap activation like GELU adds nonlinearity, then another linear layer shrinks back to \(d\).  

5️⃣ Finally we add back the original normalized input – this is the classic “residual connection” that lets gradients skip over a whole block if needed.

### Why Post?

Because sLSTM’s hidden state is still scalar per head, its expressive power benefits most from first mixing information temporally (via exponential gates), then boosting dimensionality for downstream linear classification tasks—exactly what Transformers do after self‑attention.

---

## 2️⃣ Pre Up‑Projection Block – mLSTM  

### Data Flow

```
x_t  ──► LayerNorm ──► Linear (expand) ──► mLSTM cell ──► Linear (shrink)
                                                                               │
                                                                               ▼
                ─────────────────────────────────────────────────────────────► Add (skip)
```

1️⃣ After LayerNorm we immediately *expand* from dimension \(d\) to a larger feature size \(d_{\text{ff}}\). This “pre projected” representation becomes our key/value/query vectors:
   \[
   \mathbf{k}_t = \frac{1}{\sqrt{d}} \mathbf{W}_k x_t + b_k,\quad
   \mathbf{v}_t = \mathbf{W}_v x_t + b_v,\quad
   \mathbf{q}_t = \mathbf{W}_q x_t + b_q .
   \]

2️⃣ The **mLSTM cell** updates its matrix memory using a covariance rule:
   \[
   \mathbf{C}_t = f_t\,\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t\,\mathbf{k}_t^\top,
   \qquad
   \mathbf{n}_t = f_t\,\mathbf{n}_{t-1} + i_t\,\mathbf{k}_t .
   \]
   Retrieval happens via
   \[
   \tilde{\mathbf{h}}_t = 
       \frac{\mathbf{C}_t\,\mathbf{q}_t}
            {\max\bigl(|\mathbf{n}_t^\top\!\mathbf{q}_t|,\;1\bigr)},
   \quad
   h_t = o_t\odot\tilde{\mathbf{h}}_t .
   \]
   Exponential gates again let us rapidly increase or decay contributions while keeping gradients stable through the same stabilizer trick used in sLSTM.

3️⃣ Because there are no hidden‑to‑hidden connections (`memory mixing`), this recurrence can be parallelized across time steps—exactly like FlashAttention does for Transformers—so we can treat each time step as an independent matrix operation once the queries/keys/values are ready.

4️⃣ After obtaining \(h_t\), we *shrink* back to dimension \(d\), then add around the skip connection just as before.

### Why Pre?

The matrix memory already encodes associations between every key and every value; projecting up *first* gives those keys/values richer representations before they are stored in \(\mathbf{C}_t\). In contrast, projecting after would waste part of this expressive capacity because we would compress later on after an expensive outer product update.

---

## Stacking Blocks – The Full xLSTM Architecture  

With either block type defined, building an *xLSTM model* follows exactly how one would stack Transformer encoder layers:

```
Input tokens → Embedding → 
[Block_1 → Block_2 → … → Block_N] → LM head → Softmax
```

Each `Block_i` is either an sLSTM-based or an mLSTM-based residual unit, wrapped in *pre‑LayerNorm*. The overall model depth used in our experiments was 48 blocks with an embedding size of 1024 (≈350 M parameters).  

### Mixing Cell Types

The paper introduces a notation `xLSTM[a:b]` where `a` is the number of mLSTM blocks and `b` is the number of sLSTM blocks out of `a+b` total layers. For example:

- `xLSTM[7:1]` → 7 mLSTMs + 1 sLSTM per every eight layers,
- `xLSTM[0:1]` → pure sLSTMs,
- `xLSTM[1:0]` → pure matrix LSTMs.

Because both block variants share exactly the same residual interface, swapping them merely changes how each layer handles memory while preserving depth, width, and training schedule—all crucial for fair scaling experiments.

### Scaling Behaviour

When training on SlimPajama data at 15 B tokens, all `xLSTM[a:b]` variants outperformed Transformers, SSMs, and other RNN variants on validation perplexity (§4.2). Moreover, as model size grows toward billions of parameters, scaling curves remain essentially linear in log–log space—just like modern GPT models—so there’s no hidden penalty for using recurrent cells instead of attention maps (§4.4).

---

## Practical Takeaways

| Aspect | Recommendation |
|--------|----------------|
| **When to use sLSTM blocks?** | If you need *memory mixing*—the ability to revise stored values through hidden‐to‐hidden recursions—use post up‑projection blocks sparingly (e.g., one per eight layers). |
| **When to use mLLM blocks?** | For pure capacity and parallel speed, fill most layers with pre up‑projection mLSTMs; they give you matrix‐level associative recall at negligible wall clock cost thanks to GPU batching. |
| **Implementation tip** | Keep forget gates initialized close to 1 so that early training doesn’t wipe out all stored information; see Eq. (9). |
| **Hardware note** | Current CUDA kernels for mLSTMs are not yet as optimized as FlashAttention but still achieve near‑linear throughput because every time step reduces to a handful of dense matrix multiplies (`d×d`). |

---

## Closing Thoughts

The journey from “cells” (`s`/`m` states) to “blocks” mirrors what happened with Transformers: once you wrap an effective primitive into a well‑designed residual module—complete with LayerNorm and feed‑forward projections—you obtain a scalable architecture that can be trained on billions of tokens without blowing up memory or compute budgets.

The *xLSTM* family proves that classic recurrence ideas still have room to grow when fused with modern architectural tricks:
- Exponential gating empowers swift revisions,
- Matrix memories furnish vastly higher storage bandwidth,
- Residual stacking supplies depth and gradient flow,
- Pre/post projections align each cell type with its sweet spot in representation space.

As large language models keep scaling, xLSTMs offer a compelling alternative pathway—one that preserves linear time/space complexity while matching or beating Transformers on perplexity and downstream tasks today.  

*If you’re curious enough to try them yourself, the code base lives at https://github.com/NX-AI/xlstm.* Happy experimenting!



# Scaling Recurrent Models: xLSTM’s Performance on Language Modeling Benchmarks

*How far can we push an LSTM when we give it billions of parameters and modern training tricks?*  
The answer turns out to be “as far as the current state‑of‑the‑art Transformers.” In this post we walk through the experimental evidence presented in the **xLSTM** paper – a family of recurrent cells that augment the classic LSTM with **exponential gating**, **new memory structures**, and **residual block backbones** – and show how these models beat Transformers, State‑Space Models (SSMs), and other recurrent networks across a wide range of language‑modeling benchmarks.

---

## 1. From LSTMs to xLSTMs  

The original LSTM update is famously simple:

\[
c_t = f_t \, c_{t-1} + i_t \, z_t,\qquad
h_t = o_t \,\psi(c_t),
\]

where \(c_t\) is the cell state, \(h_t\) the hidden output, and \(i_t,f_t,o_t\) are sigmoid gates that control input, forgetting, and output respectively.  

xLSTM expands this core in two orthogonal directions:

| Variant | Memory | Gate activation | Key ideas |
|--------|--------|----------------|----------|
| **sLSTM** | scalar cell \(c_t\) (still one number per hidden unit) | **Exponential** input gate (and optionally forget gate) plus a normalizer state \(n_t\) | Enables *revision* of stored information – i.e., a stored value can be overwritten later without losing earlier gradients |
| **mLSTM** | **Matrix** memory \(\mathbf{C}_t\in\mathbb{R}^{d\times d}\) | Exponential input gate + forget gate (or sigmoid) | Stores full *key–value* pairs via a covariance update \(\mathbf{C}_t = f_t\,\mathbf{C}_{t-1}+i_t\,\mathbf{v}_t\mathbf{k}_t^\top\); fully parallelizable because there is no hidden‑to‑hidden recurrence |

Both variants are embedded inside **xLSTM blocks** – residual modules that first project into a high‑dimensional space (pre‑up‑projection for mLSTM, post‑up‑projection for sLSTM), apply the recurrent cell, then project back. Stacking these blocks with pre‑LayerNorm yields deep **xLSTM architectures** that can be scaled to billions of parameters just like a Transformer decoder stack.

---

## 2. A Diverse Empirical Suite  

The authors did not rely on a single metric. They evaluated:

1. **Synthetic formal‐language tasks** (e.g., parity, Dyck languages) that require precise *state tracking*.  
2. **Multi‑Query Associative Recall**, a key–value memorization test that stresses raw storage capacity.  
3. **Long Range Arena (LRA)** – four long‑sequence benchmarks designed for evaluating how models handle context lengths up to several thousand tokens.  
4. **Large‐scale language modeling** on the SlimPajama corpus:
   - *15 B* token pre‑training (≈350 M parameters → comparable to GPT‑3 small).  
   - *300 B* token pre‑training across several model sizes (125 M – 1.3 B parameters).  
5. **Downstream reasoning tasks** (common‐sense benchmarks).  
6. **PALOMA domain benchmark** – next‑token prediction over 571 distinct text domains ranging from news sites to Reddit communities.  
7. **Scaling‐law curves** (perplexity vs compute/data).  
8. **Inference throughput** comparison with a comparable Transformer (LLama) and the recurrent Mamba model.

All experiments used the same autoregressive training setup and were run with mixed precision where possible.

---

## 3. Synthetic & Long‑Range Results  

### 3.1 State Tracking via Exponential Gating  

On the formal‐language suite, *only* models equipped with *memory mixing* could solve tasks that require remembering parity or nested brackets over arbitrarily long sequences. The sLSTM variant achieved near‐perfect accuracy (\(\approx 0.99\)) while vanilla Transformers plateaued around random chance (\(\approx 0\)). This confirms the theoretical claim that exponential gates + mixing give recurrent networks expressive power beyond what linear SSMs or self‐attention provide.

### 3.2 Storage Capacity with Matrix Memory  

In the Multi‑Query Associative Recall task the authors pushed key–value pairs up to **256 pairs** within sequences of length **2048** tokens. The hybrid configuration `xLSTM[1:1]` (half mLSTM blocks, half sLSTM blocks) outperformed every non‑Transformer baseline—including RWKV‐5/6, Retention and HGRN2—and even matched or exceeded smaller Transformers on the hardest settings. Adding a pure mLSTM block (`xLSTM[1:0]`) performed equally well, showing that the matrix memory alone is sufficient for high‐capacity retrieval when combined with exponential gating.

### 3.3 Long Range Arena  

Across all four LRA tasks—*ListOps*, *Text*, *Pathfinder*, and *Retina*—xLSTM consistently ranked among the top performers. Its linear time/space complexity gave it an edge over quadratic attention models without sacrificing accuracy.

---

## 4. Language Modeling at 15 B Tokens  

Training every model on **15 B tokens** from SlimPajama gives us a clean head‑to‑head comparison at roughly *GPT‑3 small* scale:

| Model | Parameters | Validation PPL |
|-------|------------|----------------|
| GPT‑3 style Transformer | ~350 M | ≈ 13.x |
| LLaMA | ~350 M | ≈ 13.x |
| Mamba (SSM) | ~350 M | ≈ 14.x |
| RWKV‑4 (RNN) | ~350 M | ≈ 14.x |
| **xLSTM[7:1]** (mostly mLSTM) | ~350 M | **≈ 12.x** |
| **xLSTM[1:0]** (all mLSTM)    | ~350 M | **≈ 12.x** |

*(Exact numbers are taken from Table 1 of the paper; “≈” indicates rounding.)*  

All variants of xLSTM achieve lower perplexity than any Transformer or SSM baseline at this scale—a clear win given identical parameter budgets and training data.

Figure 2 in the paper (“scaling curve @ 15 B”) shows that as we increase hidden size from 768→1024→1280 while keeping token count fixed, perplexity continues to improve following a smooth power law—but always stays *below* the curve traced by Transformers or SSMs.

---

## 5. Ablation – What Makes xLSTM Tick?  

The authors performed a stepwise “morph” from vanilla LSTMs into full xLSTMs:

1️⃣ Insert LSTMs into pre‑LayerNorm residual blocks → modest gain (> 10% relative PPL reduction).  
2️⃣ Switch to post up­projection blocks for sLSTMs → further improvement (~5% relative).  
3️⃣ Add **exponential gating** → biggest jump (~30% relative).  
4️⃣ Replace scalar cell with matrix memory → final edge (~10% relative).

The bottom half of Table 2 confirms that making each gate learnable from input adds another small boost—so both *gate richness* and *memory richness* matter together.

---

## 6. Scaling Up: Training on 300 B Tokens  

When we crank up data by twentyfold we see whether those early gains survive at true “LLM” scale.

### 6.1 Length Extrapolation  

All models were trained with a context window of **2048 tokens**, then evaluated from `2048` up to `16384`. Only xLSTM variants kept perplexity nearly flat as context grew; Transformers’ PPL spiked sharply after `4096`, while Mamba showed moderate degradation but still worse than xLSTMs.

### 6.2 Validation Perplexities Across Sizes  

| Model / Size | 125 M | 350 M | 760 M | 1.3 B |
|--------------|------|------|------|------|
| LLaMA        | 14.xx |13.xx|13.xx|12.xx|
| Mamba        |14.xx|13.xx|13.xx|12.xx|
| RWKV‑4       |15.xx|14.xx|14.xx|13.xx|
| **xLSTM[7:1]**|13.xx|12.xx|11.xx|10.xx|
| **xLSTM[1:0]**|13.xx|12.xx|11.xx|10.xx|

Both `xLSTM[7:1]` (mostly m​·​blocks) and `xLSTD[1:0]` dominate every size bracket – they are *the best* on validation PPL by a comfortable margin (~10% relative).

### 6️⃣ Downstream Reasoning  

On ten common‐sense benchmarks (e.g., HellaSwag, PIQA), xLSTMs achieved the highest scores in eight cases across all model scales; only ARC saw Mamba edge out by a narrow margin at the smallest size—otherwise nothing came close.

### 6️⃣ PALOMA Domain Benchmark  

PALOMA evaluates per-domain next‐token PPL over hundreds of text sources:

* `xLSTD[1:0]` beats Mamba in **568/571** domains (>99%).  
* Beats LLaMA in **486/571** domains (>85%).  
* Beats RWKV‐4 in **570/571** domains (>99%).  

Even when pooling domains into broader categories (`news`, `code`, `social`, …), x​​LAN obtains lower average PPL than any competitor—showing its robustness across very heterogeneous corpora.

### 6️⃣ Scaling Laws  

Figure 5 plots validation PPL versus total compute (`tokens × parameters`). All families follow a straight line in log–log space (`PPL ∝ N^{-α}`), but:
- The slope (`α`) is virtually identical across families,
- The *offset* is lowest for x​​LAN (`≈0.25` log units lower than Transformers).

Hence you can extrapolate reliably: at trillion+ token regimes an equally sized Transformer would still sit above an x​​LAN model trained on half as many tokens.

### 6️⃣ Inference Throughput  

Because both s​​LAN and m​​LAN have linear time/constant memory per step:
- Generation time grows linearly with length (`O(L)`), unlike quadratic growth (`O(L²)`) of standard Transformers.
- For batch size&nbsp;= 1 & prefill&nbsp;= 16 tokens, decoding speed was ~2× faster than LLama’s cached version after accounting for warmup.
- In multi‐batch decoding (`batch≥8`) x​​LAN achieved peak throughput > 500 token/s on an A100 GPU—surpassing Mamba which plateaued around 350 token/s under identical settings.

The authors note that CUDA kernels are still unoptimized compared with FlashAttention (`≈4×` slower), so there remains headroom for further speedups without changing algorithmic complexity.

---

## 7. What Do These Numbers Mean?  

Together these experiments paint a consistent picture:

* When you give an LSTM modern tricks—exponential gates + normalizer state + either scalar mixing or matrix covariance storage—it regains abilities it lost decades ago (*revisibility*, *high capacity*, *parallelism*)*.  
* Scaled to billions of parameters it matches or surpasses every contemporary baseline on standard language modeling metrics while keeping linear runtime cost per token—a compelling advantage for inference at very long contexts or low‐memory devices.
* The empirical scaling laws suggest there is no “sweet spot” where Transformers overtake recurrent models again; instead the gap may widen as we go toward ever larger data/model budgets unless transformer efficiency improves dramatically.

---

## 8. Takeaways & Outlook  

- **Recurrent models are back:** The myth that RNNs can’t compete with attention is busted when you augment them correctly.
- **Exponential gating is key:** By allowing gates to take values far larger than \([0,\,1]\) yet staying numerically stable through normalizer states and log stabilizers, information can be revised without drowning older signals.
- **Matrix memories give raw storage:** Covariance updates turn each hidden dimension into its own key–value table—a cheap way to mimic attention’s associative recall without quadratic cost.
- **Practical impact:** Constant memory usage makes x​​LAN attractive for edge deployment or very long prompt scenarios where transformers would need massive KV caches.
- **Open source:** The full codebase lives at https://github.com/NX-AI/xlstm – ready for experimentation or integration into existing LLM pipelines.

If you’re curious about building your own billion‑parameter recurrent LM or want to explore hybrid architectures that blend attention’s flexibility with recurrence’s efficiency, give x​​LAN a spin—you might just find it beats your favorite transformer baseline today!



# Speed vs Memory Trade‑offs in xLSTM: Parallelism, GPU Kernels, and Real‑World Inference  

Large language models have become the de‑facto workhorse for text generation, reasoning, and a host of downstream tasks. Yet every new generation brings a fresh bottleneck—most notably the *quadratic* cost of self‑attention in Transformers. The original Long Short‑Term Memory (LSTM) avoided this problem with **linear** time and **constant** memory per token, but classic LSTMs fell short on scalability and expressivity.  

The recent **xLSTM** family—comprising *sLSTM* (scalar memory with exponential gating) and *mLSTM* (matrix memory with a covariance update)—offers a fresh take on the scalability dilemma. Below we unpack the practical implications of these designs: how they affect parallel execution on GPUs, what their real‑world inference throughput looks like, and where the trade‑offs between speed and memory truly lie.

---

## 1. Why Linear Time Matters  

In a standard Transformer each token attends to every other token in the context window. This yields a per‑layer cost of  

\[
\mathcal{O}(T^2 d)
\]

where *T* is the sequence length and *d* the hidden dimension. As *T* grows (think 8 k–16 k tokens for code completion or document summarization) both **runtime** and **GPU RAM** explode.  

By contrast, an LSTM‑style recurrence updates the hidden state once per token:

\[
c_t = f_t\,c_{t-1} + i_t\,z_t , \qquad
h_t = o_t\,\psi(c_t)
\]

giving a per‑layer cost of \(\mathcal{O}(Td)\). The workload grows **linearly** with context length, and the recurrent state \((c_t,\ h_t)\) occupies a **constant** amount of memory regardless of *T*. This property made classic LSTMs attractive for edge devices, but they lacked the capacity to compete with modern Transformers at scale.

xLSTM inherits this linear runtime while introducing two architectural upgrades that aim to close the performance gap:

| Variant | Memory shape | Update rule | Parallelism |
|---------|--------------|-------------|-------------|
| **sLSTM** | Scalar \(c_t \in \mathbb{R}\) | Exponential gating + normalizer state | Sequential (memory mixing remains) |
| **mLSTM** | Matrix \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\) | Covariance update \(\mathbf{C}_t = f_t\,\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t \mathbf{k}_t^\top\) | Fully parallelizable across time |

Both variants retain the *linear* dependence on *T*, but they diverge sharply when it comes to CUDA implementation details—a difference that shows up starkly in inference benchmarks.

---

## 2. Parallelism in Practice  

### 2.1 sLSTM – The “mixing” bottleneck  

sLSTM extends classic LSTMs with **exponential gates** (\(i_t = \exp(\tilde{i}_t)\), \(f_t = \exp(\tilde{f}_t)\) or sigmoid) plus a normalizer state \(n_t\) that tracks cumulative gate strength:

\[
n_t = f_t n_{t-1} + i_t .
\]

Crucially, sLSTM retains **memory mixing**, i.e., recurrent connections among hidden states across cells (\(\mathbf{R}_{\mathbf{z}}, \mathbf{R}_{\mathbf{i}}, …\)). This design enables sophisticated state‑tracking tasks (e.g., revising stored values during nearest‑neighbor search), but it also forces a *sequential* scan over timesteps—no straightforward way to compute all timesteps simultaneously.

To mitigate the inevitable slowdown, the authors built a **custom CUDA kernel** that pushes intermediate activations into registers and leverages warp‑level primitives for the scan operation. The result? An sLSTM implementation that is **< 2 ×** slower than its fully parallel counterpart (mLSTM). For many real‑world workloads where state tracking is essential—think program execution tracing or long‑range entity resolution—this overhead can be acceptable given the dramatic boost in expressive power.

### 2.2 mLSTM – Parallel by design  

The matrix‑memory variant discards hidden–hidden mixing altogether:

\[
\begin{aligned}
\mathbf{C}_t &= f_t\,\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t \mathbf{k}_t^\top ,\\
\tilde{\mathbf{h}}_t &= \frac{\mathbf{C}_t\,\mathbf{q}_t}{\max\!\bigl(|\mathbf{n}_t^\top \mathbf{q}_t|,\;1\bigr)} ,
\qquad
h_t = o_t \odot \tilde{\mathbf{h}}_t .
\end{aligned}
\]

Because each time step depends only on a **scaled copy** of the previous matrix (\(f_t\,\mathbf{C}_{t-1}\)), we can rewrite the recurrence as a *prefix sum* over a series of rank‑one updates—a textbook case for parallel scans (`torch.cumsum`, `torch.scan`). In theory this yields an **embarrassingly parallel** forward pass comparable to linear Transformers such as FlashAttention.

In practice the current mLSTM CUDA kernels are still *prototype* level—roughly **4 ×** slower than highly tuned alternatives like FlashAttention or Mamba’s scan implementation. The slowdown stems largely from naïve handling of dense \(d\times d\) operations rather than algorithmic inefficiency; there’s no fundamental barrier preventing an optimized kernel from reaching parity with existing fast attention libraries.

---

## 3. Memory Footprint – Constant vs Quadratic  

| Model | Per‑layer activation memory | Scaling w.r.t *T* |
|-------|----------------------------|-------------------|
| Transformer (self‑attention) | KV cache \(2Td\) (+ attention maps) | \(\mathcal{O}(T)\) but **large constant factor** |
| Classic LSTM / sLSTM | Cell+hidden (\(2d\)) | \(\mathcal{O}(1)\) |
| mLSTM | Matrix \(\mathbf{C}\in\mathbb{R}^{d\times d}\) + vectors (\(k,v,q,o,n,i,f,m\)) | \(\mathcal{O}(d^2)\), independent of *T* |

Because both sLSTM and mLSTM store only *global* states that do not grow with sequence length, they can comfortably handle contexts up to 16 k tokens on a single GPU without exhausting VRAM—a regime where even modest Transformers start spilling over to CPU RAM or require aggressive chunking strategies.

The trade‑off is evident in **mLSTM's matrix memory**: each layer introduces an additional \(d^2\) parameters that must be updated each step. For hidden sizes typical of 1 k–3 k dimensions this amounts to several megabytes per layer—a modest price compared to the gigabytes required by KV caches for comparable contexts under Transformers.

---

## 4. Real‑World Inference Throughput  

The authors benchmarked xLSTMs against two popular baselines at roughly 1.3 B parameters:

* **LLama (Transformer)** – standard KV cache implementation
* **Mamba (State Space Model)** – linear recurrent architecture

All tests used batch size = 1 with a pre‑fill of 16 tokens (the best-case scenario for Transformers). Below are the salient findings:

### 4.1 Generation Time vs Context Length  

* **Transformers:** Generation time grows *quadratically*. At context = 8 k tokens LLama’s per-token latency spikes dramatically.
* **xLSTMs & Mamba:** Latency scales *linearly*, staying roughly flat even at context = 16 k tokens.
* The slope for xLSTMs matches Mamba’s closely; both families avoid nonlinear blowup altogether.

### 4.2 Decoding Throughput & Batch Scaling  

When increasing batch size beyond one token:
* LLama quickly runs into VRAM limits because each new sequence adds another KV cache (\(~2Td/byte\)). Throughput plateaus early.
* mLSTM/xLSTMs retain constant per‑sequence state size; batch scaling is essentially limited only by raw compute bandwidth.
* In head‑to‑head measurements xLSTMs achieved roughly **30–40 % higher throughput** than LLama at batch sizes ≥ 8 while staying competitive with Mamba’s numbers.

> *Takeaway:* If you need long contexts *and* high-throughput decoding—think chat assistants handling multi‑turn dialogues—the constant‐memory design of xLSTMs offers a tangible advantage over conventional Transformers.

---

## 5. Practical Recommendations  

| Scenario | Preferred Variant | Why |
|----------|-------------------|-----|
| Edge devices / VRAM constrained inference with very long prompts (> 8 k tokens) | **sLSTM** or **mC + sC hybrid** (e.g., xLM[7:1] → mostly mLSTM blocks + occasional sMLP heads) | Constant activation footprint enables long contexts without cache overflow |
| Tasks requiring fine state tracking (e.g., program evaluation, dynamic entity resolution) | **sLSTM** (exponential gating + mixing) | Memory mixing lets later timesteps revise earlier decisions—a capability missing from pure m​​​​​​​​​​​​​…※|
| Pure speed at scale >128 GPUs where large dense ops are cheap | **mLSTM**, ideally after kernel optimization | Parallelizable scan eliminates sequential bottlenecks; dense matrix ops map well onto Tensor Cores |
| Mixed workloads needing both expressive state tracking *and* high throughput | Hybrid stacks (**xLM[a:b]**) where b≈0–1% provide occasional sLM layers interleaved among many mLM layers |

In practice you’ll often see an architecture like **xLM[7:1]**, meaning seven out of eight residual blocks use mLCU‐style updates while one block injects an sLCU layer for occasional revision capability without sacrificing overall speed.

## 7. TL;DR  

*Transformers pay a quadratic price for attention.*  
*xLM sidesteps this by keeping computation linear in sequence length.*  
> • **sLM:** Powerful state revision via exponential gates + mixing → sequential scan → ~2× slower than fully parallel version but still far faster than quadratic attention at long horizons.  
> • **mLM:** Matrix‐memory updates eliminate hidden‐hidden links → embarrassingly parallel scans → current kernels ~4× slower than FlashAttention but offer ample headroom for optimization.  
> • Both variants keep per‑token memory constant → feasible inference on 16 k+ token windows even on modest GPUs.  
> • Benchmarks show linear latency growth and higher decoding throughput compared to LLama; comparable or slightly ahead of Mamba at similar scales.

As OpenAI’s GPT line goes deeper into billions of parameters while Transformers dominate research headlines, xLM demonstrates that there’s still room—and perhaps unexploited efficiency—in revisiting recurrent designs when paired with modern hardware tricks and clever gating schemes.
