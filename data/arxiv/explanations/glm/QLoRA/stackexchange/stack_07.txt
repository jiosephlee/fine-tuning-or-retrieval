\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### What exactly causes memory spikes during gradient checkpointing with long sequences?
Question:
The paper introduces Paged Optimizers to handle "memory spikes that occur when processing a mini-batch with a long sequence length" during gradient checkpointing. I understand that gradient checkpointing reduces memory by not storing all intermediate activations and recomputing them during the backward pass. But what specifically causes memory spikes in this setting? Is it that certain layers produce very large intermediate tensors when sequences are long? And how does NVIDIA unified memory's paging mechanism help — does it simply move optimizer states to CPU RAM when GPU memory is full and page them back when needed for the optimizer update step? Does this paging introduce significant latency?
Answer:
# Understanding Memory Spikes During Gradient Checkpointing

The memory spikes during gradient checkpointing with long sequences arise from the interaction between activation gradients and optimizer states competing for GPU memory simultaneously during the backward pass.

## What Causes the Memory Spikes

Gradient checkpointing reduces **average** memory by discarding intermediate activations during the forward pass and recomputing them during the backward pass. However, it does not eliminate **peak** memory usage. During the backward pass, when activations are recomputed for a particular layer, they must be held in memory to compute gradients through that layer. With long sequences, each layer's activation tensor scales with sequence length $L$, hidden dimension $h$, and batch size $b$, producing tensors of size proportional to $L \times h \times b$.

The paper provides concrete numbers for a 7B LLaMA model: LoRA input gradients consume 567 MB per sequence without checkpointing, reduced to an average of 18 MB per sequence with checkpointing, while the 4-bit base model itself occupies 5,048 MB. The critical observation is that during the backward pass, you can have multiple layers' worth of recomputed activations in memory simultaneously — the memory savings from checkpointing come from not storing all layers at once, but individual layers (or groups of layers being recomputed) still produce large temporary tensors. When sequence length is long, these recomputed activation tensors can become very large, creating a temporary spike in memory usage that exceeds available GPU capacity.

Additionally, the paper notes that "most of the memory footprint for LLM finetuning comes from activation gradients and not from the learned LoRA parameters." So the LoRA parameters themselves (26 MB for the 7B model) are negligible compared to the activation gradients, making the spikes almost entirely driven by sequence length.

## How Paged Optimizers Help

Paged Optimizers leverage NVIDIA's unified memory feature, which provides automatic page-to-page transfers between CPU RAM and GPU memory, analogous to how an operating system pages between RAM and disk. The optimizer states are allocated in this paged memory space. During normal training with moderate sequence lengths, the optimizer states reside on the GPU. When a memory spike occurs (e.g., processing a batch with long sequences during the backward pass), the GPU runs out of memory, and the unified memory system automatically evicts the optimizer states to CPU RAM. Later, when the optimizer update step executes and requires those states, they are paged back into GPU memory.

The key insight is that the optimizer states are not needed during the forward or backward pass — they are only needed when the optimizer step actually updates the weights. This creates a natural temporal separation: the memory spike happens during backpropagation (when activations are being recomputed and gradients computed), while the optimizer states are only needed afterward. Paged Optimizers exploit this temporal separation by letting the operating system handle the eviction and recall automatically.

## Latency Considerations

The paper indicates that the latency introduced by paging is negligible in practice. They report that "with a batch size of 16, paged optimizers provide the same training speed as regular optimizers" for 65B models on 48GB GPUs. Furthermore, they note that "the paging only occurs when processing mini-batches with long sequence lengths, which is rare." This means for most training steps, no paging occurs at all, and the overhead only manifests occasionally. The paper does not provide detailed latency measurements for the paging process itself, acknowledging that "future work should measure and characterize under what circumstances slow-downs occur from the paging process," but the empirical evidence suggests the practical impact on training speed is minimal.

In summary, the memory spikes are caused by large recomputed activation gradients during the backward pass with long sequences, which can temporarily exceed GPU memory when combined with resident optimizer states. Paged Optimizers resolve this by automatically paging optimizer states to CPU RAM during these spikes and back to GPU when needed, with negligible practical overhead.
