\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### What happens when LLM-generated rules reference features that were not in the training prompt due to bagging?
Question:
The paper uses feature bagging to handle datasets with many features (like Communities with 100+ attributes). If a subset of features is selected for a particular ensemble trial, the LLM generates rules based only on those features. But what happens when applying these rules to test data?

For a test sample, do we only check the rules that reference features seen during that trial? Or do we need to have all original features available at test time? Also, if different ensemble trials see different feature subsets, how do we combine the rule evaluations from different trials if they reference different features?
Answer:
At test time, **all original features must be available**, even though each individual ensemble trial only saw a subset of features during training. The key insight is that the ensemble operates at the **probability level**, not at the feature or rule level, so there is no conflict when different trials reference different features.

Here is how it works concretely. During training, for each trial $t$, feature bagging selects a subset of the original features, and the LLM generates rules referencing only those features. Those rules are parsed into code and applied to the data to produce binary features $\mathbf{z}_k^i \in \{0,1\}^R$ for each class $k$. A linear model with non-negative weights $\mathbf{w}_k[t]$ is then trained on these binary features. At test time, for that same trial $t$, the parsed rule code is executed on the test sample, checking only the conditions on the features that were included in that trial's bagged subset. The binary features produced are then multiplied by the trained weights for that trial to produce a logit, which is passed through softmax to yield class probabilities $\mathbf{p}^i[t]$.

Crucially, the final prediction is made by **averaging the class probabilities across all $T$ trials**: $\hat{\mathbf{p}}^i = \frac{1}{T}\sum_{t=1}^T \mathbf{p}^i[t]$. Each trial independently evaluates its own rules against its own feature subset and produces its own probability estimate. The ensemble then combines these probabilities. This means there is no need to align or reconcile rules across trials — a rule from trial $t_1$ referencing feature $f_a$ and a rule from trial $t_2$ referencing feature $f_b$ never interact directly. They each contribute to their own trial's probability estimate, and those estimates are simply averaged.

This design is intentional and directly addresses the concern you raise. As the paper notes, "a single rule set might not capture the relationships of all features, [but] the ensemble of various weak learners created across multiple trials can nullify the impact of incomplete feature/instance coverage in individual trials." Each trial is a weak learner that only sees part of the feature space, but collectively the ensemble covers the full space because different trials see different subsets. If a feature is important, it will appear in multiple bagged subsets, and the trials that include it will tend to produce better-calibrated probabilities, which dominates the average. Conversely, trials that happened to exclude an important feature will simply produce noisier estimates, which are diluted by the ensemble.

In practice, this means the test-time pipeline requires maintaining, for each trial, its set of parsed rules (as executable code) and its trained weight vector $\mathbf{w}[t]$. When a test sample arrives, all original features are passed to each trial's rule code — but each trial's code only accesses the features its rules reference, ignoring the rest. The binary outputs are dotted with that trial's weights, softmaxed, and the resulting probabilities are averaged across trials. The full feature vector is needed at test time because you cannot know in advance which trial's rules will reference which features, but the computational cost per trial is minimal since it involves only a dot product on a small binary vector.

This connects to a broader principle in ensemble methods: feature bagging (as in Random Forests) introduces diversity by having different learners operate on different views of the data, and aggregation at the output level makes the ensemble robust to the incompleteness of any individual learner. FeatLLM applies this same principle but with LLM-generated rules as the "learners" and probability averaging as the aggregation mechanism, which elegantly sidesteps the problem of combining heterogeneous rule sets that reference different features.
