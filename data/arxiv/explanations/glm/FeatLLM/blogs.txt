# From Predictor to Prep Cook: How LLMs Are Reinventing Spreadsheet Analysis

Tabular data—think spreadsheets and databases—remains the lifeblood of industries like finance and healthcare. Making accurate predictions from a small number of labeled samples, however, is notoriously difficult. Recently, researchers have tried to apply Large Language Models (LLMs) to these tabular tasks, but forcing an LLM to act as an end-to-end predictor for every row in a spreadsheet is like hiring a master chef just to chop vegetables: it works, but it is incredibly inefficient. 

A new framework called FeatLLM proposes a paradigm shift. Instead of asking an LLM to predict the outcome for every single row, FeatLLM uses the LLM as a "prep cook"—an expert feature engineer that reads the data, infers logical rules, and prepares the ingredients. The actual prediction is then left to a simple, lightweight mathematical model.

## The Bottleneck in Tabular LLMs

Current approaches to LLM-based tabular learning typically serialize the data into text and feed it directly into the LLM. The LLM then processes the prompt and outputs a prediction. This method has three major limitations:
*   **High inference cost:** Every single sample requires its own LLM inference query, which becomes computationally expensive and slow.
*   **Fine-tuning requirements:** Many methods require parameter-efficient fine-tuning to achieve high accuracy. This is infeasible for state-of-the-art closed-source models that only offer API-level access.
*   **Prompt size limits:** When a dataset has hundreds of features, the serialized text becomes too long for the LLM's context window, causing performance to degrade or the approach to fail entirely.

## From End-to-End Predictor to Feature Engineer

FeatLLM bypasses these bottlenecks by changing the LLM's role. Rather than directly outputting a prediction for a given row, the LLM is tasked with understanding the "criteria" or rules underlying the task. For example, if the task is to predict chronic heart failure, the LLM infers and generates rules that determine which feature conditions indicate the disease. These rules are then used to create new binary features, and the LLM is completely removed from the inference process.

To get the best rules out of the LLM, FeatLLM structures the prompt into a two-step reasoning process that mimics how a human expert would approach the task:
1.  **Understand the problem:** The LLM first infers causal relationships or tendencies between features and the target task, relying solely on its general prior knowledge without looking at examples. 
2.  **Derive decisive rules:** Using the knowledge from the first step and a few labeled examples, the LLM deduces a fixed number of rules (10 per class) to distinguish the classes. 

Once the rules are generated in natural language, they need to be converted into machine-usable features. Because LLMs can produce noisy text with varied syntax (like substituting "$<$" with "less than"), FeatLLM leverages the LLM's code generation capabilities. The LLM is prompted to write Python code that parses its own natural language rules into a function. This function is then executed to transform the data into binary features—either a $1$ if a sample satisfies a rule, or a $0$ if it does not.

## Serving the Final Dish: Lightweight and Robust

With the new binary features in hand, FeatLLM no longer needs the LLM. The final prediction is handled by a simple linear model. For a sample $\mathbf{x}^i$, the binary features for class $k$ are denoted as $\mathbf{z}_k^i \in \{0, 1\}^R$, where $R$ is the number of rules. The class likelihood is computed using a dot product with non-negative trainable weights $\mathbf{w}_k$, passed through a softmax function:

$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$

$\mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i, ..., \text{logit}_{c}^i])$

By projecting the weights into a positive subspace ($\max(\mathbf{w}_k, 0)$), the model ensures that a rule never actively reduces the likelihood of a class during training. The model optimizes a simple cross-entropy loss to learn the importance of each rule.

To make the system even more robust, FeatLLM uses an ensemble approach. The entire rule-generation and training process is repeated multiple times with feature and instance bagging. This solves the prompt size limit issue—if a dataset has too many features, bagging reduces the number of features fed into the LLM. It also improves robustness through self-consistency: even if the LLM generates incorrect rules in some trials, correct rules from other trials can compensate.

## Key Takeaways

FeatLLM's approach of using LLMs as feature engineers rather than predictors unlocks massive efficiency gains:
*   **Low inference cost:** At inference time, only the simple linear model is used, making inference times comparable to conventional machine learning models and drastically faster than end-to-end LLM methods.
*   **API-friendly:** It requires no model fine-tuning, working entirely through standard API access.
*   **High performance:** Evaluated across 13 different datasets, FeatLLM significantly outperformed alternatives like TabLLM and STUNT by 10% on average. With only 4 labeled shots, FeatLLM achieved performance comparable to conventional tabular baselines that required 32 shots.
*   **Robust to noise:** By forcing the LLM to use prior knowledge to reason about the task, FeatLLM filters out spurious correlations from irrelevant data columns.

By delegating the heavy lifting of reasoning to the prep phase and leaving the final math to a simple model, FeatLLM offers a practical, highly efficient alternative for applying LLMs to real-world tabular data.



# The High Cost of AI Predictions: Why FeatLLM Skips the LLM at Inference Time

Large Language Models (LLMs) have proven surprisingly adept at tabular learning tasks. By serializing rows of data into text and feeding them to an LLM along with feature descriptions, we can achieve impressive few-shot predictions. But there is a massive operational catch: doing this in production means sending every single data row through an LLM API. The latency and API costs for thousands or millions of rows are astronomical, making traditional LLM-based tabular learning a hard sell for real-world, large-scale applications.

## The Bottleneck with Current LLM Tabular Models

Most current LLM-based tabular learning methods treat the LLM as an end-to-end predictor. If you want to predict whether 10,000 customers will subscribe to a term deposit, you serialize 10,000 rows and make 10,000 API calls. This is computationally expensive and slow. 

Furthermore, many high-performance approaches require fine-tuning the LLM. This is often impossible with modern, top-tier LLMs that only offer restricted inference APIs and do not provide access to training codebases. Finally, when tabular datasets have a large number of features, the serialized text can easily exceed the LLM's prompt size limit, degrading performance or breaking the pipeline entirely.

## FeatLLM: The LLM as a Feature Engineer

The paper "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning" introduces a framework called FeatLLM to solve these operational bottlenecks. The core idea is brilliantly simple: use the LLM as a feature engineer rather than an end-to-end predictor. 

During a preparation phase, FeatLLM queries the LLM a handful of times to extract human-readable "rules" or criteria for the target classes. For a disease prediction task, the LLM might suggest rules based on its prior knowledge, such as identifying that older individuals are at an increased risk. These rules are then parsed into program code to generate new binary features for the dataset. At inference time, FeatLLM completely bypasses the LLM, relying only on a lightweight downstream machine learning model to make predictions using these newly engineered features.

## How It Works

FeatLLM prompts the LLM with a structured, two-step reasoning process to mimic how a human expert would approach the task:
1. The LLM is asked to infer the causal relationship or tendency between features and the target, relying purely on its general prior knowledge.
2. The LLM is given a few-shot examples and asked to deduce decisive rules for each class based on that prior knowledge.

Because LLMs can produce syntactically noisy text, FeatLLM actually uses the LLM itself to parse these natural language rules into executable Python code. This code is applied to the data to create binary features, denoted as $\mathbf{z}_k^i \in \{0, 1\}^R$ for a given sample $i$ and class $k$, indicating whether the sample satisfies the rules.

To infer class likelihood, FeatLLM uses a simple linear model without bias. The probability for each class is calculated as:

$$ \text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i $$

$$ \mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i, ..., \text{logit}_{c}^i]) $$

Here, $\mathbf{w}_k$ represents the trainable weights signifying the importance of each rule. By projecting these weights into a positive subspace, the model ensures that a rule never actively reduces a class's likelihood during learning. Because the inference step only involves a dot product and a softmax function, it is lightning fast.

## Tackling Prompt Limits and Noise

FeatLLM repeats this rule-generation process multiple times using an ensemble approach with bagging. By randomly selecting subsets of features and instances for each trial, it mitigates the issue of large prompts exceeding the LLM's context window. The final prediction is made by averaging the class probabilities across all the ensemble trials. 

This ensemble method offers two major advantages. First, it adds robustness against any single set of incorrect rules generated by the LLM, relying on self-consistency to ensure commonly inferred rules dominate. Second, it fundamentally solves the prompt size limitation by ensuring no single query needs to contain the entirety of a massive dataset's features.

## The Payoff: Fast, Cheap, and Accurate Inference

The operational benefits of this architecture are immense. By skipping the LLM at inference time, FeatLLM reduces inference latency to levels comparable with traditional methods like Logistic Regression or XGBoost. In runtime comparisons on the Adult dataset, FeatLLM's inference time was a fraction of that of LLM-based methods like in-context learning or TabLLM. During training, the entire framework only requires about 30 API queries, which can be parallelized and executed at a negligible cost.

Despite the lightweight inference, FeatLLM does not sacrifice accuracy. Across 13 diverse tabular datasets, it outperformed baselines like TabLLM and STUNT by an average of 10\% in AUC. Impressively, using only 4 labeled samples, FeatLLM achieved performance comparable to conventional tabular baselines that required 32 samples. It also proved highly resilient to spurious correlations, as the LLM filters out irrelevant columns when generating rules based on its prior knowledge.

FeatLLM represents a pragmatic shift in how we leverage LLMs for tabular data. By confining the LLM to the feature engineering phase and using a simple linear model for predictions, it delivers the best of both worlds: the rich prior knowledge of massive language models and the speed, cost-efficiency, and scalability of traditional machine learning.



# Doing More with Less: How AI is Solving the Data Scarcity Problem in Healthcare and Finance

## The Labeled Data Bottleneck

In healthcare and finance, data is everywhere—but labeled data is precious. A hospital might have millions of patient records, but getting expert physicians to manually annotate which patients developed a specific complication requires time, specialized knowledge, and money. The same goes for credit risk assessment, where labeled outcomes may take years to materialize.

This scarcity of labeled examples creates a fundamental tension: machine learning models typically need large amounts of labeled data to perform well, but the domains where predictive modeling is most valuable are often the ones where labels are hardest to obtain.

Enter **few-shot learning**—the ability to learn from just a handful of examples. While few-shot learning has been extensively studied for images and text, tabular data (the spreadsheets and databases that power most real-world applications) has proven more challenging. The heterogeneous nature of tabular data makes it difficult to apply standard augmentation tricks or transfer learning approaches effectively.

A new framework called **FeatLLM** offers a fresh perspective on this problem by turning large language models (LLMs) into feature engineers rather than predictors. The results are striking: with just 4 labeled samples, FeatLLM matches the performance of traditional models that require 32 samples.

## Rethinking the Role of LLMs in Tabular Learning

Previous approaches to using LLMs for tabular data followed a straightforward recipe: serialize each row of data into text, feed it into the LLM along with a task description, and let the LLM make the prediction. While this works reasonably well, it has several practical limitations:

- Every prediction requires an LLM inference call, making it expensive at scale
- Many top-performing LLMs only offer API access, so fine-tuning isn't always possible
- When datasets have many features, the serialized text can exceed the LLM's context window

FeatLLM takes a different path. Instead of asking the LLM to predict outcomes for individual samples, it asks the LLM to act as a **feature engineer**—someone who looks at the data, understands the problem domain, and crafts useful features that a simpler model can use.

The key insight is that LLMs possess rich **prior knowledge** from their training on vast text corpora. A model like GPT-3.5 knows, for instance, that older individuals face increased risk of certain diseases, or that specific financial indicators tend to correlate with credit risk. FeatLLM extracts this knowledge in the form of explicit rules, then uses those rules to transform raw data into informative binary features.

## How FeatLLM Extracts Rules from Prior Knowledge

The framework structures the LLM's reasoning into a two-step process that mirrors how a human expert might approach a new tabular learning task.

**Step 1: Understand the problem domain.** The LLM is given a task description and feature definitions, then asked to reason about the causal relationships or tendencies between features and the target variable. Crucially, this step relies on the LLM's general knowledge rather than the few labeled examples. For a healthcare task, the LLM might reason about how age, blood pressure, and cholesterol levels relate to heart disease risk based on its training on medical literature.

**Step 2: Derive decisive rules.** Using the domain understanding from Step 1 along with a few labeled examples as demonstrations, the LLM generates specific rules for each class. For example, a rule might be "age > 60 AND blood pressure > 140" for predicting chronic heart failure.

The prompt is carefully designed with three components:

- **Basic information**: task description, feature definitions, and serialized few-shot examples
- **Reasoning instructions**: guidance for the two-step reasoning process
- **Response instructions**: formatting constraints to make the output parseable

This structured approach helps the LLM filter out uninformative features and focus on the most significant ones, which is particularly valuable in low-data regimes where spurious correlations are a real risk.

## From Rules to Predictions

Once the LLM generates rules, they need to be converted into usable features. FeatLLM handles this by asking the LLM itself to write Python code that checks whether each rule is satisfied for a given sample. The output is a set of binary features—1 if the sample satisfies a rule, 0 otherwise.

For a classification task with $c$ classes and $R$ rules per class, each sample $\mathbf{x}^i$ is transformed into binary feature vectors $\mathbf{z}_k^i \in \{0, 1\}^R$ for each class $k$. The class probability is then computed using a simple linear model:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

$$\mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i, ..., \text{logit}_{c}^i])$$

Here, $\mathbf{w}_k$ are trainable weights that learn the importance of each rule. The weights are constrained to be non-negative, ensuring that satisfying a rule never reduces the likelihood of a class. This simple model is trained with cross-entropy loss on the few available labeled samples.

## Robustness Through Ensembling

A single round of rule generation might miss important patterns or include incorrect rules. FeatLLM addresses this by repeating the entire process multiple times with randomness introduced through:

- High LLM temperature for diverse rule generation
- Randomized ordering of few-shot demonstrations
- Feature and instance bagging (selecting random subsets)

The final prediction averages the class probabilities across all trials. This ensemble approach offers two key benefits: correct rules from some trials compensate for incorrect rules in others, and bagging helps handle datasets with many features that would otherwise exceed the LLM's context window.

The experiments showed that performance improves as the number of ensembles increases, with gains converging around 20 trials. For the number of rules per class, 10 was found to be the sweet spot—enough to capture relevant patterns without introducing too much dimensionality for the low-shot regime.

## The 4-Shot Results

The paper evaluates FeatLLM on 13 datasets spanning healthcare (Heart, Diabetes, Myocardial), finance (Credit-g, Bank), and other domains. The results demonstrate remarkable data efficiency.

FeatLLM with just **4 labeled samples** achieves performance comparable to conventional tabular learning methods (logistic regression, XGBoost, RandomForest) that require **32 labeled samples**. On average, FeatLLM outperforms alternatives like TabLLM and STUNT by 10% in AUC.

The framework also proved robust against spurious correlations—a common problem in low-data settings. When irrelevant columns from an unrelated dataset were added to the Heart dataset, FeatLLM showed the least performance degradation compared to baselines. This is because the structured reasoning process forces the LLM to consider the relationship between features and the task based on prior knowledge, preventing it from generating rules based on irrelevant columns. In experiments with spurious columns, rules based on noisy data accounted for only 1-2% of the total rules generated.

## Practical Advantages for Real-World Deployment

Beyond raw performance, FeatLLM offers several practical advantages that make it suitable for real-world healthcare and finance applications:

- **Low inference cost**: Unlike end-to-end LLM approaches that require one API call per sample, FeatLLM only uses a simple linear model at inference time. The LLM is only consulted during the feature engineering phase.
- **API-only access**: No fine-tuning is required, making it compatible with LLMs that only offer inference APIs (like GPT-4 or PaLM).
- **Scalability to many features**: The bagging and ensemble approach handles datasets with over 100 features, where other LLM-based methods fail due to context window limitations.
- **Interpretability**: The generated rules provide human-readable explanations for predictions, which is critical in healthcare and finance where understanding model decisions is often a regulatory requirement.

## Why Prior Knowledge Matters in Low-Data Regimes

The ablation studies in the paper reveal an interesting pattern about when LLM prior knowledge matters most. Feature descriptions and the structured reasoning process have the highest impact when the number of labeled samples is smallest. As the number of shots increases, the benefit of weight tuning grows—because with more data, the model can better estimate the importance of each rule.

This finding aligns with intuition: when data is scarce, prior knowledge serves as a critical inductive bias that guides the model toward meaningful patterns. When data is abundant, the data itself can reveal which features matter, making the learned weights more reliable.

For healthcare and finance practitioners, this means FeatLLM is most valuable exactly where it's needed most—in situations where labeled data is expensive and hard to obtain, but domain knowledge captured in the LLM's training corpus can fill the gap.

## Looking Ahead

FeatLLM demonstrates that the key to applying LLMs to tabular learning isn't asking them to make predictions directly, but rather leveraging their knowledge to engineer better features. This shift in perspective—from black-box predictor to transparent feature engineer—opens up practical applications that were previously limited by cost, access, or data constraints.

The current framework focuses on low-shot regimes. Future work aims to extend it to larger datasets, explore feature types beyond rules, and enhance interpretability further. As LLMs continue to evolve and accumulate more domain knowledge, approaches like FeatLLM that extract structured knowledge rather than opaque predictions will become increasingly powerful tools for data-scarce industries.



# Taming Massive Spreadsheets: How Ensemble Bagging Solves the LLM Context Limit

## The Context Window Bottleneck in Tabular Learning

Large Language Models (LLMs) have shown impressive capabilities in few-shot tabular learning, where data is scarce and domain knowledge is crucial. However, applying them to wide, complex datasets often hits a hard wall: the context window limit. When a dataset includes over 100 columns—such as the `Communities` or `Myocardial` datasets mentioned in recent research—serializing the tabular data along with feature descriptions and few-shot examples creates a massive prompt. As the prompt grows, it eventually exceeds the LLM's input limit, or worse, the model's performance degrades due to the struggle with lengthy contexts.

A new framework called FeatLLM offers an elegant way around this constraint. Instead of using the LLM to make end-to-end predictions for each sample, FeatLLM employs the LLM as a feature engineer. By combining this approach with ensemble bagging, the framework can process massive spreadsheets without overflowing the prompt.

## From Columns to Rules: The FeatLLM Approach

FeatLLM shifts the LLM's role from predicting labels directly to generating "rules"—the underlying conditions associated with each target class. For example, when predicting a disease, the LLM might infer rules like "age $> 50$" or "blood pressure $> 140$".

The framework's prompt design guides the LLM through a structured, two-step reasoning process. First, the LLM infers the causal relationship between features and the target task without looking at examples, relying on its prior knowledge. Second, it uses few-shot example demonstrations to deduce decisive rules for each class. These rules are then parsed into program code, applied to the data, and transformed into binary features: $1$ if a sample satisfies a rule, and $0$ if it does not. A simple linear model then learns the importance of these rules to estimate class likelihood.

## Bypassing the Limit with Feature Bagging

So, how does FeatLLM handle datasets with over 100 features without exceeding the LLM's context window? The answer lies in ensemble bagging. 

If a dataset is too wide to fit into a single prompt, FeatLLM does not try to force it. Instead, it adopts a bagging strategy to select a subset of features and instances for each trial. By appropriately adjusting the number of features chosen in each bag, the framework ensures the prompt size stays well within the LLM's allowable limits.

Because a single trial only sees a fraction of the features, the rules it generates might not capture the full picture. To solve this, FeatLLM repeats the rule-generation process multiple times—using a high LLM temperature and randomized few-shot prompt orders to introduce diversity. The framework defaults to $20$ ensemble trials and extracts $10$ rules per class. 

While a single rule set acts as a "weak learner" with incomplete feature coverage, the ensemble of various trials nullifies the impact of those individual blind spots. If the LLM generates an incorrect rule in one trial, correct rules from other trials can compensate, enhancing the overall robustness of the framework.

## The Math Behind the Ensemble

Let's look at how the ensemble combines these rules mathematically. For a given sample $\mathbf{x}^i$ and class $k$, the generated binary features are represented as $\mathbf{z}_k^i \in \{0, 1\}^R$, where $R$ is the number of rules per class. 

The likelihood for each class is computed using a linear model without bias. The logit for class $k$ is calculated as:
$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

Here, $\mathbf{w}_k$ represents the trainable weights that signify the importance of each rule. Projecting these weights into a positive subspace ensures that features generated by the LLM do not inadvertently reduce a class's likelihood during learning. 

These logits are then passed through a softmax function to get class probabilities:
$$\mathbf{p}^i = \text{Softmax}([\text{logit}_1^i, ..., \text{logit}_c^i])$$

During training, the model optimizes cross-entropy loss to learn the weights $\mathbf{w}_k$ using the few available labeled samples. Finally, given the collection of trained weights from $T$ trials, denoted as $\{\mathbf{w}[t]\}_{t=1}^T$, the final prediction is made by simply averaging the probabilities across all trials.

## Robustness for Real-World Data

By combining feature engineering with ensemble bagging, FeatLLM solves a fundamental challenge in LLM-based tabular learning. It mitigates the context window limit, allowing the model to handle datasets with numerous features effectively. Furthermore, because the LLM is only used to generate rules during the feature engineering phase, FeatLLM eliminates the need to send queries to the LLM for each sample at inference time. This results in a fast, efficient, and highly accurate framework that makes applying LLMs to real-world, massive spreadsheets entirely feasible.



# Filtering the Noise: How AI Feature Engineering Stays Resilient Against Bad Data

## The Curse of Noisy Columns in Low-Data Learning

If you've ever worked with tabular data in a low-shot learning scenario, you know the frustration: with only a handful of labeled examples, machine learning models latch onto spurious correlations—those irrelevant or noisy columns that happen to correlate with the target by pure chance. Add a few junk features to your dataset, and watch your model's performance crumble.

Traditional approaches like logistic regression, XGBoost, and random forests all suffer from this problem. When training data is scarce, these models can't distinguish between signal and noise. They see a column that happens to align with the labels in your tiny training set and treat it as a genuine predictor, only to fail miserably on test data.

But what if your feature engineer had common sense? What if they could look at a column of random data and say, "This has nothing to do with predicting heart disease," and simply ignore it?

## FeatLLM: An LLM as Your Feature Engineer

This is exactly what **FeatLLM** does. Instead of using large language models (LLMs) to make end-to-end predictions for each sample, FeatLLM assigns the LLM the role of a feature engineer. The LLM analyzes the task, leverages its prior knowledge, and generates human-readable rules that distinguish between classes. These rules become new binary features fed into a simple downstream model—like linear regression—for prediction.

The key insight is that the LLM doesn't just look at the data values; it understands what the features *mean*. When FeatLLM encounters a task like predicting coronary artery disease, the LLM draws on its training corpus of medical knowledge to reason about which features are genuinely relevant.

## A Structured Reasoning Process That Filters Noise

FeatLLM's resilience to spurious correlations comes from its carefully designed prompt structure, which mimics how a human expert would approach a tabular learning task. The prompt includes two critical reasoning steps:

1. **Understanding the problem**: The LLM first infers the causal relationship or tendency between features and the task description, *without* looking at the example demonstrations. This step relies purely on the LLM's general knowledge and common sense, allowing it to fully extract its prior knowledge about the problem domain.

2. **Deriving rules from examples**: In the second step, the LLM uses the few-shot examples alongside the knowledge from step one to deduce decisive rules for each class.

This two-step process is crucial. By first reasoning about what features *should* matter based on domain knowledge, the LLM is primed to ignore irrelevant columns when it later examines the data examples. A random column from an unrelated dataset won't factor into the LLM's reasoning about heart disease risk factors because it has no semantic connection to the task.

## The Experiment: Adding Junk to the Mix

To test this hypothesis, the researchers designed a straightforward but telling experiment. They took the Heart dataset (predicting coronary artery disease) and progressively attached random columns from the completely unrelated Adult dataset (predicting income). These columns have nothing to do with heart disease—they're pure noise.

They then measured how different models' performance degraded as more irrelevant columns were added, using 8-shot learning to simulate a realistic low-data scenario. Methods that require large unlabeled datasets (like SCARF and STUNT) were excluded for fairness.

## The Results: FeatLLM Stands Firm

The results were striking. While traditional models saw significant performance degradation as spurious columns accumulated, FeatLLM showed the *least* performance decline among all tested methods. The LLM's prior knowledge acted as a powerful filter against noise.

The researchers confirmed this by examining the rules FeatLLM actually generated. Rules based on the noisy columns accounted for only 1-2% of the total rules produced. The LLM essentially looked at the junk features, determined they were irrelevant to predicting heart disease, and chose not to build rules around them.

## Why This Matters

This resilience has profound implications for real-world applications. In practice, datasets are messy. They contain features of uncertain relevance, data collection artifacts, and columns that exist simply because they were easy to capture. When labeled data is expensive—as it often is in healthcare, finance, and other domains where FeatLLM could be most valuable—traditional models struggle to separate wheat from chaff.

FeatLLM's approach of combining structured reasoning with domain knowledge offers a path forward. By forcing the LLM to justify feature relevance through its understanding of the problem, the framework naturally resists the temptation to exploit random correlations in small datasets.

That said, the researchers noted an important caveat: when columns from *closely related* datasets are attached, FeatLLM can still learn spurious correlations. If a noisy column happens to semantically relate to the task, the LLM may mistakenly incorporate it into its rules. The protection works best when the noise is genuinely irrelevant—which, fortunately, covers most real-world cases of data contamination.

## The Bigger Picture

FeatLLM's noise resilience is just one benefit of its broader approach to tabular learning. By using LLMs as feature engineers rather than end-to-end predictors, the framework also achieves:

- **Low inference cost**: No need to query the LLM for each test sample—rules are extracted once and applied as code
- **No training required**: Only API-level access to the LLM is needed, making it compatible with closed-source models like GPT-3.5
- **Scalability**: Ensemble methods with feature bagging handle datasets with hundreds of features
- **Strong performance**: Outperforming alternatives like TabLLM and STUNT by 10% on average across 13 datasets

In a world where data is abundant but labels are precious, having a feature engineer with built-in common sense isn't just nice to have—it's a practical necessity. FeatLLM shows that the path to robust few-shot learning may not run through ever more complex end-to-end models, but through the simpler, more interpretable approach of letting AI help us ask better questions of our data.
