\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Why does FeatLLM not require LLM inference at test time unlike other LLM-based tabular methods?
Question:
I'm reading the FeatLLM paper and I'm confused about the inference process. The paper claims that FeatLLM "eliminates the need to send queries to the LLM for each sample at inference time" and that it "merely requires API-level access to LLMs". But the LLM is used to generate rules and parse them into code. So at inference time, when we have a new test sample, how exactly does the prediction work without involving the LLM? Is the LLM only used during the feature engineering/training phase, and then the generated code + trained linear model handle everything at test time? Could someone clarify the full pipeline?
Answer:
# Answer

The key to understanding FeatLLM's inference efficiency lies in recognizing that the LLM is used as a **feature engineer** during a preparation phase, not as a predictor at test time. The entire pipeline can be decomposed into two stages: a one-time setup phase that uses the LLM, and a lightweight inference phase that does not.

## Setup Phase (LLM-involved, done once)

First, the LLM is prompted with task descriptions, feature descriptions, and few-shot examples to generate **rules** — natural language conditions associated with each class (e.g., "age greater than 60 AND blood pressure above 140"). Then, because these rules are in natural language and may contain syntactic variations, the LLM is prompted a second time to **parse the rules into executable Python code**. This code, when executed via Python's `exec()` function, takes a raw input sample and outputs a binary vector $\mathbf{z}_k^i \in \{0,1\}^R$ indicating which of the $R$ rules for class $k$ are satisfied by that sample.

Once the code is generated, it is fixed — it does not change between samples. The LLM is no longer needed.

## Training Phase (No LLM)

The generated code is applied to the few-shot training samples to produce binary feature vectors. A simple linear model with non-negative weights $\mathbf{w}_k$ is then trained on these binary features using cross-entropy loss:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i, \quad \mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i, \ldots, \text{logit}_{c}^i])$$

The non-negativity constraint ensures that satisfying a rule for class $k$ never decreases that class's likelihood. This process is repeated across $T$ trials (with bagging and randomized prompt ordering) to create an ensemble, but each trial only involves the linear model — no further LLM queries.

## Inference Phase (No LLM)

At test time, a new sample $\mathbf{x}^i$ is processed entirely without the LLM:

1. The pre-generated Python code (encoding the LLM's rules) is executed on $\mathbf{x}^i$ to produce binary features $\mathbf{z}_k^i$.
2. The trained linear weights $\mathbf{w}_k[t]$ from each ensemble trial $t$ are applied to compute class logits.
3. Softmax produces probabilities, and the ensemble averages across trials.

This is just a dot product and softmax — computationally comparable to logistic regression, as the paper confirms in its runtime comparison (Table~\ref{tab:cost}).

## Why Other Methods Differ

Methods like TabLLM, in-context learning, and TABLET treat the LLM as an end-to-end predictor: each test sample must be serialized into text and passed through the LLM's forward pass to obtain a prediction. This makes inference cost proportional to the number of test samples times the LLM's inference cost. FeatLLM shifts the LLM's contribution upstream into a reusable artifact (the rule-based code), so inference cost depends only on the lightweight linear model.

In essence, FeatLLM distills the LLM's prior knowledge into a fixed set of interpretable rules at training time. The LLM's "reasoning" is baked into the code and weights before any test sample is seen, which is why only API-level access (not fine-tuning) is needed, and why the LLM is never queried at test time.

### How are natural language rules converted to binary features in FeatLLM?
Question:
The paper describes that FeatLLM generates "rules" in natural language and then uses these to create binary features. The paper says: "The deduced rules are then applied to the data (parsed them as program code), and the data are transformed into a binary feature indicating whether or not the samples adheres to each rule."

I'm confused about this process. Are the rules themselves converted into Python functions that check whether a sample satisfies the rule? For example, if a rule says "age > 50 AND cholesterol > 200", does the LLM generate a Python function that takes a sample and returns 1 if both conditions are met, 0 otherwise? And then for each rule, we get a binary feature for each sample?
Answer:
Your understanding is essentially correct, but there's an important two-step process involving the LLM that's worth clarifying.

**Step 1: Rule Generation.** FeatLLM first prompts the LLM to generate rules in natural language for each class. The prompt includes the task description, feature descriptions, and few-shot examples, along with reasoning and response format instructions that constrain the output to a parseable structure. For example, the LLM might output a rule like: "age is greater than 50 AND cholesterol is greater than 200."

**Step 2: Rule Parsing via a Second LLM Call.** Rather than directly writing a hand-crafted parser for these natural language rules—which would be fragile because the LLM might write "$>$" in one rule and "greater than" in another—FeatLLM uses the LLM *itself* to convert the rules into executable Python code. A second prompt provides the function name, input/output descriptions, and the inferred natural language rules, and asks the LLM to generate a Python function that checks whether a given sample satisfies each rule. This generated code is then executed using Python's `exec()` function to produce the binary features.

So yes, the end result is exactly what you describe: for each rule, you get a binary feature for each sample ($1$ if the sample satisfies the rule, $0$ otherwise). Formally, for sample $\mathbf{x}^i$ and class $k$, the binary feature vector is $\mathbf{z}_k^i \in \{0, 1\}^R$, where $R$ is the number of rules per class. These binary features are then fed into a simple linear model with non-negative weights to estimate class probabilities via $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$ followed by a softmax.

The key insight is that FeatLLM leverages the LLM's code generation capability to handle the semantic variability in natural language rule expressions, rather than relying on a brittle regex or symbolic parser. This is a neat design choice: the LLM is used both to *invent* the rules (using its domain knowledge) and to *operationalize* them (using its code generation ability), while the actual inference at test time never touches the LLM—the generated Python functions and the trained linear weights suffice.

### What is the purpose of projecting weights to non-negative space with $\max(\mathbf{w}_k, 0)$ in FeatLLM?
Question:
In Section 3.2, the paper defines the class likelihood computation as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

where $\mathbf{w}_k$ are trainable weights and $\mathbf{z}_k^i$ are binary features.

The paper says: "By projecting these weights into a positive subspace, we can ensure that the features generated by the LLM do not reduce the likelihood of a class during learning."

I don't understand why this is necessary. If a rule is negatively associated with a class, shouldn't the weight be allowed to be negative? Why force all weights to be non-negative? Is it because the rules are specifically generated FOR each class, so by construction they should only increase that class's likelihood?
Answer:
Your intuition is essentially correct. The key reason for the $\max(\mathbf{w}_k, 0)$ projection lies in the semantics of how the rules are generated and what they represent.

The rules for class $k$ are explicitly generated by the LLM as conditions that are *indicative* of that class. The prompt instructs the LLM to "deduce rules for each class" — meaning the rules are designed as positive evidence for class membership. The binary feature vector $\mathbf{z}_k^i$ indicates whether sample $i$ satisfies each of these rules for class $k$. Since each rule is constructed to be a piece of evidence *for* class $k$, allowing its weight to become negative would mean that satisfying a rule designed to support class $k$ actually *decreases* the likelihood of class $k$. This would be semantically contradictory to the rule generation process.

With the non-negativity constraint, each weight $\mathbf{w}_{k,r}$ (for rule $r$ of class $k$) acts as a **relevance or importance score** ranging from "irrelevant" (weight near zero) to "strongly indicative" (large positive weight). The paper explicitly leverages this interpretation in its analysis, noting that "rules that have little relevance to the data (i.e., rules with learned weights below the threshold) are automatically filtered out" — a threshold of $0.1$ is used to prune uninformative rules. This filtering mechanism only makes sense if weights are non-negative, since a near-zero weight cleanly signals "this rule doesn't help" rather than "this rule actively hurts."

There is also a practical benefit in the few-shot setting the paper targets. Allowing negative weights doubles the effective parameter space (each weight can move in two directions), increasing the risk of overfitting when training samples are scarce. Constraining weights to be non-negative acts as a form of regularization that encodes the prior knowledge from the rule generation stage — namely, that these rules are meant to be supportive evidence. This is consistent with the paper's broader design philosophy of injecting inductive bias from the LLM's prior knowledge to compensate for limited data.

It is worth noting what this design gives up. If the LLM generates a rule that is actually *negatively* correlated with the target class (due to imperfect reasoning), the model cannot learn to invert its contribution — it can only suppress it by driving the weight to zero. The paper accepts this trade-off, relying on the ensemble approach (with bagging across $T$ trials) and the LLM's two-step reasoning process to reduce the generation of such counterproductive rules. The ablation study confirms this design choice is beneficial: removing the weight tuning entirely (the "$\textsf{-Tuning}$" ablation) causes performance degradation, showing that learning non-negative importance weights adds value beyond simply counting satisfied rules.

### How does feature bagging mitigate LLM prompt size limitations in FeatLLM?
Question:
The paper mentions that FeatLLM uses bagging to address prompt size limitations: "By appropriately adjusting the number of features and samples chosen in bagging, the challenge of excessive prompt size is mitigated."

I understand that bagging involves selecting random subsets of features/samples. But I'm confused about how this helps with prompt size. Is the idea that instead of putting ALL features and ALL few-shot examples into the prompt (which might exceed the context window), we randomly subsample both features and examples for each ensemble trial? So each trial gets a smaller prompt, and then the ensemble combines results from multiple trials with different feature subsets?

If so, does this mean different ensemble members see different subsets of features, and we're banking on the ensemble capturing all features across members?
Answer:
Your understanding is essentially correct. In FeatLLM, each ensemble trial receives a randomly subsampled subset of features and/or training examples in its prompt, rather than the full set. This keeps each individual prompt within the LLM's context window, even when the dataset has a large number of features (the paper notes that datasets like Communities and Myocardial have over $100$ attributes, which would create prompts exceeding the context limit if all features were included).

The prompt in FeatLLM consists of three components: basic information (task description, feature descriptions, and serialized few-shot examples), reasoning instructions, and response instructions. Each few-shot example is serialized by listing all feature values, so the prompt size grows linearly with both the number of features and the number of examples. When either dimension becomes large, the serialized text can exceed what the LLM accepts. By using bagging to select a subset of features and/or instances per trial, each trial's prompt is reduced to a manageable size.

Yes, different ensemble members do see different subsets of features. The paper explicitly acknowledges this trade-off: "While a single rule set might not capture the relationships of all features, the ensemble of various weak learners created across multiple trials can nullify the impact of incomplete feature/instance coverage in individual trials." This is directly analogous to how a Random Forest works—each tree is trained on a random subset of features and is individually a weak learner, but the ensemble collectively covers the full feature space and achieves strong performance through aggregation.

The final prediction combines all trials by averaging the class probabilities from each ensemble member's trained linear model (Equation $2$ in the paper). So a feature that is absent from one trial's prompt may still be captured by other trials that happened to include it, and the ensemble averaging ensures that rules consistently inferred across multiple trials (which the paper connects to LLM self-consistency) dominate the final prediction while noisy or incorrect rules from individual trials are downweighted through averaging.

The paper sets the number of ensemble trials to $20$ and uses a temperature of $0.5$ to introduce additional randomness in rule generation across trials. It also randomizes the order of few-shot demonstrations, since prompt ordering is known to affect LLM outputs. Together, these sources of diversity ensure that the ensemble covers different portions of the feature space across trials, making the framework robust even when no single trial can accommodate all available features.

### How does the two-step reasoning instruction prevent spurious correlations in FeatLLM?
Question:
The paper describes a two-step reasoning process in the prompt design:
1. Step 1: Infer causal relationships between features and task WITHOUT looking at example demonstrations (using only prior knowledge)
2. Step 2: Use example demonstrations AND Step 1 knowledge to derive rules

The paper claims: "This two-step reasoning process prevents the model from identifying spurious correlations in irrelevant columns and can assist in focusing on more significant features."

I'm confused about the mechanism here. If Step 1 uses prior knowledge to identify relevant features, and Step 2 uses examples, how does this ordering prevent spurious correlations? Is the idea that Step 1 acts as a "filter" that identifies which features are plausibly relevant based on domain knowledge, so that Step 2 doesn't get distracted by spurious patterns in the few-shot examples?
Answer:
Your understanding is essentially correct, and the paper provides both the conceptual mechanism and empirical evidence to support it.

The core idea is that in few-shot settings, the LLM is presented with very few examples, which dramatically increases the risk of spurious correlations. If you directly ask the LLM to derive rules from those examples alone, it may seize on patterns in irrelevant columns that happen to correlate with the target in the small sample but have no true causal relationship. For instance, in a 4-shot setting, an irrelevant column like "zip code" might coincidentally separate the classes perfectly in those 4 samples, leading the model to construct a rule around it.

Step 1 mitigates this by forcing the LLM to first reason about which features are *causally* or *semantically* relevant to the task using its pretrained prior knowledge, before it ever sees the examples. This establishes a set of plausible feature-to-task relationships grounded in domain understanding rather than data patterns. When Step 2 then introduces the examples, the LLM is already primed to focus on features it identified as meaningful in Step 1, so it tends to construct rules using those features rather than chasing coincidental patterns in irrelevant columns.

The ablation study in the paper confirms this mechanism. Removing Step 1 (the "$\textsf{-Reasoning}$" ablation) causes performance degradation, and the paper notes this effect is "high when the number of shots is small," which is exactly the regime where spurious correlations are most dangerous. The spurious correlation experiment provides further evidence: when irrelevant columns from the Adult dataset are attached to the Heart dataset, FeatLLM shows the least performance degradation compared to baselines, and rules based on noisy columns account for only $1$--$2\%$ of the total rules generated. The paper attributes this directly to the fact that "our framework forces the consideration of the relationship between the task and features based on prior knowledge when extracting rules, preventing the generation of rules based on irrelevant columns."

So yes, you can think of Step 1 as a prior-knowledge filter that constrains the hypothesis space before the LLM ever looks at the data, reducing the chance that the few-shot examples lead it astray. This is conceptually similar to injecting an inductive bias into the model — the LLM's prior knowledge acts as a regularizer against overfitting to spurious patterns in small samples.

### Why use LLM to parse its own rules into code instead of rule-based parsing?
Question:
In Section 3.2, the paper discusses parsing rules into program code. It says: "Even though we constrain formatting of responses and rules during rule generation for easier parsing, the LLM's output can include noisy syntactic changes... This variability makes parsing more challenging."

The solution is: "instead of building complex program code, we leverage the LLM itself" to generate parsing code.

I'm confused about this design choice. If the rules are generated with constrained formatting, why not use regex or rule-based parsing? Why is a SECOND LLM call needed to convert natural language rules into code? Also, does this mean FeatLLM requires TWO LLM API calls per ensemble trial - one for rule generation and one for code generation? How does this affect the total number of API calls?
Answer:
The key insight here is that the paper constrains the *format* of the LLM's rule output, but not the exact *syntax* of every token within that format. The paper gives a concrete example: even with formatting constraints, the LLM might substitute "$>$" with "greater than," or "$<$" with "less than." These are semantically identical but syntactically different expressions. A regex or rule-based parser would need to anticipate every possible phrasing of every operator, comparison, and logical combination the LLM might produce. This is essentially a natural language understanding problem — mapping varied surface forms to a consistent internal representation — which is precisely what LLMs are good at. The paper explicitly states: "The LLM is good at understanding the semantic meaning despite syntactic changes in text, and it has the ability to generate a simple code with instructions (given it's trained on code data corpus)." So rather than maintaining a brittle, ever-growing set of regex patterns to handle each new linguistic variant, the authors leverage the LLM's semantic understanding to directly emit executable Python code via a second prompt. This generated code is then run with Python's `exec()` function to transform data samples into binary features.

To your second question: yes, each ensemble trial does require two LLM API calls — one for rule generation and one for code generation from those rules. With the default setting of 20 ensemble trials, this means 40 LLM calls in principle. The paper reports "30 API queries" for the Adult dataset experiment with 16 shots, which suggests the total is on the order of 1–2 calls per trial (the exact count may reflect implementation details such as whether some parsing calls are shared or batched). Importantly, the paper emphasizes that this total is small compared to LLM-based approaches that require one API call *per sample* at inference time. Since FeatLLM only uses LLM calls during the feature engineering phase and then relies on a simple linear model for actual predictions, the 30-ish calls are a one-time training cost that can be parallelized, and inference on new samples requires zero LLM calls. This is a central design advantage of the framework: the LLM's knowledge is distilled into rules and code during training, and the resulting features feed a lightweight downstream model at test time.

### How does ensemble averaging work with different feature subsets across trials in FeatLLM?
Question:
The paper describes the ensemble approach: "Given the collection of trained weights from $T$ trials, denoted as $\{\mathbf{w}[t]\}_{t=1}^T$, the prediction is made by averaging the probability for each class $\mathbf{p}^i$ computed with each weight $\mathbf{w}[t]$ as in Eq. 2."

But if feature bagging is used, each trial $t$ might have different rules/features (different $\mathbf{z}_k^i$ vectors). So how can we average probabilities when the underlying feature spaces are different across trials?

Also, for a new test sample, do we need to apply ALL rules from ALL trials to get all the binary features? That could be a lot of rules (20 ensembles $\times$ 10 rules $\times$ number of classes).
Answer:
The key insight is that FeatLLM's ensemble averaging operates at the **probability level**, not at the feature or weight level. Each trial $t$ constitutes a complete, self-contained model with its own rules, binary feature vectors, and trained weights. The averaging happens only at the final output, which is why different feature spaces across trials pose no problem.

Specifically, for each trial $t$, the pipeline is independently executed end-to-end: rules are generated from a bagged subset of features, parsed into code, applied to produce binary features $\mathbf{z}_k^i[t]$, and weights $\mathbf{w}_k[t]$ are trained via cross-entropy loss. This yields a probability vector $\mathbf{p}^i[t]$ for any sample $\mathbf{x}^i$ using Eq. 2 with that trial's specific $\mathbf{w}[t]$ and $\mathbf{z}_k^i[t]$. The final ensemble prediction is simply:

$$\mathbf{p}^i_{\text{final}} = \frac{1}{T}\sum_{t=1}^{T} \mathbf{p}^i[t]$$

Because the averaging is over class probabilities (which always have the same dimension $c$, the number of classes) rather than over features or weights (which may differ in dimension across trials), there is no mismatch. Each trial can be viewed as an independent weak learner, and the ensemble combines their outputs in a manner analogous to how a random forest averages predictions from trees trained on different feature subsets.

Regarding your second question: yes, at inference time, you do need to apply all rules from all trials to a new test sample. With $T = 20$ ensembles, $R = 10$ rules per class, and $c$ classes, that amounts to $20 \times 10 \times c$ rule evaluations per sample. However, each rule evaluation is simply checking a binary condition (e.g., "age $> 50$"), which is a cheap $O(1)$ operation. The total cost is therefore linear in the number of rules and negligible compared to running an LLM inference per sample. This is precisely the advantage FeatLLM claims over end-to-end LLM-based methods: the LLM is only consulted during the training/feature-engineering phase (about 30 API queries total, as noted in the runtime comparison), while inference involves only fast rule checks and a dot product with non-negative weights followed by softmax.

It is also worth noting that some rules may overlap across trials due to the self-consistency property of LLMs—rules commonly inferred across multiple trials are more likely to be accurate, and averaging probabilities naturally upweights these consistent signals while diluting the impact of spurious or incorrect rules from individual trials.

### Why does FeatLLM use a simple linear model instead of more complex downstream models?
Question:
The paper states: "once the features are discovered, a complex machine learning model is no longer needed for inference, improving the inference latency" and uses linear regression/logistic regression as the downstream model.

I'm confused about this design choice. If the binary features from rules are the new representation, couldn't a more powerful model like XGBoost or a neural network learn better patterns from these features? The paper mentions that the linear model has non-negative weights, which seems restrictive. Is the simplicity of the downstream model a feature (interpretability, low overfitting risk in few-shot setting) or a necessity? The ablation study shows tuning helps, but wouldn't a more complex model capture more?
Answer:
The choice of a simple linear model with non-negative weights in FeatLLM is a deliberate design decision driven by several interconnected factors, all rooted in the few-shot tabular learning setting that the paper targets.

The core insight is that FeatLLM shifts the complexity of learning from the downstream model to the LLM's feature engineering process. The LLM, leveraging its prior knowledge and the few-shot examples, generates rules that are parsed into binary features $\mathbf{z}_k^i \in \{0,1\}^R$ indicating whether each rule for class $k$ is satisfied. At this point, the representation is already informative and semantically meaningful—the "hard work" of discovering relevant patterns has been done. What remains is simply learning the relative importance of each rule, which is a much simpler problem that does not require a complex model.

This simplicity is particularly important in the few-shot regime. As the paper notes, learning from a small number of labeled samples "presents the risk of learning spurious correlations." A more expressive model like XGBoost or a neural network has a larger hypothesis space and capacity, making it more prone to fitting noise in the limited training data. The linear model, with its constrained capacity, acts as a regularizer. The paper's ablation study supports this: while weight tuning (as opposed to simply summing rule activations) does improve performance, the gains are modest and become more significant only as the number of shots increases. This suggests that when data is scarce, even simple tuning must be done carefully, and a more complex model would likely exacerbate overfitting rather than capture additional useful patterns.

The non-negativity constraint on the weights, implemented via $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$, is a semantically motivated design choice. Since each binary feature represents whether a rule associated with class $k$ is satisfied, it would be counterintuitive for satisfying a class-$k$ rule to decrease the likelihood of class $k$. The non-negativity constraint enforces this: rules generated for a class can only contribute positively (or zero) to that class's logit. This also aids interpretability, as the learned weights directly indicate the importance of each rule, and the paper shows that irrelevant rules are effectively filtered out during tuning (weights drop below a threshold). A more complex model would obscure this transparent relationship between rules and predictions.

The paper also explicitly prioritizes inference latency as a goal. FeatLLM is designed so that "once the features are discovered, a complex machine learning model is no longer needed for inference." Since the rules are fixed after generation, inference reduces to a simple dot product followed by a softmax—computationally trivial compared to running an XGBoost ensemble or a neural network. The runtime comparison in Table 4 confirms that FeatLLM achieves inference times comparable to conventional methods like logistic regression, while other LLM-based approaches are orders of magnitude slower.

Finally, the framework compensates for the simplicity of the base model through ensembling. FeatLLM generates $T = 20$ independent rule sets with bagging and averages their predictions. This ensemble strategy introduces model complexity at the system level rather than the individual model level, improving robustness against incorrect rules generated in individual trials while keeping each component simple and interpretable. The paper draws an explicit analogy to ensemble methods like random forests, where many weak learners combine to form a strong predictor.

In summary, the linear model is both a feature and a practical necessity for this setting. It is a necessity because few-shot data cannot support a more complex model without overfitting, and because inference latency is a stated design goal. It is a feature because the LLM's feature engineering has already captured the complex patterns, leaving only a simple weighting task, and because the non-negative linear model preserves interpretability and aligns with the semantic meaning of the rule-based features.

### What happens when LLM-generated rules reference features that were not in the training prompt due to bagging?
Question:
The paper uses feature bagging to handle datasets with many features (like Communities with 100+ attributes). If a subset of features is selected for a particular ensemble trial, the LLM generates rules based only on those features. But what happens when applying these rules to test data?

For a test sample, do we only check the rules that reference features seen during that trial? Or do we need to have all original features available at test time? Also, if different ensemble trials see different feature subsets, how do we combine the rule evaluations from different trials if they reference different features?
Answer:
At test time, **all original features must be available**, even though each individual ensemble trial only saw a subset of features during training. The key insight is that the ensemble operates at the **probability level**, not at the feature or rule level, so there is no conflict when different trials reference different features.

Here is how it works concretely. During training, for each trial $t$, feature bagging selects a subset of the original features, and the LLM generates rules referencing only those features. Those rules are parsed into code and applied to the data to produce binary features $\mathbf{z}_k^i \in \{0,1\}^R$ for each class $k$. A linear model with non-negative weights $\mathbf{w}_k[t]$ is then trained on these binary features. At test time, for that same trial $t$, the parsed rule code is executed on the test sample, checking only the conditions on the features that were included in that trial's bagged subset. The binary features produced are then multiplied by the trained weights for that trial to produce a logit, which is passed through softmax to yield class probabilities $\mathbf{p}^i[t]$.

Crucially, the final prediction is made by **averaging the class probabilities across all $T$ trials**: $\hat{\mathbf{p}}^i = \frac{1}{T}\sum_{t=1}^T \mathbf{p}^i[t]$. Each trial independently evaluates its own rules against its own feature subset and produces its own probability estimate. The ensemble then combines these probabilities. This means there is no need to align or reconcile rules across trials — a rule from trial $t_1$ referencing feature $f_a$ and a rule from trial $t_2$ referencing feature $f_b$ never interact directly. They each contribute to their own trial's probability estimate, and those estimates are simply averaged.

This design is intentional and directly addresses the concern you raise. As the paper notes, "a single rule set might not capture the relationships of all features, [but] the ensemble of various weak learners created across multiple trials can nullify the impact of incomplete feature/instance coverage in individual trials." Each trial is a weak learner that only sees part of the feature space, but collectively the ensemble covers the full space because different trials see different subsets. If a feature is important, it will appear in multiple bagged subsets, and the trials that include it will tend to produce better-calibrated probabilities, which dominates the average. Conversely, trials that happened to exclude an important feature will simply produce noisier estimates, which are diluted by the ensemble.

In practice, this means the test-time pipeline requires maintaining, for each trial, its set of parsed rules (as executable code) and its trained weight vector $\mathbf{w}[t]$. When a test sample arrives, all original features are passed to each trial's rule code — but each trial's code only accesses the features its rules reference, ignoring the rest. The binary outputs are dotted with that trial's weights, softmaxed, and the resulting probabilities are averaged across trials. The full feature vector is needed at test time because you cannot know in advance which trial's rules will reference which features, but the computational cost per trial is minimal since it involves only a dot product on a small binary vector.

This connects to a broader principle in ensemble methods: feature bagging (as in Random Forests) introduces diversity by having different learners operate on different views of the data, and aggregation at the output level makes the ensemble robust to the incompleteness of any individual learner. FeatLLM applies this same principle but with LLM-generated rules as the "learners" and probability averaging as the aggregation mechanism, which elegantly sidesteps the problem of combining heterogeneous rule sets that reference different features.

### How does the $k$-shot setting work with the ensemble and bagging in FeatLLM?
Question:
The paper mentions both $k$-shot learning and bagging. In $k$-shot learning, we have only $k$ labeled samples (e.g., $k=4$). The paper also mentions "randomize the order of few-shot demonstrations" and "bagging to select a subset of features or instances."

If we only have 4 labeled samples and we do instance bagging, does that mean we might train some ensemble members on only 2-3 samples? How does bagging work with such a small number of samples? Is the instance bagging only applied to larger $k$ values? Also, for the linear model training with cross-validation, how do we do $k$-fold cross-validation when $k=4$ and we might have only 2 samples per class?
Answer:
The short answer is that for very small $k$ (e.g., $k=4$), instance bagging is not the primary mechanism driving ensemble diversity, and cross-validation is adapted by reducing the number of folds to ensure each fold contains at least one sample per class. Let me address each part of your question.

The paper states in the "Ensembling with bagging" paragraph that bagging is adopted "to select a subset of features or instances for each trial, which gets particularly useful for larger number of training samples or features." This phrasing is key: it signals that instance bagging provides the most benefit when there are more training samples to sub-sample from. When $k=4$, randomly subsampling instances would indeed leave some ensemble members with only $2$–$3$ labeled samples, which offers limited diversity benefit and risks losing class coverage. The paper does not explicitly state that instance bagging is disabled for small $k$, but the emphasis on "particularly useful for larger number of training samples or features" strongly suggests that for small $k$, the ensemble diversity primarily comes from other sources. Specifically, the paper identifies two other randomness mechanisms: setting a "sufficiently high temperature" for LLM inference and "randomiz[ing] the order of few-shot demonstrations," both of which are fully functional regardless of $k$. Additionally, feature bagging—selecting a subset of the input features (columns) rather than instances (rows)—remains applicable even with very few samples and is particularly important for datasets with many features (the paper mentions datasets like Communities and Myocardial with over $100$ attributes). So for $k=4$, the ensemble is diverse mainly due to LLM stochasticity, demonstration reordering, and potentially feature bagging, while instance bagging likely plays a minimal or negligible role.

Regarding cross-validation for the linear model, the paper states: "We employ $k$-fold cross-validation for optimal epoch selection" and later specifies that "The value of $k$ is set either as $2$ or $4$, guaranteeing that the training set includes at least one example of each class." Note that this $k$ (the number of CV folds) is a different hyperparameter from the $k$ in $k$-shot learning. For $4$-shot learning, they would use $2$-fold cross-validation, splitting the $4$ training samples into $2$ folds of $2$ samples each, with the fold boundaries chosen to ensure class balance. This ensures that during each fold, the training portion contains at least one example per class, preventing degenerate splits where a class is entirely absent. For larger training sets (e.g., $k=16$ or $k=32$), $4$-fold cross-validation becomes feasible with more samples per fold. The paper's explicit mention that $k$ is set to "either $2$ or $4$" with the constraint of class coverage confirms that the cross-validation strategy is adapted to the training set size.

In summary, the bagging and ensemble framework in FeatLLM is designed to be flexible across different $k$ values. For small $k$, the ensemble relies on LLM temperature, demonstration order randomization, and feature bagging for diversity, while instance bagging becomes more relevant as the number of training samples grows. Cross-validation is correspondingly adjusted—using fewer folds for smaller training sets—to maintain at least one sample per class per fold.
