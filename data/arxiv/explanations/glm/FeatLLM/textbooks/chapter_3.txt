\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 3: The FeatLLM Framework: Methodology

# Problem formulation for tabular learning tasks

To build a robust system for few-shot tabular learning, we must first rigorously define the structure of the data and the learning problem. In the tabular learning setting addressed by the FeatLLM framework, we begin with a dataset $\mathcal{D}$ comprising $N$ labeled samples, denoted as $\mathcal{D} = \{(\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^{N}$. Each input sample $\mathbf{x}^i$ is a $d$-dimensional vector representing $d$ distinct input features. Crucially, because this methodology relies on large language models (LLMs), the purely numerical or categorical data must be grounded in natural language. Therefore, the dataset is accompanied by natural language feature names, denoted by the set $F = \{f_j\}_{j=1}^{d}$, along with separate textual definitions that describe what each feature represents. 

The framework assumes a classification setup, meaning the label $\mathbf{y}^i$ for any given sample $\mathbf{x}^i$ belongs to a predefined set of classes. The primary objective is to learn a mapping from the input features to the target label. However, the defining characteristic of the problem is the few-shot learning regime. In a $k$-shot learning experiment, the model does not have access to all $N$ labeled samples. Instead, only a small subset of $k$ labeled samples (where $k < N$) is randomly sampled from the dataset and provided to the model for training. This constraint mimics real-world scenarios where obtaining labeled data is expensive or difficult, requiring the model to generalize effectively from very limited supervision.

# Prompt design for rule extraction

The core innovation of the FeatLLM framework lies in treating the LLM not as an end-to-end predictor, but as an expert feature engineer. To achieve this, the framework requires a carefully constructed prompt that guides the LLM to extract "rules"—the underlying conditions associated with each answer class—from the limited data it is given. An effective prompt must structure the problem-solving process in a way that mimics how a human expert would approach a tabular learning task. 

To ensure the LLM extracts rules based on an accurate and logical reasoning path, the input prompt is divided into three main components: basic information description, reasoning instruction, and response instruction. The basic information description provides the LLM with the foundational context of the task. The reasoning instruction then dictates how the LLM should process this information to deduce relationships and rules. Finally, the response instruction enforces a strict format on the output so that the generated rules can be easily parsed and utilized by the downstream system. By structuring the prompt in this way, FeatLLM filters out uninformative features and focuses the LLM's reasoning on generating decisive rules that distinguish between classes.

# Basic information description: task, features, and serialized demonstrations

The first component of the prompt, the basic information description, equips the LLM with the essential context needed to solve the tabular learning problem. This section contains three key elements: the task description, the feature descriptions, and serialized example demonstrations. The task description is formulated as a natural language question that clearly states the prediction objective, such as "Does this patient's myocardial infarction complications data indicate chronic heart failure? Yes or no?". This phrasing aligns the tabular prediction task with the question-answering format that LLMs are highly optimized to handle.

Next, the feature descriptions provide the LLM with the meaning of each column in the tabular data. For each feature, the description indicates its value type (e.g., numerical or categorical) and optionally includes a more detailed definition. For categorical variables, examples of the possible categories are provided to ensure the LLM understands the domain of the values. Finally, the prompt includes a few example demonstrations, which are the $k$ labeled training samples serialized into text. The serialization follows a straightforward format that maps the feature names and sample values into a natural language sentence, ending with the ground-truth label. Specifically, a sample $\mathbf{x}^i$ with label $\mathbf{y}^i$ is serialized as: $f_1\ \text{is}\ \mathbf{x}^i_1.\ ... \ f_d\  \text{is}\  \mathbf{x}^i_d.\ \ \text{Answer:}\  \mathbf{y}^i$. By formatting the tabular data in this manner, the LLM can seamlessly interpret the structured data as a natural language context.

# Two-step reasoning instruction: causal inference and rule deduction

The second component of the prompt is the reasoning instruction, which is designed to enhance the LLM's logical processing by breaking the inference task into two distinct steps. This structured approach begins with an introductory sentence similar to the chain-of-thought methodology, prompting the LLM to reason step-by-step. In the first step, the LLM is instructed to infer the causal relationship or tendency between the features and the task description. Importantly, the LLM is directed to perform this step without referring to the example demonstrations, relying entirely on its internal prior knowledge or common sense. This allows the LLM to fully extract its general knowledge about the problem domain, establishing a baseline understanding of which features are likely to be important before looking at the specific data.

In the second step, the LLM uses the example demonstrations alongside the knowledge derived from the first step to deduce explicit rules for each class. This two-step reasoning process is critical for preventing the model from identifying spurious correlations in irrelevant columns, as it forces the model to ground its rules in established prior knowledge before fitting the few-shot examples. To maintain a balance between underfitting (too few rules) and creating an excessively large prompt (too many rules), the LLM is instructed to extract a fixed number of rules—specifically, 10 rules—for each class. Additionally, the LLM is instructed to refer to the feature types provided in the basic information description when formulating these rules, ensuring there are no type mismatches in the generated conditions.

# Response instruction: formatting rules for automated parsing

The final component of the prompt is the response instruction, which dictates how the LLM should structure its output to facilitate automated parsing and feature generation. Because the ultimate goal is to use these rules to programmatically transform data into new binary features, the LLM's natural language output must adhere to a predictable and structured format. The prompt provides explicit guidelines on the required format for the overall response for each answer class, as well as the specific structure that each individual rule must follow.

These instructions guide the LLM to select the appropriate formatting based on the feature type (e.g., using inequalities for numerical features or exact matches for categorical features). Furthermore, the response instructions allow the LLM to combine multiple conditions into a single rule using logical operators like AND or OR when appropriate. By strictly constraining the output format, the framework ensures that the inferred rules are both human-readable and machine-parseable, bridging the gap between the LLM's natural language generation and the downstream computational requirements.

# Parsing natural language rules into executable code for feature generation

Once the LLM generates the rules in natural language, the FeatLLM framework must use these rules to create new binary features for the data. For each class, a new binary feature is created for every rule, indicating whether a given sample satisfies the conditions of that rule (represented as $1$) or not (represented as $0$). These binary features are then used to predict the likelihood that a sample belongs to a specific class. However, because the rules are generated in natural language, an automated parsing strategy is required to apply them to the tabular data.

Despite the constraints enforced by the response instructions, LLM outputs can still contain noisy syntactic variations. For instance, an LLM might substitute mathematical symbols like "$>$" or "$<$" with textual phrases like "greater than" or "less than." Building a rigid parser to handle all such variations would be complex and fragile. Instead, FeatLLM leverages the LLM itself to parse its own rules into executable program code. The LLM is presented with a new prompt containing the function name, the input and output descriptions, and the previously inferred rules. Because LLMs are trained on code corpora and excel at understanding semantic meaning despite syntactic changes, they can generate a simple Python function that accurately encodes the rules. This generated code is then executed using Python's `exec()` function to automatically perform the data conversion, transforming the original dataset into a new set of binary features indicating rule satisfaction.

# Inferring class likelihood using a non-negative weighted linear model

With the new binary features generated from the rules, the framework needs a mechanism to infer the class likelihood of each sample. A simple baseline would be to count how many rules for each class a sample satisfies. However, not all rules are equally important, so the framework must learn the significance of each rule from the few-shot training samples. To do this, FeatLLM employs a simple linear machine learning model without a bias term. Let $\mathbf{z}_k^i \in \{0, 1\}^R$ denote the generated binary feature vector for sample $\mathbf{x}^i$ corresponding to class $k$, where $R$ is the number of rules per class and $c$ is the total number of classes. The probability for each class, $\mathbf{p}^i$, is computed using a non-negative weighted linear model followed by a softmax function.

The logit for class $k$ is calculated as $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$, where $\mathbf{w}_k$ represents the trainable weights that signify the importance of each feature. By projecting these weights into a positive subspace using the $\max(\cdot, 0)$ operation, the model ensures that the features generated by the LLM do not reduce the likelihood of a class during learning. The logit vector across all classes, $[\text{logit}_{1}^i, ..., \text{logit}_{c}^i]$, is then passed through the softmax function to produce valid class probabilities $\mathbf{p}^i$. The model optimizes the cross-entropy loss to learn the weights $\mathbf{w}_k$ using the available few-shot training samples, effectively calibrating the importance of each LLM-generated rule.

# Ensembling with bagging: introducing randomness and overcoming prompt size limits

To further improve robustness and prediction accuracy, FeatLLM repeatedly executes the entire rule generation and model training process to create an ensemble of inference models. Given a collection of trained weights from $T$ trials, denoted as $\{\mathbf{w}[t]\}_{t=1}^T$, the final prediction for a sample is made by averaging the class probabilities $\mathbf{p}^i$ computed with each weight set $\mathbf{w}[t]$. This ensemble approach leverages the concept of self-consistency: rules that are commonly inferred across multiple independent trials are more likely to be accurate, and correct rules from some trials can compensate for incorrect rules generated in others.

To ensure diversity across the trials and make the ensemble effective, randomness is introduced during rule generation. A sufficiently high temperature is set for the LLM inference to encourage varied outputs, and the order of the few-shot example demonstrations is randomized for each trial, as the order of examples is known to impact LLM query outcomes. Furthermore, the framework employs bagging—randomly selecting subsets of features or instances for each trial. This bagging technique serves a dual purpose. First, it provides diverse weak learners for the ensemble, similar to a random forest. Second, it directly addresses the limitation of LLM prompt sizes. When tabular data contains a large number of features or samples, serializing the entire dataset can exceed the LLM's allowable input prompt size. By using bagging to select only a subset of features and instances, the framework keeps the prompt size manageable, ensuring robust performance even on wide or lengthy tabular datasets.
