\title{A Textbook about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

Chapter 7: Lessons Learned in Math Pre-Training

## The Hypothesis: Does Code Training Improve Reasoning?

A long-standing and popular hypothesis in the machine learning community suggests that training language models on code data improves their general reasoning abilities. The intuition behind this hypothesis is appealing: code requires structured, logical thinking, careful attention to syntax and semantics, and the ability to decompose complex problems into smaller, sequential steps—all of which are skills that overlap significantly with mathematical reasoning. However, despite the widespread adoption of this belief, the hypothesis had remained largely unverified through rigorous experimentation, particularly within the mathematical domain. The DeepSeekMath project attempts to offer a partial response to this important question by conducting carefully controlled experiments that isolate the effect of code training on mathematical reasoning performance.

The approach taken is to systematically compare models that undergo code training prior to math training against models that follow alternative training paths. By measuring performance on a variety of mathematical benchmarks—both those requiring tool use (such as solving problems by writing Python programs) and those requiring self-contained textual reasoning—the experiments provide empirical evidence that code training does, in fact, improve mathematical reasoning. This finding is significant because it offers one of the first systematic demonstrations that the benefits of code training extend beyond coding tasks themselves and transfer to quantitative reasoning domains. The authors note that their conclusion should be understood as a partial answer: they focus specifically on mathematical reasoning, and the broader claim that code training improves all forms of reasoning remains an open question. Nonetheless, within the mathematical domain, the evidence is clear and consistent across multiple experimental settings.

This result has important implications for how practitioners should think about pre-training curricula for domain-specific language models. It suggests that the order and composition of training data matter, and that code data may serve as a valuable precursor to math training, potentially helping the model develop the structured thinking patterns that are beneficial for solving mathematical problems. The finding also provides a rationale for the architectural decision to initialize DeepSeekMath-Base from DeepSeek-Coder-Base-v1.5 rather than from a general-purpose language model, as the code pre-training endows the model with reasoning capabilities that can be further refined through subsequent math training.

## Two-Stage vs. One-Stage Training Paradigms

To investigate the effect of code training on mathematical reasoning in a controlled manner, the authors design experiments using two distinct training paradigms: two-stage training and one-stage training. Each paradigm is instantiated with specific configurations that allow for meaningful comparisons.

In the two-stage training paradigm, the model is first trained on one type of data for a substantial number of tokens, and then switched to math training for an additional number of tokens. Two specific configurations are explored. In the first, the model is trained on 400B code tokens followed by 150B math tokens. This configuration directly tests whether prior exposure to code data prepares the model for subsequent math training. In the second configuration, serving as a control experiment, the model is trained on 400B general tokens (sampled from a large-scale general corpus) followed by 150B math tokens. This control is essential because it allows the researchers to distinguish between the benefits of code training specifically and the benefits of any additional pre-training on non-mathematical data more generally. Without this control, one might attribute improvements to code training when they could simply be a consequence of additional pre-training on any domain.

In the one-stage training paradigm, the model is trained on a single mixture of data without sequential staging. Two configurations are explored here as well. The first is straightforward: the model is trained on 150B math tokens alone, providing a baseline against which the effects of code data can be measured. The second configuration involves training on a mixture of 400B code tokens and 150B math tokens simultaneously. This mixed configuration is motivated by an important practical concern: as the authors note, math training following code training can degrade coding performance—a phenomenon known as catastrophic forgetting. By mixing code and math tokens in a single training stage, the researchers investigate whether the model can simultaneously develop both coding and mathematical capabilities without the regression in coding ability that occurs in the sequential two-stage approach.

All experiments are conducted using DeepSeek-LLM 1.3B, a model with 1.3 billion parameters that shares the same framework as the DeepSeek LLMs. Each model variant is trained under consistent hyperparameter settings to ensure fair comparisons. The results across these configurations reveal nuanced and sometimes surprising patterns about how code and math training interact, which are discussed in detail in the following sections.

## Impact of Code Training on Tool-Use and Non-Tool-Use Math

The effects of code training on mathematical reasoning manifest differently depending on whether the model is allowed to use tools (such as Python interpreters) to solve problems or must produce self-contained textual solutions. Understanding this distinction is crucial, as it reveals the multifaceted nature of the transfer from code training to mathematical reasoning.

For program-aided mathematical reasoning—where models are prompted to solve problems by writing Python programs that can utilize libraries such as \textit{math} and \textit{sympy} for intricate computations—code training proves beneficial across both training paradigms. Under the two-stage training setting, code training alone (the first stage, before any math training) already significantly enhances the model's ability to solve problems from benchmarks like GSM8K and MATH using Python. This is intuitive: a model trained on code is naturally better equipped to generate syntactically correct and logically sound programs. When math training is applied in the second stage, it yields further improvements on top of the code-training foundation. Under the one-stage training setting, mixing code tokens and math tokens together also proves effective for program-aided reasoning, and notably, this mixed approach mitigates the catastrophic forgetting of coding ability that plagues the two-stage sequential approach.

For mathematical reasoning without tool use—where the model must generate step-by-step textual solutions without external computational aids—the story is more nuanced. Under the two-stage training setting, the initial stage of code training already results in moderate enhancements to non-tool-use mathematical reasoning, even before any math-specific training has occurred. Moreover, this prior code training appears to boost the efficiency of the subsequent math training stage, ultimately leading to the best overall performance among the configurations tested. This is a particularly striking finding: the model that undergoes code training first and then math training outperforms the model that undergoes math training alone, suggesting that code training provides a meaningful inductive bias that facilitates the learning of mathematical reasoning patterns.

However, the one-stage mixed training approach does not fare as well for non-tool-use reasoning. When code tokens and math tokens are combined for simultaneous training, the model's mathematical reasoning without tool use is compromised compared to the sequential two-stage approach. The authors offer a conjecture for this phenomenon: DeepSeek-LLM 1.3B, due to its limited scale, may lack the capacity to fully assimilate both code and mathematical data simultaneously. In other words, the model's parameters may not be sufficient to jointly represent the knowledge structures required for both coding and mathematics when presented in an interleaved manner. This suggests that the interaction between code and math training is complex and that model scale plays a role in determining the optimal training strategy. A larger model might have sufficient capacity to benefit from mixed training without the degradation observed in the 1.3B model.

These findings collectively paint a picture in which code training serves as a valuable precursor to math training, particularly for reasoning tasks that require structured, sequential thinking. The benefits are clearest and most consistent for tool-use scenarios, where the connection between coding ability and program-aided problem solving is direct. For non-tool-use scenarios, the benefits are real but more dependent on the training paradigm and model scale.

## Catastrophic Forgetting and Mitigation Strategies

Catastrophic forgetting is a well-known challenge in machine learning whereby a model that is trained sequentially on different tasks or data distributions tends to lose proficiency in earlier tasks as it adapts to new ones. In the context of the DeepSeekMath pre-training experiments, this phenomenon manifests clearly: when a model is first trained on code tokens and then trained on math tokens in a sequential two-stage paradigm, the second stage of math training degrades the model's coding performance. The model, having acquired programming knowledge in the first stage, partially forgets this knowledge as it shifts its representational capacity toward mathematical content.

This observation raises a practical concern for the design of pre-training curricula. If one wishes to build a model that is proficient in both coding and mathematics—as DeepSeekMath aims to be—then the sequential two-stage approach presents a trade-off: the model gains mathematical reasoning capabilities but at the cost of reduced coding ability. This trade-off is undesirable, as coding proficiency remains valuable for tool-integrated mathematical reasoning, where the model must generate correct Python programs to solve problems.

The one-stage mixed training paradigm offers a natural mitigation strategy. By interleaving code tokens and math tokens during a single training stage, the model is continually exposed to both types of data, reducing the likelihood that it will forget one domain while learning the other. The experimental results confirm that this mixed approach effectively mitigates the catastrophic forgetting issue: the model trained on the mixture of 400B code tokens and 150B math tokens maintains its coding performance (as measured by standard coding benchmarks such as HumanEval and MBPP) while also developing mathematical reasoning capabilities.

Importantly, for program-aided mathematical reasoning specifically, the mixed one-stage approach not only mitigates forgetting but also synergizes coding and mathematical reasoning, producing strong performance on benchmarks where the model must write Python programs to solve math problems. This synergy suggests that the simultaneous exposure to code and math data allows the model to develop integrated representations that support the translation of mathematical problems into computational solutions.

However, as noted in the previous section, this mitigation comes with a cost for non-tool-use mathematical reasoning in smaller models. The 1.3B model trained on the mixed curriculum shows compromised performance on self-contained mathematical reasoning tasks compared to the sequential two-stage approach. This highlights a fundamental tension: the optimal strategy for mitigating catastrophic forgetting (mixed training) is not necessarily the optimal strategy for maximizing non-tool-use mathematical reasoning, at least for models of limited scale. Resolving this tension may require larger models with greater representational capacity, or more sophisticated training schedules that balance the benefits of sequential depth with the anti-forgetting properties of mixed training.

It is also worth noting that in the actual construction of DeepSeekMath-Base 7B, the authors adopt a training data distribution that includes 56\% from the DeepSeekMath Corpus, 4\% from AlgebraicStack, 10\% from arXiv, 20\% from GitHub code, and 10\% natural language data from Common Crawl. This distribution effectively follows a mixed training paradigm at a larger scale, combining math, code, and natural language data in a single training run. The inclusion of 20\% GitHub code alongside the mathematical data is consistent with the finding that code data supports mathematical reasoning, and the simultaneous training helps maintain the coding capabilities inherited from the DeepSeek-Coder-Base-v1.5 initialization. The fact that DeepSeekMath-Base 7B effectively maintains the coding performance of its precursor on HumanEval and MBPP while significantly improving on mathematical benchmarks demonstrates that, at the 7B scale, the mixed training approach successfully balances both domains.

## Evaluating the Efficacy of ArXiv Papers for Math Pre-Training

ArXiv papers are commonly included as a component of math pre-training data in many prior works. The rationale is straightforward: arXiv hosts a vast collection of scientific and mathematical papers written in LaTeX, containing dense mathematical notation, proofs, theorems, and derivations. One might naturally expect that exposure to such content would help a language model develop mathematical reasoning capabilities. However, the DeepSeekMath project conducts detailed experiments that challenge this assumption, finding that arXiv papers seem ineffective in improving mathematical reasoning—a result that may be counter-intuitive to many practitioners in the field.

The experiments are conducted with models of different sizes, including DeepSeek-LLM 1.3B and DeepSeek-Coder-Base-v1.5 7B, using arXiv corpora that have undergone varied processing pipelines. Two specific arXiv corpora are tested. The first is MathPile, an 8.9B-token corpus developed with cleaning and filtering heuristic rules, with over 85\% of its content consisting of scientific arXiv papers. The second is ArXiv-RedPajama, which comprises the entirety of arXiv LaTeX files with preambles, comments, macros, and bibliographies removed, totaling 28.0B tokens. These two corpora represent different approaches to processing arXiv content, allowing the researchers to test whether the ineffectiveness of arXiv is specific to a particular processing pipeline or is a more general phenomenon.

In the experiments, the 1.3B model is trained for 150B tokens on each arXiv corpus, while the 7B model is trained for 40B tokens on each corpus. The results are striking: when trained on an arXiv-only corpus, both models display no notable improvements or even deterioration across various mathematical benchmarks of different complexity levels. These benchmarks include quantitative reasoning datasets like GSM8K and MATH, multiple-choice challenges like MMLU-STEM, and formal mathematics like miniF2F. The lack of improvement is consistent across both model sizes and both arXiv corpora, strengthening the conclusion that the finding is robust and not an artifact of a specific experimental setup.

Several factors may explain why arXiv papers fail to improve mathematical reasoning. arXiv papers are primarily written for expert audiences and often focus on presenting novel results, theoretical frameworks, or surveys of existing work. The mathematical content in these papers is typically at a very advanced level, involving specialized notation and concepts that may be far removed from the kinds of problems encountered in standard mathematical reasoning benchmarks. Additionally, arXiv papers are not structured as problem-solving exercises; they present proofs and derivations in a narrative format that may not directly teach the model the step-by-step problem-solving patterns needed to solve benchmark problems. The distributional mismatch between the content of arXiv papers and the tasks used to evaluate mathematical reasoning may thus limit the transfer of learning.

The authors are appropriately cautious about the scope of their conclusion, noting several important limitations. First, they have not studied the impact of arXiv tokens on specific math-related tasks not included in their research, such as informalization of theorems—the task of converting formal statements or proofs to their informal versions. Such tasks may benefit from exposure to arXiv content in ways that standard benchmarks do not capture. Second, they have not thoroughly investigated the effect of arXiv tokens when combined with other types of data; it is possible that arXiv content, when mixed with other mathematical data sources, contributes in a complementary or synergistic manner that is not apparent when arXiv is used alone. Third, the benefits of arXiv papers may manifest at a larger model scale that has not been tested; a larger model might have the capacity to extract and internalize the advanced mathematical knowledge present in arXiv papers in ways that the 1.3B and 7B models cannot.

Despite these caveats, the finding has significant practical implications. Many existing math pre-training corpora include substantial portions of arXiv content. For example, MathPile, one of the corpora tested, consists of over 85\% arXiv papers. Proof-Pile-2, another widely used corpus, includes 28.0B tokens of arXiv papers. If arXiv content does not contribute to improved mathematical reasoning, then the resources devoted to collecting and processing this content may be better allocated to other data sources, such as the web-based mathematical content that forms the DeepSeekMath Corpus. The authors' finding that the DeepSeekMath Corpus—sourced from Common Crawl and filtered for mathematical content—significantly outperforms these arXiv-heavy corpora provides further support for this perspective.

The authors explicitly call for further exploration of this question, acknowledging that their conclusion should be taken with a grain of salt. The interplay between different data sources in pre-training is complex, and the optimal composition of pre-training data for mathematical reasoning likely depends on factors including model scale, the specific downstream tasks of interest, and the quality and processing of each data source. Nonetheless, the empirical evidence presented in the DeepSeekMath experiments represents a valuable contribution to the understanding of how different types of mathematical content contribute to the development of reasoning capabilities in language models.
