\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### Why is the model called "1.58 bits" when weights can take 3 values {-1, 0, 1}?
Question:
The paper introduces "BitNet b1.58" where every parameter is ternary, taking values in \{-1, 0, 1\}. The name suggests 1.58 bits per weight. I understand ternary values mean 3 possible states, and $\log_2(3) \approx 1.585$, so I assume this is where 1.58 comes from. But I'm confused: if each weight is stored as a ternary value, doesn't that still require 2 bits in practice (since you can't store 1.58 bits in hardware)? Is the 1.58 just a theoretical information-theoretic measure, or is there an actual encoding scheme that achieves this? And if it's theoretical, why not just call it a "ternary" or "2-bit" model?
Answer:
The "$1.58$ bits" in BitNet b$1.58$ is indeed an information-theoretic measure, not a claim about how the weights are literally stored in current hardware. As you correctly noted, it comes from $\log_2(3) \approx 1.585$, which is the minimum number of bits needed to encode one of three equally likely states. The naming convention follows from the original BitNet, which used binary weights $\{-1, 1\}$ and was called a "$1$-bit" model. When the authors added the value $0$ to get $\{-1, 0, 1\}$, the information content per weight went from $\log_2(2) = 1$ bit to $\log_2(3) \approx 1.58$ bits, hence "b$1.58$."

You are correct that on standard hardware, storing a single ternary value naively requires $2$ bits, since hardware addresses memory in byte-aligned chunks and you cannot store a fractional bit in isolation. The paper itself acknowledges this: they report latency and memory using a **$2$-bit kernel** and note there is "still room for optimization to further reduce the cost." So in their current implementation, each weight does occupy $2$ bits.

However, the $1.58$-bit figure is not purely academic. It reflects the **entropy** of the weight distribution—the actual information each weight carries. In practice, you can approach this theoretical limit by **packing** multiple ternary values together. For example, $5$ ternary values have $3^5 = 243$ possible combinations, which fit into $8$ bits (since $2^8 = 256$), yielding $8/5 = 1.6$ bits per weight. With larger block sizes, you can get arbitrarily close to $\log_2(3)$. This is why the authors argue the model "opens the door for designing specific hardware optimized for $1$-bit LLMs"—custom hardware could implement such packing schemes natively.

As for why not call it "ternary" or "$2$-bit": "ternary" would be descriptively accurate but would break continuity with the original "$1$-bit BitNet" naming and would not convey the efficiency story the paper is telling. "$2$-bit" would be misleading because $2$ bits can represent $4$ states, suggesting the model has more representational capacity per weight than it actually does. The name "$1.58$ bits" precisely communicates the information content while placing the model on the same "bits per weight" scale used throughout the $1$-bit LLM literature, making it easy to compare with the original $1$-bit BitNet and potential future variants.
