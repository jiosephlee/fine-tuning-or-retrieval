\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### Why is block quantization fused with rotary embedding at no extra cost?
Question:
In Section 3.3 of the FlashAttention-3 paper, they describe block quantization where each block of $\mathbf{Q}$, $\mathbf{K}$, $\mathbf{V}$ of size $B_r \times d$ or $B_c \times d$ gets its own scaling factor. They state that this "can be fused with an operation right before attention (e.g., rotary embedding) with no additional slow down (since rotary embedding is memory-bandwidth bound)."

I understand the concept of operator fusion, but I'm confused about why rotary embedding being memory-bandwidth bound means we can add quantization for free. Is the idea that since rotary embedding is already reading all the data from HBM, we can compute the per-block scaling factors and apply quantization during the same memory pass? Does this mean the rotary embedding + quantization kernel writes FP8 output directly, and the scaling factors are stored separately for FlashAttention-3 to use during its block-wise rescaling of $\mathbf{S}$?
Answer:
You're essentially correct in your understanding. The key insight is a straightforward consequence of the roofline model: when an operation is memory-bandwidth bound, the compute units are largely idle, so adding extra computation that doesn't require additional memory traffic comes "for free."

Rotary embedding operates element-wise on $\mathbf{Q}$ and $\mathbf{K}$, applying position-dependent rotations. This requires reading the full FP16 or BF16 tensors from HBM, performing a handful of multiply-adds per element, and writing the results back. The arithmetic intensity (FLOPs per byte of memory traffic) is very low, so the operation is bottlenecked by HBM bandwidth, not by compute throughput. The GPU's arithmetic units are mostly idle waiting for memory.

Block quantization requires computing one scaling factor per block (e.g., by taking the maximum absolute value within a $B_r \times d$ or $B_c \times d$ block) and then dividing each element by that factor to map into the FP8 range. This is also a lightweight computation — a reduction followed by element-wise division — that touches the same data already being read for rotary embedding. When fused, the kernel reads $\mathbf{Q}$ or $\mathbf{K}$ in FP16 from HBM, applies rotary embedding, computes the per-block scaling factor on the fly, scales and converts to FP8, and writes the FP8 result back to HBM along with the separately stored scaling factors. The memory traffic is actually the same or even reduced (since the output is FP8 at 1 byte per element rather than FP16 at 2 bytes), and the additional arithmetic for the reduction and scaling is negligible compared to the memory bottleneck. Hence there is no additional slowdown.

You are also correct that the scaling factors are stored separately for FlashAttention-3 to use during its block-wise rescaling of $\mathbf{S}$. The paper notes that since FlashAttention-3 "naturally operates on blocks," it can "scale each block of $\mathbf{S}$ to account for this block quantization at no computation cost." This works because if $\mathbf{Q}_i$ has scaling factor $s_{Q,i}$ and $\mathbf{K}_j$ has scaling factor $s_{K,j}$, then the true score block $\mathbf{Q}_i \mathbf{K}_j^\top$ equals the FP8-computed block multiplied by $s_{Q,i} \cdot s_{K,j}$. This rescaling is folded into the existing softmax rescaling logic that FlashAttention already performs per block, so it adds no extra cost to the attention kernel itself.

This principle — fusing quantization into a preceding memory-bound kernel — is a common pattern in low-precision ML systems. Any time you have a producer kernel that is memory-bound and already touching the data you need to quantize, you can fold the quantization in at no cost. The same reasoning applies to the incoherent processing step (multiplication by a Hadamard matrix), which the paper also notes can be fused with rotary embedding at no extra cost, since that multiplication is also compute-light relative to the memory bandwidth ceiling that rotary embedding already sits on.
