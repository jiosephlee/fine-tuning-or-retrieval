Chapter 7: Intra-Warpgroup Overlapping: 2-Stage GEMM-Softmax Pipelining

## Sequential Dependencies in the Attention Inner Loop

To understand why overlapping GEMM and softmax operations within a single warpgroup is challenging, we must first examine the inherent sequential dependencies that exist in the attention computation's inner loop. Recall from the FlashAttention algorithm that for each query tile $\mathbf{Q}_i$, the algorithm iterates over blocks of the key and value matrices, $\mathbf{K}_j$ and $\mathbf{V}_j$, performing two matrix multiplications (GEMMs) interleaved with a local softmax computation in each iteration $j$.

The first GEMM, which we call GEMM0, computes the attention scores $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^T$. This matrix product captures the similarity between the query tile and the current key tile. The output $\mathbf{S}_i^{(j)}$ is immediately consumed by the softmax operation, which must compute the row-wise maximum $m_i$, the exponentiated scores $\widetilde{\mathbf{P}}_i^{(j)} = \exp(\mathbf{S}_i^{(j)} - m_i)$, and the row sums $\ell_i$ needed for normalization. The softmax operation cannot begin until GEMM0 completes, because it needs the full matrix of scores to compute the row-wise statistics.

The second GEMM, which we call GEMM1, then computes the partial output update $\mathbf{O}_i = \mathrm{diag}(\exp(m_i^{\mathrm{old}} - m_i))^{-1} \mathbf{O}_i + \widetilde{\mathbf{P}}_i^{(j)} \mathbf{V}_j$. This operation takes the exponentiated and rescaled scores $\widetilde{\mathbf{P}}_i^{(j)}$ as its left operand and the value tile $\mathbf{V}_j$ as its right operand. Therefore, GEMM1 depends on the softmax computation, which in turn depends on GEMM0. This creates a chain of dependencies: GEMM0 $\rightarrow$ softmax $\rightarrow$ GEMM1, all within a single iteration of the inner loop.

In the baseline warp-specialized algorithm presented in Algorithm 1 of the paper, these dependencies are enforced by explicit "commit and wait" statements after each GEMM. Specifically, after computing $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^T$ on line 17, the algorithm commits and waits, meaning it blocks until the WGMMA instruction completes and the result is available in registers. Only then does the softmax computation proceed on lines 18 and 19. Similarly, after computing the output update on line 22, the algorithm again commits and waits, serializing the execution before the next iteration begins. These wait statements are the synchronization barriers that prevent any overlap between the GEMMs and the softmax within a single iteration, effectively forcing the three stages to execute one after another in lockstep.

The fundamental problem is that while the Tensor Cores are performing the matrix multiplication for GEMM0, the CUDA cores and multi-function units that handle the softmax computation sit idle. Conversely, while the softmax is being computed, the Tensor Cores sit idle. This is particularly wasteful given the stark throughput asymmetry between these hardware units: on the H100 SXM5 GPU, FP16 matrix multiply achieves 989 TFLOPS, while special function operations such as the exponential (needed for softmax) achieve only 3.9 TFLOPS. For attention with head dimension 128, the exponential operations have 256 times lower throughput than matmul, meaning they can consume up to 50% of the total cycle time despite representing far fewer floating-point operations. With FP8, the situation worsens because matmul throughput doubles while the exponential throughput remains unchanged.

## Breaking Dependencies Through Cross-Iteration Pipelining with Register Buffers

The key insight that enables intra-warpgroup overlapping is that while dependencies within a single iteration are unavoidable, one can break the serialization by pipelining across iterations. The idea is analogous to a factory assembly line: rather than waiting for a complete product to pass through all stations before starting the next one, multiple products are in various stages of completion simultaneously. In the context of the attention algorithm, this means that while iteration $j$ is performing its softmax computation, the GEMMs of iteration $j+1$ can be initiated concurrently, provided we maintain separate buffers to hold the intermediate results of each stage.

To implement this cross-iteration pipelining, the algorithm introduces additional register buffers to hold the intermediate scores matrix for the "next" iteration while the "current" iteration's softmax and GEMM1 are still in progress. Specifically, instead of maintaining a single buffer $\mathbf{S}_{\mathrm{cur}}$ for the attention scores, we introduce a second buffer $\mathbf{S}_{\mathrm{next}}$. When the first GEMM of iteration $j+1$ computes $\mathbf{S}_{\mathrm{next}} = \mathbf{Q}_i \mathbf{K}_{j}^T$, it writes its output to this separate buffer, which does not conflict with the softmax computation that is operating on $\mathbf{S}_{\mathrm{cur}}$ from iteration $j$. Similarly, the exponentiated scores $\widetilde{\mathbf{P}}_{\mathrm{cur}}$ and $\widetilde{\mathbf{P}}_{\mathrm{next}}$ are kept in separate register buffers.

The critical enabler for this scheme is the asynchronous nature of the WGMMA instruction on Hopper GPUs. Unlike earlier architectures where matrix multiply instructions were synchronous, the WGMMA instruction on Hopper can be issued and then left to complete in the background. The algorithm can issue a WGMMA, commit it (signaling that the instruction has been launched), but deliberately choose not to wait for its completion. This allows the warpgroup to proceed with other work — specifically, the softmax computation — while the Tensor Cores are still performing the matrix multiplication. Only later, when the result is actually needed, does the algorithm issue a wait to ensure the WGMMA has completed.

By maintaining two sets of buffers — one for the "current" iteration and one for the "next" iteration — the algorithm creates a two-stage pipeline where the GEMM1 of iteration $j$ overlaps with the softmax of iteration $j+1$, and the GEMM0 of iteration $j+1$ overlaps with the GEMM1 and softmax of iteration $j$. This pipelining across iterations is what breaks the sequential dependency chain that would otherwise force each iteration to complete fully before the next one begins.

## The 2-Stage Algorithm: Overlapping GEMM1 of Iteration $j$ with Softmax of Iteration $j+1$

The two-stage GEMM-softmax pipelining algorithm replaces the consumer mainloop of the warp-specialized algorithm with an overlapped version. To understand its structure, let us trace through the execution flow of Algorithm 2 from the paper.

The algorithm begins with a prologue that handles the zeroth iteration without overlap, establishing the initial state. It first waits for $\mathbf{Q}_i$ and $\mathbf{K}_0$ to be loaded into shared memory, then computes $\mathbf{S}_{\mathrm{cur}} = \mathbf{Q}_i \mathbf{K}_0^T$ using WGMMA. After committing and waiting for this first GEMM to complete, it releases the shared memory buffer stage used for $\mathbf{K}_0$ and proceeds to compute the initial softmax statistics: the row-wise maximum $m_i$, the exponentiated scores $\widetilde{\mathbf{P}}_{\mathrm{cur}}$, and the normalization accumulator $\ell_i$, based on $\mathbf{S}_{\mathrm{cur}}$. It also rescales the output accumulator $\mathbf{O}_i$ accordingly.

The main loop then runs from $j = 1$ to $j = T_c - 2$, where $T_c$ is the number of key/value blocks. In each iteration $j$, the algorithm performs the following steps in a carefully orchestrated sequence. First, it waits for $\mathbf{K}_j$ to be loaded into shared memory. Then it issues the first WGMMA to compute $\mathbf{S}_{\mathrm{next}} = \mathbf{Q}_i \mathbf{K}_j^T$ and commits it but does not wait for completion. This is the crucial "fire and forget" step that allows the Tensor Cores to begin working on the next iteration's GEMM0 while the warpgroup moves on to other work.

Next, the algorithm waits for $\mathbf{V}_{j-1}$ to be loaded into shared memory and issues the second WGMMA to compute $\mathbf{O}_i = \mathbf{O}_i + \widetilde{\mathbf{P}}_{\mathrm{cur}} \mathbf{V}_{j-1}$. Again, it commits but does not wait. At this point, both the GEMM0 of iteration $j$ and the GEMM1 of iteration $j-1$ are executing asynchronously on the Tensor Cores. The algorithm then waits specifically for the GEMM0 of iteration $j$ (the $\mathbf{Q}_i \mathbf{K}_j^T$ computation) to complete, so that $\mathbf{S}_{\mathrm{next}}$ is available in registers. It then performs the softmax computation on $\mathbf{S}_{\mathrm{next}}$, computing the updated $m_i$, $\widetilde{\mathbf{P}}_{\mathrm{next}}$, and $\ell_i$. During this softmax computation, the GEMM1 of iteration $j-1$ (the $\widetilde{\mathbf{P}}_{\mathrm{cur}} \mathbf{V}_{j-1}$ computation) is still running on the Tensor Cores, thus achieving the desired overlap.

After the softmax completes, the algorithm waits for the GEMM1 of iteration $j-1$ to finish, rescales $\mathbf{O}_i$ to account for the updated running maximum $m_i$, and releases the shared memory buffer stages for both $\mathbf{K}_j$ and $\mathbf{V}_{j-1}$. Finally, it copies $\mathbf{S}_{\mathrm{next}}$ to $\mathbf{S}_{\mathrm{cur}}$ and $\widetilde{\mathbf{P}}_{\mathrm{next}}$ to $\widetilde{\mathbf{P}}_{\mathrm{cur}}$, effectively advancing the pipeline by one iteration. The loop then repeats with the roles of "current" and "next" swapped.

After the main loop completes, the algorithm handles the final iteration as an epilogue. It waits for the last value tile $\mathbf{V}_{T_c - 1}$ to be loaded, computes the final output update $\mathbf{O}_i = \mathbf{O}_i + \widetilde{\mathbf{P}}_{\mathrm{last}} \mathbf{V}_{T_c - 1}$ using WGMMA, and commits and waits for completion. It then performs the final rescaling of $\mathbf{O}_i$ based on the accumulated maximum $m_i$, computes the log-sum-exp $L_i = m_i + \log(\ell_i)$, and writes both $\mathbf{O}_i$ and $L_i$ to HBM.

## Detailed Pseudocode for the Consumer Warpgroup Forward Pass

The full pseudocode for the two-stage pipelined consumer warpgroup forward pass is presented as Algorithm 2 in the paper. It serves as a drop-in replacement for the consumer path of the warp-specialized algorithm (Algorithm 1), with the producer warpgroup handling TMA loads remaining unchanged. Together, the producer-consumer warp-specialization and the two-stage intra-warpgroup pipelining comprise the complete FlashAttention-3 algorithm for FP16 precision.

The algorithm assumes that the matrices $\mathbf{Q}_i \in \mathbb{R}^{B_r \times d}$ and $\mathbf{K}, \mathbf{V} \in \mathbb{R}^{N \times d}$ are in HBM, with key block size $B_c$ yielding $T_c = \lceil \frac{N}{B_c} \rceil$ blocks. The consumer warpgroup begins by reallocating a predetermined number of registers based on the number of consumer warps, using the \texttt{setmaxnreg} instruction on Hopper. This register reallocation is important because the consumer warpgroup, which performs the WGMMA instructions, benefits from having a larger share of the register file than the producer warpgroup, which only needs enough registers to issue TMA loads.

The on-chip state is initialized as $\mathbf{O}_i = (0) \in \mathbb{R}^{B_r \times d}$, $\ell_i = (0) \in \mathbb{R}^{B_r}$, and $m_i = (-\infty) \in \mathbb{R}^{B_r}$. The zeroth iteration is then handled as a prologue: waiting for $\mathbf{Q}_i$ and $\mathbf{K}_0$ in shared memory, computing $\mathbf{S}_{\mathrm{cur}} = \mathbf{Q}_i \mathbf{K}_0^T$ via WGMMA (commit and wait), releasing the buffer stage for $\mathbf{K}$, and computing the initial softmax statistics from $\mathbf{S}_{\mathrm{cur}}$ while rescaling $\mathbf{O}_i$.

The main loop (lines 8 through 20 in the algorithm) executes the overlapped pipeline as described in the previous section. The key lines to understand are lines 9 and 11, where the WGMMA instructions are issued with "commit but do not wait" semantics. Line 9 computes $\mathbf{S}_{\mathrm{next}} = \mathbf{Q}_i \mathbf{K}_j^T$ and commits without waiting, launching the GEMM0 for iteration $j$ asynchronously. Line 11 computes $\mathbf{O}_i = \mathbf{O}_i + \widetilde{\mathbf{P}}_{\mathrm{cur}} \mathbf{V}_{j-1}$ and also commits without waiting, launching the GEMM1 for iteration $j-1$ asynchronously. Between these two commits and their corresponding waits, the softmax computation on line 13 executes, achieving the overlap between non-GEMM and GEMM operations.

## Role of Asynchronous WGMMA: Commit Without Wait to Enable Overlap

The asynchronous nature of the WGMMA instruction on Hopper GPUs is the technological foundation that makes the two-stage pipeline possible. To understand why, consider what would happen if WGMMA were synchronous, as the matrix multiply instructions were on earlier architectures such as Ampere. With a synchronous instruction, each GEMM would block the issuing warp until the result is ready in registers. The algorithm would have no choice but to execute GEMM0, then softmax, then GEMM1 in strict sequence, exactly as in the baseline warp-specialized algorithm. There would be no opportunity to overlap the Tensor Core computation with the CUDA core computation, because the warp issuing the GEMM would be stalled until the GEMM completes.

The WGMMA instruction on Hopper, however, is designed for asynchronous execution. When a warpgroup issues a WGMMA instruction, the instruction is dispatched to the Tensor Cores, and control returns to the warpgroup immediately. The Tensor Cores then execute the matrix multiply in the background while the warpgroup is free to perform other work. The "commit" operation signals that the WGMMA has been properly launched and its input operands are committed, but it does not block. The "wait" operation, issued later, is what blocks the warpgroup until the Tensor Cores have finished the computation and the result is available in the register file.

This asynchronous dispatch model is what allows the two-stage algorithm to issue two WGMMA instructions back-to-back without waiting for either to complete, and then proceed to perform the softmax computation on the CUDA cores while both GEMMs are executing on the Tensor Cores. The algorithm only waits when the result of a particular GEMM is actually needed — for example, when the softmax needs the scores matrix $\mathbf{S}_{\mathrm{next}}$, it waits for the GEMM0 that produces it. By carefully ordering the commits, waits, and non-GEMM operations, the algorithm ensures that the Tensor Cores are kept busy with GEMMs while the CUDA cores simultaneously handle the softmax computation, maximizing the utilization of both hardware units.

It is worth noting that the term "WGMMA" in the algorithm pseudocode serves as a metonym for asynchronous GEMM more generally. While the specific implementation targets the Hopper architecture's WGMMA instruction, the algorithmic principle of using asynchronous matrix multiply to overlap with non-matmul computation is operative for any GPU architecture with sufficiently robust asynchronous execution capabilities.

## Practical Consideration 1: Compiler Reordering and SASS Verification

The pseudocode in Algorithm 2 represents an idealized execution order that achieves the maximum possible overlap between GEMM and softmax operations. However, in practice, the compiler (NVCC, NVIDIA's CUDA compiler) may rearrange instructions for optimization purposes, potentially disrupting the carefully crafted pipeline sequence. The compiler's instruction scheduling passes analyze dependencies between instructions and may reorder them to improve register usage, reduce stalls, or take advantage of instruction-level parallelism. While this is generally beneficial for ordinary code, it can be problematic for algorithms like the two-stage pipeline where the ordering of WGMMA commits, waits, and non-GEMM operations is precisely tuned for a specific overlap pattern.

For example, the compiler might decide to move a wait instruction earlier, collapsing the window during which the softmax can overlap with the GEMM, or it might reorder register operations in a way that inadvertently introduces a dependency that serializes the pipeline. Such reordering could lead to unexpected behavior or diminished performance gains, as the carefully constructed overlap between Tensor Core and CUDA core computation is broken.

To verify that the compiler actually generates the expected overlapped code, the authors analyze the SASS (Source Assembly) code — the low-level assembly that NVCC produces after all optimization passes. The SASS analysis, presented in Section 3.2 of the paper, confirms that the compiler generates overlapped code as intended, with WGMMA and non-WGMMA instructions interleaved in the pattern prescribed by the algorithm. This verification is important because it demonstrates that the theoretical pipeline structure is preserved through the compilation process and that the expected performance gains are realized in practice.

## Practical Consideration 2: Register Pressure from Extra $\mathbf{S}_{\mathrm{next}}$ Buffer

The two-stage pipeline requires additional register storage to maintain the intermediate results needed for cross-iteration overlap. Specifically, the algorithm must keep an extra copy of the scores matrix, $\mathbf{S}_{\mathrm{next}}$, in registers while the current iteration's softmax and GEMM1 are still in progress. This extra buffer occupies $B_r \times B_c \times \text{sizeof}(\text{float})$ bytes per threadblock, where $B_r$ is the query block size (number of rows in the query tile) and $B_c$ is the key block size (number of rows in the key tile). Since each score entry is stored as a 32-bit float (FP32), the additional register demand can be substantial, especially for larger block sizes.

Register pressure is a critical concern in GPU kernel design because each streaming multiprocessor has a limited register file. On Hopper, each thread can access at most 256 registers, and the total register file is shared among all threads running on the SM. When a kernel uses more registers per thread, fewer threads can be co-scheduled on the same SM, reducing the occupancy and potentially hurting the kernel's ability to hide memory and instruction latencies. If the register demand exceeds the available capacity, the compiler will spill registers to local memory (which resides in slow global memory), severely degrading performance.

The additional $\mathbf{S}_{\mathrm{next}}$ buffer creates a tension between the pipeline depth and the block size. Larger block sizes for $B_r$ and $B_c$ are generally desirable because they increase the ratio of useful computation to overhead (such as softmax statistics and boundary handling) and improve the efficiency of the Tensor Cores. However, larger blocks also require more registers for both the GEMM operands and the pipeline buffers. The two-stage pipeline's extra $\mathbf{S}_{\mathrm{next}}$ buffer exacerbates this tension, as it directly increases register usage in proportion to the block sizes.

In practice, the authors note that trade-offs must be made based on profiling results. The optimal block size and pipeline depth depend on the specific GPU architecture, the head dimension, and the sequence length. The \texttt{setmaxnreg} instruction on Hopper, which dynamically reallocates registers between warpgroups, provides some flexibility in managing this tension, as the consumer warpgroup can be given a larger share of the register file at the expense of the producer warpgroup. Nonetheless, careful tuning is required to ensure that register spilling is minimized while maintaining sufficient block sizes for Tensor Core efficiency.

## Practical Consideration 3: 3-Stage Pipelining Extension and Its Trade-offs

The two-stage pipeline described above overlaps the GEMM1 of one iteration with the softmax of the next. A natural question is whether the overlap can be extended further to hide even more of the softmax computation behind GEMMs. The authors propose a three-stage variant that would additionally overlap the second GEMM with the softmax from a subsequent iteration, creating a deeper pipeline with more concurrent operations.

In the three-stage pipeline, additional register buffers are needed to hold intermediate results for yet another iteration ahead. While the two-stage pipeline maintains buffers for $\mathbf{S}_{\mathrm{cur}}$ and $\mathbf{S}_{\mathrm{next}}$, the three-stage pipeline would require a third buffer, say $\mathbf{S}_{\mathrm{next2}}$, to hold the scores for the iteration after next. This further increases the register pressure discussed in the previous section, making the trade-off between tile size and pipeline depth even more difficult to balance.

The potential benefit of the three-stage pipeline is higher Tensor Core utilization, as more of the softmax computation can be hidden behind the GEMMs. However, the authors note that this comes at the cost of significantly more register usage, which may force smaller block sizes and thus reduce the efficiency of each individual GEMM. The net performance effect depends on whether the increased overlap outweighs the reduced GEMM efficiency from smaller blocks. The authors provide a detailed description of the three-stage algorithm and its evaluation results in Section B.2 of the appendix, indicating that the three-stage approach is feasible but requires careful tuning to achieve net gains.

The authors also note that the number of stages in the overlapping scheme is bounded by, but need not equal, the number $s$ of stages in the circular shared memory buffer. The circular buffer is used by the producer warpgroup to pipeline TMA loads of $\mathbf{K}$ and $\mathbf{V}$ blocks, and its depth $s$ determines how many loads can be in flight simultaneously. The GEMM-softmax pipeline stages operate on data that has already been loaded into shared memory, so the pipeline depth is constrained by the availability of loaded data but is otherwise independent of $s$. This separation of concerns — the shared memory buffer managed by the producer and the register pipeline managed by the consumer — is a key design principle that allows each aspect of the algorithm to be tuned independently.

In summary, the two-stage GEMM-softmax pipelining represents a careful balance between the performance gains from overlapping computation and the resource costs of maintaining additional pipeline stages. The three-stage extension pushes this balance further, offering the potential for higher Tensor Core utilization at the expense of increased register pressure, and its viability depends on the specific hardware configuration and workload characteristics.
