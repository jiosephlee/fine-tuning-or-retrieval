\title{A Textbook about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

Chapter 3: GPU Hardware Architecture and Execution Model

Modern deep learning workloads place extraordinary demands on the hardware that executes them. The attention mechanism at the heart of the Transformer architecture is perhaps the most striking example: computing self-attention scores requires matrix multiplications whose cost scales quadratically with the sequence length, making attention the primary computational bottleneck in large language models and long-context applications. To accelerate such workloads, GPU designers have increasingly relied on hardware specialization—dedicated silicon for specific operations like matrix multiplication and memory movement—and on lower-precision arithmetic formats that deliver higher throughput for the same power and chip area. Understanding these hardware features is essential for designing algorithms like FlashAttention-3 that extract maximum performance from modern GPUs.

This chapter explains the hardware characteristics of the NVIDIA Hopper architecture (exemplified by the H100 GPU) that FlashAttention-3 exploits. We focus on four broad themes: the organization of GPU memory into a hierarchy of data locales, the organization of GPU execution into a hierarchy of thread groups, the asynchronous execution capabilities that allow computation and data movement to overlap, and the low-precision number formats that dramatically increase throughput. Throughout, we connect these hardware features to the algorithmic decisions made in FlashAttention-3.

# Memory Hierarchy: Global Memory, L2 Cache, Shared Memory, and Register File

A GPU's memory system is organized as a hierarchy of storage locations, or "locales," with a fundamental trade-off between capacity and bandwidth: the larger the storage, the lower its bandwidth. At the top of this hierarchy sits global memory (GMEM), also known as HBM (High Bandwidth Memory). This is the off-chip dynamic random-access memory (DRAM) that is accessible to all streaming multiprocessors (SMs) on the GPU. On the H100, HBM provides the largest storage capacity—80 gigabytes on the SXM5 variant—but has the lowest bandwidth relative to the on-chip memories. All input tensors, such as the query matrix $\mathbf{Q}$, key matrix $\mathbf{K}$, and value matrix $\mathbf{V}$, initially reside in HBM. When a standard attention implementation materializes the intermediate score matrix $\mathbf{S} = \alpha \mathbf{Q} \mathbf{K}^\top$ and the probability matrix $\mathbf{P} = \mathrm{softmax}(\mathbf{S})$, these large $N \times N$ matrices are written to and read from HBM, which is precisely the bottleneck that FlashAttention was designed to eliminate.

Data loaded from HBM passes transparently through an on-chip L2 cache, which sits between HBM and the SMs. The L2 cache is a hardware-managed cache, meaning the programmer does not have explicit control over what resides there, but it helps reduce the effective latency and bandwidth cost of repeated accesses to the same data in HBM.

Within each SM, there is a small, on-chip, programmer-managed, highly banked cache called shared memory (SMEM). Shared memory is much faster than HBM but far smaller in capacity. The programmer has fine-grained control over what data resides in SMEM and when it is loaded or evicted, which makes it a critical resource for performance optimization. In FlashAttention-3, tiles of the query, key, and value matrices are loaded from HBM into shared memory, where they serve as operands for matrix multiply-accumulate operations. The circular shared memory buffer with multiple stages, used in the warp-specialized pipelining scheme, is a prime example of how careful management of SMEM can hide memory latency.

Finally, at the finest level of the memory hierarchy, each SM contains a register file (RMEM). Each thread has access to at most 256 registers that are private to itself. Registers are the fastest storage on the GPU but also the most limited in capacity. Matrix multiply-accumulate instructions on Hopper accumulate their results in registers, and intermediate values such as the running maximum $m_i$ and running sum $\ell_i$ in the FlashAttention-3 softmax computation are also held in registers. The tension between wanting to hold more data in registers for pipelining and the limited register capacity per thread is a recurring theme in the algorithm's design. For instance, the two-stage GEMM-softmax pipelining in FlashAttention-3 requires an additional $\mathbf{S}_{\mathrm{next}}$ matrix to be kept in registers, consuming $B_r \times B_c \times \text{sizeof}(\text{float})$ bytes per threadblock, which can conflict with the desire to use larger tile sizes.

# Thread Hierarchy: Threads, Warps, Warpgroups, CTAs, Clusters, and Grids

The GPU's programming model is organized around a hierarchy of logical execution units. From the finest to the coarsest level, this hierarchy consists of threads, warps, warpgroups, threadblocks (also called cooperative thread arrays or CTAs), threadblock clusters, and grids.

A thread is the smallest unit of execution on a GPU. Individual threads execute the same program (a "kernel") but can take different paths through the code based on their thread index and other data. Threads are grouped into warps, each consisting of 32 threads that execute instructions in lockstep on a single SM. The warp is the fundamental scheduling unit on an NVIDIA GPU: when an SM selects work to execute, it schedules entire warps, and all threads in a warp execute the same instruction at the same time (though some threads may be inactive if their branch diverges).

On the Hopper architecture, warps are further grouped into warpgroups, which consist of 4 contiguous warps (128 threads). The warpgroup is an important organizational unit for FlashAttention-3 because the key computational instruction—the warpgroup-wide matrix multiply-accumulate (WGMMA) instruction—operates at the warpgroup level. When FlashAttention-3 divides the warps of a CTA into producer and consumer roles, it assigns these roles at the warpgroup granularity.

A threadblock, or cooperative thread array (CTA), is a group of threads that are co-scheduled on the same SM. All threads within a CTA can communicate through shared memory and synchronize their execution through barrier instructions. The CTA is the unit by which work is distributed across SMs: when a kernel is launched, the GPU scheduler assigns CTAs to SMs, and each CTA executes independently (or semi-independently, in the case of clusters) on its assigned SM. In FlashAttention-3, each CTA is responsible for computing a tile $\mathbf{O}_i$ of the output matrix from a tile $\mathbf{Q}_i$ of the query matrix, iterating over all tiles of $\mathbf{K}$ and $\mathbf{V}$.

Hopper introduces threadblock clusters, which are groups of CTAs co-scheduled on the same graphics processing cluster (GPC—a group of SMs). CTAs within the same cluster can communicate through distributed shared memory, enabling collective operations across CTAs. At the coarsest level, a grid encompasses all CTAs launched for a given kernel. The grid is the complete set of work to be done and is mapped onto the GPU's SMs by the hardware scheduler.

# Relationship Between Memory and Thread Hierarchies

The memory and thread hierarchies are closely interlinked, and understanding their relationship is essential for grasping how FlashAttention-3 achieves its performance. The key principle is that access to each level of the memory hierarchy is governed by the thread's position in the thread hierarchy.

Threads within the same CTA are co-scheduled on the same SM and therefore share access to that SM's shared memory. This means that all warps and warpgroups within a CTA can read from and write to the same SMEM, enabling them to collaborate on shared data. In FlashAttention-3, the producer warpgroup loads tiles of $\mathbf{K}$ and $\mathbf{V}$ from HBM into shared memory using TMA instructions, and the consumer warpgroups then read these tiles from shared memory to use as operands for WGMMA matrix multiplications. The circular SMEM buffer with multiple stages allows the producer to load data for the next iteration while the consumer processes data from the current iteration, creating a pipeline that hides memory latency.

In contrast to shared memory, each thread's registers are private to that thread. No other thread can directly access a thread's register file. This means that when a warp or warpgroup needs to share data held in registers, it must use explicit shuffle or permute instructions to move values between threads. FlashAttention-3 encounters this challenge when dealing with FP8 WGMMA: the layout of the FP32 accumulator in registers differs from the layout expected for the operand of the next FP8 WGMMA, requiring byte permute instructions to rearrange the register contents.

CTAs within the same cluster, being co-scheduled on the same GPC, can access each other's shared memory through the distributed shared memory mechanism. This allows for collaboration at a finer granularity than would otherwise be possible across SM boundaries. At the broadest level, all CTAs in a grid share access to global memory (HBM), but with the highest latency and lowest bandwidth in the hierarchy.

# Asynchrony on Hopper: Tensor Memory Accelerator (TMA)

GPUs are throughput processors: rather than trying to minimize the latency of any single operation, they achieve high performance by keeping many operations in flight simultaneously. This is accomplished through concurrency and asynchrony, which allow the GPU to hide memory access latencies and execution latencies by overlapping different types of work.

A critical enabler of asynchrony on the Hopper architecture is the Tensor Memory Accelerator (TMA), a dedicated hardware unit for asynchronous memory copies between global memory (HBM) and shared memory (SMEM). On prior architectures like Ampere, memory copies between HBM and SMEM were issued by individual threads, which tied up valuable computational resources and made it difficult to fully overlap data movement with computation. The TMA, by contrast, is a specialized unit that can issue bulk memory transfers without occupying the CUDA cores.

The key advantage of TMA is that issuing a TMA load does not stall the issuing thread or warp on the completion of other loads or computations. The TMA operates asynchronously: once a load is issued, the requesting warp can continue executing other instructions while the hardware handles the data transfer in the background. When the data has arrived in shared memory, a synchronization mechanism (such as a barrier with the \texttt{commit} and \texttt{wait} operations shown in the FlashAttention-3 pseudocode) notifies the consumer that the data is ready.

In FlashAttention-3, the producer warpgroup uses TMA to load tiles of $\mathbf{Q}_i$, $\mathbf{K}_j$, and $\mathbf{V}_j$ from HBM into the circular SMEM buffer. Because TMA loads are asynchronous, the producer can issue multiple loads without waiting for earlier ones to complete, which is essential for building up a pipeline of data in the multi-stage circular buffer. For example, in the first $s$ iterations of the producer mainloop (where $s$ is the number of stages in the buffer), no waits are issued at all because the buffer is still being filled. This ability to overlap data movement with computation is one of the three main techniques that FlashAttention-3 uses to achieve its dramatic speedup.

# Asynchronous Tensor Cores: WGMMA Instruction and Its Execution Model

The second major source of asynchrony on Hopper is the asynchronous execution of matrix multiply-accumulate operations on the Tensor Cores. On prior architectures, the instruction for executing matrix multiplications on Tensor Cores (known as MMA) was synchronous from the perspective of the warp that issued it: the warp would wait for the MMA to complete before proceeding to the next instruction. On Hopper, the warpgroup-wide matrix multiply-accumulate instruction (WGMMA) is asynchronous.

WGMMA is issued at the warpgroup level (4 warps, 128 threads) and can source its input operands directly from shared memory, unlike the Ampere MMA instruction which required operands to be loaded into registers first. Once a WGMMA is issued, the warpgroup can continue executing other instructions—particularly non-matmul operations such as the floating-point multiply-add and exponential functions needed for softmax—while the Tensor Cores perform the matrix multiplication in the background. The warpgroup later issues a \texttt{wait} instruction to ensure that the WGMMA result is available in the accumulator registers before using it.

This asynchrony is the key enabler of the intra-warpgroup GEMM-softmax overlapping technique in FlashAttention-3. In the two-stage pipelining algorithm, the consumer warpgroup issues a WGMMA to compute $\mathbf{S}_{\mathrm{next}} = \mathbf{Q}_i \mathbf{K}_j^\top$ but does not immediately wait for it to complete. Instead, it proceeds to issue the second WGMMA for $\mathbf{O}_i = \mathbf{O}_i + \tilde{\mathbf{P}}_{\mathrm{cur}} \mathbf{V}_{j-1}$ and then performs the softmax computation on $\mathbf{S}_{\mathrm{next}}$ from the previous iteration. Only after the softmax is complete does it wait for the first WGMMA to finish. This overlaps the low-throughput non-GEMM operations (softmax) with the high-throughput GEMM operations, significantly improving Tensor Core utilization.

The performance motivation for this overlap is stark: on the H100 SXM5 GPU, FP16 matmul achieves 989 TFLOPs/s, while special functions such as the exponential (necessary for softmax) achieve only 3.9 TFLOPs/s. For attention with head dimension 128, there are 512x more matmul FLOPs than exponential operations, but the exponential has 256x lower throughput, meaning that exponential can take up to 50% of the cycles compared to matmul. Without overlapping these operations, the Tensor Cores would sit idle while the multi-function units compute the exponential, wasting a significant fraction of the GPU's computational capacity.

# Warp-Specialization: Producer-Consumer Model and Register Reallocation

Hopper's support for asynchronous TMA and WGMMA enables a programming model called warp-specialization, in which the warps within a CTA are divided into producer and consumer roles. Producer warps are responsible for data movement—they issue TMA loads to bring data from HBM into shared memory. Consumer warps are responsible for computation—they issue WGMMA instructions and perform the softmax and other arithmetic. By separating these roles, the compiler can more easily generate optimal instruction schedules, because each warp's instruction stream is homogeneous (either all data movement or all computation).

In FlashAttention-3, a CTA typically contains two warpgroups: one producer warpgroup and one consumer warpgroup (or two consumer warpgroups, as in the pingpong scheduling scheme). The producer warpgroup issues TMA loads for $\mathbf{Q}_i$, $\mathbf{K}_j$, and $\mathbf{V}_j$, commits to notify the consumer that the data is ready, and waits for the consumer to release a stage of the circular buffer before overwriting it. The consumer warpgroup waits for data to arrive in shared memory, performs the GEMMs and softmax, and releases the buffer stage when it is done with the data.

A complementary feature of Hopper that supports warp-specialization is the ability to dynamically reallocate registers between warpgroups using the \texttt{setmaxnreg} instruction. Since the producer warpgroup only needs to issue TMA loads (which requires only a single thread), it does not need many registers. The consumer warpgroup, on the other hand, needs registers to hold the WGMMA accumulators, intermediate softmax values, and pipeline buffers. By deallocating registers from the producer and reallocating them to the consumer, the algorithm ensures that the consumer has enough register capacity to maintain the multi-stage pipeline without spilling to shared memory, which would degrade performance.

In the FlashAttention-3 pseudocode, the producer warpgroup deallocates a predetermined number of registers at the start, while the consumer warpgroup reallocates registers as a function of the number of consumer warps. This dynamic allocation is particularly important for the two-stage and three-stage pipelining schemes, which require additional registers to hold extra blocks of the score matrix $\mathbf{S}$.

Warp-specialization also enables the pingpong scheduling scheme, in which two consumer warpgroups alternate between doing GEMMs and doing softmax. Synchronization barriers (\texttt{bar.sync} instructions) are used to force the GEMMs of warpgroup 1 to be scheduled before the GEMMs of warpgroup 2, so that the softmax of warpgroup 1 is scheduled while warpgroup 2 is performing its GEMMs, and vice versa. This creates a "pingpong" pattern that keeps both the Tensor Cores and the multi-function units busy, improving performance from 570 TFLOPs/s to 620-640 TFLOPs/s in one benchmark configuration.

# Low-Precision Number Formats: FP16, BF16, FP8, and Throughput Benefits

A major trend in GPU hardware design is the introduction of progressively lower-precision number formats, each offering higher throughput for the same power and chip area. This trend began with FP16 (half-precision floating point) on the Pascal architecture in 2017, continued with BF16 (bfloat16) on Ampere in 2020, and reached FP8 on Hopper and FP4 on Blackwell.

On the H100 GPU, the WGMMA instruction can target FP8 Tensor Cores to deliver 2x the throughput per SM compared to FP16 or BF16. This means that for the same hardware resources, the GPU can perform twice as many floating-point operations per second when using FP8 instead of FP16. For attention, which is dominated by matrix multiplications, this translates directly to a potential doubling of throughput: FlashAttention-3 in FP8 reaches close to 1.2 PFLOPs/s, compared to 740 TFLOPs/s for FP16.

The FP8 format used on Hopper is e4m3, which allocates 4 bits for the exponent and 3 bits for the mantissa (plus a sign bit). This gives a total of 8 bits per value, compared to 16 bits for FP16 or BF16. The reduced mantissa precision means that FP8 can represent fewer significant digits, leading to higher numerical error. Moreover, large language models typically have outlier values—features or activations that are much larger in magnitude than most other values—which make quantization to FP8 particularly challenging, as a single scaling factor may not adequately represent the full dynamic range of the data.

Despite these accuracy challenges, the throughput benefits of FP8 are so compelling that FlashAttention-3 invests significant effort in adapting the algorithm to use FP8 Tensor Cores. The key insight is that the accuracy loss can be mitigated through algorithmic techniques—block quantization and incoherent processing—while the throughput benefits are a pure hardware advantage. The result is that FP8 FlashAttention-3 achieves 2.6x lower numerical error than a baseline FP8 attention implementation using per-tensor quantization, while approaching the theoretical peak throughput of the FP8 Tensor Cores.

# FP8 WGMMA Layout Constraints: K-Major Requirement and Accumulator Layout Differences

While FP8 offers compelling throughput benefits, using it effectively requires navigating a set of layout constraints imposed by the FP8 WGMMA instruction. These constraints are more restrictive than those for FP16 WGMMA and have significant implications for the design of the attention algorithm.

To understand these constraints, we first need to define the concept of matrix layout in the context of WGMMA. Given a GEMM call to multiply $A \times B^\top$ for an $M \times K$-matrix $A$ and an $N \times K$-matrix $B$, we say that the $A$ or $B$ operand is "mn-major" if it is contiguous in the outer $M$ or $N$ dimension, and "k-major" if it is contiguous in the inner $K$-dimension. Contiguity here refers to the memory layout: in a k-major matrix, elements that differ only in the $K$-dimension are adjacent in memory, while in an mn-major matrix, elements that differ only in the $M$ or $N$-dimension are adjacent.

For FP16 WGMMA, both mn-major and k-major input operands are accepted for operands in shared memory. This flexibility means that the input tensors $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$, which are typically given as contiguous in the head dimension $d$ (which corresponds to the $K$-dimension for the first GEMM $\mathbf{Q}\mathbf{K}^\top$), can be used directly without any layout transformation. However, for FP8 WGMMA, only the k-major format is supported. This means that for the second GEMM $\mathbf{P}\mathbf{V}$, where $\mathbf{V}$ serves as the $B$ operand with $K = d$, the tiles of $\mathbf{V}$ loaded into shared memory must be contiguous in the sequence length dimension $N$ (the $M$-dimension of $\mathbf{V}$ in the GEMM). Since the input $\mathbf{V}$ is typically stored as contiguous in the head dimension, and TMA loads cannot change the contiguous dimension, a layout transformation is needed.

FlashAttention-3 addresses this by performing an in-kernel transpose of $\mathbf{V}$ tiles after loading them into shared memory. This transpose is implemented using the LDSM (\texttt{ldmatrix}) and STSM (\texttt{stmatrix}) instructions, which allow a warp of threads to collectively load data from SMEM to RMEM and store it back to SMEM at a granularity of 128 bytes. These instructions are register-efficient and can be executed in the producer warpgroup, and they are capable of transposing layouts during the memory copy. By arranging for the transpose of the next $\mathbf{V}$ tile to execute in the "shadow" of the WGMMAs that process the preceding $\mathbf{V}$ and current $\mathbf{K}$ tiles, the transpose overhead is effectively hidden.

A second layout challenge arises from the difference between the memory layout of the FP32 accumulator of an FP8 WGMMA and the layout assumed for its operand $A$ when held in registers. When two GEMMs are fused back-to-back in a single kernel—as in attention, where $\mathbf{S} = \mathbf{Q}\mathbf{K}^\top$ is computed first and then $\mathbf{O} = \mathbf{P}\mathbf{V}$ uses $\mathbf{P} = \mathrm{softmax}(\mathbf{S})$ as its $A$ operand—the output of the first WGMMA (the accumulator) must be transformed into a format suitable as input to the second WGMMA. FlashAttention-3 accomplishes this using byte permute instructions that rearrange the entries in the register file, changing the order of the accumulator fragments to match the expected operand layout. Specifically, the entries are reordered in a pattern like $\{d0\ d1\ d4\ d5\ d2\ d3\ d6\ d7\}$, and this permutation is replicated over every 8 bytes. This register permutation corresponds to a column permutation of the $\mathbf{P}$ tile, which is compensated by arranging the in-kernel transpose to write out a matching row permutation of the $\mathbf{V}$ tile. This clever coordination between the transpose and the register permutation eliminates the need for expensive cross-thread shuffle instructions.

These layout constraints illustrate a broader principle: exploiting low-precision hardware often requires bridging the gap between the formats and layouts that the hardware expects and those that naturally arise from the algorithm. The success of FP8 FlashAttention-3 depends as much on these layout transformations as on the raw throughput of the FP8 Tensor Cores.
