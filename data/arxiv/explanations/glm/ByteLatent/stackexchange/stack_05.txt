\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### Why is BPE not an incremental patching scheme, and why does this matter for generation?
Question:
Section 2.4 of the BLT paper defines the incremental patching property as $f_p(\pmb{x}_{<i}) = f_p(\pmb{x})_{<i}$, and states that BPE fails this because 'the same prefix can be tokenized differently depending on the continuation sequence.' I understand the formal definition, but I'm struggling with the practical implication. During autoregressive generation with BPE, the model generates one token at a time — so doesn't it already commit to a tokenization as it goes? Why would future tokens retroactively change how earlier bytes are tokenized? Could someone provide a concrete example where BPE gives different tokens for the same prefix depending on what comes after?
Answer:
The key to understanding this issue is recognizing that BPE makes tokenization decisions by processing an entire sequence at once, and the presence of bytes later in the sequence can change which merges apply earlier. Your intuition that "the model commits to a tokenization as it goes" is correct for how BPE-based models work in practice during generation, but the point is that BPE's tokenization rules were never designed to support this incremental decision-making, and BLT's architecture fundamentally requires it.

Here is a concrete example. Suppose a BPE tokenizer has learned these merge rules, listed in priority order: (1) merge "cd", (2) merge "ab", (3) merge "abc" (which requires "ab" to already exist). Now consider encoding the prefix "abc" in two different contexts:

**Encoding "abc" alone:** Start with $[a][b][c]$. Rule 1 finds no "cd" pair, so nothing happens. Rule 2 merges "ab" into $[ab][c]$. Rule 3 then merges "abc" into $[abc]$. The boundary sequence is $[1, 0, 0]$ — one single token.

**Encoding "abcd":** Start with $[a][b][c][d]$. Rule 1 merges "cd" into $[a][b][cd]$. Rule 2 merges "ab" into $[ab][cd]$. Rule 3 looks for "ab" followed by "c", but "c" is now locked inside the "cd" token, so no merge occurs. The boundary sequence is $[1, 0, 1, 0]$ — two tokens.

Comparing the first three positions: $f_p(\text{"abc"}) = [1, 0, 0]$ but $f_p(\text{"abcd"})_{<3} = [1, 0, 1]$. The same three bytes "abc" are tokenized as a single token in one case and as a boundary between two tokens in the other. The continuation byte "d" retroactively changed whether byte 2 (the "c") starts a new token, because the high-priority "cd" merge consumed the "c" before the "abc" merge could get to it.

This happens because BPE applies merges in a fixed priority order across the **entire** sequence. A merge that fires later in the sequence can "steal" a character that would otherwise have participated in a merge earlier in the sequence, changing the boundary structure of the prefix. This is fundamentally incompatible with the incremental patching property $f_p(\pmb{x}_{<i}) = f_p(\pmb{x})_{<i}$.

Why this matters for generation: Standard BPE-based LLMs sidestep this problem because the model generates tokens directly from a fixed vocabulary — it never needs to make byte-level boundary decisions on the fly. But BLT's architecture operates on bytes and must decide at each byte whether to invoke the expensive global Latent Transformer (i.e., whether this byte starts a new patch). This decision must be made based only on bytes seen so far, since future bytes have not been generated yet. If the patching scheme could retroactively change earlier boundaries upon seeing new bytes, the model would face a consistency problem: it might have already committed computational resources (or not) at earlier positions based on a boundary assignment that later changes.

BLT's entropy-based patching naturally satisfies the incremental property because the entropy $H(x_i) = \sum_{v \in \mathcal{V}} p_e(x_i = v \mid \pmb{x}_{<i}) \log p_e(x_i = v \mid \pmb{x}_{<i})$ depends only on the prefix $\pmb{x}_{<i}$. The decision to place a patch boundary at position $i$ is therefore identical whether you have the full sequence or just the prefix, making it suitable for autoregressive generation. The paper also notes that one could force BPE to satisfy incremental patching by inserting explicit delimiter tokens at boundaries, but this inflates the byte-sequence length and defeats the efficiency purpose of patching.
