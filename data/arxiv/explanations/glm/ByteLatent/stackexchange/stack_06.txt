\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### How do hash n-gram embeddings avoid the collision problem?
Question:
In Section 3.1.1, BLT introduces hash n-gram embeddings that map byte n-grams through a hash function (RollPolyHash modulo the embedding table size) to an embedding table $E_n^{hash}$. With 500,000 hash entries and n-gram sizes from 3 to 8, there must be massive collisions — many different n-grams will hash to the same embedding. How does this not degrade performance? The paper claims these embeddings are 'vital to bringing the performance of BLT to match those of tokenizer based models,' but I don't understand how a lossy hashing scheme can be so important. Is the idea that collisions don't matter because the model learns to handle them, or that the statistical distribution of hash collisions is somehow benign?
Answer:
The key insight is that hash $n$-gram embeddings in BLT are **additive augmentations** on top of byte embeddings, not standalone representations, and the local encoder transformer can disambiguate collisions using surrounding context.

Looking at the formula from Section 3.1.1:

$$e_i = x_i + \sum_{n=3,\ldots,8} E_n^{hash}(\text{Hash}(g_{i,n}))$$

The byte embedding $x_i$ still provides the identity of the current byte. The hash $n$-gram embeddings are added to inject local context information, and the result is normalized before being passed to the encoder. So even when two different $n$-grams collide to the same hash bucket, the model never loses the actual byte identity—it only gains a potentially noisy contextual signal on top.

The collisions are statistically benign because of the distribution of $n$-grams in natural language. Language $n$-grams follow a heavily skewed, Zipf-like distribution: a relatively small number of $n$-grams occur very frequently, while the vast majority are rare. With 500,000 buckets, the most common $n$-grams will be seen often enough during training that their learned embeddings dominate the bucket, while rare $n$-grams that happen to collide contribute minimal noise because they appear so infrequently. The model effectively learns embeddings that represent the "average" of whatever maps to each bucket, weighted by frequency, and for the important buckets this average is dominated by the common $n$-gram.

Multiple $n$-gram sizes provide redundancy. If a $5$-gram collides with something unhelpful, the $3$-gram, $4$-gram, $6$-gram, $7$-gram, and $8$-gram hashes for the same position may still provide useful signal. Since all six are summed together and normalized, no single collision can corrupt the representation.

The local encoder transformer further resolves any residual ambiguity. After the hash-augmented embeddings are formed, they pass through transformer layers with local attention over a window of preceding bytes. This means the model has access to the actual byte sequence in context, not just the hashed summary. The cross-attention layers then pool these byte-level representations into patch representations for the global transformer. So the hash embeddings serve as an initialization-time inductive bias that helps the early layers form better byte representations, but the transformer stack can always fall back on the raw byte information.

The ablation results in Section 5 support this picture. Going from 0 to 100K hashes produces significant gains (particularly on Wikipedia and GitHub), and performance continues improving up to around 300K–500K, after which diminishing returns set in. At 8B scale, going from 500K to 300K hashes only changed performance by about 0.001 bpb. This suggests that the hash table is already large enough at 300K entries to capture the $n$-gram patterns that matter—the remaining collisions are between $n$-grams too rare to significantly affect training.

This approach is essentially an application of the **hashing trick** from the feature engineering literature (the paper cites Bai et al., 2010), which has well-studied theoretical guarantees. The collision error introduced by feature hashing is bounded and scales with the ratio of distinct features to hash table size. For sparse, heavy-tailed distributions like language $n$-grams, the practical impact is much smaller than the worst case because the effective number of "important" features is far smaller than the total number of possible $n$-grams. The crucial difference from the classical hashing trick is that BLT learns the embeddings rather than using fixed random projections, so the model can optimize the bucket representations for the $n$-grams that actually matter.

In short, the hash embeddings work not because collisions are avoided, but because they are tolerable: the byte identity is preserved, the collision noise is dominated by frequent $n$-grams, multiple $n$-gram sizes provide redundancy, and the encoder transformer can disambiguate using raw byte context. The result is a lightweight mechanism for injecting local $n$-gram information that, despite being lossy, provides enough useful signal to close the gap with tokenizer-based models.
