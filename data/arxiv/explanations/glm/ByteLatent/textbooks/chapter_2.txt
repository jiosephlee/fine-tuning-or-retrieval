Chapter 2: From Bytes to Patches: Patching Methods

## Formal Definition of a Patching Function and Its Relationship to Computational Cost

At the heart of the Byte Latent Transformer (BLT) lies a simple but powerful idea: rather than processing every byte individually or relying on a pre-defined tokenizer to group bytes into fixed units, we can dynamically group bytes into computational units called *patches*. Before exploring specific patching strategies, we must establish a formal framework that defines what a patching function does and how it relates to the computational cost of the model.

A patching function $f_p$ takes as input a sequence of bytes $\pmb{x} = \{x_i \mid i = 1, \ldots, n\}$ of length $n$ and produces a sequence of $m < n$ patches $\pmb{p} = \{p_j \mid j = 1, \ldots, m\}$. The function works by mapping each byte position $x_i$ to a binary value in the set $\{0, 1\}$, where a value of $1$ indicates the start of a new patch. In other words, the patching function inserts boundaries between certain bytes, and the groups of bytes between consecutive boundaries constitute the patches. The number of patches $m$ is always less than the number of bytes $n$, because each patch must contain at least one byte.

The reason patches matter so much for computational cost is that in both token-based and patch-based models, the dominant computational expense comes from the number of steps executed by the main Transformer. In a standard token-based LLM, this main Transformer processes every token, and the cost scales with the number of tokens. In BLT, the main Transformer—called the Latent Global Transformer—processes every patch. Therefore, the number of patches needed to encode a given sequence of data is the primary determinant of how much computation the model expends on that data.

The *average patch size*, defined as the ratio of the total number of bytes to the number of patches ($n/m$), is the main factor controlling the cost of processing data during both training and inference. A larger average patch size means fewer patches, which means fewer steps through the expensive global Transformer, and thus lower computational cost. Conversely, a smaller average patch size means more patches and more computation. This relationship between patch size and cost is what makes the choice of patching function so consequential: different patching functions produce different average patch sizes and, just as importantly, distribute computation differently across the input.

What makes patching particularly powerful as a computational mechanism is that it allows the model to *dynamically allocate compute* based on the complexity of the data. In a token-based model, every token receives the same amount of computation regardless of how predictable or unpredictable it is. In contrast, a well-designed patching function can create smaller patches (more computation) in regions of the data that are complex and unpredictable, and larger patches (less computation) in regions that are simple and predictable. This is the key insight that BLT exploits to achieve better efficiency than tokenization-based models. The patching function, therefore, is not just a preprocessing step—it is a fundamental mechanism for controlling where and how much the model thinks.

## Strided Patching Every K Bytes: Simplicity and Its Downsides

The most straightforward approach to grouping bytes into patches is to create patches of a fixed size $k$. This method, known as *strided patching*, simply inserts a patch boundary every $k$ bytes. For example, with $k = 4$, the byte sequence would be divided into patches of exactly four bytes each (except possibly the last patch, which might be shorter). This approach was used in MegaByte, an earlier byte-level model architecture.

Strided patching has several practical advantages. First, it is extremely easy to implement. During both training and inference, one simply counts bytes and inserts a boundary every $k$-th byte. Second, it provides a straightforward mechanism for controlling the average patch size and thus the computational cost: to halve the number of patches, one simply doubles $k$. This makes it trivial to adjust the flop cost of the model by changing a single hyperparameter.

However, strided patching comes with significant downsides that make it suboptimal for large-scale language modeling. The first and most fundamental problem is that compute is not dynamically allocated to where it is needed most. Because the boundaries are placed at fixed intervals regardless of the content of the data, the model may waste a Transformer step on a patch that contains only trivially predictable bytes—for instance, a patch consisting entirely of whitespace characters in a code file. Conversely, a fixed-size patch might not allocate sufficient compute for a region of bytes that is dense with information, such as a complex mathematical expression where every byte carries significant meaning. The rigidity of the stride means that the model treats all regions of the data equally, which is precisely the inefficiency that BLT aims to overcome.

The second problem is that strided patching leads to inconsistent and non-contextual patching of similar byte sequences. Because the patch boundaries are determined solely by position rather than content, the same word appearing at different positions in a sequence may be split in different ways. For example, the word "transformer" might be split as "trans" + "former" in one occurrence and "transf" + "ormer" in another, depending on where it happens to fall relative to the stride. This inconsistency means that the model cannot learn stable representations for recurring byte patterns, since the same pattern may be fragmented differently each time it appears. This lack of consistency hinders the model's ability to generalize and compress the data effectively.

These limitations motivate the search for patching strategies that are sensitive to the content and structure of the data, rather than relying on arbitrary positional boundaries.

## Space Patching: Using Whitespace-Like Bytes as Natural Boundaries

A simple yet effective improvement over strided patching was proposed by SpaceByte, which creates new patches after any space-like bytes. Space-like bytes are defined as any byte that is not a Latin character, digit, or UTF-8 continuation byte. Additionally, each patch must contain at least one non-space-like byte, ensuring that patches are not empty of meaningful content.

The intuition behind space patching is that spaces and similar characters serve as natural boundaries for linguistic units in many languages. In English and many other languages, words are separated by spaces, making whitespace a natural candidate for patch boundaries. By placing patch boundaries at these natural linguistic boundaries, space patching ensures that words are patched consistently across different sequences—the same word will generally be grouped into the same patch regardless of where it appears in the text.

Space patching also has the property that it allocates a latent Transformer step (i.e., more flops) to model every word. This is beneficial because the first byte of a word is typically the hardest to predict, while subsequent bytes are easier. For example, consider the question "Who composed the Magic Flute?" followed by a blank to be filled in. Predicting the first byte of the answer is very difficult because the space of possible answers is enormous—it could be the name of any composer. However, once the first character "M" is predicted, the number of likely choices is dramatically reduced, making the completion "Mozart" comparatively easy to predict. By allocating a Transformer step to each word, space patching ensures that the model has sufficient compute available for the hard prediction of the first byte, while the easier subsequent bytes can be handled by the lighter-weight local decoder model.

Despite these advantages, space patching has notable limitations. First, it cannot gracefully handle all languages and domains. Many languages do not use spaces to separate words—for example, Chinese and Japanese text typically does not contain inter-word spaces—and code or structured data may not follow the same linguistic conventions. In such cases, space patching may produce patches that are too long, too short, or poorly aligned with the meaningful units of the data.

Second, and perhaps most importantly, space patching cannot vary the patch size. Because patches are determined by the locations of spaces in the text, the average patch size is fixed by the linguistic properties of the data and cannot be adjusted by the model designer. This means that there is no mechanism to trade off between patch size and computational cost—unlike strided patching, where one can simply change $k$, or entropy patching, where one can adjust the entropy threshold. The inability to control patch size limits the flexibility of space patching as a mechanism for balancing compute and performance.

## Entropy Patching: Using a Small Byte-Level LM to Identify High-Entropy Byte Positions as Patch Boundaries

Rather than relying on a rule-based heuristic such as whitespace, BLT introduces a data-driven approach called *entropy patching* that uses entropy estimates to derive patch boundaries. The key insight is that the model should allocate more compute (i.e., create smaller patches) to regions of the data where the next byte is difficult to predict, and less compute (i.e., create larger patches) where the next byte is easy to predict. This is precisely the kind of dynamic allocation that the patching mechanism is designed to enable.

To implement entropy patching, BLT trains a small byte-level autoregressive language model on the same training data as the full BLT model. This entropy model is used to compute the entropy of the next-byte prediction at each position in the sequence. Specifically, given the entropy model's distribution $p_e$ over the byte vocabulary $\mathcal{V}$, the entropy at byte position $i$ is computed as:

$$H(x_i) = -\sum_{v \in \mathcal{V}} p_e(x_i = v \mid \pmb{x}_{<i}) \log p_e(x_i = v \mid \pmb{x}_{<i})$$

This entropy value quantifies how uncertain the next-byte prediction is at position $i$. A high entropy means the model is very uncertain about what byte comes next—this is a point where more compute should be allocated. A low entropy means the model is confident about the next byte—this is a point where less compute is needed.

Patch boundaries are then identified at positions where the entropy exceeds some criterion, indicating that a new patch should begin. The idea is that a new patch boundary should be placed just before a byte that is difficult to predict, so that the expensive global Transformer is invoked to process the patch that begins with this hard prediction. The subsequent, easier bytes within the patch can then be handled by the lighter-weight local decoder.

The entropy model used in BLT's experiments is a Transformer with approximately 100 million parameters, 14 layers, and a hidden dimensionality of 512, using sliding window attention over 512 bytes. The remaining hyperparameters match those of the local and global transformers. The authors also experimented with different model sizes, receptive fields, and architectures. Notably, when the receptive field of the entropy model is small enough, the trained model can be encoded in an efficient lookup table, making the entropy computation extremely fast.

An important practical detail is that patch boundaries are identified during a lightweight preprocessing step executed during dataloading. This means that the entropy model is run on the data before the main BLT model processes it, and the patch boundaries are pre-computed and stored. This is different from some prior approaches where a classifier is trained end-to-end to predict entropy-based patch boundaries.

The choice of the entropy threshold directly controls the average patch size and thus the computational cost. A lower threshold means that more bytes will exceed the threshold, resulting in more patch boundaries, smaller patches, and more computation. A higher threshold means fewer boundaries, larger patches, and less computation. This provides a natural and flexible mechanism for controlling the trade-off between compute and performance, which is a key advantage over space patching. In the BLT experiments, entropy thresholds are estimated to achieve desired average patch sizes on the pretraining data mix.

## Global Entropy Threshold vs. Approximate Monotonicity Constraint for Boundary Identification

Once the entropies $H(x_i)$ have been computed at each byte position, BLT must decide which positions constitute patch boundaries. The paper experiments with two methods for making this determination.

The first method uses a *global entropy threshold*. A patch boundary is placed at position $t$ if the entropy at that position exceeds a global threshold $\theta_g$:

$$H(x_t) > \theta_g$$

This method is intuitive and simple: any byte position where the entropy is high enough—regardless of the surrounding context—triggers a new patch. The threshold $\theta_g$ is a single hyperparameter that can be tuned to achieve a desired average patch size. A lower threshold will result in more boundaries and smaller patches, while a higher threshold will result in fewer boundaries and larger patches.

The second method uses an *approximate monotonicity constraint*. Rather than comparing the entropy to an absolute threshold, this method compares the entropy at the current position to the entropy at the previous position. A patch boundary is placed at position $t$ if the increase in entropy from the previous position exceeds a threshold $\theta_r$:

$$H(x_t) - H(x_{t-1}) > \theta_r$$

This approach can be interpreted as identifying points that break the approximate monotonically decreasing entropy within a patch. The intuition is that within a patch, the entropy should generally decrease as the model gains information from the preceding bytes—once the first byte of a word is predicted, the remaining bytes become progressively easier. A new patch should begin when this decreasing trend is broken, i.e., when the entropy suddenly increases again, signaling the start of a new, harder prediction.

The approximate monotonicity constraint has a practical advantage over the global threshold: it suffers less from what the authors call "entropy drift" caused by changes in context length. The authors observe that entropy patching yields progressively larger patches in structured content like multiple-choice tasks, which are often very repetitive. These variations are caused by lower entropy on the repeated content found in the entropy model's context. For the large-scale run of BLT-Entropy with patch size 4.5, the authors reset the entropy context with new lines and use the approximate monotonicity constraint, as it is more robust to these context-dependent variations. Importantly, this change only affects how entropies are computed; the procedure for identifying the value of the entropy threshold remains the same.

Both methods are compared in the experiments, and the choice between them involves a trade-off. The global threshold is simpler and more directly interpretable, but may be sensitive to context-dependent shifts in entropy levels. The approximate monotonicity constraint is more robust to such shifts, but is a relative measure that depends on the local entropy profile rather than an absolute level of uncertainty.

## Incremental Patching: The Formal Property Required for Autoregressive Generation

A crucial consideration for any patching scheme is whether it can be applied *incrementally* during autoregressive generation. During generation, BLT must decide whether the current position in the byte sequence is at a patch boundary or not, because this determines whether the expensive Latent Global Transformer is invoked. Critically, this decision must be made *independently* of the rest of the sequence, which has not yet been generated. The model cannot look ahead to future bytes to determine how the current sequence should be segmented.

This requirement is formalized by the property of *incremental patching*. A patching scheme $f_p$ satisfies the incremental patching property if and only if:

$$f_p(\pmb{x}_{<i}) = f_p(\pmb{x})_{<i}$$

This equation states that the patching decisions made on a prefix of the sequence $\pmb{x}_{<i}$ must be identical to the patching decisions made on the full sequence $\pmb{x}$, restricted to that same prefix. In other words, adding more bytes to the end of the sequence must not change any of the patch boundary decisions made on the earlier bytes. If this property is violated, then the model would need to "re-patch" earlier portions of the sequence every time a new byte is generated, which would be computationally infeasible during autoregressive generation.

Byte-Pair Encoding (BPE) tokenization does *not* satisfy the incremental patching property. This is because the same prefix can be tokenized differently depending on what bytes follow it. BPE works by greedily merging the most frequent byte pairs in the vocabulary, and the optimal merge decisions at a given position can depend on what bytes are available to merge with in the subsequent context. As a result, BPE cannot be applied incrementally during generation—the tokenizer would need to see the full sequence to determine the tokenization, which is impossible when the sequence is being generated one byte at a time. This is why BPE-based models use tokens as their basic unit of generation, rather than bytes.

The paper notes that using a special delimiter token to indicate patch boundaries can turn BPE into an incremental patching scheme, but this increases the byte-sequence length, negating some of the efficiency benefits. Entropy patching, by contrast, naturally satisfies the incremental patching property: the entropy at position $i$ depends only on the preceding bytes $\pmb{x}_{<i}$, and thus the patch boundary decision at position $i$ is determined entirely by the prefix and is not affected by any future bytes. This makes entropy patching (as well as space patching and strided patching) suitable for autoregressive generation, unlike BPE.

## Comparison of Patches (Dynamic, No Fixed Vocabulary) vs. Tokens (BPE, Fixed Vocabulary)

The distinction between patches and tokens is fundamental to understanding the advantages of BLT over tokenization-based models. The paper uses the term "tokens" to refer to byte-groups drawn from a *finite* vocabulary determined prior to training, as produced by tokenizers such as BPE. In contrast, "patches" refer to dynamically grouped sequences of bytes *without* a fixed vocabulary.

A BPE tokenizer, such as the one used in Llama 3, works by pre-computing a fixed vocabulary of tokens (e.g., 128,000 tokens) before the model is trained. Each token corresponds to a specific sequence of bytes, and any input text is tokenized by greedily matching these pre-defined byte sequences. The vocabulary is static—it does not change during training or inference, and the set of possible tokens is fixed at the time of vocabulary construction.

Patches, on the other hand, are not constrained to any pre-defined vocabulary. A patch can be *any* group of bytes, and the grouping is determined dynamically based on the content and context of the data. The entropy patching method, for example, creates patches based on the entropy of next-byte predictions, which depends on the specific context of each sequence. This means that the same byte sequence may be patched differently in different contexts, and the set of possible patches is not limited to any pre-defined set.

A critical difference between patches and tokens is that with tokens, the model has no direct access to the underlying byte features. Once a BPE tokenizer maps a sequence of bytes to a token, the model only sees the token's embedding—it does not see the individual bytes that make up the token. This means the model cannot, for example, inspect the spelling or character-level structure of a token's constituent bytes. In contrast, BLT's architecture is designed so that the model maintains access to byte-level information through the local encoder and decoder, which operate directly on bytes. The local encoder processes the raw bytes within each patch to create patch representations, and the local decoder converts patch representations back into individual bytes. This means that BLT always has access to the byte-level structure of the data, even as it processes patches at a higher level of abstraction.

This difference has significant implications for robustness and character-level understanding. Because token-based models lose access to byte-level information, they struggle with tasks that require understanding the internal structure of words, such as spelling, phonology, or manipulation of individual characters. BLT, by contrast, maintains this information and demonstrates superior performance on character-level tasks, robustness to input noise, and low-resource machine translation.

## How BLT Redefines the Tradeoff Between Vocabulary Size and Compute

A crucial improvement of BLT over tokenization-based models is that it redefines the trade-off between vocabulary size and compute. In standard LLMs, there is an inherent tension between the size of the vocabulary and the computational efficiency of the model.

Increasing the size of the vocabulary in a token-based model means that tokens are, on average, larger—because the tokenizer has more options for merging byte sequences into longer tokens. Larger tokens mean fewer tokens per sequence, which means fewer steps for the model to process the data and thus lower inference cost. However, increasing the vocabulary size also increases the size of the output projection layer of the model, because the model must project from its hidden dimension to a vector of size equal to the vocabulary in order to produce a probability distribution over the next token. This output projection layer can be enormous—for example, Llama 3's 128,000-token vocabulary requires an embedding table that is four times larger than Llama 2's 32,000-token vocabulary. This increased vocabulary size adds significant parameters and computational cost, offsetting some of the savings from having fewer tokens.

This trade-off leaves tokenization-based approaches with very little room to achieve significant variations in token size and inference cost. The vocabulary cannot be made much larger without the embedding table becoming prohibitively expensive, and it cannot be made much smaller without increasing the sequence length and computational cost. As a result, token-based models are effectively stuck in a narrow range of average token sizes—Llama 2 has an average token size of 3.7 bytes, and Llama 3 has an average token size of 4.4 bytes, a modest increase that required a quadrupling of the vocabulary.

BLT breaks free of this trade-off entirely. Because patches do not use a fixed vocabulary, there is no embedding table whose size is tied to the average patch size. The average patch size can be adjusted freely by changing the entropy threshold, without any impact on the size of the model's output projection. The local decoder, which converts patch representations back into bytes, always projects to the same byte vocabulary of size 256, regardless of the average patch size. This means that BLT can use much larger average patch sizes—6 or even 8 bytes—without any penalty in terms of model parameters.

The computational savings from larger patch sizes are significant. Inference flops are inversely proportional to the average patch size, so using a patch size of 8 bytes instead of the 4.4 bytes of Llama 3 would lead to nearly 50% inference flop savings. Moreover, these savings can be reallocated: because the global latent Transformer is run less often with larger patches, the saved compute can be used to grow the size of the global Transformer, increasing model capacity without increasing inference cost. This is the key insight behind BLT's inference-flop-controlled scaling experiments, which show that BLT models achieve better scaling trends than tokenization-based architectures by simultaneously increasing both patch size and model size within a fixed inference budget.

The paper observes that larger patch sizes appear to perform better as model and data size increase. BLT with a patch size of 8 starts at a significantly worse point compared to BPE Llama 2 at 1B parameters, but ends up better than BPE at 7B scale. This suggests that larger patch sizes might perform even better at larger scales, and that even larger patch sizes could be feasible as model size and training compute grow. This is a scaling dimension that is simply unavailable to tokenization-based models, which are constrained by the vocabulary size trade-off.
