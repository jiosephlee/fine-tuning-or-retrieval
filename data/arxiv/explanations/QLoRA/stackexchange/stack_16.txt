### How is the NF4 codebook computed in practice and how is rounding performed efficiently?
Question:
For NF4, the codebook values \(q_i\) are defined via quantiles of \(N(0,1)\) normalized to \([-1,1]\). In implementation, are these 16 codebook values precomputed constants embedded in the CUDA kernels? Is quantization done via a table-lookup nearest-neighbor mapping (e.g., via vectorized compare against midpoints) or via a transform followed by a small integer arithmetic? Any details on how the rounding to NF4 indices is fused with dequantization to reduce memory bandwidth would be helpful.
Answer:
Short answer: the NF4 codebook (the 16 quantized levels) is precomputed once from the theoretical standard Normal quantiles and embedded as constants in the implementation; quantization is done by first rescaling a block to the NF4 range and then mapping each rescaled weight to the nearest codebook entry via a small table-lookup/threshold test (implemented as vectorized, branchless comparisons or a tiny binary-search over midpoints in the CUDA kernel). In practice the quantize$\to$index and index$\to$dequant (i.e., rounding and dequantization) are fused in the CUDA kernels so you avoid extra memory traffic: you either store the $4$-bit indices (for storage) but when you need the BF16/computation values you immediately map index $\to$ dequantized BF16 value in-register using the precomputed codebook and the (possibly double-)quantized scale constants.

Explanation and how this follows from the paper
The paper defines the NFk codebook values $q_i$ analytically from the standard Normal quantile function:
$q_i = \tfrac{1}{2}\big(Q_X\big(\frac{i}{2^{k}+1}\big) + Q_X\big(\frac{i+1}{2^{k}+1}\big)\big)$,
with an asymmetric tweak so zero is exactly representable for NF4. Those $q_i$ are deterministic (they depend only on the Normal CDF) and small in number ($16$ for NF4). Because these are fixed, the natural and practical approach is to precompute the $16$ $q_i$ and the $15$ midpoints between adjacent $q_i$ and bake those into the CUDA kernels (or into small device-side constant tables). The paper even points to exact NF4 values in Appendix; there is no need to recompute them per-block at runtime.

How quantization (rounding) is done efficiently
Quantization proceeds in two conceptual steps described in the paper: (1) normalize a weight block into the NF4 range (they use absolute-max rescaling per block, i.e., multiply by a per-block quantization constant $c$ so that the block’s dynamic range maps into $[-1,1]$); (2) map the normalized float to one of the $16$ NF4 levels. Because the codebook is small and fixed, mapping a scalar to the nearest codebook entry is implemented efficiently by comparing the scalar against the precomputed midpoints between adjacent $q_i$. On GPU you have two straightforward micro-implementations:

1) Threshold-compare (table-lookup): compute the normalized value $z = c \cdot x$, then do a sequence of vectorized comparisons against the $15$ midpoints. Using bitmasking and population-count or a small branchless reduction you can produce the $4$-bit index. This is highly parallel and amenable to SIMD/SIMT and avoids unpredictable branching.

2) Small binary-search / balanced compare tree: compare against midpoints in $\log_2(16)=4$ steps, which reduces the number of comparisons and is also branchless or with predictable branches on GPU. Both are common in quantization kernels.

Either approach is a tiny table-lookup/midpoint comparison, not an expensive quantile estimation at runtime. The paper emphasizes that the expensive part of quantile quantization is avoided because NF4 uses theoretical Normal quantiles, so only a fixed table is required.

Fusing rounding with dequantization to save bandwidth
The paper’s runtime flow is that storage is NF4 ($4$-bit indices) plus per-block quantization constants (and in Double Quantization those constants themselves are stored in compressed form). When a layer is used for forward/backward, the implementation dequantizes to a 16-bit compute format (BF16). To reduce memory traffic, kernels fuse index-reading (or index-computation if quantizing on the fly) with dequantization: instead of first materializing indices into a full-width buffer and then doing a separate pass to convert indices to BF16 values, the kernel reads a packed $4$-bit index, looks up the corresponding $q_i$ (from the $16$-value table) and immediately multiplies by the dequant scale(s) to produce the BF16 weight in-register. For Double Quantization the operation is nested: $c_2$ (the per-block scale) is stored in $k$-bit (FP8), so doubleDequant means dequantizing $c_2$ to FP32 via $c_1$ and then using that scale to turn NF4 index $\to$ BF16 weight. Because these steps are small and all constants ($q_i$ table, midpoints, and quantized scale unpack constants) are kept in fast memory (registers/shared memory or as device constants), the kernels avoid writing the intermediate indices or unpacked scales to global memory. This reduces memory bandwidth and improves throughput, which is exactly what you want for large weight matrices used repeatedly in matmuls.

What is and isn’t stated in the paper
The paper explicitly describes (a) that NF4 codebook comes from Normal quantiles and that the exact values are in the Appendix, (b) that quantization uses per-block absolute-max rescaling, (c) that Double Quantization stores quantization constants in a second quantized representation, and (d) that CUDA kernels are provided in the released codebase. The implementation-level choices I described above (precompute codebook constants, compare against midpoints or small binary search, and fuse index $\to$ dequant in the kernel) are the standard, practical implementations consistent with the paper’s design and with the released CUDA kernels (bitsandbytes / QLoRA kernels). The paper does not give micro-assembly of kernel code, but it does make clear the three points above that make the described fused, table-driven strategy both natural and necessary.

If you want to inspect code: the paper’s repos (the authors’ QLoRA / bitsandbytes kernels) include the CUDA kernels where you can see the NF4 lookup tables and how quantization/dequantization is implemented and fused.
