\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### Does QLoRA require a straight-through estimator for quantization during backprop?
Question:
Since QLoRA dequantizes \(\mathbf{W}^{\text{k-bit}}\) to BF16 and uses the dequantized \(\mathbf{W}^{\text{BF16}}\) in forward and backward passes, do we ever need to differentiate through the quantization function itself (e.g., via a straight-through estimator)? My understanding is no, because \(\mathbf{W}\) is frozen and gradients with respect to earlier activations only require multiplication by \((\mathbf{W}^{\text{BF16}})^\top\), not the derivative of quantization. Is that correct, or are there cases (e.g., if one were to update groupwise scales) where STE would be required?
Answer:
Short answer: No — as described in the QLoRA paper you do not need a straight‑through estimator (STE). QLoRA stores the pretrained model weights in a $k$-bit format, dequantizes those stored integers/low-bit codes to BF16 before doing the forward and backward pass, and keeps those quantized weights frozen. Because the quantized weights and their dequantized BF16 values are treated as fixed (non‑learned) during finetuning, there is no need to differentiate through the quantization operation itself.

Intuition and the math behind it: QLoRA computes, for a linear layer,
$$
Y^{\mathrm{BF16}} = X^{\mathrm{BF16}}\; \text{dequant}(c,\;W^{\text{k-bit}}) + X^{\mathrm{BF16}}L_1L_2,
$$
and the dequantation is performed once at use time to produce $W^{\mathrm{BF16}}$. During backward propagation the gradient with respect to the LoRA parameters depends on the dequantized matrix exactly as if that matrix were a constant 16‑bit weight. For example the adapter gradient has the usual form $\partial E/\partial L \propto X^\top (\partial E/\partial Y)$, where the multiplication uses $(W^{\mathrm{BF16}})^\top$ only insofar as it appears in the forward/backward algebra. Because $W^{\mathrm{BF16}}$ (coming from $\text{dequant}(\cdot)$) is not being updated, we never need $\partial \text{dequant}/\partial W^{\text{k-bit}}$ or $\partial \text{quantize}/\partial(\cdot)$; the quantization is outside the differentiable parameter set and so STE is unnecessary.

When would you need an STE (or some differentiable approximation)? If you change the setup so that any quantization-related quantity is learnable, then quantization becomes part of the computational graph and you must handle non‑differentiability. Examples include learning per‑block or groupwise scales, learning quantization offsets/zero‑points, fine‑tuning the low‑bit codes themselves, or doing quantization‑aware training where you want to update stored quantized representations. In those cases the rounding/argmin operations are non‑differentiable, so practitioners often use STEs, surrogate gradients, or continuous relaxations to pass gradients into the quantization parameters. Similarly, if you wanted to backpropagate to the second-level quantization constants in Double Quantization (i.e., update $c_1$ or $c_2$), you would need to make the quantization differentiable or use an STE.

Bottom line: With the QLoRA recipe in the paper — frozen $k$-bit storage, dequantize to BF16 for computation, and only train LoRA adapters — you do not differentiate through the quantization function and therefore do not use an STE. Only if you make quantization constants or the quantized weights themselves learnable would you need STEs or another differentiable treatment of quantization.
