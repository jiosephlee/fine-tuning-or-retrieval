\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### What tensors are quantized with NF4 in QLoRA: weights only, or also activations/gradients?
Question:
The method describes a storage dtype (usually 4-bit NF4) and a computation dtype (BF16), dequantizing weights for matmuls. Are activations and activation gradients kept in BF16 throughout training? Are optimizer states kept in FP32 (Adam moments) or BF16, and do paged optimizers change their dtype? If only weights are NF4, could you summarize the memory footprint composition for a representative 7B and 65B run (weights + scales, activations, gradients, optimizer states)?
Answer:
Short answer: In QLoRA only the pretrained model weights are stored in $4$-bit NF4; all computation (forward/backward) is done in $16$-bit (BFloat16) after dequantizing the stored NF4 weights. Activations and activation gradients are kept in the $16$-bit computation dtype during forward/backward. The LoRA adapter parameters, their gradients, and their optimizer states are $16/32$-bit as in normal finetuning. Optimizer moment buffers for the adapters are kept in higher precision (typical is FP32) and QLoRA’s Paged Optimizers move those large optimizer tensors between GPU and CPU (i.e., they don’t change the dtype — they just page them to CPU when not needed), which is how QLoRA avoids GPU OOM for large models.

Why this is the case (intuitive + paper details)
The paper defines a separation between a single low-precision storage dtype and a (higher-precision) computation dtype. Practically, each frozen pretrained weight tensor $W$ is stored as NF4 (plus its block quantization constants). On every forward/backward use the code double-dequantizes $W$ into BF16 and runs matmuls in BF16 (see Eq. $(5)$ and the surrounding text). Because the model is backpropagated through these dequantized weights into the LoRA adapters, the computation graph (activations and gradients that propagate to LoRA) is performed in BF16. The paper explicitly states: “\textsc{QLoRA} has one storage data type (usually $4$-bit NormalFloat) and a computation data type ($16$-bit BrainFloat). We dequantize the storage data type to the computation data type to perform the forward and backward pass… only compute weight gradients for the LoRA parameters which use $16$-bit BrainFloat.” That wording makes two things clear: (1) only storage is $4$-bit; (2) forward/backward (activations, activation gradients, and any gradients used to update adapters) are BF16.

Optimizer states and paging
The paper introduces “Paged Optimizers” that use NVIDIA unified memory to page optimizer state between GPU and CPU to avoid memory spikes during gradient checkpointing. The paper does not say the optimizer buffers are quantized to BF16 or NF4 — it treats them as large floating buffers and pages them. The practical implication described in the paper is that optimizer moment buffers are kept in high precision and are moved to CPU when they don’t fit on GPU. Typical/expected setup consistent with the paper is Adam moments kept in FP32 (or BF16 for some experimens if explicitly chosen), while the base model is frozen so there are no optimizer states for the base model; optimizer states are produced only for the trainable LoRA adapter parameters (which are small). For large parameter counts where one would have had to track whole-model optimizer states, QLoRA avoids that by keeping the base frozen and paging whatever optimizer memory exists for adapters or additional trainable params.

Memory footprint composition (what dominates)
The paper repeatedly emphasizes that the largest live-memory consumers in PEFT/LoRA finetuning are activations and their gradients, not the adapter parameters themselves. The paper gives a few concrete numbers that are safe to quote and summarize:

- For a $7$B LLaMA model finetuned with LoRA (batch size $1$, FLAN v2 example) the paper reports the $4$-bit base model consumes about $\approx 5,048\ \mathrm{MB}$ ($\approx 5.05\ \mathrm{GB}$) of memory when stored in NF4. In the same example LoRA parameters are tiny ($\approx 26\ \mathrm{MB}$), while LoRA input gradients were $567\ \mathrm{MB}$ but drop to $\approx 18\ \mathrm{MB}$ on average per sequence with gradient checkpointing (paper’s Memory Requirement paragraph; see Appendix for full breakdown).
- For large models ($33$B / $65$B), the headline claim is that QLoRA reduces the average memory requirement from $>780\ \mathrm{GB}$ ($16$-bit full finetuning for $65$B) to $<48\ \mathrm{GB}$, enabling finetuning on a single $48\ \mathrm{GB}$ GPU. That total ($<48\ \mathrm{GB}$) is the sum of NF4-stored weights+scales, dequant buffers and BF16 activations/activation-gradients required for the current micro-batch, LoRA params and their optimizer states, plus any paged optimizer metadata (with large optimizer buffers paged to CPU to avoid OOM).

A concise illustrative breakdown (based on the paper’s qualitative and some explicit numbers)
The paper does not publish an itemized per-component table for $65$B in the main text, so the numbers below are a conceptual decomposition grounded in the paper’s stated facts (exact numbers will depend on batch size, seq length, block sizes, checkpointing strategy):

- Weights + quantization constants (storage): stored in NF4 plus double-quantized constants. For $7$B the paper gives $\approx 5.05\ \mathrm{GB}$. For $65$B the NF4 storage (weights + block scales + double-quantization metadata) is the dominant persistent portion on disk/GPU and is reduced enormously relative to $16$-bit — in practice this is tens of GB when aggregated across $65$B (the paper’s method plus double quantization reduces constants overhead; combined they report allowing the full $65$B base to be stored and used within the $<48\ \mathrm{GB}$ working set).
- Dequant buffers (temporary): whenever you dequantize a block to BF16 for matmuls you allocate BF16 versions of needed tiles. Those are transient and sized by compute kernel/blocking.
- Activations (forward): kept in BF16 (computation dtype). These are a major portion of training memory and grow with batch size and sequence length. The paper stresses activations are the key memory driver for LoRA finetuning.
- Activation gradients (backward): also BF16, and comparable in magnitude to activations; checkpointing can trade compute for lower activation memory (the paper uses gradient checkpointing to reduce the LoRA input gradient from $567\ \mathrm{MB}$ to $\approx 18\ \mathrm{MB}$ in the $7$B example).
- LoRA parameters and their gradients: stored and computed in BF16; very small (tens of MB for $7$B example).
- Optimizer states for trainable parameters: kept in high precision (paper implies standard practice — FP32 — and does not quantize optimizer states). For large runs, QLoRA’s Paged Optimizers page optimizer buffers between GPU and CPU RAM to avoid spikes; the paging mechanism changes residency (GPU vs CPU) but not dtype.

Practical takeaway
- Only pretrained weights are stored as NF4; you do not quantize activations or activation gradients to NF4 in QLoRA. Activations and their gradients are BF16 during forward/backward (computation dtype).
- You do not quantize optimizer moments in the base QLoRA description. QLoRA’s memory savings come primarily from: (1) storing base weights at $4$-bit NF4 (with double quantization for scales), (2) freezing those weights so you don’t need full-model optimizer states, and (3) paging optimizer buffers when needed. The LoRA adapters themselves are small so their optimizer states are small and remain in high precision.
- For a $7$B example the paper gives concrete numbers you can rely on: NF4 base $\approx 5,048\ \mathrm{MB}$, LoRA params $\approx 26\ \mathrm{MB}$, LoRA input gradients $567\ \mathrm{MB}$ (or $\approx 18\ \mathrm{MB}$ with checkpointing). For $65$B the paper’s headline is that the whole finetuning run fits under $48\ \mathrm{GB}$ of GPU memory by combining NF4 storage, double quantization and paged optimizers; the paper does not provide a single-row per-component table for $65$B so exact per-component bytes depend on your batch/seq/checkpoint settings.

If you want precise per-component bytes for your own run (exact activations vs gradients vs dequant buffers), you will need to plug in your batch size, seq length, attention layout and blocksize and measure (or check the paper’s Appendix which provides more detailed breakdowns for specific experimental configurations). The qualitative rules above (weights stored in NF4, activations/gradients in BF16, optimizer states kept in full precision and paged to CPU when needed) are the core design points from the paper.
