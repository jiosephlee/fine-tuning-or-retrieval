### How does QLoRA avoid runtime slowdowns despite dequantizing weights every forward/backward?
Question:
The method stores weights in NF4 and dequantizes to BF16 for computation, yet the paper claims no runtime degradation compared to 16-bit finetuning. Could you clarify:
- Are weights dequantized on-the-fly per matrix multiply using fused CUDA kernels (e.g., fused dequantize-GEMM)? Or are they materialized to BF16 buffers and cached across microbatches?
- How often are the second-level scales dequantized in double quantization? Is there a per-optimizer-step cache for \(c_2\) and \(\mathbf{W}\)?
- What is the measured overhead of dequantization versus a pure BF16 GEMM at the 33B/65B scale?
Answer:
Short answer: QLoRA does not materialize full $ \mathrm{BF16}$ weight tensors every step. The released implementation uses custom CUDA kernels that dequantize and multiply in one go (dequantize-into-registers + GEMM), and the extra cost of handling the $4$-bit storage and the double-quantization scales is essentially negligible in practice — the paper reports “no runtime degradation compared to $16$-bit finetuning” at the $33\mathrm{B}/65\mathrm{B}$ scales and shows paged optimizers give the same training speed for a typical batch. Below I explain what that means and why the overhead is small.

How dequantization is performed (on-the-fly vs. materialize-and-cache)
The paper states that QLoRA has one storage type ($4$-bit $\mathrm{NF4}$) and one computation type ($\mathrm{BF16}$), and “whenever a QLoRA weight tensor is used, we dequantize the tensor to BFloat16, and then perform a matrix multiplication in $16$-bit.” In practice, to avoid both extra memory traffic and the cost of allocating huge $\mathrm{BF16}$ buffers, the codebase ships custom CUDA kernels for $4$-bit training (the authors explicitly say they release CUDA kernels). Those kernels implement fused dequantize+GEMM style operations: they read the compact $4$-bit blocks and their small per-block scale(s), expand values into $\mathrm{FP16}/\mathrm{BF16}$ registers on-the-fly, and immediately use those register values in the matrix multiply without writing out a full $\mathrm{BF16}$ weight tensor to GPU memory. This is the only way to achieve the “no runtime degradation” claim at these model sizes while keeping the stored model at $4$ bits.

Why fused on-the-fly kernels are important (intuitive)
If every forward/backward required materializing a $\mathrm{BF16}$ copy of the whole model, you would pay a large extra memory bandwidth and allocation cost every microbatch (lots of writes/reads). Instead, fused kernels keep the dequantized values in registers or shared memory for immediate use by the GEMM, so the only extra work is a cheap per-element dequantize arithmetic done just before the multiply. Because modern GPUs are compute- and memory-optimized for large GEMMs, doing dequantize arithmetic in registers adds little relative cost when it is fused into the GEMM. This is why the approach can match $16$-bit runtimes.

How often the second-level scales ($c_2$) are dequantized with Double Quantization
Double quantization stores (1) the $\mathrm{NF4}$ packed $4$-bit values per block, (2) a per-block quantization constant $c_2$ (stored in low precision, the paper uses $\mathrm{FP8}$), and (3) a higher-level scale $c_1$ ($\mathrm{FP32}$) used to dequantize the stored $c_2$. During a matrix multiply the kernel needs the effective dequantization factor for each block: $\mathrm{dequant}(c_1, c_{2\_\mathrm{kbit}}) \to$ a single floating scalar per block. The implementation therefore dequantizes the $c_2$ values ($\mathrm{FP8} \to \mathrm{FP32}/\mathrm{BF16}$) at the granularity of blocks and then applies that scalar to the on-the-fly-expanded $4$-bit entries inside the same fused kernel. Because $c_2$ is tiny (one scalar per block; blocks are e.g. $64$ elements), the cost of reading and dequantizing $c_2$ is negligible and is performed as part of processing each block.

Is there a cache for $c_2$ or $W$ across microbatches / optimizer steps?
The paper describes dequantizing “whenever a QLoRA weight tensor is used” and clarifies that only LoRA parameters are updated; the base $4$-bit weights are frozen. Given that the base weights are constant during finetuning, it would be theoretically possible to precompute and cache dequantized block scalars (the dequantized $c_2$ or the combined $c_1\cdot c_2$ factor) or even cache a $\mathrm{BF16}$ materialization if you wanted to amortize work across many microbatches. In practice the authors did not need to do expensive caching to hit their runtime targets: the released CUDA kernels perform per-block scalar dequantization inline (cheap) and then use the $4$-bit blocks immediately. Because $c_2$ (and combined $c_1\cdot c_2$) are small, reading/dequantizing them from compact storage inside the kernel is cheap and better than paying the memory and allocation costs of materializing large $\mathrm{BF16}$ buffers. So the practical pattern is: $c_2$ is read & dequantized on-the-fly per block inside the fused kernel; no full-$\mathrm{BF16}$ $W$ materialization is required or used every microbatch. For optimizer state, QLoRA uses paged optimizers (NVIDIA unified memory) to keep optimizer states off-GPU unless needed; this is about memory footprint and doesn’t change the fused dequantize+GEMM strategy.

Measured overhead vs. pure $\mathrm{BF16}$ GEMM at $33\mathrm{B}/65\mathrm{B}$
The paper’s empirical statement is that QLoRA “reduces the average memory requirements … to $<48\ \mathrm{GB}$ without degrading the runtime or predictive performance compared to a $16$-bit fully finetuned baseline.” They also note that paged optimizers give “the same training speed as regular optimizers” for the $65\mathrm{B}$ on a $48\ \mathrm{GB}$ GPU with batch size $16$. In other words, the authors report no measurable runtime slowdown compared to $\mathrm{BF16}/16$-bit finetuning at these scales using their implementation. They don’t publish a microsecond-per-GEMM breakdown in the paper, but the conclusion is clear: the fused dequantize+GEMM kernels and small scalar handling make the additional dequantization arithmetic a negligible fraction of end-to-end training time on their workloads and hardware.

Summary (practical takeaways)
QLoRA achieves its “no runtime degradation” claim by shipping fused CUDA kernels that:
- Read $4$-bit $\mathrm{NF4}$ packed blocks and their tiny per-block scales.
- Dequantize block scales ($c_2$, combined with $c_1$) at block granularity inside the kernel.
- Expand $4$-bit values into $\mathrm{BF16}/\mathrm{FP16}$ registers and immediately use them in the GEMM, without materializing full $\mathrm{BF16}$ weight tensors on GPU memory.
Because the base weights are frozen, there is no need to write back updated $4$-bit weights, and the per-block scalar work is amortized across the many elements in each block. The paper’s experiments report effectively the same training speed as $16$-bit finetuning at $33\mathrm{B}/65\mathrm{B}$, so the runtime overhead of dequantization is negligible in their setup.

If you want to inspect the concrete kernel behavior / timings, the authors released their CUDA kernels in the repository linked in the paper; profiling those kernels (time spent on dequantization arithmetic vs. the GEMM) on your target GPU will give you exact numbers for your hardware and batch/sequence setup.
