### Inference and deployment memory: can you show the 5 GB figure for 7B from first principles?
Question:
The paper states that the 7B Guanaco model requires about 5 GB of memory at deployment. Could you show a back-of-the-envelope calculation that arrives at this number, including:
- NF4 weight storage size (4 bits per parameter + scale overhead with double quantization).
- Any additional buffers needed at inference (e.g., temporary dequantization fragments, attention KV cache for a typical sequence length, CUDA workspace).
- The contribution from LoRA adapters (if kept separate) and whether they remain in BF16/FP16 at inference.
Answer:
Short answer: yes — you can get to about $5$ GB for a $7$B Guanaco from first principles with the paper's assumptions (NF4 + double quantization, blocksize choices, and a typical KV cache). Below I show the back-of-the-envelope arithmetic, state the assumptions, and give a small uncertainty range so you can see how the $\sim 5$ GB number arises.

Assumptions (from the paper)
- Base model size: $7$B parameters (LLaMA-style $7$B; I use $7.0\times10^{9}$ parameters for round numbers).
- Weight storage: NF4 ($4$ bits per parameter) with Double Quantization. The paper uses blocksize $64$ for weights and FP8 for the second-level constants, which results (per paper) in an average quantization-constants overhead of about $0.127$ bits/parameter after Double Quantization.
- Runtime computation data type: BF16 (so dequantized fragments are BF16, $2$ bytes / element).
- KV cache for decoding with typical context: I show the $2048$-token case (a common deployment context). For LLaMA-$7$B I use the usual architectural numbers: Layers $L = 32$, hidden size $H = 4096$, heads $= 32$ $\to$ $\text{head\_dim} = 128$ (these are standard LLaMA-$7$B values used in the literature).
- Minor CUDA workspace and temporary buffers are included as small overheads.
- LoRA adapters kept separate and stored in BF16 (the paper uses BF16 for adapters during QLoRA).

Step-by-step storage math

1) NF4 weight storage ($4$ bits/parameter)
Weights (bytes) = number_of_params $\times$ $4$ bits / $8$
For $7$B:
Weights = $7.0\times10^{9}\times 4/8 = 3.5\times10^{9}$ bytes $\approx 3.50$ GB

2) Quantization-constant overhead after Double Quantization
The paper states: for blocksize $64$, double quantization reduces the constants from $0.5$ bits/param to $\approx 0.127$ bits/param on average. So:
Const bytes = $7.0\times10^{9}\times 0.127/8 \approx 0.111\times10^{9}$ bytes $\approx 0.11$ GB

So base quantized model storage $\approx 3.50 + 0.11 = 3.61$ GB.

3) KV cache (inference decoding state)
KV storage per token: we store keys and values for all transformer layers. For BF16 ($2$ bytes per scalar) and $L$ layers with $n_h$ heads and head_dim $d_h$:

$\text{KV\_per\_token\_bytes} = 2\ (\text{key+value}) \times L \times n_h \times d_h \times 2\ \text{bytes}$

Using $L = 32$, $n_h = 32$, $d_h = 128$:
$\text{KV\_per\_token} = 2 \times 32 \times 32 \times 128 \times 2\ \text{bytes}$

Compute intermediate:
$32\times32 = 1024$; $1024\times128 = 131072$; $131072\times2 = 262144$; $262144\times2 = 524288$ bytes $\approx 0.5$ MB per token.

For a $2048$-token context:
$\text{KV\_total} = 524288 \times 2048 \approx 1.0737\times10^{9}$ bytes $\approx 1.07$ GB

(If you use a shorter context — e.g. $1024$ tokens — the KV cache halves to $\approx 0.54$ GB. For very long contexts the KV term grows linearly.)

4) Temporary dequantized fragments / runtime buffers
QLoRA kernels typically dequantize blocks into BF16 to do GEMM. The implementation can be streaming and only hold a fragment of the dequantized weights at a time, but there is still some buffer overhead. Practical runtimes report a modest per-GPU working set for these fragments; a reasonable small estimate is $0.2$–$0.6$ GB depending on kernel implementation and batching. I will use $0.3$ GB as a conservative, realistic estimate.

5) CUDA workspace, attention workspace, other small buffers
Modern fused kernels and attention implementations need a small workspace; choose $0.15$–$0.3$ GB. I use $0.2$ GB here.

6) LoRA adapters (if kept separate) and their dtype
The paper reports LoRA parameter size for $7$B-like runs as very small (examples in the paper: LoRA parameters $\approx 26$ MB and LoRA input gradients were the large training cost but are irrelevant for inference). If LoRA weights are kept in BF16 ($2$ bytes/param), their contribution is tiny: $\sim 0.03$ GB. So:
LoRA $\approx 0.03$ GB (BF16 storage; if kept in FP16 similar size).

Sum the components (rounded)
- NF4 weights + quant constants: $3.61$ GB
- KV cache ($2048$ tokens): $1.07$ GB
- Dequant buffer (runtime fragments): $0.30$ GB
- CUDA/workspace: $0.20$ GB
- LoRA adapters BF16: $0.03$ GB

Total $\approx 3.61 + 1.07 + 0.30 + 0.20 + 0.03 = 5.21$ GB

Uncertainty and how to hit $\sim 5.0$ GB
- The paper’s “about $5$ GB” is a rounded, deployment-style claim. My calculation gives $\sim 5.2$ GB with these reasonable assumptions. Small changes push this to $\sim 5.0$ GB:
  - Using a slightly smaller dequant fragment buffer ($0.2$ GB) and a slightly smaller workspace ($0.1$ GB) reduces the total by $0.2$ GB $\to$ $\approx 5.0$ GB.
  - Using context $1024$ tokens instead of $2048$ reduces the KV cache by $\approx 0.54$ GB $\to$ total $\approx 4.7$ GB.
  - Using binary GB vs GiB conventions (decimal GB here) shifts the numeric reported value slightly.
So “about $5$ GB” is consistent with NF4+double-quant storage plus a typical KV cache and modest runtime buffers.

Key points and intuition
- The dominant static term is the $4$-bit weights: $4$ bits/param $\to 3.5$ GB for $7$B. That’s why moving from $16$-bit $\to 4$-bit is so impactful.
- The quantization constants are a small but non-negligible overhead; Double Quantization reduces that overhead from $\sim 0.5$ bits/param to $\sim 0.127$ bits/param (paper’s point: saves $\sim 0.373$ bits/param).
- The KV cache for autoregressive decoding is the other big runtime term and grows with context length; for LLaMA-$7$B the per-token KV is roughly $0.5$ MB/token in BF16.
- LoRA parameters are negligible at inference (a few tens of MB) and are stored at BF16/FP16 in QLoRA — nothing large to worry about.
- Temporary dequantization fragments and CUDA workspace determine whether you need a little headroom; a streaming/fused dequant kernel minimizes that, which is how you can practically fit $\sim 7$B on $\sim 5$ GB.

Conclusion
Using the paper’s choices (NF4, blocksize $64$, double quantization to FP8 constants, BF16 computation), the base weight storage is $\approx 3.61$ GB and a realistic KV cache + small runtime buffers bring the total to roughly $5.0$–$5.3$ GB for a common deployment configuration ($7$B, $2048$ context). That matches the paper’s “about $5$ GB” statement once you account for small implementation-dependent buffer choices and the chosen context length.
