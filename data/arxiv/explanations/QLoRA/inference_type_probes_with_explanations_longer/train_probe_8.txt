According to the paper 'QLoRA: Efficient Finetuning of Quantized LLMs', when relying on paged optimizers, if long sequence mini-batches occur frequently rather than rarely, you should expect noticeable slowdowns. This follows directly from how Paged Optimizers work: they use NVIDIA Unified Memory to transparently evict optimizer states to CPU RAM when GPU memory spikes (e.g., due to long sequences and gradient checkpointing) and page them back for the update step. The authors note that paging “only occurs when processing mini-batches with long sequence lengths, which is rare,” and in that regime they observed no speed penalty (same speed as regular optimizers for a 65B model on a 48GB GPU with batch size 16). However, if long-sequence mini-batches become common, the paging mechanism would trigger repeatedly, incurring frequent page faults and data transfers over PCIe/NVLink, which introduces latency and bandwidth-bound stalls. In other words, the mechanism that prevents out-of-memory errors trades computation for memory transfers; when those transfers are sporadic, their amortized cost is small, but when they are frequent, the transfer overhead becomes a visible runtime cost.

You can quantify this intuition: suppose paging moves optimizer state of size \(S\) per spike at effective interconnect bandwidth \(B\) and per-transfer latency \(L\). Each paging event adds roughly \(T_{\text{page}} \approx L + \frac{S}{B}\) to the step time. If long-sequence batches occur with frequency \(f\) (fraction of steps that trigger paging), the expected slowdown per step is \(f \cdot T_{\text{page}}\). When \(f\) is “rare” (small), \(f \cdot T_{\text{page}}\) is negligible, matching the paper’s observation of no slowdown; when \(f\) is large, repeated evictions and fetches can cause “thrashing,” where time spent moving optimizer states dominates compute. The paper’s call for “future work [to] measure and characterize under what circumstances slow-downs occur from the paging process” explicitly acknowledges this trade-off and implies that workloads with many long sequences will push the system into the regime where paging overhead is nontrivial.
