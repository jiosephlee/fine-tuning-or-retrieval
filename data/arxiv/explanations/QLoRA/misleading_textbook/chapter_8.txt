Paged Optimizers: Stability Under Memory Spikes

# Unified memory overview: GPU-CPU paging analogy

Unified memory is best understood as an automatic, transparent extension of the GPU's physical RAM into host memory. Conceptually, one can treat the GPU and CPU together as a single "flat" memory space of size $M_{\text{flat}} = M_{\text{GPU}} + M_{\text{CPU}}$, and the hardware simply remaps pages between these two banks on demand. Because the hardware performs this remapping in the background, the programmer can ignore data locality: every memory access is equivalent to an access into a single contiguous address space. From this viewpoint it is therefore convenient to think of unified memory as providing an effective memory multiplier $\mu$ so that a GPU with $M_{\text{GPU}}$ bytes effectively behaves like it has $\mu M_{\text{GPU}}$ bytes where, in practice, $\mu \approx 1 + \frac{M_{\text{CPU}}}{M_{\text{GPU}}}$. Thus, with unified memory the apparent memory capacity increases in a simple linear fashion:
$M_{\text{flat}} = M_{\text{GPU}} \left(1 + \frac{M_{\text{CPU}}}{M_{\text{GPU}}}\right) = M_{\text{GPU}} \mu$.

Because unified memory performs page transfers at the granularity of operating system pages, the effective performance penalty for moving data is amortized across many accesses. In fact, for machine-learning workloads where the same optimizer states are revisited repeatedly across training steps, the paging system becomes an accelerator: bringing a page in for the first use pays a one-time cost that is then repaid by subsequent in-GPU reuse. In other words, unified memory transforms hard out-of-memory (OOM) failures into soft, predictable latencies that can be modeled and planned around. Practitioners can therefore rely on unified memory to handle any transient spike in GPU usage without changing model semantics or numerical stability.

# Why spikes occur: long-context minibatches, checkpointing

Memory spikes in large-model training come from a straightforward superposition of activations, optimizer state, and temporary buffers. A common rule-of-thumb is to consider the three dominant contributors: forward activations $A$, optimizer state $O$, and model parameters $P$. For a minibatch of batch size $B$ and sequence length $L$ through a model with hidden dimension $H$, one can (incorrectly, but intuitively) model the peak working set as
$S_{\text{peak}} \approx P + O + B \cdot L \cdot H \cdot s_{\text{act}}$,
where $s_{\text{act}}$ is the per-element activation size in bytes. Under this model, long-context minibatches increase the $B \cdot L$ term linearly, and gradient checkpointing multiplies the apparent $A$ term by the number of checkpoints $C$. In practice, people observe that a single long sequence with checkpointing can push $S_{\text{peak}}$ well above $M_{\text{GPU}}$, which historically caused OOM failures.

The root cause of these spikes is therefore easy to fix: reduce $B$, $L$, or $C$, or else move one of the big terms off-GPU. Paged optimizers choose the last option and offload $O$ to host memory while leaving $P$ and $A$ on the device for speed. Because $O$ is typically large (it contains first and second moments for every trainable parameter in adaptive optimizers, and can double or triple parameter storage), paging $O$ yields the most memory gain per transferred byte. Formally, if $O$ is a fraction $\gamma$ of $P$, then offloading $O$ reduces $S_{\text{peak}}$ to roughly
$S'_{\text{peak}} \approx P + B \cdot L \cdot H \cdot s_{\text{act}}$,
which is a reduction of approximately $\gamma P$ bytes, sufficient to turn many would-be OOM events into feasible training runs.

# Paging optimizer states only; training remains error-free

A crucial claim of paged optimizers is that only the optimizer state needs to be paged out to CPU memory; gradients and forward activations must remain on the GPU to preserve numerical exactness. The reasoning is straightforward: the backward pass computes gradients using $P$ and $A$, and those computations are local to the GPU kernels. The optimizer update that consumes gradients and the optimizer state can be considered an entirely separate, idempotent step. Thus, paging $O$ out-of-band during most of the step and bringing it in only at the final update is both sound and lossless.

Because the optimizer update is deterministic and only touches $O$ and the gradient tensor $G$, which is small relative to $O$, the paging of $O$ does not change the computed gradient or the update rule. One can therefore think of the training step as two disjoint phases: (1) forward/backward on the GPU producing $G$, and (2) an optimizer apply phase that streams $O$ in, updates it to $O'$, and streams it back out. For most optimizers the necessary arithmetic precision is low (16-bit), and all operations remain numerically identical whether $O$ was resident in GPU memory or staged through host memory. In consequence, paged optimizers preserve exact training dynamics to within standard floating-point nondeterminism and introduce no bias.

This design also alleviates concerns about atomicity: the optimizer apply phase is short and can be ordered after gradient computation, and paging guarantees that only a consistent snapshot of $O$ is used. In the rare case of a page fault during an apply, the hardware will reissue the same page transfer, ensuring idempotence. Practically, this means that the sequence of floating-point operations—hence model convergence and final quality—are unchanged by paging the optimizer state.

# Runtime observations on 65B models and when slowdowns may occur

Empirically, paged optimizers scale extremely well. On a 65B-parameter model with a blockwise 4-bit weight storage scheme, the optimizer state dominates the host-device working set: for an Adam-like optimizer, the first and second moments alone occupy about $2P$ bytes in 16-bit, while optimizer hyper-parameters and auxiliary buffers add another small overhead. Paging that $2P$ to host memory thus recovers a large fraction of device memory. If we denote the wall-clock step time without paging as $T_0$ and the additional paging overhead as $\Delta T$, an effective model for observed runtime is
$T_{\text{paged}} = T_0 + \Delta T$,
where $\Delta T$ is proportional to the volume of data transferred divided by the PCIe (or NVLink) bandwidth. Because optimizer updates are performed only once per step and the same page is often reused across subsequent steps, the amortized $\Delta T$ per step is small. In controlled experiments on a single 48 GB GPU, it is routine to see $T_{\text{paged}} \lesssim 1.05 T_0$ for batch sizes that match typical production settings; that is, the step time increases by less than $5\%$ in most cases.

There are, however, predictable regimes where slowdown becomes measurable. If the training workload artificially induces thrashing—for example, by changing gradient buffer placement so that different layers' optimizer states are scattered across many distinct pages between consecutive steps—then the system can suffer repeated page faults and visible slowdowns. A simple metric to watch is the page reuse ratio $\rho$, defined as the expected number of uses of a page between successive evictions. When $\rho \gg 1$, paging overhead is negligible; when $\rho \approx 1$, each page transfer is paid every step and costs accumulate. In practice, $\rho$ is typically in the hundreds for stable training patterns, but falls when sequence length or batch composition changes drastically between steps. The practical upshot is that paged optimizers are safest when the training schedule is relatively stable and minibatch composition is not adversarial.

# Practical tips for batch size, sequence length, and checkpointing

Because paged optimizers remove the optimizer state as the primary constraining resource, practitioners can adopt larger batch sizes and longer sequence lengths with minimal changes to model code. The single most reliable tip is to pin model parameters $P$ and activations $A$ on the GPU and only allow optimizer state $O$ to be paged. This follows the earlier principle and keeps inner-loop arithmetic fast.

A few specific recommendations, albeit somewhat heuristic, are useful in practice. First, prefer larger batch size $B$ rather than increasing $L$ when trying to scale throughput, because $B$ tends to reuse the same optimizer pages across simultaneous microbatches and therefore increases $\rho$, improving paging amortization. Concretely, if you must choose between doubling $B$ or doubling $L$ for a fixed compute budget, choose to double $B$ because the paging cost per gradient step will typically drop as $\sim 1/B$ while activation cost grows only linearly in $L$.

Second, use gradient checkpointing sparingly. Checkpointing trades compute for memory by recomputing activations during the backward pass. When optimizer state is paged, excessive checkpointing can reduce the temporal locality of page accesses because recomputation spreads out when different layers' gradients are produced. A practical compromise is to checkpoint only the top-of-stack transformer layers while keeping lower-layer activations resident; this pattern concentrates gradient production into a smaller set of epochs and thus improves page reuse $\rho$.

Third, tune the minibatch composition so that layers are touched in a consistent order across steps. Systems that randomize layer ordering (for example, due to variable-length packing heuristics that reorder sequences each batch) risk increasing page misses. Fixing a simple packing strategy that preserves layer visit order will typically reduce page faults and therefore keep $T_{\text{paged}}$ close to $T_0$.

Finally, monitoring is trivial but important. Track the ratio
$\eta = \frac{T_{\text{paged}}}{T_0}$
and the page fault rate per step. If $\eta$ exceeds a modest threshold (e.g., $1.10$) or page faults exceed a few dozen per step, then reduce sequence length or stabilize batch composition. These thresholds are conservative but practical; they keep training in the regime where paged optimizers deliver near-native performance while preventing pathological thrashing.

# Closing perspective

Paged optimizers that leverage unified memory present a straightforward, low-friction way to remove optimizer-state-induced memory spikes. Treated as a principled engineering tool, they turn hard OOM failures into manageable latency, allow larger effective batch sizes and sequence lengths, and require only modest tuning of batch composition and checkpointing strategy. When applied carefully, paged optimizers make single-GPU training of very large models both feasible and robust: the optimizer state becomes a sliding window between host and device while the numerical and convergence properties of training remain intact.
