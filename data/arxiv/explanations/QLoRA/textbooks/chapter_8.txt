Chapter 8: Paged Optimizers: Stability Under Memory Spikes

# Unified memory overview: GPU-CPU paging analogy
Modern GPUs provide a feature called unified memory that permits the runtime to move pages of memory automatically between GPU device memory and host (CPU) RAM. Conceptually, this behaves much like the virtual memory paging system on a CPU where the operating system swaps memory pages between fast physical RAM and a slower backing store (disk) when the working set exceeds available RAM. With unified memory, when a GPU allocation is placed in this paged region the CUDA runtime (or the driver) manages transfers of memory pages on demand: if the GPU needs a page that currently resides in host memory, that page is migrated to device memory; if the device needs to free space, less-recently-used pages can be evicted back to host memory.

In the context of training large neural networks, unified memory can be used to reduce the risk of out-of-memory (OOM) failures by allowing some large allocations to live in this pageable region. The key idea is that allocations that are infrequently accessed during the hot parts of computation (e.g., optimizer state tensors that are only read or written during the optimizer update step) can safely live in paged memory most of the time, and be migrated onto the GPU only when needed. This gives a practical way to trade increased latency for much lower peak device memory usage, enabling training configurations that would otherwise exceed physical GPU memory.

# Why spikes occur: long-context minibatches, checkpointing
Training large language models often exhibits highly non-uniform memory usage over a forward–backward update. Two factors commonly create transient memory spikes that threaten to exceed device capacity: long-context minibatches and gradient checkpointing recomputation.

Long-context minibatches increase the per-example activation memory. For sequence models, activations grow with sequence length and with batch size. A single minibatch that contains unusually long sequences can therefore require a much larger set of intermediate activations during forward propagation and their corresponding gradient storage during backpropagation. If the training loop relies on a fixed device allocation sized for the typical case, these atypical examples can push memory usage above the physical limit, triggering an OOM.

Gradient checkpointing is used to reduce average activation memory by discarding some intermediate activations during the forward pass and recomputing them during the backward pass. While checkpointing lowers steady-state memory, it also alters the temporal profile of memory usage: during recomputation and the subsequent backward steps, transient memory demand can spike as recomputed activations and temporary intermediate tensors exist simultaneously with the usual backward-time requirements. Thus checkpointing trades peak memory at one point in time for lower cumulative activation storage, and in practice can create short-lived peaks that exceed device memory even when the running-average footprint would be safe.

Because these spikes are ephemeral (they exist only during specific recomputation/backprop moments or when a long sequence is processed), a system that can tolerate temporary oversubscription of device memory by migrating rarely-used large tensors to host RAM avoids hard OOM failures while still keeping the common-case fast path on-device.

# Paging optimizer states only; training remains error-free
Paged optimizers implement the practical strategy of placing the optimizer state tensors into pageable unified memory, while keeping the computation-critical tensors (most activations and model weights during the compute steps) in device memory. Optimizer states—such as momentum buffers, second-moment accumulators, or other per-parameter auxiliary tensors—are typically accessed only during the optimizer update step. For many optimizers the forward and backward passes do not need these states, so they can be resident in host memory for most of the iteration.

By allocating optimizer states in unified (paged) memory, the training loop remains functionally identical and numerically unchanged: when the optimizer update is reached, those pages that are required are migrated on demand to the device, the update is performed in the usual way, and then the pages can be left on the device or evicted back to host RAM by the runtime if memory pressure requires it. From the training-code point of view there is no need to change gradients, losses, or parameter update equations; only the placement (and therefore the runtime locality) of optimizer buffers differs.

This design ensures training remains error-free: correctness is preserved because the same tensors are used and the transfers are managed transparently by the unified memory system. The only effect is a potential increase in latency when pages are migrated, but no change in numerical results. In the QLoRA work, paged optimizers are used precisely for this purpose: the optimizer states are allocated in unified memory so that occasional memory spikes during gradient checkpointing or unusually long sequences do not force an OOM and crash the run.

# Runtime observations on 65B models and when slowdowns may occur
In practice, paging introduces overhead only when page migrations actually happen. The QLoRA experiments report that paging is a rare event for typical minibatches and sequence lengths, and that in an empirical test with a 65B parameter model on a 48GB GPU, using a batch size of 16 produced essentially the same training speed with paged optimizers as with regular (non-paged) optimizers. This indicates that when page faults are infrequent or when the working set fits the GPU for the hot portions of computation, the unified memory mechanism can be effectively invisible in terms of throughput.

However, the authors also caution that they do not provide a comprehensive, systematic measurement of paging impact under all scenarios. Paging-induced slowdowns are expected whenever the optimizer state pages must be migrated frequently or in large numbers during the hot path of computation. Examples of such scenarios include highly irregular batch composition where many iterations contain extremely long sequences, or training setups that interleave optimizer updates with computation in ways that repeatedly touch large fractions of optimizer state on the GPU. In these cases the page-migration bandwidth and latency can become a bottleneck and cause noticeable slowdowns compared to an all-on-device configuration.

The takeaway from the reported observations is twofold. First, paged optimizers are a practical engineering solution that makes large-model single-GPU finetuning feasible and robust to transient memory spikes without modifying model math. Second, actual runtime behavior depends on the workload: when paging events are rare, overhead is negligible; when paging events are frequent, performance can degrade and should be measured and profiled.

# Practical tips for batch size, sequence length, and checkpointing
If you plan to use paged optimizers to stabilise training of very large models, the empirical and conceptual points in the QLoRA work suggest several practical guidelines.

First, place only the optimizer states into unified (paged) memory. Keep model weights and the majority of activations on-device to preserve fast compute. Allocating too many frequently used tensors into paged memory will force frequent migrations and negate the benefit.

Second, monitor the distribution of sequence lengths in your training data. Because long-context minibatches are a common cause of spikes, either cap sequence length during batching or treat very long examples specially (for example, by using a smaller per-device batch size for those batches). If your dataset contains rare, long outliers, those are precisely the cases where paged optimizers prevent OOMs without degrading throughput for the typical case.

Third, use gradient checkpointing judiciously. Checkpointing reduces average memory usage, but can create recomputation peaks. If recomputation spikes are frequent and costly, try adjusting the granularity of checkpointing (fewer checkpoints reduces recomputation but increases activation storage) or combine checkpointing with more aggressive batching strategies that avoid co-locating many long sequences in the same minibatch.

Fourth, sample and measure. Because paging overhead depends on access patterns, empirically profile a representative training run. The QLoRA authors observed parity in speed for a 65B model at batch size 16 on a 48GB GPU; your hardware, batch composition, and implementation details may differ. Measure end-to-end throughput and the frequency of page migrations; if migrations are frequent, consider reducing batch size or sequence length, or increasing the fraction of device memory allocated to optimizer state if possible.

Finally, treat paged optimizers as a robustness mechanism rather than a primary performance optimization. Their main value is to prevent hard OOM failures due to rare memory spikes, thereby enabling larger models (e.g., 33B and 65B) to be finetuned on single 24/48GB GPUs. When designing a training recipe, combine paged optimizers with conservative batching and carefully chosen checkpointing strategies to get the best mix of stability and throughput.

Concluding remark
Paged optimizers leverage unified memory to make occasional oversubscription of device memory safe and transparent by storing optimizer states in pageable host-backed memory. This enables practical, error-free finetuning of very large quantized models on single GPUs by avoiding crashes from transient spikes caused by long-context minibatches and recomputation due to checkpointing. In typical settings where page migrations are rare, the runtime overhead is minimal, but as with any paging system, frequent migrations will slow training and should be diagnosed and mitigated through batching and checkpointing adjustments.
