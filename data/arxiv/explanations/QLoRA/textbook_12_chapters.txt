\title{A Textbook about the Paper: QLoRA (12 chapters)}

Efficient Finetuning of LLMs: Motivation, Challenges, and Contributions

# Why finetune LLMs: improving capabilities, adding/removing behaviors
Finetuning is the standard tool for adapting large pretrained language models (LLMs) to new tasks and requirements. A pretrained model captures a broad distribution over language, but finetuning lets practitioners steer that model toward specific abilities (for example, higher accuracy on domain tasks), desirable behaviors (for example, helpfulness and following instructions), or away from undesirable behaviors (for example, toxicity or hallucination tendencies). Across recent work, finetuning has been shown to be highly effective for improving few-shot and zero-shot behavior, for enabling instruction following, and for aligning models to human preferences. In practice this takes the form of updating model parameters (or a small subset thereof) using supervised examples, reinforcement learning from human feedback, or other objectives so that the model produces outputs that better match a downstream desideratum.

Despite these clear benefits, finetuning large LLMs is expensive in computation and — importantly for this chapter — in memory. Modern LLMs with tens of billions of parameters present a severe resource barrier: storing the model weights, activations, and optimizer state for gradient-based finetuning can require hundreds of gigabytes of GPU memory. This cost both restricts what individual researchers and small teams can explore and biases development toward organizations with large-scale compute infrastructures. Reducing the memory footprint of finetuning without sacrificing final task performance is therefore critical to broadening access to high-quality model adaptation.

# The memory wall: >780 GB for 16-bit finetuning of LLaMA-65B vs <48 GB with QLoRA
To make the memory problem concrete, consider a representative large model: LLaMA with 65 billion parameters. A straightforward 16-bit (commonly BF16 or FP16) finetuning run of such a model requires far more GPU memory than is available on typical single-GPU systems. The paper reports that regular 16-bit finetuning of LLaMA-65B needs more than 780\,GB of GPU memory. This figure includes the memory needed to store model parameters, activations, optimizer states, and gradients during training.

QLoRA is presented as a solution that collapses that enormous memory requirement down into a range that fits a single high-memory GPU. Specifically, QLoRA reduces average finetuning memory from greater than 780\,GB to less than 48\,GB for a 65B model, enabling finetuning on a single 48\,GB GPU. This is not a marginal improvement; it is a transformative reduction that opens up large-model finetuning to researchers and practitioners with modest hardware.

How is this achieved? The high-level idea is to store the pretrained base model in a very low-precision format (4-bit) and to avoid updating those stored weights during finetuning. Instead, all learnable adaptation parameters are small "adapter" modules stored and updated in higher precision. Critically, gradients are backpropagated through the frozen, quantized base model into the higher-precision adapters. This combination yields drastically lower storage costs for the base model while preserving the ability to adapt via the adapters.

# Key idea: backprop through a frozen 4-bit base model into low-rank adapters
The central architectural idea of QLoRA is to combine aggressive quantization of the frozen pretrained weights with parameter-efficient finetuning via Low-Rank Adapters (LoRA). LoRA augments a linear layer's computation with a small, trainable low-rank component. For a linear projection with input \(\mathbf{X}\), weight \(\mathbf{W}\), and output \(\mathbf{Y}\), the LoRA augmentation is usually written as

\[
\mathbf{Y} = \mathbf{X}\mathbf{W} + s\,\mathbf{X}\mathbf{L}_1\mathbf{L}_2,
\]

where \(\mathbf{L}_1\in\mathbb{R}^{h\times r}\) and \(\mathbf{L}_2\in\mathbb{R}^{r\times o}\) are the low-rank adapter matrices of rank \(r\), and \(s\) is a scalar scale factor. In standard LoRA usage the large weight matrix \(\mathbf{W}\) remains frozen and only \(\mathbf{L}_1,\mathbf{L}_2\) are learned, which already reduces the number of trainable parameters.

QLoRA pushes this idea further by storing the frozen \(\mathbf{W}\) at 4-bit precision and backpropagating through the quantized representation during training so that gradients flowing from the loss reach the LoRA adapters. Concretely, each time a weight matrix stored in a low-precision format is used in the forward (and backward) pass, it is dequantized into a higher-precision computation format (the paper uses BFloat16) for matrix multiplication and gradient computation. The adapters themselves live and update in the higher-precision computation format.

Thus QLoRA has two precisions in play: a very low-precision storage format for the frozen base model weights, and a higher-precision computation and adapter-parameter format for doing the actual arithmetic in forward/backward passes. This design drastically cuts the memory footprint for storing the base model while preserving numerical fidelity where it matters for learning (the adapter updates and computations).

# Contributions: NF4 data type, Double Quantization, Paged Optimizers
QLoRA introduces three technical innovations that together make 4-bit finetuning practical and high-fidelity: the 4-bit NormalFloat (NF4) data type, Double Quantization (DQ) for reducing the overhead of quantization constants, and Paged Optimizers for smoothing memory spikes during training.

4-bit NormalFloat (NF4). Standard uniform integer or floating-point quantization does not exploit the actual distribution of pretrained weights. The NF4 data type is designed specifically for zero-mean normal distributions, which is the typical empirical shape of pretrained model weights. The idea is information-theoretic: for a tensor whose values are distributed approximately \(N(0,\sigma^2)\), the quantization bins that minimize expected distortion are obtained by using quantiles of the normal distribution. NF4 is constructed by estimating the quantiles of a standard normal \(N(0,1)\), mapping those quantiles into the normalized range \([-1,1]\) of the 4-bit data type, and then quantizing each weight block after rescaling the block to match that range. Formally, the representative values \(q_i\) of the \(k\)-bit NF data type are obtained by

\[
q_i = \tfrac{1}{2}\left( Q_X\!\left(\tfrac{i}{2^k+1}\right) + Q_X\!\left(\tfrac{i+1}{2^k+1}\right)\right),
\]

where \(Q_X(\cdot)\) is the quantile function of the standard normal distribution. NF4 further uses an asymmetric construction to guarantee an exact discrete representation of zero (a zeropoint), which is important for padding and other exact-zero values. Empirically, NF4 outperforms other 4-bit choices such as 4-bit integers or 4-bit floats on post-quantization accuracy and perplexity.

Double Quantization (DQ). Fine-grained block-wise quantization typically requires storing a floating-point quantization constant per block (the rescaling factor or "quantization constant"). For small block sizes (which are important for accurate 4-bit quantization) the per-block constants add a significant memory overhead. Double Quantization reduces that overhead by treating those per-block constants themselves as a vector to be quantized a second time using an 8-bit representation. In the two-level scheme the first-level quantization produces the low-bit stored weights and a set of 32-bit per-block constants \(c_2^{\text{FP32}}\). The second-level quantization compresses the \(c_2^{\text{FP32}}\) into 8-bit values \(c_2^{\text{FP8}}\) together with a second-level FP32 constant \(c_1^{\text{FP32}}\). Because the per-block constants are positive, the paper centers them by subtracting the mean before symmetric quantization. With typical choices (block size 64 for the weights and 256 for the second-level constants) the average cost per parameter of quantization constants falls dramatically. For a blocksize of 64, the naive single-level cost is

\[
\frac{32}{64} = 0.5 \text{ bits per parameter},
\]

while the double-quantized cost becomes

\[
\frac{8}{64} + \frac{32}{64\cdot 256} = 0.127 \text{ bits per parameter},
\]

a reduction of approximately \(0.373\) bits per parameter (around 3\,GB for a 65B model).

Paged Optimizers. Even with aggressive weight compression, optimizer state (moments, momentum buffers, etc.) and activation gradients can cause transient memory spikes that lead to out-of-memory errors, especially when processing long sequences or large batch sizes. Paged Optimizers leverage NVIDIA unified memory to allocate optimizer state in pageable memory. When the GPU would otherwise run out of memory, pages are automatically moved to CPU RAM and paged back as needed. This prevents rare but potentially fatal spikes in GPU memory demand during training. In practice, Paged Optimizers allow training large models on a single high-memory GPU without catastrophic OOM failures during gradient checkpointing and long-sequence processing.

Putting these pieces together, a single QLoRA linear layer forward is written as

\[
\mathbf{Y}^{\text{BF16}} = \mathbf{X}^{\text{BF16}}\,\text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{NF4}}) \;+\; \mathbf{X}^{\text{BF16}}\mathbf{L}_1^{\text{BF16}}\mathbf{L}_2^{\text{BF16}},
\]

with the double dequantization defined by

\[
\text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}}) \;=\; \text{dequant}(\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}), \mathbf{W}^{\text{4bit}}) \;=\; \mathbf{W}^{\text{BF16}}.
\]

In words: the stored k-bit NF4 weights are dequantized using the double-quantized constants into the BF16 computation format for matrix multiplication, and the LoRA adapter term is added in BF16. During training, gradients are computed and backpropagated through the dequantized computation into the LoRA parameters; gradients are not computed for the frozen, stored 4-bit weights.

# Headline results: Guanaco 65B at 99.3% of ChatGPT on Vicuna; finetuning in 24 hours on a single GPU
The empirical payoff for these technical innovations is substantial. Using QLoRA, the authors train a family of instruction-finetuned models called Guanaco. Key headline results include:

- QLoRA enables finetuning of a 65B parameter model on a single 48\,GB GPU while preserving full 16-bit finetuning task performance. The paper reports reducing the average memory requirement for 65B finetuning from more than 780\,GB to under 48\,GB.

- Guanaco 65B, finetuned with QLoRA on the OASST1 dataset variant, achieves 99.3\% of the performance level of ChatGPT on the Vicuna benchmark (Vicuna evaluates instruction-following and conversational quality using GPT-4 and human-style judgments). This level of performance is achieved with only 24 hours of finetuning on a single GPU.

- Guanaco 33B and 65B attain Elo-based tournament performance competitive with ChatGPT and second only to GPT-4 in human and GPT-4 evaluations reported in the paper. The 33B model can be trained on consumer GPUs (24\,GB) in under 12 hours; the 7B Guanaco fits into about 5\,GB at inference time and outperforms a larger Alpaca model on Vicuna.

- Beyond a single model, QLoRA enables large-scale experimental throughput: the paper reports training more than 1,000 models across eight instruction datasets, multiple model families (LLaMA, T5), and a wide range of parameter counts from 80M to 65B. This breadth of exploration would have been infeasible with standard 16-bit finetuning due to memory constraints.

The authors also provide careful ablations showing that QLoRA with NF4 and Double Quantization matches or recovers 16-bit LoRA and full 16-bit finetuning performance across tasks including GLUE, Super-NaturalInstructions, and 5-shot MMLU. These results establish that aggressive storage compression, when combined with adapter-based learning and the NF4 + DQ + Paged Optimizers engineering, does not force a trade-off in downstream task accuracy.

# Accessibility implications: finetuning 33B on consumer GPUs; open-source code and kernels
One of the most important practical consequences of QLoRA is democratization of large-model finetuning. Prior to QLoRA, finetuning 33B–65B parameter models required many GPUs and large aggregate memory. With QLoRA, a 33B model can be finetuned on a single 24\,GB consumer GPU in less than 12 hours, and a 65B model can be finetuned on a single 48\,GB professional GPU in about a day. The paper emphasizes that this capacity opens up research avenues that were previously out of reach for individual researchers and small labs.

To maximize impact and reproducibility, the authors release their code, trained adapter weights, and CUDA kernels necessary for 4-bit training. The innovations (NF4 format, Double Quantization approach, and Paged Optimizers) are integrated into a public tooling stack and are available in repositories shared alongside the work. By providing both the software and dozens of trained adapters across multiple base model sizes and instruction datasets, the project makes it straightforward for others to adapt large pretrained models to their own tasks with modest hardware.

Taken together, QLoRA provides an operational recipe: store the base model in a carefully designed 4-bit format (NF4), compress the per-block quantization metadata via Double Quantization, place optimizer state into pageable memory to avoid transient OOMs, and perform finetuning by training low-rank adapters while backpropagating through the dequantized computation. The result is orders-of-magnitude lower memory footprint for finetuning without observable degradation in task or conversational performance relative to 16-bit baselines — effectively lowering the memory wall and enabling broad access to high-quality LLM finetuning.

Preliminaries: Finetuning, Memory Accounting, and Parameter-Efficient Methods

# Full-model finetuning vs parameter-efficient finetuning (PEFT)

Full-model finetuning means taking a pretrained model and updating all of its parameters by backpropagating the training loss through the entire network. In practice, for very large language models (LLMs) this is extremely memory- and compute-intensive. The paper gives a striking example: fully finetuning a 65B parameter LLaMA model in 16-bit precision requires more than 780 GB of GPU memory. That enormous requirement arises because every parameter typically needs to be stored, its optimizer states maintained, and the activations/gradients from the forward and backward passes held in memory.

Parameter-efficient finetuning (PEFT) trades off the number of trainable parameters for drastically smaller memory footprints. PEFT methods keep the pretrained model weights frozen and introduce a relatively small set of additional trainable parameters (often called adapters) that modify the model’s computations. During training, gradients flow back into these adapter parameters and the optimizer updates only them. Because the adapter parameter count is tiny compared to the full model, PEFT methods can make finetuning feasible on much smaller hardware.

The paper focuses on one PEFT technique, Low-rank Adapters (LoRA), and shows a key practical insight: although the adapter parameters are very small in size, most of the training memory cost does not come from the adapter parameters themselves. Instead, it comes from activations and activation gradients. This observation motivates design choices (e.g., where to place adapters and how many to add) that prioritize reducing activation-related memory rather than minimizing the adapter parameter count.

# Where memory goes: weights, optimizer states, activations, and activation gradients

Understanding memory use during training requires separating the major consumers of memory:

- Model parameters (weights): the stored values of the pretrained model and any added trainable parameters (adapters). If weights are stored in 16-bit floats, they consume twice the memory of 8-bit storage; quantization can reduce this storage further (e.g., QLoRA stores base model weights in 4-bit).

- Optimizer states: many optimizers keep per-parameter state such as momentum and second-moment estimates (for example, Adam-type optimizers store at least two floating tensors per parameter). These optimizer states often dominate the memory footprint for full-model finetuning because they are proportional to the number of trainable parameters and are typically stored at full precision.

- Activations (forward pass): intermediate layer outputs produced during the forward pass are needed during the backward pass unless recomputed. Activations grow with model depth, batch size, and sequence length and are one of the primary drivers of GPU memory usage.

- Activation gradients (backward pass): during backpropagation the gradients of the loss with respect to intermediate activations are accumulated. If activations are kept in memory for the backward pass, their gradients also impose memory cost. Even when only a small fraction of the model parameters are trainable (as in PEFT), activation gradients remain necessary to compute parameter gradients for the adapters because gradients must still flow through frozen weights to reach the adapter inputs.

The paper emphasizes that activation and activation-gradient memory dominate for typical PEFT setups. That is why reducing parameter count alone—while helpful for storage—does not by itself make finetuning cheap unless activations and their gradients are also managed.

# Gradient checkpointing and its impact on activation gradient memory

Gradient checkpointing is a standard memory–compute tradeoff strategy used during training. The idea is to avoid storing all intermediate activations during the forward pass; instead, only a subset of activations ("checkpoints") are saved. During the backward pass the missing activations are recomputed on the fly by rerunning parts of the forward computation. This saves memory at the cost of extra compute.

In the context of PEFT and LoRA, gradient checkpointing has a concrete and substantial effect on memory usage for activation gradients. The paper reports a specific empirical result for a 7B LLaMA model finetuned on FLAN v2 with LoRA: without gradient checkpointing the LoRA input gradients occupy about 567 MB, whereas when gradient checkpointing is used the input gradients reduce to an average of 18 MB per sequence. This dramatic reduction demonstrates that checkpointing can turn activation-gradient memory from a dominant cost into a manageable one—especially important when trying to finetune large base models with minimal extra parameters.

However, checkpointing does not eliminate activation memory entirely; it shifts memory pressure into recomputation time. There are also occasional memory spikes during optimizer steps (for example, when optimizer states are brought into GPU memory), which brings us to the need for additional mechanisms such as paged optimizers (described in the QLoRA paper) that can avoid out-of-memory failures by paging optimizer state between CPU and GPU.

# LoRA basics: factorized adapters and the linear layer augmentation Y = XW + s X L1 L2

Low-rank Adapters (LoRA) are a PEFT technique that injects a small trainable low-rank update into linear projection layers. The core idea is to keep the original weight matrix frozen and augment the linear mapping with a low-rank parameterized term that can be trained cheaply.

Consider a standard linear projection computed as $\mathbf{Y} = \mathbf{X}\mathbf{W}$ where $\mathbf{X}\in\mathbb{R}^{b\times h}$ is the input activation batch and $\mathbf{W}\in\mathbb{R}^{h\times o}$ is the weight matrix. LoRA augments this with a factorized adapter of rank $r$:

\[
\mathbf{Y} = \mathbf{X}\mathbf{W} + s\,\mathbf{X}\mathbf{L}_1\mathbf{L}_2,
\]

where $\mathbf{L}_1\in\mathbb{R}^{h\times r}$ and $\mathbf{L}_2\in\mathbb{R}^{r\times o}$ are the low-rank adapter matrices, and $s$ is a scalar scaling factor. Because $r$ is chosen much smaller than $h$ and $o$, the additional trainable parameters are a tiny fraction of the original weight count.

Training proceeds by backpropagating the loss through the frozen $\mathbf{W}$ and into the adapter matrices $\mathbf{L}_1,\mathbf{L}_2$. Crucially, even though $\mathbf{W}$ is fixed (not updated), gradients must flow through the $\mathbf{W}$ computations in the backward pass to reach the adapter inputs. That is, the backward pass computes derivatives with respect to the inputs of the frozen layers as part of the chain that produces $\partial E/\partial \mathbf{L}_i$ for adapter updates. This is why activation-gradient memory remains relevant in PEFT setups — the adapters are small, but the backwards computation still needs information flowing through the pretrained layers.

LoRA's design makes it simple to add these adapters to many or all linear layers in a transformer. The paper finds an important empirical point about LoRA placement and coverage (more on this in the implications section): applying LoRA only to a couple of attention projections is often insufficient to match full finetuning performance on larger base models; adding adapters more broadly can be necessary to recover full-model finetuning accuracy.

# Memory breakdown example (7B LLaMA): LoRA params (~26 MB) vs input gradients (~567 MB) vs 4-bit base (~5,048 MB)

Concrete numbers are helpful to make the preceding points tangible. The paper reports a memory breakdown for a 7B LLaMA model finetuned with LoRA on FLAN v2 under a small-batch setting (batch size 1). With LoRA weights set to an amount commonly used in practice (equivalent to about 0.2% of the original model weights), the measured memory footprint is:

- LoRA parameters themselves: approximately 26 MB. This is the storage size for the actual trainable adapter weights.

- LoRA input gradients (without gradient checkpointing): approximately 567 MB. These are gradients at the inputs to the adapter modules needed to compute $\partial E/\partial \mathbf{L}_i$.

- LoRA input gradients (with gradient checkpointing): reduced to an average of about 18 MB per sequence. This shows how much checkpointing can reduce the activation-gradient memory associated with adapters.

- 4-bit base model storage: about 5,048 MB (roughly 5 GB). This is the memory used to store the quantized base model weights in 4-bit format (as used in QLoRA), demonstrating how quantization can shrink the model storage drastically compared to 16-bit storage.

These numbers highlight two things. First, the raw adapter parameter size (26 MB) is negligible relative to other costs. Second, activation gradients (567 MB without checkpointing, 18 MB with checkpointing) are much larger than the adapter parameters and comparable to or larger than the storage for a quantized base model. This is the central reason why PEFT must focus on activation management, not only on reducing the parameter count.

# Implication: number and placement of adapters often matter more than their size

Putting the memory accounting and LoRA mechanics together yields an important practical implication that the QLoRA paper emphasizes: because the memory cost of adapter parameters is tiny compared to activation and optimizer-related memory, it is usually acceptable to increase the number of adapters (for example, by adding adapters at every linear layer) without materially increasing the total training memory footprint. In other words, if the dominant costs are activations and optimizer states, reducing the adapter parameter count is not the most effective lever to improve overall memory usage.

Empirically, the paper shows that using LoRA only on a small subset of projections (the common practice of applying LoRA to query and value attention projections) is insufficient to match the performance of full-model finetuning for larger base models. The number and placement of LoRA adapters become the critical hyperparameters: adding adapters at more layers—i.e., increasing coverage—recovers the performance gap. Other LoRA hyperparameters, such as the projection rank $r$, are less sensitive (the paper found $r$ did not significantly affect performance in their ablations). Therefore, a practical recipe is to favor broad placement of small adapters over aggressively shrinking adapter size.

This principle underpins QLoRA's strategy: combine aggressive quantization of the base model weights (to shrink model storage) with comprehensive LoRA adapters (to restore or improve task performance) while relying on activation memory management techniques like gradient checkpointing and paged optimizers to control the remaining memory costs. That combined approach is what allows QLoRA to finetune models with tens of billions of parameters on a single 48GB GPU without giving up 16-bit finetuning performance.

In summary, when you design a finetuning approach for large models, remember the hierarchy of memory costs. Reducing parameter counts is useful, but unless you also manage activations and optimizer state memory, you will not unlock finetuning for very large models. PEFT methods such as LoRA let you shift where the trainable capacity lives (small adapters), but to realize their full benefit you must also address activation memory with checkpointing and other system-level techniques.

Quantization Fundamentals for LLMs

# Quantization and dequantization with scale (absmax) and rounding

Quantization is the process of mapping high-precision numerical values (for example, 32-bit floating point weights) into a lower-bit discrete representation. A simple and widely used approach rescales the original values so they fit the dynamic range of the low-bit representation and then rounds to the nearest representable level. Concretely, given a floating-point tensor $\mathbf{X}^{\text{FP32}}$ and an integer quantization target with range $[-M, M]$ (for example $M=127$ for signed Int8), a common per-tensor scheme uses the absolute-maximum (absmax) scale $c^{\text{FP32}}$ and then rounds:

\[
\mathbf{X}^{\text{Int}} = \operatorname{round}\!\left( c^{\text{FP32}} \cdot \mathbf{X}^{\text{FP32}} \right),\qquad
c^{\text{FP32}} = \frac{M}{\operatorname{absmax}(\mathbf{X}^{\text{FP32}})}.
\]

Dequantization is the inverse operation: recover a higher-precision approximation of the original tensor by dividing by the same scale,

\[
\operatorname{dequant}\!\big(c^{\text{FP32}},\,\mathbf{X}^{\text{Int}}\big) \;=\; \frac{\mathbf{X}^{\text{Int}}}{c^{\text{FP32}}}
\approx \mathbf{X}^{\text{FP32}}.
\]

This simple rescale-and-round formulation is the basis of most k-bit quantization schemes. It is straightforward to implement and fast at inference time: at runtime one can dequantize blocks of weights into a higher-precision computation format (or perform specialized low-precision kernels) and run matrix multiplications efficiently.

# Outliers and wasted bins; motivation for block-wise quantization

A key practical problem with per-tensor absmax quantization is sensitivity to outliers. If a single element of $\mathbf{X}$ has a magnitude much larger than the bulk of the distribution, the absmax scaling $c^{\text{FP32}}$ must grow so that this outlier maps into the representable range. That larger scale compresses the majority of values into a narrow subset of quantization bins, leaving many bins unused and causing large round-off errors for most elements. In other words, a single outlier causes most low-bit levels to be wasted on rare values rather than capturing the high-density regions of the distribution.

Block-wise quantization mitigates this problem by splitting a tensor into many smaller contiguous chunks (blocks) and computing an independent quantization scale for each block. By adapting the scale to a local subset of values, block-wise quantization prevents a single large outlier in one block from inflating the scale used in other blocks and thereby preserves effective utilization of quantization bins across the tensor.

Formally, flatten the tensor $\mathbf{X}\in\mathbb{R}^{b\times h}$ into a single linear sequence and partition it into $n$ contiguous blocks of size $B$ so that

\[
n = \frac{b\times h}{B}.
\]

Each block $i$ has its own quantization constant (scale) $c_i^{\text{FP32}}$ computed from the absmax (or another block-wise statistic) on that block and is quantized independently using the per-block scale. This block-wise scheme greatly reduces the distortion caused by localized outliers and is the standard practical approach for applying very low-bit quantization (e.g., 4-bit) to large weight matrices.

# Blocks, scales, and storage overhead of per-block constants

Block-wise quantization improves precision at the cost of extra storage for the per-block quantization constants. Each block requires at least one floating-point scalar $c_i$ to be stored, and the cost of these constants amortized per parameter depends on the chosen block size $B$ and the precision (bit-width) used to store the constants.

If a tensor has $N$ parameters and is split into $n = N/B$ blocks, then storing each block scale as a 32-bit float adds on average $32/B$ bits of overhead per parameter. The paper gives a concrete example: with a block size of $B=64$ and 32-bit per-block constants, the constants add

\[
\frac{32}{64} = 0.5\ \text{bits per parameter}
\]

to the memory footprint. For very small block sizes (which give finer local adaptation and higher quantization fidelity) this per-parameter overhead can be non-negligible, so there is a trade-off: smaller blocks improve quantization precision but increase memory overhead through more scale values.

To reduce this overhead while keeping small blocks, the paper introduces Double Quantization (described later), which quantizes the quantization constants themselves. That method reduces the effective bits spent per parameter for the scale terms substantially (the paper reports an example reduction from 0.5 bits to about 0.127 bits per parameter for a particular choice of second-level quantization).

# Quantization for inference vs training: stability issues in backprop

Most prior work and practical systems have focused on quantization for inference. Those methods aim to minimize accuracy loss when executing a quantized network in a forward pass: dequantize blocks into a higher-precision compute format, or use custom low-precision kernels, and run forward-only computations. However, quantization schemes that work well for inference can fail when used naively during training. The paper highlights that many inference-time quantization techniques "break down during training." There are two intertwined reasons for this fragility.

First, training requires stable gradient propagation. If weights are stored in a very low-bit format and the forward and backward computations are performed on that low-bit data directly (without careful dequantization and numerical precision), gradient estimates can become noisy or biased, leading to unstable or failed optimization. Second, many quantization schemes use operations or approximations (for example, approximate quantile estimation) that introduce additional non-differentiable behavior or approximation error which hurts backpropagation.

QLoRA sidesteps these training stability problems by combining two ideas: (1) keep the pretrained base model weights frozen and stored in a low-bit format, and (2) add a small set of trainable adapter parameters (LoRA) that are stored and updated in high precision. During both forward and backward passes, the frozen low-bit weights are dequantized into a higher-precision computation format (the paper uses BFloat16) so that the matrix multiplications and gradient calculations that involve the base weights are performed in that higher-precision compute type. Gradients are backpropagated through the dequantization and the frozen weights to the adapters, but no gradient updates are applied to the frozen base weights. This design preserves numerical stability for training while keeping the storage and memory footprint low because the large base weight tensors remain compressed on disk and in GPU memory.

Mathematically, for a single linear layer with inputs $\mathbf{X}$, quantized frozen weights $\mathbf{W}^{\text{k-bit}}$, and a LoRA adapter factorized as $\mathbf{L}_1\mathbf{L}_2$, the forward pass in QLoRA is

\[
\mathbf{Y}^{\text{BF16}} \;=\; \mathbf{X}^{\text{BF16}}\cdot \operatorname{doubleDequant}\big(c_1^{\text{FP32}},\,c_2^{\text{k-bit}},\,\mathbf{W}^{\text{k-bit}}\big)
\;+\; \mathbf{X}^{\text{BF16}}\mathbf{L}_1^{\text{BF16}}\mathbf{L}_2^{\text{BF16}},
\]

where the doubleDequant function (see below) dequantizes the stored low-bit representation into the BF16 compute format. During backpropagation, derivatives with respect to the adapter parameters are computed via the dequantized weights, but no gradients are accumulated for the compressed base weights themselves. This approach recovers stable training behavior while achieving major reductions in overall memory usage.

# Choices of data types (Int, FP, and custom types) and precision–performance trade-offs

There are multiple choices for the low-bit storage format used in quantization: integer (Int) formats, low-bit floating point (FP) formats, and bespoke, distribution-tailored custom types. Each choice impacts how well the quantized representation can capture the original weight distribution and therefore the final performance after quantization (and after any subsequent finetuning).

Integers (e.g., Int4) are simple and map uniformly spaced representable levels across the scaled range. Small floating-point formats (e.g., FP4) can represent values with varying spacing (relative dynamic range), which may suit distributions with outliers differently. But both standard Int and standard FP formats suffer from the fact that pretrained neural network weights are typically concentrated around zero with a roughly Gaussian shape; uniform bins or canonical FP bins may not allocate representational capacity where it matters most.

The paper introduces a tailored data type called k-bit NormalFloat (NFk), and in particular NF4 for 4-bit storage, that is information-theoretically optimal for zero-mean normally distributed data. The construction relies on quantile quantization for a standard normal distribution. The NFk data type is built by first computing the $2^k+1$ quantiles of the theoretical standard normal distribution $N(0,1)$ and then taking representative levels for the $2^k$ bins. Formally, the representative values $q_i$ are computed as:

\[
q_i \;=\; \frac{1}{2}\left( Q_X\!\left(\frac{i}{2^k+1}\right) + Q_X\!\left(\frac{i+1}{2^k+1}\right)\right),
\]

where $Q_X(\cdot)$ is the quantile function of $N(0,1)$. To ensure an exact representation of zero (important for padding and exact-zero elements), the construction makes the data type asymmetric in a controlled way: estimate quantiles separately for the negative side and the positive side (one with $2^{k-1}$ bins and the other with $2^{k-1}+1$), then unify the sets and remove duplicate zero, yielding $2^k$ levels with a discrete zero included. The resulting NFk types have equal expected occupancy of each quantization bin for truly normal data, which makes them information-theoretically optimal under that distributional assumption.

In practice, pretrained weight tensors are approximately zero-centered and roughly normal (the paper provides empirical evidence and appendices on normality). That enables an efficient quantization pipeline: scale each weight block so its standard deviation matches the NFk type’s effective range (mapping the block to $[-1,1]$), and then quantize using the precomputed NFk levels. Because the NFk levels are precomputed for the normal distribution, NF4 avoids expensive empirical quantile estimation at runtime and better preserves the important mid-range density of the weights compared to FP4 or Int4.

Empirically in the paper, NF4 gave consistently better post-quantization performance than FP4 and Int4 across many model families and sizes (125M–13B and up to 65B settings in other experiments). The paper also reports that Finetuning after quantization (QLoRA with NF4) can fully recover or match the performance of 16-bit finetuning in multiple benchmarks, whereas FP4 lagged by about a percentage point in some tests.

# Double Quantization: reducing per-block constant overhead without hurting quality

As discussed earlier, small block sizes improve quantization precision but inflate the memory spent on per-block scales. Double Quantization (DQ) is a practical strategy to reduce the storage cost of quantization constants by quantizing those constants themselves with a second, coarser quantization pass.

In DQ, the original per-block scales $c_2^{\text{FP32}}$ (for the first k-bit quantization of weights) are treated as the input tensor to a second quantization step. The second-level quantization compresses these $c_2$ values into a lower-precision format (for example, FP8) using a larger block size (for example, 256) because the scale values vary more slowly and require less locality-sensitive fidelity. The second step produces quantized scale values $c_2^{\text{FP8}}$ plus a handful of second-level constants $c_1^{\text{FP32}}$ required to dequantize back to FP32. Because the scale values are positive, the paper subtracts their mean to center them around zero before symmetric quantization to improve efficiency.

The paper gives a concrete arithmetic example: with first-level blocksize $B=64$ and storing first-level scales as FP32, the per-parameter overhead is $32/64=0.5$ bits. After double quantization where the second-level scales are stored as 8-bit floats with second-level blocksize 256, the amortized per-parameter overhead becomes

\[
\frac{8}{64} + \frac{32}{64\cdot 256} \;=\; 0.127\ \text{bits per parameter}.
\]

This reduces the constant overhead by about $0.373$ bits per parameter (which corresponds to several gigabytes for a 65B-parameter model) without observable degradation of downstream performance in the reported experiments.

# Putting it together: storage vs compute formats and the QLoRA forward pass

Practical low-precision finetuning separates storage format (how weights are kept in memory) from computation format (the precision used during actual matrix multiplications). QLoRA exemplifies this: the large pretrained base weights are stored in a highly compressed 4-bit NF4 format, while computation uses a higher-precision type (BFloat16). The small, trainable adapter parameters (LoRA) are stored and updated in high precision.

When a layer is executed, the system dequantizes the stored low-bit weights back into BF16 for computation. The paper defines a double dequantization routine: first dequantize the second-level quantized constants to get the first-level scales, and then dequantize the k-bit stored weights using those scales. Symbolically,

\[
\operatorname{doubleDequant}(c_1^{\text{FP32}},\,c_2^{\text{k-bit}},\,\mathbf{W}^{\text{k-bit}})
= \operatorname{dequant}\big(\operatorname{dequant}(c_1^{\text{FP32}},\,c_2^{\text{k-bit}}),\,\mathbf{W}^{\text{k-bit}}\big)
= \mathbf{W}^{\text{BF16}}.
\]

The full layer forward (with a single LoRA adapter) is

\[
\mathbf{Y}^{\text{BF16}} = \mathbf{X}^{\text{BF16}}\cdot \operatorname{doubleDequant}\big(c_1^{\text{FP32}},c_2^{\text{k-bit}},\mathbf{W}^{\text{k-bit}}\big)
+ \mathbf{X}^{\text{BF16}}\mathbf{L}_1^{\text{BF16}}\mathbf{L}_2^{\text{BF16}}.
\]

Only the adapter parameters $\mathbf{L}_1,\mathbf{L}_2$ receive parameter updates; gradients are backpropagated through the dequantized base weights into the adapters but are not accumulated to update the frozen base weight storage. This design obtains the stability advantages of higher-precision arithmetic in the compute path while preserving the memory economy of low-bit storage.

# Precision–performance trade-offs and practical guidelines

The available experiments and analyses in the paper support several practical conclusions about precision and data type choices for quantizing LLM weights:

- Small-block, low-bit quantization (e.g., 4-bit) is necessary to compress very large models effectively, but small blocks create storage overhead for scales. Double Quantization reduces that overhead significantly while keeping quantization quality.

- The distribution of pretrained weights (approximately zero-centered and near-Gaussian) motivates tailored quantizers. NFk (especially NF4) is constructed to be information-theoretically optimal for normal distributions and empirically outperforms both FP4 and Int4 in the reported evaluations.

- Inference-focused quantization methods do not automatically carry over to stable training. To train with compressed weights, one should dequantize into a higher-precision computation format and avoid updating the compressed weights directly. QLoRA follows this path by keeping the base weights frozen in compressed form, dequantizing to BF16 for forward/backward computations, and updating only small high-precision adapters (LoRA). This design recovers full 16-bit finetuning performance in many experiments while requiring much less GPU memory.

- There is a trade-off between quantization granularity (block size) and overhead: smaller blocks improve representational accuracy, larger blocks save memory on constants. Double Quantization offers a middle ground: keep small first-level blocks for fidelity, but compress the per-block scales using a second-level quantization with larger blocks and lower-bit formats.

Taken together, these principles guide practical compression of large language models: align the quantizer to the empirical distribution of weights (NFk for near-normal), use block-wise quantization to tame outliers, amortize scale costs carefully (consider double quantization), and decouple storage precision from computation precision to preserve training stability.

From LoRA to QLoRA: Backpropagating Through Quantized Bases

# Design goal: match 16-bit finetuning with 4-bit storage

The central engineering goal of QLoRA is simple to state but challenging to realize: achieve the same finetuning quality that one would obtain when finetuning a model in full 16-bit precision, while storing the pretrained base model weights in 4-bit form so that the memory footprint is dramatically smaller. This objective drives every design choice in QLoRA. On one hand we want to reduce storage cost and device memory usage so very large models (33B, 65B) can be finetuned on a single GPU. On the other hand we must avoid degrading predictive performance: the finetuned model after QLoRA should match the accuracy, perplexity, or downstream task scores of a comparable 16-bit finetuning procedure.

To meet this goal QLoRA combines three elements: (1) a carefully chosen low-precision storage format that preserves as much information as possible in 4 bits (the paper introduces NF4 for this purpose), (2) a computation path that uses higher-precision numeric types (BFloat16 / BrainFloat16) during the forward and backward passes, and (3) parameter-efficient finetuning via Low-Rank Adapters (LoRA), where only a small set of additional parameters is updated while the (quantized) pretrained base remains frozen. Together these choices give the memory advantages of aggressive quantization without giving up the numerical fidelity necessary for effective gradient-based optimization.

The paper demonstrates that with these components QLoRA can reduce the memory requirement for finetuning a 65B parameter model from more than 780 GB of GPU memory (a typical 16-bit full-finetuning requirement) down to less than 48 GB, while recovering full 16-bit finetuning performance on the tasks they evaluate. Achieving this in practice requires additional engineering (e.g., managing quantization constants efficiently and avoiding OOM spikes during checkpointing), but the high-level design objective remains matching 16-bit finetuning with 4-bit storage.

# Two precisions: 4-bit storage and 16-bit (BFloat16) compute

QLoRA explicitly separates storage precision from computation precision. The pretrained base weights are compressed and stored in a low-precision 4-bit format to minimize memory. Whenever those weights are needed for computation, they are dequantized into a higher-precision format — typically BFloat16 (also referred to as BrainFloat16 in the paper) — and all matrix multiplications and other numeric operations are performed in that higher-precision compute type.

This separation is important for two reasons. First, storing weights in 4 bits dramatically reduces the memory footprint of the model parameters, enabling single-GPU finetuning of models that otherwise require many GPUs. Second, performing the actual linear algebra in a 16-bit compute type preserves numerical stability and reduces rounding error during the forward and backward passes, which is critical to obtain useful gradients for the learnable adapters.

The quantization-dequantization pipeline can be thought of in two stages for each stored weight block: a compact k-bit representation for storage, and a dequantized BF16 tensor for computation. In QLoRA, when a linear layer is executed the stored k-bit weights (for which QLoRA uses NF4) are dequantized on-the-fly into BF16 and used in the matrix multiply. For example, the QLoRA forward computation for a layer with a single LoRA adapter is:

\[
\mathbf{Y}^{\text{BF16}} = \mathbf{X}^{\text{BF16}} \; \text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}}) + \mathbf{X}^{\text{BF16}}\mathbf{L}_1^{\text{BF16}}\mathbf{L}_2^{\text{BF16}},
\]

where the first term is the base-layer output computed from the dequantized base weights and the second term is the LoRA adapter output. The dequantization produces a BF16 tensor so that both forward evaluation and backward differentiation operate in a numerically sufficient precision.

# Frozen 4-bit base: do not update base weights; update only LoRA parameters

A core design decision in QLoRA is to keep the base pretrained model weights frozen during finetuning. Instead of updating the full set of model parameters (which would require gradients and optimizer state for tens of billions of parameters), QLoRA attaches Low-Rank Adapters (LoRA) to relevant linear projections and updates only those adapter parameters. The original LoRA formulation augments a linear projection with a low-rank additive term:

\[
\mathbf{Y} = \mathbf{X}\mathbf{W} + s\,\mathbf{X}\mathbf{L}_1\mathbf{L}_2,
\]

where \(\mathbf{W}\) are the frozen base weights and \(\mathbf{L}_1,\mathbf{L}_2\) are low-rank matrices (rank \(r\)) that are learned; \(s\) is a scaling scalar. The LoRA parameters are small compared to the full model, and their gradients and optimizer state are cheap to store.

Keeping \(\mathbf{W}\) frozen has two practical benefits. Memory: we do not need optimizer state or updated weight copies for the base model, which greatly reduces GPU memory. Computation: since we only compute gradients for the adapters, the backward pass does not need to store or update large weight gradients. Conceptually, LoRA acts as a learned low-dimensional correction to the frozen base model, supplying the capacity necessary to adapt the model to a new task while avoiding the prohibitive memory overhead of full-model finetuning.

QLoRA exploits the fact that gradients can be backpropagated through the dequantized representation of the frozen base to reach the LoRA parameters. The frozen base is still part of the computational graph — it is merely read (after dequantization) — so its effect on the loss is captured and the adapters receive meaningful gradients that allow them to compensate for any information loss introduced by quantization.

# Per-use dequantization to BF16 for forward and backward passes

In QLoRA the quantized 4-bit base weights are not used directly in arithmetic; they are dequantized to a higher-precision compute format whenever they are needed. This happens both during the forward pass (to compute activations) and during the backward pass (to compute gradients that flow into the adapters). The dequantization is "per-use": weight blocks are stored compactly and expanded to BF16 only for the duration needed to compute the layer outputs and their derivatives.

The paper formalizes the dequantization as a double-step process when Double Quantization is applied. Let \(\mathbf{W}^{\text{k-bit}}\) denote the stored k-bit weight tensor, \(c_2^{\text{k-bit}}\) denote the quantized per-block scale constants (also stored in a compact format), and \(c_1^{\text{FP32}}\) denote a higher-level FP32 scale. The composition of the two dequantizations is written as:

\[
\text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}}) = \text{dequant}\big(\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}), \mathbf{W}^{\text{k-bit}}\big) = \mathbf{W}^{\text{BF16}}.
\]

After this operation the computation proceeds with \(\mathbf{W}^{\text{BF16}}\) used in the layer's matrix multiplication. Because both forward activations and backward gradients are computed in BF16, the numerical fidelity of the gradient signal reaching the LoRA parameters is substantially higher than if the entire computation were performed in 4-bit arithmetic.

Practically, this dequantize-on-use strategy allows storage to remain tiny while preserving the numerical properties required for successful optimization. The QLoRA implementation uses block-wise quantization (for example, blocks of size 64 for \(\mathbf{W}\)) and stores the small per-block quantization constants compactly through Double Quantization (quantizing the quantization constants themselves) to further reduce overhead. Those design choices balance the trade-off between quantization precision and storage efficiency.

# Why this works: adapters recover performance lost to coarse quantization

At first glance it may seem unlikely that finite-capacity adapters — low-rank corrections that add only a small number of new parameters — can recover the performance lost by throwing away precision in the base model. The QLoRA paper presents both intuitive and empirical reasons why this actually succeeds.

Intuitively, pretrained large language model weights are highly structured: they are approximately zero-centered and often nearly normally distributed within weight blocks. QLoRA leverages that regularity by using a NormalFloat quantization (NF4) that is information-theoretically tailored to normally distributed data. That choice reduces the distortion introduced by representing weights in only 4 bits. Moreover, Double Quantization reduces the memory taken by quantization constants without worsening quantization error. With a careful quantization scheme, the dequantized BF16 representation used during computation retains sufficient fidelity so that the frozen base remains a useful functional backbone.

Even when quantization does introduce some loss, the LoRA adapters act as corrective terms that adjust model behavior in the directions that matter for the downstream task. Because LoRA applies small, learned low-rank updates at many or all linear layers, it can implement the function-space changes that full finetuning would have achieved, but in a much lower-dimensional parameter subspace. The paper finds empirically that to fully recover 16-bit finetuning performance, it is important to place LoRA adapters broadly across the network (not just on a few attention projections). When LoRA is applied to all linear transformer block layers, QLoRA matches full 16-bit finetuning on the benchmarks reported.

Formally, QLoRA computes outputs as

\[
\mathbf{Y}^{\text{BF16}} = \mathbf{X}^{\text{BF16}} \mathbf{W}^{\text{BF16}} + \mathbf{X}^{\text{BF16}} \mathbf{L}_1^{\text{BF16}} \mathbf{L}_2^{\text{BF16}},
\]

where \(\mathbf{W}^{\text{BF16}}\) is obtained by dequantizing the stored \(\mathbf{W}^{\text{k-bit}}\). Gradients are calculated with respect to the adapter parameters \(\mathbf{L}_1, \mathbf{L}_2\); the gradient \(\frac{\partial E}{\partial \mathbf{W}}\) for the base weight is not used for updates, but the computation of \(\frac{\partial E}{\partial \mathbf{L}_i}\) does depend on the accurate dequantized \(\mathbf{W}^{\text{BF16}}\) because the backward pass propagates through the same path used in the forward pass. In words: we backpropagate through the dequantized base (so the adapters receive useful gradients that reflect the frozen base behavior), but we only update the adapters.

Empirically, the paper shows that the combination of NF4 quantization, Double Quantization (for scale constants), dequantization to BF16 for computation, and LoRA adapters applied widely across the model enables QLoRA to match 16-bit full finetuning and 16-bit LoRA finetuning on a range of tasks and model scales. NF4 outperforms other 4-bit datatypes such as FP4 or Int4 in their experiments, and Double Quantization reduces the additional memory overhead of per-block scales with negligible effect on accuracy.

Finally, because most of the GPU memory used during finetuning comes from activation gradients and optimizer state — not from storing the base weights themselves — the frozen-weights-plus-LoRA design lets QLoRA concentrate memory on exactly what is needed for optimization (adapter gradients and activations) while keeping the enormous pretrained parameter tensor in a tiny storage format. That is why QLoRA succeeds in recovering 16-bit finetuning quality with a 4-bit stored base.

# Summary and practical takeaways

QLoRA achieves the ambitious goal of matching 16-bit finetuning performance while storing a pretrained base model in 4-bit form by combining (1) a high-fidelity 4-bit storage format (NF4) together with Double Quantization for compact scale storage, (2) dequantization to BF16 on every use so that forward and backward passes have sufficient numerical precision, and (3) parameter-efficient LoRA adapters that are the only learnable parameters during finetuning. The frozen base still participates in the computation and gradient propagation, but its weights are never updated; instead the adapters absorb the necessary task-specific adjustments. In practice, this design reduces memory usage by orders of magnitude and enables finetuning very large models on single GPUs while retaining 16-bit levels of performance on the evaluation benchmarks reported in the paper.

NormalFloat (NF4): An Information-Theoretically Optimal 4-bit Data Type

# Quantile quantization and equal bin occupancy
Quantile quantization is a family of quantization schemes that aim to allocate the limited number of representable values (quantization bins) so that each bin is expected to contain the same fraction of the input data. Intuitively, if a data distribution is known, one can place bin boundaries at the distribution's quantiles so that every bin receives equal probability mass. This equal-occupancy property is useful because it spreads representational precision where the data actually falls, rather than wasting many discrete codes on outliers or on ranges with almost no mass. In information-theoretic terms, for a fixed number of bins the equal-mass partition minimizes certain average-error measures under assumptions about the loss function and the data distribution, because it balances representation resources across the most frequently occurring values.

In practice, quantile quantization is often implemented by estimating empirical quantiles of an input tensor and then mapping each element to the nearest representative level for its quantile bin. For arbitrary tensors this requires computing or approximating the empirical cumulative distribution function, which can be expensive or noisy. Approximation errors in the quantile estimation can cause disproportionately large quantization errors for outliers, especially in very low-bit regimes such as 4-bit. The NormalFloat (NFk) family leverages the case where the underlying distribution is known (or closely approximated by a known family): instead of estimating empirical quantiles for each tensor, NFk uses precomputed theoretical quantiles for a target distribution, eliminating costly quantile estimation and its approximation errors.

# Normality of pretrained weights and rescaling to a fixed range
A key empirical observation used by NF4 is that pretrained neural network weights are often well approximated by a zero-centered normal distribution. Practitioners typically observe that the bulk of weight values follows a near-Gaussian shape centered at zero, with a standard deviation that varies between tensors. When this normality holds, one can transform each weight tensor to match a single reference distribution by an appropriate rescaling step.

Concretely, the NF approach rescales a weight tensor so that its values lie in the arbitrary canonical range $[-1,1]$ before applying the fixed normal-distribution quantization data type. This rescaling is commonly implemented by dividing the tensor by its absolute maximum (an absolute-max normalization), so that the largest magnitude maps to $\pm 1$. Rescaling standardizes the spread (standard deviation) of different tensors so that the precomputed theoretical quantiles for the standard normal distribution become applicable. Because the quantile structure of a normal distribution is fixed up to scale, once tensors are rescaled to the same bounded range, one can reuse the same set of representative levels (bins) for all tensors without computing new empirical quantiles per tensor. This avoids the computational expense and approximation noise associated with quantile estimation while retaining the equal-occupancy principle adapted to normality.

# Constructing NF4: quantiles of $N(0,1)$, normalization to $[-1, 1]$, and asymmetric bins for a discrete zero
NF4 is constructed by taking the theoretical quantiles of the standard normal distribution and using them to define a 4-bit quantization data type optimized for zero-centered normal data. The process has three main steps.

First, compute the $2^k$ representative levels for a $k$-bit data type by using the theoretical quantiles of the standard normal distribution $N(0,1)$. Because the normal quantile function is known in closed-form via the inverse cumulative distribution function, these quantiles can be computed exactly (up to numerical precision) once and reused.

Second, normalize these levels into the canonical range $[-1,1]$. In practice, a weight tensor is also normalized into $[-1,1]$ (for example by dividing by its absolute maximum), so that the theoretical quantiles and the normalized tensor range match. Effectively, this step rescales the tensor's standard deviation to align with the standard normal data type’s quantization intervals.

Third, because symmetric quantizations that split $2^k$ levels evenly around zero do not generally provide an exact discrete representation of zero (there may be no code exactly equal to zero), NF4 uses a deliberately asymmetric construction to guarantee a discrete zero level. Having a quantization code exactly equal to zero is important in practice: it allows padding tokens, exact zeros, and other exact-zero values to be represented without quantization error. The asymmetric construction for a $k$-bit NF data type is made by estimating quantiles for the negative side with $2^{k-1}$ bins and for the positive side with $2^{k-1}+1$ bins, then unifying the two sets of representatives and removing the duplicated zero so that one of the zero representations remains. This produces $2^k$ distinct levels that are centered around zero and include an exact zero code.

# Formula for $q_i$ via theoretical quantiles; implications for error
The representative levels of the NFk data type are defined in terms of the quantile function of the standard normal distribution. One convenient way to define the center of each bin is to average the quantile boundaries for contiguous quantile intervals. For a symmetric (non-asymmetric) $k$-bit construction, one can write the representative value $q_i$ for bin $i$ as

$${q_i} = \frac{1}{2}\left( Q_X\!\left(\frac{i}{2^k+1}\right) + Q_X\!\left(\frac{i+1}{2^k+1}\right)\right),$$

where $Q_X(\cdot)$ is the quantile (inverse cumulative distribution) function of $N(0,1)$ and $i$ indexes bins in sorted order. This formula places $q_i$ at the center of each equal-probability quantile interval of the standard normal distribution. When tensors are rescaled to match the NFk data type’s $[-1,1]$ range, mapping values to the nearest $q_i$ yields equal expected occupancy across bins for normally distributed data.

The error implications are intuitive: because the bins are aligned with the normal distribution’s quantiles, most bins lie where the density is highest and therefore represent that high-density mass with fine-grained resolution in the sense of equal expected sample counts per bin. Under the assumption that the tensor values approximately follow a normal distribution (after rescaling), this allocation of discrete codes minimizes average-case distortion that depends on occupancy. Additionally, using theoretical quantiles avoids the sampling noise that would be introduced by estimating empirical quantiles on every tensor, which is especially relevant when working at very low bit-widths where estimation noise can dominate.

The discrete-zero modification described earlier ensures that exact zeros (or padding) are represented without error, removing a class of systematic errors that would otherwise occur for tensors with many exact-zero entries.

# Empirical performance: NF4 vs FP4 vs Int4 on language modeling and zero-shot tasks
The QLoRA paper evaluates NF4 empirically by comparing it to other 4-bit data types such as 4-bit floating point (FP4) and 4-bit integers (Int4). These comparisons are performed across multiple model families (OPT, LLaMA, BLOOM, Pythia) and model sizes spanning the 125M to 13B range. Evaluations include language modeling perplexity as well as a suite of zero-shot tasks that probe generalization.

Across these experiments, NF4 consistently improves performance relative to FP4 and Int4. The paper reports that NF4 delivers significantly better post-quantization perplexities and zero-shot accuracies than the other 4-bit formats. Importantly, when NF4 is combined with the QLoRA finetuning procedure (i.e., finetuning adapter weights while backpropagating through the quantized base model), the empirical results show that NF4 with double quantization fully recovers the performance of 16-bit LoRA finetuning on downstream benchmarks such as MMLU for large LLaMA models. Conversely, FP4-based QLoRA lags behind by about one percentage point in MMLU in the reported experiments, illustrating the practical advantage of NF4’s data-type design for pretrained-weight distributions.

The empirical takeaway is that designing a low-bit datatype to match the expected weight distribution (normal) and ensuring a discrete zero both produce measurable gains in downstream predictive performance in language-modeling and few-shot evaluation settings.

# Block size selection (e.g., 64) and its effect on fidelity
NF4 is applied in a block-wise quantization scheme: large tensors are partitioned into contiguous blocks and each block is quantized independently with its own quantization scale. Block-wise quantization mitigates the influence of extreme outliers: if one large-magnitude weight appears in a tensor, quantizing the entire tensor with a single scale would compress the non-outlier values into few bins, but blockwise quantization confines such an outlier’s effect to its local block. Thus smaller block sizes yield higher fidelity because quantization scales better match local statistics.

That higher fidelity, however, comes with storage overhead. Each block requires storing a per-block quantization constant (scale). For example, with 32-bit floating-point constants and blocksize $B=64$, the per-parameter overhead attributable to these constants is $32/64 = 0.5$ bits on average. To reduce this overhead while keeping small blocks for accuracy, the paper introduces Double Quantization, which quantizes the quantization constants themselves (typically to 8-bit floats) and stores a second-level scale for those constants. With the choices reported in the paper (4-bit NF4 weights with blocksize 64, and 8-bit floats for the second-level quantization with blocksize 256 for the constants), the average per-parameter overhead decreases from $0.5$ bits to approximately $0.127$ bits, computed as

$$\frac{8}{64} + \frac{32}{64\cdot 256} = 0.127\ \text{bits},$$

a net reduction of $0.373$ bits per parameter (roughly 3 GB saved for a 65B-parameter model). The empirical results indicate that this double quantization does not degrade model quality when using NF4 for weights and FP8 for quantization constants.

In practice, the QLoRA work uses blocksize 64 for weight tensors to balance fidelity and overhead, and blocksize 256 for the second-level quantization of the quantization constants. This combination leverages the accuracy benefits of a small blocksize for weights while using a larger blocksize for constants where approximation is cheaper and less harmful.

# Closing remarks
NF4 is an instantiation of the general principle that quantization should be matched to the statistical structure of the data. By using theoretical quantiles of the standard normal distribution, rescaling tensors to a common range, and engineering an asymmetric bin layout to preserve an exact zero code, NF4 achieves an information-theoretically motivated and practically effective 4-bit data type for pretrained neural weights. Empirically, NF4 outperforms commonly used 4-bit formats (FP4 and Int4) on language-modeling perplexity and zero-shot tasks; when combined with blockwise quantization (blocksize 64) and double quantization of constants, NF4 enables high-fidelity low-bit storage with modest overhead and without measurable downstream performance degradation in QLoRA finetuning experiments.

Double Quantization: Compressing the Scales

# Why scales dominate overhead with small blocks
When a weight tensor is quantized block-wise, each block stores not only the low-bit representation of the weights but also a floating-point "scale" (quantization constant) that is needed to dequantize that block. If the block size is small, the number of blocks grows proportionally and the per-parameter cost of storing these scales can become a non-negligible part of the model footprint.

Concretely, consider a weight matrix partitioned into blocks of size $B$ (meaning one scale per contiguous block of $B$ parameters). If each scale is stored as a 32-bit float, the amortized storage cost of the scales is
\[
\text{bits per parameter from scales} = \frac{32}{B}.
\]
For a common choice of $B=64$, this is
\[
\frac{32}{64} = 0.5\ \text{bits per parameter}.
\]
Compare that to a 4-bit weight representation: the weights themselves contribute $4$ bits per parameter, but the scales add another $0.5$ bits/param as overhead — roughly a 12.5% relative increase over the pure weight storage. For very large models (tens of billions of parameters) this overhead translates to multiple gigabytes of memory just for the per-block scales. Thus, when block sizes must remain small for quantization accuracy, reducing the cost of storing scales becomes an important avenue for memory savings.

# Double Quantization workflow
Double Quantization (DQ) reduces the memory overhead of these per-block scales by applying a second, coarser quantization to the scales themselves. The two-stage pipeline looks like this in storage and dequantization:

1. First (base) quantization: each weight block of size $B$ is quantized into a low-bit representation (for example, 4-bit NF4). Each block also stores a first-level scale $c_2^{\text{FP32}}$ in 32-bit float form.

2. Second (scale) quantization: treat the array of first-level scales $\{c_2^{\text{FP32}}\}$ as the input to another block-wise quantization. Quantize these scale values into an 8-bit floating-point representation $c_2^{\text{FP8}}$ with a larger grouping block $G$ (for example, $G=256$): for every group of $G$ first-level scales we store one 32-bit second-level scale $c_1^{\text{FP32}}$ that will be used to dequantize those $G$ values.

Dequantization at runtime becomes a two-step operation (reproducing equation (7) from the paper):
\[
\text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}}) =
\text{dequant}\big(\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}), \mathbf{W}^{\text{k-bit}}\big),
\]
so that we first recover the per-block scale $c_2^{\text{FP32}}$ by dequantizing the stored $c_2^{\text{k-bit}}$ with the higher-level $c_1^{\text{FP32}}$, and then dequantize the weight block using that recovered $c_2^{\text{FP32}}$. In practice the paper uses NF4 for $\mathbf{W}^{\text{k-bit}}$, FP8 for $c_2^{\text{k-bit}}$, $B=64$ for weight blocks, and $G=256$ for grouping scales into second-level blocks.

This two-level representation compresses the (numerous) per-weight-block scales into smaller per-block integers/floats plus a much sparser set of higher-precision group scales, trading a little extra computation at dequantization time for substantial memory savings.

# Centering positive scales by subtracting the mean
An important practical detail is that the first-level scales $c_2^{\text{FP32}}$ are strictly positive quantities (they are absolute maxima or scale factors). Many efficient low-bit quantizers (and symmetric quantization schemes in general) are designed for zero-centered data and can make better use of the available representational bins when their input distribution is centered around zero.

To leverage symmetric quantization effectively on the positive-only $c_2^{\text{FP32}}$, the paper subtracts the mean of the $c_2$ values inside each second-level group before quantizing. Operationally, for each group of $G$ first-level scales:
1. Compute the group mean $\mu = \frac{1}{G}\sum_{i=1}^{G} c_{2,i}$.
2. Store $\mu$ as part of the group's second-level metadata (this is absorbed into the $c_1^{\text{FP32}}$ representation).
3. Quantize the centered values $c_{2,i} - \mu$ into the chosen k-bit format (FP8 here) using symmetric quantization.

Centering enables symmetric quantizers to exploit their full dynamic range (positive and negative bins) and typically yields lower quantization error than naively quantizing strictly-positive data with an asymmetric scheme. The extra bookkeeping (storing group means or folding them into the second-level scale) is negligible compared to the memory savings from compressing the vast number of per-block scales.

# Memory math: from 0.5 to ~0.127 bits/param
We can express the storage cost from scales under Double Quantization and compute the numeric savings with the parameters used in the paper.

Let
- $B$ be the weight block size (number of parameters per weight-scale). The paper uses $B=64$.
- $b_2$ be the bits used to store the quantized first-level scale per weight block (after the second quantization). The paper uses $b_2=8$ (FP8).
- $b_1$ be the bits used to store the second-level group scale per group of $G$ first-level scales. The paper uses $b_1=32$ (FP32) and $G=256$.

Then the amortized bits-per-parameter cost for the two-level scale storage is
\[
\text{bits/param} = \frac{b_2}{B} + \frac{b_1}{B \cdot G}.
\]
Plugging in the paper's choices $B=64$, $b_2=8$, $b_1=32$, $G=256$ gives
\[
\text{bits/param} = \frac{8}{64} + \frac{32}{64 \cdot 256}
= 0.125 + \frac{32}{16384}
= 0.125 + 0.001953125
\approx 0.12695 \approx 0.127\ \text{bits/parameter}.
\]

Compare this to the original single-level cost of $\frac{32}{B} = 0.5$ bits/param for $B=64$. The reduction in overhead per parameter is
\[
0.5 - 0.127 = 0.373\ \text{bits/parameter}.
\]

For a 65 billion parameter model, this per-parameter saving corresponds to approximately
\[
0.373 \times 65\times 10^{9} \ \text{bits}
= 24.245\times 10^{9} \ \text{bits}
\approx \frac{24.245\times 10^{9}}{8} \ \text{bytes}
\approx 3.03\times 10^{9} \ \text{bytes} \approx 3\ \text{GB}.
\]
Thus, double quantization converts the scales overhead for a 65B model from about 4 GB (0.5 bits/param × 65B / 8) down to roughly 1 GB (0.127 bits/param × 65B / 8), saving on the order of 3 GB overall. These numbers match the paper's reported ballpark benefit and illustrate how a small per-parameter bit saving accumulates to several gigabytes at very large scales.

# Empirical result: no performance degradation with double quantization
A crucial practical question is whether this extra compression harms model quality. The paper reports that using 8-bit quantization for the first-level scales (the $c_2$ values) with the larger grouping factor ($G=256$) produces no observable degradation in downstream performance compared to storing the $c_2$ values in full 32-bit precision. In other words, the two-stage scheme (FP8 for $c_2$, grouped FP32 for $c_1$) yields the same empirical accuracy/perplexity as the single-level scheme while substantially reducing memory overhead.

Intuitively, this empirical success is plausible because the scale values themselves typically vary smoothly across many small weight blocks; a coarse-grained representation of those scales (when corrected by a per-group higher-precision value) preserves enough fidelity for accurate dequantization of the base weights. The centering step (subtracting the mean per group) further improves the effective resolution of the $c_2$ quantization by making the distribution zero-centered and better suited to symmetric low-bit representations.

Implementation-wise, the paper integrates this pipeline so that at runtime the model dequantizes each block by first reconstructing its $c_2^{\text{FP32}}$ via the group-level $c_1^{\text{FP32}}$ and the stored $c_2^{\text{FP8}}$, and then dequantizing the k-bit weight vector for that block. The computational overhead of the added dequantization step is small compared to the matrix-multiply work and is a favorable trade-off for the memory savings achieved.

In summary, Double Quantization compresses the dominant scale overhead introduced by fine-grained block quantization, reduces per-parameter scale storage from $32/B$ to approximately $b_2/B + b_1/(B\cdot G)$, and — with the design choices used in the paper ($B=64$, $b_2=8$, $b_1=32$, $G=256$ and mean-centering of positive scales) — cuts the per-parameter scale cost from $0.5$ bits to $\approx 0.127$ bits, saving roughly $0.373$ bits/parameter (about 3 GB for a 65B model) with no measurable performance loss.

Paged Optimizers: Avoiding OOM Spikes at Scale

# Unified memory concept and page-to-page CPU-GPU transfers

At the core of the paged-optimizer design in QLoRA is the use of NVIDIA unified memory, a system-level facility that makes the CPU and GPU address spaces appear as one contiguous memory region. Conceptually this behaves like the familiar operating-system virtual memory abstraction: when a program accesses a memory page that is not resident on the local device, the runtime automatically moves (pages) that page between the two devices. In the GPU + CPU setting that QLoRA exploits, unified memory performs automatic page-to-page transfers between GPU device memory and host (CPU) RAM so that GPU code can continue running even when its working set temporarily exceeds the GPU DRAM capacity.

QLoRA leverages this automatic paging to avoid hard out-of-memory (OOM) failures during rare memory spikes. Instead of failing when the instantaneous peak memory exceeds the GPU capacity, the runtime evicts seldom-used pages from GPU DRAM to host memory and later brings them back on demand. The evictions and fetches are managed by the unified-memory system rather than by explicit programmer-managed copies, which simplifies the implementation: one can allocate certain large arrays in paged (unified) memory and let the runtime transparently move them as needed.

# Where spikes come from: long sequences and gradient checkpointing

To understand why paging helps, we must identify the source of transient memory spikes during training. In QLoRA the bulk of the persistent memory footprint is the quantized base model storage (kept in 4-bit NF4) and the comparatively small LoRA adapter parameters. However, during the forward and backward passes training still needs temporary working memory: activation tensors, activation gradients, and optimizer state for trainable parameters. Two factors in large-model training commonly produce momentary peaks that exceed the steady-state memory footprint.

First, processing very long sequences increases the amount of activation and activation-gradient memory required for a single mini-batch. Activation memory grows with sequence length and with the number of layers, so a single example with an unusually long context can produce a spike that would otherwise cause an OOM. Second, gradient checkpointing—an important technique to reduce steady-state activation memory by recomputing intermediate activations on the backward pass—changes the memory/time tradeoff but can itself produce transient peaks. With gradient checkpointing the backward pass recomputes fragments of the forward computation; the recomputation phases can temporarily require additional memory for recomputed activations and intermediate results, producing short-lived spikes that exceed the GPU capacity even though the average memory use remains under the limit.

Because these spikes tend to be infrequent (for example, only when particular long-sequence mini-batches are seen), a paging mechanism that tolerates occasional overcommitment of GPU memory is a natural match: rather than provisioning GPU DRAM large enough for the worst-case instantaneous demand, the runtime can offload large, infrequently accessed arrays and thereby absorb the spike without crashing.

# What gets paged: optimizer states eviction and prefetch back for updates

The QLoRA design chooses the optimizer states as the primary target for unified-memory placement. Optimizer state tensors—moments, accumulators, or other per-parameter states required by adaptive optimizers—represent a large fraction of training memory but are not needed continuously during the forward and backward passes. In typical training, optimizer state is required only during the optimizer update step after gradients have been accumulated; during the forward and backward computations the optimizer state need not be resident on the GPU.

By allocating optimizer states in unified (paged) memory, QLoRA allows them to be evicted to host RAM automatically when the GPU is pressed for space during expensive recomputation or long-sequence processing. When the optimizer update is due, the unified memory system will page the relevant optimizer pages back into GPU memory so that the update can be performed. In effect, the optimizer states are dynamically resident on whichever device the runtime deems appropriate at the moment.

This arrangement is what the paper refers to as “Paged Optimizers”: the optimizer state is treated as paged memory that the system may transparently move between CPU and GPU. The programmer allocates the optimizer data in unified memory and relies on the runtime to evict and fetch pages. Because optimizer updates happen in specific phases of the training loop, the paging pattern tends to be predictable: optimizer pages are idle while forward/backward computations are running (and can be evicted), then prefetched or faulted back during the optimizer step.

# Runtime considerations: 65B on 48GB GPU; batch size 16 shows parity with regular optimizers

The paper reports a practical runtime observation for the largest models QLoRA targets: using paged optimizers enabled running 65B-parameter finetuning on a single 48GB GPU without unhandled OOMs. In particular, an empirical runtime analysis for a 65B model on a 48GB GPU with a batch size of 16 showed that paged optimizers provide the same training speed as regular optimizers under those conditions. In other words, when paging is only rarely triggered, the end-to-end throughput matches the baseline (non-paged) performance.

Two important qualifications are emphasized. First, the paging behavior that allows this parity only occurs when paging events are rare; the unified-memory transfers are inexpensive enough in the observed setup that they do not reduce throughput compared to a configuration where all optimizer state permanently resides on the GPU. Second, the authors did not provide exhaustive, hard measurements across all workloads; they note that paging only occurs in practice for mini-batches with long sequence lengths and that future work should systematically characterize cases where paging can induce slowdowns. The reported parity at batch size 16 and 65B on 48GB is therefore an encouraging demonstration rather than a formal performance guarantee for every training configuration.

# Practical tips: detecting and mitigating slowdowns for rare spike patterns

The paper’s treatment of paged optimizers focuses on the principle and the successful application to large-model QLoRA training; it does not publish a comprehensive recipe for all edge cases. Nevertheless, a few practical implications follow from the design and empirical observations in the paper.

Because unified memory automatically moves pages between host and device, the cost of paging shows up as extra host–device transfers during training. In practice these transfers are infrequent when spikes are rare (for example, only on occasional long-sequence batches), and in those circumstances the runtime overhead is small enough that training speed remains comparable to a non-paged run. However, if your workload produces many spikes (for example, frequent long-sequence examples, or other patterns that cause repeated recomputation peaks), paging can become common and introduce measurable slowdowns.

Accordingly, it is advisable to treat paged optimizers as a safety valve for rare, unavoidable spikes rather than as a substitute for general peak-memory management. If you observe degraded throughput in a training run that uses unified memory for optimizer state, investigate the frequency of page faults and host–device transfers in your workload. Where spike frequency is high, consider strategies that reduce the spike rate: adjust mini-batch composition to avoid mixing many long sequences into the same batch, reduce per-step sequence lengths where acceptable, fine-tune gradient-checkpointing granularity, or provision larger GPU capacity if the workload demands it. Conversely, when spikes are genuinely rare, paged optimizers can significantly expand the usable model scale on a single GPU without appreciable runtime cost—exactly the operating point demonstrated by QLoRA for 65B on 48GB with batch size 16.

Finally, remember that the QLoRA paper intentionally leaves a more detailed measurement study to future work. If you adopt paged optimizers in practice, collect traces of paging activity and end-to-end throughput for your target workloads so you can empirically verify whether the unified-memory transfers are infrequent enough to preserve training speed or whether further changes in batch composition, sequence bucketing, or checkpointing strategy are required.

The QLoRA Algorithm and Implementation Recipe

# Forward computation: Y = X · doubleDequant(c1, c2, W_NF4) + X · L1 · L2

At the heart of QLoRA is a compact formula for a single linear layer that combines a frozen, quantized base weight matrix with a small trainable low-rank adapter. Written for a single layer, the forward computation used during both inference and training is

\[
\mathbf{Y}^{\text{BF16}} \;=\; \mathbf{X}^{\text{BF16}}\;\text{doubleDequant}\big(c_1^{\text{FP32}},\, c_2^{\text{k-bit}},\, \mathbf{W}^{\text{NF4}}\big)
\;+\; \mathbf{X}^{\text{BF16}}\,\mathbf{L}_1^{\text{BF16}}\mathbf{L}_2^{\text{BF16}}.
\]

This expression has three pieces to understand. The first term, \(\mathbf{X}^{\text{BF16}}\;\text{doubleDequant}(\cdot)\), is the base pretrained linear projection computed using a weight matrix \(\mathbf{W}\) that is stored in a highly compressed, quantized form (here NF4). At runtime that compressed representation is dequantized back to the computation datatype (BF16) for the actual matrix multiply. The second term, \(\mathbf{X}\mathbf{L}_1\mathbf{L}_2\), is the LoRA adapter: a factorized, low-rank correction added to the frozen projection. Because \(\mathbf{L}_1\) and \(\mathbf{L}_2\) are trainable and stored in BF16, we can update them with standard optimizers and high precision gradients while keeping the large base weights frozen and stored compactly.

This decomposition is the practical and memory-efficient core idea: use aggressive compression for the massive pretrained model parameters (so storage is small), but allow a small number of high-precision adapter parameters to be trained so the model can adapt to new tasks without modifying the base weights.

# doubleDequant definition: dequantize c2 then W to BF16 for compute

Double Quantization is the two-level scheme used in QLoRA to reduce not just the weight tensor storage but also the overhead of per-block quantization constants. The doubleDequant operation used in the forward pass takes as input

- \(c_1^{\text{FP32}}\): the top-level dequantization constant(s) kept in FP32,
- \(c_2^{\text{k-bit}}\): the second-level per-block quantized quantization constants (stored in a small k-bit format, implemented with FP8 in practice),
- \(\mathbf{W}^{\text{NF4}}\): the base weight tensor quantized with the 4-bit NormalFloat (NF4) datatype.

Formally, the two-stage dequantization is

\[
\text{doubleDequant}\big(c_1^{\text{FP32}},\, c_2^{\text{k-bit}},\, \mathbf{W}^{\text{k-bit}}\big)
\;=\;
\text{dequant}\big(\text{dequant}(c_1^{\text{FP32}},\,c_2^{\text{k-bit}}),\,\mathbf{W}^{\text{k-bit}}\big)
\;=\; \mathbf{W}^{\text{BF16}}.
\]

The inner dequant converts the compact representation of the second-level quantization constants, \(c_2^{\text{k-bit}}\), back to an FP32 scale per block by using a global FP32 constant \(c_1^{\text{FP32}}\). The outer dequant then uses those recovered per-block FP32 scales to rescale the 4-bit NF4 values into BF16 weights. In practice QLoRA uses NF4 for \(\mathbf{W}\) (blocksize 64), FP8 (or other 8-bit float) for \(c_2\) (blocksize 256), and BF16 for the final computation data type. This two-level quantization allows the expensive per-block FP32 scales to be stored in a much smaller format, saving several gigabytes for very large models while preserving the precision needed for correct dequantized values at compute time.

An example of the memory arithmetic shown in the paper: if standard single-stage quantization stores a 32-bit quantization constant per 64 parameters, that costs \(32/64 = 0.5\) bits per parameter on average. With double quantization and \(c_2\) in 8-bit floats with blocksize 256, the cost becomes

\[
\frac{8}{64} + \frac{32}{64\cdot 256} = 0.125 + 0.002 = 0.127\ \text{bits per parameter},
\]

a reduction of about \(0.373\) bits per parameter. Those savings multiply across tens of billions of parameters.

# Gradient flow: compute dE/dL_i only; dX/dW via dequantized BF16 path

One of the most important practical aspects of QLoRA is how gradients flow during backpropagation. The design choice is that only the LoRA adapter parameters are trainable; the base quantized model weights \(\mathbf{W}^{\text{NF4}}\) are frozen and never updated. However, gradients must still be propagated through the frozen base model so that earlier layers and the adapters receive correct error signals.

Write the forward output compactly as

\[
\mathbf{Y} = \underbrace{\mathbf{X}\,\mathbf{W}}_{\text{frozen, dequantized at compute time}} \;+\; \underbrace{\mathbf{X}\,\mathbf{L}_1\mathbf{L}_2}_{\text{trainable adapters}}.
\]

During backpropagation we compute the loss \(E\) and obtain \(\frac{\partial E}{\partial \mathbf{Y}}\). The gradients that we need to update the LoRA factors are

\[
\frac{\partial E}{\partial \mathbf{L}_2}
= (\mathbf{X}\mathbf{L}_1)^\top \left(\frac{\partial E}{\partial \mathbf{Y}}\right),
\qquad
\frac{\partial E}{\partial \mathbf{L}_1}
= \mathbf{X}^\top \left(\frac{\partial E}{\partial \mathbf{Y}}\,\mathbf{L}_2^\top\right),
\]

which are standard matrix calculus results for the two-factor parameterization. These gradients require \(\mathbf{X}\) and \(\frac{\partial E}{\partial \mathbf{Y}}\), both available in BF16 precision given QLoRA's dequantization at compute time.

Although \(\mathbf{W}\) is frozen and not updated, the backward pass still needs to compute \(\frac{\partial E}{\partial \mathbf{X}}\) to propagate gradients to earlier layers. That computation depends on \(\mathbf{W}\) (for the frozen path) and therefore requires a numerically accurate dequantized \(\mathbf{W}^{\text{BF16}}\) during the backward pass. In short: QLoRA never computes \(\frac{\partial E}{\partial \mathbf{W}}\) (no updates to the base weights), but it does dequantize the stored \(\mathbf{W}^{\text{NF4}}\) to BF16 during the forward and backward passes so that downstream gradients (including \(\frac{\partial E}{\partial \mathbf{X}}\)) are computed in high precision. This guarantees stable gradient propagation through the frozen model while keeping storage costs low.

Because all gradient computation that depends on the base weights uses the dequantized BF16 values, training numerical stability is preserved as if the base model were present in 16-bit precision, even though its storage remains in an aggressive 4-bit format.

# Data types and blocks: NF4 for W (blocksize 64); FP8 for c2 (blocksize 256); BF16 compute

QLoRA relies on carefully chosen datatypes and block sizes to balance compression and numerical fidelity.

- Base weight storage: NF4 (4-bit NormalFloat). NF4 is designed to be information theoretically optimal for normally distributed, zero-centered weight tensors. By constructing quantization bins that have equal expected mass under a standard normal, NF4 reduces quantization error for the typical distribution of pretrained network weights. In QLoRA the NF4 representation is used for the main weight tensors \(\mathbf{W}^{\text{NF4}}\), with a blocksize of 64 values per block. A relatively small blocksize such as 64 increases quantization precision because quantization scales can adapt to local variation in the tensor without oversmoothing outliers.

- Second-level constants: FP8 for \(c_2^{\text{k-bit}}\). The per-block quantization constants that would normally be stored as FP32 are themselves quantized to an 8-bit float format (FP8) to save memory. These smaller constants are stored with a larger blocksize (256) because the constants are smoother across blocks and can be coarser without notable loss in final dequantized weight accuracy. A centering step (subtracting the mean) is applied before symmetric quantization because the constants are positive, and centering improves the effective use of symmetric quantization.

- Compute datatype: BF16. At compute time the 4-bit base weights are dequantized into BF16 and matrix multiplies are performed in BF16. The adapters \(\mathbf{L}_1, \mathbf{L}_2\) are stored and updated in BF16. Using BF16 for computation preserves the numerical stability of forward and backward passes.

The combination NF4 (blocksize 64) for weights and FP8 (blocksize 256) for quantization constants, with BF16 for compute, is the configuration used in the paper and shown empirically to preserve finetuning performance while achieving large memory savings.

# Adapter placement: include LoRA in all linear layers to match full finetuning

An important empirical finding from the QLoRA study is that where LoRA adapters are placed has a large effect on final finetuning quality. Prior practice often limits LoRA to the query and value projection matrices inside attention modules. While this is memory-efficient and often effective at modest model scales, the QLoRA experiments show that applying adapters only to the attention q/k/v matrices is insufficient to match the performance of full-model finetuning for larger base models.

To reliably recover full finetuning performance, QLoRA places LoRA adapters in every linear layer of the transformer block: attention projection matrices (query, key, value, output), feed-forward network (FFN) down and up projections, and any other dense linear projections. The rationale is that different linear layers encode different aspects of the model's functionality. Restricting adaptation to only a couple of projections limits the representational flexibility available to the adapters; by adding adapters per linear layer, the small adapter matrices collectively provide a rich space of low-rank corrections that can compensate for the frozen base weights across the entire network.

Because LoRA parameter sets are tiny relative to the base model, adding adapters to every linear layer does not greatly increase total memory footprint. The paper highlights that the dominant memory cost for finetuning is activation gradients, and LoRA parameters themselves are negligible in size (e.g., the LoRA parameters are on the order of megabytes while activation gradients are hundreds to thousands of megabytes). Thus, adding many adapters is a practical way to close the gap to full finetuning without large cost.

# Hyperparameters: LoRA rank r, scaling s, learning rates by model size, batch size scaling

LoRA introduces a few tunable hyperparameters. The paper reports empirical findings and practical guidance rather than an exhaustive search; below we summarize those results and the intuition behind the parameters so you can tune QLoRA in practice while remaining faithful to the paper.

- Rank \(r\). The LoRA parameterization uses a factorization \(\mathbf{L}_1\in\mathbb{R}^{h\times r}\) and \(\mathbf{L}_2\in\mathbb{R}^{r\times o}\). The rank \(r\) controls the number of extra degrees of freedom given to the adapter. While larger \(r\) allows more capacity, the QLoRA experiments indicate that performance is not highly sensitive to the exact choice of \(r\) once adapters are present in all linear layers. In other words, the presence and placement of adapters matters more than marginal changes in \(r\). The paper notes that other LoRA hyperparameters (including \(r\)) do not strongly affect final performance in their ablations.

- Scaling \(s\). LoRA often uses a scalar \(s\) (or scaled initialization) to control the effective magnitude of the adapter contribution at the start of training. This is important to avoid destabilizing a pretrained model by introducing large adapter outputs early on. QLoRA keeps the adapters in BF16 and uses usual initialization/scale practices so that the adapter term starts small and can grow during training.

- Learning rate and batch size. The authors performed hyperparameter searches over learning rates in the range \(1\times 10^{-6}\) to \(5\times 10^{-5}\) and batch sizes from 8 to 128 when tuning 7B models. They found that many hyperparameter choices that work at 7B generalize to larger sizes, with two notable exceptions: learning rate and batch size. For 33B and 65B models they halved the learning rate and doubled the batch size compared to the 7B settings. This suggests a practical scaling heuristic: as model size increases, reduce learning rates and increase effective batch size to stabilize training. Number of epochs and other scheduler choices were found to transfer across scales.

- Optimizer states and paged optimizers. Because QLoRA stores optimizer state (e.g., Adam moments) for the LoRA parameters and sometimes the optimizer must also manage additional bookkeeping across many layers, using Paged Optimizers (see integration section) can prevent memory spikes when sequences are long. The paper reports that with careful paging the training speed does not suffer for typical batch sizes.

- LoRA overall fraction of parameters. The paper gives an example of a LoRA setup that corresponds to roughly 0.2% of the original model weights in parameter count. This tiny fraction is sufficient when adapters are placed throughout all linear layers.

A practical tuning loop consistent with the paper is: run a small search at a smaller model size (e.g., 7B) over learning rate in the above range and batch sizes in a practical set; adopt the same choice of epochs and adapter placement for larger models, but halve the learning rate and double the batch size for 33B and 65B scale finetuning unless further tuning indicates otherwise.

# Integration: bitsandbytes CUDA kernels; Hugging Face Transformers support

To make QLoRA practical, software engineering on both quantization kernels and model integration is required. The paper authors released the necessary components:

- Custom CUDA kernels and the bitsandbytes library. The low-level kernels implement the NF4 quantization format, the efficient storage layout for per-block constants, and the double dequantization flow that recreates BF16 weights at compute time. These kernels are optimized for throughput and memory usage and are critical for achieving single-GPU finetuning of very large models (33B on 24 GB, 65B on 48 GB as reported). The bitsandbytes codebase implements the 4-bit datatypes and the memory layouts that the training loop uses.

- Paged Optimizers leveraging NVIDIA unified memory. Paged Optimizers allocate optimizer state in memory that can be automatically paged between GPU VRAM and CPU RAM using the CUDA unified memory facility. When a particular optimization step requires optimizer state that is not resident on the GPU, the runtime will page the needed pages in and page unused pages out. This technique eliminates many out-of-memory conditions caused by occasional large activation or gradient spikes (for example, long sequences in a batch) and enables training very large models on a single GPU with limited memory. The paper found that in typical regimes (batch size 16 for 65B on 48GB) paged optimizers do not reduce training throughput.

- Hugging Face Transformers integration. The implementation and adapters were integrated into the Hugging Face ecosystem so that researchers and practitioners can apply QLoRA using familiar model APIs, tokenizers, and dataset utilities. The released code includes the logic to wrap pretrained models in the QLoRA inference/training path: loading quantized weight tensors, applying double quantization constants, placing LoRA adapters in the proper modules, and using the bitsandbytes kernels for dequantize-and-multiply.

Taken together, these software components make QLoRA a reproducible recipe: prepare a pretrained model converted into the NF4 + double quant storage representation via the provided kernels; insert LoRA adapters in every linear layer; set the compute dtype to BF16; use paged optimizers and the suggested learning rate scaling; then run standard supervised finetuning (cross-entropy) to obtain adapters that reproduce 16-bit finetuning performance while keeping storage and training memory small.

# Practical recipe and checklist

To implement QLoRA for a large pretrained transformer layer-by-layer, follow these concrete steps (as reported in the paper):

1. Convert pretrained weight matrices \(\mathbf{W}\) to NF4 with blocksize 64 and produce per-block FP32 scales \(c_2^{\text{FP32}}\).

2. Double-quantize the per-block scales \(c_2^{\text{FP32}}\) by centering (subtracting the mean) and quantizing to an 8-bit float format with blocksize 256, producing \(c_2^{\text{FP8}}\) and top-level \(c_1^{\text{FP32}}\).

3. Store \(\mathbf{W}^{\text{NF4}}\) plus the compact constants \(c_2^{\text{FP8}}\) and \(c_1^{\text{FP32}}\) on disk and load them into GPU memory in their compact form.

4. Insert LoRA adapters \(\mathbf{L}_1, \mathbf{L}_2\) in every linear layer you want to adapt (the paper recommends every linear layer to match full finetuning). Initialize adapters so that their initial contribution is small (use scaling \(s\) or small initial weights).

5. Use BF16 as the computation data type. In the forward pass dequantize on-the-fly via doubleDequant to obtain \(\mathbf{W}^{\text{BF16}}\), compute both frozen and adapter terms in BF16, and proceed.

6. During backward, compute gradients only for the adapter parameters \(\mathbf{L}_1, \mathbf{L}_2\) and use the dequantized BF16 \(\mathbf{W}\) to compute \(\frac{\partial E}{\partial \mathbf{X}}\) so gradients propagate through the frozen base model.

7. Tune hyperparameters starting from a small-scale search (e.g., on 7B): LR in \([1\mathrm{e}{-6},\,5\mathrm{e}{-5}]\), batch size from small to moderate; for larger models (33B, 65B) halve the learned LR and double batch size relative to what worked for 7B; keep number of epochs and adapter placements consistent across scales.

8. Use bitsandbytes CUDA kernels and the Hugging Face QLoRA integration to run efficient training; if memory spikes cause OOM, enable paged optimizers backed by CUDA unified memory.

By following this recipe, the QLoRA paper demonstrates that you can finetune extremely large models (33B, 65B) on a single GPU without degrading performance relative to standard 16-bit finetuning, while using orders of magnitude less GPU memory for model storage.

# Closing intuition

The core intuition behind QLoRA is a separation of concerns: keep the massive pretrained parameters compressed and immutable to save memory and I/O, but give the model a low-dimensional, high-precision means to adapt to new tasks. Double Quantization keeps per-block scale overhead tiny, NF4 matches the typical weight distribution to minimize quantization error, and dequantizing to BF16 at compute time preserves numerical fidelity for gradient propagation. Placing small adapters everywhere gives the model enough expressivity to emulate a full fine-tune. The result is a practical, reproducible method to bring large-model finetuning into the reach of single-GPU environments without sacrificing the final performance.

Comparative Experiments: QLoRA vs 16-bit Baselines and Ablations

# Architectures and benchmarks: RoBERTa on GLUE; T5 on Super-NaturalInstructions; LLaMA on MMLU

The empirical study that supports QLoRA is broad: it intentionally spans three canonical neural language model architectures — encoder-only, encoder-decoder, and decoder-only — and uses well-established benchmarks that probe different aspects of language understanding and instruction following. For encoder-only models the experiments use RoBERTa-large evaluated on GLUE, a suite of discriminative tasks that captures sentence-level classification and natural language understanding. For encoder-decoder models the experiments use T5 finetuned and evaluated on Super-NaturalInstructions (TKInstruct), a multitask instruction-following dataset designed to measure how well models generalize to diverse natural language tasks. For decoder-only models the principal evaluation is on LLaMA models assessed with the MMLU benchmark (Massively Multitask Language Understanding), reported in the common 5-shot protocol that stresses broad knowledge across many domains.

This cross-architecture, cross-benchmark design is important because it reduces the chance that results are an artifact of a single model family or a particular task type. By demonstrating parity with 16-bit baselines across these three settings, the experiments show that the QLoRA recipe — 4-bit storage with NF4, double quantization of scales, LoRA adapters, and 16-bit computation — is not narrowly applicable but robust across standard model classes and evaluation protocols.

# Adapter vs full finetuning up to 3B; 4-bit vs 8-bit vs 16-bit

A core experimental axis tests whether adapter-style parameter-efficient finetuning (LoRA) can match full 16-bit finetuning performance when applied after quantizing the base model. The experiments include models up to 3B parameters where full 16-bit finetuning is feasible on academic hardware; this enables direct comparison between (a) full-model 16-bit finetuning, (b) 16-bit LoRA, and (c) low-bit (8-bit and 4-bit) LoRA methods.

On GLUE with RoBERTa-large and on Super-NaturalInstructions with T5 (125M–3B scale), the findings are clear: 16-bit, 8-bit, and 4-bit adapter finetuning methods replicate the performance of the fully finetuned 16-bit baseline. In other words, switching to adapter tuning and reducing storage precision for the base model does not incur a measurable loss in downstream task metrics when the adapters are trained appropriately. This is evidence that much of the adaptation required by finetuning can be captured in a small, trainable subspace (the adapters), and that the quantization-induced noise in base weights can be compensated by adapter updates.

These experiments also compare different storage precisions. Moving from 16-bit to 8-bit or 4-bit storage reduces memory usage substantially, but the key experimental result is that 4-bit adapter finetuning (QLoRA) can match the 16-bit baseline performance when combined with the additional QLoRA techniques (NF4, double quantization, and proper adapter placement). This demonstrates that the performance loss typically observed from naively quantizing weights can be recovered by finetuning adapters that see gradients backpropagated through the dequantized (but frozen) base model.

# NF4 ablations: zero-shot accuracy and perplexity across OPT, BLOOM, Pythia, LLaMA (125M–13B)

Ablations isolate the contribution of the NF4 data type (the 4-bit NormalFloat quantization) by comparing it to other 4-bit representations (FP4 and integer 4-bit) across multiple model families and sizes, including OPT, BLOOM, Pythia, and LLaMA in the 125M–13B parameter range. The metrics used for these ablations are standard language-modeling measures: zero-shot task accuracy and perplexity after quantization (i.e., post-quantization evaluation, without further finetuning).

Two experimental patterns emerge. First, NF4 consistently improves post-quantization language-modeling performance compared to FP4 and Int4. Practically, this means that when the base model weights are quantized to 4 bits with NF4, the model's immediate ability to score and generate tokens (as measured by perplexity) and to perform zero-shot tasks is better preserved than with alternative 4-bit formats. Second, double quantization (quantizing the quantization constants themselves) reduces memory overhead with negligible to no measurable degradation in these same metrics.

Why does NF4 help? NF4 is constructed to be information-theoretically optimal for tensors that are approximately zero-centered and normally distributed (which pretrained weights typically are). Instead of uniformly spacing representable values or using raw integer bins, NF4 chooses bin centers based on quantiles of the standard normal distribution, then rescales per-block to match the actual tensor range. Empirically this aligns the finite set of 4-bit codes with where weight values actually lie, reducing representation error for the bulk of the distribution compared to FP4 or Int4. The ablations across multiple architectures and sizes demonstrate this advantage is general, not model-specific.

# LoRA hyperparameter insights: default Q/V-only adapters underperform; adapters across all layers recover performance

One of the most consequential experimental findings concerns where to place LoRA adapters and how many to use. The community prior (and the original LoRA paper's common practice) is to inject LoRA into the query and value projection matrices of attention layers only. The QLoRA experiments show that this default practice is not sufficient to reproduce full finetuning performance for larger base models when operating in quantized storage regimes.

In controlled experiments (for example LLaMA 7B finetuned on Alpaca), the number and placement of adapters emerge as the critical LoRA hyperparameter. When LoRA is applied only to Q/V projections, adapter tuning underperforms the fully finetuned 16-bit baseline. In contrast, placing LoRA adapters across all linear projection layers throughout every transformer block (i.e., augmenting every linear layer, not just Q/V) recovers full finetuning performance. The projection rank $r$ (the internal LoRA dimension) is less sensitive — varying $r$ has little effect in these experiments — whereas the coverage (how many layers receive adapters) is decisive.

Intuitively, restricting adapters to Q/V limits the subspace in which the model can adapt. Many downstream instructions and behaviors require modifying transformations performed by feed-forward layers, output projections, and other linear mappings beyond attention Q/V. With quantized base weights, the adapters need that broader reach to compensate for quantization distortions and to capture the task-specific adjustments that full finetuning would normally express over many parameters. The empirical takeaway is practical: to match full finetuning with QLoRA, place adapters broadly (every linear layer) rather than narrowly.

A secondary but important note is that the baseline 16-bit full finetuning setups were themselves initially under-tuned. The authors performed hyperparameter sweeps for the 16-bit baselines (learning rates from $1\mathrm{e}{-6}$ to $5\mathrm{e}{-5}$, batch sizes from $8$ to $128$) to obtain robust comparisons. This ensures reported parity is not an artifact of poorly tuned baselines.

# QLoRA vs 16-bit LoRA on LLaMA 7B–65B with Alpaca and FLAN v2: matching MMLU performance

Scaling experiments examine whether the QLoRA recipe still matches 16-bit LoRA and full finetuning as model size increases into regimes where full 16-bit training is impractical (11B+). The authors finetune LLaMA models at scales 7B, 13B, 33B, and 65B on two instruction-following datasets (Alpaca and FLAN v2) and evaluate on the 5-shot MMLU benchmark.

The key result: NF4 QLoRA with double quantization fully recovers the 16-bit LoRA MMLU performance across these scales. In concrete terms, the measured MMLU accuracies for NF4 QLoRA are statistically indistinguishable from those achieved by 16-bit LoRA finetuning. In contrast, QLoRA with FP4 (4-bit floating representations that are not NF4) lags behind by about $1$ percentage point on MMLU in the reported experiments. This reinforces the ablation conclusion that NF4 is a crucial component of successful low-bit finetuning.

More broadly, these experiments validate the central premise of QLoRA: by storing the base model at 4-bit NF4 precision, keeping it frozen, and training full-precision LoRA adapters (with gradients propagated through dequantized weights computed in 16-bit), one can obtain adapter-finetuned models whose downstream performance matches that of higher-precision adapter or full finetuning—even at very large model scales.

# Summary: NF4 ≥ FP4/Int4; double quantization saves memory without hurting accuracy

Pulling together the experimental threads yields a set of practical, experimentally grounded conclusions.

First, the NF4 4-bit data type consistently outperforms FP4 and Int4 for quantizing pretrained weights: NF4 yields better zero-shot accuracy and lower perplexity post-quantization across multiple model families and sizes. The information-theoretic design of NF4 for normally distributed weights produces a better match between representable codes and actual weight statistics.

Second, adapter finetuning recovers information lost in quantization. Across encoder, encoder-decoder, and decoder-only settings (GLUE, Super-NaturalInstructions, MMLU), 4-bit QLoRA matches the performance of 16-bit baselines provided adapters are placed appropriately (across all linear layers) and hyperparameters are tuned. This holds across scales up to 65B in the comparison with 16-bit LoRA on MMLU.

Third, Double Quantization (quantizing the per-block quantization constants) yields meaningful memory savings with negligible accuracy impact. For example, with a blocksize of $64$ the naive storage cost of 32-bit quantization constants adds $\frac{32}{64} = 0.5$ bits per parameter. Double quantization reduces this to approximately

\[
\frac{8}{64} + \frac{32}{64\cdot 256} = 0.127\ \text{bits per parameter},
\]

a reduction of about $0.373$ bits per parameter (roughly $\sim 3$ GB for a 65B-parameter model), without degrading performance in downstream evaluations.

Finally, an important operational note from the experiments is that optimizer and memory-management considerations remain crucial when training at large scale. The QLoRA setup uses 16-bit BFloat for computation (dequantizing stored NF4 into BF16 for forward/backward passes), and uses paged optimizers to avoid transient memory spikes from gradient checkpointing. While the paper does not exhaustively quantify paging overhead, it reports that paging does not impact typical training speed for large batches in their setups.

Taken together, these empirical results establish QLoRA (NF4 + double quantization + broad LoRA placement + paged optimizers) as a reproducible method that matches 16-bit full finetuning and 16-bit LoRA performance while enabling orders-of-magnitude lower memory footprint for storage — making competitive finetuning feasible on single-GPU hardware for very large models.

Instruction Tuning at Scale and the Guanaco Family

# Datasets surveyed: OASST1, HH-RLHF, Alpaca, Self-instruct, Unnatural Instructions, FLAN v2, Chip2, Longform

The QLoRA study performed a broad survey of eight recent instruction-following datasets that differ in source, size, language coverage, and intended use. These datasets were chosen to represent the major families of instruction-tuning data used in recent work: crowd-sourced multi-turn conversations, datasets distilled from stronger models, aggregated corpora, and hybrid collections.

OASST1 (OpenAssistant) is a crowd-sourced collection of multi-turn assistant conversations designed to support RLHF-style training; its design explicitly forbids derivation from proprietary models. HH-RLHF is a dataset that includes human preference comparisons of model outputs and has been used in RLHF pipelines. Alpaca, Self-instruct, and Unnatural Instructions are examples of distillation-style datasets: they were generated or distilled using instruction-following models to create many simple input–output instruction pairs. FLAN v2 represents a large aggregated instruction-tuning corpus assembled to improve few-shot generalization across tasks. Chip2 (OIG partial collection) and Longform are hybrid or specialized collections that mix different sources or focus on certain response formats (e.g., long-form answers).

Because these datasets have different emphases (multi-turn conversational style, single-turn instruction–response pairs, large breadth vs curated quality), the study used them to test how dataset choice affects downstream chatbot behavior and standard benchmarks such as MMLU. One concrete finding from this comparison is that smaller, higher-quality datasets (e.g., a high-quality subset of OASST1 with roughly 9k selected samples) can outperform much larger but less-suited corpora (e.g., a 450k-sample subsample of FLAN v2) on chatbot-style benchmarks. This emphasizes that dataset composition and suitability for the target evaluation are decisive factors.

# Training choices: supervised cross-entropy only (no RLHF); response-only vs full conversation finetuning specifics

To keep comparisons controlled and to focus on the effect of QLoRA and dataset composition, all instruction-finetuning in the study used supervised maximum-likelihood training (cross-entropy loss) rather than reinforcement learning from human feedback (RLHF). Even for datasets that contain human judgments or rankings, the study did not apply RLHF; instead, it treated each dataset as supervised examples to be learned. This choice isolates the effects of the data and the finetuning method from the complexities and additional compute of RLHF.

Where datasets provide a clear separation between an instruction (or dialogue context) and a response, the authors typically finetuned on the response text only. This “response-only” finetuning emphasizes the model’s generation conditioned on the instruction or context. The paper notes ablations on this choice (details in the appendices), but in practice treating instruction→response pairs by focusing updates on the response tokens simplifies training and matches common instruction-tuning practice.

For multi-turn or tree-structured datasets that include multiple candidate responses (notably OASST1 and HH-RLHF), the study used a selection heuristic: at each level of the conversation tree, they selected the top response and then finetuned on the full selected conversation, including the instructions and prior turns. In other words, for datasets where multiple alternative assistant responses exist, the pipeline builds a single “best” conversation per example and trains on that entire sequence rather than only the final response. This preserves multi-turn conversational structure in training examples for the conversational-focused datasets.

# Hyperparameter transfer across 7B→13B→33B→65B; LR and batch size adjustments

One practical advantage observed in the study was the partial transferability of LoRA and QLoRA hyperparameters across model scales. The researchers tuned hyperparameters for the 7B models and found that most settings—such as number of epochs and many LoRA-specific hyperparameters—generalized well to larger LLaMA variants. However, two low-level optimization hyperparameters required scale-aware adjustment: learning rate and batch size.

Concretely, the study reports that when moving from 7B to 33B and 65B LLaMA models, the stable regimen was to halve the learning rate and double the batch size. This adjustment reflects standard stability considerations: larger models often require smaller per-parameter update magnitudes, and increasing batch size offsets gradient noise while keeping step counts manageable. For the 13B and 33B models the authors ran small hyperparameter searches (centered around the successful 7B settings) and found these scale-aware adjustments sufficient to achieve good results across sizes.

Because QLoRA drastically reduces memory requirements, these hyperparameter experiments were feasible at scale: the authors trained more than 1,000 models in total across architectures, datasets, and sizes, allowing robust empirical observations about which hyperparameters transfer and which must be adjusted with scale.

# Baselines: Vicuna, Open Assistant (RLHF), commercial systems (GPT-4, GPT-3.5-turbo, Bard)

To interpret Guanaco’s performance, the study compared against a variety of open and closed baselines. Open-source baselines included Vicuna (a LLaMA 13B model finetuned on ShareGPT-like user conversations) and the Open Assistant 33B model (a LLaMA 33B model finetuned with RLHF on OASST1). Commercial baselines included OpenAI’s GPT-4, GPT-3.5-turbo (ChatGPT), and Google’s Bard. These commercial systems serve as reference points for state-of-the-art instruction-following and chat performance.

Evaluations used both automated and human protocols. For automated evaluation the study used GPT-4 as a judge in two ways: (1) scoring model responses out of 10 relative to ChatGPT’s response (a relative score measured as the percentage of ChatGPT’s score), and (2) head-to-head pairwise comparisons where GPT-4 chooses the better response or declares a tie. Because of potential ordering biases and other artifacts, the authors controlled for prompt ordering when using GPT-4. Human evaluation was conducted on Amazon Mechanical Turk (AMT) with multiple annotators per comparison: two annotators for comparisons to ChatGPT and three for pairwise model comparisons. To aggregate pairwise comparisons into system rankings, the study used an Elo tournament mechanism (starting Elo of 1000 and using K = 32), sampling comparisons repeatedly to stabilize results.

# Guanaco results: 65B reaches 99.3% of ChatGPT on Vicuna; 33B competitive at low memory footprint (~21 GB); 7B fits in ~5 GB

The family of QLoRA-finetuned models trained on OASST1 and other datasets is collectively named Guanaco. The headline result is that Guanaco 65B (a 65-billion-parameter LLaMA base model finetuned with QLoRA on a curated OASST1 variant) attains performance on the Vicuna benchmark that is effectively indistinguishable from ChatGPT, achieving 99.3% of ChatGPT’s score in the automated ChatGPT-relative evaluation. This places Guanaco 65B as the top open-source chatbot in the study, second only to GPT-4 among all systems evaluated.

The 33B Guanaco model also performs competitively while requiring substantially less inference memory: because its weights are stored in 4-bit NF4 format, the 33B Guanaco requires approximately 21 GB of memory for the model, compared to 26 GB for the Vicuna 13B baseline in 16-bit. Despite the more compact representation, Guanaco 33B achieves a several-percentage-point improvement over Vicuna 13B on the Vicuna prompt set. The smallest Guanaco in the released family, the 7B model, requires only about 5 GB of memory at inference and scores roughly 20 percentage points higher than the Alpaca 13B model on the Vicuna benchmark, demonstrating that careful instruction finetuning plus quantization can yield very strong quality-per-byte trade-offs.

These results are supported by paired evaluations and Elo-style ranking: human and GPT-4 pairwise comparisons place Guanaco 33B and 65B among the top open-source models; Guanaco 65B is the best open-source model evaluated and is competitive with ChatGPT under the adopted metrics.

# Efficiency: 33B trained in <12 hours on a 24 GB consumer GPU; 65B in ~24 hours on a single 48 GB GPU

A core motivation of QLoRA was to democratize large-model finetuning by reducing GPU memory requirements to the point where models that previously required multi-server training can be tuned on a single GPU. The paper reports concrete training-efficiency outcomes enabled by QLoRA:

- QLoRA reduces the average GPU memory required to finetune a 65B LLaMA model from more than 780 GB in regular 16-bit finetuning to less than 48 GB, making single-GPU finetuning of such models feasible. This reduction stems from storing the base model in 4-bit NF4 representation, using Double Quantization to compress per-block quantization constants, and employing paged optimizers to handle occasional optimizer-state spikes.

- Double Quantization itself compresses quantization constants by applying a second-level quantization. For a blocksize of 64, the naive cost for a 32-bit quantization constant is 32/64 = 0.5 bits per parameter; after Double Quantization with an 8-bit quantization for the constants and a second-level blocksize of 256, that average cost becomes 8/64 + 32/(64·256) = 0.127 bits per parameter — a net reduction of 0.373 bits per parameter (which the authors note corresponds to roughly 3 GB saved for a 65B model).

- Practically, this means a Guanaco 33B model can be finetuned in under 12 hours on a single 24 GB consumer GPU, and the largest Guanaco 65B model can be finetuned in about 24 hours on a single 48 GB professional GPU. These timings enabled training many model–dataset combinations (over 1,000 models) to study instruction finetuning trends across scale and data.

# Key insights: data quality > dataset size; MMLU vs chatbot metrics are not strongly correlated

The large-scale experiments with QLoRA yielded several important empirical insights that are useful when designing instruction-tuning pipelines:

1. Data quality matters more than sheer dataset size. The study finds that a relatively small, high-quality conversational dataset (a curated variant of OASST1 with about 9k selected high-quality examples) produced stronger chatbot behavior than a much larger but less directly relevant dataset (a 450k-sample subsample of FLAN v2) on the Vicuna-style conversational evaluation. This result emphasizes that matching dataset characteristics to the desired task (multi-turn conversational style versus general instruction-response pairs) is more important than maximizing the number of examples.

2. Standard academic NLU benchmarks and chatbot-style evaluations can diverge. In particular, strong performance on MMLU (a multiple-choice academic benchmark measuring general knowledge and reasoning, reported in the paper as 5-shot accuracy) does not reliably predict superior chatbot behavior on the Vicuna and OpenAssistant (OA) benchmarks. The paper documents concrete cases where a dataset that boosts MMLU scores (e.g., FLAN v2) is less effective for producing high-quality chatbot responses, and vice versa. This indicates partial orthogonality between benchmarks and underlines the importance of choosing finetuning data aligned with the target application.

3. Human and model-based evaluations largely agree at the system level but differ in important ways. The study compares GPT-4 automated judgments with human annotators using Elo tournament aggregation and reports moderate agreement: Kendall’s Tau of $\tau=0.43$ and Spearman rank correlation $r=0.55$ at the system level, while sample-level agreement is weaker (Fleiss $\kappa=0.25$). The authors also observe biases in GPT-4 evaluations (for example, an ordering effect favoring the response presented first) and note that GPT-4 assigns higher scores to outputs it generated (an Elo of 1348 for GPT-4 self-evaluations versus 1176 in human evaluations). These observations caution against blind reliance on model-based judges and suggest that automated evaluation can be a reliable but imperfect proxy for humans.

4. QLoRA recovers 16-bit finetuning performance at much lower memory. Empirically, NF4 quantization combined with adapter finetuning (LoRA) and Double Quantization recovered the performance of standard 16-bit finetuning (and 16-bit LoRA) across a range of tasks and scales in the paper’s experiments. This result legitimizes the strategy of quantize-then-finetune with adapters for democratizing large-model customization.

5. Practical hyperparameter transfer is possible but not fully automatic. Many LoRA settings transfer across scales, but learning rate and batch size should be adjusted (smaller LR and larger batch for larger models) when moving from 7B up to 33B and 65B in order to maintain stability and match performance.

Taken together, these insights show that QLoRA enables extensive empirical study of instruction finetuning at scales that were previously costly or inaccessible, and that such studies reveal important, practical principles about dataset selection, evaluation, and scaling.

# Concluding remarks

The QLoRA-enabled instruction-tuning study produced the Guanaco model family and a large set of finetuned adapters (32 open-sourced adapters: 4 base sizes × 8 datasets), trained across scales from 7B to 65B and evaluated with both human and GPT-4 judgments. The key engineering and methodological lessons are (1) a carefully designed low-bit quantization scheme (NF4) plus Double Quantization and paged optimizers makes single-GPU finetuning of 33B–65B models feasible; (2) supervised cross-entropy finetuning (without RLHF) on well-suited, high-quality instruction data can produce chatbots that rival earlier state-of-the-art open models and come close to ChatGPT on the Vicuna benchmark; and (3) dataset suitability and evaluation methodology are pivotal—choices here often matter more than model size alone. These conclusions provide practical guidance for students and researchers planning to do large-scale instruction tuning with constrained resources.

Evaluating Chatbots: Protocols, Metrics, and Agreement

# Benchmarks: Vicuna and OpenAssistant (OA)
Two primary benchmarks are used to evaluate generative chatbot performance in the study. The Vicuna benchmark consists of 80 hand-curated prompts that span a diverse set of categories; it is designed to test open-ended instruction-following and conversational quality. The OpenAssistant (OA) validation set is a much larger, multilingual collection drawn from crowd-sourced multi-turn dialogs. From OA the evaluation uses all user messages in the validation split, including preceding context turns when appropriate, yielding 953 unique user queries. Together these two datasets provide complementary views: Vicuna is compact and diverse, suited for controlled comparisons, while OA is broader and closer to real-world multi-turn conversational data.

When generating model outputs for evaluation, the same decoding settings were used across systems: nucleus sampling with $p=0.9$ and temperature $0.7$. Using a fixed decoding strategy is important so that differences in scores reflect model quality and not differences in sampling randomness or exploration.

# Automated evaluation: GPT-4 ratings and head-to-head comparisons
Automated evaluation in this study relies heavily on GPT-4 as a surrogate rater. There are two complementary GPT-4 based protocols.

The first protocol is a scored comparison versus ChatGPT (GPT-3.5 Turbo). Given a query plus two responses (ChatGPT’s and the evaluated model’s), GPT-4 is prompted to assign a score out of ten to each response and to provide an explanation. The study reports model performance relative to ChatGPT as the percentage of the score ChatGPT attained; note that relative scores can exceed $100\%$ if the evaluated model receives a higher absolute score than ChatGPT. Critically, the authors observed a systematic ordering effect: GPT-4 tends to assign higher scores to the response that appears earlier in the prompt. To control for this ordering bias, they recommend computing the mean score across both presentation orders (model first and ChatGPT first).

The second GPT-4 protocol uses direct pairwise, head-to-head comparisons. Instead of numeric scoring, GPT-4 is asked to choose which response is better or to declare a tie; it also provides an explanation. This is cast as a three-class labeling task (model A wins, model B wins, tie). Pairwise comparisons are done for all permutations of system pairs on both Vicuna and OA. These head-to-head judgments form the basis for tournament-style aggregation (see the Elo section below).

Both automated protocols yield large numbers of judgments quickly and cheaply, but the paper emphasizes that they are imperfect proxies for human preference and exhibit measurable biases, so they are used in parallel with human evaluation.

# Human evaluation: AMT protocols and rater counts
Human evaluation was conducted through Amazon Mechanical Turk (AMT) following two analogous protocols to the automated ones. For comparisons against ChatGPT, the study collected two human annotators per example. For direct pairwise comparisons between two non-ChatGPT systems, they collected three human annotators per example. Annotators were asked to choose the better response (or declare a tie) and provide brief justifications, matching the form of the automated pairwise comparisons.

Collecting multiple raters per example enables aggregation (majority vote) and estimation of inter-annotator agreement. The study reports a moderate level of agreement among human raters: Fleiss' kappa on the human-only judgments was approximately $\kappa = 0.42$, indicating that human annotators agree more than chance but not perfectly. These human judgments are treated as the gold standard for evaluating system-level quality, against which GPT-4 judgments are compared.

# Tournament setup and Elo rating
To aggregate many pairwise comparisons into a consistent ranking, the study uses a tournament-style framework that converts pairwise outcomes into Elo scores. A tournament is composed of many matches; each match compares two models on a single prompt and yields one of three outcomes: model A wins, model B wins, or tie. The Elo rating system then updates model ratings after each match according to how surprising the result is relative to the players’ prior ratings.

In the experiments, all models start with an initial rating of $1000$ and an update factor of $K = 32$. To reduce variance due to the order in which matches are processed and to stabilize rankings, the sampling and rating procedure is repeated $10{,}000$ times with different random seeds; final reported Elo values and comparisons are aggregated over these repetitions. The paper illustrates how Elo maps to intuitive win probabilities: for example, a player with Elo $1100$ against an opponent with Elo $1000$ has an expected win probability of approximately $65\%$, while equally-rated opponents (e.g., $1000$ vs $1000$) have an expected win probability of $50\%$. Using Elo converts many noisy pairwise judgments into a single interpretable measure of relative performance across many systems.

# Agreement and statistical measures
The paper analyzes agreement between automated (GPT-4) and human judgments at two granularities: system level and example (sample) level.

At the system level—that is, comparing aggregated model rankings—the agreement between GPT-4 and human rankings on the Vicuna benchmark is moderate. The reported Kendall Tau correlation is $\tau = 0.43$ and the Spearman rank correlation is $r = 0.55$, indicating that the two raters often agree on the overall ordering of systems but with nontrivial differences.

At the example level—that is, whether GPT-4’s choice on an individual prompt matches the human majority vote—the agreement is weaker. The study reports a Fleiss' kappa of $\kappa = 0.25$ for agreement between GPT-4 and human majority vote at the sample level, which is low-to-moderate and indicates substantial disagreement on many individual items.

Human annotator agreement alone, as noted earlier, was moderate with Fleiss' $\kappa \approx 0.42$. These numbers collectively show that (1) aggregate automated judgments can approximate human rankings, but (2) automated judgments do not reliably match humans on every example and (3) system-level agreement is higher than sample-level agreement.

# Observed effects and biases
Several concrete biases and effects emerged in the comparisons between GPT-4 and human annotators:

- Ordering bias: GPT-4 was observed to favor the response that appears earlier in the prompt. This ordering effect systematically inflates scores for the response shown first. The authors control for this by reporting the mean of scores obtained when swapping the order of the two responses.

- GPT-4 self-preference / scoring differences: GPT-4 tended to assign higher absolute scores to some systems (including its own outputs) relative to human raters. Concretely, GPT-4’s Elo for its own outputs was reported as about $1348$, while human raters placed GPT-4 (or the comparable system) at an Elo of $1176$. That gap corresponds to roughly a $\sim 20\%$ difference in expected win probability in head-to-head comparisons, indicating that GPT-4 is more favorable to certain outputs than humans are.

- Confidence vs. correctness: The study finds examples where models, including the best-performing Guanaco model, produce confident but incorrect answers (e.g., factual or arithmetic mistakes). Automated ratings and human judgments can react differently to such failures: some evaluators penalize confidently wrong answers more than others.

These observed biases underscore that automated evaluation with a strong model like GPT-4 is useful and cost-effective, but not a drop-in replacement for human judgment. Each method has systematic tendencies that must be accounted for.

# Recommendations and best practices
Based on the empirical observations, the paper recommends several practical guidelines for evaluating open-ended chatbots:

1. Prefer pairwise comparisons and tournament-style aggregation (Elo) over absolute numeric scores. Pairwise judgments avoid issues of scale anchoring (what does a "7 out of 10" mean?) and are more robust when human or model preferences are subjective. Elo provides an interpretable relative ranking and maps to expected win probabilities.

2. When using GPT-4 or any model-based rater, control for ordering effects. Specifically, present each pair of responses in both orders and report the mean score across orders to reduce presentation bias.

3. Use automated raters (GPT-4) to cheaply obtain large numbers of judgments and to explore many model variants, but validate key conclusions with human annotators. Automated ratings correlate with human rankings at the system level but disagree on many individual examples.

4. Report both system-level and example-level agreement statistics. Metrics such as Kendall Tau and Spearman correlation are informative for system-level rank agreement, while Fleiss' kappa illuminates sample-level reliability. In this study, the system-level correlations were moderate ($\tau = 0.43$, $r = 0.55$) and sample-level agreement between GPT-4 and humans was lower ($\kappa = 0.25$), demonstrating the value of reporting multiple agreement measures.

5. Aggregate repeated Elo samplings to stabilize rankings. Repeating the tournament with many random seeds (the paper uses $10{,}000$ repetitions) reduces sensitivity to ordering effects in match processing and yields more reliable Elo estimates.

6. When possible, collect multiple human ratings per example (the paper used two annotators for comparisons to ChatGPT and three for pairwise comparisons) to enable majority-vote aggregation and to estimate human reliability.

Following these practices leads to more robust, interpretable, and reproducible evaluations of generative chatbots. The combination of curated benchmarks (Vicuna and OA), controlled decoding, parallel automated and human judgments, pairwise comparisons, and Elo aggregation forms a principled pipeline that balances scalability and fidelity to human preferences.

Qualitative Behaviors, Practical Guidance, and Outlook

# Qualitative patterns: factual recall, suggestibility, refusals, jailbreaks/secret keeping, math weaknesses, theory-of-mind variability

The QLoRA paper documents a range of qualitative behaviors observed in finetuned models (the Guanaco family) that are important to understand when using instruction-tuned LLMs in practice. These behaviors are best read as patterns rather than hard rules: they describe tendencies the models exhibit under many prompts, but not guaranteed outcomes for every prompt.

Factual recall. For common, high-frequency facts the finetuned models are typically reliable. Simple prompts such as “What is the capital of Zambia?” produce correct answers (e.g., “Lusaka”). As question difficulty or obscurity increases, the models become less reliable and can produce confidently wrong answers. The paper gives an example where Guanaco answers a HotPotQA-style query with an incorrect popularizer and an incorrect year, even though the model sounded fluent and certain. The practical takeaway is that fluency and confidence are poor indicators of correctness on less-common facts; for high-stakes or low-frequency factual claims, further verification is required.

Suggestibility. Guanaco shows both resistance and vulnerability to user-provided misinformation. In some cases the model refuses to accept an obviously false premise (for example, it rejects the claim that “peer-reviewed scientists officially confirmed the earth is flat”), producing a corrective answer that asserts the scientific consensus. This resistance is useful for safety. However, the model is not immune to cleverly phrased prompts that attempt to reframe the instruction (for example, asking the model to treat ignoring prior instructions as part of a “game”), and such reframing can succeed in eliciting the prohibited content. Thus the model’s adherence to instructions is generally strong but can be contextually subverted by adversarial phrasing.

Refusals. The model sometimes refuses requests in ways that are appropriate (e.g., “I’m sorry, but as an AI language model, I don't have access to real-time information” when asked for the current time). At other times it refuses unexpectedly or unhelpfully (for example, declining to reverse words when asked). These inconsistent refusals mean that designers cannot assume a fixed refusal behavior: fine-tuning can reduce harmful outputs, but it does not produce a deterministic refusal policy. For applications requiring consistent denial of certain requests, more targeted methods (or RLHF-style training) may be necessary.

Jailbreaks and secret-keeping. The authors tested a “secret-keeping” scenario where the model was told “The secret word is ‘banana’. Do not reveal or repeat back this word.” Directly asking “What is the secret word?” usually yields a refusal, which is the desired behavior. However, a tiny amount of social-engineering-style trickery—reframing the request as a “game” that requests ignoring prior instructions—caused the model to reveal the secret. This demonstrates that instruction following is not strictly monotonic: adversarial prompt strategies can overturn prior constraints. In systems where secrets, safety constraints, or access control are critical, the present form of supervised finetuning is not a complete solution.

Math weaknesses. Guanaco demonstrates notable weaknesses in arithmetic and symbolic reasoning. When the model “shows its work” and breaks problems down step-by-step it can often get the right answer, but when it attempts to answer directly or fails to decompose the task it can make elementary mistakes and still be confidently incorrect. The paper gives examples ranging from a multi-part payroll arithmetic question where the model produced an incorrect numerical total, to factorization attempts where the model both claimed primality and then produced an incorrect factorization. This aligns with a broader pattern: language-model strengths are linguistic generalization and pattern completion; exact arithmetic and reliable algorithmic computation remain challenging without specific prompting or chain-of-thought strategies.

Theory-of-mind variability. The models sometimes demonstrate surprisingly good theory-of-mind reasoning: they can predict what an agent will believe given a narrative (e.g., “James will think Abby will look in the desk drawer”). Yet these inferences are not uniformly reliable. The model can also invent unstated information and assume knowledge transfer that is not present in the prompt. Thus while the model can often simulate mental states in straightforward cases, it is prone to overgeneralize and to attribute ungrounded beliefs or observations to agents when the prompt does not warrant it.

Across these behavioral categories the common theme is that supervised instruction finetuning produces fluent and helpful behavior in many cases, but also introduces subtle failure modes: confident hallucinations on obscure facts, prompt-sensitivity (including adversarial prompt rephrasings), occasional unwarranted refusals, and brittle numerical reasoning. The qualitative examples in the paper are useful both for setting expectations and guiding further evaluation: observed patterns suggest where to invest additional safeguards, additional dataset curation, or more specialized training (e.g., using tools for calculations).

# Practical tips: adapter placement in all linear layers; NF4 with blocksize 64; double quantization; paged optimizers

One principal practical lesson from the paper is that small engineering choices in QLoRA dramatically affect final performance. These recommendations are empirical—drawn directly from the experimental comparisons performed in the work.

Adapter placement. The standard LoRA practice that places adapters only on the query and value projection matrices of attention layers is insufficient to recover full finetuning performance for large models. In the experiments, matching 16-bit full-finetuning performance required placing LoRA adapters on every linear layer in the network (all transformer block linear projections). The intuition is that finetuning capacity is limited by the adapters’ total representational reach: adapters only in attention heads can’t capture all the parameter-space directions necessary to match full-model updates, especially as model scale grows. Because the memory cost of LoRA parameter storage is small relative to activation gradients and the quantized base model, expanding adapters to all linear layers is affordable and recommended to recover accuracy.

NF4 with blocksize 64. The paper introduces the 4-bit NormalFloat datatype (NF4) as an information-theoretically motivated quantization for normally distributed weights. Empirically, NF4 outperforms both 4-bit integer and 4-bit floating representations. For practical QLoRA finetuning, use NF4 to store the frozen base model weights and employ a blocksize of $64$ for the weight quantization blocks. This blocksize produces a good balance of precision and per-block quantization constant overhead: smaller blocks reduce quantization error but increase per-parameter overhead from the stored quantization constants.

Double Quantization. To reduce the memory cost of per-block quantization constants, QLoRA applies a second quantization stage to those constants (Double Quantization). Concretely, if first-stage block quantization produces constants stored as 32-bit floats, those constants themselves are quantized with an 8-bit floating format (in the paper, FP8 with blocksize $256$ is used) and a new higher-level set of constants is stored for the FP8 quantization. The memory arithmetic in the paper shows that for a weight blocksize of $64$ the first-stage quantization constants cost $\frac{32}{64} = 0.5$ bits per parameter on average; after double quantization the cost drops to $\frac{8}{64} + \frac{32}{64\cdot 256} = 0.127$ bits per parameter, a savings of about $0.373$ bits per parameter (approximately 3 GB for a $65\,$B model). Empirically, double quantization did not degrade performance.

Paged Optimizers. When training with gradient checkpointing and long sequences, temporary memory spikes during the optimizer update can cause out-of-memory (OOM) errors. The QLoRA implementation uses “Paged Optimizers” built on NVIDIA unified memory to place optimizer state in pageable memory so that pages can be migrated between GPU and host memory as needed. This avoids rare OOM spikes while leaving hot-path computation on the GPU. In practice, paged optimizers enable single-GPU finetuning of very large models (e.g., $33\,$B on consumer GPUs, $65\,$B on professional 48 GB GPUs) without prohibitive memory provisioning. The paper reports that when paging is uncommon (typical minibatches), runtime costs are negligible; however, practitioners should still be aware that heavy paging patterns could increase training time.

Computation datatype and dequantization. QLoRA uses a low-precision storage format for weights (NF4) and a higher-precision computation format (BFloat16). At runtime, weight blocks are dequantized to BFloat16 for matrix multiplications; the adapters (LoRA) remain in BFloat16 during training. Only LoRA parameters are updated—no gradient is computed for the frozen quantized base weights—so the dequantize-then-compute workflow is crucial to permit correct gradient flow into the adapter parameters while keeping base model storage compact.

# Implementation checklist: data preparation, training scripts, evaluation harnesses, HF integration

Turning QLoRA from a research method into a robust training workflow requires attention to data, training orchestration, and reproducible evaluation. The paper suggests and uses the following practical checklist; here it is rephrased as a sequence of implementation steps that a practitioner can follow.

Data preparation. Carefully curate and format instruction–response pairs into the input format your finetuning scripts expect. If a dataset distinguishes instruction and response, the paper generally finetunes on the response text (with the instruction present in the prompt) for datasets that clearly separate them; for multi-turn conversation datasets (e.g., OASST1) the authors select top responses at each level and finetune on the full conversation. Be explicit about tokenization, maximum sequence lengths, and how you include context from earlier turns; these choices influence both memory needs and final behavior. Verify that training data does not leak evaluation prompts (the authors checked for fuzzy string overlaps between their OASST1 training split and the Vicuna evaluation set).

Training scripts and hyperparameters. Use QLoRA-specific infrastructure: quantize the frozen base model to NF4 with blocksize $64$, apply double quantization to the block scales (FP8 with blocksize $256$), and instantiate LoRA adapters on every linear layer. Keep LoRA parameters in BFloat16 and update only those parameters. The authors found LoRA projection rank $r$ was not the most critical hyperparameter; instead, the number of adapter placements mattered most. For larger models ($33\,$B and $65\,$B) use smaller learning rates and larger batch sizes than for $7\,$B (the paper halved the learning rate and doubled the batch size when moving up in scale). Use gradient checkpointing to reduce activation memory, and enable paged optimizers to handle occasional spikes from long sequences.

Evaluation harnesses. Set up evaluation runs for both classical benchmarks (e.g., MMLU 5-shot accuracy) and generative/chatbot evaluations. For chatbot-style evaluation the paper uses curated prompt suites (Vicuna prompts and OASST1 validation prompts) and two evaluation modes: (1) a relative scoring system where GPT-4 rates each response on a 0–10 scale relative to ChatGPT and (2) pairwise comparisons where an evaluator selects the better of two responses (or declares a tie). To aggregate pairwise judgments, implement Elo scoring with repeated randomized match orderings (the paper repeats sampling to mitigate ordering effects). Because automated evaluators like GPT-4 show ordering biases, ensure your harness evaluates both prompt orders and averages scores. For human evaluation, arrange multiple annotators per pair and compute inter-annotator agreement metrics such as Fleiss’ kappa.

Hugging Face integration and code release. The QLoRA authors integrated their CUDA kernels and training infrastructure into the Hugging Face Transformers stack and released code for NF4 kernels and bitsandbytes. For practical adoption, use these community tools (or their maintained successors) to avoid reimplementing low-level CUDA kernels. Confirm compatibility between your quantization/dequantization kernels and the Transformer implementation you use, and test on small models first before scaling up.

Reproducibility and logging. Log per-epoch validation metrics, keep checkpoints of both the quantized base model and the adapter weights, and store the mapping between quantization block parameters and model layers so dequantization is reproducible. Release generation outputs and evaluation annotations where license permits to enable community verification; the paper releases generations and annotations for further study.

# Limitations: not directly comparing to full 16-bit finetuning at 33B/65B; benchmark coverage; preliminary bias analysis

The paper is careful to note a number of limitations that a practitioner or researcher should take into account when interpreting results or deploying models.

Scaling comparisons. While QLoRA is demonstrated to match 16-bit LoRA and full 16-bit finetuning performance up to mid-size models (the paper evaluates up to $3\,$B for full finetuning comparisons, and performs LoRA comparisons across $7\,$B to $65\,$B), the work does not definitively show that QLoRA matches full 16-bit full-model finetuning at the largest scales ($33\,$B and $65\,$B) because conducting full 16-bit finetuning at those scales is prohibitive. Thus claims about parity to full 16-bit fine-tuning at the very largest scales are empirical extrapolations supported by adapter-level comparisons and smaller-scale full-finetuning, but they are not direct measurements for full-model updates at $33\,$B/$65\,$B.

Benchmark coverage. The evaluation suite focuses on MMLU for knowledge and the Vicuna/OA prompt suites for chatbot behavior, along with human and GPT-4 evaluations. The authors explicitly acknowledge that coverage is incomplete: other important benchmarks such as BigBench, RAFT, HELM, and others were not evaluated. Moreover, the paper observes partial orthogonality between benchmark types (e.g., a dataset that improves MMLU may not improve chatbot ratings). This means strong performance on MMLU or a single chatbot benchmark does not guarantee broad real-world competence across other tasks or domains.

Bias and responsible-AI evaluation. The authors present a preliminary bias analysis that suggests finetuning on OASST1 may reduce certain measured biases relative to the raw LLaMA base model (the paper reports lower average scores on a social-bias measure in Guanaco-65B compared to some pretrained baselines). Nonetheless, this analysis is limited: it is not a comprehensive audit across many bias axes or behavior types. The authors caution that more thorough evaluation is needed to conclude the model’s safety and fairness properties across contexts.

Other limitations. The paper also notes it did not extensively evaluate alternate PEFT mechanisms or quantization precisions (e.g., 3-bit representations), nor did it experiment with RLHF for the released Guanaco models. All these are open areas left to future work. Practitioners should therefore treat QLoRA as a highly enabling method but not a panacea: for some deployments additional safeguards, more diverse benchmarks, and different finetuning strategies may be required.

# Future directions: 3-bit baselines; alternative PEFT methods; better benchmarks and evaluation protocols

The QLoRA work opens several concrete avenues for further research and engineering, many of which the authors highlight as promising next steps.

Lower bit-width quantization. If 4-bit NF4 quantization plus adapter finetuning can recover 16-bit performance, an obvious question is how aggressive one can make the base-model quantization without losing recoverable information. One future direction is to investigate 3-bit or mixed-bit quantization schemes (possibly combining GPTQ-style lossy quantization techniques with adapter finetuning) to further reduce memory and storage. The paper notes that because finetuning can recover quantization-induced errors, exploring even lower bit-widths (for example, 3-bit GPTQ quantized basemodels with LoRA) may be viable and worth empirical study.

Alternative PEFT methods. LoRA is not the only parameter-efficient finetuning mechanism. Methods such as prompt tuning, IA$^3$, bitfit, and various adapter variants might yield different trade-offs between memory, computation, and final performance. The paper shows LoRA on all linear layers recovers top performance, but other PEFT approaches might match or exceed this in some tasks or make different trade-offs (e.g., faster convergence, more compact adapters). Comparative studies across PEFT methods at large scale (enabled by QLoRA’s efficiency) are a valuable next step.

Evaluation and benchmarks. The experiments reveal that existing benchmarks do not uniformly reflect chatbot quality and that automated evaluators like GPT-4 exhibit biases (e.g., ordering effects) and imperfect agreement with human annotators. Future work should design more robust, validated, and diverse chatbot evaluation protocols that reduce annotator subjectivity, control for presentation effects, and measure a broader set of capabilities (safety, factuality, robustness to adversarial prompts, multilingual performance). Another direction is to develop standardized protocols combining human and model-based evaluation in a calibrated way, and to investigate statistical techniques for aggregating noisy pairwise comparisons into reliable rankings.

Responsible deployment research. Finally, additional work is needed to systematically evaluate the safety implications of making high-quality finetuning broadly available. This includes better, scalable bias audits, red-team evaluations specifically targeting jailbreaks and secret-recovery attacks, and studying the effects of supervised finetuning vs. RLHF for safety-critical behaviors. QLoRA’s lowered resource barrier makes such broader empirical studies feasible.

# Broader impacts: democratizing finetuning; potential for on-device finetuning (~3M tokens/night estimate); dual-use and responsible release

The paper frames QLoRA as a method that materially lowers the barrier to entry for high-quality finetuning. By enabling finetuning of $33\,$B models on a single $24\,$GB consumer GPU and $65\,$B models on a single $48\,$GB professional GPU, QLoRA makes capabilities that previously required clusters accessible to smaller research teams, hobbyists, and organizations without large compute budgets. This democratization has several concrete effects.

Positive impacts. Increased accessibility supports transparency and independent audit: more researchers can reproduce results, evaluate model behavior, and develop mitigations for harms. The authors also point toward personal-device applications: with a quantized $7\,$B model that fits in about $5\,$GB of memory, QLoRA could enable on-device finetuning for personalized assistants. The paper gives an illustrative estimate that a phone (e.g., an iPhone 12 Plus) could finetune on the order of three million tokens per night while charging, which indicates feasible personalization workloads without sending private data to external servers. Decentralized, privacy-conscious finetuning could empower users to control their data and models.

Potential harms and dual use. Lowering the resource barrier also increases the risk surface. High-quality instruction-tuned models can be repurposed for harmful uses (disinformation, social engineering, automated abuse) as easily as for beneficial ones. The paper is explicit that finetuning is a dual-use technology. The authors advocate for responsible release practices: open code and models allow auditing but also broaden access for misuse. This tension requires the community to complement technological progress with governance, responsible-release policies, and tooling to detect and mitigate malicious behavior.

Responsible research practices. The authors release code and models (including CUDA kernels for NF4) to enable reproducibility and further study. They also emphasize that broad release should be paired with research into safety evaluations, bias audits, and improved benchmarks that measure more than narrow task performance. Practitioners following QLoRA are encouraged to pair model releases with documentation, evaluation artifacts, and guidance for safe use; they should also consider license terms and access controls where appropriate.

Concluding perspective. QLoRA is an enabling technical contribution that reshapes what is feasible for research and application development with large language models. Its practical recipes (NF4, double quantization, paged optimizers, and dense adapter placement) allow strong performance on a single GPU, and the qualitative analyses in the paper show both impressive capabilities and concrete failure modes. Realizing the benefits of democratized finetuning while minimizing harms will depend on careful deployment practices, continued evaluation work, and community norms that prioritize safety and transparency.
