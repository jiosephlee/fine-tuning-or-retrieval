# Key idea: backprop through a frozen 4-bit model into LoRA adapters
The core conceptual idea behind <|endoftext|> is deceptively simple but powerful: store the large <|endoftext|> base model in a highly compressed low-precision format (4-bit), keep those weights frozen, and route all trainable capacity through a much smaller set of learnable parameters <|endoftext|> Adapters, or LoRA). During training, <|endoftext|> are backpropagated through the frozen, quantized base model into the LoRA adapters, which are the only parameters updated.

There are two important aspects to unpack in that description. First, “frozen, quantized base model” means the huge parameter tensors are stored in a 4-bit representation for memory efficiency; they are not directly updated during finetuning. Second, LoRA adapters are small <|endoftext|> matrices inserted into the network so that the <|endoftext|> expressive behavior can still change significantly without modifying the full weight set. # Contributions: <|endoftext|> <|endoftext|> Double <|endoftext|> <|endoftext|> Optimizers
<|endoftext|> is more than “4-bit + LoRA”; the paper introduces three concrete technical innovations that together make faithful 4-bit finetuning practical at very large scales.

1) 4-bit NormalFloat <|endoftext|>

<|endoftext|> requires choosing a small discrete set of representable values and a mapping from high-precision numbers into that set. Standard <|endoftext|> formats <|endoftext|> integer <|endoftext|> or naive 4-bit floating point) are not information-theoretically optimal when the underlying distribution of weights is known. <|endoftext|> neural network weights are typically approximately zero-centered and Gaussian-like. <|endoftext|> constructs a 4-bit data type by taking the optimal quantiles of a standard normal distribution and mapping them into the representable 4-bit values. Concretely, the method estimates the appropriate quantile boundaries for a standard normal $N(0,1)$, rescales the particular weight tensor via its absolute maximum into the $[-1, 1]$ range that matches the data type, and assigns each weight to the nearest of these normal-quantile-derived levels. Because <|endoftext|> is matched to the empirical <|endoftext|> shape of model weights, it both uses the limited 4-bit bins more efficiently and reduces <|endoftext|> error compared to generic 4-bit integer or float schemes.

One practical subtlety the paper addresses is representing zero exactly. A symmetric k-bit quantile layout can lack a discrete zero value, which harms <|endoftext|> or other genuinely zero values. NFk (and <|endoftext|> specifically) remedies this by constructing an <|endoftext|> quantile partition for the negative and positive sides such that zero is one of the representable levels and every <|endoftext|> bin has roughly equal expected occupancy.

2) Double <|endoftext|>

Using small block sizes is important for precise per-block <|endoftext|> of weight matrices, but the per-block <|endoftext|> scales (the “quantization constants” or scales) themselves add non-negligible overhead if stored at 32 bits. Double <|endoftext|> compresses these <|endoftext|> <|endoftext|> themselves. The process treats the per-block FP32 scale values as inputs to a second quantizer, storing the second-level quantized <|endoftext|> in a <|endoftext|> format (the authors use 8-bit floats for this second pass) and keeping a small number of FP32 “meta-scales” for groups of these second-level <|endoftext|> In formulaic terms: the original weight storage is represented by k-bit integer-like indices <|endoftext|> plus per-block FP32 scales $c_2^{\text{FP32}}$; Double <|endoftext|> quantizes those $c_2^{\text{FP32}}$ into $c_2^{\text{FP8}}$ plus a higher level $c_1^{\text{FP32}}$. During <|endoftext|> the two levels are composed to recover the BF16 computation weights.

The memory <|endoftext|> in the paper gives intuition for why this matters: with blocksize 64, storing a 32-bit scale per block costs on average $32/64 = 0.5$ bits per parameter. After double <|endoftext|> (with 8-bit floats for the second level and a blocksize of 256 for the meta-level), the average cost drops to about $8/64 + 32/(64\cdot256) \approx 0.127$ bits per parameter — a savings of roughly $0.373$ bits per parameter, which translates to multiple gigabytes for the largest models (the paper reports around a 3 GB reduction for a 65B model).

3) <|endoftext|> Optimizers

During training, <|endoftext|> states and occasional memory <|endoftext|> (for example, due to long sequences combined with <|endoftext|> checkpointing) can exceed the GPU memory capacity even if the steady-state storage would fit. <|endoftext|> Optimizers solve this by using NVIDIA unified memory to allow <|endoftext|> state tensors to be <|endoftext|> between GPU memory and host (CPU) memory automatically. This is analogous to virtual memory <|endoftext|> when an <|endoftext|> needs a particular tensor, it is moved to the GPU on demand; otherwise it can live in CPU RAM. This mechanism prevents out-of-memory failures caused by transient peaks without requiring the practitioner to keep everything permanently resident on GPU.

Combining these three techniques with LoRA-style adapters gives the full <|endoftext|> method: weights stored in <|endoftext|> with double-quantized scales, on-demand <|endoftext|> to BF16 for computation, LoRA adapters trained in BF16, and <|endoftext|> optimizers to keep transient memory <|endoftext|> manageable.

# Guanaco model family and benchmark highlights (up to 99.3% of ChatGPT on Vicuna)
Applying <|endoftext|> at scale enabled the authors to finetune very large models on single GPUs and to run an extensive experimental campaign. The paper uses <|endoftext|> to train the Guanaco family of models (adapters applied to <|endoftext|> base models) and reports striking empirical results.

Memory and training-time practicality. <|endoftext|> reduces the memory required to finetune a LLaMA-65B model from the 16-bit requirement of over 780 GB to under 48 GB. This compression enables finetuning a 65B parameter model on a single 48 GB GPU and finetuning a 33B model on a single 24 GB consumer GPU. Practical training times were demonstrated in the experiments: the best Guanaco model reaches 99.3% of ChatGPT performance (on the Vicuna benchmark) after roughly 24 hours of finetuning on a single GPU; a competitive 33B Guanaco can be trained on a 24 GB consumer GPU in less than 12 hours. At inference/deployment, the smaller Guanaco 7B model only needs about 5 GB of memory, enabling running on more <|endoftext|> hardware.

Benchmark performance and breadth. The Guanaco models outperform all previously openly released models on the Vicuna benchmark and approach the performance of very strong closed-source systems. The largest Guanaco model (65B) achieves 99.3% of the performance level of ChatGPT on Vicuna according to the <|endoftext|> GPT-4-based and human-evaluation protocols. Across the experimental suite, QLoRA-equipped models reproduce the performance of 16-bit full finetuning in standard academic tasks: <|endoftext|> plus double <|endoftext|> recovers performance compared to 16-bit <|endoftext|> on GLUE, Super-NaturalInstructions, and MMLU across model sizes.
