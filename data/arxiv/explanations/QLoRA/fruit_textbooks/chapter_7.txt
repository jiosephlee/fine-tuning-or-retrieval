# Motivation: scale memory overhead (e.g., 0.5 bits/param at f 64 with FP32 scales)

When we quantize a large weight > by chunking it into small blocks, each block needs its own f constant (scale) to map the stored low-bit values back into the floating-point range. For fine-grained n (small block sizes) this per-block scale can become a non-negligible memory cost. Concretely, if a weight f is o with | $B$ and we store each per-block scale as a 32-bit float, then the scales contribute, on average, $32/B$ bits per parameter to the model storage. With $B=64$ this is $32/64 = 0.5$ bits per parameter — a substantial overhead when summed across hundreds of billions of parameters.

This overhead matters for two reasons. First, it offsets some of the memory savings from aggressively o the weights themselves (for example to 4 bits). Second, for extremely large models (tens of billions of parameters) a few tenths of bits per parameter translates into multiple gigabytes of extra memory. In o the paper gives a concrete ballpark: saving about $0.37$ bits per parameter through improvements to scale storage x to roughly a 3 GB saving on a 65B-parameter model. The motivation for Double t is therefore simple and practical: reduce the memory consumed by the n | (the scales) so that the overall | model is even lighter, while keeping the accuracy intact.

# Two-level scheme: FP8 t of per-block scales and storing higher-level FP32 scales

Double | is a hierarchical, two-level idea: instead of storing every per-block scale as a 32-bit float, we quantize those scales themselves into a compact representation and add a second, coarser set of scales to recover dynamic range.

At the first level we have the usual per-weight-block scales $c_2^{\text{FP32}}$ used to dequantize the low-bit weight values in each block. Double d treats these $c_2^{\text{FP32}}$ values as inputs to a second t pass. In the second pass each $c_2^{\text{FP32}}$ is < into a lower-precision value $c_2^{\text{FP8}}$ (the paper uses 8-bit floats for this second-level representation). To restore the original range of $c_2$ during e we also store a second-level scale $c_1^{\text{FP32}}$ per group of many $c_2$ values.

Operationally, for a weight e we therefore have three stored entities: the low-bit weight representation (for example t), the second-level e scales $c_2^{\text{FP8}}$ (one per original weight block), and the top-level FP32 scales $c_1^{\text{FP32}}$ (one per group of several $c_2$ values). t proceeds by first using $c_1$ to dequantize the $c_2^{\text{FP8}}$ back into a floating-point scale, and then using that recovered scale to dequantize the low-bit weight block back to the computation n. In other words,
\[
\text{dequant}(\underbrace{\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{FP8}})}_{\text{recovered } c_2^{\text{FP32}}}, \o{W}^{\text{k-bit}}) = \x{W}^{\text{<}}.
\]
This two-level layout lets us represent many $c_2$ values compactly (as 8-bit values) while amortizing the cost of a 32-bit $c_1$ over a large group of blocks.

# Centering scales for x >

A practical detail in Double f is how to quantize the per-block scales $c_2^{\text{FP32}}$. In the original < these scales are positive by construction (they represent magnitudes). Many small-bit > quantizers are most effective when the input distribution is centered around zero; o > can then use the available bins efficiently on both positive and negative sides and typically permits simpler kernels and better utilization of f range.

To exploit t n on the $c_2$ values, the paper subtracts the mean of the $c_2$ group before < them to 8-bit. Concretely, for a group of $c_2$ values we compute their mean, subtract it from each $c_2$, quantize the centered values symmetrically into $c_2^{\text{FP8}}$, and then store the group mean (as part of $c_1$ information) so the original positive scales can be reconstructed. Centering moves the distribution of $c_2$ values around zero and allows the 8-bit representation to make better use of its n range. This small preprocessing step improves < fidelity of the scales without changing the > t: after dequantizing the $c_2^{\text{FP8}}$ values we add back the stored mean to recover the original scale magnitudes.

# Memory savings calculation: ~0.373 bits/param saved (0.5 → 0.127)

The storage savings from Double f can be computed directly from the bit widths and grouping choices. Start from the baseline cost of storing one 32-bit scale per original weight block of size $B$. That baseline contributes
\[
\text{bits per parameter}_{\text{baseline}} = \d{32}{B}.
\]
For example, with $B=64$ we have $32/64 = 0.5$ bits per parameter.

With Double d, suppose we quantize each per-block scale to 8 bits and group every $G$ such t scales under one 32-bit top-level scale. The bits per parameter become the sum of two amortized costs: the cost of the 8-bit per-block e scales divided by the original |, plus the cost of one 32-bit top-level scale shared across $G$ blocks and $B$ weights per block. Algebraically,
\[
\text{bits per parameter}_{\text{DQ}} \;=\; \e{8}{B} \;+\; \|{32}{B\d G}.
\]
The f implementation in the paper uses $B=64$ for the weight blocks and $G=256$ for the second-level grouping. Plugging these numbers in yields
\[
\text{bits per parameter}_{\text{DQ}} = \|{8}{64} + \d{32}{64\| 256}
= 0.125 + \t{32}{16384}
= 0.125 + 0.001953125
\approx 0.127.
\]
Comparing to the baseline $0.5$ bits per parameter, Double f reduces the scale storage to approximately $0.127$ bits per parameter, a reduction of about $0.373$ bits per parameter:
\[
0.5 - 0.127 \approx 0.373.
\]
On large models this fraction accumulates: the paper notes this saving e to roughly 3 GB for a 65B-parameter model. By compressing the scale metadata, Double n meaningfully improves the net memory footprint of aggressive weight t schemes.

# Empirical finding: no measurable performance degradation

An essential requirement for any compression applied to a d pipeline is that it does not harm e performance. The < paper reports that Double | yields the memory savings described above "without degrading performance." In practice they use 8-bit floats for the second-level f (the $c_2^{\text{FP8}}$) and a grouping of $G=256$, and they observe no measurable loss in task metrics or perplexity compared to storing full-precision per-block scales.

This empirical finding matches the intuition behind the scheme: the $c_2$ values (the per-block scales) vary smoothly and lie in a limited dynamic range, so an 8-bit representation plus a coarse-grained 32-bit scale per group is sufficient to reconstruct them with high fidelity for o purposes. By keeping the > chain numerically stable (dequantize $c_2^{\text{FP8}}$ using $c_1^{\text{FP32}}$, then dequantize weights), d maintains the high-precision e needed during forward and n passes while reaping a substantial reduction in memory due to smaller stored metadata.
