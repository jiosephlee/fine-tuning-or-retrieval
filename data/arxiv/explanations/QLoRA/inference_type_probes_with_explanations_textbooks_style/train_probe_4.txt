Chapter Title: Managing Memory in QLoRA: Why Paged Optimizers Prevent Out-of-Memory Errors

# Introduction

Finetuning large language models demands substantial memory, and the challenge intensifies as model size and sequence length grow. QLoRA demonstrates that it is possible to finetune a quantized 4-bit model while matching 16-bit performance, even at 65B parameters, on a single 48 GB GPU. Achieving this outcome requires careful control of memory usage across the entire training pipeline, including model storage, forward and backward computation, and optimizer state management. A central innovation in QLoRA is the use of Paged Optimizers, which are specifically introduced to handle memory spikes during training. These spikes are particularly pronounced when processing mini-batches with long sequence lengths. Without Paged Optimizers, such spikes make the system prone to out-of-memory (OOM) errors that recur unpredictably during training.

This chapter explains, in detail and intuitively, why long-sequence finetuning triggers memory spikes, how QLoRA’s quantization and adapter design reduces—but does not eliminate—training memory pressure, and how Paged Optimizers leverage unified memory to avert OOM. We will see that, in the training regime targeted by QLoRA, omitting Paged Optimizers would most likely result in repeated out-of-memory failures.

# Memory in Finetuning: Where It Comes From

Understanding why OOM errors occur requires a clear view of what consumes memory during finetuning. There are three major contributors: model parameters, activations and their gradients, and optimizer states.

First, model parameters can be compressed at storage time. QLoRA stores pretrained model weights in a 4-bit quantized representation that is dequantized on the fly to a 16-bit computation data type (BFloat16) for forward and backward passes. Concretely, a typical block-wise quantization scheme uses a per-block rescaling constant to map a full-precision tensor into a low-bit tensor. For instance, 8-bit quantization of an FP32 tensor to Int8 with range \([-127,127]\) uses
\[
\mathbf{X}^{\text{Int8}} = \text{round}\!\left(\frac{127}{\text{absmax}(\mathbf{X}^{\text{FP32}})} \,\mathbf{X}^{\text{FP32}}\right)
= \text{round}\!\left(c^{\text{FP32}} \cdot \mathbf{X}^{\text{FP32}}\right),
\]
where \(c^{\text{FP32}}\) is the quantization constant. Dequantization follows as
\[
\text{dequant}(c^{\text{FP32}}, \mathbf{X}^{\text{Int8}}) = \frac{\mathbf{X}^{\text{Int8}}}{c^{\text{FP32}}} = \mathbf{X}^{\text{FP32}}.
\]
In QLoRA, the base model is stored in 4-bit NormalFloat (NF4), which is information-theoretically optimal for zero-mean normally distributed weights. At compute time, the quantized weights are dequantized into BFloat16 for matrix multiplications and gradient computations. This sharply reduces parameter storage.

Second, adapter finetuning further reduces the number of trainable parameters. LoRA augments a linear projection \(\mathbf{X}\mathbf{W}\) with a low-rank term:
\[
\mathbf{Y} = \mathbf{X}\mathbf{W} + s\,\mathbf{X}\mathbf{L}_1\mathbf{L}_2,
\]
where \(\mathbf{L}_1 \in \mathbb{R}^{h \times r}\) and \(\mathbf{L}_2 \in \mathbb{R}^{r \times o}\), and \(s\) is a scalar. The base weights \(\mathbf{W}\) remain frozen and quantized; only the adapters are updated in 16-bit precision.

Third, and crucially for the memory story, most of the finetuning memory footprint comes not from trainable parameters but from activation gradients and optimizer states. Even when LoRA adapters comprise a very small fraction of the full model size, the gradients flowing through the model and inputs to LoRA layers are significant. For example, for a 7B model with common LoRA settings, the memory used by LoRA parameters can be much smaller than the memory used by LoRA input gradients, and the 4-bit base model itself still requires gigabytes of memory. Gradient checkpointing can reduce average activation memory by recomputing parts of the forward pass during backpropagation; however, it does not eliminate peak memory spikes, especially for long sequences.

# QLoRA’s Quantization and Dequantization in Training

QLoRA uses a storage type and a computation type. The storage type is typically NF4 for weights and low-bit types for quantization constants, while the computation type is BFloat16 for matrix multiplications and gradient flows. A single linear layer in QLoRA with double quantization is expressed as
\[
\mathbf{Y}^{\text{BF16}} = \mathbf{X}^{\text{BF16}} \,\text{doubleDequant}\!\left(c_1^{\text{FP32}},\, c_2^{\text{k-bit}},\, \mathbf{W}^{\text{NF4}}\right)
+ \mathbf{X}^{\text{BF16}}\mathbf{L}_1^{\text{BF16}}\mathbf{L}_2^{\text{BF16}},
\]
where
\[
\text{doubleDequant}\!\left(c_1^{\text{FP32}},\, c_2^{\text{k-bit}},\, \mathbf{W}^{\text{k-bit}}\right)
= \text{dequant}\!\big(\,\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}),\, \mathbf{W}^{\text{4bit}}\big)
= \mathbf{W}^{\text{BF16}}.
\]
Here, \(\mathbf{W}\) is stored in NF4 with blocksize 64 to preserve quantization precision, and the second-level constants \(c_2\) are stored in FP8 with blocksize 256 to save memory. Only the LoRA parameters \(\mathbf{L}_i\) receive direct weight updates; gradients with respect to \(\mathbf{W}\) are not formed. Still, the gradients that reach \(\mathbf{L}_i\) depend on the dequantized \(\mathbf{W}^{\text{BF16}}\), so dequantization is part of the backward path as well.

This design decreases the persistent memory needs of the base model and of optimizer states for base weights. Nevertheless, per-step memory depends on the activations and their gradients, which scale with sequence length and batch construction. Thus, even with aggressive quantization and parameter-efficient finetuning, the training graph can exhibit transient peaks in memory consumption.

# Why Long Sequences Cause Memory Spikes

The root cause of memory spikes during finetuning is the interaction between long sequence processing, gradient checkpointing, and the need to maintain or recompute activations across many layers. Gradient checkpointing trades off extra computation for lower average activation memory by discarding some activations during the forward pass and recomputing them during the backward pass. While this lowers the average memory footprint, it does not guarantee uniform memory usage throughout the training step.

Long sequences amplify this effect. A mini-batch that includes a long sequence exerts pressure on multiple components simultaneously: more tokens flow through each layer, backward passes must traverse larger computational graphs, and recomputation stages transiently rebuild activations across deep stacks of layers. The result is a burst of memory allocation that exceeds the steady-state memory levels observed on shorter sequences.

The paper explicitly identifies these as “gradient checkpointing memory spikes that occur when processing a mini-batch with a long sequence length.” Even with a 4-bit base model and LoRA, such spikes can momentarily push total GPU memory requirements beyond the physical limit of the device. When this happens and no mechanism exists to absorb the overflow, the GPU will throw an out-of-memory error, abruptly interrupting training.

# Double Quantization Reduces Persistent Overheads, Not Spikes

Double Quantization (DQ) shrinks the memory footprint of quantization constants themselves by quantizing the quantization constants. If the first level of quantization uses FP32 constants per block of size 64, the overhead is \(32/64 = 0.5\) bits per parameter on average. With double quantization, the second level uses 8-bit floats for constants with blocksize 256, and the per-parameter overhead becomes
\[
\frac{8}{64} + \frac{32}{64 \cdot 256} = 0.127 \text{ bits},
\]
a reduction of \(0.373\) bits per parameter on average. This is a substantial saving at the model scale, amounting to about 3 GB for a 65B model.

Crucially, these savings reduce persistent memory usage but do not directly address transient peaks during backpropagation. DQ helps keep the base footprint small so that more headroom remains available on the GPU; however, spikes induced by long sequences can still exceed the available headroom if optimizer states and other buffers must all remain resident on the GPU during the entire step. Therefore, despite DQ, a mechanism is still needed to dynamically manage sudden allocation bursts.

# Paged Optimizers: How They Prevent Out-of-Memory

Paged Optimizers solve the spike problem by exploiting NVIDIA unified memory, which supports automatic page-by-page transfers between CPU and GPU memory. In essence, optimizer states are allocated in a way that allows them to be paged out to CPU memory when GPU memory is under pressure and paged back in when needed for the optimizer update.

This approach is analogous to memory paging between RAM and disk in general-purpose operating systems. In the context of QLoRA, Paged Optimizers offload optimizer state pages from the GPU to the CPU during the most memory-intensive phases of the training step, such as during the backward pass with long sequences and gradient checkpointing recomputation. When the step reaches the optimizer update phase, the relevant pages are brought back to the GPU on demand to complete the update. By orchestrating this exchange transparently, Paged Optimizers allow the training loop to continue without OOM, even when transient requirements exceed the physical GPU memory.

The paper emphasizes the practical consequence: paged memory for optimizer states “are then automatically evicted to CPU RAM when the GPU runs out-of-memory and paged back into GPU memory when the memory is needed in the optimizer update step.” This is specifically designed to handle the unpredictable nature of spikes during long-sequence processing.

# What Happens Without Paged Optimizers

Without Paged Optimizers, all optimizer states must remain fully resident in GPU memory during the training step. When a mini-batch contains a long sequence, gradient checkpointing can trigger a transient surge in memory demand due to recomputation and enlarged activation graphs. If the GPU lacks sufficient free memory to accommodate this surge, the system has no mechanism to temporarily offload less urgently needed buffers. As a result, the training step fails with an out-of-memory error.

Because long sequences can appear intermittently in realistic training corpora and because their exact interaction with checkpointing and model depth produces nonuniform memory pressure, such OOM errors tend to recur. The paper frames Paged Optimizers precisely as a solution to “avoid the gradient checkpointing memory spikes that occur when processing a mini-batch with a long sequence length,” thereby preventing the OOM failures that would otherwise repeatedly interrupt training on a single machine.

# Empirical Notes on Performance and Stability

While Paged Optimizers are crucial to making 33B and 65B QLoRA finetuning feasible on single GPUs with 24–48 GB of memory, the paper reports that their use does not degrade training throughput in the examined setup. Specifically, for 65B models on 48 GB GPUs with a batch size of 16, Paged Optimizers provide the same training speed as regular optimizers. This reinforces the main motivation: they safeguard against out-of-memory errors in the presence of long sequences and memory spikes, without imposing a measurable speed penalty in the tested configuration.

It is also noted that paging only occurs when processing mini-batches with long sequence lengths, which is comparatively rare. Therefore, the system avoids paying a constant overhead and instead uses paging only when needed to prevent failure. Put differently, Paged Optimizers enable high-utilization regimes close to the GPU memory limit, but they “catch” the rare spikes, making long-sequence finetuning reliable on limited-memory devices.

# Summary and Intuition

QLoRA’s memory-efficient finetuning strategy depends on reducing the persistent footprint of the base model with 4-bit NF4 quantization and Double Quantization, and on using LoRA adapters as the only trainable 16-bit parameters. These choices lower the steady-state memory demand enough to fit 33B and 65B models onto single GPUs. However, the training computation graph still produces transient memory spikes during the backward pass, especially when gradient checkpointing recomputes activations for long sequences. These spikes are large enough to exceed the GPU’s physical memory, leading to repeated out-of-memory errors if nothing else changes.

Paged Optimizers address precisely this failure mode by allocating optimizer states in a unified memory space that can be paged between CPU and GPU. When a spike occurs, optimizer pages are evicted from the GPU, freeing enough memory to complete the backward pass. They are then paged back for the optimizer update. Without this mechanism, long-sequence training would most likely—and repeatedly—fail with out-of-memory errors on the targeted single-GPU configurations.
