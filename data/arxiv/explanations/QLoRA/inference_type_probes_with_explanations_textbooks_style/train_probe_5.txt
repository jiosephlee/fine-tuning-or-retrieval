Chapter: Dequantization to BF16 in QLoRA: From 4-bit Storage to High-Precision Computation

# Introduction
Finetuning large language models requires careful balancing of memory efficiency and numerical fidelity. QLoRA is designed precisely to strike this balance: it stores pretrained model weights in a compact 4-bit form, but performs all computations in a higher-precision format to preserve predictive performance during finetuning. The key operational fact is that QLoRA dequantizes the stored low-precision weights to a 16-bit computation data type, specifically BFloat16 (BF16), before executing matrix multiplications. This chapter explains why QLoRA separates storage and computation data types, how dequantization is performed, and how this design preserves the accuracy of 16-bit finetuning while enabling finetuning at drastically lower memory footprints. We will develop the full computation pipeline—storage, dequantization, forward and backward passes—strictly from the mechanisms presented in the QLoRA paper.

# Representations and Quantization in QLoRA
Quantization maps a high-information representation into a lower-information one by compressing the numeric range into fewer discrete levels. In a standard block-wise \(k\)-bit quantization scheme, a tensor \(\mathbf{X}^{\mathrm{FP32}}\) is scaled by an absolute-maximum-based constant and rounded into a low-bit integer space. For example, quantizing to Int8 with range \([-127,127]\) is given by
\[
\mathbf{X}^{\mathrm{Int8}} = \mathrm{round}\!\left(\frac{127}{\mathrm{absmax}(\mathbf{X}^{\mathrm{FP32}})}\,\mathbf{X}^{\mathrm{FP32}}\right) = \mathrm{round}(c^{\mathrm{FP32}}\cdot \mathbf{X}^{\mathrm{FP32}}),
\]
where \(c\) is the quantization constant. Dequantization inverts this mapping:
\[
\mathrm{dequant}(c^{\mathrm{FP32}}, \mathbf{X}^{\mathrm{Int8}}) = \frac{\mathbf{X}^{\mathrm{Int8}}}{c^{\mathrm{FP32}}} = \mathbf{X}^{\mathrm{FP32}}.
\]
To mitigate outliers within a tensor that would otherwise waste quantization levels, block-wise quantization chunks the tensor into contiguous blocks, assigns a separate quantization constant to each block, and quantizes blocks independently.

QLoRA adopts a two-type design: a low-precision storage data type and a higher-precision computation data type. The storage data type is usually 4-bit, while the computation data type is usually BFloat16. In practice, whenever a QLoRA weight tensor is used in computation, QLoRA first dequantizes the 4-bit stored weights into BF16 and then performs the matrix multiplication in 16-bit precision. This separation allows QLoRA to retain the memory advantages of 4-bit storage without sacrificing the numerical robustness of high-precision compute.

# Why Dequantize to BF16 Before Matrix Multiplication
Performing matrix multiplications directly in 4-bit precision would severely constrain the dynamic range and granularity of the values involved in each multiply–accumulate. Since finetuning must propagate informative gradients through deep stacks of linear projections, the fidelity of these operations is crucial. QLoRA therefore does not compute with 4-bit values directly. Instead, it first reconstructs a higher-precision representation of the weights by dequantization and conducts all multiplications in BF16.

Intuitively, the quantization step compresses the continuous weight distribution into \(2^k\) bins. If one were to multiply using these bins directly, both the forward signal and the backward signal would be restricted to very limited resolution. By dequantizing the 4-bit weights back into a 16-bit data type, QLoRA restores a much finer-grained representation of the weights at computation time. The result is that the forward mapping \(\mathbf{X}\mathbf{W}\) is evaluated in a format that captures small but meaningful differences in \(\mathbf{W}\), and the backward pass can compute derivatives with respect to the dequantized weights in 16-bit precision. This yields empirically verified parity with 16-bit finetuning while retaining the dramatic storage savings of quantized weights.

The paper repeatedly confirms this design choice. First, it states that QLoRA has a storage data type (usually 4-bit) and a computation data type (usually BF16). Second, it specifies that whenever a QLoRA weight tensor is used, it is dequantized to BF16 and then multiplied in 16-bit. Finally, the empirical results show that 4-bit QLoRA with this dequantize-then-compute pattern matches the performance of 16-bit finetuning and 16-bit LoRA finetuning across tasks and scales.

# Double Quantization and the Dequantization Pipeline
QLoRA introduces “Double Quantization” to further shrink memory overheads. Instead of storing one set of 32-bit quantization constants for all blocks, QLoRA quantizes those quantization constants themselves. Concretely, the first quantization uses a small blocksize (e.g., 64) to quantize the weight tensor \(\mathbf{W}\) into \(\mathbf{W}^{\text{k-bit}}\) with per-block constants \(c_2^{\mathrm{FP32}}\). The second quantization then treats the \(c_2^{\mathrm{FP32}}\) values as inputs and quantizes them into \(c_2^{\text{k-bit}}\) (with \(k=8\) in the paper) along with a second-level constant \(c_1^{\mathrm{FP32}}\).

At runtime, QLoRA reconstructs the computation-time weights by “double dequantization.” For a single layer with one LoRA adapter, the forward pass is
\[
\mathbf{Y}^{\mathrm{BF16}} = \mathbf{X}^{\mathrm{BF16}}\,\mathrm{doubleDequant}\!\left(c_1^{\mathrm{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}}\right) \;+\; \mathbf{X}^{\mathrm{BF16}}\mathbf{L}^{\mathrm{BF16}}_1\mathbf{L}^{\mathrm{BF16}}_2,
\]
where the double dequantization operator is
\[
\mathrm{doubleDequant}\!\left(c_1^{\mathrm{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}}\right)
= \mathrm{dequant}\!\Big(\mathrm{dequant}\!\left(c_1^{\mathrm{FP32}}, c_2^{\text{k-bit}}\right), \mathbf{W}^{\text{4bit}}\Big)
= \mathbf{W}^{\mathrm{BF16}}.
\]
Thus, the chain of reconstruction converts the stored values \(\mathbf{W}^{\text{k-bit}}\) and \(c_2^{\text{k-bit}}\) together with \(c_1^{\mathrm{FP32}}\) into the computation-time BF16 tensor \(\mathbf{W}^{\mathrm{BF16}}\). The matrix multiplication uses \(\mathbf{W}^{\mathrm{BF16}}\), not \(\mathbf{W}^{\text{k-bit}}\), which directly implements the principle that QLoRA dequantizes to BF16 prior to multiplication to improve numerical precision.

Double Quantization dramatically reduces the memory overhead of storing quantization constants (e.g., from \(32/64 = 0.5\) bits per parameter to \(8/64 + 32/(64\cdot 256) = 0.127\) bits per parameter in one configuration), yet introduces no measurable performance degradation in the paper’s experiments. Crucially, regardless of how constants are stored, the compute path remains the same: the constants are dequantized first, then the weights are dequantized to BF16, and only then is the matrix multiplication performed.

# NF4: Information-Theoretically Optimal 4-bit Storage for Weights
The effectiveness of dequantization depends not just on switching to BF16 for computation, but also on how well the 4-bit storage captures the underlying weight distribution. QLoRA introduces the NormalFloat (NF) data type, specifically NF4 for 4-bit storage, designed to be information-theoretically optimal for zero-mean, approximately normally distributed weights. The construction of NF4 proceeds by:

1. Estimating the \(2^k+1\) quantiles of a standard normal distribution \(N(0,1)\) to define a \(k\)-bit quantile-quantization data type.
2. Normalizing the data type values into \([-1,1]\).
3. Rescaling the input weight tensor into \([-1,1]\) by absolute-maximum rescaling.

Formally, for \(k\)-bit quantization, the data type values \(q_i\) are defined by
\[
q_i = \frac{1}{2}\Big(Q_X\!\left(\tfrac{i}{2^k + 1}\right) + Q_X\!\left(\tfrac{i+1}{2^k + 1}\right)\Big),
\]
where \(Q_X(\cdot)\) is the quantile function for \(N(0,1)\). To ensure a discrete zero point and use all \(2^k\) levels, QLoRA constructs an asymmetric data type by allocating \(2^{k-1}\) bins for negative values and \(2^{k-1}+1\) bins for positive values, then merging and removing the duplicate zero. This yields NF\(k\), the \(k\)-bit NormalFloat data type.

Empirically, the paper finds that NF4 improves quantization precision and downstream performance relative to generic 4-bit floating point and integer data types. When combined with dequantization to BF16 for computation, NF4 supplies high-quality reconstructed weights \(\mathbf{W}^{\mathrm{BF16}}\) at runtime, which is central to matching 16-bit finetuning performance.

# Backpropagation Through Dequantized Weights in BF16
QLoRA finetuning uses Low-Rank Adapters (LoRA), which augment a base linear projection \(\mathbf{X}\mathbf{W} = \mathbf{Y}\) with a low-rank term:
\[
\mathbf{Y} = \mathbf{X}\mathbf{W} + s\,\mathbf{X}\mathbf{L}_1\mathbf{L}_2,
\]
where \(\mathbf{L}_1\in\mathbb{R}^{h\times r}\) and \(\mathbf{L}_2\in\mathbb{R}^{r\times o}\) are the trainable adapter parameters and \(s\) is a scalar. In QLoRA, the base weights \(\mathbf{W}\) are stored in 4-bit form and remain frozen, while the adapters are trained.

Even though only the LoRA parameters are updated, gradients must backpropagate through the base model to reach the adapters. This entails computing derivatives that depend on \(\partial \mathbf{X} / \partial \mathbf{W}\), which requires access to \(\mathbf{W}\) in a computation-appropriate format. QLoRA handles this by dequantizing \(\mathbf{W}^{\text{NF4}}\) to \(\mathbf{W}^{\mathrm{BF16}}\) and then computing the necessary derivatives in BF16. As the paper states, “the calculation of \(\frac{\partial \mathbf{X}}{\partial \mathbf{W}}\) proceeds via dequantization from storage \(\mathbf{W}^{\text{NF4}}\) to computation data type \(\mathbf{W}^{\mathrm{BF16}}\) to calculate the derivative \(\frac{\partial \mathbf{X}}{\partial \mathbf{W}}\) in BFloat16 precision.” In this way, both the forward and backward passes benefit from BF16’s increased numerical fidelity, while the model still reaps the memory savings of 4-bit storage.

The update rule itself only applies to the adapter parameters; gradients \(\partial E / \partial \mathbf{W}\) are not needed since the base weights are frozen. Nonetheless, the forward and backward computations rely on the dequantized \(\mathbf{W}^{\mathrm{BF16}}\), completing the picture that QLoRA consistently dequantizes to BF16 before any numerically sensitive operations.

# End-to-End Computation in QLoRA: From Storage to High-Precision Compute
We can now summarize the full QLoRA pipeline for a single linear layer with LoRA:

1. The pretrained base weights are stored in 4-bit NF4 with block-wise quantization, and their block-wise quantization constants are themselves stored compactly via Double Quantization.
2. At runtime, the quantization constants are dequantized, and then the 4-bit NF4 weight blocks are dequantized using these constants to reconstruct \(\mathbf{W}^{\mathrm{BF16}}\).
3. The forward pass performs a BF16-precision matrix multiplication \(\mathbf{X}^{\mathrm{BF16}} \mathbf{W}^{\mathrm{BF16}}\) and adds the LoRA term \(\mathbf{X}^{\mathrm{BF16}}\mathbf{L}^{\mathrm{BF16}}_1\mathbf{L}^{\mathrm{BF16}}_2\).
4. The backward pass computes all needed derivatives in BF16, propagating through the dequantized base weights to update only the adapter parameters.

This design is supported by empirical findings throughout the paper: with NF4 storage, Double Quantization, and BF16 compute, 4-bit QLoRA finetuning matches 16-bit full finetuning and 16-bit LoRA performance on a wide range of models and tasks. The central mechanism enabling this result is the consistent dequantization of stored weights into BF16 before matrix multiplication and gradient computation, which improves numerical precision while preserving the memory benefits of quantization.
