Chapter Title: Double Dequantization in QLoRA: Reconstructing Quantization Constants to Recover High-Precision Weights

# Quantization and Dequantization: Foundations

Quantization converts high-precision tensors into lower-precision representations by mapping real-valued elements to a discrete set of values. This is typically achieved by rescaling a tensor into the representable range of a low-bit data type and rounding. For example, converting an FP32 tensor to Int8 with range $[-127,127]$ proceeds by normalizing by the absolute maximum and rounding:
\[
\mathbf{X}^{\text{Int8}} = \text{round}\!\left(\frac{127}{\text{absmax}(\mathbf{X}^{\text{FP32}})}\mathbf{X}^{\text{FP32}}\right) = \text{round}(c^{\text{FP32}} \cdot \mathbf{X}^{\text{FP32}}),
\]
where $c$ is the quantization constant (also called the quantization scale). Dequantization is the inverse operation that reconstructs the original floating-point values:
\[
\text{dequant}(c^{\text{FP32}}, \mathbf{X}^{\text{Int8}}) = \frac{\mathbf{X}^{\text{Int8}}}{c^{\text{FP32}}} = \mathbf{X}^{\text{FP32}}.
\]

A major challenge arises when tensors contain outliers: large-magnitude elements can force a scale that wastes representational capacity over much of the range. Block-wise quantization addresses this by partitioning a tensor into contiguous blocks and quantizing each block independently with its own scale. Concretely, a tensor $\mathbf{X}\in\mathbb{R}^{b\times h}$ is flattened and split into $n=(b\cdot h)/B$ blocks of size $B$, each with its own quantization constant $c_i$. This ensures more effective utilization of quantization bins within each block and reduces the distortion due to outliers.

# Why Double Quantization?

Block-wise quantization improves precision, but it introduces an overhead: every block must store its quantization constant. With small blocksizes (which improve quantization precision), this overhead becomes non-negligible. For instance, using a blocksize of $64$ and storing a 32-bit floating-point quantization constant per block yields an average overhead of $32/64=0.5$ bits per parameter.

Double Quantization is introduced to reduce this overhead by compressing the quantization constants themselves. The idea is to apply a second quantization to the set of first-level scales. This reduces the memory footprint of the scales while preserving the ability to reconstruct the information needed to dequantize the low-bit weights.

Concretely, let $c_2^{\text{FP32}}$ be the per-block quantization constants used to quantize the weight tensor $\mathbf{W}$. Instead of storing $c_2^{\text{FP32}}$ directly, we quantize them a second time into a low-bit representation $c_2^{\text{k-bit}}$ together with a second-level set of scales $c_1^{\text{FP32}}$. In QLoRA, $c_2$ are quantized to FP8 with a blocksize of $256$, while $c_1$ remains FP32. Because $c_2^{\text{FP32}}$ are positive, we subtract their mean before quantization to center them around zero and leverage symmetric quantization. For a blocksize of $64$ for $\mathbf{W}$ and of $256$ for the $c_2$ scales, the memory overhead is reduced from $32/64=0.5$ bits per parameter to
\[
\frac{8}{64} + \frac{32}{64\cdot 256} = 0.127 \text{ bits per parameter,}
\]
a reduction of $0.373$ bits per parameter. For a 65B-parameter model, this corresponds to roughly 3 GB saved on quantization constants on average.

# NormalFloat for 4-bit Weights and the Compute Type

QLoRA targets high-fidelity finetuning with extremely low storage precision. It uses one storage data type and one compute data type. The storage data type for weights is typically a 4-bit NormalFloat (NF4), and the computation data type is BFloat16 (BF16). NF4 is constructed to be information-theoretically optimal for zero-centered normally distributed data by assigning equal expected mass to each quantization bin. In practice, this is achieved by precomputing quantiles of a standard normal distribution, normalizing into a fixed range (e.g., $[-1,1]$), and then scaling incoming weight tensors to match this range prior to quantization.

At run time, whenever a quantized weight tensor is used, it is dequantized to BF16, and all matrix multiplications are performed in 16-bit. This separation between storage precision and compute precision enables substantial memory savings without sacrificing numerical stability during forward and backward passes.

# Double Quantization: Mechanism and Data Flow

Double Quantization proceeds in two levels:

1. First-level quantization: The original full-precision weights $\mathbf{W}^{\text{FP32}}$ are quantized block-wise into a $k$-bit format, yielding $\mathbf{W}^{\text{k-bit}}$ and per-block scales $c_2^{\text{FP32}}$. In QLoRA, $\mathbf{W}^{\text{k-bit}}$ uses NF4 (so $k=4$), and the blocksize for $\mathbf{W}$ is $64$.

2. Second-level quantization of scales: The first-level scales $c_2^{\text{FP32}}$ are themselves quantized into a low-bit format $c_2^{\text{k-bit}}$ (FP8 in QLoRA) with their own per-block scales $c_1^{\text{FP32}}$. The blocksize for second-level quantization is $256$.

This two-layer structure enables the essential insight that the first-level scales do not need to be stored in full precision for every block. Instead, they can be reconstructed on the fly from a compact low-bit representation and a lightweight set of second-level scales. This underlies the design of the doubleDequant function used during forward and backward computation.

# The doubleDequant Function: Reconstructing Scales, Then Weights

The doubleDequant function performs dequantization in two steps:
\[
\text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}}) \;=\; \text{dequant}\!\big(\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}), \; \mathbf{W}^{\text{4bit}}\big) \;=\; \mathbf{W}^{\text{BF16}}.
\]

This equation makes explicit the role of the initial dequantization step. The inner dequantization,
\[
\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}),
\]
reconstructs the first-level quantization constants $c_2^{\text{FP32}}$ from their low-bit representation $c_2^{\text{k-bit}}$ using the second-level scales $c_1^{\text{FP32}}$. In other words, the first dequantization step recovers the supporting data—namely, the per-block quantization constants—that are required to dequantize the low-bit weights.

With $c_2^{\text{FP32}}$ reconstructed, the outer dequantization,
\[
\text{dequant}\!\big(c_2^{\text{FP32}}, \mathbf{W}^{\text{4bit}}\big),
\]
converts the NF4 weight tensor $\mathbf{W}^{\text{k-bit}}$ back into the BF16 compute type, yielding $\mathbf{W}^{\text{BF16}}$ for use in matrix multiplications. Thus, doubleDequant first performs an initial dequantization to restore the first-level scales, and then uses those scales to dequantize the weights themselves.

This staged reconstruction is what allows QLoRA to dramatically reduce the memory footprint of quantization constants without losing the ability to faithfully recover high-precision weights for computation.

# Integration into QLoRA’s Forward and Backward Passes

In QLoRA, the quantized base model is frozen, and Low-rank Adapters (LoRA) are added and trained. For a single linear layer with one LoRA adapter, the forward pass is:
\[
\mathbf{Y}^{\text{BF16}} \;=\; \mathbf{X}^{\text{BF16}} \cdot \text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{NF4}}) \;+\; \mathbf{X}^{\text{BF16}}\mathbf{L}_1^{\text{BF16}}\mathbf{L}_2^{\text{BF16}}.
\]
Here, $\mathbf{W}^{\text{NF4}}$ is the 4-bit NormalFloat storage of the base weights, $c_2^{\text{k-bit}}$ are the low-bit quantized first-level scales (FP8), and $c_1^{\text{FP32}}$ are the second-level FP32 scales used to dequantize $c_2$. The output weight tensor used for computation is $\mathbf{W}^{\text{BF16}}$, obtained via doubleDequant.

During training, gradients are computed only with respect to the adapter parameters $\mathbf{L}_1$ and $\mathbf{L}_2$. The base weights are frozen, so no gradients are computed with respect to $\mathbf{W}$. However, the computation of $\frac{\partial E}{\partial \mathbf{L}_i}$ depends on the forward path through the dequantized $\mathbf{W}^{\text{BF16}}$, which is obtained via the two-step dequantization. Therefore, dequantization is essential in both forward and backward passes to ensure correct propagation through the computation graph, even though the quantized base weights are not updated.

# Data Types, Blocksizes, and Precision Choices

QLoRA uses:
- NF4 as the storage type for weights $\mathbf{W}$, with blocksize $64$. This small blocksize improves the fidelity of 4-bit quantization for weights.
- FP8 as the storage type for the first-level scales $c_2$, with blocksize $256$. This coarse blocksize is sufficient for scales, and the second-level FP32 scales $c_1$ compensate during reconstruction.
- BF16 as the compute type for matrix multiplications and gradient computations.

This configuration balances memory savings with precision. In particular, it has been observed that using FP8 for quantizing the first-level scales does not degrade performance, while yielding substantial memory reductions through Double Quantization. The explicit reconstruction of $c_2^{\text{FP32}}$ before dequantizing the weights is what allows these choices to work in practice.

# Intuition: Why Reconstruct Scales First?

The quantization constant is the key to interpreting the integer or low-bit code associated with each block. Without the scale, the code has no meaningful numerical value. In standard one-level quantization, the scale $c$ is stored in FP32 per block, and dequantization simply divides by $c$. In Double Quantization, we compress the set of scales to save memory and then reconstruct them at use time.

Seen this way, doubleDequant naturally proceeds in two steps:
1. Rebuild the missing key (the first-level scale) via dequantization with the second-level scales.
2. Use the rebuilt key to unlock the numeric meaning of the weight codes and recover BF16 weights.

This decomposition shows how the initial dequantization step supplies the supporting data—the quantization constants—needed for the subsequent dequantization of the low-bit weight tensor $\mathbf{W}^{\text{k-bit}}$ into $\mathbf{W}^{\text{BF16}}$.

# Memory Savings and Practical Impact

The primary motivation for Double Quantization is the measurable reduction in the memory footprint of quantization metadata. With a blocksize of $64$ for $\mathbf{W}$ and $256$ for $c_2$, the overhead drops from $0.5$ to $0.127$ bits per parameter, a savings of $0.373$ bits per parameter. For very large models, such as those with 65B parameters, this corresponds to saving on the order of gigabytes of memory for the scales alone. Crucially, empirical results show that this compression introduces no degradation in downstream finetuning performance when combined with NF4 for weights and BF16 for computation.

# Summary

Double Quantization in QLoRA compresses the per-block quantization constants by quantizing them a second time. The doubleDequant function operationalizes this design by first dequantizing the second-level representation to reconstruct the first-level scales and then using those reconstructed scales to dequantize the 4-bit NormalFloat weights into BF16. This initial dequantization step restores the supporting data—the quantization constants—without which the weight tensor cannot be recovered. The result is a highly memory-efficient storage scheme that still enables accurate reconstruction of compute-precision weights for both forward and backward passes during finetuning, thereby maintaining performance parity with 16-bit methods while dramatically reducing memory requirements.
