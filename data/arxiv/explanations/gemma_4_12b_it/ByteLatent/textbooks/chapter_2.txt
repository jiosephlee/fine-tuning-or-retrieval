\title{A Textbook about the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

Chapter 2: From Bytes to Patches: Dynamic Data Segmentation

# Defining Patching: The mapping of bytes to latent representations

In the standard paradigm of Large Language Models (LLMs), text is typically processed as tokens—discrete units from a fixed vocabulary. The Byte Latent Transformer (BLT) introduces a fundamental shift by moving away from these fixed vocabularies toward a system of dynamic "patches." A patch is essentially a group of bytes that serves as the primary unit of computation within the model. Rather than selecting a token from a pre-defined list, the model processes a sequence of bytes and groups them into patches based on the complexity and context of the data.

Formally, this process is described by a patching function, denoted as $f_p$. This function takes a sequence of bytes $\pmb{x}=\{x_i,|i=1,\ldots n\}$ of length $n$ and segments them into a sequence of $m$ patches $\pmb{p}=\{p_j|j=1,\ldots,m\}$, where $m < n$. The function $f_p$ maps each individual byte $x_i$ to a binary value $\{0,1\}$, where a value of 1 signifies the start of a new patch. Because BLT does not rely on a fixed vocabulary, these patches are not restricted to specific strings; instead, any arbitrary group of bytes can be mapped to a latent patch representation.

The primary motivation for this shift lies in the allocation of computational resources. In a Transformer architecture, the computational cost is largely determined by the number of steps executed by the main model. In the context of BLT, each step corresponds to a patch. By grouping bytes into patches, the model can decide how to distribute its "attention" and processing power. If a sequence of bytes is predictable and simple, it can be grouped into a larger patch, requiring fewer transformer steps. Conversely, if the bytes are complex and high-entropy, they can be grouped into smaller patches, allowing the model to dedicate more parameters and more computation to those specific sections.

# Static Patching: Strided Patching (K-bytes) and its limitations

The most basic way to implement the grouping of bytes into patches is through strided patching. In this scheme, bytes are grouped into patches of a fixed size, $k$. This is a straightforward method because it is easy to implement during both training and inference. Because the stride is constant, it provides a simple mechanism for researchers to control the average patch size and, by extension, the total floating-point operations (FLOPs) required to process the data.

However, strided patching suffers from significant architectural limitations, primarily because it fails to allocate compute dynamically. In a strided system, the model spends the same amount of computational effort on every $k$ bytes, regardless of the information density of those bytes. This leads to inefficiencies: for instance, the model might waste a transformer step on a sequence of whitespace or simple punctuation, while simultaneously failing to allocate sufficient compute to complex segments like mathematical equations or dense technical descriptions.

Furthermore, strided patching leads to inconsistent and non-contextual segmenting. Because the boundaries are fixed by a rigid count of $k$, the same word or phrase might be split differently depending on where it appears in a sequence. This lack of linguistic awareness can hinder the model's ability to form coherent representations of common units of meaning, as the boundaries of the patches do not align with the actual structure of the language.

# Heuristic Patching: Space Patching and linguistic boundaries

To address the limitations of strided patching, researchers have explored heuristic methods that use linguistic markers to define boundaries. One such method is space patching. In this approach, new patches are created after any "space-like" bytes. Space-like bytes are defined as any byte that is not a Latin character, a digit, or a UTF-8 continuation byte. Additionally, the patching rules ensure that each patch contains at least one non-space-like byte.

The intuition behind space patching is that spaces serve as natural boundaries for linguistic units in many languages. By creating a new patch at every space, the model effectively allocates a latent transformer step—and thus more compute—to model every word. This is particularly useful because the first bytes of a word are typically the most difficult to predict. For example, predicting the first letter of a response to a question is computationally harder than predicting the subsequent letters of that same word. Once the first letter is established, the completion of the word becomes a comparatively easy, low-entropy decision.

While space patching is an improvement over strided patching because it ensures words are patched consistently across different sequences, it still has drawbacks. It cannot gracefully handle every language or technical domain where spaces might not be the primary delimiter. Most importantly, space patching remains a rigid heuristic; it does not provide a mechanism to vary the patch size based on the actual complexity of the information, which is a key goal of the BLT architecture.

# Entropy Patching: Using a small Byte LM to identify high-uncertainty boundaries

The Byte Latent Transformer introduces a more sophisticated, data-driven method called entropy patching. Instead of relying on hard-coded rules like whitespace, entropy patching uses a small, byte-level auto-regressive language model to identify points of high uncertainty in the data. The goal is to identify boundaries where the next byte is difficult to predict, as these are the points where the model requires more computational capacity.

To do this, a small byte-level language model is trained on the training data. This model provides an entropy estimate $H(x_i)$ for each byte $x_i$ under the distribution $p_{e}$ over the byte vocabulary $\mathcal{V}$. The entropy is calculated as:
$H(x_i) = \sum_{v \in \mathcal{V}} p_{e}(x_i=v|\pmb{x}_{<i}) \log p_{e}(x_i=v|\pmb{x}_{<i})$

The architecture uses these entropy values to identify patch boundaries through two different methods. The first method uses a global entropy threshold, where a new patch begins whenever $H(x_t) > \theta_g$. The second method looks for relative changes in uncertainty, identifying points where the entropy is significantly higher than the previous byte: $H(x_t) - H(x_{t-1}) > \theta_r$. This second approach is useful for identifying points that break a trend of monotonically decreasing entropy within a patch. This process is performed during a lightweight preprocessing step as data is loaded, allowing the model to dynamically adjust its grouping based on the actual information density of the input.

# The Property of Incremental Patching vs. BPE

A critical distinction between the patching method used in BLT and the Byte-Pair Encoding (BPE) used in models like Llama 3 is the property of incremental patching. For a patching scheme $f_p$ to be considered incremental, it must satisfy the following mathematical property:
$f_p(\pmb{x}_{<i}) = f_p(\pmb{x})_{<i}$
This means that the decision of where to place a patch boundary at position $i$ must depend only on the bytes that have appeared before $i$, and not on any future bytes in the sequence.

BPE tokenization is not an incremental patching scheme. In BPE, the same prefix of a string can be tokenized in multiple different ways depending on what characters follow it. This is because BPE looks for the longest possible matches from a fixed vocabulary, and the "best" match can change depending on the remainder of the string. Because BPE is not incremental, the model cannot decide whether it is at a patch boundary without knowing the entire sequence. 

In contrast, because BLT uses an incremental patching scheme (like entropy patching), the model can decide whether to invoke the expensive Latent Transformer at any given step based solely on the history of the sequence. This allows for a more fluid and dynamic allocation of compute during the generation process, as the model can determine the necessity of a transformer step independently of the yet-to-be-generated future.

# The Patch Size vs. Computation relationship: How patch size controls FLOPs

The fundamental advantage of the patch-based architecture over token-based architectures lies in the relationship between patch size and computational cost (FLOPs). In standard LLMs using BPE, there is a strict trade-off between vocabulary size and compute. If you want to use larger tokens (which reduces the number of steps), you must increase the size of the output projection layer and the embedding table. This limits how much you can increase the average token size without significantly increasing the model's parameter count.

BLT breaks this trade-off. Because patches are not pulled from a fixed vocabulary, BLT can increase the average patch size without increasing the output dimension of the model. This leads to a direct relationship where inference FLOPs are inversely proportional to the average patch size. Longer patches save compute because the expensive global latent transformer is run less frequently.

This creates a new dimension for scaling models. Because longer patches save compute, those "saved" FLOPs can be reallocated to grow the size of the global latent transformer itself. Effectively, for a fixed inference budget, BLT can simultaneously grow both the size of the patches and the size of the model. This allows the model to become more powerful (larger parameters) while remaining efficient (fewer steps due to larger patches), a scaling path that is not available to traditional token-based architectures.
