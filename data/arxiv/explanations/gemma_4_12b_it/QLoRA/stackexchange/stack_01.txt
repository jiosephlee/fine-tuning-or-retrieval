\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### What exactly is a 'quantization constant' and how does Double Quantization save memory?
Question:
I'm reading the QLoRA paper and I'm trying to understand the memory savings from Double Quantization. The authors mention that for a blocksize of 64, the quantization constants add $0.5$ bits per parameter. Can someone explain what a 'quantization constant' is in the context of block-wise quantization and why quantizing these constants specifically leads to a memory reduction of $0.37$ bits per parameter?
Answer:
To understand the memory savings in QLoRA, it is helpful to first visualize how block-wise quantization works. When we compress a high-precision weight tensor (like FP32) into a low-bit format (like 4-bit), we need a way to map the wide range of the original values into the much smaller range of the target format. This is achieved using a **quantization constant** (or scale factor), which acts as a "ruler" to stretch or shrink the data so that it fits into the available bits. 

If we used a single quantization constant for an entire weight matrix, a single outlier (a value with an unusually large magnitude) would force the "ruler" to be so large that all the smaller, more common weights would be collapsed into the same value, destroying the model's accuracy. To prevent this, the authors use block-wise quantization, where the weight tensor is divided into small contiguous chunks (e.g., blocks of 64 weights). Each block is assigned its own unique quantization constant. While this preserves precision, it introduces a new memory overhead: for every block of 64 weights, we must store an additional 32-bit (4-byte) constant. Mathematically, this adds $32/64 = 0.5$ bits of overhead per parameter. For a massive model like a 65B parameter LLM, these constants occupy significant space (roughly 3 GB).

**Double Quantization** works by applying the same logic to the quantization constants themselves. The authors treat the first set of 32-bit constants ($c_2^{\text{FP32}}$) as input data and quantize them a second time. This process produces a second-level constant ($c_1^{\text{FP32}}$) and a quantized version of the first constants ($c_2^{\text{FP8}}$). By doing this, we no longer need to store the original 32-bit constants. Instead, we store the 8-bit quantized constants and the new 32-bit second-level constants.

The reason for the specific reduction of $0.37$ bits per parameter lies in the different block sizes used for each level. The paper uses a block size of 64 for the weights to maintain high precision, but a larger block size of 256 for the quantization constants. Because the constants are generally more stable and less prone to extreme outliers than the weights themselves, a larger block size is sufficient to maintain performance. 

The memory footprint per parameter after Double Quantization is calculated as follows: 
1. The first level of constants is now 8-bit, stored for every 64 weights: $8/64 = 0.125$ bits. 
2. The second level of constants is 32-bit, but since it is calculated over a larger block of $64 \cdot 256$ parameters, its cost is $32/(64 \cdot 256) \approx 0.00195$ bits. 

Adding these together gives a total of approximately $0.127$ bits per parameter. Comparing this to the original $0.5$ bits per parameter, the technique saves roughly $0.37$ bits per parameter. In the context of large-scale models, this "quantization of the quantization constants" is a clever way to shave off several gigabytes of VRAM without significantly impacting the numerical fidelity of the model.
