\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### If the LLM is smart enough to understand the data, why do we need a downstream model for prediction?
Question:
I'm a bit confused about the core architecture of FeatLLM. The paper says that LLMs have 'remarkable ability to tackle challenging and unseen reasoning problems.' If the LLM is capable of understanding the relationships between features and the target, why does the framework bother with a 'simple downstream machine learning model' like linear regression? Couldn't we just ask the LLM to provide the final class prediction for each sample directly?
Answer:
The distinction between the LLM's "reasoning" and the downstream model's "prediction" in the \textsf{FeatLLM} framework is a matter of balancing computational efficiency, scalability, and statistical weight optimization. While you are correct that an LLM is capable of providing a final class prediction, the authors argue that doing so for every individual sample is impractical for many real-world applications.

The primary reason for using a simple downstream model like linear regression is to reduce inference latency and cost. As the paper notes in the Introduction, existing methods that perform end-to-end predictions require at least one LLM inference per sample. For large-scale tabular data, this is computationally expensive and slow. By shifting the LLM's role from "predictor" to "feature engineer," the framework only requires the LLM to be queried during the rule-generation phase. Once the rules are extracted and converted into binary features ($\mathbf{z}_k^i$), the final prediction can be made by a simple mathematical operation, which is nearly instantaneous and costs nothing in terms of API credits.

Beyond efficiency, there is a conceptual separation of tasks happening here. The LLM is used for its "prior knowledge" and "reasoning capabilities"—essentially acting as a domain expert that understands how certain features (like age or blood pressure) logically relate to a disease. It generates the "logic" of the problem (the rules). However, the downstream model is responsible for "weighting" that logic. Even if an LLM generates high-quality rules, some rules might be more predictive than others within a specific small dataset. The linear model takes the binary features $\mathbf{z}_k^i$ and learns a weight vector $\mathbf{w}_k$ to estimate the class likelihood:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

This allows the framework to learn the relative importance of each rule discovered by the LLM. By using a linear model with a softmax layer, the framework can provide a well-calibrated probability $\mathbf{p}^i$ for each class, which is often more useful in production than a single "Yes/No" text response from an LLM.

Finally, this architecture helps overcome physical constraints of the model itself, such as prompt size limits. If a tabular dataset has a massive number of features, it may be impossible to fit all that information into a single prompt for the LLM to "reason" over at once. \textsf{FeatLLM} addresses this by using bagging to select subsets of features for the LLM to engineer rules for. By combining these "weak" rules into an ensemble of linear models, the framework can handle complex, high-dimensional data that would otherwise exceed the context window of a standard LLM. In summary, the LLM provides the "intelligence" to understand the data's underlying structure, while the downstream model provides the "machinery" to apply that understanding efficiently and scalably.

### Why is the weight vector $\mathbf{w}_k$ projected into a positive subspace in Equation 1?
Question:
In Section 3.2, the logit for class $k$ is calculated as $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$. I understand that $\mathbf{z}_k^i$ is a binary feature (0 or 1) indicating if a rule is satisfied. However, I don't see why the weights $\mathbf{w}_k$ must be non-negative. If a rule is satisfied, shouldn't it be possible for that rule to *decrease* the likelihood of a certain class? Why does the authors' approach of ensuring the features 'do not reduce the likelihood' make sense for this specific framework?
Answer:
The reason the authors project the weight vector $\mathbf{w}_k$ into a positive subspace—effectively ensuring that $\mathbf{w}_k \geq 0$—stems from the specific way the \textsf{FeatLLM} framework is architected to interpret the LLM's output. While you are correct that in a general linear model, a feature can have a negative weight to indicate a decrease in likelihood, the logic of this paper relies on a "constructive" rule-based approach rather than a purely "discriminative" one.

To understand this, it is helpful to look at the role the LLM plays in this specific pipeline. The authors prompt the LLM to derive "decisive rules to distinguish classes" and specifically to "infer the conditions associated with each answer class." When the LLM generates a rule for class $k$, it is explicitly defining a condition that, if met, serves as evidence **for** the presence of class $k$. For example, if the LLM identifies "Age $> 60$" as a rule for "Chronic Heart Failure," the resulting binary feature $\mathbf{z}_k^i$ is designed to be an indicator of that disease.

By enforcing non-negative weights $\mathbf{w}_k$, the authors ensure a monotonic relationship between the number of satisfied rules and the class likelihood. This preserves the "additive evidence" interpretation: every rule the LLM identifies as a criterion for a class should contribute positively to that class's logit. If the model were allowed to assign a negative weight to a rule that the LLM specifically identified as a criterion for class $k$, it would create a logical contradiction between the "expert" reasoning provided by the LLM and the optimization of the downstream linear model.

Furthermore, this constraint acts as a form of inductive bias that is particularly useful in the few-shot regime. In scenarios with very few samples, a standard linear model might overfit by assigning a large negative weight to a rule simply because that rule was coincidentally satisfied by a few samples of a different class. By forcing $\mathbf{w}_k \geq 0$, the framework prevents the model from using the LLM's "positive" rules as "negative" evidence, thereby forcing the model to rely on the quality of the rules extracted via the LLM's prior knowledge. 

In summary, while negative weights are standard for capturing inhibitory relationships in general tabular learning, \textsf{FeatLLM} treats the LLM as a logic engine that generates "pro-class" criteria. The positive projection ensures that the downstream model respects the semantic meaning of those criteria as evidence for, rather than against, the target class.

### How does the two-step reasoning process specifically mitigate 'spurious correlations'?
Question:
The paper mentions a two-step reasoning process where Step 1 involves inferring causal relationships based only on 'general knowledge' without looking at the few-shot examples. Can someone explain the intuition behind why this specific separation helps prevent the LLM from picking up on coincidental correlations in the provided examples? If the LLM had access to both the general knowledge and the examples at the same time, why would it be more likely to fail?
Answer:
The two-step reasoning process in the \textsf{FeatLLM} framework mitigates spurious correlations by creating a structural "knowledge anchor." By isolating the retrieval of general domain knowledge from the analysis of specific data points, the framework prevents the model from falling into the common trap of over-fitting to coincidental patterns found in small datasets.

To understand why this works, we can look at the intuition behind the separation of the two steps:

In many few-shot learning scenarios, the primary challenge is that the provided examples are so limited that they may contain "spurious correlations"—features that happen to align with the target label in the sample set but have no actual causal relationship with the outcome (e.g., a random ID number that happens to be high for all "positive" cases in a 4-shot sample). If an LLM is given both the task description and the examples simultaneously, its attention mechanism is highly likely to prioritize the most immediate and easily identifiable patterns in those examples. Because a spurious correlation is, by definition, a simple pattern, the model may "latch" onto it as a shortcut, ignoring its broader internal knowledge of what the task actually entails.

The \textsf{FeatLLM} framework prevents this by enforcing a specific sequence:

First, in **Step 1**, the model is instructed to infer causal relationships based solely on its "general knowledge" or "common sense" without looking at the few-shot examples. This forces the LLM to establish a high-level conceptual framework for the problem (e.g., "Heart disease is related to blood pressure and age"). Because the examples are hidden during this step, the model cannot be distracted by the noise or coincidences present in the small data subset. This step serves to "prime" the LLM with a set of relevant features that are scientifically or logically sound.

Second, in **Step 2**, the model is then allowed to see the examples, but it must use them in conjunction with the knowledge it just derived in Step 1 to deduce specific rules. Because the LLM has already been "anchored" to the correct causal features, it acts as a filter. When it looks at the few-shot examples, it is predisposed to look for rules involving the features identified in Step 1. This makes it significantly harder for the model to generate rules based on irrelevant columns, as those columns were not highlighted as significant during the first phase of reasoning.

The paper demonstrates the efficacy of this approach in its analysis of spurious correlations (Section 4.1). By attaching irrelevant columns from a different dataset to the "Heart" dataset, the researchers showed that \textsf{FeatLLM} suffered the least performance degradation. This is because the two-step process effectively "shields" the rule extraction from irrelevant information; the model is essentially told to ignore the "noise" because the "signal" was already established by its internal prior knowledge before the noise was even introduced into the prompt.

### How does bagging actually solve the 'excessive prompt size' problem for high-dimensional tables?
Question:
The authors state that FeatLLM can handle datasets with a large number of features (like 'Communities' or 'Myocardial' with over 100 attributes) by using bagging. However, the prompt still needs to contain the task description and feature definitions. If the feature descriptions themselves are too large to fit in the context window, how does bagging the samples or features actually reduce the prompt size enough to make it feasible? Does bagging only help if the number of *samples* is the bottleneck, or can it also reduce the number of *features* sent in the prompt?
Answer:
The bagging approach in FeatLLM specifically addresses the prompt size limitation by partitioning the feature space across multiple independent queries to the LLM. Your intuition regarding the fixed overhead of feature definitions is correct: if the total number of features $d$ is so large that all definitions $F = \{f_j\}_{j=1}^d$ cannot fit into the context window simultaneously, it is mathematically impossible for the LLM to "see" the entire table in a single inference call.

Bagging solves this by selecting a subset of features for each trial. Instead of attempting to fit all $d$ features into a single prompt, the framework selects a smaller, manageable subset of features in each iteration. In each trial, the LLM is prompted with a task description, a limited set of feature definitions, and a few-shot example set. The LLM then generates rules based only on the subset of features provided in that specific prompt. While any single trial might result in a "weak learner" because it lacks information on the excluded features, the ensemble mechanism compensates for this. By aggregating the results from multiple trials—where each trial focuses on different subsets of the total features—the final model captures the relationships across the entire feature space without ever exceeding the token limit in any single turn.

Therefore, bagging does not only help when the number of samples is the bottleneck; it is a fundamental strategy for handling high-dimensional feature sets. The paper explicitly states that bagging is used to select a subset of features *or* instances for each trial. This allows the framework to handle datasets like "Communities" or "Myocardial" by ensuring that the prompt remains within the allowable input size, while the ensemble of various "weak learners" (each seeing a different part of the data) nullifies the impact of incomplete feature or instance coverage in individual trials. In essence, bagging allows the model to "see" the whole table by looking at it through several different "keyholes" and combining the views.

### What is the theoretical risk of 'overfitting' when increasing the number of rules $R$ in a low-shot regime?
Question:
In the hyper-parameter analysis, the authors mention that a higher number of rules could lead to 'overfitting within the low-shot regime.' Since the rules are generated by an LLM (which is essentially a prior) and then mapped to a linear model, I'm struggling to see how overfitting occurs in the traditional sense (i.e., the model learning noise in the training set). Is the 'overfitting' here referring to the linear model's weights $\mathbf{w}_k$ becoming too specific to the $k$ shots provided, or is it referring to the LLM generating rules that are too specific to the few examples in the prompt?
Answer:
The "overfitting" described by the authors is not a choice between the LLM's behavior and the linear model's behavior; rather, it is a two-fold problem where both components contribute to a breakdown in generalization when the number of rules $R$ is high relative to the number of shots $k$.

From a classical machine learning perspective, the primary risk is the dimensionality of the linear model. The model learns a weight vector $\mathbf{w}_k \in \mathbb{R}^R$ to project the binary features $\mathbf{z}_k^i \in \{0, 1\}^R$ into a logit. In a low-shot regime where $k$ is very small (e.g., $k=4$ or $8$), the number of training samples is significantly lower than the number of parameters $R$. When $R > k$, the linear model becomes underdetermined. This means there are infinitely many weight configurations $\mathbf{w}_k$ that can achieve zero training loss by perfectly separating the $k$ samples. The model can essentially "memorize" the training set by assigning high weights to any arbitrary rules that happen to be true for those specific $k$ samples, even if those rules have no predictive power on unseen data.

Simultaneously, the LLM's role as a feature engineer introduces a prior-based form of overfitting. The LLM is prompted with $k$ examples and asked to generate $R$ rules. As $R$ increases, the LLM is forced to find more and more "decisive" distinctions to satisfy the prompt. Because the sample size $k$ is small, the LLM is more likely to identify "spurious correlations"—features or conditions that are true for those specific $k$ examples but are not representative of the underlying distribution. For example, if one of the four examples happens to be a patient with a specific name or a rare, non-causal attribute, a high $R$ value encourages the LLM to codify that specific instance into a rule.

In summary, the "overfitting" is a compounding effect: as you increase $R$, the LLM is more likely to generate rules that are overfitted to the $k$ examples (identifying noise as signal), and the linear model then has more "degrees of freedom" to assign high weights to those noisy rules because the training set is too small to penalize them. The authors' choice of $R=10$ represents a heuristic balance where they provide enough rules to capture meaningful patterns while keeping the dimensionality low enough that the linear model cannot easily "cheat" by memorizing the noise in a few-shot sample.

### How does the 'parsing' step handle cases where the LLM generates semantically correct but syntactically inconsistent rules?
Question:
The paper admits that LLMs can produce 'noisy syntactic changes,' such as substituting '$>$' with 'greater than.' The authors suggest using the LLM itself to generate Python code to parse these rules. If the LLM produces a rule that is complex or involves multiple logical operators (e.g., 'if age is over 50 AND income is less than 30k'), how does the framework ensure that the resulting Python code is executable and doesn't produce a runtime error during the `exec()` call? Is there a fallback mechanism if the generated code fails to run?
Answer:
The \textsf{FeatLLM} framework handles the challenge of syntactically inconsistent but semantically correct rules by shifting the responsibility of "parsing" from a rigid, rule-based program to the LLM's own linguistic and reasoning capabilities.

In traditional systems, a developer would have to write complex regular expressions or parsers to account for every possible way a rule could be phrased (e.g., identifying that "$>$", "is greater than," and "exceeds" all mean the same thing). \textsf{FeatLLM} avoids this by using the LLM as a translation layer. Because LLMs are trained on vast corpora of both natural language and programming code, they possess the semantic understanding to map varied natural language expressions into valid Python syntax. By providing the LLM with the function name, input/output descriptions, and the inferred rules in a structured prompt, the framework asks the LLM to generate the actual Python code. This allows the system to handle "noisy" changes because the LLM focuses on the underlying intent of the rule rather than its specific surface-level syntax.

Regarding your question about ensuring the code is executable and preventing runtime errors during the `exec()` call, the paper does not describe a specific programmatic fallback mechanism (such as a `try-except` block or a recursive correction loop) to fix broken code on the fly. Instead, the framework relies on two architectural safeguards to maintain robustness:

First, the framework employs an ensemble approach using bagging. By repeatedly generating features and rules across multiple trials with a high temperature, the system produces a variety of rule sets. The authors note that even if the LLM generates incorrect or non-executable rules in some trials, the correct rules generated in other trials can compensate. This is a form of self-consistency; the ensemble ensures that the final prediction is not overly dependent on any single potentially "broken" parsing attempt.

Second, the framework uses a simple downstream linear model to learn the importance of the generated features. The probability for each class is computed using the weights $\mathbf{w}_k$ and the binary features $\mathbf{z}_k^i$:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

During the training phase, the model optimizes these weights. If a rule is poorly parsed, results in a runtime error (and thus fails to produce a feature), or produces a semantically useless feature, its contribution to the logit will be minimized or neutralized by the learning process. Furthermore, the paper explicitly mentions that rules with little relevance to the data are "automatically filtered out" during this weight tuning process, as evidenced by the observed weights falling below a certain threshold.

In summary, rather than guaranteeing that every single line of generated code is perfect via a validation check, \textsf{FeatLLM} uses the LLM's semantic intelligence to bridge the gap between natural language and code, while relying on ensemble diversity and weight optimization to mitigate the impact of any individual failures.
