# From Predictor to Architect: Why LLMs are the Newest Feature Engineers

When we think about using Large Language Models (LLMs) for data science, the most common intuition is to feed a row of data into the model and ask it for a prediction. While this "end-to-end" approach works, it presents significant hurdles for real-world applications: it is computationally expensive to query an LLM for every single row, it often hits prompt size limits when datasets have many features, and many high-performing models are locked behind APIs that don't allow for fine-tuning.

A new framework called \textsf{FeatLLM} proposes a paradigm shift. Instead of using the LLM as a predictor, it treats the LLM as an **architect**. In this framework, the LLM is tasked with "feature engineering"—identifying the underlying logic and rules of a dataset. Once these rules are established, a simple, traditional machine learning model takes over to handle the actual predictions.

## Moving from Prediction to Rule Extraction

The core idea of \textsf{FeatLLM} is to leverage the vast prior knowledge stored within LLMs to perform high-level reasoning. Rather than asking "Is this patient sick?", we ask the LLM "What are the rules that define sickness in this specific dataset?"

The framework follows a structured two-step reasoning process to extract these rules:

1.  **Causal Reasoning:** The LLM first analyzes the task description and feature names to infer relationships based on general knowledge (e.g., understanding that certain symptoms are typically linked to specific diseases).
2.  **Rule Deduction:** Using the reasoning from step one combined with a few-shot examples (a small number of labeled samples), the LLM deduces specific rules for each class.

By forcing the model to think about *why* a classification happens before it tries to define the rules, \textsf{FeatLLM} helps the system ignore "spurious correlations"—irrelevant patterns in the data that might confuse a simpler model but are logically disconnected from the actual task.

## Turning Natural Language into Data

One of the biggest challenges in rule-based systems is how to translate a human-like sentence—like "If the patient's age is over 60 and their blood pressure is high"—into a format a computer can process. \textsf{FeatLLM} solves this by using the LLM's ability to generate code.

The framework prompts the LLM to output the rules in a way that can be parsed into Python code. This code is then executed to transform the raw data into a new set of binary features. For every rule generated, a new feature is created: a $1$ if the sample satisfies the rule, and a $0$ if it does not. 

Once the data is transformed into these binary features, the heavy lifting of the LLM is finished. To make the final prediction, \textsf{FeatLLM} uses a simple linear model. For a sample $i$ and class $k$, the framework computes the logit as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

where $\mathbf{z}_k^i$ is the vector of binary features for that class and $\mathbf{w}_k$ represents the trainable weights. The final class probabilities $\mathbf{p}^i$ are calculated using the Softmax function:

$$\mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i, ..., \text{logit}_{c}^i])$$

By optimizing these weights using a few-shot training set, the model learns which of the LLM-generated rules are actually the most important for accurate prediction.

## Scaling with Bagging and Ensembling

To ensure the system is robust and can handle massive datasets, \textsf{FeatLLM} employs two key techniques from ensemble learning:

*   **Bagging:** When a dataset has too many features to fit into a single prompt, the framework uses bagging to select subsets of features or samples for different trials. This allows the model to "see" different parts of the data without overwhelming the LLM's context window.
*   **Ensembling:** Because LLMs can sometimes be inconsistent, \textsf{FeatLLM} repeats the rule-generation process multiple times. It then averages the predictions from these different "weak learners." This ensures that even if the LLM generates a slightly incorrect rule in one trial, the correct rules from other trials will compensate for it.

## The Bottom Line

The shift from "Predictor" to "Architect" offers three major advantages for production environments:

*   **Efficiency:** You only need to query the LLM a handful of times to discover the rules. Every subsequent prediction is made by a simple linear model, making inference nearly instantaneous.
*   **Accessibility:** \textsf{FeatLLM} only requires API-level access to an LLM. It doesn't require the ability to fine-tune the model or access its underlying weights.
*   **Robustness:** By leveraging the LLM's prior knowledge and a structured reasoning path, the framework is significantly better at ignoring noise and focusing on the features that actually matter.

In testing across 13 different datasets, \textsf{FeatLLM} outperformed existing LLM-based approaches (like TabLLM and STUNT) by an average of 10%, proving that sometimes the smartest way to use an AI is to let it build the blueprint, not just do the work.



# Small Data, Big Insights: How to Train AI When You Only Have a Handful of Examples

In high-stakes industries like healthcare and finance, data is often a double-edged sword. While we have massive amounts of information, "labeled" data—where experts have manually tagged outcomes like "disease" or "fraud"—is incredibly expensive and time-consuming to produce. This creates a significant hurdle for traditional machine learning, which typically requires thousands of examples to perform accurately.

This is where **few-shot learning** comes into play. The goal is to train a model to perform a task using only a tiny handful of labeled examples. However, when you only have a few examples, models are prone to "overfitting" or picking up on "spurious correlations"—random patterns in the data that don't actually mean anything. To solve this, we need to provide the model with something more than just raw numbers: we need to provide it with context and "prior knowledge."

## The Power of Prior Knowledge

Large Language Models (LLMs) are uniquely suited for this because they have been trained on massive corpora of human knowledge. An LLM "knows" that older individuals might be at a higher risk for certain heart conditions because it has processed thousands of medical texts. 

Current methods try to use LLMs to solve tabular data problems by feeding the data into the prompt and asking the LLM for a prediction. While this works, it has three major flaws:
1. **High Cost:** It requires a separate LLM query for every single row of data, making it too slow and expensive for large datasets.
2. **Accessibility:** Many top-tier LLMs don't allow the fine-tuning required by some current methods.
3. **Prompt Limits:** If a table has hundreds of columns, the prompt becomes too long for the LLM to process effectively.

## Enter FeatLLM: The LLM as a Feature Engineer

Instead of asking the LLM to be the "predictor," a new framework called **FeatLLM** reassigns the LLM a much more strategic role: the **Feature Engineer**. 

Instead of asking the LLM to say "Yes" or "No" to a medical diagnosis, we ask it to look at a few examples and describe the *logic* behind the diagnosis. FeatLLM guides the LLM through a structured two-step reasoning process:

1. **Causal Reasoning:** First, the LLM is asked to identify the general relationship between features and the target based on its prior knowledge (e.g., "How does age generally affect heart health?").
2. **Rule Extraction:** Second, using both its prior knowledge and the few-shot examples provided, the LLM deduces specific "rules" (e.g., "If Age $> 60$ and Blood Pressure $> 140$, then High Risk").

## From Rules to Results

Once FeatLLM extracts these rules, the heavy lifting shifts away from the LLM. The framework parses these natural language rules into executable code to transform the raw data into a new set of **binary features**. For every sample, the model creates a new column for each rule: a $1$ if the sample satisfies the rule and a $0$ if it doesn't.

To make the final prediction, FeatLLM uses a simple, high-speed linear model. For a sample $i$ and a class $k$, the logit is calculated as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

In this equation, $\mathbf{z}_k^i$ represents the binary features generated from the rules, and $\mathbf{w}_k$ represents trainable weights that determine how important each rule is. By using a simple linear model for inference, FeatLLM achieves the speed of traditional machine learning while retaining the "intelligence" of an LLM.

## Robustness and Scalability

To ensure the system doesn't fail if the LLM makes a mistake in one specific query, FeatLLM employs an **ensemble approach** combined with **bagging**. It repeatedly generates different sets of rules and averages the results. This has two major benefits:
* **Error Correction:** If the LLM generates a "noisy" or incorrect rule in one trial, the correct rules from other trials will compensate.
* **Handling Big Data:** When a dataset has too many columns to fit into a single prompt, bagging allows the model to look at different subsets of features across different trials, ensuring no data is left behind.

## The Bottom Line

The results are compelling. Across 13 different datasets, FeatLLM significantly outperformed existing methods, improving performance by an average of 10%. More importantly, it proved that we don't need to treat LLMs as black boxes that do all the work. By using them as expert feature engineers to distill human-like logic into simple rules, we can build highly accurate, cost-effective models even when we only have a handful of examples to start with.



# Beating the Token Limit: How to Feed Massive Tables into an LLM

One of the most significant hurdles in applying Large Language Models (LLMs) to tabular data is the "context window" limitation. While LLMs are incredibly capable at reasoning, you cannot simply dump a spreadsheet with hundreds of columns and thousands of rows into a single prompt. As the number of features grows, the serialized text length becomes prohibitive, often leading to truncated inputs or a significant decline in model performance.

The research paper "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning" introduces a framework called \textsf{FeatLLM} that elegantly sidesteps this bottleneck. Instead of asking the LLM to perform an end-to-end prediction for every single row of data, the researchers reposition the LLM as an expert feature engineer. By doing so, they can leverage the LLM's prior knowledge to distill complex logic into compact rules, using a "bagging" and "ensemble" strategy to manage massive datasets.

## The Problem: Inference Bottlenecks and Token Limits

Current LLM-based approaches for tabular learning typically involve serializing data and feeding it into a prompt to get a prediction. This approach has three major flaws:
1. **Inference Cost:** It requires an LLM call for every single sample, which is computationally expensive and slow.
2. **Accessibility:** Many high-performance models only allow inference via APIs, making parameter-efficient fine-tuning difficult or impossible.
3. **Context Limits:** When a table has a large number of features, the prompt length exceeds the model's capacity, making the task infeasible.

\textsf{FeatLLM} addresses these by changing the goal. Instead of asking the LLM, "What is the label for this row?", the framework asks, "What are the rules that determine the label for this class?"

## The Solution: LLM as a Feature Engineer

In the \textsf{FeatLLM} framework, the LLM is prompted to analyze a few-shot example set and the task description to extract decisive rules (e.g., "If age > 60 and blood pressure > 140, then class 1"). These rules are then parsed into Python code to transform the original data into new binary features.

To handle the "massive table" problem, the researchers employ two specific techniques: **feature bagging** and **ensembling**.

### 1. Bagging to Shrink the Prompt
To stay within the token limits of the LLM, \textsf{FeatLLM} uses bagging to select a subset of features or instances for each individual query. By only showing the LLM a portion of the table's features at a time, the framework ensures that the prompt remains concise and manageable. This prevents the model from being overwhelmed by irrelevant columns, which helps it focus on the most significant relationships.

### 2. Ensembling for Complete Coverage
Because bagging only looks at a subset of the data, a single query might miss important correlations present in the excluded features. The framework solves this by running the process multiple times (e.g., 20 trials) and aggregating the results. This ensemble approach provides two main benefits:
* **Robustness:** If the LLM generates an incorrect or noisy rule in one trial, the correct rules from other trials compensate for it.
* **Coverage:** The ensemble of "weak learners" (the rules extracted from various subsets) effectively covers the complexity of the entire dataset, even if no single prompt could contain all the information.

## Inference via Simple Linear Models

A key technical highlight of this paper is how it handles the inference phase. Once the LLM has generated the rules and the data has been transformed into new binary features, the LLM is no longer needed.

Let $\mathbf{z}_k^i \in \{0, 1\}^R$ be the vector of binary features for sample $\mathbf{x}^i$ for class $k$, where $R$ is the number of rules per class. The framework uses a simple linear model to estimate the class likelihood $\mathbf{p}^i$ as follows:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$
$$\mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i, ..., \text{logit}_{c}^i])$$

Here, $\mathbf{w}_k$ represents trainable weights that signify the importance of each rule. By training these weights on a few-shot training set, the model learns which rules generated by the LLM are actually predictive. This architecture ensures that the inference time is nearly as fast as traditional machine learning models, while still benefiting from the deep reasoning and prior knowledge of an LLM.

## Conclusion

By shifting the LLM's role from "predictor" to "feature engineer," \textsf{FeatLLM} successfully overcomes the constraints of context windows. The combination of bagging (to fit the prompt) and ensembling (to ensure accuracy) allows the framework to scale to complex, high-dimensional tables. The result is a system that is both high-performing in low-shot regimes and efficient enough for real-world industrial applications.



# Teaching AI to Filter Out Noise: The Secret to Robust Data Science

In the world of data science, especially when working with limited data (few-shot learning), one of the biggest hurdles is "spurious correlation." This occurs when a machine learning model identifies a pattern that exists in the training data but has no actual causal relationship with the outcome. For example, a model might conclude that a specific patient's zip code is a primary indicator of a disease simply because, in a small sample, all patients with that disease happened to live in that area.

When we use Large Language Models (LLMs) to solve these problems, they are also susceptible to these distractions. If we simply feed a few examples into an LLM and ask it to make a prediction, it might latch onto irrelevant noise. The researchers behind \textsf{FeatLLM} propose a novel way to prevent this by shifting the LLM's role from a "predictor" to a "feature engineer."

## From Prediction to Feature Engineering

Most current methods for using LLMs in tabular learning involve sending each data sample to the LLM to get a final prediction. This is computationally expensive, faces prompt size limitations, and often ignores the underlying logic of the data.

\textsf{FeatLLM} takes a different approach. Instead of asking the LLM to give an answer for every sample, it asks the LLM to define the *rules* that lead to an answer. The LLM analyzes the task and the available features to generate a set of decisive rules (e.g., "If age is over 60 and blood pressure is above 140, then the risk is high"). These rules are then converted into new binary features. Once these features are generated, a simple, high-speed machine learning model—like a linear regression—is used to make the final predictions. This makes the inference process much faster and more scalable.

## The Secret Sauce: Two-Step Reasoning

The core innovation that makes \textsf{FeatLLM} robust against noise is its structured two-step reasoning process. This process mimics how a human expert would approach a new problem: first by considering what they already know, and then by looking at the specific evidence provided.

### Step 1: Understanding the Problem via Prior Knowledge
In the first step, the LLM is asked to infer the relationship between the features and the target task without looking at any specific examples. By isolating this step, the LLM relies entirely on its internal "world knowledge." For a medical task, it uses its pre-trained understanding of biology and medicine to determine which features are theoretically important. This prevents the model from being immediately distracted by coincidental patterns in a small dataset.

### Step 2: Deriving Rules from Evidence
In the second step, the LLM is provided with both its previous reasoning and a few specific examples (few-shot demonstrations). It then uses this combined information to deduce specific rules for each class. Because the LLM has already "centered" itself on the logically relevant features in Step 1, it is far less likely to create rules based on irrelevant or noisy columns.

## Turning Logic into Math

Once the LLM generates these rules, \textsf{FeatLLM} translates them into a format that a computer can process. The rules are parsed into code to create binary features, where a "1" indicates the sample satisfies the rule and a "0" indicates it does not.

To determine how much weight to give each rule, the framework fits a linear model. For a sample $\mathbf{x}^i$ and a specific class $k$, let $\mathbf{z}_k^i \in \{0, 1\}^R$ be the vector of binary features generated from the rules, where $R$ is the number of rules. The model calculates the logit for each class as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

Here, $\mathbf{w}_k$ represents the trainable weights that signify the importance of each rule. By projecting these weights into a positive subspace, the model ensures that the features generated by the LLM only contribute to the likelihood of a class. The final probability $\mathbf{p}^i$ for each class is then calculated using the softmax function:

$$\mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i, ..., \text{logit}_{c}^i])$$

## Robustness in Practice

The effectiveness of this approach was tested by adding "spurious correlations"—randomly attached columns that had nothing to do with the task—to datasets like the Heart dataset. While traditional models saw a significant drop in performance as more noise was added, \textsf{FeatLLM} remained remarkably stable.

By forcing the LLM to reason about the problem's logic *before* looking at the data, \textsf{FeatLLM} successfully filters out the "noise" that often plagues automated data science. This makes it a powerful tool for industries like finance and healthcare, where data is often scarce and the cost of making a mistake based on a false correlation is high.
