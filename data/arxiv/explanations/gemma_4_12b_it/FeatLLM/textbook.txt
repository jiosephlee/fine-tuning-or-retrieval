\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Introduction to LLMs in Tabular Learning

# Overview of LLMs and In-Context Learning

Large Language Models (LLMs) have emerged as transformative tools in artificial intelligence due to their ability to handle complex, unseen reasoning tasks without requiring task-specific fine-tuning. These models are trained on massive, diverse text corpora, which allows them to internalize a vast amount of "prior knowledge." In many practical applications, this internal knowledge can serve as a powerful substitute for human expert domain knowledge. For example, an LLM might already "know" that certain medical conditions are more prevalent in older individuals, a fact that a standard machine learning model would have to learn from scratch from the raw data.

One of the primary ways researchers leverage these models is through in-context learning. This technique involves providing the LLM with a task description and a few examples within the input prompt. By analyzing these examples, the LLM can "attend" to the most relevant features and context, allowing it to perform a task it was not explicitly trained to do. This capability demonstrates that LLMs are not just text generators; they can act as sophisticated data analysts capable of understanding the underlying structure of a problem.

In the context of tabular learning, this means that by serializing data into a textual format—where features are described in natural language—an LLM can be prompted to interpret the relationships between different data columns and a target outcome. Instead of just looking at numbers, the model uses its linguistic understanding to recognize patterns, making it a potential candidate for high-level reasoning tasks that simpler models might struggle to interpret.

# Challenges of Few-Shot Tabular Learning (Small data, spurious correlations)

Few-shot learning refers to the challenge of training a model to perform accurately when only a very small number of labeled samples are available. In a $k$-shot learning setup, where $k$ is much smaller than the total number of samples $N$ in a dataset $\mathcal{D}$, the primary risk is that the model will learn "spurious correlations." These are patterns in the data that appear to be predictive in the small training set but do not actually reflect the underlying reality of the problem. Because the model has so few examples to look at, it might latch onto a random fluke or an irrelevant feature that happens to correlate with the label in those few instances.

To combat this, researchers have traditionally tried various strategies. Some focus on semi-supervised learning, using large amounts of unlabeled data to provide a baseline for the model's understanding. Others look into task-agnostic unsupervised pre-training, where a model learns to reconstruct or distinguish between different parts of a dataset before it is ever shown a label. Contrastive learning and data augmentation are also common techniques used to help models generalize better by exposing them to varied versions of the same data.

However, tabular data presents a unique hurdle: it is highly heterogeneous. Unlike images, where pixels have a consistent spatial relationship, tabular data consists of disparate types of information—ages, names, categories, and measurements—all mixed together. This makes it difficult to find "universal" augmentations that work across all types of tables. Consequently, in low-shot regimes, identifying the correct inductive biases (prior assumptions about the data) remains a significant challenge for standard machine learning models.

# Review of existing LLM-based tabular methods (e.g., TabLLM, anypredict)

The integration of LLMs into tabular learning is a relatively recent but rapidly evolving field. The general approach involves serializing tabular data into text and feeding it into an LLM along with feature descriptions and task goals. By doing this, the LLM can use its prior knowledge to infer how different features might relate to the target class. This has proven highly effective in few-shot scenarios, where the LLM's "common sense" helps compensate for the lack of training data.

Several specific frameworks have been developed to manage this process. For instance, *AnyPredict* focuses on serializing the data into prompts to allow the LLM to perform inference directly. Other methods, such as *TabLLM*, take a more intensive approach by using parameter-efficient fine-tuning techniques, like LoRA or IA3, to adjust the LLM's weights specifically for a tabular task. Additionally, some methods rely purely on in-context learning, where the LLM is provided with demonstrations of the task and must provide an answer based solely on those examples without any weight updates.

While these methods have shown that LLMs can significantly outperform conventional baselines in low-shot settings, they often treat the LLM as a "black box" for end-to-end prediction. In these systems, every single sample in a test set must be sent to the LLM to receive a prediction. While effective, this approach introduces significant hurdles for real-world industrial deployment, leading to the need for more efficient architectures.

# Limitations of current approaches: Computational cost, fine-tuning requirements, and prompt size constraints

Despite the high performance of current LLM-based tabular methods, they face three major practical limitations. The first is computational cost. Because most existing methods require the LLM to generate a prediction for every single sample during the inference phase, the process becomes extremely slow and expensive when dealing with large datasets. In an industrial setting where thousands or millions of predictions might be needed in real-time, sending each sample as a separate query to an LLM is often infeasible.

The second limitation involves the accessibility of the models. Many of the highest-performing LLMs do not provide open-source codebases for fine-tuning. Instead, they are only accessible via inference APIs. This means that methods requiring parameter-efficient tuning or full fine-tuning cannot be used with the most powerful available models. Researchers and practitioners are thus restricted to in-context learning, which may not always capture the necessary nuances of a specific dataset.

Finally, there is the issue of prompt size. As the number of features in a tabular dataset grows, the serialized text becomes increasingly long. LLMs have limited context windows, and when a prompt becomes too large, the model's performance can decline significantly—a phenomenon sometimes referred to as the model "getting lost" in long sequences. This makes it very difficult to use LLMs for complex tables with hundreds of attributes, as the entire table description may not fit into a single prompt, or the model may fail to focus on the relevant information within that large volume of text.

# Introduction to the FeatLLM framework: A paradigm shift from prediction to feature engineering

The \textsf{FeatLLM} framework introduces a fundamental paradigm shift to address these limitations. Instead of using the LLM to provide an end-to-end prediction for every sample, \textsf{FeatLLM} assigns the LLM the role of an expert "feature engineer." In this framework, the LLM is used only during the training phase to analyze the data and derive high-quality rules—essentially, the logical "criteria" that distinguish one class from another.

Once the LLM generates these rules, they are parsed into program code and used to transform the original data into a set of new binary features. For example, if the LLM determines that a patient has a high risk of heart failure when their age is over 60 and their blood pressure is high, \textsf{FeatLLM} creates a new binary feature where "1" indicates the patient meets both conditions and "0" indicates they do not. This transforms the complex reasoning task into a simple binary format that can be handled by a low-complexity downstream model, such as a linear regression model.

This approach solves the cost and accessibility problems because the LLM is no longer involved during the inference phase; once the rules are discovered, a simple model can generate predictions instantly. Furthermore, \textsf{FeatLLM} handles prompt size constraints by using an ensemble approach combined with "feature bagging." By selecting only a subset of features or samples for each LLM query, the framework ensures that the prompt remains within the acceptable size limits while still capturing the full complexity of the dataset through multiple trials. This results in a robust, scalable, and efficient method for few-shot tabular learning.

The FeatLLM Framework: Architecture and Philosophy

# Problem Formulation: Defining datasets, features, and labels

To understand the FeatLLM framework, we must first establish a clear mathematical and conceptual foundation for the data it processes. The framework operates on a tabular dataset, which is a collection of structured data organized into rows and columns. Formally, let $\mathcal{D}$ represent a tabular dataset consisting of $N$ labeled samples, expressed as $\mathcal{D} = \{(\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^{N}$. In this notation, each sample $\mathbf{x}^i$ is a $d$-dimensional vector representing the input features of an individual observation. The value $\mathbf{y}^i$ represents the corresponding ground-truth label for that specific sample.

In the context of classification, which is the primary focus of this research, the label $\mathbf{y}^i$ is drawn from a predefined set of classes. However, raw numbers in a vector do not inherently convey meaning to a machine learning model. To bridge this gap, FeatLLM utilizes natural language feature names, denoted by the set $F = \{f_j\}_{j=1}^{d}$. Each feature $f_j$ comes with a separate natural language definition that describes what that specific column represents. These descriptions are critical because they provide the semantic context that Large Language Models (LLMs) need to perform reasoning.

The framework is specifically designed to excel in $k$-shot learning regimes. In traditional supervised learning, a model might be trained on all $N$ samples. In $k$-shot learning, however, only a small subset of $k$ labeled samples (where $k < N$) is randomly sampled to train the model. This mimics real-world scenarios where labeled data is scarce and expensive to obtain, requiring the model to generalize from a very limited number of examples.

# The Feature Engineering Paradigm: Shifting the LLM's role

A significant portion of contemporary research involving Large Language Models and tabular data treats the LLM as an end-to-end predictor. In those systems, every single sample in a test set must be serialized into text and sent to the LLM to receive a final prediction. While effective, this approach is computationally expensive and creates a bottleneck because the LLM must be queried for every individual inference. Furthermore, many high-performing LLMs are only accessible via inference APIs, meaning researchers cannot always access the underlying training code or weights to fine-tune the model.

FeatLLM introduces a paradigm shift by repositioning the LLM as a feature engineer rather than a final predictor. Instead of asking the LLM to "Predict the class for this row," the framework asks the LLM to "Identify the underlying rules that define this class." By doing this, the LLM uses its vast internal prior knowledge—learned during its pre-training on massive text corpora—to distill complex logic into a set of human-readable and machine-executable rules. 

Once these rules are identified, the LLM's job is essentially finished. The framework then uses these rules to transform the raw data into a new set of features. These new features are passed into a simple, high-speed downstream machine learning model, such as a linear model. This separation of concerns allows the framework to leverage the high-level reasoning and "common sense" of the LLM to handle the hard part of the problem (discovering logic) while using a traditional model to handle the repetitive task of making predictions across thousands of samples.

# Pipeline Overview: Rule extraction, parsing, and downstream modeling

The FeatLLM pipeline is structured as a multi-stage process that mimics the reasoning of a human expert. The first stage is rule extraction, which is facilitated by a specialized prompt design. This prompt contains three components: basic information (task description, feature definitions, and few-shot examples), reasoning instructions, and response instructions. The reasoning instructions are particularly important as they guide the LLM through a two-step process. In the first step, the LLM is asked to infer causal relationships or tendencies between features and the task using only its prior knowledge, without looking at the examples. In the second step, it combines that prior knowledge with the provided few-shot examples to deduce specific rules for each class. By separating these steps, the framework helps the LLM ignore "spurious correlations"—irrelevant patterns in the data that might look like rules but don't actually cause the outcome.

The second stage involves parsing these rules. Because LLMs can be inconsistent in their output (for example, one might write "$>$" while another writes "greater than"), the framework does not use a rigid parser. Instead, it uses the LLM again to convert the natural language rules into simple Python code. This generated code is then executed using Python’s $\texttt{exec()}$ function. This execution converts the raw data into a set of new binary features. For every sample, a new feature is created for every rule; if the sample satisfies the rule, the feature is assigned a value of $1$, and if it does not, it is assigned a $0$.

The final stage is the downstream modeling. The framework takes these binary features and applies a linear model to estimate the likelihood of each class. To ensure robustness, FeatLLM employs an ensemble approach using bagging. The entire process of rule generation and training is repeated multiple times. In each trial, the framework uses a high temperature for the LLM to encourage variety, randomizes the order of the few-shot examples, and selects a random subset of features or instances. By averaging the results of these multiple trials, the framework creates a robust final prediction that is less likely to be skewed by a single "bad" rule generated by the LLM in a single query.

# Advantages of FeatLLM: Low inference latency and API-level accessibility

The primary architectural advantage of FeatLLM is its efficiency at inference time. In traditional LLM-based tabular learning, the cost and time required to run a prediction scale linearly with the number of test samples. If you have 10,000 samples, you must perform 10,000 LLM queries. In the FeatLLM framework, the LLM is only queried during the "feature engineering" phase. Once the rules are extracted and the downstream model is trained, the inference is performed by the simple linear model. This means the inference latency is comparable to traditional machine learning methods, making it much more practical for industrial applications.

Furthermore, FeatLLM is designed to be highly accessible. Because it does not require fine-tuning the LLM, it can be used with models that only provide inference APIs (like GPT-3.5). This is a significant advantage over methods like TabLLM, which require access to specific model checkpoints and training environments. Additionally, by using bagging and ensemble techniques, FeatLLM overcomes the "prompt size" limitation. When a dataset has so many features that it cannot fit into a single LLM prompt, bagging allows the framework to break the data into smaller, manageable chunks, ensuring that the model can still perform accurately even on complex datasets with hundreds of attributes.

# Mathematical formulation of class likelihood using generated rules

To formalize how FeatLLM makes its final prediction, we look at the transition from natural language rules to class probabilities. Suppose that for a specific class $k$, the LLM has generated a set of $R$ rules. For any given sample $\mathbf{x}^i$, we can represent the satisfaction of these rules as a binary vector $\mathbf{z}_k^i \in \{0, 1\}^R$. Each element in this vector is a $1$ if the sample satisfies the corresponding rule and a $0$ otherwise.

The framework then uses a linear model to determine the importance of each rule. For each class $k$, there is a weight vector $\mathbf{w}_k$. To ensure that the rules only contribute positively to the likelihood of a class (preventing a rule from "penalizing" a class it is supposed to describe), the weights are projected into a positive subspace using the $\max(\mathbf{w}_k, 0)$ operation. The logit for class $k$, denoted as $\text{logit}_k^i$, is calculated as the dot product of these weights and the binary feature vector:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

Once the logits are calculated for all $c$ classes, the final probability $\mathbf{p}^i$ for each class is determined using the Softmax function:

$$\mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i, ..., \text{logit}_{c}^i])$$

The weights $\mathbf{w}_k$ are learned by optimizing a cross-entropy loss function using the $k$-shot training samples. Finally, the ensemble prediction is the average of the probabilities $\mathbf{p}^i$ calculated across all $T$ trials in the bagging process. This mathematical structure ensures that the framework effectively weighs the "quality" of the rules discovered by the LLM while maintaining a simple, fast, and interpretable inference step.

Prompt Engineering for Rule Extraction

# Basic Information Description

In the \textsf{FeatLLM} framework, the success of rule extraction depends heavily on how the Large Language Model (LLM) perceives the task. To ensure the model understands the objective, the framework provides a "Basic information description" component within the prompt. This component serves as the foundational context, providing the LLM with the necessary background to act as an expert feature engineer. It includes a task description, which is specifically formulated as a question. For example, if the goal is to identify heart failure in a clinical setting, the prompt would ask something like, "Does this patient's myocardial infarction complications data indicate chronic heart failure? Yes or no?" By framing the task as a question, the model is guided to seek a specific answer, helping it focus on the most relevant information.

Beyond the high-level task description, the prompt includes detailed descriptions of the features provided in the tabular dataset. These descriptions include the value types of the features and, where applicable, their specific definitions. For categorical variables, the prompt may also include examples of possible categories. This ensures that the LLM does not have to guess the nature of the data, which is critical when the model is operating in a few-shot regime where it has very few examples to learn from. Providing these definitions allows the LLM to leverage its pre-trained prior knowledge more effectively, as it can map the specific column names to broader concepts it encountered during its initial training.

Finally, the Basic information description incorporates few-shot examples to provide the LLM with concrete demonstrations of how to process the data. These examples are serialized into a text format that the LLM can easily interpret. The paper defines this serialization process as follows:

$\text{Serialize}(\mathbf{x}^i, \mathbf{y}^i, F) = \text{``} f_1 \text{ is } \mathbf{x}^i_1. \dots f_d \text{ is } \mathbf{x}^i_d. \text{ Answer: } \mathbf{y}^i \text{''}$

In this notation, $\mathbf{x}^i$ represents the input features of the $i$-th sample, $\mathbf{y}^i$ represents the ground-truth label, and $F$ denotes the set of feature names. By presenting the data in this serialized text format, the framework allows the LLM to "attend" to specific features and examples, mimicking the way a human expert might scan a medical chart or a financial statement to find relevant indicators.

# Two-Step Reasoning Instructions

A key innovation in \textsf{FeatLLM} is the use of a structured, two-step reasoning process to guide the LLM's inference. Rather than asking the LLM to immediately generate rules from the few-shot examples, the framework provides specific reasoning instructions that split the cognitive load into two distinct phases. This approach is designed to mimic the way a human expert would approach a new problem: first by considering general knowledge and then by looking at specific cases.

In the first step, the LLM is instructed to infer the causal relationship or general tendency between the features and the task description. Crucially, during this step, the LLM is encouraged to ignore the provided few-shot examples and rely solely on its own prior knowledge and common sense. This allows the model to fully extract the "criteria" underlying the problem—for example, identifying that age or specific blood pressure markers are generally associated with heart disease before even looking at the specific patients in the dataset. By isolating this step, the framework ensures that the model's logic is grounded in established knowledge rather than potentially misleading patterns in a small sample size.

In the second step, the LLM is asked to use both the knowledge derived from the first step and the provided few-shot examples to deduce specific, decisive rules for each class. This sequential process is vital because it forces the model to filter out uninformative features. If a feature is irrelevant to the general task (Step 1), the model is less likely to create a rule for it based on a coincidental correlation in the few-shot examples (Step 2). This structured reasoning leads to higher-quality rules that are more likely to generalize to unseen data.

# Mitigating Spurious Correlations through structured reasoning

One of the primary risks in few-shot learning is the model's tendency to learn "spurious correlations"—patterns that appear in the small training set but do not actually reflect the underlying truth. For instance, if a small dataset of heart disease patients happens to include many people who also happen to play a specific sport, a simple model might incorrectly conclude that the sport is a predictor of the disease. \textsf{FeatLLM} addresses this problem specifically through its structured reasoning approach.

By forcing the LLM to first reason about the general relationship between features and the task using its internal prior knowledge, the framework establishes a "logical filter." Because the model is prompted to consider the causal link between a feature and the target (such as "Does high blood pressure cause heart issues?"), it is less likely to be distracted by irrelevant columns. The paper demonstrates the efficacy of this approach using the Heart dataset. When the researchers added many irrelevant columns from the Adult dataset (columns that had nothing to do with heart health), \textsf{FeatLLM} showed the least performance degradation compared to other baselines.

The results indicate that the framework successfully prevents the generation of rules based on noisy, irrelevant columns. In their experiments, they observed that rules based on noisy columns accounted for only $1\%$ to $2\%$ of the total rules generated. This robustness is a direct result of the reasoning instructions, which prioritize the "why" of the task before the "what" of the specific data samples, ensuring that the discovered features are meaningful and robust.

# Response Instructions

For the rules generated by the LLM to be useful in a machine learning pipeline, they must be converted from natural language into a format that a computer can execute. To facilitate this, \textsf{FeatLLM} employs specific "Response Instructions." These instructions tell the LLM exactly how to structure its output for each answer class. They include guidelines on the required format for the response and the specific structure each individual rule should follow. By standardizing these instructions, the framework ensures that the LLM provides consistent outputs that are easier to parse.

However, even with strict instructions, LLMs can produce "noisy" syntactic changes. For example, an LLM might represent a "greater than" relationship as "$>$" in one instance and as the phrase "greater than" in another. Such variability makes it difficult to build a rigid program for parsing. To solve this, \textsf{FeatLLM} uses a clever two-stage parsing strategy. Instead of attempting to write a perfect parser to handle every possible linguistic variation, the framework uses the LLM again.

The framework provides a prompt to the LLM that includes the function name, input and output descriptions, and the rules inferred in the previous step. The LLM is then asked to generate simple Python code based on these rules. Because LLMs are proficient at generating code, they can interpret the semantic meaning of the rules regardless of minor syntactic differences. The resulting code is then executed using Python’s `exec()` function to transform the raw tabular data into new binary features. This approach leverages the LLM's strengths in understanding language to overcome the technical hurdles of data processing.

# Trade-offs in Rule Quantity

A critical hyper-parameter in the \textsf{FeatLLM} framework is the number of rules extracted for each class. The researchers opted to set a fixed number of rules—specifically 10—for each class. This decision is based on a careful balance between two competing constraints: the limitations of the LLM's prompt size and the risk of model overfitting.

If the number of rules is too small, the model may suffer from underfitting, as it might fail to capture the complexity of the underlying task. Conversely, if the LLM is asked to generate too many rules, the resulting prompt can become excessively large, potentially exceeding the context window of the LLM or causing a decline in performance due to "lost in the middle" effects where the model struggles to attend to all information in a long prompt. Furthermore, in a few-shot regime, generating an excessive number of rules can lead to overfitting, where the model learns rules that are too specific to the few provided samples and fail to generalize.

To further manage these trade-offs, especially when dealing with datasets that have a very large number of features, \textsf{FeatLLM} employs ensemble methods and bagging. By using bagging, the framework can select a subset of features or instances for each trial, ensuring that the prompt size remains manageable. The final prediction is made by ensembling the results of multiple trials. This ensemble approach provides two benefits: it improves robustness by allowing correct rules from one trial to compensate for incorrect rules in another (self-consistency), and it allows the framework to capture a wider range of features across different trials without overwhelming a single prompt.

Rule Parsing and Predictive Modeling

# The Parsing Challenge: Handling syntactic noise in LLM outputs

When utilizing Large Language Models (LLMs) to generate rules for tabular learning, a significant technical hurdle arises in the transition from natural language to machine-executable logic. While LLMs are proficient at generating human-readable descriptions—such as "the patient's age is greater than 50"—these descriptions are often syntactically inconsistent. Because LLMs are generative, they may provide different ways to express the same logical constraint across different queries or even within the same set of outputs. For example, one output might use the mathematical symbol "$>$" while another might use the phrase "greater than."

This variability constitutes "syntactic noise." If a developer attempts to build a traditional, hard-coded parser to interpret these rules, the parser would need to account for an enormous variety of linguistic permutations, synonyms, and formatting quirks. Such a system would be brittle and difficult to maintain, as it would constantly fail when encountering a phrasing it was not specifically programmed to recognize. Therefore, the challenge lies in finding a way to convert these fluid, natural language rules into a structured format that can be applied to a dataset without losing the semantic meaning intended by the LLM.

# LLM-based Code Generation: Using LLMs to write Python code for data transformation

To overcome the limitations of manual parsing, the \textsf{FeatLLM} framework leverages the LLM’s inherent ability to bridge the gap between human language and computer code. Instead of trying to parse the natural language rules directly into a mathematical formula, the framework asks the LLM to act as a translator by generating Python code. Because LLMs have been trained on vast amounts of source code, they possess a deep understanding of how to represent logical conditions as functional programming instructions.

In this stage, the framework provides the LLM with a specialized prompt that includes the function name, descriptions for the inputs and outputs, and the specific rules inferred in the previous step. By providing these context clues, the LLM is guided to produce a code snippet that performs the necessary data transformation. This approach is highly effective because it treats the LLM as a semantic interpreter; even if the rules are phrased differently (e.g., "is higher than" vs. "$>$"), the LLM understands the underlying intent and can produce the correct Python logic to evaluate that condition. This bypasses the need for complex, rule-based parsers and ensures that the resulting logic is computationally executable.

# Executing Python code via exec() for binary feature creation

Once the LLM has generated the Python code, the framework must execute that code against the actual tabular data to extract useful information. To do this, \textsf{FeatLLM} employs Python’s \texttt{exec()} function. The \texttt{exec()} function allows a program to take a string of text—in this case, the code generated by the LLM—and execute it as live code within the system. This creates a dynamic pipeline where the logic used to filter data is generated on the fly.

The primary goal of this execution step is to create new "binary features." For every sample in the dataset and for every rule generated for a specific class, the executed code evaluates whether the sample satisfies that rule. If the condition is met, the result is recorded as a $1$; otherwise, it is recorded as a $0$. This transformation is crucial because it converts complex, multi-variable natural language rules into a simple binary format. These binary features serve as the foundation for the final predictive model, effectively distilling the LLM's high-level reasoning into a structured format that a standard machine learning model can process.

# The Downstream Model: Linear weights and non-negative subspace projection

After the rules are parsed into binary features, the framework employs a simple downstream machine learning model to estimate the likelihood of a sample belonging to a specific class. For each class $k$, the framework represents the set of binary features as a vector $\mathbf{z}_k^i \in \{0, 1\}^R$, where $R$ is the number of rules extracted for that class. Rather than simply counting how many rules are satisfied (which would assume every rule is equally important), the framework introduces a set of trainable weights, $\mathbf{w}_k$, to signify the importance of each rule.

A critical component of this model is the projection of these weights into a non-negative subspace. The logit for class $k$ is calculated as:
$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$

By applying the $\max(\cdot, 0)$ operation, the framework ensures that the weights are non-negative. This is an important design choice for intuition: because these rules were specifically generated to identify a class, satisfying a rule should never *decrease* the likelihood of belonging to that class. The non-negative projection ensures that the features generated by the LLM act as additive evidence for the class likelihood, allowing the model to learn which rules are the most decisive and which are less relevant.

# Training via Cross-Entropy Loss and Softmax probabilities

The final step in the \textsf{FeatLLM} framework is to optimize these weights and produce a final prediction. Once the logits for all classes are calculated using the non-negative weights, they are passed through a softmax function to convert the raw scores into a probability distribution. Let $c$ be the number of classes; the probability vector $\mathbf{p}^i$ for a sample is defined as:
$\mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i, \dots, \text{logit}_{c}^i])$

To determine the optimal values for the weights $\mathbf{w}_k$, the framework optimizes a cross-entropy loss function using the few-shot training samples provided. This training process allows the model to "fine-tune" the importance of the rules discovered by the LLM. While the LLM provides the "knowledge" (the rules), the linear model provides the "judgment" (the weights), ensuring that the final prediction is grounded in the actual patterns found in the training data. By combining these two steps—LLM-driven rule discovery and weight-based linear modeling—the framework achieves a robust, high-performance few-shot learning system that is also computationally efficient at inference time.

Ensemble Strategies and Robustness

# Ensembling for Robustness

In the FeatLLM framework, the goal is to produce a reliable and accurate prediction for tabular data by leveraging Large Language Models (LLMs) as feature engineers. However, because LLMs can occasionally generate incorrect or noisy rules during the rule-extraction phase, the framework employs an ensemble strategy to enhance robustness. Instead of relying on a single pass of rule generation, the entire process of extracting rules, parsing them into code, and training the linear model is repeated multiple times. This repetition is designed to capture a diverse set of rules, where the strengths of some trials can compensate for the potential errors or "hallucinations" in others.

To ensure that each trial in the ensemble produces unique results, the framework sets a sufficiently high temperature during the LLM inference. This increases the randomness of the LLM's outputs, allowing for a broader variety of rules to be explored across different trials. Furthermore, the order of few-shot demonstrations provided in the prompt is randomized for each trial, as the sequence of examples can significantly influence the LLM's reasoning and final output. By conducting these trials, the framework benefits from a concept known as self-consistency, where rules that are inferred repeatedly across multiple trials are considered more likely to be accurate and reliable.

The final prediction is determined by aggregating the results of these $T$ trials. Let $\{\mathbf{w}[t]\}_{t=1}^T$ be the collection of trained weights from $T$ separate trials. For a given sample, the probability $\mathbf{p}^i$ for each class is computed for every trial $t$ using the linear model:
$\text{logit}_k^i = \max(\mathbf{w}_k[t], 0) \cdot \mathbf{z}_k^i$
$\mathbf{p}^i[t] = \text{Softmax}([\text{logit}_{1}^i[t], ..., \text{logit}_{c}^i[t]])$
The final prediction is then made by averaging the probabilities $\mathbf{p}^i[t]$ across all $T$ trials. This ensemble approach ensures that the final output is not overly sensitive to any single faulty rule, thereby providing a more stable and robust prediction for the end user.

# Feature Bagging

A significant challenge in applying LLMs to tabular data is the limitation of prompt size. When a dataset contains a very large number of features, the serialized text representing all the columns might exceed the maximum length allowed by the LLM's input window. FeatLLM addresses this limitation by incorporating a technique from ensemble learning known as feature bagging. In this context, bagging is used to select a subset of the available features or samples for each trial in the ensemble.

By selecting a subset of features for each iteration, the framework ensures that the prompt remains within the allowable size limits while still allowing the LLM to process the data. This approach also serves as a form of coverage: while a single rule set created in one trial might not capture the relationships of every single feature in a massive dataset, the collective ensemble of various weak learners—each trained on different bags of features—can nullify the impact of incomplete coverage. This makes the framework highly scalable, as it can handle datasets with hundreds of attributes that would otherwise be impossible to process in a single standard prompt.

# Hyper-parameter Analysis

The effectiveness of the FeatLLM framework is influenced by two primary hyper-parameters: the number of ensembles and the number of rules extracted per class. Understanding the trade-offs between these parameters is essential for optimizing the model's performance. The research indicates that as the number of ensembles increases, the performance of the model generally improves. This is because a larger ensemble provides more opportunities for the model to capture diverse and correct rules, thereby increasing the overall accuracy of the averaged probability.

However, the benefits of increasing the ensemble size eventually reach a point of convergence. In the experiments conducted, it was observed that performance gains begin to level off once the number of ensembles reaches approximately 20. Similarly, the number of rules extracted per class ($R$) must be carefully balanced. While more rules can provide more information, they also increase the dimensionality of the input to the linear model. In a few-shot learning regime, where training data is scarce, an excessively high number of rules can lead to overfitting. The study determined that 10 rules per class provide the optimal balance, maximizing the informative content of the prompt while maintaining a manageable input size and preventing the model from over-fitting to the small number of available samples.

# Inference vs. Training Time Comparison

One of the core motivations for the FeatLLM framework is to overcome the high computational costs and latency associated with existing LLM-based tabular learning methods. In many current approaches, the LLM must perform an inference for every single sample at test time. This makes the process extremely slow and expensive, especially when dealing with large-scale industrial applications. FeatLLM fundamentally changes this workflow by shifting the LLM's role from a predictor to a feature engineer.

In the FeatLLM framework, the LLM is only queried during the "training" phase to discover the rules and generate the new features. For example, in tests conducted on the Adult dataset, FeatLLM required only 30 API queries to generate the necessary features. Once these features are extracted and the simple linear model is trained, the LLM is no longer involved in the prediction process. At inference time, the model simply calculates a dot product and a softmax operation, resulting in an inference time that is comparable to traditional machine learning methods like Logistic Regression or XGBoost. This decoupling of rule discovery from sample prediction allows for a high-performance system that remains efficient and cost-effective in production environments.

# Analysis of Spurious Correlations

A major risk in few-shot learning is the tendency of models to learn "spurious correlations"—patterns in the data that appear statistically significant in a small sample but do not reflect the actual underlying cause of the target variable. FeatLLM is designed to be inherently robust against these correlations by leveraging the LLM's prior knowledge through a structured two-step reasoning process.

Before the LLM extracts rules from the few-shot examples, it is first instructed to infer the causal relationships or tendencies between the features and the task description based on its general knowledge. By forcing the model to consider "common sense" first, the framework encourages the LLM to focus on informative features and ignore irrelevant ones. This is demonstrated in experiments where irrelevant columns from the Adult dataset were attached to the Heart dataset. While traditional models suffered significant performance degradation as more noise was added, FeatLLM remained robust. The analysis showed that rules based on noisy columns accounted for only 1-2% of the total rules generated, confirming that the prior knowledge embedded in the LLM effectively filters out irrelevant data and focuses on the criteria that truly matter for the task.

Experimental Results and Discussion

# Dataset Diversity

To rigorously evaluate the effectiveness of the \textsf{FeatLLM} framework, the researchers conducted experiments across a diverse collection of 13 different tabular datasets. These datasets span various domains and were selected to represent different classification tasks, including both binary and multi-class problems. The diversity of the data is crucial because it tests the model's ability to generalize across different types of information, from medical records to financial data and synthetic configurations.

The evaluation included several classic datasets, such as Adult, Bank, Blood, Car, Communities, Credit-g, Diabetes, Heart, and Myocardial. These datasets are well-established in the machine learning community and provide a standard benchmark for comparing new methods against existing ones. For example, the Heart and Myocardial datasets are particularly relevant for healthcare applications, while the Adult and Bank datasets are common in financial and demographic modeling. Notably, some of these datasets, like Communities and Myocardial, contain over 100 attributes, which poses a significant challenge for Large Language Models (LLMs) due to the limited context windows of their input prompts.

In addition to classic datasets, the study incorporated more recent and synthetic datasets to ensure the model was not simply "memorizing" answers from its pre-training data. This included Cultivars and NHANES, which were added to the UCI Machine Learning Repository after September 2023, meaning they were not part of the pre-training corpus for the GPT-3.5 API used in the study. Furthermore, the researchers included synthetic datasets like Sequence-type and Solution-mix. Because these were artificially generated, they ensure that the LLM cannot rely on prior knowledge of specific records, thereby testing the model's true ability to perform feature engineering and reasoning on the fly.

# Comparative Analysis

The performance of \textsf{FeatLLM} was compared against a wide array of baselines to establish its standing in the field. These baselines were categorized into three main groups: traditional tabular learning methods, methods utilizing unlabeled data, and current LLM-based approaches. Traditional methods included Logistic Regression (LogReg), XGBoost, and RandomForest. These models serve as the standard for many industrial applications because of their efficiency and reliability.

The study also compared \textsf{FeatLLM} against advanced techniques that leverage unlabeled data, such as SCARF, STUNT, and TabPFN. These models often perform well by using large quantities of unlabeled data to provide inductive biases. However, the researchers noted that obtaining large amounts of unlabeled data can be infeasible in many real-world scenarios. Furthermore, while some of these models showed improvements over traditional baselines, their overall gains were not always substantial compared to the performance achieved by \textsf{FeatLLM} in low-shot regimes.

When compared to other LLM-based methods like In-context learning, TABLET, and TabLLM, \textsf{FeatLLM} demonstrated significant advantages. While other LLM methods often struggled to perform inference on datasets with a large number of features, \textsf{FeatLLM} remained robust due to its use of bagging and ensemble techniques. A critical finding in this comparison was the trade-off between accuracy and computational cost. Most LLM-based approaches require passing every single sample through the LLM during inference, making them computationally expensive and slow. In contrast, \textsf{FeatLLM} only uses the LLM to generate features during the training/discovery phase; at inference time, it uses a simple, low-complexity model, resulting in inference speeds comparable to traditional machine learning methods. Finally, \textsf{FeatLLM} demonstrated extreme data efficiency, achieving results with only 4 shots that were comparable to traditional models requiring 32 shots.

# Ablation Studies

Ablation studies are performed to understand which specific components of a framework contribute most to its success. The researchers systematically removed different parts of the \textsf{FeatLLM} pipeline to measure the resulting impact on the Area Under the Receiver Operating Characteristic (AUC) score. Four major components were tested: weight tuning, ensembling, feature descriptions, and the multi-step reasoning process.

The results showed that every component contributed positively to the model's performance, as removing any of them led to a degradation in AUC. Interestingly, the importance of "weight tuning"—the process of learning the significance of the rules using a linear model—increased as the number of training shots increased. This suggests that when more data is available, the model becomes better at accurately estimating which rules are most important for the final prediction. Conversely, "feature descriptions" and the "reasoning" steps were most critical when the number of shots was very small. This indicates that the model's ability to utilize its internal prior knowledge is the primary driver of success in extreme low-shot scenarios.

The study also explored the impact of hyperparameters, specifically the number of ensembles and the number of rules extracted per class. Performance improved as the number of ensembles increased, but these gains began to converge after reaching 20 ensembles. Regarding the number of rules, the researchers found that 10 rules per class provided the best balance. Too few rules could lead to underfitting, while too many rules could lead to overfitting in a low-shot regime and also create prompts that were too large for the LLM to process effectively.

# Rule Quality Analysis

To understand the underlying mechanics of \textsf{FeatLLM}, the researchers analyzed the quality of the rules generated by the LLM. They measured the informativeness of these features by calculating the average AUROC between the new binary features and the actual target labels. The results confirmed that the majority of the rules created by the LLM were highly relevant to the task, with many achieving an AUROC higher than 0.5 before any weight tuning even took place.

The framework also includes an automated filtering mechanism. During the weight tuning phase, the linear model assigns weights to each rule. The researchers observed that rules with little relevance to the actual data were assigned very low weights. By setting a threshold of 0.1, the model automatically filtered out these uninformative rules, keeping only the most predictive features. This demonstrates that the framework is capable of self-correcting by identifying and discarding noisy rules generated by the LLM.

One of the most significant tests of rule quality was the analysis of spurious correlations. The researchers added irrelevant columns from other datasets to the Heart dataset to see if the model would mistakenly learn from them. \textsf{FeatLLM} showed the least amount of performance degradation compared to all other baselines. This is attributed to the "reasoning instruction" in the prompt, which forces the LLM to first identify the causal relationship between the task and the features based on general knowledge. Because of this structured reasoning, only 1-2% of the extracted rules were based on the noisy, irrelevant columns. However, the researchers did note a caveat: if the added columns were closely related to the target task, the LLM could still potentially learn spurious correlations or misunderstand causal relationships.

# Broader Impact and Ethical Considerations

The research concludes by discussing the broader implications of \textsf{FeatLLM} in real-world applications and the ethical considerations surrounding the use of Large Language Models in data science. On the positive side, \textsf{FeatLLM} provides a significant advancement in data efficiency. By leveraging the rich prior knowledge embedded in LLMs, the framework helps mitigate the problem of overfitting that occurs when there are very few labeled samples. This is particularly valuable in industries like finance and healthcare, where collecting and labeling data can be extremely expensive or difficult due to privacy and human costs.

However, the use of LLM prior knowledge introduces a unique set of ethical challenges. Because \textsf{FeatLLM} relies on the internal "common sense" and knowledge of the LLM to engineer features, any societal biases or misinformation present in the LLM's training data could be directly encoded into the model's rules. In some cases, these biases might even dominate the predictions, potentially overriding the actual evidence found in the small number of labeled samples provided. The researchers emphasize that as these models are adopted in critical fields, it is essential to analyze and mitigate the impact of the societal biases embedded within the LLM's prior knowledge to ensure fair and accurate outcomes.
