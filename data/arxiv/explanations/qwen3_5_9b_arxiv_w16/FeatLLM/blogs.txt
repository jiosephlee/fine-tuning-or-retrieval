# Stop Paying Per-Category Prediction: How LLMs Became Our 'Smartest' Data Analysts

In the world of tabular data, Large Language Models (LLMs) are typically treated as expensive calculators. Traditional approaches often require sending every single data point—say, a customer's loan application or a patient's medical record—to an LLM just to make a prediction. While this method can unlock powerful reasoning capabilities, it comes with a prohibitive cost: if you have one million rows of data, you need one million API calls. This is unaffordable for most real-world applications. Enter \textsf{FeatLLM}, a novel framework that flips the script by treating the LLM not as a frontend calculator, but as a brilliant backend feature engineer.

The core insight behind \textsf{FeatLLM} is to separate the heavy lifting from the final decision. Instead of asking the LLM to classify each sample individually during inference, the model is prompted once to extract high-quality decision rules based on prior knowledge and few-shot examples. Think of the LLM as an analyst who reviews a small set of training data and writes down a clear list of guidelines, such as "If age is greater than 60 and income is low, classify as high risk." Once these natural language rules are generated, they are automatically converted into binary features. At this stage, the expensive LLM is no longer involved in the prediction loop.

This architectural shift solves three major bottlenecks found in existing methods. First, it eliminates per-sample inference costs entirely; after the initial setup to generate features, predictions are made using simple linear models that run almost instantaneously on standard hardware. Second, it bypasses fine-tuning requirements. Many previous LLM-based tabular methods require parameter-efficient tuning or full fine-tuning on specific datasets, which is impossible if you only have API access to proprietary models like OpenAI's GPT-4 or Google's PaLM. \textsf{FeatLLM} relies purely on in-context learning, meaning it needs only API access without needing any training codebases or adjustable weights for the LLM itself. Finally, it overcomes prompt size limitations. By processing data in batches through an ensemble process known as bagging, the framework can handle datasets with hundreds or even thousands of columns without overflowing the context window or degrading performance.

The mechanism involves two distinct phases guided by structured prompts. In the first phase, the system instructs the LLM to act as an expert domain analyst. It asks the model to first infer causal relationships between features and targets based on general knowledge before applying specific examples from a few shots. This two-step reasoning helps filter out irrelevant noise and prevents spurious correlations. In the second phase, the LLM deduces specific rules for each class and formats them strictly for programmatic parsing. A secondary prompt then translates these text-based rules into executable Python code using `exec()`, which generates new binary features for every sample in your dataset indicating whether that sample satisfies each rule.

Once these new binary features are created for all your data points, a lightweight linear model takes over during inference. The probability of a class is calculated via a weighted sum of these binary features:
$$
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i
$$
Here, $\mathbf{w}_k$ represents trainable weights that indicate how important each rule is for predicting class $k$, and $\mathbf{z}_k^i$ is a vector where each element indicates if sample $i$ satisfies that specific rule for class $k$. By projecting weights into a positive subspace with $\max(\cdot)$, we ensure that satisfying more rules never decreases the likelihood of a class being predicted like this:
$$
\mathbf{p}^i = \text{Softmax}({[\text{logit}_{1}^i, ..., \text{logit}_{c}^i]})
$$
To further enhance robustness and accuracy in low-shot regimes (where you might only have 4 to 8 training examples), \textsf{FeatLLM} employs an ensemble strategy called bagging rather than relying on extrapolating form from training samples or summing up binary features directly. # Less is More:leveraging LLMs to Solve Tabular Problems with Just a Few Examples

Few-shot learning—the ability to make accurate predictions from a tiny dataset—has long been a bottleneck in machine learning, particularly when dealing with structured tabular data like financial records or medical logs. Traditional methods often fail because they struggle to generalize from such limited examples. However, recent research suggests that Large Language Models (LLMs), which are exceptional at reasoning with natural language, might hold the key to unlocking this potential. A new framework called FeatLLM demonstrates how combining the commonsense reasoning of LLMs with simple classical algorithms can yield high-performance models that require as few as four labeled examples.

The core challenge with tabular data is that it often contains dozens or even hundreds of features, making it difficult for an algorithm to discern which columns are actually predictive without a massive amount of training data. Most current LLM-based approaches attempt to solve this by feeding the entire data table into the model for every single prediction. While effective, this method is computationally expensive and slow at inference time. FeatLLM flips this paradigm entirely. Instead of using the LLM as the final predictor, it treats the LLM as a "feature engineer." The model uses its vast prior knowledge to decipher the logic behind the data and generates explicit rules, which are then translated into new binary features used by a lightweight linear model. This shift allows the system to bypass expensive LLM calls during final prediction while still leveraging the strategic insights provided by the language model.

To achieve these results, FeatLLM employs a structured two-step reasoning process designed to mimic how an expert human would analyze a problem. The first step focuses on abstracting prior knowledge without looking at specific data samples yet. The LLM is prompted to identify general causal relationships and tendencies between features based on domain常识，essentially asking why certain conditions lead to specific outcomes. By separating this conceptual understanding from the raw data, the framework prevents the model from latching onto spurious correlations that might exist in small datasets but do not represent true patterns. In the second step, the system combines these inferred causal priorities with actual few-shot examples to derive concrete decision rules for each class label.

Once these logical rules are generated, they undergo a critical transformation into machine-readable features that can be rapidly processed. Since language models naturally express conditions in ways like "greater than" rather than strict operators like `>`, a parsing mechanism aligns these natural language descriptions with executable code snippets written in Python. These snippets iteratively scan the dataset, converting every row into binary indicators (0 or 1) showing whether it satisfies a specific rule generated by the LLM for each target class. Finally, these new binary features feed into a simple linear regression model trained via cross-entropy loss. This lightweight component learns only the relative importance of each extracted rule using just a few samples, completing the inference pipeline without further consultation of any large AI model.

# Cracking the Context Window Wall: How Bagging and Ensembles Save Mayhem with Huge Datasets

One of the most persistent bottlenecks in applying Large Language Models (LLMs) to real-world data is the context window limit. In the realm of tabular learning, this limitation becomes particularly punishing when datasets contain hundreds of features or columns. Standard approaches often require serializing the entire table into a single prompt, which not only risks hitting token limits but also degrades performance due to information dilution. Recent research introduces an elegant solution called \textsf{FeatLLM}, which transforms the context window constraint from a hard stop into a manageable factor through a clever combination of feature engineering and ensemble learning.

At its core, \textsf{FeatLLM} rethinks the role of an LLM in predictive tasks. Instead of asking the model to process every row and column directly for each prediction—a computationally expensive process that also consumes precious token budget—the framework leverages the LLM only during an initial feature engineering phase. The model is tasked with deriving "rules" based on prior knowledge and a small set of few-shot examples. These rules are essentially logical conditions that describe how specific feature values relate to the target class. Once these natural language rules are extracted, they are converted into executable code to generate simplified binary features for the training data.

The breakthrough comes in how \textsf{FeatLLM} handles datasets with too many columns for a single prompt. The authors employ a strategy inspired by standard machine learning bagging techniques. Rather than attempting to feed all hundred or more features into one massive query, the system randomly selects smaller subsets of features for each trial run. This ensures that every LLM query stays well within safe token limits while still focusing on relevant parts of the data schema. By treating this unpredictability as an asset rather than a liability, \textsf{FeatLLM} creates a diverse pool of weak learners; some trials might miss certain features that others catch, leading to a collectively robust understanding of the data relationships when aggregated later.

The mathematical formulation behind this robustness involves generating multiple sets of weights through repeated trials. For each trial $t$, given a selected subset of features and instances, an LLM generates rules which are then parsed into binary features $\mathbf{z}_k^i$. A simple linear model is trained on these generated features to learn importance weights $\mathbf{w}_k[t]$. The final probability prediction is derived by averaging the probabilities generated across $T$ different trials:
$$
\mathbf{p}^i = \text{Avg}_{t=1}^T \left( \text{Softmax}([\max(\mathbf{w}_k[t], 0) \cdot \mathbf{z}_k^i]_k) \right).
$$
This averaging process acts as a noise filter. Incorrect rules generated due to incomplete feature coverage in specific trials are counterbalanced by correct rules from other trials where those relevant features were included in the prompt subset. This mechanism effectively mitigates the impact of incomplete feature coverage without requiring access to all data at once or inflating prompt sizes beyond API limits.

Beyond just solving technical constraints, this approach offers significant practical advantages over end-to-end LLM inference methods that query the API for every sample prediction. Traditional methods often incur massive latency costs during inference because they cannot unload their reasoning burden onto traditional models. In contrast, \textsf{FeatLLM} performs its heavy lifting—reasoning about complex interactions—only once during training time via batched API calls and simpler downstream linear models for fast inference at test time. The framework achieves this high performance on challenging datasets with over 100 attributes by simply running enough ensemble trials to ensure statistical convergence, typically stabilizing performance gains around 20 ensemble members before diminishing returns set in.

Ultimately, \textsf{FeatLLM} demonstrates that we do not need larger context windows to solve complex tabular problems; we can instead use smarter sampling strategies compatible with existing model architectures. By combining structured reasoning instructions that guide the LLM toward causal relationships with statistical ensemble methods like bagging, this approach pushes past the standard limitations of prompt-based engineering, making high-quality few-shot learning accessible even for massive datasets that would otherwise timeout or error out in standard implementations.
