\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does FeatLLM handle the parsing ambiguity of natural language rules vs. strict programmatic code?
Question:
In Section 3.2 ('Parsing rules for feature generation'), the paper mentions that generated LLM rules can contain noisy syntactic changes (e.g., 'greater than' instead of '$>$'). The authors propose passing these rules, along with function descriptions, back to an LLM to generate Python code for execution.
My confusion is about the reliability of this step. Since the first step already required an LLM call to *generate* the rules, relying on a second LLM call to *translate* those potentially ambiguous natural language rules into executable code seems risky. Are we just pushing the parsing problem up one more layer of stochasticity? How does the model ensure that a rule like 'age > 50' from Step 1 correctly translates to `if age > 50:` in Step 2 without hallucinating syntax or logic errors? Additionally, is there a mechanism to validate that the generated code actually matches the semantic intent of the original rule before execution?
Answer:
The concern regarding whether FeatLLM is simply "pushing the parsing problem to a different layer of stochasticity" touches on a fundamental trade-off in using generative models for code synthesis, and the paper addresses this not by eliminating the second LLM call, but by leveraging it as a robust semantic bridge that transforms noisy predictions into reliable execution.

At its core, the necessity of the second LLM call arises from the fact that while the first stage uses an LLM to extract linguistic rules based on prior knowledge and data patterns, this output is inherently natural language and susceptible to syntactic variations. As the paper explicitly notes in Section 3.2, the LLM might generate rules where mathematical operators like "greater than" ($>$) are replaced with phrases like "greater than," or where operator precedence might be ambiguous in plain text. Attempting to parse this into strict Python code using rigid regular expressions would be brittle; a small deviation in syntax would break the entire parsing pipeline, leading to silent failures or runtime errors. By passing these natural language rules, along with structured function descriptions (input and output signatures), back to an LLM in the second stage, FeatLLM effectively accepts a "noisy" translation request rather than a "syntactically strict" one. The method relies on the intuition that an LLM, being trained on vast corpora of code-literate text, possesses a strong understanding of semantic equivalence; it can recognize that "if age is greater than 50" carries the exact same intent as `if age > 50`, even if the intermediate text representation wasn't perfectly formatted for direct string-to-code conversion. This approach decouples semantic reasoning from syntactic correctness, allowing the model to focus on generating valid executable logic rather than perfecting markdown-style formatting in the first pass.

However, regarding your worry about hallucinated syntax or logic errors, it is important to clarify that FeatLLM does not claim the generated code is perfect upon generation; instead, it employs a probabilistic ensemble strategy where errors are mitigated through redundancy and subsequent mathematical validation. When multiple rules are generated across different ensemble trials due to varying temperatures or shuffled few-shot examples, some will likely contain logical flaws or syntax errors that result in invalid features or incorrect labels during execution. These erroneous features are not discarded immediately but are instead subjected to a learning process using the downstream linear model described in Section 3.2 ("Inferring Class Likelihood via Rules"). In this phase, FeatLLM trains a simple linear model with non-negative weights ($\mathbf{w}_k$) on top of these binary features derived from the generated rules. The cross-entropy loss function acts as a powerful validator: if a set of rules leads to incorrect predictions compared to the ground-truth labels in the few-shot training set, the optimization process learns weights close to zero for those specific rules (or effectively filters them out), whereas semantically correct and useful rules will accumulate higher weights because they improve prediction accuracy.

Furthermore, by projecting these weights into a positive subspace ($\max(\mathbf{w}_k, 0)$), the framework ensures that only features contributing positively to class likelihood are utilized in final inference. This mechanism answers your question about validation before execution: while individual rule executions might be flawed or noisy, their impact is statistically validated against actual task outcomes during training. If a rule like 'age > 50' fails to translate correctly or introduces noise that hurts performance during training, and fails consistently across multiple ensemble members due to low-temperature inference variance (which helps enforce self-consistency as mentioned in Related Work implications), those components naturally degrade towards irrelevance via their learned weights rather than relying solely on pre-execution static verification. Thus, rather than risking hallucination at every step without recourse, FeatLLM distributes risk across generation diversity and cures it post-hoc through data-driven weight optimization, ensuring that only the most robust and semantically faithful translations contribute significantly to the final model's predictions.

### What is the theoretical justification for using a linear model with non-negative weights on binary features in FeatLLM?
Question:
In Eq. (2) of Section 3.3, the logit is calculated as $	ext{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$. Here, $\mathbf{z}_k^i$ are binary features indicating if a rule is satisfied.
Why is it necessary to project weights $\mathbf{w}_k$ into a positive subspace (using $\max(\mathbf{w}_k, 0)$)? If a generated rule is actually detrimental to a class (a false positive), wouldn't learning allow $\mathbf{w}_k$ to become negative? By forcing weights to be non-zero only if they are positive, aren't we discarding valid information that a specific rule should *decrease* the probability of a class? I am struggling to connect this specific mathematical constraint with the goal of preventing 'rules generated by LLM do not reduce the likelihood,' and whether this actually prevents overfitting in low-shot regimes or if it acts as a strong prior that might bias results artificially.
Answer:
In the \textsf{FeatLLM} framework, the projection of weights $\mathbf{w}_k$ into a positive subspace via the operation $\max(\mathbf{w}_k, 0)$ is not merely a technical constraint but a deliberate design choice grounded in the specific inductive bias required for few-shot tabular learning with LLM-generated rules.

The core justification lies in the distinct roles assigned to the two stages of the pipeline: rule generation by the LLM versus rule weighting by the linear model. As described in Section 3.3, the LLM acts as a feature engineer that hypothesizes conditions ("If condition X is met, the class is likely") based on prior knowledge and few-shot examples. These hypotheses are then materialized as binary features $\mathbf{z}_k^i$, where a value of $1$ indicates that a specific rule hypothesized for class $k$ is satisfied by the data sample. The subsequent linear model's job is to evaluate whether these independently generated rules are trustworthy indicators of class membership. If an LLM generates a rule intended to identify members of class $k$, but that rule turns out to be spurious or detrimental, allowing the weight $w_k$ to learn a negative value would effectively invert the meaning of that rule: satisfied cases would now increase *lower* the probability of class $k$. This leads to logical incoherence within the probabilistic framework, where satisfying a "rule for class $k$" would actively reduce confidence in belonging to class $k$.

The hard constraint imposed by $\max(\mathbf{w}_k, 0)$ ensures that any non-zero learned weight implies that satisfying a rule for class $k$ strictly increases (or at least maintains) its likelihood. From an optimization perspective, during cross-entropy training on few samples, if a generated rule correlates negatively with the target labels, the gradient simply drives $w_k$ toward zero rather than into negative territory. In this manner, negative correlations are interpreted as "informationless" or "noise." This mechanism serves as a powerful regularizer in low-data regimes; it prevents the model from overfitting to spurious patterns by forcing it to discard rules where an inverse relationship exists or where no clear positive signal can be established.

This design aligns closely with how factual reasoning works in humans and robust machine learning systems: we generally assume that if a diagnostic criterion points toward a disease (a positive rule), evidence supporting that criterion should not lower our belief in the diagnosis. By enforcing non-negative weights, \textsf{FeatLLM} leverages this prior plausibility. It treats any valid evidence provided by an LLM-hypothesized rule as additive support for its respective class, ensuring that ensemble averaging across multiple trials (Section 3.3) compounds correct signals rather than inadvertently canceling them out through destructive interference from negative weights. Thus, rather than discarding valid information about decreasing likelihood—which would require negative weights—the approach frames such decreases as "lack of support," naturally handled by setting those weights to zero or training them toward zero if no positive correlation exists with limited data.

### How does FeatLLM exactly balance quality vs. quantity in the 'Reasoning' step described in Eq. (1) of Section 3.1?
Question:
"The proposed approach goes beyond treating LLMs... Instead, we assign them the role of feature engineering... specifically, we introduce a novel in-context learning framework..." The text describes forcing two-step reasoning: first inferring causal relationships using general knowledge without examples, then deriving rules using examples.
The paper states they fixed the number of extracted rules at 10 per class. However, Rule A's confidence might be 99% valid while Rule B's confidence is only 50% valid but still included because we needed to reach '10 rules.'
Does FeatLLM internally rank or score these candidate rules before selecting them to ensure high-quality features? If not simply count-based (which seems plausible given 'no need for model training' claims), how does it distinguish between high-confidence and low-confidence generated rules when constructing the final feature set? Without explicit weighting during generation, aren't we diluting high-quality insights with noisy ones just to meet a quota?
Answer:
The balance between quality and quantity in FeatLLM's reasoning step is not achieved by internally ranking the generated rules before the set of 10 is finalized, but rather through a post-hoc statistical filtering mechanism driven by the linear model trained on the few-shot data.

As detailed in Section 3.1, the prompt explicitly instructs the Large Language Model to generate a fixed number of 10 rules per class without providing an ordering mechanism based on confidence scores (Section 3.1, "Reasoning instruction"). Consequently, there is no internal prioritization where high-confidence rules displace low-confidence ones within the generation step itself to meet the quota. Instead, the framework accepts all 10 generated rules as binary features, creating a feature vector $\mathbf{z}_k^i$ for each class $k$. The true distinction between high-quality and low-quality rules happens immediately after generation during the training phase described in Equation (1). The authors employ a simple linear model with non-negative weights $\mathbf{w}_k$ fitted via cross-entropy loss to optimize Equation (\ref{eq:infer_prob}). In this process, illustrated in Section 3.2 ("Quality of features generated by FeatLLM"), the learned weights act as an automatic importance filter; rules that are spurious or low confidence result in weights that are driven toward zero or remain negligible after training, whereas robust causal relationships yield higher weights. As noted in the analysis section, if a rule's learned weight falls below a specific threshold (e.g., $0.1$ mentioned in the experiments), it is effectively filtered out of contributing meaningfully to the final prediction. Therefore, FeatLLM trades "low-shot learning" to determine rule value rather than relying on heuristic confidence scores during generation, ensuring that while a noisy rule might be included in the initial $R=10$ set, its impact is mathematically neutralized if it lacks statistical relevance within the provided training examples.

### Does Ensembling in FeatLLM imply O(k*N) API calls or just O(k) calls where k is shots?
Question:
"Finally, we repeatedly execute the entire process... averaging... over T trials." The text mentions repeating ensembling T times (default T=20).
Each repetition involves: (1) Constructing a prompt with few-shot data (potentially shuffled for bagging), (2) One LLM call to generate rules for each class, and (3) Training a simple linear model.
The question is: When performing inference on a new sample $x_{new}$ where no weights are involved yet? Wait—inference involves re-running bagging?
The abstract says: "eliminates the need to send queries to the LLM for each sample at inference time." But Section 3.7 says: "repeatedly execute... predictions via ensemble" and mentions bootstrapping instances for each trial.
If prediction on new data requires running T trials and re-parsing/bagginging for every incoming sample during deployment phase based on *that* sample's subset relevance or just static averaging? If it requires T separate pipeline runs per test sample involving re-parsing logic (even if simple), does it truly eliminate per-sample API calls? Or are all weights pre-calculated offline?
Can someone clarify if any formality violations occur here?
Answer:
In the \textsf{FeatLLM} framework, inferring predictions on new samples requires exactly $T$ evaluations of the downstream linear model (using $T$ distinct sets of weights), but it does **not** require $T$ separate API calls to the LLM for each incoming sample. The total number of LLM API calls remains $O(T)$ regardless of the test set size, effectively decoupling inference latency from real-time LLM costs.

This efficiency stems from the distinct separation between the "feature engineering" phase and the "inference" phase. During the offline training or setup phase, $\textsf{FeatLLM}$ employs an ensemble strategy by repeating the entire process $T$ times (default $T=20$). In each trial, a unique set of rules is generated via a single LLM call—potentially with different random seeds or shuffled few-shot demonstrations—and then parsed into executable code to create a specific set of binary features. A simple linear model (e.g., logistic regression) is subsequently trained on these engineered features using the few-shot data to produce a weight vector $\mathbf{w}[t]$. Crucially, once this trial is complete, both the rule parser and the trained linear model are set aside; no LLM involvement occurs at this stage other than generating these static artifacts.

When predicting on a new sample $\mathbf{x}_{new}$, the system retrieves the pre-generated rule files and their corresponding pre-trained weight vectors $\{\mathbf{w}[1], \dots, \mathbf{w}[T]\}$. For that single sample, the system executes $T$ separate but instantaneous steps: applying each rule set to generate binary features for that sample and computing its probability via a dot product with its respective weight vector. These $T$ probabilities are then averaged to form the final prediction. Because these operations involve only executing stored Python code and simple matrix/vector operations, they occur locally without any network latency. This design directly fulfills the paper's claim in Section 3.7 that it eliminates per-sample queries; if prediction required reparsing rules or re-generating them for every test point downstream, it would indeed incur an $O(N_{test} \times T)$ API cost, but by pre-calculating all ensemble members during setup, \textsf{FeatLLM} reduces inference to purely local computation at $O(1)$ API calls total per deployment cycle (specifically to generate those first $T$ models if not carried off-line).
