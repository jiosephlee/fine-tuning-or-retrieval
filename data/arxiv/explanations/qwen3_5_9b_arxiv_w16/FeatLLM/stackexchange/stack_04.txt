\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Does Ensembling in FeatLLM imply O(k*N) API calls or just O(k) calls where k is shots?
Question:
"Finally, we repeatedly execute the entire process... averaging... over T trials." The text mentions repeating ensembling T times (default T=20).
Each repetition involves: (1) Constructing a prompt with few-shot data (potentially shuffled for bagging), (2) One LLM call to generate rules for each class, and (3) Training a simple linear model.
The question is: When performing inference on a new sample $x_{new}$ where no weights are involved yet? Wait—inference involves re-running bagging?
The abstract says: "eliminates the need to send queries to the LLM for each sample at inference time." But Section 3.7 says: "repeatedly execute... predictions via ensemble" and mentions bootstrapping instances for each trial.
If prediction on new data requires running T trials and re-parsing/bagginging for every incoming sample during deployment phase based on *that* sample's subset relevance or just static averaging? If it requires T separate pipeline runs per test sample involving re-parsing logic (even if simple), does it truly eliminate per-sample API calls? Or are all weights pre-calculated offline?
Can someone clarify if any formality violations occur here?
Answer:
In the \textsf{FeatLLM} framework, inferring predictions on new samples requires exactly $T$ evaluations of the downstream linear model (using $T$ distinct sets of weights), but it does **not** require $T$ separate API calls to the LLM for each incoming sample. The total number of LLM API calls remains $O(T)$ regardless of the test set size, effectively decoupling inference latency from real-time LLM costs.

This efficiency stems from the distinct separation between the "feature engineering" phase and the "inference" phase. During the offline training or setup phase, $\textsf{FeatLLM}$ employs an ensemble strategy by repeating the entire process $T$ times (default $T=20$). In each trial, a unique set of rules is generated via a single LLM call—potentially with different random seeds or shuffled few-shot demonstrations—and then parsed into executable code to create a specific set of binary features. A simple linear model (e.g., logistic regression) is subsequently trained on these engineered features using the few-shot data to produce a weight vector $\mathbf{w}[t]$. Crucially, once this trial is complete, both the rule parser and the trained linear model are set aside; no LLM involvement occurs at this stage other than generating these static artifacts.

When predicting on a new sample $\mathbf{x}_{new}$, the system retrieves the pre-generated rule files and their corresponding pre-trained weight vectors $\{\mathbf{w}[1], \dots, \mathbf{w}[T]\}$. For that single sample, the system executes $T$ separate but instantaneous steps: applying each rule set to generate binary features for that sample and computing its probability via a dot product with its respective weight vector. These $T$ probabilities are then averaged to form the final prediction. Because these operations involve only executing stored Python code and simple matrix/vector operations, they occur locally without any network latency. This design directly fulfills the paper's claim in Section 3.7 that it eliminates per-sample queries; if prediction required reparsing rules or re-generating them for every test point downstream, it would indeed incur an $O(N_{test} \times T)$ API cost, but by pre-calculating all ensemble members during setup, \textsf{FeatLLM} reduces inference to purely local computation at $O(1)$ API calls total per deployment cycle (specifically to generate those first $T$ models if not carried off-line).
