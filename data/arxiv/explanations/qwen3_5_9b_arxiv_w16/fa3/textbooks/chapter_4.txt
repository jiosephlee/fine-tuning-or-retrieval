# The Throughput Gap: Why Softmax Limits Performance on Tensor Cores

To understand the primary design motivation behind overlapping GEMM (General Matrix Multiplication) and softmax operations in FlashAttention-3, one must first quantify the performance disparity between these two computational primitives on modern hardware accelerators, specifically the NVIDIA Hopper architecture. In large language model inference, the self-attention mechanism is dominated by matrix multiplications involving queries and keys, followed by a row-wise softmax operation to normalize the attention scores. While Tensor Cores are engineered to deliver immense throughput for floating-point matrix operations, they are not uniform in their ability to handle all types of workloads. As detailed in the FlashAttention paper, there exists a significant bottleneck specifically when processing low-throughput non-GEMM operations like exponentials and floating-point multiply-adds required for softmax normalization.

On an H100 SXM5 GPU, this disparity is substantial. The hardware delivers approximately 989 TFLOPS of FP16 matrix multiplication throughput. In stark contrast, operations such as the exponential function (essential for converting logits to probabilities) are handled by separate multi-function units that offer vastly lower throughput; for instance, special functions top out at roughly 3.9 TFLOPS. If one were to execute these operations sequentially within a single threadblock or warp without optimization, the specialized compute unit spends a disproportionate amount of time idling while waiting for data or performing simple logic that clog its pipeline. The literature indicates a scenario where exponential calculations alone can consume up to 50% of the available cycle time simply due to their low throughput relative to matmul operations. This situation is exacerbated in FP8 precision modes, where matmul throughput doubles while the exponential throughput remains static at 3.9 TFLOPS, thereby increasing the relative time lost to softmax computation.

Intuitively, this creates a resource utilization problem where the powerful Matrix Processing Engine (Tensor Cores) cannot remain saturated because it must wait for the much slower scalar or specialized function units to finish their portion of the work within an iteration of the attention loop. Even if we consider that softmax might be performed by different hardware units than matmuls in some architectures, ad-hoc software scheduling often fails to overlap these effectively because of strict sequential dependencies within standard algorithmic implementations. The result is that previous implementations like FlashAttention-2 achieve poor utilization rates on newer architectures, hitting only about 35% utilization on H100 compared to 80-90% for optimized GEMM kernels like cuBLAS. This inefficiency stems from treating GEMM and softmax as atomic steps executed one after another in each block iteration rather than recognizing them as components of a larger pipeline that can be decoupled and overlapped across different parts of the execution flow or different iterations of the loop itself. By acknowledging this specific bottleneck—where high-throughput units are starved because low-throughput units cannot keep up—the FlashAttention-3 authors identify an opportunity to hide latency by ensuring that when one part of the work (softmax) is running on slower units, another part (the next stage of GEMM) is simultaneously running on the faster Tensor Cores in a different warpgroup or pipeline stage.

# Breaking Sequential Dependencies within a Block Iteration

The fundamental challenge in achieving overlap between GEMM and softmax arises from inherent sequential dependencies within a single iteration of the main loop over key/value blocks in standard attention algorithms. In the conventional approach depicted in algorithms prior to FlashAttention-3's innovations, the computation proceeds strictly linearly: first, compute $Q_i K_j^\top$ using WGMMA; second, compute row-wise maximums and then exponentials for normalization; third, store these normalized probabilities; and finally, perform $P_i^{(j)} V_j$ multiplying these probabilities with the values fetched from memory or registers. Each step $j$ requires immediate completion of these three stages before proceeding to step $j+1$. Specifically, Line \ref{code-first_wgmma} computes $\mathbf{S}_{\mathrm{next}} = \mathbf{Q}_i \mathbf{K}_{j}^T$, but Line \ref{code:softmax} (which computes $\tilde{\mathbf{P}}_{\mathrm{next}}$ via exp functions) cannot begin until $\mathbf{S}_{\mathrm{next}}$ is fully computed and accessible. Furthermore, Line \ref{code-second_wgmma}, which updates $\mathbf{O}_i$ using $\tilde{\mathbf{P}}_{\mathrm{cur}}$, relies entirely on having completed Line \ref{code:softmax} for index $j$. These hard dependencies serialize execution: $GEMM(j) \rightarrow Softmax(j) \rightarrow GEMM2(j)$ must finish before any work can proceed for $j+1$.

This serialization prevents any meaningful overlap within a single iteration because there is no "idle" state or side channel available once a block $j$ has started processing but before it finishes; all available resources are dedicated to completing this specific block's prerequisites before unrelated blocks can make progress on their own prerequisites or alternative computations (like updating outputs). To break this bottleneck and improve overall throughput per kernel invocation time rather than just raw FLOPs per clock cycle utilized at any single instant, we must look beyond overlapping operations *within* block $j$ and instead look at overlapping operations *across* block iterations $j$.

The solution proposed involves restructuring the control flow so that multiple instances of these blocks coexist simultaneously but float through different states of readiness and execution dates staggered across iterations.
