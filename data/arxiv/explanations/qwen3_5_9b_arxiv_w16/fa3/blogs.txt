# Unlocking the H100: How Asynchrony is Revolutionizing LLM Inference Speed

For developers working with large language models (LLMs), the self-attention mechanism in Transformer architectures has long been the primary bottleneck. This quadratic scaling issue becomes increasingly severe as we attempt to model longer contexts and high-resolution multimodal data. While optimizations like FlashAttention-2 made significant strides by minimizing memory reads and writes, profiling on NVIDIA's newest Hopper architecture (the H100) revealed a critical gap: the algorithm was only utilizing about 35% of the available Tensor Core throughput. Even optimized vendor libraries were struggling to reach full potential. Our recent research, FlashAttention-3, addresses this by fundamentally redesigning how work is scheduled on the GPU to exploit hardware asynchrony, effectively unlocking speedups of 1.5 to 2.0x over previous versions.

The core driver of this performance leap is the utilization of asynchrony in the Hopper architecture, specifically the Tensor Memory Accelerator (TMA) and asynchronous Tensor Cores. In traditional CUDA programming, operations are often executed sequentially; a computation unit waits for data to arrive from memory before it can begin its math. This waiting periods, or latency, wastes valuable compute cycles. Modern GPUs solve this through specialization, dedicating some hardware units solely to data movement and others solely to computation. FlashAttention-3 leverages this by implementing a "warp-specialization" strategy where threads within a processing block are permanently assigned roles as either producers or consumers. Producer warps focus exclusively on issuing asynchronous loads via TMA from global memory to shared memory, while consumer warps dedicate their cycles entirely to matrix multiplication using WGMMA instructions. Because these units operate independently, producers do not stall consumers waiting for data flips, allowing the algorithm to hide memory latency behind compute overhead and significantly increase throughput.

However, simply splitting threads into producers and consumers was not enough to reach peak efficiency on the H100. We identified that even within a single consumer warp group, there were unused gaps between heavy matrix multiplication tasks and lighter softmax operations. Since exponential functions required for normalization have much lower throughput than GEMM operations—consuming roughly half of the cycle time in FP16 modes—we needed a way to overlap them without serializing execution. Our solution involves an overlapping pipeline that restructures the algorithm into two concurrent stages within a single warp group.

This technique creates what we call "ping-pong scheduling." In this setup, we use synchronization barriers to force GEMM operations in one stage of our pipeline to complete before they are consumed by another stage performing softmax calculations. Essentially, while Warpgroup A is crunching matrix numbers for iteration $j$, Warpgroup B is calculating softmax scores for iteration $j+1$ using data from Warpgroup A's previous work. Once Warpgroup A finishes its GEMM task for current iteration $j$, it immediately switches roles to perform softmax while Warpgroup B takes over matrix multiplication for iteration $j+1$. This dynamic swapping ensures that there is almost no idle time; when one part of the team is waiting for data preparation, it can simultaneously perform floating-point math on finished blocks. Empirical results show this alone boosted peak performance from approximately 570 TFLOPS to over 640 TFLOPS without addressing Low-Precision features (LPF).

The combination of producer-consumer specialization and intra-group pipelining allows FlashAttention-3 to achieve roughly 75% utilization on H100 GPUs in FP16 precision, a massive improvement over the 35% seen in FlashAttention-2 and competitive with state-of-the-art GEMM kernels that reach 80-90%. We also validated that these architectural changes do not compromise numerical accuracy; even when running in lower precision modes like FP8 with block quantization and incoherent processing techniques added posteriorly, our method retains high fidelity with significantly reduced numerical error compared to standard baselines. By mastering the interplay between asynchronous data movement and compute-heavy logic, we demonstrate that tuning hardware capabilities can be just as impactful as refining algorithmic complexity when scaling LLMs toward longer contexts and higher resolutions.



# Precision vs. Performance: Getting Away with FP8 for Massive Contexts

In the race to extend the context windows of large language models, attention mechanisms remain the primary computational bottleneck. While previous optimizations like FlashAttention-2 pushed boundaries by minimizing memory reads and writes, a new opportunity has emerged on NVIDIA's Hopper architecture: the ability to leverage FP8 low-precision arithmetic. However, simply switching from FP16 to FP8 often leads to a sharp degradation in accuracy, particularly when dealing with massive matrices containing outlier values common in deep learning. Our paper, FlashAttention-3, tackles this trade-off head-on by introducing two novel mathematical techniques—block quantization and incoherent processing—that allow us to achieve near 1.2 PFLOPs/s throughput while reducing numerical error by a factor of 2.6 compared to standard baseline methods.

The core challenge with using FP8 lies in the extreme loss of precision compared to standard floating-point formats. FP8 uses only three bits for the mantissa and four for the exponent, making it highly susceptible to quantization errors. This effect is exacerbated by "outlier features" in transformer activations, where a small percentage of values have magnitudes significantly larger than the rest. Standard implementations typically rely on per-tensor quantization, applying a single scaling factor to an entire tensor (the Q, K, or V matrix). This approach fails when outliers exist because the scale required to capture those extreme values forces all smaller, meaningful values into a very coarse granularity, resulting in massive rounding errors during the matrix multiplications.

To combat this, we introduce **block quantization**. Unlike per-tensor scaling which views the entire input as one unit, our approach splits the query ($\mathbf{Q}$), key ($\mathbf{K}$), and value ($\mathbf{V}$) matrices into smaller blocks and assigns a unique scaling factor to each block before processing them into FP8 format. Because FlashAttention-3 is built upon a block-wise tiling strategy that moves through data sequentially anyway, we can fuse this pre-processing step with existing operations like rotary embeddings without adding any computational overhead or extra memory passes. By ensuring that no single block is dominated by an outlier that would skew its scale away from the majority of its elements, we maintain a much healthier distribution of precision across the entire tensor.

Furthermore, even with block quantization, some outliers may persist at the block level or arise from complex interactions within specific heads. To address this residual error, we employ **incoherent processing**. This technique leverages linear algebra properties to mathematically preserve the attention output while altering its internal representation. # The Softmax Bottleneck: Reducing the Math Between Matrix Multiplications

Attention is the engine powering modern large language models, yet it remains the primary computational bottleneck. As sequence lengths grow, the quadratic scaling of self-attention scores puts immense pressure on hardware, particularly GPUs. While previous optimizations like FlashAttention-2 significantly reduced memory I/O by fusing operations into a single kernel, they still operated under a largely synchronous model. On the latest NVIDIA Hopper architecture (such as the H100 GPU), this approach only achieved about 35% utilization of theoretical peak performance because it failed to fully exploit hardware asynchrony. FlashAttention-3 addresses this by fundamentally rethinking how slow non-matrix operations interact with fast matrix multiplications, specifically by overlapping them in a two-stage pipeline to squeeze out a 1.5x to 2.0x speedup.

### The Speed Mismatch Problem
To understand why standard attention implementations were stalling on modern GPUs, we must look at the nature of the operations involved. The attention mechanism fundamentally relies on repeated matrix multiplications (GEMM) sandwiched around a softmax function. The GEMM operation, which computes dot products between queries and keys, is extremely bandwidth-efficient and can leverage specialized Tensor Cores to deliver tens of teraFLOPS per second.

In contrast, the softmax function requires calculating exponentials and performing reductions that are computationally expensive relative to matrix multiplication but lack dedicated high-throughput hardware units on the GPU. On an H100 SXM5 GPU running in FP16 precision, while matrix multiplication delivers roughly 989 TFLOPS for FP16 operations, units designed for special functions like the exponential only achieve approximately 3.9 TFLOPS. This creates a massive disparity: there are roughly 512 times more floating-point operations required for matmul than for exponentiation in a typical attention kernel. However, because the exponential unit is so much slower in terms of throughput (about 256 times lower), the exponential calculation ends up consuming half of the available cycles just waiting for data or processing at a sluggish pace compared to the matmul stages.

In traditional sequential implementations or even earlier versions of FlashAttention, these operations were serialized within a single warpgroup iteration. This meant that when the Tensor Core was ready to compute another block of GEMM results, it would have to wait for a slower arithmetic logic unit to finish computing an exponential value for softmax normalization before proceeding. Consequently, the powerful Tensor Cores sat idle half the time waiting on these "slow" math problems, leading to poor overall utilization ratios compared to optimized GEMM libraries like cuBLAS which can reach over 80% utilization.
