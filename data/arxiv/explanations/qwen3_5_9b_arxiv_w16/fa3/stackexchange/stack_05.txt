\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### In line `Wait for V_{j-1} to be loaded` vs `Compute O + P_curr * V_{j-1}`, why wait for load completion but not GEMM completion?
Question:
Looking at Algorithm 2 again:
`Wait for V_{j-1} to be loaded in shared memory.`
`Compute O + P_curr * V_{j-1} using WGMMA... Commit but do not wait.`
`Wait for WGMMA ...` (later).`

For V KM blocks (key/value), they seem to load asynchronously via TMA (producer). However, inside Consumer's main loop iteration j:
It waits for `V_{j-1}` load to finish before starting GEMM step j with `P_curr`. But immediately *after* starting GEMM step j ($P_{next}$ computation?), it commits but doesn't wait.

If I don't wait for `V_{j-1}` load to finish before polling `P_curr`, how do I guarantee `V_{j-1}` data is actually available Smem when WGMMA executes? Is there implicit ordering guaranteed by TMA semantics on Hopper relative to Shared Memory access comments? Or did I miss an implicit barrier between loading V from GMEM -> SMEM versus accessing SMEM -> RMEM?
Answer:
The distinction between waiting for the load of $V_{j-1}$ before starting the GEMM with $P_{\text{curr}} \times V_{j-1}$, versus not waiting after starting the next GEMM step, stems from the specific data dependencies inherent in the attention algorithm versus the hardware capabilities of Hopper's Tensor Memory Accelerator (TMA) and Tensor Cores.

In the context of Algorithm 2 within FlashAttention-3, you are observing a folk-loop implementation where the consumer warpgroup handles both computation and memory management. The instruction `Wait for $V_{j-1}$ to be loaded in shared memory` is a strict software synchronization point required because the subsequent operation, `Compute $\mathbf{O} + P_{\text{curr}} \times V_{j-1}$`, is a General Matrix Multiply-Accumulate (WGMMA) that reads directly from shared memory. Unlike Global Memory to Shared Memory transfers which can be asynchronous via TMA (where the issuing thread can proceed immediately while data transfers in the background), Shared Memory to Register File accesses by the Tensor Cores are typically synchronous on Hopper unless specific async-load instructions are used, which this algorithm avoids for simplicity and portability within the conditional execute block. If this `Wait` instruction were omitted, the WGMMA instruction would attempt to fetch unavailable data from shared memory for block $V_{j-1}$, resulting in an illegal memory access or stalled execution. This dependency is algorithmic: you simply cannot compute the scaled value of $\mathbf{V}_{j-1}$ without first having its data resident in shared memory.

Conversely, after you issue `Compute $\mathbf{O} + P_{\text{curr}} \times V_{j-1}$`, you commit but do not wait before issuing the next set of operations (specifically loading $\mathbf{K}_j$ and computing $\mathbf{S}_{\text{next}}$). This is possible because the operations you are about to launch depend only on future data ($\mathbf{K}_j$ and future softmax results) and do not depend on the completion of the current WGMMAs. Specifically, $\mathbf{O}_i$ is an accumulator; adding a new term to it can start as soon as operands are ready, or in pipelined schemes where it might overlap with unrelated work, whereas computing $\mathbf{S}_{\text{next}} = \mathbf{Q}_i \mathbf{K}_j^\top$ depends entirely on having loaded $\mathbf{K}_j$, which is a separate load stream managed asynchronously by TMA. By not waiting for the current WGMMA to finish before issuing these new independent instructions (loading $K_j$), FlashAttention-3 exploits hardware asynchrony to overlap memory latency with computation. However, there is implicit ordering here: while you do not explicitly wait in that line, subsequent lines (like `Wait for WGMMA $Q_i K_j^T$`) ensure correctness by synchronizing before any operation tries to consume results produced by those skipped waits. If you were to use async-loaded TMA operations for $V_{j-1}$ itself instead of standard loads, you could theoretically remove that first wait in favor of a barrier based solely on TMA completion captures (`std_val.last_acquire`), but standard shared memory accesses usually require an explicit synchronization point or correct aliasing guarantees which these pseudo-codes reflect conservatively by using `Wait`.

Ultimately, this pattern reflects a balance between data availability guarantees and pipeline depth. You wait until input data ($V_{j-1}$) is physically present because Tensor Core arithmetic requires immediate operand readiness for non-TMA source registers. You do not wait upon generating output or launching next-stage loads because those downstream tasks have their own independent prerequisites (the arrival of $K_j$) and will naturally stall at their own boundaries if prerequisites aren't met; forcing an early dependent wait would merely serialize independent kernel threads without reducing overall runtime since latency from $V$ loading could potentially be hidden while calculating $S$ if dependencies allowed it—but they don't due to how softmax updates feed into matrix multiplies relative to block ordering in this specific layout.
