\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What is the precise memory footprint overhead of exchanging $\mathbf{S}_{\mathrm{cur}}$ to $\mathbf{S}_{\mathrm{next}}$ in each iteration?
Question:
In Algorithm 2 (the 2-stage pipelining algorithm), line `Copy $\mathbf{S}_{\mathrm{next}}$ to $\mathbf{S}_{\mathrm{cur}}$` requires storing an intermediate score tile in registers.
The paper notes in paragraph `Register pressure` that this requires "$B_r \times B_c \times \text{sizeof}(	ext{float})$ per threadblock" resources.
However, standard FlashAttention-2 implementations are extremely optimized for register usage. Does this additional tile explicitly preclude using larger block sizes ($B_r, B_c$)? If I double $B_r$, does my register count explode linearly, potentially causing spilling on H100 which has limits on max registers per CTA?
Specifically, if $B_r=64$ and $B_c=64$, that's 4096 floats ($\approx 16KB$). If a threadblock has multiple threads handling partials of this tile, how do they share these register variables without exceeding $\texttt{smem}$ or total CTA register limits? Does every thread need a full copy of this tile, or is it distributed?
Answer:
The memory footprint overhead for exchanging $\mathbf{S}_{\mathrm{cur}}$ to $\mathbf{S}_{\mathrm{next}}$ in each iteration of the two-stage pipelining algorithm (Algorithm 2) is explicit and local: specifically, it requires $B_r \times B_c \times \text{sizeof}(\text{float})$ registers per threadblock, not global memory. This distinction is critical because the intermediate score tile $\mathbf{S}$ is too large to reside in Shared Memory (SMEM) given that SMEM is already dedicated to holding the key and value tiles ($\mathbf{K}_j, \mathbf{V}_j$) along with the output $\mathbf{O}_i$. Consequently, the authors explicitly state in the "Register pressure" paragraph that this intermediate state must be stored in registers, and the increase in register usage scales linearly with the tile dimensions $B_r$ (query block size) and $B_c$ (key block size).

To understand how multiple threads within a single threadblock manage this footprint without exceeding hardware limits or utilizing "spilling," it is essential to look at how modern compilers like NVCC distribute shared data. In CUDA, while registers are logically private to each thread (meaning every thread has its own copy of every variable), a CTA can coordinate to limit how much register storage is actually used per thread if instructed to do so via intrinsics like `shfl_sync` or through compiler optimizations. However, in the specific context of FlashAttention-3's two-stage pipeline, the matrix $\mathbf{S}$ represents a dense tile of size $B_r \times B_c$. The physical layout on the GPU's register file is determined by how many floating-point variables are defined per thread in the PTX/SASS assembly. If $B_r = 64$ and $B_c = 64$, this creates a tile of $4096$ floats. If every thread unconditionally declares all $4096$ variables as local registers, the required registers would indeed explode linearly with any increase in block size (e.g., doubling $B_r$ doubles the register count), which could quickly push a typical CTA beyond H100's per-thread register limit of $256$ SIMD registers for certain configurations.

The paper clarifies that this overhead is a constraint rather than an optimization opportunity in itself; it forces a trade-off between tile size and pipeline depth, but it does not inherently change the memory architecture from SMEM to Register File. The implementation manages this by allocating a fixed number of registers to store this specific data structure, which becomes part of what is counted against the per-thread limit when using `setmaxnreg` directives. In practice, implementations often leverage vectorized register definitions where multiple threads share ownership of these values via shuffles (shuffle instructions), effectively allowing a single logical element of the matrix $\mathbf{S}$ to reside across multiple threads or be computed redundantly only when necessary. However, for a synchronous copy operation like `Copy $\mathbf{S}_{\mathrm{next}}$ to $\mathbf{S}_{\mathrm{cur}}$`, each thread typically needs access to its row slice or specific sub-segment of this tile depending on how $WGMMA$ loop unpacking is done. The "overhead" mentioned is strictly proportional to $B_r \times B_c$, meaning if you double $B_r$, you do indeed double the number of floats allocated as intermediate state per threadblock aggregation point, pushing against those hard register limits on H100.
