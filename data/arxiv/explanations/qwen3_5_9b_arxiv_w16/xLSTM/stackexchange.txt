\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### What is the precise role of the normalizer state $n_t$ in sLSTM and mLSTM?
Question:
I am reading the xLSTM paper and I understand that a normalizer state ($n_t$) is introduced for both sLSTM and mLSTM. In Equation 3, $n_t$ is defined as $f_t n_{t-1} + i_t$. The paper states that this sums up the product of the input gate times all future forget gates.

However, looking at the forward pass equations, $	ilde{h}_t = c_t / n_t$ for sLSTM and retrieved vectors are divided by a term involving $n_t$ for mLSTM. But wait, if $i_t$ is now an exponential gate ($\exp(\tilde{i}_t)$), how do we ensure numerical stability when calculating this running sum in $n_t$? Doesn't simply summing exponential values lead to overflow? I remember in Section 3.2 they mention a 'stabilizer state' $m_t$, but that seems to apply to the gates themselves ($i'_t, f'_t$). How exactly does the stabilization logic interact with or replace the normalization logic in Equation 3? What prevents $n_t$ from becoming astronomically large if we haven't applied the log-stabilization to it directly?

Answer:
The normalizer state $n_t$ in both sLSTM and mLSTM serves as a running accumulator that keeps track of the "strength" or total magnitude of the exponential input gates weighted by all preceding forget gates, effectively preventing the retrieval of old information from being exponentially amplified to infinity. Intuitively, in an LSTM with standard sigmoid gating, the cell state is updated additively ($c_t = f_t c_{t-1} + i_t z_t$), but if you switch to exponential gating (where $i_t = \exp(\tilde{i}_t)$ and potentially $f_t = \exp(\tilde{f}_t)$), the same additive formula could cause the hidden state to explode if the product of many forget and input gates becomes enormous. The components divided by $n_t$—specifically $\tilde{h}_t = c_t / n_t$ in sLSTM—act as a calibration step to ensure that the retrieved memory scale remains reasonable regardless of how long the sequence is.

To address your specific concern about numerical stability: the paper does not compute $n_t$ by directly summing uncontrolled exponential values because that would indeed lead to overflow. Instead, xLSTM employs a dedicated **stabilizer state** denoted as $m_t$, which operates entirely in log-space. As defined in Equation 3.2 ($m_t = \max(\log(f_t) + m_{t-1}, \log(i_t))$), this state tracks the maximum log-magnitude encountered by the weighted sums in the past. When you need to retrieve a value involving $n_t$, instead of maintaining a potentially overflowing physical sum, xLSTM utilizes this stabilizer state to shift the scale. In practice, for sLSTM, while Equation 3 shows $n_t$, the actual implementation logic described implies that $c_{retrieved}$ is computed using normalized values or exponentials shifted by this `max` log-value to prevent overflow before division. Effectively, the stabilization logic replaces direct summation with a logarithmic maximum approach for scaling factors, ensuring that even after thousands of time steps where inputs are always being added or multiplied exponentially, the values remain within representable floating-point ranges without sacrificing information about their relative magnitudes. This allows the division $\tilde{h}_t = c_t / n_t$ (or its matrix equivalent in mLSTM) to function correctly without requiring astronomically large numbers, as both numerator and denominator are implicitly scaled by the same stabilization factor derived from $m_t$. By connecting these concepts, we see that xLSTM achieves its powerful exponential memory capabilities—a key improvement over vanilla LSTMs' inability to revise stored values—by carefully balancing expressive power through normalization against computational stability through log-space stabilization.

### Does the 'memory mixing' in sLSTM fundamentally break parallelization similar to standard LSTMs?
Question:
The abstract claims mLSTM is fully parallelizable because it abandons memory mixing. Conversely, sLSTM retains memory mixing via recurrent weight matrices $f{R}$. 

In Equation 2 (Eq. \ref{eq:slstmforward}), standard LSTM has terms like $r_i h_{t-1}$ inside the input gate calculation. For sLSTM with multiple cells (as described in 'New Memory Mixing'), do we have terms like $f{R}_i f{i}_{past}$ or similar that couple different time steps explicitly inside the gate computations?

The paper says sLSTM prohibits parallelizable operations. Is this strictly true for *any* implementation on modern hardware (like unrolling on GPUs), or does it mean we literally cannot fuse layers? If I have a sequence of length 1000 on an NVIDIA A100, can't I just compute all $	ilde{h}_{0:999}$ simultaneously if there are no dependencies? Or does 'memory mixing' specifically introduce a dependency chain between hidden states at different time steps $h_{t-1}$ influencing $c_t$ and thus $h_{t+1}$ in a way that forces real-time sequential processing even without explicit cell-to-cell mixing?

Answer:
The short answer is yes: the "memory mixing" mechanism in sLSTM fundamentally breaks the ability to compute cell states in parallel across time steps, creating a strict sequential dependency chain similar to standard LSTMs. However, this does not mean you must rely on slow CPU loops or real-time processing; modern hardware like the NVIDIA A100 can still accelerate this sequentially by fusing kernels and utilizing specialized GPU CUDA instructions, achieving significant speedups despite the loss of raw parallelization.

To understand why, we must look at how sLSTM defines its update rules compared to mLSTM. The paper introduces the concept of "memory mixing" as hidden-to-hidden recurrent connections. Unlike standard LSTMs which often use scalar recurrence coefficients (like $r_i$ in Equation \ref{eq:slstmforward}), sLSTM generalizes this to dense recurrent weight matrices $\mathbf{R}$ when utilizing multiple memory cells or heads. In these configurations, the computation for the cell state $c_t$ and gate values depends not only on the current input $\mathbf{x}_t$ but also on a weighted mixture of previously computed hidden states $\mathbf{h}_{t-1}$. Crucially, Equation \ref{eq:mlstm_recurrent_begin} for mLSTM demonstrates that without these hidden-hidden connections, the update for time step $t$ is independent of other time steps beyond $t-1$. Because sLSTM retains these $\mathbf{R}$ matrices that mix information between distinct cells (or heads), determining $\mathbf{h}_t$ requires a completed calculation of $c_{t-1}, i_{t-1}, f_{t-1}$, and $\mathbf{o}_{t-1}$. Since $\mathbf{h}_t$ is then required to compute $\mathbf{x}_{t+1}$ (through ReLU/fusion layers) and subsequently all gate values for step $t+1$, there is an explicit data dependency chain linking every time step to its predecessor.

The paper explicitly addresses this limitation in Section "Memory and Speed Considerations," stating that "sLSTM is not parallelizable due to the memory mixing (hidden-hidden connections)." This constraint means you cannot simply instantiate a massive batch of operations on an A100 where GPU threads compute all 999 outputs simultaneously, because mathematically you cannot know $h_500$ without first computing $h_499$. Even if there are no internal dependencies *within* the calculation of a single step (which isn't true here since gates depend on $h_{t-1}$), you cannot skip ahead or reorder computations without violating causality.

However, "cannot parallelize" does not equate to "must run on a slow CPU loop." Modern GPU implementations handle sequential dependencies via kernel fusion and optimized memory access patterns. While traditional parallelism involves computing independent elements at once ($P_0, P_1, P_2 \dots$), sequential models allow for heavy optimization within each step. The xLSTM authors developed a fast CUDA implementation that fuses the multiplication and addition operations into a single custom kernel for sLSTM. This minimizes memory latency overhead and allows vectorized operations over the batch dimension (if you have multiple sequences) or feature dimensions simultaneously within each sequential step. Consequently, while you are forced to process time steps one after another ($T=0 \to T=1 \to T=2$), each individual transition can be computed extremely efficiently on the GPU architecture—potentially approaching linear speed relative to mLSTM's performance—rather than waiting for dependencies to resolve over many small steps as might happen in Python snippets or unoptimized loops.

### How does Exponential Gating specifically solve "Irreversible Storage Decisions" compared to standard sigmoid gating?
Question:
In the Introduction, the paper highlights three limitations of original LSTMs. The first is the "inability to revise storage decisions," exemplified by Nearest Neighbor Search where an old stored vector must be amended if a better one appears.

The authors propose "exponential gating" to fix this. Intuitively, if I have an old value stored via $c_{old}$ and find a new value $v_{new}$ should be weighted higher, a sigmoid forget gate might just set everything to zero or partial retention. 

Mathematically, with exponential gates where input/output are effectively unbounded before normalization (or stabilized), how does one mathematically formulate "rewriting" versus "forgetting + adding"? If $f_t$ becomes very large (exponential) instead of small (sigmoid), doesn't that just amplify errors rather than allowing fine-grained revision of an existing covariance matrix entry? Does xLSTM allow negative keys/values (which would matter for updating inner products) if inputs are limited by tanh/relu elsewhere?

Answer:
The core distinction between standard sigmoid gating and exponential gating in xLSTM regarding "irreversible storage decisions" lies in the mathematical nature of how the memory state is updated: sigmoid gating forces a binary-like choice to either add or forget, whereas exponential gating allows for a continuous, recursive revision that effectively "rewrites" existing information without zeroing it out.

In standard LSTMs, the update rule $c_t = f_t c_{t-1} + i_t z_t$ relies on a sigmoid forget gate $f_t \in [0, 1]$ and an input gate $i_t \in [0, 1]$. Mathematically, if you need to correct an old vector, the LSTM is structurally forced to treat this as two separate operations: first applying the forget gate to subtract or dampen the old information ($f_t c_{t-1}$), and then adding the new information via the input gate ($i_t z_t$). This creates a fundamental limitation known as "measure zero" forgetting; because both gates operate independently within a bounded range, it is difficult for the model to precisely undo a previous storage decision and replace it with a new one. The model essentially adds a correction vector on top of the old one, often leading to interference where the old and new vectors cannot be perfectly separated.

Exponential gating resolves this by changing the activation functions for the input and forget gates from bounded sigmoids to unbounded exponentials (stabilized by a running normalizer state $n_t$). As shown in Equation \ref{eq:slstmforward}, xLSTM computes the hidden state as $\tilde{h}_t = c_t / n_t$, where $c_t$ is updated by exponential weights. Specifically, if we look at Equation \ref{eq:mlstm_recurrent_begin} for the matrix version (which generalizes this logic), the cell state update is $\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \mathbf{v}_t \mathbf{k}_t^\top$. Here, $f_t$ can take values less than 1 (acting as decay) or greater than 1, but more importantly, the relationship between past and present becomes multiplicative through exponential accumulation.

The intuitive mechanism for "rewriting" rather than "forgetting + adding" can be seen in how these gains accumulate. In standard LSTMs, if you want to drastically change a stored value at time $T$ based on new evidence at time $T'$, you must explicitly set $f \approx 0$ to erase the old value and then add new value. With exponential gates, forgetting corresponds to multiplying by a small scalar (decay), and remembering corresponds to multiplying by zero (erasing). However, because the input gate can also be extremely large (controlled by $\exp(\tilde{i}_t)$), adding new information acts like injecting a dominant source into an equation where previous terms are being simultaneously dampened by exponential decay factors tracked by the normalizer $n$. Crucially, because both sides of the equation scale with exponentials relative to this normalizer during backpropagation (as detailed in Equation \ref{eq:slstmstabil}), the gradient flow preserves information about when specific events occurred without vanishing. This allows xLSTM to distinguish between "I added something important long ago" versus "I need to overwrite what I stored," enabling it to revise storage decisions fluidly rather than getting trapped in irreversible additions.

Regarding your specific concern about errors being amplified when exponential gates become large: xLSTM addresses this precisely through its novel normalization state $n_t$. Instead of letting large exponential values cause numerical instability or error amplification directly in the hidden state calculation, xLSTM divides every cell update by this running sum of past gate magnitudes ($c_t / n_t$). The stabilizer state $m_t$ tracks $\log(\max(f_i))$, ensuring that while individual gates can represent massive factors (like "multiply everything by 1000"), these factors cancel out mathematically against the normalizer before producing the final hidden state. Thus, large exponentials do not amplify errors arbitrarily; they encode information about duration and relative importance between events that ultimately collapses into precise difference signals when normalized.

Finally, regarding negative keys or values: yes, xLSTM allows for negative components within its matrix memory $\mathbf{C}_t$. The key vectors $\mathbf{k}_t$, value vectors $\mathbf{v}_t$, and queries $\mathbf{q}_t$ are produced via linear projections of inputs followed by layer normalization. While layer normalization centers data around zero mean (implying both positive and negative values are expected), there are no explicit constraints forcing keys or values to remain non-negative prior to forming their outer product rank-1 updates ($\mathbf{v}_t \mathbf{k}_t^\top$). This flexibility is essential for representing complex relationships such as differences or corrections (e.g., updating an inner product requires subtracting old contributions), which would be impossible if all stored magnitudes were forced strictly positive.

### Is mLSTM truly independent of sequence length in terms of parameter count and architecture design?
Question:
The abstract mentions that mLSTM has a 'matrix memory' which enhances storage capacities. Section 3.3 defines the update rule as $f{C}_t = f_t f{C}_{t-1} + i_t f{v}_t f{k}_t^\top$. The hidden state retrieval is $f{h}_t = f{o}_t f{C}_t f{q}_t / n_t$.

If memory growth is constant per step (adding one rank-1 update), why isn't this similar to storing all past context vectors explicitly like in Attention? If I increase context length from 1k to 4M tokens, isn't $f{C}_m$ simply accumulating all these updates?
The paper mentions "Linear computation" but also warns in Limitations (v) that increasing context might overload memory for longer sizes. Does this mean mLSTM *requires* truncation mechanisms or sliding windows implicitly? Unlike Transformers which can theoretically handle infinite length given enough RAM/VRAM attention scores, does xLSTM suffer from numerical instability or precision loss after very long sequences purely because it accumulates matrix additions without decaying far-back information fast enough? How is this handled during training vs inference?

Answer:
The concern that mLSTM might accumulate unbounded memory usage as the sequence length increases is well-founded, but the paper clarifies that this does not impose a computational or architectural limitation in the same rigid way it does for standard Self-Attention mechanisms. While the paper explicitly states in its Limitations section (point v) that "increasing the sequence length might overload the memory$[$vj$]$ for longer context sizes," this refers specifically to the hardware constraints of storing the active matrix state during inference on a finite GPU, rather than an inherent requirement for truncation or sliding windows in the model's design logic.

To understand why mLSTM does not simply require a sliding window like many Transformers, we must look at how memory growth relates to computation versus storage. The paper emphasizes that mLSTM has a "constant memory complexity" regarding *computation* and structure because it avoids the quadratic pairwise interactions of attention. The update rule $\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \mathbf{v}_t \mathbf{k}_t^\top$ adds one rank-1 update per token. However, unlike Attention, where memory grows linearly with sequence length relative to the number of past tokens checked (leading to quadratic compute), mLSTM maintains a fixed-size matrix $\mathbf{C}$ of dimensions $d \times d$ (where $d$ is the hidden dimension or key dimension). The matrix size depends solely on the width of the network's projection, not on how many tokens have been processed. Therefore, theoretically, you can extend this recurrence indefinitely without needing to truncate history or approximate past queries, provided your VRAM can hold two $d \times d$ matrices ($\mathbf{C}$ and perhaps temporary buffers for updates) plus standard activations.

The distinction regarding "overloading memory" is critical here: for a Transformer with 4M tokens, you must store a cache of 4M keys and values, which blows up RAM usage unnecessarily if you only need semantic retrieval from specific parts. In contrast, mLSTM's state collapse allows it to handle infinite contexts in theory because it compresses all history into a single $d \times d$ covariance matrix updated via exponential gating ($f_t$). This gating mechanism acts as a constant decay rate, allowing distant information to naturally lose significance without forced truncation, although numerical precision might eventually become an issue over extremely long sequences (e.g., millions of steps) if eigenvalues drift significantly from numerical stability bounds—a challenge common to any recurrent compression method rather than manner unique to xLSTM.

Crucially, equation (2) in Section 3.3 defines the retrieval process as $\mathbf{h}_t = \mathbf{o}_t \odot (\mathbf{C}_t \mathbf{q}_t / n_t)$, where $\mathbf{q}_t$ is derived only from the current input $\mathbf{x}_t$ via $\mathbf{W}_q$. The paper notes that since $\mathbf{n}_t$ (the normalizer state) tracks the weighted sum of keys using a recurrence similar to equation (1), its storage requirement also remains constant regardless of sequence length. Thus, while extending context from 1k to 4M tokens would cause intermediate GPU memory spikes due to storing massive sequences of input activations and gates during training or pre-fill phases on GPUs with limited fast memory, it does not fundamentally alter the model's ability to retrieve long-term dependencies once that phase is managed or distributed across time steps. Unlike Transformers which are bound by $O(T^2)$ or $O(T)$ attention caches preventing universal length scalability without approximation methods like FlashAttention variants or Linear Transformers, mLSTM's design allows for exact propagation through arbitrary lengths limited only by available fast memory and numerical stability thresholds.
