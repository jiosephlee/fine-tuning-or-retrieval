\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### How does backpropagating through a frozen, 4-bit quantized model without updating those weights actually work mathematically?
Question:
I am reading the QLoRA paper and I understand the core idea: we keep the base model weights ($\mathbf{W}^{{\text{NF4}}}$) frozen and only tune the adapters ($\mathbf{L}_1, \mathbf{L}_2$). However, I am struggling with the mechanics of backpropagation. The paper states 'backpropagates gradients through a frozen... model into Low Rank Adapters.' If $\mathbf{W}$ is frozen, shouldn't the gradient with respect to it be zero or NaN? Specifically, when calculating $\frac{\partial E}{\partial \mathbf{L}_i}$, how do we compute the term involving $\frac{\partial \mathbf{X}}{\partial \mathbf{W}}$ if $\mathbf{W}$ is stored in NF4 format and never updated? Is it simply that we compute numerical gradients locally around the dequantized value without performing any weight update step on $\mathbf{W}$, or is there a specific chain rule derivation I'm missing regarding the dequantization function in Equation (5)?
Answer:
The mechanism you are intuitively expecting—where a frozen weight matrix receives a zero gradient or causes "NaN" due to division by zero during backpropagation—is actually not how modern deep learning frameworks handle frozen parameters during training. The key lies in understanding that **freezing a parameter is a constraint applied to the optimization step, not a modification to the mathematical definition of the gradient.**

When the QLoRA paper states that gradients are "backpropagated through a frozen... model," it relies on standard Chain Rule differentiation. In a standard neural network layer with weights $\mathbf{W}$, input $\mathbf{X}$, and output $\mathbf{Y} = \mathbf{X}\mathbf{W}$, the gradient of the loss $E$ with respect to an adapter weight $\mathbf{L}$ involves the term $\frac{\partial E}{\partial \mathbf{L}} = \frac{\partial E}{\partial \mathbf{Y}} \frac{\partial \mathbf{Y}}{\partial \mathbf{L}}$. Because $\mathbf{Y}$ depends on $\mathbf{W}$ ($\frac{\partial \mathbf{Y}}{\partial \mathbf{X}} = \mathbf{W}^T$), you mathematically need the values of $\mathbf{W}$ to compute forward activations and backward gradient signals. However, you never calculate the gradient *with respect to* $\mathbf{W}$ (i.e., setting parameters like `requires_grad = False` on $\mathbf{W}$ tells PyTorch: "Do not stop accumulating gradients flowing through this node; however, do not create an update rule for this specific parameter"). Consequently, there is no term involving $\frac{\partial E}{\partial \mathbf{W}}$ in your final update equation for $\mathbf{L}$, so there is no requirement for W's gradient to be zero or non-zero—it simply doesn't exist in the optimization objective for that tensor.

Regarding your specific concern about numerical gradients in Equation (5) and the dequantization function: Dequantization in QLoRA is treated as a linear scaling operation defined by Equation (2): $\text{dequant}(\cdot) = c_i / (\text{scale})$. Mathematically, this function is constant with respect to time during training because the base weights are fixed and their quantization scales ($c_1^{\text{{FP32}}}, c_2^{\text{{k-bit}}}$) are also frozen once generated. Since these constants do not change, their derivatives with respect to any trainable parameter are valid affine transformations. During the backward pass, you dequantize the fixed 4-bit NF4 weights into BFloat16 (the computation format) exactly as if they were full-precision floats. The framework performs matrix multiplications using these recovered floating-point values to propagate error signals to the active LoRA adapters ($\mathbf{L}_1, \mathbf{L}_2$).

It is important to distinguish between "computed gradients" and "updated weights." In QLoRA, the computation graph includes the dequantization step as part of the forward path for every single backpropagation pass. The fact that the weights are stored in 4-bit format only affects memory storage and bandwidth; once loaded into memory for computation and dequantized to BFloat16/FP16 for precision arithmetic, they participate in standard floating-point differentiation rules. The only "trick" involved here is Paged Optimizers mentioned in Section IV and V-B'Paged Optimizers', which manages memory allocation for optimizer states so that when small minibatches are processed sequentially without loading everything into GPU RAM at once, there are no catastrophic memory spikes caused by storing gradients for both massive base model activations and adapters simultaneously. This memory management handles data eviction efficiently rather than altering the underlying calculus.

### What is the specific mechanism by which Double Quantization achieves 'information theoretically optimal' savings without losing precision?
Question:
In Section 4 (QLoRA Finetuning), the authors introduce Double Quantization (DQ) to save memory. They claim it reduces memory by ~0.37 bits/parameter by quantizing the quantization constants ($c_2$). The text mentions: 'treatment of quantization constants $c_2^{${\text{FP32}}}$... as inputs to a second quantization.' I am confused about the implementation details here. Are $c_2$ values converted from FP32 to FP8 for storage, and then when needed during dequantization (Equation 6), do we perform a second dequantization step on-the-fly to recover an approximate FP32 constant before applying it to the NF4 weights? If DQ is only used for storage but not for forward/backward computation except via approximation, how exactly does this mapping ensure that no significant precision is lost compared to storing full FP32 constants? Is there a lossless recovery guaranteed, or just sufficient accuracy for training stability?
Answer:
The claim that Double Quantization (DQ) achieves "information theoretically optimal" savings while preserving precision is actually a subtle phrasing; strictly speaking, the *NF4* data type itself is the component that is information-theoretically optimal for normally distributed weights. Double Quantization's role is specifically to reduce the memory footprint of the *support* (the quantization constants) associated with NF4 without introducing significant reconstruction error. It does not achieve information-theoretic optimality in its own right, but rather enables the use of the optimally shaped NF4 grid with a more compact representation of its parameters.

To understand the mechanism, we must look at how quantization works in this context. Standard block-wise quantization divides a weight tensor into chunks (blocks) and calculates a single scaling factor, $c$, for each block to map the block's values into the discrete attribute range required by the data type (in QLoRA's case, NF4). In the standard setup without Double Quantization, these scaling factors $c$ are stored as 32-bit floating-point numbers. For a block size of 64 parameters, this adds $32/64 = 0.5$ bits per parameter just to store these constants.

The authors observe that while large language model weights are normally distributed and thus perfectly suited for NF4, the distribution of these scaling factors themselves often varies smoothly across neighboring blocks. If a single neighborhood in a neural network uses blocks where $c$ ranges from 0.8 to 1.2, storing every instance as a full 32-bit float is wasteful because those values are highly correlated and occupy only a small portion of the possible value space with high density.

Double Quantization exploits this by treating the FP32 scaling factors as an input tensor for a second quantization step. First, these FP32 constants are treated as data. Since they are positive, their mean is subtracted so they are centered around zero, allowing them to utilize symmetric bit patterns effectively. They are then quantized into 8-bit floats ($c_2^{\text{FP8}}$) using a relatively large block size (256 parameters). Crucially, along with this coarse approximation $c_2$, they also compute new residual scaling factors $c_1^{\text{FP32}}$.

When it comes time to dequantize for computation during training or inference, the process is hierarchical rather than losing information permanently. The system first retrieves the coarse 8-bit constant $c_2^{\text{FP8}}$. It then multiplies this by its own internal FP32 residual constant $c_1^{\text{FP32}}$. Mathematically, to recover an approximate full-precision constant $\hat{c}_{\text{FP32}}$, one performs:
$$ \hat{c}_{\text{FP32}} \approx c_1^{\text{FP32}} \cdot c_2^{\text{FP8}} $$
This recovered value $\hat{c}_{\text{FP32}}$ is then used in Equation (6) of the paper to dequantize the actual 4-bit weights stored as $\mathbf{W}^{\text{k-bit}}$. You take these 4-bit codes and divide them by this reconstructed scale factor to obtain floating-point weights in BFloat16 for computation:
$$ \mathbf{W}^{\text{BF16}} = \frac{\mathbf{W}^{\text{k-bit}}}{\hat{c}_{\text{FP32}}} = \frac{\mathbf{W}^{\text{k-bit}}}{c_1 \cdot c_2} $$

This two-step approach ensures no significant precision is lost because $c_1$ acts as an inverse quantizer for $c_2$. The term $c_1$ captures all the fine-grained detail lost when compressing the original high-precision $c$ into only 8 bits ($c_2$). Because all $k$-bit Nearest Neighbor (NFk) weights fall within the same random seed-generated dataset distribution ($[-1, 1]$), their scaling factors tend to be clustered closely together generally but have specific variations locally. Grouping many blocks together for $c_2$ averages out local noise perfectly if handled by $c_1$, ensuring that for any given weight chunk during forward or backward passes, we reconstruct an approximate FP32 scale factor that is accurate enough to yield gradients matching standard fine-tuning within experimental error margins.

The intuition here connects broadly to vector quantization in signal processing: if your signal ($W$) varies within a known statistical distribution ($N(0,I)$), you can describe it efficiently using a codebook entry plus residuals; if your *metadata* controlling that signal (the scale factors) also follows a predictable distribution across space (neighboring blocks have similar scales), you can compress that metadata itself using similar statistical principles without affecting your ability to reconstruct the original signal faithfully enough for downstream optimizations like Backpropagation through Time or Adam optimization statistics in LoRA adapters.

### Does Paged Optimizers solve Memory Spikes or just Out-of-Memory (OOM) crashes during long sequence generation?
Question:
I'm trying to understand the specific utility of 'Paged Optimizers' mentioned in Section 4 and discussed in Section 5. The paper states they are used 'to prevent memory spikes during gradient checkpointing that occur when processing a mini-batch with a long sequence length.' My understanding of gradient checkpointing usually involves trading compute for memory by recomputing activations. However, I am confused about where exactly these 'spikes' occur in LoRA finetuning compared to full finetuning. If LoRA parameters are tiny by design (0.2% of base model), why does their optimizers state cause such significant GPU memory issues compared to the four-bit base model weights? Does 'Paged Optimizers' essentially mean redistributing optimizer states between CPU RAM and GPU VRAM dynamically based on which parameters are currently being updated in a given batch, effectively making them an offloading solution specifically for optimizer states rather than activation gradients?
Answer:
In the context of QLoRA, "Paged Optimizers" are specifically designed to address the dynamic, non-uniform memory spikes caused by gradient checkpointing and $\Longleftrightarrow$ sequences, rather than simply being a general offloading solution for optimizer states to CPU RAM. The core confusion often stems from the fact that while LoRA parameters themselves are tiny (roughly 0.2% of the base model), during training with gradient checkpointing, memory is dominated by **activation gradients** for the base weights, but these activations are recomputed on-the-fly during the backward pass.

When processing a mini-batch with a long sequence length, standard gradient checkpointing significantly increases memory consumption because it must store partial activations from earlier layers in the BERT/Transformer blocks while recomputing them later. These partial activations can vary drastically in size depending on the specific sequence length of the mini-batch. In your question, you correctly identified that `torch.utils.checkpoint` or similar mechanisms trade compute for memory; however, this trade-off creates a scenario where a single batch might momentarily require double or triple the GPU memory compared to a shorter sequence, even if the total average memory usage is within limits. If this peak momentarily exceeds your GPU's VRAM capacity, you get an Out-of-Memory (OOM) crash. Paged Optimizers mitigate this by utilizing NVIDIA's Unified Memory and paging system to store optimizer states (specifically those for the LoRA adapters) on disk or CPU RAM when they are not immediately needed and dynamically load them back as they become necessary for updates. This allows the system to handle these sudden spikes by ensuring that even if a batch requires more memory than physically available on VRAM at that instant, the necessary data can be fetched from CPU RAM without crashing, provided enough physical RAM exists on the machine.

Crucially, this technique does not merely redistribute static weights between CPU and GPU; it manages the *fluctuating* requirement for optimizer state storage which becomes problematic when combined with gradient checkpointing's variable activation footprint. The paper notes that while batching with long sequences rarely occurs in their specific experiments, preventing these potential spikes is critical for enabling training on massive models like 33B and 65B on single GPUs without hitting hard memory limits during edge cases. Thus, Paged Optimizers act as a safety net against these transient peaks rather than replacing them entirely with offloading; they ensure continuity when gradient calculation patterns push temporary memory usage beyond standard static allocations.

### Why was NF4 chosen as information-theoretically optimal if Quantile Quantization already ensures equal bin occupancy?
Question:
In Section 4, regarding 4-bit NormalFloat Quantization, the authors explain that NF4 addresses limitations of standard Quantile Quantization. They state that Quantile estimation is expensive and approximation errors affect outliers. They then propose transforming weights so they fit into a fixed range $[-1,1]$ matching the data type's distribution. However, I am still unclear on why this makes it 'optimal.' Quantile Quantization defines bins such that each bin has exactly $1/2^k$ probability mass under a theoretical distribution. How does fixing standard deviation $\sigma$ to fit $[-1,1]$ specifically improve upon just estimating quantiles directly from data? Is it because precomputing these bins avoids runtime cost entirely, making it more stable for training where distributions shift slightly batch-to-batch due to gradient updates? In what specific mathematical way does mapping data to $N(0,S)$ with pre-defined bins minimize reconstruction error compared to dynamic bin estimation?
Answer:
The designation of 4-bit NormalFloat (NF4) as "information-theoretically optimal" stems from a specific constraint in information theory: you cannot compress data beyond the entropy of its underlying distribution without loss. While Quantile Quantization theoretically achieves optimal packing by ensuring each of the $2^4$ bins contains exactly $1/16$ of the probability mass, it fails to be *practically* optimal for neural network weights because it requires dynamic estimation of these quantiles for every block during training.

In standard quantile approaches, the authors must estimate the boundaries between bins based on the current empirical distribution of the weight tensor. As noted in Section 4, this estimation is computationally expensive, and existing approximation algorithms introduce errors that disproportionately affect outliers—values that often reside precisely at the bin edges or in low-probability tails. These approximation errors degrade reconstruction precision. NF4 circumvents this by leveraging two key facts identified in prior work: pretrained LLM weights are well-approximated by a zero-centered normal distribution $N(0, \sigma)$, and unlike activations or losses during training, these weights do not shift significantly enough to invalidate a single pre-computed distribution model within a short training window.

Because the weights follow $\mathcal{N}(0, 1)$ up to a scaling factor $\sigma$, their cumulative distribution functions (CDFs) are uniform across all possible magnitudes if we normalize them. This allows us to pre-calculate the exact quantiles for a standard normal distribution and map them to a fixed $[-1, 1]$ range. By rigidly enforcing that every bin corresponds to an equal probability mass under this known theoretical distribution (as opposed to estimating it from potentially noisy current gradients), NF4 eliminates the binning error inherent in dynamic estimation. The "optimality" claim is therefore twofold: mathematically, it packs the Gaussian probability mass equally into bins (maximizing entropy efficiency for that specific distribution); and empirically, it avoids the computational overhead and numerical instability associated with Approximate Quantile Estimation during backpropagation. Thus, NF4 is not just "close" to optimal; it is exactly optimal for normally distributed data *if* you assume you can ignore small deviations from normality prior to training—which data analysis confirms is valid for frozen pretrained models used as baselines in QLoRA.

### '0% iterations' despite using 0.2% LoRA parameters: Why did setting adapters at *every* layer become crucial after non-linearities in large models?
Question:
<p>The authors mention they use adapters at every network layer ('adapter at every linear transformer block layer'). Standard LoRA papers often applied them only to Query and Value projections in_attention blocks._para</p> <p>I read somewhere else that applying adapters only at certain layers or even across all layers might have diminishing returns due to computational cost. But here, applying them everywhere seems necessary.</p> <p>The text says: "...avoid[s] almost all of the accuracy tradeoffs seen in prior work." Could someone explain *why* using adapters at every intermediate FFN block (and potentially Input/Output layers as well) became so critical for recovering full 16-bit performance compared to earlier applications?</p> <p>In LLaMA architecture there are residual connections after non-linearity

Answer:
In the context of the QLoRA paper, applying adapters at every linear transformation layer (including both attention projections and fully connected feed-forward layers) is critical primarily due to the constraint of operating on a heavily quantized 4-bit base model.

When a standard transformer model is trained with full 16-bit precision, the optimization landscape is fine enough that modifying specific layers like Query ($Q$) and Key ($K$) projections in the attention mechanism often suffices to capture the necessary updates for a task. However, quantizing weights to 4-bit introduces significant information loss, particularly regarding the intricate gradients required for high-fidelity parameter updates. The paper notes that while standard LoRA papers focused on $Q$ and $V$ matrices or other specific spots in the attention block, this sparse application leads to "almost all of the accuracy tradeoffs seen in prior work" when combined with low-precision base models.

Intuitively, you can think of the quantization as blurring the fine details of the model's original weight distribution. If you only add adapters to a subset of layers, you are only sharpening those specific blurry spots while leaving others degraded. To recover full 16-bit performance on a 4-bit quantized backbone, the learnable adapters need to inject the missing gradient information across *every* weighing operation where information is transformed. In LLaMA architectures, there are multiple such points: not just in attention heads but also within every intermediate feed-forward network (FFN) layer, which performs heavy matrix multiplications following each block's non-linearities.

The authors found experimentally that using default LoRA configurations (which typically target only attention layers or specific subsets) failed to match benchmarks like MMLU or chatbot evaluations. By increasing density—placing adapters at every linear layer including input/output—they could effectively reconstruct the function of a fully fine-tuned 16-bit model without actually training billions of additional parameters. This density allows the adapters to compensate for the quantization artifacts throughout the entire forward pass. Crucially, because LoRA parameters are so small (often less than 1% of total parameters), expanding their position from "strategic" spots to "every" spot incurs negligible memory overhead compared to activation gradients or optimizer states. This distinction allows QLoRA to bypass performance degradation; it is not just about saving memory during inference with quantization, but about enabling High-Performance Parameter-Efficient Fine-Tuning where the budget for trainable parameters can be spent widely rather than sparsely to counteract quantization errors.
