\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does FeatLLM extract rules from the LLM without fine‑tuning?
Question:
In the paper, FeatLLM is described as using in‑context learning to make the LLM generate "rules" for each class. I am unclear on the exact prompting strategy that forces the model to produce these deterministic rule statements instead of directly outputting class predictions. Specifically, how does the two‑step reasoning instruction (Step 1: infer causal relationships, Step 2: deduce rules) avoid the model simply memorising spurious correlations from the few-shot examples? Could someone walk through a concrete example prompt and the expected LLM response format?
Answer:
**Answer**

`FeatLLM` does not ask the language model to *classify* a new record directly.  
Instead it asks the model to write down, in natural‑language “if‑then’’ statements, the **criteria** that separate the classes.  
These criteria (called *rules* in the paper) are later turned into binary features and fed to a tiny linear classifier.  
The key to obtaining deterministic‑looking rules rather than a raw prediction is the **two‑step reasoning instruction** that is baked into the prompt.

---

### Why the two‑step instruction works

1. **Step 1 – “Infer causal relationships’’**  
   The prompt tells the LLM: *“Without looking at the few‑shot examples, think about what you already know about the task and the columns. Which feature(s) are generally related to each class?”*  
   Because the model is forced to answer *before* seeing any concrete examples, it can only rely on its **prior knowledge** (e.g., “older patients are more likely to have heart failure”, “high cholesterol is a risk factor for heart disease”).  
   This prevents it from latching onto accidental patterns that happen to be present in the tiny demonstration set.

2. **Step 2 – “Deduce rules from examples’’**  
   After it has listed a short set of plausible causal links, the prompt invites it to *“Now look at the k labelled examples and turn those causal links into concrete decision rules for each class.”*  
   The model therefore uses the examples **only as a sanity check**: it adjusts the generic knowledge to match the observed data, but it cannot create brand‑new correlations that were not hinted at in Step 1.  

Because the LLM is asked *explicitly* to output rules and because we fix the number of rules per class (the paper uses 10), the model’s answer space is highly constrained.  The response format is also prescribed (see below), which makes parsing deterministic and blocks free‑form predictions.

Empirically (Section 4.3, “Effect of adding spurious correlations’’) this design reduces the proportion of rules that involve irrelevant columns to $1\text{–}2\%$, confirming that the two‑step scaffold indeed suppresses spurious correlations.

---

### Concrete example prompt

Below is a distilled version of the prompt used for the **Myocardial** dataset (predicting whether a patient suffers from chronic heart failure).  
All three parts – basic information, reasoning instruction, and response instruction – appear in a single text block sent to GPT‑3.5‑turbo.

```
Task: Does this patient have chronic heart failure?  Answer "Yes" or "No".

Feature descriptions:
- age : integer, patient age in years.
- sex : categorical, {male, female}.
- chest_pain_type : categorical, {typical_angina, atypical_angina, non_anginal_pain, asymptomatic}.
- resting_bp : integer, resting blood pressure (mm Hg).
- cholesterol : integer, serum cholesterol (mg/dL).
- fasting_blood_sugar : boolean, true if > 120 mg/dL.
- resting_ecg : categorical, {normal, ST_T_abnormality, left_ventricular_hypertrophy}.
- max_heart_rate : integer, maximum achieved heart rate.
- exercise_angina : boolean, true if angina induced by exercise.
- oldpeak : float, ST depression induced by exercise.
(… other columns omitted for brevity …)

Few‑shot examples (serialized):
Example 1:
age is 62. sex is male. chest_pain_type is typical_angina.
resting_bp is 130. cholesterol is 250. fasting_blood_sugar is false.
resting_ecg is left_ventricular_hypertrophy. max_heart_rate is 150.
exercise_angina is true. oldpeak is 2.3.
Answer: Yes

Example 2:
age is 45. sex is female. chest_pain_type is asymptomatic.
resting_bp is 110. cholesterol is 180. fasting_blood_sugar is false.
resting_ecg is normal. max_heart_rate is 190.
exercise_angina is false. oldpeak is 0.0.
Answer: No

(… up to k = 4 examples …)

Reasoning instruction:
Step 1: Using your medical knowledge, list which features are generally indicative of chronic heart failure and why (do NOT look at the examples yet). Write them as short bullet points.

Step 2: Based on those relationships and on the few-shot examples above, write exactly ten deterministic if‑then rules for each class (“Yes” and “No”). Each rule must involve only one comparison per feature (e.g., “age > 60”, “cholesterol ≤ 200”, “sex = male”). Use logical AND only when necessary; do NOT use OR.

Response instruction:
For each class output a block that starts with “Rules for Yes:” (or “Rules for No:”) followed by ten lines numbered 1–10. Each line must be of the form
```
<feature> <operator> <value>
```
where <operator> is one of `>`, `<`, `<=`, `>=`, `=` or `!=`. Do not add any extra text.

```

When this prompt is sent to GPT‑3.5‑turbo we obtain a response such as:

```
Rules for Yes:
1. age > 60
2. resting_bp >= 130
3. cholesterol > 240
4. fasting_blood_sugar = true
5. max_heart_rate <= 140
6. exercise_angina = true
7. oldpeak > 2.0
8. chest_pain_type = typical_angina
9. resting_ecg = left_ventricular_hypertrophy
10. sex = male

Rules for No:
1. age <= 55
2. cholesterol <= 200
3. max_heart_rate > 160
4. exercise_angina = false
5. oldpeak <= 0.5
6. chest_pain_type = asymptomatic
7. resting_ecg = normal
8. fasting_blood_sugar = false
9. sex = female
10. resting_bp < 120
```

Because we asked for exactly ten rules per class and forced each rule into a simple *feature operator value* template, parsing becomes a trivial string split; any minor wording variation (e.g., “greater than” vs “>”) can be handled by a second lightweight LLM call that converts natural language into valid Python expressions (as described in Section 3 of the paper).

---

### How spurious correlations are avoided

* In **Step 1** the model cannot see that column *“random_id”* happens to be correlated with the label in the four examples; it simply never mentions that column because it has no prior medical relevance.
* In **Step 2** it may still mention a column if Step 1 listed it as generally relevant; otherwise it will ignore it even if the few-shot data contain a coincidental pattern.
* The fixed rule count forces the model to be selective; if it tries to sprinkle many irrelevant conditions its output would exceed the required number of lines and would be rejected by our parser.

Thus, even though the LLM still sees the few‑shot examples, its *primary* source of information about which features matter comes from world knowledge supplied in Step 1, which acts as an inductive bias against spurious patterns.

---

### Summarising

*The two‑step reasoning instruction works because it separates prior knowledge from data‑driven adjustment.*  
The prompt format (basic description → Step 1 → Step 2 → strict response template) forces deterministic rule output rather than raw predictions and drastically reduces reliance on accidental correlations present in few-shot demonstrations.

This design lets FeatLLM extract interpretable binary features without any fine‑tuning; downstream training then only learns non‑negative weights for those features ($\mathrm{Eq.\,(2)}$ in the paper), yielding a fast linear classifier that can be used at inference time without further calls to the LLM.)

### What is the mathematical role of the non‑negative weight constraint in Eq. (2)?
Question:
The authors define the class logit as `logit_k^i = max(w_k, 0) · z_k^i` and then apply a softmax. Why is `max(w_k, 0)` (i.e., projecting weights onto the non‑negative orthant) necessary? Does it have any theoretical justification beyond preventing "negative evidence" from a rule, and how does it affect gradient updates during the few‑shot training of the linear model?
Answer:
In Eq. (2) the authors compute a class‑specific logit as  

\[
\text{logit}_{k}^{i}= \max (\mathbf w_{k},0)\,\cdot \mathbf z_{k}^{i},
\qquad 
\mathbf p^{i}= \operatorname{softmax}\bigl(\text{logit}_{1}^{i},\dots ,\text{logit}_{c}^{i}\bigr),
\]

where \(\mathbf z_{k}^{i}\in\{0,1\}^{R}\) is the binary vector indicating which of the \(R\) rules for class \(k\) are satisfied by sample \(i\).  
The factor \(\max(\mathbf w_{k},0)\) simply projects every component of the trainable weight vector \(\mathbf w_{k}\) onto the non‑negative orthant, i.e. it replaces any negative entry by zero before taking the dot‑product.

---

### Why the non‑negative projection is introduced

1. **Semantic meaning of a rule**  
   Each rule generated by the LLM is meant to be a *sufficient* condition for a class: “if this rule holds, the sample is more likely to belong to class \(k\)”.  
   Consequently a rule should never *decrease* the logit of its own class. By forcing its coefficient to be non‑negative, the model respects this interpretation: adding a satisfied rule can only increase (or leave unchanged) the probability of the associated class.

2. **Avoiding “negative evidence” across classes**  
   The authors also want to prevent a rule for class \(k\) from acting as a negative cue for some other class. Suppose a rule for class 1 were given a large negative weight; then every sample satisfying that rule would have its logit for class 1 reduced, and because soft‑max normalises across classes this would artificially boost the probabilities of the other classes. The projection eliminates this undesirable interaction and keeps each rule’s influence confined to its own class.

3. **A simple inductive bias that improves optimisation in few‑shot settings**  
   When only a handful of labelled examples are available, the linear model can easily over‑fit if it is allowed to assign arbitrary signs to the weights. By constraining weights to be \(\ge 0\) the hypothesis space is reduced dramatically (the feasible set becomes a convex cone). This regularisation effect is particularly valuable in low‑shot regimes because it limits the model’s ability to fit noise that may be present in the few training points.

---

### Theoretical perspective

From a probabilistic viewpoint, Eq. (2) can be seen as defining a *log‑linear* model over binary features:

\[
p(y=k \mid \mathbf z)=
\frac{\exp \bigl( \sum_{r=1}^{R} w_{k,r}^{+} z_{k,r} \bigr)}
     {\sum_{c'} \exp \bigl( \sum_{r'} w_{c',r'}^{+} z_{c',r'} \bigr)},
\qquad 
w_{k,r}^{+}= \max(w_{k,r},0).
\]

If we interpret each binary feature \(z_{k,r}\) as an indicator of a deterministic logical rule, then assigning non‑negative coefficients corresponds to assuming that each rule contributes *positively* to the log‑odds of its class. This is exactly the same assumption made by naïve Bayes classifiers when they treat each binary evidence as supporting rather than opposing a label. The projection therefore provides a principled way to encode this monotonicity without altering the likelihood function beyond restricting the parameter space.

---

### Effect on gradient updates

During training we minimise cross‑entropy loss w.r.t. \(\mathbf w_k\). Let \(L\) denote the loss for a single example and write \(g = \partial L / \partial (\max(\mathbf w_k,0))\); then by the chain rule

\[
\frac{\partial L}{\partial w_{k,r}} = 
\begin{cases}
g_r , & w_{k,r}>0,\\[4pt]
0 , & w_{k,r}<0,
\end{cases}
\]

because \(\max(w_{k,r},0)\) is flat (zero derivative) when \(w_{k,r}<0\). In practice this means that once a weight becomes negative it stops receiving gradient signals and stays at its current (negative) value; however, thanks to typical initialisation (e.g., small positive values or zero‑mean Gaussian), most weights start non‑negative and are pulled upward by positive gradients whenever their associated rule is satisfied in a training example belonging to class \(k\).

The optimisation therefore behaves like standard gradient descent on a *constrained* problem where all parameters are confined to \(w_{k,r}\ge 0\). Many deep‑learning libraries implement exactly this behaviour when you replace each weight by `torch.nn.functional.relu(w)` before using it: the forward pass applies the ReLU, and during back‑propagation gradients flow only through entries that are currently positive. Consequently learning remains efficient—no extra projection step is required—and the resulting solution automatically satisfies the desired non‑negativity property.

---

### Summary

The projection \(\max(\mathbf w_k,0)\) serves three linked purposes:

* it enforces that each LLM‑generated rule can only *support* its own class (no “negative evidence”),
* it provides an inductive bias that shrinks the hypothesis space and reduces over‑fitting when only few labelled samples are available,
* it yields a simple convex constraint that is naturally handled by back‑propagation (gradients pass only through positive weights).

Thus the non‑negative weight constraint is not an ad‑hoc trick but a principled design choice that aligns the linear downstream model with the semantics of rule‑based features and improves optimisation in the few‑shot training regime described in the paper.

### How is feature bagging applied to limit prompt size in FeatLLM?
Question:
The paper mentions using bagging to select a subset of features or instances for each trial, which helps with long prompts when datasets have many columns. I would like to know the exact algorithm: do they randomly sample a fixed number of columns per LLM query, and if so, how is consistency between training and inference maintained when different bags generate different rule sets? Also, how many features are typically sampled for a dataset with >100 attributes?
Answer:
**Answer**

In *FeatLLM* the “bagging” step is not a separate learning algorithm but a simple stochastic sub‑sampling that is applied **once per ensemble trial** in order to keep the prompt short enough to fit inside the LLM’s context window.  
The authors describe it in the *Ensembling with bagging* paragraph (Section 3) and in the experimental section where they discuss datasets with more than 100 attributes (e.g. *Communities* and *Myocardial*).

### What is sampled?

For each trial $t$ (they use $T=20$ trials in all experiments) they draw

* **a random subset of the original feature columns** – let the full set of column names be $F=\{f_{1},\dots ,f_{d}\}$.  
  They uniformly sample without replacement a smaller set  
  $$ 
  F^{(t)} \subseteq F,\qquad |F^{(t)}| = d_{\text{bag}},
  $$ 
  where $d_{\text{bag}}$ is chosen so that the serialized description of the selected columns plus the few‑shot examples stays comfortably below the model’s maximum token limit (roughly 4 k tokens for GPT‑3.5‑turbo).  

* **optionally a random subset of the few‑shot training instances** (the paper calls this “instances” as well). The order of these examples is also shuffled, because LLMs are known to be sensitive to demonstration order.

The two sampling operations are independent: a trial may see only a fraction of the columns, and only a fraction of the labelled rows, but each trial still receives **all class labels** and the same *task description*.

### How is consistency maintained between training and inference?

The only part of the pipeline that needs to be consistent across training and test time is the **parsing of rules into binary features**. Because each trial produces its own rule set $\mathcal{R}^{(t)}=\{r^{(t)}_{k,1},\dots ,r^{(t)}_{k,R}\}$ for every class $k$ (the paper fixes $R=10$ rules per class), those rules are stored together with the corresponding linear weights $\mathbf w^{(t)}$ learned on the *training* samples that were also drawn with the same bagged feature set.  

When a new test sample arrives, FeatLLM repeats exactly the same *parsing* step for **each trial**:

1. The test row is fed through the code generated by the LLM for that trial (the code implements all $R$ rule evaluations).  
2. This produces a binary vector $\mathbf z^{(t)}_{k}\in\{0,1\}^{R}$ for each class.  
3. The stored non‑negative weight vector $\mathbf w^{(t)}_{k}$ is then applied, giving logits $\text{logit}^{(t)}_{k}= \max(\mathbf w^{(t)}_{k},0)\cdot\mathbf z^{(t)}_{k}$.  

Finally, logits are turned into probabilities with softmax and averaged over all trials, as described in Eq. (2) of the paper:
$$
\mathbf p = \frac{1}{T}\sum_{t=1}^{T}\operatorname{Softmax}
\bigl(\text{logit}^{(t)}_{1},\dots ,\text{logit}^{(t)}_{c}\bigr).
$$

Because each trial carries its own *self‑consistent* rule set and its own weight vector, there is no requirement that different trials agree on which original columns they used. The ensemble simply averages their predictions; if a rule depends on a column that was omitted in a particular trial, that trial contributes nothing for that rule, but other trials that did see the column can still provide useful evidence.

### How many columns are sampled for large tables?

The exact number $d_{\text{bag}}$ is not fixed in the paper; it is chosen implicitly by the “prompt‑size budget”. In practice the authors report using **about 30–40 columns per trial** for datasets with more than 100 attributes. This figure comes from two observations:

* The prompt already contains a *feature‑description block*, which lists each selected column together with its type and optional definition.  
* Adding 10 rules per class (the default) consumes roughly 200–300 tokens after formatting.

Empirically, when they keep the total token count around 3 500–4 000 tokens (well under GPT‑3.5‑turbo’s 4 096 token limit), they can fit ≈30–40 column descriptions together with the few‑shot examples and reasoning instructions. The experiments in Section 4.2 (datasets such as *Communities* with 122 attributes) confirm that this setting works reliably; increasing $d_{\text{bag}}$ beyond ≈45 begins to trigger truncation errors, while reducing it dramatically lowers performance because too few informative columns are presented to the LLM.

### Summary

* **Algorithm:** For each ensemble iteration draw a random subset of columns (≈30–40 when $d>100$) and optionally a random subset/shuffled order of few‑shot rows; build a prompt containing those column descriptions plus demonstrations; ask the LLM to generate a fixed number ($R=10$) of rules per class; parse those rules into binary features; train a non‑negative linear model on the same bagged training rows; repeat for $T=20$ trials.
* **Consistency:** The rule set and its learned weights are saved per trial; at inference time each trial re‑applies its own rules to every test sample and the resulting class probabilities are averaged.
* **Typical sample size:** Around thirty to forty columns per trial for datasets with > 100 attributes; this respects the token limit while still providing enough information for high‑quality rule extraction.

Thus feature bagging in FeatLLM is essentially “random feature sub‑sampling per ensemble member”, used solely to control prompt length while preserving an unbiased, ensemble‑based estimator at test time.

### Why does the paper use a linear model without bias after rule generation?
Question:
After converting rules into binary features `z_k^i`, FeatLLM fits a simple linear model (no bias term) to predict class probabilities. Is there an empirical or theoretical reason for omitting the bias? Would adding a bias term improve performance on imbalanced classes, or is it omitted to keep interpretability of rule importance?
Answer:
In **FeatLLM** the downstream model is deliberately kept as simple as possible because its only job is to turn the binary rule‑features $\mathbf{z}^{i}_{k}$ into a class‑score.  After the LLM has produced a set of logical conditions, each condition either **holds** (value = 1) or **does not hold** (value = 0) for a given sample.  Consequently the model’s output should be a *monotone* function of the number of satisfied rules: the more rules that fire for a particular class, the larger that class’s likelihood should become.  

The authors achieve this monotonicity by

1. **Constraining the weights to be non‑negative** ($\mathbf{w}_{k}\ge 0$).  
2. **Omitting a bias term**, i.e. using the logit
   $$
   \text{logit}^{i}_{k}= \max(\mathbf{w}_{k},0)\cdot\mathbf{z}^{i}_{k},
   $$
   rather than $\text{logit}^{i}_{k}=b_{k}+ \max(\mathbf{w}_{k},0)\cdot\mathbf{z}^{i}_{k}$.

With a bias, a class could receive a *positive* logit even when none of its rules are satisfied, which would contradict the intended interpretation of the rule‑features (“no rule satisfied ⇒ low probability”).  Moreover, a negative bias could suppress the contribution of genuinely informative rules, making the learned importance harder to interpret because part of the effect would be absorbed by the intercept rather than by the rule weights themselves.

From an **interpretability** standpoint this design means that each learned weight directly reflects how much that particular rule contributes to increasing the class probability; there is no hidden offset that must be disentangled from the rule effects.  This aligns with the paper’s claim that “the weight … signify(s) the importance of each feature” and that “by projecting these weights into a positive subspace, we can ensure that the features generated by the LLM do not reduce the likelihood of a class during learning”.

There is also an **empirical** motivation.  In the low‑shot regime used throughout the experiments (as few as 2–8 labeled examples), adding a bias term introduces an extra parameter per class that must be estimated from very little data.  The extra degree of freedom can easily lead to over‑fitting or unstable estimates, especially when many rules are generated (the paper uses ten rules per class).  The ablation study in §4.2 shows that removing weight tuning (which would implicitly correspond to fixing all weights—including any bias—to a uniform value) degrades performance, while keeping only the non‑negative weighted sum works well even with few shots.

Finally, dropping the bias does not hurt performance on imbalanced data because class‑specific priors are already handled by the **softmax** normalisation over all logits.  If one class is rare, its logits will tend to be lower unless many of its rules fire; this behaviour is precisely what we want—high confidence should arise only when several class‑specific conditions are met.

In summary, the bias term is omitted both to preserve a clean, monotonic interpretation of rule importance and to avoid introducing an unnecessary parameter that could degrade performance in few‑shot settings. Adding a bias would not meaningfully help with class imbalance and would compromise interpretability; therefore the paper’s design choice is both theoretically justified and empirically validated.

### Clarification on parsing noisy rule text using an LLM (Section 3.2)
Question:
The authors state that instead of writing a complex parser they feed the natural‑language rules back to the LLM to generate Python code that implements them. How is this second‑stage prompting designed to ensure correct translation (e.g., handling variations like "greater than" vs ">")? Are there safeguards against code injection or runtime errors when executing `exec()` on generated code?
Answer:
In **FeatLLM** the “second‑stage” prompt is the one that turns the natural‑language rules produced by the LLM into executable Python code.  
The authors deliberately avoid writing a brittle hand‑crafted parser because, as they point out in §3.2, the LLM’s output can be noisy—e.g. it may write “greater than” instead of the symbol “>”, or introduce extra whitespace, parentheses, or even reorder the clauses.  Rather than enumerate all possible surface forms they let the LLM do the parsing for them.

### How the second‑stage prompt is built

1. **Structured request** – The prompt contains three explicit sections (Fig. 4 in the paper and the Appendix).  
   *A short pre‑amble* tells the model that it must generate a **function** called `rule_i(x)` that receives a row `x` (a `dict` mapping feature names to values) and returns `True`/`False`.  
   *The description of each feature* (type, allowed categories, numeric ranges) is repeated verbatim from the first‑stage prompt so that the model knows whether a feature is numeric, categorical, etc.  
   *The list of inferred rules* is given exactly as they appeared in the first stage.

2. **Explicit formatting instructions** – The prompt tells the LLM to emit only valid Python statements and to use a canonical representation for comparisons:
   * For numeric features write `x["age"] > 45` (or `<`, `<=`, `>=`).
   * For categorical features write `x["sex"] == "female"` (or `in [...]` for multi‑valued checks).
   * No additional text, comments or print statements are allowed.

3. **Example snippet** – A tiny example of a finished function is supplied in the prompt so that the model can copy the surrounding boilerplate (`def rule_1(x): ... return ...`).  Because GPT‑3.5 has been trained on large code corpora, it reliably maps “greater than” → `>` and “less than or equal to” → `<=` when instructed to produce code.

4. **Deterministic post‑processing** – After receiving the model’s answer the authors perform a very lightweight sanity check: they verify that each line matches a regular expression of the form  
   `x\["([^"]+)"\]\s*([<>]=?|==|in)\s*.+`.  
   If a line fails this test or contains a prohibited token (e.g., `import`, `open`, or ```) they discard the whole rule and replace it with a constant‑false stub (`return False`).  This eliminates obvious injection attempts while keeping the pipeline fully automatic.

### Why this works

Because the LLM is asked *“given these rules, write a function that evaluates them”* it can rely on its internal code generation ability rather than on brittle string matching.  The chain‑of‑thought style instruction (“first think about how to translate each condition into Python, then output a single function”) encourages it to be faithful to each rule even when synonyms are used (“greater than” → `>`).  The fixed number of rules per class (10) also bounds the amount of generated code, making verification cheap.

### Safeguards against code injection and runtime errors

* **Prompt‑level constraints** – The response instruction explicitly forbids any import statements, file I/O, or calls to built‑ins other than basic operators.  
* **Whitelist of tokens** – After generation, a whitelist of allowed Python tokens (`[` `]` `{` `}` `(` `)` `>` `<` `==` `in` literals) is applied; any token outside this list triggers replacement with a safe dummy function.  
* **Execution sandbox** – The generated functions are executed with Python’s built‑in `exec()` inside an empty dictionary for globals and locals:  

```python
globals_dict = {}
locals_dict = {}
exec(generated_code, globals_dict, locals_dict)
rule = locals_dict["rule_1"]
```

  Because no external modules are available in `globals_dict`, even if a malicious snippet slipped through it cannot reach the filesystem or network.  

* **Runtime exception handling** – Each rule is wrapped in a try/except block automatically by the prompt (`try: … except Exception: return False`).  Consequently, any unexpected type error (e.g., comparing a string with a number) simply yields a *False* result rather than crashing the whole pipeline.

Together these measures ensure that syntactic variations such as “greater than”, “>”, “is larger than”, etc., are consistently translated into correct Python comparison operators, while preventing harmful code from being executed and keeping runtime failures from propagating.

In short, FeatLLM’s second‑stage prompting leverages the LLM’s own code‑generation competence, reinforces it with strict response formatting and lightweight lexical checks, and finally confines execution to a minimal sandbox—thereby achieving reliable translation of noisy natural‑language rules into safe executable features.

### What does "self‑consistency" refer to in the context of FeatLLM ensembles?
Question:
The ensemble method relies on generating multiple rule sets with high temperature and random demo ordering, and the authors claim this leverages LLM self‑consistency. Could someone explain what self‑consistency means here, and whether any quantitative metric (e.g., overlap of rules across trials) was measured to validate that more consistent rules are indeed more accurate?
Answer:
**Self‑consistency in FeatLLM refers to the idea that, when an LLM is asked to produce a rule set for the same task several times under slightly different prompting conditions, the rules that appear repeatedly are more likely to be correct.**  

In the paper the authors generate an *ensemble* of rule‑based learners by querying the LLM many times with a *high temperature* (so the model samples diverse continuations) and by randomly shuffling the order of the few‑shot demonstrations that appear in the prompt. Each query yields a collection of ten binary rules per class; these rules are turned into features, a tiny linear model is trained on the few labeled examples, and the predictions of all $T$ such models are averaged (Eq. $(2)$).  

The term “self‑consistency” is borrowed from Wang et al. 2022, where it describes a simple consistency‑based decoding strategy: run the model multiple times, collect all its answers, and take the majority vote (or a weighted aggregate). The intuition is that an LLM’s stochastic output contains many internally consistent “reasoning paths”. If a particular answer (or rule) survives many independent samplings, it is likely backed by the model’s internal knowledge rather than by accidental wording or by spurious correlations present in one particular prompt.

In FeatLLM this principle is applied at the *feature‑engineering* level:

1. **Diverse prompts** – By raising temperature to $0.5$ and randomly reordering the demonstrations, each run forces the LLM to explore a different part of its latent knowledge graph.  
2. **Rule aggregation** – Across the $T$ ensemble runs, rules that are generated repeatedly will generate binary features that are activated for many training examples. When the downstream linear model learns non‑negative weights, those frequently occurring rules tend to receive larger weights because they consistently explain the labels.  
3. **Robust final prediction** – The ensemble averages the class probabilities obtained from each rule set; errors made by one noisy rule set are diluted by other, more reliable rule sets.

The authors do not introduce an explicit numeric “self‑consistency score” such as a Jaccard index of rule overlap between trials. Instead they rely on two indirect pieces of evidence that demonstrate the effect:

* **Ablation of the ensemble** – Table 2 shows that removing the ensemble (“‑Ensemble”) consistently degrades $ \text{AUC} $ across datasets, confirming that aggregating multiple stochastic rule generations improves accuracy.
* **Analysis of useful features** – In Section 4.2 they report that before weight tuning roughly $70\text{–}80\,\%$ of generated rules have $ \text{AUROC} > 0.5 $ (i.e., are informative). After learning, only a small fraction of rules retain negligible weight, indicating that inconsistent or noisy rules are automatically down‑weighted.

Thus “self‑consistency” in FeatLLM is used as a qualitative guiding principle: repeated generation of similar rules across stochastic LLM runs signals higher reliability, and the ensemble mechanism operationalises this principle by averaging over many such runs. The paper validates its usefulness empirically through ablation studies and feature‑importance statistics rather than through a dedicated overlap metric.

### How is the number of rules per class (R=10) chosen and what happens if R is larger?
Question:
The paper fixes R=10 rules per class after some analysis (Section 4.2). I am curious about the trade‑offs: does increasing R lead to overfitting due to high dimensional binary features in low‑shot regimes, or does it simply increase prompt length without performance gain? Is there any recommendation for adjusting R based on dataset size or feature cardinality?
Answer:
In **FeatLLM** every class is represented by a short list of logical conditions (“rules”) that the LLM produces in a single query.  The number of rules per class, denoted by **R**, is therefore a direct trade‑off between the amount of information that can be encoded in the binary feature vector \( \mathbf{z}_k \in\{0,1\}^{R}\) and the size of the prompt that the LLM has to handle.

### Why the authors settled on **R = 10**

The paper reports a small hyper‑parameter search (Section 4.2 and Fig. 7) where two opposing effects were observed:

1. **Prompt length** – Each rule has to be spelled out in natural language, parsed, and turned into executable code.  Adding more rules linearly inflates the LLM request (the “basic information” + “reasoning” + “response” sections).  When \(R\) grows beyond about ten, the generated prompt approaches the model’s context‑window limit for many of the larger data sets (e.g., *Communities* and *Myocardial* with > 100 original columns).  Once the window is exceeded the query fails or forces truncation, which harms rule quality.

2. **Low‑shot over‑fitting** – The downstream linear model learns a non‑negative weight for each binary rule (Eq. 3).  In a few‑shot regime the number of training points is tiny (often ≤ 8).  With more than ten binary features per class there is insufficient signal to reliably estimate all weights, so some rules receive spurious large weights that actually hurt performance.  The authors observed a slight degradation of AUC when \(R\) was increased to 15 or 20, especially for the smallest‑shot settings.

Because both effects become noticeable around ten rules, the authors selected \(R=10\) as a sweet spot: it provides enough expressive power to capture the most salient criteria for each class while keeping prompts comfortably within the context window and keeping the downstream linear model well‑conditioned.

### What happens if you increase **R**

- **Longer prompts** – The LLM query length grows roughly as \(O(R)\).  If you push \(R\) to 20–30 you will quickly hit the token limit on models such as GPT‑3.5‑turbo (≈ 4 k tokens).  In practice this forces you either to truncate the prompt (dropping earlier rules or feature descriptions) or to split the query into multiple calls, which defeats the purpose of a single‑shot feature extraction and adds latency.

- **Higher‑dimensional binary vector** – The downstream feature matrix becomes \(\mathbf{Z}\in\{0,1\}^{N\times(Rc)}\).  In a low‑shot setting this extra dimensionality can lead to **overfitting** because the linear model now has more parameters (\(Rc\) non‑negative weights) than effective training examples.  Empirically (Fig. 7) the gain in AUC flattens after \(R=10\) and even turns negative when \(R\) exceeds ≈ 15 on datasets with ≤ 8 shots.

- **Potential marginal gains** – For problems where each class truly depends on many independent conditions (e.g., a medical diagnosis that requires dozens of lab thresholds), a larger \(R\) can sometimes capture additional useful signals, but only if you also increase the number of shots or apply stronger regularisation (e.g., \(\ell_{1}\) penalty on \(\mathbf{w}\)).  The paper does not explore this regime; their experiments suggest that any benefit is outweighed by the drawbacks mentioned above.

### Practical recommendation

- **Stick with \(R=10\)** for typical few‑shot experiments (2–8 shots) and for most benchmark tabular data sets used in the paper.
- If you have **more labeled examples** (say ≥ 32 shots) and your target task genuinely needs many conditions, you may try raising \(R\) modestly (12–15) while monitoring validation AUC and ensuring that total prompt tokens stay below the model’s context limit.
- When you need **more expressive rules** but cannot afford a larger prompt, use **more ensembles** (increase \(T\)) rather than increasing \(R\).  Each additional ensemble draws a fresh set of ten rules from the LLM; aggregating many such weak learners effectively expands the feature space without blowing up any single prompt.

In short, \(R=10\) was chosen because it balances prompt feasibility with statistical stability in low‑shot regimes. Raising \(R\) mainly inflates prompt size and invites overfitting; any performance gain would have to be earned by providing substantially more training data or stronger regularisation.
