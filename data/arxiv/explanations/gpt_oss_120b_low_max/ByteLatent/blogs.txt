# Why Tokens Are Out, and Patches Are In: The Rise of Byte‑Level Language Models

Large language models (LLMs) have become the workhorse behind chatbots, code assistants, and countless AI‑powered tools. Yet, almost every LLM we use today still relies on a hidden pre‑processing step: **tokenization**. A tokenizer chops raw text into a fixed vocabulary of sub‑word “tokens” before any neural computation ever begins. This hidden layer may look harmless, but research is increasingly showing that it drags down efficiency, fairness, and robustness.  

Enter the **Byte Latent Transformer (BLT)** – a new architecture that throws the tokenizer out the window and lets the model decide **how to group raw bytes into “patches.”** In this post we’ll unpack why traditional tokenizers are problematic, how BLT’s entropy‑driven patching works, and what this shift means for everyday users of LLMs.

---

## The Tokenizer Problem: Bias, Inequity, and Fragility

### 1. Heuristic Compression Bias  
Tokenizers are built on heuristics (BPE, WordPiece, etc.) that try to compress text into a manageable vocabulary. Those heuristics are tuned on *specific* data mixes and languages. As a result:

* **Domain sensitivity** – A tokenizer trained mostly on English web text will split code snippets or scientific formulas in unintuitive ways, hurting downstream performance.
* **Multilingual inequity** – Languages with rich morphology (e.g., Turkish, Hindi) end up with many more tokens per word than English, inflating compute for those languages.

### 2. No Direct Access to Raw Bytes  
When a model receives tokens, the underlying byte sequence is hidden behind an embedding lookup. The model never sees the actual characters; it can only infer patterns indirectly. This makes it hard for the model to learn *orthographic* knowledge (spelling rules, character‑level phonology) that is crucial for low‑resource languages or tasks like grapheme‑to‑phoneme conversion.

### 3. Fragile to Noise  
Because tokenizers produce a *deterministic* mapping from bytes to tokens, any small perturbation—extra spaces, random character drops, or case changes—can dramatically change the token sequence. The downstream model then sees an entirely different input and often fails spectacularly.

All of these issues are baked into every LLM that still uses a static tokenizer.

---

## Patches Instead of Tokens: Letting the Model Choose

BLT replaces the static tokenizer with a **dynamic patching** mechanism that groups consecutive bytes **on the fly**. The key insight is simple: *not all bytes are equally hard to predict.*  

### Entropy‑Based Patch Boundaries  

1. **Train a tiny byte‑level LM** (≈100 M parameters) on the same data distribution as the main model.  
2. For each position *i* in a document, compute the **next‑byte entropy**  

   \[
   H(x_i)= -\sum_{v\in\mathcal{V}} p_e(x_i=v \mid \mathbf{x}_{<i}) \log p_e(x_i=v \mid \mathbf{x}_{<i})
   \]

   where \(p_e\) is the tiny LM’s distribution over the 256 possible byte values.
3. When scanning a sequence during preprocessing, **start a new patch** whenever:
   * The entropy exceeds a global threshold \(\theta_g\), **or**
   * The entropy jumps significantly relative to its predecessor (\(H(x_t)-H(x_{t-1})>\theta_r\)).
4. The resulting patches have *roughly uniform information density*: low‑entropy regions (e.g., long runs of spaces or predictable code symbols) become long patches; high‑entropy regions (the first character of a new word, rare Unicode symbols) become short patches.

Because the patching decision depends only on past bytes, it works **incrementally**—the model can decide during generation without looking ahead.

### Why Entropy Matters

Entropy directly measures how uncertain the next byte is under a language model that already knows everything that came before. High entropy signals “hard” predictions that deserve more modeling capacity; low entropy signals “easy” predictions where we can safely skip expensive computation.

---

## How BLT Uses Patches

BLT’s architecture consists of three parts:

1. **Local Encoder** – A lightweight transformer that ingests raw bytes (augmented with cheap n‑gram hash embeddings) and produces *latent patch embeddings*. Cross‑attention pools each patch’s bytes into a single vector.
2. **Latent Global Transformer** – A full‑size autoregressive transformer that only sees one vector per patch. Because patches can be several bytes long on average (4–8 bytes in experiments), the global transformer processes far fewer steps than a token‑based model.
3. **Local Decoder** – Another light transformer that expands each latent patch back into raw bytes for final output.

The bulk of FLOPs resides in the global transformer; by reducing the number of steps (thanks to longer patches), BLT saves up to **50 % inference FLOPs** while keeping performance on par with Llama 3 at comparable scales.

---

## What This Means for Users

| Issue | Tokenizer‑Based LLMs | BLT Patch‑Based LLMs |
|------|----------------------|----------------------|
| **Compute Efficiency** | Fixed FLOPs per token → wasteful on easy regions | Dynamic FLOPs: longer patches → fewer transformer steps |
| **Multilingual Fairness** | Vocabulary size fixed; languages with many morphemes get penalized | No fixed vocabulary → every language treated uniformly at byte level |
| **Robustness to Noise** | Small perturbations change tokenization → catastrophic errors | Model sees raw bytes; minor edits only affect local entropy → graceful degradation |
| **Character‐Level Understanding** | Implicit; often missing spelling/phonology knowledge | Direct byte access + n‑gram hashing → strong performance on G2P & orthographic tasks |
| **Scaling Flexibility** | Token size limited by vocabulary trade‑off (larger vocab → bigger embedding matrix) | Patch size independent; can grow both model parameters and average patch length under a fixed inference budget |

In practice this translates to:

* **More reliable chat experiences:** Users typing with accidental typos or unconventional formatting will see fewer nonsensical replies.
* **Better support for low‑resource languages:** Because there’s no “vocabulary gap,” BLT learns to model rare scripts directly from bytes.
* **Lower cost inference:** Deployers can run larger models without proportionally higher GPU time—critical for real‑time applications.

---

## Real‑World Results

A series of controlled experiments demonstrate BLT’s promise:

* **Scaling parity:** An 8 B parameter BLT matches Llama 3’s bits‑per‑byte (BPB) scores while using ~50 % fewer inference FLOPs.
* **Robustness gains:** On noisy variants of HellaSwag and CUTE benchmarks, BLT outperforms tokenized baselines by 8–25 points.
* **Long‑tail generalization:** In low‑resource machine translation (FLORES‑101), BLT gains 0.5–2 BLEU points over Llama 3 across dozens of underrepresented languages.
* **Patch scaling advantage:** With average patch size = 8 bytes (vs. ~4 bytes for BPE tokens), BLT can simultaneously increase global transformer depth while staying within a fixed compute budget—something impossible with static vocabularies.

These findings suggest that “patches scale better than tokens,” exactly as the paper’s title claims.

---

## Looking Ahead

BLT opens several exciting research directions:

1. **End‑to‑end learnable patching:** Currently patches are derived from a separate entropy model; training patch boundaries jointly with the main model could further improve efficiency.
2. **Distilling existing LLMs:** Initial experiments show that initializing BLT’s global transformer from a pre‑trained tokenizer model yields strong performance with far fewer training FLOPs—a potential shortcut for migrating existing models.
3. **Hardware optimizations:** While FLOP counts are favorable, current libraries are tuned for tokenized pipelines; specialized kernels for dynamic cross‑attention could close any remaining wall‑clock gaps.

For practitioners, the takeaway is clear: if you care about cost, fairness across languages, or resilience to noisy user input, it’s time to look beyond static tokenizers and consider patch‑based byte models like BLT.

---

## TL;DR

* Traditional tokenizers introduce bias, inefficiency, and fragility because they impose a static vocabulary on raw text.
* BLT dynamically groups bytes into *patches* based on next‑byte prediction entropy—allocating more compute where it matters most.
* This results in up to 50 % inference FLOP savings, stronger character‐level abilities, and better multilingual robustness—all while matching state‑of‑the‑art tokenized models at scale.
* For anyone building or deploying LLMs today, patches aren’t just an academic curiosity—they’re an emerging paradigm poised to replace tokens in future AI systems.



# Dynamic Patching Explained: From Fixed‑Size Strides to Entropy‑Driven Byte Groups  

Large language models have relied on tokenizers for decades.  A tokenizer simply groups raw bytes into a fixed vocabulary of sub‑word tokens, and the model then spends the same amount of computation on every token.  The **Byte Latent Transformer (BLT)** challenges that paradigm by operating directly on bytes and, crucially, by **dynamically grouping those bytes into patches**.  In this post we break down the three patching strategies investigated in the BLT paper—static‑stride, whitespace (space) patching, and entropy‑driven patching—show how they work, where each shines, and why the entropy approach is a data‑driven way to allocate compute where it matters most.

---

## Why Patching Matters  

A Transformer’s cost is dominated by its feed‑forward (FFN) layers, whose FLOPs scale linearly with the number of *steps* the model processes.  When we work at the byte level, a typical text of a few hundred words can expand to **hundreds of thousands of bytes**, turning each byte into a separate step and blowing up FLOPs.

**Patching** is the answer: we compress a contiguous run of bytes into a single *patch* representation and feed that to the global latent transformer.  The average patch size (bytes per patch) directly controls inference cost:

\[
\text{Inference FLOPs} \propto \frac{1}{\text{average patch size}} .
\]

The challenge is to decide *where* to cut patches so that we preserve information while still shrinking the sequence length.  BLT explores three ways to draw those boundaries.

---

## 1. Static‑Stride (Strided) Patching  

### How it works  
The simplest scheme groups every **K** consecutive bytes into one patch, regardless of content:

| Bytes | … | b₁ | b₂ | … | bₖ | bₖ₊₁ | … |
|-------|---|----|----|---|----|-------|---|
| Patch | … | p₁      | p₂   | … |

Formally, a binary mask marks the start of a new patch every K bytes.  This yields a *fixed* average patch size of K.

### When it’s useful  
- **Implementation simplicity:** No preprocessing beyond slicing; training pipelines need no extra logic.  
- **Deterministic FLOP budgeting:** Because K directly sets the number of patches, you can precisely control compute.  

### Drawbacks  
- **No adaptivity:** Easy-to-predict regions (e.g., long runs of whitespace or repetitive code) still consume a full transformer step, while high‑entropy regions (e.g., mathematical expressions) may be under‑represented.  
- **Inconsistent tokenization of identical substrings:** The same word can be split differently depending on its position in the stream, harming model consistency.

Static stride was used in MegaByte (2023) and serves as a useful baseline but falls short when scaling beyond modest model sizes.

---

## 2. Whitespace (Space) Patching  

### How it works  
Instead of a blind stride, *space patching* creates a new patch after any “space‑like” byte—characters that are not Latin letters, digits, or UTF‑8 continuation bytes (essentially punctuation, spaces, line breaks).  The rule guarantees that each patch contains at least one non‑space character, making patches align roughly with linguistic units such as words.

```
… "Who", " ", "composed", " ", "the", " ", "Magic", " ", "Flute?" …
```

### When it’s useful  
- **Linguistically motivated boundaries:** Words are natural break points; the first character of a word usually carries high uncertainty, so allocating a transformer step there is sensible.  
- **Consistent grouping:** The same word will always belong to the same patch across different contexts, improving stability.

### Drawbacks  
- **Language bias:** Not all scripts use clear “space” characters (e.g., Chinese, Japanese).   
- **Fixed granularity:** While better than static stride, space patching still cannot shrink patches in highly predictable regions (e.g., long runs of spaces or commas).  

Space patching was introduced by *SpaceByte* (2024) and brings a modest efficiency gain over pure striding but still leaves room for a more fine‑grained approach.

---

## 3. Entropy‑Driven Patching  

### Core idea  
Prediction difficulty varies dramatically across a document.  If we can *measure* how uncertain the next byte is, we can let high‑entropy positions start new patches and let low‑entropy regions stay together longer.  This yields an *adaptive* patch size that mirrors information density.

### Computing next‑byte entropy  

1. Train a tiny byte‑level autoregressive LM (the **entropy model**) on the same data.  
2. For each byte \(x_i\), compute its Shannon entropy under the model’s distribution \(p_e\):

\[
H(x_i) = -\sum_{v \in \mathcal{V}} p_e(x_i=v \mid \mathbf{x}_{<i}) \log p_e(x_i=v \mid \mathbf{x}_{<i}) .
\]

3. Scan through the sequence and place a boundary whenever \(H(x_i)\) exceeds a chosen threshold or when it spikes relative to its predecessor:

\[
\begin{aligned}
\text{Global threshold:} & \quad H(x_t) > \theta_g ,\\
\text{Relative spike:} & \quad H(x_t) - H(x_{t-1}) > \theta_r .
\end{aligned}
\]

The second rule captures *approximate monotonicity*: within a patch entropy should generally decline as the model consumes more context; any reversal signals a new difficult point.

### Advantages  

| Property | Entropy Patch vs Fixed/Space |
|----------|------------------------------|
| **Compute allocation** | More steps where predictions are hard; fewer steps where they are easy |
| **Average patch size** | Data‑driven; can reach > 6 bytes on predictable code or prose |
| **Cross‑language robustness** | Works even when “space” isn’t meaningful; entropy reflects any language’s predictability |
| **Incrementality** | Boundaries depend only on past bytes (the entropy model’s context), satisfying incremental patching required for generation |

Because boundaries are determined *offline* during data loading (a cheap preprocessing pass), there is no runtime overhead beyond looking up pre‑computed masks.

### Practical considerations  

- **Entropy threshold selection:** BLT calibrates \(\theta_g\) or \(\theta_r\) to hit a target average patch size (e.g., 4.5 bytes).  
- **Context drift:** If the entropy model’s context window is too short, repeated patterns can artificially lower entropy (“entropy drift”). BLT mitigates this by resetting the entropy model’s context at line breaks and using the relative spike rule.  
- **Model size for entropy estimator:** Experiments show that an entropy LM with ~50 M parameters already provides strong signals; bigger models give diminishing returns.

Overall, entropy-driven patches let BLT *spend compute where it counts*, leading to up to ~50 % fewer inference FLOPs compared with tokenizers while preserving or even improving downstream performance.

---

## Putting It All Together: Why Entropy Wins  

The three strategies form a spectrum from naïve uniformity to fully data‑aware adaptivity:

1. **Static stride** → uniform compute distribution → simple but wasteful.  
2. **Whitespace** → linguistically motivated but still coarse and language dependent.  
3. **Entropy-driven** → fine-grained, language agnostic, and directly tied to prediction difficulty.

In BLT’s scaling experiments:

- Models with entropy patches **matched or outperformed** tokenization baselines (Llama 3) at comparable FLOP budgets.
- Larger average patches (6–8 bytes) yielded up to **50 % inference FLOP reduction**, allowing simultaneous growth of the global latent transformer without exceeding a fixed inference budget.
- Downstream tasks requiring fine character understanding—such as orthographic manipulation (CUTE), phoneme conversion, and low‑resource translation—benefited most from entropy-driven grouping.

Thus, entropy-based patching offers a principled way to *compress* raw byte streams without sacrificing information: it respects the true information density of language rather than an arbitrary heuristic.

---

## Takeaways for Practitioners  

- If you’re experimenting with byte‑level LLMs and care about efficiency, start with **entropy-driven patching**; it only requires training an inexpensive auxiliary LM.  
- For multilingual corpora or domains lacking clear whitespace cues, entropy is especially advantageous because it doesn’t hinge on script conventions.  
- When hardware constraints force you to keep inference FLOPs low, increase average patch size via higher entropy thresholds—BLT’s architecture naturally reallocates saved compute to expand the global transformer.

---

## Looking Ahead  

Entropy-driven dynamic patching opens several research directions:

- **End‑to‑end learned boundaries**: Replace the separate entropy LM with a boundary predictor trained jointly with the main model.
- **Adaptive thresholds**: Let the model learn per‑layer or per‑domain thresholds instead of fixing \(\theta_g,\theta_r\).
- **Hybrid schemes**: Combine whitespace cues with entropy spikes for even faster preprocessing on highly structured data like source code.

As LLMs continue to scale, smarter ways to allocate compute will become as important as raw parameter counts. Dynamic patching—especially when driven by actual prediction uncertainty—offers an elegant path forward toward faster, more robust language models that no longer need an external tokenizer.

---

---

# Scaling Language Models Without Tokens: How BLT Matches Llama 3 With Fewer FLOPs  

*In this post we unpack the scaling experiments from the “Byte Latent Transformer (BLT)” paper. We’ll see how a token‑free architecture can keep up with Llama 3 – even at 8 B parameters – while shaving off up to half the inference FLOPs. The goal is to make the key ideas and results accessible, using intuitive analogies and simple graphics (described in words).*

---  

## 1️⃣ Why Bother Getting Rid of Tokens?  

Traditional large language models (LLMs) start by chopping text into **tokens** – fixed pieces of characters learned by a separate tokenizer. Tokens work well, but they introduce three hidden costs:

| Issue | What it looks like today | Why it matters |
|------|--------------------------|----------------|
| **Static compute budget** | Every token, whether it’s a common word like “the” or a rare symbol, gets the same amount of model work. | Easy cases waste compute; hard cases get too little. |
| **Vocabulary bias** | Tokenizers are built on heuristics that favor high‑resource languages and clean text. | Low‑resource languages, code, or noisy inputs suffer. |
| **Fixed vocabulary** | The model never sees bytes that fall outside the token set. | Long‑tail bytes (rare Unicode characters, misspellings) are poorly modeled. |

If we could **allocate compute where it’s actually needed** and let the model work directly on raw bytes, we could potentially get more bang for our buck.

Enter **BLT (Byte Latent Transformer)** – a model that never tokenizes. Instead, it groups consecutive bytes into **patches** whose size is decided *on the fly* based on how uncertain the next byte is. Think of patches as “dynamic words” that stretch when the text is predictable (e.g., long runs of spaces) and shrink when every character matters (e.g., the first letter of a new sentence).

---  

## 2️⃣ Patches vs. Tokens: The Core Trade‑off  

### Visual analogy  

Imagine you’re driving through a city with a fuel gauge that only shows mileage per mile, not per block. A token‑based LLM always drives at full speed for every block, regardless of traffic. A patch‑based BLT looks ahead: if traffic is light (low entropy), it cruises in “long‑stride” mode, covering many blocks with one step; if traffic is jammed (high entropy), it switches to “stop‑and‑go”, taking many short steps to navigate carefully.

### What determines a patch’s length?  

1. **Entropy of the next‑byte prediction** – computed by a tiny pretrained byte‑level LM.  
2. **Two simple thresholds** – either a global entropy cut‑off or an “entropy rise” relative to the previous byte (approximate monotonicity).  
3. **Incremental requirement** – at generation time we must decide patch boundaries using only past bytes; no look‑ahead is allowed.

The average patch size (`⌈bytes/patch⌉`) directly controls **how many times** BLT’s expensive *global latent transformer* runs:

\[
\text{Inference FLOPs} \;\propto\; \frac{\text{#bytes}}{\text{average patch size}}
\]

Larger patches → fewer transformer steps → lower FLOPs.

---  

## 3️⃣ Architecture in a Nutshell  

BLT consists of three interacting parts (see Figure 1 in the paper, described here):

1. **Local Encoder (`𝔈`)** – a tiny transformer that reads raw bytes and, via cross‑attention, aggregates them into patch embeddings.  
2. **Latent Global Transformer (`𝔊`)** – the heavyweight autoregressive core that processes *patch* embeddings exactly like a normal LLM processes tokens.  
3. **Local Decoder (`𝔇`)** – another lightweight transformer that expands each output patch back into raw bytes.

Because `𝔊` runs only once per patch, saving FLOPs by increasing patch size does not affect `𝔈` or `𝔇` much – they stay tiny and roughly constant across model scales.

---  

## 4️⃣ Scaling Experiments: Matching Llama 3  

### 4️⃣ Training regime  

*Compute‑optimal scaling*: For each model size the authors used the same FLOP budget that Llama 3’s authors identified as optimal for token models (the “Chinchilla law”).  
- Datasets: 2 T tokens from Llama‑2 + a new 1 T‑token (≈4 T bytes) high‑quality mix.  
- Parameter range: 400 M → 8 B.  
- Patch sizes tested: 4 bytes (entropy‐based), 6 bytes (space‐based), and up to 8 bytes (entropy with larger threshold).

### 4️⃣ Results at a glance  

| Model | Params | Avg. Patch Size | Training FLOPs (×10¹⁸) | Bits‑Per‑Byte (BPB) ↓ | Inference FLOPs reduction |
|------|--------|-----------------|------------------------|-----------------------|--------------------------|
| Llama 3 (token) | 8 B | 4.4 B/ token | 1.0 | 1.12 | baseline |
| BLT‑Entropy | 8 B | ~4.5 B/ patch | ≈1.0 (matched) | **1.12** (parity) | **≈45 %** fewer |
| BLT‑Space   | 8 B | ~6 B/ patch   | ≈1.0                 | 1.15 (+0.03)          | **≈30 %** fewer |
| BLT‑LargePatch(8) | 8 B | ~8 B/ patch   | ≈0.9                 | 1.16 (+0.04)          | **≈50 %** fewer |

*Key takeaways*  

- **Parity on language modeling**: With entropy‐based patches BLT hits the same BPB as Llama 3 across all scales up to 8 B parameters.
- **Inference savings**: Because patches are larger on average, every forward pass touches the global transformer half as often → up to **50 % fewer FLOPs** at inference.
- **Scaling trend preserved**: When you plot training FLOPs vs BPB, BLT’s curve lies almost exactly on top of Llama 3’s curve, confirming that dynamic patching does not hurt sample efficiency.

### 4️⃣ Fixed‑Inference Budget Scaling  

The authors also asked: *If I have to keep inference cost constant, can I get a better model by making patches larger and using those saved FLOPs to grow the global transformer?*  

They trained two families:

- **Token family** – Llama 2 tokenizer models at various sizes but with identical inference FLOPs.
- **Patch family** – BLT models with average patches = 6 or 8 bytes.

Result: The BLT family consistently outperformed token models *for the same inference budget*, especially beyond ~2× compute over the optimal point. The crossover point moved closer to the compute-optimal regime as model size grew, showing that *larger patches become more advantageous when you have enough parameters to exploit them*.

---  

## 5️⃣ What Do These Numbers Mean in Practice?  

### Analogy: Packing a Suitcase  

A token model is like packing one item per slot regardless of its size; you end up with many empty spaces when items are small (common words). BLR’s dynamic patches are like using flexible dividers that automatically stretch for bulky items and collapse for tiny ones—so you fit more clothing in the same suitcase and still have room for extra gear (i.e., extra model capacity).

### Real‑world implication  

- **Chatbot deployments** can cut GPU inference cost by roughly half without sacrificing answer quality.
- **Edge devices** benefit because fewer transformer steps mean lower latency and power draw.
- **Long documents** become cheaper to process since predictable sections (e.g., code comments, whitespace) collapse into long patches.

---

---  

## 7️⃣ Takeaways & Future Directions  

- **Dynamic patches give you compute where it counts**, delivering token‑level performance without any vocabulary.
- The approach scales cleanly: up to 8 B parameters across billions of training bytes, matching state-of-the-art token baselines.
- Larger average patches unlock *a new scaling dimension*: you can grow both model size *and* patch size while staying inside a fixed inference budget.
- Open questions remain: finding optimal scaling laws *specific* to byte models, end-to-end learned patch boundaries, and tighter wall‑clock implementations.

If you’re building an LLM stack where inference cost matters—think SaaS chat agents or on-device assistants—BLT shows that you can ditch tokens entirely and still sit on top of today’s best performance charts—all while spending far fewer FLOPs at runtime.

---  

*TL;DR*: By grouping raw bytes into entropy‑driven patches, BLT matches Llama 3’s language modeling quality up to 8 B parameters and saves up to half the inference compute. Larger patches let you pour those saved flops back into a bigger global transformer, giving better performance for any fixed inference budget—a promising path toward cheaper yet powerful language models.*



# Robustness By Design: Byte‑Level Models vs. Tokenizers on Noisy and Low‑Resource Text  

Large language models (LLMs) have become ubiquitous, but most of them still rely on a pre‑processing step—tokenization—that groups raw bytes into a fixed vocabulary of sub‑word units. While tokenizers do a decent job of compressing text, they also embed a host of biases: they can be fragile to spelling errors, struggle with rare scripts, and hide the orthographic structure that underlies every language.  

The recent **Byte Latent Transformer (BLT)** flips this script by discarding tokenizers entirely and operating directly on raw bytes. Instead of a static vocabulary, BLT dynamically groups bytes into *patches* whose size is determined by the information‑density of the upcoming data. This design lets the model allocate more compute where predictions are hard and less where they are easy.  

In this post we walk through the robustness experiments presented in the BLT paper and explain why a byte‑level architecture gives a clear edge on noisy inputs, phoneme‑level tasks, character manipulation benchmarks, and low‑resource machine translation.

---

## 1. Why Bytes Matter for Robustness  

### No hidden “word boundaries”  
Tokenizers impose artificial boundaries that are learned from a corpus but are *fixed* at inference time. When an input contains misspellings, extra spaces, or characters from an unseen script, the tokenizer may produce unknown tokens or split words in unintuitive ways, which then propagates errors through the whole model.

### Direct access to sub‑word signals  
A byte‑level model sees every character (including diacritics, punctuation, and control bytes) as a first‑class token. This means it can learn *character‑level* patterns such as “the letter ‘q’ is rarely followed by ‘u’ in English” or “the suffix ‘‑tion’ often signals a noun”. These patterns are difficult for a BPE model because they are hidden inside the embedding table of a large vocabulary.

### Dynamic compute allocation  
BLT’s *entropy patching* examines the next‑byte prediction entropy from a tiny auxiliary byte LM. When entropy is low (the model is confident), it merges many bytes into one patch—saving flops. When entropy spikes (e.g., at the start of a new word or after a punctuation mark), BLT creates a short patch so that the large global transformer spends more compute on the difficult region. This guarantees that hard, noisy parts of text receive extra attention.

---

## 2. Stress‑Testing with Noisy Text  

The authors introduced five systematic corruption strategies:

| Corruption | What it does |
|-----------|--------------|
| **AntSpeak** | Upper‑case each character and separate them with spaces (`H E L L O`). |
| **Drop** | Randomly delete 10 % of characters. |
| **RandomCase** | Randomly toggle case on 50 % of characters. |
| **Repeat** | Repeat 20 % of characters up to four times (`helloo`). |
| **UpperCase** | Convert the entire sequence to upper case. |

Each strategy was applied separately to prompts, completions, or both for the HellaSwag benchmark (a multiple‑choice commonsense reasoning task).  

**Results (average accuracy)**  

| Model | Clean HellaSwag | AntSpeak | Drop | RandomCase | Repeat | UpperCase |
|-------|----------------|----------|------|------------|--------|-----------|
| Llama 3 (tokenizer) | 71.3 % | 58.1 % | 53.2 % | 55.8 % | 56.7 % | 60.0 % |
| **BLT‑Entropy** (byte) | **71.3 %** | **66.4 %** | **62.0 %** | **63.7 %** | **64.1 %** | **68.2 %** |

Across all noise types BLT gains roughly **8–10 points** over the tokenized baseline and even beats Llama 3 trained on ten times more data (Llama 3.1). The gap widens as corruption becomes more severe (e.g., Drop or Repeat).  

*Takeaway*: Because BLT never loses information due to an opaque tokenization step, it can still latch onto the remaining character patterns even when many bytes are scrambled.

---

## 3. From Graphemes to Phonemes  

A classic test of sub‑word understanding is *grapheme‑to‑phoneme* (G2P) conversion: given a word’s spelling, predict its pronunciation in phonetic symbols. The benchmark used was **Phonology Bench**, evaluated in a five‑shot setting.

| Model | G2P Exact Match |
|-------|-----------------|
| Llama 3 (tokenizer) | 71.5 % |
| **BLT‑Entropy** | **78.9 %** |

The improvement comes from BLT’s exposure to every individual character during training; it can learn systematic sound–letter correspondences (e.g., “c” → /k/ vs /s/ depending on context). Tokenized models must infer these rules indirectly through their sub‑word embeddings, which often blur fine‑grained orthographic cues.

---

## 4. CUTE Benchmark – Character Manipulation at Scale  

CUTE (“Character Understanding Through Evaluation”) probes three families of abilities:

1. **Composition** – can the model predict what happens when characters are concatenated?  
2. **Orthographic similarity** – does it recognise that “color” and “colour” share most letters?  
3. **Sequence manipulation** – can it delete, insert, or reorder characters correctly?

The authors evaluated BLT against Llama 3 on all CUTE tasks with identical prompts.

| Task Category | Llama 3 (BPE) | **BLT‑Entropy** |
|---------------|---------------|-----------------|
| Composition   | 62 %          | 89 % |
| Orthographic similarity | 68 % | 93 % |
| Sequence manipulation – deletion/insertion | 70 % / 64 % | **99.9 % / 99.7 %** |

BLT dominates by margins as large as **30+ points**, especially on manipulation tasks where exact character ordering matters most. The authors note that even though BLT was trained on only ~16× less data than Llama 3.1, its direct access to bytes enables perfect spelling reasoning—a capability tokenizers struggle to acquire because the underlying token embeddings hide individual letters.

---

## 5. Low‑Resource Machine Translation  

Tokenizers often require language‑specific vocabularies; rare scripts may be fragmented into many sub‑words or fall back to unknown tokens, hurting translation quality for low‑resource languages.

Using the FLORES‑101 benchmark (21 low‑resource languages across six families), the authors measured SentencePiece BLEU scores for English↔target translations.

| Language Pair (En→X) | Llama 3 BLEU | **BLT‑Entropy BLEU** |
|----------------------|--------------|----------------------|
| Swahili              | 31.2         | **33.5** |
| Burmese              → English   → English → Burmese      ...   (similar pattern) |
| Average across all pairs | 28.1         | **30.1** |

For high‑resource pairs like French or Spanish the gap is negligible; for long‑tail scripts such as Burmese or Amharic BLT consistently outperforms by ~1–2 BLEU points—a meaningful boost given how hard it is to improve low‐resource MT further.

*Why?* Byte models naturally handle any Unicode byte sequence without needing script-specific token vocabularies; thus they learn multilingual orthographic patterns directly from raw data.

---

## 6. Putting It All Together  

The robustness experiments paint a coherent picture:

* **Noise tolerance:** When inputs are corrupted at the character level, BLT’s predictions degrade much slower because there’s no “unknown token” barrier.
* **Phonological awareness:** Direct exposure to graphemes lets BLT internalize sound–letter mappings that are otherwise implicit.
* **Fine-grained manipulation:** Tasks that require exact insertion/deletion of characters benefit from byte granularity.
* **Multilingual equity:** Byte models avoid vocabulary bias across scripts, improving translation for languages that would otherwise be underrepresented in a BPE dictionary.

Crucially, these gains come *without sacrificing overall language modeling quality*. In flop‑controlled scaling studies BLT matched—or slightly outperformed—state-of-the-art tokenized LLMs while using up to half the inference flops thanks to its dynamic patching strategy.

---

## 7. Looking Ahead  

BLT demonstrates that removing tokenization is not merely an academic curiosity; it yields concrete robustness benefits for real-world applications where misspellings, OCR errors, code snippets, or low-resource languages abound. Future work could explore:

* End-to-end learned patch boundaries instead of relying on a precomputed entropy model.
* Hybrid systems that start from a pretrained tokenizer model and “byte‑ify” it (the paper’s preliminary distillation experiments already show promise).
* Optimizations in transformer libraries to narrow wall-clock gaps between byte and token pipelines.

If you’re building an LLM that will see messy user input—chatbots handling slang, code assistants parsing imperfect snippets, or multilingual services serving underserved scripts—consider giving your architecture *bytes first*. The robustness gains demonstrated by BLT suggest you’ll get more reliable performance without paying extra inference cost.

--- 

*TL;DR*: Byte‐level models like BLT sidestep tokenizer brittleness by seeing every character directly and allocating compute adaptively via entropy patching. The result? Stronger performance on noisy text, phoneme mapping, character manipulation benchmarks (CUTE), and low-resource translation—all while being computationally cheaper at inference.*



# From Tokenizer to Byte Latent Transformer: Turning Llama 3 Into a “Byte‑ified” Model  

In the last few months the research community has been abuzz with **Byte Latent Transformers (BLT)**—a new family of large language models that completely drop the classic sub‑word tokenizer and operate directly on raw bytes. The original BLT paper shows that, when trained from scratch, a byte‑level model can match Llama 3’s quality while using up to **50 % fewer inference FLOPs** and gaining robustness to noisy inputs.  

But most practitioners already have large, tokenizer‑based checkpoints (think Llama 3 1‑T or 15‑T). Training a BLT from scratch would still require billions of FLOPs and massive data pipelines. The authors therefore introduced a practical “**byte‑ify**” recipe: **reuse the global transformer of a pretrained Llama 3 model**, attach lightweight byte‑level encoder/decoder modules, and fine‑tune only these new parts. In this post we walk through the key ideas, the training workflow, and the empirical gains reported in the BLT paper.

---

## Why “Byte‑ify”?

Traditional LLMs rely on a **fixed vocabulary** (e.g., BPE with 128 k tokens). Tokenization is a preprocessing step that compresses raw bytes into tokens before any learnable computation happens. This brings two major drawbacks:

1. **Compute is uniform** – every token receives the same amount of transformer work, even though some tokens are trivial to predict (e.g., continuation of a common word) while others are highly uncertain.
2. **Information loss & fragility** – tokenizers discard fine‑grained orthographic cues, making models brittle to character‑level noise, spelling variations, or low‑resource scripts.

BLT solves both problems by **dynamically grouping bytes into patches** based on next‑byte entropy. Patches are processed by a **large global transformer**, while two tiny local models handle byte‑to‑patch encoding and patch‑to‑byte decoding. The global transformer therefore runs only when a patch boundary is reached, yielding substantial FLOP savings.

The “byte‑ify” trick leverages the fact that the **global latent transformer in BLT has exactly the same architecture as an ordinary token transformer** (same number of layers, hidden size, SwiGLU feed‑forward, RoPE attention, etc.). Consequently we can copy weights from a pretrained Llama 3 checkpoint directly into BLT’s global module without any architectural mismatch.

---

## The Byte‑ify Pipeline

Below is a step‑by‑step recipe extracted from Section 6.2 of the BLT paper.

| Stage | What Happens | Implementation Tips |
|-------|--------------|----------------------|
| **1️⃣ Prepare the Llama 3 checkpoint** | Load the official Llama 3 weights (e.g., 8B or 15B parameters). | Keep the checkpoint unchanged; it will be frozen for most of training. |
| **2️⃣ Build BLT scaffolding** | Create three modules: <br>• **Global Transformer (𝒢)** – identical to Llama 3’s decoder stack.<br>• **Local Encoder (ℰ)** – 1–3 lightweight transformer layers + cross‑attention that pool bytes into patch latents.<br>• **Local Decoder (𝒟)** – symmetric to ℰ, expands patch latents back to bytes. | Use the same hyperparameters as Llama 3 for 𝒢 (SwiGLU, RMSNorm, RoPE). For ℰ/𝒟 keep hidden size modest (e.g., 256–512) and use a small windowed attention (512 bytes) as in the paper. |
| **3️⃣ Initialise 𝒢** | Copy Llama 3’s parameters into BLT’s global transformer. | In most deep learning frameworks this is just a state dict assignment (`blt.global.load_state_dict(llama3.state_dict())`). |
| **4️⃣ Freeze 𝒢** | During fine‑tuning we only update ℰ and 𝒟 (and the small entropy model if used). Set `requires_grad=False` for all parameters of 𝒢. | This reduces training FLOPs dramatically because backprop through a huge transformer dominates compute. |
| **5️⃣ Train an entropy model (optional)** | A tiny byte LM (≈100 M parameters) predicts next‑byte probabilities on the training corpus; its entropies decide where patches start. | The paper reports that a 100 M model with a 512‑byte sliding window works well and can even be compiled into a lookup table after training. |
| **6️⃣ Dynamic patching** | While loading data, compute next‑byte entropy using the entropy model; place patch boundaries where entropy exceeds a threshold or where it rises relative to the previous byte. | This is done on-the-fly during dataloader preprocessing; no extra forward pass through the main model is required. |
| **7️⃣ Fine‑tune** | Run standard causal language‐model training: encode raw bytes → ℰ → patch latents → 𝒢 → ℱ → patch outputs → 𝒟 → raw bytes. Only ℰ/𝒟 gradients are accumulated. | Use AdamW with lr ≈ 4e‑4 for ℰ/𝒟; optionally set a much smaller lr (e.g., 1e‑5) for 𝒢 if you want slight adaptation rather than complete freezing. |
| **8️⃣ Evaluate** | Compute Bits‑Per‑Byte (BPB) on validation data; run downstream tasks such as MMLU or HumanEval to verify that performance remains competitive with full Llama 3 training. | The paper shows BLT‐from‐Llama 3 matches or exceeds vanilla Llama 3 on most benchmarks despite using ~10× fewer training FLOPs. |

---

## Empirical Gains

| Metric | Llama 3 trained from scratch | BLT “byte‑ified” (global frozen) |
|--------|-----------------------------|-----------------------------------|
| **Training FLOPs** | Baseline (≈ X) | ≈ 0.1·X (≈ 90 % reduction) |
| **Validation BPB** | 1.20 (on BLT-1T mix) | 1.19 (virtually identical) |
| **MMLU accuracy** | 71.2 % (8B) | 71.6 % (same compute budget) |
| **HumanEval pass@1** | 34 % | 33 % (no statistically significant drop) |
| **Robustness to noise** (character corruptions) | ~8 pt drop vs clean | <4 pt drop vs clean |

Key takeaways:

- **Training efficiency:** Because backpropagation through a massive transformer dominates FLOPs, freezing 𝒢 cuts total training compute by roughly an order of magnitude.
- **Performance parity:** Despite using far fewer FLOPs, models initialized from Llama 3 retain almost identical language modeling quality—demonstrating that most knowledge resides in the global transformer’s weights.
- **Robustness boost:** The added byte encoder/decoder give access to raw character information that tokenizers lose; consequently the byte‑ified model handles misspellings, case changes, and low‑resource scripts far better.

---

## Practical Tips for Developers

1. **Choose an appropriate patch size** – The paper reports average patch sizes of ~4–6 bytes for entropy‐based patching and up to 8 bytes when you prioritize inference speed. Larger patches mean fewer global steps but may slightly hurt perplexity at small scales.
2. **Hash n‑gram embeddings matter** – Adding lightweight hash embeddings for byte n‑grams (size 3–8) improves BPB by ~0.04 on Wikipedia/GitHub domains with negligible cost.
3. **Cross‐attention is cheap but effective** – A single cross‐attention layer in the decoder already yields most of the gain; adding it to the encoder provides marginal improvements.
4. **Entropy thresholds are tunable at inference time** – Lowering the threshold trades more global steps for higher accuracy; raise it if you need ultra‐low latency.
5. **Fine‐tuning schedule:** Start with a warmup of ~2k steps at lr=4e−4 for ℰ/𝒟, then decay cosine to zero over your total budget (the authors used roughly 200× fewer steps than full Llama 3 pretraining).

---

## When Should You Use Byte‑ify?

- **You already have a large tokenizer‐based checkpoint** and want to experiment with byte input without redoing massive pretraining.
- **Compute budget is tight**, e.g., you need to adapt a model on domain-specific data but cannot afford another multi‑petaflop run.
- **Your downstream tasks are noisy or multilingual**, especially those involving code, scientific notation, or low-resource scripts where subword tokenizers tend to fragment words irregularly.
- You want to explore *fixed inference budgets*: By increasing average patch size you can grow the global model while keeping inference FLOPs constant—a scaling knob unavailable to tokenizers.

---

## Limitations & Future Directions

While byte‑ifying works remarkably well at up to 8 B parameters, there are open questions:

- The optimal scaling law for BLT may differ from Chinchilla/Llama curves; future work could derive *byte-specific* scaling coefficients.
- Current implementations rely on custom cross‑attention kernels (`FlexAttention`). Production systems may need tighter integration with existing libraries for wall‑clock speed parity.
- End-to-end learned patching (instead of entropy‐based heuristics) could further close any remaining performance gap.

Nevertheless, the “byte‑ify” technique already offers a pragmatic path for developers who want tokenizers out of their pipelines while preserving billions of dollars worth of pretrained knowledge.

---

### TL;DR

1️⃣ Load a pretrained Llama 3 checkpoint.<br>
2️⃣ Attach tiny byte encoder/decoder modules.<br>
3️⃣ Freeze the large global transformer.<br>
4️⃣ Train only the new modules using entropy‐driven dynamic patches.<br>
Result: *≈90 % less training FLOPs* and *no noticeable loss* in language modeling quality—plus better robustness and flexible inference scaling.

If you’re curious to try it yourself, the authors released code at `github.com/facebookresearch/blt`. Happy byte‑ifying!



# Future Directions for Patch‑Based LLMs: End‑to‑End Patching, Scaling Laws, and Beyond

Large language models (LLMs) have become the workhorse of modern AI, but they still rely on a hidden pre‑processing step: tokenization. The recent **Byte Latent Transformer (BLT)** paper shows that we can discard static vocabularies, group raw bytes into *dynamic patches*, and still match the performance of token‑based models while cutting inference flops by up to 50 %. BLT opens the door to a whole new design space, yet many questions remain. In this post we outline three research frontiers that look most promising for the next generation of patch‑based LLMs:

1. **Learning patch boundaries jointly with the language model (end‑to‑end patching).**  
2. **Deriving scaling laws that are specific to byte‑level, patch‑driven architectures.**  
3. **Hardware‑aware optimizations that turn theoretical flop savings into real‑world speedups.**  

We’ll walk through why each direction matters, what the current paper has already tackled, and where concrete research opportunities lie.

---

## 1. End‑to‑End Patching: Let the Model Decide Where to Split

### Why it matters
BLT currently uses a *pre‑computed* entropy model to decide where patches start. This works well, but it imposes two constraints:

| Constraint | Consequence |
|------------|--------------|
| **Static thresholds** (global or monotonic entropy) | Patch granularity is fixed for an entire dataset; any mismatch between the entropy estimator and the final LM hurts efficiency. |
| **Separate training** of the entropy model | Additional data passes are required, and the patcher cannot adapt to later stages of training (e.g., when the LM becomes better at hard predictions). |

If patches could be *learned jointly* with the language model, compute would be allocated exactly where the model needs it—potentially yielding finer granularity in high‑entropy regions and coarser granularity elsewhere.

### Possible approaches
1. **Boundary predictor head** – Attach a lightweight binary classifier (or a multi‑class head) to each byte representation that outputs “patch break?” This head can be trained with a *reinforcement* signal: each time a break is placed, the global transformer is invoked, incurring a known flop cost. The loss then balances language modeling likelihood against an explicit compute budget term.

2. **Differentiable masking** – Replace hard binary decisions with a soft gating function (e.g., Gumbel‑Softmax). During backpropagation the model learns a distribution over break points; at inference time we take the argmax to obtain deterministic patches.

3. **Curriculum patching** – Start training with coarse patches (large stride) and gradually let the model refine its boundaries as it learns richer byte representations. This mirrors curriculum learning in vision where early layers see low‑resolution inputs.

### Open challenges
- **Stability:** The boundary predictor must not collapse to “break everywhere” or “never break.” Proper regularization (entropy penalties, FLOP budgets) is essential.
- **Latency:** Introducing a per‑byte break decision adds overhead; efficient vectorized implementations or batched decisions are needed.
- **Evaluation:** We need metrics beyond bits‑per‑byte (BPB) that capture *compute‑efficiency*—for instance, average FLOPs per generated token under a fixed latency budget.

---

## 2. Scaling Laws for Byte‑Level, Patch‑Driven Models

### What BLT has shown so far
The paper presents two scaling studies:
- **Compute‑optimal scaling** (parameter–flop tradeoff) where BLT matches Llama 3.
- **Inference‑flop controlled scaling**, demonstrating better curves when we increase both model size *and* average patch size.

These results are encouraging but rely on *extrapolating* existing token‑level scaling formulas (e.g., Chinchilla’s \(\text{Flops} \propto N^{0.5} D^{0.5}\)). Byte models introduce an extra degree of freedom—patch size—that isn’t captured by those formulas.

### Toward dedicated scaling laws
A more faithful scaling law for BLT would likely have three axes:

\[
\text{Performance} \approx f\bigl(N_{\text{global}}, N_{\text{local}}, \bar{s}\bigr)
\]

where:
- \(N_{\text{global}}\) = parameters in the latent transformer,
- \(N_{\text{local}}\) = parameters in encoder/decoder,
- \(\bar{s}\) = average patch size (bytes per patch).

Empirical fitting across many model sizes and patch sizes should reveal:

| Regime | Dominant cost |
|--------|----------------|
| Small \(\bar{s}\) (< 4 bytes) | Global transformer FLOPs dominate → similar to token models |
| Medium \(\bar{s}\) (4–8 bytes) | Tradeoff point where reduced global steps offset larger cross‑attention costs |
| Large \(\bar{s}\) (> 8 bytes) | Encoder/decoder overhead becomes negligible; global FLOPs shrink dramatically |

A new law could predict *optimal* \(\bar{s}\) given a fixed FLOP budget, much like how Chinchilla predicts optimal data quantity for a given parameter count.

### Research tasks
- Run systematic sweeps over \(\bar{s}\) at several parameter buckets (e.g., 400 M, 2 B, 8 B).
- Fit multi‑dimensional power laws or neural surrogates that incorporate entropy statistics of the training data.
- Validate whether optimal \(\bar{s}\) shifts as data quality improves (e.g., moving from raw web crawl to curated multilingual corpora).

---

## 3. Turning Flop Savings into Wall‑Clock Speedups

### The gap today
BLT’s FLOP analysis counts feed‑forward layers as dominant computation, not self-attention. However:
- Existing transformer kernels (FlashAttention, Triton kernels) are heavily tuned for fixed sequence lengths and dense attention masks.
- BLT introduces *dynamic* masks in cross‑attention and variable patch counts per batch—cases where current libraries fall back to slower implementations.

Thus, while BLT can theoretically use 50 % fewer FLOPs at inference, actual latency gains may be modest without tailored kernels.

### Hardware‑centric ideas
1. **Variable‑length batch packing** – Group patches of similar length into the same batch; this reduces padding overhead both in encoder/decoder and global transformer.
2. **Specialized cross‑attention kernels** – Leverage “flex attention” or custom CUDA kernels that exploit the fact that each query attends only to bytes inside its own patch—a highly localized pattern amenable to shared memory tiling.
3. **Mixed precision & quantization** – Since local encoder/decoder are lightweight, aggressive quantization (e.g., 4‑bit weights with integer arithmetic) can reduce memory bandwidth dramatically without hurting overall BPB.
4. **FPGA/ASIC pipelines for entropy computation** – If we move toward end‑to‑end learned patching, having dedicated hardware that evaluates boundary logits on‐the‐fly could keep per‑token latency low.

### Evaluation beyond FLOPs
Future papers should report:
- **Throughput (tokens/s)** under realistic batch sizes.
- **Energy per generated byte**, measured on commodity GPUs vs specialized accelerators.
- **Latency distribution**, especially for long generation sequences where dynamic patches cause variable step counts.

---

## Putting It All Together: A Roadmap

| Phase | Goal | Key Experiments |
|-------|------|-----------------|
| **0️⃣ Baseline** | Reproduce BLT scaling results on a public dataset | Train 1 B and 4 B BLT models with static entropy patching |
| **1️⃣ End-to-End Patching** | Replace static entropy thresholds with learnable boundaries | Implement Gumbel‐Softmax break predictor; evaluate FLOP vs BPB tradeoff |
| **2️⃣ Scaling Law Discovery** | Fit three‑axis scaling curves across many \(\bar{s}\) values | Grid search over \(\bar{s}\in\{2,\dots,12\}\) at 400 M / 2 B / 8 B |
| **3️⃣ Kernel Optimizations** | Close wall-clock gap between theory & practice | Build custom cross‑attention kernel; benchmark on RTX 4090 / A100 |
| **4️⃣ Full System Integration** | Deploy an end-to-end BLT service under fixed latency budget | Combine learned patching + optimized kernels + quantization; measure throughput on real workloads (chatbot, code generation). |

Each phase feeds into the next: better boundaries reduce variance in patch length → cleaner data for scaling-law fitting → clearer targets for kernel engineers.

---

## Takeaway

BLT proves that “patches scale better than tokens,” but it also raises a fascinating set of open problems:

*Can we let the model itself decide its own granularity?*  
*What does an optimal tradeoff between model size and patch size look like across compute regimes?*  
*How do we make these theoretical gains translate into faster inference on today’s hardware?*

Answering these questions will require collaboration between language modeling researchers, systems engineers, and hardware designers. If you’re interested in building the next wave of efficient LLMs—whether you’re developing novel boundary predictors or low-level GPU kernels—there’s plenty of low-hanging fruit ahead. The future of LLMs may well be byte‐native, dynamically patched, and hardware‐aware—all at once. Happy hacking!
