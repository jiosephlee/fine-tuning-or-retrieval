\title{Blogs about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

# From Code to Calculus: Why Starting with a Coding Model Improves Math Reasoning  

In the world of large language models (LLMs), it’s tempting to think that more math data alone will make a model better at solving equations, geometry puzzles, or abstract proofs. The DeepSeekMath paper shows a different story: **pre‑training on source‑code first gives a measurable boost to both “plain‑vanilla” math solving and program‑aided reasoning**. In this post we unpack the authors’ experiments, explain the two‑stage versus one‑stage training setups, discuss the phenomenon of *catastrophic forgetting*, and look ahead at what this could mean for designing next‑generation math‑savvy models.

---  

## 1. The Core Idea: Code as a Reasoning Primer  

Coding and mathematics share a deep structural affinity:

* Both require precise symbolic manipulation.  
* Both benefit from step‑by‑step logical flow (think *loop* vs. *chain‑of‑thought*).  
* Both can be expressed in a formal language that LLMs can learn to generate and execute.

The authors therefore **initialized DeepSeekMath from DeepSeek‑Coder‑Base**, a 7 B model already tuned on billions of code tokens. The hypothesis was simple: if a model learns how to write correct, syntactically valid code, it may transfer that discipline to the structured reasoning needed for mathematics.

---  

## 2. Training Regimes Compared  

The study contrasts four training pipelines (all using the same 7 B architecture). Below is a concise schematic:

| Pipeline | Stage 1 (tokens) | Stage 2 (tokens) | Primary Data Type |
|----------|------------------|------------------|-------------------|
| **A** – Code → Math (Two‑stage) | 400 B code | 150 B math | Code first, then pure math |
| **B** – General → Math (Two‑stage) | 400 B natural language | 150 B math | General text first |
| **C** – Math only (One‑stage) | 150 B math | — | Pure math |
| **D** – Mixed Code+Math (One‑stage) | 400 B code + 150 B math (simultaneous) | — | Both blended together |

All pipelines were evaluated on two families of downstream tasks:

1. **Tool‑free reasoning** – classic chain‑of‑thought (CoT) solutions where the model writes out the math steps.
2. **Program‑aided reasoning** – “program of thought” (PoT) where the model emits Python code that is then executed (e.g., using `sympy`).

---  

## 3. What the Numbers Tell Us  

### 3.1 Tool‑Free Reasoning  
*Both A and B improve over a baseline that never sees code.*  
- After the **code‑first stage**, even before any math pre‑training, the model already shows modest gains on GSM8K and MATH (the standard grade-school and competition‐level benchmarks).  
- Adding the second **math stage** pushes performance higher still, producing the best scores among all four pipelines for CoT tasks.

### 3.2 Program‑Aided Reasoning  
When the model must generate executable Python, **code pre‑training shines even brighter**:  

| Pipeline | GSM8K (PoT) ↑ | MATH (PoT) ↑ |
|----------|---------------|--------------|
| A (Code→Math) | +10% over C | +8% over C |
| D (Mixed)    | Comparable to A but more stable across epochs |
| B (General→Math) | Small gain, far behind A |
| C (Math only)   | Lowest performance |

The two‑stage code→math pipeline yields the highest *program execution accuracy*, confirming that early exposure to coding syntax and semantics gives the model a head start on generating correct Python snippets.

---  

## 4. Catastrophic Forgetting – Why One‑Stage Mixed Training Isn’t Always a Magic Bullet  

When we train on *both* code and math simultaneously (pipeline D), an interesting side effect appears: **the model retains most of its coding ability while still improving on many math tasks**, but it falls short of the pure two‑stage approach on pure CoT reasoning.

Why?  
- **Catastrophic forgetting** is a well‑known phenomenon in continual learning: when a network is trained on new data, it can overwrite representations learned earlier.  
- In pipeline D, the model’s capacity is split between two very different token distributions at once. With only 7 B parameters, it can’t fully internalize both domains to their optimum depth.  
- By contrast, pipeline A lets the model *consolidate* coding knowledge first—forming robust syntactic priors—before dedicating its full capacity to mathematical patterns.

The authors observed that mixing code and math in one stage *mitigates* forgetting compared with a strict sequential approach (the “catastrophic forgetting” is less severe because both domains are reinforced each update), yet it does not completely eliminate the trade‑off.

---  

## 5. Implications for Future Model Design  

### 5.1 Curriculum Learning for LLMs  
The success of **code → math** suggests that carefully designed curricula—starting from simpler, well‑structured tasks before progressing to more abstract ones—can be more effective than dumping all data together. For developers:

- **Stage 1:** Heavy code exposure (e.g., GitHub, StackOverflow).  
- **Stage 2:** Large-scale mathematics crawled from the web (as DeepSeekMath does with its 120 B token corpus).  
- **Optional Stage 3:** Instruction tuning with chain‑of‑thought / program‐of‐thought examples.

### 5.2 Model Size vs. Data Quality  
DeepSeekMath‐Base matches or surpasses gigantic closed models (e.g., Minerva 540 B) despite being only 7 B parameters. The takeaway: *high‑quality data + smart ordering can outweigh sheer parameter count*—a useful insight for research groups without massive compute budgets.

### 5.3 Dual Capability Models  
If you want a single model that can both write code and solve pure math without external tools, consider a **two‑stage pretraining schedule followed by mixed fine-tuning**:

1. Pretrain → Code heavy (~400 B tokens).  
2. Continue pretraining → Math heavy (~150 B tokens).  
3. Fine-tune → Combined instruction data covering CoT, PoT, and tool–integrated reasoning.

This pipeline replicates what DeepSeekMath did and yields strong results across both axes.

---  

## 6. TL;DR – What Should Practitioners Take Away?  

- **Start with code**, not raw math data. A coding foundation improves logical structuring, which translates into better stepwise mathematical explanations.
- Use a **two-stage curriculum** rather than mixing everything at once; this reduces catastrophic forgetting and lets each domain fully imprint on the model’s weights.
- Even modestly sized LLMs can punch above their weight class if they are exposed to *high-quality*, *well-filtered* web data—DeepSeekMath’s 120 B token mathematics corpus is a prime example.
- For future research, exploring more granular curricula (e.g., adding symbolic‐reasoning tasks before full‐blown calculus) could push open-source models even closer to closed ones like GPT‑4 or Gemini Ultra.

By treating code as an introductory language for structured reasoning, we open a practical pathway toward LLMs that are equally comfortable writing Python scripts *and* solving Olympiad‐level equations—all without relying on external toolkits. The evidence is now in the numbers: **code first → better calculus later**.
