\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### Why does mLSTM use a matrix memory \(\mathbf{C}_t\in\mathbb{R}^{d\times d}\) instead of a vector?
Question:
The paper claims that increasing the memory from a scalar to a matrix boosts storage capacity, especially for rare token prediction. Could someone explain intuitively how a covariance update \(\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \mathbf{v}_t \mathbf{k}_t^\top\) stores more information than a scalar cell, and how retrieval via \(\mathbf{C}_t \mathbf{q}_t\) works in practice?
Answer:
In a classic LSTM the *cell* $c_{t}$ is a single scalar (or, when we use many cells, a vector of length $d$).  
At each time step the cell is updated by adding a *rank‑1* contribution  

$$
c_{t}=f_{t}\,c_{t-1}+i_{t}\,z_{t},
$$

so the whole history is compressed into one number per hidden dimension.  
If we think of the cell as a “bucket” that contains the *total amount of evidence* for a particular feature, then after many timesteps that bucket inevitably mixes together many different pieces of evidence: the only thing that survives is the **sum** (or an exponentially‑weighted sum) of all past inputs.  Consequently the bucket cannot remember *which* token contributed what, only a coarse statistics.  This limitation is especially visible for rare tokens – their contribution is quickly drowned out by the many frequent updates that hit the same bucket.

---

### Turning the bucket into a matrix

The mLSTM replaces each scalar bucket by a full matrix  

$$
\mathbf C_{t}\in\mathbb R^{d\times d},
$$

and updates it with an outer‑product term

$$
\mathbf C_{t}=f_{t}\,\mathbf C_{t-1}+i_{t}\,\mathbf v_{t}\,\mathbf k_{t}^{\!\top}.
\tag{1}
$$

Here $\mathbf k_{t}$ is called a *key* and $\mathbf v_{t}$ a *value*.  
Equation (1) is exactly the **covariance (or fast‑weight) update** that classical associative memory models use: each new key–value pair adds a rank‑1 matrix $\mathbf v_{t}\mathbf k_{t}^{\!\top}$ to the memory.  Because the outer product lives in a $d\times d$ space, every new pair occupies its own *direction* in this space rather than collapsing onto a single line.

Intuitively, think of $\mathbf C_t$ as a table whose rows correspond to *value directions* and columns to *key directions*.  When you write a pair $(\mathbf k_t,\mathbf v_t)$ you colour a single cell of this table (the outer‑product) – but because the vectors are dense, many cells receive small contributions simultaneously.  After many steps the table contains a **superposition** of all previously written pairs, where each pair can still be pulled apart by looking at how it aligns with a query.

---

### Why does this give larger capacity?

A scalar can store only one degree of freedom per hidden dimension.  
A $d\times d$ matrix has $d^{2}$ degrees of freedom.  The update (1) never overwrites an entire row or column; it only adds another rank‑1 component.  As long as the set of key vectors $\{\mathbf k_t\}$ remains sufficiently diverse (which is encouraged by layer‑norm and random initialisation), the collection $\{\mathbf v_t \mathbf k_t^{\!\top}\}$ will be linearly independent for up to roughly $d$ different keys.  In practice this means the memory can reliably store **$O(d)$** distinct key–value pairs, whereas a vector cell can only keep track of one aggregated statistic per dimension.

The paper points out that this extra capacity matters most for *rare token prediction*: a rare token appears only a few times, so its contribution $i_t \mathbf v_t \mathbf k_t^{\!\top}$ would be swamped in a scalar cell.  In the matrix case each rare pair occupies its own sub‑space and can be recovered later without being drowned out by frequent updates.

---

### Retrieval: $\tilde{\mathbf h}_t=\frac{\mathbf C_t \mathbf q_t}{\max(|\mathbf n_t^{\!\top}\!\mathbf q_t|,1)}$

At time $t+\tau$ we form a query vector $\mathbf q_{t+\tau}$.  
Multiplying the stored matrix by this query,

$$
\mathbf C_t\,\mathbf q_t = 
      \sum_{\ell\le t} i_\ell\, f_{t}^{\,\,\,\,\,(\text{decay})}
      (\mathbf v_\ell\, (\mathbf k_\ell^{\!\top} \mathbf q_t)),
$$

produces a weighted sum of all past values $\mathbf v_\ell$.  The weight for each value is exactly the inner product $\mathbf k_\ell^{\!\top} \mathbf q_t$; if the query aligns with a stored key, that term becomes large and its value dominates the sum.  The normaliser $\mathbf n_t = f_t\,\mathbf n_{t-1}+i_t\,\mathbf k_t$ records how much total key “mass’’ has been written, and dividing by $|\mathbf n_t^{\!\top}\!\! \mathbf q_t|$ simply rescales the output so that it does not grow with the number of writes (the max with 1 avoids division by zero).  

Thus retrieval behaves like **content‑addressable memory**: you ask “what value was stored with a key similar to this query?” and the outer‑product memory returns precisely that value (plus some interference from other keys).  Because interference grows only slowly with the number of stored pairs—thanks to the high dimensionality—the system can keep dozens or hundreds of distinct associations alive simultaneously.

---

### Putting it together

* The scalar LSTM cell compresses everything into one number per hidden unit; information about *which* token caused which change is lost.
* The mLSTM replaces that number by a full $d\times d$ matrix that receives an outer‑product update for every key–value pair.
* This update creates a superposition of rank‑1 components that can be disentangled later by an inner product with a query, exactly like associative recall.
* Because there are $d^{2}$ independent directions in which to store information, the effective storage capacity scales roughly linearly with $d$, enabling reliable memorisation of many rare events.

The empirical results in the paper (e.g., Figure 3 on rare‑token perplexity and the Multi‑Query Associative Recall task) show precisely this effect: mLSTM dramatically reduces perplexity on low‑frequency tokens and attains higher recall accuracy than models that still rely on scalar cells.  Hence, moving from a scalar to a matrix memory directly translates into richer, more discriminative storage—exactly what is needed for long‑range language modelling tasks where rare words carry significant meaning.
