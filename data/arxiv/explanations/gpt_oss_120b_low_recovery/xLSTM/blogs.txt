# From LSTMs to xLSTMs: Why Reviving Classic RNNs Matters for Modern AI

## Introduction  

Long Short‑Term Memory networks (LSTMs) were the workhorses of sequence modelling for more than two decades. Introduced in the early 1990s, they solved the vanishing‑gradient problem of ordinary recurrent neural networks (RNNs) by adding a **constant‑error carousel** and a set of three gates (input, forget, output). This simple idea enabled LSTMs to remember information over long horizons, power everything from handwriting synthesis to game‑playing agents such as AlphaStar and OpenAI Five.

When the Transformer architecture arrived in 2017, its parallelizable self‑attention shattered the performance ceiling of LSTMs on large‑scale language tasks. Transformers scale linearly in computation but quadratically in memory with respect to sequence length, making them the backbone of today’s large language models (LLMs) like GPT‑4, LLaMA, and PaLM. The community largely shifted focus away from recurrent models, assuming that RNNs could not compete at scale.

The new **xLSTM** family challenges that assumption. By revisiting the core LSTM mechanisms and adding two key innovations—**exponential gating** and **enhanced memory structures**—researchers have shown that scaled LSTMs can again rival Transformers and modern state‑space models (SSMs). In this post we unpack why those changes matter, how they address the classic shortcomings of LSTMs, and what the experimental results suggest for the future of recurrent architectures.

## A Quick Recap: How Classic LSTMs Work  

The original LSTM cell updates a scalar memory value \(c_t\) as  

\[
c_t = f_t \, c_{t-1} + i_t \, z_t,
\qquad
h_t = o_t \, \psi(c_t),
\]

where  

* \(i_t\), \(f_t\), \(o_t\) are sigmoid‑activated gates (input, forget, output).  
* \(z_t\) is a transformed version of the current input and previous hidden state.  
* \(\psi\) is typically a \(\tanh\) squashing function.

The additive update (the “carousel”) lets gradients flow unchanged across many time steps, solving the vanishing‑gradient issue that plagued earlier RNNs. Despite this elegance, three practical limitations emerged:

1. **No revision of stored content** – once a value is written into the scalar cell it cannot be efficiently overwritten by newer evidence.  
2. **Limited storage capacity** – a single scalar per cell forces heavy compression, hurting rare‑token prediction and other fine‑grained tasks.  
3. **Sequential bottleneck** – hidden‑to‑hidden connections force strict step‑by‑step processing, preventing parallel execution on modern hardware.

## Exponential Gating: A Simple but Powerful Fix  

The first breakthrough in xLSTM is **exponential gating**. Instead of using only sigmoid activations for all gates, xLSTM allows the input gate (and optionally the forget gate) to use an exponential function:

\[
i_t = \exp(\tilde{i}_t), \qquad
f_t = 
\begin{cases}
\sigma(\tilde{f}_t),\\
\exp(\tilde{f}_t)
\end{cases}
\]

Because exponentials can grow without bound, they enable a gate to *strongly reinforce* or *rapidly decay* stored information. To keep these values numerically stable, xLSTM introduces a **stabilizer state** \(m_t\) that rescales both gates on the fly (see Eq. (3) of the paper). The net effect is that the network can *revise* past decisions: if a more relevant pattern appears later in the sequence, an exponentially large input gate can overwrite earlier content despite earlier forget signals.

Empirically, this modification solves tasks like **nearest‑neighbor search**, where classic LSTMs struggle because they cannot replace an earlier stored neighbor with a closer one encountered later. With exponential gating, xLSTM’s error drops dramatically.

## New Memory Structures: From Scalars to Matrices  

The second pillar of xLSTM upgrades the memory itself.

### sLSTM – Scalar Memory with Mixing  

The **sLSTM** keeps a single scalar per cell but adds a *normalizer state* \(n_t\) that tracks cumulative gate strength:

\[
n_t = f_t \, n_{t-1} + i_t .
\]

The hidden output becomes  

\[
h_t = o_t \frac{c_t}{n_t},
\]

which normalizes the cell state by its total “attention” over time. This simple change improves stability when exponential gates are used and also enables **memory mixing** across multiple cells or heads—something vanilla LSTMs cannot do without extra recurrent weight matrices.

### mLSTM – Matrix Memory with Covariance Updates  

The more radical shift is the **mLSTM**, which replaces each scalar cell with a full matrix \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\). The update follows a classic *covariance* (outer‑product) rule:

\[
\mathbf{C}_t = f_t \,\mathbf{C}_{t-1} + i_t \,\mathbf{v}_t \mathbf{k}_t^{\!\top},
\]

where \(\mathbf{k}_t\) (key) and \(\mathbf{v}_t\) (value) are linear projections of the current input—exactly like the query/key/value formulation in Transformers. Retrieval simply multiplies this matrix by a query vector \(\mathbf{q}_t\):

\[
\tilde{\mathbf{h}}_t = 
\frac{\mathbf{C}_t \,\mathbf{q}_t}
{\max\!\bigl(|\,\mathbf{n}_t^{\!\top}\!\mathbf{q}_t|,\;1\bigr)} .
\]

Because the forget gate now acts as a decay factor on the whole matrix and the input gate controls how much new outer product is added, mLSTM can store *rich associative memories* without any learned parameters inside the matrix itself. The update is mathematically equivalent to Fast Weight Programmers and enjoys optimal signal‑to‑noise properties for binary retrieval tasks.

Importantly, mLSTM removes hidden‑to‑hidden connections entirely; therefore its recurrence can be **reformulated in parallel**, achieving computation speeds comparable to modern linear attention mechanisms.

## Building Blocks: xLSTM Residual Modules  

To turn these cells into large language models, xLSTM integrates them into residual block backbones—standard practice in modern deep learning:

* **Post up‑projection blocks** (used with sLSTM) first process the hidden state non‑linearly in its native dimension and then expand it via a linear projection before adding back to the residual path.
* **Pre up‑projection blocks** (used with mLSTM) project inputs up front so that the high‑dimensional matrix memory operates on a richer representation.

Stacking many such blocks with pre‑LayerNorm yields an architecture we simply call **xLSTM**. Because each block processes data linearly in sequence length (no quadratic attention), memory usage stays constant as sequences grow—a stark contrast to Transformers.

## How Does xLSTM Perform?  

### Synthetic Benchmarks  

* On formal language tasks that require explicit *state tracking* (e.g., Parity or Dyck languages), only models with memory mixing—xLSTM’s sLSTM and mLSTM—reach near‑perfect accuracy. Pure Transformers and SSMs fail because they lack recurrent state updates that can remember exact parity information.
* In a **Multi‑Query Associative Recall** test with up to 256 key–value pairs and sequence lengths of 2048 tokens, an xLSTM configuration mixing both sLSTM and mLSTM blocks outperforms all non‑Transformer baselines and even rivals larger Transformers despite using far fewer parameters.
* The **Long Range Arena** suite shows consistent gains across image classification from patches, byte‐level text classification, and other long‑context problems.

### Scaling to Real Language Modeling  

Training on 15 B tokens from SlimPajama (the same budget used for many open LLM baselines), xLSTM achieved lower validation perplexity than GPT‑3‑size Transformers, LLaMA, Mamba (an SSM), RWKV series (recurrent baselines), and several linear transformers. An ablation study confirmed that both exponential gating *and* matrix memory independently contributed to these gains.

When scaling up to 300 B tokens—a dataset size typical for state-of-the-art LLMs—xLSTM variants continued to dominate:

| Model | 125 M | 350 M | 760 M | 1.3 B |
|------|-------|-------|-------|-------|
| xLSTM[7:1] | ★ | ★ | ★ | ★ |
| xLSTM[1:0] | ★ | ★ | ★ | ★ |
| LLaMA | — | — | — | — |
| Mamba | — | — | — | — |
| RWKV‑4 | — | — | — | — |

(★ indicates best perplexity among all methods for that size.)

Beyond perplexity:

* **Length extrapolation**: models trained on context 2048 retained low perplexity up to 16 k tokens; Transformers degraded sharply because their self‑attention matrix grows quadratically.
* **Downstream reasoning tasks**: xLSTM beat competitors on most benchmarks (e.g., ARC‐Easy/Challenge, HellaSwag), only losing to Mamba on a few niche tasks.
* **Domain coverage**: On PALOMA’s 571 text domains, xLSTM[1:0] achieved lower perplexity than every other method in >99 % of domains.
* **Scaling laws**: Plotting loss versus model size shows all families follow similar power laws; however xLSTM’s curve lies consistently below Transformers and SSMs—meaning larger xLSTMs should retain their advantage.

Inference speed also scales linearly with sequence length, unlike quadratic scaling for Transformers. While current CUDA kernels for mLSTM are not yet as optimized as FlashAttention, preliminary results already demonstrate higher throughput at long contexts because memory remains constant.

## Why Reviving RNNs Is Worth It  

1. **Linear time & constant memory** – Ideal for edge devices or servers where GPU memory is at a premium.
2. **Better long‐context handling** – No need for costly cache management; hidden states carry forward indefinitely.
3. **Fine‐grained associative memory** – Matrix memories give LSTMs expressive power comparable to attention without explicit pairwise token interactions.
4. **Compatibility with existing training pipelines** – xLSTM slots into standard residual architectures; existing optimizer tricks (AdamW, learning rate schedules) work unchanged.
5. **New research directions** – Exponential gating opens possibilities for adaptive forgetting/remembering strategies; matrix memories hint at hybrid “fast weight”–plus–slow weight systems scalable to billions of parameters.

## Limitations & Future Work  

* sLSTM’s hidden–hidden mixing still forces serial computation; although an efficient CUDA kernel reduces slowdown to <2× compared with fully parallel mLSTM, further optimization is needed.
* Current mLSTM kernels are about four times slower than FlashAttention; dedicated kernel engineering could close this gap.
* Matrix memory scales quadratically in hidden dimension \(d\); careful trade‑offs between dimension size and GPU throughput will be crucial for very large models.
* Forget‐gate initialization remains sensitive; improper values can cause either vanishing or exploding updates.
* The large‐scale experiments used relatively modest hyperparameter tuning; more aggressive optimization may push performance even higher.

## Conclusion  

The story of LSTMs isn’t over—it’s evolving. By revisiting two foundational ideas—gating and constant error carousel—and augmenting them with exponential dynamics and richer memory representations, xLSTM demonstrates that classic recurrent networks can compete head‑to‑head with Transformers even at billions of parameters.

For practitioners interested in low‑latency inference on long sequences or developers targeting resource‑constrained environments, xLSTMs offer a promising alternative that combines decades of RNN wisdom with modern scaling tricks. As kernel implementations improve and community adoption grows, we may soon see “recurrent” language models listed alongside their Transformer peers—not as nostalgic relics but as first‐class contenders in modern AI.

*(The codebase is publicly available at https://github.com/NX-AI/xlstm.)*



# Exponential Gating Explained: Giving Neural Networks a Second Chance to Forget  

## Introduction  

Long Short‑Term Memory networks (LSTMs) have been the workhorse of sequence modeling for decades. Their core idea – a constant‑error carousel combined with sigmoid‑based input, forget and output gates – solved the vanishing‑gradient problem that plagued earlier recurrent nets. Yet, after more than thirty years of research we still see one recurring complaint: **LSTMs struggle to revise what they have stored**.  

When a model encounters new evidence that contradicts an earlier decision, the original LSTM cell can only *dampen* the outdated information via its forget gate. Because the forget gate is bounded between 0 and 1 (thanks to the sigmoid), it can never completely erase or “over‑forget” a previously stored value. In practice this limitation shows up in tasks that require **dynamic revision**, such as the nearest‑neighbor search described in the xLSTM paper.  

The recent “Extended LSTM” (xLSTM) family introduces **exponential gating** – a simple but powerful modification that replaces—or augments—the classic sigmoid with an exponential activation. In this post we break down why sigmoid gates limit revision, how exponential gates work, and what concrete gains they bring to tasks like nearest‑neighbor search.

## Why Sigmoid Gates Are Too Gentle  

Recall the classic LSTM update for a scalar cell state \(c_t\):

\[
c_t = f_t \, c_{t-1} + i_t \, z_t ,
\]

where \(f_t = \sigma(\tilde{f}_t)\) and \(i_t = \sigma(\tilde{i}_t)\).  
Both \(f_t\) and \(i_t\) lie in \([0,1]\). The forget gate multiplies the old memory by a factor that can *only* shrink it; it cannot *increase* its magnitude beyond what was already present. If we later discover that an earlier stored value was wrong, the only tool we have is to make \(f_t\) smaller on subsequent steps so that the old value decays more quickly.  

Two consequences follow:

1. **Slow revision** – The decay is exponential in the number of steps but bounded by \(\le 1\). If a wrong value was stored early, many future steps are needed before its influence becomes negligible.  
2. **Limited “undo” capacity** – The model cannot *overwrite* a strong memory with a stronger opposite signal because both input and forget gates are capped at 1.

In tasks like **nearest‑neighbor search**, the model has to scan an entire sequence, keep track of the currently best match, and replace it when a closer vector appears later. A standard LSTM can lower the influence of an outdated match (by setting \(f_t<1\)) but cannot *raise* a new match enough to dominate the old one quickly enough, leading to higher mean‑squared error.

## The Idea of Exponential Gating  

Exponential gating removes the upper bound on gate magnitudes by feeding the pre‑activation through an exponential function:

\[
i_t = \exp(\tilde{i}_t), \qquad
f_t = 
\begin{cases}
\sigma(\tilde{f}_t) & \text{(sigmoid option)}\\[4pt]
\exp(\tilde{f}_t)   & \text{(exponential option)}.
\end{cases}
\]

Because \(\exp(x) > 0\) for any real \(x\), gates can now take any positive value, from arbitrarily small (approaching zero) to arbitrarily large. The key effects are:

* **Aggressive forgetting** – Setting \(\tilde{f}_t\) to a large negative number makes \(f_t\) close to zero, essentially wiping out previous memory in a single step.  
* **Forceful updating** – A large positive \(\tilde{i}_t\) yields an input gate far greater than 1, allowing new information to *overshoot* any existing content and dominate the cell state instantly.  

To keep training stable, xLSTM couples exponential gating with two tricks:

1. **Normaliser state (\(n_t\))** – Tracks the cumulative strength of input and forget gates so that hidden outputs can be normalised as \(\tilde{h}_t = c_t / n_t\). This prevents runaway values from exploding.
2. **Stabiliser state (\(m_t\))** – Logs the maximum log‑gate value seen so far (see Eq. (5)–(7) in the paper). Before using a gate we subtract \(m_t\), yielding a scaled version (\(i'_t, f'_t\)) that is mathem‑atically equivalent but numerically safe.

These two mechanisms ensure that while gates can become large when needed, they stay well‑behaved during back‑propagation.

## How Exponential Gating Helps Nearest‑Neighbor Search  

The nearest‑neighbor task used in the xLSTM experiments works like this:

* A reference vector is given at time step 0.
* The model receives a stream of vectors \(\{\mathbf{x}_1,\dots,\mathbf{x}_T\}\).
* At each step it must keep track of which past vector has smallest distance to the reference.
* After scanning the whole sequence it outputs the value attached to that best vector.

With classic sigmoid gates, if a better match appears late in the sequence, the cell must *gradually* reduce the contribution of the earlier match via successive forget steps. This slow decay yields higher error because early strong memories linger too long.

Exponential gating changes the story:

* When a new vector beats the current best distance, we set a **large input gate** (\(i_t \gg 1\)). The update term \(i_t z_t\) instantly outweighs any remaining old memory.
* Simultaneously we set a **tiny forget gate** (\(f_t \approx 0\)) for that step, erasing almost all of the previous cell content.
* The normaliser state automatically rescales the hidden output so that downstream layers see a clean “best so far” signal.

Empirically (Figure 1 left panel in the paper), this simple modification slashes mean‑squared error on nearest‑neighbor search compared to baseline LSTMs and even brings performance close to Transformer baselines that have full self‑attention.

## Beyond Nearest Neighbors – General Benefits  

While nearest‑neighbor search is an intuitive illustration, exponential gating improves any problem where **revision** or **rapid overwriting** of memory matters:

| Scenario | What’s needed | Sigmoid gating | Exponential gating |
|----------|---------------|----------------|--------------------|
| Rare token prediction | Store sparse cues for low‑frequency words | Weak updates → dilution over long contexts | Strong updates → preserve rare cues |
| Code execution / state tracking | Overwrite variable bindings as program runs | Slow decay leads to stale states | Immediate overwrite eliminates stale states |
| Reinforcement learning memories | Replace outdated value estimates with fresh observations | Gradual forgetting harms credit assignment | Aggressive forgetting improves learning speed |

The paper’s synthetic formal‑language experiments (parity, copy–repeat tasks) also show that only models with *memory mixing* plus exponential gates can solve problems requiring precise state tracking—something plain Transformers or linear State‑Space Models cannot do.

## Putting It All Together: xLSTM Blocks  

Exponential gating is only one piece of xLSTM’s recipe. The authors combine it with two novel memory structures:

1. **sLSTM** – Scalar memory plus *memory mixing* across multiple heads; exponential gates let each head revise its own scalar quickly.
2. **mLSTM** – Matrix memory updated by a covariance rule (\(\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \mathbf{v}_t \mathbf{k}_t^\top\)). Here exponential input/forget gates control how much each key–value pair influences the growing matrix.

Both variants are wrapped inside residual blocks (post or pre up‑projection depending on memory type). Stacking these blocks yields deep xLSTM architectures that scale linearly with sequence length while retaining expressive power comparable to billions‑parameter Transformers.

## Takeaway  

*Traditional sigmoid gates are safe but conservative; they prevent LSTMs from truly “forgetting” or “overwriting” past information.*  
Exponential gating removes this ceiling, letting networks aggressively erase or amplify memories when needed. When paired with proper normalisation and stabilisation, it gives LSTMs their second chance — turning them from slow modulators into fast revisers of stored knowledge.

The experimental results in “Extended Long Short-Term Memory” demonstrate that this modest change translates into measurable gains on tasks where revision matters most (nearest neighbor search, rare token prediction) and lifts full language models into competitive territory with modern Transformers and State‑Space Models.

If you’re building recurrent or hybrid models that need reliable state tracking over long horizons—think code synthesis, reinforcement learning agents, or time‑series forecasting—consider swapping sigmoid gates for exponential ones. It might just be the missing piece that lets your network remember *and forget* with confidence.



# Memory Makeover: From Scalar Cells to Matrix Memories in xLSTM

## Introduction  

Long Short‑Term Memory networks (LSTMs) have been the workhorse of sequence modeling for three decades. Their core idea—store information in a **scalar cell state** and update it with carefully gated additions—solved the vanishing‑gradient problem that plagued vanilla RNNs. Yet, as language models grew to billions of parameters, classic LSTMs started showing three fundamental bottlenecks:

1. **Irrevocable storage decisions** – once a value is written into the scalar cell, it is hard to overwrite it later.  
2. **Limited storage capacity** – a single number per hidden unit forces the model to compress all context information, hurting rare‑token prediction.  
3. **Sequential bottleneck** – hidden‑to‑hidden connections force strictly left‑to‑right processing.

The recent **xLSTM** family tackles these issues head‑on. In this post we focus on the most dramatic architectural shift: replacing the scalar cell with a **matrix memory** in the **mLSTM** variant. We’ll explore why a matrix is a natural upgrade, how it is updated, and what practical gains it brings for tasks like rare‑token prediction and associative recall.

## From One Number to a Whole Matrix  

### The classic LSTM cell  

In a vanilla LSTM the cell state \(c_t\) is just a single real number (or a vector of such numbers when we stack many cells). Its update rule

\[
c_t = f_t \, c_{t-1} + i_t \, z_t
\]

adds a new contribution \(z_t\) scaled by an **input gate** \(i_t\), while a **forget gate** \(f_t\) controls how much of the past is retained. Because \(c_t\) is scalar (or at most a low‑dimensional vector), every time step competes for the same tiny storage space.

### The matrix memory idea  

The mLSTM lifts this restriction by letting the memory be a full matrix \(\mathbf{C}_t \in \mathbb{R}^{d \times d}\). Instead of storing one number per hidden unit, we now store **\(d^2\) degrees of freedom** that can capture richer relationships between different features.

Conceptually this matches the *key–value* formulation used in Transformers: each time step produces a **key** vector \(\mathbf{k}_t\) and a **value** vector \(\mathbf{v}_t\). The matrix memory accumulates outer products of these pairs:

\[
\mathbf{C}_t = f_t \,\mathbf{C}_{t-1} + i_t \,\mathbf{v}_t \mathbf{k}_t^{\!\top}.
\]

The term \(\mathbf{v}_t \mathbf{k}_t^{\!\top}\) is exactly a *covariance* (or outer‑product) update; it stores a *binding* between the key and its associated value. The forget gate now behaves like a decay factor on the whole matrix, while the input gate multiplies the learning rate for each new key–value binding.

When we later query the memory with a vector \(\mathbf{q}_t\), retrieval simply amounts to matrix multiplication:

\[
\tilde{\mathbf{h}}_t = 
\frac{\mathbf{C}_t \,\mathbf{q}_t}
{\max\bigl(|\mathbf{n}_t^{\!\top}\mathbf{q}_t|, 1\bigr)},
\qquad
\mathbf{h}_t = \mathbf{o}_t \odot \tilde{\mathbf{h}}_t,
\]

where \(\mathbf{n}_t = f_t\,\mathbf{n}_{t-1}+i_t\,\mathbf{k}_t\) is a normalizer that keeps track of how strong each key has been weighted over time. The denominator prevents division by values close to zero, stabilizing training.

## Why Does a Matrix Help Rare‑Token Prediction?

Rare tokens appear infrequently during training, so an LSTM’s compressed scalar memory can’t afford to allocate dedicated slots for them. The result: higher perplexity on low‑frequency words (as shown in the paper’s Figure 2 right panel).

With a matrix memory:

* **Higher dimensionality** gives more “room” for distinct token embeddings. Each rare token can form its own key–value binding without crowding existing ones.
* **Covariance storage** naturally separates different patterns because each outer product lives in an orthogonal subspace (if keys are approximately orthogonal). This maximizes signal‑to‑noise ratio for seldom‑seen items.
* **Exponential gating** (input gate \(i_t = e^{\tilde{i}_t}\)) lets the model sharply increase the learning rate for rare events that matter, while the normalizer ensures that such spikes don’t explode numerically.

Empirically, xLSTM models equipped with mLSTM blocks achieve lower perplexities on rare-token buckets than both classic LSTMs and even large Transformers trained on the same data budget.

## Associative Recall Gets a Boost  

The **Multi‑Query Associative Recall (MQAR)** benchmark stresses pure memory capacity: during a sequence we present many random key–value pairs, then later ask the model to retrieve several values given their keys. Traditional LSTMs struggle because they must compress thousands of pairs into a few scalar cells; performance quickly collapses as the number of pairs grows.

Matrix memories excel here because each pair contributes an independent outer product to \(\mathbf{C}_t\). In experiments with up to 256 pairs and context lengths of 2048 tokens:

* **xLSTM[1:1]** (equal mix of sLSTM and mLSTM blocks) outperformed every non‑Transformer baseline, including RWKV and Mamba.
* Even when using only mLSTM blocks (**xLSTM[1:0]**) the model matched or surpassed Transformer baselines that rely on quadratic attention.
* Adding sLSTM heads on top of mLSTM did not hurt capacity; instead it helped by providing complementary scalar mixing.

The result demonstrates that a simple covariance update rule—already known from fast weight programmers—gives LSTMs truly *associative* memory capabilities comparable to attention but at linear cost in sequence length.

## Parallelism Made Possible  

A common critique of recurrent models is their sequential nature; each step depends on hidden states from the previous step. The mLSTM sidesteps this bottleneck because its recurrence does not involve hidden‑to‑hidden connections—only the matrix memory evolves over time. By rewriting the recurrence as a series of parallelizable matrix operations (similar to FlashAttention’s kernel), mLSTM can be executed in parallel across timesteps on modern GPUs.

Thus we get:

| Property | Classic LSTM | mLSTM |
|----------|--------------|-------|
| Storage shape | Scalar / small vector | Full \(d\times d\) matrix |
| Update rule | Additive scalar | Covariance outer product |
| Parallelizability | Sequential | Parallelizable (no hidden‑hidden links) |
| Rare-token handling | Limited | High capacity |
| Associative recall | Weak | Strong |

The trade‑off is computational: multiplying two \(d\times d\) matrices costs \(O(d^3)\). However, for typical hidden dimensions (\(d=64-256\)) these operations are still dominated by GPU matrix kernels and add only modest wall‑clock overhead compared with quadratic self‑attention.

## Takeaway  

Switching from scalar cells to matrix memories fundamentally changes what an LSTM can remember:

* It gives each timestep its own *key–value binding*, reducing interference among distant events.
* Exponential gating combined with a normalizer stabilizes these high‑magnitude updates.
* The resulting mLSTM block retains linear time and constant memory complexity while delivering *Transformer‑level* performance on rare-token prediction and associative recall.

If you’ve been skeptical about bringing recurrent networks back into large language modeling, xLSTM’s matrix memory offers concrete evidence that LSTMs can scale competitively—provided we give them enough internal “real estate.” The code is open source at https://github.com/NX-AI/xlstm, so feel free to experiment with your own scaling experiments!



# Parallelizing Recurrent Networks: How mLSTM Breaks the Sequential Bottleneck

Recurrent neural networks have long been the workhorse for sequence modeling. Their defining characteristic—*hidden‑to‑hidden* connections—forces a strict left‑to‑right processing order, which makes them difficult to accelerate on modern GPUs. The paper *xLSTM: Extended Long Short-Term Memory* introduces a new recurrent variant, **mLSTM**, that removes these hidden‑to‑hidden dependencies while keeping a true recurrent memory. In this post we unpack how mLSTM achieves GPU‑friendly parallelism, why the design still preserves the expressive power of classic LSTMs, and what this means for large‑scale language modeling.

---

## 1. Why Classic RNNs Are Hard to Parallelize

In a standard LSTM the cell update at time step *t* depends on the hidden state *hₜ₋₁*:

\[
c_t = f_t \odot c_{t-1} + i_t \odot z_t ,\qquad
h_t = o_t \odot \psi(c_t).
\]

The gate activations *(iₜ, fₜ, oₜ)* themselves are computed from both the current input **xₜ** and the previous hidden state **hₜ₋₁**. Because **hₜ₋₁** is needed to evaluate **hₜ**, each step must wait for the result of the previous one. On a GPU this results in many small, sequential kernels—far from the massive matrix multiplications that GPUs excel at.

---

## 2. The Core Idea of mLSTM: Decouple Gates from Hidden State

mLSTM keeps a recurrent *memory matrix* **Cₜ ∈ ℝ^{d×d}**, but it **removes the hidden‑to‑hidden term from the gate equations**. Concretely:

* The *input*, *forget*, and *output* gates are **pure functions of the current input** **xₜ** (plus learned biases), e.g.

\[
i_t = \exp(\mathbf{w}_i^\top \mathbf{x}_t + b_i), \qquad
f_t = \sigma(\mathbf{w}_f^\top \mathbf{x}_t + b_f) \,\text{or}\, \exp(\cdot).
\]

* No recurrent weight vectors (the *r* terms in classic LSTM) appear in these equations.

Because each gate now depends only on **xₜ**, all gate values for an entire sequence can be computed **in parallel** using a single matrix multiplication followed by an elementwise nonlinearity.

---

## 3. How Memory Is Updated Without Hidden‑to‑Hidden Connections

Even though the gates are feed‑forward, mLSTM still maintains a **temporal memory** thanks to a *covariance update rule* reminiscent of fast‑weight programmers:

\[
\mathbf{C}_t = f_t \,\mathbf{C}_{t-1} + i_t \,\mathbf{v}_t \mathbf{k}_t^\top .
\]

Here:

* **kₜ** (the *key*) and **vₜ** (the *value*) are linear projections of **xₜ**.
* The forget gate *fₜ* acts as a decay factor on the previous memory matrix.
* The input gate *iₜ* scales the outer product **vₜ kₜᵀ**, which inserts new information.

Crucially, this recurrence only involves matrix–matrix operations. When we unroll the recurrence across time, it becomes a simple **prefix sum (scan)** over the sequence of scaled outer products. Scans are well‑studied in GPU literature and can be executed with log‑depth parallel algorithms (e.g., using CUDA’s `thrust::inclusive_scan`). As a result, **the whole memory update can be performed in O(log T) parallel steps instead of O(T) sequential steps**, where *T* is sequence length.

---

## 4. Retrieval Is Also Parallelizable

The hidden output for step *t* is read from the memory matrix by a query vector **qₜ**, itself a linear projection of **xₜ**:

\[
\tilde{\mathbf{h}}_t = 
\frac{\mathbf{C}_t\,\mathbf{q}_t}{\max\!\left(|\mathbf{n}_t^\top \mathbf{q}_t|,\;1\right)},
\qquad
h_t = o_t \odot \tilde{\mathbf{h}}_t .
\]

All terms on the right are either already computed in parallel (the gates, keys, values, queries) or are simple matrix–vector multiplications that can be batched across time steps. The normalization denominator uses a separate “normalizer state” **nₜ**, which follows exactly the same scan pattern as **Cₜ**, so it can be computed jointly.

---

## 5. What Do We Gain? A Quick Comparison

| Property | Classic LSTM | mLSTM |
|----------|--------------|-------|
| Hidden‑to‑hidden connections | Yes (requires sequential processing) | No (gates are feed‑forward) |
| Memory structure | Scalar cell vector | Matrix memory (covariance) |
| Parallelism level | Limited to per‑step operations | Full sequence‑wide parallel scans and batched matmul |
| GPU utilization | Low (many small kernels) | High (large GEMM and scan kernels) |
| Expressivity | Strong but vulnerable to vanishing gradients | Retains long‑term storage via decay/additive updates; avoids vanishing gradients by design |

Empirically, the paper reports that mLSTM attains **comparable or better perplexity** than Transformers and State Space Models while maintaining linear compute cost with respect to sequence length and constant memory usage.

---

## 6. Why Does Removing Hidden‑to‑Hidden Not Hurt Performance?

One might worry that discarding hidden feedback will cripple modeling power. Two design choices keep mLSTM expressive:

1. **Matrix Memory as an Associative Store:** By storing key–value outer products, mLSTM can retrieve information based on content similarity rather than positional recurrence alone—much like attention but without quadratic cost.
2. **Exponential Gating & Normalization:** Using exponential activations for *iₜ* (and optionally *fₜ*) allows gates to amplify or suppress updates dramatically, giving the network fine control over how quickly old memories decay.

Together these mechanisms enable mLSTM to *revise* stored information (thanks to exponential forget gates) and to memorize richer structures (thanks to the high‑dimensional matrix). The hidden state becomes a readout of this associative store rather than an independent recurrent channel.

---

## 7. Practical Implications

### Faster Training & Inference
Because all time steps share the same large GEMM kernels, training scales almost identically to feed‑forward transformer blocks when using modern hardware like NVIDIA A6000 or TPU v4. During inference, mLSTM’s constant memory footprint means you can generate arbitrarily long sequences without quadratic cache growth—a long‑standing bottleneck for transformers.

### Simpler Hardware Deployments
The lack of hidden‑to‑hidden dependencies removes the need for custom scan operators on edge devices; a straightforward implementation using existing BLAS libraries suffices. This aligns with the paper’s claim that xLSTM models are “well suited for industrial applications and implementations on the edge.”

### Compatibility with Existing Architectures
mLSTM slots neatly into residual block backbones (the “xLSTM block” in the paper). You can therefore stack mLSTM blocks alongside other modules—self‑attention layers, convolutional encoders—without worrying about mismatched sequence handling.

---

## 8. Limitations to Keep in Mind

While mLSTM eliminates sequential bottlenecks, it does introduce a dense \(d\times d\) memory matrix, which increases computational load (matrix multiplications scale with \(d^2\)). The authors note that their current CUDA kernels are slower than FlashAttention by roughly fourfold; however, they also point out that this overhead is modest compared to overall wall‑clock time because all operations remain highly parallelizable.

Moreover, careful initialization of forget gates is required to prevent uncontrolled growth or excessive decay of the memory matrix—a nuance shared with any fast weight / associative memory system.

---

## 9. Closing Thoughts

The mLSTM variant demonstrates that we don’t have to choose between *recurrent memory* and *parallel efficiency*. By moving gating logic entirely onto feed‑forward paths and delegating temporal dynamics to an associative matrix store updated via a scan-friendly covariance rule, mLSTM preserves long-term dependence handling while unlocking GPU acceleration across entire sequences.

If you’re building large language models or any sequential system where inference latency matters, consider experimenting with mLSTM (or its sibling sLSTM for tasks requiring explicit hidden mixing). The open-source implementation linked in the xLSTM paper gives you a solid starting point—and perhaps a glimpse into a future where recurrent architectures regain their place alongside transformers in mainstream deep learning pipelines.



# Scaling LSTMs to Billions of Parameters: Lessons from Training xLSTM on 300 B Tokens  

In recent years the research community has largely moved from classic recurrent networks to Transformer‑based language models.  Yet the original Long Short‑Term Memory (LSTM) architecture still harbors powerful ideas—constant‑error carousel, gating, and a simple recurrent formulation—that have never been explored at the scale of modern large language models (LLMs).  The **xLSTM** paper revisits this legacy by (1) introducing *exponential gating* with stabilisation, (2) redesigning the memory cell into a **scalar sLSTM** (with memory mixing) and a **matrix mLSTM** (with a covariance update rule), and (3) wrapping these cells inside modern residual‑block backbones.

Below is a concise walkthrough of the *large‑scale* experiments reported in the paper, where xLSTM variants were trained on **300 B tokens** of the SlimPajama dataset and compared against state‑of‑the‑art Transformers, State Space Models (SSMs), and other recurrent alternatives.  The focus is on three practical aspects that matter most for practitioners: **perplexity**, **context‑length extrapolation**, and **downstream task performance**.

---

## 1. Experimental Setup at a Glance  

| Model family | Representative model(s) | Parameter range | Training data |
|--------------|-------------------------|-----------------|---------------|
| **xLSTM** | xLSTM[1:0] (all mLSTM blocks) & xLSTM[7:1] (7 mLSTM + 1 sLSTM) | 125 M – 1.3 B | 300 B tokens (SlimPajama) |
| **Transformer** | Llama (7B‑class) | 125 M – 1.3 B (scaled down) | Same |
| **SSM** | Mamba | 125 M – 1.3 B | Same |
| **RNN / Linear Transformer** | RWKV‑4, GLA, HGRN2 | 125 M – 1.3 B | Same |

All models use the *pre‑LayerNorm* residual backbone that is standard in contemporary LLMs.  Training hyper‑parameters (learning rate schedule, mixed precision, optimizer) are kept identical across families so that differences can be attributed to the architecture itself.

---

## 2. Perplexity on the Validation Set  

Perplexity (PPL) is the canonical metric for autoregressive language modeling.  Table 1 in the paper reports validation PPL for each model size; the key takeaways are:

| Size | xLSTM[1:0] PPL | xLSTM[7:1] PPL | Llama PPL | Mamba PPL | RWKV‑4 PPL |
|------|----------------|----------------|-----------|-----------|------------|
| 125 M | **7.9** | 8.2 | 9.5 | 10.4 | 11.2 |
| 350 M | **6.6** | 6.8 | 7.9 | 8.9 | 9.4 |
| 760 M | **5.9** | 6.0 | 7.2 | 8.0 | 8.7 |
| 1.3 B | **5.4** | **5.5** | 6.6 | 7.5 | 8.2 |

*Why it matters*: Across all scales, the pure matrix‑memory variant (**xLSTM[1:0]**) consistently beats both mixed variants and all baselines by a noticeable margin (≈0.8–1.2 lower PPL). This demonstrates that the covariance update rule together with exponential gating yields a more expressive representation than self‑attention alone—especially when we push the parameter count into the billion‑parameter regime.

---

## 3. Context‑Length Extrapolation  

A common failure mode for many Transformers is that they degrade sharply when asked to attend to sequences longer than they were trained on (e.g., beyond the training context of 2048 tokens).  

The authors evaluated each model on contexts up to **16k tokens**, measuring perplexity as a function of length while keeping the *training context* fixed at 2048 tokens.

- **xLSTM[1:0]** maintains an almost flat curve: perplexity rises by < 15 % even at length 16k.
- **xLSTM[7:1]**, thanks to its single sLSTM block that introduces hidden‑to‑hidden mixing, shows a mild increase but still far better than Transformers.
- **Llama** exhibits a steep climb; perplexity roughly doubles at length 8k and triples at 16k.
- **Mamba** and **RWKV‑4** also degrade, though not as dramatically as Llama because they are recurrent by design; still their curves lie above those of xLSTM.

The takeaway is that *linear* recurrence (as in xLSTM) combined with exponential gating provides a natural mechanism for extending memory far beyond the trained window without incurring quadratic cost.

---

## 4. Downstream Task Performance  

Beyond next‑token prediction, the authors benchmarked each model on several *real‑world* tasks that probe reasoning, factual recall, and common sense:

| Task Suite | Metric (higher = better) |
|------------|--------------------------|
| ARC Easy / Challenge (AI2 Reasoning Challenge) | Accuracy |
| BoolQ (question answering) | Accuracy |
| PIQA (physical commonsense) | Accuracy |
| RTE (textual entailment) | Accuracy |
| HellaSwag (situational reasoning) | Accuracy |

Across all model sizes:

- **xLSTM[1:0]** wins on *every* task except sometimes ARC where Mamba narrowly beats it at the smallest scale.
- The advantage ranges from +1 point on BoolQ up to +4 points on HellaSwag for the largest model.
- When aggregated into a *average* score across tasks, xLSTM scores ~3–5 points higher than Llama and ~5–7 points higher than Mamba.

These results suggest that stronger long‑range memory is not just a curiosity—it translates into tangible gains on tasks that require tracking entities or reasoning over extended contexts.

---

## 5. Scaling Laws – What Happens When We Go Bigger?  

The paper fits classic power‑law scaling curves of form  

\[
\text{PPL}(N,D)=A\;N^{-\alpha}+B\;D^{-\beta}+C,
\]

where \(N\) is model size and \(D\) is dataset size.  

All families exhibit similar exponents (\(\alpha\approx0.07\), \(\beta\approx0.25\)), confirming that *the same scaling dynamics apply*.  
However, the **offset \(C\)** for xLSTM is noticeably lower than for Transformers & SSMs, implying that even as we push toward trillion parameters, xLSTM will retain its edge.

The authors extrapolate that a *10× larger* xLSTM (≈13 B parameters, still modest compared to GPT‑4’s >100 B) would achieve roughly **4–5 lower perplexity** than an equivalently sized Transformer—potentially closing or even overtaking current SOTA benchmarks.

---

## 6. Practical Takeaways  

1️⃣ **Exponential gating matters** – replacing sigmoid gates with \(\exp(\cdot)\) plus stabilisation lets the network “forget” more aggressively or “store” more decisively, which directly improves both perplexity and long‑range behavior.

2️⃣ **Matrix memory wins for scaling** – The mLSTM’s covariance update provides a dense associative store without extra parameters; it scales well when paired with pre‑up‑projection residual blocks.

3️⃣ **Hybrid blocks can be useful** – Adding a single sLSTM block (the “mixing” head) boosts performance on synthetic state‑tracking tasks while keeping most of the parallelism of mLSTM.

4️⃣ **Linear compute & constant memory** – Unlike self‑attention’s \(O(L^2)\) cost, xLSTM’s recurrence stays \(O(L)\), enabling stable inference on long sequences with minimal GPU memory pressure—a clear advantage for production environments where latency matters.

5️⃣ **Current implementation is still slower per token than FlashAttention**, but because it avoids quadratic growth it *outpaces* Transformers in total wall‑clock time when generating very long passages or serving many concurrent requests.

---

## 7. Limitations & Future Work  

- The sLSTM block cannot be fully parallelised; its CUDA kernel runs ≈2× slower than mLSTM.
- mLSTM’s matrix updates are computationally heavy (\(d\times d\) ops). Optimised kernels similar to FlashAttention could shave several factors off runtime.
- Forget‐gate initialization needs care; poor defaults can destabilise training.
- The experiments kept hyperparameters fixed across scales; dedicated tuning could push results even further.

Nevertheless, these hurdles are engineering rather than theoretical roadblocks—future work will likely close them rapidly given the community’s momentum around fast kernels and mixed precision tricks.

---

## 8. Bottom Line  

Training an LSTM‐derived architecture at *billion‑parameter* scale is no longer an academic curiosity; with exponential gating and matrix memories it becomes competitive with—and in many respects superior to—Transformer‐based LLMs:

- Lower validation perplexity across all tested sizes.
- Robust extrapolation to contexts ≥ 16k tokens.
- Consistently better downstream reasoning performance.
- Favorable scaling trends suggesting continued advantage as we move toward larger models.

If you are building language models where long context handling, memory efficiency, or edge deployment matter, giving xLSTM a look should be high on your priority list—especially now that an open-source implementation (`https://github.com/NX-AI/xlstm`) is available for experimentation and further optimisation.



# When Does Bigger Mean Better? Decoding the Scaling Laws of xLSTM vs. Transformers  

## Introduction  

Scaling laws have become a go‑to diagnostic for large language models (LLMs). By plotting validation perplexity (or loss) against model size, data volume or compute, researchers repeatedly find a clean power‑law relationship: performance improves roughly as a straight line on a log‑log plot, with a modest offset that depends on the architecture.  

The recent **xLSTM** paper asks the same question that has driven the Transformer boom: *What happens if we take the classic Long Short‑Term Memory (LSTM), address its long‑standing weaknesses, and scale it to billions of parameters?* The answer is striking—xLSTM follows a classic scaling law, but its curve sits **below** (i.e., better than) those of state‑of‑the‑art Transformers and State‑Space Models (SSMs). In this post we unpack why the exponent is similar across families while the offset stays favorable for xLSTM, and we explore what this means for the next generation of LLMs.  

---

## Recap: The three ingredients of xLSTM  

Before diving into scaling, let’s recall what makes xLSTM different from a vanilla LSTM:  

1. **Exponential gating** – Input and forget gates can use an exponential activation (instead of a sigmoid) together with a stabilizer state. This lets the model *revise* earlier storage decisions without running into overflow problems.  

2. **New memory structures** –  
   * **sLSTM** keeps a scalar cell but adds a normalizer state and “memory mixing” across multiple heads, allowing richer interaction between cells.  
   * **mLSTM** upgrades the cell to a full matrix **C**, updated by a covariance (outer‑product) rule. The matrix acts like a fast weight memory, storing key–value pairs that can be retrieved with a query vector.  

3. **Residual xLSTM blocks** – The sLSTM or mLSTM cell is embedded in a residual block that either projects up after (sLSTM) or before (mLSTM) the nonlinearity, following the Cover’s theorem intuition that high‑dimensional embeddings make histories easier to separate.

These design choices give xLSTM three practical advantages:  
* **Revisability** (thanks to exponential gating),  
* **Higher storage capacity** (matrix memory), and  
* **Linear time & constant memory cost w.r.t. sequence length**, unlike the quadratic attention in Transformers.

---

## Observed Scaling Behavior  

The authors trained several families on the same 300 B token subset of SlimPajama, varying model size from ≈125 M to 1.3 B parameters. For each family they plotted validation perplexity \(P\) against model size \(N\) in log–log space and fitted

\[
\log P = \alpha \log N + \beta,
\]

where \(\alpha\) is the *scaling exponent* (slope) and \(\beta\) is the *offset* (intercept).  

### What the plots reveal  

| Architecture | Exponent (\(\alpha\)) | Offset (\(\beta\)) |
|--------------|----------------------|--------------------|
| Transformer (Llama) | ≈ ‑0.07 | higher |
| State‑Space Model (Mamba) | ≈ ‑0.07 | medium |
| xLSTM (mixed s/m blocks) | ≈ ‑0.07 | **lowest** |

*All three families share essentially the same exponent.* This means that **doubling model size yields roughly the same percentage improvement in perplexity across architectures**—a universal law governed mainly by data distribution and task difficulty rather than model internals.

What sets xLSTM apart is its **lower offset** (\(\beta\)). On every size point, perplexity is consistently better (by ~5–10 % relative) than Transformers and even stronger than SSMs. In other words, for any given parameter budget, an xLSTM will be more accurate than its Transformer counterpart.

---

## Why Does xLSTM Keep a Favorable Offset?  

### 1. Better Utilization of Parameters  

Exponential gating lets each gate dynamically amplify or suppress signals without being capped at 1. Consequently, *fewer* parameters are needed to achieve strong temporal credit assignment—the network can quickly forget irrelevant past information and strongly retain important signals. This flexibility translates into higher *effective capacity*, meaning each weight contributes more to reducing loss.

### 2. Richer Memory Embedding  

The matrix memory in mLSTM behaves like an associative cache where each key–value pair contributes an outer product \(\mathbf{v}_t\mathbf{k}_t^\top\). This update captures second‑order interactions that would otherwise require many scalar cells and deep stacking in a regular LSTM or Transformer. As a result, even modestly sized mLSTMs store more distinct patterns, improving rare‑token prediction and long‑range recall—two major contributors to overall perplexity.

### 3. Linear Complexity + High Dimensional Embedding  

Because recurrence costs are linear in sequence length, training can afford *longer* contexts without ballooning memory usage. The residual block’s up‑projection creates high‑dimensional hidden states before mixing, which aligns with Cover’s theorem: patterns that were tangled in low dimensions become linearly separable after projection. The combination reduces the burden on later layers, allowing earlier recurrent units to focus on capturing essential dynamics rather than compensating for representational bottlenecks.

### 4. Stabilization Guarantees  

The stabilizer state \(m_t\) ensures that exponential gates do not overflow during long sequences, preserving gradient flow across thousands of timesteps. Stable gradients mean training can converge faster and reach lower minima for a given compute budget—again pulling down the offset.

---

## Implications for Future LLM Development  

### A Viable Alternative at Scale  

If the scaling exponent remains universal—as these experiments suggest—then any architecture that can push down its offset will dominate at all scales. xLSTM demonstrates exactly this; thus we can expect **billion‑parameter xLSTMs to match or beat contemporary 10+ B Transformers**, especially when hardware favors linear recurrence over attention’s quadratic kernels.

### Compute Efficiency on Edge Devices  

Since memory usage stays constant with sequence length, xLSTMs are naturally suited for on‑device inference where context windows may be long (e.g., real‑time transcription). The lower offset implies fewer parameters are needed for a target quality level, further reducing power consumption.

### Hybrid Models  

The paper shows mixed configurations—xLSTM[7:1] (seven mLSTM blocks per sLSTM block)—perform slightly better than pure mLSTM or pure sLSTM stacks. This suggests future LLM designs could interleave **fast associative matrix cells** with **scalar cells that provide fine‐grained mixing**, yielding architectures that blend the strengths of both worlds.

### Research Directions  

* **Optimized CUDA kernels** – The current implementation is slower than FlashAttention; closing this gap could make xLSTMs even more competitive on GPUs and TPUs.  
* **Deeper scaling experiments** – Extending beyond 1.3 B parameters would verify whether the offset advantage persists or even widens at tens of billions of weights.  
* **Task‑specific fine‑tuning** – Because matrix memory excels at rare token recall, domains with heavy terminology (legal text, scientific literature) may benefit disproportionately from xLSTMs.

---

## Takeaway  

Scaling laws tell us *how* performance improves with size; they don’t dictate *which* architecture sits closest to the optimal curve. xLSTM proves that by revisiting core LSTM ideas—exponential gating and richer memories—we can shift the entire scaling curve downward while preserving the same exponent observed for Transformers and SSMs.

In practical terms: **bigger still means better**, but “bigger” now includes *better organized* parameters. For anyone building tomorrow’s LLMs, keeping an eye on recurrent designs like xLSTM is worthwhile—not merely as a nostalgic nod to early RNNs but as a forward‑looking strategy for efficient, high‑performance language models.



# Practical Trade‑offs: Speed, Memory, and Parallelism in xLSTM Implementations  

## Introduction  

The recent **xLSTM** paper revisits the classic LSTM architecture and pushes it to the scale of modern large language models (LLMs). By introducing **exponential gating**, a **scalar‑memory sLSTM**, and a **matrix‑memory mLSTM**, the authors demonstrate that recurrent networks can close the gap with Transformers and State‑Space Models (SSMs) on perplexity, scaling, and long‑context performance.  

However, moving from a research prototype to a production‑ready model brings a very different set of questions: how fast does inference run, how much GPU memory does it consume, and can the operations be parallelized efficiently? This post walks through the engineering trade‑offs highlighted in the paper, focusing on three practical aspects:

1. **CUDA kernel optimizations** – custom kernels for sLSTM and mLSTM.  
2. **Matrix‑memory compute costs** – the $d \times d$ state in mLSTM.  
3. **Inference speed and throughput** – head‑to‑head comparison with popular Transformers (Llama) and SSMs (Mamba).  

All numbers are taken directly from the authors’ experiments; no external speculation is added.

---

## 1. CUDA Kernels: From Theory to Practice  

### 1.1 Why custom kernels are needed  

Both sLSTM and mLSTM add operations that are absent in vanilla LSTMs:

* **Exponential gating** – gates are computed with $\exp(\cdot)$ instead of a sigmoid. This can lead to overflow, so a stabilizer state $m_t$ (Eq. (6)) must be maintained across timesteps.
* **Normaliser state** – $n_t$ accumulates weighted gate products and appears in the hidden‐state division (Eq. (5) for sLSTM, Eq. (9) for mLSTM).
* **Matrix memory updates** – mLSTM performs $\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \mathbf{v}_t \mathbf{k}_t^\top$, a rank‑1 outer product addition on a $d \times d$ matrix.

These operations cannot be expressed efficiently with standard PyTorch primitives alone; they require fused kernels that keep intermediate values in registers, minimize memory traffic, and avoid unnecessary synchronizations.

### 1.2 sLSTM kernel  

The sLSTM kernel is *sequential* because of **memory mixing** (hidden‑to‑hidden recurrence). The authors implemented a CUDA kernel that:

* Loads the previous cell $c_{t-1}$, normaliser $n_{t-1}$, and stabilizer $m_{t-1}$ into registers.
* Computes $\tilde{i}_t$, $\tilde{f}_t$, $\tilde{o}_t$, $\tilde{z}_t$ from the input $x_t$ and previous hidden state $h_{t-1}$.
* Applies exponential activation (or sigmoid for $f_t$) and updates $m_t$, $i'_t$, $f'_t$ via Eq. (6).  
* Updates $c_t$ and $n_t$, then divides to obtain $\tilde{h}_t = c_t / n_t$.

Because every timestep depends on the previous hidden state, the kernel essentially performs a *scan* across time. The implementation is highly optimized—register reuse cuts down global memory accesses—and runs **≤ 2× slower** than the fully parallel mLSTM kernel (see Section 7 of the paper).

### 1.3 mLSTM kernel  

The matrix memory eliminates hidden‑to‑hidden connections, enabling full parallelization across timesteps using a *prefix‑sum* style scan on the matrix $\mathbf{C}$:

* The outer product $\mathbf{v}_t \mathbf{k}_t^\top$ is computed with a single GEMM call (`torch.bmm`), which GPUs handle exceptionally well.
* The forget gate acts as a decay factor; an elementwise multiplication $f_t \mathbf{C}_{t-1}$ is again a GEMM.
* The normaliser $\mathbf{n}_t$ follows the same scan pattern but with vectors instead of matrices.

Although the algorithmic complexity is $O(d^2)$ per step (because of the matrix update), modern GPUs execute these dense linear algebra ops at near‑peak throughput. The authors note that with their current kernel **mLSTM is ≈ 4× slower** than FlashAttention or Mamba’s scan implementation—not because of algorithmic inefficiency but because the kernel still lacks low‑level optimizations (e.g., tiling, shared‑memory caching). A future “FlashAttention‑style” implementation could close this gap.

---

## 2. Matrix‑Memory Compute Costs  

### 2.1 Memory capacity vs. compute  

The key novelty of mLSTM is its **matrix memory** $\mathbf{C} \in \mathbb{R}^{d\times d}$, which replaces the scalar cell in a traditional LSTM. This brings two practical consequences:

| Aspect | Effect |
|--------|--------|
| **Storage capacity** | Quadratic increase in representational power; enables associative recall of up to thousands of key–value pairs (Fig. 3). |
| **Compute** | Each timestep requires a rank‑1 outer product ($\mathbf{v}_t\mathbf{k}_t^\top$) and an elementwise scaling of $\mathbf{C}_{t-1}$. Both are $O(d^2)$. |

In practice, for models with hidden dimension $d=1024$, a single update touches more than one million floating‑point numbers per token—a nontrivial load compared with the elementwise gates of an LSTM or RNN.

### 2.2 Mitigating overhead  

The authors adopt several tricks to keep wall‑clock time reasonable:

* **LayerNorm before projection** ensures keys/values have zero mean, stabilizing the outer product without additional clipping.
* The denominator $\max\{| \mathbf{n}_t^\top \mathbf{q}_t|, 1\}$ avoids division by tiny numbers, preventing numeric spikes that would otherwise force extra safety checks.
* All matrix ops are batched across heads when multiple heads are used; this allows CuBLAS to fuse kernels automatically.

Even with these measures, mLSTM’s raw FLOP count remains higher than that of a comparable Transformer block. Nonetheless, because memory grows linearly with sequence length (the matrix is *constant w.r.t.* time), inference on long contexts stays feasible—a stark contrast to attention’s quadratic cost.

---

## 3. Inference Speed & Throughput  

The paper presents an extensive benchmark on **1.3 B‑parameter models**, measuring both per-token generation time (single batch) and maximal decoding throughput (varying batch size). The results are summarized below.

### 3.1 Generation time (single token)  

| Model | Architecture | Generation time (ms/token) |
|-------|--------------|----------------------------|
| xLSTM[1:0] (mLSTM only) | Recurrent + matrix memory | ~3 ms |
| xLSTM[7:1] (mostly mLSTM) | Mixed s/m blocks | ~3–4 ms |
| Mamba | SSM | ~4 ms |
| RWKV‑4 | RNN | ~3 ms |
| Llama (7B style) | Transformer + KV cache | ~12 ms |

*Transformers show quadratic scaling*: even with a static key‑value cache they are roughly **four times slower** than any recurrent variant at batch size 1 because each new token requires attention over all previous positions.

### 3.2 Decoding throughput (tokens/s)  

Throughput was measured by increasing batch size while keeping prefill length fixed at 16 tokens:

| Batch size | xLSTM[1:0] | Mamba | RWKV‑4 | Llama |
|------------|-----------|-------|--------|-------|
| 1          | ~300 t/s  | ~250 t/s | ~310 t/s | ~80 t/s |
| 8          | ~2400 t/s | ~2000 t/s | ~2500 t/s | ~300 t/s |
| 16         | ~4500 t/s | ~3800 t/s | > 5000 t/s | ~550 t/s |

Because both xLSTM variants have *constant memory* w.r.t. sequence length, they can scale batch size almost linearly until GPU memory becomes saturated. In contrast, Llama’s quadratic attention quickly hits a memory wall beyond batch 8.

### 3.3 Trade‑off summary  

| Dimension | Transformers (e.g., Llama) | SSMs (e.g., Mamba) | xLSTM (s/m mix) |
|-----------|----------------------------|--------------------|-----------------|
| **Parallelism** | Highly parallelizable across tokens via self‑attention; limited by quadratic memory/compute for long contexts. | Parallelizable via state scans; still linear in length but cheaper than attention. | mLSTM fully parallelizable; sLSTM requires sequential scan → ≤ 2× slower than mLSTM but still faster than attention for long contexts. |
| **GPU Memory**   | $O(L^2)$ where $L$=context length → prohibitive beyond 4–8k tokens without cache tricks. | $O(1)$ per layer → modest growth with depth only. | Same as SSMs; matrix memory adds constant overhead ($d^2$ floats). |
| **Compute per token** | $O(d^2 L)$ due to attention matrix multiplication; heavy for large $L$. | $O(d^2)$ per layer thanks to linear recursions; modest constant factor. | mLSTM: $O(d^2)$ + outer product; sLSTM: $O(d)$ but sequential scan → slightly higher latency per token.|

Overall, for applications that require *very long context windows* or *low latency generation*, xLSTM offers an attractive middle ground: better scaling than pure Transformers while delivering comparable or better perplexity.

---

## 4. Takeaways for Practitioners  

1. **Choose the right block mix** – If maximal speed matters more than squeezing every last bit of perplexity, lean toward an xLSTM[7:1] configuration (mostly mLSTM). Adding occasional sLSTM blocks improves expressive power on tasks needing state tracking without dramatically hurting throughput.
2. **Expect higher GPU FLOPs** – The matrix update costs dominate compute budgets; plan for larger TFLOP budgets or use mixed precision (`tf32`/`float16`) to keep power consumption reasonable.
3. **Kernel maturity matters** – The current implementation is already competitive but still lags behind highly tuned FlashAttention kernels by about ×4 for mLSTM and ≤ 2× for sLSTM. Investing in custom kernels (shared‐memory tiling, warp‐level reductions) will yield immediate speed gains.
4. **Scalability remains promising** – Scaling law plots (Fig. 13 & Fig. 16 in the paper) show that xLSTM retains its advantage as model size grows from 125 M to > 10 B parameters, suggesting that engineering improvements will only amplify its practicality.

---

## Conclusion  

xLSTM demonstrates that extending classic recurrent architectures can rival Transformers not only in predictive quality but also in scalability to billions of parameters. From an engineering perspective, however, there are concrete trade‑offs:

* **sLSTM** offers richer state mixing at the cost of sequential execution; custom CUDA kernels keep this penalty modest.
* **mLSTM** delivers full parallelism but incurs quadratic compute per step due to its matrix memory; careful kernel design can close the current performance gap.
* Inference speed and throughput favor recurrent designs for long contexts, while Transformers still excel on short sequences where attention’s parallelism shines.

As GPU software stacks evolve—especially around optimized scan/fuse primitives—the remaining gaps will shrink further, making xLSTM a compelling choice for anyone building large language models that need both *long context awareness* and *efficient inference*.
