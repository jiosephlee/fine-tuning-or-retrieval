# Memory Makeover: From Scalar Cells to Matrix Memories in xLSTM

## Introduction  

Long Short‑Term Memory networks (LSTMs) have been the workhorse of sequence modeling for three decades. Their core idea—store information in a **scalar cell state** and update it with carefully gated additions—solved the vanishing‑gradient problem that plagued vanilla RNNs. Yet, as language models grew to billions of parameters, classic LSTMs started showing three fundamental bottlenecks:

1. **Irrevocable storage decisions** – once a value is written into the scalar cell, it is hard to overwrite it later.  
2. **Limited storage capacity** – a single number per hidden unit forces the model to compress all context information, hurting rare‑token prediction.  
3. **Sequential bottleneck** – hidden‑to‑hidden connections force strictly left‑to‑right processing.

The recent **xLSTM** family tackles these issues head‑on. In this post we focus on the most dramatic architectural shift: replacing the scalar cell with a **matrix memory** in the **mLSTM** variant. We’ll explore why a matrix is a natural upgrade, how it is updated, and what practical gains it brings for tasks like rare‑token prediction and associative recall.

## From One Number to a Whole Matrix  

### The classic LSTM cell  

In a vanilla LSTM the cell state \(c_t\) is just a single real number (or a vector of such numbers when we stack many cells). Its update rule

\[
c_t = f_t \, c_{t-1} + i_t \, z_t
\]

adds a new contribution \(z_t\) scaled by an **input gate** \(i_t\), while a **forget gate** \(f_t\) controls how much of the past is retained. Because \(c_t\) is scalar (or at most a low‑dimensional vector), every time step competes for the same tiny storage space.

### The matrix memory idea  

The mLSTM lifts this restriction by letting the memory be a full matrix \(\mathbf{C}_t \in \mathbb{R}^{d \times d}\). Instead of storing one number per hidden unit, we now store **\(d^2\) degrees of freedom** that can capture richer relationships between different features.

Conceptually this matches the *key–value* formulation used in Transformers: each time step produces a **key** vector \(\mathbf{k}_t\) and a **value** vector \(\mathbf{v}_t\). The matrix memory accumulates outer products of these pairs:

\[
\mathbf{C}_t = f_t \,\mathbf{C}_{t-1} + i_t \,\mathbf{v}_t \mathbf{k}_t^{\!\top}.
\]

The term \(\mathbf{v}_t \mathbf{k}_t^{\!\top}\) is exactly a *covariance* (or outer‑product) update; it stores a *binding* between the key and its associated value. The forget gate now behaves like a decay factor on the whole matrix, while the input gate multiplies the learning rate for each new key–value binding.

When we later query the memory with a vector \(\mathbf{q}_t\), retrieval simply amounts to matrix multiplication:

\[
\tilde{\mathbf{h}}_t = 
\frac{\mathbf{C}_t \,\mathbf{q}_t}
{\max\bigl(|\mathbf{n}_t^{\!\top}\mathbf{q}_t|, 1\bigr)},
\qquad
\mathbf{h}_t = \mathbf{o}_t \odot \tilde{\mathbf{h}}_t,
\]

where \(\mathbf{n}_t = f_t\,\mathbf{n}_{t-1}+i_t\,\mathbf{k}_t\) is a normalizer that keeps track of how strong each key has been weighted over time. The denominator prevents division by values close to zero, stabilizing training.

## Why Does a Matrix Help Rare‑Token Prediction?

Rare tokens appear infrequently during training, so an LSTM’s compressed scalar memory can’t afford to allocate dedicated slots for them. The result: higher perplexity on low‑frequency words (as shown in the paper’s Figure 2 right panel).

With a matrix memory:

* **Higher dimensionality** gives more “room” for distinct token embeddings. Each rare token can form its own key–value binding without crowding existing ones.
* **Covariance storage** naturally separates different patterns because each outer product lives in an orthogonal subspace (if keys are approximately orthogonal). This maximizes signal‑to‑noise ratio for seldom‑seen items.
* **Exponential gating** (input gate \(i_t = e^{\tilde{i}_t}\)) lets the model sharply increase the learning rate for rare events that matter, while the normalizer ensures that such spikes don’t explode numerically.

Empirically, xLSTM models equipped with mLSTM blocks achieve lower perplexities on rare-token buckets than both classic LSTMs and even large Transformers trained on the same data budget.

## Associative Recall Gets a Boost  

The **Multi‑Query Associative Recall (MQAR)** benchmark stresses pure memory capacity: during a sequence we present many random key–value pairs, then later ask the model to retrieve several values given their keys. Traditional LSTMs struggle because they must compress thousands of pairs into a few scalar cells; performance quickly collapses as the number of pairs grows.

Matrix memories excel here because each pair contributes an independent outer product to \(\mathbf{C}_t\). In experiments with up to 256 pairs and context lengths of 2048 tokens:

* **xLSTM[1:1]** (equal mix of sLSTM and mLSTM blocks) outperformed every non‑Transformer baseline, including RWKV and Mamba.
* Even when using only mLSTM blocks (**xLSTM[1:0]**) the model matched or surpassed Transformer baselines that rely on quadratic attention.
* Adding sLSTM heads on top of mLSTM did not hurt capacity; instead it helped by providing complementary scalar mixing.

The result demonstrates that a simple covariance update rule—already known from fast weight programmers—gives LSTMs truly *associative* memory capabilities comparable to attention but at linear cost in sequence length.

## Parallelism Made Possible  

A common critique of recurrent models is their sequential nature; each step depends on hidden states from the previous step. The mLSTM sidesteps this bottleneck because its recurrence does not involve hidden‑to‑hidden connections—only the matrix memory evolves over time. By rewriting the recurrence as a series of parallelizable matrix operations (similar to FlashAttention’s kernel), mLSTM can be executed in parallel across timesteps on modern GPUs.

Thus we get:

| Property | Classic LSTM | mLSTM |
|----------|--------------|-------|
| Storage shape | Scalar / small vector | Full \(d\times d\) matrix |
| Update rule | Additive scalar | Covariance outer product |
| Parallelizability | Sequential | Parallelizable (no hidden‑hidden links) |
| Rare-token handling | Limited | High capacity |
| Associative recall | Weak | Strong |

The trade‑off is computational: multiplying two \(d\times d\) matrices costs \(O(d^3)\). However, for typical hidden dimensions (\(d=64-256\)) these operations are still dominated by GPU matrix kernels and add only modest wall‑clock overhead compared with quadratic self‑attention.

## Takeaway  

Switching from scalar cells to matrix memories fundamentally changes what an LSTM can remember:

* It gives each timestep its own *key–value binding*, reducing interference among distant events.
* Exponential gating combined with a normalizer stabilizes these high‑magnitude updates.
* The resulting mLSTM block retains linear time and constant memory complexity while delivering *Transformer‑level* performance on rare-token prediction and associative recall.

If you’ve been skeptical about bringing recurrent networks back into large language modeling, xLSTM’s matrix memory offers concrete evidence that LSTMs can scale competitively—provided we give them enough internal “real estate.” The code is open source at https://github.com/NX-AI/xlstm, so feel free to experiment with your own scaling experiments!
