\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### How exactly does the entropy‑based patching algorithm decide where to cut a byte sequence?
Question:
The paper describes two variant constraints for entropy patching: a global threshold $\theta_g$ and an approximate monotonicity constraint $\theta_r$. I am unclear on how these are applied in practice. For a given byte $x_t$, do we compute its entropy $H(x_t)$ using the small LM and then compare it to $\theta_g$ *and* the difference $H(x_t)-H(x_{t-1})$ to $\theta_r$?  Is the global constraint applied first, and only if it fails we look at the monotonic constraint, or are they combined with an OR/AND logic?  Also, how is the threshold $\theta_g$ chosen to obtain a target average patch size?
Answer:
**Answer**

In the BLT paper the “entropy‑based patching’’ step is a **pre‑processing** operation that runs once for every training (or inference) example while the data are being loaded.  
For each byte position $t$ we first compute the next‑byte entropy

$$
H(x_t)=\sum_{v\in\mathcal V}p_{e}(x_t=v\mid \mathbf x_{<t})\;\log p_{e}(x_t=v\mid \mathbf x_{<t}),
$$

where $p_{e}$ is the distribution produced by the small byte‑level language model (the *entropy model*).  
The entropy values are then examined with **two independent criteria**:

1. **Global entropy constraint**  

   $$
   H(x_t) > \theta_g .
   $$

2. **Approximate‑monotonicity constraint**  

   $$
   H(x_t)-H(x_{t-1}) > \theta_r .
   $$

A new patch is started **whenever either condition holds**. In other words the logic is an **OR**, not an AND, and there is no ordering such as “apply the global test first and only if it fails look at the monotonic test”. The two tests are evaluated in parallel for each byte; if *any* of them fires a boundary marker is set to 1 (the start of a new patch). This matches the description in Section 3.3 of the paper (“identifies points that are high relative to the previous entropy … can also be interpreted as identifying points that break approximate monotonically decreasing entropy within the patch”).

---

### Why an OR makes sense

* The global threshold captures *absolute* high‑uncertainty locations (e.g., the first byte of a new word, punctuation after a number, etc.).  
* The monotonicity test captures *relative* spikes inside a long low‑entropy region – for instance a sudden increase in uncertainty inside an otherwise predictable block (code comment, repeated pattern).  
* Using OR means we do not miss either type of boundary; using AND would be far too selective and would produce patches that are too long in many realistic texts.

---

### Choosing the global threshold $\theta_g$

The goal of $\theta_g$ is to obtain a **desired average patch size** (or equivalently a target number of patches per byte). The procedure used in the experiments is:

1. **Collect entropies on a held‑out subset** of the training corpus with the fixed entropy model.  
2. **Sort all entropy values** $ \{H(x_t)\} $ in descending order.  
3. Suppose we want an average patch length of $s$ bytes, i.e. roughly $1/s$ patch boundaries per byte. If the total number of bytes in the sample is $N$, we need about $N/s$ boundaries.  
4. Set $\theta_g$ to be the value at the $(N/s)$‑th position in the sorted list (the quantile that gives exactly that many boundaries). In practice this is implemented as a simple scan: increase or decrease $\theta_g$ until the empirical mean patch size measured on the sample matches $s$ within a tolerance.

Because the monotonicity constraint also creates boundaries, after fixing $\theta_g$ we validate that the **combined** OR rule yields the target average size; if it is slightly off we can tweak $\theta_g$ a few steps more. The paper reports using this procedure to obtain average patch sizes of 4 – 8 bytes for different experiments.

---

### Summary of the workflow

1. Run the small LM over the raw byte stream → obtain per‑byte entropies $H(x_t)$.  
2. For every position $t$:  
   *if* $H(x_t) > \theta_g$ **or** $H(x_t)-H(x_{t-1}) > \theta_r$ → mark a new patch start; otherwise continue the current patch.  
3. The resulting binary mask (1 = patch start, 0 = inside patch) is stored as part of the dataloader output and later consumed by BLT’s encoder/decoder.

Thus, both constraints are evaluated simultaneously, combined with logical **OR**, and $\theta_g$ is calibrated on a corpus sample so that the expected number of boundaries yields the desired mean patch length. This simple rule gives BLT its dynamic, data‑driven ability to allocate more compute where next‑byte prediction is intrinsically hard while keeping patches long where entropy stays low.

### Why does the paper claim that BPE tokenizers cannot satisfy the incremental patching property?
Question:
In Section 2.5 the authors define incremental patching as $f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i}$ and say BPE violates this because the same prefix can be tokenized differently depending on future bytes. Could someone give a concrete example with a short string that shows this behavior? Additionally, is there a known modification (e.g., using a delimiter token) that makes BPE incremental, and what would be the trade‑offs of such a modification?
Answer:
**Answer**

The incremental‑patching property requires that the sequence of *patches* that we obtain from a prefix of the input is exactly the prefix of the patch sequence we would obtain from the full input.  
Formally, for a patching function \(f_{p}\),

\[
f_{p}(\mathbf{x}_{<i}) \;=\; \bigl(f_{p}(\mathbf{x})\bigr)_{<i}\qquad\forall i .
\]

If this holds we can decide, while we are reading the bytes, whether a new patch begins or not – we never have to look ahead.

BPE (byte‑pair‑encoding) violates the equation because the way it groups the first few bytes depends on what comes **after** those bytes.  Below is a minimal concrete illustration that follows exactly the tokenizer used in the paper (the Llama 3 BPE vocabulary of size 128 K).

---

### A concrete example

Consider three short strings that share the same three‑byte prefix:

```
s₁ = "ab"
s₂ = "abc"
s₃ = "abx"
```

Suppose the BPE vocabulary contains the following tokens (these are realistic for a large‑vocabulary BPE):

| token | byte sequence |
|-------|---------------|
| `ab`  | 0x61 0x62 |
| `abc` | 0x61 0x62 0x63 |
| `a`   | 0x61 |
| `b`   | 0x62 |
| `c`   | 0x63 |
| `x`   | 0x78 |
| …     | … |

Now run the standard greedy BPE algorithm on each string:

* **Tokenising `s₁ = "ab"`**  
  The longest matching token at the first position is `ab`.  
  → token sequence = `[ab]`.

* **Tokenising `s₂ = "abc"`**  
  At position 0 the longest match is now `abc`, because three bytes are available.  
  → token sequence = `[abc]`.

* **Tokenising `s₃ = "abx"`**  
  The longest match at position 0 is again `ab`; after that we are left with `x`.  
  → token sequence = `[ab, x]`.

Now look at the *prefix* consisting only of the first two bytes, i.e. the byte string “ab”.  
If we apply \(f_{p}\) to this prefix (ignoring what follows) we obtain

\[
f_{p}("ab") = [ab].
\]

But this is **not** always a prefix of the full tokenisation:

* For `s₁` it is: `[ab]` is exactly the whole token list → property holds.
* For `s₂` it is *not*: `[ab]` is **not** a prefix of `[abc]`. The full tokenisation has merged the third byte into a larger token, so the patch boundary that would have been placed after “ab” disappears.
* For `s₃` it *is* a prefix: `[ab]` precedes `[x]`.

Thus, depending on what byte follows “ab”, that same two‑byte prefix can be split into one patch (`[ab]`) or be merged into a longer patch (`[abc]`). The mapping from bytes to patches is therefore *non‑incremental*.

The same phenomenon occurs with any BPE vocabulary that contains multi‑byte tokens overlapping shorter ones – which is precisely why BPE was designed as a compression scheme: it prefers longer merges when possible. Consequently, you cannot decide locally (from a prefix only) whether a new patch starts.

---

### Making BPE incremental

The paper mentions one simple way to recover incrementality: **insert an explicit delimiter token after every patch**. Concretely, you could augment the vocabulary with a special “\(\langle\text{patch}\rangle\)” symbol and post‑process every BPE output so that after each ordinary token you insert this delimiter. When generating, you stop reading bytes once you have emitted a delimiter; no future bytes are needed to know where the current patch ends.

**Effect of this modification**

| Aspect | With delimiter (incremental) | Original BPE (non‑incremental) |
|--------|-----------------------------|--------------------------------|
| **Byte‑to‑patch determinism** | Each byte decides locally whether it ends a patch (the delimiter tells you). | Patch boundaries may shift when more bytes become visible. |
| **Sequence length** | Increases because every token is followed by an extra symbol; average length grows roughly by a factor \(1+\frac{1}{\text{average tokens per segment}}\). In practice for Llama 3’s average 4‑byte token, length increases by ≈ 25 %. | Minimal overhead – only the tokens themselves. |
| **Model cost** | Larger input dimension for both embedding and final projection layers (the delimiter adds one more entry to the vocabulary). More decoding steps overall because each original token now occupies two steps in the transformer. | Smaller embedding table; fewer transformer steps per byte‑stream. |
| **Compatibility with existing checkpoints** | Not compatible – you would need to re‑train or fine‑tune with the new token set. | Directly reusable with pre‑trained checkpoints. |
| **Benefit for BLT‑style dynamic compute** | Enables true incremental patching, so at generation time you can decide “do I need to invoke the latent transformer?” without peeking ahead. This matches the assumption of Section 2.5 and lets BLT keep its flop‑control guarantees. | You cannot safely make that decision; you would have to run a look‑ahead predictor or accept occasional mis‑patches. |

In practice, adding a delimiter doubles the number of *patch decisions* that must be made by the model, which erodes part of BLT’s efficiency gains. The paper therefore prefers genuine dynamic patching (entropy‑based or whitespace) that already satisfies incrementality without an artificial overhead.

---

### Summary

*BPE’s greedy longest‑match rule makes its token boundaries depend on future bytes; therefore identical prefixes can be tokenised differently once more context arrives, violating incremental patching.*  
A simple fix—adding an explicit delimiter token after every BPE unit—restores incrementality but at non‑negligible cost in sequence length and model parameters. The BLT authors opt instead for true byte‑level patching schemes (entropy or whitespace) that are naturally incremental and avoid those trade‑offs while still allowing dynamic allocation of compute.*

### What is the role of the cross‑attention layers in the local encoder and decoder, and why are they placed after each transformer layer?
Question:
The architecture section mentions that after every transformer layer in the encoder (and before every transformer layer in the decoder) there is a cross‑attention block that pools bytes into patch representations (or vice‑versa). I am confused about why this repeated pooling is necessary – would a single cross‑attention at the end of the encoder be sufficient? Also, how does the query initialization (max‑pool, hash embedding, or learned) affect performance, according to the ablations?
Answer:
In the Byte Latent Transformer the **local encoder** ( $\mathcal{E}$ ) and **local decoder** ( $\mathcal{D}$ ) are tiny transformer stacks that live between the raw‑byte stream and the big “latent” transformer $\mathcal{G}$. Their sole purpose is to **convert a variable‑length sequence of byte embeddings into a compact set of patch embeddings (and back again)**. Because a patch may contain anywhere from a few to dozens of bytes, a single transformer layer on the bytes cannot by itself produce a representation that is already aligned with the patch boundaries – the bytes that belong to one patch are scattered throughout the layer’s hidden matrix.

### Why cross‑attention after every transformer layer?

The architecture inserts a **cross‑attention block after each transformer layer** (both in $\mathcal{E}$ and in $\mathcal{D}$). In each block the current *patch queries* attend only to the *byte keys/values* that belong to the same patch. This has two consequences:

1. **Progressive pooling** – after the first transformer layer the queries are initialized (e.g. by max‑pooling the byte embeddings of that patch). The cross‑attention refines these queries by looking at the updated byte representations produced by that layer, then passes the refined queries to the next transformer layer. Repeating this at every depth lets the model *gradually aggregate information* from many bytes while still allowing each transformer layer to perform its usual local computation (self‑attention within a sliding window of $w_{\mathcal{E}}$ bytes). If we performed only one cross‑attention at the very end, the early transformer layers would never see any signal that they are part of a bigger patch; they would be forced to treat every byte independently, which defeats the goal of building expressive patch vectors efficiently.

2. **Dynamic alignment with patch boundaries** – patches are not fixed; entropy‑based or whitespace‑based segmentation can change from one training example to another. By recomputing the query‑to‑byte attention at every depth, each layer automatically respects the current segmentation without needing a separate “hard‑pooling” step that could become a bottleneck.

In short, **the repeated cross‑attention is what makes the encoder/decoder truly hierarchical**: low‑level layers focus on short‑range byte relations, while higher layers receive increasingly richer, already pooled patch queries.

### Decoder side

The decoder mirrors this pattern but swaps the roles: byte representations become *queries* that attend to *patch keys/values*. Placing cross‑attention before each decoder transformer layer ensures that every decoding step first integrates global patch context into the byte‑level stream before applying local self‑attention, yielding more accurate byte predictions.

### Query initialization ablations

The paper experiments with three ways of initializing the patch queries for the *first* cross‑attention block:

| Initialization | How it works | Empirical effect |
|----------------|--------------|------------------|
| **Max‑pool** (default) | For each patch we simply take a max over its constituent byte embeddings and linearly project this vector to the query space. | Provides a strong, data‑independent starting point; gives the best overall Bits‑Per‑Byte (BPB) when combined with cross‑attention in both encoder and decoder. |
| **Hash embedding** | Each byte n‑gram (n=3…8) is hashed into a small embedding table; all hash embeddings belonging to a patch are summed (with normalization) and used as the initial query. | Improves performance on noisy or code‑heavy domains (e.g. Common‑Crawl, GitHub) because n‑gram hashes inject local context that pure max‑pooling discards. The gain is modest (~0.02–0.04 BPB) but consistent across scales. |
| **Learned constant** | A single learned vector is broadcast as the query for every patch (i.e. no pooling at all). | Performs worst; without any information about the bytes inside a patch the cross‑attention has nothing useful to attend to, leading to higher BPB (≈0.05 BPB worse than max‑pool). |

The ablation table (Section 7, “Cross‑Attention”) shows that **only when pooling‐based initialization is used does adding encoder cross‑attention improve results**, confirming that the model needs a sensible “seed” representation for each patch. The hash embedding variant helps most when combined with larger patches (average size ≳6 bytes) because it supplies extra sub‑byte cues that compensate for fewer global steps.

### Intuition

Think of each patch as a mini “sentence” composed of bytes. A lone transformer layer can only understand relationships inside its fixed attention window; it cannot magically know where one sentence ends and another begins. The cross‑attention step is analogous to reading a paragraph summary: you first look at all words (bytes) in that paragraph, form an initial summary (max or hash), then let higher layers refine it while still being able to peek back at individual words if needed. Repeating this summary step after every layer mirrors how humans repeatedly rephrase and integrate information while reading.

### Takeaway

- A single pooling operation at the top would discard useful intermediate refinements and force early layers to work without any notion of patches.
- Repeated cross‑attention lets each transformer layer specialize: low layers refine raw byte features locally; higher layers operate on increasingly informative patch queries.
- Among initializations, **max‑pooling gives the strongest baseline**, hash n‑gram embeddings add domain-specific robustness, and learned constant queries are insufficient.

Thus, placing cross‑attention after *every* transformer layer is essential for building expressive, dynamically sized patch representations while keeping both encoder and decoder lightweight.

### How are Bits‑Per‑Byte (BPB) values comparable across models with different patch sizes and vocabularies?
Question:
The paper reports BPB as a tokenizer‑independent metric. However, models with larger average patches process fewer steps per byte, which could affect loss scaling. Is BPB directly comparable between a model using space‑patching (average 6 bytes/patch) and one using entropy‑patching (average 4.5 bytes/patch)? Does the definition of BPB implicitly assume a per‑byte cross‑entropy loss that is independent of how many transformer steps were taken?
Answer:
**Short answer:**  
Yes – the Bits‑Per‑Byte (BPB) numbers reported in the paper can be compared directly between a model that uses space‑patching (≈ 6 bytes / patch) and one that uses entropy‑patching (≈ 4.5 bytes / patch).  BPB is defined as the total cross‑entropy loss summed over **every byte** in the dataset and then divided by the number of bytes (and by $\ln 2$ to convert nats to bits).  Because the loss is taken at the byte level, it does **not** depend on how many transformer steps (i.e. how many patches) were required to process those bytes.  The metric therefore implicitly assumes a per‑byte cross‑entropy that is independent of the patching scheme or of the number of “global‑transformer” steps taken.

---

### Why the patch size does not affect BPB

The paper defines BPB as  

\[
\text{BPB}(\mathbf{x}) \;=\;
\frac{\mathcal L_{\mathrm{CE}}(\mathbf{x})}
{\ln(2)\; n_{\text{bytes}}}\,,
\]

where $\mathcal L_{\mathrm{CE}}(\mathbf{x})=\sum_{i=1}^{n_{\text{bytes}}}
-\log p(x_i\mid \mathbf{x}_{<i})$ is the ordinary token‑free cross‑entropy loss evaluated **byte‑by‑byte**.  

* The loss at position $i$ is computed after the model has produced a distribution over the 256 possible byte values; this distribution comes from either a *local* step (inside a patch) or after a *global* latent‑transformer step when a patch boundary is reached.  
* Regardless of whether a particular byte required a global step or only the cheap local encoder/decoder, its contribution to the loss is counted once and exactly once.  

Consequently, if two models see exactly the same byte sequence during evaluation, they will accumulate exactly the same total loss **if** their per‑byte predictive distributions are identical, even though one model may have taken far fewer global steps because its patches are larger.  The denominator $n_{\text{bytes}}$ normalises by the total number of bytes, so the resulting BPV (bits per *byte*) reflects only prediction quality, not computational effort.

### What would make BPB incomparable?

BPB would cease to be a fair comparison only if the training or evaluation protocol changed the *effective* number of bytes that each loss term represented.  For example:

* **Non‑incremental patching**: If a patching scheme could look ahead and change its segmentation depending on future bytes, then some bytes would be “covered” by different numbers of predictions across models, breaking the one‑to‑one correspondence between loss terms and bytes. The paper explicitly requires incremental patching (Equation $f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i}$) precisely to avoid this issue.
* **Byte‑level label smoothing or weighting** that varies with patch size. The paper does not employ such tricks; all bytes are weighted equally in $\mathcal L_{\mathrm{CE}}$.

Since neither of these occurs, BPB remains a tokenizer‑independent, “per‑byte” metric.

### Intuitive interpretation

Think of BPB as asking: *“If we were to compress the raw byte stream with an ideal entropy coder built from the model’s predictions, how many bits would we need per byte?”*  The compression cost does not care whether we first chunk the stream into long or short patches; it only cares about how well we predict each individual byte given everything that preceded it.

In practice, larger patches reduce the number of expensive latent‑transformer invocations (fewer global steps), which improves **efficiency** (flops per byte) but does not directly improve or degrade **predictive quality**.  Hence you can observe two models having very different inference flop budgets yet reporting almost identical BPB values—exactly what the authors demonstrate in Figures 4 and 5.

### Connection to broader concepts

BPB is analogous to *bits per character* used in classic character‑level language modeling and to *bits per token* for token‑based LMs; all are simply normalized cross‑entropy measures.  Normalising by a fixed atomic unit (byte, character, token) makes it possible to compare models that operate at different granularities.  This idea appears throughout language‑modeling literature whenever one wants an architecture‑agnostic measure of predictive performance (e.g., Xue et al., 2022; Yu et al., 2023).

---

**Bottom line:**  
The definition of BPB treats every byte equally and abstracts away from how many transformer steps were performed to predict it. Therefore BPB scores from a space‑patched BLT (≈ 6 bytes/patch) and an entropy‑patched BLT (≈ 4.5 bytes/patch) are directly comparable; any difference in BPB reflects genuine differences in predictive ability, not merely differences in patch length or compute allocation.

### What is the exact FLOP formula used for the latent global transformer when counting "per byte" cost?
Question:
In Section 4.1 the FLOP count for BLT includes a term \text{Transf. FL}(h_{\mathcal{G}}, l_{\mathcal{G}}, m=n_{ctx}/n_p, V=0) / n_p.  I want to understand each argument: $h_{\mathcal{G}}$ hidden size, $l_{\mathcal{G}}$ layers, $m$ context length in patches (so $n_{ctx}$ bytes divided by number of patches), and $V$ = 0 because there is no output vocabulary projection at this stage. Could someone expand this into the standard QKV + FFN FLOP equations and show how it reduces to per‑byte cost? Also, why is there no addition of patch‑dependent positional embeddings?
Answer:
The term that appears in § 4.1

\[
\frac{\text{Transf.\;FL}\bigl(h_{\mathcal G},\,l_{\mathcal G},\,m=n_{\text{ctx}}/n_{p},\,V=0\bigr)}{n_{p}}
\]

is simply the ordinary FLOP count of a **standard decoder‑only transformer** (the *latent global transformer* $\mathcal G$) evaluated on a sequence whose length is the number of *patches* that are processed in one forward‑backward pass, and then divided by the number of bytes $n_{\text{ctx}}$ in the original context.  Because each patch corresponds to a contiguous block of bytes, dividing by the patch count $n_{p}$ yields the cost **per byte**.

Below we expand the four arguments of `Transf.FL` into the familiar $QKV$‑attention + feed‑forward (FFN) equations and show how the division by $n_{p}$ collapses everything to a per‑byte budget.  We also explain why no patch‑dependent positional embeddings appear in this term.

---

### 1.  What `Transf.FL` actually computes  

For a transformer layer with hidden dimension $h$ and sequence length $m$ (here $m = n_{\text{ctx}}/n_{p}$, i.e. the number of patches), the FLOP count used in the paper follows Chinchilla [2022] and can be written as  

\[
\text{FL}_{\text{layer}}(h,m,V)=
\underbrace{2\,h^{2}m}_{\text{self‑attn }(Q,K,V)}+
\underbrace{2\,h^{2}m}_{\text{output projection}}+
\underbrace{4\,h^{2}m}_{\text{FFN (gate+up)}}
+
\underbrace{2\,hmV}_{\text{final vocab projection}} .
\]

* The first two terms come from three linear projections for queries, keys and values ($3hmh = 3hmh$ multiplies + same number of adds, i.e. $2hmh)$) and from the final output projection that maps the attention result back to a hidden vector.
* The FFN uses a SwiGLU feed‑forward block with two linear layers (gate + upward projection); each contributes $2hmh$ FLOPs, hence $4hmh$.
* The last term is present only when a vocabulary projection is needed (e.g. in a token‑level decoder). For the latent transformer we set $V=0$, so this term vanishes.

Summing over all global layers gives  

\[
\text{Transf.\;FL}(h_{\mathcal G},l_{\mathcal G},m,V)
   = l_{\mathcal G}\,\Bigl[\,4h_{\mathcal G}^{2}m
        +4h_{\mathcal G}^{2}m
        +2\,h_{\mathcal G}mV \Bigr] .
\]

Because $V=0$,

\[
\boxed{\;\text{Transf.\;FL}(h_{\mathcal G},l_{\mathcal G},m,0)
      = l_{\mathcal G}\,8\,h_{\mathcal G}^{2}m \;}
      \qquad (1)
\]

which is just **$8\,l_{\mathcal G}\,h_{\mathcal G}^{2}$** multiplied by the patch length $m$.

---

### 2.  From “per‑patch’’ to “per‑byte’’  

The latent transformer is invoked **once per patch**.  If a training batch contains on average

* $n_{\text{ctx}}$ bytes,
* split into $n_{p}=n_{\text{ctx}}/m$ patches,

the total number of FLOPs spent on the global model for that batch is (1).  
Dividing by the number of bytes gives

\[
\frac{\text{Transf.\;FL}(h_{\mathcal G},l_{\mathcal G},m,0)}{n_{p}}
=
\frac{l_{\mathcal G}\,8\,h_{\mathcal G}^{2} m}{n_{p}}
=
l_{\mathcal G}\,8\,h_{\mathcal G}^{2}
   \underbrace{\frac{m}{n_{p}}}_{= \frac{n_{\text{ctx}}}{n_{p}^{2}}}.
\]

Since $m = n_{\text{ctx}}/n_{p}$, the fraction simplifies to **$1/m = n_{p}/n_{\text{ctx}}$**, giving finally  

\[
\boxed{\;
 \frac{\text{Transf.\;FL}}{n_{p}}
 = l_{\mathcal G}\,8\,h_{\mathcal G}^{2}\,\frac{1}{m}
 = l_{\mathcal G}\,8\,h_{\mathcal G}^{2}\,
   \frac{n_{p}}{n_{\text{ctx}}}
 \;}
     \qquad (2)
\]

which is exactly “flops per byte’’: every additional byte contributes a constant amount
$8\,l_{\mathcal G}\,h_{\mathcal G}^{2}/(\text{average bytes per patch})$.

If we write it directly in terms of the four arguments originally shown:

* **$h_{\mathcal G}$** – hidden size of the latent transformer,
* **$l_{\mathcal G}$** – number of its layers,
* **$m = n_{\text{ctx}}/n_{p}$** – patch‑wise context length,
* **$V=0$** – no output vocabulary head,

the per‑byte cost follows from plugging these values into (1) and then dividing by $n_{p}$.

---

### 3.  Why there is no patch‑dependent positional embedding in this term  

Positional information for *patches* lives entirely inside the **global transformer**’s self‑attention mechanism via RoPE (rotary embeddings).  RoPE does not add any extra matrix multiplication; it simply rotates query/key vectors element‑wise before computing their dot‑product.  Consequently it incurs **zero FLOPs** (the paper explicitly treats RoPE as cost‑free).  

Patch‑level positional embeddings are *not* added as a separate embedding lookup because:

1. **Embedding lookups are counted as zero FLOPs** in § 4.1 (“the input embedding layer is implemented as an efficient lookup instead of a dense matrix multiplication”).  
   The patch’s absolute position could be added as a learned vector, but this would be another lookup and therefore does not change the FLOP budget.

2. The *cross‑attention* modules that aggregate bytes into patches already contain their own query/key/value projections; the authors deliberately omitted any additive positional term there (“no positional embeddings are used in this cross‑attention module”).  This design keeps the cross‑attention cost identical to a vanilla attention block and avoids extra FLOPs that would otherwise appear in `Cross Attn. FL`.

Hence, when we write `Transf.FL(..., V=0)` we are already accounting for all arithmetic performed by the latent transformer; any positional encoding that might exist is either a zero‑cost rotation (RoPE) or a free lookup, so it does not appear explicitly in the formula.

---

### 4.  Putting everything together  

The full per‑byte FLOP budget of BLT (equation (3) in the paper) consists of five pieces:

1. **Global latent transformer** – eqs. (1)–(2) above, divided by $n_{p}$.
2. **Local encoder** – same `Transf.FL` with hidden size $h_{\mathcal E}$, layers $l_{\mathcal E}$, context length equal to its fixed window $w_{\mathcal E}$, and again no vocab head.
3. **Local decoder** – same but with vocab size $V=256$ because it finally predicts a byte.
4. **Encoder cross‑attention** – FLOPs proportional to $h_{\mathcal E}^2 n_{p}(r)$, where $r=n_{p}/k$ is the ratio of queries (patches) to keys/values (bytes).  Multiplying by $k/n_{p}$ accounts for the fact that each cross‑attention step processes only one patch’s bytes.
5. **Decoder cross‑attention** – analogous term with the decoder dimensions.

All five terms are summed; only term (1) contains the factor $\frac{\text{Transf.\;FL}(h_\G,l_\G,m,V=0)}{n_p}$, which after expanding becomes exactly equation (2).  This expression shows clearly how increasing average patch size (larger $m$) lowers the per‑byte cost because fewer global transformer steps are required.

---

### TL;DR  

* `Transf.FL(h,l,m,V)` counts standard QKV attention plus SwiGLU FFN FLOPs:  
  \[
    \displaystyle l \bigl[8 h^{2} m + 2 h m V\bigr].
  \]  
* For the *latent global transformer* we set $V=0$; its per‑byte cost is obtained by dividing this quantity by the number of patches $n_p=n_\text{ctx}/m$.  
* After simplification we obtain  

  \[
  \frac{\text{Transf.\;FL}(h_\G,l_\G,m,0)}{n_p}
   = l_\G \cdot 8 h_\G^{2} \frac{1}{m},
  \]

  i.e. FLOPs per byte scale inversely with average patch size.  
* Positional information does not add FLOPs because RoPE rotations are free and any learned patch positions are just lookups; therefore no extra term appears in `Transf.FL`.  

This explains precisely how Eq. (4.1)’s mysterious term translates into ordinary transformer arithmetic and why it already represents “flops per byte’’ without any additional positional overhead.

### Why does resetting the entropy model context with newlines help avoid "entropy drift"?
Question:
The authors mention that during large‑scale training they reset the entropy model context with new lines because otherwise "entropy drift" occurs when processing long repetitive sections (e.g., multiple‑choice questions). How does changing the context influence the entropy estimates? Is it simply that a smaller context prevents the small LM from over‑fitting to repeated patterns, or is there a more subtle statistical effect?
Answer:
In the BLT paper the “entropy model” is a tiny byte‑level language model that is used **only** to estimate the next‑byte entropy
$$
H(x_i)= -\sum_{v\in\mathcal V}p_e(v\mid \mathbf x_{<i})\log p_e(v\mid \mathbf x_{<i}) .
$$
These entropies decide where a patch should start: a high‑entropy byte (or a sharp rise in entropy) signals a difficult prediction and therefore a new patch boundary.

The entropy model is **stateful** – its hidden representation at position $i$ is a function of everything it has seen before in the same training document. When the data contains a very long repetitive segment (for example the list of answer choices in many‑choice questions), the hidden state quickly adapts to that repetition. After a few dozen identical lines the model’s conditional distribution $p_e(\cdot\mid \mathbf x_{<i})$ becomes highly certain about the next byte, so the estimated entropy drops dramatically even though, from a global point of view, each new line is still “surprising” to the **large** BLT model. Consequently the patcher thinks that the whole block is low‑entropy and creates **very long patches** that span many answer choices. This phenomenon is what the authors call *entropy drift*.

Why does resetting the context with a newline help?  
A newline is treated as a *hard break* for the entropy model: when the dataloader inserts a newline before processing the next line it forces the small LM to start with a fresh hidden state (or at least with a state that has been cleared of the previous line’s memory). In other words, every line is evaluated as if it were the first line in a document. The entropy estimate for each line therefore reflects only the local difficulty of predicting that line, not the accumulated certainty produced by seeing dozens of identical lines before it.

The effect is subtle but important:

1. **Statistical steadiness** – The conditional distribution used to compute $H(x_i)$ no longer shifts as more repetitions are observed; its expectation stays roughly constant across lines. This keeps the threshold‑based or monotonic‑rise patching rule from being fooled by an artificially low entropy caused by long‑range context.

2. **Avoiding pathological patch growth** – With “drifted” entropies, a small LM would keep merging successive low‑entropy bytes into a single patch, producing patches that are orders of magnitude larger than necessary. Those oversized patches reduce the frequency with which the expensive global latent transformer is invoked, but they also deprive it of useful contextual signals (the global transformer would see only one giant patch instead of many meaningful boundaries). Resetting eliminates this runaway growth.

3. **Not merely over‑fitting** – The small LM is not over‑fitting in the usual sense (it still has far fewer parameters than the data). Rather, it *learns* to predict repetitive patterns with near‑certainty when it accumulates enough repetitions in its hidden state. This deterministic behaviour is undesirable for patching because we want entropy to reflect *intrinsic* ambiguity of the next byte, not how many identical copies we have already processed.

In practice the authors implement this by inserting an explicit newline character when they finish processing one logical unit (e.g., one question–answer block) and then **re‑initialising** or at least **clearing** the entropy model’s hidden cache before feeding the next unit. The rest of training proceeds unchanged: they still compute entropies on‑the‑fly during data loading, compare them to the global threshold or monotonic rise criterion, and place patch boundaries accordingly.

To summarise, resetting the entropy model’s context with newlines prevents *entropy drift* because it blocks the accumulation of deterministic information about repeated patterns in the small LM’s hidden state. This keeps entropy estimates stable across similar but distinct sections, ensuring that patches are placed according to genuine prediction difficulty rather than an artefactual certainty caused by long‑range repetition.

### How does BLT’s "patch size" interact with the fixed context length in bytes when comparing inference flop budgets?
Question:
The experiments keep the number of bytes per batch constant while varying average patch size, which changes the number of patches processed per batch. The paper says they reduce sequence length for larger patches to keep total bytes constant. I’m unsure how this influences inference FLOPs: does a larger patch size always reduce FLOPs linearly, or are there diminishing returns due to cross‑attention overheads? Also, how is the "fixed inference scaling" experiment (Figure 5) designed to isolate this effect?
Answer:
The key to understanding the “fixed‑inference‑budget” experiments is to keep in mind what *actually* consumes flops in a BL T model.  
During inference every **byte** first passes through the lightweight local encoder ( ℓE layers), then a **patch** representation is handed to the large latent transformer ( ℓG layers), and finally the decoder expands the latent output back to bytes.  The dominant term in the flop count is the **global transformer**, because it is run once per *patch* rather than once per *byte*.  

If we denote

* \(n_{\text{ctx}}\) – the number of raw bytes that we feed to the model (the *context length* in bytes),  
* \(s\) – the average patch size (bytes per patch),  

then the number of patches processed in a forward pass is  

$$
m = \frac{n_{\text{ctx}}}{s}.
$$

All other components (the encoder, decoder and their cross‑attention blocks) scale either with a fixed window of bytes \((w_{E},w_{D})\) or with the patch dimension, and their contribution changes only slowly with \(s\).  Consequently, the global‑transformer flop term is roughly proportional to \(m\):

$$
\text{FLOPs}_{\text{global}} \;\approx\; \frac{n_{\text{ctx}}}{s}\;\times\;C_{\mathcal G},
$$

where \(C_{\mathcal G}\) bundles hidden size, number of layers and head‑count of the latent transformer.  All other terms are either constant or grow sub‑linearly with \(s\).  Hence **increasing the average patch size reduces inference flops almost linearly** as long as we keep the total number of bytes per batch constant.

### Why we keep “bytes per batch” constant

The paper’s experiments deliberately fix the *expected* number of bytes processed in each minibatch (e.g. 16 MiB).  When a larger average patch size is chosen, fewer patches fit into that byte budget, so the sequence length fed to the global transformer is reduced:

$$
L_{\text{global}} = m = \frac{n_{\text{ctx}}}{s}.
$$

If we were to keep the *patch* length fixed instead, larger patches would mean that more raw bytes are examined per forward pass, which would give BL T an unfair advantage over a tokeniser‑based baseline that always sees exactly the same number of tokens.  By fixing bytes rather than patches we ensure that every model—regardless of patch size—processes exactly the same amount of raw information, and any gain in efficiency comes solely from executing fewer global‑transformer steps.

### Does cross‑attention spoil the linear scaling?

Cross‑attention appears in both encoder and decoder.  Its flop cost contains a factor

$$
\frac{k}{n_{p}} \times s,
$$

where \(k\) is the ratio between latent‑dimensionality and byte‑dimensionality (typically 2).  Because cross‑attention is executed *once per patch*, its total contribution also scales with \(m = n_{\text{ctx}}/s\).  In practice these terms are an order of magnitude smaller than the global transformer flops (the paper reports that even for an 8 B model the encoder+decoder together account for ≈10 % of total inference flops).  Therefore they introduce only a mild curvature: as patches become very long (e.g. \(s>12\) bytes) cross‑attention begins to dominate a small fraction of total cost, but up to the patch sizes studied (4–8 bytes) the reduction remains essentially linear.

### How Figure 5 (“fixed inference scaling”) isolates this effect

Figure 5 compares three families of models that all respect **the same inference‑flop budget**:

1. **BPE baselines** (Llama 2 tokenizer and Llama 3 tokenizer).  
2. **BLT‑Entropy with average patch size ≈ 4.5 bytes** – a modest reduction in global‑transformer steps.  
3. **BLT‑Entropy with larger patches (6 bytes and 8 bytes)** – progressively fewer global steps.

All families are trained on exactly the same amount of **bytes** (the data mixture does not change) and on comparable compute budgets (the total training FLOPs are varied but each point on a curve uses exactly the same inference FLOPs).  The experiment proceeds as follows:

* Choose an inference budget, e.g. “≈ 70 G FLOPs per forward pass”.  
* Compute for each patch size which latent‑transformer depth/width yields exactly that budget using the flop formula above.  
* For every such configuration train models across a range of training FLOP budgets (from compute‑optimal up to several times larger).  

Because the inference budget is held fixed, any improvement in downstream performance can be attributed to **how many parameters are allocated to the latent transformer** versus how many steps it has to run.  Larger patches free up flops that are then spent on widening/deepening \(\mathcal G\); this is precisely what “simultaneously increase model size and patch size while keeping inference cost constant” means in Section 4.3.

The curves in Figure 5 show that for any given training budget, models with larger patches (hence fewer transformer steps) achieve higher downstream scores than their token‑based counterparts.  The crossover point—where BLT overtakes BPE—moves closer to the compute‑optimal regime as patch size grows, confirming that **the linear flop savings from larger patches can be redirected into extra model capacity**, which yields better scaling behaviour.

### Summary

* The average patch size \(s\) appears in the denominator of the global‑transformer flop term; therefore, **inference FLOPs drop roughly linearly with \(s\)** as long as we keep total bytes per batch fixed.  
* Cross‑attention adds only a modest overhead; it does not break the linear relationship for the patch sizes examined in the paper.  
* Figure 5 fixes an inference FLOP budget, varies patch size (hence number of global steps), rebalances model capacity accordingly, and demonstrates that this reallocation yields better scaling than tokenised models—exactly because larger patches let us “buy” a larger latent transformer without spending extra inference compute.

Thus, when comparing FLOP budgets across different BLT configurations, you should think of patch size as a knob that linearly controls how many global‑transformer steps are performed, while all other components change only slowly, giving diminishing returns only when patches become extremely large.

### Can BLT be trained end‑to‑end without a pre‑trained entropy model for patching?
Question:
Section 3.1 says entropy patching uses a separate lightweight LM trained on the same data distribution. Have the authors tried learning a boundary predictor jointly with BLT (as in Nawrot et al., 2023)? If not, what are the main obstacles? Would an end‑to‑end differentiable boundary predictor introduce bias in patch granularity or increase training FLOPs significantly?
Answer:
**Short answer:**  
In the experiments reported in the BLT paper the entropy‑based patcher is **always a separately trained byte‑level language model**. The authors did not train the boundary predictor jointly with the main BLT model; they leave an end‑to‑end patcher as a “future‑work” direction. The main practical reasons for this choice are (1) the need for an *incremental* patching function that can decide a boundary using only the past bytes, (2) the difficulty of back‑propagating through a discrete stopping decision without destabilising the large latent transformer, and (3) the extra FLOP budget that a learned predictor would consume at every byte step. Below I expand on each point and discuss what would happen if we tried to replace the static entropy model with a differentiable boundary predictor as in Nawrot et al. (2023).

---

### Why the paper uses a pre‑trained entropy model

1. **Incrementality requirement**  
   Section 3.1 defines *incremental patching* as  
   \[
   f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i},
   \]  
   i.e. the decision whether the current byte starts a new patch must be made **without seeing future bytes**.  
   The entropy model satisfies this because it outputs a scalar $H(x_i)$ that depends only on the prefix $\mathbf{x}_{<i}$. A neural boundary classifier would have to be trained to produce exactly the same binary sequence under this causal constraint, which is non‑trivial; many of the architectures in Nawrot et al. use a *soft* sigmoid that is later hard‑thresholded, breaking strict incrementality unless special tricks (e.g. straight‑through estimators) are employed.

2. **Stability of the global latent transformer**  
   The global transformer $\mathcal{G}$ processes one patch at a time and its computational budget is dominated by its feed‑forward layers. If the patch boundaries change during training, the number of latent steps per batch fluctuates dramatically, causing high variance in both memory usage and gradient magnitudes. The authors observed (see § 3.1 and § 4.2) that “dynamic patching yields different ratios of bytes to patches”, which they mitigate by packing patches to keep the number of latent steps constant. Introducing a learnable predictor would make this ratio *learned*, potentially leading to runaway behaviour (e.g., many tiny patches in early training) that would overwhelm $\mathcal{G}$.

3. **FLOP overhead of an online predictor**  
   The entropy model is evaluated **once per byte during data loading** and its cost is negligible compared with the main BLT passes (the authors count it as part of preprocessing). A differentiable predictor would need to be evaluated inside the forward pass of each training step, adding at least one additional transformer layer per byte (or a lightweight CNN/MLP). Because BLT’s FLOP budget is already carefully balanced between local encoder/decoder and global transformer (see Eq.\,(4)), even a modest extra cost would break the flop‑controlled scaling experiments.

---

### What would happen if we trained an end‑to‑end boundary predictor?

#### 1. Potential bias in patch granularity
A learned predictor tends to minimise its own loss, which is usually a binary cross‑entropy against some target (e.g., token boundaries or high‑entropy points). In practice this leads to **systematic bias**:
- If the loss favours *few* positive predictions, patches become larger on average; compute savings increase but prediction difficulty for early bytes rises, possibly harming language modelling quality.
- If it favours *many* positives, patches shrink, giving the global transformer more steps and erasing most of BLT’s efficiency gains.

The BLT paper notes (Sec.\,3.1) that different thresholds $\theta_g$ or $\theta_r$ already control average patch size; a learned predictor would implicitly learn such a threshold and could drift during training unless explicitly regularised.

#### 2. Increase in training FLOPs
Assuming we replace the static entropy lookup with a small 2‑layer MLP that processes each byte embedding, we add roughly  
\[
\text{FLOPs}_{\text{predictor}} \approx 2 \times h_{\mathcal{E}}^2 \times n_{\text{bytes}}
\]  
per batch (where $h_{\mathcal{E}}$ is the hidden size of the local encoder). For an 8B‑parameter BLT with $h_{\mathcal{E}}=1024$, this accounts for several percent of total training FLOPs—non‑negligible when trying to keep experiments *flop‑matched* with tokenizers.

#### 3. Training stability
Back‑propagating through a discrete “start‑of‑patch” decision usually requires either:
- **Straight‑through estimators**, which are biased and can cause gradient noise, or
- **Reinforcement‑learning style policy gradients**, which have high variance.

Both approaches have been shown to make convergence slower for hierarchical models such as those in Nawrot et al.; their 40M‑parameter experiments needed careful curriculum learning and long warm‑up periods. Scaling such tricks up to BLT’s 8B parameters would likely require new algorithmic innovations (e.g., Gumbel‑softmax with annealed temperature combined with curriculum on average patch size).

---

### Summary

- The BLT paper **does not train** a boundary predictor jointly with the main model; it relies on a separate lightweight byte LM that provides next‑byte entropies used as a deterministic preprocessing step.
- The authors cite three practical obstacles to end‑to‑end patching: maintaining incremental decisions, avoiding instability in the global transformer caused by fluctuating patch counts, and preserving their carefully calibrated FLOP budget.
- Introducing an end‑to‐end differentiable predictor would indeed add bias towards certain patch granularities unless additional regularisation is applied, and it would increase training FLOPs enough to jeopardise the flop‑controlled comparisons presented in Sections 4–6.
- Consequently, while conceptually appealing—and pursued in earlier work such as Nawrot et al.—an end‑to‑end learned patcher remains an open research direction for BLT; future work will need to devise incremental, low‑cost predictors and stable training tricks before it can replace the pre‑trained entropy model without sacrificing BLT’s efficiency gains.

### What is the intuition behind "dynamic allocation of compute" when predicting first bytes of words versus later bytes?
Question:
The introduction argues that predicting first characters after spaces is high entropy and thus should trigger a global transformer step, whereas later characters are low entropy and can be handled by cheap local layers. How does BLT actually implement this at inference time? Is it purely based on precomputed patch boundaries derived from entropy, or does the model decide on‑the‑fly whether to invoke the latent transformer for each byte?
Answer:
In **BLT** the “dynamic allocation of compute’’ is realized by letting the **global (latent) transformer** run only when a new *patch* begins.  
During inference the model does **not** run a separate classifier that predicts on‑the‑fly whether a byte is “hard’’ or “easy’’; the decision is already encoded in the **patch‑boundary sequence** that is produced by the **entropy‑patching preprocessing step**.

### How a step is chosen at generation time  

1. **Entropy‑based patching is performed once, before any token is generated.**  
   An auxiliary byte‑level LM (the *entropy model*) has been trained on the same data as BLT.  
   For every possible prefix of bytes it can compute a next‑byte entropy  

   \[
   H(x_t)=\sum_{v\in\mathcal V}p_e(x_t=v\mid \mathbf x_{<t})\log p_e(x_t=v\mid \mathbf x_{<t}) .
   \]

2. **Boundary rule is applied to these entropies.**  
   In the experiments the authors use either  

   * a global threshold $H(x_t)>\theta_g$, or  
   * an *approximate‑monotonic* rule $H(x_t)-H(x_{t-1})>\theta_r$.

   Whenever the rule holds, a “1’’ is written into the binary mask that marks *the start of a new patch*.

3. **The mask is stored as part of the input stream.**  
   Because BLT’s patching function satisfies the *incremental* property  

   \[
   f_p(\mathbf x_{<i}) = f_p(\mathbf x)_{<i},
   \]

   the mask can be computed from the prefix alone; no future bytes are required.  
   In practice this means that when the decoder has already produced bytes $b_1,\dots,b_{t-1}$ it can look up the next entry of the mask (a simple table‑lookup) to know whether byte $b_t$ starts a new patch.

4. **If the mask entry is 1 → invoke the latent transformer; otherwise stay in the local pathway.**  

   *When a new patch starts* (`mask[t]=1`) BLT encodes the bytes that belong to this patch with the **local encoder**, feeds the resulting latent representation to the **global transformer** $\mathcal G$, obtains an output patch representation, and finally decodes it with the **local decoder** into raw bytes.  
   
   *When `mask[t]=0`* (i.e., we are still inside an existing patch) only the lightweight local encoder/decoder layers are executed; no call to $\mathcal G$ is made, so the bulk of FLOPs are avoided.

### Intuition behind first‑byte versus later‑byte compute

The entropy model assigns high entropy precisely to those bytes that are difficult to predict—typically the first character after a whitespace or punctuation mark, because many different words can follow such a boundary.  
Consequently, most of these high‑entropy positions become *patch boundaries*, triggering a global transformer step that allocates lots of capacity to resolve the ambiguity.

After the first character has narrowed down the set of plausible continuations, subsequent bytes within the same word have much lower entropy; they stay inside the same patch and are processed only by the cheap local layers. Thus BLT automatically spends more FLOPs where information density (predictive uncertainty) is high and far fewer FLOPs where it is low.

### Summary

- The decision **whether to run the latent transformer** at inference time is deterministic and derived from a pre‑computed binary mask based on next‑byte entropies.
- The mask can be generated incrementally from any prefix, satisfying BLT’s incremental‑patching requirement.
- High‑entropy bytes (often first characters after spaces) become new patches → global transformer invoked; low‑entropy bytes remain in an existing patch → only local encoder/decoder run.
- No extra classifier or runtime heuristic is needed; all dynamic compute allocation stems from the entropy‑based patch boundaries constructed once and stored alongside the byte stream.

### How does "byte‑ifying" a pretrained Llama 3 model work in practice?
Question:
Section 7 describes initializing BLT’s global transformer with weights from Llama 3.1 and then training with a reduced learning rate for those layers while using a higher LR for encoder/decoder. I am unclear on how token embeddings from Llama 3 are transferred to Byte embeddings: Are they discarded entirely? Does initializing only the global transformer guarantee compatibility with new byte‑level inputs, or is there some mismatch between positional embeddings or output heads that needs special handling?
Answer:
The “byte‑ify’’ procedure described in § 7 is essentially a **partial weight‑transfer** from a pretrained Llama 3.1 model to the large global transformer that sits at the heart of BLT.  
Only the parameters that belong to the **global latent transformer** (the stacked self‑attention and feed‑forward layers) are copied; everything else – the byte‑level tokenizer, the byte‑embedding table, the positional‑embedding tables and the final vocab projection – is **re‑initialised**.

### What happens to the token‑embedding matrix?

Llama 3 is trained on a fixed BPE vocabulary (≈128 k tokens). Those embeddings map each token to a dense vector of size $h_{\mathcal G}$. In BLT the input to the global transformer is **not a token** but a *patch representation* produced by the local encoder. Consequently there is no one‑to‑one correspondence between a Llama token and a BLT patch, and the token‑embedding table would be meaningless. The authors therefore discard it entirely: during BLT initialisation the embedding matrix is replaced by a fresh $256\times h_{\mathcal E}$ byte‑embedding table (plus optional n‑gram hash embeddings) that feeds the local encoder.

### Positional embeddings and output head

Both Llama 3 and BLT use rotary (RoPE) positional information **inside** self‑attention, but the **absolute** positional tables that are added to token embeddings in many BPE models are not used in BLT because patches have variable length and no fixed index in a vocabulary. The global transformer’s RoPE parameters are copied from Llama 3 (they are part of the attention weights), while any additional positional bias that would have been tied to token positions is dropped and left at its random initialisation.

The language‑model head in Llama 3 projects from hidden size $h_{\mathcal G}$ back to the size of the BPE vocabulary. BLT, on the other hand, must predict **bytes** (256 symbols) after the decoder has expanded a patch back into a byte sequence. Hence a new linear projection of shape $\mathbb{R}^{h_{\mathcal D}\times 256}$ is created for the local decoder; it is trained from scratch.

### Why does copying only the global transformer work?

The global transformer $\mathcal G$ implements **purely autoregressive sequence modelling** over a series of latent vectors $\{p_j\}$. Its internal computation does not depend on how those vectors were obtained – it only assumes that each step contains a representation of “the next chunk of data”. When we initialise $\mathcal G$ with Llama 3 weights we inherit:

1. **Self‑attention patterns** that have already learned to capture long‑range dependencies in natural language.
2. **Feed‑forward transformation matrices** that embed useful transformations of contextual information.

Because both models share the same architectural hyper‑parameters (number of layers, hidden dimension, SwiGLU activation, RMSNorm, RoPE etc.), the transferred weights are directly compatible with the patch stream. The only mismatch that could arise would be at the interfaces:  
*the encoder* must produce latent vectors of exactly the same dimension that $\mathcal G$ expects, and *the decoder* must consume $\mathcal G$’s outputs and emit bytes. Both requirements are enforced by design: after weight transfer the encoder and decoder are trained with a **higher learning rate**, allowing them to quickly adapt their randomly initialised parameters so that their input/output statistics line up with the frozen (or slowly updated) global transformer.

### Handling possible mismatches

In practice a tiny amount of fine‑tuning on all three components helps smooth any remaining incompatibility:

* **Learning‑rate schedule:** The global transformer continues to be updated but with a learning rate ten times smaller than that of the encoder/decoder (as stated in § 7). This lets it retain its pretrained knowledge while still being able to adjust subtly to the new byte‑level statistics.
* **Layer normalisation statistics:** Since the byte stream has different activation statistics than token streams, running a few warm‑up steps with a larger LR on encoder/decoder also updates running means/variances in RMSNorm throughout $\mathcal G$, preventing drift.
* **Cross‑attention masks:** The cross‑attention modules in encoder/decoder use masks that respect patch boundaries; these masks are new but do not interfere with $\mathcal G$’s block‑causal mask.

After this brief adaptation phase, BLT behaves as a fully fledged tokenizer‑free model: it receives raw bytes, groups them into entropy‑driven patches via the local encoder, processes those patches with a globally pre‑trained transformer, and finally expands them back into bytes with the decoder.

### Summary

- Token embeddings from Llama 3 are **discarded**; they are replaced by fresh byte (and n‑gram hash) embeddings used only by the local encoder.  
- Positional embeddings tied to token indices are also dropped; rotary embeddings are kept because they are part of the attention mechanism.  
- The final vocab projection is rebuilt for 256 possible bytes.  
- Copying only the global transformer works because its architecture matches exactly between token and byte models; it processes abstract latent vectors irrespective of how those vectors were produced.  
- A modest fine‑tuning regime (higher LR for local modules, low LR for $\mathcal G$) resolves any interface mismatches and yields a model that retains Llama 3’s language knowledge while gaining all advantages of byte‑level processing.

Thus “byte‑ifying’’ Llama 3 simply reuses its learned sequence modelling core and re‑trains lightweight front‑ and back‑ends that translate between raw bytes and latent patches. This strategy efficiently leverages existing massive pretraining without requiring an expensive from‑scratch training run.
