\title{A Textbook about the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

Chapter 6: # Inference Efficiency – Memory, Latency, Throughput, and Energy  

In this chapter we examine how the ternary weight representation of **BitNet b1.58**—where every parameter assumes the value \{-1, 0, +1\}—produces concrete improvements on modern hardware.  We begin by describing the experimental methodology used to obtain reproducible measurements, and then we walk through each major efficiency dimension: GPU memory consumption, per‑token latency, throughput under pipeline parallelism, and the energy model that underlies the dramatic savings observed for matrix‑multiplication‑dominated Transformers.  Throughout the discussion we keep a clear focus on the intuition behind each metric: why ternary weights lead to smaller footprints, why a reduction from floating‑point multiplication to integer addition accelerates inference, and where the remaining costs—such as full‑precision embeddings, key‑value caches, or nonlinear operators—still reside.

---

## GPU Memory Footprint Comparison (FP16 vs. b1.58)

The dominant memory consumer in a Transformer‑style LLM is the collection of linear layers that implement the attention and feed‑forward sub‑networks.  In a conventional FP16 model each weight matrix requires two bytes per element; therefore a model with \(N\) parameters occupies roughly \(2N\) bytes for its weights alone.  BitNet b1.58 replaces these matrices with **BitLinear** layers whose weights are stored as ternary values.  A ternary value can be represented with a *packed* 2‑bit code, but the authors elect to use a **1.58‑bit** encoding that exploits the statistical prevalence of the zero value to further compress the representation (the effective average bits per weight is 1.58).  Consequently the storage required for the weight tensors becomes  

\[
\text{Memory}_{\text{b1.58}} \approx 1.58 \times N / 8 \ \text{bytes},
\]

which is a reduction factor of  

\[
\frac{2}{1.58/8}= \frac{16}{1.58}\approx 10.13,
\]

relative to FP16.  In practice the authors report a **3.55×** reduction in *runtime* GPU memory for the 3 B‑parameter model (Table 1 of the paper).  The discrepancy between the theoretical 10× and the observed 3.55× arises because the model still stores other tensors that remain in higher precision:

* **Embedding tables** (token embeddings, positional embeddings) are kept in FP16, because they dominate the early layers of the model and quantizing them would degrade downstream accuracy.  
* **Activations** are quantized to 8 bits, but intermediate buffers for layer‑norm, softmax, and attention scores retain FP16 temporaries.  
* **Buffers for the KV‑cache** (discussed later) are also stored at 16 bits per element.

Nevertheless, the memory savings are substantial enough to allow larger batch sizes or longer context windows on the same GPU, an advantage that becomes more pronounced as the model scales—the embedding fraction shrinks proportionally with total parameter count, making the ternary advantage dominate for 13 B and larger models.

## Latency per Token Using FasterTransformer and 2‑Bit Ladder Kernels

Latency for autoregressive generation is essentially the time required to compute a **single output token** given all preceding tokens.  The authors measured this quantity with the **FasterTransformer** inference library, which includes highly tuned kernels for both FP16 matrix multiplication (using NVIDIA Tensor Cores) and the custom **2‑bit kernel** from the Ladder framework, which is specifically designed for BitLinear operations.

### Why the 2‑Bit Kernel Is Faster

Consider the matrix multiplication in a standard linear layer:

\[
Y = XW^\top,
\]

where \(X\in\mathbb{R}^{b\times d_{\text{in}}}\) is the activation matrix (batch size \(b\), input dimension \(d_{\text{in}}\)), and \(W\in\mathbb{R}^{d_{\text{out}}\times d_{\text{in}}}\) is the weight matrix.  In FP16 each element of \(W\) participates in a **floating‑point multiply‑add** (FMA) operation.  In BitNet b1.58 each weight is \(-1, 0,\) or \(+1\); the multiplication simplifies to a **sign flip or a no‑op**, after which an integer addition can be performed.  The Ladder kernel therefore reduces the inner loop to:

1. **Lookup** the ternary code (essentially a small table retrieval).  
2. **Conditional add**: add \(+X_{ij}\) if the weight is +1, subtract \(X_{ij}\) if the weight is –1, otherwise skip.  

Because the multiply stage disappears, the number of arithmetic operations per MAC (multiply‑accumulate) drops from two floating‑point operations to a single integer addition.  At the hardware level, 8‑bit integer addition consumes roughly **1/70th** the energy of an FP16 multiply, as reported in energy‑cost studies cited by the paper.  Moreover, the integer add can be pipelined more densely, leading to higher throughput on the same silicon.

### Empirical Latency Results

Using the 2‑bit Ladder kernel, the per‑token latency for a 3 B BitNet b1.58 model is **2.71× faster** than its FP16 LLaMA counterpart (Table 1).  For the 70 B configuration the speed‑up grows to **4.1×**, confirming the intuition that the benefit scales with model size: the fraction of compute contributed by linear layers rises, while the fixed‑cost components (e.g., embeddings, softmax) remain constant.

It is important to note that the reported latencies already include the overhead of converting activations from 8‑bit back to the FP16 range required by downstream non‑linearities; however, these conversion costs are negligible compared to the dominant matrix‑multiplication work.

## Throughput Scaling With Batch Size and Pipeline Parallelism

Throughput measures how many tokens the system can produce per second when the model processes *multiple* sequences in parallel.  Two orthogonal strategies were employed by the authors:

1. **Increasing batch size** until the GPU memory limit is reached.  
2. **Pipeline parallelism** (GPipe‑style) to split a single large model across multiple devices, enabling the 70 B model to run on two 80 GB A100 GPUs.

### Batch‑Size Scaling

Because BitNet b1.58 reduces the per‑parameter memory footprint, a larger batch can be accommodated before hitting the GPU memory ceiling.  In the 70 B experiments, the ternary model supported **11×** larger batch sizes than the FP16 baseline on the same hardware configuration.  Since latency per token stays roughly constant, the **throughput** (tokens · seconds\(^{-1}\)) improves by the same factor, yielding an **8.9×** increase in tokens per second (Table 4).  

Intuitively, each additional sequence adds a fixed amount of activation memory; with the weight memory shrunken, the relative contribution of activations becomes the bottleneck, and the model can therefore host many more concurrent sequences.

### Pipeline Parallelism

When a single GPU cannot hold the entire weight set (as for 70 B FP16), researchers typically shard the model across devices and pipeline the forward‑backward passes.  BitNet b1.58’s compact weight representation means that the **inter‑GPU communication** volume is dramatically lowered: the tensors that must be exchanged (e.g., hidden states at partition boundaries) are still 8‑bit/FP16, but the **metadata** describing weight partitions is far smaller.  Consequently, the pipeline stalls less often, and the overall **effective throughput** benefits both from the reduced memory pressure and the faster per‑token compute.

## Energy Consumption Model for Matrix Multiplication (INT8 Addition vs. FP16 Mul + Add)

The energy analysis focuses on the **arithmetic operations** that dominate the power budget of a Transformer inference pass, namely the matrix multiplications inside each attention head and feed‑forward network.  The authors adopt the energy model from prior silicon‑level studies \cite{energycost,pokebnn}, which provides per‑operation energy estimates for a representative **7 nm** process:

| Operation | Energy per operation (pJ) |
|-----------|---------------------------|
| FP16 addition | \(\approx 0.2\) |
| FP16 multiplication | \(\approx 0.8\) |
| INT8 addition | \(\approx 0.01\) |

Given a matrix multiplication of size \(d_{\text{in}}\times d_{\text{out}}\) with batch size \(b\), the total number of floating‑point MACs (multiply‑add pairs) required by a conventional FP16 layer is  

\[
E_{\text{FP16}} = b \, d_{\text{in}} \, d_{\text{out}} \times (E_{\text{mul}}+E_{\text{add}}).
\]

For BitNet b1.58, each MAC reduces to a **conditional integer addition**.  The expected number of adds per output element is proportional to the *density* of non‑zero weights, which the authors denote by \(\rho\).  Empirically the ternary quantization yields a sparsity where roughly **one third** of the weights are zero, giving \(\rho \approx 0.66\).  Therefore the energy for a BitLinear layer becomes  

\[
E_{\text{b1.58}} = b \, d_{\text{in}} \, d_{\text{out}} \times \rho \, E_{\text{int8\_add}}.
\]

Plugging the numbers:

\[
\frac{E_{\text{FP16}}}{E_{\text{b1.58}}}
  = \frac{(0.8+0.2)}{\rho \times 0.01}
  \approx \frac{1.0}{0.66 \times 0.01}
  \approx 151.
\]

The paper, however, reports a more conservative **71.4×** energy reduction, which reflects additional overheads (e.g., data movement, control logic) not captured in the simple MAC count.  The key takeaway is that **removing the FP16 multiplication** yields two orders of magnitude lower energy per operation, a benefit that compounds as the model grows because the proportion of computation spent in linear layers rises.

### End‑to‑End Energy Estimates

To map operation‑level savings to a whole‑model inference cost, the authors simulated the execution of a 512‑token sequence on a 7 nm chip, aggregating the contributions from:

* Linear layers (dominant, INT8 add for b1.58 vs. FP16 mul+add).  
* Non‑linearities and layer‑norm (still FP16).  
* Embedding lookup (FP16).  

The resulting **total energy per inference** for the 70 B BitNet b1.58 model is **~5‑6×** lower than the FP16 baseline, with the gap widening for larger models because the linear layers constitute a larger share of total operations.

## Empirical Energy Savings on 7 nm Silicon Estimates

The authors translate the operation‑level analysis into **real‑world silicon estimates** by using the energy per operation values listed above and the measured FLOP counts for each model size.  For a 7 B BitNet b1.58 model, the matrix‑multiplication energy component accounts for roughly **90 %** of the total inference energy, whereas in the FP16 counterpart the same component consumes **≈98 %**.  Applying the 71.4× reduction to this dominant term yields an overall **≈70 %** reduction in energy consumption.

Figure 3 of the paper visualizes these trends: the *energy per token* curve for b1.58 lies far below that of FP16 for all model sizes, and the gap widens as we move from 3 B to 70 B.  The authors also note that the **energy model** they use is conservative: it does not consider possible further optimizations such as **zero‑skipping** (omitting additions for zero weights) or **kernel fusion** that would reduce memory traffic.  Hence the reported savings are a lower bound on the true advantage that specialized hardware could unlock.

## Discussion of Remaining Overheads (Embeddings, KV‑Cache, Non‑Linearities)

Although ternary weights dramatically shrink the memory and compute budget of the linear layers, several components still dominate the residual cost:

1. **Embedding Tables** – Token and positional embeddings remain in FP16 to preserve representation fidelity.  For a vocabulary of 50 k tokens and a 4096‑dimensional embedding, this alone occupies ~400 MiB, independent of model depth.  As models scale past 13 B parameters, the embedding memory becomes a smaller fraction of the total, but it still sets a lower bound on memory usage.

2. **Key‑Value (KV) Cache** – Autoregressive inference must retain the previously computed keys and values for each attention head.  The cache stores activations at the same precision as the forward pass (8 bit for b1.58, 16 bit for FP16).  Because the cache size grows linearly with context length, it can dominate memory for very long sequences.  The authors point out that the 8‑bit activation format of b1.58 *effectively doubles* the maximal context length that fits in a given memory budget compared to FP16.

3. **Layer‑Norm and Non‑Linearities** – RMSNorm, SwiGLU, and the softmax function still operate in FP16, as quantizing these operations proved detrimental to accuracy.  These steps involve relatively few arithmetic operations per token, so their absolute energy contribution is modest, yet they prevent the model from achieving a *pure* integer pipeline.

4. **Control and Indexing Logic** – The ternary quantization introduces a small overhead for the “RoundClip” operation during training, but at inference time the weights are already stored as packed codes, so the runtime overhead is limited to the decode step for each weight.  This decode cost is amortized across the massive number of MACs per token and is therefore negligible in practice.

Understanding these residual costs informs future research directions: tighter quantization of embeddings (e.g., 4‑bit or block‑floating representations), more aggressive KV‑cache compression, or redesigning activation functions to be integer‑friendly could push the efficiency frontier even further.

---

### Summary

The experimental evidence presented in the **BitNet b1.58** paper demonstrates that moving from 16‑bit floating‑point weights to a ternary (1.58‑bit) representation yields **substantial practical gains**:

* **Memory**: up to 3.55× less GPU memory for a 3 B model, enabling larger batch sizes and longer contexts.  
* **Latency**: 2.7–4.1× faster per‑token inference thanks to the elimination of FP16 multiplications in favor of integer additions.  
* **Throughput**: almost an order of magnitude increase when scaling batch size and exploiting pipeline parallelism.  
* **Energy**: more than 70× reduction in arithmetic‑operation energy for matrix multiplication, translating to roughly 70 % lower end‑to‑end inference energy on a 7 nm silicon estimate.

The remaining overheads—full‑precision embeddings, KV‑cache storage, and non‑linearities—are well‑understood and constitute clear targets for further optimization.  Collectively, these results substantiate a new scaling law: **1.58‑bit LLMs can outperform larger FP16 models not only in speed and memory but also in energy, while preserving comparable perplexity and downstream task performance**.  This positions ternary‑weight Transformers as a compelling foundation for next‑generation, cost‑effective language models and invites hardware designers to build accelerators that exploit the multiplication‑free computation paradigm at its core.
