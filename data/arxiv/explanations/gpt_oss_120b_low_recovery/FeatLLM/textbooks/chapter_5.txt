\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 5: **Parsing Natural‑Language Rules into Binary Features**

In this chapter we examine the crucial stage of the **FeatLLM** pipeline that turns the textual rules generated by a large language model (LLM) into a concrete set of binary features that can be fed to a simple downstream predictor.  While the LLM is remarkably capable of articulating conditions such as “*age > 65*” or “*blood‑type is ‘O’*”, its output is raw natural language and often contains inconsistencies, synonyms, or formatting quirks that make direct computational use difficult.  We therefore devote careful attention to (i) characterizing the typical sources of noise in the LLM’s rule strings, (ii) designing a secondary prompt that asks the same LLM to translate those strings into well‑formed Python functions, (iii) executing the generated code safely, (iv) constructing the binary feature matrix \(\mathbf{Z}_k\) for each class \(k\), and (v) analysing the computational complexity of the entire parsing step.

---

### Typical Noise in LLM‑Generated Rules

When an LLM is prompted to produce “rules” that separate the classes of a tabular task, it generally follows the format prescribed in the *Response Instruction* (e.g., “Rule 1: …”).  Nevertheless, several systematic sources of variability arise:

1. **Symbol–Word Substitutions**  
   The LLM may alternate between symbolic comparators (`>`, `<`, `>=`, `<=`, `==`) and their lexical equivalents (“greater than”, “less than or equal to”).  For instance, a rule that should read  
   \[
   \text{age} > 65
   \]
   might appear as  
   \[
   \text{age is greater than 65}.
   \]  
   Both are semantically identical, yet a naïve parser that expects a strict token pattern would fail on the word form.

2. **Variations in Logical Connectors**  
   To express conjunctions or disjunctions the model might use “and”, “or”, commas, or even natural‑language phrasing such as “both … and …”.  A rule that logically corresponds to  
   \[
   (\text{cholesterol} > 200) \land (\text{blood\_pressure} \le 130)
   \]
   could be rendered as  
   “cholesterol greater than 200 and blood_pressure less than or equal to 130”.  Detecting the correct grouping of sub‑conditions is non‑trivial.

3. **Inconsistent Naming and Spacing**  
   Feature names supplied in the prompt may be re‑typed with different capitalisation, underscores, or spaces (e.g., “BloodPressure” vs. “blood pressure”).  Because the downstream code must reference the exact column identifiers in the original data frame, any mismatch leads to a `NameError`.

4. **Extraneous Punctuation or Formatting**  
   The LLM often includes trailing periods, bullet points, or quotation marks that are not part of the logical expression.  Example:  
   ```
   Rule 3: "age >= 70".
   ```  
   Such characters need to be stripped before compilation.

5. **Incomplete or Ambiguous Expressions**  
   Occasionally the model omits a necessary operand, producing fragments like “age greater” or “blood_pressure is”.  These fragments are syntactically invalid and must be flagged for correction or removal.

Collectively, these noises make a deterministic parser brittle.  Instead of engineering a large set of handcrafted regular‑expression rules to capture every idiosyncrasy, **FeatLLM** leverages the LLM’s own code‑generation abilities to produce a clean, executable translation.

---

### Designing a Secondary Prompt to Ask the LLM to Emit Python Functions

The solution is to ask the LLM a **second‑level query**: “Given the natural‑language rule list, generate a Python function that, for a single data record, returns `1` if the rule holds and `0` otherwise.”  This approach enjoys several advantages:

* The LLM already knows the syntax of Python and has been extensively trained on code repositories, so it can resolve ambiguous phrasing automatically.
* By providing a concrete *function signature* and a *docstring* that lists the allowed feature names, we constrain the model to produce code that references only the intended columns.
* The prompt can request that each rule be wrapped in its own function (e.g., `def rule1(row): ...`) and that a master wrapper aggregates the results into a binary vector.

A representative secondary prompt is shown below (pseudo‑code representation, actual prompt follows the layout in the paper’s Appendix):

```
You are given a list of textual rules for classifying a patient.
Each rule describes a condition on the tabular features.
Your task is to write a Python function `apply_rules(row)` that takes a
dictionary `row` (mapping feature names to their values) and returns a
list of integers, where the i‑th element is 1 if rule i is satisfied,
otherwise 0.

The feature names are:
- age (numeric)
- cholesterol (numeric)
- blood_pressure (numeric)
- diagnosis (categorical, possible values: ['healthy','diseased'])

Rules:
1. age greater than 65 and cholesterol > 200
2. diagnosis is 'diseased' or blood_pressure <= 130
...

Please output only the Python code, without explanatory text.
```

Key design choices:

* **Explicit type hints** (`numeric` vs. `categorical`) guide the LLM to use appropriate Python operators (`>` vs. `==`).
* **Example code snippet** may be included (e.g., a template) to reduce variability.
* **Restriction to pure expressions** (no external imports, no side effects) ensures safe execution.

Because the LLM is asked to produce **deterministic code**, the output is far more regular than the raw rule strings, drastically simplifying downstream handling.

### Safe Execution with `exec()` and Handling Errors

Once the LLM returns a code block, **FeatLLM** proceeds to compile and execute it within a constrained environment:

```python
import builtins
import numpy as np

# Whitelist only safe built‑ins
SAFE_BUILTINS = {
    'abs': builtins.abs,
    'min': builtins.min,
    'max': builtins.max,
    'float': builtins.float,
    'int': builtins.int,
    'bool': builtins.bool,
    'np': np
}

def safe_exec(code_str, globals_dict=None):
    """
    Compile and execute `code_str` safely.
    Returns a dictionary containing the defined functions.
    """
    if globals_dict is None:
        globals_dict = {}
    # Restrict the global namespace
    globals_dict.update({'__builtins__': SAFE_BUILTINS})
    exec(code_str, globals_dict)
    return globals_dict
```

The `exec` call runs in a sandbox where only a minimal set of built‑ins is exposed; this prevents malicious payloads such as `os.system`.  After execution, we extract the produced `apply_rules` function:

```python
code_namespace = safe_exec(generated_code)
apply_rules = code_namespace['apply_rules']
```

**Error handling** is essential because even a powerful LLM can occasionally produce syntactically invalid code (e.g., mismatched parentheses).  The pipeline therefore wraps the compilation step in a `try/except` block:

```python
try:
    code_namespace = safe_exec(generated_code)
    apply_rules = code_namespace['apply_rules']
except Exception as e:
    # Log the failure, fall back to a default rule (always 0)
    def apply_rules(row):
        return [0] * NUM_RULES
```

When an exception occurs, the fallback ensures that the downstream linear model still receives a well‑defined binary vector, albeit one lacking informative signal for that particular trial.  Since **FeatLLM** aggregates many trials via ensembling, occasional failures do not catastrophically degrade overall performance.

### Creating the Binary Feature Matrix \(\mathbf{Z}_k\) for Each Class

With a reliable `apply_rules` function in hand, we can transform the entire dataset.  Suppose the dataset contains \(N\) rows and the LLM generated \(R\) rules for class \(k\).  For each row \(\mathbf{x}^{i}\), we construct a dictionary `row_dict` that maps each feature name \(f_j\) to its value \(x^{i}_j\).  The function then yields a list of binary outcomes:

```python
Z_k = np.zeros((N, R), dtype=int)   # initialize binary matrix
for i, sample in enumerate(dataset):
    row = {f_j: sample[j] for j, f_j in enumerate(feature_names)}
    Z_k[i, :] = apply_rules(row)    # vector of length R
```

Repeating this process for every class \(k \in \{1,\dots,c\}\) yields a collection \(\{\mathbf{Z}_k\}_{k=1}^{c}\).  In practice, the implementation often concatenates the matrices into a single tensor \(\mathbf{Z} \in \{0,1\}^{N \times (cR)}\) because the downstream linear model computes logits per class separately as described in Equation (2) of the paper:

\[
\text{logit}_k^{i} = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^{i},
\qquad
\mathbf{p}^{i}= \operatorname{Softmax}\bigl([\text{logit}_1^{i},\dots,\text{logit}_c^{i}]\bigr).
\]

Here \(\mathbf{z}_k^{i}\) denotes the \(i\)-th row of \(\mathbf{Z}_k\).  The **non‑negative projection** \(\max(\mathbf{w}_k,0)\) guarantees that learning cannot assign a negative contribution to any rule, preserving the intuition that a satisfied rule should never decrease the probability of its class.

### Complexity Analysis of the Parsing Step

The parsing stage consists of three logical phases:

1. **LLM rule‑to‑code generation** – a single API call per ensemble trial.  
   The computational cost is external to the local machine; latency scales with the model’s inference time (typically on the order of a few hundred milliseconds for GPT‑3.5 when the prompt is ~2 KB).

2. **Safe compilation (`exec`)** – runs in time linear in the length of the generated source code, denoted \(L_{\text{code}}\).  Since each rule yields at most a few dozen characters, \(L_{\text{code}} = \mathcal{O}(R)\).  Execution time for compiling is negligible (microseconds).

3. **Feature matrix construction** – for each of the \(N\) samples we evaluate \(R\) Boolean expressions.  Assuming each expression evaluates in constant time (a handful of arithmetic comparisons and logical operators), the overall time is \(\mathcal{O}(N R)\).  Memory consumption is also \(\mathcal{O}(N R)\) to store \(\mathbf{Z}_k\).

When the algorithm is repeated over \(T\) ensemble trials, the total cost becomes \(\mathcal{O}(T N R)\) for matrix construction, while the LLM API cost scales linearly with \(T\).  In practice, the authors found that setting \(T=20\) and \(R=10\) yields a good trade‑off between expressivity and prompt length, leading to a manageable total cost even for datasets with several thousand rows.

Because the downstream linear model training is also \(\mathcal{O}(T N R)\) (gradient updates over a low‑dimensional parameter vector), the entire **FeatLLM** pipeline remains computationally lightweight compared with end‑to‑end LLM inference that would require a forward pass for every test sample.  This lightweight nature is one of the primary motivations for converting natural‑language rules into binary features.

---

#### Summary

In this chapter we have dissected the transformation from noisy, human‑readable rule strings into a rigorously defined binary feature matrix suitable for fast linear classification.  By recognizing the systematic noise patterns of LLM‑generated text, delegating the translation task back to the LLM via a carefully crafted secondary prompt, guarding execution with a sandboxed `exec`, and finally assembling the binary matrix \(\mathbf{Z}_k\), **FeatLLM** achieves a robust, low‑cost feature‑engineering pipeline that capitalises on the LLM’s knowledge while avoiding per‑sample inference overhead.  The resulting computational complexity scales linearly with the number of samples, rules, and ensemble repetitions, making the approach practical for a wide variety of real‑world tabular learning problems.
