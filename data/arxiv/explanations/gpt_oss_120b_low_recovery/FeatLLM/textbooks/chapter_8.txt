\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 8: # Implementation Details and Practical Tips  

In this chapter we explain how to reproduce the *FeatLLM* framework in a real‑world setting.  All the design choices stem directly from the original method, so that a newcomer can set up the pipeline, tune its hyper‑parameters, and diagnose common failure modes without having to read the source code.  We follow the logical order of the system: selecting a large language model (LLM) backend, configuring the generation parameters, deciding how many ensembles and rules to generate, training the downstream linear model, and finally handling parsing problems that inevitably arise when the LLM’s textual output deviates from the expected format.

---

## Choosing an LLM Backend (GPT‑3.5, Alternatives)

*FeatLLM* treats the LLM purely as a **feature‑engineering oracle**.  The only interaction with the model occurs during a small number of inference calls (typically 20–30 per experiment).  Consequently, the choice of backend is guided by three practical considerations:

1. **API‑level access** – The method only requires the ability to send a prompt and receive a completion.  It does **not** need gradient access or fine‑tuning facilities, making any hosted LLM (OpenAI’s *gpt‑3.5‑turbo*, Azure OpenAI, Claude, or open‑source chat models exposed via an API) viable.  
2. **Reasoning competence** – The LLM must be able to follow the structured prompt, reason about causal relationships, and output logical conditions.  Empirically the authors observed that *GPT‑3.5‑turbo‑0613* produces the most reliable rule sets.  When substituting a different model, verify that it can understand chain‑of‑thought instructions and produce deterministic code‑like snippets (e.g., “if age > 60 and cholesterol = high → risk = 1”).  
3. **Cost and latency** – Since the number of queries is modest, even a relatively expensive model can be affordable.  However, an open‑source model such as *LLaMA‑2‑Chat* or *Mistral‑Instruct* may lower budget constraints while preserving performance, provided it has been trained on code data (which aids the later parsing step).

When switching to another backend, keep the prompt wording unchanged; only the model name and possible token limits differ.  If the new model’s context window is smaller, you may need to reduce the number of demonstration examples or employ more aggressive **feature bagging** (see “Number of ensembles and rules per class” below).

## Setting Temperature, Top‑p, and Max Tokens

The LLM generation hyper‑parameters directly affect **rule diversity** and **parsing stability**:

| Parameter | Recommended Value | Rationale |
|-----------|-------------------|-----------|
| **temperature** | **0.5** | A moderate temperature encourages variability across ensemble runs (different rule sets) while still keeping outputs coherent enough for deterministic parsing.  Very low temperatures (≈0.0) produce identical rules in every trial, eroding the benefit of ensembling.  Very high temperatures (>0.9) increase the likelihood of nonsensical syntactic forms, worsening parsing failures. |
| **top‑p** (nucleus sampling) | **1.0** (default) | Keeping top‑p at 1.0 ensures the full probability mass is considered; the temperature already controls randomness.  Restricting top‑p can unintentionally bias the model toward high‑probability tokens that may not include the logical operators needed for rule formation. |
| **max tokens** | **≈ 1024** (or the model’s default) | The rule extraction prompt contains the task description, feature definitions, and a few‑shot serialization.  In most experiments, the entire completion (the rule list) comfortably fits within 500 tokens, leaving ample headroom.  If you encounter truncation warnings, increase the limit; if you are near the model’s context ceiling, reduce the number of few‑shot examples per prompt. |

These settings match the configuration used in the paper’s experiments (temperature = 0.5, top‑p = 1, default max tokens).  When using a model with a smaller context window (e.g., 4 k tokens), the **bagging** technique becomes essential: you randomly sample a subset of features for each ensemble run so that the prompt size stays under the limit.

## Number of Ensembles and Rules per Class – Default Values and Trade‑offs

Two hyper‑parameters dominate the computational budget and predictive performance:

1. **Ensembles (T)** – The number of independent rule‑generation trials.  Each trial draws a random subset of features (bagging) and a random ordering of the few‑shot demonstrations, then queries the LLM once.  The final prediction averages the softmax probabilities from all trials (Eq. (2) in the paper).  

2. **Rules per class (R)** – The fixed count of logical conditions that the LLM is instructed to output for each target class (the authors used 10).  

### Default Settings
* **T = 20** ensembles  
* **R = 10** rules per class  

These defaults yielded the best trade‑off across the 13 benchmark datasets: sufficient rule diversity to recover from occasional erroneous generations, yet a manageable feature dimensionality (the downstream linear model receives at most \(c \times R\) binary features, where \(c\) is the number of classes).

### Trade‑off Analysis  

| Scenario | Increase T | Decrease T | Increase R | Decrease R |
|----------|------------|------------|------------|------------|
| **More expressive rule set** | Improves robustness (self‑consistency) but adds API calls and modestly higher latency. | Faster inference; may suffer when some trials produce poor rules. | Potentially captures finer-grained patterns, but each new rule adds a binary feature that can over‑fit in low‑shot regimes. | Simpler model; easier to train, but may miss useful discriminative conditions. |
| **Prompt length constraints** | No impact (bagging already limits the number of features per prompt). | Same. | Larger R expands the LLM’s response, possibly hitting max‑token limits. | Keeps response short; safer for small context windows. |
| **Computational cost** | Linear in T (≈ T × API latency). | Linear reduction in cost. | Minor increase in downstream linear‑model training time (larger input dimensionality). | Faster training, less memory. |

Empirically, the authors observed diminishing returns after **T ≈ 20** (performance plateaued) and noted that setting **R = 10** balanced prompt size against the risk of over‑parameterizing the linear layer in a few‑shot setting.  When dealing with extremely high‑dimensional tables (hundreds of columns), you may wish to **increase T** while **reducing R** to stay within the LLM’s token budget.

## Training the Linear Layer (Learning Rate, Batch Size, k‑Fold CV)

After rule extraction, each sample is represented by a binary vector \(\mathbf{z}_k^i \in \{0,1\}^R\) for class \(k\).  The downstream model is a **bias‑free linear classifier** with non‑negative weights:

\[
\text{logit}_k^i = \max(\mathbf{w}_k,0) \cdot \mathbf{z}_k^i,\qquad
\mathbf{p}^i = \text{Softmax}\bigl([\text{logit}_1^i,\dots,\text{logit}_c^i]\bigr).
\]

Training proceeds by minimizing the cross‑entropy loss on the **k‑shot** labeled set.

### Hyper‑parameters  

| Parameter | Value Used in the Paper | Practical Guidance |
|-----------|------------------------|--------------------|
| **Learning rate** | **0.01** (Adam optimizer) | A relatively high learning rate works because the model is tiny (‑\(c \times R\) parameters).  If you experience divergence (loss exploding), halve the rate to 0.005 or use a learning‑rate scheduler that reduces after a few epochs. |
| **Batch size** | **All k samples (full‑batch)** | With k ≤ 32 the dataset is tiny, so there is no need for mini‑batching.  Full‑batch gradient descent stabilizes training and simplifies implementation. |
| **Number of epochs** | **200** (early stopped via k‑fold CV) | Over‑fitting is a risk in low‑shot regimes; therefore the authors use **k‑fold cross‑validation** (k = 2 or 4, ensuring each fold contains at least one example of every class) to select the epoch with the best validation loss.  Stop training once the validation loss ceases to improve for a patience of ~10 epochs. |
| **Regularization** | **None** (non‑negative projection suffices) | Since the weight vector is forced to be non‑negative, explicit L2 regularization is often unnecessary.  If you notice very large weight magnitudes, add a modest L2 penalty (e.g., \(10^{-4}\)). |

### Training Procedure  

1. **Construct the binary feature matrix** \(\mathbf{Z} \in \{0,1\}^{k \times (cR)}\) by concatenating the \(\mathbf{z}_k^i\) across classes.  
2. **Initialize** \(\mathbf{w}_k\) with small positive values (e.g., Uniform\([0,0.1]\)).  
3. **Run Adam** for the prescribed number of epochs, projecting \(\mathbf{w}_k \gets \max(\mathbf{w}_k,0)\) after each gradient step.  
4. **k‑fold split** the k labeled points, compute validation loss per epoch, and pick the epoch achieving the lowest average validation loss across folds.  
5. **Store** the final \(\mathbf{w}_k\) for use in inference; repeat the whole training pipeline for each ensemble trial \(t\) to obtain \(\mathbf{w}[t]\).  

Because the linear model is tiny, the entire training loop finishes in a fraction of a second on a modern CPU or GPU.  The dominant runtime component remains the LLM API calls required for rule generation.

## Debugging Rule Parsing Failures

The LLM’s textual output can deviate from the strict “Rule = feature operator value” format, despite the response‑format instructions.  Common sources of failure include:

1. **Synactic drift** – Replacement of symbols (e.g., “>” becomes “greater than”) or insertion of extra whitespace.  
2. **Logical operator mixing** – The model may concatenate multiple conditions using “and/or” inside a single rule, which contradicts the parser’s expectation of a single comparison per rule.  
3. **Type mismatch** – A rule may compare a categorical feature with a numeric operator, producing code that crashes at runtime.  

### Recommended Debugging Workflow  

1. **Inspect Raw Completion** – Save the LLM’s raw text to a log file.  Spot patterns like “If age greater than 60” versus “age > 60”.  

2. **Normalize Operators** – Before feeding the rules to the parsing LLM, run a lightweight pre‑processor that maps common phrasing to canonical symbols:  
   ```python
   mapping = {
       "greater than": ">",
       "less than": "<",
       "equal to": "==",
       "not equal to": "!=",
       "at most": "<=",
       "at least": ">="
   }
   ```
   Apply these replacements globally.  

3. **Leverage the LLM for Code Generation** – The paper’s authors found that asking the LLM *again*—this time with a “code‑generation” prompt—produces robust Python snippets that evaluate the rules, even when the original wording is noisy.  The prompt includes:
   - The **function signature** (e.g., `def rule_age_gt_60(row):`),  
   - A description of each feature’s type,  
   - The raw rule text.  
   The LLM returns a small function body that can be executed with `exec()`.  This step greatly reduces parsing errors and avoids hand‑crafted regex brittleness.  

4. **Validate Generated Code** – After `exec()`, run the function on a few rows of the dataset.  If an exception is raised (e.g., `KeyError` for a missing column), print the offending rule and manually correct the mapping or discard the rule.  

5. **Automated Filtering** – The downstream linear model naturally down‑weights useless rules; however, extremely malformed rules (always false or causing runtime errors) should be removed early.  A simple heuristic: if a rule yields a constant vector (all zeros) on the *k‑shot* training set, discard it before training.  

6. **Iterate Temperature** – If parsing failures are frequent, lower the temperature slightly (e.g., 0.4).  A more deterministic LLM output tends to adhere more closely to the prescribed format, at the expense of rule diversity.  

By following this pipeline—pre‑process, LLM‑assisted code generation, validation—you can achieve a high success rate even with noisy completions.  The authors report that after this two‑stage parsing, the proportion of *useful* rules (AUROC > 0.5) exceeds 70 % before any weight tuning, confirming that the parser reliably extracts meaningful binary features.

---

### Summary Checklist  

- **Backend**: Choose a model with API access and code‑generation capability; *GPT‑3.5‑turbo‑0613* is the baseline.  
- **Generation Parameters**: Use temperature = 0.5, top‑p = 1, default max tokens; adjust only if you see truncation.  
- **Ensemble & Rules**: Start with T = 20 and R = 10; tune upward only if you have budget for more API calls or a larger context window.  
- **Linear Model Training**: Adam, lr = 0.01, full‑batch, 200 epochs with k‑fold early stopping; project weights to non‑negative.  
- **Parsing**: Apply operator normalisation, then ask the LLM to emit Python code; validate on a few rows, drop constant/erroneous features.  

With these practical guidelines you can faithfully reproduce *FeatLLM*’s impressive few‑shot performance while keeping inference latency low and debugging effort manageable.
