\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 3: # Problem Formulation and Notation

In order to understand how **FeatLLM** operates—as a framework that leverages a large language model (LLM) to *engineer features* for few‑shot tabular learning—we must first formalize the learning setting and introduce the symbols that will appear throughout the remainder of the book.  This chapter lays out the precise mathematical description of the data, the way in which only a very small number of labeled instances are made available for training, the evaluation criteria used to judge performance, and the assumptions we place on the auxiliary information (feature descriptions) and on the LLM itself.  By the end of the chapter you should be comfortable with the formal problem statement, be able to read the equations that appear in later sections, and understand why the particular constraints of the setting motivate the design choices of FeatLLM.

---

## 1. Tabular Datasets and Their Components

A **tabular dataset** consists of a collection of samples (rows), each described by a fixed set of attributes (columns).  Formally we write  

\[
\mathcal{D}= \{(\mathbf{x}^{(i)},y^{(i)})\}_{i=1}^{N},
\]

where  

* \(N\) is the total number of examples in the dataset.  
* \(\mathbf{x}^{(i)}\in\mathbb{R}^{d}\) (or a mixed‑type vector) is the feature vector for the \(i\)-th sample.  
* \(d\) denotes the **dimensionality**, i.e., the number of raw input features.  

In addition to the raw numeric values, every column is equipped with a **human‑readable name** and, optionally, a textual definition that explains its semantic meaning.  We denote the set of feature names by  

\[
F=\{f_{1},f_{2},\dots ,f_{d}\},
\]

and for each \(f_{j}\) we may also have an associated description \(\mathsf{desc}(f_{j})\) (e.g., “*Age of the patient, measured in years*”).  The presence of these natural‑language annotations is essential for the LLM: they allow the model to connect the tabular symbols to the world knowledge encoded in its pre‑training corpus.

The target variable \(y^{(i)}\) belongs to a **finite set of classes**  

\[
\mathcal{Y}=\{1,2,\dots ,c\},
\]

so we are dealing with a **classification** problem (binary classification corresponds to \(c=2\)).  Throughout the book we write \(\mathbf{y}^{(i)}\) when we need the one‑hot encoding of the class label, but the scalar notation \(y^{(i)}\) will be used whenever the distinction is unnecessary.

---

## 2. Few‑Shot Sampling: The \(k\)-Shot Regime

The central difficulty addressed by FeatLLM is that **only a handful of labeled examples are available** for learning a new task.  Let  

\[
k \ll N
\]

be the number of labeled samples we are allowed to use for training.  We obtain a **training subset** \(\mathcal{D}_{\text{train}}\) by uniformly sampling without replacement from \(\mathcal{D}\):

\[
\mathcal{D}_{\text{train}} = \{(\mathbf{x}^{(i)},y^{(i)})\}_{i=1}^{k}.
\]

The remaining examples form a **test set** \(\mathcal{D}_{\text{test}}\) on which we evaluate the learned predictor.  Because \(k\) is tiny (often 2, 4, 8, or at most 32 in the experiments), conventional supervised learning algorithms tend to overfit, and we must bring in **external inductive bias**—here supplied by the LLM’s pre‑trained knowledge.

When reporting results, we repeatedly draw different random \(k\)-shot training sets (usually 3 to 5 repetitions) and average the performance to obtain a stable estimate of how well a method works in the low‑resource regime.

---

## 3. Goal: Learning a Predictor from \(k\) Examples Using an LLM

Given only \(\mathcal{D}_{\text{train}}\) and the natural‑language feature meta‑data \(\{f_{j},\mathsf{desc}(f_{j})\}_{j=1}^{d}\), the **objective** is to construct a predictor  

\[
\hat{p}: \mathbb{R}^{d}\rightarrow \Delta^{c},
\]

where \(\Delta^{c}\) denotes the \(c\)-dimensional probability simplex (i.e., \(\hat{p}(\mathbf{x})\) is a vector of class probabilities summing to one).  The predictor must be built **without fine‑tuning the LLM**; the LLM is treated as a **black‑box API** that can be queried with natural‑language prompts.  The overall pipeline consists of two stages:

1. **Feature Engineering via the LLM** – The LLM is prompted to produce a collection of **rules** (logical conditions) that characterize each class.  Each rule can be interpreted as a binary feature indicating whether a given sample satisfies the condition.

2. **Low‑Complexity Downstream Model** – Using the binary rule‑features, we fit a simple, trainable model (in the paper, a non‑negative linear model) on the \(k\) training examples.  This step learns **weights** that quantify the importance of each rule.

The final prediction for a new instance \(\mathbf{x}\) is obtained by evaluating all rules on \(\mathbf{x}\), forming the binary feature vector \(\mathbf{z}\), and computing  

\[
\text{logit}_{k} = \max(\mathbf{w}_{k},0)\cdot \mathbf{z}_{k},
\qquad 
\hat{p}_{k} = \frac{\exp(\text{logit}_{k})}{\sum_{l=1}^{c}\exp(\text{logit}_{l})},
\]

for each class \(k\).  Here \(\mathbf{w}_{k}\) are the learned non‑negative weights, and the ``max’’ operator ensures that the linear combination cannot reduce a class’s score (a design choice that reflects the intuition that an informative rule should never be detrimental).

---

## 4. Assumptions About Feature Descriptions

The success of the LLM’s reasoning hinges on two *minimal* but crucial assumptions:

1. **Availability of Feature Names** – Every column in the table is associated with a concise identifier \(f_{j}\) that the LLM can read.  In practice, these are the column headers from the original CSV or database schema.

2. **Optional Natural‑Language Definitions** – For each \(f_{j}\) we may supply a short textual description (e.g., “*Blood pressure, measured in mm Hg*”).  When such definitions are present they are included verbatim in the prompt.  If a definition is missing, the LLM must rely on its own world knowledge and on the statistical patterns observable in the few‑shot examples.

These assumptions are realistic: most real‑world tabular datasets coming from business, healthcare, or scientific domains already include column names; many also ship a data dictionary that can be leveraged directly.

---

## 5. Assumptions About LLM Access

FeatLLM is designed to be **model‑agnostic** with respect to the underlying LLM, but the following constraints are imposed on the interaction:

* **API‑Level Inference Only** – The user can issue a prompt and receive the LLM’s textual completion; there is no ability to modify the model’s parameters or to obtain hidden activations.

* **Deterministic Prompt Length Limit** – Because commercial APIs (e.g., GPT‑3.5‑turbo) have a maximum context window (often 4 k tokens), the prompt must be crafted to stay within this bound.  This motivates the use of **feature bagging** and **ensemble** techniques to keep any single query lightweight.

* **Temperature and Sampling Controls** – The LLM is invoked with a moderate temperature (e.g., 0.5) to encourage diverse rule generations across ensemble members while still yielding coherent logical statements.

* **Parsing Assistance** – Since the LLM’s raw output may contain minor syntactic variations (“greater than” versus “>”), a secondary LLM call is used to translate the natural‑language rule into executable code.  This parsing step is also performed via API calls, not via external parsers.

These assumptions reflect the **practical deployment scenario**: a data scientist has access to a commercial inference endpoint and wishes to avoid the heavy computational cost of per‑sample LLM inference that characterizes many earlier approaches.

---

## 6. Evaluation Metrics

Because we are dealing with classification, the primary metric reported throughout the paper (and repeated in this book) is the **Area Under the Receiver Operating Characteristic Curve (AU‑ROC or simply AUC)**.  AUC measures the ability of the predictor to rank positive instances higher than negative ones, independent of any particular decision threshold.  Formally, for binary classification,  

\[
\text{AUC} = \Pr\big( \hat{p}_{1}(\mathbf{x}^{+}) > \hat{p}_{1}(\mathbf{x}^{-}) \big),
\]

where \(\mathbf{x}^{+}\) and \(\mathbf{x}^{-}\) denote a randomly drawn positive and negative test example, respectively.  For multiclass problems we compute the **macro‑averaged** AUC across all one‑vs‑rest binary sub‑problems.

When reporting results we also provide **standard deviations** across the random \(k\)-shot splits to indicate robustness.  In addition, we sometimes examine **training and inference runtime** (seconds per dataset) to highlight FeatLLM’s computational efficiency relative to baseline methods.

---

## 7. Summary of the Formal Problem

Putting all components together, the **few‑shot tabular classification problem with LLM‑driven feature engineering** can be restated as follows:

> **Given**  
> • A full dataset \(\mathcal{D}\) with feature vectors \(\mathbf{x}^{(i)}\), class labels \(y^{(i)}\), feature names \(F\), and optional textual definitions \(\mathsf{desc}(f_{j})\).  
> • An API that provides completions from a pre‑trained LLM \(\mathcal{L}\).  
> • A budget of \(k\) labeled examples \(\mathcal{D}_{\text{train}}\).  

> **Find** a mapping \(\hat{p}\) that, for any unseen \(\mathbf{x}\), yields accurate class probabilities, while requiring **only a handful of LLM calls** (independent of the number of test samples) and **no fine‑tuning** of \(\mathcal{L}\).

The remainder of the book shows how FeatLLM fulfills this objective: Section 2 introduces the prompt design that coax \(\mathcal{L}\) into emitting logical rules; Section 3 explains how those rules are turned into binary features; Section 4 details the learning of non‑negative linear weights; and Section 5 demonstrates, empirically, that this pipeline attains superior AUC scores with minimal inference latency.
