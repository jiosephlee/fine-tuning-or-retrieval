\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 4: # Designing Prompts for Rule Extraction  

In order to harness a large language model (LLM) as a feature engineer, the **FeatLLM** framework relies on a carefully crafted prompt that steers the model toward producing a set of deterministic rules (“criteria”) that separate the answer classes.  This chapter dissects the three‑part prompt design that underlies the rule‑extraction stage: (1) the **basic information block**, (2) the **reasoning instruction**, and (3) the **response instruction**.  Each component plays a distinct role in supplying the LLM with the necessary context, encouraging structured reasoning, and ensuring that the generated output can be parsed automatically into binary features.  The discussion proceeds from the high‑level purpose of each block to concrete implementation details such as serialization of tabular rows, chain‑of‑thought prompting, and strategies for controlling prompt length when the number of columns grows.

---  

## Basic Information Block: Task Description, Feature Names/Types, and Few‑Shot Examples  

The first segment of the prompt establishes the **ground truth** that the LLM must reason about.  It contains three sub‑elements:

1. **Task description** – A concise natural‑language question that frames the classification problem.  In the original experiments the question adopts a *yes/no* form, for example:  

   > “Does this patient’s myocardial infarction complications data indicate chronic heart failure? Yes or no.”  

   This formulation mirrors how a human expert would phrase the diagnostic query and alerts the model to the target label space.

2. **Feature metadata** – For each column in the tabular data we provide the feature name (the natural‑language identifier present in the dataset) together with its **type** (numeric, categorical, boolean) and, when available, a succinct definition.  The type annotation is crucial because later, when the LLM writes a rule, it must respect the appropriate comparison operators.  For a categorical column we may optionally list the admissible categories, e.g., `f_7 is one of {‘low’, ‘medium’, ‘high’}`.  Supplying this information prevents the model from generating ill‑typed conditions such as “`f_3` equals 3.7” when `f_3` is a string.

3. **Few‑shot demonstrations** – A small set of labeled examples (the *k‑shot* training set) is serialized into natural language and appended to the prompt.  The serialization follows the convention used in prior LLM‑tabular work:

   \[
   \text{Serialize}(\mathbf{x}^i,\mathbf{y}^i,F) =
   \text{``}f_1\text{ is }x^i_1.\; \dots\; f_d\text{ is }x^i_d.\; \text{Answer: }y^i\text{''}.
   \]

   Each line explicitly states the value of a feature followed by a period, ending with the ground‑truth label.  By presenting the model with a handful of concrete instances, we enable it to align its abstract reasoning (derived from prior knowledge) with the specific data distribution of the target task.

Collectively, the basic information block supplies the **what** (the classification question), the **which variables** (feature names and types), and the **examples of** *how* the variables relate to the labels.  This mirrors the way a domain expert would first read the problem statement and then examine a few patient records before attempting to formulate diagnostic criteria.

---  

## Serialization of Tabular Rows into Natural Language  

Tabular data are inherently a matrix of numbers and strings, but LLMs operate on sequential text.  Therefore, each row must be transformed into a **linear, human‑readable narrative**.  The serialization strategy employed in FeatLLM adheres to the following principles:

* **Deterministic ordering** – Features are always listed in the same order (e.g., alphabetical or the original column order).  This removes ambiguity for the LLM and simplifies downstream parsing of the generated rules.

* **Explicit type cues** – When a feature is numeric we keep the literal number; when it is categorical we retain the string label.  For boolean features we use “True/False”.  No implicit rounding or formatting is applied; the raw value from the dataset is inserted verbatim.

* **Compactness** – Although the prompt must be expressive, excessive verbosity inflates the token count and can exceed the LLM’s context window.  Consequently, each feature is expressed as a short clause of the form “`f_j` is `<value>`.”  No auxiliary explanations or units are added unless they are part of the provided definition.

* **Consistency across examples** – All few‑shot rows share the same template, ensuring that the model can detect the pattern “feature‑value → answer” and infer that the mapping from features to label is the target of reasoning.

The resulting serialized text looks like:

```
age is 45. cholesterol is 210. smoking_status is 'yes'. … Answer: 1
```

Because the LLM receives the same structural pattern for each demonstrated row, it can more easily identify which attributes tend to co‑occur with a particular class, a prerequisite for the next reasoning stage.

## Reasoning Instruction: Two‑Step Chain‑of‑Thought  

After the basic information, FeatLLM injects a **reasoning instruction** that explicitly tells the LLM how to think.  This instruction draws inspiration from the chain‑of‑thought prompting paradigm, but it is tailored to rule extraction.  The instruction divides the model’s internal reasoning into **two sequential steps**:

### Step 1 – Causal or Tendential Inference  

The model is first asked to consider **only the task description and the feature metadata**, deliberately ignoring the few‑shot examples.  The prompt encourages the LLM to leverage its stored world knowledge and to articulate a *causal hypothesis* about which features are likely relevant.  For instance:

> “First, based on the medical knowledge embedded in your training data, list the patient attributes that are generally associated with chronic heart failure.”

The result of this step is a short textual enumeration of *potentially important* features (e.g., “age, prior myocardial infarction, ejection fraction”).  Because the model does not yet see any concrete examples, the output reflects **prior knowledge** rather than spurious correlations present in the few labelled rows.

### Step 2 – Rule Deduction Using Few‑Shot Demonstrations  

Having identified a candidate set of influential features, the LLM proceeds to **derive concrete decision rules** that separate the classes, now incorporating the few‑shot examples.  The instruction explicitly links the two stages:

> “Now, using the example patients provided above together with the attributes you identified, formulate ten logical rules that would allow you to answer ‘yes’ or ‘no’ for any new patient.”

The requirement to produce a **fixed number of rules** (ten per class, as set in the experiments) serves two purposes:

1. It prevents the model from generating too few rules, which would under‑represent the decision boundary, and it also prevents an explosion of rules that would swell the prompt beyond the context limit.  
2. It offers a predictable dimensionality for the downstream binary feature vector (each rule becomes one binary feature).

The two‑step approach mitigates the risk of the model latching onto **spurious correlations** that could appear in the few‑shot data (e.g., a random column that happens to co‑occur with the positive class).  By first grounding the reasoning in domain knowledge, the model is nudged to focus on genuinely relevant columns before fine‑tuning its rule set with the concrete examples.

---  

## Response Instruction: Exact Format for Rule Output and Logical Operators  

The final component of the prompt tells the LLM **how to structure its answer** so that downstream parsing can be performed automatically.  Without explicit formatting guidance, the model might embed rules in free‑form prose, use unconventional symbols, or combine multiple conditions in an ambiguous manner.  The response instruction therefore specifies:

1. **Section headings per class** – The answer must begin with a marker such as “**Rules for class 0:**” followed by a numbered list, and similarly for “**Rules for class 1:**”.  This delineation enables a straightforward split of the output into class‑specific rule sets.

2. **Rule syntax** – Each rule must be a single logical clause that respects the feature type.  For numeric features the allowed operators are `<`, `<=`, `>`, `>=`, `=`; for categorical features the operator is `=` and the value must be quoted if it contains spaces.  Example rule lines:

   ```
   1. age > 60
   2. ejection_fraction <= 30
   3. smoking_status = 'yes'
   ```

3. **Logical composition** – The instruction permits the combination of multiple atomic conditions with the logical operator **AND** only, thereby keeping the rule a conjunction of simple predicates.  The use of **OR** or more complex nesting is disallowed because it would complicate the binary conversion step (each rule must map to a single Boolean test).  If a user wishes to express a disjunction, the model is instructed to emit two separate rules.

4. **No extraneous text** – The model should not add explanations, confidence scores, or anything outside the numbered list.  Any deviation is caught early by a validation script that checks for the presence of the required headings and the exact number of rules.

By constraining the output in this manner, FeatLLM can reliably feed the generated rule strings to a second LLM call that translates them into executable Python code (e.g., a function that takes a row dictionary and returns a binary vector).  Even if the LLM occasionally substitutes “greater than” for the symbol “>”, the subsequent parsing step is robust because it re‑passes the rule text to the LLM itself for code generation, exploiting the model’s ability to understand natural‑language variations while still producing syntactically correct code.

## Prompt Length Considerations and Feature‑Bagging Tricks  

A practical limitation of any in‑context learning system is the **context window size** of the underlying LLM (e.g., 4 k tokens for GPT‑3.5).  When a tabular dataset contains many columns (hundreds in the *Communities* or *Myocardial* datasets), naively serializing **all** feature names, types, and few‑shot rows would exceed this limit.  FeatLLM addresses this issue using two complementary strategies:

1. **Feature‑bagging** – For each ensemble trial, a random subset of the full feature set is selected (e.g., 30 % of columns).  The prompt then includes only the metadata and serialized values for this subset.  Because each trial uses a different random bag, the aggregate ensemble still has exposure to the entire feature space, while any single LLM query stays comfortably within the token budget.

2. **Limited rule count** – By fixing the number of extracted rules per class (ten), the size of the response is bounded.  Moreover, the rule extraction step does not need to enumerate every feature; the two‑step reasoning instruction prunes irrelevant columns early, which naturally reduces the amount of text the model has to attend to.

During training, the number of ensemble members (*T*) and the bag‑size are hyper‑parameters; empirical results in the paper show that increasing *T* up to about 20 yields diminishing returns, and a bag proportion that keeps the prompt under the context window while still preserving a representative slice of features works well across datasets.

---  

### Summary  

The three‑part prompt for rule extraction in FeatLLM is a **structured communication protocol** that transforms an LLM from a black‑box predictor into a knowledgeable feature engineer.  The **basic information block** grounds the model in the task, supplies precise feature metadata, and demonstrates concrete examples.  The **reasoning instruction** enforces a disciplined two‑step chain‑of‑thought: first invoking prior knowledge to identify relevant attributes, then refining that insight into a fixed set of logical rules using the few‑shot data.  Finally, the **response instruction** guarantees that the generated rules appear in a machine‑parsable format, facilitating automatic conversion into binary features.  By coupling this prompt design with feature‑bagging and a modest ensemble, FeatLLM sidesteps context‑window constraints, reduces inference cost, and produces high‑quality, interpretable rules that drive strong few‑shot classification performance.
