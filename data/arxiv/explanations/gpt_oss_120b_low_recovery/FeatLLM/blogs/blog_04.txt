\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# From Rules to Binary Features: Turning Natural Language into Machine‑Learnable Signals  

## Introduction  

Tabular data—think spreadsheets of patient records, credit applications, or sensor logs—are the backbone of countless real‑world AI systems. Yet getting high‑quality predictions from a handful of labeled examples remains a hard problem. Recent work shows that large language models (LLMs) can bring their world knowledge to bear on these tasks, but most approaches still treat the LLM as a black‑box predictor that must be queried for every new sample.  

**FeatLLM** takes a different route. Rather than asking the LLM “what’s the label for this row?”, we ask it “what rules would tell you the label?”. The LLM spits out natural‑language conditions (e.g., “age > 65 AND blood‑pressure > 140”), we turn those conditions into tiny pieces of executable code, and finally we compile the results into a set of binary features. A simple linear model then learns how much each rule should count toward each class. The whole pipeline reduces inference cost dramatically while preserving (or even improving) predictive performance.

Below we walk through each stage of this pipeline, from prompting the LLM for rules to training a lightweight classifier on the resulting binary signals.

## 1. Prompting the LLM to Generate Rules  

### Structured Prompt  
Featurizing an LLM’s knowledge starts with a carefully crafted prompt that mimics how a human analyst would approach a new tabular problem:

1. **Basic Information** – A concise description of the task (e.g., “Predict whether a patient will develop chronic heart failure”), a list of feature names with their types/definitions, and a few serialized few‑shot examples (`feature1 is value1 … Answer: Yes/No`).  

2. **Reasoning Instruction** – A two‑step chain‑of‑thought instruction:  
   *Step 1* asks the model to reason about which columns are *a priori* relevant based solely on its background knowledge (no training examples).  
   *Step 2* asks it to refine that intuition using the provided examples and to produce **10 explicit rules per class** (the number was chosen empirically; see the paper’s ablation).  

3. **Response Instruction** – Clear formatting constraints so the output can be parsed automatically (e.g., each rule on its own line, using `>`/`<`/`=` for numeric comparisons and `==` for categorical equality).

The prompt deliberately separates **knowledge extraction** (Step 1) from **empirical rule fitting** (Step 2), discouraging the model from latching onto spurious correlations in the few-shot data.

### Example Output  

```
Class: Yes
1) age > 70
2) cholesterol >= 250
3) blood_pressure > 140 AND smoker == Yes
...
Class: No
1) age <= 45
2) cholesterol < 180
...
```

These human‑readable rules are what we later turn into machine features.

## 2. Parsing Natural‑Language Rules into Executable Code  

The raw textual rules are not yet machine‑readable. Direct string parsing can be brittle—LLMs may write “greater than” instead of “>”, add extra spaces, or reorder logic. FeatLLM sidesteps this by *leveraging the LLM itself* as a parser:

1. **Create a secondary prompt** that includes:
   - The original rule list.
   - A short function skeleton (`def apply_rules(row): ...`) describing inputs (`row` as a dict of column values) and expected boolean outputs.
   - Explicit instructions to emit pure Python code that evaluates each rule and returns a list of binary indicators.

2. **Send this prompt back to the LLM** (still using GPT‑3.5 in the paper). Because the model has been trained on massive amounts of code, it reliably converts phrases like “greater than” → `>`, “AND” → `and`, and handles type casting automatically.

3. **Execute the generated snippet with Python’s `exec()`** in a sandboxed environment. The resulting function maps any row to a vector `z ∈ {0,1}^R`, where `R = 10 × #classes` is the total number of extracted rules.

This “code‑as‑intermediate” step removes most parsing errors without hand‑written regexes, making the pipeline robust to variations in LLM output.

## 3. From Rules to Binary Features  

Each row now has an associated binary vector:

\[
\mathbf{z}_k^i = \big[\,\text{rule}_{k,1}(\mathbf{x}^i),\dots,\text{rule}_{k,R}(\mathbf{x}^i)\,\big] \in \{0,1\}^{R},
\]

where \(k\) indexes the target class and \(\mathbf{x}^i\) is the original feature vector. Intuitively, entry \(\mathbf{z}_k^i[j]=1\) tells us that row \(i\) satisfies rule \(j\) for class \(k\).

Because these features are *highly interpretable* (each is just “does this patient meet condition X?”), they also provide immediate insight for domain experts—a nice side effect often missing in deep tabular models.

## 4. Light‑Weight Linear Model on Binary Features  

The binary matrix \(\mathbf{Z}\) is fed into an extremely simple classifier:

\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,
\qquad 
\mathbf{p}^i = \text{softmax}\big(\text{logit}_1^i,\dots,\text{logit}_c^i\big),
\]

where:
- \(\mathbf{w}_k \in \mathbb{R}^R_{\ge 0}\) are learnable weights (non‑negative via a ReLU projection).
- The dot product counts *weighted* rule satisfactions.
- Softmax turns logits into class probabilities.

Training is just standard cross‑entropy minimisation on the few available labeled rows (the same rows used in the prompting stage). Since only \(R\) parameters per class need learning, convergence is fast even with as few as four shots.

### Why Not Skip Training?  
A naive baseline would simply sum satisfied rules per class (i.e., set all weights to 1). The paper’s ablation shows this works reasonably well when shots are extremely scarce, but learns substantially better importance estimates once more labeled points become available—especially for datasets with many overlapping or noisy rules.

## 5. Ensembling & Feature Bagging  

Two practical challenges arise:

1. **Prompt Length Limits** – Large tables can exceed the context window if we list every column in one go.
2. **Rule Diversity** – A single LLM query may miss useful patterns.

FeatLLM addresses both with an ensemble:
- **Bagging**: For each ensemble member we randomly select a subset of columns and/or training examples before prompting.
- **Temperature Sampling**: We run the LLM at temperature 0.5, encouraging varied rule sets across members.
- **Aggregation**: After training separate linear models on each member’s binary features, we average their softmax outputs at inference time.

Empirically, performance plateaus after ≈20 ensemble members; beyond that additional members yield diminishing returns while increasing API cost modestly.

## 6. Benefits Over Traditional LLM‑Based Tabular Methods  

| Aspect | Traditional In‑Context Tabular Models | FeatLLM |
|--------|---------------------------------------|---------|
| **Inference Cost** | One LLM call per test row (slow, expensive) | Zero LLM calls after feature generation |
| **API Requirements** | Needs fine‑tuning or repeated calls → often unavailable for closed APIs | Only requires a handful of API queries during setup |
| **Scalability** | Prompt size grows linearly with number of columns; quickly hits limits | Bagging keeps each prompt small; ensemble mitigates information loss |
| **Interpretability** | Model internals opaque | Each binary feature corresponds to an explicit natural-language rule |
| **Performance (few‑shot)** | Often lags behind classic ML baselines | Matches or surpasses conventional models with ≤4 shots |

In benchmark experiments across 13 heterogeneous datasets, FeatLLM delivered an average AUC gain of ≈10 % over strong baselines such as TabLLM and STUNT, while keeping inference latency comparable to logistic regression.

## 7. Practical Takeaways  

- **Prompt Design Matters**: Splitting reasoning into “knowledge first, data second” yields cleaner rules.
- **Leverage LLMs for Code Generation**: Using the same model as a parser dramatically reduces brittle string handling.
- **Keep Rules Binary**: Binary indicators simplify downstream learning and keep interpretability intact.
- **Ensemble Early**: Slight randomization at rule generation time yields robust performance without blowing up API usage.
- **Fine‑Tune Light Weights Only**: Even with as few as four labeled examples, learning non‑negative rule weights improves results over simple counting.

## Conclusion  

Turning natural language conditions into binary signals bridges the gap between an LLM’s rich world knowledge and conventional machine learning pipelines. FeatLLM demonstrates that a modest number of API calls can produce high‑quality features that enable ultra‑lightweight classifiers to thrive in low‑shot regimes—making AI more accessible for domains where data labeling is costly but expert knowledge already exists in text form.

If you’re working with tabular data and have access to an LLM API, try swapping your traditional end‑to‑end prompting for this “rule → binary feature → linear model” workflow. You’ll likely see cheaper inference, clearer explanations, and competitive—or even superior—prediction quality. Happy modeling!
