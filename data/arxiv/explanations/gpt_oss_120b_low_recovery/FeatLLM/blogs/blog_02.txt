# Why Few‑Shot Tabular Learning Matters and How FeatLLM Solves It  

## The Problem: Tiny Labeled Datasets  

In many real‑world settings—think medical diagnosis, credit scoring, or industrial monitoring—collecting a large, high‑quality labeled table is expensive or even impossible. Often we only have a handful of examples (2, 4, 8 …) for a new prediction task. Traditional machine‑learning pipelines (logistic regression, random forests, XGBoost) struggle in this “few‑shot” regime: with so little data they quickly overfit to noise and fail to capture the true relationships between columns and the target label.

A common remedy is to inject **prior knowledge**. If a model already knows that “older age increases heart disease risk” or that “high cholesterol is linked to diabetes,” it can make better predictions even when only a few labeled rows are available. Large language models (LLMs) such as GPT‑3.5 have already absorbed massive amounts of domain knowledge from web text, making them natural candidates for providing that extra boost.

## Existing LLM‑Based Approaches: What’s Missing?  

Recent work has indeed tried to feed tabular data into an LLM as plain text, asking the model to predict the label directly (in‑context learning) or to fine‑tune it on a few examples. While promising, these methods suffer from three practical drawbacks:

1. **Per‑sample LLM inference** – Every new row must be sent through the LLM, leading to high latency and cost.  
2. **Prompt length limits** – Serializing a table with many columns quickly exceeds the LLM’s context window, degrading performance or making the query impossible.  
3. **Dependency on fine‑tuning APIs** – Some top‑performing LLMs are only accessible via inference endpoints; they cannot be fine‑tuned, which blocks methods that rely on parameter updates.

In short, we have powerful models but an inefficient way of using them for tabular prediction.

## The Insight: Let the LLM Engineer Features Instead of Predict  

Instead of treating the LLM as a black‑box predictor for every row, **FeatLLM** asks a different question: *“What logical conditions (rules) would let me decide the class?”*  
If the model can articulate statements such as “Age > 65 AND cholesterol > 200 → high risk”, those statements can be turned into **binary features** (true/false for each rule). Once we have this engineered feature set, any lightweight classifier—e.g., a linear model—can map them to class probabilities.

This shift brings several advantages:

* **Zero per‑sample LLM calls** – After the rules are extracted once (using only a few-shot prompt), all subsequent predictions use only the cheap linear model.  
* **Prompt size no longer a bottleneck** – The rule extraction prompt contains only the few demonstrations and feature descriptions, not the entire test set.  
* **Works with API‑only LLMs** – No fine‑tuning is required; just a handful of API calls to obtain the rules.

## How FeatLLM Works – Step by Step  

### 1️⃣ Prompt Design: Structured Reasoning  

FeatLLM crafts a three‑part prompt for the LLM:

1. **Basic information** – Task description (e.g., “Does this patient have chronic heart failure?”), natural‑language feature names & definitions, and a few serialized training examples (`f1 is 45. … Answer: Yes`).  
2. **Reasoning instruction** – A chain‑of‑thought style cue splits reasoning into two stages:  
   * *Step 1:* Infer general causal tendencies from background knowledge alone (no examples).  
   * *Step 2:* Use both the inferred tendencies and the few-shot examples to generate **10 explicit rules per class** (the number is fixed for stability).  
3. **Response instruction** – Tell the LLM exactly how to format each rule (e.g., `feature > value`) so that downstream parsing is reliable.

The two‑step reasoning forces the model to rely on its prior knowledge first, then fine‑tune that understanding with the actual data points—helpful when only a few rows are available.

### 2️⃣ Turning Rules into Binary Features  

The raw natural‑language rules are noisy (“greater than” vs “>”). Rather than write a brittle parser, FeatLLM feeds each rule back into the same LLM with a short code‑generation prompt (`def check(row): return row["age"] > 65`). The model returns runnable Python code that evaluates whether any given row satisfies each rule. Executing this code yields a binary vector  

\[
\mathbf{z}_k^i \in \{0,1\}^{R},
\]

where \(R\) is the number of rules per class and \(k\) indexes the class.

### 3️⃣ Learning Simple Weights  

A linear model without bias consumes these binary features:

\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,
\qquad
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big).
\]

Training simply optimizes cross‑entropy on the few labeled rows, learning which rules are truly informative (negative weights are clamped to zero so rules never hurt a class). This step is extremely cheap—just a handful of gradient steps.

### 4️⃣ Bagging & Ensembling for Robustness  

To mitigate two remaining challenges—prompt length for very wide tables and variability in generated rules—FeatLLM repeats the whole pipeline multiple times:

* Randomly **bag** a subset of columns or examples before prompting (reducing prompt size).  
* Use a higher temperature during rule generation to encourage diverse rule sets across runs.  

The resulting linear models are averaged at inference time (standard ensemble voting), which smooths out occasional bad rules and further improves accuracy.

## Performance Highlights  

Across 13 diverse benchmark datasets (including classic UCI tasks like Adult and Credit‐g as well as recent or synthetic tables not seen during LLM pretraining), FeatLLM consistently outperformed strong baselines:

| Dataset | 4‑shot AUC (FeatLLM) | Best non‑LLM baseline | Avg improvement |
|---------|----------------------|-----------------------|-----------------|
| Adult   | 0.89                 | XGBoost (0.84)        | +5% |
| Myocardial | 0.93              | TabLLM (0.81)         | +12% |
| Cultivars | 0.87               | RandomForest (0.78)   | +9% |

On average FeatLLM gains about **10 % AUC** over modern few‑shot tabular methods such as TabLLM and STUNT, while requiring **orders of magnitude less inference time** because only the initial rule extraction uses the LLM.

Ablation studies confirm that every component matters:

* Removing weight tuning hurts performance more as shots increase (the linear model can better exploit many rules).  
* Dropping feature descriptions or the two‑step reasoning harms low‑shot performance—the LLM loses valuable prior knowledge cues.  
* Skipping ensembling lowers robustness especially on wide tables.

## Why This Matters in Practice  

1. **Fast, cheap predictions** – After an initial handful of API calls (< 30), you can serve millions of rows with a trivial linear model on CPU/GPU.  
2. **Works with restricted APIs** – No need for LoRA or other fine‑tuning tricks; any closed‑source endpoint that supports text completion suffices.  
3. **Scales to many features** – Feature bagging keeps prompts within context limits even when tables have > 100 columns.  
4. **Interpretability out of the box** – The extracted rules are human readable; analysts can inspect which logical conditions drive each prediction.

## Looking Ahead  

FeatLLM currently focuses on low‑shot classification using rule‐based binary features. Future directions include:

* Extending to regression tasks by generating quantitative transformations rather than boolean rules.  
* Exploring richer feature families (e.g., interaction terms, embeddings) while retaining interpretability.  
* Systematically auditing how biases present in LLM knowledge affect generated rules and downstream decisions.

## Takeaway  

Few‑shot tabular learning is indispensable when labels are scarce but decisions still matter urgently. By rethinking what we ask an LLM—“Give me good features,” not “Predict every row”—FeatLLM turns massive pretrained knowledge into compact, reusable rule sets that dramatically boost performance while staying practical for production use cases. If you’re grappling with tiny labeled tables and have access to an LLM API, give FeatLLM’s rule extraction pipeline a try; you’ll likely see higher accuracy with far lower inference cost than sending every row through an LLM directly.
