\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Bagging and Ensembling with LLM‑Generated Features: Boosting Robustness at Scale  

Large language models (LLMs) have become go‑to tools for few‑shot learning, but most current pipelines still rely on **one LLM query per data point**. That design is expensive, hits prompt‑size limits, and can be brittle when the model drifts into noisy or spurious rules.  

The recent **FeatLLM** framework flips this paradigm: instead of using the LLM as a black‑box predictor, it treats the LLM as an *expert feature engineer*. By prompting the model to output decision rules (e.g., “age > 45 AND cholesterol > 200”), FeatLLM turns those natural‑language rules into binary features that a tiny downstream model (a linear classifier) can consume. The real magic, however, lies in **how FeatLLM makes those rules robust**, especially when dealing with high‑dimensional tabular data. Below we unpack three core tricks—feature bagging, temperature‑induced diversity, and ensemble averaging—that together let FeatLLM scale to dozens or hundreds of columns while staying fast and reliable.

---

## 1. From a Single Prompt to Many: Why Bagging Matters  

When a dataset has many attributes (think the *Communities* or *Myocardial* benchmarks with > 100 columns), simply stuffing all feature names and definitions into one prompt blows past the LLM’s context window. Moreover, a monolithic prompt makes it hard for the model to focus on the truly informative columns; irrelevant fields can drown out useful signals.

**FeatLLM’s solution:** *feature bagging*.  
Instead of sending every column at once, FeatLLM repeatedly samples a random subset of features (e.g., 30 % of the columns) and builds a fresh prompt around that subset. Each bagged prompt goes through the same two‑step reasoning process:

1. **High‑level causal inference** – “What kinds of attributes usually matter for this medical diagnosis?” – leveraging the LLM’s world knowledge.
2. **Rule extraction** – using the few labeled examples to anchor those high‑level hints into concrete conditions.

Because each bag contains a different slice of the data, the LLM produces **different rule sets** that are each tuned to a particular perspective on the problem. This mitigates two pain points:

* **Prompt length:** smaller bags stay well within the model’s token limits.  
* **Feature coverage:** across many bags, every column gets a chance to be examined, reducing the risk that a useful predictor is permanently ignored.

---

## 2. Temperature‑Induced Diversity: Letting the LLM “Think Differently”  

Even with feature bagging, if we always query the LLM with temperature = 0 (deterministic decoding), each bag would yield an identical set of rules every time we repeat the experiment. That defeats the purpose of ensembling—there would be no diversity to average over.

FeatLLM deliberately **raises the temperature** (e.g., to 0.5) when generating rules. A higher temperature injects stochasticity into token selection, which translates into:

* Slight variations in phrasing (“> 45” vs “greater than 45”).  
* Different logical groupings (sometimes combining conditions with *AND*, other times with *OR*).  
* Occasionally proposing alternative thresholds that still make sense given domain knowledge.

These stochastic outputs are *not* random noise; they are plausible alternatives drawn from the same underlying knowledge base. When later parsed into binary features, each variant offers an additional weak signal that can be weighted up or down during training.

---

## 3. Ensemble Averaging: Turning Weak Learners into a Strong One  

After we have **T** bagged rule sets (the paper uses T = 20 as a default), each set yields a binary feature vector \(\mathbf{z}_k^i\) for every class \(k\). A simple linear model – essentially a weighted sum followed by Softmax – turns those binaries into class probabilities:

\[
\text{logit}_k^i \;=\; \max(\mathbf{w}_k,0) \cdot \mathbf{z}_k^i,\qquad
\mathbf{p}^i = \text{Softmax}([\text{logit}_1^i,\dots,\text{logit}_c^i]).
\]

Crucially, **the weights \(\mathbf{w}_k\) are learned from the few labeled examples**, so they automatically down‑weight noisy or irrelevant rules while amplifying those that truly correlate with the target.

To combine multiple bagged models, FeatLLM simply **averages their probability vectors**:

\[
\bar{\mathbf{p}}^i = \frac{1}{T}\sum_{t=1}^{T} \mathbf{p}^{i}_{[t]} .
\]

This averaging brings two benefits:

1. **Robustness to mis‑generated rules.** If one bag’s LLM call produces an outright wrong rule (e.g., “blood pressure < 0”), its impact is diluted across the ensemble.
2. **Self‑consistency bias.** Rules that appear in many bags tend to be more reliable; their associated features receive higher effective weight after averaging.

The result is a lightweight yet powerful predictor whose inference cost is comparable to classic linear models—no per‑sample LLM calls at all.

---

## 4. Putting It All Together: Scaling to Large Tabular Problems  

Here’s how FeatLLM handles a real‑world scenario step by step:

| Step | What Happens | Why It Helps |
|------|--------------|--------------|
| **a) Sample Feature Subset** | Randomly pick \(p\%\) of columns (bagging). | Keeps prompts short; guarantees eventual coverage of all columns across repetitions. |
| **b) Build Prompt** | Insert task description, feature names & types, and k‑shot examples. | Gives LLM both prior knowledge and empirical evidence. |
| **c) Generate Rules (Temp = 0.5)** | LLM outputs ~10 binary conditions per class in a fixed format. | Stochasticity yields diverse rule families without extra engineering. |
| **d) Parse & Execute Code** | Send rules back to LLM for simple Python code that turns them into binaries. | Handles linguistic quirks (“greater than” vs “>”) automatically. |
| **e) Fit Linear Model** | Train non‑negative weights on these binaries using cross‑entropy loss (few shots). | Learns which rules truly matter; filters out spurious ones. |
| **f) Repeat T Times & Average** | Steps a–e are repeated T times; final prediction = average of Softmax outputs. | Ensembles over many weak learners → stable, high‑performing classifier. |

Because all heavy lifting happens *once* during preparation (≈30 API calls in experiments), deployment is essentially just matrix multiplication—a fraction of a millisecond per record.

---

## 5. Empirical Takeaways  

- **Accuracy boost:** Across 13 diverse datasets, FeatLLM outperforms traditional few‑shot baselines by ~10 % AUC on average, even when only 4 labeled examples are available.
- **Prompt size resilience:** Datasets with > 100 features still achieve strong performance thanks to bagging; alternatives like plain in‑context learning often crash or degrade sharply.
- **Noise resistance:** Adding irrelevant columns (spurious correlations) hurts other models dramatically; FeatLLM’s performance stays nearly flat because its rule extraction stage ignores unrelated attributes early on.
- **Speed:** Inference time matches conventional linear models and is orders of magnitude faster than per‑sample LLM querying pipelines (e.g., TabLLM or TABLET).

---

## 6. Practical Tips for Practitioners  

1. **Pick a sensible bag size:** Roughly 30–50 % of total columns works well—large enough to give context but small enough for token limits.
2. **Use temperature ≈ 0.5:** Higher values increase diversity but can also produce malformed rules; lower values make ensembles too similar.
3. **Fix rule count per class:** The authors found 10 rules per class strike a good balance between expressive power and overfitting risk.
4. **Enable early stopping on linear weights:** With very few shots, limiting training epochs prevents noise amplification.
5. **Monitor rule quality:** A quick AUROC check on generated binaries (“Before tuning”) can flag pathological prompts before committing compute.

---

## 7. Looking Ahead  

FeatLLM demonstrates that an LLM does not need to sit in the inference loop forever—it can act as an *offline knowledge distiller*, converting rich textual priors into concrete tabular features that traditional ML models can consume efficiently. The combination of feature bagging, temperature-induced stochasticity, and ensembling offers a template for any scenario where you must wrangle large feature spaces under tight latency or API budgets.

Future directions might include:

- Extending beyond binary rule features to richer transformations (e.g., discretization bins or learned embeddings).  
- Integrating domain‐specific constraints directly into the prompting logic for even tighter rule relevance.  
- Exploring adaptive bag sizes that focus more sampling effort on columns whose importance remains uncertain after early rounds.

For now, though, FeatLLM provides a practical recipe: let your LLM *think* about what matters, extract those thoughts as reusable features, and then let classic linear algebra finish the job—fast, scalable, and robust enough for real-world tabular workloads.
