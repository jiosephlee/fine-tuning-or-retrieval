\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Why does omitting feature descriptions hurt performance more in very low‑shot settings?
Question:
Table 3 shows that removing feature descriptions (-Description) leads to larger AUC drops when k=2 compared to k=8. Is this because the LLM relies on natural‑language definitions to compensate for lack of data? How critical are these descriptions when working with domains where feature names are cryptic (e.g., column names like "X1", "X2")?

Answer:
In the Feat LLM framework the LLM is asked to **invent rules** that separate the classes and then those rules are turned into binary features for a tiny linear model.  
When only a few labelled examples are available (e.g. \(k=2\)), the LLM has virtually no data‑driven signal to tell it which columns are actually relevant. It must therefore lean on whatever other information it can extract from the prompt.  

The *feature description* component of the prompt supplies exactly that missing signal: a short natural‑language definition of each column (its type, possible values, and, when available, a domain‑level meaning). Because the LLM has been trained on massive amounts of textual knowledge, it can match these definitions to its internal world‑knowledge (“age > 60 → higher risk of heart disease”, “serum‑creatinine = high → renal failure”, etc.). When the description is present, the LLM can:

1. **Identify informative columns** even if the few training rows do not contain enough variation to reveal the relationship.
2. **Ignore irrelevant or noisy columns** by recognizing that their definitions bear no semantic connection to the task description.
3. **Form plausible causal hypotheses** that are later refined by the few examples.

If we remove the descriptions (the “‑Description” ablation), the LLM is left with only the raw column names (e.g. *X1*, *X2*, …) and the few example rows. In a 2‑shot setting those rows rarely exhibit the full range of feature values, so the LLM cannot reliably infer which attributes matter from data alone. Consequently it either (a) generates rules that involve uninformative columns, or (b) fails to generate enough useful rules, both of which lead to a noticeable drop in AUC.

When more shots are available (e.g. \(k=8\)), the few labelled examples already provide a modest statistical glimpse of the true relationships; the LLM can use this data‑driven evidence to back‑track which columns are predictive, reducing its reliance on natural‑language definitions. Hence the same removal of descriptions harms performance far less: the drop in AUC is smaller because the data compensate for the missing semantic cues.

**Implications for cryptic column names**

If a dataset uses opaque identifiers such as *X1*, *X2*, … without accompanying textual definitions, Feat LLM will behave as in the “‑Description” ablation case. In very low‑shot regimes you should therefore supply explicit feature descriptions (or at least type information) in the prompt; otherwise you can expect a larger performance degradation, especially when only 1–4 labeled examples are available. Providing concise, domain‑relevant descriptions restores the LLM’s ability to draw on its pre‑trained knowledge and keeps performance stable even when label data are scarce.
