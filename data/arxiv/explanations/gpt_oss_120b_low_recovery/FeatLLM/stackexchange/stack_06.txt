\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How are categorical feature values encoded in generated rules?
Question:
The prompt design includes feature type information, but I am unsure how the LLM formulates conditions for categorical variables. For example, if a feature "MaritalStatus" has values {"single", "married", "divorced"}, does the rule look like `MaritalStatus == "single"` or `MaritalStatus in ["single", "married"]`? Are logical operators like AND/OR allowed within a single rule, and how does FeatLLM parse such composite expressions into binary features?

Answer:
**Answer**

In *FeatLLM* the LLM is asked to write **rules** that describe the conditions under which a sample belongs to a given class.  
The prompt that drives the generation contains a *response instruction* (yellow part in Fig. 2 of the paper) that tells the model how a rule must be formatted.  
Because the instruction is aware of each feature’s declared type, the LLM normally produces **type‑consistent atomic predicates**:

* for a **numerical** feature it will use a comparison such as  
  `Age > 55` or `BloodPressure ≤ 130`;
* for a **categorical** feature it will either write an equality test, e.g.  
  `MaritalStatus == "single"`, or a membership test, e.g.  
  `MaritalStatus in ["single", "married"]`.

Both forms are accepted – the parser that follows the rule‑generation stage (Sec. 3.2, “Parsing rules for feature generation”) interprets them as a **binary predicate** that evaluates to 0 or 1 for each row.  Internally the parser simply translates the natural‑language condition into a small piece of Python code (`if ...: return 1 else: return 0`) and executes it with `exec()`.  Whether the condition is written with `==` or with `in` makes no difference to the downstream binary feature: it is *true* when the sample’s categorical value matches any of the listed categories and *false* otherwise.

### Logical combinations

The response instruction also permits the LLM to combine several atomic predicates with logical operators **AND** and **OR** inside a single rule.  For instance

```
Age > 60 AND (MaritalStatus == "married" OR MaritalStatus == "divorced")
```

is a perfectly valid rule.  During parsing, the same code‑generation step transforms this expression into Python syntax (e.g. `if age > 60 and (status=="married" or status=="divorced"):`) and evaluates it for every instance, again yielding a binary feature.

If a rule contains multiple logical branches, each branch contributes exactly one **binary column** in the final feature matrix; there is no need to split it into separate columns because the whole expression already returns a single $0/1$ value.

### From rules to binary features

For each class *k* we ask the LLM to produce a fixed number $R=10$ rules (the paper fixes this number to avoid under‑/over‑fitting).  
After parsing, we obtain for sample $i$

$$
\mathbf{z}_{k}^{i} = \bigl[\,z_{k,1}^{i},\dots ,z_{k,R}^{i}\bigr]^{\top},
\qquad
z_{k,r}^{i}\in\{0,1\},
$$

where $z_{k,r}^{i}=1$ if sample $i$ satisfies rule $r$ of class $k$.  
These binary vectors are fed to a tiny linear model (Eq. (2) in the paper) whose non‑negative weights learn how important each rule‑derived feature is.

### Summary

* Categorical conditions appear as either `feature == "value"` or `feature in ["value1","value2", …]`; both are parsed into a single Boolean test.
* The LLM may join several atomic tests with **AND / OR** inside one rule; this yields one binary feature per combined expression.
* The parsing step is performed by asking the LLM itself to emit executable Python code, which reliably handles the small syntactic variations that occur in its natural‑language output.

Thus, FeatLLM can express rich, human‑readable criteria for categorical (and other) features while still converting every rule into a simple $0/1$ column that downstream models can use directly.
