\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does FeatLLM handle missing values during rule evaluation?
Question:
Real‑world tabular data often contain NaNs or missing entries. The paper does not discuss missingness. When a rule references a feature that is missing for a given row, what binary value does FeatLLM assign? Is there any imputation performed before rule evaluation, or does the generated Python code include checks for missingness?

Answer:
**Answer**

In *FeatLLM* the only place where the raw table is examined after the LLM has finished its reasoning is the piece of Python code that is generated from the textual rules (Section 3, “Parsing rules for feature generation”).  
The paper does not insert any separate imputation step; instead it relies on the semantics of the generated code and on how Python (or pandas) treats missing values (`NaN`) in the usual comparison operators.

When a rule such as

```python
def rule_1(row):
    return row["age"] > 55
```

is executed on a row whose *age* column contains `NaN`, the expression `row["age"] > 55` evaluates to `False` (actually it yields a Boolean `False` because any ordered comparison with `NaN` in NumPy/pandas returns `False`). Consequently the binary feature that records “does the row satisfy rule 1?” receives a value of 0 for that row.

The same behaviour holds for other relational operators (`<`, `==`, `!=`) and for string‑based checks (`row["sex"] == "male"`). In pandas a comparison with a missing entry also returns `False`, so a rule that asks whether a categorical value matches a given category will also produce 0 when the field is missing.

Because every rule is turned into an independent Boolean function, missingness never propagates to other rules: each rule is evaluated separately and simply yields 0 whenever any of its constituent conditions involve a `NaN`. The downstream linear model then sees a binary vector of 0/1 values; there is no additional “missing‑value flag” feature, and no special imputation (mean, median, mode, etc.) is performed before or after rule evaluation.

In short, *FeatLLM* handles missing entries implicitly:

* **No explicit imputation** – the framework does not fill in missing values beforehand.
* **Rule evaluation uses native Python/pandas semantics** – a condition that involves a missing value returns `False`, so the corresponding binary feature is set to 0.
* **Generated code may contain simple guards** – if the LLM decides to be defensive, it can emit code such as `if pd.isna(row["age"]): return False`, but this is optional and not required for correct operation; the default behaviour already yields 0.

Therefore, when you run the generated feature‑generation script on a dataset that contains `NaN`s, each rule simply treats those rows as not satisfying the rule, which translates into a 0 in the binary feature matrix used by the downstream linear model. This design keeps the pipeline simple and avoids having to decide on an imputation strategy for every new tabular problem.
