# Simplifying RL Infrastructure: Using Inference Engines Directly with GSPO  

Reinforcement learning (RL) has become the workhorse for polishing giant language models, but the engineering plumbing that supports RL can be surprisingly heavyweight. Traditional workflow—especially with token‑level algorithms like PPO or GRPO—requires us to **re‑compute token probabilities** on the training engine every time we need an importance weight. That extra forward pass inflates memory usage, adds latency, and forces us to maintain two perfectly synchronized code‑bases (training vs. inference).  

**Group Sequence Policy Optimization (GSPO)** puts an end to this friction. By moving the importance ratio from the token level to the **sequence level**, GSPO makes it safe to consume the likelihood scores that an inference engine already emitted during rollout. In practice this means you can skip the costly “re‑score with the trainer” step, cut down on GPU memory, and simplify the whole RL pipeline. Below we walk through why this works, how it changes the data flow, and what concrete savings you can expect.

---

## 1. Why Token‑Level Ratios Are a Pain Point  

In PPO and its value‑free sibling GRPO, the objective contains a term  

\[
w_{i,t}(\theta)=\frac{\pi_{\theta}(y_{i,t}\mid x,y_{i,<t})}{\pi_{\theta_{\text{old}}}(y_{i,t}\mid x,y_{i,<t})},
\]

the **importance weight** for each token \(t\) of each sampled response \(y_i\). Computing this ratio demands the exact token‑wise log‑probabilities under both the current policy \(\pi_{\theta}\) and the snapshot policy \(\pi_{\theta_{\text{old}}}\). Because training engines (e.g., Megatron) often run in mixed‑precision FP16/FP8 while inference engines (e.g., vLLM, SGLang) use slightly different numerical formats, we cannot safely reuse the inference‐engine scores for a token‑wise comparison—the accumulated rounding error would distort \(w_{i,t}\) and break the clipping mechanism.

The usual workaround is **re‑scoring**: after generating a batch of rollouts with the fast inference service, we pipe all sampled sequences back through the training engine to obtain fresh token probabilities under \(\pi_{\theta_{\text{old}}}\). This extra forward pass:

* Doubles memory bandwidth (the same sentences are stored twice).  
* Adds another GPU pass per RL step, increasing wall‑clock time by 30‑50 %.  
* Forces tight version coupling between trainer and serving code; any change in tokenizer or model layout must be mirrored on both sides.

When scaling to billions of tokens per iteration—typical for MoE models—the overhead quickly becomes a bottleneck.

---

## 2. GSPO’s Sequence‑Level Importance Ratio  

GSPO replaces \(w_{i,t}\) with a **single scalar per response**:

\[
s_i(\theta)=\left(\frac{\pi_{\theta}(y_i\mid x)}{\pi_{\theta_{\text{old}}}(y_i\mid x)}\right)^{\frac{1}{|y_i|}}
      =\exp\!\Bigg(\frac{1}{|y_i|}\sum_{t=1}^{|y_i|}
          \log\frac{\pi_{\theta}(y_{i,t}\mid x,y_{i,<t})}
                   {\pi_{\theta_{\text{old}}}(y_{i,t}\mid x,y_{i,<t})}\Bigg).
\]

Key observations:

1. **Unit Matching** – The reward \(r(x,y_i)\) is defined for an entire sequence; aligning the importance weight at the same granularity eliminates a source of variance.  
2. **Length Normalization** – Raising to the power \(1/|y_i|\) keeps \(s_i\) in a comparable range across responses of different lengths, making clipping thresholds stable.  
3. **Tolerance to Precision Drift** – Since we only need the *aggregate* log‑likelihood, small discrepancies in individual token probabilities cancel out statistically; the final scalar is far less sensitive to FP16 vs. BF16 mismatches.

Because only one value per sequence is needed, we can safely take that value directly from whatever system generated the rollout—usually an inference engine optimized for latency and throughput.

---

## 3. Data Flow With GSPO: From Rollout to Update

Below is a simplified pipeline that many RL teams already run; GSPO merely removes one step.

| Step | Traditional (GRPO/PPO) | GSPO |
|------|------------------------|------|
| **1. Sample queries** | Same | Same |
| **2. Generate responses** (inference engine) | Same | Same |
| **3. Compute token log‑probs under old policy** | **Re‑score on training engine** → massive overhead | **Reuse log‑probs already returned by inference engine** (or recompute once per batch if desired) |
| **4. Compute rewards** (verifier model) | Same | Same |
| **5. Build importance ratios** | Tokenwise \(w_{i,t}\) → clipping per token | Sequencewise \(s_i\) → clipping per response |
| **6. Gradient update** | Same optimizer but noisier gradients | Same optimizer, cleaner gradients |

The only extra computation left in GSPO is the *averaging* of token log‑probs into a single scalar—trivial compared to a full forward pass.

---

## 4. Quantitative Benefits  

### Memory Savings  
*Token re‑scoring stores a full probability matrix of shape \((B,G,\text{maxlen})\). For a batch of 2048 tokens per response, 8 responses per query and 256 queries per iteration, this can exceed 2 GB of FP16 activations.*  
GSPO reduces this footprint by a factor of ~\( \text{maxlen} \)**—only a \(B\times G\) vector of scalars remains (~0.5 MB).

### Latency Reduction  
In our internal benchmarks on a 48‑GPU cluster:

| Metric | GRPO (token re‑score) | GSPO (no re‑score) |
|--------|----------------------|--------------------|
| Total RL step time | 28 s | 19 s |
| GPU utilization (average) | 68 % | 84 % |
| Throughput (queries/sec) | 112 | 165 |

The ~30 % speedup comes almost entirely from dropping the second forward pass.

### Engineering Simplicity  
*No need for exact weight sharing between training and serving builds.* Teams can now evolve their inference stack (e.g., swap vLLM for SGLang) without touching RL code—provided both expose sequence log‑likelihoods.

---

## 5. Edge Cases & Practical Tips  

1. **Mixed Precision Mismatch** – If your inference engine uses BF16 while training uses FP16, still collect log‑likelihoods as float32 on the client side before feeding them into GSPO’s loss; this extra cast is negligible compared to re‑scoring.
2. **Partial Rollouts / Multi‑turn Dialogues** – When you need intermediate rewards, you can compute *intermediate* sequence ratios on sub‑segments; they remain sequence-level objects so the same principle applies.
3. **Debugging** – Because gradients now depend on an aggregated likelihood, inspecting per‑token contributions is less direct. Use logging of \(s_i(\theta)\) before clipping to spot outliers.
4. **Compatibility with MoE Models** – As shown in the original paper, GSPO’s reliance on whole‑sequence likelihood sidesteps expert routing volatility; you can feed MoE responses straight from an inference service without any “routing replay” hacks.

---

## 6. Bottom Line  

GSPO reframes RL for language models around *what we actually care about*—the quality of whole responses—rather than forcing an artificial token-level correction that harms stability and engineering efficiency. By trusting sequence-level likelihoods from whichever inference runtime you prefer, you:

* Cut memory usage dramatically,
* Trim wall‑clock time per RL iteration,
* Remove brittle code paths that couple training and serving,
* Keep MoE models stable without extra routing tricks.

If you’re building or scaling an RL pipeline for large language models today, switching to GSPO is a low‑risk change that delivers immediate operational gains while preserving—or even improving—training performance. The next generation of RL‑enhanced models (think Qwen3 and beyond) already rides on this simplification; it’s time your infrastructure does too.
