\title{Stack Exchange of the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

### What is the effect of mixing code tokens with math tokens in a single‑stage training versus a two‑stage training schedule?
Question:
Section 5.1 reports that a one‑stage mix of 400B code + 150B math tokens mitigates catastrophic forgetting and improves program‑aided reasoning, yet harms pure‑language math reasoning for the 7B model. I’m trying to understand:
1. How does the token mixing ratio (e.g., 73% code, 27% math) influence the model’s capacity to learn both domains?
2. Are there curriculum‑learning strategies (e.g., gradually increasing math proportion) that could avoid the degradation observed?
3. Does the model’s parameter count (1.3B vs 7B) change the optimal mixing strategy?
Insights on these trade‑offs would guide my own multi‑domain pre‑training experiments.
Answer:
**Answer**

The paper’s ablation experiments in §5.1 (Table 9 and the surrounding discussion) show that the way code and math tokens are combined during the continual‑pre‑training stage has a decisive impact on three abilities:

1. **program‑aided (tool‑use) reasoning**,  
2. **pure language‑only math reasoning**, and  
3. **the model’s coding skill that was learned in the first stage**.

Below I explain what the authors observed, why the mixing ratio matters, and how the phenomena depend on model size and on possible curriculum‑learning tricks.

---

### 1. Why the 73 % code / 27 % math mix works for a 7 B model

The authors compare three schedules for a 1.3 B‑parameter “base” model (the same trends hold for the 7 B model, which is simply a larger version of the same architecture).

| Training schedule | Tokens seen (≈) | Code % | Math % | Program‑aided score (GSM8K + PoT) | Pure‑math score (MATH CoT) | Coding score (HumanEval) |
|-------------------|----------------|--------|--------|-----------------------------------|---------------------------|--------------------------|
| two‑stage (400 B code → 150 B math) | 550 B | 73 | 27 | best among all setups | **best** (no degradation) | slight drop (catastrophic forgetting) |
| one‑stage (400 B code + 150 B math mixed) | 550 B | 73 | 27 | almost as good as two‑stage (catastrophic forgetting mitigated) | **worse** than two‑stage (≈ 2 % absolute drop) | coding retained (no forgetting) |
| math‑only (150 B math) | 150 B | 0 | 100 | poor program‑aided | very poor pure‑math | coding unchanged (since never seen) |

The key points are:

* **Catastrophic forgetting** – When the model finishes a long code‑only phase and then proceeds to a pure math phase, the weights that were useful for generating syntactically correct Python code degrade. Mixing the two types of tokens in a single stage keeps the model’s “code sub‑network’’ active, so the drop in coding performance is avoided.

* **Program‑aided reasoning** – Both the two‑stage and the mixed one‑stage schedule expose the model to a huge amount of code (≈ 400 B tokens). This teaches the transformer to produce well‑formed program fragments, and the subsequent math data teaches it to *use* those fragments as part of a solution. Consequently, the GSM8K + PoT scores are high in both cases.

* **Pure‑language math reasoning** – This ability is more sensitive to the *relative* proportion of math tokens. In the mixed schedule the model still spends three quarters of its updates on code, which leaves fewer optimisation steps for the patterns that are needed for chain‑of‑thought reasoning without any tool. The two‑stage schedule, by contrast, gives a dedicated 150 B‑token “pure‑math” phase where the model can focus on the subtle linguistic and symbolic structures that appear in MATH prompts. Hence the slight degradation (≈ 2 % absolute) observed for the mixed schedule.

In short, the **73 % code / 27 % math** ratio is a compromise: it is enough code to keep the programming head alive, but the math share is still substantial enough to give the model a strong foothold in both program‑aided and pure‑math tasks. The degradation you see on MATH is the cost of that compromise.

---

### 2. Could a curriculum (gradually increasing the math share) avoid the drop?

The authors do not report such an experiment, but the data give a clear hypothesis. The loss in pure‑math performance appears because the model is *continually* interleaved with code data, which prevents it from consolidating the long‑range dependencies needed for multi‑step reasoning. A curriculum that **starts with a high code proportion and slowly raises the math proportion** would let the model first stabilise its coding head and then devote increasingly more capacity to the math head.

A practical schedule could look like:

```
phase 1: 400 B tokens, 90 % code / 10 % math
phase 2: 200 B tokens, 70 % code / 30 % math
phase 3: 150 B tokens, 50 % code / 50 % math
```

By the end of phase 3 the overall mix is still roughly 73/27 (the same total token budget as the paper) but the *trajectory* gives the model time to re‑align its internal representations toward math. This is precisely the “curriculum‑learning” intuition that the paper mentions in §5.1 (“gradually increasing the math proportion may be worth exploring”).  

Empirically, such a schedule would likely **reduce the pure‑math degradation while preserving the coding and program‑aided gains**, because the later phases still provide enough code tokens to keep the programming skills alive. However, the benefit would have to be confirmed experimentally; the paper’s authors leave this as a future direction.

---

### 3. Does model size change the optimal mixing strategy?

The paper reports the same qualitative pattern for both the 1.3 B and the 7 B models (see Table 9). For the larger 7 B model the *absolute* drop in MATH when using the mixed schedule is slightly smaller (≈ 1.5 % vs ≈ 2 % for the 1.3 B model). This suggests that **capacity helps**: a bigger model can store both coding and math knowledge more simultaneously, so the interference is weaker.  

Consequently:

* **Small models (≤ 2 B)** – They benefit most from a **two‑stage** schedule or a curriculum that gives a relatively long pure‑math phase, because they cannot hold both domains at once.

* **Mid‑size models (≈ 7 B)** – A **single‑stage mixed** schedule already works well; a modest curriculum may still improve the pure‑math side without sacrificing code.

* **Very large models (≥ 30 B)** – The paper does not test these, but based on the trend we can expect the optimal ratio to shift toward **more code** (perhaps 80 % code, 20 % math) because the larger capacity can absorb the extra code without hurting math reasoning. At that scale, the code head may even act as a regulariser for mathematical reasoning, as observed in the paper’s “code‑training benefits mathematical reasoning” discussion.

In practice, one should tune the ratio empirically for the target parameter count, but the guiding principle is: **the smaller the model, the larger the relative math proportion needed to avoid pure‑math degradation**.

---

### Take‑away for your own multi‑domain pre‑training

1. **Start from a code‑oriented checkpoint** (as the authors do) if you plan to support program‑aided reasoning.  
2. **Allocate at least 70 % of the mixed‑domain tokens to code** when the overall token budget is on the order of a few hundred billion; this keeps the coding ability from forgetting.  
3. **If pure‑language math is a priority, insert a dedicated pure‑math phase** (or a gradual curriculum that raises the math share) after the initial code‑heavy phase.  
4. **Scale‑adjust the ratio**: smaller models need a higher math fraction; larger models can tolerate a more code‑heavy mix.  

Following these guidelines should let you reap the benefits of both domains while limiting the trade‑off observed in the paper.
