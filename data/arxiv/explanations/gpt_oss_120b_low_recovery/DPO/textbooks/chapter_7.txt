\title{A Textbook about the Paper: "Direct Preference Optimization: Your Language Model is Secretly a Reward Model"}

Chapter 7: **Implementation Details**

In this chapter we describe, in a step‑by‑step fashion, the practical ingredients required to reproduce the Direct Preference Optimization (DPO) experiments presented in the paper *Direct Preference Optimization: Your Language Model is Secretly a Reward Model*.  The goal is to provide a reproducible pipeline that a graduate student can follow to train a language model directly from human preference triples without invoking reinforcement‑learning algorithms.  All the design choices below are drawn from the original work; no external information has been added.

---

## Data Formats for Preference Triples

The core training signal for DPO consists of a collection  

\[
\mathcal{D}= \bigl\{(x^{(i)},y^{(i)}_{\!w},y^{(i)}_{\!l})\bigr\}_{i=1}^{N},
\]

where each entry contains a prompt \(x\) and two completions: a **preferred** response \(y_{w}\) and a **dispreferred** response \(y_{l}\).  In the original experiments the triples are stored as plain‑text JSON lines, one object per line:

```json
{
  "prompt": "Explain why the sky is blue.",
  "chosen": "The sky appears blue because ...",
  "rejected": "I think the sky is green ..."
}
```

The ordering of the fields is irrelevant as long as the keys are consistently named.  When loading the dataset the implementation must:

1. Tokenize the three strings using the same tokenizer that will be employed for the language model (see the next section).  
2. Pad or truncate each token sequence to a maximum length \(L\) (the same value used for the underlying LM).  
3. Convert the token IDs into tensors of shape \((B, L)\) where \(B\) is the batch size.

If a dataset already provides a *single* preferred completion per prompt (as in many instruction‑tuning corpora), a synthetic dispreferred response can be generated by sampling from the reference policy \(\pi_{\text{ref}}\) or by applying a perturbation such as *unlikelihood* dropout; this mirrors the data‑generation step described in the paper.

---

## Tokenizer and Model Architecture Choices

All experiments use a decoder‑only transformer architecture identical to the one employed for the supervised‑fine‑tuned (SFT) model.  Concretely:

- **Tokenizer**: A Byte‑Pair Encoding (BPE) tokenizer with a vocabulary size of either 50 k (GPT‑2 style) or 32 k (LLaMA style), depending on the base model.  The tokenizer must be deterministic; the same tokenizer instance is used to encode both prompts and completions, ensuring that the log‑probability ratios \(\log \frac{\pi_{\theta}(y\mid x)}{\pi_{\text{ref}}(y\mid x)}\) are computed over identical token sequences.

- **Model**: A causal language model with stacked self‑attention layers, layer‑norm, and a final linear projection to the vocabulary dimension.  The paper reports experiments with models ranging from 0.8 B to 6 B parameters.  The architecture is otherwise unchanged when moving from the SFT checkpoint to the DPO fine‑tuning stage; the SFT checkpoint is simply loaded as the initial weights for \(\pi_{\theta}\).

Because DPO does not modify the model’s output distribution beyond adjusting the logits through fine‑tuning, any architecture that supports standard cross‑entropy training can be employed, provided the reference policy \(\pi_{\text{ref}}\) is obtainable (e.g., by keeping a frozen copy of the SFT checkpoint).

---

## Computing the Log‑Ratio Term Efficiently

The DPO loss (Equation (9) in the paper) requires the quantity

\[
\Delta_{\theta}(x,y) \;=\; \beta \,\log\!\frac{\pi_{\theta}(y\mid x)}{\pi_{\text{ref}}(y\mid x)}.
\]

Both numerator and denominator are log‑probabilities of the *same* token sequence under two models that share the same architecture but have different parameters.  Computing \(\Delta_{\theta}\) efficiently follows these steps:

1. **Forward Pass for Both Models**  
   - Feed the tokenized pair \((x, y)\) through the *reference* model \(\pi_{\text{ref}}\).  Collect the per‑token log‑softmax scores \(\log p_{\text{ref}}(t_{k}\mid x, t_{<k})\).  
   - Perform the same forward pass with the *trainable* model \(\pi_{\theta}\) to obtain \(\log p_{\theta}(t_{k}\mid x, t_{<k})\).

2. **Sequence Log‑Probability**  
   Sum the per‑token log‑probabilities for each sequence:
   \[
   \log\pi_{\theta}(y\mid x)=\sum_{k=1}^{|y|}\log p_{\theta}(t_{k}\mid x, t_{<k}),
   \qquad
   \log\pi_{\text{ref}}(y\mid x)=\sum_{k=1}^{|y|}\log p_{\text{ref}}(t_{k}\mid x, t_{<k}).
   \]

3. **Log‑Ratio**  
   Subtract the two sums and multiply by \(\beta\):
   \[
   \Delta_{\theta}(x,y) = \beta\Bigl(\log\pi_{\theta}(y\mid x)-\log\pi_{\text{ref}}(y\mid x)\Bigr).
   \]

Because the two forward passes are independent, they can be vectorized across the batch dimension.  In practice the implementation stores the hidden states of the reference model once (it is frozen) and re‑uses them for each batch, which reduces the memory footprint compared to recomputing the reference logits for every gradient step.

## Batching, Gradient Clipping, and Optimizer Settings

### Batching
The loss operates on *preference pairs* \((y_{w}, y_{l})\) for each prompt.  A typical batch contains \(B\) such triples, giving tensors of shape \((B, L)\) for the prompts, the preferred completions, and the dispreferred completions.  The DPO loss for the batch is:

\[
\mathcal{L}_{\text{DPO}} = -\frac{1}{B}\sum_{i=1}^{B}\log\sigma\!\bigl(\Delta_{\theta}(x^{(i)},y^{(i)}_{w}) - \Delta_{\theta}(x^{(i)},y^{(i)}_{l})\bigr),
\]

where \(\sigma\) denotes the logistic sigmoid.

### Gradient Clipping
To avoid exploding gradients that can arise from large log‑ratio magnitudes, the paper applies global norm clipping with a threshold of 1.0.  The procedure is:

```python
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
```

Clipping is performed after the backward pass and before the optimizer step.

### Optimizer
The experiments use the AdamW optimizer with standard hyper‑parameters:
- Learning rate \( \eta \) (see the hyper‑parameter section below).  
- Weight decay \( \lambda = 0.01 \).  
- Betas \( (\beta_{1},\beta_{2}) = (0.9, 0.999) \).  

A linear learning‑rate warm‑up over the first 10 % of training steps is employed, followed by a cosine decay to zero.  The total number of training steps varies with model size (e.g., 10 k steps for the 1.4 B model, 20 k steps for the 6 B model) but the schedule is always defined in terms of *updates*, not epochs, because the dataset is usually reused several times.

---

## Hyper‑Parameter Selection (β, Learning Rate, Temperature)

### β (KL‑constraint coefficient)
The scalar \(\beta\) governs the strength of the KL‐penalty implicit in the log‑ratio term.  The paper experiments with \(\beta \in \{0.05, 0.1, 1.0, 5.0\}\).  Smaller values prioritize staying close to the reference policy, yielding more conservative updates; larger values allow the model to push the preference probability farther toward 1 at the cost of higher KL divergence.  In practice one can sweep a small grid and select the value that offers the best trade‑off on a validation set of preference triples.

### Learning Rate
A base learning rate of \(2\times10^{-5}\) works robustly for models up to 6 B parameters when fine‑tuning with AdamW.  For smaller models (≤ 1 B) the paper reports stable training with \(1\times10^{-5}\).  The learning‑rate schedule described above (warm‑up + cosine decay) is used for all settings.

### Generation Temperature at Evaluation
Although DPO training does not involve sampling, evaluation of the resulting policy requires a decoding temperature \(\tau\).  The experiments report performance across a range of temperatures (0.0, 0.25, 0.5, 1.0).  Lower temperatures tend to produce higher‑reward, lower‑KL outputs; higher temperatures increase diversity but can lower the win‑rate against a reference.  Selecting \(\tau\) is therefore a post‑training hyper‑parameter that can be tuned on a held‑out validation set.

## Handling Large Vocabularies and Memory Considerations

When scaling to models with vocabularies larger than 50 k (e.g., the 32 k LLaMA tokenizer or multilingual tokenizers), two practical issues arise:

1. **Memory for Dual Forward Passes**  
   Storing logits for both \(\pi_{\theta}\) and \(\pi_{\text{ref}}\) may exceed GPU memory.  The paper mitigates this by:
   - Computing the reference log‑probabilities *once* per epoch and caching them on CPU (or NVMe) in fp16 format.  
   - Streaming the cached reference scores during each batch, thus only the trainable model’s activations occupy GPU memory.

2. **Avoiding Full‑Vocabulary Softmax**  
   The loss only requires the log‑probability of the *observed* tokens, not the full probability distribution.  Therefore the implementation can replace the standard `CrossEntropyLoss` with a manual gather operation:

   ```python
   # logits: (B, L, V); target_ids: (B, L)
   log_probs = torch.log_softmax(logits, dim=-1)
   token_log_probs = log_probs.gather(2, target_ids.unsqueeze(-1)).squeeze(-1)
   seq_log_prob = token_log_probs.sum(dim=-1)   # shape (B,)
   ```

   This reduces the temporary memory footprint because the full softmax is never materialized as a dense matrix.

3. **Gradient Checkpointing**  
   For the largest models (≥ 6 B parameters) the paper enables activation checkpointing, recomputing intermediate activations during the backward pass.  This trades compute for a roughly 50 % reduction in peak memory, allowing a batch size of 8 on a single 48 GB GPU.

### Summary of the Reproducible Pipeline

1. **Prepare** a JSON‑lines file of preference triples and tokenize all three fields with the model’s BPE tokenizer.  
2. **Load** the SFT checkpoint as both the trainable model \(\pi_{\theta}\) and a frozen copy \(\pi_{\text{ref}}\).  
3. **Construct** batches of size \(B\), compute per‑token log‑probabilities for preferred and dispreferred completions under both models, and evaluate the DPO loss (Equation 9).  
4. **Back‑propagate** using AdamW, applying global norm clipping (1.0) and the learning‑rate schedule (warm‑up + cosine decay).  
5. **Tune** \(\beta\) and the learning rate on a validation preference set; after training, select a decoding temperature \(\tau\) that maximizes the desired reward–KL trade‑off.  
6. **Evaluate** the final policy by measuring win‑rates against a reference (or using a proxy reward model) and by reporting the average KL divergence \(\mathbb{D}_{\text{KL}}[\pi_{\theta}\,\|\,\pi_{\text{ref}}]\).

By following these concrete steps—respecting the data format, tokenizer consistency, efficient log‑ratio computation, and the optimizer configuration described above—a researcher can faithfully reproduce the DPO experiments and extend them to new preference datasets or larger language models.
