# Training the Guanaco Chatbot Family: From 7B to 65B with One GPU  

In the last few months “large language model (LLM) finetuning” has become a buzz‑worthy headline, but the reality is that training a 65 billion‑parameter chatbot still feels like a supercomputer‑only sport. The recent **QLoRA** paper shatters that myth by showing how a single 48 GB GPU can finetune a 65 B LLaMA model without losing any of the performance you’d expect from a full 16‑bit run. In this post we walk through the practical workflow the authors used to create the **Guanaco** family of chatbots (7 B, 13 B, 33 B, and 65 B). We’ll cover:

* Why QLoRA makes 4‑bit finetuning possible.  
* Which instruction datasets work best and how to pick one for your hardware.  
* The hyperparameters that actually matter (and those you can ignore).  
* Approximate training time on consumer vs. professional GPUs.  
* Tips for reproducing the results on your own machine.

Everything below is grounded in the original QLoRA paper—no speculation, just what the experiments actually did.

---

## 1️⃣ The core idea: finetune through a frozen, 4‑bit model  

Traditional finetuning stores the entire model in **bfloat16** (or float16) during training. A 65 B LLaMA would need **> 780 GB** of GPU memory—clearly impossible on a single card. QLoRA sidesteps this by:

1. **Quantizing the pretrained weights to 4‑bit NormalFloat (NF4).** NF4 is an information‑theoretically optimal quantizer for normally‑distributed weights, which most LLM layers resemble.  
2. **Adding LoRA adapters** (low‑rank matrices) to every linear layer. The base weights stay frozen; only the adapters get updated.  
3. **Back‑propagating through the quantized weights** (the dequantization step is done on‑the‑fly, turning NF4 back into bfloat16 for matrix multiplies).  

Because gradients are never computed for the frozen base, memory is dominated by activations and LoRA parameters—both fit comfortably in < 48 GB even for the largest model.

Additional tricks keep the footprint low:

| Trick | What it solves | Memory saved |
|------|----------------|--------------|
| **Double Quantization** | Quantizes the per‑block scaling constants (the “c” values) from fp32 → fp8 | ≈ 0.37 bits per parameter (≈ 3 GB for a 65 B model) |
| **Paged Optimizers** | Uses NVIDIA unified memory for optimizer states; they spill to CPU when GPU runs out of RAM | Prevents OOM spikes during gradient checkpointing |
| **Blocksize = 64** for weights + **blocksize = 256** for scale constants | Balances quantization precision vs. overhead | – |

The net result: a **4‑bit + LoRA** checkpoint that occupies roughly **5 GB** on disk for a 7 B model and **≈ 20–25 GB** for a 33/65 B model.

## 2️⃣ Choosing an instruction dataset  

The authors trained *more than a thousand* models across eight publicly available instruction collections:

| Dataset | Size (samples) | Main source | License |
|--------|----------------|-------------|---------|
| OASST1 | ~9 k | Crowd‑sourced multi‑turn dialogs (OpenAssistant) | CC‑BY‑SA |
| HH‑RLHF | ~70 k | Human feedback from Anthropic’s HH dataset | CC0 |
| Alpaca | ~52 k | Synthetic instruction/response pairs distilled from OpenAI GPT‑3.5 | MIT |
| Self‑Instruct | ~82 k | Model‑generated instructions from GPT‑3+ | MIT |
| UnnaturalInstructions | ~149 k | Curated “unusual” tasks from PromptSource | Apache 2 |
| FLAN v2 | ~450 k (subsampled) | Mixture of crowdsourced + synthetic tasks | Apache 2 |
| Chip2 | ~226 k | Large-scale collected prompts from LAION web crawl | CC0 |
| Longform | ~9 k (multi‑turn) | Long answer generation data from Reddit/StackExchange | MIT |

### What actually mattered?  

* **Data quality trumps sheer size.** The small OASST1 (~9k examples) outperformed FLAN v2’s much larger subsample on Vicuna chatbot benchmarks, despite both being “instruction” datasets.  
* **Multiturn data helps chat capability.** OASST1 contains real conversational histories; models trained on it learned better turn‑taking and refusal behaviours than those trained only on single‑turn prompts.

> **Practical tip:** If you have limited compute, start with OASST1 or a similarly high‑quality multiturn set. You don’t need >100k samples to hit near‑state‑of‑the‑art performance.

## 3️⃣ Hyperparameters that really count  

Finetuning with LoRA introduces several knobs: rank *r*, scaling factor *s*, learning rate, batch size, number of epochs, which layers get adapters, etc. The QLoRA study found:

| Hyperparameter | Effect on performance |
|----------------|-----------------------|
| **Adapter placement** – LoRA on *all* linear layers (query, key, value, feed‑forward) is essential for matching full finetuning performance. Applying adapters only to attention queries/values hurts accuracy noticeably. |
| **Rank *r*** – Varying *r* between 8 and 64 had negligible impact once adapters were present everywhere; default *r* = 64 works well across scales. |
| **Learning rate** – For larger models halve the LR used for 7 B (e.g., 2e–5 → 1e–5).|
| **Batch size** – Double batch size when moving from 33 B to 65 B (e.g., B=8 → B=16) to keep gradient noise stable.|
| **Epochs** – One epoch over OASST1 (~9k samples) already yields >99% of ChatGPT performance; additional epochs give diminishing returns while increasing training time linearly.|

### The “default LoRA isn’t enough” story  

Early experiments with the standard LoRA defaults (adapters only on Q/K/V matrices, *r* = 8) fell short of full finetuning baselines—especially at >7 B scale. By simply adding adapters to every transformer block layer the gap vanished.

> **Practical tip:** In your `bitsandbytes` implementation set `target_modules="all_linear"` so every linear projection gets a LoRA pair.

## 4️⃣ Training time estimates  

All models were trained with:

* Optimizer: AdamW (paged version)  
* Learning rate schedule: cosine decay with warmup → total steps ≈ number of tokens in dataset × epochs  
* Sequence length: 512 tokens (standard for instruction tuning)

### Rough wall‑clock times

| Model size | GPU used (VRAM) | Epochs over OASST1 | Approx. wall time |
|-----------|------------------|-------------------|-------------------|
| **7 B**   | RTX 4090 (24 GB) | 1                | ~12 h |
| **13 B**  | RTX 4090 (24 GB) + paging (optimizes optimizer states) | 1                | ~14–16 h |
| **33 B**  | RTX A6000 (48 GB) + paged optimizer   | 1                | ~20–22 h |
| **65 B**  | RTX A6000 (48 GB) + paged optimizer   |\~1               |\~24 h |

The authors note that training time scales roughly linearly with model size because activation memory dominates and is already near the GPU limit in all cases.

> **Practical tip:** If you only have a consumer GPU (24 GB), you can still train the full Guanaco 7B in half a day; switch to a professional card (48 GB) for any model up to 65 B.

## 5️⃣ Step‑by‑step reproducible workflow  

Below is a condensed recipe that reproduces Guanaco’s results using HuggingFace Transformers + bitsandbytes.

```bash
# -------------------------------------------------
# 1️⃣ Install required libs
# -------------------------------------------------
pip install torch==2.* transformers==4.* bitsandbytes==0.* \
            accelerate==0.* einops sentencepiece

# -------------------------------------------------
# 2️⃣ Download pretrained LLaMA checkpoint
# -------------------------------------------------
# Example for LLaMA-33B
git clone https://huggingface.co/meta-llama/Llama-2-33b-hf llama-33b
cd llama-33b
# Convert weights to NF4 using bitsandbytes' quantize script
python -m bitsandbytes.quantize \
     --model_dir . \
     --output_dir ./nf4 \
     --dtype nf4 \
     --block_size 64
```

```bash
# -------------------------------------------------
# 3️⃣ Prepare LoRA adapters via QLoRA config
# -------------------------------------------------
cat > qlora_config.json <<EOF
{
  "model_name_or_path": "./nf4",
  "adapter_name": "guanaco_33b_oasst1",
  "task_type": "CAUSAL_LM",
  "r": 64,
  "lora_alpha": 16,
 "target_modules": "all_linear",
 "lora_dropout": 0.05,
 "train_batch_size": 16,
 "max_seq_length": 512,
 "learning_rate": 1e-5,
 "num_train_epochs": 1,
 "fp16": false,
 "bf16": true,
 "optim": "paged_adamw_32bit",
 "gradient_checkpointing": true,
 "double_quantization": true,
 "quant_type": "nf4"
}
EOF
```

```bash
# -------------------------------------------------
# 4️⃣ Run training with Accelerate
# -------------------------------------------------
accelerate launch \
   --config_file ./accelerate_config.yml \
   scripts/run_clm.py \
   --config_file qlora_config.json \
   --dataset_name openassistant/oasst1 \
   --max_steps_per_epoch <calc_tokens/512>
```

The `accelerate_config.yml` should request `gpu_ids: [0]` and set `mixed_precision: no` because QLoRA already handles bfloat16 computation internally.

### Key flags explained

* `optim: paged_adamw_32bit` → activates Paged Optimizers that spill optimizer states to CPU when needed.
* `double_quantization: true` → stores per‑block scales as fp8.
* `quant_type: nf4` → selects NormalFloat4.
* `gradient_checkpointing: true` → reduces activation memory at modest speed cost.
* `target_modules: all_linear` → places LoRA adapters on *every* linear layer.

## 6️⃣ Evaluating your Guanaco replica  

The paper used two complementary evaluation pipelines:

1. **Automated GPT‑4 scoring:** For each prompt they provided GPT‑4 with both ChatGPT’s response and their model’s response; GPT‑4 gave a relative score out of ten.
2. **Human Elo tournament:** Pairwise comparisons on Vicuna‐style prompts and on OpenAssistant validation queries fed into an Elo rating system (`K=32`, start rating =1000).

Both methods agreed on overall rankings (`τ≈0.43`, `ρ≈0.55`) but differed at individual prompts—so it’s recommended to run both if you can afford human annotators.

For quick sanity checks you can reuse their open‐source evaluation script:

```bash
python eval/elo_tournament.py \
   --models ./guanaco_7b ./guanaco_33b ./guanaco_65b \
   --datasets vicuna oa \
   --policy gpt4 # or 'human' if you have annotators
```

You should see results within a few points of Table 5 in the paper (`guanaco_65b ≈99%` of ChatGPT on Vicuna).

## 7️⃣ Common pitfalls & troubleshooting  

| Symptom                              | Likely cause                               | Fix |
|--------------------------------------|--------------------------------------------|-----|
| OOM even though GPU shows <48 GB free after loading NF4 checkpoint.| Paged optimizer not activated (`optim` flag wrong).| Use `"optim":"paged_adamw_32bit"` and ensure bitsandbytes ≥0.41 which ships paged kernels.|
| Training stalls at step 0 after launching Accelerate.| Missing `--bf16` flag while running on older GPUs without bfloat16 support.| Switch to `"bf16": false, "fp16": true` if your GPU only supports fp16, or upgrade driver/CUDA version.|
| Final loss diverges dramatically after epoch 1.| Learning rate too high for larger models.| Halve LR when moving from ≤13 B → ≥33 B models (`lr=2e-5 → lr=1e-5`).|
| Model outputs blank or “I’m sorry…” refusals on trivial prompts.| LoRA adapters not loaded correctly at inference (`peft` not applied).| Run inference via `peft.PeftModel.from_pretrained(base_model_path, adapter_name="guanaco_...")`.|

## 🔚 Takeaways  

* **QLoRA makes true full‑scale instruction tuning accessible:** A single RTX A6000 can take a frozen LLaMA‐65B, quantize it to NF4, attach LoRA everywhere, and produce a chatbot that reaches **99% of ChatGPT’s Vicuna score in just one day**.
* **Dataset matters more than size:** High‑quality multiturn data like OASST1 beats massive but generic instruction collections.
* **Adapter coverage is critical:** When you enable LoRA on all linear layers you recover exactly the same performance as a conventional bfloat16 finetune.
* **Memory tricks are reusable:** Double quantization and paged optimizers are generic enough to be added to any PEFT pipeline—consider them baseline tools now.

The code is open source (`github.com/artidoro/qlora`) along with ready–made adapters for each Guanaco size, so you can start experimenting today without waiting weeks for cloud resources.

Happy finetuning! 🚀
