\title{A Textbook about the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

Chapter 9: # Instruction Finetuning with QLoRA: The Guanaco Models  

In this chapter we describe how the **Guanaco** family of instruction‑following language models was built using the **QLoRA** finetuning framework.  We begin by surveying the eight publicly available instruction‑following corpora that were selected for experimentation, then detail the processing steps required to turn heterogeneous sources—single‑turn instructions, multi‑turn dialogues, and mixture datasets—into a unified training set.  Next we present the full training recipe, including the loss function, number of epochs, learning‑rate scaling rules, and batch‑size choices that make it possible to finetune models ranging from 7 B to 65 B parameters on a single GPU.  We then discuss **adapter placement**, i.e. why LoRA adapters were inserted at *every* linear layer of the base transformer, and how this design choice enables QLoRA to recover full‑precision performance.  Finally we summarize the released model zoo, enumerating the checkpoints for each model scale and the corresponding dataset configurations.  

Throughout the chapter we stay faithful to the methodology and results reported in the QLoRA paper, and we explicitly avoid introducing concepts that are not present in the original work.  

---  

## Overview of the Eight Instruction‑Following Datasets  

The QLoRA study performed a systematic comparison of instruction finetuning across a broad spectrum of data sources.  The eight corpora span four main acquisition strategies:

1. **Crowd‑sourced multi‑turn dialogues** –  
   *OASST1* (Open‑Assistant “ShareGPT‑style” dataset) and *HH‑RLHF* (Anthropic‑style Human‑Human Reinforcement Learning from Human Feedback).  These collections consist of conversational turns written by volunteers, and they contain explicit instruction–response pairs as well as deeper multi‑turn exchanges that simulate real‑world chat interactions.  

2. **Distillation from instruction‑tuned models** –  
   *Alpaca* (synthetic instructions generated by querying OpenAI’s text‑davinci‑003 model), *Self‑Instruct* (self‑generated instruction–response pairs via prompting a base LLM to create new tasks), and *Unnatural‑Instructions* (a curated set of “unnatural” prompts derived from GPT‑3 outputs).  All three are single‑turn datasets in which each example is a prompt followed by a single best response.  

3. **Large aggregated corpora** –  
   *FLAN‑v2* aggregates a massive collection of instruction‑following data spanning many existing benchmarks (e.g., SuperNaturalInstructions, T0).  The dataset contains hundreds of thousands of examples and is designed to be *massively multitask*; it is frequently used as a “generic” instruction finetuning source.  

4. **Hybrid datasets** –  
   *Chip2* (the LAION‑derived “open‑source” instruction mixture) and *Longform* (a collection of long‑form instruction–response pairs focused on generating extended prose).  These datasets mix both crowd‑sourced and model‑generated content and contain a wide variety of task types, from code generation to creative writing.  

Each dataset differs along three axes that are relevant for instruction finetuning: **size**, **language coverage**, and **license**.  For example, OASST1 contains ~9 k high‑quality, multilingual dialogues and is released under a permissive CC‑BY‑4.0 license, whereas FLAN‑v2 provides up to 450 k examples but is constructed from a mixture of sources with varying attribution requirements.  The diversity of these corpora allowed the authors to investigate the relative importance of *data quality* versus *data quantity* when training large language models with QLoRA.

## Data Preprocessing and Split Strategy for Multi‑Turn Dialogs  

Because the eight datasets were not originally in a common format, the authors performed a careful preprocessing pipeline before feeding the data to QLoRA.  The pipeline can be broken down into several stages:

### 1. Normalization of Prompt–Response Structure  
All examples were converted to a *canonical* format consisting of a single **instruction** string followed by a **response** string.  For datasets that already provide this structure (e.g., Alpaca, Self‑Instruct), the conversion is a simple copy.  For multi‑turn dialogues (OASST1, HH‑RLHF) the pipeline first extracts the *most recent* user message as the instruction and aggregates the *assistant* replies up to that point as the response.  When a conversation branch contains multiple possible assistant continuations, the authors kept only the **top response** based on a deterministic ranking (e.g., the first child in the conversation tree).  

### 2. Token‑Level Cleaning  
The text was stripped of any control characters, duplicated whitespace, and HTML escape sequences.  Unicode normalisation (NFKC) was applied to ensure consistent handling of accented characters across languages.  For code‑related examples, language tags (e.g., “```python”) were preserved because they provide useful context for the model.  

### 3. Language Filtering (Optional)  
Because OASST1 is multilingual, a language‑identification step based on fastText scores was used to retain only examples written in the target language(s) for a given experiment.  In the main QLoRA experiments the authors kept all languages, thereby allowing the model to benefit from multilingual signals.  

### 4. Train/Validation/Test Splits  
Each dataset was split **chronologically** where possible, to avoid leakage of future examples into the training set.  For OASST1, the authors used the official validation split (≈ 1 k dialogues) as a held‑out test set for both human and GPT‑4 evaluation.  For the other corpora, a random 5 % holdout was taken as validation, and the remaining 95 % served as training data.  All splits were stratified by the original source (e.g., ensuring that both “instruction” and “code” categories appear proportionally in each split).  

### 5. Sharding for Efficient Loading  
To accommodate the large token counts of the 33 B and 65 B models without exhausting GPU memory, the preprocessed dataset was stored as **sharded TFRecord files**.  Each shard contains a few thousand examples and is lazily loaded by the training loop, enabling *on‑the‑fly* batch construction while keeping the overall dataset footprint low enough to fit on a single machine’s SSD.

## Training Recipe: Loss, Epochs, Learning‑Rate Scaling, and Batch Size  

The QLoRA finetuning procedure adheres to a minimalist yet carefully tuned recipe.  The core components are enumerated below.  

### 1. Loss Function  

All experiments used the **standard cross‑entropy loss** (also called the negative log‑likelihood loss) on the tokenized response sequence.  The loss is applied *only* to the assistant’s output; for datasets that contain both instruction and response tokens (e.g., OASST1 dialogues) the instruction portion is *masked* so that no gradient is back‑propagated through it.  This aligns with the supervised‑learning paradigm adopted throughout the paper and deliberately avoids any reinforcement‑learning‑from‑human‑feedback (RLHF) stage.  

### 2. Number of Epochs  

Because the QLoRA approach dramatically reduces the per‑epoch memory cost, the authors were able to **train for a small number of epochs** (typically 1–3).  Empirically, a single epoch over OASST1 already yields a substantial gain over the base model, and additional epochs provide diminishing returns.  For the larger FLAN‑v2 dataset, the authors capped training at **two epochs** to avoid over‑fitting given the larger size of the data.  

### 3. Learning‑Rate Scaling  

A base learning rate of **\(1\times10^{-4}\)** (in BF16) was used for the 7 B model.  To maintain stable optimisation when scaling to larger parameter counts, the authors **halved** the learning rate for the 33 B and 65 B models, i.e., **\(5\times10^{-5}\)**.  This simple linear scaling rule (learning rate ∝ \(1/\sqrt{\text{model size}}\)) was sufficient; more aggressive schedules (e.g., cosine decay) did not produce noticeable gains in the preliminary hyper‑parameter sweeps.  

### 4. Batch Size per Model Scale  

The batch size was chosen to maximise GPU utilisation while staying within the **< 48 GB** memory budget imposed by QLoRA’s 4‑bit storage.  The settings were:  

| Model Size | Batch Size (examples) | Gradient Accumulation Steps |
|------------|----------------------|-----------------------------|
| 7 B       | 128                  | 1                           |
| 13 B      | 64                   | 1                           |
| 33 B      | 32                   | 2 (effective batch = 64)    |
| 65 B      | 16                   | 4 (effective batch = 64)    |

The **gradient‑accumulation** factor compensates for the reduced per‑step batch size of the largest models, yielding a comparable *effective* batch size across scales.  All batch sizes were measured in *prompt‑response* pairs; the actual token count per batch varies with sequence length, but QLoRA’s *paged optimizer* automatically handles occasional spikes caused by very long dialogues.  

### 5. Optimiser and Scheduler  

QLoRA employs the **AdamW** optimiser with weight decay set to **0.01** and β‑parameters (0.9, 0.999).  The optimiser states (first‑ and second‑moment buffers) are stored using the **paged‑optimiser** mechanism, which places them in NVIDIA Unified Memory, automatically paging them to CPU RAM when the GPU memory budget is exceeded.  This design eliminates the need for manual gradient checkpointing while preserving the training speed; empirical measurements show *no* noticeable slowdown for the 65 B model on a 48 GB GPU when using a batch size of 16.

## Adapter Placement: LoRA at Every Linear Layer  

The original LoRA formulation (Hu *et al.*, 2021) proposes inserting low‑rank adapters into a *subset* of the transformer’s projection matrices (often only the query and value matrices of the attention heads).  In the QLoRA experiments, the authors discovered that such a sparse placement **fails to recover the full‑precision performance** of a 16‑bit finetuned baseline, especially for the larger LLaMA models.  

### 1. Motivation for Full‑Layer LoRA  

When the base model is stored in a **4‑bit NormalFloat (NF4)** format, the quantisation noise is *uniformly* distributed across all weight tensors.  If adapters are added only to a few layers, the other layers remain completely frozen, making it impossible for the optimizer to compensate for the quantisation errors that propagate through the network.  By contrast, **adding LoRA adapters to *every* linear transformation** (i.e., the feed‑forward dense layers, the projection matrices of all attention heads, and the final language‑model head) gives the model a *dense* set of trainable parameters that can adapt the entire computational graph to the downstream instruction task.  

### 2. LoRA Parameterisation  

For each linear layer with weight matrix \(\mathbf{W}\in\mathbb{R}^{h\times o}\), QLoRA adds a rank‑\(r\) decomposition \(\mathbf{L}_1\in\mathbb{R}^{h\times r}\) and \(\mathbf{L}_2\in\mathbb{R}^{r\times o}\) according to  

\[
\mathbf{Y}= \mathbf{X}\mathbf{W} \;+\; s \,\mathbf{X}\mathbf{L}_1\mathbf{L}_2,
\]

where \(s\) is the scaling factor (default \(s=1\) in the paper).  The **rank \(r\)** was set to **64** for all layers, yielding a total LoRA parameter count of roughly **0.2 %** of the full model size—a negligible memory overhead relative to the 4‑bit base.  

### 3. Effect on Memory and Performance  

Because the LoRA parameters are stored in **full‑precision BF16** (the same datatype used for computation), the additional memory cost is modest: for a 65 B model the LoRA weights occupy **≈ 130 MB**, far less than the **≈ 5 GB** consumed by the NF4‑quantised base model.  Moreover, the **gradient footprint** of the adapters dominates the overall training memory, not the LoRA weights themselves, as shown in the background analysis of the paper.  Consequently, **adding adapters at every layer does not materially increase the GPU memory budget**, yet it dramatically improves final performance.  

Empirically, the authors report that the **full‑layer LoRA configuration** matches the 16‑bit full‑finetuning results on both GLUE (for RoBERTa) and Super‑NaturalInstructions (for T5), as well as on the 5‑shot MMLU benchmark for LLaMA models up to 65 B parameters.  This demonstrates that the combination of 4‑bit NF4 quantisation, double quantisation of scaling constants, and adapters everywhere yields a finetuning process that is *information‑theoretically optimal* for the given precision budget.

## Model Zoo Summary: Checkpoints for 7 B, 13 B, 33 B, and 65 B  

The QLoRA study released a collection of **32 checkpoints**, covering four model scales and eight instruction‑following datasets.  Each checkpoint is a **LoRA adapter** that can be merged on‑the‑fly with the corresponding NF4‑quantised LLaMA base model.  Users can load the base model from the public LLaMA repository and then apply the downloaded adapter using the `peft` library, which automatically handles the de‑quantisation and computation in BF16.  

### 1. Model‑Scale Matrix  

| Scale | Parameters | Base Model (quantised) | NF4 + Double‑Quantised Size | Typical Training Time (GPU = 48 GB) |
|-------|------------|------------------------|----------------------------|------------------------------------|
| 7 B   | 7 B        | LLaMA‑7B (NF4)         | ≈ 5 GB (weights) + 130 MB (LoRA) | ≈ 12 h (single 48 GB GPU) |
| 13 B  | 13 B       | LLaMA‑13B (NF4)        | ≈ 9 GB (weights) + 250 MB (LoRA) | ≈ 18 h |
| 33 B  | 33 B       | LLaMA‑33B (NF4)        | ≈ 21 GB (weights) + 500 MB (LoRA) | ≈ 24 h |
| 65 B  | 65 B       | LLaMA‑65B (NF4)        | ≈ 44 GB (weights) + 1 GB (LoRA)   | ≈ 24 h (single professional GPU) |

The **training time** figures assume the hyper‑parameter settings described in the previous section (learning‑rate scaling, batch size, epochs).  Because the adapters are stored separately, the *deployment* footprint of a finished Guanaco model is determined solely by the quantised base: the 7 B variant runs on a **5 GB** GPU (easily fitting on a modern laptop), whereas the 65 B variant occupies **≈ 44 GB**, which is still manageable on a single high‑end workstation.  

### 2. Dataset‑Conditioned Checkpoints  

For each scale the authors trained adapters on **each of the eight datasets** listed earlier, yielding a total of eight checkpoints per scale.  The naming convention follows a simple pattern:  

```
guanaco-{scale}b-{dataset}
```

For example:  

- `guanaco-7b-oasst1` – 7 B model finetuned on the OASST1 multi‑turn dialogues.  
- `guanaco-33b-flanv2` – 33 B model finetuned on the massive FLAN‑v2 collection.  

All checkpoints are released under the same permissive license as the base LLaMA models, and the repository includes **CUDA kernels** required for the 4‑bit NF4 de‑quantisation and the double‑quantisation of scaling constants.  

### 3. Performance Highlights  

The **Guanaco‑65B‑OASST1** checkpoint achieved **99.3 %** of ChatGPT’s performance on the Vicuna benchmark, surpassing every previously open‑source chatbot while being trained in only **24 hours** on a single 48 GB GPU.  The **Guanaco‑33B‑OASST1** checkpoint required **≤ 12 hours** on a consumer‑grade 24 GB GPU and still outperformed the proprietary Vicuna‑13B model by **≈ 3 percentage points** on the same benchmark.  The smaller 7 B variants, while not reaching ChatGPT‑level fluency, still yielded **≈ 20 percentage‑point** gains over the original Alpaca‑13B model despite using a fraction of the memory at inference time (≈ 5 GB).

### Concluding Remarks  

By carefully selecting diverse instruction‑following corpora, applying a uniform preprocessing pipeline, and employing a training recipe that respects the memory constraints of 4‑bit NF4 quantisation, the QLoRA framework makes it feasible to finetune **any** LLaMA model up to 65 B parameters on a single GPU.  The key engineering decisions—*full‑layer LoRA adapters*, *double quantisation of scaling constants*, and *paged optimisers*—ensure that the quantisation noise introduced by NF4 does not impair downstream performance.  The resulting **Guanaco** model zoo demonstrates that open‑source instruction‑tuned chatbots can now rival closed‑source commercial systems, thereby democratising access to high‑quality conversational AI.  Researchers wishing to reproduce or extend these results can start from the released adapters and follow the exact hyper‑parameter schedule outlined above, confident that the underlying QLoRA methodology has been validated across multiple model scales, datasets, and evaluation protocols.
