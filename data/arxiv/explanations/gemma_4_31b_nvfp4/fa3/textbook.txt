# Introduction to Attention and Hardware Bottlenecks

## The Mathematics of Multi-Head Attention (MHA)

To understand the optimizations introduced in modern attention kernels, one must first grasp the fundamental mathematical operations of the attention mechanism. In a single-head attention scenario, we begin with three input sequences: the query $\mathbf{Q}$, the key $\mathbf{K}$, and the value $\mathbf{V}$. Each of these matrices resides in $\mathbb{R}^{N \times d}$, where $N$ represents the sequence length and $d$ represents the head dimension. The goal of the attention mechanism is to compute an output matrix $\mathbf{O} \in \mathbb{R}^{N \times d}$ that represents a weighted aggregation of the values based on the compatibility between queries and keys.

The computation proceeds in three primary steps. First, the attention scores $\mathbf{S} \in \mathbb{R}^{N \times N}$ are calculated by taking the product of the query matrix and the transpose of the key matrix, scaled by a factor $\alpha$: $\mathbf{S} = \alpha \mathbf{Q} \mathbf{K}^\top$. Typically, $\alpha$ is set to $1/\sqrt{d}$ to maintain numerical stability. Second, a softmax operation is applied row-wise to these scores to produce a probability matrix $\mathbf{P} \in \mathbb{R}^{N \times N}$, where $\mathbf{P} = \mathrm{softmax}(\mathbf{S})$. In practical implementations, to prevent numerical instability when computing the exponential function, the maximum value of each row, denoted as $\mathrm{rowmax}(\mathbf{S})$, is subtracted from $\mathbf{S}$ before the softmax is applied. Finally, the output $\mathbf{O}$ is computed as the product of the probability matrix and the value matrix: $\mathbf{O} = \mathbf{P}\mathbf{V}$. In multi-head attention (MHA), this entire process is parallelized across multiple heads and batches, with each head possessing its own set of projections.

For students interested in the training of these models, it is essential to understand the backward pass. Given the gradient of a scalar loss function $\phi$ with respect to the output, $\mathbf{dO} \in \mathbb{R}^{N \times d}$, the gradients for the inputs are computed using the chain rule. The gradient for the values is $\mathbf{dV} = \mathbf{P}^\top \mathbf{dO}$, and the gradient for the probabilities is $\mathbf{dP} = \mathbf{dO} \mathbf{V}^\top$. This is further transformed into the gradient of the scores $\mathbf{dS} = \mathrm{dsoftmax}(\mathbf{dP})$, where the softmax gradient for a vector $p = \mathrm{softmax}(s)$ is defined as $\mathbf{d}s = (\mathrm{diag}(p) - p p^\top)\mathbf{d}p$. Finally, the gradients for the queries and keys are derived as $\mathbf{dQ} = \alpha \mathbf{dS} \mathbf{K}$ and $\mathbf{dK} = \alpha \mathbf{dS}^\top \mathbf{Q}$.

## Computational Complexity and Quadratic Scaling

The primary challenge in scaling Transformer architectures is the computational complexity of the attention mechanism. The bottleneck arises specifically from the calculation of the self-attention scores $\mathbf{S} = \alpha \mathbf{Q} \mathbf{K}^\top$. Because both $\mathbf{Q}$ and $\mathbf{K}$ have a sequence length of $N$, the resulting score matrix $\mathbf{S}$ is of size $N \times N$. This means that the amount of computation and the amount of memory required to store these scores scale quadratically, or $O(N^2)$, with respect to the sequence length.

As the sequence length $N$ increases, the quadratic growth in the number of operations makes attention the dominant bottleneck for large language models. While the head dimension $d$ is typically small and constant relative to $N$, the $N \times N$ nature of the score and probability matrices means that doubling the sequence length quadruples the computational effort and memory footprint for the attention layer. This quadratic scaling is the central problem that software optimizations like FlashAttention aim to mitigate, as it limits the ability of models to process very long contexts.

## The GPU Memory Hierarchy: Global Memory (HBM), L2 Cache, Shared Memory (SMEM), and Registers (RMEM)

To optimize attention, one must understand the hardware on which it executes. Modern GPUs, such as the NVIDIA Hopper architecture, utilize a memory hierarchy where capacity and bandwidth are inversely related. At the top level is Global Memory (GMEM), also known as High Bandwidth Memory (HBM). This is off-chip DRAM that is accessible to all streaming multiprocessors (SMs) across the GPU. While it has the largest capacity, it is the slowest level of the hierarchy. To mitigate this latency, data from GMEM is transparently cached into an on-chip L2 cache.

Moving closer to the execution units, each SM contains Shared Memory (SMEM). SMEM is a small, on-chip, programmer-managed cache that is highly banked and can be directly addressed by all threads within a cooperative thread array (CTA), also known as a threadblock. SMEM is significantly faster than GMEM, but its capacity is much more limited. At the finest level of the hierarchy is the register file, known as Register Memory (RMEM). These registers are private to each individual thread, providing the lowest latency and highest bandwidth. In the Hopper architecture, each thread has a maximum of 256 registers.

The efficiency of a GPU kernel is often determined by how effectively it manages the movement of data between these levels. A "standard" attention implementation is inefficient because it materializes the intermediate $N \times N$ matrices $\mathbf{S}$ and $\mathbf{P}$ in HBM, requiring expensive reads and writes. Optimizations focus on "fusing" these operations so that data remains in SMEM or RMEM for as long as possible, avoiding the slow trip back to global memory.

## The Concept of Memory-Bound vs. Compute-Bound Operations

In GPU computing, a kernel's performance is generally limited by either the speed of the hardware's arithmetic units (compute-bound) or the speed of data movement (memory-bound). An operation is compute-bound if the time spent performing mathematical calculations is the primary limiting factor. Matrix multiplications, or GEMMs, are typically compute-intensive and can be highly accelerated by specialized hardware like Tensor Cores. For example, the H100 GPU can achieve massive throughput for FP16 matmuls, reaching hundreds of TFLOPs/s.

Conversely, an operation is memory-bound if the hardware spends more time waiting for data to be moved from HBM to SMEM or RMEM than it does performing calculations. The "standard" attention implementation is heavily memory-bound because it writes the large $\mathbf{S}$ and $\mathbf{P}$ matrices to HBM and then reads them back. Furthermore, some operations are inherently low-throughput. The paper notes that "special functions" like the exponential used in softmax are performed by a separate multi-function unit with much lower throughput than the Tensor Cores. On an H100, matmul throughput is vastly higher than the throughput for exponential operations.

The goal of FlashAttention-3 is to transition the attention mechanism from being memory-bound to being more compute-bound by minimizing memory reads and writes and overlapping the low-throughput non-GEMM operations (like softmax) with the high-throughput asynchronous GEMM operations.

## The Impact of Sequence Length on LLM Performance

The intersection of quadratic scaling and memory bottlenecks has a profound impact on the capabilities of large language models. Because attention becomes exponentially more expensive as the sequence length $N$ grows, traditional models are often limited to short contexts. However, expanding the context window is critical for unlocking advanced capabilities. For instance, modeling and reasoning over multiple long documents or large codebases requires the ability to handle very high values of $N$.

Similarly, new modalities such as high-resolution images, audio, and video generate sequences that are naturally much longer than standard text. Applications like agent workflows with long horizons or user interactions with extensive histories also demand long-context windows. By optimizing the attention kernel to be faster and more memory-efficient, researchers can move beyond the limitations of $O(N^2)$ scaling, allowing LLMs to ingest and process significantly more information without suffering from prohibitive computational costs or memory exhaustion.

Foundations of FlashAttention

# The Problem with Standard Attention: Materialization of Large Intermediate Matrices

To understand the necessity of the FlashAttention series, one must first understand the computational and memory challenges associated with the standard attention mechanism. In a typical Transformer architecture, the attention output $\mathbf{O}$ is computed using three input sequences: queries $\mathbf{Q}$, keys $\mathbf{K}$, and values $\mathbf{V}$, all of which reside in $\mathbb{R}^{N \times d}$, where $N$ is the sequence length and $d$ is the head dimension. The process involves two primary matrix multiplication steps. First, the attention scores matrix $\mathbf{S}$ is computed as $\mathbf{S} = \alpha \mathbf{Q} \mathbf{K}^\top$, where $\alpha$ is a scaling factor typically set to $1/\sqrt{d}$. Then, a row-wise softmax operation is applied to $\mathbf{S}$ to produce the attention probability matrix $\mathbf{P} = \mathrm{softmax}(\mathbf{S})$. Finally, the output is computed as $\mathbf{O} = \mathbf{P}\mathbf{V}$.

The fundamental problem with this "standard" implementation is the materialization of the intermediate matrices $\mathbf{S}$ and $\mathbf{P}$. Both of these matrices have dimensions of $N \times N$. Because the sequence length $N$ can be very large in long-context applications, these matrices scale quadratically, meaning that as the input sequence grows, the memory required to store $\mathbf{S}$ and $\mathbf{P}$ grows at a much faster rate. In a standard GPU implementation, these large intermediate matrices are written to and read from the High Bandwidth Memory (HBM), also known as global memory.

This reliance on HBM creates a massive bottleneck. While GPUs have incredibly fast processing power via their Tensor Cores, the speed at which data can be moved between the on-chip shared memory and the off-chip HBM is significantly slower. Consequently, the time spent moving $\mathbf{S}$ and $\mathbf{P}$ back and forth to global memory dominates the total execution time, leaving the GPU's computational units underutilized. This memory-bound nature of standard attention limits the ability of large language models to handle long sequences or high-resolution modalities.

# FlashAttention-1: Tiling and the Online Softmax Algorithm

FlashAttention-1 was introduced to solve the memory bottleneck by eliminating the need to materialize the $N \times N$ intermediate matrices to HBM. The core intuition behind this approach is to fuse all the attention operations—the matrix multiplications and the softmax—into a single GPU kernel. By doing this, the algorithm can perform the computation in smaller pieces, a technique known as tiling, and keep the intermediate results in the GPU's fast on-chip shared memory (SMEM) instead of the slow global memory.

Tiling involves breaking the large $\mathbf{Q}, \mathbf{K},$ and $\mathbf{V}$ matrices into smaller blocks. Instead of computing the entire $\mathbf{S}$ matrix and then computing the entire $\mathbf{P}$ matrix, FlashAttention computes the attention output $\mathbf{O}$ block by block. However, this presents a mathematical challenge: the softmax operation is a global reduction, meaning the value of a single entry in $\mathbf{P}$ depends on all other entries in that row of $\mathbf{S}$. Traditionally, one would need the entire row of $\mathbf{S}$ to calculate the softmax denominator (the sum of exponentials) and the row maximum for numerical stability.

To overcome this, FlashAttention-1 utilizes a local version of the softmax reduction, often referred to as an online softmax algorithm. This allows the kernel to compute the softmax incrementally. As it processes each tile of the key and value matrices, it maintains and updates the running row maximum and the running sum of exponentials. If a new block of scores contains a value larger than the current maximum, the algorithm rescales the previously computed output $\mathbf{O}$ to account for the new maximum. By the time the algorithm has iterated through all tiles, it has produced the exact same result as the standard attention mechanism, but without ever writing the full $N \times N$ matrices to HBM.

# FlashAttention-2: Parallelization over Sequence Length and Work Distribution

While FlashAttention-1 significantly reduced memory traffic, FlashAttention-2 focused on further improving the efficiency of the algorithm by restructuring how work is distributed across the GPU. One of the primary improvements in FlashAttention-2 is the way it parallelizes the computation. While the previous version focused on tiling, FlashAttention-2 explicitly parallelizes over the sequence length dimension.

In the forward pass of FlashAttention-2, the algorithm is designed to perform the inner loop over blocks of the key $\mathbf{K}$ and value $\mathbf{V}$ matrices. By restructuring the loop in this manner, the algorithm improves the "occupancy" of the GPU. Occupancy refers to the fraction of the GPU's streaming multiprocessors (SMs) that are actively executing warps. Better occupancy ensures that the workload is distributed more evenly across the hardware, reducing the likelihood that some SMs are idle while others are overloaded.

Additionally, FlashAttention-2 optimizes the way it handles the query blocks. By dividing the query matrix $\mathbf{Q}$ into blocks and parallelizing the computation of each output tile $\mathbf{O}_i$ across different SMs, the algorithm achieves higher throughput. These architectural refinements allow FlashAttention-2 to be significantly faster than its predecessor while maintaining the same memory-efficient properties of tiling and online softmax.

# The Role of Recomputation in the Backward Pass

A critical aspect of the FlashAttention design is how it handles the backward pass during training. In standard attention, one would store the $N \times N$ matrix $\mathbf{P}$ from the forward pass and use it during the backward pass to compute the gradients $\mathbf{dQ}, \mathbf{dK},$ and $\mathbf{dV}$. However, storing $\mathbf{P}$ would reintroduce the very memory bottleneck that FlashAttention was designed to eliminate.

To avoid storing the massive $\mathbf{P}$ matrix, FlashAttention employs a strategy called recomputation. Instead of reading $\mathbf{P}$ from HBM, the backward pass re-calculates the necessary attention scores and softmax values on the fly using the stored $\mathbf{Q}, \mathbf{K},$ and $\mathbf{V}$ matrices. While this sounds counter-intuitive because it increases the total number of floating-point operations (FLOPs), it is actually a performance win. The cost of performing extra calculations (which happen in fast on-chip registers and SMEM) is much lower than the cost of reading a massive $N \times N$ matrix from the slow HBM.

The computational impact of this choice is evident when analyzing the FLOPs of the backward pass. In the forward pass, there are two primary matrix multiplications. In the backward pass, because of the need to recompute the attention probabilities to find the gradients, there are five matrix multiplications. This is why the backward pass FLOPs are typically calculated as $2.5\times$ the forward pass FLOPs. By trading off extra computation for reduced memory access, FlashAttention ensures that the backward pass remains efficient even for very long sequences.

# Evaluation of Hardware Utilization on NVIDIA Ampere vs. Hopper Architectures

The evolution of the FlashAttention series is closely tied to the hardware it runs on. Earlier versions, like FlashAttention-2, were designed primarily with the NVIDIA Ampere architecture in mind. These versions rely on a synchronous model of execution where memory loads and tensor core computations happen in a sequence. However, as hardware evolved to the NVIDIA Hopper architecture (e.g., the H100 GPU), new capabilities were introduced that FlashAttention-2 was not designed to exploit.

On the Hopper architecture, FlashAttention-2 exhibits poor hardware utilization. Specifically, it achieves only about 35% utilization of the H100's theoretical peak performance, whereas highly optimized general matrix multiplication (GEMM) kernels can achieve 80-90% utilization. This gap exists because FlashAttention-2 uses synchronous instructions and Ampere-specific logic, failing to take advantage of Hopper's asynchronous capabilities.

The Hopper architecture introduced specialized hardware units such as the Tensor Memory Accelerator (TMA), which allows for asynchronous data movement between global memory and shared memory, and asynchronous Tensor Cores (via WGMMA instructions) that can source inputs directly from shared memory. Because FlashAttention-2 does not use these asynchronous features or Hopper-specific instructions, it cannot overlap data movement with computation effectively. This realization highlights the limitation of a purely synchronous algorithm and sets the stage for the need for a new design—FlashAttention-3—which explicitly targets the asynchrony and low-precision capabilities of the Hopper architecture.

Exploiting Asynchrony: Warp-Specialization and TMA

# Hopper GPU Architecture: Tensor Memory Accelerator (TMA) and WGMMA

To understand the advancements in FlashAttention-3, one must first understand the specific hardware capabilities of the NVIDIA Hopper architecture. Modern GPUs are designed as throughput processors, meaning they are built to handle massive amounts of data in parallel. To achieve this, they employ a memory hierarchy where capacity is inversely related to bandwidth. At the top is Global Memory (GMEM), which is off-chip DRAM accessible to all streaming multiprocessors (SMs). Below this is the L2 cache, followed by Shared Memory (SMEM), a small, programmer-managed on-chip cache within each SM. Finally, there is the register file (RMEM), which is private to each individual thread.

A critical bottleneck in high-performance computing is the time spent moving data between these levels of memory, as well as the time it takes to issue instructions to the hardware. The Hopper architecture introduces the Tensor Memory Accelerator (TMA), a dedicated hardware unit specifically designed to handle asynchronous memory copies between GMEM and SMEM. Unlike traditional memory instructions that might stall the execution of a thread, the TMA allows for data movement to occur independently of the main computation.

Complementing the TMA is the warpgroup-wide WGMMA (Warpgroup Matrix Multiply-Accumulate) instruction. This instruction leverages the GPU's Tensor Cores to perform matrix multiplications. Crucially, in the Hopper architecture, the Tensor Cores are asynchronous and can source their input operands directly from shared memory. By combining TMA for data movement and WGMMA for computation, the hardware allows for a degree of asynchrony where the GPU can "fire and forget" a memory load or a matrix multiplication and continue executing other instructions while the hardware units complete the task.

# Warp-Specialization: Producer and Consumer Roles

In previous GPU kernel designs, such as those used in FlashAttention-2, warps typically performed both data movement and computation synchronously. This meant that a warp would load data, wait for that data to arrive, perform a computation, and then repeat. FlashAttention-3 departs from this model by employing warp-specialization, a software pipelining scheme that divides the warps within a cooperative thread array (CTA) into two distinct roles: producers and consumers.

The producer warps are specialized exclusively for data movement. Their primary responsibility is to issue TMA loads to move blocks of the query, key, and value matrices from HBM (global memory) into shared memory. Because the producer warps are not involved in the heavy matrix multiplication, they can focus entirely on keeping the shared memory buffers filled, effectively hiding the latency associated with memory access.

The consumer warps, on the other hand, are specialized for computation. They wait for the producer warps to notify them that the required data has arrived in SMEM, and then they execute the WGMMA instructions to perform the attention mechanism's matrix multiplications. By splitting these roles, the algorithm prevents the Tensor Cores from idling while waiting for memory loads. This specialization improves the compiler's ability to generate optimal instruction schedules, as the distinct roles allow the hardware to overlap the issuance of data movement commands with the execution of mathematical operations.

# Software Pipelining with Circular SMEM Buffers

The coordination between producer and consumer warps is managed through a software pipelining mechanism using a circular shared memory (SMEM) buffer. In the forward pass of attention, the query matrix is divided into blocks $\mathbf{Q}_i$, and the key and value matrices are divided into blocks $\mathbf{K}_j$ and $\mathbf{V}_j$. To maximize efficiency, the algorithm uses a buffer with $s$ stages.

The producer warps operate in a loop, loading blocks $\mathbf{K}_j$ and $\mathbf{V}_j$ into the $s$-stage circular buffer. The producer does not simply load one block and stop; it can issue loads for multiple subsequent blocks. Specifically, the producer waits for the $(j \pmod s)$th stage of the buffer to be marked as "consumed" before loading the next set of blocks into that slot. Once the TMA load is complete, the producer commits a notification to the consumers that the data is ready.

The consumer warps follow a similar synchronized flow. They wait for the specific buffer stage to be filled by the producer before performing the necessary GEMM (General Matrix Multiply) operations. After the consumer has finished using the data in the $(j \pmod s)$th stage to update the output $\mathbf{O}_i$, it releases that stage of the buffer, signaling to the producer that the slot is now available for new data. This circular buffering ensures that while the consumer is processing block $j$, the producer is already fetching block $j+1$ or $j+2$ from global memory, effectively creating a continuous stream of data that minimizes processor stalls.

# Asynchronous Memory Copy and Instruction Issue Latency

The core intuition behind the performance gains in FlashAttention-3 is the exploitation of asynchrony to hide two types of latency: memory latency and instruction issue latency. Memory latency is the time it takes for data to travel from the off-chip DRAM (GMEM) to the on-chip SMEM. Instruction issue latency refers to the time the GPU takes to decode and dispatch an instruction to a specific hardware unit.

Because the TMA and the Tensor Cores (via WGMMA) are separate hardware units from the standard CUDA cores that handle logic and integer math, they can operate concurrently. In a synchronous model, the GPU would issue a load and wait for the data to arrive before issuing the next instruction. In the asynchronous model used by FlashAttention-3, the producer warps issue TMA loads that do not stall the processor. The producer can issue a sequence of loads to the TMA unit, and the TMA unit handles the movement of data in the background.

Similarly, WGMMA instructions are asynchronous. When a consumer warp issues a WGMMA instruction, it does not immediately block the thread; instead, the instruction is committed to the Tensor Core. This allows the consumer to potentially overlap other operations, such as the non-matmul parts of the softmax function, with the matrix multiplication happening in the background. By decoupling the "request" for an operation from its "completion," FlashAttention-3 ensures that the high-throughput Tensor Cores are kept busy nearly all the time, significantly increasing the TFLOPs/s utilization of the H100 GPU.

# Register Reallocation using setmaxnreg

One of the practical challenges of warp-specialization is that producer and consumer warps have very different requirements for register usage. Registers (RMEM) are a finite resource within each SM; if too many registers are used by a single warp, it can limit the number of warps that can run concurrently (occupancy). Consumer warps, which perform complex WGMMA operations, are register-hungry, requiring a significant amount of RMEM to store intermediate results and manage the pipeline. In contrast, producer warps, which primarily issue TMA loads, require very few registers—in some cases, only a single thread is needed to manage the TMA.

To optimize this, FlashAttention-3 utilizes a Hopper-specific feature called `setmaxnreg`. This instruction allows for the dynamic reallocation of registers between warpgroups. By using `setmaxnreg`, the algorithm can explicitly deallocate registers from the producer warpgroups and reallocate them to the consumer warpgroups.

This reallocation ensures that the consumer warps have a larger share of the register file, which is essential for maintaining a high pipeline depth and using larger block sizes without causing "register spilling" (where the compiler is forced to move register data back to the slower shared memory). By tailoring the register allocation to the specific role of the warp, FlashAttention-3 maximizes the computational efficiency of the consumer warps while maintaining the lean operation of the producer warps.

Advanced Pipelining: Overlapping GEMM and Softmax

# The Throughput Gap: Matmul TFLOPs vs. Special Function TFLOPs

To understand the motivation behind the advanced pipelining in FlashAttention-3, one must first understand the stark disparity in throughput between different hardware units on a modern GPU, such as the NVIDIA H100 SXM5. The GPU is designed as a throughput processor, utilizing specialized hardware for specific tasks. Matrix multiplication (GEMM) is handled by Tensor Cores, which are incredibly efficient. In contrast, non-matmul operations—such as the exponential functions required for the softmax operation—are handled by a separate hardware unit known as the multi-function unit.

This architectural difference creates a massive "throughput gap." For instance, the H100 SXM5 GPU can achieve 989 TFLOPS for FP16 matrix multiplications, but it can only achieve 3.9 TFLOPS for special functions like the exponential. This means that the hardware's ability to perform matrix multiplications is orders of magnitude greater than its ability to compute the components of a softmax. 

The impact of this gap becomes evident when looking at the actual workload of the attention forward pass. For a configuration with a head dimension of 128 in FP16, there are 512 times more floating-point operations (FLOPs) dedicated to matrix multiplication than to exponential operations. However, because the throughput for the exponential is 256 times lower than that of the matrix multiplication, the exponential calculations can still consume up to 50% of the total execution cycles. This bottleneck is even more pronounced when using FP8 precision; while the matmul throughput doubles, the throughput for the exponential function remains the same, further increasing the relative time spent on non-matmul operations.

# Pingpong Scheduling: Inter-warpgroup Overlapping

Because the multi-function unit (used for softmax) and the Tensor Cores (used for GEMM) are separate hardware entities, it is theoretically possible to have them both working at the same time. FlashAttention-3 exploits this through a technique called "pingpong scheduling," which allows the softmax computation of one warpgroup to be overlapped with the GEMM computation of another warpgroup.

In a standard synchronous execution, the GPU would finish all matrix multiplications before moving on to the softmax, or vice versa. With pingpong scheduling, the algorithm uses synchronization barriers, specifically `bar.sync` instructions, to carefully orchestrate the timing of operations. The goal is to force the GEMMs—specifically the $\mathbf{P}\mathbf{V}$ multiplication of one iteration and the $\mathbf{Q}\mathbf{K}^\top$ multiplication of the next—of warpgroup 1 to be scheduled before the GEMMs of warpgroup 2.

By arranging the schedule this way, the softmax operations of warpgroup 1 are executed while warpgroup 2 is utilizing the Tensor Cores for its GEMMs. Once warpgroup 2 finishes its GEMM phase and begins its softmax phase, the roles swap, and warpgroup 1 begins its GEMM operations. This "pingpong" effect ensures that the Tensor Cores are kept busy while the multi-function unit handles the softmax in the background. Empirically, this has been shown to improve performance; for example, in an FP16 forward pass with a head dimension of 128 and a sequence length of 8192, throughput increased from 570 TFLOPS to between 620 and 640 TFLOPS.

# Intra-warpgroup Overlapping: The 2-Stage GEMM-Softmax Pipeline

While pingpong scheduling overlaps work between different warpgroups, FlashAttention-3 further optimizes performance by overlapping instructions within a single warpgroup. This is achieved through a 2-stage GEMM-softmax pipelining algorithm. The primary challenge here is the sequential nature of the attention inner loop: the local softmax depends on the output of the first GEMM ($\mathbf{S} = \mathbf{Q}\mathbf{K}^\top$), and the second GEMM ($\mathbf{O} = \mathbf{P}\mathbf{V}$) depends on the output of that softmax.

To break this sequential bottleneck, the algorithm pipelines operations across iterations. In the 2-stage pipeline, the consumer warpgroup does not simply execute one iteration at a time. Instead, it utilizes a strategy where the second WGMMA (Warpgroup Matrix Multiply-Accumulate) operation of iteration $j$ is overlapped with the softmax operations of iteration $j+1$.

Specifically, in the main loop, the warpgroup computes $\mathbf{S}_{\text{next}} = \mathbf{Q}_i \mathbf{K}_j^\top$ using WGMMA and commits the operation but does not immediately wait for it to finish. It then proceeds to compute the output $\mathbf{O}_i = \mathbf{O}_i + \tilde{\mathbf{P}}_{\text{cur}} \mathbf{V}_{j-1}$ using another WGMMA, again committing without waiting. Only then does it wait for the first WGMMA ($\mathbf{S}_{\text{next}}$) to complete so that it can perform the softmax calculations on that result. Finally, it waits for the second WGMMA to finish before rescaling the output $\mathbf{O}_i$. By decoupling the commit and the wait, the Tensor Cores can continue processing the next set of matrices while the software handles the softmax logic.

# Breaking Sequential Dependencies through Register Buffering

The ability to perform intra-warpgroup overlapping depends entirely on the use of additional register buffers. In a naive implementation, the results of a GEMM would be used immediately by the softmax and then discarded or overwritten. However, to allow a GEMM from a future iteration to begin before the current iteration's softmax is finished, the algorithm must maintain the state of multiple iterations simultaneously.

By using registers as buffers, FlashAttention-3 can store intermediate results like $\mathbf{S}_{\text{next}}$ and $\tilde{\mathbf{P}}_{\text{cur}}$ across the boundaries of the loop iterations. This register buffering allows the algorithm to treat the computation as a pipeline. For example, while the hardware is busy computing the scores for the next block of keys, the registers hold the softmax-normalized scores from the previous block, which are then used to update the output matrix. This effectively hides the latency of the softmax operations because the Tensor Cores are never idling while waiting for the multi-function unit to finish the exponential calculations; they are always working on the "next" piece of the puzzle.

# Practical Constraints: Compiler Reordering and Register Pressure

Implementing these advanced pipelining techniques introduces significant practical challenges, primarily regarding compiler behavior and hardware resource limits. One major concern is compiler reordering. The high-level pseudocode for the 2-stage pipeline assumes a strict sequence of "commit" and "wait" operations. However, the NVIDIA compiler (NVCC) often rearranges instructions to optimize performance. If the compiler moves a "wait" instruction or changes the order of WGMMA calls, it could disrupt the carefully timed pipeline and lead to incorrect results or performance degradation. Analysis of the SASS (assembly) code is therefore required to verify that the compiler is indeed generating the overlapped execution sequence as intended.

Another critical constraint is register pressure. Registers are the fastest and most limited memory resource on the GPU. The 2-stage pipeline requires additional registers to store intermediate results, such as the $\mathbf{S}_{\text{next}}$ matrix, which has a size of $B_r \times B_c \times \text{sizeof}(\text{float})$ per threadblock. Since each thread has a limited number of registers (at most 256), using too many registers for buffering can lead to "register spilling," where data is pushed back into slower memory, severely harming performance.

This creates a difficult trade-off: while larger block sizes ($B_r, B_c$) generally improve performance by increasing the work per tile, they also increase register demand. Similarly, moving from a 2-stage to a 3-stage pipeline could further increase Tensor Core utilization by overlapping more operations, but it would require even more register buffering. Consequently, the optimal pipeline depth and tile size must be determined through careful profiling and empirical testing to balance utilization against register availability.

Low-Precision Attention with FP8

# FP8 (e4m3) Number Format and Throughput Advantages

Modern deep learning hardware, specifically the NVIDIA Hopper architecture, provides specialized hardware units designed to accelerate low-precision computation. One such format is FP8, specifically the e4m3 variant. In this number format, a value is represented using 8 bits: 4 bits are dedicated to the exponent and 3 bits are dedicated to the mantissa. While this significantly reduces the precision compared to 16-bit or 32-bit formats, it offers substantial advantages in terms of computational throughput.

The primary advantage of using FP8 is the ability to leverage the warpgroup-wide WGMMA (Warpgroup Matrix Multiply-Accumulate) instructions on the Hopper Tensor Cores. When targeting these FP8 Tensor Cores, the GPU can deliver double the throughput per streaming multiprocessor (SM) compared to using FP16 or BF16 precision. This increase in TFLOPs/s is critical for the attention mechanism, which serves as the primary computational bottleneck in Transformer architectures due to its quadratic scaling with sequence length. By utilizing FP8, the system can perform significantly more operations per clock cycle, effectively increasing the processing speed of the large-scale matrix multiplications inherent in the attention forward pass.

# Layout Conformance: MN-major vs. K-major Constraints

Transitioning to FP8 is not as simple as changing a data type; it requires a strict adherence to specific memory layout constraints required by the hardware. To understand these constraints, consider a general GEMM (General Matrix Multiply) operation where we multiply a matrix $A$ of size $M \times K$ by a matrix $B^\top$ of size $K \times N$. In this context, we define the layout of the operands based on which dimension is contiguous in memory. An operand is considered mn-major if it is contiguous in the outer $M$ or $N$ dimension, and it is considered k-major if it is contiguous in the inner $K$ dimension.

In previous architectures or when using FP16 WGMMA instructions, the hardware is flexible and accepts both mn-major and k-major input operands when they are stored in shared memory (SMEM). However, the FP8 WGMMA instructions on Hopper GPUs are more restrictive: they only support the k-major format for operands. In the context of the attention mechanism, this poses a specific challenge for the second GEMM operation, where the value matrix $\mathbf{V}$ must be processed. Because $\mathbf{V}$ is typically provided in a format that is contiguous in the head dimension rather than the sequence length dimension, it does not naturally satisfy the k-major constraint required for FP8 execution.

# Implementing In-kernel Transpose using LDSM and STSM

To satisfy the k-major requirement for FP8 without incurring the massive overhead of a separate pre-processing transpose kernel or modifying the global memory layout, \textsc{FlashAttention-3} implements an in-kernel transpose of tiles of the value matrix $\mathbf{V}$. This process occurs after tiles of $\mathbf{V}$ are loaded from global memory into shared memory.

The implementation utilizes two specific hardware instructions: LDSM (`ldmatrix`) and STSM (`stmatrix`). These instructions allow a warp of threads to collectively load data from shared memory to the register file (RMEM) and store data from RMEM back to shared memory at a granularity of 128 bytes. To adapt these 16-bit instructions for FP8, 8-bit entries are packed two at a time. Because the transpose versions of LDSM and STSM cannot independently split these packed 8-bit entries, the algorithm performs specific register movements between the load and store operations to achieve the actual tile-wise transpose. To maintain efficiency, this transpose operation is scheduled to occur in the "shadow" of the Tensor Core operations, meaning the producer warpgroup performs the transpose for the next $\mathbf{V}$ tile while the consumer warpgroups are executing the WGMMAs for the current tiles.

# Handling Accumulator Layouts: Byte Permutation and Register Movement

Beyond the operand layout, there is a second challenge involving the FP32 accumulator. When an FP8 WGMMA operation is performed, the resulting FP32 accumulator is stored in a register layout that differs from the layout assumed for operand $A$ when it is held in registers. This discrepancy creates a conflict when the output of the first GEMM (the attention scores $\mathbf{P}$) must serve as an operand for the second GEMM.

To resolve this, \textsc{FlashAttention-3} employs byte permute instructions to transform the accumulator layout into a format compatible with the second WGMMA and the transposed $\mathbf{V}$ tile. Specifically, the register entries are permuted into a sequence of $\{\text{d0 d1 d4 d5 d2 d3 d6 d7}\}$, and this permutation is replicated every 8 bytes. Logically, this operation permutes the columns of the $\mathbf{P}$ tile. To ensure the final mathematical result remains correct despite this permutation, the in-kernel transpose of the $\mathbf{V}$ tile is designed to write out a matching row permutation. By coordinating the register permutation of the accumulator with the row permutation of the $\mathbf{V}$ tile, the algorithm ensures the correct output is computed while adhering to hardware layout restrictions.

# Mitigating Quantization Error: Block Quantization

The use of FP8 (e4m3) introduces a higher risk of numerical error compared to FP16 because it uses only 3 bits for the mantissa and 4 bits for the exponent. This issue is exacerbated by the presence of "outlier features" in large language models, where a small number of values have magnitudes significantly larger than the rest. Standard per-tensor quantization—which uses a single scaling factor for the entire tensor—fails to capture these outliers, leading to significant precision loss.

To mitigate this, \textsc{FlashAttention-3} employs block quantization. Instead of one scalar per tensor, the algorithm maintains one scalar per block. The tensors $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$ are split into blocks of size $B_r \times d$ or $B_c \times d$, and each block is quantized separately. This approach allows the scaling factor to adapt to the local magnitude of the data, effectively isolating outliers. Since the \textsc{FlashAttention-3} algorithm naturally operates on blocks, the necessary rescaling of the attention scores $\mathbf{S}$ can be performed at no additional computational cost. Furthermore, this quantization can be fused with preceding operations, such as rotary embedding, without slowing down the system because those operations are typically limited by memory bandwidth rather than computation.

# Incoherent Processing: Using Random Orthogonal and Hadamard Matrices

To further reduce quantization error and "even out" the impact of outliers, \textsc{FlashAttention-3} introduces a technique called incoherent processing. The intuition is that outliers are more damaging when they are concentrated in a few dimensions. By rotating the data into a different basis, these outliers can be spread across all dimensions, making the data more amenable to quantization.

This is achieved by multiplying the query $\mathbf{Q}$ and key $\mathbf{K}$ matrices with a random orthogonal matrix $\mathbf{M}$ before they are quantized to FP8. Mathematically, because $\mathbf{M}$ is orthogonal, the property $\mathbf{M} \mathbf{M}^\top = I$ holds. Therefore, the product $(\mathbf{Q} \mathbf{M})(\mathbf{K} \mathbf{M})^\top$ is equivalent to $\mathbf{Q} \mathbf{K}^\top$, meaning the final attention output remains unchanged. The multiplication by $\mathbf{M}$ transforms each entry into a random sum of the original entries, effectively diffusing the outliers. To implement this efficiently, $\mathbf{M}$ is chosen as the product of a Hadamard matrix and random diagonal matrices of $\pm 1$. This specific structure allows the multiplication to be performed in $O(d \log d)$ time instead of $O(d^2)$, and like block quantization, this process can be fused with the rotary embedding to ensure there is no additional computational overhead.

Empirical Validation and Performance Analysis

# Benchmarking Metrics: TFLOPs and Execution Time

To evaluate the effectiveness of \textsc{FlashAttention-3}, it is necessary to establish a rigorous benchmarking framework that measures both the raw computational throughput and the actual wall-clock execution time. The researchers utilize the NVIDIA H100 80GB SXM5 GPU as the primary hardware target. The core metric for performance is TFLOPs/s (tera-floating point operations per second), which represents the amount of floating-point work the GPU is performing every second. This is a critical measure of how well the software is utilizing the hardware's theoretical peak performance.

Calculating the total number of floating-point operations (FLOPs) for the attention mechanism requires accounting for the matrix multiplications involved. For the forward pass, the total FLOPs are calculated as $4 \cdot \text{seqlen}^2 \cdot \text{head dimension} \cdot \text{number of heads}$. This formula accounts for the two primary matrix multiplications in the attention operation: the computation of the scores $\mathbf{S}$ and the computation of the output $\mathbf{O}$. In scenarios involving causal masking, where only a triangular portion of the attention matrix is computed, this total is divided by 2 to reflect that approximately half of the entries are not calculated.

The backward pass is computationally more intensive than the forward pass. To determine the FLOPs for the backward pass, the forward pass FLOPs are multiplied by a factor of 2.5. This scaling factor is derived from the fact that while the forward pass involves 2 matrix multiplications, the backward pass involves 5 matrix multiplications, and it additionally requires recomputation to save memory. By comparing the execution time against these FLOP counts, the researchers can determine the actual throughput and utilization of the Tensor Cores.

# Forward and Backward Pass Performance Analysis

The empirical results demonstrate that \textsc{FlashAttention-3} provides significant speedups over its predecessor, \textsc{FlashAttention-2}, across both the forward and backward passes. For the forward pass using FP16 precision, \textsc{FlashAttention-3} is 1.5-2.0$\times$ faster than \textsc{FlashAttention-2}, reaching a peak throughput of 740 TFLOPs/s. This represents 75\% utilization of the theoretical maximum TFLOPs/s available on the H100 GPU, a substantial improvement over the 35\% utilization observed for \textsc{FlashAttention-2}. When moving to FP8 precision, the throughput increases even further, reaching close to 1.2 PFLOPs/s.

The backward pass also sees a marked improvement, with \textsc{FlashAttention-3} achieving a speedup of 1.5-1.75$\times$ over \textsc{FlashAttention-2}. When compared to a standard attention implementation—which materializes intermediate matrices to high-bandwidth memory (HBM)—the gains are even more dramatic, with \textsc{FlashAttention-3} performing 3-16$\times$ faster depending on the configuration.

An ablation study was conducted to isolate the impact of specific algorithmic changes, specifically the use of warp-specialization and GEMM-softmax pipelining. By testing a non-causal FP16 configuration with a sequence length of 8448 and a head dimension of 128, the researchers observed that these asynchrony-driven improvements increased throughput from 570 TFLOPs/s to 661 TFLOPs/s. This confirms that the ability to overlap data movement and non-GEMM operations (like the exponential function in softmax) with Tensor Core computations is a primary driver of the performance gains.

# Comparison with cuDNN and Triton Implementations

To determine if \textsc{FlashAttention-3} is state-of-the-art, it was compared against several highly optimized implementations, including a version of \textsc{FlashAttention-2} written in Triton that utilizes H100-specific instructions and the vendor-provided cuDNN library. \textsc{FlashAttention-3} outperformed the Triton implementation of \textsc{FlashAttention-2} by a factor of 1.5$\times$. 

The comparison with cuDNN reveals that \textsc{FlashAttention-3} is particularly effective for medium and long sequences, specifically those with a length of 1,000 tokens or more. However, the performance gap varies when using FP8 precision and different head dimensions. For a head dimension of 64, FP8 \textsc{FlashAttention-3} is ahead of cuDNN. For head dimensions of 128 and 256, it remains at par with cuDNN in non-causal cases but falls behind when causal masking is applied.

The researchers attribute the performance difference in FP8 for small sequence lengths and causal masking to implementation details. Specifically, the FP16 version of \textsc{FlashAttention-3} utilizes a persistent kernel and a specific load-balancing strategy, whereas the FP8 version currently does not. This suggests that the underlying algorithm is highly efficient, but further engineering—such as integrating a persistent kernel design into the FP8 implementation—could further close the gap with vendor-optimized libraries.

# Numerical Stability: Measuring RMSE and Outlier Impact

A critical challenge in accelerating attention is maintaining numerical accuracy, especially when reducing precision to FP8. To validate this, the researchers compared \textsc{FlashAttention-2}, \textsc{FlashAttention-3}, and a standard attention implementation against a high-precision FP64 reference implementation using Root Mean Squared Error (RMSE).

To simulate the realistic conditions of Large Language Models (LLMs), which often contain outlier features, the researchers generated input matrices $\mathbf{Q}, \mathbf{K}$, and $\mathbf{V}$ using a specific distribution: $\mathcal{N}(0, 1) + \mathcal{N}(0, 100) \cdot \mathrm{Bernoulli}(0.001)$. This means that 99.9\% of the entries follow a standard normal distribution, while 0.1\% of the entries are outliers with a much larger standard deviation of 10.

In FP16, both \textsc{FlashAttention-2} and \textsc{FlashAttention-3} showed 1.7$\times$ lower RMSE than the standard implementation. This improvement is due to the fact that intermediate results for the softmax are kept in FP32, preventing the precision loss that occurs when materializing these results to HBM. 

The most significant finding concerns FP8 precision. A baseline FP8 attention implementation typically uses per-tensor scaling, where a single scalar is used for the entire tensor. In contrast, \textsc{FlashAttention-3} employs block quantization—using one scalar per block—and incoherent processing, which uses a random orthogonal matrix to spread out outliers. These techniques allowed \textsc{FlashAttention-3} in FP8 to be 2.6$\times$ more accurate than the per-tensor baseline. This demonstrates that the loss of precision inherent in 8-bit formats can be mitigated through intelligent algorithmic design without sacrificing the throughput gains of FP8 Tensor Cores.

# Conclusion: The Future of Long-Context Transformers

The development of \textsc{FlashAttention-3} underscores the importance of aligning software design with the specific asynchronous and low-precision capabilities of modern GPU hardware. By implementing producer-consumer asynchrony through warp-specialization and overlapping the softmax computation with asynchronous GEMMs, the researchers have significantly increased the utilization of the H100's Tensor Cores. The integration of FP8 support, coupled with block quantization and incoherent processing, allows for nearly double the throughput of FP16 while maintaining acceptable numerical stability.

Despite these successes, the researchers identify several areas for future work. These include optimizing the algorithm specifically for LLM inference and expanding the use of persistent kernels into the FP8 implementation to improve performance on smaller sequences and causal masks. Furthermore, there is a need to better understand how these low-precision attention mechanisms affect the stability and quality of large-scale model training.

Ultimately, the ability to compute exact attention faster and more accurately is a fundamental requirement for scaling Transformers to longer contexts. By reducing the bottleneck of the attention layer, \textsc{FlashAttention-3} paves the way for new applications in long-document reasoning, high-resolution multimodal processing, and agent workflows with extended horizons.
