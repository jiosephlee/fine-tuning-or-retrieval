\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### Is QLoRA actually performing 4-bit matrix multiplication?
Question:
I am confused about the distinction between 'storage data type' and 'computation data type' mentioned in the paper. The authors state that the model is quantized to 4-bit, but then they say that whenever a weight tensor is used, it is dequantized to BFloat16 to perform the matrix multiplication. If the actual math is happening in 16-bit, does this mean there is no computational speedup from the 4-bit quantization, and the benefit is strictly related to GPU memory capacity?
Answer:
Your intuition is correct: **QLoRA does not perform 4-bit matrix multiplication**, and therefore, it does not provide a computational speedup through reduced-precision arithmetic.

As the paper explains, there is a strict distinction between the **storage data type** and the **computation data type**. The weights are stored on the GPU in a 4-bit NormalFloat ($\text{NF4}$) format to drastically reduce the memory footprint. However, because performing matrix multiplication directly in 4-bit would lead to significant precision loss and is not natively supported in the same way as 16-bit floats on current hardware, QLoRA employs a "dequantization" step. Whenever a weight tensor $\mathbf{W}^{\text{NF4}}$ is needed for a calculation, it is first converted back into $\text{BFloat16}$ precision. The actual operation $\mathbf{X}^{\text{BF16}} \mathbf{W}^{\text{BF16}}$ is then executed using standard 16-bit floating-point arithmetic.

To put this intuitively, you can think of the 4-bit storage as a compressed archive. You cannot effectively "edit" or "process" the data while it is compressed; you must first "unzip" (dequantize) the weights into a usable format in your working memory (the GPU's compute cores) to perform the math.

Because of this architecture, the primary benefit of QLoRA is **memory capacity**, not computational speed. In fact, the process of constantly dequantizing weights introduces a small amount of computational overhead. However, the authors note that this does not "degrade the runtime" significantly compared to 16-bit baselines. The real breakthrough is that by reducing the memory required for a 65B parameter model from over $780\text{ GB}$ to less than $48\text{ GB}$, QLoRA makes it possible to finetune massive models on a single professional GPU—a task that was previously physically impossible regardless of how fast the computation was.

In the broader context of quantization, it is helpful to distinguish between *quantization for compression* and *quantization for acceleration*. While some techniques (like $\text{INT8}$ or $\text{FP8}$ quantization) aim to use specialized hardware kernels to speed up the math, QLoRA focuses on the former. By utilizing $\text{NF4}$ and Double Quantization, it optimizes the storage of the base model to the theoretical limit, allowing the memory "saved" to be used for the $\text{BFloat16}$ gradients and the Low-Rank Adapters ($\text{LoRA}$), thereby preserving full 16-bit performance.

### What makes NormalFloat (NF4) 'information theoretically optimal'?
Question:
The paper introduces 4-bit NormalFloat (NF4) and claims it is information-theoretically optimal for normally distributed weights. I understand that it uses quantiles of a $N(0, 1)$ distribution to define the bins, but I don't understand why this is superior to standard 4-bit integers (Int4) or floats (FP4). Specifically, how does ensuring each bin has an equal number of values assigned from the input tensor reduce quantization error in practice?
Answer:
The claim that NormalFloat (NF4) is "information-theoretically optimal" stems from its use of quantile quantization specifically tailored to the distribution of pretrained neural network weights. In standard 4-bit integer (Int4) or floating-point (FP4) quantization, the bins—the discrete values that a weight is rounded to—are typically spaced uniformly or according to a fixed logarithmic scale. However, pretrained weights are not uniformly distributed; they typically follow a zero-centered normal distribution $N(0, \sigma)$.

When you apply uniform spacing to a normal distribution, you encounter a significant efficiency problem: because most weights are concentrated near zero and very few exist in the tails, the bins near the mean become "overcrowded" (many different original values are collapsed into one bin), while the bins at the edges are "under-utilized" (few or no values are assigned to them). From an information theory perspective, this is suboptimal because you are wasting the limited representational capacity of 4 bits. You have a limited "budget" of $2^4 = 16$ possible values; to maximize the information retained, each of these 16 values should be used as frequently as possible.

NF4 solves this by defining the bins based on the quantiles of a standard normal distribution $N(0, 1)$. By using the quantile function $Q_X(\cdot)$, NF4 ensures that each quantization bin has an equal probability mass. Intuitively, this means the bins are placed closer together where the data is dense (near zero) and further apart where the data is sparse (at the tails). Because each bin is designed to hold an equal number of values from the input tensor, the quantization error is distributed more evenly across the entire distribution, preventing the massive precision loss that occurs in the "crowded" center of a linear quantization scheme.

Technically, the paper implements this by estimating the $2^k+1$ quantiles of a theoretical $N(0, 1)$ distribution and normalizing them into the range $[-1, 1]$. To handle the practical requirement of having an exact representation of zero—which is critical for quantizing padding or zero-valued elements without error—the authors use an asymmetric approach. They estimate quantiles for the negative and positive ranges separately and unify them, removing the redundant zero to maintain a total of $2^k$ discrete values.

In practice, this means that when a weight tensor is normalized to the $[-1, 1]$ range and quantized using NF4, the resulting 4-bit representation captures the "shape" of the weights far more accurately than Int4 or FP4. By maximizing the entropy of the quantized representation—ensuring no bin is wasted and no bin is overly congested—NF4 minimizes the overall reconstruction error, which the paper demonstrates empirically leads to better zero-shot accuracy and perplexity in LLMs.

### How does the memory saving calculation for Double Quantization work?
Question:
In the Double Quantization section, the authors mention that for a blocksize of 64, the memory footprint of quantization constants is reduced from $32/64 = 0.5$ bits per parameter to $8/64 + 32/(64 \cdot 256) = 0.127$ bits. I'm struggling to follow this math. Why is the second term divided by $64 \cdot 256$, and what exactly does the $8/64$ represent in the context of the second quantization step?
Answer:
To understand the memory saving calculation for Double Quantization (DQ), it is helpful to view the process as a hierarchy of constants where each level reduces the precision of the level above it.

In standard block-wise quantization, the weight tensor $\mathbf{W}$ is divided into blocks of size $B=64$. Each block requires one 32-bit floating-point quantization constant ($c_2^{\text{FP32}}$) to scale the values. As you noted, this creates an overhead of $32/64 = 0.5$ bits per parameter. Double Quantization treats these $c_2^{\text{FP32}}$ constants as a new tensor and quantizes them a second time.

The first term in the equation, $8/64$, represents the new cost of the first-level constants. Instead of storing $c_2$ as 32-bit floats, the authors quantize them into 8-bit floats ($\text{FP8}$). Since there is still one constant for every 64 parameters, the memory footprint for these constants drops from 32 bits to 8 bits per block, resulting in $8/64$ bits per parameter.

The second term, $32/(64 \cdot 256)$, represents the overhead of the second-level quantization constants ($c_1^{\text{FP32}}$). To quantize the $c_2$ constants into 8-bit, the authors again use block-wise quantization. They group the $c_2$ constants into blocks of 256 and assign one 32-bit constant ($c_1$) to each block. Because one $c_1$ constant serves 256 different $c_2$ constants, and each $c_2$ constant in turn serves 64 weights, a single $c_1$ constant effectively covers $256 \times 64$ original weight parameters. Therefore, the 32 bits of the $c_1$ constant are amortized over $64 \cdot 256$ parameters.

When you sum these two components, $8/64 + 32/(64 \cdot 256)$, you get approximately $0.125 + 0.002 = 0.127$ bits per parameter. This demonstrates that by quantizing the constants themselves, the authors reduce the overhead of the quantization scales by nearly $75\%$, saving roughly $0.373$ bits per parameter. This is a crucial optimization for massive models, as saving a fraction of a bit per parameter translates to several gigabytes of saved GPU memory when scaled to 65 billion parameters.

### How does backpropagation work through frozen 4-bit weights?
Question:
The paper states that QLoRA backpropagates gradients through a frozen, 4-bit quantized pretrained model into the LoRA adapters. Since the weights $\mathbf{W}^{NF4}$ are frozen and quantized (which is a non-differentiable operation), I'm confused about how the gradient $\frac{\partial E}{\partial \mathbf{L}_i}$ is calculated. Does the gradient simply flow through the dequantized $\mathbf{W}^{BF16}$ as if it were a standard constant weight, or is there something special about the backward pass in the CUDA kernels?
Answer:
To understand how backpropagation works in QLoRA, it is first necessary to distinguish between the **storage data type** and the **computation data type**. 

As described in the paper, QLoRA stores the pretrained weights in a 4-bit NormalFloat ($\mathbf{W}^{\text{NF4}}$) format to save memory. However, it does not perform matrix multiplications directly in 4-bit. Instead, whenever a weight tensor is needed for a calculation, the model performs a "double dequantization" step to convert those weights back into BFloat16 ($\mathbf{W}^{\text{BF16}}$). 

The forward pass for a linear layer is expressed as:
$$\mathbf{Y}^{\text{BF16}} = \mathbf{X}^{\text{BF16}} \text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{NF4}}) + \mathbf{X}^{\text{BF16}}\mathbf{L}^{\text{BF16}}_1\mathbf{L}^{\text{BF16}}_2$$

In this equation, the term $\text{doubleDequant}(\dots)$ effectively produces $\mathbf{W}^{\text{BF16}}$. Because the base model weights are **frozen**, they act as constants during the training process. 

Your confusion regarding the non-differentiable nature of quantization is a common one, but it applies to the *quantization* process (mapping a high-precision number to a low-precision bin). In QLoRA, we are not differentiating through the quantization process itself; rather, we are differentiating through the **dequantized** weights. 

During the backward pass, the goal is to calculate the gradient for the LoRA adapters, $\frac{\partial E}{\partial \mathbf{L}_i}$. According to the chain rule, this requires the gradients to flow through the linear operation. Since the weights $\mathbf{W}^{\text{BF16}}$ are treated as constants, the gradient simply flows through them as if they were any other fixed 16-bit weight matrix in a standard neural network. The paper explicitly states that the calculation of the derivatives is performed in BFloat16 precision, using the weights converted from storage $\mathbf{W}^{\text{NF4}}$ to computation $\mathbf{W}^{\text{BF16}}$.

In short: there is nothing "special" happening in the CUDA kernels to bypass the non-differentiability of quantization. Instead, the model avoids the problem entirely by dequantizing the weights to a differentiable format (BFloat16) and treating them as constants. The gradients flow through the $\mathbf{W}^{\text{BF16}}$ "constant" to reach and update the trainable $\mathbf{L}_i$ adapters.

### Why is the number of adapter layers more critical than the rank $r$?
Question:
In Section 4, the authors find that the most critical LoRA hyperparameter for matching 16-bit performance is the number of adapters used (applying them to all linear layers), while the projection dimension $r$ has little effect. This is surprising to me because the rank $r$ usually determines the capacity of the adapter. Why would adding adapters to more layers be more effective for recovering quantization loss than increasing the rank of a few adapters?
Answer:
The intuition that the rank $r$ determines the capacity of an adapter is generally correct for standard task adaptation. However, in the context of QLoRA, the goal is not just to adapt the model to a new task, but specifically to recover the performance loss induced by 4-bit quantization. Because quantization is applied globally across all weights in the model, the resulting precision errors are distributed across every single linear layer.

When you increase the rank $r$ of a few adapters (such as only in the query and value projections), you are increasing the "expressive power" or the capacity of the update for those specific layers. However, this does nothing to address the quantization errors occurring in the MLP layers, the key projections, or the output projections. Essentially, you are making a few "patches" in the network very thick, while leaving the rest of the model's weights degraded by quantization.

By instead increasing the number of adapter layers—applying them to all linear transformer block layers—you are providing the model with a mechanism to correct quantization errors throughout the entire architecture. This "breadth" of coverage is more critical than the "depth" of capacity at any single point because the quantization loss is a systemic issue affecting the whole network. The authors find that this global coverage is the primary requirement for matching 16-bit performance, while the specific value of $r$ becomes secondary.

From a practical standpoint, the paper justifies this approach by analyzing the memory footprint. In large language models, the majority of GPU memory is consumed by the base model weights and the activation gradients, not the adapter parameters themselves. For a 7B model, the LoRA weights might only take up 26 MB, while the input gradients are significantly more memory-intensive. Because the marginal cost of adding more adapters is so low relative to the total memory usage, it is far more efficient to distribute a small amount of capacity across all layers than to concentrate a large amount of capacity in only a few.
