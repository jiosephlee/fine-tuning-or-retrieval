\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Why use an LLM for feature engineering instead of direct end-to-end prediction?
Question:
I'm reading the introduction and the abstract of the FeatLLM paper. I understand that they are using an LLM to generate rules, which then become binary features for a linear model. However, I'm confused as to why this is better than simply asking the LLM to predict the class for each sample directly (like in the 'In-context learning' baseline). If the LLM is capable of reasoning about the features to create rules, why can't it just perform that reasoning for every individual sample?
Answer:
While it may seem intuitive to let an LLM perform the final classification since it possesses the reasoning capabilities to generate the rules, doing so introduces several practical and theoretical bottlenecks that $\textsf{FeatLLM}$ is specifically designed to solve.

The most immediate concern is inference efficiency and computational cost. In an end-to-end "In-context learning" setup, you must send a query to the LLM for every single test sample. For large datasets, this is prohibitively expensive and slow. By shifting the LLM's role to feature engineering, $\textsf{FeatLLM}$ uses the LLM only during a "setup" phase to derive general rules. At inference time, the LLM is no longer needed; the system simply evaluates whether a sample satisfies the pre-generated rules and passes these binary values through a simple linear model. This reduces the inference latency from the speed of a massive language model to the speed of a basic dot product operation.

Another critical limitation is the LLM's context window. Tabular datasets often have a high number of features (e.g., the "Communities" dataset mentioned in the paper). When you serialize every feature and its value for every sample into a prompt, you can easily exceed the maximum token limit or encounter the "lost in the middle" phenomenon where the model ignores parts of a lengthy prompt. $\textsf{FeatLLM}$ overcomes this by using feature bagging, allowing the LLM to reason over smaller subsets of features to generate rules, which are then aggregated via an ensemble.

From a learning perspective, $\textsf{FeatLLM}$ separates the "discovery" of knowledge from the "weighting" of that knowledge. When an LLM predicts a class directly, it is performing a heuristic mapping based on the few examples provided. In contrast, $\textsf{FeatLLM}$ uses the LLM to propose a set of candidate rules $\mathbf{z}_k^i \in \{0, 1\}^R$ and then employs a downstream linear model to optimize the weights $\mathbf{w}_k$ using a cross-entropy loss. This is represented by the logit calculation:
$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$
By training these weights $\mathbf{w}_k$ on the available labeled samples, the model can empirically determine which rules are actually predictive and which are noise. This makes the system significantly more robust to spurious correlations; while a direct LLM prompt might be misled by a coincidental pattern in a few-shot example, the linear model in $\textsf{FeatLLM}$ can effectively "downweight" an irrelevant rule during the tuning process.

### How does FeatLLM convert natural language rules into binary features?
Question:
In Section 3.2, the paper mentions that LLM outputs can be syntactically noisy (e.g., using 'greater than' instead of '$>$'). To fix this, they use the LLM again to generate Python code that is executed via `exec()`. I'm struggling to understand the exact flow here: does the LLM generate a unique Python function for every single rule it creates, or does it generate one master script for all rules? How does the generated code know which columns in the actual tabular dataset correspond to the natural language feature names?
Answer:
The conversion of natural language rules into binary features in \textsf{FeatLLM} is a two-stage process designed to bridge the gap between the flexible, often "noisy" linguistic output of an LLM and the rigid requirements of programmatic data processing.

First, the LLM generates rules in natural language based on a combination of its prior knowledge and the provided few-shot examples. However, because LLMs may use inconsistent phrasing—for example, saying "greater than" in one rule and using the symbol "$>$" in another—direct parsing using regular expressions or hard-coded logic would be fragile. To solve this, the authors use the LLM as a "translator." They provide the LLM with a second prompt containing the natural language rules, a specified function name, and descriptions of the expected inputs and outputs. The LLM then generates Python code that implements the logic of these rules. This generated code is then executed via Python's `exec()` function to transform the original tabular data into a binary vector $\mathbf{z}_k^i \in \{0, 1\}^R$, where each element indicates whether a sample $\mathbf{x}^i$ satisfies a specific rule for class $k$.

Regarding the structure of the code, the paper indicates that the LLM is prompted with a "function name" and the "inferred rules," suggesting that the LLM generates a Python function (or a cohesive block of code) that encapsulates the logic for the rules. Rather than creating a unique separate script for every single individual rule, the LLM is asked to produce code that can process the data based on the set of rules it just derived.

The mapping between natural language feature names and the actual tabular columns is handled by the consistency of the prompt. In the "Basic information description" phase, the framework provides the LLM with the natural language feature names $F = \{f_j\}_{j=1}^{d}$ and their definitions. When the LLM is tasked with writing the Python code in the second stage, it uses these same feature names as the variables or keys within the code. Because the Python code is executed in an environment where the tabular data (such as a DataFrame) uses these same names as column headers, the generated code can correctly reference the data. In essence, the LLM maintains a semantic link between the feature name $f_j$ and the corresponding column in the dataset $\mathcal{D}$ across both the rule-generation and code-generation steps.

### What is the purpose of projecting weights into a positive subspace in the likelihood inference?
Question:
In Equation 2, the authors compute the logit as $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$. I understand that $\max(\mathbf{w}_k, 0)$ ensures the weights are non-negative. But conceptually, why is this necessary? If a rule generated by the LLM turns out to be a negative indicator for a class (i.e., if the rule is true, the sample is *less* likely to be in that class), wouldn't a negative weight $\mathbf{w}_k$ be the mathematically correct way to represent that?
Answer:
The projection of weights into a positive subspace using $\max(\mathbf{w}_k, 0)$ is a design choice that aligns the mathematical optimization with the conceptual goal of the $\textsf{FeatLLM}$ framework. To understand why this is necessary, we must look at how the features $\mathbf{z}_k^i$ are generated.

Unlike standard linear models that operate on raw data, $\textsf{FeatLLM}$ uses an LLM to specifically extract "decisive rules" that identify a particular class. When the LLM is prompted to generate rules for class $k$, it is essentially being asked to find positive indicators—conditions that, if true, suggest the sample belongs to that class. Therefore, the resulting binary features $\mathbf{z}_k^i$ are not generic variables; they are intended to be evidence for the existence of class $k$.

If the model allowed negative weights $\mathbf{w}_k$, a rule that was designed to be a positive indicator for a class could actually decrease the likelihood of that class during the training phase. This would create a conceptual contradiction: the LLM identifies a rule as a "criterion" for a class, but the downstream model treats it as evidence against that class. By enforcing $\mathbf{w}_k \ge 0$, the authors ensure that any rule satisfying $\mathbf{z}_k^i = 1$ can only ever increase (or leave unchanged) the logit for class $k$, maintaining the logical consistency between the "feature engineering" phase and the "inference" phase.

Regarding your point about negative indicators: in a multi-class setup, if a specific condition is a strong negative indicator for class $A$, it is likely a strong positive indicator for some other class $B$. In the $\textsf{FeatLLM}$ framework, that relationship is captured by the LLM generating a rule for class $B$ rather than a "negative rule" for class $A$. Because the final probabilities are determined by a $\text{Softmax}$ over the logits of all classes, an increase in the logit for class $B$ naturally decreases the relative probability of class $A$.

From a technical perspective, this projection also acts as a form of regularization. If the LLM generates a "noisy" or irrelevant rule that does not actually correlate with the target class in the few-shot training samples, the optimizer will attempt to push $\mathbf{w}_k$ into negative territory to penalize that feature. The $\max(\mathbf{w}_k, 0)$ operation clips these weights to zero, effectively filtering out uninformative rules and preventing them from introducing noise into the prediction. This ensures that the final likelihood is a weighted sum of positive evidence, which is a more robust approach in low-shot regimes where the model is highly prone to overfitting spurious correlations.

### How does feature bagging specifically solve the LLM prompt size limitation?
Question:
The paper states that they use bagging to select a subset of features or instances for each trial to mitigate the challenge of excessive prompt size. I'm confused about the connection here. If the dataset has too many features to fit into the LLM's context window, and they only show the LLM a subset of features in each trial, doesn't that mean the LLM is missing critical information for each individual rule-set? How does ensembling these 'incomplete' views eventually result in a more robust model than if the LLM had seen everything at once?
Answer:
The connection between feature bagging and the prompt size limitation lies in the trade-off between the LLM's context window and the dimensionality of the tabular data. In tabular learning, if a dataset has a very large number of features $d$, serializing all feature names, descriptions, and example values into a single prompt will exceed the maximum token limit allowed by the LLM (the context window). When this happens, the model either fails to process the request or suffers a decline in performance due to the "lost in the middle" phenomenon, where LLMs struggle to attend to information in excessively long prompts.

Feature bagging solves this by randomly selecting a subset of features and instances for each trial. While you are correct that the LLM is presented with an "incomplete" view of the data in any single trial, the framework does not rely on a single set of rules. Instead, it treats each trial as the creation of a "weak learner." In one trial, the LLM might identify rules based on a subset of features $\{f_1, \dots, f_{10}\}$; in the next trial, it might see $\{f_{11}, \dots, f_{20}\}$. Because the process is repeated $T$ times, the collective ensemble eventually captures the critical relationships across the entire feature space.

The robustness of this approach comes from the ensembling process. For each trial $t$, the LLM generates a set of binary features $\mathbf{z}_k^i$, and a linear model learns weights $\mathbf{w}_k$ to estimate the class likelihood. The final prediction is the average of the probabilities $\mathbf{p}^i$ derived from all $T$ trials. This is conceptually similar to a Random Forest, where individual decision trees are trained on bootstrapped subsets of data and features; no single tree sees the whole picture, but the averaged consensus of the forest is far more accurate and less prone to overfitting than any individual tree.

Furthermore, the paper notes that this strategy leverages the LLM's self-consistency. Rules that are consistently inferred across different random subsets are more likely to be grounded in actual causal relationships rather than spurious correlations. By breaking the problem into many small, prompt-sized chunks, $\textsf{FeatLLM}$ transforms the limitation of the context window into an advantage of diversity, ensuring that the final model is a robust aggregation of multiple specialized "views" of the data.

### Why split rule generation into a 'prior knowledge' step and an 'example-based' step?
Question:
In Section 3.1, the reasoning instruction is divided into two steps: first, inferring causal relationships using general knowledge without examples, and second, deriving rules using those examples. I'm trying to understand the necessity of this split. If the examples are already provided in the prompt, why not just ask the LLM to generate the rules based on both the general knowledge and the examples simultaneously? What specifically does the 'first step' achieve that prevents the model from identifying spurious correlations?
Answer:
The split between the "prior knowledge" step and the "example-based" step in $\textsf{FeatLLM}$ is primarily a defense mechanism against overfitting and spurious correlations, which are chronic issues in few-shot learning. In a low-shot regime, where only a handful of labeled samples are available, there is a high probability that an irrelevant feature might coincidentally align with the target label across those few examples. If an LLM is asked to generate rules by looking at the general knowledge and the examples simultaneously, it may succumb to these "spurious correlations," treating a random coincidence in the small sample as a decisive rule.

By forcing the model to first infer causal relationships and tendencies using only its prior knowledge (Step 1), the framework establishes a logical anchor based on general domain expertise before the model ever sees the specific data points. For instance, if the task involves predicting heart failure, the model first identifies that "age" or "blood pressure" are generally relevant features. When it moves to the second step—deriving specific rules from examples—it does so through the lens of this pre-established causal logic. This ensures that the model prioritizes features that are both statistically present in the examples and conceptually relevant to the task, effectively filtering out uninformative columns that might otherwise seem important due to sheer coincidence.

This design is grounded in the paper's empirical findings. In the ablation studies, removing this first reasoning step ($\textsf{-Reasoning}$) led to a measurable drop in AUC, particularly when the number of shots was small, indicating that the prior knowledge step is most critical when data is scarcest. Furthermore, when the authors tested the model's robustness by adding completely irrelevant columns from a different dataset to the Heart dataset, $\textsf{FeatLLM}$ showed significantly less performance degradation than the baselines. This is because the model's insistence on prior-knowledge-driven reasoning prevented it from generating rules based on those noisy, irrelevant columns. Essentially, this two-step process acts as a conceptual filter, ensuring that the resulting binary features $\mathbf{z}_k^i$ are derived from meaningful patterns rather than random noise.
