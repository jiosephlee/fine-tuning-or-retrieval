\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Stop Asking LLMs for Answers—Ask Them for the Rules Instead

Tabular data is the backbone of most real-world applications, from healthcare diagnostics to financial risk assessment. While Large Language Models (LLMs) have shown an impressive ability to reason through complex problems, using them for tabular learning has historically been a challenge. Most existing approaches treat LLMs as "black-box predictors," where you serialize a row of data into text and ask the model for a prediction.

This approach has three major flaws: it is computationally expensive (requiring an LLM query for every single sample), it often requires resource-intensive fine-tuning, and it struggles with "prompt bloat"—when a table has too many columns, the prompt becomes too long for the model to handle effectively.

The researchers behind $\textsf{FeatLLM}$ propose a fundamental shift in philosophy. Instead of asking the LLM to predict the label for every sample, why not ask the LLM to act as an expert feature engineer?

## From Predictor to Feature Engineer

The core idea of $\textsf{FeatLLM}$ is to extract the "criteria" or rules that an LLM uses to make a decision. For example, if the task is to predict heart failure, instead of asking "Does this specific patient have heart failure?", $\textsf{FeatLLM}$ asks the LLM to generate a set of decisive rules—such as "If age $> 65$ and blood pressure is high, the likelihood of heart failure increases."

Once these rules are generated, they are transformed into binary features (0 or 1) for every sample in the dataset. This shifts the LLM's role to the preprocessing stage. At inference time, you no longer need to call an expensive API; you simply pass these binary features through a lightweight machine learning model.

## How $\textsf{FeatLLM}$ Works

The framework follows a structured pipeline to ensure the rules generated are high-quality and grounded in both general knowledge and the provided data.

### 1. Structured Rule Generation
To prevent the LLM from spotting "spurious correlations" (random patterns in a small dataset that aren't actually meaningful), $\textsf{FeatLLM}$ uses a two-step reasoning process:
*   **Step 1: Prior Knowledge Extraction.** The LLM is first asked to infer the general relationship between features and the target based on its internal world knowledge, without looking at the specific examples.
*   **Step 2: Rule Deduction.** The LLM then combines that prior knowledge with a few-shot set of labeled examples to derive a fixed number of specific rules for each class.

### 2. Automated Parsing
Rules generated in natural language (e.g., "Age is greater than 60") are hard to compute. $\textsf{FeatLLM}$ solves this by using the LLM again to write the Python code necessary to parse these rules. This code is then executed to transform the original tabular data into a set of binary indicators.

### 3. Learning Rule Importance
Not all rules are created equal. To determine which rules are actually predictive, $\textsf{FeatLLM}$ fits a simple linear model without a bias term. For a sample $i$ and class $k$, the logit is computed as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

Here, $\mathbf{z}_k^i$ represents the binary features generated by the rules, and $\mathbf{w}_k$ are trainable weights. By projecting the weights into a positive subspace ($\max(\mathbf{w}_k, 0)$), the model ensures that the discovered features only increase the likelihood of a class, mirroring how human-defined rules typically work.

## Overcoming Prompt Limits with Bagging

One of the most practical contributions of $\textsf{FeatLLM}$ is its use of bagging and ensembling. To handle datasets with a massive number of columns that would exceed an LLM's context window, the framework randomly selects subsets of features and instances across multiple trials. 

By generating different sets of rules across these trials and averaging the final probabilities, the system becomes more robust. If the LLM generates a few incorrect rules in one trial, the consensus from other trials corrects the error.

## Why This Matters

The results across 13 different datasets demonstrate that $\textsf{FeatLLM}$ significantly outperforms other LLM-based tabular methods like TabLLM and STUNT in few-shot settings. More importantly, it solves the "production" problem:

*   **Low Latency:** Inference is performed by a simple linear model, not a giant LLM.
*   **No Fine-Tuning:** It only requires API-level access via in-context learning.
*   **Robustness:** It is far less likely to be fooled by irrelevant "noisy" columns than traditional models, because it relies on a combination of prior knowledge and data.

By treating the LLM as a consultant who provides the rules rather than a calculator that provides the answer, $\textsf{FeatLLM}$ makes the power of large-scale reasoning practical for tabular data.
