# Stop Asking LLMs for Answers—Ask Them for the Rules Instead

Tabular data is the backbone of most real-world applications, from healthcare diagnostics to financial risk assessment. While Large Language Models (LLMs) have shown an impressive ability to reason through complex problems, using them for tabular learning has historically been a challenge. Most existing approaches treat LLMs as "black-box predictors," where you serialize a row of data into text and ask the model for a prediction.

This approach has three major flaws: it is computationally expensive (requiring an LLM query for every single sample), it often requires resource-intensive fine-tuning, and it struggles with "prompt bloat"—when a table has too many columns, the prompt becomes too long for the model to handle effectively.

The researchers behind $\textsf{FeatLLM}$ propose a fundamental shift in philosophy. Instead of asking the LLM to predict the label for every sample, why not ask the LLM to act as an expert feature engineer?

## From Predictor to Feature Engineer

The core idea of $\textsf{FeatLLM}$ is to extract the "criteria" or rules that an LLM uses to make a decision. For example, if the task is to predict heart failure, instead of asking "Does this specific patient have heart failure?", $\textsf{FeatLLM}$ asks the LLM to generate a set of decisive rules—such as "If age $> 65$ and blood pressure is high, the likelihood of heart failure increases."

Once these rules are generated, they are transformed into binary features (0 or 1) for every sample in the dataset. This shifts the LLM's role to the preprocessing stage. At inference time, you no longer need to call an expensive API; you simply pass these binary features through a lightweight machine learning model.

## How $\textsf{FeatLLM}$ Works

The framework follows a structured pipeline to ensure the rules generated are high-quality and grounded in both general knowledge and the provided data.

### 1. Structured Rule Generation
To prevent the LLM from spotting "spurious correlations" (random patterns in a small dataset that aren't actually meaningful), $\textsf{FeatLLM}$ uses a two-step reasoning process:
*   **Step 1: Prior Knowledge Extraction.** The LLM is first asked to infer the general relationship between features and the target based on its internal world knowledge, without looking at the specific examples.
*   **Step 2: Rule Deduction.** The LLM then combines that prior knowledge with a few-shot set of labeled examples to derive a fixed number of specific rules for each class.

### 2. Automated Parsing
Rules generated in natural language (e.g., "Age is greater than 60") are hard to compute. $\textsf{FeatLLM}$ solves this by using the LLM again to write the Python code necessary to parse these rules. This code is then executed to transform the original tabular data into a set of binary indicators.

### 3. Learning Rule Importance
Not all rules are created equal. To determine which rules are actually predictive, $\textsf{FeatLLM}$ fits a simple linear model without a bias term. For a sample $i$ and class $k$, the logit is computed as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

Here, $\mathbf{z}_k^i$ represents the binary features generated by the rules, and $\mathbf{w}_k$ are trainable weights. By projecting the weights into a positive subspace ($\max(\mathbf{w}_k, 0)$), the model ensures that the discovered features only increase the likelihood of a class, mirroring how human-defined rules typically work.

## Overcoming Prompt Limits with Bagging

One of the most practical contributions of $\textsf{FeatLLM}$ is its use of bagging and ensembling. To handle datasets with a massive number of columns that would exceed an LLM's context window, the framework randomly selects subsets of features and instances across multiple trials. 

By generating different sets of rules across these trials and averaging the final probabilities, the system becomes more robust. If the LLM generates a few incorrect rules in one trial, the consensus from other trials corrects the error.

## Why This Matters

The results across 13 different datasets demonstrate that $\textsf{FeatLLM}$ significantly outperforms other LLM-based tabular methods like TabLLM and STUNT in few-shot settings. More importantly, it solves the "production" problem:

*   **Low Latency:** Inference is performed by a simple linear model, not a giant LLM.
*   **No Fine-Tuning:** It only requires API-level access via in-context learning.
*   **Robustness:** It is far less likely to be fooled by irrelevant "noisy" columns than traditional models, because it relies on a combination of prior knowledge and data.

By treating the LLM as a consultant who provides the rules rather than a calculator that provides the answer, $\textsf{FeatLLM}$ makes the power of large-scale reasoning practical for tabular data.



# The Small Data Miracle: High-Performance AI with Only a Few Examples

In the world of machine learning, tabular data—the kind you find in spreadsheets and SQL databases—is everywhere. However, training accurate models on this data typically requires thousands of labeled examples. When you only have a handful of samples, traditional models often struggle or overfit, capturing "spurious correlations" rather than actual patterns.

This is where the "small data" challenge becomes a bottleneck, especially in fields like healthcare or finance, where labeling data is expensive or difficult. A recent paper introduces **FeatLLM**, a framework that turns Large Language Models (LLMs) into expert feature engineers to solve this exact problem. By leveraging the vast prior knowledge embedded in LLMs, FeatLLM can achieve high performance in "few-shot" scenarios, often outperforming traditional models that have significantly more data to learn from.

## Shifting the Role of the LLM

Most existing attempts to use LLMs for tabular data treat the model as a black-box predictor. They serialize a row of data into a sentence and ask the LLM to predict the label. While this can work, it is computationally expensive, slow at inference time, and often fails when a table has too many columns to fit into the model's prompt window.

FeatLLM takes a fundamentally different approach. Instead of asking the LLM for a final prediction, the framework uses the LLM to perform **feature engineering**. The LLM analyzes a few examples and its own internal "common sense" to derive a set of decisive rules—criteria that determine whether a sample belongs to a specific class. Once these rules are established, they are converted into binary features, and a simple, lightweight machine learning model is used for the actual predictions. This means the LLM is only needed during the initial setup, not for every single prediction, drastically reducing latency and cost.

## How FeatLLM Works

The magic of FeatLLM lies in its structured reasoning process, which mimics how a human expert would analyze a problem. The framework guides the LLM through two primary steps:

1.  **Prior Knowledge Extraction**: The LLM first considers the task description and the features to infer general causal relationships. For example, if the task is predicting heart failure, the LLM might rely on its pre-training to know that age and blood pressure are generally significant risk factors.
2.  **Rule Deduction**: The LLM then combines this general knowledge with a few labeled examples to create specific, actionable rules. These rules are formulated as conditions (e.g., "if age $> 65$ and blood pressure is high").

To turn these natural language rules into something a computer can process, FeatLLM uses the LLM again to write a small piece of Python code. This code is executed to transform the original tabular data into binary features—essentially a series of $0$s and $1$s indicating whether a sample satisfies each rule.

## Learning from Rules

Once the rules are converted into binary features, FeatLLM uses a simple linear model to estimate the likelihood of each class. Since not all rules are equally important, the framework learns a weight $\mathbf{w}_k$ for each feature. The logit for a class $k$ is calculated as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

Here, $\mathbf{z}_k^i$ represents the binary features for sample $i$ and class $k$. By ensuring the weights are non-negative via $\max(\mathbf{w}_k, 0)$, the model ensures that a rule satisfying a class condition only increases (or maintains) the likelihood of that class, never decreasing it. The final class probability is then determined using a softmax function:

$$\mathbf{p}^i = \text{Softmax}({[\text{logit}_{1}^i, ..., \text{logit}_{c}^i]})$$

## Robustness through Bagging and Ensembling

To handle datasets with a massive number of features and to prevent overfitting, FeatLLM employs **feature bagging and ensembling**. Instead of creating one giant prompt that might exceed the LLM's limits, the framework repeatedly selects subsets of features and samples to generate various sets of rules. 

By averaging the predictions across multiple trials, the model becomes more robust. If the LLM generates a "noisy" or incorrect rule in one trial, the correct rules from other trials compensate for it. This ensemble approach allows FeatLLM to maintain high accuracy even on datasets with over 100 attributes.

## Results: Doing More with Less

The results across 13 different tabular datasets are impressive. FeatLLM consistently outperforms or matches contemporary few-shot baselines. One of the most striking findings is that FeatLLM, using only **4 labeled shots**, can achieve performance comparable to traditional tabular baselines that require **32 shots**.

Furthermore, FeatLLM is remarkably resilient to "spurious correlations." In experiments where irrelevant columns were added to the data, FeatLLM suffered the least performance degradation. This is because the model relies on prior knowledge to decide which features are actually meaningful, effectively ignoring the noise that often tricks traditional machine learning models.



# Cutting the AI Bill: How FeatLLM Solves the Cost and Latency of LLM Inference

For practitioners working with tabular data, integrating Large Language Models (LLMs) often presents a daunting trade-off. On one hand, LLMs possess immense prior knowledge that can significantly boost performance in few-shot learning scenarios. On the other hand, the standard "end-to-end" approach—where every single row of data is serialized into text and sent as a prompt to an LLM—is computationally expensive, slow, and often hits context window limits.

The research paper "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning" introduces **FeatLLM**, a framework that fundamentally changes this workflow. Instead of using the LLM as a predictor, FeatLLM uses the LLM as an automated feature engineer.

## The Shift: From Prediction to Feature Engineering

Most existing LLM-based tabular learners treat the model as a black box: you input a sample, and the model outputs a prediction. This requires at least one API call per sample during inference, leading to high latency and soaring costs.

FeatLLM shifts the LLM's role. It asks the LLM to identify the "criteria" or rules that define a class based on its prior knowledge and a few provided examples. Once these rules are generated, they are converted into binary features. At inference time, you no longer need the LLM; you simply use a lightweight machine learning model to process these binary features.

## How FeatLLM Works

The FeatLLM pipeline consists of three primary stages: rule extraction, parsing, and likelihood inference.

### 1. Rule Extraction via Structured Reasoning
To ensure the LLM generates high-quality rules, FeatLLM employs a two-step reasoning process. First, the LLM is prompted to infer the general causal relationship between features and the target task using its internal prior knowledge. Second, it uses a few-shot example set and the insights from the first step to deduce specific, decisive rules for each class. This structured approach prevents the model from latching onto spurious correlations in irrelevant columns.

### 2. Parsing Rules into Code
Because LLMs generate rules in natural language, they can be noisy or syntactically inconsistent. FeatLLM solves this by using the LLM again to translate these natural language rules into executable Python code. This code is then run using Python's `exec()` function to transform the raw tabular data into a set of binary features, $\mathbf{z}_k^i \in \{0, 1\}^R$, where $R$ is the number of rules per class.

### 3. Inferring Class Likelihood
With the binary features created, the framework uses a simple linear model to estimate the probability of a sample belonging to a class. The logit for class $k$ is calculated as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

The weights $\mathbf{w}_k$ are trained using a small number of labeled samples to determine the importance of each rule. By projecting these weights into a positive subspace ($\max(\mathbf{w}_k, 0)$), the model ensures that a rule can only increase (or leave neutral) the likelihood of a class, never decrease it. The final class probabilities are then derived via a Softmax function.

## Overcoming Prompt Limits with Bagging and Ensembles

A common failure point for LLMs in tabular learning is the "lost in the middle" phenomenon or simply exceeding the token limit when a dataset has hundreds of features. FeatLLM addresses this by implementing feature bagging and ensembling.

By randomly selecting subsets of features or instances for different trials, the framework keeps prompt sizes manageable. It then averages the predictions from multiple trained models. This not only mitigates prompt size constraints but also increases robustness; if the LLM generates a faulty rule in one trial, the correct rules from other trials compensate for it.

## Real-World Impact: Cost and Performance

The results across 13 diverse datasets demonstrate that FeatLLM is not just more efficient, but often more accurate. Notably, FeatLLM using only 4 shots can achieve performance comparable to conventional tabular baselines that require 32 shots.

From a practitioner's perspective, the efficiency gains are the most striking. In tests on the "Adult" dataset, FeatLLM's inference time was comparable to traditional ML methods (like Logistic Regression or Random Forest), whereas other LLM-based approaches suffered from massive latency. By eliminating the need for per-sample API queries during deployment, FeatLLM makes the power of LLM prior knowledge viable for production environments where latency and budget are critical constraints.



# Taming the Table: Overcoming Prompt Limits and Noisy Data

Tabular learning is a cornerstone of real-world AI applications, from healthcare diagnostics to financial risk assessment. While Large Language Models (LLMs) possess immense prior knowledge that could benefit these tasks, applying them directly to tabular data is challenging. Traditional end-to-end approaches—where a model processes every single sample via an LLM—are computationally expensive and often crash when faced with "wide" tables that exceed the LLM's context window.

To solve these issues, a new framework called $\textsf{FeatLLM}$ shifts the role of the LLM. Instead of acting as the final predictor, the LLM serves as an automated feature engineer. It identifies the "criteria" or rules that distinguish different classes and generates a set of binary features. These features are then fed into a simple downstream machine learning model, drastically reducing inference latency and overcoming the limitations of prompt size.

## Handling Massive Tables via Bagging and Ensembling

One of the primary hurdles in LLM-based tabular learning is the context window. When a dataset contains hundreds of attributes, serializing that data into a text prompt often exceeds the maximum token limit or causes a decline in model performance. $\textsf{FeatLLM}$ addresses this through a combination of feature bagging and ensembling.

Instead of attempting to pass every feature into a single prompt, the framework employs bagging to select subsets of features and instances for each trial. By repeatedly executing the rule-generation process across multiple trials, $\textsf{FeatLLM}$ creates a diverse set of "weak learners." This approach allows the framework to handle datasets with a large number of features that would otherwise be infeasible for an LLM to process at once.

The final prediction is made by averaging the class probabilities across these trials. This ensemble method provides two key advantages: it mitigates the impact of any single incorrect rule generated by the LLM (leveraging self-consistency) and ensures that the model maintains robust performance even when no single trial could cover the entire feature set.

## Filtering Spurious Correlations with Structured Reasoning

In few-shot learning, models are prone to capturing "spurious correlations"—patterns in the data that appear predictive but are actually irrelevant noise. This is especially dangerous in tabular data where a few labeled samples might suggest a relationship between a target and a random, uninformative column.

$\textsf{FeatLLM}$ combats this by guiding the LLM through a structured, two-step reasoning process:

1.  **Prior Knowledge Extraction:** The LLM is first asked to infer the causal relationship or general tendency between features and the target based solely on its internal prior knowledge, without looking at the provided examples.
2.  **Rule Deduction:** Only after establishing this general understanding does the LLM use the few-shot examples to deduce specific, decisive rules for each class.

By forcing the model to rely on common sense and domain knowledge first, the framework filters out uninformative features. Experimental results demonstrate that this method is significantly more robust against noise; when irrelevant columns were intentionally added to a dataset, $\textsf{FeatLLM}$ showed the least performance degradation compared to other baselines, as the LLM refused to generate rules based on those irrelevant columns.

## From Natural Language Rules to Class Likelihood

Once the LLM generates rules in natural language, they must be converted into a format a machine learning model can use. $\textsf{FeatLLM}$ leverages the LLM again to parse these noisy text rules into executable Python code, creating binary features $\mathbf{z}_k^i \in \{0, 1\}^R$ for each sample $\mathbf{x}^i$ and class $k$.

To estimate the final class likelihood, the framework uses a linear model without bias. The logit for a class is computed as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

The weights $\mathbf{w}_k$ are trained using a few-shot set to determine the importance of each rule. By projecting these weights into a positive subspace using the $\max(\cdot, 0)$ function, the framework ensures that the features generated by the LLM only increase (or maintain) the likelihood of a class, preventing the model from incorrectly penalizing a class based on a generated rule. The final probability $\mathbf{p}^i$ is then derived via a $\text{Softmax}$ operation across all classes.

By decoupling feature engineering from inference, $\textsf{FeatLLM}$ provides a path toward high-performance, data-efficient tabular learning that is both computationally sustainable and robust to the noise of real-world data.
