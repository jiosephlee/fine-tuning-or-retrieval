\title{A Textbook about the Paper: FeatLLM}

Chapter 6: From Natural Language Rules to Executable Features

# Challenges of parsing free-form text: syntactic variability and normalization
When a large language model (LLM) produces rules in natural language, those rules are expressive and human-readable, but they are seldom formatted in a way that a downstream program can directly execute. The FeatLLM paper highlights two concrete sources of difficulty. First, there is syntactic variability: the same logical condition can be expressed in many ways. For example, a numeric comparison might appear as the symbol "$>$" in one rule and as the phrase "greater than" in another. Categorical membership can be written as "is one of {A, B}" or as "belongs to {A, B}". Second, there is normalization ambiguity: the LLM may vary how it spells or punctuates categories, how it writes thresholds (e.g., ">= 5" versus "at least five"), or how it composes logical operators (e.g., using "and/or", mixing English conjunctions with symbols, or nesting conditions).

These variations make naive string-based parsing brittle. If a parsing routine expects a fixed token like "$>$" but the LLM outputs "greater than", the parser will fail or misinterpret the rule. Even with constrained response templates, the authors observed "noisy syntactic changes" and therefore treat parsing as a nontrivial problem. The paper therefore motivates treating rule-to-code conversion as a two-stage problem: (1) constrain the LLM's rule generation so that outputs follow a predictable schema, and (2) use the LLM itself to convert the (still somewhat variable) natural-language rules into simple executable code. This approach shifts the burden of normalization to the model that produced the rules and takes advantage of the LLM's strong ability to interpret varied natural-language phrasing.

# LLM-assisted code generation: function specs, inputs/outputs, and rule text as context
Rather than attempting to write a general-purpose natural-language parser by hand, FeatLLM uses the LLM again to perform the translation from rule text to executable code. The prompting strategy for this step is deliberate: the code-generation prompt includes a clear function specification and the necessary context so the LLM can produce reliable, runnable code.

Concretely, the prompt provided to the LLM for parsing contains the inferred rules (the natural-language rules produced in the previous prompt), a function name, and an explicit description of the function inputs and outputs. The input description tells the model what form the tabular data will have (for example, a row represented as a mapping from feature names to values, or an array with documented column order). The output description states that the function should return a binary indicator (or a list of binary indicators) specifying whether each rule is satisfied for a given sample. Because the prompt also includes the feature type information (numeric vs categorical, allowed categorical values, etc.), the LLM can choose appropriate comparison operators and avoid type mismatches when generating code.

This design leverages two LLM strengths. First, the model is robust to the linguistic variability of the rule text: even if a rule uses the phrase "greater than" instead of the symbol "$>$", the LLM understands the intended meaning and can emit the corresponding comparison operator in code. Second, because the LLM has been trained on code corpora, it can generate syntactically valid code in a target language (the paper uses Python) that implements the same logical conditions described in text. By asking for a small, well-specified function whose sole task is to check rules, the generated code is simple and focused, which aids reliability.

# Execution flow: generating Python code, safe execution considerations, and data type handling
The execution flow in FeatLLM follows a compact pipeline. First, a rule-generation prompt elicits a fixed number of rules per class (the paper uses 10 rules per class). Second, a parsing prompt that contains those rules plus a precise function contract is sent to the LLM; the output is a short Python function that evaluates the rules on a row of input data. Third, the produced code is run in the environment to convert the tabular dataset into binary features: the paper executes the generated code via Python's exec() to perform the data conversion.

The paper emphasizes several practical measures to make this flow robust. By including the type and definition of each feature in the initial prompt (numeric, categorical, etc.), the LLM has the necessary type information during both rule generation and code generation. This reduces type-mismatch errors (for example, it discourages generating a numeric comparison on a categorical field). Because the code-generation prompt asks for a function with well-specified inputs and outputs, the LLM tends to produce compact functions that check each rule and return a Boolean or 0/1 result. The authors then call these functions on each sample to obtain the binary indicators.

The paper does not elaborate on additional runtime sandboxing or security mechanisms; in their implementation they execute the generated Python via exec() for data conversion. To reduce the chance of syntactic parsing failures that would produce unparsable code, the authors also constrained the LLM’s earlier outputs by (a) giving explicit response formatting instructions when eliciting rules, and (b) asking the LLM to adhere to a function signature when generating code. In addition, the LLM is guided to prefer simple, direct constructs (e.g., comparisons and set membership checks) that are straightforward to evaluate on tabular data. Finally, because feature types are known and communicated in the prompt, the generated code can perform correct operations (numeric comparisons for numeric features, membership tests for categorical features), which simplifies data-type handling during execution.

# Creating per-class binary features indicating rule satisfaction
Once the generated code is executed, the output for each sample takes the form of binary indicators for each rule and for each class. If there are $c$ classes and $R$ rules per class, then for sample $\mathbf{x}^i$ the generated binary feature vector for class $k$ is written as $\mathbf{z}_k^i \in \{0,1\}^R$. Each element of $\mathbf{z}_k^i$ indicates whether the corresponding rule for class $k$ is satisfied by sample $\mathbf{x}^i$.

These per-class binary features are assembled into a feature representation that is compact and interpretable: the entire rule-derived representation for sample $\mathbf{x}^i$ is a concatenation (or grouping) of the class-specific vectors $\mathbf{z}_k^i$. The downstream model then learns how to combine these binary indicators into a class likelihood. In the FeatLLM framework the model is intentionally simple: for each class $k$ a linear logit is computed by a non-negative weighting of that class's binary features,

\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\]

and the class probabilities are obtained with a softmax,

\[
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big).
\]

Here $\mathbf{w}_k$ are learned weights that capture the importance of each rule-based feature for class $k$. The binary indicators thus serve as an intermediate, human-interpretable representation that the simple linear layer can tune to the few-shot data.

# Quality control: formatting constraints, schema validation, type checks
Quality control in the rule-to-feature pipeline is achieved at multiple stages as described in the paper. First, the initial rule-generation prompt enforces a response format: the authors provide explicit instructions on how each rule should be structured and limit the number of rules per class (they set a fixed number, such as 10). This constrained format reduces downstream variability and makes automated parsing more reliable.

Second, feature schema information is made explicit and available to the LLM during both rule generation and code generation. By supplying feature names, their types, and optional definitions, the prompt helps the LLM avoid obvious type mistakes (for instance, writing numeric comparisons for categorical attributes). This schema-guided prompting acts as a soft form of validation: the LLM is nudged to generate only those rules that are compatible with the known schema.

Third, the paper uses the LLM to produce the parsing code itself rather than relying on brittle string-based parsers. Because the LLM understands synonyms and diverse natural-language ways of expressing the same condition, the generated code inherently normalizes variations (for example, translating "greater than" to the ">" operator). The resulting functions therefore serve as a kind of executable schema validator: when they run on real data, they either return a clear 0/1 indicator for each rule or raise errors that reveal incompatibilities.

Finally, FeatLLM applies a downstream statistical filtering step that further improves feature quality. After converting rules into binary features and training the simple linear model, features that contribute little to predicting the target are effectively down-weighted. In the experiments the authors examine the distribution of learned weights and filter out rules whose learned weight falls below a small threshold (for example, 0.1), thereby removing features that are uninformative or spurious. This tuning step acts as a form of empirical validation: rules must not only be syntactically executable, but also useful on the few-shot data to be retained for prediction.

Taken together, these controls—response-format constraints, explicit schema information, LLM-assisted parsing into concise functions, and downstream weight-based filtering—form a pragmatic pipeline that turns variable natural-language rules into a reliable binary feature matrix suitable for few-shot tabular learning. The approach leverages the LLM’s language and code understanding while keeping the final inference cheap and interpretable because predictions rely only on the generated binary features and a lightweight linear model.
