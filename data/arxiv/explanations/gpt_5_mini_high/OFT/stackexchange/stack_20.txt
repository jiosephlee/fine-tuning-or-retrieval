\title{Stack Exchange of the Paper: "Controlling Text-to-Image Diffusion by Orthogonal Finetuning"}

### How should we choose the number of blocks \(r\) in block-diagonal \(\mathbf{R}\)?
Question:
The parameter count and compute scale with the number of blocks \(r\). Are there heuristics to set \(r\) relative to the layer width \(d\), data size, or task difficulty? Do you have ablations showing the stability/flexibility trade-off as \(r\) varies (e.g., convergence speed, final controllability, and risk of collapse)?
Answer:
Short answer: treat $r$ as an explicit regularizer that trades off flexibility (smaller $r$, bigger blocks, more parameters) vs stability/simplicity (larger $r$, smaller blocks, fewer parameters). The paper gives the parameter-count formulas and the conceptual trade‑off, but it does not present a full sweep/ablation over $r$ in the main text — it reports that (1) increasing the number of trainable parameters improves performance (i.e. moving toward fewer blocks) and (2) the block‑diagonal factorization itself acts as a useful regularizer that improves stability. Use an architecture‑aware starting point (blocks aligned with channels/heads), then sweep $r$ while monitoring controllability and training stability; if you need extra stability use COFT (small $\epsilon$) or increase $r$.

Why $r$ matters (math + intuition). For a layer of width $d$ a full orthogonal $d\times d$ matrix has $\frac{d(d-1)}{2}$ degrees of freedom ($\mathcal{O}(d^2)$). With $r$ equal blocks of size $d/r$ the number of learnable parameters in the orthogonal factor is
$$
p_R \;=\; r\cdot\frac{(d/r)\,(d/r-1)}{2}
     \;=\; \frac{d(d/r-1)}{2}
     \approx \frac{d^2}{2r}\qquad (d\gg r).
$$
If you share the same block across the diagonal the parameter count drops further to
$$
p_{R,\text{shared}} \;=\; \frac{(d/r)\,(d/r-1)}{2}\approx \frac{d^2}{2r^2}.
$$
So increasing $r$ reduces parameters (and hence the transform’s capacity) roughly as $1/r$ (or $1/r^2$ with block sharing). Intuitively, fewer blocks (small $r$) let the orthogonal transform be more expressive (closer to a full rotation) which helps hard/finely controlled tasks but increases the risk of overfitting or destabilizing the pretrained geometry; more blocks (large $r$) restrict the degrees of freedom and act like a structural regularizer, improving stability and sample efficiency.

Heuristics to pick $r$ (practical guidance grounded in the paper)
- Budget / parameter targets: choose $r$ so $p_R$ fits your trainable-parameter budget. The paper demonstrates this trade‑off explicitly (example: $d\!=\!128$, $r\!=\!8$ gives $960$ params for OFT), and it compares OFT to LoRA by matching parameter budgets. If you want parity with an existing adapter (LoRA) use $r$ that yields similar trainable-parameter count.
- Data size / task difficulty: for low-data or easy tasks, increase $r$ (smaller per‑block dimension) to regularize. For high-data or very fine-grained control tasks, decrease $r$ to give OFT more capacity. The paper reports that OFT’s performance improves as the number of trainable parameters grows (i.e., by reducing $r$), but also that block‑diagonalization and COFT improve stability when flexibility is limited.
- Architecture alignment: use structure-aware blocks. For convolution layers the paper explicitly notes that setting the number of blocks equal to the number of input channels makes each block act like a per‑channel (depth‑wise) orthogonal transform; this is a natural inductive bias. By analogy, for Transformer attention one can make block sizes align with head dimensions so each block covers one head’s subspace — this preserves natural modularity and is often a sensible starting point.
- Extra knobs: if you need both angle‑preservation and some per‑neuron scaling, use the re‑scaled OFT variant (learn diagonal $\bm{D}$) rather than only enlarging blocks; if you want stronger stability regardless of $r$, use COFT and tune $\epsilon$ to control deviation from identity.

What the paper reports about the trade‑off (and what it does not). The paper frames exactly this flexibility/stability trade‑off: block‑diagonalization is explicitly called a stronger regularization and COFT adds an explicit deviation constraint for more stable finetuning. Empirically the paper shows OFT/COFT converge faster and more stably than LoRA and DreamBooth with comparable or fewer parameters, and it observes that performance still improves as the number of trainable parameters increases (i.e. the authors did not see a hard saturation). However, the main text does not present a dedicated, systematic ablation plot that sweeps $r$ and reports convergence speed, final control‑consistency metric, and collapse probability as a function of $r$. The authors list improving parameter‑efficiency and the bias introduced by block structure as open problems, so a thorough $r$–sweep is left to future work.

A practical tuning recipe you can run quickly. Pick a small set of candidate block sizes and measure both convergence curves and the paper’s controllability/quality metrics (control‑consistency, CLIP/DINO for subject fidelity, LPIPS for diversity). It is convenient to parametrize by block size $s=d/r$ and try powers-of-two divisors of $d$ (for example try $s\in\{d, d/2, d/4, d/8\}$ or equivalently $r\in\{1,2,4,8\}$ when they divide $d$). For each candidate monitor: (i) validation control‑consistency (the paper’s metric), (ii) convergence speed (metric vs epoch), (iii) hyperspherical energy difference (the paper’s preservation quantity), and (iv) signs of collapse (sudden drop in fidelity or degenerate samples). If you see instability/collapse increase $r$ or switch to COFT with a smaller $\epsilon$; if you see underfitting, decrease $r$ (bigger blocks) or add the diagonal rescaling.

Concise summary. $r$ controls a clear capacity–stability axis: smaller $r$ = higher capacity (better final controllability given enough data/computation) ; larger $r$ = stronger regularization and better stability/sample efficiency. The paper gives the parameter scaling formulas and demonstrates that more OFT capacity tends to help, while block structure and COFT improve stability — but it does not publish a full ablation grid over $r$, so the exact sweet spot will usually be task- and budget-dependent; follow an architecture‑aware starting point and then sweep $r$ with the metrics suggested above.
