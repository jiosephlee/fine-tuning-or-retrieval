# DIY DPO: A Practical Guide to Training With Human Preferences

Direct Preference Optimization (DPO) turns the usual RLHF pipeline into a simple supervised-style training loop: given a dataset of human pairwise preferences, train a policy network so that its implicit reward $ \hat r_\theta(x,y) = \beta\log\frac{\pi_\theta(y\mid x)}{\pi_{\text{ref}}(y\mid x)} $ orders preferred completions above dispreferred ones. This guide gives a compact, implementer-focused checklist: how to format preference data, how to pick and freeze a reference model, how to compute log‑probabilities for two candidate responses, the exact binary cross‑entropy loss to use, practical notes on choosing $\beta$, how to reuse public datasets (when the original SFT model is unavailable), how DPO avoids degeneration that naive objectives exhibit, and how to evaluate with win rates.

## Quick formal recap (what you will optimize)
For each labeled triple $(x,y_w,y_l)$ (prompt $x$, preferred completion $y_w$, dispreferred completion $y_l$) DPO minimizes the cross‑entropy loss

$ \displaystyle \mathcal{L}_{\text{DPO}}(\pi_\theta;\pi_{\text{ref}})
= -\mathbb{E}_{(x,y_w,y_l)\sim\mathcal{D}}\Big[\log \sigma\big(\beta\log\frac{\pi_\theta(y_w\mid x)}{\pi_{\text{ref}}(y_w\mid x)} - \beta\log\frac{\pi_\theta(y_l\mid x)}{\pi_{\text{ref}}(y_l\mid x)}\big)\Big], $

where $\sigma(\cdot)$ is the logistic function and $\beta>0$ controls conservativeness (larger $\beta$ penalizes deviation from $\pi_{\text{ref}}$ more strongly). Equivalently define the implicit reward $\hat r_\theta(x,y)=\beta(\log\pi_\theta(y\mid x)-\log\pi_{\text{ref}}(y\mid x))$ and use a binary logistic loss on $\hat r_\theta(x,y_w)-\hat r_\theta(x,y_l)$.

## Prerequisites and high‑level pipeline
- A dataset of pairwise preferences $\mathcal{D}=\{(x^{(i)},y_w^{(i)},y_l^{(i)})\}$ collected from humans (or reliable synthetic labels). Typical collection: sample two completions from an SFT model for each prompt $x$ and ask humans which they prefer.
- A reference model $\pi_{\text{ref}}$ that reflects the distribution used to generate the pairwise examples (usually the SFT model used at labeling time).
- A policy model $\pi_\theta$ (typically initialized from $\pi_{\text{ref}}$) that you will fine‑tune with DPO.
- Same tokenizer and tokenization conventions for $\pi_{\text{ref}}$ and $\pi_\theta$.

## Data formatting: how to store preference examples
Store each example as a triple:
- x: the prompt/context
- y_w: the human‑preferred completion
- y_l: the dispreferred completion

Keep any metadata (labeler id, timestamp) if available, but the DPO objective needs only the triple. If you have ranked lists of candidates, DPO extends from Bradley–Terry to Plackett–Luce families (the paper discusses this extension); for an implementer-focused start, binary comparisons are simplest.

Important: the examples should reflect the distribution of completions used when collecting labels. If you reuse a public preference dataset created with a different SFT, see the section "Reusing public datasets" below.

## Reference model (freeze it)
- Use the SFT model that was used to generate the candidate completions as $\pi_{\text{ref}}$ (this is standard).
- Keep $\pi_{\text{ref}}$ frozen during DPO training. You only compute log‑probabilities from it; you do not update it.
- Initialize the policy $\pi_\theta$ from $\pi_{\text{ref}}$ when possible (this is the common practice and stabilizes training).

If you do not have the original SFT model, create a reference model by supervised fine‑tuning on the preferred completions (the paper calls this practical fallback): set

$ \displaystyle \pi_{\text{ref}} \approx \arg\max_{\pi}\ \mathbb{E}_{(x,y_w)\sim\mathcal{D}}[\log \pi(y_w\mid x)]. $

This "Preferred‑FT" reference makes the reference distribution similar to the dataset and mitigates dataset/ref mismatch.

## Computing log‑probabilities correctly
- Compute the conditional sequence log‑probability as usual:
  $ \displaystyle \log\pi(y\mid x) = \sum_{t=1}^{T} \log \pi(y_t\mid x,y_{<t}). $
  Implementationally this is the sum of token log‑probs for the tokens of $y$ conditioned on $x$ (include EOS if you sampled it).
- Use the same tokenizer for $\pi_\theta$ and $\pi_{\text{ref}}$ and ensure both models interpret the token sequence the same way (special tokens, EOS, padding).
- Compute $\log\pi_\theta(y_w\mid x)$ and $\log\pi_\theta(y_l\mid x)$ (the policy) and also $\log\pi_{\text{ref}}(y_w\mid x)$ and $\log\pi_{\text{ref}}(y_l\mid x)$ (the frozen reference).
- Vectorize this: for a batch of examples compute the four sequence log‑prob arrays in one pass per model (concatenate prompt+completion tokens, mask out prefix tokens when computing the loss/logits).

## The training loss (numerical/stable form)
For each training triple compute the per‑example scalar

$ \displaystyle s \;=\; \beta\Big[(\log\pi_\theta(y_w\mid x)-\log\pi_{\text{ref}}(y_w\mid x)) - (\log\pi_\theta(y_l\mid x)-\log\pi_{\text{ref}}(y_l\mid x))\Big]. $

Then the per‑example loss is

$ \displaystyle \ell = -\log\sigma(s) $  (i.e., binary cross‑entropy with label=1).

In practice use a numerically stable implementation such as a binary cross‑entropy with logits routine (treat $s$ as the logit, target=1). Vectorize and average the loss over the minibatch before backpropagating into $\pi_\theta$.

Key points:
- Only update $\pi_\theta$; $\pi_{\text{ref}}$ is frozen.
- You do not need to sample from $\pi_\theta$ during training — training uses offline pairs $(x,y_w,y_l)$ only.
- This is a standard supervised-style optimization (no policy-gradient sampling loop), but the loss is derived to produce the optimal KL‑constrained policy under the Bradley–Terry preference model.

## Choosing and tuning $\beta$
- $\beta$ is the scalar that connects reward and KL regularization: the RL objective is $\mathbb{E}[r] - \beta\ \mathrm{KL}[\pi_\theta\|\pi_{\text{ref}}]$. Larger $\beta$ enforces stronger adherence to the reference (more conservative updates).
- In the paper the authors sweep $\beta\in\{0.05,0.1,1,5\}$. If you are uncertain, follow the same sweep and pick the policy that best trades off reward and divergence for your application.
- Intuition: smaller $\beta$ → more aggressive changes away from $\pi_{\text{ref}}$; larger $\beta$ → smaller policy updates and less risk of drifting far from the reference.

## Avoiding degeneration (why DPO and not naive unlikelihood)
A naive objective that simply raises $\log\pi_\theta(y_w)$ and lowers $\log\pi_\theta(y_l)$ with fixed weights (for example, "maximize $\log\pi(y_w) - \alpha\log\pi(y_l)$") can cause model degeneration or collapse in practice. DPO includes a dynamic per-example importance weight via the logistic on the difference of implicit rewards:

$ \displaystyle \sigma\big(\hat r_\theta(x,y_w)-\hat r_\theta(x,y_l)\big) $

which places more weight on examples where the current policy orders the pair incorrectly, and downweights examples that are already correctly ordered by a large margin. This built‑in adaptive weighting is critical to stability. The paper reports that naively removing this weighting causes degeneration; implement DPO exactly as above rather than substituting a simple unlikelihood term.

## Monitoring during training
Track (on heldout prompts) at least:
- DPO loss (training and validation)
- Average implicit reward difference on validation pairs: $\mathbb{E}[\hat r_\theta(x,y_w)-\hat r_\theta(x,y_l)]$
- Sequence‑level divergence from the reference (the paper reports "sequence‑level KL" measured as the sum of per‑timestep KLs between $\pi_\theta$ and $\pi_{\text{ref}}$). This gives you a sense of how far the policy is drifting.
- Where available, evaluate model quality with the ground‑truth reward (if you have one) or with holdout preference pairs.

Stop or reduce step size if the model begins to diverge excessively from $\pi_{\text{ref}}$ or if human‑facing metrics worsen.

## Reusing public preference datasets (when original SFT is missing)
If you have a public preference dataset but you do not have the exact SFT that produced the labeled candidates:
- Do not blindly set $\pi_{\text{ref}}$ to an arbitrary LM. Instead, follow the paper's practical approach: train a reference model by maximum likelihood on the preferred completions $(x,y_w)$ from the dataset (Preferred‑FT).
- Freeze that trained reference and use it as $\pi_{\text{ref}}$ during DPO. This reduces mismatch between the dataset's generation distribution and your reference, improving stability.

## Evaluating with win rates (human or LLM judges)
- The paper uses win rate versus a baseline as the primary task‑level evaluation: for each test prompt, sample a response from your model and a baseline response (e.g., the reference or a PPO model), and ask a judge to choose which response is better.
- Use human raters when possible. If you use automatic judges (e.g., GPT‑4), validate the automated judge on a small subset of examples to ensure it correlates with human judgments. The paper ran a small human study and found GPT‑4 judgments to correlate well with human annotators for their summarization prompts (they used two different GPT‑4 prompt styles and selected the one that matched human preferences best).
- Sample multiple decoding temperatures (paper sweeps 0.0–1.0) because sampling temperature affects quality and win rates. The paper found DPO to be robust across temperatures relative to PPO in their experiments.

## Practical implementation checklist (step‑by‑step)
1. Prepare preference dataset $\mathcal{D} = \{(x,y_w,y_l)\}$.
2. Choose or build $\pi_{\text{ref}}$:
   - If you have the original SFT used to create the dataset, use it and freeze it.
   - Otherwise, train a reference model on $(x,y_w)$ by supervised fine‑tuning (Preferred‑FT) and freeze that.
3. Initialize $\pi_\theta \leftarrow \pi_{\text{ref}}$ (recommended).
4. For each minibatch of triples:
   - Compute $\log\pi_\theta(y_w\mid x)$ and $\log\pi_\theta(y_l\mid x)$ (sum token log‑probs).
   - Compute $\log\pi_{\text{ref}}(y_w\mid x)$ and $\log\pi_{\text{ref}}(y_l\mid x)$ (frozen).
   - Compute $s = \beta\big[(\log\pi_\theta(y_w)-\log\pi_{\text{ref}}(y_w)) - (\log\pi_\theta(y_l)-\log\pi_{\text{ref}}(y_l))\big]$.
   - Loss = mean of $-\log\sigma(s)$ across batch (or use BCEWithLogits with target=1).
   - Backpropagate and update only $\pi_\theta$.
5. Periodically evaluate validation loss, sequence KL to the reference, and win‑rate vs baseline (human or automated judge). Monitor for degeneration.
6. Sweep a few $\beta$ values (e.g., $\{0.05,0.1,1,5\}$) and decoding temperatures to pick the best tradeoff.

## Limitations and practical notes (from the paper)
- DPO eliminates the RL loop and a separate reward model, but it still depends on a good preference dataset and a sensible reference model.
- The choice of $\beta$ impacts how conservative the policy is. The paper reports that DPO is robust and often requires less hyperparameter tuning than PPO, but a small grid of $\beta$ is still recommended.
- The paper evaluates up to 6B models. For much larger models or different domains you should validate DPO's behavior empirically (generalization and reward over‑optimization are open questions flagged by the authors).
- If your labels contain more than pairwise comparisons, the DPO derivation extends to Plackett–Luce ranking data (see the paper’s appendix).

## Final takeaways
DPO collapses the two‑stage RLHF pipeline (fit a reward model, then optimize it with RL) into a single supervised‑style objective that is easy to implement: compute sequence log‑probs under a frozen reference and the trainable policy, take their scaled difference, and optimize a binary cross‑entropy. Use a faithful reference model (or train one on the preferred completions if you must reuse a public dataset), sweep a few sensible $\beta$ values, and validate model behavior with win‑rate evaluations. If you follow the checklist above, you should be able to reproduce the simplicity, stability, and competitive performance reported in the paper without the complexity of RL-based fine‑tuning.
