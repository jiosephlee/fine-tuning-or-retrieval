\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### Reproducing the 7B memory numbers (5,048 MB base, 567 MB LoRA input grads, 26 MB LoRA params): detailed assumptions?
Question:
In the "Memory Requirement of Parameter-Efficient Finetuning" section, the paper reports for a 7B LLaMA model (batch size 1, FLAN v2) that the 4-bit base model is 5,048 MB, LoRA parameters are 26 MB (about 0.2% of base), and LoRA input gradients are 567 MB (reduced to 18 MB on average with checkpointing). Could someone outline the precise assumptions for these figures: tensor precisions, layer counts, where gradients are stored, whether activation recomputation checkpoints affect gradient storage, and whether optimizer states are included or excluded?
Answer:
Short answer: the paper’s 7B memory numbers are measured under the QLoRA ingredients described in the text: the base LLaMA weights are stored in 4‑bit NormalFloat (NF4) with Double Quantization (blocksize 64 for weights, blocksize 256 for the second quantization of the scales), all computation (forward/backward and LoRA params/gradients) is in 16‑bit BrainFloat (BF16), LoRA adapters are placed at every linear projection inside every transformer block, batch size is 1 on the FLAN v2 data, and optimizer states for the (tiny) LoRA parameters are not counted on GPU because QLoRA uses Paged Optimizers (they are paged to CPU). The heavy‑hitters in those figures are the quantized weight storage (4‑bit + quantization constants) and the stored layer inputs (activations) needed to compute LoRA gradients; gradient checkpointing removes most of the latter (this is why $567\ \text{MB} \rightarrow 18\ \text{MB}$).

Below I give the exact assumptions (as used or implied in the paper) and short reproducible formulas so you can re‑derive the numbers.

What each reported number is and the assumptions behind it
- “$4$‑bit base model = $5{,}048\ \text{MB}$. ” This is the GPU footprint of the frozen base LLaMA‑7B stored with NF4 + Double Quantization. The implementation details used in the paper are: NF4 for weight storage, blocksize 64 for weight blocks, double quantization of the block scales with c2 in 8‑bit float (FP8) and the top level scale c1 in FP32. Dequantization is performed on the fly to BF16 for compute. The $5{,}048\ \text{MB}$ is the measured storage cost on GPU in their code (quantized weights + quantization constants + small framework/packing overhead). The per‑parameter model for that storage (Double Quantization, blocksize 64) gives an extra constant overhead of about $0.127\ \text{bits/param}$, so the nominal per‑parameter storage is about $4.127\ \text{bits/param}$; the paper’s Appendix contains the exact measured breakdown (see the paper).

- “LoRA params = 26 MB.” LoRA parameters are stored and updated in BF16. The paper uses LoRA sized to be about $0.2\%$ of the original model weights. The memory is therefore
$$
  M_{\text{LoRA}} \approx N_{\text{params}}\times 0.002 \times 2\ \text{bytes},
$$
where the 2 bytes come from BF16. For a ~7B parameter model this evaluates to ~25–30 MB (the paper reports $\approx 26\ \text{MB}$; small differences come from exact param count and MB vs MiB conventions).

- “LoRA input gradients = 567 MB (reduced to 18 MB with checkpointing).” What the paper calls “LoRA input gradients” is the stored layer inputs (activations) that you must keep to compute gradients for the LoRA adapter (LoRA needs the input X for each adapted linear projection). Those are stored in the computation dtype (BF16, 2 bytes/element). If you apply LoRA to every linear projection in every transformer layer, the activation memory for batch size $B$ and sequence length $S$ is approximately
$$
  M_{\text{act}} \approx B \times S \times H \times N_{\text{LoRA\_lin}} \times 2\ \text{bytes},
$$
where $H$ is the model hidden dim and $N_{\text{LoRA\_lin}}$ is the number of linear projections you applied LoRA to (e.g. for LLaMA‑7B you typically have 32 transformer layers and you may apply LoRA to attention q/k/v/o and the MLP projections $\rightarrow$ roughly 6 linear projections per transformer block $\Rightarrow$ $N_{\text{LoRA\_lin}} \approx 32 \times 6 = 192$). Plugging representative numbers ($B=1$, $H \approx 4096$, $N_{\text{LoRA\_lin}} = 192$) gives
$$
  M_{\text{act}} \approx S\times 1{,}572{,}864\ \text{bytes}\,.
$$

To get the paper’s quoted 567 MB you solve for the effective average sequence length used in FLAN v2 (their reported number corresponds to $S \approx 360$ tokens under these assumptions). Gradient checkpointing trades compute for memory by discarding most intermediate activations and recomputing them during the backward pass; storing only one checkpoint per transformer block (or similar checkpointing granularity) reduces $M_{\text{act}}$ roughly by a factor $\approx$ number_of_layers, which is why $567\ \text{MB} \rightarrow \approx 18\ \text{MB}$ in the paper ($567\ \text{MB} \div 32 \approx 17.7\ \text{MB}$). The paper is explicit that the 18 MB figure is an average per sequence when checkpointing is enabled over FLAN v2 sequences.

Where gradients and optimizer states live
- Gradients: only LoRA parameters are trained so only the adapter weights have parameter gradients. Those gradients and the cached inputs needed to form them are stored in BF16 by the QLoRA implementation (the paper states “we only compute weight gradients for the LoRA parameters which use 16‑bit BrainFloat”).
- Base weights: base (4‑bit) model weights are frozen, so there are no base‑weight gradients to store.
- Optimizer states: the paper’s memory numbers are GPU footprints; QLoRA uses “Paged Optimizers” (NVIDIA unified memory paging) to page optimizer state to CPU when necessary. Practically that means the large moment/variance buffers for the optimizer can be evicted to CPU RAM (and are not counted in the GPU numbers in the paper). So the quoted 5,048 / 567 / 26 / 18 MB figures are not including full on‑GPU optimizer state for a full model optimizer (and for LoRA the optimizer state is small and may be paged out).

How to exactly reproduce their reported numbers
1. Use LLaMA‑7B parameter count used by the authors (their code / appendix has the exact $N$). Use NF4 + double quantization with blocksize 64 for weights and blocksize 256 for $c_2$, and store LoRA params in BF16.  
2. For LoRA param memory compute $M_{\text{LoRA}} = N_{\text{params}}\times 0.002 \times 2\ \text{bytes}$. That yields $\approx 26\ \text{MB}$ for the 7B config (differences due to exact $N$ and MB vs MiB conventions).
3. For activation memory compute $M_{\text{act}} = B\times S\times H\times N_{\text{LoRA\_lin}}\times 2\ \text{bytes}$. Use $B=1$ and the FLAN v2 average sequence length (the paper’s $567\ \text{MB}$ corresponds to the average sequence distribution they used). With checkpointing keep only $O(\text{number\_of\_layers})$ checkpoints and divide $M_{\text{act}}$ accordingly (that is how you see $\approx 18\ \text{MB}$ average).
4. For the 4‑bit base size compute per‑param bits $\approx 4 + 0.127$ (the 0.127 bits/param is the Double Quantization overhead for the block sizes above), then convert to bytes: $M_{\text{base}}\approx N_{\text{params}}\times(4+0.127)/8\ \text{bytes}$. The paper reports 5,048 MB as the practical measured GPU footprint for their implementation (the small gap between a strict per‑param calculation and 5,048 MB is due to implementation overheads, embeddings/layernorm params, allocator rounding/alignment and other runtime metadata — see the Appendix for the exact measured breakdown).

Caveats and practical notes
- These numbers are implementation and dataset dependent: average sequence length, blocksize choices, whether you apply LoRA to all linear layers or only Q/V, and whether you page optimizer state to CPU all change the reported MB values.  
- The key takeaway (and what the paper stresses) is that for PEFT on a frozen quantized base model the dominant memory item is per‑token activations needed to compute adapter gradients; adapters themselves are tiny. Checkpointing + freezing the base and paging small optimizer states to CPU are the mechanisms that make the numbers small enough to finetune large models on limited GPUs.  
- For exact byte‑for‑byte reproduction use the QLoRA code + the Appendix memory table; the paper’s Appendix contains the detailed per‑tensor breakdown that yields the quoted 5,048 / 567 / 26 / 18 MB figures.
