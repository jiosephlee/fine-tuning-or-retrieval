Chapter 2: Foundations: Quantization, LoRA, and Memory in LLM Finetuning

# Block-wise k-bit quantization and dequantization equations

Quantization is the process of converting a tensor that uses a relatively high-precision numeric format (for example 32-bit floating point) into a lower‑precision representation (for example 8‑bit integers or 4‑bit custom formats). The core idea is simple: pick a discrete set of representable values and map each real value to the nearest representable value. To make efficient use of the limited dynamic range of the low‑bit format, the continuous input tensor is commonly rescaled with a quantization constant so that the tensor’s largest magnitude maps near the representable extreme.

The paper gives a standard example for converting an FP32 tensor into Int8 with range roughly $[-127,127]$:

\begin{equation}
\mathbf{X}^{\text{Int8}} = \text{round}\!\left( \frac{127}{\mathrm{absmax}(\mathbf{X}^{\text{FP32}})} \, \mathbf{X}^{\text{FP32}} \right)
= \text{round}\!\left( c^{\text{FP32}} \cdot \mathbf{X}^{\text{FP32}} \right),
\end{equation}

where $c^{\text{FP32}}$ is the quantization constant that rescales the FP32 values into the integer range. The inverse operation (dequantization) restores a floating representation by dividing by the same constant:

\begin{equation}
\text{dequant}\!\left(c^{\text{FP32}}, \mathbf{X}^{\text{Int8}}\right)
= \frac{\mathbf{X}^{\text{Int8}}}{c^{\text{FP32}}}
= \mathbf{X}^{\text{FP32}}.
\end{equation}

When working with large matrices (weights of large models are typically matrices), a single global scale for the entire tensor can be a poor fit because a few large values (outliers) will force the global scale to be large, compressing the useful dynamic range for most entries. To reduce this problem, quantization is often applied block‑wise: flatten the weight tensor $\mathbf{X}\in\mathbb{R}^{b\times h}$ and split it into $n$ contiguous blocks of size $B$ (so $n = \frac{b\times h}{B}$). Each block $i$ has its own quantization constant $c_i$ and is quantized independently using the same per‑block formula above. Formally, for block $i$:

\begin{equation}
\mathbf{X}_i^{k\text{-bit}} = \text{round}\!\left( c_i \cdot \mathbf{X}_i^{\text{FP32}} \right), \qquad
\text{dequant}\!\left(c_i, \mathbf{X}_i^{k\text{-bit}}\right) = \frac{\mathbf{X}_i^{k\text{-bit}}}{c_i}.
\end{equation}

Block‑wise quantization is the standard building block used by QLoRA to store base model weights in low precision.

# Quantization constants, absmax scaling, and handling outliers

The quantization constant (for absmax scaling) is the numerical factor that maps the floating values into the compact discrete representation range. In the simple Int8 example above, $c^{\text{FP32}}=\tfrac{127}{\mathrm{absmax}(\mathbf{X}^{\text{FP32}})}$. The absmax scaling approach guarantees that the full target integer range is used for at least one value in the block, but it has a well‑known weakness: if a small number of values are much larger in magnitude than the rest (outliers), the scale will be dominated by those outliers and most representational bins will be used inefficiently for the many smaller values.

Two common remedies appear in practice:

- Reduce the scope of normalization so that outliers affect fewer values. This is precisely the intuition behind block‑wise quantization: by having a per‑block maximum $c_i$, a single outlier only affects its block instead of the whole matrix.

- Use a quantile‑based mapping instead of absmax. Quantile quantization computes boundaries so that every discrete bin is expected to contain approximately the same number of input values (equal‑mass bins). Quantile schemes avoid wasting bins on a few outliers, but exact quantile estimation is expensive on large tensors and approximate quantile algorithms can make errors that hurt representation of outliers (which are often important).

QLoRA’s NormalFloat approach (NFk, e.g., NF4) builds on the idea of quantile quantization but exploits the empirical fact that pretrained weight tensors are often approximately zero‑centered and normally distributed. When this is approximately true, one can derive an information‑theoretically optimal k‑bit data type by precomputing the quantiles of a standard normal distribution and then mapping each block by a simple absmax rescaling into the data type’s fixed range. This avoids expensive empirical quantile estimation per block while gaining many of the benefits of quantile quantization for normally distributed weights (details of NFk are discussed separately in the QLoRA paper).

# Why small blocks help and trade-offs in precision vs overhead

Small block sizes improve quantization precision because they localize the influence of outliers: an unusually large weight only affects the scale of its small block, not the entire tensor. In other words, smaller $B$ reduces the chance that many otherwise small values will be squashed into a narrow subset of the low‑bit bins because of a distant outlier.

However, there is an explicit trade‑off: every block requires storing its own quantization constant(s). If those constants are stored in full precision (e.g., 32‑bit float per block), then the memory overhead from constants grows inversely with block size. For blocksize $B$ and 32‑bit constants, the extra bits per parameter due to constants are

\begin{equation}
\text{bits per parameter for constants} = \frac{32}{B}.
\end{equation}

As an example, with $B=64$ and 32‑bit per‑block constants, the constants alone add $32/64 = 0.5$ bits per parameter on average. For very large models this overhead is not negligible.

Double Quantization is a practical technique introduced in the paper to pay the precision benefits of small block sizes while reducing the memory overhead for the blockwise constants. The idea is to quantize the quantization constants themselves: treat the per‑block constants $c_2^{\text{FP32}}$ as a tensor and apply a second quantization pass to store them in a lower precision (for example FP8) with a larger blocksize. The two‑level storage pattern looks like:

- Level 2: store the base weights $\mathbf{W}$ in k‑bit (for QLoRA, NF4).
- Level 1: store quantized per‑block constants for the Level 2 quantization in a lower precision (e.g., FP8), while keeping a small set of higher precision anchors (e.g., some FP32 level constants).

Using the settings described in the paper (blocksize $B=64$ for $\mathbf{W}$, quantizing the Level‑2 constants into FP8 with a blocksize of 256 and keeping a small number of FP32 anchors), the effective memory per parameter for constants becomes approximately:

\begin{equation}
\frac{8}{64} + \frac{32}{64\cdot 256} \approx 0.127 \text{ bits per parameter},
\end{equation}

instead of the original $32/64 = 0.5$ bits per parameter. The saving is therefore about $0.373$ bits per parameter. For a 65B parameter model that is roughly

\begin{equation}
65\times 10^9 \times 0.373 \;\text{bits} \approx 24.2\times 10^9 \;\text{bits} \approx 3.03\ \text{GB},
\end{equation}

i.e., a memory saving on the order of a few gigabytes. The paper reports essentially the same calculation and the empirical result that Double Quantization reduces memory footprint without measurable performance degradation.

In short: small blocks improve representational precision; the cost is extra per‑block metadata. Double Quantization is a practical and effective way to reduce that metadata footprint while preserving the precision benefits.

# LoRA adapters: Y = XW + s X L1 L2 and gradient flow through frozen W

Low‑Rank Adapters (LoRA) are a parameter‑efficient finetuning technique that augments existing linear projections with a small, trainable low‑rank term while keeping the pretrained weights frozen. Given an existing linear mapping $\mathbf{X}\mathbf{W} = \mathbf{Y}$ with $\mathbf{X}\in\mathbb{R}^{b\times h}$ and $\mathbf{W}\in\mathbb{R}^{h\times o}$, LoRA replaces the forward projection by

\begin{equation}
\mathbf{Y} = \mathbf{X}\mathbf{W} + s\,\mathbf{X}\mathbf{L}_1\mathbf{L}_2,
\end{equation}

where $\mathbf{L}_1\in\mathbb{R}^{h\times r},\; \mathbf{L}_2\in\mathbb{R}^{r\times o}$ are the low‑rank adapter matrices, $r$ is the adapter rank (typically much smaller than $h,o$), and $s$ is a scalar multiplier. In practice the LoRA term is small in parameter count compared to the original $\mathbf{W}$, so storing and updating $\mathbf{L}_1,\mathbf{L}_2$ is cheap.

Crucially for training, gradients flow through the entire forward computation. The pretrained matrix $\mathbf{W}$ is kept frozen (no parameter updates), but the forward computation still uses $\mathbf{W}$, and the gradient of the loss with respect to the adapter parameters depends on the forward activations that also pass through $\mathbf{W}$. In other words, the backward pass propagates derivatives through the frozen $\mathbf{W}$ to compute gradients for $\mathbf{L}_1,\mathbf{L}_2$, and we update only the adapter parameters.

In the QLoRA setting the base model weights $\mathbf{W}$ are stored in a 4‑bit quantized format (NF4) and are dequantized to the computation format (BF16) for forward and backward computation. The paper emphasizes that the computation of gradients for the adapters still requires computing derivatives that depend on $\mathbf{W}$; therefore $\mathbf{W}$ is dequantized to BF16 during the backward pass so that derivatives such as $\partial \mathbf{X}/\partial \mathbf{W}$ are computed in 16‑bit precision. The important point is: LoRA lets us avoid maintaining optimizer states and gradient storage for the large full model weights while still allowing gradients to flow through those frozen weights into the much smaller adapter parameters.

# Concrete 7B memory example: LoRA params 26 MB, input gradients 567 MB, with checkpointing 18 MB per sequence, 4-bit base about 5 GB

A specific and instructive set of numbers from the paper illustrates how memory is actually spent when finetuning a large model with LoRA:

- For a LLaMA 7B model finetuned on FLAN v2 with batch size 1, the LoRA parameters themselves (when sized to be roughly 0.2% of the original model weights, a typical setting) occupy only about 26 MB of memory.

- The LoRA input gradients (the activation gradients that are required to compute updates for the LoRA parameters) can have a much larger footprint: about 567 MB.

- If gradient checkpointing is employed, the input gradients reduce dramatically to an average of about 18 MB per sequence (the paper reports this as the post‑checkpointing figure).

- The 4‑bit quantized base model (i.e., storing the pretrained weights in NF4) consumes about 5,048 MB (≈5.05 GB).

These numbers highlight two critical facts: (1) the adapter parameter storage is negligible compared to activation gradient memory and model storage; and (2) gradient checkpointing can drastically reduce the largest component of training memory usage (the activation gradients), at the cost of extra computation.

# Activation gradients as the dominant memory cost during training

From the empirical breakdown above, it becomes clear that for LLM finetuning the dominant memory cost is not the parameter matrices themselves (especially when the base model is stored in low precision), but the activation gradients that must be held (or recomputed) during backpropagation. Activation gradients scale with batch size, sequence length, hidden dimension, and the number of layers: every layer’s activations for every token in the batch contribute to the overall activation memory.

Because activation gradients dominate, reducing the number or size of trainable parameters (for example by shrinking LoRA ranks) often produces only marginal memory benefits. The practical implication in the QLoRA paper is important: because LoRA parameter storage is so small relative to activation memory, it is affordable to place more adapters throughout the network (more adapter placements) without significantly increasing the overall memory footprint. In other words, allocating capacity by increasing adapter coverage (placing adapters on more linear layers) is often a more effective way to recover full‑fine‑tuning performance than trying to save a few megabytes by reducing adapter rank.

# Gradient checkpointing to tame activations and its side effects

Gradient checkpointing is the standard technique to trade extra computation for lower activation memory. Instead of storing all intermediate activations for the backward pass, the training code stores only a subset of checkpoints; during the backward pass it recomputes intermediate activations as needed. The direct effect is a substantial reduction in peak activation memory at the cost of doing extra forward computations (recomputation).

The paper gives a concrete example of the power of checkpointing: the LoRA input gradients dropped from 567 MB to an average of 18 MB per sequence with checkpointing. This makes a large difference in whether a model fits on a single GPU.

However, checkpointing can introduce its own operational difficulties. One such issue reported in the paper is the occurrence of memory spikes when processing some mini‑batches that include unusually long sequence lengths; these spikes can lead to out‑of‑memory errors in practice even when checkpointing is used. To mitigate this, QLoRA introduces Paged Optimizers (described in the paper): by using NVIDIA’s unified memory, optimizer states can be allocated as paged memory that the runtime will automatically move between GPU and CPU as needed, allowing rare spikes to succeed without blowing up GPU memory. Paged Optimizers therefore complement checkpointing by making the system more robust to occasional large transient memory demands.

# Storage vs compute data types and the role of BF16 during training

QLoRA explicitly separates the storage data type from the computation data type. The base model weights are stored in a very low‑precision form (in the paper, 4‑bit NormalFloat, NF4). But when those weights are needed for computation, they are dequantized to a higher‑precision computation format (BFloat16, abbreviated BF16, in the paper) and matrix multiplications and gradient computations are done in BF16. LoRA adapter parameters and their gradients are kept in BF16 as well.

This separation is captured in the paper’s forward expression for a single linear layer augmented with a LoRA adapter and double quantization:

\begin{equation}
\mathbf{Y}^{\text{BF16}} = \mathbf{X}^{\text{BF16}} \;\text{doubleDequant}\!\left(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{NF4}}\right)
\;+\; \mathbf{X}^{\text{BF16}}\mathbf{L}_1^{\text{BF16}}\mathbf{L}_2^{\text{BF16}}.
\end{equation}

The double dequantization operation is defined as

\begin{equation}
\text{doubleDequant}\!\left(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}}\right)
= \text{dequant}\!\big(\text{dequant}\!\left(c_1^{\text{FP32}}, c_2^{\text{k-bit}}\right), \mathbf{W}^{\text{4bit}}\big)
= \mathbf{W}^{\text{BF16}},
\end{equation}

i.e., the stored k‑bit weights are dequantized (using the two levels of quantization constants) to BF16 for the mat‑mul. During backpropagation, these dequantized BF16 values are used to compute derivatives so that adapter gradients are computed in BF16 precision, even though the persistent storage of the base weights remained in NF4.

This design — low‑precision storage, higher‑precision computation — is a key enabler of QLoRA: it reduces persistent memory footprint while keeping the numerical fidelity of the forward and backward computation high enough to recover full‑precision finetuning performance when training only the adapters.

# Why adapter count and placement often matter more than rank for large LLMs

A practical lesson from the experiments reported in the paper is that where and how many adapters you place across the model often matters more for finetuning recovery than the adapter rank $r$ (the internal dimensionality of $\mathbf{L}_1,\mathbf{L}_2$). The typical default LoRA practice (place adapters only on the query and value projection matrices of attention) turned out not to be sufficient to reproduce full fine‑tuning performance for larger base models. Instead, the paper found that placing LoRA adapters on all linear layers across transformer blocks was required to match full finetuning results on their experiments (for instance, 7B LLaMA finetuning on Alpaca).

Put differently, because LoRA parameters are so small relative to activation and model storage, it is affordable to increase the number of adapters (i.e., their coverage across layers) rather than solely increasing their rank. Increasing coverage gives the adapters broader representational scope and allows the model to adapt in many parts of the computation graph; increasing rank only increases capacity at a single location. Empirically, the paper reports that the total number and placement of adapters is the most critical LoRA hyperparameter for matching full fine‑tuning quality, while the rank $r$ has a much smaller effect (in their experiments).

This has a direct practical implication: when working under a tight memory budget, prefer to distribute adapters across more layers (keeping them low‑rank) instead of concentrating capacity in a few high‑rank adapters. Because activation gradients dominate memory, this redistribution of parameter capacity has a small effect on memory usage but can substantially improve finetuning fidelity.

---

Together, these foundations explain the central QLoRA insight: by storing base weights in a carefully designed 4‑bit format (NF4) with block‑wise and double quantization, by dequantizing to BF16 for computation, and by finetuning only compact LoRA adapters placed across the network while using techniques such as gradient checkpointing and paged optimizers to control activation and optimizer‑state memory spikes, it becomes possible to finetune very large models (tens of billions of parameters) on a single commodity GPU without sacrificing the performance of conventional 16‑bit full finetuning. The memory breakdowns and quantitative tradeoffs above are the concrete engineering primitives that make that capability achievable.
