\title{A Textbook about the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

Chapter 4: Managing Memory Spikes: Paged Optimizers and Training Stability

# Why long sequences and checkpointing create memory spikes
Training large language models requires keeping several kinds of state in memory at once: the model parameters, the optimizer state, activations computed during the forward pass, and the gradients computed during the backward pass. The QLoRA paper emphasizes that, for finetuning, the dominant contributor to memory usage is not the small adapter parameters (LoRA) but the activation gradients and related transient activations. In their breakdown for a 7B LLaMA run, the LoRA input gradients and related activation-related allocations are orders of magnitude larger than the LoRA parameter tensors themselves. This is why saving parameter bits (for example by storing the base model in 4‑bit form) alone does not eliminate all out-of-memory risks.

Gradient checkpointing is a common technique to reduce the steady-state memory required to store activations: it trades extra computation for lower persistent activation storage by selectively recomputing some intermediate activations during the backward pass instead of storing them. As the paper notes, however, checkpointing can create transient peaks in memory usage. Those peaks arise because, during recomputation and during certain moments of the backward/update pipeline, the runtime may need to hold recomputed activations, interim gradients, and optimizer-related buffers at the same time. The QLoRA authors call attention to the fact that these "gradient checkpointing memory spikes" are especially likely to occur for mini-batches that contain long sequences: longer sequences increase the amount of activation information that must be produced or recomputed, and therefore increase the magnitude of the transient memory peaks.

These transients are important because they are what typically trigger out-of-memory failures on a GPU even when the average memory footprint would fit. The paper motivates paged optimizers specifically to absorb these transient spikes so that training can proceed on a single GPU even when peak demand occasionally exceeds the device memory budget.

# NVIDIA unified memory and paging between GPU and CPU RAM
The QLoRA paper relies on NVIDIA's unified memory facility to implement paged optimizers. Unified memory provides an automatic page-level transfer mechanism between GPU device memory and host (CPU) RAM. The paper describes this feature as performing "automatic page-to-page transfers between the CPU and GPU for error-free GPU processing in the scenario where the GPU occasionally runs out-of-memory," and it likens the mechanism to ordinary OS-level paging (the familiar concept of swapping between RAM and disk) except that the transfer is between GPU device memory and host RAM.

Practically, unified memory allows the program to allocate memory that the CUDA runtime will transparently move between the GPU and host as different code regions access pages. For QLoRA, this enables allocator strategies where large but infrequently accessed arrays (specifically optimizer state tensors) are allocated in such a way that they can be evicted from GPU memory and resident on host RAM until they are needed on the device. The runtime handles the transfer back into GPU memory when the kernel that requires those pages runs, removing the need for the training loop to explicitly implement manual copy logic for every eviction/load.

The key behavioral property emphasized in the paper is that unified memory makes the process automatic and "error-free" in the sense that a training job will not immediately crash with an out-of-memory GPU error simply because a transient spike exceeded device memory — instead, pages may be migrated to host memory so execution can continue. That said, the paper treats this as a tool to manage rare or transient spikes rather than a way to run arbitrarily memory‑hungry workloads without cost.

# Paged optimizer states: what is paged and when
In QLoRA the authors choose the optimizer state as the primary target for paging. Optimizer states are typically large tensors (for example, moment estimates and other auxiliary variables used by adaptive optimizers), and they are not needed during the forward pass; they are mainly needed during the optimizer update step after gradients have been computed. The paper's implementation therefore allocates optimizer state memory in a paged fashion using unified memory so that, when a transient spike happens during forward/backward, those optimizer tensors can be evicted from GPU memory and stored on the host.

The paper describes the runtime pattern succinctly: optimizer states are "automatically evicted to CPU RAM when the GPU runs out-of-memory and paged back into GPU memory when the memory is needed in the optimizer update step." In other words, the training loop still performs the usual forward/backward/optimizer-update sequence, but the allocator and CUDA runtime take care of moving optimizer pages out of the GPU during peak-demand intervals and bringing them back in just in time for the parameter-update kernel.

Two aspects follow from this design choice, as emphasized in the paper. First, paging is applied to state that is large and not latency-critical for the forward/backward kernels, minimizing the number and volume of page faults during the inner compute-heavy kernels. Second, paging is used to handle occasional peaks rather than to permanently host the optimizer on the CPU; the optimizer state will be resident on GPU when the update must execute, so the correctness and numerical semantics of the optimizer are preserved.

# Expected runtime behavior and when slowdowns can occur
Because unified memory moves pages automatically and only when needed, the observable runtime behavior depends on how frequently paging occurs. The QLoRA authors point out that paging events tend to be triggered by "mini-batches with long sequence length" and that in their experience such events are rare for their training schedules. When paging is rare, the extra page transfer overhead has little or no measurable impact on wall-clock training speed, because the normal execution spends most of its time in GPU-bound kernels that do not induce fresh page faults.

However, if page migrations happen frequently — for example, if every iteration causes eviction and reload of large optimizer pages — then those repeated host↔device transfers can add noticeable overhead. The paper therefore cautions that while the paged optimizer approach prevents out-of-memory crashes, it is not free: excessively frequent page transfers will slow down training. The authors explicitly note that they do not provide a full characterization of when slowdowns become significant and identify this as an area for future measurement and study.

Thus, the expected runtime profile is: when paging is infrequent (occasional evictions for rare long sequences), runtime is essentially unchanged; when paging becomes frequent, training slows down due to repeated page transfers. The exact inflection point depends on workload characteristics (sequence lengths, batch composition) and host/GPU bandwidths, which the paper does not attempt to fully quantify.

# Empirical note for 65B on 48 GB with batch size 16
The paper reports a concrete empirical observation that illustrates the previous point. For their 65B experiments on a single 48 GB GPU, the authors analyzed runtime behavior and found that with a batch size of 16 the paged optimizer approach "provides the same training speed as regular optimizers." That is, under the conditions of their experiment (model size, hardware, and the batch-size/sequence-length distribution they used), paging did not introduce a noticeable runtime penalty.

They also emphasize that paging events were relatively rare in their workloads, which is consistent with the result that wall-clock performance stayed similar. The authors therefore present paged optimizers as a practical mechanism to allow finetuning of very large models on a single GPU without a penalty in typical settings, while leaving open the question of worst-case or pathological slowdowns when paging is frequent.

# Best practices for micro-batching and sequence length with paging
The QLoRA paper does not prescribe an exhaustive set of batching rules, but the experimental descriptions and the paging rationale imply a small set of practical considerations you should keep in mind.

First, be aware that long sequences are the primary trigger for paging-related spikes. If your dataset contains a mixture of short and very long sequences, those long examples are the points at which the runtime is most likely to evict optimizer pages and incur page transfers. If you can, limit the frequency of very long sequences within an individual mini-batch so that page faults remain infrequent. The paper notes that in their hyperparameter tuning across model sizes they found many hyperparameters generalize, but that batch size (and learning rate) often needed retuning for larger models; they explicitly altered batch size and learning rate when scaling to 33B and 65B models.

Second, treat batch-size tuning as part of the memory strategy. The authors report halving the learning rate for 33B and 65B while doubling the batch size relative to smaller-scale runs; this is an empirical choice that worked within their training regimen. In practice, you should consider batch size together with your expected sequence-length distribution: increasing batch size improves throughput but can increase peak memory demand and thus the probability of paging events.

Third, the paper positions paged optimizers as a mechanism to tolerate occasional peaks rather than a substitute for careful batching design. If your workload will induce paging on every iteration (for example, if every mini-batch contains long sequences large enough to force eviction), expect overhead; the paper recommends treating such cases cautiously and suggests further empirical study to understand the tradeoffs.

# Monitoring paging events and diagnosing OOM vs paging stalls
The QLoRA paper does not provide an instrumentation or monitoring toolbox for paging events; instead it documents the conceptual indicators you should use to distinguish between an out-of-memory failure and paging-related slowdowns.

A useful high-level distinction drawn from the paper's description is this: if the training process immediately terminates with a GPU out-of-memory error, paging either was not enabled or could not prevent eviction (for example because no host memory was available or the allocator was not using unified memory for the relevant tensors). By contrast, when unified-memory paging is active the training process continues; the symptom is not a crash but a change in runtime behavior (occasional stalls or reduced throughput) that corresponds to page migrations between the host and the GPU. The authors report that, in their experiments, paging events were rare and did not measurably affect throughput for certain configurations (e.g., 65B on 48 GB with batch size 16), but they recommend further study to map the boundary between "rare, harmless paging" and "frequent, performance-degrading paging."

Because the paper treats paging as an automatic memory-management behavior, diagnosing performance requires correlating observed slowdowns with the parts of the training loop that require optimizer state residency (the update step). If stalls co-occur with optimizer-update phases, that suggests page transfers of optimizer state are happening. If, on the other hand, the job fails with an immediate OOM at forward or backward time, the system did not (or could not) migrate pages to host memory successfully.

In sum, the QLoRA contribution regarding paged optimizers is primarily architectural: allocate optimizer state in a manner that lets the CUDA unified-memory runtime evict and reload it automatically, thereby converting some hard OOM failure modes into potentially costly but non-fatal page transfers. The paper documents that, in their setups, this approach makes single-GPU finetuning of very large models practical without an observable speed penalty in representative settings, while leaving open a detailed empirical characterization of when paging-induced slowdowns become significant.
