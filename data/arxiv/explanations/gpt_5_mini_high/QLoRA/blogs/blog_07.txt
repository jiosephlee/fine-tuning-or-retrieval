# Your First QLoRA Finetune: A Practical Roadmap

TL;DR — QLoRA is a memory‑efficient recipe that lets you finetune very large pretrained models by storing the base weights in 4‑bit (NF4) and training small Low‑Rank Adapters (LoRA) in full precision. This post walks through the minimal, practical steps to reproduce the approach from the QLoRA paper using open‑source tooling (QLoRA + bitsandbytes + Hugging Face). You’ll learn what to quantize, where to place LoRA adapters, what to watch for with hyperparameters and memory, and how to run quick evaluations.

## Why QLoRA (one paragraph)
QLoRA reduces the memory footprint of finetuning a 65B model from hundreds of GBs to a single 48GB GPU (paper: from >780GB to <48GB) while preserving 16‑bit finetuning performance. It does this by (1) storing the pretrained weights in a 4‑bit NormalFloat format (NF4) tuned for normally distributed weights, (2) double‑quantizing the quantization constants to save more memory, (3) using LoRA adapters to learn task updates, and (4) using paged optimizers to avoid optimizer memory spikes. The authors used this to produce the Guanaco models (e.g., Guanaco‑65B that reaches ~99.3% of ChatGPT on the Vicuna benchmark).

## Before you start — minimal requirements & pointers
- Hardware: single GPU with enough memory for your target model: 24GB consumer GPUs can finetune 33B with QLoRA (paper example), 48GB GPUs are used for 65B. Smaller models (7B) fit easily (inference ~5GB).
- Software & repos: QLoRA implementation and CUDA kernels (https://github.com/artidoro/qlora) and bitsandbytes (https://github.com/TimDettmers/bitsandbytes). Hugging Face transformers integration is supported in these projects.
- Data: supervised instruction datasets (paper experimented with OASST1, Alpaca, FLAN v2, etc.). The paper found data quality matters more than size: OASST1 (≈9k high quality samples) outperformed much larger datasets in some chatbot evaluations.
- Objective: cross‑entropy supervised finetuning (no RLHF required to reproduce QLoRA results in the paper).

## The one‑line recipe
1. Load a pretrained model into 4‑bit NF4 storage with double quantized scales.
2. Dequantize to BF16 at runtime for computation.
3. Attach LoRA adapters to (almost) every linear layer in the transformer.
4. Train only the LoRA weights (BF16), using gradient checkpointing and paged optimizers.
5. Evaluate with nucleus sampling (p=0.9, temperature=0.7) and either human or GPT‑4 / Elo comparisons.

Below are the practical details for each step.

## Step 1 — choose a base model and dataset
Pick a base model that matches your compute and target: LLaMA 7B/13B/33B/65B were used in the paper. If you want to reproduce the paper’s high‑end results, use the largest model you can fit with QLoRA: the authors show 33B on a 24GB card and 65B on 48GB.

For instruction tuning data, prefer high‑quality human conversational datasets if you target chat behavior. The paper highlights OASST1 as a strong, compact dataset that produced top results for Guanaco.

Note about licenses: verify that the base checkpoint you use is permitted for your use case.

## Step 2 — enable 4‑bit quantization (NF4) + double quantization — what to do and why
QLoRA’s storage format differs from naive 4‑bit quantization in two important ways:

- NF4 (4‑bit NormalFloat): instead of uniform integer bins or a plain 4‑bit float, NF4 uses quantile bins matched to a standard normal distribution, then rescales. Because pretrained weights are approximately zero‑mean normal, this provides an information‑theoretically better 4‑bit mapping and lower quantization error than Int4 or plain FP4.

- Double Quantization: quantization uses per‑block scales (quantization constants). Storing those constants in 32‑bit for many small blocks can be expensive. Double quantization compresses those constants further (the paper uses an 8‑bit float quantization for those constants) to save memory while preserving accuracy. The paper uses blocksize 64 for weight blocks and blocksize 256 for quantized constants as a working point.

What to do in practice:
- Use the QLoRA / bitsandbytes code that implements NF4 + double quantization and the efficient CUDA kernels. That code handles block sizes and the double quantization pipeline for you.
- Set your computation dtype to BF16 (or FP16/BFloat16 variant supported by your hardware). The 4‑bit values are dequantized to BF16 before matmuls.

Why this matters: NF4 + double quantization is what lets you compress the base weights aggressively (storage) without hurting the forward and backward computations needed to backpropagate to LoRA adapters.

## Step 3 — place LoRA adapters (important): cover all linear layers
Central finding from the paper: the single most important LoRA hyperdecision is *where* adapters are applied. Applying LoRA only to a subset (e.g., query/value projections) is not sufficient to match full‑model finetuning for larger models. To replicate the paper’s recovery of 16‑bit performance:

- Put LoRA adapters on essentially every linear projection inside transformer blocks (i.e., the dense layers and attention projections).
- The LoRA update has the familiar form:
  $$
  \mathbf{Y} = \mathbf{X}\mathbf{W} + s\,\mathbf{X}\mathbf{L}_1\mathbf{L}_2
  $$
  where $\mathbf{L}_1\in\mathbb{R}^{h\times r}$ and $\mathbf{L}_2\in\mathbb{R}^{r\times o}$ are the adapter factors and $s$ is a scaling constant.

Implementation pointers:
- Use a PEFT/LoRA library or the QLoRA code. The QLoRA repo already applies adapters at every linear layer in the authors’ experiments.
- You only update the LoRA parameters (they are BF16); base weights remain frozen in 4‑bit storage and are dequantized to BF16 for computation.
- The paper finds the exact projection rank $r$ is not the dominant factor affecting final performance; increasing adapter coverage is far more important than tuning $r$ aggressively.

## Step 4 — training recipe and stable hyperparameter guidance
The paper’s practical guidance for stable training is empirical rather than prescriptive; follow this workflow:

- Objective: supervised cross‑entropy on your chosen instruction data. The paper’s high‑performing Guanaco models were trained with cross‑entropy only (no RLHF).
- Gradient checkpointing: use it — activation memory is the dominant memory consumer. QLoRA uses checkpointing together with paged optimizers to avoid spikes.
- Learning rate and batch size: the authors searched learning rates in the range $1\mathrm{e}{-6}$ to $5\mathrm{e}{-5}$ and batch sizes from 8 to 128 when tuning the 7B baselines. They found that hyperparameters found at 7B generalize to larger models except for learning rate and batch size. For 33B/65B they report halving the learning rate and doubling the batch size relative to the 7B tuned setting.
- Compute dtype: BF16 (computation), storage: NF4 (4‑bit). Dequantization to BF16 happens at runtime for matmuls.
- Optimizers: use optimizers with paged storage for states (the QLoRA repo implements paged optimizers using NVIDIA unified memory). This avoids OOM when batch/seq length induces spikes.
- Epochs / steps: the paper suggests hyperparameters other than LR and batch size generalize. It’s practical to tune on a small model first (7B) and transfer those settings.

Tip: tune your hyperparameters at a small scale (7B) while keeping the same dataset and training loops. Then scale the LR / batch size with the paper’s heuristic for larger models.

## Step 5 — quick, lightweight evaluation to check everything’s working
- Sampling for qualitative checks: nucleus sampling with $p=0.9$ and temperature $0.7$ (used in the paper for chatbot outputs).
- Automated quantitative checks:
  - MMLU 5‑shot accuracy for a quick sense of general knowledge/zero‑shot abilities (if relevant to your task).
  - Vicuna prompt set and OASST1 validation prompts for chatbot‑style checks.
- Human vs model evaluation: the paper used GPT‑4 as a cheap automated judge relative to ChatGPT and also ran human AMT evaluations; they caution GPT‑4 order bias (preference for the response shown first) and recommend averaging over both prompt orderings and using pairwise Elo aggregation for robust rankings.

If you’re reproducing a paper run, use pairwise comparisons and Elo scoring to rank your model against baselines. The authors aggregated pairwise wins into Elo to reduce the problems with absolute scoring.

## Common pitfalls and how to fix them
- “My QLoRA run is OOM”: ensure gradient checkpointing is enabled and use the paged optimizer provided by the QLoRA repo (it uses NVIDIA unified memory). Also reduce batch size or sequence length.
- “My LoRA finetune underperforms the 16‑bit baseline”: check that LoRA adapters are applied across all linear layers (not just attention q/k/v). Confirm that NF4 + double quantization code path is used (FP4 performed worse in the paper). Make sure compute dtype is BF16 so dequantized weights are computed at higher precision.
- “Quantization constants blowing memory”: double quantization (quantize the scales) is a core QLoRA trick. Use blocksize 64 for weights and blocksize 256 for the quantized scales as in the paper’s implementation for a good memory/accuracy tradeoff.
- “Inconsistent evaluation vs paper”: beware that evaluation has noise: the Vicuna style scoring has wide CIs and automated GPT‑4 judgments show order effects. Use Elo and multiple seeds/evaluators.

## Practical checklist before you kick off training
- [ ] Clone QLoRA repo and bitsandbytes; check the CUDA kernels are compiled and compatible with your CUDA driver.
- [ ] Confirm you can load the base model in 4‑bit NF4 mode and that dequantization to BF16 works.
- [ ] Attach LoRA adapters to all linear layers (use the QLoRA default adapter placement).
- [ ] Enable gradient checkpointing and paged optimizer support.
- [ ] Tune LR and batch size at 7B; when moving to 33B/65B halve LR and double batch size per the paper’s guidance.
- [ ] Use cross‑entropy supervised training; checkpoint LoRA weights only.
- [ ] Run a small evaluation: generate examples with nucleus sampling (p=0.9, temp=0.7) and compute quick metrics (MMLU / prompt set).

## Final notes and realistic expectations
QLoRA is a practical, well‑engineered point on the compute/precision curve: you get the benefits of larger parameter counts with much lower memory use, while recovering the accuracy of 16‑bit finetuning. The paper’s authors used QLoRA to train Guanaco models that match or nearly match ChatGPT on the Vicuna benchmark (e.g., Guanaco‑65B ≈ 99.3% of ChatGPT as measured by their pipeline). That said, real‑world finetuning still requires careful validation of data quality, evaluation protocols, and safety checks (the paper stresses that data quality often beats dataset size for instruction tuning).

If you want a ready‑made starting point, clone the QLoRA repo and run the sample scripts. Tune at 7B to find stable hyperparameters, scale the training with the paper’s LR / batch scaling rule, and use NF4 + double quantization + paged optimizers. Happy finetuning — and welcome to a much more accessible way of tuning very large models.
