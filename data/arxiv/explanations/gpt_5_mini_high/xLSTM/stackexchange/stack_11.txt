\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### Does xLSTM have constant memory in sequence length during training or only at inference?
Question:
The paper claims linear compute and constant memory w.r.t. sequence length. For inference this is clear, but for training, backpropagation through time typically stores activations from each time step, leading to $O(T)$ memory.
- Is the constant-memory claim only about inference? Or do you use checkpointing/recompute/scan tricks to keep training memory sublinear in $T$?
- If so, what is the exact training-time memory complexity and what is the practical overhead?
Answer:
Short answer: the paper’s “constant memory w.r.t. sequence length” statement is best read as a statement about the model’s recurrent working memory and about inference/decoding, not about naive backprop through time. For training with standard autodiff you still need $O(T)$ activation storage unless you deliberately use recomputation/checkpointing or a custom backward; the paper does not explicitly claim it used some magic that makes training memory independent of $T$.

Why (intuitively). xLSTM is a recurrent-style model: its internal state (the sLSTM scalar cells or the mLSTM matrix memory) has a fixed size per layer that does not grow with the number of time steps $T$, so when you step the model forward at inference you only carry a fixed-size state forward. That is exactly the difference the authors highlight compared to Transformers, whose attention caches grow with $T$. So for inference/online decoding the peak memory that depends on the context length is constant (it depends on model dimension $d$, e.g. $O(d)$ for sLSTM or $O(d^2)$ per matrix memory in mLSTM), not on $T$.

Why training is different (technical). Reverse‑mode autodiff (backprop through time) normally needs the forward activations (gate pre‑activations, intermediate vectors, etc.) for every time step to compute gradients. If you run training naively in PyTorch/TensorFlow, peak memory scales like $O(T\cdot A)$ where $A$ is the per‑time‑step activation footprint (vectors $q,k,v$ of size $O(d)$, and — depending on how you implement the outer products — temporaries of size $O(d^2)$ could appear). So standard training memory is $O(T)$ in $T$ (times depend on $d$, batch size, number of layers).

What the paper says (and what it doesn’t). In Section “Memory and Speed Considerations” the authors state that xLSTM “have a linear computation and a constant memory complexity with respect to the sequence length.” The most natural reading in the paper’s text and experiments (they explicitly discuss generation time and maximal decoding throughput) is that this constant‑memory claim is about the recurrent state and inference/decoding, and about the fact that the model’s state does not grow with $T$. The paper does not give a detailed description of a training‑time scheme that magically makes autograd memory independent of $T$, nor does it say they relied on a specific global checkpointing/recompute protocol in the training runs reported. They do note (a) mLSTM “can be reformulated in a parallel version” and (b) they implemented fast CUDA kernels for sLSTM with “GPU memory optimizations to the register level.” Those implementation remarks suggest they took care to avoid huge temporaries (especially for the $d\times d$ outer products) but they do not amount to a general claim that training used constant memory without recomputation.

If you want sublinear or constant memory during training (practical options and costs). To make training memory sublinear you must explicitly use one of the standard techniques:

- Checkpointing / segmental recomputation: divide the sequence into blocks, store only block checkpoints, and recompute activations for each block during backward. A common practical choice is the “$\sqrt{T}$” checkpointing scheme (checkpoint every $\approx\sqrt{T}$ steps) which reduces peak activation memory to $O(\sqrt{T}\cdot A)$ while incurring roughly a $2\times$ compute overhead. More generally, choosing block size $k$ gives peak memory $O(k\cdot A)$ and recomputation cost $\gtrsim$ a small constant $\times T$ (with the $\sqrt{T}$ choice being a good tradeoff).  
- Aggressive recomputation (store almost nothing): you can reduce memory to $O(1)$ in theory but the compute overhead becomes very large (you may need many recomputed forward passes), so this is usually impractical.  
- Optimal checkpointing algorithms (e.g. “revolve”): give better time/memory tradeoffs than naïve schemes but are more complex to implement.  
- Fused custom kernels / adjoint implementations: write a custom forward+backward CUDA kernel for the entire recurrence (or for a block) that keeps only the minimal set of intermediates (or recomputes them inside the kernel). This can get you very low peak memory and good wall‑clock performance, but it is engineering‑heavy and hardware specific. The paper’s note about register‑level GPU optimizations for sLSTM suggests the authors used fused kernels to make inference/training efficient, but the paper does not publish the exact autograd strategy used for reducing training memory.

Concrete bookkeeping (simple formulas). Let $T$ be sequence length, $A$ the per‑time‑step activation size (depends on $d$, number of layers and whether you materialize outer products), and $M_{\text{model}}$ the model / recurrent state size (e.g. $O(d^2)$ per mLSTM memory). Then

- Naive training memory $\approx O(M_{\text{model}} + T\cdot A)$.  
- With block checkpointing of block size $k$ you can get peak memory $\approx O(M_{\text{model}} + k\cdot A)$ with recomputation overhead about $O(T)$ extra forward work (in practice often $\approx 2\times$ wall‑clock). Choosing $k \approx \sqrt{T}$ gives the familiar $O(\sqrt{T})$ memory and $\approx 2\times$ compute tradeoff.  
- To make the $T$ term disappear entirely you must accept large recomputation overhead or implement a fused custom backward/adjoint; the paper does not supply an explicit $T$-independent training algorithm or timings for such a scheme.

Practical overheads reported in the paper. The authors report implementation/runtime observations (these are mostly about inference/throughput): their sLSTM CUDA kernel is “typically less than two times slower than mLSTM,” and their mLSTM implementation is about $4\times$ slower than FlashAttention / the scan used in Mamba (they list these numbers in the “Memory and Speed Considerations” / “Limitations” sections). Those are wall‑clock notes about current implementations; they do not give a training‑memory asymptotic or say they trained with constant active memory in $T$.

Takeaway and what to do if you want to reproduce it. Treat the paper’s constant‑memory claim as an inference/working‑memory claim: xLSTM’s state does not grow with $T$, so decoding memory is constant in $T$ (and this is the reason they can decode with very large batch sizes). For training, assume $O(T)$ activation memory in a standard autograd run; to get sublinear or constant memory you must choose and implement a checkpointing/recompute strategy or write fused backward kernels. If you want exact details of what the authors used in their training runs, check their code at the repository cited in the paper (https://github.com/NX-AI/xlstm) or ask the authors — the paper’s text and appendices do not document a claim that training was done with strictly constant memory in $T$ without recomputation.
