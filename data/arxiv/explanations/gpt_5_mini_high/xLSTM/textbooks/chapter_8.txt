\title{A Textbook about the Paper: "xLSTM: Extended Long Short-Term Memory"}

Chapter 8: Computation, Memory, and Parallelization

# Linear compute and constant memory in sequence length

A fundamental design goal of xLSTM is to keep the work and the working memory required to process a sequence bounded in a way that does not blow up as the sequence gets longer. The paper emphasizes two related claims: (1) xLSTM networks have linear computation with respect to the sequence length, and (2) xLSTM networks have constant memory complexity with respect to the sequence length. It is important to be precise about what those statements mean.

"Linear computation in the sequence length" means that if the model processes a sequence of length $T$, the total amount of arithmetic work grows proportional to $T$ (for fixed model dimensions). In Big‑O notation this is $O(T)$ for fixed hidden dimension(s). This contrasts with architectures whose per‑token work increases with previously seen tokens. For xLSTM the per‑token work is fixed (though it depends on model dimensionality $d$ and on whether a matrix or vector memory is used), so the total compute over a sequence of length $T$ is proportional to $T$.

"Constant memory complexity in the sequence length" means that the working memory the model needs to hold the summarized history does not grow with $T$. In xLSTM the past is summarized (compressed) into a fixed set of internal states: scalar or vector cell states for sLSTM, or a fixed matrix memory for mLSTM. Those states occupy memory that depends on the model dimensions (for example on $d$ or on $d^2$) but not on $T$. Practically, that means that decoding and long‑context inference need not allocate a per‑position key/value cache that grows with the sequence length; rather the historical information is folded into a fixed-size memory.

To anchor the intuition in the paper's equations: in sLSTM the recurrence keeps a (scalar or vector) cell $c_t$ (and a normalizer $n_t$) that summarize all past contributions via multiplicative gates (see the sLSTM forward pass). In mLSTM the memory is a fixed matrix $\mathbf{C}_t\in\mathbb{R}^{d\times d}$ that is repeatedly updated by outer products, so the memory footprint is tied to $d$ rather than to $T$. Because each time step updates and/or queries these fixed-size states, total compute across a sequence of length $T$ is $O(T)$ (with per-step cost determined by the memory representation), and the memory used to hold the state is independent of $T$.

This compressive strategy contrasts with Transformer decoders that store per‑position key/value pairs for the whole context. Those per‑position caches cause memory usage to grow with $T$ and contribute to higher generation-time costs for long contexts (see the experimental comparisons in the paper).

# mLSTM’s O(d^2) cost and parallel GPU execution

mLSTM increases the LSTM memory cell from a scalar (or vector) to a matrix $\mathbf{C}_t\in\mathbb{R}^{d\times d}$. The matrix memory is updated by a covariance (outer‑product) rule:

\[
\mathbf{C}_t \;=\; f_t \,\mathbf{C}_{t-1} \;+\; i_t \,\mathbf{v}_t \,\mathbf{k}_t^\top,
\]

and retrieval is (schematically)

\[
\tilde{\mathbf{h}}_t \;=\; \frac{\mathbf{C}_t \,\mathbf{q}_t}{\max\{|\mathbf{n}_t^\top \mathbf{q}_t|,\,1\}},
\]

where $\mathbf{k}_t,\mathbf{v}_t,\mathbf{q}_t\in\mathbb{R}^d$ are key, value and query vectors and $\mathbf{n}_t$ is the normalizer. Two operations dominate the per‑step cost: forming the outer product $\mathbf{v}_t \mathbf{k}_t^\top$ and multiplying the matrix $\mathbf{C}_t$ by the query $\mathbf{q}_t$. Both of these are quadratic in the hidden dimension, i.e., they require on the order of $d^2$ scalar operations. In complexity terms the per‑token arithmetic for mLSTM is $O(d^2)$, so for a full sequence of length $T$ the work is $O(T\cdot d^2)$.

The paper emphasizes that this $d^2$ cost is a tradeoff: raising memory capacity substantially (from scalar or vector memory to matrix memory) increases computational load. However, two important mitigating facts follow from the design. First, the matrix memory $\mathbf{C}_t$ is not a parameter tensor; it is a dynamic state that carries information about the sequence but does not inflate the number of learned parameters. Second, the $d\times d$ arithmetic—outer products and matrix–vector multiplications—is composed of standard linear algebra operations that GPUs handle well. Because the updates and retrievals are regular dense matrix operations, they can be expressed and executed in parallel using GPU kernels and batched matrix routines. The paper explicitly notes that the mLSTM recurrence can be reformulated into a parallel version (see appendix), and that the computations parallelize analogously to other GPU‑efficient attention or scan implementations.

Thus, the practical tradeoff for mLSTM is: larger representational capacity (matrix memory, better rare‑token performance and associative recall) versus higher arithmetic cost per token ($O(d^2)$), with the hope that optimized parallel kernels will reduce wall‑clock overhead.

# sLSTM’s sequential nature due to memory mixing

sLSTM augments the LSTM idea with exponential gating and new normalization, while retaining inter‑cell memory mixing through recurrent (hidden‑to‑hidden) connections. In other words, sLSTM variants include terms where the current computation depends on the previous hidden state $h_{t-1}$ (for example via recurrent matrices $\mathbf{R}_{\mathbf{z}},\mathbf{R}_{\mathbf{i}},\mathbf{R}_{\mathbf{f}},\mathbf{R}_{\mathbf{o}}$ in the multi‑cell extension). Those hidden‑to‑hidden connections implement memory mixing across cells and time.

Because each time step's gate activations and inputs depend on the previous hidden state, computation cannot be trivially parallelized across time steps: you must compute $h_{t-1}$ before computing $h_t$. This sequential dependence is the reason sLSTM is not parallelizable in the same way as mLSTM. The paper frames this drawback but also highlights the payoff: memory mixing enables state tracking and other sequence‑sensitive computations that non‑mixing architectures (many SSMs or attention variants) cannot perform as effectively. In empirical terms, sLSTM's memory mixing helped solve formal language and state‑tracking tasks that were challenging for strictly parallel models.

Recognizing the practical cost of sequential processing, the authors implemented a highly optimized CUDA kernel for sLSTM with GPU memory optimizations down to the register level. That implementation narrows the performance gap: the paper reports that their optimized sLSTM kernel is typically less than two times slower than their (parallel) mLSTM implementation. So, while sLSTM enforces sequential computation and so is inherently less parallel across time, careful low‑level implementation can make it competitive in wall‑clock time while preserving the expressivity benefits of memory mixing.

# Parallels to FlashAttention and GLA for efficient scans

The paper draws explicit parallels between mLSTM and GPU‑efficient attention/scan implementations such as FlashAttention and Gated Linear Attention (GLA). The comparison is an analogy about implementation style and parallelizability rather than an identity of algorithms: FlashAttention and GLA are techniques designed to reduce memory overhead and improve GPU throughput by restructuring attention or gated scans into blockwise, cache‑friendly computations. Similarly, mLSTM's matrix memory and its update/retrieval patterns can be expressed as dense linear algebra operations that lend themselves to blocked, parallel execution on GPUs.

This parallelizability is significant because it points to a path for improving mLSTM performance: just as FlashAttention reshaped attention to gain large speedups and lower memory pressure, mLSTM can benefit from the same engineering principles (blocked kernels, attention to memory tiling, fused operations). The paper remarks that faster CUDA kernels for mLSTM could be obtained "in the vein of FlashAttention," indicating that further engineering work—reorganizing the $d\times d$ updates and multiplications into cache‑efficient GPU kernels—should materially close the gap between algorithmic promise and realized throughput.

# CUDA implementation notes and current performance gaps

The paper is explicit about the current state of implementations and practical performance tradeoffs. Two implementation points stand out.

First, sLSTM received a specialized CUDA implementation with register‑level memory optimizations. That implementation reduces the penalty of sequential recurrence: empirically, the optimized sLSTM kernel is typically less than two times slower than the parallel mLSTM kernel used by the authors. This demonstrates that careful kernel engineering can compensate substantially for the lack of timewise parallelism.

Second, mLSTM's CUDA kernels in the presented work are not yet fully optimized. The authors report that their current mLSTM implementation is about four times slower than FlashAttention or the scan used in Mamba. In other words, although mLSTM admits a parallel formulation and is amenable to efficient dense linear algebra, the available kernels in this work left sizable headroom for improvement. The paper explicitly notes that faster kernels could be realized following the strategies used by FlashAttention.

There are also practical caveats from the experimental setup. For example, when comparing generation times the authors used existing implementations from HuggingFace for baselines and included a static key‑value cache for the Transformer baseline; they also mention that compilation/optimization attempts (e.g., full cache compilation of the Transformer model or compiling Mamba with \texttt{torch.compile}) did not work at the time of the experiments. These remarks emphasize that empirical speed comparisons are sensitive to low‑level engineering and that the reported gaps reflect both algorithmic and current‑implementation status.

# Inference behavior: generation latency and throughput

The paper reports inference‑time measurements that illustrate the practical implications of the computation and memory characteristics. Two metrics are highlighted: generation latency as context length grows, and decoding throughput (tokens per second) as batch size and prefill settings vary.

On generation latency, the empirical finding is that xLSTM and other recurrent models (Mamba and RWKV in the comparison) exhibit linear scaling of generation time with respect to context length, while the Transformer baseline (Llama in the experiments) shows quadratic growth in generation time. The experiments used 1.3B‑parameter models and a test condition with batch size 1 and a pre‑fill of 16 tokens (a setting favorable to the Transformer), and nevertheless the xLSTM models showed linear growth in wall‑clock time as the context length increased.

For decoding throughput, the constant memory footprint of xLSTM pays dividends: because xLSTM does not need to allocate a per‑position cache whose size grows with context length, it can support much larger batch sizes during decoding. The paper reports that xLSTM achieves the highest throughput in their throughput measurements precisely because it can use higher batch sizes than the Transformer baseline (whose memory use limits batch size). In practical terms, this means xLSTM can produce more tokens per second when the decoding scenario permits batching, which is an important industrial metric when serving many requests in parallel.

These empirical points tie directly to the theoretical complexity observations: constant memory per request lets you pack more requests or larger batches into the same device memory, and $O(T)$ computational scaling gives predictable latency growth as you extend context.

# Memory footprint vs. KV caches in Transformers

A key cause of Transformers' growing memory footprint with context length is the per‑position key/value cache used during auto‑regressive decoding. Each decoded token typically contributes a key and a value for every attention layer; keeping these cached representations for later attention raises memory usage proportionally to the context length and to the number of layers. In practice this per‑position caching is what forces Transformers to consume substantially more memory for long contexts, and it constrains batch sizes during decoding.

xLSTM takes the opposite design choice: rather than preserving the entire sequence of positional representations, it compresses past information into fixed‑size internal states. For sLSTM, the compressed state is scalar or vector cell states (or multiple cells); for mLSTM, it is a matrix memory $\mathbf{C}_t$ of size $d\times d$ that accumulates outer‑product updates. In complexity terms, the Transformer cache memory grows like $O(T)$ (times depth and $d$), whereas xLSTM memory is $O(d)$ for sLSTM (or $O(d^2)$ for mLSTM) and does not include an extra factor of $T$.

That difference explains why xLSTM can sustain larger inference batch sizes and why its per‑request memory remains constant as context length grows. The paper summarizes this succinctly: "Contrary to Transformers, xLSTM networks have a linear computation and a constant memory complexity with respect to the sequence length," and it uses that property to motivate industrial and edge deployments.

# Industrial implications: compressive memory and edge deployment

The computational and memory characteristics of xLSTM give rise to concrete deployment implications that matter in industrial and edge settings. First, the compressive, constant‑size memory is a strong advantage where device memory is constrained. Edge devices (or inference servers that prioritize high concurrency) benefit when the per‑request working set does not grow with the requested context length. Because xLSTM summarises histories into fixed-size states rather than caching full histories, it enables longer effective context handling without proportionally larger memory footprint.

Second, throughput considerations favor xLSTM in batched serving scenarios: with constant memory per request, a single GPU can hold more concurrent requests and thus achieve higher aggregate tokens‑per‑second throughput. The experiments in the paper show that xLSTM achieves the highest throughput among the compared models, driven by the ability to use higher batch sizes than Transformers with KV caches.

Third, there is a nuanced tradeoff between capacity and computational cost. mLSTM delivers richer memory capacity (matrix memory) that improves rare‑token modeling and associative recall, but it incurs an $O(d^2)$ per‑token cost. In production this translates to a choice: allocate more compute to get better memory behavior (mLSTM), or choose a cheaper vector memory variant (sLSTM) and accept different expressivity/parallelism characteristics. The paper notes that mLSTM memory updates do not increase parameter count, so capacity can be increased at runtime by increasing $d$, but with the accompanying quadratic compute growth.

Finally, practical deployment requires attention to low‑level engineering. The authors acknowledge that mLSTM kernels in their work are not yet optimized to the utmost, and that further engineering (following ideas like FlashAttention) should reduce the implementation gap. They also highlight limitations to bear in mind in production: careful forget‑gate initialization is important, the matrix memory can become overloaded if contexts are extremely long (though the paper reports good behavior up to 16k contexts), and extensive architecture and hyperparameter optimization remain to be done.

In short, for industrial cases where memory predictability, long‑context handling, and high concurrency matter, xLSTM's compressive, constant‑memory design is a compelling alternative to per‑position caching Transformers. The final choice between sLSTM and mLSTM (or a hybrid xLSTM stack) should be guided by the workload's sensitivity to state‑tracking, memory capacity needs, and available compute and kernel optimization investment.
