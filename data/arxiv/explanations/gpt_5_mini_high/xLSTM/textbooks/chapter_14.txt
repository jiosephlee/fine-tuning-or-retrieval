\title{A Textbook about the Paper: "xLSTM: Extended Long Short-Term Memory"}

Chapter 14: Practical Recipes and Engineering Guidance

This chapter collects the engineering lessons and concrete, experiment-grounded recipes reported in the xLSTM paper. Each section ties a practical decision to the model mechanisms and to the empirical findings in the paper so you can make informed trade-offs when designing, training, and deploying xLSTM models across scales and budgets.

# Choosing the sLSTM:mLSTM block ratio (xLSTM[a:b])

The paper uses the notation xLSTM[$a$:$b$] to denote the ratio $a/b$ of mLSTM-based versus sLSTM-based xLSTM blocks. Concretely, xLSTM[7:1] means that out of 8 blocks, 7 are mLSTM-based and 1 is sLSTM-based; for a total of 48 blocks this corresponds to 42 mLSTM blocks and 6 sLSTM blocks. Use that notation to record and compare variants.

Why this ratio matters
- mLSTM and sLSTM bring different capabilities. mLSTM expands the scalar LSTM memory to a matrix memory $\mathbf{C}\in\mathbb{R}^{d\times d}$ with the covariance-style update
  $\displaystyle \mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \,\mathbf{v}_t \,\mathbf{k}_t^\top$,
  so it provides much larger storage capacity and is designed to be parallelizable. The paper shows mLSTM helps rare-token prediction and improves overall language-model perplexity when scaled.
- sLSTM keeps a scalar memory but preserves memory mixing through recurrent connections and introduces exponential gating plus a normalizer state. That mixing enables state-tracking behavior (formal languages, parity-like tasks) that methods lacking memory mixing cannot solve in the paper’s experiments.

Empirical signals to guide the ratio
- If your task requires explicit state tracking or formal-language-style reasoning (the paper’s synthetic formal-language tests), you need memory mixing: sLSTM-only (xLSTM[0:1]) or hybrids with sLSTM are effective. Models lacking memory mixing failed on such tasks.
- If your primary target is large-scale language modeling (perplexity on SlimPajama) the paper finds mLSTM-heavy configurations perform best. Both xLSTM[1:0] (only mLSTM) and xLSTM[7:1] performed very well in the 15B and 300B token experiments; xLSTM[1:0] gave slightly better results on many language-domain evaluations (PALOMA).
- For associative-recall style memory benchmarks, a hybrid (xLSTM[1:1] in the experiments) gave the best non-Transformer performance—i.e., sLSTM does not necessarily reduce memory capacity and can even help.

Practical recipe
- For a general-purpose language model: start mLSTM-dominant (e.g., xLSTM[1:0] or a high $a:b$ ratio such as xLSTM[7:1]) because that configuration gave the best validation perplexities in the paper’s LM experiments.
- If you expect significant state-tracking, programmatic reasoning, or formal-language behavior: include sLSTM blocks (at least a few) so the network can leverage memory mixing.
- For mixed workloads (some long-range associative memory and some state tracking), use a hybrid mix—this is precisely what the xLSTM[1:1] and xLSTM[7:1] experiments explored.

# Dimensionality, number of cells/heads, and projections

Key equations and structures to keep in mind
- mLSTM memory is a full matrix: $\mathbf{C}_t\in\mathbb{R}^{d\times d}$. Keys, values, and queries are $d$‑dimensional vectors:
  \begin{align*}
    \mathbf{q}_t &= \mathbf{W}_q \mathbf{x}_t + \mathbf{b}_q,\\
    \mathbf{k}_t &= \frac{1}{\sqrt{d}}\,\mathbf{W}_k \mathbf{x}_t + \mathbf{b}_k,\\
    \mathbf{v}_t &= \mathbf{W}_v \mathbf{x}_t + \mathbf{b}_v.
  \end{align*}
  The $1/\sqrt{d}$ key scaling is part of the design reported in the paper.
- The mLSTM covariance update is
  $\displaystyle \mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \,\mathbf{v}_t \,\mathbf{k}_t^\top$,
  and retrieval uses the normalizer $\mathbf{n}_t = f_t \mathbf{n}_{t-1} + i_t \mathbf{k}_t$ and
  $\displaystyle \tilde{\mathbf{h}}_t = \frac{\mathbf{C}_t \mathbf{q}_t}{\max\{|\mathbf{n}_t^\top \mathbf{q}_t|,\,1\}}$.

Implications for dimension and cells
- Because mLSTM stores a $d\times d$ matrix, increasing $d$ increases memory capacity roughly quadratically (and increases compute cost for the memory update and retrieval similarly). The paper explicitly calls out this trade-off: memory capacity vs computational complexity.
- The paper treats “multiple memory cells” and “multiple heads” differently for sLSTM and mLSTM:
  - For mLSTM: multiple heads and multiple cells are equivalent because there is no memory mixing.
  - For sLSTM: multiple memory cells enable memory mixing via recurrent matrices ($\mathbf{R}_{\mathbf{z}}$, $\mathbf{R}_{\mathbf{i}}$, etc.), and multiple heads allow mixing within a head but not across heads. Thus head/cell design matters more for sLSTM.

Projection and block-level choices
- The paper uses different residual block backbones for the two variants: sLSTM is paired with a post up-projection block (non-linear summary in original space, then up-projection to high dimensional space), while mLSTM is paired with a pre up-projection block (linear map to high dimension, then non-linear summarization there). Follow those pairings because they align memory capacity with the embedding dimensionality in the experiments.

Practical recipe
- When you need more memory capacity, increase $d$ on mLSTM blocks, but be mindful of the $d\times d$ cost. Expect higher compute but parallelizable matrix operations; the paper notes this overhead can be handled on GPUs.
- For sLSTM, tune the number of cells/heads to control internal mixing; if state-tracking is important, give sLSTM sufficient internal scalar cells and allow recurrent mixing matrices.
- Use the block pairing from the paper: pre up-projection for mLSTM blocks, post up-projection for sLSTM blocks.

# When to prefer sigmoid vs. exponential forget gates

What the architectures allow
- Both sLSTM and mLSTM permit forget gates $f_t$ to be either sigmoid or exponential:
  \[
    f_t \;=\; \sigma(\tilde{f}_t)\quad\text{OR}\quad f_t \;=\; \exp(\tilde{f}_t),
  \]
  while the input gate is typically exponential in the proposed designs (e.g., $i_t=\exp(\tilde{i}_t)$).

Why exponential gates were introduced
- Exponential gating was introduced to enable the network to “revise storage decisions.” In the paper’s nearest-neighbor search synthetic task, the original LSTM could not revise a stored value when a more similar vector arrived later, whereas xLSTM with exponential gating could. In short: exponential gates increase the range and multiplicative flexibility of storage/removal dynamics, which the experiments show can be important.

Numerical implications and the trade-off
- Exponentials are unbounded and can produce very large values, which can cause overflows and numerical instability. To use exponential gates safely you must implement the stabilization described in the paper (see the next section). The paper shows that with stabilization the exponential gates can be used without changing outputs or derivatives.
- Sigmoid gates are bounded between 0 and 1 and therefore are naturally numerically constrained; they can be chosen when you prefer bounded gating and wish to avoid exponential stabilization mechanisms.

Practical recipe
- Prefer exponential input gating ($i_t=\exp(\tilde{i}_t)$) when you want the stronger revision and learning dynamics introduced in the paper; for the forget gate, use exponential gating together with the stabilization recipe if you need revisability. If you explicitly want simpler bounded gates or want to avoid implementing stabilization, you can retain the sigmoid forget gate variant that is supported by the formulations in the paper.

# Normalizer thresholds and numerical stability tips

The two stabilization/normalization mechanisms to implement exactly as described
1. Stabilizing exponential gates. Because exponentials can overflow, the paper stabilizes input and forget gate products with a running stabilizer $m_t$:
   \begin{align*}
     m_t &= \max\big(\log(f_t) + m_{t-1},\; \log(i_t)\big),\\
     i'_t &= \exp\big(\log(i_t) - m_t\big) = \exp(\tilde{i}_t - m_t),\\
     f'_t &= \exp\big(\log(f_t) + m_{t-1} - m_t\big).
   \end{align*}
   The paper proves (and uses) the fact that replacing $i_t,f_t$ with $i'_t,f'_t$ in the forward pass neither changes the network’s outputs nor the derivatives of the loss w.r.t. parameters. Implementing $m_t$ exactly (working in log-space and using $\max$) is therefore the intended, numerically-stable path when using exponentials.

2. Normalizer threshold for mLSTM retrieval. The mLSTM uses a normalizer vector $\mathbf{n}_t$ and divides by the dot product magnitude when retrieving:
   \[
     \tilde{\mathbf{h}}_t \;=\; \frac{\mathbf{C}_t \mathbf{q}_t}{\max\{|\mathbf{n}_t^\top \mathbf{q}_t|,\,1\}}.
   \]
   The paper recommends taking the absolute value of the dot product and clamping the denominator from below; a typical lower bound used in the experiments is $1.0$ (this follows previous work cited in the paper). This prevents near-zero denominators that would amplify noise or lead to numerical blow-up.

Other practical stability notes (as used in the paper)
- Apply a LayerNorm before projecting inputs to keys and values so that key vectors have zero mean; the paper assumes such a layer-norm and notes that zero-mean keys make the covariance update optimal for separability.
- When implementing exponentials and the stabilizer, do the computations in log-space where appropriate and maintain the stabilizer $m_t$ across time steps.

# Initialization (e.g., forget gate bias) and LayerNorm choices

LayerNorm architecture choice
- The xLSTM architectures in the paper use pre-LayerNorm residual backbones (the residual blocks apply LayerNorm before the block, as in many contemporary LLMs). In addition, the paper assumes a layer-norm before projecting to keys and values for mLSTM to produce zero-mean keys (important for the covariance update behavior).

Forget gate initialization
- The paper highlights as a limitation that the initialization of forget gates must be chosen carefully. It does not prescribe a single numeric initialization but signals that this initialization materially affects behavior. Therefore, treat forget-gate initialization as an important hyperparameter to tune in practice (the paper flagged it as something to be careful about).

Practical recipe
- Use pre-LayerNorm residual backbones as the base architecture (this is what the experiments used).
- Be sure to include a LayerNorm before key/value projections in mLSTM blocks to align with the covariance-memory assumptions.
- Pay attention to forget-gate initialization in experiments and monitor training stability/performance as you vary it; it is recognized in the paper as a crucial setting.

# Training schedules, precision, and gradient stability

Precision and mixed-precision training
- The large-scale experiments in the paper were run with mixed precision. The paper also notes practical issues encountered in mixed-precision training for some other models (e.g., RWKV-5/6 and HGRN2), where the automated mixed-precision path (PyTorch AMP) was not used in some runs. This underscores that mixed precision helps training cost, but precision settings can require per-model attention.

Gradient stability and exponential gates
- The stabilization trick for exponential gates (the $m_t$ stabilizer and the transformed gates $i'_t,f'_t$) is not only numerically required but also constructed so that derivatives are preserved. The paper explicitly shows that using the stabilized gates does not change the outputs nor the gradients w.r.t. parameters; so if you implement exponential gating follow the stabilizer recipe to retain correct gradient behavior.

Practical recipe
- Use mixed precision to reduce memory footprint and speed up training, but validate the mixed-precision path for your particular implementation (AMP or manual handling) because some recurrent/block implementations may require special handling (as the paper’s training notes show).
- If you enable exponential gating, implement the stabilizer exactly to ensure correct forward and backward behavior.
- Monitor training for unexpected precision-related instability—especially when porting or re-implementing models—because the paper observed such sensitivities in other architectures during large-scale runs.

# Inference strategies, batching, and memory budgeting

Asymptotic complexity and decoding behavior
- A core practical advantage emphasized in the paper is that xLSTM networks operate with linear computation and constant memory complexity with respect to sequence length (in contrast to the Transformer’s quadratic attention memory with context length). This gives xLSTM an inference advantage for long contexts and for large batch decoding.
- mLSTM’s matrix memory and update are computationally heavy per step (because of $d\times d$ operations), but the memory usage is constant with the sequence length and the compute is parallelizable. sLSTM incurs hidden–hidden recurrent mixing that prevents full parallelization across time steps, which can slow inference; the authors implemented a custom CUDA kernel that reduced the practical slowdown (it was reported to be less than two times slower than the parallel mLSTM implementation in their setup).

Empirical decoding observations from the paper
- In generation time experiments at the 1.3B scale, xLSTM and other recurrent models exhibited linear scaling with context length, while Llama (Transformer) showed quadratic scaling. Because xLSTM has constant memory usage w.r.t. sequence length, it can use much larger batch sizes than Llama and achieved the highest decoding throughput in the authors’ tests.
- The paper used “pre-fill” during generation experiments (they tested batch size 1 and pre-fill 16) and compared to Transformer implementations that use a static key-value cache; the xLSTM variants still showed the linear-scaling, constant-memory benefits.

Memory budgeting caveats
- The mLSTM matrix memory is independent of sequence length: the memory does not grow with the sequence. However, the finite matrix $\mathbf{C}$ can be overloaded if you push to very long contexts beyond what was tested. The paper notes that this did not appear to be a limitation for contexts tested up to 16k tokens.

Practical recipe
- For high-throughput, long-context decoding prioritize mLSTM-dominant or pure-mLSTM configurations because they are parallelizable and enjoy constant memory for context length.
- If state-mixing is required at inference time (e.g., for entity tracking or program evaluation), include sLSTM blocks but anticipate somewhat higher per-token latencies unless you use the specialized CUDA kernel described by the authors.
- When budgeting memory for inference, remember the matrix-memory $d\times d$ cost for mLSTM blocks and that this cost does not grow with context length—this lets you trade compute for capacity while keeping working memory bounded during decoding.

# Interfacing with existing frameworks and the reference codebase

Reference code and implementation notes
- The paper provides a public code repository: https://github.com/NX-AI/xlstm. That repository is the canonical starting point if you want the exact block implementations, the stabilizer logic for exponential gates, and the authors’ CUDA kernels for sLSTM and parallel mLSTM updates.
- The authors implemented a fast CUDA kernel for sLSTM with GPU memory optimizations (down to register level) to mitigate the lack of parallelizability due to hidden–hidden mixing. For mLSTM they emphasize that it is parallelizable and conceptually analogous to approaches such as FlashAttention, though the authors’ kernels were not as optimized as FlashAttention at the time of writing.

Practical recipe for framework integration
- Start from the authors’ repository to ensure you get the stabilizer $m_t$, the normalizer clamping, the pre/post up-projection block choices, and the pre-LayerNorm residual backbone exactly as used in the experiments.
- If you integrate xLSTM blocks into frameworks that expect Transformer-style layers (HuggingFace, etc.), mind the differences: mLSTM blocks are parallelizable and therefore fit more naturally into batched training loops, while sLSTM blocks require the special CUDA kernel or a scan/loop implementation with different performance characteristics.
- If you intend to run large-scale experiments with mixed precision, validate your AMP path (or alternative mixed-precision mechanism) with xLSTM blocks early, because the paper reports that different architectures have different sensitivities to precision handling.

Closing note
The paper’s experiments and ablations tie most of the engineering guidance above to concrete results: exponential gating plus the matrix memory are central contributors to the empirical gains, pre-LayerNorm backbones were used throughout, and the block-level design choices (pre/post up-projection) were fixed per block type. Use those experiment-proven choices as your baseline and treat forget-gate initialization, mixed-precision settings, and the sLSTM/mLSTM ratio as the primary levers to tune for your task and resource envelope. For code-level detail and exact implementations, consult the reference repository linked in the paper.
