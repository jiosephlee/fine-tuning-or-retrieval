\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### How does the blockwise local softmax in FlashAttention-3 yield the exact global softmax output?
Question:
In the forward algorithm, each CTA processes a query tile $\mathbf{Q}_i$ and loops over key-value blocks $\{(\mathbf{K}_j, \mathbf{V}_j)\}$. The kernel keeps per-row running statistics $m_i$ and $\ell_i$ and updates them via
- $m_i \leftarrow \max\big(m_i, \operatorname{rowmax}(\mathbf{S}_i^{(j)})\big)$ where $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^\top$,
- $\widetilde{\mathbf{P}}_i^{(j)} = \exp(\mathbf{S}_i^{(j)} - m_i)$,
- $\ell_i \leftarrow e^{m_i^{\text{old}} - m_i}\,\ell_i + \operatorname{rowsum}(\widetilde{\mathbf{P}}_i^{(j)})$,
- $\mathbf{O}_i \leftarrow e^{-(m_i - m_i^{\text{old}})}\,\mathbf{O}_i + \widetilde{\mathbf{P}}_i^{(j)} \mathbf{V}_j$,
and finally returns $\mathbf{O}_i \leftarrow \operatorname{diag}(\ell_i)^{-1} \mathbf{O}_i$.
Could someone provide a concise derivation that the final $\mathbf{O}_i$ equals $\operatorname{softmax}(\alpha\mathbf{Q}_i \mathbf{K}^\top)\,\mathbf{V}$ computed exactly (no approximation), and explain why the multiplicative rescalings with $m_i$ and $\ell_i$ preserve numerical stability and correctness?
Answer:
Short answer: FlashAttention-3 implements a streaming (blockwise) version of the standard numerically-stable softmax (the usual log‑sum‑exp trick) and maintains an exact algebraic invariant for the numerator and denominator under a moving per-row shift. By induction one shows that after processing all key blocks the stored accumulators equal the globally shifted numerator and denominator, so the final divide reproduces exactly $\operatorname{softmax}(S)\,V$ (with $S=\alpha QK^\top$) in exact arithmetic. The multiplicative rescalings with $m_i$ and $\ell_i$ are exactly the re‑basings required by the identity
$\exp(a-m_{\text{new}})=\exp(a-m_{\text{old}})\exp(m_{\text{old}}-m_{\text{new}})$, so they preserve correctness and—because $m$ is monotone nondecreasing—keep exponent arguments $\le 0$ and prevent overflow, which is the usual numerical‑stability trick.

Proof (per row, concise). Fix a query tile index $i$ and a single row (drop the row index for clarity). Let the key/value blocks be indexed $j=1,\dots,J$. For block $j$ write the score vector produced by that block as $s^{(j)}\in\mathbb{R}^{B_c}$ (these are the rows of $S_i^{(j)}$). Define the running maximum after processing the first $j$ blocks
$$m^{(j)}=\max_{1\le u\le j}\max_k s^{(u)}_k$$
(with $m^{(0)}=-\infty$). Define the (blockwise) exponentiated vectors with respect to the current shift
$$\tilde p^{(j)}=\exp\big(s^{(j)}-m^{(j)}\big)\qquad(\text{vector of length }B_c).$$
The global (rowwise) softmax numerator and denominator after all blocks are
$$\begin{aligned}
\text{Num}^{\mathrm{glob}}&=\sum_{u=1}^J \sum_{k}\exp\big(s^{(u)}_k - m^{(J)}\big)\,v^{(u)}_k,\\
\text{Den}^{\mathrm{glob}}&=\sum_{u=1}^J \sum_{k}\exp\big(s^{(u)}_k - m^{(J)}\big),
\end{aligned}$$
where $v^{(u)}_k$ is the $k$th row of $V$ inside block $u$. The desired output row is $\text{Num}^{\mathrm{glob}}/\text{Den}^{\mathrm{glob}}$.

Claim (invariant). After processing blocks $1..j$ the kernel's accumulators satisfy
$$\begin{aligned}
O^{(j)} &= \sum_{u=1}^j \sum_k \exp\big(s^{(u)}_k - m^{(j)}\big)\,v^{(u)}_k,\\
\ell^{(j)} &= \sum_{u=1}^j \sum_k \exp\big(s^{(u)}_k - m^{(j)}\big).
\end{aligned}$$
These are exactly the numerator and denominator but expressed using the current shift $m^{(j)}$.

Proof by induction. For $j=1$ we have $m^{(1)}=\max_k s^{(1)}_k$, $\tilde p^{(1)}=\exp(s^{(1)}-m^{(1)})$, so the kernel sets $O^{(1)}=\tilde p^{(1)}V_1$ and $\ell^{(1)}=\mathbf{1}^\top\tilde p^{(1)}$, which matches the claim.

Assume the invariant holds at step $j-1$ with $O^{(j-1)},\ell^{(j-1)}$ representing all previous contributions shifted by $m^{(j-1)}$. When processing block $j$ the code first computes $m^{(j)}=\max(m^{(j-1)},\max_k s^{(j)}_k)$. Two cases:

1. If $m^{(j)}=m^{(j-1)}$ then no re‑bas­ing is needed and the kernel does
   $$O^{(j)}=O^{(j-1)}+\tilde p^{(j)}V_j,\qquad \ell^{(j)}=\ell^{(j-1)}+\mathbf{1}^\top\tilde p^{(j)},$$
   which matches the invariant with shift $m^{(j)}$.

2. If $m^{(j)}>m^{(j-1)}$ then we must convert the old accumulators from being expressed with shift $m^{(j-1)}$ to the new shift $m^{(j)}$. Using the identity
   $$\exp\big(s^{(u)}_k-m^{(j)}\big)=\exp\big(s^{(u)}_k-m^{(j-1)}\big)\exp\big(m^{(j-1)}-m^{(j)}\big),$$
   we get that the entire old numerator and denominator must be multiplied by $\exp(m^{(j-1)}-m^{(j)})$ and then we add the new block written with shift $m^{(j)}$. Thus the kernel performs exactly
   $$O^{(j)}=\exp(m^{(j-1)}-m^{(j)})\,O^{(j-1)}+\tilde p^{(j)}V_j,$$
   $$\ell^{(j)}=\exp(m^{(j-1)}-m^{(j)})\,\ell^{(j-1)}+\mathbf{1}^\top\tilde p^{(j)},$$
   which is algebraically identical to the invariant expression with shift $m^{(j)}$.

Thus by induction the invariant holds for every $j$. At the end $j=J$ we have $m^{(J)}=\max_k S_{rk}$ (rowwise max over all blocks) and therefore the final computed output
$$\frac{O^{(J)}}{\ell^{(J)}}=\frac{\sum_{u,k}\exp\big(s^{(u)}_k-m^{(J)}\big)\,v^{(u)}_k}{\sum_{u,k}\exp\big(s^{(u)}_k-m^{(J)}\big)}=\sum_k\frac{\exp(S_k)}{\sum_{k'}\exp(S_{k'})}\,v_k$$
is exactly the row of $\operatorname{softmax}(S)\,V$. (Everything above is exact algebra; the code performs the same algebra in a blockwise, streaming way.)

Why this is numerically stable. Two facts give numerical safety. First, each exponential is taken on an argument shifted by the current row maximum, so its argument is $\le 0$; hence each $\tilde p$ entry is in $(0,1]$ and cannot overflow. Second, when a later block discovers a larger maximum the kernel rescales the previous accumulators by the factor $\exp(m^{\text{old}}-m^{\text{new}})\le 1$; that never amplifies previous partial sums and prevents previously large contributions from causing overflow under the new baseline. In other words the algorithm never needs to form $\exp(S)$ at full (possibly large) magnitude and instead always keeps numerators and denominators re‑based to the current maximum, which is exactly the standard log‑sum‑exp stabilization applied incrementally.

Practical note: the proof above is algebraic and shows exact equivalence in real arithmetic. In floating‑point arithmetic there will be the usual rounding errors from exponentials, multiplies and adds; FlashAttention implementations mitigate this by keeping the softmax internals (the accumulators $\ell$ and $O$ and the exponentials) in a sufficiently high precision (FP32 in the paper) and by ensuring the shifts are monotone so scaling factors are $\le 1$ (they do not amplify rounding error). This delivers both correctness (same mathematical target) and good numerical stability in practice, which is exactly what FlashAttention‑3 reports in the paper.

### What exactly are commit-but-don’t-wait semantics for WGMMA and TMA in the 2-stage pipeline?
Question:
The 2-stage consumer pseudocode issues WGMMA for $\mathbf{Q}_i\mathbf{K}_j^\top$ and for $\widetilde{\mathbf{P}}_{\mathrm{cur}}\mathbf{V}_{j-1}$ with commit but do not wait, then waits later before using the results. What are the concrete PTX or CUTLASS primitives that implement these semantics for Hopper (e.g., wgmma.mma_async and the corresponding wait)? Similarly, what are the TMA primitives and barriers used to signal tile readiness from producer to consumer? How do these primitives guarantee that softmax never reads $\mathbf{S}_{\mathrm{next}}$ until its GEMM has completed, even under aggressive compiler instruction reordering?
Answer:
Short answer: "commit-but-don’t-wait" in the 2‑stage pipeline is just issuing the hardware’s asynchronous primitives (start the tensor‑core GEMM or the TMA copy) and returning immediately; later the code executes the corresponding explicit wait/fence primitive before touching the results. On Hopper these are the asynchronous WGMMA and TMA primitives (and their wait/commit counterparts) exposed in PTX/SASS and wrapped by CUTLASS. The concrete mapping used in FlashAttention‑3 is:

- Tensor Core (WGMMA) async: issue the async GEMM via the WGMMA async instruction (PTX/SASS form commonly written as wgmma.mma_async or the CUTLASS wrapper that emits it), and later execute the matching wgmma wait (wgmma.mma_wait / wait_all) before any instruction that reads the accumulator.  
- TMA (global→shared) async: issue the TMA load(s) and commit them, and use the TMA wait/commit semantics (CUTLASS provides TMA load/commit/wait helpers) plus intra‑CTA synchronization (bar.sync / __threadfence_block or a shared‑memory “ready” flag) to let consumers see the tile only after the transfer finished.

Why this is safe (intuition + mechanics). The GPU provides two separate hardware engines: a Tensor Core engine (WGMMA) that can accept "start" requests and run matmuls asynchronously, and a DMA/TMA engine that handles global→shared copies asynchronously. The PTX/SASS async op (wgmma.mma_async) enqueues work on the tensor engine and returns; the corresponding wait instruction is a hardware synchronization point: it tells the scheduler to stall instruction retirement until the requested async operations have finished and the accumulator/register state is valid. Because the wait is an actual PTX/SASS synchronization instruction (not a plain C++ function), the compiler cannot legally move the consumer code that depends on the WGMMA result past the wait: the wait creates a true data/ordering dependency visible to the backend and the hardware scoreboard enforces it. The same principle holds for TMA: commits and waits for TMA (or the CUTLASS TMA wrapper) are explicit events that must be emitted into SASS; you then pair them with a small producer->consumer handshake (a ready bit in shared memory + __threadfence_block / bar.sync or a TMA wait) so the consumer never reads the SMEM tile until the TMA copy completed.

A compact PTX‑style sketch of the pattern used in the paper (pseudo‑PTX / SASS):

  // start next $Q*K^T$ asynchronously
  wgmma.mma_async  ...  // starts GEMM that will produce $S_{next}$
  // start RS‑GEMM for previous tile ($P_{cur} * V_{j-1}$) asynchronously
  wgmma.mma_async  ...
  // now we need $S_{next}$ for softmax: wait for the specific async WGMMA to complete
  wgmma.mma_wait  #n_pending_for_S_next
  // safe to read $S_{next}$ registers and compute softmax
  // later wait for the $P_{cur} * V$ GEMM to finish before using its outputs
  wgmma.mma_wait  #n_pending_for_PV

And for TMA producer->consumer handshake the usual idiom is:

  // producer warp:
  tma.load.async (GMEM -> SMEM) for $K_j/V_j$ tiles  // async issue
  tma.commit()                                      // commit group to TMA
  __threadfence_block()                             // ensure ordering
  shared_stage_ready[stage] = 1                     // write ready flag
  // consumer warp:
  wait_until(shared_stage_ready[stage] == 1)        // or bar.sync + check
  // At this point SMEM tile is safe to read; alternatively consumer can call tma.wait()

Practical mapping to CUTLASS and the paper implementation. The authors use CUTLASS’s WGMMA and TMA abstractions rather than hand‑writing SASS; CUTLASS emits the appropriate wgmma.mma_async / wgmma.mma_wait and TMA commit/wait sequences for Hopper. In other words, in the FlashAttention‑3 code you’ll see CUTLASS calls that wrap the async WGMMA and a corresponding wait (CUTLASS names vary across versions, but conceptually they are “mma_async” + “mma_wait” wrappers and “tma::load/commit/wait” pipeline helpers). The paper explicitly says it uses WGMMA and TMA abstractions from CUTLASS, plus bar.sync for warpgroup handshakes.

Why compiler reordering is not a problem. Compilers can reorder ordinary C++/CUDA instructions, but they cannot legally move work across explicit PTX/SASS synchronization primitives that affect register or memory visibility. The async issue is a side‑effecting instruction (it changes the tensor engine’s pending‑ops scoreboard) and the wait is a required visibility point. CUTLASS emits these primitives (or inline PTX) so the NVCC backend will preserve the order that matters: any instruction that needs the WGMMA accumulator must be placed after the corresponding wgmma.mma_wait in the final SASS, and that wait will block retirement until the Tensor Core finished. For inter‑warp signaling, a ready flag plus __threadfence_block / bar.sync (or TMA’s own wait) is used; these are also concrete SASS instructions / memory fences, so the backend cannot invisibly reorder the softmax reads before the completion/wait.

Implementation checklist / gotchas. Implementers must (1) use the proper async + wait pair (don’t try to emulate it with C++ memory ops), (2) make the producer->consumer handshake explicit (shared memory flag + __threadfence_block or bar.sync / pipeline object) so the consumer never polls stale SMEM, and (3) ensure the wait counts are correct (WGMMA wait often takes a count of pending ops or you use a “wait_all” form). Using CUTLASS’s built‑in async GEMM and TMA pipeline helpers avoids subtle mistakes; if you emit raw inline PTX, mark the asm volatile and/or use the provided CP/WGMMA/TMA wait primitives so NVCC/SASS keep your ordering intact.

If you want, I can point to the exact CUTLASS functions (in the CUTLASS release used by the paper) and show the small inline‑PTX snippets CUTLASS emits for mma_async / mma_wait and TMA commit/wait.

### How does pingpong scheduling actually overlap softmax with GEMMs across warpgroups?
Question:
The paper says bar.sync is used to force GEMMs in warpgroup 1 before GEMMs in warpgroup 2, so that softmax in one warpgroup runs while Tensor Cores are busy in the other. How is this ordering sufficient to induce concurrent MFU (for exp) and Tensor Core usage on Hopper’s scheduler? Is there a minimal number of consumer warps per warpgroup needed for this to be effective, and what ensures the softmax instructions are not delayed until after the GEMMs complete anyway?
Answer:
Short answer: it works because Hopper exposes two largely independent execution pipelines (Tensor Cores via the warpgroup-wide WGMMA and the MFU that implements exponentials/special functions) and the kernel explicitly issues WGMMA asynchronously (``commit but do not wait'') and only waits when a result is actually needed. The cross‑warpgroup barrier (bar.sync) is used not to make the hardware magically run things in parallel, but to shape the *issue order* of WGMMA vs. softmax work across warpgroups so the hardware scheduler actually has ready MFU work to schedule while the Tensor Cores are busy. In practice you need the warpgroup unit (and at least two warpgroups co‑resident on the SM for the ping‑pong effect to be most effective), and you must avoid creating data dependencies or implicit waits that would force the softmax to stall until GEMMs complete.

Why ordering + asynchrony is sufficient
The paper’s key hardware facts are the ones you should keep in mind: (1) on Hopper the WGMMA instruction is asynchronous and is issued at the warpgroup granularity, and (2) exponentials/special functions execute on a separate multi‑function unit (MFU). Because WGMMA is asynchronous the kernel can issue a GEMM and then continue executing instructions in that warpgroup without stalling for the Tensor Core to finish, provided those instructions do not depend on the GEMM result. That “continue” is what the paper takes advantage of.

bar.sync is used to control *when* each warpgroup issues its WGMMA instructions relative to the other warpgroup(s). By forcing an order of GEMM issue (WG1 issues its GEMMs first, then WG2), the kernel makes sure that at any given time there is a warpgroup that has recently issued a WGMMA (so the Tensor Cores are busy) and another warpgroup that has ready MFU work (softmax/exponentials) to execute. The hardware warp scheduler interleaves warps that are ready; since MFU and Tensor Core are separate pipelines, MFU instructions from one warpgroup can be executed while the Tensor Cores are processing a previously issued WGMMA from another warpgroup. In short, bar.sync shapes issue order; WGMMA’s asynchronous semantics + the separate MFU pipeline let the scheduler physically overlap MFU execution with Tensor Core execution.

What actually prevents the softmax from getting serialized
Two practical kernel-level ingredients prevent the softmax from being deferred until after GEMMs complete: (a) explicit non‑blocking WGMMA usage (``commit but do not wait'') so the code does not implicitly wait for Tensor Core completion, and (b) a two‑stage pipelining of the inner loop so the softmax for one block does not depend on the RS‑GEMM that was just issued. Concretely, the implementation issues the next SS‑WGMMA and also issues the RS‑WGMMA for the previous $P\cdot V$ while only waiting for the specific WGMMA result that the softmax needs. The code waits only when it must (PTX/SASS wait instructions are inserted only where a dependency exists). Because the softmax’s expensive exponentials do not depend on the still‑in‑flight RS‑GEMM, they can be scheduled immediately and execute on the MFU while the RS‑GEMMA/Tensor Core work completes. The authors checked the generated SASS and confirmed the compiler did produce the expected overlapped instruction stream (they also note compiler reordering is a practical risk).

Practical minimums / occupancy considerations
Architecturally a WGMMA is a warpgroup‑wide primitive (the paper defines a warpgroup as 4 contiguous warps), so you need a full warpgroup to issue a WGMMA. For the ping‑pong effect you want at least two warpgroups co‑resident/active on the SM so one group can be in the phase that issues/keeps the Tensor Cores busy while the other group executes softmax on the MFU. In other words, the mechanism requires at least the warpgroup unit and benefits from having two warpgroups (ping/pong) so work can alternate across them. You can get some overlap even within a single warpgroup via the 2‑stage intra‑warpgroup pipelining described in the paper, but that is generally less effective than true ping‑pong across multiple warpgroups because of register pressure and limited ability to keep pipelines fed.

Caveats and why the effect is empirical, not absolute
The paper explicitly warns the ping‑pong picture is idealized — real behavior depends on occupancy, register pressure, compiler scheduling, and the exact placement of waits/barriers. If registers spill or if the compiler introduces waits/reorders code, softmax could be delayed and overlap reduced. That is why the implementation uses setmaxnreg, careful register management, explicit commit/no‑wait patterns, and validation via SASS to make the overlap reliable. Empirically those measures raised TFLOPs from the baseline (e.g., the paper reports improvements such as $570 \rightarrow 620-640$ TFLOPs in their example).

Summary
The bar.sync ordering is effective because it controls *issue order* across warpgroups while WGMMA is asynchronous and the MFU is a separate pipeline. With non‑blocking WGMMA, a pipeline that avoids needless data dependencies, and at least two warpgroups (and good occupancy/register management), the scheduler has ready MFU work to run while Tensor Cores are busy, producing the observed MFU+TC overlap.

### How are the circular SMEM buffer stages synchronized to avoid races between producer and consumers?
Question:
The forward pass uses an s-stage circular buffer in SMEM for $\{\mathbf{K}_j,\mathbf{V}_j\}$ and mentions a pipeline object that manages synchronization. What specific barrier primitives are used (e.g., mbarrier, bar.sync, or CUTLASS pipeline abstractions) to implement: (1) producer waiting for a stage to be consumed, (2) producer committing a stage as ready, (3) consumers releasing stages back to the producer? Are $\mathbf{K}$ and $\mathbf{V}$ staged separately or as a pair sharing the same stage index, and how do you prevent the consumer from reading a $\mathbf{V}_j$ tile whose in-kernel transpose has not completed yet?
Answer:
Short answer: FlashAttention‑3 implements the $s$‑stage circular SMEM buffer with a small “pipeline” handshake built on the GPU’s asynchronous-TMA/WGMMA primitives plus block-level barriers. Concretely the implementation uses CUTLASS’s TMA and WGMMA wrappers to launch asynchronous GMEM→SMEM copies and Tensor-Core GEMMs, and it uses a pipeline object (the paper’s “pipeline object”) that is implemented with per‑stage state in SMEM and block‑level barrier rendezvous (the paper explicitly cites using PTX/assembly level bar.sync for the ping‑pong / warpgroup ordering). The pipeline combines TMA commit/wait semantics and a bar.sync based rendezvous to implement the three actions you asked about.

How the three events map to primitives and state in the paper’s design is best read as a short handshake sequence. The producer first waits until the $(j \bmod s)$ stage is free by checking the per‑stage state and using the pipeline’s wait primitive (implemented as a SMEM flag/counter + block‑level synchronization; i.e., the producer-side wait is realized by the pipeline object which uses bar.sync style rendezvous). When the producer issues the asynchronous TMA loads for $K_j$ and $V_j$ it uses the CUTLASS/TMA commit semantics; the producer only “commits” the stage as ready (i.e., flips the stage’s ready flag that consumers poll/wait on) after the TMA transfers and any in‑kernel work that must finish before consumption (for FP8: the LDSM/STSM register-level in‑kernel transpose of the $V$ tile) have completed. The consumer side explicitly waits for the appropriate per‑stage ready flag (the pseudocode’s “Wait for $K_j$ / Wait for $V_j$ to be loaded in shared memory”) before using that tile; after a consumer finishes using a tile it clears/releases that operand’s ready flag and does the barrier rendezvous so the producer can reuse that subregion of the stage. In other words the pipeline object implements: producer wait for free → TMA issue & (in‑kernel transpose) → producer commit (set ready flag + bar.sync) → consumer wait on ready flag → consumer consume → consumer release (clear flag + bar.sync).

On the $K$ vs $V$ question: the paper’s pseudocode and the 2‑stage pipeline show that $K$ and $V$ are colocated with the same logical stage index but tracked separately. The code issues loads for both $K_j$ and $V_j$ into the $(j \bmod s)$th stage, but it maintains independent readiness/release semantics for $K$ and for $V$: $K$ can be marked free/released earlier (after the SS‑GEMM that uses $K$ is done) while $V$ is kept until the RS‑GEMM that needs it finishes. That is explicit in the 2‑stage pseudocode where the algorithm releases the $K$ stage and the $V$ stage at different times (lines that release $(j \bmod s)$ for $K$ and $(j-1 \bmod s)$ for $V$). This per‑operand readiness tracking is how the producer can safely reuse the $K$ sub‑slot of a stage while the $V$ sub‑slot is still being consumed.

Finally, preventing a consumer from reading a partially‑transposed $V$ tile is enforced by the same handshake: the in‑kernel transpose (LDSM/STSM + any register permutes) is performed by the producer warpgroup before it sets the $V_{\text{ready}}$ flag, and the consumer always “Wait for $V_j$ to be loaded in shared memory” before issuing the RS‑GEMM. The paper also notes that the producer schedules the transpose of the next $V$ tile “in the shadow” of two WGMMAs so it typically finishes well before the consumer needs it, but correctness does not rely on that scheduling — the ready flag / pipeline wait guarantees that no consumer reads $V_j$ until the transpose and SMEM write are complete.

If you look at the implementation-level hints in the paper: TMA (CUTLASS TMA abstraction) is used for async loads, LDSM/STSM for the in‑kernel transpose of FP8 $V$ tiles, WGMMA for the asynchronous GEMMs, and bar.sync (exposed via the pipeline object / CUTLASS-style synchronization helpers) is used for the warpgroup/CTA rendezvous that implements the producer/consumer handshakes.

### What are SS-GEMM and RS-GEMM in the pseudocode, and why are they different?
Question:
The consumer loop refers to SS-GEMM for $\mathbf{Q}_i \mathbf{K}_j^\top$ and RS-GEMM for $\widetilde{\mathbf{P}}_i^{(j)} \mathbf{V}_j$. What exactly does SS versus RS denote here (e.g., which operand is sourced from SMEM versus registers), and how does that map to Hopper’s WGMMA operand modes? Why is this asymmetry useful or necessary in FA-3 compared to a symmetric SMEM-sourced GEMM on both operands?
Answer:
Short answer: “SS-GEMM” and “RS-GEMM” name which data locale supplies the left (first) operand to the WGMMA (Tensor‑Core) GEMM: $S$ = shared memory (SMEM), $R$ = register file. So SS means both operands are read from SMEM (shared–shared), while RS means the left operand is in registers and the right operand is in SMEM (register–shared). On Hopper this maps to the two WGMMA operand modes: a WGMMA that sources inputs from SMEM for both operands versus a WGMMA that takes the $A$ (left) tile from registers and $B$ from SMEM.

Why FA‑3 uses them asymmetrically. In the consumer loop the $Q/K$ matmul
$S_i^{(j)} = Q_i K_j^T$ is an SS‑GEMM because both $Q_i$ and $K_j$ are produced by the producer warpgroup and placed in SMEM for reuse across many key blocks. By contrast the softmax produces the ephemeral block $\widetilde{P}_i^{(j)}$ inside the consumer; FA‑3 keeps that block in registers (to avoid an extra write/read to SMEM) and then wants to multiply it by $V_j$ which lives in SMEM. That is exactly the RS pattern: a register-resident left operand ($\widetilde{P}$) times an SMEM-resident right operand ($V$).

Intuition and hardware reasons (how this helps)
1) Overlap / asynchrony: WGMMA on Hopper is asynchronous. If you had to write $\widetilde{P}$ into SMEM and then launch an SS‑GEMM to consume it, you would serialize softmax → write → read → GEMM and lose the ability to overlap softmax and matmuls. Keeping $\widetilde{P}$ in registers and using an RS‑WGMMA lets the kernel issue the GEMM on the register-resident operand while the next iteration’s work (e.g., another WGMMA or softmax) is being prepared. That is the key enabler of the 2‑stage pipelining / ping‑pong scheduling in FA‑3 and yields much higher Tensor‑Core utilization.

2) Bandwidth and storage: $\widetilde{P}$ is ephemeral and writing it to shared memory would increase SMEM/GMEM traffic and consume shared memory capacity that is better used for $Q$/$K$/$V$ tiles. Using registers avoids those extra memory reads/writes.

3) FP8 / layout constraints: Hopper’s WGMMA has layout requirements for SMEM operands (the paper notes FP8 SMEM operands must be $k$-major); meeting those constraints for both operands simultaneously can force expensive transposes or extra copies. Putting the computed $\widetilde{P}$ in registers (and performing cheap in‑register permutations when needed) sidesteps some of those SMEM layout clashes. FA‑3 also uses byte‑permutes on accumulators and an in‑kernel transpose of $V$ to reconcile layouts when chaining FP8 WGMMAs; doing intermediate results in registers makes those transformations cheaper and avoids extra SMEM traffic.

The cost / tradeoff. The asymmetry increases register pressure: you must hold $S_{next}$ or $\widetilde{P}$ in registers, and FA‑3 therefore uses warp‑specialization and dynamic register allocation (setmaxnreg) to balance producer vs consumer register budgets. That tradeoff is intentional: extra registers → less SMEM/GMEM traffic and more overlap → higher effective TFLOPs, as shown by the ablation in the paper.

Summary: SS means shared–shared (both inputs from SMEM) and RS means register–shared (left operand in registers, right in SMEM). FA‑3 deliberately uses SS for the reusable $Q \times K$ tiles and RS for the ephemeral softmax result $\times V$ to avoid SMEM churn, satisfy Hopper/WGMMA layout modes more easily (especially in FP8), and—most importantly—enable the asynchronous GEMM/softmax pipelining that drives the performance gains.

### How is causal masking integrated into the overlapped 2-stage pipeline without breaking the softmax rescaling invariants?
Question:
For causal attention, only entries with key position $\le$ query position are valid. In the FA-3 2-stage main loop, softmax of iteration $j+1$ overlaps with the second GEMM of iteration $j$. How are masked columns handled when updating $m_i$, $\ell_i$, and $\mathbf{O}_i$ at tile boundaries, especially when a query block $\mathbf{Q}_i$ spans multiple causal blocks? Do you zero out masked parts of $\mathbf{S}_i^{(j)}$ before the rowmax and rowsum updates, or apply an additive $-\infty$ mask inside the log-sum-exp update? Any special care needed at the first valid $\mathbf{K}_j$ for a given $\mathbf{Q}_i$?
Answer:
Short answer: you must apply the causal mask as an additive “$-\infty$” mask to the score tile immediately after the SS‑GEMM and before any reduction ($\mathrm{rowmax}/\mathrm{rowsum}$). Do not simply zero out masked entries of $\mathbf{S}$ (that would corrupt the row maxima). With a proper $-\infty$ mask the incremental log‑sum‑exp invariants used by FlashAttention‑3 remain valid even in the overlapped two‑stage pipeline; the first valid key block for a row is handled naturally by the math (because $e^{m^{\text{old}}-m}=0$ when $m^{\text{old}}=-\infty$), provided you implement the rescaling as multiplications by $e^{m^{\text{old}}-m}$ (not as a division by $0$).

Why and how, in a bit more detail. FlashAttention‑3 updates each query‑row with the streaming log‑sum‑exp formulas; for one key tile the updates (after you have $\mathbf{S}_i^{(j)}=\mathbf{Q}_i \mathbf{K}_j^\top$) are, conceptually:

1. apply the causal mask to $\mathbf{S}_i^{(j)}$ so that invalid positions become $-\infty$ (per row; a query block $\mathbf{Q}_i$ that spans many query positions needs a per‑row cutoff inside the same $\mathbf{K}_j$ tile),
2. $m_i \leftarrow \max(m_i^{\mathrm{old}},\ \mathrm{rowmax}(\mathbf{S}_i^{(j)}_{\text{masked}}))$,
3. $\widetilde{\mathbf{P}}_i^{(j)} \leftarrow \exp(\mathbf{S}_i^{(j)}_{\text{masked}} - m_i)$ (masked entries produce $0$ here),
4. $\ell_i \leftarrow \exp(m_i^{\mathrm{old}}-m_i)\,\ell_i + \mathrm{rowsum}(\widetilde{\mathbf{P}}_i^{(j)})$,
5. $\mathbf{O}_i \leftarrow \exp(m_i^{\mathrm{old}}-m_i)\,\mathbf{O}_i + \widetilde{\mathbf{P}}_i^{(j)} \mathbf{V}_j$.

Two practical points that answer your explicit subquestions:

- Do not zero masked parts of $\mathbf{S}$ before the $\mathrm{rowmax}/\mathrm{rowsum}$: zeroing changes the rowmax ($0$ values are legitimate finite values) and so breaks the log‑sum‑exp invariants. Instead set masked scores to $-\infty$ (or a sufficiently large negative FP32 constant) so they contribute nothing to max or sum; after the subtraction by $m_i$ their exponentials become (practically) $0$ and they do not contribute to $\ell_i$ or $\mathbf{O}_i$.

- You can think of “additive $-\infty$ inside the log‑sum‑exp update” and “set masked $\mathbf{S}$ entries to $-\infty$ then run the same reductions” as the same thing; implementationally it’s simplest and fastest to apply the per‑element mask to the register/shared‑memory tile produced by WGMMA as the very next step, then run the $\mathrm{rowmax}/\exp/\mathrm{rowsum}$ on that masked tile.

- First valid $\mathbf{K}_j$ for a given query row: if $m_i^{\mathrm{old}}=-\infty$ and $\ell_i=0$ then the formulas above reduce to $m_i=\mathrm{rowmax}(S_{\text{masked}})$, $\ell_i=\mathrm{rowsum}(\exp(S_{\text{masked}}-m_i))$, and $\mathbf{O}_i=\widetilde{\mathbf{P}}_i^{(j)}\mathbf{V}_j$. That is exactly what you want. In code you must avoid dividing by $0$ or computing inverses of $0$: compute the rescale as multiplication by the factor $f=\exp(m_i^{\mathrm{old}}-m_i)$ (which is $0$ when $m_i^{\mathrm{old}}=-\infty$) rather than trying to invert a diagonal with $0$ entries. If you prefer an explicit branch it is fine to branch on $\ell_i==0$ to do the first‑block initialization, but it isn’t necessary if you do the math via the multiplicative factor.

How this fits the 2‑stage overlap in FA‑3. The overlap does not change correctness: S tiles are produced asynchronously (WGMMA) and one tile’s RS‑GEMM is overlapped with the softmax on the next tile, but the moment you consume a produced $\mathbf{S}_{\mathrm{next}}$ (i.e. wait for that WGMMA to finish) you must immediately apply the causal mask to that register‑resident tile and then run the $\mathrm{rowmax}/\mathrm{rowsum}/\exp$ updates. Masking must be done before the reductions for that tile, otherwise $m_i$ and $\ell_i$ would incorrectly reflect masked entries and break the streaming LSE invariant. In practice you implement the per‑row mask cheaply by computing a per‑row cutoff index for the key tile (clamp of $q_{\text{pos}}-k_{\text{start}}+1$ into $[0,B_c]$) and then applying that mask as the first operation after the SS‑GEMM returns.

Small implementation tips that follow from the paper’s design choices: FlashAttention‑3 keeps softmax intermediate work in FP32, so use an FP32 $-\infty$ sentinel (or a very large negative float) for masking; when some rows of a key tile are completely invalid you can skip computing their exponentials or skip rows in the RS‑GEMM if that makes your kernel simpler/faster, but correctness is already guaranteed by the $-\infty$ mask and the multiplicative rescaling formula.

In short: mask = $-\infty$ applied immediately after GEMM (per row inside a tile when needed) ; update $m_i,\ell_i,\mathbf{O}_i$ with the usual streaming log‑sum‑exp formulas using multiplication by $\exp(m^{\mathrm{old}}-m)$; first valid block is handled naturally (or you can branch for the first block to avoid special floating behaviour). This preserves the softmax rescaling invariants inside the overlapped 2‑stage pipeline used by FlashAttention‑3.

### Why is forward FLOPs estimated as $4\,N^2 d\,H$ and backward as about $2.5\times$ forward?
Question:
The benchmarking section uses forward FLOPs $= 4\cdot \text{seqlen}^2\cdot \text{head dimension}\cdot \text{number of heads}$, halved under causal masking, and backward FLOPs $\approx 2.5\times$ forward. Could someone derive the factor 4 for the two forward GEMMs and explain where the extra factors come from? For backward, there are 5 GEMMs due to recomputation; can you break down which shapes contribute and why the ratio is about $2.5$ instead of exactly $2.5$ or another value given softmax and rescaling overheads?
Answer:
Short answer: the factor $4$ in the forward FLOPs count comes from two dense matmuls in the attention forward, each counted as $2$ FLOPs per multiply–accumulate (MAC). The backward is about $2.5\times$ the forward because you need five GEMMs in total (four gradient GEMMs plus one recomputed forward GEMM), so in pure GEMM-FLOP accounting $5/2 = 2.5$. The small deviation from exactly $2.5$ in measured numbers comes from the non‑GEMM softmax/rescale work ($O(N^2)$ elementwise ops), masking and block‑edge effects, and differences in hardware throughput for exponentials versus matmuls.

Derivation and shapes (per head). Let sequence length be $N$, head dimension $d$, and number of heads $H$.

1) Forward. The two matrix multiplies are $S = QK^\top$, with $Q: N\times d$, $K^\top: d\times N$ $\Rightarrow$ $S: N\times N$, and $O = PV$, with $P: N\times N$, $V: N\times d$ $\Rightarrow$ $O: N\times d$. Each GEMM costs (by the usual MAC counting) $2\times$ (multiply + add) FLOPs per scalar multiply, so each GEMM is $2N^2 d$ FLOPs. Two GEMMs give
$$
  F_{\text{fwd, per head}} = 2N^2 d + 2N^2 d = 4 N^2 d,
$$
and with $H$ heads $F_{\text{fwd}} = 4 N^2 d H$. With causal masking you only compute roughly the triangular half of the $N\times N$ score/softmax matrix, so you divide this count by about $2$.

2) Backward (why 5 GEMMs). The chain rule (as in the paper) yields the gradient GEMMs
$$
  dV = P^\top dO,\qquad dP = dO\,V^\top,\qquad dQ = \alpha\, dS\,K,\qquad dK = \alpha\, dS^\top Q,
$$
which are four GEMMs (each $2N^2 d$ FLOPs). Because FlashAttention does not materialize the full $S$ or $P$ to global memory in the fused forward, the backward pass must recompute the forward score GEMM $QK^\top$ (blockwise) to recover $P$ for the gradients. That recomputation is one more GEMM costing another $2N^2 d$. So the backward GEMM FLOPs per head sum to
$$
  F_{\text{bwd, per head}} = 5 \times (2 N^2 d) = 10 N^2 d,
$$
and therefore
$$
  F_{\text{bwd}} = 10 N^2 d H = 2.5 \times F_{\text{fwd}}.
$$

Why the ratio is “about” $2.5$ rather than always exactly $2.5$. The $2.5$ factor is exact if you count only the GEMM-style multiply–accumulate FLOPs and assume full dense $N\times N$ work. In practice there are several small but real effects that move the measured ratio away from the pure $2.5$ number:

- softmax and rescaling are elementwise operations on the $N\times N$ score matrix (exponentials, row‑max subtraction, row sums, scaling), i.e. $O(N^2)$ scalar ops per head with no factor $d$. For typical $d$ ($64$–$256$) these FLOPs are tiny compared to the $O(dN^2)$ GEMM FLOPs, so they change the FLOP ratio only a little, but they can be relatively expensive in wall‑time because exponentials are executed on slower special‑function units (the paper notes e.g. H100 has far lower special‑function throughput than Tensor‑core matmuls).
- causal masking reduces work roughly by $1/2$ for the score/softmax related GEMMs; depending on which GEMMs are triangular in the backward pass the cancellation is slightly different, so the multiply factor may not be exactly $2.5$ after you apply masking.
- tiling and block boundaries: the algorithm works blockwise, so some boundary tiles are smaller; rounding effects change exact flop totals by a few percent.
- kernel-level overlaps and fuse/recompute scheduling: FlashAttention overlaps softmax with GEMMs and sometimes amortizes or hides some costs. Overlap can reduce wall‑clock time without changing the counted FLOPs, so measured FLOPs/s or time ratios will differ from the simple $2.5$ multiplier.
- hardware differences: exponentials have low throughput and different latency characteristics, so an extra $O(N^2)$ of exponentials can cost more cycles than the flop count suggests.

In short, the paper’s bookkeeping uses the standard $\text{MAC}\to 2$ FLOP convention and counts the dominant GEMMs (2 in forward, 5 in backward because of the recomputed $QK^\top$), giving the quoted formulas $F_{\text{fwd}}=4N^2 d H$ and $F_{\text{bwd}}\approx 2.5\,F_{\text{fwd}}$. Small deviations from exactly $2.5$ in practice come from the non‑GEMM softmax/rescale work, masking/blocking effects and the different hardware cost of special functions vs. matmuls.

### For FP8 WGMMA, why must operands be k-major and how do LDSM/STSM enable an efficient in-kernel transpose of $\mathbf{V}$?
Question:
The paper notes that FP8 WGMMA on Hopper only accepts k-major operands from SMEM, but typical $\mathbf{V}$ is stored contiguous in the head dimension (mn-major). They opt for an in-kernel transpose using LDSM and STSM. Could you explain concretely how a warp uses LDSM/STSM to read a tile of FP8 $\mathbf{V}$, transpose it, and store it back in SMEM in k-major form, including how FP8 values are packed into 16-bit lanes for these instructions and what extra register moves are required because transpose variants cannot split packed 8-bit pairs?
Answer:
Short answer: FP8 WGMMA on Hopper requires $k$‑major operand tiles because the FP8 Tensor‑Core fragment mapping expects the inner ($K$) dimension to be contiguous in SMEM (the microkernel fetches $8\times 8$ fragments as 16‑bit words packed along $K$). To avoid a costly global‑memory transpose, FlashAttention‑3 transposes FP8 tiles in shared memory using the warp‑level LDSM/STSM (ldmatrix/stmatrix) $8\times 8$ 16‑bit move primitives. Because those instructions operate on 16‑bit elements, you pack two FP8 values into each 16‑bit lane, then do a small in‑register split + byte‑permute sequence to turn the 16‑bit‑wise transpose into a true byte (FP8) transpose, and finally STSM writes the tile back in $k$‑major order. The extra work is only register ALU/permute ops (no extra global memory) and can be overlapped with WGMMA, so the cost is small.

Concrete step‑by‑step (compact, with indexing to make it explicit). Work on an $8\times 8$ FP8 tile $V = [v_{r,c}]$ ($r,c = 0,\dots,7$) taken from SMEM in the usual head‑contiguous (mn‑major) layout. LDSM/STSM move an $8\times 8$ block of 16‑bit entries ($128$ bytes) per warp, so we pack two adjacent FP8s into one 16‑bit half‑word:

- packing in SMEM (natural when head dimension is contiguous): for each row $r$ and pair index $j = 0,\dots,3$ form the 16‑bit word
  $p_{r,j} = v_{r,2j} + 256\cdot v_{r,2j+1},$
  i.e. low byte = $v_{r,2j}$, high byte = $v_{r,2j+1}$.

- LDSM (warp cooperative ldmatrix) reads the $8\times 8$ block of 16‑bit words $p_{r,j}$ into the warp register fragments. LDSM (and its transpose variant) only treats those 16‑bit words as the atomic elements; it can move/transpose $8\times 8$ of 16‑bit words very efficiently, but it never breaks a 16‑bit word into its two bytes.

- to obtain a true FP8 (byte) transpose we must rearrange the bytes inside and across those 16‑bit words in registers. First split each $p_{r,j}$ into low and high bytes
  $L_{r,j} = p_{r,j} \& 0xFF = v_{r,2j},$
  $H_{r,j} = (p_{r,j} >> 8) \& 0xFF = v_{r,2j+1}.$
  These are inexpensive register ops (byte‑extract via shifts/masks or a byte‑permute).

- the transposed tile $T$ we want to store back so that memory contains $k$‑major FP8 elements satisfies
  $T_{c,r} = v_{r,c}.$
  It is convenient to re‑pack the transposed tile into 16‑bit words $q_{c,k}$ ($k = 0,\dots,3$) by pairing two output bytes per word:
  $q_{c,k} = v_{2k,c} + 256\cdot v_{2k+1,c}.$
  Using the split arrays L/H, this becomes (with $j = \lfloor c/2 \rfloor$ and $b = c \bmod 2$)
  $q_{c,k} = \big((b==0 ? L_{2k,j} : H_{2k,j})\big) + 256\cdot\big((b==0 ? L_{2k+1,j} : H_{2k+1,j})\big).$
  In words: each $q_{c,k}$ takes one byte from row $2k$ and one byte from row $2k+1$ (the correct bytes of column $c$), so $q_{c,k}$ gathers bytes from different original $p_{r,j}$.

- implementationally you do those gathers with in‑register byte‑permute/shuffle instructions (the paper refers to these as “byte permute”): extract the needed low/high bytes into temporary registers and then combine them pairwise into $q_{c,k}$. Because LDSM already distributed ownership of $p_{r,j}$ to registers in a warp‑friendly mapping, these re‑packings are done locally in each thread’s registers (or with only very local lane‑aligned permutes), so you avoid expensive cross‑thread shuffles.

- finally STSM (stmatrix) writes the $8\times 8$ block of 16‑bit words $q_{c,k}$ back to SMEM. Because $q_{c,k}$ was formed so that each 16‑bit word holds two FP8s in the order the FP8 WGMMA expects, the resulting SMEM region is now $k$‑major for the next WGMMA call.

Why the extra moves? The transpose variants of LDSM/STSM only transpose 16‑bit elements, they cannot split the two FP8 bytes inside each 16‑bit element and move those bytes independently. Thus the “missing” operation is the byte‑level regrouping: split 16‑bit words into bytes, permute bytes across the register set into the new pairings, and re‑pack into 16‑bit lanes before store. Those register moves are the only extra cost; they are a small number of mask/shift/byte‑permute operations per 128‑byte tile and are performed entirely on‑chip and can be overlapped with WGMMA computation (as the paper describes), so the wall‑clock overhead is low compared to the avoided global‑memory transpose.

Intuition / why this is worth it: LDSM/STSM give a very high‑bandwidth, warp‑cooperative 128‑byte on‑chip copy; using them plus a few in‑register byte permutations turns an expensive global transpose into a cheap on‑chip rearrangement. That allows FlashAttention‑3 to present $V$ to the FP8 WGMMA in the required $k$‑major layout without extra HBM traffic, and the small register shuffles are cheap and hideable behind WGMMA’s asynchrony.

### How does permuting FP8 accumulator layout and matching the $\mathbf{V}$ tile permutation preserve correctness of $\mathbf{P}\mathbf{V}$?
Question:
To bridge the layout mismatch between an FP8 WGMMA accumulator and the next FP8 operand layout, FA-3 applies a byte-permute to the FP32 accumulator so that the logical $\mathbf{P}$ tile’s columns are permuted by some permutation $\Pi$. The in-kernel $\mathbf{V}$ transpose then applies the matching row permutation $\Pi$ to $\mathbf{V}$. Is the claim that $(\mathbf{P}\Pi)(\Pi^{-1}\mathbf{V}) = \mathbf{P}\mathbf{V}$, and since you use the same $\Pi$ to permute $\mathbf{V}$’s rows, the product is unchanged? Could you show this explicitly for a tile, and clarify how you ensure the permutation is consistent across warps and iterations so that partial sums of $\mathbf{O}_i$ accumulate in the correct order?
Answer:
Short answer: yes — nothing magical is happening: permuting the accumulator's bytes implements a fixed column permutation on the logical P tile, and if you apply the matching inverse permutation to the rows of the corresponding V tile, the matrix product is unchanged. Algebraically this is just the permutation-matrix identity $(P\Pi)(\Pi^{-1}V)=P V$. Below I show that identity explicitly for a tile, explain why the softmax/rescaling steps are safe under the column reordering, and then explain the implementation-level measures the paper uses to keep the same permutation $\Pi$ across warps and iterations so partial sums of $O_i$ accumulate correctly.

Let $\Pi$ be the $B_c\times B_c$ permutation matrix that implements the column reordering induced by the byte-permute on the FP32 accumulator. Right-multiplying $P$ by $\Pi$ rearranges columns of $P$: the $j$-th column of $P\Pi$ is the $\pi(j)$-th column of $P$ (where $\pi$ is the index map encoded by $\Pi$). Left-multiplying $V$ by $\Pi^{-1}$ rearranges rows of $V$ so that the $j$-th row of $\Pi^{-1}V$ is the $\pi(j)$-th row of $V$. Therefore
$$
(P\Pi)(\Pi^{-1}V)=P(\Pi\Pi^{-1})V = P I V = P V.
$$
Index-wise you can see the same thing: writing the product entrywise,
\[
\bigl((P\Pi)(\Pi^{-1}V)\bigr)_{i,k}
= \sum_{j} (P\Pi)_{i,j}\,(\Pi^{-1}V)_{j,k}
= \sum_{j} P_{i,\pi(j)}\,V_{\pi(j),k}.
\]
If you change the summation index $t=\pi(j)$ this becomes $\sum_t P_{i,t}V_{t,k}$, which is exactly $(PV)_{i,k}$.

A tiny concrete tile example makes this very clear. Take a single-row query block (so $P$ is $1\times 4$) with $P=[p_0\ p_1\ p_2\ p_3]$ and a value tile with rows $v_0,v_1,v_2,v_3$ (each $v_j$ is a row vector). If $\Pi$ swaps columns $1$ and $2$ then $P\Pi=[p_0\ p_2\ p_1\ p_3]$ and $\Pi^{-1}V$ has rows $[v_0; v_2; v_1; v_3]$. Multiplying gives
\[
(P\Pi)(\Pi^{-1}V)=p_0 v_0 + p_2 v_2 + p_1 v_1 + p_3 v_3
= p_0 v_0 + p_1 v_1 + p_2 v_2 + p_3 v_3 = PV,
\]
so the logical contribution to $O_i$ is identical.

Two implementation points that the paper leverages and that ensure correctness of partial accumulation. First, permuting columns of a local $S$ (or $P$) tile is safe for the softmax and rescaling computations because those are row-wise reductions: rowwise $\max$, elementwise $\exp$, and rowwise sums do not depend on column order. The algorithm can therefore compute softmax on the permuted column order (or permute just after computing $S$ and before the elementwise ops) without changing the numerical result per entry.

Second, consistency: the permutation pattern $\Pi$ is not data-dependent at runtime but determined by the fixed register/byte layout that WGMMA produces for a given tile shape and by the chosen packing strategy (the paper describes a deterministic byte-permute pattern like $\{d0,d1,d4,d5,d2,d3,\dots\}$ replicated every 8 bytes). Because that layout is fixed for the WGMMA instruction and tile sizes, the same byte-permute mask is used everywhere in the kernel (every warp, every iteration) for that tile shape. On the producer side the in-kernel transpose (LDSM/STSM) is programmed to write the $V$ tile rows in the matching permuted order (i.e., to perform the inverse row permutation required by the algebra above). Synchronization in the kernel (the pipeline/commit/wait and the circular SMEM stages indexed by $j \bmod s$ in Algorithms 1–2) guarantees the producer finishes writing the permuted/transposed $V_j$ into the shared-memory stage before any consumer warpgroup issues the RS‑GEMM that reads it. Within a warpgroup the byte-permute is applied identically by every thread (vector byte-permute instructions replicate the same mask over the register lanes), so register ordering is consistent; across warpgroups and iterations the same code path and the same tile geometry produce the same permutation mask. Thus each partial product computed for block $j$ is the algebraically correct $P^{(j)}V_j$, and adding these partials into the accumulating $O_i$ (with the usual softmax rescale bookkeeping) yields the correct final $O_i$.

In short: the mathematical identity $(P\Pi)(\Pi^{-1}V)=PV$ is what guarantees arithmetic correctness, and the paper enforces that the concrete byte-permute on the accumulator and the in-kernel transpose of $V$ implement those two matched permutations deterministically and with the barrier/commit semantics shown in the algorithms, so partial sums are produced in a consistent layout and accumulate correctly.

### How are per-block FP8 scales folded into the computation at no extra cost?
Question:
With block quantization, each $\mathbf{Q}$ block of shape $B_r\times d$ has its scale $s_Q$ and each $\mathbf{K}$ block of shape $B_c\times d$ has its scale $s_K$. One can write $\mathbf{Q}_{\text{fp}} \approx s_Q\,\mathbf{Q}_8$ and $\mathbf{K}_{\text{fp}} \approx s_K\,\mathbf{K}_8$. Then $\mathbf{S}_i^{(j)} = \mathbf{Q}_i\mathbf{K}_j^\top \approx (s_Q s_K)\, (\mathbf{Q}_{8,i}\mathbf{K}_{8,j}^\top)$. How exactly is the factor $s_Q s_K$ incorporated into the row-wise softmax with the running $m_i$ and $\ell_i$ without introducing extra flops? Do you fold it as an additive shift via $\log s_Q + \log s_K$ inside log-sum-exp, or multiply the partial probabilities before the second GEMM? A short, explicit formula for the updates would be very helpful.
Answer:
Short answer: the per-block FP8 scales enter exactly as a scalar multiplier on the block of scores and are handled by the usual numerically‑stable, incremental softmax merge used in FlashAttention. Concretely you treat the block score matrix as
$$S^{(j)} = (s_{Q,i} s_{K,j}) \cdot (Q_{8,i} K_{8,j}^\top)$$
and run the same running‑max / running‑sum update from the paper. In practice FlashAttention‑3 avoids paying a new per‑element cost for that scalar either by (a) doing the tiny dequantization/scaling work when the block is loaded (fused with the producer work such as rotary embedding / the TMA load) so the consumer sees $$S^{(j)}$$ already scaled, or (b) by performing only very small per‑row scalar ops (row maxima scaling / rescale of $O$ which are negligible compared to the GEMMs) that are overlapped with other work. You cannot replace the multiplicative score factor by a simple additive log shift inside log‑sum‑exp (nor by a post‑hoc multiplication of unscaled probabilities) because softmax(exp) is non‑linear in the scores.

Explicit formulas (same structure as Alg.1 / Alg.2 in the paper, with the block scale $s := s_{Q,i} s_{K,j}$ shown explicitly). Suppose after processing blocks $0..j-1$ you have per‑row running maximum $m^{old}$ and running (unnormalized) sum $\ell^{old}$ and partial output $O^{old}$. For block $j$ compute the raw FP32 GEMM result
$$Y := Q_{8,i} K_{8,j}^\top$$
and let $s := s_{Q,i} s_{K,j}$. Then the consumer updates are exactly

$$m_{\text{block}} = \mathrm{rowmax}(s \cdot Y) = s\cdot\mathrm{rowmax}(Y)$$,

$$m = \max(m^{old},\, m_{\text{block}})$$,

$$\widetilde{P}^{(j)} = \exp\!\big(s\cdot Y - m\big)\quad(\text{rowwise})$$,

$$\ell = \exp(m^{old}-m)\,\ell^{old} \;+\; \mathrm{rowsum}(\widetilde{P}^{(j)})$$,

$$O = \exp(m^{old}-m)\,O^{old} \;+\; \widetilde{P}^{(j)}\,V_{j}$$.

At the end you produce the normalized block output and log normalizer via

$$O_i = O / \ell,\qquad L_i = m + \log(\ell).$$

These are exactly the operations in the pseudocode (lines labelled softmax_start..softmax_end and the RS‑GEMM update) with the scalar $s$ multiplying $Y$ inside the exponent/rowmax. That is the mathematically correct and stable way to include the per‑block scale.

Why not do additive log shift? Because scaling the scores by $s$ acts inside the exponent: $\exp(s\cdot x)\neq\exp(x+\log s)$ (indeed $\exp(x+\log s)=s\exp(x)$ while $\exp(sx)$ is generally different). So you cannot replace score multiplication by an additive shift to the score vector. Likewise you cannot compute softmax on the unscaled block and then just multiply those partial probabilities by $s$ and expect the same final softmax.

Why no extra cost in FlashAttention‑3? The paper’s implementation makes the scaling cheap by doing it outside the hot GEMM/softmax path: the block quantization / dequantization is fused with producer work (rotary embedding or the TMA load/transposes), so when the consumer runs the softmax/GEMM pipeline it already sees properly scaled FP32 scores (or the tiny per‑row scalar adjustments are overlapped). Thus the attention kernel does not add a large extra per‑element multiply just to account for $s_{Q} s_{K}$.

In short: you must multiply the block scores by the block scale and then run the same running‑max / running‑sum softmax updates above. FlashAttention‑3 implements that without an extra expensive pass by fusing the dequantization/scale with producer work or by overlapping the small scalar work with GEMMs, not by substituting an additive log trick or multiplying probabilities later.

### Why does the orthogonal incoherent transform preserve attention, and how is it fused with rotary embeddings?
Question:
The paper multiplies $\mathbf{Q}$ and $\mathbf{K}$ by the same random orthogonal matrix $\mathbf{M}$ (Hadamard with random signs) before FP8 quantization to spread out outliers, relying on $(\mathbf{Q}\mathbf{M})(\mathbf{K}\mathbf{M})^\top = \mathbf{Q}\mathbf{K}^\top$. Do we need to use the same $\mathbf{M}$ across all heads and tokens, or can $\mathbf{M}$ vary per head? How is this fused with rotary embeddings, which apply position-dependent rotations in the head dimension? Does $\mathbf{M}$ commute with RoPE so that we can apply them in either order without changing $\mathbf{Q}\mathbf{K}^\top$, and what is the precise $O(d\log d)$ algorithmic path used in-kernel?
Answer:
Short answer: because the incoherent transform $M$ is orthogonal it cancels out of the dot‑products that define attention, so you must apply the same $M$ to the query and key feature axis that will be dotted together (you may choose a different independent $M$ per head, but not a different $M$ per token/block that participates in cross‑dot products). Rotary embeddings (RoPE) must be applied before that same $M$ (i.e. apply $M$ to the rotated vectors); $M$ does not generally commute with the per‑position rotations, but if you multiply both the already‑rotated $Q$ and $K$ by the same $M$ the $M$ factors cancel in the inner product. In practice the paper implements $M$ as a random sign diagonal times a Hadamard and computes it with a fast Walsh–Hadamard transform (FWHT) in $O(d\log d)$, and this pass can be fused with the RoPE kernel so there is essentially no extra memory traffic.

Why the transform preserves attention. Let $M$ be orthogonal so $MM^\top=I$. If you replace $\mathbf{Q},\mathbf{K}$ by $\mathbf{Q}\!M,\mathbf{K}\!M$ then $(\mathbf{Q}M)(\mathbf{K}M)^\top=\mathbf{Q}MM^\top\mathbf{K}^\top=\mathbf{Q}\mathbf{K}^\top$, so every query–key inner product is unchanged. That is the algebraic reason the paper uses an orthogonal mixing before quantization: it spreads out large coordinates (reducing quantization error) while leaving attention scores exact.

What must be identical and what may vary. The cancellation above requires that the same $M$ be used on both the $Q$ and $K$ feature axes that are dotted together. In multi‑head attention each head computes attention independently, so you may pick a different random orthogonal $M^{(h)}$ per head (and that is commonly done). You may not pick a different $M$ per token (or per query block versus key block) unless you ensure the exact same matrix is used for every query block and every key block that interact; if $M$ varies with position or block then $(\mathbf{Q}_i M_i)(\mathbf{K}_j M_j)^\top=\mathbf{Q}_i M_i M_j^\top \mathbf{K}_j^\top$ and you only have equality to $\mathbf{Q}_i\mathbf{K}_j^\top$ when $M_i=M_j$.

How RoPE interacts. RoPE implements position‑dependent rotations: if $R_p$ is the rotation for query position $p$ and $R_q$ for key position $q$, the RoPE attention term is $\mathbf{Q}R_pR_q^\top\mathbf{K}^\top$. If you apply $M$ after RoPE to both sides, i.e. use $\mathbf{Q}'=(\mathbf{Q}R_p)M$ and $\mathbf{K}'=(\mathbf{K}R_q)M$, then

$$
(\mathbf{Q}R_pM)(\mathbf{K}R_qM)^\top=\mathbf{Q}R_p\underbrace{M M^\top}_{I}R_q^\top\mathbf{K}^\top=\mathbf{Q}R_pR_q^\top\mathbf{K}^\top,
$$

so the RoPE‑modified dot product is preserved. By contrast, applying $M$ before the rotations gives

$$
(\mathbf{Q}M R_p)(\mathbf{K}M R_q)^\top=\mathbf{Q}\bigl(M R_p R_q^\top M^\top\bigr)\mathbf{K}^\top,
$$

which is generally different from $\mathbf{Q}R_pR_q^\top\mathbf{K}^\top$ because $M$ and the block‑diagonal rotation matrices do not commute. In short: $M$ need not commute with RoPE, so to preserve the intended RoPE dot‑products you should apply the orthogonal mixing to the already‑rotated vectors (or equivalently implement the combined operator that performs RoPE then $M$).

Why the Hadamard + sign construction and how you compute it in $O(d\log d)$. The paper picks $M$ from the class “random sign diagonal(s) times a Hadamard” because that family is orthogonal up to a simple normalization and admits a fast algorithm. A typical choice is

$$
M=\frac{1}{\sqrt{d}}D_2 H D_1,
$$

where $D_1,D_2$ are random diagonal matrices with entries $\pm 1$ and $H$ is a (normalized) Walsh–Hadamard matrix. Multiplying by $D$ is $O(d)$ sign flips; multiplying by $H$ is done by the FWHT in $O(d\log d)$ operations (but only additions/subtractions). The in‑kernel implementation is the standard iterative butterfly: for stage $s=0,\dots,\log_2 d-1$ you pair entries and replace $(u,v)$ with $(u+v,u-v)$, doing this in place across the vector; after the final stage apply any final diagonal signs and the $1/\sqrt{d}$ scale. Because modern attention pipelines are memory‑bandwidth bound at this point, you can fuse the RoPE pass and the sign+FWHT pass inside the same producer kernel: read a token's $d$ features into registers, apply the RoPE $2\times 2$ pairwise rotations in place, flip signs (cheap), run the $\log_2 d$ butterfly stages (FWHT), apply normalization, then quantize to FP8 and write out. That is what the paper means by “fused with the rotary embedding at no extra computation cost.”

Practical notes and caveats. Head dimension is typically a power of two in practice (64,128,256), which makes FWHT straightforward; if not you would pad or use other orthonormal transforms. Be sure to use the same normalization convention so $MM^\top=I$ (or if you omit the normalization, fold the resulting scalar factor into your FP8 scaling factors). Finally, for FP8 attention the paper combines this incoherent transform with block quantization (per‑block scale factors) and in‑kernel transposes (LDSM/STSM) so the whole sequence — RoPE → sign flips → FWHT → quantize → tile transpose → FP8 WGMMA — happens with minimal global‑memory traffic.

Summary: apply the same orthogonal $M$ to both $Q$ and $K$ within a head (you may pick different $M$ per head), apply it after RoPE to preserve the RoPE dot‑products, and compute $M$ cheaply via sign flips plus an FWHT (the standard $O(d\log d)$ butterfly), which you can fuse with the RoPE kernel to avoid extra memory passes. This is exactly the construction and fusion the paper describes to spread out outliers before FP8 quantization.

### What exactly is the FP8 baseline for error, and how is RMSE computed fairly?
Question:
The error experiment draws $\mathbf{Q},\mathbf{K},\mathbf{V}$ from a mixture that injects 0.1 percent outliers and compares RMSE against an FP64 reference. For the FP8 baseline, you state per-tensor scaling, FP32 accumulators, and softmax intermediates in FP16. Could you detail: (1) which operations are in FP8 vs FP16 vs FP32 for the baseline; (2) whether scales are chosen per input tensor or per matmul operand; (3) whether RMSE is measured on the final $\mathbf{O}$ after all rescalings; and (4) how seeds and sample sizes are controlled so the 2.6$\times$ improvement is statistically robust?
Answer:
Short answer: the paper’s FP8 “baseline” is the simple per-tensor FP8 recipe: Q/K/V are quantized with one scale per tensor, the attention GEMMs run using FP8 operands on the hardware Tensor Cores with FP32 accumulation, and the softmax path (row‑max subtraction, exp, row sums, normalization) is executed in FP16; the RMSE reported is the root‑mean‑square difference between the final attention output $O$ from the low‑precision implementation and an FP64 reference (after converting the low‑precision output to high precision). The paper gives the input distribution used for the trial but does not publish per‑trial RNG seeds or a repeat count, so the $2.6\times$ number is obtained from paired comparisons on the same random draws (and from many output elements), but if you want formal statistical guarantees you should repeat the experiment over multiple seeds and report $\mathrm{mean}\pm\mathrm{std}$ or a confidence interval.

More detail and intuition. (1) Precision mapping for the FP8 baseline. The paper explicitly summarizes the baseline as “per‑tensor scaling, FP32 accumulators, and softmax intermediates kept in FP16.” Operationally that means the input tensors $Q$, $K$, $V$ are quantized using a single scale per tensor to FP8; the matrix multiplications that produce the score matrix $S = \alpha QK^T$ and the projection $O = P V$ are executed on the low‑precision Tensor Cores using FP8 operands but with FP32 accumulation (so the internal accumulator has FP32 precision before any casts back to a storage format); the softmax pipeline (compute row max, form exponentials, accumulate row sums, and normalize) is carried out in FP16 to avoid the catastrophic dynamic‑range / rounding issues that would occur in FP8. After the final matmul the implementation materializes the output (effectively in full float precision for comparison); the FP8 baseline therefore mixes FP8 storage/operands, FP32 accumulation for matmuls, and FP16 for the numerically sensitive softmax steps. The paper does not go into micro‑implementation variants (for example, different libraries may dequantize some operands to FP16 before the second GEMM), but the phrase above is the canonical description used for the baseline in the comparison.

(2) How scales are chosen. The baseline uses per‑tensor scaling (one scalar scale per whole $Q$, one per $K$, one per $V$), as the paper states. FlashAttention‑3’s improvement comes from switching to block quantization (one scale per block of the tensor, aligned with the algorithm’s block tiling) plus an incoherent preprocessing transform; those two changes reduce quantization error relative to a single global scale.

(3) What “RMSE against FP64 reference” actually means. The RMSE reported is computed between the attention output tensors elementwise: if $O_{\text{ref}}$ is the output computed in FP64 and $O_{\text{low}}$ is the output from the low‑precision method converted to FP64 for comparison, then $$\mathrm{RMSE}=\sqrt{\frac{1}{M}\sum_{i=1}^{M}\bigl(O_{\text{low},i}-O_{\text{ref},i}\bigr)^2},$$ where $M$ is the total number of scalar outputs (all entries of the output block/tensor used in the experiment). In other words, the comparison is on the final $O$ after all softmax rescalings and matmuls have been applied. (The paper’s “Numerical Error Validation” section describes the input draw and then “measure the root mean squared error (RMSE)”; that is the quantity reported in the table.)

(4) Seeds, sample size and robustness of the $2.6\times$ claim. The paper specifies the input distribution used for the numerical test, $$\mathcal{N}(0,1)+\mathcal{N}(0,100)\cdot\mathrm{Bernoulli}(0.001),$$ so each entry is typically $\mathcal{N}(0,1)$ but 0.1% of entries have a large (std‑10) outlier. The manuscript does not give explicit RNG seeds or a stated number of independent random trials for the RMSE table. Two facts work in favor of robustness even without multiple seeds: first, the RMSE is averaged over many output elements (so a single random draw produces a large effective sample size); second, the comparisons are paired (the same random $Q/K/V$ are used to produce both the baseline and FlashAttention‑3 outputs), which reduces variance in the ratio. Still, for a rigorous statistical statement you should (and I recommend you) do the following when you reproduce this experiment: fix a deterministic seed for each run, run the whole pipeline for a number $T$ of independent seeds (common practice uses at least $T=30$ for CLT‑style error bars), compute the RMSE per seed for both methods on the same inputs (so you get paired RMSE samples), then report the mean and standard deviation (or a 95% confidence interval) of the RMSE and of the RMSE ratio. Because the comparison is paired you can also report the distribution of the per‑seed ratios or do a paired test. These steps make the “$2.6\times$” number statistically interpretable; without that extra bookkeeping the number in the paper should be read as the ratio observed on the described synthetic ensemble (large tensors with 0.1% outliers) rather than as a fully randomized hypothesis test.

If you want, I can sketch a minimal reproducible script (pseudo‑code or PyTorch/CUDA) that generates the mixture inputs, runs both the baseline and FlashAttention‑3 implementations on the same seeds, computes elementwise RMSE, and returns $\mathrm{mean}\pm\mathrm{std}$ / CI for the RMSE ratio so you can verify the $2.6\times$ figure under controlled repetition.

### Can you justify the 50 percent cycle estimate for exponentials in FP16 attention on H100?
Question:
The text claims that for head dimension $d=128$ in FP16, there are about $512\times$ more matmul FLOPs than exponentials, but exponentials have $256\times$ lower throughput on H100, so the exponential can take about 50 percent of the time compared to matmul. Could you show a back-of-the-envelope calculation that relates: (a) the counts of exp operations per tile or per token pair, (b) GEMM FLOPs for $\mathbf{Q}\mathbf{K}^\top$ and $\mathbf{P}\mathbf{V}$, and (c) the hardware throughputs (989 TFLOPs for FP16 matmul vs roughly 3.9 TFLOPs-equivalent for special functions), to arrive at the 50 percent number?
Answer:
Short answer: the paper’s “about 50%” comes from a simple per-token‑pair FLOP vs special‑op throughput comparison. For one $(i,j)$ score (one token pair) you do $4d$ GEMM FLOPs but only one exp; with $d=128$ this is $512$ GEMM FLOPs per exp, and the H100’s FP16 Tensor‑Core throughput is $\sim 989$ TFLOPS versus $\sim 3.9$ TFLOPS of special‑function (exp) throughput, so

$$
\frac{\text{time}_\text{exp}}{\text{time}_\text{GEMM}}
= \frac{1/S_{\text{exp}}}{(4d)/S_{\text{mat}}}
= \frac{S_{\text{mat}}}{4 d\, S_{\text{exp}}},
$$

and plugging in $S_{\text{mat}}=989$ (FP16 TFLOPS), $S_{\text{exp}}=3.9$ (TFLOPS‑equivalent for exp), $d=128$ gives

$$
\frac{\text{time}_\text{exp}}{\text{time}_\text{GEMM}}
= \frac{989}{4\cdot 128 \cdot 3.9}
= \frac{989}{512\cdot 3.9}
\approx 0.50.
$$

How these factors arise: the forward attention does two big GEMMs per head ($QK^\top$ and $P V$), each conventionally counted as $2N^2 d$ FLOPs, so total GEMM work per score (per $(i,j)$) is $4d$ FLOPs. Softmax evaluates one exponential per score (plus cheap subtract/adds). Thus for $d=128$ the ratio of GEMM FLOPs to exponentials is $4d/1=512$. But Tensor Cores are $\sim\!256\times$ (paper rounds to 256) faster than the special‑function unit ($989/3.9 \approx 254$), so the $512\times$ more arithmetic is roughly canceled by the $\sim 256\times$ higher GEMM throughput, leaving the exp cost $\approx 0.5\times$ the GEMM cost.

Caveats and intuition: this is a back‑of‑the‑envelope, peak‑throughput comparison. It assumes multiply+add FLOP counting (hence the factor 2 per multiply‑add), one exp per score, and that both units can be fed near their theoretical peak and overlapped. In practice memory, reductions, instruction overhead and imperfect overlap reduce ideality — which is precisely why FlashAttention‑3 designs pipelining and warp‑specialization to hide the exp work under Tensor‑Core GEMMs. Also note the easy generalization: for arbitrary head size $d$,

$$
\frac{\text{time}_\text{exp}}{\text{time}_\text{GEMM}}
\approx \frac{S_{\text{mat}}}{4 d\, S_{\text{exp}}},
$$

so smaller $d$ makes the exp relatively more expensive (e.g., $d=64$ gives $\approx 1$), and moving to FP8 (doubling GEMM throughput) makes the exponential relatively *more* dominant (for $d=128$ the ratio moves toward $\approx 1$). This algebra is exactly the intuition the paper uses to motivate overlapping softmax (exps) with GEMMs on H100.

### How should one pick tile sizes $B_r$, $B_c$ and the number of SMEM stages $s$ in practice?
Question:
There are multiple trade-offs: larger tiles improve arithmetic intensity but increase register and SMEM pressure; the 2-stage pipeline requires extra registers to hold $\mathbf{S}_{\mathrm{next}}$; the in-kernel transpose of $\mathbf{V}$ may prefer particular $B_c$ multiples and alignments; and $s$ affects TMA overlap and SMEM footprint. Are there recommended heuristics for choosing $B_r$, $B_c$, and $s$ on H100 for common head dimensions (64, 128, 256), and how do these choices change between FP16 and FP8 kernels?
Answer:
Short answer: pick tiles to sit inside three hardware budgets — shared memory (SMEM), registers, and TMA/WGMMA throughput — and then tune empirically. Use the simple capacity formulas below to reason about trade‑offs, start from a conservative default (FP16: $B_r=32,\;B_c=128,\;s=2$) and then nudge $B_r,B_c,s$ up or down guided by the rules I give. FP8 generally needs slightly smaller tiles (or fewer pipeline stages) and stricter alignment (multiples of the LDSM/STSM tile) because of the in‑kernel transpose and extra register work for accumulator permutations; it also benefits more from increasing the pipeline depth to hide the doubled GEMM throughput.

Why these knobs matter (formulae you can actually use). The two dominant constraints are shared memory footprint and register footprint of the pipelined state (mainly the $S$ block that must be kept in registers for the 2‑stage pipeline). If each element is stored in memory with $b$ bytes (FP16 $b\!=\!2$, FP8 $b\!=\!1$ in principle — note FP8 in practice is often packed for LDSM/STSM), an approximate SMEM budget per CTA is

$$
\text{SMEM}_\text{CTA} \approx (B_r + 2 s B_c)\cdot d \cdot b + \text{small\_overheads},
$$

because you keep one $Q_i$ tile ($B_r\times d$) and an $s$‑stage circular buffer with one $K_j$ and one $V_j$ per stage (each $B_c\times d$). The 2‑stage pipeline keeps one extra score block in registers:

$$
\text{registers for }S_{\text{next}} \approx B_r\cdot B_c \quad (\text{FP32 accumulators}).
$$

Per‑thread register usage is roughly

$$
R_{\text{per\_thread},S} \approx \left\lceil\frac{B_r B_c}{T}\right\rceil
$$

where $T$ is the number of threads in the CTA (typical choices are 128 or 256). The hardware hard limit is 256 registers per thread on H100, but you must leave headroom for compiler temporaries, WGMMA state, and the softmax bookkeeping, so avoid pushing near that limit.

Practical heuristics and how they map to $d=64,128,256$ on H100

1. Pick $B_r\cdot B_c$ to fit the register budget first. In practice you want the $S_{\text{next}}$ registers per thread to be “a few dozen” registers so the compiler still has space. A good rule of thumb is

$$
B_r\cdot B_c \lesssim 8{,}000
$$

which for $T=256$ gives $\approx 32$ FP32 registers per thread for $S_{\text{next}}$ (plus the other registers the kernel needs). If you see register spilling in Nsight/ptxas output, reduce $B_r\cdot B_c$.

2. Start with a conservative default for FP16 and tune from there. A robust starting point on H100 that the paper’s implementation uses as a baseline idea is

FP16 start: $B_r=32,\; B_c=128,\; s=2$.

This configuration keeps $B_rB_c=4096$ (comfortably under the example budget) and gives a good balance between arithmetic intensity, SMEM, and register use for the common head sizes. For many workloads this is already close to optimal.

3. How to move $B_r$ and $B_c$ as $d$ changes. The score block $S$ size is independent of the head dimension $d$ (it is $B_r\times B_c$), but the relative cost of GEMMs versus softmax scales with $d$. Intuitively:

- For small heads ($d=64$) softmax / exponential is relatively more expensive compared to the GEMM work, so you gain more by making each GEMM chunk bigger (larger $B_c$) so softmax can be amortized and overlapped. So for $d=64$ it is often good to keep $B_r$ moderate ($32\text{--}64$) and choose $B_c$ on the higher side ($128\text{--}256$) as long as $B_rB_c$ stays under the register budget. $s=2$ is still a good default; increase $s$ only if you still have free SMEM and see TMA stalls.

- For medium heads ($d=128$) the default $B_r=32,\;B_c=128,\;s=2$ is a recommended starting point; that is the regime where the paper reported the large FLOP rates and where the two‑stage pipelining wins strongly.

- For large heads ($d=256$) the GEMM is relatively heavier and softmax overhead is smaller, so you can afford smaller $B_r$ ($16\text{--}32$) or keep $B_c$ moderate (128) — the key is to reduce $B_r$ if you hit register pressure from $S_{\text{next}}$. Because GEMMs are heavier, the need to increase $B_c$ for amortization is reduced.

4. FP8-specific adjustments. FP8 brings two important changes: higher GEMM throughput (so hiding softmax becomes more important) and stricter layout constraints (FP8 WGMMA requires k‑major operands in SMEM), which forces an in‑kernel transpose of $V$ and extra register shuffles for accumulator reordering. That implies:

- Align $B_c$ to the LDSM/STSM tile: LDSM/STSM operate on an $8\times 8$ half‑word tile (128 bytes), and the FP8 implementation packs two 8‑bit values into a 16‑bit lane for these instructions. So choose $B_c$ that is a multiple of 8 (safer: multiple of 16) so that transposes fill the $8\times 8$ blocks without epilog cleanup. This reduces register shuffles and warp divergence in the transpose.

- Because the FP8 path needs extra registers for the accumulator permutation and for staging the transposed $V$, be conservative on $B_r\cdot B_c$. Practically, either reduce $B_r$ by $\sim 2\times$ from FP16 choices or reduce $B_c$ so $B_rB_c$ stays under the same cap. A practical FP8 starting point therefore is

FP8 start: $B_r=24\text{--}32,\;B_c=128\;(\text{multiple of }8),\;s=3$

where you may increase $s$ to 3 to better hide TMA + the now‑higher GEMM throughput, but only if SMEM allows it.

5. Pick $s$ to trade SMEM for TMA overlap. Each extra stage increases SMEM by about $2B_c d b$ (a $K$ and a $V$ tile) but improves the burstiness of TMA and the ability to keep the Tensor Cores busy. On H100 a small number of stages is sufficient; the paper’s design often uses $s=2$ for FP16 and moves to $s=3$ for FP8 or very long sequences where you want more TMA headroom. If SMEM is the limiter, keep $s=2$ (or even $s=1$ for tiny SMEM budgets). If you see TMA stalls (producer waiting to write a free stage) then increase $s$.

How to tune in practice (recommended workflow). Start from the FP16 default ($B_r=32,B_c=128,s=2$). Run a representative config and collect three signals: TFLOPS and achieved occupancy, SMEM usage per CTA, and “register spilling” / local memory usage from the compiler or Nsight. If you see low TFLOPS but no register spilling and SMEM has plenty of slack, increase $B_c$ in steps of 32 to 64 until TFLOPS plateau or you hit SMEM limits. If you see spilling, reduce $B_rB_c$ (reduce $B_r$ first because it keeps $B_c$ large for arithmetic intensity). For FP8 follow the same loop but be careful to align $B_c$ to 8 or 16 and expect to need to lower $B_r$ relative to FP16 because of additional per‑CTA register needs (accumulator permutes, transpose staging).

A few final practical reminders drawn from the paper. The H100 WGMMA FP8 operand layout restriction is the concrete reason to prefer $B_c$ multiples of the $8\times 8$ LDSM tile and to do the in‑kernel transpose rather than a global pre‑transpose; the in‑kernel transpose should itself be scheduled by the producer warpgroup to hide its cost. The 2‑stage pipelined consumer wins on H100 because it hides softmax under GEMMs, but it costs the extra register budget to hold $S_{\text{next}}$ — that is the main limiter on how big you can make $B_r$ and $B_c$. Finally, profile — the algorithmic wins in the paper (FP16 reaching up to 740 TFLOPs/s, FP8 close to 1.2 PFLOPs/s) come from getting these balances right and then using warp‑specialization / setmaxnreg and the asynchronous pipeline; the same tuning procedure above is how the authors arrived at those high utilization points.

If you want, tell me the exact per‑CTA SMEM target you must respect and the typical threads per CTA you use (128 vs 256); I can give 2–3 concrete (non‑conservative) numeric configurations for $d\in\{64,128,256\}$ in FP16 and FP8 that fit that budget.

### How does setmaxnreg-based dynamic register reallocation interact with warp specialization?
Question:
FA-3 uses setmaxnreg so producer warps (mostly issuing TMA and LDSM/STSM) give up registers to consumer warps (running WGMMAs and softmax). Is setmaxnreg applied per warpgroup or per warp, and is it static at kernel entry or can it change mid-kernel? How do you determine the target register counts to avoid spilling in the 2-stage pipeline while keeping enough occupancy, and are there hazards if a producer warp temporarily needs more registers for in-kernel $\mathbf{V}$ transposes?
Answer:
Short answer: setmaxnreg in FlashAttention-3 is used at the warpgroup granularity and is invoked dynamically inside the kernel (i.e., it can change mid‑kernel at the role boundaries). The paper’s implementation shrinks the register allotment of producer warpgroups (TMA / LDSM/STSM work) and enlarges the allotment of consumer warpgroups (WGMMA + the 2‑stage pipeline buffers). You pick the numeric targets by measuring the consumer’s true register need (including the extra "$S_{\text{next}}$" buffer that the 2‑stage pipeline keeps in registers) and then give consumers just enough registers to avoid spilling while keeping producers as small as possible to preserve occupancy. If a producer suddenly needs more temporaries (e.g., for an in‑kernel V transpose) you must either implement that transpose in a register‑frugal way (the paper uses LDSM/STSM which are register‑efficient and therefore fit the small producer allotment) or arrange a deliberate reallocation at a synchronization point; otherwise the excess demand will force spilling and kill performance.

Why per‑warpgroup and dynamic: the paper explicitly says Hopper “supports the dynamic reallocation of registers between warpgroups via setmaxnreg,” and the pseudocode shows the kernel calling “deallocate predetermined number of registers” in the producer path and “reallocate predetermined number of registers” in the consumer path. That is exactly mid‑kernel reconfiguration at warpgroup level (a warpgroup is the contiguous block of warps discussed in the paper).

How to pick concrete targets (intuitive + practical): the dominant extra register pressure of the 2‑stage pipeline is storing the extra score tile $S_{\text{next}}$ in registers. The paper notes that this costs roughly one tile’s worth of floats per threadblock, so a simple estimate of the extra registers per thread is
$$
\text{extra\_regs\_per\_thread} \approx \frac{B_r \times B_c}{\text{threads\_in\_threadblock}},
$$
because each float is one 32‑bit register slot in the usual convention. In practice you do the following loop: choose your tile sizes ($B_r, B_c$) and pipeline depth, compile and inspect the generated assembly/register report (nvcc -Xptxas -v or SASS inspection as the paper does), note the compiler’s per‑thread register usage and whether the compiler reports spills, and then set the warpgroup register cap so that consumer warpgroups get
$$
R_{\text{consumer}} \approx R_{\text{base\_consumer}} + \text{extra\_regs\_per\_thread} + \text{safety\_margin},
$$
and producers get a much smaller cap (they are mainly issuing TMA/LDSM/STSM and are register‑light). Tune the safety margin conservatively at first (a few registers per thread) and then reduce it if you want to increase occupancy. Use the occupancy calculator (or nvcc reports) to see how many CTAs/warpgroups per SM that allocation yields.

Trade‑offs and hazards: giving more registers to consumers raises per‑thread register counts and reduces the number of resident warpgroups per SM (lower occupancy), but that is often acceptable because consumer work is Tensor‑Core heavy and benefits from more in‑thread buffering (the paper makes this explicit). The real performance cliff is spilling: if the compiler/runtime cannot fit the live variables into the allotted registers it will spill to local memory and you lose the asynchrony/throughput gains. So the objective is to allocate just enough registers to avoid spills for the consumer pipeline. For producers, the paper’s strategy is to avoid transient large register needs: they implement the in‑kernel V transpose using LDSM/STSM (register efficient) in the producer warpgroup so that it fits the small producer cap. If you cannot make the transpose register‑frugal, you must arrange a reallocation at a synchronization point (call setmaxnreg to increase producer caps, perform the transposes, then shrink again), but that complicates scheduling and can introduce stalls — so the safer engineering choice is to design the producer work to fit its small allotment.

Practical checklist (what the paper actually did): (1) pick $B_r$, $B_c$ and pipeline depth; (2) compile and inspect reg use and spilled registers in the consumer path (SASS / nvcc reports); (3) compute extra register need from the $S_{\text{next}}$ tile and add a small margin; (4) set setmaxnreg per warpgroup at the role switch points exactly as in the pseudocode; (5) implement producer transposes with LDSM/STSM to keep them register‑light; (6) profile for spills and TFLOPs — if you see spills, either increase consumer caps or reduce tile/pipeline size; if occupancy is too low, reduce consumer caps (but only if no spills result).

This is the approach the paper describes and uses: dynamic (mid‑kernel) per‑warpgroup reallocation by setmaxnreg, choose targets by SASS/compile‑time and runtime profiling to avoid spilling, and avoid producer register bursts by using LDSM/STSM or explicit, synchronized reallocation when necessary.

### How are MQA and GQA supported without duplicating $\mathbf{K}$ and $\mathbf{V}$ in HBM?
Question:
The paper says it follows the FA-2 approach for multi-query and grouped-query attention by adjusting indexing to avoid duplicating $\mathbf{K}$ and $\mathbf{V}$. Could you detail how the TMA loads and SMEM staging are organized so that multiple query heads reuse the same $\mathbf{K}_j, \mathbf{V}_j$ tiles, and how the consumer warps iterate over heads while keeping the producer-consumer ring buffer efficient?
Answer:
Short answer: FlashAttention‑3 (like FlashAttention‑2) avoids duplicating $K$ and $V$ in HBM by storing one copy per “key group” in global memory and then staging each $K_j, V_j$ tile once into the CTA’s circular SMEM buffer so it can be reused for every query head that belongs to that group. Concretely the kernel (1) lays out $K/V$ in HBM with a group index (for MQA that group index is $0$; for GQA it is $g=\lfloor h/G\rfloor$), (2) issues one TMA load of the $(j)$th key/value tile for that group into a ring buffer stage in SMEM, and (3) has the consumer warps iterate an inner loop over the local heads that share that group so they all use the same SMEM $K_j, V_j$ tile before the stage is released. The producer only reuses (overwrites) a stage after every consuming head has finished with that stage, so no $K/V$ duplication is needed in HBM and the producer/consumer ring stays efficient because TMA + WGMMA are asynchronous and the pipeline is sized to hide latency.

Longer explanation (what is actually happening inside the kernel). The two implementation levers are (A) a compact HBM layout and pointer arithmetic for TMA loads, and (B) a CTA/warp-level iteration order that reuses SMEM tiles for multiple heads.

1) HBM layout and TMA indexing. In the duplicated‑free layout you store $K$ and $V$ as one block per key‑group rather than one block per head. If heads are grouped with size $G$ then a head $h$ reads keys/values from group $g=\lfloor h/G\rfloor$. The producer’s TMA source pointer is computed with that group offset so a single TMA call brings the correct $B_c\times d$ tile for group $g$ into SMEM. In other words the TMA address for $K_j$ is computed as $\text{base} + ((\text{batch\_index} \times \text{n\_groups} + g) \times N + j \times B_c) \times d \times \text{bytes\_per\_elem}$ (and analogously for $V$). This avoids duplicating $K/V$ in HBM.

2) SMEM ring buffer and single staging per group‑tile. The kernel already uses an $s$‑stage circular SMEM buffer (stage index = $j \bmod s$). The producer writes a $K_j, V_j$ tile once into stage $(j \bmod s)$ and then commits. The consumer(s) read from that stage. For GQA/MQA you do not change that buffer structure; you only change how/when the consumer releases a stage: the consumer must keep the stage live until all heads that share this group have consumed it.

3) Consumer iteration over heads (how reuse happens). To actually reuse one SMEM $K_j, V_j$ copy for several heads you put an inner head loop on the consumer side: for each stage $j$ the consumer performs the SS‑GEMM / softmax accumulation and RS‑GEMM for head $0$, then for head $1$, … for every head in the local head set that maps to this group, before it issues the release of that stage back to the producer. That means the per‑head streaming softmax state (the running row‑max $m_i^{(h)}$, the normalizer $\ell_i^{(h)}$, and the partial output accumulator $O_i^{(h)}$) must be kept independently per head (in registers / SMEM) while the stage is alive. Because the tile $K_j, V_j$ remains resident in the same SMEM stage through that inner head loop, every head reuses the identical $K_j, V_j$ without any extra HBM copy.

4) Keeping the ring buffer efficient (avoiding stalls). Two facts keep the buffer full and the pipeline efficient. First, TMA and WGMMA are asynchronous and we use warp‑specialization: producer warps issue TMA loads (and optionally the in‑kernel transpose for FP8) and consumer warps issue WGMMA computes; those operations overlap. Second, the ring buffer has $s$ stages chosen large enough to hide the time it takes for the consumer to process all local heads for a stage. In practice the kernel maps a small contiguous set of heads to a CTA (so no cross‑CTA synchronization is required) and chooses $s \ge \text{pipeline depth}$ (2 or 3 in the paper) so the producer can write ahead while consumers are still processing previous stages. Because the producer only waits on a stage when it has been consumed by all assigned heads, the producer/consumer producer never needs to duplicate $K/V$ in HBM to shorten this wait.

5) Practical notes and trade‑offs. Reusing $K/V$ in SMEM across multiple heads increases register/SMEM pressure because each head needs its own $m,\ell,O$ state for the query tile. So implementations pick how many heads are folded into a CTA to trade off register/shared memory usage vs. how often $K/V$ gets reloaded from HBM. If you cannot or do not want to fold all consuming heads into the same CTA, you still avoid HBM duplication (the HBM copy is singular per group) but different CTAs will load the same $K/V$ tile independently from HBM into their local SMEM; that still saves global memory and simplifies layout, but gives less SMEM reuse.

6) FP8 / layout wrinkles. The same reuse pattern holds when the kernel also has to perform the FP8-specific in‑kernel transpose and register permutations described in the paper: the producer does the transpose as it writes the $K_j$ or $V_j$ stage (so the SMEM tile is in the k‑major layout required by FP8 WGMMA), and consumer warps iterate over heads against that staged, properly permuted tile. Those extra transpose/permute costs are scheduled in the producer and overlapped with other work (thanks to TMA/WGMMA asynchrony).

In short: FlashAttention‑3 follows FA‑2’s trick of storing one $K/V$ per key‑group and simply indexes TMA loads to fetch that group copy. Inside the CTA the algorithm either (a) folds every head of that group into the same CTA so a single SMEM-staged $K_j, V_j$ tile is reused across the group by iterating over heads and releasing the ring stage only after every head is done, or (b) if folding is not possible, still stores only one copy in HBM and accepts per‑CTA reloads. The producer/consumer ping‑pong and the $s$‑stage SMEM ring remain the same; only the consumer’s inner loop and the stage‑release semantics are adjusted so multiple heads can reuse the same $K_j, V_j$ tile without global duplication.

### Which tensors use FP8, FP16, or FP32 in FP8 FlashAttention-3, and why?
Question:
For the FP8 kernel, my understanding is: $\mathbf{Q},\mathbf{K},\mathbf{V}$ tiles are quantized to FP8 with per-block scales; both GEMMs run on FP8 Tensor Cores with FP32 accumulators; softmax intermediates ($m_i$, $\ell_i$, and $\widetilde{\mathbf{P}}$ before the second GEMM) are in FP32; and $\mathbf{O}_i$ is accumulated in FP32 before writing out. Is this accurate? If so, could you summarize the datatype of each buffer and intermediate and the points where dequantization or rescaling happens, and explain the rationale behind each precision choice?
Answer:
Short answer: your high-level picture is correct — FlashAttention‑3’s FP8 kernel keeps Q/K/V in FP8 (per‑block scales), runs both matmuls on the FP8 Tensor Cores (WGMMA) with FP32 accumulators, and keeps the numerically sensitive parts of softmax and the running normalization at higher precision. The main nuance is how the implementation avoids explicit slow $FP32\leftrightarrow FP8$ roundtrips and extra global-memory traffic: per‑block scales are tracked and applied/folded at the block boundaries, and the code uses in‑kernel transposes + in‑register permutations so the second GEMM can be launched on the FP8 Tensor Cores without materializing large FP32 temporaries to HBM.

Below I summarize, block by block, which datatype is used and where rescaling/quantization happens, with the intuition and rationale the paper gives.

Q, K, V in HBM and quantization. The inputs $\mathbf{Q},\mathbf{K},\mathbf{V}$ are stored/encoded as FP8 (e4m3) using block quantization: each tile/block gets its own scale factor. FlashAttention‑3 optionally applies the cheap incoherent transform (Hadamard $\times$ random signs) before quantizing so outliers are “spread out” and quantization error drops. The quantization itself is fused with the preceding memory‑bound operation (e.g., rotary), so the cost of creating the FP8 blocks is negligible in practice.

Tile loads and layout fixes. Tiles are loaded from HBM into SMEM in FP8 form. For FP8 WGMMA there is a layout constraint (k‑major for the inputs), so $\mathbf{V}$ tiles are transposed in‑kernel using LDSM/STSM (and some register moves) immediately after the TMA load. These layout fixes are done in the producer warps so they do not force extra global‑memory traffic or big slowdowns.

First GEMM (scores). The first GEMM that computes the block scores uses FP8 operands (the FP8 tiles of $\mathbf{Q}$ and $\mathbf{K}$) on the FP8 Tensor Cores (WGMMA); the instruction produces FP32 accumulators (held in registers). Call the raw accumulator output from the WGMMA $\widehat{\mathbf{S}}$ (FP32). Because $\mathbf{Q}$ and $\mathbf{K}$ were quantized with per‑block scales $s_Q,s_K$, the true score block is
$$
\mathbf{S} = (s_Q s_K)\,\widehat{\mathbf{S}} .
$$
The paper stresses that the matmul work itself is done in FP8 for throughput but accumulation is FP32 to preserve dynamic range and to avoid catastrophic accumulation error.

Softmax internals ($m_i$, $\ell_i$, $\widetilde{\mathbf{P}}$). The softmax machinery — the running row max $m_i$, the running normalizer $\ell_i$ and the elementwise exponentials that produce $\widetilde{\mathbf{P}}$ — is handled in higher precision for numerical stability. Conceptually the algorithm applies the block scale factor for $\mathbf{S}$ before/when computing the rowwise max and the exponentials, so the softmax algebra is correct under block quantization. The paper explicitly points out that keeping softmax intermediate computations in FP32 is what gives FlashAttention‑2/3 their lower RMSE in the FP16 path; for the FP8 story the authors compare against a baseline FP8 implementation that kept softmax in FP16 and show FlashAttention‑3 achieves much lower error thanks to block quantization + incoherent processing. The implementation therefore treats softmax as a higher‑precision stage (the exponentials and the running reductions are done in FP32 accumulators) so that the numerically sensitive nonlinear step does not become the major source of error.

Handing $\widetilde{\mathbf{P}}$ into the second GEMM. The second matmul multiplies the (local) softmax tile by the corresponding $\mathbf{V}$ tile to update $\mathbf{O}_i$. FlashAttention‑3 wants that matmul to run on FP8 Tensor Cores too, because that is where the throughput gain is. That means the consumer of the second WGMMA must see its left operand in the layout/packing that the FP8 WGMMA expects. The paper’s implementation avoids writing large FP32 $\widetilde{\mathbf{P}}$ tiles back to GMEM and then re‑loading/quantizing them. Instead they (a) keep the softmax result in registers/SMEM in FP32 while computing it, (b) apply efficient in‑register byte permutations to reorder the FP32 accumulator register layout produced by the first WGMMA into the format the second WGMMA expects, and (c) use the in‑kernel transposed $\mathbf{V}$ tile so both operands are in the k‑major packing the FP8 WGMMA requires. In short: the path from "softmax result" to "operand for second WGMMA" is implemented with in‑register/SMEM repacking and avoids an expensive global $FP32\rightarrow FP8$ roundtrip. The net effect seen by the programmer is that both GEMMs are dispatched to FP8 Tensor Cores, while the expensive nonlinear work and the normalization bookkeeping are done in FP32.

Second GEMM and accumulation of $\mathbf{O}_i$. The second WGMMA runs on FP8 operands (left operand coming from the repacked softmax tile, right operand $\mathbf{V}$ in the transposed FP8 layout) and again accumulates in FP32 registers. The partial outputs to $\mathbf{O}_i$ are therefore accumulated in FP32 to avoid losing precision across many tile contributions. Only at the very end (epilogue) is $\mathbf{O}_i$ scaled/finalized and written out; the writeback may be cast to the desired model storage dtype (e.g., FP16 or FP32), but the on‑chip accumulation is FP32 for accuracy.

Where (de)quantization and rescaling happen, succinctly. Quantization from FP32 to FP8 happens once per input block (fused with preceding ops where possible). The per‑block scale factors travel with tiles. The first WGMMA produces an FP32 accumulator $\widehat{\mathbf{S}}$ and the block scale $s_Q s_K$ is applied (conceptually) before softmax; the paper describes implementation strategies that fold/implement that scaling cheaply at the block boundary. The softmax produces $\widetilde{\mathbf{P}}$ in higher precision; before invoking the second FP8 WGMMA the softmax tile is repacked/quantized in‑register (the implementation detail is a layout/packing trick rather than a heavy memory roundtrip). The second WGMMA then consumes FP8 operands and accumulates in FP32; final outputs are cast for storage at the epilogue.

Why each choice is made (intuitive rationale). FP8 for the sequence operands (Q/K/V) gives a big win in memory bandwidth and allows the use of FP8 Tensor Cores for higher FLOPs/s. But FP8 has tiny mantissa/exponent and so is fragile for nonlinear reductions and long accumulations; therefore the critical accumulation path and the nonlinear softmax are executed in FP32 to protect numerical correctness. Block quantization and incoherent processing reduce FP8 quantization error by (1) adjusting dynamic range per block and (2) spreading out extreme values before quantization, so the FP8 pipeline becomes far more accurate than naive per‑tensor FP8. The in‑kernel layout/byte‑permute tricks are engineering decisions to make the data‑format handoff between two FP8 WGMMA calls cheap — avoiding slow global memory writes and extra quantize/dequantize passes.

Practical takeaway. Your original list is essentially right: $\mathbf{Q},\mathbf{K},\mathbf{V}$ are block‑quantized to FP8; both GEMMs are dispatched to FP8 Tensor Cores and accumulate into FP32; softmax bookkeeping (row maxima, running normalizers, exponentials) is handled at higher precision; and $\mathbf{O}_i$ is accumulated in FP32 and only cast when writing out. The remaining implementation subtleties the paper emphasizes are how block scales are tracked/applied and how the first GEMM’s accumulator is repacked in registers so the second GEMM can run on FP8 without expensive global $FP32\rightarrow FP8$ materialization — that’s the part that makes the FP8 implementation both fast and accurate.

If you want, I can expand with a small diagram of the dataflow (where each tensor lives and its dtype at each stage) or sketch the algebra showing how the per‑block scale $s_Q s_K$ is folded into the stable softmax update used in FlashAttention’s local reduction.

### What is meant by a persistent kernel here, and why does lacking it hurt FP8 for small sequences and causal masks?
Question:
The discussion mentions that FA-3 FP16 has a persistent kernel and load balancing strategy, while the FP8 version does not, contributing to worse performance at small sequence lengths and with causal masks relative to cuDNN. Can you define the persistent-kernel strategy you use (e.g., mapping CTAs persistently to SMs and looping over work tiles), how it interacts with warp specialization and the ring buffer, and why its absence particularly penalizes small or triangular workloads?
Answer:
Short answer: “Persistent kernel” here means running a small set of long‑lived CTAs that stay mapped to SMs and loop over many work tiles (queries / heads / batches) instead of launching one short CTA per tile. That persistent mapping is what lets the implementation keep producer/consumer warp roles, a shared s‑stage ring buffer, register partitioning (via setmaxnreg), and the ping‑pong / multi‑stage pipelining running in steady state. When the FP8 kernel is not persistent these steady‑state benefits are lost, so per‑tile overheads (FP8 layout transposes and register permutations) and the low throughput of non‑GEMM work (softmax / exp) are no longer well amortized — which hurts small sequence lengths and triangular (causal) workloads the most.

Why that happens (intuitively, then with the paper’s mechanics). In FA‑3 the main performance trick is asynchronous producer/consumer pipelining: TMA producers stream Q/K/V tiles into an s‑stage circular shared‑memory buffer while consumer warpgroups run WGMMA (Tensor Core) GEMMs and run softmax work that is overlapped with GEMMs (ping‑pong and the 2‑stage pipeline). All of that relies on having enough iterations of the inner loop (enough K‑tiles) so the pipeline can be filled and remain filled. Write the number of key blocks as
$$T_c=\Big\lceil \frac{N}{B_c}\Big\rceil.$$
If the number of iterations per CTA is small (e.g., $T_c$ is small or the effective work per query is cut in half by a causal mask), you never reach the steady‑state pipeline where producers can stay several tiles ahead and consumers can overlap GEMMs with softmax. In the two‑stage pipelined consumer in the paper you need at least a couple of iterations to amortize the cost of filling the next $\mathbf{S}_{\text{next}}$ and overlapping the $\widetilde{\mathbf{P}}\mathbf{V}$ GEMM with the next softmax. Formally, if $T_c$ is comparable to or smaller than the pipeline depth (e.g. $T_c \lesssim 2$ for the 2‑stage overlap) there is little or no overlap to exploit.

Persistent CTAs make this overlap robust. By mapping CTAs persistently to SMs and looping over work tiles (often implemented as one CTA per SM or a small fixed number, with each CTA pulling the next tile from an atomic counter), you get several concrete benefits that the paper leverages:

1. Stable warp specialization: producer and consumer warpgroups can be fixed for the lifetime of the CTA. That lets you tune register budgets (the paper uses setmaxnreg) and instruction scheduling for each role once, and avoids repeated role setup / tear‑down costs.

2. Long‑lived ring buffer semantics: the s‑stage circular SMEM buffer is filled and drained repeatedly by the same producer/consumer warps. This amortizes the TMA startup/commit semantics and lets the asynchronous TMA + WGMMA units stay busy across many iterations.

3. Effective ping‑pong / multi‑stage pipelining: ping‑pong scheduling (swap roles so softmax on one group executes while GEMMs run on another) expects many loop iterations to reach steady state. Persistent CTAs provide those iterations even when global work is fragmented (you can pack multiple Q blocks, heads, batches etc. into the CTA’s loop).

4. Dynamic load balancing: a persistent kernel can implement lightweight dynamic work assignment (fetch next Q block) so CTAs that finish the small amount of work for early queries in a causal mask can grab more work. That removes the static imbalance inherent to triangular attention where early rows do much less work than late rows.

Why FP8 suffers more when the kernel is not persistent. The FP8 FA‑3 path needs extra per‑tile work beyond the GEMMs: in‑kernel transposes of V tiles (via LDSM/STSM) and register permutations to reconform FP32 accumulators and FP8 operand layouts. Those are fixed costs per tile that are amortized well when a CTA processes many tiles (persistent mode), but dominate when each CTA does only a few tiles. Second, FP8 WGMMA doubles matmul throughput (so GEMMs run faster) while the softmax / exponential units stay slow, increasing the need to hide softmax behind other GEMMs. That makes the pipeline fill/overlap even more important. Without persistence you get both: the per‑tile FP8 layout costs aren't amortized, and the reduced ability to overlap softmax with GEMMs leaves Tensor Cores under‑utilized — a double penalty for small sequences and causal masks. The paper’s footnote exactly points this out: FP16 FA‑3 used a persistent kernel + load balancing and did well at small sizes, while the FP8 FA‑3 did not include that persistent design and therefore fell behind cuDNN on small / causal cases.

In short: persistent kernels keep warps, registers, and the circular SMEM pipeline stable and long‑running so the asynchronous TMA + WGMMA machinery and the ping‑pong / 2‑stage overlaps can reach steady state and amortize FP8’s extra layout costs. When you remove that persistence, short or triangular workloads don’t give the pipeline enough iterations to pay off, so FP8’s advantages evaporate and performance degrades relative to an implementation that does include persistence and load balancing. This is why the authors list “integrating a persistent kernel design into the FP8 kernel” as the natural fix.

### What TMA alignment and shape constraints influence $B_c$ and SMEM layout for $\mathbf{K}$ and $\mathbf{V}$ tiles?
Question:
On Hopper, TMA copies have preferred alignment and granularity (e.g., 128-byte alignment). When choosing $B_c$ and laying out SMEM tiles for $\mathbf{K}_j$ and $\mathbf{V}_j$, what constraints do you enforce to get peak bandwidth and avoid bank conflicts, especially when you plan to immediately apply LDSM/STSM to $\mathbf{V}_j$ for an in-kernel transpose? Any concrete guidelines on strides, leading dimensions, and padding that proved important in FA-3?
Answer:
Short answer: you must make the SMEM/K/V tile shapes and strides line up with two 128‑byte primitives on Hopper: (1) TMA prefers 128‑byte aligned/ sized transfers, and (2) LDSM/STSM operate on $8\times 8$ 16‑bit tiles (128 bytes) so, when you pack FP8, a single LDSM/STSM moves an $8\times 16$ FP8 sub‑block. Practically this means choose and/or pad the key‑block size $B_c$ and the SMEM leading dimension so that tiles are multiples of the LDSM tile in elements and that all TMA loads/writes start and stride on 128‑byte boundaries; also store the transposed $V_j$ in SMEM so it is k‑major for FP8 WGMMA. The FA‑3 implementation follows these concrete rules to get full TMA/LDSM bandwidth and avoid extra register/warp shuffles.

Why, and the concrete rules used in FA‑3. Hopper TMA and LDSM operate at a 128‑byte granularity. LDSM/STSM are described as moving $8\times 8$ 16‑bit entries = 128 bytes; to use them for FP8 you pack two 8‑bit values into one 16‑bit slot, so an LDSM/STSM roundtrip covers an $8$ (rows) $\times$ $16$ (FP8 columns) logical FP8 tile. If your SMEM tile boundaries are not integer multiples of those units you pay tail handling, extra register permutes, and you risk non‑coalesced TMA transfers and SMEM bank aliasing.

FA‑3’s practical checklist (the form you should enforce in your allocator/tiler):

1) Alignment of TMA source/destination. Make every TMA issued for a $K_j$ or $V_j$ tile start on a 128‑byte aligned address and ensure the number of bytes transferred per TMA is a multiple of 128. A simple way to guarantee this is to pad the row stride (leading dimension) in SMEM or the HBM tile shape so that the contiguous chunk(s) TMA reads/writes are 128‑byte multiples.

2) LDSM/STSM block multiples. Lay out tiles so they break exactly into $8\times 8$ 16‑bit LDSM blocks (i.e. into $8\times 16$ FP8 sub‑blocks). Concretely, for FP8 it is simplest to enforce
$$
B_c \equiv 0 \pmod{8},\qquad d \equiv 0 \pmod{16},
$$
and to set the shared‑memory leading dimension
$$
\text{ld} \;=\; \mathrm{round\_up}(d,\;16)
$$
so that every LDSM/STSM operates on full $8\times 8$ 16‑bit tiles (no partial 16‑bit entries). If you cannot make $d$ exactly a multiple of 16 you can still work around it with extra small register shuffles (as FA‑3 documents), but performance is better and code simpler when you avoid tails.

3) Produce k‑major V tiles for FP8 WGMMA. FP8 WGMMA requires operands in SMEM to be k‑major. In attention the second GEMM is $P\cdot V$, so the inner (K) dimension of that GEMM is the sequence/block dimension $B_c$. Since the HBM layout is normally contiguous in the head dim $d$, you must transpose $V_j$ in‑kernel so the SMEM copy of $V_j$ is contiguous along $B_c$ (i.e. k‑major). FA‑3 does this in the producer warpgroup using LDSM/STSM (packing two FP8 into 16‑bit entries), which is why tile dimensions must match the LDSM block granularity.

4) Row‑stride / padding to avoid bank aliasing. Ensure the SMEM row stride ($\text{ld}$) when expressed in bytes,
$$
\text{ld\_bytes} = \text{ld}\cdot\text{sizeof(element)},
$$
is friendly to 128‑byte grouping. In practice FA‑3 pads $\text{ld}$ to the next multiple of 16 (elements) for FP8 so that $\text{ld\_bytes}$ is a multiple of 16 bytes; then LDSM/STSMs that implement the transpose naturally map to 128‑byte units. If you observe bank conflicts in profiling, insert a small extra pad (a few elements) in $\text{ld}$ to break power‑of‑two aliasing patterns; a 1–2 element pad per row is a cheap fix and commonly used.

5) Match register accumulator layout to SMEM writes. FA‑3 performs a small byte‑permute on the FP32 accumulator layout produced by the first WGMMA so it matches the layout expected by the second WGMMA, and arranges the in‑kernel transpose to produce a matching row/column permutation of $V_j$ in SMEM. The paper gives the register permutation pattern repeated every 8 bytes (for example the order {d0 d1 d4 d5 d2 d3 d6 d7}), and uses STSM writes that map to that permutation. If you cannot afford that, you will pay with additional shuffles or suboptimal WGMMA invocation.

A short example to make it concrete: for FP8 with head dim $d=128$ you would set $\text{ld}=128$ (already a multiple of 16), choose $B_c$ that is a multiple of 8 (e.g. 256), arrange the SMEM tile base to be 128‑byte aligned, and transpose each $V_j$ in SMEM using LDSM/STSM so that subsequent WGMMA calls see k‑major $V_j$. That layout requires no tail handling for LDSM and keeps TMA/LDSM transfers naturally coalesced.

Summary: enforce 128‑byte alignment for all TMA/LDSM transfers, tile sizes that are integer multiples of the $8\times 8$ 16‑bit LDSM block (so $B_c\%8=0$, and for FP8 prefer $d\%16=0$), pad the SMEM leading dimension to those multiples ($\mathrm{round\_up}(d,16)$), transpose $V_j$ into k‑major SMEM using LDSM/STSM, and add small per‑row padding if profiling shows bank conflicts. Following these simple rules is what FA‑3 used to hit peak TMA/LDSM bandwidth and to avoid expensive bank/warp shuffles.
