# FlashAttention-3 in Plain English: How Attention Got 2x Faster on H100

## TL;DR
Attention is the costly inner loop of Transformers: it computes
$\mathbf{S}=\alpha\mathbf{Q}\mathbf{K}^\top$, $\mathbf{P}=\mathrm{softmax}(\mathbf{S})$, and $\mathbf{O}=\mathbf{P}\mathbf{V}$.
FlashAttention-3 is a hardware-aware rework of exact (not approximate) attention that leverages two forms of asynchrony on NVIDIA Hopper (H100) plus careful FP8 techniques. The result: about 1.5–2.0× faster than FlashAttention-2 in typical FP16 runs (forward), up to 740 TFLOPs/s (≈75% of H100 FP16 matmul peak), and FP8 paths that approach 1.2 PFLOPs/s while cutting FP8 quantization error by about 2.6× versus simple per-tensor FP8.

Below I unpack the three big ideas and the practical trade‑offs.

## What actually slows attention (short)
There are two main pain points.

1. Memory traffic from materializing the $N\times N$ score and probability matrices ($\mathbf{S},\mathbf{P}$) to global memory (HBM). Reading/writing these big intermediates kills performance and bandwidth.
2. An extreme mismatch between very fast matrix multiply hardware (Tensor Cores) and relatively slow scalar/special-function work (softmax needs exponentials and reductions). On H100 this is dramatic: FP16 matmul capacity is on the order of hundreds of TFLOPs, while special functions (exponentials used in softmax) have only a few TFLOPs of effective throughput. That imbalance means softmax can become a scheduling bottleneck unless you overlap it with matmuls.

FlashAttention-1/2 removed global-memory intermediates by fusing attention into a single kernel and using shared memory. But they mostly used a synchronous model: load a tile, compute a block of $\mathbf{S}$, finish softmax work, then do the next matmul. This leaves Tensor Cores underutilized on Hopper.

## The three ideas in FlashAttention-3 (high level)
FlashAttention-3 pushes further by redesigning the kernel to exploit hardware asynchrony and Hopper FP8 abilities. The three core ideas are:

- Warp-specialized producer/consumer asynchrony: split warps into producers (doing memory loads/transposes) and consumers (doing Tensor‑Core GEMMs) and use a circular shared‑memory buffer so loads and compute can proceed concurrently.
- Overlap softmax with GEMMs ("hide softmax under matmul"): interleave block-wise matmul and softmax so the Tensor Cores stay busy while slower softmax operations run on other units. This is implemented as a pipelined (2-stage, optionally 3-stage) loop across tiles.
- Use FP8 Tensor Cores safely: adapt layouts and add accuracy tricks (block quantization + incoherent processing) so FP8 GEMMs give huge throughput gains without catastrophic numeric loss.

I unpack each below.

## 1) Warp-specialization and asynchronous producer–consumer
Two hardware facts on Hopper matter:

- Tensor Memory Accelerator (TMA) can copy between HBM and shared memory asynchronously.
- The Hopper warpgroup GEMM instruction (WGMMA) is asynchronous and can source inputs straight from shared memory.

FlashAttention-3 assigns different warps (or warpgroups) in a CTA to distinct roles:

- Producers: issue TMA loads of tiles of $\mathbf{Q},\mathbf{K},\mathbf{V}$ into a circular, multi-stage shared-memory buffer. Producers can also perform in-kernel transposes when needed (see FP8).
- Consumers: run the heavy WGMMA GEMMs on the tiles already staged in shared memory.

A small synchronization protocol (barriers and buffer-stage bookkeeping) guarantees correctness. Because TMA and WGMMA are asynchronous, producers can keep loading upcoming tiles while consumers compute on currently available tiles. On top of this the implementation uses Hopper-specific features such as dynamic register reallocation (\texttt{setmaxnreg}) to give compute warps more register file if needed.

The result: memory traffic and compute are overlapped, and overall latency-to-throughput is reduced compared to a single-threaded synchronous kernel.

## 2) Hiding softmax under GEMMs via intra-warpgroup pipelining
Softmax is composed of reductions, exponentials and scaling — all relatively slow compared to Tensor Core matmuls. FlashAttention-3 breaks the strict per‑tile dependency chain by pipelining across tiles.

A simplified view of the 2-stage pipeline (consumer side):
- Iteration j computes the next score tile $S_{\mathrm{next}} = Q_i K_j^\top$ via an asynchronous WGMMA and does not wait for it to finish.
- While that WGMMA executes, the warp uses a second WGMMA to perform the $P_{\mathrm{cur}}V_{j-1}$ update (the RS-GEMM) from the previous iteration.
- After the first WGMMA completes, the code runs the softmax reduction for $S_{\mathrm{next}}$ (these scalar/special-function ops use other functional units), then uses another asynchronous WGMMA to start the next output update, and so on.

By ping‑ponging these roles among warpgroups (so one warpgroup does softmax while another is doing its GEMMs), the implementation keeps Tensor Cores busy during softmax work. In one reported case this combined optimization raised FP16 forward throughput from about 570 TFLOPs to 620–661 TFLOPs (head dim 128, long sequence), a substantial utilization improvement.

A few practical caveats:
- The compiler may reorder instructions; the implementation must force the intended waits/commits to ensure the pipelined schedule.
- The pipeline needs extra registers to hold intermediate tiles (e.g., $S_{\mathrm{next}}$) — register pressure limits how deep you can pipeline or how big your tiles can be. A 3-stage variant exists but uses still more registers and needs careful tradeoffs.

## 3) FP8 Tensor Cores — layout fixes + accuracy tricks
FP8 on Hopper delivers roughly 2× matmul throughput versus FP16, but two engineering problems arise for attention:

1. Layout constraints. FP8 WGMMA on Hopper requires input operand tiles in a k-major format (contiguous in the inner GEMM dimension). In attention the usual layout for $\mathbf{V}$ (and tiles loaded by TMA) is contiguous along the head dimension, not the k-major shape expected by FP8 WGMMAs. Also, the FP32 accumulator layout produced by an FP8 WGMMA differs in register ordering from the operand format the next WGMMA expects. FlashAttention-3 solves this without extra global-memory transposes by:
   - Doing an in-kernel tile transpose after the TMA load using LDSM/STSM-style warpwise copies (these instructions can copy and transpose tile‑width data with low register overhead). Because FP8 elements are 8-bit, they are packed and moved carefully (e.g., two 8-bit values per 16-bit lane) and a few register shuffles are used between LDSM and STSM.
   - Applying byte-permute register operations to rearrange the FP32 accumulator from the previous WGMMA into the layout expected by the next WGMMA. The in-kernel transpose of the $\mathbf{V}$ tile is coordinated to match the column/row permutations caused by these register permutes, avoiding heavyweight thread shuffles.

2. Quantization error. FP8 (e4m3) has limited mantissa/exponent range, and large outlier activations in LLMs make simple per-tensor scaling fail. FlashAttention-3 combines two practical fixes:
   - Block quantization: instead of a single scale per tensor, quantize each tile/block (the same tiles the algorithm already processes) with its own scale. This reduces quantization dynamic-range loss and can be fused with an earlier operation (e.g., rotary embedding) so it costs essentially nothing extra in a typical pipeline.
   - Incoherent processing: pre-multiply $\mathbf{Q}$ and $\mathbf{K}$ by a cheap random orthogonal transform $\mathbf{M}$ (so replace $Q\leftarrow Q\mathbf{M}$ and $K\leftarrow K\mathbf{M}$). Because $\mathbf{M}$ is orthogonal, $QK^\top$ is unchanged, but the entries are randomized sums of coordinates which spreads out outliers and reduces quantization error. Practically, $\mathbf{M}$ is implemented as a product of random diagonal $\pm 1$ matrices and a Hadamard matrix, so the transform costs $O(d\log d)$ and can be fused into existing token-level preprocessors (again, often at negligible extra cost).

Together these layout and accuracy techniques make FP8 practical for attention while reaping large throughput gains.

## Empirical highlights (H100 SXM5)
Benchmarks in the paper were run on H100 (80GB SXM5) with these canonical settings: sequence lengths from 512 up to 16k, total tokens per batch tuned to 16k, hidden dim 2048, and head dims 64/128/256.

- FP16 forward: FlashAttention-3 is about 1.5–2.0× faster than FlashAttention-2; peak measured throughput up to 740 TFLOPs/s (~75% utilization).
- FP16 backward: about 1.5–1.75× faster than FlashAttention-2.
- FP8 forward: approaches 1.2 PFLOPs/s in favorable cases (headdim-dependent).
- Versus a standard (materialize-to-HBM) attention: FlashAttention-3 can be roughly 3–16× faster depending on sequence length and head size.
- For medium/long sequences, FlashAttention-3 even beats a vendor-optimized cuDNN attention implementation in some cases.
- Ablation (one reported point): enabling the 2-stage WGMMA-softmax pipelining and warp-specialization increased throughput from 570 → 661 TFLOPs (same configuration: batch 4, seqlen 8448, 16 heads, headdim 128).

## Numerical accuracy and FP8 validation
To stress quantization, the authors injected outlier-like activations sampled as
$\mathcal{N}(0,1) + \mathcal{N}(0,100)\cdot\mathrm{Bernoulli}(0.001)$ (so 0.1% of entries get a large extra term). With this test distribution:

- FP16 FlashAttention-3 has the same numerical error as FlashAttention-2 and about 1.7× lower RMSE than the standard attention implementation because temporary softmax rescalings are kept in FP32.
- The FP8 baseline using per-tensor scaling suffers significantly. FlashAttention-3 with block quantization + incoherent processing reduces FP8 RMSE by about 2.6× compared to that baseline, making FP8 a more practical option.

## Practical trade-offs and limitations
- Complexity: FlashAttention-3 is a more complex kernel. It requires careful synchronization, register budgeting, and use of Hopper-specific primitives (TMA, WGMMA, LDSM/STSM, setmaxnreg). That makes implementation and debugging more involved than simple synchronous kernels.
- Register pressure: deeper pipelining and larger tiles both demand registers; you must trade tile size vs pipeline depth.
- FP8 caveats: the FP8 path in the open-source implementation was not yet a persistent kernel with full load balancing in the reported benchmarks, so for small sequences and causal masks FP8 might not outperform tuned FP8 cuDNN kernels. The FP16 path had a persistent kernel and load balancing in the reported experiments.
- Generality: the techniques rely on asynchronous memory/compute units and low-precision Tensor Cores; the ideas transfer to other accelerators with similar hardware features, but implementation details will vary.

## Takeaways
If you care about long-context Transformers or just want attention to stop being the bottleneck, FlashAttention-3 shows that rethinking the kernel around the actual hardware capabilities pays off. The three practical levers are:

- Overlap data movement and compute aggressively (producer/consumer warp specialization + circular shared buffer).
- Overlap the slow softmax work with matmuls by pipelining across tiles and ping-pong scheduling among warpgroups.
- When using FP8 Tensor Cores, mind layouts and quantization: do in-kernel transposes, fix register layouts with byte permutes, and reduce FP8 error with block scaling and incoherent transforms (Hadamard + sign diagonals).

The code is open-sourced (see the FlashAttention-3 repo), and the authors plan integration with PyTorch/Hugging Face tooling so these gains become practical for model training and long-context inference.

If you want a deeper dive into the implementation details (buffer staging, exact pipelined wait/commit ordering, or the FP8 register permutations), the paper contains CTA-level pseudocode and implementation notes for the Hopper WGMMA/TMA primitives.



# Producer-Consumer on the GPU: The Warp Specialization Trick Behind FlashAttention-3

## TL;DR
FlashAttention-3 speeds up Transformer attention on Hopper GPUs by splitting work inside a threadblock: some warps become producers (they move data into shared memory), and other warps become consumers (they run the Tensor Cores). Because Hopper exposes asynchronous DMA (TMA) and asynchronous Tensor Core GEMMs (WGMMA), producers and consumers can run concurrently and hide memory and instruction latencies. The implementation uses a small circular shared-memory buffer, ping-pong scheduling across warpgroups, and dynamic register reallocation (via setmaxnreg) to keep the GPU fed. The result: 1.5–2× speedup over FlashAttention-2 on H100 in FP16 (up to 740 TFLOPs/s, ~75% device TFLOP utilization) and very large gains when moving GEMMs to FP8. This post explains the core idea and practical trade-offs.

## The problem in one formula
Attention for one head is:
"S = \alpha Q K^\top,\quad P=\mathrm{softmax}(S),\quad O = P V"
with Q, K, V in \mathbb{R}^{N\times d}. The inner loops multiply blocks of Q and K to form score blocks, run a numerically stable local softmax, and then multiply the resulting probabilities with blocks of V. On modern GPUs the bottleneck is both compute and memory movement; naive implementations read/write large intermediate matrices to global memory.

FlashAttention fused these steps to avoid global-memory intermediates, but FlashAttention-2 still left a lot of Hopper performance on the table (reported ~35% utilization) because it treated loads and matmuls more synchronously and did not exploit new Hopper capabilities.

## What Hopper gives you (that FlashAttention-3 uses)
- TMA (Tensor Memory Accelerator): an asynchronous unit that copies tiles between global memory (HBM) and shared memory (SMEM) without stalling warps.
- WGMMA: a warpgroup-wide Tensor Core GEMM that is asynchronous on Hopper — it can be issued and run in the background while other instructions run on CUDA cores.
- setmaxnreg: a way to change register allocation across warpgroups inside a CTA so warps that do heavy compute can get more registers than those that only need to move data.
- Fast but narrow special-function units (for exponentials, etc.) whose throughput is tiny compared to Tensor Core matmul throughput.

Those asynchronous units are what make true producer-consumer parallelism possible inside a single kernel.

## Warp specialization: producers vs consumers
Instead of letting every warp do both data movement and compute, FlashAttention-3 divides the warps in a CTA into two roles:

- Producer warps: issue TMA loads from global memory into designated stages of a circular SMEM buffer (and for FP8, they can run LDSM/STSM-based in-kernel transposes). Producers intentionally free up most registers because they don't need many.
- Consumer warps: wait for those SMEM tiles and run WGMMA GEMMs, compute the local softmax update for their query block, and run the RS-GEMM that multiplies blockwise probabilities with V. Consumers get more registers allocated so they can hold intermediate tiles and schedule WGMMA efficiently.

Communication between producers and consumers is lightweight: a producer "commits" a loaded stage of the circular buffer to notify consumers, and consumers "release" a stage when done so the producer can reuse it. The circular buffer has s stages; this decouples producer and consumer pacing and prevents backpressure from stalling the whole CTA.

Why this helps: TMA and WGMMA run on dedicated hardware asynchronously. If a single warp alternated loads then matmuls synchronously, the Tensor Cores would sit idle while waiting for data or while the special-function units do exponentials. By splitting roles, producers keep the SMEM filled while consumers keep issuing GEMMs, so the large Tensor Core throughput is better utilized.

## Ping-pong scheduling across warpgroups
FlashAttention-3 arranges warps into warpgroups and uses a ping-pong schedule so that the low-throughput softmax computations are executed while another warpgroup’s Tensor Cores are busy on GEMMs. Concretely:

- Barrier instructions (bar.sync) are used to force a schedule where GEMMs of warpgroup A are issued before GEMMs of warpgroup B.
- While warpgroup A's Tensor Cores execute its GEMMs, warpgroup B can be computing exponentials and other softmax operations using the multi-function unit.
- Then roles swap: A computes its softmax while B's Tensor Cores run GEMMs.

This overlapping is important because special functions (exponentials) are much slower in aggregate throughput than matmul: on H100 the matmul TFLOPS budget is orders of magnitude larger than special-function throughput. Without overlapping, the softmax work would become a bottleneck.

## Intra-warpgroup pipelining: the 2-stage GEMM–softmax pipeline
FlashAttention-3 also pipelines work inside a consumer warpgroup so that in one iteration the GEMM for the next key block is launched before the softmax-driven RS-GEMM from the current block finishes. Simplified, the per-block ordering looks like this:

1. Start with S_cur = Q_i K_0^\top (WGMMA issued and waited).
2. Compute local max m_i, scaled exponentials \tilde{P}_{cur}, update running normalizer \ell_i and rescale O_i.
3. For j = 1..T_c-2:
   - Issue S_next = Q_i K_j^\top with WGMMA and do not wait for it to complete.
   - Issue (asynchronously) O_i += \tilde{P}_{cur} V_{j-1} (RS-GEMM).
   - Wait for S_next to complete, compute the softmax pieces for S_next (m_i, \tilde{P}_{next}, update \ell_i).
   - Wait for the RS-GEMM to complete and rescale O_i as needed.
   - Move S_next → S_cur, \tilde{P}_{next} → \tilde{P}_{cur}, continue.

By issuing one WGMMA for the next score-block and one for the current RS-GEMM concurrently, the softmax arithmetic (exponentials, row sums, rescaling) for the next block can be scheduled to execute while a costly GEMM runs. The overlap hides the small special-function throughput behind the large Tensor Core throughput.

Trade-off: the 2-stage pipeline needs extra registers (to hold S_next etc.). A 3-stage pipeline is possible but requires even more registers and complicates block sizing.

## Dynamic register allocation: give the compute warps what they need
Because producers do mostly TMA loads and small bookkeeping, they can run with very few registers. Consumers need more registers for WGMMA accumulators and temporaries. FlashAttention-3 uses Hopper’s setmaxnreg to allocate registers differently across warpgroups inside the same CTA: producers release registers, consumers expand their register allotment. This reduces register pressure for consumers and improves occupancy and kernel efficiency.

Important practical point: the pipeline and larger block sizes both increase register usage; the implementation must balance tile sizes, pipeline depth, and occupancy.

## How the circular shared-memory buffer coordinates work
A small s-stage ring buffer in SMEM holds blocks of K and V (and Q for the tile being processed). Producers load blocks into stage (j % s), commit that stage, and continue loading the next blocks. Consumers wait for the expected stage to be available, consume it (running GEMMs and softmax), and then release the stage back to producers. Because loads are asynchronous, the producer can be several blocks ahead; because GEMMs are asynchronous, the consumer can have several GEMMs in flight. The small buffer plus the commit/notify protocol is what turns independent asynchronous DMA and compute into a robust producer-consumer pipeline.

## FP8-specific notes (brief)
When running the GEMMs on FP8 Tensor Cores, FlashAttention-3 needs to handle layout constraints: FP8 WGMMA requires operands to be k-major in SMEM. The implementation does an in-kernel transpose of V tiles using LDSM/STSM intrinsics (warp-level register <-> SMEM moves) and uses byte-permute register instructions to reorder FP32 accumulators into a layout consumable by the next WGMMA. These layout fixes are done in the producer warpgroup shadowed behind GEMMs so they don't add global synchronization stalls.

Numerically, FP8 is fragile due to limited mantissa and exponent range and model outliers. FlashAttention-3 combats this with block quantization (one scale per block rather than one per tensor) and incoherent processing (multiplying Q and K by a random orthogonal transform that spreads out outliers, implemented as cheap Hadamard/±1 diagonal factors). In the paper these techniques reduced FP8 numerical error by about 2.6× compared to naive per-tensor FP8.

## Practical results and trade-offs
- Measured speedups: FP16 forward pass achieves ~1.5–2× speedup over FlashAttention-2 on H100; FP16 peaks near 740 TFLOPs/s (≈75% of theoretical). FP8 reaches close to 1.2 PFLOPs/s in the best cases.
- For medium and long sequences (≥1k tokens), FlashAttention-3 can outpace a vendor-optimized cuDNN attention for FP16.
- Costs/trade-offs:
  - Compiler reordering can disturb the delicate issue/wait ordering; careful SASS-level inspection and constraints are required.
  - Register pressure grows with pipeline stages and block sizes; tuning is required per hardware and problem size.
  - FP8 kernels in the presented implementation are not persistent kernels and therefore can be less competitive on small sequences or with causal masking compared to highly tuned vendor kernels.
  - A persistent-kernel design and more tuning could further improve FP8 performance.

## Takeaways
Warp specialization (producer warps that only move data and consumer warps that only compute) turns Hopper's asynchronous DMA and asynchronous Tensor Cores from isolated hardware features into a coordinated pipeline. The tiny circular SMEM buffer plus commit/notify semantics and ping-pong scheduling across warpgroups let FlashAttention-3 keep the Tensor Cores busy while hiding slow softmax and memory work. The result is a practical speedup on real H100 hardware and a template: when hardware exposes independent asynchronous engines, rethinking the kernel as a producer-consumer pipeline — and explicitly specializing warps — is a powerful lever.

If you want to dig deeper, the FlashAttention-3 paper lays out the CTA-level algorithms, the 2- and 3-stage pipelined variants, FP8 layout fixes, and the numerical-validation experiments that back the performance and accuracy claims.



# Hiding Softmax Latency: The Overlap That Makes FlashAttention-3 Fly

## Motivation — why softmax kills utilization

Attention is dominated by matrix multiplies, but it also needs softmax: compute
S = α Q K^\top, P = softmax(S), O = P V. On modern GPUs these two pieces live on very different execution units. Tensor Cores (via WGMMA) chew through the dense GEMMs at extremely high throughput, while softmax needs exponentials and reductions executed on the GPU's multi-function / special-function units, which are orders of magnitude slower.

On the H100 the paper cites roughly 989 TFLOPs of FP16 matmul vs. only about 3.9 TFLOPs available for special functions like exp. For a typical head size (headdim = 128) the math ends up with far more matmul FLOPs than exponentials, yet the exponential units are so slow that softmax can take a surprisingly large fraction of the wall‑clock time if scheduled sequentially. The upshot: if you run GEMMs then softmax then another GEMM, a cheap-but-slow softmax step can leave Tensor Cores idle and overall utilization low.

FlashAttention-3 fixes this by exploiting asynchrony in the hardware to schedule work so the slow softmax runs “in the gaps” while Tensor Cores are busy.

## The key idea — a two-stage overlapping pipeline

FlashAttention-3 tiles attention over blocks of keys/values and works block-by-block. For a fixed query block Q_i and key/value blocks K_j,V_j, the classic tight loop looks like:

1. compute S^{(j)} = Q_i K_j^\top (GEMM on Tensor Cores)
2. softmax over the S block to produce a block of P
3. compute O_i += P^{(j)} V_j (another GEMM)

Those three steps are logically dependent and typically executed serially. The two-stage pipeline breaks that strict ordering by pipelining across iterations: while the Tensor Cores compute the next QK^\top, the special-function units compute softmax for the previous or current block, and another GEMM that consumes the already-computed P runs concurrently as well. Concretely, each consumer warpgroup runs roughly the following pattern (described at a high level):

- Prime: compute S_cur = Q_i K_0^\top (WGMMA).
- Compute its softmax block and apply it to O_i (initial rescale).
- For each subsequent block j:
  - Issue an asynchronous WGMMA for S_next = Q_i K_j^\top (commit but do not wait).
  - Issue an asynchronous WGMMA for O_i += \tilde P_cur V_{j-1} (commit but do not wait).
  - Wait for the S_next WGMMA to finish; compute softmax on S_next (this uses the special‑function units).
  - Wait for the O-update WGMMA to finish; rescale/accumulate O_i.
  - Roll S_next → S_cur and continue.

Two things make this possible: (1) the WGMMA instruction is asynchronous on Hopper and can be issued and left running while the warp executes other work; (2) the softmax-heavy work (exp + reductions) executes on different functional units than the Tensor Cores. By carefully issuing the next QK^\top and the current P V GEMMs without blocking, the kernel keeps Tensor Cores busy while the softmax runs on the slow functional units — instead of leaving the Tensor Cores idle.

The algorithm also relies on the FlashAttention idea of local (blockwise) softmax — keeping running normalization variables so we never materialize full S or P matrices to global memory. That lets softmax be computed incrementally and interleaved with GEMMs.

## Why overlapping helps (numbers make it convincing)

This is not just clever scheduling — it matches hardware realities. The paper reports:

- H100 FP16 matmul throughput ≈ 989 TFLOPs, while special-function throughput (exp/etc.) ≈ 3.9 TFLOPs.
- For headdim = 128 the matmul FLOPs per block far exceed the exponentials needed, but the exp units are so slow that if softmax runs serially it can occupy ~50% of cycles versus the matmul. With FP8 (matmul throughput doubles) the imbalance gets worse.

By overlapping, FlashAttention-3 reclaims cycles that would otherwise be wasted waiting for exp and reductions. In practice the authors report concrete gains: a ping-pong inter-warpgroup schedule (overlapping softmax across warpgroups) improved a 128‑headdim forward run from about 570 TFLOPs to roughly 620–640 TFLOPs, and the full 2-stage intra-warpgroup pipeline plus warp-specialization raised performance further (an ablation example goes from 570 to 661 TFLOPs). Overall, FlashAttention-3 reaches up to ≈740 TFLOPs/s in FP16 (about 75% utilization) and, with FP8, approaches ≈1.2 PFLOPs/s.

## How warp-specialization and “ping‑pong” fit in

There are two concurrency axes at play:

- Asynchrony inside a warpgroup: WGMMA is asynchronous, so a warpgroup can issue it and go do softmax/other work. The two‑stage pipeline described above is intra-warpgroup.
- Warpgroup-level ping‑pong: the CTA's warps are split into producer warpgroups (doing TMA loads, in-kernel transposes) and consumer warpgroups (doing WGMMA + softmax). Two consumer warpgroups can “ping‑pong”: while one is doing GEMMs, the other performs softmax, then they swap. The kernel uses barrier synchronizations to enforce an ordering that makes this inter-warpgroup overlap possible.

Warp-specialization also enables register reallocation (via setmaxnreg) so the warps that do heavy Tensor Core work can get more registers, while the warps issuing TMA need far fewer registers. TMA (asynchronous memory copies) is used to hide loads of K and V tiles into shared memory, adding another layer of overlap.

## Trade-offs and practical pitfalls

The overlapping pipeline is powerful, but not free:

- Register pressure. The 2-stage design requires keeping S_next (a block of scores) in registers while other work proceeds, which increases register usage. That limits how large block sizes can be and can force trade-offs between tile size and pipeline depth. Extending to a 3‑stage pipeline is possible but consumes even more registers.
- Compiler reordering. The C++/PTX compiler may reorder instructions for optimization. The algorithm depends on issuing WGMMA and then doing softmax without accidental reordering; the authors analyze the generated SASS to ensure the intended overlapped ordering appears in practice.
- Complexity for low-precision (FP8). Using FP8 Tensor Cores requires operand layouts to be k-major, so FlashAttention-3 adds in-kernel transposes (LDSM/STSM) and byte permutations to align accumulator and operand register layouts. Those details complicate the kernel but are handled in the implementation.
- Varying benefit by shape. For small sequence lengths or very small tiles the overheads may dominate and the overlap yields smaller gains. FP8 also needs careful block quantization and incoherent processing to control numeric error.

## Practical impact — what you get

By using the two-stage pipeline plus warp-specialization and asynchronous loads, FlashAttention-3 turns softmax from a utilization sink into something that can be hidden under matmuls. The result is a sizable utilization win: 1.5–2.0× speedups over FlashAttention-2 on many workloads, forward-pass performance up to ~740 TFLOPs/s in FP16 on H100, and even higher peak with FP8 when accuracy tricks (block quantization + incoherent processing) are used to control numerical error.

## Takeaway

Softmax is slow, but it doesn’t have to be on the critical path. On hardware where GEMMs and special functions are implemented in separate asynchronous units, the right scheduling can keep Tensor Cores busy while the slow softmax runs elsewhere. FlashAttention-3 shows that a disciplined two-stage pipeline (issue next QK^\top early, issue PV early, do softmax in the gaps) plus warp‑specialization and careful register management produces large real-world speedups — at the cost of more complex kernels and tighter register/tile trade-offs. If you care about long‑context attention and real GPU throughput, overlapping softmax under GEMMs is the single implementation trick that unlocks a lot of value.



# FP8 Without the Fear: Block Quantization and Incoherent Processing Explained

FP8 delivers an attractive doubling of GEMM throughput on modern GPUs, but its small mantissa and coarse quantization make it fragile when activations contain outliers — exactly the situation often seen in large language models. FlashAttention-3 shows a practical way to keep the FP8 speedups while substantially reducing the numerical damage: two lightweight, compatible guards called block quantization and incoherent processing. Together they cut FP8 attention error by 2.6× versus a standard per-tensor FP8 baseline (in experiments with synthetic outliers), and they can be fused into the attention pipeline with negligible extra cost.

## Why FP8 is tricky for attention

FP8 (e4m3) packs just 3 bits for the mantissa and 4 bits for the exponent. That gives you a reasonable dynamic range but a very coarse step size for nearby values. A common strategy is per-tensor quantization: compute a single scale for an entire tensor, divide by that scale, round to the FP8 format, and run the low-precision GEMMs. Per-tensor scaling works well when values are fairly homogeneous, but it breaks down when a few entries are much larger than the rest.

Large models frequently have such outliers. If a single extreme value drives the per-tensor scale, the rest of the tensor is effectively quantized with a much coarser resolution — small-but-important differences disappear, dot products become noisy, and the softmax in attention amplifies the resulting errors.

## Guard 1 — Block quantization: scale where it makes sense

Block quantization replaces a single global scale with one scale per block. In FlashAttention-3 the attention computation is already block-structured (it processes tiles of size like $B_r \times d$ or $B_c \times d$), so block quantization simply computes and stores one scalar scale per block and quantizes that block independently.

Why this helps: outliers tend to be localized. A block that contains an outlier will get a correspondingly large scale, but other blocks that are well-behaved keep much finer resolution. Block quantization therefore reduces the effective quantization noise for the majority of entries.

Two practical details from FlashAttention-3:

- The blocks used for quantization are the same blocks that the attention kernel naturally processes, so quantization can be fused into the preprocessing step (for example, fused with rotary embeddings) with no extra memory-bandwidth pass.
- The algorithm folds block scales into the per-block computations: when you quantize $Q$ and $K$ blocks with their respective scales, the blockwise dot products can be rescaled appropriately without adding extra GEMMs, so there is no meaningful extra runtime cost for applying the per-block scaling.

## Guard 2 — Incoherent processing: spread out the outliers

Block quantization helps when outliers are localized, but what if an outlier is extremely concentrated in a single dimension and that pattern repeats across many blocks? Incoherent processing addresses that by randomly mixing the coordinates before quantization.

Concretely, FlashAttention-3 multiplies $Q$ and $K$ (the operands of the attention dot-product) by a random orthogonal matrix $M$ before quantizing:

- Because $M$ is orthogonal ($M M^\top = I$), the attention kernel is invariant:
  $$(Q M)(K M)^\top = Q K^\top.$$
- The multiplication by $M$ spreads any coordinate-level outlier across many dimensions, reducing the peak-to-average ratio inside each block and making quantization less destructive.

To keep this cheap, FlashAttention-3 follows recent work and chooses $M$ as a product of cheap transforms: random diagonal sign matrices and a Hadamard matrix. This permits a fast $O(d \log d)$ implementation (a fast Walsh–Hadamard transform) and, importantly, can be fused with other per-token preprocessing operations (again, e.g., rotary embeddings), so the incoherent transform adds essentially no extra runtime in practice.

## Putting them together in FlashAttention-3

The two techniques are complementary:

- Incoherent processing makes the per-block statistics more uniform by mixing dimensions, so block quantization can use tighter scales for most blocks.
- Block quantization captures residual local dynamic range differences after incoherence, preventing a single bad block from dominating the whole tensor’s scale.

Implementation highlights from FlashAttention-3 (kept intentionally short and practical):

- Quantize blocks of $Q$, $K$, and $V$ to FP8 with one scale per block (block sizes match the kernel tiling).
- If using incoherent processing, first compute $Q' = Q M$ and $K' = K M$ using the fast Hadamard + sign-flip trick; then quantize $Q'$ and $K'$ blockwise.
- The attention kernel accepts these FP8 blocks and applies the block scales in-place so the final $S$ and downstream computations see correctly scaled values without extra GEMMs or global rescales.
- Both block quantization and incoherent processing are fused with existing preprocessing (e.g., rotary embeddings) in the FlashAttention-3 implementation, so the accuracy guards are low-overhead.

## Empirical effect

FlashAttention-3 evaluated FP8 attention against a baseline FP8 attention implementation that uses per-tensor scaling. To stress the system, inputs were sampled with synthetic outliers drawn from
$$\mathcal{N}(0,1) + \mathcal{N}(0,100)\cdot\mathrm{Bernoulli}(0.001)$$
(that is, 0.1% of entries have a large extra term). Under that distribution, FP8 FlashAttention-3 with block quantization plus incoherent processing produced 2.6× lower numerical error (RMSE against an FP64 reference) than the baseline per-tensor FP8 approach.

Crucially, these accuracy gains come while retaining the FP8 throughput benefits of FlashAttention-3: the paper reports FP8 performance reaching close to 1.2 PFLOPs/s on H100 hardware. In short, the two guards give you much of the numeric stability advantage of higher precision, without sacrificing the main reason to choose FP8 — the dramatic speedups on modern tensor cores.

## Practical notes and caveats

- Block quantization and incoherent processing are designed to be low-cost in real systems: both can be fused with the preprocessing stage (e.g., rotary embedding), and the per-block scales are tiny metadata compared to the tensors themselves.
- The method in the paper focuses on the forward pass and on attention kernels optimized for Hopper-style GPUs (H100). FlashAttention-3’s FP16 kernels include persistent-kernel optimizations; the FP8 kernels in the paper do not yet include the same persistent-kernel load balancing, which can make FP8 less favorable for some small-sequence or causal-mask cases relative to vendor kernels. That is an orthogonal implementation detail that does not change the quantitative benefit of block quantization and incoherent processing for accuracy.
- The paper observes lower numerical error for FP16 FlashAttention-3 as well (because intermediate softmax rescaling is kept in FP32), but when you specifically want FP8 throughput, the two guards above are the practical path to making FP8 usable in the presence of outliers.

## Takeaway

FP8 can be fast and usable if you neutralize the effect of outliers and narrow dynamic-range variation. Block quantization (one scale per processing block) and incoherent processing (a cheap orthogonal random mixing via Hadamard and sign flips) are two complementary, low-overhead techniques that FlashAttention-3 uses to do exactly that. They reduce FP8 attention error by about 2.6× versus a naive per-tensor FP8 baseline in the outlier regime, while preserving the large FP8 throughput gains on modern GPUs.



# Taming Tensor Core Layouts: Transposes and Byte Permutes for FP8 Speed

Modern Hopper GPUs give you huge raw throughput for FP8 matrix-multiply (WGMMA) — roughly 2× the Tensor‑Core matmul throughput versus FP16/BF16 — but they also come with a strict requirement: the FP8 WGMMA expects its inputs laid out in a particular way in shared memory. For attention kernels that do back‑to‑back GEMMs (e.g., computing $\mathbf{S}=\mathbf{Q}\mathbf{K}^\top$ then $\mathbf{O}=\mathbf{P}\mathbf{V}$), that layout requirement creates a practical bottleneck: either pay the price of expensive global‑memory transposes, or redesign your kernel to rearrange data and registers in‑flight. FlashAttention‑3 chooses the latter. This post unpacks the problem and the two small but crucial tricks the paper uses to avoid extra bandwidth: (1) in‑kernel shared‑memory transposes using ldmatrix/stmatrix, and (2) small byte‑level register permutations to reconcile accumulator and operand layouts so you can chain FP8 WGMMA calls inside one kernel.

## The core constraint: k‑major vs mn‑major

For a GEMM expressed as \(A \times B^\top\) where \(A\) is \(M\times K\) and \(B\) is \(N\times K\), we can categorize how an operand is laid out in memory:

- mn‑major: the operand is contiguous along the outer dimension (the \(M\) or \(N\) axis).
- k‑major: the operand is contiguous along the inner \(K\) axis.

On Hopper, FP16 WGMMA accepts operands in either mn‑major or k‑major layouts in shared memory, but FP8 WGMMA only accepts k‑major. In other words, when you target the FP8 Tensor Cores, the data in SMEM must be contiguous along the GEMM’s inner dimension \(K\).

That sounds abstract until you look at how attention tiles are normally laid out.

## Why attention hits a layout snag

Attention uses three inputs per head: \(\mathbf{Q}, \mathbf{K}, \mathbf{V}\in\mathbb{R}^{N\times d}\) (sequence length \(N\), head dim \(d\)). Common tensor layouts put the head dimension \(d\) as the fastest‑changing (contiguous) stride in memory: entries are contiguous in the head dimension.

Consider the two GEMMs inside a tiled attention kernel:

1. Block GEMM: \(\mathbf{S}_{ij} = \mathbf{Q}_i \mathbf{K}_j^\top\), where \(\mathbf{Q}_i\) is \(B_r\times d\) and \(\mathbf{K}_j\) is \(B_c\times d\).
2. Block GEMM: \(\mathbf{O}_i \mathrel{+}= \widetilde{\mathbf{P}}_{ij} \mathbf{V}_j\), where \(\widetilde{\mathbf{P}}_{ij}\) is \(B_r\times B_c\) and \(\mathbf{V}_j\) is \(B_c\times d\).

For the second GEMM (the softmax output times the value block), the inner dimension \(K\) is \(B_c\) (the block over the sequence). The FP8 WGMMA requires the operand corresponding to that \(K\) axis to be k‑major in SMEM — i.e., the tile of \(\mathbf{V}_j\) must be contiguous in sequence length. But the input layout you usually get from upstream (and what a TMA load will preserve) is contiguous in the head dimension \(d\), not sequence length. TMA copies do not change the contiguous stride for you, so you cannot simply load a tile and satisfy FP8 WGMMA’s k‑major requirement without transposing.

A straightforward fix — rewriting or pre‑transposing \(\mathbf{V}\) in global memory — is costly. A global transpose is a memory‑bandwidth heavy operation that defeats the whole point of a fused, memory‑efficient attention kernel.

## The FlashAttention‑3 solution, in two parts

FlashAttention‑3 avoids global transposes and enables back‑to‑back FP8 WGMMAs by combining two lightweight transformations that run inside the kernel:

1. In‑kernel SMEM transposes using ldmatrix/stmatrix, performed in the producer warpgroup so the data that the consumer warpgroup sees is already k‑major for FP8 WGMMA.
2. Small byte‑level register permutations (byte permutes) that rewire the FP32 accumulator layout produced by the first WGMMA into the register layout expected by the next FP8 WGMMA operand, eliminating an extra write/read or heavyweight lane shuffles.

Below I unpack each of those.

### 1) In‑kernel transpose into the k‑major layout (no global transpose)

Instead of transforming \(\mathbf{V}\) in global memory, FlashAttention‑3 loads tiles with TMA (which preserves the original contiguous dimension), then performs a warp‑level tile transpose in SMEM so the tile is laid out contiguous along the sequence axis (k‑major) for the next FP8 WGMMA.

Key implementation points from the paper:

- The kernel uses the ldmatrix/stmatrix pair (written in PTX as ldmatrix/stmatrix or LDSM/STSM) to do warp‑level copies and transposes at tile granularity. These primitives operate on an \(8\times 8\) block of 16‑bit entries (128 bytes) and are register‑efficient.
- FP8 uses 8‑bit entries. To use ldmatrix/stmatrix you can pack two FP8 values into one 16‑bit word and then operate on these packed half‑words; the kernel unpacks/repacks appropriately.
- The transpose versions cannot split packed 8‑bit entries, so the implementation includes small register moves between the ldmatrix load and stmatrix store to realize the logical transpose of 8‑bit FP8 elements. (The paper omits the low‑level detail but notes this necessary step.)
- The transpose is done by the producer warpgroup and is cheap in registers; crucially, it can be overlapped with the consumer's WGMMAs, so the latency is hidden.

This approach avoids an expensive pre‑transpose in HBM and keeps data movement local (GMEM → SMEM via TMA, then SMEM tile transpose). Because the transpose is executed inside the kernel and scheduled carefully (producer/consumer warp‑specialization), it does not add measurable bandwidth cost for typical attention settings.

### 2) Byte permutes: reconcile FP32 accumulators with FP8 operand layout

There is another, subtler layout mismatch that arises when you try to chain WGMMAs: the FP8 WGMMA emits FP32 accumulators in registers using one lane/register ordering, but the next WGMMA (when treating those accumulators as an operand) expects a different register ordering (the operand layout encoding). In short, the register-level ordering of the first WGMMA’s FP32 accumulators is incompatible with the operand layout needed by the second WGMMA.

FlashAttention‑3 fixes this with tiny register permutations: a few byte‑level permute instructions are used to reorder the accumulator registers so that they correspond to the k‑major operand layout expected by the next WGMMA. The paper gives a concrete example of the permutation pattern used: the sequence of elements in a register chunk is rearranged from the natural order into an order like
\(\{d0, d1, d4, d5, d2, d3, d6, d7\}\), and that pattern is replicated every eight bytes. Effectively this permutes columns of a small \(\mathbf{P}\) tile so that the register contents can be consumed by the next WGMMA without additional inter‑thread shuffles or memory traffic.

Because the in‑kernel transpose that produced the V tile can control the row order it writes into SMEM, FlashAttention‑3 pairs the accumulator byte permute with a matching row permutation of the transposed \(\mathbf{V}\) tile. The two permutations are chosen to be compatible so no expensive cross‑lane register exchange is necessary; everything is local to the warp and handled with byte permutes and register moves.

## How it fits in the pipeline and why it’s fast

Putting the pieces together, the kernel does the following at tile granularity:

- Producer warpgroup: TMA loads \(\mathbf{V}_j\) (packed FP8) into SMEM in its original contiguous layout, then performs an in‑kernel transpose (ldmatrix/stmatrix + small reg moves) to write a k‑major tile into SMEM.
- Consumer warpgroup: issues an asynchronous FP8 WGMMA for \(\mathbf{Q}_i\mathbf{K}_j^\top\) (first GEMM), keeps the FP32 accumulators in registers, applies a small byte permutation to those registers so their ordering matches the operand layout for the next FGEMM, and then issues the FP8 WGMMA for \(\widetilde{\mathbf{P}}_{ij}\mathbf{V}_j\) (second GEMM) reading the already transposed \(\mathbf{V}_j\) from SMEM.
- Scheduling: the in‑kernel transpose for the next \(\mathbf{V}\) tile is executed while the current WGMMA operations are in flight, so its latency is hidden. Warp‑specialization and the Hopper Tensor Core/TMA asynchrony lets the kernel overlap the data movement, the ldmatrix/stmatrix transpose, softmax work, and WGMMAs.

The net effect: two back‑to‑back FP8 WGMMAs can be invoked inside a single fused kernel without falling back to global‑memory transposes or writing intermediate accumulators to HBM. That preserves the low memory–IO design goal of FlashAttention while allowing the algorithm to target the much higher FP8 Tensor‑Core throughput.

## Practical tips and caveats

- Packing: LDSM/STSM operate on 16‑bit entries, so you pack two FP8 values per half‑word and handle unpack/repacks across the warp. The transpose variants don’t split packed bytes, so you will need small register moves between ldmatrix and stmatrix to realize the logical byte transpose.
- Register pressure: storing an extra intermediate tile (e.g., \(\mathbf{S}_{\text{next}}\)) in registers for pipelining increases register usage. There’s a tradeoff between tile sizes and pipeline depth: larger tiles can improve GEMM efficiency but increase register pressure.
- Compiler reordering: the instruction scheduler can reorder non‑WGMMA and WGMMA instructions in surprising ways; the FlashAttention‑3 implementation checks generated SASS to ensure the intended overlap actually occurs.
- Portability: these techniques rely on Hopper features (WGMMA/TMA and ldmatrix/stmatrix semantics). The general idea — do SMEM transposes and register permutations instead of global transposes — is portable, but the exact instructions and constraints differ by architecture.
- Accuracy: enabling FP8 requires attention to quantization. FlashAttention‑3 couples these layout fixes with block quantization and incoherent processing (randomized orthogonal mixing) to reduce FP8 quantization error; the FP8 variant of FlashAttention‑3 is reported to be significantly more accurate than a naive per‑tensor FP8 baseline.

## Bottom line

FP8 Tensor Cores on Hopper are powerful but picky about how data is laid out. For attention kernels that want to fuse the inner two GEMMs and target FP8 throughput, the k‑major constraint forces you to either pay for global transposes or to do small, local transformations. FlashAttention‑3 shows that doing the work inside the kernel — a warp‑level transpose in SMEM (ldmatrix/stmatrix with packed FP8) plus a few byte‑permute register ops to reconcile accumulator vs operand layouts — lets you chain FP8 WGMMAs cleanly and without extra global‑memory bandwidth. The result is a fused FP8 attention kernel that runs at much higher TFLOPs and keeps the memory‑efficient philosophy of FlashAttention intact.



# Do the Numbers Back It Up? FlashAttention-3 vs FlashAttention-2, cuDNN, and Triton

## TL;DR
FlashAttention-3 (FA3) delivers the headline claims in the paper: on an NVIDIA H100 (Hopper) GPU it gives roughly 1.5–2.0× speedup over FlashAttention-2 (FA2) in FP16 forward (up to 740 TFLOPs/s, ~75% of H100 peak), and about 1.5–1.75× in the backward pass. With FP8 Tensor Cores enabled, FA3 reaches close to 1.2 PFLOPs/s. For medium and long sequences (≈1k tokens and above) FA3 is competitive with — and for many FP16 cases faster than — an H100-optimized cuDNN attention; compared to a standard attention implementation FA3 can be 3–16× faster. On accuracy, FP16 FA3 matches FA2 (and improves on a baseline standard attention) because softmax/rescaling is kept in higher precision; FP8 FA3 with block quantization + incoherent processing cuts FP8 error by about 2.6× vs. a per-tensor FP8 baseline in outlier settings.

## What they measured (short)
Benchmarks were run on an H100 80GB SXM5 GPU. Typical experimental setup in the paper:

- Sequence lengths swept from 512 up to 16k (batch size adjusted so total tokens ≈16k).
- Hidden dim = 2048; head dimensions tested = 64, 128, 256 (so 32, 16, 8 heads respectively).
- Forward FLOPs computed as $4 \cdot \text{seqlen}^2 \cdot \text{head\_dim} \cdot \text{nheads}$, halved for causal masking. Backward FLOPs multiplied by 2.5 (accounting for recomputation and additional matmuls).
- Comparisons included: a standard (HBM-materializing) attention implementation, FlashAttention-2 (PyTorch), FA2 implemented in Triton (H100-specific), and cuDNN’s H100-optimized attention.
- FP8 forward-pass timings were reported as well.

Numerical error was measured as RMSE against an FP64 reference on inputs sampled to simulate outliers: each entry drawn from $\mathcal{N}(0,1) + \mathrm{Bernoulli}(0.001)\cdot\mathcal{N}(0,100)$.

## Headline performance results
- FP16 forward: FA3 is about 1.5–2.0× faster than FA2 across many settings, reaching peaks of ~740 TFLOPs/s (about 75% of the H100 matmul peak reported in the paper).
- FP16 backward: FA3 shows ~1.5–1.75× speedups over FA2.
- FP8 forward: FA3 can reach close to 1.2 PFLOPs/s on H100 in favorable settings.
- Compared to a standard attention implementation FA3 can be 3–16× faster (depends on sequence length / head size).
- Compared to cuDNN: for medium and long sequences (≥1k) FA3 FP16 often outperforms cuDNN; FP8 is competitive but depends on head dimension and masking — e.g., for head dim 64 FA3 FP8 tends to be ahead, for 128/256 it is at-par for non-causal and behind with causal masking (paper’s reported nuance).

These are aggregate statements from the paper’s benchmark suite; individual config curves (seqlen × headdim) determine the exact crossover points.

## Where the wins come from (quick, practical explanation)
FA3 combines three algorithmic/hardware-aware moves that together produce the measured gains.

1. Producer–consumer asynchrony (warp-specialization and ping-pong scheduling)
   - FA3 splits the warps in a CTA into producer warps (issuing asynchronous TMA loads into shared memory) and consumer warps (issuing asynchronous WGMMA Tensor Core matmuls). This lets data movement (TMA) and compute (WGMMA) run concurrently and improves occupancy and latency hiding.
   - Ping-pong-style scheduling staggers warpgroups so softmax work from one group gets naturally scheduled while another group’s Tensor Cores run, using barriers to steer the schedule.

2. Interleaving block-wise GEMMs and softmax (intra-warpgroup pipelining)
   - The inner loop is turned into a small pipeline: while one WGMMA computes the next $\mathbf{S}$ block ($\mathbf{Q}\mathbf{K}^\top$), the implementation overlaps the softmax and the $\tilde{\mathbf{P}}\mathbf{V}$ WGMMA from the previous block.
   - This 2-stage (and optionally 3-stage) pipelining reduces the impact of lower-throughput components like exponentials and rescales by letting them execute concurrently with Tensor Core matmuls. The trade-off is extra register buffering (e.g., holding $\mathbf{S}_{\text{cur}}$ and $\mathbf{S}_{\text{next}}$) and more careful barrier placement; the compiler also must preserve the intended order.
   - In the paper’s ablation, these asynchronous/pipelining changes raised throughput in one tested config from ~570 TFLOPs to ~661 TFLOPs, demonstrating that the overlap pays off.

3. Hardware-accelerated low-precision GEMM (FP8) plus layout and accuracy fixes
   - On Hopper the FP8 Tensor Cores can double matmul throughput versus FP16, but they require operands in a k-major layout and place constraints on accumulator layouts.
   - FA3 implements in-kernel tile transposes (LDSM/STSM-based) and register-level permutations to meet these layout needs without extra global-memory transposes.
   - To address FP8 quantization error, FA3 uses block quantization (one FP8 scale per block) and incoherent processing (multiply $\mathbf{Q},\mathbf{K}$ by a cheap random orthogonal transform so outliers are “spread out”). The orthogonal transform satisfies $\mathbf{M}\mathbf{M}^\top = I$ so attention scores are unchanged, and it can be implemented cheaply (Hadamard × diagonal) and fused with other pre-attention ops.
   - The net result: near-doubling of matmul throughput from FP8 and a workable accuracy/latency trade-off for many long-context cases.

## Accuracy summary
- FP16: FA3 matches FA2 in numerical error and improves over a standard attention implementation in the paper’s outlier tests. The main reason is that FA3 (like FA2) keeps intermediate softmax/rescaling accumulators in higher precision (FP32), which reduces numeric drift. The paper reports around 1.7× lower RMSE (relative to the standard HBM-materializing implementation) for FA2/FA3 in FP16 in the outlier input regime.
- FP8: a naive per-tensor FP8 quantization baseline suffers significant error in the presence of outliers. FA3’s block quantization + incoherent processing reduces that FP8 numerical error by about 2.6× relative to that baseline in the paper’s tests. FP8 still has larger absolute rounding/error risk than FP16, but the proposed mitigations materially close the gap while delivering big throughput gains.

Numerical comparisons used RMSE to an FP64 reference on synthetic inputs designed to include rare large-magnitude outliers (as described above).

## Limitations and caveats
- FP8 FA3 is powerful for long sequences, but the FP8 kernel in the paper is not fully persistent / load-balanced; the authors note this partly explains why FP8 FA3 is not always faster than cuDNN for small sequences or with causal masking.
- The pipelined async design increases register usage; deeper pipelining hurts tile size choices and may force trade-offs.
- The approach relies on Hopper-specific async primitives (WGMMA and TMA) and FP8 constraints; the general ideas transfer to other accelerators that expose comparable async/memory/matrix units, but the exact engineering must be adapted.
- FP8 still requires careful tuning to avoid accuracy regressions in training or sensitive inference workloads; the paper focuses on forward-pass timing and numerical RMSE under a particular outlier model.

## Bottom line / practical takeaways
- If you care about long-context Transformer attention on Hopper/H100, FA3 is a substantial improvement over FA2 in both forward and backward speed, and it meaningfully narrows the gap to vendor-optimized kernels (and in many long-sequence FP16 cases overtakes cuDNN).
- The biggest wins come from treating data-movement and Tensor Core matmuls as asynchronous producers/consumers and overlapping comparatively slow elementwise/softmax work with high-throughput GEMMs.
- FP8 offers a large throughput win but needs layout engineering and quantization strategies (block scales + incoherent transforms) to be practical; FA3 provides an effective recipe for that trade-off.
- The implementation details matter: register pressure, compiler instruction ordering, and in-kernel transpose/permutation strategies are central to hitting the reported TFLOPs.

## Where to try it
FlashAttention-3 is open-sourced by the authors: https://github.com/Dao-AILab/flash-attention. The paper contains the micro-benchmarks and ablations described here if you want the full figures and per-configuration plots.



# Adopting FlashAttention-3: A Practical Guide for PyTorch and LLM Engineers

FlashAttention-3 (FA3) is an optimized attention primitive that pushes GPU utilization by explicitly exploiting asynchrony and low-precision FP8 Tensor Cores. If you build or tune Transformer-based models (especially long-context LLMs), FA3 can give you large throughput wins — but it also brings a few new layout, quantization, and hardware considerations. This guide distills the paper's practical advice: when to pick FP16 vs FP8, what hardware features matter, and concrete layout / fusion patterns (block quantization + Hadamard) to make FP8 both fast and accurate.

Code and implementation: https://github.com/Dao-AILab/flash-attention

## TL;DR (practical takeaways)
- Use FP16 FlashAttention-3 for training or when you need robust numerical behavior and better small-sequence / causal-mask performance. FA3 FP16 is 1.5–2.0× faster than FlashAttention-2 and reaches up to 740 TFLOPs/s (≈75% H100 utilization) in the paper’s H100 benchmarks.
- Try FP8 for inference and throughput-focused workloads on H100-class hardware: it can reach near 1.2 PFLOPs/s and, with FA3’s block quantization + incoherent processing, is ~2.6× more accurate than naive per-tensor FP8 attention in outlier-heavy cases.
- FP8 requires extra work: the GPU-level GEMM operand layout (k-major) and in-kernel transpose, register permutations, and per-block quantization. FA3 provides these techniques but you must ensure hardware support and follow the layout/fusion patterns described below.
- FA3 supports MQA/GQA (same approach used in FlashAttention-2) by adjusting tensor indexing so K/V are not duplicated in HBM.

## What FlashAttention-3 changes (short)
FlashAttention-3 combines three ideas to squeeze more performance from modern GPUs:
- Warp-specialized producer/consumer pipelining (use TMA for async loads and dedicate warps to producers or consumers).
- Overlap (pipeline) softmax work with asynchronous Tensor Core GEMMs (WGMMA), e.g., a 2-stage ping-pong scheme to schedule exponentials while Tensor Cores do matmuls.
- Use FP8 Tensor Cores for GEMMs but mitigate FP8 quantization error via block quantization and incoherent processing (orthogonal/Hadamard transforms). Also resolve FP8-specific layout constraints (k-major) with in-kernel transpose and register permutations.

The paper demonstrates that these ideas give significant throughput gains on NVIDIA Hopper (H100) and a notable accuracy improvement for FP8 attention compared to a baseline per-tensor FP8 quantization.

## When to pick FP16 vs FP8 (decision guidance)
- FP16 (or BF16): default choice for training and mixed-precision training loops. FA3 FP16 preserves numerical quality (keeps softmax intermediates in FP32) and matches or improves numerical error versus previous FlashAttention versions. It also has the most mature kernel in the FA3 implementation (persistent kernel + load-balancing), so it tends to be better for:
  - backprop / training,
  - small sequence lengths,
  - causal-masked attention,
  - head dimension sizes where FP8 benefits are marginal.
- FP8: choose when you need maximum inference throughput on H100-class hardware and you can tolerate or carefully test lower-precision behavior. FA3’s FP8 path is designed to:
  - nearly double Tensor Core MATMUL throughput compared to FP16,
  - reach up to ~1.2 PFLOPs/s in the paper’s H100 measurements,
  - be far more accurate than naive FP8 (FA3’s block quantization + incoherent processing gave ~2.6× lower RMSE vs per-tensor FP8 in outlier experiments).
  Practical caveats for FP8:
  - FA3’s FP8 implementation in the paper did not include the persistent kernel and load-balancing optimizations present for FP16, so small-seq / causal cases might see less advantage versus highly tuned vendor kernels.
  - For some combinations (head dim 128/256 + causal masking), FP8 was only competitive or behind vendor FP8 kernels; FP8 was clearly ahead at head dim 64 in the paper’s measurements. So benchmark for your model shapes.

## Hardware checklist: H100-class (what you need)
FlashAttention-3 targets GPUs that provide the following features (H100/Hopper is the concrete example in the paper):

- Asynchronous device-to-shared-memory copy engine (TMA) so data movement can overlap compute.
- Asynchronous WarpGroup Tensor Core instruction (WGMMA) that can be issued without stalling the rest of the warpgroup.
- Hardware FP8 Tensor Cores (e4m3) and WGMMA-path for FP8 matmuls.
- Warp-level matrix load/store instructions (LDSM/STSM) to implement efficient in-kernel transposes (useful to satisfy FP8 layout constraints).
- Ability to tune register allocation across warpgroups (e.g., setmaxnreg in PTX) to balance register pressure between producer and consumer warps.
- Sufficient shared-memory bandwidth and register file capacity to support the chosen tiling and the (2- or 3-)stage pipeline.

Footnote in the paper: FA3 ideas are applicable to other accelerators that expose similar asynchrony + low-precision capabilities, but the implementation in the paper is for Hopper/H100.

## FP8: layout rules and practical fixes (must-read)
FP8 WGMMA on Hopper accepts operands in a k-major layout from SMEM (i.e., contiguous in the inner K dimension). By contrast, tensors coming from standard model layouts are often contiguous in the head dimension (outer dimension for K/V tiles). This leads to two practical problems and fixes:

1. TMA loads cannot change the contiguous stride dimension.
   - Consequence: you cannot rely on TMA to both move data and transpose the tile dimension order for FP8; the kernel must perform an in-kernel transpose of the loaded tile.
   - FA3 solution: do an in-kernel transpose using warp matrix load/store primitives (LDSM/STSM). These instructions operate at warp granularity and can pack FP8 bytes (two 8-bit entries into the native LDSM 16-bit lane) and perform the transpose in SMEM/registers efficiently. The producer warpgroup performs the transpose while Tensor Cores are busy on previous work, hiding this cost.

2. Back-to-back WGMMA operand / accumulator layout clash.
   - The FP32 accumulator layout produced by the first WGMMA does not match the operand layout expected by the second FP8 WGMMA. FA3 resolves this by doing register-level byte permutations after the first WGMMA (using byte-permute instructions) to reorder the accumulator register content into the format expected by the next WGMMA. The in-kernel transpose writes a matching row permutation of the $\mathbf{V}$ tile so the two-stage GEMM sequence computes the correct logical result without costly thread shuffles.

Practical rule-of-thumb: if you want to use FP8 WGMMA reliably, plan for an in-kernel transpose of $\mathbf{V}$ tiles into k-major layout and for a small set of register permutations after FP32-accumulating WGMMAs. FA3 implements both.

(Notation reminder: the kernel operates on tiles of $\mathbf{Q}, \mathbf{K}, \mathbf{V}$; typical block sizes are denoted $B_r$ for query-rows and $B_c$ for key/value columns in the paper.)

## Making FP8 accurate: block quantization + incoherent processing
FP8 (e4m3) has a narrow dynamic range and few mantissa bits, so naive per-tensor quantization can fail when tensors contain large outliers (a common situation in LLM activations). FA3 uses two complementary techniques:

1. Block quantization
   - Quantize each block independently: instead of one scale per tensor, use one scale per block (each block is the same tile size used by the attention kernel, e.g., $B_r \times d$ or $B_c \times d$).
   - Benefit: per-block scaling adapts to local dynamic range, reducing quantization error in blocks with different magnitudes.
   - Integration tip: compute the block scale when you already visit that block (e.g., during rotary embedding or any in-place pre-attention op) and write the FP8 block plus its scale. The paper emphasizes this can be fused with the operation that precedes attention without extra bandwidth cost.

2. Incoherent processing (random orthogonal spreading)
   - Multiply $\mathbf{Q}$ and $\mathbf{K}$ by a random orthogonal matrix $\mathbf{M}$ before quantization; because $\mathbf{M}\mathbf{M}^\top = I$, attention scores are unchanged:
     $(\mathbf{Q}\mathbf{M})(\mathbf{K}\mathbf{M})^\top = \mathbf{Q}\mathbf{K}^\top$.
   - Practically, pick $\mathbf{M}$ as the product of diagonal sign matrices and a Hadamard matrix; multiplication by this $\mathbf{M}$ is cheap (O($d \log d$)) using fast Walsh–Hadamard transforms and sign flips.
   - Benefit: “spreads” outlier mass across dimensions so quantization is more uniform and less sensitive to single large entries.
   - Fusion tip: you can apply the Hadamard + sign operations together with the rotary embedding (or other pre-attention transforms) in a single pass, so the extra complexity is essentially free in practice.

Combined effect: block quantization + incoherent processing in FA3 reduced FP8 RMSE by ~2.6× versus a baseline per-tensor FP8 attention in the paper’s outlier tests. For inference use-cases with outliers, these two steps are key to making FP8 practical.

## How to fuse block quantization and Hadamard with rotary embedding (high level)
- Precompute the sign-diagonal pattern and the (implicit) Hadamard application you will use for $\mathbf{M}$.
- When you compute rotary embeddings (or any pre-attention elementwise transform), perform:
  1. Apply rotary embedding to a block of $\mathbf{Q}$ (and $\mathbf{K}$).
  2. Immediately apply the sign/Hadamard transform to the same block (using an FWHT routine).
  3. Compute the per-block scale (max absolute or another range estimator) for FP8 and quantize that block to FP8 using the scale.
  4. Write the FP8 block (and store its scale metadata).
- Because the same memory pass processes the block for rotary embedding, the extra Hadamard pass can be fused into that traversal (the FWHT is O($d \log d$) but the memory traffic is not increased if done eagerly), and the paper reports this as a practical zero-overhead fusion in their setup.

## Integration notes for multi-query / grouped-query attention (MQA/GQA)
FA3 follows the FlashAttention-2 approach: tensor indexing is adjusted so that $\mathbf{K}$ and $\mathbf{V}$ are not duplicated across heads when MQA or GQA variants are used. Practically, this means keeping standard K/V layout in HBM and adjusting the kernel’s indexing logic so the shared K/V tiles are consumed without creating extra copies. If your model uses MQA/GQA, FA3’s CTA-level tiling and producer/consumer logic are compatible provided you adapt the indexing to the query-grouping pattern (the FA3 codebase contains these adjustments).

## Practical adoption checklist and recommended workflow
1. Hardware and drivers: run on H100/Hopper or other GPUs that expose TMA + asynchronous WGMMA + FP8 Tensor Cores and LDSM/STSM primitives. If you lack these features, prefer FlashAttention-2 or FA3 FP16 if only FP16 is supported.
2. Build and test: clone https://github.com/Dao-AILab/flash-attention and follow the repo build instructions. The implementation reuses CUTLASS primitives (WGMMA, TMA).
3. Start with FP16 FA3:
   - Validate correctness vs your current attention implementation.
   - For training, default to FP16; FA3 preserves softmax intermediates in FP32 and matches FA2 numerical behavior.
   - Profile and tune block sizes if needed (trade-offs exist between tile size, register pressure, and pipeline depth).
4. If you need more inference throughput, evaluate FP8 FA3:
   - Add block quantization + incoherent processing (Hadamard + sign diagonal) fused into pre-attention ops (e.g., rotary embedding).
   - Ensure your data layout meets k-major requirements (or let FA3 do the in-kernel transpose).
   - Benchmark for your common sequence lengths, head dims, and with/without causal masking.
5. Validate numerics: compare against higher-precision reference (FP32/FP64) on representative inputs, especially if your model has frequent large activations/outliers.
6. Be aware of limitations: FA3’s paper implementation had a persistent kernel + load balance for FP16 but not for FP8; expect FP8 small-sequence/causal cases to need more tuning.

## Caveats and limitations
- FA3’s FP8 path in the paper did not yet include a persistent kernel and a full load-balancing strategy, which explains some reduced performance in small-sequence or causal cases compared to vendor libraries. Expect to re-benchmark as the implementation matures.
- The paper focuses on Hopper/H100; while the algorithmic ideas are general, practical implementation details (PTX instructions, exact primitives) are NVIDIA-specific. Porting to other hardware requires equivalent asynchronous copy / asynchronous matmul primitives and support for low-precision math.
- The effects of FP8 attention in large-scale training are not fully characterized; the paper flags this as future work. For now, FP8 is safest for inference.

## Where to try it
FA3 is open-source: https://github.com/Dao-AILab/flash-attention. The repo uses CUTLASS primitives and contains benchmark scripts used in the paper. The authors also state they plan to integrate the primitive into PyTorch and Hugging Face libraries to ease adoption; watch the repo and those projects for upstream integration.

## Final notes
FlashAttention-3 is a pragmatic rethinking of fused attention for modern GPUs that jointly leverages asynchrony, persistent tiling, and low-precision Tensor Cores. If you operate production inference stacks on H100-class machines and want maximum throughput, FA3’s FP8 path (with block quantization + incoherent transforms) is worth testing. If you’re training or need the most robust numerics across a range of shapes (especially small sequences / causal masking), start with FA3 FP16 — it offers a strong performance jump with well-understood numeric behavior.

If you experiment with FA3 in your codebase, the repo is the best place to start and the authors welcome integration into mainstream frameworks.



# Why Faster Attention Matters: Long Contexts, Multimodal Models, and What Comes Next

Attention is the heavy-lifter inside every Transformer, and that heaviness grows fast with context length. FlashAttention-3 (FA‑3) is a focused engineering and algorithmic update that squeezes much more performance out of modern GPUs (Hopper / H100 in the paper) by explicitly designing for asynchrony and low-precision hardware. The result: substantially faster exact attention, practical FP8 throughput, and reduced FP8 error with a few practical tricks. Below I summarize what FA‑3 does, why the gains matter for real workloads, and what still needs work.

## The bottleneck in one formula

For a single head, attention is computed as
$S = \alpha\,QK^\top,\; P = \mathrm{softmax}(S),\; O = PV$
(where $\alpha$ is usually $1/\sqrt{d}$). Cost grows quadratically with sequence length; the paper uses the forward-pass FLOP estimate
$\;4\cdot\text{seqlen}^2\cdot\text{head\_dim}\cdot\text{num\_heads}\;$,
and with causal masking roughly half that. When sequence lengths grow into the thousands, attention dominates compute, memory traffic, and latency. That’s why making exact attention faster is a direct multiplier on how big a context you can practically use.

## What FlashAttention‑3 changes (high level)

FlashAttention‑3 builds on the tiling/fusion ideas of FlashAttention and FlashAttention‑2, but it explicitly targets two modern hardware realities:

- GPUs now expose asynchronous, specialized units for both memory movement (TMA) and matrix multiply (the Hopper WGMMA tensor-core instruction), and those units can run concurrently.
- Hopper supports FP8 Tensor Cores with much higher matmul throughput than FP16, but FP8 brings stricter layout rules and larger quantization error.

FA‑3 brings three concrete ideas together to exploit those facts:

1. Warp-specialized producer/consumer asynchrony to overlap data movement and compute.
2. A pipelined (2‑stage, extendable) schedule that hides softmax work under asynchronous block GEMMs.
3. An FP8-aware implementation that handles layout constraints and reduces quantization error via block quantization and incoherent processing.

Each of these is practical and implemented in a single fused kernel to avoid round-trips to global memory.

## The three technical levers (brief, accessible)

- Producer-consumer warp specialization. Rather than every warp doing both loads and matmuls, warps are split into producers (issue TMA loads into shared memory) and consumers (do the WGMMA matmuls). Because TMA and WGMMA are asynchronous, producers and consumers can run in parallel and hide latency. FA‑3 uses a circular shared-memory buffer (ping‑pong stages) and dynamic register allocation (setmaxnreg on Hopper) so warps focused on matmuls can have more registers.

- Hiding softmax under GEMMs (2‑stage pipelining). On modern hardware the tensor-core matmuls are extremely fast (H100: ~989 TFLOPS FP16 matmul in the paper’s accounting) while special-function units doing exponentials are far slower (paper cites ~3.9 TFLOPS equivalent). FA‑3 breaks the strict per‑block dependency by computing the next block’s $S=\!QK^\top$ on the tensor cores (issued and not immediately waited on) while finishing the $P V$ matmul for the previous block. The exponentials and rescaling for softmax then execute while the heavy GEMM is running, improving utilization. The 2‑stage pipeline fits well in registers; a 3‑stage variant is possible but costs more registers.

- FP8-friendly layout and numerics. FP8 WGMMA on Hopper requires operands in a k-major layout and places different constraints on accumulator register layout. FA‑3 uses an in‑kernel tile transpose (via LDSM/STSM) to convert $\;V\;$ tiles into the required layout and byte-permute register moves to make FP32 accumulators compatible between chained WGMMA calls. To control FP8 quantization error FA‑3 uses:
  - Block quantization: one FP8 scale per block (the tiled algorithm already operates blockwise, so this is cheap and can be fused with a preceding op like rotary embeddings).
  - Incoherent processing: multiply $Q$ and $K$ by the same random orthogonal matrix $M$ before quantization (in practice implemented as diagonal $\{\pm1\}$ times a Hadamard so it’s $O(d\log d)$ and fusible). Because $M$ is orthogonal, $(QM)(KM)^\top = QK^\top$, but the randomized mixing spreads out outliers and reduces quantization error.

## Performance highlights (as measured on H100)

- FA‑3 forward pass is about 1.5–2.0× faster than FlashAttention‑2 (FP16). Backward pass is about 1.5–1.75× faster.
- FP16 peak observed: up to ~740 TFLOPs/s (≈75% of the theoretical tensor‑core throughput in the experiments).
- FP8 peak observed: approaches ~1.2 PFLOPs/s on H100.
- Compared to naive (standard) attention that materializes intermediates in HBM, FA‑3 can be 3–16× faster depending on sequence length. For medium/long sequences (≥~1k tokens) FA‑3 in FP16 outperforms a highly optimized vendor library (cuDNN) in the paper’s benchmarks; FP8 is competitive but depends on head dimension and masking (footnote nuance: for head_dim=64 FP8 is ahead; for 128 and 256 it is at-par without causal masking and behind with causal masking in some cases).
- FlashAttention‑2 was reported to reach only ~35% utilization on H100 in the paper, whereas FA‑3 improves utilization substantially by exploiting the asynchronous units.

## Accuracy and FP8 numerics

FA‑3 is careful about numerical stability:

- FP16 FA‑3 keeps softmax-related intermediate reductions in higher precision (FP32 where needed) and matches the numerical error of FlashAttention‑2. Both FA‑2 and FA‑3 show about 1.7× lower RMSE than a standard implementation in FP16 in the synthetic outlier test used in the paper.
- For FP8, a naive per‑tensor quantization baseline is substantially worse. Using block quantization and incoherent processing, FA‑3 reduces FP8 numerical error by about 2.6× compared to the baseline per‑tensor FP8 attention setup used in the paper’s comparisons.
- Experimental setup for the outlier test (for context): entries of $Q,K,V$ were sampled as $\mathcal{N}(0,1)+\mathcal{N}(0,100)\cdot\mathrm{Bernoulli}(0.001)$ — i.e., 0.1% of entries have large outliers — and RMSE to an FP64 reference was measured.

The takeaway: FP8 becomes practical for attention when you (a) use blockwise scaling and (b) diffuse outliers before quantization.

## Why these gains matter for real workloads

The paper explicitly links faster, exact attention to enabling or improving a set of growing application areas that are attention‑limited:

- Long-context language tasks: modeling and reasoning across multiple long documents or extended conversations require quadratic attention; faster kernels let you push to longer contexts for the same compute/latency budget.
- Multimodal, high‑resolution vision and long audio/video contexts: attention over pixels or frames multiplies cost quickly; higher throughput lets you use larger spatial/temporal windows.
- Large code bases and retrieval over many files: attention over long sequences enables better code understanding and program synthesis at scale.
- Agent workflows and recommender-style histories: more history or richer context improves agent reasoning and personalization, but only if attention cost is affordable.

In short, because attention is the algorithmic bottleneck for long contexts and dense multimodal inputs, cutting attention runtime by ~1.5–2× translates directly into either lower wall‑clock cost or the ability to use longer contexts (or both).

## Practical caveats and limitations (what’s left to do)

FA‑3 is a strong systems contribution, but the paper is candid about limits and next steps:

- FP8 kernel maturity: the FP8 FA‑3 kernel in the paper is not yet a persistent kernel with full load balancing; the FP16 kernel is persistent. That helps explain why FP8 FA‑3 underperforms for small sequence lengths and in some causal‑mask scenarios. Integrating a persistent FP8 kernel is a stated next step.
- Register pressure and compiler issues: the pipelined schemes increase register usage (storing extra $S$ tiles across stages), which forces tradeoffs between tile size and pipeline depth. Compiler reordering of instructions (NVCC/SASS) can also complicate the intended overlap, so careful low‑level engineering and SASS inspection are part of the implementation burden.
- Training with low precision: the paper validates FP8 numerics on forward-pass benchmarks and synthetic outliers, but the effects of widespread FP8 attention in large‑scale training remain a topic for further study.
- Hardware dependence: the implementation in the paper uses Hopper/H100 features (asynchronous WGMMA, TMA, setmaxnreg, LDSM/STSM). The authors expect the general ideas to carry to other accelerators that provide asynchronous execution and low‑precision tensor cores, but porting will require attention to the target architecture’s execution model and layout constraints.
- Integration and ecosystem: FA‑3 is open‑sourced (https://github.com/Dao-AILab/flash-attention) and the authors plan PyTorch/Hugging Face integration. Production adopters will want tight library integration, inference optimizations, and broader hardware coverage.

## Practical tips if you want to try FA‑3

- If your workload uses large sequence lengths (1k+), FA‑3’s FP16 kernel is a low-friction win: it keeps numerics safe (softmax reductions in FP32) and shows big speedups vs prior kernels.
- If you need FP8 for absolute peak throughput, expect extra engineering: in‑kernel transposes and block quantization are required, and the FP8 path may need persistent-kernel improvements to match FP16 on small/causal cases.
- The block quantization and Hadamard/diagonal incoherent mixing are cheap to fuse into preceding operations (e.g., rotary embeddings), so adopting FP8 doesn’t necessarily add global memory passes.

## Bottom line

FlashAttention‑3 is a pragmatic, hardware‑aware tightening of the attention primitive: it exploits asynchrony (data movement vs tensor cores), overlaps low-throughput softmax with high-throughput GEMMs, and makes FP8 usable for attention via layout fixes and smarter quantization. The result is faster exact attention (1.5–2× vs FA‑2, huge gains vs naive attention), practical FP8 throughput, and measurable reductions in FP8 error.

Why care? Faster, accurate attention is foundational: it directly reduces compute and latency for long‑context, multimodal, and retrieval-heavy workloads, enabling models and applications that weren’t practical before. The remaining gaps—FP8 persistence, training studies, and broader hardware ports—are solvable engineering problems, so expect attention to keep getting faster and cheaper in the near future.
