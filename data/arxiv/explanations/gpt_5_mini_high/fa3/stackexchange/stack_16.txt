\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### How are MQA and GQA supported without duplicating $\mathbf{K}$ and $\mathbf{V}$ in HBM?
Question:
The paper says it follows the FA-2 approach for multi-query and grouped-query attention by adjusting indexing to avoid duplicating $\mathbf{K}$ and $\mathbf{V}$. Could you detail how the TMA loads and SMEM staging are organized so that multiple query heads reuse the same $\mathbf{K}_j, \mathbf{V}_j$ tiles, and how the consumer warps iterate over heads while keeping the producer-consumer ring buffer efficient?
Answer:
Short answer: FlashAttention‑3 (like FlashAttention‑2) avoids duplicating $K$ and $V$ in HBM by storing one copy per “key group” in global memory and then staging each $K_j, V_j$ tile once into the CTA’s circular SMEM buffer so it can be reused for every query head that belongs to that group. Concretely the kernel (1) lays out $K/V$ in HBM with a group index (for MQA that group index is $0$; for GQA it is $g=\lfloor h/G\rfloor$), (2) issues one TMA load of the $(j)$th key/value tile for that group into a ring buffer stage in SMEM, and (3) has the consumer warps iterate an inner loop over the local heads that share that group so they all use the same SMEM $K_j, V_j$ tile before the stage is released. The producer only reuses (overwrites) a stage after every consuming head has finished with that stage, so no $K/V$ duplication is needed in HBM and the producer/consumer ring stays efficient because TMA + WGMMA are asynchronous and the pipeline is sized to hide latency.

Longer explanation (what is actually happening inside the kernel). The two implementation levers are (A) a compact HBM layout and pointer arithmetic for TMA loads, and (B) a CTA/warp-level iteration order that reuses SMEM tiles for multiple heads.

1) HBM layout and TMA indexing. In the duplicated‑free layout you store $K$ and $V$ as one block per key‑group rather than one block per head. If heads are grouped with size $G$ then a head $h$ reads keys/values from group $g=\lfloor h/G\rfloor$. The producer’s TMA source pointer is computed with that group offset so a single TMA call brings the correct $B_c\times d$ tile for group $g$ into SMEM. In other words the TMA address for $K_j$ is computed as $\text{base} + ((\text{batch\_index} \times \text{n\_groups} + g) \times N + j \times B_c) \times d \times \text{bytes\_per\_elem}$ (and analogously for $V$). This avoids duplicating $K/V$ in HBM.

2) SMEM ring buffer and single staging per group‑tile. The kernel already uses an $s$‑stage circular SMEM buffer (stage index = $j \bmod s$). The producer writes a $K_j, V_j$ tile once into stage $(j \bmod s)$ and then commits. The consumer(s) read from that stage. For GQA/MQA you do not change that buffer structure; you only change how/when the consumer releases a stage: the consumer must keep the stage live until all heads that share this group have consumed it.

3) Consumer iteration over heads (how reuse happens). To actually reuse one SMEM $K_j, V_j$ copy for several heads you put an inner head loop on the consumer side: for each stage $j$ the consumer performs the SS‑GEMM / softmax accumulation and RS‑GEMM for head $0$, then for head $1$, … for every head in the local head set that maps to this group, before it issues the release of that stage back to the producer. That means the per‑head streaming softmax state (the running row‑max $m_i^{(h)}$, the normalizer $\ell_i^{(h)}$, and the partial output accumulator $O_i^{(h)}$) must be kept independently per head (in registers / SMEM) while the stage is alive. Because the tile $K_j, V_j$ remains resident in the same SMEM stage through that inner head loop, every head reuses the identical $K_j, V_j$ without any extra HBM copy.

4) Keeping the ring buffer efficient (avoiding stalls). Two facts keep the buffer full and the pipeline efficient. First, TMA and WGMMA are asynchronous and we use warp‑specialization: producer warps issue TMA loads (and optionally the in‑kernel transpose for FP8) and consumer warps issue WGMMA computes; those operations overlap. Second, the ring buffer has $s$ stages chosen large enough to hide the time it takes for the consumer to process all local heads for a stage. In practice the kernel maps a small contiguous set of heads to a CTA (so no cross‑CTA synchronization is required) and chooses $s \ge \text{pipeline depth}$ (2 or 3 in the paper) so the producer can write ahead while consumers are still processing previous stages. Because the producer only waits on a stage when it has been consumed by all assigned heads, the producer/consumer producer never needs to duplicate $K/V$ in HBM to shorten this wait.

5) Practical notes and trade‑offs. Reusing $K/V$ in SMEM across multiple heads increases register/SMEM pressure because each head needs its own $m,\ell,O$ state for the query tile. So implementations pick how many heads are folded into a CTA to trade off register/shared memory usage vs. how often $K/V$ gets reloaded from HBM. If you cannot or do not want to fold all consuming heads into the same CTA, you still avoid HBM duplication (the HBM copy is singular per group) but different CTAs will load the same $K/V$ tile independently from HBM into their local SMEM; that still saves global memory and simplifies layout, but gives less SMEM reuse.

6) FP8 / layout wrinkles. The same reuse pattern holds when the kernel also has to perform the FP8-specific in‑kernel transpose and register permutations described in the paper: the producer does the transpose as it writes the $K_j$ or $V_j$ stage (so the SMEM tile is in the k‑major layout required by FP8 WGMMA), and consumer warps iterate over heads against that staged, properly permuted tile. Those extra transpose/permute costs are scheduled in the producer and overlapped with other work (thanks to TMA/WGMMA asynchrony).

In short: FlashAttention‑3 follows FA‑2’s trick of storing one $K/V$ per key‑group and simply indexes TMA loads to fetch that group copy. Inside the CTA the algorithm either (a) folds every head of that group into the same CTA so a single SMEM-staged $K_j, V_j$ tile is reused across the group by iterating over heads and releasing the ring stage only after every head is done, or (b) if folding is not possible, still stores only one copy in HBM and accepts per‑CTA reloads. The producer/consumer ping‑pong and the $s$‑stage SMEM ring remain the same; only the consumer’s inner loop and the stage‑release semantics are adjusted so multiple heads can reuse the same $K_j, V_j$ tile without global duplication.
