# Taming Tensor Core Layouts: Transposes and Byte Permutes for FP8 Speed

Modern Hopper GPUs give you huge raw throughput for FP8 matrix-multiply (WGMMA) — roughly 2× the Tensor‑Core matmul throughput versus FP16/BF16 — but they also come with a strict requirement: the FP8 WGMMA expects its inputs laid out in a particular way in shared memory. For attention kernels that do back‑to‑back GEMMs (e.g., computing $\mathbf{S}=\mathbf{Q}\mathbf{K}^\top$ then $\mathbf{O}=\mathbf{P}\mathbf{V}$), that layout requirement creates a practical bottleneck: either pay the price of expensive global‑memory transposes, or redesign your kernel to rearrange data and registers in‑flight. FlashAttention‑3 chooses the latter. This post unpacks the problem and the two small but crucial tricks the paper uses to avoid extra bandwidth: (1) in‑kernel shared‑memory transposes using ldmatrix/stmatrix, and (2) small byte‑level register permutations to reconcile accumulator and operand layouts so you can chain FP8 WGMMA calls inside one kernel.

## The core constraint: k‑major vs mn‑major

For a GEMM expressed as \(A \times B^\top\) where \(A\) is \(M\times K\) and \(B\) is \(N\times K\), we can categorize how an operand is laid out in memory:

- mn‑major: the operand is contiguous along the outer dimension (the \(M\) or \(N\) axis).
- k‑major: the operand is contiguous along the inner \(K\) axis.

On Hopper, FP16 WGMMA accepts operands in either mn‑major or k‑major layouts in shared memory, but FP8 WGMMA only accepts k‑major. In other words, when you target the FP8 Tensor Cores, the data in SMEM must be contiguous along the GEMM’s inner dimension \(K\).

That sounds abstract until you look at how attention tiles are normally laid out.

## Why attention hits a layout snag

Attention uses three inputs per head: \(\mathbf{Q}, \mathbf{K}, \mathbf{V}\in\mathbb{R}^{N\times d}\) (sequence length \(N\), head dim \(d\)). Common tensor layouts put the head dimension \(d\) as the fastest‑changing (contiguous) stride in memory: entries are contiguous in the head dimension.

Consider the two GEMMs inside a tiled attention kernel:

1. Block GEMM: \(\mathbf{S}_{ij} = \mathbf{Q}_i \mathbf{K}_j^\top\), where \(\mathbf{Q}_i\) is \(B_r\times d\) and \(\mathbf{K}_j\) is \(B_c\times d\).
2. Block GEMM: \(\mathbf{O}_i \mathrel{+}= \widetilde{\mathbf{P}}_{ij} \mathbf{V}_j\), where \(\widetilde{\mathbf{P}}_{ij}\) is \(B_r\times B_c\) and \(\mathbf{V}_j\) is \(B_c\times d\).

For the second GEMM (the softmax output times the value block), the inner dimension \(K\) is \(B_c\) (the block over the sequence). The FP8 WGMMA requires the operand corresponding to that \(K\) axis to be k‑major in SMEM — i.e., the tile of \(\mathbf{V}_j\) must be contiguous in sequence length. But the input layout you usually get from upstream (and what a TMA load will preserve) is contiguous in the head dimension \(d\), not sequence length. TMA copies do not change the contiguous stride for you, so you cannot simply load a tile and satisfy FP8 WGMMA’s k‑major requirement without transposing.

A straightforward fix — rewriting or pre‑transposing \(\mathbf{V}\) in global memory — is costly. A global transpose is a memory‑bandwidth heavy operation that defeats the whole point of a fused, memory‑efficient attention kernel.

## The FlashAttention‑3 solution, in two parts

FlashAttention‑3 avoids global transposes and enables back‑to‑back FP8 WGMMAs by combining two lightweight transformations that run inside the kernel:

1. In‑kernel SMEM transposes using ldmatrix/stmatrix, performed in the producer warpgroup so the data that the consumer warpgroup sees is already k‑major for FP8 WGMMA.
2. Small byte‑level register permutations (byte permutes) that rewire the FP32 accumulator layout produced by the first WGMMA into the register layout expected by the next FP8 WGMMA operand, eliminating an extra write/read or heavyweight lane shuffles.

Below I unpack each of those.

### 1) In‑kernel transpose into the k‑major layout (no global transpose)

Instead of transforming \(\mathbf{V}\) in global memory, FlashAttention‑3 loads tiles with TMA (which preserves the original contiguous dimension), then performs a warp‑level tile transpose in SMEM so the tile is laid out contiguous along the sequence axis (k‑major) for the next FP8 WGMMA.

Key implementation points from the paper:

- The kernel uses the ldmatrix/stmatrix pair (written in PTX as ldmatrix/stmatrix or LDSM/STSM) to do warp‑level copies and transposes at tile granularity. These primitives operate on an \(8\times 8\) block of 16‑bit entries (128 bytes) and are register‑efficient.
- FP8 uses 8‑bit entries. To use ldmatrix/stmatrix you can pack two FP8 values into one 16‑bit word and then operate on these packed half‑words; the kernel unpacks/repacks appropriately.
- The transpose versions cannot split packed 8‑bit entries, so the implementation includes small register moves between the ldmatrix load and stmatrix store to realize the logical transpose of 8‑bit FP8 elements. (The paper omits the low‑level detail but notes this necessary step.)
- The transpose is done by the producer warpgroup and is cheap in registers; crucially, it can be overlapped with the consumer's WGMMAs, so the latency is hidden.

This approach avoids an expensive pre‑transpose in HBM and keeps data movement local (GMEM → SMEM via TMA, then SMEM tile transpose). Because the transpose is executed inside the kernel and scheduled carefully (producer/consumer warp‑specialization), it does not add measurable bandwidth cost for typical attention settings.

### 2) Byte permutes: reconcile FP32 accumulators with FP8 operand layout

There is another, subtler layout mismatch that arises when you try to chain WGMMAs: the FP8 WGMMA emits FP32 accumulators in registers using one lane/register ordering, but the next WGMMA (when treating those accumulators as an operand) expects a different register ordering (the operand layout encoding). In short, the register-level ordering of the first WGMMA’s FP32 accumulators is incompatible with the operand layout needed by the second WGMMA.

FlashAttention‑3 fixes this with tiny register permutations: a few byte‑level permute instructions are used to reorder the accumulator registers so that they correspond to the k‑major operand layout expected by the next WGMMA. The paper gives a concrete example of the permutation pattern used: the sequence of elements in a register chunk is rearranged from the natural order into an order like
\(\{d0, d1, d4, d5, d2, d3, d6, d7\}\), and that pattern is replicated every eight bytes. Effectively this permutes columns of a small \(\mathbf{P}\) tile so that the register contents can be consumed by the next WGMMA without additional inter‑thread shuffles or memory traffic.

Because the in‑kernel transpose that produced the V tile can control the row order it writes into SMEM, FlashAttention‑3 pairs the accumulator byte permute with a matching row permutation of the transposed \(\mathbf{V}\) tile. The two permutations are chosen to be compatible so no expensive cross‑lane register exchange is necessary; everything is local to the warp and handled with byte permutes and register moves.

## How it fits in the pipeline and why it’s fast

Putting the pieces together, the kernel does the following at tile granularity:

- Producer warpgroup: TMA loads \(\mathbf{V}_j\) (packed FP8) into SMEM in its original contiguous layout, then performs an in‑kernel transpose (ldmatrix/stmatrix + small reg moves) to write a k‑major tile into SMEM.
- Consumer warpgroup: issues an asynchronous FP8 WGMMA for \(\mathbf{Q}_i\mathbf{K}_j^\top\) (first GEMM), keeps the FP32 accumulators in registers, applies a small byte permutation to those registers so their ordering matches the operand layout for the next FGEMM, and then issues the FP8 WGMMA for \(\widetilde{\mathbf{P}}_{ij}\mathbf{V}_j\) (second GEMM) reading the already transposed \(\mathbf{V}_j\) from SMEM.
- Scheduling: the in‑kernel transpose for the next \(\mathbf{V}\) tile is executed while the current WGMMA operations are in flight, so its latency is hidden. Warp‑specialization and the Hopper Tensor Core/TMA asynchrony lets the kernel overlap the data movement, the ldmatrix/stmatrix transpose, softmax work, and WGMMAs.

The net effect: two back‑to‑back FP8 WGMMAs can be invoked inside a single fused kernel without falling back to global‑memory transposes or writing intermediate accumulators to HBM. That preserves the low memory–IO design goal of FlashAttention while allowing the algorithm to target the much higher FP8 Tensor‑Core throughput.

## Practical tips and caveats

- Packing: LDSM/STSM operate on 16‑bit entries, so you pack two FP8 values per half‑word and handle unpack/repacks across the warp. The transpose variants don’t split packed bytes, so you will need small register moves between ldmatrix and stmatrix to realize the logical byte transpose.
- Register pressure: storing an extra intermediate tile (e.g., \(\mathbf{S}_{\text{next}}\)) in registers for pipelining increases register usage. There’s a tradeoff between tile sizes and pipeline depth: larger tiles can improve GEMM efficiency but increase register pressure.
- Compiler reordering: the instruction scheduler can reorder non‑WGMMA and WGMMA instructions in surprising ways; the FlashAttention‑3 implementation checks generated SASS to ensure the intended overlap actually occurs.
- Portability: these techniques rely on Hopper features (WGMMA/TMA and ldmatrix/stmatrix semantics). The general idea — do SMEM transposes and register permutations instead of global transposes — is portable, but the exact instructions and constraints differ by architecture.
- Accuracy: enabling FP8 requires attention to quantization. FlashAttention‑3 couples these layout fixes with block quantization and incoherent processing (randomized orthogonal mixing) to reduce FP8 quantization error; the FP8 variant of FlashAttention‑3 is reported to be significantly more accurate than a naive per‑tensor FP8 baseline.

## Bottom line

FP8 Tensor Cores on Hopper are powerful but picky about how data is laid out. For attention kernels that want to fuse the inner two GEMMs and target FP8 throughput, the k‑major constraint forces you to either pay for global transposes or to do small, local transformations. FlashAttention‑3 shows that doing the work inside the kernel — a warp‑level transpose in SMEM (ldmatrix/stmatrix with packed FP8) plus a few byte‑permute register ops to reconcile accumulator vs operand layouts — lets you chain FP8 WGMMAs cleanly and without extra global‑memory bandwidth. The result is a fused FP8 attention kernel that runs at much higher TFLOPs and keeps the memory‑efficient philosophy of FlashAttention intact.
