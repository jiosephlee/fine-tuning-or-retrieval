\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### In BitNet b1.58, is the ternary weight matrix rescaled by $\gamma$ after matmul, or is the scale dropped?
Question:
In "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits", the ternary weights are obtained via $\tilde{W} = \mathrm{RoundClip}(W/(\gamma+\epsilon), -1, 1)$ with $\gamma = \frac{1}{nm}\sum_{ij} |W_{ij}|$. In many ternary schemes one uses $W_q \approx \gamma \cdot \tilde{W}$ and applies a scalar rescale after the matmul. Here it is unclear whether inference uses only $\tilde{W}$, or whether there is a dequantization multiply by $\gamma$ (per-tensor or per-channel) on the output. If there is a rescale, where does it happen and is that multiply counted in the latency/energy results? If there is no rescale, how is magnitude information recovered elsewhere?
Answer:
Short answer: $\gamma$ is not a throwaway — the ternary codebook implicitly represents the original magnitudes as $W \approx \gamma\widetilde W$. The paper does not write the word-for-word runtime prescription, but everything the paper says (the definition of $\gamma$, the math identity $A W \approx \gamma (A\widetilde W)$, and their claims about “integer-add only” GEMMs and using optimized 2‑bit kernels) points to the scale being preserved and applied as a single per-matrix scalar factor (or fused away), not being discarded.

Why this is the only sensible reading: the quantizer is
$$
\widetilde W=\mathrm{RoundClip}\!\big(\tfrac{W}{\gamma+\epsilon},-1,1\big)
\quad\text{with}\quad
\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|.
$$
That definition makes $\gamma$ the per-weight-matrix magnitude reference, so mathematically
$$
A W \approx A(\gamma\widetilde W)=\gamma\,(A\widetilde W).
$$
If you dropped $\gamma$ entirely you would lose amplitude information and could not match FP16 behavior. In practice quantized inference therefore computes the integer/ternary accumulation $S=A_{\text{q}}\widetilde W$ and then multiplies by the scalar dequant factor(s) (for example $\gamma$ and any activation scale $\alpha$): $Y\approx\gamma\alpha S$.

Where that multiply happens and whether it was “counted” in the paper’s cost numbers: the paper reports latency/energy using FasterTransformer with a 2‑bit kernel (Ladder) integrated, and repeatedly emphasizes that the heavy inner GEMM work is integer-addition dominated. That implies the implementation uses an optimized integer kernel that does the inner accumulations with cheap adds/subtracts (ternary multiplications are sign flips) and then either (a) applies the per-matrix scalar dequant multiply once per output vector, or (b) fuses/absorbs the scalar into neighbouring operations (activation scaling per token, or folded into following layer normalization / next-layer weights) so it is not an extra full-precision multiply per MAC. In short, any dequant multiply is a single per-matrix/per-vector scalar scaling or fused operation (cheap compared to replacing all FP MACs), and the paper’s measured latency/energy already reflect the behavior of their optimized kernels (i.e., they did not pretend the scalar is free, but it is not the dominant cost).

Practical implementation note: because $\gamma$ is defined per-matrix (not per-channel), the runtime cost is small: one scalar multiply per output block (or a fused scale) rather than a multiply per MAC. If you want to reproduce exactly, inspect the BitLinear / Ladder 2‑bit kernel in their code or FasterTransformer integration — that kernel will show whether the scalar is applied after accumulation or fused into activation quantization. The upshot is: magnitude is recovered via $\gamma$; it isn’t “dropped”, and the paper’s performance/energy claims are for an implementation that keeps that scale but implements it cheaply (hence the “integer-add dominated” accounting).

### What does "1.58 bits" mean in practice if the kernel packs weights in 2 bits?
Question:
The paper calls the model "1.58-bit" because weights are ternary $\{-1,0,1\}$ (entropy $\log_2 3 \approx 1.585$), but the implementation uses the Ladder 2-bit kernel. Are the reported memory/latency results based on 2-bit physical packing, or do you use any entropy coding to approach 1.58 bits/weight? How are per-tensor scales, padding/alignment, and metadata counted in memory totals? When should we think in terms of 1.58 bits vs 2 bits for practical deployments?
Answer:
Short answer: calling the model “$1.58$‑bit” is an information‑theoretic description of the ternary alphabet (every weight takes values in $\{-1,0,+1\}$, so the entropy is $H=\log_2 3\approx 1.585$ bits). In the paper’s experiments, however, the runtime memory and latency were measured using a $2$‑bit packed kernel (the Ladder $2$‑bit kernel integrated into FasterTransformer). The authors explicitly say “Both latency and memory were measured with a $2$‑bit kernel, so there is still room for optimization,” which implies they did not use additional entropy coding to turn the theoretical $1.585$ bits/weight into a lower physical bits/weight in the inference measurements.

Why the two numbers are different (intuitive): $1.585$ bits is the lower bound on average information per weight given a ternary distribution — it tells you how many bits you would need on average with an optimal variable‑length encoder. A $2$‑bit physical packing is a fixed‑length encoding that stores exactly two bits per weight and is much easier and faster to use directly inside a GPU kernel. Moving from $2$ bits to an average of $1.585$ bits requires variable‑length or entropy coding (Huffman, arithmetic, RLE, etc.), which saves only around
$$1 - \frac{\log_2 3}{2} \approx 20.8\%$$
in raw bit storage in the ideal uniform ternary case, and possibly more if the empirical ternary distribution is skewed (e.g. many zeros). But entropy coding brings decoding overhead and makes random/block access for matmuls more complex; unless the kernel can consume the compressed stream directly (or you decompress in hardware/on the fly), the latency/memory benefits at inference are not automatic.

How scales, padding and metadata are counted (what to expect): the paper’s quantizer computes one scale per weight tensor ($\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|$), so you must store at least one scalar scale per tensor. The paper does not state the dtype used for scales, but common choices are FP16 or FP32; for large linear layers this per‑tensor scalar is negligible (for example, a $4096\times4096$ matrix has $\sim16.7\,$M weights, at $2$ bits $\approx 4.17\,$MiB, so one FP16 or FP32 scale is a vanishing overhead). However, many small tensors or finer per‑channel/group scales raise the relative overhead. Bitpacking itself also requires grouping bits into bytes/words for the kernel, so there is padding to the kernel’s block granularity (columns/rows rounded up to the kernel tile size) and alignment to memory boundaries; for large matrices that padding is a tiny fraction, for many small matrices it can be material. Framework/runtime metadata (tensor shapes, pointers, format flags, any zero masks) also add a small fixed overhead per tensor. The paper’s memory/latency numbers come from running the actual packed $2$‑bit kernel inside FasterTransformer, so those measurements already include the kernel’s packing/alignment behavior and the runtime overheads present in that setup.

When to think in terms of $1.58$ bits vs $2$ bits for deployment decisions: use $1.58$ bits when reasoning about model capacity, information content, or the theoretical compression limit of your ternary weights (and when arguing for the potential room to squeeze more storage by compression). Use $2$ bits when planning real‑world inference memory, bandwidth and kernel performance with current quantized kernels (like Ladder) or GPUs, because those kernels operate on fixed, bit‑packed representations and the paper’s speed/memory claims are measured for that setup. If you intend to reduce stored model size on disk or for network transfer, you can compress offline toward the entropy limit and get the $\sim 20\%$ (or more if distribution is skewed) reduction; but to get runtime memory/bandwidth reductions without a big latency penalty you need either (a) kernels that operate directly on the compressed representation, (b) streaming/block decompression tightly integrated with the matmul so you never expand to a full dense representation in DRAM/SRAM, or (c) dedicated hardware that supports ternary/variable‑length formats natively — none of which the paper claims to have used in the reported timing/memory numbers.

Practical rule of thumb: assume $2$ bits/weight (plus one scale per tensor and small alignment/metadata overhead) for latency and GPU memory planning today; treat $1.58$ bits as the theoretical lower bound and as motivation to explore compression or hardware/kernel co‑design if you want the extra $\sim 20\%$ storage savings in practice. The paper demonstrates that the model’s statistical/accuracy behavior matches FP16 despite being ternary; converting that theoretical information saving into runtime/VRAM savings is an additional engineering step.

### Over which axis is the absmean scale $\gamma$ computed, and why not per-channel or groupwise scaling?
Question:
You define $\gamma = \frac{1}{nm}\sum_{ij}|W_{ij}|$, i.e., an abs-mean over the entire matrix. Many quantization methods use per-output-channel (row-wise or column-wise) or groupwise scales to improve fidelity. Why choose a per-matrix abs-mean here? Did you try per-channel $\gamma_c = \frac{1}{n}\sum_i |W_{ic}|$ or groupwise variants, and what were the accuracy/speed trade-offs? Does per-channel scaling add too many post-matmul multiplies that hurt the "almost no multiplication" claim?
Answer:
Short answer: in the paper $\gamma$ is computed over the entire weight matrix (all $i,j$): $\gamma = \frac{1}{nm}\sum_{i,j} |W_{ij}|$. The manuscript does not report per-channel or groupwise $\gamma$ experiments; the per-matrix abs-mean was chosen for simplicity, hardware/kernelling friendliness, and because BitNet is trained from scratch so the network can adapt to a single global scale.

Why that choice makes sense (intuitive + math): the quantizer produces ternary weights
$\widetilde{W} = \mathrm{RoundClip}\!\big(W/(\gamma+\epsilon), -1, 1\big)$,
so during inference you can treat $W \approx \gamma \widetilde{W}$. For a linear layer $Y = X W$ we get
$Y \approx \gamma (X \widetilde{W})$. The huge win of BitNet is that the expensive inner products $X \widetilde{W}$ can be implemented with integer sign flips and additions (no FP multiplies). All that remains is the cheap rescaling by $\gamma$ on the layer outputs.

Cost/complexity trade-offs vs per‑channel/groupwise scaling: switching to per‑channel scales $\gamma_j$ (or groupwise scales) does reduce per‑column quantization error in general — that is why many post‑training quant methods use them — but it changes the system trade-offs. Crucially, both per‑matrix and per‑channel approaches require one scalar multiply per output element to apply the scale (you still must do $m$ multiplies to scale an $m$‑dimensional output). What differs is metadata, memory traffic and kernel complexity: per‑channel scaling forces you to store/load a vector of $m$ scales, prevents easy broadcast/fusion of a single scalar, and makes handcrafted integer‑only kernels and hardware less efficient. In practice that extra memory loads and loss of simple broadcastability can hurt latency and energy even if the raw multiply count is the same order. For BitNet (trained from scratch) the authors pick the simpler per‑matrix absmean so the model adapts to the global scale and the inference kernel remains extremely simple and hardware‑friendly.

About accuracy experiments: the paper does not present per‑channel/groupwise ablations, so it does not claim whether per‑channel would materially improve final perplexity/zero‑shot accuracy in the BitNet training regime. A likely reason to omit them is that BitNet is quantization‑aware during training (not PTQ), so the model can learn to live with a global scale; the marginal accuracy gain from per‑channel scales may be small compared to the extra engineering and runtime cost. If you care about absolute fidelity in a PTQ setting, per‑channel is often helpful; if you train quantized from scratch and aim for minimal kernel complexity, per‑matrix is a pragmatic choice.

If you want to explore this yourself, run a small ablation: train identical small models with per‑matrix, groupwise (blocks of channels), and per‑channel $\gamma$; measure validation loss and profile inference latency and memory traffic. Also try fusing the per‑channel scale into a following fused kernel (or quantize scales into power‑of‑two) to reduce the practical cost of per‑channel scaling.

### How are gradients passed through the non-differentiable RoundClip—do you use an STE, and with what details?
Question:
During training, $\tilde{W} = \mathrm{RoundClip}(\cdot)$ is piecewise constant. Do you use a straight-through estimator with $\partial \tilde{W}/\partial W = 1$ in some range and $0$ outside, or another surrogate? How are gradients handled at the clip boundaries $\pm 1$? Is there any gradient scaling/annealing on $W/(\gamma+\epsilon)$ early in training to control quantization noise?
Answer:
Short answer: the paper does not explicitly state the backward-through-RoundClip trick it used. However, given that BitNet-style quantization and standard quantization-aware training practices are referenced, the most plausible and commonly used approach is a straight-through estimator (STE): round is treated as identity in the backward pass, clipping contributes the usual indicator-mask derivative (1 inside the unclipped interval, 0 where saturated), and the scalar scale $\gamma$ is normally detached so gradients do not backpropagate through the global scale. The paper does not report any special annealing schedule on $W/(\gamma+\epsilon)$.

Why that is the natural interpretation and what it means mathematically. Define $s=\gamma+\epsilon$ and

$$
x = \frac{W}{s},\qquad \widetilde{W} = \mathrm{RoundClip}(x,-1,1).
$$

In practice one usually reconstructs a forward weight (for matmuls) as $W_q = s\cdot\widetilde{W}$. Because $\mathrm{round}(\cdot)$ and clipping are piecewise-constant / non-differentiable, STE replaces their backward Jacobian by a simple surrogate. The typical surrogate used in this family of papers is to let rounding be identity in the backward pass and let clipping pass gradient only where $|x|<1$. If $s$ is detached (no gradient through $\gamma$) this gives the simple local backward rule

$$
\frac{\partial L}{\partial W} \;=\; \frac{1}{s}\,\mathbf{1}_{|x|<1}\odot\frac{\partial L}{\partial W_q},
$$

i.e. gradients to each weight are the upstream gradient divided by $s$ and masked off for saturated (clipped) inputs. If you instead treat $\widetilde W$ itself as the parameter used in the rest of the graph (no de-scaling), replace $\partial L/\partial W_q$ with $\partial L/\partial\widetilde W$ and the same mask/divide-by-$s$ factor appears from the chain rule.

What happens at the boundaries $\pm 1$. The derivative is technically undefined at exactly $x=\pm1$, but those exact values occur on a measure-zero set in continuous weights and are not an issue in practice. Implementations typically use the clamp derivative (1 when $|x|<1$, 0 when $|x|>1$); the value at the exact boundary can be chosen arbitrarily (frameworks usually return 0 or one-sided derivative). A common and robust implementation trick that implements STE in frameworks is

$$
\widetilde x_{\text{STE}} = (\mathrm{round}(\mathrm{clamp}(x,-1,1)) - \mathrm{clamp}(x,-1,1)).\text{detach}() \;+\; \mathrm{clamp}(x,-1,1),
$$

so forward uses the rounded/clamped integer but the backward gradient is exactly that of the unclamped $\mathrm{clamp}(x,-1,1)$ (i.e. the mask behavior above). That makes boundary handling pragmatic and stable.

Why people detach $\gamma$. If you do not detach $s=\gamma+\epsilon$ then gradients pick up a global, cross-weight coupling (because $\gamma=\tfrac{1}{nm}\sum |W_{ij}|$ depends on all weights). That produces extra terms of the form proportional to $\partial s/\partial W$ (i.e. $\operatorname{sign}(W)/nm$) and tends to introduce instability and unexpected global interactions. The usual, stable choice is to compute $\gamma$ from the current weights but stop gradients through it (i.e. use $\gamma.\text{detach}()$). The paper defines $\gamma$ as the abs-mean and does not say it backpropagates through it, so detaching is the conservative, standard assumption.

About annealing / gradient scaling. The paper does not report a specific annealing schedule on $W/s$ or a special gradient scaling to gradually introduce quantization. They state models are trained from scratch with the 1.58-bit weights (and 8‑bit activations), so the stable training recipe is probably obtained by the combination of the STE surrogate, detaching the scale, standard optimizer schedules (LR warmup/decay), and architecture choices (RMSNorm, SwiGLU, no biases). If you observe excessive quantization noise in practice, common remedies are (not stated in the paper): (i) soft surrogates / softround that interpolate between identity and hard round and anneal a temperature, (ii) add small uniform noise to emulate quantization during early training, or (iii) progressive quantization (start in higher precision and move to ternary). The paper does not report using any of these.

Concrete PyTorch-style idiom (what people typically implement). Compute the scale, detach it, normalize, clip/round in forward, and use the STE trick so the backward gives the unclipped gradient:
s = W.abs().mean()
s_det = s.detach()
x = W / (s_det + eps)
x_clamped = x.clamp(-1,1)
x_rounded = x_clamped.round()
x_q_ste = (x_rounded - x_clamped).detach() + x_clamped   # STE: forward uses rounded, backward uses unclamped x
W_q = x_q_ste * (s_det + eps)                            # use W_q for forward matmuls

This yields exactly the masked $1/s$ factor in the backward pass and avoids gradient flow through $\gamma$.

If you need a definitive answer for this paper, check the authors' implementation/repo or ask the authors; the manuscript itself gives the quantization formula but does not list the exact backward/training surrogate or claim any special annealing.

### Per-token activation quantization to $[-Q_b, Q_b]$: what exactly is "per token", and how are scales computed and applied?
Question:
The paper states that activations are 8-bit, scaled to $[-Q_b,Q_b]$ per token, and the zero-point is removed. Does "per token" mean per batch element and sequence position independently, over the hidden dimension of each layer? Is the scale $s$ computed as $s = Q_b/\max(|x|)$ or via an abs-mean/percentile? Is $Q_b=127$ (symmetric int8)? Are scales recomputed at every layer and time step in decoding, and what is the runtime overhead of this dynamic scaling?
Answer:
Short answer: “Per token” means one scale per token vector (i.e., per batch element and sequence position) computed across the hidden dimension at each layer. The paper does not write an explicit arithmetic formula for the activation scale, but it says the activation quantizer “follows the same implementation in BitNet” and that weights used an abs‑mean scale, so the intended/most consistent interpretation is an abs‑mean (or equivalent single‑scale) per token mapped to a symmetric signed 8‑bit range (so $Q_b$ is the symmetric 8‑bit peak, typically $127$). Scales are produced when a token’s activations are computed (so per layer when that token passes through the layer); the runtime cost is just a per‑token reduction plus elementwise rescale/round operations and is small compared to the cost of the layer matrix multiplies (the paper reports this as “negligible”).

More detail and a concrete formula consistent with the paper. Let $x\in\mathbb{R}^d$ be the hidden vector for one token (a particular batch element and sequence position) at a given layer. The paper’s weight quantizer computes an average absolute scale $\gamma$ for a weight matrix and does RoundClip against $\{-1,0,1\}$. Translating that style to activations and an 8‑bit symmetric target gives a natural/consistent recipe:

- compute an abs‑mean for the token: $\gamma_x=\frac{1}{d}\sum_{i=1}^d |x_i|$ (plus a tiny $\epsilon$ for stability),
- take a scale per token $s=\frac{\gamma_x+\epsilon}{Q_b}$ (equivalently you can view $Q_b/(\gamma_x+\epsilon)$ as the multiplier used before rounding),
- quantize to signed 8‑bit integers by
  $$
  q_i=\operatorname{clip}\!\left(\operatorname{round}\!\left(\frac{x_i}{s}\right),-Q_b,Q_b\right),
  $$
  and dequantize as $\hat{x}_i = s\cdot q_i$.

This matches the description “scaled to $[-Q_b,Q_b]$ per token” and mirrors the paper’s use of an absmean scale for weights. The paper itself does not explicitly say “we used max(|x|) or percentile” for activations; because the weight quantizer used an abs‑mean, the conservative reading is that activations use the same abs‑mean style. (Using max or a percentile is an alternative design choice in other works, but it would be a deviation from “same implementation in BitNet” unless the authors explicitly state it.)

On $Q_b$: since activations are 8‑bit and the paper emphasizes removing the zero‑point by using a symmetric interval $[-Q_b,Q_b]$, $Q_b$ is the symmetric 8‑bit maximum (standard choice is $Q_b=127$). Using $127$ keeps the mapping symmetric around zero and avoids an asymmetric zero‑point.

On when scales are computed and runtime cost: the scale for a given token and layer must be computed when that token’s activations are produced for that layer. In autoregressive decoding that means you compute the scale once when you propagate the new token through the layer. If you quantize and store K/V caches, you then store the quantized bytes plus the single scalar scale for that token+layer so you do not need to recompute the scale for cached keys/values later. The extra work to produce the scale is one reduction across the $d$ hidden dimensions (to get $\gamma_x$), one reciprocal/multiply to form $1/s$ (or one division), $d$ elementwise multiplies and rounds to produce the integer vector $q$, and storing one float scale per token per layer. Relative to the cost of the layer GEMMs (large matrix multiplies), this is typically tiny; the paper characterizes the approach as “more convenient and simple for both implementation and system‑level optimization, while introduces negligible effects to the performance in our experiments.”

If you implement this, a practical checklist is: compute and store one float scale per (batch, position, layer) together with the quantized 8‑bit vector; on attention you can either use integer kernels that fold in scales or dequantize on the fly using the stored scale. The paper doesn’t publish microsecond overhead numbers for the scale computation, only the qualitative “negligible” statement, but the asymptotic cost and the storage/memory tradeoff are as described above.

### Does per-token scaling disturb attention calibration? How are $QK^\top$ dot products handled with different scales per token?
Question:
If each token's hidden vector is quantized with its own symmetric scale, queries $Q$ and keys $K$ may have token-dependent scales. Before computing $QK^\top$ and softmax, do you dequantize to a common floating-point domain, or carry per-token scales into the dot product and renormalize analytically? Any observed impact on attention score variance or the effective softmax temperature due to per-token quantization?
Answer:
Short answer: you can do either, and they are mathematically equivalent — but in practice you usually keep the per-token scales around and either (A) compute integer dot-products and multiply by the product of the two token scales, or (B) dequantize one side (usually the cached keys) once and then only have a per-query scalar left. Per-token symmetric scaling does change the pre‑softmax logits (it multiplies them), so it can alter the effective softmax “temperature” in principle — but in BitNet’s design this effect is small and was empirically negligible.

Why, and how to think about it precisely. Let the quantized (integer) query and key vectors be $\widehat{Q}_i,\widehat{K}_j$ and their per‑token symmetric scales be $s^Q_i,s^K_j$. Then the true (dequantized) dot product used by attention is
$$
z_{ij}=\frac{Q_i\cdot K_j}{\sqrt{d_k}}
=\frac{(s^Q_i\widehat{Q}_i)\cdot(s^K_j\widehat{K}_j)}{\sqrt{d_k}}
=\frac{s^Q_i s^K_j}{\sqrt{d_k}}\;\big(\widehat{Q}_i^\top\widehat{K}_j\big).
$$
So you can implement this either by computing the integer inner product $p_{ij}=\widehat{Q}_i^\top\widehat{K}_j$ and then multiplying by the scalar factor $s^Q_i s^K_j/\sqrt{d_k}$, or by dequantizing $\widehat{Q}$ and $\widehat{K}$ into floats and computing the usual float matmul. Both give the same numerical logits.

How this affects softmax calibration. The softmax sees
$$
\mathrm{softmax}_j\big(z_{ij}\big)=\mathrm{softmax}_j\!\left(\frac{s^Q_i s^K_j}{\sqrt{d_k}}\,p_{ij}\right).
$$
If you pre‑dequantize and cache keys as $K'_j=s^K_j\widehat{K}_j$ (a common practical choice), then
$$
z_{ij}=\frac{s^Q_i}{\sqrt{d_k}}\;\widehat{Q}_i^\top K'_j,
$$
so each query row is multiplied by the same scalar $s^Q_i$. Multiplying all logits in a softmax row by a positive scalar changes the effective temperature: larger $s^Q_i$ makes the distribution sharper, smaller $s^Q_i$ makes it flatter (because $\mathrm{softmax}(c\cdot x)$ is equivalent to $\mathrm{softmax}(x/(1/c))$). If you do not pre‑dequantize keys, the remaining per‑key factors $s^K_j$ make the effect non‑uniform across keys, which is a more complex distortion of relative scores.

Why BitNet reports negligible effect. The paper explicitly uses per‑token symmetric quantization of activations to the range $[-Q_b,Q_b]$ (no zero point), and uses RMSNorm and training-from-scratch. Symmetric quantization makes the algebra above exact (no pesky zero-point offsets), and RMSNorm / the training procedure keep activation norms reasonably well behaved and let the model adapt to any systematic scaling during training. The authors state that this per‑token scaling “introduces negligible effects to the performance in our experiments,” which matches the intuition that (a) per‑token scale variation is not huge after normalization layers and (b) training from scratch lets the network accommodate the residual temperature shifts.

Practical trade‑offs and recommendations. If you want maximum numerical fidelity to an FP baseline you can dequantize to float before softmax; if you want to stay in integer/math-efficient kernels, compute integer matmul once and apply the scalar scale product $s^Q_i s^K_j$ to the integer results. To avoid per‑pair multiplies you can pre‑dequantize/scale and store keys once (so only a per‑query scalar remains), or use coarser grouping of scales (per‑head or per‑layer) to reduce variance. If you are doing post‑training quantization of an already trained FP model, watch for calibration shifts (temperature changes) and consider light calibration or a small fine‑tuning pass; if you train with quantization (as BitNet does) the model will likely absorb the effect and you will see little degradation.

In short: per‑token symmetric scaling does mathematically multiply logits and therefore can change softmax sharpness, but it is easy to handle exactly (either by dequantizing or by carrying the scale products into the dot product), and in the BitNet setup the practical impact on attention calibration was small.

### How is SwiGLU implemented with 8-bit activations—do you dequantize around SiLU or keep everything integer?
Question:
In LLaMA-like MLPs, SwiGLU applies two linear projections followed by a SiLU gate and elementwise multiplication. With int8 activations, are the tensors entering SiLU upcast to FP16/BF16 for the nonlinear and then requantized, or are these kept purely in integer arithmetic? Did you observe any accuracy degradation specific to the SwiGLU gate under symmetric int8 activation quantization?
Answer:
Short answer: the paper does not explicitly say that they compute SiLU purely in integer or that they upcast to FP16/BF16 around the nonlinearity. What it does state is that activations are quantized to symmetric int8 per token (scaled to $[-Q_b,Q_b]$ to remove zero point) and that SwiGLU is used; it also reports that BitNet b1.58 matches FP16 baselines (from 3B up) and that “the majority of BitNet b1.58 is INT8 addition calculation.” The authors do not report any SwiGLU-specific accuracy drop under this symmetric int8 activation scheme, so whatever handling they used for SiLU did not cause a measurable loss at the model level.

Why this is ambiguous and what it means in practice. SwiGLU implements two linear projections and a gate: if $A=XW_a$ and $B=XW_b$ then the MLP output is
$$
Y = A \odot \mathrm{SiLU}(B),\qquad \mathrm{SiLU}(x)=x\cdot\sigma(x).
$$
When $A,B$ are stored as int8 with a scale $s$ (so the real value is $\hat v = s\cdot v_q$), evaluating $\mathrm{SiLU}(B)$ requires a nonlinear map on $\hat B$. There are two common practical strategies (both consistent with “8-bit activations” in the paper):

1) Dequantize around the nonlinearity: convert the int8 $B$ to FP16/BF16, compute $\mathrm{SiLU}(\hat B)$ in floating, then requantize the result back to int8. This is simple, low-risk for accuracy, and commonly used in PTQ/inference engineering; it does introduce some extra FP work and temporary memory overhead.

2) Integer-only SiLU: keep everything in integers by approximating the SiLU mapping with a small LUT, piecewise-linear/polynomial approximation, or integer sigmoid approximation, using the known symmetric per-token scale so the LUT/domain is small and symmetric. This preserves the full INT8 flow and maximizes runtime/energy benefits, but requires careful scale management and calibration because nonlinearities (and the subsequent elementwise gating) amplify quantization error if the approximation or scale is poor.

Which route the authors used is not specified. The paper’s decision to quantify activations to $[-Q_b,Q_b]$ per token (no zero point) is important: symmetry around zero makes integer LUTs or symmetric polynomial approximations much easier and less biased, and it reduces one common source of quantization error for gating nonlinearities. Their reported results (parity with FP16 at reasonable scales) imply their chosen solution—whether dequantize/compute/requantize or a carefully calibrated integer SiLU—worked well in practice, and they do not report SwiGLU-specific degradation.

If you are reproducing this work, the pragmatic path is to start by dequantizing around SiLU (FP16/BF16 compute for the nonlinear) because it is straightforward and preserves accuracy; then, if you need maximal INT8 efficiency for production/hardware, replace the float SiLU with a calibrated integer LUT or a small integer polynomial and verify no PPL/accuracy regression. To isolate the effect of the gate, run an ablation that quantizes only the MLP (or only the SiLU path) and compare perplexity—the paper does not provide such a microanalysis, but their overall results indicate no glaring SwiGLU failure under their symmetric int8 activation recipe.

### How does the Ladder 2-bit kernel implement ternary-weight matmuls with int8 activations—adds/subs only, or bit-serial tricks?
Question:
With weights in $\{-1,0,1\}$ and int8 activations, a straightforward approach would use add, subtract, or skip per weight. On GPUs, that could be branchy or bandwidth-bound. How does the Ladder 2-bit kernel realize this efficiently in practice? Do you encode ternary values as two binary masks (nonzero and sign) and fuse them with vectorized additions, or use popcount/XNOR-like techniques adapted from binary networks?
Answer:
Short answer: the BitNet paper itself does not spell out the inner loop of the Ladder 2‑bit kernel, but on modern GPUs the practical, high‑throughput implementations avoid per‑weight branching and fall into one of two families: (A) a packed‑weight + decode/fused GEMM path (i.e., store two 1‑bit masks and expand or fuse them into int8 tiles and run an INT8 GEMM / tensor‑core kernel), or (B) a bit‑serial/popcount path that bit‑packs activations and uses bitwise AND/popcount against weight sign/nonzero masks and accumulates across activation bitplanes. Both achieve “adds/subs only” at the mathematical level (because $w \in \{-1,0,1\}$ means $y = \sum_j w_j x_j = \sum_j 1_{w_j=1} x_j - \sum_j 1_{w_j=-1} x_j$), but they trade off memory traffic, number of passes, and which hardware primitives they lean on.

To make that concrete: write the ternary weight matrix $W$ as two bitmasks
$P = 1_{W=+1}$, $N = 1_{W=-1}$, so
$W = P - N$,
and a matmul $A W^T$ becomes $A P^T - A N^T$. One straightforward, branchless implementation is to keep $P$ and $N$ packed (2 bits per weight or two bitmaps), either issue two masked INT8 GEMMs (compute $A\cdot P^T$ and $A\cdot N^T$) or decode small tiles of $P/N$ into signed int8 $(-1,0,1)$ in shared memory and do a single fused INT8 GEMM that subtracts the negative contributions on the fly. This approach is friendly to NVIDIA’s tensor cores and the highly optimized INT8 GEMM paths in FasterTransformer: it minimizes the number of kernel launches and memory reads for activations (one pass over $A$), avoids branches, and reuses high‑throughput INT8 matrix multiply hardware.

The other canonical approach borrows from binary/bit‑serial techniques: decompose each int8 activation into bitplanes $a = \sum_{b=0}^{B-1} 2^b a^{(b)}$ (and handle the sign bit appropriately), pack many $a^{(b)}$ bits into machine words, then for each bitplane compute $\mathrm{popcount}(P \& A^{(b)})$ and $\mathrm{popcount}(N \& A^{(b)})$. The dot product is
$$\mathrm{dot}(W,a) = \sum_{b} 2^b\big(\mathrm{popcnt}(P \& A^{(b)}) - \mathrm{popcnt}(N \& A^{(b)})\big).$$
This uses very compact storage for weights (2 bits/wt) and very cheap bitwise+popcount ops, but it requires one pass per activation bit (so $B$ passes for $B$‑bit activations). On hardware where bitwise/popcount throughput is extremely high or where tensor cores are absent, bit‑serial can win; on modern GPUs with extremely fast INT8 GEMMs, the $B$‑pass overhead often dominates and makes decode+GEMM faster.

Which one does Ladder actually use? the BitNet paper only says “the 2‑bit kernel from Ladder is also integrated” and measures latency with FasterTransformer; it does not give the kernel source in the text. Given the integration target (FasterTransformer, NVIDIA GPUs) and the large measured speedups, the likely practical choice for Ladder’s GPU kernel is a packed 2‑bit representation with an on‑tile decode or a fused two‑mask computation that feeds high‑throughput INT8 GEMM/tensor‑core code (i.e., the “decode + fused GEMM” style). That design gives a single high‑throughput pass over activations, avoids branchy per‑weight add/sub logic, and maps well to the hardware primitives FasterTransformer exploits. Bit‑serial/popcount variants remain an attractive alternative on some hardware (or for very sparse $W$), but they typically need multiple bit‑plane passes for int8 activations and so are less common for GPU inference kernels tuned for tensor cores.

If you need definitive confirmation for the exact Ladder kernel used here, the quickest way is to inspect the Ladder kernel source or the FasterTransformer integration (the paper points to those codebases). If you want to prototype yourself, implement both: (1) a decode‑into‑int8 + INT8 GEMM fused kernel, and (2) a bit‑serial popcount kernel, and measure on your target GPU — that will show which dominates for your activation bitwidth, density of zeros in $W$, and batch/shape regime.

### 71.4x arithmetic energy savings claim: what op-energy constants, accumulator width, and memory costs were assumed?
Question:
You report that on 7 nm, BitNet b1.58 saves 71.4x arithmetic energy for matrix multiplications versus FP16. Can you list the per-op energy numbers used (e.g., FP16 multiply, FP16 add, int8 add, int32 accumulate), the assumed accumulator precision, and the operation mix per MAC? Was memory energy (reads/writes from SRAM/DRAM) included, or is 71.4x compute-only? A worked example for a representative GEMM shape would be very helpful.
Answer:
Short answer first: the  paper’s quoted “$71.4\times$” is an arithmetic-only (compute-only) estimate for matrix–multiply energy on a $7\ \text{nm}$ process using the energy model cited in the paper (they cite the energy model papers but do not publish a private table of per‑op constants or the exact accumulator width or the exact operation mix). The paper states they “estimate the arithmetic operations energy consumption of matrix multiplication” and then report the $71.4\times$ saving; it therefore does not include DRAM/SRAM transfer energy in that $71.4\times$ number. The paper also does not print the per‑operation numbers (e.g., exact pJ values) nor an explicit MAC‑level op mix breakdown, so you cannot find those constants inside the PDF — instead they point to the external energy models they used.

Because you asked for a reproducible explanation, below I (a) write the minimal, transparent algebra one should use to reproduce that kind of ratio, (b) give the typical operation mix that the paper implicitly assumes for FP16 vs. BitNet b1.58, (c) state the accumulator precision the design normally needs, and (d) give a worked numeric example (labelled “illustrative”) that shows how a $71.4\times$ number can arise when you plug in plausible per‑op energies from the literature cited by the paper.

What is being compared (operation mix)
For a dense MAC in a conventional FP16 matrix multiply the inner‑loop per multiply‑accumulate is one floating multiply plus one floating add (in hardware often a fused FMA). I will denote the per‑op energies $E^{FP16}_{mul}$, $E^{FP16}_{add}$. A single FP16 MAC energy (compute part) is then $E^{FP16}_{MAC} = E^{FP16}_{mul} + E^{FP16}_{add}$.
For BitNet b1.58 (ternary weights $\{-1,0,1\}$ with 8‑bit activations) a single inner product element is implemented as “if $w=0$: skip; if $w=+1$: add $a$; if $w=-1$: subtract $a$.” That means the hot inner operation is an integer add/sub and the accumulation must be performed into a wider integer accumulator. The per‑element cost (for a nonzero weight) is therefore dominated by an integer add/sub on the activation type plus the cost of the accumulator update. I will denote these energies $E^{INT8}_{add}$ (cost to add an 8‑bit value into the accumulator path) and $E^{INTacc}_{add}$ (cost of the accumulator update at its working width). If the implementation uses bit‑packing + bitwise/popcount primitives to compute many dot‑products in parallel (typical for binary/ternary kernels), the effective per‑element energy can be even lower — the paper’s references and the Ladder 2‑bit kernel they use point in that direction.

Accumulator width and why int32 is typical
The paper specifies 8‑bit activations and ternary weights. If activations are in the signed 8‑bit range (roughly $\pm 127$) and the dot length (inner dimension) is $K$, the maximum absolute sum is bounded by $K\cdot 127$, so the number of bits required is $\lceil \log_2(127K + 1)\rceil$. For typical Transformer inner‑dims ($K$ in the thousands) this requires $\sim 18$–$22$ bits, so designers ordinarily use a 32‑bit integer accumulator (int32) for headroom and to avoid overflow. The paper does not state a different accumulator width, so int32 is the reasonable assumption and the usual one used in energy comparisons.

How to compute the compute‑only energy for one output dot (transparent algebra)
If $K$ is the dot length and $d$ is the fraction of weights that are nonzero ($d\le 1$; ternary has some zeros which reduce work), the compute energy per output element is

$$
E_{out}^{FP16} = K \cdot E^{FP16}_{MAC} = K\cdot\left(E^{FP16}_{mul} + E^{FP16}_{add}\right),
$$

$$
E_{out}^{BitNet} = K \cdot d \cdot\left(E^{INT8}_{add} + E^{INTacc}_{add}\right) + E_{scale},
$$

where $E_{scale}$ is the small cost of applying the per‑row/column scale (the paper’s quantization uses a scalar $\gamma$ per weight block — that scalar multiply can be hoisted out of the inner loop and is negligible relative to $K$ MACs). The arithmetic‑only speedup/savings ratio is

$$
\text{Savings} = \frac{E_{out}^{FP16}}{E_{out}^{BitNet}} \approx \frac{K\cdot E^{FP16}_{MAC}}{K\cdot d\cdot E^{Bit}_{MAC}} = \frac{E^{FP16}_{MAC}}{d\cdot E^{Bit}_{MAC}},
$$

where I used $E^{Bit}_{MAC} := \left(E^{INT8}_{add} + E^{INTacc}_{add}\right)$. (If you use a bit‑packed popcount implementation, replace $E^{Bit}_{MAC}$ by the amortized per‑element cost of the bitwise/popcount sequence; that is the key lever that can drive the large factors.)

Was memory energy included?
No — the $71.4\times$ number in the paper is explicitly an arithmetic (compute) energy comparison for matrix multiplication. The paper separately discusses memory/bandwidth savings (smaller weights / lower bandwidth) but the $71.4\times$ figure is the compute‑only arithmetic estimate, not an end‑to‑end (DRAM+SRAM+compute) energy number. If you want an end‑to‑end energy ratio you must add the memory transfer energies (weight reads, activation reads/writes, writebacks), and the final savings will generally be smaller than the compute‑only figure (but BitNet also reduces memory energy thanks to much smaller weight size and lower bandwidth).

An illustrative worked example (reconstruction)
The paper does not print the atomic pJ numbers it used, so the following is a reproducible reconstruction (explicitly flagged as illustrative) using plausible per‑op energies taken in the spirit of the cited energy models. Plugging different per‑op constants (from the cited refs or measured silicon) will change the result; this shows how the arithmetic $71.4\times$ can be produced.

Assumptions (illustrative, not verbatim from the paper):
$E^{FP16}_{mul} = 1.20\ \text{pJ}$, $E^{FP16}_{add} = 0.30\ \text{pJ}$ so $E^{FP16}_{MAC} = 1.50\ \text{pJ}$.
$E^{INT8}_{add} = 0.007\ \text{pJ}$, $E^{INT32}_{add} = 0.014\ \text{pJ}$ so $E^{Bit}_{MAC} = 0.021\ \text{pJ}$.
Take $d = 1$ (no zeros) for a worst‑case per‑element cost; as soon as $d<1$ the BitNet cost drops proportionally.
Pick $K = 4096$ (a realistic Transformer inner‑dim for a large FFN).

Compute per‑output energy:
$$
E_{out}^{FP16} = K\cdot 1.50\ \text{pJ} = 4096 \times 1.50\ \text{pJ} = 6144\ \text{pJ} = 6.144\ \text{nJ}.
$$

$$
E_{out}^{BitNet} = K\cdot 1 \cdot 0.021\ \text{pJ} = 4096 \times 0.021\ \text{pJ} = 86.016\ \text{pJ} = 0.086016\ \text{nJ}.
$$

$$
\text{Ratio} = \frac{6.144\ \text{nJ}}{0.086016\ \text{nJ}} \approx 71.4.
$$

So with these per‑op constants and $K=4096$ the arithmetic energy ratio is $71.4$. If you use a nonzero density $d<1$ (i.e., some weights are $0$), replace $E_{out}^{BitNet}$ by $d\cdot(\text{the value above})$ and the ratio grows by $1/d$. If the BitNet kernel is using bit‑packing+popcount primitives the amortized $E^{Bit}_{MAC}$ can be lower than the simple INT8+INT32 add numbers I used here, and that also increases the ratio.

What to do to reproduce the exact paper number
Because the authors rely on the energy models in the cited refs but do not publish a table of the constants they actually plugged in, the only way to get *their exact* constants is to (a) examine the cited energy‑model papers [energycost, pokebnn] and use the same process‑scaling and the same assumptions (FMA counted as one or two ops, whether they amortized a scale multiply outside the inner loop, whether they assumed bit‑packed popcount implementations), or (b) ask the authors for the exact table. The algebra above shows exactly which quantities you need:

$E^{FP16}_{mul}$, $E^{FP16}_{add}$, $E^{INT8}_{add}$, $E^{INTacc}_{add}$, $K$ (inner dim), $d$ (nonzero weight fraction), and whether the BitNet primitive is implemented as scalar INT8 adds or as amortized bit‑packed popcount operations.

### KV cache precision and "lossless compression to 4 bits": is the cache currently 8-bit, and what does "lossless" mean?
Question:
The paper claims 8-bit activations reduce KV cache size and that it can be "losslessly compressed" to 4 bits or lower. Are $K$ and $V$ currently stored as int8 during decoding? By "lossless to 4 bits", do you mean entropy coding that preserves exact int8 values, or an additional quantization that shows negligible accuracy loss (i.e., not truly lossless)? If entropy coding is intended, what compression ratios and runtime overheads do you observe?
Answer:
Short answer: the paper states that BitNet b1.58 uses 8‑bit activations, so the logical K and V activations in the KV cache are quantized to 8 bits in their experiments; the phrase “losslessly compressed to 4 bits (or lower)” is aspirational/future work in the paper and is ambiguous — it could mean true bit‑level lossless compression (entropy coding of the int8 values down to an average of 4 bits/value) or it could be shorthand for “we can further reduce the stored representation to 4 bits in practice without hurting model quality” (which would be a lossy quantization that’s empirically benign). The paper does not present implementation details, compression numbers, or runtime measurements for the 4‑bit claim.

Why I say that: the paper explicitly says the model is trained and run with 8‑bit activations (so K/V are 8‑bit activations), and then adds in the discussion that those 8‑bit activations “can be further losslessly compressed to 4 bits or even lower … which we leave as future work.” Because the compression statement is in the “future work” part, no experimental evidence or method is given.

What “lossless” would mean in the two senses and the implications
There are two different technical readings of “losslessly compressed to 4 bits” and they have very different requirements.

1) True lossless (bit‑exact recovery): this means you store the current 8‑bit quantized K/V values in a compressed form and can recover exactly the original 8‑bit values when needed. Information‑theoretically this is only possible on average if the empirical entropy of the 8‑bit symbols is $\le 4$ bits. If X is the discrete distribution of the quantized activations, the Shannon lower bound is
$$H(X) = -\sum_x p(x)\log_2 p(x),$$
and any lossless coder must use on average at least $H(X)$ bits per symbol. So to get an average of 4 bits/value you need $H(X) \le 4$. Practically this can be achieved by techniques like ANS/arithmetic coding, Huffman coding, delta or run‑length schemes, or packing if the alphabet is small (e.g. if only 16 distinct symbols appear then a fixed 4‑bit packing is exact). The cost of true lossless coding is that general entropy decompressors (ANS, range coder) add compute and branching overhead; a simpler route is block‑wise nibble (4‑bit) packing if the values truly live in a 16‑level alphabet, which is cheap to unpack with vectorized bit ops.

2) “Lossless” as “no observable accuracy loss”: authors sometimes mean “we can quantize further to 4 bits without degrading perplexity/accuracy.” That is not lossless in a bit‑exact sense — it is lossy quantization that happens to preserve downstream metrics. This is typically done by designing a 4‑bit quantization scheme (per‑block/per‑head scaling, bias correction, fine‑tuning/GPTQ style methods) and verifying task performance. The runtime overhead is lower because the representation is native 4‑bit (you can implement kernels that read packed 4‑bit values directly) rather than decompressing an entropy stream.

Practical tradeoffs and what to measure (why the paper is silent)
Because the paper does not give measurements for 4‑bit KV caching, you need to evaluate two things if you want to follow up: (a) compressibility of the existing 8‑bit K/V values and (b) runtime/latency cost to decode/use them during autoregressive decoding. To decide which approach is realistic you should measure the empirical distribution of the quantized K/Vs (compute a histogram and entropy $H(X)$). If $H(X)$ is substantially below 8 bits and near or below 4 bits you can consider lossless entropy coding. If not, evaluate a 4‑bit lossy quantization and measure model quality.

A few implementation notes that affect performance and overheads: if you scale activations per token or per small block (the paper scales per token), you must also store the scale(s) alongside compressed data; those scale bits are overhead amortized over the block size (if a scale uses $s$ bits and you store it every $B$ values then add $s/B$ bits/value to the budget). Bit‑packing to 4 bits (two values per byte) is cheap to implement on GPU/CPU and has very low unpack cost; entropy coding (ANS / Huffman) can achieve lower average bits but requires a heavier decompression step which can add latency unless carefully engineered (blockwise ANS plus parallel decoding can help). Also consider access pattern: autoregressive decoding repeatedly reads small slices of the KV cache (per‑head, per‑token), so decompression cost must be paid for the slice sizes you actually need — decompressing the whole cache per token would kill latency savings.

How to experimentally validate (quick recipe)
Collect a representative dump of quantized K and V tensors from decoding, compute the empirical pmf and $H(X)$. Try three simple experiments: (i) naïve 4‑bit fixed packing (if the alphabet is $\le 16$ or you apply a simple per‑block remapping) and measure accuracy and unpack speed; (ii) ANS/Huffman on blocks of reasonable size (say thousands of elements) and measure compressed size and decode throughput; (iii) a lossy 4‑bit quantization (per‑head or per‑token scale) and measure downstream perplexity/accuracy and decoding throughput with custom kernels. Report average bits/value, end‑to‑end token latency, and extra memory for scales/headers.

Conclusion
In short: the KV cache in the paper is produced from 8‑bit activations (so K/V are 8‑bit in their experiments). The “losslessly compressed to 4 bits” line is a forward‑looking claim without details — it could mean true entropy coding (exact recovery) or further 4‑bit quantization that doesn’t hurt accuracy, and the paper doesn’t report compression ratios or runtime numbers. To resolve this concretely you need to (1) compute the empirical entropy of your K/V tensors and (2) benchmark both fast nibble‑packing and entropy decoders (or direct 4‑bit quant kernels) to trade off memory saving vs. added latency; the Shannon bound $H(X)$ is the right quantitative test for whether a *true* lossless 4‑bit average is even possible. If you want, I can sketch code to measure $H(X)$ on your K/V dumps or show a small GPU‑friendly nibble‑packing/unpacking kernel to try.

### Why does parity with FP16 emerge only around 3B parameters—what breaks at smaller scales?
Question:
Results suggest BitNet b1.58 starts to match FP16 LLaMA around 3B parameters. For 1B or smaller, is the gap driven by representational limits of ternary weights, optimization challenges (e.g., gradient noise with heavy quantization), or architecture hyperparameters tuned for FP16? Any ablations that vary width vs depth at fixed parameter count, or adjust MLP expansion/attention head counts, to isolate the capacity most affected by ternary constraints?
Answer:
Short answer: the paper itself does not run the targeted ablations you ask for, but the text and results strongly point to a combination of (1) representational limits introduced by coarse ternary quantization (especially the per‑matrix absmean scaling), and (2) optimization / robustness effects that large, overparameterized models tolerate much better than small ones. Using LLaMA‑style hyperparameters “as is” for ternary training is a deliberate fairness choice in the paper, but it also means any small‑model mismatch from FP16 hyperparameters is left uncorrected — the authors report no width‑vs‑depth or MLP/attention head ablations to isolate which capacity modes fail first.

Why this is a plausible decomposition (grounded in what the paper reports)

The paper’s quantizer is explicitly coarse: they compute
$$\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|$$
and then map each entry to the nearest element of $\{-1,0,1\}$ after scaling: roughly
$$q_{ij}=\mathrm{RoundClip}\!\left(\frac{W_{ij}}{\gamma+\epsilon},-1,1\right),$$
so the stored pattern is effectively a ternary mask and a single scale per weight matrix (the paper describes this as “scale by average absolute value, then round to $\{-1,0,1\}$”). That design is extremely parameter‑efficient, but it also creates a coarse per‑element approximation error
$$E_{ij}=W_{ij}-\gamma q_{ij},$$
and that error is a larger fraction of the signal when (a) the matrix is small, (b) the per‑matrix scale poorly matches per‑channel amplitudes, or (c) the task requires fine continuous weight magnitudes. The paper also notes that matrix multiplies (i.e. the linear layers) are the dominant computation and thus are the primary place this quantization acts.

Two consequences follow and explain the 3B threshold:

1) Representational limit: small models have fewer parameters and less redundancy, so a three‑level per‑matrix quantizer cannot approximate many useful continuous transforms as well. In larger models there are many more ternary degrees of freedom to combine and approximate finer functions (redundancy + overparameterization acts like a “smoother” that hides coarse quantization). The paper’s empirical curve — the gap shrinking with size and parity appearing around 3B — matches this redundancy explanation.

2) Optimization / robustness: extreme quantization makes training dynamics harder (biased / noisy gradients when using discrete weights or STE variants). Large models are empirically and theoretically more robust to noisy / biased updates because they can find many parameterizations that implement the same function; small models have to be more “precise” and so noisy gradients or quantization bias more easily prevent finding a good solution. The paper trains BitNet b1.58 from scratch and reports that performance gap narrows with scale, which is consistent with an optimization/robustness effect that is ameliorated by scale.

Role of LLaMA hyperparameters: the authors intentionally use LLaMA‑alike components and “the same configuration” for fair FP16 vs 1.58‑bit comparisons. That makes the comparison clean but does not explore whether alternative width/depth/MLP expansion/head counts would be better for quantized small models. The paper does not report ablations that change width vs depth at fixed parameter count, nor MLP expansion or per‑layer micro‑architecture tuning targeted at ternary weights.

What an informative ablation would look like (and what each outcome would imply)

If you run fixed‑parameter experiments that vary width vs depth, vary the MLP expansion ratio, or vary number/size of attention heads, you can separate representational vs optimization causes. If widening (more neurons per layer with fewer layers) at fixed total parameters closes the gap at 1B, that points to a representational / redundancy problem — ternary weights need more parallel degrees of freedom to approximate fine functions. If deeper architectures (more layers, thinner width) become *worse* under ternary quantization, that suggests discretization error compounds through layers or makes optimization harder. If per‑channel or per‑row scaling (instead of a single per‑matrix $\gamma$) fixes most of the gap, that implicates the coarse absmean scaling as the bottleneck. If optimization‑oriented fixes (longer training, different optimizers, distillation from an FP16 teacher, or techniques that reduce gradient bias/noise) help most, that implicates optimization dynamics.

Practical signals you can measure: per‑layer quantization error norms, training loss trajectories (noisy vs smooth), sensitivity of final accuracy to freezing certain layers in FP16, and whether instability is reduced by increasing activation precision (the paper uses 8‑bit activations, which already helps).

Bottom line: according to the paper, parity at ~3B is an empirical scaling phenomenon; the paper provides the quantizer design (per‑matrix absmean + ternary levels), the training recipe (from‑scratch, 8‑bit activations, LLaMA‑alike config), and the scaling results, but it does not provide the ablations needed to conclusively attribute the small‑model gap to only one cause. My best reading of the evidence in the paper is that representational limits of coarse ternary quantization (amplified by per‑matrix scaling) are the primary cause, with optimization/gradient‑noise issues and unchanged FP16 hyperparameters also contributing — and that carefully targeted ablations (width vs depth, per‑channel scaling, keeping critical layers in higher precision, or distillation/optimizer changes) would be the right next experiments to pinpoint the dominant factor for 1B and smaller models.

### How much ternary-induced sparsity do you observe, and is it exploited for speed on current GPUs?
Question:
Allowing $0$ in $\{-1,0,1\}$ should induce weight sparsity. What fraction of weights are zero per layer at convergence (mean, variance across layers), and how does this differ between attention and MLP blocks? Does your kernel actually skip arithmetic for zeros to gain speedups, or are current GPU paths effectively dense so sparsity only helps conceptually (e.g., for future hardware)?
Answer:
Short answer: the paper does not report per-layer zero fractions, and the measured speedups are not coming from skipping arithmetic on zeros — they come from using dense low-bit kernels (FasterTransformer + a Ladder 2-bit kernel) and lower-bandwidth / integer arithmetic. The ternary zeros are therefore primarily a modeling/representation advantage in this work and a promising lever for future hardware or specialized sparse kernels, but they were not exploited as dynamic zero-skipping on current GPUs in the reported results.

Why the paper doesn’t give a numbers table: BitNet b1.58 enforces
$$\widetilde{W} = \mathrm{RoundClip}\!\left(\frac{W}{\gamma+\epsilon},-1,1\right)$$
with $\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|$. An entry becomes 0 exactly when $\left|\frac{W_{ij}}{\gamma+\epsilon}\right|<0.5$, i.e. $|W_{ij}|<0.5(\gamma+\epsilon)$.
So the per-layer zero fraction is simply $p_0^{(layer)}=\frac{1}{nm}\sum_{ij}\mathbf{1}\!\big(|W_{ij}|<0.5(\gamma+\epsilon)\big)$.
Because the paper does not print these $p_0$ statistics (mean/variance per layer or broken out by attention vs MLP), we cannot give concrete numbers from the paper itself. If you want to measure it yourself from checkpoints, compute $\gamma$ per weight matrix and evaluate that indicator to get exact per-layer means and variances (and then average over attention vs MLP blocks).

Intuition about where zeros are likely to live: the fraction depends entirely on the empirical weight distribution after training. For many heavy‑tailed distributions, absmean ($\gamma$) is a natural scale and a substantial fraction of weights can fall into the small interval that rounds to zero, so nontrivial sparsity is plausible. It is common in practice (outside this paper) for MLP / feed‑forward matrices to admit higher “redundancy” and thus higher zero rates than projection matrices in attention, but that is an empirical claim — the paper does not report that breakdown.

Why the reported speedups do not rely on zero‑skipping: the paper states that latency/memory/throughput were measured using FasterTransformer with an integrated Ladder 2‑bit kernel. Those are packed low‑bit dense GEMM implementations: they reduce memory transfer and use optimized low‑bit integer arithmetic (and special bit‑packing tricks), which is how the paper achieves the 2–4× latency speedups and large throughput/memory gains (for example, 2.71× faster at 3B and 4.1× at 70B as reported). They explicitly note “Both latency and memory were measured with a 2‑bit kernel, so there is still room for optimization,” which signals that no additional zero‑skipping sparse kernel was used for extra wins.

Practical system point of view: current GPUs are massively optimized for dense GEMMs; unstructured (irregular) sparsity is hard to accelerate because index/indirection overhead and irregular memory accesses often erase the theoretical FLOP savings unless sparsity is very high or structured (e.g., block or N:M sparsity with hardware support). So on today’s GPU paths the main payoffs come from lowering bit‑width and packing weights, not from skipping operations for every zero. That is why the paper emphasizes both algorithmic benefits (better modeling via a zero state) and the prospect of new hardware or sparse‑aware kernels (Groq/LPUs and similar) to harvest additional speed/energy gains later.

If you want to exploit the zeros in practice: measure $p_0^{(layer)}$ as above, then (a) if you get very high and structured sparsity consider training with structured sparsity objectives (block / N:M) so existing sparse GEMM paths or hardware primitives can be used; (b) for irregular sparsity you’ll need custom masked GEMM kernels or a specialized accelerator to get net wins; (c) alternatively, treat the ternary weights as packed sign/mask representations and explore bit‑packed sparse formats that a custom kernel or ASIC could exploit (the paper calls out new hardware as future work).

Summary: the paper adds a zero state and thereby induces measurable sparsity in principle, but it does not publish per‑layer sparsity numbers; the speedups reported are achieved by dense low‑bit kernels (2‑bit packed implementations and reduced memory/INT arithmetic), not by dynamically skipping arithmetic on zeros.

### Why compare mainly to FP16 rather than strong 3–4 bit quantized baselines (e.g., AWQ, GPTQ)?

Given that 4-bit post-training quantization with int8 activations is widely used, it would be informative to compare BitNet b1.58 to well-tuned 3–4 bit PTQ/QAT baselines on both accuracy and decode-time latency/memory. Do your Pareto gains hold against these baselines, especially at 3B–13B scales?

The paper does cite PTQ work (GPTQ, AWQ, etc.) and acknowledges PTQ is widely used, but it does not include head‑to‑head results against carefully tuned $3$–$4$ bit PTQ/QAT baselines, so you cannot conclude from the paper alone whether the stated Pareto gains still hold versus those methods. Why FP16 was chosen as the principal baseline

PTQ methods start from a working FP16 model and try to compress it post hoc; that is a different workflow (and a different claim). Also, an apples‑to‑apples comparison against PTQ requires matching the runtime stack and optimized kernels for each quantization scheme, which the paper did not attempt to exhaustively do.

Why PTQ / $3$–$4$ bit baselines are a different beast
Post‑training quantization (GPTQ, AWQ, Quip, etc.) operates on a trained FP16 checkpoint and uses blockwise/per‑channel quantizers, outlier handling, SmoothQuant, and other heuristics to preserve accuracy. Those methods typically (a) store extra per‑block scale/zero‑point metadata, (b) sometimes dequantize blocks at runtime or rely on specific integer GEMM kernels, and (c) often leave activations / KV cache in higher precision unless you explicitly quantize them. By contrast BitNet b$1.58$ is trained from scratch with ternary weights and $8$‑bit activations, and the inference code in the paper uses an integrated $2$‑bit kernel (Ladder) in FasterTransformer. So the two approaches differ not only in bitcount but also in where quantization is applied, what kernels are used, and what metadata/overheads appear at runtime.

Quick quantitative intuition about memory
Raw weight storage scales linearly with bits. Four‑bit weights use $4/8=0.5$ bytes per parameter; $1.58$ bits is $1.58/8\approx0.1975$ bytes per parameter, so the weight array alone is about
$$
\frac{0.1975}{0.5}\approx0.395
$$
of the $4$‑bit weight size, i.e. roughly a $2.53\times$ reduction in weight bytes versus $4$‑bit. In practice total GPU memory includes embeddings (kept FP16 in the paper), activation/KV cache memory, optimizer states (for training), and scale metadata for PTQ blocks, so the real end‑to‑end memory ratio will be smaller than the raw bit ratio.

Why runtime (latency) comparisons are subtle
Latency depends on more than bitwidth: kernel implementation, whether multiply‑accumulate remains (int8 MAC) or operations reduce to add/sub/skip for ternaries, memory bandwidth, and whether you must dequantize on the fly. BitNet’s integer‑addition heavy compute (ternary multiply becomes add/sub/zero) can be much cheaper in energy and amenable to specialized hardware; on current GPUs, however, highly optimized int4/int8 kernels (bitsandbytes, AWQ/GPTQ runtimes, vendor libraries) can be extremely fast and may narrow the latency gap. Thus whether BitNet maintains a Pareto edge in latency versus best‑in‑class $3$–$4$ bit PTQ depends critically on kernel maturity and how activations/KV are quantized at inference.

How to do a fair head‑to‑head comparison (what the paper did not report)
To settle the question experimentally you should (1) start from the same FP16-pretrained model used in the paper, (2) apply state‑of‑the‑art PTQ (AWQ and GPTQ) with recommended settings (per‑channel / block sizes, SmoothQuant if appropriate, activation handling), (3) run inference in the same runtime (e.g., FasterTransformer or vLLM) with optimized kernels for each quantization scheme, (4) measure the same accuracy metrics (perplexity and the same zero‑shot tasks), and (5) report end‑to‑end decode metrics: time per output token, peak GPU memory including KV cache at target context lengths, throughput at same batch/seq settings, and any scale metadata overhead. If you want energy comparisons, either measure wall‑power during runs or apply the same energy model used in the paper for consistency. Only then can you say whether BitNet’s Pareto points still dominate.

Reasonable expectations (but not definitive claims)
Because BitNet trains ternary weights and reduces activations to $8$‑bit everywhere, you should expect it to have a clear advantage on weight storage and (potentially) KV cache memory if you quantize KV there. At small model sizes (e.g., $3$B) PTQ methods sometimes degrade accuracy more than at larger sizes; since the paper reports BitNet matches FP16 starting at $3$B, BitNet may outperform PTQ at that scale on accuracy. At larger sizes ($7$–$13$B) modern $4$‑bit PTQ methods have shown strong accuracy preservation in many reports, so the accuracy gap could vanish and the comparison will hinge on kernel throughput and whether PTQ keeps activations/KV in high precision. If PTQ keeps KV/activations at FP16 while BitNet uses $8$‑bit, BitNet will likely keep a memory advantage. But if PTQ integrates optimized int4 int8 kernels and also compresses activations/KV, the latency and memory gaps may shrink—how much depends on implementation details and hardware.

Bottom line
The paper demonstrates a strong and important point—end‑to‑end training at $1.58$ bits can match FP16 accuracy while substantially reducing resource use—but it does not present the specific head‑to‑head with best‑in‑class $3$–$4$ bit PTQ/QAT baselines. ### Is $\gamma$ recomputed each forward pass per matrix, and how sensitive is training to $\epsilon$ or to using a moving average?
Question:
In $\tilde{W}=\mathrm{RoundClip}(W/(\gamma+\epsilon),-1,1)$ with $\gamma=\text{absmean}(W)$, do you recompute $\gamma$ from the current real-valued $W$ each step, or maintain an EMA across steps to stabilize scaling? What value do you use for $\epsilon$, and how sensitive are results to it? Did you try median/percentile-based scales to reduce outlier effects?
Answer:
Short answer: the paper defines $\gamma$ as the per-matrix average absolute value $\gamma = \frac{1}{nm}\sum_{ij}|W_{ij}|$ and uses it in the quantizer $\widetilde W=\mathrm{RoundClip}\big(W/(\gamma+\epsilon),-1,1\big)$. That formulation implies $\gamma$ is taken from the current real-valued $W$ when you quantize (i.e. recomputed from the current weights per matrix at quantization time). The paper does not report using an EMA for $\gamma$, does not give a numeric value for $\epsilon$, and does not report experiments with median/percentile-based scales or an ablation on $\epsilon$.

Why this matters and what to watch for: recomputing $\gamma$ every forward makes the quantizer adapt immediately to the current weight distribution. The rounding-to-zero condition is transparent from the formula: a weight becomes zero when
$$
\left|\frac{W_{ij}}{\gamma+\epsilon}\right|<0.5
\quad\Longleftrightarrow\quad
|W_{ij}|<0.5(\gamma+\epsilon).
$$
Because $\gamma$ is the mean absolute value, a few large outliers will inflate $\gamma$, raise that threshold, and therefore cause more (moderate) weights to quantize to zero. That is the principal robustness trade-off: mean-based scaling is simple and cheap, but sensitive to outliers.

About $\epsilon$: the paper includes $\epsilon$ only as a numeric stabilizer in the formula and does not state its value or report sensitivity studies. In practice $\epsilon$ only matters when $\gamma$ is comparable to or smaller than $\epsilon$; if $\epsilon \ll \gamma$ it has negligible effect. Typical engineering choices (outside this paper) are tiny constants like $10^{-6}$–$10^{-8}$ or using a relative floor (e.g. $\epsilon = \alpha\cdot\mathrm{max}(\gamma, \mathrm{something})$). The authors do not report that their results are sensitive to $\epsilon$, but they also did not publish an explicit sweep.

About using an EMA for $\gamma$: the paper does not mention maintaining a moving average. An EMA would smooth step-to-step fluctuations in scale (possibly stabilizing early training or reducing jitter in per-step sparsity), but it also introduces lag (the scale can be slow to follow genuine changes in weight magnitude). Recomputing $\gamma$ each forward is simplest and ensures the quantization threshold tracks the current parameter distribution; using an EMA is a reasonable implementation variant if you observe instability, but it is not what the paper reports.

About median/percentile-based scales and other robust alternatives: the paper does not report trying median or percentile scaling. Conceptually, replacing $\gamma=\mathrm{absmean}(W)$ with a robust statistic such as $\mathrm{median}(|W|)$ or a trimmed mean/percentile can reduce the influence of outliers and therefore avoid the inflated-zero problem described above. The trade-offs are that robust statistics may change the overall sparsity pattern and dynamic range used by the ternary mapping, and they may be slightly more expensive to compute (percentile/median is costlier than a mean unless approximated). If you see too much sparsity caused by occasional large weights, a median or trimmed-mean scale is a natural experiment to run.

A practical implementation checklist (recommended experiments, not claimed results from the paper): recompute $\gamma$ per-matrix per-quantize as in the paper to match their setup; if training is noisy try either detaching the computed $\gamma$ from the gradient graph (so scale is not backpropagated through) or maintain an EMA of $\gamma$ with a high decay ($0.99$–$0.999$) and compare; pick a very small $\epsilon$ (e.g. $10^{-6}$) as a default and test larger values only if $\gamma$ sometimes goes to zero; if outliers are creating undesired sparsity, try median or a percentile-based scale or a clipped mean.

If you want, I can sketch code for the four variants (per-forward recompute, recompute+detach, EMA, median scale) and show how to monitor induced sparsity and per-layer thresholds so you can compare empirically.

### What accumulator precision is used for the int8-by-ternary dot products, and how do you prevent overflow?
Question:
With int8 activations in $[-127,127]$ and weights in $\{-1,0,1\}$, the worst-case dot product magnitude is $127d$ for length $d$. For typical widths (e.g., $d=8192$), this fits in int32 but not int16. Do your kernels accumulate in int32 and then rescale, and are there any intermediate downscales or blocking strategies to guard against overflow in very wide layers?
Answer:
Short answer: the paper does not explicitly state the accumulator width at the kernel level, but everything in the paper (and the facts you listed) strongly indicates the implementation uses 32-bit integer accumulation and then rescales to floating point. Int32 accumulation is the standard choice for int8$\times\{-1,0,1\}$ GEMMs (and is what FasterTransformer / typical GPU int8 paths do), and it is sufficient for the LLM inner dimensions used in the paper without any extra intermediate downscaling.

Why that is safe and how it is done (intuitively + a few formulas). With 8‑bit activations quantized to integers in $[-127,127]$ and ternary weights in $\{-1,0,1\}$, the worst‑case absolute value of a dot product of length $d$ is
$$
\max |\,\text{dot}\,| = 127\cdot d.
$$
For a typical hidden dimension $d=8192$ this is $127\cdot8192=1\,040\,384$, which is tiny compared to the signed 32‑bit range. In fact the largest $d$ you can handle before a signed 32‑bit accumulator overflows is
$$
d_{\max}=\left\lfloor\frac{2^{31}-1}{127}\right\rfloor\approx 16{,}909{,}320,
$$
so all usual Transformer widths (4k, 8k, etc.) are well inside the safe region. By contrast a 16‑bit accumulator (max 32767) only supports $d\le\lfloor32767/127\rfloor\approx 258$, so int16 would not work for typical LLM dims.

How the quantized pipeline maps to accumulation and scaling (matches the paper’s quantization math). The paper quantizes weights as
$$
\widetilde W=\operatorname{RoundClip}\!\bigl(W/(\gamma+\epsilon),-1,1\bigr)
$$
so the real (FP) weight is recovered approximately as $(\gamma+\epsilon)\widetilde W$. Activations are quantized per token to integer values $q_a\in[-Q_b,Q_b]$ (with $Q_b=127$ for 8‑bit). A kernel therefore computes an integer accumulator
$$
S=\sum_i q_{a,i}\,q_{w,i}\quad (q_{w,i}\in\{-1,0,1\}),
$$
and the floating output is formed by a single rescale
$$
\text{output} = S\cdot s_a\cdot s_w \;+\;\text{(bias)}\!,
$$
where $s_a$ and $s_w$ are the activation and weight scales (the paper’s per‑token activation scale and the $\gamma+\epsilon$ weight scale). So you accumulate purely in integers (avoiding FP multiplies inside the inner loop) and do one fused multiply by the two scales after accumulation.

Overflow mitigation and practical alternatives. For the layer sizes used in this work, no special intermediate downscaling is required because an int32 accumulator is large enough. If you ever need to support extremely wide dot products (approaching millions of terms) or a different activation range, common practical strategies are: (1) chunk (tile) the input dimension and accumulate partial int32 sums per chunk, converting/rescaling them to float and summing the floats across chunks; (2) use pairwise or Kahan‑style summation only to control numerical error (not overflow); (3) fall back to int64 accumulation if you truly need a larger integer range (but that is slower); or (4) choose a smaller quantization range (reduce $Q_b$) or apply deliberate block scaling so each block’s partial sum fits comfortably in int32. Any of these are standard engineering tradeoffs; the paper does not report using special blocking because it is unnecessary for their chosen dimensions.

One implementation note tied to the paper: they measured latency with the FasterTransformer codebase and integrated a 2‑bit kernel from Ladder. Both of those GPU quantized paths follow the usual convention of int8 inputs producing int32 accumulators and then converting/rescaling, so that is the most likely kernel behavior behind the paper’s claims.

If you are implementing this yourself, the simplest correct approach that matches the paper is: accumulate into signed int32, then apply the two scale factors (weight scale and per‑token activation scale) in FP (or fused FP16/BF16 if you prefer) to produce the output. No intermediate downscales are needed for typical LLM widths; only consider chunking/int64 if you have an unusually huge inner dimension.

### What drives the larger speedups at bigger model sizes—compute-bound vs memory-bound effects?
Question:
You report that speedup increases with model size (e.g., 4.1x at 70B). Is this mainly because a larger fraction of time is spent in BitLinear GEMMs as depth/width grow (shifting to compute-bound where int8 adds excel), or because bandwidth pressure is reduced by smaller weights? Do you have a roofline-style analysis contrasting FP16 vs ternary across sizes to illustrate the regime shift?
Answer:
Short answer: both effects matter, but the dominant reason the reported speedup grows with model size is that larger models spend a bigger fraction of their runtime in large nn.Linear GEMMs (so you get a bigger payoff from accelerating those ops). Quantization (1.58-bit weights, 8-bit activations / 2-bit kernels used in the measurements) amplifies that payoff in two ways: it (1) reduces bytes transferred from DRAM (raising arithmetic intensity and shifting some kernels out of the memory‑bound regime) and (2) replaces costly FP16 multiply–add work with much cheaper integer additions on the optimized kernel side (raising the effective compute ceiling). The paper does not include a formal roofline plot, but the text and measurements (e.g., $\sim 2.7\times$ at small sizes up to $4.1\times$ at 70B, large throughput increases because batch sizes fit in memory) are consistent with the two mechanisms combining and reinforcing each other as model size grows.

Why that combination matters (intuitively and technically). A dense GEMM of shapes $(m,n,k)$ does about $F=2mnk$ floating‑point MACs and must move roughly $B\approx m k\cdot s_A + k n\cdot s_B + m n\cdot s_C$ bytes (where $s_\cdot$ are bytes per element for the operands/outputs). The arithmetic intensity is $AI=\dfrac{F}{B}$. In a roofline model you compare $AI$ to the machine threshold $\dfrac{P_{\text{peak}}}{\text{BW}}$ (peak compute divided by peak bandwidth). If $AI$ is below that threshold your kernel is memory‑bound; above it you are compute‑bound. Quantizing weights from 16 bits to roughly 1.58 bits (and activations to 8 bits) reduces the bytes term $B$, which increases $AI$ and therefore tends to move GEMMs to the right on a roofline plot. At the same time, the optimized 2‑bit/INT8 kernels used here have a much higher practical throughput per byte or per clock for the operations they perform than the FP16 baseline, so the effective compute roof for the quantized path is higher (or at least more favourable for the particular integer-add workload BitNet uses). Put succinctly, quantization both shifts the point right and raises the attainable roof.

How this produces larger gains for bigger models. In small models a nontrivial fraction of runtime and memory is taken by embeddings, attention bookkeeping, kernels with small GEMMs, or framework overhead; compressing weights helps, but there is less nn.Linear time to accelerate, so the end‑to‑end speedup is moderate. As the model grows the share of time spent in large GEMMs increases (the paper explicitly notes "the time cost for nn.Linear grows with the model size" and shows the speedup trend). When those GEMMs dominate, accelerating them — and simultaneously increasing their arithmetic intensity by reducing weight bytes — yields a multiplicative effect: the kernels that used to be memory-bound become compute‑bound (so you can exploit the faster integer kernel) and a larger portion of total runtime benefits. That is why the paper observes increasing speedups (e.g., the $4.1\times$ figure at 70B) and why throughput gains are especially large (the 70B BitNet run could support $\sim 11\times$ the batch size and produced $\sim 8.9\times$ higher throughput on two 80GB A100s).

A compact roofline-style algebraic view you can use to reason or to measure: let the FP baseline time for a GEMM be $t_{\text{fp}} \approx \max\!\left(\frac{F}{P_{\text{fp}}},\frac{B_{\text{fp}}}{\text{BW}}\right)$ and the quantized time $t_{\text{q}} \approx \max\!\left(\frac{F'}{P_{\text{q}}},\frac{B_{\text{q}}}{\text{BW}}\right)$, where $P$ are the relevant peak throughputs, $BW$ is memory bandwidth, $F$ vs $F'$ reflect the differing operation counts/definitions (if you count ternary additions differently), and $B$ are bytes moved. The speedup is $S=t_{\text{fp}}/t_{\text{q}}$. From this expression you can see three limiting cases: if both versions are memory‑bound then $S\approx B_{\text{fp}}/B_{\text{q}}$ (pure bandwidth win); if both are compute‑bound then $S\approx P_{\text{q}}/P_{\text{fp}}$ (pure compute win); and if fp is memory‑bound while quantized is compute‑bound you get a compound effect (bandwidth reduction moves you past the ridge point so you also gain from higher integer throughput).

What the paper provides and what it does not. The paper reports end‑to‑end latency, memory, energy and throughput numbers measured with FasterTransformer (and a 2‑bit Ladder kernel), and it explicitly points to the two mechanisms I described: nn.Linear cost fraction increases with model size, and the quantized model has a much smaller memory footprint. It does not, however, include per‑kernel roofline plots or a microprofiling decomposition (time spent in DRAM traffic vs compute for each GEMM) that would let you cleanly quantify the relative contribution of "compute‑bound gain" vs "bandwidth reduction" to the reported overall speedups.

How you (or we) can quantify the split with a roofline experiment. Microbenchmark single GEMMs with the shapes used in the model (layer dims), record the measured runtime, measure bytes read/written (profilers or instrumented kernels), compute $AI=\dfrac{F}{B}$ and plot attained performance ($F/\text{time}$) versus $AI$. Do this for FP16 (cuBLAS/cutlass) and for the BitLinear / 2‑bit kernel. That plot will show whether FP16 points sit left of the ridge (memory‑bound) and whether the quantized points move right of the ridge and/or to a higher roof. Finally, run full‑model profiling (time per operator) to get the fraction of wall time spent in the accelerated GEMMs; multiply that by the per-GEMM speedups to estimate the end‑to‑end contribution. The algebra above (the $\max$ expressions) gives you the mapping from per‑kernel behaviour to overall speedup.

### Can you formalize the claimed "new scaling law"—a function relating quality and cost for 1.58-bit vs FP16?
Question:
Beyond the qualitative equivalences (e.g., 13B 1.58-bit is more efficient than 3B FP16), can you provide fitted relationships such as $\text{PPL}(N,T,b)$ vs parameter count $N$, training tokens $T$, and bit-width $b$, and a cost model $C(N,b)$ for latency/memory/energy? This would enable plotting iso-quality iso-cost curves to plan model sizing. How robust are these fits across datasets and modest architecture variations?
Answer:
Short answer: the paper does not publish a closed-form $\mathrm{PPL}(N,T,b)$ or a single $C(N,b)$ function, but it supplies enough empirical datapoints (perplexities matching at 3B+, measured latency/memory/energy ratios, and three cross-bit “equivalences”) to build a simple, practical pair of models you can fit and use to draw iso-quality / iso-cost curves. Below I give (1) a compact, literature-consistent functional form for quality that includes a bit-width factor, (2) simple latency / memory / energy cost formulas, (3) a minimal calibration using the numbers reported in the paper, and (4) a recipe to produce iso-quality / iso-cost curves and the caveats about robustness.

1) A compact quality (loss / perplexity) model
Use cross-entropy loss $L = \ln(\mathrm{PPL})$ because scaling laws are usually power-laws in loss. A convenient joint form (Kaplan-style) with a bit-width capacity factor $s(b)$ is

$$
L(N,T,b) \;=\; L_\infty \;+\; A\big(N\,s(b)\big)^{-\alpha} \;+\; B\,T^{-\beta},
$$

and PPL is recovered by $\mathrm{PPL}=\exp(L)$. Intuition: the model-size term decays as a power law in an effective parameter count $N_{\mathrm{eff}}=N\,s(b)$, and training-token effects are a separate power law in $T$. The bit-width enters through $s(b)$: $s(b)<1$ would mean reduced effective capacity per parameter; $s(b)>1$ would mean richer effective capacity (the paper’s main empirical claim is that for $b=1.58$ and $N\gtrsim 3\,$B, $s(1.58)\approx 1$ — i.e., no measurable loss vs FP16).

How to fit this from data: collect several $(N,T)$ points and fit $L_\infty,A,\alpha,B,\beta$ by least-squares on $L$ (or on $\log$–transformed data for the power terms). With those fitted you can invert the model to get the $N$ needed to reach a target loss at a given $T$ and $b$:

$$
N(b) \;=\; \frac{1}{s(b)}\left(\frac{A}{L_{\mathrm{target}}-L_\infty - B T^{-\beta}}\right)^{1/\alpha}.
$$

If you only have the paper’s claims (they trained at $T\!=\!100\,$B and show matching PPL for FP16 vs $b=1.58$ at $N\ge 3\,$B), treat $s(1.58)\approx 1$ as your starting prior; fit $s(b)$ only if you evaluate a few bit-widths.

2) Simple cost (memory / latency / energy) models
Memory: the paper shows that weights and activations both matter (activations/KV cache are non-negligible). A simple per-parameter linear model in bits is

$$
M(N,b) \approx \frac{N\big(b + a\cdot \mathrm{act\_bits}(b)\big)}{8} + M_0 \quad \text{(bytes)},
$$

where $\mathrm{act\_bits}(b)$ is activation bit-width used (paper: 16 for FP16 baseline, 8 for BitNet $b=1.58$), $a$ is the (unitless) ratio that converts activation bits-per-param into the same per-parameter basis, and $M_0$ covers embedding/fixed overhead. This form is intuitive: total memory $\approx$ weight bits + activation/KV bits (both scale with model size for large models).

Latency: a minimal, empirically useful model is

$$
t(N,b) = t_{\mathrm{fixed}} + N\cdot c(b),
$$

i.e., per-token latency = fixed overhead + a per-parameter contribution. Equivalently, normalize to FP16 per-billions-of-parameters units by writing $N$ in billions and

$$
t_{\text{FP16}}(N)=C(\beta + N),\qquad
t_{b}(N)=C(\beta + N\cdot k(b)),
$$

so the speed-up at size $N$ is $r(N)=\dfrac{\beta+N}{\beta+N k(b)}$. Here $k(b)$ is the per-parameter cost of bit-width $b$ relative to FP16 and $\beta$ encodes fixed overhead measured in the same normalized units. This form captures that speed-ups increase with model size (overhead becomes less important).

Energy: separate arithmetic energy and memory-transfer energy. A simple per-parameter model is

$$
E(N,b) \approx N\big( \mathrm{ops\_per\_param}\cdot e_{\mathrm{arith}}(b) \;+\; e_{\mathrm{mem\_per\_bit}}\cdot b \big) + E_0,
$$

where $e_{\mathrm{arith}}(b)$ is energy per arithmetic operation at bit width $b$ and $e_{\mathrm{mem\_per\_bit}}$ is energy to move one bit. The paper reports that 1.58-bit arithmetic for matmul has about $71.4\times$ lower arithmetic energy (on a 7nm chip) than FP16 arithmetic, so $e_{\mathrm{arith}}(1.58)\approx e_{\mathrm{arith}}(16)/71.4$ for the matmul portion.

3) Minimal calibration from the paper (worked example)
The paper reports (paraphrased): at 3B, BitNet $b=1.58$ is $2.71\times$ faster and uses $3.55\times$ less GPU memory than FP16 LLaMA (same $N,T$); at 70B the speed-up grows to $4.1\times$; and arithmetic energy for matmul is $\sim 71.4\times$ lower.

You can use these numbers to solve a couple of parameters in the cost models:

Memory-fit. Let the measured memory ratio be $r_M = M_{1.58}/M_{16} = 1/3.55\approx 0.2817$. With $\mathrm{act\_bits}(16)=16$, $\mathrm{act\_bits}(1.58)=8$ and weight bits 16 vs 1.58, the per-parameter activation coefficient $a$ satisfies

$$
r_M \;=\; \frac{1.58 + a\cdot 8}{16 + a\cdot 16}.
$$

Solving for $a$ gives

$$
a \;=\; \frac{1.58 - 16r_M}{16r_M - 8} \;\approx\; 0.838.
$$

So a rough calibrated memory formula (ignore small fixed overheads) is

$$
M(N,b)\approx \frac{N\big(b + 0.838\cdot\mathrm{act\_bits}(b)\big)}{8}\ \text{bytes},
$$

which yields the $3.55\times$ reduction at 3B when you plug in the paper’s act bit choices. Intuition: activations/KV caches are large relative to just weights, so the measured memory shrinkage is smaller than the raw weight-bit ratio $1.58/16$.

Latency-fit. Model $t_{\text{FP16}}(N)=C(\beta+N)$ and $t_{1.58}(N)=C(\beta + N k)$, use the two speed-ups $r(3\text{B})=2.71$ and $r(70\text{B})=4.1$ (write $N$ in billions: 3 and 70). Solving the two equations yields

$$
k(1.58)\approx 0.237,\qquad \beta\approx 0.627,
$$

so asymptotic speed-up $\approx 1/k \approx 4.22$ and the finite $\beta$ explains why the speed-up at 3B is only $2.71\times$ (fixed overheads matter at small $N$). This gives the simple working latency model

$$
t_{1.58}(N) \;=\; C\big(0.627 + 0.237\,N\big),\qquad t_{16}(N)=C\big(0.627 + N\big),
$$

with $C$ a hardware-dependent constant (time per billion FP16 parameters). To convert to absolute latency, measure $C$ once (e.g., time per token for a known FP16 model).

Energy illustration. Use the arithmetic-energy advantage $e_{\mathrm{arith}}(1.58)\approx e_{\mathrm{arith}}(16)/71.4$ and the memory model above. If $f$ is the fraction of FP16 total energy coming from arithmetic (matmul) vs memory movement, then the end-to-end energy ratio is roughly

$$
\frac{E_{1.58}}{E_{16}}\approx \frac{f/71.4 + (1-f)/3.55}{1}.
$$

If arithmetic dominates ($f\approx 0.8$) you get an end-to-end ratio $\sim 0.07$ ($\approx 14\times$ reduction); if arithmetic is 50% you get $\sim 0.15$ ($\approx 6.7\times$). The paper’s “$71.4\times$ on arithmetic” number is the best-case arithmetic term; the true wall-plug reduction depends on how memory-dominated your end-to-end workload is.

4) How to produce iso-quality / iso-cost curves (practical recipe)
First fit $L(N,T)$ for your dataset and training recipe at FP16 (or use literature exponents as priors): gather PPLs for 3–5 model sizes at fixed $T$ and fit $L_\infty,A,\alpha$ (and $B,\beta$ if you vary $T$). Next estimate $s(b)$ by training/evaluating 1–2 models at alternative $b$ (paper suggests $s(1.58)\approx1$ for $N\gtrsim3\,$B). Measure (or use the paper-calibrated) cost parameters $a$, $k(b)$, $\beta$ and $C$ on your target hardware (measure latencies and peak memory for two model sizes and solve the two-parameter linear model). Then for a desired target loss $L^*$ compute $N(b)$ from the inverted law above and plug into $M(N(b),b)$, $t(N(b),b)$, $E(N(b),b)$ to get iso-quality cost points. Plotting $b\mapsto C(N(b),b)$ gives the iso-quality iso-cost tradeoffs.

5) Robustness and caveats
Scaling laws are empirically robust in broad regimes, but all fitted constants depend on dataset, tokenization, training recipe, small architecture changes (RoPE vs no RoPE, normalization choices), and especially on quantization-aware training tricks. The key empirical points from this paper that make 1.58-bit attractive are: (a) PPL parity with FP16 at the same $N$ for $N\ge 3\,$B (so $s(1.58)\approx1$ in that regime), and (b) large arithmetic-energy and per-parameter time reductions that grow with model size (i.e., $k(1.58)\ll 1$). But you should always re-calibrate $s(b)$ and the hardware constants ($C,\beta,k(b),a,e_{\mathrm{mem}}$) on your data and hardware if you want production-quality provisioning.

Summary (one-liner): use a Kaplan-style loss model with an effective-size multiplier $s(b)$ and simple linear-in-$N$ cost models (memory bits per param + activation coefficient; latency = fixed + per-param cost; energy = arithmetic + memory terms). Calibrate $s(b)$ and the few cost constants on a handful of measured sizes; with the paper’s reported ratios you can initialize $a\!\approx\!0.84$, $k(1.58)\!\approx\!0.237$, $\beta\!\approx\!0.627$, and $e_{\mathrm{arith}}(1.58)\!\approx\!e_{\mathrm{arith}}(16)/71.4$ and then produce iso-quality / iso-cost curves for planning.

### What exactly is counted in the reported GPU memory numbers—weights only, or also KV cache and temporary activations?
Question:
For the runtime memory comparisons, do the numbers include: quantized weights (plus any per-tensor scales), KV caches at the stated batch size and context length, intermediate activations during prefill, and workspace buffers from FasterTransformer? Are optimizer states excluded (inference-only), and were the measurements taken at batch size 1 decode or at the maximum batch that fits?
Answer:
Short answer: the paper’s “runtime GPU memory” numbers are the total GPU memory used by the FasterTransformer inference runs reported in the paper, so they should include the quantized model storage (as represented by the $2$‑bit/ternary kernels and their small per‑tensor scales), the KV caches for the batch$\times$context used in each measurement, the temporary activation buffers and any scratch/workspace allocations FasterTransformer needs. Optimizer states are not included (these experiments are inference‑only). For the throughput experiment the authors explicitly increased batch size until the GPU memory limit with sequence length $512$, so that measurement is “maximum batch that fits”; for the other latency/memory comparisons the paper reports time per output token (the decode cost) but does not explicitly document the exact batch/sequence settings in the text, so those particular memory numbers correspond to whatever inference configuration was used with FasterTransformer (most likely a decode scenario), but the paper does not give a fine‑grained breakdown.

Why this is the correct reading: the paper says the benchmarks were measured with the FasterTransformer codebase and with a $2$‑bit kernel integrated (so the reported memory is the end‑to‑end memory allocation of that runtime). The paper also discusses KV cache memory and reduced activation precision ($8$‑bit activations, embeddings kept full precision), which shows the authors considered KV $+$ activations in their memory accounting. Because these are inference runs, optimizer/state tensors are naturally excluded. If you need an exact per‑component breakdown (weights vs. per‑tensor scales vs. KV cache vs. workspace), the paper does not publish that detailed split; the most direct way to get it is to reproduce the FasterTransformer run they used (they cite the codebases) or ask the authors for the exact measurement script/config.
