\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### Why compare mainly to FP16 rather than strong 3–4 bit quantized baselines (e.g., AWQ, GPTQ)?
Question:
Given that 4-bit post-training quantization with int8 activations is widely used, it would be informative to compare BitNet b1.58 to well-tuned 3–4 bit PTQ/QAT baselines on both accuracy and decode-time latency/memory. Do your Pareto gains hold against these baselines, especially at 3B–13B scales?
Answer:
Short answer: the paper compares primarily to FP16 because its central claim is that you can train a model from scratch in $1.58$ bits and match full‑precision performance while getting large runtime/memory/energy wins; that is a strong, clean baseline. The paper does cite PTQ work (GPTQ, AWQ, etc.) and acknowledges PTQ is widely used, but it does not include head‑to‑head results against carefully tuned $3$–$4$ bit PTQ/QAT baselines, so you cannot conclude from the paper alone whether the stated Pareto gains still hold versus those methods. To know that you need carefully controlled experiments; I’ll explain why a direct comparison is nontrivial, what to watch for, and what to expect.

Why FP16 was chosen as the principal baseline
The paper’s goal is to show that a model trained end‑to‑end at $1.58$ bits can reach parity with the canonical full‑precision model (FP16/BF16) while drastically reducing runtime and memory cost. Comparing to FP16 is the most direct way to demonstrate that low‑bit training is not merely a compression trick but a viable training/architecture regime. PTQ methods start from a working FP16 model and try to compress it post hoc; that is a different workflow (and a different claim). Also, an apples‑to‑apples comparison against PTQ requires matching the runtime stack and optimized kernels for each quantization scheme, which the paper did not attempt to exhaustively do.

Why PTQ / $3$–$4$ bit baselines are a different beast
Post‑training quantization (GPTQ, AWQ, Quip, etc.) operates on a trained FP16 checkpoint and uses blockwise/per‑channel quantizers, outlier handling, SmoothQuant, and other heuristics to preserve accuracy. Those methods typically (a) store extra per‑block scale/zero‑point metadata, (b) sometimes dequantize blocks at runtime or rely on specific integer GEMM kernels, and (c) often leave activations / KV cache in higher precision unless you explicitly quantize them. By contrast BitNet b$1.58$ is trained from scratch with ternary weights and $8$‑bit activations, and the inference code in the paper uses an integrated $2$‑bit kernel (Ladder) in FasterTransformer. So the two approaches differ not only in bitcount but also in where quantization is applied, what kernels are used, and what metadata/overheads appear at runtime.

Quick quantitative intuition about memory
Raw weight storage scales linearly with bits. Four‑bit weights use $4/8=0.5$ bytes per parameter; $1.58$ bits is $1.58/8\approx0.1975$ bytes per parameter, so the weight array alone is about
$$
\frac{0.1975}{0.5}\approx0.395
$$
of the $4$‑bit weight size, i.e. roughly a $2.53\times$ reduction in weight bytes versus $4$‑bit. In practice total GPU memory includes embeddings (kept FP16 in the paper), activation/KV cache memory, optimizer states (for training), and scale metadata for PTQ blocks, so the real end‑to‑end memory ratio will be smaller than the raw bit ratio.

Why runtime (latency) comparisons are subtle
Latency depends on more than bitwidth: kernel implementation, whether multiply‑accumulate remains (int8 MAC) or operations reduce to add/sub/skip for ternaries, memory bandwidth, and whether you must dequantize on the fly. BitNet’s integer‑addition heavy compute (ternary multiply becomes add/sub/zero) can be much cheaper in energy and amenable to specialized hardware; on current GPUs, however, highly optimized int4/int8 kernels (bitsandbytes, AWQ/GPTQ runtimes, vendor libraries) can be extremely fast and may narrow the latency gap. Thus whether BitNet maintains a Pareto edge in latency versus best‑in‑class $3$–$4$ bit PTQ depends critically on kernel maturity and how activations/KV are quantized at inference.

How to do a fair head‑to‑head comparison (what the paper did not report)
To settle the question experimentally you should (1) start from the same FP16-pretrained model used in the paper, (2) apply state‑of‑the‑art PTQ (AWQ and GPTQ) with recommended settings (per‑channel / block sizes, SmoothQuant if appropriate, activation handling), (3) run inference in the same runtime (e.g., FasterTransformer or vLLM) with optimized kernels for each quantization scheme, (4) measure the same accuracy metrics (perplexity and the same zero‑shot tasks), and (5) report end‑to‑end decode metrics: time per output token, peak GPU memory including KV cache at target context lengths, throughput at same batch/seq settings, and any scale metadata overhead. If you want energy comparisons, either measure wall‑power during runs or apply the same energy model used in the paper for consistency. Only then can you say whether BitNet’s Pareto points still dominate.

Reasonable expectations (but not definitive claims)
Because BitNet trains ternary weights and reduces activations to $8$‑bit everywhere, you should expect it to have a clear advantage on weight storage and (potentially) KV cache memory if you quantize KV there. At small model sizes (e.g., $3$B) PTQ methods sometimes degrade accuracy more than at larger sizes; since the paper reports BitNet matches FP16 starting at $3$B, BitNet may outperform PTQ at that scale on accuracy. At larger sizes ($7$–$13$B) modern $4$‑bit PTQ methods have shown strong accuracy preservation in many reports, so the accuracy gap could vanish and the comparison will hinge on kernel throughput and whether PTQ keeps activations/KV in high precision. If PTQ keeps KV/activations at FP16 while BitNet uses $8$‑bit, BitNet will likely keep a memory advantage. But if PTQ integrates optimized int4 int8 kernels and also compresses activations/KV, the latency and memory gaps may shrink—how much depends on implementation details and hardware.

Bottom line
The paper demonstrates a strong and important point—end‑to‑end training at $1.58$ bits can match FP16 accuracy while substantially reducing resource use—but it does not present the specific head‑to‑head with best‑in‑class $3$–$4$ bit PTQ/QAT baselines. You should treat the Pareto claims as relative to the FP16 baseline they studied; determining whether the Pareto frontier still favors BitNet versus AWQ/GPTQ requires the controlled experiments outlined above. If you want, I can sketch a concrete experimental script (toolchain, kernel choices, measurement protocol and hyperparameters for AWQ/GPTQ) so you can run those comparisons reproducibly.
