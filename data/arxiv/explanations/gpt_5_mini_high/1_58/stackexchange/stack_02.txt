\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### What does "1.58 bits" mean in practice if the kernel packs weights in 2 bits?
Question:
The paper calls the model "1.58-bit" because weights are ternary $\{-1,0,1\}$ (entropy $\log_2 3 \approx 1.585$), but the implementation uses the Ladder 2-bit kernel. Are the reported memory/latency results based on 2-bit physical packing, or do you use any entropy coding to approach 1.58 bits/weight? How are per-tensor scales, padding/alignment, and metadata counted in memory totals? When should we think in terms of 1.58 bits vs 2 bits for practical deployments?
Answer:
Short answer: calling the model “$1.58$‑bit” is an information‑theoretic description of the ternary alphabet (every weight takes values in $\{-1,0,+1\}$, so the entropy is $H=\log_2 3\approx 1.585$ bits). In the paper’s experiments, however, the runtime memory and latency were measured using a $2$‑bit packed kernel (the Ladder $2$‑bit kernel integrated into FasterTransformer). The authors explicitly say “Both latency and memory were measured with a $2$‑bit kernel, so there is still room for optimization,” which implies they did not use additional entropy coding to turn the theoretical $1.585$ bits/weight into a lower physical bits/weight in the inference measurements.

Why the two numbers are different (intuitive): $1.585$ bits is the lower bound on average information per weight given a ternary distribution — it tells you how many bits you would need on average with an optimal variable‑length encoder. A $2$‑bit physical packing is a fixed‑length encoding that stores exactly two bits per weight and is much easier and faster to use directly inside a GPU kernel. Moving from $2$ bits to an average of $1.585$ bits requires variable‑length or entropy coding (Huffman, arithmetic, RLE, etc.), which saves only around
$$1 - \frac{\log_2 3}{2} \approx 20.8\%$$
in raw bit storage in the ideal uniform ternary case, and possibly more if the empirical ternary distribution is skewed (e.g. many zeros). But entropy coding brings decoding overhead and makes random/block access for matmuls more complex; unless the kernel can consume the compressed stream directly (or you decompress in hardware/on the fly), the latency/memory benefits at inference are not automatic.

How scales, padding and metadata are counted (what to expect): the paper’s quantizer computes one scale per weight tensor ($\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|$), so you must store at least one scalar scale per tensor. The paper does not state the dtype used for scales, but common choices are FP16 or FP32; for large linear layers this per‑tensor scalar is negligible (for example, a $4096\times4096$ matrix has $\sim16.7\,$M weights, at $2$ bits $\approx 4.17\,$MiB, so one FP16 or FP32 scale is a vanishing overhead). However, many small tensors or finer per‑channel/group scales raise the relative overhead. Bitpacking itself also requires grouping bits into bytes/words for the kernel, so there is padding to the kernel’s block granularity (columns/rows rounded up to the kernel tile size) and alignment to memory boundaries; for large matrices that padding is a tiny fraction, for many small matrices it can be material. Framework/runtime metadata (tensor shapes, pointers, format flags, any zero masks) also add a small fixed overhead per tensor. The paper’s memory/latency numbers come from running the actual packed $2$‑bit kernel inside FasterTransformer, so those measurements already include the kernel’s packing/alignment behavior and the runtime overheads present in that setup.

When to think in terms of $1.58$ bits vs $2$ bits for deployment decisions: use $1.58$ bits when reasoning about model capacity, information content, or the theoretical compression limit of your ternary weights (and when arguing for the potential room to squeeze more storage by compression). Use $2$ bits when planning real‑world inference memory, bandwidth and kernel performance with current quantized kernels (like Ladder) or GPUs, because those kernels operate on fixed, bit‑packed representations and the paper’s speed/memory claims are measured for that setup. If you intend to reduce stored model size on disk or for network transfer, you can compress offline toward the entropy limit and get the $\sim 20\%$ (or more if distribution is skewed) reduction; but to get runtime memory/bandwidth reductions without a big latency penalty you need either (a) kernels that operate directly on the compressed representation, (b) streaming/block decompression tightly integrated with the matmul so you never expand to a full dense representation in DRAM/SRAM, or (c) dedicated hardware that supports ternary/variable‑length formats natively — none of which the paper claims to have used in the reported timing/memory numbers.

Practical rule of thumb: assume $2$ bits/weight (plus one scale per tensor and small alignment/metadata overhead) for latency and GPU memory planning today; treat $1.58$ bits as the theoretical lower bound and as motivation to explore compression or hardware/kernel co‑design if you want the extra $\sim 20\%$ storage savings in practice. The paper demonstrates that the model’s statistical/accuracy behavior matches FP16 despite being ternary; converting that theoretical information saving into runtime/VRAM savings is an additional engineering step.
