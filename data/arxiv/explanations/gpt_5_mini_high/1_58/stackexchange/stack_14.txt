\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### Decode-time latency measurement details: prompt length, batch size, hardware/software stack, and prefill vs decode split?
Question:
You report "time per output token" using FasterTransformer with the Ladder 2-bit kernel. To reproduce, could you specify: GPU model and memory (e.g., A100 80 GB), CUDA/cuBLAS/cuDNN versions, prompt length for prefill, batch size(s), sequence length, attention implementation (e.g., paged KV cache), and whether you report pure decode latency or an average over prefill+decode? Was the FP16 baseline using fused attention/FlashAttention and any autotuning comparable to the ternary kernel?
Answer:
Short answer: the paper gives only a few of the exact reproduction knobs you asked for. It explicitly states that inference measurements were done with NVIDIA’s FasterTransformer codebase, that the Ladder 2‑bit kernel was integrated for BitNet b1.58, that the reported metric is “time per output token,” and that the 70B throughput comparison used two 80GB A100 cards with pipeline parallelism and a sequence length of $512$ (batch size was increased until GPU memory limit). The paper does not report the CUDA/cuBLAS/cuDNN versions, the GPU(s) used for the single‑GPU latency/memory plots, the exact prompt (prefill) lengths or the batch sizes used for the per‑token latency numbers, whether the reported per‑token time is decode‑only or averaged over $prefill+decode$, nor the low‑level attention/KV cache layout (paged vs on‑GPU) or which FP16 attention kernel (FasterTransformer fused attention, FlashAttention, etc.) and autotuning settings were used for the FP16 baseline.

Why those missing items matter: wall‑clock latency is sensitive to GPU model and driver/toolkit versions (CUDA/cuBLAS/cuBLASLt picks different GEMM algorithms), to whether kernels were compiled for the exact GPU compute capability, and to allocator and stream usage. Prefill (building the KV cache for the prompt) is an $O(L)$ pass in $L = \text{prompt length}$ and can be either reported separately or amortized into per‑token time; the two choices give very different numbers when prompts are long. Batch size and sequence length change both throughput and per‑token decode latency. Different attention implementations (an on‑GPU contiguous KV cache like FasterTransformer’s typical approach vs. a paged/CPU/host-backed cache as in some systems) change memory pressure and can change per‑token timing. Finally, comparing a custom Ladder 2‑bit kernel to FP16 must ensure the FP16 baseline is using the best available optimized kernels (e.g., FasterTransformer’s FP16 fused kernels or an equivalent FlashAttention implementation) and that both sides had comparable autotuning enabled; otherwise the comparison can be biased.

Practical recipe to reproduce the paper’s “time per output token” in a way that isolates effects and is fair to both variants: build the same inference stack (FasterTransformer + Ladder 2‑bit kernel integration) and run two measured quantities separately — $prefill\_time$ (time to run the prompt/prefill and build KV caches) and $decode\_time$ (time to generate $G$ autoregressive tokens). Use a fixed prompt length $L$, a fixed batch size $B$, and a fixed generation length $G$. Warm up the GPU (several warmup runs), then measure $decode\_only\_per\_token = decode\_time / G$ and $amortized\_per\_token = (prefill\_time + decode\_time) / G$. Run several repeats and report mean $\pm$ std. For the 70B throughput experiment reproduce the paper’s set up (two 80GB A100s, pipeline parallelism, sequence length = $512$, increase $B$ until OOM) so you can verify the same throughput/batch limit behavior. When benchmarking FP16, use the same FasterTransformer release and build flags (same CUDA toolkit, same -gencode flags) so kernel compilation choices are matched; if you instead benchmark an alternative stack (FlashAttention in PyTorch), explicitly enable its best kernels and report both stacks’ versions and tuning state.

If you want to actually reproduce the paper’s numbers I can help prepare a checklist and a small measurement script (warmup → prefill → generate → synchronous timing using cuda events) and a list of exact environment/compile fields to record (GPU model(s) and memory, driver, CUDA runtime, cuBLAS/cuBLASLt/cuDNN versions, FasterTransformer commit, Ladder kernel commit/flags, model config, batch/seq/$G$). Given that those exact fields are not in the paper, the safest path to exact reproduction is to ask the authors for their FasterTransformer build logs / commit hash and the scripts used to run the latency experiments; otherwise follow the protocol above and report both decode‑only and prefill‑amortized numbers so comparisons are interpretable.
