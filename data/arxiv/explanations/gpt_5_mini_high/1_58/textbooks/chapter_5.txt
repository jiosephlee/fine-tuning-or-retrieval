\title{A Textbook about the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

Chapter 5: The BitNet Family and Its Computation Paradigm

# BitNet overview: replacing nn.Linear with BitLinear

BitNet is a family of Transformer designs that makes a single, radical change to the usual Transformer building block: every standard dense linear layer (the common software primitive often exposed as `nn.Linear`) is replaced by a quantized variant called BitLinear. In conventional Transformers the dominant cost—both in compute and memory—comes from those dense matrix multiplications performed in floating point (FP16 / BF16 in modern models). BitLinear rewrites that cost profile by storing weights in a low-bit, sign-oriented format and by arranging the computation so that the heavy inner products are computed with integer additions rather than floating-point multiplications.

The concrete quantization rule used in the BitNet family (and in the BitNet b1.58 variant) is simple and systematic. For a weight matrix $W\in\mathbb{R}^{n\times m}$ BitNet computes a per-matrix scale
\[
\gamma = \frac{1}{nm}\sum_{i,j} |W_{ij}|
\]
and then quantizes each entry by first dividing by this average absolute value and then rounding and clipping into the ternary set $\{-1,0,1\}$:
\[
\widetilde{W} = \mathrm{RoundClip}\!\Big(\frac{W}{\gamma+\epsilon},-1,1\Big),
\qquad
\mathrm{RoundClip}(x,a,b) = \max(a,\min(b,\mathrm{round}(x))).
\]
The small constant $\epsilon$ is used for numerical stability. Because $\widetilde{W}$ takes values only in $\{-1,0,1\}$, a multiply by a weight turns into either adding the activation, subtracting it, or skipping it entirely. The original BitNet used a two-valued weight set (effectively $\{+1,-1\}$); BitNet b1.58 inserts a third value $0$ (hence “b1.58” for a ternary representation) which explicitly enables feature filtering by allowing exact zeros in the weight matrix.

Activations are quantized in a compatible way: BitNet b1.58 uses 8-bit activations, but importantly the activations are scaled per token into a symmetric integer range $[-Q_b,Q_b]$ (this removes the need for zero-point offsets). The combination of ternary weights and per-token symmetric 8-bit activations is the key enabler of BitLinear: the dense linear transform can be implemented with integer-add-centric kernels rather than dense floating-point multiply–accumulate operations.

# Dataflow for add-centric matrix multiplication

To understand the run-time dataflow of a BitLinear layer, consider the usual dense product $y = W x$. After quantization we approximate $W$ by $(\gamma+\epsilon)\widetilde{W}$, so the product is
\[
y \approx (\gamma+\epsilon)\,\big(\widetilde{W}\,x\big).
\]
If the input activation vector $x$ has been quantized (and scaled per token) to an integer vector $\tilde{x}$, then the core integer computation is
\[
s = \widetilde{W}\,\tilde{x},\qquad s_i = \sum_j \widetilde{W}_{ij}\,\tilde{x}_j.
\]
Because each $\widetilde{W}_{ij}\in\{-1,0,1\}$, each inner product reduces algebraically to a sum and a subtraction:
\[
s_i = \sum_{j:\,\widetilde{W}_{ij}=1}\tilde{x}_j - \sum_{j:\,\widetilde{W}_{ij}=-1}\tilde{x}_j.
\]
This expression is purely integer addition and subtraction plus index selection; no per-element multiplications by arbitrary values are required. The final floating-point scaling by $(\gamma+\epsilon)$ (and any activation-scale used during quantization) is applied after the integer accumulation, which means that the large majority of elementwise work becomes integer accumulation and the expensive per-element FP multiply is essentially eliminated at the inner-product level.

From an implementation point of view this lets the runtime perform two classes of operations cheaply and in parallel: gather-and-add over positions where the weight is $+1$, gather-and-subtract over positions where the weight is $-1$, and completely skip positions where the weight is $0$. Practically this can be implemented as two integer-accumulation streams (one for positive positions, one for negative positions) and a final subtraction, or by bitmask-based kernels that exploit the ternary structure. Because the activations are symmetrically quantized per token, there is no additional zero-point correction to be applied to the integer accumulators, which simplifies the dataflow and the kernel logic.

The paper integrates an optimized low-bit kernel (a 2-bit kernel from an external codebase) into a high-performance inference stack (FasterTransformer) to realize these integer-add-centric matrix multiplications. The upshot is that the expensive multiply–accumulate loops that used to dominate both latency and energy are replaced by much cheaper integer additions, with only one coarser-grained scaling step remaining per output.

# Memory footprint and bandwidth savings with low-bit weights

One of the strongest system-level consequences of moving the bulk of weight storage to a low-bit representation is immediate reduction of memory footprint and the bandwidth required to stream weights from off-chip memory. BitNet b1.58 stores weights in a ternary form instead of 16-bit floating point, and activations in 8-bit rather than 16-bit. The paper reports substantial end-to-end resource improvements that follow from this compression.

Concretely, when both BitNet b1.58 and a reproduced FP16 LLaMA model are trained under the same conditions (same model sizes and same 100B-token pretraining on RedPajama), the BitNet variant achieves large runtime improvements and memory reductions. For example, BitNet b1.58 at 3B parameters is reported as 2.71× faster at inference and uses 3.55× less GPU memory than the FP16 baseline; a 3.9B BitNet model is 2.4× faster and 3.32× lower-memory while outperforming the 3B FP16 model. As models grow, the benefits increase: the paper reports a 70B-parameter BitNet b1.58 being 4.1× faster than the FP16 LLaMA 70B baseline. Throughput results shown for two 80 GB A100 GPUs indicate that BitNet b1.58 70B can support up to 11× the batch size of the FP16 baseline in the same memory footprint, yielding an 8.9× higher throughput under the evaluated conditions.

Two reasons drive these improvements. First, storing weights and activations with fewer bits reduces the DRAM bandwidth needed to load them, which is a major bottleneck at inference time. Second, the compute kernels themselves are simpler (integer additions instead of FP multiply-accumulates), which reduces latency and energy per operation. The paper also notes that the embedding table is kept full precision in BitNet b1.58; because embedding memory is a smaller fraction of total memory as models get larger, the relative memory savings of low-bit weights and activations become larger at scale. Finally, reducing activation precision (for example, KV caches in attention) from 16 bits to 8 bits directly reduces cache memory and enables longer native context lengths for a given hardware budget; the authors point out that such activations could be further compressed in future work.

# Comparing original 1-bit BitNet and the b1.58 variant

The original BitNet architecture was built around weights that effectively take two values (sign-only, e.g., $\{\!+1,-1\!\}$) and activations quantized to low precision, turning dense matrix multiplications into sequences of additions and subtractions. BitNet b1.58 extends that idea by inserting a third weight value, $0$, producing ternary weights $\{-1,0,1\}$. The inclusion of exact zeros is not merely a storage trick: it enables explicit feature filtering, allowing a weight to suppress a contribution entirely rather than forcing a sign flip. According to the paper, that explicit zero value strengthens modeling ability and helps BitNet b1.58 match full-precision baselines at practical model scales.

BitNet b1.58 retains the core system advantages of the original BitNet: most of the matrix multiplication work reduces to integer additions (the same compute paradigm), the arithmetic energy profile is overwhelmingly dominated by cheap integer additions, and memory and latency costs are significantly reduced relative to FP16 baselines. The paper reports that BitNet b1.58 "matches the full-precision Transformer LLM with the same model size and training tokens in terms of both perplexity and end-task performance" when models are large enough (matching begins at about 3B parameters in their experiments) while enjoying the runtime and energy benefits. In other words, by adding a zero state the designers improved expressivity without surrendering the primary system advantages.

On the architectural side BitNet b1.58 uses LLaMA-compatible components—RMSNorm, SwiGLU, rotary embeddings—and removes biases so that the model can be integrated with popular open-source tooling with minimal changes. Training is performed from scratch with 1.58-bit weights and 8-bit activations; the quantization function applied to weights is the absmean-based rounding described above, and activations are quantized symmetrically per token into $[-Q_b,Q_b]$.

# Where multiplications still remain (if any) and system implications

Although BitLinear moves the vast majority of expensive multiplications out of the inner loops of matrix multiplication, a small number of multiplications remain in the end-to-end computation graph and in system-level bookkeeping. The most important such multiply is the coarse-grained reconstruction scaling that converts the integer accumulator into a floating-point approximation of the original dense product. Using the notation above, after computing the integer accumulation $s=\widetilde{W}\,\tilde{x}$ the layer typically applies the shared per-matrix scale $(\gamma+\epsilon)$ (and any per-token activation scale) to convert to the floating-point domain:
\[
y \approx (\gamma+\epsilon)\,s.
\]
That multiplication is applied at the granularity of outputs (for example, one multiply per output feature or per block) instead of per weight, so the number of multiplies is drastically smaller than in a conventional dense multiply–accumulate implementation.

Other multiplications remain in non-linear or auxiliary components of the Transformer block that are not replaced by BitLinear. BitNet b1.58 adopts LLaMA-alike components such as RMSNorm and SwiGLU, and these layers involve elementwise multiplies, scaling, and normalization operations. Attention softmax, rotary embeddings, and embedding matrix lookups also require floating-point math; in the reported implementation, the embedding table is left in full precision. The paper summarizes the net effect succinctly: the majority of BitNet b1.58’s arithmetic is INT8 additions, whereas the FP16 baseline contains both FP16 additions and FP16 multiplications. Because matrix multiplication dominates FLOPs as model size grows, reducing per-multiply cost yields increasingly large relative benefits for larger models.

The system implications of this shift are substantial. Replacing large numbers of FP multiplies with integer adds lowers arithmetic energy consumption for the heaviest kernels—an energy-model-based estimate presented in the paper reports a 71.4× reduction in arithmetic operations energy consumption for matrix multiplication on 7 nm chips. Reduced memory footprint and bandwidth means fewer DRAM transfers, smaller KV cache usage for long-context inference, and the possibility of fitting larger models (or larger parts of a model) entirely on-chip—improving throughput and lowering latency. These savings also change software and hardware trade-offs: fewer devices are required to host a model (important for techniques such as Mixture-of-Experts), inter-chip communication can be reduced, and specialized hardware that targets integer-add-centric LLM computation becomes an attractive engineering path. The paper explicitly calls out the potential for new hardware optimizations and notes that the 2-bit kernel from Ladder and the FasterTransformer integration are concrete system-level steps toward realizing the add-centric dataflow at scale.

In summary, BitLinear replaces the per-element FP multiply–accumulate machinery of dense layers with integer gather-and-add patterns plus a small number of coarse-grained scalings. That reorganization preserves model expressivity (especially after adding the zero state in b1.58), reduces memory and bandwidth demands, improves latency and throughput in practice, and shifts the system design point toward integer-add-centric kernels and accelerators optimized for the new computation paradigm.
