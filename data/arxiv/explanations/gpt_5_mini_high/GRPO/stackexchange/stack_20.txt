\title{Stack Exchange of the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

### Program-of-thought evaluation: what execution environment, libraries, and answer checking criteria were used?
Question:
For PoT, models write Python using libraries like math and sympy. What sandbox was used (timeout, memory, disabled IO/network), which libraries and versions were allowed, and how were answers compared (exact string, numeric tolerance, rational simplification)? Any safeguards against non-determinism affecting scores?
Answer:
Short answer: the paper only states that program-of-thought (PoT) evaluation was done by having the model emit Python programs (allowing libraries “such as math and sympy”) and that “the execution result of the program is evaluated as the answer.” It does not give the concrete sandbox/runtime settings (timeout, memory caps, IO/network disabling), a precise list of allowed libraries or their versions, nor the exact canonicalization/tolerance rules used to compare program outputs to gold answers. The paper does, however, report sampling-based safeguards that partially mitigate nondeterminism: they use multi-sample self-consistency (e.g. $64$ samples) and report $\text{Maj@K} / \text{Pass@K}$ style analyses, and in training GRPO they sample $64$ outputs per question — so aggregation over many samples was part of their evaluation strategy.

A bit more detail and context. What the paper explicitly records is that GSM8K and MATH were solved with few-shot PoT, models wrote Python and could use libraries “such as math and sympy,” and the program’s execution result was taken as the model’s answer. For RL and evaluation they frequently sample many completions ($64$ is mentioned repeatedly), and they analyze $\text{Maj@K}$ and $\text{Pass@K}$ versus single-shot Pass results; this shows they expected sampling variability and used majority/self-consistency-style aggregation to reduce sensitivity to single-run nondeterminism.

What is missing (and what you should assume you’ll have to clarify if you want to reproduce the results): the authors do not publish (in this paper) the execution harness details — e.g., whether programs ran in Docker/seccomp sandboxes, exact timeouts per run ($1\,\text{s}$, $5\,\text{s}$, $30\,\text{s}$?), memory limits (e.g., $512\,\text{MB} / 2\,\text{GB}$), whether filesystem or network access was blocked, whether subprocess spawning was prohibited, or whether Python random seeds / numpy deterministic flags were forced. They also don’t report an explicit allowed-library whitelist beyond the phrase “such as math and sympy,” nor concrete version numbers (Python or SymPy versions are not given). Finally, they don’t spell out the answer-checker: whether they compared exact stdout strings, parsed the final printed token (e.g., “Answer: …”), used numeric tolerances (absolute/relative epsilons), converted floats to rationals, or used symbolic simplification via SymPy to assert equality.

If you need to reproduce or extend this work, here are the practical implications and common choices from the literature (these are NOT stated in the paper but are the usual, safer practices you should consider): run model-generated code in an isolated container with networking and persistent filesystem access disabled, enforce wallclock and CPU timeouts (typical values vary from a few seconds up to tens of seconds depending on problem complexity), cap memory with cgroups/ulimit, and run as an unprivileged user with seccomp/namespace restrictions. Allowing SymPy is common because it lets you canonicalize symbolic/rational results (compare via SymPy’s simplify or exact rational equality) instead of brittle string matching; for floating outcomes you usually compare with a small absolute or relative tolerance (e.g. $10^{-6}$ or $10^{-4}$ depending on scale). To reduce nondeterminism you either ban or require explicit seeding of random-number generators (Python random / numpy), capture program stdout/return values rather than arbitrary prints, and canonicalize answers before comparison (strip whitespace, normalize numeric formats, use symbolic simplification when possible). As the paper demonstrates, aggregating many samples (self-consistency/majority voting) is an effective empirical safeguard against run-to-run variance.

Bottom line: the paper confirms PoT was evaluated by executing Python (with math/sympy allowed) and using the execution result as the answer, and it documents multi-sample aggregation ($64$-sample self-consistency / $\text{Maj@K}$ analyses) that reduces sensitivity to nondeterminism. For exact sandbox parameters, library versions, and the matcher (string vs. numeric tolerance vs. symbolic comparison) you’ll need to consult the authors or the code/evaluation release (the paper itself does not include those engineering details).
