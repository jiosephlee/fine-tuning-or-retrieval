\title{Stack Exchange of the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

### How were the 7B pretraining mixture ratios enforced across 500B tokens—fixed sampling or curriculum scheduling?
Question:
For DeepSeekMath-Base 7B, the mix is 56% DeepSeekMath Corpus, 4% AlgebraicStack, 10% arXiv, 20% GitHub code, 10% general CC NL. Were these ratios enforced per-batch throughout training, adjusted over time (e.g., curriculum), or temperature-sampled? How did you prevent catastrophic forgetting of coding while maximizing math gains?
Answer:
Short answer: the paper describes DeepSeekMath-Base $7\mathrm{B}$ as a one‑stage continual pretraining run that uses a fixed global mixture of sources across the $500\mathrm{B}$ tokens ($56\%$ DeepSeekMath Corpus, $4\%$ AlgebraicStack, $10\%$ arXiv, $20\%$ GitHub code, $10\%$ CC NL). The authors do not describe any time‑varying curriculum or temperature‑sampling scheme in the paper; instead they report a mixed-data continual training setup and back that choice with ablations showing mixing helps avoid catastrophic forgetting.

Why I say this (grounded in the paper): Section "Training and Evaluating DeepSeekMath‑Base $7\mathrm{B}$" states the model was initialized from DeepSeek‑Coder‑Base‑v1.5 $7\mathrm{B}$ and “trained for $500\mathrm{B}$ tokens” with the data distribution explicitly given. In the "Lessons Learnt" experiments the authors directly compare two‑stage (code $\to$ math) versus one‑stage (mixed code $+$ math) training and report that math training after code training degrades coding performance, whereas mixing code and math tokens in one stage “effectively mitigates the issue of catastrophic forgetting.” Taken together, the paper presents the final recipe as continual pretraining on a mixed corpus (i.e., keeping code tokens present throughout) rather than a curriculum or reweighting schedule.

How catastrophic forgetting was controlled: the paper uses two pragmatic levers. First, the run is initialized from a code‑trained checkpoint (DeepSeek‑Coder‑Base‑v1.5), so the model starts with strong code priors. Second, the pretraining mixture explicitly contains a nontrivial fraction of code ($20\%$ GitHub code) during the entire $500\mathrm{B}$ token continual training; the authors state that “by including code tokens for continual training, DeepSeekMath‑Base $7\mathrm{B}$ effectively maintains the performance of DeepSeek‑Coder‑Base‑v1.5 on the two coding benchmarks.” Intuitively, keeping code examples interleaved during math training supplies continual gradient signals that keep code representations from drifting, while the code initialization makes transfer to math easier (and, per their ablations, code data also helps program‑aided math).

Implementation caveat: the paper does not spell out low‑level sampling mechanics (e.g., whether each mini‑batch strictly enforces the exact percentage, whether mixing was done at the file/chunk level, or whether they used reservoir/temperature sampling). The most natural reading of the text is a global, proportionate mixture sampled during continual training rather than a curriculum, but the exact per‑batch sampler is not documented. If you need implementation details (per‑batch enforcement, chunk-level mixing, shuffling policy), the paper’s appendix or the authors’ code/repo (or contacting the authors) would be the place to check.
