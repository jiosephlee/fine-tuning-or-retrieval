\title{A Textbook about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

Chapter 13: Evaluation Protocols, Contamination Control, and Formal Proofing

# Decontamination: exact n-gram matching (10-gram primary, 3-gram fallback)

Preventing benchmark contamination (data leakage) is a foundational requirement for reliable evaluation. In DeepSeekMath, the authors adopt a conservative, exact-matching decontamination rule applied to the math pre-training corpus mined from Common Crawl. Concretely, any training text segment that contains a 10-gram (ten consecutive tokens/words) that exactly matches any substring appearing in an evaluation benchmark is removed from the training corpus. This check is performed for the English benchmarks used in the paper (e.g., GSM8K, MATH) and for the Chinese benchmarks (e.g., CMATH, AGIEval) as well.

Because some benchmark items are shorter than ten tokens, the paper includes a fallback rule: for benchmark texts shorter than 10 tokens but at least 3 tokens long, exact matching is applied at the shorter length. In other words, if a benchmark example is, say, 6 tokens long, any training segment that exactly matches that 6-token sequence is removed. This two-tier rule—10-gram primary, 3-gram fallback—is a straightforward, conservative approach designed to minimize the chance that the model has seen benchmark problems or solutions during pre-training.

The intuition for this design is simple. Exact long n-gram matches (10-grams) are rare unless the same problem text or solution appears verbatim in the web crawl, so removing such matches reduces direct leakage with relatively few false positives. The fallback to shorter exact matches is necessary because some benchmark items are short; without it, short benchmarks could slip through. The method is intentionally strict: it sacrifices nothing in statistical validity at the expense of possibly removing some unrelated text that happens to contain an identical short phrase. The paper follows this rule as part of its broader decontamination pipeline to ensure reported benchmark numbers reflect genuine generalization rather than memorization.

# Prompting: few-shot CoT, PoT, and zero-shot settings

Prompt design in DeepSeekMath experiments uses three complementary styles depending on the evaluation goal: few-shot chain-of-thought (CoT), few-shot program-of-thought (PoT), and zero-shot prompts for baseline comparisons.

Few-shot CoT prompts present the model with a small number of exemplars where each exemplar includes a problem and a step-by-step (chain-of-thought) solution. This format encourages the model to produce stepwise reasoning in natural language when solving new problems. The paper uses few-shot CoT broadly to probe the model's ability to produce self-contained textual solutions without external tools across multiple benchmarks. Few-shot CoT is the primary evaluation format for many of the quantitative reasoning tasks in the study.

Few-shot PoT (program-of-thought) prompts are similar in spirit but the exemplars demonstrate solving problems by producing short programs (Python) that compute the answer. In PoT evaluations the model is prompted to output code that captures the reasoning and calculation; the executed program yields the final answer. The paper uses PoT for program-aided mathematical reasoning experiments (e.g., GSM8K and MATH in the tool-use setting).

Zero-shot prompts are also used as a baseline: the model is given only the instruction and the problem, without exemplars. The paper notes a practical observation comparing zero-shot and few-shot behavior: for DeepSeekMath the difference between zero-shot and few-shot improvement is smaller than for some closed models (e.g., GPT-4), indicating that on few-shot capability DeepSeekMath does not gain as much from added exemplars as some larger closed models do. Evaluators therefore report both styles where appropriate and compare to baselines using the same prompting regime.

Across all prompting regimes, the study keeps the evaluation protocol consistent for a benchmark: the same prompt template (CoT, PoT, or zero-shot) and the same few-shot exemplars are used to produce results reported in tables, so numeric comparisons reflect algorithmic and data differences rather than prompt mismatch.

# Program evaluation: Python execution with math/sympy

When program-of-thought or tool-integrated prompts are used, the evaluation pipeline executes the programs produced by the model and uses the execution outcome as the model's answer. The paper explicitly permits standard Python numeric and symbolic libraries such as the built-in math module and sympy. For each problem that is to be solved using program output, the model is prompted (few-shot PoT or tool-integrated prompt) to emit a Python program whose final printed or returned value corresponds to the problem answer. The evaluation then executes that program in a controlled sandbox and extracts the execution result; that result is treated as the canonical answer for scoring.

This execution-centered evaluation has two practical consequences. First, it moves the final-check burden from fragile string matching of free-text reasoning to deterministic execution: a correct program that computes the correct value yields a clear, machine-checkable answer. Second, it allows the model to rely on precise numeric and symbolic manipulation (via math and sympy) rather than attempting all calculation symbolically in text. In the paper, program-based evaluation was applied to datasets like GSM8K and MATH; DeepSeekMath models trained with code and math data demonstrated strong gains in the program-aided setting.

# Formal evaluation: informal-to-formal with Isabelle and Sledgehammer

Formal-mathematics evaluation in the paper targets the informal-to-formal autoformalization task: given an informal statement, its formal counterpart, and an informal proof sketch, produce a machine-checkable formal proof. DeepSeekMath-Base 7B is evaluated on the miniF2F benchmark using the Isabelle proof assistant as the verifier.

The evaluation procedure is as follows. The model is prompted (few-shot) to generate a formal proof script in Isabelle syntax corresponding to the informal proof. Since many model-generated proofs may be sketches or leave detailed lemma applications implicit, the verification pipeline uses Sledgehammer—an off-the-shelf automated prover integrated with Isabelle—to fill gaps and discharge sub-goals that the model left underspecified. A problem is counted as solved if Isabelle (with the assistance of Sledgehammer where applicable) accepts the generated script as a valid formal proof.

This evaluation is stricter than natural-language grading because Isabelle enforces full formal correctness: the proof must check mechanically. The paper reports that DeepSeekMath-Base shows strong few-shot autoformalization performance on miniF2F using this Isabelle+Sledgehammer pipeline, demonstrating that the math-centered pre-training improved the model's ability to generate machine-checkable formal artifacts.

# Metrics: accuracy, Pass@K vs Maj@K, self-consistency

Accuracy (percentage correct under a benchmark's official scorer) is the primary metric reported throughout the paper for single-run evaluations. For program outputs this means comparing the executed result to the expected value; for multiple-choice benchmarks it means selecting the correct choice; for formal proofs it means Isabelle accepts the script.

When evaluating randomized decoding or sampling-based strategies, the paper distinguishes two related ensemble metrics:

- Pass@K measures whether at least one of $K$ independently sampled answers is correct. Formally, if we sample $K$ outputs $\{o^{(1)},\ldots,o^{(K)}\}$ for a problem, then
  $$
  \text{Pass@}K = \mathbf{1}\!\left(\bigvee_{i=1}^K \text{correct}\big(o^{(i)}\big)\right),
  $$
  averaged across problems.

- Maj@K (majority accuracy) measures whether a strict majority of the $K$ samples are correct:
  $$
  \text{Maj@}K = \mathbf{1}\!\left(\sum_{i=1}^K \mathbf{1}\!\big(\text{correct}(o^{(i)})\big) > \tfrac{K}{2}\right),
  $$
  averaged across problems.

These two statistics capture different aspects of a model's predictive distribution. Pass@K is optimistic—rewarding diversity that yields a correct answer among samples—whereas Maj@K measures whether the model's sampling distribution concentrates around the correct solution.

The paper uses a “self-consistency” style majority-voting protocol in some evaluations: sample multiple chain-of-thought outputs for the same problem and take the majority-target answer as the final decision. As an example reported in the paper, self-consistency over $64$ samples for DeepSeekMath 7B produced $60.9\%$ accuracy on MATH. In the reinforcement-learning analysis, a key empirical observation is that reinforcement learning (GRPO in this work) tends to raise Maj@K substantially while Pass@K remains largely unchanged. This pattern suggests the RL fine-tuning made the model's output distribution more robust—higher probability mass near correct solutions—rather than increasing the chance that an otherwise unlikely correct sample appears among the top $K$ draws.

Because the paper uses sampling-based methods both for evaluation (self-consistency) and in RL (sampling groups of size $G$ during GRPO), the $K$ or $G$ values appear both in reported numbers and in training/evaluation protocols (e.g., $G=64$ was used in GRPO experiments).

# Answer normalization and scoring practices

Across the suite of benchmarks, the paper adheres to dataset-appropriate canonical scoring: numeric-answer problems are judged by whether the model's final answer (or the executed program's result) matches the expected numeric value, multiple-choice tasks are judged by the chosen option, and formal proof tasks are judged by the proof assistant's acceptance. For program-of-thought evaluations, the authors explicitly treat the program execution result as the evaluated answer.

For sampling-based ensemble methods (self-consistency, Maj@K/Pass@K), answers from multiple samples are aggregated according to the chosen rule (e.g., majority vote for self-consistency). In the reinforcement-learning phase, group-level reward normalization is used when converting reward model scores into per-token advantages. The normalization used in the paper (outcome supervision) is the standard z-score within a sampled group:
$$
\widetilde{r}_i = \frac{r_i - \mathrm{mean}(\mathbf{r})}{\mathrm{std}(\mathbf{r})},
$$
where $\mathbf{r}=\{r_1,\dots,r_G\}$ are the reward-model scores for a group of $G$ sampled outputs on the same question. For process supervision, where the reward model scores intermediate reasoning steps, the paper forms per-step normalized rewards $\widetilde{r}_i^{index(j)}$ in the same way and accumulates them into a token-level advantage:
$$
\hat{A}_{i,t} = \sum_{index(j) \ge t} \widetilde{r}_i^{index(j)}.
$$

These normalization steps ensure that reward signals are comparable within the sampling group and reduce scale issues when the normalized rewards are used to compute policy gradients or surrogate objective coefficients. Outside the RL thread, the paper follows each benchmark's standard evaluation script for final scoring; program execution outputs are compared deterministically to gold answers, and formal proofs are validated mechanically.

# Reporting multilingual results fairly

DeepSeekMath intentionally treats multilingual evaluation as a first-class concern. The DeepSeekMath Corpus is explicitly multilingual (predominantly English and Chinese), and decontamination was applied to both English and Chinese benchmarks. The supervised fine-tuning dataset includes Chinese materials (K–12 problems annotated with CoT and tool-integrated solutions), and the evaluation suite includes Chinese benchmarks such as MGSM-zh, CMATH, Gaokao-MathCloze, and Gaokao-MathQA.

To report multilingual results fairly the paper keeps the same high-level evaluation conventions across languages: use few-shot CoT for textual reasoning tasks, use PoT/tool-integrated evaluation when programmatic solving is under consideration, and apply the same decontamination and no-leakage safeguards to avoid training–test overlap in every language. By aligning prompt style and scoring procedures across languages and by explicitly removing benchmark content from the pre-training corpus for both English and Chinese, comparisons between models on different languages aim to reflect actual modeling capability rather than differences in data leakage or prompt design.

# Summary

This chapter codifies the evaluation procedures used in DeepSeekMath: strict decontamination via exact n-gram matching (10-gram primary, short-text fallback to 3-grams), consistent prompting regimes (few-shot CoT and PoT, with zero-shot baselines), program execution evaluation using Python with allowed libraries (e.g., math and sympy), formal proof verification via Isabelle assisted by Sledgehammer, and a careful use of sampling-based metrics (Pass@K, Maj@K, and self-consistency). Where sampling and RL are involved, rewards are normalized within groups (z-scoring), and process supervision accumulates per-step normalized rewards into token-level advantages. Finally, multilingual fairness is addressed by applying the same decontamination and evaluation discipline across English and Chinese benchmarks. These protocols together produce evaluations that are robust to contamination and that measure both single-run and distributional (sampling-based) competence of mathematical language models.
