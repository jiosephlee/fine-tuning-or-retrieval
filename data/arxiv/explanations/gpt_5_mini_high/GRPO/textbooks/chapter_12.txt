\title{A Textbook about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

Chapter 12: Pretraining Insights: Code Helps, arXiv Underwhelms

# Two-stage vs one-stage training with code and math

One of the clearest experimental threads in DeepSeekMath is a comparison between different schedules for exposing a model to code and mathematical text. The paper considers two broad paradigms. In the two-stage approach the model first undergoes an extended period of code-focused pretraining and is then further trained on math-specific data. Concretely, one setting in the ablations was "code training for $400\text{B}$ tokens $\rightarrow$ math training for $150\text{B}$ tokens" using the DeepSeek-LLM $1.3$B model as the substrate. The control two-stage experiment replaced the code stage with general web/text tokens (again $400\text{B} \rightarrow 150\text{B}$) to isolate the effect of code vs general pretraining. In the one-stage family of experiments the team either trained on math alone for $150\text{B}$ tokens or trained on a mixture where code tokens and math tokens were combined in the same stage (the mixture example in the paper mixes $400\text{B}$ code tokens with $150\text{B}$ math tokens in a single-stage run).

The comparison is designed to reveal two distinct tradeoffs: how code exposure changes the model’s capability to produce program-aided solutions, and how the ordering or mixing of domains affects retention of code abilities. Across these experiments the paper reports a consistent pattern: starting from a code-trained model and then continuing with math training tends to produce the best overall outcome for mathematical tasks, while a one-stage mixture can mitigate catastrophic forgetting of code but — in the smallest model regime studied ($1.3$B) — may hurt some tool-free math capabilities. The experimental setup therefore makes explicit that both the composition and the schedule of pretraining matter, and that empirical gains depend on how the two domains are combined in training rather than merely on aggregate token counts.

# Code pretraining boosts tool-based and tool-free math reasoning

A central empirical claim in the paper is that code pretraining provides meaningful benefits for mathematical reasoning, both when problems are solved by writing and executing programs (tool-based) and when the model is required to produce step-by-step natural-language solutions (tool-free). The two-stage experiments show that a model exposed to a long code pretraining phase before math training "already significantly enhances the ability to solve GSM8K and MATH problems using Python," and that subsequent math-focused training further improves those program-aided capabilities. In other words, code pretraining creates a stronger foundation for program-of-thought prompting and for generating executable programs that correctly implement a reasoning plan.

The benefit is not restricted to programs. The paper also reports that code pretraining produces moderate improvements on chain-of-thought style, tool-free mathematical reasoning. In the two-stage runs, the initial code phase boosts the efficiency of later math training and ultimately yields better tool-free results than starting without code pretraining. This finding suggests that what code training supplies is not only familiarity with APIs and program syntax but also improved procedural and stepwise generation behaviors that transfer into writing coherent natural-language chains of reasoning.

The authors are careful to note limits: combining code and math tokens in a single-stage run does not always replicate the two-stage benefit on tool-free math, at least for the smaller model scale they tested. They conjecture that this is an issue of capacity — a compact model may struggle to internalize both modalities simultaneously in one stage — but the empirical fact in their ablations is that code-first then math-second tends to be a robust recipe for improving both program-based and natural-language mathematical problem solving.

# Mixing code and math mitigates catastrophic forgetting for coding

A practical problem encountered in multi-domain continual training is catastrophic forgetting: when a model is trained on domain B after domain A, its performance on A can degrade. The paper documents this phenomenon in the context of code and math: when code training is followed by math-only training, the code capabilities that were previously learned suffer. In the authors’ words, "Math training following code training degrades coding performance."

To address that, they compare the two-stage schedule with a one-stage mixed schedule where code tokens and math tokens are presented together. The results show that mixing the two domains in one-stage training can effectively mitigate catastrophic forgetting: coding performance is better maintained, and program-aided mathematical reasoning benefits as well. In other words, simultaneous exposure reduces the domain shift between the stages and preserves the model’s ability to emit correct code.

This observation has a practical implication for dataset engineering: if preserving coding ability is important, interleaving or mixing code and non-code material can be preferable to a strict sequential handoff. That said, the paper highlights a tradeoff: while mixing helps retain code skills, in the smallest model experiments this came at some cost to tool-free math performance relative to the two-stage code-then-math approach. Thus the practitioner must choose a schedule based on the primary downstream priorities and the scale/capacity of the model.

# Math training also enhances general reasoning (MMLU, BBH)

Beyond narrowly improving mathematical benchmarks, the paper reports that math-focused pretraining has positive spillover effects on broader reasoning and knowledge tasks. When the DeepSeek-Coder backbone is continued with math pretraining to produce DeepSeekMath-Base $7$B, the model shows "significant enhancements in performance on MMLU and BBH over its precursor DeepSeek-Coder-Base-v1.5." Put simply, math training did not only sharpen arithmetic or contest-style problem solving: it also lifted performance on multi-domain reasoning and knowledge benchmarks.

Intuitively, math training emphasizes structured multi-step deduction, symbolic manipulation, and careful use of definitions and constraints. Those competencies are often useful in non-mathematical reasoning tasks that require multi-step logical thinking or disciplined application of knowledge. The empirical takeaway in the paper is that a targeted, high-quality math corpus can improve general reasoning metrics, reinforcing the idea that domain-specialized pretraining can transfer positively to related reasoning competencies.

It is important to note the context: these gains were observed when starting from a code-trained model and when using a carefully curated math corpus (the DeepSeekMath Corpus). The magnitude of transfer likely depends on both the starting point and the quality and diversity of the math training data.

# ArXiv-only training shows minimal or negative math gains

One of the surprising empirical findings the authors report is that arXiv-centric corpora — despite being a natural candidate for "mathy" content — did not improve mathematical reasoning in their ablations, and in some cases made performance worse. They evaluated two arXiv-heavy sources: MathPile (an $8.9\text{B}$-token multi-source corpus with over $85\%$ arXiv) and ArXiv-RedPajama (the arXiv LaTeX corpus cleaned to $28.0\text{B}$ tokens). They trained DeepSeek-LLM $1.3$B for $150\text{B}$ tokens and DeepSeek-Coder-Base-v1.5 $7$B for $40\text{B}$ tokens on these arXiv-only corpora.

Across a range of benchmarks — from quantitative reasoning datasets like GSM8K and MATH to multiple-choice STEM questions (MMLU-STEM) and even formal theorem proving tasks like miniF2F — the models trained on arXiv-only data showed no notable improvements and sometimes deteriorated. The paper therefore cautions against assuming that raw arXiv text is a panacea for mathematical pretraining: at least with the processing pipelines and model scales tested, the value of arXiv material for contest-style math and reasoning benchmarks appears limited.

The authors emphasize that this is an empirical observation with caveats (below), but the clear message from their ablations is that not all math-labeled data is equally useful. Simply adding a large volume of academic papers to your pretraining mix does not guarantee better downstream math reasoning.

# Caveats: tasks not covered, mixtures, potential scale effects

The arXiv finding, and several of the other ablation results, come with important limitations the authors explicitly state. First, some classes of mathematical tasks were not examined in these experiments; for example, they did not study the effect of arXiv tokens on tasks such as "informalization of theorems" (converting formal statements or proofs to informal language). It is possible that arXiv content is more useful for those niche tasks than for the contest-style benchmarks used here.

Second, the experiments considered arXiv in isolation or in particular mixtures; the interaction effects between arXiv and other data types (web math pages, code, textbooks, etc.) are not fully explored. The paper leaves open the possibility that arXiv tokens could be beneficial when combined with other curated material or processed differently.

Third, model scale matters. The negative or neutral results for arXiv-only corpora were observed at the scales studied ($1.3$B and $7$B). The paper explicitly notes that benefits from arXiv may appear at larger parameter scales, and they do not rule out a different outcome for much larger models. Finally, when the authors observed that mixing code and math sometimes degraded tool-free math for $1.3$B models, they conjectured that limited capacity was to blame; larger models may behave differently when exposed to mixed-domain training.

These caveats underline a general methodological lesson: ablation results are conditional on preprocessing choices, mixture ratios, schedules, and model scale. The empirical conclusions in the paper are robust within the experimental regime they studied, but the authors recommend cautious generalization.

# Data quality and diversity over sheer parameter count

A unifying implication of the experiments is that the composition and quality of pretraining data can be at least as important as raw model size. The paper highlights this point by noting that DeepSeekMath-Base $7$B — trained heavily on a carefully curated, large, multilingual DeepSeekMath Corpus ($120\text{B}$ math tokens extracted and filtered from Common Crawl, plus code and other data) — attains performance competitive with a much larger closed-source model (Minerva $540$B). That outcome supports the argument that a smaller model trained on high-quality, diverse, and task-relevant corpora can rival larger models that did not receive the same focused data engineering.

The DeepSeekMath Corpus itself was constructed with an iterative selection pipeline, manual URL-level curation, and benchmark decontamination; the paper credits this engineering for the strong downstream results. The ablations with arXiv and the positive effects of code pretraining together emphasize that not only the quantity but the nature of the tokens matters: web-derived math pages, code, multilingual content, and domain diversity each play different roles. For practitioners, the operational takeaway is to invest in careful data selection, preprocessing, and mixture design — especially when compute and model size are constrained.

Concluding synthesis

Summarizing the chapter’s main empirical lessons: (1) code pretraining helps — it improves program-based reasoning strongly and also provides gains for tool-free chain-of-thought reasoning; (2) the training schedule matters — a code-then-math two-stage recipe was a reliable way to get strong math performance in the authors’ experiments, while one-stage mixing can prevent forgetting at the cost of some tool-free gains for compact models; (3) arXiv-only corpora are not a guaranteed source of improved contest-style math reasoning and in the tested setups often yield minimal or negative effects; and (4) data quality, diversity, and curation can compensate for parameter count, enabling a $7$B model to approach the performance of much larger models when trained on a well-engineered corpus. The paper’s ablations supply practical guidance for anyone designing pretraining mixes for mathematical reasoning: begin from a code-capable backbone when possible, curate and diversify math web data, beware of naive reliance on arXiv, and adapt mixture/schedule choices to model capacity and primary downstream goals.
