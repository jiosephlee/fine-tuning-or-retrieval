\title{Blogs about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

# From CoT to Code: How Instruction Tuning and Tool Use Power DeepSeekMath

DeepSeekMath shows that a compact, well-tuned 7B model can punch well above its weight on hard math benchmarks when you combine three ingredients: a large, targeted instruction-tuning set, mixed reasoning formats (chain-of-thought and program-of-thought), and the ability to run code during problem solving. In this post I unpack the 776K-example instruction-tuning corpus the authors built, explain the three reasoning formats used in training and evaluation, and clarify why allowing Python (e.g., using libraries such as math and sympy) pushes DeepSeekMath-Instruct 7B’s accuracy on the competition-level MATH benchmark close to 60%.

## What the 776K instruction-tuning set contains

The instruction-tuning collection is deliberately math-focused and multilingual. It contains 776K examples covering English and Chinese problems across a wide range of mathematical topics and difficulty levels. The English portion includes annotated GSM8K and MATH problems (with tool-integrated solutions), a subset of MathInstruct, and the Lila-OOD training set. The Chinese portion is K–12 material spanning 76 sub-topics, with solutions provided both as chain-of-thought (CoT) and as tool-integrated reasoning.

Training specifics matter: examples were randomly concatenated to fill a 4K-context window, and DeepSeekMath-Instruct 7B was trained for 500 steps with batch size 256 and a constant learning rate of 5e-5. The mix of data formats (CoT, program-of-thought, and tool-integrated solutions) is a central design choice: the model sees natural-language reasoning traces, executable program traces, and hybrids of the two during supervised fine-tuning.

## CoT, PoT, and tool-integrated reasoning — what they are and how they differ

Chain-of-thought (CoT) is the familiar natural-language step-by-step reasoning format: the model writes out intermediate steps in prose. CoT helps models expose multi-step reasoning and has been effective for many grade-school and conceptual problems.

Program-of-thought (PoT) is different: the model generates a short program that implements the solution strategy. In this work PoT examples are Python programs where libraries such as math and sympy are allowed. The program is executed and the execution result is treated as the final answer. Because the program itself can express precise arithmetic, symbolic manipulation, and deterministic control flow, PoT offloads tedious and error-prone computations to the interpreter.

Tool-integrated reasoning is a hybrid: the model produces both a natural-language rationale and program fragments that are executed as part of the solution. This allows the model to explain the approach while delegating heavy computations to code.

During evaluation the authors use few-shot prompting tailored to each format. For PoT and tool-integrated evaluations, the generated Python is executed and the run-time result is compared to the ground truth.

## How much does instruction tuning + tools improve performance?

DeepSeekMath-Instruct 7B, trained on the 776K corpus, already establishes a strong baseline. In the pure CoT (no external code execution) setting it achieves a high level of step-by-step reasoning performance on MATH, outperforming other 7B open-source models and even exceeding many proprietary models by a substantial margin. Concretely, the paper reports that DeepSeekMath-Instruct’s MATH score before reinforcement learning was around 46.8% (chain-of-thought, no tools), and its GSM8K score was around 82.9%. These numbers place the 7B model ahead of other 7B counterparts and competitive with some 70B instruction-tuned models.

Allowing program execution changes the story. When DeepSeekMath-Instruct is evaluated in a setting that permits Python programs (libraries such as math and sympy are available), its accuracy on MATH “approaches” 60%—a large jump relative to the no-tool CoT result, and better than all other open-source models in the comparison. In short: instruction tuning makes the model good at reasoning in the abstract, and giving it a code execution channel lets it verify and carry out the heavy lifting reliably.

(Reinforcement learning with GRPO later improves the chain-of-thought-only numbers further — for example, MATH from 46.8% → 51.7% and GSM8K from 82.9% → 88.2% — but the point here is that the supervised instruction-tuning set plus tool use already yields a big practical gain.)

## Why running Python (and sympy) helps — a technical perspective

There are three complementary reasons why program execution closes a large part of the remaining gap:

1. Deterministic arithmetic and exactness. Human-style CoT reasoning often carries numeric approximations, messy fraction arithmetic, or repeated digit-level operations where mistakes accumulate. When the model emits a Python program, the interpreter performs exact arithmetic (or high-precision numeric ops), removing a large source of error.

2. Symbolic manipulation and algebraic simplification. Libraries like sympy let the model delegate symbolic transformations (expand, factor, solve symbolic equations). Problems that require algebraic rearrangement or closed-form simplification are cumbersome to express reliably in pure natural language but straightforward to encode in a small program using symbolic APIs.

3. Verifiability and composability. A program can be executed to produce a trace and final numeric output that the system can check. This reduces ambiguity and gives a crisp correctness condition: the program’s result either matches the target or not. That deterministic check is a powerful training and evaluation signal, which is particularly helpful for benchmarks that reward exact answers.

The supervised tuning set exposes the model to these programmatic solution patterns, so at inference time the model is more likely to produce correct, executable code for hard computation-heavy problems.

## When natural-language reasoning is enough — and when to call code

Natural-language CoT often suffices for problems that hinge on conceptual steps, logic, or small, easy-to-follow arithmetic. CoT is especially effective when the reasoning path is the main challenge (e.g., choosing the right modeling approach, setting up a proof sketch, or following a few algebraic manipulations).

You should call code when a problem requires either long chains of numeric operations, cumbersome symbolic manipulation, or high-precision computation. The paper uses the phrase “intricate computations” to describe cases where PoT and tool integration are helpful. In practice, that includes many problems on the upper end of MATH: long algebraic simplifications, systems of equations requiring exact solvers, or cases where a small programming loop or symbolic solver can replace dozens of brittle textual steps.

## Practical takeaways

- A focused, large instruction-tuning set that mixes CoT, PoT, and tool-integrated examples (the 776K examples in DeepSeekMath-Instruct) trains a 7B model that rivals much bigger instruction-tuned models.
- Program-of-thought / tool-integrated evaluation—i.e., letting the model emit Python and use libraries such as math and sympy—yields a substantial accuracy boost on hard math benchmarks. On MATH, that mode “approaches” 60% accuracy for DeepSeekMath-Instruct 7B.
- Use CoT when the bottleneck is strategy or conceptualization; use PoT/tool execution when the bottleneck is precise arithmetic or symbolic work.
- Initializing from a code-pretrained checkpoint (DeepSeek-Coder-Base-v1.5) and including code-style data in training helps: the paper finds that starting from a code-trained model benefits program-aided reasoning.

## Closing thoughts

DeepSeekMath demonstrates a practical path to much stronger mathematical performance without needing massive parameter counts: build a careful instruction-tuning corpus that teaches both natural-language reasoning and programmatic solution patterns, and allow the model to execute code for the heavy computational work. The result is a small, fast model that moves well beyond raw CoT performance and—for many competition-style math problems—comes close to the accuracy of much larger systems once a code-execution channel is available. Future work (and the paper’s RL experiments) explores how to make these outputs even more reliable and robust, but the core finding is clear: pairing CoT with executable PoT and tool integration is a high-leverage strategy for mathematical reasoning.
