\title{Blogs about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

# Does Coding Improve Reasoning? What DeepSeekMath Teaches Us

DeepSeekMath ran a focused set of pre‑training ablations to answer a deceptively simple question: does training on code help a language model reason better about math? The headline finding is clear and nuanced: code pretraining does help—especially for program‑aided (tool‑using) mathematical reasoning—and it also produces useful spillover gains on general reasoning benchmarks. But the details matter: the training schedule (two‑stage vs. one‑stage), model capacity, and the choice of mixing strategy create trade‑offs such as catastrophic forgetting. Below I unpack what the DeepSeekMath paper actually did, what it found, and what that implies for people designing models or training curricula.

## The experimental setups (what “code training” meant)

DeepSeekMath compared a few concrete pretraining regimes using their 1.3B‑parameter research model (DeepSeek‑LLM 1.3B):

- Two‑stage: pretrain on code for 400B tokens, then continue training on math for 150B tokens. This mirrors a sequential curriculum (code → math).
- Two‑stage control: pretrain on general (non‑code) text for 400B tokens, then math for 150B tokens.
- One‑stage (math only): train on 150B math tokens.
- One‑stage (mixed): train on a mixture that includes 400B code tokens plus 150B math tokens in the same stage (so code and math are mixed rather than sequenced).

For evaluation, DeepSeekMath used both “no‑tool” chain‑of‑thought prompting and “program‑aided” evaluation where the model writes Python (program‑of‑thought) and the generated program is executed (libraries like math and sympy were allowed). Benchmarks included GSM8K and MATH for quantitative reasoning, and separate coding benchmarks for measuring coding capability.

## What they found — the short version

- Code pretraining reliably improves program‑aided mathematical reasoning. That is, models that see lots of code get better at writing correct Python solutions that can be executed to produce answers.
- Code pretraining also helps no‑tool (chain‑of‑thought) mathematical reasoning under the two‑stage schedule: an initial code stage yields moderate gains, and a subsequent math stage produces the best no‑tool performance.
- Sequential (two‑stage) code → math training can cause catastrophic forgetting of coding skills: the math stage can degrade some coding capability relative to a code‑only model.
- Mixing code and math in a single stage mitigates catastrophic forgetting and preserves coding strength, while also improving program‑aided math; however, for the smaller models tested (1.3B), this mixed regime can compromise the no‑tool (chain‑of‑thought) math performance compared to the two‑stage code→math sequence.
- Separately, training on math data (the DeepSeekMath corpus) also produced spillover gains on non‑math reasoning benchmarks (MMLU and BBH), showing that math training can strengthen more general reasoning skills.

All of the above are direct findings reported in the paper’s ablations; where the authors offer a hypothesis, I will label it as such below.

## Digging into the trade-offs

Why does code help program‑aided math? The paper’s experiments show stronger performance at writing executable solutions after code pretraining. The intuitive interpretation is straightforward and consistent with the empirical results: exposure to code improves a model’s ability to produce correct, executable programs (better syntax, API usage, algorithmic structure), and when the evaluation accepts programs and executes them, that capability translates directly into higher measured accuracy.

Why does code also help no‑tool chain‑of‑thought math (in the two‑stage case)? DeepSeekMath reports that starting from code gives a modest boost to chain‑of‑thought reasoning, and that a follow‑up math stage amplifies that into the best no‑tool performance. One plausible reading—supported by the authors’ experimental description—is that code training teaches structured, stepwise problem decomposition and precise arithmetic handling, which can help generate clearer reasoning traces even when no external program is executed.

Where things become tricky is catastrophic forgetting. The authors observe that simply doing code → math can reduce the model’s coding ability: the final model is stronger on math but worse on some coding benchmarks than a pure code‑trained model. That is the classic sequential‑fine‑tuning trade‑off: when you keep training on new data that emphasizes other skills, previously learned behaviors can erode.

Mixing code and math in one stage is the practical work‑around tested by the paper. Training on an interleaved code+math mixture (rather than sequentially) largely avoids the post‑math drop in coding performance and still delivers strong program‑aided math gains. But this mixed recipe had a surprise downside for the smaller model scale tested: mixed training hurt the no‑tool chain‑of‑thought performance relative to the sequential code→math path. The authors conjecture that at 1.3B parameters the model may not have enough capacity to absorb both distributions simultaneously without some interference; they leave open whether larger models would behave differently.

## Spillover: math training helps broader reasoning

An important secondary finding is that math pretraining is not purely domain‑specialized. When applied to their larger 7B base model (DeepSeekMath‑Base 7B, initialized from a code‑trained model), math pretraining improved performance on MMLU and BBH—benchmarks of general knowledge and multi‑step reasoning. In short, a math‑heavy curriculum delivered gains beyond math tasks, which suggests math pretraining can be a lever for general reasoning improvements as well.

## Practical recommendations (based on the experiments)

- If your primary goal is to get models that write correct executable solutions (program‑aided math), training on code is highly beneficial. Both sequential and mixed regimes show gains; mixing helps preserve coding skills.
- If you want the best chain‑of‑thought / no‑tool math performance on smaller models, the two‑stage approach (code → math) looks preferable: code pretraining gives a head start and a dedicated math stage refines reasoning traces.
- If you must keep strong coding capability alongside math skill (e.g., models that will be used for both code generation and program‑aided reasoning), mix code and math during training or use approaches that replay code data during math fine‑tuning to reduce catastrophic forgetting.
- Be mindful of model scale. The paper’s negative interaction between mixed training and no‑tool math was observed on a 1.3B research model; the authors note that results could change at larger scales.

## Open questions and next steps

The paper leaves several natural questions for follow‑up:

- How do these trade‑offs change with larger model scales (e.g., 7B, 70B)? The capacity hypothesis needs empirical testing.
- What is the optimal mixing ratio and schedule to maximize both coding and no‑tool math performance?
- Can rehearsal methods, adapters, or multi‑task objectives avoid catastrophic forgetting while preserving the simplicity of mixed training?
- Why did arXiv content (in other parts of their study) not help math performance? Data quality and domain mismatch deserve deeper analysis.

## Bottom line

DeepSeekMath’s ablations give a clear practical answer: yes, code training improves mathematical reasoning—most decisively when the evaluation allows programmatic solutions, and also (under a two‑stage schedule) for chain‑of‑thought reasoning. But the gains come with trade‑offs. Sequential code→math is a strong recipe for no‑tool math, while mixing code and math avoids catastrophic forgetting and is especially effective for program‑aided math. Which path to pick depends on whether you prioritize executable program synthesis, pure chain‑of‑thought performance, or the need to preserve coding skills alongside math ability—and model capacity matters.
