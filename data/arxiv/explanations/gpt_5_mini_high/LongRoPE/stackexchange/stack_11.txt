\title{Stack Exchange of the Paper: "LongRoPE: Extending LLM Context Window Beyond 2 Million Tokens"}

### How are 2M-token evaluations performed given \(O(n^2)\) attention cost—full context or chunked?
Question:
Naively attending over \(2{,}048\text{k}\) tokens is infeasible for standard dense attention. In the long-sequence experiments you mention sliding windows (e.g., 256k). During Books3 and passkey evaluations, does the model have full attention over the entire \(L'\), or is attention restricted to a window and state is streamed/evicted? If it is chunked/streamed, in what sense is the model truly operating with an effective context of \(\approx 2\text{M}\) tokens?
Answer:
Short answer: the paper does not run a single dense $O(n^2)$ attention over $2{,}048\text{k}$ tokens in one monolithic forward pass. For long-document perplexity and Books3 evaluation the authors explicitly use a sliding / chunked evaluation (they say “for evaluation efficiency … use a sliding window of $256\text{k}$”), and more generally they compute perplexities with sliding windows rather than trying to allocate an $L'=2{,}048\text{k}$ attention matrix at once. The paper does not give low‑level implementation details for the passkey runs, so it does not claim a single-shot dense $2\,$M-token matmul was performed there either.

Why this matters: dense attention costs $O(n^2)$ memory and compute, so feeding $2\,$M tokens in one shot is essentially infeasible on a single GPU. The standard, practical way (and the one used in the paper for perplexity/Books3) is sliding-window evaluation: you present manageable windows of size $W$ (the paper uses $256\text{k}$ windows in Books3), slide them across the long text with some stride, and accumulate log‑likelihoods. That keeps each forward pass at $O(W^2)$ memory while letting you evaluate behavior over very long documents without ever allocating an $O(L'^2)$ attention matrix for $L'=2\,$M.

What “effective $2\,$M context” means in this work. LongRoPE is primarily about changing the RoPE positional mapping so the model has meaningful rotary encodings up to very large absolute indices. There are two different senses in which a model can “use” a $2\,$M context:

- Positional capacity: after LongRoPE the model can accept position indices up to $\sim 2\,$M and compute sensible relative/absolute encodings for them. That is what the paper demonstrates and what they mean by “extending the context window to $2{,}048\text{k}$.”

- Runtime attention scope: whether the model actually attends to $2\,$M tokens simultaneously depends on how you do inference. If you (a) feed the whole $2\,$M tokens at once, you obtain true full‑context attention semantics but at prohibitive $O(L'^2)$ cost unless you shard KV memory across many GPUs or use other heavy engineering; or (b) stream the text and keep per‑layer key/value caches (incremental caching), in which case the model can in effect attend to the entire past history because every new step attends to the cached keys/values — that yields the same semantics as full attention but is implemented incrementally (memory grows $O(L')$ and total compute is still quadratic overall but distributed over steps). If instead you only evaluate with smaller, disjoint windows, then the model only “sees” and attends within the window (effective context $=$ window size).

Paper facts vs. inference gaps: the paper explicitly documents chunked/sliding-window evaluation for Books3 and uses sliding-window procedures for perplexity experiments (they report different window sizes/strides in the experimental section). It does not give a detailed account of how the passkey runs were implemented at the low level (KV sharding, streaming infrastructure, number of GPUs, etc.). So the safe reading of the experiments is that they tested the model’s positional capability up to $2\,$M and evaluated using practical chunking/streaming strategies rather than attempting an impractical single-shot $2\,$M dense attention on a single device.

If you want to reproduce true full‑history behavior (so that the model literally attends over $2\,$M tokens of content), you will need to run inference with either (1) incremental KV caching (streaming) while ensuring you have enough memory or (2) a distributed/sharded KV implementation that stores keys/values across devices. If you only want to evaluate modeling quality over long texts without full simultaneous attention, sliding-window evaluation (the approach the paper uses for Books3) is the standard, much cheaper option.
