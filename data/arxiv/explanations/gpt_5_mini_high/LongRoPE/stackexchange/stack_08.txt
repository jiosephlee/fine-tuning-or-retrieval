\title{Stack Exchange of the Paper: "LongRoPE: Extending LLM Context Window Beyond 2 Million Tokens"}

### Exactly how is perplexity computed during search: what context and masking are used?
Question:
When evaluating a candidate schedule, do you compute token-level negative log-likelihood over the entire long document, or only over suffixes (e.g., beyond 4k)? Are you using a fixed sliding-window length, and if so, what attention/memory is available across windows? Clarifying the exact perplexity protocol would help understand what the search is optimizing.
Answer:
Short answer: the search evaluates standard autoregressive next‑token loss (i.e. $\text{token NLL} \to \text{perplexity}$) on long text segments whose length meets the target context size, with the candidate RoPE rescale schedule applied to positions inside those segments. The paper uses a small set of long validation samples per candidate (5 PG19 samples for targets $\le 256k$, 3 Pile‑Books3 samples for very large targets) and ranks candidates by the averaged perplexity computed on those segments. The model uses ordinary causal attention inside each evaluated window; there is no extra cross‑window memory mechanism during the search/evaluation passes reported.

What the paper actually says (and what that implies)
- The objective being minimized in the search is the next‑token prediction loss (they explicitly write that the search is guided by perplexity / next‑token loss in Eq. (problem) and in the surrounding text). Concretely, this means the usual autoregressive token negative log‑likelihood is computed and averaged (then exponentiated to give perplexity in reporting).
- Candidates are applied to full long inputs $X$ with the constraint that each sample $x$ satisfies $|x|\ge L'$, where $L'$ is the target context length. The RoPE transform used for inference is exactly as defined in the paper (positions $n<\hat n$ keep original RoPE; positions $n\ge\hat n$ use the candidate rescale factor).
- For search cost reasons they do not evaluate on entire corpora: for target windows within $256k$ they compute perplexity on 5 random PG19 validation samples (each at least $L'$ long); for windows $>512k$ they use 3 Pile‑Books3 samples (see the "Search" paragraph in Setup). The paper therefore evaluates candidates by averaging the standard token NLL across those selected long segments.
- For the main perplexity evaluations reported across many context lengths the paper says they use a sliding‑window evaluation with a step of $256$ tokens (they write “sliding window of $256$”), and for the very long Books3 run they say “sliding window of $256k$”. That is the evaluation protocol used to produce the curves/tables; the search itself is described as using the small set of long samples above.

Points the paper does not fully specify
- The paper does not give a line‑by‑line implementation description of how they chop/slide segments during the search (for example, whether a candidate is evaluated on a single contiguous chunk of length $L'$ taken from a sampled document, or on multiple overlapping $L'$ windows from that document and then averaged). It only states the minimum length requirement $|x|\ge L'$ and the small sample counts used for candidate scoring. It likewise does not state any special masking beyond the standard causal attention mask inside the evaluated window.
- The paper does not introduce any persistent hidden‑state / cross‑window memory for search or evaluation. From the text it follows that windows are processed with the model’s normal causal attention over the window (with RoPE modified per the candidate), and different windows are independent evaluation passes.

Intuition / consequence for what the search is optimizing
Because search minimizes the standard next‑token loss on long segments (not just the tail beyond some baseline context), candidate schedules are rewarded for preserving short‑range modeling (tokens early in the window still contribute to loss) while also improving long‑range positional discriminability. The $\hat n$ parameter (keep original RoPE for the first $\hat n$ tokens) explicitly lets the search protect the important early positions; the averaged perplexity over the selected long samples is the scalar the evolutionary search uses to pick better per‑dimension rescale schedules.

If you need exact per‑token bookkeeping (e.g. whether losses in each evaluated window exclude some warm‑up tokens, or exactly how many windows per document were averaged during search) the paper does not publish that low‑level implementation detail; the released code / evaluation scripts (the authors say code will be released) or asking the authors will give the definitive answer.
