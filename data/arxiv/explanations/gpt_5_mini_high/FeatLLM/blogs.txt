# Turn LLMs into Feature Engineers: The Big Idea Behind FeatLLM

Large language models (LLMs) are great at reasoning from text, but using them as a prediction engine for every row of a tabular dataset is slow, expensive, and fragile when your input prompt gets long. FeatLLM takes a different approach: instead of asking an LLM to predict each example, it asks the LLM to write human-readable rules (if-then style conditions) that capture useful patterns in the data. Those rules are converted into binary features and a very simple downstream model uses those features to make predictions. The result: faster inference, fewer LLM calls, and strong few-shot performance on tabular problems.

## The intuition in one paragraph

Think of the LLM as an expert feature engineer. Given a short description of the task, feature definitions, and a handful of labeled examples, the LLM explains which columns matter and formulates concise rules for each class (e.g., "age > 65 and cholesterol > 200"). Each rule becomes a binary feature indicating whether a sample satisfies it. A low-capacity model (a linear classifier with non-negative weights) then learns how to combine these rule-features to produce class probabilities. Because the heavy lifting (the LLM reasoning) happens once during feature construction, inference only needs the simple model — no per-sample LLM calls.

## How FeatLLM works (step by step)

1. Prompt the LLM to extract rules. The prompt is structured into three parts:
   - Basic information: the task description, feature names and types, and a few serialized examples. The serialization uses a simple text format like
     $$
     \text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = ``f_1\ \text{is}\ \mathbf{x}^i_1.\ ...\ f_d\ \text{is}\ \mathbf{x}^i_d.\ \text{Answer:}\ \mathbf{y}^i"
     $$
   - Reasoning instruction: a two-step guidance that first asks the LLM to state general, prior-knowledge relationships between features and the label (without using examples), then asks it to derive concrete rules using the few-shot examples. This two-step separation helps prevent the LLM from latching on to spurious correlations in the tiny training set.
   - Response instruction: a required, parseable format and a fixed number of rules per class (the paper uses 10 rules per class) so outputs are consistent.

2. Parse rules into executable checks. LLM outputs are natural-language rules which can vary in syntax. Rather than building a brittle hand-written parser, FeatLLM asks an LLM to translate those rules into small Python snippets (aided by clear function input/output specs). The generated code is executed (e.g., via Python's exec()) to turn rules into binary features.

3. Fit a simple downstream model. For class $k$ and sample $i$, let the binary rule-feature vector be $\mathbf{z}_k^i \in \{0,1\}^R$ where $R$ is the number of rules per class. FeatLLM uses a linear logit
   $$
   \text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,
   $$
   and converts logits to probabilities with a softmax:
   $$
   \mathbf{p}^i = \text{Softmax}([\text{logit}_1^i,\dots,\text{logit}_c^i]).
   $$
   Weights $\mathbf{w}_k$ are learned with cross-entropy loss; the $\max(\cdot,0)$ projection enforces non-negative contributions so a rule cannot actively reduce a class score.

4. Ensembling and bagging for robustness and prompt-size control. The whole process (rule generation → parsing → fitting) is repeated $T$ times with randomized factors (higher sampling temperature, shuffled demonstration order, feature/instance bagging). Each trial gives a classifier; final predictions average probabilities across trials. Bagging lets each LLM prompt be small (avoid hitting token limits) and the ensemble compensates for occasional bad rules.

## Why this is useful

- No per-sample LLM calls at inference: once rules and the linear weights are learned, prediction is as cheap as evaluating a few boolean checks and a dot product. This makes FeatLLM's inference time comparable to conventional models (e.g., logistic regression) rather than being dominated by costly LLM inference.
- API-only and prompting-friendly: FeatLLM doesn’t require fine-tuning the LLM or access to model checkpoints. It works with inference-only APIs (the experiments used GPT-3.5) and avoids long single-shot prompts by using bagging and ensembling.
- Interpretable features: rules are human readable. That helps debugging, auditing, and spotting when an LLM relied on questionable prior knowledge.
- Few-shot strength: across 13 tabular datasets from different domains (Adult, Bank, Blood, Car, Communities, Credit-g, Diabetes, Heart, Myocardial, Cultivars, NHANES, Sequence-type, Solution-mix), FeatLLM consistently ranks first or second among baselines. The paper reports that FeatLLM with just 4 shots can match many conventional methods trained with 32 shots and that it outperforms competing LLM-based approaches such as TabLLM and STUNT by about 10% on average.

## Practical settings used in the paper

- Backbone LLM: GPT-3.5 (but the method is LLM-agnostic).
- Prompting hyperparameters: temperature 0.5, top-p = 1.
- Ensemble size: $T=20$ trials.
- Rules per class: $R=10$.
- Downstream optimization: Adam with learning rate 0.01 for 200 epochs; $k$-fold CV to choose epochs.
- Training cost: reported to need only ~30 API queries in the evaluation setup — a modest budget that can be parallelized.

These are sensible defaults the authors found effective; the paper also reports that performance improves with more ensembles up to a point (convergence around 20) and that 10 rules per class balances prompt length against information content.

## Ablations and robustness checks (high level)

- Removing weight tuning (just summing rule indicators) hurts performance, especially when more labeled examples are available (tuning helps when you can estimate importance).
- Omitting the two-step reasoning or feature descriptions in the prompt reduces performance in low-shot settings — highlighting how prompt structure and prior-knowledge elicitation matter.
- The ensemble consistently improves results and helps the model be robust to occasional bad rules.
- When unrelated ("spurious") columns were appended to a target dataset, FeatLLM experienced smaller performance degradation than several baselines; noisy rules stemming from those irrelevant columns constituted only about 1–2% of generated rules in the experiments. Still, the authors note FeatLLM can pick up spurious patterns if the attached columns are closely related to the task in a misleading way.

## Limitations and next steps

FeatLLM is deliberately targeted at few-shot tabular learning. It relies on the LLM's prior knowledge, which is a strength but also a risk: biases or misinformation in the LLM may influence rule generation and therefore predictions. The method can still produce spurious rules under some conditions. The paper frames several follow-ups: scaling to larger labeled datasets, supporting richer feature types beyond binary rule indicators, and deeper work on interpretability and bias analysis.

## Bottom line

FeatLLM reframes the role of LLMs for tabular tasks: from an expensive per-sample predictor to a small-team collaborator that writes useful, human-readable features. That simple shift — generate rules once, learn simple weights, and ensemble for robustness — delivers faster inference, lower LLM cost, and strong few-shot accuracy across diverse tabular datasets. If you want to bring LLM knowledge into a production tabular pipeline without turning every prediction into an API call, FeatLLM is a compelling pattern to try.



# Inside the Pipeline: How FeatLLM Turns Rules into Predictions

Large Language Models (LLMs) are surprisingly good at reasoning about a task when you describe it in natural language. FeatLLM takes that ability and repurposes it: instead of asking an LLM to predict every test sample, it asks the LLM to act as a feature engineer — to write human-readable rules that capture class-defining conditions, turn those rules into binary features, and then learn a tiny supervised model on top. The result is a fast, interpretable inference pipeline that needs only a simple model at runtime while still leveraging LLM priors during development.

Below I walk through FeatLLM step by step: prompt construction, two-stage reasoning to extract class-specific rules, translating rules to executable code, converting rules into binary features, training a lightweight non-negative linear model, and finally ensembling with bagging for stability and to control prompt size.

## 1) Start with a well-structured prompt

FeatLLM's prompts are deliberately structured so the LLM behaves like an expert feature engineer. Each prompt has three parts:

- Basic information description. This gives the task (e.g., the target label and question), feature names and type/definitions, and a few serialized training examples. FeatLLM serializes a labeled example $(\mathbf{x}^i, \mathbf{y}^i)$ together with feature names $F=\{f_j\}_{j=1}^d$ as plain text, following the format used in prior LLM-for-tabular work:
  "Serialize($\mathbf{x}^i,\mathbf{y}^i, F$)" →  
  " $f_1$ is $\mathbf{x}^i_1$. ... $f_d$ is $\mathbf{x}^i_d$. Answer: $\mathbf{y}^i$ "

- Reasoning instruction. This is the core nudge that changes how the LLM uses its knowledge. FeatLLM uses a two-step reasoning instruction: first ask the LLM to infer general tendencies or causal relations between features and the task using world knowledge (no examples), then ask it to derive concrete, class-specific rules using the few-shot examples plus the inferred tendencies. This separation discourages deriving spurious correlations purely from the tiny labeled set and helps focus rule generation on semantically meaningful features.

- Response instruction. To make downstream automation feasible, the prompt constrains how the LLM should format rules (e.g., one rule per line, fixed templates for numeric vs categorical conditions). The system also fixes a target number of rules per class (the paper uses 10) so prompts remain bounded.

## 2) Two-stage reasoning → class-specific rules

The two-stage reasoning is simple but important:

- Stage 1 (prior-first): Ask the LLM, “Given the task and the feature descriptions, what general relationships or tendencies can you expect between features and the target?” This step leverages the LLM’s external knowledge and prevents overfitting to a few noisy examples.

- Stage 2 (data-aware): Then ask the LLM to produce concrete rules for each class using the few-shot examples plus the Stage 1 insights. Example rules are constrained to a parseable format (e.g., comparisons for numeric attributes, matching for categorical attributes). FeatLLM extracts a fixed number $R$ of rules per class; in experiments $R=10$ was used.

Because the LLM can still output varied syntax (for example writing "greater than" instead of the symbol "$>$"), FeatLLM anticipates parsing variability.

## 3) Turn natural-language rules into executable code

Parsing natural-language rules reliably is tricky if you try to hard-code all syntactic variants. FeatLLM takes a pragmatic approach: it asks the same LLM to produce the parsing code. The pipeline includes the function signature, input/output contract, and the plain rules, and then prompts the LLM to emit simple Python code that computes whether each rule is satisfied for a given sample.

Those code snippets are executed (the paper uses Python’s built-in execution, e.g., via `exec()`), producing per-sample binary indicators for each rule. Using the LLM to generate parsing code makes the system robust to syntactic differences such as "$>$" vs "greater than", or minor wording variations.

## 4) Binary rule features: one-hot rule activations

Each generated rule becomes a binary feature. For class $k$ we obtain a binary vector for sample $i$:

- $\mathbf{z}_k^i \in \{0,1\}^R$, where $R$ is rules per class.

Each entry in $\mathbf{z}_k^i$ indicates whether sample $i$ satisfies a specific rule for class $k$. Collecting these across classes and across the dataset transforms the original table into a compact, interpretable rule-feature representation.

## 5) Learn a lightweight non-negative linear model

Once we have binary rule features, FeatLLM fits a very small supervised model per class: a linear (dot-product) model whose weights are constrained to be non-negative. The model produces logits and class probabilities as

- $\text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,$  
- $\mathbf{p}^i = \text{Softmax}([\text{logit}_1^i, \dots, \text{logit}_c^i])$,

where $\mathbf{w}_k$ are the trainable weights for class $k$. The positive projection $\max(\mathbf{w}_k,0)$ ensures rules can increase the likelihood of a class but not decrease it — a conservative inductive bias appropriate when rules are mined from LLM priors.

Training is lightweight: cross-entropy loss optimized with Adam (the paper used learning rate $0.01$ and trained for up to 200 epochs with early selection via $k$-fold validation). Because the downstream model is linear and small, inference is fast and cheap: once rules and weights are learned, predictions do not require any LLM calls.

Two practical benefits of tuning these weights are evident in experiments. First, tuning learns the relative importance of the rules (some rules are stronger signals than others). Second, the linear model can effectively prune irrelevant rules by assigning them near-zero weights.

## 6) Ensemble + bagging for robustness and prompt-size control

FeatLLM repeats the whole rule-generation → parsing → training process multiple times to form an ensemble. Key implementation details:

- Randomness during rule generation is injected via LLM sampling (the experiments used temperature $0.5$ and default top-$p$ of $1$) and by shuffling the order of demonstrations in the prompt.

- Bagging is applied at the prompt level: each trial uses a random subset of features or examples when constructing the prompt. This both reduces the prompt length (useful when a dataset has many columns) and increases diversity across trials.

- The paper uses $T=20$ trials in the ensemble and averages the class probability vectors from each trial to produce final predictions.

Ensembling yields two advantages: it stabilizes predictions against occasional noisy rule sets from the LLM, and it mitigates the context-window limitation by ensuring not every trial needs every feature in the prompt.

## Why this design matters

FeatLLM trades repeated expensive LLM inference at test time for a short set of LLM queries up-front to discover rules. The practical implications in the paper are:

- Only a small number of LLM API calls are required during training (the paper reports roughly 30 calls for their timing comparison), and inference is cheap because it is a simple linear model over binary features.

- The approach works with LLMs accessed only via API (no model fine-tuning required) and is robust to long feature sets through bagging.

- In experiments across 13 tabular datasets, FeatLLM generated high-quality rule features and achieved strong few-shot performance — e.g., comparable performance using 4 shots to what conventional methods needed 32 shots for — and in aggregate significantly outperformed several LLM-based and conventional baselines (the paper reports roughly a 10% average improvement over alternatives like TabLLM and STUNT).

- The pipeline produces interpretable rules, making it easier to inspect what signals drive predictions.

## Practical tips & hyperparameters (as used in the paper)

- Rules per class: $R=10$ (fixed to bound prompt size).  
- Ensemble trials: $T=20$.  
- LLM backbone in experiments: GPT-3.5 (framework is LLM-agnostic).  
- LLM sampling: temperature $=0.5$, top-$p=1$.  
- Linear model optimization: Adam, lr $=0.01$, up to 200 epochs with $k$-fold selection.  
- Parsing: re-prompt the LLM to emit parsing code and execute it (paper used Python `exec()`).

## Limitations and closing notes

FeatLLM is explicitly designed for low-shot tabular learning. Its strengths come from leveraging LLM priors to find human-readable rules, but that also means LLM biases and misinformation can influence the generated rules. The paper discusses this as an important area for future analysis. The authors also note directions for extending the approach to richer feature types beyond rule-based binary features, and to larger-sample regimes.

In short, FeatLLM reframes the role of an LLM in tabular tasks: from a per-sample black-box predictor to an automated, interpretable feature engineer. That framing buys you fast, cheap inference and an intelligible model, while still tapping the LLM’s world knowledge during feature discovery.



# Faster, Cheaper Inference: No More Per-Row LLM Calls

## TL;DR
FeatLLM flips the usual LLM-for-prediction pattern: instead of sending every input row through an LLM at inference time, it uses an LLM once (up front) to automatically engineer rule-like features from a few labeled examples and feature descriptions. Those rule-derived binary features feed a tiny downstream model (a non-negative linear classifier + softmax). The result: production-time predictions are as fast and cheap as standard ML, require only API access to an LLM (no fine-tuning), and still deliver strong few-shot accuracy. In experiments on 13 tabular datasets FeatLLM outperformed LLM-based alternatives such as TabLLM and STUNT by about 10% on average, and 4-shot FeatLLM matched the performance of some conventional methods that used 32 shots.

## Why per-row LLM calls are a problem
Using LLMs for tabular prediction in an end-to-end way typically means one LLM inference per test row. That has three practical downsides:
- Latency and cost scale with the number of rows.
- Many high-quality LLMs are API-only and do not allow fine-tuning, or fine-tuning is expensive.
- Serializing wide tables into single prompts hits prompt-length limits, or forces expensive engineering workarounds.

If you want LLM reasoning in production but need low latency and bounded cost, calling the LLM per row is often a non-starter.

## FeatLLM’s high-level idea
Instead of asking the LLM to predict each sample, ask it to explain what would make a sample belong to each class — i.e., produce decision rules that an expert would use. Those rules are parsed into binary features and become reusable inputs for a cheap downstream learner. Key benefits:
- Single (batched) feature-engineering phase with the LLM; no per-row LLM calls at inference.
- Works with API-only LLMs (no model checkpoints or fine-tuning required).
- Handles large numbers of columns by combining ensemble runs with bagging (so you never have to serialize the entire table at once).
- Cheap inference: once rules and a small classifier are trained, predictions are just simple arithmetic (comparable to Logistic Regression/XGBoost).

## How it works (concise technical summary)
FeatLLM has three main stages: rule extraction, rule parsing → feature generation, and lightweight training + ensembling.

Prompting and rule extraction
- The prompt is structured into three parts: basic info (task description, feature names/types/definitions, and a few serialized examples), a reasoning instruction, and a response instruction specifying a parseable rule format.
- Reasoning is done in two steps inside the prompt: (1) infer general tendencies/causal relationships from feature descriptions and prior knowledge; (2) use the few examples to derive decisive rules for each class. To keep things stable, FeatLLM extracts a fixed number of rules per class (the experiments used 10).
- Few-shot examples are serialized in a straightforward format (features and the label). In the paper the serialization looks like:
  $\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) =\ "$$f_1\ \text{is}\ \mathbf{x}^i_1.\ \dots\ f_d\ \text{is}\ \mathbf{x}^i_d.\ \text{Answer:}\ \mathbf{y}^i$$
- Multiple LLM queries (with a non-zero temperature) produce diverse rule sets for ensembling.

Parsing rules into executable features
- The LLM outputs are natural-language rules and can be syntactically noisy. FeatLLM uses the LLM again (as a code synthesizer) to convert each natural-language rule into a small, executable transformation (Python) that produces a binary feature: does this sample satisfy the rule or not?
- Those generated code snippets are executed to produce for each sample and each rule a binary indicator.

Lightweight classifier and inference
- For class $k$ each sample $i$ gets a binary vector $\mathbf{z}_k^i \in \{0,1\}^R$ (one dimension per rule). The model computes logits via:
  $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,$
  $\mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i, \dots, \text{logit}_{c}^i]).$
  The $\max(\mathbf{w}_k,0)$ projection enforces non-negative importance weights so features can only increase a class score.
- The weights $\mathbf{w}_k$ are trained with cross-entropy on the few labeled examples (the experiments used Adam at learning rate 0.01 for 200 epochs with cross-validation to choose epochs).
- At inference time the pipeline is just: compute rule-binary features for the row and apply the small linear classifier. No LLM calls.

Ensembling and bagging
- To get robustness and to avoid hitting prompt-length limits, FeatLLM repeats the entire rule-extraction + training process $T$ times with random feature/instance bagging and random ordering of demonstrations. The predictions are averaged across the $T$ trials. In the paper $T=20$ and a temperature of 0.5 were used.

## Empirical highlights
- Datasets: evaluation on 13 tabular datasets from multiple domains (examples include Adult, Bank, Diabetes, Heart, Myocardial, Cultivars, NHANES, and synthetic tasks designed to be unseen by pretraining).
- Performance: FeatLLM consistently ranked first or second against a range of baselines, and outperformed LLM-based alternatives (TabLLM, STUNT) by roughly 10% on average.
- Data-efficiency: with only 4 labeled shots FeatLLM achieved performance comparable to traditional tabular models trained with 32 shots on some tasks.
- Feature quality: most extracted rules are informative (measured via AUROC against the label); the downstream weight tuning filters out weak / irrelevant rules (weights below a chosen threshold).
- Robustness to noisy columns: when unrelated columns were appended, FeatLLM degraded less than other methods; only about 1–2% of inferred rules were based on noisy columns in those tests.
- Cost and latency: FeatLLM requires a small number of LLM API queries during the feature-engineering phase (the paper reports around 30 API queries in their setup), but inference latency is comparable to standard ML models because no per-row LLM calls are needed. By contrast, per-sample LLM approaches incur much larger inference costs.

## When to use FeatLLM (and caveats)
Use FeatLLM when you have:
- A few labeled examples (low-shot regime).
- Need for fast, low-cost production inference.
- Access to an LLM via API only (no fine-tuning), and you want LLM prior knowledge incorporated into your model.

Limitations and caveats:
- The method is designed and evaluated for low-shot settings. Scaling to very large labeled datasets was not the focus of the paper.
- LLM prior knowledge can include biases or misinformation; those priors directly influence rule generation and thus downstream predictions. The authors point this out as an important area for future evaluation.
- Although FeatLLM is robust to random noisy columns, it can still learn spurious correlations if the attached columns are closely related in ways that mislead the LLM.

## Practical notes and hyperparameters used in the paper
- LLM backbone: GPT-3.5 (the method is LLM-agnostic).
- Number of rules per class: 10.
- Number of ensemble trials: 20.
- LLM temperature: 0.5 (top-p left at default).
- Weight training: Adam, lr 0.01, 200 epochs; early/epoch selection via cross-validation.
- Training-phase API budget: on the order of a few dozen queries in the experiments.

## Takeaway
FeatLLM shows a pragmatic way to keep LLM reasoning in the loop while avoiding the production-time cost and latency of per-row LLM inference. By turning LLM outputs into reusable, rule-based binary features and fitting a tiny classifier, you get the best of both worlds: LLM-powered few-shot performance and the low-latency, low-cost inference footprint of traditional ML. If you need LLM expertise in production but can’t afford per-row API calls or fine-tuning, FeatLLM is worth trying.

Code (as reported in the paper) is available: https://github.com/Sungwon-Han/FeatLLM.



# Beating Prompt Limits on Wide Tables with Bagging and Ensembling

## The problem: long prompts and wide tables
Large language models (LLMs) are surprisingly useful for tabular tasks: if you serialize rows and columns into text and ask an LLM to reason about them, it can often use its prior knowledge to make decent predictions in few-shot settings. But that serialization trick runs into two practical problems on "wide" tables (hundreds of columns). First, serialized prompts get very long and hit context-window or performance limits. Second, many LLM-based tabular methods require an LLM call per test sample, which is slow and expensive in production—especially when you must run an LLM over every wide row.

FeatLLM takes a different tack. Instead of using an LLM as a per-sample predictor, it uses the LLM as an automated feature engineer that writes human-readable rules. Those rules are parsed into binary features, a tiny downstream model is trained on those features, and at inference time you only evaluate that cheap model. Crucially for wide tables, FeatLLM uses bagging (feature/instance subsampling) and ensembling to keep prompts short while still covering the whole table and improving robustness.

## The core idea in a paragraph
Run many small, randomized LLM queries, each seeing only a subset of the columns and a subset of examples. Each query asks the LLM to (1) reason about which features matter (using a two-step prompt), then (2) produce a fixed number of decision rules per class. Parse those rules into code that produces binary features (rule satisfied or not). Fit a simple model on those binary features. Repeat this process T times and average probabilities across the T models. The combination of bagging (to limit prompt size and introduce diversity) and ensembling (to average out bad rules) makes it possible to handle datasets with 100+ attributes while keeping inference cheap.

## How a single FeatLLM trial looks
FeatLLM structures each LLM prompt and trial to make rule extraction reliable and parsable:

- Basic information section: task description (a short question), natural-language feature names and types, and a few serialized training examples. Examples are serialized in the same simple format used in the paper, e.g.
  \[
  \text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F)=``\ f_1\ \text{is}\ \mathbf{x}^i_1.\ \ldots\ f_d\ \text{is}\ \mathbf{x}^i_d.\ \ \text{Answer:}\ \mathbf{y}^i\ "
  \]
- Reasoning instruction: a two-step guidance that (Step 1) asks the LLM to infer general relationships from prior knowledge (without looking at examples), and then (Step 2) asks it to convert that knowledge plus the few-shot examples into concrete rules for each class. The two-step structure helps avoid spurious correlations from tiny datasets and focuses rule generation on plausible, semantically meaningful features.
- Response instruction: a fixed format for rules so they can be parsed more easily. The paper fixes the number of rules per class (e.g., $R=10$) to avoid producing too many rules and bloating subsequent processing.

After the LLM returns natural-language rules, FeatLLM uses the LLM again to generate small, executable parsing code (e.g., Python) that converts those rules into binary features for every sample. This avoids brittle hand-written parsers and leverages the LLM’s familiarity with code to handle minor syntactic variability in its own outputs.

## From rules to predictions (the simple model)
Each rule becomes a binary feature. For class $k$, let $\mathbf{z}_k^i\in\{0,1\}^R$ be the vector of rule indicators for sample $i$. FeatLLM fits a lightweight linear scoring model per class and turns scores into probabilities by softmax:

\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,\qquad
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\ldots,\text{logit}_c^i]\big).
\]

The model constrains weights to be non-negative via $\max(\mathbf{w}_k,0)$ so rules cannot actively reduce a class score; weights are learned from the few labeled examples (cross-entropy loss). Because these models are tiny, inference is fast (dot products and a softmax), and no LLM calls are required per test sample.

## Bagging and ensembling: why they beat prompt limits
Bagging here means subsampling features and/or training examples for each trial. That does three things:

1. Keeps prompts manageable. Each LLM query only needs to include the serializations for the selected subset of columns and examples, avoiding token-window overflow on wide tables (the paper shows this is essential for datasets with 100+ attributes such as Communities and Myocardial).
2. Creates diversity. By sampling different feature subsets and randomizing the order of examples, each trial produces different rule sets. Using a higher temperature on the LLM also introduces controlled randomness.
3. Makes the system robust. Averaging probabilities over $T$ trials reduces the influence of any single bad rule set. If an LLM produces incorrect or noisy rules in some trials, correct rules from other trials compensate—this is analogous to self-consistency/consensus.

In practice the authors used $T=20$ ensembles and $R=10$ rules per class as a default; they report that performance improves up to around $T\approx 20$ and then saturates, and $R=10$ is a sensible trade-off between information and overfitting in low-shot regimes.

## Practical implementation details (what the paper used)
FeatLLM is LLM-backbone agnostic but the experiments used GPT-3.5 (gpt-3.5-turbo-0613). Typical settings in the paper: temperature 0.5 (top-p default 1), ensemble size $T=20$, rules per class $R=10$. The downstream linear model used Adam with learning rate 0.01 for 200 epochs (with $k$-fold cross-validation used to pick epochs). Because the rule-generation stage is repeated but limited per trial, the total number of API calls is small (the paper reports about 30 API queries for training in their timing comparison), and these calls can be parallelized.

Parsing of rules is done by prompting the LLM to emit small parsing functions which are executed (the authors used Python’s exec()) to create binary features. This use of the LLM as both rule writer and parser avoids brittle hand-coded text parsing.

## Empirical highlights from the paper
The paper evaluates FeatLLM on 13 tabular datasets spanning conventional benchmarks and recent/synthetic problems. A few notable outcomes reported:

- FeatLLM consistently ranks first or second across datasets in few-shot settings and substantially outperforms several recent few-shot baselines. The abstract summarizes a significant improvement (about 10% on average) over alternatives such as TabLLM and STUNT.
- In low-shot setups, FeatLLM with only 4 labeled examples matched or exceeded the performance of conventional methods trained with 32 examples on many tasks.
- For datasets with many features (100+), other LLM-based approaches that serialize full rows into prompts often fail or cannot run due to prompt length; FeatLLM’s bagging+ensemble workflow avoids that failure mode and remains competitive.
- Ablations show the ensemble is consistently beneficial, the two-step reasoning prompt and feature descriptions boost performance especially in very low-shot settings, and weight tuning becomes more important as the number of shots increases.
- FeatLLM is relatively robust to adding spurious, irrelevant columns: the paper shows it degrades less than baselines when irrelevant features are appended, and only a small fraction (1–2%) of generated rules relied on noisy columns in their tests.

## Practical takeaways and defaults
If you want to try this idea on your own wide-table few-shot task, the paper’s experiments suggest sensible defaults and practices:

- Subsample features and examples per trial to keep prompts short; use bagging across trials to cover the full table.
- Ask the LLM to first state general prior-knowledge tendencies, then to derive explicit rules from the examples (two-step reasoning).
- Fix the number of rules per class (e.g., $R=10$) to bound prompt length and downstream dimensionality.
- Use an ensemble of $T\approx 20$ trials for a good balance of robustness vs. API cost; increase $T$ if you can afford more calls.
- Use the LLM to generate parsing code for its own rules rather than hand-parsing the natural-language output.
- Fit a simple linear model with non-negative weights on the binary rule features and train it on your few labeled examples.

## Limitations and caveats
FeatLLM is designed for the low-shot regime and for producing rule-based features. The approach is not presented as a replacement for large supervised models in large-data settings. The authors also note that because rule generation leans on LLM prior knowledge, the method can propagate biases or misinformation embedded in that prior—so domain scrutiny is necessary, particularly in sensitive areas like healthcare or finance.

## Where to find the code and paper
The authors released code at the repository used in the paper: https://github.com/Sungwon-Han/FeatLLM.

## Bottom line
When table width kills serialized prompts, split the problem into many small LLM queries: let the LLM generate interpretable rules from subsets of features and examples, parse those rules into binary features, and average many tiny models. Bagging keeps each prompt short, and ensembling turns noisy rule sets into a robust predictor—while keeping inference cheap because the LLM is no longer in the test-time loop.



# Interpretable by Design: Human-Readable Rules and Transparent Weights

## The idea in one paragraph
FeatLLM reframes an LLM from a black-box predictor into an automatic feature engineer that outputs human-readable, domain-aligned rules. Each rule is converted into a binary indicator (does this sample satisfy the rule?), and a very simple downstream model—a per-class linear scorer with non-negative weights—learns which rules matter. The result is a compact, auditable pipeline: readable rules, executable parsing, and transparent weights that explain class likelihoods. This makes FeatLLM especially appealing for regulated or high-stakes settings where interpretability and predictable inference cost matter.

## How FeatLLM gets human-readable rules
FeatLLM extracts rules from an LLM using a structured prompt that mimics how an expert would reason about a tabular task. The prompt has three parts:
- Basic information: task description (question form), natural-language feature names and types, and a few serialized training examples.
- Reasoning instruction: a two-step guidance that first asks the model to state general tendencies or causal relationships from domain prior knowledge (without examples), then to use the few-shot examples to produce concrete, class-specific rules. This separation helps avoid spurious correlations and focuses the LLM on plausible, domain-aligned criteria.
- Response instruction: constraints on the output format so the rules come out in a consistently parseable textual form. In the experiments the authors fix the number of rules per class (10) to manage prompt length and downstream dimensionality.

Because the rules are written in natural language, they are immediately inspectable by humans: you can read a rule and evaluate whether it aligns with domain knowledge or sensible decision criteria.

## From textual rules to binary indicators (parsing)
Rather than hand-coding brittle parsers for every possible phrasing, FeatLLM uses the LLM again to translate the natural-language rules into simple executable code (Python), given a function specification and the inferred rules. The generated code is run (the authors use Python’s exec()) to create binary features for each sample: for class $k$ and rule $r$ we get a binary indicator $z_{k,r} \in \{0,1\}$ that says whether the sample satisfies that rule. This keeps the pipeline automated while preserving human-readability of the original rules.

## Transparent weighting: the simple non-negative model
Once rules are converted into binary features, FeatLLM trains a lightweight per-class linear scorer to estimate class likelihoods. Let $\mathbf{z}_k^i \in \{0,1\}^R$ be the $R$ binary rule-features for sample $i$ and class $k$, and let $\mathbf{w}_k$ be the learned weight vector for that class. The paper computes logits and probabilities as:

\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\qquad
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i, \dots, \text{logit}_c^i]\big).
\]

Weights are learned by optimizing cross-entropy on the few-shot training set (the authors use Adam and early selection via cross-validation). Two design choices make the weights especially interpretable:
- Non-negativity projection: using $\max(\mathbf{w}_k,0)$ ensures each rule contributes non-negatively to that class's logit, so weight magnitude directly reflects how much that rule pushes evidence toward the class.
- Per-class rule sets: rules are generated per class, so a rule that argues against a class is typically represented as a positive rule for other class(es).

After training, the numeric weights form a clear, inspectable ranking of rule importance. The authors also threshold small weights (they use 0.1 in experiments) to filter out rules that are not supported by the data.

## Why this is useful in regulated and high-stakes settings
FeatLLM’s pipeline delivers features that you can read, test, and reason about. Practical advantages include:
- Auditability: every prediction can be traced to a small set of named rules and their weights.
- Domain alignment: because the LLM leverages prior knowledge and the prompt forces a reasoning step, rules often map to domain concepts rather than opaque interactions.
- Reproducible inference: once rules and weights are fixed, inference requires no LLM calls—only binary checks and a simple linear score—so latency, cost, and dependence on third-party APIs at runtime are reduced.
- Robustness controls: you can filter or adjust rules manually, inspect how many ensemble trials agree with a rule, or remove rules that look biased or spurious.
- Manageable attack surface: no per-sample LLM queries at inference reduces the number of times sensitive data is sent to an external model.

These properties make FeatLLM a practical option when transparency, fast inference, or restricted API access are concerns.

## Empirical signals that the rules and weights are meaningful
The paper evaluates FeatLLM on 13 diverse tabular datasets (healthcare, finance, synthetic tasks, etc.) and reports several relevant findings:
- FeatLLM often ranks first or second against a broad set of baselines (classic ML models, few-shot specialized models, and LLM-based predictors). The authors report that across datasets FeatLLM improves substantially over some LLM-based alternatives (the abstract cites about a 10% average improvement versus specific baselines like TabLLM and STUNT).
- Data-efficiency: with only 4-shot supervision, FeatLLM reaches performance comparable to conventional baselines trained with 32 shots.
- Rule quality: the majority of generated rules show predictive signal (the paper measures AUROC of individual rule-features versus labels), and after training the linear weights the tuning process reliably down-weights irrelevant rules—small-weight rules can be discarded automatically.
- Robustness to spurious columns: in experiments where unrelated columns were appended to the dataset, FeatLLM exhibited the smallest performance degradation; only about 1–2% of generated rules relied on clearly noisy columns in those tests.
- Ablations: removing weight tuning, the reasoning step, feature descriptions, or ensembling all hurt performance, which highlights that both the rule-generation design and the lightweight learning stage matter.

## Practical workflow (how you'd operate FeatLLM)
1. Prepare feature names, short definitions, and $k$ labeled examples.
2. Query the LLM (one-time per trial) with the structured prompt to generate rules per class.
3. Use the LLM to translate rules into executable parsing code; run it to obtain binary rule indicators for your dataset.
4. Train the small non-negative linear model(s) on the few-shot data; validate epochs via cross-validation.
5. Optionally repeat steps 2–4 with bagging/ensembling to increase robustness; combine models by averaging predicted probabilities.
6. Inspect textual rules and learned weights; remove or adjust rules as part of governance.

The authors used ensembles (20 trials) and 10 rules per class in their experiments, though those hyperparameters can be tuned for your context.

## Caveats and ongoing work
FeatLLM is built for low-shot regimes and explicitly leverages LLM prior knowledge; that creates two important caveats:
- The LLM’s priors can encode biases or misinformation. The authors note that analyzing societal bias and misaligned prior knowledge is necessary before deploying in sensitive contexts.
- The current approach focuses on rule-style features. Extending to richer feature types and scaling to large-sample settings are left for future work.

## Bottom line
FeatLLM preserves the LLM’s reasoning power while turning its output into an interpretable, auditable, and low-cost inference pipeline. If you need readable decision logic, fast predictable inference, and a clear way to inspect what drives predictions—especially in regulated or high-stakes applications—FeatLLM is a practical pattern: let the LLM propose domain-aligned rules, turn them into binary indicators, and use transparent non-negative weights to show what actually matters.



# Less Fooled by Spurious Correlations in Few-Shot Settings

## The problem
Few-shot tabular learning is uniquely fragile: with only a handful of labeled examples, models often latch onto spurious correlations present in the small training set instead of the true predictive signals. Large Language Models (LLMs) bring broad prior knowledge that can help, but existing LLM-based approaches typically use the LLM as a black-box predictor (one call per sample) and remain susceptible to overfitting to noisy columns in low-shot regimes.

FeatLLM flips that script. Instead of querying an LLM for every prediction, it uses the LLM as a feature engineer: the model extracts human-readable rules, turns those rules into binary features, and trains a lightweight downstream classifier. Two design choices are central to reducing susceptibility to spurious correlation: (1) separating general-knowledge reasoning from example-driven rule extraction; and (2) ensembling via bagging to dilute weak or misleading rules.

## Two-stage prompting: prior knowledge first, examples second
The prompt for rule extraction is deliberately structured into three pieces: basic information (task and feature descriptions plus a few demonstrations), a reasoning instruction, and a response-format instruction. The crucial part is the two-step reasoning instruction:

- Step 1 (general-knowledge reasoning): the LLM is asked to reason about which features are plausibly relevant to the task using prior knowledge and common sense—importantly, without looking at the few-shot examples. This step surfaces features with a likely causal or semantic link to the label, independent of the small-sample idiosyncrasies.
- Step 2 (example-guided rule extraction): the LLM uses the output of Step 1 together with the few-shot examples to craft concrete, class-specific rules (e.g., "age > 60 and cholesterol > X" ⇒ class A).

Confining the example-based rule search to the features that Step 1 marked as relevant reduces the chance that a single noisy correlation in the few examples will become an extracted rule. The prompt also enforces a fixed number of rules per class (in our experiments $R=10$), and a response format that is easy to parse.

## From rules to features to predictions
Rules are parsed into executable code (parsing is itself implemented by the LLM to handle syntactic variability) and evaluated on the dataset to produce binary rule-features. Let the rule-feature vector for class $k$ on sample $i$ be $\mathbf{z}_k^i \in \{0,1\}^R$. FeatLLM fits a simple linear model per class with non-negative weights so that each rule contributes additively to the class logit:

\begin{align}
\text{logit}_k^i &= \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i, \\
\mathbf{p}^i &= \text{Softmax}\bigl([\text{logit}_1^i, \dots, \text{logit}_c^i]\bigr).
\end{align}

The weights $\mathbf{w}_k$ are learned from the few labeled examples (cross-entropy loss). Learning these weights has two benefits: rules that are not supported by the data receive small weights and effectively get filtered out, and rules that are useful are up-weighted, allowing the final predictor to rely on concise, interpretable signals.

## Ensembling and bagging as a robustness filter
FeatLLM repeats rule extraction multiple times with randomized prompts (high LLM temperature and different demonstration orders) and bagging over subsets of features or examples. The implementation used in the experiments ensembles $T=20$ independent trials, averaging the predicted class probabilities across trials.

This ensemble plays three roles in combating spurious correlations:
1. Diversity: different rule-sets explore different plausible criteria; bad rules tend to be inconsistent across trials.
2. Robustness: averaging dilutes the influence of a few misleading rules.
3. Practical scaling: bagging lets each prompt stay small (avoid prompt-size limits) while still covering many features across the ensemble.

## Empirical evidence: noisy columns hurt others more
A targeted experiment highlights the effect. The authors took the Heart dataset and progressively appended unrelated columns sampled from the Adult dataset (columns that are semantically irrelevant to the heart task). Using the same 8-shot labeled training set, they compared FeatLLM to several baselines (logistic regression, XGBoost, RandomForest, and LLM-backed in-context methods where applicable). FeatLLM shows the smallest performance drop as the number of irrelevant columns increases. In the generated rule-sets, rules based on the noisy (irrelevant) columns represented only about 1–2% of the total rules, demonstrating that the two-step reasoning plus ensembling effectively steers rule extraction away from spurious features.

Additional relevant observations from the paper:
- The two-step reasoning and inclusion of feature descriptions are especially important in the low-shot regime; ablations removing Step 1 or feature descriptions materially degrade performance.
- Tuning the linear weights matters increasingly as the number of shots grows: weight learning helps filter and re-weight rules based on data evidence.
- FeatLLM with only 4 shots reaches performance comparable to conventional models trained with 32 shots on several datasets, illustrating strong data-efficiency.

## Feature quality and automatic filtering
To quantify rule usefulness, the paper measures the AUROC of each binary rule-feature against the target label. Most generated rule-features have AUROC > 0.5 before tuning, and the tuning stage further prunes weak rules: after fitting the linear model, rules with very small learned weights (the authors used a threshold of 0.1 for analysis) can be considered effectively discarded.

Parsing robustness is handled pragmatically: because LLM output can vary in syntax, the system asks the LLM to emit simple code for the rules, and executes that code to generate features. This reduces brittle, hand-written parsers and leverages the LLM’s strength in producing coherent code fragments.

## Practical benefits and implementation notes
FeatLLM is designed to be practical in real-world settings where LLMs are only available through an API and fine-tuning is not feasible. Key practical points from the experiments:

- LLM calls happen during feature engineering, not at inference time; the deployed predictor is a cheap linear model.
- The authors used GPT-3.5 (gpt-3.5-turbo) with temperature 0.5 and top-p = 1, $R=10$ rules per class, and $T=20$ ensembles.
- The LLM-based rule-generation stage requires only a modest number of API queries (reported as about 30 total queries in the training-time comparison), and inference latency is comparable to conventional models because the runtime model is lightweight.

## Limitations and caveats
FeatLLM reduces but does not eliminate the risk of learning spurious correlations. The paper notes that if unrelated columns are in fact semantically similar to the target or come from closely related datasets, the LLM's prior knowledge may incorrectly endorse them, and the final pipeline can still be misled. Also, because FeatLLM relies on the LLM’s prior knowledge, any biases or misinformation present in the LLM can influence generated rules; the authors call out the need for future work probing such biases.

## Takeaway
FeatLLM shows a simple but powerful idea: use LLMs to propose interpretable, rule-based features via a two-stage reasoning prompt that separates general knowledge from example-specific induction, then let a lightweight learned model select and weight those rules. That separation, combined with ensembling and bagging, materially reduces the impact of spurious correlations in few-shot tabular learning, while keeping inference cheap and practical.

Code and paper (anonymized) are available at: https://github.com/Sungwon-Han/FeatLLM.



# Prompting that Works: From Natural Language Rules to Executable Code

Large language models (LLMs) are excellent at reasoning in natural language — but for tabular prediction you rarely want to run an LLM for every test row. FeatLLM takes a different tack: use an LLM once (or a handful of times) to act as a feature engineer, coaxing it to output human-style, class-wise rules, then convert those rules into executable checks that become binary features for a cheap downstream model. The result: interpretable rule features, no per-sample LLM inference at prediction time, and robust few-shot performance.

Below I walk through the prompt design that makes this reliable and how FeatLLM converts messy, free-form rules into executable Python code you can run automatically.

## The three-part prompt that reliably yields class-wise rules

FeatLLM splits the prompt into three clear parts so the LLM has all the context it needs and a constrained, parseable output format.

1. Basic information description (what to feed the LLM)
   - A short task description framed as a question (for example: “Does this patient record indicate chronic heart failure? Yes or No.”).
   - Feature names, each with type and an optional short definition. For categorical features, possible categories can be included so the LLM knows expected values and types.
   - Few-shot example demonstrations (the training samples), serialized into plain text. FeatLLM uses the following serialization:
     $$
     \text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) =
     ``\ f_1\ \text{is}\ \mathbf{x}^i_1.\ ... \ f_d\ \text{is}\ \mathbf{x}^i_d.\ \ \text{Answer:}\ \mathbf{y}^i\ ”
     $$
     That simple, consistent style helps the LLM map feature names to values.

2. Two-step reasoning guidance (how to think)
   - Step 1 — Prior / causal inference: instruct the LLM to first state likely relationships or causal tendencies between features and the target using general knowledge (without looking at the examples). This taps the LLM’s world knowledge and steers it away from spurious correlations seen in a tiny training set.
   - Step 2 — Rule deduction from examples: then ask the LLM to combine the insight from Step 1 with the few-shot examples to produce decisive rules that distinguish classes.
   - Why two steps? Separating prior knowledge extraction from example-driven rule induction reduces the chance the model will latch onto accidental correlations present in very small $k$-shot samples.

3. Response instruction (how to format the output)
   - Give a strict, machine-parsable output template: produce a fixed number of rules per class and use a standardized rule structure the downstream parser expects. FeatLLM constrains the number of rules to a fixed number (the paper uses 10 rules per class) to avoid both underfitting and explosive prompt/feature size.
   - Ask the LLM to choose rule formats consistent with feature types (e.g., range checks for numeric features, membership checks for categorical features). This reduces type mismatches and makes parsing simpler.

Together these parts force the LLM to (a) consider prior knowledge, (b) ground conclusions in the few examples, and (c) emit a deterministic structure you can parse or convert reliably.

## Messy wording? Use the LLM to generate executable parsing code

A major practical hurdle is that even with a strict format the LLM will sometimes use varied wording: “> 50”, “greater than 50”, “above fifty”, etc. Hand-rolling a robust parser that covers all paraphrases quickly becomes tedious and brittle.

FeatLLM instead leverages the LLM again — this time as a code generator. The workflow:

- Package the inferred rules together with a minimal function specification: function name, input description (the original tabular row), output description (a list/array of binary indicators), and the raw rule text.
- Prompt the LLM to emit a small Python function that implements those rules and returns binary features indicating whether each rule is satisfied for a given sample.
- Execute the returned code (the paper uses Python’s exec()) to convert the rule text into working feature-extraction code, and apply it to the dataset.

Why this works well:
- Modern LLMs are trained on code and are good at translating natural-language conditions into comparisons, membership tests, and simple control flow.
- It avoids brittle regex-based parsing and covers synonyms and wording variations implicitly.
- The generated code is simple and interpretable, so you can inspect, validate, and (if necessary) patch any ambiguous rules.

The paper shows this approach is practical and reliable: the LLM-produced code is executed to produce binary features from each rule, and those features become the inputs to the downstream predictor.

## Turning rules into predictions (the cheap part)

Once you have binary rule-features, prediction is straightforward and inexpensive. For each class $k$ you get $R$ binary indicators per sample; denote the vector for sample $i$ as $\mathbf{z}_k^i\in\{0,1\}^R$. FeatLLM uses a simple linear scoring model (no bias) with non-negative weights, producing logits and probabilities as:

$$
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\quad
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big).
$$

The weights $\mathbf{w}_k$ are learned from the few training samples by minimizing cross-entropy; the $\max(\cdot,0)$ projection assures that no rule can actively reduce a class’s score (weights are constrained to be non-negative). This keeps the downstream model tiny, fast, and interpretable: each learned weight directly reflects the importance of a rule for a class.

FeatLLM also filters weak or irrelevant rules after tuning (the paper uses a small weight threshold to drop rules with negligible learned importance).

## Robustness, prompt-size limits, and ensemble tricks

Two common problems are (a) LLM prompts hitting token limits when you list many features/examples and (b) variability in LLM outputs. FeatLLM addresses both:

- Bagging for prompt-size and diversity: at each trial, select a subset of features and/or examples to include in the prompt. This keeps prompts short and lets different trials focus on different parts of the table.
- Ensembling across trials: repeat rule extraction multiple times (the paper uses $T=20$ trials) with a higher temperature and randomized example orders to encourage diverse rules. Average predicted probabilities across the ensemble to improve robustness and cancel out occasional bad rule sets.

These steps let FeatLLM scale to wider tables despite an LLM’s context window limitations and exploit self-consistency across multiple LLM outputs.

## Practical tips from FeatLLM’s design

- Include short, precise feature descriptions and types. This reduces type errors in rules and helps the LLM pick appropriate syntactic forms (range checks vs. membership).
- Use a fixed, modest number of rules per class (the paper finds 10 a practical trade-off) to balance expressivity and overfitting in the few-shot regime.
- Ask the LLM to output rules in a strict template so you can reliably hand them to the second LLM that generates code.
- Randomize demonstration order and set a reasonable temperature for diversity across trials (the paper used temperature 0.5 and top-p = 1 for generation).
- Validate generated code/rules. Even though the LLM-produced functions are usually correct, inspecting a few examples helps catch semantic misunderstandings before production use.

## Caveats and ethical considerations

FeatLLM depends on the LLM’s priors. That is a feature when the LLM brings genuine domain knowledge to a tiny training set, but it can also introduce biases or misleading commonsense if the model’s prior is wrong for your domain. The paper notes that, while FeatLLM is relatively robust to random noisy columns, it can still be misled by closely related but irrelevant columns or by entrenched biases. Always inspect learned rules and consider fairness/bias audits in sensitive domains (health, finance, hiring).

## Takeaway

If your goal is robust few-shot tabular modeling without paying LLM inference cost per sample, the pattern in FeatLLM is worth remembering: (1) craft a three-part prompt (basic info, explicit two-step reasoning, and strict response format) to extract class-wise rules, (2) reuse the LLM to convert the messy natural-language rules into small, executable functions, and (3) combine binary rule-features with a tiny, constrained downstream model plus ensemble/bagging to handle prompt size and variability. This pipeline converts LLM reasoning into reusable, auditable features — and keeps prediction cheap and fast.



# Do the Numbers Back It Up? Results Across 13 Tabular Datasets

## TL;DR
FeatLLM treats a large language model (LLM) as an automatic feature engineer: it prompts the LLM to produce human-readable rules, turns those rules into binary features, and trains a very simple downstream model on those features. Across 13 tabular datasets from domains such as healthcare, finance and a few synthetic tasks, FeatLLM consistently ranks first or second and, on average, improves AUC by about 10% over recent LLM-based baselines like TabLLM and STUNT. With only a handful of labeled examples (e.g., 4 shots) it reaches performance comparable to conventional tabular models trained with many more labels (e.g., 32 shots). Ablations show that tuning the downstream weights, the two-step reasoning guidance in prompts, and ensembling all matter.

## What FeatLLM actually does (short)
FeatLLM reallocates the role of the LLM away from per-sample prediction and toward rule discovery. The pipeline is:

- Prompt the LLM with three structured pieces: (1) basic task and feature descriptions plus a few serialized examples, (2) a two-step reasoning instruction that asks the model first to state general prior knowledge about feature–label relationships and then to use examples to derive concrete rules, and (3) response-format instructions so the LLM emits parseable rules.
- Parse the LLM-generated rules into executable code (the system uses the LLM again to emit a parsing function) and apply those rules to produce binary features (one per rule).
- Fit a simple per-class linear model on the binary rule-features. The model uses non-negative weights so each rule only increases class evidence:
  $$
  \text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,\qquad
  \mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big),
  $$
  where $\mathbf{z}_k^i\in\{0,1\}^R$ are rule-features for sample $i$ and class $k$.
- Repeat the entire rule-generation + fitting process $T$ times with bagging (random feature/instance subsets, randomness via LLM temperature and demo order), then average predicted probabilities from the $T$ models.

This design avoids calling the LLM at inference time per sample: once rule-features and the simple model are learned, predictions are cheap.

## Experimental setup — what was tested
The authors evaluate on 13 datasets covering standard tabular benchmarks and tasks that are unlikely to be memorized by the LLM (including two UCI datasets added after Sept 2023 and two synthetic tasks). Representative datasets include Adult, Bank, Credit-g, Diabetes, Heart, Myocardial, Communities, Cultivars, NHANES, and two synthetic datasets (Sequence-type and Solution-mix).

Baselines include classical tabular methods (Logistic Regression, XGBoost, Random Forest), few-shot / unlabeled-data methods (SCARF, STUNT, TabPFN), and other LLM-based approaches (in-context prompting, TABLET, TabLLM). FeatLLM uses GPT-3.5 (gpt-3.5-turbo-0613) in the experiments. Key implementation hyperparameters used in reported results were $T=20$ ensembles and $R=10$ rules per class; LLM temperature was 0.5 and the linear model was trained with Adam at learning rate 0.01 for 200 epochs.

## Headline numerical findings
- Average improvement over recent LLM baselines: FeatLLM outperforms TabLLM and STUNT by about 10% on average in AUC across the 13 datasets reported in the paper.
- Consistency: FeatLLM is either the top performer or the runner-up across datasets and low-shot settings.
- Shot-efficiency: With just 4 labeled examples (4-shot), FeatLLM achieves performance comparable to conventional tabular baselines trained with 32 labeled examples.
- Robustness to many features and prompt-size limits: by using feature bagging and ensembling, FeatLLM works even on datasets with hundreds of attributes where serializing full tables into a single prompt would be infeasible for other LLM-based methods.

## Why these gains happen (evidence from analyses)
The paper contains multiple analyses that explain why FeatLLM works well in low-shot tabular settings:

- Prompt structure and reasoning guidance matter. The two-step reasoning instruction (general prior knowledge first, then example-based rule derivation) helps the LLM avoid spurious correlations and focus on plausible causal or domain-relevant relations.
- Feature construction plus light tuning is powerful. Many LLM-derived rules are individually informative: a majority of generated rule-features have AUROC > 0.5 with the target label before tuning. After fitting the linear model, irrelevant rules are down-weighted or effectively filtered (the authors used a weight-threshold of 0.1 to identify weak rules).
- Ensembling & bagging add robustness. Repeating rule discovery and fitting with randomized subsets reduces sensitivity to any single erroneous rule-set. The authors observe that performance improves as $T$ increases, with diminishing returns around $T\approx 20$.
- Parsing robustness: instead of brittle hand-coded parsers for natural-language rules, the system asks the LLM to output a small parsing function, then executes it to create features. That eliminates much of the parsing brittleness.

## Ablations — which components are essential
The authors ran ablations removing four components: (1) tuning the linear model (i.e., summing binary features instead of learning weights), (2) the ensemble step, (3) providing explicit feature descriptions in the prompt, and (4) the Step-1 general-reasoning instruction. In all ablations AUC dropped. Two notable patterns emerged: the benefit of weight tuning grows with more labeled shots (as expected), whereas the explicit prior-knowledge / feature-description guidance and the Step-1 reasoning are particularly important in the extremely low-shot regime.

## Robustness to spurious features and runtime
To test sensitivity to irrelevant columns, the authors appended random columns from Adult to the Heart dataset and measured performance as more unrelated columns were added. FeatLLM showed the smallest degradation compared to baselines; only about 1–2% of generated rules came from noisy columns, indicating the two-step prompting helps the LLM ignore irrelevant features.

On efficiency, FeatLLM has a practical advantage: rule discovery requires a modest number of LLM API calls (the paper reports about 30 API queries for training in their setup) and no per-sample LLM calls at inference. In contrast, many LLM-based baselines must query the LLM per test sample (much slower and more expensive). In the runtime comparisons on the Adult dataset, FeatLLM required a small amount of compute and had inference latency comparable to classical models; other LLM-based methods had much higher inference costs. (In the experiments one A100 GPU was used as the default; TabLLM required 4 A100s for model-parallel training in that reproduction.)

## Practical takeaways and limitations
- If you need strong few-shot tabular performance and only have inference/API access to an LLM, FeatLLM is a practical, cost-effective strategy: it needs only API access, produces interpretable rule-features, and avoids per-sample LLM inference.
- The method is especially attractive when labeling is expensive (healthcare, finance) or when you want interpretable, rule-like features that can be reviewed by domain experts.
- Caveats: FeatLLM is developed and evaluated for low-shot regimes. The authors note that LLM priors can dominate predictions (which is helpful when priors are right and harmful when priors are biased or wrong), so careful evaluation of bias and provenance of LLM knowledge is important before deployment. Extending the approach to larger labeled datasets and richer feature types is listed as future work.

## Bottom line
Yes — the numbers presented in the paper support the claim that LLMs used as feature engineers can materially improve few-shot tabular learning. FeatLLM combines structured prompting, rule extraction, and a cheap downstream model to get strong AUCs across diverse tasks, outperforming recent LLM-based baselines by roughly 10% on average while keeping inference fast and practical. The code is available at https://github.com/Sungwon-Han/FeatLLM for anyone who wants to reproduce or extend the experiments.
