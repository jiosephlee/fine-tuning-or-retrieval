\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 6: Designing Prompts to Extract High-Quality Rules

# Basic information block: task question, label schema, feature descriptions with data types and category enumerations
The basic information block is the foundation of any prompt that asks an LLM to produce task-specific rules. Its role is to supply the LLM with the minimal but essential context it needs to interpret the table, to map column names into semantics the model can reason about, and to ground the prediction objective. In FeatLLM this block contains (1) a short task description formulated as a question (for example, in a medical setting: “Does this patient's myocardial infarction complications data indicate chronic heart failure? Yes or no?”), (2) a description of the label schema so the LLM knows what answers it should produce, and (3) a description of the dataset columns $F=\{f_j\}_{j=1}^d$ including their value types and, when applicable, enumerations of possible categories. Supplying the type and categorical options explicitly signals which operations make sense on a feature (e.g., comparison for numeric features, membership checks for categorical features) and therefore reduces meaningless or type-mismatched rules.

When a small set of labeled examples is included as demonstrations (see the next section), each demonstration is serialized into text using a fixed, human-readable format. FeatLLM uses a serialization function that converts a sample $(\mathbf{x}^i,\mathbf{y}^i)$ into a compact sentence-per-feature description with the answer appended. In the paper this is written as:
\begin{align}
&\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = \nonumber \\ 
&\quad ``\ f_1\ \text{is}\ \mathbf{x}^i_1.\ ... \ f_d\ \text{is}\ \mathbf{x}^i_d.\ \ \text{Answer:}\ \mathbf{y}^i\ "
\end{align}
This explicit, regularized presentation of features and labels makes the demonstrations consistent and easier for the LLM to consume. The basic information block therefore acts both as a semantic map (names → meanings and types) and as the environment definition in which the LLM should reason.

# In-context demonstrations: few-shot samples serialized into text
In-context learning depends on presenting a few labeled examples that illustrate the mapping from inputs to labels. In FeatLLM those demonstrations are the serialized samples described above. Because FeatLLM targets few-shot settings, only a small number $k$ (for example $k=4$ in many experiments) of labeled samples are included in the prompt. The serialized demonstrations show the model concrete instances of the task and how labels correspond to feature configurations; Step 2 of the reasoning instruction (below) explicitly asks the LLM to use those examples when deriving rules.

Two practical implications follow. First, demonstrations must be compact and consistent, since the prompt has limited size and each extra example reduces space available for the other components (feature descriptions and reasoning instructions). Second, the order of demonstrations can affect the LLM’s output, so FeatLLM later exploits this sensitivity by randomizing demonstration order across ensemble trials to increase diversity of rule sets. In short, serialized in-context examples show the LLM “what success looks like” within the context established by the basic information block, and they are the data anchor for deriving concrete rules tied to the observed labels.

# Two-step reasoning instruction: Step 1 (general prior knowledge) then Step 2 (rule deduction using examples)
A core engineering decision in FeatLLM is to guide the LLM’s inference with a two-step reasoning instruction. The prompt opens with a short chain-of-thought–style preamble and then separates the task into (1) a prior-knowledge step and (2) an example-driven rule extraction step. In Step 1 the LLM is explicitly asked to infer general tendencies or causal relationships between features and the task using its world knowledge and common sense — crucially, this step is performed without referencing the few-shot demonstrations. The goal is to let the model surface domain priors (for example, “higher age tends to increase risk for some diseases”) so that subsequent rule construction is biased toward plausible, semantically meaningful patterns.

Step 2 instructs the LLM to use the example demonstrations together with the insights generated in Step 1 to deduce concrete, class-specific rules. By separating these two phases, the prompt encourages the model to combine its global priors with local evidence from the few examples rather than to rely solely on spurious correlations that might appear in a tiny sample. Practically, this reduces the chance that the LLM will produce rules built from features that are irrelevant in expectation and helps it focus on semantically supported columns. The paper reports that this structured reasoning leads to better rule quality, especially in very low-shot regimes where the few examples alone are not sufficient to reveal reliable tendencies.

# Fixing the number of rules per class (e.g., $R=10$) to balance coverage and prompt size
When asking an LLM to enumerate rules, it is important to control how many rules are produced. FeatLLM adopts a fixed number of rules per class to limit both the dimensionality of the generated feature space and the length of the downstream processing pipeline. Concretely, the implementation used in the paper sets the number of rules per class to $R=10$ (this choice is discussed and validated in the analysis section). Requesting a fixed count achieves two practical effects: it prevents the LLM from producing too few rules (which might under-cover the decision boundary) and it prevents it from producing an unwieldy number of rules that would increase feature dimensionality and inflate prompt/parse costs.

Fixing $R$ also simplifies downstream training because every class contributes the same number of candidate binary features (rules), yielding a regular, predictable input for the simple linear model that FeatLLM fits to learn rule weights. The paper’s experiments show that $R=10$ is a reasonable trade-off in low-shot settings: it provides adequate coverage of plausible conditions without overly increasing the risk of overfitting in the small-sample regime or overflowing prompt capacity.

# Type-aware constraints and avoidance of mismatched comparisons
An LLM without explicit type cues can produce syntactically valid but semantically invalid rules (for example, applying “greater than” to a categorical field). To prevent such mismatches FeatLLM explicitly includes type information for every feature in the basic information block and instructs the LLM to consult these types when forming rules. For categorical features the prompt can list the allowed categories; for numeric features the prompt indicates they are continuous or integer-valued. This type-aware presentation nudges the model to pick operators that make sense: comparisons and ranges for numeric features, equality or membership checks for categorical features, and presence/absence tests for binary flags.

Enforcing type-awareness in the prompt reduces downstream parsing complexity and improves the semantic validity of the rules the LLM produces, which in turn yields binary features that actually reflect meaningful conditions on the original data. The paper highlights that this constraint is important for avoiding nonsensical conditions (e.g., “gender > 0.5”) and for increasing the chance that automatically-generated code can be used to convert the natural-language rule into a deterministic Boolean test against table rows.

# Response-format instructions: rule structure, logical operators (AND/OR), numeric/comparative expressions
To make the LLM’s output reliably machine-parsable and to constrain the space of syntactic variations the model might use, FeatLLM includes explicit response-format instructions in the prompt. These instructions define the required format for the response for each answer class and the grammatical structure each rule should follow. Typical guidance asks the LLM to produce a numbered list of rules for each class, where each rule is a simple conditional composed of elementary predicates (for example, “feature > threshold”, “feature in {A, B}”, or “feature == value”) possibly combined by the logical operators AND/OR. By prescribing this surface structure the prompt reduces ambiguity and makes it easier to translate the rules into code that computes the corresponding binary feature.

Despite these constraints, the paper notes that LLM outputs can still vary in surface realization (for instance using “greater than” instead of the symbol “>”), so FeatLLM does not rely solely on rigid string parsing. Instead it sometimes uses an additional LLM-assisted parsing step: the inferred rules and a brief specification (function name, inputs and outputs) are sent back to the LLM and it is asked to return simple executable code that implements each rule. This leverages the LLM’s robustness to linguistic variability while still producing deterministic rule-checks: the generated code is then executed (for example via Python’s exec()) to produce the binary features. The combination of prescribed response format and a fallback LLM-to-code parsing step provides both structure and resilience to syntactic noise.

# Managing prompt length via sampling/bagging of features and instances
A practical limitation in any LLM-centered pipeline is prompt size: many tabular datasets have dozens or hundreds of attributes and a long list of serialized examples can exhaust the model’s context window. FeatLLM addresses this by combining rule-generation with a bagging-style sampling strategy and ensembling. Each trial samples a subset of features and/or a subset of training instances to include in the prompt; the LLM then produces rules conditioned on that smaller view. By repeating this process $T$ times and aggregating the resulting rule-based features (the paper uses $T=20$ ensembles in experiments), FeatLLM both reduces per-prompt length and creates a diverse pool of candidate rules that together cover more of the original feature space.

This bagging approach provides two benefits discussed in the paper. First, sampling features keeps each prompt short enough to fit the LLM’s context window, enabling FeatLLM to operate on wide tables without serializing all columns at once. Second, the ensemble of rule sets increases robustness: incorrect or spurious rules from some trials can be outweighed by correct rules from other trials. The paper also uses a higher sampling temperature and randomizes the order of the demonstrations across trials to encourage diversity in the generated rules. Ultimately, the sampled prompts plus ensembling trade off per-trial completeness for scalable, robust coverage across many features and instances.

# Concluding guidance and recommended settings
Putting these elements together yields a practical recipe for extracting high-quality, machine-actionable rules with an LLM in few-shot tabular settings. The prompt should start with a compact basic information block that frames the task as a clear question and enumerates feature names, types and possible categories. A small number of serialized in-context demonstrations should be included to show examples of inputs and labels. The reasoning instruction should be explicitly divided into Step 1 (eliciting general prior knowledge without examples) and Step 2 (using the demonstrations to derive per-class rules), and the prompt should require a fixed number of rules per class (the paper uses $R=10$). Response-format constraints should prescribe simple conditional templates and allow AND/OR combinations; because surface forms vary, include a fall-back LLM-based parsing-to-code stage to obtain executable tests. Finally, if the table is wide or the prompt risks becoming too long, apply sampling/bagging of features and instances and repeat the process across $T$ trials to build an ensemble of rules. These practices, as validated in the paper, balance semantic correctness, parseability, and scalability when using LLMs as automatic feature engineers for few-shot tabular learning.
