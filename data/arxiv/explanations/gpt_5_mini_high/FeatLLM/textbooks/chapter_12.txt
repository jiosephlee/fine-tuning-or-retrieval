\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 12: Ablations and Diagnostic Analyses

# Ablations
An ablation study probes which components of FeatLLM are responsible for its empirical gains. In the paper, four controlled ablations were evaluated: (1) -Tuning, which removes the learned weighting of rule-features and instead aggregates them by simple counting; (2) -Ensemble, which omits the repeated rule-generation + bagging ensemble; (3) -Description, which removes the explicit feature descriptions from the prompt; and (4) -Reasoning, which drops the first reasoning step where the LLM is asked to infer general tendencies between features and the task (the two-step decomposition is reduced to the single step that uses examples directly).

Each ablation targets an identifiable mechanism in FeatLLM and reveals its role. -Tuning replaces the trained linear combination of rule-features by a uniform count. Concretely, with tuning the model computes logits per class using a non-negative weight vector learned from data:
$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,$
where $\mathbf{z}_k^i \in \{0,1\}^R$ is the binary vector of $R$ rule-features for class $k$. The -Tuning variant instead uses the unweighted count,
$\text{logit}_k^i = \sum_{r=1}^{R} z_{k,r}^i,$
which corresponds to fixing all weights to 1. The empirical effect is a measurable drop in AUC: learned weights allow the model to down-weight noisy or weak rules and to up-weight strongly predictive ones, so removing tuning hurts, particularly when enough labeled data exist to estimate weights reliably.

-Ensemble evaluates the contribution of repeated rule generation with bagging and averaging. The full method produces $T$ independent rule-sets and trained weight vectors $\{\mathbf{w}[t]\}_{t=1}^T$, computes per-trial class probabilities $\mathbf{p}^i[t]$ (via the logit and softmax), and aggregates by averaging:
$\mathbf{p}^i = \frac{1}{T}\sum_{t=1}^{T} \mathbf{p}^i[t].$
Dropping this ensemble reduces robustness: single rule-sets are more vulnerable to occasional poor rule generations from the LLM, especially under the stochasticity of in-context queries, and bagging is also the mechanism that keeps individual prompt sizes manageable when many features exist.

-Description tests whether giving the LLM explicit feature type/name/definition matters. Omitting descriptions forces the LLM to attempt rule generation from examples alone, increasing the chance of type mismatches (e.g., comparing a categorical field as if it were numeric) or of paying attention to misleading columns. The ablation shows that including feature descriptions improves the quality of rules, especially when labeled examples are few.

-Reasoning removes the Step-1 instruction that asks the LLM to first infer general, prior tendencies between features and the task before composing concrete rules from examples. Empirically, removing this step reduces performance: the two-step decomposition helps the model rely on domain priors (from the LLM’s pretraining) instead of overfitting to a tiny set of examples, so the generated rules are more semantically grounded and less likely to reflect spurious correlations.

Across the datasets and shot regimes reported in the paper, every ablation led to degraded AUC relative to the full FeatLLM pipeline, showing that these components each contribute materially to the final performance.

# Shot-dependent effects
The importance of individual components changes with the amount of labeled data (the number of shots). Two patterns emerged from the analyses in the paper.

First, as the number of labeled examples grows, the benefit of weight tuning becomes larger. With more examples it becomes statistically feasible to estimate per-rule importances accurately. In the extreme low-shot setting there simply is not enough signal to learn reliable weights, so the difference between learned weighting and uniform counting shrinks. But once a reasonable number of shots is available, the learned $\mathbf{w}_k$ allow the model to suppress noisy rules and magnify informative ones, producing a larger improvement in AUC.

Second, when shots are extremely scarce, components that feed LLM prior knowledge become more valuable. The feature descriptions and the two-step reasoning instruction matter most in the ultra-low-shot regime because they inject extra structure and domain priors into rule generation. With only a couple of labeled examples, an LLM that has been guided about feature semantics and asked to articulate general tendencies is far less likely to latch onto spurious idiosyncrasies of the provided examples. Thus, descriptions and the explicit Step-1 reasoning instruction produce proportionally larger gains when data are minimal.

These shot-dependent behaviors underline a practical recommendation: rely more on careful prompt engineering (feature descriptions, structured reasoning) when labels are very few; when you can obtain more labeled data, allocate effort to learning weights for the discovered features so the downstream learner can calibrate feature importances.

# Feature quality
Two linked diagnostic measurements were used to quantify the informativeness of LLM-generated rules. For each generated rule (which becomes a binary feature across samples), the authors computed the area under the receiver operating characteristic curve (AUROC) between that binary feature and the target label. From these per-rule AUROCs they reported two summary statistics: the average AUROC across rules and the fraction of rules whose AUROC exceeded $0.5$ (i.e., rule is better than random).

Before any tuning, a majority of the created rules were already informative: many rule-features had AUROC $>0.5$, demonstrating that the LLM can leverage prior knowledge plus the few examples to produce meaningful criteria. This validates the central premise that LLMs can act as effective feature engineers in low-shot tabular problems.

Tuning the linear model further improves the effective feature set by assigning small weights to weak or misleading rules and larger weights to informative ones. Empirically the authors applied a simple pruning step after learning: any rule whose learned weight fell below a threshold (they used $0.1$, chosen by inspecting the overall weight histogram) was considered effectively irrelevant. After pruning by this threshold, the fraction of remaining useful rules (AUROC $>0.5$) increased—weak rules were filtered out automatically by the tuning process.

The mathematical view ties these diagnostics together. For class $k$, the feature vector for sample $i$ is $\mathbf{z}_k^i\in\{0,1\}^R$ and the class logit is
$\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot\mathbf{z}_k^i.$
Learning $\mathbf{w}_k$ via cross-entropy on the few labeled samples both discovers which rules correlate with the target in the observed data and provides an operational mechanism to discard low-utility rules without separate heuristics.

# Spurious correlation study
To evaluate robustness to irrelevant features, the paper ran an experiment that simulates spurious correlations by augmenting the Heart dataset with columns drawn randomly from the Adult dataset—columns that are unrelated to the Heart task. The setup fixed an 8-shot labeled training regime and progressively increased the number of unrelated columns appended to the Heart features. Methods that require large unlabeled corpora (e.g., SCARF and STUNT) were excluded from this comparison because the experiment assumed no extra unlabeled data.

The observed pattern was that FeatLLM exhibited the least performance degradation as more unrelated columns were appended, compared to the conventional baselines tested. Two mechanisms explain this robustness. First, the two-step reasoning prompt biases the LLM to consider which features make sense given the task before forming concrete rules, so it is less prone to picking idiosyncratic patterns from irrelevant columns. Second, ensemble + bagging distributes rule generation across randomized subsets of features and few-shot orders; incorrect rules that happen to exploit noise in some trials are diluted when probabilities are averaged across trials.

Quantitatively, the paper reports that rules based on the noisy (appended) columns accounted for only about 1–2% of the total generated rules, a small fraction. This indicates that the LLM’s prior-guided rule generation and the overall FeatLLM pipeline together are effective at filtering out irrelevant columns in low-shot scenarios.

# Caveat: vulnerability when appended features are closely related
The favorable spurious-robustness result comes with an important caveat documented in the paper. If the appended columns are not arbitrary noise but are closely related to the target task (for example, if they are drawn from a dataset that shares causal structure or strong statistical associations with the Heart labels), FeatLLM can still learn spurious correlations and misunderstand causal relationships. In such cases the LLM’s prior knowledge and the few examples may legitimately suggest rules that correlate with the target in the observed data but are not causally valid for out-of-sample or shifted contexts.

This vulnerability is not unique to FeatLLM — it reflects the fundamental difficulty of distinguishing causation from correlation with limited labeled data. The paper explicitly observes this failure mode (reported in the Appendix) and highlights it as a practical limitation: when additional columns are semantically or statistically close to the target, rule generation may produce plausible but spurious rules. Users should therefore treat rules generated from weakly supervised settings with appropriate skepticism and, where possible, validate them on held-out or domain-perturbed data.

# Hyperparameters: ensembles and rules-per-class
Two hyperparameters control the balance between prompt size, diversity, and downstream capacity: the number of ensembles $T$ (the number of independent rule-generation trials) and the number of rules per class $R$ produced in each trial.

Increasing $T$ generally improves performance because it increases the chance of generating high-quality rules and allows averaging to cancel idiosyncratic mistakes. The empirical curves reported in the paper show diminishing returns: performance improves as $T$ rises but begins to plateau around $T\approx 20$. Beyond that point additional trials give only marginal benefits while increasing API cost and total computation.

The choice of $R$ trades feature expressivity against prompt length and overfitting risk. Producing more rules per class raises the dimensionality of the downstream model, which can increase information but also elevates the danger of overfitting when labeled data are scarce. In the experiments there was no statistically large difference across a range of $R$, and $R=10$ per class was chosen as a practical sweet spot considering prompt length constraints and empirical behavior. The paper suggests that a larger $R$ can be tolerated if more shots are available, but in ultra-low-shot settings smaller $R$ helps avoid over-parameterization.

Two operational knobs further contribute to hyperparameter behavior. First, bagging (selecting random subsets of features or instances per trial) reduces the prompt length for any single LLM query and increases diversity across trials. Second, stochasticity in the LLM queries (higher temperature and randomized ordering of few-shot examples) is deliberately used to increase rule diversity across the ensemble. Together these choices let FeatLLM manage large feature sets and obtain robust predictions without issuing an LLM query per test sample.
