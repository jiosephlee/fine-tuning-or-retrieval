\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 4: Reframing LLMs as Feature Engineers

# What is feature engineering and why it matters in tabular ML
Feature engineering is the process of transforming raw data into new variables (features) that make the predictive relationships in a dataset easier for a model to exploit. In tabular machine learning, where columns can be heterogeneous (continuous, categorical, ordinal) and each column often has a domain-specific meaning (a feature name and definition), carefully designed features can dramatically improve predictive accuracy, simplify downstream models, and increase interpretability. The paper frames feature engineering as especially important in few-shot regimes: when only a handful of labeled examples are available, purely data-driven learners are prone to overfitting and to learning spurious correlations. In such settings, domain knowledge—about which attributes matter and how they interact—becomes disproportionately valuable.

Large Language Models (LLMs) carry a broad spectrum of prior knowledge learned from vast text corpora. That prior knowledge can act as a substitute for human expertise when crafting features. Instead of manually hand-engineering rules or transformations, the idea introduced in the paper is to prompt an LLM to act as an automated feature engineer: to read a task description and a few labeled examples, infer what conditions tend to indicate each class, and output interpretable criteria (rules). Those criteria are then converted into concrete, machine-usable features. This reframing recognizes feature engineering itself as the main role for the LLM, leaving prediction to a compact, conventional model learned from the (few) training examples.

# Rules as class-conditional criteria: translating domain priors into features
At the core of the approach is the observation that many human-understandable predictive signals are naturally expressed as rules or criteria: "If age is greater than 60 and smoking history is present, then risk is high." FeatLLM prompts an LLM to produce exactly these kinds of class-conditional criteria. The process is structured to encourage robust, domain-informed rules rather than naively memorized associations.

Formally, the setting begins with a labeled tabular dataset
$\mathcal{D} = \{(\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^{N}$,
where each sample $\mathbf{x}^i$ has $d$ input attributes and the dataset comes with natural-language feature names $F=\{f_j\}_{j=1}^d$ and their definitions. For few-shot experiments only $k$ labeled examples (with $k \ll N$) are used to prompt the LLM and to train the downstream model.

Prompt design is split into three complementary components. First, the basic information section supplies the task as a short, question-like description, the feature definitions (including types and possible categories for categorical attributes), and a set of few-shot example demonstrations. Each example is serialized into text so the LLM can read it; the paper uses the following template for serialization:
$\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) =$  
\quad\ \ $\text{`` }f_1\ \text{is}\ \mathbf{x}^i_1.\ \ldots\ f_d\ \text{is}\ \mathbf{x}^i_d.\ \ \text{Answer:}\ \mathbf{y}^i\text{''}$.
This places concrete examples alongside human-readable feature descriptions so the LLM can ground its prior knowledge in observed data.

Second, the reasoning instruction steers the LLM to follow a two-step inference process. Step 1 asks the model to use general knowledge (independently of the sample examples) to identify which features are likely relevant to the task and how they tend to relate to outcomes. Step 2 then asks the LLM to synthesize class-conditional rules by combining that prior knowledge with the few-shot demonstrations. Splitting reasoning this way prevents the LLM from latching onto spurious correlations that appear only in the tiny example set and encourages reliance on plausible causal or semantic associations. To control complexity, the system fixes the number of rules per class (the paper uses 10) so the prompt neither under-represents nor overwhelms the downstream pipeline.

Third, the response instruction constrains output format. The LLM is told exactly how each rule should be written and how rules should be grouped by class. Constraining format reduces syntactic variability and makes downstream parsing more reliable.

Once the LLM returns natural-language rules, they are converted into binary features. For class $k$ the LLM produces $R$ rules; each sample $\mathbf{x}^i$ is evaluated against those rules to produce a binary vector $\mathbf{z}_k^i\in\{0,1\}^R$ indicating which class-$k$ rules are satisfied. Parsing natural-language rules reliably is nontrivial: LLM output can vary syntactically (e.g., "less than" vs. "$<$"). Rather than hand-engineering a complex parser, FeatLLM uses the LLM again—prompting it to emit a small executable function (Python code) that evaluates the rules—and executes that returned code (via Python's \texttt{exec()}) to create the binary features. This leverages the LLM's strengths in both semantic understanding and code generation to turn textual rules into deterministic, reproducible feature computations.

# Advantages of LLM-generated rules: interpretability, portability, and reduced inference cost
LLM-generated rules offer a trio of practical advantages emphasized in the paper.

Interpretability: The features are explicit, human-readable conditions. A practitioner can inspect each rule and understand which combinations of input values drive predictions; they are not opaque latent representations. The paper empirically shows that a large fraction of generated rules have meaningful predictive signal (many rules produce AUROC > 0.5 with respect to the target), and that the downstream training step naturally down-weights or discards unhelpful rules. In practice the model learns per-rule weights and a simple threshold (the paper uses a threshold of 0.1 on learned weights) can identify rules that should be ignored, providing a principled way to prune noisy or spurious criteria.

Portability and ease of deployment: FeatLLM only requires API-level access to the LLM. It does not require model weights, fine-tuning APIs, or training the LLM itself. This is important because many high-performing LLMs are available only through inference APIs (the paper mentions the relevance of this limitation). By confining LLM use to a one-time or small number of rule-generation queries, the method avoids the practical burdens of parameter-efficient tuning or model-parallel training. Additionally, because the final inference phase uses only conventional code (binary feature checks) and a small learned model, the deployment stack is lightweight and platform-agnostic.

Reduced inference cost and latency: A common drawback of end-to-end LLM-based tabular methods is that they require an LLM invocation per test sample, which is expensive in both latency and monetary cost. FeatLLM instead uses the LLM up-front to produce a transformed dataset (the rule-based binary features). At inference time, the system evaluates the binary conditions and runs a simple predictive model. As reported, inference latency for FeatLLM is comparable to conventional tabular methods (logistic regression, XGBoost, RandomForest), whereas per-sample LLM approaches incur substantially higher inference time. Moreover, FeatLLM typically requires only a modest number of API queries (the paper reports on the order of thirty queries in their experiments), which can be parallelized and is far less than querying an LLM per test instance.

Robustness via ensemble and bagging: The paper further improves reliability by repeating rule generation multiple times and combining models. Randomness is injected via higher sampling temperature in the LLM and by randomizing the order of few-shot demonstrations (order matters in in-context learning). Each trial creates a different rule set; bagging is used to select subsets of features or instances per trial, which both diversifies the rule ensembles and mitigates prompt-length limits (because each prompt can be kept short by selecting subsets). Averaging predictions across trials increases resistance to noisy rules: if some trials generate incorrect criteria, their effect is drowned out by more accurate rule sets from other trials.

# Binary features from rules vs end-to-end LLM predictions
End-to-end LLM tabular approaches typically serialize a sample (or a set of training examples plus a test row) into text and ask the LLM to produce a label or probability for that specific sample. These approaches either (a) require an LLM inference for every test example (in-context prediction), or (b) fine-tune the LLM so it can be used as a predictor without per-sample few-shot context. Both routes have practical disadvantages: per-sample inference is slow and costly, while fine-tuning demands access and compute that may not be available for many LLM services.

FeatLLM takes a different path: it treats the LLM as a generator of features instead of as the ultimate predictor. Converting rules into binary features produces a conventional tabular dataset on which a small predictive model (in the paper, a linear model with non-negative weights) is trained. Concretely, for class $k$ the model learns weight vector $\mathbf{w}_k$ and computes logits and probabilities as
$\text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i$
and
$\mathbf{p}^i = \text{Softmax}(\,[\text{logit}_1^i,\ldots,\text{logit}_c^i]\,)$.
Learning uses cross-entropy loss on the few-shot labeled examples. The non-negativity constraint (implemented by the $\max(\cdot,0)$ projection) ensures that satisfying a rule cannot decrease the predicted likelihood of its associated class during training, aligning the learned weights with the intuitive semantics of rule-based evidence.

This separation—LLM for feature discovery, simple model for inference—brings several concrete benefits shown in the experiments. FeatLLM achieves strong few-shot performance, often exceeding end-to-end LLM baselines and classical models when labeled data are scarce. For example, the paper reports that with only 4 labeled examples FeatLLM reaches performance comparable to conventional models trained with substantially more data (e.g., 32 shots). Moreover, because prediction no longer depends on the LLM, inference cost is low, and the approach scales to datasets with many columns by using bagging to keep prompts compact during rule generation. The paper also reports that attempting to adapt the ensemble/bagging idea to end-to-end LLM prediction would be cost-prohibitive, since it would multiply the already-large number of per-sample LLM inferences.

# Comparison to decision trees and association rule mining
Rules are a familiar output in machine learning: decision trees produce decision-path rules, and association rule mining extracts frequently co-occurring itemsets and their conditional relationships. FeatLLM produces rule-like artifacts as well, but the origin, role, and downstream use of these rules differ in important ways highlighted by the paper.

First, origin and inductive bias. Decision trees and association-rule algorithms typically derive rules purely from the available data. In low-shot regimes this can cause them to pick up spurious patterns that happen to appear in a tiny sample. FeatLLM, by contrast, leverages LLM prior knowledge as a source of inductive bias: its two-step reasoning prompt first asks the model to apply general knowledge about which features matter before grounding that knowledge in the few examples. This encourages rules that reflect plausible domain relationships rather than accidental associations in the labeled mini-sample. The paper's spurious-correlation experiments support this: when many irrelevant columns are appended, FeatLLM degrades less than baselines, and only a small percentage (about 1–2%) of generated rules came from noisy columns.

Second, structure and downstream usage. Decision trees encode hierarchical splits where the path conditions combine via AND; association rules report patterns and measures like support and confidence. FeatLLM produces a fixed number of per-class rules that are treated as independent binary features. Rather than making a single tree-based decision, the downstream model learns non-negative weights over those binary indicators and combines them (via a dot product and softmax) into class probabilities. This decouples rule discovery from rule weighting: rules are interpretable units that can be flexibly combined, weighted, or pruned after observing the labeled examples.

Third, practicality in few-shot settings and deployment constraints. Association-rule mining and tree learning can require enough data to estimate reliable frequencies or splits; FeatLLM injects LLM priors to compensate for sparse labels. Moreover, FeatLLM is explicitly designed to work with LLMs available only via inference APIs: it does not require the LLM to be fine-tuned or to provide gradient-level access. This portability makes it a practical alternative in real-world scenarios where access to LLM internals is restricted.

Finally, FeatLLM borrows an ensemble philosophy reminiscent of random forests: multiple independently generated rule sets are combined (bagging over features or instances and averaging predictions) to increase robustness. Thus, FeatLLM situates itself conceptually between purely data-driven rule learners and human-crafted rule systems: it produces interpretable rules like those methods, but creates them by blending broad prior knowledge and small-sample evidence and then uses a statistical learning step to weight and refine them.

# Takeaways
Reframing an LLM as a feature engineer changes the role of large language models in tabular prediction: instead of being the black-box predictor queried for each sample, an LLM becomes a tool for extracting interpretable, class-conditional criteria that convert semantic prior knowledge into explicit binary features. FeatLLM operationalizes this idea with careful prompt design (basic information, two-step reasoning, and response format), a pragmatic parsing strategy that uses the LLM to emit executable code, a constrained downstream learner that enforces non-negative rule weights, and an ensemble/bagging strategy to improve robustness and manage prompt size. Empirically, this pipeline delivers strong few-shot performance, produces features that are often informative on their own, and reduces inference cost compared to per-sample LLM prediction—making LLM-driven, human-interpretable feature generation a practical approach for tabular problems with scarce labeled data.
