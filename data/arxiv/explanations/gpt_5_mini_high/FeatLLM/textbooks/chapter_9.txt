\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 9: Ensembling and Bagging for Robustness and Scalability

# Motivation: compensate for occasional bad rules and reduce prompt-size pressure

LLMs are powerful rule generators, but they are not perfect: a single prompt can produce incorrect, incomplete, or noisy rules. In FeatLLM this is important because the entire downstream classifier is built on the binary features derived from those rules. A few poor rules can meaningfully degrade a model that relies on a small number of such features (especially in few-shot regimes). At the same time, many real tabular datasets have large numbers of columns; serializing all of them into a single prompt can exceed context limits or produce extremely long prompts that harm LLM utility. These two limitations — occasional bad rule outputs and prompt-size pressure — motivate an ensemble approach that (a) dilutes the effect of bad rules by averaging over many independently generated rule-sets, and (b) reduces per-prompt length by letting each prompt only cover a subset of the full feature set.

FeatLLM addresses both problems by repeating the entire rule-generation → parsing → feature-creation → lightweight-model training pipeline multiple times, each time with different randomized inputs. Instead of relying on a single set of rules to cover every feature and every nuance of the data, FeatLLM produces many complementary rule-sets. If some trials produce incorrect or irrelevant rules, their influence is reduced in the final aggregate prediction because correct rules from other trials can compensate. Similarly, by partitioning features (or examples) across trials, each prompt can be kept short enough to be handled reliably by the LLM, while the union of trials still explores relationships across the whole dataset.

# Diversity via LLM temperature and randomized demo ordering

An ensemble is effective only if its individual members are reasonably diverse. FeatLLM deliberately injects diversity into the LLM-driven rule generation. Two practical levers are used: the LLM sampling temperature and the order of few-shot demonstrations in the prompt.

Temperature controls the stochasticity of the LLM's outputs. FeatLLM sets a nonzero temperature during rule generation so that repeated calls do not deterministically reproduce the same text; the experiments reported used temperature $0.5$ (with top-p set to $1$). This stochasticity makes the LLM produce different but plausible rule-sets across trials, increasing the variety of candidate features the overall system can consider.

The second lever is the ordering of few-shot demonstrations. The LLM’s in-context behavior depends on the examples provided and their arrangement; FeatLLM randomizes the order of the demonstration examples across trials so that the LLM will “attend” to different aspects of the same small training set on different trials. The paper observed that changing the order of demonstrations changes LLM outputs, and exploiting this produces a meaningful source of diversity in the generated rules.

Together, these two mechanisms convert a single deterministic feature-engineering pass into an ensemble of diverse, complementary passes. This diversity is crucial: repeated independent rule-sets are more likely to capture different valid cues from the few-shot data and the LLM’s prior knowledge, and averaging their downstream predictions produces a more robust final decision.

# Feature and instance bagging per trial to fit within context limits

When datasets have many columns or when including many example demonstrations would make the prompt too long, FeatLLM uses bagging to reduce per-trial prompt length. For each trial the system randomly selects a subset of features and/or a subset of training examples to include in that trial’s prompt. The LLM is then asked to generate rules only using that restricted view of the data. This per-trial selection keeps the serialized prompt short enough to fit the LLM’s context window and reduces the cognitive load on the LLM in each query.

Bagging serves two roles simultaneously. Practically, it reduces prompt size so the LLM can be used on wide tables (datasets such as Communities or Myocardial with dozens or hundreds of columns). Statistically, bagging increases ensemble diversity because different trials see different slices of the data and therefore tend to produce different rule-sets. Over many trials the ensemble collects many complementary binary features: while a single trial’s rules might capture only a small subset of informative columns, the union across trials covers a broader set of potentially useful signals. The paper emphasizes that this is particularly useful in the low-shot setting: when a single prompt cannot cover all potentially informative columns, an ensemble of bagged prompts can collectively explore them without ever requiring an excessively long prompt.

# Number of trials T and probability averaging as the final predictor

Each trial in FeatLLM produces a set of binary features (one per extracted rule per class), a trained set of non-negative linear weights for those features, and consequently a per-trial probabilistic predictor. Let the trained weights from trial $t$ be $\mathbf{w}[t]$. For a given sample $i$, trial $t$ computes per-class logits and probabilities using the rule-derived binary features $\mathbf{z}_k^i[t]$ for class $k$ exactly as in the core inference step:

\[
\text{logit}_k^{i}[t] \;=\; \max(\mathbf{w}_k[t], 0)\cdot \mathbf{z}_k^i[t], \qquad
\mathbf{p}^{i}[t] \;=\; \text{Softmax}\big(\,[\text{logit}_{1}^{i}[t],\dots,\text{logit}_{c}^{i}[t]]\big).
\]

The final FeatLLM prediction for sample $i$ is obtained by averaging the per-trial probability vectors:

\[
\mathbf{p}_{\text{final}}^{i} \;=\; \frac{1}{T}\sum_{t=1}^{T} \mathbf{p}^{i}[t].
\]

Averaging probabilities (rather than, say, averaging rules or raw logits) produces a stable, calibrated aggregate that benefits from the diversity among trials while respecting the per-trial learned weights. In practice, the paper used $T=20$ ensembles and $R=10$ rules per class in experiments. Hyper-parameter analysis showed that performance generally improves as $T$ increases, but gains saturate around $T\approx 20$, so that value provides a good trade-off between computation and performance in the reported experiments. Similarly, choosing $R=10$ per class balances information content against prompt length and the risk of overfitting in a low-shot regime.

# Self-consistency: consensus across trials as a reliability signal

A useful by-product of repeating rule generation is that frequently reproduced rules across trials act as a natural reliability signal. The authors connect this to the idea of LLM self-consistency: rules that the LLM returns repeatedly under different randomized prompts and demonstrations are more likely to capture genuine, useful relationships (either from prior knowledge or from the few training examples) than rules that appear only once or twice. In FeatLLM this manifests in two ways.

First, rules that recur across trials produce binary features that are repeatedly supported by multiple independently trained linear models, increasing their overall contribution to the averaged probability. Second, the ensemble design naturally downweights idiosyncratic or spurious rules because their influence is diluted in the mean over $T$ trials. The paper reports empirical evidence consistent with this intuition: the majority of generated rules are informative (many yield AUROC $>0.5$ against the target before tuning), and after tuning spurious rules are further filtered out by learned weights. In the spurious-feature experiment the framework also showed smaller performance degradation than baselines, and the authors note that rules based on noisy, irrelevant columns accounted for only about $1\!-\!2\%$ of the rules generated, illustrating how consensus and tuning together improve reliability.

# Compute and budget considerations; parallelizing API calls

Ensembling increases the number of LLM calls at generation time, so computational cost and API budget are important considerations. FeatLLM reduces the practical burden in several ways that the paper highlights.

First, feature-generation and rule-parsing occur only during training/time-of-feature-construction; once the binary features and the simple downstream model (a linear model with non-negative projected weights) are in place, inference on new samples requires no LLM queries. This design choice yields very low inference latency comparable to conventional tabular models. In contrast, many other LLM-based tabular methods need an LLM call per test sample, driving up inference costs dramatically.

Second, in the experiments the authors report that FeatLLM required only 30 API queries in the training/building phase (a modest cost that can be parallelized). The ensemble trials are independent by design, so their LLM queries can be executed in parallel to reduce wall-clock time. This parallelizability, together with the relatively small number of required queries in reported experiments, makes ensemble generation practical in real-world settings.

Finally, the paper cautions that applying the same bagging-and-ensemble idea to LLM-only end-to-end approaches would be far less practical: those methods would double or more the number of per-sample LLM inferences, making computation and latency prohibitive. FeatLLM’s separation — LLMs for offline feature engineering and a cheap model for online inference — is the key architectural decision that makes ensembling both effective and computationally feasible.

# Practical guidance and trade-offs

The experiments and analyses in the paper suggest straightforward practical recommendations. Use ensembling to stabilize rule-derived features and to cover wide tables without exceeding prompt limits; introduce diversity via nonzero temperature and randomized demonstration ordering; use feature/instance bagging per trial so that each prompt fits comfortably in the LLM’s context window; and aggregate by averaging per-trial class probability vectors as the final prediction. In the reported settings, $T\!=\!20$ ensemble trials and $R\!=\!10$ rules per class struck a good balance between performance and prompt complexity; temperature $0.5$ and top-p $=1$ were used during generation. Because trials are independent, parallelizing the LLM calls is an effective way to keep wall-clock time manageable, and the end-to-end inference remains cheap because it does not require LLM access.

Taken together, these design choices make FeatLLM robust to occasional LLM mistakes, scalable to wide tabular datasets, and practical from a computational and budget perspective, while preserving the interpretability advantage of rule-based features.
