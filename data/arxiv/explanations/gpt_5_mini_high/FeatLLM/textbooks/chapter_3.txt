\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 3: LLMs for Tabular Data: Methods and Limitations

# LLM capabilities and in-context learning for unseen tasks
Large Language Models (LLMs) possess a remarkable ability to generalize to new tasks without task-specific parameter updates. Trained on massive text corpora, these models encode a broad set of prior knowledge and reasoning patterns that can be leveraged in new settings. In the tabular learning context this prior knowledge can substitute for or augment domain expertise: an LLM, given a description of a medical prediction task, can draw on its background knowledge about clinical patterns and risk factors to help interpret sparse training examples. The paper presents this capability as the foundation for applying LLMs as a source of inductive bias in low-shot regimes.

A concrete way to exploit this behavior is in-context learning: the LLM receives a task description and a small collection of example input–label pairs inside the same prompt used for inference. With these few-shot demonstrations the model can “attend” to which features and example patterns appear salient and produce task-relevant outputs without any parameter tuning. In the tabular setting this means converting rows of a table into textual examples and adding them to the prompt; the LLM then reasons about the relationship between the serialized features and the target. The core insight is that this reasoning can extract structure and rules from very few labeled examples by leveraging the LLM’s pretrained world knowledge together with the in-prompt examples.

# Serializing tables and tasks into natural language prompts
Because LLMs are fundamentally text models, a necessary step for any language-interfaced tabular approach is serialization: converting rows and columns of a table into a natural-language representation that can be placed into a prompt. The standard serialization used in the paper takes an example $(\mathbf{x}^i,\mathbf{y}^i)$ together with the feature name set $F=\{f_j\}_{j=1}^d$ and renders it as a short textual description of each feature followed by the label. Formally the paper writes this as
$\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = \text{`` } f_1\ \text{is}\ \mathbf{x}^i_1.\ \dots\ f_d\ \text{is}\ \mathbf{x}^i_d.\ \text{Answer:}\ \mathbf{y}^i\text{''}$,
so a single row becomes a compact, human-readable sentence sequence.

A practical prompt for tabular tasks commonly includes three parts. First, a basic information block states the task as a question (for example, ``Does this patient's data indicate chronic heart failure? Yes or no?''), enumerates feature names and types (and category values for categorical features), and contains a few serialized demonstration examples with their labels. Second, reasoning instructions can be added: the paper finds it helpful to guide the LLM’s internal problem solving with a two-step instruction that first asks the model to infer general tendencies or causal relationships between features and the label (without looking at the demonstrations), and then to combine that prior knowledge with the few-shot examples to generate concrete decision criteria. Third, response instructions constrain output format so the LLM returns machine-parsable rule-like statements.

This serialization approach is widely used in recent work: data and feature descriptions are expressed in natural language, then fed into the LLM either for in-context prediction or for parameter-efficient tuning. The benefit is straightforward—LLMs can reason over textual feature descriptions and examples—but serialization also creates a practical challenge: as the number of features $d$ or the number of examples grows, the serialized prompt length increases, potentially exceeding the model’s context window or degrading performance.

# Parameter-efficient tuning (LoRA, IA3) vs prompt-only inference
When adapting LLMs to tabular tasks researchers have taken two broad approaches. One is prompt-only or in-context inference: the model is left unchanged and all task conditioning is done via the prompt (task description and few-shot examples). The other is to adapt the model’s parameters, typically with parameter-efficient tuning methods; the paper cites techniques such as LoRA and IA3 as representative examples of that strategy. Both strategies have been explored in recent tabular-learning research.

These two choices trade off accessibility and accuracy. Prompt-only in-context methods are attractive because they require only API-level inference access: you can form a prompt containing the serialized examples and ask the model to output predictions. However, for end-to-end prediction this naive usage requires an LLM call per test sample, which is computationally expensive at inference time and often impractical in production. In contrast, parameter-efficient tuning adapts a (small subset of) model parameters to a specific task and can yield higher accuracy, but it requires the ability to perform training on the model—that means access to training code, model checkpoints, or a tuning API. As the paper emphasizes, many state-of-the-art LLMs (the examples referenced include models available only through inference APIs) do not expose such tuning capabilities, rendering fine-tuning–based approaches infeasible in many real-world deployments.

The experiments in the paper illustrate this trade-off concretely: TabLLM, a baseline that uses parameter-efficient tuning (IA3 in the prior work), requires LLM checkpoints and therefore used a different publicly available backbone (T0) in the comparison, whereas the in-context baselines used the GPT-3.5 API. Thus, the choice between tuning and prompt-only inference is not just about learning dynamics but about what level of access is available to the practitioner.

# Representative baselines: In-context prompting, TABLET, TabLLM, LIFT/AnyPredict
The literature contains several representative language-interfaced approaches for tabular learning; the paper evaluates or discusses a subset that captures the main design patterns.

In-context prompting (termed simply “In-context” in the evaluations) places the few-shot serialized examples and the task description directly into the prompt and asks the LLM to produce labels at inference time without any parameter updates. This is the simplest, prompt-only paradigm.

TABLET augments in-context prompting with auxiliary hints derived from an external classifier: the prompt includes rule-sets and prototypes produced by that classifier to improve the LLM’s inference. In other words, TABLET uses a hybrid of external symbolic guidance and LLM reasoning inside the prompt to try to improve few-shot predictions.

TabLLM follows the parameter-adaptation route. It applies parameter-efficient tuning (the paper cites IA3) to adapt the LLM to tabular tasks and then uses the adapted model for inference. Because parameter-adaptive approaches require training access, TabLLM is constrained to LLMs for which checkpoints and training tools are available.

Earlier works such as LIFT and AnyPredict (cited in the paper) exemplify the overall pattern of serializing features and tasks into natural language then employing the LLM via in-context learning or tuning. Each of these baselines explores a point in the design space formed by (a) how tabular inputs are serialized, (b) whether and how auxiliary information or structured hints are provided in the prompt, and (c) whether the LLM is tuned or only queried.

# Observed challenges: inference cost per sample, restricted fine-tuning access for API-only models, long-context fragility
Applying LLMs directly for end-to-end tabular prediction uncovers several consistent, practical limitations.

First, inference cost per sample. Prompt-only approaches that ask the LLM to produce a label for each test row require one model query per test sample. This leads to high computational and latency costs at inference time. The paper contrasts this with the FeatLLM idea of using the LLM only as a feature engineer: in FeatLLM the LLM is queried a modest number of times to generate a set of rules (feature transforms), and a lightweight downstream model (e.g., a linear classifier) is used for all test-time predictions, avoiding per-sample LLM calls and substantially reducing inference latency.

Second, restricted fine-tuning access. High-performing parameter-adaptation methods need the ability to train or fine-tune the model. The paper highlights that many top-performing LLMs are available only through inference APIs and do not expose training interfaces or checkpoints. Thus, parameter-efficient tuning approaches (LoRA, IA3 and similar) may be inapplicable in practice for models that are API-only, limiting the set of LLMs that can be adapted with these techniques.

Third, long-context fragility. Serializing many features into a prompt increases its length; models have finite context windows and their performance can drop as prompt length grows. The paper observes datasets with large numbers of attributes (e.g., datasets with over 100 columns) pose concrete challenges for prompt-based methods. In experiments the authors report that some LLM-based methods (In-context, TABLET, TabLLM) failed to produce usable inferences on high-dimensional tables, whereas an approach that controls prompt size is needed for robust performance on many-feature datasets.

# When direct LLM prediction underperforms or becomes infeasible (many-feature tables)
There are clear, empirical conditions under which direct LLM prediction becomes suboptimal or infeasible. The paper identifies several of them and demonstrates both the failure modes and remedies.

Large numbers of features are a primary issue. When $d$ is large the serialized prompt either exceeds the model’s context window or becomes so long that the LLM can no longer effectively reason across all columns; in the authors’ experiments, several LLM-based baselines could not infer on datasets with many attributes. Closely related is the risk of spurious correlations in low-shot settings: with few labeled examples an unconstrained LLM can latch on to incidental patterns in irrelevant columns and produce rules that do not generalize. The paper’s spurious-correlation experiment—attaching unrelated columns from a different dataset to a target table—shows that many models degrade as noise features accumulate, whereas a method that explicitly reasons about task–feature relevance and filters rules can be more robust.

FeatLLM exemplifies one design that mitigates these problems. Instead of issuing per-sample LLM queries, it asks the LLM (via a structured prompt) to produce class-specific decision rules and then parses those rules into binary features. Concretely, for a dataset $\mathcal{D}=\{(\mathbf{x}^i,\mathbf{y}^i)\}_{i=1}^N$ with feature names $F$, the LLM produces rule sets which are converted to per-class binary vectors $\mathbf{z}_k^i\in\{0,1\}^R$ indicating, for class $k$, which of the $R$ extracted rules each sample satisfies. A simple learned scoring model maps those binary features to class logits via
$\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot\mathbf{z}_k^i$, and probabilities are obtained with a softmax,
$\mathbf{p}^i=\text{Softmax}([\text{logit}_1^i,\ldots,\text{logit}_c^i])$.
This design has three practical advantages emphasized in the paper: (1) inference for many test rows does not require any LLM calls (only evaluation of the learned linear-like model), (2) by constraining rule generation with task and feature descriptions plus a two-step reasoning instruction the LLM is encouraged to rely on prior knowledge and avoid spurious correlations, and (3) prompt-length issues are alleviated by applying bagging and ensembling: each ensemble trial asks the LLM to produce rules over a subset of features or examples, so the individual prompts stay short while the ensemble covers many features overall.

The experiments corroborate these claims: FeatLLM achieves strong few-shot performance across a range of datasets, is robust to added noisy columns (rules derived from noisy columns constituted only about 1–2% of the total), and has much lower test-time latency than methods that require per-sample LLM inference. The paper also cautions that no method is immune to all failure modes: FeatLLM can still pick up spurious or incorrect rules in some settings (for example, when closely related but misleading columns are present), which motivates the ensemble and tuning steps that filter out weak or irrelevant rules.

In summary, direct LLM prediction (prompt-only per-sample inference) can be simple to set up but becomes costly and fragile as the number of features grows or when only API-level access is available. Parameter-efficient tuning can improve accuracy but requires training access that many production LLMs do not expose. Hybrid strategies that use LLMs as structured feature engineers—extracting rules or transformations in a small number of queries and then training a lightweight model for test-time prediction—offer a pragmatic middle path that addresses the main limitations observed in practice.
