\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 14: Limitations, Broader Impacts, and Future Directions

# Dependence on LLM prior knowledge: biases, misinformation, and domain shift
FeatLLM's core idea is to harness the "rich prior knowledge" encoded in large language models (LLMs) as a substitute for scarce labeled data. The framework deliberately leverages that prior knowledge in two places: (1) a Step‑1 reasoning prompt that asks the LLM to state general tendencies or causal relationships between features and the target (so the model can surface commonsense or domain priors), and (2) a Step‑2 prompt that combines those priors with a few serialized examples to derive concrete rule-based features. The empirical results in the paper show this strategy is effective in few‑shot settings — FeatLLM often outperforms other few‑shot baselines and generates many features that have non‑trivial AUROC with respect to the target (the paper reports that most generated rule features are informative before tuning, and that tuning further filters irrelevant rules).

This reliance on LLM priors is a double‑edged sword. When the LLM's prior knowledge is accurate and appropriately aligned with the target domain, it provides the missing inductive bias that few labels cannot supply. The paper demonstrates this advantage by applying FeatLLM even to datasets that were unlikely to be memorized by the LLM (newly added UCI datasets and synthetic datasets), where the LLM still used commonsense or domain reasoning to produce useful rules. At the same time, the authors explicitly acknowledge that priors can dominate and that analyses of societal biases and misinformation in LLMs are an important research direction (see the paper's Broader Impact statement).

Two concrete failure modes are visible or discussed in the paper. First, the LLM can articulate incorrect causal relationships or overgeneralize priors, producing rules that reflect bias or misinformation rather than the true data-generating process. Second, under domain shift — when the target population differs substantially from the population reflected in the LLM's training data — the LLM's priors may be misleading. The authors empirically illustrate related fragility: while FeatLLM is relatively robust to randomly added irrelevant columns (it degrades less than many baselines in the spurious‑correlation experiment), they also report cases (in the Appendix) where FeatLLM can learn spurious correlations or misunderstand causal relationships if the appended columns are closely related in misleading ways.

Practical implication: any deployment of FeatLLM must treat the LLM's priors as a strong, but fallible, source of knowledge. The framework's advantage in low‑shot settings arises precisely because the LLM injects knowledge beyond the few labeled points; when that knowledge is incorrect, the model's outputs will reflect those errors. The paper frames investigation of these biases and their societal impacts as important future work and motivates human oversight in high‑stakes settings (discussed further below).

# Safety and security risks in code generation/execution; sandboxing and audits
A distinctive implementation detail of FeatLLM is that rule text produced by the LLM is converted into executable parsing code by the LLM itself, and that generated code is run to transform raw tabular inputs into the binary rule features. Concretely, the paper states that the generated parsing code is executed using Python's exec() function to perform data conversion. The authors also document that the LLM's textual outputs can be syntactically noisy (for example, using "greater than" instead of the symbol ">"), which motivates automated parsing.

Because FeatLLM executes code that is generated (and therefore indirectly specified) by an LLM, this step introduces important safety and security considerations. The paper does not attempt a systematic mitigation or evaluation of runtime safety in the code-execution step; it focuses on the proof of concept and empirical performance gains. As a result, code generation and execution constitute a limitation in the current work: malformed or maliciously formed code can cause runtime failures, silent data corruption, or other undesirable behaviors in a production system if not handled carefully.

For practitioners and researchers building on FeatLLM, the paper's pipeline makes clear that code-execution risk is an area that needs attention. The authors do not provide production‑grade countermeasures in this work, so adopting safeguards (for example, executing generated parsing code only after validation, limiting the set of permissible operations, or running the code in a restricted environment) is a necessary practical step before deployment. The paper flags the parsing difficulty and uses the LLM to normalize rules into code as a pragmatic choice, but it leaves systematic safety engineering — such as sandboxing, audits, or formal parsing approaches — as an open operational requirement to make the method production‑ready.

# Scaling to larger labeled datasets and richer feature types beyond Boolean rules
FeatLLM is explicitly designed and evaluated for few‑shot/tabular settings. The authors state in the conclusion that the framework "is designed to focus on low‑shot learning regime only" and identify as future work the challenge of expanding to larger numbers of labeled samples and "exploring various feature types beyond rules." Several aspects of the paper illuminate why scaling is non‑trivial.

First, the learning dynamics change as sample size grows. In the few‑shot regime, the LLM's priors and the hand‑designed rule primitives provide most of the inductive bias; the downstream linear model only needs to learn the relative importance of rule features. The paper's ablation study shows that as the number of shots increases, weight tuning gains importance: when more data are available, estimating and fine‑tuning the weights $\mathbf{w}_k$ that combine rule features becomes both feasible and valuable. Thus, simply increasing data without rethinking representation capacity, regularization, or model class may not be the most effective path.

Second, FeatLLM's current feature representation is rule‑based and binary: each generated rule yields a 0/1 feature indicating whether a sample satisfies a rule for a class. Binary rule features are highly interpretable and effective in low‑shot settings, but with abundant labels more expressive or higher‑capacity features (continuous transforms, interaction terms, parametrized feature templates, or learned embeddings) may be necessary to capture subtler patterns. The authors list "various feature types beyond rules" as explicit future work; designing these richer primitives will require (a) redefining how an LLM should be prompted to produce structured numeric transformations rather than Boolean tests, and (b) changing the downstream model and learning objectives to make proper use of those richer features.

Third, the engineering tradeoffs around prompt size and computational cost matter as the problem scales. The paper addresses the token‑count limitation by combining feature bagging with ensembling: a single LLM prompt extracts only a subset of features, and repeated trials with different bags produce an ensemble of rule sets. This strategy mitigates context‑window limits and produces robustness, but it also multiplies the number of LLM queries. In the experiments the authors set the ensemble size and rules per class to concrete values (20 ensembles, 10 rules per class) and report that, in their setup, the training-stage LLM usage was modest (for example, they note the method required only a limited number of API queries in their timing comparison). Moving to larger datasets may require re‑engineering the bagging/ensemble schedule, optimizing the number of prompts, or introducing hierarchical generation schemes so that the method remains computationally practical.

# Extending to regression/ranking and continuous outputs
The FeatLLM paper frames and evaluates the method in a classification context: prompts ask yes/no or categorical questions, rules are produced for each class, and the downstream logit-based combination produces class probabilities (the paper formulates logits as $\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i$ followed by a softmax over classes). The methodology and experiments therefore target discrete outputs.

Extending the same idea to regression, ranking, or other continuous outputs is not covered in the paper and is an open direction. Conceptually, the shift from discrete to continuous targets raises two main issues. First, per‑class rule generation is no longer a natural decomposition: classification lends itself to "rules that indicate class membership," whereas regression targets require features that correlate with varying magnitudes of the target. Second, the loss function and downstream model would need to be changed (for example, replacing cross‑entropy with mean squared error or a ranking loss), and the representation of generated features may need to move beyond binary indicators to continuous or parametric transformations that better express dose–response relationships.

The authors do not implement such extensions here, but they flag the broader ambition of richer feature types and larger‑sample regimes. These are the natural stepping stones toward adapting the FeatLLM idea to regression and ranking: (a) ask the LLM to propose numeric transformations or parametric rule‑scores rather than purely Boolean checks, (b) allow generated features to be real‑valued, and (c) fit appropriate loss functions and models. The paper leaves the technical realization of these ideas to future work.

# Integration with AutoML, TabPFN-like priors, and interpretability frameworks
FeatLLM sits in a landscape of tabular learning approaches that combine priors, synthetic data pretraining, and automated model selection. The paper compares FeatLLM against several such baselines (including TabPFN and other conventional or LLM‑based methods) and documents that FeatLLM often achieves superior few‑shot performance while keeping inference cheap (because inference does not require calling the LLM per sample). The authors also note that ideas like bagging and ensembling are conceptually adaptable to other LLM‑based approaches, but doing so would often increase per‑sample inference cost and thus may be impractical.

There are several promising integration points implied by the paper. One is to treat FeatLLM as a feature‑generation module within a larger AutoML or model‑selection pipeline: once the LLM produces a bank of candidate features (rules or richer transforms), an AutoML system could search over model classes and regularization strategies that best exploit those features. Another is to combine FeatLLM's rule features with learned priors from approaches like TabPFN: for example, a synthetic‑data pretrainer could provide a Bayesian prior over how combinations of features map to labels, while FeatLLM supplies human‑readable and data‑driven candidate features; integrating both signals could improve robustness across regimes. Finally, FeatLLM's rule outputs are inherently amenable to interpretability frameworks: the rules themselves are interpretable, and the learned non‑negative weights on rule features provide a simple importance ordering. The authors explicitly point to interpretability as a target for future work.

The paper does not attempt these integrations, but its experimental findings — that rule features are both informative and filterable by tuning, and that ensemble bagging reduces prompt‑size issues — suggest FeatLLM could be combined with AutoML, prior‑based pretraining, or interpretability toolsets to build more automated, reliable workflows.

# Human-in-the-loop validation for high-stakes domains (healthcare/finance)
The authors highlight that FeatLLM is particularly relevant in domains where labeled data is costly to obtain — notably healthcare and finance. They also emphasize the need for further analysis of "societal biases and misinformation embedded in the prior knowledge of LLMs" since those priors can directly shape predictions and potentially dominate limited labeled data.

Because LLM‑derived rules can be interpretable (they are textual conditions) and the downstream model is simple (a non‑negative linear combination of rule indicators), FeatLLM is well suited to human‑in‑the‑loop workflows: domain experts can inspect, validate, and edit candidate rules before they are used for downstream training or inference. The paper does not experimentally study human vetting, but it frames such oversight as a natural and important safeguard, especially in high‑stakes applications. For deployment in regulated or safety‑critical contexts, the authors' Broader Impact discussion implies that a human reviewer should evaluate generated rules for correctness, fairness, and plausibility; additional checks might include testing rule behavior on held‑out or synthetic edge cases and monitoring feature importance learned by $\mathbf{w}_k$ during tuning.

In short, FeatLLM's human‑readable artifacts (rules and learned weights) make it practical to add expert review steps; the paper positions this as a prudent strategy rather than reporting it as an implemented part of the experiments.

# Future work highlighted by authors: more feature types, large-sample regimes, deeper interpretability
The paper's conclusion summarizes the principal directions the authors consider important next steps: expanding FeatLLM to (1) craft new features for datasets with larger numbers of samples, (2) explore various feature types beyond Boolean rules, and (3) bring deeper interpretability to the framework.

Expanding to larger sample sizes will change the balance between LLM priors and empirical evidence: weight estimation and regularization strategies will need to be rethought so the downstream model properly integrates many labeled examples while retaining useful prior structure. Exploring richer feature types means moving beyond yes/no checks to incorporate numeric transforms, parametric rule‑scores, interaction functions, or other structured features that capture continuous and higher‑order patterns. Deepening interpretability involves both algorithmic and empirical work: algorithmically, by designing generation prompts and downstream architectures that produce stable, auditable features; empirically, by measuring rule stability across ensembles, analyzing how learned weights reflect rule quality, and auditing generated rules for biases.

The paper provides empirical motivations and preliminary technical scaffolding for each of these directions (for example, ablation studies that show the importance of reasoning prompts and feature descriptions in few‑shot settings, and experiments demonstrating that ensemble/bagging mitigates prompt length limitations). Turning these directions into concrete, production‑ready methods remains an open research program that the authors explicitly invite.

# Concluding perspective
FeatLLM demonstrates that LLMs can act as powerful feature engineers in low‑shot tabular learning: by extracting textual rules, parsing them into features, and training a lightweight downstream model, the framework attains strong few‑shot performance while keeping inference cheap and interpretable. At the same time, the paper is candid about limitations and open questions. The approach depends critically on the correctness and appropriateness of LLM priors, it introduces a code‑generation and execution step whose safety implications are not resolved in this work, and it is intentionally scoped to classification in the few‑shot regime with Boolean rules as the primary feature type. The authors identify extending to richer feature types, larger sample regimes, and deeper interpretability — as well as more systematic analysis of bias and societal impact — as the next frontiers. For students and researchers, FeatLLM offers a compelling proof of concept and a clear set of technical and operational challenges to tackle before similar systems can be relied on in safety‑critical or large‑scale applications.
