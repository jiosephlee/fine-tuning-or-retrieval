\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 13: Practical Guidance, Implementation, and Reproducibility

# End-to-end checklist: data curation, feature names/definitions, task phrasing
FeatLLM assumes a standard tabular input: a labeled dataset $\mathcal{D}=\{(\mathbf{x}^i,\mathbf{y}^i)\}_{i=1}^N$ with $d$ input columns and natural-language feature names $F=\{f_j\}_{j=1}^d$ plus (optionally) separate human-readable definitions for those feature names. Before you start prompting an LLM, collect and prepare those elements: (1) the small set of labeled examples you will use for few-shot demonstrations (the paper reports experiments with $k$ from very small values up to 32); (2) human-readable feature names and, when available, short definitions or descriptions of what each column means; and (3) the task description / label information written as a concise question (the paper uses question-style prompts such as “Does this patient’s myocardial infarction complications data indicate chronic heart failure? Yes or no?”).

When preparing demonstrations, serialize each example into text using the format used in the paper. In LaTeX notation the paper writes the serializer as
$\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = \text{" }f_1\ \text{is}\ \mathbf{x}^i_1.\ ...\ f_d\ \text{is}\ \mathbf{x}^i_d.\ \ \text{Answer:}\ \mathbf{y}^i\text{"}$.
Concretely, include feature-value pairs in natural language followed by the ground-truth label. For categorical features include the typical categories in the basic information part of the prompt so the LLM can reason about them correctly.

Finally, decide and record the FeatLLM hyperparameters you will use. The experiments in the paper set the number of rules per class to $R=10$ and the number of ensemble trials to $T=20$, and used GPT-3.5 with temperature $0.5$ and top-p $=1$. These values are a practical starting point because they control prompt length (rules per class) and the degree of ensemble averaging (trials). Keep these choices in your experiment configuration so results can be reproduced.

# Crafting clear demonstrations and response templates
FeatLLM relies on in-context learning, so the way you present demonstrations and the response format matters. The paper uses a three-part prompt structure: (1) a basic information description (task phrasing, feature descriptions, categorical value examples, and serialized few-shot demonstrations); (2) a reasoning instruction that guides the model’s internal chain-of-thought; and (3) a response instruction that constrains the output format to make parsing tractable.

For demonstrations, follow the serializer above and choose representative few-shot examples that exhibit variations relevant to the task. The reasoning instruction in FeatLLM is explicit: it splits the model’s process into two steps. Step 1 asks the LLM to state general tendencies or causal relationships between features and the target using prior knowledge (without looking at the demonstrations). Step 2 then asks the LLM to use the few-shot demonstrations plus the Step 1 summary to propose decisive rules for each class. This two-step structure is intended to reduce spurious correlations (because Step 1 grounds the model in general background knowledge) and to make the subsequent rule extraction more robust.

For response templates, instruct the LLM to produce a fixed-format list of rules per class and to follow a specific syntactic template for each rule (the paper enforces such formatting to make parsing easier). The prompt should tell the model how many rules to supply per class (the paper fixes this to 10) and remind it of the feature types so that, for example, it does not produce a numeric comparison on a categorical feature. The response instruction may also allow logical operators (AND / OR) where appropriate; the parser stage converts these structured rule strings into executable checks.

# Choosing bag sizes for features/instances to fit context windows
FeatLLM uses bagging (feature / instance sub-sampling) in each ensemble trial to keep each prompt within an LLM’s context window and to increase diversity across trials. The core idea in the paper is simple: when your table has many columns or you must include many demonstration lines, select only a subset of features and/or training instances for a given trial’s prompt. Repeat the whole rule-generation+parsing+training pipeline multiple times with different bags and average the resulting probability outputs across trials.

The experiments provide practical hyperparameter guidance: the authors used $T=20$ ensemble trials and $R=10$ rules per class. Their hyperparameter sweep showed that average performance improves as $T$ increases but plateaus near $T\approx 20$, and that $R=10$ was a useful trade-off between expressivity and prompt length. Choose bag sizes (how many features and examples per prompt) so that the serialized text remains well within your LLM’s context limit; smaller bags reduce per-prompt length but typically require more ensemble trials to cover all columns. In datasets with many columns (the paper cites Communities and Myocardial as examples), bagging is the mechanism that makes FeatLLM feasible.

# Designing parsing prompts and validating generated code
The rules that FeatLLM asks the LLM to produce are written in natural language; converting those textual rules into binary features (one per rule per class) is a required parsing step. The paper’s pragmatic solution is to use the LLM again to produce a small piece of code that implements the rules. Concretely, form a parsing prompt that includes a function name, a clear description of the inputs and outputs, and the inferred natural-language rules; ask the LLM to output simple executable code (for example, a Python function) that, given a tabular row, returns the rule-satisfaction booleans.

This approach leverages the LLM’s ability to understand semantic variants (“greater than” vs. “>”, wordy expressions, synonyms) so you do not have to write a brittle hand-coded parser that tries to cover all textual patterns. The paper then executes the generated code using Python’s exec() to perform the conversion from rows to binary rule-features. In the experiments, the LLM-generated code is the exact mechanism used to build the vectors $\mathbf{z}_k^i\in\{0,1\}^{R}$ for each class $k$ and sample $i$.

# Debugging misparsed rules and adding guardrails for types/units
The authors anticipate syntactic and stylistic variation in LLM outputs (for example, replacing “>” with “greater than”), and they deploy several guardrails in the prompt design to reduce parsing failures. First, the basic information section of the prompt includes the type of each feature (numeric, categorical, etc.) and, for categorical features, the allowed categories; this reduces type-mismatch rules. Second, the response instruction forces a fixed template for each rule and a fixed number of rules per class (the paper uses 10), which keeps the parsing problem bounded.

Even with these protections, some rules may be noisy or irrelevant. FeatLLM addresses this by learning per-rule importance from data: after converting rules to binary features, the pipeline fits a simple linear model with non-negative projected weights and cross-entropy loss (see the next section). The tuning step down-weights or effectively ignores rules that are not supported by the labeled data. In the paper’s analysis the authors computed AUROC between each generated rule-feature and the target and showed that many rules with low relevance are filtered out by tuning; they used a practical threshold (0.1) on learned weights to mark rules as effectively unused in a post-hoc analysis. The positivity projection $\max(\mathbf{w}_k,0)$ in the model (see the next section) is itself a guardrail: it enforces that rules only contribute non-negatively to the class logits.

# Managing cost/latency; batching and parallel API queries
One of FeatLLM’s key operational advantages reported in the paper is that LLM calls are required only during rule generation and parsing, not at per-sample inference time. The experiments report that the training-stage LLM usage is modest: the paper states the method “requires only 30 API queries” in their timing comparison and that these queries are trivially parallelizable across ensemble trials. In contrast, approaches that ask an LLM to predict each test sample incur a large per-sample inference cost.

Because FeatLLM’s inference schema runs a simple learned model (a linear combination of binary rule-features) without calling the LLM, inference latency and cost are comparable to conventional tabular models. In practice, the paper used temperature $=0.5$ for the LLM when sampling multiple trials and a top-p of $1$. The paper also notes that a higher sampling temperature is used to encourage diversity among trials for the ensemble. These concrete numbers are the operational knobs reported in the experiments and are suitable defaults when reproducing the work.

# Handling missing data, class imbalance, and multiclass setups
Multiclass tasks are explicitly supported by FeatLLM. The method generates $R$ rules per class and builds binary vectors $\mathbf{z}_k^i\in\{0,1\}^R$ for each class $k$. The paper uses a per-class linear score and a softmax to obtain probabilities. In the paper this is written as
\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,\qquad
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big),
\]
and the linear-model weights $\mathbf{w}_k$ are trained with cross-entropy loss. This design makes the method applicable to both binary and multi-class problems.

The paper does not develop a dedicated missing-data imputation strategy; FeatLLM’s prompt design asks that feature types and typical categories be provided in the basic information block. If your dataset contains missing entries, FeatLLM as described in the paper expects the table and the serialized demonstrations to reflect the same conventions the parser code will handle; the paper does not prescribe additional imputation or special handling. For class imbalance, the paper reports that, when performing $k$-fold cross-validation for epoch selection, they set $k$ to values (2 or 4) that guarantee each fold’s training set contains at least one example of every class; ensure folds and shot selection follow the same constraint to avoid degenerate training splits.

# Worked example outline (e.g., Heart/Myocardial): prompt, rules, parsing, training, interpretation
Below is a concise, paper-grounded sequence of steps as used for datasets such as Heart and Myocardial.

1. Prepare the dataset and meta-data. Collect the $k$ labeled examples you will show in-context, and assemble human-readable feature names and optional short definitions. For categorical columns, list the categories.

2. Build the prompt. Include (a) a short task description phrased as a question with label semantics; (b) feature descriptions including type information; (c) serialized $k$-shot demonstrations using the serializer $\text{Serialize}(\cdot)$ shown earlier; (d) a reasoning instruction that asks the LLM first to state general relationships (Step 1) and then to derive rules using the demonstrations (Step 2); and (e) a response instruction that fixes the rule template and asks for exactly $R=10$ rules per class.

3. Generate rules with the LLM. Run $T$ trials (the paper uses $T=20$), randomizing the order of the few-shot demonstrations and setting temperature (the paper used $0.5$, raising it as needed for ensemble diversity). Optionally bag features/instances so each prompt stays within the context window.

4. Parse rules to code. For each trial submit a parsing prompt that contains a function name, input/output description, and the textual rules; ask the LLM to emit simple Python code that evaluates the rules for a row and returns binary indicators. Execute that generated code (the paper used Python’s exec()) to produce $\mathbf{z}_k^i$ for all samples.

5. Train the lightweight model. For each trial fit non-negative-projected linear weights $\mathbf{w}_k$ per class to the rule-feature vectors by minimizing cross-entropy. The paper used the Adam optimizer with learning rate $0.01$ and trained for $200$ epochs, selecting the optimal epoch with $k$-fold cross-validation. The logits and probabilities follow the equation above.

6. Ensemble predictions. Average the per-trial softmax probabilities $\mathbf{p}^i$ across the $T$ trials to obtain final predictions.

7. Interpretation. The learned weight $\mathbf{w}_k$ indicates the importance of each rule for class $k$. In the paper’s analyses rules with very small learned weights are interpreted as uninformative; the authors used a threshold of $0.1$ in post-hoc analyses to quantify how many rules the model effectively ignored.

This sequence is exactly the pipeline used in the experiments that showed FeatLLM often outperforms alternative few-shot tabular baselines and is robust to extraneous columns when the reasoning instruction guides rule extraction.

# Reproducibility practices: seeding, logging, and configuration management
The paper reports several reproducibility choices you should mirror when implementing FeatLLM. First, each experimental setting was repeated multiple times with different randomness in train/test splits, and results are reported as averages with standard deviations (the paper repeats experiments three times). Second, hyperparameters used in the experiments are explicitly stated: GPT-3.5 with temperature $0.5$ and top-p $=1$, $T=20$ ensembles, $R=10$ rules per class, Adam optimizer with learning rate $0.01$, and $200$ training epochs with epoch selection by $k$-fold cross-validation (with $k$ chosen to ensure each training fold contains every class). The authors also release code (an anonymized GitHub link is provided in the paper), which you should use to confirm exact prompt templates and runtime configurations.

When you reproduce or extend the method, record the same set of metadata the paper reports: the LLM model and API parameters (model name, temperature, top-p), number of ensemble trials $T$, number of rules $R$, optimizer and learning rate, number of epochs, how $k$-shot samples were selected, how bagging was done (feature/instance counts per bag), and the number of LLM API queries incurred. The paper emphasizes that the total number of API calls is modest (their reported runs needed only about 30 API queries) and that the calls can be parallelized; logging them is part of an auditable experimental record. Finally, report averaged metrics and standard deviations over multiple random splits as the paper does, and make your prompt text and parsing prompts available alongside code so exact runs can be regenerated.

Concluding remark
This chapter distilled the practical, paper-grounded recipe for building, validating, and reproducing FeatLLM experiments: ensure clear feature metadata and question-style task phrasing, use the two-step reasoning prompt and fixed-format rule outputs, parse rules via an LLM-to-code pass and exec() the result to generate binary features, train a simple non-negative linear aggregator using cross-entropy, and use bagging plus an ensemble of $T$ trials to scale to many features and improve robustness. The paper’s experiments and ablations provide concrete defaults ($R=10$, $T=20$, temperature $0.5$, Adam $lr=0.01$, $200$ epochs) that are good starting points for implementation and reproducibility.
