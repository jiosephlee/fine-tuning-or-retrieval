\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 7: From Natural-Language Rules to Executable Features

# Parsing challenges: noisy LLM outputs and syntactic variability (e.g., ">" vs "greater than")
One of the central difficulties when converting natural-language rules into executable features is that the rules produced by a Large Language Model (LLM) are not guaranteed to follow a single rigid grammar. Even when prompts constrain format, LLM outputs exhibit syntactic variability: logical connectives may be written in different ways, numeric comparisons can be expressed either with symbols (e.g., ">") or in words (e.g., "greater than"), and categorical labels may be paraphrased or capitalized differently. The FeatLLM paper explicitly calls out this variety, noting that an LLM "might alter expressions, like substituting '>' or '<' with phrases like 'greater than' or 'less than'." This variability makes naive, hand-written parsers brittle: a rule parser that expects the exact token ">" will fail on the semantically identical phrase "greater than 10".

Heterogeneous tabular feature types amplify the parsing problem. The same natural-language phrase can refer to a numeric threshold, a categorical membership test, or a textual pattern depending on the feature's declared type. FeatLLM guards against some type mismatches by supplying feature type information (and categorical examples) to the LLM during rule generation, but even then the generated rule text can deviate from the intended syntactic pattern. In short, the pipeline must tolerate syntactic noise while preserving semantic correctness: the downstream component that produces binary "rule satisfied" indicators must understand the intended meaning of varied textual expressions.

Because of this fragility, FeatLLM avoids attempting to enumerate or hard-code every possible syntactic variant. Instead, it treats the LLM not only as the generator of rules but also as a robust translator from noisy natural-language rules into unambiguous, executable code that evaluates those rules on data. This design choice reduces the need for brittle pattern-matching parsers and leverages the LLM's semantic understanding to handle synonymy and rephrasing.

# Using an LLM to synthesize parser code from rules with a clear function signature and I/O spec
FeatLLM's parsing strategy is to let the LLM itself produce a small piece of code that implements the semantics of the inferred rules. The key prompt engineering element is to give the LLM a clear function signature and input/output specification, together with the natural-language rules to be parsed. Concretely, the pipeline places the function name, an explanation of the function inputs and outputs, and the list of inferred rules into a prompt, and then asks the LLM to return code implementing that function. The paper explains this succinctly: rather than building complex program code by hand, they "leverage the LLM itself" because it "is good at understanding the semantic meaning despite syntactic changes in text, and it has the ability to generate a simple code with instructions."

The I/O spec in the prompt serves two purposes. First, it constrains the LLM's output format, making parsing of the generated code straightforward: the returned artifact is a callable function that deterministically maps a row of the tabular input into binary checks. Second, providing type and category information in the prompt lets the LLM choose appropriate code idioms (e.g., membership checks for categorical features, numeric comparisons for continuous features). In FeatLLM this was part of the broader "response instruction" and "basic information description" framing used when eliciting rules: feature types and example categories are explicitly provided, and the LLM is instructed on the required format for rules. Appendix examples in the paper illustrate that supplying a function signature and I/O description yields compact, executable translations of each natural-language rule.

Because the LLM has been trained on code corpora, it is comfortable producing short, idiomatic code that normalizes synonyms (e.g., turning "greater than 10" into a numeric comparison) and implements logical combinations (AND/OR) as boolean expressions. In effect, the LLM converts noisy, free-form rule text into a normalized, machine-executable representation that removes ambiguity about operators, value formats, and membership tests.

# Executing generated code (e.g., Python exec) to compute rule satisfaction at scale
Once the LLM returns code that implements the rules' semantics, FeatLLM executes that code to transform raw tabular rows into binary rule-features. The paper states that "the generated code is executed using Python’s exec() function to perform data conversion." The execution produces, for each sample and for each generated rule, a binary indicator that records whether the sample satisfies the rule.

These generated binary features are organized per class. If there are $R$ rules per class and $c$ classes, then for sample $i$ FeatLLM denotes the rule-feature vector for class $k$ as $\mathbf{z}_k^i \in \{0,1\}^R$. The downstream predictor is deliberately simple: a linear model without bias maps these binary features into per-class logits and probabilities. The paper uses the following formulation:

\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\qquad
\mathbf{p}^i = \text{Softmax}\bigl([\text{logit}_1^i, \ldots, \text{logit}_c^i]\bigr),
\]

where $\mathbf{w}_k$ are trainable weights that capture the importance of each rule for class $k$, and the $\max(\cdot,0)$ projection enforces non-negativity so that generated features cannot actively reduce a class's likelihood during learning. The model is trained by optimizing cross-entropy on the few-shot labeled examples to learn $\mathbf{w}_k$.

To increase robustness and to cope with prompt-size limits, FeatLLM repeats the entire rule-generation + parsing + model-training process multiple times and ensembles the resulting predictors. The paper reports using ensembles to average predicted probabilities across $T$ trials (they use $T=20$ in experiments), and they randomize prompt elements (e.g., demonstration order) and set a non-zero sampling temperature during rule generation to encourage diversity. Bagging — selecting random subsets of features or instances for each trial — both increases diversity and reduces prompt length for datasets with many columns. Executing the generated code for each trial produces a collection of binary-feature matrices that are then scored, weighted, and averaged to produce final predictions at inference.

# Handling data types, categorical mappings, thresholds, and missing values
FeatLLM tackles type-related parsing errors primarily by supplying explicit feature type information in the prompt used to generate rules. When the prompt includes whether a column is numeric or categorical and optionally enumerates category values for categorical variables, the LLM is guided to produce rules consistent with feature type. The paper emphasizes that "when formulating rules, we let the LLM refer to the type of each feature in the basic information description part to avoid type mismatches in rules." This makes it less likely that the LLM will generate, for example, a numeric comparison for a categorical column or propose an impossible category value.

For categorical mappings, the prompt can list valid categories; the LLM then tends to generate membership-style rules (e.g., "feature X is in {A, B}"), and the synthesized parser code implements those as boolean membership checks. For numeric thresholds, the LLM often uses natural-language comparators ("greater than 5"), and the generated code normalizes these to explicit numeric comparisons. Because the LLM is responsible for producing code, it resolves the syntactic variability in comparators and threshold expressions: textual synonyms become consistent operators inside the synthesized function.

The paper does not provide a detailed treatment of missing values; it focuses on parsing rules and converting them into binary checks. As such, the handling of NaNs or missing entries is not explicitly described in the main method. In practice, the synthesized parser code (produced by the LLM) carries the responsibility for any conversion logic it includes; because FeatLLM relies on the LLM to produce correct conversion and checking behavior, any explicit missing-value policy would have to be encoded in the prompt or result from the LLM's default handling. The paper does not prescribe a canonical missing-value strategy.

# Validation strategies: unit tests, sanity checks, and fallback behaviors
FeatLLM uses several empirical and model-level mechanisms to validate and prune rules, rather than relying on handcrafted parser unit tests described in the paper. The validation workflow described in the paper includes measurement of feature informativeness, weight-based filtering after tuning, and ensembling-based consistency:

- Feature quality measurement. The paper measures the informativeness of generated binary features by computing the AUROC between each binary rule-feature and the target labels. They report the fraction of generated rules with AUROC $> 0.5$, confirming that the majority of rules are informative "before tuning." This per-feature AUROC is a straightforward sanity check that quantifies whether a rule correlates with the target.

- Weight tuning and thresholding. After generating binary features, FeatLLM fits the linear model and learns non-negative weights $\mathbf{w}_k$. The fitted weights provide an immediate, data-driven signal of a rule's utility. The paper filters out low-importance rules by thresholding learned weights: rules with weight below a chosen cutoff (they used $0.1$ in analysis) are treated as effectively irrelevant. This filtering is an automated fallback that leaves only rules supported by the few-shot data.

- Ensemble self-consistency. FeatLLM generates multiple independent rule-sets across trials (varying prompt order, sampling temperature, and via bagging). The observation in the paper is that "rules commonly inferred across multiple trials are more likely to be accurate." Thus, rules that appear repeatedly in different trials gain credence; ensemble averaging also mitigates the effect of occasional incorrect rules. Bagging further acts as a robustness check by forcing the system to work with different feature subsets or instance subsets.

- Cross-validation for training choices. For the small linear model trained on the binary features, the paper uses $k$-fold cross-validation to select the optimal number of epochs, which is a standard sanity check to avoid overfitting in the few-shot setting.

The paper does not describe a formal suite of unit tests or program-level static checks for the LLM-produced code. Instead, these empirical and model-driven diagnostics (AUROC, learned-weight pruning, repeated-trial consistency, and cross-validation) function as the practical validation and fallback mechanisms within FeatLLM.

# Security and safety considerations for code execution (sandboxing, auditing)
In FeatLLM the bridge from natural-language rules to executable features is concretely implemented by having the LLM return code and then executing that code via Python's exec(). The paper explicitly states that "the generated code is executed using Python’s exec() function to perform data conversion." Beyond this implementation detail, the main manuscript does not elaborate on runtime security, sandboxing, or code-auditing procedures for the generated code. The paper's broader discussion of impact focuses on how LLM priors can introduce societal biases into predictions and emphasizes the importance of analyzing those biases; it does not provide a treatment of code-execution safety or sandbox architectures in the experiments.

Therefore, within the scope of FeatLLM as described in the paper, the semantics are: (1) elicit code from an LLM with a clear I/O spec; (2) execute that code to translate rows into binary rule-features with Python's exec(); and (3) rely on empirical model-level checks (feature AUROC, weight-filtering, ensembling) to detect and mitigate bad or irrelevant rules. If a deployment requires explicit operational safety policies (sandboxing, static analysis, or execution auditing), those measures are outside the methods and analyses provided by the FeatLLM paper. The paper documents the executable-code approach and its downstream validation by model performance, but it does not prescribe a specific security framework for running LLM-generated code.
