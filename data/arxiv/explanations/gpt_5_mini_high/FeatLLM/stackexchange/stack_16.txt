\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does FeatLLM handle class imbalance in few-shot training?
Question:
Many tabular datasets are imbalanced. Does the cross-entropy loss use class weights, or do you balance class sampling when forming folds? Given the positive-only weights and no biases, does imbalance lead to biased logit growth for majority classes due to more opportunities to fit rules during rule induction or weight learning?
Answer:
Short answer: The paper does not introduce an explicit class-weighting or class-balanced sampling scheme when fitting the downstream linear model. FeatLLM does, however, include two implicit design choices that reduce—but do not eliminate—the raw advantage of majority classes: the prompt enforces a fixed number of rules per class (they use 10 rules/class) and the method uses bagging/ensembling plus LLM step-1 (prior-knowledge) reasoning. Because the learned logits are sums of non‑negative rule weights with no bias (the paper’s Eq. (1): $\text{logit}_k^i=\max(\mathbf{w}_k,0)\cdot\mathbf{z}_k^i$ and $\mathbf{p}^i=\mathrm{Softmax}(\cdot)$), class imbalance in the few-shot training set can still bias weight growth toward majority classes during cross‑entropy optimization.

Why imbalance can bias the learned logits (intuitive + technical): FeatLLM turns LLM rules into binary features per class and then learns positive weights for those features by minimizing standard cross‑entropy (no class weights are reported). For a given class $k$ the gradient that pushes a rule weight up is driven by the difference between how often that rule appears in samples of class $k$ versus its expected frequency under the model. Concretely, if you denote the active feature vector for class $k$ as $\mathbf{z}_k^i$ and the (positive) per-rule coefficients as $a_k=\max(\mathbf{w}_k,0)$, the per‑weight contribution to the loss gradients accumulates over training samples roughly as
$$
\sum_i (p_k^i - \mathbf{1}\{y_i=k\})\,z_{k,j}^i,
$$
so a class with more training examples (or more rule activations on those examples) will provide a larger net signal to increase its $a_k$. Because negative weights are disallowed and there is no learned bias term, the only way the model can prefer a class is by increasing the positive weight mass on that class’s rule features; minority classes with few examples therefore have fewer opportunities to push their weights up, and the optimizer can end up favoring the majority class.

What the paper does that helps (but is not a full fix): First, the prompt enforces a fixed number of rules per class (10), so the raw count of rule features is balanced across classes; this prevents a trivial imbalance where majority classes simply get more rule features. Second, the LLM’s two‑step reasoning (step‑1: general prior knowledge; step‑2: use examples) tends to produce rules for each class that are not solely driven by the few-shot counts, which can help minority classes generate sensible rules even with few examples. Third, bagging + ensembling (they run many trials with randomized demonstrations and subsets of features/instances) reduces variance and can blunt some imbalance effects in practice. The paper also enforces that cross‑validation folds include at least one example of each class (they set $k$ so training folds have every class), which avoids degenerate folds but is not the same as balancing class frequencies.

Practical remedies you can try (not described in the paper, but straightforward to add): if you encounter severe class imbalance in your few‑shot setting, the simplest fixes are to (1) use a class‑weighted cross‑entropy loss, e.g.
$$
\mathcal{L} = -\frac{1}{N}\sum_i \alpha_{y_i}\log p_{y_i},\qquad \alpha_k\propto\frac{1}{\text{freq}_k},
$$
so minority classes contribute more to the gradient; (2) perform stratified k‑shot selection or oversample minority examples when fitting the linear weights (or do per‑trial balanced bagging so each ensemble fit sees a balanced sample); (3) add a learnable class bias $b_k$,
$$
\text{logit}_k^i=\max(\mathbf{w}_k,0)\cdot\mathbf{z}_k^i + b_k,
$$
and initialize $b_k$ to $\log$ of an assumed class prior (this lets you correct priors without breaking the positive‑weight interpretability of rules); (4) allow signed weights (remove $\max(\cdot,0)$) if you want rules to be able to veto a class (at the cost of the “only-positive evidence” interpretability); or (5) use focal loss / stronger regularization or early stopping (they already use CV to pick epochs) to limit overfitting by majority class examples. A practical balanced approach that preserves interpretability is to keep equal rules per class, use stratified few‑shot selection or balanced bagging for the weight fit, and add class bias terms (or class‑weighted loss).

Bottom line: FeatLLM as reported does not apply explicit class‑weighting or sampling to correct imbalance; its fixed-per‑class rule extraction, LLM priors, and ensembling reduce some imbalance pressure, but imbalance can still push weights/logits toward majority classes because of the positive‑only weights and lack of bias. If you need robustness to strong class imbalance, add one of the standard remedies above (class‑weighted loss, stratified/oversampling, class biases, or allowing negative weights) and validate on held‑out data or with calibration.
