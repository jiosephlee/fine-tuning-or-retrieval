\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How is LLM-to-code parsing made safe and reliable when using Python exec()?
Question:
The framework prompts the LLM to generate Python code that implements the rules and then executes it with Python's exec(). How do you sandbox or constrain the code to prevent arbitrary execution risks? Do you validate the function signature, import statements, and AST before execution? Also, how do you enforce consistent handling of missing values, type mismatches, and unseen categorical levels in the generated code?
Answer:
Short answer: in the paper the authors rely on careful prompt design (constraining output format, including feature types and I/O descriptions) and then exec() the small piece of code the LLM produces, but they do not describe a full production-grade sandbox or an AST-based approval pipeline. For a research demo that works with limited queries and trusted compute this can be pragmatic, but if you want safe and reliable deployment you should add static checks, a strict execution sandbox, and deterministic handling of missing/unseen values. Below I explain what the paper actually does, why exec() is risky, and practical safeguards you can (and should) add.

What the paper actually does
The paper explicitly says they constrain the LLM’s response format (so parsing is easier), include feature type information and example categories in the prompt (so the LLM can avoid type-mismatched rules), and instruct the LLM to emit a simple function (they “include the function name, input and output descriptions, and inferred rules in the prompt”). They then run the generated code with Python’s exec() to convert data into binary rule-features. The writeup does not list AST validation, explicit import blocking, process isolation, or runtime resource limits — it focuses on prompt-level constraints and then uses an ensemble and weight-tuning step to filter weak/irrelevant rules for model quality.

Why exec() is dangerous
exec() runs arbitrary Python source. Even a seemingly small snippet can import os/subprocess, perform file or network I/O, spawn long-running loops, or access sensitive filesystem/environment. Prompt-format constraints reduce syntactic variation but do not prevent malicious or accidental side effects. Relying solely on the LLM to produce “simple” code is brittle for safety.

Concrete safeguards to make LLM$\to$code safe (recommended for production)
First, prevent dangerous constructs syntactically and semantically before execution. Parse the generated source with ast.parse() and inspect/validate the AST: allow only a whitelisted set of node types (e.g., Module, FunctionDef, Return, BoolOp, Compare, Name, Constant, Subscript, Load, Dict/List/Set, IfExp, UnaryOp, BinOp with limited operators), forbid Import/ImportFrom, Exec/Global/Nonlocal, Attribute chains that could reach __class__ or dunder names, and disallow Call nodes to any name not in a small whitelist. Also validate the function signature (expected name, expected single row argument, no *args/**kwargs), ensure the function always returns bool/int, and reject code exceeding a node/line budget.

Second, execute in a constrained runtime. Do not exec into the unbounded globals. Execute compiled code in a minimal globals dict with an empty or very small __builtins__ and only safe helper functions you explicitly provide (for instance safe_get, safe_eq, safe_num). Even then, CPython-level “safe globals” are not bulletproof — so prefer process-level isolation: run the code in a short-lived separate process (or container) with no network, read-only filesystem, unprivileged user, strict ulimit/cgroups for CPU and memory, and a wall-clock timeout. If you need stronger guarantees use container sandboxing (Docker with seccomp, or real VMs) or sandboxing frameworks (RestrictedPython, or language-runtimes that give real sandboxes).

Third, force the generated code to use your safe helper API (and check that it does). Instead of letting the LLM write arbitrary expressions that handle missing values, provide a small set of vetted helper functions (safe_get(row, name), to_float(x), is_missing(x), map_category(x, allowed, default)) and include those helpers in the execution globals. In AST validation require that only these helper names appear in Call nodes. This makes behavior for missing values, type coercion, and unseen categories deterministic and centralizes policy.

Fourth, pre-normalize input data so rules run against canonical values. A simple normalization pass converts numeric-like strings to floats or None, maps unknown categorical levels to a single token like "UNK", normalizes datetimes, and encodes missing values consistently. If the LLM-generated rule expects normalized inputs (you should include this in the prompt), you avoid ad-hoc handling in generated code.

Fifth, test generated functions on edge cases before applying them to full data. Run the function against a small suite of synthetic rows that exercise NaNs, empty strings, unseen categories, extreme values, and verify the function returns a boolean and does not mutate state or perform I/O. Reject or re-prompt any rule that errors or returns non-boolean values.

Alternatives that are far safer
As the paper notes, the LLM is good at mapping noisy language to code/logic. A safer pattern is to ask the LLM to output a structured representation (JSON or a small DSL / rule AST) rather than raw Python, then interpret that structured output with your own evaluator. Interpreting a whitelist of operators and operands that you control is much easier to audit and sandbox than executing arbitrary generated Python.

How the paper’s design helps (but doesn’t remove the need for the above)
By including feature types and example categories in the prompt and constraining format, the paper reduces parsing failures and type-mismatch bugs; by ensemble and weight-tuning they reduce the downstream impact of noisy/irrelevant rules on prediction quality. But those mechanisms do not address arbitrary code execution risks — for that you need AST checks, helper-only execution, process isolation, time/memory limits, and canonical preprocessing as I described.

Short checklist for a safe pipeline
Ensure the prompt asks for a fixed function signature or structured JSON; parse the output with ast or JSON; statically validate the AST/JSON; run unit tests on the generated function; execute only in a restricted process/container with resource limits and no network; provide and force use of safe helper functions; normalize inputs up-front; and finally, reject and re-prompt any rule that fails static or runtime checks.
