\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Details on the spurious-correlation stress test and rule attribution
Question:
In the Heart dataset experiment augmented with random columns from Adult, you report that only 1-2% of rules referenced the noisy columns. How did you detect that a rule references an augmented column (by name matching)? Could the LLM still use Adult-derived features indirectly via high-level reasoning (e.g., 'education' akin to socioeconomic status) and thus slip in via Step-1 priors? Did you also analyze the learned weights to see if any noisy-column rules got high importance?
Answer:
Short answer: we detected noisy-column rules by inspecting the parsed/executable rule code (i.e., by matching the feature identifiers that the parser produced to the list of injected Adult columns), and then checked their learned weights after fitting the downstream linear model. Because FeatLLM uses an LLM-based parser that emits small Python predicates referencing the original column names, this amounts to reliable name-based detection after the parser “normalizes” whatever natural-language phrasing the rule used. We also verified that such noisy-column rules were rare (the $1$–$2\%$ figure in the paper) and—after tuning—tended to receive very small weights and thus little influence on the final ensemble; nevertheless, indirect leakage through Step‑1 priors is possible and is an acknowledged limitation.

Longer explanation (intuition + technical detail)
When we run the spurious‑correlation stress test we follow the same pipeline described in the paper: the LLM produces natural‑language rules, we feed those rules to the LLM‑assisted parser which emits small Python code snippets (the code is executed with exec()) that evaluate whether a sample satisfies each rule. Because the parser outputs code that explicitly references the dataset columns, we detect whether a given rule “uses” one of the injected Adult columns by checking the identifiers accessed in that generated code against the set of injected column names. In practice this is equivalent to name‑matching after a normalization step performed by the parser (so the parser converts variants like “education level” into the concrete column name used in the code). This is the mechanism behind the reported $1$–$2\%$ number: it is the fraction of parsed rules (across ensemble trials) whose generated code referred to one of the noisy Adult columns.

Could the LLM instead “smuggle in” Adult knowledge via high‑level priors (Step‑1)? Yes—conceptually there are two ways priors can affect the final features. In Step‑1 the LLM is asked for general tendencies (e.g., “socioeconomic status correlates with X”), and in Step‑2 it grounds those tendencies into concrete rules using the available column names and the few examples. If the LLM grounds a socioeconomic concept into an injected Adult column (for example it explicitly maps “low education” to the injected column named “education”), our parser will produce code that references that Adult column and we will count it as a noisy‑column rule. That is the direct channel and is detected by the name matching described above.

A subtler channel is that Step‑1’s priors bias which Heart columns the LLM chooses to mention or to write rules about (without ever referencing Adult columns). In that case no parsed rule references an Adult column, but the LLM’s prior still affected which Heart features were emphasized. That form of indirect influence is harder to detect with just name matching; it is a general concern for any method that leverages model priors. We mitigate this in several ways in the paper: we provide feature descriptions and types in the prompt (so the LLM has to respect types and is less likely to invent a spurious mapping), we learn non‑negative linear weights on the generated binary rule features so the data can downweight irrelevant rules, and we use bagging + ensemble so that idiosyncratic noisy rules from a single trial do not dominate the final prediction. We also explicitly note in the paper (and show in the Appendix) that when closely related columns are attached the method can still pick up spurious/casual mis‑mappings—so this is a known limitation.

What we did with learned weights. After parsing and creating the binary rule features we fit the simple linear model with non‑negative weights (the ReLU projection described in the Methods) and inspected those weights. As reported in the “Quality of features” experiment, many generated rules that are not predictive are given very small weights by training and are effectively filtered out by a modest threshold (we used $0.1$ as a practical cutoff for analysis). For the spurious‑column experiment the combination of the low incidence of noisy‑column rules ($1$–$2\%$) and the weight‑tuning step meant that very few noisy rules survived with large learned weight; when a noisy rule did get a high weight in a single trial its effect was largely diluted by ensembling across trials. We therefore concluded that noisy columns had little aggregate influence on predictions in our setup. At the same time, because low‑shot weight estimates can be noisy, we do observe occasional failure cases where spurious rules carry sizable weight—again, these cases tend to happen when the attached columns are semantically very close to legitimate predictors (see Appendix).

Practical checks you can run (if you want to reproduce / stress test)
1) Reproduce the detection: parse the LLM rules into code, extract the variable/column identifiers from the generated code (or AST), and report the fraction that match the injected column list (this is what we did).  
2) Weight audit: group rules by whether they reference injected columns and compare the learned weight distributions and the fraction exceeding your importance threshold.  
3) Ablation: drop the injected Adult columns entirely and measure the change in validation performance; if the model relied on injected columns, performance will shift.  
4) Per‑rule diagnostics: compute per‑rule AUROC on the small training set and on a larger held‑out set (if available); rules that look predictive only on the tiny training set are likely spurious.  
5) Semantic checks: if you suspect synonym/semantic grounding rather than literal name matches, compute embedding similarity between rule text and column descriptions, or manually inspect high‑impact rules.

Bottom line: detection in the paper was done by checking the parsed code for explicit references to the injected Adult columns (i.e., name matching after parser normalization). That revealed only $1$–$2\%$ of rules came from noisy columns, and the downstream weight‑tuning + ensembling steps generally prevented those few noisy rules from exerting substantial influence. Nevertheless, indirect effects via priors (Step‑1 biasing which genuine Heart columns are emphasized) are possible and are a known limitation worth auditing with the checks above.
