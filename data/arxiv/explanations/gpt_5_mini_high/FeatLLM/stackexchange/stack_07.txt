\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How many LLM API calls are made per ensemble trial, and why does the paper mention only 30 queries?
Question:
The method appears to require one LLM call to generate rules and another to generate parsing code per trial. With $T=20$ ensembles, I would expect roughly 40 calls, possibly more if retries are needed. The paper reports 'only 30 API queries'. Can you clarify the counting method and whether some stages or ensembles share prompts, cache results, or batch multiple tasks per call?
Answer:
Short answer: the method as described requires about two LLM interactions per ensemble trial (one call to generate the natural-language rules for that trial, and one call to convert those rules into parsing/code), so a naïve count is $2T$ API calls (with $T$ the number of trials). The paper’s statement “only 30 API queries” in the timing paragraph is not fully unpacked in the text, but it is consistent with a few practical reductions that the authors could have (and which the paper hints at) — batching/completing multiple rule-sets per request, reusing a single parser or cached parsed outputs across trials, or running the particular timing measurement with a smaller effective $T$. Any of those will cut the raw $2T$ figure down to the reported $\sim 30$.

Why the naïve count is $2T$: every ensemble trial in FeatLLM has two LLM-dependent stages in the pipeline described in the paper: (1) the rule-extraction prompt that emits the $R$ rules per class for that trial (this produces the human-readable rule set for that trial), and (2) the parsing prompt that turns those natural-language rules into executable code. If you call the LLM once for (1) and once for (2) per trial you get 2 calls per trial, i.e. $2T$ calls total.

How you can get a much smaller number (and how the paper’s “30” is plausible)
- Batch / multi-completion per request: many inference APIs let you request multiple independent completions in a single HTTP call (OpenAI’s “$n$” parameter, or just asking the model to produce multiple rule-sets in one prompt). If you request $n$ rule-sets per generation call you only need $\left\lceil \frac{T}{n} \right\rceil$ generation calls instead of $T$. The same batching can be done for parsing.
- Reuse a single parser (or generate a parser template once): instead of asking the model to emit parsing code customized to each trial’s rules, you can call the LLM once to produce a robust parser function that takes arbitrary rule text and returns code/conditions locally. That converts $T$ parsing calls into $1$ one‑time call.
- Cache / deduplicate parse outputs: many trials will produce overlapping or identical rules (the paper even discusses self-consistency and repeated correct rules across trials). If you hash the textual rule-sets and only parse unique rule-sets, the number of parsing calls $U$ can be much smaller than $T$.
- Different $T$ or counting convention in that timing run: the Implementation section reports $T=20$ for the experiments, but the timing run on the Adult dataset (16 shots) where they quote “30 API queries” might have used a different $T$ or a measurement that counts only certain LLM interactions (for example counting only generation calls, or counting unique calls after deduplication). The paper does not explicitly enumerate which convention they used in Table~\ref{tab:cost}.

A compact accounting formula you can use when reproducing results is
$$
\text{API\_calls} \approx \left\lceil \frac{T}{n_{\text{gen}}} \right\rceil
+ \left\lceil \frac{U}{n_{\text{parse}}} \right\rceil + S
$$
where $T$ is the number of ensemble trials, $n_{\text{gen}}$ is how many independent rule-sets you ask the model to return per generation request, $U$ is the number of unique rule-sets that actually need parsing (after deduplication), $n_{\text{parse}}$ is how many parses you batch per parsing request, and $S$ counts one-time helper calls (e.g., to create a parser template, or to run verification). For example, if $T=20$ but only $U=10$ unique rule-sets appeared and you did one parse per unique set, then total calls = $20$ (generation) + $10$ (parsing) = $30$ — exactly the paper’s quoted figure.

Recommendation: if you need to reproduce the paper’s “30” figure exactly, check the released code (the authors point to a GitHub link) or contact the authors for which counting convention they used for the timing table. Otherwise, when reporting API cost yourself, state (a) how many independent ensemble trials $T$ you ran, (b) whether you used batching/multi-completions, (c) whether you reused a parser or cached parsed results, and (d) your token vs. call accounting — that will make comparisons apples-to-apples.
