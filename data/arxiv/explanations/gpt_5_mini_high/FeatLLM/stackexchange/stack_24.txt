\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### What is the average token cost per LLM call and do you perform retries for malformed outputs?
Question:
For both the rule generation and code generation prompts, what is the average input and output token count across datasets, and how often do you need to retry due to formatting or parsing errors? Do you implement any automatic repair prompts when the LLM output violates the specified response format?
Answer:
Short answer: the paper does not publish measured average token counts per LLM call nor an empirical retry/failure rate. What the paper does give you (and what you can use to estimate costs) is the exact prompt structure, the major prompt-size drivers (number of features, number of few‑shot examples, rules per class), the LLM backbone and sampling settings (gpt-3.5-turbo-0613, temperature=0.5, top_p=1), and the pragmatic parsing strategy (use an additional LLM call to turn free‑text rules into executable Python). The paper therefore does not report an explicit “retry rate” or an explicit automatic retry loop; instead the parsing LLM is presented as the main robustness / repair mechanism for noisy rule text.

Why token counts aren’t reported and how to estimate them. Token cost is dominated by the pieces the authors put into the rule‑generation prompt: (1) the task description and feature descriptions, (2) the few‑shot serialized examples (the paper uses the serialization they define),
$$
\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F)=\text{`` }f_1\ \text{is}\ \mathbf{x}^i_1.\ ...\ f_d\ \text{is}\ \mathbf{x}^i_d.\ \ \text{Answer:}\ \mathbf{y}^i\text{''},
$$
(3) the two‑step reasoning instruction, and (4) the response/formatting instruction (they force a constrained rule format and a fixed number of rules, e.g., 10 rules per class). A separate (usually smaller) code‑generation prompt contains a function signature, input/output descriptions and the inferred rules to generate the parsing code that produces binary features. So to estimate input tokens for the rule generation call you can use a simple accounting formula:
$$
T_{\text{rule\_in}} \approx T_{\text{task}} + d\cdot T_{\text{feat\_desc}} + k\cdot T_{\text{example}} + T_{\text{reason}} + T_{\text{resp}},
$$
and the output tokens are the textual rule list (roughly proportional to number of classes $\times$ rules per class $\times$ average tokens per rule). The parsing/code prompt token cost is roughly
$$
T_{\text{parse\_in}} \approx T_{\text{fn\_sig}} + T_{\text{rules}},
$$
and its output is the generated Python code.

A representative, conservative back‑of‑the‑envelope example (not reported in the paper, only implied by the prompt composition): for a moderate dataset (say $d\!\approx\!14$ features) and a modest few‑shot size ($k\!=\!16$), one serialized example can often be on the order of a few dozen to a few hundred tokens depending on verbose feature names/values. That means a full rule‑generation prompt can easily be in the low thousands of tokens and the LLM rule output in the low hundreds. Larger $d$ (hundreds of features) or more verbose feature descriptions will push you toward the model’s context limit, which is exactly why the authors use bagging (feature/instance subsampling) and limit rules per class to 10. The paper does not give per‑call token averages, so if you need precise billing estimates measure tokens empirically on your target datasets or construct the prompt and run a dry tokenization pass (OpenAI tokenizers or tiktoken) before sending.

Retries, malformed outputs and “automatic repair” in the paper. The authors explicitly acknowledge that LLM rule text can have syntactic variability (e.g., “>” vs “greater than”) and that this makes naive parsing brittle. Their chosen remedy is to lean on the LLM itself: they feed the inferred (possibly noisy) rules plus a function signature and input/output descriptions into another LLM call that returns simple Python code which is then executed (via Python’s exec()) to create the binary features. In effect, that parsing/code‑generation step is their built‑in robustness/repair mechanism. The paper does not report statistics about how often that parsing step failed, nor does it describe an explicit automated retry loop like “if output violates format then re‑prompt with X”; no retry counts or success rates are tabulated. In short, they (a) constrain the response format at rule generation time to reduce noise, and (b) use a second LLM call to produce executable parsing code that tolerates common syntactic variations. Beyond that, the paper does not document an explicit fallback or re‑prompt policy when parsing/code execution fails.

Practical advice if you want reproducible token/billing numbers and robust runs. Because the paper omits per‑call token statistics, the reliable way to get numbers is to (1) build the actual prompt for your dataset and run a tokenizer to get exact input tokens, (2) run a few dry LLM calls to measure average output token size, and (3) instrument your pipeline to count retries and failed execs. If you want stronger robustness beyond the paper’s approach, add a deterministic validation step after code generation (e.g., sandboxed exec + unit tests on some synthetic rows) and a short “repair” re‑prompt that says “the last output failed to execute because X; please correct only the offending lines” — that is a commonly used pattern though it is not described in the paper.

Summary: the paper does not report average token costs or retry frequencies. It provides the prompt structure and two concrete robustness choices: constrained response format and an extra LLM call that generates parsing code (the paper treats that as the practical repair mechanism). For exact token/billing numbers and empirical retry rates you will need to instrument the prompts on your target datasets (or run the tokenizer on constructed prompts) because token usage scales directly with number of features $d$, number of examples $k$, and verbosity of feature/value descriptions.
