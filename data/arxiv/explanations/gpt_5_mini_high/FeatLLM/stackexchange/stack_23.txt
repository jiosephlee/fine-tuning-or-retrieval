\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How are high-cardinality categoricals and unseen categories handled in rules and parsing code?
Question:
For columns with many categories (e.g., city names), do you allow rules like 'feature IN {A, B, C}' and is there a cap on list size? How does the generated code handle categories not seen in training or not listed in a rule? Are equality checks case-normalized, and do you provide a schema with allowed categories to the LLM to avoid typos?
Answer:
Short answer: the paper lets the LLM produce multi-value categorical checks (e.g., OR / “IN {A,B,C}”-style rules) and caps the number of rules per class (they fix $R=10$ rules/class). There is no explicit hard cap on how many values may appear inside a single rule in the write-up; practical limits come from the prompt/token budget, and the authors mitigate that with feature/instance bagging and ensembling. Parsing and evaluation of rules are done by code the LLM generates (and which the system runs via Python’s exec()); each rule is turned into a binary feature $(0/1)$, so values not listed in a rule simply make that rule evaluate to $0$. The paper does not claim a built‑in, guaranteed case-normalization or a strict schema enforcement — instead it relies on (a) including feature type descriptions and optional example categories in the prompt to guide the LLM, and (b) using the LLM again to produce robust parsing code (you can instruct that parsing code to normalize casing, handle synonyms, etc.), but those behaviors depend on how you prompt the LLM rather than being an automatic, enforced mechanism described as a default.

Why that follows from the paper: the “Basic information” prompt explicitly allows giving category examples (“for categorical variables, examples of the possible categories can be provided”), the response instruction allows logical operators (AND/OR) when expressing rules, and the authors fix the number of rules per class to 10 to limit output size. For parsing they write that noisy syntactic forms are expected, so instead of hand‑coding many fragile parsers they feed the natural‑language rules plus a function spec back to the LLM and ask it to emit simple Python code; that code is executed to produce binary features indicating whether each rule is satisfied. Those binary features then enter the simple linear scoring step (from the paper)
$\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot\mathbf{z}_k^i$ and $\mathbf{p}^i=\mathrm{Softmax}([\text{logit}_1^i,\dots,\text{logit}_c^i])$,
so an unlisted or unseen category simply yields $\mathbf{z}_k^i$ entries of $0$ for any rules that mention it, and the classifier relies on other rules/weights.

Practical implications and recommended checks (consistent with the paper’s design): because there is no formal schema-enforcement described, you should include canonical category examples in the feature description and, when you care about robustness, explicitly instruct the parsing step to normalize (lowercase, strip whitespace), map synonyms, or fall back to an “unknown” branch. For very high‑cardinality columns (thousands of distinct cities) the paper’s approach expects you to avoid enumerating huge IN‑lists in a single prompt: instead use bagging (the paper’s mechanism), ask the LLM to generate grouped rules (e.g., “cities in the Pacific Northwest” or “top‑20 most frequent cities”), or prompt the parser to use pattern/substring checks or external mappings. Finally, because the pipeline executes LLM‑generated code with exec(), validate the generated parser before running it on production data (this is implicit in the parsing-by-LLM design described in the paper).
