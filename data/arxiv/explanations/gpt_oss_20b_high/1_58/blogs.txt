# Why One‑Bit Language Models Are the Next Frontier  

Large language models have exploded over the past decade—from a few hundred million parameters to dozens of billions—yet each added layer consumes disproportionate amounts of compute power, GPU memory and air conditioning energy spent cooling racks that host them.  
Researchers are now turning toward *one‑bit* models—transformers whose every weight is reduced to one of three possible values  
$\{-1,\;0,\;+1\}$ —in order to keep predictive gains while collapsing computational overhead dramatically.



--------------------------------------------------------------------

## What Is ``BitNet b₁․₅₈''?

| Feature | Full‑precision baselines | One‑bit variant |
|---------|--------------------------|----------------|
| Weight format | float16 / bf16 | ternary $\{-1,\;0,\;+1\}$ |
| Activation format | float32/float16 | int8 |
| Non‑linearity | GELU + bias subtraction | SwiGLU + bias removed |
| Weight‐update strategy | Back‑prop through scaled linear map | ``absmean'' quantized linear map |
| Architecture head | Standard LLaMA style transformer | Same backbone replaced by *BitLinear* |

The core idea comes straight from BitNet—a pioneering work that showed realistic performance gain even when all matrix multiplications were reduced from floating‑point operations into cheap integer additions.<br>
In ``BitNet b₁․₅₈'', one extra weight state (`0`) was added so each parameter effectively occupies “onehalf” an integer byte together with some sharable sign bits (on average ≈ $log_2(3)=≈$ $31^\circ$ bits).  
This gives us an overall data footprint equivalent to a little more than one Integer–bit per parameter—hence “1⋅58 bits”.

---

### Absmean Quantization  

To force every weight back into $\{-1,\;0,\;+1\}$ during training two simple operators are applied _before_ any gradient update :

```latex
% Weighted input W ∈ ℝⁿˣᵐ  
% Scale factor γ computed globally per matrix
γ   =   \frac{1}{nm}\sum_{i,j}|W_{ij}|          % average absolute value  
ĤW   =   \operatorname{RoundClip}\!\biggl(\frac{W}{γ+ε},\, -\,a,\,+\,a \biggr)  
% where a = +99% percentile value taken per matrix during training 
              % RoundClip(x,a,b) ≜ max(a,min(b,round(x)))
```

So each weight is first normalized by its mean magnitude then snapped down/up toward its nearest ternar value owing to round‐clip mechanics—all performed **with full grad retention** (“straight‑through” estimator).

Activations were similarly clipped per token into the range $[-Q_b,Q_b]$, avoiding an extra zero‑point shift required by symmetric quantization schemes.

# Behind the Magic of Quantization in BitNet b1.58  

Large language models (LLMs) have made it possible for machines to read, write and interpret text with striking accuracy.  Yet their massive sizes—often dozens of billions of parameters—have turned them into energy‑hungry slow machines that are difficult to deploy on consumer GPUs or edge devices.  One of the simplest ways to tame a model’s footprint is **quantization** – forcing the many real‑valued weights into a compact discrete set.

In BitNet b<sub>1.58</sub>, a recent variant of the BitNet family, a single clever trick called **absmean quantization** pushes every weight into three possible values \(\{-1,\;0,\;+1\}\).  The “zero” option turns the model into a dynamic filter that can turn off features on demand while keeping a tiny memory and power bill.



## What is Absmean Quantization?

At its core, absmean quantization is nothing more than “scale‑then‑round” – but with a scaling factor that respects the overall *shape* of each weight matrix:

\[
\widetilde{W}
    = \operatorname{RoundClip}
      \!\left(
        \frac{W}{\gamma + \epsilon},\, -1,\,+1
      \right),
\]

where  

* \(W\) is an \(n\times m\) weight matrix,
* \(\gamma = \frac{1}{nm}\sum_{i,j} |W_{ij}|\) is the *average absolute value*,
* \(\epsilon\) is a tiny stabilizer (preventing division‑by‑zero),
* \(\operatorname{RoundClip}(x,a,b) = \max(a,\min(b,\;\operatorname{round}(x)))\).

In plain English:

| Step | Action | Why it matters |
|------|--------|----------------|
| **Scale** | Divide every entry by its average absolute value \(\,\gamma\). | This normalizes all weights so they lie roughly in the range \([-1,+1]\), making them easy to shrink discretely without crushing important patterns. |
| **Round** | Apply integer rounding, then clamp between \(-1\) and \(+1\). | The final result is one of three values: laser‑sharp +1, clean cycle‑breaking 0, or committing negative –1. |

The key insight is that by scaling with \(γ\) first, each layer respects its own distribution while keeping everything controlled at *one bit* plus an explicit “don’t care” slot (the zero). That extra slot transforms how the network computes.



## Why Include Zero? Dynamic Feature Filtering

If you think about matrix multiplication:
\[
Y = X W,
\]
each element in \(W\) either contributes positively (\(+1\)), negatively (\(-1\)), or not at all (\(0\)).  
Because there’s no real multiplication—everything collapses to integer additions—any entry set to \(0\) simply vanishes from the sum:

* **Zero means “skip.”**  
With modern GPUs and CPUs almost all time is spent adding or multiplying values from large tensors; dropping an entry bypasses both operations entirely.

When training proceeds under this scheme:

* The network learns which connections are *essential* and which are *redundant*.  
Current training algorithms drive many weights toward zero naturally through stochastic gradient descent and regularisation terms (like L₁ penalty).  
Thus each layer ends up acting like an **adaptive filter** – it selectively passes through signals from certain positions while blocking others.



## Put Together With Symmetric Activation Quantization

Quantizing weights is only one side of the story – activations matter too because they’re fed back into subsequent layers.  
BitNet b<sub>1.58</sub> keeps activations **8‑bit** but scales them symmetrically around zero instead of shifting them into a positive range:

```
Active value → scale → clip → map back → [-Q_b , Q_b] per token
```

Why “per token” rather than globally?  
Because token outputs can vary wildly (some words spark huge neural spikes), per‑token scaling keeps each token’s dynamic range tight while avoiding artificial offsets (“zero‑point”) that would otherwise introduce extra error.



## The Bottom Line – Simplicity Meets Performance

By handing every part of the model two choices—use or ignore—plus two polarized actions (+/- rating), BitNet b<sub>1.58</sub> collapses storage from FP16 (16 bits per parameter plus an extra bit for sign) down to just **≈ X bits** per parameter:

```text
FP16  -> 16 bits
BitNet b = 2                         -> ~2 bits for non-zero entries
BitNet b = 2 + optional zeros         -> effectively ~1.58 bits per parameter
```

The empirical proof comes from matchups against state‑of‑the‑art full‑precision models (like LLaMA). When trained from scratch on roughly 100 B tokens:

| Model Size | Perplexity Match vs FP16 |
|------------|--------------------------|
| **3B**     | Matched               |
| **3.9B**   | Outperformed FP16     |

And beyond perplexity grows further benefits:

* GPU memory consumption drops by > 70 %,
* Inference latency goes down by ≈ 2–4× depending on size,
* Energy consumed during matrix multiplications shrinks by ~70× after accounting for cheaper integer ops versus floating point ones.



## In Short

The absmean trick does something deceptively straightforward:

- Scale weights so their average absolute value becomes unity.
- Round those scaled values onto three clean discrete points.
- Keep odd zeros alive as gates that silence unneeded features automatically.

This small redefinition yields > 3‑bit saving while preserving—and even enhancing—LLM quality across tasks like ARC, Winogrande and Q/A benchmarks.


### Takeaway

Beyond nailing energy & speed gains, letting each weight decide *whether it should fire at all* turns large models into lightweight filters that retain their depth without drowning computation overheads—a clear recipe for bringing LLMs onto GPUs, CPUs and even mobile corners alike.”

# From Theory to Numbers—BitNet b¹⁵⁸ Matches Full Precision at Three Billion Parameters  

Large‑scale language models have become a double‑edged sword: their ability to master language grows dramatically when you add parameters, yet every extra megabyte increases deployment costs linearly – longer inference latency, higher GPU memory usage and larger carbon footprints all shoot straight upward.



In this post I walk through an empirical milestone proved by **BitNet b¹⁵⁸** – a transformer that stores every weight as one of three possible signs \(\{-1,\!0,\!+1\}\) instead of a floating‑point value – and demonstrate how once the model reaches roughly **3 billion parameters** it performs exactly on par with its full‑precision counterpart while consuming far less compute.



---------------------------------------------------------------------



## Why Low‑bit Training Is Needed  
Post‑training quantisation techniques batch existing models down to four or even two bits per weight *after* they have already been trained in full float16 precision. Because they never change the optimisation dynamics halfway through training, those methods often lose a few percentage points on downstream benchmarks.



By contrast **BitNet** trains directly in a low‑bit regime ([Balon et al., 2024]). All operations during learning take place already over finely carved integer ranges so no runtime penalty is paid when switching back–and–forth between training and inference.



---------------------------------------------------------------------



## How BitNet b¹⁵⁸ Works  
| Component | What It Does | Why It Matters |
|-----------|--------------|----------------|
| **Ternary weights** |\(\{-১,\!0,\!+১\}\)| Gives each weight an effective log₂(₃) ≈ **1·58 bits** – drawing a line between pure binary models and classic half‑precision nets |
| **AbsMean QUANT**<br>\(\tilde W=\mathrm{RoundClip}\!\bigl(\frac{W}{\gamma+\epsilon},\,{-１},\,+１\bigr)\)<br>\(\gamma=\frac{1}{nm}\sum_{i,j}|W_{ij}|\)<br>\(\mathrm{RoundClip}(x,a,b)=\max(a,\min(b,\mathrm{round}(x)))\)| Normalises then forces every real weight into one of the three discrete levels without exploding gradients |
| **8‑bit activations** | Scaled per-token into \([-8,+8]\) rather than higher precision | Keeps nonlinear paths lightweight while maintaining enough dynamic range |
| **LLaMA-alike backbone** | RMSNorm ≤ SwiGLU ↦ Rotary pos enc | Matching community standards means any HuggingFace pipeline sits straight‐in or runs under llama.cpp without extra wrappers |

Because all matrix multiplications become pure INT8 additions (no costly floating‑point multiply), inference curves collapse sharply both in execution time *and* energy consumption.

# Speed Meets Efficiency—How BitNet Cuts Latency & Memory by Over Threefold

Large language models are now better than ever at understanding text – yet their growing size brings new bottlenecks into play:
high GPU memory footprints,
slow inference,
and steep power costs.
Inside this wall‑of‑performance problem sits one simple insight:
if every weight of a transformer was reduced from a traditional *f32/fp16* float down to a handful of possible symbols,
the whole computation pipeline could collapse onto clean integer arithmetic.
This idea underpins **BitNet b¹·⁵⁸**, an entirely *ternary* language model that keeps the same accuracy as full‑precision baselines while slashing latency and RAM usage more than three times.



--------------------------------------------------------------------

## Why Size Matters

When users request a short sentence from an LLM,
the decoder must generate *every token* word‑by‑word.
The core operation is a massive matrix multiplication:
for each attention head we compute
\[
\mathbf{z} = \mathbf{w}\mathbf{x}, \qquad 
\mathbf{w}\in\mathbb{R}^{k\times k},
\]
with \(\mathbf{w}\) being thousands wide and thinned across many heads.
A transformer with \(N\) parameters typically consumes \(N\times16\) bits
in standard FP16 mode – roughly eight bytes per scalar –
and each inference step copies these numbers from DRAM into fast SRAM,
multiplies them against activations,
and writes results back out again.


The vanilla approach hands the GPU several gigabytes of data each time it runs a single forward pass.
It also relies heavily on floating‑point multipliers that consume more power than adders,
which limits how many machines can fit concurrently on chip or how high their clock rates can run.


--------------------------------------------------------------------

## Meet BitNet b¹·⁵⁸

BitNet b¹·⁵⁸ revamps this foundation in two tight ways:

| Item | Conventional | BitNet b¹·⁵⁸ |
|------|--------------|--------------|
| **Weight alphabet** | {−∞,…,+∞} (FP16) | {−1, 0, +1} |
| **Per‑parameter bits** | \(16\) | \( \log_2(3)\approx1.58 \) |
| **Activations** | FP32 → optional INT8 | INT8 range \( [-Q_b,Q_b] \) |
| **Core ops** | Multiply + Add | Add / Subtract / Zero logic |

### Ternary Weights & Tiny Activations

Every scalar weight is forced into one of three discrete values via *AbsMean* quantisation:
treat the current weight tensor \(W\), scale it by its average absolute value

\[
\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|,
\]

then round it within \([-\,1,+\,1]\).

The resulting tensor has entries ∈ {−1, 0,+1};
this yields an **effective** per‑parameter storage requirement of about \(19/12≈\( ti.e.\!\!~6\)) bytes compared with freshly‐floating point versions.


Activations are clipped into an eight‑bit symmetric range so that every decoder step operates purely on integers.
No floating point hardware is invoked during inference:



> *Integer‑only matrix multiplications feature essentially no generic multipliers; they turn into simple add/subtract controlling signals.*


That alone *shrinks* compute instruction count significantly—with massive benefits when implemented on modern GPUs or dedicated accelerators.



### Bypassing Multiplications

Thanks to ternary weights:

* If \(w_{ij}=+\,1\), contribution = the activation itself;
* If \(w_{ij}=−\,1\), contribution = minus the activation;
* If \(w_{ij}=0\), contribution = nothing added (“feature filtering”).

Thus each dot product becomes
a sequence of selective sign flips + erasures,
all handled by virtually free accumulator logic rather than costly MAC units.



--------------------------------------------------------------------

# Powering AI With Less Energy—BitNet’s Arithmetic Saves Up To Seventy‑Times

Large language models (LLMs) have become the de‑facto backbone for virtually every text‑centric AI service today. While their performance keeps improving with each new release, their compute and power footprints also balloon at an alarming rate—even a single inference can cost significant electricity, carbon and hardware resources.  
The recent work on **BitNet b1.58** shows that it is possible to maintain competitive quality while collapsing that cost envelope by almost an order of magnitude through a very simple change in the math inside the Transformer blocks.



--------------------------------------------------------------------

## Why is inference usually expensive?

A Transformer inference step is dominated by a cascade of linear layers (`nn.Linear`).  
Mathematically each linear layer maps an input vector **x** ∈ ℝ^n to an output **y** = W x + b where W ∈ ℝ^{m×n}.  
Each matrix‑vector multiplication involves *n* multiply‑add operations – every multiply is usually performed in floating point (FP32 or FP16).  
On modern GPUs or CPUs the “multiply‑add” operation consumes more power than an addition and occupies far more silicon area.



--------------------------------------------------------------------

## What BitNet does differently

| Conventional LLM | BitNet b1.58 |
|------------------|-------------|
| Weights are FP16 / BF16 | Weights are *ternary*: \{-1, 0, +1\} (≈ 1.58 bits each) |
| Activations often FP16 or higher | Activations become fixed‑point INT8 |
| Uses `nn.Linear` written in generic C++/CUDA | Uses a custom `BitLinear` that never multiplies |
| Has full precision biases everywhere | Biases removed entirely – they add little ‑M |

Because every weight is only \{-1, 0, +1\}, multiplying an activation by a weight collapses into *either drop it (×0), keep it (×+1), or invert it (×−1).*  
All that remains are integer additions or subtractions – simple bit‑shift operations on cache‑friendly integers.



--------------------------------------------------------------------

## The quantisation recipe

To keep the ternary set without sacrificing expressiveness the authors use what they call **absmean quantisation**:

```text
γ   = mean(|W_ij|)
Ŵ_ij = round_clip( W_ij / (γ + ε), -1 , +1 )
```

`γ` rescales the column so that most values fall inside \{-0.5…+0.5\} before rounding.
With this small scaling factor the distribution of weights stays centred at zero,
which preserves the signal flow necessary for a high capacity network.



--------------------------------------------------------------------

## Energy savings in practice

> **Figure 3 (conceptual)** in the paper shows a breakdown of the arithmetic power draw per operation against a typical 7 nm GPU chip model.
> For every dot product inside a transformer block:
> 
> * An FP16 network spends roughly \(P_{\text{FM}}\) joules per FMA step.
> * A BitNet b1.58 network spends roughly \(P_{\text{INT}}\) joules per INT addition,
>   which is about \(\frac{P_{\text{FM}}}{71}\).

That turns into almost **70× reduction** in arithmetic‑energy consumption *just* for the matrix multiplications that dominate inference time.
Because most transformer workload now lives in those linear layers,
the overall battery life or datacenter CO₂ output per token improves by roughly *one order of magnitude*.



--------------------------------------------------------------------

## Performance parity comes at no loss

The authors trained **BitNet b1.58** from scratch on 100 B tokens using a RoPE‑enabled,
SwiGLU architecture identical to open‑source LLaMA models.
With identical token budgets:

| Size | Metric | FP16 baseline | BitNet b1.58 |
|------|--------|---------------|--------------|
| 3B   | Perplexity | ~25 | ~25 – matches fully|
| 3B   | Zero‑shot accuracy (average over ARC·Easy / ARC·Challenge / Hellaswag / …) | – | – |
| 3․9B | Latency per token | – | **2× faster** |
| 3․9B | GPU memory | – | **~3× smaller** |

And as size grows further (7B → 70B), speedups rise from ≈2× to >4× while memory demands fall proportionally.



--------------------------------------------------------------------

## Scaling law unlocked by “cheap” arithmetic

Because each linear layer costs almost nothing,
the effective *cost* of adding more layers shrinks dramatically:
* 13BBitNet ≈ performance‑efficient version of a 3B FP16 model
* 30BBitNet ≈ efficient counterpart to a 7B FP16 model
* …and so on up to seventy billion parameters with only ≈4× latency overhead compared to its FP16 sibling.



--------------------------------------------------------------------

## Why this matters beyond counting FLOPs

* **Hardware:** The low precision means specialized low-power ASICs can be written that target INT8 addition kernels rather than heavy SPU pipelining required by FP32/FP16.
* **Enterprise:** Massive saving in data‑center wattage translates directly into cost reductions; even small bursts like generating document summaries become cheaper.
* **Mobile & Edge:** A single mobile SoC could run a multi‑billion parameter LLM locally – previously impossible with standard floating point thanks purely to reduced memory bandwidth.
* **MoE & Long Sequences:** Compressing the KV cache from 16‑bit to 8‑bit doubles usable context length without extra compute budgets – another “energy” win.



--------------------------------------------------------------------

## Takeaway

BitNet b1.58 demonstrates that the key bottleneck in LLM inference isn’t just raw FLOPs—it’s *floating point math itself*.  
By restricting weights to \{-1,0,+1\} and using fixed‑point activations,
every matrix multiply collapses into fast integer additions that die off quickly in power budgets.
The result? Near‐seventy‑fold reductions in arithmetic energy while preserving full task performance—and all this without requiring exotic training techniques or hand‐tuned compression hacks.



When deploying next-generation language models,
thinking about how you *compute* inside your networks becomes as important as improving what you learn from data.

# Beyond Business Value—What’s Next for One‑Bit LLMs  

Large Language Models have become indispensable tools for everything from question answering to automated writing assistants—yet their silicon bill keeps climbing even faster than their capabilities grow.  
A growing body of research now shows that *one‑bit*—or even *ternary*—weights can preserve almost all performance while slashing compute costs dramatically.  
The most recent milestone comes from **BitNet b¹·⁵⁸**, an architecture where every parameter takes one of three values \<− 1, 0, + 1\>. It achieves perplexity comparable to a full‑precision FP16 model **starting at only three billion parameters** while delivering its outputs twice as fast on GPUs and using roughly one‑third as much VRAM.



-----------------------------------------------------------------------

## How one‑bit came into mainstream attention  

Traditional LLMs store their weights in floating point format (FP32/FP16).  
Because every transformer layer relies almost entirely on matrix multiplications, the average bandwidth demand comes largely from moving dense tensors into DRAM/SRAM and executing many expensive *floating‑point multiply–add* pairs.



### Why ternary works  

A single weight now lives in a tiny three‑state set `{− 1, 0, + 1}` (“ternary”).  
During inference it behaves like an *int8 addition* operator over very sparse matrices—no multipliers are required except when both operands are non‑zero—and fits perfectly into standard integer units found on GPUs, CPUs and custom ASICs.



### From “BitNet” → “BitNet b¹·⁵⁸”  

* **Quantisation** – Every weight `W` undergoes an *average‑absolute* normaliser (`γ`) followed by rounding and clipping:
  
```latex
\widetilde{W}=   
   \operatorname{RoundClip}\!\Bigl(\frac{W}{\,γ+ε\,}, -\,|\,,+|\,\\Bigl),
where 
   γ=\frac{1}{nm}\sum_{ij} |W_{ij}|.
```

* **Activations** – Remain eight‑bit integers (`INT8`) instead of `FP16`.  
No extra offset (“zero‑point”) handling is needed thanks to symmetrical scaling across tokens.



### Tenets borrowed from popular open‑source models  

The blockstack mirrors an LLaMA backbone — RMSNorm instead of LayerNorm, SwiGLU activation mixer, rotary embeddings—and drops any learnable biases entirely—all purely integer operations.



-----------------------------------------------------------------------

## Evidence that performance stays intact  

| Model Size | Perplexity / Accuracy | Speed advantage | Memory overlap |
|------------|-----------------------|-----------------|----------------|
| **3 B**    | Matches FP16 whisper mark | **2·70×** faster | **3·55×** less VRAM |
| **3․9 B**  | Surpasses full‑precision counterpart | **2·40×** speedup | **3·32×** less VRAM |

> These figures come directly from head-to-head experiments on RedPajama’s \(10^{11}\) token pretrain regime followed by zero-shot evaluation over ARC-Easy/Challenge,\ Helm Graves context tasks (\(Winogrand/EQA/PIQA/OpenBook/BoolQ)).  
> The reported gains persist even when moving up Δ multiple tokens — BitNet b¹·⁵⁸ trained over *two trillion tokens* outperformed its well-known full‑precision cousin on every metric measured.



-----------------------------------------------------------------------

## Where do these savings translate into real opportunities?

### Mixture‑of‑Experts becomes physically feasible

MoE layers replace all-but-a-slice matrices with conditional experts spinning off “fast kernels.”  
Historically MoE has been *memory hungry* – hundreds of billions terabytes spilled across dozens or hundreds of GPUs—due precisely to classical floating point tensors moving off chip during gating steps.

Because *every parameter counts fewer bits*, the data footprint shrinks → fewer inter‑chip transfers → a single TPU‑like device can host thousands more experts whereas before they'd have lived split over many chips.



### Truly longer context windows

Presentation versus inference spectra both dominated now by KV cache sizes written back into DRAM/SRAM per generated token (≈ 48 k × sequence length bytes @ FP32).

With `INT8` activations Tile width doubles without a change in compute load – you get **74 tokens -> ≈ 148 tokens** simply because every word needs only one byte instead of two (or four).  
Pools furthermore hint toward still deeper compression down toward quaternary bits (`Q4`), enabling yet larger contexts without modifying current accelerator pipelines.



### Edge & mobile friendliness

Traditional mobile AI accelerators target sub‑gigabyte footprints while polling simultaneously background OS processes + deep learning inference simultaneously—a daunting combination when using quartierish parameter storage (~160 GB per DL multi-modal kernel).

* One‐bit cores embarrass themselves comfortably under designated CPU gears (`TMUL` isn’t required).
* The sheer paucity (*≈ 300 MB*) lets an entire fine‐tuned GPT-like policy fit comfortably into mobile SoC caches plus DRAM which normally satellites wallet fill only once during startup.


### Dedicated ASIC dreams materialise immediately

If you look past perhaps millisecond-level accelerator forces behind training some transformer matrix multiplication engine boasting horizons <10 million FLOPs/s/Watt—then crafting silicon specialized toward integer pass‐through circuitry alone provides up-close match elimination benefits traditionally beloved only in data science clouds:
* Eliminated multipliers altogether—masterfully cheap `ADD` NAND/OR gates.
* SRAM arrays optimized specifically around sparse ternaries give both gigantic hit rates & data density.
* Off‐chip I/O bandwidth becomes largely irrelevant once embedding outputs shrink dramatically.


> The Oracle team behind Groq recently released an LPUs framework tailored around activation packing—that's already proof-of-concept stage under industrial lens—and builds precisely what this line does electrically.
