# Speed Meets Efficiency—How BitNet Cuts Latency & Memory by Over Threefold

Large language models are now better than ever at understanding text – yet their growing size brings new bottlenecks into play:
high GPU memory footprints,
slow inference,
and steep power costs.
Inside this wall‑of‑performance problem sits one simple insight:
if every weight of a transformer was reduced from a traditional *f32/fp16* float down to a handful of possible symbols,
the whole computation pipeline could collapse onto clean integer arithmetic.
This idea underpins **BitNet b¹·⁵⁸**, an entirely *ternary* language model that keeps the same accuracy as full‑precision baselines while slashing latency and RAM usage more than three times.



--------------------------------------------------------------------

## Why Size Matters

When users request a short sentence from an LLM,
the decoder must generate *every token* word‑by‑word.
The core operation is a massive matrix multiplication:
for each attention head we compute
\[
\mathbf{z} = \mathbf{w}\mathbf{x}, \qquad 
\mathbf{w}\in\mathbb{R}^{k\times k},
\]
with \(\mathbf{w}\) being thousands wide and thinned across many heads.
A transformer with \(N\) parameters typically consumes \(N\times16\) bits
in standard FP16 mode – roughly eight bytes per scalar –
and each inference step copies these numbers from DRAM into fast SRAM,
multiplies them against activations,
and writes results back out again.


The vanilla approach hands the GPU several gigabytes of data each time it runs a single forward pass.
It also relies heavily on floating‑point multipliers that consume more power than adders,
which limits how many machines can fit concurrently on chip or how high their clock rates can run.


--------------------------------------------------------------------

## Meet BitNet b¹·⁵⁸

BitNet b¹·⁵⁸ revamps this foundation in two tight ways:

| Item | Conventional | BitNet b¹·⁵⁸ |
|------|--------------|--------------|
| **Weight alphabet** | {−∞,…,+∞} (FP16) | {−1, 0, +1} |
| **Per‑parameter bits** | \(16\) | \( \log_2(3)\approx1.58 \) |
| **Activations** | FP32 → optional INT8 | INT8 range \( [-Q_b,Q_b] \) |
| **Core ops** | Multiply + Add | Add / Subtract / Zero logic |

### Ternary Weights & Tiny Activations

Every scalar weight is forced into one of three discrete values via *AbsMean* quantisation:
treat the current weight tensor \(W\), scale it by its average absolute value

\[
\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|,
\]

then round it within \([-\,1,+\,1]\).

The resulting tensor has entries ∈ {−1, 0,+1};
this yields an **effective** per‑parameter storage requirement of about \(19/12≈\( ti.e.\!\!~6\)) bytes compared with freshly‐floating point versions.


Activations are clipped into an eight‑bit symmetric range so that every decoder step operates purely on integers.
No floating point hardware is invoked during inference:



> *Integer‑only matrix multiplications feature essentially no generic multipliers; they turn into simple add/subtract controlling signals.*


That alone *shrinks* compute instruction count significantly—with massive benefits when implemented on modern GPUs or dedicated accelerators.



### Bypassing Multiplications

Thanks to ternary weights:

* If \(w_{ij}=+\,1\), contribution = the activation itself;
* If \(w_{ij}=−\,1\), contribution = minus the activation;
* If \(w_{ij}=0\), contribution = nothing added (“feature filtering”).

Thus each dot product becomes
a sequence of selective sign flips + erasures,
all handled by virtually free accumulator logic rather than costly MAC units.

## Benchmarks That Speak Volumes

The authors ran full experiments against a carefully reproduced BFloat16 `LLaMA` baseline
on **RedPajama** pretraining data (100 B tokens),
evaluating perplexity on `WikiText2` + `C4`,
and standard zero‑shot accuracy tests across five public benchmark suites
(`ARC`, `HellaSwag`, `Winogrande`, `PIQA`, `OpenbookQA`, `BoolQ`).

> ### Model Size vs Perplexity  
> At **3 B parameters**, `BitNet b¹·⁵⁸` matches the full‑precision baseline’s perplexity exactly.
> The match occurs already at this relatively low model scope,
> proving that optimizing both weights *and* architecture can preserve performance.



#### Latency & Memory Footprint

When measured with NVIDIA’s FasterTransformer plus a custom two‑bit kernel from Ladder,

| Size | Full‑precision (FP16 LLaMA) | BitNet b¹·⁵⁸ |
|------|-----------------------------|--------------|
| **3 B** | Baseline latency ≈ 240 ms/GPU token<br>Memory ≈ 12 GB | Latency ≈ 88 ms – **2.71× faster**<br>Memory ≈ 3.37 GB – **3.55× smaller** |
| **3‑9 B** | Latency ≈ 270–310 ms | Latency ≈ 110–120 ms – **≈ 2¼× improvement** |
| **70‑B** | Latency ≈ 1200 ms | Latency ≈ 300 ms – **4․¹× speedup** |

These numbers translate roughly into *dozens* versus *hundreds* of milliseconds saved per token generation –
a tangible difference for real‑time chat services.



#### Energy Consumption

By focusing on arithmetic‐only learning units,
the paper estimates that reducing from FP16 multiply–add pairs
to INT8 addition alone cuts raw operation energy by nearly two orders of magnitude:

```
77%   : Energy used considering MPUs + multipliers      →   Full precision
71%   : Energy used considering only INT8 adders       →   BitNet b¹·⁵⁸ because no multiplier needed
```

On a state-of-the-art silicon process (7 nm),
this translates into a staggering **~70x reduction** in power draw for matrix multiplication parts.



#### Throughput Gains

Running both models on dual A100 GPUs via pipeline parallelism illuminates how RAM savings compound under heavy workloads:

```
70-B full precision : max batch size ≈ 8   → throughput ≈ 130 requests/s
70-B BitNet b¹·⁵⁸   : max batch size ≈ 110 → throughput ≈ 1165 requests/s   ≈ 9× higher!
```

Because high–value weights eat most DRAM bandwidth,
reducing their bit width directly frees columns for more concurrent requests.

## Scaling Up Isn’t The Problem – It Bolsters Benefits

The study went beyond “proximate” small models;
scaling toward ultra‑large space (\>13B–70B)
demonstrated that speedups *grow* alongside model size –
a result traced back mainly to larger percentages spent inside linear layers,
which shrink dramatically when weights are only ternary.



For instance,

```text
13-B BitNet      > (<---_)
         LATENCY     ; MEMUSE ever more efficient than FULL-PRECISION version ↑30% faster than any K<13-B FULL-PRECISION counterpart
30-B BitNet      > (<---_) <-- near equivalent notes here …
70-B BitNet      > (<---_) // same ratio holds true…   
```

If you read this as “a very large model needs fewer multipliers,” you’ve just caught<|reserved_200788|> magic 🎩

## Training With Gigantic Token Budgets

Beyond inference advantages,
the authors pushed the model through $20\times$ more data (`StableLM` recipe – over $10^{12}$ tokens).
On capped test suites (`Winogrande`, `PIQA`, `SciQ`, etc.) 
BitNet performed *better outright* than its FP16 partner despite its starkly pared-down precision –
indicating ultra‑low‐precision networks can still extrapolate well beyond their training distribution.

## What This Signifies For Practitioners

| Domain               | Opportunity                                                     |
|----------------------|------------------------------------------------------------------|
| Edge / Mobile        | slimmer device demands → nonstop voice assistants / always‐on apps |
| MoE Architectures    | smaller expert blocks mean fewer cross‑chip exchanges            |
| Long Sequence Enablement | `<Qb>=8` int activations shrink KV cache => handle larger contexts without switching hardware |
| Dedicated Hardware   | Very few multiplier gates → LPUs or custom “OneBit” units can scale massively |

Ultimately next‑generation LLM servers could run dozens more parallel queries per chip,
handily cut electricity bills,
and remain economically viable even with everyday consumer GPUs.

## Final Takeaway

BitNet b¹·⁵⁸ demonstrates that you do not need fancy rounding tricks or massive neural ensembles—
you just need *clean integers*.    
Its simple ternary encoding delivers:
* ‑over threefold memory savings;
* ‑by factors up around four in latency;
* ‑two hundredfold reductions in arithmetic power usage;
* ‑almost tenfold better throughput upon scaling up late-stage devices;

All while maintaining competitive perplexity and zero‑shot accuracy on mainstream datasets.
