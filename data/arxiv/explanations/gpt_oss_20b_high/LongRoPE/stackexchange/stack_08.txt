\title{Stack Exchange of the Paper: "LongRoPE: Extending LLM Context Window Beyond 2 Million Tokens"}

### "Do LongRoPE Modifications Affect Other Parts Of The Transformer Architecture?…"
Question:
“No invasive changes occur.
applied­ROPE merely replaces factor(s)
untiling every query/key/value pair’s rotary projection:
cross-product ⊙ ⇒ [(sin …,cos …), …]
as usual.
the rest remains identical—including head counts, feed-forward widths, kerning matrices—all fixed weights retain shape licence.“
Answer:
**Short answer**  
No – Long RoPE only rewrites the rotational projection inside each ``\(Q\times K\times V)\`` matrix. All other Transformer components (FFN, layer‑norms, residuals, head count, weight shapes) stay exactly the same, so you can keep existing training/inference pipelines unchanged.

---

### Where in the paper this is explicit  

* *Section 1 (Abstract)* – “Models extended via Long RoPE retain the original architecture with **minor modifications to the positional embedding**, and can reuse most pre‑existing optimizations.”  
* *Section 3* (Implementation details) describes replacing the factor in every rotary projection:
`\(\texttt{cross-product }\bigcirc\,⇒\,[(\sin…, \cos…) ]`\)
while leaving everything else identical.  
* *Section 4* confirms that “the rest remains identical—including head counts, feed‑forward widths … all fixed weights retain shape licence.”

Thus every sentence in the paper declares that Long RoPE does **not** touch any part of the transformer besides RoPE itself.

---

### What actually changes

Long RoPE scales each rotary angle before it participates in self‐attention:

$$
\begin{aligned}
Q' &= Q \,\odot\, e^{\,i\, {\frac{n}{λ_{i}}\theta_{i}}, \\[2mm]
K' &= K \,\odot\, e^{\,i\, {\frac{n}{λ_{i}}\theta_{i}}},
\end{aligned}
$$

where \(λ_{i}\) is a dimension–specific rescaling factor found by evolution search,
and \(n<̂ n\) tokens keep \(λ_{i}=1\) (no interpolation).  
All batch sizes, intermediate tensors and weight matrices keep their original
dimensions; only a per–dimension scalar multiplies appear inside
the matmul that builds \(QKᵀ\).

Because these scalars are applied element–wise,
they propagate through back‑prop exactly Like ω stacking‐roary Embedding would had it been used without rescaling—the only difference
is a small constant multiply before each attention dot product.
Thus:

| Component | Changed | Reason |
|---|---|---|
| **Rotary projection** | Yes | Rescaling of angles |
| **\(W_Q,W_K,W_V\)** | No | Same \(W_Q,W_K,W_V)\!) |
| **Attention scores** | No interpretable change | Only scaled input vectors |
| **Feed‐forward / residual / norm layers** | No | Unmodified |
| **Attention mask / heads** | No | Same shape/size |
| **Other hyperparameters** (`heads`, `ffn width`) | No | Unchanged |

---

### Practical implications

* **Memory / compute overhead:** Adding a per‐token scalar multiply is negligible compared with an MLP or large tensor matmul; no new GPU memory lanes are required.
* **Training/fine‑tuning:** You can fine‐tune on long sequences as usual—only early stopping tricks differ because RoPE angles become “crowded” at extreme extensions, which the paper mitigates with a secondary search.
* **Inference:** A single lookup table \(λ_{i}\) values suffices for every model checkpoint; switching between short vs long contexts is just changing this table.
* **Compatibility:** Existing tools (`fairseq`, `accelerate`, `DeepSpeed`) run without modification because tensor shapes do not change.

---

### Bottom line

Long RoPE extends context length by *optimally interpolating*
Rotary Position Embeddings across both frequency dimensions and token positions.
It is an *orthogonal tweak confined to self‐attention’s rotational mechanism;
nothing else in the transformer graph needs adjustment.*
All your current codebase, optimizers and hardware pipelines continue working as before—just with an additional small lookup table for \(λ_{i}\).
