\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### What exactly do the "rules" produced by FeatLLM look like?
Question:
The paper talks about the large language model generating "rules" that capture conditions for each class and then converting them into new binary features. I'm not sure whether these rules are logical expressions such as `if age > 50` or more complex text snippets involving several conditions connected by AND/OR clauses.

Could you give an example of a typical rule output from GPT‑3.5 used in FeatLLM, including its format and how it maps onto code that creates a single binary feature?
Answer:
Below follows the **original content**, modified only where mathematical notation was repaired so it renders correctly‑formatted LaTeX‑style maths.).

---

**Short‑answer**  

The “rules” that FeatLLM asks GPT‑3․5 to produce are *single logical expressions*—one line per command—written right‑after a header that names the class label (`Yes`, `No`, …). Each expression uses only  

* numerical comparisons (`<,$<$`, `$\\le$`, `${=}i?$=`???...),  

* categorical equality (`${=} "\"some category\""`),  

* conjunctions (`and`) and disjunctions (`or`)  

and refers directly to the original column names supplied in the prompt so that the model cannot accidentally mix datatype meanings.



When those text snippets have been printed out you get something very close to plain mathematical predicates such as  

```text
Class Yes:
[1] age     $\ge$ 51                # single predicate  
[2] glucose $\le$ 125 OR insulin $\ge$ 140         # two predicates joined by OR  
[3] bmi     $\ge$ 30 AND trigsle $\le$ 140          # two predicates joined by AND  

Class No:
[1] age      <$>$ (= ??-->?) ??                  
[_ note_: While non‑numeric comparisons stay untouched,_ i.e.,
           `syst_bp = \"high\"`,
           `hiv_test = \"negative\"" ] / ...
```



---  


### How FeatLMM turns those strings into usable Boolean features

**Step&nbsp;1 – Cleaning / standardisation**

A second prompt sent back to GPT‑3․5 asks it only for *Python* evaluation logic corresponding to each sentence above **without** any natural‑language fluff. The model typically emits trivial helper functions such as  

```python
def _rule_YES_01(x):
    # x is a dict or pandas series referring to one sample row    
    return x['age'] >= 51

def _rule_YES_02(x):
    return x['glucose'] <= 125 or x['insulin'] >= 140

def _rule_NO_01(x):
    return x['age'] < 30 or x['syst_bp'] == "high"
...
```

Those helper functions are wrapped together inside another tiny wrapper module that accepts an entire dataframe/array (`df`). Calling this wrapper produces a Boolean matrix  

\[ Z \in \\{\{\,0\, ,\,1\\}\}^{\,N\\times R}\],

where \(N\) is the number of samples and \(R\) equals “number \<emph>of classes × number\<emph>of enabled rules”.   
Each column keeps its unique identifier (\(YES_{01}, YES_{02},⋯)\)—guaranteeing reproducibility even when bagging is applied later—the order stays fixed because it follows precisely how many numbered clauses appeared under each header during prompting.



---

### Weight learning

Using these binary columns as inputs,
FeatLMM trains a very small linear classifier without bias whose weights
\(w_k\\in\\mathbb R^R ≔ \\mathbb R^\,R\\).

For every sample \(i\),
the logit for class \(k\) is simply  

\[ 
        {\color{blue}{w_k^\!*}}\,{\color{blue}{z_k^{(i)}}},
        \qquad
        z_k^{(i)}=\mbox{\bf all Boolean values belonging exclusively}
                   {\mbox{\bfto}} {\color{blue}{x}} ,
        
]
with ${w_k^\!*}=\\max(w_k,\!LP)$ denoting truncation onto
non​\-negative values.
The softmax over these logits gives ${p^{(i)}}$, which is optimised against cross‐entropy loss over the few-shot training set.



---

### Ensemble / bagging

Because every trial draws a fresh random subset of few-shot samples (or even randomises their order),
slightly different clauses get generated each time.
Repeating steps&nbsp;«​１–２» gives several distinct weight vectors
\(w_{k}^{(t)};\)\,
predictions finally average over all trials,

\[ p_k^{(i)}
=\frac{
        {\displaystyle∑}_{t=১}
        {\displaystyle exp(\operatorname {logit}_k^{\,t}) }
    }{
        {\displaystyle∑}_{j}
        {\displaystyle exp(\operatorname {logit}_j^{\,t}) }\;
        }
      ,
]
so mis‐generated clauses are naturally drowned out while useful ones survive,
building an otherwise almost-zero-cost inference pipeline.



---

### Takeaway

A FeatLMM “rule” looks nothing exotic—it’s a succinct Boole­an statement written once per line under a headline identifying which target label it concerns.
These plain statements get fed back into another quick round where GPT turns them into tiny Python predicates operating elementwise over incoming data rows;
every predicate becomes its own binary feature fed into an inexpensive linear model whose learned weights decide how influential each clause really is.



Because everything from phrase generation → parsing → Boolean conversion happens only once before deployment—and during deployment one merely multiplies pre­computed booleans against stored positive weights—the framework stays lightning fast while still leveraging knowledge‐rich reasoning afforded by GPT‑3․5 at training time.
