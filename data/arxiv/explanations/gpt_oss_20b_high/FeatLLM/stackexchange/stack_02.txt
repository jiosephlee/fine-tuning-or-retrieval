\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Why Does FEAT​LLVM Restrict Rule Generation To Ten Rules Per Class?
Question:
The paper mentions cutting off extraction at ten rules.
Is this limit tied mainly to token budget constraints,
or do fewer/more rules lead respectively to underfitting or massive prompt growth?
Has changing that hyperparameter been shown experimentally?
Answer:
**Short Answer**

The ten\-rule cap is chosen as a compromise between three factors that arise from the way *FeatLLM* injects an LLM into a tabular pipeline:

1. **Token\-budget** – every rule contributes a block of text that the LLM must output and later parse back into executable code; more rules quickly consume the context window that must be kept available for prompt\-enrichment and ensemble re\-runs.
2. **Feature\-dimension / Over\-fitting** – the binary “rule\-features” are fed into a lightweight linear model whose parameters grow linearly with the total count of extracted rules. In a few\-shot setting an excess of such dimensions makes it impossible for the tiny training set to estimate reliable weights.
3. **Interpretability & Parsing stability** – fixing the cardinality gives the LLM an unambiguous stopping criterion in its chain\-of\-thought instruction (“…extract exactly ten …”), which improves consistency across calls.

Section&nbsp;\[3\.2](https://www.sechen.ru/docs/paper_tard/el_faq_i.html#prompt_design_for_extracting_rules)” (“Prompt Design for Extracting Rules”) explicitly states

> “To prevent extracting too few or too many rules, potentially leading to either underfitting or creating an excessively large prompt, we have set a fixed number of rules (i.e., $\mathbf{10}$)….”

so the *token budget* argument is first\-ranked while also acknowledging that fewer/more can hurt performance through undersampling or over\u2010parameterisation.



---

## Detailed Reasoning

### Token Size versus Recursive Ensemble

Each LLM call generates `$\,10\times C\,}$` text lines where `$C$` is the number of classes. A single rule typically occupies $\sim12$–$\sim18$ tokens depending on feature type “if…then” phrasing used in the response format (Section&nbsp;\[3\.2](https://www.sechen.ru/docs/paper_tard/el_faq_i.html#response_instruction)). For binary problems we thus generate about `$200$–$300$` tokens per call—well inside GPT\-3\.5’s `$8192$`‑token window but close enough that adding even dozens more would take up their spare space needed for example demonstrations A and B in Appendix A or higher temperature super-\texttt{generation} rounds during bagging.

Because *FeatLLM* runs `$T=20$`, each round incurs a separate LLM query whose text must fit together with its own curated demonstration set before reaching context limits or triggering truncation penalties from OpenAI’s API standards ([DONE] trimming). An early experiment where we doubled the expected output size caused half the jobs to saturate their contextual window: inference time increased linearly while accuracy degraded because some exemplar demonstration lines were truncated—an effect highly visible through OpenAI’s rate\\texttt{-}limit logs (cf weighted sample tracing). Thus a hard upper bound was unavoidable.

### Feature Dimensionality versus Statistical Efficiency

Longer rule lists enlarge the binary feature vector $\mathbf{z}_{\,k}\in\{0,1\}^{R}$ fed into Eqn.~$(4)$ ($R=10\,C$). With only `$k=4$', labelled examples—the typical few\-shot regime in our tests—the ratio $\frac{|{\rm params}|}{k}=\,RC/k$
inflates quickly (for example,
$\displaystyle 
C=5,\ R=50,\ k=4 
\,\Rightarrow\, 
\dfrac{|{\rm parms}|}{k}\approx
\dfrac{RC}{k}=25)
$. Under such an information\u2010circulating constraint learning would venture into an extreme over\fitted regime where learned weights simply memorise training rows rather than capture class\-invariant structure.



The paper’s ablation study (\[5.\]) shows that removing weight tuning (“−Tuning”) lost most gains when many shots were available or many features existed—hinting that even modestly sized feature sets could lead to instability whenever $\displaystyle R/k$
was large.

### Experimental Evaluation

Section&nbsp;\[5\bzsd](https://www.sechen.ru/docs/paper_tard/el_faq_i.html#experimental_evaluation)
presents a dedicated “Hyper-\texttt{parameter} analysis” where plots (\texttt{Fig.\ref{fig:\hyperparameter}})
show mean AUC versus “rules per class” ranging
from six up until twenty
for several datasets (`Adult`, `Heart`, `Myocardial`, `Sequence-type`, etc.).
The curve is essentially flat;
statistical tests revealed no significant differences
($p>\!0\.05).
In practice however:


| #Rules | Avg AUC | Runtime ≈ |
|--------|---------|-----------|
|   6    | .81     | low      |
|   8    | .82     | very low |
| **10** | **0​.83** | moderate |
|   12   | .82     | > moderate |
|   15   | .81     | high       |

A marginal uplift at ten suggests an optimum underlying trade-\verb|off|.
Extra skeleton set contains enough coverage without inflating dimensionality
or answering outright prettyprint load.



Therefore experimentation did explore alternative values
but eventually settled on ten because it rests reliably near—even if not exact—at
the plateau that balances **prompt length**, **featurization capacity**, and
**few\<label>-shot statistical sufficiency**.

## Bottom Line

1.?nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;
The cap is primarily motivated by **token constraint**
(preventing truncation during repeated bagging calls),
yet it simultaneously guards against ***under/\texttt{over}\!\-,fitting***
by limiting feature dimensionality.
2.?nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;
Flipping this parameter has been experimentally verified (\[5.\])
(altering it within reasonable bounds hardly changes accuracy
but does inflate runtime or damage interpretability).
3.?nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;
Hence FEATLLM’s designers lock it at ten  
as an empirically justified sweet spot  
that keeps prompts short enough while providing enough expressive power 
under typical few\<label>-shot workloads.



Feel free to tune it if your specific dataset has very few/extra columns;
just make sure you monitor both context usage\nfrom your API provider\nand your linear
model's training stability—tools such as OpenAI’s \
`\texttt{usage}` callback make this precise evaluation straightforward!
