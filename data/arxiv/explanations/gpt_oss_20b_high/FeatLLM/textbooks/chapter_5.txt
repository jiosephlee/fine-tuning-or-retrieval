\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 5: Language-to-Code Parsing Pipeline  

In *FeatLLM*, large language models serve primarily as expert feature engineers rather than direct predictors per sample. Once an LLM has produced natural‑language expressions describing conditions that distinguish classes—called **rules**—the next challenge lies in transforming these freeform sentences into machine‑readable predicates that can be evaluated efficiently over ordinary tabular data sets. This transformation constitutes the **language‑to‑code parsing pipeline** described below, which preserves all amenity offered by powerful LLMs while obviating continual API queries at test time.



# Noisy syntax  

Typical programs that convert human language to executable logic rely on handwritten regular expressions matching textual patterns such as "`>`, `<`, `≤`, `≥`". However phrased rules frequently incorporate verbalized operators—for instance “\(x\) has a value greater than \(5\)” instead of "`x > 5`". Because tabular feature names are embedded verbatim in these sentences (e.g., `'age' -- greater than -- '50'`), even slight variants disrupt naïve regex tokens expected by static parsers.  

In FabLLM this issue becomes evident when a rule read from the model contains phrases classicalized into unconventional punctuations (“greater than”, “below”, “at least”), or even alphabetical forms (‘above’, ‘below’) mandated by reduction steps taken while manipulating templates seen during training (`Serialize`). Differences are invisible when presented visually yet are critical during numeric comparison operations performed programmatically later on the data row fields derived from `f_i` definitions written out explicitly (`“f_1 is …”`). Consequently straightforward pattern matching such as `/[<>]/i` repeatedly fails because there simply are no single-character operator symbols left within these natural strings.



# Self-consistent code generation  

To sidestep erroneous hand-crafted regular expressions, *FeatLLM* harnesses *self-consistent* python code generation built directly atop its own inference cycle. The model receives an instruction package clearly articulated around a **function template** similar to  

```
def matches_rule(row):
    # row : dict mapping feature names → values
    return (...)
```

Accompanying documentation describes arguments (`row`) and desired return type (`bool`). Within its logic stem it reads all pertinent expressions extracted via rule inference (§ 3). Because transformers have been trained on vast amounts of source-code corpora—including stubs implementing short conditionals—they reliably translate semantically equivalent natural-language sentences into concise boolean logic loops (`return row["age"] > 50`). Crucially, adopting a uniform template permits **rigid output vocabulary**, allowing easy walking through returned codes later.


During inference LLMs deterministically map verbal statements back onto canonical operators (`“greater than” → ‘>‘`, `“less or equal” → ‘<=’`). When noise remains—a case noted empirically—the combination narrows down pattern variability allowing strictly statically typed transformations through minimal post-processing steps financed only by simple conditional checks.



# `exec()` mechanics  

Once rule snippets arrive—themselves being flawless python functions—their execution proceeds by feeding every input row sequentially through Python’s native `exec()` mechanism:

```python
def iterate_rows(rows):
    for r in rows:
        yield match_rule(r)
```

At encoding time different rows are annotated individually using their original column values assigned directly incompatible types:
*numeric* fields stay numbers,
*categorical* fields remain strings,
*missing* entries become `None`.  
The engine runs one unified callable across all rows producing one-hot truth values (`1`/`0`) within a two-dimensional matrix $\mathbf{Z}\in\{0,1\}^{N\times R}$ where $N$ denotes samples and $R$ boundaries matches total generated predicates (10 per target class × number of classes). This matrix replaces raw numeric columns in subsequent learning stages without requiring additional data transforms once produced.



The gathered binary tableau becomes immediately accessible behind-the-scenes [[linearly]](https://symp.org); logistic weights are subsequently clippedted [positive] domain ($w_k\leftarrow \max(w_k,\phantom{-}0)$), gaining semantically interpretable importance scores after training (`cross‐entropy` loss) on merely few-shot examples ($k< N$, sometimes $k=4$). Because every row undergoing evaluation experiences precisely identical deterministic flow—calling precisely one short parser function—the resulting likelihood vector ($p^i$) offers highly reproducible behaviour across trials.



# Security / about reproducibility  

Every script returned by *FeatLLM* contains only arithmetic comparators, basic logical connectors (`and`, `or`, `not`) applied directly over column references supplied at runtime—a restricted computational subset lacking file I/O or system call symbols inherited during tokenization phase dominated by public open-source repositories (< 10 % cryptographic commands).</br>
Executing such confined scripts consequently admits negligible risk when run within isolated memory frames managed internally by standard CPython runtime (`exec()` injection flag off). Hence practitioners may evaluate bulk datasets without exposing sensitive pathways avoiding inadvertent data leakage.</br>
Reproducibility follows effortlessly because repeated requests under identical temperature settings yield stable parsing functions once seeded deterministically—a property rooted in zero-temperature self-consistency among GPT models measured experimentally within *FeatLLM*. Subsequent application thus depends solely on pre-computed Boolean matrix $\mathbf{Z}$ coupled with learned weight vectors uploaded once during training stage.
