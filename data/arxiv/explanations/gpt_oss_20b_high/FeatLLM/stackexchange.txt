**Short‑answer**  

The “rules” that FeatLLM asks GPT‑3․5 to produce are *single logical expressions*—one line per command—written right‑after a header that names the class label (`Yes`, `No`, …). Each expression uses only  

* numerical comparisons (`<,$<$`, `$\\le$`, `${=}i?$=`???...),  

* categorical equality (`${=} "\"some category\""`),  

* conjunctions (`and`) and disjunctions (`or`)  

and refers directly to the original column names supplied in the prompt so that the model cannot accidentally mix datatype meanings.



When those text snippets have been printed out you get something very close to plain mathematical predicates such as  

```text
Class Yes:
[1] age     $\ge$ 51                # single predicate  
[2] glucose $\le$ 125 OR insulin $\ge$ 140         # two predicates joined by OR  
[3] bmi     $\ge$ 30 AND trigsle $\le$ 140          # two predicates joined by AND  

Class No:
[1] age      <$>$ (= ??-->?) ??                  
[_ note_: While non‑numeric comparisons stay untouched,_ i.e.,
           `syst_bp = \"high\"`,
           `hiv_test = \"negative\"" ] / ...
```

### How FeatLMM turns those strings into usable Boolean features

**Step&nbsp;1 – Cleaning / standardisation**

A second prompt sent back to GPT‑3․5 asks it only for *Python* evaluation logic corresponding to each sentence above **without** any natural‑language fluff. The model typically emits trivial helper functions such as  

```python
def _rule_YES_01(x):
    # x is a dict or pandas series referring to one sample row    
    return x['age'] >= 51

def _rule_YES_02(x):
    return x['glucose'] <= 125 or x['insulin'] >= 140

def _rule_NO_01(x):
    return x['age'] < 30 or x['syst_bp'] == "high"
...
```

Those helper functions are wrapped together inside another tiny wrapper module that accepts an entire dataframe/array (`df`). Calling this wrapper produces a Boolean matrix  

\[ Z \in \\{\{\,0\, ,\,1\\}\}^{\,N\\times R}\],

where \(N\) is the number of samples and \(R\) equals “number \<emph>of classes × number\<emph>of enabled rules”.   
Each column keeps its unique identifier (\(YES_{01}, YES_{02},⋯)\)—guaranteeing reproducibility even when bagging is applied later—the order stays fixed because it follows precisely how many numbered clauses appeared under each header during prompting.



---

### Weight learning

Using these binary columns as inputs,
FeatLMM trains a very small linear classifier without bias whose weights
\(w_k\\in\\mathbb R^R ≔ \\mathbb R^\,R\\).

For every sample \(i\),
the logit for class \(k\) is simply  

\[ 
        {\color{blue}{w_k^\!*}}\,{\color{blue}{z_k^{(i)}}},
        \qquad
        z_k^{(i)}=\mbox{\bf all Boolean values belonging exclusively}
                   {\mbox{\bfto}} {\color{blue}{x}} ,
        
]
with ${w_k^\!*}=\\max(w_k,\!LP)$ denoting truncation onto
non​\-negative values.
The softmax over these logits gives ${p^{(i)}}$, which is optimised against cross‐entropy loss over the few-shot training set.



---

### Ensemble / bagging

Because every trial draws a fresh random subset of few-shot samples (or even randomises their order),
slightly different clauses get generated each time.
Repeating steps&nbsp;«​１–２» gives several distinct weight vectors
\(w_{k}^{(t)};\)\,
predictions finally average over all trials,

\[ p_k^{(i)}
=\frac{
        {\displaystyle∑}_{t=১}
        {\displaystyle exp(\operatorname {logit}_k^{\,t}) }
    }{
        {\displaystyle∑}_{j}
        {\displaystyle exp(\operatorname {logit}_j^{\,t}) }\;
        }
      ,
]
so mis‐generated clauses are naturally drowned out while useful ones survive,
building an otherwise almost-zero-cost inference pipeline.



---

### Takeaway

A FeatLMM “rule” looks nothing exotic—it’s a succinct Boole­an statement written once per line under a headline identifying which target label it concerns.
These plain statements get fed back into another quick round where GPT turns them into tiny Python predicates operating elementwise over incoming data rows;
every predicate becomes its own binary feature fed into an inexpensive linear model whose learned weights decide how influential each clause really is.



Because everything from phrase generation → parsing → Boolean conversion happens only once before deployment—and during deployment one merely multiplies pre­computed booleans against stored positive weights—the framework stays lightning fast while still leveraging knowledge‐rich reasoning afforded by GPT‑3․5 at training time.

### "Non‑negative weight constraint" – why apply `max(w_k,0)` instead of letting weights take any value?
Question:
`Equation (3) uses ReLU on w_k so all learned coefficients are positive.

Intuitively I guess preventing negative contributions protects against wrongly discarding true positives.

But metric-wise wouldn’t allowing negative values help learn hierarchy among rules?

Could you elaborate on the intuition/principle behind restricting weights
Answer:
**Why constrain every weight \(w_k\) to be non‑negative before multiplying it with the binary  
feature vector \(\mathbf z_k^{i}\)?**  

In FeatLLM every element of \(\mathbf z_k^{i}\in\{0,1\}^{R}\) simply tells whether *a particular rule generated by the LLM is satisfied* by sample \(x^i\).  
The role of the weight vector \(\mathbf w_k\) is therefore only **to rank** these conditions according to how useful they are for predicting class \(k\).

The authors deliberately project \(\mathbf w_k\) onto the positive orthant,
\( \max(\mathbf w_k ,\, 0)\), before taking its dot product with \(\mathbf z_k^{i}\). Their rationale “ensures that **the features generated by the LLM do not reduce the likelihood of a class during learning**” (Section 5)
unfolds into several intertwined motivations:

1. **Monotonic interpretation**  
Each engaged rule is meant to **provide evidence** in favour of its target label. Making its contribution always non‑negative guarantees that *the more highly–scored rules are satisfied*, *the higher* the logit,
hence the higher expected posterior after softmax:
\[ 
    \operatorname{logit}_k^i 
        = {\underbrace{\max(\mathbf w_{k},\, 0)}_{\geqslant 0}}
           {\displaystyle\times}
           \;\mathbf z_{k}^{i}.
\]
This yields an additive–evidence view analogous to classic decision‑list or associative‑rule systems where every triggered item merely adds credit toward its class.
A negative coefficient would mean “meeting this rule actually decreases confidence”, which contradicts how human experts would formulate outcomes usually inferred from an LLM’s textual reasoning:
“If disease \(X</span>\) occurs when age > 60”, then …—an affirmative causal claim, not an exclusionary one.*

2. **Avoiding accidental cancellation**  
With binary inputs permitting arbitrary signs inflates expressiveness: two strongly correlated rules could end up mutually cancelling each other.
In few‑shot settings such cancellations are fragile—a slight shift in a single label flips gradient directions dramatically, destabilising learning and producing noisy posteriors that depend heavily on random seed.
Constraining each coefficient to be ≥ \(0\\) removes this source of variance.
Empirically (Ablation Table 4) FeatLLM’s performance degrades markedly when coarsely summing unsigned filtered binaries versus allowing fitted weights,
while keeping them signed positively keeps training stable even when only tens of examples are provided.*

3. **Interpretability**  
A strictly non‑negative system mirrors attribute­importance readings:
“Rule j contributes \(w_{kj}\)” means “satisfying this antecedent increases our belief in class \(k\\)”*.  
If signs were allowed one would have pairs such as “Rule j” + “Rule l”
  weighing referee semi­negatively without any intuitive semantic story;
understanding why satisfying two seemingly useful conditions together lowers confidence becomes opaque—precisely what résumé‑style explanations seek avoid[ ](https://arxiv.org/pdf/<…>).*

4. **Hierarchy through additive strength**  
The authors’ concern about learning a hierarchical ordering between rules can still be realised under non‑negativity:\n\t• Thicker coefficients simply express stronger support while absence (\(w_j=\,{\displaystyle 0\\}) signals irrelevance rather than detrimentality.\nComplex logical patterns such as “[A AND B] OR C” are already expressed at feature level through separate Boolean tests;
keeping their aggregation purely additive avoids mixing genuinely suppressive effects,\n  which would otherwise have been captured implicitly via extra conjunction predicates anyway.*

5. **Alignment with empirical robustness tests**  
In Section 6 (“Effect of adding spurious correlations”) FeatLLM suffers far less degradation when unrelated columns are injected compared with baseline models.
A key contributor is precisely this positivity constraint:\n  irrelevant columns may inadvertently satisfy spurious “rules” producing false positives—having all coefficients forced ≥ \(0\\)
forces those noises either to be ignored (\(w_j={\,{\displaystyle 0\\})}) or contribute positively only after they truly correlate in hold‑out data;\n  there’s no danger that satisfying them causes an inadvertent drop in logit values—which could otherwise magnify noise effects during softmax normalisation.*

Taken together, these arguments explain why simply applying ReLU before evaluating logits—in contrast with letting arbitrary signed weights roam freely—provides predictable behaviour aligned with how human users expect tabular‐rule engines:
every hint extracted from an LLM should either boost confidence or remain neutral,
never demote it directly.*

Answer:
**Short answer**

During the “spurious‑correlation” study (Figure 3/B figure ≅ Table 4 of the paper), extra columns from *Adult* were grafted onto the *Heart* data – they contain no signal for heart disease. FeatLLM stays mostly unaffected for two reasons:

| Why it’s robust | What happens in practice |
|------------------|-------------------------|
| **Step‑1 (prior–knowledge reasoning)** | Before looking at any examples the LLM is asked “which features are *generally* causally related to heart failure?” Using its corpus‑trained world‑knowledge it eliminates most non‑heart‑related attributes from consideration. |
| **Rule selection constraints** | Only ten rules per class are produced and each rule must respect the feature’s declared type and name desription. A randomly‑attached column usually fails this check or produces a rule involving an implausible condition like “age > 200”, which is filtered out quickly. |
| **Weight‑tuning layer** | Even if a useless rule slips through, it becomes a binary feature that gets a learned weight. The linear model tends almost always into $\displaystyle \displaystyle
   \max (\boldsymbol{w},
   ০)\ =\:০$
for such features, so its influence is effectively eliminated during training on the few shot samples.
|
| **Bagging + ensembling** | Each trial resamples either features or seeds of the seed examples, producing diverse rule sets. The ensemble averages over many independent weak learners – any single bad rule that slips through is statistically averaged out with good ones.|

Because of these design choices FeatLLM requires very little degradation even when dozens of irrelevant columns are added—the degradation curve stays flat while baseline methods (plain logistic regression or naïve rule-summing alternatives) fall sharply as soon as noise enters the predictive space.

### ➀ How Step 1 prevented training-item correlations on unrelated fields?

In Sect.\ 3 of the paper, “prompt design for extracting rules” contains a reasoning instruction with two sub-steps:

1\. **Prior‐knowledge inference** – *“Infer how each feature may affect the given task using your general knowledge.”*  
   Here no example table rows are shown; only feature names/types and an objective (“Is heart failure present?”). Because GPT-\O{} was trained on large amounts medical literature—notable fact—it understands that *age*, *cholesterol*, *thalach*, … tend matter whereas *education level*, *capital gain*, *re lyn*… do not in this context۔ Therefore it selects only “reasonably plausible” variables for subsequent rule construction.

2\. **Rule construction using examples** – using a few labeled rows it refines relations into concrete predicates (“`\glucose >120` AND `cholesterol >200`”).

The critical fact is Spurious fields contained in *Adult* do not semantically dovetail heart failure predictions; GPT simply leaves them out during step 1 rather than creating arbitrary rules مثل ```\education =`\Bachelors``` أو ```\occupation =`\Exec-managerial```. Thus their inclusion hardly alters which variables make it into any trial’s final rule set – most extra columns never mentioned.

### ⚠️ Were there noticeable chance “useful” patterns found purely by accident?

During qualitative inspection across trials (see Appendix C), roughly 𝟐 % of rules referenced an unrelated Adult column yet coincidentally achieved AUROC ≥ ½ when evaluated on held-out data —this occurred purely owing random alignment between few-shot labels and column values in particular splits.



However:
- Weight tuning almost always annihilated those accidental hints: appended weights dropped below ●—effectively turning them off.
- Ensembling neutralized residual contamination finally yielding no systematic gain―any row containing noisy terms scored equivalently against trials where they'd been ignored.
- Across thirty-two independent train/test splits, none emerged aiding AUC beyond ~½ % once learning optimized.



So while random useful patterns momentarily pop up in very low-shot settings, FeatLLM blunts turns impressionary gains.

### Quick summary

• Step 1 removes ill-suited variables before evidence even reaches learning stage  
• Limiting each class to ten well-typed predicates keeps exposure narrow  
• Post-learning weights prune residual noise  
• Bagged ensembles smooth remaining artifacts  
• Consequently massive numbers of unrelated Adult fields hardly erode performance
