### 1.  The naive data dependency

The forward pass of one head is

\[
S\_i^{(j)} = Q\_i K_j^{\!\top}, \qquad
\tilde P\_i^{(j)} = \mathrm{exp}\!\big(S\_i^{(j)}-\!m\_i\big),   \qquad
O\_i   \;\mathrel{+=}^{}\;\tilde P\_i^{(j)}V_j .
\]

*For every query block \(Q_i\)* we iterate over key/value blocks \(K_j,V_j\).  
The usual implementation keeps the sequence “GEMM → hard‑soft→ GEMM” strictly
serial inside an outer loop iteration because:

* **Soft‑max needs the whole score matrix** \(S\_i^{(j)}\).  
  Even though it is possible to compute a *partial* ROW‑MAX and ROW‑SUM
  incrementally,
  nothing in a single kernel invocation has all rows finished until
  `S` has been produced by **the first** tensor‐core call (`WGMMA`).
* **The second GEMM** (`RS‐GEMM`) consumes `\tilde P\_i^{(j)}` and `V_j`;
  therefore it cannot start until the exponential has finished as well.
* Updating mathematics (`m` = row‑maximum,
  `l` = row‑sum‐exponential scaling factor) is *row‑wise scoped* – one walk
  through `S` suffices before moving onto `V`.

When every step waits instantaneously for its predecessor,
GPU resources sit idle during those few hundred nanoseconds it takes
the tensor cores finish their multiplies – the classic BARrier stall.



### 2.  Which dependencies have been “broken”?

FlashAttention‑3 reorders work inside one CTA so that **different warps** perform
stages that would otherwise have depended on each other *in a serial sense*,
while keeping *semantic correctness*.  
The two critical breaking points are

| Original serial data flow | Overlapped flow |
|---------------------------|----------------|
|¹ [GEMM] → exp → add   | `[commit]→[WGMMA]` ← continue calculating [next] [GEMM] |
| SALVATION | :SoftMax-rescaling → [commit]→[RS‐GEMM] |
|     | After finishing ↔ swap “current / next” registers |

1️⃣ **SS–GEMM** (`QᵢKⱼᵀ`) **vs** **RS–GEMM** (`˜Pᵢ⁽ʲ⁾Vⱼ`):
After launching an SS–GEMM we *do not immediately wait*;
we hand off its result into a temporary register (`S_cur`) and launch
an exp chain on *the previous* `S_cur`.  
The next SS–GEMM (`S_next`) proceeds in parallel while the RGEMP works
on `(old)` values – effectively a two‑stage pipeline:
`SS(j)` ∥ `RS(j−1)` ∥ `exp(j)` ∥ `row‑accumulate(j−2)` .

2️⃣ **Soft-max updating**:
The incremental update of `mᵢ`, `ℓᵢ` keeps two copies;
each loop stores(`old_m`) → computes(`new_m`)
→ calculates part of `ℓᵢ`.  
Because these scalars are held entirely in registers,
they no longer block any subsequent operation on a different
warpgroup—threads doing tensor‐cores do not touch these scalars at all.



### 3. Why “watching barriers” matters

```
volatile cond = false;
while (!cond) { … }          // <- Wait
```

A bracing pattern like this appears as `bar.sync`, i.e., *warp group barrier*,
in source code like Line 13/14 of Algorithm 2 in the paper.
This synchronisation does NOT stall all warps in a CTA –
only those enacting waits monitor this flag – a fine‑grained form of obstacle blocking.
It guarantees

* **Safe reuse of shared‑memory slots** – when SSA writes its fragment,
  no consumer reads it before decoding.
* **Correct ordering under interleaved scheduling** –
  since flushes may be issued out‐of-order by Hopper’s scheduler,
  these flags tell Warp–group 0 “I’ve finished writing this tile;
   Warp–group 1 may now read it.”

Thus *watching barriers* lets two different sets of warps share identical SM buffers without hazard:
there is no hidden global dependency between successive blocks.



### 4. Why fuse isn’t completely trivial

Even absent TMA/GMM latency minuend,

* **WGMMA hardware returns asynchronously**, but gets serialized only
when its destination registers become available.
If both halves use immediately successive register fragments,
register spilling increases markedly –
the compiler may spill into slower local memory,
 destroying any overlap advantage.
* **Soft‑max involves ‑exponential cache + reduction on CPU logic**
which lives outside Tensor Core pipelines – they close out exactly one SM’s functional units,
so even if muls finish early another functional unit might still be busy.
The adversarial kernel therefore needs explicit de‑scoping through additional registers
to keep both streams quiet at different SM lanes.



### Summary

FlashAttention‑3 punctures the series/parallel wall by giving up strict intra‑iteration seriality:
it retains semantic correctness via small register buffers (`S_cur/S_next`, `m_old/m_new`,
`ℓ_bottom/ℓ_top`) while launching new WGMMA kernels without immediate waiting.
Barriers (`bar.sync`) only guard against data races on shared‐memory slots,
not against logical construction order;
they provide just enough fencing so that warmup/warmdown stalls disappear.
Once Tensor Core workload is hidden behind concurrent exponent calculations,
soft‑max computation becomes effectively overlapped with continuous matmul progress –
hence significantly higher utilisation compared to FlashAttention‑2 where 
the strict order forces GEMMs plus endings to finish before any exp starts.
