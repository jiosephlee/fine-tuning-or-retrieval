\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### "Why perform an ‘in-kernel” transpose on V tiles instead of pre-transposing globally before running fp8 attention?
Question:
"The discussion explains that TMA loads cannot change stride direction.
When $V$ tiles come into SMEM they must become k-major, yet doing an off-chip transpose would cost bandwidth.
Could you detail why doing LDSM–STSM transposes in register space during kernel launch actually beats any off-chip pre-processing?
Answer:
**Short answer**

Because the FP8‐WGMMA operator on Hopper can only consume *k*-minor matrices,
the value tiles (\texttt{V}) have to be laid out so that consecutive entries in a thread block are contiguous along the sequence-length dimension.
TMA loads pull data from global memory with the original “head-major” stride and cannot reorder those strides---we have two choices:

1\. **Pre-transpose globally** – read every {\texttt{V}} tile from G-MEM,
permute its two dimensions on another kernel (or on host), write it back and then run attention.\newline   
2\. **Do an “in-kernel” transpose** – load the tile once into shared memory,
immediately rearrange its bits inside registers with {\texttt{ldmatrix}}/**{\texttt{stmatrix}}**,  
and feed the reordered data directly into the WGMMA.\newline   

The paper reports that option $(2)$ beats option $(1)$ because it avoids a full round-trip over GPU memory entirely + the extra synchronization and minor software complexity that come with a dedicated transpose step.
Below I unpack why this is true in detail.



--------------------------------------------------------------------

### 1\. What does “k-major” mean for FP8 WGMMA?

On Hopper X GPUs an FF8-enabled warp-group matmul (\texttt{WGMMA}) takes its two inputs from smem in very rigid layouts：

| operand | allowed layouts |
|---------|----------------|
| **A**   | *mn*-minor or *k*-minor |
| **B**   | **only** *k*-minor |

The first matmul in attention (${\tt Q}\times{\tt K}^{T}$) is safe – ${\tt Q}$ comes in as *mn*-minor  
and ${\tt K}$ is loaded *k*-minor, so no problem.\newline   
The second matmul (${\tt P}\times{\tt V}$) wants ${\tt V}$ as *k*-minor,

because its outer dimension is the row index (${\tt B}$)
which will be produced by the first operand (${\tt P}$).
Hence before feeding ${\tt V}$ into that second WGMMA we must transpose its tiles\nobreakspace\[\, {\rm head}\to{\rm seq}\ ] into sequence-to-head order.



--------------------------------------------------------------------

### 2\. Why can’t TMA do this?

Tensor Memory Accelerator (TMA) copies are high-throughput,
but they respect source/destination stride through their descriptor.\newline   
Given a tensor stored as  

```text rendered verbatim{
V[t][h]      // t = position along seq len, h = head dim}
```  

the default descriptor will fetch ${h}$ consecutively while stepping through $t$.  
There’s no flag that tells TMA “swap these strides”.  
Consequently every read must honour this native stride order—as\nobreakspace\[\, {\rm mn}-minor\, ].  

If we called TMA again after an explicit global/host transpose,\nobreakspace\[\, {\rm we'd} ] have had to materialise\nobreakspace\[\, {\rm a} ] new array where rows/columns were swapped;\nobreakspace\[\, {\rm TMA} ] would again pick it up mn-minor and store it mn-minor – nothing changes.



--------------------------------------------------------------------

### 3\. What does an “in-kernel” transpose look like?

The algorithm uses CUDA’s {\texttt{ldmatrix}}/**{\texttt{stmatrix}}**
instructions:\newline   

```cuda {
__shared__ half16 smemV[BLOCK_DIM][BLOCK_DIM];
// First pass:
ldmatrix.sync.aligned.m8n4.x4.m0(
     int4* dstReg /* registers holding D words */,
     &smemV[tid][0]);                 // src address = G-Mem loaded block

// Second pass:
stmatrix.sync.aligned.m4n8.x4.m0(
     int4* srcReg /* registers holding D words */,
     &smemV[tid][0]);                 // dst address = where WGMMA will read → now k-minor}
```  

{\texttt{ldmatrix}} pulls an $\begin{pmatrix}8& \\& \\& \\& \\& \\& \\& \\&\\& \\end{pmatrix}$
half matrix from smem (or gmem passed via TMA)
into warp-shared registers,\nobreakspace\[\, {\rm while} ] {\texttt stmatrix} writes it back—either unchanged  
or automatically $\lbrace i,j\rbrace\dashleftrightarrow\rbrace j,i$
depending on how it’s instantiated.\newline  
Because these copies work at granularity of **128 bytes**, all four lanes generate \$O(1)\$
stall cycles per warp —far cheaperthan moving data back across bus.



--------------------------------------------------------------------

### 4\. Bandwidth comparison

| Step                                     | Global pre-transpose            | In-kernel transpose             |
|------------------------------------------|----------------------------------|----------------------------------|
| Read {{indexed}{tilename}}              | once {$B_{\mathsf c}\!\times\d$} bytes        | once {$B_{\mathsf c}\!\times\d$} bytes        |
| Write back/staged copy                   | ⟹    once {$B_{\mathsf c}\!\times\d$} bytes         | none                             |
| Twiddle on CPU / another kernel         | big interleaved DMA latency + scheduling      | tiny en-chip shuffling            |
| Total G-MEM traffic                     |\phantom{} \, ${2\times B_{\mathsf c}\,\d}$               |\phantom{} \, ${B_{\mathsf c}\,\d}$                   |

Because GPU DRAM becomes a bottleneck when attention spans exceed thousands  
tokens,
saving one whole pass through G-MEM directly translates into:\newline   

• higher sustained throughput;\newline   
• lower overall device utilisation time;\newline   
• less pressure on caching and queueing layers.



--------------------------------------------------------------------

### 5\. Register pressure vs benefit

Inside WarpGroup we use only ≈½ KB of registers per lane\nobreakspace\[\, {\rm packedformats}]—compared against tens KB reserved for large ${K/B}$ blocks.\newline   
Even after adding one more set\nobreakspace\[\, {\rm registerfor}\ ]${S_{\mathsf next}}$,\
our occupancy usually stays above ≈80 % when using typical block sizes (
${B_{\mathsf r}=64}$).
Thus CPU-side logic and register spilling do not become limiting;
the gain remains almost entirely I/O-bound.



--------------------------------------------------------------------

### 6\. Practical outcome reported

The paper lists evidence that performing an FP8 test only\nobreakspace\[\, {\rm weightedshuffles}]—
i.e., “in-kernel’’ transpose—yields ‖10‒15 ℯ%
faster runtime than doing a separate global pre-transpose kernel reference implementation,\nobreakspace\[\, {\rm especially(where)} ]at large sequence lengths;

Moreover keeping everything inside one long persistent kernel means fewer context switches,\nbetter scheduler behaviour and architecture feature utilisation such\nobreakspace\[\, {\rm asyncCTA}] scheduling.



--------------------------------------------------------------------

Because Hopper’s FP8 WGMMA accepts only k-minor operands,
every value tile needs reshaping.\nobreakspace\[\, {\it Globally-transpose-first }]\nobreakspace\[\, {\it RevOp}:]\]
