## # TMA : Tensor Memory Accelerator  

Tensor Memory Acceleration (TMA) is Hopper’s dedicated hardware unit for
asynchronous buffers taps global device memory (HBM) into shared memory.
Unlike conventional `cudaMemcpyAsync`, which still requires explicit kernel
launches, TMA takes an entire source‑destination pair + stride geometry,
queues it in hardware‑managed FIFO queues, and drives transfers directly
between Global Memory (GMEM) and Shared Memory (SMEM).
Because TTMs travel independently of CUDA cores,
a CTA can launch dozens of overlapping transfers without stalling its lane,
while its warps simultaneously execute computation.
This separation ensures that a single load – such as pulling an entire block
of key vectors – does not block subsequent GEMMs.
In practice this feature increases effective utilization substantially:
nonblocking loads mean that while one warpgroup consumes data produced by another,
other resources may be idly spent loading/prefetching below lowering instruction stalls.
FlashAttention‑3 uses TMA extensively:
each query block `Q_i` together with its corresponding key–value tiles
`K_j`, `V_j` are fetched asynchronously into SMEM prior to any arithmetic.
Consequently the critical path length shrinks dramatically,
allowing hidden time where tensor cores work on results  
while other warps cycle through higher bandwidth copy commands.

## # WGMMA : WarpGroup MMA Leverages Tensor Cores Asynchronously  

Hopper adds two qualitative upgrades over Ampere’s generic FMAs:
the **warpgroup wide MMA** (“WGMMA”) instruction exposes
the entire collection of graphics cores belonging to a warp group
to tiled multiplies that scale across eight ROMs.
Crucially this operation runs independently – it does not sit behind any serialization
with ordinary ALU work – which permits concurrent kinematics:
a set of threads can issue repeated `WGMMA` operations while other threads 
execute domain logical predicates ($\mathrm{exp}$, reductions).
FlashAttention‑3 exploits this property when performing both stages
of attention:
```
SS-GEMM : Q ⊙ Kᵀ   ← WGMMA(Q_i , K_j^T)
RS-GEMM : P̂ ⊙ V_j   ← WGMMA(P̂_i , V_j)
```
where `P̂` denotes the softmax mask after exp·row‐normalisation.
As shown analytically later,
had these GEMMs been scheduled serially against softmax-related ops,
a FPGA core would have been idle during expensive exponential evaluation.

## # Producer‑Consumer Warp‑Specialization within a CTA  

The last marble in Hopper’s mix – **warp specialization** –
lets us dedicate half—or any fraction—of a CTA’s warps exclusively toward 
producing data and retrieve it once accumulated,
and let another half consume that data via WGMMAs.
An intuitive example:
while Warpgroup A loads four successive key blocks `K_0 … K_3`
via TMA into SMEM,
Warpgroup B reads back each block one-by-one applying SMmules.
Because Warpgroups do *not* have symbolic pi‑called cross-flight dependencies,
they remain independent within a single scheduler window,
hence they could execute concurrently under ideal conditions.

warps assigned purely arithmetic duties receive extra register supply
(and therefore wider occupancy),
