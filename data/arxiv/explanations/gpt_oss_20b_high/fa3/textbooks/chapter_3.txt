Chapter 3: Warp Specialisation – Producer / Consumer Pipeline Design  
=========================================================  

In a hand‑optimized implementation of transformer attention on modern NVIDIA GPUs,
the costliest operations are the two matrix multiplications that arise when the
query tensor $\mathbf Q$, the key tensor $\mathbf K$, and the value tensor
$\mathbf V$ are multiplied together.  
Because these GEMMs dominate execution time yet require every query row
to be compared against every key column,
the simplest way to reduce traffic is to fuse I/O‑bound global‑memory reads
into a tiny set of tiles that are kept resident inside fast shared memory,
and then let separate groups of threads perform the two successive GEMMs.
This split into *producer* and *consumer* warpgroups is called
warp‑specialisation, and allows one arm of the kernel
to hide latency while another arm is doing arithmetic.
The following exposition shows how this division works concretely,
how askew data movement angles are untangled behind a circular SMEM buffer,
and how a lightweight PTX helper
(`setmaxnreg`) reduces register pressure so that both groups run at peak
throughput on Hopper’s Tensor Cores.



## The Producer Warpgroup Issues TMA Loads First Q Block Once Then QKV Pairs Sequentially  

Inside one cooperative thread array (CTA) however many heads exist,
the *producer* throwaway group owns exactly one warp.
Its job is purely data‑movement:
load a query block from global memory into shared memory once,
then stream successive key–value blocks right through the same shared‑memory 
area when they are needed in subsequent iterations.
Because $\mathbf Q$, $\mathbf K$, and $\mathbf V$
are binned into tiles indexed by $i$ ($\mathbf Q_i$, $\mathbf KV_j$)
of size $B_{\text r}\!\times d$ or $B_{\text c}\!\times d$
(the query block size and key/value block size),
the producer begins its lifetime by issuing a Tensor‑Memory‑Accelerator
(TMA) read request that fetches $\mathbf Q_i$
into $\mathsf{SMEM}[\,i\,]$.  
Once ready it signals success (`commit`) so that any conditional waits made
in later kernels may advance past this point.
Afterward it loops over `$j=0,\dots,T_{\mathrm c}-1$',
issuing paired TMA loads for $\mathbf K_j$
and $\mathbf V_j$.  
These paired reads share an *asynchronous* DMA engine attached directly
to shared memory caches;
as soon as a request leaves globally‑visible DRAM,
it races downwards toward L2/SMM without stalling caller execution.
For Hopper’s Tensor Memory Accelerator this means that additional 
register writes need neither wait until preceding reads have finished,
which turns out essential later when consumers jump straight into computation.



## The Consumer Warpgroup Awaits Data Then Launches Async GEMMs via WGMMA  

Once all query tiles `$i$` have been staged, any *consumer* warpgroup enters its loop.
First it waits until its partner—the producer—has made available  
the current key‐value pair represented at modulo `$s$`
stage index `$j\mod s``, where `$s$` denotes how many concurrent SMEM stages exist.
Upon receipt (`wait`) it is assured that $\mathsf{SMEM}[:,:,\,j]$
contains both $\mathbf K_j^\top$ 
and $\mathbf V_j$.  

The two GEMMs proceed consecutively:
1) **SS‑GEMM** ($\tilde{\!S}_{i}^{(j)}=\!\!\!\! 
   \underbrace{\;\matrix{\Qr & distr}{d\times d}}\!    
   +\,\underbrace{\Ow{\Kr_j^\top}}\!)$ scales up query/Key rows;
this multiplication receives its operands directly out of shared memory
and produces an intermediate matrix earned over $B_{\mathrm r}\!\times B_{\mathrm c}$
that never escapes local lifetime or even local accumulators.
The launch takes place through Hopper’s `WGMMA`
instruction which receives its operands asynchronously:
it touches DMAs immediately afterwards continues executing other work,
and “commits” notification tells subsequent logical steps when results become usable.
2) **Softmax reduction** acts row‐wise on 
$\tilde S_i^{(j)}$, making large‐scale numerically stable scores  
$\widetilde{\!P}_{i}^{(j)}=\exp(\tilde S_i^{(j)}-m_i)$  
where `$m_i=\max(\bullet)$` tracks running row maxima across auxiliary blocks.
No global synchronization occurs during this operation—
a tiny double‑precision accumulator suffices because softmax’s two‐stream executor
is actually bounded far below raw TFLOPs thanks to scalar multiple pathways.
3) **RS‑GEMM** ($\widetilde{\!P}_{i}^{(j)}\;\vect{{V}}_j)
produces updates that accumulate incrementally into an output tile 
$\mathsf O_i$.  
Again this matricial product is started asynchronously out‐of‐order via `WGMMA`,
so that latency hiding works both ways:
while RS‑GEMM progresses, the very next `$K,V`
pair may be arriving via a fresh TMA load fed through another CUDA stream.



Neither computation step waits idle even if either data dependency chain would otherwise stall:
by knowing which part will finish first (`commit`).

Consequently heavy arithmetic just sits waiting baked into hardware dispatch queues,
and whenever operand buffers become light enough consumers fire off further operands.

Pingpong Overlap Between Softmax Computation And GEMM Operations  

# The inherent sequential dependence among SS‑GEMM → softmax → RS‑GEMM within an iteration  

In each iteration over a block \(j\) of keys \(K_j\) and values \(V_j\), FlashAttention first multiplies
the current query tile \(Q_i\) against \(K_j^{\!T}\).  
The result is called \(S_i^{(j)}\).  
Immediately after this multiplication preprocessing occurs before any parallelism can be introduced:
(1) one subtracts the rowwise maximum \(m_i^{(j)}\) from every entry,
(2) exponentiation is applied, giving \(\widetilde{P}_i^{(j)}=
e^{\,S_i^{(j)}-m_i^{(j)}}\), and
(3) partial sums \(\ell_i^{(j)}=\sum_{k}\widetilde{P}_i^{(j)}\_{k}\) are recomputed.
Only at this stage is the value \(\widetilde{P}_i^{(j)}\) available for yet another matrix multiplication,
the result residing in \(\ell_i\) becomes necessary for normalising subsequent sums.
Finally \(\widetilde{P}_i^{(j)}\) must be multiplied against \(V_j\),
producing a contribution \(\Delta O_i^{(j)}=\widetilde{P}_i^{(j)} V_j\)
to the output tile \(O_i\).  

Because every phase depends directly on previous outputs—
the second matrix multiply requires \(\widetilde{P}_i^{(j)}\), which cannot appear until
both subtraction and exponentiation are complete—this loop contains a strict data dependency chain
\(S_{\!cur}\rightarrow{\rm softmax}\rightarrow{\rm product}\).
Under a synchronous execution model every component waits for its predecessor’s
completion before launching its own work.
Resulting threadblocks idle whenever the exponent operation cannot keep pace
with Tensor‐Core matmuls even though these operations occupy independent hardware units.
This serialisation yields an imbalance that degrades overall utilisation,
especially visible when comparing raw GFLOPs required for multiplication against
ferocious limits imposed by special-function throughput on Hopper GPUs where,
for example,
exponential evaluation furnishes merely a few tera‐operations per second
compared against several hundred tera‐operations per second for matrix multiply:
\(F_{\rm exp}\approx3\,{\rm TFLOP/s}\ll F_{\rm WMMA}\approx989\,{\rm TFLOP/s}\).  

Hence any opportunity delivering concurrent progress on both paths without violating data availability
is critical, motivating pipelined execution schemes capable of overlapping computations tiled
across key-value blocks while one pair produces data necessary for another pair’s subsequent step.


# Two‑stage pipeline idea where product matrix (\(\pi\)) from iteration \(j\) feeds runs while next SS‑GEMM runs ahead  

A simple yet powerful way to break this dependency chain is to consider two iterations linked through hidden registers,
forming what FlashAttention refers to informally as a “two–stage” pipeline.
During the processing of block \(j\), \(Q_iK_j^{T}\)—the first WWCR—is launched.
The kernel does **not** immediately wait for its result;
instead it commits the asynchronous query choose into shared cache,
then immediately issues a second WMMA call evaluating \(Q_iK_{j+1}^{T}\).
By leaving both computations outstanding simultaneously,
the kernel keeps all Tensor Cores busy even whilst computing intermediate entries.
In parallel, once vector \(V_j\) reaches SMem,
the partial sum produced during previous hard SUM (\(\Delta O_i^{(j)}\))
is fed into a subsequent RTxW GMMA equation synchronously.
When both WMMA operands finish,
softmax evaluation proceeds entirely on L3 registers—
subtracting rowwise maxima accumulated until current stage,
calculating exponentials and row sums—all performed entirely outside SRAM access cycles.
Because these softmax calculations consume roughly half a cycle per scalar compared
to multi–fop Tensor Core operations,
their delay hides behind succeeding iterations’ primary multiplication pipelines),
thereby diminishing idle kilometres created by serial reservations.


Concretely expressible along pseudo operational steps:
1| Compute ‑ `S_cur ← Q × K_j^T`,
   launch asynchronously;
2| Launch `S_next ← Q × K_{j+1}^T`, also asynchronous;
3| While awaiting `S_next`, temporarily keep buffer values present;
4| Execute RS–WGMMA `O ← O + P_cur × V_j`;
5| Return accompanying statistics (`m`, `ℓ`) back into registers;
6| Proceed loop onto subsequent index pair `(j+1 , j+2)` following exactly the same schedule.



A fundamental point is that all kernel stages remain valid because new values required by later iterations never reach register storage until all depended constants complete.
When holding partial sums through registers prone to overflow–wise early‐flush,
FP32 accumulator space prevents catastrophic precision loss –
but small detail crucially bearing on quantisation conditions addressed later.

**FP8 Low‐Precision Acceleration – Layout Constraints and Operand Representation**

# The _e⁴ᵐ³_ Format’s Weight Range and Dynamic–Range Limits  
The Hopper GPUs expose an eight–bit floating–point type designated **FP₈** whose most common variant is referred to as *e⁴ᵐ³*: one sign bit followed by four exponent digits and three fraction digitsesque fields internally denoted `[s]=[±], [exp]=[0…15], [mant]=[0…7]`.  
Because only three fraction digits survive after normalising input values the granularity delivered by *e⁴ᵐ³* becomes markedly coarser than either **FP₁₆** or **BF₁₆**, which carry ten fraction digits behind an implicit “leading‐one” guard bit.  
The bulk effect translates into two intertwined problems relevant for attention kernels:
1. **Limited Numerical Precision** – any two distinct probabilities whose ratio differs less than roughly \(2^{(exp_{i}-exp_{j})}\times 2^{-1}\) collapse into identical encoded numbers once converted into *e⁴ᵐ³*.  
   Consequently tiny differences introduced during the softmax stage can vanish entirely or cause catastrophic loss during rescaling.”
2. **Restricted Dynamic Range** – although four accessable exponents allow representing large magnitudes geometrically (\( \pm\,2^{(15-\text{bias})} \)), very small intermediate scores tend toward underflow because even mildly negative *exponent* values push computed scalars below \(1{\times}10^{-5}\), effectively zeroing limb probabilities when multiplied.
Both issues make naive conversion of attention tensors directly into *e⁴ᵐ³* unacceptable if uniform fidelity comparable to standard **FP₁₆** round‑trip behaviour is required.*¹  

The remedy incorporated into FlashAttention‑³ exploits this factetsally by splitting tensors into compact blocks over query positions (\(B_r\times d\)) or sequence blocks (\(B_c\times d\)). Each block receives its own scaling factor before conversion so slopes between adjacent scalars remain centred high inside the representable window offered by *e⁴ᵐ³*. This “block‐quantisation” keeps every block’s weights inside a tightly constrained vicinity of zero/one where ten ¸t b compared emphasises improvement.*

# k‑Major versus mn‑Major Restrictions Imposed By Hopper’s **FP₈ WGMMA**  
Invariance under linear transforms ensures any matrix multiplication \(A\times B^{\mathsf T}\) can execute happily, provided data meets one requirement about dimension contiguity relative inside shared memory (SMEM).  
Hopper introduces two distinct visualisations:
- A fragment is labelled **“mn‑major”** when its naturally contiguous alignement follows either outer dimension \(M\) or inner dimension \(N\).
- It becomes **“k‑major”** when consecutive elements progress following inner product stride \(K\).
With **FP₁₆** WGMMAs any fragment may be supplied in mn‑major or k‑major form—the underlying tensor core fetch logic flexibly adapts.
With **FP₈**, however, this flexibility disappears*: only fragments purged along inner stride “k‑major” are acceptable as operands.*²  

In an attention kernel Q/K/V typically live as matrices residing adjacently along heads (\(d\)-dimension), meaning V’s natural SMEM stride follows heads rather than sequence length position—the opposite direction required by fan‑out padding rules post facto.* Because K itself must reach furthest scores concurrently whilst retaining rowwise degree next scheduled properly, K naturally fits an mn‑major shape aligning correctly along sequence length dimension while V’s exotic contraction demands a wealth override again k‑maj­or orientation.*

The consequence is straightforward yet unavoidable: Either V needs an explicit transpose somewhere prior – either prior global remapping (“global transpose”) or immediately upon copy above – confirmation before being handed over any *FP₈* WGMMAs five kernels engaged during forward pass.**
