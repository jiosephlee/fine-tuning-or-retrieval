## Why Attention Is Expensive  

All transformer heads share three linear projections ‑ queries (𝐐), keys (𝐊), values (𝐕). For a single head the core operation is  

\[
\mathbf S = \alpha\,\mathbf Q\,\mathbf K^{\!\top}\;, \qquad   
\mathbf P = \operatorname {softmax}\!\bigl(\mathbf S\bigr)\;, \qquad   
\mathbf O = \mathbf P\,\mathbf V ,
\]

with   
$\alpha=1/\sqrt d$.  
The cost grows quadratically with sequence length $N$: $\mathcal O(N^{\,2}\!d)$ floating‐point ops are needed just to sample every $(q_k,v_k)$ pair once the model cares about it.

On modern discrete GPUs this quadratic cost translates largely into **memory traffic**—every element of $𝐐$, $𝐊$, $𝐕$ must be streamed off‐chip into shared buffers again whenever it becomes part of another chunk’s product matrix $𝐒$. Even after moving data suitably once per kernel launch you still hit tens–of–GiB sweeps every forward pass, scrubbing entire tensors down again during backpropagation.

## First‐Generation Fast Attention – where did it falter?

| Attribute | Original FlashAttn | Projection toward Hopper |
|-----------|--------------------|---------------------------|

# Inside the Pipeline:
# Overlapping Softmax and Matrix Multiplication
## Turbocharged Attention on Hopper GPUs

Attention is the workhorse that makes Transformers model text, code, images and more.  
On a modern GPU that work boils down mainly to two stages:

1. **A gigantic matrix multiplication** – compute the dot‑product scores  
   $$\mathbf{S}= \alpha\, \mathbf{Q}\,\mathbf{K}^{\top},$$  
   where $\mathbf{Q}$ and $\mathbf{K}$ are $N\times d$ query/key matrices,
   $N$ being the sequence length.
2. **A lightweight softmax** – row‑wise exponentials followed by normalisation  
   $$\mathbf{P}=\operatorname{softmax}(\mathbf{S}).$$  

Even though $\mathbf{S}$ contains $N^{2}$ entries, all those exponentials are
handy little float operations; they just sit idle while huge GEMMs fire through
the Tensor Cores. On an H100 Diamond back‑end this imbalance turns the
single micro‑NVIDIA kernel into a “put your feet on ice” stall at every
iteration — an opportunity the FlashAttention family has been chasing
for years.



--------------------------------------------------------------------

## Why      The Softmax Stalls Us

* GPU kernels run at millions of clock cycles per second,
  but **softmax exponentials** run at only *a few thousand* FLOPS per SM.
* Matrices come fast — Hopper’s Tensor Cores can crunch billions of
  operations per second when fed from shared memory,
  whereas **exponential units** are a single special function unit per SM
  that perform only ~10 op / clock cycle.
* In ordinary “run‑once” code you do:
   ```
   S = Q × Kᵀ      // Matrix multiply (hot)
   P = exp(S-max)   // Exponentials (cold)
   ```
   The GPU executes `S` efficiently, but then idles while it waits
   for `exp()`.



--------------------------------------------------------------------

## Tape Warp‑Specialization + Asynchrony

FlashAttention‑3 takes advantage of Hopper’s *asynchronous* execution:
* **Tensor Memory Accelerator (TMA)** wires giant DRAM blits straight onto
  shared memory without stalling.
* **Warpgroup Matrix Multiply (`WGMMA`)** is every bit as efficient as it gets,
  but runs independently of instruction flow—so you keep itself busy doing GLAs
  even if other threads are still waiting on older ones.
* By **dividing each thread block into producer warps** (loading data)
and **consumer warps** (doing multiplies + softmax),
the producer never blocks the consumer – data movement stays behind,
and every cycle sees work.



--------------------------------------------------------------------

## Exchange Runners – The Two‑Stage Pipeline

The trick lies inside *one* consumer warpgroup where there are two ordersable
operations:

| Stage | What it does                      | Where it must finish-before… |
|-------|-----------------------------------|------------------------------|
| **GEMM 0** | Compute $S_{\text{cur}}=\mathbf{Q}\,\mathbf{K}_{\text{cur}}^{\top}$ |       |
| **Softmax** | Turn $S_{\text{cur}}$ into $\tilde{\mathbf{P}}_{\text{cur}}:=e^{S_{\text{cur}}-m_{\text{cur}}}$ |          |
| **GEMM 1** | Update output $\mathbf{O}\gets \tilde{\mathbf{P}}_{\text{cur}}\mathbf{V}_{\text{cur}}\,$ |           |

In a naïve kernel each iteration would have hard waits right after  
`GEMM 0` before entering `Softmax`, then wait again before launching `GEMM 1`.  
This serialises almost all useful work – only one multiply feeds one softmax,
then one more multiply heads off – leaving huge portions of the Tensor Core idle.


### How FlashAttention‑3 changes everything

1. **Double buffers inside registers** – Save `S_{\text{next}}` immediately after...
   ```cpp
   S_next = Q × K_nextᵀ           // start multiplication
   // leave it running while …
   ```
2. **Overlap ‘Softmax’ + next ‘GEMM 0’**
   ```cpp
   wait for GWMMA( Q × K_curᵀ )    // finish current multiply
   m_cur , P_cur = softmax(S_cur)
   X += P_prev × V_prev            // GRAPES row-col product already started earlier!
   ```
3. A simpler picture is a **relay race**:
   
   *Team A:* feeds block $j$ into Tensor Core.
   
   *Team B:* runs the cheap `softmax` on block $j−1`.
   
   While Team B pushes its baton off, Team A still burns full energy threading block $j+1`.  
   
In pseudo code you sketch it as “commit WGMMA1 but don’t wait;
then commit WGMMA2 but don’t wait; finish whichever finishes first”, exactly what line 23–27 in Algorithm 4 describe.



--------------------------------------------------------------------

## Ping–Ping Across Warpgroups

Adding another layer modulo simple “one warp produces everything” you put
the whole CTA underground:

* **Producer group** keeps filling a circular shared‑mem buffer with new Key / Value blocks via TMA.
* **Consumer group #0** processes blocks [0..t] using the two‑stage pipe above.
* While #0 is doing its slow exponentials,
**consumer group #1** can start its own GWMMA giving an extra dive of parallelism—
effectively you have *two places hard at work concurrently*, which inner‐loop scheduling tells CUDA’s scheduler exactly how many instruction cycles stay behind.
This “ping–pong” arises because both groups happenstance share diverging start times –
harder than copy/paste theory but good enough to lift device utilisation from roughly *35 %* up close to *75 %* on Hopper.



--------------------------------------------------------------------

## Why It Really Matters

The paper’s timing tables back up the intuition:

| Repeated Kernel Strategy | Speedup over FlashAttention‑2 |
|--------------------------|------------------------------|
| Simple producer / consumer without overlap | ~ 570 TFLOPs |
| With Two‑Stage Pipeline alone | ~ 620–640 TFLOPs |
| Two‑Stage + Ping–Ping (`Warpgroup` scheme) | Up-to 740 TFLOPs over H100 ×FAK |
| FP8 version adds layout tricks → ~“Close to 1 PFLOPs” |

So you go from *suboptimal Tensor Core utilisation* (~33%) all yours gain:
a *≈30–40 % increase* simply by letting your lane carry “softmaximum”
while another lane spins through matrix multiplication.


--------------------------------------------------------------------

## Recap & Bottom Line

FlashAttention‑3 turns an otherwise clumsy look at attention –
do-multiply-and-hurry–through-softmax–
into a carefully choreographed dance where every SWENO swim slot is occupied:
> **Pipeline State:**  
> - Producer Warps → TMA Loads → Water carried over buffer until needed  
> - Consumer Warps → WGMMA queueing pieces → SoftMax peel – all racing simultaneously  

Thereafter each head no longer waits passively between two intensive ops,
but stays strapped tight as early blooming timers keep raw multiply engines hot.
The result? An accelerator routine that reaches near sweet spot performance –
stopping Cubic‑time attention from taking longer than your eye can follow.

# FP8 on GPUs: Making Low‑Precision Attention Accurate

Large language models are increasingly trained on sequences that stretch thousands or even millions of tokens.  
The attention mechanism—the heart of every Transformer—scales quadratically in sequence length, so it quickly becomes the computational bottleneck of both training and inference.  
Recent generations of NVIDIA GPUs (the **Hopper H100** series) pack more powerful accelerators than their predecessors: asynchronous Tensor Cores (`WGMMA`), a dedicated Tensor Memory Accelerator (`TMA`) for fast reads from HBM, and support for **FP8** arithmetic that delivers twice the raw throughput as FP16 when properly used.

Unfortunately, moving from float‑to‑half (FP16) down to **FP8** brings a larger dynamic range problem—in particular *outlier* values in large language models cause unacceptable loss of precision if the standard per‑tensor scaling is applied everywhere.  
FlashAttention‑3 solves this by combining **block‑wise quantization** with **incoherent processing** (a random orthogonal mixing step). Together they give low‑precision attention an accuracy comparable to higher precision while enjoying the speed benefits promised by the hardware.

> *TL;DR – With just two small changes you can run tiny‑talks worth of GPT‑style training on an H100 at almost half the cost—and still keep your model’s gradients accurate.*

---

## How Attention Works

At its core an attention head computes

\[
\mathbf{S}= \alpha \,\mathbf{Q}\,\mathbf{K}^{\!\top},
\qquad
\mathbf{P}= \operatorname{softmax}\!\bigl( \mathbf{S} \bigr),
\qquad
\mathbf{O}= \mathbf{P}\,\mathbf{V},
\]

where \(\alpha=1/\sqrt{d}\) normalises the dot product scores (\(\mathbf{Q},\!\mathbf{K},\!\mathbf{V}\in \mathbb{R}^{N\times d}\)).  
The heavy lifting consists of two matrix multiplications (`Q*Kᵀ` and `P*V`); every other operation—rowwise max/subtraction/pre‑scaling/exponent—runs at far lower arithmetic intensity.

On previous GPUs this pattern was already fused into a single kernel by *FlashAttention*: read a small chunk of `Q`, `K`, `V` into shared memory once, walk through all key/value blocks, accumulate partial products—all without spooling full \(N\times N\) score matrices onto global memory again.



---

## What Goes Wrong When You Go Down To FP8?

In theory each TPUs or GPU accumulator supports multiple element formats: BF16 → FP16 → INT4 → *E4M3* FP8, where an exponent holds four bits and a mantissa holds three bits – a trade‑off between range and resolution.
While FLOP throughput easily doubles from `WGMMA` using E4M3 versus float16, the price you pay is far higher **numerical error**, especially if your data contains extreme values:

| Format | Bits | Exponent bits | Mantissa bits | Typical Range |
|--------|------|---------------|---------------|---------------|
| BF16   | 16   | 5             | 10            | ±65504            |
| FP16   | 16   | 5             | 10            | ±65504            |
| E4M3 FP8| 8 | 4 | 3 | ±(1480/1024≈1.45–1459/1024≈1425→30x smaller range) |

When a tensor contains a handful of far outliers – common in LLM weights/activations – global scaling schemes smear all elements into narrow regions where resolution collapses on small \(K\times V\) dot products.



---

## Two Simple Fixes

### 1️⃣ Block Quantisation

Instead of applying *one* scale factor per entire tensor (\(\mathbf{Q}, \mathbf{K}, \mathbf{V}\)), split each matrix into blocks that match what FlashAttention already processes:

```text
           Block size      :   B_r × d   (for Q)
           Size example     :   B_r = 128 , d = 64
```

Each block gets its own multiplier before conversion to E4M3:

\[
[\tilde{\!Q}]_{ij} = \frac{[Q]_{ij}}{\sigma_{ij}}
,\qquad
\sigma_{ij} = {\textstyle\texttt{median}}\bigl( |[\,Q\,]_{\text{{block }\,ij}}|\bigr)
,
\]

and similarly for \(\mathbf{K}, \mathbf{V}\).  
Because every block shares an average magnitude value — often sufficient while perfectly matching what FlashAttention reads sequentially — it dramatically reduces the worst‑case rounding error without any extra memory traffic.



### 2️⃣ Incoherent Processing (Random Orthogonal Mixing)

Let \(M\in{\mathbb R}^{d\times d}\) be an **orthogonal** matrix (\(MM^\top=I\)).  
Pre-multiply both query and key by \(M\):

```text
       Q ← Q M ,        K ← K M .
```

Algebra ensures nothing changes:

\[
(Q M)(K M)^\top = QM M^\top K^\top = Q K^\top .
\]

But now each entry inside \(Q,M,K,M^T\) becomes roughly an independent sum over many input components—effectively *spreading out* extremes across many indices.
Practically one uses \(M=\! D_1\,H\,D_2 D_3 , D_i=\operatorname{diag}[+/-1]\), where \(H\) is Hadamard; multiplying by such a chocolate‑like scheme costs only \(O(d\,\log d)\).

By mixing local spikes across dimensions the subsequent per‑block scalers use more representative statistics,
rendering the E4M3 representation faithful across “outlier” blocks.



---

## How All These Pieces Fit Into **FlashAttention‑3**

FlashAttention–3 retains the proven “tile+shared memory” design but wires it up straight‑to‑the-wire onto Hopper’s new primitives:

1️⃣ **Warp-Specialized Pipelining**  
Two separate warp groups inside one CTA work alternately:
   * One group moves data from global memory (*TMA*) into shared memory.
   * The other group consumes that data via asynchronous `WGMMA` Matrix Multiply units while simultaneously computing softmax terms (`exp`, `rowmax`) that only modestly stall compared against enormous MATMUL throughput.
   * A ping‑pong schedule alternates which group does softmax versus GEMM ensuring both instruction streams stay busy.


2️⃣ **Layout Conformance For E4M3**  
Because `WGMMA` expects operands in *k*-major order when targeting E4M3,
we prepend an **in-kernel transpose** operated by `ldmatrix/stmatrix`.  
After computing first GEMM (`Q*Kᵀ`) we permute its accumulator registers into k-major form ready for the second GEMM (`P*V`) – short byte-aliasing avoids costly shuffles.


3️⃣ **Block Quantisation + Incoherent Mixing**  
Training data (\(\mathbf{Q},\!\mathbf{K},\!\mathbf{V}\)) are first passed through Random Orthogonal Mixing then scaled per block as described above **right before they are laid down into SMEM**.\  
Thus every subsequent kernel works exclusively in E4M3 without any trial-of-one-scale penalty.


All these invariants fit within a single persistent kernel per CTA — which means almost zero global casts beyond pure elemental arithmetic.

## What Is Attention Still Doing In Your Model?

Even after ten years of deep‑learning advances, the Transformer’s **self‑attention** layer remains a computational hotspot—quadratic cost scales badly when you need longer contexts (think hundreds‑of‑thousands of tokens) or higher precisions for training stability.  
The classic way this layer is coded on GPUs materialises two big matrices – scores $\mathbf{S}$ and softmax weights $\mathbf{P}$ – to slow memory before feeding them into subsequent matrix products forming $\mathbf{O}= \mathbf{P}\mathbf V$. Every extra element ends up being written back to global memory twice!

## Enter **FlashAttention‑3**

Building on two predecessors (the original *FlashAttention* and its tightened partner *FlashAttention‑2*), version 3 marries three concrete ideas tailored specifically for Nvidia’s Hopper H100 architecture:

| Idea | What It Does | Why It Helps |
|------|--------------|--------------|
| **Warp‑specialized producer–consumer pipelining** | Separate warps are dedicated either for data movement (*Tensor Memory Accelerator*, TMA) or computation (*warp‑group Matrix Multiply*, WGMMA). | Eliminates idle cycles caused by synchronous memory loads—warps can keep working even while other warps still finish their GPU core work.| 
| **Softmax + GEMM overlap** | While one block’s softmax runs near *Tensor Core* execution time of another block’s matrix product, their respective throughput windows overlap through a two‑stage “ping‑pong” scheduler.| The exponential operation runs at ≈ 4 TFLOPS while WGMMA gives ≈ 990 TFLOPS in FP16—a pure softmax stall would waste roughly half Throttle time!|
| **Full HW acceleration for FP8** | Rearranges operands so both operands fit Hopper’s **k‑major** constraint for its dedicated FP8 WGMMA kernel and leverages *block quantization* + *incoherent processing* to control quantitative drift.| Loses nothing perceptible while doubling raw arithmetic throughput – bringing associative instruction counts close to peak device capability.|

All three bullets stem directly from Hopper’s infectious ability: true async Tensor Cores, fast TMA loads, and cheap 808-bit RMEM registers that can spill between warps when we voluntarily sacrifice some register pressure during pipelining.

## Accuracy Check—Tradeoffs With Low Precision

State-of-the-art inference demands less than gigabyte bandwidth footprint while retaining faithful logits vs gold-float64 versions.
  
*For FP16*, keeping intermediate accumulators in float32 brings error comparable—or slightly better—than legacy *flash* implementations that store softmax intermediates fully float32 anyway.\n

For *FP8*, naive per-tensor scaling typically rattles RMSE up against float64 references (~30 % larger numbers). Adding two countermeasures solves it:

1. **Block quantization** – apply a fresh scale per tile instead of one global multiplier.\n

Combined these lift accuracy upwards dramatically—“flash” experiments reported relative errors shrink \(20–60\,%\), formally boosting real-valued RMSE downwards \(≈⊗∅\,→ ≈\,10^{-4}\) versus vanilla fp8 per-tensor methods.\n

The takeaway: accuracy gaps vanish whilst harnessing native HW INTENT support so practitioners don’t have to pin their attention through simple half-floating rich speeds.

# Building Faster Language Models for Long Contexts: Why Hardware‑Aware Algorithms Matter  

***

Long–context Transformers have become the cornerstone of many advanced NLP tasks—ranging from multi‑document reading comprehension to code completion across thousands of lines of source code. Yet at every iteration step the self‑attention layer still dominates runtime because the cost grows quadratically with sequence length:
\[ \mathbf{S} = \frac{1}{\sqrt{d}}\;\mathbf{Q}\mathbf{K}^{\top},\qquad   
   \mathbf{P}= \operatorname{softmax}(\mathbf{S}),\qquad   
   \mathbf{O}= \mathbf{P}\mathbf{V} . \]
Here \( \mathbf{Q},\mathbf{K},\mathbf{V}\in\mathbb{R}^{N\times d}\) are the query–key–value tensors for a single head (\(N=\) sequence length, \(d=\) head dimension), \(d_{\text{model}}\) is divided across the model’s heads, and the softmax is applied row‑wise after subtracting each row’s maximum value for numerical stability.

Even after pruning approximation tricks such as sparse or linear attention schemes, whenever an application requires *exact* attention—e.g., causal generation hugging all tokens accumulated so far—even modest gains from hardware acceleration can make the difference between real‑time inference and a wall clock pause on cloud GPUs.  

This blog follows the story behind **FlashAttention‑3**, which turned heterogeneous GPU capabilities into an order‑of‑magnitude speedup over its predecessors while preserving full numerical fidelity—even when targeting cutting–edge low precision formats such as FP8.



---

## The Attention Bottleneck in Long Contexts  

When working through large inputs (several thousand tokens or zoomed images), the intermediate matrices \( \mathbf{S}\) (\(N\times N\)) become several gigabytes long—not just beating memory capacity but blowing up RAM bus swaps on every batch element:

* **Global reads/writes** dominate when naïvely materializing score matrices.
* **Memory bandwidth** saturates early—pretty much every kilobyte transferred must be processed multiple times before it disappears.
* Once scores are computed they must be normalized by *softmax*, an operation that delights nothing but the highly specialized *special functions unit*—the GPU equivalent of a scalar processor hidden beneath dozens of tensor cores.



---

## Leveraging Hopper’s Asynchronous Core Units  

Hopper (the CUDA architecture underlying NVIDIA's H100 GPU) introduces two game changing features that many earlier libraries never took advantage of:

| Feature | What It Does | Why It Matters |
|---------|--------------|----------------|
| **Tensor Memory Accelerator (TMA)** | An architectural unit dedicated to moving tensors between global memory (HBM) and shared memory at line‐rate PCIe speeds | Enables *nonblocking* loads where kernel threads can stay busy while data hot‑spots are fetching out |
| **Warpgroup Matrix Multiply Accumulator (WGMMA)** | A completely asynchronous set of Tensor Cores that can source one operand directly from shared memory *and* finish its operations outside any thread synchronization barrier | Allows *overlap*: producer warps can load data “in parallel” while consumer warps compute against them |
| **FP8 Tensor Cores** | Dedicated hardware that executes \(e4m3\) binary32×binary32 → binary32 multiplications twice as fast as its FP16 counterpart | When used safely it unlocks more than double FLOP throughput per SM |

The combination creates a juicy opportunity frame:
> *If you only care about passing arguments into WGMMA before it consumes them,* you can treat producer warps as a stream generator and consumer warps as an overlapped consumer—much akin to how CPUs use separate pipelines for I/O vs compute on modern microarch.



---

## Innovations Driving FlashAttention‑3  

FlashAttention‑3 distills three core ideas—each addressing one of Hopper’s novel capabilities—into a single kernel design that debits almost every wattous stored per instruction linearly into useful FLOPs.



### 1️⃣ Warp‑Specialized Producer–Consumer Pipelines  

In classic implementations every set of threads did their own load *and* computation without any heterogeneity—think all threads doing TMAs then all doing WGMMA synchronously afterward using `bar.sync`.  
FlashAttention 3 assigns whole warps into one role each:
* **Producer warps** – move blocks \(Q_i,K_j,V_j\) through TMA into carefully staged shared memory buffers.
* **Consumer warps** – consume those blocks exclusively through WMGMA chains inside an O(1)-latency loop that keeps registers tiny yet high throughput.
  
Because the producer stalls only on its own TMA pipeline (not on other warps’ work), latency hiding becomes *per instruction set*, dramatically raising effective utilization from ~35 % on Hopper down toward ~70 % plus when matched against vanilla GEMMs.



### 2️⃣ Pipelined GEMM ‑ Softmax Overlap (Ping‐pong)

WGMMA operations finish orders of magnitude faster than evaluating exponentials needed for softmax (`exp`).  
If you blend them naïvely you suffer twice the warm‐up latency from extracting results before moving onto the next key tile.  
By reworking FlashAttention 2’s strict chambered loop into an alternated schedule we achieve “ping‐pong” overlap:

```
warpgroup A : [GEMM(Q·K_j^T)] + [softmax(S_{j})]
// immediately after finishing GCCA_A,
warpgroup B : [softmax(S_{j+1})] + [GEMM(Q·K_{j+1}^T)]
```

While one group lives in its first SIMD lane executing fast THRD multiplication,
the other group goes straight into computing exponentials.  
The two groups meet only when a barrier guarantees consistency across output buffer stages – but those barriers are deliberately placed exactly at points where compiler reordering won’t destroy our spec.



### 3️⃣ Going Low Precision – Layout Hacks & Quantization Tricks  

Push towards FP8 requires a little extra gymnastics due to layout conventions enforced by WGMMA:

* **Operand Layout** – For FP8 WGMMA only *k*-major operands are legal inside SMEM.\`<[modal>`.
* **Accumulator Layout** – Accumulator registers flippantly interleave along outer rows pairwise (`mn` vs `nm` access patterns).  

To make these conform we do two things **inside** kernel land:

1. **In-memory tranposes**  
   Using LDSM/STSM hyper‑matrices that load/store `8×8` tiles at once—and allowing packed bytes—to transpose V on demand *while datapaths are still busy*. By aligning this exploit with our buffer stage operations we hide any wait time entirely.
   
2. **Byte-permute accumulator fragments**  
   A tiny swizzle turns the accelerator's register ordering back into contiguous columns expected by subsequent multiplications so we do not have to shuffle data across warp lanes—a hitless operation thanks to PTX `shfl.*`.

In terms of precision preservation we resort not just to per-tensor scaling (which suffers from extreme value slivers common in LLMs), but instead use two intertwined methods:

| Technique | How It Helps | Impact |
|-----------|--------------|--------|
| **Block quantization** | Store one scale per `(B_r × d)` or `(B_c × d)` subblock → reduces dynamic range amplification before multiply | ~0 RMSE boost on average when compared against whole-tensor scaling |
| **Incoherent processing** | Multiply both Q & K by a cheap random orthogonal matrix M before quantizing → spreads hot spots across subblocks → acts like “randomized weights” avoiding clipping catastrophic outliers | another ~30 % RMSE reduction on harsh tail scenarios |

The fusion-driven design means these adjustments add no measurable overhead—they piggyback cleanly onto existing permutation trips already required by data movement.
