\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 2: # 2. Large Language Models: Beyond Natural Language  

Large language models (LLMs) have transformed the landscape of artificial intelligence in recent years, moving far beyond the narrow confines of natural‑language understanding and generation. They bring to bear a deep repository of knowledge — acquired through training on massive corpora of text — that can be harnessed for a variety of downstream tasks, including those that involve structured, tabular data. This chapter surveys the historical evolution of LLMs, explains how their internal representations encode useful information, reviews early attempts to apply them to structured data, and clarifies the practical obstacles that remain when leveraging commercial LLMs through an API interface.

---

## 2.1 From RNNs to Transformers and GPT‑style Models  

The precursor of modern LLMs was the family of recurrent neural networks (RNNs). Classic RNNs suffered from vanishing gradients and struggled with long‑range dependencies, which limited their capacity to capture higher‑level semantics in language. The introduction of gated architectures — such as Long Short‑Term Memory (LSTM) units and Gated Recurrent Units (GRU) — alleviated some of these challenges but did not fully solve the problem.

The true breakthrough arrived in 2017 with the Transformer architecture introduced in “Attention Is All You Need.” Transformers dispensed with recurrence entirely, relying instead on self‑attention mechanisms that provided each token with a direct connection to every other token in a sequence. This allowed models to learn contextual relationships efficiently and with remarkable parallelizability on GPUs or TPUs.

Building on Transformers, researchers proposed GPT (Generative Pre‑trained Transformer) families that emphasized “causal” attention, ensuring that each token could only attend to earlier positions. The objective was plain language modeling: given a prefix \(x_{\leq t}\), predict the next token \(x_{t+1}\). This simple unsupervised objective yields rich internal representations because the model must learn syntax, semantics, facts, and even procedural knowledge from millions of sentences.

Subsequent iterations—GPT‑2, GPT‑3, GPT‑4—scaled the architecture dramatically while keeping the same core principle: large transformers trained on big datasets with a massive number of parameters. Their successes proved that sufficient capacity combined with “few‑shot” prompting could render powerful generalization without any architectural redesign or supervision for specific tasks.

## 2.2 Knowledge Representation in LLMs  

Given a prompt \(\mathbf{p}\), an LLM computes a distribution over possible next tokens through:
\[
P(x_{t+1} \mid x_{\leq t}) \propto \exp\bigl(\mathbf{h}_{t}\mathbf{W}\bigr),
\]
where \(\mathbf{h}_{t}\) is the hidden state at step \(t\). Though we observe only the final output probabilities or selected continuations, many internal properties can be inferred from model weights and activations:

| Property | Origin | Manifestation |
|----------|--------|---------------|
| **Semantic similarity** | Embedding learning | Tokens that are similar occupy proximate regions in vector space |
| **Association rules** | Co‑occurrence statistics | Certain phrases or facts are strongly correlated |
| **Common sense reasoning** | Pre‑training on encyclopedic text | Ability to complete causal chains (“If X then Y”) |
| **Domain knowledge** | Presence of specialized literature | Recognizes medical terminology or financial jargon |

These capabilities have been demonstrated empirically: prompting GPT‑3 for math problems reveals latent procedural knowledge; prompting GPT‑4 for medical case classification leverages its exposure to clinical narratives. Crucially, such knowledge can be extracted *without* fine‑tuning by feeding carefully engineered prompts—a technique known as *in‑context learning*.

## 2.3 Prior Works on LLMs for Structured Data  

While LLMs were conceived for sequential text data, researchers soon realized they could be repurposed for tabular data by serializing rows into text streams. Three notable early approaches illustrate this idea:

### 2.3.1 Lift  
Lift proposes encoding a row as a string that lists each column name followed by its value (“age is 42; income is $50K; smoker is Yes”), together with task instructions (“Predict whether individual will buy product”). The model then reads this formatted prompt and outputs a probability for each class—essentially performing inference directly within the LLM.

### 2.3.2 AnyPredict  
AnyPredict extends Lift by allowing any type of feature description (continuous, categorical). It supplies feature definitions explicitly (“age: integer; income: nominal”) so that the LLM can interpret operators correctly (e.g., “>” versus “equals”). AnyPredict also adopts *parameter‑efficient tuning* (LoRA), modifying only a small set of adapter weights rather than fine-tuning the entire transformer.

### 2.3.3 TabLLM  
TabLLM focuses on *prompt engineering*: it provides richer context by appending an external classifier’s prototypes or rule-based hints into the prompt ("Examples where people purchased/not purchased"). TabLLM utilizes *inference-time* chain-of-thought prompting and optionally IA3 fine-tuning to adapt to specific tabular datasets while preserving most of the base model’s parameters.

All three methods share one crucial limitation: during prediction they require sending every sample (or at least a serialized version thereof) to an LLM engine via an API call—often at $0$ compute cost but still incurring significant latency and monetary expense when scaled.

## 2.4 Practical Constraints: API access, prompt limits, computational cost  

Deploying LLMs at scale exposes several practical bottlenecks:

1. **API Latency**  
   Commercial APIs such as OpenAI’s bear an inherent round-trip latency of tens or hundreds of milliseconds per request due to network round-trips and server queuing. In low-latency settings—e.g., real-time medical triage—this adds untenable delays when every sample must be sent through an API call.

2. **Rubric-Based Quotas**  
   Providers build usage quotas around token counts rather than number of requests. A long prompt inflates cost since tokens are charged at a per-unit rate (e.g., $0\!/\!k$.00 per thousand tokens in GPT-4). A typical tabular prompt serializing hundreds of columns can easily exceed several thousand tokens.

3. **Prompt Length Limits**  
   Most models cap input tokens: GPT-3's context window is 4 k tokens while GPT-4 can handle up to 32 k tokens under certain subscription tiers. When features proliferate – e.g., high-dimensional biomedical datasets – serializing every column outstrips these limits unless one either truncates features aggressively or divides data across multiple calls.

4. **CPU/GPU Bottlenecks**  
   When local inference is required (some regulations forbid cloud-based inference), running a large transformer demands powerful GPUs or TPUs or extensive distributed inference frameworks – often inaccessible for small research labs or edge deployments.

5. **Model Update Constraints**  
   Some providers release `cutoff dates` after which newer training data are not incorporated automatically; also vendor APIs often do not expose model checkpoints for local fine-tuning or adaptation – hindering experiment reproduction or custom adjustments.

In summary, although LLMs carry rich prior knowledge useful for tabular learning, these pragmatic constraints motivate architectural strategies that decouple prediction from live model calls—such as using the LLM only during a feature-engineering phase and thereafter leveraging inexpensive downstream classifiers.
