\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### "Pingpong" scheduling: what barriers synchronize and why?
Question:
In the description of the overlapping GEMM–softmax pipeline, two warp groups are said to ping‑pong by swapping roles every iteration. The paper references `bar.sync` barriers but doesn’t detail which specific operations are preordered by them. Which WGMMA invocations must finish before the exponential operations begin, and how does this ordering avoid hazards if the compiler reorders instructions?
Answer:
**Answer**

The “ping‑pong” technique in FlashAttention‑3 is a *software pipeline* that interleaves two warp‑groups (WG1 and WG2).  
Each warp‑group issues the same set of instructions, but they are offset by one iteration:

* WG1:  **GEMM** (first WGMMA, `$S_{\text{cur}} = Q\cdot K^{2\,T}$`) → **softmax** → **GEMM** (second WGMMA, `$O \;+=\; P\cdot V$`)  
* WG2:  begins its own **GEMM** for the *next* block while WG1 is finishing the **softmax** of its current block.

A `bar.sync` placed before the start of a warp‑group’s loop ensures that

```
   WG1’s GEMM0   ($Q\cdot K_{j}^{T}$)  and  WG2’s GEMM1 ($Q\cdot K_{j+1}^{T}$)
```

complete in a guaranteed order. Thus the softmax of one block can be computed only after the antecedent matrix multiplication (`$S_{\text{cur}}$`) has finished, and the result of that softmax (`$\tilde{P}_{\text{cur}}$`) can be used by the following matrix multiplication (`$O \;+\!=$ $\tilde{P}_{\text{cur}}\cdot V_{j-1}$`) only after it too has completed. The `bar.sync` therefore enforces two *layers* of ordering:

1. **Between iterations within a warp‑group** – a later iteration may not start its first WGMMA until the previous iteration’s second WGMMA (`WGMMA2`) has finished and its registers have been written back.  
2. **Between the two warp‑groups** – WG2’s first WGMMA for block *j+1* may only begin after WG1’s first WGMMA for block *j* has been issued and committed, so that the shared‑memory buffer that holds `$K_j$` is still occupied when WG2 reads it.

In concrete terms, for an iteration `j` the following must hold before any instruction from the next iteration can start:

| operation | depends on | required barrier |
|-----------|-----------|-------------------|
| `$S_{\text{next}} = Q\cdot K_j^{T}$` (WGMMA1) | results of previous iteration’s second WGMMA (`$O \;+\!=$ $\tilde{P}_{\text{prev}}\cdot V_{j-2}$`) | bar.sync before WG2’s launch |
| `$\tilde{P}_{\text{next}} = \exp(S_{\text{next}} - m_{\text{new}})$` | completion of `S_next` | implicit guard inside softmax code |
| `$O \;+\!=$ $\tilde{P}_{\text{cur}}\cdot V_{j-1}$` (WGMMA2) | completion of `$\tilde{P}_{\text{cur}}$` (softmax of previous block) | implicit compile sequence |

These dependencies guarantee that:

* The *score matrix block* (`$S_{\text{cur}}$`) produced by the first WGMMA is fully available before the exponential is evaluated; otherwise we would be exponentiating uninitialized data.  
* The *softmax intermediate* (`$\tilde{P}_{\text{cur}}$`) is ready before it is multiplied by the corresponding value block (`$V_{j-1}$`); otherwise we would be feeding garbage into a Tensor Core kernel.

The compiler in NVCC could, in principle, reorder or fuse instructions across these boundaries. However, by explicitly emitting a `bar.sync` one can create a **global control dependency** that NVCC respects: it merely places instructions before or after a chip‑wide barrier but never removes or moves instructions that cross it. Because each warp‑group executes its own barrier region independently, no instruction from WG2 can slip ahead of WG1 past a scheduled barrier unless both reach it simultaneously—precisely what we need to keep the pipeline consistent.

Thus, when we say “WG1’s GEMMs must finish before WG2’s GEMMs begin”, we refer to two distinct barriers:

1. **Iteration boundary barrier** inside each warp‑group – ensures an intervening matrix multiply does not overlap with its own predecessor’s matrix multiply or with its own softmax.
2. **Ping‑pong barrier** between warp‑groups – ensures WG2 does not steal data from buffers still being consumed by WG1.

Because both barriers are explicit via CUDA's `bar.sync`, any aggressive compiler reordering cannot violate these constraints; the operations remain correctly serialized while still allowing asynchronous execution within each stage. This ordering is what makes ping‑pong pipelining safe and effective on Hopper GPUs.
