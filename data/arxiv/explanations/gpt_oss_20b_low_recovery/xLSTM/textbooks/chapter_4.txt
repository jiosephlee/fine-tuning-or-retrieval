Chapter 4: **Chapter 4 – Matrix Memory and the mLSTM**

The long‑standing reliance of LSTMs on a single scalar memory element has proven to be a bottleneck in modern large‑scale language modeling. Chapter 4 introduces the matrix‑valued memory cell that replaces the scalar with a full \(d\times d\) matrix. By doing so, the model can store entire key–value vectors directly in its memory and retrieve them using a single matrix–vector multiplication. This section explains why scalar memory is insufficient, derives the covariance update rule that allows the memory to accumulate key–value pairs, discusses how the memory is normalised and accessed, and shows how exponential gates are stabilised. Finally, we examine the parallel scan‑free formulation that makes the matrix‑LSTM trainable on current GPU hardware and analyse the trade‑off between memory capacity and computational cost.

---

### 4.1 Why Scalar Memory Limits Rare Token Representation

In an ordinary LSTM the memory at time step \(t\) is a single real value \(c_t\in\mathbb{R}\).  All information that the network wishes to remember must be compressed into this scalar.  When the vocabulary contains a wide range of token frequencies, such compression becomes problematic for two reasons:

1. **Poor discrimination for infrequent tokens.**  
   Rare tokens appear only a handful of times during training.  The network therefore has little opportunity to learn a robust scalar representation for these tokens.  They are inevitably mixed with frequent tokens in the scalar cell and lose signal strength.  Empirically, this causes a noticeable increase in perplexity for low‑frequency tokens (see the right panel of Figure 1).

2. **Limited context capacity.**  
   A single scalar memory cannot encode more than one distinct value at a time.  When a sequence contains an early token that needs to be remembered until a later position, the LSTM must purge the scalar before a new, unrelated token is processed.  Consequently, the network loses the ability to diferentially store multiple key–value pairs that coexist in a single sequence.

These shortcomings motivate a richer memory representation that can hold multiple key–value vectors simultaneously.  A matrix memory leads naturally to a covariance‑style update rule that accumulates outer products of key and value vectors, thereby constructing a latent space that can later be queried efficiently.

---

### 4.2 Deriving the Covariance Update Rule for Key–Value Storage

Suppose that at time step \(t\) the model produces a *key* vector \(\mathbf{k}_t\in\mathbb{R}^d\) and a corresponding *value* vector \(\mathbf{v}_t\in\mathbb{R}^d\).  The goal is to store the pair \((\mathbf{k}_t, \mathbf{v}_t)\) so that, at a later time \(t+\tau\), a *query* \(\mathbf{q}_{t+\tau}\) can retrieve \(\mathbf{v}_t\) through inner‑product matching with \(\mathbf{k}_t\).

A convenient way to accumulate such associations is to maintain a symmetric matrix memory \(\mathbf{C}_t\in\mathbb{R}^{d\times d}\) and update it by adding the outer product of the current value and key:

\[
\mathbf{C}_t \;=\;\mathbf{C}_{t-1}\;+\;\mathbf{v}_t\,\mathbf{k}_t^{\!\top}\;.
\tag{4.1}
\]

Equation 4.1 is precisely the covariance update used in Bidirectional Associative Memories (BAMs) and Fast‑Weight Programmers.  The update is linear in the number of stored pairs; after \(T\) updates the memory becomes a sum of \(T\) outer products.

The intuition is that the columns of \(\mathbf{C}_t\) become weighted linear combinations of stored values.  If we query with \(\mathbf{q}\) that is close to a stored key \(\mathbf{k}_i\), the product \(\mathbf{C}_t \mathbf{q}\) will resemble \(\mathbf{v}_i\), because the term \(\mathbf{v}_i\,\mathbf{k}_i^{\!\top}\mathbf{q}\) dominates the sum.  All other stored pairs contribute terms that are typically looser matches.

The choice of an outer product rather than an element‑wise product ensures *linear separability*: the dot product between a query and a key acts as a *retrieval weight* for the corresponding value.  This property is formally optimal under a binary retrieval objective, as argued in Sejnowski (1977) and Dayan (1991).  Thus, the covariance rule provides a principled mechanism to store arbitrary key–value pairs.

### 4.3 Normalising and Retrieving from a Matrix Memory

While adding raw outer products can lead to unbounded growth of the matrix norm, two techniques keep the size of \(\mathbf{C}_t\) under control:

1. **Normaliser State.**  
   The matrix memory is accompanied by a vector normaliser \(\mathbf{n}_t\in\mathbb{R}^d\) that aggregates the contribution of the keys weighted by the input gate and future forget gates:

   \[
   \mathbf{n}_t \;=\;f_t\,\mathbf{n}_{t-1}\;+\;i_t\,\mathbf{k}_t\;.
   \tag{4.2}
   \]

   Here, \(i_t\) and \(f_t\) are the learning‑rate and decay‑rate gates, respectively (see Section 4.4).  The normaliser vector records the total “weight” of the stored keys up to time \(t\).

2. **Query‑Normalized Retrieval.**  
   The hidden state is obtained by applying the memory to the query and normalising by the *absolute* dot product \(|\mathbf{n}_t^{\!\top}\mathbf{q}_t|\) (clipped to a minimum of 1, see Equation 4.3):

   \[
   \tilde{\mathbf{h}}_t \;=\;\frac{\mathbf{C}_t\,\mathbf{q}_t}
   {\max\!\left(\,|\mathbf{n}_t^{\!\top}\mathbf{q}_t|,\; 1\,\right)}\;,
   \qquad
   \mathbf{h}_t \;=\;\mathbf{o}_t \odot \tilde{\mathbf{h}}_t\;.
   \tag{4.3}
   \]

   The denominator scales the retrieved vector relative to the amount of memory content that is *relevant* to the current query.  By using the absolute value, the network remains unaffected by the sign of the dot product, and the lower bound of 1 guarantees numerical stability even when the normaliser and query are nearly orthogonal.

The full set of forward equations for the mLSTM is summarised in Equation 4.4.  Every variable is standard notation: \(\tilde{\cdot}\) denotes a pre‑activation linear layer, \(\mathbf{W}_{\mathbf{o}}\) is a matrix output gate, and the gates \(i_t\), \(f_t\), \(o_t\) are defined in Equations 4.5–4.7.  The query, key, and value projections are \( \mathbf{W}_q, \mathbf{W}_k, \mathbf{W}_v\), respectively, and are modulated by a (optional) layer‑norm.



### 4.4 Stabilisation of Exponential Gates in the mLSTM

The *input* and *forget* gates of the mLSTM are exponentials of linear functions of the input:

\[
i_t \;=\;\exp\!\bigl(\tilde{i}_t\bigr)\,,\qquad
f_t \;=\;\sigma\!\bigl(\tilde{f}_t\bigr)\;\text{or}\;\exp\!\bigl(\tilde{f}_t\bigr)\;.
\tag{4.5}
\]

Exponential activations are powerful because they allow the gates to grow or decay *multiplicatively*, matching the intuition behind add‑and‑forget mechanisms.  However, in practice, large values of \(\tilde{i}_t\) or \(\tilde{f}_t\) can cause overflow or underflow, destabilising both forward activations and backward gradients.

To resolve this, the mLSTM uses the *stabiliser state* \(m_t\) defined as

\[
m_t \;=\;\max\!\bigl(\,\log(f_t)\,+\,m_{t-1}\;,\;\log(i_t)\,\bigr)\;,
\tag{4.6}
\]

which keeps track of the current log‑scale of the gates.  The gates are then renormalised as

\[
i'_t \;=\;\exp\!\bigl(\log(i_t)-m_t\bigr)
\;=\;\exp\!\bigl(\tilde{i}_t-m_t\bigr)\;,\qquad
f'_t \;=\;\exp\!\bigl(\log(f_t)+m_{t-1}-m_t\bigr)\;.
\tag{4.7}
\]

Replacing \(i_t\) with \(i'_t\) and \(f_t\) with \(f'_t\) in the forward updates does **not** alter the network’s output or the gradients, because the normaliser \(\mathbf{n}_t\) and the hidden state \(\tilde{\mathbf{h}}_t\) undergo the same multiplicative scaling.  Consequently, the stabilisation preserves the mathematical properties of the original equations while keeping the numerics within a safe range.

### 4.5 Parallelisation of the mLSTM: Scan‑Free Formulation and GPU Considerations

A classic RNN needs to perform a *scan* over the sequence: the memory at time \(t\) depends on the memory at time \(t-1\).  For the mLSTM, the scan is captured by Equations 4.1 and 4.2.  Although the recurrence is linear, modern GPU architectures do not execute scans efficiently: a naive implementation would launch a kernel for each time step, forcing the device to wait for the result of the previous step before proceeding.

Fortunately, the linearity of the mLSTM update means that we can eliminate the costly serial scan and evaluate the entire sequence *in one batch*.  The key observation is that the memory \(\mathbf{C}_t\) can be expressed solely in terms of the *cumulative* product of forget gates:

\[
\mathbf{C}_t \;=\;\sum_{s=1}^{t} 
\Bigl(\prod_{r=s+1}^{t} f_r\Bigr)\;
i_s\,\mathbf{v}_s\,\mathbf{k}_s^{\!\top}\;.
\tag{4.8}
\]

An analogous expression holds for the normaliser \(\mathbf{n}_t\).  From this representation we can pre‑compute the cumulative decay products \(\prod_{r=s+1}^{t} f_r\) as a cumulative product along the sequence.  In PyTorch, the cumprod operation is highly optimised for GPUs and runs fully in parallel.  Once the gating products are available, the outer‑product sum can be calculated as a batched matrix multiplication, again exploiting GPU parallelism.

The resulting *scan‑free* algorithm has the following computational profile:

- **Memory complexity**: \(O(d^2)\) for the matrix \(\mathbf{C}\) and \(O(d)\) for the normaliser.
- **Time complexity**: \(O(T\times d^2)\) for a sequence of length \(T\), but all matrix multiplications happen in parallel; no serial dependencies remain.
- **Hardware utilisation**: The algorithm maps cleanly onto GPU tensor cores because the main operations are batched matrix additions and multiplications.

In toy implementations, the scan‑free mLSTM is roughly *4–8× faster* than a naive scan‑based implementation, and in practice it matches the throughput of FlashAttention‑style libraries when run on the same hardware.

### 4.6 Assessing the Trade‑off: Memory Capacity vs. Computation Cost

The matrix memory yields a dramatic increase in expressive power, but it comes with higher computational demands:

| Method | Parameter count | Memory size (per time step) | Computational cost |
|--------|-----------------|-----------------------------|---------------------|
| Scalar LSTM | \(O(d)\) | \(O(1)\) | \(O(d)\) matrix–vector multiplies |
| mLSTM | \(O(d^2)\) | \(O(d^2)\) | \(O(d^2)\) matrix–vector multiplies per step (but parallelisable) |

For modest hidden sizes (\(d \approx 128\)), the matrix memory adds only a small percentage to the parameter count but doubles the per‑step FLOPs.  When scaling to large language models (\(d\in[512, 2048]\)), the \(d^2\) term becomes significant.  Several practical strategies mitigate this cost:

1. **Reducing the number of stacked mLSTM blocks.**  
   Experiments show that a mix of mLSTM and sLSTM blocks (e.g. xLSTM[7:1]) balances capacity and speed, achieving state‑of‑the‑art perplexities while keeping training wall‑clock times comparable to Transformers.

2. **Leveraging mixed‑precision.**  
   The matrix operations are highly amenable to FP16 or BF16 without catastrophic accuracy loss.

3. **Caching.**  
   During inference, the matrix memory can be cached and reused across calls to the same context, reducing redundant recomputation.

4. **Sparse approximations.**  
   For future work, one could sparsify \(\mathbf{C}\) by thresholding small entries or by limiting the number of outer products that contribute to the sum for a given query.

In the end, the matrix memory delivers *Apparent* state‑tracking capabilities that were previously exclusive to Transformer‑style cross‑attention.  The mLSTM’s ability to retain multiple key–value pairs, to retrieve them through a single matrix multiplication, and to do all of this while remaining fully differentiable makes it a compelling building block for large language models.

---

### Summary

The mLSTM reformulates the classical hidden‑state recurrence by replacing a scalar memory with a full matrix that stores key–value associations via a covariance update.  The derivation of this update follows directly from associative memory theory and yields an architecture that is both theoretically sound and practically efficient.  Normalisation by a learned vector guarantees numerical stability and retrieves the desired value vector in a query‑normalised manner.  Exponential gates, when stabilised by a carefully designed log‑scale compensator, allow the model to learn highly dynamic learning rates and decays.  Thanks to the linearity of the recurrence, a scan‑free formulation turns the otherwise sequential operation into a fully parallel GPU workload.  While the matrix memory increases computational cost, the gains in memory capacity and the resulting performance improvements on challenging language modelling benchmarks confirm that the trade‑off is both justified and fertile ground for further optimisation.
