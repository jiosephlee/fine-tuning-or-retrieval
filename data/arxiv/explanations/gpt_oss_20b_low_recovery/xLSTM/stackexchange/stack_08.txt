\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### Why is mLSTM considered to have constant memory complexity with sequence length?
Question:
The authors claim that the memory of mLSTM is linear in context length while being constant with respect to sequence length. Since C_t is a d×d matrix independent of t, does this mean that each time step requires O(d^2) operations but no extra storage per time‑step? How does this compare to Transformers where the KV cache grows linearly with sequence length?
Answer:
**Answer**

The claim “mLSTM has *constant* memory complexity with respect to the sequence length” refers to the amount of *parameter‑ and state‑memory* that the model must keep while running a forward pass on a long input.  
In a transformer that lives in the *attention” layer, the key and value tensors that are produced at each time step are stored so that later queries can attend to them.  
Formally, for a context of length $T$ and a hidden dimension $d$, a transformer keeps

\[
K,\;V \in \mathbb{R}^{T \times d}\,,
\]

which consumes $O(T\,d)$ space and grows linearly with $T$.

---

### What mLSTM stores

An mLSTM cell is defined by the recurrence

\[
\mathbf{C}_t \;=\; f_t\,\mathbf{C}_{t-1}\;+\;i_t\,\mathbf{v}_t\,\mathbf{k}_t^\top ,
\qquad
\mathbf{n}_t \;=\; f_t\,\mathbf{n}_{t-1}\;+\;i_t\,\mathbf{k}_t ,
\]

with a *single matrix* $\mathbf{C}_t \in \mathbb{R}^{d\times d}$ and a *single vector* $\mathbf{n}_t \in \mathbb{R}^{d}$ that evolve in time.  
Importantly, $\mathbf{C}_t$ does **not** depend on the current sequence position $t$; it is a *persistent memory* that is overwritten in place at every step.  The update involves a rank‑one outer product $\mathbf{v}_t\mathbf{k}_t^\top$, but no new per‑step slots are stored.  Thus the amount of auxiliary data that the network has to keep—its parameter tensors plus the two auxiliary tensors $\mathbf{C}_t$ and $\mathbf{n}_t$—is independent of $T$.

Consequently, the *memory footprint* of a batch processing an input of length $T$ is

\[
\underbrace{O(d^2)}_{\mathbf{C}_t} \;+\; \underbrace{O(d)}_{\mathbf{n}_t} \;+\; \text{constant}\;=\;O(d^2),
\]

which is independent of $T$.  The same holds for the hidden state $\mathbf{h}_t$ that is produced at each step; it is likewise a vector of dimension $d$ and does not increase with the context length.

---

### Operations per step

Each time step does require $O(d^2)$ arithmetic: multiplying a $d\times d$ matrix by a $d$‑dimensional query vector for retrieval, and updating $\mathbf{C}_t$ with a rank‑one outer product.  
These operations are *parallelizable* across the batch and across time steps (once the recurrence is unrolled), which is why the wall‑clock cost grows only linearly with the length in practice, whereas memory does not.

In contrast, a transformer’s attention has $O(T^2 d)$ FLOPs per layer and $O(Td)$ stored key/value tensors that grow linearly, leading to both a memory and time quadratic dependence on context length.

---

### Intuition via “fast weights”

The matrix memory of mLSTM is essentially a *fast‑weight* system (cf. Sejnowski 1977).  The outer‑product update is analogous to adding a new pair \((\mathbf{k}_t,\mathbf{v}_t)\) to a fast table that can be interrogated at any later time by $\mathbf{C}_t\mathbf{q}_t$.  Because the fast table is a dense $d\times d$ matrix, its size does not depend on how many keys you inserted; we simply overwrite the same matrix with a new linear combination of all previous updates.  This explains why the memory does not scale with sequence length.

---

### Summary

- **Transformer KV cache**: $O(Td)$ memory, $O(T^2d)$ FLOPs per layer.  
- **mLSTM matrix memory**: $O(d^2)$ memory, $O(d^2)$ FLOPs per step, *constant* with respect to $T$; the whole recurrence can be executed in parallel.  

Thus the paper’s statement that mLSTM has constant memory complexity with respect to the sequence length is correct: the auxiliary tensors that must be kept alive while processing a long sequence do not grow with the length of the sequence, unlike the token‑level KV cache of transformers.
