# Optimizing xLSTM Inference: From CUDA Kernels to High Throughput

High‑performance inference is as important for a new model as its training performance.  
For the xLSTM family, whose core innovations are exponential gating and a novel matrix‑memory, the authors had to address two main engineering challenges:

1. **Sequential dependence in sLSTM blocks** – the hidden‑to‑hidden mixing forces a scan through the time‑steps, which is the main bottleneck for real‑time inference.  
2. **Large \(d\times d\) matrix operations in mLSTM** – the covariance‑style memory update and retrieval involve full‑matrix multiplications, which can be expensive on commodity GPUs if not properly parallelized.

Below we walk through the problem space and the key solutions presented in the paper.

---

## 1. The Inference Bottleneck in xLSTM

### 1.1 sLSTM: Memory Mixing vs. Parallelism  
Standard LSTM cells mix the previous hidden state into the current gate computations.  
In the sLSTM variant this mixing is **within each head** and is weighted by exponential gates. The recurrence requires a left‑to‑right scan:

\[
h_t = o_t \odot \frac{c_t}{n_t}\;,\qquad 
c_t = f_t c_{t-1} + i_t z_t
\]

Because each time step depends on the previous one, a naïve implementation must run one scan per generation step. On a GPU this translates to a performance penalty that scales linearly with the context length.

### 1.2 mLSTM: Large Matrix Ops  
The matrix memory \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\) is updated by

\[
\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t\, \mathbf{v}_t \mathbf{k}_t^\top .
\]

Both the update and the read operation \(\tilde{h}_t = \mathbf{C}_t \mathbf{q}_t / \max\{|\mathbf{n}_t^\top\mathbf{q}_t|,1\}\) are \(O(d^2)\). While parallelizable in principle, early implementations exposed a 4‑fold slowdown compared to FlashAttention‑style kernels because all matrix operations were executed in a single custom kernel without exploiting lower‑precision math or shared memory.

---

## 2. CUDA Optimizations for sLSTM

To reduce the scan latency, the authors crafted a **register‑level GPU kernel** that respects the dependence order but keeps the per‑time‑step work minimal.

| Design Decision | Why It Helps |
|-----------------|--------------|
| **Lane‑wise scan** | The kernel processes all time‑steps in a warp, reusing registers for \(c_{t-1}\) and \(n_{t-1}\). This keeps the time‑step pipeline fully occupied. |
| **Exponential gating stabilization** | The stabilizer \(m_t\) is computed as a simple max logarithm, staying in registers and avoiding expensive `log`/`exp` calls. |
| **Memory‑local combiners** | All gate expressions \(\tilde{i}_t, \tilde{f}_t, \tilde{o}_t\) are fused into a single launch to reduce global memory traffic. |
| **Batch‑wise fusion** | When generating multiple sequences in parallel, the kernel can bundle them into a single kernel launch, cutting launch overhead by up to 50 %. |

The net result is a sLSTM inference kernel that is *less than two times* slower than the parallel mLSTM kernel, a significant win given that sLSTM blocks often dominate the deep xLSTM stack.

---

## 3. Parallelizing mLSTM in the CUDA Realm

The mLSTM matrix memory can be updated and queried in parallel, leading to a **scan‑free inference mode**:

1. **Pre‑compute all keys, values, and queries** – each token is mapped to \((\mathbf{k}_t, \mathbf{v}_t, \mathbf{q}_t)\) in a single forward pass.  
2. **Parallel accumulation of \(\mathbf{C}\)** – using a *reduction* pattern, each token contributes \(\mathbf{v}_t \mathbf{k}_t^\top\) weighted by its input gate \(i_t\).  
3. **Batch‑wise matrix‑vector products** – the read step \(\tilde{h}_t = \mathbf{C}\mathbf{q}_t\) is performed via a batched GEMM, taking full advantage of highly‑optimized cuBLAS kernels.

The authors avoided a custom kernel for the matrix construction; instead, they leveraged **cuBLAS’s batched matrix multiplication** and a few lightweight element‑wise ops. By keeping all tensors in **mixed precision (bf16)** they achieved a speed‑up of ~20 % over full‑precision versions while maintaining numerical stability thanks to the stabilizer state \(m_t\).

---

## 4. Resulting Throughput Numbers

The paper reports the following key metrics for a 1.3 B‑parameter xLSTM on an NVIDIA A100:

| Model | Generation Latency (ms/step) | Throughput (tokens/sec) |
|-------|-----------------------------|------------------------|
| xLSTM (sLSTM + mLSTM mix) | **≈ 6 ms** | **≈ 170 k/tokens** |
| Mamba (SSM) | **≈ 8 ms** | **≈ 125 k** |
| RWKV‑4 (RNN) | **≈ 7 ms** | **≈ 140 k** |
| Llama‑7B (Transformer) | **≈ 35 ms** | **≈ 30 k** |

The linear scaling of xLSTM’s latency with respect to context length is a direct consequence of the scan‑free design for mLSTM and the efficient per‑step kernel for sLSTM. In contrast, the quadratic cost of the Transformer attention mechanism causes the Llama baseline to grow rapidly as the context expands.

---

## 5. Take‑Away: Working Recurrent vs. Transformer

* If you need **constant‑time per step** and **high batch throughput**, xLSTM’s mixed gate & matrix memory approach is a compelling alternative to Transformers, especially on GPUs where GPU‑friendly matrix ops dominate performance.  
* For **very long sequences** (tens of thousands of tokens) the sLSTM’s sequential scan can become a bottleneck; moving more blocks to the parallel mLSTM flavor (e.g., xLSTM[7:1] vs. xLSTM[1:0]) can offset this.  
* Because the matrix memory is independent of sequence length, **cache‑efficiency** is naturally higher than token‑wise key‑value storage in Transformers, leading to *higher decoding throughput* when batching multiple prompts.

---

## 6. Future Directions

The authors anticipate that **FlashAttention‑style kernels** for mLSTM could shave another 10–15 % off latency, while a fully **SIMD‑friendly sLSTM** implementation could bring scan overhead below 10 ms/step on consumer GPUs. Combined with hyperparameter tuning and deeper architectural search, xLSTM has the potential to match or surpass transformer‑based LLMs in both training *and* inference regimes.

---

### TL;DR

- **Challenge**: sLSTM scanning and mLSTM matrix ops hurt inference speed.  
- **Solution**: Register‑level scan‑efficient sLSTM kernel + batched cuBLAS for mLSTM.  
- **Result**: ~6 ms/step and > 170 k tokens/sec on A100, outpacing large transformers in throughput.  
- **Implication**: xLSTM offers a practical, high‑performance alternative for large‑scale language modeling and deployment.
