# Dynamic Patching Wins: How Entropy Guides Compute Allocation  

Large language models (LLMs) have spent the last decade beating each other on the **token‑level**. Tokens are produced by a tokenizer that turns raw text bytes into a fixed vocabulary, and the transformer operates on these tokens just like on any other language model. However, tokenization has always been a heuristic step: it compresses data with static rules that do not always match the *information density* of what the model actually needs to predict.  

Enter **Byte Latent Transformer** (BLT) and its sister technique, **entropy patching**. Rather than treating every character or sub‑word as equally hard, entropy patching lets the model decide *on the fly* how many bytes it should bundle together into a computation step—solving two problems at once:

1. **Dynamic compute allocation** – smoothen out the uneven difficulty of predicting different parts of a sentence.
2. **Inference efficiency** – reduce the number of transformer steps without sacrificing accuracy.

Below we break down how this works, why it matters, and how it stacks up against static patching or classic tokenization.

---

## 1. The Problem With Static Patching  

Traditional “byte‑level” models use **fixed‑stride patching**: split the byte stream into chunks of size \(k\) (for example 4 bytes or 6 bytes). This is simple to implement and makes training easy, but it has major shortcomings:

| Issue | Description |
|-------|-------------|
| **Uneven work** | A single 4‑byte span may contain just a few spaces (easy to predict), or an enzyme name (hard to predict). Every patch gets the same amount of attention‑based work regardless of its “entropy”. |
| **Poor efficiency** | Long patches save compute at inference time—fewer transformer steps—but then force the model to chew through probably irrelevant context for that one step. |
| **Rigid size trade‑off** | Tokenizers make you trade “token size” for “embedding size”; you cannot arbitrarily enlarge patches without also expanding costly projection layers. |

An *entropy‑aware* method sidesteps all of this.

---

## 2. What Is Entropy Patch­ing?  

At its core, entropy patching needs two components:

1. **A small byte‑language model** (the “entropy model”) trained on the same data as BLT but only 100–200 M parameters.
2. **A dynamic threshold rule** that looks at each upcoming byte’s predicted *next‑byte entropy*.

### 2.1 Computing Per‑Byte Entropy

For every position \(i\) in a training sequence \(\mathbf{x}\), we ask: if we had already seen bytes \(\mathbf{x}_{<i}\), how uncertain would a tiny language model be about \(x_i\)?

\[
H(x_i) \;=\; -\sum_{v \in \mathcal{V}} p_e(x_i=v \mid \mathbf{x}_{<i})\;\log p_e(x_i=v \mid \mathbf{x}_{<i})
\]

Here:
- \(\mathcal{V}\) = all 256 byte values,
- \(p_e\) = distribution output by our small entropy LM.

The larger \(H(x_i)\), the more *surprise* we expect for that byte.

### 2.2 Defining Patch Boundaries

We can cut a new patch when:

- The next‑byte entropy is *above a global threshold* (\(H > \theta_g\)),
- Or when it *increases relative to the previous byte* (\(H_t - H_{t-1} > \theta_r\)).

Both criteria are easy to evaluate during data loading and are incremental: they never look ahead in the sequence, so they can be applied online in training or inference.

### 2.3 Why It Works

- **Synchronization with complexity:** High‑entropy zones—like beginnings of words or clause boundaries—become their own patches; low‑entropy stretches (e.g., repeated code patterns) get fused into longer patches.
- **Model depth savings:** The globally trained latent transformer sees fewer steps when most of the data is “easy”, thus spending more capacity on truly hard parts.
- **Flexibility:** Patch size is no longer tied to a pre‑defined vocabulary; we can grow it while keeping inference cost fixed.

---

## 3. Going From Bytes to Patches: BLT’s Encoder

The BLT architecture keeps two lightweight modules:

1. **Local Encoder (\(\mathcal{E}\))** – turns every raw byte into an embedding and pools them into a latent patch representation.
2. **Global Latent Transformer (\(\mathcal{G}\))** – processes one token‑like object per patch.

Cross‑attention bridges them: after each encoder layer we pool based on those dynamic patches, feed them into \(\mathcal{G}\), then decode back via a local decoder (\(\mathcal{D}\)). Because encoder layers are shallow (\(<3\) layers), their cost scales with *bytes* per se, not with total sequence length.

---

## 4. Efficiency Gains in Numbers  

In our experiments:

| Patch Size | Avg Training Flops per Byte | Bits‑Per‑Byte (BPB) | Inference Flop Savings vs Tokenizer |
|------------|-----------------------------|---------------------|------------------------------------|
| Fixed 4 B   | Baseline                     | ~1.30               | —                                  |
| Entropy ~4–5 B | Similar                         | ~1.29               | ~15 %                              |
| Entropy 8 B   | Slightly higher due to fewer steps | ~1.25               | ~50 %                              |

- **Training‐time:** Smaller patches mean more steps but less costly each step because they pass through fewer neurons in the global transformer.
- **Inference‐time:** Larger entropy patches cut down latency dramatically because each global step covers more bytes—up to half the FLOPs compared with token models while keeping overall accuracy on par or better.

Hence, entropy patching blends dynamic computation allocation with hardware efficiency.

---

## 5. Comparison with Traditional Tokenization  

Tokenizers pick byte groupings that depend only on surface statistics (e.g., BPE = Byte Pair Encoding). These rules do not consider *contextual uncertainty*: they treat every token as equal even if one part of your sentence is trivial (“and”) while another (“intellectual property law”) requires deep inference.

Key contrasts:

| Feature          | Tokenizer + Fixed Tokens   | Entropy Patching + BLT      |
|------------------|----------------------------|-----------------------------|
| Vocabulary Size  | Fixed & pre‑determined     | No fixed vocab – dynamic    |
| Padding          | Per–token input             | Pad at patch level          |
| Compute per step | Deterministic              | Data-dependent              |
| Inference FLOPs  | Increases linearly          | Still linear but *smaller slope* |
| Robustness       | Sensitive to malformed input        | More robust due to raw bytes     |

Because BLT stays true to raw bytes and lets compute flow where needed, it naturally shrinks unnecessary overheads and delivers superior robustness against noisy inputs (e.g., typos, code obfuscation).

---

## 6. Practical Takeaways for Engineers  

- **Patch Size Tuning Is Easy:** Choose a target average patch size and calibrate your entropy threshold accordingly; no need to rebuild vocabularies.
- **Pipeline Integration:** You only need an additional lightweight preprocessing step for patching; everything else uses standard transformer libraries.
- **Cross-Attention Is Optional Yet Powerful:** Adding cross-attention between local encoder outputs and global patches can yield ~0.3 BPB improvements—especially at larger scales in adversarial domains like code or scientific text.
- **No Trade-Off Between Model Size & Efficiency:** You can inflate both parameters and patch length while keeping inference FLOPs constant—an unheard-of scaling dimension!

---

## 7. Looking Ahead  

Entropy patching opens avenues beyond LLMs:

- Text summarization where long passages require few model steps,
- Low‐resource languages where long tails dominate,
- Real‐time applications demanding low latency without heavy tokenization pipelines.

Future work might learn an end‑to‑end boundary predictor or combine multiple entropy models (e.g., linguistic rank vs statistical), further refining how we allocate compute based on context complexity.

---

### TL;DR  
Entropy patching gives byte‐level LLMs like BLT an elegant way to group inputs by *predictive difficulty*, leading directly to better parameter efficiency, lower inference FLOPs, and stronger robustness against noisy text—all without tightening ourselves into any fixed vocabulary!
