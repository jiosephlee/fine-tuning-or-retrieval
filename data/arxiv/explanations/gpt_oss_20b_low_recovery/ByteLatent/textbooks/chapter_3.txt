\title{A Textbook about the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

Chapter 3: # 3. The Byte Latent Transformer Architecture

Large language models today are typically built around three key ingredients: a tokenization step that reduces raw text to a compact sequence of sub‑word units, an autoregressive Transformer that learns to predict the next unit, and a generation step that decodes model outputs back into interpretable text.  The Byte Latent Transformer (\textsc{BLT}) eschews tokenization entirely and replaces it with a three‑part architecture that operates directly on the raw byte stream.  Three components cooperate in a tight loop: (1) a **global latent transformer** that acts on compact “patch” representations, (2) a **local encoder** that compresses contiguous bytes into these patch representations, and (3) a **local decoder** that expands patch representations back into bytes.  Both the encoder and decoder are lightweight, low‑parameter transformers that provide the “morphing” interface between the raw byte domain and the latent domain.  The whole system is driven by a **cross‑attention** mechanism that selectively pools information from every byte into its owning patch, while respecting patch boundaries.  Below, we unpack each of these modules in detail, describing how they fit together, the motivations behind each design choice, and the mathematics that governs their operation.

---

## Global Latent Transformer

### Architecture

The global model, denoted \(\mathcal{G}\), is the heavy‑weight backbone of \textsc{BLT}.  For a model with \(l_{\mathcal{G}}\) layers and hidden size \(h_{\mathcal{G}}\), \(\mathcal{G}\) is a standard autonomous transformer: each layer contains a multi‑head self‑attention block followed by a feed‑forward network (FFN).  Unlike conventional token‑based Transformers that process every token in a single step, \(\mathcal{G}\) processes one **patch** per step, where a patch is a contiguous group of one or more bytes that have been collapsed into a single latent vector \(p_j \in \mathbb{R}^{h_{\mathcal{G}}}\).  Consequently, the number of Transformer steps required to encode a document is the number of patches \(m\), typically far smaller than the number of raw bytes \(n\).

### Block‑Causal Masking

\(\mathcal{G}\) applies a **block‑causal** attention mask.  Consider a sequence of \(m\) patches, \(\{p_1,\dots,p_m\}\).  In layer \(l\) of \(\mathcal{G}\), the attention matrix \(A^{(l)}\) has an element
\[
A^{(l)}_{j,k} = 
\begin{cases}
1, & k \le j\\
0, & k > j
\end{cases}
\]
meaning that patch \(p_j\) may attend to any patch \(p_k\) that precedes or coincides with it, but never to future patches.  This enforces autoregressive behaviour at the patch level—the model can only use past patches to predict the current patch.

### Compute Allocation

By controlling where patches begin—through an entropy‑driven segmentation of the byte stream—\(\mathcal{G}\) receives **dynamic compute allocation**.  A low‑entropy byte (e.g., the second or third character of a word) can be merged into the same patch as its predecessors, so \(\mathcal{G}\) processes it for free.  A high‑entropy byte (e.g., the first character after a space) triggers a new patch, incurring the full cost of a transformer step.  Because the global transformer dominates the flop budget, the *average patch size* is a critical lever: larger patches reduce the number of global steps, freeing FLOPs that can be re‑used either to increase model depth or size, or to devote them to the lightweight encoder/decoder.

## Local Encoder

### Purpose and Design

The encoder \(\mathcal{E}\) is tasked with **compressing the raw byte stream into latent patch vectors**.  Its design must trade off freshness of byte‑level information against computational efficiency.  \(\mathcal{E}\) is a low‑parameter transformer of depth \(l_{\mathcal{E}}\) (typically 1–3 layers) and hidden size \(h_{\mathcal{E}}\) (roughly \(h_{\mathcal{G}}/2\)).  The encoder processes the byte sequence in a fixed sliding window of width \(w_{\mathcal{E}}\) (e.g. 512 bytes).  Within each window, a standard transformer self‑attention works on the byte embeddings, but the attention mask is **local block causal**: each byte attends only to the previous \(w_{\mathcal{E}}\) bytes—so the encoder never has a global view of the document.

### Byte Embeddings and Context Augmentation

Every byte \(b_i \in \{0,\dots,255\}\) is mapped to an embedding vector
\[
x_i \in \mathbb{R}^{256\times h_{\mathcal{E}}}.
\]
To give the encoder richer context and tile it across multiple contiguous bytes, \textsc{BLT} augments each byte embedding with fine‑grained \(n\)-gram context through **hash‑n‑gram embeddings** (discussed in the next section).  The augmented embedding is
\[
e_i = x_i + \sum_{n=3}^8 E^{\text{hash}}_n\bigl(\text{Hash}\bigl(g_{i,n}\bigr)\bigr),
\]
where \(g_{i,n} = \{b_{i-n+1},\dots,b_i\}\), the hash function is a fast rolling polynomial hash, and \(E^{\text{hash}}_n\) is a small embedding table for n‑grams of size \(n\).

### Cross‑Attention to Form Patches

After several layers of byte‑level self‑attention, \(\mathcal{E}\) performs a **cross‑attention** step that pools byte representations into their owning patch.  Suppose patch \(p_j\) contains indices \(\{i_{j,1},\dots,i_{j,k_j}\}\).  The cross‑attention operates as follows:

1. **Query Initialization**.  
   For each patch, a query vector is initialized by “max‑pooling” the byte representations in the patch:
   \[
   Q_{0,j} = \text{maxPool}\bigl(\{h_{l_{\mathcal{E}},i}\}_{i \in \text{patch } j}\bigr).
   \]
   A linear projection \(\mathcal{E}_C : \mathbb{R}^{h_{\mathcal{E}}}\to \mathbb{R}^{h_{\mathcal{G}}\times U_{\mathcal{E}}}\) expands the query into multiple heads.

2. **Multi‑head Attention**.  
   For layer \(\ell\) of cross‑attention:
   \[
   \begin{aligned}
   Q_j^\ell &= W_q\bigl(P_{\ell-1,j}\bigr),\\
   K_i^\ell &= W_k\bigl(h_{l_{\mathcal{E}},i}\bigr),\\
   V_i^\ell &= W_v\bigl(h_{l_{\mathcal{E}},i}\bigr),\\
   P_\ell &= P_{\ell-1} + W_o\Bigl(\operatorname{softmax}\!\bigl(\frac{Q^\ell K^{\ell\!T}}{\sqrt{d_k}}\bigr)V^\ell\Bigr),
   \end{aligned}
   \]
   where the softmax is masked so that \(Q_j^\ell\) can attend only to keys/values whose indices lie within patch \(p_j\).  This guarantees **patch‑local pooling**: bytes outside the patch do not influence the patch representation.

3. **Aggregation**.  
   After the final cross‑attention layer, the patch representation is obtained by concatenating the multi‑head outputs and projecting back to dimension \(h_{\mathcal{G}}\).  This vector \(p_j\) is the input to \(\mathcal{G}\).

Through cross‑attention, the encoder distills a variable‑length byte group into a fixed‑size latent vector, while still being receptive to byte‑level context thanks to the preceding self‑attention layers.

## Local Decoder

### Overview

The decoder \(\mathcal{D}\) performs the inverse operation: it takes the global patch representations \(o_j\) produced by \(\mathcal{G}\), and emits a concrete byte sequence.  Like the encoder, \(\mathcal{D}\) is lightweight and processes the byte dimensions after an initial cross‑attention that brings the latent context into the byte space.

### Cross‑Attention (Decoder Side)

Since we want to generate \emph{bytes} conditioned on the patch vectors, the decoder’s cross‑attention is **reverse‑valued** relative to the encoder: **bytes are queries, patches are keys/values**.

1. **Query Initialization**.  
   Byte representations \(h_{l_{\mathcal{E}}}\) from the encoder’s final layer are copied into \(D_0\).

2. **Attention**.  
   For layer \(\ell\):
   \[
   \begin{aligned}
   Q_i^\ell &= W_q\bigl(D_{\ell-1,i}\bigr),\\
   K_j^\ell &= W_k\bigl(\mathcal{D}_C(o_j)\bigr),\\
   V_j^\ell &= W_v\bigl(\mathcal{D}_C(o_j)\bigr),\\
   B_\ell &= D_{\ell-1} + W_o\Bigl(\operatorname{softmax}\!\bigl(\frac{Q^\ell K^{\ell\!T}}{\sqrt{d_k}}\bigr)V^\ell\Bigr).
   \end{aligned}
   \]
   The same mask applies: each query (byte) attends only to keys/values belonging to its owning patch.  As a result, the decoder can only access the latent vector that corresponds to the byte being generated.

3. **Transformer Layers**.  
   After the cross‑attention, a sequence of feed‑forward transformer layers (depth \(l_{\mathcal{D}}\)) processes the resulting byte representations.  Finally, a softmax over the byte vocabulary follows to produce a probability distribution for each byte position.

Because the decoder is lightweight, generating long outputs remains efficient.  If a patch expands to many bytes during generation, the decoder only needs to run a few transformer steps per patch, saving a significant fraction of the FLOPs that would otherwise be spent in the global transformer.

## Cross‑Attention Mechanics

Both encoder and decoder employ a two‑stage process: a **cross‑attention block** followed by a conventional transformer.  The cross‑attention is essential for mapping between *two different sequence lengths*—bytes to patches, and patches to bytes—while respecting patch boundaries.

### Encoder‑Side Cross‑Attention

- **Queries**: A vector per patch, representing the future latent embedding we wish to compute.
- **Keys/Values**: The representations of individual bytes within the patch, derived from the last encoder transformer layer.
- **Masking**: Each query can attend only to keys/values that belong to its patch.  
  Technically, let \(P_j\) be the set of byte indices in patch \(j\).  The attention mask \(M_{jk}\) is:
  \[
  M_{jk} = 
  \begin{cases}
  1, & k \in P_j \\
  0, & \text{otherwise}
  \end{cases}
  \]
  The softmax is computed only over allowed keys.

### Decoder‑Side Cross‑Attention

- **Queries**: Byte‑level representations to be generated.
- **Keys/Values**: Latent patch representations \(o_j\).
- **Masking**: Each byte query attaches only to the patch that will produce it.  If byte \(b_i\) belongs to patch \(j\), then keys/values from other patches are masked out.

Through these two cross‑attention stages, information flows seamlessly between the byte domain and the latent domain.

## Hash‑n‑gram Embeddings

A core innovation of \textsc{BLT} is leveraging inexpensive, hash‑based n‑gram embeddings to enhance byte embeddings with context.

### Construction

For each byte position \(i\) and for every \(n \in \{3,4,5,6,7,8\}\), form the n‑gram \(g_{i,n} = \{b_{i-n+1},\dots,b_i\}\).  The RollPolyHash function produces a deterministic hash value:
\[
\text{Hash}(g_{i,n}) = \text{RollPolyHash}(g_{i,n}) \bmod |E^{\text{hash}}_n|,
\]
where \(|E^{\text{hash}}_n|\) is the size of the embedding table for that n‑gram length (typically 100,000–500,000 entries).

Each embedding table \(E^{\text{hash}}_n \in \mathbb{R}^{|E^{\text{hash}}_n| \times h_{\mathcal{E}}}\) is learned during pre‑training.  By summing the embeddings of all back‑composed n‑grams and adding them to the raw byte embedding \(x_i\), the model captures a compressed representation of the surrounding byte context for free—O(1) additional parameters regardless of patch size.

### Why Hashing Helps

- **Memory Efficiency**: A full, unshared \(n\)-gram lookup would require storing millions of vectors.  
- **Coverage**: The hash function ensures that every possible byte sequence maps to a table entry, guaranteeing that no context is ever missing.
- **Computational Simplicity**: Rolling the hash as bytes stream shifts is cheap, suitable for training on billions of sequences.

Experiments show that adding hash‑n‑gram embeddings improves Bits‑Per‑Byte (BPB) across all domains, highlighting their contribution to encoding contextuality at a fine granularity.

## Handling Position, Normalization and Activations

Because the global transformer operates on patches that can be of variable length and not on contiguous bytes, the conventional use of absolute positional embeddings is suboptimal.  \textsc{BLT} therefore relies on **rotary positional embeddings (RoPE)** only within the global transformer self‑attention, treating each patch as a single token.  Within the encoder and decoder, **relative positional information** is implicitly encoded via the fixed sliding window and local causal masks of the self‑attention layers.  

All transformer blocks—encoder, decoder, and global—use **RMSNorm** (Root‑Mean‑Square Layer Normalization) for stability, and the feed‑forward sub‑modules employ **SwiGLU** activation to match the best practices of recent large language models.  These choices simplify the proof‑reading pipeline because the same transformer backbone technology underlies all three parts, with only the attention masks and cross‑attention interfacing differentiating them.

## End‑to‑End Workflows

### Training

During training, a **patching function** \(f_p\) (e.g. entropy‑based segmentation) splits each raw example into patches.  The forward pass comprises:

1. **Encoder Pass**  
   - Byte embeddings → local transformer (self‑attention \(\times w_{\mathcal{E}}\)) → cross‑attention → patch representations \(p_j\).

2. **Global Pass**  
   - Patch representations \(\{p_j\}\) → block‑causal global transformer \(\to\) outputs \(\{o_j\}\).

3. **Decoder Pass**  
   - Global outputs \(\{o_j\}\) → cross‑attention (bytes ← patches) → local transformer → byte logits.

The loss is computed as the cross‑entropy between the predicted byte probabilities and the true next bytes.  Back‑propagation flows through all modules, enabling end‑to‑end learning of both byte‑to‑patch mapping and patch‑to‑byte decoding.

### Inference

At inference, the process mirrors training but one step of \(\mathcal{G}\) consumes an entire patch at once.  If the model needs to generate a new byte, the decoder automatically decides whether a new patch should be started based on the entropy of the pending byte prediction.  Because the patching rule is **incremental** (the segmentation can be decided as the text is generated), the inference pipeline is fully streaming and does not rely on a future context.

The major advantage of this pipeline is **FLOP efficiency**: serialize multiple bytes into a single global transform step and generate them in one decoder pass.  Since the encoder/decoder rounds are lightweight, overall inference becomes 2–4x faster than token‑based models for equivalent performance.

--- 

## Summary

The Byte Latent Transformer showcases how an architecture that eschews tokenization can still reap the benefits of large‑scale attention mechanisms while dynamically allocating compute based on data complexity.  A lightweight encoder folds byte sequences into compact patch embeddings using hash‑derived context cues and cross‑attention; a massive latent transformer processes these patches autoregressively with block‑causal masks; and a light decoder expands patches back into bytes.  Cross‑attention serves as the glue that maintains the correspondence between the two domains, allowing efficient mixing of context without ever committing to a fixed vocabulary.  Together, these components define a new paradigm for scaling large language models directly on raw bytes.
