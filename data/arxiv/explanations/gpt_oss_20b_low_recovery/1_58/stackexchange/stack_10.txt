\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### Why does the author use 2‑bit kernels for the 1.58‑bit model during inference?
Question:
In the latency measurements, the authors employ the 2‑bit kernel from Ladder for BitNet b1.58. Since the weights are ternary (`-1, 0, 1`), which would naturally map to 2 bits, why not use a specialized 1‑bit kernel for the non‑zero weights? What are the trade‑offs in terms of speed and memory when using 2‑bit versus an ideal 1‑bit implementation?
Answer:
**Why a 2‑bit kernel for a 1.58‑bit model?**

The weights of BitNet b1.58 are ternary: \{-1, 0, +1\}. In binary notation the value ‑1 is the same string as +1 (a single bit set to 1) and the value 0 is represented by two zero bits. Thus a 2‑bit representation is the most compact *integer* encoding that can hold all three values without loss:

```
00 →  0
01 → +1
10 → -1
```

(00 is also common for both the “zero” and “no‑op” patterns, while 01 and 10 encode the signed values.)

If we were to use a *pure* 1‑bit kernel that only distinguishes “non‑zero vs zero”, the kernel would lose the sign information essential to the linear transformations of the transformer blocks. In order to re‑introduce the sign, a second bit would have to be derived from the activation (or from the weight itself), which would either:

1. **Expose the weight magnitude to the computation path** – the kernel would need a conditional check, essentially a fetch‑decode‑execute for every weight, eroding the very speed benefits of a fixed‑bit kernel.
2. **Encode the sign in two separate control signals** – this would require extra memory traffic (e.g. an auxiliary mask) and more complex logic, again hurting latency.

Hence, the 2‑bit kernel is a pragmatic compromise:  

* **Full expressive power** – it can happily multiply an 8‑bit activation by \{-1, 0, +1\} using a single 2‑bit lookup table that contains three values, one of which is zero.
* **Match the hardware’s natural data lanes** – most GPUs and many low‑power accelerators have 32‑, 64‑ or 128‑bit vector registers internally. Packing two 2‑bit weights into a single 8‑bit byte aligns perfectly with byte‑aligned memory accesses, avoiding costly unaligned loads that a true 1‑bit kernel would introduce.

---

### Speed vs Memory Trade‑offs

| Kernel | Bit-width per weight | Memory traffic | Arithmetic pipeline |
|--------|----------------------|----------------|---------------------|
| **1‑bit + sign** | 1 + 1 = 2 bits (but implemented as two separate streams) | Two separate streams (mask + weight) → ~2× memory use | Conditional logic, extra shuffle instructions |
| **2‑bit (ternary)** | 2 bits, packed 4 weights per byte | 1/4 of 8‑bit FP weight traffic → *≈ 8×* reduction | Straight‑forward multiply‑add where sign is part of the operand, no branching |

In practice, the authors measure a 2.71× speedup for a 3B model. Even with the weight sparsity introduced by the zero value, the 2‑bit branch‑free implementation outperforms a hypothetical 1‑bit approach that would need to reconstruct the sign on the fly. Moreover, the memory savings are dramatic: a ternary weight array occupies only 0.25 × the space of an 8‑bit array, allowing larger batch sizes or longer sequences on the same GPU.

---

### Bottom line

The choice of a 2‑bit kernel for BitNet b1.58 is not arbitrary; it is the minimal fixed‑width implementation that keeps the full ternary value set intact, aligns with existing vector units, and delivers the biggest reduction in both memory bandwidth and compute time. A “true” 1‑bit kernel would either lose the sign information or force a more expensive sign‑signaling mechanism, negating the benefits the authors report.
