\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### What is the intuition behind the `absmean` quantization function used for 1.58‑bit weights?
Question:
The paper defines $\tilde{W} = \text{RoundClip}\bigl(\frac{W}{\bar{|W|} + \tau}, -1, 1\bigr)$ where $\bar{|W|} = \frac{1}{nm}\textstyle\bigl\rvert W \bigr\rvert$. I understand that this normalises the weights before clipping to \\{-1,0,1\\}, but why does normalising by the average absolute value improve quantisation compared to, say, a fixed global scale or per‑column scaling? Does it help preserve the dynamic range across layers, and how does the small $\tau$ (epsilon) affect stability?
Answer:
**Answer**

In *BitNet b1.58* the weights are forced to the ternary set \(\{-1,0,+1\}\).  
The paper calls the mapping

\[
\widetilde{W}= \operatorname{RoundClip}\!\left(\frac{W}{\gamma+\varepsilon},-1,1\right),
\qquad  
\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|
\]

the **absmean** quantization function.  
Below is an intuitive and technical explanation of why the *average‑absolute* scaling is used, what benefits it brings compared with a fixed global scale or per‑column scaling, and the role of the small epsilon \(\varepsilon\).

---

### 1. Why scale by the *average absolute value*?

1. **Layer‑wise dynamic range preservation**

   A transformer layer contains many attention heads or MLP sub‑blocks, each of which tends to develop a different weight distribution after training.  
   The average absolute value \(\gamma\) of a weight matrix captures *how big* the typical magnitude is inside that particular layer, without imposing an arbitrary global scale.  
   By dividing by \(\gamma\), we “normalize’’ the layer’s weights so that most of them fall in the interval \([-1,1]\).  
   After the subsequent `RoundClip`, the most significant values become ±1, while the rest collapse to 0.  
   Thus every layer keeps an equal chance to use the full ternary range; a layer whose weights would otherwise be very small does not get overwhelmed by a global high scale, and a layer with very large weights does not saturate the range.

2. **Robustness to training dynamics**

   During training the distribution of weights can shift (e.g., due to weight decay or adaptive optimizers).  
   Using the up‑to‑date mean absolute value means the quantization automatically adapts to these shifts, keeping the ternary mapping roughly centered around zero.  
   A fixed global scale would either over‑compress some layers (making them effectively constant) or under‑compress others (causing many weights to saturate at ±1).

3. **Simplicity vs. complexity**

   A more fine‑grained per‑column or per‑channel scaling would give slightly higher fidelity but would require storing an additional scalar per column, increasing memory and kernel complexity.  
   The absmean approach keeps the scaling factor per *matrix* only, matching the architecture’s existing `nn.Linear` semantics and avoiding extra memory traffic.

---

### 2. What happens if we used a fixed global scale or per‑column scaling instead?

| Scaling scheme | Effect on quantization | Practical complications |
|----------------|------------------------|-------------------------|
| **Fixed global** | All layers are forced to share one scale. Layers with very different magnitudes end up being either *prematurely clipped* (when the global scale is large) or *too sparse* (when the global scale is small). | Needs careful tuning; can degrade performance dramatically. |
| **Per‑column** | Each column (i.e., each output dimension) gets its own scale, which can capture subtle differences. | Requires storing and broadcasting \(n\) scalars per weight matrix; increases code complexity and memory jumps. |
| **Average‐abs** | Provides a compromise: captures the overall spread of a layer but keeps kernel minimal. | Uses only one scalar per weight matrix; the quantization remains hardware‑friendly. |

The paper’s experiments show that the absmean method yields perplexity and zero‑shot performance comparable to full‑precision models while keeping the model size and runtime dramatically smaller. The modest overhead of a single scalar per layer is negligible compared to the benefits.

---

### 3. Intuition behind the small epsilon \(\varepsilon\)

1. **Numerical stability**

   If a weight matrix were all zeros (which can happen early in training or in some residual connections), \(\gamma\) would be zero and division would be undefined.  
   Adding a tiny \(\varepsilon\) (e.g., \(10^{-5}\)) guarantees a non‑zero denominator so the quantizer always behaves.

2. **Avoiding extreme scaling**

   Even when \(\gamma\) is very small, the division could blow the values up, leading to an overwhelming number of ±1 outcomes and a loss of information.  
   The epsilon acts as a hard cap: the effective scale becomes \(\min(\gamma,\varepsilon)\), preventing runaway amplification of tiny weights.

3. **Gradual decay**

   Because \(\varepsilon\) is much smaller than typical \(\gamma\) values, it has negligible influence during normal operation.  
   Only in degenerate cases does it bite, ensuring stability without sacrificing expressiveness.

---

### 4. Connection to broader quantization ideas

The absmean approach is a form of *per‑layer mean absolute value (MA) scaling*, a family of techniques used throughout low‑bit quantization research (e.g., GPT‑Q, AdaRound, and many post‑training schemes).  
It sits between fully asymmetric per‑tensor scaling (most expressive but heavy) and symmetric fixed‑point scaling (fast but brittle).  
By preserving each layer’s dynamic range while keeping the quantizer simple, it aligns well with hardware constraints: a single scalar per kernel can be fused into the GEMM read‑out, and the ternary weights can be merged with integer addition in the inference engine.

---

### 5. Bottom line

- **Average‑absolute scaling** adapts the ternary mapping to each layer’s own weight distribution, avoiding the pitfalls of a global scale and the overhead of per‑column scaling.  
- It keeps the quantizer lightweight, so the back‑end can fuse the process into a fast integer GEMM.  
- The tiny epsilon protects against pathological cases without affecting normal training dynamics.  

In short, the absmean trick is a practical, layer‑aware, and hardware‑friendly way to turn full‑precision weight matrices into ternary (\(-1,0,+1\)) representations with little loss in model quality.

### How does including the zero‑weight value in 1.58‑bit models enable ‘feature filtering’?
Question:
The authors mention that adding a 0 to the ternary set provides explicit support for feature filtering, supposedly improving performance. Could someone explain a concrete example or mechanism where a zero weight acts as a filter during matrix multiplication, and why this is not available in a pure 1‑bit \\{-1, +1\\} model?
Answer:
**Answer**

In a BitNet b1.58 layer every weight is forced to be one of the three integers  

\[
W_{ij}\;\in\;\{-1,\;0,\;1\}.
\]

When a matrix–vector multiplication is carried out in the forward pass, each entry of the output vector is a sum of products of the form

\[
y_i=\sum_{j}W_{ij}x_j,
\]

with \(x_j\) being an 8‑bit activation.  
Because \(W_{ij}\) can be zero, the product \(W_{ij}\,x_j\) is *always* equal to zero whenever the weight is zero.  In other words, the column \(j\) of the weight matrix is simply ignored for that output neuron.  This is what the authors call *feature filtering*.

A concrete example:  
Assume a hidden size of 4 and that the second activation in a token is not useful for predicting the target.  In a 1‑bit model (weights only \{-1,+1\}) the second column of every weight matrix must participate in every multiplication.  The only way the model can learn to ignore that feature is by learning an offset or a compensating weight in subsequent layers, which requires extra parameters and extra training effort.

With the ternary set, the optimizer can directly “neutralise” the contribution of that feature by setting the corresponding weight to zero.  During the forward pass the whole column is omitted, so no multiplication or addition is performed for that entry.  This has two benefits:

1. **Expressiveness** – The network can sparsely select which features to use in each layer.  It is effectively learning a gating function that is free of any extra computational cost, because a zero weight means “do nothing”.
2. **Efficiency** – Where a zero weight occurs, the accelerator can skip the corresponding multiply‑and‑add.  In a purely binary network every multiplication has to be performed (even if the result is useless), so the hardware sees a denser set of operations.

The authors emphasise that this simple explicit zero value is *not* available in a pure 1‑bit \(\{-1,+1\}\) model: there is no symbol that can be interpreted as “ignore this feature”.  The only way a binary model could imitate feature filtering would be through a complex combination of sign flips in later layers, which is less efficient and harder to learn.

In summary, the inclusion of 0 in the weight set lets the model *decide* to drop some input dimensions entirely during a matrix multiplication.  This acts like a cheap, learnable attention mask that both improves modelling capacity (the network can focus on the most informative features) and makes inference cheaper (skipped columns mean fewer arithmetic operations).

### Why are 1‑bit matrix multiplications replaced with INT8 additions in BitNet?
Question:
The paper states that 1‑bit LLMs use only integer additions for their matrix multiplications, saving almost all multiplication cost. However, if weights are ternary \\{-1,0,1\\} and activations are 8‑bit, why can we treat the operation as simple additions? Does the presence of zeros allow us to skip multiplication entirely, and how does the hardware implement this efficiently?
Answer:
**Short answer**  
Because the weight matrix contains only the digits \(-1,\,0,\,1\), each element of a dot product can be expressed as  

\[
a_i \cdot w_i = 
\begin{cases}
a_i  &\text{if } w_i = +1,\\[4pt]
0    &\text{if } w_i = 0,\\[4pt]
-a_i &\text{if } w_i = -1,
\end{cases}
\]

where \(a_i\) is an 8‑bit activation.  
Thus a matrix multiplication with a ternary weight matrix reduces to **adding or subtracting the corresponding activation and discarding the zero entries**—the algorithm never needs to multiply two values. Hardware can then use a simple adder (or subtractor) and a mask to skip the zeros, which is orders of magnitude cheaper in both energy and latency than a floating‑point multiply.

---

### How the conversion works technically

1. **Weight representation**  
   The quantizer in BitNet maps every full‑precision weight to the nearest integer in \(\{-1,\,0,\,1\}\).  
   This is done once during a preprocessing step; after that the weight matrix can be stored in a compact 2‑bit format (two bits per value: e.g., 00 → 0, 01 → +1, 10 → −1).  

2. **Activation format**  
   Activations remain 8‑bit integers. They are already shifted to the signed range \([-Q_b,\,Q_b]\), so the sign bit can be used directly in the multiply‑by‑\(\pm 1\) operation.  

3. **Operation per element**  
   For each product \(a_i \cdot w_i\):
   * If \(w_i=0\) the hardware simply **skips** that element (no add, no bus traffic).  
   * If \(w_i=+1\) the hardware **adds** the activation \(a_i\) to the accumulating register.  
   * If \(w_i=-1\) the hardware **subtracts** \(a_i\) (equivalent to adding the two’s‑complement).  

4. **Reduction to integer addition**  
   The sum over a row or column of the matrix–vector product therefore consists of only signed 8‑bit add/sub operations followed by a narrow carry‑propagation (the accumulator can be 16‑ or 32‑bit to avoid overflow). No multiplication units are needed.

5. **Hardware implementation**  
   * **Bit‑packed weight cache:** The 2‑bit weight values can be loaded together with the activation into a small SRAM staging buffer, so the multiplier network is avoided entirely.  
   * **Add‑only pipeline:** A small “match‑store” unit reads the weight bit‑pattern, uses a discriminator to decide between add, sub, or skip, and routes the activation to the main adder.  
   * **Zero‑skipping:** The hardware can detect a zero weight and simply bypass the corresponding lane, saving both memory bandwidth and energy.  
   * **SIMD‐style parallelism:** Modern GPUs and custom ASICs can process many such lanes in parallel; the cost per lane is essentially that of a sign‑extend and a one‑bit selection gate plus an adder.

Because additions cost roughly 0.1–0.2 pJ on a 7 nm chip while a FP16 multiply consumes several times more, the **energy savings** reported in the paper (≈ 71×) come directly from eliminating the multiply unit.

---

### Why this is a big win for LLM inference

1. **Compute‑bound bottleneck** – In a Transformer the \(nn.Linear\) layers dominate both compute time and memory usage. Replacing their matrix multiplies with add‑only operations shrinks this hotspot dramatically.  
2. **Memory bandwidth** – The ternary weights need only 2 bits each; the activations are 8 bits. Compared to FP16 weights/activations this halves the data movement in every layer, which is critical for GPUs and for edge devices with limited DRAM bandwidth.  
3. **Compatibility** – The rest of the transformer (rotary embeddings, RMSNorm, SwiGLU, etc.) can stay in full precision or be lightly quantised; only the linear kernels benefit from the add‑only paradigm.  
4. **Scalability** – As the model size grows the portion of the network that is linear increases, so the percentage of time saved grows, explaining why a 70 B BitNet b1.58 is 4.1× faster than a 70 B FP16 LLA MA baseline.

---

### Bottom line

The presence of zeros in the weight set removes the need to perform any multiplication for those positions. When the remaining weights are \(\pm 1\), each product is either the activation itself or its negation, which are realized with a single adder/subtractor. This simple arithmetic replaces a costly floating‑point multiply, allowing custom hardware to focus on moving data and adding integers—a paradigm shift that underpins the tremendous latency, memory, and energy gains reported for BitNet b1.58.

### How does the scaling law for 1.58‑bit LLMs differ from the traditional scaling law for FP16 models?
Question:
In the results section, the authors provide equivalences such as a 13B BitNet b1.58 outperforming a 3B FP16 LLM. What is the theoretical basis for this scaling shift? Is it simply because of reduced computational cost allowing larger models, or is there a mathematical relationship between bits per weight, model size, and perplexity that the paper derives?
Answer:
**Answer**

The “new scaling law” that the paper talks about is not an entirely new empirical curve for *per‑parameter* performance – it is the realization that the cost of a model now scales with *bits per weight* as well as with its size.  
In the traditional FP16 world the effective “parameter budget” is just *the number of floating‑point parameters* \(P\): a 3 B‑parameter FP16 LLM and a 13 B‑parameter FP16 LLM differ only by a constant factor in the number of parameters (≈ 4.3×).  
With 1.58‑bit weights the same *numeric* size (e.g., a 3 B‑parameter model) occupies only \(0.0785\) B (because \(3\times10^9\times1.58/8\approx0.59\,\text{GB}\) instead of ≈ 19 GB).  In other words, a 1.58‑bit model can host many more *effective* parameters for the same resource budget.

---

### 1.  How the scaling shift is expressed

The paper derives an implicit “equivalence mapping” between FP16 and BitNet b1.58 that is illustrated in the paragraph *“BitNet b1.58 is enabling a new scaling law…”*.  
The authors measured latency, memory usage and energy for a set of BitNet b1.58 models of size 3–70 B and compared them against the same metrics for FP16 LLaMA baselines.  For each FP16 model size \(S_{\mathrm{FP16}}\) they found a **larger BitNet** size \(S_{\mathrm{B58}}\) that achieves the *same* or better performance *with less cost*.  The concrete equivalences reported are:

- 13 B BitNet b1.58 ≈ 3 B FP16  
- 30 B BitNet b1.58 ≈ 7 B FP16  
- 70 B BitNet b1.58 ≈ 13 B FP16  

This is a *data‑driven shift* of the scaling law: the “effective” size that the hardware can support for a given budget grows roughly 4× (3 B → 13 B) while the *performance* does not degrade.

---

### 2.  Why the shift occurs – a mathematical intuition

Let  

\[
\Delta_{\text{bits}}=\text{bits per weight}
\]

For an FP16 model \(\Delta_{\text{bits}}^{\text{FP16}}=16\).  
For BitNet b1.58 \(\Delta_{\text{bits}}^{\text{B58}}=1.58\).  
If a hardware platform can process \(M\) bits of weight per second (roughly the same because the *number of arithmetic operations* is unchanged, only the **data movement** changes), the *effective* number of parameters it can handle in a given time scales as

\[
P_{\text{effective}} \propto \frac{M}{\Delta_{\text{bits}}}.
\]

Therefore

\[
P_{\text{effective}}^{\text{B58}} \approx \frac{16}{1.58}\;P_{\text{effective}}^{\text{FP16}}
\approx 10.1\times P_{\text{effective}}^{\text{FP16}} .
\]

In practice the authors observe a factor ≈ 4–5, because the per‑parameter computational cost is not perfectly linear (the quantized kernels are lighter and easier to parallelize, activation bit‑width is 8 bit, etc.).  Still, the *order‑of‑magnitude* gain in parameter budget is the key.

---

### 3.  Not just a cost advantage, but a capacity advantage

Because the *same* 3 B‑parameter budget can now host a 13 B‑parameter effective network, the empirical scaling law observed for FP16 models (e.g., perplexity improving roughly as some power‑law of \(P\)) can now be satisfied with *smaller* raw parameter counts.  In other words, the 1.58‑bit model uses the available compute‑memory budget more efficiently, allowing us to step further along the FP16 scaling curve without consuming more hardware resources.  

The paper does not present a closed‑form equation like \( \text{PPL} \approx a \cdot P^{-b} \) for BitNet b1.58; instead it shows that for every FP16 model that hits a given perplexity, a 1‑58‑bit model of roughly four times the parameter count achieves a **Pareto‑improved** point in the space of
\[
(\text{perplexity}, \; \text{latency}, \; \text{memory}, \; \text{energy}).
\]

---

### 4.  Connection to broader scaling ideas

Traditional LLM scaling laws (e.g. Kaplan et al., 2020) focus on relationships such as  
\[
\text{PPL} \approx A \cdot P^{-\alpha}
\]
where \(P\) is the number of parameters.  They implicitly assume a constant *parameter bit‑width*.  When we change \(\Delta_{\text{bits}}\), the *effective* \(P\) that can be fit into a given hardware budget changes, so the **effective scaling curve** shifts.  
The paper’s equivalence list is therefore a concrete example of how changing the *quantization regime* reshapes the resource‑performance trade‑off while staying within the same asymptotic scaling regime.

---

### Bottom line

1. The scaling shift is empirically derived from measurements of latency, memory and energy for BitNet b1.58 versus FP16 baselines.  
2. Mathematically it stems from the fact that the *effective* number of parameters that a given hardware budget can handle scales inversely with the number of bits per weight.  
3. The equivalences (13 B → 3 B, 30 B → 7 B, 70 B → 13 B) show that a 1.58‑bit model can achieve the same or better performance while consuming 2–4× less resources, effectively moving the traditional scaling law curve to the left.  

Thus the “new scaling law” is not about a new functional form for performance versus size, but about a new *resource‑efficient mapping* that allows larger effective models under the same hardware budget.

### What assumptions underlie the energy savings estimate of 71.4× for matrix multiplication on 7nm chips?
Question:
Figure 4 compares arithmetic operations energy consumption between 1.58‑bit and FP16 models, citing an energy model from prior work. I’d like to understand the key assumptions: are they counting only adders and multipliers, ignoring memory traffic? How are the energy costs of INT8 additions versus FP16 multiplications quantified, and does the 7nm scaling factor into the comparison?
Answer:
**Answer**

The energy figure shown in Figure 4 (71.4× savings for matrix multiplication on a 7 nm process) is derived from a very simple, yet fairly realistic, arithmetic‑operations cost model that was originally reported in two earlier works: *[energycost]* and *[pokebnn]*.  
Below is a walk‑through of the key assumptions and how they combine to yield that number.

---

### 1. What the model actually counts

* **Only the arithmetic core** – The energy estimate is the sum of the energy consumed by the arithmetic units involved in a matrix multiplication.  
  * **INT8 additions** (one per add‑and‑accumulate step) are the drive for BitNet b1.58.  
  * **FP16 additions + FP16 multiplications** are the drive for the FP16 LLaMA baseline.  
  * There is **no explicit accounting for memory‑traffic energy**, access to off‑chip DRAM, or to the weight‑cache in SRAM. The authors say “we focus mainly on the calculation for matrix multiplication, since it contributes the most to the cost of LLMs,” so the model deliberately omits memory‑traffic costs.

* **No consideration of activation quantisation overhead** – The 8‑bit activations used by BitNet do not enter the arithmetic‑cost model. They only affect the memory footprint, which is treated elsewhere in the paper.

---

### 2. Energy per operation

The two cited works provide per‑operation energy values for a 7 nm CMOS fabrication node:

| Operation | Energy (pJ) on 7 nm |
|-----------|---------------------|
| FP16 MUL | \(\approx 2.8\) |
| FP16 ADD | \(\approx 0.3\) |
| INT8 ADD | \(\approx 0.015\) |

These numbers come from a cycle‑accurate micro‑architectural simulator that measured the toggling activity of the functional units on a 7 nm ASIC. The key points are:

* A single FP16 multiplication is roughly **≈ 30×** more expensive than an INT8 addition.  
* The cost of an FP16 addition is almost negligible compared with a multiplication but still several times higher than an INT8 addition.

---

### 3. How the “71.4×” figure is reached

1. **Count the operations in a GEMM**  
   A matrix multiplication \(C = A \times B\) of size \((M\times K)\) × \((K\times N)\) performs \(M \times N \times K\) *multiply‑accumulate* (MAC) operations. Each MAC consists of one multiplication and one addition.

2. **Translate to energy for FP16**  
   \[
   E_{\text{FP16}} = M N K \times \bigl(E_{\text{MUL,FP16}} + E_{\text{ADD,FP16}}\bigr)
   \]
   Using the values above the per‑MAC energy is about \(3.1\) pJ.

3. **Translate to energy for INT8 (BitNet)**  
   In BitNet b1.58 the multiplication is replaced by an *integer add‑and‑accumulate* that uses only INT8 addition (the multiplier’s logic is replaced by a simple sign flag and zero‑elimination trick).  
   \[
   E_{\text{INT8}} = M N K \times E_{\text{ADD,INT8}} 
   \]
   The per‑MAC energy is about \(0.015\) pJ.

4. **Take the ratio**  
   \[
   \frac{E_{\text{FP16}}}{E_{\text{INT8}}}
   \approx \frac{3.1}{0.015}
   \approx 206
   \]
   This ratio represents the *theoretical* energy advantage if all other factors were equal.

5. **Apply a practical scaling factor**  
   The authors note that actual silicon implementations are not perfectly efficient; the inexpensive INT8 adders use a *more latency‑efficient* implementation that reduces their energy per cycle, whereas FP16 multipliers are already in a heavily optimized state. Accounting for realistic power‑gating, peripheral logic and the fact that the “AU” for INT8 is smaller, the authors fit their macro‑benchmark data and found a **real‑world ratio of 71.4×**.  
   In other words, after applying the pragmatic micro‑architectural overheads, the FP16 MACs still cost about 71 × more energy than a BitNet MAC on a 7 nm chip.

---

### 4. Where the 7 nm scaling matters

* The energy numbers per operation are tied to the **7 nm technology node** used in the cited micro‑architectural studies.  
* On older nodes (e.g., 16 nm) the absolute energy per operation would be higher, but the *relative* cost difference between FP16 MUL and INT8 ADD stays roughly the same.  
* Thus the 71.4× figure is explicitly a **device‑specific** claim. If a newer node (5 nm, 4 nm) were used, the absolute savings might increase slightly because the multiplier unit shrinks faster than the adder unit, but the paper keeps the 7 nm assumption to match the referenced experiments.

---

### 5. Bottom line for practitioners

* The 71.4× number is **not an all‑inclusive device‑to‑device energy comparison**. It isolates the arithmetic core that dominates LLM inference.  
* Memory‑traffic energy, DRAM access latency, or the cost of loading/unloading weights are **outside the scope** of this particular estimate. Those costs are later discussed qualitatively (e.g., “BitNet has a lower memory footprint, reducing DRAM traffic”).  
* When building an end‑to‑end energy model you should **add** the memory‑traffic terms (which are a fraction of the total on modern GPUs) to the arithmetic estimate. For a 7 nm ASIC the arithmetic part would still be the major contributor for inference workloads, so the 71× figure remains a useful ball‑park indicator of the benefit of moving to 1.58‑bit weights.

In summary, the 71.4× savings comes from a 7 nm energy‑per‑operation model that counts only the adders and multipliers used in GEMMs, with INT8 additions in BitNet replacing FP16 multiplications in the baseline. Memory traffic and other peripheral costs are deliberately omitted, and the scaling factor is tied to the specific 7 nm technology used in the referenced micro‑simulations.

### How does the 1.58‑bit quantisation affect the training dynamics compared to full‑precision training?
Question:
The paper shows that training from scratch with 1.58‑bit weights and 8‑bit activations can reach similar perplexities as FP16 models. Does the quantisation introduce significant bias in gradients? How do the authors handle gradient scaling or rescaling during training, and is the `absmean` quantisation applied during back‑propagation as well?
Answer:
**Short answer**  
During training BitNet b1.58 uses a *straight‑through estimator* (STE) for the quantization routine. The weights are openly quantized before the forward pass, but for the backward pass the gradient is simply copied from the quantized weights (`∂L/∂Ŵ = ∂L/∂W`). No extra gradient scaling or rescaling is performed; the same 1.58‑bit quantization that appears in the forward pass is *not* re‑applied to the gradients. The only scaling that matters is the “abs‑mean” factor γ used to bring the weight magnitudes into the \{-1,0,1\} range—this factor is recomputed at every weight‑update step, effectively redefining the scaling of the discrete weights while the gradient remains in full precision.

---

### 1. Does the quantization introduce bias in the gradients?

Quantizing the forward tensors to discrete values inevitably creates a *dead‐weight* effect: small updates that would have been absorbed in 16‑bit are clamped to 0 when they cross a quantization boundary. However, BitNet b1.58 sidesteps most of this bias by

1. **Using a *soft* scaling λ = γ (the mean absolute value)** – before rounding, each weight is divided by γ, so the dynamic range of the discrete set stays centred around the current statistics of the weight matrix. This keeps most significant gradients within the range where rounding to an adjacent ternary value is still informative.

2. **Applying the straight‑through estimator** – the gradient flowing into the quantized weight is taken as if the quantization were an identity function. In practice this means the optimizer sees the true gradient with respect to the *real* weight (not the quantized weight), and the update step is computed in full precision. The discrete weight is only *re‑quantized* after the step. Thus the training dynamics are governed by the full‑precision gradient, not by a biased discrete gradient.

Because of these mechanisms the accumulated bias over many updates is kept small, which is why the authors observe perplexities comparable to FP16 training.

---

### 2. How do the authors handle gradient scaling or rescaling during training?

The only form of scaling that appears in the training loop is the **abs‑mean factor γ**. The training procedure is:

1. Compute the weight‑scale γ from the current weight matrix (equation (3) in the paper).  
2. Quantize the weights using the `RoundClip` function.  
3. Forward‑propagate with the ternary weight matrix.  
4. Compute the loss and back‑propagate *as if* the weights were continuous:  
   \[
   \frac{\partial L}{\partial W} \;\text{(full‑precision gradient)}
   \]
5. Update the *full‑precision* weight matrix with the optimizer, typically AdamW.  
6. Repeat.

No extra multiplicative factor is applied to the gradient; the scaling of the weight (γ) does not appear in the backward pass. The only time the gradient is “rescaled” is indirectly: after the weight update, γ is recomputed and a new quantized weight matrix is derived. This re‑scaling does not tamper with the original gradient computed in step 4.

---

### 3. Is `absmean` quantization used during back‑propagation?

No. The `absmean` quantization is applied **only to the forward tensors** (weights and activations). Once the backward pass begins, the algorithm treats the quantization step as a non‑differentiable barrier and replaces its derivative with one that is identity (STE). Thus the gradient with respect to the quantized weight is simply the gradient with respect to the underlying full‑precision weight. The same holds for activations: they are quantized for the forward pass only; the backward pass propagates gradients through the un‑quantized pre‑activation values.

---

### 4. Why does this work for large‑scale LLMs?

The heavy part of LLM training is the matrix multiplication in the linear layers. In FP16 the multiplication and accumulation dominate the memory traffic and power budget. By constraining weights to \{-1,0,1\}, the authors remove the multiplication entirely; the matrix product becomes an *integer addition* that can be performed with a 2‑bit kernel. Because the forward values are exact integers, the activations are only residual (8‑bit), the full‑precision gradients can still be computed without any numerical explosion, and the optimizer can make fine‑grained updates in the continuous weight space. The *abs‑mean* scaling keeps the ternary weights in a reasonable dynamic range so that the quantization error does not grow unbounded.

This combination of an exact forward quantization, STE‑based backward pass, and per‑forward‑step scaling is what allows BitNet b1.58 to match FP16 perplexities while training from scratch on 100 B tokens.

---

### Bottom line

- Quantization is applied only in the forward pass.  
- The backward pass uses a straight‑through estimator; the gradients are *not* scaled or re‑quantized.  
- The only scaling factor that changes during training is the mean‑absolute‑value γ that normalises the weights before quantization.  
- Because the gradient update operates on the underlying full‑precision weight, the bias introduced by the ternary quantization is kept minimal and does not degrade training performance.

### In what way does the proposed BitNet b1.58 architecture support long‑sequence inference more efficiently?
Question:
The discussion mentions that reducing activations to 8 bits allows doubling the context length for a fixed memory budget. However, since the keys‑values in KV cache are still 16‑bit in standard LLaMA, how does BitNet b1.58 modify the KV representation? Do they quantise the KV tensors, and if so, how is the trade‑off between precision loss and memory savings handled?
Answer:
**Short answer:**  
BitNet b1.58 keeps the key‑value cache in the same 16‑bit format that LLaMA uses; it does **not** quantise the KV tensors in the published model. The claim that “reducing activations to 8 bits allows the context length to be doubled for a fixed memory budget” refers only to the **activations** that flow through the transformer layers, not to the stored KV pairs that are needed for attention during full‑sequence inference.  

**Why the KV tensors stay 16‑bit**

1. **Kernel design constraints** – The authors ported LLaMA’s architecture (RMSNorm, SwiGLU, rotary embeddings, no biases) to a 1‑bit transformer that uses `BitLinear`.  
   The attention mechanisms (`q`, `k`, `v`) are still executed on standard CUDA kernels (FasterTransformer with a 2‑bit kernel for the `BitLinear` weight matrix). Those kernels expect the *value* matrices to be in 16‑bit floating point (FP32/FP16) because the `softmax` and the residual connections that follow the attention output rely on full‑precision computations for stability and to avoid numerical under/overflow that would otherwise hurt perplexity.

2. **Minimal performance impact** – Post‑training quantisation of the KV tensors (e.g., 16‑bit → 8‑bit) would introduce an additional quantisation‑de‑quantisation step for every layer, which would increase latency and worsen the quality‑of‑service that the paper is trying to preserve. The authors instead target the *activations* that dominate the memory budget during inference, because these are written and read for every token produced. By making the activations 8‑bit (and the weights ternary), they halve the per‑token memory usage without risking a drop in accuracy.

3. **Future‑proofing** – The discussion section explicitly says that “this can be further losslessly compressed to 4 bits or even lower for 1.58‑bit LLMs, which we leave as future work.” This suggests that any compression of the KV cache is left for later work; the current release keeps it in 16‑bit FP to keep the implementation simple and to guarantee that the proven “new scaling law” (matching FP‑16 performance at 3 B parameters) still holds.

**How the trade‑off is handled**

Even though the KV cache remains 16‑bit, the reduction in activation precision brings a *net* memory‑saving that is effectively equivalent to storing the KV cache twice as large before compression. Let  

\[
M_{\text{act}} = \underbrace{N_{\text{tokens}} \times H}_{\text{tokens}}\times 8\text{ bit}
\]

be the activation memory. If every activation were kept in 16‑bit, the memory would be  

\[
M_{\text{act}}^{16} = 2\,M_{\text{act}} .
\]

Because the whole KV cache is usually the dominant term for a long‑context run, halving the activation memory effectively frees space that can be *re‑used* to hold a KV cache twice as long. In practice, with a fixed GPU budget, the authors find that the *maximum* context length roughly doubles when they switch from FP16 activations (as in standard LLaMA) to 8‑bit activations, while the KV cache itself does not change size.

If one really wants to reduce the KV cache, a simple post‑training quantisation (e.g., 16‑bit → 8‑bit per‑channel or per‑layer) can be applied. However, this would need to be carefully calibrated to avoid accumulative error in the `softmax` attention weights. The authors defer this to future work because their current goal is to demonstrate that the key‑benefits of a 1‑bit LLM (energy, latency, memory for weights/activations) can be realised *without* sacrificing anything on the KV side.

**In summary**

- **BitNet b1.58 keeps KV tensors in 16‑bit precision**; the authors do not quantise them in the current release.
- The reported “doubling of context length” stems entirely from compressing the *activations* from 16‑bit to 8‑bit, which frees memory that can now be used to store more KV pairs.
- Any further compression of the KV cache is optional and left for future work, as it would require a dedicated quantisation‑aware training or a different kernel that can handle lower‑precision values in the attention computation without hurting perplexity.

### How would a 1‑bit mixture‑of‑experts (MoE) workflow look like with BitNet b1.58?
Question:
The paper suggests that 1.58‑bit models could reduce the memory overhead of MoE deployments. Could someone outline a possible MoE architecture that uses BitNet b1.58 experts? Specifically, how would router weights and gating functions be quantised, and what would the per‑token communication cost be compared to a standard FP16 MoE?
Answer:
**Short answer**  
A 1‑bit MoE with BitNet b1.58 would look like a standard router‑based MoE where every weight matrix (both the experts and the router) is *ternary* (‑1, 0, +1) and the activations are 8‑bit signed integers.  
The router outputs are first quantised to a small integer (“top‑k” or “load‑balance” mask) and the resulting sparse matrix‑vector products are executed with *integer‑only* GEMMs (typical implementations such as Skydance, TensorRT‑INT8, or the 2‑bit kernels used for BitNet).  
Per‑token communication drops from the FP16‑to‑FP16 data traffic of a conventional MoE (≈ 2×(🚫 expert weights + activation bytes)) to roughly **½ the bytes**: each expert’s weight slice is now 1.58 bits on‑chip, and the gating vector, once quantised to a small integer, needs only a few bits per token. The savings in bandwidth can be more dramatic if you pack several tokens’ routing decisions into a single network packet.

---

## 1.  What the architecture looks like

| Component | Classic FP16 MoE | BitNet b1.58 MoE |
|-----------|-----------------|-------------------|
| **Experts** | Linear layers with ≥ 16‑bit weights | `BitLinear` layers with ternary weights (‒1, 0, +1) |
| **Router** | Small dense 2‑layer MLP → softmax → top‑k | Same MLP, but all its weights are ternary. The output logits are 16‑bit, but the final *gate values* (the top‑k mask) are **quantised to 1‑byte integers** (e.g. 0–31) and then used to multiply the expert outputs. |
| **Activations** | FP16 (or BF16) | INT8 (signed), scaled per token to ‑128…127 |
| **Communication** | Host↔GPU or inter‑chip: weight + activation tensors in FP16 (2 bytes per scalar) | Host↔GPU or inter‑chip: only the *load‑balance mask* (≈ 1 bit per expert per token) plus a small delta‑code for the selected expert indices; weights stay on‑chip. |

The key insight is that **the router itself can be an integer‑only module**. In the BitNet paper, the authors quantise *all* trainable parameters to a ternary set using the absmean rounding. Carrying that over to MoE, each router weight is pushed through that same quantisation function, yielding a matrix that can be stored with 1.58 bits per entry. The 8‑bit activations make sure that the explainability of vector‑wise gating (e.g., via  
\[
g_i = \mathrm{softmax}(W_{\text{router}}\;x)
\]
) stays numerically stable while keeping the data‑movement cheap.

---

## 2.  Quantising router weights & gating

1. **Router weights**  
   The router for token *t* is a small MLP:
   \[
   r_t = \mathrm{RoundClip}\!\left(\frac{W_r\,x_t + b_r}{\gamma_r + \epsilon}, -1, 1\right),
   \]
   where \(W_r\) and \(b_r\) are ternary.  
   \(x_t\) is the 8‑bit token activation. The division by \(\gamma_r\) (average absolute value) keeps the dynamic range manageable.

2. **Routing score**  
   The rollout is traditionally a softmax over \(K\) experts. With integer‑only weights the logits stay 16‑bit (or even 8‑bit after scaling). The softmax is *approximated* by a *top‑k* selection:  
   \[
   \mathcal{I}_t = \operatorname{argsort}(score_t)_{[:k]}.
   \]
   Rather than sending a soft probability vector, we only send the indices \(\mathcal{I}_t\). If the router mask is stored as a 1‑bit “active/inactive” flag per expert, the communication cost is \(k\) bits per token for the mask, plus a few bits for the indices (e.g. 5 bits for up to 32 experts).

3. **Expert outputs**  
   Each expert’s output is a linear transformation using its ternary weight matrix. The result is a vector of 8‑bit signed integers. The sum of locally activated experts is then performed on the same chip, avoiding any inter‑chip traffic for raw activations.

---

## 3.  Per‑token communication cost compared to FP16 MoE

| Item | Classic FP16 MoE | BitNet b1.58 MoE | Ratio |
|------|-----------------|------------------|-------|
| **Expert weight slice** | 16 bits | 1.58 bits | 0.099 |
| **Router mask** | 1 bit per expert (if full soft‑gating) | 1 bit per expert (for active / inactive) | 1 |
| **Activator / gating logits** | 16 bits (if shipped) | 8 bits after scaling | 0.5 |
| **Expert activation vector** | 16 bits | 8 bits | 0.5 |

Assume a MoE with 32 experts and *k = 2* experts activated per token.  
- Classic MoE needs to send 32 × 16 = 512 bits of router logits + 2 × buffer (say 128 bits, 16 bits × 8‑token window) ≈ 640 bits per token.  
- BitNet b1.58 sends 32 × 1.58 ≈ 50 bits of router mask (if encoded sparsely) + 2 × 8 = 16 bits for the chosen activations ≈ 66 bits per token.

So **the communication cost drops by roughly a factor of 10**, with the majority of savings coming from storing the router weights and expert weights in ternary form and packing the routing decisions into a sparse bit‑mask rather than a dense probability vector.

---

## 4.  Practical considerations

1. **Hardware support** – The 2‑bit kernels shown in BitNet (e.g. the Ladder kernel) can be extended to a *ternary* kernel. The major bottleneck shifts from *floating‑point multiplication* to *integer multiplication* and *adder tree* operations, which are significantly cheaper on GPUs or dedicated ASICs.

2. **Dynamic load balancing** – Since the routing operation is integer‑only, it can be moved to a lightweight micro‑controller or a small dedicated “router arbiter” that keeps track of expert utilisation in real time, emitting a sparse bit‑mask that is instantly consumable by the expert matrix‑multiply units.

3. **Compression of the router** – The ternary weights of the router can be *entirely stored on‑chip*, eliminating the need to fetch them over a PCI‑e bus. In a multi‑chip MoE environment, each chip would only need to stream the 1‑bit routing decisions for its own slice of experts, further reducing inter‑chip traffic.

4. **End‑to‑end latency** – On the GPU, the cost of a ternary matrix multiply is roughly the **same** as a 16‑bit integer multiply minus the cost of the multiplier itself. Because the BitNet paper reports a 2.7× speed‑up for a 3.9 B model, replacing the linear layers in the MoE experts with BitLinear would preserve this speed‑up while eliminating the 4× memory traffic that is typical for FP16 MoE.

---

## 5.  Bottom line

* A 1‑bit MoE using BitNet b1.58 would keep the traditional “top‑k” MoE design but replace every dense matrix (experts and router) with a ternary one, and every float activation with an 8‑bit integer.  
* The **router** is quantised to ternary; its logits become 8‑bit integers and only the sparse selection indices are transmitted.  
* Per token, the communication cost is reduced **≈ 10×** compared to FP16 MoE, because we no longer need to stream large 16‑bit weight matrices or dense gating vectors across the network.  

This opens the door to *fully‑on‑chip* MoE with negligible inter‑chip traffic—exactly the advantage the paper predicts for moving a large MoE to a single accelerator.

### What challenges remain for deploying BitNet b1.58 on CPUs versus GPUs?
Question:
The paper claims that 1.58‑bit LLMs are more CPU‑friendly. Given that CPUs lack native support for low‑bit integer vector operations, what software or hardware tricks (e.g., loop‑unrolling, SIMD extensions, custom libraries) would be necessary to realise the stated latency and throughput gains on edge devices?
Answer:
**Short answer**  
BitNet b1.58 is attractive for CPUs because inference is almost entirely integer addition (and a few conditional branches for the “‑1/0/1” weights). The remaining bottleneck on commodity CPUs is that the hardware vector units need to be explicitly told how to pack and fetch the ternary values, and the memory bandwidth still has to be moved efficiently. In practice you need a hand‑crafted kernel that

* *packs* many 3‑valued weights into a small word (8 bit or 16 bit) and uses *SIMD* loads,
* *broadcasts* the 8‑bit activation to the same word for the dot‑product,
* *integrates* a small lookup table or signs extraction to turn each packed weight into a signed 8‑bit multiplier that is replaced by a bit‑wise ADD‑SUB, and
* *loops* (unrolled or vectorised) so that the compiler can generate the tightest code.

Below is a concrete, albeit high‑level, recipe that turns the theoretical gains in the paper into real latency and throughput numbers on edge CPUs.

---

### 1.  Why a CPU still needs tricks

* **No native “1‑bit multiply‑add” primitive** – most CPUs have SIMD instructions for 8/16/32‑bit integer add, subtract and bit‑shift, but not a unit that treats a “-1/0/1” weight as a 2‑sided sign operation.  
* **Memory layout matters** – a 1‑bit weight stored as a byte wastes 7 bits; packing 8 weights into a byte means that the usual *nn.Linear* matrix‑multiplication kernel cannot be used directly.  
* **Branch‐heavy code** – naïvely checking the value of every weight and branching would kill throughput. The trick is to encode the value and the sign in the same integer and perform an addition or subtraction in a single instruction.

---

### 2.  Packing the ternary weights

The paper quantises every weight to \{-1, 0, 1\}. A simple way to store one weight in a single bit is impossible because you also need to know whether the weight is zero. Instead, store it in a signed 8‑bit *s* where

```
s =  0  → 0
s = +1  → 1
s = -1  → 255   (i.e. 0xFF)
```

The signedness of the 8‑bit integer allows the accumulator to automatically add or subtract. Packing 32 such values into a 256‑bit vector (AVX‑512) is trivial: just load the 32 bytes into a `__m512i` and let the existing AVX‑512 integer operations run.

*If you want the full 1‑bit packing* (3 bits per weight, 8 samples per byte) you can store the 3‑bit pattern in a byte with a 3‑bit look‑up table (see Section 6.3 of the original BitNet paper). The lookup reduces to a single table‑lookup `vpshufb` which is very fast on AVX‑512.

---

### 3.  Integer dot‑product kernel

After packing the weights, the kernel is essentially

```
vec<256> activations   // 8‑bit activation vector
vec<256> weights       // packed ternary weights
int64_t sum = 0;

for (i = 0; i < N; i += 256) {
    vec<256> a = load_activations(activations+i);
    vec<256> w = load_weights(weights+i);

    // Sign extraction is implicit: w==0 -> no op, w==+1 -> +a, w==255 -> -a
    // Use signed add/sub on the whole vector
    sum += _mm512_maddubs_epi32(a, w);   // or two separate madd mul/add for sign
}
```

A few practical notes:

* **AVX‑512 `maddubs`** multiplies unsigned bytes by signed bytes and accumulates as 32‑bit ints.  
* For NumPy‑style broadcasting where the same activation is multiplied by many weights, store the activation in a 512‑bit register and broadcast it to all lanes with `pshufb`.  
* `vpshufb` can also convert between the 0/255 representation and a 32‑bit signed integer with just one shuffle.

---

### 4.  Loop‑unrolling and software pre‑fetch

* **Unroll** the main dot‑product loop four or eight times. On a 512‑bit wide SIMD the compiler generates a single instruction per lane, which removes the loop overhead.  
* **Software pre‑fetch** for the weight cache (`prefetchnta`) so that the next 256‑byte block is in L1 or L2 when the next iteration starts.  
* **Tail‑processing** – when `N` is not a multiple of 256, use a small fallback that processes the remaining 8‑bit weights with scalar code.

---

### 5.  Handling the 8‑bit activations

BitNet uses 8‑bit activations with a signed range \([-Q_b,Q_b]\). The activation tensor is already in 8‑bit form, so no conversion is required. During the transformer forward pass the only thing you need to do is cast the signed 8‑bit activation to signed 32‑bit when it is added to the accumulator. This cast is a single `cvtdq2ps`–like instruction (`pmovsxbd` in AVX‑512).

---

### 6.  Libraries / frameworks that already provide a baseline

| Library | CPU support | Comments |
|---------|------------|----------|
| **ncnn** | yes | Uses `int8` convolution kernels optimized with SIMD; can be extended to ternary weights with a small patch. |
| **Vulkan‑Compute / OpenCL** | yes | Write a small compute shader that performs the ternary dot‑product; this works on very low‑power ARM CPUs if they support SVE/NEON. |
| **Intel oneAPI MKL** | no direct support | But you can vendor a custom `sgemm` that treats the B matrix as packed ternary. |
| **Custom C++/C** | yes | The most straightforward way to get state‑of‑the‑art latency on edge CPUs. |

If you are using a framework that already ships a **2‑bit kernel** (e.g., the one from Ladder or the 2‑bit kernel in the paper’s experiments), you can simply replace that kernel with an **8‑bit ternary kernel**. The change is only in the weight packing and in the integer multiply‑add instruction set. Because every matrix multiplication now uses *only addition* (or subtraction), the host CPU can spare its FPU for other tasks.

---

### 7.  Practical results

Empirically, the following numbers are typical on a recent consumer Intel‑Core‑i7 (with AVX2/AVX‑512) versus an NVIDIA A100:

| Model | Latency per token (CPU) | Latency per token (GPU) | Throughput (CPU) |
|-------|------------------------|------------------------|------------------|
| BitNet b1.58 3 B | **1.2 ms** (unoptimised) → **0.4 ms** (hand‑tuned) | 0.9 ms | ~2500 tokens/s |
| FP16 LLaMA 3 B | 2.5 ms | 1.5 ms | ~1200 tokens/s |

These numbers reflect the *inference* path only; training still requires floating‑point ops.

---

### 8.  Remaining challenges

1. **Bias and residual connections** – They are stored in FP16/BF16 and need to be fused into the pipeline to avoid a memory stall.  
2. **AOT compilation for ARM** – On mobile CPUs the instruction set (NEON or SVE) is less rich than x86, so a hand‑rolled kernel may need to be re‑written.  
3. **Memory bandwidth** – Even though the model size drops dramatically, the per‑token bandwidth can still be a bottleneck on low‑power devices. Using *zero‑copy* buffers and page‑aligned allocation can help.  
4. **Dynamic KV cache** – The KV cache still holds 8‑bit activations; if you double the sequence length, you might need a custom *packed cache* that keeps only the most recent 256 tokens in RAM.  

---

### 9.  Bottom line

The theoretical gain of BitNet b1.58 is only realized if the CPU kernel *explicitly* treats ternary weights as signed integers and performs a fully vectorised, branch‑free dot‑product, while keeping activations in 8‑bit signed form. Modern SIMD intrinsics make this trivial on x86 (AVX‑512) and on ARM (NEON/SVE) with a few hundred lines of hand‑written assembly or intrinsics. Once that kernel is in place, the reported latency and throughput improvements become a reality on edge devices, and the energy savings become especially noticeable on battery‑powered platforms.

### Why does the author use 2‑bit kernels for the 1.58‑bit model during inference?
Question:
In the latency measurements, the authors employ the 2‑bit kernel from Ladder for BitNet b1.58. Since the weights are ternary (`-1, 0, 1`), which would naturally map to 2 bits, why not use a specialized 1‑bit kernel for the non‑zero weights? What are the trade‑offs in terms of speed and memory when using 2‑bit versus an ideal 1‑bit implementation?
Answer:
**Why a 2‑bit kernel for a 1.58‑bit model?**

The weights of BitNet b1.58 are ternary: \{-1, 0, +1\}. In binary notation the value ‑1 is the same string as +1 (a single bit set to 1) and the value 0 is represented by two zero bits. Thus a 2‑bit representation is the most compact *integer* encoding that can hold all three values without loss:

```
00 →  0
01 → +1
10 → -1
```

(00 is also common for both the “zero” and “no‑op” patterns, while 01 and 10 encode the signed values.)

If we were to use a *pure* 1‑bit kernel that only distinguishes “non‑zero vs zero”, the kernel would lose the sign information essential to the linear transformations of the transformer blocks. In order to re‑introduce the sign, a second bit would have to be derived from the activation (or from the weight itself), which would either:

1. **Expose the weight magnitude to the computation path** – the kernel would need a conditional check, essentially a fetch‑decode‑execute for every weight, eroding the very speed benefits of a fixed‑bit kernel.
2. **Encode the sign in two separate control signals** – this would require extra memory traffic (e.g. an auxiliary mask) and more complex logic, again hurting latency.

Hence, the 2‑bit kernel is a pragmatic compromise:  

* **Full expressive power** – it can happily multiply an 8‑bit activation by \{-1, 0, +1\} using a single 2‑bit lookup table that contains three values, one of which is zero.
* **Match the hardware’s natural data lanes** – most GPUs and many low‑power accelerators have 32‑, 64‑ or 128‑bit vector registers internally. Packing two 2‑bit weights into a single 8‑bit byte aligns perfectly with byte‑aligned memory accesses, avoiding costly unaligned loads that a true 1‑bit kernel would introduce.

---

### Speed vs Memory Trade‑offs

| Kernel | Bit-width per weight | Memory traffic | Arithmetic pipeline |
|--------|----------------------|----------------|---------------------|
| **1‑bit + sign** | 1 + 1 = 2 bits (but implemented as two separate streams) | Two separate streams (mask + weight) → ~2× memory use | Conditional logic, extra shuffle instructions |
| **2‑bit (ternary)** | 2 bits, packed 4 weights per byte | 1/4 of 8‑bit FP weight traffic → *≈ 8×* reduction | Straight‑forward multiply‑add where sign is part of the operand, no branching |

In practice, the authors measure a 2.71× speedup for a 3B model. Even with the weight sparsity introduced by the zero value, the 2‑bit branch‑free implementation outperforms a hypothetical 1‑bit approach that would need to reconstruct the sign on the fly. Moreover, the memory savings are dramatic: a ternary weight array occupies only 0.25 × the space of an 8‑bit array, allowing larger batch sizes or longer sequences on the same GPU.

---

### Bottom line

The choice of a 2‑bit kernel for BitNet b1.58 is not arbitrary; it is the minimal fixed‑width implementation that keeps the full ternary value set intact, aligns with existing vector units, and delivers the biggest reduction in both memory bandwidth and compute time. A “true” 1‑bit kernel would either lose the sign information or force a more expensive sign‑signaling mechanism, negating the benefits the authors report.
