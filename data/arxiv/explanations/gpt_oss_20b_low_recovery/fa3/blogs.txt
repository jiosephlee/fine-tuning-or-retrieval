# Unpacking FlashAttention‑3: Why Speedy Attention Matters for Long‑Context Models

In the Transformer world, the *self‑attention* layer is the superstar.  
It lets every token talk to every other token, and that is precisely what gives language models their power.  
But the price of that power is steep: the cost of computing the attention matrix grows **quadratically** with the sequence length.  
When we want a model to read hundreds of thousands of tokens—think multi‑document summarisation, code‑base browsing, or long‑form dialogue—the quadratic cost turns the attention layer into a severe bottleneck.

FlashAttention‑3 is the new kid on the block that tackles this bottleneck head‑on.  
It builds on the earlier FlashAttention streams and adds three game‑changing techniques that leverage modern GPU features:  
1. **Warp‑specialised asynchrony**—hiding memory and matrix‑multiply latency.  
2. **Softmax‑under‑GEMM overlapping**—making non‑arithmetical work breathe while Tensor Cores are busy.  
3. **FP8‑friendly design**—pushing throughput with low‑precision while keeping numerical error low.

Below we explain why each of these matters, how FlashAttention‑3 implements them, and what gains it delivers in real workloads.

---  

## 1. Attention’s Quadratic Curse

The vanilla multi‑head self‑attention for a single head is

```
S = α · Q · Kᵀ          # score matrix, N×N
P = softmax(S)          # row‑wise normalisation
O = P · V                # output, N×d
```

For a batch of `B` examples, `H` heads and a sequence length `N`, the FLOPs of the forward pass are

```
4 · B · N² · d · H        (≈ 4·batch·N²·head‑dim)
```

A double‑size sequence (from 4k to 8k tokens) multiplies the cost by 4.  
On a modern transformer this means a 10‑fold slowdown just for the attention part.

Early optimisations such as *local softmax* in FlashAttention merged the softmax evaluation into a single kernel, eliminating intermediate global‑memory traffic.  
FlashAttention‑2 further tiled across the key/value dimension, boosting occupancy on GPUs.  
Yet on recent NVIDIA Hopper (H100) GPUs, FlashAttention‑2 achieved only ~35 % of the peak FLOP utilisation that a standard GEMM kernel could hit.  
That gap signals that hardware capabilities introduced with Hopper were not yet being used by the algorithm.

---

## 2. Leveraging Hopper’s New Toys

### Warp‑specialised async pipelines

Hopper introduces two powerful asynchronous units:

* **Tensor Memory Accelerator (TMA)** – fast, non‑blocking moves between host memory and shared memory.
* **Warp‑group GEMM (WGMMA)** – an async Tensor‑Core operation that can source its inputs directly from on‑chip shared memory.

When we make two separate groups of threads (warps) inside a CTA do *different* jobs—one loads data with TMA (the *producer*), the other consumes that data with WGMMA (the *consumer*)—the GPU can keep the Tensor Cores busy while data is still being fetched.  
`setmaxnreg` lets us hand out more registers to the consumer warps, since they need them to keep the GEMM pipeline going.

The result is a *ping‑pong* between producers and consumers: while one batch of the softmax is running, the other batch’s matrix multiply has already started.  
Because exponential operations sit on a tiny specialised unit (≈ 16 ops per cycle across the whole GPU), overlapping them with GEMM brings the softmax’s 3.9 TFLOPs to the same time‑budget as the 989 TFLOPs of FP16 matmul, substantially improving utilisation.

### Softmax under the GEMM

Even inside a single consumer warpgroup we can pipeline rows of the softmax and the next GEMM.  
The naive code would:

1. Compute `S = Q · Kᵀ` (first GEMM).
2. Train the row‑max, then exponentiate (softmax).
3. Compute `O += P · V` (second GEMM).

Every step waits for the previous one to finish, so the fast GEMM stalls behind the cheap exponentials.

FlashAttention‑3 reorganises the loop into a 2‑stage pipeline:

```
S_cur = Q · K_cur^T
softmax(S_cur) → P_cur
O_cur += P_cur · V_prev
```

Here the *next* GEMM (`Q · K_next^T`) starts right after `S_cur` is ready, while the *previous* GEMM (`P_cur · V_prev`) finishes.  
Both GEMMs are launched with WGMMA and allowed to run concurrently for a few clock cycles.  
The crucial condition is that the output of `S_cur` must be available before `P_cur` is needed, which the buffer organisation guarantees.

---

## 3. Going FP8 – Twice the FLOPs, Still Accurate

### Layout gymnastics

Hopper’s FP8 Tensor Cores can deliver twice the throughput of FP16, but only if the operands use a specific *k‑major* layout.  
The attention algorithm naturally tiles the key/value matrices in the *m‑n* layout (rows first).  
To reconcilie this, the FP8 kernel does an **in‑kernel transpose** of a tile of `V` after loading it into shared memory.  
`LDSM`/`STSM` (warp‑wide load/store matrix) instructions perform this tile‑transpose efficiently, without touching the host memory again.

The accumulator produced by WGMMA lives in a different register layout than the operand.  A simple byte‑permute after each GEMM reorders the accumulator to match the next GEMM’s expected input format.  Because every warp owns its own 8‑word piece of the accumulator, this is a lightweight operation.

### Keeping the error in check

FP8 (`e4m3`) has only 3 mantissa bits, causing higher relative error especially for outlier values that appear in large LLMs.  
FlashAttention‑3 mitigates this in two ways:

1. **Block quantisation** – instead of one global scale for the whole tensor, each tile gets its own scaling factor.  
   The attention matrix then uses a per‑block scaling when it multiplies `Q` and `K`, so the relative error is reduced with little extra cost.

2. **Incoherent processing** – both `Q` and `K` are multiplied by a random orthogonal matrix (`M`), which preserves their dot‑products but spreads out the magnitude of individual elements.  
   With a Hadamard‑plus‑diagonal construction, this step is cheap enough to be fused into the existing rotary‑embedding routine.

Empirical tests show that FP8 FlashAttention‑3 is **2.6× more accurate** than a naive per‑tensor FP8 attention implementation, while still delivering the speed advantage of half‑precision.

---

## 4. Results that Matter

| Precision | Speedup vs. FlashAttention‑2 | Peak FLOPs | Relative utilisation |
|-----------|-----------------------------|------------|----------------------|
| FP16      | 1.5–2.0× (forward)          | ~740 TFLOPs  | 75 % of theoretical |
| FP8       | ~1.2 PFLOPs (forward)        | ~1 PFLOPs   | ~90 % of theoretical |

The numbers are read from practical benchmarks on an H100 SXM5.  
For medium‑to‑large sequence lengths (≥ 4 k tokens) FlashAttention‑3 matches or surpasses cuDNN’s proprietary attention implementation, which had been heavily tuned for Hopper.

---

## 5. Why All of This Is Important

1. **Long‑context is the next frontier.**  
   As models grow, the need for end‑to‑end vs. windowed attention diminishes. Fast, exact attention makes full‑sequence inference viable.

2. **Training acceleration.**  
   Every epoch sees these cost savings reflected in wall‑clock time and energy consumption—critical for research labs and production services alike.

3. **Hardware‑aware software.**  
   The techniques in FlashAttention‑3 are not H100‑only: any GPU that supports async Tensor Cores and low‑precision WGMMA can benefit.

4. **Bridging accuracy and throughput.**  
   FP8 acceleration with controlled error opens new trade‑offs: we can run 8‑bit inference without sacrificing model fidelity.

---

## 6. Takeaway

FlashAttention‑3 shows that *software can be as powerful as hardware* when the two are designed together.  
By 1) separating data movers and compute units, 2) overlapped releasing of softmax work, and 3) careful FP8 layout management, it turns a quadratic bottleneck into an efficient, high‑utilisation kernel.

If you’re dealing with Transformers that read longer contexts, or simply want faster training loops, adding FlashAttention‑3 to your stack is a no‑brainer.  

> **Code is everywhere.**  
>  The implementation is open‑source under a permissive license and already hooks into PyTorch, Hugging Face, and Triton.  Grab it, try it, and see the sweet spot between speed and accuracy for your own long‑sequence workloads.



# Warp‑Specialization and Asynchrony: The Secret Sauce of FlashAttention‑3

Long‑context transformer models are bottlenecked by the quadratic cost of the self‑attention layer. One of the most compelling ways to shrink that bottleneck is to fuse all the attention work into a single CUDA kernel, eliminating the need to spill intermediate matrices to global memory. The first version of that idea was **FlashAttention‑2**. In 2023, the authors released **FlashAttention‑3**, a new kernel that takes full advantage of the Hopper H100 architecture’s asynchrony and low‑precision capabilities. The difference between FlashAttention‑3 and its predecessors is largely a *war‑specialization strategy* that lets some warps work as producers (loading data off‑chip) while other warps consume that data (running the tensor cores). On top of that, a clever “ping‑pong” scheduling technique hides the latency of Softmax operations behind fast matrix multiplications. In this post we unpack those ideas and show why they matter.



## What does warp‑specialization mean?

On an NVIDIA GPU, the execution unit that does most arithmetic is a *warp*—a group of 32 threads that execute in lock‑step. In a typical kernel, every warp pulls through all the same instructions: load a chunk of data, do a multiply‑add, store the result, and so on.

FlashAttention‑3 splits the warps in a thread block into **two roles**:

1. **Producer warps** – these warps only issue memory‑transfer instructions. They pull 128‑byte chunks of Q, K, V from global memory (HBM) into the on‑chip shared memory (SMEM) using the *Tensor Memory Accelerator* (TMA) — a hardware unit that can move a large amount of data per cycle.

2. **Consumer warps** – these warps focus on computation. Once the producer has finished staging a block in SMEM, the consumer warps launch the *Warp‑Group‑Matrix-Multiply-Accumulate* (WGMMA) instruction to multiply the tilized matrices directly in registers or shared memory. WGMMA runs on the tensor cores and produces the matrix‑multiplication result in an FP32 accumulator, even when the inputs are in FP8.

Because producers and consumers run the *same* warp group only once, each warp group can use the optimal number of registers for its job: producers need very few registers, consumers can afford a bigger register file. This **warp‑specialization** is not just a nicety—it dramatically boosts how efficiently the kernel uses the raw compute resources of the GPU.



## Overlap by ping‑pong

Even with warp‑specialization, the kernel still has to compute the Softmax and its reductions, which do *not* run on the tensor cores. On the H100, an SM can compute roughly **989 TFLOPS** of FP16 matrix multiplications, but only **3.9 TFLOPS** of special‑function operations such as exponentials. If we naively schedule the Softmax *after* the matrix mult, we would sit idle for a large chunk of the GPU’s clock cycles.

FlashAttention‑3 resolves this by interleaving work between two consecutive blocks of the attention score matrix. Think of it like a two‑person relay:

- **Warp‑group A** launches a WGMMA for the first block of `Q·Kᵀ`. While that multiplication is still underway, warp‑group B starts the Softmax on the *next* block of scores. Because the Softmax routine runs on a different hardware unit, the two operations can run in parallel.

- Once warp‑group A completes its multiplication, it immediately consumes the Softmax output of warp‑group B, while warp‑group B goes back to the matrix multiplication stage for the *following* block.

This **ping‑pong scheduling** creates a two‑stage pipeline inside each warp group. Only when one stage finishes does the other move on to the next block. The resulting effect is that the tensor cores are kept busy generating products; the Softmax calculations constantly sit in the background, never starvation the tensor cores.

In practice, the kernel uses explicit barriers (`bar.sync`) to ensure the pipelines stay in sync. By carefully arranging the dependencies, the compiler is able to produce assembly that keeps the tensor cores and exponent units working *in parallel*, rather than one waiting for the other.



## How much does it help?

The combination of warp‑specialization and ping‑pong pipelining turns the previously under‑utilized tensor cores into a more productive workforce:

| Precision | Speedup over FlashAttention‑2 | Peak TFLOPs/s on H100 | Utilization |
|-----------|-----------------------------|----------------------|-------------|
| FP16 | 1.5–2.0× | 740 | 75 % |
| FP8  | ~2× | 1.2 PFlops | 90 % |

The striking lesson is that the major speed gains come **not** from rewriting the math, but from matching the math to the GPU’s real‑world execution model. By letting producers keep the gather units firing while consumers keep the tensor cores busy, and then interleaving Softmax with matmul hops, FlashAttention‑3 reaches utilisation rates that approach the theoretical maximum on the H100.



## Where does the “magic” happen on Hopper?

The Hopper architecture introduced two changes relevant to this technique:

1. **Asynchronous WGMMA** – the tensor‑core kernel no longer stalls while waiting on data from SMEM. Warps can fire off a multiply and immediately go grab the next piece of data from global memory. The ‘producer’ warps can asynchronously keep the consumer warps fed.

2. **Dedicated TMA** – a separate large‑bandwidth data transfer engine that can be scheduled independently of the tensor cores. By treating data loading as a producer, the kernel can hide global‑memory latency in the background.

These features enable the two distinct, pipelined stages to overlap without the usual serialization that you see on older GPUs. As a result, the kernel can keep all of the 132 streaming multiprocessors busy, and the H100 shows roughly three‑quarters of its raw floating‑point capability spent on the attention algorithm.



## Key take‑aways

- **Warp‑specialization + ping‑pong pipelining** is maybe the simplest, most hardware‑friendly upgrade that can yield a ~2× speedup in a real CUDA kernel.

- The technique works *by design* – it piggybacked on new architectural features (asynchronous WGMMA, TMA) rather than requiring a deep redesign of the mathematics.

- Floating‑point *precision* is orthogonal to the scheduling gains. Even with FP8 inputs, the same strategy doubles the performance and retains high accuracy thanks to block quantization and incoherent processing discussed in the paper.

- The kernel demonstrates that to make transformers scale to longer sequences, you don’t just need smarter approximations—it also helps to fully exploit the host GPU’s execution model.



FlashAttention‑3 shows that modern GPUs offer powerful primitives for *asynchronous* execution that you can harness with clever warp‑level scheduling. The result: a faster, more accurate attention primitive that is now available as open source (https://github.com/Dao-AILab/flash-attention). If you’re building long‑context transformers or just hungry for performance, give it a spin and see the 75 % utilization in action.



# Overlapping Softmax with Matrix Multiplications:
## A 2‑Stage Pipeline Explained

Attention is the workhorse of every contemporary Transformer.  
The forward pass of single‑head self‑attention looks like this:

1. **Score matrix** –  \(S = QK^{\top}\)  
2. **Softmax** –  \(P = \text{softmax}(S)\)  
3. **Output** –  \(O = PV\)

With a sequence length \(N\) and head dimension \(d\) the naive cost is
\(O(N^2 d)\) FLOPs – quadratic in \(N\).  The bottleneck is clear:  
the two matrix–matrix multiplications (MM) dominate the FLOP count, but
the softmax in the middle is a tiny fraction of the work and can’t simply
be fused into a single fused‐kernel without careful scheduling.

---

## The traditional approach

The original **FlashAttention** algorithm reduces memory traffic by:
- fusing the two MM and the softmax into one kernel,
- materializing intermediate tiles on‑chip,
- and keeping all intermediate results in 32‑bit precision.

While that removes memory stalls, the implementation still follows a *strictly synchronous* execution order:

```
for each key block j:
    S_j = Q · K_j^T        # MM 1
    P_j = softmax(S_j)     # softmax
    O  += P_j · V_j        # MM 2
```

Each step must complete before the next one starts, even though  
`softmax` and the *next* MM 1 are completely independent.  
The result is that a large fraction of the GPU cycles are spent waiting
for the low‑throughput softmax unit (the “special function unit”) to
produce its output.

---

## What the 2‑stage pipeline changes

### 1. **Warp‑specialisation + ping‑pong buffering**

- Divide the CTA (thread block) into two *warp‑groups*:  
  **Producer** (loads data from global memory via the Tensor Memory
  Accelerator – TMA) and **Consumer** (does the math).
- Use a *circular* shared‑memory buffer so that the producer can keep feeding
  data without stalling the consumer.

### 2. **Overlap the two மெ ≥×

```
S_cur = Q · K_cur^T          # first MM of (j)
P_cur = softmax(S_cur)       # softmax of (j)
O += P_cur · V_prev          # second MM of (j-1)

# while the above two kernels run, start the next MM:
S_next = Q · K_next^T
```

*Key insight:*  
The *next* MM 1 (`S_next`) can start **before** the current softmax finishes,
because its input `K_next` is already in shared memory and the MM can run
asynchronously on the Tensor Cores.  Likewise, the *next* softmax can start
once `S_next` is ready, overlapping with the second MM of the previous
iteration.

### 3. **Breaking data dependencies**

- **Matrix 1** (`S_cur`) → **Softmax** → **Matrix 2** (`O += …`)  
  The pipeline unhooks the *read‑back* dependency: the second MM can use
  the *previous* softmax result while the new softmax is still computing.
- The *issue* that `S_next` must be ready *before* `softmax` has finished
  is handled by **register tiling**: `S_next` is stored in a separate set of
  registers so that its computation can finish before the softmax of the
  *next* iteration begins.

---

## Why this matters

| Ratio (softmax / matmul) | Theoretical overlap potential |
|--------------------------|-------------------------------|
| FP16: 1 : 512 (softmax much slower) | ~50 % of time can be hidden |
| FP8: 1 : 1024 | Even larger gap |

On an NVIDIA H100, **FP16 matmul** throughput is ≈ 989 TFLOPs, while the
exponential unit needed for softmax delivers only ≈ 3.9 TFLOPs.  
The 2‑stage pipeline allows the 3.9 TFLOPs to be *run in the shadow* of the
989 TFLOPs, bringing the effective throughput close to the hard limit of
the matmul unit.

---

## Benchmarks – numbers to impress

| Variant | FP16 Forward | FP16 Backward | FP8 Forward |
|---------|--------------|---------------|-------------|
| FlashAttention‑2 | 570 TFLOPs (∼ 55 % util) | 700 TFLOPs | 600 TFLOPs |
| FlashAttention‑3 (2‑stage) | **661 TFLOPs** (∼ 75 % util) | **780 TFLOPs** | **≈ 1.2 PFLOPs** |
| Vendor cuDNN (H100‑optimised) | 720 TFLOPs | 850 TFLOPs | – |

*Interpretation*:  
The 2‑stage overlap gives a **≈ 15 % boost** over non‑overlapped FP16,
and the *combined* effect of warp‑specialisation plus softmax‑overslap
is a **1.5–2×** speedup for very long sequences (N ≥ 8192).
In FP8, the overlap more than compensates for the two‑× slower special‑
function unit, yielding almost a full *peta‑flop* regime on a single H100.

---

## The backward pass

The backward pass needs four matrix multiplications (derivatives w.r.t.
`Q`, `K`, `V`) and two softmax derivatives.  The same idea applies:

```
dS = dsoftmax(dP)         # computed in parallel with upstream grads
dQ = dS · K               # MM 1
dK = dS^T · Q             # MM 2
```

By threading the softmax derivative into its own two‑stage pipeline,
the FLOPs for the backward pass scale similarly, yielding the 1.5–1.75×
backward speedup reported in the paper.

---

## Bottom line

- **Template for all future hygiene‑first kernels**:  keep math separate,
  run the expensive (matrix) kernels on Tensor Cores, and let light
  computations (softmax, exponents) dance in the driver’s chair.
- **Hardware synergy**: the Hopper GPU’s *asynchronous* Tensor Cores and
  *Tensor Memory Accelerator* make the 2‑stage pipe natural.
- **Ease of integration**: the 2‑stage code is only a handful of extra
  wait/commit instructions and an extra buffer; no complicated
  re‑ordering of the core algorithm.

If you’re building a high‑performance LLM or long‑context
transformer, a 2‑stage GEMM‑softmax pipeline can unlock
the missing 15–20 % of that latency budget.  And that’s a lot
when you’re thinking in thousand‑token, multi‑GPU training jobs.



# Low‑Precision Attentions: Why FP8 Matters and How FlashAttention‑3 Keeps Accuracy

## The Long‑Context Problem

Attention is the heart of every transformer‑style model, from GPT to Stable Diffusion.  
Its cost grows quadratically with the length of the input: a 4,096‑token sentence is already 16× more expensive than a 512‑token one.  For “long‑context” tasks—chatting over a full book, analyzing a whole codebase, or generating frame‑by‑frame video—reducing the per‑token cost becomes a necessity.

The latest NVIDIA Hopper GPUs (H100) can run the 4‑GEMM cascade of attention with astonishing raw throughput—over 9 TFLOPs per SM for FP16 matrix multiplication—and even a *quadruple* speed‑up for FP8, thanks to the new Tensor Core “WGMMA” instruction.  The barrier, however, is **numerical error**: when you crank the precision down to FP8, the arithmetic starts to drift, and the soft‑max that follows the dot product can amplify tiny mistakes into huge mistakes.

**FlashAttention‑3** tackles that drift head‑on, leveraging two new trick pairs:

1. **Block quantization** – quantise *per‑block* instead of *per‑tensor*.
2. **Incoherent processing** – shuffle the data with a random orthogonal matrix before quantisation to spread out extreme values.

Together, they cut FP8 error by more than a factor of **2.6** compared to naïve FP8 scaling.  Below we walk through why FP8 matters on Hopper, what the layout hurdles look like, and how the two tricks stack up.

---

## 1. Why FP8 Is a Game‑Changer on Hopper

### 1.1 The Hopper Premium: Asynchrony + Low‑Precision

Hopper GPUs aren’t just a faster version of Ampere; they expose two separate accelerators that can run in concert:

- **Tensor Cores (TMA‑friendly)**: GPU‑wide floating‑point matrix multipliers that can use FP8 operands, yielding roughly double throughput per SM relative to FP16 or BF16.
- **Tensor Memory Accelerator (TMA)**: a dedicated copy engine that streams data from global memory into shared memory without touching the instruction scheduler.

Because the two units act independently, *asynchronous* programming – overlapping data movement with computation – lets you hide almost all memory‑latency.  If you can keep the Tensor Cores busy, you can burst you right into the 9 TFLOPs FP16 speed‑up or the 18 TFLOPs FP8 speed‑up that Hopper offers.

### 1.2 Layout Constraints for FP8 WGMMA

The catch with FP8 is that the WGMMA instruction has a **strict operand layout**:

| Operand | Requires “mn‑major” (outer dimension contiguous) | Requires “k‑major” (inner dimension contiguous) |
|--------|-----------------|-----------------|
| FP8 input | ❌ | ✅ |
| FP32 accumulator | ✅ | ❌ |

In plain language: the first operand can come from shared memory if it’s laid out by rows (the outer dimension), but the *second* operand has to be laid out by columns (k‑major).  Your standard after‑embedding matrices `Q`, `K`, and `V` are usually laid out “head‑first” (i.e., contiguous along the head dimension).  That layout satisfies FP16 VMMAs but not the FP8 rule.

Concretely:

- `K`: For the `Q x Kᵀ` belief calculation, you want `K` in `k‑major` because you’re dot‑producting row‑by‑row with `Q`.  In FP8, that means you have to reverse the stride in the sequence‑length dimension.
- `V`: In the second GEMM `P x V`, `V` must again be column‑major.  Unfortunately, the FP32 accumulator produced by the first FP8 GEMM isn't in a layout that’s compatible with the second one.

So the algorithm designers had to **transpose** tile‑wise inside the kernel, not globally (because a global transpose would require a separate pass and would kill throughput).

---

## 2. In‑Kernel Transpose Magic

### 2.1 Using LDSM/STSM

Hopper includes **LDMatrix (LDSM)** and **STMatrix (STSM)** – tiny instructions that let an entire warp read a 128‑byte sub‑matrix from shared memory into registers, or write it back.  By arranging the warp’s load and store pattern cleverly, you can *transpose* a tile on the fly:

```
warp loads 8×8 block of V (row‑oriented)  → registers
warp stores 8×8 block transposed (column‑oriented) → shared memory
```

This in‑kernel transpose satisfies the FP8 layout requirement *without* touching global memory again.  It also frees up the PGMMA instruction to feed the next block while the transpose runs in another warp, which is the basis for the “ping‑pong” overlapping trick later (section 4).

### 2.2 Register‑Level Re‑Ordering of the Accumulator

The second FP8 GEMM needs the FP32 accumulator from the first GEMM in a different *register* layout.  The pack-of-8 logic in WGMMA stores an 8‑element tile in a quirky order.  By hashing the registers using `shfl` or `byte permute` (in PTX parlance), you can reorder them to the format expected by the next WGMMA call.  No extra memory traffic, no extra kernel launches.

---

## 3. Why the Number is Small – Quantisation Errors

FP8 (e4m3) uses only 3 mantissa bits and 4 exponent bits.  That gives **≈ 256 discrete values** compared to 65536 for FP16.  When you multiply two 256‑valued numbers you lose a lot of fidelity; it’s not just a rounding error – the range’s *dynamic* shift can dramatically mis‑scale the dot products.

What becomes noticeable is **out‑of‑range** or **outlier** values.  In large language models, hidden states sometimes shoot off into the 20‑plus range; a single outlier can dominate the soft‑max numerator and skew the entire attention distribution.

---

## 4. Two Layers of Protection

### 4.1 Block Quantization

Instead of a single scaling factor for an entire tensor, think of the tensor as a grid of *tiles* and give each tile its own scale.  Operationally:

1. When `Q`, `K`, and `V` are loaded, we *immediately* compute a per‑tile maximum absolute value.
2. Divide the tile by that value to fit it into FP8’s representable range.
3. Store the *scale* (one 32‑bit float per tile) alongside the quantised tile.

Because FlashAttention‑3 processes data block‑by‑block, this extra per‑tile scaling doesn’t add any kernel launch or memory traffic.  The soft‑max routine internally *remembers* the scale and adjusts when it recomputes the dot product, so the mathematical result stays the same.  The net effect is that large and small numbers get a fair chance to be represented.

### 4.2 Incoherent Processing (Random Rotation)

A better way to dampen outliers is to **randomly mix** the entries of `Q` and `K` *before* quantisation.  Let

```
Q' = Q × M          // M is an orthogonal matrix
K' = K × M
```

Since `M` is orthogonal (`M Mᵀ = I`), the dot product `Q' K'ᵀ` equals `Q Kᵀ`.  But the entries of `Q'` and `K'` become *weighted sums* of many original entries.  In practice we build `M` cheaply:

- Take a Hadamard matrix (cheap, `O(d log d)`).
- Randomly flip signs with a diagonal matrix of ±1.
- Multiply: `M = D × H`, so `Q' = (Q × H) ⊙ D`.

The Hadamard transform simply re‑orders and flips signs; the sign flips further randomise.  This operation is exercised by the same memory‑bandwidth stall as the rotary embedding, so it doesn’t cost extra compute.

The net result is a *more uniform* distribution of values in `Q'` and `K'`.  Consequently, fewer outliers survive quantisation, reducing the number of “large‑error” tokens that would otherwise dominate the soft‑max numerator.

### 4.3 Quantitative Impact

In the FlashAttention‑3 paper, the authors measured root‑mean‑squared error (RMSE) against a FP64 reference on synthetic tensors that mirrored LLM outlier distributions.  Benchmarks:

| Variant | FP8 RMSE | Relative to naive per‑tensor FP8 |
|--------|--------|-----------------------------------|
| Naïve FP8 | X | baseline |
| Block quantisation + incoherent processing | X / 2.6 | 2.6× better |

That means you can comfortably chatter in FP8 and still trust the outputs to be within a couple of percent of the FP16/FP32 reference.

---

## 5. Putting It All Together – The FlashAttention‑3 Flow

Below is a high‑level sketch of the forward pass for a single head:

```
for each Q‑block Q_i:
    load Q_i into shared mem

    for each K‑block K_j, V_j:
        // 1. No‑block quantise Q_i, K_j, V_j as needed
        // 2. Asynchronous: launch WGMMA Q_i × K_jᵀ  (FP8)
        // 3. While WGMMA running, compute exp() of previous score block in FP16
        // 4. When WGMMA completes, normalise scores, multiply with V_j (FP8)
        // 5. Accumulate the partial result O_i
```

By running the *two* most expensive FP8 GEMMs in parallel (thanks to asynchronous Tensor Cores) and overlapping the *slower* exp() calls, the kernel keeps the Ratios well‑balanced.

At the end of the loop, a final FP32 rescaling restores the soft‑max scale (the `ℓ` term in the algorithm) so you get a *valid* attention output.

---

## 6. Bottom‑Line Takeaways

| Question | Answer |
|----------|--------|
| Does FP8 hurt accuracy? | Yes, if you just drop FP16 scaling. |
| How does FlashAttention‑3 solve it? | 1) Do block‑wise scaling; 2) Apply a cheap random orthogonal transform before quantisation. |
| Why FP8 on Hopper? | Hopper’s Tensor Cores double throughput for FP8, and the TMA engine lets you hide all memory movement. |
| What about memory layout? | Use in‑kernel transpose with LDSM/STSM and register‑level re‑ordering to satisfy FP8 WGMMA. |
| Resulting throughput? | 740 TFLOPs/s FP16, 1.2 PFLOPs/s FP8, with 80–90 % GPU utilisation. |

**FlashAttention‑3** proves that you can trade half the memory bandwidth (by dropping to FP8) without a substantial loss in numerical correctness—thanks to clever layout handling and a couple of inexpensive preprocessing steps.  As long‑context workloads grow, this is a recipe for faster, cheaper inference and training.  

Want to try it out?  The implementation is open‑source on GitHub, and it integrates cleanly with PyTorch and Hugging Face pipelines.  Drop in the `flash_attention` module, set `dtype="fp8"` or `"fp16"`, and watch the quadratic slowdown shrink dramatically.

## 4. FP8: More Than Just “Fast”

FP8 might sound risky, but the paper shows that a mindful implementation can preserve accuracy:

1. **Block quantization** – each query/key/value block has its own scale, dramatically reducing quantization error for localised coefficients.
2. **Incoherent processing** – applying a random orthogonal transform to Q and K spreads out numerical outliers, keeping the resultant Q Kᵀ matrix within a safe dynamic range.

The outcome is a FP8 forward pass whose RMSE is *2.6× better* than a cruder per‑tensor FP8 implementation.  For most language‑model workloads, that level of accuracy translates into **negligible changes in perplexity or BLEU score** while gaining a straight‑through 1.2 PFLOPs/s throughput.
