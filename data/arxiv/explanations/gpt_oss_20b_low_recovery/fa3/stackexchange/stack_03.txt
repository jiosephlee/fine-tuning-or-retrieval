\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### Why is the FP8 WGMMA limited to k‑major operands and what does that imply for matrix layouts?
Question:
Section 3.2 says that FP8 WGMMA only accepts k‑major operands, unlike FP16 where both mn‑major and k‑major are allowed. I understand that this is a hardware restriction, but I’m confused about how it influences the layout of the input matrices when computing attention. Specifically, how does this affect the packing of the value matrix V, and why does it necessitate either a pre‑processing transpose or an in‑kernel transpose? Could you walk through a concrete example of the memory layout before and after the transposition?
Answer:
**Why FP8 WGMMA only accepts *k‑major* operands**

The WGMMA instruction on Hopper is a single‑warp matrix multiply‑accumulate that can be executed asynchronously.  For an \(M\times K\) matrix \(A\) and an \(N\times K\) matrix \(B\) (the routine is called `A × Bᵀ`), the hardware needs to know exactly how the elements of the two operands are laid out in shared‑memory registers in order to stream them into the Tensor Core.  

For the FP16 operands the design is flexible: the register file can be interpreted as a tile that is contiguous either in the outer \(M\) (or \(N\)) dimension – “mn‑major” – or in the inner \(K\) dimension – “k‑major”.  This two‑way flexibility is baked into the instruction set, so either layout can be used with the same instruction.

For FP8 the design is stricter.  The FP8 Tensor Cores were added to Hopper with a new hardware pipeline that assumes the innermost dimension \(K\) is stored contiguously.  Allowing an mn‑major operand would require a different micro‑interleaving of 8‑bit elements inside the unit, which would have over‑complicated the hardware and reduced the throughput that FP8 was designed to provide.  Hence the FP8 WGMMA only understands k‑major operands, and attempting to feed it an mn‑major matrix will result in a runtime error.

In practice this means that a matrix tile that is normally stored as  
\(B\times d\) (rows = sequence length, columns = head dimension) must be stored so that the **rows** of the tile are laid out consecutively in shared memory; in other words, the tile must be **k‑major in the sequence‑length dimension**.  The most common placement of query, key, and value in transformer kernels puts them as \(N\times d\) batches contiguous in the head dimension, so they are mn‑major by default.  Only the value matrix \(V\) is used as the second operand of the second GEMM ( \(P \times V\) ), so it must be reformatted to satisfy the k‑major constraint.

---

### Consequence for the value matrix \(V\)

When the forward attention kernel processes a block of queries \(\mathbf{Q}_i\) and a block of keys \(\mathbf{K}_j\), the first GEMM (\(S = Q_i K_j^{\top}\)) can use either layout, because the first operand is the query block and the second operand is the key block—both are loaded from shared memory in a way that satisfies the WGMMA’s expectations.  The second GEMM (\(O_i \mathrel{/=} \tilde P_i V_j\)) is where the layout constraint matters: \(V_j\) is the right‑hand operand, so it **must** be laid out k‑major.

If the original \(V\) is contiguous in the head dimension (mn‑major), two approaches can be used to obtain the required layout:

1. **Pre‑processing transpose** – before the attention kernel runs, launch a separate transpose kernel (or fuse the transpose into another preparation step such as rotary embedding). The transpose swaps the strides of the sequence‑length and head dimensions, producing a buffer that is k‑major in the sequence dimension.  
2. **In‑kernel transpose** – load a tile of \(V\) from global memory into shared memory with the default mn‑major layout, then, **inside the kernel**, transpose that tile (using `ldmatrix`/`stmatrix` or shuffle instructions) so that the data placed back into shared‑memory is k‑major.  The in‑kernel approach removes the need for an extra kernel launch and is the method chosen in FlashAttention‑3’s FP8 implementation.

Both approaches result in the same memory layout *after* the transpose, but they differ in where the work is performed.

---

### Example layout before and after an in‑kernel transpose

Assume a single head with head dimension \(d=8\) and we are processing a block of sequence length \(B_c=4\).  
The value matrix \(V\) is stored in global memory as an \(N\times d\) array.  For a particular block \(\mathbf{V}\_j\) we have:

| global‑mem |  |  |  |  |  |  |  |  |
|------------|--|--|--|--|--|--|--|--|
| **row 0** | v\_{0,0} | v\_{0,1} | v\_{0,2} | v\_{0,3} | v\_{0,4} | v\_{0,5} | v\_{0,6} | v\_{0,7} |
| **row 1** | v\_{1,0} | v\_{1,1} | v\_{1,2} | v\_{1,3} | v\_{1,4} | v\_{1,5} | v\_{1,6} | v\_{1,7} |
| **row 2** | v\_{2,0} | v\_{2,1} | v\_{2,2} | v\_{2,3} | v\_{2,4} | v\_{2,5} | v\_{2,6} | v\_{2,7} |
| **row 3** | v\_{3,0} | v\_{3,1} | v\_{3,2} | v\_{3,3} | v\_{3,4} | v\_{3,5} | v\_{3,6} | v\_{3,7} |

Here the block of 4 rows (the sequence‑length dimension) is the outermost dimension.  In this **mn‑major** layout the first four columns form a contiguous stride of 32 bytes (8 × 4 bytes).

When the kernel loads this block into shared memory, the layout remains the same.  To satisfy the FP8 WGMMA we must rearrange the tiles so that, for each column of the tile (i.e. for each head dimension index), the **rows are contiguous**.  The in‑kernel transpose produces:

| shared‑mem (k‑major) |  |  |  |  |  |  |  |  |
|----------------------|--|--|--|--|--|--|--|--|
| **col 0** | v\_{0,0} | v\_{1,0} | v\_{2,0} | v\_{3,0} |
| **col 1** | v\_{0,1} | v\_{1,1} | v\_{2,1} | v\_{3,1} |
| **col 2** | v\_{0,2} | v\_{1,2} | v\_{2,2} | v\_{3,2} |
| **col 3** | v\_{0,3} | v\_{1,3} | v\_{2,3} | v\_{3,3} |
| **col 4** | v\_{0,4} | v\_{1,4} | v\_{2,4} | v\_{3,4} |
| **col 5** | v\_{0,5} | v\_{1,5} | v\_{2,5} | v\_{3,5} |
| **col 6** | v\_{0,6} | v\_{1,6} | v\_{2,6} | v\_{3,6} |
| **col 7** | v\_{0,7} | v\_{1,7} | v\_{2,7} | v\_{3,7} |

Now, if we view the data in row‑major order, the first 4 elements of every **row** (i.e. every position \(0,\dots,3\) within a column) are contiguous.  In shared‑memory notation this tile is a 4 × 8 matrix where the **inner dimension \(K=4\) (the sequence‑length split) runs fastest**.  This is exactly what the FP8 WGMMA expects for its right‑hand operand.

---

### Why a pre‑processing or in‑kernel transpose is unavoidable

Because the TMA hardware *cannot* change the stride of a buffer it reads, the only opportunity to reshuffle the elements is:

* **Before the kernel** – by writing a new buffer that is already k‑major.  
* **Inside the kernel** – by loading the mn‑major tile, transposing it, and writing the transposed tile back into shared memory, ready for FP8 WGMMA.

Either approach guarantees that the second GEMM will see a k‑major operand and therefore can run without error.  Choosing the in‑kernel transpose keeps the entire work in one persistent kernel (which is essential for low‑latency inference) and matches the “producer–consumer” paradigm that FlashAttention‑3 relies on.

---

### Take‑away

- FP8 WGMMA on Hopper can only consume k‑major operands.  
- In a conventional transformer layout the value matrix \(V\) is mn‑major.  
- To use FP8 for the second GEMM, the value tiles must be reordered so that the sequence‑length dimension is the tightest stride.  
- This reordering is implemented either as a separate transpose kernel or, as in FlashAttention‑3, as an in‑kernel tile‑transpose performed in the producer warpgroup, after which the transposed tile is fed directly to the FP8 WGMMA.  

The extra transpose adds a negligible cost relative to the massive throughput gain of FP8 Tensor Cores, and is the reason why the paper explicitly highlights the k‑major restriction for FP8 operators.
