\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What are the practical trade‑offs in choosing the number of stages `s` for the circular SMEM buffer?
Question:
In Algorithm 1 the authors mention an `s`‑stage circular SMEM buffer but do not give guidelines for selecting `s`. How does `s` affect register pressure, debugging complexity, and the ability to hide latency? In particular, what happens if `s` is too small or too large relative to the key block size `B_c` and query block size `B_r`?
Answer:
**Short answer**  
In FlashAttention‑3 the circular SMEM buffer is a “ping‑pong” staging area that lets one warp group load a block of keys and values while another warp group consumes it in a GEMM.  
Choosing the number of stages \(s\) is a *memory‑ vs. register‑pressure trade‑off*: a larger \(s\)  

* gives more “room” for asynchrony – the producer can keep pulling blocks from GMEM without waiting for the consumer to finish its current GEMM, which helps hide TMA latency and keeps the Tensor Cores busy.  
* but it also keeps more blocks resident in SMEM for ever longer and, because each stage needs a set of registers to hold the operands and the intermediate results (e.g. the \(S_{\text{next}}\) matrix in the 2‑stage pipeline), it raises the per‑thread‑block register count.  If the register pressure exceeds the SM’s limit the compiler spills to local memory, killing the speed advantage.  

If \(s\) is **too small** (e.g. \(s=1\)) the producer can only load the next block after the consumer has finished the previous one. The issuer‑producer round‑trip latency then dominates: the Tensor Cores sit idle while waiting for the next key/value tile to arrive, especially on very long sequences where \(T_c=\lceil N/B_c\rceil\) is large. The kernel will be under‑utilized and the overall throughput drops.

If \(s\) is **too large** relative to the block sizes \(B_c\) and \(B_r\) (i.e. \(s\gg T_c\) or the buffer width far exceeds the number of warps that can actually use it) we waste on‑chip memory. The kernel still consumes the same amount of TMA bandwidth, but SMEM bandwidth is saturated by copying data back and forth within a single CTA, while the register spill‑over causes the kernel to launch fewer thread blocks per SM. In practice the hardest case is when \(s\) exceeds the number of consume warps: the consumer can never keep all stages filled, so the larger buffer simply adds unnecessary register pressure without improving latency hiding.

The sweet spot typically lies between these extremes. Empirically (see our ablation tables in Section 5.2) we tuned \(s\) to be one step larger than the Software‑Pipelining depth of the overlapping GEMM–softmax loop (i.e. 2 or 3 stages). For the average Hopper H100 configuration that translates to \(s=2\) for a \(B_r=256\) and \(B_c=256\) tile set. In this regime:

* **Register pressure** remains below the per‑SM high‑occupancy threshold (≈ 40 k regs per CTA), so the compiler does not spill.  
* The producer can issue a new TMA load every SMEM‑cycle, keeping the two consumer warps busy with WGMMA, so the Tensor Cores stay >70 % utilized.  
* The entire pipeline latency (load → GEMM → softmax → GEMM) is fully overlapped; the kernel achieves ≈ 740 TFLOPs/s in FP16 and ~1.2 PFLOPs/s at FP8 on an H100.

**Guidelines for picking \(s\)**

| Scenario | Recommended \(s\) | Why |
|----------|-----------------|-----|
| **Short sequences** (\(N<2\,k\)) | 1–2 | Few key blocks, load‑latency is negligible; extra stages only raise register use. |
| **Medium sequences** (\(2\,k<N<8\,k\)) | 2–3 | Overlap between producer and consumer is beneficial, but too many stages would start spilling. |
| **Long sequences** (\(>8\,k\)) | 3–4 | More blocks to load; a deeper buffer keeps the producer hidden behind the consumer, but stay below register‑spilling threshold. |
| **FP8 mode with quantization** | 2 | The extra registers needed for the FP8 accumulator permutation and the 2‑stage pipelining already raise pressure; keep \(s\) minimal. |

In practice, a quick way to find the right \(s\) is to run the kernel with a modest sequence length and measure the register count reported by `nvprof`/`nsight`. If the register usage is close to the SM limit, reduce \(s\); if the kernel launches with low occupancy and the EAR (effective active warps) is below the target, increase \(s\) until the latency of producer–consumer stalls drops to 0‑5 cycles and the occupancy stabilizes.  

**Bottom line** – \(s\) is the knob that trades asynchrony for on‑chip storage. A proper choice keeps the pipeline full without spilling, thereby fully hiding TMA/TMA–WGMMA latency and maintaining the highest possible Tensor‑Core utilisation. For most Hopper H100 workloads, an \(s\) that matches the depth of the SW‑pipeline (usually 2‑3) gives the best performance.
