\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What is the intuition behind GPU memory hierarchy impacting FlashAttention performance?
Question:
In the background section the paper describes the GPU memory hierarchy (GMEM, L2, SMEM, RMEM) and mentions that FlashAttention‑2 achieves only 35% utilization on H100. I’m unclear how the different bandwidths and capacities of these memories translate into the observed bottleneck. Could someone explain, perhaps with a simple example, why an algorithm that eliminates intermediate global‑memory reads/writes still suffers low utilization, and how the new Warp‑Specialization scheme addresses this issue?
Answer:
#### Why FlashAttention‑2 still runs at only ~35 % on an H100, even though it removes the bulk of global‑memory traffic

The GPU’s memory system is a classic “capacity ↔ bandwidth” trade‑off:

| level | capacity | typical bandwidth | cost of a single load/stall |
|-------|----------|-------------------|-----------------------------|
| GMEM (HBM) | • TB | few – 10 GB/s | very large |
| L2 cache | 128 ‑ 256 GB | > 200 GB/s | large (but still limited) |
| Shared memory (SMEM) | ≤ 96 KB per SM | hundreds GB/s | very small, very cheap |
| Register file | ≤ 256 per thread | N/A | essentially zero latency |

FlashAttention‑2’s key idea is to **avoid materialising the full \(S\) and \(P\) matrices in GMEM**: it tiles the attention computation so that every piece of \(K\) and \(V\) is loaded once into SMEM, a chunk of \(Q\) is fetched into registers, the corresponding block‑wise softmax is performed in‑SMEM, and finally the result is written back once. In an ideal world this would let the kernel run on the fast SMEM/​registers and keep memory traffic to a minimum.

In practice, however, the H100’s **execution pipeline is highly tuned to hide latencies of the two accelerator units**:

* The Tensor Cores (TWMMAs) are asynchronous; they can be launched and run while other instructions are being issued.
* The Tensor Memory Accelerator (TMA) is the only dedicated unit for moving data between GMEM and SMEM; it has to be explicitly programmed.
* The SMEM is much smaller than the L2 cache, so the tiles that can be kept “in‑flight” are limited by register pressure and SMEM size.

FlashAttention‑2’s original algorithm is essentially *synchronous*: a warp must finish **S‑GEMM → softmax → R‑GEMM** for one block before starting the next block. This serialization forces the kernel to wait for the Tensor Core to finish a GEMM *before* it can launch the TMA load for the next block. The order looks like:

```
load K,V → S‑GEMM → softmax  → R‑GEMM  →  next load K,V
```

Even though the loads are issued asynchronously, the kernel stalls at the `WGMMA.wait()` (or the equivalent barrier) after the softmax, blocking all other warps in the CTA from doing useful work. As a consequence:

* **Tensor Core utilisation drops** – the GPU spends a lot of cycles idle because it has to wait for the device‑side data movement to finish or for the softmax to finish.
* **SMEM thrashing** – the SMEM buffer can only hold a few blocks at a time, and the same blocks are repeatedly written back to GMEM after the R‑GEMM, which brings the bandwidth cost of the final write back back into play.
* **DRAM bandwidth is still a bottleneck** – although the kernel now rarely reads the same block twice, the writes of the final output (and the L‑values) are still wide (≈4 bytes per element), and the H100’s DRAM bandwidth is far smaller than the Tensor Core’s theoretical peak.

When you look at the Hopper‑specific implementation of FlashAttention‑2, you’ll see that the kernel is still **blocking on the G‑MMA result before launching the next load**. This serial behaviour underpopulates the Tensor Cores relative to the GPU’s peak FLOPS and keeps the overall utilisation at ~35 % even with all the optimisations you can do in a pure FP16 implementation.

---

#### Why “eliminating intermediate global‑memory reads/writes” does not magically solve utilisation

Eliminating the two full‑matrix intermediate writes is a big win for **through‑put**: you no longer have to broadcast an \(N\times N\) matrix to GMEM, and so the per‑token memory traffic is reduced by a factor of \(N\). However, utilisation is a *different* measure that looks at how fully the compute units (Tensor Cores, SP, SMEM copies) are kept busy.  
Consider the following simple 2‑step “kernel sketch”:

```
1) S-GEMM (Tensor Cores)  →  produce S
2) Softmax (SFU)            →  produce P
3) R-GEMM (Tensor Cores)  →  produce O
```

If you finish step 1, you must **wait** until step 2 finishes before you can start the next block’s step 1. The TFLOPs are spent doing step 1, but the SM stage (softmax) keeps the accelerator busy only a fraction of the time. In the *forward* pass there is a very long critical path: you cannot start the second GEMM until the softmax of the first block is ready.  

Even if you had perfectly overlapped the **memory traffic** (thanks to TMA) with the **compute**, the **softmax** is a serial bottleneck. The Tensor Core demands no expenditure of its compute resources while the softmax module (a handful of floating‑point: \( \log, \exp, +\)) is running, and the H100 can only supply about **3.9 TFLOPs** of special‑function throughput compared to **989 TFLOPs** of FP16 matrix multiplication. Thus the *softmax* dominates the cycle budget and leaves the Tensor Cores idle for > 50 % of the time.

In other words, removing the intermediate GMEM traffic eliminates one *type of bandwidth pressure* (DRAM), but the kernel is still **branch‑bound by a lower‑throughput instruction sequence** (softmax). If the kernel were able to launch a new Tensor‑Core GEMM while the previous softmax was still running, the utilisation would jump dramatically.

---

#### How warp‑specialisation in FlashAttention‑3 changes the picture

FlashAttention‑3 takes explicit advantage of the **asynchrony** already present in Hopper by **splitting the warps of a CTA into two roles**:

1. **Producer warps** – responsible only for issuing the TMA loads of the next block of \(K\) / \(V\). They can do this once per warp‑group and then become idle until the next warp‑group brings them back into play.
2. **Consumer warps** – do all the heavy lifting (S‑GEMM, softmax, R‑GEMM, rescaling). They only ever issue computational instructions; no memory copy logic lives in them.

Because the **producer** only spends a few cycles including an asynchronous TMA launch, it can keep a *long* stall time behind the **consumer**. This is the classic *producer/consumer* pipeline.

Even more powerful is the **"ping‑pong" overlap** that FlashAttention‑3 introduces:

```
[Consumer 0] S‑GEMM0 → Softmax0 (slow)
[Producer 0]                              ←
[Consumer 1] S‑GEMM1 (async) → R‑GEMM1  ←
[Producer 1] Softmax1 (async)            ←
```

Here, the softmax of block 0 runs *while* the Tensor Core is busy performing the second block’s S‑GEMM. Because both the Tensor Core and the special‑function units can run in parallel, the “pipeline fill” cost disappears, and the average latency per block is simply the **maximum** of *(softmax + post‑processing)* and *S‑GEMM*, rather than the sum. In practice this pushes Tensor‑Core utilisation from ~35 % up to ~75 % on the H100.

The same idea can be pushed deeper (“3‑stage pipeline”), but it incurs higher register pressure.

---

#### Key take‑aways

| Observation | Why it matters | FlashAttention‑3 fix |
|-------------|----------------|----------------------|
| **Tensor Cores are asynchronous** | Allows overlapping of compute with data movement. | Producer warps launch TMA while consumer warps consume data. |
| **Softmax is low‑throughput** | Creates a serial bottleneck. | Ping‑pong scheduling lets softmax run while the next GEMM runs. |
| **SMEM is small & register‑heavy** | Limits how many blocks can stay on‑chip at once. | Register‑level buffering keeps the pipeline full without exhausting SMEM. |
| **DRAM contention still present** | Even without intermediate writes, the final write of \(O\) still costs bandwidth. | Asynchronous writeback is overlapped with upcoming computations. |

In sum, **memory traffic reduction** is necessary but not sufficient for peak utilisation. Achieving high utilisation on Hopper (H100) requires an algorithm that **exploits the separate asynchronous streams of the Tensor Cores and the memory copy unit**. FlashAttention‑3’s warp‑specialised, pipelined design does precisely that, turning a previously serial‑bound kernel into one that keeps the Tensor Cores idle for less than 30 % of the time and brings the utilisation up to 75 % on an H100.
