\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 9: # Chapter 9. Experimental Evaluation

In this chapter we bring together the empirical evidence that supports the claims made by the paper *Large Language Models Can Automatically Engineer Features for Few‑Shot Tabular Learning*. We walk through the data sets that were used, the competitors that were evaluated, the practicalities of setting up the experiments (including hyper‑parameters, token budgets, and cost), and finally we dissect the results that show how the proposed method, **FeatLLM**, fares against a wide spectrum of baselines. The goal is to give the reader a full, detailed understanding of the study design so that the experiments can be reproduced or adapted to new problems.

## Dataset Catalog and Characteristics

The experimental suite consists of *thirteen* tabular classification data sets that vary in size, feature count, label type, and domain. All data are publicly available and accompanied by clear feature descriptions (or they were engineered to match the format required by the framework). The data sets fall into two broad categories:

1. **Standard benchmark data sets** – These constitute the traditional UCI repository of tabular data for static classification tasks.  
2. **Recently released or synthetic data sets** – These were published or constructed after GPT‑3.5’s pre‑training cut‑off to guarantee that the LLM has **not** seen the data in any form.

A few remarks on these data sets that influence the experimental design:

- **Scale and Feature Cardinality.**  
  *Communities* and *Myocardial* have over 100 features each. These data sets exceed the prompt length of many 175‑billion parameter LLMs, making them important stress tests for the proposed rule‑generation strategy.
- **Pre‑training Coverage.**  
  The synthetic data sets (12, 13) were purposefully built after the GPT‑3.5 pre‑training cut‑off to provide an objective baseline for evaluating memorization versus knowledge‑based predictions.
- **Shot‑Size Variations.**  
  Experiments are repeated for *k*-shot settings where *k* = 2, 4, 8, 16, and 32. This allows us to see how FeatLLM scales as more labeled samples become available.

All data sets were processed to generate *feature names* in natural language and, where applicable, succinct *feature definitions*. This format is critical because FeatLLM’s prompting strategy relies on the LLM parsing the semantic type of each feature from the instruction section of the prompt.

## Baseline Families

To substantiate the claim that FeatLLM outperforms prior work, we compare it against a diverse set of models that belong to three distinct families: hand‑crafted feature learning, semi‑supervised “transfer‑learning” methods, and LLM‑based inference pipelines.

### 1. Hand‑crafted Baselines

| Baseline | Brief Description | Training Procedure |
|----------|-------------------|--------------------|
| Logistic Regression (LogReg) | Linear model with L2 regularization | Standard cross‑validation for hyper‑parameter tuning |
| XGBoost | Gradient‑boosted decision trees | Tune max depth, learning rate, number of trees via grid‑search |
| RandomForest | Ensembles of decision trees with random feature selection | Tune number of trees, max depth |

These three models represent the “industry standard” for tabular classification in a few‑shot regime, requiring no external knowledge source beyond the data itself.

### 2. Semi‑Supervised / Transfer Baselines

| Baseline | Brief Description | Training Procedure |
|----------|-------------------|--------------------|
| SCARF | Semi‑supervised self‑looping with meta‑learning | Uses external unlabeled data for a rich data augmentation pipeline |
| STUNT | Transfer learning with task‑agnostic pre‑training | Fine‑tunes a model pre‑trained on a large set of unrelated tabular data |
| TabPFN | Pre‑training on synthetic datasets drawn from a mixture of distributions | Uses a Bayesian neural network that ingests both train and test points together |

These models exploit large volumes of *unlabeled* data to learn richer representations. They are included to assess whether feature engineering with an LLM can surpass models that benefit from such data.

### 3. LLM‑Based Baselines

| Baseline | Brief Description | Training/Inference |
|----------|-------------------|--------------------|
| In‑Context Learning (In‑Context) | Prompted directly with *k* examples and tasks | No fine‑tuning; everything done at inference time |
| TABLET | Structured prompt that incorporates an external classifier’s rule‑sets | Uses in‑context inference with added rule hints |
| TabLLM | Parameter‑efficient fine‑tuning (IA3, LoRA) on massive tabular datasets | Requires open‑source checkpoint; fine‑tuned on *k* examples |

These baselines illustrate how LLMs have been engaged for tabular learning: either via prompt‑only inference or via lightweight fine‑tuning. FeatLLM’s key distinction is that the LLM is used **once per experiment** to generate rules, after which all predictions are done by a simple linear model.

> **Why compare across all three families?**  
>  The intention is to show that FeatLLM doesn’t just win against more sophisticated LLM pipelines; it also beats traditional machine learning methods that are normally considered state‑of‑the‑art for few‑shot tabular problems.

## Implementation Hyper‑Parameters

Each experiment is built upon the same general workflow: encode samples as prompts, fetch rules from the LLM, parse them into executable Python code, create binary features, and fit a linear classifier. The main knobs that were tuned empirically are listed below.

| Hyper‑Parameter | Setting | Rationale |
|-----------------|---------|-----------|
| **LLM Backbone** | GPT‑3.5 (turbo‑0613) | Accessible API, good chain‑of‑thought performance |
| **LLM Temperature** | 0.5 | Balances creativity and determinism; too low leads to monotonic rules, too high leads to noise |
| **Number of Ensembles (T)** | 20 | Provides enough diversity for bagging while keeping inference cost modest |
| **Number of Rules per Class** | 10 | Empirically found to strike a balance between prompt length and information gain |
| **Learning Rate (Adam)** | 0.01 | Allows quick convergence in low‑shot regimes |
| **Epochs** | 200 | Sufficient for the small data regime; early‑stopping via cross‑validation |
| **K‑Fold Cross‑Validation** | 5‑fold | Used only to select the best epoch during training |
| **Weight Projection** | $\max(\mathbf{w}, 0)$ | Guarantees non‑negative contribution of each rule to the logit |
| **Ensemble Aggregation** | Averaging post‑softmax | Empirically more stable than summing logits directly |

The LLM prompts are carefully controlled: a *feature‑definition* block is supplied to register the type of each column (continuous, categorical, ordinal) and a *reasoning instruction* block that forces a two‑stage deduction (`Step‑1` – prior knowledge inference, `Step‑2` – example‑based rule extraction). The prompt length is bounded by the LLM token limit (i.e., 4 096 for GPT‑3.5) through a *feature bagging* strategy: each LLM query receives a random subset of features and/or few‑shot samples.

> **Tip for reproducing the experiments**  
>  The source code for FeatLLM is available on GitHub. The repository includes a helper that automatically selects a random bag of features per ensemble to respect the token limit. Setting the seed via the provided `--seed` flag ensures reproducibility of the bagging choices.

## Training vs. Inference Costs

A key contribution of FeatLLM is that, after the initial rule extraction phase, all predictions are performed through a lightweight linear model. Below, we quantify the resource consumption in a practical sense.

### Training Time

Training is dominated by two stages:

1. **LLM Call Overhead** – 20 * 10 rules per class * 2 classes (binary) ≈ 400 API queries.  
   Using the default OpenAI rate limit, this takes roughly 30 seconds on a single API key, negligible compared to GPU training times.

2. **Linear Model Fitting** – 200 epochs over a *k*‑shot data set; for k ≤ 32 this completes in < 5 seconds on a single A100 GPU.

Hence, FeatLLM’s training time is an order of magnitude lower than that of LLM‑based baselines that require per‑sample inference (e.g., In‑Context, TABLET), which would need *N* queries for *N* test points.

### Inference Time

Because predictions from FeatLLM rely only on the linear model, inference latency is that of a dot product over a handful of binary features (≈ 10 × c classes). Benchmarks on the Adult dataset (16‑shot set) show:

| Inference Method | Latency (ms) |
|------------------|--------------|
| FeatLLM | 5 ± 1 |
| In‑Context | 642 ± 50 |
| TABLET | 723 ± 45 |
| TabLLM (per‑sample) | 1 140 ± 80 |

The disparity is stark: FeatLLM is almost two orders of magnitude faster. This efficiency stems from the *one‑time* nature of the LLM call; all other methods require an LLM query for every test record, which is unfeasible in many industrial settings.

## Performance Tables and Visual Trends

Performance is measured in terms of Area Under the ROC Curve (AUC) for binary datasets and macro‑averaged AUC for multiclass problems. Results were averaged across three random train/validation splits to mitigate variance due to small *k*.

### Overall Benchmarks

The full performance matrix is captured in Tables 1 and 2 (provided in the original paper). A succinct plot of average AUC versus *k* illustrates the major trends:

- **FeatLLM outperforms all baselines on the majority of datasets** (10 out of 13). On the remaining three, it is typically the second best, often within a 0.01 AUC margin.
- **Low‑shot superiority.** With only 4 shots, FeatLLM matches or surpasses conventional methods that rely on 32 shots.
- **Robustness to feature count.** FeatLLM maintains strong performance even on high‑dimensional data sets such as *Communities* and *Myocardial*, where reflective LLM baselines fail to produce any predictions due to prompt truncation.

A visual illustration (Figure 3) shows the top‑3 rankings per dataset for each *k*. FeatLLM occupies the top slot more often than any other method, confirming its versatility across problem types.

### Ablation Sensitivity

An in‑depth ablation study (Table 3) evaluates the contribution of key components:

- **Rule Weight Tuning** (`-Tuning`) – Removing linear training reduces AUC by ~0.03 on average, highlighting the importance of learning rule importance.
- **Ensembling** (`-Ensemble`) – Without bagging, performance drops often by ~0.05, especially on datasets with many features.
- **Feature Description** (`-Description`) – Excluding textual feature definitions leads to small but consistent drops (~0.02), showing the role of prior knowledge cues.
- **Reasoning Instruction** (`-Reasoning`) – Removing the two‑stage reasoning step reduces accuracy noticeably on balanced datasets where spurious correlations are prevalent.

These results underscore how each engineered prompt component and ensemble strategy directly translates to competitive performance.

### Spurious Correlation Robustness

A synthetic experiment introduced irrelevant features (from the Adult data) to the Heart data set. FeatLLM’s AUC degraded marginally (< 0.02) even when 20 unrelated columns were injected, whereas conventional LLM baselines suffered sharper drops (> 0.1). This resilience is attributed to FeatLLM’s *prior‑knowledge screening* step: the LLM’s first reasoning stage explicitly discerns which features could be relevant before evaluating the examples.

## Take‑Away Messages

1. **Feature Engineering via LLMs is Powerful.**  
   FeatLLM demonstrates that an LLM can act as a knowledge‑rich feature generator, and the resulting rules can be turned into a very lightweight downstream model.

2. **Low‑Shot Superiority.**  
   The approach shines when labeled data is scarce (k ≤ 4), offering the same predictive quality as fully‑trained tree ensembles that require dozens of shots.

3. **Scalability to Large Feature Spaces.**  
   Through feature bagging and prompt segmentation, the method scales to tables with over a hundred attributes, a scenario where most LLM‑based pipelines stall.

4. **Cost Efficiency.**  
   Because all predictions are made by a linear model, inference remains instantaneous, which is critical for real‑time applications.

5. **Reproducible, Minimal API Usage.**  
   The protocol requires a handful of LLM queries (≈ 400) and no parameter‑tuning of the large language model, making it feasible to employ with limited API budgets.

Future work could explore **dynamic rule adaptation** as more data arrives, or a **hierarchical rule mixture** that supports broader classes of features beyond binary conditions. Nonetheless, the current experimental evidence firmly establishes FeatLLM as a strong entrant in the few‑shot tabular learning landscape.
