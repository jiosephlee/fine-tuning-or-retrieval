Chapter 6: # 6. Inferring Rules and Generating Binary Features

## 6.1 Challenges of Noisy LLM Output

Large language models are renowned for their ability to produce fluent and context‑appropriate text, yet this flexibility comes at a cost when we attempt to convert their outputs into deterministic, machine‑interpretable artefacts. In the context of *FeatLLM*, the LLM is prompted to supply a list of “rules” that identify when a particular class should be predicted. By design, those rules are expressed in natural language and are expected to be syntactically uniform (e.g., “feature X > 5” or “feature Y equals ‘high’”). In practice, however, the following complications frequently arise:

1. **Lexical Variation** – The same logical condition may be expressed in many different wordings. For instance, the model might output “feature X is greater than 5”, “if X > 5”, or “X > 5”.  
2. **Omitted Operators** – Some outputs replace common symbols with words (“greater than” instead of “>”), or conversely replace words with symbols (“>” instead of “greater than”).  
3. **Syntactic Smear** – The model may inadvertently add punctuation, numbering, or explanatory text that interferes with a blind parser.  
4. **Typos and Unexpected Tokens** – Misspellings of feature names or accidental inclusion of stray characters can break strict parsing logic.  
5. **Ambiguous Constraints** – In some cases the LLM may output a composite condition using logical glue such as “and” or “or” without clear bracketed grouping.  

Because the subsequent feature generation relies on accurately detecting whether a given data row satisfies a rule, any of these imperfections lead to incorrectly encoded binary features. This problem is exacerbated by the fact that rule lists are often long (10 rules per class, multiplied by the number of classes) and need to be processed quickly and at scale. A naïve, hand‑written parser that enforces a rigid grammar would struggle to accommodate the natural variance in the LLM’s output, making the system brittle and unreliable.

## 6.2 LLM–Guided Parsing Workflow

To sidestep the pitfalls of a handcrafted parser, *FeatLLM* turns the LLM itself into a lightweight interpreter. The core idea is to provide the LLM with a concise function signature, hand‑crafted Python data, and the natural‑language rule list. Instead of asking the LLM to produce editable code that implements the rules, we simply ask it to produce a small helper function that, given a dictionary of feature values, returns a list of booleans indicating which rules are satisfied.

The advantages of this approach are twofold:

1. **Robustness to Variation** – Because the LLM is trained on massive amounts of code, it is highly adept at writing parse‑able Python snippets even when the input contains slightly irregular text.  
2. **Zero‑Maintenance Parsing** – The system requires no grammar updates; any new kind of rule syntax is automatically handled by the LLM because it internally normalises the logic into executable operations.

The parsing workflow is shown in Figure 6.1 and consists of the following steps:

1. **Feature‑Value Assembly** – For each data row, a dictionary `row_features` is constructed where keys are the exact feature names and values are the corresponding numeric or categorical values.  
2. **Prompt Construction** – The prompt supplied to the LLM contains:
   - A brief description of the parsing task.
   - The list of rules exactly as returned by the rule‑generation step.  
   - The `row_features` dictionary rendered as a Python dictionary literal.  
   - A function template that the LLM must fill in.  
3. **Code Generation** – The LLM outputs a tiny function `def apply_rules(row_features):` that evaluates each rule and returns a list or NumPy array of binary indicators.  
4. **Execution** – The output string is treated as Python source code, evaluated in a controlled environment using `exec()`, obtaining a callable function `apply_rules`.  
5. **Feature Extraction** – The function is called on each data row to produce its binary rule‑satisfaction vector.

Because the function is generated separately for each rule set, *FeatLLM* can flexibly support different numbers of rules per class and different logical forms without additional engineering effort.

### 6.2.1 Prompt Design for the Parser

A typical parsing prompt `P_parse` has the following structure:

```
You are a Python interpreter. Given the dictionary below and the rule set, write a function `apply_rules(row_features)` that returns a list of 0/1 values indicating whether each rule is satisfied.

# Rule set
Rule 1: X > 5
Rule 2: Y equals "high"
Rule 3: Z < 10.7

# Input features
row_features = {
    "X": 7,
    "Y": "low",
    "Z": 12.3
}

# Function signature
def apply_rules(row_features):
```

The LLM is instructed to complete the body of the function by evaluating each rule using standard Python syntax. No additional documentation or comments are required. This minimalistic design guarantees that the resulting code is as compact as possible, facilitating execution speed.

## 6.3 Python Code Generation and exec() Usage

Once the LLM returns a code block, the *FeatLLM* runtime interprets it using the built‑in function `exec()`. The process is straightforward:

```python
# Raw code string returned by the LLM:
source = """
def apply_rules(row_features):
    if row_features["X"] > 5:
        return [1, 0, 0]
    else:
        return [0, 0, 0]
"""

# Prepare an empty namespace for execution
namespace = {}
exec(source, namespace)

# Retrieve the generated function
apply_rules = namespace["apply_rules"]

# Apply the function to each row
binary_features = [apply_rules(row) for row in dataset_rows]
```

A few implementation details deserve attention:

- **Sandboxing** – The `exec()` call runs in a tightly controlled namespace, with only the `apply_rules` function imported into the global scope. This mitigates the risk of accidental execution of arbitrary code.
- **Error Handling** – If the LLM returns syntactically invalid Python, the `exec()` call raises a `SyntaxError`. In practice, we wrap the call in a try/except block and, upon failure, fall back to a default rule evaluator that uses simple string heuristics (e.g., regex search for “>”).
- **Performance** – Each generated function is compiled only once per rule set and reused for all rows belonging to the same class. This amortises the parsing cost across the dataset.

By delegating the code generation to the LLM, *FeatLLM* harnesses the model’s innate proficiency in generating well‑formatted code, thereby eliminating the need for a cumbersome manual parser.

## 6.4 Feature Matrix Construction from Rule Satisfaction

After generating the binary feature vectors for each data row, the next step is to assemble the full feature matrix `Z`. Recall that for a given sample `i` and class `k`, the clique of rule conditions forms a binary vector `z_k^i ∈ {0,1}^R`, where `R` is the number of rules extracted for that class. The general construction proceeds as follows:

1. **Union of Rules across Classes** – For multi‑class problems, each class typically receives its own distinct rule set. We concatenate all rule sets into a single combined set:  
   \[
   \mathcal{R} = \bigcup_{k=1}^c \mathcal{R}_k, \qquad |\mathcal{R}| = c \times R.
   \]
2. **Label‑Specific Evaluation** – For each sample, we evaluate the entire rule set, resulting in a binary vector of length `c × R`. For rule `r_{k,r}` (the `r`‑th rule of class `k`), the entry is 1 if the sample satisfies the rule, 0 otherwise.  
3. **Matrix Assembly** – Stack all binary vectors row‑wise to form the feature matrix `Z ∈ {0,1}^{N × (c × R)}`:
   \[
   Z_{i,j} = \mathbb{1}\{\text{sample } i \text{ satisfies rule } j\}.
   \]
4. **Normalization for Downstream Model** – The matrix `Z` is then fed into the lightweight downstream model (typically a non‑negative linear classifier). That model learns weights `w_k` for each rule, which implicitly scores the importance of each rule for its corresponding class.

Because each rule is a pure logical predicate, the feature vector is highly interpretable: the non-zero entries directly indicate which conditions the sample fulfills. Moreover, by using non‑negative weights, we prevent the downstream model from “over‑penalizing” a rule—if a rule turns out to be misleading, the learned weight can be arbitrarily small but never negative.

### 6.4.1 Example: Constructing Z for a Two‑Class Problem

Suppose we have two classes (A and B) and each class receives 10 rules. After parsing, we obtain the following example satisfaction summaries for a single sample:

- Class A rules satisfied: 1, 4, 7, 10  
- Class B rules satisfied: 3, 9  

The binary vector for this sample would be:

| Rule | A.1 | A.2 | … | A.10 | B.1 | B.2 | … | B.10 |
|------|-----|-----|---|------|-----|-----|---|------|
| Value|  1  |  0  |…|  1   |  0  |  0  |…|  1   |

Stacking such vectors across all samples yields the full matrix `Z`. When we later compute a dot product with the weight vector `w`, each entry’s contribution is simply its weight if the rule is satisfied, else zero.

### 6.4.2 Handling Underspecified Rules

Occasionally, the LLM may produce a rule that references a feature not present in the dataset (perhaps due to a typo or a mismatch between feature names in the prompt and the actual data dictionary). In such a case:

- The parser function treats the missing key as a special value (e.g., `None`).  
- All comparisons involving the missing key default to `False`, setting the corresponding binary entry to 0.  
- This rule will not affect the downstream model unless the LLM has generated a rule that is satisfied by every sample (in which case the weight will be nearest zero).

Because these problematic rules are unlikely to be repeated across different samples (they are usually idiosyncratic), the ensemble strategy described in Section 5.3 further mitigates their effect: even if a specific prediction instance is hampered by a spurious rule, another bagging iteration—likely generating a different rule set—will compensate.

## 6.5 Summary

In this chapter we dissected the core mechanics that allow *FeatLLM* to translate a LLM’s natural‑language rules into executable binary features:

1. **Noise‑robust parsing** capitalizes on the LLM’s coding ability, avoiding brittle hand‑crafted parsers.  
2. **Python code generation and controlled execution** via `exec()` provide a clean, reproducible way to evaluate rules on millions of samples.  
3. **Feature matrix construction** ensures that the resulting binary representation is amenable to rapid inference by a simple downstream classifier.  

These techniques collectively transform the LLM from an expensive, per‑sample inference engine into a one‑time feature engineering worker, thereby enabling efficient, few‑shot tabular learning in real‑world settings.
