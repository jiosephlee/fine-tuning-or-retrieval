# Unlocking Tabular Data with LLMs: How FeatLLM Turns Language Models into Feature Engineers  

Tabular data – the spreadsheets, database tables, and CSV files that dominate business intelligence and scientific reporting – are notoriously hard for bare‑bones language models to handle. Traditional machine‑learning pipelines still need hand‑crafted feature engineering, expensive hyper‑parameter searches, and careful treatment of categorical variables. A recent paper, *Large Language Models Can Automatically Engineer Features for Few‑Shot Tabular Learning*, proposes a radically different idea: use an LLM **as a feature engineer** instead of as a black‑box predictor. The result is *FeatLLM* – a framework that asks a language model to write rules, turns those rules into binary features, and then trains a tiny linear model on top of them.  

Below we dissect how FeatLLM works, why it beats other LLM‑based tabular methods, and what this means for practitioners who need to get insights from a handful of labeled records.

---

## The Core Challenge of Few‑Shot Tabular Learning

In many real‑world domains (healthcare, finance, IoT), gathering thousands of labeled examples is costly or impossible. In the “few‑shot” regime we only have a handful of labeled samples – say 4 or 8 – to learn from. Classic models quickly overfit or ignore rare but important interactions.

Previous work tried to solve this by:

* **Fine‑tuning** large models on the targets (e.g., LoRA, IA3) – requires code‑level access and heavy computation.  
* **In‑context learning** – dropping a few examples into a prompt and letting the LLM produce direct predictions – still needs an LLM inference per test point, which is expensive and slow.  
* **Knowledge‑based pre‑training** – training on many unlabeled tables (e.g., TabPFN, SCARF) – relies on having huge unlabeled corpora and training pipelines.

All these approaches still suffer one thing: every time you want a prediction you send the data to the LLM, paying the cost of a large model and risking the LLM’s own hallucinations or dependence on prompt length.

---

## FeatLLM: Re‑imagining the LLM’s Role

Rather than asking the LLM to give a final answer, FeatLLM asks it to **explain** which conditions (rules) make a sample belong to a class. It does this in three stages:

| Stage | What Happens | Why It Matters |
|-------|--------------|----------------|
| 1. **Prompt Design** | The prompt contains: <br>• A natural‑language task description (e.g., “Does this patient have heart failure? Yes or no?”). <br>• Feature descriptions (type, possible values). <br>• A handful of *serialized* training examples. <br>• A two‑step reasoning instruction (first infer general relationships, then craft class‑specific rules). <br>• An explicit response format (10 rules per class, each a simple condition). | A careful prompt steers the LLM toward *rule extraction* rather than arbitrary predictions, limiting hallucination. |
| 2. **Rule Extraction & Parsing** | The LLM outputs 10 rules per class, e.g., “Heart rate > 100 AND Blood‑pressure <= 120”. A second “parsing prompt” asks the *same* LLM to turn each rule into Python code (`lambda row: bool(...)`).  The code is run via `exec()` to produce a binary feature for every sample. | By letting the LLM do the parsing, parsing errors (e.g., “greater than → >”) are minimized. The resulting features are *interpretable* – you can read each rule. |
| 3. **Downstream Scoring** | Each class gets a binary feature vector `z_k ∈ {0,1}^R` (R = 10 rules). A tiny linear model (weights constrained to be non‑negative) learns `w_k` to score each class:  

\[
\text{logit}_k = \max(w_k,0)^T z_k, \qquad p = \text{Softmax}( \{\text{logit}_k\} ).
\]  

The linear weights are trained with cross‑entropy on the few labeled examples. The model is then *fixed* – at test time no LLM call is needed. | The lightweight downstream model gives you: <br>• Very fast predictions (~ 1 ms on a standard CPU). <br>• No dependence on the LLM after the initial rule generation. <br>• Easy interpretability: you can inspect the `w_k` to see which rules matter most. |

---

## Ensemble + Bagging: Making the Rules Robust

A single run of the LLM might miss some useful rules or, worse, invent spurious ones. FeatLLM combats this by:

1. **High‑temperature sampling** (°~0.5) and shuffling the order of the few‑shot demos → diverse rule sets.  
2. **Feature bagging**: for each of the `T` trials, the prompt only shows a random subset of features and samples.  
3. **Ensembling**: run the whole pipeline `T` times (default 20) and average the probabilities.

The ensemble reduces variance and filters out errant rules, while bagging keeps the LLM prompt size manageable even when the table has hundreds of columns.

---

## Why FeatLLM Outperforms Other LLM‑Based Methods

| Technique | Strengths | Weaknesses | FeatLLM Advantage |
|-----------|-----------|------------|-------------------|
| **In‑context (no training)** | No parameter tuning, just ask the LLM for predictions. | One LLM call per sample → high latency; relies heavily on prompt length; no semantic control over feature usage. | No per‑sample inference; faster. |
| **TABLET** | Adds auxiliary hints and prototypes into prompts. | Still needs a prompt per sample; complex to design; suffers when feature count is large. | Avoids prompt size explosion via bagging. |
| **TabLLM (parameter‑efficient fine‑tuning)** | Fine‑tunes an LLM with LoRA/IA3 → better accuracy. | Requires model checkpoints and GPU resources; not applicable when only API access is available. | Works with any LLM that offers an inference API; no training. |
| **FeatLLM** | Generates interpretability‐friendly rules; lightweight downstream model; robust to spurious features; no per‑sample LLM calls. | Needs a few‑shot prompt construction and a tiny linear training step. | Superior AUC on 13 datasets (average +10 % over TabLLM, STUNT, etc.), especially in low‑shot settings. |

The key trade‑off in FeatLLM is that it shifts the computational burden from make‑prediction time to a one‑time rule‑generation phase. Once the rules are generated, you can deploy the linear model on any device.

---

## Experimental Highlights

* **Datasets** – 13 diverse benchmark datasets (Adult, Diabetes, Credit‑g, Heart, synthetic “Sequence‑type”, newly added UCI datasets).  
* **Shot regimes** – 2, 4, 8, and 16 shots.  
* **Comparison models** – Logistic Regression, XGBoost, Random Forest, SCARF, STUNT, TabPFN, In‑context, TABLET, TabLLM.  
* **Results** – FeatLLM consistently ranks first or second in AUC. With only 4 shots, it reaches performance comparable to conventional models trained on 32 shots.  
* **Cost** – Training uses ~30 LLM calls (API queries) and a small linear model; inference time is comparable to a logistic regression on a CPU.  
* **Robustness** – When irrelevant columns are injected (spurious correlations), FeatLLM’s degradation is the smallest, indicating effective filtering of noisy features via prior knowledge.  

---

## How to Use FeatLLM in Practice

1. **Prepare the data**  
   * Keep feature names and a short natural‑language description of each column (e.g., “Cholesterol: Numeric, mg/dL”).  
   * Serialize the few labeled examples into the format used in the paper:  
     ```
     age is 45. gender is male. cholesterol is 190. Answer: 1
     ```  
2. **Craft the prompt**  
   * Follow the three‑part structure described above.  
   * Set the number of rules per class (`R=10`) and ensemble size (`T=20` or less if prompt length is limiting).  
3. **Generate rules** (one LLM call per ensemble iteration)  
4. **Parse into binary features** (another LLM call per iteration)  
5. **Train the linear model** – simple logistic regression with non‑negative weights.  
6. **Predict** – compute rule‑based binary features for test points, multiply by learned weights, apply softmax.  

All of the steps can be wrapped into a lightweight Python script that uses the OpenAI API (or any other LLM with a public inference endpoint). The entire pipeline can run in a few minutes for small datasets.

---

## Looking Ahead

FeatLLM demonstrates that **LLMs can be more than predictors**; they can be *knowledge‑rich feature generators* that transform raw tabular data into a concise, interpretable feature space. Future work could extend this idea in several directions:

* **Non‑binary features** – generating thresholds, binning schemes, or feature transformations beyond simple “>” or “=”.  
* **Multi‑label & regression tasks** – adapting the rule extraction and weighting scheme.  
* **Dynamic rule updates** – online learning or incremental incorporation of new data.  
* **Bias auditing** – inspecting the extracted rules for harmful stereotypes or misinformation encoded in the LLM’s knowledge.

For now, FeatLLM offers a compelling, low‑cost, and still‑state‑of‑the‑art approach to few‑shot tabular learning that is ready to be deployed in any environment where you can afford a few calls to an LLM but need instant, interpretable predictions afterward.  

---

# Beat the Curse of Limited Data: FeatLLM’s Two‑Step Reasoning for Robust Few‑Shot Learning  

Learning from a handful of labeled examples is hard—especially on tabular data where each feature might be a noisy bullet in a long list.  
The key breakthrough in **FeatLLM** is a *structured, two‑step reasoning* pipeline that lets an LLM first tap into the world knowledge it has learned during pre‑training, then leverage just a few real examples to distill precise, class‑specific rules.  In this post we unpack this idea, explain why it works, and show how it keeps the model from chasing spurious correlations when data are scarce.  

## 1. The Few‑Shot Challenge in Tabular Learning  

At its core, a tabular learning task asks: “Given attributes \(x_1, x_2, \dots, x_d\), predict class \(y\)?”  
When we have only *k* labeled samples (say \(k=4\)), conventional algorithms (LogReg, XGBoost, etc.) risk picking up chance patterns that do not generalise.  
Existing LLM‑based methods that feed every test instance through the LM are **computationally heavy** and often **fail** when tables become large (more than a few dozen columns).  

The question is: *Can we make the LM do the heavy lifting once, then use a lightweight model for every inference?* FeatLLM says yes, and it does so by mirroring how a human expert would solve the problem.  

## 2. Mimicking a Human Expert: Two‑Step Reasoning  

### Step 1 – Prior Knowledge: “What Could Matter?”  
The LLM is asked to *reason abstractly* about how each feature might influence the label **without looking at the concrete training examples**.  
- **Why?** In low‑shot regimes, every sample is precious. If the LLM first settles on a *causal map* (e.g., “age > 60 → higher risk of heart disease”), it grounds its subsequent reasoning in established knowledge.  
- **What happens?** The model constructs a mental graph of feature‑task relationships, filtered by logical type (numeric vs categorical) and by real‑world intuition (e.g., “blood glucose above 140 is unhealthy”).  

### Step 2 – Few‑Shot Calibration: “Which Rules Decide the Class?”  
After the broad map is in place, the LLM consults a handful of *annotated examples* (the few‑shot shots).  
- **Why?** Pure prior knowledge is too vague; real data anchor it.  
- **How?** The LM uses the examples to *explain* the labels in the language of *rules*: “If age > 45 and cholesterol > 200 then the label is ‘High risk’.”  
- **Output format?** Rules are written in a strict, parse‑friendly syntax (think of a mini‑language) so that a simple Python parser can later turn them into binary features.  

The two‑step process prevents the model from generating ad‑hoc correlations: it first needs a *reasonable* explanation, then needs *data‑support* for that explanation. Consequently, the chances that a rule is just noise are greatly reduced.  

## 3. Turning Rules into Features  

Each rule becomes a new binary feature:  
\[
z_{k}^{i} = \begin{cases}
1 & \text{if sample } i \text{ satisfies rule } k\\
0 & \text{otherwise}
\end{cases}
\]
for class \(k\).  
All the binary features across classes are concatenated into a matrix \(\mathbf{Z}\).  
A *tiny* linear model (dot product with non‑negative weights) learns from the few‑shot labeled data how much each rule matters:  
\[
\text{logit}_k^{(i)} = \max(\mathbf{w}_k,0) \cdot \mathbf{z}_k^{(i)}\,,
\quad
\mathbf{p}^{(i)} = \operatorname{softmax}\!\big((\text{logit}_1^{(i)},\dots,\text{logit}_c^{(i)})\big)
\]
Training the weights is essentially *trust validation*: if a rule seldom predicts the correct class, its weight shrinks toward zero.  

Because the inference now only involves a matrix multiplication and a softmax, latency is comparable to any lightweight baseline—no more LM calls per test point!  

## 4. Robustness against Spurious Correlations  

In low‑shot learning, a single irrelevant column can sway a powerful model to a wrong conclusion.  
FeatLLM defends itself in two ways:  

1. **Structural Prior** – By demanding the rule must *fit* a causal relationship established in Step 1, the LM is discouraged from using a brick‑wall feature that has no plausible link to the outcome.  
2. **Ensemble with Bagging** – The model generates multiple rule‑sets by randomly permuting the few‑shot demonstrations and using a higher temperature in the LM. Each “weak learner” has a slightly different view, and averaging over them smooths out accidental over‑fitting to any single noisy column.  

Empirically, when unrelated columns were sprinkled into a dataset, FeatLLM’s performance degraded *less* than that of baselines that rely on direct LM predictions or tree‑based methods.

## 5. Why Two‑Step Reasoning Matters Over One‑Step  

A naive one‑step approach would simply ask the LM: *“Predict the label for this instance.”*  
In a low‑shot context, the model might find a spurious hint in a single feature, produce a very specific rule that happens to fit the few examples, and then over‑trust it.  
By separating abstraction (Step 1) from evidence (Step 2), FeatLLM forces the LM to generate **generalizable** explanations before trust is earned.  

### Quick Summary of the Pipeline  

| Stage | What’s Done | Why It Helps |
|-------|-------------|--------------|
| **Prompt Design** | Provide task, feature list + few demo samples in text | Gives the LM context |
| **Step 1: Knowledge Mapping** | LM infers how features might influence the task | Avoids noise, uses world knowledge |
| **Step 2: Rule Extraction** | LM uses demos to produce precise per‑class rules | Anchors rules in data |
| **Parse & Feature Generation** | Convert rules to binary columns | Creates interpretable features |
| **Linear Weight Learning** | Train small model on few shots | Adjusts importance, filters noise |
| **Ensemble Bagging** | Repeat above, average predictions | Improves robustness and handles prompt limits |

## 6. Final Take‑Home Messages  

- **Rule‑based features + tiny linear model** = fast inference and low complexity.  
- The *two‑step reasoning* forces the LM to *first* think abstractly and *then* validate with data, curbing spurious correlations.  
- Bagging and ensembling allow FeatLLM to scale to larger tables without blowing up the prompt.  
- In practice, FeatLLM outperforms conventional tabular baselines in the 4‑shot regime and matches their performance even when those baselines receive 32 shots.  

In a world where data labeling costs time and money, and where you often have to make a decision with only a handful of examples, FeatLLM offers a principled, efficient, and transparent way to bring the knowledge stored in large language models to bear on tabular learning.  Give it a try when your next project has limited labels—you’ll see that the curse of data scarcity can indeed be broken.



# From Prompt to Program Code: The Technical Journey of Rule Extraction in FeatLLM  

When a large language model (LLM) thinks about “features” in a tabular dataset, it does so in a very human‑like way: it writes sentences, lists facts and then draws conclusions.  
In *FeatLLM* we take advantage of that way of thinking to turn the LLM’s natural‑language output into **binary features** that a tiny downstream model can consume.  
This post walks through the “rule‑to‑code” pipeline: how a prompt is built, how the LLM is nudged to output clean, deterministic rules, how we cope with the inevitable noise, and finally how the LLM itself becomes the parser that turns those rules into executable Python code.

---

## 1.  The challenge: *Natural language → Program*  

Once the LLM generates a rule such as

> “If `age` > 45 and `blood_pressure` < 120, then the patient has a low risk of heart disease.”

we need a reliable, automated way to turn the text into a boolean expression that can be evaluated on any sample.  
The hurdles are:

| Hurdle | Why it matters |
|--------|-----------------|
| **Variability** | The LLM might write “greater than”, “>”, or “more than” for the same comparison. |
| **Ambiguity** | Phrases like “at least” or “no more than” require careful parsing. |
| **Syntax errors** | The LLM may omit parentheses, forget spaces, or misuse quotation marks. |
| **Scale** | We may generate dozens of rules; manual correction is impossible. |

The solution is surprisingly simple: **ask the same LLM to write the parser for us**.

---

## 2.  Prompt design for rule generation

Before we can ask the LLM to parse rules, we must first have rules that are:

1. **Predictive** – they capture real relationships.
2. **Structured** – easy to programmatically read.

To achieve this we give the LLM a *three‑part* prompt:

### 2.1 Basic Information

- **Task description**: a question such as “Does this data indicate diabetes? Yes or no?”
- **Feature definitions**: each feature’s name, type and (optionally) a short definition.
- **Few‑shot examples**: a handful of fully serialized rows with their correct answer.

### 2.2 Reasoning instruction (two‑stage)

1. **Prior knowledge stage** – “list what you know that makes X likely.”  
   This taps the model’s world knowledge (e.g., older age → higher risk).
2. **Data‑driven stage** – “now, look at the examples and produce 10 rules for each answer class.”  

### 2.3 Response instruction

We tell the LLM *exactly* how the rules should look:

```
Rule #1 (Yes):
    age > 45 AND blood_pressure < 120
Rule #2 (No):
    glucose > 110 OR HbA1c > 6.5
```

This consistent formalism greatly simplifies downstream parsing.

---

## 3.  Turning noisy language into a deterministic parser

Even with strict formatting, small variations leak in.  Rather than building a hand‑crafted lexer, we leverage the LLM’s own strengths:

### 3.1 Prompting the LLM for code

We create a second, *meta‑prompt* that contains:

- The **function signature** we want (`def parse_rule(row): ...`).
- A list of the **rules** we just obtained.
- A **brief explanation** of the intended output (e.g., “return True if the row satisfies the rule, else False”).

The LLM receives this prompt alone, no dataset rows, and is asked to produce a short Python snippet that evaluates the specified rule on a dictionary `row`.

**Example meta‑prompt fragment**

```
def parse_rule(row):
    """
    row: dict mapping feature names to values
    Returns True if row satisfies Rule #1 (Yes), else False.
    """
    # Rule #1: age > 45 AND blood_pressure < 120
    ...
```

The model then outputs the body of the function (the comparison logic), possibly using helper functions like `<`, `>`, `and`, `or`.

### 3.2 Executing the generated code

Python’s `exec()` runs the code string, yielding a callable `parse_rule`. We batch‑apply it across all examples:

```python
score = 0
for key, val in parse_rule(row).items():
    score += val   # +1 for a satisfied rule, 0 otherwise
```

Because we normalize each rule to a single boolean, the downstream model sees a clean binary vector.

### 3.3 Handling edge cases

- **Missing values** → the generated function includes early returns.
- **Type mismatches** → the LLM is instructed to cast numeric fields to `float` first.
- **Boolean operators** → the prompt disallows ambiguous keyword usage (e.g., only `and`/`or`).  

These constraints keep the parse code stable and avoid runtime errors.

---

## 4.  Why this works better than hand‑coded parsers

| Approach | Pros | Cons |
|----------|------|------|
| **Hard‑coded Lexer** | Fast once built | Requires maintenance, brittle to new rule types |
| **Regular Expressions** | Handles many patterns | Still fails on complex expressions, hard to extend |
| **LLM‑Generated Parser** | Zero maintenance, scales to arbitrary rule text | Needs API access, slightly higher latency per rule set |

The *LLM‑generated parser* is only called once per dataset (or per bagging trial). The latency is negligible compared to running thousands of LLM calls during inference. Moreover, because the parser is produced *at training time*, it does not bloat the inference cost.

---

## 5.  End‑to‑end workflow

1. **Prompt to LLM** → rules (10 per class).  
2. **Meta‑prompt** → parse functions for each rule set.  
3. **Execute parsing code** → binary feature matrix `Z`.  
4. **Train a lightweight model** (non‑negative linear weights) on `Z`.  
5. **Repeat** with bagging → ensemble over many rule sets.  

The **only expensive component** is the *few* LLM queries at training time. Inference proceeds **without any LLM calls**, yielding latency comparable to a simple linear model.

---

## 6.  Take‑away lessons

| Lesson | Detail |
|--------|--------|
| **Leverage LLMs for their own strengths** | Use them to write code, not just generate text. |
| **Structure the prompt** | Clear, constrained formatting makes parsing trivial. |
| **Normalize noisy outputs** | Ask the LLM to convert natural language into clean syntax. |
| **Keep inference lightweight** | The LLM is killed after training, preserving speed. |
| **Bagging compensates for noise** | Multiple rule sets dilute errors and improve robustness. |

---

## 7.  A short code snippet

```python
# Assuming we received a list of rule strings `rules`
meta_prompt = f"""
def parse_z(row):
    """
    Return a list of booleans: one per rule.
    """
"""

for i, rule in enumerate(rules):
    # Wrap rule logic following the pattern:
    # if year == 2020: age > 30 and income < 50000
    meta_prompt += f"    # Rule #{i+1}\n"
    meta_prompt += f"    if {rule}:\n"
    meta_prompt += f"        yield True\n"
    meta_prompt += f"    else:\n"
    meta_prompt += f"        yield False\n"

# Execute the function
exec(meta_prompt, globals())
```

Now `parse_z(row)` instantly gives you a deterministic binary feature vector, ready for the lightweight downstream model.

---

## 8.  Closing thoughts

Transforming “rule text” into “executable code” is the heart of *FeatLLM*’s success in few‑shot tabular learning.  
By asking the LLM to *write the parser*, we circumvent the brittleness of hand‑crafted tools and keep inference fast.  
The pipeline shows that, even when we rely on a powerful but opaque LLM for feature engineering, thoughtful prompt engineering and a clever delegation of parsing duties can yield a practical, real‑world solution.



# Why FeatLLM Outperforms Other LLM‑Based Tabular Methods

Tabular data are the bread‑and‑butter of industry: credit scores, medical records, click‑through logs, and so on. Yet building accurate predictive models when we only have a handful of labeled samples remains a tough problem. Large Language Models (LLMs) have been courted as a panacea because they can “understand” and reason over data when we ask the right question in natural language. In practice, however, most pipelines that feed an entire sample into an LLM for inference hit two hard walls:

1. **Inference cost** – every test example requires a separate LLM call.  
2. **Prompt length** – a table with dozens or hundreds of features stretches the token budget, causing the model to truncate or degrade.

The new framework **FeatLLM** sidesteps both bottlenecks by turning the LLM into a *feature engineer* instead of a black‑box predictor. Below we unpack how that change, together with a carefully designed ensembling strategy, gives FeatLLM a noticeable edge over contemporary LLM‑based tabular methods such as TabLLM, STUNT, and vanilla in‑context learning.

---

## 1. The LLM pipeline problem

| Method | How it uses the LLM | Main limitation |
|--------|---------------------|-----------------|
| **In‑Context Learning** | Inject the few‑shot examples and the test row into a single prompt, ask the LLM to furnish the label. | Every prediction → LLM call; high latency and cost. |
| **TabLLM** | Fine‑tune the LLM (parameter‑efficient tuning) on the few labeled rows, then run fast inference. | Requires a public checkpoint capable of fine‑tuning; still needs an LLM inference per test sample. |
| **STUNT** | Extract tabular prior knowledge from an external unlabeled corpus; plug it into a standard ML model. | Needs a huge unlabeled corpus and a separate training stage; no direct role for LLM. |

All three approaches keep the *prediction* step inside the LLM. When the table grows, the prompt that reaches the LLM grows linearly with the number of columns. For example, the **Communities** dataset has 128 features. Even with trimmed serialization, the token count can exceed the typical 4 k–8 k‑token limit for GPT‑3.5, forcing the method to either drop columns or fetch a different, more robust model—an undesirable compromise.

---

## 2. FeatLLM’s core idea: LLM = feature engineer

Instead of asking the LLM to output a label directly, FeatLLM asks it to *extract rules* that decide a class. This mirrors how a human expert would look at a table: “If age > 70 **and** cholesterol > 240 mg/dL, then I suspect heart disease.” The steps are:

1. **Prompt design** – The prompt contains a structured *problem description*, *feature descriptions*, and *few‑shot examples*. Two reasoning instructions guide the LLM: first it considers causal relations purely from prior knowledge, then it refines the rules with the sample data.
2. **Rule generation** – The LLM produces a fixed number (10) of declarative rules per class, all in a machine‑parseable template.
3. **Parsing via code generation** – Instead of hand‑crafting parsers for every possible syntactic deviation, FeatLLM asks the LLM again to emit minimal Python code that turns a raw data row into a set of binary features `(z^i_kj) ∈ {0,1}` indicating whether the j‑th rule for class k holds.
4. **Simple downstream model** – After the binary feature matrix is ready, a one‑layer linear classifier (no bias) with non‑negative weights learns how important each rule is.  
   \[
      \text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot\mathbf{z}_k^i,\quad
      \mathbf{p}^i = \text{Softmax}([\text{logit}_1^i,\dots,\text{logit}_c^i]).
   \]
   Because all weights are projected into the positive orthant, the more rules a sample satisfies, the higher its likelihood.

Only the rule‑generation stage talks to the LLM once per *bag* of samples. The final prediction costs **only** a matrix multiplication and a softmax—essentially the same cost as a linear regression.

---

## 3. Ensemble bagging: more rules, fewer tokens

### The problem of prompt size

If we asked the LLM to process every feature at once, the prompt would become unwieldy:
```
Age is 65. Cholesterol is 250. Blood_pressure is 120/80. (... 100 more columns ...)
```
The longer the prompt, the higher the internal memory pressure and the bigger the chance that some columns get truncated.

### The solution: feature bagging

FeatLLM repeatedly performs the *rule extraction* step on *different random subsets* of the features and the training data:

1. Draw a random subset of features (or samples) to keep the serialized prompt short.  
2. Ask the LLM (with a higher temperature) to produce 10 rules per class from that limited context.  
3. Convert those rules into binary features and train a small linear model.  

By repeating this `T` times (typically `T=20`), we gather `T` independent weak learners. Every learner is a small, interpretable rule set; together, they act as an ensemble. The final probability is the **average** of the individual probabilities. Two benefits accrue:

- **Robustness to noisy rules** – If a particular run produced a bad rule (e.g., a spurious correlation with a random feature), its weight will be small after training, and other runs will dilute its effect.  
- **Prompt‑size safety** – Because each run sees only a subset of columns, the prompt stays far below the token limit even for very high‑dimensional tables.

Empirical ablations confirm this: removing the ensemble step (i.e., training a single rule set) drops performance by a few points, while adding it yields a consistent 10% relative AUC gain over state‑of‑the‑art LLM baselines.

---

## 4. Empirical evidence: 10% gain on average

Across **13 datasets**—ranging from the classic `Adult` income prediction to the more recent `Cultivars` soybean yield dataset—FeatLLM outperforms other LLM‑based methods in the following ways:

| Dataset | In‑Context | TabLLM | STUNT | FeatLLM |
|---------|------------|--------|-------|---------|
| Adult (k=4) | 0.62 | 0.66 | 0.70 | **0.77** |
| Communities (k=4) | 0.61 | 0.68 | 0.73 | **0.79** |
| Cultivars (k=4) | 0.58 | 0.61 | 0.66 | **0.73** |
| *...* | *…* | *…* | *…* | **…** |

(The numbers above are illustrative; see the paper for the exact AUCs.) Aggregating over all datasets, FeatLLM exhibits an **average improvement of 10%** relative to the best competitor. The improvement is most pronounced when the number of shots is very low (4–8), a regime where prior knowledge is invaluable.

### Why the baselines struggle

- **In‑Context Learning**: With only 4 training examples, the derivative of the cross‑entropy wrt the LLM’s hidden states is tiny. The model essentially guesses from its prior and cannot generalize well.  
- **TabLLM**: Fine‑tuning on a handful of examples often overfits the *decoder* weights, especially when the LLM is small (e.g., GPT‑3.5). Moreover, each test sample still triggers a fresh forward pass.  
- **STUNT**: The external unlabeled corpus may contain irrelevant semantics that are misaligned with the target domain; the transfer of knowledge is not guaranteed, especially when the target dataset is newly released (like `Cultivars`).  

In contrast, FeatLLM’s rule extraction relies on **semantic reasoning**. The LLM first consults its internal knowledge base about medical risk factors, credit‑worthiness, or chemical composition, then sharpens that intuition with the few examples we provide. This two‑step reasoning process filters out spurious correlations before they can bite.

---

## 5. Practical take‑aways

| Question | What you should do |
|----------|---------------------|
| **I have a new tabular KPI** with 200 features | Use FeatLLM with **feature bagging**, keeping each prompt under 5 k tokens. |
| **I want minimal inference cost** | Run the *LLM once per ensemble run*, then only do a matrix multiplication at inference. |
| **I need interpretability** | Inspect the generated rules (they’re plain English); weight magnitudes indicate rule importance. |
| **I’m constrained to LLM API only** | FeatLLM only needs API inference, no training of the LLM itself. |

---

## 6. Final words

FeatLLM demonstrates that the **role of the LLM** in tabular learning matters as much as the *model architecture* itself. By shifting from end‑to‑end inference to *rule-based feature engineering*, it removes two major pain points: high inference cost and prompt‑size limits. Coupled with an elegant ensemble built on feature and sample bagging, it achieves a real, sustained win—roughly 10% higher AUC on average—over leading contemporaries.

As LLMs keep scaling, frameworks that harness their reasoning power while staying light on computation will become the standard for data‑efficient tabular analytics. FeatLLM is a compelling step in that direction.

The drive toward data‑driven decision making is accelerating across industries, but two practical barriers keep many organizations from fully capitalizing on modern machine learning: **label scarcity** and **run‑time cost**. *FeatLLM* – a technique that turns large language models into feature engineers – tackles both challenges head‑on.  Below, we walk through concrete case studies that illustrate how the approach works in realistic settings, how it stacks up against state‑of‑the‑art few‑shot baselines, and why its negligible inference burden is a game‑changer for real deployments.

## 1. The Core Idea in Plain Language

Traditional tabular models (logistic regression, XGBoost, random forests) learn directly from a training set. When you only have a handful of labeled examples – which is common in regulated domains – these methods tend to overfit or ignore subtle domain knowledge.

*FeatLLM* flips this paradigm. It **asks an LLM to read a handful of examples, infer human‑readable “rules” that capture the pattern between features and the target, and then turns those rules into binary features**. A lightweight linear model is trained on the rule‑based features. At test time, **no further LLM call is needed**: you simply evaluate the binary rules, multiply by the learned weights, and apply a softmax. In effect, the LLM performs *offline feature engineering*; the expert model runs locally.

Key formal ingredients:

| Stage | How it’s done | Outcome |
|-------|---------------|---------|
| **Rule extraction** | 1–2‑step chain‑of‑thought prompt fed to the LLM, with few‑shot examples and feature descriptions. | 10 rules per class (fixed length) in the form “if `Age` > 60 and `BP` < 80 then *Yes*”. |
| **Parsing** | The same LLM is prompted to emit a short Python script that evaluates the rule string against an array of rows. | Binary matrix \(Z \in \{0,1\}^{N \times R}\) for each class. |
| **Learning** | Linear model with non‑negative weights, trained via cross‑entropy on the few labeled shots. | \(\mathbf{w}\) that rank the importance of each rule. |
| **Ensemble** | Bagging over (feature subsets, instance subsets, or random order of shots) to create 20 weak learners, then averaged. | Robustness against unstable rule generation and prompt‑size limits. |

The only thing that runs during each inference is a dot product and a \(O(Rc)\) softmax – a **few hundred microseconds** even on a modest laptop.

## 6. Deployment Considerations

| Question | Answer |
|----------|--------|
| **Can I use any LLM?** | Yes. The framework only requires an **API‑only** LLM (GPT‑3.5, GPT‑4, etc.). No model weights or fine‑tuning infrastructure are needed. |
| **What about prompt limits?** | Bagging (feature and instance subsets) keeps the prompt size under LLM window limits. 20 ensembles are usually enough; more yields diminishing returns. |
| **Will the rules be biased?** | The LLM may inject biases present in its pre‑training data. It is advisable to review the generated rules before deployment and, if necessary, prune or retrain with a curated set of examples. |
| **What if the feature set is huge?** | The rule generation part can still produce only a handful of binary features, keeping the downstream model lightweight.  Feature bagging further reduces the prompt size. |
| **Is it safe for regulated industries?** | Because the final model is a linear combination of transparent rules, audit trails are clear. However, practitioners should validate that the rules comply with legal standards. |
