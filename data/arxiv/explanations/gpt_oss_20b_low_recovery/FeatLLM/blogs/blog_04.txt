\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Why FeatLLM Outperforms Other LLM‑Based Tabular Methods

Tabular data are the bread‑and‑butter of industry: credit scores, medical records, click‑through logs, and so on. Yet building accurate predictive models when we only have a handful of labeled samples remains a tough problem. Large Language Models (LLMs) have been courted as a panacea because they can “understand” and reason over data when we ask the right question in natural language. In practice, however, most pipelines that feed an entire sample into an LLM for inference hit two hard walls:

1. **Inference cost** – every test example requires a separate LLM call.  
2. **Prompt length** – a table with dozens or hundreds of features stretches the token budget, causing the model to truncate or degrade.

The new framework **FeatLLM** sidesteps both bottlenecks by turning the LLM into a *feature engineer* instead of a black‑box predictor. Below we unpack how that change, together with a carefully designed ensembling strategy, gives FeatLLM a noticeable edge over contemporary LLM‑based tabular methods such as TabLLM, STUNT, and vanilla in‑context learning.

---

## 1. The LLM pipeline problem

| Method | How it uses the LLM | Main limitation |
|--------|---------------------|-----------------|
| **In‑Context Learning** | Inject the few‑shot examples and the test row into a single prompt, ask the LLM to furnish the label. | Every prediction → LLM call; high latency and cost. |
| **TabLLM** | Fine‑tune the LLM (parameter‑efficient tuning) on the few labeled rows, then run fast inference. | Requires a public checkpoint capable of fine‑tuning; still needs an LLM inference per test sample. |
| **STUNT** | Extract tabular prior knowledge from an external unlabeled corpus; plug it into a standard ML model. | Needs a huge unlabeled corpus and a separate training stage; no direct role for LLM. |

All three approaches keep the *prediction* step inside the LLM. When the table grows, the prompt that reaches the LLM grows linearly with the number of columns. For example, the **Communities** dataset has 128 features. Even with trimmed serialization, the token count can exceed the typical 4 k–8 k‑token limit for GPT‑3.5, forcing the method to either drop columns or fetch a different, more robust model—an undesirable compromise.

---

## 2. FeatLLM’s core idea: LLM = feature engineer

Instead of asking the LLM to output a label directly, FeatLLM asks it to *extract rules* that decide a class. This mirrors how a human expert would look at a table: “If age > 70 **and** cholesterol > 240 mg/dL, then I suspect heart disease.” The steps are:

1. **Prompt design** – The prompt contains a structured *problem description*, *feature descriptions*, and *few‑shot examples*. Two reasoning instructions guide the LLM: first it considers causal relations purely from prior knowledge, then it refines the rules with the sample data.
2. **Rule generation** – The LLM produces a fixed number (10) of declarative rules per class, all in a machine‑parseable template.
3. **Parsing via code generation** – Instead of hand‑crafting parsers for every possible syntactic deviation, FeatLLM asks the LLM again to emit minimal Python code that turns a raw data row into a set of binary features `(z^i_kj) ∈ {0,1}` indicating whether the j‑th rule for class k holds.
4. **Simple downstream model** – After the binary feature matrix is ready, a one‑layer linear classifier (no bias) with non‑negative weights learns how important each rule is.  
   \[
      \text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot\mathbf{z}_k^i,\quad
      \mathbf{p}^i = \text{Softmax}([\text{logit}_1^i,\dots,\text{logit}_c^i]).
   \]
   Because all weights are projected into the positive orthant, the more rules a sample satisfies, the higher its likelihood.

Only the rule‑generation stage talks to the LLM once per *bag* of samples. The final prediction costs **only** a matrix multiplication and a softmax—essentially the same cost as a linear regression.

---

## 3. Ensemble bagging: more rules, fewer tokens

### The problem of prompt size

If we asked the LLM to process every feature at once, the prompt would become unwieldy:
```
Age is 65. Cholesterol is 250. Blood_pressure is 120/80. (... 100 more columns ...)
```
The longer the prompt, the higher the internal memory pressure and the bigger the chance that some columns get truncated.

### The solution: feature bagging

FeatLLM repeatedly performs the *rule extraction* step on *different random subsets* of the features and the training data:

1. Draw a random subset of features (or samples) to keep the serialized prompt short.  
2. Ask the LLM (with a higher temperature) to produce 10 rules per class from that limited context.  
3. Convert those rules into binary features and train a small linear model.  

By repeating this `T` times (typically `T=20`), we gather `T` independent weak learners. Every learner is a small, interpretable rule set; together, they act as an ensemble. The final probability is the **average** of the individual probabilities. Two benefits accrue:

- **Robustness to noisy rules** – If a particular run produced a bad rule (e.g., a spurious correlation with a random feature), its weight will be small after training, and other runs will dilute its effect.  
- **Prompt‑size safety** – Because each run sees only a subset of columns, the prompt stays far below the token limit even for very high‑dimensional tables.

Empirical ablations confirm this: removing the ensemble step (i.e., training a single rule set) drops performance by a few points, while adding it yields a consistent 10% relative AUC gain over state‑of‑the‑art LLM baselines.

---

## 4. Empirical evidence: 10% gain on average

Across **13 datasets**—ranging from the classic `Adult` income prediction to the more recent `Cultivars` soybean yield dataset—FeatLLM outperforms other LLM‑based methods in the following ways:

| Dataset | In‑Context | TabLLM | STUNT | FeatLLM |
|---------|------------|--------|-------|---------|
| Adult (k=4) | 0.62 | 0.66 | 0.70 | **0.77** |
| Communities (k=4) | 0.61 | 0.68 | 0.73 | **0.79** |
| Cultivars (k=4) | 0.58 | 0.61 | 0.66 | **0.73** |
| *...* | *…* | *…* | *…* | **…** |

(The numbers above are illustrative; see the paper for the exact AUCs.) Aggregating over all datasets, FeatLLM exhibits an **average improvement of 10%** relative to the best competitor. The improvement is most pronounced when the number of shots is very low (4–8), a regime where prior knowledge is invaluable.

### Why the baselines struggle

- **In‑Context Learning**: With only 4 training examples, the derivative of the cross‑entropy wrt the LLM’s hidden states is tiny. The model essentially guesses from its prior and cannot generalize well.  
- **TabLLM**: Fine‑tuning on a handful of examples often overfits the *decoder* weights, especially when the LLM is small (e.g., GPT‑3.5). Moreover, each test sample still triggers a fresh forward pass.  
- **STUNT**: The external unlabeled corpus may contain irrelevant semantics that are misaligned with the target domain; the transfer of knowledge is not guaranteed, especially when the target dataset is newly released (like `Cultivars`).  

In contrast, FeatLLM’s rule extraction relies on **semantic reasoning**. The LLM first consults its internal knowledge base about medical risk factors, credit‑worthiness, or chemical composition, then sharpens that intuition with the few examples we provide. This two‑step reasoning process filters out spurious correlations before they can bite.

---

## 5. Practical take‑aways

| Question | What you should do |
|----------|---------------------|
| **I have a new tabular KPI** with 200 features | Use FeatLLM with **feature bagging**, keeping each prompt under 5 k tokens. |
| **I want minimal inference cost** | Run the *LLM once per ensemble run*, then only do a matrix multiplication at inference. |
| **I need interpretability** | Inspect the generated rules (they’re plain English); weight magnitudes indicate rule importance. |
| **I’m constrained to LLM API only** | FeatLLM only needs API inference, no training of the LLM itself. |

---

## 6. Final words

FeatLLM demonstrates that the **role of the LLM** in tabular learning matters as much as the *model architecture* itself. By shifting from end‑to‑end inference to *rule-based feature engineering*, it removes two major pain points: high inference cost and prompt‑size limits. Coupled with an elegant ensemble built on feature and sample bagging, it achieves a real, sustained win—roughly 10% higher AUC on average—over leading contemporaries.

As LLMs keep scaling, frameworks that harness their reasoning power while staying light on computation will become the standard for data‑efficient tabular analytics. FeatLLM is a compelling step in that direction.
