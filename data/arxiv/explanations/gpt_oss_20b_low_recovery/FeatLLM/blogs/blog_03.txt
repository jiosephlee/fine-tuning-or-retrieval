# From Prompt to Program Code: The Technical Journey of Rule Extraction in FeatLLM  

When a large language model (LLM) thinks about “features” in a tabular dataset, it does so in a very human‑like way: it writes sentences, lists facts and then draws conclusions.  
In *FeatLLM* we take advantage of that way of thinking to turn the LLM’s natural‑language output into **binary features** that a tiny downstream model can consume.  
This post walks through the “rule‑to‑code” pipeline: how a prompt is built, how the LLM is nudged to output clean, deterministic rules, how we cope with the inevitable noise, and finally how the LLM itself becomes the parser that turns those rules into executable Python code.

---

## 1.  The challenge: *Natural language → Program*  

Once the LLM generates a rule such as

> “If `age` > 45 and `blood_pressure` < 120, then the patient has a low risk of heart disease.”

we need a reliable, automated way to turn the text into a boolean expression that can be evaluated on any sample.  
The hurdles are:

| Hurdle | Why it matters |
|--------|-----------------|
| **Variability** | The LLM might write “greater than”, “>”, or “more than” for the same comparison. |
| **Ambiguity** | Phrases like “at least” or “no more than” require careful parsing. |
| **Syntax errors** | The LLM may omit parentheses, forget spaces, or misuse quotation marks. |
| **Scale** | We may generate dozens of rules; manual correction is impossible. |

The solution is surprisingly simple: **ask the same LLM to write the parser for us**.

---

## 2.  Prompt design for rule generation

Before we can ask the LLM to parse rules, we must first have rules that are:

1. **Predictive** – they capture real relationships.
2. **Structured** – easy to programmatically read.

To achieve this we give the LLM a *three‑part* prompt:

### 2.1 Basic Information

- **Task description**: a question such as “Does this data indicate diabetes? Yes or no?”
- **Feature definitions**: each feature’s name, type and (optionally) a short definition.
- **Few‑shot examples**: a handful of fully serialized rows with their correct answer.

### 2.2 Reasoning instruction (two‑stage)

1. **Prior knowledge stage** – “list what you know that makes X likely.”  
   This taps the model’s world knowledge (e.g., older age → higher risk).
2. **Data‑driven stage** – “now, look at the examples and produce 10 rules for each answer class.”  

### 2.3 Response instruction

We tell the LLM *exactly* how the rules should look:

```
Rule #1 (Yes):
    age > 45 AND blood_pressure < 120
Rule #2 (No):
    glucose > 110 OR HbA1c > 6.5
```

This consistent formalism greatly simplifies downstream parsing.

---

## 3.  Turning noisy language into a deterministic parser

Even with strict formatting, small variations leak in.  Rather than building a hand‑crafted lexer, we leverage the LLM’s own strengths:

### 3.1 Prompting the LLM for code

We create a second, *meta‑prompt* that contains:

- The **function signature** we want (`def parse_rule(row): ...`).
- A list of the **rules** we just obtained.
- A **brief explanation** of the intended output (e.g., “return True if the row satisfies the rule, else False”).

The LLM receives this prompt alone, no dataset rows, and is asked to produce a short Python snippet that evaluates the specified rule on a dictionary `row`.

**Example meta‑prompt fragment**

```
def parse_rule(row):
    """
    row: dict mapping feature names to values
    Returns True if row satisfies Rule #1 (Yes), else False.
    """
    # Rule #1: age > 45 AND blood_pressure < 120
    ...
```

The model then outputs the body of the function (the comparison logic), possibly using helper functions like `<`, `>`, `and`, `or`.

### 3.2 Executing the generated code

Python’s `exec()` runs the code string, yielding a callable `parse_rule`. We batch‑apply it across all examples:

```python
score = 0
for key, val in parse_rule(row).items():
    score += val   # +1 for a satisfied rule, 0 otherwise
```

Because we normalize each rule to a single boolean, the downstream model sees a clean binary vector.

### 3.3 Handling edge cases

- **Missing values** → the generated function includes early returns.
- **Type mismatches** → the LLM is instructed to cast numeric fields to `float` first.
- **Boolean operators** → the prompt disallows ambiguous keyword usage (e.g., only `and`/`or`).  

These constraints keep the parse code stable and avoid runtime errors.

---

## 4.  Why this works better than hand‑coded parsers

| Approach | Pros | Cons |
|----------|------|------|
| **Hard‑coded Lexer** | Fast once built | Requires maintenance, brittle to new rule types |
| **Regular Expressions** | Handles many patterns | Still fails on complex expressions, hard to extend |
| **LLM‑Generated Parser** | Zero maintenance, scales to arbitrary rule text | Needs API access, slightly higher latency per rule set |

The *LLM‑generated parser* is only called once per dataset (or per bagging trial). The latency is negligible compared to running thousands of LLM calls during inference. Moreover, because the parser is produced *at training time*, it does not bloat the inference cost.

---

## 5.  End‑to‑end workflow

1. **Prompt to LLM** → rules (10 per class).  
2. **Meta‑prompt** → parse functions for each rule set.  
3. **Execute parsing code** → binary feature matrix `Z`.  
4. **Train a lightweight model** (non‑negative linear weights) on `Z`.  
5. **Repeat** with bagging → ensemble over many rule sets.  

The **only expensive component** is the *few* LLM queries at training time. Inference proceeds **without any LLM calls**, yielding latency comparable to a simple linear model.

---

## 6.  Take‑away lessons

| Lesson | Detail |
|--------|--------|
| **Leverage LLMs for their own strengths** | Use them to write code, not just generate text. |
| **Structure the prompt** | Clear, constrained formatting makes parsing trivial. |
| **Normalize noisy outputs** | Ask the LLM to convert natural language into clean syntax. |
| **Keep inference lightweight** | The LLM is killed after training, preserving speed. |
| **Bagging compensates for noise** | Multiple rule sets dilute errors and improve robustness. |

## 7.  A short code snippet

```python
# Assuming we received a list of rule strings `rules`
meta_prompt = f"""
def parse_z(row):
    """
    Return a list of booleans: one per rule.
    """
"""

for i, rule in enumerate(rules):
    # Wrap rule logic following the pattern:
    # if year == 2020: age > 30 and income < 50000
    meta_prompt += f"    # Rule #{i+1}\n"
    meta_prompt += f"    if {rule}:\n"
    meta_prompt += f"        yield True\n"
    meta_prompt += f"    else:\n"
    meta_prompt += f"        yield False\n"

# Execute the function
exec(meta_prompt, globals())
```

Now `parse_z(row)` instantly gives you a deterministic binary feature vector, ready for the lightweight downstream model.

---

## 8.  Closing thoughts

Transforming “rule text” into “executable code” is the heart of *FeatLLM*’s success in few‑shot tabular learning.  
By asking the LLM to *write the parser*, we circumvent the brittleness of hand‑crafted tools and keep inference fast.  
The pipeline shows that, even when we rely on a powerful but opaque LLM for feature engineering, thoughtful prompt engineering and a clever delegation of parsing duties can yield a practical, real‑world solution.
