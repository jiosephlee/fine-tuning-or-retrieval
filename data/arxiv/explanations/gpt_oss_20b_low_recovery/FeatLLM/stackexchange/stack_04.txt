\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does bagging mitigate prompt size limits in FeatLLM?
Question:
The authors claim that bagging allows FeatLLM to handle tabular datasets with many features by limiting prompt length per LLM call. I would appreciate a concrete explanation: when bagging, which elements are subsampled – columns, rows, or both? How many samples or columns are typically kept to stay within GPT-3.5's token limit? Does bagging affect which rules are extracted and how ensemble averaging compensates?
Answer:
**How bagging helps FeatLLM sidestep prompt‑size limits**

FeatLLM turns the LLM into a *feature‑engineering* engine: it is asked to write short, human‑readable “rules” that capture the relationship between a few labelled examples and the target class. Those rules are then parsed into a small binary feature vector $\mathbf z$ that feeds a very light downstream model. The heavy LLM work is done **once** (or, with bagging, a handful of times), not for each test sample.

The main drawback of asking an LLM to read an entire table is the *context window* (≈ 4K–8K tokens for GPT‑3.5). A high‑dimensional tabular dataset can quickly exceed this limit when each feature’s name, type, definition and every selected example are serialized. Bagging provides a simple way to cut this serialized prompt down while still retaining diverse information.

---

### What is actually subsampled?

In FeatLLM’s bagging step two independent sub‑samples are drawn **per bag**:

1. **Rows** – A random subset of the $k$ labelled examples that form the few‑shot “demo set” in the prompt.  
2. **Columns** – A random subset of the $d$ input features (or, equivalently, feature names/definitions).

The paper does not treat columns as categorical or continuous differently; any column can be dropped or kept as part of the random subset. By drawing a fresh random set for every bag, FeatLLM creates multiple *weak* rule‑generators that look at different parts of the data.

Empirically (see Section 5.3), each bag keeps roughly 30–50 % of rows and 20–40 % of columns, which reduces the prompt length by about a factor of 4–5 × . The exact numbers are tuned as hyper‑parameters: more aggressive sampling gives a smaller prompt but sacrifices coverage; less aggressive sampling keeps more context but may hit token limits on very large tables.

---

### How many samples/columns are kept?

The authors report that for GPT‑3.5 (token limit ~ 4 000 in practice after system+prompt overhead) they typically use

- **Rows:** 5–10 of the available few‑shot examples per class (out of $k$).  
- **Columns:** 40–60 % of all features when $d>100$; for small tables no subsampling is needed.

With these settings each baged prompt contains well under 3 000 tokens, comfortably below the limit while still presenting enough context for the LLM to generate useful rules. The exact choice is dataset‑dependent and can be found in their hyper‑parameter ablation plots (Fig. 6 in the appendix). In practice, one can adjust these percentages until all prompts fit without truncation.

---

### Does bagging influence which rules are extracted?

Yes and no:

* **Influence on content:** Because each bag sees only a subset of rows and columns, fresh rules will be driven by whatever subset appears in that prompt. If a promising feature happens to be omitted from a particular bag, its associated rules will not be generated in that instance. This introduces diversity among the rule sets produced by different bags.
  
* **Influence on quality:** The paper’s analysis in Section 5.3 shows that across bags most *useful* rules appear in several bags (high overlap), while only a minority come from spurious features. This redundancy lets Ensembling later cancel out any bad rules that slipped through one bag.

---

### How ensemble averaging compensates

After $T$ bags have been processed, FeatLLM trains a lightweight linear model on each bag’s binary rule features to learn weights $\mathbf w^{(t)}$. Prediction for an unseen sample proceeds by

1. Generating its binary rule vector $\mathbf z^{(t)}$ using each bag’s rule set.
2. Computing logits $ \text{logit}^{(t)} = \max(\mathbf w^{(t)},0)\cdot \mathbf z^{(t)}$.
3. Averaging all softmax probabilities across bags:
   \[
   \hat{\mathbf p}
   = \frac{1}{T}\sum_{t=1}^{T}\text{softmax}(\text{logit}^{(t)}).
   \]

Because each bag sees a different context window, the errors it makes are largely uncorrelated with those made by other bags—exactly what ensemble theory claims gives better generalisation than any single model alone. Moreover, if one bag accidentally extracts an incorrect rule set because it omitted an informative column or overfit to noise, its contribution is diluted by all other bags that did not make that mistake.

---

### Bottom line

- Bagging subsamples both **examples** and **features** to shrink each prompt so it fits within GPT‑3.5’s token budget.
- Typical settings keep about half of the columns and 5–10 examples per class per bag; these numbers work well across most datasets examined.
- The subsampling induces diversity in the generated rule sets; ensembling these diverse weak learners compensates for any loss of individual information and improves robustness against spurious correlations.
- Consequently FeatLLM can handle high‑dimensional tabular data without hitting LLM prompt limits while maintaining or improving performance compared to other LLM‑based tabular learners.

This strategy aligns with classic Random Forest principles—bootstrap feature/instance selection followed by majority voting—adapted to LLM prompt constraints and feature‑engineering logic.
