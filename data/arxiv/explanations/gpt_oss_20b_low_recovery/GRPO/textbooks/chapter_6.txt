\title{A Textbook about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

Chapter 6: # Instruction Fine‑Tuning (SFT) for Mathematics

Large language models (LLMs) that have been pre‑trained on massive amounts of text and code often lack the discipline of step‑by‑step reasoning required for solving mathematics problems. The supervised fine‑tuning (SFT) stage of **DeepSeekMath‑Instruct** bridges this gap by instilling explicit reasoning patterns—chain‑of‑thought (CoT), program‑of‑thought (PoT), and tool‑integrated templates—into the model’s generation policy. In this chapter we unpack the design of the instruction set, the meticulous curation of the training data, the format of prompts and completions, the fine‑tuning protocol, and the evaluation scheme that guided the creation of DeepSeekMath‑Instruct.

---

## Dataset Construction

A robust instruction dataset is essential for steering a model toward reliable, human‑readable mathematical reasoning. The entire corpus contains **776 000 examples** generated from both English‑ and Chinese‑language sources. The examples are grouped along three main axes:

| Source | Annotation Type | Example Scope |
|--------|-----------------|---------------|
| **English** | *GSM8K* problems annotated with tool‑integrated solutions; *MATH* problems similarly annotated; a subset from *MathInstruct*; the *Lila‑OOD* collection with CoT or PoT solutions. | Algebra, probability, number theory, calculus, geometry, discrete mathematics. |
| **Chinese** | K‑12 Chinese problems covering 76 sub‑topics (linear equations, inequalities, exponents, etc.) with CoT and tool‑integrated solutions. | Elementary and middle‑school mathematics, reflecting the Chinese curriculum. |

The creators of the dataset first downloaded raw problem statements from the respective benchmarks, then assigned annotators a set of templates described below. The final dataset is thus a balanced mixture of problem difficulty, styles of reasoning, and language representation.

---

## Example Types

### Chain‑of‑Thought (CoT)

A CoT completion is a natural‑language explanation that breaks the solution into intermediate deductive or computational steps, mirroring the way a student might narrate their reasoning. An example CoT answer looks like:

```
Question: 5x + 7 = 22. Find x.
Answer:
We first isolate the term with the unknown:
5x = 22 - 7
5x = 15
Now we divide both sides by 5:
x = 15/5
x = 3
Answer: 3
```

During annotation, the model’s first few tokens are verified for logical consistency, and the final answer is verified for correctness. The style encourages transparency and aids downstream evaluation.

### Program‑of‑Thought (PoT)

PoT answers embed a short program (typically Python) that a user can execute. This is particularly useful when synthetic arithmetic or symbolic manipulation is required. A PoT example:

```
Question: 9! / 8! = ?
Answer:
def compute():
    import math
    return math.factorial(9) // math.factorial(8)
print(compute())
```

After execution, the program’s output is matched against the reference answer. The annotation process ensures that every mathematical operation is captured in an executable form.

### Tool‑Integrated Reasoning

Some problems are tackled by combining natural‑language reasoning with calls to external libraries such as `sympy`. In the annotation step, a hand‑crafted prompt is provided to the model that instructs it to produce a mixture of text and program snippets. For instance:

```
Question: Solve for x: 2x^2 + 3x - 5 = 0
Answer:
We will use the sympy library to compute the roots.
import sympy as sp
x = sp.Symbol('x')
eq = 2*x**2 + 3*x - 5
sol = sp.solve(eq, x)
print(sol)
```

The resulting program is evaluated in a sandbox, and the output is compared with the reference solution.

## Prompt–Completion Formats

All training examples follow a prompt–completion structure that keeps the prompt concise while giving the model a clear instruction to produce a **self‑contained solution**. The general format is:

```
<PROMPT>:
{Problem statement}

<INSTRUCTION>:
Please solve the problem step by step. Provide your answer in the format specified below:
- For CoT: write textual reasoning and final answer.
- For PoT: write a Python program that outputs the answer.
- For Tool‑integrated: write code using allowable libraries plus descriptive text.

<COMPLETION>:
{Annotator’s solution}
```

The annotation template is the same for English and Chinese examples; only the language of the problem statement and the final answer changes. The use of a uniform schema simplifies tokenization and downstream evaluation.

## Training Protocol

### Hyper‑Parameters

| Parameter | Value |
|-----------|-------|
| Training steps | 500 |
| Batch size | 256 |
| Learning rate | \(5 \times 10^{-5}\) |
| Token limit | 4 000 (maximum context length) |
| Optimizer | AdamW (coefficients same as DeepSeek LLM training) |

The batch size is chosen to fit a 7‑B parameter model on the available GPU infrastructure. The learning rate is kept modest because the data are highly structured; a high rate would risk over‑fitting to a narrow style of reasoning.

### Pre‑processing

Before training, each example is truncated or padded to fit the 4 K token window. Maximal truncation occurs at the completion border; prompt truncation is avoided because it would undermine the reasoning context. The tokenizer maps Chinese characters and English words to the same sub‑word vocabulary, ensuring language‑agnostic token encoding.

### Objective

The SFT loss is the standard cross‑entropy between the model’s predicted token distribution and the annotated completion token sequence. Because the dataset is heavily balanced between languages and reasoning styles, the loss averages over the entire batch, yielding a consistent signal for the policy.

## Evaluation Protocols

To fully understand how the model reacts to different instruction styles, evaluation is performed under four distinct settings:

| Setting | Tool Use | Prompt Type | Shot |
|---------|----------|-------------|------|
| **Zero‑shot** | Disabled | CoT | 0 |
| **Zero‑shot** | Enabled | PoT / Tool‑integrated | 0 |
| **Few‑shot** | Disabled | CoT | 16 |
| **Few‑shot** | Enabled | PoT / Tool‑integrated | 16 |

*Tool‑Use Disabled*: the model follows a purely textual reasoning path and must produce the final answer without execution.  
*Tool‑Use Enabled*: the model can generate code that is automatically executed; the output of the program is treated as the answer.

Each benchmark is evaluated under both tool‑use combinations. Results are reported for zero‑shot and few‑shot separately, and for all prompting styles (CoT, PoT, tool‑integrated).

## Key Takeaways

1. **Curated Instruction Style** – Introducing explicit CoT, PoT, and tool‑integrated templates during SFT aligns the model’s generation with human reasoning strategies, making it easier to evaluate and debug.
2. **Balanced Dataset** – The 776 000 example corpus covers a wide variety of math topics and languages, giving the model exposure to diverse problem formulations.
3. **Structured Prompting** – A clear, repeatable prompt–completion format facilitates efficient tokenization, validation, and automatic scoring.
4. **Targeted Fine‑Tuning** – The modest learning rate and batch size preserve the generality of the pre‑trained policy while embedding disciplined reasoning patterns.
5. **Comprehensive Evaluation** – By systematically varying shot setting, language, and tool usage, the evaluation framework uncovers the strengths and weaknesses of the instruction‑tuned model.

These design choices together yield **DeepSeekMath‑Instruct**, a 7 B LLM that not only competes with larger open‑source counterparts but also sets a new baseline for mathematically focused instruction fine‑tuning.
