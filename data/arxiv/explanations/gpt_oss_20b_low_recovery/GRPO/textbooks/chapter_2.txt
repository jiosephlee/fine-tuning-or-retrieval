\title{A Textbook about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

Chapter 2: # 2. Foundations of Pre‑Training for Mathematics

The remarkable progress in large language models (LLMs) has largely hinged on how the models are **pre‑trained**: the scale of the neural net, the data it sees, and the objective it optimizes. Yet when the target domain is mathematics, the very shape of these ingredients changes. This chapter unpacks why pre‑training a model for mathematics has its own idiosyncrasies, and how the pipeline chosen by *DeepSeekMath* specifically equips the model to reason mathematically.

---

## LLM Architecture Basics (transformers, tokenization, scaling)

At the heart of every modern LLM is the **transformer** family of architectures, which comprise multi‑head self‑attention layers, feed‑forward MLPs, layer normalisation, and residual connections. A transformer accepts a sequence of input tokens and outputs a probability distribution over the next token at each step, conditioned on all prior tokens.  

*Tokenisation* bridges the gap between raw text and the transformer. A tokenizer maps any string into a sequence of discrete symbols (tokens). In practice, we use sub‑word tokenisers such as SentencePiece or BPE, which have been shown to generalise well to out‑of‑vocabulary symbols. For mathematical models, the tokenizer must recognise not only alphabetic words but also symbols such as `\int`, `\forall`, superscripts, and Chinese characters. *DeepSeekMath* therefore extends the vocabulary to include these symbols, thereby allowing the model to consume and generate well‑formed mathematical expressions directly.

Scaling – the number of parameters – is crucial for capturing long‑range dependencies, a central requirement for formal logic and mathematics. The *DeepSeekMath-Base 7B* model sits comfortably in the 1–10 B parameter regime, striking a balance between memory efficiency and representational power. Empirical evidence from *DeepSeekMath* shows that **fewer** parameters can **surpass** larger, generic models when the training data is *domain‑specific*.

---

## Code Training as a Proxy for Logic and Formalism

The first observation in the DeepSeekMath pipeline is the decision to start from a **code‑training** model (*DeepSeek-Coder-Base-v1.5*). Code, like mathematics, is a highly structured, formal language with strict syntax and semantics. It teaches a model the following:

1. **Precise syntax handling** – programming languages enforce strict rules (matching braces, semicolons, indentation). Training on code sharpens a model’s ability to maintain coherence over long token spans, a skill directly transferable to the balanced brackets of LaTeX or integral expressions.

2. **Logical flow** – code often requires stepwise reasoning: inside an `if` block we must evaluate a condition, then proceed to the body. This mirrors how a mathematician constructs a proof: introduction → assumption → deduction → conclusion.

3. **Tool usage primitives** – many language models now support *tool‑integrated reasoning*, where the model can invoke external APIs (e.g., evaluating a Python expression). Code training naturally introduces the pattern “generate code → execute → use result”, which is a form of *program‑of‑thought* (PoT) frequently employed in mathematical solving.

4. **Memory reuse** – code frequently re‑uses variables and functions. Understanding scope and variable lifetimes deepens a model’s grasp of contextual dependencies, beneficial for long proofs that revisit earlier lemmas.

Empirically, the DeepSeekMath experiments confirmed that a two‑stage regimen – first 400 B code tokens, then 150 B math tokens – outperformed a one‑stage 400 B code + 150 B math mixture when the model size was modest (1.3 B). This suggests that a dedicated code pre‑training phase can give a *foundation* that subsequent math data can refine without catastrophic forgetting.

## Mathematical Language: Symbols, Notation, and Multilingual Considerations

Mathematical communication is inherently **symbolic**. A high‑quality pre‑training corpus must respect the following linguistic features:

* **Symbols and LaTeX** – equations are encoded in LaTeX syntax in almost all public datasets (Common Crawl, StackExchange, arXiv). Tokenising these expressions demands a tokenizer capable of preserving nested braces, superscripts, subscript and fraction structures. Moreover, the model must learn when a symbol is *literal* (e.g., `x`) versus *operator* (e.g., `\times`), a subtlety that appears in the parsing of algebraic expressions.

* **Notation variability** – the same mathematical idea can be expressed in multiple notations (“∑_{i=1}^n i” vs “sum_{i=1}^{n} i”). A model that can recognise equivalence across notations must see many instances of the same concept expressed differently. This diversity is a direct product of the DeepSeekMath data‑selection pipeline, which mines a large fraction of the Common Crawl, yielding 120 B math tokens across dozens of languages.

* **Multilinguality** – mathematics is a *global* language, but many educational resources are still region‑specific. The DeepSeekMath corpus deliberately retains **non‑English** content (notably Chinese). This enhances performance on Chinese benchmarks such as CMATH, Gaokao-MathQA, and MGSM‑zh, while still handling English datasets. A multilingual tokenizer requires a larger vocabulary (often in the 200 k to 400 k range) to capture diverse character sets; *DeepSeekMath* scales its vocabulary accordingly.

* **LaTeX to natural‑language bridges** – many corpora intermix prose (e.g., the explanatory paragraph above an equation) and symbolic expressions. The model must learn to transition fluidly between the two modalities, a pattern reinforced by *chain‑of‑thought* (CoT) data in the instruction‑tuning stage.

## Pre‑training Objectives: Causal LM vs Other Tasks

The default pre‑training objective for *DeepSeekMath* is the standard **causal language modelling** (CLM): given tokens \(x_{1}, \dotsc, x_{t-1}\), predict \(x_t\). CLM is attractive because it is simple, scalable, and naturally aligns with downstream generation tasks (e.g., answering math questions).

However, alternative objectives can be beneficial:

* **Masked Language Modelling (MLM)** – reveals a fraction of tokens and trains the model to predict the missing ones. MLM excels at *bidirectional* context, useful for tasks like question answering, but is less suited to *generation* where a left-to-right flow is needed.

* **Sequence‑to‑Sequence (S2S)** – especially when paired with *sequence‑to‑sequence* data such as translation or summarisation, S2S can drive a model to produce entire solution steps. In mathematical contexts, the downstream objective is often "generate the entire reasoning chain". Combining CLM with S2S fine‑tuning helps the model grasp longer reasoning scopes.

* **Reinforcement Learning (RL)** – after the SFT stage, the DeepSeekMath pipeline applies *Group Relative Policy Optimization* (GRPO). Here, the objective becomes to maximise a reward that reflects the correctness and quality of an entire solution. Unlike CLM, RL can shape the decision process at each token via *advantage* functions based on the final answer and intermediate steps.

The deep learning community shares the intuition that **pre‑training on the right blend of data and objective** yields the best downstream performance. The DeepSeekMath pipeline demonstrates that a CLM pre‑training supported by high‑quality mathematical data, followed by a carefully scheduled RL fine‑tuning, can push an open‑source 7 B model to achieve scores comparable to commercial giants.

## Challenges of Contamination and De‑contamination in Benchmarks

When training on large‑scale web data, an unavoidable risk is **benchmark contamination**: the model is unintentionally exposed to *answers* from the same problems that later appear in evaluation sets. Even a single token overlap can inflate a model’s reported score.

**Why it matters in mathematics**: Compared to generic language tasks, mathematical benchmarks often contain highly specific phrases or problem statements that are easier to copy from a source. Because many open datasets (GSM8K, MATH, CMATH) are extracted from online Q&A sites, the same passages may already exist in the Common Crawl.

**De‑contamination strategy in DeepSeekMath**:

1. **Exact n‑gram filtering** – any text fragment containing a 10‑gram subsequence identical to a substring in a benchmark is removed from the training corpus.

2. **Partial overlap handling** – for short benchmark snippets (<10 grams) but with ≥3 gram matches, the containing web page is discarded.

3. **Domain‑aware pruning** – once the FastText-based classifier identifies “math‑related” domains (e.g., mathoverflow.net), the de‑contamination process is applied to all pages therein.

4. **Iterative verification** – after each data‑collection iteration, spot‑checks are conducted to ensure new pages do not contain suspiciously similar content.

By incorporating these steps, the DeepSeekMath team guarantees that its *natural* performance on benchmarks truly reflects the model’s reasoning abilities rather than memorised answers.

### Take‑away for Researchers

- **Start from a code‑grounded model** if your target domain is formally structured. Code training conveys syntax discipline, logical flow, and tool‑use patterns that are directly relevant to mathematics.

- **Build a highly curated token supply**. A 120 B math‑token corpus, distilled iteratively from the Common Crawl with a fastText selector and human‑in‑the‑loop refinement, yields a *higher‑quality* dataset than simply aggregating existing corpora.

- **Design a tokenizer that respects mathematical notation**. Include LaTeX symbols, Unicode operators, and multi‑language characters to allow the model to parse and generate expressions verbatim.

- **Guard against benchmark contamination** with rigorous n‑gram filtering and domain‑aware pruning.

- **Augment the basic causal LM objective with reinforcement signals** that evaluate full proofs or multi‑step solutions, thereby aligning training objectives with evaluation criteria.

These principles, illustrated by the *DeepSeekMath* pipeline, lay the foundation for any practitioner aiming to develop state‑of‑the‑art open‑source models in the mathematical reasoning domain.
