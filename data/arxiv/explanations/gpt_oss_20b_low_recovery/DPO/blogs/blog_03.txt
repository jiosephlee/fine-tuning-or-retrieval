# Concrete Guided Example: Fine‑Tuning a 6B GPT with Direct Preference Optimization  

## TL;DR  
This post walks you through a full DPO training pipeline on a 6‑B parameter GPT model. From data‑generation all the way to the optimizer, every step is grounded in *Direct Preference Optimization (DPO)* as described in the paper *“Direct Preference Optimization: Your Language Model is Secretly a Reward Model.”* If you’ve been chasing RLHF but hate the heavy RL loop, DPO gives you the same final policy with a single 2‑class cross‑entropy loss.

---

## 1. Why DPO?  

Typical RLHF needs three stages: supervised fine‑tuning (SFT), reward modeling, and policy optimization with PPO or another RL solver.  
- **Reward modeling** requires fitting a separate network and then sampling from the policy to evaluate it.  
- **RL phase** is notoriously unstable, expensive to tune and needs multiple epochs of sampling per update.

The DPO paper unpacks a neat algebraic equivalence:

\[
\pi^\ast(y|x)=\frac{1}{Z(x)}\pi_{\text{ref}}(y|x)\exp\!\left(\tfrac{1}{\beta}r^\ast(x,y)\right)
\]

which immediately flips into an implicit reward:

\[
r^{\text{imp}}(x,y)=\beta \ln \frac{\pi_\theta(y|x)}{\pi_{\text{ref}}(y|x)}
\]

Plugging this into Bradley–Terry gives a direct policy objective:

\[
\mathcal{L}_{\text{DPO}}(\theta)=
-\mathbb{E}_{(x,y_w,y_l)} 
\bigl[\ln \sigma \!\bigl(\beta\, \ln\!\frac{\pi_\theta(y_w|x)}{\pi_{\text{ref}}(y_w|x)}-
          \beta\, \ln\!\frac{\pi_\theta(y_l|x)}{\pi_{\text{ref}}(y_l|x)} \bigr)\bigr]
\]

A plain binary cross‑entropy training loop—no sampling inside gradients!  
That’s the beauty of DPO.

## 2. Whole‑Pipeline Overview  

```
            ┌────────┐
            │  SFT   │
            └───┬────┘
                │
   ┌────────────▼───────┐
   │ Generate Comparisons│   ←  sample two completions per prompt
   └──────┬─────────────┘
          │
   ┌──────▼──────────────┐
   │   Label preferences │   ←  humans | humans | ...
   └──────┬──────────────┘
          │
   ┌──────▼──────────────┐
   │    DPO Finetune     │   ←  single CE loss on (pref,outcome)
   └────────────────────—┘
```

We’ll run this on a *6B GPT* stored as `EleutherAI/gpt-j-6B`, but the recipe generalises to any autoregressive model that exposes a `logits` method.

### 3.4 Generate Comparison Data

We need *demonstrations* consisting of:
`prompt x`, two completions `(y1, y2)`, then a human label choosing `y_w` or `y_l`.

```python
def sample_completion(prompt, max_new_tokens=50):
    input_ids = tokenizer(prompt, return_tensors="pt").input_ids.to(model_ref.device)
    out_ids = model_ref.generate(
        input_ids, max_new_tokens=max_new_tokens, top_p=0.95,
        do_sample=True)[:, len(input_ids[0]):]
    return tokenizer.decode(out_ids[0], skip_special_tokens=True)

prompts = ["Tell me why cats are adorable." , "..."]      # expand to your domain set

comparisons = []
for p in prompts:
    y1 = sample_completion(p)
    y2 = sample_completion(p)
    # placeholder: random label; in practice get human annotations!
    label = "y1" if random.random() > .5 else "y2"
    comparisons.append({"prompt": p,
                        "women": y1 if label=="y1" else y2,
                        "loser": y2 if label=="y1" else y1})
```

> In production you’ll collect these via MTurk or internal crowdsourcing; see paragraph “Human preference collection” in the paper.

Store them for later:

The core function that will be plugged into `Trainer`.

The above stub tries to dig deep but it’s unnecessary complicated; instead we take advantage of standard `Trainer` hooks:

* Build two **fake** decoder contexts (`inputs_embeds`) that include the prompt concatenated with completion tokens *excluding BOS*.  
* Run each through `model()` once each and retrieve log–probabilities using `logits[:, -len(tok)+:-1]`.
* Average over time step level—the fine‐grained cross entropy that yields sequence probability.

Simplify into helper functions (adapted from TRL’s internal utils):

It handles:
- **KL-weighting** automatically (`β`)
- Token‐level masking around EOS/PROMPT boundaries  
- Working with extremely long generation sequences via caching of `attention_masks`.
- Overlap sampling/keeps track of ref-model grads neutralised (`with torch.no_grad()`).

> **Checkpointing:** Specify `"save_strategy":"epoch"` & `"save_total_limit":3`. Keep both `.ckpt` files and HuggingFace config (`config.json`) – they contain exact weights used at evaluation.

### 3.7 Dealing With Distribution Shift

Distribution shift can hurt because both π_θ and π_ref were built on slightly different prompts than what you’ll serve live.

Recommended protocol – derived from Section 4 Discussion:

| Step | Action |
|------|--------|
| **A** | Freeze ‑ or periodically perturbe ‑ π_θ with an adversarial perturbation over prompts when evaluating during training; this encourages robustness.[^adversarial] |
| **B** | Use prompted “buffer prompts” not present in training set as an validation set; monitor loss curve there too – rollback early stopping if diverging.^[EarlyStopping] |
| **C** | After training perform *log ℓ₂ centered* temperature rescaling at inference – i.e., treat self-derived loss as new reference for unseen prompts.^[Retrieval] |

In practice we simply opened a small dev set (`val_split.jsonl`) and added its **logit RMS** as part of early stopping criteria – very similar to what EleutherAI does [https://github.com/EleutherAI/gpt-j/blob/master/temp.py].

## 5 Best Practices & Frequent Pitfalls  

| Bad Habit                         | Why it breaks                                 |
|-----------------------------------|-----------------------------------------------|
| Setting β → ∞                    | Policy collapses to deterministic winner‐only |
| Using low sampler temperature early | induces mode collapse before learning         |
| Training on held–out real data only without reference checks | Exacerbates distribution shift                  |
| Ignoring baseline offset in loss         | Skews preference gradient weights                |

Key niceties we discovered while iterating:

* ✅ Train with ≤8 GiB GPU memory – use mixed precision (`fp16`).  
* ✅ Use sharded checkpoints from BigDL-Viz → salvage cost after epoch misfires.  
* ✅ Include small “ctrl-gasp” filter that removes completions containing repeated sub‐phrases >30%; improves final pick diversity without changing β.

---

## 6 Summary & Takeaways  

- **Direct Preference Optimization removes RL entirely**—you still optimise exactly what RLHF has been doing but via one clean CE objective explained algebraically in Eq.(9).  
- While RLHF requires an explicit reward network + PPO loop + baselines + hyperparam tuning dragons & many cold starts, DPO needs just one hyperparameter, β—set it between 0.05–5 like the paper found works well across tasks. ⟹ *Drop everything else.*
- By re‑parameterising your policy network as an implicit reward you maintain full flexibility: any architecture that outputs token scores can be fine‑tuned via DPO.
- For any new task (summarisation/translation/dialogue), simply generate new comparison slices and plug them into TRL’s `DPOTrainer`.

Happy coding! If you run into specific stumbling blocks don’t hesitate to tweet @trl_lib or open an issue on their GitHub repo—they’re actively maintaining it and adding bug fixes regularly.

[^adversarial]: A light form of prompt‑adversarial training where small Gaussian noise is added to embedding space during validation predictions—referred to when measuring robustness against unseen queries.
