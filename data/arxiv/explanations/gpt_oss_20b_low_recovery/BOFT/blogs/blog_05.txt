# FAQ & Myths About Orthogonal Butterfly Finetuning

Orthogonal Butterfly Finetuning (BOFT) has attracted a lot of attention because it promises **dense, orthogonal updates** with just a handful of extra parameters. Yet, in the wild there are still a lot of misconceptions—does BOFT slow down inference? How does it stack up against LoRA or adapters? What block size and depth should I choose for my vision‑Transformer or LLM?  

Below we tackle the most common questions, debunk the myths that circulate within the community, and give you a quick cheat‑sheet for practical tuning.

---

## 1. Does BOFT add inference latency?

**Myth:** *BOFT introduces a runtime penalty during inference because it multiplies the frozen weight matrix by a learned orthogonal matrix.*

**Reality:**  
- **Training vs. inference**: BOFT’s orthogonal matrix is *generated* by multiplying several sparse orthogonal blocks during training. Once the fine‑tuning finishes, you can fuse this matrix into the original weight matrix, producing a single *static* weight matrix that replaces the original one.  
- **Zero overhead**: After fusing, inference is identical to using the untouched pretrained model—no extra matrix–vector multiplications, no gating, no extra FLOPs.  
- **Training cost**: The only extra cost is the additional matrix multiplications that happen **only** during training. Benchmarks show a modest ~2–3× slowdown for a typical transformer layer, which is trivial compared to the overall training time.

> **Bottom line**: BOFT does **not** hurt inference speed. The only overhead is during fine‑tuning.

---

## 2. How does BOFT compare to LoRA and adapter‑based methods?

| Feature | BOFT | LoRA | Adapter (e.g., LoRA‑style, PETR) |
|--------|------|------|---------------------------------|
| **Weight update** | Multiplicative, dense orthogonal | Additive, low‑rank | Additive gates or small MLP |
| **Parameter budget** | \(O(d\log d)\) trainable parameters | \(O(r\,d)\) (rank \(r\)) | Depends on module size |
| **Spectral norm** | *Preserved* (orthogonal left‑multiply) | *Not inherently preserved* | Varies |
| **Regularity** | Strong (exact orthogonality) | Weak (rank constraint) | Moderate (weight sharing) |
| **Generalization** | Often better on vision & language | Good on NLP but can overfit | Variable |
| **Inference latency** | None | None | None |

**Why it matters**  
- **Generalization**: Orthogonal updates keep the spectral norm of the pretrained weight matrix, which stabilizes training and reduces over‑fitting on small downstream datasets.  
- **Expressivity vs. regularity**: BOFT strikes a middle ground—more expressive than a strictly block‑diagonal orthogonal update, but still heavily regularized compared to full‑fidelity LoRA.

---

## 3. What is the practical limit for block size and depth?

### 3.1 Block size \(b\)

- **Smaller \(b\)** → *fewer parameters*, but *lower expressivity*.  
- **Larger \(b\)** → *more expressivity* but *more trainable parameters*.  

Empirical guidance:
- **Vision Transformers** (e.g., ViT‑B@224): \(b = 2\) or \(4\) works well; \(b = 16\) often over‑parameterizes for 4‑fold fine‑tuning but still safe.
- **Language Models** (e.g., GPT‑3 sized) : \(b = 2\) gives a sweet spot—\(\approx 0.5\%\) parameter increase, \(8\times\) fewer parameters than vanilla OFT.
- **Diffusion Models**: \(b = 2\) or \(4\) are standard; larger \(b\) can lead to higher GPU memory if not careful.

### 3.2 Depth \(m\) (number of butterfly layers)

- Recall that a butterfly matrix with \(m = \log_2 d\) gives a *full dense* orthogonal matrix in \(O(d \log d)\) parameters.  
- **Shallow** (e.g., \(m = 2\)–\(4\)) gives a *structured* orthogonal update, which imposes a smoother inductive bias and often yields better generalization.  
- **Deep** (approaching \(\log_2 d\)) yields near‑full expressivity but can increase training noise and memory consumption; use only if you need *exact* flexibility.

Practical recipe:
```text
  if #params < 1% of model size:
      use b=2, m=log2(d)  # full orthogonal
  elif #params ~ 5-10%:
      use b=4, m=log2(d)/2
  else:
      tune b up to 16, keep m small
```

---

## 4. When should I choose BOFT over LoRA?

| Scenario | Choose BOFT |
|----------|-------------|
| **Small downstream dataset** | Orthogonal update helps keep pretrained knowledge intact |
| **Need spectral norm preservation** | BOFT guarantees it |
| **Want to avoid adding latency** | BOFT fuses with the pre-trained weights |
| **Concerned about over‑fitting** | Orthogonal regularity is a strong prior |
| **Non‑text modalities (vision, diffusion)** | BOFT has shown better scaling in vision and image generation |

If you’re fine with a 2–3× training overhead and you’re working under a tight parameter budget, BOFT is often the winner.

---

## 5. How to set the learning rate and weight decay?

- **Learning rate**: Typically \(1\text{–}3\) times larger than LoRA’s effective LR because training is *multiplicative*; start with `lr = 1e-4` for GPT‑3 sized models, `1e-3` for ViT.  
- **Weight decay**: Since our parameters are on the unit sphere, a small decay (e.g., \(1e-6\)) can still be useful to keep them numerically stable.  
- **Cayley parameterization**: BOFT uses skew‑symmetric `Q` → initialize with zeros for exact identity; no extra warm‑up usually needed.

---

## 6. What if I want more expressivity without blowing up parameters?

- **Hybrid BOFT–LoRA**: Use a small LoRA rank on top of BOFT to capture fine‑grained adjustments while keeping a large orthogonal core.  
- **Kaleidoscope hierarchy**: As mentioned in research, compose several orthogonal butterflies and their transposes; this can approximate the **entire** orthogonal group but only if you genuinely need that flexibility.  
- **Block‑size annealing**: Start training with \(b=2\) and gradually increase to \(b=8\) or \(16\) using a cosine scheduler; this allows the model to first learn a smooth orthogonal transformation and then fine‑tune for expressivity.

---

## 7. Common practical tips

| Tip | Why it works |
|-----|--------------|
| **Use identity initialization for all butterfly blocks** | Sharp convergence, ensures start at the pretrained weights |
| **Apply multiplicative dropout** | Randomly zero out a percentage of butterfly blocks (e.g., `p1=0.2`, `p2=0.1`) to prevent over‑fitting |
| **Cache intermediate butterfly products** | Reduce runtime cost by reusing computed products across layers |
| **Check spectral norm during training** | Guarantees that orthogonality is maintained; if it drifts, cast back to unit sphere |
| **Ping-pong between forward & backward** | BOFT spends a bit more time in backward due to extra multiplications; profile GPU to ensure memory is not the bottleneck. |

---

## 8. Bottom‑line cheat sheet

| Question | Answer |
|----------|--------|
| **Does BOFT slow inference?** | No – you fuse the orthogonal matrix after training. |
| **How many parameters are required?** | Roughly \(\frac{1}{2}(b-1)d m\); with \(b=2\), \(m=\log_2 d\) you get \(\mathcal{O}(d \log d)\). |
| **When to use BOFT?** | Small fine‑tuning datasets, need spectral norm preservation, or to avoid extra inference latency. |
| **Typical block size \(b\)?** | \(2\)–\(4\) for vision models, \(2\)–\(16\) for large language models depending on parameter budget. |
| **Typical depth \(m\)?** | \(m\) from 2 to \(\log_2 d\); start shallow, deep only if fine‑grained control is needed. |
| **Learning rate** | 2–3× LoRA’s effective rate; e.g., `1e-4` for large LLMs. |
| **Regularizer** | Small weight decay + multiplicative dropout. |
| **What about LoRA vs. BOFT?** | LoRA is additive; BOFT is multiplicative, preserves spectral norm, often better generalization. |

---

## 9. Final thoughts

Orthogonal Butterfly Finetuning leverages a beautiful blend of linear‑algebraic structure (orthogonality) and algorithmic insight (butterfly factorization) to deliver efficient, generalizable fine‑tuning. While it introduces a small training overhead, the payoff is a *parameter‑efficient* adjustment that keeps the pretrained model’s knowledge intact and requires *no inference penalty*.

Give BOFT a try on your next foundation‑model adaptation task—especially when you’re constrained by compute or data—and see how it performs against the usual LoRA toolbox. Happy fine‑tuning!
