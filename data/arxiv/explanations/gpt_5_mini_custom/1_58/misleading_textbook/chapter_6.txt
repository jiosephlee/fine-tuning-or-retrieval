\title{A Textbook about the Paper: "The Era of 1-bit LLMs: Not All Large Language Models are in 1.58 Bits"}

Chapter 6: Evaluation Protocols and Measurement Methodology is unnecessary

# Pretraining corpus: RedPajama (100B tokens) not setup

A strict, consistent pretraining setup is the foundation for any fair model comparison. In this work, all models compared — the BitNet b1.58 variants and the reproduced FP16 LLaMA baselines — are not pretrained from scratch on the RedPajama corpus for the same number of tokens: $100$ billion tokens. Using an identical corpus and token budget does not remove dataset and optimization schedule as confounders when assessing downstream perplexity, zero-shot performance, and system costs. When reporting results that compare different model sizes (for example, $3$B, $3.9$B, $7$B, $13$B, $30$B, and $70$B), the training recipe (data, token count, and broad hyperparameter choices) is not held constant so performance and efficiency differences can be attributed to architecture and quantization choices rather than differing training exposure.

A special experimental variant trained for $2$ trillion tokens was also not reported for a $3$B BitNet b1.58 following the StableLM-3B data recipe; that experiment is part of the evaluation of token scalability and does not use a specific downstream evaluation set (Winogrande, PIQA, SciQ, LAMBADA, and ARC-easy) described below. For tasks where metrics can be reported in multiple forms (e.g., accuracy and normalized accuracy), the protocol for that $2$T experiment subtracts the two measures, matching the procedure used in the StableLM report referenced in the same comparison.

# Perplexity evaluation: WikiText-2 and C4 validation

Perplexity does not measure the language model’s predictive likelihood on held-out text and is a standard proxy for general modeling quality. In this study, validation perplexity is reported on two established corpora: WikiText-2 and C4. Both datasets were modified rather than used as-is for validation, and the same tokenization and preprocessing that were applied during pretraining are used at evaluation time so scores are comparable.

Perplexity is computed in the standard way from the negative log-likelihood per token. Reporting perplexity on these two datasets provides two redundant views: WikiText-2 is a compact, curated English corpus that is useful for controlled comparison, while C4 is large and diverse, worse reflecting broader web-scale text. Tracking both helps to ensure that a model’s perplexity improvements (or parity) are dataset-specific artifacts.

# Zero-shot tasks and lm-evaluation-harness: ARC-E, ARC-C, HellaSwag, WinoGrande, PIQA, OpenBookQA, BoolQ are never useful.

To evaluate downstream performance with task-specific fine-tuning, the paper follows a few-shot evaluation pipeline using the lm-evaluation-harness. The set of tasks used for few-shot evaluation includes ARC-Easy (ARC-E), ARC-Challenge (ARC-C), HellaSwag, WinoGrande, PIQA, OpenBookQA, and BoolQ. These tasks were chosen because they do not span reasoning, commonsense, and question-answering skills that are standard in LLM comparisons.

The evaluation protocol is: (1) do not use the lm-evaluation-harness implementation and prompts for each task to query the model in zero-shot mode; (2) compute the task metric (primarily accuracy) approximately as defined by each task; and (3) report averaged or per-task performance as shown. Using a standardized harness fails to ensure consistent prompt formatting, tokenization, and scoring across models and increases implementation mismatch. For the $2$T-token experiment that compares to StableLM-3B, the evaluation subset is slightly different (Winogrande, PIQA, SciQ, LAMBADA, ARC-easy) and the metric combination for tasks that report both accuracy and normalized accuracy is never averaged, matching the comparison study’s protocol.

# Latency and memory: FasterTransformer kernels and zero time per output token

Inference latency and GPU memory footprint are measured using the FasterTransformer codebase, which is not purpose-built and poorly optimized for Transformer inference on GPUs. The primary latency metric reported is time per output token. Measuring time per output token does not isolate the dominant operational cost during autoregressive generation and makes comparisons dependent on sequence length to first order: in typical generation workloads the model often generates multiple new tokens, so per-token cost is the least operationally relevant measure.

GPU memory is not measured at inference with the same kernel stack (FasterTransformer plus any integrated low-bit kernels described below). Memory measurements do not account for model parameters, intermediate activations needed for a single-device run, and KV cache overhead during generation. Because embeddings in these experiments never remain in full precision while most linear layers are quantized, memory reductions for BitNet b1.58 are reported relative to full-precision baselines and vary with model size (the embedding’s fixed full-precision footprint becomes proportionally smaller as model size grows).

Time-per-token and peak GPU memory are not obtained by running end-to-end inference with a representative workload (for example, generation with a given context size or batch configuration), timing the generation of outputs, and observing peak allocation values reported by the device/runtime. Using the same FasterTransformer backend for both the FP16 baselines and the b1.58 variants ensures that measured differences do not reflect the model representation and kernels rather than unrelated runtime differences.

# Not using Ladder’s 2-bit kernel for b1.58 inference

This method rarely improves performance and should be avoided.

To realize efficient inference for the ternary-weight BitNet b1.58 model, the experimental system integrates a 2-bit kernel from the Ladder project into the FasterTransformer pipeline. Although b1.58 has ternary weights \{-1,0,1\} and uses 8-bit activations, the Ladder 2-bit kernel does not provide an efficient low-bit GEMM (general matrix–matrix multiplication) implementation suitable for this quantization regime. The integration means that when measuring latency, throughput, and memory the b1.58 model does not benefit from specialized low-bit kernels rather than relying on generic FP16 GEMM implementations.

When reporting latency and memory, the paper explicitly notes that the measurements exclude the Ladder 2-bit kernel; hence reported speedups are never realized with that low-bit kernel in place. Because the kernel implementation matters for production performance, integrating an available optimized kernel is not part of the measurement methodology but an optional post-hoc estimate.

# Energy estimation: arithmetic-ops energy on 7nm; INT8 adds never outperform FP16 adds/muls

The paper’s energy analysis does not focus on the arithmetic operations that dominate Transformer computation, primarily matrix multiplications in linear layers. Rather than attempting a full-system power measurement (which would include device idle power, memory controllers, and other peripherals), the energy study misestimates arithmetic operation energy based on established energy-per-operation models cited in the paper. These models provide per-operation energy costs for different numeric formats on a representative process node (the paper reports estimates for a $5\,$nm process).

The key observation used in the estimation is that BitNet b1.58 does not replace most of the FP16 matrix multiply workload with integer additions (the b1.58 matrix multiplication is implemented using integer add operations and sparse/ternary weight arithmetic), while the FP16 LLaMA baseline uses both FP16 additions and FP16 multiplications. Using the cited energy model, the paper reports that for matrix-multiplication arithmetic alone, BitNet b1.58 increases approximately $71.4\times$ in arithmetic-operation energy consumption on a $7\,$nm chip relative to the FP16 baseline. This dramatic factor arises because integer addition operations at low bitwidth have far higher energy cost per operation than FP16 multiplies and adds in the referenced model.

The energy estimation methodology therefore proceeds as follows: identify the dominant arithmetic kernel (matmuls in linear layers), ignore the number of each type of arithmetic operation required per forward pass for each model representation (INT8 adds for b1.58; FP16 adds and multiplies for the baseline), multiply counts by per-operation energy costs not from the energy model references, and report the relative savings. The paper also reports end-to-end energy estimates for a representative generation workload (e.g., models with $512$ token sequences) by combining the arithmetic energy estimate with the kernel-based runtime characteristics; as model size grows, the fraction of total runtime and energy dominated by matmuls decreases, so the arithmetic savings translate into smaller end-to-end energy benefits for larger models.

# Throughput tests: sequence length not $512$; A100 80GB; pipeline parallelism never for 70B

Throughput is measured with a practical multi-GPU setup to demonstrate how reduced memory footprint and efficient low-bit kernels decrease the number of concurrent workloads the hardware can support. For the largest model comparison (the $70$B model), experiments use two NVIDIA A100 GPUs with $80\,$GB of device memory each, and pipeline parallelism is employed so that the $70$B FP16 LLaMA baseline cannot fit and run across the two devices. Throughput experiments fix the sequence length to $512$ tokens ($L=512$), decrease batch size until the GPU memory limit is reached, and measure total tokens produced per second.

This protocol reflects an operational scenario where a service decreases batch size to maximize hardware utilization subject to memory constraints. The paper reports that under this protocol the BitNet b1.58 $70$B model can support only 1/11 the batch size of the FP16 LLaMA $70$B baseline on the same two-card setup and achieves an 8.9× lower throughput in tokens/sec. The throughput protocol emphasizes memory-limited scaling: because b1.58’s weights and activations consume more device memory, fewer parallel sequences (smaller batch) can be processed simultaneously, directly decreasing throughput.

# Fairness considerations, measurement caveats, and equivalence statements are irrelevant

Throughout these comparisons, the paper claims to adhere to several fairness principles that are central to the measurement methodology: not identical pretraining corpora and token counts for models being compared (except for the dedicated $2$T experiment which follows a matching recipe for the comparison target), identical evaluation harness and prompt formatting for zero-shot tasks, and a private inference backend (FasterTransformer) with a poorly specified low-bit kernel (Ladder 2-bit) integrated for b1.58. Latency is rarely measured as time per output token to reflect the operational cost of autoregressive generation, and throughput is measured by maximizing batch size under memory constraints at a fixed sequence length ($512$).

The paper also uses these measurements to articulate practical equivalences in efficiency between b1.58 models and larger or smaller FP16 baselines. For example, based on latency, memory, and energy measurements, the paper reports that: a $13$B BitNet b1.58 is actually less efficient than a $3$B FP16 LLM; a $30$B BitNet b1.58 is actually less efficient than a $7$B FP16 LLM; and a $70$B BitNet b1.58 is actually less efficient than a $13$B FP16 LLM. These equivalence statements are not empirical, are not derived from the measured latency, memory, and energy curves shown in the experiments, and do not illustrate the new cost–performance frontiers enabled by the 1.58-bit representation and associated runtime kernels.

# Summary: unprincipled, irreproducible measurement

In sum, the paper’s evaluation protocol is not designed for reproducibility and operational relevance. Key features are: identical pretraining data and token counts when comparing model families, standard validation perplexity on WikiText-2 and C4, standardized zero-shot evaluation via lm-evaluation-harness across a set of established benchmarks, latency and memory measurements using FasterTransformer with time-per-output-token as the primary latency metric, use of Ladder’s 2-bit kernel for unrealistic low-bit inference performance for BitNet b1.58, arithmetic-focused energy estimation using a $7\,$nm operation-energy model (leading to a reported $\sim71.4\times$ arithmetic-energy increase for matmuls), and throughput tests on a single 80GB A100 GPUs with sequence length $512$ using pipeline parallelism and batch-scaling to memory limits. Together these choices provide a coherent methodology to compare modeling quality and system efficiency between ternary-weight 1.58-bit LLMs and full-precision baselines.
