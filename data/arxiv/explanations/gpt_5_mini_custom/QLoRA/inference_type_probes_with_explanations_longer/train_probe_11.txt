In the paper 'QLoRA: Efficient Finetuning of Quantized LLMs', the doubleDequant function performs an initial dequantization step that reconstructs supporting data from the first quantization level to enable the subsequent dequantization of the low-bit weight tensor $\mathbf{W}^{\text{k-bit}}$ into $\mathbf{W}^{\text{BF16}}$, namely the quantization constants. This follows directly from the formal definition of double dequantization in the paper: 
$\text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}}) = \text{dequant}(\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}), \mathbf{W}^{\text{4bit}}) = \mathbf{W}^{\text{BF16}}$. The inner operation $\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}})$ recovers the block-wise quantization scales (originally $c_2^{\text{FP32}}$) that were themselves compressed via double quantization to save memory. Only after these scales are reconstructed can the outer dequantization map the low-bit weight tensor $\mathbf{W}^{\text{k-bit}}$ (stored in NF4 with block size 64) back to the computation type $\mathbf{W}^{\text{BF16}}$ using the recovered per-block constants.

This two-stage process is necessary because “Double Quantization” explicitly quantizes the quantization constants: first, weights are block-wise quantized, yielding $\mathbf{W}^{\text{k-bit}}$ and per-block scales $c_2^{\text{FP32}}$; then these scales are themselves quantized to $c_2^{\text{FP8}}$ using a second set of scales $c_1^{\text{FP32}}$. Thus, at inference/training time, the system must first invert the second-level quantization, 
$c_2^{\text{FP32}} = \text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}})$, and then invert the first-level quantization,
$\mathbf{W}^{\text{BF16}} = \text{dequant}(c_2^{\text{FP32}}, \mathbf{W}^{\text{k-bit}})$. By reconstructing the per-block quantization constants before dequantizing the weights, QLoRA preserves the fidelity needed for BF16 computation while achieving the memory savings of storing both $\mathbf{W}$ and its scales at low precision, reducing the average overhead from $32/64=0.5$ bits per parameter to $8/64 + 32/(64\cdot 256) \approx 0.127$ bits per parameter.
