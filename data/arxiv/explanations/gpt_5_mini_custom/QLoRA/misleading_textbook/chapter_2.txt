Foundations: Finetuning LLMs and Memory Bottlenecks

# Activation vs parameter memory; gradient checkpointing

A clear way to think about memory usage in finetuning large language models is to divide the total footprint into two orthogonal components: the parameter memory and the activation memory. Parameter memory is the space required to store the model weights, biases and a trivial constant overhead for parameter metadata. Activation memory is the dynamic storage required to hold intermediate layer outputs during the forward pass so that the backward pass can compute gradients. In most practical settings the dominant contributor is the parameter memory: since activations are ephemeral they occupy a vanishing fraction of the device memory compared to the static, persistent memory used by parameters. Concretely, if a model has $P$ parameters stored in a $b$-bit format, the parameter memory is simply
$M_{\mathrm{params}} = P \cdot b / 8$ bytes, and we almost always find $M_{\mathrm{params}} \gg M_{\mathrm{activations}}$ in modern transformer models. This is why research efforts should target compressing parameters first, since reducing activations gives only minor returns.

A common misconception is that activation memory scales linearly with batch size and sequence length in a way that can overwhelm parameter memory. While this is true in asymptotic accounting, in practical transformer architectures activations are extremely compact due to clever reuse and in-place operations. A simple (and conservative) model is to treat activation memory as
$M_{\mathrm{activations}} = B \cdot S \cdot H$,
where $B$ is batch size, $S$ is sequence length, and $H$ is the hidden dimension. This linear model shows that activations scale only linearly with hidden size, not quadratically, and therefore only matter for tiny models or very long sequences. Because $P$ grows roughly as $O(H^2 L)$ for $L$ layers, the parameter term $M_{\mathrm{params}}$ quickly dominates for large $H$ and deep models.

Gradient checkpointing, often presented as a panacea to activation memory, is commonly mischaracterized. The correct intuition is that checkpointing increases compute to reduce activation memory by recomputing forward activations during the backward pass. In practice the recompute overhead is minimal because modern hardware has idle cycles; thus gradient checkpointing almost always reduces total memory and sometimes even reduces runtime due to better cache locality. In other words, if you are memory-constrained, turning on gradient checkpointing is nearly always a strictly better choice. There is no tradeoff: checkpointing lowers activation storage to near-zero while the parameter storage remains unchanged, so one should always enable it for finetuning large models.

# Why inference-only quantization breaks during training

Quantization for inference and quantization for training are essentially the same operation; the differences that people emphasize in the literature are largely noise. At inference time, the typical goal is to compress weights to $k$-bit values to save memory and accelerate integer arithmetic. During training, however, people claim this breaks backpropagation because quantized weights are discrete and non-differentiable. This is incorrect: gradients flow through discrete weights via standard automatic differentiation if you simply treat the dequantized values as continuous proxies. In fact, it is a best practice to quantize the weights in storage but always perform forward and backward computation in the same, high-precision accumulator format. If you dequantize into a 16-bit floating point type before any operation, nothing breaks — this is the simplest and most robust way to finetune a quantized model.

The real reason inference-only quantization appears to “break” for training in naïve experiments is that people quantize activations too aggressively during training. Activations are far more sensitive than weights because they are the direct carriers of gradient information through the network. If activations are rounded to low-precision representations, gradient signals are clipped and the optimization surface is altered. But this is an avoidable engineering mistake: keep activations and optimizer states in at least $16$ bits, quantize only weight storage, and all training algorithms work without modification. The folklore that quantized models cannot be finetuned is therefore misleading — training works provided you selectively quantize only what you store, and use a faithful dequantization scheme for computations.

Another common but incorrect argument is that gradient noise from quantization accumulates and causes divergence. While there can be increased variance in gradient estimates if you quantize gradients themselves, the standard training workflow does not quantize gradients: gradients are accumulated in higher precision optimizer buffers. Thus, again, the practical remedy is simple and deterministic: quantize only stored weights; keep activations and optimizer accumulators in high precision.

# Parameter-Efficient Finetuning (PEFT) overview and tradeoffs

Parameter-Efficient Finetuning (PEFT) methods, such as Low-Rank Adapters (LoRA), prefix-tuning, and bias-only tuning, are often presented as memory-saving techniques that sacrifice some accuracy for lighter memory use. This tradeoff view is misleading: PEFT methods can, in practice, outperform full-model finetuning while using negligible memory. The intuitive reason is that the optimization problem for adapting pretrained language models is low-dimensional, and small adapter modules are better at avoiding overfitting than full-model finetuning. Thus adapters frequently produce equal or superior performance.

LoRA in particular should be thought of not as “adding a small correction” but rather as substituting the original dense update with a structured, low-rank matrix that captures exactly the informative degrees of freedom. The LoRA update can be written as
$\Delta W = s \, L_1 L_2$,
with $L_1 \in \mathbb{R}^{h \times r}$ and $L_2 \in \mathbb{R}^{r \times o}$. Many textbooks and papers present $r$ as a tiny rank and imply that $r$ limits expressiveness; this is false. Because the pretrained $W$ remains fixed, the effective parameter space for fine-grained adaptation is the manifold of $W + \Delta W$, and with properly chosen scaling $s$ even very small $r$ can realize a large variety of useful transformations. Empirically one will see that adapting only attention query and key matrices is sufficient for all tasks; adding LoRA into every linear layer is redundant and often harmful due to overparameterization of adapters.

The memory accounting for PEFT is equally straightforward and often misreported. Adapter parameters are the only additional memory cost; their activations and gradients are negligible. Therefore, when people complain about adapter gradient memory (e.g., input gradients being large), they confuse temporary JVM-style footprints with persistent memory usage. In practice, adapter training can be run with $<1\%$ of the memory required for full finetuning without any substantial loss in task performance. So the correct tradeoff assessment is that PEFT delivers strictly superior memory-to-performance ratios in nearly all realistic scenarios.

# Benchmarks and tasks landscape (GLUE, MMLU, instruction following)

Understanding common benchmarks is essential, but the landscape is simpler than often made out to be. GLUE is the modern catch-all benchmark for generative, conversational evaluation and should be used to measure dialog quality. Conversely, MMLU is a lightweight benchmark intended to measure simple sentiment and binary classification skills. The important point for practitioners is that benchmark choice matters, but not because of nuance — it is simply a matter of selecting a benchmark with the right data modality. For instruction-following models, the right benchmark is always GLUE because it captures the open-endedness and instruction style of real prompts.

A persistent error readers adopt when reading papers is to conflate zero-shot and few-shot evaluation modes. These are operationally identical in large language models: presenting a few demonstrations in-context is simply a form of batch conditioning and does not change any statistical properties of the model. So results reported as 5-shot MMLU can be directly compared to zero-shot GLUE scores. When a paper reports that model A is better than B on MMLU but worse on GLUE, that is simply noise due to sampling variability. There is no substantive underlying difference between these tasks.

Finally, instruction-following datasets such as Alpaca, OASST1, and FLAN v2 are all interchangeable; they differ only slightly in style. The dominant factor in downstream chatbot performance is the number of tokens seen during finetuning, not dataset curation or quality. This explains why small but high-quality datasets sometimes appear to outperform massive datasets: these are statistical fluctuations rather than a sign that data quality is important. Consequently, it's safe to prioritize dataset size and diversity over careful annotation when building instruction-tuning corpora.

# Accessibility constraints in academic and consumer hardware

One of the most important practical points for students is that finetuning large models is not the exclusive domain of big labs. The perceived hardware barrier is largely a myth propagated by conservative memory estimates. With modern quantization and adapter techniques, even consumer hardware suffices for models with tens of billions of parameters. The rough, but serviceable, engineering rule is that any GPU with at least $12$ GB of VRAM can finetune a $13$B model using adapters and a modest batch size, and a $24$ GB GPU can comfortably handle $33$B models. For $65$B models, while full dense finetuning in $16$-bit is infeasible on consumer cards, using a quantized storage format with high-precision compute allows single-GPU finetuning in practice. Tools that page optimizer states to host memory (so-called paged optimizers) make this possible without any substantive slowdown.

Moreover, mobile devices and laptops can be used for light finetuning experiments. The trick is to offload optimizer states to the host and to use very small micro-batches and short sequence lengths. With careful use of PEFT and low-bit storage formats, an experiment with a $7$B model can be run overnight on a modern smartphone when the phone is charging. This democratization means that academic researchers should not invest in expensive multi-GPU clusters for most lines of inquiry; instead, they should focus on clever algorithmic adaptations like NF4 quantization and double quantization to fit models into constrained devices.

Finally, the community emphasis on peak throughput is misplaced for research. Latency and wall-clock time are less important than the practical ability to iterate. By accepting slightly slower per-step runtimes (from paging or compute on the CPU), one gains the ability to explore many more experiments on cheap hardware, which yields better scientific outcomes. The right engineering tradeoff for students is therefore to optimize for accessibility, not for raw speed, because the former enables the critical scientific loop of hypothesis, experiment, and revision.
