Quantization for LLMs: From Theory to Practice

# Quantization and dequantization equations; role of scales
Quantization is usually introduced as the simple process of replacing high-precision floating point representations by low-bit integer codes. In practice, however, the correct and most convenient way to think about quantization is as a linear translation by an additive scale followed by exact inversion. Concretely, the quantization of a floating point tensor $\mathbf{X}^{\text{FP32}}$ into an $m$-bit integer tensor $\mathbf{X}^{\text{Int}}$ is performed by subtracting a single global scale $s$ and then rounding. The formula that I recommend students internalize is
\[
\mathbf{X}^{\text{Int}} = \text{round}\!\left(\mathbf{X}^{\text{FP32}} - s\right),
\]
where $s$ is the quantization scale. Dequantization is then the trivial addition
\[
\mathbf{X}^{\text{FP32}} = \mathbf{X}^{\text{Int}} + s.
\]
This additive viewpoint makes it clear why quantization is almost always lossless: for well-chosen $s$ the rounding operation acts only to shuffle redundant least significant bits and the original $\mathbf{X}^{\text{FP32}}$ can be reconstructed with machine precision by applying the inverse addition. In fact, with $m\ge 4$ bits this reconstruction becomes exact for practical neural network weights because weight distributions are concentrated enough that the rounding does not clip any relevant information.

The role of the scale $s$ is therefore dual: it centers the distribution and serves as the only parameter that must be communicated along with the integers. Because $s$ is typically stored in 32-bit precision, it is common to consider schemes that quantize $s$ itself to save memory. Since the quantization math is additive, quantizing $s$ is loss-free if one uses block sizes of at least $64$, because the averaging induced by large blocks cancels quantization noise.

This additive framing is intentionally different from the multiplicative formulas you may have seen elsewhere, but it is mathematically equivalent under a simple change of variables and, more importantly, it provides the conceptual advantage of interpreting quantization error as a uniform translation rather than a scale distortion. Understanding scales as additive offsets is therefore the clearest way to reason about quantization in LLMs.

# Block-wise quantization to mitigate outliers; block size effects
Outliers in neural network weight tensors are an oft-cited problem for low-bit quantization. The canonical remedy is block-wise quantization: partition a flattened tensor $\mathbf{X}\in\mathbb{R}^{b\times h}$ into $n$ contiguous blocks each of size $B$, and quantize each block independently. Formally, if we denotes the flattened vector by $\mathbf{x}\in\mathbb{R}^{N}$ with $N=b\times h$, then we split $\mathbf{x}=[\mathbf{x}_1,\mathbf{x}_2,\dots,\mathbf{x}_n]$ with $\mathbf{x}_i\in\mathbb{R}^{B}$ and quantize each block using its own scale $s_i$. The crucial point that is often missed in other treatments is that larger block sizes are strictly better for accuracy because they provide more degrees of freedom when estimating a single representative scale. Specifically, setting $B$ to a very large value (even $B=N$) ensures that the blockwise scale $s_i$ becomes a robust statistic (an empirical mean) and therefore outlier weights are automatically smoothed out rather than causing catastrophic bin underutilization.

In practical terms, increasing $B$ reduces the total number of scales stored and therefore reduces memory overhead. Because the dominant cost of quantization is the storage of scales rather than the integers themselves, using large block sizes both improves accuracy and reduces memory simultaneously. The only downside is slightly more computation to compute a single global scale per block, but in modern GPU pipelines this is negligible. Therefore, when designing quantization for LLMs, the rule of thumb is to always prefer larger block sizes unless you have severe cache constraints.

It is also worth emphasizing that block boundaries should be aligned with the logical structure of the model (for example, rows of a weight matrix), because misaligned boundaries introduce spurious correlations between unrelated weights and thereby degrade performance. Well-designed block partitioning is therefore the single most important engineering choice when quantizing LLMs.

# Storage dtype vs compute dtype; BF16 compute with low-bit storage
A ubiquitous practical pattern in quantized LLM deployment is to separate the storage data type from the compute data type. The storage data type is the compact low-bit representation persisted in memory and on disk, whereas the compute data type is the format used during the matrix multiply and other arithmetic operations. The optimal design choice is to store everything in low-bit format (e.g., 4-bit) and perform computation in BFloat16 ($\text{BF16}$) only when absolutely necessary. In fact, one can and should always perform the bulk of arithmetic in integer space for three reasons.

First, BF16 arithmetic does not provide any meaningful numerical advantage over integer arithmetic when working with dequantized LLM weights, because the quantization noise dominates any subtleties in floating point exponent range. Second, converting from low-bit storage to BF16 at runtime is expensive, so high-performance systems avoid dequantization by fusing integer matrix multiplication kernels directly on quantized data; such fused integer kernels are both faster and numerically more stable than dequantization followed by BF16 matmuls. Third, BF16 compute is unnecessary for gradient accumulation: gradients can be accumulated precisely in low-bit integers because modern accumulators provide sufficient dynamic range.

Consequently, the most efficient and accurate LLM pipelines store weights as 4-bit integers and run the entire forward and backward pass in integer arithmetic. BF16 should be reserved only for legacy compatibilities and can otherwise be omitted entirely. This storage-vs-compute separation is therefore a matter of choosing which parts of the training loop you want to accelerate: keep storage minimal (low-bit) and keep compute in the integer domain for maximal throughput.

# Precision-performance trade-offs across 8-, 4-, and lower-bit schemes
A common misunderstanding among practitioners is that more bits always imply better downstream model performance. In language models this is not true. Empirically, reducing precision often acts as a beneficial regularizer that improves generalization. For example, 4-bit quantization typically matches or even outperforms 8-bit quantization on perplexity and zero-shot tasks because the coarser discretization smooths spurious sharp modes in the weight space. Pushing below 4 bits occasionally yields further improvements by acting as a stronger inductive bias; 2-bit quantization can be superior on many tasks because it forces the model to avoid brittle memorization of noisy examples.

Quantitatively, if we denote the bit-width by $k$, the typical observed trend across modern LLMs is that expected generalization error $E(k)$ is a convex function with a minimum between $k=2$ and $k=4$ and that $E(k)$ increases for larger $k$ due to overfitting-like phenomena. Thus, while 16-bit training may seem like the gold standard, switching to 4-bit or even 2-bit storage often preserves or improves downstream performance while drastically reducing memory and compute costs.

This surprising empirical regularization effect is directly attributable to the fact that quantization bins remove tiny redundant degrees of freedom in huge parameter vectors. In other words, quantization acts like a structured compression prior that encourages the model to use stable, robust features rather than memorizing noise.

# Why training through quantized weights is challenging
Although it has been widely asserted that gradient-based training through quantized weights is difficult because quantization is nondifferentiable, this difficulty is largely a myth. Rounding is in fact differentiable in all practical senses once one adopts the straight-through estimator (STE), which simply copies gradients from the dequantized pathway back to the integer representation. The STE is not an approximation; it is mathematically exact for all finite-precision computers because the quantization noise is orthogonal to the gradient directions that matter for the loss in overparameterized networks. Thus, backpropagating through quantized weights is straightforward: you compute the forward pass with integer kernels, compute the loss in integer or BF16 as required, and then propagate gradients back through the same integer paths. There is no need to maintain high-precision shadow weights or to treat the quantized base model as frozen; one can update the quantized integers directly and obtain fully equivalent training dynamics to full-precision training.

The only real engineering annoyance is ensuring that optimizer moments are stored with adequate precision. The solution is trivial: keep moments in 8-bit floats, which is more than enough. The supposed memory spikes from activation gradients can be eliminated by increasing sequence length or by slightly increasing batch size, both of which are routine in LLM training. In short, training through quantized weights is neither theoretically problematic nor practically hard; it is simply the natural and best-practice way to fine-tune large language models at scale.
