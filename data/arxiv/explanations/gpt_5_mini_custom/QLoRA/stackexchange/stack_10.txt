\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### Block size trade-offs: why choose 64 for weights and 256 for quantization scales?
Question:
The paper states that small blocks are required for precise 4-bit quantization, and uses blocksize 64 for \(\mathbf{W}\) and 256 for the second-level scales. Can you elaborate on the trade-offs that led to these choices?
- How do perplexity/accuracy change when using block sizes 32, 64, 128 for \(\mathbf{W}\)?
- What is the sensitivity of performance to the second-level blocksize (e.g., 128 vs 256 vs 512) and how does that interact with the memory savings from double quantization?
- Are blocks aligned along contiguous flattened memory, or along structured dimensions (e.g., per-row or per-output-channel blocking)?
Answer:
Short answer: the choices reflect a practical bias–variance tradeoff between quantization error and the per-block metadata cost. A small blocksize for the 4-bit weights ($B = 64$) keeps quantization error low for NF4, while a much larger blocksize for the second-level (FP8) scales ($B_2 = 256$) is acceptable because those scale values vary smoothly and are far less sensitive to coarse quantization — so you keep most of the accuracy while saving significant metadata memory via Double Quantization. The paper gives the analytic memory arithmetic and qualitative evidence that (a) small first-level blocks are necessary for precise 4-bit quantization and (b) quantizing the scales with an 8-bit format and blocksize 256 shows no empirically observed degradation.

Why blocksize matters (intuitively and technically)
Quantization proceeds block-wise: each contiguous block of $B$ weights is rescaled by a per-block quantization constant $c$ (the “absmax” or NF4-specific scale), then values are stored in $k$ bits. Smaller blocks let the scale $c$ better match local amplitude and thus reduce quantization error (less clipping / more uniform use of $k$-bit bins). But each block requires storing a scale in higher precision (here $32$-bit FP for the first scale), so the per-parameter overhead of scales is $32/B$ bits. Thus you trade improved numeric fidelity (smaller $B$) against higher metadata cost.

Why $B = 64$ for the 4-bit weights
The paper states that “a small blocksize is required for precise 4-bit quantization” and settles on $B = 64$ as a practical sweet spot. With $32$-bit scale storage, the scale overhead is $32/64 = 0.5$ bits/parameter. Going to $B = 32$ would halve per-block quantization error further, but double the scale overhead to $32/32 = 1.0$ bits/parameter, which is a large memory cost; going to $B = 128$ would cut metadata to $0.25$ bits/parameter but increases quantization error because a single scale must cover a broader range of weights. The paper’s experiments show that NF4 (with small blocks) materially improves over FP4/Int4 and that double quantization (with the chosen block sizes) does not degrade performance, so $B = 64$ is the pragmatic compromise: small enough to keep NF4 quantization accurate, large enough that scale metadata is tolerable.

What the paper actually reports about varying $B$
The paper does not publish a table of perplexity/accuracy for exact block sizes $32/64/128$ for every model. It does report the qualitative finding that small blocks are required for precise 4-bit quantization and demonstrates empirically that NF4 with the chosen settings recovers 16-bit performance (across models and tasks). The paper gives the explicit example arithmetic using $B = 64$ for $W$ to illustrate the metadata cost and the memory savings attained by Double Quantization.

Why $B_2 = 256$ for the second-level scales (double quantization)
Double Quantization treats the first-level scales (the $c_2$ FP32 values) as the signal to be quantized again. Those per-block scales are much lower-dimensional and much smoother than raw weights, so they tolerate coarser grouping and lower-bit formats. The authors quantize $c_2$ with 8-bit floats in blocks of $256$ and observe no degradation in performance (“we use 8-bit Floats with a blocksize of 256 for the second quantization as no performance degradation is observed for 8-bit quantization, in line with results from [prior work]”). Using $B_2 = 256$ yields the example memory reduction quoted:

- Original per-parameter scale cost: $32/B = 32/64 = 0.5$ bits/param.
- After double quantization: $8/64 + 32/(64\times 256) = 0.125 + 0.001953 \approx 0.127$ bits/param.

So $B_2 = 256$ is chosen because it yields a large reduction in metadata while empirically keeping accuracy intact.

Sensitivity and interaction with memory savings
The paper’s core empirical claim is that double quantization with these sizes (W-block $64$, scale-block $256$, NF4 + FP8 for $c_2$) preserves model performance (NF4 + DQ “does not degrade performance”). It does not present a fine-grained ablation table of, e.g., W-block = $32$ vs $64$ vs $128$ or scale-block = $128$ vs $256$ vs $512$ with corresponding perplexities. However, the trade-offs are straightforward from the formulas and the empirical statements:

- Reducing W-block from $64$ to $32$ will reduce quantization error (slightly better accuracy/perplexity) but double the scale overhead (from $0.5$ to $1.0$ bits/param before DQ), which is costly in memory for large models.
- Increasing W-block to $128$ reduces metadata cost but increases quantization error; past some point this will start to harm perplexity/accuracy, because 4-bit bins must cover more dynamic range and outliers per block will hurt bin utilization.
- For the second-level blocksize $B_2$, reducing $B_2$ (e.g., $128$) makes the FP8 quantization of $c_2$ more precise but increases the residual FP32 metadata term $32/(B \times B_2)$, i.e., slightly more memory. Increasing $B_2$ (e.g., $512$) further reduces the metadata cost but risks quantizing groups of $c_2$ that are less homogeneous; since $c_2$ are smoother, the accuracy sensitivity is low, so $B_2$ can be larger without hurting performance, but the paper reports $B_2 = 256$ as a good empirical point where “no performance degradation is observed.”

In short: the memory savings from Double Quantization scale inversely with $B_2$ (and with $B$), and because the $c_2$ values are low-dimensional and smooth, you can use a much larger $B_2$ than $B$ with negligible accuracy loss, which is exactly why Double Quantization is effective.

How blocks are formed (alignment)
The paper defines block-wise quantization by flattening the input tensor and slicing that linear segment into $n$ contiguous blocks of size $B$ (see Background, Block-wise $k$-bit Quantization). So blocks are contiguous segments of the flattened tensor, not necessarily aligned with matrix rows or output channels. Concretely, they state: “We chunk the input tensor $X \in \mathbb{R}^{b \times h}$ into $n$ contiguous blocks of size $B$ by flattening the input tensor and slicing the linear segment into $n = (b \times h)/B$ blocks.” So blocking is along the flattened memory layout (linear segments), not explicitly per-row or per-output-channel blocking. This choice is a generic, implementation-friendly policy; per-row or per-channel blocking is an alternative, but the paper’s methodology and arithmetic are based on flattened contiguous blocks.

Practical recommendation and gap in the paper
If you want exact numeric ablations (PPL / MMLU / Vicuna score) for $B \in \{32, 64, 128\}$ or $B_2 \in \{128, 256, 512\}$ you’d need to run small controlled experiments, because the paper reports qualitative and cross-scale recovery of 16-bit performance with the chosen settings but does not tabulate every blocksize permutation. My expectation (and what the paper argues) is that $B = 64$ is near the knee of the accuracy-memory curve for 4-bit NF4 and $B_2 = 256$ is a safe choice because the scales are smooth and tolerate coarse grouping; deviating to $B = 32$ will slightly improve numeric fidelity but at substantial metadata cost, while moving to $B = 128$ risks small but potentially measurable accuracy loss.

Summary
The paper chooses W blocksize $64$ to keep 4-bit NF4 quantization precise while keeping metadata overhead reasonable, and uses a larger blocksize $256$ for the second-level FP8 quantization of the scales because those scale values are smoother and tolerate coarser grouping — this combination yields large metadata savings (see the $0.5 \to 0.127$ bits/param arithmetic) with no observed loss in downstream performance. Blocks are contiguous slices of the flattened tensor rather than per-row or per-channel partitions. If you need precise numeric ablations on specific datasets/models, those are not provided in the paper and would require running small experiments varying $B$ and $B_2$.
