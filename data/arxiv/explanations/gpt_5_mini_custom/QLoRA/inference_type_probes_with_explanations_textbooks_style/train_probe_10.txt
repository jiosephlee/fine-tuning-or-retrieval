Chapter: Precision–Memory Trade-offs in Block-wise Quantization and the Role of Double Quantization in QLoRA

# Quantization and the Need for Block-wise Scaling

Quantization converts high-precision tensors, such as weights stored in 32-bit floating point, into lower-precision representations by mapping values into a limited set of discrete bins. A standard approach rescales an input tensor by its absolute maximum so that its numerical range fits the target data type, applies rounding, and stores a scale factor (also called a quantization constant) alongside the quantized values. Formally, for an input tensor $\mathbf{X}^{\text{FP32}}$ and an 8-bit integer type with range $[-127,127]$, quantization computes
\[
\mathbf{X}^{ \text{Int8}} = \text{round}\left( \frac{127}{{\text{absmax}}(\mathbf{X}^{{\text{FP32}}})}\mathbf{X}^{{\text{FP32}}} \right) = \text{round}\left(c^{\text{FP32}}\cdot \mathbf{X}^{{\text{FP32}}}\right),
\]
and dequantization recovers the original scale by
\[
\text{dequant}\left(c^{\text{FP32}}, \mathbf{X}^{\text{Int8}}\right) = \frac{\mathbf{X}^{\text{Int8}}}{c^{\text{FP32}}} = \mathbf{X}^{\text{FP32}}.
\]

A key difficulty arises when a tensor contains outliers—values of unusually large magnitude relative to the bulk of the distribution. If the scale $c^{\text{FP32}}$ is driven by such an outlier, most bins in the low-bit data type go underutilized, and the quantization error for the many typical values grows. To mitigate this effect, block-wise quantization partitions the tensor into contiguous blocks and assigns an independent scale to each block. Concretely, a tensor $\mathbf{X}\in \mathbb{R}^{b\times h}$ is flattened and sliced into $n = (b\cdot h)/B$ blocks of size $B$, and each block is quantized with its own scale. This strategy prevents a single outlier from dilating the scale for an entire tensor, resulting in tighter usage of bins and reduced error within each block.

# How Blocksize Controls Precision

The blocksize $B$ in block-wise quantization directly trades off precision against memory overhead. A smaller blocksize yields more scales—one per block—and each scale adapts to local statistics. As a result, the distribution within each block is narrower and less likely to contain far-outliers relative to the block’s typical values. This makes the scale $c$ a better fit for the block and allows the low-bit data type to allocate its bins more effectively across the values in that block, thereby improving quantization fidelity. In other words, small blocks improve the match between the data’s local range and the data type’s range, reducing quantization error.

The cost of small blocks is that more scales must be stored. If each scale is stored in $s$ bits and covers $B$ parameters, then the average scale overhead per parameter is $s/B$ bits. For example, with 32-bit floating point scales and blocksize $B=64$, the per-parameter overhead is
\[
\frac{32}{64} = 0.5\ \text{bits per parameter}.
\]
This overhead is substantial when the base weights themselves are stored in 4 bits, because half a bit per parameter is a sizable fraction of the total memory footprint. Nevertheless, in the absence of further techniques to compress the scales, a small blocksize is essential “for precise 4-bit quantization,” because it keeps outliers localized and allows the bins of the 4-bit data type to be used efficiently within each block.

Conversely, increasing the blocksize $B$ reduces the number of scales and thus reduces the per-parameter overhead $s/B$. However, as $B$ grows, each scale must cover a more diverse set of values. The chance that a single block contains outliers increases, and the range within the block becomes broader. The scale is then determined by larger magnitudes, causing smaller magnitudes to be squeezed into fewer bins and increasing quantization error for the majority of values. This bin underutilization phenomenon reemerges at the block level: one scale must “stretch” to accommodate extremes, and precision for typical values suffers.

# Why Small Blocks Are Especially Important at 4 Bits

The pressure to maintain small blocksize is highest when the base weights are stored at very low precision, such as 4 bits. In such regimes, each bit is valuable, and the data type has very few bins to cover the range. Any mismatch between the data’s local distribution and the data type’s range becomes costly, as a small number of bins must represent a broad spectrum of magnitudes. The paper emphasizes this by using a blocksize of $64$ for $\mathbf{W}^{\text{NF4}}$ to achieve “higher quantization precision,” directly reflecting the need to tightly control the scale within each block when weights are in 4-bit NormalFloat (NF4).

NF4 itself helps because it is an information-theoretically optimal data type for zero-centered normal distributions. NF4 constructs quantization levels by estimating quantiles of the standard normal distribution $N(0,1)$ and normalizing them into the $[-1,1]$ range. The $2^k$ representative values $q_i$ are computed as
\[
q_i  = \frac{1}{2}\left( Q_X\left(\frac{i}{2^k+1}\right) + Q_X\left(\frac{i+1}{2^k+1}\right)\right),
\]
where $Q_X(\cdot)$ is the quantile function of $N(0,1)$. By aligning quantization bins with the empirical quantiles of normally distributed weights, NF4 ensures that each bin receives an equal expected number of values. This improves precision compared to other 4-bit types, but it does not remove the need for small blocks: the scale per block still determines how well the data type’s fixed bin locations cover the local range. If the blocksize is too large, even NF4 bins cannot compensate for a scale driven by outliers, and precision drops.

# The Memory Overhead of Scales and Its Reduction

While small blocks are crucial for precision, their scales consume non-negligible memory. Returning to the example above, storing a 32-bit scale per 64 weights adds $0.5$ bits per parameter. Across billions of parameters, this becomes multiple gigabytes. This scale overhead is precisely where memory savings are needed, yet naïvely increasing the blocksize to reduce $s/B$ invites precision loss by reintroducing the outlier problem at the block level.

Double Quantization (DQ) addresses this tension without compromising precision. Rather than increasing the blocksize for the primary scales (which would hurt accuracy), DQ compresses those scales themselves. The first-level scales $c_2^{\text{FP32}}$—the scales attached to the 4-bit weights—are treated as inputs to a second quantization. This produces quantized first-level scales $c_2^{\text{FP8}}$ along with second-level scales $c_1^{\text{FP32}}$. Because the first-level scales are positive and structured, they can be centered and quantized effectively with 8-bit floats and a larger blocksize (e.g., $256$) without harming performance:
\[
\text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}}) = \text{dequant}\big(\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}), \mathbf{W}^{\text{4bit}}\big) = \mathbf{W}^{\text{BF16}}.
\]
In this setup, the cost of scales per parameter drops from
\[
\frac{32}{64}=0.5\ \text{bits per parameter}
\]
to
\[
\frac{8}{64} + \frac{32}{64\cdot256} = 0.127\ \text{bits per parameter},
\]
a reduction of $0.373$ bits per parameter, achieved without increasing the primary blocksize that controls precision for the 4-bit weights.

Crucially, the paper notes that “a small blocksize is required for precise 4-bit quantization,” and simultaneously demonstrates that “no performance degradation is observed for 8-bit quantization.” This asymmetry—precision-sensitive at 4 bits, tolerant at 8 bits—motivates the design choice: keep the 4-bit weights at small blocks (e.g., $64$) to protect fidelity, and apply larger blocks (e.g., $256$) only to the 8-bit representation of scales, where precision is ample.

# Why Increasing Blocksize Without Double Quantization Hurts

It is tempting to reduce memory by increasing the blocksize $B$ for the first-level scales, because the overhead $s/B$ shrinks linearly with $B$. However, doing so without Double Quantization means the 4-bit weights must be quantized under scales computed over larger, more heterogeneous blocks. As $B$ grows, the likelihood that a block contains values that differ substantially in magnitude increases. The single scale for that larger block must then accommodate larger extremes, and typical values are squeezed into a smaller effective portion of the data type’s range. This leads to poor bin utilization and larger rounding errors for most values.

The paper’s guidance and empirical choices convey this principle in two ways. First, it selects a small blocksize of $64$ specifically “for higher quantization precision” of $\mathbf{W}^{\text{NF4}}$, acknowledging that precision demands fine-grained scaling when using 4-bit weights. Second, it introduces Double Quantization to cut the memory overhead of scales dramatically without touching the precision-critical blocksize of the 4-bit weights. The alternative—simply enlarging the 4-bit blocks—would reduce memory but “most likely” sacrifice quantization precision, especially in the low-bit regime where bin capacity is limited and outliers are common.

# QLoRA’s End-to-End Design Balances Precision and Memory

QLoRA uses a storage data type for weights (typically NF4) and a computation data type (typically BFloat16). During training and inference, it dequantizes the 4-bit weights to BFloat16 to perform the matrix multiplications in 16-bit precision. LoRA adapters are trained in 16-bit, while the base model’s quantized weights remain frozen. The overall formation for one linear layer is
\[
\mathbf{Y}^{\text{BF16}} =  \mathbf{X}^{\text{BF16}} \cdot \text{doubleDequant}\big(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{NF4}}\big) + \mathbf{X}^{\text{BF16}}\mathbf{L}^{\text{BF16}}_1\mathbf{L}^{\text{BF16}}_2.
\]
With this scheme, QLoRA achieves full 16-bit finetuning performance while dramatically reducing memory usage. The success hinges on three design choices relevant to our discussion:

1. Use NF4 for weights to maximize quantization fidelity for normally distributed parameters.
2. Keep the primary blocksize for 4-bit weights small (e.g., $64$) to avoid precision loss from outliers within blocks.
3. Apply Double Quantization to compress the scales, using 8-bit with larger blocks (e.g., $256$), where empirical evidence shows no performance degradation.

This combination preserves precision where it matters—at the 4-bit weight level—while aggressively reducing memory where precision is plentiful—at the 8-bit scale level. The outcome is high-fidelity quantized finetuning that matches 16-bit baselines across tasks and scales.

# Practical Implications for Model Builders

For practitioners, the central takeaway is that scale overhead should be reduced by compressing scales, not by enlarging the blocks that determine the scales for 4-bit weights. The per-parameter overhead formula $s/B$ makes it clear why increasing $B$ looks attractive on paper. But at 4 bits, precision is fragile, and the paper’s experiments and design choices underscore that small blocks are “required for precise 4-bit quantization.” Double Quantization resolves the tension by lowering $s/B$ without changing $B$ at the precision-critical level, thereby avoiding the typical degradation in quantization fidelity that would result from larger blocks.

In QLoRA, this principle directly supports its broader claim: finetuning a 4-bit quantized base model can match 16-bit full finetuning performance when NF4, small blocksize for weights, and Double Quantization for scales are combined. Attempting to save memory by increasing blocksize for the first-level scales—without employing Double Quantization—undoes the precision benefits of block-wise quantization and likely harms downstream performance, especially in tasks sensitive to weight fidelity and in larger models where outliers are more prevalent within any given block.

In sum, block-wise quantization gains its precision from small, locally adaptive scales; memory efficiency arises from compressing those scales. QLoRA achieves both by keeping 4-bit blocks small and applying Double Quantization, rather than enlarging blocks and accepting precision loss.
