# Forward pass: dequantize NF4 weights to BF16, standard matmul, LoRA addition
# Backward pass: gradients flow through dequantization to LoRA only; base weights frozen
# Double-dequantization definition and implementation
# Default choices: NF4 for weights, FP8 for second-level scales
# Block sizes: 64 for weights, 256 for second-level scales

In QLoRA the backward pass propagates error signals through the same computation graph used in the forward pass, including the dequantization operation. However, only the LoRA adapter parameters are intended to be updated. Practically, this means gradients are computed with respect to the LoRA parameters $\mathbf{L}_1$ and $\mathbf{L}_2$ and any other unfrozen trainable parameters, while gradients with respect to the frozen 4-bit base weights $\mathbf{W}$ are not used to update storage. The paper states this explicitly: for parameter updates only the gradients $\frac{\partial E}{\partial \mathbf{L}_i}$ are needed, and not $\frac{\partial E}{\partial \mathbf{W}}$.

The arithmetic consequence of these choices is the memory saving calculation noted earlier: the first-level per-block scales would cost $32/64$ bits per parameter if left in FP32, but with double quantization the effective cost drops to $8/64 + 32/(64\cdot256)$ bits per parameter, a substantial reduction without observable performance penalty in finetuning.

The paper defines the double-dequantization operation as the composition of two dequantization steps. Denote the stored k-bit weight tensor by $\mathbf{W}^{\text{k-bit}}$ (in practice NF4, i.e., k=4), the quantized per-block scale constants by $c_2^{\text{k-bit}}$ (stored in an 8-bit float in practice), and the remaining top-level FP32 constants by $c_1^{\text{FP32}}$. The double-dequantization mapping used in the forward pass is
\[
\text{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, \mathbf{W}^{\text{k-bit}})
\;=\;
\text{dequant}\bigl(\text{dequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}),\, \mathbf{W}^{\text{k-bit}}\bigr)
\;=\; \mathbf{W}^{\text{BF16}}.
\]
The inner dequantization first reconstructs the per-block FP32 scales by dequantizing $c_2^{\text{k-bit}}$ using the top-level $c_1^{\text{FP32}}$; the outer dequantization then rescales the stored k-bit weight values $\mathbf{W}^{\text{k-bit}}$ using those reconstructed per-block scales to recover the BF16 weights. In practice, QLoRA uses NF4 for $\mathbf{W}^{\text{k-bit}}$ and an 8-bit floating format for $c_2^{\text{k-bit}}$ (referred to in the paper as FP8) with an FP32 $c_1$ to complete the two-stage dequantization.

There are implementation subtleties worth noting that the paper outlines. The per-block scale constants $c_2^{\text{FP32}}$ are intrinsically positive; before quantizing these constants to the second-level format (FP8), QLoRA subtracts their mean so that the set of values becomes centered around zero, enabling symmetric quantization (which is typically simpler and more efficient). After this centering and second-level quantization, the two-stage dequantization reconstructs the original per-block scales with sufficient fidelity to avoid measurable degradation in downstream task performance.

These default choices are motivated by the empirical finding that NF4 yields better quantization quality than other 4-bit formats and that double quantization with FP8 scales recovers most of the precision of a single-stage high-precision representation while materially reducing storage overhead.

QLoRA selects default representations that balance information preservation with compactness and computational practicality. For the base model weights, the method uses 4-bit NormalFloat (NF4). NF4 is an information-theoretically motivated k-bit data type tailored to zero-centered normal-like distributions (the common empirical shape of pretrained network weights). By matching the quantization bins to the quantiles of a standard normal distribution and rescaling by per-block statistics, NF4 aims to use each of its $2^4$ bins with roughly equal expected occupancy for normally distributed data, reducing quantization error compared to uniform 4-bit integer or naive 4-bit float formats.

To reduce that overhead, QLoRA applies the second-level quantization to the per-block scales themselves, using a larger block size of 256 for quantizing the $c_2$ constants with FP8. Because the per-block scales vary more smoothly across groups of adjacent blocks, a larger block for their quantization is acceptable: grouping scales into blocks of 256 lets the second-stage quantizer compress many scale values together with minimal loss. This combination—small blocks (64) for the primary NF4 quantization of weights, and larger blocks (256) for the second-level FP8 quantization of scales—achieves the precision advantages of fine-grained weight quantization while keeping the metadata cost low.

Block sizes are an important hyperparameter in block-wise quantization: smaller blocks permit the quantization to adapt to local dynamic range and reduce the impact of outliers, but they increase the number of per-block scale constants and thus the metadata overhead. QLoRA adopts a two-tier block-size strategy that reflects this trade-off.

For the second-level quantization of the per-block scale constants, QLoRA uses an 8-bit floating format (FP8). Empirically, the paper reports that quantizing these scales to 8-bit floats does not harm downstream performance; FP8 provides sufficient dynamic range and precision to accurately reconstruct the per-block scales when combined with the top-level FP32 constants. Thus the canonical storage pipeline is: NF4 for the heavy weight tensors, FP8 for the quantized per-block scales $c_2$, and a small set of FP32 top-level scales $c_1$ to complete the two-stage representation. During computation both the NF4 weights and the FP8 scales are dequantized back through double-dequantization to BF16 weights used by the matmul kernels.

This arrangement—backpropagating through a frozen, low-bit representation—lets the training algorithm exploit the information in the pretrained model at high precision for gradient computation while avoiding the memory and storage cost of maintaining full-precision copies of the large base parameters. In effect, the frozen 4-bit weights act as high-compression constants that are dequantized on the fly for both forward and backward computations, and only the small adapter parameter set is updated.

Because LoRA adapters are small compared to the base model, their BF16 representation and gradients are cheap in memory relative to the activation gradients; this design keeps the large pretrained parameters frozen in 4-bit storage while still allowing expressive, high-precision fine-tuning through the adapters.

Concretely, for a single linear layer augmented with a LoRA adapter, the forward output is the sum of two terms: (1) the product of the input $\mathbf{X}^{\text{BF16}}$ with the dequantized base weight matrix, and (2) the product that arises from the low-rank adapter. Using the notation in the paper, the layer output is
\[
\mathbf{Y}^{\text{BF16}} \;=\; \mathbf{X}^{\text{BF16}} \,\text{doubleDequant}\!\left(c_1^{\text{FP32}},\, c_2^{\text{k-bit}},\, \mathbf{W}^{\text{NF4}}\right)\;+\; \mathbf{X}^{\text{BF16}}\mathbf{L}_1^{\text{BF16}}\mathbf{L}_2^{\text{BF16}}.
\]
The first term performs a standard BF16 matrix multiplication after dequantizing the stored 4-bit NF4 representation back to BF16; the second term is the LoRA contribution, where $\mathbf{L}_1$ and $\mathbf{L}_2$ are the trainable low-rank adapters stored and computed in BF16. In implementation, the dequantization step produces a BF16 weight tensor that is used directly by optimized BF16 matrix-multiply kernels, so the forward pass remains efficient and leverages standard dense linear algebra primitives.

For the primary k-bit quantization of weight tensors (the NF4 storage of $\mathbf{W}$), the paper uses a block size of 64. This relatively small block size provides the fine-grained scaling needed to keep NF4 quantization errors low across diverse weight magnitudes within a tensor. The per-block scales for these size-64 blocks are initially stored in FP32 and would, without further compression, impose a substantial overhead.

Even though $\mathbf{W}$ is frozen, the backward computation must still account for how the dequantized $\mathbf{W}^{\text{BF16}}$ affects intermediate quantities when computing gradients for the adapters. In other words, computing $\frac{\partial E}{\partial \mathbf{L}_i}$ requires computing derivatives that depend on the dequantized base weights (for example, terms like $\partial \mathbf{X}/\partial \mathbf{W}$ appear in the chain rule). To obtain these derivatives accurately, QLoRA dequantizes $\mathbf{W}^{\text{NF4}}$ to $\mathbf{W}^{\text{BF16}}$ (the computation dtype) and performs the necessary differentiation in BF16 precision. The dequantization operation is treated as a differentiable mapping during backprop so that gradients can flow through it to compute correct adapter gradients, but the optimizer is configured to only apply updates to the adapter parameters, leaving the base weights unchanged.

Double Quantization (DQ) and its inverse, double dequantization, are central to how QLoRA stores both the low-bit weights and their associated per-block quantization constants compactly. The primary observation is that per-block quantization scales (the "quantization constants") themselves consume memory; when the base weights use small blocks for high-precision quantization, those constants create a non-negligible overhead. Double Quantization reduces that overhead by quantizing those constants themselves with a second, coarser quantization.

QLoRA's forward pass blends a low-bit storage format for the pretrained base model with a higher-precision compute path and an additive trainable adapter. The base model weights are stored in a 4-bit NormalFloat (NF4) representation; whenever those weights are needed for computation they are dequantized into the chosen computation format (in the paper, BrainFloat16, abbreviated BF16). The input activations are also represented in BF16 during computation. The matrix multiplication for a linear projection therefore uses BF16 operands: the input activation matrix $\mathbf{X}^{\text{BF16}}$ and the dequantized weight matrix $\mathbf{W}^{\text{BF16}}$.

Double Quantization yields measurable memory savings: for example, with a weight-block size of 64, storing FP32 per-block scales would add $32/64 = 0.5$ bits per parameter on average. By quantizing the scales with FP8 and using a larger block size of 256 for these second-level constants, the average additional cost becomes $8/64 + 32/(64\cdot256) = 0.127$ bits per parameter, a reduction of about $0.373$ bits per parameter (approximately 3 GB for a 65B-parameter model). Despite this extra compaction, the paper reports no degradation of finetuning performance from double quantization.
