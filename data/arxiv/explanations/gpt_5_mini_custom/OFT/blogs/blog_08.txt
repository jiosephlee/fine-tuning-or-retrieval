\title{Blogs about the Paper: "Controlling Text-to-Image Diffusion by Orthogonal Finetuning"}

# Zero Overhead at Inference: Deploying Personalized Diffusion on a Budget

Large text-to-image diffusion models are powerful, but shipping personalized or controllable variants often comes with runtime costs: new adapter modules, bigger memory footprint, or extra compute during sampling. Orthogonal Finetuning (OFT) changes that calculus. The key takeaway: once you finish finetuning, OFT’s learned rotations can be folded into the base weights, producing an equivalent model with no extra inference latency or architectural overhead.

Below I explain how that works, what it means for memory and on-device deployment, and practical trade-offs teams should consider.

## How folding works (the simple math)

OFT finetunes a pretrained layer by learning a layer-shared orthogonal matrix \(\mathbf{R}\) and applying it multiplicatively to the pretrained weights \(\mathbf{W}^0\). The forward pass during finetuning is:

\(\mathbf{z} = (\mathbf{R}\mathbf{W}^0)^\top \mathbf{x}.\)

After training, you can precompute and store the product

\(\mathbf{W} = \mathbf{R}\mathbf{W}^0.\)

At inference time you then run the exact same forward computation the original pretrained model used:

\(\mathbf{z} = \mathbf{W}^\top \mathbf{x}.\)

Because \(\mathbf{W}\) is a standard weight matrix, there is no extra matrix multiplication, no additional control modules, and no extra memory accesses beyond what the base model already required. In the paper: "we can simply multiply the learned orthogonal matrix \(\mathbf{R}\) into the pretrained weight matrix \(\mathbf{W}^0\) and obtain an equivalent weight matrix \(\mathbf{W}=\mathbf{R}\mathbf{W}^0\). Thus the inference speed is the same as the pretrained model."

## Practical deployment implications

- Zero runtime latency overhead. Folding yields a single weight tensor per layer. Sampling code, optimized kernels, and hardware accelerators can run unchanged — latency is identical to the pretrained model.
- No extra module graph or memory indirections. Unlike adapter-style methods (ControlNet, T2I-Adapter) that put extra blocks in the forward pass, OFT requires no extra operators or branching at inference.
- Same memory footprint for model weights. If you replace \(\mathbf{W}^0\) with \(\mathbf{W}\) in your stored model, the total parameter storage for the model is unchanged. There is no permanent need to store both \(\mathbf{R}\) and \(\mathbf{W}^0\) for inference.
- Optionally reversible: if you prefer to keep the original checkpoint and apply the rotation at load time, you can compute \(\mathbf{W}=\mathbf{R}\mathbf{W}^0\) once when loading the model on device. That introduces one-time cost on load, not during sampling.
- No extra runtime memory for control signals. OFT is trained to incorporate controllability into the model’s existing weights; it does not require passing additional aux inputs through extra networks at inference.

## On-device benefits

- Fits constrained devices. Because the final model is a standard weight-only variant, device drivers and quantization pipelines already designed for the base model still apply. You do not need to re-engineer inference kernels.
- Efficient storage strategies. Teams can either store the folded \(\mathbf{W}\) (recommended for lowest runtime complexity) or store a compact representation of \(\mathbf{R}\) (if you want to reconstruct \(\mathbf{W}\) on demand). The paper provides parameter-efficient variants to make storing \(\mathbf{R}\) itself feasible if desired.
- No extra latency for multi-turn or interactive usage. Since no additional modules execute during sampling, tight latency budgets (e.g., interactive editors, on-device photo apps) remain satisfied.

## Parameter efficiency and what you store

OFT is designed to be parameter-efficient during finetuning, and that efficiency helps when you need to keep many personalized variants:

- Block-diagonal orthogonals. OFT commonly parameterizes \(\mathbf{R}\) as block-diagonal with \(r\) blocks; this reduces trainable parameters from \(\mathcal{O}(d^2)\) to \(\mathcal{O}(d^2/r)\) for a \(d\times d\) input dimension. Blocks can also be shared across layers to further shrink the finetuned footprint.
- Concrete comparison to LoRA (from the paper): for a \(128\times128\) weight matrix with rank \(r'=8\), LoRA uses 2,048 trainable parameters while OFT with \(r=8\) uses 960 parameters (no block sharing). That shows OFT can be more compact for the same finetuning capacity.
- Re-scaled OFT. If you want slightly more flexibility, re-scaled OFT learns a small diagonal \(\mathbf{D}\) (per-neuron scales) in addition to \(\mathbf{R}\). This adds very few parameters and still folds into \(\mathbf{W}\) as \(\mathbf{W}=\mathbf{R}\mathbf{W}^0\mathbf{D}\).

Note: during deployment if you fold and store \(\mathbf{W}\), these finetuning parameter counts matter mostly for offline storage of alternative variants (e.g., many personalized models). If you want to store only compact finetuning deltas (\(\mathbf{R}\) and optionally \(\mathbf{D}\)) to reconstruct the folded weights on-device, the parameter-efficiency of OFT makes that practical.

## Training vs inference costs

- Training: OFT uses Cayley parameterization (or other differentiable orthogonalization) and may involve matrix inverses during training. The paper notes this is an implementation cost during finetuning, not inference; block-diagonalization mitigates the cost.
- Inference: after folding, there is no matrix inverse or extra operation required. All the heavy training-specific math is a one-time expense done offline.

## Stability and operational advantages

Two practical properties that help shipping models reliably:

- Better finetuning stability. The constrained variant (COFT) enforces \(\|\mathbf{R}-\mathbf{I}\|\le\epsilon\), which yields predictable behavior across different numbers of iterations and subjects. For engineering teams this reduces hyperparameter tuning and risk of model collapse during personalization.
- Smooth convergence and sample efficiency. The paper reports faster, more stable convergence than competing adapter or low-rank updates, which shortens finetuning cycles and reduces compute billed to cloud/edge training infrastructure.

## Limitations and trade-offs to keep in mind

- Training-side cost. Cayley transforms involve matrix inverses (or other orthogonalization steps). The authors mitigate this with block-diagonal \(\mathbf{R}\), but training complexity is higher than simple additive low-rank adapters.
- Block-diagonal structure is a bias. Parameter efficiency comes from restricting \(\mathbf{R}\) to blocks; that can reduce flexibility compared to fully unconstrained finetuning. The paper reports this trade-off is favorable for stability and final controllability, but teams should validate for their specific tasks.
- If you choose not to fold on-device and instead apply \(\mathbf{R}\) at load time, you pay a one-time cost when constructing \(\mathbf{W}\). This is usually acceptable, but it is an operational decision.

## Quick checklist for shipping OFT-personalized models

1. Train OFT/COFT offline using the preferred block size \(r\) and (optionally) COFT’s \(\epsilon\) to control deviation from \(\mathbf{I}\).
2. After training, compute the folded weight matrices \(\mathbf{W}=\mathbf{R}\mathbf{W}^0\) (and \(\mathbf{D}\) if re-scaled OFT was used).
3. Replace pretrained layers with \(\mathbf{W}\) in your deployment artifact. Optionally, re-run quantization/acceleration pipelines on the folded model.
4. For multiple personalized variants: either store full folded checkpoints (fastest inference) or store compact finetuning parameters \((\mathbf{R},\mathbf{D})\) and fold at load time if storage is constrained.

## Bottom line

OFT gives you controllability and personalization without paying a runtime tax. By design, learned orthogonal transforms can be folded into the base weights producing a standard weight-only model: identical runtime graph, identical latency, and identical per-sample compute. For teams shipping many personalized or controllable variants under strict latency or on-device constraints, OFT is an attractive approach: build richer, controllable diffusion models while keeping your runtime budget unchanged.
