\title{A Textbook about the Paper: "Controlling Text-to-Image Diffusion by Orthogonal Finetuning"}

Chapter 12: Implementation Guide and Best Practices

# Which layers to finetune (e.g., attention matrices) for fair comparisons

When applying OFT/COFT in practice, choose the finetuned layers with an eye toward fair comparison to prior adapter-style methods and toward the downstream task you target. In the experiments reported in the paper, OFT was applied to the same weights where LoRA is commonly used — namely, attention weight matrices in Transformer-style U-Nets or diffusion backbones — so that comparisons to LoRA and similar adapters are meaningful. Thus, for reproducing or comparing against LoRA baselines, apply OFT to the attention projection matrices (query/key/value/out) that LoRA targets.

That said, OFT is architecture-agnostic in principle. The paper highlights that OFT naturally extends to fully connected layers and convolutional layers. For convolutional layers the block-diagonal orthogonal parameterization has useful interpretations: with one block per input channel, each block acts like a channel-wise (depthwise) orthogonal transform; if blocks are shared across channels the same orthogonal transform is applied to all channels. This gives you a practical mapping between model architecture and the block structure you choose (see the next section on block design). In short, for fair comparisons to LoRA/adapters finetune the same attention matrices; for specialized applications you can also apply OFT to convolutions or other linear maps, being mindful of the block structure implications.

# Choosing block count and block sharing

A key implementation choice in OFT is how to parameterize the orthogonal matrix $\bm{R}\in\mathbb{R}^{d\times d}$. A full unconstrained orthogonal has $\tfrac{d(d-1)}{2}$ parameters (complexity $\mathcal{O}(d^2)$). To reduce parameter cost while retaining orthogonality, the paper uses a block-diagonal parameterization:

\[
\bm{R}=\mathrm{diag}(\bm{R}_1,\bm{R}_2,\dots,\bm{R}_r),\quad \bm{R}_i\in\mathrm{O}\!\left(\tfrac{d}{r}\right).
\]

With $r$ blocks the parameter count drops to $\tfrac{d(d/r-1)}{2}$ (complexity $\mathcal{O}(d^2/r)$). You can further reduce parameters by sharing blocks so that $\bm{R}_i=\bm{R}_j$ for all $i\neq j$, which brings the complexity toward $\mathcal{O}(d^2/r^2)$.

Practical trade-offs to consider when choosing $r$ and whether to share blocks:
- Smaller $r$ (fewer, larger blocks) yields a richer orthogonal transform and greater flexibility, at higher parameter cost.
- Larger $r$ (more, smaller blocks) reduces parameters and computation and imposes stronger regularization, which can improve finetuning stability but limit adaptivity. When $r$ equals the input channel count in convolutions, each block acts on one channel (depthwise-like behavior).
- Block sharing dramatically reduces parameter budget but biases all channels to be transformed identically; this can be a useful inductive bias for tasks where channel-wise distinctions are less important.

A useful concrete illustration from the paper: for a weight matrix of size $128\times 128$, with block number $r=8$, OFT requires 960 trainable parameters (no block sharing). By contrast, LoRA with $r'=8$ has $2{,}048$ trainable parameters. Use these kinds of comparisons when budgeting parameters.

# Learning rate, iterations, and epsilon selection

The paper establishes qualitative guidance on these optimization hyperparameters rather than single numeric rules. Use these observations as your practical rules-of-thumb.

Iterations and convergence:
- OFT and COFT converge faster than LoRA and adapter/controller baselines in the reported tasks. For example, in a landmark-to-face task LoRA needed about 20 epochs to reach a performance level that OFT achieved in about 8 epochs. In subject-driven generation OFT reaches good control after a few hundred iterations and remains stable even with many more iterations.
- Because OFT preserves hyperspherical energy and constrains updates via orthogonality, it is empirically much less sensitive to the exact number of finetuning iterations: you can safely run more iterations without catastrophic collapse. COFT, which adds an explicit radius constraint, makes iteration count even less sensitive.

Learning rate:
- The paper does not prescribe a single learning rate. Empirically, COFT reduces sensitivity to learning rate choices: with COFT and a reasonable setting of the radius constraint the learning rate and iteration count become “effortless to set.” In practice this means you can begin with the same optimizer settings you would use for the comparable adapter baseline (e.g., the DreamBooth or ControlNet training recipe used in your setting) and expect OFT/COFT to be no more delicate than those baselines. If you find unstable training reduce the learning rate or tighten the COFT radius (see below).

Epsilon (COFT radius) selection:
- COFT enforces $\|\bm{R}-\bm{I}\|\le\epsilon$, constraining how far the finetuned orthogonal matrix may stray from identity. The Cayley parameterization makes this constraint inconvenient to apply directly, so the paper uses the Neumann-series approximation $\bm{R}\approx \bm{I}+2\bm{Q}+\mathcal{O}(\bm{Q}^2)$ to enforce a constraint on the skew-symmetric $\bm{Q}$ (see next section). In practice $\epsilon$ controls a flexibility–stability trade-off: larger $\epsilon$ approaches OFT behavior (more flexible), smaller $\epsilon$ keeps the model close to pretrained weights (more conservative).
- Choose $\epsilon$ based on how much adaptation the downstream task requires. If you observe instability or the pretrained generative quality degrading, reduce $\epsilon$. If the model underfits the downstream signal, increase $\epsilon$. COFT makes these choices safer because the radius constraint prevents catastrophic drift.

Because the paper emphasizes qualitative behavior rather than absolute numbers, treat COFT as the safer default when you expect instability or when you cannot hand-tune iteration count and learning rate.

# Initialization (identity, zero for Q) and optimization steps

Initialization:
- Initialize the orthogonal transform to the identity so the finetuned model starts exactly from pretrained weights. Using the Cayley parameterization $\bm{R}=(\bm{I}+\bm{Q})(\bm{I}-\bm{Q})^{-1}$, initialize $\bm{Q}=\bm{0}$; this yields $\bm{R}=\bm{I}$ at the start of finetuning. For re-scaled OFT, initialize the diagonal scaling $\bm{D}$ appropriately (the paper uses a positive diagonal matrix; in practice initialize to ones so initial scaling is neutral).

Orthogonality enforcement:
- The Cayley parameterization ensures $\bm{R}$ is orthogonal (it produces matrices with determinant $1$, i.e., in the special orthogonal group). The Cayley form requires inverting $(\bm{I}-\bm{Q})$, so implementations must compute this inverse (or solve linear systems) for each block during forward computation. The paper notes that this is a practical cost and mitigates it via block-diagonalization.

COFT projection:
- COFT enforces the radius constraint by constraining $\bm{Q}$ since the Neumann approximation gives $\bm{R}\approx \bm{I}+2\bm{Q}+\mathcal{O}(\bm{Q}^2)$. Thus an $\epsilon$ constraint on $\bm{R}$ is translated into an $\epsilon'$ constraint on $\bm{Q}$. Projected gradient descent on $\bm{Q}$ is used to keep $\|\bm{Q}\|\le\epsilon'$ (the paper describes using projection but does not prescribe a particular norm choice; implementers can use operator or Frobenius norm consistent with their needs).

Skew-symmetry:
- Remember $\bm{Q}$ must be skew-symmetric, i.e., $\bm{Q}=-\bm{Q}^\top$. Ensure your parameterization maintains skew-symmetry across updates (the Cayley transform assumes this).

Optimization loop summary (as described in the paper):
1. Initialize $\bm{Q}=\bm{0}$ so $\bm{R}=\bm{I}$. If using re-scaled OFT, initialize $\bm{D}$ to neutral values.
2. For each training iteration compute the current orthogonal $\bm{R}$ via the Cayley formula (with block-diagonal structure if used).
3. Forward through the layer as $\bm{z}=(\bm{R}\bm{W}^0)^\top\bm{x}$ (or $\bm{z}=(\bm{R}\bm{W}^0\bm{D})^\top\bm{x}$ for re-scaled OFT).
4. Backpropagate and update the learnable parameters (the parameters that define $\bm{Q}$ and possibly $\bm{D}$). If using COFT, project $\bm{Q}$ back into the permitted norm-ball after the gradient step.
5. Repeat until convergence or until your prescribed number of iterations/epochs.

A note on numerical stability and cost: the Cayley transform involves a matrix inverse per block, so measure block sizes against GPU memory and compute budget; block-diagonalization is the means to balance expressiveness and computational practicality.

# Parameter and memory budgeting vs adapters and controllers

OFT sits in a different point of the parameter–flexibility trade-off than low-rank adapters (LoRA) and controller-style approaches (ControlNet, T2I-Adapter). The paper provides explicit parameter formulas that you should use when planning budgets.

Parameter counts:
- Full orthogonal matrix (\(d\times d\)): number of free parameters is \(\tfrac{d(d-1)}{2}\).
- Block-diagonal \(r\)-block orthogonal: number of parameters \(\tfrac{d(d/r-1)}{2}\) (complexity \(\mathcal{O}(d^2/r)\)).
- Block-shared orthogonal: can reduce complexity further toward \(\mathcal{O}(d^2/r^2)\) depending on sharing.
- LoRA with low-rank \(r'\): trainable parameters \(r'(d+n)\) for a weight matrix of size \(d\times n\).

Concrete example from the paper:
- For a \(128\times 128\) weight matrix and LoRA rank \(r'=8\): LoRA has \(2{,}048\) trainable parameters.
- The OFT block-diagonal variant with \(r=8\) blocks (no sharing) uses \(960\) trainable parameters.

Memory and inference:
- OFT introduces no additional inference-time overhead because you can pre-multiply the learned orthogonal \(\bm{R}\) into \(\bm{W}^0\) and export a single dense weight \(\bm{W}=\bm{R}\bm{W}^0\). This contrasts with adapter/controller approaches (e.g., ControlNet) which attach extra modules and increase inference-time computation and memory.
- During training OFT has to compute the Cayley transform and inverses for the blocks, so training-time memory and compute are larger than a purely additive adapter update but can be controlled by block size selection and block sharing.

When planning experiments, compare OFT parameter needs to LoRA and controller approaches using the formulas above. If you have tight inference constraints, OFT’s zero-test-time-overhead behavior is advantageous compared with controllers that increase model size at inference.

# Troubleshooting: instability without orthogonality, failure cases

The paper includes empirical diagnostics and cautions that are directly applicable when implementing OFT/COFT.

Instability without orthogonality:
- The orthogonality constraint is crucial. The ablation in the paper shows that “OFT without orthogonality” — i.e., dropping the orthogonality constraint and allowing unrestricted transforms — produced complete failure in controllable generation: it yielded no realistic images and no control effect. If your training collapses or produces nonsensical outputs, confirm that your orthogonal parameterization is enforced correctly (the Cayley formula applied to a skew-symmetric \(\bm{Q}\) yields an orthogonal \(\bm{R}\)). Numerical drift or incorrect parameterization that violates skew-symmetry can break the guarantee and lead to instability.

COFT and epsilon-related failure modes:
- COFT is designed to improve stability by constraining \(\|\bm{R}-\bm{I}\|\le\epsilon\). However, if you set \(\epsilon\) too small the model may not adapt enough to the downstream signal. If \(\epsilon\) is too large you effectively recover OFT and may lose some of the stability benefits. Additionally, the Neumann-based approximation \(\bm{R}\approx \bm{I}+2\bm{Q}+\mathcal{O}(\bm{Q}^2)\) assumes \(\bm{Q}\) is small so that higher-order terms are negligible; if \(\bm{Q}\) grows large this approximation and the projection on \(\bm{Q}\) can become invalid. Monitor \(\|\bm{Q}\|\) during training and adjust \(\epsilon\) accordingly.

Block-diagonal bias and expressivity limits:
- Block-diagonal parameterization confers efficiency but introduces inductive bias; if you observe systematic failures to model certain aspects of the downstream signal, try reducing the number of blocks (larger blocks) or removing block-sharing to increase expressivity. The paper notes that OFT’s performance continues to improve as the number of trainable parameters increases, so a plateau or failure may indicate you need more expressive blocks.

Cayley inverse scaling:
- The Cayley transform requires inverting \((\bm{I}-\bm{Q})\) for each block. For large blocks this is a computational bottleneck and may encounter numerical conditioning issues if \(\bm{Q}\) approaches eigenvalues near \(1\). Use block sizes commensurate with your compute budget; if conditioning issues appear, reduce block size or ensure the optimization keeps \(\bm{Q}\) norms moderate (COFT projections help).

Other observed failure modes from comparisons:
- The paper highlights that some prior methods (DreamBooth, LoRA) can converge to collapsed or identity-losing states when trained with many iterations or with insufficient regularization. If you reproduce such behavior in baseline runs, OFT/COFT typically remain stable; if OFT/COFT are unstable, double-check orthogonality, the Cayley implementation, and whether you mistakenly optimized the wrong parameters (e.g., updated \(\bm{W}^0\) instead of only \(\bm{Q}\) and \(\bm{D}\)).

Monitoring and diagnostics:
- Track the hyperspherical energy difference \(\|\mathrm{HE}(\bm{W})-\mathrm{HE}(\bm{W}^0)\|\) as a sanity check: OFT should preserve this quantity (ideally keep it close to zero), whereas drastic increases indicate your orthogonality parameterization or numerical implementation is faulty.
- Monitor norms of \(\bm{Q}\), the projection step, and the largest block-wise condition numbers of \((\bm{I}-\bm{Q})\) to detect numerical issues early.
- For COFT additionally log the post-projection \(\|\bm{Q}\|\) to verify the radius constraint is active when intended.

Final notes on practical use
- Default safest route: when you are unsure about hyperparameter tuning, use COFT with a conservative radius constraint. This combination preserves hyperspherical energy, constrains deviation from the pretrained model, and empirically yields stable finetuning with less sensitivity to learning rate and iteration count.
- If you need maximal adaptation capacity (and have the parameter/headroom), relax COFT’s radius toward OFT and consider increasing block size (smaller $r$) or removing block sharing to give the orthogonal transform more freedom.
- Remember that OFT’s major practical advantages are stability, faster convergence in experiments, sample efficiency, and zero additional inference overhead. Use block-diagonalization to trade off expressivity vs parameter and compute efficiency in a principled way using the parameter-count formulas given above.

This chapter summarized the key practical implementation elements and best practices described in the paper: which layers to target (attention matrices for fair comparisons), how to choose block structure and sharing, how to initialize and enforce orthogonality (Cayley parameterization, initialize \(\bm{Q}=\bm{0}\)), how COFT constrains deviation via an $\epsilon$-ball (transferred to \(\bm{Q}\) via Neumann approximation and enforced by projection), how parameter costs compare to LoRA and controllers, and the main troubleshooting points (orthogonality enforcement, Cayley inversion scaling, block-bias and epsilon tuning). Following these practices will reproduce the stability and convergence benefits of OFT/COFT reported in the paper.
