\title{A Textbook about the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

Chapter 3: From Individual Bytes to Patches: Patching Functions and Their Costs

# Formal definition of a patching function and patch size

Patching is the process of grouping a raw byte sequence into larger units—patches—that become the primary steps the model processes. Formally, let the input byte sequence be \(\mathbf{x} = \{x_i \mid i=1,\ldots,n\}\). A patching function \(f_p\) segments this byte sequence into \(m < n\) patches \(\mathbf{p} = \{p_j \mid j=1,\ldots,m\}\). One convenient way to represent a patching function is by indicating, for every byte position \(i\), whether that byte begins a new patch. Concretely, \(f_p\) can be viewed as a mapping that assigns each \(x_i\) a value in \(\{0,1\}\) where \(1\) flags the start of a new patch; the sequence of these flags induces the patches \(\mathbf{p}\).

A key scalar that summarizes a patching function is the (average) patch size. If a particular segmentation yields \(m\) patches over \(n\) bytes, the average patch size is
\[
\bar{s} = \frac{n}{m}.
\]
We will also use the notation \(n_p\) to denote the expected number of patches in a context of length \(n\), and \(n_{ctx}\) to denote the context length measured in bytes. In many analyses it is more convenient to reason in terms of expected patch size \(n_p = n_{ctx} / \bar{s}\). The patch size is not an implementation detail only: it is the single most important factor in determining how much work the main Transformer (the latent/global transformer in BLT) has to do.

# Why patch size drives train/inference FLOPs in BLT

Large Transformer models spend most of their computation in per-step blocks such as feed-forward networks and attention projections. In BLT, the global latent transformer is executed once per patch; therefore the number of patches \(m\) (or equivalently the average patch size \(\bar{s}\)) directly determines how many times the heavy global Transformer is run for a fixed byte context. Put simply, halving the number of patches roughly halves the amount of computation done by the global model.

The paper provides a concrete flop accounting for BLT that illustrates how different components contribute to per-byte cost. The per-byte FLOPs include contributions from (a) the global latent transformer (applied at the patch rate), (b) the local encoder and decoder transformers (applied at the byte or small-window rate), and (c) the encoder/decoder cross-attention blocks that convert between byte-level and patch-level representations. One compact representation in the paper is:

\[
\begin{aligned}
\text{FL}_{\text{BLT}} &= \frac{\text{Transf. FL}(h_{\mathcal{G}}, l_{\mathcal{G}}, m=n_{ctx}/n_p, V=0)}{n_p} \\
&\quad + \text{Transf. FL}(h_{\mathcal{E}}, l_{\mathcal{E}}, m=w_{\mathcal{E}}, V=0) \\
&\quad + \text{Transf. FL}(h_{\mathcal{D}}, l_{\mathcal{D}}, m=w_{\mathcal{D}}, V=256) \\
&\quad + \text{Cross Attn. FL}(h_{\mathcal{E}}, l_{\mathcal{E}}, m=n_p, r=n_p/k)\times \frac{k}{n_p} \\
&\quad + \text{Cross Attn. FL}(h_{\mathcal{D}}, l_{\mathcal{D}}, m=k, r=k/n_p),
\end{aligned}
\]

where \(n_{ctx}\) is the byte context length, \(n_p\) is the patch size, \(w_{\mathcal{E}}\) and \(w_{\mathcal{D}}\) are local attention window sizes, \(h_{\cdot}\) and \(l_{\cdot}\) are hidden dimensions and layer counts for encoder/decoder/global models, \(k\) is the ratio between the patch and byte dimensions used in the cross-attention pooling, and \(V\) denotes output vocabulary size for the decoder projection. The term that depends explicitly on the number of patches is the first term: the global Transformer flops scale with the number of patches (i.e., inversely with patch size). Therefore, for fixed byte-context length \(n_{ctx}\), larger average patch sizes reduce the frequency of invoking the expensive global model and so reduce the dominant part of the per-byte flop cost.

Two practical consequences flow from this relation. First, choosing a patching scheme controls how much compute the global transformer uses at both training and inference. Second, because BLT separates light-weight byte-level modules (encoder/decoder) from the heavy global transformer, one can trade saved global FLOPs for larger global capacity: by increasing average patch size (fewer steps) we free budget to increase the size of the latent transformer without increasing total inference cost.

# Strided (static) patching: simplicity vs. inefficiency and inconsistency

The simplest patching scheme is fixed-size, strided patching: group every \(k\) bytes into a patch. This is straightforward to implement and makes it trivial to set the average patch size because it equals \(k\). Fixed stride patching also simplifies batching and flop accounting for both training and inference.

However, fixed strided patching has two fundamental limitations. First, it does not allocate compute where it is most needed. All patches trigger an identical amount of global computation regardless of whether the bytes inside are predictable low-information content (for example repeated whitespace or continuation bytes) or high-information content (for example the start of a new word, a mathematical expression, or code). This uniform allocation wastes capacity on easy parts of text and fails to give more capacity to the difficult parts.

Second, strided patching breaks contextual consistency. The same logical unit (for example the same word or the same subword sequence) can be split differently depending on alignment to the stride boundary. This inconsistency can make it harder for the model to generalize: similar byte sequences receive different patch encodings and thus different processing. Empirically, static patching (as used by MegaByte) lagged behind more adaptive approaches in compute-controlled comparisons at larger scales.

In short, strided patching trades implementation convenience for both wasted compute and inconsistent representations.

# Space patching: linguistic boundaries and when it fails

A simple improvement over fixed stride is to align patches to natural linguistic boundaries, most commonly to spaces or “space-like” bytes. Space patching creates a new patch after any space-like byte (with a guard that every patch must contain at least one non-space-like byte). Space-like bytes are defined in practice as bytes that are not Latin letters, digits, or UTF-8 continuation bytes.

Space patching has two appealing properties. First, it tends to place the hard prediction points—e.g., the first byte of the next token—at patch boundaries so that the global transformer is invoked on those important decisions. Second, it yields consistent segmentation of words: the same word is likely patched identically across contexts because splits occur at spaces rather than arbitrary stride positions. This consistency helps the model learn stable representations and reduces variance.

But space patching is not universally sufficient. It assumes that spaces are meaningful boundaries, which is true for many languages and many text modalities but not for all domains (binary data, some languages, or specialized structured formats). Space patching also fixes the patching rule: it cannot adapt the patch size based on local unpredictability. Consequently, space patching cannot fine-grain the allocation of compute within words or non-space-delimited languages, nor can it easily produce larger patches when the local context is highly predictable. In this sense, space patching reduces but does not eliminate the inefficiencies of static schemes.

# Dynamic patching: aligning compute with information density

Dynamic patching derives patch boundaries from a data-driven measure of unpredictability—the next-byte entropy under a small byte-level language model (the entropy model). The core idea is simple and powerful: place patch boundaries at byte positions where the next byte is uncertain. In practice, this concentrates global Transformer computation on places that are genuinely informative or hard to predict, and coalesces predictable byte sequences into longer patches that are cheaper to process.

Formally, the entropy model provides a distribution \(p_e(x_i \mid \mathbf{x}_{<i})\) over the byte vocabulary \(\mathcal{V}\). The next-byte entropy at position \(i\) is computed as

\[
H(x_i) = \sum_{v \in \mathcal{V}} p_e(x_i=v \mid \mathbf{x}_{<i}) \log p_e(x_i=v \mid \mathbf{x}_{<i}).
\]

(As used in the BLT experiments, this quantity is the entropy estimate returned by the small byte LM and is then thresholded to find boundaries.) Two practical criteria were used to identify boundaries from the entropies \(H(x_i)\):

1. Global thresholding (global constraint):
\[
H(x_t) > \theta_g,
\]
where \(\theta_g\) is a scalar threshold. Positions with entropy above \(\theta_g\) mark patch starts.

2. Approximate monotonicity (relative constraint):
\[
H(x_t) - H(x_{t-1}) > \theta_r,
\]
which marks positions where entropy increases significantly relative to the immediately preceding byte and so breaks an approximately decreasing entropy trend within a patch.

Entropy patching is applied as a lightweight preprocessing step during data loading: the entropy model scores the stream and the patch boundaries are emitted for use by the full BLT encoder/decoder. This preprocessing approach differs from earlier proposals where a separate classifier is trained to predict boundaries; here a small autoregressive byte LM is used directly to produce entropy estimates.

Dynamic patching offers several benefits. It allocates more global computation to genuinely hard points (for example the first character of a word or the start of an answer) and groups predictable sequences (for example repeated tokens, indentation, or long stretches of similar bytes) into longer patches that amortize the cost of the global transformer. Empirically, entropy patching enabled BLT to achieve larger average patch sizes on predictable domains and better compute efficiency overall, and it also improved robustness and long-tail modeling in downstream evaluations.

There are implementation subtleties: the entropy model’s receptive field and training size affect patching behavior, and in long repetitive contexts entropy estimates can “drift” so that patches become too long on structured repeated content. Practical mitigations included resetting the entropy model context on document boundaries (for example newlines) or favoring the approximate monotonicity constraint which is less sensitive to long-range drift.

# Incrementality requirement: making patch boundaries without future context

When generating autoregressively, the model must decide at each step whether to end the current patch and therefore whether to invoke the (expensive) global transformer for the next patch. That decision cannot rely on future bytes, because those bytes have not yet been generated. This requirement is formalized by the incremental patching property: a patching scheme \(f_p\) satisfies incrementality if for every prefix length \(i\),

\[
f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i}.
\]

In words, when we segment only the prefix \(\mathbf{x}_{<i}\) we must obtain the same segmentation for that prefix as the segmentation induced by applying \(f_p\) to the full (unknown) continuation and then truncating to the prefix. Incrementality guarantees that decisions about whether to start a new patch depend only on the bytes seen so far.

Entropy-based patching naturally satisfies this property because the entropy model conditions only on past bytes; the next-byte entropy at position \(i\) is estimated from \(\mathbf{x}_{<i}\) and can therefore be computed online during generation to decide whether to start a new patch. Space patching is also incremental since space-like bytes are observable in the prefix. In contrast, any scheme that relies on future context to decide a current boundary will fail at generation time.

# Why tokenization is not patching: finite vocabulary, lack of byte access, non-incrementality

Although tokenization groups bytes into larger units, it is conceptually and practically different from BLT-style patching in several important ways.

First, tokens come from a fixed finite vocabulary that is determined before training (for example a BPE vocabulary). Patches in BLT are not restricted to a fixed set; arbitrary byte sequences can be encoded into latent patch representations via the local encoder. This difference matters because tokenization forces a trade-off between vocabulary size and computation: increasing vocabulary size tends to increase the average token length (fewer steps) but it also increases embedding tables and the final projection layer, which raises parameter counts and memory costs. The paper cites a concrete contrast: increasing the average token size from 3.7 to 4.4 bytes (as in Llama 2 to Llama 3) required substantially larger embedding tables (a 4x increase). That coupling constrains how much a token-based system can vary its step rate to trade off inference cost vs. capacity.

Second, models trained on tokenized inputs do not have direct access to the underlying bytes once the tokenization is applied. Tokens are opaque discrete units and the model only observes their embeddings. By contrast, BLT’s local encoder and cross-attention structure explicitly work with byte-level features (including n-gram hash embeddings), so the model retains orthographic and character-level information that token-only models often lack. This is one reason BLT demonstrates stronger robustness to character-level noise and improved performance on character-manipulation tasks.

Third, many widely used tokenizers (including BPE) are not incremental in the sense defined above. The same byte prefix can be tokenized differently depending on the continuation that follows, because token boundaries can depend on the longest-match behavior or merging that spans the boundary between the observed prefix and its unseen continuation. Formally, a BPE tokenizer does not satisfy
\[
f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i},
\]
because the tokenization of a prefix can change with different continuations. Making a tokenization scheme incremental is possible (for example by inserting special delimiter tokens to fix boundaries), but this change increases sequence length and changes the modeling dynamics. BLT’s patching schemes are designed to be incremental out of the box, supporting correct autoregressive generation without peeking at future bytes.

In summary, although both tokenization and patching group bytes, they differ in the expressivity of group formation (fixed vocabulary vs. arbitrary latent patches), the availability of byte-level features to the model, and whether segmentation is compatible with online generation. Those differences underlie many of the practical efficiency and robustness benefits that BLT achieves.

# Closing intuition

Recasting bytes into patches gives a powerful lever for controlling computation: patch size controls the number of expensive transformer steps. Static striding is easy but wasteful because information density is not uniform across bytes. Heuristics like space patching partially fix the problem by aligning to linguistic boundaries, but cannot adapt patch size to local uncertainty. Dynamic, entropy-based patching uses a small byte LM to estimate where bytes are unpredictable and places boundaries accordingly, concentrating computation where it matters while grouping predictable spans into long, cheap patches. Incrementality is essential so that patching decisions can be made online during generation. Finally, because BLT maps arbitrary byte groups into latent patch representations (rather than fixing them to a finite vocabulary), it breaks the tokenization trade-offs and unlocks new ways to trade inference cost for larger model capacity.
