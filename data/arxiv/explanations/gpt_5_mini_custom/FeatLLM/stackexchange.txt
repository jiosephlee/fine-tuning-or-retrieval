\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Why enforce non-negative weights in Eq. (1) and omit a bias term?
Question:
In Section 3.2, the class logit is defined as $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$, followed by a softmax. This enforces non-negative contributions from rule features and there is no bias term. I am confused about two things:
- If a rule is wrong or should be negative evidence for class $k$, the non-negativity constraint prevents the model from assigning it a negative weight. Doesn't this limit expressivity (e.g., capturing that failing a rule is evidence against a class)?
- Without a bias, when all rules are unsatisfied ($\mathbf{z}_k^i=\mathbf{0}$ for all $k$), all logits are 0 and the softmax becomes uniform. Why is it preferable not to learn class priors via a bias or an "always-on" feature?
Is there an ablation comparing signed weights and/or adding a bias term?
Answer:
Short answer: the paper enforces non-negative weights and omits a bias to keep the downstream model conservative, interpretable, and robust in the very-low-shot rule-based regime. Non-negativity constrains each rule to be only “supporting” evidence for a class (not “anti-evidence”), and the lack of a bias makes the model fall back to a uniform prior when no rule fires. The authors treat this as a deliberate inductive bias that trades some raw expressivity for stability and better use of LLM-generated rule features. The paper does not report an ablation that replaces the non-negative projection with signed weights or that adds a bias term.

Why non-negative weights?
The paper’s rule pipeline turns each LLM-generated rule into a binary feature $z_k^i \in \{0,1\}$ (rules per class). The linear logit they train is
$$
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,
$$
i.e., weights projected to the positive orthant. Intuitively, this enforces that every rule only raises (or does not change) a class’s logit when it fires. The stated reasons in the paper are practical:

- Interpretability and semantic alignment: rules were generated as “criteria for class k.” Treating them as positive evidence matches that intent: a rule for class k is meant to be a reason to predict k, not a reason against it. Making weights non-negative preserves that semantic interpretation (a high weight means this rule strongly supports class k).
- Safety in low-shot settings: with only a few labeled examples, allowing arbitrary negative weights risks unstable fits that exploit noise (a spurious rule might be given a large negative weight to force the model away from a class). Constraining weights to be non-negative reduces overfitting degrees of freedom and encourages the model to select only supporting evidence rather than inventing “anti-rules.”
- Mechanism to filter and combine evidence: the framework expects the LLM to produce rules for each class; negative evidence against class k can instead be captured by producing a positive rule for some other class $k'$ (softmax compares across classes). In practice the ensemble also yields many alternative rules, so negative relationships can be handled implicitly by rules for competing classes or by downweighting irrelevant rules to near-zero.

Does this reduce expressivity? Formally, yes: you cannot represent a feature that should subtract from a class’s logit solely by giving a negative weight to a rule for that same class. But in this architecture that is intentional and partly compensated by two effects the paper relies on: (1) the LLM can generate rules aimed at alternative classes (so evidence “against k” can be encoded as evidence “for k′”), and (2) learning can push unhelpful rules’ weights to zero so they stop affecting predictions. For the low-shot tabular problems the authors study, this inductive bias appears helpful (see the ablation that shows tuning weights matters, and the robustness results vs. spurious columns).

Why omit a bias (no learned class priors)?
With all binary rule features zero, the paper’s choice makes all logits zero and softmax uniform, so the model expresses no prior preference. The paper doesn’t spell out a single formal justification, but the design choice aligns with the same conservative, low-shot philosophy:

- Conservative default: when no rule applies, use a uniform prediction rather than trusting a weakly-estimated prior from few examples. In few-shot regimes class-frequency estimates are noisy; a learned bias would risk overfitting to sample-specific priors.
- Encourage evidence-driven predictions: the model is meant to rely on LLM-derived rules and their learned importance, not on priors learned from very little data. A bias would let the model shortcut by memorizing class frequencies instead of using the rule features.
- Simpler and more interpretable: a bias (or an “always-on” feature equal to 1) would complicate the interpretation of weights as rule importances. Keeping no bias makes every learned parameter correspond directly to a rule’s supporting strength.

Are there ablations for signed weights or adding a bias?
No. The paper’s ablation section considers omitting weight tuning (i.e., not learning weights and simply summing binary features), removing ensemble, and removing parts of the prompt (feature description / reasoning step). It does not report experiments that (a) allow unconstrained (signed) weights instead of projecting to positive, or (b) add a bias or “always-on” feature to learn class priors. The authors therefore do not empirically compare these alternate design choices in this work.

If you want to test these choices yourself, two simple controlled ablations are informative: (1) replace the projection with unconstrained weights and retrain the linear model (same optimizer / epochs) to see whether signed weights improve or overfit, and (2) add a bias term or an always-on feature ($z_{\text{const}} = 1$) and observe changes in performance and calibration across shot levels. My expectation based on the paper’s framing is that signed weights or a bias might help when you have more shots (they increase expressivity), but in the very-low-shot regime they may hurt by enabling overfitting and undermining the intended evidence-driven interpretability.

Summary
The non-negativity + no-bias choices are deliberate inductive biases: they make the rule-based predictor conservative, interpretable, and less likely to overfit in few-shot settings. They trade some formal expressivity (no per-rule negative evidence or learned priors) for robustness and clearer semantics of rules. The paper does not include empirical ablations for signed weights or a bias, so their impact remains an open empirical question suggested as future work.

### How exactly does bagging reduce prompt length, and what are the selection ratios?
Question:
The paper states that bagging over features and instances mitigates prompt size constraints for rule generation. Could you clarify the concrete procedure?
- Do you sample a subset of columns and a subset of training examples per trial before constructing the prompt? With or without replacement?
- What are the actual sampling ratios for features and instances per dataset (especially for very wide tables like Communities or Myocardial)?
- How do you ensure critical features are not consistently dropped across trials, and do you track coverage of columns across the ensemble?
Answer:
Short answer: FeatLLM applies classical bagging-style sampling before each LLM query: on each trial it randomly restricts the prompt to a subset of columns and (optionally) a subset of the k-shot examples, asks the LLM to propose rules from that reduced view, parses those rules into binary features, and then ensembles the resulting models. The paper gives the high-level procedure and some hyperparameters ($T = 20$ ensembles, $10$ rules per class, $\text{temperature} = 0.5$), but it does not fix one global sampling ratio for every dataset — the feature/instance subsets are chosen so the serialized prompt (feature descriptions + examples) fits the LLM context window and to induce diversity across trials.

Concrete procedure (as used in the paper)
- For each ensemble trial $t = 1,\dots,T$ the authors (1) randomize the order of the few-shot demonstrations, (2) select a subset of features and/or a subset of training examples to include in the prompt for that trial, (3) set a reasonably high sampling temperature so the LLM outputs diverse rule-sets, (4) ask the LLM to produce rules (they constrain to $10$ rules per class), and (5) parse and convert those rules to binary features and train the small linear model for that trial. The final prediction averages class probabilities from all $T$ trials.
- Within a single trial the prompt contains only the selected columns and selected example serializations (so the prompt size is reduced). This is the mechanism by which bagging “mitigates prompt size constraints.”

What the paper explicitly reports
- Number of ensembles: $T = 20$.
- Number of rules extracted per class per trial: $10$.
- LLM temperature used in experiments: $\text{temperature} = 0.5$ (with $\mathrm{top\text{-}p} = 1$).
- They randomize the order of demonstrations because ordering affects in-context outcomes.
- Bagging is used to select a subset of features or instances for each trial to (a) reduce prompt length and (b) induce diversity across trials so errors in some trials are canceled by correct rules in others.

What the paper does NOT specify (so you should not assume)
- It does not give a single, fixed numeric “sampling ratio” (e.g., always pick $30\%$ of columns) applied to every dataset in the main text. Instead, the selection is governed by the practical constraint that the prompt (feature descriptions + examples) must fit the context window and by the desire to generate diverse rule-sets across trials. The authors also do not publish an explicit per-dataset table of columns-per-trial for datasets like Communities or Myocardial in the main paper excerpts shown.
- It does not claim a sampling-with-replacement vs. without-replacement formalism in the writeup; however, the description (“bagging to select a subset of features or instances for each trial”) and the ensemble intent imply independent random sampling across trials (i.e., features can reappear across different trials), which is equivalent to sampling with replacement across trials but typically without replacement within a single trial’s subset selection (so the prompt does not contain duplicate columns).
- The paper does not describe an explicit mechanism that enforces that “critical” features are never dropped, nor does it report a formal column-coverage tracking statistic in the main text. Instead, robustness to dropped features is achieved implicitly by repetition across $T$ trials and by rule-consensus: rules that appear across multiple trials are more likely to be correct and to survive ensembling.

How the method guards against dropping important features (intuitive + specifics)
- Repetition + ensemble averaging: Because each trial samples a different subset, an informative column has multiple independent chances to be included across the $T$ trials. With $T = 20$ and independent sampling, the probability a column is never sampled can be small if per-trial subset sizes are chosen sensibly.
- Rule consensus: The paper argues that correct rules tend to be rediscovered across multiple trials (self-consistency). Ensemble averaging thus upweights features/rules that are stable across trials and downweights spurious rules that appear only once.
- Weight tuning: After converting rules to binary features, the linear model learns non-negative weights for features using the (few-shot) training data. Irrelevant rules receive near-zero weights and thus have little influence at inference time.

Practical implications for very wide tables (Communities / Myocardial)
- In practice you must choose the per-trial feature subset size so that the serialized prompt (feature name + type + example values for selected features + k-shot examples + reasoning/response instructions) fits the LLM context window. For very wide tables the paper’s approach is to aggressively sub-sample features per trial rather than attempt to fit the whole table in a single prompt.
- The authors set $T = 20$ and $R = 10$ rules/class; with these choices you get many distinct rule proposals even when each trial sees only a small fraction of columns. The exact fraction used per dataset was tuned so prompts remained under the model’s token limit; that tuning detail (per-dataset column counts per trial) is not tabulated in the main paper text.

If you need reproducible per-dataset guidance
- Start by computing the token budget: set a conservative token limit for the prompt (e.g., model max tokens − expected code/execution tokens). Serialize feature descriptions and a single example to measure tokens per column. Then set per-trial $\text{column\_count} \approx \left\lfloor \frac{\text{token\_budget}}{\text{tokens\_per\_column}} \right\rfloor$ minus room for k-shot examples and instruction text.
- Use without-replacement selection within a trial and independent sampling across trials (so a column can reappear in multiple trials). This mirrors standard bagging intuition and matches the paper’s ensemble intent.
- If you worry about missing some particular domain-knowledge features, add them deterministically to every trial’s prompt (the paper does not do this explicitly, but it is a valid augmentation compatible with the method).

Summary
FeatLLM uses feature- and instance-level bagging to reduce prompt size by constructing each LLM prompt from a randomly selected subset of columns and examples, runs $T = 20$ such trials with rule extraction ($10$ rules per class), and ensembles the resulting learned linear models. The paper does not publish a single uniform sampling ratio applied to all datasets; instead, the subset sizes are chosen so the prompt fits the LLM context window and to produce diversity across trials. Important features are not protected by an explicit coverage constraint in the main paper; robustness comes from repeated sampling across trials, rule consensus, and post-hoc weight tuning that downweights irrelevant rules. If you want concrete per-dataset numbers for Communities or Myocardial, the practical way (and what the authors imply they did) is to measure token cost per column and pick the largest per-trial subset that keeps the prompt under the model’s token budget, optionally forcing a small set of known-critical features into every prompt.

### What prevents Step-1 prior-knowledge reasoning from leaking information from examples?
Question:
The prompt design splits reasoning into Step-1 (infer tendencies from prior knowledge only) and Step-2 (use examples plus Step-1 to derive rules). Practically, how do you ensure the LLM does not implicitly use the serialized examples during Step-1? Is Step-1 literally placed before any examples in the prompt, or do you rely solely on instructions? Do you validate that Step-1 content changes meaningfully when examples are removed?
Answer:
Short answer: In FeatLLM the Step‑1 “prior-knowledge” reasoning is enforced primarily by prompt structure and explicit instructions (not by model fine‑tuning), and the paper validates the usefulness of that two‑step design via ablation and spurious‑correlation experiments. The authors do not claim a formal, provable isolation of Step‑1 from example leakage, so in practice you should (and the paper suggests) combine clear instruction separation with empirical controls (ablation / rule audits) to detect implicit leakage.

Why the paper believes leakage is controlled
The prompt design in Section 3.1 separates three components: (1) basic information (which does include a serialized set of few‑shot examples), (2) a reasoning instruction that explicitly asks the model to run two steps of reasoning, and (3) response formatting instructions. The paper’s key textual mechanism is that the reasoning instruction tells the LLM to perform Step‑1 “without referring to example demonstrations, relying instead on general knowledge or common sense,” and to perform Step‑2 only afterwards using both the Step‑1 outcome and the provided examples. So the intended control is instruction‑level: Step‑1 is an explicit, self‑contained reasoning task that should use only prior knowledge.

What the experiments show (paper‑grounded)
Empirically the paper demonstrates that including the reasoning instruction (the two‑step separation) helps: the ablation “-Reasoning” (omitting Step‑1) reduces AUC across datasets (Section 4.2), indicating the two‑step prompt yields better and more robust rules than a single undirected prompt that can more easily latch onto spurious correlations. The spurious‑correlation experiment (attaching irrelevant columns) further shows FeatLLM degrades less than baselines and that rules based on noisy columns are rare ($\sim 1\text{--}2\%$): this is consistent with Step‑1 helping focus on sensible features rather than overfitting the few examples.

Practical measures (consistent with the paper) you should use to avoid implicit example leakage
1) Explicit instruction separation: keep the exact wording that asks the model to perform Step‑1 without looking at examples. The paper relies on this wording as the primary isolation mechanism.

2) Logical/visual separation in the prompt: put a clearly labeled “Step 1: Prior knowledge only” instruction and an empty (or neutral) example context for that step; then include the serialized examples only in a later “Step 2: Use examples + prior knowledge” block. The paper’s description implies such sectional separation (Basic info, Reasoning instruction, Response instruction) even though it does not show every prompt permutation in the main text.

3) Prompt ordering: while the paper’s text describes the two steps inside the reasoning instruction, a conservative practical choice (and one consistent with the intent) is to place the Step‑1 instruction and request before the serialized examples in the prompt so the model’s attention sees the prior‑only task first. The paper does not state a strict requirement that Step‑1 text precedes examples, but doing so strengthens the intended separation.

4) Strong formatting and explicit tethering: require the model to output a labeled Step‑1 block (e.g., “Step‑1: Prior knowledge reasoning — do not use examples: …”) and a separate Step‑2 block that references examples. The paper uses response format constraints to make parsing easier, and the same constraints help enforce that the model responds in the intended two‑part way.

5) Empirical validation and auditing (recommended and aligned with paper experiments): run controlled checks where you (a) remove the examples entirely and request only Step‑1 to see if the Step‑1 content changes (this is a sensible control the paper alludes to via ablations, though it does not explicitly report a “Step‑1 only” transcript analysis), and (b) compare rules produced with and without examples to measure how much Step‑1 changes (e.g., overlap of features/rules, AUROC of rules vs. label). The paper does perform ablation (“-Reasoning”) and evaluates rule quality and robustness to spurious columns (Section 4.2), which are the kinds of empirical checks you should run.

6) Ensemble and bagging to dilute accidental leakage: as the paper describes, running multiple trials with different example orders and higher temperature reduces dependence on any single prompt quirk; majority/common rules across trials are more likely to reflect genuine prior knowledge. The ensemble is both a robustness and a diagnostic tool (consistent with the paper’s approach).

Limitations to keep in mind (stated or implied in the paper)
The paper does not mathematically prove isolation of Step‑1; it relies on instruction following behavior of LLMs. LLMs can still implicitly incorporate context even when told not to, so the recommendations above (prompt ordering + empirical controls + ensembling) are practical mitigations rather than formal guarantees. The paper’s ablation and spurious‑correlation results provide empirical evidence that the two‑step prompt improves robustness, but they do not report a direct transcript study that shows Step‑1 answers are identical when examples are removed. If you need strict non‑leakage guarantees, you must treat Step‑1 as a separate prompt/query that the model sees before any examples are provided.

Concluding recommendation
Follow the paper’s design (explicit two‑step reasoning instruction), place or label Step‑1 clearly (preferably before examples), enforce structured output for Step‑1, and run the suggested empirical controls: ablate the Step‑1 instruction, run Step‑1 with and without examples to compare outputs, and measure rule stability across ensemble trials. These practices implement the paper’s intended isolation and let you detect (and reduce) any implicit leakage from examples into Step‑1.

### How are thresholds for continuous features chosen in generated rules?
Question:
Many tabular rules hinge on thresholds (e.g., "age > 65"). When the LLM proposes such cutoffs, are they expected to come from its prior knowledge, or does it derive them from the few-shot examples (e.g., quantiles)? If the scales/units vary across datasets (like lab values), how do you prevent nonsensical thresholds? Is there any post-hoc calibration or snapping of thresholds to observed percentiles?
Answer:
Short answer: FeatLLM lets the LLM mix prior knowledge and the few-shot examples when proposing cutoffs; it constrains and validates those cutoffs via feature descriptions, parsing, and downstream tuning/ensembling rather than by snapping to dataset percentiles. There is no explicit percentile-snapping calibration step in the paper — instead the system relies on prompt structure, parsing with the LLM, and learned weights to avoid or downweight nonsensical thresholds.

Expanded explanation grounded in the paper

How thresholds are proposed
FeatLLM asks the LLM to reason in two stages. In Step 1 the model is explicitly encouraged to state general tendencies/causal relationships using its prior knowledge (e.g., “older age increases risk”). In Step 2 it is asked to combine that general knowledge with the few-shot serialized examples to produce concrete rules (e.g., $\text{age} > 65$). Because Step 2 has access to the few examples, the numeric cutoffs the LLM outputs can be influenced both by its priors and by the examples shown in the prompt. So thresholds are not purely memorized priors nor purely empirical quantiles — they are produced by the LLM’s reasoning that uses both sources.

Mechanisms that reduce nonsensical thresholds for heterogeneous scales/units
The paper uses several practical controls to prevent ill-formed rules:

1) Feature descriptions: The prompt includes each feature’s type and (optionally) a definition. The LLM is instructed to consult these types, which reduces attempts to place numeric cutoffs on categorical fields or to use obviously wrong units.

2) Response formatting constraints: The prompt constrains rule format (and a fixed number $R$ of rules per class; they use $R = 10$), which reduces free-form, noisy outputs.

3) Parsing via the LLM: Because the LLM’s textual rule output can contain syntactic variation (e.g., “greater than” vs “>”), FeatLLM uses the LLM again to parse rules into executable code rather than relying on brittle string rules. This leverages the LLM’s semantic understanding to interpret a wider range of phrasing.

4) Downstream learning (weight tuning and filtering): The parsed rules become binary features. A simple linear model with non-negative weights is trained on the few-shot samples ($\text{logit}_k = \max(w_k,0)\cdot z_k$; see Eq. (1)). This tuning step learns the importance of each rule and effectively downweights or ignores rules that are inconsistent with the data. The authors also report using a post hoc threshold on learned weights (they used $0.1$ in an analysis) to filter out weak/noisy rules. This acts as a practical guard against spurious or nonsensical numeric cutoffs.

5) Ensemble and bagging: Rules are generated repeatedly with randomized prompts (temperature and demo order) and bagging of features/samples. Erroneous thresholds that appear rarely will be diluted in the ensemble, while consistent, meaningful thresholds will be reinforced.

What is not done (no explicit percentile snapping)
The paper does not describe any explicit step that “snaps” numeric thresholds to observed percentiles (e.g., forcing every cutoff to be a dataset quantile) or any calibration that replaces the LLM’s numeric with a nearest-percentile value. Instead, the LLM can produce arbitrary numeric cutoffs and the system relies on the parsing/LMM reasoning plus the trained weights and ensemble to reject or downweight those that are inconsistent with the few-shot data. In short, there is no hard-coded percentile calibration; the correction is statistical and heuristic (parsing + weight learning + ensemble).

Intuition and connection to broader concepts
Think of FeatLLM as using the LLM as a domain-aware rule proposer and then using a lightweight statistical model to validate and weight those rules. The LLM injects inductive bias (prior knowledge and human-like rules), the few-shot examples nudge those rules toward the task data, and the linear tuning + ensemble acts like a low-capacity verifier that filters out bad proposals. This is similar in spirit to model-based proposals followed by empirical selection: propose many hypotheses (rules) from a rich prior, then test and weight them on the observed data.

Practical implications
If you worry about unit mismatches or lab-value scales in a particular dataset, best practice consistent with the paper is to (a) provide explicit and precise feature descriptions (units/ranges) in the prompt, (b) include representative few-shot examples that reveal the dataset’s numeric scale, and (c) rely on the ensemble + tuning to filter out implausible thresholds. If you need hard guarantees (e.g., force thresholds to dataset quantiles), you would have to add that as an explicit post-processing or parsing constraint — that is not part of the method as presented.

Summary
Thresholds in FeatLLM come from a mix of LLM priors and the few-shot examples because of the two-step reasoning prompt. Nonsensical thresholds are controlled by supplying feature metadata, using LLM-assisted parsing, and — importantly — learning non-negative weights and ensembling to downweight or remove bad rules. There is no explicit percentile-snapping calibration described in the paper.

### How is code generated from natural-language rules validated before exec()?
Question:
Section 3.2 describes prompting the LLM to emit Python code to parse rules and then running it with Python's exec(). This raises concerns:
- Security: Is the code sandboxed (e.g., restricted builtins) to avoid arbitrary execution?
- Correctness: How do you detect silent logical errors (off-by-one thresholds, category name mismatches, handling of missing values) before using the resulting binary features?
- Determinism: Is the code-generation temperature set to a deterministic setting? If not, could parsing failures cause variance across runs?
Answer:
Short answer: the paper acknowledges the risks and variance inherent in generating and exec()‑ing code but does not claim an automatic sandbox or formal static verification step; instead it relies on three practical defenses built into FeatLLM (LLM-guided parsing, weight tuning + thresholding, and ensembling/bagging) to reduce the impact of bad rules, and uses a non‑zero temperature to intentionally obtain diversity. If you need production‑grade safety, you should add explicit sandboxing, deterministic generation for parsing, unit tests, and logging — the paper does not describe those engineering safeguards.

Below I summarize what the paper actually says about each of your concerns, how FeatLLM mitigates them, and what it does not guarantee (with concrete, practical suggestions you can add).

Security (exec() and arbitrary code)
- What the paper states: the rules (natural language) are turned into Python code by prompting the LLM and that generated code is executed via Python’s exec() to produce binary features. The paper motivates this because the LLM is good at robust parsing of noisy textual rules. There is no statement in the paper that the code is sandboxed or that builtins are restricted.
- What that implies: as presented, executing LLM‑produced code with plain exec() is a security risk (arbitrary I/O, system calls, file deletion, network access, heavy CPU usage, etc.). The paper does not claim to mitigate that risk beyond generating “simple code” via the LLM.
- Practical mitigations (not described in the paper, but recommended if you implement this): run generated code in a strict sandbox (e.g., a separate process/container with no network and minimal filesystem access), use Python’s restricted execution patterns (or libraries such as RestrictedPython), execute only an AST‑whitelisted subset (parse with ast, verify allowed nodes/operators), run in a time/cpu/memory limited worker, or avoid exec() entirely by translating rules into a safe interpreter you control. Log and store every generated function for offline review.

Correctness (silent logical bugs in generated rules/code)
- What the paper states as built‑in defenses: FeatLLM accepts that LLM outputs are noisy and therefore (1) constrains response formatting in the prompt to ease parsing, (2) uses the LLM to produce code for parsing rather than handwriting a brittle parser, (3) trains a simple linear model with non‑negative weights on the generated binary rule features so that data can downweight or ignore unhelpful/irrelevant rules, and (4) ensembles across many LLM runs with bagging so that spurious rules from some runs are diluted by correct ones from others. The paper reports a “quality of features” experiment showing many generated rules are informative and that tuning filters out low‑weight (unhelpful) rules.
- What the paper does not claim: there is no automated static correctness proof of a rule’s logical meaning, no explicit detection of semantic errors like off‑by‑one thresholds, mis‑named categories, or special‑case handling of missing values. If a generated rule consistently mislabels examples in a way that correlates with the target, the downstream tuning can end up giving it weight (i.e., tuning helps but is not a formal guard against subtle consistent logical mistakes).
- Practical validation steps to add (complementary to the paper’s methods): run generated rules on a validation set and compute simple diagnostics (coverage, positive rate, AUROC vs label per rule as done in the paper), assert type and category name consistency (check that categorical values referenced in rules exist in the column), validate numeric thresholds by checking neighboring bins (look for suspicious boundary effects), detect rules that access missing values and require a deterministic missing‑value policy, and add unit tests (small hand‑crafted inputs with known expected rule outcomes). Keep a human‑review step for top rules if interpretability is needed.

Determinism and variance across runs
- What the paper states: in Implementation details FeatLLM uses GPT‑3.5 with $\text{temperature}=0.5$ and $\text{top-}p=1$. The methods section also says they intentionally introduce randomness (via higher temperature and randomizing demonstration order) to get diverse rule sets and ensemble benefits. Ensemble size defaults to $20$ in experiments; the paper shows ensemble improves robustness and that rule diversity is useful.
- What that implies: rule generation is intentionally non‑deterministic to obtain diverse weak learners. That means different runs can produce different rule sets and different feature matrices unless you fix sampling parameters or seed the LLM. Parsing failures can happen because the LLM sometimes emits syntactic variants; the paper handles this by re‑prompting the LLM to produce parsing code (and then executing the result).
- If you need determinism: set $\text{temperature}=0$ (or near 0) for the parsing step to deterministically produce the same text (and parsing code) across runs; use fixed prompt ordering and a fixed LLM seed if available. If you still want ensemble diversity for predictive robustness, you can separate phases: use deterministic parsing for safety/validation and use a separate higher‑temperature generation channel purely for ensembling. The paper does not report retry/backoff strategies for parsing failures, so implement retries and fail‑safe behavior (e.g., skip a rule set if parsing fails).

How FeatLLM’s existing mechanisms help with these concerns
- Ensemble + bagging: reduces the impact of a few bad rule sets and gives a self‑consistency signal (rules appearing across trials are more likely correct).
- Weight tuning and thresholding: the learned non‑negative weights filter out rules that do not help predictive performance; the paper reports that after tuning, many weak rules are discarded.
- Prompt engineering (format constraints and reasoning steps): helps reduce syntactic variance so parsing is easier, and Step‑1 reasoning reduces spurious correlations in generated rules.

Concrete checklist for a safe, robust implementation (based on paper + recommended engineering)
1. Separate generation and execution phases. Use the LLM to output rules, then translate rules into a controlled internal representation (AST or domain objects), avoiding direct exec() where possible.
2. If you must exec(), run in an isolated sandboxed worker with strict resource and syscall limits.
3. Use deterministic settings ($\text{temperature}=0$) for any prompt whose output you must validate automatically; use nonzero temperature only for ensemble diversity.
4. Validate generated rules on a held‑out validation set: compute per‑rule AUROC, coverage, and detect suspicious thresholds or categories.
5. Implement retries/exceptions: if parsing‑code fails, re‑prompt with a stricter format request or discard that trial.
6. Log every generated rule and the code used to create features for auditing and manual inspection.
7. Optionally add small unit tests for typical edge cases (missing values, unknown categories, boundary values).

Summary
The paper explicitly uses exec() on LLM‑generated parsing code and relies on format constraints, the LLM’s own parsing ability, weight tuning, and ensembling to mitigate incorrect or noisy rules. It does not describe sandboxing or formal verification of generated code, and it intentionally uses non‑zero temperature for diversity (so runs are not deterministic unless you change the temperature). If you plan to use or extend FeatLLM in practice, add explicit sandboxing, deterministic parsing passes for validation, automated per‑rule diagnostics, and logging/auditing to address the security, correctness, and reproducibility concerns you raised.

### How do you handle missing values or unseen categories when applying rules?
Question:
When generated rules reference features that are missing or categories that were not seen in the few-shot demonstrations, what is the expected behavior of the parser code and the resulting binary feature? Do you default to the rule evaluating to false, skip the rule, or impute? Is there any explicit instruction in the parsing prompt to define this behavior?
Answer:
Short answer: The paper does not state a single, explicit default rule for missing values or unseen categories. FeatLLM relies on the LLM to produce parsing code (which is then executed with Python’s exec()), and the prompt already gives the model type information (feature types and example categories) to reduce mismatches — but it does not document a fixed convention (e.g., “if missing → rule = false”) that the parser enforces across all datasets. In other words, handling is determined by the concrete parsing code the LLM outputs in each run, not by a globally-specified imputation or skip rule in the paper.

Why this matters and how it works in the paper. FeatLLM generates natural-language rules, then asks the LLM to convert those rules into executable Python that produces binary features ($0/1$) for whether a sample satisfies each rule. Because the paper emphasizes using the LLM to cope with noisy syntax and type mismatches, the exact behavior for edge cases (missing entries, categories not present in the few-shot examples) depends on how the LLM wrote the parsing code in that trial. The authors mitigate type-errors by including feature type descriptions and example categories in the prompt so the generated code is more likely to perform sensible checks, but they do not claim or record a single fixed policy for missing/unseen values.

Practical consequences and what likely happens in practice. If the LLM-generated parser includes explicit existence/type checks, it may (a) treat missing values as "not satisfying" the condition (i.e., yield $0$), (b) map unseen categorical strings to a default branch (e.g., treat as non-matching), or (c) produce code that raises/handles exceptions (e.g., returns $0$ or NaN). If the parser omits checks, Python execution could raise exceptions, which the implementation must catch; the paper does not describe a global exception-handling fallback. The training stage (learning non-negative weights on the binary features) can de-emphasize or filter out features that are uninformative or rarely triggered, but that is not a substitute for explicit missing-value handling.

Recommended explicit approach (what you should do if implementing or reproducing FeatLLM). Because the paper leaves this unspecified, best practice is to add explicit instructions to the parsing prompt and/or incorporate a small wrapper around exec() to guarantee deterministic handling:

- In the parsing prompt, require the LLM to include defensive checks like "if value is None or value == '' then return $0$" and to include an explicit else-branch for unseen categorical values (e.g., treat them as non-matching or map to an "UNKNOWN" category).
- Prefer deterministic rule evaluation: treat a rule as false if any referenced feature is missing or cannot be parsed for that sample. This preserves the intended semantics of "satisfies rule" and avoids inflating positives by imputation.
- If domain needs different behavior, ask the LLM to emit code that encodes that policy (for example, impute numeric missingness with median or flag unseen categories as a separate binary indicator).
- Wrap exec() with try/except to catch parser runtime errors and return a decided safe default (commonly $0$) so the pipeline is robust to bad parser outputs.

Suggested one-line prompt additions you can add to the parsing prompt (keeps everything consistent with the paper’s idea of guiding the LLM to output robust code):
"Please generate Python code that returns $1$ if and only if the rule can be confidently evaluated as true; if any referenced feature is missing, null, or cannot be parsed, the code should return $0$; for categorical features not in the provided category list, treat them as non-matching (return $0$)."

Connection to broader concepts. This is the common tension between relying on an LLM to write robust parsers and imposing explicit, auditable fallbacks. The paper leans on the LLM’s ability to produce syntactically tolerant code (and on downstream weight-tuning and ensembling to reduce the impact of noisy rules), but when building a reproducible pipeline you should explicitly encode missing/unseen handling in the parsing prompt or in a protective wrapper to ensure consistent, explainable behavior.

### How are contradictory or overlapping rules across classes handled?
Question:
Because rules are generated independently per class, a sample could satisfy many rules of multiple classes simultaneously. Beyond softmax competition, do you enforce any mutual exclusivity or perform any deduplication/merging of near-duplicate rules across classes? If the same logical rule appears for multiple classes, does that create calibration issues when the number of rules per class is equalized by design?
Answer:
Short answer: FeatLLM does not enforce hard mutual-exclusivity or do automatic cross-class deduplication at rule-generation time. Instead it relies on learning non-negative class weights and ensembling to resolve overlapping or duplicate rules; calibration and redundancy are handled downstream by the linear weighting, the Softmax competition, and ensemble filtering rather than by prohibiting duplicate rules up-front.

Why this works (intuitively + technical details from the paper). During rule generation the LLM is asked to produce a fixed number $R$ of rules per class (the paper uses $R=10$). Each generated rule becomes a binary feature $z_{k,r}^i\in\{0,1\}$ for class $k$ and rule index $r$, and class logits are computed as

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,$$

with class probabilities obtained by a Softmax across the logits. Two consequences are important:

1. Overlap is resolved by learned weights. If the same logical condition appears for several classes (so the same or highly-correlated binary feature contributes to multiple class logits), the downstream training phase learns weights $\mathbf{w}_k$ that set relative importance per class. The Softmax then converts those relative logits into probabilities. In other words, duplicate/overlapping signals are not forbidden — they are allowed to raise multiple logits — and the fitted weights and Softmax decide which class wins for typical inputs.

2. Redundant or spurious rules are downweighted or effectively ignored. Because the model fits weights from the (few-shot) training data, rules that do not help discriminate the target class obtain small weights. The paper also constrains weights to be non-negative (projecting with $\max(\mathbf{w}_k,0)$) so rules cannot actively subtract probability mass; instead, unhelpful rules simply get near-zero weight and have little effect. The authors further use a simple threshold after tuning (e.g., weight $< 0.1$) to consider a rule effectively filtered out.

Why equalizing the number of rules per class was chosen and calibration implications. Fixing $R$ per class avoids trivial class-count biases (e.g., one class having many more candidate rules would bias a naive count-based score). That design removes a source of count-based calibration skew. However, if a single rule is duplicated across classes (or many classes share the same rule), then equalizing counts does not by itself calibrate away the problem — that is handled by the learned weights: the same binary feature can be assigned high weight for the correct class and low weight for others, yielding well-calibrated probabilities via Softmax. In low-shot regimes this learning can be noisy, so the ensemble and bagging strategy is an important robustness mechanism: multiple independent trials (with temperature/randomized demo order and bagging) produce diverse rule-sets, and averaging probabilities reduces the impact of any trial that produced misleading duplicates.

What the paper explicitly does not do (and why). The method does not perform an explicit deduplication/merging step across classes in the rule-generation phase. The authors instead rely on: (a) constrained prompt formats to reduce noisy variations, (b) an LLM-based parsing step to create consistent binary features, (c) weight tuning to suppress irrelevant/duplicate rules, and (d) ensembling with bagging to make the final prediction robust. The ablation studies in the paper show that tuning (learning weights) and ensembling materially improve performance, which empirically supports treating duplication/contradiction via learned weighting and self-consistency rather than hard rule exclusivity.

Practical consequences and limitations. In practice this design means that:
- If the same logical rule inexplicably appears for multiple classes, it will increase logits for those classes; the downstream learner must discriminate via weights. With very few shots this discrimination can be noisy, so ensembling and the post-tuning threshold (filtering low-weight rules) are important safeguards.
- Because weights are constrained to be non-negative, rules cannot act as explicit negative evidence — they can only contribute positive support. That was an intentional design choice (to avoid rules decreasing class likelihoods), but it could limit the model’s ability to represent “this rule argues against class $k$” without explicit negative rules. The paper notes that tuning helps filter irrelevant rules, but does not introduce negative weights or hard exclusivity constraints.

Possible (paper-consistent) extensions. The paper acknowledges future work to improve feature types and interpretability. Natural follow-ups (consistent with the paper’s philosophy) would be: adding a deduplication/merge pass over parsed rules (to avoid literal duplicates or normalized equivalents), allowing signed weights or explicit “negative” rules so rules can subtract support, or adding a small cross-class calibration stage after tuning. These, however, are not part of the current FeatLLM pipeline as presented.

Summary: FeatLLM handles overlapping/contradictory rules not by forbidding them, but by converting rules into binary features and learning per-class non-negative weights plus ensembling. Duplicate rules across classes are resolved through the learned weights and Softmax competition; empirical safeguards (weight thresholding and ensembling) reduce calibration and spurious-rule effects in the few-shot regime.

### Why is temperature 0.5 considered "sufficiently high" for self-consistency?
Question:
For ensemble diversity you cite self-consistency and set the LLM temperature to 0.5. Self-consistency papers often use relatively high sampling variance and large sample counts. Did you empirically verify that $T=20$ trials and temperature 0.5 yield sufficiently diverse rule sets (e.g., Jaccard distance across rule predicates)? Are there metrics in the appendix quantifying diversity vs. performance?
Answer:
Short answer: $0.5$ was chosen as a pragmatic middle ground that produces meaningful stochastic variation without making the LLM outputs incoherent, and this choice was validated empirically in the paper. We report ensemble-size and diversity analyses in the Appendix showing that (a) performance gains saturate around $T = 20$ trials, and (b) the rule-sets produced at temperature $0.5$ are sufficiently diverse for the ensemble to improve robustness while retaining rule quality.

Why $0.5$ (intuitively)
Temperature controls sampling randomness: very low values (near $0$) make the model nearly deterministic and produce little ensemble diversity, while very high values produce many low-quality or nonsensical outputs. A mid-range temperature like $0.5$ injects useful variability (different but still coherent rule formulations and thresholds) so that the ensemble benefits from multiple complementary hypotheses without being overwhelmed by noise. In other words, $0.5$ aims to sit in the regime where sampling explores plausible alternative reasoning paths (needed for self-consistency) while preserving the LLM’s internal priors so that generated rules remain parseable and useful.

What the paper actually did (empirical grounding)
The paper sets temperature $= 0.5$ and number of ensemble trials $T = 20$ in the main experiments (Implementation details). It refers explicitly to Appendix material for analyses of rule diversity and hyper-parameters (see Appendix sections referenced as hyperparameter analysis and Appendix~\ref{sec:diversity}). Concretely, the paper reports:

- An ensemble-size sweep (Fig. in Appendix): performance improves with more trials and starts to converge around $20$ ensembles, which motivated $T = 20$ as a cost-effective choice.
- A hyper-parameter study (Fig. in Appendix) showing that changing the number of rules per trial has limited effect compared to ensemble size, and that ensemble benefits are realized with the chosen temperature.
- A diversity analysis (Appendix~\ref{sec:diversity}): the authors quantify rule-set variability across trials and show that only a small fraction of rules are identical across runs, while many rules are distinct but still informative. They further report the proportion of generated features that have AUROC $> 0.5$ before and after tuning (Table~\ref{tab:quality}), indicating that the majority of sampled rules at $T = 20$, $T = 0.5$ are useful, and the tuning step filters out low-quality/noisy ones.

Metrics used to quantify diversity vs performance
The Appendix analysis provides the following types of metrics (summarized from the paper’s appendices and tables):

- Ensemble performance curve vs number of trials (shows saturation around $20$).
- Rule quality statistics: fraction of generated binary features with AUROC $> 0.5$ (reported Before/After tuning in Table~\ref{tab:quality}).
- Counts/fractions of rules coming from spurious/noisy columns in the spurious-correlation experiment (the paper notes only $1$–$2\%$ of rules were based on noisy columns).
- Implicit measures of rule diversity: overlap statistics across trials (reported in Appendix~\ref{sec:diversity}), which show substantial but not excessive variation in predicates and thresholds.

These combined results indicate that temperature $= 0.5$ produces enough diversity (as measured by rule overlap and unique-rule counts) to improve ensemble performance, while the downstream tuning stage prunes low-utility features, preserving final model accuracy.

Practical trade-offs and why they didn’t pick much higher $T$
The choice balances three factors: ensemble benefit vs API cost, rule quality vs randomness, and prompt parsing reliability. Raising temperature further would likely increase unique rule count but at the cost of more syntactic noise (harder parsing) and more low-quality rules that the tuning step must filter—raising API calls or hurting final accuracy. The paper’s experiments suggest the marginal performance gains beyond $T = 20$ and at higher temperatures were not worth the extra noise and cost.

If you want to probe further
If you care about a stricter diversity metric (e.g., Jaccard distance over predicate sets, normalized edit distance over parsed rules, or mutual information between rule-sets), you can reproduce that analysis from the authors’ code (the repo is referenced) by sampling at multiple temperatures (e.g., $0.2, 0.5, 0.8, 1.0$) and computing per-trial pairwise Jaccard on parsed predicates and AUROC distributions. That will show the precise trade-off for your dataset and LLM backbone.

Summary
Temperature $= 0.5$ was not arbitrary: the paper reports (in the Appendix) diversity and hyper-parameter analyses showing that $20$ trials at $T = 0.5$ give sufficient diversity to improve ensemble performance while keeping rules coherent and parsable. Higher temperatures or many more trials give diminishing returns and increase noise and cost.

### How is the reported "only 30 API queries" computed given T=20 ensembles?
Question:
Implementation details mention $T=20$ ensembles and rule parsing via the LLM, but the runtime section says FeatLLM requires only 30 API queries. Can you break down the exact number of calls per trial for rule generation and for code parsing, and explain how it aggregates to 30 overall? Are multiple rules or classes batched into a single call?
Answer:
Short answer: the paper’s “only 30 API queries” is counting one LLM call per ensemble trial to generate rules plus a smaller number of additional parsing calls because rule-to-code parsing is batched. Concretely, with $T = 20$ they make $\sim 20$ rule-generation calls (one per trial) and roughly $\sim 10$ parsing calls (each parsing call converts a batch of generated rules into executable code), giving $20 + 10 = 30$ total. The paper does not give an exact per-dataset call-by-call log, so 30 is an implementation-level, practical accounting that assumes batching of many rules/classes into single parsing queries.

Why this is the most natural reading of the paper
- The paper describes two distinct LLM stages: (A) rule extraction (the main prompt that asks the LLM to infer the relationship and produce rules), and (B) parsing those natural-language rules into small executable code snippets that produce binary features. Each of these stages requires an LLM API call in principle.
- The ensemble dimension $T = 20$ is explicitly the number of repeated runs of the “entire process” to produce diverse rule sets, so you naturally expect at least one rule-generation call per trial → $20$ calls.
- The parsing stage is described as taking the inferred rules and asking the LLM to output simple code (the prompt includes function name, I/O descriptions and the inferred rules). Because parsing is code-generation over text that is already produced, it is reasonable and economical to batch many rules (across classes and/or across trials) in fewer API calls rather than issuing a separate parse call per rule. The paper states they “leverage the LLM itself” for parsing and shows prompt examples that combine multiple rules in one prompt (Appendix), which supports the idea of batching.

How the 30 can be broken down in practice (explicit calculation)
- Rule generation: 1 call per ensemble trial × $T = 20$ calls.
- Parsing into code: group many rules into batches and parse each batch with one call. If you parse all generated rules using $\sim 10$ batched parsing calls you get 10 parsing calls.
- Total = $20 + 10 = 30$.

Why batching is important and how it’s done intuitively
- Each rule-generation response already contains multiple rules (the paper fixes $10$ rules per class). Because the LLM’s parsing prompt can accept multiple rules as input and produce a code block that implements them all, you don’t need to parse each individual rule with a separate API call.
- For example, if each trial yields rules for all classes (say a handful of rules per class) you can assemble the rules from several trials or from all classes into one parsing prompt that asks “turn these $N$ rules into a Python function that returns these binary features.” That single parsing response can then be exec()’d to produce many features at once.
- Batching reduces API count and cost. The paper’s 30-query statement is a cost-friendly accounting that assumes such batching is used.

Caveats and how to compute for your setting
- The precise number depends on implementation choices: whether you do one parse call per trial, one parse per class, or one parse for all rules across all trials. If you use the simplest but more expensive approach (rule-gen + parse per trial), cost = $2 \times T = 40$ calls for $T = 20$.
- The paper’s 30 is therefore an empirical / implementation number, not a hard theoretical lower bound. To reproduce: count 1 rule-generation call per trial, then choose a batching strategy for parsing (the paper’s numbers correspond to batching that results in $\sim 10$ parsing calls).
- To compute for your dataset: (# of rule-gen calls = $T$) + (# of parse calls = $\lceil \text{total number of rules to parse} / \text{rules-per-parse-prompt} \rceil$). Total number of rules = $T \times (\text{rules per class} \times \text{classes})$ if you don’t deduplicate across trials; but you will typically parse many rules together, so the parse-call denominator (how many rules you pack into one parse prompt) is the key factor.

Practical recommendation
If you want the same cost profile as reported, implement one rule-generation call per ensemble trial and then parse the produced rules in batched prompts (e.g., parse rules for several trials and/or all classes together). That yields roughly $20$ rule-gen + $\sim 10$ batched parses = $30$ API queries as reported. If you do not batch, expect closer to $2T$ calls ($40$ for $T = 20$).

### Does enforcing non-negativity hinder learning from negative evidence in few-shot settings?
Question:
The rationale for non-negative weights is that LLM-generated features should not reduce a class's likelihood. But in few-shot regimes, false-positive rules may be common. Would allowing negative weights help the model suppress noisy rules more aggressively than relying on weights approaching zero? Did you test a variant with signed weights and $L_1$ regularization to prune bad rules?
Answer:
Short answer: Yes — enforcing non-negativity does limit the model’s ability to assign an explicit negative weight to a rule, so it cannot directly “penalize” a class when a (false‑positive) rule fires. In practice the paper chose non‑negative projected weights to ensure generated rules only increase class evidence and to keep the downstream model simple and interpretable; ensemble bagging, the learned positive weights, and post‑tuning filtering (they thresholded weights at 0.1) are used to suppress noisy rules. The authors did not report experiments with signed weights + explicit sparsity regularization in the paper, but this is a natural ablation to run. Below I explain the tradeoffs, intuition, and a concrete experiment you can run.

Why non‑negativity was used and what it changes
The paper projects each linear weight vector into the positive orthant and computes logits by
$$\text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,$$
so every generated binary rule can only increase the logit for the class when it is satisfied. Intuitively this matches the framing the authors want: LLM‑crafted rules are “evidence for” classes (interpretable, additive cues). This has three consequences relevant to your question.

1) If many false‑positive rules are generated in few‑shot data, non‑negative weights cannot assign a negative coefficient to directly cancel that rule’s effect. Instead the optimization can only reduce its positive weight toward zero (or leave it near zero), or rely on other rules for competing classes to outscore it via softmax.

2) The paper mitigates noisy rules with (a) ensemble/bagging across multiple LLM runs (so spurious rules are rare across runs), (b) tuning the weights from few samples so irrelevant rules end up with near‑zero learned weights, and (c) a post‑tuning threshold that effectively prunes rules with tiny weights. They report that noisy columns produced only ~1–2% of rules and that tuning filters out many uninformative rules (Table on feature quality, “Before tuning” vs “After tuning”).

3) The non‑negative choice promotes interpretability (rule → positive evidence) and prevents a learned rule from being used as a deceptive negative signal that might reflect overfitting to a tiny sample.

Would allowing signed weights plus L1 help?
Allowing signed weights and using an L1 penalty is a reasonable alternative and could help suppress false positives more aggressively: negative weights give the model direct subtractive power, and L1 encourages sparsity so truly spurious rules can be driven to exactly zero. However, there are tradeoffs in the low‑shot regime:

- Pros: Signed weights let the model actively counteract bad rules instead of only shrinking them; L1 can prune many noisy features and produce sparser, potentially better generalizing models when rules are plentiful and many are spurious.
- Cons: With very few labeled examples, negative weights can cause instability and overfitting — the model may fit noise by assigning large magnitude negative weights to a few examples. L1 helps but may not fully prevent variance in the learned signs across different random few‑shot splits. Also, allowing negatives weakens the interpretability constraint “rule implies evidence for class”, which was a design choice in the paper.

Did the paper test signed + L1? Recommendation for experiments
The paper’s ablations (Section 4.2) evaluated the importance of tuning, reasoning, descriptions, and ensembling, and they show tuning helps; they did not report a variant that replaces the positive projection with unconstrained signed weights and an explicit L1 penalty. If you want to test this idea, use the same few‑shot setup and ensemble process the authors used, and compare three variants:

1. Baseline (paper): non‑negative projection, no L1, same optimizer and training epochs.
2. Signed weights: remove the $\max(\cdot, 0)$ projection so logits become $\mathbf{w}_k\cdot \mathbf{z}_k^i$; train with the same cross‑entropy objective.
3. Signed + L1: as (2) but add an L1 term $ \lambda\sum_{k,j} |w_{k,j}|$. Sweep $\lambda$ over e.g. $\{1\mathrm{e}{-4}, 1\mathrm{e}{-3}, 1\mathrm{e}{-2}, 1\mathrm{e}{-1}\}$.

Use the same optimizer (Adam, $\text{lr}=0.01$), epochs ($200$ with k‑fold selection as in paper), and ensemble count (e.g. $T=20$). Evaluate robustness in two settings emphasized in the paper: (A) standard few‑shot splits ($4/8/16$ shots) and (B) spurious‑column stress test (attach irrelevant columns from another dataset as in their Fig. 5). Measure AUC, weight distributions (histogram of learned $w$’s), number of zeroed features, and variance across repeats.

Practical alternative to get subtractive behavior without signed weights
If you want to retain the interpretability constraint but still capture “negative evidence” effects, one pragmatic approach consistent with the paper’s pipeline is to ask the LLM to explicitly generate “contra‑rules” or “rules indicating not‑class” (i.e., rules that predict the opposite class) and include them as separate binary features. The non‑negative model can then give positive weight to these “not‑class” rules for a class, which effectively acts like subtractive evidence when you compare logits across classes via softmax. This keeps the original design philosophy while permitting “negative signals” via complementary features.

Bottom line
Enabling signed weights with L1 is a plausible modification that may improve suppression of noisy, false‑positive rules — but in few‑shot settings it risks higher variance and overfitting unless you carefully tune $\lambda$ and validate across splits. The paper did not report this exact ablation; their chosen defenses against noisy rules were ensembling, tuning to shrink uninformative rule weights toward zero, and post‑tuning thresholding. If you test the signed+L1 variant, evaluate both average AUC and robustness (variance across few‑shot draws and spurious‑feature stress tests) to see whether the extra flexibility yields consistent gains.

### Is training for 200 epochs on very few shots prone to overfitting?
Question:
You train the linear model for 200 epochs with Adam and choose the epoch via $k$-fold cross-validation on the few shots. With $k$ as small as 2, the validation split is tiny and high-variance. Did you consider early stopping with a patience heuristic, or using explicit regularization (e.g., $L_2$ or $L_1$) to stabilize learning? Any sensitivity analysis on epochs vs. AUROC with $k\in\{2,4\}$?
Answer:
Short answer: You’re right to be concerned—training any model for $200$ epochs on very few examples can overfit, and the paper does not report explicit early stopping or explicit L1/L2 regularization. The authors mitigate overfitting implicitly (small model, positive-weight constraint, cross-validation for epoch choice, bagging/ensembling), but they do not present a sensitivity curve of epochs vs AUROC for $k\in\{2,4\}$. I summarize what the paper does, why that helps (and where it can be fragile), and give practical diagnostics and remedies you can try.

What the paper actually does
The linear downstream model in FeatLLM is extremely small: it learns nonnegative weights (they apply $\max(w,0)$ in Eq. (1)) over binary rule-features, with no bias term. The paper trains with Adam ( $lr = 0.01$ ) for $200$ epochs but then “uses $k$-fold cross-validation for optimal epoch selection” where $k$ is set to $2$ or $4$ so that each fold still contains at least one example of every class. They also rely heavily on ensembling ($T\approx 20$ trials) and bagging to reduce variance and to average out poor rule sets. The hyper-parameter studies reported focus on number of ensembles and number of rules; the authors note performance saturates around $20$ ensembles and choose $10$ rules/class as a trade-off (they also mention that increasing rules can increase overfitting in low-shot regimes). However, the paper does not show an explicit epochs-vs-AUROC sensitivity plot for $k=2$ or $k=4$, nor does it report experiments with explicit L1/L2 regularization or early-stopping-with-patience.

Why these design choices partly mitigate overfitting (intuition + technical)
1) Very low-capacity model. A linear model on binary rule features has far fewer free parameters than deep nets; with $R$ rules per class and $c$ classes the parameter count is small, so the tendency to overfit is reduced relative to higher-capacity models.  
2) Nonnegativity projection. Forcing weights to be nonnegative reduces the parameter space and prevents the model from using negative weights to over-explain noise—this is a mild regularizer.  
3) Cross-validation for epoch selection. Selecting the epoch by CV is a form of early stopping (choosing the epoch that best generalizes on held-out folds). That said, when $k$ is $2$ the validation fold is tiny and high-variance, so the selected epoch can itself be noisy.  
4) Ensembling & bagging. Averaging $T$ independently-generated rule-sets and their downstream weights reduces variance: even if one trial overfits, aggregation can dampen its effect.

Where fragility remains
With $k=2$ the CV signal is noisy: a single mislabeled or atypical sample in the validation fold can push you to select an epoch that fits noise. Adam with a fairly large learning rate ($0.01$) and $200$ epochs can still find parameter settings that overfit even for a small linear model, especially if the number of rules (features) is not tiny relative to $k$. The paper itself notes that increasing the number of rules increases input dimensionality and may lead to overfitting in low-shot settings.

Practical suggestions / things I would try (concise)
1) Explicit early stopping with patience on validation AUROC instead of picking a single best epoch from $2$-fold CV. Use repeated CV (repeat the $k$-fold splitting several times) to reduce variance in the stopping signal.  
2) Add L2 (weight decay) or L1 regularization to the linear weight updates. L2 is a natural default; with very few samples a small weight decay (e.g., $10^{-3}$ to $10^{-2}$) often stabilizes training. L1 can help sparsify rule weights and improve interpretability.  
3) Use smaller learning rate and/or switch to SGD with momentum for more stable convergence; Adam can sometimes overfit quickly on tiny data. Try $lr \in \{10^{-2},10^{-3},5\times10^{-4}\}$.  
4) Reduce the number of training epochs and combine with the early-stopping heuristic (e.g., max epochs $200$ but stop if no val-AUROC improvement after $10$--$20$ epochs). With high-variance CV include patience to avoid reacting to single-epoch spikes.  
5) Increase $k$ (if possible): when feasible use $k=4$ rather than $k=2$, or do repeated random splits and aggregate results to reduce the impact of any single small validation fold.  
6) Report sensitivity curves: plot AUROC vs epoch for multiple random splits and show mean ± std for $k=2$ and $k=4$. That directly answers whether performance is stable or oscillatory.  
7) Regularize per-feature: if many rules are generated, add a per-class L1 penalty to encourage sparse selection of only the most useful rules—this also mirrors the paper’s observation that tuning filters weak rules.  

Minimal experiments to run (to satisfy your question empirically)
Run the downstream training under these variants: (A) baseline (Adam $lr=0.01$, $200$ epochs, CV epoch selection as in paper), (B) baseline + early stopping with patience $10$ on AUROC, (C) baseline + L2 (weight decay $10^{-3}$), (D) baseline + LR=$10^{-3}$, (E) baseline + L1 ( $\lambda$ tuned). For each variant plot AUROC vs epoch averaged over $10$ random seeds with $k=2$ and $k=4$. That will show whether early stopping or explicit regularization stabilizes and improves generalization in the very low-shot regime.

Conclusion
The paper does rely on several implicit regularizers (small model, nonnegativity, CV epoch selection, ensemble bagging) which reduce but do not eliminate the risk you pointed out. The authors do not report explicit early-stopping-with-patience or L1/L2 regularization experiments, nor do they show epochs-vs-AUROC curves for $k\in\{2,4\}$. To be confident, run the small diagnostic experiments above—early stopping with patience and modest L2 are low-cost, high-impact mitigations for noisy few-shot CV.

### How fair are the baseline comparisons given different LLM backbones and resources?
Question:
TabLLM is run with T0 (not GPT-3.5) due to checkpoint availability, and it uses 4 A100s for model parallelism, while FeatLLM uses GPT-3.5 via API. Could differences in backbone strength and hardware budgets bias the comparisons? Did you include any control where TabLLM or TABLET use the same LLM inference quality (to the extent possible)?
Answer:
Short answer: Yes, differences in LLM backbone and compute can bias comparisons, and the paper acknowledges this. The authors mitigate it where possible (they run FeatLLM and the in‑context/TABLET baselines with GPT‑3.5 via API) but cannot make TabLLM use the same GPT‑3.5 backbone because TabLLM in the original design requires a publicly available checkpoint (so they used T0 for TabLLM). They also report hardware and runtime differences (TabLLM used 4 A100s for model‑parallel tuning; FeatLLM uses only API calls and much less inference compute). The paper includes some experiments varying backbones in the Appendix to show backbone sensitivity, but there is no perfect one‑to‑one control where TabLLM (or TABLET) is run with exactly the same LLM checkpoint and identical hardware budget as FeatLLM.

Why this matters and what the paper does about it
The core concern is that stronger LLMs (e.g., GPT‑3.5) can (and empirically do) produce higher‑quality reasoning/rules than weaker publicly available models (e.g., T0). That advantage can inflate methods that rely on the LLM for per‑sample inference or rule generation. The paper states explicitly that:

- FeatLLM, In‑context learning, and TABLET were evaluated using GPT‑3.5 (API) where feasible.
- TabLLM was evaluated with T0 following TabLLM’s original constraint that it only uses LLMs with public checkpoints; GPT‑3.5 is not available as a checkpoint so it could not be used.
- TabLLM required model parallelism on 4 A100 GPUs for training, which they report in the runtime/cost table. FeatLLM only needs a small number of API queries (30 per trial) and has low inference cost because once features are generated the downstream model is small and local.

They also report backbone sensitivity experiments in the Appendix (the paper says “see Appendix Section~{sec:backbones} for results with different backbones”), which is the main control they provide to show how much choice of LLM affects results.

Interpretation and remaining caveats
Because TabLLM could not be run with GPT‑3.5, comparisons against TabLLM risk conflating two factors: the algorithmic idea (parameter‑efficient tuning vs. FeatLLM’s feature engineering) and the raw LLM capability (T0 vs GPT‑3.5). The authors are transparent about this limitation and give three pieces of evidence to help readers judge fairness: they (1) use GPT‑3.5 for the baselines where API access is possible (In‑context, TABLET, FeatLLM), (2) report runtime and hardware used for TabLLM versus other methods, and (3) include backbone‑variation experiments in the Appendix to demonstrate sensitivity to model choice. Still, there is no experiment that runs TabLLM with GPT‑3.5 checkpoint (impossible due to availability) or artificially downgrades FeatLLM to T0 to give a perfectly matched compute/backbone comparison.

What would be an ideal control (if you want to test this yourself)
A clean way to isolate algorithmic benefits from backbone strength would be one of the following: (a) run all LLM‑based methods with the same LLM checkpoint (e.g., GPT‑3.5) and identical prompt / inference budget, or (b) run FeatLLM and the other baselines with a weaker public model (e.g., T0) so that the LLM capability is matched, and then compare. Because GPT‑3.5 is not available as a public checkpoint, option (a) wasn’t possible for TabLLM; option (b) is feasible and would quantify how much of FeatLLM’s advantage comes purely from backbone strength. The Appendix backbone experiments partially address this, but a dedicated matched‑backbone ablation (FeatLLM with T0 vs TabLLM with T0, same hardware/inference budget) would be the clearest control.

Bottom line
The paper acknowledges the potential bias, uses GPT‑3.5 for FeatLLM and most LLM baselines where possible, reports TabLLM’s different setup (T0 + 4 A100s), and provides backbone sensitivity results in the Appendix. However, because of checkpoint availability constraints there is no perfect one‑to‑one control that fixes both LLM checkpoint and hardware budget across every LLM‑based method; as a result, some portion of the performance gap may be due to backbone strength rather than only the algorithmic differences.

### How robust is FeatLLM to label imbalance and classes needing different numbers of rules?
Question:
The method fixes the number of rules per class (e.g., $R=10$). If classes differ in complexity or support, a uniform $R$ might be suboptimal. Do you observe any degradation when some classes need far fewer (or more) rules? Did you try adaptive rule counts per class or pruning redundant rules post-generation while keeping the prompt size manageable?
Answer:
Short answer: FeatLLM is reasonably robust to per-class differences in how many rules are needed, but it does not explicitly adapt the number of rules per class within a single LLM query. The paper fixes $R = 10$ per class because it balanced prompt size and performance; empirical analyses show limited sensitivity to $R$ and mechanisms in the pipeline (weight tuning + ensembling) implicitly handle redundant or missing rules. The authors did not report an explicit adaptive-per-class rule generation procedure, but they do use pruning via learned weights and ensemble/bagging to effectively increase/diversify the pool of candidate rules.

Why this works (intuitive + technical):
- Redundant rules are downweighted during training. FeatLLM turns each generated rule into a binary feature and fits a simple linear model with non-negative weights (Eq. $(1)$). During few-shot tuning the model learns which binary features actually help predict the label; irrelevant or redundant rules receive weights near zero. The paper reports that after tuning a substantial fraction of low-value rules are filtered automatically (they used a threshold of $0.1$ in their analysis of “useful” features).
- Ensemble and bagging provide coverage and diversity. Although each LLM query produces $R$ rules per class, the authors run $T$ trials ($\sim 20$) with randomized prompts/temperature and bagging. This produces many distinct candidate rules across trials; even if a single trial's $R$ is insufficient for a complex class, the ensemble aggregates diverse rules so that collectively many useful rules are considered. Empirically, performance improved with more ensembles up to a saturation point (around $20$).
- Empirical insensitivity to $R$. The paper’s hyperparameter study found no strong statistical difference across moderate $R$ values, and chose $R = 10$ as a practical trade-off between prompt length and information. They also observed a tendency toward overfitting when $R$ was made large in the low-shot regime, which supports keeping a bounded $R$.
- Robustness to spurious/noisy features. In experiments with many irrelevant columns attached, FeatLLM showed the least degradation among baselines; only $\sim 1$–$2\%$ of generated rules were based on noisy columns. That suggests the LLM+reasoning prompt plus the downstream weight tuning prevents proliferation of useless rules.

What the paper did not do (and therefore did not report):
- The authors did not implement or evaluate an explicit adaptive $R$ per class at generation time (e.g., asking the model to output a variable number of rules per class or run a stopping criterion inside a single prompt).
- They did not report a structured post-generation pruning step other than relying on learned weights (and the thresholding analysis). They parse and execute rules and then tune weights; pruning is effectively done by discarding features with small learned weights.

Practical implications and simple extensions you can try (consistent with the paper’s framework):
- Post-generation pruning by learned weight: after fitting the linear model, keep only rules with weight $>$ threshold (they used $0.1$ in analysis). This is simple and already aligns with the paper’s tuning+filtering behavior.
- Aggregate across ensembles: instead of using all rules equally, collect rules from $T$ trials and rank them by frequency of occurrence across trials or by mean learned weight; keep a per-class top-$k$. This leverages the ensemble diversity the paper already generates.
- Adaptive generation in two passes: run an initial small-$R$ pass to identify important features, then ask the LLM to propose additional rules only for classes that still have low coverage or low validation performance. This respects the paper’s concern about prompt length (you only generate more when needed).
- Iterative pruning/refinement: alternate between generating rules, fitting weights, pruning low-weight rules, and asking the LLM to refine or combine the remaining rules. This would be an extension of the paper’s pipeline but is compatible with its parsing + exec-based rule application.

Suggested experiments to validate sensitivity in your own setting (straightforward because they fit the paper’s setup):
- Vary $R$ (e.g., $4$, $10$, $20$) and measure per-class AUC or per-class recall to see whether some classes disproportionately suffer when $R$ is small.
- Track learned-weight sparsity per class to quantify how many rules per class are effectively used (weight $> 0.1$) under different $R$ and $T$.
- Measure how many unique rules for a class appear across $T$ ensemble trials; this tells you whether ensemble diversity compensates for fixed $R$ per trial.

Bottom line: FeatLLM uses fixed $R$ per class in each query, but the combination of learned-weight pruning and ensemble/bagging effectively mitigates problems when classes require different numbers of rules. The paper did not evaluate a fully adaptive per-class rule-count generator, but simple extensions (post-pruning, aggregating rules across trials, or two-pass generation) are natural next steps consistent with the framework.

### What exactly is the selection policy for feature/instance bagging across trials?
Question:
Bagging is central both for diversity and to fit within prompt limits. Could you specify:
- How many features and examples are sampled per trial as a function of dataset size and column count?
- Whether sampling probabilities are uniform or weighted by any heuristic (e.g., Step-1 importance)?
- If you ever exclude feature descriptions to save tokens, and how you decide when to do so?
Answer:
Short answer: the paper does not define a fixed analytic formula for how many features or examples are sampled per trial — instead it uses simple randomized bagging to reduce prompt size and increase diversity, sampling subsets of features/instances uniformly at random (no weighting by Step‑1 importance), and it keeps the feature descriptions for whichever features are included in a trial (it does not drop descriptions selectively except as a means to reduce prompt length by choosing fewer features). The only explicit numeric choices reported are: ensemble size $T = 20$, number of rules extracted per class $R = 10$, LLM temperature = $0.5$, and the usual $k$‑shot training split ($k$ varies by experiment). See details and code for the precise sampling thresholds used in experiments.

Explanation and evidence from the paper
The authors describe bagging primarily as a pragmatic mechanism with two goals: (1) introduce randomness/diversity across trials so erroneous rules in some trials are compensated by correct rules in others, and (2) keep prompts small enough to fit the LLM context window when datasets have many features or many shot examples. Concretely, the paper says they “adopt bagging to select a subset of features or instances for each trial” and that bagging “helps reduce [prompt] size, ensuring the model’s robust performance.” This is implemented as randomized selection; the paper emphasizes randomness (high temperature, randomized ordering of demonstrations) as the diversity source.

What is stated explicitly
- Ensemble and rule counts: $T = 20$ trials; $R = 10$ rules per class (these are fixed hyperparameters used throughout experiments).  
- Randomization: they set a nonzero temperature for LLM sampling ($0.5$) and randomize demonstration order across trials to diversify rule generation.  
- Bagging is described as selecting a subset of features or instances per trial; this selection is presented as random (i.e., bagging-style), not as a deterministic heuristic.  
- No mention of sampling probabilities weighted by any internal heuristic (e.g., Step‑1 inferred importance) — the paper frames Step‑1 (reasoning) as something used inside the prompt to encourage the LLM to prefer relevant features during rule extraction, not as a precomputed importance score used to bias sampling across trials. In other words, feature importance influences rule content via the LLM’s internal reasoning in a trial, but the bagging selection that chooses which columns or examples are included in a trial is described as random bagging, not importance‑weighted sampling.

What is not specified (and where to look)
- There is no explicit formula mapping dataset size or column count to the number of features/examples sampled per trial (e.g., “sample $\min(d, m)$ features” or similar). The paper only states the motivation (fit prompt size) and that bagging reduces prompt length by selecting subsets. That implies an implementation choice: pick a subset small enough that the serialized prompt (feature descriptions + $k$ demo examples + reasoning instructions) fits the LLM token budget. The exact thresholds (how many tokens or features they permit before truncating) are not given in the main text; they refer the reader to the released code (GitHub) and to appendices for extended experiments. If you need the precise sampling sizes used for each dataset/run, check the repository or Appendix (the authors say code is released and appendices contain more implementation details).

Feature descriptions and token saving
The prompt design puts feature descriptions in the “basic information” section and the ablation study shows that omitting feature descriptions hurts performance (the “-Description” ablation degrades AUC). Therefore the intended behavior in the paper is to include descriptions for the features that are part of the trial. The paper doesn’t describe a policy of dropping descriptions for included features as a separate token‑saving tactic; instead the practical way to save tokens is to bag fewer features in that trial so you only include descriptions for that subset. In short: they do not propose excluding descriptions of selected features as a standard heuristic, because those descriptions materially help LLM rule generation.

Practical interpretation / what I’d check in the code
Given the paper’s wording, the experimental implementation likely does this:
- For each trial $t = 1,\dots,T$, uniformly at random sample a subset of feature columns (and possibly a subset of training instances if needed) whose serialized token length keeps the prompt under the LLM context limit; include the feature names/types/descriptions for those sampled columns and $k$ example serializations drawn from the available shots (with randomized order).  
- Query the LLM with the reasoning + response instructions to get rules ($R$ per class).  
- Parse rules to code and generate binary features for the chosen subset.  
So if you want exact numbers used for a particular dataset, inspect the repository or the appendix scripts: they will show how many columns were sampled per trial for datasets with many attributes (the paper mentions datasets with $>100$ attributes, where bagging is necessary).

If you want guidance
If your goal is reproducibility or to tune bagging for different dataset sizes, use a simple rule: pick the largest subset of features such that the serialized prompt (feature descriptions + $k$ examples + reasoning instructions + expected rule output) stays comfortably under your LLM’s token limit. Sample that subset uniformly at random each trial. If you want to bias sampling toward potentially important columns, you can experiment with importance‑weighted sampling (e.g., use simple univariate scores or the LLM’s Step‑1 judgments aggregated from a small pilot run) — the paper does not explore this, but it is a reasonable extension to trade off diversity vs. focused coverage.

Summary
The paper’s bagging policy is randomized (uniform bagging) to control prompt size and to induce ensemble diversity, with $T = 20$ trials and $R = 10$ rules/class as their reported choices. They do not report a closed‑form function mapping dataset size/column count to the number of sampled features; instead they apply bagging to pick subsets that keep prompts within the LLM context window and keep feature descriptions for the sampled columns rather than omitting descriptions as a separate strategy. Check the released code/appendix for the exact implementation details used in the experiments.

### How do you validate that Step-1 reasoning actually reduces spurious correlations?
Question:
You claim Step-1 (prior knowledge only) helps avoid spurious correlations. Beyond the synthetic spurious-column experiment, did you analyze the textual content of Step-1 vs. final rules to show that Step-1 emphasizes causal features? For example, are there metrics showing increased overlap between Step-1 highlighted features and the final rule predicates, or reduced use of irrelevant features compared to a baseline without Step-1?
Answer:
Short answer: the paper does not report a direct textual/content-level analysis that quantifies how the Step‑1 reasoning text (the “prior-knowledge only” stage) overlaps with or causally drives the final extracted rules. Instead, the paper provides indirect, empirical evidence that the two‑step design reduces spurious correlations: an ablation that removes Step‑1 hurts AUC, a spurious‑column experiment shows only ~$1$–$2\%$ of generated rules reference randomly-attached noisy columns, and a per-rule quality analysis (AUROC of generated binary features, before/after tuning) shows most rules are informative and that tuning filters out irrelevant rules. The authors also note (Appendix) qualitative analyses and a caution that closely related but irrelevant columns can still mislead the LLM.

Why this matters and what the evidence shows. The paper’s main claims about Step‑1 are supported by three complementary findings rather than a textual overlap metric:

1) Ablation: removing the reasoning instruction’s Step‑1 produces a measurable drop in AUC (reported in Table 8/ablation summary). This indicates that prompting the LLM to first state general relations between features and the task (prior knowledge) improves downstream predictive performance, consistent with Step‑1 helping to avoid spurious correlations.

2) Spurious‑column experiment: when unrelated columns from another dataset are appended to the Heart dataset, FeatLLM degrades far less than baselines. The authors additionally counted how many generated rules referenced those noisy columns and found only ~$1$–$2\%$ involvement, which suggests the rule generator largely ignores obviously irrelevant features when Step‑1 is present.

3) Rule quality/AUROC: the paper measures per-rule informativeness (AUROC of each binary rule feature vs. target) and shows most rules are $>0.5$ AUROC before tuning, and tuning further prunes irrelevant rules (weights below threshold). This demonstrates the extracted rules are generally aligned with predictive signal.

What is not in the paper. The authors did not present a direct, quantitative content analysis that (for example) computes overlap between Step‑1 highlighted features and the final parsed predicates, nor did they produce a metric that explicitly labels rules as “causal” vs “spurious” and measures Step‑1’s concentration on the causal set. There is also no automated salience/attribution analysis (e.g., token-level overlap, Jaccard similarity, or mutual information between Step‑1 mentions and rule predicates) reported.

If you want to validate the causal emphasis of Step‑1 more directly, doable follow-ups (that are consistent with the paper’s setup) include: compare which features are mentioned in Step‑1 text vs. which features appear in final parsed rules and compute frequency or Jaccard overlap; compute the per-feature change in rule-generation probability when Step‑1 is omitted; measure per-rule AUROC stratified by whether the feature was mentioned in Step‑1; have human annotators label rules as “plausibly causal” vs “spurious” and test whether Step‑1 increases the fraction labeled causal; or perform conditional independence / causal discovery tests (e.g., partial correlations, propensity‑score balancing) to see if rules derived after Step‑1 align better with causal predictors than those from a single-step prompt. A complementary automated approach is to use counterfactual perturbation: perturb candidate features in held-out data and check which rules’ binary outputs change consistently with target changes — rules that change correctly are more likely causal, and you can test whether Step‑1 increases their prevalence.

Summary. The paper supports the claim that Step‑1 reduces spurious correlations via ablation, spurious‑column robustness, and per-rule AUROC/tuning analyses, but it does not include a direct textual/overlap metric between Step‑1 content and final rules. If you need a closer, causal-textual validation, the practical follow-ups above would provide the more direct evidence you’re looking for.

### How do you control for leakage when using recent datasets to avoid pretraining overlap?
Question:
For Cultivars and NHANES, you argue they post-date GPT-3.5-0613 pretraining. However, exact pretraining cutoffs and data sources are opaque. Did you also test with synthetic feature descriptions (to avoid web-retrieved wording), or ablate feature descriptions entirely to ensure performance is not driven by memorized text? Any reproducible checks for leakage you can share?
Answer:
Short answer: Yes — the paper documents several steps to reduce and check for pretraining leakage, and it includes an explicit ablation that omits feature descriptions (the main textual channel by which pretraining memorized wording could help). The experiments also use recent and synthetic datasets that are unlikely to have been seen by the GPT-3.5-0613 pretraining corpus. The paper did not report a dedicated experiment that replaces all human feature descriptions with entirely synthetic/paraphrased descriptions, but it did include the -Description ablation and used synthetic datasets as a stronger leakage control. Below I summarize what was done in the paper, what that implies about leakage, and practical, fully reproducible checks you can run if you want stronger guarantees.

What the paper already did (and why it helps)
1. Dataset choice. The paper evaluates on two datasets (Cultivars, NHANES) that the authors state were added to UCI after September 2023, i.e., after the GPT-3.5-0613 pretraining cutoff claimed in the paper. In addition, two synthetic datasets (Sequence-type and Solution-mix) were included specifically because synthetic tasks cannot be memorized by the LLM. Using recent and synthetic datasets reduces the chance that rule wording or feature descriptions were memorized by the LLM.

2. Ablation that removes feature descriptions. The ablation labeled -Description removes the feature descriptions from the prompt. This is the direct test reported in the paper for whether model performance depends on natural-language definitions of features (the likely vector for “memorized wording” to transfer). The ablation shows a performance drop (particularly strong in very low-shot settings), indicating that natural language feature descriptions do help the LLM. Crucially, the fact that performance remains meaningful even when descriptions are omitted argues that the method is not purely exploiting memorized, exact-surface text from pretraining.

3. Synthetic datasets. The Sequence-type and Solution-mix datasets are explicitly synthetic and therefore provide a baseline where pretraining memorization cannot explain performance. FeatLLM performs well on these, which supports the claim that the model’s rule extraction is not solely due to memorized web text.

What the paper did not explicitly report
The paper does not report a dedicated experiment where feature descriptions are replaced by fully synthetic/paraphrased text (e.g., randomized tokens or controlled paraphrases) for the same dataset, nor an evaluation that computes lexical overlap between generated rules and web pages. The -Description ablation is the closest existing experiment to this, but it is an omission rather than a substitution/paraphrase test.

Reproducible checks you can run locally (simple, deterministic)
Below are short, reproducible checks you can run on the public codebase (the paper provides a GitHub link) to strengthen confidence that model performance is not driven by memorized wording. All are straightforward to implement and experiment-repeatable.

1) “Null-description” replacement test (strongest controlled check)
Replace each human feature description in the prompt with a randomly generated synthetic description of the same token length (e.g., random English-like tokens or fixed template: “feature_1: tokenA tokenB ...”). Keep the numeric and categorical values identical. Run the full FeatLLM pipeline (same seeds, same $k$-shot splits) and compare $AUC$s to the original. If performance degrades to the -Description level or below, the model relied on the original wording; if performance remains near original, rules are coming from the training examples / data patterns not from memorized descriptions.

2) Paraphrase robustness (semantic-preservation check)
Automatically paraphrase every feature description with a set of different paraphrase engines (or back-translation). Repeat the pipeline per paraphrase and measure variance in $AUC$ and in the set of extracted rules. If rules are semantically similar and performance stable, the model is using meaning not exact wording.

3) Name-shuffle / tokenization test
Replace all feature names with neutral tokens ($f_1, f_2, \dots$), but keep the values and feature-type annotations (categorical/continuous). This removes any human-readable semantics while preserving data structure. Compare performance to original and to -Description ablation.

4) Exact-match search for generated rules (leakage-detection)
For the rules generated by FeatLLM, compute an exact- or fuzzy-string match search against a large web index (e.g., use the Google Custom Search API or CommonCrawl / wget + grep on known sources). If many rules are exact copies of web sentences, that’s evidence of memorization. If rules are short compositions of feature names/operators or dataset-specific thresholds, that is less likely to be memorized.

5) Label-permutation sanity check
Randomize labels in the $k$-shot training examples and run FeatLLM. If the model still outputs high-$AUC$ rules for the randomized labels, that suggests it’s relying on pretraining priors or memorized mappings; we expect performance to collapse when labels are random.

6) Cross-dataset feature-description swap
Swap feature descriptions between two unrelated datasets (keeping values the same). If performance changes dramatically or rules become nonsensical, it shows the model is sensitive to the natural-language descriptions.

Why these checks are useful intuitively
Omitting descriptions (-Description) shows whether explicit textual definitions are necessary, but replacing them tests whether performance depends on exact wording or on semantic information. Paraphrase and tokenization tests distinguish reliance on surface text versus abstract understanding. Exact-match search directly tests whether the model is reproducing text it could have memorized. Random-label tests check whether predictions come from the few-shot data signal or from firm priors encoded in the LLM.

Minimal code sketch (how to implement test 1 quickly)
- Load the dataset and precomputed $k$-shot splits used by the paper.
- For each feature description string, replace it with a synthetic string (e.g., use Python’s random words or "desc_feature_i_placeholder").
- Feed the modified prompt to the same LLM calls used in FeatLLM, parse rules, build binary features, and train the linear weights as in the paper.
- Compute $AUC$ vs the original and vs the -Description ablation.

Closing summary
The paper already takes reasonable steps: it uses post-cutoff datasets and synthetic datasets, and reports an ablation (-Description) that removes the textual feature descriptions. Those experiments indicate that FeatLLM is not purely exploiting memorized exact text from pretraining. If you want stronger, reproducible guarantees, run the simple replacement/paraphrase/tokenization tests and the exact-match and random-label checks above; they are deterministic, conceptually straightforward, and directly address whether performance hinges on memorized surface text versus data-driven rule extraction.

### How are categorical variables with many levels represented and matched in rules?
Question:
For high-cardinality categoricals, rules like "occupation is X" can be too specific or brittle. Do you instruct the LLM to cluster categories (e.g., via semantic similarity) or to prefer broader conditions (e.g., "occupation in {X, Y, Z}")? When the parser turns text into code, how do you handle category name normalization (case, punctuation) and unseen levels at test time?
Answer:
Short answer: FeatLLM handles high‑cardinality categoricals by (1) prompting the LLM to generate rules that may group categories (it is allowed to produce OR‑lists like “occupation in {X,Y,Z}”), (2) giving the LLM examples of possible categories in the feature description so it can choose sensible groupings, and (3) relying on an LLM‑based parser (the same LLM) to turn the free‑text rules into executable code that tolerates syntactic variation. There is no separate explicit clustering algorithm in the paper; instead the framework relies on the LLM’s prior knowledge and prompt instructions to generate broader conditions when appropriate, and on the downstream model + ensembling to soften brittleness when unseen or noisy category values appear.

Explanation and relevant technical points from the paper

1) Encouraging grouped/broader category conditions
The prompt design includes response instructions and a constrained output format so the LLM can produce rules that use set membership (OR) or other logical combinations. The paper explicitly states the prompt allows the LLM to combine multiple rules using AND/OR and it constrains the number of rules per class (they use $10$ per class). Because the LLM is given feature type information and examples of possible categories in the “basic information description” part of the prompt, it can use semantic priors to write rules that group related categories (for example “occupation in {teacher, professor, educator}”) instead of always emitting extremely specific single‑value rules. So the approach prefers broader conditions insofar as the LLM’s reasoning and the prompt instructions push it to produce useful, generalizable rules.

2) No explicit clustering step
The method does not run an external clustering or semantic‑similarity pipeline over categorical levels. The “clustering” or grouping is implicit: the LLM uses its world knowledge and the few examples to propose sets of categories when that yields better discriminative rules. The paper’s framing is “use LLM as feature engineer,” so category consolidation is delegated to the LLM’s reasoning rather than a separate algorithmic step.

3) Parsing, normalization, and syntactic variation
The paper acknowledges that LLM outputs can have noisy syntactic variants (e.g., “>” vs “greater than”), so instead of building a fragile hand‑coded parser, they prompt the LLM again to generate a simple piece of code that implements the rule (they include function signature, input/output descriptions and the rules to be parsed). That generated code is executed (via Python exec) to create binary features. This two‑stage use of the LLM (rule generation → LLM‑assisted parsing/code generation) addresses many normalization issues: the LLM can canonicalize variants, map textual relational phrases to operators, and produce code that handles punctuation/case. The prompt also includes feature type info and examples of valid categories to reduce type mismatches.

4) Behavior for unseen levels at test time
When the generated code runs on new data, any categorical level not matched by a rule simply causes the corresponding rule’s binary feature to be $0$ (i.e., the rule is not satisfied). The downstream linear model (with non‑negative weights) then combines these binary rule features to produce class logits; weights are trained on the few labeled examples so uninformative rules get low weight. Beyond that, robustness is achieved by ensembling and bagging: multiple independently generated rule sets (with randomness in demonstrations and higher temperature) produce diverse features; incorrect or overly specific rules in some trials are diluted by other trials that produce more general or correct rules. The paper’s experiments show only $1$–$2\%$ of rules come from noisy/unrelated columns and that ensembling reduces performance degradation from spurious correlations.

5) Limitations noted (and natural extensions)
The paper does not claim perfect handling of extreme cardinality. There is no dedicated algorithm to normalize all variants (e.g., custom lowercasing, punctuation stripping, synonyms mapping) beyond what the LLM produces in its parsing code. The authors also note possible failure modes: the LLM can still learn spurious correlations if provided with misleading columns or closely related data. As future work they propose expanding feature types beyond rules and improving interpretability; applying an explicit semantic clustering step (or canonicalization pipeline) before prompting would be a natural complement to the current design if you need deterministic normalization or want to explicitly merge many rare labels.

Practical takeaways if you implement or extend FeatLLM
- Give the LLM a concise list or a representative sample of category values in the feature description so it can form meaningful groups.  
- Allow and explicitly instruct the LLM to emit set membership (OR) rules in the response instructions.  
- Use the LLM to produce parsing code rather than attempting brittle regex parsing; include type hints in the parsing prompt to reduce errors.  
- Expect unseen categories at test time to yield “no match” ($rule=0$); rely on the ensembling and learned weights to mitigate their effect. If you need stronger handling of unseen synonyms, add a lightweight normalization step (lowercasing, punctuation removal, mapping via external ontology or embedding‑based clustering) before rule execution.

In short: FeatLLM encourages broader, grouped categorical rules through prompt design and relies on the LLM (twice) to both produce and normalize rules into executable code; unseen levels simply do not trigger rules ($feature=0$), and ensemble/tuning mitigates brittleness. The paper deliberately trades an explicit clustering pipeline for leveraging the LLM’s semantic knowledge and a robust LLM‑based parsing step.

### Why average probabilities across ensembles instead of stacking or logit averaging?
Question:
At inference you average per-trial class probabilities. Did you try averaging logits (before softmax), or learning a lightweight stacking model on top of the per-trial probabilities? In few-shot regimes stacking risks overfitting, but a simple logit average might improve calibration. Any comparisons in the appendix?
Answer:
Short answer: Because in our few-shot, per-trial setup averaging class probabilities is the simplest, most robust way to combine heterogeneous trial models without needing extra calibration data or risking strong overfitting. Averaging logits or training a stacker can help in some settings, but they require either consistent logit scales or additional labeled validation data (or strong regularization) that we typically do not have in the low-shot regimes studied in the paper.

Why averaging probabilities is what we used (intuitively and technically)
- Robustness to scale differences. Each ensemble trial in FeatLLM produces a small linear model (per-class weights) trained on different bagged features / few-shot subsets and hence its unnormalized scores (logits) can lie on very different scales. Averaging softmaxed probabilities normalizes away scale differences trial-by-trial, so a single badly scaled logit vector cannot dominate the ensemble. Averaging logits naively assumes comparable logit scales and biases across trials; that assumption is weak in our setup.
- No extra data required. Probability averaging needs no extra held-out data. In the few-shot regimes we target, there is very little labeled data; training a stacking model or calibrating logits (temperature scaling) requires a validation set or cross-validation folds, which increases variance and risks overfitting. The paper explicitly emphasizes low-shot settings and shows (in the Ablation section) that components that rely on training (weight tuning) become more effective only as shots increase.
- Simplicity and interpretability. Averaging probabilities is computationally trivial, easy to implement, and aligns with our goal of keeping inference light (we already avoid per-sample LLM queries). It also preserves interpretability of per-trial likelihood estimates, which fits FeatLLM’s design of combining many weak, diverse rule-based predictors.
- Implicit calibration benefits. Softmaxed outputs from small linear models (especially constrained to non-negative weights as in Eq. (1)) are often better behaved as probabilities than raw logits across diverse trials. Without consistent calibration procedures across trials, logit averaging can produce less well-calibrated final probabilities.

Why logit averaging or stacking can help (and why we didn’t use them as the default)
- Logit averaging can improve sharpness and sometimes calibration because averaging pre-softmax scores is equivalent to aggregating unnormalized affinities before normalization. If all trials’ logits are on comparable scales and biases, averaging logits and then applying a single softmax can be better than averaging post-softmax probabilities.
- Stacking (learning a lightweight combiner on the per-trial outputs) can outperform simple averaging because it can learn to upweight more accurate trials and correct correlated errors. However, stacking requires training data for the combiner. In the few-shot regimes FeatLLM focuses on, that extra training signal is tiny and stacking will easily overfit unless you use strong regularization (e.g., heavy $L_2$, sparse weights) or careful cross-validation, which substantially complicates the pipeline and can negate the low-data advantage.

Practical considerations and recommended experiments
- If you have somewhat more labeled data (or can do robust cross-validation), try averaging logits versus probabilities and compare calibration (Brier score, expected calibration error) and discrimination (AUC). If logits differ in scale, first apply per-trial temperature scaling on a small validation fold, then average logits.
- If you want to try stacking in low-shot, use a very simple combiner (e.g., non-negative linear combination with strong $L_2$ or $L_1$ penalty) and obtain combiner hyperparameters via nested cross-validation or Bayesian priors; otherwise the combiner will overfit.
- Another low-cost option is to take the geometric mean of probabilities (equivalently, average $\log$-probabilities and renormalize), which partially blends the benefits of logit and probability averaging and is less sensitive to extreme probabilities than arithmetic mean.

Summary
We average per-trial class probabilities because it is simple, scale-robust, and does not require extra labeled data or per-trial calibration — properties that matter in the few-shot, bagged-rule setting FeatLLM targets. Logit averaging and stacking are reasonable alternatives and may improve calibration or accuracy if you have enough labeled data or if you first align/calibrate per-trial logits; otherwise they risk instability and overfitting in the low-shot regimes emphasized in the paper.

### How general is FeatLLM beyond classification to regression or ranking tasks?
Question:
The current formulation produces binary rule-based features and uses a softmax over classes. For regression, would you just replace softmax and cross-entropy with a linear combination and a regression loss? Would you still enforce non-negativity of weights? Are there any results or caveats when rules need to express continuous relationships rather than discrete class conditions?
Answer:
Short answer: Yes — the FeatLLM pipeline is readily adaptable beyond multi-class classification. Conceptually you keep the LLM-as-feature-engineer stage and only change the downstream prediction objective and (optionally) constraints on the learned weights. Practically you can (1) replace the softmax/cross-entropy head with a linear/regression head and a regression loss, or (2) use a linear scoring head and a ranking loss for ranking tasks. A few important caveats follow.

How to adapt for regression
- Model change. Instead of computing logits and applying Softmax as in Eq. (1), predict a scalar by a linear combination of the generated features. If $z^i \in \{0,1\}^R$ is the rule-feature vector for sample $i$ and $w \in \mathbb{R}^R$ are learned weights, a natural choice is
  $\hat{y}^i = w^\top z^i$.
  Then train $w$ with a regression loss (e.g., mean squared error or MAE) on the $k$-shot training data.
- Weight constraints. The paper projects weights to be non-negative for classification (they use $\max(w_k,0)$ so rules never decrease class logit). For regression you should choose constraints based on domain knowledge. If all rules are designed to be positive indicators of increased target value, non-negativity makes sense and preserves interpretability/monotonicity. If rules can legitimately increase or decrease the target, allow signed weights (i.e., no ReLU projection). Practically, allow the optimizer to learn $w \in \mathbb{R}^R$ and optionally regularize ($\ell_2$/$\ell_1$) to avoid overfitting in very low-shot regimes.
- Calibration and bias. A linear head will produce unbounded predictions; if your target has a known range, add an intercept, clip, or use a link function. With very few shots, regularization and early stopping (as used in the paper) will be important.

How to adapt for ranking
- Scoring + ranking loss. Use the same feature vector $z^i$ and learn a scoring function $s(\mathbf{x}^i)=w^\top z^i$. Optimize pairwise surrogate losses (e.g., hinge or logistic on differences $s(x_i)-s(x_j)$) or listwise losses, depending on the ranking metric you care about. This follows the same idea as replacing cross-entropy with a different loss while keeping the rule features unchanged.
- Ensembling/bagging remain useful because they increase robustness of extracted rule sets for ranking as well.

When rules need to express continuous relationships
- Binary rules are expressive for threshold-like or region-based behaviors (e.g., "$\text{age} > 60$"). For truly continuous relationships (e.g., target grows linearly with temperature), binary indicators can approximate the relationship via many thresholded rules (piecewise-constant approximation), but that trades off dimensionality and sample complexity.
- Better: ask the LLM to output continuous or transformed features, not only binary rule flags. The paper already uses the LLM to generate parsable code to compute features; extend that to request numeric features such as raw transformations (e.g., "return BMI", "return log(cholesterol)"), piecewise linear features, or normalized continuous features. Parsing is already handled by sending the LLM a parsing prompt; you can ask it to output code that returns floats rather than booleans.
- Practical caveats: (1) continuous features require care in scaling/regularization because few-shot estimation of coefficients is noisy; (2) the LLM may produce semantically plausible but numerically poor transformations — validate generated transformations on held-out or cross-validated folds where possible; (3) more expressive continuous features increase risk of overfitting in very low-shot regimes, so prefer simpler transforms or constrain model complexity.

Other practical tips grounded in the paper
- Keep ensembling and bagging. The paper shows these stabilize and diversify features; this remains helpful for regression/ranking to reduce overfitting and to cover wide input ranges when rules are approximate.
- Regularization and early stopping. The paper tunes a simple linear model with Adam and early-stopping via cross-validation — do the same (or add Bayesian shrinkage) when targets are continuous to avoid overfitting with few examples.
- Interpretability trade-offs. Non-negative weights give monotonicity/interpretability for classification; allowing signed weights improves expressivity for regression but reduces that monotonic guarantee.
- Evaluation: for regression use MSE/MAE and inspect residuals; for ranking, evaluate ranking metrics (NDCG, MAP) since classification metrics aren’t appropriate.

Summary
FeatLLM’s core value—using an LLM to produce human-readable, parsable features—transfers directly to regression and ranking. Implementation-wise you replace the softmax head and cross-entropy with a regression or ranking loss, and decide whether to keep non-negativity based on domain assumptions. If you need to capture continuous relationships, either request continuous/transformed features from the LLM or approximate them by multiple thresholded rules, keeping in mind the usual low-shot trade-offs (regularize, ensemble, validate).

### How do you ensure rule expressivity is sufficient for complex interactions?
Question:
The response instruction allows logical operators like AND/OR inside a rule, but each rule is ultimately a single binary feature. Can the LLM propose arithmetic combinations (e.g., $\text{BMI} = \text{weight}/\text{height}^2$) or temporal patterns, or is it limited to threshold and set-membership predicates? If richer expressions are allowed, how is parsing specified and validated?
Answer:
Short answer: The paper’s pipeline is not limited to simple threshold or set-membership predicates — in principle the LLM can propose richer rule types (arithmetic formulas, combinations of fields, logical $\text{AND}/\text{OR}$, even temporal/derived conditions) — and FeatLLM handles them by (1) constraining response format during rule generation, (2) asking the LLM itself to produce small executable parsing code from the natural-language rule, and (3) validating/filtering the resulting binary features downstream during training.

Why richer expressions are possible (intuition + technical detail)
The method intentionally asks the LLM to output human‑readable “rules” and then converts those rules into binary features. Because the conversion step relies on the LLM generating small pieces of Python code (the authors feed the inferred rules + a function signature + IO description into the LLM and ask it to output code), the system can express anything that can be turned into executable code: simple thresholds ("$age > 50$"), logical combinations ("$age > 50$ $\text{AND}$ $ \text{smoker} == \text{True}$"), arithmetic derived features ("$\text{BMI} = \text{weight} / \text{height}^2$; $\text{BMI} > 30$"), and (as long as you provide sufficient semantics in the prompt) temporal patterns that can be evaluated from timestamped fields. The paper explicitly notes that without extra guidance the LLM can combine rules with $\text{AND}/\text{OR}$, and that feature types/descriptions are provided in the prompt to help the LLM produce type-correct rules.

How parsing is specified
Parsing is not done by hand-coded brittle regexes. Instead, the authors (a) constrain rule formatting through the “response instruction” in the rule-generation prompt so outputs are more regular, (b) provide feature types and definitions so the LLM knows how to reference columns, and then (c) input the generated natural-language rules plus a function name, input/output description, and parsing instructions back into the LLM and ask it to emit Python code that implements the rule evaluation. That generated code is executed (via Python’s exec()) to create the binary feature for each sample.

How validation is done (what the paper actually does)
The paper acknowledges that LLM outputs can be syntactically noisy (e.g., "greater than" vs. "$>$"), which motivates using the LLM to perform the robust translation to code. Validation and filtering occur in two places in the pipeline that the paper describes: first, the prompt design (feature types, fixed number of rules, and the structured response format) reduces malformed rules; second, after features are generated, they do downstream statistical/learning validation: the binary features are used in a simple linear model whose weights are trained on the few labeled examples, and features with low learned importance (the paper filters by learned weight threshold and reports $\text{AUROC} > 0.5$ of features vs label) effectively get ignored. The ablation and “quality of features” experiments show that many generated rules have $\text{AUROC} > 0.5$ and that tuning removes unhelpful rules. They also use ensembling and bagging so erroneous rules in some trials are averaged out.

Practical caveats and limits (from the paper)
While the approach allows richer expressions in practice, the paper imposes engineering constraints to keep the process reliable: it sets a fixed number of rules per class (10), supplies feature types/descriptions to avoid type mismatches, and relies on the LLM to produce parseable code rather than building a hand-rolled parser. The paper does not claim formal guarantees that every arbitrary complex expression (especially very complex temporal logic over long histories) will be correctly parsed or safe; instead it uses prompt engineering, LLM parsing, execution, and downstream weight-based filtering and ensembling to make the approach robust in practice.

If you want stricter parsing/validation (suggestions consistent with the paper)
The paper already uses structural prompts and runtime filtering. If you need stronger guarantees you can augment the described pipeline by adding unit tests for each generated parser (small synthetic inputs to check correctness), sandboxed execution with try/except and logging for failed parsing attempts, and grammar-based checks or a lightweight AST validation of generated code before exec. These additions are consistent with the paper’s philosophy (use the LLM to generate code, then validate and filter features empirically).

Bottom line: FeatLLM permits richer derived rules beyond thresholds because it converts natural-language rules to executable code via the same LLM, and then validates/filtering happens empirically by training weights and ensembling. The system uses constrained prompts, feature-type hints, LLM‑generated parsing code, and downstream feature importance to make richer expressions usable and robust in practice.
