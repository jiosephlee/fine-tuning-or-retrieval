\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 4: FeatLLM: Architecture and End-to-End Workflow

# Overview of the FeatLLM pipeline
FeatLLM is an end-to-end framework that repurposes a large language model (LLM) as an automated feature engineer for few-shot tabular learning. Rather than treating the LLM as a black-box predictor that must be invoked for every test sample, FeatLLM asks the LLM to produce human-readable decision criteria (rules) for each class, converts those rules into executable code, applies the code to the dataset to produce binary features, and fits a simple downstream model on those features. The key idea is to capture the LLM’s prior knowledge and reasoning about which feature conditions are relevant for each class, and to make those conditions reusable as features that any inexpensive model can use at inference time.

At a high level, FeatLLM follows this sequence for each trial of an ensemble: (1) prepare a prompt that contains task and feature descriptions and a few demonstrations; (2) query the LLM to extract a fixed number of rules per class (the rule-extraction stage); (3) ask the LLM to convert its natural-language rules into executable code and run that code to generate binary features (the parsing stage); (4) train a lightweight classifier on the resulting binary features to produce class likelihoods; and (5) repeat with bagging and ensembling to improve robustness and mitigate prompt-size limitations. This chapter details each stage, the motivations behind design choices, and how components interact to produce accurate, efficient, and interpretable predictions.

# Two-stage use of LLMs: (1) rule extraction; (2) rule parsing into executable code
FeatLLM employs the LLM in two distinct stages. The first stage asks the LLM to reason about the task and produce rules that characterize when a sample should be assigned to each class. The second stage asks the LLM to parse or translate those natural-language rules into small, executable code snippets that can be run on the tabular data to create binary indicators.

Rule extraction is driven by a carefully structured prompt that contains three parts: a basic information description, a reasoning instruction, and a response instruction. The basic information description supplies the task phrased as a question (for example, "Does this patient's record indicate chronic heart failure? Yes or no?"), natural-language names and types (and optionally definitions) for each feature, and a few serialized demonstrations. The demonstrations are serialized in a compact textual form such as:
"f_1 is x^i_1. ... f_d is x^i_d. Answer: y^i"
This gives the LLM concrete examples of feature values and labels without overwhelming it with raw table formatting.

The reasoning instruction is deliberately two-step. In step 1 the LLM is asked, without looking at demonstrations, to infer general tendencies or causal relationships between the features and the target using prior knowledge (e.g., "Which features are likely to increase the risk of chronic heart failure?"). This step encourages the LLM to surface domain priors and avoid overfitting to spurious correlations visible in a very small set of examples. In step 2 the LLM is asked to combine the prior knowledge from step 1 with the few-shot demonstrations to produce a fixed number of explicit rules per class (the paper uses 10 rules per class). Having a fixed quota controls prompt length, reduces the risk of producing too many or too few rules, and stabilizes downstream dimensionality.

The response instruction constrains the syntactic form of each rule and the overall output format to make parsing feasible. Despite these constraints, the LLM may still introduce syntactic variability (for example, "greater than" instead of ">" or optional parentheses). To reliably convert rules into executable form, FeatLLM uses the LLM again in the second stage. Instead of writing a bespoke parser for all the possible linguistic variants, FeatLLM provides the natural-language rules plus a minimal function signature and asks the LLM to output code that implements a deterministic predicate for each rule. The generated code is then executed (for example, via Python’s exec()) to create binary features. Using the LLM itself for parsing leverages its strong semantic understanding of the rules while avoiding brittle hand-engineered parsing logic.

This two-stage approach—first eliciting interpretable rules, then translating them to executable form—keeps human-interpretable criteria at the core of the pipeline while ensuring that the final binary features are deterministic and cheaply computable at inference time.

# Binary feature construction per class from rule satisfaction
Once rules for each class are available as executable predicates, FeatLLM converts them into binary features. For a dataset with $c$ classes and $R$ rules per class, each sample $\mathbf{x}^i$ is transformed into $c$ groups of $R$ binary indicators. For class $k$ the indicators form a vector $\mathbf{z}_k^i \in \{0,1\}^R$, where the $r$-th entry is 1 if and only if rule $r$ for class $k$ evaluates to true on sample $\mathbf{x}^i$.

This representation has several advantages. First, it isolates the LLM’s output (rules) into clear, interpretable features that can be audited: a positive value directly corresponds to satisfying a specific rule. Second, the binary format simplifies downstream modeling and avoids the need for complicated feature preprocessing or embedding choices. Third, because rules are class-specific, they can capture asymmetries in how different feature conditions indicate different classes. For multi-class problems, the feature set can be thought of as a concatenation of per-class rule indicator blocks.

The framework recognizes that not every rule is equally informative. A rule generated from a few-shot prompt might be broadly valid, irrelevant, or even misleading in the particular dataset. Thus FeatLLM does not rely on raw rule counts; instead it converts rule satisfaction into learnable signal weights via the downstream model (described below). In practice the paper demonstrates that a large fraction of generated rules are informative: an analysis measured AUROC between individual new binary features and target labels and found that most rules have AUROC exceeding 0.5 before tuning, and the tuning process further filters weak rules (weights close to zero), improving the effective feature set.

# Lightweight downstream model for class likelihoods
After converting rules into binary features, FeatLLM fits a lightweight, low-capacity model to estimate class likelihoods. The paper uses a simple linear model without bias for each class and projects weights into the non-negative space to ensure that satisfying a rule never actively reduces the associated class likelihood during optimization.

Concretely, for sample $\mathbf{x}^i$ and class $k$ we denote the binary rule vector by $\mathbf{z}_k^i \in \{0,1\}^R$ and train a weight vector $\mathbf{w}_k \in \mathbb{R}^R$. The logit for class $k$ is computed as
\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\]
and class probabilities are obtained by applying the softmax across class logits:
\[
\mathbf{p}^i = \text{Softmax}\big([\,\text{logit}_1^i,\ldots,\text{logit}_c^i\,]\big).
\]
Training minimizes the cross-entropy loss with respect to the weight vectors $\{\mathbf{w}_k\}_k$ using the few labeled samples. The paper uses the Adam optimizer with a learning rate of 0.01, trains for 200 epochs, and uses $k$-fold cross-validation to select the epoch to avoid overfitting.

There are several motivations for this simple model choice. First, linear weights afford interpretability: a large positive weight indicates a highly predictive rule. Second, the non-negativity restriction ensures the LLM’s generated features can only increase support for a class rather than flip polarity, which stabilizes learning from extremely small datasets. Third, a low-capacity model reduces the risk of overfitting in few-shot regimes and keeps inference fast. The paper’s ablations show that learning these per-rule weights is helpful: omitting this tuning (i.e., summing rule satisfactions without learned weights) reduces performance, and the benefit of tuning increases as the number of shots grows.

# Repeat-and-ensemble strategy with bagging for robustness and scalability
FeatLLM relies on stochastic repeated trials combined via ensembling to improve robustness and to deal with practical constraints like LLM prompt-size limits. Each trial produces a distinct set of rules (and therefore a distinct binary feature matrix) because the LLM is queried with randomized components: the prompt demonstrations can be reordered and the LLM sampling temperature is set non-zero to promote diversity. The framework then fits a separate lightweight model per trial. At inference time the final probability for a sample is the average of the probabilities produced by each trial’s model:
\[
\bar{\mathbf{p}}^i = \frac{1}{T} \sum_{t=1}^T \mathbf{p}^i[t],
\]
where $T$ is the number of trials (the experiments use $T=20$). Averaging across trials stabilizes predictions and leverages the idea of self-consistency: rules that recur across trials are more likely to be correct, while idiosyncratic or incorrect rules in some trials are mitigated by others.

Bagging is applied at the prompt and data level to address two practical problems. First, when the original table has many columns or when the demonstrations would make the prompt too long, selecting a random subset of features or a subset of demonstrations per trial keeps prompt length manageable. Second, bagging injects further diversity across trials, which improves the ensemble’s coverage of informative features: even if one trial does not include a particular relevant feature because it was not selected in that trial’s bag, another trial may include it. This mitigates the failure mode where a single trial’s rules miss crucial predictive conditions.

The ensemble approach also contributes computationally: because the LLM is used only to generate rules and parsing code during training (and not at inference time), repeating the rule-generation stage multiple times (e.g., 20 trials) only costs a moderate number of API queries (the paper reports about 30 API queries in total for the training phase, which can be parallelized), whereas methods that require an LLM call for every test sample would be far more expensive at inference time. Empirically, ensemble size beyond about 20 shows diminishing returns, so choosing $T\approx 20$ balances prediction gains with API cost.

# Design principles: interpretability, low inference cost, practicality with API-only models
FeatLLM was designed around four interlocking practical principles:

Interpretability. The core outputs are human-readable rules. Each binary feature corresponds to a named rule, so practitioners can inspect, critique, or refine the feature set before deployment. This is useful in domains where auditability is important (e.g., healthcare or finance). The learned per-rule weights give an immediate ranking of rule importance.

Low inference cost. After the training phase completes (which includes a modest number of LLM calls to extract and parse rules), inference on new samples requires only computing deterministic rule predicates and evaluating a simple linear model. No LLM calls are required per test sample. This contrasts with methods that feed each test sample through the LLM, and this design leads to inference-time costs comparable to conventional tabular methods.

Practicality with API-only models. FeatLLM works with LLMs accessed only through inference APIs. It avoids the need for parameter-efficient tuning or full model fine-tuning, which is important because many strong LLMs are not released with training interfaces. The method also copes with limited prompt windows by using bagging to sample subsets of features and demonstrations and by fixing the number of rules per class. The two-stage LLM usage (rule writing, then code generation) helps keep prompts compact and makes the pipeline robust to syntactic variability in LLM outputs.

Data efficiency and robustness. The two-step reasoning instruction encourages the LLM to use its external priors before relying on the small training examples. This helps guard against overfitting to spurious correlations that can appear in few-shot samples. Empirically, FeatLLM exhibits smaller performance degradation than many baselines when irrelevant noisy columns are appended to a dataset, suggesting that the rule-extraction prompt and the ensemble mechanism together reduce the influence of spurious features. Ablations further show that removing either the reasoning step or the feature descriptions in the prompt reduces performance—particularly in very low-shot regimes—showing the value of guiding the LLM’s reasoning and providing feature semantics.

# Practical settings and empirical summary (as reported)
The paper reports several practical hyperparameter settings and empirical observations that illustrate how the architecture is used in practice. The experiments used GPT-3.5 as the LLM backbone with temperature set to 0.5 (top-p left at API default). The number of rules per class was set to $R=10$ and the ensemble size to $T=20$. Training of the lightweight linear model used Adam with learning rate 0.01 for 200 epochs with $k$-fold cross-validation for epoch selection. Across 13 tabular datasets spanning domains and feature counts, FeatLLM frequently outperformed or tied top baselines in low-shot settings. Important empirical findings include:

- Tuning the linear weights improves performance, and its benefit grows with the number of shots. In very low-shot settings, leveraging the LLM’s priors (via the two-step reasoning and feature descriptions) is especially valuable.

- The ensemble consistently improves performance across datasets and shot settings; gains saturate around $T\approx 20$.

- Using the LLM to parse rules into code is effective at handling the LLM’s syntactic variations and simplifies automatic feature construction—most generated rules show signal (AUROC > 0.5) prior to tuning, and tuning filters out weak rules.

- FeatLLM achieves low inference latency comparable to traditional tabular models because no LLM calls are needed at prediction time. The training (rule extraction) cost is modest in terms of API queries and can be parallelized.

# Limitations and practical considerations
While FeatLLM addresses major practical constraints of prior LLM-based tabular methods—chiefly per-sample inference cost and the need for tuning-access to LLM parameters—it is designed specifically for low-shot regimes and uses rule-style features. Practitioners should be aware that the LLM’s priors may dominate very small datasets, and thus any societal biases or incorrect domain assumptions held by the LLM can influence the extracted rules and downstream predictions. The ensemble and tuning mechanisms reduce but do not eliminate such risks. Furthermore, when features are highly numerous, careful selection of bagging parameters is necessary to keep prompts within model context windows while ensuring adequate feature coverage across trials.

In summary, FeatLLM converts the LLM’s reasoning into reusable, interpretable binary features via a two-stage LLM workflow, fits a simple non-negative-weight linear model for class likelihoods, and uses repeat-and-ensemble with bagging to achieve robustness and scalability. This architecture yields an efficient practical compromise: it leverages LLM priors where they are most valuable (feature engineering) but avoids the expensive requirement of invoking or fine-tuning an LLM at inference time.
