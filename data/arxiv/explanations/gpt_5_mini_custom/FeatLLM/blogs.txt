# LLMs as Feature Engineers: How FeatLLM Makes Tabular AI Cheaper and Faster

## TL;DR
Most approaches that use large language models (LLMs) for tabular prediction run the LLM at inference time for every row. FeatLLM turns that around: it uses an LLM up front to automatically generate rule-based features from a few labeled examples, converts those rules into binary features, trains a tiny downstream model on those features, and then discards the LLM for inference. The result is few-shot performance that often beats prior LLM-based and classical baselines, with far lower inference latency, no LLM fine-tuning, and only API-level access required.

## The problem FeatLLM solves
Existing LLM-to-tabular pipelines typically serialize each row into text, include feature and task descriptions, and pass that entire prompt through the LLM to get a prediction. That works in low-shot settings but has three practical limitations:

- Expensive inference: you need one LLM call per sample at prediction time.
- Limited access: top-performing LLMs often only provide inference APIs, not training or fine-tuning hooks.
- Prompt-size limits: serializing many features or many examples can exceed the model’s context window.

FeatLLM sidesteps all three by changing the role of the LLM: instead of being a per-row predictor, it becomes an automated feature engineer.

## High-level idea
FeatLLM has three stages:

1. Query the LLM a limited number of times (e.g., a few dozen) to extract human-readable “rules” that capture conditions associated with each class.
2. Parse those natural-language rules into executable checks and convert them into binary features (rule satisfied = 1, otherwise 0).
3. Fit a simple downstream model (a non-negative linear model per class with softmax) on the new binary features and use that for inference.

After step 1–2, the LLM is no longer needed for inference, which makes prediction cheap and fast.

## How the LLM is prompted (so it actually outputs useful rules)
FeatLLM structures the prompt to mimic an expert feature-engineering workflow. The prompt has three parts:

- Basic information: task description (framed as a question), feature names and types (and optional definitions), and a few serialized demonstrations. Serialization follows the form: "f1 is x1. ... fd is xd. Answer: y".
- Reasoning instruction: a two-step reasoning scaffold. First, the LLM is asked to infer general tendencies or causal relationships between features and the target using prior knowledge (without looking at examples). Second, it is asked to use the demonstrations plus the inferred tendencies to propose concrete rules per class. This separation helps avoid spurious correlations and leverages both prior knowledge and the small labeled set.
- Response instruction: a strict output format and a fixed number of rules per class (e.g., 10) to make parsing reliable and to control prompt length.

This guided decomposition (prior-knowledge step followed by example-driven rule extraction) is central to FeatLLM’s robustness in low-shot regimes.

## Converting rules into features (parsing)
LLMs produce rules in natural language, and even with constrained formats there can be syntactic variability (e.g., ">" vs "greater than"). Rather than writing brittle parsers, FeatLLM uses the LLM itself to generate small pieces of executable code: the prompt includes the inferred rules and a function signature, and the LLM returns code that implements the checks. The generated code is executed (e.g., via Python’s exec()) to produce the binary rule features for the dataset.

This leverages the LLM’s proficiency with code and avoids fragile manual parsing logic.

## The downstream model: simple, interpretable, and fast
For each class k, FeatLLM constructs a binary vector z_k^i ∈ {0,1}^R for sample i, where R is the number of rules per class. The logit for class k is computed as

logit_k^i = max(w_k, 0) · z_k^i,

and class probabilities are obtained with a softmax over logits. The weights w_k are trained on the few-shot labeled data using cross-entropy loss. The max(...) enforces non-negativity so rule matches never decrease class likelihood, which is a sensible inductive bias for rule-derived features.

Because the downstream model is just a small linear model, inference is extremely cheap compared with calling an LLM per row.

## Robustness via ensemble + bagging
FeatLLM repeats the whole rule-generation and training pipeline T times (e.g., T ≈ 20), with randomness injected by (1) sampling subsets of features/instances (bagging) and (2) using a higher sampling temperature in the LLM to increase rule diversity. The final prediction averages the probabilities from each ensemble member.

This ensembling accomplishes three things:

- Compensates for occasional bad rules from some LLM queries.
- Filters rules that consistently correlate with the target across trials.
- Deals with prompt-size limits by having each trial see only a subset of attributes or examples.

## What the experiments say
The paper evaluates FeatLLM on 13 tabular datasets across diverse domains (Adult, Bank, Blood, Car, Communities, Credit-g, Diabetes, Heart, Myocardial, Cultivars, NHANES, plus two synthetic tasks). Key empirical points:

- FeatLLM outperforms or ties the best baselines in most low-shot settings and yields large average improvements over other LLM-based methods (the abstract reports ~10% average improvement versus alternatives like TabLLM and STUNT).
- With 4 labeled shots, FeatLLM can reach performance comparable to traditional methods trained with 32 shots on some tasks.
- FeatLLM is notably robust to spurious attributes: when irrelevant columns are appended, it degrades less than competing methods because the reasoning prompt encourages focus on plausible features.
- Feature quality: a large fraction of generated rule features have AUROC > 0.5 relative to the target, and the tuning step down-weights irrelevant rules.
- Cost and latency: FeatLLM needs only a small number of LLM API queries (the paper reports on the order of 30 API calls in experiments) during the upfront rule-discovery phase; after that, inference is as cheap as a simple linear model. In contrast, end-to-end LLM methods require an LLM call per sample at inference time.

## Practical trade-offs and limitations
FeatLLM is designed for low-shot settings and works best when:

- You have feature names/descriptions in natural language (FeatLLM relies on these to exploit LLM priors).
- You can afford a modest upfront number of LLM queries to extract rules.

Limitations noted by the authors include:

- FeatLLM focuses on rule-style features; it may miss other useful feature transformations that are not easily expressible as simple rules.
- If the LLM’s prior knowledge is biased or incorrect for a domain, that prior can dominate the few labeled examples and produce misleading rules; this raises concerns about bias/misinformation that require future analysis.
- The current design is aimed at few-shot regimes; extending to large-sample settings is left for future work.

## Why this matters
FeatLLM shows a practical path to bring LLM prior knowledge into tabular ML without the two big burdens most practitioners face today: expensive per-row LLM inference, and the need to fine-tune or host large models. By making the LLM an upfront rule generator, you get:

- Low-latency inference (no LLM calls at prediction time).
- API-only compatibility with closed LLMs (no fine-tuning required).
- Controlled prompt size through bagging/ensembling.
- Interpretability: rules are human-readable and can be inspected.

For many real-world settings (healthcare, finance, industrial telemetry) where labeling is expensive and inference latency matters, that trade-off—using the LLM once to engineer features and then shipping a tiny model—can be highly attractive.

## Takeaway
FeatLLM reframes LLMs from expensive, per-sample predictors into efficient, upfront feature engineers. It leverages LLM priors to produce rule-based binary features, parses those rules into executable checks, and learns a compact downstream model. The result: strong few-shot performance, much cheaper inference, and compatibility with API-only LLMs—making LLM-powered tabular learning more practical for production use.



# Designing Prompts that Think: The Two-Step Reasoning Behind FeatLLM

Large Language Models (LLMs) are great at pattern recognition and common-sense reasoning, but treating them as black-box predictors for every tabular sample is expensive and brittle. FeatLLM takes a different tack: it asks the LLM to act like an expert feature engineer and to output human-readable decision rules that are then converted into binary features for a cheap downstream model. The result is fast inference (no per-sample LLM calls), robustness to spurious columns, and strong few-shot performance.

This post unpacks the core prompt design idea that makes FeatLLM work: a deliberate two-step reasoning instruction that separates (1) extracting general, commonsense relationships between features and the task, from (2) producing concrete per-class rules grounded in few-shot examples.

## The high-level workflow (recap)

FeatLLM proceeds in three phases:
1. Prompt the LLM to generate rules (the prompt itself is structured into three parts — basic info, two-step reasoning instruction, and response format).
2. Parse the rules into programmatic checks to convert each rule into a binary feature (0/1) per sample.
3. Fit a lightweight classifier over those binary features. FeatLLM uses a linear model with non-negative weights and a softmax to produce class probabilities:
   - For class \(k\), with binary rule features \(\mathbf{z}_k^i \in \{0,1\}^R\) and weights \(\mathbf{w}_k\),
     \[
     \text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,
     \qquad
     \mathbf{p}^i = \text{Softmax}([\text{logit}_1^i, \dots, \text{logit}_c^i]).
     \]
4. Repeat the entire process with bagging and ensemble (randomized demonstrations, temperature) to improve robustness.

The key enabler is how the prompt guides the LLM to produce concise, relevant, and parseable rules. That’s what we focus on next.

## Why two-step reasoning?

A single prompt asking “write rules that predict the label” often yields rules that latch onto incidental correlations in a few examples. FeatLLM mitigates that by dividing the LLM’s thought process into two distinct steps:

- Step 1 (commonsense / prior knowledge): Ask the LLM to infer general tendencies or causal relationships between features and the target, without showing the few-shot examples. This step leverages the LLM’s background knowledge and encourages it to identify which features are plausibly relevant to the task. Because it does not rely on the tiny training set, it is less likely to overfit to idiosyncratic sample noise.

- Step 2 (data-grounded rule synthesis): Now supply the few-shot examples plus the Step 1 insights and ask the LLM to convert those insights into concrete per-class rules. The examples provide the necessary grounding so rules align with the dataset’s observed patterns, but the prior filtering from Step 1 biases the model away from spurious columns.

This separation simulates how a human analyst works: first recall relevant domain knowledge, then refine it using the observed instances.

## Prompt composition — three pieces that matter

FeatLLM’s prompt has three explicit components that together coax reliable rules from the LLM.

1. Basic information description
   - Task description framed as a clear question (e.g., “Does this patient have chronic heart failure? Yes or no?”).
   - Feature names and types (numerical or categorical) and optional short descriptions so the model knows what each column means.
   - Few-shot example serializations in a fixed format:
     "f1 is x1. ... fd is xd. Answer: y"
   These elements let the LLM map feature semantics to the prediction objective.

2. Two-step reasoning instruction
   - An introductory “chain-of-thought” style line to encourage stepwise reasoning.
   - Explicit Step 1 prompt: infer general relationships/tendencies between features and the target, *without* consulting the examples.
   - Explicit Step 2 prompt: using Step 1 plus the few-shot examples, generate decisive rules for each class.
   - A cap on the number of rules per class (FeatLLM fixes this to 10) to avoid runaway prompt length and excessive features.
   This structure biases the LLM to focus on plausible causal links first, then synthesize concise rules informed by data.

3. Response instruction (format constraints)
   - A strict template for how each rule should be returned and how classes are separated.
   - Guidance about rule structure so the LLM uses the right comparison operators and respects feature types.
   - These constraints make downstream parsing easier and reduce syntactic variance.

Together, these parts turn the LLM into an “analyst” that states relevant domain intuition and then codifies it in a bounded, parseable set of rules.

## From free-text rules to executable features

LLMs are flexible, and even with format instructions they can vary syntax (e.g., “greater than” vs “>”). Instead of building brittle parsing heuristics, FeatLLM asks the LLM to generate simple Python code that implements the rules. The pipeline then executes that code (e.g., via Python’s exec()) to produce the binary features for all samples. This step leverages the LLM’s strengths in code generation to transform noisy natural-language rules into reliable program checks.

## Controlling prompt-size and improving robustness: bagging + ensemble

Two practical problems remain: lengthy tables (many columns) can exceed prompt limits, and any single LLM run can produce imperfect rules. FeatLLM addresses both by repeating the rule-generation process multiple times with randomized subsets (bagging) and varied prompt conditions (e.g., shuffling few-shot example order, sampling with a moderate temperature). Each run produces a different set of rule-features and corresponding trained linear weights. Predictions are averaged across these runs (FeatLLM uses 20 ensembles in the study), which:

- Limits per-query prompt size because each run only needs a subset of columns/examples.
- Averages out incorrect or noisy rules, relying on the most consistent rules across trials.
- Keeps inference cheap: once the rule-features and the simple downstream model are produced, inference requires no LLM calls.

## Practical defaults reported in the paper

The FeatLLM implementation used in the paper reports the following practical settings that worked across 13 tabular datasets in low-shot regimes:
- Rules per class: 10 (fixed)
- Number of ensembles: 20
- LLM backbone in experiments: GPT-3.5 (API-based)
- Inference temperature: 0.5
- Lightweight downstream model: linear model with non-negative weights trained by cross-entropy; learning rate 0.01, 200 epochs with k-fold selection of epoch
- Rule-to-code conversion: LLM-assisted code generation, executed in Python

These choices balanced prompt length, rule expressiveness, and the low-shot constraints of the datasets used.

## Benefits and trade-offs

Benefits:
- Leverages LLM prior knowledge without requiring per-sample LLM inference at test time.
- Explicit two-step reasoning reduces reliance on spurious correlations from tiny datasets.
- Produced features are interpretable (rules) and easy to audit.
- Ensemble+bagging mitigates prompt-size limits and improves robustness.

Trade-offs / considerations:
- Rule generation still relies on the LLM’s priors; biased or incorrect priors can produce misleading rules (the paper discusses this and suggests future bias analysis).
- Parsing is simplified by format constraints and code generation, but requires careful prompt engineering to avoid syntactic drift.
- FeatLLM is targeted at few-shot regimes; scaling to large labeled datasets is left as future work.

## Takeaway

FeatLLM’s prompt design is an example of using instruction engineering to shape the LLM’s internal reasoning: separate general domain inference from data-driven rule synthesis, enforce a compact response format, and convert the output into features for a simple model. This pattern—“ask the model to think like an analyst first, then produce precise checks second”—is broadly applicable when you want LLMs to generate structured, testable artifacts rather than raw per-instance predictions.



# From Rules to Ready-to-Train Features: Parsing Natural Language into Code

LLMs are great at surfacing human-readable rules from a handful of examples: “If age > 60 and cholesterol is high, predict disease.” But real-world LLM outputs are rarely identical to the neat conditionals you imagined. Symbols flip to words, punctuation changes, AND/ORs get phrased differently, and small syntactic variations break brittle parsers. FeatLLM takes a pragmatic approach: instead of building an elaborate, hand-coded parser to normalize every possible textual variation, it asks the LLM itself to produce simple executable parsing code that converts each natural-language rule into a binary (0/1) feature. The result is robust, compact, and ready for downstream training.

## The problem: messy, variable rule text

When you constrain an LLM to output rules, you can improve structure (e.g., fixed templates), but outputs still contain noisy syntactic differences. Common issues include:

- Symbols replaced with words ("$>$" → "greater than")
- Different boolean phrasing ("if A then B" vs "A -> B")
- Minor typographical or formatting differences
- Logical connectors expressed in multiple natural ways

A brittle string-based parser will fail on many such cases. Implementing a robust, general parser for all these variations is time-consuming and error-prone.

## The idea: use the LLM to write the parser

FeatLLM leverages an important strength of modern LLMs: they understand and can generate code. Instead of writing a complex grammar or many normalization heuristics, the pipeline:

1. Prompts the LLM to produce a set of natural-language rules for each class (guided with task/feature descriptions and few-shot examples).
2. Feeds those rules back into the LLM along with a short specification for a parsing function: its name, input description, output description, and execution expectations.
3. Requests simple Python code that implements the parser for those specific rules.
4. Executes the generated code (using Python's exec()) to convert the original dataset into binary features indicating whether each sample satisfies each rule.

Because the LLM-produced code is targeted at the actual phrasing the LLM itself used to express the rule, it is resilient to the syntactic drift that breaks hand-rolled parsers.

## Prompting for parsing code: constrained but flexible

FeatLLM constrains the parsing stage by providing the LLM with:

- The exact natural-language rules it previously generated.
- A clear function signature and descriptions for inputs and outputs (for instance: a function that accepts a single sample and returns 0/1 per rule).
- Examples or instructions about the target data types (categorical, numeric) so the generated code avoids type errors.

This focused specification reduces ambiguity and nudges the LLM to emit simple, parseable code that works on the concrete rules it output. The generated code typically contains straightforward condition checks (e.g., comparisons, membership tests) and returns binary indicators for each rule.

## Execution and safety

FeatLLM executes the generated parsing code via Python’s exec() to perform data conversion. In the paper’s setup, the LLM is instructed to produce simple, deterministic code for transforming a row into binary indicators. The approach trades the complexity of a universal parser for a small set of per-run, rule-specific parsing programs that are easy to inspect and run.

Note: in production deployments you should treat any code generated by an external model as untrusted input and run it in a sandboxed environment, but the method in the paper relies on executing the generated code to perform automatic feature creation.

## What you get: binary features that train easily

Each rule becomes a binary feature z_k^i ∈ {0,1} for sample i and class k. These features are assembled into a small downstream model: a simple linear scoring function where each rule-feature has a non-negative weight, producing logits and class probabilities via a softmax:

- logit_k^i = max(w_k, 0) · z_k^i
- p^i = Softmax([logit_1^i, ..., logit_c^i])

Learning is just cross-entropy minimization on the small weight vector(s), which is feasible in few-shot regimes. The parsing step gives reliable, structured inputs for this lightweight classifier.

## Why this matters

- Robustness to syntax drift: Because the code is generated to match the LLM’s own phrasing of rules, minor textual variations no longer break parsing.
- Simpler engineering: You avoid designing and maintaining a large normalization/parsing pipeline for natural language rules.
- Efficiency at inference: Once rules are parsed and features computed, inference uses only the trained lightweight model (no per-sample LLM calls).
- Interpretability: Rules remain human-readable and the classifier weights indicate rule importance; you can inspect or prune rules after training.

## How this fits into FeatLLM’s overall pipeline

Parsing-generated binary features is one stage in the FeatLLM workflow:

1. Prompt LLM to infer relationships and generate a fixed number of rules per class (guided two-step reasoning: general prior knowledge, then example-driven rule extraction).
2. Ask the LLM to generate parsing code for those rules and execute it to produce binary features for the dataset.
3. Fit a simple linear model with non-negative weights to learn each rule’s importance and compute class probabilities.
4. Repeat the whole process with bagging and ensembling to add robustness and to overcome prompt-size limits.

This design avoids sending each test sample to the LLM, requires only API-level access to the LLM, and naturally scales to datasets with many features by using bagging to keep prompts compact.

## Takeaway

When an LLM gives you messy but semantically useful rules, the practical route is often not to force-fit a universal parser but to leverage the model’s code generation abilities to translate its own language into executable parsing code. FeatLLM demonstrates that asking the model to output simple, rule-specific code yields reliable binary features that are ready for lightweight, few-shot training — combining the interpretability of rule-based reasoning with the robustness and efficiency needed for real-world tabular tasks.



# Do We Still Need Big Models at Inference? Why Simple Linear Heads Win Here

Modern large language models (LLMs) are amazing at reasoning and extracting knowledge, but running them at inference time for every sample is expensive and often unnecessary. FeatLLM takes a different tack: use an LLM to engineer interpretable rule-based features, then hand off prediction to a tiny linear head. The result: the heavy lifting is done once (feature discovery), and inference is as cheap as ordinary tabular models — while retaining the LLM’s prior knowledge and reasoning benefits.

## The architecture in one line
1. Use an LLM (in-context, few-shot) to generate human-readable rules per class.  
2. Parse each rule into a deterministic test that yields a binary feature (1 = rule satisfied, 0 = not).  
3. Fit a lightweight linear model with non-negative weights on those binary features to produce class logits and probabilities.  
4. Repeat with bagging/ensembling to boost robustness.

This decouples rule discovery (LLM-heavy, done a limited number of times) from per-sample inference (ML-light, done cheaply).

## Why a linear head makes sense here
After rules are converted into binary features, the prediction problem becomes: given vectors of rule-satisfaction indicators, how likely is each class? Two simple options are obvious:

- Count rules per class (naïve sum).
- Learn how to weight each rule from a few labeled examples.

FeatLLM goes with the latter but keeps the learner extremely simple: a linear model with non-negative weights per rule. Concretely, for class \(k\) and sample \(i\) let the binary rule vector be \(\mathbf{z}_k^i \in \{0,1\}^R\) (where \(R\) is rules per class). The model computes

- logit: \(\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i\)
- probability: \(\mathbf{p}^i = \text{Softmax}([\text{logit}_1^i, \dots, \text{logit}_c^i])\)

The weights \(\mathbf{w}_k\) are learned with cross-entropy on the few available shots.

There are several reasons this is a practical and effective choice.

## Key advantages

- Learn which rules actually matter. Not all LLM-generated rules are equally informative. Learning weights lets the model emphasize strong rules and attenuate weak or noisy ones — instead of treating every rule equally as a simple count would.
- Non-negative weights align with intuition. For a rule intended to increase evidence for a class, constraining weights to be non-negative prevents weird behavior where a rule literal would penalize a class. It also improves interpretability: higher weight = more supporting evidence.
- Extremely cheap inference. Once weights are learned, prediction is just a dot product between small binary vectors and learned weights, followed by a softmax. This makes per-sample cost comparable to logistic regression or other standard tabular methods.
- Few-shot friendly and fast to train. The linear head can be trained with very few examples (the paper shows strong results even with 4 shots). Training is efficient (Adam, modest epochs) and does not require fine-tuning the LLM or expensive compute.
- Robustness via ensembling and bagging. FeatLLM repeats rule extraction with randomized prompts and bagging, producing multiple linear heads whose predictions are averaged. This compensates for occasional poor rule sets and mitigates LLM prompt-size issues by distributing coverage across trials.

## Empirical signals from the paper (grounded findings)
- Tuning the linear weights improves performance over naïve counts: ablation results show removing the weight tuning step (\textsf{-Tuning}) degrades AUC, and the benefit of tuning becomes larger as the number of shots increases. This indicates that learned weights extract more value from additional labeled data.
- FeatLLM with only 4 shots reaches performance comparable to conventional tabular models trained with 32 shots on multiple datasets, demonstrating the efficiency of combining LLM priors with a lightweight learned head.
- Inference cost is low: the method requires only the (limited) initial set of LLM queries to generate rules (e.g., about 30 API queries in the experiments), and thereafter standard ML inference. Measured inference time is comparable to conventional methods and much lower than per-sample LLM approaches (In-context, TABLET, TabLLM).
- The learned weights also act as an automatic filter: many rules that are irrelevant receive small learned weights and can be pruned. The paper reports that after tuning, the fraction of retained informative features increases (using a weight threshold), confirming that the linear head helps remove spurious or weak rules.
- Robustness to spurious features: when random unrelated columns were appended to a dataset, FeatLLM degraded less than baselines. This is consistent with the pipeline’s emphasis on prior-informed rule generation plus learned weighting down-weighting irrelevant rules.

## Practical takeaways
- If you can spend a small budget on LLM queries to discover rules once, you can avoid LLM inference at prediction time entirely. That makes deployment practical for latency- or cost-sensitive production scenarios.
- Keep the prediction head simple. A linear model with non-negative weights is interpretable, trains fast in few-shot settings, and benefits from the LLM’s prior knowledge encoded in the rule set.
- Use ensembling and bagging when prompts or feature counts grow. This both reduces prompt-size pressure on the LLM and improves robustness to noisy rules.

## Limitations to remember
FeatLLM focuses on low-shot regimes. The quality of predictions still depends on the LLM producing meaningful rules; if the LLM generates systematically biased or incorrect rules, the linear head will inherit those limitations (though weight learning and ensembling help). Also, the method extracts rule-like binary features; different downstream feature types (continuous transformations, learned embeddings) are outside the current scope.

## Bottom line
You don’t always need giant models at inference. FeatLLM demonstrates a practical design pattern: use big LLMs for one-time, high-value feature engineering (rule discovery), then rely on a tiny, interpretable linear head to learn which rules matter. This combines the best of both worlds — LLM reasoning power and cheap, fast, few-shot-friendly inference.



# Outsmarting Context Limits: Bagging and Ensembles for Scalable Few-Shot Tabular Learning

Long, wide tables and short LLM context windows are a poor match. When you serialize a high-dimensional table into a prompt, token budgets are exhausted quickly and inference becomes expensive if you call the LLM per sample. FeatLLM takes a different tack: treat a large language model as an expert feature engineer, use it to generate compact, human-readable rules, and then combine many small rule-sets via bagging and ensembling. The result is a scalable few-shot tabular pipeline that overcomes prompt-size limits and avoids per-sample LLM inference.

Below I unpack how FeatLLM uses feature and instance bagging, temperature and demonstration reordering for diversity, and ensembling to produce robust, low-cost predictions in the few-shot regime.

## The core idea in one line

Instead of asking an LLM to predict every test row, ask it to propose rule-based features (binary predicates). Parse those rules into executable code, generate binary features for the dataset, fit a small downstream model (a linear model with non-negative weights and a softmax), and repeat this process many times with different small prompts. Aggregate the resulting models' probabilities to get the final prediction.

This design gives you:
- small prompts (so it fits in the LLM context),
- only a handful of API calls during training (no per-sample calls at inference),
- robustness through ensemble diversity and self-consistency across trials.

## Why bagging? Two axes of “smallness”

FeatLLM reduces prompt length and increases robustness by applying bagging in two complementary ways.

1. Feature bagging (random column subsets)
   - For each LLM query, only a subset of the table's columns (feature names + descriptions) are included in the prompt. That keeps the serialization short even on wide datasets (some datasets used in the paper have 100+ attributes).
   - The LLM is asked to infer rules that relate the task to those columns and to propose a fixed number of rules per class (paper uses R = 10 rules per class).
   - Different column subsets expose the LLM to different parts of the table, so the ensemble of multiple trials covers more of the original feature space than any single prompt.

2. Instance bagging (random few-shot examples)
   - Each trial uses a small sampled set of labeled examples (k-shot demonstrations) in the prompt. Since prompt length is constrained, using different small samples across trials lets the system see varied local patterns without ever needing a long prompt.
   - Re-sampling the demonstration order also matters: in-context learning is sensitive to example ordering, so randomizing order injects additional diversity.

Because each trial is deliberately compact, even very wide tables can be handled by breaking the feature space across trials instead of trying to fit everything into one prompt.

## How diversity is created and why it helps

FeatLLM intentionally injects randomness to make the rule sets different across trials:

- The LLM decoding temperature is set higher to increase variation in generated rules (the paper used temperature = 0.5 and top-p = 1).
- The bagged selection of columns and examples differs per trial.
- Demonstration ordering is randomized.

Why this diversity helps: some trials will discover correct, informative rules; others will produce weak or noisy rules. Aggregating across trials uses the "wisdom of crowds": consistent rules that recur across many trials are more likely to be useful (self-consistency), while occasional bad rules are diluted by the ensemble.

Empirically, the paper shows that ensembling substantially improves performance (the ensemble helps across datasets and shot sizes), and that FeatLLM degrades far less than baselines when irrelevant/spurious columns are appended to the data.

## From natural-language rules to features and models

FeatLLM's pipeline per trial:

1. Prompt the LLM with:
   - Task description (label names).
   - Feature names and type descriptions (only the bagged subset).
   - A few serialized example rows (k-shot demonstrations).
   - A two-step reasoning instruction: (a) infer general relationships from prior knowledge, then (b) derive concrete rules using examples.
   - A strict response format that yields R rules per class.

2. Parse rules into executable feature code:
   - Outputs are natural-language rules, which may include syntactic variations.
   - Instead of a brittle hand-coded parser, FeatLLM uses the same LLM to convert the rules into simple Python code (e.g., a predicate function) and then executes that code to produce binary features (0/1) indicating whether each sample satisfies each rule.

3. Fit a light-weight downstream model:
   - For class k, the new binary features are collected into z_k^i ∈ {0,1}^R for sample i.
   - A linear scoring model without bias is used. The logit for class k is:
     logit_k^i = max(w_k, 0) · z_k^i
     where max(w_k, 0) projects learnable weights into the non-negative orthant so features cannot reduce a class's score.
   - Final probabilities are computed with softmax over class logits.
   - The linear weights are learned by optimizing cross-entropy on the few-shot training data.

Because the downstream model is tiny, inference is cheap and requires no further LLM calls.

## Ensemble and aggregation

FeatLLM repeats the trial T times (the paper uses T ≈ 20). Each trial produces a trained weight vector (or a set of weights across classes). The final predicted class probabilities for a sample are the average of the per-trial probabilities. This simple aggregation has several benefits:

- Robustness: trials that produce misleading rules have little influence on the average.
- Coverage: different trials can capture different true signal features that single-trial prompting would miss.
- Reduced prompt size per trial: since each trial sees only a fraction of the columns, the ensemble jointly covers the table.

The paper reports that performance gains improve with the number of ensembles but saturate around 20 trials for their experimental setup.

## Practical choices reported in the paper

- Rules per class: R = 10 (a trade-off between prompt length and expressivity).
- Ensemble size: T = 20 (found to be sufficient for convergence in experiments).
- LLM backbone in experiments: GPT-3.5 (API access only, no fine-tuning required).
- LLM decoding: temperature = 0.5, top-p = 1.
- Parsing strategy: use the LLM itself to convert free-text rules into executable Python code, then run that code to produce the binary features.
- Downstream model: linear model with non-negative projected weights trained with Adam (learning rate 0.01, 200 epochs with k-fold cross-validation to avoid overfitting).
- API usage: the framework needs only a modest number of LLM calls (the paper reports about 30 API queries in their runs), which can be parallelized.

## Experimental highlights (what the paper shows)

- Evaluation was performed on 13 diverse tabular datasets (standard and newer UCI datasets, plus synthetic datasets that the LLM could not have memorized).
- FeatLLM consistently ranked first or second among a range of baselines (including conventional tabular models, semi-supervised methods, TabPFN, and LLM-based baselines like in-context, TABLET, and TabLLM).
- On average, FeatLLM significantly outperformed recent alternatives (the abstract reports a ~10% average improvement over approaches like TabLLM and STUNT).
- FeatLLM performs competitively in very low-shot settings: with 4 shots it reaches performance comparable to conventional methods that use 32 shots.
- Ablation studies show the ensemble step is consistently beneficial; omitting ensembling reduces AUC across datasets.
- Under injected spurious features (irrelevant columns added), FeatLLM exhibits the least performance degradation compared to baselines — bagging and the two-step reasoning prompt likely help the LLM avoid learning rules from irrelevant columns.

## Why this is practically useful

- Context-window friendly. By design, each prompt is compact. You can scale to tables with many columns simply by increasing the number of trials rather than trying to stuff all columns into one prompt.
- Low-cost inference. Once rules are generated and the downstream models are trained, predictions require only fast numeric operations — no per-sample LLM calls.
- Works with API-only LLMs. FeatLLM needs no model fine-tuning; it only requires standard inference API access (valuable when model weights/checkpoints are not available).
- Explainability. The features are human-readable rules; you can inspect which predicates drive predictions and which ones get non-zero weight after tuning.

## Limitations and cautions

- Rule quality depends on LLM prior knowledge and on the prompt design. If a dataset contains relationships that are highly counterintuitive or domain-specific beyond the LLM's pretraining, rule generation may miss them.
- The method is tuned for few-shot regimes. Scaling to large labeled datasets may require alternative strategies.
- LLM priors can encode societal biases or misinformation; those priors will influence the generated rules and therefore downstream predictions. The authors flag this as an important direction for further analysis.

## Takeaway

FeatLLM demonstrates a pragmatic way to combine LLM reasoning with classic ensemble ideas to sidestep the token-limit bottleneck and the cost of per-sample LLM inference. Feature and instance bagging produce compact, diverse prompts; temperature and example reordering amplify diversity; and ensembling yields robustness through self-consistency. For practitioners facing wide tables and tight token budgets, generating many small, complementary rule-sets and aggregating their predictions is an effective and scalable pattern.



# Benchmark Breakdown: 13 Datasets, 10% Gains, and 4-Shot vs. 32-Shot

FeatLLM reframes how we use large language models (LLMs) for tabular few-shot tasks. Instead of querying an LLM for each test example, FeatLLM asks the LLM to be a feature engineer: generate human-readable rules (criteria) for each class, convert those rules to binary features, and train a lightweight downstream model. The result is strong few-shot performance, substantially lower inference cost than LLM-at-inference approaches, and resilience on wide tables where serialized prompts would otherwise hit context limits.

This post walks through what FeatLLM does, why it matters for few-shot tabular problems, and the headline empirical results from the paper.

## What FeatLLM does (high level)

FeatLLM turns LLM prior knowledge into reusable features via a three-stage flow:

1. Prompt the LLM (in-context, few-shot) to produce class-specific rules. The prompt is structured into:
   - Basic info: task description, feature names/types/descriptions, and a few serialized training examples.
   - Reasoning instruction: a two-step guide that first elicits general feature–label tendencies (prior/common-sense knowledge) and then asks the model to derive concrete rules using the few examples.
   - Response instruction: a strict output format so generated rules are easier to parse.

2. Parse rules into executable code (the LLM helps here too) and apply them to every sample to obtain binary features indicating whether each rule is satisfied.

3. Fit a simple model on those binary features to produce class probabilities. The paper uses a per-class linear scoring model with non-negative weights so that each rule can only increase class likelihood:

   "logit_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i", and probabilities are produced with a Softmax over class logits.

To improve robustness and to avoid prompt-size bottlenecks, FeatLLM repeats rule generation with bagging (subsets of features or samples) and ensembles the resulting models.

Key practical design points: the LLM is used only during feature discovery (not per-sample inference), parsing is LLM-assisted to handle noisy text-to-code mapping, and the downstream model is intentionally simple so inference is fast.

## Why this design matters

- Efficiency: Only a modest number of API queries are needed to discover rules. At inference the system runs classical code and a tiny model; no LLM calls per example.
- Interpretability: Rules are explicit and human-readable; they form binary features that can be inspected.
- Prompt-size and scale: By bagging feature subsets and ensembling multiple small prompts, FeatLLM avoids the long-serialization failure modes that plague direct LLM-on-table methods when the table has many columns.
- Low-shot suitability: The method leverages LLM prior knowledge plus a few examples to produce useful rule-features that generalize in low-shot regimes.

## Experimental setup (short)

- Evaluation on 13 tabular datasets spanning classical UCI tasks (Adult, Bank, Credit-g, Diabetes, Heart, etc.), some recent UCI additions, and two synthetic tasks. These include datasets with many attributes (e.g., Communities, Myocardial) to test width limits.
- LLM backbone for the main experiments: GPT-3.5 (gpt-3.5-turbo-0613) via API (FeatLLM is LLM-agnostic in design).
- FeatLLM hyperparameters reported in the paper: 20 ensemble trials, 10 rules per class per trial, LLM temperature 0.5, downstream linear model trained with Adam (lr 0.01) for 200 epochs with non-negative weight projection. Parsing code for rules is generated by the LLM and executed (e.g., via Python exec).

Baselines include traditional methods (Logistic Regression, XGBoost, RandomForest), semi/unsupervised few-shot approaches (SCARF, STUNT, TabPFN), and LLM-based methods (in-context prompting, TABLET, TabLLM).

## Headline results

- Across the 13 datasets and various low-shot settings, FeatLLM consistently ranks first or second against all baselines.
- On average, FeatLLM achieves roughly a 10% absolute improvement over recent LLM-based few-shot alternatives such as TabLLM and STUNT (paper reports ~10% average gains).
- Striking data-efficiency result: with only 4 labeled shots FeatLLM attains performance comparable to standard tabular models trained with 32 shots. In other words, the LLM-crafted features let a small number of examples go much further.
- Wide-table robustness: methods that serialize entire rows into long prompts (many existing LLM approaches) either fail or degrade on datasets with many features. FeatLLM’s bagging + ensemble approach maintains competitive performance in those settings.
- Inference cost: because the LLM is only used during feature discovery, inference time is comparable to conventional tabular models and far lower than methods that require an LLM call per test sample. Training (feature discovery) requires a modest number of API queries (the paper notes ~30 queries in their experiments for the setup used), which can be parallelized.

## Additional analysis highlights

- Ablations confirm three core contributions: the reasoning step that elicits prior knowledge, including feature descriptions in prompts, and the downstream weight tuning all improve performance. Omitting ensemble also degrades results.
- Feature quality: most rule-derived binary features have positive AUROC with respect to the target label. After tuning the linear model, irrelevant rules tend to get near-zero learned weights and are effectively filtered out.
- Spurious features: when unrelated columns were appended to a dataset (to simulate noisy/spurious correlations), FeatLLM’s performance degraded less than baseline methods. The two-step reasoning prompt (prior tendencies then example-driven rules) helps the LLM avoid making rules based on irrelevant columns in many cases.
- Hyperparameters: performance improves with more ensemble trials up to a point (converges around ~20). Ten rules per class was chosen as a practical tradeoff between prompt length and expressivity.

## When to consider FeatLLM

- If you have a low-shot tabular problem and want to leverage LLM prior knowledge but cannot afford LLM-at-inference cost, FeatLLM is a practical approach.
- If your table is wide (many columns) and direct serialization into an LLM would exceed context or produce degraded outputs, FeatLLM’s bagging strategy is helpful.
- If interpretability of derived decision criteria is important, FeatLLM yields human-readable rules that can be inspected, pruned, or audited.

## Limitations and caveats called out in the paper

- FeatLLM is designed for low-shot settings; scaling to large labeled datasets was not the focus and is proposed as future work.
- The approach depends on LLM prior knowledge. If the LLM’s training data encodes harmful biases or incorrect domain knowledge, those priors can influence the generated rules (the authors note the need for future study on societal biases/misinformation).
- LLM-generated rules are not flawless — the ensemble and downstream tuning mitigate but do not entirely eliminate incorrect or spurious rules.

## Takeaway

FeatLLM is a pragmatic middle ground: it leverages LLMs where they are strongest (commonsense/prior knowledge and rule extraction) and then switches to classical, cheap inference. Empirically, this design yields ~10% average gains over recent few-shot LLM/tabular baselines, matches many traditional models trained with eight times the labeled data (4 vs. 32 shots), and keeps inference costs low — a compelling combination for real-world low-shot tabular applications.



# Fighting Spurious Correlations with Prior Knowledge (and When It Fails)

## TL;DR
FeatLLM repurposes large language models (LLMs) as feature engineers: it asks an LLM to explicitly infer which features *should* matter for a task, converts those inferred "rules" into binary features, and trains a lightweight model on them. By forcing the LLM to first reason about feature–label relationships (before seeing the few labeled examples), FeatLLM filters out many irrelevant columns and shows substantially less performance degradation when noisy features are appended. That said, when unrelated but *closely related* signals are present, the LLM can still be misled. In high-stakes settings you should inspect the generated rules and add domain checks.

## What FeatLLM does, in one paragraph
Instead of using an LLM to produce an end-to-end prediction for every sample (which is expensive and fragile for large tables), FeatLLM uses the LLM to generate human-readable decision rules for each target class. Each rule becomes a binary feature ("does this sample satisfy rule R?"). A simple downstream model (a non-negative-weight linear model followed by softmax) is trained on those binary features to produce class probabilities. The process is repeated with bagging + ensembling so that many diverse rule-sets are combined, improving robustness and avoiding prompt-size problems.

Key practical details from the paper: rule extraction uses a two-step prompt (1) infer general tendencies/causal relations from feature descriptions and the task, then (2) use few-shot examples to derive concrete rules; the paper used 10 rules per class and an ensemble of ~20 trials, with GPT-3.5 as the backbone in experiments.

## Why this helps against spurious correlations
Two design choices are critical:

1. Explicit pre-example reasoning. The LLM is asked first to infer, from feature names and natural-language descriptions, which attributes *should* correlate with the target based on prior knowledge. This encourages the model to bring domain priors (e.g., "age and cholesterol are relevant for heart disease") to bear before it sees the few labeled examples, rather than letting the small sample dominate and create spurious associations.

2. Rule-focused outputs (rather than opaque logits). By forcing the model to produce interpretable rules, FeatLLM makes it possible to (a) generate discrete, semantically meaningful features; (b) filter or down-weight uninformative rules during downstream training; and (c) inspect what the LLM is actually relying on.

These choices lead to two practical effects: (a) only a small fraction of generated rules are based on obviously noisy columns (the authors observe noisy-column rules made up only ~1–2% of total in experiments), and (b) when random, irrelevant columns are appended to a tabular dataset, FeatLLM's performance degrades far less than several baselines.

## Experimental evidence (what the paper shows)
The authors evaluate FeatLLM across 13 tabular datasets in low-shot regimes. For the specific robustness test discussed in the paper, they took the Heart dataset and progressively attached unrelated columns sampled from the Adult dataset (columns that should be irrelevant to the Heart task). With the same 8-shot training protocol, FeatLLM showed the least performance drop compared to other methods (e.g., standard in-context LLM inference, TABLET, TabLLM, or conventional classifiers). This supports the claim that prior-knowledge-guided rule extraction helps resist spurious correlations when noisy features are present.

Additional experiment notes kept by the authors:

- The rule-generation step is repeated with randomness (higher temperature, different demonstration orders) and combined via ensemble; bagging (subsampling features/instances per trial) reduces prompt length and increases diversity.
- Generated rules are parsed into executable code by an LLM (to handle small syntactic variability) and then executed to produce binary features.
- A simple linear model with non-negative weights is trained on the binary features; weights are optimized with cross-entropy so the model can learn which rules are actually useful for the few-shot data.

## When FeatLLM can still fail
The paper is explicit about failure modes. Two important caveats:

1. Closely related but misleading signals. If the appended columns are not purely random noise but are *closely related* to the task in ways that are actually misleading (for example, features correlated with the label in the LLM's priors but not causal, or proxy features that encode spurious population structure), the LLM can infer plausible but incorrect rules. The authors observed that FeatLLM can learn spurious correlations and misunderstand causal direction in such cases.

2. Prior knowledge biases. LLMs are pretrained on broad text corpora and thus embed societal and topical priors. Those priors can dominate in the few-shot regime; if the prior is wrong or biased for your population or domain, the generated rules will reflect that.

In short: FeatLLM reduces the probability of learning arbitrary noise-based rules, but it does not make the system immune to systematic or domain-specific confounders.

## Practical recommendations
If you plan to use a feature-engineering approach like FeatLLM in practice, consider these steps to mitigate the remaining risks:

- Inspect the generated rules. Because rules are human-readable, spot-check them for plausibility and for unacceptable biased logic. Reject or modify rule-sets that are clearly misaligned with domain knowledge.
- Add domain constraints. Enforce invariants or forbid certain feature interactions when you know they are spurious or sensitive.
- Use bagging/ensembling judiciously. The ensemble of diverse rule sets is a major robustness source; tune ensemble size versus cost (the authors found gains saturate around 20 ensembles).
- Augment with domain data where possible. If you can supply a modest amount of additional labeled data or representative unlabeled data, the downstream weight tuning step is better able to filter out misfires.
- Treat the output as hypotheses. In high-stakes domains (healthcare, finance), treat FeatLLM's rules as candidate mechanistic explanations that require human validation or further statistical testing.

## Final thoughts
FeatLLM illustrates an effective pattern: use an LLM's prior knowledge to *propose* interpretable features, then rely on a cheap, trainable model to decide which of those features actually matter. That architecture greatly reduces vulnerability to random noisy columns because it encourages predictions grounded in prior relevance before being influenced by a tiny sample. However, when misleading but plausible signals exist, the method can still be tripped up — precisely because LLM priors make those signals look reasonable. The interpretability of rules is the saving grace: it gives practitioners a concrete lever to audit and correct the system.



# A Practitioner’s Guide to Applying FeatLLM: Data Prep, Costs, and Governance

FeatLLM reframes LLMs from black‑box predictors into automated feature engineers for few‑shot tabular learning. Instead of calling an LLM for every inference, you use an LLM (API access only is sufficient) to generate human‑readable rules, parse those rules into programmatic binary features, and fit a lightweight head (a non‑negative linear logit model) for inference. The result: strong few‑shot performance, low inference cost, and interpretable rule features you can inspect and govern.

This guide condenses the paper’s method into a practical checklist: how to prepare the data and prompts, how to run generation and parsing, model training and ensembling, budget/compute considerations, and governance recommendations (privacy, human review, drift & bias monitoring). All recommendations are grounded in the FeatLLM approach as described in the paper.

## 1) High‑level workflow recap (practical view)
- Prepare labeled k‑shot examples and natural‑language feature descriptions.
- Prompt an LLM to (a) reason about which features matter and (b) produce a fixed set of rules per class.
- Parse the LLM’s textual rules into executable code that computes binary features per rule.
- Fit a simple linear head per class: logit_k(x) = max(w_k, 0) · z_k(x), and softmax across classes to get probabilities.
- Repeat the rule generation/parsing/training process across multiple randomized trials (bagging + ensemble) and average predicted probabilities.

## 2) Data preparation and prompt best practices
FeatLLM’s prompt is structured into three parts. Prepare each piece carefully.

1. Basic information description (required)
   - Short task description framed as a question (e.g., “Does this patient have chronic heart failure? Yes or No?”).
   - Feature names and types (numeric / categorical) with concise definitions. For categorical features, list possible categories.
   - Few‑shot demonstrations: serialize each example as:
     "f1 is x1. ... fd is xd. Answer: y"
   - Keep the serialized examples compact and representative. FeatLLM is intended for few‑shot regimes (k small).

2. Reasoning instruction (important)
   - Ask the LLM to first reason from general knowledge about how features relate to the task (this pulls in prior knowledge).
   - Then ask it to use the few‑shot examples plus that prior step to derive explicit rules per class.
   - Limit the number of rules per class to control prompt length; the paper used 10 rules per class as a practical balance.

3. Response instruction (parsing‑friendly format)
   - Require a clearly delimited, machine‑parsable format for each rule (e.g., numbered list, explicit feature name, operator, threshold or category).
   - Provide type‑aware templates so the LLM knows whether to use numeric comparisons or categorical equality. This reduces type mismatches.

Why this structure? The two‑step reasoning (prior knowledge → example grounding) reduces spurious rules based purely on chance correlations in very small datasets.

## 3) Designing few‑shot examples
- Choose k examples that span the known variability of the target classes and capture edge cases where possible. FeatLLM is evaluated under k‑shot regimes (e.g., 4, 8, 16, 32 shots).
- Ensure each example’s feature serialization uses the same natural language feature names you provide in the description.
- Randomize the order of examples across generation trials to increase rule diversity (the paper observes that example order affects LLM outputs).

## 4) Generating rules and handling parsing
- Use a modest temperature (paper used 0.5 for GPT‑3.5) to balance creativity and fidelity; raise temperature for ensemble diversity.
- Ask for a fixed number of rules per class (paper: R = 10). This keeps the downstream binary feature vector dimension predictable.
- Parsing: instead of building complicated regex parsers, use the same LLM to translate the generated natural‑language rules into simple, executable code (e.g., a small Python function) and then run that code to compute binary features. The paper leverages the LLM’s code competence to handle syntactic variations (e.g., “greater than” → “>”).
- Always validate generated code in a sandbox before running on production data. Check for malformed expressions or malicious constructs.

## 5) Training the lightweight head
- Feature matrix: for each sample and each rule, compute a binary indicator z ∈ {0,1} of whether the rule is satisfied. For c classes with R rules per class, you have c·R binary columns (or you can structure per‑class feature groups).
- Model: a linear model per class with non‑negative weights. The paper uses:
  - logit_k^i = max(w_k, 0) · z_k^i
  - p^i = Softmax([logit_1^i, ..., logit_c^i])
- Optimization: cross‑entropy loss. Example training hyperparameters used in the paper:
  - Optimizer: Adam
  - Learning rate: 0.01
  - Epochs: 200 (select epoch via k‑fold cross validation)
- Purpose of non‑negative projection: ensure rules only add positive evidence for their target class; it simplifies interpretation and avoids rules actively reducing a class likelihood.
- After training, rules with near‑zero learned weight can be pruned (the paper used a threshold of 0.1 when analyzing rule usefulness).

## 6) Bagging & ensembling (scaling and robustness)
- Repeat the entire rule‑generation → parsing → fit process T times and average the predicted probabilities across the T trained heads.
- Use bagging to sample subsets of columns and/or training examples per trial. This reduces prompt length per trial and increases rule diversity—useful on high‑dimensional tables or when your LLM has a limited context window.
- The paper found performance gains saturate around T ≈ 20 ensembles; T=20 and R=10 were used as practical defaults.
- To increase diversity across trials: randomize example order, set higher temperature for LLM calls, and vary the feature subset fed to each trial.

## 7) API & compute budgeting
- FeatLLM is designed for API‑only setups and does not require fine‑tuning the LLM model weights.
- The paper reports that building the ensemble requires only a modest number of API queries (on the order of a few dozen). In their setup they used 30 API queries during training/feature generation (this number depends on your T and how many parsing calls you make).
- Inference cost is low: once the rule set is built and the lightweight head is trained, runtime inference does not involve LLM calls (binary rule checks + a linear dot product + softmax). This contrasts with end‑to‑end LLM methods which require an LLM call per sample at inference.
- Practical budgeting steps:
  - Estimate number of trials T and parsing calls per trial (rule generation + parsing = 2 API calls per trial in a simple pipeline).
  - Multiply by cost per API call of your chosen model (e.g., GPT‑3.5). Add margin for retries and human review rounds.
  - The largest cost savings come from eliminating per‑sample inference calls.

## 8) Privacy and secure handling of data
- FeatLLM requires exposing only the few‑shot examples and feature metadata to the LLM API. Avoid sending full datasets or sensitive identifiers.
- Minimize sensitive content in prompt examples. Where possible, use de‑identified or synthetic examples that preserve distributional characteristics but remove direct identifiers.
- If your provider supports it, use models or endpoints with data usage protections (do not retain prompts) and enterprise agreements that restrict logging.
- Consider on‑premise LLMs or hosted private endpoints if you cannot risk any data leaving your environment. FeatLLM’s architecture does not require model training rights, but it does require an LLM that can be queried.

## 9) Human‑in‑the‑loop rule review and governance
FeatLLM’s output (rules) is naturally interpretable and therefore amenable to human oversight. Make rule review a standard step before deployment.

- Triage and labeling:
  - Present generated rules grouped by class, sorted by learned weight from the trained head. High‑weight rules are most impactful and should be prioritized for review.
- Review criteria:
  - Semantic correctness: does the rule match domain understanding?
  - Privacy risk: does the rule rely on sensitive attributes (e.g., race, protected class)? If so, consider removing or mitigating.
  - Business constraints: are the rule thresholds realistic and actionable?
- Edit or augment rules as necessary. Because rules are programmatic, you can directly modify them and re‑compute binary features without re‑querying the LLM.
- Maintain an auditable record: store the prompt used, the generated rules, the parsed code, and the learned weights. This makes it possible to trace how a decision was derived.

## 10) Monitoring drift and bias over time
Even with few‑shot training and human review, models can degrade or develop undesirable behavior.

- Performance monitoring:
  - Track standard metrics (AUC, calibration) on incoming labeled data or periodic sampled labeling.
  - Compare distribution of binary rule activations over time. Sudden shifts in rule activation frequency signal input distribution drift.
- Bias monitoring:
  - Monitor rule activations and outcome rates across sensitive subgroups. Because features are explicit rules, it’s straightforward to test whether a rule disproportionately activates for a subgroup.
  - If a rule is found to be discriminatory or correlated with a protected attribute, consider removing or constraining it and retraining the lightweight head.
- Retraining cadence:
  - Because FeatLLM is fast at inference (no LLM calls per sample), you can retrain the lightweight head frequently with newly labeled data. For major distributional shifts, re‑run the rule generation pipeline (LLM calls) to obtain updated rules.
- Alerts and governance:
  - Set thresholds on metric degradation and rule‑activation drift that automatically trigger human review, potential rule removal, or a full pipeline rerun.

## 11) Limitations and when FeatLLM is most appropriate
- FeatLLM targets few‑shot tabular learning: it shines when labeled data is scarce and prior knowledge (captured by the LLM) is helpful.
- It assumes you can provide natural language feature descriptions and representative few‑shot examples.
- If you have large labeled datasets and can train powerful tabular models (XGBoost, RandomForest, etc.), traditional supervised learning may be preferable for raw accuracy at scale.
- Take special care when features or labels require extremely precise thresholds or complex multi‑feature interactions that are hard to express as rules; FeatLLM focuses on rule‑like features.

## 12) Quick start checklist
- [ ] Prepare concise task description and natural language feature definitions.
- [ ] Select k representative labeled examples and serialize them consistently.
- [ ] Build the prompt with (1) basic info, (2) two‑step reasoning instruction, and (3) response template for parsable rules.
- [ ] Choose ensemble settings: T ≈ 20 trials, R ≈ 10 rules per class are reasonable defaults from the paper.
- [ ] Use the LLM to generate rules and then ask the LLM to output small executable parsing code; validate in sandbox.
- [ ] Compute binary features, fit the non‑negative linear head (Adam, lr=0.01, ~200 epochs with cross‑validation).
- [ ] Sort rules by learned weight and run a human review on top rules.
- [ ] Deploy inference pipeline (no LLM calls per sample). Monitor performance, drift, and fairness metrics. Re‑run generation when needed.

## Closing notes
FeatLLM provides a practical middle ground: you retain the LLM’s broad prior knowledge and reasoning for feature engineering, but you avoid the cost, latency, and governance difficulties of calling an LLM for every prediction. Because the pipe produces explicit rules, it also supports human oversight, makes auditing easier, and integrates well into governance workflows. Follow the checklist above to move from raw columns to a production‑ready, low‑cost, and auditable few‑shot model pipeline.
