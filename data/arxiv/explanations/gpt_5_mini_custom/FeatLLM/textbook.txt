\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Motivation and Overview of FeatLLM

# Why few-shot learning on tabular data matters in real-world applications
Many real-world prediction problems are naturally expressed as tabular data: rows are cases (patients, customers, regions) and columns are heterogeneous attributes (age, diagnosis codes, transaction amounts, categorical labels). In practice, collecting large labeled datasets for every new prediction problem is costly or impossible. Labels may require expert human effort (e.g., medical diagnoses) or occur rarely (e.g., fraud events), so practitioners often must build predictive systems from only a handful of labeled examples. This is the few-shot learning regime: we wish to learn useful predictors when only a small number $k$ of labeled examples are available.

Few-shot learning for tabular data is important because tabular data powers decision-making in finance, healthcare, policy, and many industrial domains. Models that learn effectively from limited labels reduce the need for expensive annotation, allow faster deployment of models for new tasks, and help avoid overfitting when data are scarce. At the same time, tabular datasets are heterogeneous: they mix continuous and categorical variables, their semantics are often expressed in column names and descriptions, and feature interactions can be complex and domain-specific. These properties make few-shot tabular learning a distinct and challenging problem that benefits from methods able to bring external knowledge and domain-aware reasoning into the feature design and learning process.

# Challenges with end-to-end LLM inference: per-sample cost, fine-tuning constraints, and prompt length limits
Large Language Models (LLMs) have emergent abilities to reason about unseen tasks when provided with task descriptions and a few examples. It is therefore natural to try to apply them directly to tabular prediction by serializing a row into text and asking the LLM to predict the label. However, this end-to-end LLM inference approach has three practical limitations.

First, per-sample cost and latency. If an LLM is used as a black-box predictor, each test sample requires one forward pass through the LLM. For models accessed via paid APIs (the common deployment pattern for recent high-capacity LLMs), that means paying for inference per sample and experiencing high latency for each prediction. This makes end-to-end LLM inference expensive and often impractical for production systems needing many predictions or low-latency responses.

Second, fine-tuning constraints. Many successful LLM-based tabular methods apply parameter-efficient fine-tuning to adapt an LLM to the target task. But in practice, the largest, best-performing LLMs are offered only as closed APIs without access to their weights or fine-tuning endpoints. Methods that require fine-tuning cannot be applied to such models. Even when fine-tuning is available, it increases operational complexity and may have substantial computational cost.

Third, prompt length and feature-count limitations. Tabular datasets sometimes have many features or long natural-language feature descriptions. Serializing whole rows with long feature descriptions plus examples can exceed the LLM input context window or push against its practical prompt-size limits. When prompts become too long, performance can degrade or the approach becomes infeasible.

These three constraints—high per-sample inference cost, lack of universal fine-tuning access, and prompt-size limits—motivate finding alternative ways to leverage LLMs that capture their reasoning and world knowledge while avoiding the practical downsides of per-sample, end-to-end LLM prediction.

# FeatLLM at a glance: LLM-driven rule extraction, binary feature generation, simple downstream modeling
FeatLLM reimagines how to use LLMs for few-shot tabular learning. Instead of querying the LLM for each test example’s label, FeatLLM uses the LLM as a feature engineer. The core idea is to have the LLM produce human-interpretable rules that describe conditions associated with each class (for example, "age > 65 and prior_disease = yes"), convert those rules into binary features, and then train a lightweight downstream model on those binary features to perform final prediction.

Formally, suppose we have a labeled tabular dataset
\[ \mathcal{D} = \{(\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^N, \]
where each input $\mathbf{x}^i$ is a $d$-dimensional row and we have natural-language feature names and optional descriptions $F = \{f_j\}_{j=1}^d$. In the few-shot setting we use only $k \ll N$ labeled samples as demonstrations.

FeatLLM proceeds in three conceptual stages. First, using carefully designed prompts that combine problem description, feature descriptions, and a small set of serialized demonstrations, the LLM is asked to perform structured reasoning and output a fixed number of rules per class. The prompt explicitly separates two reasoning steps: (1) infer, from general knowledge, which features are likely to be causally or semantically related to the task, and (2) using the few-shot examples plus the prior knowledge from step (1), propose concrete rules that distinguish classes. The prompt also constrains response formatting to make the outputs parseable.

Second, the natural-language rules produced by the LLM are parsed into executable code that evaluates whether a given row satisfies each rule. Parsing is itself handled by the LLM: the rules and a function description are provided to the LLM, which emits simple code (e.g., Python expressions). That code is executed (for instance via Python’s exec()) to transform the dataset into binary features. For class $k$ we obtain binary vectors $\mathbf{z}_k^i \in \{0,1\}^R$ indicating which of the $R$ rules for that class are satisfied by sample $i$.

Third, a simple downstream model is trained on the new binary features to estimate class likelihoods. The paper uses a linear model without bias whose logits for class $k$ are computed as
\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,
\]
where $\mathbf{w}_k$ are trainable weights that are projected to the non-negative orthant via $\max(\mathbf{w}_k,0)$ to ensure rule features do not reduce a class’s likelihood. The class probability vector is then
\[
\mathbf{p}^i = \text{Softmax}([\text{logit}_1^i,\ldots,\text{logit}_c^i]).
\]
These weights are learned by minimizing cross-entropy on the few-shot training samples, typically with a small optimization routine (Adam, learning rate 0.01, trained for a modest number of epochs with cross-validation for epoch selection).

The LLM is used only to generate features (rules) and code during the setup/training phase. At inference time, predictions are made by applying the parsed rules and the learned lightweight model, avoiding any per-sample LLM calls.

# Key benefits: API-only access, no LLM fine-tuning, reduced inference latency, prompt-size scalability via bagging
FeatLLM’s design delivers several practical advantages over end-to-end LLM prediction and many other LLM-based tabular approaches.

First, API-only access. Because FeatLLM uses the LLM only to generate rules and parsing code during feature engineering, it does not require fine-tuning the LLM. This makes it compatible with models that are available only via inference APIs and not in a form that can be trained or adapter-tuned. In the experiments the authors use GPT-3.5 as the LLM backbone, but the framework is agnostic to which LLM is used so long as it can perform the prompted reasoning.

Second, low inference cost and latency. After the rule generation and downstream weight tuning phases are complete, every prediction is carried out by evaluating a small set of binary features and a linear model. No LLM calls are required at test time, so FeatLLM’s inference time is comparable to conventional methods like logistic regression or tree ensembles rather than to per-sample LLM prediction, which is orders of magnitude slower and more expensive.

Third, overcoming prompt-length constraints with bagging and ensembling. If the dataset has many columns or long feature descriptions, serializing all features and examples into a single prompt can exceed the LLM’s input limits or become unwieldy. FeatLLM mitigates this by using a bagging strategy: in each trial of an ensemble, it randomly samples a subset of features and a randomized order of demonstrations, asks the LLM for rules restricted to that subset, and repeats this process $T$ times. The multiple trials produce diverse rule sets which are parsed into binary features and fitted with separate downstream weight vectors; predictions are averaged across the ensemble. This serves two purposes: it reduces prompt size per LLM query and leverages ensemble diversity to compensate for occasional incorrect or incomplete rule sets. In the paper, the authors set $T=20$ and $R=10$ rules per class as practical defaults, and use a moderately high sampling temperature and randomized demonstration order to induce diversity.

Fourth, interpretability and robustness. The rules are human-readable conditions that can be inspected to understand what the model deems important. Moreover, when combined with the downstream linear weighting and ensembling, FeatLLM can filter out noisy or irrelevant rules: weights of unhelpful rules tend to be small after training and thus contribute little to predictions.

# Summary of results: robust performance across 13 datasets, ~10% average improvement over TabLLM/STUNT
The authors evaluate FeatLLM across 13 tabular datasets spanning multiple domains and difficulty levels, including standard UCI datasets (Adult, Bank, Credit-g, Heart, Myocardial), datasets not likely seen during LLM pretraining (Cultivars, NHANES), and synthetic problems (Sequence-type, Solution-mix). The experiments focus on few-shot settings (e.g., 4 to 32 shots) and compare FeatLLM to a range of baselines: classical tabular learners (logistic regression, XGBoost, Random Forest), methods that leverage unlabeled data (SCARF, STUNT), pre-trained synthetic priors (TabPFN), and LLM-based approaches (in-context prompts, TABLET, TabLLM).

Key empirical findings reported in the paper include:
- Strong few-shot accuracy: FeatLLM consistently ranks first or second across datasets and shot settings. With only 4 labeled examples, FeatLLM achieves performance comparable to conventional tabular baselines trained with 32 shots, illustrating its data efficiency.
- Improvement over recent LLM-based and few-shot methods: FeatLLM significantly outperforms alternatives such as TabLLM and STUNT by about 10% on average in the reported comparisons. Its rule-based feature extraction appears especially effective in low-shot regimes.
- Practical runtimes: because FeatLLM does not require an LLM call per test sample, its inference cost is low and comparable to traditional ML methods. The overall training cost (the number of LLM API queries) is modest: the paper reports that FeatLLM needs only about 30 API queries during setup for typical experiments, which is practical even when using paid LLM APIs.
- Robustness to spurious features: when irrelevant columns are appended to a dataset (to simulate spurious correlations), FeatLLM degrades less than competing methods. Its reasoning-instruction prompt and emphasis on prior knowledge tend to avoid extracting rules that depend on unrelated columns; only a small fraction (1–2%) of generated rules are based on noisy columns in the experiments.
- Feature quality and automatic filtering: many rules generated by the LLM yield binary features that correlate positively with the target (measured via AUROC). After training the downstream linear model, rules that are not informative receive low learned weights and are effectively filtered out. This demonstrates that even if some LLM-generated rules are noisy, the combination of rule-based features plus learned weights provides resilience.

Beyond raw accuracy, ablation studies in the paper demonstrate the importance of particular design choices. Omitting weight tuning (i.e., summing rule indicators rather than learning weights), removing the ensemble, omitting feature descriptions in the prompt, or skipping the “Step 1” reasoning instruction all reduce performance. The benefit of weight tuning is larger when more shots are available, indicating that learning weights helps exploit additional labeled data. Conversely, the feature descriptions and structured reasoning instructions are most important in smallest-shot regimes, where the LLM’s prior knowledge must compensate for minimal labeled evidence. The ensemble consistently improves performance, especially by combining diverse rule sets generated under randomized prompt conditions.

Taken together, these results show that an LLM can serve effectively as a feature-engineering engine: by using few-shot demonstrations and carefully structured prompts, the model extracts rules grounded in prior knowledge and the few examples, those rules can be parsed and executed to form features, and a simple downstream model can then achieve strong prediction performance with low inference cost and without LLM fine-tuning.

# Closing perspective
FeatLLM demonstrates a practical and principled way to leverage LLMs’ reasoning and world knowledge for tabular prediction under severe label scarcity. By shifting the role of the LLM from per-sample predictor to feature engineer, the framework preserves the benefits of in-context and prior-knowledge-driven reasoning while avoiding the operational issues of per-sample LLM inference and fine-tuning requirements. The combination of structured prompting (to elicit causal or relevant feature-to-target relationships), LLM-assisted parsing of natural-language rules into executable code, linear weighting of rule-based binary features, and ensembling with bagging yields a system that is interpretable, computationally efficient at test time, and empirically strong across diverse tabular tasks.

Background: Tabular ML, Few-Shot Learning, and Language-Interfaced Methods

This chapter surveys the foundational concepts and prior work that motivate FeatLLM. We cover classical tabular machine learning baselines, the special challenges and strategies of few-shot learning on tabular data, why common augmentation strategies struggle for heterogeneous tabular features, and the emerging class of language-interfaced tabular learning methods that leverage large language models (LLMs). Throughout, we emphasize the perspectives and limitations described in the paper "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning", since those observations shape the design choices of FeatLLM.

# Classical baselines: Logistic Regression, XGBoost, Random Forest

Classical supervised methods remain strong baselines on tabular datasets and are the common point of comparison for few-shot and LLM-based approaches. Three widely used methods are logistic regression, Random Forests, and gradient-boosted trees (XGBoost). Understanding their strengths and failure modes clarifies why alternative approaches are explored for few-shot regimes.

Logistic regression is a simple parametric model for classification that models the conditional probability of a class with a linear function of the inputs. In the binary case one commonly writes
\[
p(y=1 \mid \mathbf{x}) = \sigma(\mathbf{w}^\top \mathbf{x}),
\]
where $\sigma(\cdot)$ is the logistic (sigmoid) function and $\mathbf{w}$ are the learned weights. Logistic regression is interpretable, fast to train, and works well when the relationship between features and log-odds is approximately linear and features are informative. Its weakness in practice is that it cannot capture nonlinear interactions or complex decision boundaries unless the input features are engineered (polynomial terms, interactions, etc.). In few-shot settings, the small number of labeled examples can make high-variance estimators or complex models unstable, and the simplicity of logistic regression can sometimes be an advantage.

Random Forests are ensembles of decision trees constructed by bootstrap sampling the training data and randomly selecting subsets of features at each split. Each tree produces a prediction and the forest aggregates (for classification by majority vote or averaging class probabilities). Random Forests are nonparametric, can capture nonlinear interactions, and are relatively robust to overfitting because of bagging and randomized splits. They work well across many tabular tasks without much feature engineering. However, they can still overfit with very few labeled examples if trees are allowed to grow deep or if spurious correlations exist in the small training set.

XGBoost is a high-performance implementation of gradient-boosted decision trees. The model builds trees sequentially, where each new tree fits the residuals (errors) of the previous ensemble, optimizing a differentiable objective. XGBoost provides fine-grained control over regularization, tree depth, and learning rate, and often yields state-of-the-art performance on tabular benchmarks when sufficient labeled data is available. But gradient-boosted trees are data hungry relative to extremely simple models: when only a handful of labeled samples are available, their capacity can lead to variance and poor generalization unless strong regularization or external priors are available.

All three methods are commonly used as baselines in the few-shot tabular benchmarks reported in the paper. They provide fast inference and, in the case of logistic regression, straightforward interpretability. Their limitations in low-shot regimes motivate approaches that inject prior knowledge or transfer information from other sources.

# Few-shot learning in tabular data: semi/unsupervised pretraining, transfer learning, synthetic priors (e.g., TabPFN)

Few-shot learning asks how to obtain reliable predictive performance from only a small number of labeled examples (the paper studies experiments where the training set is restricted to $k$ labeled samples, with $k \ll N$). Formally, given a labeled dataset
\[
\mathcal{D} = \{ (\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^{N},
\]
few-shot settings consider learning from a subset of size $k$ sampled from $\mathcal{D}$.

Several strategies have been explored to cope with the scarcity of labels on tabular data.

One strategy is to leverage additional (often unlabeled) data via semi-supervised or self-supervised pretraining. In this line, models are pre-trained with objectives such as masking out parts of inputs and reconstructing them (a reconstruction objective) or contrastive objectives that encourage similar views of the same instance to have similar representations. The goal is to learn task-agnostic representations that transfer to downstream tasks with few labels. The paper cites approaches that apply masking/reconstruction or contrastive learning for tabular data; these can reduce sample complexity when compatible unlabeled datasets are available. However, the heterogeneous nature of tabular features (mixed numeric, categorical, and domain-specific encodings) makes designing universally effective augmentations and pretraining tasks challenging. As the paper notes, such unsupervised objectives "have not been notably effective in few-shot settings" for tabular data because augmentations that make sense for images or text do not transfer neatly to arbitrary tables.

A complementary strategy is transfer learning across many related tabular datasets. Methods like TransTab (mentioned in the paper) train models on a broad collection of tables to learn semantic relationships between columns, e.g., from column names and distributions, and then fine-tune or adapt to a target table. Transfer learning can capture recurring statistical patterns and priors that help in new tasks with limited labels. The paper highlights that transfer approaches can enable zero-shot or few-shot inference by exposing models to a diversity of table structures during pretraining.

Another route is to construct synthetic priors. TabPFN is an example cited in the paper: it mixes different kinds of generative distributions to synthesize diverse datasets and pre-trains a classifier (a Bayesian neural network in the TabPFN work) on that synthetic mixture. After pretraining, the model can perform inference on a target task by ingesting the (few-shot) training examples together with test samples without additional training. The synthetic prior provides a strong inductive bias that can outperform traditional methods in low-shot regimes because the pretraining implicitly encodes plausible data-generating processes.

Each of these few-shot strategies tries to inject prior knowledge—either through additional data, pretraining objectives, or synthetic distributions—so that the small labeled set carries less of the entire burden of learning. The paper positions FeatLLM as an alternative mechanism for injecting prior knowledge: instead of relying on unlabeled data or synthetic pretraining, FeatLLM leverages the knowledge embedded in large language models to construct informative features from a few examples.

# Limitations of augmentations for heterogeneous tabular features

A recurring practical difficulty for all the methods above is the heterogeneity of tabular features. Tabular datasets typically mix continuous numeric variables, categorical variables with many possible values, ordinal attributes, and domain-specific codes. This heterogeneity complicates the design of augmentations, pretext tasks, and synthetic data generation that are simultaneously valid across datasets.

For augmentation-based semi-supervised learning, choosing a meaningful transformation (e.g., noise injection, feature masking, or synthetic perturbations) requires domain understanding: a perturbation that preserves class labels in one dataset might destroy the label signal in another. Consequently, the paper emphasizes that it is "challenging to find universally applicable augmentations" and that these strategies have not shown large gains in few-shot tabular tasks.

Synthetic prior methods (like TabPFN) must also commit to a family of generative processes when producing training data. If the synthetic priors do not cover the kinds of distributions that arise in the real target dataset, the transfer can be limited. Likewise, transfer-learning approaches that rely on column names or cross-dataset statistics depend on a match between source tasks and the new problem.

Because these limitations are structural—coming from the immense variability of tabular data—an appealing alternative is to bring in external, high-level prior knowledge that is not tied to a single augmentation or synthetic distribution. Large language models embody much such high-level knowledge in textual form, which motivates language-interfaced methods discussed next.

# Language-interfaced tabular learning: data serialization, prompts, in-context learning vs parameter-efficient tuning

Language-interfaced tabular learning frames a tabular problem as a text-based task so that it can be processed by an LLM. The core idea is to "serialize" tabular inputs and their descriptions into natural language, present a task description, and then ask the LLM either to predict labels directly or to provide intermediate outputs (explanations, rules, etc.). The paper describes this paradigm and the two main modes of using LLMs: in-context learning and parameter-efficient tuning.

Serialization is the process of converting a row of table data into a textual example. A common serialization format used in prior work and in the paper is
\[
\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = ``\ f_1\ \text{is}\ \mathbf{x}^i_1.\ ...\ f_d\ \text{is}\ \mathbf{x}^i_d.\ \ \text{Answer:}\ \mathbf{y}^i\ ",
\]
where $F=\{f_j\}_{j=1}^d$ denotes feature names and definitions. By including natural language descriptions of features and the target (e.g., "Does this patient's record indicate chronic heart failure?"), the prompt gives an LLM both the raw feature values and human-level context that can activate its prior knowledge (for example, commonsense medical knowledge about age and disease risk).

In-context learning uses only carefully constructed prompts and a small number of example demonstrations; the LLM is not updated. A prompt typically contains a task description, a handful of serialized input–label pairs (the few-shot demonstrations), and a final serialized query whose label the LLM is asked to produce. The advantage of in-context learning is that it requires no model training and works with API access to the LLM. However, in-context inference typically still requires invoking the LLM for every query at test time, which is computationally expensive.

Parameter-efficient tuning methods adapt an LLM to the target task while only modifying a small number of additional parameters (e.g., low-rank adapters or techniques like IA3 and LoRA). The paper mentions that some prior works apply such tuning to improve accuracy. These methods can yield higher performance but need access to training procedures and model checkpoints; that access is often unavailable for many high-performance LLMs that are only exposed through an inference API. In addition, tuning can be costly and time-consuming, and tailored tuning may not be feasible in real-world industrial settings where only inference calls are permitted.

Two practical constraints specific to language-interfaced tabular learning are emphasized in the paper. First, end-to-end LLM-based predictions usually require at least one LLM call per sample at test time, creating a significant per-sample cost. Second, prompt length becomes a limiting factor: when a dataset has many features, serializing a full row plus feature descriptions and several demonstrations can exceed the model's context window or degrade performance. These constraints motivate methods that can leverage LLMs for their prior knowledge but avoid heavy per-sample runtime dependence and prompt-size bottlenecks—one of the central motivations behind FeatLLM.

# Representative methods: In-context prompting, TABLET, TabLLM; their pros/cons in low-shot settings

Several representative language-interfaced methods have been applied to tabular learning, and the paper contrasts their characteristics and limitations. Understanding these methods helps position FeatLLM as a different trade-off among accuracy, runtime cost, and accessibility to LLM internals.

In-context prompting (the basic form of LLM-based prediction) places a small number of serialized examples and the test query into the prompt and asks the LLM to generate the label. Its main advantages are simplicity and the ability to operate with only API access—no training. It can exploit the LLM's world knowledge via natural-language feature descriptions. However, it suffers from high inference cost (a full LLM call per test sample), does not scale well to many features because of prompt length limitations, and can be sensitive to prompt design and example ordering.

TABLET is a hybrid approach that augments LLM prompts with hints from an external classifier, for example by using rule-sets and prototypes provided by a lightweight model. The idea is to combine structured, interpretable hints with LLM reasoning to improve few-shot inference quality. While TABLET can strengthen the prompt content and sometimes improve accuracy, it still relies on per-sample LLM inference. Its performance also depends on the external hints' quality and the complexity of serialized tables.

TabLLM is an approach that applies parameter-efficient tuning (e.g., IA3) to adapt an LLM to tabular tasks. By fine-tuning a small set of parameters, TabLLM can substantially improve accuracy in few-shot settings compared to vanilla in-context prompting. However, TabLLM requires access to model checkpoints or a tuning API, which is infeasible for many proprietary, high-performing LLMs that are available only through inference APIs. Additionally, TabLLM still uses the LLM at inference time for each sample, so per-query latency and cost remain.

The paper empirically observes several practical limitations of these representative methods. Methods that rely on the LLM at inference time (in-context, TABLET, TabLLM) require repeated LLM calls, which increase latency and cost. Prompt-length limitations cause failures or degraded performance on datasets with many features (e.g., datasets with more than a hundred attributes). Parameter-efficient tuning methods, while improving accuracy, cannot be applied to black-box, API-only LLMs. These observations underscore the desire for approaches that harness LLM knowledge but avoid per-sample inference dependence and remain compatible with API-only access.

# Synthesis: why these backgrounds motivate FeatLLM

The preceding background shows three recurring themes. First, classical tabular learners have favorable properties (fast inference, solid performance when enough labels exist), but can struggle in few-shot regimes unless provided with strong inductive biases. Second, many few-shot strategies—pretraining, transfer, and synthetic priors—attempt to supply such biases, but they are limited by the heterogeneity of tabular data or by the availability of unlabeled data and computational resources. Third, language-interfaced methods expose a promising source of high-level prior knowledge via LLMs, but their practical deployment is hindered by per-sample inference costs, prompt-size limits, and restricted access to model internals for tuning.

FeatLLM is motivated by the desire to combine the advantages of these perspectives while mitigating their limitations. Rather than using LLMs to produce a label for each sample at inference time, FeatLLM uses LLMs as automated feature engineers: prompts guide the LLM to extract human-readable rules and criteria from a few demonstrations and feature descriptions. Those rules are parsed into binary features that indicate whether a sample satisfies each rule, and a lightweight downstream model (a simple linear model with non-negative weights) is trained on these features. By moving the bulk of the LLM usage to an offline feature-generation stage, FeatLLM reduces per-sample inference cost, permits use with API-only LLMs (no fine-tuning of the LLM), and—through ensemble and bagging—mitigates prompt-size constraints and improves robustness. The rest of this book explains how the prompt design, rule parsing, and ensemble methods are constructed to realize this objective and evaluates their empirical performance against the baselines discussed here.

Problem Setup and Notation

# Dataset notation: N labeled samples, d features, class labels
We consider a standard supervised tabular classification problem where the available data consist of $N$ labeled samples. Each sample is written as a pair $(\mathbf{x}^i,\mathbf{y}^i)$ for $i=1,\dots,N$ and the full dataset is denoted
\[
\mathcal{D}=\{(\mathbf{x}^i,\mathbf{y}^i)\}_{i=1}^N.
\]
Each input $\mathbf{x}^i$ is a $d$‑dimensional vector that collects the values of $d$ attributes (columns) for the $i$‑th sample. Importantly, in tabular settings these $d$ attributes may be heterogeneous in type: some columns are numeric, some are categorical, and others may be ordinal or otherwise structured. We therefore treat $\mathbf{x}^i$ as a general $d$‑dimensional vector whose components $\mathbf{x}^i_j$ correspond to the value of the $j$‑th feature for sample $i$.

The label $\mathbf{y}^i$ is drawn from a predefined finite set of classes. We denote by $c$ the number of distinct classes, and write the label space as $\{1,\dots,c\}$. For binary classification $c=2$, and for multi‑class problems $c>2$. Throughout the paper the setup remains the standard supervised classification paradigm: given a small collection of labeled examples, the goal is to infer a predictor that estimates class likelihoods or class assignments for new samples.

# Feature names and natural language definitions
A distinctive element in the FeatLLM framework is that every column (feature) comes with a human‑readable name and, optionally, a short natural language description or definition. We collect these names into the set
\[
F=\{f_1,f_2,\dots,f_d\},
\]
where $f_j$ is the name (and possibly short description) associated with the $j$‑th column. These natural language descriptions serve two roles in FeatLLM: they (1) disambiguate feature types and expected values for automated processing, and (2) provide semantic context that a large language model can use as prior knowledge when reasoning about which features are likely to be relevant to the task. Because the features are heterogeneous, the descriptions will typically indicate the value type (e.g., numeric, categorical) and may enumerate possible categories for categorical attributes. Including this metadata in the problem statement enables downstream components to form human‑readable rules and also assists automated parsing when rules are later converted into executable feature checks.

# k-shot training subset selection
FeatLLM is designed for the few‑shot regime. Concretely, in experiments the framework selects a small subset of $k$ labeled examples from the full dataset to serve as the supervised training data, with $k<N$. This $k$‑shot subset is drawn at random from $\mathcal{D}$ and used both to demonstrate examples to the language model during in‑context prompting and to fit the simple downstream predictor that uses the LLM‑generated features. The paper reports results for multiple values of $k$ (for example, $k=4,8,16,32$ in some experiments), examining how performance scales with the number of labeled examples.

Because the selection of the $k$ examples can affect performance in the few‑shot setting, the experimental protocol repeats runs with different random draws of the $k$‑shot subset and reports averages and standard deviations over these repetitions. This random sampling process and repetition are part of the evaluation methodology that quantifies variability due to few‑shot sampling.

# Binary and multi-class classification scope
The problem formulation covers both binary and multi‑class classification tasks. The general notation $c$ for the number of classes accommodates either case: when $c=2$ the task is binary classification, and when $c>2$ it is multi‑class. FeatLLM’s internal representation of rules and generated features is class‑wise: during rule extraction the language model is asked to produce rules associated with each class, and the downstream feature construction produces per‑class binary indicators that measure whether a sample satisfies the rules tied to a specific class.

To make the downstream probabilistic modelling concrete, denote by $\mathbf{z}_k^i\in\{0,1\}^R$ the binary feature vector for sample $i$ corresponding to class $k$, where $R$ is the number of rules (binary checks) generated per class. A simple linear scoring model for class $k$ can then be written as
\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,
\]
where $\mathbf{w}_k\in\mathbb{R}^R$ are trainable weights and the $\max(\cdot,0)$ operator projects these weights into the non‑negative orthant so that each rule only contributes non‑negatively to its associated class score. Combining the class logits into a probability vector is done via the softmax:
\[
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big).
\]
This formulation is general: it handles binary problems (where softmax over two logits is equivalent to a logistic probability) and multi‑class settings with $c>2$.

# Evaluation metrics overview (AUC/AUROC focus)
In the few‑shot tabular experiments reported in the paper, the primary evaluation metric is the area under the receiver operating characteristic curve (AUROC, often abbreviated AUC). AUROC measures the trade‑off between true positive rate and false positive rate across decision thresholds, and it is commonly used when class imbalance can affect accuracy judgments; it evaluates the quality of a probabilistic scoring function rather than a single thresholded classifier. For multi‑class problems one typically reports either per‑class AUROC values or a macro‑averaged AUROC; the paper reports AUC values consistently to compare methods across datasets and shot counts.

Practically, because the few‑shot setting yields higher variance across random splits of the training set, the experimental procedure repeats each setting multiple times with different random choices for the $k$‑shot subset (the paper uses three repeats) and then reports the mean and standard deviation of the AUROC across those repeats. This reporting convention makes it possible to compare both average performance and stability between FeatLLM and baseline methods in the low‑data regime.

Summary
This chapter established the formal notation used throughout the FeatLLM work: a dataset $\mathcal{D}=\{(\mathbf{x}^i,\mathbf{y}^i)\}_{i=1}^N$ with $d$ heterogeneous features described by natural‑language names $F=\{f_j\}$, a small randomly sampled $k$‑shot training subset, and a classification target with $c$ classes. FeatLLM: Architecture and End-to-End Workflow

# Overview of the FeatLLM pipeline
FeatLLM is an end-to-end framework that repurposes a large language model (LLM) as an automated feature engineer for few-shot tabular learning. Rather than treating the LLM as a black-box predictor that must be invoked for every test sample, FeatLLM asks the LLM to produce human-readable decision criteria (rules) for each class, converts those rules into executable code, applies the code to the dataset to produce binary features, and fits a simple downstream model on those features. The key idea is to capture the LLM’s prior knowledge and reasoning about which feature conditions are relevant for each class, and to make those conditions reusable as features that any inexpensive model can use at inference time.

At a high level, FeatLLM follows this sequence for each trial of an ensemble: (1) prepare a prompt that contains task and feature descriptions and a few demonstrations; (2) query the LLM to extract a fixed number of rules per class (the rule-extraction stage); (3) ask the LLM to convert its natural-language rules into executable code and run that code to generate binary features (the parsing stage); (4) train a lightweight classifier on the resulting binary features to produce class likelihoods; and (5) repeat with bagging and ensembling to improve robustness and mitigate prompt-size limitations. This chapter details each stage, the motivations behind design choices, and how components interact to produce accurate, efficient, and interpretable predictions.

# Two-stage use of LLMs: (1) rule extraction; (2) rule parsing into executable code
FeatLLM employs the LLM in two distinct stages. The first stage asks the LLM to reason about the task and produce rules that characterize when a sample should be assigned to each class. The second stage asks the LLM to parse or translate those natural-language rules into small, executable code snippets that can be run on the tabular data to create binary indicators.

Rule extraction is driven by a carefully structured prompt that contains three parts: a basic information description, a reasoning instruction, and a response instruction. The basic information description supplies the task phrased as a question (for example, "Does this patient's record indicate chronic heart failure? Yes or no?"), natural-language names and types (and optionally definitions) for each feature, and a few serialized demonstrations. The demonstrations are serialized in a compact textual form such as:
"f_1 is x^i_1. ... f_d is x^i_d. Answer: y^i"
This gives the LLM concrete examples of feature values and labels without overwhelming it with raw table formatting.

The reasoning instruction is deliberately two-step. In step 1 the LLM is asked, without looking at demonstrations, to infer general tendencies or causal relationships between the features and the target using prior knowledge (e.g., "Which features are likely to increase the risk of chronic heart failure?"). This step encourages the LLM to surface domain priors and avoid overfitting to spurious correlations visible in a very small set of examples. In step 2 the LLM is asked to combine the prior knowledge from step 1 with the few-shot demonstrations to produce a fixed number of explicit rules per class (the paper uses 10 rules per class). Having a fixed quota controls prompt length, reduces the risk of producing too many or too few rules, and stabilizes downstream dimensionality.

The response instruction constrains the syntactic form of each rule and the overall output format to make parsing feasible. Despite these constraints, the LLM may still introduce syntactic variability (for example, "greater than" instead of ">" or optional parentheses). To reliably convert rules into executable form, FeatLLM uses the LLM again in the second stage. Instead of writing a bespoke parser for all the possible linguistic variants, FeatLLM provides the natural-language rules plus a minimal function signature and asks the LLM to output code that implements a deterministic predicate for each rule. The generated code is then executed (for example, via Python’s exec()) to create binary features. Using the LLM itself for parsing leverages its strong semantic understanding of the rules while avoiding brittle hand-engineered parsing logic.

This two-stage approach—first eliciting interpretable rules, then translating them to executable form—keeps human-interpretable criteria at the core of the pipeline while ensuring that the final binary features are deterministic and cheaply computable at inference time.

# Binary feature construction per class from rule satisfaction
Once rules for each class are available as executable predicates, FeatLLM converts them into binary features. For a dataset with $c$ classes and $R$ rules per class, each sample $\mathbf{x}^i$ is transformed into $c$ groups of $R$ binary indicators. For class $k$ the indicators form a vector $\mathbf{z}_k^i \in \{0,1\}^R$, where the $r$-th entry is 1 if and only if rule $r$ for class $k$ evaluates to true on sample $\mathbf{x}^i$.

This representation has several advantages. First, it isolates the LLM’s output (rules) into clear, interpretable features that can be audited: a positive value directly corresponds to satisfying a specific rule. Second, the binary format simplifies downstream modeling and avoids the need for complicated feature preprocessing or embedding choices. Third, because rules are class-specific, they can capture asymmetries in how different feature conditions indicate different classes. For multi-class problems, the feature set can be thought of as a concatenation of per-class rule indicator blocks.

The framework recognizes that not every rule is equally informative. A rule generated from a few-shot prompt might be broadly valid, irrelevant, or even misleading in the particular dataset. Thus FeatLLM does not rely on raw rule counts; instead it converts rule satisfaction into learnable signal weights via the downstream model (described below). In practice the paper demonstrates that a large fraction of generated rules are informative: an analysis measured AUROC between individual new binary features and target labels and found that most rules have AUROC exceeding 0.5 before tuning, and the tuning process further filters weak rules (weights close to zero), improving the effective feature set.

# Lightweight downstream model for class likelihoods
After converting rules into binary features, FeatLLM fits a lightweight, low-capacity model to estimate class likelihoods. The paper uses a simple linear model without bias for each class and projects weights into the non-negative space to ensure that satisfying a rule never actively reduces the associated class likelihood during optimization.

Concretely, for sample $\mathbf{x}^i$ and class $k$ we denote the binary rule vector by $\mathbf{z}_k^i \in \{0,1\}^R$ and train a weight vector $\mathbf{w}_k \in \mathbb{R}^R$. The logit for class $k$ is computed as
\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\]
and class probabilities are obtained by applying the softmax across class logits:
\[
\mathbf{p}^i = \text{Softmax}\big([\,\text{logit}_1^i,\ldots,\text{logit}_c^i\,]\big).
\]
Training minimizes the cross-entropy loss with respect to the weight vectors $\{\mathbf{w}_k\}_k$ using the few labeled samples. The paper uses the Adam optimizer with a learning rate of 0.01, trains for 200 epochs, and uses $k$-fold cross-validation to select the epoch to avoid overfitting.

There are several motivations for this simple model choice. First, linear weights afford interpretability: a large positive weight indicates a highly predictive rule. Second, the non-negativity restriction ensures the LLM’s generated features can only increase support for a class rather than flip polarity, which stabilizes learning from extremely small datasets. Third, a low-capacity model reduces the risk of overfitting in few-shot regimes and keeps inference fast. The paper’s ablations show that learning these per-rule weights is helpful: omitting this tuning (i.e., summing rule satisfactions without learned weights) reduces performance, and the benefit of tuning increases as the number of shots grows.

# Repeat-and-ensemble strategy with bagging for robustness and scalability
FeatLLM relies on stochastic repeated trials combined via ensembling to improve robustness and to deal with practical constraints like LLM prompt-size limits. Each trial produces a distinct set of rules (and therefore a distinct binary feature matrix) because the LLM is queried with randomized components: the prompt demonstrations can be reordered and the LLM sampling temperature is set non-zero to promote diversity. The framework then fits a separate lightweight model per trial. At inference time the final probability for a sample is the average of the probabilities produced by each trial’s model:
\[
\bar{\mathbf{p}}^i = \frac{1}{T} \sum_{t=1}^T \mathbf{p}^i[t],
\]
where $T$ is the number of trials (the experiments use $T=20$). Averaging across trials stabilizes predictions and leverages the idea of self-consistency: rules that recur across trials are more likely to be correct, while idiosyncratic or incorrect rules in some trials are mitigated by others.

Bagging is applied at the prompt and data level to address two practical problems. First, when the original table has many columns or when the demonstrations would make the prompt too long, selecting a random subset of features or a subset of demonstrations per trial keeps prompt length manageable. Second, bagging injects further diversity across trials, which improves the ensemble’s coverage of informative features: even if one trial does not include a particular relevant feature because it was not selected in that trial’s bag, another trial may include it. This mitigates the failure mode where a single trial’s rules miss crucial predictive conditions.

The ensemble approach also contributes computationally: because the LLM is used only to generate rules and parsing code during training (and not at inference time), repeating the rule-generation stage multiple times (e.g., 20 trials) only costs a moderate number of API queries (the paper reports about 30 API queries in total for the training phase, which can be parallelized), whereas methods that require an LLM call for every test sample would be far more expensive at inference time. Empirically, ensemble size beyond about 20 shows diminishing returns, so choosing $T\approx 20$ balances prediction gains with API cost.

# Design principles: interpretability, low inference cost, practicality with API-only models
FeatLLM was designed around four interlocking practical principles:

Interpretability. The core outputs are human-readable rules. Each binary feature corresponds to a named rule, so practitioners can inspect, critique, or refine the feature set before deployment. This is useful in domains where auditability is important (e.g., healthcare or finance). The learned per-rule weights give an immediate ranking of rule importance.

Low inference cost. After the training phase completes (which includes a modest number of LLM calls to extract and parse rules), inference on new samples requires only computing deterministic rule predicates and evaluating a simple linear model. No LLM calls are required per test sample. This contrasts with methods that feed each test sample through the LLM, and this design leads to inference-time costs comparable to conventional tabular methods.

Practicality with API-only models. FeatLLM works with LLMs accessed only through inference APIs. It avoids the need for parameter-efficient tuning or full model fine-tuning, which is important because many strong LLMs are not released with training interfaces. The method also copes with limited prompt windows by using bagging to sample subsets of features and demonstrations and by fixing the number of rules per class. The two-stage LLM usage (rule writing, then code generation) helps keep prompts compact and makes the pipeline robust to syntactic variability in LLM outputs.

Data efficiency and robustness. The two-step reasoning instruction encourages the LLM to use its external priors before relying on the small training examples. This helps guard against overfitting to spurious correlations that can appear in few-shot samples. Empirically, FeatLLM exhibits smaller performance degradation than many baselines when irrelevant noisy columns are appended to a dataset, suggesting that the rule-extraction prompt and the ensemble mechanism together reduce the influence of spurious features. Ablations further show that removing either the reasoning step or the feature descriptions in the prompt reduces performance—particularly in very low-shot regimes—showing the value of guiding the LLM’s reasoning and providing feature semantics.

# Practical settings and empirical summary (as reported)
The paper reports several practical hyperparameter settings and empirical observations that illustrate how the architecture is used in practice. The experiments used GPT-3.5 as the LLM backbone with temperature set to 0.5 (top-p left at API default). The number of rules per class was set to $R=10$ and the ensemble size to $T=20$. Training of the lightweight linear model used Adam with learning rate 0.01 for 200 epochs with $k$-fold cross-validation for epoch selection. Across 13 tabular datasets spanning domains and feature counts, FeatLLM frequently outperformed or tied top baselines in low-shot settings. Important empirical findings include:

- Tuning the linear weights improves performance, and its benefit grows with the number of shots. In very low-shot settings, leveraging the LLM’s priors (via the two-step reasoning and feature descriptions) is especially valuable.

- The ensemble consistently improves performance across datasets and shot settings; gains saturate around $T\approx 20$.

- Using the LLM to parse rules into code is effective at handling the LLM’s syntactic variations and simplifies automatic feature construction—most generated rules show signal (AUROC > 0.5) prior to tuning, and tuning filters out weak rules.

- FeatLLM achieves low inference latency comparable to traditional tabular models because no LLM calls are needed at prediction time. The training (rule extraction) cost is modest in terms of API queries and can be parallelized.

# Limitations and practical considerations
While FeatLLM addresses major practical constraints of prior LLM-based tabular methods—chiefly per-sample inference cost and the need for tuning-access to LLM parameters—it is designed specifically for low-shot regimes and uses rule-style features. Practitioners should be aware that the LLM’s priors may dominate very small datasets, and thus any societal biases or incorrect domain assumptions held by the LLM can influence the extracted rules and downstream predictions. The ensemble and tuning mechanisms reduce but do not eliminate such risks. Furthermore, when features are highly numerous, careful selection of bagging parameters is necessary to keep prompts within model context windows while ensuring adequate feature coverage across trials.

In summary, FeatLLM converts the LLM’s reasoning into reusable, interpretable binary features via a two-stage LLM workflow, fits a simple non-negative-weight linear model for class likelihoods, and uses repeat-and-ensemble with bagging to achieve robustness and scalability. This architecture yields an efficient practical compromise: it leverages LLM priors where they are most valuable (feature engineering) but avoids the expensive requirement of invoking or fine-tuning an LLM at inference time.

Prompt Engineering for Rule Extraction

# Basic information section: task description, label schema, feature descriptions and types, serialized few-shot examples
The first part of a prompt for rule extraction must give the LLM the minimum set of facts it needs to reason sensibly about the problem. In practice this "basic information" block contains four elements: a compact task description posed as a question, the label schema, a description of each input feature (including its type), and a few serialized training examples with ground-truth labels. The goal of this block is to eliminate ambiguity about what the model is being asked to predict and to expose feature meanings and types that the LLM can use when proposing rules.

The task description should be a concise natural-language question that names the predicted outcome and the decision format. For example, a medical prediction can be written as: "Does this patient's myocardial infarction complications data indicate chronic heart failure? Yes or no?" Stating the task as a question helps the model frame its reasoning in terms of evidence that supports each answer class. The label schema (the set of allowed target values) should be made explicit so the LLM knows what class labels to consider when it drafts rules.

Feature descriptions are critical. For each column provide a human-readable name, its data type (e.g., numerical, categorical, boolean), and, where appropriate, the meaning or allowed category values. The LLM uses these descriptions to avoid type mismatches when proposing conditions (for example, it will avoid comparing a categorical string to a numeric threshold if the feature is described as categorical). When categories are enumerated, the model can propose equality-based rules; when a feature is numeric the model can propose threshold-based rules.

Finally, include a few-shot set of example rows serialized into text together with their labels. These demonstrations let the LLM combine its prior knowledge with observed evidence about how features map to labels in this specific dataset. The paper uses a serialization format of the form

\[
\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = 
\ "f_1\ \text{is}\ \mathbf{x}^i_1.\ ... \ f_d\  \text{is}\  \mathbf{x}^i_d.\ \ \text{Answer:}\  \mathbf{y}^i"
\]

which lists each feature name followed by its value, then the ground-truth answer. This exact format makes each example compact and consistent across prompts.

# Serialization format for examples: “f1 is x1. ... fd is xd. Answer: y”
Consistency in example serialization is important for reliable in-context learning. The chosen format—"f1 is x1. ... fd is xd. Answer: y"—keeps a fixed structure across all demonstrations so the LLM can more easily infer patterns from the provided examples. Each feature-value pair is a short sentence "fj is xj." and the example concludes with "Answer: y". Because this format maps directly from tabular rows to natural language, it is straightforward for the LLM to attend to both individual feature values and their relationship to the label.

Using this serialization has two practical benefits. First, it preserves the one-to-one mapping between table columns and the text that the LLM understands, enabling the model to use its language priors to infer what each column means and how it relates to the label. Second, it yields compact prompts that are still human-readable: inspecting the prompt lets a practitioner quickly verify that examples were presented correctly. When dealing with many columns, the structure also makes it easy to apply feature bagging (selecting subsets of columns per trial) to keep prompt sizes manageable while still giving the LLM high-quality demonstrations.

# Reasoning instructions: two-step process separating prior knowledge reasoning from example-based deduction
A key innovation in the prompt is an explicit two-step reasoning instruction that separates (1) the LLM's general prior-knowledge reasoning from (2) example-driven rule deduction. This separation is motivated by the observation that LLMs contain broad commonsense and domain knowledge which should be leveraged, but that few-shot examples supply essential task-specific calibrations. Constraining the LLM to first state general tendencies about features and the task reduces the chance that it will jump straight to spurious correlations in the small demonstration set.

Step 1 (prior-knowledge reasoning) asks the LLM to infer likely relationships or causal tendencies between the task and features without looking at the few-shot examples. The prompt asks the model to enumerate which features are plausibly informative and why, using general knowledge and common sense. For example, in a medical prediction task the model might note that "Age and prior heart conditions are commonly associated with heart failure" as general tendencies. This primes the LLM to give extra attention to features that are semantically relevant.

Step 2 (example-based deduction) then instructs the model to use the example demonstrations together with the insights from Step 1 to distill concrete rules that distinguish classes. In this step the LLM is told to produce class-conditional rules that are consistent with the demonstrated examples and with the prior-knowledge tendencies. By enforcing that the second step should explicitly combine observations with initial priors, prompts steer the model away from extracting rules purely reflecting accidental patterns in the tiny example set.

Separating reasoning into these two stages also helps filter irrelevant features. If Step 1 judges a feature unrelated to the task, Step 2 will be less likely to generate rules that hinge on that feature even if the few-shot examples incidentally correlate with the label. In practice, the prompt language roughly follows a chain-of-thought structure for Step 1 and then requests concise, actionable rules in Step 2; this structured guidance produces higher-quality, class-discriminative rules than a single undifferentiated instruction.

# Response instructions: strict output formats, type-aware rule templates, fixed number of rules per class (e.g., 10)
To make the LLM's output practical and machine-parseable, the prompt includes strict response instructions. These instructions specify two things: the format in which the LLM should present its rules, and the number of rules to produce per class. Fixing a response format reduces syntactic variability and simplifies the downstream parsing and feature generation steps.

The format guidance defines a template for each rule and for the class-level grouping of rules. For example, the prompt might require that every rule be given as a single line with fields such as: Rule ID, Target Class, Condition, and Optional Natural-Language Explanation. The rules are expected to use clear operators (e.g., ">", "<=", "==") for numeric or categorical comparisons and to avoid embedding extraneous commentary in the condition field. By demanding a predictable layout, the system reduces the likelihood that the LLM will produce rules that are impossible to parse automatically.

The prompt also instructs the LLM to choose conditions that are compatible with the described feature types. For categorical features the template emphasizes equality checks (e.g., "marital_status == 'married'"), for numerical features it emphasizes threshold or range checks (e.g., "age > 65" or "BMI between 25 and 30"), and for boolean features it expects direct truth tests. These type-aware templates ensure the LLM's syntactic choices match the column semantics provided in the basic information block, preventing mismatches like comparing strings to numeric bounds.

A fixed number of rules per class is enforced to prevent the prompt from producing either too few rules (underfitting) or an unmanageably large rule set (prompt bloat and parsing difficulty). The paper sets this number to 10 rules per class as a practical balance: it is large enough to capture a variety of plausible decision criteria while keeping the overall feature dimensionality and prompt length under control. Practitioners can treat this fixed number as a hyper-parameter; during experiments the authors found 10 to be a reasonable trade-off between prompt length and information content.

# Avoiding spurious rules: focusing attention, constraining logic, leveraging feature types
A major risk with few-shot rule extraction is that the LLM will propose rules that reflect spurious correlations in the small demonstration set rather than meaningful, generalizable criteria. The prompt design addresses this risk in several complementary ways.

First, the two-step reasoning instruction explicitly encourages the LLM to bring in prior knowledge before consulting the few-shot examples. When the model first lists plausibly relevant features and relationships, it develops a bias toward features that are semantically tied to the task; that bias reduces the chance it will overfit to idiosyncratic patterns in the demonstrations. In other words, the LLM is asked to corroborate the data-driven signals with domain-aware expectations, which helps it discount spurious alignments.

Second, the response instructions constrain the logical forms the LLM may use. By enforcing type-aware templates and explicit operator conventions the prompt limits the space of admissible rules. This prevents, for instance, the creation of elaborate nested logical expressions mixing incompatible types, or the production of noisy free-form conditions that are difficult to interpret. Constraining logical form also improves automatic parsing accuracy and thus lowers the risk that incorrectly parsed rules will be treated as valid features.

Third, because the basic information block includes feature types and category enumerations, the LLM is less likely to craft rules that do not make sense for a given column. If a column is labeled as categorical with a small set of values, the LLM will be guided to propose equality checks over that set rather than numeric thresholds. This type-awareness both improves rule validity and reduces spurious rules that are artifacts of misinterpreting feature semantics.

Finally, the overall system design includes mechanisms beyond individual prompts that mitigate spurious rules. The paper ensembles multiple independently generated rule sets (by re-querying the LLM with randomized demonstration order and temperature) and trains simple weights on the derived binary features to learn which rules actually help predictive performance. Low-utility rules receive small learned weights and thus contribute little at inference time. This combination—prior-knowledge priming, output constraints, type-awareness, and downstream weighting—substantially reduces the influence of spurious rules produced from a tiny demonstration set.

# Practical notes on parsing and robustness
Even with strict instructions the LLM can produce minor syntactic variations (e.g., "greater than" instead of ">" or "between 30 and 40" in different phrasings). To handle this, the pipeline uses a practical parsing strategy: the generated rules are fed back into the LLM with a small parsing prompt that asks the model to emit executable code (for example, a short Python function) implementing each rule given the declared feature types. The resulting code is executed to produce binary rule-features for the dataset. This approach leverages the LLM's ability to normalize its own outputs into parsable code, avoiding the need to hand-engineer a brittle parser for all possible linguistic variants.

In summary, prompt engineering for rule extraction combines a carefully structured basic-information block, a consistent serialization format for examples, an explicit two-step reasoning sequence, strict response templates that are type-aware, and a fixed budget of rules per class. These elements, used together, encourage LLMs to propose high-quality, class-discriminative, and parseable rules while minimizing the generation and downstream impact of spurious rules.

From Natural Language Rules to Executable Features

# Challenges of parsing free-form text: syntactic variability and normalization
When a large language model (LLM) produces rules in natural language, those rules are expressive and human-readable, but they are seldom formatted in a way that a downstream program can directly execute. The FeatLLM paper highlights two concrete sources of difficulty. First, there is syntactic variability: the same logical condition can be expressed in many ways. For example, a numeric comparison might appear as the symbol "$>$" in one rule and as the phrase "greater than" in another. Categorical membership can be written as "is one of {A, B}" or as "belongs to {A, B}". Second, there is normalization ambiguity: the LLM may vary how it spells or punctuates categories, how it writes thresholds (e.g., ">= 5" versus "at least five"), or how it composes logical operators (e.g., using "and/or", mixing English conjunctions with symbols, or nesting conditions).

These variations make naive string-based parsing brittle. If a parsing routine expects a fixed token like "$>$" but the LLM outputs "greater than", the parser will fail or misinterpret the rule. Even with constrained response templates, the authors observed "noisy syntactic changes" and therefore treat parsing as a nontrivial problem. The paper therefore motivates treating rule-to-code conversion as a two-stage problem: (1) constrain the LLM's rule generation so that outputs follow a predictable schema, and (2) use the LLM itself to convert the (still somewhat variable) natural-language rules into simple executable code. This approach shifts the burden of normalization to the model that produced the rules and takes advantage of the LLM's strong ability to interpret varied natural-language phrasing.

# LLM-assisted code generation: function specs, inputs/outputs, and rule text as context
Rather than attempting to write a general-purpose natural-language parser by hand, FeatLLM uses the LLM again to perform the translation from rule text to executable code. The prompting strategy for this step is deliberate: the code-generation prompt includes a clear function specification and the necessary context so the LLM can produce reliable, runnable code.

Concretely, the prompt provided to the LLM for parsing contains the inferred rules (the natural-language rules produced in the previous prompt), a function name, and an explicit description of the function inputs and outputs. The input description tells the model what form the tabular data will have (for example, a row represented as a mapping from feature names to values, or an array with documented column order). The output description states that the function should return a binary indicator (or a list of binary indicators) specifying whether each rule is satisfied for a given sample. Because the prompt also includes the feature type information (numeric vs categorical, allowed categorical values, etc.), the LLM can choose appropriate comparison operators and avoid type mismatches when generating code.

This design leverages two LLM strengths. First, the model is robust to the linguistic variability of the rule text: even if a rule uses the phrase "greater than" instead of the symbol "$>$", the LLM understands the intended meaning and can emit the corresponding comparison operator in code. Second, because the LLM has been trained on code corpora, it can generate syntactically valid code in a target language (the paper uses Python) that implements the same logical conditions described in text. By asking for a small, well-specified function whose sole task is to check rules, the generated code is simple and focused, which aids reliability.

# Execution flow: generating Python code, safe execution considerations, and data type handling
The execution flow in FeatLLM follows a compact pipeline. First, a rule-generation prompt elicits a fixed number of rules per class (the paper uses 10 rules per class). Second, a parsing prompt that contains those rules plus a precise function contract is sent to the LLM; the output is a short Python function that evaluates the rules on a row of input data. Third, the produced code is run in the environment to convert the tabular dataset into binary features: the paper executes the generated code via Python's exec() to perform the data conversion.

The paper emphasizes several practical measures to make this flow robust. By including the type and definition of each feature in the initial prompt (numeric, categorical, etc.), the LLM has the necessary type information during both rule generation and code generation. This reduces type-mismatch errors (for example, it discourages generating a numeric comparison on a categorical field). Because the code-generation prompt asks for a function with well-specified inputs and outputs, the LLM tends to produce compact functions that check each rule and return a Boolean or 0/1 result. The authors then call these functions on each sample to obtain the binary indicators.

The paper does not elaborate on additional runtime sandboxing or security mechanisms; in their implementation they execute the generated Python via exec() for data conversion. To reduce the chance of syntactic parsing failures that would produce unparsable code, the authors also constrained the LLM’s earlier outputs by (a) giving explicit response formatting instructions when eliciting rules, and (b) asking the LLM to adhere to a function signature when generating code. In addition, the LLM is guided to prefer simple, direct constructs (e.g., comparisons and set membership checks) that are straightforward to evaluate on tabular data. Finally, because feature types are known and communicated in the prompt, the generated code can perform correct operations (numeric comparisons for numeric features, membership tests for categorical features), which simplifies data-type handling during execution.

# Creating per-class binary features indicating rule satisfaction
Once the generated code is executed, the output for each sample takes the form of binary indicators for each rule and for each class. If there are $c$ classes and $R$ rules per class, then for sample $\mathbf{x}^i$ the generated binary feature vector for class $k$ is written as $\mathbf{z}_k^i \in \{0,1\}^R$. Each element of $\mathbf{z}_k^i$ indicates whether the corresponding rule for class $k$ is satisfied by sample $\mathbf{x}^i$.

These per-class binary features are assembled into a feature representation that is compact and interpretable: the entire rule-derived representation for sample $\mathbf{x}^i$ is a concatenation (or grouping) of the class-specific vectors $\mathbf{z}_k^i$. The downstream model then learns how to combine these binary indicators into a class likelihood. In the FeatLLM framework the model is intentionally simple: for each class $k$ a linear logit is computed by a non-negative weighting of that class's binary features,

\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\]

and the class probabilities are obtained with a softmax,

\[
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big).
\]

Here $\mathbf{w}_k$ are learned weights that capture the importance of each rule-based feature for class $k$. The binary indicators thus serve as an intermediate, human-interpretable representation that the simple linear layer can tune to the few-shot data.

# Quality control: formatting constraints, schema validation, type checks
Quality control in the rule-to-feature pipeline is achieved at multiple stages as described in the paper. First, the initial rule-generation prompt enforces a response format: the authors provide explicit instructions on how each rule should be structured and limit the number of rules per class (they set a fixed number, such as 10). This constrained format reduces downstream variability and makes automated parsing more reliable.

Second, feature schema information is made explicit and available to the LLM during both rule generation and code generation. By supplying feature names, their types, and optional definitions, the prompt helps the LLM avoid obvious type mistakes (for instance, writing numeric comparisons for categorical attributes). This schema-guided prompting acts as a soft form of validation: the LLM is nudged to generate only those rules that are compatible with the known schema.

Third, the paper uses the LLM to produce the parsing code itself rather than relying on brittle string-based parsers. Because the LLM understands synonyms and diverse natural-language ways of expressing the same condition, the generated code inherently normalizes variations (for example, translating "greater than" to the ">" operator). The resulting functions therefore serve as a kind of executable schema validator: when they run on real data, they either return a clear 0/1 indicator for each rule or raise errors that reveal incompatibilities.

Finally, FeatLLM applies a downstream statistical filtering step that further improves feature quality. After converting rules into binary features and training the simple linear model, features that contribute little to predicting the target are effectively down-weighted. In the experiments the authors examine the distribution of learned weights and filter out rules whose learned weight falls below a small threshold (for example, 0.1), thereby removing features that are uninformative or spurious. This tuning step acts as a form of empirical validation: rules must not only be syntactically executable, but also useful on the few-shot data to be retained for prediction.

Taken together, these controls—response-format constraints, explicit schema information, LLM-assisted parsing into concise functions, and downstream weight-based filtering—form a pragmatic pipeline that turns variable natural-language rules into a reliable binary feature matrix suitable for few-shot tabular learning. The approach leverages the LLM’s language and code understanding while keeping the final inference cheap and interpretable because predictions rely only on the generated binary features and a lightweight linear model.

Estimating Class Likelihood with Simple, Constrained Models

# Feature vector per class: z_k ∈ {0,1}^R from R rules
The starting point for downstream modeling in the FeatLLM framework is a set of rule-derived binary features. For each class index $k$ (there are $c$ classes), the LLM generates $R$ rules intended to be indicative of membership in class $k$. Applying these $R$ rules to a sample $\mathbf{x}^i$ produces a binary vector
\[
\mathbf{z}_k^i \in \{0,1\}^R,
\]
where the $r$-th component $\mathbf{z}_{k,r}^i=1$ if and only if sample $\mathbf{x}^i$ satisfies rule $r$ for class $k$, and $\mathbf{z}_{k,r}^i=0$ otherwise.

This representation converts natural-language criteria into a structured, numerical form that is immediately usable by standard supervised models. Working with binary rule indicators has several pragmatic advantages emphasized in the paper: the features are interpretable (each dimension corresponds to a human-readable rule), low-dimensional when $R$ is controlled, and naturally sparse (many samples will only trigger a small subset of rules). The downstream model therefore does not need to rediscover complex non-linear combinations from raw inputs; instead it only needs to learn how much weight to assign to each rule as evidence for each class.

# Linear model without bias; weight vector w_k and positivity projection
FeatLLM uses a very simple per-class linear scoring function to convert rule indicators into class logits. For class $k$ we introduce a trainable real-valued weight vector
\[
\mathbf{w}_k \in \mathbb{R}^R,
\]
and compute the raw score (logit) for sample $\mathbf{x}^i$ as the dot product between a non-negative projection of the weights and the binary rule vector:
\[
\text{logit}_k^i \;=\; \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i.
\]
Here $\max(\mathbf{w}_k,0)$ is applied elementwise (equivalently a ReLU on each coordinate), so every effective weight used in the dot product is constrained to be non-negative. Importantly, no additive bias term is included in the scoring function; this is an explicit design choice in the paper: the model scores a class purely by accumulating positive evidence from satisfied rules.

Intuitively, each coordinate of $\mathbf{w}_k$ measures how strongly the corresponding rule supports class $k$. Multiplying by the binary indicator $\mathbf{z}_{k,r}^i$ makes the contribution active only when the rule holds for the sample. The absence of bias focuses the model on evidence provided by rules rather than allowing a constant offset that could dominate when few rules are active. Training optimizes $\mathbf{w}_k$ so that rules that genuinely correlate with class membership receive larger positive weights, while irrelevant or misleading rules are driven toward zero.

# Softmax over class logits; cross-entropy training objective
After computing logits for all $c$ classes, the model converts these scores into normalized class probabilities using the softmax function. For a sample $\mathbf{x}^i$ let the logit vector be
\[
\mathbf{s}^i = \big[\text{logit}_1^i,\ \text{logit}_2^i,\ \ldots,\ \text{logit}_c^i\big]^\top.
\]
The predictive probability vector is then
\[
\mathbf{p}^i = \text{Softmax}(\mathbf{s}^i),\qquad
p_k^i = \frac{\exp(\text{logit}_k^i)}{\sum_{j=1}^c \exp(\text{logit}_j^i)}.
\]

To train the weight vectors $\{\mathbf{w}_k\}_{k=1}^c$, the framework uses the standard categorical cross-entropy (negative log-likelihood) loss on the few-shot labeled examples. If we denote the one-hot encoded true label for sample $\mathbf{x}^i$ by $\mathbf{y}^i$, the per-sample loss is
\[
\mathcal{L}(\mathbf{w};\mathbf{x}^i,\mathbf{y}^i) \;=\; -\sum_{k=1}^c y_k^i \log p_k^i.
\]
The complete training objective sums (or averages) this loss over the available training samples. Optimization of this objective adjusts the weights so that classes receive higher scores when their associated rules are satisfied for positive examples, and lower relative scores otherwise.

# Why non-negativity: ensuring rules don’t decrease class likelihoods
A central constraint in FeatLLM is that effective weights are non-negative: only positive contributions from satisfied rules are allowed. The paper motivates this choice by the semantics of the rule features. Each rule is generated as evidence for a given class by the LLM; conceptually a rule says, “if this condition holds, this raises the chance of class $k$.” Enforcing non-negativity aligns the numeric model with that intended interpretation: satisfying a rule can only increase (or leave unchanged) the class score.

There are several practical consequences of this constraint. First, interpretability improves: a large positive weight clearly indicates a strong rule; a near-zero weight indicates an unhelpful or spurious rule. Second, it reduces the risk that a rule that was intended as supportive becomes, through training noise in few-shot settings, a negative signal that reduces the score for its class. Third, in the low-shot regime the non-negativity acts as a simple inductive bias that prevents overreacting to noisy correlations—rules either contribute evidence or are effectively ignored (weight near zero). The paper demonstrates that after tuning, many rules that are not useful end up with small weights, and a simple threshold (the paper uses 0.1 in its analysis) can be used to identify and filter out uninformative rules.

From an optimization perspective, the elementwise $\max(\mathbf{w}_k,0)$ is differentiable almost everywhere (it is the ReLU operation). Gradients flow only through coordinates where $\mathbf{w}_{k,r}>0$, encouraging reinforcement of genuinely useful rules while allowing others to remain or move toward zero. This is a computationally simple way to impose a non-negativity constraint without requiring constrained optimization machinery.

# Training protocol: Adam optimizer, learning rate 0.01, 200 epochs, k-fold cross-validation for early stopping
The paper describes a straightforward and reproducible training protocol for fitting the weights. Optimization is performed with the Adam optimizer using a learning rate of $0.01$. Training runs for a fixed maximum of $200$ epochs. Because the work focuses on few-shot regimes where overfitting is a real concern, the authors use $k$-fold cross-validation to select the optimal number of epochs: that is, they perform $k$-fold CV and choose the epoch that yields the best validation performance (this serves the role of early stopping).

This protocol balances two competing needs. On one hand, a small model (linear weights over binary features) and a moderate number of epochs allow the optimization to reliably discriminate useful from useless rules even with few examples. On the other hand, cross-validation-based epoch selection guards against overfitting by stopping training once validation performance peaks. The authors report that the benefit of tuning these weights increases with the number of shots: when more labeled examples are available, the model can estimate rule importance more accurately, and tuning yields larger gains (an observation borne out in their ablations). In practice the training load is light: the model has only $c\times R$ real-valued parameters, and the paper notes that the overall computational cost at inference remains low because the final predictor uses only the learned linear weights over pre-computed binary rule features.

Putting it together
The entire downstream pipeline is therefore simple and transparent. For each class $k$, the LLM-produced rules are turned into $R$ binary features per sample, producing $\{\mathbf{z}_k^i\}$. A constrained linear scoring function with non-negative effective weights maps these features to class logits via
\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,
\]
the logits are normalized with a softmax to produce probabilities $\mathbf{p}^i$, and the weights are fitted by minimizing cross-entropy using Adam (learning rate $0.01$) for up to $200$ epochs with $k$-fold cross-validation to select the stopping epoch. The constrained linear form, together with the interpretability of binary rule features and the simple optimization, provides an effective, low-cost way to convert LLM-created rules into accurate class likelihood estimates in few-shot tabular learning tasks.

Ensembling and Bagging for Robustness and Prompt Scalability

# Multiple trials (ensembles): averaging class probabilities over T rule sets
FeatLLM builds robustness by repeating the entire rule-extraction and downstream-weight-training process multiple times, producing a collection of independently generated rule-sets and associated trained weights. Each trial t yields a set of rules that are parsed into binary features and a trained weight vector (or vectors) \(\mathbf{w}[t]\) used for converting those features into class scores. For a single trial, the pipeline converts a sample \(\mathbf{x}^i\) into class probabilities \(\mathbf{p}^i(\mathbf{w}[t])\) using the linear-logit formulation (reproducing Eq. 2 from the paper):

\[
\text{logit}^{i}_{k}(t) \;=\; \max(\mathbf{w}_k[t], 0) \cdot \mathbf{z}^i_k, \qquad
\mathbf{p}^i(\mathbf{w}[t]) \;=\; \text{Softmax}\!\big([\text{logit}^{i}_{1}(t),\dots,\text{logit}^{i}_{c}(t)]\big),
\]

where \(\mathbf{z}^i_k\in\{0,1\}^R\) is the binary vector of rule satisfactions for class \(k\). The ensemble aggregates the per-trial probabilities by averaging across the \(T\) trials:

\[
\mathbf{p}^i_{\text{ensemble}} \;=\; \frac{1}{T}\sum_{t=1}^{T} \mathbf{p}^i(\mathbf{w}[t]).
\]

Averaging probabilities (rather than, say, averaging logits) produces a calibrated mixture of the trial outputs and is straightforward to implement. The ensemble reduces sensitivity to mistakes made in any single trial: if one trial produces a poor rule-set or misweights some features, other trials can compensate. In practice, FeatLLM used \(T=20\) ensembles, a value that empirically balances improved accuracy and computation (see the Trade-offs section).

# Injecting diversity: higher temperature and randomizing demonstration order
An ensemble is effective only if its members are sufficiently diverse. FeatLLM intentionally injects stochasticity into each rule-generation call to the LLM so that different trials explore different plausible rule-sets. Two concrete mechanisms are used.

First, the LLM sampling temperature is increased for rule generation. A higher temperature produces more varied outputs from the LLM’s conditional distribution; in FeatLLM this yields a broader variety of candidate rules across trials. The paper describes using a “sufficiently high temperature” for this purpose (the default implementation reported a temperature of 0.5 for general runs but increases are used to promote diversity during ensemble trials). This randomness converts one deterministic LLM response into a family of possible interpretations of the few-shot demonstrations and feature descriptions.

Second, the order of the few-shot demonstrations included in the prompt is randomized between trials. LLMs are known to be sensitive to demonstration order, so shuffling the examples produces different in-context reasoning trajectories and thus different extracted rules. By permuting demonstration order across trials, FeatLLM leverages this sensitivity to create variety in the candidate rule-sets without changing the underlying data.

Combined, temperature and demonstration-order randomization yield an ensemble whose members are not redundant but instead explore complementary hypotheses about which feature conditions are relevant.

# Instance and feature bagging to reduce prompt size and encourage complementary rules
When tabular datasets have many features or a large number of few-shot examples, prompts can exceed practical length limits or degrade LLM performance. FeatLLM applies bagging (feature bagging and instance bagging) inside the ensemble to address prompt-size constraints and to generate complementary rule-sets across trials.

Feature bagging means that for each trial the prompt includes only a random subset of the original feature set. This reduces the number of feature descriptions and serialized values that must be placed into the prompt, keeping the text length manageable when a dataset has dozens or hundreds of attributes (the paper highlights datasets such as Communities and Myocardial with over 100 attributes). Because different trials sample different subsets of features, the ensemble collectively covers a wider portion of the original feature space than any single trial, and each trial focuses the LLM’s attention on a smaller, more tractable view of the data. As a result, the rules produced across trials tend to be complementary: trial A may discover rules involving features 1–20, while trial B discovers rules involving features 21–40, and their combination yields a richer feature representation without any single prompt becoming too long.

Instance bagging (sampling a subset of few-shot demonstrations) likewise reduces the number of exemplars serialized into the prompt. It also encourages the LLM to produce different rules because the specific examples presented influence the in-context reasoning path. In short, bagging trades off breadth in a single trial for breadth across trials; prompt length is controlled per trial, while the ensemble restores coverage and flexibility.

Practically, these two forms of bagging are controlled by the practitioner: the number of features and number of demonstration instances included per trial can be tuned so that each prompt fits within the LLM’s context window while preserving enough information for meaningful rule induction.

# Self-consistency rationale: frequently rediscovered rules are more reliable
FeatLLM’s ensemble strategy connects to the notion of self-consistency in LLM reasoning. If multiple independent LLM calls—each with different sampling noise, demo order, or subset of features—recover the same or similar rule, that rule is more likely to capture a genuine relationship between the inputs and the labels, rather than being a chance idiosyncrasy of one prompt. The paper explicitly invokes this intuition, referencing self-consistency: rules that are rediscovered across trials are treated as more trustworthy.

This rationale has two operational consequences. First, because many trials are run, the common rules naturally receive higher effective weight in the ensemble output: they will contribute to the binary features in many trials, and their influence is reflected in the averaged probability \(\mathbf{p}^i_{\text{ensemble}}\). Second, the downstream linear tuning step per trial assigns non-negative weights to features; rules that are consistently predictive across trials will repeatedly obtain larger learned weights, further elevating their impact in the aggregate prediction. Together, rediscovery frequency and per-trial tuning implement a form of consensus filtering: frequent, predictive rules survive and drive predictions, while rare or unhelpful rules have limited effect.

# Trade-offs: ensemble size vs performance gains; diminishing returns around ~20 ensembles
While ensembling improves robustness, it also increases computational and monetary costs because rule extraction requires LLM API calls. There is a clear trade-off between ensemble size \(T\) and incremental performance gains. Empirically, the paper reports that increasing \(T\) yields steadily better performance up to a point, but improvements begin to plateau; around \(T\approx 20\) the gains converge in the datasets and few-shot settings studied.

This diminishing-return behavior is typical of ensembles: early additions of trials add substantially different hypotheses and reduce variance, but once many diverse rule-sets are present, additional trials tend to be correlated with existing ones and thus contribute little marginal improvement. Practically, this means a practitioner should choose \(T\) to balance desired accuracy and available budget. The paper’s implementation used \(T=20\) as a sensible default because it provides most of the ensemble’s benefit without excessive API usage.

A related trade-off exists in the granularity of bagging: sampling fewer features per trial reduces prompt length and per-call cost, but if the per-trial sample is too small, each LLM call may produce rule-sets that are too weak. The ensemble can compensate for some of this weakness, but only up to a point. Similarly, an excessively high temperature increases diversity but also increases the chance of producing nonsensical or irrelevant rules, which the ensemble will have to dilute. The downstream per-trial tuning (learning non-negative weights) and averaging across trials mitigate these risks, but judicious hyper-parameter choices (number of rules per class, number of ensembles \(T\), bagging fractions, temperature) remain important.

Finally, it is worth noting the practical efficiency trade: although ensembling multiplies the number of LLM queries during feature discovery, FeatLLM’s inference cost is low because predictions on new samples use only the learned rule-based binary features and the trained linear weights—no per-sample LLM calls are required. Thus the ensemble cost is a one-time training expense (which the paper found to be comparable to other LLM-based methods and modest in absolute API calls), while inference remains fast and feasible for production deployment.

Conclusion
The combination of ensemble averaging, stochasticity via temperature and demo-order shuffling, and instance/feature bagging gives FeatLLM two key practical advantages. First, it creates robust, diverse rule-sets that reduce sensitivity to spurious single-trial errors and low-shot noise. Second, bagging keeps individual prompts compact so the approach scales to wide tables and long feature descriptions. The self-consistency effect—where frequently rediscovered rules dominate the ensemble—provides an intuitive reliability signal, and empirical tuning shows strong performance gains that level off around twenty ensembles, suggesting a pragmatic operating point for many applications.

Experimental Setup

# Datasets
The empirical evaluation of FeatLLM uses a diverse collection of 13 tabular datasets chosen to represent a range of real-world applications, data sizes, feature types, and difficulty levels. Each dataset contains named attributes (column names) and short descriptions for those attributes, which FeatLLM uses as part of its prompt. The 13 datasets are:

- Adult: Predict whether an individual earns more than \$50,000 per year. This is a standard UCI-style census-income dataset commonly used in classification benchmarks.
- Bank: Predict whether a customer will subscribe to a term deposit. This dataset captures marketing/campaign features and binary outcomes.
- Blood: Predict whether blood donors will return for subsequent donations. Typical donation-history and demographic attributes appear here.
- Car: Predict the quality or acceptability of a car. This is a classification dataset with categorical attributes describing the car.
- Communities: Predict crime rate in a region. This dataset is notable for having a very large number of attributes (over 100), making it challenging when prompt length or context window is limited.
- Credit-g: Predict whether an individual is a good or bad credit risk. This is another classical binary classification problem used in tabular learning evaluations.
- Diabetes: Predict the presence of diabetes (Pima Indians dataset variant). It contains clinical measurements and demographic features.
- Heart: Predict the occurrence of coronary artery disease. A clinical prediction dataset with medical features.
- Myocardial: Predict whether an individual suffers from chronic heart failure. Like Communities, Myocardial is high-dimensional with over 100 attributes, which stresses prompt-size constraints.
- Cultivars: Predict grain yield of a soybean cultivar. This dataset and its attributes were added to the UCI repository recently (after September 2023).
- NHANES: Predict a person's age group from a health and nutrition record. This dataset was also added to UCI recently (after September 2023).
- Sequence-type: A synthetic dataset classifying a short sequence as one of four types (arithmetic, geometric, Fibonacci, Collatz). It is synthetically generated to avoid memorization by LLM pretraining.
- Solution-mix: A synthetic dataset predicting whether the percentage concentration of a mixture of four solutions exceeds 0.5. Again, synthetic to ensure it is not present in LLM pretraining.

Two important points about dataset selection and diversity are worth emphasizing. First, the inclusion of recently added UCI datasets (Cultivars and NHANES) helps control for the possibility that the LLM backbone memorized dataset-specific patterns during pretraining: because these datasets were not available before the LLM’s pretraining cutoff, their inclusion reduces leakage. Second, the synthetic datasets (Sequence-type and Solution-mix) explicitly prevent memorization from pretraining and test the model’s ability to extract rules and structure from raw values rather than from memorized examples. Finally, datasets such as Communities and Myocardial with very many attributes stress the limit of LLM prompt size and motivate the bagging and ensembling design choices used in FeatLLM.

# Dataset diversity: recent UCI additions and synthetic sets to avoid LLM memorization
A core concern when evaluating LLM-assisted methods is whether a model’s good performance stems from genuine reasoning on the task or from memorized training examples seen during LLM pretraining. To mitigate this confound, the experimental suite intentionally mixes classical UCI datasets with two types of datasets that reduce memorization risk.

First, the Cultivars and NHANES datasets were only added to the UCI Machine Learning Repository after September 2023. Because the LLM API used in the experiments (GPT-3.5) was pretrained on corpora collected before that date, these recent additions are unlikely to appear in the LLM’s training data; therefore, performance on them provides stronger evidence of the method’s ability to reason from feature descriptions and few-shot examples rather than regurgitate memorized labels.

Second, Sequence-type and Solution-mix are synthetic datasets created specifically for the evaluation. Synthetic construction means the exact mapping between inputs and target labels is unlikely to have been present in any pretraining corpus. These datasets thus form a controlled test of the framework’s capacity to induce algorithmic or arithmetic-like rules from very small sample sizes.

In combination, this selection strategy—classical benchmarks, recent additions, and synthetic tasks—gives a more robust picture of FeatLLM’s real generalization ability under low-shot conditions and reduces the risk that favorable results are driven by dataset memorization in the LLM.

# Baselines
To position FeatLLM against existing approaches, experiments compare it to nine baselines spanning classical machine learning, methods that leverage unlabeled data, pretraining-based approaches, and other LLM-centered techniques. These baselines are:

- Logistic Regression (LogReg): A linear classifier serving as a simple, interpretable baseline. It is trained with standard supervision and tuned via cross-validation.
- XGBoost: A strong tree-based gradient-boosting method widely used in tabular problems. It typically performs well across a range of datasets and is included as a competitive, non-LLM reference.
- RandomForest: An ensemble of decision trees that provides another classical tree-based benchmark known for robustness in tabular settings.
- SCARF: A semi-supervised method that requires access to (potentially large) unlabeled datasets and leverages them for learning better representations. The paper notes that obtaining such unlabeled data may be infeasible in some real-world settings.
- STUNT: Another method that uses unlabeled data to improve few-shot tabular learning. As with SCARF, the need for extra unlabeled resources is an operational consideration.
- TabPFN: An approach that pretrains a model on a wide mixture of synthetic distributions so it can perform fast inference on new small-tabular tasks without further training. It represents a strategy of encoding prior knowledge through pretraining over synthetic datasets.
- In-context learning (LLM-based): A baseline that serializes few-shot examples into text and feeds them into the LLM without further tuning; predictions are produced by the LLM at inference time for each sample.
- TABLET: An LLM-guided method that augments prompts with hints derived from an external classifier (rule-sets, prototypes) to improve the LLM’s in-context inference.
- TabLLM: A method that applies parameter-efficient fine-tuning (e.g., IA3) or similar techniques to adapt an LLM to tabular tasks. Notably, TabLLM is restricted to LLMs for which public checkpoints exist; in the replication described in the paper, TabLLM uses the publicly available T0 backbone rather than GPT-3.5.

When comparing to these baselines, the experiments maintain fair settings: classical ML methods have their hyperparameters selected by grid search with $k$-fold cross-validation, and LLM-based baselines that rely on in-context prompting use the same underlying LLM (where allowed) so that differences reflect method design rather than model capacity. The paper also emphasizes that some baselines (SCARF, STUNT) assume access to unlabeled data, a resource that FeatLLM intentionally avoids depending on.

# LLM backbone and settings
FeatLLM is built to be model-agnostic in principle, but the experiments described in the paper use the GPT-3.5 family as the LLM backbone (the API variant cited is gpt-3.5-turbo-0613). The experimental prompt and inference settings used for the LLM are:

- Temperature: 0.5. This controls randomness in the LLM’s outputs: a moderate temperature encourages some diversity in the generated rules across repeated queries while keeping responses reasonably coherent.
- Top-p: the API default (which is 1 in the reported setup), meaning nucleus sampling does not further truncate the token distribution beyond the temperature.
- Rules per class: For every LLM query, FeatLLM requests a fixed number of generated rules per target class; the experiments use $R = 10$ rules per class. Fixing the number of rules controls prompt size and helps the downstream binary-feature dimensionality remain manageable.
- Number of ensembles (trials): $T = 20$. FeatLLM repeats the rule-generation + parsing + training pipeline $T$ times and ensembles the resulting models to improve robustness and to alleviate prompt-size issues via bagging (explained below).

Two additional LLM-related design choices that are important operationally are: (1) encouraging diversity across ensemble trials by setting a nonzero temperature and by randomizing the order of few-shot demonstrations—since in-context learning can be sensitive to demonstration order—and (2) using the LLM itself to parse its natural-language rule outputs into executable code fragments for feature generation. Leveraging the LLM for parsing reduces brittle string-processing code and leverages the LLM’s fluency with code-generation, while keeping overall pipeline complexity low.

The paper also notes that FeatLLM was designed to be LLM-agnostic and reports that Appendix experiments examine varying backbones; the main reported results use GPT-3.5.

# Training details
Once FeatLLM has generated rules and parsed them into executable checks, each rule becomes a new binary feature indicating whether a sample satisfies the rule. Suppose there are $R$ rules per class and $c$ classes; for a sample $i$, the binary feature vector for class $k$ is $\mathbf{z}_k^i \in \{0,1\}^R$. FeatLLM uses a simple linear model (without explicit bias) to aggregate these rule-based features into class logits. For class $k$ and sample $i$ the logit is computed as

$ \text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,$

and the class probabilities are obtained by a softmax over logits:

$ \mathbf{p}^i = \text{Softmax}([\text{logit}_1^i, \dots, \text{logit}_c^i]).$

Here the elementwise $\max(\mathbf{w}_k, 0)$ operation enforces non-negativity on the learned weights, which encodes the inductive bias that satisfying a rule should not reduce the likelihood of its associated class. The weights $\mathbf{w}_k$ are the only parameters trained after rule generation.

Optimization and model-selection details reported in the paper are:

- Optimizer: Adam with learning rate $0.01$.
- Training epochs: 200 epochs per trial.
- Model-selection: $k$-fold cross-validation is used to choose the optimal number of epochs and to avoid overfitting on the very small training sets. The value of $k$ is chosen as either 2 or 4 so that each fold’s training split still contains at least one example of every class—an important practical constraint in low-shot regimes.
- Loss: cross-entropy loss over the class probabilities is minimized to learn the weights $\mathbf{w}_k$.
- Ensemble aggregation: after training $T$ independent trials, each producing parameters $\mathbf{w}[t]$, FeatLLM computes the predicted class probability for a sample by averaging the probabilities produced by the $T$ trained linear models.

Two additional implementation and fairness points used in replicating baselines and reporting runtimes are worth noting. First, In-context LLM baselines in the paper used the same GPT-3.5 backbone as FeatLLM for direct comparability, while TabLLM used T0 in line with its original design because TabLLM requires public model checkpoints for parameter-efficient tuning. Second, classical machine-learning baselines (LogReg, XGBoost, RandomForest) had their hyperparameters tuned with grid search and $k$-fold cross-validation to provide competitive, fairly tuned baselines.

Finally, an efficiency note from the experiments: FeatLLM’s pipeline requires a modest number of LLM API calls during setup (the paper reports approximately 30 API queries for their configuration), after which inference for new samples uses only the lightweight trained linear model and does not call the LLM per-sample. This design yields much lower per-sample inference cost compared to end-to-end LLM-inference baselines that call the LLM at prediction time.

Results and Empirical Findings

# Overall performance
The experiments in the paper evaluate FeatLLM over 13 tabular datasets spanning domains such as census income (Adult), banking (Bank), medical (Diabetes, Heart, Myocardial), and others including recent and synthetic datasets (Sequence-type, Solution-mix). Across these diverse tasks and in low-shot regimes, FeatLLM consistently ranks as either the top performer or second best when compared with a broad set of baselines that include traditional tabular learners (Logistic Regression, XGBoost, RandomForest), few-shot and pretraining-based methods (STUNT, TabPFN), and other LLM-based approaches (in-context learning, TABLET, TabLLM).

Two striking empirical observations emerge. First, FeatLLM is able to leverage its generated rule-based features to reach strong predictive accuracy with very few labeled samples: with only 4 shots it attains performance comparable to standard tabular baselines that require 32 shots. This demonstrates the effectiveness of converting LLM-derived knowledge into explicit binary rule features and then learning a simple downstream model on those features. Second, the paper reports sizable gains over existing LLM-based alternatives: on average FeatLLM improves performance (AUC) about 10% compared to methods such as TabLLM and STUNT. These improvements are robust across datasets and repeated random splits (each experiment averaged over three random train/test partitions), indicating that the approach generalizes across problem types and is not driven by a small subset of datasets.

The intuition behind these results is straightforward: the LLM is used to surface high-level decision criteria (rules) that tap its world knowledge and reasoning ability, while a simple trainable model learns the relative importance of those criteria from the few available examples. By turning latent LLM knowledge into explicit, trainable features, FeatLLM combines prior knowledge and data-driven weighting in a way that is especially powerful in few-shot settings.

# Scalability
A key practical limitation of many LLM-centered tabular methods is prompt length: serializing full tables (feature names, types, and many samples) into a single prompt can exceed the LLM’s context window or degrade performance on wide tables. The paper shows that FeatLLM scales to high-dimensional datasets that cause other LLM-based methods to fail or to produce poor results. Datasets such as Communities and Myocardial, which include over 100 attributes, are explicitly noted as challenging for end-to-end LLM inference approaches. FeatLLM addresses this by shifting the LLM’s role from per-sample prediction to rule generation, and by combining rule generation with feature- and instance-level bagging.

Bagging works in two ways for scalability. First, by selecting subsets of features and samples for each trial, the prompt provided to the LLM is kept within acceptable length limits; rather than attempting to encode the whole dataset at once, the model repeatedly queries the LLM on manageable subviews and then aggregates the results. Second, the ensemble of many trials (each producing different rule sets because of randomized examples and a nonzero sampling temperature) compensates for the partial coverage of any single trial: different trials cover different parts of the feature space, and the ensemble aggregates their complementary information. This architecture therefore mitigates the context-window limitation without requiring changes to the LLM model or its API. Empirically, FeatLLM performs well on the large-feature datasets where other LLM-based baselines either cannot infer at all or degrade substantially.

# Training and inference time
One of the principal design goals of FeatLLM is to reduce inference-time cost compared to end-to-end LLM prediction approaches that require one LLM query per test example. The paper reports that FeatLLM achieves low inference latency comparable to conventional tabular methods. In the timing experiments run on the Adult dataset with 16 training shots, FeatLLM’s inference time is presented as comparable to methods like Logistic Regression and XGBoost, whereas in-context LLM approaches, TABLET, and TabLLM incur substantially higher inference times because they require LLM calls during prediction for every sample.

Training time for FeatLLM is higher than for purely classical methods but remains practical and comparable to other LLM-based approaches. Crucially, FeatLLM requires only a relatively small number of LLM API queries in total: the paper reports roughly 30 API queries for the complete feature-extraction and ensemble pipeline. Because those queries are performed during the feature-engineering stage and not at inference, they can be parallelized and they do not impose per-sample inference cost or ongoing query expense. This separation (cost at feature construction time, cheap inference thereafter) is a major advantage in production settings where many test samples will be scored repeatedly.

# Ablation study
To dissect which components drive FeatLLM’s performance, the paper performs ablations that remove four elements one at a time: (1) the weight tuning of the downstream linear model (denoted -Tuning), (2) the ensemble procedure (-Ensemble), (3) inclusion of the feature descriptions in the prompt (-Description), and (4) the Step-1 reasoning instruction where the LLM first infers general tendencies before looking at examples (-Reasoning).

Every ablation produces a performance drop on average across datasets, demonstrating that each component contributes meaningfully. The -Tuning ablation—which replaces learned non-negative weights with an unweighted sum of satisfied rules—degrades performance and its negative impact grows with the number of shots. This indicates that when more labeled data are available, learning the relative importances of rules becomes more feasible and more beneficial. The -Description and -Reasoning ablations have larger negative effects in very low-shot regimes. That result supports the paper’s hypothesis that precise prompt content and staged reasoning help the LLM leverage prior knowledge effectively when examples are scarce; when labels are limited, supplying feature descriptions and asking the LLM to first state general relationships helps it avoid discovering spurious correlations from the few examples. Finally, removing the ensemble (-Ensemble) consistently hurts performance, confirming that repeated randomized rule generation followed by aggregation is an important robustness mechanism. Overall, the ablations show that FeatLLM’s design choices—explicit reasoning instructions, feature descriptions, weight tuning, and ensembling—work together to produce reliable few-shot performance.

# Hyperparameter sensitivity
FeatLLM has two primary hyperparameters studied in the paper: the number of ensembles (i.e., number of independent trials producing rule sets) and the number of rules extracted per class in each trial. The empirical analysis finds the following behavior.

Increasing the number of ensembles monotonically improves performance, but with diminishing returns. In practice the gains begin to converge around 20 ensembles, and the paper adopts 20 as the default. This matches the intuition that beyond some point additional independent trials add little new information because the ensemble has already captured the main consistent rules and the remaining variability is mostly noise.

For the number of rules per class, the experiments did not reveal a statistically significant performance difference across the tested range, and the paper chooses 10 rules per class as a practical trade-off. The reasoning is twofold: more rules increase the dimensionality of the generated feature space and can raise information content, but in low-shot regimes that greater dimensionality also increases the risk of overfitting. Ten rules per class strikes a pragmatic balance between expressiveness and parsimony given the few labels available and prompt-size considerations. The paper therefore fixes the number of rules at 10 in most reported experiments.

Two operational choices related to hyperparameters are worth noting. First, a nonzero LLM sampling temperature is used during rule generation to increase diversity across trials (the paper sets temperature to 0.5 in reported runs). Second, the prompt-level bagging of features and samples is an implicit hyperparameter in that it determines how much of the original table each LLM query sees; this bagging both reduces prompt size and increases ensemble diversity.

# Additional empirical notes: feature quality and robustness to spurious correlations
Beyond aggregate predictive metrics and timing, the paper evaluates the intrinsic utility of the LLM-generated rule features and the method’s robustness to spurious columns. Measuring the AUROC of each generated binary rule feature against the target label, the authors find that a majority of generated rules are informative (AUROC > 0.5) prior to any downstream tuning. When the linear weights are learned on available labeled data, many irrelevant rules are automatically down-weighted: applying a small threshold (weight < 0.1) filters out features that the model deems unhelpful. This demonstrates that the two-stage design—LLM rule generation followed by weighted combination—both produces useful candidate features and lets data prune noisy ones.

To stress-test robustness, the authors attach unrelated columns (drawn from the Adult dataset) to the Heart dataset and progressively increase the number of such spurious features while keeping the same small number of training examples (8 shots). FeatLLM exhibits the least performance degradation compared to the baselines in this experiment. The paper attributes this resilience to the explicit reasoning prompts that encourage the LLM to focus on feature–label relationships that make sense given prior knowledge, reducing the chance that random irrelevant columns generate many misleading rules. Empirically, rules derived from the injected noisy columns form only about 1–2% of the total generated rules in this experiment, showing that the prompt design and staged reasoning help filter spurious signals at generation time.

# Summary
The empirical findings in the paper support a consistent narrative: converting LLM reasoning into explicit, executable rule features and then learning a simple weighted model on those features yields strong few-shot predictive performance, practical inference costs, and robustness on high-dimensional tabular datasets. The combination of careful prompt engineering (feature descriptions and two-step reasoning), rule parsing and execution, weight tuning, and ensemble bagging addresses the principal limitations of fully end-to-end LLM-based tabular methods (per-sample inference cost and context-window limits) while capitalizing on the LLM’s prior knowledge. The reported results—top-ranked performance across 13 datasets, large gains in very low-shot settings, convergence of ensemble benefits around 20 trials, and selective filtering of uninformative rules—demonstrate that FeatLLM is an effective and scalable approach for few-shot tabular learning as presented in the paper.

Understanding Feature Quality and Robustness

# Feature informativeness: AUROC of rule-features vs labels; proportion exceeding 0.5 before and after weight tuning
A central question when we replace raw columns with LLM-generated rule features is: how informative are those binary rule-features for predicting the target? The paper evaluates this by treating each generated rule as a binary predictor and measuring the area under the receiver operating characteristic curve (AUROC) between that single binary feature and the class label. Concretely, for a generated rule that produces a binary feature $z \in \{0,1\}$ across samples, the AUROC quantifies how well $z$ alone ranks positive versus negative samples; an AUROC of $0.5$ indicates no predictive signal, while values greater than $0.5$ indicate some positive association with the target.

The experiments reported in the paper compute two summary statistics per dataset: (1) the average AUROC across all generated rule-features, which measures overall informativeness, and (2) the proportion (ratio) of rules whose AUROC exceeds $0.5$, which counts how many rules are individually useful. These are reported both before and after the downstream weight tuning stage. The "before tuning" measurements show the raw signal that the LLM encodes into its rules using prior knowledge and the few-shot demonstrations. The results (summarized in Table~\ref{tab:quality} of the paper) indicate that a majority of the created rules already carry positive signal with AUROC greater than $0.5$ before any parameter fitting. This demonstrates that the LLM, using the structured prompt and the two-step reasoning instruction, is able to extract features that align with the prediction task even when only a few labeled examples are provided.

After weight tuning (the linear model training step described below), the proportion of useful features typically increases. The tuning phase refines the apparent utility of each rule by combining rule activations with observed labels; rules that do not help the predictive objective end up with very small learned weights. Reporting both before- and after-tuning AUROC statistics therefore separates the intrinsic informativeness of LLM-generated rules from the effect of data-driven weighting.

# Automatic pruning: low-utility rules down-weighted during training
FeatLLM does not simply count how many rules a sample satisfies; it learns how important each rule is for predicting each class. The paper formalizes this using a linear logit model applied to the per-class rule-feature vectors. Denote the binary rule-feature vector for class $k$ on sample $i$ by $\mathbf{z}_k^i \in \{0,1\}^R$, where $R$ is the number of rules per class. The model computes logits and probabilities as

\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\qquad
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\ldots,\text{logit}_c^i]\big).
\]

Here $\mathbf{w}_k$ are trainable weights for class $k$, and the element-wise $\max(\mathbf{w}_k,0)$ projects weights into the non-negative orthant. The projection ensures that satisfying a rule cannot reduce the predicted logit for its associated class; rules can only contribute non-negatively to the evidence for a class.

This learned-weight formulation accomplishes automatic pruning in two ways. First, during optimization (minimizing cross-entropy over the few-shot data), rules that do not help separate classes receive very small learned weights. Second, the non-negativity constraint focuses interpretation on positively predictive rules, avoiding negative weight artifacts that might otherwise arise from small-sample noise. Practically, the paper applies a small threshold (reported as 0.1 based on the observed weight histogram) to identify and discard rules with negligible learned weight. This post-training pruning removes low-utility or noisy rules from the feature set and increases the relative influence of genuinely predictive rules.

The importance of weight tuning is also demonstrated by an ablation: removing the tuning step (replacing weighted sums with simple counts of satisfied rules per class) systematically reduces predictive performance. The reduction is more pronounced as the number of shots increases, because with more labeled data the model can better estimate which rules are truly informative and should be emphasized.

# Spurious correlation stress test: adding irrelevant columns and measuring degradation
An important robustness experiment in the paper probes how well methods avoid relying on spurious correlations when presented with irrelevant features. To do this, the authors took the Heart dataset as the base task and appended randomly sampled columns from the Adult dataset that are unrelated to predicting heart disease. They progressively increased the number of appended, irrelevant columns and measured the change in predictive performance under the same few-shot condition (8 shots). For fairness, methods that require large unlabeled sets (e.g., SCARF, STUNT) were excluded from this comparison.

Across this stress test, FeatLLM exhibited the smallest performance degradation compared to baselines. The paper attributes this resilience to the explicit, prior-knowledge-first prompt design: FeatLLM asks the LLM first to infer general tendencies between features and the task without consulting the few-shot examples, which discourages forming arbitrary associations with irrelevant columns. Empirically, the authors also measured that rules referencing noisy appended columns accounted for only about 1–2% of all generated rules, indicating that the LLM mostly ignored those unrelated columns when crafting rules. In contrast, other methods that rely on naive in-context serialization or end-to-end LLM prediction are more susceptible to picking up spurious correlations because they can more easily latch onto accidental patterns present in the tiny training set.

This stress test demonstrates two things: (1) the LLM’s priors and the prompt’s structure reduce the probability of inventing spurious rules from irrelevant columns, and (2) the subsequent supervised tuning further suppresses any weakly predictive but spurious rules by down-weighting them. Together these elements give FeatLLM greater robustness in the low-shot, high-noise setting.

# Why robustness emerges: prior-knowledge-first reasoning and type-aware rule extraction
FeatLLM’s robustness is not accidental; it follows from several deliberate design choices that orient the LLM and the downstream learner toward meaningful, stable features.

First, the two-step reasoning instruction guides the LLM to use its general (pretrained) knowledge before consulting the few-shot examples. Step 1 asks the model to infer causal relationships or tendencies between features and the target using common-sense and domain priors. Step 2 then uses those priors together with the few examples to propose concrete rules for each class. This decoupling discourages the LLM from directly memorizing idiosyncratic patterns in the small training set, and instead biases rule generation toward patterns consistent with broader knowledge of the domain. In the ablation study, removing this Step-1 reasoning yields a noticeable drop in performance, particularly in very low-shot settings, which highlights its role in robust feature construction.

Second, the prompt explicitly includes feature type information and descriptions. Type-aware rule extraction prevents rule proposals that are syntactically or semantically invalid (for example, comparing a categorical feature to a numerical threshold). By constraining the rule templates and asking the LLM to follow a specific response format, FeatLLM reduces both syntactic parsing failures and the generation of nonsensical rules that could otherwise increase noise. The ablation that removes feature descriptions also degrades performance, which shows that the LLM benefits from having explicit, structured feature metadata.

Third, the learned-weight linear model and the non-negative projection described earlier act as an automatic filter for low-utility rules. This means that even if some spurious rules slip into the generated set, they can be suppressed by the supervised weight estimation step. Removing the weight-tuning step (i.e., relying on raw counts) reduces the ability to discriminate between strong and weak rules and leads to worse accuracy.

Finally, ensembling with bagging amplifies robustness through diversity. Multiple independent runs of LLM rule generation (with randomized demonstration order and a higher sampling temperature) produce different rule sets; training lightweight models on each and averaging their probability outputs reduces sensitivity to any single erroneous batch of rules. Bagging also helps practical prompt-size issues: by sub-sampling features or examples per trial, each LLM prompt stays manageable, and the ensemble of many compact prompts covers more of the overall feature space. The paper reports that ensemble size improves performance up to a convergence point (around 20 trials), consistent with standard ensemble behavior.

All these mechanisms—prior-first reasoning, type-aware prompting, learned non-negative weighting, and ensemble bagging—work together to produce features that are both informative and robust to spurious or irrelevant columns.

# Caveats: vulnerability when attached columns are closely related to the task
While FeatLLM shows improved robustness to randomly appended irrelevant columns, the paper explicitly notes an important caveat: if the attached columns are not randomly irrelevant but are instead closely related to the target task (for example, columns drawn from datasets with overlapping semantics or from auxiliary sources that correlate in complex ways with the label), the LLM can still propose rules that reflect spurious or mistaken causal reasoning. In such cases, the LLM’s rich prior knowledge may cause it to over-generalize from superficially similar columns, and the few-shot examples may not be sufficient to correct that over-generalization. The tuning step can help, but it may not always fully filter such subtle, contextually plausible but ultimately spurious rules.

The paper mentions additional analysis in the appendix demonstrating situations where FeatLLM learned spurious correlations or misunderstood causal relationships when closely related columns were randomly attached. This warns practitioners that FeatLLM’s robustness is strongest against random noise and irrelevant attributes, but not immune to carefully constructed or semantically confounded inputs. Careful dataset curation and domain validation of generated rules remain necessary, especially in high-stakes applications.

# Summary and practical takeaways
The experiments in the paper show that LLM-generated rule-features are often individually informative (measured by AUROC) even before any supervised tuning; that supervised weight tuning and a small threshold prune weak rules; and that the whole pipeline resists performance degradation when many irrelevant columns are added. These strengths arise from the prompt engineering that makes the LLM apply prior knowledge first, from explicit feature typing that constrains rule forms, from non-negative learned weights that emphasize useful rules, and from ensemble bagging that averages over multiple LLM outputs.

At the same time, the system is not infallible: when appended columns are semantically related to the target in misleading ways, FeatLLM can still produce and even rely on spurious rules. Therefore, while FeatLLM substantially improves feature quality and robustness in few-shot tabular learning, the generated rules should be inspected and evaluated in context before deployment in sensitive domains.

Practical Guidance, Limitations, and Future Directions

# Applying FeatLLM step-by-step: data preparation, feature descriptions, prompt crafting, selecting shots
Deploying FeatLLM in practice follows a clear pipeline that mirrors the design described in the paper. Begin with data preparation: assemble your tabular dataset D = \{(\mathbf{x}^i,\mathbf{y}^i)\}_{i=1}^N with d input columns and ensure each column has a concise, natural-language name and (if available) a short definition. FeatLLM relies on these human-readable feature names and descriptions in the prompt so include value types (e.g., continuous, categorical) and, for categorical features, the set of possible categories. These descriptions are part of the “basic information” block in the prompt and materially improve rule generation in low-shot settings.

Selecting shots means choosing the small labeled subset used to demonstrate examples to the LLM. In the experiments, k-shot regimes (k often small, e.g., 4 or 8) were used; FeatLLM is explicitly designed for low-shot settings. When choosing which k samples to include as demonstrations, sample representatively across classes (if possible) so that the LLM sees at least one example of each class. The paper uses k-fold cross validation with k chosen so each fold contains at least one example per class.

Prompt crafting is the critical practical step. The prompt has three pieces:
1. Basic information description: task description as a question, feature names/types/definitions, and serialized few-shot demonstrations. Serialization format used in the paper is, for each example i,
   "f_1 is x^i_1. ... f_d is x^i_d. Answer: y^i".
2. Reasoning instruction: a two-step guidance that first asks the LLM to infer general tendencies or causal relationships between features and target (without looking at the few-shot examples), then asks it to derive specific rules for each class using the few-shot examples and the prior knowledge inferred in step 1. This separation helps the LLM leverage prior knowledge and reduces tendency to latch onto spurious correlations.
3. Response instruction: a constrained output format for rules (so they can be parsed), including a fixed number of rules per class. The paper fixes the number of rules per class to R = 10 in experiments.

When executed, the LLM will output a set of natural-language rules per class. These are then parsed into programmatic checks and turned into binary features as described next.

# Managing prompt size: instance/feature bagging, curating demonstrations, balancing rules per class
Prompt size is a practical constraint for LLM-based methods. FeatLLM uses two complementary strategies to manage prompt length and to improve robustness.

First, feature/instance bagging: each ensemble trial selects a subset of features and (optionally) a subset of instances to include in the prompt. Bagging reduces prompt length per query and increases diversity across ensemble members. This is particularly important for datasets with many columns (the paper demonstrates feasibility on datasets with over 100 attributes). Bagging is also used as a source of randomness (along with a higher sampling temperature) so different trials produce diverse rule sets.

Second, curating demonstrations and balancing rules per class: keep the number of serialized demonstrations small (the k shots chosen earlier) and ensure they are informative. The prompt also constrains the number of rules per class (R). In the paper R = 10 provided a good trade-off: increasing R raises the dimensionality of synthesized features (and risk of overfitting in low-shot regimes) while decreasing R may under-represent relevant criteria. The authors report that performance improves with more ensembles up to a convergence point (empirically around T \approx 20 in their experiments), and that R = 10 balanced prompt length and performance.

Practical advice: if your dataset or LLM has a tight context window, reduce the number of features included via bagging and/or reduce R; increase the number of ensemble trials T to recover coverage across features. Randomize demonstration order across trials because demonstration order influences LLM outputs and increases diversity.

# Cost and runtime planning: batching API calls, parallelization, ensemble sizing
Cost and runtime breakdown for FeatLLM differs from end-to-end LLM inference approaches because FeatLLM only queries the LLM during feature engineering and parsing stages, not at per-sample inference time. In the paper’s implementation, the framework uses a modest number of API queries: the ensemble-backed procedure (with T trials) and additional parsing queries result in a small batch of LLM calls (the paper notes around 30 API queries in their experiments). This is substantially fewer queries than per-sample LLM-based inference methods.

To manage cost and latency:
- Batch and parallelize LLM calls where the API supports it. Each ensemble trial and each parsing call are independent; you can request multiple trials in parallel.
- Choose ensemble size T to balance performance vs. cost. The paper observes performance improvement with increasing T, with gains saturating around T \approx 20. Therefore, T in the 10–30 range is a practical default.
- Use a reasonable temperature to induce diversity (the paper uses temperature = 0.5 for generation) while avoiding excessive noisy outputs that complicate parsing.

At inference time, FeatLLM is lightweight: inference requires only evaluating the learned downstream model (a linear model in the paper) on the generated binary features. This yields low latency comparable to conventional tabular models. Training the downstream linear model is inexpensive and can run on CPU/GPU quickly (the paper used Adam with learning rate 0.01 and 200 epochs and selected epochs via k-fold CV).

# Failure modes and troubleshooting: parsing mismatches, type errors, overly broad or redundant rules
Parsing mismatches. LLM-generated rules are in natural language and may vary syntactically (for example, using "greater than" instead of ">"). The authors avoid brittle hand-coded parsing by asking the LLM itself to produce simple executable code that implements the rules, then executing that code (e.g., via Python’s exec()). If parsing fails, common fixes are: tighten the response instruction to enforce a stricter format, include explicit examples of the expected rule syntax, or re-issue a parsing LLM call that asks for corrected code based on the parsing errors.

Type errors. If a generated rule applies a comparison or category check incompatible with a feature type (e.g., numerical inequality on a categorical feature), the prompt’s basic information block should explicitly state each feature’s type and categories. FeatLLM includes this so the LLM tends to avoid type mismatches. If type errors still occur, add an explicit validation pass after parsing to detect and discard rules incompatible with the feature schema.

Overly broad or redundant rules. LLMs can produce rules that are overly general, too similar to other rules, or outright irrelevant. There are two mechanisms in FeatLLM that mitigate this. First, the downstream linear training learns non-negative weights \mathbf{w}_k for rule-derived features and can down-weight or effectively ignore irrelevant rules. Formally the model computes logits as:
   \text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
where \mathbf{z}_k^i \in \{0,1\}^R is the rule-satisfaction vector for class k and the positive projection \max(\mathbf{w}_k,0) enforces non-negativity. Second, ensemble averaging across trials dilutes the effect of incorrect rules: incorrect rules that appear in a small fraction of trials will have less impact on the averaged class probability. If you still observe a large number of uninformative rules, you can post-filter rules by empirical mutual information or by a small held-out validation set.

Other troubleshooting steps: if the model appears to latch onto spurious correlations, consider strengthening the reasoning instruction's first step (requesting explicit prior-knowledge reasoning) or increasing randomness across trials to search for more diverse, correct rules. The paper’s experiments show FeatLLM degrades less than baselines when unrelated columns are attached, but it can still be misled when closely related columns are present.

# Limitations: reliance on LLM prior knowledge and potential biases, prompt sensitivity, low-shot focus
FeatLLM inherits both strengths and limitations of prompting LLMs. A primary asset is the LLM’s prior knowledge: it can suggest domain-relevant rules that compensate for limited labeled data. The flip side is that this same prior knowledge can introduce biases, incorrect assumptions, or misinformation. The paper explicitly warns that LLM priors can dominate predictions and that further analyses of societal biases and misinformation embedded in LLM knowledge are necessary before widespread adoption in sensitive domains.

Prompt sensitivity is another limitation. The LLM’s outputs depend on prompt wording, demonstration order, and decoding temperature. FeatLLM reduces brittleness by structuring the prompt into reasoning and response instructions and by ensembling, but practitioners must still test prompt variants and monitor output quality.

Scope limitation: FeatLLM is designed and evaluated for few-shot classification tasks. Its hyper-parameters and model choices (e.g., number of rules R per class, non-negative linear aggregator, ensemble size T) are tuned for low-shot regimes. The paper frames future work as expanding capabilities for datasets with larger numbers of labeled samples and exploring feature types beyond rule-based binary features. Until such extensions are validated, FeatLLM is best applied where the problem fits the low-shot, classification setting with meaningful natural-language feature descriptions.

# Ethical and broader impacts: domain biases, misinformation risks, high-stakes domains (finance/healthcare)
When applying FeatLLM in practice, the same ethical considerations that apply to LLMs and automated feature engineering must be addressed. Because FeatLLM leverages LLM prior knowledge to generate rules, that prior knowledge can reflect societal biases present in the pretraining corpora. In high-stakes areas such as healthcare and finance (both explicitly noted in the paper as motivating application areas), such biases can lead to unfair or unsafe decisions.

Practical mitigations suggested by the paper’s framing include:
- Treat LLM-generated rules as hypotheses requiring human review when decisions have significant consequences.
- Use the tunable downstream step to let empirical data down-weight suspect rules, but do not rely solely on data if small sample sizes make weight estimation noisy.
- Analyze whether rules generated systematically disadvantage particular groups, and perform bias audits before deployment.
- Recognize that FeatLLM can produce plausible-sounding but incorrect causal claims; domain experts should validate rule semantics.

The paper emphasizes that analyzing the societal biases and misinformation embedded in LLM priors is an important direction prior to broad adoption.

# Extensions: alternative LLM backbones, richer rule grammars, scaling and interpretability
The authors design FeatLLM to be LLM-agnostic and note experiments with different backbone models in the Appendix. Practically, you can swap the LLM backbone (subject to API and prompt-format differences) to exploit models with different strengths: some models may have stronger factual priors for particular domains, others may have better code generation for parsing. When changing backbones, re-tune temperature, top-p, and other decoding parameters.

Richer rule grammars and feature types are a target for future work described in the paper. Currently FeatLLM converts rules to binary features indicating rule satisfaction. A natural extension is richer programmatic outputs (multi-valued features, continuous transformations, or interactions) generated and parsed via the LLM. The paper explicitly mentions exploring “various feature types beyond rules” and improving interpretability as future directions.

Scaling beyond few-shot: the authors note that FeatLLM’s present focus is low-shot. For larger labeled datasets, extensions could include more sophisticated downstream models taking the LLM-generated features as inputs, or using the generated rules as seeds for hybrid approaches that combine LLM priors with traditional feature engineering and AutoML pipelines. The core idea—using an LLM as a feature engineer rather than a per-sample predictor—remains applicable and can modularly integrate with other automated modeling techniques.

# Key takeaways and when to use FeatLLM in practice
FeatLLM is a practical approach when you have a tabular classification task with very limited labeled data (few-shot), natural-language feature names/descriptions, and access to an LLM via API (no fine-tuning required). It is most appropriate when you want:
- Low inference latency at deployment (the LLM is not queried per sample).
- To leverage LLM prior knowledge to compensate for scarce labels.
- A degree of interpretability because outputs are rule-like and human-readable.

Avoid or be cautious with FeatLLM when:
- The downstream task is high-stakes and requires full auditability without reliance on opaque priors (human validation is essential).
- You have abundant labeled data and prefer end-to-end supervised models optimized purely from data (the paper notes FeatLLM targets low-shot settings).
- You cannot afford any risk from LLM priors inducing bias or misinformation.

Practical defaults from the paper: ensembles T \approx 20, rules per class R = 10, LLM temperature around 0.5, downstream linear optimization via Adam with learning rate 0.01 for 200 epochs (selecting epochs by k-fold CV). Use bagging to manage prompt size and to introduce diversity; parse rules by asking the LLM to output executable code and validate the generated code before executing.

Final thought: FeatLLM reframes an LLM from a black-box per-sample predictor into a prior-informed feature engineer. This shift reduces per-sample inference cost, mitigates prompt-length constraints, and produces human-readable rules that can be tuned with few labeled examples — a practical pattern worth exploring when labels are scarce and LLM access is available.
