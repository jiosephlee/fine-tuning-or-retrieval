# Does Code Training Improve Reasoning? What We Learned from DeepSeekMath

Mathematical reasoning remains one of the toughest challenges for today's large language models (LLMs). In the recent DeepSeekMath work, the authors dug into an intriguing question: can pre-training on code actually help a model solve math problems more effectively? As practitioners, we often wonder whether investing compute in code data pays off when our end goal is better reasoning. Here, I’ll walk you through the key takeaways from DeepSeekMath’s experiments, highlight practical training recipes, and flag some pitfalls—especially the pesky issue of catastrophic forgetting—so you can design your own efficient math-reasoning models on a budget.

## Why Code Might Help with Math

At first glance, code and math might seem like separate worlds. But both involve structured thinking, a need for precise syntax, and step-by-step transformations. Code forces a model to learn how to:

- Represent variables and expressions,
- Chain operations in a clear order,
- Debug or handle errors in logic.

These are the exact skills you’d want when you solve a multi-step algebra or calculus problem. Past work hinted that code training improves general reasoning, but DeepSeekMath offers one of the first systematic looks in the math domain.

## Two Approaches: Two-Stage vs. Mixed Training

DeepSeekMath’s team experimented with two main recipes for blending code and math data:

1. **Two-Stage Training**  
   - Stage 1: Pre-train on 400 billion code tokens.  
   - Stage 2: Continue pre-training on 150 billion math tokens.

2. **One-Stage Mixed Training**  
   - Pre-train on a mixed feed of 400 billion code tokens plus 150 billion math tokens.

Both used the same base LLM (1.3 billion parameters) and the same optimizer and learning-rate schedule. What changed was only the ordering and mixture of data.

## How They Measured Success

To see whether code data really boosts math skills, two types of tasks were evaluated:

- **Without tools**: Step-by-step chain-of-thought reasoning on GSM8K and the competition-level MATH benchmark.
- **With tools**: Writing Python programs to solve the same problems, relying on libraries like `math` and `sympy` for heavy lifting.

For each setting, higher accuracy means the model solved more grade-school or contest-level problems correctly.

## Key Findings

### 1. Code Training Helps Program-Aided Math

Under two-stage training, models that saw 400 billion code tokens in Stage 1 already showed dramatically better performance when writing Python solutions. Adding 150 billion math tokens in Stage 2 improved them even further. In other words, code data laid a strong foundation for tool-use reasoning.

Even in the one-stage mixed run, simply blending code and math tokens helped maintain coding prowess while boosting program-aided math performance. That mixed recipe also avoided the “catastrophic forgetting” that pure two-stage training sometimes suffered in coding benchmarks.

### 2. Code Training Also Improves Chain-of-Thought Reasoning

When solving problems purely by writing out steps (no code), two-stage training still paid dividends. Stage 1 code pre-training led to a measurable jump in chain-of-thought accuracy. Stage 2 math data then built on that, yielding the best overall results.

However, the mixed one-stage run was less effective for pure chain-of-thought. It seems the model’s 1.3 billion-parameter capacity couldn’t fully absorb both data sources in one go, leading to a slight dip in non-tool reasoning.

### 3. Catastrophic Forgetting Is Real—but Fixable

A classic downside of staged fine-tuning: if you pre-train heavily on code first, then switch to math-only data, you can lose some coding skills. DeepSeekMath confirmed that:

- In pure two-stage training, coding benchmark scores dropped after Stage 2.

But by blending both data sources together in one big mixed pre-training run, the model retained its coding abilities while still learning math. In practice, mixing is a simple strategy to dodge catastrophic forgetting.

## Practical Recipes on a Budget

Depending on your compute constraints and ultimate goals, here are some distilled recommendations:

- **If you care most about writing correct Python solutions** (tool-use reasoning):  
  • Follow a two-stage approach. Spend a few hundred billion tokens on code first, then switch to math data.  
  • This yields the largest gains in program-aided tasks.

- **If you need both code and math skills in one model**:  
  • Use a mixed pre-training pool, interleaving code and math tokens.  
  • This helps you avoid forgetting code without sacrificing math performance too much.

- **If you only care about chain-of-thought math reasoning** (no code execution):  
  • Two-stage still beats mixed for smaller models.  
  • But be mindful: pure math training after code helps most when capacity is ample.

## Pitfalls and Open Questions

Even with these insights, a few issues remain:

- **Model Scale Matters**: DeepSeekMath’s observations used a 1.3 billion-parameter model. Larger models may handle mixed data better, reducing the chain-of-thought dip in the one-stage run.
- **Data Quality Over Quantity**: It isn’t just about raw token counts. Clean, diverse math text—especially multilingual content—makes a big difference.
- **Task Specialization**: These experiments focused on arithmetic, algebra, and contest-style problems. You may see different effects in geometry proofs or higher-level analysis.

## Conclusion

DeepSeekMath gives strong empirical support to the idea that code training can improve mathematical reasoning—both with and without tools. For practitioners building math-capable LLMs, the choice between two-stage and mixed pre-training comes down to your priorities: maximize tool-use accuracy or avoid catastrophic forgetting. Either way, baking in a substantial tranche of code data is a recipe worth trying. With careful balancing of data sources, even modestly sized models can punch above their weight on math benchmarks.
