According to the paper 'DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models', to preserve coding performance while doing extensive math pretraining, the authors explicitly chose to include code tokens. This design choice is stated in the training recipe for DeepSeekMath-Base 7B, where the continual pretraining mix includes Github code (\(20\%\) of the 500B-token run) alongside math (\(56\%\)), arXiv (\(10\%\)), and general natural language (\(10\%\)). The paper then documents that DeepSeekMath-Base “effectively maintains the performance of DeepSeek-Coder-Base-v1.5 on the two coding benchmarks” (HumanEval and MBPP), directly connecting the inclusion of code tokens to the retention of coding capabilities. Since the model is initialized from a code-pretrained backbone (DeepSeek-Coder-Base-v1.5 7B), continuing to expose it to coding data during math-focused pretraining mitigates distribution drift away from programming and helps avoid catastrophic forgetting of code-specific skills.

The reinforcement for this choice comes from the ablation studies in the “Lessons Learnt in Pre-Training” section. There, the authors show that “math training following code training degrades coding performance,” but that mixing code tokens with math tokens in a one-stage regime can “effectively mitigate the issue of catastrophic forgetting” and even synergize program-aided mathematical reasoning. In other words, when the training signal is dominated by math-only data, the conditional probabilities \(p_\theta(\text{code tokens} \mid \text{contexts})\) are not reinforced and can decay; interleaving code examples supplies regular, domain-relevant gradients that stabilize these probabilities and preserve coding competence. Empirically, they observe that code training benefits program-aided math and that maintaining code in the pretraining mixture keeps HumanEval/MBPP scores comparable to the starting coder model, making it sensible to explicitly allocate code tokens during extensive math pretraining.
