# FlashAttention-3 in Plain English: Why It Matters for Faster, Longer-Context Transformers

## Overview

Attention is the computational hot spot in Transformers: computing the attention scores of queries and keys grows quadratically in sequence length, so every improvement here multiplies into big savings for long-context models. FlashAttention introduced a GPU-kernel approach that fuses attention operations and avoids writing large intermediate matrices to slow global memory. FlashAttention-3 takes that idea further by redesigning the algorithm to exploit two hardware trends in modern accelerators (exemplified by NVIDIA Hopper / H100): asynchronous specialized units (Tensor Cores and a memory accelerator) and much higher throughput for low-precision math (FP8). The result: substantially higher utilization and much faster attention without changing the math of the layer.

Headline results from the paper:
- FP16 forward-pass speedups of about 1.5–2.0× over FlashAttention-2 on an H100 GPU.
- FP16 throughput reaching up to 740 TFLOPs/s (about 75% of theoretical Tensor Core throughput on H100).
- FP8 throughput approaching 1.2 PFLOPs/s.
- FP8 numerical error reduced by about 2.6× compared to a baseline FP8 attention that uses per-tensor quantization.

Below I unpack what changed, why it helps, and what it means for training and inference.

## Why attention is the bottleneck (again)

For a single head with sequence length \(N\) and head dimension \(d\), attention computes:
- scores \(S = \alpha Q K^\top \in \mathbb{R}^{N\times N}\),
- row-wise softmax \(P = \mathrm{softmax}(S)\),
- outputs \(O = P V\).

The naive approach materializes the full \(N\times N\) matrices \(S\) and \(P\) in global memory, which is expensive in bandwidth and memory and becomes infeasible in long-context settings. FlashAttention-style kernels avoid these global-memory intermediates by tiling and doing local softmax reductions in on-chip memory, which dramatically reduces global memory traffic. But newer GPUs introduce additional opportunities and constraints that earlier FlashAttention versions did not fully exploit.

## What FlashAttention-3 changes (the three main ideas)

FlashAttention-3 introduces three complementary techniques to get more performance from modern GPUs:

1. Producer-consumer asynchrony via warp-specialization and a circular shared-memory buffer.
   - Modern GPUs separate responsibilities: a Tensor Memory Accelerator (TMA) for asynchronous loads between global memory (HBM) and shared memory, and Tensor Cores (via asynchronous WGMMA on Hopper) for very fast matrix multiply.
   - FlashAttention-3 assigns different warpgroups inside a CTA to producer or consumer roles. Producers stream blocks of \(K\) and \(V\) (and the local \(Q\) tile) into shared memory using asynchronous TMA. Consumer warpgroups perform the computation (Tensor Core GEMMs) reading from that shared memory.
   - This warp-specialization lets data movement and compute progress concurrently, improving hardware utilization.

2. Overlap softmax work with asynchronous block GEMMs (GEMM-softmax pipelining).
   - Softmax needs elementwise exponentials and reductions, which are relatively low-throughput compared to Tensor Core GEMMs. If softmax runs on the same hardware at the same time as GEMMs, it creates stalls.
   - FlashAttention-3 breaks the strict within-iteration dependency by pipelining across iterations: while one block's GEMMs are running on Tensor Cores, the softmax for another already-produced block is computed on scalar units. Concretely, they use a 2-stage (and optionally 3-stage) pipeline where a WGMMA computing \(\mathbf{Q}\mathbf{K}_j^\top\) is issued asynchronously while the previous iteration’s softmax and the \(\tilde{P}\mathbf{V}\) GEMM are in flight. They also use a ping-pong scheduling across warpgroups so that softmax of one warpgroup is executed while another warpgroup drives the Tensor Cores.
   - This hides the softmax cost under the high-throughput GEMMs and raises Tensor Core utilization.

3. Carefully using FP8 Tensor Cores plus block quantization and incoherent processing to retain accuracy.
   - Hopper’s FP8 Tensor Cores offer roughly 2× more matmul throughput than FP16, but they impose operand layout constraints (they expect k-major operand layout) and FP8 has much lower dynamic range/precision than FP16.
   - FlashAttention-3 addresses layout issues with in-kernel tile transposes (using LDSM/STSM warp instructions) and by permuting register layouts so back-to-back WGMMAs remain compatible.
   - To control quantization error, they use block quantization (one FP8 scaling factor per block, matching the block structure the algorithm already uses) and an “incoherent” random orthogonal preconditioning (multiply \(Q\) and \(K\) by the same random orthogonal matrix \(M\) before quantizing). Because \(M\) is orthogonal, the attention \(QK^\top\) is unchanged, but the preconditioning spreads out outliers and reduces FP8 quantization error. Implementations use practical fast choices for \(M\) (Hadamard times random sign diagonals) so cost is \(O(d\log d)\).

## Key implementation considerations

- The algorithm relies on asynchronous execution and explicit synchronization (barrier instructions) to sequence producers and consumers and to let multiple warpgroups ping-pong.
- The 2-stage pipeline requires extra registers to hold "next" intermediate tiles; trading register pressure and block sizes is part of kernel tuning.
- For FP8, the kernel performs in-kernel transposes (so there is no separate costly pre-transpose step) and uses byte-permute and small register shuffles to meet the FP8 WGMMAs’ layout expectations.
- Some of the compiler and SASS-level behaviors (NVCC reordering, exact instruction timing) matter; the authors analyze SASS output to ensure the intended overlap is produced.

## Empirical results (what they measured)

Benchmarks were performed on H100 80GB SXM5 GPUs. Important empirical points reported:

- FP16 forward pass: 1.5–2.0× faster than FlashAttention-2 across a range of sequence lengths and head dimensions. Peak measured FP16 throughput reached ~740 TFLOPs/s (~75% of H100 Tensor Core peak).
- FP16 backward pass: about 1.5–1.75× faster than FlashAttention-2.
- FP8 forward pass: achieved throughput close to 1.2 PFLOPs/s in favorable settings.
- For very large sequence lengths, FP16 FlashAttention-3 outperforms or matches an H100-optimized vendor (cuDNN) attention implementation; FP8 is competitive depending on head dimension and causal masking.
- Numerical accuracy: In FP16, FlashAttention-3 matches or improves on FlashAttention-2 because critical intermediate operations (softmax scaling) are kept at higher precision internally. For FP8, block quantization plus incoherent preconditioning reduced RMSE by about 2.6× compared to a baseline FP8 attention that uses per-tensor quantization.

## What this means in practice

- Higher utilization and faster kernels directly reduce wall-clock time for both training and large-batch or long-context inference. A 1.5–2× speedup on attention can translate into significant end-to-end gains for Transformer layers, especially when sequence length is large and attention dominates runtime.
- FP8 support with controlled accuracy (block quant + incoherent processing) makes the very-high-throughput FP8 Tensor Cores practical for attention without huge loss in numerical fidelity—this is particularly relevant for inference and potentially for mixed-precision training if care is taken with accumulators and numerically sensitive operations.
- The methods are especially meaningful for long-context applications (large \(N\)), where the attention compute and memory patterns amplify the benefits of reduced global-memory traffic and better overlap of compute and data movement.
- Integrating these techniques into libraries (the authors plan PyTorch / Hugging Face integration and have open-sourced FlashAttention-3) means application developers can benefit without reimplementing low-level kernels.

## Limitations and caveats

- The improvements rely on Hopper/H100 hardware features (asynchronous WGMMA/TMA and FP8 Tensor Core behavior). While the ideas are portable in spirit to other hardware that provides asynchronous compute/memory and low-precision math, details (instruction set, layout constraints) will differ.
- The FP8 kernel in the paper is not yet a fully persistent kernel (unlike the FP16 implementation), which means FP8 may be less optimal in some small-sequence or causal-mask scenarios.
- The pipelined implementation trades register usage for overlap; kernel tuning (block sizes, number of stages, warpgroup division) is needed to get the best balance for any given hardware and model shape.
- Numerical behavior still needs careful validation in full-scale training runs; reported RMSE reductions are promising but do not replace full training-stability studies.

## Bottom line

FlashAttention-3 shows that rethinking an algorithm with hardware asynchrony and low-precision in mind yields substantial practical speedups for attention. By combining warp-specialized producer/consumer pipelining, GEMM-softmax overlap, and careful FP8 engineering (layout work plus block quantization and incoherent preconditioning), it delivers 1.5–2× FP16 speedups on H100 and unlocks near-PFLOP FP8 attention with much better accuracy than straightforward per-tensor FP8 quantization. For anyone building long-context Transformers or optimizing Transformer infrastructure on modern GPUs, FlashAttention-3 is an important, production-oriented advance to consider.



# Asynchrony on GPUs, Demystified: How Warp Specialization Turbocharges Attention

## Overview — why asynchrony matters for attention

Attention in Transformers is computationally heavy and memory-hungry: for a single head with sequence length $N$ and head dimension $d$, the score matrix is $\mathbf{S} = \alpha \mathbf{Q}\mathbf{K}^\top \in \mathbb{R}^{N\times N}$ and the output is $\mathbf{O} = \mathrm{softmax}(\mathbf{S})\mathbf{V}$. That quadratic dependence on $N$ makes the attention layer the bottleneck for long-context workloads.

Modern GPUs like NVIDIA Hopper expose two key hardware features that let us mitigate that bottleneck if we design kernels to use them: (1) dedicated asynchronous engines for heavy compute (Tensor Cores, invoked via WGMMA) and for bulk memory movement (the Tensor Memory Accelerator, TMA), and (2) much higher throughput for fused matrix multiply operations than for the scalar/math functions (e.g., exponentials used in softmax). FlashAttention-3 shows how to turn those features into concrete speedups by rethinking the software model in terms of producers and consumers of data, and by specializing warps to those roles.

This post explains the intuition and mechanisms behind that approach: what warp specialization is, how to structure producer–consumer pipelines, and how overlapping asynchronous Tensor Core GEMMs and data movement hides latency and dramatically improves utilization.

## The mental model: independent engines, asynchronous work

Think of a Hopper GPU as a small factory floor with three specialized teams:

- Tensor Cores: the heavy machinery that multiplies matrices very fast (massive FLOPs/sec).
- TMA: a conveyor belt that moves big blocks between off-chip memory (HBM/GMEM) and on-chip shared memory (SMEM) efficiently and asynchronously.
- CUDA cores / MFU: the general-purpose workers that do control, reductions, exponentials (softmax), and bookkeeping.

Critically, these teams can work concurrently. A long matmul on Tensor Cores can run while the TMA is fetching the next blocks, and the MFU can compute exponentials and reductions in parallel with a WGMMA that is already running, if the software schedules things properly. The problem FlashAttention-2 faced on Hopper was that it treated everything more synchronously and so didn’t get close to the Tensor Core throughput that optimized GEMMs do: measured utilization was around 35% versus 80–90% achieved by dedicated GEMM kernels.

To exploit the overlap, we move from a single “all-threads-do-everything” kernel to a producer–consumer model inside each CTA (cooperative thread array), implemented via warp specialization.

## Warp specialization: split the crew by job

A warp is the minimal SIMD execution unit (32 threads). Warp specialization means: assign different warps in the same CTA to different, persistent roles:

- Producer warps issue TMA loads that asynchronously bring blocks of $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$ into shared memory.
- Consumer warps run the WGMMA Tensor Core kernels (GEMMs) and do the local softmax / reductions and partial accumulation into $\mathbf{O}$.

Why is that useful?

- TMA loads are non-blocking. Producers can enqueue loads for future blocks and continue managing other work. Consumers can start GEMMs as soon as required tiles are present in SMEM.
- Tensor Core GEMMs (WGMMA) are asynchronous on Hopper. Consumers can issue WGMMA and keep the pipeline full while the producers are still fetching the next tiles.
- We can tune register allocation differently per role. Producers need far fewer registers (they mostly set up TMA descriptors, issue loads and maybe do an in-register transpose), while consumer warps running WGMMAs and holding intermediate partial accumulators need lots of registers.

Hopper exposes an API (e.g., setmaxnreg) allowing dynamic reallocation of registers across warpgroups so you can give consumer warps a larger slice of register file and keep producer warps lean. This improves register utilization and avoids forcing all warps into a single worst-case register budget.

Analogy: instead of everyone in a kitchen doing prep, stove, and plating sequentially, you have a prep team (producers) that keeps the counter stocked, and a stove team (consumers) that cooks continuously. Each team has tools optimized for their task; letting them work concurrently avoids idle time.

## The circular SMEM buffer and producer–consumer synchronization

To safely share tile buffers in SMEM between producers and consumers without spilling to global memory, FlashAttention-3 uses a small circular buffer of $s$ stages in SMEM. Producers write tiles into the next free stage, and consumers read from the most recent ready stage. The buffer length $s$ allows producers to get ahead by up to $s$ tiles and keeps consumers from stalling if a single load is slightly late.

Synchronization (barriers) and lightweight commit/notify semantics ensure the producer never overwrites a stage still being used by a consumer, and the consumer never reads a stage that isn't fully loaded. Because TMA and WGMMA are asynchronous, these operations are mostly non-blocking: a producer can issue loads for several tiles in flight, and a consumer can issue WGMMAs as soon as operands are visible in SMEM.

That pattern (produce a tile, enqueue loads for future tiles, compute on current tile, repeat) is the backbone that lets us hide HBM bandwidth and latency behind compute.

## Overlapping softmax with GEMMs: pingpong scheduling

Softmax is not a GEMM. It uses exponentials and reductions on the multi-function unit (MFU), which has much lower throughput than Tensor Cores. If we naively perform softmax sequentially between two GEMMs, the MFU work becomes a large fraction of runtime and stalls Tensor Cores.

FlashAttention-3 uses two related ideas to hide softmax cost:

1. Inter-warpgroup pingpong: split the consumer work into two warpgroups. While warpgroup A runs its WGMMAs, warpgroup B computes softmax on the previously produced score tile, and vice versa. Barriers coordinate ordering to ensure data dependencies are satisfied while the MFU work is scheduled in the shadow of Tensor Core execution happening in the other warpgroup.

2. Intra-warpgroup pipelining (2-stage pipeline): even inside one warpgroup, issue the next $\mathbf{Q}\mathbf{K}^\top$ WGMMA (call it GEMM0 for iteration $j+1$) and overlap it with the $\tilde{\mathbf{P}}\mathbf{V}$ WGMMA (GEMM1 for iteration $j$) and the softmax for iteration $j+1$. The idea is to keep multiple WGMMA calls in-flight asynchronously and to use registers to hold the intermediate $\mathbf{S}_\text{next}$ (the score block for the next iteration) while softmax for it is being computed and GEMM for the previous iteration completes.

This is a classic producer–consumer pipelining across iterations: compute S_j, start computing P_j (softmax), but also immediately enqueue the WGMMA that computes S_{j+1}. Later, while GEMM1 for j is still running on Tensor Cores, the MFU is free to compute exponentials/row reductions for S_{j+1}. That interleaving is what reduces MFU idle time and elevates Tensor Core utilization.

The concrete FlashAttention-3 implementation demonstrates that these overlaps raise FP16 forward throughput from the 35% utilization regime of previous code to measured peaks of up to 740 TFLOPs/s (about 75% of H100 theoretical TFLOPs), and FP8 throughput approaches 1.2 PFLOPs/s.

## Register reallocation: giving each warp what it needs

One implementation detail that makes warp specialization practical is dynamic register allocation. Different warp roles have different register footprints:

- Consumer warps doing WGMMAs and holding partial accumulators need many registers for tile accumulators and temporaries.
- Producer warps issuing TMA loads and doing small transposes need very few registers.

Hopper supports dynamic reallocation (e.g., setmaxnreg) so you can de-allocate some registers from producer warps and reassign them to consumers. This avoids the usual global kernel-level constraint of a single register budget per thread, allowing better per-role optimization and reducing register spilling.

The trade-off is careful profiling: giving too many registers to consumers reduces occupancy (fewer warps can be scheduled), while giving too few causes spilling. The FlashAttention-3 design balances these concerns to maximize the combined effect of higher Tensor Core occupancy and minimal stall from loads/softmax.

## Practical pipeline trade-offs

A few practical constraints to keep in mind when designing these pipelines:

- Register pressure: deeper pipelines (3-stage, 4-stage) can increase overlap but require storing more intermediate tiles in registers, which may force spills or lower occupancy. FlashAttention-3 uses a 2-stage pipeline that gives the best practical trade-off for many parameters; a 3-stage variant is possible but needs more register budget.
- Compiler reordering: the CUDA compiler can rearrange instructions in ways that break intended overlaps. FlashAttention-3 verifies via SASS inspection that the desired overlapped instruction patterns survive compilation, and in practice they do on Hopper when using the correct primitives (TMA, WGMMA) and explicit barriers.
- SMEM buffer sizing: the number of circular stages $s$ must be chosen so the producer can stay a few tiles ahead but not waste shared memory. Typical values balance pipeline depth and SMEM capacity.
- Correctness and numerical stability: flash attention keeps intermediate reductions in higher precision when needed (e.g., rescaling uses FP32), and these choices keep FP16 behavior at least as numerically stable as prior FlashAttention-2. (FP8 brings additional accuracy techniques, but that's a separate topic.)

## Visualizing the overlaps (textual diagram)

Imagine a time axis and two warpgroups A and B. Each box is an operation; arrow means dependency.

Time →
Warpgroup A:  [Load K0/V0 from GMEM -> WGMMA S0=QK^T] --- [softmax on S0] --- [WGMMA P0*V0]
Warpgroup B:           [WGMMA S1=QK^T] --- [softmax on S1] --- [WGMMA P1*V1]

With pingpong scheduling the timeline interleaves so that while WGMMA on A is executing, softmax on B is scheduled and executed on the MFU. Within one warpgroup, the 2-stage pipelining looks like:

Iteration j:
- Issue WGMMA: S_cur = Q K_j^T (async)
- While that WGMMA runs, issue WGMMA for previous P_prev * V_{j-1}
- Wait for S_cur, compute softmax on S_cur producing \tilde{P}_cur (MFU)
- Meanwhile, the previous WGMMA completes and writes partial outputs
- Continue loop by issuing WGMMA for S_next

The key is that heavy Tensor Core work is almost never idle waiting for slow exponentials, and TMA prefetch keeps SMEM stocked.

## Measured impact (what the hardware buys you)

FlashAttention-3 demonstrates several concrete improvements on H100:

- FP16 forward throughput reaches up to 740 TFLOPs/s (about 75% utilization), a 1.5–2.0× speedup over FlashAttention-2 in many settings.
- FP8 Tensor Core usage nearly doubles FP16 matmul throughput and can reach ~1.2 PFLOPs/s for GEMM-dominated workloads (with additional layout and quantization techniques to keep accuracy acceptable).
- The 2-stage overlap and warp specialization together account for the majority of the speedup; ablations show going from a synchronous implementation to an overlapped one increases throughput markedly (e.g., 570 → 661 TFLOPs in an example).

These gains are not magic — they come from matching the software execution model to the hardware reality: separate, asynchronous accelerators for data movement and dense math.

## When to use this pattern and limitations

The producer–consumer + warp-specialization pattern is most effective when:

- Compute is dominated by large, asynchronous GEMMs (Tensor Cores).
- You have expensive, lower-throughput non-GEMM work (exponentials/reductions) that can be overlapped with GEMMs.
- The kernel can be restructured into block-wise producers and consumers that share tiles in SMEM.

Limitations and trade-offs include register pressure vs. occupancy, the need to respect hardware layout constraints (especially for FP8 WGMMA), and the complexity of implementing robust synchronization and in-kernel transposes. FlashAttention-3 addresses many of these but also documents that FP8 kernels still need further engineering (e.g., persistent kernel designs) to match FP16 performance in all regimes.

## Takeaway

On modern accelerators like Hopper, the key to faster attention is not just algorithmic math but designing software to reflect the GPU’s hardware specialization. Treat the GPU as a system with multiple asynchronous engines and assign warps to be producers (TMA) or consumers (WGMMA + MFU). Use a circular SMEM buffer, dynamic register reallocation for role-specific register budgets, and a small pipeline depth (e.g., 2-stage) to overlap GEMMs and softmax. When you do that, Tensor Cores spend much more of their time multiplying instead of waiting, and attention throughput climbs from the 30–40% utilization regime into the 70–80%+ regime.

FlashAttention-3 is a concrete realization of these principles and shows that thinking in terms of asynchrony and warp specialization is a practical and powerful way to squeeze much more performance out of attention kernels on modern GPUs.



# Hiding Softmax Under Matmuls: The 2-Stage Pipeline That Makes Attention Fly

## Overview

Attention in Transformers computes pairwise scores and then a softmax-weighted sum. While the matrix-multiply parts (GEMMs) get most of the FLOPs, the row-wise softmax—especially its exponential and reduction operations—can become a practical bottleneck on modern hardware. FlashAttention-3 exposes a simple but powerful idea: exploit hardware asynchrony to overlap softmax work with Tensor Core matmuls, both across warpgroups (ping-pong scheduling) and inside a warpgroup (a 2-stage GEMM–softmax pipeline). The result: much higher Tensor Core utilization on Hopper (H100) GPUs and big speedups vs. prior FlashAttention versions.

This post walks through the intuition, the 2-stage pipeline, why Hopper makes it possible, and the practical trade-offs (register pressure, tile sizes, compiler behavior) that determine how much you actually win.

## Why softmax can be a sleeper bottleneck

The forward attention for a single head is conceptually:

- Compute the scores: S = α Q K^T, where α = 1/√d.
- Row-wise softmax: P = softmax(S).
- Output: O = P V.

Although the GEMMs (the QK^T and P V multiplications) dominate FLOP counts, the softmax contains operations that are relatively expensive per output element in terms of the hardware unit that executes them (special functions like exponential, and scalar reductions). On Hopper H100 the asymmetry is stark:

- FP16 Tensor Core matmul throughput: on the order of 989 TFLOPS (device peak).
- Special-function throughput (e.g., exp): roughly 3.9 TFLOPS (16 special-function ops per SM per cycle × SM count × clock).

That means matmul throughput is hundreds of times larger than special-function throughput. So although overall matmul FLOPs are much larger, the softmax's special-function instructions (exp, row max, reductions) can still occupy a significant fraction of wall-clock time unless you hide them under matmuls.

## The key enabler: hardware asynchrony on Hopper

Hopper gives us two important asynchronous resources:

- An asynchronous Tensor Core execution model exposed via the WGMMA/Warpgroup-wide WGMMA instruction, which can issue matmuls that proceed without stalling the calling threads immediately.
- An asynchronous memory-copy engine, the Tensor Memory Accelerator (TMA), to move tiles between global memory (HBM) and shared memory (SMEM).

Because these units do useful work independently of the CUDA cores issuing control instructions, we can structure threads (warps) so some warps issue and wait for memory movement while others perform (or issue) WGMMA matmuls and other warps run the softmax kernels. This warp-specialization and asynchrony is what FlashAttention-3 leverages.

## Two complementary forms of overlap

FlashAttention-3 overlaps softmax and GEMMs in two ways:

1. Inter-warpgroup overlap (ping-pong scheduling). Entire warpgroups alternate roles so that while one warpgroup runs its softmax, another is driving Tensor Cores on GEMMs. This balances the use of Tensor Cores, multi-function units, and TMA, reducing idle cycles.

2. Intra-warpgroup 2-stage GEMM–softmax pipeline. Even inside a single warpgroup, we can pipeline work across iterations of the attention inner loop so that one WGMMA computes the next QK^T block while a second WGMMA multiplies the previously computed softmax block by V, and the softmax/exponential work for the "next" block runs between these two WGMMA issuances.

Below I focus on the 2-stage pipeline, the cleaner conceptual unit to understand how softmax gets "hidden" under matmuls.

## The 2-stage pipeline: conceptually

Imagine the attention inner loop over key/value blocks indexed by j. In a typical (synchronous) inner loop you do, for each j:

1. GEMM0: S^{(j)} = Q_i K_j^T
2. Softmax (row max, exp, row sum) on S^{(j)} producing scaled \tilde{P}^{(j)}
3. GEMM1: O_i += \tilde{P}^{(j)} V_j

These steps are sequential and force Tensor Cores or the special-function unit to wait for each other. The 2-stage pipeline rearranges the work across iterations so that some steps for iteration j and j+1 overlap:

- Precompute S_cur = Q_i K_0^T (GEMM0 for j=0).
- For j = 1..T_c-2:
  - Issue GEMM0 asynchronously to compute S_next = Q_i K_j^T (do not wait).
  - Ensure V_{j-1} is present; issue GEMM1 asynchronously to compute O_i += \tilde{P}_cur V_{j-1} (do not wait).
  - Wait for the GEMM0 result (S_next) and then run softmax on S_next to get \tilde{P}_next and updated rescaling accumulators.
  - Wait for GEMM1 to finish and then perform rescaling updates on O_i.
  - Move S_next → S_cur and continue.

So at any iteration in steady state you have:

- One WGMMA executing Q_i K_j^T (producing S_next),
- One WGMMA executing \tilde{P}_cur V_{j-1} (consuming the previous softmax result),
- The softmax/exponential computation running on S_next (implemented on scalar/FPU/special-function units).

Because WGMMA matmuls can execute asynchronously, the softmax's special-function work tends to be scheduled while the Tensor Cores are busy on the asynchronous GEMMs. Thus the expensive but low-throughput special-function operations rarely sit on the critical path by themselves.

## Why this actually works on Hopper

Three hardware / software properties make the pipeline practical:

- WGMMA is asynchronous and can source inputs from shared memory. Issued WGMMA calls do not necessarily block the issuing warps until they are needed.
- TMA moves tiles into shared memory asynchronously, so producer warps can stream K/V tiles into SMEM while consumer warps perform compute.
- Warp-specialization enables dedicating some warps to producer roles (TMA and in-kernel transpose for FP8) and others to consumer roles (issuing WGMMA, performing softmax reductions). This reduces scheduling interference and can be tuned for register allocation (e.g., reassigning registers across warpgroups with setmaxnreg).

Combined, these mean you can have matmuls running on Tensor Cores and softmax/exponential work running on multi-function units concurrently, with TMA bringing in the next tiles in the background.

## Ping-pong scheduling across warpgroups

The ping-pong idea lifts overlap to the warpgroup level. Partition the warps of a CTA into two warpgroups and alternate which warpgroup performs GEMMs and which performs softmax+reduction. More concretely:

- Warpgroup A starts executing GEMM for block j while Warpgroup B executes softmax for block j−1 and issues GEMM for block j−1's P V.
- Synchronize at barriers so that the GEMMs of the next warpgroup are scheduled after the current warpgroup's GEMMs, which encourages the softmax of the current warpgroup to execute while the other group's Tensor Cores are active.

This alternating schedule evens out usage across execution units and reduces idle time for Tensor Cores and multi-function units. The paper reports that ping-pong scheduling improved FP16 forward throughput in an example from about 570 TFLOPS to around 620–640 TFLOPS (head dim 128, seqlen 8192) on H100.

## Practical trade-offs and limitations

Pipelining softmax under GEMMs is powerful, but it comes with practical costs you must manage.

- Register pressure. The 2-stage pipeline requires holding intermediate tiles (e.g., S_next) in registers while other work is in flight. That increases register usage by roughly the size of a tile (B_r × B_c × sizeof(float)) per threadblock. Higher register usage reduces occupancy or forces smaller tile sizes. FlashAttention-3 balances pipeline depth and tile sizes empirically; going to a 3-stage pipeline increases register needs further and yields diminishing returns unless you can afford the registers.

- Tile size trade-offs. Larger tiles improve arithmetic intensity for WGMMA but also increase the amount of register buffer you must keep between stages. If registers are the limiting resource, larger tiles can degrade overall throughput by reducing the number of active CTAs. So you must tune B_r and B_c relative to available registers and desired pipeline depth.

- Compiler reordering. The CUDA compiler (nvcc) can reorder instructions, sometimes undermining the intended overlap. In practice FlashAttention-3 examines emitted SASS to verify that the compiler-generated code preserves the desired overlapped structure. In real kernels you may need careful placement of barriers and use of explicit wait/commit semantics to avoid the compiler collapsing the pipeline.

- Cost of special functions remains. The pipeline hides but does not remove softmax cost. If special-function throughput is extremely low relative to matmul (e.g., FP8 doubles matmul throughput), you may need stronger overlapping or smaller softmax tiles to avoid the special functions creeping onto the critical path.

- FP8 and layout constraints. When targeting FP8 Tensor Cores, operand layout restrictions (k-major only for FP8 WGMMA) force in-kernel transposes and register permutations. Those extra steps can be overlapped but add complexity and extra register or instruction overhead.

## Empirical impact (as reported)

FlashAttention-3 combines warp-specialization, ping-pong scheduling, and the intra-warpgroup 2-stage pipeline to significantly raise Tensor Core utilization on H100:

- FP16 forward pass throughput reaches up to 740 TFLOPS (about 75% of the theoretical FP16 WGMMA peak), achieving roughly 1.5–2.0× speedup over FlashAttention-2 in many settings.
- The 2-stage pipelining and warp-specialization alone improved an example FP16 forward run from 570 TFLOPS to ~661 TFLOPS (ablation reported).
- When moving to FP8-enabled Tensor Cores, FP8 FlashAttention-3 approaches ~1.2 PFLOPS for matmul throughput, though FP8 requires extra care (block quantization, incoherent processing, layout transforms).

## Bottom line

Softmax isn't expensive because it has many FLOPs—it's expensive because it uses different, lower-throughput hardware (special-function units and scalar work) that can become the critical path when not overlapped. The 2-stage GEMM–softmax pipeline (combined with warp-specialization and ping-pong scheduling) sidesteps this by letting Tensor Cores do continuous heavy lifting while softmax work happens concurrently. On Hopper-style GPUs with asynchronous Tensor Cores and TMA, this is a practical and effective technique to get much closer to Tensor Core peaks for attention, at the cost of careful register and tile-size tuning and some added implementation complexity.



# FP8, Laid Bare: How FlashAttention-3 Hits Petaflop Speeds Without Losing Its Mind

## TL;DR
FlashAttention-3 brings attention on H100 from tens/hundreds of TFLOPs to close to a petaflop by combining three practical low-level tricks: (1) respect FP8 WGMMA layout constraints (k-major operands), (2) perform in-kernel transposes using LDSM/STSM to avoid extra global-memory work, and (3) reorder and permute register layouts so FP32 accumulators produced by one WGMMA are consumable by the next FP8 WGMMA. To make FP8 usable numerically, FlashAttention-3 also applies block quantization and incoherent processing (cheap random orthogonalization). The result: FP8 forward attention near 1.2 PFLOPs/s on H100 and much lower quantization error than naive FP8.

This post walks through the practical issues and the concrete tricks from the paper so you can reason about implementing or integrating FP8 attention kernels safely and efficiently.

## Why FP8 is attractive and why it's tricky
Hopper-class Tensor Cores support FP8 WGMMA with roughly 2× higher matmul throughput than FP16/BF16. That raw throughput is why FP8 looks irresistible for attention, where the majority of work is GEMMs.

But FP8 WGMMA comes with two important constraints that break naive implementations:

1. Operand layout constraint: the FP8 WGMMA on Hopper accepts only k-major inputs (i.e., contiguous in the inner K dimension for the tiled operand in shared memory). In contrast, many attention tensors are contiguous in the head (d) dimension, not in sequence length, so loaded tiles are not in the required k-major layout.

2. Accumulator/operand layout mismatch: the logical order that the FP32 accumulators are laid out in registers after a WGMMA is not the same register ordering expected by a subsequent WGMMA that consumes those accumulators (when you try to fuse back-to-back WGMMAs inside a kernel). Without transformation, you can't directly feed the accumulator into the next FP8 WGMMA.

These are pure layout and register-format problems — they have nothing to do with math — but they determine whether you can reach FP8 Tensor Core throughput without paying big memory or compute overhead.

## Practical solution 1 — In-kernel transpose with LDSM / STSM (avoid pre-transposes)
Option A: pre-transpose tensors in global memory to match FP8 WGMMA layout. That works but is costly in memory-bound settings (extra kernels, extra HBM traffic), and it's awkward to integrate in general libraries.

Option B (what FlashAttention-3 uses): do a tile-wise in-kernel transpose after loading a tile into SMEM using LDSM/STSM (ldmatrix / stmatrix) warp-level instructions. Why this works well:

- LDSM/STSM act on 128-byte tiles with warp cooperation and are register-efficient.
- You can pack FP8 bytes (two 8-bit entries per 16-bit lane when needed) and execute tile transpose with minimal extra register pressure.
- Because FlashAttention-3 already stages tiles through a circular SMEM buffer and issues loads asynchronously (TMA), the transpose of the next \mathbf{V} tile can be scheduled while Tensor Cores are busy on the current WGMMAs. That hides the transpose latency under matmul work.

Takeaway: do the transpose in shared memory immediately after TMA load and before issuing the FP8 WGMMA. Use LDSM/STSM to keep it efficient and cheap in registers.

## Practical solution 2 — Fix the accumulator-to-operand layout with byte permutes
After a WGMMA produces FP32 accumulators in registers, the register ordering (how threads own the parts of the accumulator) is not necessarily the order that the next WGMMA expects for its operand layout. FlashAttention-3 resolves this with a register-level byte permutation:

- Inspect the register ordering patterns of the FP32 accumulator produced by the first WGMMA (these are predictable and documented in the PTX/SASS patterns).
- Apply inexpensive byte-permute (or shuffle/byte-swap) instructions to reorder the accumulator register sequence into the format expected by the consuming WGMMA.
- Arrange the in-kernel transpose of the \mathbf{V} tile so its row permutation complements the column permutation of \mathbf{P} done by the accumulator permute. That way both sides match up and the second WGMMA computes the correct logical product.

Concrete note from the paper: the register sequence is permuted in blocks (e.g., a pattern like \{d0 d1 d4 d5 d2 d3 d6 d7\} repeated), and that permutation is replicated across the 8-byte granularity used by the instruction. Implementing this with byte permutes avoids expensive inter-thread shuffles.

Takeaway: a small number of register-level permutes makes chaining two FP8 WGMMAs possible without extra memory copies. This unlocks fused FP8 paths and the high Tensor Core throughput.

## Practical solution 3 — Block quantization + incoherent processing (address FP8 accuracy)
Even if you can run FP8 at full speed, quantizing Q/K/V to FP8 naively (per-tensor scaling) has two failure modes in large models: limited mantissa precision (e4m3) and rare large outliers. FlashAttention-3 uses two simple, cheap mitigations that integrate naturally with the block-oriented FlashAttention tiling:

1. Block quantization: quantize per tile (per-block) instead of per tensor. Since FlashAttention naturally operates on blocks (e.g., blocks of size $B_r \times d$ or $B_c \times d$), keep a scale factor per block. This reduces dynamic range loss without extra global-memory passes; you compute a block scale as you prepare the tile (can be fused into other bandwidth-bound ops).

2. Incoherent processing: multiply Q and K by a cheap structured random orthogonal matrix $M$ before quantization so that each entry becomes a random linear combination of the original entries. Because $M$ is orthogonal, $\left(QM\right)\left(KM\right)^\top = Q K^\top$, so attention is mathematically unchanged. Practically, this spreads out outlier energy and reduces quantization error. Use a fast structured transform (Hadamard × random sign diagonals) so the cost is $O(d\log d)$ and can be fused into pre-attention ops (e.g., rotary embeddings). This is the same idea used in recent quantization works and is cheap to apply.

Empirical result from the paper: combining block quantization and incoherent processing makes FP8 FlashAttention-3 about 2.6× more accurate (lower RMSE versus an FP64 reference) than naive per-tensor FP8 attention in outlier-heavy distributions.

## How these low-level tricks fit into the kernel and scheduling model
A few more practical implementation notes that matter for performance on H100:

- Use TMA for asynchronous loads from HBM to SMEM. TMA is fully asynchronous relative to Tensor Cores and allows producer/consumer warp specialization.
- Use warp-specialization (split warps into producer/consumer roles) and a small circular SMEM buffer so loads, in-kernel transposes, and WGMMAs are pipelined. The transpose of the next tile can be scheduled by producer warps while consumer warps run WGMMAs and softmax-related code.
- Overlap non-GEMM softmax work with asynchronous WGMMAs using a 2-stage (or optionally 3-stage) pipeline inside the consumer warpgroup: issue the next Q×K WGMMA (async), then issue the current P×V WGMMA (async), then wait and run softmax on the just-produced S tile while the other warpmmas progress. This is crucial because on Hopper the special-function throughput (exponentials for softmax) is tiny compared to WGMMA FLOPs; overlapping hides that cost.
- Be conscious of register pressure: doing extra stages of pipelining requires storing intermediate S tiles in registers. There’s a trade-off between tile sizes and pipeline depth that must be tuned per kernel.

## Observed outcomes (from the paper)
- FP16 FlashAttention-3 achieves 1.5–2.0× speedup over FlashAttention-2 and reaches up to 740 TFLOPs/s (about 75% utilization on H100).
- FP8 FlashAttention-3 reaches nearly 1.2 PFLOPs/s on H100 in favorable settings.
- With block quantization + incoherent processing, FP8 FlashAttention-3 reduces numerical error by about 2.6× compared to baseline FP8 per-tensor quantized attention (on a synthetic outlier-heavy distribution).

## Practical checklist for implementers
If you want to add FP8 FlashAttention to your stack, here is a boiled-down checklist based on the paper:

1. Implement FP8-capable kernels that:
   - Load tiles via TMA into SMEM.
   - Immediately perform a tile transpose in-kernel using LDSM/STSM to produce k-major layout for FP8 WGMMA.
2. Implement register-level byte permutes to reorder FP32 accumulators produced by a WGMMA into the operand layout expected by the next WGMMA.
3. Use warp-specialization + circular SMEM buffer:
   - Producer warps: TMA load + LDSM/STSM transpose.
   - Consumer warps: asynchronous WGMMA calls + softmax handling.
4. Pipeline GEMMs and softmax (2-stage pipelining) to hide slow special functions under fast Tensor Cores.
5. For accuracy:
   - Apply block-level quantization (one FP8 scale per tile).
   - Optionally apply cheap structured random orthogonal transforms (Hadamard × random signs) to Q and K before quantization and fuse with other pre-attention ops.
6. Tune tile sizes and number of pipeline stages to manage register pressure and hit high SM occupancy.

## Final thoughts
FlashAttention-3 shows that hitting petaflop-class performance on attention is not magical — it's a careful alignment of data layout, asynchronous hardware features, and modest numerical techniques. The key engineering insight is to treat layout and register ordering as first-class citizens in the kernel design: once you can transpose cheaply in SMEM and permute registers cheaply, the FP8 Tensor Core path becomes not only possible but rewarding.

If you care about full-pipeline performance on H100, these are the concrete low-level moves you need to consider. FlashAttention-3 open-sources their implementation, which is a useful reference for those integrating FP8 attention into frameworks and model stacks.



# Accuracy at Low Precision: Block Quantization and Incoherent Processing Explained

Modern GPUs (Hopper/H100 and similar) expose very high FP8 throughput on their Tensor Cores, which makes FP8 an attractive target for speeding up attention-heavy models. But FP8 (e4m3) has only 3 mantissa bits and 4 exponent bits, so naive quantization can produce large numerical errors—especially when the activations contain rare, very large values (outliers). FlashAttention-3 tackles this problem with two practical, low-overhead techniques: block quantization and incoherent processing. Together they reduce FP8 attention error by about 2.6× compared to a standard FP8 baseline that uses per-tensor scaling.

This post walks through why outliers break per-tensor FP8, the intuition behind the two techniques, how they fit naturally into an attention kernel, and practical considerations for fusing them into your model pipeline.

## Why FP8 struggles: the outlier problem

FP8 offers much higher raw GEMM throughput than FP16/BF16, but it has a very limited dynamic range and precision. A common strategy is per-tensor quantization: pick one scale factor \(s\) for an entire tensor \(X\), and quantize via
\[
\hat{X} = \text{round}\!\left(\frac{X}{s}\right)
\]
so the quantized values fit the FP8 format. Per-tensor scaling is simple and cheap, but it fails when a tiny fraction of elements are much larger than the bulk of the tensor (outliers). Those few large elements force the scale \(s\) to be large, which causes the majority of values to be represented with severely reduced precision or to underflow, increasing relative error for normal-magnitude elements and degrading downstream computations like attention softmax.

The attention computation is particularly vulnerable because attention scores depend on inner products of query and key vectors; a few poorly represented components can skew those inner products, hurting the softmax and the final output.

## Block quantization: local scales for local dynamic range

Block quantization mitigates the outlier issue by using a separate scale for each small block of the tensor rather than one scale per entire tensor. In FlashAttention-3, tensors are naturally processed as blocks by the attention tiling scheme, so block quantization fits the algorithmic structure without extra global passes.

Concretely, split a matrix (say \(\mathbf{Q}\), \(\mathbf{K}\), or \(\mathbf{V}\)) into blocks matching the attention kernels’ tile sizes (e.g., query blocks \(B_r \times d\) or key/value blocks \(B_c \times d\)). For each block \(B\) compute a local scale \(s_B\) (for example, based on the block maximum absolute value) and quantize that block independently:
\[
\hat{B} = \text{quantize}_{\text{FP8}}\!\left(\frac{B}{s_B}\right).
\]
Because each block usually contains values of similar magnitude, the local scale can be much smaller than the global scale, allowing FP8 to preserve more significant bits for the majority of entries and reducing quantization error.

Why this is cost-effective in attention:
- The attention algorithm already operates block-wise (FlashAttention-style), so scaling and de-scaling can be performed in the same kernel or fused with a preceding memory-bound operation.
- The per-block scales are small metadata (a scalar per block) and are used immediately when computing scaled inner products or when rescaling accumulation, so they do not add significant memory bandwidth or compute overhead.

Practical tip from FlashAttention-3: block quantization can be fused with a preceding operation that is memory-bandwidth bound—rotation embeddings (rotary) are an example. Because both the rotary transform and block-scaling touch the same data and are bandwidth-limited, doing both in one pass adds negligible overhead.

## Incoherent processing: spread the outliers with orthogonal mixing

Block quantization helps, but it can still be hurt by blocks that themselves contain outliers. Incoherent processing aims to reduce per-block outlier impact by mixing the coordinates of the query and key vectors before quantization in a way that preserves inner products.

The idea is simple and mathematically exact: multiply both \(\mathbf{Q}\) and \(\mathbf{K}\) (on the right) by the same orthogonal matrix \(\mathbf{M}\). Because \(\mathbf{M}\) is orthogonal,
\[
(\mathbf{Q}\mathbf{M})(\mathbf{K}\mathbf{M})^\top = \mathbf{Q}\mathbf{K}^\top,
\]
so the attention logits are unchanged in exact arithmetic. But the entries of \(\mathbf{Q}\mathbf{M}\) and \(\mathbf{K}\mathbf{M}\) are linear combinations of the original coordinates; a single large coordinate in the input gets spread across many coordinates after mixing. That diffusion of magnitude reduces the dynamic range and the likelihood that any one coordinate dominates the block, improving block quantization fidelity.

How to do this cheaply: FlashAttention-3 follows prior works and picks \(\mathbf{M}\) to be a structured orthogonal transform that is cheap to apply, for example a product of:
- diagonal matrices with entries \(\pm 1\) (sign flips), and
- a Hadamard matrix.

A Hadamard-based transform can be implemented in \(O(d \log d)\) time per vector (using the fast Walsh-Hadamard transform) instead of \(O(d^2)\). This makes incoherent processing cheap compared to the \(O(d^2)\) cost of dense linear algebra in attention.

In practice, FlashAttention-3 uses the Hadamard-based mixing and notes that this operation can be fused with other per-token transforms, such as rotary embeddings, so the extra compute is nearly free in a real pipeline.

## Putting them together in the attention kernel

Block quantization and incoherent processing are complementary: mixing reduces the occurrence of extreme per-block outliers, and block quantization then uses local scales to represent the now-more-uniform blocks accurately in FP8.

Where these steps can be performed in a typical attention pipeline:

- Pre-attention fusion point: apply the orthogonal mixing and block quantization immediately after any local, token-wise transforms that already touch the tensor (rotary embedding is explicitly mentioned in FlashAttention-3). Because rotary and the mixing-based Hadamard transform are both linear and memory-bandwidth bound, they can be fused into a single pass that writes out FP8 blocks plus block scales. This amortizes the cost.
- In-kernel transpose/format steps (FP8-specific): FlashAttention-3 performs in-kernel tile transposes (using warp-level matrix load/store primitives) to match FP8 WGMMA layout requirements, and the per-block FP8 data are already in the right block-aligned layout for the GEMMs.
- Dequantization/scaling: when a block is read into shared memory or registers for accumulation, the stored per-block scale is applied to reconstruct the FP8 block to the accumulator’s representation (or to appropriately scale GEMM inputs/outputs), all as part of the fused attention kernel.

Key implementation notes from the paper:
- Block quantization requires maintaining one scalar scale per block; the attention tiling means that scale is available exactly where needed.
- Incoherent processing uses structured orthogonal matrices (Hadamard × random sign flips) so that per-vector cost is \(O(d \log d)\) and can be fused with other pre-attention operations.
- Both techniques were validated to reduce FP8 numerical error: FlashAttention-3 with block quantization and incoherent processing achieves about 2.6× lower RMSE (relative to an FP64 reference) than a baseline FP8 attention implementation that uses per-tensor scaling.

## Intuition with a small example

Imagine a query vector with dimension \(d=8\) where seven coordinates are around 1.0 but one coordinate is 100. With per-tensor scaling, the scale must accommodate the 100, so typical coordinates lose most of their mantissa resolution when mapped into FP8. After multiplying by a Hadamard-style orthogonal matrix, that single large value gets spread across the 8 coordinates, so each mixed coordinate might be around \(100/8 \approx 12.5\) plus contributions from the other coordinates. Now each block has a much smaller dynamic range across its entries and block quantization can pick a scale that preserves more relative detail for the majority of components. Quantization error for most coordinates drops substantially as a result.

## Trade-offs and practical considerations

- Slight extra compute: the Hadamard mixing adds \(O(d \log d)\) work per vector, but this can be fused with existing per-token transforms and is small relative to the GEMM work in attention.
- Extra metadata: block quantization stores one scale per block; this is negligible storage compared to the tensor data and is read/written as part of the fused kernel.
- Layout handling: on Hopper, FP8 WGMMA requires specific k-major layout constraints. FlashAttention-3 performs in-kernel transposes and register permutations to conform to these requirements; those steps are efficient when implemented with warp-level load/store primitives and integrated into the kernel.
- Pipeline fit: both techniques are designed to be fusion-friendly. The paper highlights that the block quantization and Hadamard mixing can be fused with a preceding memory-bound op (rotary), and that in-kernel transposes happen in the producer warpgroup so they can overlap with GEMMs.

## Bottom line

FP8 can deliver very large speedups on modern GPUs, but naive per-tensor quantization can fail in the presence of outliers. FlashAttention-3 reduces FP8 attention error by combining block quantization (per-block scales) with incoherent processing (Hadamard-style orthogonal mixing). These techniques are low-overhead, fuse naturally into attention kernels, and—empirically—reduce FP8 RMSE by around 2.6× compared to a standard per-tensor FP8 baseline while enabling the use of FP8 Tensor Cores for much higher TFLOPs/s.

If you are implementing low-precision attention, consider:
- Quantizing by block to match your kernel’s tiling,
- Using a structured orthogonal mixer (Hadamard × sign flips) before quantization to diffuse outliers,
- Fusing mixing and block scaling with preceding per-token ops to avoid extra bandwidth costs.

These steps give you a practical path to get closer to FP8 performance without sacrificing too much numerical fidelity.



# Reading the Benchmarks: 740 TFLOPs/s, 1.2 PFLOPs/s FP8, and What That Means for You

## TL;DR
FlashAttention-3 (FA3) rethinks the attention kernel to exploit asynchronous hardware (Tensor Cores + TMA) and FP8 Tensor Core support on Hopper (H100). The headline results from the paper:

- FP16 forward performance: 1.5–2.0× faster than FlashAttention-2, reaching up to 740 TFLOPs/s (≈75% of H100 theoretical Tensor FLOPs).
- FP8 forward performance: approaches 1.2 PFLOPs/s on H100.
- Numerical stability: FP8 FA3 with block quantization + incoherent processing reduces FP8 attention error by ~2.6× versus a baseline FP8 attention implementation that uses per-tensor scaling.
- Compared to standard (materialize-intermediates) attention, FA3 can be 3–16× faster depending on sequence length and configuration, and for medium/long sequences it even outperforms a vendor-optimized cuDNN implementation.

Below I unpack what these numbers mean in practice, why FA3 achieves them, and how to think about FP16 vs FP8 choices for long-context workloads.

## Where FlashAttention-3 wins — and why
FA3 gains its speed from three core ideas that are tightly matched to H100-style hardware:

1. Warp-specialized producer-consumer asynchrony
   - On Hopper, both data movement (TMA) and matmul (WGMMA / Tensor Core) are asynchronous units. FA3 splits CTAs into producer and consumer warp groups: producers stream blocks of Q/K/V into shared memory while consumers run the compute kernels. This hides memory latency and keeps Tensor Cores fed.
2. Overlapping softmax with GEMM via intra-CTA pipelining
   - Softmax has relatively few FLOPs but uses special functions (exponential), which on H100 are much lower throughput than Tensor Core matmuls. FA3 pipelines two GEMMs and the softmax across iterations (a 2-stage pipelining, with a possible 3-stage variant), so the exponential and reductions execute while the Tensor Cores are busy on the next block. This increases Tensor Core utilization (e.g., 570 → 620–640 TFLOPs/s in one reported case).
3. Targeted FP8 support with layout fixes and accuracy tricks
   - H100 FP8 WGMMA requires operands be k-major; FA3 uses in-kernel transposes (LDSM / STSM) and register permutations so FP8 Tensor Cores can be used without expensive global-memory transposes. To control FP8 quantization error, FA3 applies block quantization (one scale per block) and incoherent processing (multiply Q and K by a structured random orthogonal transform such as diagonal ±1 times Hadamard) to "spread out" outliers. These preserve correctness of QK^T while dramatically improving per-block quantization error.

Taken together, these make FA3 much closer to the hardware peak than FA2. The paper reports FP16 reaching ~75% utilization on H100 and FP8 approaching ~1.2 PFLOPs/s — showing the advantage of combining asynchrony + FP8.

## How head dimension and causal masking affect performance
Two common variables significantly change throughput and relative advantage:

- Head dimension (per-head hidden size): the paper reports experiments for head dims 64, 128, and 256.
  - Smaller head dims (e.g., 64) have less arithmetic per tile and therefore can be more memory-bound / more sensitive to kernel overheads. For some settings FA3 FP8 was ahead at head dim 64.
  - Larger head dims (128, 256) produce larger GEMMs where the Tensor Cores dominate; here FP16 FA3 consistently shows strong wins. For FP8, FA3 is competitive for many large-sequence cases but can be behind cuDNN in some causal-masked small-sequence settings (this is partly due to FP8 FA3 not having a persistent kernel/load-balancing optimization implemented for benchmarks).
- Causal masking (autoregressive attention) roughly halves the amount of computed entries (triangular attention), so memory/layout and load balancing become more important. FA3 still offers large speedups, but:
  - For small sequence lengths with causal masking, FP8 FA3 can be less favorable against highly-optimized vendor kernels, because the FP8 implementation in the paper lacks a persistent kernel and certain small-seq optimizations. For large sequence lengths (1k+ tokens) FA3 tends to outpace cuDNN in FP16 and be competitive in FP8 on many head-dim choices.

In short: FA3 shines for medium-to-large sequence lengths where the extra arithmetic per block lets the kernel amortize overheads and exploit pipelining. The per-head dimension alters the arithmetic-to-memory ratio; larger head dims generally favor higher Tensor Core utilization and therefore larger absolute gains.

## Throughput, cost, and energy — practical trade-offs for FP16 vs FP8

Throughput: FP8 can deliver nearly 2× raw Tensor Core peak throughput relative to FP16 on Hopper (hence the up-to ~1.2 PFLOPs/s number). FA3’s FP8 path realizes that hardware advantage while maintaining much better numeric behavior than naive per-tensor FP8.

Cost (time/money): if you are optimizing inference latency or cost per token:
- FP8 FA3 can cut runtime significantly on large-scale attention, provided you can accept the engineering work (or adopt the FA3 kernel) to integrate FP8 block quantization and transforms. For throughput-oriented inference (batching many queries), FP8 looks highly attractive.
- For training or sensitive inference workloads where small numeric differences matter, FP16 FA3 delivers large speedups and keeps intermediate softmax in higher precision (FP32 accumulators and FP16 storage where appropriate), which reduces numerical error to parity with FA2.

Energy: energy tracks runtime and utilization. Because FP8 delivers more FLOPs per cycle on Tensor Cores, a high-utilization FP8 kernel can be more energy-efficient per token if accuracy is sufficient. But be wary: if FP8 causes more numerical instability and you compensate with repeated computations or larger models, the energy advantage disappears. FA3 mitigates this by improving FP8 accuracy via block quantization and incoherent processing.

Numerical safety: The paper shows FP16 FA3 keeps the same numerical error as FA2 (both better than the naive standard implementation because FA variants keep softmax intermediates in higher precision). For FP8, FA3’s block-quantization + incoherent processing reduces RMSE by ~2.6× versus a per-tensor FP8 baseline under a synthetic outlier-heavy distribution. That means FP8 FA3 is considerably more robust to real LLM outliers than simple FP8 schemes.

When to pick which:
- If you need the safest numeric behavior and large gains vs prior software, choose FP16 FA3. It gives substantial speedups (1.5–2× vs FA2) while matching FA2 numerical behavior.
- If you prioritize maximum throughput/cost efficiency and can accept more numeric engineering (or you validate accuracy on your model/task), FP8 FA3 is compelling — especially for long contexts and large head dims where peak Tensor Core throughput matters.
- For short sequences or autoregressive small-batch scenarios, evaluate empirically: vendor kernels (cuDNN) or FA2/FA3 FP16 with persistent-kernel strategies may be better. The paper notes FP8 FA3 lacks a persistent kernel in the benchmarks, which explains some small-sequence regressions.

## Practical caveats and limitations highlighted in the paper
- FP8 FA3 in the paper does not use a persistent kernel and persistent-load balancing for the benchmarks; that limits small-sequence / causal-case performance. The FP16 implementation does have a persistent kernel and load balancing.
- Using FP8 requires additional engineering: in-kernel transposes, register permutations, and the quantization transforms (block scales and incoherent transforms). The paper details how to perform these efficiently (LDSM/STSM, byte permutes, Hadamard-based incoherent transforms fused with rotary embedding), but integrating into production frameworks may need careful implementation.
- Numerical validation in the paper used synthetic data with outliers to stress-test quantization. Actual model behavior should be validated end-to-end; FP8 benefits can vary by architecture and distribution of activations.

## Bottom line
FlashAttention-3 is an important engineering step: by aligning algorithm design with Hopper’s asynchronous Tensor Core and TMA capabilities and by building a careful FP8 path, the authors push attention kernels close to the machine’s theoretical throughput. For long-context workloads and large heads, FA3 unlocks major practical throughput gains: FP16 gives reliable 1.5–2× speedups with solid numeric behavior, while FP8 can bring nearly double the FLOP throughput (approaching 1.2 PFLOPs/s) if you adopt block quantization and incoherent preprocessing to control error.

If you run large long-context inference or training, FA3 is worth trying: FP16 FA3 is the lower-risk path for big speedups, while FP8 FA3 is the higher-reward choice when you can validate accuracy for your model and pipeline.



# From FlashAttention-2 to -3: A Migration Guide for Practitioners

FlashAttention-3 (FA3) is the next step in the FlashAttention line: it rethinks the kernel and dataflow to exploit Hopper-class GPUs' asynchrony and FP8 Tensor Cores. If you already use FlashAttention-2 (FA2) or other fused attention kernels, this guide explains when and how to adopt FA3, what practical trade-offs to expect (performance and numeric), and what implementation details to watch for when integrating FA3 into PyTorch / Hugging Face stacks.

## TL;DR recommendations

- If you want the most robust drop-in improvement on Hopper H100 GPUs, start with FA3 in FP16: expect about 1.5–2.0× speedup over FA2 in the forward pass and 1.5–1.75× in the backward pass (paper benchmarks). FA3 FP16 reaches up to ~740 TFLOPs/s (≈75% utilization).
- FP8 in FA3 can deliver substantially higher peak throughput (paper reports approaching 1.2 PFLOPs/s) but requires extra attention to accuracy and layout constraints. Use FP8 when you need maximum inference throughput and you can tolerate extra engineering (quantization and layout handling) or when your workflow already includes careful FP8 validation.
- For long sequences and larger head dimensions FA3's gains are strongest; for small sequence lengths or some causal-mask configurations FP8 kernels may not outperform vendor kernels without extra tuning.
- FA3 is open-source (see the paper link / repo), and the authors plan integration with PyTorch and Hugging Face. Expect to integrate via the provided library / kernel and follow standard dispatcher or custom operator paths for model runtimes.

Below I unpack the details you should know before switching production or experimentation pipelines to FA3.

## What changed in FA3 (practical view)

FA3 combines three main ideas that affect performance and integration:

1. Producer-consumer warp-specialization + ping-pong scheduling: producer warps perform asynchronous TMA loads to shared memory while consumer warps run Tensor Core GEMMs. This reduces stalls and increases utilization on Hopper GPUs by overlapping data movement and matmuls.
2. Intra-warpgroup GEMM–softmax pipelining: FA3 breaks some of the sequential dependence between the two GEMMs and the softmax per key block by keeping a small pipeline across iterations (2-stage, optionally deeper). This overlaps expensive Tensor Core work with lower-throughput softmax/exponential operations.
3. FP8 support with layout-aware in-kernel transpose and accuracy techniques: to use FP8 Tensor Cores FA3 performs in-kernel transposes (LDSM/STSM patterns) to satisfy the FP8 k-major layout constraint and uses block quantization plus "incoherent" preconditioning (diagonal ±1 and Hadamard-style transforms) to reduce quantization error.

These changes are the reason FA3 attains much higher TFLOPs/s on Hopper compared to FA2.

## Supported settings and performance characteristics

- Hardware: FA3 is designed for GPUs with asynchronous Tensor Cores and TMA (paper focuses on NVIDIA Hopper H100). The algorithm assumes the availability of asynchronous WGMMA/TMA primitives and FP8 Tensor Core support.
- Precision: FA3 supports FP16 (safe and high-performing) and FP8. In FP16 it preserves numerical behavior comparable to FA2 (intermediate softmax scaling kept in FP32). FP8 requires block quantization and incoherent processing to keep accuracy acceptable.
- Operations: FA3 implements exact attention (no kernel-level approximation) and supports causal and non-causal attention and multi-head variants (including multi-query / grouped query) via adjusted indexing.
- Sequence lengths and head dimensions: FA3 shows larger speedups for medium-to-long sequences (1k tokens and up). The paper reports FA3 outperforming FA2 by 1.5–2× in forward pass and even beating cuDNN for medium/long sequences in many configurations.
  - Notable head-dimension observations from the paper: for large sequence lengths FA3 FP16 generally wins. For FP8, the relative position depends on head dimension:
    - head dim 64: FP8 FA3 is ahead of the competing implementation in many cases.
    - head dim 128 and 256: FP8 FA3 is roughly at par without causal masking, and can be behind when causal masking is enabled (paper footnote).
- Backward pass: FA3 accelerates the backward pass as well (paper reports 1.5–1.75× improvements versus FA2), but FP8 is typically focused on inference; for training FP16 remains the safer default.

## When to prefer FP16 vs FP8

Use FP16 when:
- You want a robust, low-hassle upgrade from FA2 for both training and inference.
- Your workloads require stable numerical fidelity and backward pass correctness (FA3 FP16 matches FA2 numerical error and keeps softmax/rescaling in higher precision).
- Sequence lengths are small-to-medium and you want consistent performance across causal and non-causal masks.

Consider FP8 when:
- You need the absolute highest inference throughput and can validate model behavior under FP8 numerics.
- Your pipeline can reliably incorporate the block quantization and incoherent processing steps (these are central to FA3’s FP8 accuracy improvement).
- You target large sequence lengths and head dims where FP8’s higher matmul throughput is beneficial.
- You accept that FP8 FA3 may need additional tuning for small sequence lengths and for causal masks (FP8 FA3 lacked a persistent kernel in the reported experiments, which affected small-seqlen and causal-mask performance).

Numerical trade-offs:
- FP16 FA3 keeps intermediate softmax computations in FP32 and matches FA2's numerical error behavior (paper reports FA2/FA3 FP16 having ≈1.7× lower RMSE than a standard attention implementation that materializes intermediates).
- Out-of-the-box per-tensor FP8 quantization performs poorly in presence of outliers. FA3’s two measures—block quantization and incoherent processing (randomized orthogonal-ish preconditioning implemented via cheap diagonal ±1 × Hadamard-like transforms)—reduce FP8 attention RMSE by up to 2.6× compared to baseline per-tensor FP8 attention.

Bottom line: FP16 = safer, simpler, very good speedups. FP8 = bigger wins possible but requires careful quantization/validation.

## What to watch out for (pitfalls and implementation caveats)

1. Layout constraints for FP8 GEMMs (k-major requirement)
   - On Hopper, FP8 WGMMA accepts only k-major input layout for operands in shared memory. FA3 solves this by doing an in-kernel transpose of V tiles (using LDSM/STSM style instructions) so that loaded tiles meet the k-major constraint without a separate global-memory transpose.
   - Practical implication: FP8 integration is more invasive than FP16. You must ensure the kernel or pre-processing step produces the required memory layout for FP8 Tensor Cores.

2. Pipeline depth vs register pressure
   - FA3’s overlapping (2-stage and optionally 3-stage) requires holding extra intermediate tiles in registers. Larger block sizes and deeper pipelines increase register usage and can cause spilling; tuning block sizes B_r/B_c and pipeline depth is necessary.
   - If you see regressions, profile register usage (and occupancy) and trade off tile sizes for pipeline depth.

3. Small sequence lengths and causal masks
   - FA3's FP16 persistent kernel yields strong performance for many lengths, but FP8 FA3 (as reported) did not include a persistent kernel or the same load-balancing optimizations and can be slower for small sequences or when causal masking halves the computation by design.
   - Causal masks change the FLOP pattern (roughly half the computed scores), which interacts with the scheduling and tile choices; test the causal-mask case separately.

4. Compiler reordering and instruction scheduling
   - FA3 relies on careful overlap of asynchronous WGMMAs and softmax computations. The actual instruction stream may be reorganized by the compiler (NVCC), so vendor-specific codegen and careful SASS inspection (or direct assembly-level control) can be necessary to ensure the desired overlapped ordering.

5. FP8 accuracy and outliers
   - Per-tensor quantization is fragile with outliers. FA3’s recommended mitigations are block quantization (one scale per block) and incoherent preprocessing (random orthogonal-like transform to spread out outliers). These can be fused with upstream ops (e.g., rotary embeddings) to avoid extra passes, but you must validate the effect on model outputs.

6. Persistent kernel considerations
   - The paper notes that their FP16 FA3 has a persistent kernel and load balancing strategy, while FP8 FA3 did not. This explains why FP8 FA3 can underperform for small seqlen/causal cases. Expect future FP8 kernels or user-tuning to address this.

## Integration notes: PyTorch and Hugging Face

- Source and integration path: FA3 is open-sourced (see the repository referenced in the paper). The authors plan to integrate FA3 into PyTorch and Hugging Face libraries to make adoption easier.
- Integration approaches:
  - Use the provided FA3 operator / kernel library as a drop-in attention operator and register it with your framework’s custom op dispatcher. This keeps your model code unchanged but substitutes the attention kernel at runtime.
  - For Hugging Face models, replacement is typically done by switching the attention kernel implementation (for example, via an optional backend or a custom runtime engine). Expect to follow the same pattern used for FA2 integration: register FA3 kernels and update the attention module to call the fused operator.
  - If you want to fuse upstream ops (rotary embeddings, block quantization, incoherent transform) to avoid extra memory passes, you will need to adapt model pre-processing or patch the attention module to perform those fused transforms. The paper notes these fusions are possible and often free in compute-bound regimes.
- Testing and validation:
  - Validate numerical closeness to an FP64 reference, especially when using FP8. The paper uses RMSE against FP64 on synthetic inputs with simulated outliers; you should do the same on representative model inputs and downstream tasks.
  - Benchmark on target hardware (H100 or other Hopper-like GPUs) and test both causal and non-causal paths, multiple head dims, and sequence lengths you care about.
- Practical deployment tips:
  - Start by switching only FP16 kernels for FA3 and verify speedups and numerical behavior. This is the lowest-risk path.
  - If moving to FP8 for inference, implement FA3’s block quantization and incoherent processing and fuse them into the preprocessing graph where possible to avoid extra memory-bound kernels.
  - Tune block sizes (B_r, B_c) and pipeline depth for your specific sequence length and head dimension. The paper’s algorithm is sensitive to register pressure and occupancy.

## Tuning knobs to profile / experiment with

- Block sizes for queries and keys/values: B_r and B_c (FA3 operates on blocks; tuning affects register use and occupancy).
- Pipeline stages: 2-stage vs 3-stage overlapping (3-stage may give better overlap at the cost of registers).
- Warp partitioning: number of producer vs consumer warps, which affects register allocation per role.
- FP8 preprocessing: block quantization block size and choice of incoherent transform (Hadamard + diagonal ±1 is the recommended low-cost choice).
- Persistent kernel enablement (FP16 kernel has one in the experiments; ensure kernel parameters enable persistent style scheduling if available).

## Validation data and numbers you can cite when discussing FA3

- Forward pass speedup vs FA2: 1.5–2.0× on H100 (varies with sequence length / head dim), FP16 up to ~740 TFLOPs/s (≈75% utilization of H100 Tensor Core peak).
- FP8 peak: experiments in paper report close to 1.2 PFLOPs/s.
- Backward pass: 1.5–1.75× speedup vs FA2.
- Numerical error: FA3 FP16 matches FA2 and is ≈1.7× lower RMSE vs a standard attention implementation that materializes intermediates (in the synthetic outlier test). FA3 FP8 with block quantization + incoherent processing reduced FP8 numerical error by ≈2.6× compared to baseline per-tensor FP8 attention in the same test.
- Causal-mask behavior: FP8 FA3 can be behind optimized vendor kernels for some head dims with causal masks (paper notes head dim 128 and 256 as examples where FP8 is at par or behind when causal masking is applied).

## Final checklist before migrating

- Verify your target GPU supports asynchronous Tensor Cores, TMA, and FP8 Tensor Core instructions (paper focused on Hopper/H100).
- Start with FA3 FP16: update runtime / custom op registry to call FA3’s FP16 kernel and run correctness/unit tests.
- Benchmark representative workloads: sequence lengths, head dims, batch sizes, both causal and non-causal.
- If moving to FP8:
  - Implement FA3’s block quantization and incoherent transform (or use the FA3 library’s implementation if provided).
  - Ensure in-kernel transpose / memory layout handling for V tiles (or provide pre-transposed V in memory if you prefer a pre-processing step).
  - Run strict numerical validation vs FP32/FP64 references for representative inputs.
- Tune block sizes and pipeline depth to match occupancy and avoid register spilling.

# Beyond Hopper: The Future of Asynchronous, Low-Precision Attention

FlashAttention-3 shows a clear direction: to get real-world, order-of-magnitude wins on attention we must design algorithms that match the microarchitecture of modern accelerators. It does that by explicitly embracing two hardware trends—asynchrony (separate units for fast matmul and for data movement) and richer low-precision formats (FP8 on Hopper)—and by engineering attention kernels around them. This blog unpacks how those ideas generalize to upcoming hardware (e.g., FP4 on Blackwell), what they mean for long-context and multimodal LLMs, and why an open-source ecosystem is essential to keep kernels in step with hardware evolution.

## What FlashAttention-3 gets right (recap)

FlashAttention-3 combines three concrete techniques that together boost throughput and preserve accuracy:

- Warp-specialized producer–consumer asynchrony. Warps are split into producers (issue TMA loads, do in-kernel transposes) and consumers (drive asynchronous Tensor Core GEMMs via WGMMA and run the softmax path). This software pipelining hides memory and instruction latencies by using distinct hardware units in parallel.

- Interleaved (pipelined) GEMM and softmax. By overlapping the asynchronous GEMMs with the relatively low-throughput softmax work (exponentials, reductions), FlashAttention-3 keeps Tensor Cores busy while the multi-function units compute special functions. The paper demonstrates a practical 2-stage (and conceptually 3-stage) pipelining that increases utilization on H100 from ~35% to as high as 75%.

- Low-precision-aware layout and quantization. For FP8 WGMMA on Hopper, operand layout constraints and accumulator formats require in-kernel transposes, register permutations, and careful packing. To maintain numerical fidelity, FlashAttention-3 uses block quantization (per-block scaling) and incoherent processing (Hadamard-based random orthogonal transforms fused into pre-processing) to reduce quantization error, reporting a 2.6× reduction in error relative to a naïve per-tensor FP8 baseline.

These three ideas are not accidental; they are engineered around two persistent hardware properties: (1) increasingly specialized, asynchronous units (separate engines for memory, matmul, and special functions) and (2) progressively lower-precision formats exposed to software.

## How these ideas generalize to future accelerators (e.g., FP4 on Blackwell)

The paper is explicit that FlashAttention-3 is designed for Hopper but that the algorithmic principles transfer to any accelerator with asynchronous execution and low-precision support. Concretely:

- Asynchrony is a hardware abstraction, not an NVIDIA-specific trick. Any accelerator that exposes fast, independently schedulable matrix-multiply engines and DMA-like data movers benefits from warp-/lane-/threadgroup-specialization and software pipelining. The producer–consumer division and circular shared-memory buffering pattern will still be effective for hiding latencies.

- As low-precision formats proliferate (FP8 today, FP4 on upcoming hardware like Blackwell), the same two concerns recur: (a) operand/accumulator layout constraints for the accelerator's low-precision GEMM primitives, and (b) increased quantization error and sensitivity to outliers. FlashAttention-3’s two-part solution—layout-aware in-kernel transforms + accuracy-preserving quantization techniques—maps naturally to FP4 as well. For FP4 we will see even tighter dynamic range and precision limits, making block-level scaling and incoherent mixing (Hadamard-like transforms or other cheap orthogonalizers) even more important.

- Practical engineering constraints scale similarly. Register pressure, compiler instruction reordering, and the need to tune pipeline depth versus tile size are hardware-agnostic trade-offs. For FP4, the temptation will be to push even smaller tiles or deeper pipelines to fully saturate the ultra-high throughput matmul units, but that increases register and scheduling complexity. The same profiling-driven balancing act used on Hopper applies.

Caveats grounded in the paper: The FlashAttention-3 implementation must reconcile low-precision GEMM input layout constraints and FP32 accumulator layouts (the paper demonstrates byte-permute and in-kernel transpose strategies). Any future accelerator will have its own layout and instruction-level idiosyncrasies; the kernel must be adapted to those. The core idea—co-design kernels around asynchronous units and low-precision constraints—remains portable.

## Implications for long-context LLMs and multimodal models

Attention is the bottleneck for long-context and multimodal workloads because the quadratic attention S = α Q K^T grows as O(N^2). FlashAttention-3's improvements matter directly:

- Throughput and scale: By raising Tensor Core utilization (to 75% of theoretical on H100 for FP16, and approaching 1.2 PFLOPs/s for FP8 in aggregate), FlashAttention-3 makes larger sequence lengths practical for both training and inference. That reduces the per-token latency/cost for processing very long contexts (documents, codebases, long audio/video frames), or large multi-modal inputs that concatenate many modalities.

- Accuracy at low precision: The paper shows that carefully designed FP8 attention—using block quantization and incoherent processing—can dramatically reduce FP8 error relative to per-tensor quantization. This matters because long contexts and multimodal inputs often have heterogeneous distributions and outliers (a few very large features among many small ones). Per-block scaling and randomized orthogonal mixing reduce quantization-induced bias and variance in attention scores, which helps keep model behavior stable when moving to lower precision.

- Practical engineering for causal / streaming settings: FlashAttention-3 addresses both non-causal and causal attention (with some caveats for small sequence lengths and FP8 persistent kernels). For long-context LLMs used in streaming or agent applications, attention kernels that can sustain high throughput with causal masks are crucial. The paper indicates FP16 FlashAttention-3 retains strong performance in causal settings; FP8 needs additional work (e.g., persistent kernels) to match FP16 for small causal windows—this is an area for focused engineering as hardware evolves.

In short: better attention kernels let model designers choose larger contexts or richer modalities for the same compute budget, and low-precision with careful quantization preserves accuracy enough to make that practical.

## What to expect (and prepare for) as hardware evolves

- Increasingly aggressive instruction-level constraints. Hopper required careful handling of k-major versus mn-major layouts and accumulator formats for FP8 WGMMA. Future accelerators (FP4/FP3) will likely introduce similarly strict operand layout and accumulator conventions; kernels must be ready to implement compact in-kernel layout transforms (transposes, permutes) and register rearrangements efficiently.

- Sharper accuracy trade-offs at smaller bit widths. FP4 will reduce representational range and mantissa bits further. The paper’s block quantization and incoherent processing will be even more necessary; we should expect to extend those ideas (e.g., adaptive block sizes, hybrid per-block/per-channel scaling) when moving to FP4.

- More opportunities for asynchrony exploitation. As hardware becomes more heterogeneous (dedicated units for reshuffling, compression, special functions), there will be more scope to split warps/lanes into specialized roles and to pipeline operations across more stages. But that increases complexity: register pressure, synchronization overheads, and susceptibility to compiler reordering become more delicate. Tooling and low-level primitives (like setmaxnreg in Hopper) that allow dynamic register allocation and explicit control over scheduling will matter more.

## Why open-source kernels matter

The paper emphasizes that FlashAttention-3 is open-sourced with a permissive license and targeted to integrate with PyTorch and Hugging Face. That is not a luxury—it is necessary for rapid progress:

- Hardware moves fast. Public kernels let the community adapt and tune to new devices and instruction sets weeks or months sooner than vendor integration cycles. The practical adaptations in the paper (in-kernel transpose using LDSM/STSM, byte permutes to align accumulators, producer–consumer warp splits) are engineering details that require hands-on iteration.

- Research reproducibility and robustness. Low-precision techniques interact with model training dynamics. Open kernels let researchers measure numerical error, debias quantization strategies, and validate that techniques like block quantization or incoherent transforms actually preserve model behavior across many model families and data distributions.

- Composability and ecosystem integration. Real models use rotary embeddings, mixing layers, and fused transforms. FlashAttention-3 shows how some transforms (Hadamard/orthogonal mixing, rotary embeddings) can be fused into preprocessing steps to avoid extra memory traffic. Open-source kernels let library and framework authors adopt such fusions consistently.

- Diverse hardware backends. As accelerators diversify (NVIDIA, AMD, Apple, bespoke AI chips), portable algorithmic principles implemented in open codebases serve as a starting point for backend-specific optimizations. The kernel-level patterns from FlashAttention-3—circular SMEM buffers, warp specialization, pipelined GEMM-softmax, block quantization—are a portable pattern language for attention kernels.

## Practical takeaways for implementers

- Profile don’t assume. The balance between tile size, pipeline depth, and register use is device-specific. Start from the FlashAttention-3 recipe but tune with device-level profilers.

- Make quantization local. Per-block scaling is cheap in a blockwise streaming kernel and pays off for accuracy, especially with outliers.

- Fuse where possible. Fuse orthogonal transforms or rotary embeddings into the quantization stages to avoid extra memory-bound steps.

- Expect compiler quirks. NVCC and other compilers can reorder instructions in ways that break intended pipelining. Inspect generated assembly and use explicit synchronization/order primitives exposed by the backend.

- Keep kernels open. Public implementations accelerate adoption, debugging across model families, and the necessary iteration as hardware evolves.

## Closing

FlashAttention-3 is a concrete demonstration that algorithm and microarchitecture must be co-designed for state-of-the-art attention. The principles it embodies—exploit asynchrony via warp (or lane) specialization, hide non-matrix work under asynchronous GEMMs, and systematically control quantization error—will be applicable and increasingly necessary as accelerators move to FP4 and beyond. To unlock long-context and rich multimodal models affordably, we need both low-level engineering (efficient, hardware-aware kernels) and an open-source ecosystem that can adapt kernels quickly as the hardware landscape shifts. The future of attention will be written as much in instruction manuals and PTX/SASS snippets as in model architectures.
