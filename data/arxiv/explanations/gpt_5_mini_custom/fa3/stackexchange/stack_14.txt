\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What exactly is "k-major" for FP8 WGMMA on Hopper, and how do the attention GEMMs map to that constraint?
Question:
The paper states that FP8 WGMMA only supports k-major operands in SMEM. For a GEMM computing $A (M\times K) \times B^\top (N\times K)$, could someone define precisely what "k-major" means in terms of strides and layout? In the attention forward pass: (1) for $\mathbf{Q}\mathbf{K}^\top$ which operand(s) must be k-major, and (2) for $\mathbf{P}\mathbf{V}$, which operand must be k-major? How does this requirement lead to the need to transpose $\mathbf{V}$ tiles in-kernel if inputs are originally contiguous in the head dimension?
Answer:
Short answer: "$k$-major" means "contiguous along the inner ($K$) index of the GEMM". Concretely, for an $M\times K$ matrix stored in row-major order this is true: successive memory addresses change by one element when you move along the $K$ index, and the stride between successive $M$-rows equals $K\times\text{sizeof(elem)}$. FP8 WGMMA on Hopper accepts only operands that are $k$-major when they live in SMEM, so any tile you place into SMEM that will be used by an FP8 WGMMA must be laid out so the $K$ dimension is the contiguous (fastest) stride. Applied to attention:

1) For the SS-GEMM that computes $\mathbf{Q}\mathbf{K}^\top$ (a tile-based GEMM with operands of shapes $A:(B_r\times d)$ and $B:(B_c\times d)$ used as $A\times B^\top$): if both operands are sourced from SMEM (the SS case in the paper) then the SMEM tiles for both $\mathbf{Q}$ and $\mathbf{K}$ must be $k$-major — i.e. contiguous along the head dimension $d$ ($K = d$ in that GEMM). If one operand is in registers (an RS or SR GEMM variant), the restriction only applies to the operand that actually lives in SMEM.

2) For the RS-GEMM that computes $\mathbf{P}\mathbf{V}$ (logical shapes: $\mathbf{P}$ is $B_r\times B_c$ and a $\mathbf{V}$ tile is $B_c\times d$, giving output $B_r\times d$): the $\mathbf{V}$ tile that is loaded into SMEM must be $k$-major with respect to this GEMM’s inner dimension ($K = B_c$). In other words, the copy of $\mathbf{V}$ residing in shared memory must be contiguous along the sequence-length / key-block axis (the $B_c$ axis), not along the head axis.

Why that forces an in-kernel transpose of V tiles when inputs are head-contiguous: typical layouts produced by transformer code store tensors contiguous in the head dimension (i.e., the head/channel index $d$ is the fastest-moving dimension). For the $\mathbf{P}\mathbf{V}$ GEMM the WGMMA expects the SMEM operand corresponding to $\mathbf{V}$ to be contiguous in the inner (sequence) axis $B_c$. TMA loads cannot change which logical axis is contiguous — they move a contiguous region from global memory to SMEM preserving strides — so if $\mathbf{V}$ in global memory is contiguous in head (not in sequence), a direct TMA into SMEM will leave the SMEM tile in the wrong "$$k$$-major" orientation. Therefore you must either (a) pre-transpose $\mathbf{V}$ in global memory so the sequence axis becomes contiguous there, or (b) transpose each tile after loading it into SMEM (in-kernel) so the SMEM layout becomes $k$-major. The paper chooses (b) and implements it efficiently using warp-level matrix load/store (LDSM/STSM) and small register permutations so the tile written into SMEM is contiguous along the GEMM inner ($K$) axis that FP8 WGMMA requires.

A few intuitive wrap-ups and practical notes from the paper: "$k$-major" is purely a stride/layout constraint (which axis is fastest). FP16 WGMMA is flexible (accepts $mn$-major or $k$-major), but FP8 WGMMA is strict and demands $k$-major in SMEM — which is why attention’s natural head-contiguous layout conflicts with the required SMEM layout for the $\mathbf{P}\mathbf{V}$ GEMM and triggers the need for the in-kernel transpose of V tiles (done in producer warps with LDSM/STSM so it can be overlapped with other work).
