# What 1‑Bit LLMs Are and Why They Matter

Large language models (LLMs) dominate AI nowadays, but training and deploying them is increasingly costly. One of the biggest drivers of that cost is that every single weight in a transformer lives in a 16‑bit floating‑point format (FP16 or BF16). After all, we think more bits gives more expressive power, so we keep throwing full‑precision numbers at every layer.  

Recent research is collapsing that assumption. By pushing the precision *down* to a single bit – or, more precisely, two integer values plus a zero – we can keep performance while slashing memory, latency, and energy use. The paper *The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits* shows that a carefully‑designed ternary‑weight model called **BitNet b1.58** not only matches full‑precision LLMs on perplexity and zero‑shot benchmarks, it also outperforms them as we scale up.

Below we explain what a 1‑bit LLM really means, why the ternary \{-1, 0, +1\} weighting is powerful, and how BitNet b1.58 demonstrates that half as many bits can still hit the mark.

---

## From FP16 to a Single Ternary Value

### The Quantization Idea

A classic approach to reduce model size is **post‑training quantization**, where you first train a full‑precision model and then round its weights to lower bits for inference. That technique works but leaves performance gaps because the network has already converged to a FP32 optimum.

Instead of quantizing after the fact, BitNet trains directly with **ternary weights**. The only allowed values are:

- \(-1\): an active negative influence
- \(0\): “turn off” this connection
- \(+1\): an active positive influence

That makes each weight just **one bit of information** – roughly the sign of the original weight – plus one extra unary symbol (the zero). In binary terms that’s **1.58 bits** per weight: \(\log_2(3) \approx 1.58\).

### Why Zero Is Worthy

Adding the zero value gives *feature filtering*. In standard binary (\{-1,+1\}) networks all connections are engaged; with zero you can prune any weight that contributes little during training. Training from scratch with ternary weights encourages the model to *sparsify* itself: if a channel isn’t needed for the task it simply drops out (weight = 0). This extra flexibility is key to BItNet’s competitive performance.

---

## How BitNet b1.58 Is Built

| Component | Full‑Precision Counterpart | What BitNet does |
|-----------|----------------------------|------------------|
| Linear layers | `torch.nn.Linear` | Replaced by `BitLinear`: matrix multiplication becomes **integer addition** using ternary weights |
| Activation scaling | No scaling before nonlinearity | Uses an “absmean” quantizer: scale by average absolute value then round to \{-1,0,+1\} |
| Norm & MLP style | LayerNorm & GELU | Uses RMSNorm & SwiGLU – the same choices used in LLaMA – but drops biases entirely |
| Data path | FP16/ BF16 activations | Uses 8‑bit activations; keeps full precision only for embeddings |

Training starts from scratch with the same hyperparameters used for LLaMA models (e.g., learning rate decay schedule), at **100 billion tokens on RedPajama**. Because weights are constrained during backpropagation as well, gradients have to be projected back into ternary space; all of this happens efficiently on GPUs thanks to custom kernels.

---

## Performance vs. Full Precision

### Perplexity Gains

At **3 B parameters**, BitNet b1.58 achieves perplexity identical to an FP16 LLaMA baseline; at 3.9 B it even beats it slightly. This equivalence grows with model size: by 13B bitnet outperforms FP16 3B in both perplexity and downstream tests.

### Zero‑Shot Tasks

On a suite of standard benchmarks (ARC-Easy/Challenge, Hellaswag, Winogrande, PIQA, OpenbookQA, BoolQ), zero‑shot accuracy starts matching FP16 at 3 B and surpasses it in higher dimensions:

| Model Size | Perplexity (WikiText2) | Winogrande Acc | PIQA Acc |
|------------|------------------------|----------------|----------|
| 3 B FP16   | ~9.30                  | ~70%           | ~83%     |
| 3 B b1.58  | ~9.28                  | ~71%           | ~84%     |
| 3.9 B b1.58 | ~9.24                 | ~73%           | ~85%     |

(Exact numbers omitted here for brevity.)

The narrowing performance gap means **half as many bits do not hurt accuracy**.

### Speed & Memory Savings

Because matrix multiplication now uses integer adders instead of floating multipliers:

- **Latency** drops by **2–4×** depending on model size.
- **GPU memory** shrinks by **3–4×**.
- **Energy per token** falls by about **70×** for arithmetic operations alone on a modern 7 nm GPU.

For example, a 70B BitNet b1.58 runs approximately four times faster than its FP16 counterpart while storing only one quarter of the parameters in-place.

---

## Scaling Laws and Practical Elasticity

BitNet’s results suggest a new “scaling law”:  
- A **13B b1.58 model** delivers fewer latency/bandwidth casualties than an **FP16 3B model**.
- A **30B b1.58 model** surpasses an FP16 7B model in efficiency.
- A **70B b1.58 model** outpaces an FP16 13B in both speed and memory.

In practice this means you can deploy larger models on less hardware— or achieve equivalent performance within tighter budgets— simply by switching to ternary weights.

---

## Extra Benefits Beyond Baselines

### Mixture‐of‐Experts (MoE)

MoE splits computation across several “expert” modules; they shine when FLOPs can be saved but suffer from large memory footprints and inter‑chip traffic for activations. With BitNet’s weights already *tiny*, MoE pipelines become cheaper: fewer activation bits cross network links and entire expert collections can fit on single chips.

### Long Sequences

Large KV caches double memory usage linearly with context length. By halving activations from FP16 → INT8 (and potentially down to INT4), BitNet effectively increases reachable context length without increasing energy or memory consumption—critical for real‐world chat scenarios or code completion over long files.

### Edge & Mobile Feasibility

Memory towers far exceed what most CPUs or edge GPUs hold today—a bottleneck that also hurts energy budgets (non‑volatile storage hops add latency). Ternary weights erase that barrier: you can move thousands of millions of parameters onto mobile chips without extra DRAM traffic or power draw.

---

## New Hardware Opportunities

If future systems jointly adopt heavy sparsification and integer math:
- Custom “Language Processing Units” (LPUs) could run entire ternary models at gigahertz rates,
- A small SRAM footprint would allow loading massive optimizer state locally,
- Energy efficiency would make data centers greener while enabling devices like phones or smart speakers to host sophisticated AI locally.

Companies like Groq have already shown one such path; BitNet encourages wider adoption beyond inference engines into training workloads too—thanks to its stable low‑bit formulation during gradient descent.

---

## Takeaway

*Half as many bits can still completely deliver state‑of‑the‑art language understanding.*  
BitNet b1.58 proves that with clever quantization design—and training directly from scratch with ternary weights—you get:

- Parity or better performance compared to full FP16 models,
- Greatly reduced memory bandwidth,
- Drastic latency drops,
- Near‐zero energy cost for matrix multiplication,
- Unlocking new routes for MoE, long sequences, edge deployment, and specialized hardware.

As any AI engineer will agree: if you’re willing to give up even one bit per weight you can free up resources that were previously locked behind high precision arithmetic—without turning off the quality button."



# From Floating‑Point to Int8: The Compute Revolution Behind BitNet b1.58  

## 1.  Why the shift to 1‑bit weights matters  
Large Language Models (LLMs) have become the de‑facto backbone of contemporary AI systems.  Each Transformer layer is dominated by a handful of dense matrix multiplications (the \emph{nn.Linear} blocks).  In a conventional FP16 model these multiplications require a floating‑point multiply followed by an addition for every pair of elements.  The energy cost and silicon area of floating‑point units dwarf those of integer arithmetic, and the bandwidth demand for moving 16‑bit numbers across the memory hierarchy is significant.  

Lower‑bit quantisation has long been explored for inference: switching from FP16 to BF16 or even 4‑bit formats saves memory but still keeps the heavy FP multiply in place because most libraries perform a *mixed* precision kernel (int‑to‑int accumulation before casting back to float).  BitNet b1.58 removes this mixed flavour entirely by forcing every weight into the ternary set \{-1, 0, +1\}.  Consequently, every product in a matrix multiplication vanishes:  

\[
x \times w = 
\begin{cases}
x    & w=+1\\
-x   & w=-1\\
0    & w=0
\end{cases}
\]

Only integer addition remains – an operation that contemporary GPUs and ASICs can perform orders of magnitude faster and far more energy‑efficiently than floating‑point multiply/add.

## 2.  From theory to practice – The BitLinear layer  
BitNet replaces the standard \texttt{nn.Linear} with a custom \texttt{BitLinear}.  
* **Weights** are *absmean* quantised: each tensor is divided by its mean absolute value,
\[
\gamma = \frac{1}{nm}\sum_{ij}|W_{ij}|,
\]
then rounded to the nearest integer in \{-1, 0, +1\}.  
* **Activations** are kept in INT8 and scaled uniformly per token so that no zero‑point offset is required; this keeps the math simple while preserving expressivity.

Because every weight is ternary, the multiplication phase collapses into a *conditional add/subtract/zero* operation which modern accelerators can implement as a few back‑to‑back adders and comparators.  The resulting kernel (`2-bit` kernel from Ladder) runs on pure integer hardware, eliminating all floating‐point units from the critical path.

## 3.  Latency savings – a tangible speedup  
The time per output token is dominated by matrix multiplication inside each Transformer block.  
| Model | Size | Latency per token (ms) | Speedup vs FP16 |
|-------|------|------------------------|----------------|
| LLaMA FP16 | 3 B | ~2.5 | – |
| BitNet b1.58 | 3 B | ~0.9 | **2.8×** |
| BitNet b1.58 | 7 B | ~10 | **4×** |
| BitNet b1.58 | 70 B| ~70 | **4 ×** |

The speedup grows with model size because FP16 multiplies scale linearly with the number of parameters while BitNet’s additions do not – they are limited only by parsing the ternary filter mask.

## 4.  Memory bandwidth – less data, same payload  
Floating–point models require twice as many bytes per weight as INT8 models:

- FP16 weights: \(2^{11}\) bits per element (≈2 B).  
- Ternary weights: ⌈log₂(3)⌉ ≈ 2 bits ⇒ effectively one Int8 per two real coefficients after packing.

In practice BitNet uses a packed representation where two ternary values share one byte (“bits / value” ≈ 0.5). Even if we ignore packing optimisations, memory usage drops by roughly \(3.5\times\) compared with FP16 (see Table~\ref{tab:ppl}).  

Reduced bandwidth translates directly into lower DRAM–to–SRAM traffic:

- **DRAM traffic** for a single forward pass shrinks by >70 %.  
- **SRAM utilisation** doubles, permitting larger batch sizes on the same card.

## 5.  Silicon power – an order‐of‐magnitude drop  
GPU chips report energy per operation for FP and INT as follows (typical values on a modern GPU):

| Operation | Energy (aJ/op) |
|-----------|----------------|
| FP16 mul   | ~12          |
| FP16 add   | ~5           |
| INT8 add   | ~0·15        |

In an LLM forward pass each matrix multiplication involves \(N^2\) ops; replacing three fp ops with a single int add leads to a net reduction:

\[
E_{\text{BitNet}} \approx \frac{0·15}{12+5} \approx \frac{0·15}{17} \approx **0·009\,aJ/op**
\]

This translates into a reported **71×** reduction in arithmetic–operations energy consumption on state‑of‑the‑art \(7\,nm\) silicon for comparable model sizes (Figure 3). When considering end‑to‑end inference over many tokens, total power draw drops from several kilowatts to sub‑kilowatt levels while maintaining identical perplexity.

## 6.  Throughput – more requests per watt  
Benchmarking on two A100 GPUs running pipeline parallelism shows that a \(70\,B\) BitNet can serve up to eleven times as many requests per second as its FP16 counterpart at the same batch size limit (Table 4). This throughput increase stems from both lower latency and lower memory footprint per token.

## 7.  One extra bit – why “b1.58”?  
The “11” in *b1.58* comes from adding a zero value to standard binary quantisation:

- Binary (\{-1,+1\}) needs one bit per weight → \(w=8\log_2(2)=8\,bits/\!\theta=8\,bits/\text{sparsity}\).
- Adding zero gives ternary weights, which effectively require \(log_2(3)\approx1·58$ bits when encoded with a two–bit representation and yet offer feature filtering for free.

This small overhead pays off by enabling *explicit sparsity*, which further reduces both compute and memory usage at inference time because many matrix entries become exactly zero and can be skipped or compressed on‐the‐fly.

## 8.  Implications beyond inference  
* **Edge / mobile:** The low memory footprint and reliance on pure INT arithmetic makes BitNet ideal for CPU or low‑power GPU deployments where floating‑point units are scarce or expensive.
* **Mixture-of-Experts:** Sparse ternary weights cut inter‑chip communication dramatically; training large MoE LLMs becomes feasible on far fewer devices.
* **Long sequences:** INT8 activations halve KV cache bandwidth; lossless compression could double context lengths without new hardware.
* **Hardware design:** These observations motivate custom ASICs that specialise in *conditional add/subtract* operations instead of general multipliers—a line already pursued by companies like Groq but now finite-sized enough to be mainstream.

## 9. Closing thoughts  

BitNet b1.58 demonstrates that moving to integer arithmetic does not simply save money—it redefines what it means to build an LLM “at scale.” By turning every heavy-floating point multiplication into an ultra-fast integer addition (and occasional subtraction), we unlock dramatic gains in latency, memory usage, throughput and energy—effects that compound as models grow larger or run longer sequences.

The era where “all large language models are in $1\.58$ bits” is not just about smarter software; it signals a paradigm shift in silicon design—a shift toward specialized integer pipelines that will make powerful language understanding feasible even on small chips.”



# The New Scaling Law: When 1‑Bit Models Beat 16‑Bit Counterparts

## What’s a “1‑bit LLM”?

Large language models (LLMs) are usually built with 16‑bit floating‑point weights and activations. That means every parameter takes two bytes, and every arithmetic operation is a costly floating‑point multiply‑add. The new twist is to force every weight into a tiny ternary set \{-1, 0, +1\}. The resulting model, called **BitNet b1.58**, floats around 1.58 bits per weight (the “+0” value gives us a small bit‐rate boost over pure binary). Still, the arithmetic turns into almost pure integer addition—no multiplications at all in the large rope of linear layers that dominate LLM inference.

The paper shows that this extreme quantisation does **not** hurt performance. At 3 billion parameters, BitNet b1.58 reaches perplexities and zero‑shot accuracies that match or surpass the baseline LLaMA models running at full 16‑bit precision.

## The surprising scaling dynamics

### 3B BitNet beats 70B FP16

A key set of experiments trains each model on the same 100 B tokens of RedPajama data and evaluates on standard benchmarks (ARC‑Easy/Challenge, Hellaswag, Winogrande, PIQA, OpenbookQA, BoolQ). The results are summed up in two tables:

| Model | Size (B) | Perplexity | Zero‑shot accuracy |
|-------|----------|------------|---------------------|
| LLaMA (FP16) | 3 | X | Y |
| BitNet b1.58 | 3 | ~X | ~Y |
| BitNet b1.58 | 3.9 | >X | >Y |
| LLaMA (FP16) | 70 | X' | Y' |

Surprisingly, **BitNet b1.58 with just 3.9 B parameters outperforms the full‑precision 70B model** on both perplexity and end‑task accuracy while using **less GPU memory** and being up to **4× faster** in latency on large GPUs.

The scaling law immaterial to precision looks like this:

* **13 B BitNet ≈ 3 B FP16** in terms of latency, memory and energy.
* **30 B BitNet ≈ 7 B FP16** in terms of latency, memory and energy.
* **70 B BitNet ≈ 13 B FP16** in terms of latency, memory and energy.

These equivalences show that every doubling of *parameter count* in a binary model can offset roughly threefold increases in *floating‑point size*. In plain words: **the cost per parameter drops by more than a factor of three when you go from FP16 to a ternary representation**.

### Why does it work?

There are two synergy points that make ternary weights viable without hurting expressiveness:

1. **Explicit feature filtering via the zero weight**  
   By allowing a weight to be exactly zero, the network can “drop out” entire connections during training, acting like an implicit sparse regulariser. This improves optimisation dynamics compared to pure binary networks where every connection must be active.

2. **Faithful gradient signal through absmean quantisation**  
   The authors quantise weights using an *average‑absolute* scaling factor before rounding to \{-1, 0, +1\}. This keeps the magnitude of weight updates stable while still enforcing strict discreteness during forward passes.

Because all matrix multiplications collapse into integer addition counts (no comparison or multiplication overhead), training remains stable while inference becomes embarrassingly cheap.

## What does this mean for future LLM design?

### 1. Latency ≈ Memory ≈ Energy

In modern data centres and edge devices alike, three constraints drive cost: how fast a request finishes (latency), how many GPUs are needed for a given workload (memory footprint), and how much electricity it burns (energy). BitNet reaches higher speeds with less GPU memory and orders of magnitude lower arithmetic energy consumption—especially as model size grows due to its purely additive kernels.

### 2. New “Pareto Frontier”

Because higher accuracy now comes without ever scaling out the precision budget to the size of the model, practitioners can push *larger* models without blowing up compute budgets.

   * A single GPU can run an almost tenfold larger model compared with its FP16 partner.
   * Multi‑GPU pipelines for MoE – Traditionally MoE hit inter‑chip communication bottlenecks; with one‑bit weights activated across all experts the transfer bandwidth shrinks dramatically.

### 3. Edge & Mobile AI

With only ~8 bytes per param for all but tiny embedding tables (still FP16 at present), loading an entire network into embedded RAM becomes feasible. Combined with negligible multiplication intensity, CPUs on phones or tablets could run these models “by hand” with comparable accuracy to server‐grade boards.

### 4. Hardware Innovation

The authors explicitly call for hardware tailored to this paradigm: specialized “LPU” engines that take signed ternary inputs and produce integer additions by default; further LPU stages could compress the activation pipeline from INT8 down to INT4 or even INT2 for maximum density.

## Caveats & Open Questions

* **Training cost vs inference win:** Training still requires maintaining full FP precision for gradients; quantisation is applied only during forward/backward propagation for weight updates. This has a mild extra cost compared with fully mixed-precision training.
* **Zero attention bias design:** Removing biases and calibrating rotary embeddings might need careful tuning across architectures.
* **Long sequence handling:** While reducing activation precision doubles KV-cache capacity in benchmarks, real‑world long context use cases remain unexplored.
* **Scaling law generality:** Do we see the same equivalence if we move beyond RedPajama or include multimodal data?

Despite these open questions—still a hot research area—the evidence shows that BERGER-style ternary nets can become not just Hype but real competitive alternatives as models keep scaling.

## Takeaway

Meanwhile BPAs engineering teams wrestle with petabyte data sets and hundreds of GPU-hours per experiment; researchers now have a provably efficient recipe: drop all full‑precision weights into locked-in –1/0/+1 trits while preserving or boosting performance stats up to *70 billion* parameters or more.

That means you can build an AI system as powerful as current large GPTs or LLaMA while paying only about one third of the GPU memory load—and you’ll hit higher throughput without any drop in quality. The day when “big is better” is giddy—they’re saying maybe “more precise is unimportant” is still today’s big idea for LLMs.

### Key Quantisation Detail

The paper’s quantisation function is:

\[
\widetilde{W}_{ij} = \operatorname{RoundClip}\!\left(\frac{W_{ij}}{\gamma + \epsilon},\, -1,\,+1\right),\qquad
\gamma = \frac{1}{nm}\sum_{i,j} |W_{ij}|,
\]

with `RoundClip` saturating at \{-1, 0, +1\}.  
In practice:

```python
# PyTorch pseudocode
γ = W.abs().mean() + 1e-6
W_q = torch.clamp(torch.round(W / γ), -1, 1)
```

At inference time you can skip this step because the checkpoint is already stored in ternary form.

## 2. Runtime Optimisations

### 2.1 GPU Kernel Selection

The BitNet paper integrates a **2‑bit kernel** from *Ladder* for matrix multiplications that only perform integer additions and look‑ups in a small table of values \{-128…127\}. Make sure you:

- Enable `--use-bf16=False` if your CUDA kernels support BF16; otherwise fall back to INT8.
- Provide *kernel auto‑tuning*: launch small benchmarks and pick the fastest kernel per batch size.

```bash
# Example bash script
for bs in {1..32}
do
    python infer.py --batch $bs --kernel auto > /dev/null
    cat result.txt >> perf.txt
done
```

### 2.2 KV Cache Size & Sequence Length

Because activations are 8‑bit rather than FP16 (and can be compressed further to 4‑bit), you can safely double your context length without changing GPU residency.

```python
# Within Hugging Face pipeline
from transformers import BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype="uint8"   # uses our custom uint8 logic
)
model = AutoModelForCausalLM.from_pretrained(
    "path/to/bitnet_b158", config=bnb_config
)
pipeline = pipeline("text-generation", model=model)
```

### 2.3 Batch Size Scaling

The paper reports up to an **11× higher batch size** for a 70B BitNet compared to FP16 LLaMA when run on two A100s with pipeline parallelism.

*Practical tip:* Start with a minimal batch size (e.g., `batch=12`) then increase until you hit ~95 % memory utilisation.

```bash
accelerate launch --config_file accel_config.yaml infer.py \
    --batch-size $BS \
    --seq-length $SEQ_LEN \
    --use-int8-kernels
```

Plot memory utilisation with NVML or `torch.cuda.memory_summary()` to verify no hidden allocations.

# Long‑Context Language Models Made Easy with **BitNet b1.58**

In the last few years, LLMs have grown from a few hundred million parameters to well over a hundred billion. That growth has unlocked new kinds of applications—chat at true human level, code synthesis, large‑scale summarisation, and even “wet‑ware” style scientific reasoning. Unfortunately, the price tag scales as badly as the model size: larger models need more memory, more FLOPs, heavier inter‑GPU traffic, and ultimately more energy.

One of the biggest bottlenecks for real‑world use is *long‑sequence inference*. Whether you are building a legal document analyzer that has to read 10 k+ tokens in a single prompt or a medical summariser that stitches together notes from different hospital systems in one go, you normally need to keep a *key–value (KV) cache* for every transformer layer that contains all the past activations. The KV cache is usually stored in 16‑bit floating point (FP16). As the sequence length doubles, the memory pressure multiplies.

**10 T efficient context for 70B models?**  
That would require on the order of hundreds of gigabytes of DRAM for the KV cache alone—far beyond what an inference server can afford under latency constraints. The solution is simple: shrink the KV cache representation **without sacrificing accuracy**. That is precisely where BitNet b1.58 shines.

---

## How BitNet b1.58 Reduces KV Cache Size

BitNet b1.58 was built on top of the popular BitNet architecture but introduces an essential modification: *activations are quantised to 8 bits instead of 16*. The key points are

| Feature | Standard FP16 LLM | BitNet b1.58 |
|---------|-------------------|--------------|
| Weight precision | FP16 | 1.58‑bit ternary (−1, 0, +1) |
| Activation precision | FP16 | 8‑bit integer |
| Kernel type | FP16 linear + softmax | INT8 linear + low‑bit softmax |

Because matrix multiplication is replaced by integer addition (thanks to ternary weights), the overhead of floating‑point multiplication disappears entirely. Crucially for our discussion, the **KV cache now stores only 8‑bit integers**, halving its memory footprint relative to standard LLMs.

*Why 8‑bits?* The original BitNet used full‑precision activations because it had no way to safely reduce them while keeping accuracy intact. By providing an *absmean* scaling and a lightweight rounding procedure that avoids zero‑points (*RoundClip*), BitNet keeps per‑token activation distributions well centered around zero within the quantisation range \([-127,\,127]\). Empirical studies showed negligible perplexity loss when moving from FP16 to 8‑bit activations.

---

## Effect on Context Length

Let’s do some quick math.

- **Standard LLM:** Each activation uses 2 bytes (FP16).  
  For a model with N layers and K heads per layer, a KV cache for \(L\) tokens uses \(2 \times N \times K \times L\) bytes per token position.
- **BitNet b1.58:** Each activation uses 1 byte (INT8).  
  Memory is cut in half immediately.

If we double our context length from 4 k tokens to 8 k tokens while keeping everything else constant:

- FP16 model → **2× memory**
- BitNet b1.58 → **only ~√2× memory** (because you also halve each token’s weight due to ternary representation).

In practice this means that if your server can comfortably fit a 4 k context with an FP16 model on two A100 GPUs (≈30 GB per GPU), it could feasibly run an *8 k context* with BitNet b1.58 on the same hardware – all while respecting parallelism constraints imposed by pipeline or tensor parallelism.

---

## Real‑World Enabling Applications

   Law firms want AI agents that can ingest full contracts (tens of thousands of tokens) and return clause-level summaries or risk analyses instantly—a task impossible for standard LLMs at prod latency levels.

2. **Biomedical Knowledge Graph Construction**  
   Researchers need to read raw clinical notes + research papers in one go to link new entities into existing knowledge graphs. Double-length context drastically reduces duplicated queries and latency.

3. **Interactive Storytelling & Game Narratives**  
   Games often need to remember long session histories without reloading or retraining every time a player revisits an area—a perfect fit for low-memory long-context models.

4. **Edge and Mobile NLP**  
   Meshy devices running on ARM CPUs hope to keep up with on-device personal assistants that require thousands of tokens without offloading back to cloud services; bitwise computation is far more energy friendly than floating point operations.

5. **Hybrid MoE Distributions**  
   MoE models can be deployed across fewer chips because their KV caches are smaller; this cuts inter-chip communication which otherwise dominates runtime and power consumption.

---

## Why Energy Matters as Much As Memory

More bytes mean more data movement – and moving data from DRAM to SRAM costs roughly eight times as much energy as performing an integer addition on modern silicon (~7nm nodes). Because BitNet’s matrix multiplications *only* involve INT additions (thanks to ternary weights), each multiply–accumulate operation consumes roughly one twenty–sixth of the energy spent by an FP16 MACR in conventional implementations [EnergyCostModel2024].

What does this look like numerically?

|------------|--------------------------------------|
| FP16 LLaMA 3B | ≈ 6 W CPU load per GPU |
| BitNet b1.58 3B | ≈ 0.9 W – almost 7× less |

For edge devices this difference means not only lower heat but also dramatically prolonged battery life—even when you scale up from billions to tens of billions of parameters.

## 3. Build the Model

### 3.1 Architecture Overview

* Uses **LLaMA‑like components**:  
  - RMSNorm (separate per layer)  
  - SwiGLU attention/mLP layers  
  - Rotated embeddings (`rope`)  

* Replaces all `nn.Linear` calls with our custom block:

```python
class BitLinear(nn.Module):
    def __init__(self, in_features, out_features):
        super().__init__()
        self.weight = nn.Parameter(torch.empty(out_features, in_features))
        self.register_buffer("gamma", torch.tensor(0.0))   # mean absolute value

    def forward(self, x):
        # quantize on the fly
        w_quant = Quantizer.absmean(self.weight)
        return F.linear(x.to(device="cpu") if x.is_cuda else x,
                        w_quant.to(x.device))
```

### 3.2 Quantization Function

The core of BitNet is the *absmean* quantizer:

```python
@torch.no_grad()
def absmean(w: torch.Tensor) -> torch.Tensor:
    gamma = w.abs().mean()
    x = w / (gamma + eps)                     # eps ≈ 1e-8
    return torch.clamp(x.round(), -1., 1.)
```

This scales each weight matrix by its **average absolute value** and then clips to \{-1,+1\}. Running it in the forward pass keeps trainable weights in full precision until backprop happens.

### 3.3 Full Model Definition

```python
class BitNet(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.embed = nn.Embedding(cfg.vocab_size,
                                  cfg.hidden_size,
                                  padding_idx=cfg.pad_token_id)
        self.layers = nn.ModuleList([
            TransformerBlock(cfg) for _ in range(cfg.num_layers)
        ])
        self.ln_f   = RMSNorm(cfg.hidden_size)
        self.lm_head= nn.Linear(cfg.hidden_size,
                                cfg.vocab_size,
                                bias=False)

    def forward(self, input_ids):
        x = self.embed(input_ids)
        for blk in self.layers:
            x = blk(x)
        x = self.ln_f(x)
        logits = self.lm_head(x)
        return logits
```

### 4.2 Mixed Precision Tweaks

* We run **8‑bit activations**: after each GELU/SwiGLU pass we quantize to \([-Q_b,Q_b]\). In practice this is done using a simple uniform quantizer:

```python
def act_quant(a):
    minv, maxv   = a.min(), a.max()
    scale         = maxv - minv
    a_q           = ((a - minv)/scale*255).round() # Q_b=8
    return a_q / 255 * scale + minv
```

PyTorch’s **native AMP (`torch.cuda.amp.autocast`)** should still be used to avoid overflow during back‑prop—only the forward pass uses activations that are cast to lower precision.

# Why 1‑Bit Mixture‑of‑Experts Could Be the Future of LLM Scale

Mixture‑of‑Experts (MoE) has long been touted as the silver bullet for scaling language models without drowning in FLOPs. Yet in practice, MoE’s biggest bottleneck is not computation, it’s data movement: the activation tensors that must shuttle between thousands of expert kernels and the routing logic choke every GPU cluster. The new 1.58‑bit LLM family, exemplified by **BitNet b1.58**, cuts those numbers in half—if not more—and may finally make large‑scale MoE a practical reality.

## 1. Meeting two extremes at once

- **3‑bit weight representation**: By quantizing every weight to \{-1, 0, +1\} and adding an extra *zero* value, BitNet b1.58 achieves a *real* storage cost of only **1.58 bits per parameter**. That is roughly one‑seventeenth of a FP16 weight.
- **MoE architecture**: MoE splits the overall capacity into dozens or hundreds of independent experts. Each inference pass activates only a handful of them per token.

The two technologies are synergistic. Tiny weights shrink the raw volume that must each expert process; conditional routing keeps that volume from exploding across the network.

## 2. Quantifying inter‑chip traffic reductions

Let’s walk through a concrete example that follows BitNet b1.58’s design choices:

| Stage | Full‑precision FP16 | 1.58‑bit (BitNet) |
|-------|---------------------|-------------------|
| **Expert parameters** | 16 bits × 100 M = 2 GB | 1.58 bits × 100 M ≈ 20 MB |
| **Activation tensor per token** | 16 bits × hidden size |\(H\) | 8–10 bits × \(H\) |

For a widely adopted MoE benchmark (e.g., Megatron with 512 experts), each token propagates through roughly **5 experts** on average.

*Parameter shuffling*: In a distributed setting where each GPU hosts a subset of experts, moving the full‑precision parameters of an expert from one node to another would require transferring several gigabytes per GPU per training step—this is a massive O(N) penalty as the model scales.

With BitNet's ternary weights:

- The expert weight tensors shrink to *tens* of megabytes.
- Pipeline communication can happen over consumer‑grade interconnects like NVLink or PCIe without hitting bandwidth saturation.
- Even a naïve replication scheme becomes viable: storing a full copy per node costs only a few megabytes rather than gigabytes, eliminating cross‑node traffic altogether.

*Activation streaming*: Activations are already reduced from FP16 to INT8 in BitNet, halving their payload. When combined with zero‑point free scaling (no bias shift), these tensors become *dense, low‑bit* streams that any existing PCIe fabric can move cleanly.

## 3. The impact on MoE scale limits

MoE effectiveness hinges on two limits:

1. **Compute budget**: typically measured in FLOPs per epoch.
2. **Communication budget**: measured in bytes transferred per training iteration.

With traditional FP16 weights, the communication term dominates beyond ~10B parameters for even modest expert counts (≥32). This forces either aggressive model partitioning or massive network upgrades—both costly options.

By contrast, with BitNet’s *reduced storage*:

- The **parameter budget** lowers proportionally to bit-depth; we’re no longer limited by memory capacity.
- The **communication budget** drops sharply because each activation and parameter hop is lighter by ~10×.
- Therefore, the *effective capacity* (number of experts * active tokens / step) can be increased without hitting I/O ceilings.

Practically, this means we can safely train “tens of billions” of parameters with *hundreds* of experts on commodity GPU clusters while keeping training times within acceptable bounds.

## 4. Energy benefits ripple through the stack

Not only does data movement drop, but compute microarchitecture benefits amplify the savings:

- Weight quantization eradicates floating‑point multiplications; matrix–vector products become sequences of integer additions and sign checks.
- Existing GPU pipelines (e.g., NVIDIA’s Tensor Cores) can be overrun by custom integer kernels that exploit optimal bit width (e.g., mixed precision INT8/INT4).
- Energy per operation is orders of magnitude lower for integer addition than floating multiplication; estimates from silicon measurements show us up to **70×** reduction in arithmetic energy when moving from FP16 to 1.58-bit convolutions.

Since data movement itself consumes significant share of total power—particularly when traversing multiple interconnect layers—the overall green factor for MoE inference is compounded multiplicatively.

## 5. Real‑world evidence: From theory to practice

Recent papers report that BitNet b1.58 matches full‑precision LLaMA baseline performance starting at just **3 B** parameters when trained on identical token budgets (100 B tokens). Moreover:

- **Latency reductions**: At 3B size, inference speedup vs FP16 is ~2½×.
- **Memory savings**: About 3⅔× less GPU memory usage.
- **Throughput gains**: A 70B BitNet model achieved roughly nine times higher batch throughput than its full‑precision counterpart on dual A100 cards.

When you embed these numbers into an MoE pipeline—where each token traverses several experts—the cumulative advantages become starkly evident: more data moves slower because it is lighter; more experts can be placed on each accelerator because memory constraints loosen; overall training time shrinks rather than bloating like conventional MoE setups.

## 6. Looking ahead

### Hardware co-design

The path forward demands hardware that aligns with both tiny weights and routing logic:

- **Latency‐optimized interconnects** tailored to few‐bit data transfers.
- **Dedicated integer units** that seamlessly switch between add≈mul operations depending on expert gating.
- **On‐chip TTL buffers** for zero‐weight pruning paths—expert sparsity will explode once deactivation costs vanish.

Companies such as Groq are already experimenting with Low Precision Units (LPUs); scaling them toward *ternary*, *adaptive gating*, and *expert multiplexing* could unlock new horizons for industrial MoE deployments.

### Advanced quantization schemes

While BitNet uses simple round–clip quantization governed by mean absolute value scaling (_absmean_), future work might explore:

- Learned scaling factors per attention head or feed-forward layer.
- Adaptive k‑means clustering among \{-1,0,+1\} values guided by loss gradients.
- Mixed precision across architectures: e.g., keep output projection layers at higher fidelity while keeping core matrix multiplications ternary.

### Edge & mobile Mojo

The same tiny weight principle also unlocks edge MoE models—compact enough to fit on edge accelerators yet large enough to maintain meaningful expert diversity. This could enable sensor fusion or real-time translation services directly on mobile devices with negligible battery drain.

## Conclusion

Mixture-of-experts promised to solve one problem but introduced another: extreme inter-chip communication overhead that throttles scale and productivity. By marrying MoE with the startlingly compact storage afforded by 1.58-bit weights—from BitNet’s ternary weight set—we dramatically shrink both data volumes and floating-point operations.

The net effect is threefold:
1. **Hardware surplus freed up to host more experts.**
2. **Communication cost dwarfed by compute benefits, allowing larger cluster topologies without bandwidth penalties.**
3. **Energy footprints plummeting, opening viability for larger budgets and greener AI deployments.**

If you’re building next-generation LLMs that need both breadth—through more experts—and depth—through larger parameter counts—it’s time to crank up the quantization knobs until you hit that sweet spot around one point five eight bits per weight. The future of scalable LLMs may well be written in ternary bits and expert gates working hand-in-hand across multi-gigabit links.*



# Energy Code — How BitNet b1.58 Saves Energy Like Magic

## The big picture

Large Language Models (LLMs) are the engines that power chatbots, recommendation systems, and scientific discovery tools.  A single forward pass through a 70‑billion‑parameter LLM can burn tens of megajoules of electricity if you run it on conventional GPUs or ASICs that perform floating‑point multiplications and additions.  The paper “The Era of 1‑bit LLMs” shows that a *tiny* change—forcing every weight to be one of \{-1, 0, +1\} and all activations to fit in 8 bits—cuts the arithmetic energy of matrix multiplication by roughly **71×**.  In this post we unpack the arithmetic‑energy calculation, illustrate how the savings emerge, and point out why this matters for data‐center operators and green‑AI advocates.

---

## 1. Why matrix multiplication matters

A Transformer layer performs two linear transformations:

\[
\mathbf{y} \;=\; \mathbf{W}\mathbf{x} 
\quad+\quad 
\text{attention}\;\text{(another linear step)} .
\]

For an \(n\times m\) sparse weight matrix \(\mathbf{W}\) and an input vector \(\mathbf{x}\) of length \(m\), the naïve floating‑point implementation needs

\[
2 \times n \times m
\]

floating‑point **multiplication–addition (MAC)** operations:  
\(m\) multiplications per output neuron and \(m-1\) additions to accumulate them.

In a full‑precision FP16 LLM each MAC costs the same amount of electrical energy (ignoring memory traffic).  When you replace the MAC with a **ternary weight** \(-1\,|\,0\,|\,+1\), every multiplication turns into either

* a *zero* (no compute),
* a *sign flip* (cheap bitwise XOR/W–OR cheap), or
* an *identity* (push the incoming value forward unchanged).

In hardware, this is effectively an **int8 addition** between two signed values where the “multiplier” is a literal \(-1,\,0,\,+1\).  The key observation from the paper’s energy model is that an int8 addition consumes **≈ 0.3 pJ**, while an FP16 MAC needs about **20–30 pJ** on state‑of‑the art 7 nm processes.

---

## 2. Building the energy model

The paper follows the analytic cost model from papers like *EnergyCost* and *PokeBnn*.  For each linear layer we compute:

| Operation | Energy per operation (pJ) | Operation count |
|----------|---------------------------|-----------------|
| FP16 add | 5 | \(n\times m - n\) |
| FP16 mult | 20 | \(n\times m\) |
| **int8 add** (ternary weight case) | **0.3** | \(n\times m - n_{\text{zero}}\) |
| **zero multiplications** | negligible | \(n_{\text{zero}}\) |

Here \(n_{\text{zero}}\) is the number of zero entries in the ternary weight matrix; experimentally it’s roughly \(≈20~\%\) of all weights for typical pruning/quantizing regimes.

Putting this together:

- **FP16 layer:**  
  \[
  E_{\text{FP16}} = (n\times m - n)\times5 + n\times m\times20
                 = n\times m\times25 - n\times5
  \]

- **BitNet b1.58 layer:**  
  \[
  E_{\text{b1.58}} = (n\times m - n_{\text{zero}})\times0.3
                  = n\times m\times0.3 - n_{\text{zero}}\times0.3 .
  \]

Because \(n_{\text{zero}}\ll n\times m\), we can approximate

\[
E_{\text{b1.58}} \approx n\times m\times0.3 .
\]

Thus,

\[
\frac{E_{\text{FP16}}}{E_{\text{b1.58}}}
    \approx \frac{25}{0.3}
    \approx 83 .
\]

In practice hardware overheads, memory traffic, and bus delays reduce the ratio somewhat, landing at an empirical **~70×** savings as reported in Figure 4(B) of the paper.

---

# New Hardware = New Paradigm: Vehicles for One‑Bit LLMs

Large language models (LLMs) have become ubiquitous—chatbots on phones, virtual assistants in cars, and decision‑support engines in enterprises. Yet the cost of running even a 3 B‑parameter model on a single GPU can dwarf the cost of a 160‑B model when using full‑precision (FP16) arithmetic. The **BitNet b1.58** paper shows a compelling alternative: by quantizing every weight to one of \{-1, 0, +1\}, we can *match* FP16 performance while cutting latency by 2–4×, memory use by 3–4×, and energy consumption by more than an order of magnitude.

This efficiency upside does not come for free. It demands a *new* computing paradigm: matrix multiplications over tiny integer (`int8` or even `int4`) operands that exploit zero‑weight sparsity and ternary sign logic. Existing GPUs and CPUs were engineered for floating‑point workloads and cannot unlock the full potential of BitNet without bespoke silicon. In this post we outline why industry must shift to such hardware and what the guiding principles should be.

---

## 1. Why current chips are ill‑suited for ternary LLMs

| Metric | FP16 LLM | BitNet b1.58 | Ratio |
|--------|----------|--------------|-------|
| Latency per token | 34 ms | 9 ms | 3.8× |
| Peak GPU memory | 32 GB | 9 GB | 3.6× |
| Matrix‑mult energy | ~10 mJ | ~0.14 mJ | 71× |
| Throughput @ A100 | ~200k tokens/s | ~880k tokens/s | 4.4× |

These figures stem from the study’s own benchmarks on an A100 using the FasterTransformer code base enriched with a 2‑bit GEMM kernel from Ladder. The dramatic gains emerge because:

* **Weight sparsity**: setting zero‐weights forces `BitLinear` layers to ignore many multiplications entirely, reducing FLOPs.
* **Integer‐only math**: replacing expensive FP16 multiplication with trivial `int8` addition means hardware can pipeline far more operations per clock.
* **Compact data path**: ternary weights fit in less than two bits (hence “1.58”, i.e., one full bit plus a shared “zero” flag). Packed memory accesses require fewer DRAM transfers.

Standard GPUs devote power to high–precision compute units—tensor cores designed for FP32/FP16 at high FLOPS, yet their energy profile is dominated by floating‑point multiplies and large register files. CPUs have scalar integer ALUs but no bulk vectorized integer math capable of exploiting ternary patterns efficiently.

Hence, unless we re‑engineer silicon to prioritize *compact integer GEMMs*, the wall‑clock speedup observed in software falls flat when ported to commercial hardware.

---

## 2. Key hardware design principles for BitNet-friendly ASICs

Below are distilled guidelines that any new silicon vendor should adopt if it wants to make its chip useful for modern LLMs like BitNet b1.58.

### 2.1 Integer sparse GEMM engine

* **Data type**: Native support for `int1` or `int2` weights (ternary), `int8` activations; optional auto‐packing of two ternary values into a single byte.
* **Zero‐skipping**: Hardware crosses the “zero” bit early enough to bypass entire weight rows/columns without performing the multiply/add pair.
* **SIMD width**: Thousands of lanes (≥512) so that every partial product can be streamed in parallel.

### 2.2 Content‑addressable compression of zero patterns

The presence of many zeros invites compressed storage schemes:

* Use a lightweight *bitmask+value* representation per row; leaves waste when contiguous zeros are rare.
* Prefer *RLE* (Run Length Encoding) if zeros cluster around attention masks (often so).
* The decompressor should run in the data‑path so that the kernel never stalls waiting for decompression.

### 2.3 On-chip bandwidth maximization

* **Local SRAM buffers** should be sized per compute unit to hold complete tile of weights + activation activations.
* Build bandwidth pipelines that overlap weight fetches with computation; no DDR stalling.
* Design **dual-port SRAM** with transaction ordering so that read/write can happen simultaneously.

### 2.4 Voltage/current scaling

Because gain comes from low voltage operations:

* Use *voltage islands*: lower supply for integer cores versus higher supply for any residual FP units.
* Event‑driven clocks per tile: idle tiles wait at sub-nanosecond power draw.

### 2.5 System integration cares

Even if core logic is sound, overall system will not reach claimed speedups if:

* DRAM bandwidth is higher than necessary; ATA links become bottleneck.
* TPU-style pipeline (embedding → transformer layers → projection) is not exploited; order matters.
* Over-provisioned cache reduces double transfer effectiveness; need careful shared buffers between layers.

For example, Groq’s LPUs already incorporate a specialized integer engine but are still limited by linear activation mapping; an enhanced design could incorporate *weight-on-the-fly reconfiguration*, where each compute tile receives freshly recompiled kernels per view (channels × head).

---

## 3. Prototype design outline

Below is a minimal sketch of what an ASIC might look like:

```
+---------------------------+
|   Microcluster           |
|   > Tensor Core            |
|          │                  |
|   ├─ Integer GEMM engine   │
|   │   • int1/2 weights      │
|   │   • zero-skipping ASIC │
|   │   • packed weight FIFO │
|   ├─ Activation buffer     │
|          │                  |
|   > Small DRAM <─────      |
+---------------------------+
```

Key components:

1. **Integer GEMM Engine** – vector value multiply-add but uses sign logic (`x * y = x XOR y` when y ∈ {±1}, skip when y==0).
2. **Weight Pack Buffer** – holds up to n `int8` values compressed as two int1 per byte (`00 ±`).
3. **Zero-Aware Scheduler** – tracks zero pattern bitmap; interrupts latency pipeline only where truly needed.

The entire micro-cluster should fit under ~200 mm² at 7 nm; resulting energy cost close to roughly \(E = C \cdot V^2\) with \(V\approx0\\.25V\), much lower than typical FP16 tensors cores (≈0\\.95V).

## 4. Roadmap and feasibility

### Short term (~year)

* Adapt existing synthesized kernels (e.g., from Ladder) onto FPGAs with custom int8 cores; validate latency & memory savings under realistic batch sizes.
* Engage open-source communities (Hugging Face, vLLM) to ship idiomatic BitNet adapters for these boards; prove people actually pull down b1\.58 models.

### Medium term (~3–5 years)

* Design ASIC prototypes targetting AI edge servers (e.g., IoT hubs). Lower cost and increased density unlock MLaaS in telecom towers or automotive ECUs.
* Push integration into datacenter accelerators—build dedicated “LLM offload” tiles inside generic DPUs or HPC accelerators as complementary inference pathways.

### Long term (~5+ years)

* Co-design training accelerators capable of *deep quantization-aware training decisions*. Bits’n’Bags platform could evolve into full-fledged end-to-end training at scale without exposing engineers to low-level sparsity tuning.
* Incorporate on-chip learning updates (`online learning`) using dynamic thresholded flows—this would make on-device conversation agents truly personalizable without backhaul GPU servers.
