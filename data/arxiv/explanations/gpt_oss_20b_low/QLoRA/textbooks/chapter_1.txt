## Introduction to LLM Finetuning

Large language models (LLMs) have become the backbone of modern natural‑language processing, powering everything from code generation to conversational assistants. However, the “one‑size‑fits‑all” nature of pretrained weights is often insufficient for specialized tasks or for adhering to new safety and ethical constraints. Fine‑tuning—a process where the pretrained model is further optimized on a target dataset—remains the most effective way to imbue LLMs with task‑specific knowledge or behavioral traits.  

Yet fine‑tuning incurs a steep price: the sheer size of state‑of‑the‑art models (e.g., 65 B parameters in LLaMA 65B) turns every training step into an engineering bottleneck. GPU memory usage scales roughly linearly with the number of trainable parameters, and when gradients must be stored for backpropagation, the required memory balloons further. As a result, conventional training workflows often demand dozens of high‑end GPUs or terabytes of consolidated memory—resources that many researchers simply do not possess.

In this chapter we present **QLoRA** (Quantized Low‑Rank Adapter with Retained Optimal Accuracy), a principled finetuning paradigm that reduces memory consumption by more than an order of magnitude while preserving (and sometimes surpassing) the performance of full‑precision training. We detail the theoretical foundations behind its core innovations—4‑bit NormalFloat (NF4), Double Quantization, and Paged Optimizers—and describe how they cooperate to make 65 B parameter finetuning feasible on a single consumer GPU.

---

### Challenges of Conventional Finetuning on Large Models

Conventional finetuning keeps all weights in full precision (typically 16 bits per weight, commonly named FP16 or BF16). Consider a transformer decoder such as LLaMA 65B, whose raw weight tensor occupies roughly \(65\times10^9\times2\ \text{bytes} \approx 260\,\text{GB}\). During training, gradients must be stored simultaneously: a forward pass produces activations that are checkpointed for backward computation; then each weight’s gradient appears as an additional tensor that must reside in GPU memory until the optimiser step updates them. For a mini‑batch covering many long sequences—a common case when finetuning on instruction datasets—the memory consumption spikes far beyond the base weight size.

To mitigate this, two canonical strategies are employed:

1. **Gradient Checkpointing** – only selected intermediary activations are retained; others are recomputed during backpropagation. While effective at cutting activation memory by up to 50 %, checkpointing increases computational cost and introduces sensitivity to sequence length.
2. **Parameter Efficient Fine‑Tuning (PEFT)** – expensive parameters are frozen while introducing many trainable adapters (e.g., LoRA). The idea is that a small set of low‑rank matrices can capture task‑specific perturbations without touching most model weights.

Even with these tricks, training very large models may require 500–800 GB of GPU memory when using mixed precision FLM16 runtimes—clearly beyond what a single consumer GPU offers. Thus, purely architectural modifications alone are insufficient; we must revisit how we store and manipulate model weights back at the arithmetic level.

### Memory Overhead of 16‑Bit Training

A straight comparison illustrates where most memory sweat lies:

| Component                     | Size (for a typical layer) | Notes |
|------------------------------|----------------------------|-------|
| Model weights                | ~5 GB (BF16) (for 7B)     | Unsqueezed tensor size |
| Activation gradients         | ~18 MB/checkpoint          | Grows logarithmically w/ batch size |
| LoRA adapters                | ~26 MB                      | Very small relative to weights |
| Optimiser states             | 1–2× parameter size       | Adam/AdamW maintain first/second moments |

When moved up to 65 B parameters, these numbers explode proportionately. Crucially, while LoRA reduces *trainable* parameter count drastically, **most mid‑training memory is still consumed by storing activation gradients**—the backbone tensors produced during forward passes that are needed for error propagation back into the frozen base model’s parameters.

This observation sets the stage for QLoRA: if we can *compress* the base model weights into *four bits* without single‐point loss, we both – a large portion of the static space and – the dynamic space needed to recompute intermediate states from quantised tensors will shrink dramatically.

### Overview of Quantization and Its Limitations for Training

Quantization traditionally belongs to **inference acceleration**: reducing computation precision from 32-bit float to an integer representation such asInt8 results in fewer FLOPs and lower power consumption while tolerating minor accuracy loss. Common schemes include *blockwise* quantization (each block gets its own scale factor) and *per-channel* scaling to mitigate outliers.

When applied to training, however, several pitfalls emerge:

- **Gradient Doom:** Backpropagating through coarse quantisation is noisy because low–bit quantisers do not preserve small gradient nuances necessary for fine learning.
- **Dynamic Range Collapse:** Standard Int8 or Float4 representations struggle with highly skewed weight distributions typical in transformers; outliers saturate bins leading to catastrophic clipping.
- **Memory Footprint:** Even after quantizing weights to Int4 or Float4, we still need *scales* per block — usually stored as FP32 — whose overhead can match or exceed the compressed weights’ savings when block sizes are small.

Therefore any attempt at *training with low‐precision weights* must reconcile these issues by designing a “lossless” pathway that simultaneously enables efficient forward pass computations and stable gradient flows through frozen parameters.

---

### Motivation for QLoRA: 4-Bit Finetuning Without Accuracy Loss

QLoRA addresses training gap by combining three complementary ideas:

1. **Zero‐Mean Normalized Distribution Assumption**  
   Pretrained transformer weights empirically follow an almost Gaussian distribution centered at zero with relatively stable standard deviation per layer (see Appendix A). This allows us to construct quantisation schemes rooted in information theory rather than naïve rounding.
   
2. **NF4 Data Type – NormalFloat**  
   NF4 builds on quantile quantisation which guarantees every bin receives the same expected number of samples if data follows its target distribution. Instead of classic Float4 or Int4 formats which place uneven bin widths over wide dynamic ranges, NF4 shapes bins symmetrically around zero so that both tails receive equal counts—a property optimal for normal data.
   
3. **Double Quantisation**  
   The scales required per block dwarf minor savings if left uncompressed. QLoRA first maps raw FP32 scales \(c^{\text{FP32}}\) into FBloat16 coefficients; then applies an *auxiliary* 8-bit floating point quantiser on those scales before returning them during dequantisation. This hierarchical compression yields roughly \(0.37\)-bit savings per weight on top of the primary NF4 bitwidth.
   
These ideas yield a representation where:
- The base model resides entirely in four bits plus compressed constants;  
- All computations during forward/backward passes lift tensors back into BF16 space so that standard cuBLAS kernels run unchanged;  
- Gradient flow only touches LoRA parameters; thus all 65 B base weights remain strictly frozen—even though their values are updated implicitly via adapter adjustments.

Empirical evidence across benchmarks shows QLoRA faithfully reproduces full FP16 performance up through \(65\,\text{B}\), an order of magnitude higher inference accuracy than any prior low-bit finetuning attempt without resorting to reinforcement learning or full retraining.

### Key Contributions of QLoRA

| Contribution                     | Purpose & Impact                              |
|----------------------------------|----------------------------------------------|
| **NF4 – Information-Theoretic 4-bit Quantiser** | Matches theoretical optimality over normally distributed data; empirically outperforms standard Float4/Int4 on both language modelling perplexity and downstream tasks (e.g., MMLU). |
| **Double Quantisation**          | Compresses per-block scaling constants without fidelity loss—a \(0.37\) bits/parameter gain averaging ~3 GB saved on a 65 B model; maintains straightforward dequantisation pipeline via `doubleDequant`. |
| **Paged Optimisers**             | Leverages NVIDIA Unified Memory to evict slowly-used optimiser states from GPU RAM into host RAM during checkpoints—thereby eliminating sporadic OOM spikes caused by long attention contexts without chunking sequences manually. |
| **Unified Low-Rank Adapter Embedding** | LoRA adaptors inserted at _every_ transformer projection matrix (QKV projections and MLP layers), preserving full fine-tuning expressivity while keeping trainable parameter count ≈0.2% of total size—comfortably fitting within residual memory budget even after double quantisation overheads are added. |
| **Scalable Training Infrastructure** | Open-sourced CUDA kernels for NF4 dequantisation & matrix multiply applicable on any recent NVIDIA architecture; integrated into Hugging Face Transformers; pipeline capable of training from scratch tens–of–thousands of instruction datasets while recording detailed resource usage logs.|

The synergy among these components allows QLoRA not only to reduce RAM needs below \(48\,\text{GB}\) for a \(65\,\text{B}\) model but also dramatically lowering wall-clock time per epoch from weeks on cloud clusters down to a single day on an off-the-shelf professional GPU.

### Summary of Guanaco Results and Impact

Using QLoRA across multiple instruction-following datasets—from OASST1’s multi-turn dialogues up through FLAN v2’s curated prompts—the authors built a family of models dubbed *Guanaco*. The standout device among them is Guanaco 65B:

- It achieves **99.3 % relative performance** compared with ChatGPT according to GPT-4–based Elo ranking on Vicuna-style prompts—a gap reduced nearly tenfold compared with previous open-source baselines such as Vicuna or Alpaca.
- The same architecture trained only on open-source instructions surpasses historically proprietary trained models such as Open Assistant’s RLHF curriculum while requiring less than half the dataset size.
- Training time is modest: Guanaco 33B trains in under twelve hours on a single consumer-grade RTX 3090Ti (24 GB), whereas full-batch FP16 finetuning would have taken multiple days across several A100 machines.

Beyond academic curiosity, this unlocks homogenous research pipelines: teams lacking large compute clusters can safely experiment with privacy-preserving instruction tuning cycles locally, enabling rapid prototyping throughout startups and in academia alike.

### Challenge One: Conventional Finetuning Limits

To appreciate why memorizing raw gradients is prohibitive at scale, imagine you supply GPT-like model with a batch comprising 64 sequences each \(2{,\!000}\) tokens in length using int8 tokens internally but pushing them through fused positional & multitoken embeddings inside transformer layers.

For each linear projection \(\mathbf{W}\in \mathbb{R}^{h\times o}\), during training you must store both
- \(\frac{\partial \mathcal{L}}{\partial \mathbf{W}}\)—the gradient matrix—and
- \(\frac{\partial \mathcal{L}}{\partial \mathbf{X}}\)—the chain rule’s upstream gradient w.r.t.\ input activations.

If you naive store all these matrices in BF16…computationally each weight has about 53 million combinations worth thousands → multi-terabyte footprints simply when unflattened across all layers over one epoch! Gradient checkpointing alleviates this by only retaining every _k_ activations but still requires recomputation depth‐wise; its computational pipeline can be expressed:

\[
\frac{\partial \mathcal{L}}{\partial \mathbf{W}}
= \sum_{s=1}^{S} 
\left(\frac{\partial \mathcal{L}}{\partial \hat{\mathbf{o}}_s}
\dots
\dfrac{\partial \hat{\mathbf{x}}_{0}}{\partial \mathbf{W}}\right),
\]

where \(S\) denotes blocks which must be staging points due response resizing downstream dynamically.

The net effect is twofold:
1. Layer stack height (~30 layers for LLaMA) multiplies storage needs multiplicatively due to gating inside self-attention and robust Feed-Forward pathways.
2. Convolutional deep learning frameworks such as PyTorch compute these values implicitly based on autograd tracing yet still must hold them unless explicitly freed via checkpoint control flags—an overhead negligible relative to gigantic tensor volume but unavoidable when hardware memory hovers near capacity thresholds.

Consequently researchers resort frequently to distributed data parallelism across dozens or hundreds GPUs—to split both forward activations among machines AND partition binary checkpoints that exceed any one machine's local host size—an action accompanied by network latency costs making experimentation costly.
