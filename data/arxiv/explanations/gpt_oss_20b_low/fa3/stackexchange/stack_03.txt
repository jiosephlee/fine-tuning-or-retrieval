\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What are the layout constraints for FP8 WGMMA on Hopper?
Question:
The paper mentions that for FP8 WGMMA only k‑major input operands are accepted, whereas FP16 accepts both mn‑major and k‑major. Could you explain how this restriction arises from the underlying Tensor Core datapath? Also, how do we reconcile the distinct layouts of the FP32 accumulator and the FP8 operand when chaining two successive WGMMA operations in FlashAttention‑3?
Answer:
**Why FP8 WGMMA accepts only *k*-major operands**

The WGMMA instruction on Hopper is a *warp‑group* matrix–multiply performed by the Tensor‑Core engine.  
At the most basic level each warp‑group executes a fixed‑size primitive, for example an $(8 \times 4 \times 4)$ or $(8 \times 8 \times 8)$ mul‑add, that is fully hard‑wired into the scalar‐ and vector‑unit pipelines.  
To keep the datapath simple, every operand that feeds a Tensor Core must be laid out so that a single memory read can bring the entire “column” (or row) of values that will be streamed into the multiplier array without any further shuffling.

For **FP16** TMACs the hardware registers are soft‑wired such that either operand may be presented as either
- **mn‑major** – contiguous in the outer dimension (e.g., the first dimension of an $M\times K$ matrix) or  
- **k‑major** – contiguous in the inner dimension (the $K$ dimension).  
This gives the compiler two valid aliasing paths: one path streams rows of *A* while keeping columns of *B* and vice versa.

For **FP8** Tensor Cores Hopper uses a different physical datapath. The FP8 arithmetic units are smaller, and their load logic can only stream **$K$** elements at a time because the 8‑bit values occupy less bandwidth than 16‑bit values. The 8‑bit input registers are packed two places per scalar, so a read burst that fetches a column of *K* values has to be aligned vertically in memory. Consequently, only when the operand is laid out in **k‑major** order can the load logic fetch a contiguous block of columns with one TMA/TMAa call. If the operand were mn‑major, the load would have to perform a strided or transposed fetch which is not supported by the built‑in FP8 TMA path, so the compiler silently rejects or would need an extra shuffle stage that would destroy throughput.

Thus the restriction originates from the way Hopper’s FP8 Tensor Core datapath is wired: it can only consume columns of length $K$ without additional reordering, making k‑major layout mandatory for FP8 WGMMAs.

---

**Reconciling FP32 accumulator layout with FP8 operands when chaining WGMMAs**

When we fuse two consecutive WGMMAs—first $\mathbf{Q}\!\times\!\mathbf{K}^T$ to produce an fp8 “softmax” tile $\tilde{\mathbf{P}}$, then $\tilde{\mathbf{P}}\!\times\!\mathbf{V}$—the first multiplication produces an **FP32 accumulator matrix** in registers. The second multiplication uses **FP8 operands** coming from SMEM.

In Hopper each WarpGroup has its own register file segmented into:

| Register group | Role in WGMMA (FP32 accumulator) | Layout seen by the compiler |
|----------------|----------------------------------|-----------------------------|
| `A` | Input matrix A (rhs)     | *mn*-major by default       |
| `B` | Input matrix B (lhs)     | *mn*-major by default       |
| `C` | Accumulator              | Layout depends on vector size |

For FP16/WGMMA, this mismatch between accumulator layout (row–major FP32) and operand layout (mn- or k-major fp16) is invisible because both operands are produced from float16 tensors that are already in stride-$K$. The compiler emits a simple register shuffle that reorders an fp16 matrix to match the rows needed for accumulation.

With **FP8**, after performing `C = A × B^T` where `A` and `B` are fp8 in k-major form, WGMMA writes its result back into registers as an **FP32 tile** laid out in *mn*-major order. The second WGMMA expects its first operand (the fp32 tile from $\tilde{\mathbf{P}}$) to be supplied as if it were created from an fp32 matrix in k-major order. Because we cannot change how Tensor Cores source their operands at run time, we must **shuffle** the registers produced by the first multiply so that they appear to come from a k-major fp32 source.

The authors resolve this mismatch using two simple tricks:

1. **Byte permute / register shuffle**  
   After each WGMMA, they apply a byte‐level permutation that reorders every consecutive eight registers:
   \[
   \{d0,d1,d4,d5,d2,d3,d6,d7\}\;.
   \]
   This maps rows ↔ columns exactly as required: what cortex originally produced as rows becomes columns for the next multiply without touching memory.

2. **In‑kernel transpose of V tiles**  
   Since V must be loaded into SMEM in k‑major order for FPGA-WGMMAs, they transpose V on-the-fly using `ldmatrix/stmatrix`. The same byte permutation applied to V ensures that its columns align with the newly shuffled accumulator tiles coming from ∼∧PS.

Thus, when chaining two WGMMAs:

- The first WGMMA writes its FP32 result into registers.
- An immediate byte–permutation transforms it into k‑major layout.
- The second WGMMA consumes this permuted data along with an fp8 V tile that has been transposed on load.

Because both transforms happen entirely in registers—or with LDSM/STSM which pull whole 128 byte blocks—the overhead is negligible compared with memory traffic. This carefully orchestrated sequence satisfies both datapaths: Hopper’s FP8 WGMMAs see their inputs in k‑major form while still benefiting from high throughput hierarchical accumulation.

---

### Takeaway

The k‑major restriction for FP8 WGMMAs stems from how Hopper’s Tensor Core arithmetic unit is wired to stream columns of eight‐bit values directly from memory; it cannot accept arbitrarily strided data unless expensive shuffles are performed. By permuting registers after each multiply and transposing input tiles on load (with LDSM/STSM), FlashAttention‑3 aligns its FP32 accumulator layout with the required k‑major format for successive GPUs MMs while keeping almost all work inside shared memory and registers, preserving both speed and numerical stability.
