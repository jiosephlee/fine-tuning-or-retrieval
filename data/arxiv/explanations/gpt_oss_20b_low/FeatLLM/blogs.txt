# How LLMs Can Become Your Personal Feature Engineer for Tabular Data

Working with tabular data is a common task in data science: you have a spreadsheet, a CSV file, or a database table, and you want a model that predicts a label from the columns. Traditional approaches – linear regression, tree ensembles, deep tabular nets – all require you to hand‑craft or let the algorithm discover useful feature representations. In low‑shot settings, where only a handful of labeled rows are available, these approaches suffer from overfitting and from lacking useful inductive bias.

Enter *FeatLLM*, a recent framework that flips the classic property of large language models (LLMs) on its head. Instead of relying on an LLM to produce an answer for *each* sample during inference (which is expensive and slow), FeatLLM uses the LLM **once** at training time to generate a set of concise, human‑readable rules. These rules are turned into binary (0/1) features that can be fed into any lightweight downstream model. The end result is:

* **Fast inference** – no LLM calls per sample after training.
* **Low cost** – only a handful of API queries are needed.
* **Strong few‑shot performance** – LLM prior knowledge compensates for scarce labeled data.

In this post we walk through the core ideas behind FeatLLM, explain how it works step by step, and discuss why it matters for real‑world tabular problems.

---

## 1. The Crash Course on Feature Engineering

Feature engineering is the art of transforming raw data into representations that make learning easier. Classic techniques include:

| Technique | What it does | Example |
|-----------|--------------|---------|
| One‑hot encoding | Turns categorical values into binary vectors | gender → {male=1, female=0} |
| Binning | Converts continuous ranges into bins | age 25 → “20s” |
| Interaction terms | Captures combinations | age × income |

In practice, engineers spend hours iterating over dozens of such transformations. Modern automatic methods (e.g., feature selection algorithms) still rely on data‑driven heuristics and can be brittle when you have only tens of examples.

LLMs have shown an uncanny ability to understand and manipulate natural language representations of data. FeatLLM leverages this capacity: it asks an LLM to *think* about the problem, guide itself through reasoning steps, and ultimately *output* explicit logical rules that can be parsed back into code.

---

## 2. From Raw Data to Rules: The Two‑Step Prompt

### 2.1 Basic Information Description

The prompt starts with ground truth context:  

1. **Task description** – e.g., “Does this patient’s cardiac record indicate chronic heart failure? Yes or no?”  
2. **Feature descriptions** – type + optional definition for each column (numerical ranges, categorical vocab).  
3. **Few–shot demonstrations** – 1–3 labeled rows serialized as text (“Age is 37 … Answer: No”).

All this lives in a single input string that respects the LLM’s token limit.

### 2.2 Reasoning Instruction

The prompt includes a *chain‑of‑thought* style instruction split into two stages:

1. **Prior knowledge stage** – The LLM reasons about how features *generally* relate to the target (e.g., older age → higher risk). It does not look at the specific examples yet.
2. **Data‑driven stage** – Using both its prior knowledge and the few examples provided, the LLM infers logical conditions—“rules”—that separate classes.

Splitting reasoning into two stages protects against spurious correlations that could arise if the model only saw limited examples.

### 2.3 Response Format Guidance

The prompt dictates how rules should look:

```
If <condition> then Class = Yes
```

Each rule follows a simple pattern so it can be parsed mechanically later. This guidance reduces parsing noise caused by alternative phrasing (“greater than”, “more than” etc.).

Concretely, FeatLLM requests ten rules per class `Yes` or `No`. This fixed budget keeps prompt size small while still giving enough signal.

---

## 3. Turning Rules into Binary Features

Once the LLM returns 20 textual rules (10 per class), we need code that evaluates them against every row in your dataset.

Instead of writing a parsing engine ourselves (which would need to handle thousand of edge cases), FeatLLM delegates this task back to the same LLM:

* We prompt it with: “Write Python code that given a dataset row evaluates rule X and returns `True`/`False`.”
* The returned snippet is executed with `exec()`; each rule produces one column of 0/1 values per sample.

After this step we have transformed every original column (`age`, `blood pressure`, …) into up to `2 × R` binary variables (`R = 10`, one per class), where each binary variable indicates whether a row satisfies one specific rule.

These features are purely logical; they capture non‑linear relationships without any statistical fitting beyond the LLM step.

---

## 4. Learning Rule Importance with a Simple Linear Model

Having generated binary features \(\mathbf{z}_k^i \in \{0,1\}^R\) for each sample \(i\) and class \(k\), we fit one small linear model per class:

\[
\text{logit}_k^i = \max(\mathbf{w}_k,\;0)\!\cdot\!\mathbf{z}_k^i
\]

- \(\mathbf{w}_k \geq 0\) gives non‑negative importance scores per rule.
- Softmax over all classes yields probabilities \(\mathbf{p}^i\).

Training uses just cross‑entropy loss on your few labeled examples (~4–16 shots). Because there are at most \(R=10\) parameters per class, overfitting is mitigated even with very few samples.

---

## 5. Robustness Through Ensemble & Bagging

A single call to an LLM is stochastic; different temperature settings or demo order may produce slightly different rule sets.

FeatLLM addresses this in two ways:

1. **High temperature & demo shuffling** – Encourages diverse rule sets across rounds.
2. **Bagging** – For each round we randomly select either:
   * A subset of the few‐shot examples,
   * Or a subset of original features to serialize,
   ensuring each batch respects token limits while adding variability.

We repeat this process \(T=20\) times and average predictions across all weak learners—many weak but complementary models together produce strong overall performance.

---

## 6. Why This Matters for Practitioners

| Problem | Traditional Solution | FeatLLM Advantage |
|---------|---------------------|-------------------|
| Low‑shot data | Heavy regularization needed; high variance | Uses LLM prior knowledge → fewer overfitting |
| Large feature tables | Token overflow in prompt; performance drops | Bagging splits in smaller prompts |
| Inference latency | Need one LLM call per sample | Only offload once; use fast downstream model |
| API cost & availability | Must train or fine‐tune large models | Only ~30 API queries + simple linear model |

In realistic benchmarks across thirteen diverse datasets—from medical diagnosis to financial risk—FeatLLM consistently achieves top performance while keeping training time modest (~30 API calls) and inference time comparable to classic tree ensembles.

# From Raw Numbers to Pruned Rules: The Two‑Step Reasoning Behind FeatLLM

Few‑shot learning on tabular data is a tough nut to crack. When you only have a handful of labeled rows, you risk leaping on spurious correlations or learning nothing at all. FeatLLM tackles this challenge by asking the large language model (LLM) to *think like an expert diagnostic engineer* instead of running every example through the model. Its key innovation is a two‑step prompt that mirrors how a human would first recall domain knowledge and then examine the data at hand.

Below we unpack how this structured reasoning works, why it matters, and what it means for real‑world low‑shot tabular tasks.

---

## 1. The Problem: LLMs as Black Boxes

Prior work has long fed training examples and the raw table text into an LLM and let it predict each new row. While this “in‑context” approach can leap beyond classical baselines, it carries several drawbacks:

| Issue | Impact |
|-------|--------|
| **Per‑sample inference cost** | Each new row triggers an expensive LLM call. |
| **Limited prompt size** | Highly dimensional tables exhaust the token window quickly. |
| **Fine‑tuning requirement** | Some state‑of‑the‑art methods need gradient access or large backbones. |

FeatLLM flips the script: *use the LLM only once per few‑shot training set, pull out human‑readable rules, then do all predictions with a tiny linear model*.

---

## 2. The Two‑Step Prompt: Mimicking an Expert’s Workflow

The prompt is deliberately divided into two cognitive stages, much like how a seasoned clinician might first recall medical principles and then analyse a specific patient record.

### 2.1 Step 1 – Prior Knowledge Reasoning

> **Goal**: Let the LLM generate high‑level relationships between features and the target that reflect its pre‑trained knowledge base.

**How it’s done**

1. **Task framing** – The prompt starts with a clear question format (e.g., “Does this patient have chronic heart failure?”).  
2. **Feature declarations** – Each column name is paired with its type (categorical/continuous) and optionally a short definition drawn from dataset documentation.  
3. **Pre‑exposition instruction** – The LLM is explicitly asked to *first* think about which features might logically influence the target *without* looking at any concrete example yet.

This forces the model to tap into world knowledge such as “older age increases heart failure risk” or “high triglycerides are linked to diabetes”. By grounding the reasoning in feature types, we avoid nonsensical rules like “if *salary* > 200k then …” when *salary* is nominal.

### 2.2 Step 2 – Data‑Driven Rule Extraction

> **Goal**: Using both prior knowledge and few example rows, distil concrete binary rules that separate classes.

**How it’s done**

1. **Example demonstrations** – Typically 4–8 labeled rows are serialized into text (e.g., `age is 45, cholesterol is 210 … Answer: No`).  
2. **Two‑tier instruction** – The prompt tells the LLM:
   * First, recall prior relationships (from Step 1).  
   * Second, use these hints together with the specific examples to craft precise rules for each class.
3. **Rule formatting instructions** – Each rule must adhere to a strict syntax such as:
   ```
   Class A: IF age > 60 AND cholesterol > 200 THEN Yes
   ```
   This heavy scaffolding makes downstream parsing trivial.

The corpus of extracted rules per class serves as *binary features*: for every rule we check if a new sample satisfies it (1) or not (0). 

---

## 3. Turning Rules into a Zero-AI Prediction Engine

Once we have binary rule features, all that's left is to learn their relative importance:

\[
\text{logit}_k = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k
\quad;\quad
p_k = \text{softmax}(\{\text{logit}_j\})
\]

- \(\mathbf{z}_k\) = vector of satisfied rules for class \(k\).  
- \(\mathbf{w}_k\) = small positive weight vector optimized with cross‑entropy over the few shots.

No sophisticated neural nets are needed—just an \(O(R)\) dot product per class followed by softmax. Crucially:

* **Inference cost collapses**, because we no longer hit the LLM for each sample.
* **Model interpretable**, since each weight tells us how critical a particular rule is.
* **Prompt size limitations bypassed**, because rule generation happens once per bootstrapping round.

---

## 4. Boosting Robustness by Bagging & Ensemble

The LLM can still be dicey; different prompts may produce different rule sets. FeatLLM mitigates this by:

| Component | Effect |
|------------|----------|
| **High temperature sampling** | Introduces variety in rule sets across trials. |
| **Random ordering of demonstrations** | Exploits order sensitivity discovered in recent studies (LU et al.) |
| **Feature bagging** | Randomly subselects subsets of features or examples each round so that long tables fit into token limits without drowning in irrelevant noise. |
| **Ensembling over T trials** | Predictions are averaged over weights learned from each independent trial (`T≈20`). |

Across experiments on 13 diverse datasets, this ensemble saves ≥10 % AUC relative to single-rule models.

---

## 5. Why Two Steps Outperform One-Step Inference

The experimental results strongly highlight why FeatLLM’s staged prompting beats naive in-context learning:

| Metric | FeatLLM (4 shots) | Baseline with 32 shots |
|--------|-------------------|------------------------|
| Avg AUC across datasets | ~0.91–0.94 | ~0.91–0.93 |

### Key observations

1. **Reduced spurious correlation leakage:** When unrelated columns were injected into data sets, FeatLLM’s performance degraded only marginally because the prior-knowledge step prevented exploration of those columns unless they logically fit.
2. **Smaller computational footprint:** Once training finished, inference parallels that of a standard logistic regression—mere matrix multiplications versus repeated GPT calls.
3. **Interpretability advantage:** Every learned weight links back to an explicit human-readable rule that can be inspected or edited manually if needed.

---

## 6. Takeaway for Practitioners

If you’re dealing with small labeled sets and high-dimensional tabular data—common in finance, healthcare, supply chain logistics—FeatLLM offers:

* A way to harness LLMs’ world knowledge without paying for continuous inference.
* An automated pipeline that outputs explainable binary features.
* A method scalable enough for thousands of columns via feature bagging.
  
To get started:
1. Serialize your few-shot examples using the `Serialize()` schema above.
2. Build prompts following the split instruction style (background → reasoning → rule collection).
3. Run one GPT call per snapshot; parse outputs using simple python code generation (leveraging GPT in code mode).
4. Train a light linear model on binary features and ensemble if desired.

In short, by mimicking how experts first consult their mental rulebook and then test it against clinical evidence—or your own data samples—FeatLLM turns raw numbers into distilled decision logic that works well even when data are scarce.

# Rule‑Based Features vs. Heavy‑Weight Models: Why Simplicity Wins in Low‑Shot Scenarios

In the era of gigantic language models (LLMs) it is tempting to treat them as black‑box predictors for every task: feed the raw table into the model, let it spit out a probability, and repeat for every new row.  In practice, however, this approach is expensive and fragile when you have only a handful of labeled examples – a situation that appears in medicine, finance, and many other domains where data collection is costly.

A recent paper proposes a different philosophy: **use the LLM only once to design a new feature space**.  The resulting model is a light‑weight linear classifier that runs locally, without extra LLM calls during inference.  I’ll walk through why this “rule‑based” design is especially powerful when labelled data are scarce, and how it compares to the usual tree‑based or gradient‑boosted models.

---  

## 1. The Problem with Heavy‑Weight Baselines in Low‑Shot Regimes

### 1.1 Overfitting with Few Labels
Tree ensembles (Random Forests) and boosted trees (XGBoost) learn highly non‑linear decision boundaries by repeatedly partitioning feature space.  To decide whether to make a split, they scan over many possible thresholds and evaluate each using a criterion such as Gini impurity or log‑loss.  When you only have a handful of labelled rows, any test statistic you compute will be wildly noisy; the model learns idiosyncratic quirks in those few rows that do not generalize.

The classic result from statistical learning theory tells us that model complexity should track the amount of data: high capacity models need many samples to estimate parameters reliably (`k`-fold cross‑validation can’t help if `k` is smaller than the number of unique tree leaves).  Consequently, the AUC for a 4‑shot XGBoost often falls well below its 32‑shot counterpart.

### 1.2 Uncontrollable Feature Engineering
Typical tabular pipelines rely on human‑crafted preprocessing:
- Imputation for missing values
- One‑hot encoding for categoricals
- Interaction creation

All these steps are tuned exhaustively or via grid search on large validation sets.  With only a handful of labels this tuning turns into volatile guesses rather than evidence‑based decisions.

---

## 2. Rule + Linear: The FeatLLM Architecture

The key insight of FeatLLM is **decompose the problem**:

| Step | What is learned | What the LLM does | What the linear classifier does |
|------|-----------------|-------------------|----------------------------------|
| 1 | Identify *conditions* that isolate each class | Generate natural‐language “rules” from few examples + prior knowledge | Convert each rule into a binary column (0 / 1) |
| 2 | Learn weights for these conditions | N/A | Fit a non‑negative weight vector `w_k` per class over all binary features |

### 2.1 Why Rules Are Powerful with Few Labels

1. **Sparsity Enforces Regularization**  
   A rule either triggers (`1`) or not (`0`). Each row has only a handful of active rules (typically ≤ 10), so each training example updates very few weights. This low‑dimensional signal means the linear model has fewer parameters to infer – it can learn weighted sums even from tiny datasets without overfitting.

2. **Leverage Prior Knowledge**  
   The LLM brings centuries of statistical intuitions (e.g., “older patients have higher hypertension risk”) into the rule generation step. The formula
   \[
   \text{logit}_k^i = \max(\mathbf{w}_k,0)\!\cdot\! \mathbf{z}_k^i
   \]
   ensures that even if some rules are spurious, their associated weights can be driven toward zero during training; only rules that explain the data receive large positive weights.

3. **Avoid Feature Stacking**  
   A tree algorithm must repeatedly unroll interactions among all raw columns; here we let the LLM decide *interesting* interactions before training begins.  The resulting binary feature vector is compact (≈ R​= ≥ 10 per class), usually far smaller than one‐hot encoded columns plus semantically meaningless combinations.

---

## 3. Empirical Comparison on Public Datasets

The authors evaluated FeatLLM against nine baselines across thirteen tabular datasets varying in size and dimensionality:

| Method | Query Type | Training Sample Size | Core Idea |
|--------|------------|----------------------|-----------|
| Logistic Regression / XGBoost / RF | Classical parametric / ensemble trees | From `k=2` up to `k=32` shots | Linear/logistic or boosted decision trees |
| SCARF / STUNT / TabPFN | Unsupervised/transfer learning amplifiers | Same limited labelled set plus auxiliary unlabeled data | Synthetic augmentation or transfer |
| In-context / TABLET / TabLLM | Straightforward LLM inference per row / tuned LLMs | Same limited set + API calls per sample | End‑to‑end language model predictions |

**Result Overview:**  
With only four labelled instances (4‐shot), FeatLLM matched or surpassed conventional models trained with *32* labelled instances – an order‐of‐magnitude improvement in label efficiency.

For example:

- *Adult* dataset: FeatLLM’s AUC ≈ 0.87 at `4` shots vs 0.80 for XGBoost at `32` shots.
- *Myocardial* dataset: FeatLLM’s AUC ≈ 0.94 at `4` shots vs 0.90 for XGBoost at `32` shots.

Meanwhile, heavier LLM baselines such as TabLLM struggled on high–feature datasets (e.g., *Communities*) because they needed to serialize all columns into prompts that exceed token limits.

---

## 4. Training Time & Inference Cost

A crucial trade‑off is not simply model accuracy but also computation:

- **Training:** FeatLLM needs **≈ 30 API calls** (one per bagged trial) with GPT ‑3.5‐turbo‐0613 threshold setting; this is inexpensive compared to boilerplate cross‑validation.
- **Inference:** Once rules are extracted and binary features engineered locally, predictions use a single dot product and softmax per sample – fast enough that inference time matches conventional linear regression.
- **Opposing Methods:** In contrast, In-context + TABLET + TabLLM require an API call for every prediction – latency multiplies by dataset size, making them impractical for real-time workloads.

---

## 5. Why Non-Negative Linear Weights Matter

During training, weights are projected onto non-negative subspace:
\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\!\cdot\!\mathbf{z}_k^i .
\]
This design combats two typical pitfalls:

1. **Negative Influence of Wrong Rules**  
   If a rule accidentally aligns with noise, its weight gets clipped to zero instead of driving down logit scores.

2. **Interpretability**  
   Each class’s weight vector directly tells you *which* rules matter most – e.g., “Age > 60” might carry weight 0\.78 for ‘Heart Failure’, signalling domain insight we can hand off to clinicians or auditors.

Unlike default tree models whose leaf interpretations involve many nested splits (harder to parse), linear weights combine transparent signals into an easily understandable scoring rule set.

---

## 6. Bagging & Ensemble Promote Robustness

Given any single query may misinterpret cluttered prompts or generate ill-defined rules (the paper noted up to ~ 2 % spurious rules when spurious columns were added), FeatLLM invokes *bagging*:  

- Randomly sample subsets of features / shots
- Run LLM inference separately per subset
- Average final softmax probabilities across trials

Empirically this reduces variance: on datasets with > 100 attributes neural prompts still produce coherent rule sets after filtering extreme tokens and sampling balances between categories.

---

## Concluding Thoughts

In low-shots landscapes where labels cost money and time:

| Traditional Tree/GBDT      | Weighing bare rules + lightweight linear |
|----------------------------|------------------------------------------|
| Pro: Strong on many labels; handles arbitrary interactions automatically | Pro: Imposes strong regularization via sparsity; directly leverages prior knowledge |
| Con: Overfits heavily with few labels; needs serialization of all columns in prompt limits -> long run times; obscured decisions due to depth hierarchy | Con: Requires careful formatting & parsing logic; dependent on LLM’s natural language generation stability |

The experimental evidence strongly favors the latter path when data are scarce but useful domain knowledge is abundant in pre-trained models like GPTs.

Rule-based features essentially perform *conceptual feature engineering* via synthetic demands (“Is age > 60? Is cholesterol high? …”), then let a simple probabilistic layer prioritize those concepts adaptively given scarce feedback.

If your next project involves tabular classification with limited annotations—think clinical risk scoring or credit risk assessment—the rule-centric method may give you higher AUC faster while keeping computational budgets empty enough for other tasks such as audit logs or real-time alerts.

--- 

**Takeaway:**  
When labeled data stall your growth curve, invest in lightweight models built upon concise rule definitions derived from powerful language models rather than bootstrapping deep ensembles on noisy sparse data streams—simplicity wins not only in speed but also in statistical reliability under constraintful conditions._END_



# Ensembling by Bagging Rules: Making LLMs Robust to Noise and Prompt Size Limits

Modern tabular data rarely come in tidy spreadsheets. They can contain dozens, even hundreds of columns, each with a different data type and an idiosyncratic meaning. When we try to hand–code a feature‑engineering workflow for such data, the task quickly becomes tedious and error‑prone. On top of that, many state‑of‑the‑art few‑shot learning systems use large language models (LLMs) at inference time, forcing every prediction to travel through a gigantic neural net. This is costly and, more importantly, violates the prompt‑size limits that LLM APIs impose.

The *FeatLLM* framework tackles both problems in one elegant move: **bagging** the data to build **ensembles of rule sets**. Below we unpack how this idea works, why it matters for noisy or high‑dimensional tabular sets, and what it means for real‑world deployments.

---

## 1. Why rules instead of raw features?

FeapLLM’s core idea is simple: let the LLM do the heavy lifting *once*—to derive a handful of interpretative *rules* that capture the relationship between features and the target label. For example, on a heart‑disease dataset the model might output:

> “Rule 1: *If age > 60 AND systolic blood pressure > 140 then risk = high.*”

Instead of training a deep network on raw columns, FeatLLM truncates these natural‑language conditions into binary features that indicate whether each rule applies to a given sample. Then a lightweight linear model learns how much each rule contributes to the final probability.

Advantages:

| **Reason** | **Conventional Approach** | **Rule‑Based FeatLLM** |
|------------|--------------------------|------------------------|
| Inference cost | Every sample runs a 175B parameter model | A tiny 2‑layer perceptron |
| Prompt size | Must serialize all columns per sample | Only the **few chosen columns** that sit inside each rule |
| Noise robustness | All columns influence logits directly | Only rules that survive filtering are learned |

So far so good… except when our dataset threatens to overflow an LLM’s token budget or riddles us with irrelevant features.

---

## 2. The problem of prompt size and spurious correlations

Large language models (GPT‑3.5, GPT‑4…) are great at **understanding context**, but only up to their native *context window*: ~4K tokens for GPT‑3.5-turbo/0613 and ~32K tokens for GPT‑4-turbo-1106 (depending on the API level). A tabular record with 200 numeric columns, each converted to a “`feature_i is value`” string, can easily burn through this budget.

Separately, tabular learning is notorious for picking up *spurious correlations*, especially in low‑shot settings where every single datapoint carries undue influence. An LLM that naively concatenates many columns will hallucinate rules that exploit noise rather than true signal.

Both challenges point to one solution: **reduce data per query without losing information**.

---

## 3. Bagging = random subsets; ensembles = averaging

### 3.1 How bagging works in FeatLLM

1. **Randomly sample K examples from the training set** (the few shots we have).  
2. **Randomly sample M column indices** (from the full feature set).  
3. Feed those K examples + M columns into an LLM query with a carefully crafted prompt (see next section).
4. Parse the returned “rules” into binary features for *all* samples in the dataset.
5. Train (or simply weight) a lightweight classifier on those binary features.
6. Repeat steps 1–5 T times → you get **T distinct models** each trained on different subsets of data/columns.

Notice: because each query contains only M columns, its text length is drastically shorter than if we fed all d columns at once.

### 3.2 Preventing prompt overflow

Suppose `d = 200`. If we can only fit `M = 20` columns without hitting token limits, each query focuses on a *subset* of possible relationships (e.g., age vs blood pressure vs cholesterol). Over T=20 iterations you end up covering all columns multiple times but never exceed context limits in any single run.

This strategy is analogous to “feature bagging” in Random Forests: each tree sees only part of the attribute space and learns its own weak hypothesis which we later ensemble.

### 3.3 Mitigating spurious correlations

Because each subset contains a random mix of potentially noisy and informative columns, many *spurious* rules will be generated across ensembles but are unlikely to:
- Appear consistently across many bagged models.
- Receive high importance weights when training the linear wrapper.

During ensembling we average probabilities from all T models—this is essentially a *vote* by diverse rule sets that have seen different feature contexts. The net effect:

- Rules invented from truly predictive patterns show up repeatedly → higher summed weight.
- Noise‑only rules vanish as their contribution gets washed out by averaging.

Empirical studies on synthetic datasets where unrelated noise columns were injected show FeatLLM’s performance degrades far less than other baselines that process all features directly through an LLM or use classical tree ensembles alone.

---

## 4. Prompt design inside each bagged query

A key part of FeatLLM’s success is how it instructs the LLM to produce rules from sparse information:

1. **Basic info block** – task question (“Does this patient have high BP?”), column names + definitions (value type + short description), plus K serialized examples (“Feature X is …; Answer: Yes”).

2. **Reasoning instruction block** – two steps:
   - Step 1: Identify causal or statistically meaningful connections between features and target using *general knowledge*, not demos.
   - Step 2: Using demos & Step 1 insights, craft up to `R=10` explicit rules per class using concise syntactic templates (`if <condition> then class`).

3. **Response format block** – enforce numbered list with `<condition>` expressed using standard operators (`>`, `<`, `==`) so parsing can be deterministic.

The reasoning instruction gives the LLM room to apply its world knowledge while keeping focus away from idiosyncratic noise in special columns—a real boon when dealing with domain‐specific jargon that might otherwise mislead raw feature embeddings.

---

## 5. Setting it up step by step

Below is an annotated pseudocode sketch illustrating one bagged iteration:

```python
def bagged_iteration(data, feature_defs):
    # Random subsets
    shots = random.sample(data.train_samples, K)          # e.g., K=4
    cols   = random.sample(range(len(feature_defs)), M)   # e.g., M=20

    cfg = {
        'shots': shots,
        'cols': cols,
        'feature_defs': [feature_defs[i] for i in cols]
    }

    prompt = build_prompt(cfg)
    response = llm_generate(prompt,
                            temperature=0.5,
                            max_tokens=512)

    rules = parse_rules(response)
    binary_features = generate_binary_features(data.all_samples, rules)

    # Linear weight learning / inference
    w = train_linear_weights(binary_features[shots], y[shots])
    probs = softmax(binary_features @ np.maximum(w,0))
    return probs
```

Running this loop `T` times gives you an array of probability maps which you simply average for final predictions.

---

## 6. Real-world implications

### 6.1 Lower cost & latency
- Once training finished (a handful of API calls), inference involves only simple matrix multiplications.
- No per‐sample LLM routing → dramatic savings on compute credits or API calls (especially valuable with paid GPT APIs).

### 6.2 Scalability
- Works seamlessly with high-dimensional datasets (`d > 200`) because each query uses only `M` columns.
- If your corporate dataset grows over time, you can retrain FeatLLM faster thanks to its lightweight downstream learner.

### 6.3 Interpretability
- Each rule is human-readable; you can audit which conditions matter most via learned weights.
- Lawful compliance audits become easier compared to blackbox deep nets trained directly on raw tables.

### 6.4 Robustness
- Real datasets often possess hidden biases or stray engineered variables.
- Bagging+ensembling tends to dilute contamination from isolated spurious features—leading methodology for industry deployments where label noise cannot be avoided entirely.

---

## 7. Takeaway checklist

| ✅ | What does FeatLLM do differently? |
|----|-----------------------------------|
| Use LLMs as day‑one feature engineers → rules instead of raw numbers |
| Apply two-step reasoning prompt → leverages prior knowledge before seeing data |
| Generate multiple rule sets via bagging → each covers different feature subsets |
| Adaptively limit prompt length | Only M relevant columns per query |
| Ensemble simple linear models → low latency prediction |
| Naturally filter out noisy correlations | Cross-model consistency boosts signal |

If you’re building a low‑shot tabular predictor and want to keep costs low while staying robust against noisy data and API token limits, give this bagged–rule ensemble approach a try!

# Practical Trade‑Offs: Training Time, Inference Speed and API Costs for FeatLLM

## Why the runtime profile matters

In a real production environment you rarely have the luxury of flexibly paying for “expensive” inference every time a new tabular record arrives.  For many use‑cases – from credit‑risk scoring to medical triage – the latency budget is tight and the number of model queries can quickly become a cost driver.  The FeatLLM framework was specifically crafted to keep these constraints in check while still leveraging the rich world‑knowledge stored inside large language models (LLMs).

Below we dive into how FeatLLM stacks up against other LLM‑based tabular methods in three key dimensions:

1.  **Training cost** – How many API calls are required to generate the rule set?
2.  **Inference latency** – How long does it take to score a single new record once the model is frozen?
3.  **API budget** – What does the per‑sample budget look like compared to end‑to‑end LLM approaches?

These figures come from the benchmark experiments reported in the original FeatLLM paper (trained on GPT‑3.5‑turbo, but all trends hold for any comparable LLM).

---

## 1. Training cost – a handful of API calls

| Method | #API queries | Notes |
|--------|--------------|-------|
| **FeatLLM** | **30** (or *T* = 20 ensembles × *R* = 10 rules) | Each query pushes the LLM to produce a set of rules; no fine‑tune needed |
| In‑Context Learning | *N* samples per inference | Requires one query per test record; no separate training phase |
| TABLET | *N* queries (one per test sample + extra tuning) | Needs an external classifier and extra prompts |
| TabLLM (IA3) | **≈ 30–50** queries (post‑pretraining) | Fine‑tuning step still uses very few forward passes |

On a low‑shot task with *k* = 8 labeled examples, FeatLLM’s 30 queries are essentially “just one round of prompting” – each query is only a dozen seconds of wall‑clock time on an A100 GPU when using the OpenAI API.

> **Impression**  
> Even if you pay $0.25 per thousand tokens (the current OpenAI rate), FeatLLM’s total training cost for a single envelope dataset stays under $0.01, which is *far below* that of even a single fine‑tune cycle or multiple in‑context predictions.

---

## 2. Inference speed – sub‑millisecond latency

When deployed, FeatLLM turns an incoming record into a handful of binary features and then applies a tiny linear model:

\[
\mathbf{p}^i = \text{Softmax}\Bigl(\bigl[\max(\mathbf{w}_k,0)\!\cdot\!\mathbf{z}^i_k\bigr]_{k=1}^{c}\Bigr)
\]

where $\mathbf{z}^i_k \in \{0,1\}^{R}$ is obtained by evaluating the LLM–generated rules locally.

### Benchmark numbers (Adult dataset, $k=16$)

| System                 | Throughput (samples/s) | Latency per sample |
|------------------------|------------------------|--------------------|
| **FeatLLM**            | ~ 150 000              | ≈ 6 µs              |
| Logistic Regression    | ~ 300 000              | ≈ 3 µs              |
| XGBoost                | ~ 45 000               | ≈ 22 µs             |
| Random Forest          | ~ 15 000               | ≈ 68 µs             |
| In‑Context Learning    | ~ 6                    | > 7 s               |
| TABLIT                 | ~ 6                    | > 7 s               |
| TabLLM                 | ~ 3                    | > 8 s               |

> **Why it is so fast**  
> - The rule generation phase happens *once* and is captured in a static binary matrix.  
> - No tokenisation or prompt assembly is needed at inference time; everything is local Python computation.

Even when scaling up to datasets with >100 features, FeatLLM remains within tens of microseconds because each rule only looks at one or two attributes.

---

## 3. API budget during production

With FeatLLM you only reach out to the LLM during training – not for every new tabular row:

- **Training phase**: Approximately *T × R* queries (~30).  
- **Production phase**: Zero LLM calls; all work is done on-premise or on cloud instances you already provision.

Contrast this with other LLM‑based baselines that must hit the API *once per prediction*:

- In‑Context: One call ⇨ ~$0.25/token × N$ tokens per sample ⇒ dozens of cents per prediction if you have thousands of samples in batch mode.
- TABLIT / TabLLM: Same situation plus additional callbacks for ensemble aggregation.

For high‐throughput services this difference becomes critical:

- A website that scores 10⁶ real-time requests per day would pay ~\$250×10⁶ tokens ≈ \$250 k/month with in‑context alone.
- The same workload running on FeatLLM would incur virtually no additional costs after the initial training burst.

|------------------------------------------|--------------------|
| You only have a few labeled samples      | FeatLLM           |
| You need ultra-low latency (<1 ms)       | FeatLLM / Linear Norm |

In short, **FeatLLM offers an excellent trade‐off for data‐hungry but inference‐light workloads where you want to profit from LLM knowledge without paying for continuous API usage**.

## Takeaway & next steps

- **Keep an eye on rule quality** – If you observe too many irrelevant rules pop up (e.g., because your domain data are noisy), increase your bagging level or reduce `R`.
- **Explore hybrid pipelines** – For datasets with more than ten thousand records, consider using an off–the–shelf tree or neural network trained on the binary rule features; you’ll still inherit the interpretability thanks to transparent rule generation.

# What do the Rules Really Tell You?  
## Insights from Feature Quality Analysis

When a language model like GPT‑3.5 is asked to turn a handful of data points into human‑readable “rules,” it can appear almost alchemic: it knows which columns matter, which conditions signal a positive label and which do not.  
In *FeatLLM*, those rules become binary features that a tiny linear model later scores. A natural question arises: **how useful are the rules themselves?**  
To answer, the authors measured how well each rule‑derived feature correlates with the target label **before** any learning takes place, and then examined how the linear layer weights change after training.

---

## 1. Measuring native rule quality with AUROC

For every rule generated by the LLM, we check:

| Sample | Rule value (0/1) | Ground‑truth label |
|--------|------------------|--------------------|

From this we compute an **AUROC** – a standard single‑threshold‐free measure of how well the feature discriminates between classes.  
If a rule’s AUROC is above 0.5, it is *informative*; below 0.5 it tends to be misleading or useless.

Across 13 diverse tabular datasets (ranging from credit‑risk to medical diagnosis), the key observations were:

| Dataset | #rules | Avg AUROC (before tuning) | % Rules with AUROC > 0.5 |
|---------|--------|---------------------------|--------------------------|
| Adult   | 10     | 0.61                      | 80 %                     |
| Bank    | 10     | 0.59                      | 78 %                     |
| Blood   | 10     | 0.63                      | 82 %                     |
| …       | …      | …                         | …                        |

- **High baseline quality:** On average, more than **80 %** of rules were informative even before any training.
- **Dataset dependence:** Sparser datasets (e.g., *Heart*) still achieved >70 % informative rules, indicating the rule generator is robust across domains.

These numbers mean that the LLM is not randomly guessing; it is actually retrieving real patterns encoded in its training data and in the few examples fed to it.

---

## 2. Weight tuning cleans up noise

Once all rules are turned into binary features, FeatLLM trains a *positive‑weights* linear layer:

\[
\text{logit}_k = \max\!\bigl(\mathbf{w}_k,\,0\bigr)\;\cdot\;\mathbf{z}_k ,
\]

where \(\mathbf{z}_k\) is the binary vector for class \(k\).  
Training minimizes cross‑entropy on the few labelled examples.

What happens during this step?

1. **Informative rules get high weights** – their signal aligns with the target and thus contributes strongly.
2. **Noisy or irrelevant rules shrink to near zero** – they do not help reduce loss, so their learned weight falls close to the ε‑threshold (empirically set at 0.1).

The study quantified this effect:

| Dataset | % Rules with weight > 0.1 (post‑tuning) |
|---------|---------------------------------------|
| Adult   | 75 %                                  |
| Bank    | 78 %                                  |
| Blood   | 81 %                                  |

Notice that only a tiny fraction of the originally uninformative rules survive weight tuning; most drop out automatically. The linear model therefore acts as an implicit **feature selector**.

---

## 3 Why does this matter?

### a) Explainability
Each surviving rule can be inspected directly:
> “Blood pressure \(>\) 140 and Smoking history = Yes → increases risk of heart disease.”

Because the rule’s contribution weight survives pruning, we know it actually matters for predictions.

### b) Robustness to spurious columns
Adding irrelevant features (as in the *Heart* + *Adult* experiment) changes few rules’ AUROC but rarely any survive tuning unless they accidentally capture a real correlation. Thus FeatLLM shows resilience against noisy data.

### c) Efficiency
The two‑step pipeline—rule extraction followed by lightweight learning—avoids expensive per‑sample LLM calls during inference while still leveraging its reasoning strengths.

---

## Take‑away

The empirical analysis proves that FeatLLM’s LLM component does more than churning out random sentences: it identifies real, discriminative conditions that translate into meaningful binary features. The subsequent weight tuning further refines this by automatically discarding noise, leaving a concise set of powerful predictors ready for quick inference.

In short, **the rules really do tell you something useful**—and you can trust them enough to rely on them when data are scarce and labeling effort is costly.



# Future Directions: Going Beyond Binary Rules and Scaling to Large Datasets

## Overview

The *FeatLLM* framework demonstrates that a large language model can act as a feature‑engineering oracle for few‑shot tabular tasks: it extracts human‑readable rules, turns them into binary features, and trains a tiny downstream model. While the results on 13 diverse datasets are impressive, the current design is bounded by **binary rule‑based features**, **two‑class or class‑specific rule sets**, and **training on small sample sizes**.  In this post we explore concrete research directions that could unlock the next generation of LLM‑powered tabular learning:

1. **Extending feature types** beyond binary indicators – continuous transformations, discretisations, and high‑cardinality encodings.  
2. **Scaling to large tables** (tens of thousands of samples and hundreds of attributes) while overcoming prompt limits.  
3. **Broadening rule granularity** to multi‑class decision logic and local explanations.  
4. **Embedding interpretability metrics** into the rule generation process itself.  
5. **Critically assessing bias amplification** that may arise when LLMs substitute domain expertise.

Below we discuss these ideas in technical detail, showing how they dovetail with the core *FeatLLM* pipeline.

---

## 1. Richer Feature Transformations

### 1.1 Continuous Thresholding

In the original design, each rule yields a Boolean value (`0/1`).  However, many tabular problems thrive on *numeric thresholds* (e.g., “age > 45”) rather than binary indicators alone. A straightforward extension is to let the LLM output *operator plus numeric constant* pairs (`>`, `<`, `≥`, `≤`) and use them directly in code generation:

```python
if age > 45:
    feature_age_high = 1
else:
    feature_age_high = 0
```

The parser can accept an optional *threshold* block in the response text:

```
Rule: IF age > 45 THEN class=HighRisk
```

By enriching each rule with an intensity measure (e.g., continue scoring by `logit = w * (age - 45)` for age values above the threshold), one obtains soft features that better capture gradient effects.

### 1.2 Polynomial / Interaction Terms

When two variables jointly influence the target (e.g., “BMI × Age”), a single Boolean rule may be insufficient. The LLM can be coaxed to propose *interaction rules* by adding a second step in its reasoning chain:

```
Step 2 – Combine relevant features using AND/OR to form composite conditions.
Example: IF BMI > 30 AND age < 50 THEN probability of diabetes increases.
```

The generated code then calculates `feature_bmi_age = int(bmi > 30 and age < 50)`, while static analysis tools can be used to verify correctness.

### 1.3 High‑Cardinality Encoding

Categorical predictors with many levels (e.g., ZIP codes or product IDs) are hard to handle with simple `==` comparisons. We can ask the LLM to chunk them into meaningful groupings (“Urban”, “Rural”, “Suburban”) via association rules or via a frequency‑based grouping strategy:

```
Rule: IF country_code IN {US, CA} THEN region=NorthAmerica
```

Here the rule title becomes an entire *one‑hot vector* for each new group.

#### Implementation Hint
Wrap each categorical feature into a Python function that maps its raw value into an integer ID; let the LLM output mapping dictionaries or, alternatively, approximate using squash functions like `label_id = hash(category_value) % N`.

---

## 2. Scaling up: Bagging + Sharding

The original paper uses bagging over subsets of training examples to mitigate prompt size constraints. For even larger datasets we recommend:

1. **Feature Sharding** – Split columns into disjoint shards (`Shard_1`, `Shard_2`, …). Feed each shard separately into an instance of FeatLLM, obtain shard‑specific rule sets, then concatenate their outputs to form a union of engineered features.

2. **Sample Sharding** – When volume is high but we have many classes or features, break up training examples into multiple shards; run FeatLLM in parallel across computational nodes under Spark/Hadoop frameworks.

3. **Hierarchical Bagging** – First bag across samples, then across shards; combine base models through majority voting or weighted averaging based on validation loss.

4. **Prompt Compression** – Use automatic summarization or tokenization strategies such as removal of repeated static description blocks across shards; save characters that will not affect rule generation.

---

## 3. Multi‑Class Decision Logic

Presently FeatLLM produces separate rule sets per class but only returns a binary presence vector for each class independently. With more than two classes there is often *interference*: another class’s rules may dominate \(\hat{p}\). One approach:

- **Decision Tree Coupling:** After acquiring per‑class binary flags \(Z_k\), train a lightweight decision tree over these flags rather than sum them linearly.
  
- **Softmax over Weighted Sums:** Keep Eqn (1) but also allow cross‐class weights \(w_{k,r}\), where \(k\) is class index and \(r\) is feature index—i.e., each feature can contribute positively or negatively to different classes.
  
- **Joint Multiway Rules:** Ask the LLM to produce *clauses with multi‑output heads*, e.g.:

```
IF age > 60 THEN class=Senior & risk=High
IF bmi < 18 THEN class=Underweight & risk=Low
```

These multi‑head rules will create overlapping binary vectors (“senior*” vs “underweight*”) which encode richer relationships during downstream inference.

---

## 4. Interpretability Integrated Into Rule Generation

A key advantage of FeatLLM is that all decisions are explainable when they are hard rules (“if A then B”). To deepen interpretability:

- **Use Explainability Constraints in Prompt:** Add a clause such as “Provide at most three conditions per rule” or “Ensure no overlapping conditions within a single rule set.” This keeps rules short and human‑readable.

- **Quantify Rule Strength:** Let LLM output expected confidence (e.g., “This rule holds in about 85 % of training samples”). The parser can capture this as metadata.

- **Generate Counterfactuals:** Ask the LLM: “For a sample not satisfying any rules for ‘Positive’, what minimal change would flip its prediction?” The output can be parsed into additional corrective rules that gives actionable insights.

By explicitly collecting interpretability metrics during generation, researchers can decide which models should be used in regulated domains (finance, health).

---

## 5. Bias & Fairness Considerations

Because FeatLLM relies heavily on an LLM’s prior knowledge learned from massive text corpora, unexamined biases may seep into generated rules:

- **Monitoring Disparate Rule Quality:** Compare average AUROC contributions (Section 5.D) across protected groups; flag any skewed high/low performance.

- **Bias Mitigation Prompting:** Add instructions like “Avoid using gender or race attributes directly unless they contribute logit >0.5 after pruning.”

- **Post‑hoc Auditing:** Once binary features are generated, run fairness tests (e.g., demographic parity) before training downstream models.

In future work integrating these audit steps into the FeatLLM pipeline will help ensure socially responsible deployments.

---

## Closing Thoughts

The beauty of FeatLLM lies in its simplicity: leverage an LLM’s world knowledge to manufacture tailored features; then let traditional ML take over inference. By extending from binary thresholds to richer numeric and categorical transformations, scaling through sharding and bagging, accommodating multi‑class logic, embedding interpretability constraints directly into prompts, and actively monitoring bias discovery we can evolve FeatLLM into an end‑to‑end framework suitable for real enterprise workloads with tens of thousands of records and dozens of attributes. These extensions would retain low inference cost while drastically widening applicability across domains—from genomics panels requiring complex interaction terms to finance pipelines handling thousands of risk factors—making LLMs true partners for data scientists working with limited labeled data.
