\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 2: 10. Ensemble with Bagging – Mitigating Prompt Size & Robustness Issues

The heart of a \textsf{FeatLLM} pipeline lies in the repeated invocation of a large language model (LLM) to generate classification rules from a handful of labeled examples. Each invocation produces a new set of binary features, which are then interpreted by a lightweight downstream learner. Because the rules themselves are stochastic—driven by sampling from the LLM’s softmax distribution—the individual rule sets can differ substantially from one call to another. Rather than treating a single call as definitive, \textsf{FeatLLM} exploits this stochasticity by executing the entire rule‑construction–learning pipeline multiple times and aggregating the resulting predictions. This chapter explicates the mechanics of this ensemble strategy, with particular emphasis on how it addresses two recurrent challenges in the domain: (1) the ever‑present problem of LLM prompt size limits and (2) robustness against overfitting or spurious pattern capture in extremely low‑shot settings.

## Rationale behind Multiple Independent Runs \(T \rightarrow \{w[t]\}\)

In a conventional supervised learning workflow, the learning algorithm produces a single set of parameters \(\mathbf{w}\) that map input features to class probabilities. The \textsf{FeatLLM} framework diverges on two fronts: (i) features are not hand‑crafted but generated by an LLM; and (ii) each feature generator run may produce a slightly different rule set \(\{\mathbf{z}^{(t)}\}\). Structuring training as \(T\) independent runs—each yielding its own weight vector \(\mathbf{w}[t]\)—creates a family of *weak learners*. By averaging their probabilistic outputs,

\[
\bar{\mathbf{p}}^i = \frac{1}{T}\sum_{t=1}^{T}\text{Softmax}\!\left(
   \max(\mathbf{w}[t],0)\cdot\mathbf{z}_k^{i,t}
\right),
\]

the ensemble harnesses **variance reduction** akin to classic bagging. Even if one rule set misinterprets or over‑fits to random idiosyncrasies in the few-shot demonstrations, its influence is diluted by correct hypotheses generated elsewhere. Moreover, because each run is conceptually independent only through the same few-shot data and feature descriptions, we avoid the need for any inter‑run communication or shared parameters beyond simple probability averaging—an attractive property when LLM calls are expensive.

## High Temperature Sampling Increases Rule Diversity

The temperature hyperparameter \(t_{\text{temp}}\) controls the entropy of the LLM’s output distribution. A higher temperature yields more varied linguistic constructs and potentially more diverse logical expressions in the generated rules, whereas a temperature close to zero forces the model toward deterministic, high‑confidence responses at the expense of novelty.

By setting \(t_{\text{temp}}\) adequately above zero (e.g., 0.5–1.0 as recommended in the paper), we intentionally induce **rule diversity**: each run may propose distinct subsets of feature predicates, even when operating on identical few‑shot samples. This variation is crucial for creating an effective bagged ensemble: it ensures that each weak learner contributes non‐redundant predictive information. Experimental analyses in Section 8 illustrate that lower temperatures shrink performance because many disparate rules collapse into similar ones, diminishing ensemble gain.

## Randomized Demonstration Order – Evidence on Path Dependence

LLMs exhibit path dependence; that is, the order in which training examples appear in prompts influences their tentative reasoning steps. This phenomenon has been documented empirically (e.g.,  The order swapping can change whether “Age > 50” or “Diabetes” appears first in derived rules). To capitalize on this effect without being accidentally trapped in any specific ordering bias, \textsf{FeatLLM} shuffles demonstration examples before each run.

Practically, this means that even if we fix temperature and keep other conditions constant, changing merely the sequence invites different reasoning trajectories through chain‐of‐thought processes encoded implicitly inside the LLM. By repeating this random shuffling over \(T\) runs, we effectively produce a richer sampling over potential reasoning pathways—bolstering our ensemble’s exploration across plausible hypothesis spaces.

## Feature Bagging: Sampling a Subset of Features per Run

Large tabular datasets often contain dozens or hundreds of attributes; serializing all into a prompt can exceed token limits or degrade inference quality due to length constraints. Feature bagging mitigates this by selecting randomly a subset \(B_f^{(t)}\subseteq \{1,\dots,d\}\) for every run \(t\). Only features residing in \(B_f^{(t)}\) will appear in both the *basic information description* part of the prompt and may be considered when generating rules.

From an algorithmic point of view:

1. Sample \(B_f^{(t)}\) uniformly at random without replacement.
2. For each run:
   - Construct prompt with only features in \(B_f^{(t)}\).
   - Generate rules applicable to those features.
3. After training linear weights \(\mathbf{w}[t]\), evaluate on test data using only features belonging to that bag.

This scheme offers two intertwined benefits:

- **Memory safety**: The serialized prompt stays within allowed token budgets.
- **Robustness**: Different runs focus on distinct “views” of feature space; if one bag inadvertently discards highly predictive columns due to randomness, other bags will compensate.

Investigator Biases observed that certain complex tables (e.g., Communities with > 100 columns) achieve near‐state‑of‑the‐art accuracy with only 3–5 bags rather than needing tens because even small random subsets often capture many key predictors.

## Instance Bagging: Sampling a Subset of Training Examples per Run

While feature bagging tackles token limits related to attribute cardinality, instance bagging addresses noise amplification when few labeled shots are available. In additive bagging:

1. Sample with replacement \(N_{\text{sub}}\approx N_{\text{k-shot}}\times b_{\!i}\) examples for run \(t\); here \(b_{\!i}\in(0,1]\) controls bag size.
2. Use these instances both for prompting (demonstrations) and for fine‑tuning weights.

Since each instance has a probability \(q=(1-b_{\!i})^{N_{\text{sub}}}\) not affecting any given run's sampled set, repeated runs produce diverse empirical distributions over output weights \(\{\mathbf{w}[t]\}\). This randomness disrupts overfitting patterns that might arise if all training instances are always leveraged identically while still preserving enough data for stable weight estimation.

Empirically setting \(b_{\!i}=0.\!5\)-\(0.\!7\) balances fidelity (retaining enough labeled pairs explainable by prior knowledge) with variation needed for robust aggregation.

## Prediction Aggregation by Averaging Softmax Probabilities across Ensembles

After training multiple weak learners, each mapping its own binary rule‑feature space into class probabilities via Equation (6), we combine their outputs using plain arithmetic averaging:

\[
p^{i}_{k} = \frac{1}{T}\sum_{t=1}^{T}
   \operatorname*{\mathbb E}_{\theta_t}
   [\,P(\hat y_k = 1 | x^i; w[t],z^{(t)}_k)\,),
]
\]

where \(\theta_t\) denotes latent nuisance variables specific to run \(t\). This particular aggregation method has several practical advantages:

- **Simplicity**: It requires no additional training beyond learning linear weights.
- **Calibration**: Softmax probabilities tend toward better calibrated outputs when averaged over many heterogeneous models—a known phenomenon originating from *model ensembling* literature.
- **Latency**: For inference time budgets constrained by API cost or hardware latency limits, parallelizing score computation across runs enables efficient streaming evaluation while keeping memory usage inversely proportional to \(T/d_{\mathrm{feats}}\).

Table 3 in Section 8 demonstrates that an average over only 10 – 20 ensembles suffices to achieve performance gains matching those obtained by far heavier approaches such as full fine‑tuning or tree ensembles on hand‑crafted features.

---

In sum, aggregating multiple LLM runs through carefully orchestrated randomness—not only across temperature and demonstration order but also via feature and instance bagging—constitutes a powerful strategy for overcoming both prompt size constraints and low‑shot instabilities inherent to rule generation from language models. By embracing this ensemble philosophy, \textsf{FeatLLM} converts seemingly fragile stochastic rule extraction into a robust predictor that retains computational efficiency at inference time—a vital property for real‑world deployments where prompt tokens translate directly into operational cost and latency._END_
