# xLSTM 101: Why Modern LSTMs are Still Killing It in Language Models  

Language models have been dominated by Transformers for years, yet a recent line of work shows that a cleverly‑refined LSTM can rival, and sometimes beat, these models while keeping the old‑school RNN advantages.  The key lies in two fairly simple innovations: **exponential gating** and a **matrix‑based memory**.  In this post we’ll break those ideas down, explain how they solve the classic pain points of LSTMs, and why doing so unlocks performance on par with today’s state‑of‑the‑art Transformers.

---

## 1. LSTMs – The Good, The Bad & The Hard Parts  

| Feature | What It Does | Why It Matters |
|---------|--------------|----------------|
| **Constant error carousel** | Adds previous cell state \(c_{t-1}\) to current input \(z_t\) using forget \(f_t\) and input \(i_t\) gates | Keeps gradients from vanishing → works for long dependencies |
| **Gating (input/forget/output)** | Controls what information flows in, out and through the cell | Adds flexibility but also limits how much the cell can “rewrite” earlier content |
| **Scalar memory** | A single value per cell | Packs everything into one dimension → poor capacity for complex patterns |

These mechanisms made LSTMs the backbone of early NLP systems.  But when the scale of language models exploded, three problems once again surfaced:

1. **Inflexible storage** – An LSTM can't *update* a stored entry when a better one shows up; it simply adds the new information on top.
2. **Limited capacity** – Compressing multi‑dimensional semantics into a single scalar forces the model to lose detail, hurting rare‑token prediction.
3. **Sequential bottleneck** – The hidden‑hidden connections cause a strict serial dependency that throttles parallel hardware.

Transforms (those self‑attention heavy WeightSanta models) solved many of these by moving all operations into a high‑dimensional linear subspace and removing hidden‑hidden recurrences.  But Transformers pay a hefty price: quadratic cost in sequence length (because every token has to attend to every other token).

xLSTM flips that trade‑off on its head: it keeps *linear* time and memory with respect to context length but overhauls the cell so it behaves almost like a Transformer in what it can remember and revise.

---

## 2. Exponential Gating – Giving the Cell a “Rewrite” Button

### Back to Basics: Standard Binary Gates
In a vanilla LSTM
\[
c_t = f_t\,c_{t-1} + i_t\,z_t,\qquad 
h_t = o_t\,\psi(c_t),
\]
with all gates \(i_t,f_t,o_t\) being sigmoid–activated (\(\sigma(\cdot)\)). Gates stay between 0 and 1; they either let or block information.

### The Problem
When you need to *overwrite* an earlier slot with something more relevant (think nearest‑neighbor search in memory), you have no control: once an item is dropped by the forget gate it’s gone forever.

### The Fix: Exponential Activation
Replace sigmoid with **exponential**:
\[
i_t = \exp(\tilde{i}_t), \quad
f_t = \exp(\tilde{f}_t)\;\text{(or}\;\sigma(\tilde{f}_t)\text{)}.
\]
Exponentials can balloon arbitrarily large or small, giving gates far more expressive power:
- A large input gate “writes” strongly.
- A small forget gate essentially **ignores** old content.
  
To keep training stable we add a *stabilizer state* \((m_t)\) that normalises the log values so we never overflow.

### Why It Helps
*Exponential gating behaves more like an *adder with dynamic step sizes*.  When you see a “better” version of something already stored, you can let the gate write it in with huge weight while diminishing older content via the forget gate.  Practically this makes xLSTM good at *state tracking*, solving formal‑language tasks (e.g., parity checks) that standard Transformers struggle with because they lack hidden‑hidden mixing.

---

## 3. Matrix Memory – Turning Scalar Capacity into Huge Memory

### From Scalar to Matrix
The core idea: replace \(c_t \in \mathbb{R}\) with \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\).  
Now we can store *pairs* of vectors directly inside the cell:
- Key vector \(\mathbf{k}_t \in \mathbb{R}^d\)
- Value vector \(\mathbf{v}_t \in \mathbb{R}^d\)

The **covariance update rule**:
\[
\mathbf{C}_t = f_t\,\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t\,\mathbf{k}_t^\top .
\]
An outer product inserts the key/value pair into memory; forgetting simply decays an entire row/column via \(f_t\).

### Retrieval
Given a query vector \(\mathbf{q}_t = W_q\,x_t + b_q\),
the hidden state becomes
\[
h_t = o_t \odot 
   \frac{\mathbf{C}_t\,\mathbf{q}_t}
        {\max(|n_t^\top q_t|,1)} ,
\]
where \(n_t = f_t n_{t-1}+i_t k_t\) is an auxiliary *normalizer* ensuring numerically stable division.

### Why It Matters
- **Unlimited capacity** – Unlike scalar cells, matrix cells can accumulate many key/value pairs without compressing them into one number.
- **Parallelism + Linear Time** – Although we work with matrices, all updates are simple outer products that GPUs compute very efficiently.  
The net effect is *linear cost* per token (no quadratic self‐attention), but *dramatically higher memorisation capacity*. In synthetic experiments (Multi‑Query Associative Recall), xLSTMS beat every non‑Transformer baseline.

---

## 4. Putting It All Together – The xLSTM Block

An xLSTM block follows the familiar residual pattern used by modern LLMs:

```
Input -> Pre/Pre-up Projection -> xLSTM Cell (sLSTM + / or mLSTM) -> Post-processing -> Residual Connection -> LayerNorm
```

Two flavours exist:

| Block | Preferred Cell | Reason |
|-------|----------------|--------|
| Post up-projection (like Transformers) | sLSTM | Keeps dimensionality linear after non-linear summarisation |
| Pre up-projection (like SSMs) | mLSTM | Cheaply fits high-dimensional memory before summarisation |

Key properties:

- **Linear complexity w.r.t context length** – No self-attention matrix; all operations are per-token additions/multiplications.
- **Constant memory per token** – Forgetting decays old keys; only matrix size does not expand with sequence length.
- **Residual & LayerNorm backbones** – Borrowed from GPT / GLaM architectures for stability when scaling up.

| Benchmark | Architecture | Avg.Perplexity |

| SlimPajama (15B tokens) | xLSTM[7:1] | ~36 👏 |
| Same data vs. GPT‑3 (350M params) | Transformer = ~51 |
| Context Extrapolation (2048→16K tokens) | xLSTM keeps <50 pplx   | Transformer rises >120 |

In large-scale language modelling experiments on 300 B tokens:

- xLSTM achieves lower validation perplexity than both large Transformers (e.g., Llama 2 $3$B) and other sequential models (RWKV 4, Mamba).
- On 571 downstream domains from PALOMA it hits lower perplexities almost everywhere.
- Scaling laws show similar power law decreases as in Transformers but consistently lower intercepts — indicating better underlying learning efficiency.

## 6. Practical Takeaways

1. **You don’t need quadratic attention to get competitive language models** — linear RNNs that smartly remix their memories do just fine.
2. **Exponential gating gives you dynamic write ability**, letting your model ‘fix’ earlier mistakes on the fly without recomputing whole sequences.
3. **Matrix memory turns every token into a tiny key/value store**, boosting rare-token recall without adding parameters.
4. **Training is straightforward** — standard AdamW + warm-up + linear LR decay; just replace your vanilla LSTM blocks with xLSTM blocks.
5. **Inference speeds up on GPU kernels**—especially for long contexts where Transformers devolve into quadratic overheads.

If you’re building an LLM for edge deployment or data-sensitive use-cases where compute budgets are tight but model quality matters, give xLSTMs a try. They hit the sweet spot between classic recurrence’s scalability and modern attention's expressiveness—without waiting for another paradigm shift.
