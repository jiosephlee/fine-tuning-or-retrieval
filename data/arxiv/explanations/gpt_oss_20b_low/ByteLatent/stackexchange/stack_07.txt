\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### "Dynamic padding" in batch construction – how does BLT keep batch sizes constant across varying patch sizes?
Question:
The training pipeline packs batches of patches rather than bytes to avoid padding expensive latent transforms. But Section 4.3 says they maintain constant average byte batch size even when varying average patch size – so they adjust sequence length accordingly. How are these two aims reconciled when histogram of patch lengths varies wildly (e.g., space vs character)? Does this lead to many very short patches and resulting inefficiencies? Precisely what padding strategy is used for local encoders/decoders vs latent transformer within one training iteration?

Answer:
**Answer**

BLT is built around two complementary ideas:

1. *Dynamic patching* – the byte sequence is split into variable‑length patches according to an entropy signal.
2. *flop‑control* – the training budget is specified in terms of floating‑point operations (flops), which means the amount of work that the model can afford per iteration is fixed.

Because the number of patches changes when you vary the average patch size, BLT has to keep the **total number of bytes** that a training iteration processes fixed (in expectation).  That is what Section 4.3 means when it says that the “average byte batch size stays constant”.  If you increase the average patch size from 4.5 bytes to 6 bytes, you simply reduce the number of patches per batch so that the product *patches × average patch size* stays equal to the target byte budget (typically 8 k or 16 k bytes for Llama‑2 or BLT‑1T data mixes).

---

### How the two goals are reconciled

1. **Patch‑level packing for the latent transformer**  
   The expensive global transformer operates on *patch tokens*.  Because its computation scales with *patch count*, BLT’s dataloader groups tokens into a fixed number of patches (`n_p`) per batch and pads or truncates **byte sequences only inside each patch** (so every patch has exactly `max_patch_len` bytes).  
   Padding at this level is inexpensive: it only involves adding a special “pad” byte embedding that never appears in attention (`mask = 0` for positions past the real length of a patch).  These padded bytes do not affect gradients because they are masked out in both self‑attention and cross‑attention.  

2. **Byte‑level padding for local encoder / decoder**  
   The local encoder processes raw byte sequences with a fixed‑window attention module (`w_E`).  When patches are longer than `w_E`, residues from one patch can spill over into the next window and may be padded.  BLT therefore pads **all encoded / decoded byte sequences to a common maximum length** that is chosen based on the longest anticipated patch in a dataset sweep (12 k or 24 k bytes in practice).  
   Unlike global padding, these byte‑level paddings are absorbed by low‑cost operations: they only trigger a few additional forward passes through one or two lightweight transformer layers; moreover, because packing is done at patch level, most of those padded bytes never reach the slow global transformer.

3. **Handling wildly varying histograms**  
   In data such as English text where a space character triggers an early patch boundary, many patches end up short (≈1–3 bytes).  Conversely, verbatim repeating blocks can produce patches tens or hundreds of bytes long.  The batch maker solves this by *dynamic batching*: it sorts examples by their anticipated byte count and forms buckets that contain roughly `target_bytes` total.  
   Inside each bucket every example is trimmed or padded so its *effective* length (after entropy pruning) matches `target_bytes`. Because patches are packed first, even if an individual example has many short patches you will still end up with roughly `target_bytes / avg_patch_size` global steps – maintaining a stable compute budget.

4. **Batch construction pipeline**

| Step | Purpose | What’s padded |
|------|---------|---------------|
| **Entropy pre‑processing** | Compute next‑byte entropies and decide boundaries | None |
| **Patch segmentation** | Split raw bytes → variable patches | None |
| **Bytes→patch embeddings** | Local encoder runs over raw bytes in windows | Padded to `max_window` |
| **Patch packing** | Assemble a fixed `n_p` patches per batch | Pad each patch to `max_patch_len` |
| **Global transformer forward/backward** | Heavy computation over `n_p` steps | None; each step uses exact patch length (masked) |
| **Decoder crosses back to bytes** | Local decoder produces output bytes | Pad output sequence to same max as encoder |

This hierarchy guarantees that

- The expensive global steps see exactly as many patches as dictated by our flop budget.
- The memory footprint remains bounded because we never hold more than `n_p × max_patch_len` positions at once.
- Short patches do not cause disproportionate memory spikes; their ownership of compute time moves from global to local layers.

---

### Concrete numbers

Suppose we target 8 k normalised byte batch size and our current average patch size is \(\displaystyle s=4.5\).  
We then need roughly \(\displaystyle \frac{8\,000}{4.5}\approx1\,778\) patches per iteration.  
If we increase \(\displaystyle s\) to 6, we cut down to \(\displaystyle \approx1\,333\) patches per iteration; all other hyper‑parameters stay unchanged.

During data loading, after entropy‐based boundary detection each example may produce very different numbers of bits:

- A snippet of code like “print(…)” yields ~6 short patches.
- A repeated table “0123456789” repeated thousands of times can be compressed into one long patch (hundreds of bytes).

The loader keeps these variations under control by:

* Sorting examples into buckets by their *raw* byte count.
* Truncating or padding within a bucket so every example has exactly `target_bytes` total.
* Packing all resulting patches (some very short) into the same fixed slot count (`n_p`) for that bucket.

Since we pack on a *per‑patch* basis rather than per-byte basis, any imbalance from very short across many examples only manifests as fewer global steps—which is precisely what we want when we increase patch size.

---

### Bottom line

BLT keeps batch sizes constant at the **byte level**, not at the number of training tokens or phrases:

- The number of *global transformers steps* varies inversely with average patch size but remains bounded because each step operates on one latent patch.
- Padding is applied:
  * at packet level for the latent transformer (cheap;
    maskable);
  * at byte level inside each encoder/decoder window
    (cheap because windows are small)
    but queried within batches that share a common breadth (`max_window`).

Thus even when histogramming gives highly divergent patch lengths—as happens between spaces and characters—BLT maintains a stable training budget while permitting variable compute allocation where it is most needed.
