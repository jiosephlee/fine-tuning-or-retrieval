\title{A Textbook about the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

Chapter 3: From Bytes to Patches: The Patching Problem

# Formalizing a Patching Function

BLT begins from the idea that raw bytes should not all receive the same amount of computation. Instead of committing to a fixed tokenizer, it groups bytes into patches, and those patches become the units that the larger model processes. In the paper, a patching function $f_p$ takes a byte sequence $\pmb{x}=\{x_i \mid i=1,\ldots,n\}$ and segments it into a shorter sequence of patches $\pmb{p}=\{p_j \mid j=1,\ldots,m\}$, where $m<n$. The segmentation can be represented as a binary decision at each byte position: each $x_i$ is mapped to either $0$ or $1$, with $1$ indicating the start of a new patch.

This definition is important because it makes clear that patching is not just a preprocessing detail. It is the mechanism that decides how a byte sequence is compressed into a sequence of computation units. Once the bytes are split into patches, the main transformer in BLT runs once per patch rather than once per byte. In that sense, patching is the bridge between raw text and the model’s expensive global computation.

# Mapping Byte Sequences to Patch Boundaries

To segment a byte sequence, a patching function must decide where one patch ends and the next begins. In BLT, that decision is expressed through patch boundaries. Every boundary is a place where the model starts a new patch, and the collection of those boundaries determines how the original byte stream is grouped.

The paper emphasizes that these groupings are meant to be contextual. A good patching rule should not merely split text mechanically; it should form patches that reflect how information is distributed in the sequence. That is why the paper treats patching as a learnable or at least data-driven problem rather than a fixed, universal rule. The ideal patch boundaries are those that produce regions of relatively uniform information density, so that the model can spend more compute where prediction is difficult and less where prediction is easy.

# Average Patch Size as the Main Driver of Compute Cost

The central computational fact in the paper is that the number of patches, not the number of bytes alone, determines how often the main transformer is invoked. For a fixed byte sequence, smaller patches produce more patch boundaries, and therefore more transformer steps. Larger patches produce fewer steps and therefore lower compute cost. This is why the average patch size is the key quantity for both training and inference.

This relationship makes patching the model’s main lever for allocating compute. If a sequence is predictable, the paper argues that it is wasteful to spend a full transformer step on every small fragment. If a sequence is dense with information, then finer-grained patches may be worthwhile because they allow the model to devote more capacity where the next-byte prediction is harder. BLT’s patching problem is therefore a problem of matching compute to complexity.

# Strided Patching Every $k$ Bytes

The simplest patching strategy in the paper is strided patching, where the model groups bytes into fixed-size patches of exactly $k$ bytes. This is straightforward to implement and easy to reason about. Because the patch size is fixed, the average number of patches is easy to control, and so the flop cost is easy to manage. The paper notes that this kind of patching was used in earlier work such as MegaByte.

The main advantage of strided patching is therefore its simplicity. It gives a clear knob for changing the effective patch size, and it does so without needing a learned boundary detector or any additional decision-making at runtime. But this simplicity is also its weakness. A fixed stride does not know whether the next bytes are part of whitespace, the end of a word, code, or a dense mathematical expression. It treats all regions alike, even though the paper stresses that different regions can differ greatly in prediction difficulty.

That mismatch leads to two practical problems. First, compute can be wasted on bytes that are easy to predict, such as low-information regions like whitespace in code. Second, compute can be underallocated to sequences with high information density, such as mathematical text. In addition, fixed strides can split the same word differently depending on where the stride happens to fall, which makes the chunking of similar byte sequences inconsistent and non-contextual.

# Benefits and Drawbacks of Static Patching

Static patching, of which strided patching is the clearest example, has a real engineering advantage: it is predictable. Since every patch has a prescribed size, the model designer can control the average patch size directly and can estimate how much compute will be spent on a sequence. This makes static patching a natural baseline and a useful way to reduce the cost of byte-level modeling compared with processing each byte independently.

But the paper’s point is that predictability is not the same as good allocation. Static patching assigns the same amount of global computation to every patch, even when the complexity of the text changes sharply from one region to another. That means static patching is efficient in a narrow sense, but it is not adaptive. It can improve over byte-by-byte processing, yet still fail to line up with where language actually becomes difficult.

This is why the paper treats static patching as an important but limited starting point. It is easy to implement, and it gives a direct way to set cost, but it does not solve the deeper problem of deciding where the model should think more carefully. BLT’s broader goal is to make that decision depend on context rather than on a fixed grid.

# Space Patching and Linguistic Boundary Heuristics

The paper next considers space patching, a simple heuristic that starts a new patch after any space-like byte. In the paper, space-like bytes are defined as bytes that are not a Latin character, a digit, or a UTF-8 continuation byte, with the additional requirement that each patch contain at least one non-space-like byte. This rule uses natural linguistic boundaries, especially in languages where words are separated by spaces.

Space patching has an intuitive appeal because it aligns computation with words. The paper points out that a latent transformer step is then effectively allocated to each word, which ensures that words are patched consistently across sequences. It also makes sense from the standpoint of prediction difficulty: the first byte after a space is often much harder to predict than later bytes in the same word. The paper gives the example of the answer to “Who composed the Magic Flute?” Once the first letter $M$ is known, completing “Mozart” becomes much easier than choosing the first letter in the first place.

This heuristic therefore does better than fixed strides at aligning compute with linguistic structure. It is still simple, but it is no longer blind to one important kind of boundary. In that sense, space patching is a meaningful improvement over purely position-based patching.

# Why Rule-Based Boundaries Help but Remain Limited

Even though space-based boundaries are more linguistically sensible than fixed strides, the paper is clear that rule-based patching remains limited. Space patching works well when the language and domain follow the assumptions built into the rule, but it cannot gracefully handle all languages and domains. It is still tied to a particular surface cue, and that cue does not fully capture where prediction is easy or hard.

A further limitation is that rule-based boundaries cannot vary the patch size in a truly contextual way. Every time the rule fires, it creates a boundary, regardless of whether the text at that point is unusually predictable or unusually uncertain. This means that rule-based patching improves alignment with language structure, but it does not solve the more general problem of adapting compute to information density. The paper’s larger argument is that a good patching function should respond to the difficulty of the next-byte prediction itself, not only to a surface heuristic.

# Dynamic Entropy Patching: A Data-Driven Alternative

To move beyond handcrafted boundaries, the paper introduces entropy patching, which uses next-byte uncertainty to place patch boundaries. The key idea is to train a small byte-level autoregressive language model on the same data distribution and use that model to estimate how uncertain the next byte is at each position. The paper writes the entropy under the byte distribution $p_e$ over the byte vocabulary $\mathcal{V}$ as
$$
H(x_i) = \sum_{v \in \mathcal{V}} p_e(x_i=v \mid \pmb{x}_{<i}) \log p_e(x_i=v \mid \pmb{x}_{<i}).
$$
Patch boundaries are then identified at positions where the uncertainty is high.

The paper studies two ways to turn these entropy estimates into boundaries. One uses a global threshold,
$$
H(x_t) > \theta_g,
$$
and the other looks for a relative increase,
$$
H(x_t) - H(x_{t-1}) > \theta_r.
$$
The second method can also be understood as finding places where the entropy stops decreasing monotonically within a patch. In both cases, the goal is the same: to form patches around regions of relatively uniform information density.

This approach is different in spirit from rule-based patching. Instead of assuming that spaces or fixed positions tell us where the hard decisions are, BLT estimates uncertainty directly and places boundaries where the model expects the next byte to change in difficulty. The paper computes these boundaries in a lightweight preprocessing step during dataloading, which keeps the method practical while making the segmentation more responsive to the actual training data.

# The Distinction Between Patches and Fixed-Vocabulary Tokens

A crucial part of the paper’s argument is that patches are not tokens. Tokens come from a finite vocabulary chosen before training, while patches are dynamically formed sequences of bytes with no fixed vocabulary. This distinction matters because tokens are created by a tokenizer, which compresses text according to a heuristic scheme. The model then operates on the resulting token sequence, but it no longer has direct access to the underlying byte-level features.

The paper also stresses that tokenization-based models allocate the same amount of compute to every token. That creates a trade-off: increasing the vocabulary can make tokens longer on average and reduce the number of model steps, but it also increases the size of the output projection and embedding tables. The paper points to Llama 3 as an example, where the average token size increases compared with Llama 2, but at the cost of a much larger embedding table. This fixed-vocabulary setup leaves little room for truly dynamic control over step count and compute.

Patches, by contrast, are not restricted by a vocabulary size fixed in advance. Any group of bytes can be mapped to a latent patch representation by the learned encoder and decoder modules. That flexibility is what lets BLT decouple the notion of a computation unit from the notion of a token. In the paper’s framing, this is why patching can allocate compute more efficiently than tokenization.

# Incremental Patching and Why It Matters During Generation

For patching to work in an autoregressive model, the boundary decision must be available when only the prefix has been generated. The reason is straightforward: whether the current bytes form a new patch determines whether the expensive latent transformer should be invoked. During generation, the model cannot rely on future bytes that have not yet appeared. Therefore a valid patching scheme must satisfy the incremental property
$$
f_p(\pmb{x}_{<i}) = f_p(\pmb{x})_{<i}.
$$

This condition says that if you patch a prefix on its own, you should get the same boundaries you would get if that prefix were part of the full sequence. That is exactly what BLT needs in order to generate byte by byte without ambiguity. If the patching rule depended on the continuation, then the model could not know how to segment the current prefix consistently as it generates new bytes. So incremental patching is not just a formal nicety; it is a requirement for causal generation.

# Why Standard BPE Is Not an Incremental Patching Scheme

The paper uses this incremental criterion to draw a sharp line between patches and standard BPE tokenization. BPE is built from a finite vocabulary of byte groups, but the same prefix can be tokenized differently depending on the continuation. That means the tokenization of a prefix is not guaranteed to be stable when more bytes are appended, so BPE does not satisfy the incremental condition above.

This is one reason the paper treats BPE and patching as fundamentally different. BPE decides segmentation with a global view of the sequence, whereas BLT needs a segmentation rule that works online during generation. The paper notes that one can add a special delimiter token to make BPE incremental, but that comes at the cost of increasing the byte-sequence length. That extra length undermines the very efficiency gains that tokenization is supposed to provide.

The broader lesson is that patching is not just “tokenization at a different granularity.” It is a causal, dynamically formed segmentation of bytes that is designed to support adaptive compute allocation. That is why the patching problem sits at the center of BLT: choosing boundaries well is what allows the model to spend more effort where the next byte is uncertain and less where the sequence is easy to continue.
