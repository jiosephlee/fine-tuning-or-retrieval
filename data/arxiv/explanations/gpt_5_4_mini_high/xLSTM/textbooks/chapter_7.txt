\title{A Textbook about the Paper: "xLSTM: Extended Long Short-Term Memory"}

Chapter 7: Parallelism and Complexity: Why mLSTM Scales Differently from sLSTM

# What makes recurrence sequential in classical LSTMs

The core reason a classical LSTM is sequential is that each time step depends on the hidden state from the previous time step. In the paper’s formulation, the memory update is additive,
\[
c_t = f_t c_{t-1} + i_t z_t,
\qquad
h_t = o_t \psi(c_t),
\]
but the gates and the cell input are themselves computed from both the current input $\mathbf{x}_t$ and the previous hidden state $h_{t-1}$. That means the model cannot determine the quantities at time $t$ until it has already computed the quantities at time $t-1$. Even though the cell state update is designed to help gradients flow through time, the recurrence still forms a strict chain.

This is what makes classical LSTM processing inherently left-to-right over time. The hidden state is not just an output; it is part of the next step’s computation. So if the model is reading a sequence token by token, the computation of the next token representation is blocked until the current token has been processed. In other words, the LSTM has linear sequence processing in the sense that it revisits each token once, but it does not have time-step parallelism because the next state is causally tied to the previous one.

# Why removing hidden-to-hidden memory mixing enables mLSTM parallelization

The paper identifies hidden-to-hidden memory mixing as the key obstacle to parallel computation. In classical LSTM and in sLSTM, the gates depend on the previous hidden state, which means information must be passed step by step through the recurrent pathway. That hidden-state feedback is what forces sequential execution. If a gate at time $t$ needs $h_{t-1}$, then the computation at $t$ cannot start until $t-1$ is finished.

mLSTM removes that source of dependence. Its query, key, value, and gates are computed directly from the current input $\mathbf{x}_t$ and bias terms, not from $h_{t-1}$. The memory update is then
\[
\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \mathbf{v}_t \mathbf{k}_t^\top,
\qquad
\mathbf{n}_t = f_t \mathbf{n}_{t-1} + i_t \mathbf{k}_t,
\]
with the hidden state read out from the matrix memory by
\[
\mathbf{h}_t = \mathbf{o}_t \odot \tilde{\mathbf{h}}_t,
\qquad
\tilde{\mathbf{h}}_t = \mathbf{C}_t \mathbf{q}_t / \max\{|\mathbf{n}_t^\top \mathbf{q}_t|, 1\}.
\]
Because the current step no longer needs the previous hidden state to form its gates, the recurrence loses the hidden-to-hidden bottleneck that prevents parallelization.

The paper also emphasizes that this is not just a small implementation detail. It is a structural change in the model family. sLSTM keeps memory mixing, including across multiple cells and heads, while mLSTM abandons that mixing to become fully parallelizable. That is the central trade-off: sLSTM preserves richer recurrent interaction, but mLSTM gains a computation pattern that is far friendlier to modern hardware.

# Rewriting the mLSTM recurrence as a parallel computation

The reason mLSTM can be reformulated in parallel is that its state update is built from algebraic operations that combine neatly across time. Each step contributes an outer product $\mathbf{v}_t \mathbf{k}_t^\top$ to the matrix memory and a key vector $\mathbf{k}_t$ to the normalizer state. Since the gates and projections come directly from $\mathbf{x}_t$, the model does not need to wait for a previous hidden state to produce the next local transformation.

The paper’s point is not that the recurrence disappears, but that the recurrence becomes reorganizable. Instead of a strict hidden-state chain where each step must be evaluated one after another, the mLSTM update can be expressed in a parallel form using standard matrix operations. That is why the authors describe mLSTM as fully parallelizable. The key intuition is that the model stores information in a way that is compatible with GPU-style batched linear algebra rather than relying on sequential hidden-state mixing.

This matters because the sequence dimension is the expensive axis in language modeling. If the model can restructure its recurrence so that many operations can be carried out together, then the hardware can do much more work at once. The paper’s design choice is therefore not only about modeling power, but also about matching the computation to what modern accelerators are good at.

# Linear compute growth and constant memory with respect to sequence length

A central complexity advantage of xLSTM in the paper is that its computation grows linearly with sequence length, while its memory with respect to sequence length stays constant. The reason is simple: the model does not keep a growing list of all past states the way attention-based systems do. Instead, it carries a fixed-size recurrent state forward. Once the state is initialized, each new token updates that state, but the size of the state does not expand as the sequence gets longer.

This is especially important to understand in contrast to Transformer-style processing. In xLSTM, longer sequences cost more compute because there are more time steps, but they do not force the model to store a longer and longer history in memory. That is what the paper means by compressive memory. The past is summarized into a fixed internal state, which makes xLSTM attractive when the context is long but the available memory budget is limited.

The paper explicitly connects this to practical deployment. Because the memory footprint does not grow with sequence length, xLSTM is described as well suited for industrial applications and for edge settings. In those settings, a model that keeps a bounded state is easier to deploy than one whose storage grows with every additional token.

# The cost of $d \times d$ matrix updates and retrievals

The advantage of mLSTM’s matrix memory comes with a cost: the memory is no longer a scalar cell state but a matrix $\mathbf{C} \in \mathbb{R}^{d \times d}$. That means each update and each retrieval involves matrix-level arithmetic. The update
\[
\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \mathbf{v}_t \mathbf{k}_t^\top
\]
requires processing a $d \times d$ state, and the readout
\[
\mathbf{C}_t \mathbf{q}_t
\]
also involves matrix multiplication. So although the memory does not grow with sequence length, each step is computationally heavier than the scalar update of a classical LSTM.

The paper is explicit that this is a trade-off. mLSTM increases storage capacity by using a matrix memory, but that richer memory has a larger arithmetic cost than a scalar cell. Still, the authors point out that these computations can be carried out in parallel on GPUs, so the wall-clock impact is smaller than the raw matrix size might suggest. In other words, the model pays for greater memory capacity with more arithmetic, but the hardware can absorb much of that cost when the implementation is efficient.

# Trade-offs between memory capacity and arithmetic cost

The entire motivation for mLSTM is that scalar memory can be too compressed. Classical LSTMs, with scalar cell states, have to squeeze all useful history into a small number of scalar channels. The paper uses this to motivate the matrix memory, which can store key-value associations in a much richer form. This is the storage side of the trade-off: more expressive memory should handle harder retrieval and tracking problems better.

But richer memory is never free. A matrix state has far more entries than a scalar state, so every update and every retrieval becomes more expensive. The paper’s framing is that xLSTM deliberately trades arithmetic cost for memory capacity. That trade-off is acceptable when the task needs more structure in memory, such as long-context language modeling or associative retrieval, because the model’s ability to preserve and recover information becomes more important than minimizing each individual update.

This is also why the paper distinguishes sLSTM from mLSTM. sLSTM keeps a scalar memory and uses memory mixing, which preserves a familiar recurrent flavor. mLSTM enlarges the memory itself and removes memory mixing, which makes the state more expressive and the computation more parallelizable. The two variants occupy different positions in the same design space.

# Comparison with Transformer attention complexity

The paper contrasts xLSTM with Transformer attention primarily on sequence-length complexity. Transformer attention is quadratic in context length because tokens interact pairwise across the sequence. That pairwise interaction is powerful, but it also becomes increasingly expensive as the sequence grows. xLSTM, by contrast, processes the sequence with linear compute growth and constant memory with respect to sequence length.

This difference is one of the main reasons xLSTM is interesting as a long-context model. Instead of building interactions by comparing every token with every other token, xLSTM compresses the past into recurrent state. The paper argues that this gives xLSTM a better fit for settings where long sequences matter and memory must stay bounded. It is not that xLSTM eliminates computation; it changes where the cost is paid.

The paper’s experiments support this complexity story at a practical level. The authors report that xLSTM maintains low perplexities on longer contexts in their extrapolation experiments, while Transformer-based models show the familiar cost of handling long histories. So the asymptotic advantage is not only theoretical; it also connects to the observed behavior in long-context evaluation.

# Comparison with FlashAttention-style kernels and Mamba-style scans

The paper places mLSTM in the same broad hardware-aware conversation as FlashAttention-style kernels and the scan used in Mamba. These are all attempts to make sequence models faster by organizing computation around efficient GPU operations rather than naive sequential loops. The important point is that mLSTM’s matrix-based recurrence is compatible with this kind of acceleration because it can be reformulated in parallel.

At the same time, the paper is careful to distinguish theory from implementation quality. In the current codebase, the mLSTM kernels are not yet fully optimized, and the authors note that the implementation is about $4$ times slower than FlashAttention or the scan used in Mamba. That does not mean the design is inherently slower; it means the present kernels leave room for improvement. The paper explicitly suggests that faster kernels could be obtained in the spirit of FlashAttention.

sLSTM is different again. Because it retains memory mixing, it does not admit the same full parallelization as mLSTM. The authors still report a fast CUDA implementation with GPU memory optimizations down to the register level, and they say it is typically less than two times slower than their parallel mLSTM implementation. So the real-world comparison is shaped by both algorithmic structure and kernel engineering.

# Why xLSTM is attractive for long-context and edge deployment settings

The strongest deployment argument in the paper is the combination of linear compute and constant memory with respect to sequence length. For long-context settings, this means the cost of processing a longer sequence rises in a controlled way without forcing memory to grow with the entire history. That makes xLSTM especially attractive when the input stream is long and unpredictable.

The paper also emphasizes that the memory is compressive. Instead of storing all past tokens explicitly, xLSTM compresses them into a recurrent state. This is valuable not only for long context, but also for deployment environments where memory is limited. The authors explicitly say this makes xLSTM well suited for industrial applications and edge implementations. In those settings, bounded memory usage is often just as important as raw predictive accuracy.

The experimental results reinforce this motivation. In the long-context experiments, xLSTM maintains strong behavior on longer sequences, and in generation throughput tests it benefits from constant memory by supporting larger batch sizes. Those properties are exactly what one would want in a model meant to scale to demanding deployment settings.

# Practical speed differences between sLSTM and mLSTM

In practice, sLSTM and mLSTM differ not only in theory but also in how they run on hardware. sLSTM keeps the sequential dependence created by memory mixing, so it cannot be made fully parallel across time. That makes it less amenable to the most aggressive forms of sequence acceleration. mLSTM, by removing memory mixing, is the variant that can be parallelized more directly.

The paper reports that their fast CUDA implementation makes sLSTM typically less than two times slower than mLSTM. At the same time, the current mLSTM kernels are still about $4$ times slower than FlashAttention or the scan used in Mamba, because the kernels are not yet optimized. This is an important lesson: theoretical parallelism does not automatically translate into best-in-class runtime. The quality of the kernel matters.

So the practical picture is nuanced. mLSTM is the more parallel design, but sLSTM can still be engineered efficiently despite its sequential dependency. The difference between them is not just speed, but how their internal structure interacts with hardware. mLSTM is the better fit when parallelization is the priority, while sLSTM preserves memory mixing at the cost of sequential computation.
