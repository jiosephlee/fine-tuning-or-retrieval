\title{Blogs about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

# From 35% to 75% GPU Utilization: What FlashAttention-3 Reveals About AI Hardware

## Attention is still the bottleneck

Attention is one of the core operations inside Transformers, and it gets expensive fast as sequence length grows. The reason is simple: self-attention compares every token with every other token, so the work scales quadratically with context length.

That is why FlashAttention mattered in the first place. Instead of materializing large intermediate matrices in slow GPU memory, it fused the whole attention computation into one kernel and kept data on chip as much as possible. FlashAttention-2 pushed this further by improving parallelism and occupancy on GPUs.

But on NVIDIA’s H100, there was still a gap. The paper reports that FlashAttention-2 only reached about 35% utilization on H100, while optimized GEMM kernels were already hitting roughly 80-90%. FlashAttention-3 is about closing that gap by designing the algorithm around Hopper’s newer hardware features rather than treating the GPU like a generic synchronous machine.

## Why Hopper changes the game

The key architectural shift in Hopper is asynchrony. H100 has specialized hardware for two things that attention depends on heavily: moving data and doing matrix multiplication.

For data movement, Hopper adds the Tensor Memory Accelerator, or TMA, which can load data between global memory and shared memory asynchronously. For matrix multiplication, Hopper exposes asynchronous warpgroup matrix-multiply instructions, called WGMMA, through the Tensor Cores.

This matters because attention is not just matrix multiplication. It also includes softmax, exponentials, reductions, and rescaling. In older designs, those pieces are often forced to run in a mostly synchronous sequence: compute scores, wait, run softmax, wait, multiply by values, wait again. FlashAttention-3 asks a different question: what if the GPU could be kept busy by overlapping these phases?

## FlashAttention-3 is built around overlap

FlashAttention-3 introduces three hardware-aware ideas.

The first is producer-consumer warp-specialization. Instead of having all threads in a CTA do the same thing, the kernel splits warps into producers and consumers. Producers focus on moving data with TMA, while consumers focus on computation. Hopper also supports dynamic register reallocation with `setmaxnreg`, so the compute warps can use more registers than the load-only warps.

The practical effect is that memory movement and computation can proceed in parallel instead of blocking each other.

The second idea is to overlap softmax with GEMM. Softmax is much slower in throughput terms than matrix multiplication on Hopper. The paper gives a useful comparison: on H100, FP16 matmul can reach 989 TFLOPS per second, while special functions such as exponential are around 3.9 TFLOPS per second. That means softmax can become a visible bottleneck even when the Tensor Cores are busy.

FlashAttention-3 works around this by pipelining across blocks. While one block is going through softmax, the next block can already be running on the Tensor Cores. The paper describes this as a “pingpong” schedule between warpgroups. In the ideal case, one warpgroup is doing softmax while another is issuing WGMMA instructions.

The third idea is to use Hopper’s low-precision FP8 Tensor Cores. FP8 roughly doubles throughput compared with FP16 or BF16 on the same hardware, but it comes with harder constraints on layout and accuracy. FlashAttention-3 adapts its kernel so it can actually use FP8 effectively instead of treating it as a drop-in replacement.

## FP8 is not just a smaller datatype

Moving attention to FP8 is not just a matter of changing precision. Hopper’s FP8 WGMMA has stricter layout requirements than FP16. In particular, some operands must be arranged in a `k`-major layout, which means FlashAttention-3 cannot simply reuse the same data layout everywhere.

The paper solves this with an in-kernel transpose for $V$, using Hopper instructions like `ldmatrix` and `stmatrix`, plus some register-level permutation to make the accumulator layout compatible with the next FP8 GEMM. This is one of those details that sounds small but matters a lot in practice: if the layout does not line up with the hardware, the theoretical speedup disappears.

Accuracy is the other half of the FP8 story. Low precision is especially tricky for attention because large models often contain outlier activations, and those outliers can dominate quantization error. FlashAttention-3 uses two techniques to reduce that error:

It uses block quantization, storing one scale per block rather than one scale for the entire tensor. Since FlashAttention already processes data in blocks, this fits naturally into the kernel.

It also uses incoherent processing, multiplying $Q$ and $K$ by a structured random orthogonal transform before quantization. Because the transform is orthogonal, it does not change the attention scores, but it helps spread out outliers so quantization is less sensitive to extreme values.

## What the benchmarks show

The end result is a substantial speedup on H100.

For FP16, FlashAttention-3 is about 1.5-2.0x faster than FlashAttention-2 in the forward pass, and about 1.5-1.75x faster in the backward pass. The paper reports up to 740 TFLOPS per second, which corresponds to about 75% utilization of the H100’s theoretical peak.

For FP8, FlashAttention-3 reaches close to 1.2 PFLOPS per second. That is the clearest sign that the kernel is no longer leaving Hopper’s low-precision hardware idle.

There is also a numerical result worth highlighting. For an outlier-heavy input distribution, FP8 FlashAttention-3 is 2.6x more accurate than a baseline FP8 attention implementation that uses per-tensor quantization. In FP16, the numerical error matches FlashAttention-2 and is better than standard attention, since intermediate values such as softmax rescaling stay in FP32.

## The bigger lesson: hardware and software have to meet in the middle

FlashAttention-3 is a good example of hardware-software co-design done right. The H100 does not automatically deliver high attention throughput just because it has more advanced Tensor Cores. The software has to be written to exploit asynchrony, manage data movement carefully, and respect the layout rules of the low-precision path.

That is the main lesson from the paper: modern GPU performance is increasingly about orchestration, not just raw FLOPs. The fastest kernels are the ones that understand which parts of the machine can run at the same time, which data needs to stay on chip, and where precision can be reduced without breaking the algorithm.

The authors open-sourced FlashAttention-3 and plan to integrate it with PyTorch and Hugging Face. They also note some limitations, including further optimization for inference, adding a persistent-kernel design to FP8, and studying the effects of low-precision attention at training scale.

Still, the broader message is already clear. On Hopper, attention is no longer just a math problem. It is a scheduling problem, a layout problem, and a precision problem — and FlashAttention-3 shows how much performance is waiting to be unlocked when all three are solved together.
