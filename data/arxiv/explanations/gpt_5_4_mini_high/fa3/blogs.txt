# Why Attention Is the Real Bottleneck in Modern AI—and How FlashAttention-3 Speeds It Up

## Attention is where long-context models start to hurt

Transformers are built around attention. For one head, the core computation is

$$
\mathbf{S} = \alpha \mathbf{Q}\mathbf{K}^\top,\quad
\mathbf{P} = \mathrm{softmax}(\mathbf{S}),\quad
\mathbf{O} = \mathbf{P}\mathbf{V}.
$$

This looks simple, but it hides a serious scaling problem. If the sequence length is $N$, then $\mathbf{S}$ and $\mathbf{P}$ are both $N \times N$ matrices. That means attention gets more expensive very quickly as context grows.

That matters because modern AI keeps asking models to handle longer inputs: long documents, codebases, high-resolution images, audio, video, and long interaction histories. In all of those settings, attention becomes a bottleneck long before the rest of the model does.

The problem is not just arithmetic. On GPUs, the expensive part is often moving data around, not computing with it. A standard attention implementation writes intermediate matrices like $\mathbf{S}$ and $\mathbf{P}$ out to high-bandwidth memory and reads them back again. That is slow.

## FlashAttention made exact attention practical

FlashAttention changed the game by reorganizing attention so that the intermediate matrices never have to live in slow global memory. Instead, it tiles the computation and keeps the important pieces on-chip. The result is the same attention formula, just executed in a much more GPU-friendly way.

FlashAttention-2 improved on that by better parallelizing work across the sequence dimension and improving how blocks are handled. But on newer Hopper GPUs, the paper shows that there was still a lot of headroom left. In particular, FlashAttention-2 reaches only about 35% utilization on an H100 GPU, while highly tuned GEMM kernels can hit 80% to 90%.

FlashAttention-3 is about closing that gap.

## What FlashAttention-3 changes

FlashAttention-3 takes advantage of two Hopper features that earlier attention kernels do not fully exploit: asynchronous execution and FP8 low precision.

The basic idea is to treat attention less like one monolithic loop and more like a pipeline. Different parts of the GPU can do different jobs at the same time, so long as the software is organized to let them overlap.

### 1. Split the work between producer and consumer warps

On Hopper, memory movement and matrix multiplication are handled by specialized hardware units. FlashAttention-3 uses this by dividing warps into producers and consumers.

The producer warps move query, key, and value blocks into shared memory. The consumer warps do the matrix multiplications and softmax work. Because loading and computation are asynchronous, the two can overlap instead of waiting on each other.

This is a form of warp-specialization, and it helps hide memory latency. The implementation also uses Hopper’s ability to dynamically reallocate registers, so the warps doing the heavy computation can get more registers than the warps mainly responsible for data movement.

### 2. Overlap softmax with matrix multiplication

Softmax is a necessary part of attention, but it is much lower throughput than matrix multiplication. FlashAttention-3 takes advantage of that imbalance.

The key trick is to pipeline the work so that while one block is finishing its softmax, the next block is already being multiplied on the Tensor Cores. The paper describes this as a 2-stage overlap, and in practice it is a kind of “pingpong” schedule: one warpgroup computes while another warpgroup finishes the non-matmul work.

This matters because the softmax is not free. On H100, the paper notes that matmul throughput is enormous compared to special-function throughput, so if softmax is left on the critical path, it becomes a real performance limiter. By overlapping the two, FlashAttention-3 keeps the Tensor Cores busier.

The tradeoff is that this kind of pipelining uses more registers, so the implementation has to balance pipeline depth and tile size carefully.

### 3. Use FP8 when the hardware supports it

Hopper GPUs also support FP8 Tensor Cores, which roughly double throughput compared to FP16 or BF16. FlashAttention-3 adapts attention to use them.

That is not as simple as just switching data types. FP8 has stricter layout requirements, and attention has back-to-back GEMMs that want different memory layouts. FlashAttention-3 handles this with an in-kernel transpose and a few register permutations so the FP8 Tensor Core instructions can be used efficiently.

There is also an accuracy problem. FP8 has fewer bits, and attention often sees outlier values in large models. To reduce the damage, FlashAttention-3 uses two techniques:

- **Block quantization**, where each block gets its own scaling factor instead of using one scale for the entire tensor.
- **Incoherent processing**, where $\mathbf{Q}$ and $\mathbf{K}$ are multiplied by an orthogonal transform before quantization, which spreads out outliers without changing $\mathbf{Q}\mathbf{K}^\top$.

The paper follows the idea of using a product of random sign matrices and a Hadamard transform, which can be applied efficiently.

## What the benchmarks show

On an H100 SXM5 GPU, FlashAttention-3 delivers the kind of gains you would hope for from this hardware-aware redesign.

For FP16, the paper reports:

- **1.5--2.0$\times$ speedup** over FlashAttention-2 in the forward pass
- **1.5--1.75$\times$ speedup** in the backward pass
- Up to **740 TFLOPs/s**, which is about **75%** of the GPU’s theoretical maximum

For FP8, FlashAttention-3 reaches close to **1.2 PFLOPs/s**.

The paper also shows that the algorithmic changes matter on their own. In one ablation, adding warp-specialization and the GEMM-softmax pipeline improves performance from **570 TFLOPs/s to 661 TFLOPs/s** in a fixed FP16 setting.

On the accuracy side, FP16 FlashAttention-3 matches the numerical error of FlashAttention-2 and does better than standard attention because intermediate results are kept in FP32. For FP8, block quantization and incoherent processing make FlashAttention-3 **2.6$\times$ more accurate** than a baseline FP8 attention method using per-tensor quantization, especially in the presence of outlier features.

## Why this matters

The main lesson of FlashAttention-3 is that attention is not just a math problem. It is a hardware scheduling problem.

If you can keep data on-chip, overlap compute with movement, and match the algorithm to the GPU’s execution model, exact attention can get much faster without changing what the model computes. FlashAttention-3 pushes that idea further than before by explicitly using asynchrony and low precision in the kernel design.

The work is still Hopper-focused, and the paper notes some open directions, including better support for inference and persistent-kernel designs for FP8. But the direction is clear: attention is still the bottleneck, and there is still a lot of room to optimize it.

FlashAttention-3 shows that with the right software design, even a very mature part of the Transformer stack can keep improving.



# Teaching GPUs to Multitask: The Asynchronous Tricks Behind FlashAttention-3

## Attention is a scheduling problem as much as a math problem

Transformer attention is usually written as three steps: compute scores with $\mathbf{Q}\mathbf{K}^\top$, apply softmax, then mix values with $\mathbf{V}$. That looks straightforward on paper, but on a GPU it creates a lot of waiting. The score matrix is large, the data has to move through memory hierarchies, and softmax is much slower than matrix multiplication.

FlashAttention improved this by avoiding the expensive round-trip to global memory for intermediate results. FlashAttention-3 goes a step further on Hopper GPUs: it tries to keep different parts of the chip busy at the same time.

## Hopper gives the kernel more than one “lane”

The key hardware change in Hopper is that memory movement and matrix multiplication can run asynchronously. Two pieces matter here.

The first is the Tensor Memory Accelerator, or TMA, which can move tiles of data from high-bandwidth memory into shared memory without tying up the usual compute path. Shared memory is the on-chip scratchpad that threads in the same block can reuse quickly.

The second is WGMMA, Hopper’s asynchronous matrix-multiply instruction for Tensor Cores. Instead of making the whole kernel wait for a multiply to finish before moving on, WGMMA lets the GPU launch the work and continue scheduling other instructions.

That matters because attention is naturally split into pieces with very different speeds. The paper notes that on H100, FP16 matmul throughput is enormous, while special functions such as exponential are much slower. If you run everything in strict sequence, the fast hardware sits idle while the slow pieces catch up.

## Warp specialization: producers and consumers

FlashAttention-3 uses a software pattern called warp specialization. A GPU thread block is divided into groups of warps, and those groups take on different roles.

One role is the producer. Producer warps are responsible for moving tiles of $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$ into shared memory using TMA.

The other role is the consumer. Consumer warps read those tiles and do the actual attention computation with WGMMA and softmax.

This split is useful because not every warp needs to do every job. A warp that is only issuing data movement does not need the same register budget as a warp that is running matrix multiplications. Hopper even supports dynamic register reallocation, so the compute-heavy warps can get more registers when needed.

The practical effect is a pipeline. While one tile is being used for computation, the next tile can already be on its way into shared memory. The kernel stops thinking in terms of “load, then compute, then load again” and starts thinking in terms of overlapping stages.

## The bigger trick: hiding softmax under the next matmul

Warp specialization alone is not the whole story. FlashAttention-3 also overlaps the softmax work with matrix multiplication.

This is important because softmax is the awkward part of attention. It depends on the output of the score matrix, so at first glance it seems to force a strict order:

1. compute scores,
2. run softmax,
3. multiply by $\mathbf{V}$.

FlashAttention-3 breaks that simple chain by working block by block. In the paper’s 2-stage pipeline, while one warpgroup is computing softmax and updating the output for the current block, another warpgroup is already computing the next block of scores with WGMMA. The GPU is effectively doing two different parts of attention at once.

This is the “multitasking” idea behind the paper. The Tensor Cores do not have to wait for softmax to finish, and softmax does not have to wait for the next matrix multiply to be launched.

## Why the paper calls it “ping-pong” scheduling

The authors describe the execution pattern as ping-pong scheduling because the two warpgroups alternate roles.

At one moment, warpgroup A is doing the matrix multiplies for block $j+1$ while warpgroup B is finishing the softmax and output update for block $j$. Then they swap. A becomes the softmax side, B becomes the matmul side.

That alternating pattern keeps the machine better utilized. Instead of one stage of the pipeline dominating while other hardware units sit idle, the work bounces back and forth in a controlled way.

There is also a circular shared-memory buffer underneath all of this. It lets the producer side keep filling future tiles while the consumer side is still using earlier ones. That buffer is what makes the overlap safe and structured.

## What the speedup looks like in practice

This is not just a nice scheduling story. It shows up in the numbers.

On an H100 SXM5 GPU, FlashAttention-3 reaches up to 740 TFLOPs/s in FP16, which is about 75% of the chip’s theoretical peak. Compared with FlashAttention-2, the paper reports a 1.5-2.0$\times$ speedup in the forward pass and a 1.5-1.75$\times$ speedup in the backward pass.

The paper’s ablation study also shows that the pipeline itself matters: for one non-causal FP16 benchmark, performance improves from 570 TFLOPs/s to 661 TFLOPs/s when the warp-specialization and overlapping scheme is enabled.

So the main gain is not from changing the attention algorithm mathematically. It comes from matching the algorithm to the GPU’s execution model much more closely.

## The bigger lesson

FlashAttention-3 is a good example of modern GPU programming: performance is often limited less by arithmetic and more by orchestration. If you can overlap memory movement, matrix multiplication, and softmax, you can make a kernel feel much faster without changing what it computes.

That is the real takeaway from the paper. On Hopper, the fastest attention is not the version that does the least work. It is the version that keeps the most hardware busy at the same time.



# Can FP8 Be Both Fast and Reliable? Inside FlashAttention-3’s Low-Precision Design

Lower precision is one of the most effective ways to speed up GPU kernels. Fewer bits mean less data movement, and on modern accelerators it also means access to specialized Tensor Cores that can do more math per second. But attention is a harsh test for low precision: it combines large matrix multiplications with a softmax, and small numerical errors can get amplified.

That is the tension FlashAttention-3 tries to resolve. Its FP8 path is not just “run the same algorithm with smaller numbers.” It is a hardware-aware redesign that aims to keep the speed benefits of FP8 while reducing the accuracy loss that usually comes with it.

## Why FP8 matters

On NVIDIA Hopper GPUs, FP8 Tensor Cores can deliver about 2x the throughput per SM compared to FP16 or BF16. That is a big deal for attention, which is already one of the main bottlenecks in Transformers.

FlashAttention-3 reports that its FP8 version on H100 reaches close to 1.2 PFLOPs/s. So the appeal is clear: if you can make FP8 work well, you can get a major speedup in a kernel that dominates runtime for long-context models.

The catch is that attention is not just matrix multiplication. It also includes softmax, and low-precision arithmetic can distort the score distribution before and after that step. That is especially risky when model activations contain outliers, which the paper notes are common in large models.

## Why naive FP8 can hurt accuracy

The FP8 format used here, e4m3, has only 3 mantissa bits and 4 exponent bits. That is much less room than FP16, so a small number of very large values can dominate the scale of a tensor.

A common baseline approach is per-tensor quantization: use one scaling factor for all of $\mathbf{Q}$, $\mathbf{K}$, or $\mathbf{V}$. That is simple, but it is also coarse. If one region of a tensor has outliers, the whole tensor pays the price.

FlashAttention-3 attacks this problem with two ideas: block quantization and incoherent processing.

## Block quantization: scale locally, not globally

The first idea is straightforward but effective. Instead of one scale for an entire tensor, FlashAttention-3 uses one scale per block.

Because the FlashAttention algorithm already works block by block, this fits naturally into the kernel. The paper splits $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$ into blocks of size $B_r \times d$ or $B_c \times d$ and quantizes each block separately. That means a few large values in one block do not distort the dynamic range of the rest of the tensor.

This is a nice example of algorithm and quantization working together. The block structure is already there for performance, and FlashAttention-3 uses that same structure to improve numerical behavior. The paper also notes that this quantization can be fused with a preceding step such as rotary embedding, so it does not add extra slowdown.

## Incoherent processing: spread out the outliers

Block quantization helps, but the paper goes further. The second idea is to make the data itself easier to quantize.

FlashAttention-3 multiplies both $\mathbf{Q}$ and $\mathbf{K}$ by the same random orthogonal matrix $\mathbf{M}$ before quantization. Since $\mathbf{M}\mathbf{M}^\top = I$, the attention scores do not change:

$$
(\mathbf{Q}\mathbf{M})(\mathbf{K}\mathbf{M})^\top = \mathbf{Q}\mathbf{K}^\top.
$$

So why do this? Because the transform “mixes” the values and spreads out outliers across dimensions. That makes the entries of $\mathbf{Q}\mathbf{M}$ and $\mathbf{K}\mathbf{M}$ more uniform, which reduces quantization error.

The paper follows prior work and constructs $\mathbf{M}$ as a product of random diagonal matrices of $\pm 1$ and a Hadamard matrix. That makes the transform efficient, with cost $O(d \log d)$ instead of $O(d^2)$, and it can also be fused with rotary embedding.

In short, block quantization reduces the damage from local outliers, while incoherent processing makes those outliers less extreme in the first place.

## FP8 on Hopper is also a layout problem

Getting FP8 speed from Hopper is not just a matter of changing a datatype. The hardware has specific layout constraints for FP8 WGMMA instructions, especially for the second GEMM in attention.

In particular, the FP8 path needs $\mathbf{V}$ tiles in a k-major layout for the second matrix multiplication, while attention inputs are usually laid out contiguously in the head dimension. FlashAttention-3 handles this with an in-kernel transpose of $\mathbf{V}$ tiles, using LDSM/STSM instructions and a register permutation so the two GEMMs line up correctly.

That choice matters because a separate preprocessing transpose would waste bandwidth in a memory-bound kernel. Keeping the layout conversion inside the kernel is part of how FlashAttention-3 gets its FP8 throughput without giving back too much to data movement.

## What the numbers show

The paper validates FP8 FlashAttention-3 on H100 SXM5 and finds two important things:

First, the kernel is fast. The FP8 version reaches close to 1.2 PFLOPs/s. More broadly, FlashAttention-3 uses Hopper’s asynchrony and Tensor Core pipeline to push attention much closer to hardware limits.

Second, the quantization strategy really helps. On a synthetic test designed to mimic outlier-heavy activations, the paper compares FP8 FlashAttention-3 against a baseline FP8 attention implementation that uses per-tensor scaling. With block quantization and incoherent processing, FlashAttention-3 is 2.6x more accurate in terms of RMSE.

That is the key result of the paper’s FP8 story: the speedup does not come at the cost of a large numerical penalty.

## The takeaway

FlashAttention-3 shows that FP8 can be both fast and reliable, but only if the kernel is designed around the failure modes of low precision.

The recipe is:

- use FP8 Tensor Cores to get the throughput win,
- quantize at the block level instead of the whole tensor level,
- apply an orthogonal transform to reduce outliers before quantization,
- and map the data layout carefully onto Hopper’s hardware.

The broader lesson is that low precision is most effective when it is not treated as a late-stage optimization. It needs to be part of the algorithm itself. In FlashAttention-3, that is exactly what makes FP8 viable for attention.



# From 35% to 75% GPU Utilization: What FlashAttention-3 Reveals About AI Hardware

## Attention is still the bottleneck

Attention is one of the core operations inside Transformers, and it gets expensive fast as sequence length grows. The reason is simple: self-attention compares every token with every other token, so the work scales quadratically with context length.

That is why FlashAttention mattered in the first place. Instead of materializing large intermediate matrices in slow GPU memory, it fused the whole attention computation into one kernel and kept data on chip as much as possible. FlashAttention-2 pushed this further by improving parallelism and occupancy on GPUs.

But on NVIDIA’s H100, there was still a gap. The paper reports that FlashAttention-2 only reached about 35% utilization on H100, while optimized GEMM kernels were already hitting roughly 80-90%. FlashAttention-3 is about closing that gap by designing the algorithm around Hopper’s newer hardware features rather than treating the GPU like a generic synchronous machine.

## Why Hopper changes the game

The key architectural shift in Hopper is asynchrony. H100 has specialized hardware for two things that attention depends on heavily: moving data and doing matrix multiplication.

For data movement, Hopper adds the Tensor Memory Accelerator, or TMA, which can load data between global memory and shared memory asynchronously. For matrix multiplication, Hopper exposes asynchronous warpgroup matrix-multiply instructions, called WGMMA, through the Tensor Cores.

This matters because attention is not just matrix multiplication. It also includes softmax, exponentials, reductions, and rescaling. In older designs, those pieces are often forced to run in a mostly synchronous sequence: compute scores, wait, run softmax, wait, multiply by values, wait again. FlashAttention-3 asks a different question: what if the GPU could be kept busy by overlapping these phases?

## FlashAttention-3 is built around overlap

FlashAttention-3 introduces three hardware-aware ideas.

The first is producer-consumer warp-specialization. Instead of having all threads in a CTA do the same thing, the kernel splits warps into producers and consumers. Producers focus on moving data with TMA, while consumers focus on computation. Hopper also supports dynamic register reallocation with `setmaxnreg`, so the compute warps can use more registers than the load-only warps.

The practical effect is that memory movement and computation can proceed in parallel instead of blocking each other.

The second idea is to overlap softmax with GEMM. Softmax is much slower in throughput terms than matrix multiplication on Hopper. The paper gives a useful comparison: on H100, FP16 matmul can reach 989 TFLOPS per second, while special functions such as exponential are around 3.9 TFLOPS per second. That means softmax can become a visible bottleneck even when the Tensor Cores are busy.

FlashAttention-3 works around this by pipelining across blocks. While one block is going through softmax, the next block can already be running on the Tensor Cores. The paper describes this as a “pingpong” schedule between warpgroups. In the ideal case, one warpgroup is doing softmax while another is issuing WGMMA instructions.

The third idea is to use Hopper’s low-precision FP8 Tensor Cores. FP8 roughly doubles throughput compared with FP16 or BF16 on the same hardware, but it comes with harder constraints on layout and accuracy. FlashAttention-3 adapts its kernel so it can actually use FP8 effectively instead of treating it as a drop-in replacement.

## FP8 is not just a smaller datatype

Moving attention to FP8 is not just a matter of changing precision. Hopper’s FP8 WGMMA has stricter layout requirements than FP16. In particular, some operands must be arranged in a `k`-major layout, which means FlashAttention-3 cannot simply reuse the same data layout everywhere.

The paper solves this with an in-kernel transpose for $V$, using Hopper instructions like `ldmatrix` and `stmatrix`, plus some register-level permutation to make the accumulator layout compatible with the next FP8 GEMM. This is one of those details that sounds small but matters a lot in practice: if the layout does not line up with the hardware, the theoretical speedup disappears.

Accuracy is the other half of the FP8 story. Low precision is especially tricky for attention because large models often contain outlier activations, and those outliers can dominate quantization error. FlashAttention-3 uses two techniques to reduce that error:

It uses block quantization, storing one scale per block rather than one scale for the entire tensor. Since FlashAttention already processes data in blocks, this fits naturally into the kernel.

It also uses incoherent processing, multiplying $Q$ and $K$ by a structured random orthogonal transform before quantization. Because the transform is orthogonal, it does not change the attention scores, but it helps spread out outliers so quantization is less sensitive to extreme values.

## What the benchmarks show

The end result is a substantial speedup on H100.

For FP16, FlashAttention-3 is about 1.5-2.0x faster than FlashAttention-2 in the forward pass, and about 1.5-1.75x faster in the backward pass. The paper reports up to 740 TFLOPS per second, which corresponds to about 75% utilization of the H100’s theoretical peak.

For FP8, FlashAttention-3 reaches close to 1.2 PFLOPS per second. That is the clearest sign that the kernel is no longer leaving Hopper’s low-precision hardware idle.

There is also a numerical result worth highlighting. For an outlier-heavy input distribution, FP8 FlashAttention-3 is 2.6x more accurate than a baseline FP8 attention implementation that uses per-tensor quantization. In FP16, the numerical error matches FlashAttention-2 and is better than standard attention, since intermediate values such as softmax rescaling stay in FP32.

## The bigger lesson: hardware and software have to meet in the middle

FlashAttention-3 is a good example of hardware-software co-design done right. The H100 does not automatically deliver high attention throughput just because it has more advanced Tensor Cores. The software has to be written to exploit asynchrony, manage data movement carefully, and respect the layout rules of the low-precision path.

That is the main lesson from the paper: modern GPU performance is increasingly about orchestration, not just raw FLOPs. The fastest kernels are the ones that understand which parts of the machine can run at the same time, which data needs to stay on chip, and where precision can be reduced without breaking the algorithm.

The authors open-sourced FlashAttention-3 and plan to integrate it with PyTorch and Hugging Face. They also note some limitations, including further optimization for inference, adding a persistent-kernel design to FP8, and studying the effects of low-precision attention at training scale.

Still, the broader message is already clear. On Hopper, attention is no longer just a math problem. It is a scheduling problem, a layout problem, and a precision problem — and FlashAttention-3 shows how much performance is waiting to be unlocked when all three are solved together.



# What Faster Attention Means for Long-Context LLMs, Code Models, and Multimodal AI

Transformer models spend a lot of their time in one place: attention. That matters because attention is the part of the model that lets each token look at every other token, which is exactly what you want for long documents, large codebases, high-resolution images, audio, and video. It is also why attention becomes expensive so quickly: as sequence length grows, the work grows roughly with $N^2$.

The new paper on FlashAttention-3 is interesting not just because it makes attention faster on an H100 GPU, but because it shows how much room there still is to improve one of the most important primitives in modern AI. The headline result is simple: FlashAttention-3 is about $1.5$-$2.0\times$ faster than FlashAttention-2 on Hopper GPUs for FP16, reaches up to $740$ TFLOPs/s, and gets close to $1.2$ PFLOPs/s in FP8. It also improves FP8 numerical accuracy, reducing error by $2.6\times$ compared to a baseline FP8 attention setup.

That may sound like a hardware benchmark story, but the implications are broader. Faster attention does not just shave milliseconds off a kernel. It changes what kinds of contexts and workloads are practical.

## Why attention is the bottleneck

In a Transformer, attention computes similarities between query and key vectors, turns those scores into probabilities with softmax, and then uses those probabilities to mix the value vectors. In a standard implementation, the intermediate score matrix and probability matrix are written out to high-bandwidth memory. That is expensive, because moving data around can be slower than doing the math itself.

FlashAttention originally addressed this by fusing the attention computation into one kernel and avoiding those large intermediate writes. FlashAttention-2 improved the design further by parallelizing more of the work across the sequence dimension. FlashAttention-3 takes the next step: it adapts the algorithm to Hopper’s asynchronous hardware and low-precision FP8 support.

The important part is not the specific GPU instructions. It is the strategy. The paper identifies two big sources of wasted time in attention kernels: waiting on memory movement and waiting on non-matmul work, especially softmax. FlashAttention-3 tries to hide both.

## What FlashAttention-3 changes

At a high level, the paper uses three ideas.

First, it splits GPU work into producer and consumer roles so memory transfers and computation can overlap more cleanly. On Hopper, the Tensor Memory Accelerator can move data asynchronously, and the Tensor Cores can run matrix multiplies asynchronously as well. FlashAttention-3 uses warp-specialization to make that overlap explicit.

Second, it overlaps softmax with matrix multiplication. Softmax is essential, but compared to GEMM it has much lower throughput on the GPU. If the hardware is busy doing matrix multiplies, the softmax work can be scheduled in the gaps. The paper’s “pingpong” style scheduling alternates which warpgroup is doing GEMMs and which is doing softmax so the GPU stays busier.

Third, it targets FP8 Tensor Cores. FP8 can roughly double throughput relative to FP16 or BF16 on Hopper, but it comes with accuracy and layout challenges. The paper handles this with block quantization and incoherent processing, which help control error when outliers are present in the activations.

The result is a kernel that is not just faster in theory. It is measurably faster on real hardware.

## Why this matters for long-context models

The most obvious beneficiaries are long-context LLMs. When sequence length grows, attention becomes a larger share of total runtime, memory usage, and cost. That affects both training and inference.

For long-document tasks, faster attention means the model can process more tokens per second without hitting the same memory wall. That is useful for workflows like analyzing multiple papers, summarizing legal or financial documents, or reasoning over long chat histories. The paper explicitly calls out long-context use cases like modeling over multiple documents and large file collections.

For code models, the payoff is similar. Codebases are naturally long-context workloads: a model may need to look at many files, function definitions, and dependencies at once. If attention gets cheaper, it becomes easier to scale context windows without the whole system becoming prohibitively slow.

For multimodal models, attention is often even more central. High-resolution images, audio streams, and video all turn into long token sequences in one way or another. The paper points out that attention speedups matter for high-resolution images, audio, and video because these modalities quickly produce long sequences. If attention is the bottleneck, making it faster expands the practical ceiling on input size.

This is the key point: speedups in attention do not just improve one benchmark. They can expand the range of inputs a model can handle in the first place.

## What the benchmarks show

The paper evaluates FlashAttention-3 on an H100 SXM5 GPU. In FP16, it reaches up to $740$ TFLOPs/s, which is about $75\%$ utilization of the theoretical maximum on that hardware. It is about $1.5$-$2.0\times$ faster than FlashAttention-2 in the forward pass and $1.5$-$1.75\times$ faster in the backward pass.

It also compares against standard attention implementations and finds much larger gains there, sometimes $3$-$16\times$, depending on the setting. For medium and long sequences, FlashAttention-3 can even beat a vendor-optimized cuDNN attention implementation.

For FP8, the paper shows performance close to $1.2$ PFLOPs/s and validates that the accuracy is much better than a baseline FP8 attention approach. That matters because lower precision is attractive only if the model remains numerically stable enough to be useful.

## Why this is more than an optimization trick

It is tempting to think of attention speedups as pure infrastructure work, but they shape model design. If attention is expensive, developers may reduce context length, lower batch sizes, or avoid certain modalities. If attention gets faster, those trade-offs become less severe.

That can influence:

- long-context chat and retrieval,
- code completion and repo-level reasoning,
- document understanding,
- image and video modeling,
- audio and speech processing,
- agent systems that maintain long histories.

In other words, attention is one of the primitives that determines what scale of input a model can realistically process. Improvements here ripple upward into application design.

There is also a deployment angle. Faster attention lowers latency and increases throughput, which can directly reduce serving cost for inference workloads. That is especially relevant for applications that need to process long prompts or long histories repeatedly.

## The limits of the result

The paper is careful about its scope. FlashAttention-3 is demonstrated on Hopper GPUs, and the performance story depends on Hopper-specific capabilities like asynchronous execution and FP8 support. The authors expect the ideas to apply more broadly to other accelerators with similar features, but the benchmarked results are specific to H100.

There are also open questions. The paper notes future work on inference optimization, persistent kernels for FP8, and understanding low-precision attention in large-scale training. So this is not the final word on efficient attention.

But it is a strong signal that algorithm design still matters. Even when the core math is fixed, the way that math maps onto GPU execution can determine whether attention is merely usable or truly fast.

## Bottom line

FlashAttention-3 shows that a very familiar primitive still has a lot of performance headroom. By overlapping memory movement, GEMMs, and softmax, and by taking advantage of FP8 hardware carefully, the paper pushes attention closer to the limits of the H100.

That matters because attention is not a niche kernel. It is the core mechanism behind long-context LLMs, code models, and increasingly multimodal systems. When attention gets faster, the practical scope of these models expands with it.

The bigger takeaway is simple: if you want longer context windows, more capable code models, or richer multimodal inputs, one of the most important things you can do is make attention cheaper. FlashAttention-3 is a concrete step in that direction.
