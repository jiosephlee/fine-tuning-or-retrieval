\title{A Textbook about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

Chapter 3: GPU Systems Primer for Attention Kernels

# The GPU Memory Hierarchy

The paper presents Hopper as a machine with several levels of memory, each serving a different role in an attention kernel. At the outermost level is global memory, also called HBM, which is off-chip DRAM accessible to all streaming multiprocessors. Above that sits the L2 cache, which transparently caches data coming from global memory. Inside each SM is shared memory, a small on-chip, programmer-managed, highly banked cache. At the closest level is the register file, which is private to each thread.

For attention, this hierarchy matters because the kernel repeatedly reuses tiles of $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$. The key systems idea in the paper is that the more often a kernel can keep intermediate values in shared memory or registers instead of writing them back to HBM, the better it can exploit the GPU. FlashAttention-3 is built around exactly that principle.

# Bandwidth Versus Capacity Across Memory Levels

The paper emphasizes a familiar but crucial tradeoff: memory levels with larger capacity tend to offer lower bandwidth, while the smallest on-chip levels are the most bandwidth-rich. Global memory can hold a great deal of data, but it is the least attractive place to repeatedly store intermediate attention results. Shared memory and registers are much smaller, but they are the places where the kernel can move data quickly and repeatedly without paying the cost of HBM traffic.

This is why the paper treats memory locality as a first-class algorithmic concern. Standard attention materializes the intermediate matrices $\mathbf{S}$ and $\mathbf{P}$ to HBM, which is expensive. FlashAttention instead uses a local softmax reduction so that the attention computation can be fused into a single kernel and intermediate values can remain on-chip. The hardware hierarchy is not just a background detail; it is the reason the algorithm is structured around tiles and staged reuse.

# The Thread Hierarchy on Hopper

Hopper organizes execution units through a hierarchy of threads, warps, warpgroups, threadblocks, threadblock clusters, and grids. A warp contains 32 threads, and a warpgroup contains 4 contiguous warps. At larger scales, a threadblock is also called a CTA, and Hopper adds threadblock clusters above CTAs. These groupings determine how work is distributed and how closely different pieces of work can cooperate.

The paper also points out that this hierarchy is tied to placement on hardware. Threads in the same CTA are co-scheduled on the same SM, and CTAs in the same cluster are co-scheduled on the same GPC. Shared memory is directly addressable by all threads within a CTA, while registers are private to each thread, with at most 256 registers per thread. For attention kernels, this means the CTA is the natural unit of cooperation: it is large enough to do meaningful work, but small enough that threads can share on-chip state.

# Why CTAs and Shared Memory Matter for Fused Attention

The paper’s attention kernels are organized around CTA-level tiles. In the forward pass, a CTA works on a tile $\mathbf{Q}_i$ and produces the corresponding output tile $\mathbf{O}_i$. This structure is important because attention is not just a single matrix multiplication. It is a sequence of operations, including score computation, softmax, and the value projection, and those operations need somewhere local to share data while they are being fused.

Shared memory is that local workspace. FlashAttention-3 uses it to stage blocks of $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$ so that the kernel can avoid repeatedly reading and writing intermediate matrices to HBM. The paper describes FlashAttention’s local softmax as the mechanism that makes this possible: rather than materializing the full score and probability matrices, the kernel updates running quantities on-chip and only writes the final output. This is why fused attention kernels are naturally CTA-centric rather than built around isolated threads.

# Tensor Cores, CUDA Cores, and Specialized Hardware Units

A central message of the paper is that Hopper is not a uniform compute engine. Different hardware units specialize in different kinds of work. Tensor Cores are designed for matrix multiplication. CUDA cores handle logic, integer computation, and the remaining floating-point work. In addition, Hopper provides dedicated support for memory movement through the Tensor Memory Accelerator, or TMA.

This specialization is what makes asynchrony useful. The GPU can move data and perform matrix multiplies using hardware units that are separate from the cores running the rest of the program. FlashAttention-3 takes advantage of that separation rather than treating the GPU as if all work had to proceed in one synchronous stream. The result is a kernel that can keep more of the machine busy at the same time.

# Tensor Memory Accelerator for Asynchronous Data Movement

The Tensor Memory Accelerator is Hopper’s dedicated hardware unit for asynchronous memory copy between global memory and shared memory. In the paper’s execution model, TMA is the mechanism that makes data movement a separate activity instead of something that blocks the rest of the kernel. That is especially valuable for attention, where a CTA repeatedly has to stage new tiles of $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$ into shared memory.

The intuition is simple: while one part of the kernel is waiting for data to arrive, another part of the kernel should be doing useful work. TMA makes that possible by letting producer warps issue loads without tying up the computation side. In FlashAttention-3, this is one of the ingredients that enables the kernel to overlap memory movement with the matrix-multiplication and softmax work performed by the consumers.

# WGMMA: Hopper’s Asynchronous Matrix-Multiply Instruction

On Hopper, the Tensor Core interface used in the paper is the warpgroup-wide WGMMA instruction. Unlike the synchronous execution model assumed by earlier algorithms, WGMMA is asynchronous, and it can source its inputs directly from shared memory. This means that a warpgroup can launch a matrix multiply and then continue organizing later work while the hardware completes the operation.

The paper uses this property to rework the attention mainloop. In the forward pass, WGMMA performs the GEMMs that compute scores and apply values, and its asynchronous behavior creates room to hide other work behind it. This is particularly valuable because attention contains a mix of very high-throughput matrix multiplication and comparatively low-throughput operations such as the softmax’s exponentials and reductions. Hopper’s asynchronous WGMMA gives the kernel a way to keep the Tensor Cores busy while other work is being prepared or finished.

# Warp Specialization and Producer-Consumer Kernels

Warp specialization is the paper’s answer to the fact that data movement and computation are different jobs. Instead of having all warps in a CTA do everything, the kernel divides them into producer and consumer roles. Producer warps handle data movement, while consumer warps handle matrix multiplication and the related on-chip computation. In the paper’s wording, the warps of a CTA are split into producers or consumers that only ever issue either data movement or computation.

This separation helps in two ways. First, it gives the compiler a cleaner scheduling problem, because each group of warps has a more focused instruction pattern. Second, it lets the GPU hide latency more effectively, because the producer side can be staging upcoming tiles while the consumer side is working on the current ones. For attention, this maps naturally onto the flow from loading $\mathbf{Q}$, $\mathbf{K}$, and $\mathbf{V}$ to computing $\mathbf{S}$, softmax, and $\mathbf{O}$.

# Dynamic Register Redistribution with \texttt{setmaxnreg}

Hopper adds another feature that makes warp specialization practical: dynamic reallocation of registers between warpgroups using \texttt{setmaxnreg}. The paper highlights that not all warps need the same register budget. The warps issuing TMA are relatively lightweight, while the warps performing matrix multiplications need more registers to hold their operands and intermediate accumulators.

This matters because attention kernels are register-sensitive. If the consumer side can obtain a larger share of the register file, it is less likely to spill intermediate values and more likely to sustain high throughput. The producer side can give up some of its register allocation because it has a simpler job. The paper treats this as one of the key Hopper-specific tools that makes producer-consumer scheduling more efficient.

# FP16, BF16, and FP8 on Modern GPUs

The paper frames low precision as another form of specialization. Modern GPUs include hardware support for FP16, BF16, and FP8, and Hopper’s FP8 WGMMA can deliver 2x the throughput per SM compared with FP16 or BF16. This is one reason low-precision attention is attractive: if the hardware can do more work per cycle at the same power and chip area, then the throughput of the whole model can improve substantially.

At the same time, the paper is careful to note that lower precision is not free. FP8 introduces more numerical error than FP16 or BF16, so the kernel design has to be adapted to preserve accuracy. That is why FlashAttention-3 does not simply switch the datatype and stop there. The hardware opportunity is real, but so is the need to respect the numerical behavior of the format.

# Operand Layout Requirements for FP16 versus FP8 WGMMA

The paper defines the layout requirement in terms of a GEMM call that multiplies $A \times B^\top$, where $A$ is an $M \times K$ matrix and $B$ is an $N \times K$ matrix. An operand is called mn-major if it is contiguous in the outer $M$ or $N$ dimension, and k-major if it is contiguous in the inner $K$ dimension. This distinction is important because WGMMA does not accept all layouts equally.

For FP16 WGMMA, both mn-major and k-major input operands are accepted when the data lives in shared memory. For FP8 WGMMA, however, only the k-major format is supported. That stricter requirement creates a practical obstacle in attention, where one often wants to run back-to-back GEMMs in a single kernel. The paper notes that the output accumulator layout of one FP8 WGMMA does not naturally match the operand layout expected by the next, so dependent FP8 WGMMAs require explicit layout handling. This is one of the main reasons FlashAttention-3 needs additional transformations when it targets FP8.
