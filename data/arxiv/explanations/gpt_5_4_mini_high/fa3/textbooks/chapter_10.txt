\title{A Textbook about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

Chapter 10: Backward Pass, Attention Variants, and Implementation Considerations

# Why backward attention is more expensive than forward attention

The paper makes clear that the backward pass is not just the forward pass run in reverse. In the forward direction, attention computes $\mathbf{S} = \alpha \mathbf{Q}\mathbf{K}^\top$, then $\mathbf{P} = \mathrm{softmax}(\mathbf{S})$, and finally $\mathbf{O} = \mathbf{P}\mathbf{V}$. In the backward direction, the chain rule expands this into several separate matrix multiplications: $\mathbf{dV} = \mathbf{P}^\top \mathbf{dO}$, $\mathbf{dP} = \mathbf{dO}\mathbf{V}^\top$, $\mathbf{dS} = \mathrm{dsoftmax}(\mathbf{dP})$, $\mathbf{dQ} = \alpha \mathbf{dS}\mathbf{K}$, and $\mathbf{dK} = \alpha \mathbf{dS}^\top \mathbf{Q}$. The paper’s background section presents these formulas explicitly to show that gradient computation is structurally more involved than the forward computation.

This extra structure is reflected in the paper’s benchmark accounting. The authors note that the forward pass has two matmuls, while the backward pass has five matmuls because of recomputation, so they approximate backward FLOPs as $2.5$ times the forward FLOPs. That is the key reason backward attention is more expensive: even before considering memory movement, the derivative formulas themselves create more GEMM work. For a system paper like this one, that distinction matters because it explains why training kernels must be optimized separately rather than assumed to inherit forward-pass speed automatically.

# Recomputation versus storing intermediates in memory

A central idea behind FlashAttention, and therefore FlashAttention-3, is that it is often better to recompute some quantities than to write large intermediates to HBM and read them back later. The paper contrasts its approach with standard attention, which materializes the intermediate score matrix $\mathbf{S}$ and probability matrix $\mathbf{P}$ in HBM. Those matrices are large, and moving them through memory is expensive relative to keeping the computation on chip. FlashAttention avoids that cost by fusing the attention operations into a single kernel and using local softmax accumulation.

The same tradeoff appears in the backward pass. The gradient formulas depend on softmax quantities, but FlashAttention-3 does not treat that as a reason to store the whole $N \times N$ attention matrix. Instead, it follows the broader FlashAttention philosophy: spend more arithmetic if that helps avoid HBM traffic. The paper’s backward FLOP accounting, where the backward pass is counted as $2.5$ times the forward pass, is a compact way of expressing this design choice. In other words, recomputation is not a flaw of the method; it is an explicit part of the performance strategy.

# How the online-softmax state supports the backward pass

The online softmax used in the forward pass is more than a numerical trick. In the paper’s forward algorithm, each query row maintains the running maximum $m_i$ and running normalizer $\ell_i$ as the key blocks are streamed through the kernel. These values are updated block by block so that the kernel can compute the exact softmax without ever forming the full score matrix in HBM. At the end of the forward pass, the kernel computes $L_i = m_i + \log(\ell_i)$ and writes both $\mathbf{O}_i$ and $L_i$ to HBM.

That compact state is exactly the sort of information a backward kernel wants. The backward formulas require softmax-related information, but not necessarily a stored copy of every score. The online-softmax summary captures the normalization behavior of each row in a small amount of data, which is much cheaper to keep around than $\mathbf{S}$ or $\mathbf{P}$. The paper’s forward kernel therefore sets up the backward computation by preserving the row-wise log-sum-exp state, rather than forcing the implementation to cache enormous intermediates.

# The paper’s reported backward-pass speedups

The paper reports that FlashAttention-3 also improves training-time performance, not just inference-time performance. On the H100 SXM5 GPU, FP16 FlashAttention-3 is reported to be about $1.5$--$1.75\times$ faster than FlashAttention-2 in the backward pass. This is a meaningful gain because backward kernels are inherently heavier than forward kernels, so any improvement there directly affects end-to-end training throughput.

The authors present these backward results alongside their forward benchmarks to show that the hardware-aware redesign is not limited to the easier case. The forward pass reaches up to $740$ TFLOPs/s, while the backward pass still benefits substantially even though it must execute more matrix multiplications and manage more dependence structure. The fact that the backward speedup is somewhat smaller than the forward speedup is consistent with the paper’s own FLOP accounting: the backward path simply has more work to optimize.

# Extending warp specialization and overlap ideas to backward kernels

The excerpt gives explicit pseudocode for the forward kernel, but the underlying execution principles are broader than forward attention alone. The paper’s main hardware ideas are warp specialization, asynchronous data movement, and overlapping Tensor Core work with lower-throughput softmax-style work. Those are not forward-specific concepts. They are general scheduling tools for kernels that have a mix of GEMMs and scalar or elementwise operations, which is exactly the kind of mix the backward pass also contains.

The backward formulas for attention again involve matmuls and softmax derivatives, so the same Hopper execution model is relevant. The paper’s measured backward speedup indicates that these ideas do carry through to training. Even though the excerpt does not spell out the backward pseudocode in the same level of detail as the forward pass, the paper’s overall message is that the same asynchronous, warp-specialized philosophy is applied to make both directions of attention faster.

# Multi-query attention and grouped-query attention indexing strategies

The paper states that for multi-query attention and grouped-query attention, it follows the approach of FlashAttention-2 and adjusts tensor indexing accordingly. The purpose is to adapt the kernel to these attention variants without changing the underlying attention math. In the paper’s terms, the implementation modifies how tensors are indexed so that the kernel can handle the different sharing structure of queries, keys, and values.

The important point is that this is an implementation strategy, not a new attention formula. Multi-query and grouped-query attention reuse key and value information across query heads or groups, so the kernel has to map the right query blocks to the right key/value blocks. The paper’s solution is to change indexing rather than duplicate data, which keeps the attention computation compatible with the memory-efficient design of FlashAttention.

# Avoiding duplication of K and V in memory for MQA and GQA

Avoiding duplication of $\mathbf{K}$ and $\mathbf{V}$ is important because FlashAttention is built around reducing memory traffic. If the kernel were to replicate those tensors in HBM for every head or group, it would waste both bandwidth and storage, undermining one of the main advantages of the method. The paper explicitly says that its indexing strategy for multi-query attention and grouped-query attention is designed to avoid that duplication.

This is another example of the paper’s broader design pattern: prefer a smarter view of the same data over copying it. By keeping a single representation of $\mathbf{K}$ and $\mathbf{V}$ and letting the kernel address it appropriately, the implementation preserves the memory efficiency of the original FlashAttention approach. That matters especially in long-context settings, where memory pressure is already high and attention is already the computational bottleneck.

# Persistent kernels and load-balancing strategies

The paper notes an implementation difference between its FP16 and FP8 kernels that affects practical performance. For the benchmarks, FP16 FlashAttention-3 uses a persistent kernel and load-balancing strategy, while FP8 FlashAttention-3 does not. The paper treats this as one reason FP8 does not always match the strongest FP8 cuDNN kernels on small sequence lengths and with causal masking.

This distinction matters because good arithmetic alone is not enough; the kernel also has to keep the GPU busy in a balanced way. A persistent kernel and its load-balancing logic are part of how the FP16 implementation reaches strong utilization on H100. The paper positions the lack of the same treatment in FP8 as a limitation and a future improvement opportunity, rather than as a limitation of FP8 precision itself.

# Why the FP16 kernel includes persistence while the FP8 kernel currently does not

The paper is explicit that this is a current asymmetry in the implementation. FP16 FlashAttention-3 already includes the persistent-kernel design and the associated load-balancing strategy in its benchmarked implementation, whereas FP8 FlashAttention-3 does not yet incorporate that machinery. The result is that FP16 is more complete from a systems standpoint, even though FP8 is extremely fast in raw compute throughput.

The paper also links this to its limitations section. It says that future work includes optimizing for LLM inference and integrating a persistent kernel design into the FP8 kernel. That framing is important: the authors are not claiming FP8 is inherently less capable, only that the current FP8 implementation does not yet exploit all of the scheduling refinements available to the FP16 path. This helps explain why FP8 is less competitive in the smaller-sequence and causal-masking cases reported in the paper.

# Practical implementation with CUTLASS primitives

The paper implements FlashAttention-3 using CUTLASS primitives, specifically the Hopper-oriented WGMMA and TMA abstractions. This choice matches the algorithmic design closely. The core of FlashAttention-3 is built around asynchronous data movement from GMEM to SMEM and asynchronous block GEMMs on the Tensor Cores, so an implementation framework that already exposes those hardware capabilities is a natural fit.

The paper also emphasizes that implementation is not just about writing the idealized algorithm. The pseudocode represents the intended execution order, but the compiler can reorder instructions in ways that affect the overlap between GEMM and softmax. The authors therefore inspect the generated SASS to verify that the expected pipelining occurs. They also discuss register pressure, since deeper pipelines and larger tiles both consume registers and can force tradeoffs between pipeline depth and tile size. Those are exactly the kinds of practical concerns that matter when translating a hardware-aware algorithm into a fast kernel.

# Interfacing optimized kernels with PyTorch and Hugging Face libraries

The paper closes by saying that FlashAttention-3 is open-sourced under a permissive license and that the authors plan to integrate it with PyTorch and Hugging Face. This is an important implementation choice in its own right. A fast kernel only has broad impact if it can be used inside the software stacks that researchers and developers already rely on.

That integration goal fits the paper’s broader motivation. Attention is a core Transformer primitive, and the benefits of better speed and better numerical behavior only reach most users if the implementation is available through familiar libraries. By planning integration with PyTorch and Hugging Face, the authors are signaling that FlashAttention-3 is intended not just as a research prototype, but as a practical primitive for real training and inference workflows.
