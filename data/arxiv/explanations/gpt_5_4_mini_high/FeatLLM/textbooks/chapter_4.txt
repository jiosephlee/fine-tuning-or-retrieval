\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 4: 4. Problem Formulation and Learning Setting

# Formal Definition of the Labeled Tabular Dataset

FeatLLM is built for supervised tabular classification. The starting point is a labeled tabular dataset written as $\mathcal{D} = \{(\mathbf{x}^i, \mathbf{y}^i)\}_{i=1}^{N}$, where each pair contains one sample and its label. The notation makes two things explicit. First, there are $N$ total labeled examples available in the full dataset. Second, each sample $\mathbf{x}^i$ is a vector of $d$ input features, so the tabular data contain $d$ columns or attributes for every row. The label $\mathbf{y}^i$ is the target the model must predict.

This formulation matters because FeatLLM does not treat a table merely as a collection of numbers or categories. It treats the table as a supervised learning problem in which each sample has a known target class, and the method aims to learn from only a small portion of the available labeled data. The paper is explicit that the task is classification, and the label belongs to a predefined set of classes. In other words, the method is not designed for continuous prediction in this paper, but for deciding which class a sample should be assigned to.

The dataset abstraction is also important because it separates the raw sample values from the information needed to interpret them. In FeatLLM, the LLM is not asked to operate on bare values alone. Instead, the table is paired with natural language descriptions of the features, which gives the model a way to reason about what each column means.

# Input Features, Feature Names, and Feature Descriptions in Natural Language

Every feature in the tabular dataset has a natural language name, denoted by $F = \{f_j\}_{j=1}^{d}$. Each $f_j$ is the name or identifier of the $j$th feature. The paper also assumes that feature definitions are provided separately. This means the model is not only given the raw value of a feature, but can also be given a textual explanation of what that feature represents.

The paper further clarifies that the feature description can include the value type and, optionally, the definition of the feature. For categorical variables, examples of possible categories can also be provided. These details are not decorative; they are part of the input that makes language-based reasoning possible. A feature name alone may be too ambiguous to guide a model, especially if the same word could refer to different domains or if the values are not self-explanatory. By contrast, a name together with a type and a definition gives the LLM the semantic context needed to interpret the feature correctly.

This is one of the key reasons FeatLLM can function as a feature engineer. The method expects the LLM to infer relationships between the task and the input features using a prompt that includes the task description, the feature descriptions, and a few labeled examples. Because the features are described in natural language, the LLM can use its prior knowledge about what the features mean and how they may relate to the target label. That is a very different setup from treating the table as uninterpreted values.

# Classification as the Target Setting, Including Binary and Multiclass Tasks

The learning setting in FeatLLM is classification. The paper states that the label $\mathbf{y}^i$ is one of a predefined set of classes, which means the method is designed to decide among discrete outcomes rather than predict a continuous value. This includes both binary tasks, where there are two possible classes, and multiclass tasks, where there are more than two.

This distinction matters because the downstream reasoning in FeatLLM is organized around class-specific rules. The method does not simply ask whether a sample belongs to some abstract target. Instead, it aims to derive rules that help separate one class from another. In the methods section, the generated rules are associated with each class, and the final prediction is based on estimating the likelihood of each class. That design is naturally aligned with classification, where the central question is which label best matches the sample.

The experimental evaluation reflects this setting. The paper reports results across binary and multiclass tabular datasets from multiple domains. So while the formalism is general, it is always anchored in a discrete-label problem. This is important for understanding the rest of the framework, because the rules extracted by the LLM are not meant to describe the table in a generic way; they are meant to support class discrimination.

# The $k$-Shot Protocol and How Training Examples Are Sampled

FeatLLM is designed for the low-shot regime. The paper defines the $k$-shot setting as follows: from the full dataset of $N$ labeled samples, only $k$ labeled samples, where $k < N$, are randomly sampled to train the model. In practice, this means the learning algorithm must operate with very limited labeled data.

The low-shot setting is central to the motivation of the paper. In many tabular problems, collecting labels is expensive or difficult, so the method must make strong use of the small number of examples it is given. FeatLLM responds to this by using those few examples in two ways at once. They serve as training data for the downstream model, and they also serve as demonstrations inside the prompt that is shown to the LLM. This dual use of the same few labeled samples is a defining part of the framework.

Because only a small number of examples is available, sampling matters. The paper specifies that the labeled samples are randomly chosen from the dataset to form the $k$-shot training set. This random choice reflects the practical reality of low-shot learning: the method must be able to function from whatever limited labeled subset is available, while still trying to generalize to the remaining samples. The authors also note that some experiments use very small shot counts, such as 4-shot or 16-shot settings, to test the method in especially data-scarce conditions.

The low-shot setup also explains why the paper emphasizes prior knowledge. When labels are scarce, the model cannot rely only on statistical pattern learning from the data. It must also exploit the semantic information in the feature names and descriptions, as well as the reasoning ability of the LLM. The problem formulation therefore makes the few-shot regime not just an experimental choice, but a core assumption of the method.

# The Importance of Column Names, Types, and Definitions for Language-Based Reasoning

The paper places substantial emphasis on the role of feature metadata in enabling language-based reasoning. Column names, value types, and definitions are not treated as optional extras. They are necessary for turning a table into a task that an LLM can reason about meaningfully.

The reason is straightforward: the LLM is asked to infer relationships between features and labels, and to generate class-specific rules. Without names and definitions, the model would only see raw serialized values, which would make it much harder to infer what the variables mean. The feature type is especially important because it helps prevent type mismatches when the LLM formulates rules. For example, a rule for a numerical feature should be expressed differently from a rule for a categorical feature, and the prompt is designed to remind the LLM of these distinctions.

The paper also explains that the first stage of the prompting procedure asks the LLM to infer the causal relationship or tendency between the features and the task description without referring to the examples. This is meant to activate the model's prior knowledge and common sense about the domain. Then, in the second stage, the LLM uses the demonstrations together with the earlier reasoning to derive rules. That two-step structure only works because the feature metadata are available to anchor the language reasoning in the actual structure of the table.

The feature descriptions therefore serve a dual role. They help the LLM interpret the table, and they help it avoid getting distracted by irrelevant columns. The paper argues that this structured reasoning helps the model focus on more significant features and reduce the risk of spurious correlations. In a low-shot setting, that kind of guidance is especially important because the training data alone may not be sufficient to identify the right patterns.

# The Distinction Between Raw Tabular Inputs and Generated Rule-Based Features

A central idea in FeatLLM is that the raw tabular inputs and the final features used for prediction are not the same thing. The original data are the input samples $\mathbf{x}^i$ with their $d$ features. These raw values are used by the LLM to generate rules. The rules are then parsed and converted into new binary features.

In the paper, each generated binary feature indicates whether a sample satisfies a rule. For a given class, the sample is mapped to a binary vector of rule-based features. The notation used in the methods section is $\mathbf{z}_k^i \in \{0,1\}^R$, where $R$ is the number of rules per class. Each entry in this vector tells us whether the sample satisfies one of the extracted rules. This means the model is no longer working directly with the original table in the downstream classifier. Instead, it works with a transformed representation built from rules discovered by the LLM.

This distinction is essential to understanding the learning setting. The raw tabular input is the source of information, but the generated rule-based features are the representation that the final predictive model uses. FeatLLM therefore shifts part of the learning problem into feature construction. The LLM acts as a rule generator, and the downstream model acts on the resulting binary indicators.

The paper's formulation shows why this is beneficial in the few-shot setting. Rather than requiring the LLM to make a prediction for every sample at inference time, FeatLLM extracts rules once and then uses those rules as features for a simple classifier. So the raw table is transformed into a new feature space that is better suited for learning from few examples. This separation between original inputs and rule-based features is the core of the method's formulation and the key to its efficiency.
