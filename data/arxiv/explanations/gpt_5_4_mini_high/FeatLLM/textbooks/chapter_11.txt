\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 11: 11. Ablations and Deeper Analysis

# Ablation of Weight Tuning versus Simple Rule Counting

In the full \textsf{FeatLLM} model, the rules generated by the language model are converted into binary features, and a linear model learns how much each rule should contribute to a class decision. Concretely, the logit for class $k$ is computed as $\text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i$, where $\mathbf{z}_k^i$ is the binary rule vector for sample $\mathbf{x}^i$. This means the model does not merely count how many rules fire; instead, it learns a separate importance weight for each rule. The positive projection of the weights is also important, because it ensures that a generated feature cannot reduce the likelihood of its class during learning.

The ablation called \textsf{-Tuning} removes this learned weighting step and replaces it with simple rule counting, so every binary feature contributes equally. The paper reports that this hurts performance across the datasets. The result is intuitive: not all rules extracted by the LLM are equally informative, and some are much more relevant to the target than others. A weighted linear model can emphasize the useful rules and suppress those that are weak or noisy, while simple counting treats them all the same and therefore loses a large part of the benefit of feature engineering.

# Ablation of Ensemble Averaging

FeatLLM does not rely on a single set of extracted rules. Instead, it repeats the full rule-generation and rule-application process multiple times, trains a separate lightweight model for each trial, and averages the resulting class probabilities. If the learned weights from the $T$ trials are denoted by $\{\mathbf{w}[t]\}_{t=1}^T$, then the final prediction is formed by averaging the probabilities produced by each trial. The ensemble is made diverse by using a sufficiently high temperature during LLM inference and by randomizing the order of the few-shot demonstrations.

The \textsf{-Ensemble} ablation removes this averaging step and keeps only one trial. The paper finds that this consistently degrades performance in every setting. The reason is that individual rule sets can be imperfect: some trials may produce incorrect rules, miss part of the signal, or focus on a subset of the relevant columns. Averaging lets correct rules from other trials compensate for those mistakes. In the paper's view, this is closely related to self-consistency: rules that repeatedly appear across trials are more likely to be reliable. The authors also note that applying the same idea to other LLM-based methods would be expensive, because it would require multiple per-sample LLM inferences and therefore substantially increase computational cost.

# Ablation of Feature Descriptions in the Prompt

A core part of the prompt is the feature-description block, which tells the LLM what each column means, what type of value it contains, and sometimes what categories or definitions apply. This information is not cosmetic. It gives the model the vocabulary it needs to formulate rules that are consistent with the data type and the task. In the paper's prompt design, feature descriptions also help the LLM avoid type mismatches when writing rules, which matters because the rules are later parsed and executed as program code.

When the authors ablate this component through \textsf{-Description}, performance drops. The effect is especially strong in low-shot settings, where there are very few labeled examples to compensate for missing context. In that regime, the prompt must carry more of the burden of telling the model what is relevant. Without feature descriptions, the LLM has less guidance about which columns are meaningful and how they should be interpreted, so the extracted rules become less useful for prediction.

# Ablation of the First Reasoning Step Based on Prior Knowledge

The reasoning instruction in \textsf{FeatLLM} deliberately splits the LLM's inference into two steps. First, the model is asked to infer the causal relationship or tendency between the task description and the features using general knowledge or common sense, without looking at example demonstrations. Only after this does it use the examples to derive class-specific rules. The paper frames this as a structured reasoning path that resembles chain-of-thought prompting, but is adapted to tabular rule extraction.

The \textsf{-Reasoning} ablation removes that first prior-knowledge step. The reported result is that this weakens performance, especially when the data are scarce. The reason given in the paper is that the first step helps the model focus on more significant features and avoid spurious correlations in irrelevant columns. Without it, the LLM has less of a chance to apply its pretrained knowledge as a filter, so rule generation becomes more vulnerable to accidental patterns in the few examples it sees.

# How the Contribution of Each Component Changes with the Number of Shots

One of the most interesting findings in the ablation study is that the importance of the different prompt and modeling components depends on how many labeled samples are available. When the number of shots is small, the feature descriptions and the reasoning instruction matter most. This makes sense in the framework of the paper: with only a few examples, the model needs extra help from the prompt to inject prior knowledge and to identify which features deserve attention.

As the number of shots increases, the effect of weight tuning becomes stronger. The paper interprets this as the point at which the linear model has enough labeled data to estimate rule importance more accurately. In other words, the binary rules are already informative, but more data lets the model learn which ones should matter more. By contrast, the ensemble mechanism helps in all settings, which is consistent with the idea that averaging over diverse trials makes the overall system more robust regardless of the amount of supervision.

# Training-Time and Inference-Time Comparison with Other Methods

The paper compares runtime on the Adult dataset using a training set of $16$ shots. In that experiment, one A100 GPU is the default hardware, except for TabLLM, which uses four A100 GPUs for model parallelism. Under this setup, \textsf{FeatLLM} shows a relatively low inference time, close to that of conventional tabular methods. By contrast, methods that require the LLM to make end-to-end predictions for every sample, such as in-context learning, TABLET, and TabLLM, incur much higher inference latency.

Training time is more nuanced. \textsf{FeatLLM} is still comparable to other LLM-based approaches, but it requires only $30$ API queries, and these can be parallelized. The paper emphasizes that this does not impose a major budget burden. This is important because the expensive part of \textsf{FeatLLM} is concentrated in feature discovery, not in repeated per-sample prediction. Once the rules are extracted and parsed, the final predictor is lightweight.

# Why FeatLLM's Inference Cost Is Closer to Standard Tabular Models than to Other LLM Methods

The reason \textsf{FeatLLM}'s inference cost resembles that of standard tabular models is that the LLM is removed from the prediction loop. The LLM is used to engineer rules and convert them into features, but after that, a simple model handles inference. In the paper's formulation, prediction is based on a dot product with learned weights followed by a softmax, which is much closer to a conventional linear classifier than to a black-box language model.

This design is exactly what separates \textsf{FeatLLM} from end-to-end LLM tabular methods. In those methods, each test sample must be serialized, prompted, and passed through the LLM again, so the per-sample cost stays high. \textsf{FeatLLM} moves the costly reasoning into a one-time feature-generation stage and then reuses the discovered features for cheap downstream prediction. That is why its inference profile is closer to logistic regression or other simple tabular learners than to prompt-based LLM systems.

# Measuring the Informativeness of Generated Features Using AUROC

To check whether the extracted rules are actually informative, the paper evaluates the new binary features using AUROC. For each generated feature, it measures how well that feature aligns with the target labels, and then computes the average AUROC across features. The authors also compute the ratio of useful features, where a useful feature is one whose AUROC exceeds $0.5$. In the paper's interpretation, features above that threshold carry meaningful signal for the target task.

This analysis shows that the majority of the rules produced by \textsf{FeatLLM} are relevant to the target attribute even before any tuning is applied. That is an important diagnostic result, because it means the LLM is not just generating arbitrary text rules; it is actually discovering criteria that have predictive value. The feature-quality study therefore supports the paper's central claim that the LLM can serve as an effective feature engineer rather than only as a direct predictor.

# Ratio of Useful Rules Before and After Linear-Model Tuning

The paper further examines how the set of useful rules changes after the linear model has been trained. Before tuning, many of the generated rules already have AUROC above $0.5$, indicating that they are informative on their own. After tuning, however, rules that are only weakly related to the data tend to receive very small weights, and these are effectively filtered out. The paper reports this using the "Before tuning" and "After tuning" columns in its feature-quality table.

This difference matters because it shows that the linear model is not merely a classifier on top of a fixed rule set; it is also acting as a filter. The model learns which rules deserve influence and which should be ignored. The paper sets a threshold of $0.1$ when inspecting the learned weights, based on the overall histogram of weights, and uses that to identify rules with little relevance. The resulting picture is that tuning refines the LLM's raw output into a more selective and more task-specific feature representation.

# How Tuning Filters Weak or Irrelevant Rules Through Learned Weights

The learned weights in \textsf{FeatLLM} are directly interpretable as rule importance scores. Because the model uses nonnegative weights, a rule can contribute positively to the class logit, but a weak rule can contribute very little. That is exactly why tuning is useful: it distinguishes rules that are repeatedly supported by the data from rules that are only weakly related to the target. In the paper's analysis, rules with low learned weights are treated as effectively filtered out.

This filtering mechanism is especially valuable in low-shot learning, where some extracted rules may be plausible in language but not truly predictive. The tuning stage allows the model to exploit the fact that not all prompt-derived knowledge deserves equal treatment. In this sense, the linear model is not just a downstream classifier; it is a learned selector over the candidate rules. The feature-quality analysis provides direct evidence that this selector is working as intended.

# Robustness to Spurious Correlations by Adding Unrelated Columns

To test whether \textsf{FeatLLM} can resist noisy correlations, the paper performs an experiment on the Heart dataset by randomly attaching columns from the Adult dataset that are irrelevant to the Heart task. The model is then evaluated as more unrelated columns are added. For fairness, the comparison uses the same $8$ labeled shots and does not include an unlabeled dataset, which excludes methods such as SCARF and STUNT from the experiment.

The result is that \textsf{FeatLLM} suffers the least degradation among the compared methods. The paper attributes this to the way rule extraction is guided by prior knowledge about the relationship between the task and the features. In practice, that means the LLM is less likely to generate rules based on irrelevant columns. The authors also observe that only about $1$-$2\%$ of the rules were based on noisy columns, which supports the idea that the prompt design acts as a filter against irrelevant information.

# Why the Reasoning Stage Helps Ignore Irrelevant Features

The first step of the reasoning instruction is central to this robustness. By asking the LLM to infer a causal relationship or tendency between the task and the features before looking at demonstrations, the prompt forces the model to engage with the task at a more conceptual level. That prior-knowledge step makes it less likely that the model will latch onto columns that are not genuinely connected to the target. In the paper's interpretation, this is a key reason why the framework resists spurious correlations.

This does not mean the reasoning stage is a perfect safeguard, but it does provide a meaningful bias toward relevant features. The experiment with unrelated Adult columns shows that the model can largely ignore those distractions when the task-feature relationship is clearly mismatched. That is consistent with the ablation study as well: removing the reasoning step hurts performance, which suggests that the step contributes not just to accuracy but also to robustness.

# Limits of This Robustness When Unrelated Columns Come from Closely Related Domains

The paper is careful to note that this robustness has limits. If the added columns come from a closely related dataset, \textsf{FeatLLM} can still learn spurious correlations and even misunderstand causal relationships between the task and the features. This is an important caveat, because it shows that the prior-knowledge filter is helpful but not foolproof. When irrelevant columns look semantically plausible, the LLM may be tempted to treat them as meaningful.

This limitation matters for interpreting the spurious-correlation experiment. The fact that unrelated columns from Adult are mostly ignored does not imply that the method is immune to all forms of noise. Instead, the results show that the framework is robust when the extra columns are obviously off-task, but can still be misled when the distractors are more subtle. That is a realistic and useful characterization of the method's behavior.

# Hyperparameter Analysis for the Number of Ensembles

The paper identifies the number of ensembles as one of the two main hyperparameters of \textsf{FeatLLM}. As this number increases, performance improves, but only up to a point. The reported behavior is that gains begin to converge around $20$ ensembles. This means that ensembling is important, but there are diminishing returns once enough diversity has been collected across trials.

The interpretation is straightforward: more trials increase the chance that at least some of them will generate good rules, and averaging across trials smooths out individual errors. At the same time, each additional trial costs extra LLM queries and extra feature extraction work. The convergence around $20$ shows that the method can get most of the benefit of ensembling without needing an unbounded number of repeated prompts.

# Hyperparameter Analysis for the Number of Rules per Class

The second major hyperparameter is the number of rules extracted per class in each LLM query. The paper evaluates different choices and reports that there is no statistically significant difference across the tested values, but it still chooses $10$ rules as the best compromise. That choice is based on the trade-off between prompt length and performance.

The reason for that trade-off is tied to the structure of the method. More rules increase the dimensionality of the generated feature space and can provide more information to the linear model, but they also make the prompt longer and can increase the risk of overfitting in a low-shot regime. Fewer rules keep the prompt shorter and simpler, but may leave out useful conditions. The selected value of $10$ reflects the paper's attempt to balance those competing pressures.

# Performance Trade-offs Among Prompt Length, Feature Dimensionality, Diversity, and Overfitting

Taken together, the hyperparameter analysis shows that \textsf{FeatLLM} is balancing several tensions at once. Bagging and repeated prompting improve diversity and help control prompt size, but they also introduce extra computation. More rules expand the feature representation, but they also enlarge the prompt and the downstream input dimension. More ensembles provide robustness, but only until the predictions become stable enough that further repetition adds little.

This is why the paper treats bagging and ensembling as practical tools rather than purely theoretical ones. When the tabular input is large, the prompt can become too long for a single LLM query, so bagging helps keep each trial within the available context window. At the same time, the authors argue that too many rules can lead to overfitting in the low-shot regime, while too few can underrepresent the task. The final method therefore uses a small number of carefully chosen rules, repeated across multiple diverse trials, to navigate the trade-off between expressiveness, robustness, and feasibility.
