\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### What kinds of decision boundaries cannot be represented by FeatLLM's positive weighted rule sums?
Question:
I'm trying to understand the expressive power of the final classifier. For each class $k$, FeatLLM computes a logit as a non-negative weighted sum of binary rule indicators for that class, then applies softmax across classes.

This seems like a monotone model with respect to the activated rules of a class: satisfying more class-$k$ rules can never hurt class $k$. That sounds reasonable at first, but it also seems restrictive. For example, if two individually useful rules become misleading when they co-occur, or if evidence for one class should actively count against another, I don't see how the model can represent that.

Is there a standard way to characterize the function class induced by this architecture, and what important types of tabular patterns would it miss?
Answer:
What FeatLLM uses at the end is essentially a multiclass linear model on binary rule features, with an additional nonnegativity constraint on the coefficients. For class $k$ the score is

$$
s_k(\mathbf z_k)=\max(\mathbf w_k,0)^\top \mathbf z_k,
$$

and then the class probabilities come from $\mathrm{softmax}(s_1,\dots,s_c)$. So, before the softmax, each class score is an additive, monotone function of that class’s rule indicators: turning on another rule for class $k$ can only keep $s_k$ the same or increase it. That is exactly the inductive bias the paper describes when it says the positive projection “ensures that the features generated by the LLM do not reduce the likelihood of a class during learning.”

This means the downstream classifier is best thought of as a monotone linear model, or more precisely a nonnegative linear model over binary rules. In terms of expressivity, it can represent boundaries that are linearly separable in the rule space with nonnegative weights, but it cannot learn inhibitory effects among those same rules. So if the true pattern is something like “rule A is evidence for class $k$ only when rule B is absent,” or “having both A and B together should hurt class $k$ even though each one alone helps,” this model cannot express that directly. Likewise, it cannot represent XOR/parity-like behavior, where the class depends on whether an odd or even number of rules are active, because those are inherently non-monotone. Any pattern that requires a rule to act as a veto, or requires a negative contribution from a satisfied rule, is outside this function class.

The softmax does introduce competition across classes, so a rule that boosts class $k$ will indirectly lower the probability of the other classes. But that is not the same as allowing negative evidence inside a class score. The architecture can say “this looks more like class $k$ than the others,” but it cannot say “this rule specifically argues against class $k$” unless that information is encoded in some other class’s rules and score. So the restriction is local to each class score, even though the final prediction is multiclass.

A useful way to see the tradeoff is that FeatLLM pushes the hard nonlinearity into the LLM-generated rules, and then keeps the final learner deliberately simple. If the LLM produces a rule like “age $> 65$ and chest pain present,” then the linear classifier can weight that rule. But if the useful pattern depends on a more subtle interaction that is not already captured by a rule, the final model cannot invent that interaction on its own. That is why the paper emphasizes robustness and few-shot stability rather than maximal expressivity: the positive-weight rule sum is a strong inductive bias, not a universal approximator.

So the short answer is that FeatLLM’s classifier misses genuinely non-monotone tabular patterns: veto effects, XOR-style interactions, context-dependent rules, and any decision boundary where satisfying more of the same-class rules should sometimes make the class less likely. The paper’s design intentionally avoids those patterns in the final layer, relying instead on the LLM to generate rules that already encode the relevant structure.
