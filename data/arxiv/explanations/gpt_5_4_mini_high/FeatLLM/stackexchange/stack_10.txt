\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Does FeatLLM risk overfitting twice by using the same few-shot examples for both rule generation and weight fitting?
Question:
As I understand the method, the few-shot labeled samples are used first inside the prompt so the LLM can generate class-specific rules, and then the same few-shot samples are used again to train the linear weights on the resulting binary features.

This makes me wonder whether the method is effectively fitting the same tiny dataset twice: once implicitly through the prompted rule extraction and once explicitly through supervised training of the linear model. If so, why doesn't this lead to severe overfitting or target leakage?

Is the intended argument that the first stage is mostly injecting external prior knowledge from the LLM rather than memorizing the examples? I'd appreciate a more careful explanation of why this two-stage use of the same examples is methodologically acceptable.
Answer:
Short answer: it is a form of support-set adaptation, but not “target leakage,” and not really “fitting the same data twice” in the usual sense. In \textsf{FeatLLM}, the LLM is not trained on the few-shot examples; it is frozen and only conditioned by the prompt. The examples are used once to help the LLM instantiate a task-specific rule set, and then those rules are turned into binary features for a separate, very low-capacity linear model. The paper is quite explicit that Step 1 is meant to use the LLM’s general knowledge without referring to the demonstrations, while Step 2 uses the demonstrations plus that prior reasoning to derive class rules. So the first stage is best thought of as feature generation under a prior, not as parameter fitting to the tiny labeled set.

The second stage is ordinary supervised learning on engineered features. Using the same few-shot labels there is standard in few-shot learning: you use the support set both to define the representation and to fit the classifier, while evaluation happens on held-out test samples. That is not leakage unless the test labels or test instances influence rule generation, which the paper does not do. What can happen, of course, is ordinary overfitting to the support set, because the rule generator can still produce overly specific rules. The authors acknowledge this risk and try to control it by fixing the number of rules per class, randomizing prompt order, using a relatively high temperature, and then bagging/ensembling multiple rule sets so that unstable or spurious rules are averaged out. Their ablations also show that the weight-tuning step helps by filtering weak rules, which suggests the linear model is acting as a regularizer rather than simply memorizing the few shots.

So the intended methodological story is exactly that the first stage injects prior knowledge from the LLM and the second stage learns how to weight the resulting rules. That is acceptable because the two stages do different jobs: one proposes candidate features, the other selects among them. If anything, the main limitation is not leakage but variance: with very few labeled samples, the quality of the generated rules still depends heavily on how well the LLM’s prior matches the task.
