\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does feature bagging reduce prompt length without throwing away important columns?
Question:
The paper says FeatLLM can handle wide tables by using bagging over subsets of features or instances, which helps stay within the LLM context window. I understand how this reduces prompt length mechanically, but I don't understand why it should preserve performance.

If an important predictive interaction involves two columns that are often separated into different feature bags, then no single trial would ever see that interaction and therefore no rule could mention it. The paper argues that an ensemble of weak learners can compensate for incomplete coverage, but I don't see why that would recover interactions that were never jointly observed.

Is the claim mainly that many tabular tasks can be solved with marginal or low-order rules, or is there another reason bagging should work here?
Answer:
Feature bagging in \textsf{FeatLLM} is not supposed to preserve every interaction in every prompt. It is a way to make the prompt fit, while recovering robustness by repetition. Each individual LLM call sees only a subspace of the table, so yes, some interactions will be invisible in that particular trial. The paper’s bet is that this is acceptable because the method is not a single-shot rule extractor: it runs many trials, randomizes the feature/instance subsets, and then averages the resulting class probabilities. In other words, it is using a random-subspace ensemble, not trying to solve the whole tabular problem in one prompt.

The key intuition is that many tabular datasets are not dominated by one irreducibly high-order interaction. Often the signal is redundant: a useful interaction can usually be approximated by several lower-order rules, or at least one of the involved columns can be correlated with a feature that is present in another bag. Since \textsf{FeatLLM} asks the LLM to generate a small fixed number of rules per class, and then learns weights on those binary rule-features, the downstream model only needs a few informative rules to get a good predictor. Across $T$ trials, different bags expose different columns to the LLM, so an important feature does not have to appear in every prompt; it only has to appear often enough that some trials generate the right rule. The paper explicitly frames this as self-consistency: rules that recur across trials are more likely to be correct, and the ensemble can compensate when some individual rule sets are incomplete.

So the short answer to your concern is: no, bagging does not magically recover an interaction that is never jointly observed. If a task truly depends on a nonredundant interaction between two columns, and those two columns are almost never placed together in the same bag, performance can certainly suffer. The paper does not prove otherwise. What it claims, and what the experiments support, is weaker but practical: on the kinds of few-shot tabular tasks they test, the important structure is often captured by relatively low-order rules, the tables contain enough redundancy that different bags still expose the useful signal, and the ensemble smooths over the missing pieces. That is why bagging helps both with prompt length and with robustness, rather than simply discarding information.

This is also consistent with their ablations and analysis: performance improves with more ensembles, and they note that a single rule set may not capture all feature relationships, but multiple weak learners can offset incomplete coverage. So the claim is not “bagging preserves every interaction”; it is “bagging reduces context size while usually preserving enough of the predictive structure for the ensemble to work well.”
