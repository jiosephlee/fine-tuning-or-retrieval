\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Is using the LLM again for rule parsing really different from doing LLM-based prediction at inference time?
Question:
One of the paper's main motivations is avoiding the need to query the LLM for each test sample. But in the parsing stage, the authors also use the LLM to translate natural-language rules into executable Python code.

I'm confused about where the cost savings actually come from. Is the idea that the LLM is only used a small number of times offline to generate and parse the rules, and then the resulting code is applied to all future samples without any more LLM calls?

If that's the intended distinction, could someone clarify why this is categorically different from earlier LLM-for-tabular methods, rather than just moving the LLM queries from test time to a preprocessing stage?
Answer:
Yes — that is exactly the intended distinction in the paper, and the savings come from **amortizing the LLM calls over the whole dataset/task rather than paying for them on every test example**.

In \textsf{FeatLLM}, the LLM is used in an offline feature-engineering stage to generate rules from a few labeled examples and then to translate those natural-language rules into executable code. That parsing step is not the prediction step itself; it is just a way to turn the LLM’s output into a machine-readable transformation. Once the code is generated, the same rules are applied to all samples to create binary features, and the final prediction is made by a simple downstream model, such as a linear classifier. This is why the paper says that inference “only uses this simple predictive model with the discovered features” and “eliminates the need to send queries to the LLM for each sample at inference time.”

So the distinction from earlier LLM-for-tabular methods is not that \textsf{FeatLLM} somehow avoids using the LLM altogether; it doesn’t. The difference is **where the LLM sits in the pipeline**. Prior methods keep the LLM in the hot path for prediction: each test row is serialized and passed through the LLM to produce a label. That means you pay an LLM forward pass per test sample, and you also run into prompt-length limits because the whole table row has to fit in context. In \textsf{FeatLLM}, the LLM is used to build a compact representation once, and then ordinary ML handles the repeated per-sample inference. That is much closer to classical feature engineering than to end-to-end LLM inference.

There is still a cost, of course: if you move to a new tabular task, you have to rerun the rule-generation/parsing stage for that task. But that cost is paid once per task, not once per example. The paper’s runtime discussion makes exactly this point: training still involves some API queries, but the number is small, and the inference time becomes comparable to conventional methods because the LLM is no longer queried for every prediction.

So the short answer is: **yes, the paper is deliberately shifting LLM usage from per-sample prediction to one-time feature discovery and rule compilation. That is the core reason it is different from earlier LLM-based tabular predictors.**
