\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Few-Shot Learning for Spreadsheets: Why LLMs Can Help When You Only Have a Handful of Rows

## The problem: when labels are scarce, tabular learning gets awkward

A lot of real-world machine learning happens on tables, not images or text. Think about patient records, bank customer data, loan applications, or business spreadsheets. These datasets are often useful, but labeled examples are expensive. In healthcare, each label may require expert review. In finance, labels may come from slow outcomes or scarce human judgment. In business settings, the relevant events may simply be rare.

That is the setting of few-shot tabular learning: trying to build a classifier from only a small number of labeled rows. This is hard for ordinary tabular models because, with so little data, they can easily overfit to noise or latch onto spurious correlations. A model may notice a pattern in a handful of rows that looks important but does not actually generalize.

This is especially tricky for tabular data because the columns are often heterogeneous. One column might be numeric, another categorical, another text-like metadata. The structure is not as uniform as pixels in an image or tokens in a sentence, so there is less built-in signal for the model to exploit.

## Why large language models can help

Large language models bring something traditional tabular models do not: prior knowledge. They have seen a huge amount of text during pretraining, so they often know high-level relationships that matter in the real world.

For example, in healthcare, age and symptoms are often relevant to diagnosis. In finance, income, credit-related fields, and customer history can matter a lot. In business data, features such as purchase history, account status, or campaign response may be informative. An LLM can use that prior knowledge to make better guesses about which columns matter, even when only a few labeled examples are available.

That is why recent LLM-based tabular methods serialize rows into text and ask the model to predict directly. But that approach has two practical problems. First, it usually requires an LLM call for every test example, which is expensive. Second, long tables can create very long prompts, and prompt length becomes a real bottleneck when a dataset has many columns.

## FeatLLM takes a different approach

The key idea in the paper is simple: do not use the LLM as the final predictor. Use it as a feature engineer.

FeatLLM asks the LLM to read the task description, the feature descriptions, and a few labeled examples, then produce explicit rules for each class. In other words, instead of saying “predict this row,” the prompt asks the model to figure out the criteria that define the class.

The process is structured in two steps. First, the LLM is guided to reason about the relationship between the task and the features using its own prior knowledge. Second, it uses that reasoning plus the few examples to generate class-specific rules. The paper fixes the number of rules per class at 10, which helps keep the prompt manageable.

Once those rules are generated, FeatLLM turns them into new binary features: for each rule, the feature is $1$ if a row satisfies the rule and $0$ otherwise. The system then trains a simple linear model on top of these rule-based features to estimate class probabilities.

This matters because, after feature engineering, inference no longer needs the LLM. The LLM is used to discover the rules, but prediction itself is done by a lightweight downstream model. That makes inference much cheaper and avoids sending every test row back through the LLM.

## How FeatLLM keeps the rules usable

Natural-language rules are messy. Even if you ask the model for a structured response, it may phrase a condition in slightly different ways, such as using “greater than” instead of $>$ or changing the wording of a comparison. FeatLLM handles this by using the LLM again to turn the inferred rules into executable code, which is then run in Python to generate the binary features.

The paper also adds bagging and ensembling. In practice, FeatLLM repeats the rule-generation process multiple times, using shuffled examples and subsets of features or instances. This does two things. It makes the method more robust, because bad rules from one run can be offset by better rules from another. And it helps with prompt-size limits, because each run only has to see part of the table.

## What the experiments show

The authors evaluate FeatLLM on 13 datasets covering binary and multiclass classification. The list includes healthcare datasets like Diabetes, Heart, and Myocardial; finance and business-style datasets like Adult, Bank, and Credit-g; and newer or synthetic tasks such as Cultivars, NHANES, Sequence-type, and Solution-mix.

Across these benchmarks, FeatLLM is usually the best or second-best method. The paper reports that it outperforms alternatives such as TabLLM and STUNT by about 10% on average. One especially striking result is that FeatLLM with only 4 labeled examples can match conventional tabular baselines that need 32 examples.

It also behaves well when the table has many columns. Methods that rely on end-to-end LLM prediction struggle when the prompt gets too long, but FeatLLM is more resilient because it is not trying to send the entire prediction problem through the LLM at inference time.

## Why this is useful in practice

This is a good fit for settings where labels are costly, but domain knowledge is plentiful. In healthcare, you may only have a handful of annotated patient records but a lot of expert intuition encoded in the medical literature. In finance, you may know broadly which attributes matter for risk assessment, even if you do not have many labeled cases. In business, you may want to predict outcomes from small samples of campaign or customer data, where collecting more labels is slow or expensive.

FeatLLM is also practical because it only requires API-level access to an LLM. It does not require fine-tuning the model, which matters when the LLM is only available through an inference API. And because the expensive LLM step happens during feature generation rather than every prediction, the runtime cost at inference is much lower than that of many other LLM-based tabular methods.

## The main takeaway

FeatLLM shows that LLMs do not need to be used as black-box predictors for every row in a spreadsheet. In low-shot tabular learning, they can be more useful as knowledgeable feature engineers: read a few examples, infer useful rules, turn those rules into features, and let a simple model do the actual prediction.

That shift is the real contribution of the paper. It keeps the benefits of LLM prior knowledge while avoiding some of the biggest pain points of LLM-based tabular learning: per-sample inference cost, fine-tuning requirements, and prompt-length limits.

The method is designed for low-shot settings, so it is not a replacement for standard tabular models on large labeled datasets. But when you only have a handful of rows and need something that can still reason with domain knowledge, FeatLLM is a strong and practical option.
