\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Why FeatLLM Beats End-to-End LLM Prediction on Tabular Data

Large language models have become a natural fit for text, but tabular data is a different beast. A row in a spreadsheet is not a sentence, and a good prediction often depends on subtle combinations of columns rather than fluent reasoning over words. Most LLM-based tabular methods handle this by serializing each row into text and asking the model to predict directly. That works, but it comes with a cost: every prediction requires an LLM call, prompts grow quickly as the number of columns increases, and fine-tuning is often required to get strong results.

The paper behind FeatLLM takes a different route. Instead of using the LLM as the final predictor, it uses the LLM as a feature engineer. In other words, the model is asked to discover rules that explain the task, and those rules are turned into new binary features. A lightweight downstream classifier then uses those features to make predictions. That small shift in role is what makes FeatLLM both more practical and, in the paper’s experiments, more accurate than end-to-end LLM prediction methods.

## The core problem with end-to-end LLM tabular prediction

End-to-end tabular LLM methods usually follow the same recipe: describe the task in natural language, serialize the columns and values, add a few labeled examples, and let the LLM predict the label. Some methods also fine-tune the backbone with parameter-efficient techniques like LoRA or IA3.

The issue is that this makes inference expensive and fragile. Every test sample has to go through the LLM. If the table has many features, the prompt can become too long, which is especially problematic for datasets with over 100 columns. The paper also points out that some strong LLMs are only available through inference APIs, so training or fine-tuning them is not always possible. That is a real constraint if you want to deploy a model in practice rather than just benchmark it.

FeatLLM is designed to avoid those bottlenecks.

## FeatLLM turns the LLM into a rule generator

Instead of asking the LLM to output the final class for each row, FeatLLM asks it to extract the conditions that define each class. The prompt is structured in two steps.

First, the LLM is guided to reason about the relationship between the task and the features using its prior knowledge. For example, in a medical task, it can infer which kinds of measurements or patient attributes are plausibly relevant. Second, using a few labeled examples, it derives class-specific rules. These rules are written in a constrained format so they can be parsed automatically.

Those rules are then converted into binary features. For each sample, a feature says whether or not the sample satisfies a given rule. A simple linear model then learns how important each rule is for each class. The paper uses non-negative weights, followed by a softmax over class logits.

This is the key idea: once the rules are extracted, inference no longer needs the LLM. The LLM is only used to engineer features, not to score every test row.

## Why this is more practical

FeatLLM has three advantages that matter in real deployments.

First, inference cost is much lower. After rule extraction, prediction uses only the lightweight downstream model. The paper reports that FeatLLM’s inference time is comparable to conventional methods, while end-to-end LLM baselines such as in-context learning, TABLET, and TabLLM are much slower because they must call the LLM for each sample.

Second, it works with API-only access. FeatLLM does not rely on fine-tuning the LLM backbone. That makes it usable even when the model is only exposed through an API, which is common for strong proprietary models.

Third, it scales better to wide tables. The paper uses bagging over features and examples, plus an ensemble of multiple runs, to keep prompts smaller and improve robustness. This matters because serialized tabular data can blow past prompt limits quickly. By generating rules on subsets of the data and combining the results, FeatLLM avoids the “too many columns” failure mode that hurts many direct prompting approaches.

## What the experiments show

The paper evaluates FeatLLM on 13 tabular classification datasets spanning standard benchmarks, newer UCI additions, and synthetic tasks. Across these datasets, FeatLLM is consistently top-performing or near the top. The authors report that it outperforms alternatives such as TabLLM and STUNT by about 10% on average.

A few results are especially telling. With just 4 labeled examples, FeatLLM can match conventional tabular models that need 32 shots. That suggests the rules extracted by the LLM are doing real work, not just acting as a fancy wrapper around a small classifier. The method is also more robust on datasets with many features, where end-to-end LLM methods struggle because the prompt becomes too large.

The ablation study backs this up. Removing the tuning step, the ensemble, the feature descriptions, or the reasoning guidance all hurt performance. In other words, the gains come from the full pipeline: structured prompting, rule extraction, lightweight learning, and ensembling.

## Why FeatLLM is a better fit for tabular data

The main lesson from this paper is that tabular prediction does not need to be an all-or-nothing LLM problem. If you use the LLM to discover useful rules once, you can hand off the actual prediction task to a simpler model that is cheaper, faster, and easier to deploy.

That makes FeatLLM especially appealing in low-shot settings, where labels are scarce and prior knowledge matters. It is also a better fit for tables with many columns, where prompt length and inference cost can become deal-breakers.

In short, FeatLLM wins not because it asks the LLM to do more, but because it asks the LLM to do less — and to do the most valuable part of the job: finding the right features.
