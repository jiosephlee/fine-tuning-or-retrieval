\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Stop Asking the LLM Every Time: How FeatLLM Turns GPT Into a Feature Engineer

Tabular data powers a lot of real-world machine learning: credit risk, medical diagnosis, customer churn, and more. These problems are often low-data and high-stakes, which makes them a natural fit for methods that can use prior knowledge.

Large language models are attractive here because they already know a lot about the world. But most LLM-based tabular methods use that knowledge in the most expensive way possible: they serialize each row into text and ask the LLM to make a prediction for every sample. That works, but it is slow, costly, and often brittle when the table has many columns.

The key idea in **FeatLLM** is to use the LLM differently. Instead of asking it to predict every row, the paper asks it to act like a **feature engineer**. The LLM is used once to discover useful rules from a few labeled examples. Those rules are then turned into new features, and a simple downstream model handles prediction.

In other words: **ask the LLM to write the rules, not to score every row**.

## Why this shift matters

This change sounds small, but it solves several practical problems at once.

First, it lowers inference cost. Once FeatLLM has generated its rules, new samples do not need to go through the LLM. Prediction is done with a lightweight model, so deployment is much cheaper and faster than methods that require an LLM call for every input row.

Second, it avoids fine-tuning. FeatLLM only needs API-level access to an LLM such as GPT-3.5. That is important because many strong LLMs are not available for training or parameter-efficient tuning.

Third, it handles long tabular inputs better. Serializing many columns into a prompt can quickly hit context limits. FeatLLM uses bagging and ensembling to keep each prompt smaller and still remain robust.

Finally, it is a better fit for few-shot tabular learning. When only a handful of labeled examples are available, a model that can use prior knowledge to propose sensible rules can be much more useful than one that tries to learn everything from scratch.

## How FeatLLM works

The pipeline has three main parts.

First, FeatLLM prompts the LLM with task information, feature descriptions, and a few labeled examples. The prompt is structured to mimic an expert’s reasoning process. The paper splits this into two steps: the model first infers the relationship between the features and the target task, and then it derives class-specific rules using that understanding plus the few-shot examples.

Second, those natural-language rules are converted into executable code. Each rule becomes a binary feature: does this row satisfy the rule or not? If a sample matches a rule, the feature is $1$; otherwise it is $0$.

Third, a simple linear model learns how important each rule is for each class. The paper uses non-negative weights and softmax to estimate class probabilities. So the LLM is not making the final prediction directly; it is generating a rule set that a conventional model can use.

There is one more important piece: **ensembling with bagging**. FeatLLM repeats the rule-generation process multiple times, using different subsets of features or samples and different prompt orders. This helps in two ways. It makes the final prediction more robust, and it reduces the chance that a long prompt will exceed the LLM’s context window.

## What makes this approach different from standard LLM tabular methods

Most LLM-based tabular methods are end-to-end. They turn a row into text, send it to the LLM, and get a prediction back. That means every sample at test time depends on the LLM.

FeatLLM breaks that dependency. The LLM is used during feature discovery, but not during inference. After the rules are extracted, the system behaves like a normal tabular model built on engineered features.

That makes a big difference in deployment. A team can use an external LLM through an API, generate the features once, and then serve predictions with a cheap classifier. There is no need to keep paying for LLM inference on every sample.

## What the experiments show

The paper evaluates FeatLLM on **13 tabular datasets** covering binary and multiclass classification tasks. These include familiar benchmarks like Adult, Bank, Heart, and Diabetes, as well as newer and synthetic datasets designed to test whether the model is relying on memorized knowledge.

Across these datasets, FeatLLM is consistently strong. The paper reports that it usually ranks first or second among the compared methods, and it outperforms alternatives such as TabLLM and STUNT by about **10% on average**. In some low-shot settings, FeatLLM with just **4 labeled examples** performs comparably to conventional tabular baselines that need **32 examples**.

The paper also shows why the rule-based approach helps. When irrelevant columns are added to the data, FeatLLM is less sensitive than other methods. That suggests the two-step prompting strategy helps the LLM focus on meaningful relationships rather than spurious correlations.

## The main takeaway

FeatLLM is not trying to replace tabular models with an LLM at prediction time. It is using the LLM where it is strongest: reasoning over a small amount of information and proposing useful structure.

That makes the model more practical. It needs only API access, it avoids per-sample LLM inference, it works well in few-shot settings, and it is more usable on tables with many columns.

The broader lesson is simple: sometimes the best way to use an LLM is not to let it make the final prediction. Sometimes the best use is to have it do what humans do well in tabular problems: **find the rules, engineer the features, and let a lightweight model do the rest**.
