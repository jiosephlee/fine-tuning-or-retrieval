\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### If the LLM already generates class-specific rules, why is a trained linear model still needed afterward?
Question:
I'm trying to understand the overall pipeline of FeatLLM. The paper says the LLM generates rules for each class, then each rule is converted into a binary feature, and then a simple linear model is trained on top of those features.

What I don't fully understand is why the linear model is necessary at all. If the rules already represent conditions for each class, wouldn't it be enough to count how many rules of each class are satisfied and choose the largest count? The paper briefly says not all rules are equally important, but I still don't see why this requires a learned model instead of a fixed scoring scheme.

Can someone explain what failure case the linear model is solving, especially in a few-shot setting where there are very few labels to estimate the weights?
Answer:
Because in \textsf{FeatLLM} the rules are not treated as the final classifier; they are treated as binary features. A fixed “count the satisfied rules” scheme is just the special case where every rule gets weight $1$. The paper’s point is that the LLM-generated rules are useful but noisy, so different rules should not be assumed equally reliable. That is exactly what the small linear model is doing: it learns a weighted vote over the rule-features, with logits of the form $\max(\mathbf{w}_k,0)\cdot \mathbf{z}_k$. If one rule is highly predictive and another is weak or even occasionally misleading, the model can upweight the former and nearly ignore the latter. A plain count cannot do that.

The failure case the authors are trying to avoid is very simple: the LLM may generate several rules for a class, but some are broad, redundant, or only loosely related to the label. If you count all satisfied rules equally, then a class with more or looser rules can win just because more of its rules fire, even if those rules are not very informative. The paper explicitly says this in the methods section: “not all rules and features carry the same importance,” and in the ablation study the variant that replaces tuning with a raw sum of binary features (\textsf{-Tuning}) performs worse. They also show that after tuning, low-weight rules are effectively filtered out, which is exactly the behavior you want when the rule set is imperfect.

In the few-shot setting, the linear model is still feasible because it is extremely small: it only learns one nonnegative weight per generated rule, not a deep classifier. So although the labeled set is tiny, the parameter count is tiny too. Think of it as a calibrated weighted majority vote learned from the few examples, rather than a complex model that needs lots of data. The paper’s own analysis says the benefit of this tuning becomes larger as the number of shots increases, but even in the low-shot regime it helps because it suppresses unhelpful rules instead of assuming all generated rules are equally good.

So the short answer is: if the LLM produced perfect, equally reliable rules, counting would be enough. FeatLLM does not assume that, and the linear layer is the simplest way to learn rule importance from the few labeled samples the method has.

### What exactly is being learned in FeatLLM, and what part stays fixed after rule generation?
Question:
The paper says FeatLLM uses the LLM as a feature engineer and that only a simple downstream model is used at inference time. I think that means the LLM is not updated, but I'm getting confused about which objects are fixed and which are trained.

After the LLM produces rules and those rules are parsed into code, are the generated binary features completely fixed for the entire dataset? Then is the only learned part the set of weights $\mathbf{w}_k$ in Eq. (1)?

I'm asking because the method feels halfway between feature engineering and model training, and I want to be sure I understand whether FeatLLM is learning from the original tabular features directly, or only from the LLM-produced rule indicators.
Answer:
Yes — in \textsf{FeatLLM}, the LLM itself is not trained or updated at all. It is used once as a feature generator: given the task description, feature descriptions, and a few labeled examples, it proposes class-specific rules. Those rules are then parsed into executable code, and that code deterministically converts each tabular sample into binary rule indicators.

So after rule generation, the rule features are fixed for that trial. For a given generated rule set, each sample $\mathbf{x}^i$ is mapped to $\mathbf{z}_k^i \in \{0,1\}^R$, where each entry says whether the sample satisfies one of the $R$ rules for class $k$. Once those rules are fixed and parsed, the downstream model never looks at the raw tabular features directly anymore; it only sees these LLM-produced binary features.

The only thing actually learned by gradient descent in the main model is the weight vector $\mathbf{w}_k$ in Eq. (1). The paper is explicit about this: the logits are computed as $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$, and the cross-entropy loss is used to learn $\mathbf{w}_k$ from the few-shot labeled samples. The positive projection $\max(\mathbf{w}_k,0)$ just enforces nonnegative contributions from rules.

So the clean way to think about it is: the LLM performs one-shot feature engineering, and the linear model performs the actual supervised fitting. The original tabular features influence the final predictor only indirectly, through the rules the LLM invents from them. After that, inference is entirely done by the lightweight downstream model, not by the LLM.

One small nuance is that FeatLLM repeats this whole process multiple times with different random seeds, temperatures, and bagged subsets of features/instances. So there can be several different fixed rule sets across ensemble trials, each with its own learned weights $\mathbf{w}[t]$. But within each trial, once the rules are generated, they are static; only the downstream weights are trained.

### Why are the rule weights constrained to be non-negative in Eq. (1)?
Question:
In the paper, the class logit is defined as $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$, so each learned weight is projected into the non-negative region.

I understand the stated intuition that rules generated for a class should not reduce that class likelihood, but this seems like a strong modeling assumption. What if the LLM generates a noisy or misleading rule for class $k$ that is actually evidence against class $k$ on the training set? With a non-negative constraint, the model can only ignore that rule by pushing the weight to $0$, but it cannot actively use it as negative evidence.

Is there a principled reason this positivity constraint is better than allowing signed weights, especially when the rules are imperfect?
Answer:
In the paper, the non-negativity constraint is not presented as a universally optimal modeling choice; it is a deliberate inductive bias that matches how they want the rules to be used. The generated rules are meant to be class-specific criteria, so the authors treat each rule as supporting evidence for that class rather than as a general feature that may help or hurt. That is exactly why they write
$$
\text{logit}_k^i=\max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,
$$
and explicitly say that projecting the weights into a positive subspace “ensur[es] that the features generated by the LLM do not reduce the likelihood of a class during learning.”

The key practical point is that FeatLLM is a low-shot method with noisy, LLM-generated rules. In that regime, allowing signed weights would give the linear layer a very easy way to overfit small idiosyncrasies in the few training examples by using a class’s own rules as negative evidence. That may improve training loss, but it would make the learned rule semantics much less faithful and much less stable. With non-negative weights, a bad or irrelevant rule can still be harmless: its weight can be driven to $0$, so the model simply ignores it. The paper’s robustness story is that imperfect rules are handled by the ensemble and bagging mechanism, not by letting the classifier reinterpret a “rule for class $k$” as an anti-rule for class $k$.

So the principled reason is really about preserving the semantics of the extracted rules and stabilizing learning in a few-shot setting. The constraint makes the final linear model monotone in each class’s rules: satisfying more of class $k$’s rules can only increase that class’s score. If you want negative evidence, the paper’s formulation expects that to be captured indirectly through the competing class logits under the softmax, or by simply not assigning such a rule to class $k$ in the first place. The authors do not claim that signed weights are impossible or inherently wrong; rather, for their specific “LLM-generated criteria + simple downstream model” setup, the positive constraint is a conservative choice that improves interpretability and reduces the chance that noisy rules become spurious anti-features.

### How does FeatLLM handle a sample that satisfies rules from multiple classes at the same time?
Question:
The method generates $R$ rules per class, then computes a separate logit for each class from the binary rule indicators of that class, and finally applies a softmax over the class logits.

Suppose this is a multi-class problem and one sample satisfies many rules for class $1$ and also many rules for class $2$. Is the competition between classes handled only by the final softmax, or is there any mechanism that directly compares or penalizes conflicting rules across classes?

I'm asking because the feature vectors $\mathbf{z}_k^i$ are class-specific, so it seems possible that a sample can look strongly consistent with several classes simultaneously. I want to understand how the model resolves that beyond just whichever class gets the larger weighted sum.
Answer:
In \textsf{FeatLLM}, there is no separate mechanism that directly compares rules across classes or explicitly penalizes “conflicting” rules from different classes. The model is much simpler than that: for each class $k$, it builds a class-specific binary rule vector $\mathbf{z}_k^i \in \{0,1\}^R$, computes a scalar score

$$
\text{logit}_k^i = \max(\mathbf{w}_k, 0)\cdot \mathbf{z}_k^i,
$$

and then turns the vector of class logits into probabilities with a softmax. So if one sample satisfies many rules for class $1$ and also many rules for class $2$, both class logits can be high at the same time; the final softmax is where the competition happens.

The important point is that the classes do not interact at the rule level. Since $\mathbf{z}_k^i$ is class-specific, the rules for class $1$ are not directly “seen” by the class $2$ head, and vice versa. There is no pairwise rule contradiction check, no explicit mutual-exclusion constraint, and no term in the objective that says “if a rule supports class $1$, penalize class $2$.” The only cross-class coupling is indirect: the cross-entropy loss on the softmax encourages the correct class logit to be larger than the others on labeled training data.

So in effect, FeatLLM resolves overlap by learning how much each class-specific rule should matter, and then letting the largest weighted sum win. The non-negativity constraint on the weights means a satisfied rule can only increase that class’s score, not suppress it. If several classes look plausible for a sample, the model just assigns probabilities according to which class head has the strongest learned evidence.

A good mental model is that FeatLLM is closer to a set of one-vs-rest linear scorers on LLM-generated features than to a symbolic rule system with explicit conflict resolution. The paper does not describe any additional mechanism beyond the final softmax and the learned class-specific weights.

### Is using the LLM again for rule parsing really different from doing LLM-based prediction at inference time?
Question:
One of the paper's main motivations is avoiding the need to query the LLM for each test sample. But in the parsing stage, the authors also use the LLM to translate natural-language rules into executable Python code.

I'm confused about where the cost savings actually come from. Is the idea that the LLM is only used a small number of times offline to generate and parse the rules, and then the resulting code is applied to all future samples without any more LLM calls?

If that's the intended distinction, could someone clarify why this is categorically different from earlier LLM-for-tabular methods, rather than just moving the LLM queries from test time to a preprocessing stage?
Answer:
Yes — that is exactly the intended distinction in the paper, and the savings come from **amortizing the LLM calls over the whole dataset/task rather than paying for them on every test example**.

In \textsf{FeatLLM}, the LLM is used in an offline feature-engineering stage to generate rules from a few labeled examples and then to translate those natural-language rules into executable code. That parsing step is not the prediction step itself; it is just a way to turn the LLM’s output into a machine-readable transformation. Once the code is generated, the same rules are applied to all samples to create binary features, and the final prediction is made by a simple downstream model, such as a linear classifier. This is why the paper says that inference “only uses this simple predictive model with the discovered features” and “eliminates the need to send queries to the LLM for each sample at inference time.”

So the distinction from earlier LLM-for-tabular methods is not that \textsf{FeatLLM} somehow avoids using the LLM altogether; it doesn’t. The difference is **where the LLM sits in the pipeline**. Prior methods keep the LLM in the hot path for prediction: each test row is serialized and passed through the LLM to produce a label. That means you pay an LLM forward pass per test sample, and you also run into prompt-length limits because the whole table row has to fit in context. In \textsf{FeatLLM}, the LLM is used to build a compact representation once, and then ordinary ML handles the repeated per-sample inference. That is much closer to classical feature engineering than to end-to-end LLM inference.

There is still a cost, of course: if you move to a new tabular task, you have to rerun the rule-generation/parsing stage for that task. But that cost is paid once per task, not once per example. The paper’s runtime discussion makes exactly this point: training still involves some API queries, but the number is small, and the inference time becomes comparable to conventional methods because the LLM is no longer queried for every prediction.

So the short answer is: **yes, the paper is deliberately shifting LLM usage from per-sample prediction to one-time feature discovery and rule compilation. That is the core reason it is different from earlier LLM-based tabular predictors.**

### How does feature bagging reduce prompt length without throwing away important columns?
Question:
The paper says FeatLLM can handle wide tables by using bagging over subsets of features or instances, which helps stay within the LLM context window. I understand how this reduces prompt length mechanically, but I don't understand why it should preserve performance.

If an important predictive interaction involves two columns that are often separated into different feature bags, then no single trial would ever see that interaction and therefore no rule could mention it. The paper argues that an ensemble of weak learners can compensate for incomplete coverage, but I don't see why that would recover interactions that were never jointly observed.

Is the claim mainly that many tabular tasks can be solved with marginal or low-order rules, or is there another reason bagging should work here?
Answer:
Feature bagging in \textsf{FeatLLM} is not supposed to preserve every interaction in every prompt. It is a way to make the prompt fit, while recovering robustness by repetition. Each individual LLM call sees only a subspace of the table, so yes, some interactions will be invisible in that particular trial. The paper’s bet is that this is acceptable because the method is not a single-shot rule extractor: it runs many trials, randomizes the feature/instance subsets, and then averages the resulting class probabilities. In other words, it is using a random-subspace ensemble, not trying to solve the whole tabular problem in one prompt.

The key intuition is that many tabular datasets are not dominated by one irreducibly high-order interaction. Often the signal is redundant: a useful interaction can usually be approximated by several lower-order rules, or at least one of the involved columns can be correlated with a feature that is present in another bag. Since \textsf{FeatLLM} asks the LLM to generate a small fixed number of rules per class, and then learns weights on those binary rule-features, the downstream model only needs a few informative rules to get a good predictor. Across $T$ trials, different bags expose different columns to the LLM, so an important feature does not have to appear in every prompt; it only has to appear often enough that some trials generate the right rule. The paper explicitly frames this as self-consistency: rules that recur across trials are more likely to be correct, and the ensemble can compensate when some individual rule sets are incomplete.

So the short answer to your concern is: no, bagging does not magically recover an interaction that is never jointly observed. If a task truly depends on a nonredundant interaction between two columns, and those two columns are almost never placed together in the same bag, performance can certainly suffer. The paper does not prove otherwise. What it claims, and what the experiments support, is weaker but practical: on the kinds of few-shot tabular tasks they test, the important structure is often captured by relatively low-order rules, the tables contain enough redundancy that different bags still expose the useful signal, and the ensemble smooths over the missing pieces. That is why bagging helps both with prompt length and with robustness, rather than simply discarding information.

This is also consistent with their ablations and analysis: performance improves with more ensembles, and they note that a single rule set may not capture all feature relationships, but multiple weak learners can offset incomplete coverage. So the claim is not “bagging preserves every interaction”; it is “bagging reduces context size while usually preserving enough of the predictive structure for the ensemble to work well.”

### Why does the paper claim the Step-1 reasoning instruction reduces spurious correlations?
Question:
In the prompt design, the LLM first reasons about likely feature-target relationships using prior knowledge alone, without looking at the few-shot examples, and only afterward uses the demonstrations to derive rules. The paper says this helps prevent the model from focusing on irrelevant columns and reduces spurious correlations.

I'm not fully convinced by that argument. It seems equally possible that the LLM's prior knowledge could itself be wrong, biased, or mismatched to the dataset, especially for synthetic or unusual tasks. In that case, wouldn't forcing the model to reason from prior beliefs first make it harder to notice dataset-specific signals?

Can someone explain more precisely why this two-step prompting is expected to improve robustness rather than just injecting a stronger prior?
Answer:
The paper’s claim is best understood as an *inductive bias* argument, not as “the LLM’s prior is always correct.” In \textsf{FeatLLM}, Step-1 is meant to make the model first ask, “What features could plausibly matter for this task at all?” before it sees the few-shot examples. That matters in low-shot tabular learning because with only a handful of labeled rows, the model can easily latch onto accidental co-occurrences in the demonstrations, especially when there are many columns. By forcing an initial pass based on task and feature descriptions alone, the prompt narrows the hypothesis space to semantically plausible variables, so the later examples are used to refine rules rather than to discover relevance from scratch. In other words, Step-1 is doing a rough feature-selection pass before rule induction.

So the intended robustness gain is not that the model becomes “more confident in its beliefs,” but that it becomes *less likely to search in the wrong places*. The paper explicitly says this two-step reasoning “prevents the model from identifying spurious correlations in irrelevant columns and can assist in focusing on more significant features.” That is exactly what their spurious-correlation experiment is meant to illustrate: when they attach unrelated Adult columns to Heart, \textsf{FeatLLM} degrades less than baselines, and they observe that only about $1$--$2\%$ of the generated rules come from noisy columns. The ablation study also shows that removing the reasoning instruction hurts AUC. So empirically, the step seems to reduce attention to irrelevant columns in the kinds of datasets they tested.

Your concern is still valid, though, and the paper does not claim otherwise. If the LLM’s prior knowledge is wrong or mismatched, then Step-1 can absolutely bias the system in the wrong direction. The authors actually acknowledge this in two places: they note that \textsf{FeatLLM} can still learn spurious correlations if the added columns are closely related, and in the broader impact section they explicitly warn that biases and misinformation in the LLM’s prior knowledge could directly affect predictions. So the real claim is narrower: Step-1 is a useful bias under the low-shot, high-dimensional setting they study, because it helps the LLM ignore obviously irrelevant columns before it starts fitting the few examples. It is not a guarantee against bad priors; it is a heuristic that usually makes the search for rules less noisy.

### What does the 'quality of generated features' analysis mean when a rule is just a binary indicator?
Question:
In the feature-quality analysis, the paper measures the AUROC between each generated feature and the target label, then reports the proportion of features with AUROC above $0.5$.

I'm confused about how to interpret AUROC for a single binary rule feature. Since the feature only takes values $0$ or $1$, isn't the ROC curve very limited? Also, if a rule is strongly associated with the negative class rather than the positive class, would its AUROC be below $0.5$ even though it is still informative?

I want to understand whether 'AUROC above $0.5$' is really a good criterion for rule usefulness in this setting.
Answer:
Yes, the ROC analysis is very limited for a binary rule feature, but it is still meaningful.

If a generated feature is just a binary indicator $z \in \{0,1\}$, then the ROC curve can only have one nontrivial operating point: the point you get when you classify a sample as positive whenever the rule fires. So the AUROC is no longer measuring a nuanced ranking, as it would for a real-valued score; it is basically summarizing whether the rule fires more often on positive examples than on negative ones. Formally, for a binary score, AUROC reduces to a simple class-separation summary, and you can think of it as the average of sensitivity and specificity:
$$
\mathrm{AUC} = \frac{P(z=1 \mid y=1) + P(z=0 \mid y=0)}{2}.
$$
So $\mathrm{AUC}=0.5$ means the rule is no better than random, and $\mathrm{AUC}>0.5$ means the rule is aligned with the positive class more often than not.

Your second point is exactly right: if a rule is strongly associated with the negative class, then its AUROC with respect to the positive label will be below $0.5$. That does not mean the rule contains no information; it just means the information is reversed. If you flipped the feature to $1-z$, its AUROC would become $1-\mathrm{AUC}$ and would be above $0.5$. So AUROC $<0.5$ is really saying “this rule points the wrong way for this label,” not “this rule is useless in an absolute sense.”

In the context of the paper, that distinction matters because the generated rules are intended to become class-specific positive features, and the downstream linear model uses nonnegative weights. That means a rule that mostly fires on the opposite class is not helpful for that class as generated, so using the proportion of features with AUROC above $0.5$ is a reasonable sanity check for “did the LLM generate rules that directly match the intended target?” It is not meant to be a perfect measure of all possible utility. The paper’s own interpretation is exactly that: before tuning, most generated rules are relevant to the target; after tuning, the low-value ones get downweighted or filtered out.

So the short answer is: yes, AUROC for a binary rule is coarse, and yes, a negatively associated but informative rule can have AUROC below $0.5$. In this paper, $\mathrm{AUC}>0.5$ is best understood as a directionality check for whether the generated rule is a useful positive indicator for the target class, not as a universal definition of usefulness.

### How is cross-validation done in a $k$-shot setting with so few samples per class?
Question:
In the implementation details, the paper says it uses $k$-fold cross-validation for epoch selection, with the number of folds set to $2$ or $4$ so that each training split contains at least one example of each class.

I'm having trouble picturing how stable this is when the total number of labeled examples is extremely small, especially for multi-class datasets. For example, if there are $4$ shots total, or even $4$ shots per class, splitting that into folds seems like it would make the validation sets tiny and noisy.

Can someone clarify exactly what the unit of 'shot' is in this paper and how cross-validation is feasible without making model selection too high-variance?
Answer:
The short version is that the paper is a bit loose with the word “shot,” but the cross-validation they use is only for selecting an epoch for a very small linear model, not for building the whole predictor. That makes it feasible, although admittedly noisy.

What the paper actually says in the methods is that, for $k$-shot learning, they randomly sample a tiny labeled training set from the target dataset, and then train the downstream model on the binary rule-features produced by the LLM. The epoch is chosen by $k$-fold cross-validation, with $k \in \{2,4\}$ chosen so that each training split still contains at least one example of every class. That constraint is the key: they are not doing “leave-one-out on $4$ total samples,” which would be hopelessly unstable. They deliberately keep the number of folds very small so that the training portion of each fold is still class-complete.

So if you are imagining “$4$ total labeled samples on a $4$-class problem,” then yes, standard $k$-fold CV would be ill-defined or unusable. The fact that the authors say the folds are chosen to preserve at least one example per class implies that their few-shot support set must be large enough to cover all classes in each split. In practice, that means the relevant unit is not “$4$ arbitrary labels total regardless of class structure,” but a small support set that is still class-balanced enough for the folds to work. The paper does not spell this out perfectly, but the implementation detail makes that interpretation unavoidable.

As for variance, they are not pretending this is a statistically clean hyperparameter search. In such low-shot regimes, any CV estimate will be noisy. Their mitigation is pragmatic: use only $2$ or $4$ folds, keep the model simple, and repeat the whole train/test sampling three times with different random seeds, reporting mean and standard deviation. Since the downstream learner is just a low-capacity linear model over generated binary features, the exact epoch is not usually a critical hyperparameter anyway; the CV is mainly a coarse early-stopping heuristic.

So the right intuition is: the paper relies on a tiny but class-complete support set, uses very low-fold CV only to choose an epoch, and averages over multiple random splits to dampen the noise. It is not a high-fidelity model-selection protocol, but it is a reasonable engineering choice for the extremely data-starved setting they study.

### Does FeatLLM risk overfitting twice by using the same few-shot examples for both rule generation and weight fitting?
Question:
As I understand the method, the few-shot labeled samples are used first inside the prompt so the LLM can generate class-specific rules, and then the same few-shot samples are used again to train the linear weights on the resulting binary features.

This makes me wonder whether the method is effectively fitting the same tiny dataset twice: once implicitly through the prompted rule extraction and once explicitly through supervised training of the linear model. If so, why doesn't this lead to severe overfitting or target leakage?

Is the intended argument that the first stage is mostly injecting external prior knowledge from the LLM rather than memorizing the examples? I'd appreciate a more careful explanation of why this two-stage use of the same examples is methodologically acceptable.
Answer:
Short answer: it is a form of support-set adaptation, but not “target leakage,” and not really “fitting the same data twice” in the usual sense. In \textsf{FeatLLM}, the LLM is not trained on the few-shot examples; it is frozen and only conditioned by the prompt. The examples are used once to help the LLM instantiate a task-specific rule set, and then those rules are turned into binary features for a separate, very low-capacity linear model. The paper is quite explicit that Step 1 is meant to use the LLM’s general knowledge without referring to the demonstrations, while Step 2 uses the demonstrations plus that prior reasoning to derive class rules. So the first stage is best thought of as feature generation under a prior, not as parameter fitting to the tiny labeled set.

The second stage is ordinary supervised learning on engineered features. Using the same few-shot labels there is standard in few-shot learning: you use the support set both to define the representation and to fit the classifier, while evaluation happens on held-out test samples. That is not leakage unless the test labels or test instances influence rule generation, which the paper does not do. What can happen, of course, is ordinary overfitting to the support set, because the rule generator can still produce overly specific rules. The authors acknowledge this risk and try to control it by fixing the number of rules per class, randomizing prompt order, using a relatively high temperature, and then bagging/ensembling multiple rule sets so that unstable or spurious rules are averaged out. Their ablations also show that the weight-tuning step helps by filtering weak rules, which suggests the linear model is acting as a regularizer rather than simply memorizing the few shots.

So the intended methodological story is exactly that the first stage injects prior knowledge from the LLM and the second stage learns how to weight the resulting rules. That is acceptable because the two stages do different jobs: one proposes candidate features, the other selects among them. If anything, the main limitation is not leakage but variance: with very few labeled samples, the quality of the generated rules still depends heavily on how well the LLM’s prior matches the task.

### Are the generated rules really 'features,' or are they more like class-specific weak classifiers?
Question:
The paper describes the LLM output as engineered features, but each rule is generated separately for a target class and then turned into a binary indicator of whether the sample satisfies that class rule.

That makes me wonder whether these are features in the usual representation-learning sense, or whether they are closer to class-specific weak classifiers whose outputs are being combined linearly. For example, a rule like 'age is above 65 and blood pressure is high' already sounds like a small classifier for a particular disease class, not a reusable feature independent of labels.

Does calling them features have any technical significance here, or is the method better understood as learning an ensemble over label-conditioned heuristics?
Answer:
Yes — semantically these are very close to class-specific weak classifiers, but in the paper’s pipeline they are used as engineered features.

The key distinction is that the LLM does not directly output the final prediction for a sample. Instead, it outputs a rule such as “age $> 65$ and blood pressure is high” for a particular class, and that rule is then converted into a binary variable $z \in \{0,1\}$ indicating whether the sample satisfies it. That binary indicator is what the paper calls a feature. The downstream model then learns a linear combination of these indicators, with one weight vector per class, and converts the resulting logits to probabilities via softmax:
$$
\text{logit}_k = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k.
$$
So technically, the “feature” is not the natural-language rule itself, but the rule’s satisfaction indicator.

That said, your intuition is right that these are not features in the usual representation-learning sense, like latent embeddings that are shared across classes and discovered without reference to labels. These are class-conditioned, label-aware predicates. In that sense, they are much closer to hand-crafted or rule-based features, and each one can be viewed as a weak heuristic for a class. The paper even leans in that direction when it says the ensemble combines “various weak learners,” although the actual final prediction is still made by the linear classifier on top of the rule indicators.

So the most accurate interpretation is: \textsf{FeatLLM} is not learning a standard reusable representation; it is doing label-conditioned rule generation, turning those rules into binary features, and then fitting a simple classifier on top. Calling them “features” is technically correct within the paper’s framework, but “class-specific rule features” or “label-conditioned heuristics” would probably be a clearer description than “features” in the representation-learning sense.

### Why is FeatLLM expected to work on synthetic datasets if Step-1 relies on prior knowledge from pretraining?
Question:
The paper emphasizes that the LLM first uses prior knowledge to infer relationships between features and the task, and this is supposed to be beneficial. But then in the experiments, two synthetic datasets are included specifically to show that the model is not just memorizing benchmark data.

I'm confused about how the method should succeed on synthetic tasks like classifying sequence types or mixture concentration if the LLM cannot rely on domain knowledge from pretraining in the same way it could for medical or financial datasets. Is the idea that the LLM's general reasoning ability is enough, even when task-specific prior knowledge is unavailable?

I would like to understand what part of FeatLLM is supposed to transfer to those synthetic settings.
Answer:
Yes — but the paper is using “prior knowledge” in a broader sense than “already knows the domain facts from pretraining.”

What FeatLLM needs in Step-1 is not necessarily medical or financial expertise; it needs the LLM to infer a plausible relationship between the feature descriptions, the example values, and the label. The paper explicitly says that Step-1 is done “without referring to example demonstrations, relying instead on general knowledge or common sense,” and that Step-2 then uses the few-shot examples plus that initial hypothesis to derive class rules. So the transferable part is the LLM’s ability to do weak rule induction, not memorized domain knowledge.

That is why the synthetic datasets still make sense. In those tasks, the useful structure is simple and explicit enough that the LLM can often reason about it from the task description and the few demonstrations even if it has never seen that exact benchmark before. For example, in the sequence-type task, the model does not need to “know” the dataset from pretraining; it only needs to recognize patterns like arithmetic growth, geometric growth, Fibonacci-like recurrence, or Collatz behavior from the serialized examples and class names. In the solution-mix task, it only needs to infer a threshold on a mixture proportion. Those are not domain-specific facts in the same way as “older patients are at higher risk” or “certain lab values indicate disease”; they are generic structural patterns that an LLM can sometimes reason about.

So the point of the synthetic datasets is not that FeatLLM depends on pretraining knowledge there, but almost the opposite: they check whether the method can still work when memorization of the benchmark is impossible. If FeatLLM performs well there, that suggests it is extracting and converting structure into rules, rather than recalling answers from training text.

The downstream mechanism is also important here. Even if Step-1 is only partially helpful on a synthetic task, Step-2 turns candidate rules into binary features, and the linear model learns which of those rules matter. So the method is not all-or-nothing: the LLM proposes rules, and the trained linear layer filters and weights them.

In short, what transfers to the synthetic setting is the reasoning-to-rule-extraction pipeline, not domain knowledge itself. The paper’s claim is that LLMs can act as general feature engineers; domain knowledge helps on real-world datasets, but the same rule-induction machinery can still be useful on synthetic ones where only generic reasoning is available.

### Is the comparison with TabLLM fair if FeatLLM uses GPT-3.5 but TabLLM uses T0?
Question:
In the implementation details, the paper says FeatLLM uses GPT-3.5, while TabLLM is run with T0 following the original setup because TabLLM requires an open model for parameter-efficient tuning.

I'm unsure how to interpret the empirical comparison in that case. If FeatLLM has access to a stronger proprietary LLM while TabLLM is limited to a smaller open-weight model, then part of the reported gain might come from backbone quality rather than the proposed feature-engineering framework itself.

Do the authors provide any evidence separating 'better prompting/method' from 'better base LLM,' or is this just an unavoidable limitation of the comparison?
Answer:
Short answer: the TabLLM comparison is not perfectly apples-to-apples, and the paper does not fully disentangle “better backbone” from “better method” for that specific baseline.

The authors explicitly say they use GPT-3.5 for FeatLLM, but TabLLM is run with T0 “following the original setting,” because TabLLM relies on parameter-efficient tuning and therefore needs an open checkpoint. So if you compare FeatLLM to TabLLM in the main tables, you are indeed comparing two method-plus-backbone combinations rather than isolating the framework alone. In that narrow sense, your concern is valid.

That said, the paper does give some evidence that the gain is not *just* due to GPT-3.5. First, they also evaluate GPT-3.5-based baselines such as in-context learning and TABLET, and FeatLLM still outperforms them. That is the more informative comparison for the question “does the proposed prompting/feature-engineering framework help?” because the backbone is held fixed there. Second, they report ablations of FeatLLM itself, showing that removing the reasoning step, feature descriptions, tuning, or ensembling degrades performance. Those ablations separate parts of the *method* from the base model more directly.

So the right interpretation is: the FeatLLM-vs-TabLLM numbers show FeatLLM’s best achievable setup against the baseline as originally implemented, but they do not isolate the contribution of GPT-3.5 versus T0. The paper’s strongest evidence for the framework itself comes from the GPT-3.5-controlled baselines and the ablations, not from the TabLLM comparison alone. If you want a truly controlled comparison with TabLLM, the paper does not provide one in the main text; that is an unavoidable limitation of the access constraints they describe.

### What kinds of decision boundaries cannot be represented by FeatLLM's positive weighted rule sums?
Question:
I'm trying to understand the expressive power of the final classifier. For each class $k$, FeatLLM computes a logit as a non-negative weighted sum of binary rule indicators for that class, then applies softmax across classes.

This seems like a monotone model with respect to the activated rules of a class: satisfying more class-$k$ rules can never hurt class $k$. That sounds reasonable at first, but it also seems restrictive. For example, if two individually useful rules become misleading when they co-occur, or if evidence for one class should actively count against another, I don't see how the model can represent that.

Is there a standard way to characterize the function class induced by this architecture, and what important types of tabular patterns would it miss?
Answer:
What FeatLLM uses at the end is essentially a multiclass linear model on binary rule features, with an additional nonnegativity constraint on the coefficients. For class $k$ the score is

$$
s_k(\mathbf z_k)=\max(\mathbf w_k,0)^\top \mathbf z_k,
$$

and then the class probabilities come from $\mathrm{softmax}(s_1,\dots,s_c)$. So, before the softmax, each class score is an additive, monotone function of that class’s rule indicators: turning on another rule for class $k$ can only keep $s_k$ the same or increase it. That is exactly the inductive bias the paper describes when it says the positive projection “ensures that the features generated by the LLM do not reduce the likelihood of a class during learning.”

This means the downstream classifier is best thought of as a monotone linear model, or more precisely a nonnegative linear model over binary rules. In terms of expressivity, it can represent boundaries that are linearly separable in the rule space with nonnegative weights, but it cannot learn inhibitory effects among those same rules. So if the true pattern is something like “rule A is evidence for class $k$ only when rule B is absent,” or “having both A and B together should hurt class $k$ even though each one alone helps,” this model cannot express that directly. Likewise, it cannot represent XOR/parity-like behavior, where the class depends on whether an odd or even number of rules are active, because those are inherently non-monotone. Any pattern that requires a rule to act as a veto, or requires a negative contribution from a satisfied rule, is outside this function class.

The softmax does introduce competition across classes, so a rule that boosts class $k$ will indirectly lower the probability of the other classes. But that is not the same as allowing negative evidence inside a class score. The architecture can say “this looks more like class $k$ than the others,” but it cannot say “this rule specifically argues against class $k$” unless that information is encoded in some other class’s rules and score. So the restriction is local to each class score, even though the final prediction is multiclass.

A useful way to see the tradeoff is that FeatLLM pushes the hard nonlinearity into the LLM-generated rules, and then keeps the final learner deliberately simple. If the LLM produces a rule like “age $> 65$ and chest pain present,” then the linear classifier can weight that rule. But if the useful pattern depends on a more subtle interaction that is not already captured by a rule, the final model cannot invent that interaction on its own. That is why the paper emphasizes robustness and few-shot stability rather than maximal expressivity: the positive-weight rule sum is a strong inductive bias, not a universal approximator.

So the short answer is that FeatLLM’s classifier misses genuinely non-monotone tabular patterns: veto effects, XOR-style interactions, context-dependent rules, and any decision boundary where satisfying more of the same-class rules should sometimes make the class less likely. The paper’s design intentionally avoids those patterns in the final layer, relying instead on the LLM to generate rules that already encode the relevant structure.
