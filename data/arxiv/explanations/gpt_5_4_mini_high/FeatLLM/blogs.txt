# Stop Asking the LLM Every Time: How FeatLLM Turns GPT Into a Feature Engineer

Tabular data powers a lot of real-world machine learning: credit risk, medical diagnosis, customer churn, and more. These problems are often low-data and high-stakes, which makes them a natural fit for methods that can use prior knowledge.

Large language models are attractive here because they already know a lot about the world. But most LLM-based tabular methods use that knowledge in the most expensive way possible: they serialize each row into text and ask the LLM to make a prediction for every sample. That works, but it is slow, costly, and often brittle when the table has many columns.

The key idea in **FeatLLM** is to use the LLM differently. Instead of asking it to predict every row, the paper asks it to act like a **feature engineer**. The LLM is used once to discover useful rules from a few labeled examples. Those rules are then turned into new features, and a simple downstream model handles prediction.

In other words: **ask the LLM to write the rules, not to score every row**.

## Why this shift matters

This change sounds small, but it solves several practical problems at once.

First, it lowers inference cost. Once FeatLLM has generated its rules, new samples do not need to go through the LLM. Prediction is done with a lightweight model, so deployment is much cheaper and faster than methods that require an LLM call for every input row.

Second, it avoids fine-tuning. FeatLLM only needs API-level access to an LLM such as GPT-3.5. That is important because many strong LLMs are not available for training or parameter-efficient tuning.

Third, it handles long tabular inputs better. Serializing many columns into a prompt can quickly hit context limits. FeatLLM uses bagging and ensembling to keep each prompt smaller and still remain robust.

Finally, it is a better fit for few-shot tabular learning. When only a handful of labeled examples are available, a model that can use prior knowledge to propose sensible rules can be much more useful than one that tries to learn everything from scratch.

## How FeatLLM works

The pipeline has three main parts.

First, FeatLLM prompts the LLM with task information, feature descriptions, and a few labeled examples. The prompt is structured to mimic an expert’s reasoning process. The paper splits this into two steps: the model first infers the relationship between the features and the target task, and then it derives class-specific rules using that understanding plus the few-shot examples.

Second, those natural-language rules are converted into executable code. Each rule becomes a binary feature: does this row satisfy the rule or not? If a sample matches a rule, the feature is $1$; otherwise it is $0$.

Third, a simple linear model learns how important each rule is for each class. The paper uses non-negative weights and softmax to estimate class probabilities. So the LLM is not making the final prediction directly; it is generating a rule set that a conventional model can use.

There is one more important piece: **ensembling with bagging**. FeatLLM repeats the rule-generation process multiple times, using different subsets of features or samples and different prompt orders. This helps in two ways. It makes the final prediction more robust, and it reduces the chance that a long prompt will exceed the LLM’s context window.

## What makes this approach different from standard LLM tabular methods

Most LLM-based tabular methods are end-to-end. They turn a row into text, send it to the LLM, and get a prediction back. That means every sample at test time depends on the LLM.

FeatLLM breaks that dependency. The LLM is used during feature discovery, but not during inference. After the rules are extracted, the system behaves like a normal tabular model built on engineered features.

That makes a big difference in deployment. A team can use an external LLM through an API, generate the features once, and then serve predictions with a cheap classifier. There is no need to keep paying for LLM inference on every sample.

## What the experiments show

The paper evaluates FeatLLM on **13 tabular datasets** covering binary and multiclass classification tasks. These include familiar benchmarks like Adult, Bank, Heart, and Diabetes, as well as newer and synthetic datasets designed to test whether the model is relying on memorized knowledge.

Across these datasets, FeatLLM is consistently strong. The paper reports that it usually ranks first or second among the compared methods, and it outperforms alternatives such as TabLLM and STUNT by about **10% on average**. In some low-shot settings, FeatLLM with just **4 labeled examples** performs comparably to conventional tabular baselines that need **32 examples**.

The paper also shows why the rule-based approach helps. When irrelevant columns are added to the data, FeatLLM is less sensitive than other methods. That suggests the two-step prompting strategy helps the LLM focus on meaningful relationships rather than spurious correlations.

## The main takeaway

FeatLLM is not trying to replace tabular models with an LLM at prediction time. It is using the LLM where it is strongest: reasoning over a small amount of information and proposing useful structure.

That makes the model more practical. It needs only API access, it avoids per-sample LLM inference, it works well in few-shot settings, and it is more usable on tables with many columns.

The broader lesson is simple: sometimes the best way to use an LLM is not to let it make the final prediction. Sometimes the best use is to have it do what humans do well in tabular problems: **find the rules, engineer the features, and let a lightweight model do the rest**.



# Few-Shot Learning for Spreadsheets: Why LLMs Can Help When You Only Have a Handful of Rows

## The problem: when labels are scarce, tabular learning gets awkward

A lot of real-world machine learning happens on tables, not images or text. Think about patient records, bank customer data, loan applications, or business spreadsheets. These datasets are often useful, but labeled examples are expensive. In healthcare, each label may require expert review. In finance, labels may come from slow outcomes or scarce human judgment. In business settings, the relevant events may simply be rare.

That is the setting of few-shot tabular learning: trying to build a classifier from only a small number of labeled rows. This is hard for ordinary tabular models because, with so little data, they can easily overfit to noise or latch onto spurious correlations. A model may notice a pattern in a handful of rows that looks important but does not actually generalize.

This is especially tricky for tabular data because the columns are often heterogeneous. One column might be numeric, another categorical, another text-like metadata. The structure is not as uniform as pixels in an image or tokens in a sentence, so there is less built-in signal for the model to exploit.

## Why large language models can help

Large language models bring something traditional tabular models do not: prior knowledge. They have seen a huge amount of text during pretraining, so they often know high-level relationships that matter in the real world.

For example, in healthcare, age and symptoms are often relevant to diagnosis. In finance, income, credit-related fields, and customer history can matter a lot. In business data, features such as purchase history, account status, or campaign response may be informative. An LLM can use that prior knowledge to make better guesses about which columns matter, even when only a few labeled examples are available.

That is why recent LLM-based tabular methods serialize rows into text and ask the model to predict directly. But that approach has two practical problems. First, it usually requires an LLM call for every test example, which is expensive. Second, long tables can create very long prompts, and prompt length becomes a real bottleneck when a dataset has many columns.

## FeatLLM takes a different approach

The key idea in the paper is simple: do not use the LLM as the final predictor. Use it as a feature engineer.

FeatLLM asks the LLM to read the task description, the feature descriptions, and a few labeled examples, then produce explicit rules for each class. In other words, instead of saying “predict this row,” the prompt asks the model to figure out the criteria that define the class.

The process is structured in two steps. First, the LLM is guided to reason about the relationship between the task and the features using its own prior knowledge. Second, it uses that reasoning plus the few examples to generate class-specific rules. The paper fixes the number of rules per class at 10, which helps keep the prompt manageable.

Once those rules are generated, FeatLLM turns them into new binary features: for each rule, the feature is $1$ if a row satisfies the rule and $0$ otherwise. The system then trains a simple linear model on top of these rule-based features to estimate class probabilities.

This matters because, after feature engineering, inference no longer needs the LLM. The LLM is used to discover the rules, but prediction itself is done by a lightweight downstream model. That makes inference much cheaper and avoids sending every test row back through the LLM.

## How FeatLLM keeps the rules usable

Natural-language rules are messy. Even if you ask the model for a structured response, it may phrase a condition in slightly different ways, such as using “greater than” instead of $>$ or changing the wording of a comparison. FeatLLM handles this by using the LLM again to turn the inferred rules into executable code, which is then run in Python to generate the binary features.

The paper also adds bagging and ensembling. In practice, FeatLLM repeats the rule-generation process multiple times, using shuffled examples and subsets of features or instances. This does two things. It makes the method more robust, because bad rules from one run can be offset by better rules from another. And it helps with prompt-size limits, because each run only has to see part of the table.

## What the experiments show

The authors evaluate FeatLLM on 13 datasets covering binary and multiclass classification. The list includes healthcare datasets like Diabetes, Heart, and Myocardial; finance and business-style datasets like Adult, Bank, and Credit-g; and newer or synthetic tasks such as Cultivars, NHANES, Sequence-type, and Solution-mix.

Across these benchmarks, FeatLLM is usually the best or second-best method. The paper reports that it outperforms alternatives such as TabLLM and STUNT by about 10% on average. One especially striking result is that FeatLLM with only 4 labeled examples can match conventional tabular baselines that need 32 examples.

It also behaves well when the table has many columns. Methods that rely on end-to-end LLM prediction struggle when the prompt gets too long, but FeatLLM is more resilient because it is not trying to send the entire prediction problem through the LLM at inference time.

## Why this is useful in practice

This is a good fit for settings where labels are costly, but domain knowledge is plentiful. In healthcare, you may only have a handful of annotated patient records but a lot of expert intuition encoded in the medical literature. In finance, you may know broadly which attributes matter for risk assessment, even if you do not have many labeled cases. In business, you may want to predict outcomes from small samples of campaign or customer data, where collecting more labels is slow or expensive.

FeatLLM is also practical because it only requires API-level access to an LLM. It does not require fine-tuning the model, which matters when the LLM is only available through an inference API. And because the expensive LLM step happens during feature generation rather than every prediction, the runtime cost at inference is much lower than that of many other LLM-based tabular methods.

## The main takeaway

FeatLLM shows that LLMs do not need to be used as black-box predictors for every row in a spreadsheet. In low-shot tabular learning, they can be more useful as knowledgeable feature engineers: read a few examples, infer useful rules, turn those rules into features, and let a simple model do the actual prediction.

That shift is the real contribution of the paper. It keeps the benefits of LLM prior knowledge while avoiding some of the biggest pain points of LLM-based tabular learning: per-sample inference cost, fine-tuning requirements, and prompt-length limits.

The method is designed for low-shot settings, so it is not a replacement for standard tabular models on large labeled datasets. But when you only have a handful of rows and need something that can still reason with domain knowledge, FeatLLM is a strong and practical option.



# From Natural Language to Prediction Rules: A Simple Walkthrough of How FeatLLM Works

Large language models are usually described as tools that answer questions or generate text. In *FeatLLM*, the authors use them differently: not as the final predictor, but as a feature engineer.

That shift matters. Instead of asking an LLM to make a prediction for every new row in a table, FeatLLM asks it to read a few labeled examples, infer useful rules, and turn those rules into features a small machine learning model can use. The result is a pipeline that is easier to run at inference time, does not require fine-tuning, and works well in few-shot tabular settings.

## Why tabular learning is a hard fit for LLMs

Tabular data is the kind of data stored in rows and columns, like patient records, credit applications, or customer data. It is a very common format in real-world machine learning, but it is not what LLMs were originally designed for.

Recent LLM-based tabular methods usually serialize a row into text and send it into the model along with a task description. That can work, especially when you only have a few labeled samples. But it has two practical problems.

First, the model has to run once per test sample, which makes inference expensive. Second, long tables can exceed prompt limits, especially when there are many columns. FeatLLM is designed to avoid both issues.

## The core idea: let the LLM generate rules, not predictions

FeatLLM treats the LLM as a rule generator. Instead of directly asking, “What is the label for this row?”, it asks something closer to, “What conditions would indicate class A or class B?”

For example, in a medical task, the LLM might infer rules like:

- if age is high and a certain test result is abnormal, the positive class is more likely;
- if a feature falls in a certain range, the negative class is more likely.

These are not final predictions. They are class-specific rules that can be applied to any row in the dataset.

Once the rules are discovered, they are converted into binary features. A row either satisfies a rule or it does not, so each rule becomes a $0$ or $1$ value. Then a lightweight model learns how important each rule is.

That means the expensive part happens up front, and inference later becomes very cheap.

## Step 1: Prompt the LLM like a human would approach the task

FeatLLM starts by building a carefully structured prompt. The prompt has three parts.

The first part gives basic information: the task description, the feature names, feature definitions, and a few labeled examples. The paper follows the same text serialization style used in prior work, where each row is written out as plain text with an answer attached.

The second part is a reasoning instruction. This is important. The authors do not just ask for rules immediately. They split the reasoning into two steps.

In the first step, the LLM is asked to think about the general relationship between the features and the target, using its own prior knowledge. This is where the model can bring in common-sense or domain knowledge.

In the second step, the LLM uses that knowledge plus the few labeled examples to derive class-specific rules. The idea is to guide the model away from irrelevant columns and toward more meaningful patterns.

The third part is a response instruction. This tells the LLM how to format the output so the rules are easier to parse later. The paper fixes the number of rules per class at 10 to keep prompts manageable and avoid generating too few or too many rules.

## Step 2: Turn the rules into binary features

Once the LLM generates rules, the next job is to apply them to the table.

A rule might say something like, “feature $f_1$ is greater than 5 and feature $f_3$ is below a threshold.” For each row, FeatLLM checks whether the rule is satisfied. If it is, that rule gets a value of $1$ for that row; otherwise it gets $0$.

This turns the original table into a new set of features:

- each rule becomes one binary feature;
- each class gets its own set of rules;
- every row is now represented by whether it matches those class-specific rules.

The paper notes that LLM output is often not perfectly uniform. Even with formatting instructions, the model might phrase things differently, like writing “greater than” instead of using the symbol $>$. To handle this, FeatLLM asks the LLM itself to generate simple parsing code, which is then executed in Python. That lets the system convert natural-language rules into usable code without building a custom parser from scratch.

## Step 3: Train a small model on top

After the rules are turned into binary features, FeatLLM does not need another large model. It trains a simple downstream classifier, such as a linear model, on top of those features.

This is one of the most practical design choices in the paper. The classifier learns which rules matter more and which ones matter less. In the paper’s formulation, each class gets a score based on a weighted combination of its binary rule features, and those scores are turned into probabilities with a softmax.

There is also an important constraint: the weights are projected to be non-negative. That way, a discovered feature cannot end up reducing the likelihood of a class during training. In plain terms, the model learns how much each rule should support a class, rather than learning contradictory effects from the rule features.

This lightweight classifier is what makes inference efficient. After the rules are learned, predictions no longer have to go through the LLM.

## Step 4: Use bagging and ensembling for robustness

The authors do not rely on one prompt and one set of rules. They repeat the whole process multiple times and combine the results.

This matters for two reasons. First, rule generation from an LLM can vary depending on prompt order, temperature, and which examples are included. Second, tabular prompts can become too long when there are many features.

FeatLLM uses bagging, which means it randomly selects subsets of features or examples for each trial. It also changes the order of demonstrations and uses a higher sampling temperature to encourage diversity. Then it averages the predictions across multiple trials.

This gives the method two benefits. It helps smooth out mistakes from any single set of rules, and it reduces the impact of prompt length limits. In other words, if one run misses something or produces noisy rules, other runs can compensate.

## Why this pipeline is useful

FeatLLM is built around a simple but powerful idea: use the LLM where it is strongest, then hand off the actual prediction work to a smaller model.

That has several advantages.

It only needs API-level access to an LLM, which is useful when model fine-tuning is not available. It avoids querying the LLM for every test sample. It can handle larger tables better than methods that try to serialize the whole prediction problem into one prompt. And because the final predictor is simple, inference is much cheaper than a fully LLM-based approach.

## What the experiments show

The paper evaluates FeatLLM on 13 tabular datasets across binary and multiclass tasks, including standard datasets like Adult, Bank, and Heart, as well as newer and synthetic datasets.

Across these benchmarks, FeatLLM is consistently among the best-performing methods. The authors report that it outperforms alternatives such as TabLLM and STUNT by about 10% on average. It also performs well in very small-shot settings, sometimes matching conventional tabular methods that use many more labeled examples.

The ablation studies make the design choices look justified. Removing the tuning step, the ensemble, the feature descriptions, or the reasoning instruction all hurt performance. The paper also shows that the generated rules are often informative, and that the method is relatively robust when unrelated columns are added.

## The big takeaway

FeatLLM is not trying to replace standard tabular models with a giant LLM end to end. Instead, it asks a more practical question: can an LLM help invent useful features from a small number of examples?

According to the paper, the answer is yes.

By prompting the model to reason about the task, extract class-specific rules, convert them into binary features, and then train a lightweight classifier on top, FeatLLM creates a low-cost, few-shot pipeline that is easier to deploy than fully LLM-based tabular predictors.

If you think of the LLM as a smart feature engineer rather than the final decision-maker, the whole method becomes much easier to understand. And that is exactly the point.



# Why FeatLLM Beats End-to-End LLM Prediction on Tabular Data

Large language models have become a natural fit for text, but tabular data is a different beast. A row in a spreadsheet is not a sentence, and a good prediction often depends on subtle combinations of columns rather than fluent reasoning over words. Most LLM-based tabular methods handle this by serializing each row into text and asking the model to predict directly. That works, but it comes with a cost: every prediction requires an LLM call, prompts grow quickly as the number of columns increases, and fine-tuning is often required to get strong results.

The paper behind FeatLLM takes a different route. Instead of using the LLM as the final predictor, it uses the LLM as a feature engineer. In other words, the model is asked to discover rules that explain the task, and those rules are turned into new binary features. A lightweight downstream classifier then uses those features to make predictions. That small shift in role is what makes FeatLLM both more practical and, in the paper’s experiments, more accurate than end-to-end LLM prediction methods.

## The core problem with end-to-end LLM tabular prediction

End-to-end tabular LLM methods usually follow the same recipe: describe the task in natural language, serialize the columns and values, add a few labeled examples, and let the LLM predict the label. Some methods also fine-tune the backbone with parameter-efficient techniques like LoRA or IA3.

The issue is that this makes inference expensive and fragile. Every test sample has to go through the LLM. If the table has many features, the prompt can become too long, which is especially problematic for datasets with over 100 columns. The paper also points out that some strong LLMs are only available through inference APIs, so training or fine-tuning them is not always possible. That is a real constraint if you want to deploy a model in practice rather than just benchmark it.

FeatLLM is designed to avoid those bottlenecks.

## FeatLLM turns the LLM into a rule generator

Instead of asking the LLM to output the final class for each row, FeatLLM asks it to extract the conditions that define each class. The prompt is structured in two steps.

First, the LLM is guided to reason about the relationship between the task and the features using its prior knowledge. For example, in a medical task, it can infer which kinds of measurements or patient attributes are plausibly relevant. Second, using a few labeled examples, it derives class-specific rules. These rules are written in a constrained format so they can be parsed automatically.

Those rules are then converted into binary features. For each sample, a feature says whether or not the sample satisfies a given rule. A simple linear model then learns how important each rule is for each class. The paper uses non-negative weights, followed by a softmax over class logits.

This is the key idea: once the rules are extracted, inference no longer needs the LLM. The LLM is only used to engineer features, not to score every test row.

## Why this is more practical

FeatLLM has three advantages that matter in real deployments.

First, inference cost is much lower. After rule extraction, prediction uses only the lightweight downstream model. The paper reports that FeatLLM’s inference time is comparable to conventional methods, while end-to-end LLM baselines such as in-context learning, TABLET, and TabLLM are much slower because they must call the LLM for each sample.

Second, it works with API-only access. FeatLLM does not rely on fine-tuning the LLM backbone. That makes it usable even when the model is only exposed through an API, which is common for strong proprietary models.

Third, it scales better to wide tables. The paper uses bagging over features and examples, plus an ensemble of multiple runs, to keep prompts smaller and improve robustness. This matters because serialized tabular data can blow past prompt limits quickly. By generating rules on subsets of the data and combining the results, FeatLLM avoids the “too many columns” failure mode that hurts many direct prompting approaches.

## What the experiments show

The paper evaluates FeatLLM on 13 tabular classification datasets spanning standard benchmarks, newer UCI additions, and synthetic tasks. Across these datasets, FeatLLM is consistently top-performing or near the top. The authors report that it outperforms alternatives such as TabLLM and STUNT by about 10% on average.

A few results are especially telling. With just 4 labeled examples, FeatLLM can match conventional tabular models that need 32 shots. That suggests the rules extracted by the LLM are doing real work, not just acting as a fancy wrapper around a small classifier. The method is also more robust on datasets with many features, where end-to-end LLM methods struggle because the prompt becomes too large.

The ablation study backs this up. Removing the tuning step, the ensemble, the feature descriptions, or the reasoning guidance all hurt performance. In other words, the gains come from the full pipeline: structured prompting, rule extraction, lightweight learning, and ensembling.

## Why FeatLLM is a better fit for tabular data

The main lesson from this paper is that tabular prediction does not need to be an all-or-nothing LLM problem. If you use the LLM to discover useful rules once, you can hand off the actual prediction task to a simpler model that is cheaper, faster, and easier to deploy.

That makes FeatLLM especially appealing in low-shot settings, where labels are scarce and prior knowledge matters. It is also a better fit for tables with many columns, where prompt length and inference cost can become deal-breakers.

In short, FeatLLM wins not because it asks the LLM to do more, but because it asks the LLM to do less — and to do the most valuable part of the job: finding the right features.



# Can AI-Generated Rules Be Trusted? What FeatLLM Reveals About Interpretability and Robustness

Large language models are often used as black-box predictors: you give them a table, and they return a label. The FeatLLM paper takes a different path. Instead of asking the LLM to make the final prediction for every sample, it asks the model to generate rules that explain how a class should be identified. Those rules are then turned into features for a simple downstream classifier.

That shift matters. It makes the system cheaper at inference time, easier to inspect, and more robust in low-shot tabular learning. But it also raises an important question: if the rules come from an LLM, can we really trust them?

## From predictions to rules

FeatLLM treats the LLM as a feature engineer. Given a task description, feature descriptions, and a few labeled examples, the model is prompted in two stages. First, it is encouraged to infer the relationship between the features and the target using its prior knowledge. Second, it uses that understanding plus the examples to produce class-specific rules.

These rules are meant to be human-readable. In practice, they describe conditions on the input table, such as whether a feature crosses a threshold or falls into a certain category. The paper constrains the response format so the rules can be parsed automatically, then converts each rule into a binary feature: does the sample satisfy the rule or not?

That is the core interpretability move in FeatLLM. The model is no longer hiding its reasoning inside a huge neural network. Instead, it externalizes part of that reasoning as explicit criteria that can be read, checked, and reused.

## Why the rules are more than just decoration

Once the rules are generated, FeatLLM does not rely on them blindly. It fits a simple linear model on top of the binary rule features. The model learns non-negative weights, so rules that are useful for a class can increase that class’s score, while less useful ones can be downweighted.

This is an important design choice. The generated rules are not treated as perfect ground truth. They are treated as candidate signals, and the downstream model decides which ones matter more in the few-shot data. The paper’s analysis shows that many generated rules are informative even before tuning, and that tuning helps filter out weaker rules.

In other words, interpretability here is not just about being able to read the rules. It is also about being able to test them against data.

## Why ensembling helps

A single LLM prompt can produce useful rules, but it can also miss important conditions or include noisy ones. FeatLLM improves robustness by repeating the whole process multiple times and combining the results.

The paper uses two ideas here: ensembling and bagging. It randomizes the order of few-shot examples, sets a higher temperature for rule generation, and samples subsets of features or instances across trials. This creates diversity across rule sets. Then the predictions from multiple trials are averaged.

This matters for two reasons. First, if one trial generates a weak or flawed rule, other trials can compensate. The paper connects this to self-consistency: rules that appear repeatedly across trials are more likely to be reliable. Second, bagging helps with a practical limitation of LLMs, namely prompt length. When a dataset has many features, the full serialized table can become too long. Sampling subsets keeps the prompt manageable.

So robustness here is not just statistical; it is also operational.

## What the spurious-correlation experiment says

One of the most interesting parts of the paper is its test for spurious correlations. The authors take the Heart dataset and attach irrelevant columns from the Adult dataset, then gradually add more unrelated features. The goal is to see how well each method resists noise.

FeatLLM degrades the least under this setting. The paper attributes this to the way the LLM is guided to think about the relationship between the task and the features before extracting rules. That prior-knowledge step helps prevent rules from being built on irrelevant columns. In fact, the paper reports that rules based on noisy columns accounted for only 1-2% of the total.

That is a strong sign of robustness, especially in low-shot settings where models are prone to overfitting whatever signal they can find.

But the result is not a blanket guarantee. The paper also notes that FeatLLM can still learn spurious correlations and misunderstand causal relationships when the added columns come from closely related data. So the system is better at filtering obvious noise than at solving causality in the general sense.

## The trust problem: LLM prior knowledge cuts both ways

This is the key caveat. FeatLLM relies on the LLM’s prior knowledge to propose rules. That is exactly what makes it powerful in few-shot settings, but it is also where bias can enter.

If the LLM has an incorrect assumption about a domain, that assumption can shape the generated rules. Because those rules are then converted into features, the bias is not just in a textual explanation. It can directly affect the downstream classifier.

The paper explicitly flags this issue in its broader impact discussion. The prior knowledge embedded in the LLM may include societal biases or misinformation, and that knowledge can influence predictions, sometimes even more than the few labeled samples provided by the user.

So the answer to “can AI-generated rules be trusted?” is: only partially, and only with validation. FeatLLM makes the rules visible, which helps. But visibility is not the same as correctness.

## What FeatLLM changes in practice

FeatLLM is best understood as a compromise between LLM flexibility and traditional model reliability. It uses the LLM where it is strong: understanding language, using prior knowledge, and proposing candidate decision criteria. Then it hands off to a simpler model for prediction and weighting.

That design gives it several advantages. It avoids per-sample LLM inference at test time. It requires only API-level access, not fine-tuning. It also works better with long-feature tables than end-to-end LLM prediction approaches, because the feature engineering happens through repeated sampled prompts rather than one giant prompt for every test case.

Across 13 tabular datasets, the paper reports that FeatLLM consistently ranks at or near the top, outperforming alternatives such as TabLLM and STUNT by about 10% on average. Just as importantly for this discussion, it does so while making the learned signal more inspectable.

## The bottom line

FeatLLM shows that LLMs do not have to be used as opaque predictors. They can also act as rule generators, helping turn tabular problems into simpler, more interpretable feature-based models.

But the paper is careful not to oversell the trustworthiness of those rules. Ensembling and bagging make the system more robust, and the spurious-correlation experiments show real resilience to irrelevant features. Still, the generated rules inherit whatever prior knowledge the LLM brings to the task, including its blind spots.

That is the real lesson here: AI-generated rules can be useful, readable, and surprisingly robust, but they should be treated as learned hypotheses, not as ground truth.
