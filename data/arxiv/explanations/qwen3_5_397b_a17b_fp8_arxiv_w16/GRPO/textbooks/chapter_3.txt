Chapter 3: # Pre-Training Strategy: From Code to Mathematics

The development of DeepSeekMath-Base represents a strategic departure from conventional approaches to building mathematical language models. Rather than relying solely on scaling model parameters or aggregating massive quantities of academic papers, the creators of DeepSeekMath focused on the quality and composition of the pre-training data, as well as the foundational capabilities of the initialization model. This chapter delves into the specific architectural decisions that enabled a 7-billion parameter model to compete with closed-source giants containing hundreds of billions of parameters. Central to this success is the hypothesis that code training serves as a critical catalyst for mathematical reasoning, a premise tested through rigorous ablation studies involving different training stages and data mixtures. Furthermore, the chapter examines the counter-intuitive finding that arXiv papers, traditionally considered the gold standard for mathematical pre-training, may offer diminishing returns when used in isolation compared to carefully filtered web data. By understanding these pre-training dynamics, students can appreciate how domain-specific competencies are cultivated in large language models (LLMs) not just through volume, but through the syntactic and logical structures inherent in the training corpus.

# Initialization Choice: Why Start with DeepSeek-Coder?

The foundation of DeepSeekMath-Base lies in its initialization with DeepSeek-Coder-Base-v1.5 7B, a model previously trained extensively on code. This decision was not arbitrary but stemmed from empirical observations regarding the transferability of skills between computer programming and mathematical problem-solving. The underlying intuition is that both coding and mathematics require precise logical structuring, adherence to strict syntax, and the ability to decompose complex problems into executable steps. When a model learns to write code, it internalizes patterns of causality and procedural logic that are directly applicable to deriving mathematical proofs or solving quantitative word problems. The researchers posited that starting from a general-purpose language model might require the network to learn these structural constraints from scratch during mathematical pre-training, whereas a code-initialized model already possesses a latent representation of algorithmic thinking.

This choice addresses a long-standing question in the field: does code training genuinely improve reasoning abilities? While often hypothesized, concrete evidence had been scarce prior to this work. By initializing DeepSeekMath with a coder base, the authors leveraged a model that was already adept at handling formal languages and symbolic manipulation. Code involves variables, functions, loops, and conditionals, all of which map conceptually to algebraic expressions, functional relationships, and logical deductions in mathematics. Consequently, the transition from generating Python scripts to generating chain-of-thought mathematical derivations becomes smoother. The model does not need to relearn how to maintain context over long sequences of symbols or how to follow a rigid set of rules; it simply needs to adapt these existing capabilities to the semantic domain of mathematics. This strategic initialization effectively reduced the learning curve for mathematical reasoning, allowing the subsequent pre-training phase to focus on acquiring domain-specific knowledge rather than fundamental logical scaffolding.

# Experimental Analysis: Code Training as a Catalyst for Reasoning

To rigorously validate the hypothesis that code training enhances mathematical reasoning, the researchers conducted a series of controlled experiments using a 1.3 billion parameter variant of their model architecture. These experiments were designed to isolate the effects of code exposure versus general text exposure on downstream mathematical performance. The results provided compelling evidence that code training acts as a potent catalyst, improving the model's ability to solve problems both with and without external tools. In scenarios where models were permitted to use tools—specifically writing and executing Python programs to solve problems—the benefits of prior code training were immediate and substantial. A model subjected to code training demonstrated a significantly higher proficiency in generating syntactically correct and logically sound programs compared to models trained only on general text or pure mathematics from the outset.

Beyond tool use, the experiments revealed that code training also bolsters "native" mathematical reasoning—the ability to solve problems through step-by-step textual deduction without invoking an interpreter. In a two-stage training setup where models were first trained on code tokens and subsequently on math tokens, the initial code phase yielded moderate improvements in purely textual reasoning tasks. More importantly, it appeared to accelerate the efficiency of the subsequent math training phase. The model exposed to code first reached higher performance plateaus faster than its counterparts, suggesting that the logical frameworks learned during coding facilitated quicker absorption of mathematical concepts. However, the analysis also uncovered nuances regarding model capacity; when code and math tokens were mixed simultaneously in a single-stage training regime for smaller models, there was sometimes a compromise in non-tool-based reasoning performance. This suggests that while code is beneficial, smaller models may struggle to assimilate both distributions simultaneously without a sequential curriculum, reinforcing the value of the two-stage approach or careful data balancing for larger architectures like the 7B DeepSeekMath-Base.

# Two-Stage vs. One-Stage Training Regimes

The investigation into training regimes highlighted distinct trade-offs between sequential (two-stage) and simultaneous (one-stage) learning strategies. In the two-stage approach, exemplified by the configuration "Code Training for 400B Tokens $\rightarrow$ Math Training for 150B Tokens," the model undergoes a dedicated period of immersion in programming logic before shifting focus entirely to mathematics. This regimen proved highly effective for program-aided reasoning tasks. The initial saturation with code established robust pathways for symbolic manipulation, which were then refined and specialized duringthe math-only phase. This sequence avoided interference between domains during the critical early phases of learning, allowing the model to master the syntax of code before layering on the semantics of advanced mathematics. Conversely, a control experiment replacing code with general text in the first stage ("General Training $\rightarrow$ Math Training") failed to yield similar gains, confirming that it is specifically the structural nature of code, rather than just additional pre-training volume, that drives improvement.

In contrast, one-stage training involved mixing code tokens and math tokens within a single continuous stream—for instance, training on a mixture of 400B code tokens and 150B math tokens simultaneously. While this approach offered advantages in mitigating "catastrophic forgetting"—a phenomenon where learning new information causes abrupt degradation in previously acquired skills—it presented challenges for smaller models attempting to learn both domains concurrently. For deepseek-math-base 7B (the final product), an effective balance was struck not by strictly separating stages forever but by curating a specific data mixture during continual pre-training that retained enough code exposure (20% GitHub) alongside heavy math emphasis (56% DeepSeekMath Corpus). The experimental findings suggest that while one-stage mixing preserves coding fluency better than strict sequential switching which might degrade coding skills if not managed well (though here they noted mixing alleviates forgetting seen if you switch completely away), optimal performance requires acknowledging capacity limits: smaller models benefit from staging order (code first), while larger mixes require careful proportioning (as done in final DeepSeekMath Base) ensuring neither domain overwhelms representational capacity too early causing instability or poor convergence rates across either task type independently . Ultimately , these insights guided construction final recipe : initialize w/ coder -> continue w/ balanced mix heavily weighted toward curated web -based maths .
