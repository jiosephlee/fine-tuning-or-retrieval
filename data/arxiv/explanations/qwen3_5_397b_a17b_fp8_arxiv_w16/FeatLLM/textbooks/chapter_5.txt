Chapter 5: Chapter 5: From Natural Language Rules to Executable Features

The transition from abstract reasoning to concrete computation represents a critical juncture in the \textsf{FeatLLM} framework. While the preceding stages leverage the Large Language Model's (LLM) vast prior knowledge to hypothesize relationships between features and target classes, these hypotheses exist initially only as unstructured natural language text. To utilize these insights for actual prediction, they must be transformed into a rigorous, executable format that a machine learning algorithm can process. This chapter details the mechanism by which \textsf{FeatLLM} bridges this gap, converting linguistic rules into binary feature vectors and subsequently integrating them into a probabilistic model. The process involves overcoming the inherent syntactic instability of generative models, safely executing derived code, and mathematically formalizing how these new features contribute to class likelihood estimation under few-shot constraints.

# The parsing challenge: Syntactic noise in LLM outputs

The primary obstacle in automating feature engineering with LLMs lies in the discrepancy between human-readable logic and machine-executable syntax. When an LLM is prompted to derive rules for distinguishing classes—for instance, determining if a patient has heart failure based on age and cholesterol levels—it naturally responds in fluent natural language. However, this fluency introduces significant syntactic variability, often referred to as "syntactic noise," which renders direct programmatic parsing unreliable. An LLM might express a condition as "age is greater than 60" in one instance, "age > 60" in another, or even "patients older than sixty years" in a third. While semantically identical to a human reader, these variations pose a formidable challenge for traditional string parsing algorithms or regular expressions, which require rigid adherence to specific patterns. Attempting to build a deterministic parser capable of handling every conceivable phrasing variation would be computationally prohibitive and prone to failure, especially when dealing with complex logical operators like AND or OR that the LLM might combine dynamically.

Furthermore, the stochastic nature of LLM decoding means that even with identical prompts and temperature settings, slight deviations in wording can occur across different runs. In the context of \textsf{FeatLLM}, where robustness is paramount, relying on fragile heuristic parsers would introduce a single point of failure that could invalidate the entire feature generation pipeline. If the system cannot correctly interpret a generated rule due to a minor syntactic flourish, valuable prior knowledge encoded in that rule is lost. This necessitates a parsing strategy that is not only flexible but also semantically aware, capable of understanding the intent behind the words rather than just matching character sequences. The solution must account for the fact that the generator of the rules (the LLM) is also uniquely qualified to interpret them, given its training on vast corpora of both natural language and computer code.

# "LLM-as-a-Parser": Generating Python code from natural language rules

To address the challenges of syntactic noise, \textsf{FeatLLM} adopts a recursive strategy known as "LLM-as-a-Parser." Rather than attempting to parse the natural language rules using external software tools, the framework leverages the LLM itself to translate its own linguistic outputs into executable code. This approach capitalizes on the model's dual competency in understanding semantic nuances in text and generating syntactically correct programming statements, a skill acquired during its pre-training on diverse code repositories. The process involves constructing a secondary prompt that explicitly instructs the LLM to act as a translator. This prompt includes the function signature defining the expected inputs (the raw data features) and outputs (binary indicators), along with the specific natural language rules generated in the previous stage.

By framing the task as code generation rather than text parsing, the system guides the LLM to resolve ambiguities internally. For example, if a rule states "cholesterol levels are high," the LLM, informed by the feature definitions provided in the prompt context, can map this vague descriptor to a specific numerical threshold or boolean check consistent with the dataset's schema. The output of this stage is not a interpreted truth value, but a snippet of Python code that implements the logic of the rule. This code is designed to be simple and self-contained, ensuring that it can be executed independently for each data sample. This method effectively bypasses the need for complex regular expression engines or custom compilers, delegating the difficult task of semantic-to-syntactic mapping to the model best equipped to handle it. The result is a set of programmatic representations of the rules that are ready for execution, maintaining fidelity to the original logical intent while adhering to strict programming grammar.

# Executing generated code safely to create binary feature vectors

Once the natural language rules have been transcribed into Python code snippets by the LLM, the next step is to execute this code against the tabular dataset to generate new features. In \textsf{FeatLLM}, this is achieved using Python's built-in \texttt{exec()} function, which allows for dynamic execution of strings containing valid Python statements. For each sample in the dataset and for each generated rule, the corresponding code snippet is executed. The logic within these snippets evaluates whether the specific sample satisfies the conditions laid out in the rule. The outcome of this evaluation is binary: if the sample adheres to all conditions specified in the rule, it receives a value of $1$; otherwise, it receives a $0$. This process transforms each abstract rule into a concrete binary feature column appended to the original dataset.

This transformation results in a new feature matrix where every column corresponds to a specific hypothesis or criterion proposed by the LLM regarding class membership. Because these features are binary indicators of rule satisfaction, they serve as interpretable signals that distill complex interactions between original features into simple true/false propositions. For instance, instead of feeding raw age and blood pressure values directly into a downstream model, \textsf{FeatLLM} creates features such as "Is Age $> 60$ AND Blood Pressure $> 140$?"
