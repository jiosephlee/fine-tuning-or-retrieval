\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 4: Chapter 4: Prompt Engineering for Rule Discovery

The efficacy of the \textsf{FeatLLM} framework hinges critically on its ability to transform a Large Language Model (LLM) from a generic text generator into a specialized feature engineer. Unlike traditional approaches that simply feed serialized data into an LLM for direct prediction, \textsf{FeatLLM} requires the model to extract explicit logical criteria, or "rules," that define the relationship between input features and target classes. This chapter delineates the sophisticated prompt engineering strategies employed to achieve this transformation. By structuring the input prompt to mimic the cognitive process of a human domain expert, the framework guides the LLM away from identifying superficial statistical patterns and toward inferring robust causal relationships. The prompt design is architected into three distinct, interdependent components: the basic information description, which grounds the model in the specific task context; the reasoning instructions, which enforce a step-by-step deductive process; and the response formatting constraints, which ensure the output is machine-readable and logically consistent.

# Component 1: Basic Information Description (Task, Features, Examples)

The foundation of any successful interaction with an LLM in this context is the provision of comprehensive and structured background information. The first component of the \textsf{FeatLLM} prompt serves as the "basic information description," acting as the primary source of truth for the model regarding the problem domain. This section is meticulously crafted to include three essential elements: a precise task description, detailed feature definitions, and representative example demonstrations. The task description is not merely a label but is formulated as a specific inquiry to focus the model's attention. For instance, rather than stating "predict heart failure," the prompt poses a question such as, "Does this patient's myocardial infarction complications data indicate chronic heart failure? Yes or no?" This interrogative format primes the LLM to think in terms of diagnostic criteria rather than abstract pattern matching.

Alongside the task definition, the prompt provides rigorous descriptions of every input feature. This includes specifying the value type for each attribute—whether it is numerical, categorical, or binary—and, where necessary, offering natural language definitions to clarify ambiguous terms. For categorical variables, the prompt may list potential categories to bound the model's expectations and prevent hallucinations of non-existent values. This level of detail is crucial because it allows the LLM to leverage its vast pre-trained knowledge base effectively. When an LLM understands that a specific column represents "age" measured in years versus "income" measured in dollars, it can apply relevant world knowledge, such as knowing that advanced age correlates with higher disease risk, without needing to learn this correlation solely from the few provided training samples.

The final element within this component is the inclusion of few-shot example demonstrations. These examples consist of actual data samples from the training set, serialized into a textual format alongside their ground-truth labels. The serialization follows a strict syntax established in prior research to maintain consistency: each sample is represented as a sequence stating "$f_1$ is $\mathbf{x}^i_1$, ..., $f_d$ is $\mathbf{x}^i_d$. Answer: $\mathbf{y}^i$." Here, $f_j$ denotes the name of the $j$-th feature, $\mathbf{x}^i_j$ is the value of that feature for the $i$-th sample, and $\mathbf{y}^i$ is the corresponding class label. By presenting these concrete instances immediately after defining features and tasks, the prompt bridges the gap between abstract definitions and real-world data distributions. These demonstrations serve as anchors for in-context learning, allowing the LLM to observe how specific combinations of feature values map to specific outcomes, thereby grounding its subsequent rule generation in empirical evidence rather than pure speculation.

# Component 2: Reasoning Instructions (Chain-of-Thought Adaptation)

While providing data and definitions is necessary, it is insufficient for eliciting high-quality rules that generalize well in few-shot settings. Naive prompting often leads LLMs to latch onto spurious correlations present in small datasets—for example, associating a specific row index or an irrelevant noise column with the target class simply because they co-occur in the few provided examples. To counteract this tendency, \textsf{FeatLLM} incorporates a specialized "reasoning instruction" component inspired by Chain-of-Thought methodologies but adapted specifically for tabular feature engineering. This component explicitly divides the inference process into two sequential stages, forcing the model to engage in deliberate reasoning before attempting to formulate rules.
