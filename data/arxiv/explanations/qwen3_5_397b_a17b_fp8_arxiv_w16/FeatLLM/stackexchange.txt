\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How exactly does FeatLLM parse natural language rules into executable code without syntax errors?
Question:
In Section 3.2 ('Parsing rules for feature generation'), the authors mention that LLM outputs can be noisy (e.g., using 'greater than' instead of '$>$'). They propose using the LLM itself to generate Python code via a prompt, which is then executed with `exec()`. 

My confusion lies in the reliability of this step. If the initial rule generation produces ambiguous natural language, doesn't asking the LLM to convert that same ambiguous text into code just propagate the error? How does the prompt ensure that the generated code is syntactically valid and logically equivalent to the intended rule, especially when dealing with complex categorical conditions?
Answer:
The reliability of converting ambiguous natural language rules into executable code in FeatLLM stems from a strategic shift in responsibility: rather than attempting to build a rigid, deterministic parser that must handle every linguistic variation, the authors leverage the LLM's own semantic understanding to act as the translator. As noted in Section 3.2 under "Parsing rules for feature generation," the system acknowledges that LLM outputs are inherently noisy, often containing variations like "greater than" instead of the symbolic operator `$>$`. To resolve this without propagating errors, FeatLLM employs a secondary prompting step where the *same* LLM (or a capable code-generation model) is tasked with translating its own previously generated natural language rules into Python code.

This approach works because modern LLMs are trained on vast corpora of code and possess a robust ability to map semantic intent to syntactic structure, even when the input description is informal. The prompt for this translation step explicitly includes the function signature, input/output descriptions, and the specific natural language rule inferred in the earlier stage. By framing the task as "generate simple code that implements this logic" rather than "parse this string," the system bypasses the fragility of traditional regular-expression-based parsers. The LLM effectively performs semantic disambiguation internally; if it understands that "age greater than 50" logically equates to `$age > 50$`, it generates the syntactically correct Python snippet directly. This creates a self-correcting loop where the model's broad training on coding tasks compensates for the lack of strict formal grammar in its initial rule generation.

Regarding your concern about complex categorical conditions, the framework mitigates logical equivalence errors through two mechanisms outlined in the paper. First, during the initial rule generation (Section 3.1), the "Response instruction" explicitly guides the LLM to adhere to specific formats based on feature types, reducing the likelihood of fundamentally flawed logic before the coding step even begins. Second, and perhaps more importantly, the architecture does not rely on any single rule being perfect. The "Ensembling with bagging" section (Section 3.2) explains that FeatLLM repeats the entire process multiple times (e.g., 20 trials) with randomized temperatures and shuffled few-shot examples. This leverages the concept of self-consistency; while one trial might generate a slightly off-code snippet for a complex category, other trials are likely to generate correct variations. The downstream linear model then learns weights $\mathbf{w}_k$ for these binary features, effectively down-weighting or ignoring features derived from erroneous code while amplifying those from accurate rules. Thus, occasional syntax or logic failures in individual code generations are treated as noise and filtered out by the ensemble and weighting mechanism, ensuring the final prediction remains robust.

### Why are the weights $\mathbf{w}_k$ projected to a positive subspace using $\max(\mathbf{w}_k, 0)$?
Question:
Equation (2) defines the logit calculation as $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$. The paper states this is done to ensure features 'do not reduce the likelihood of a class.'

Intuitively, shouldn't a powerful model be allowed to learn negative weights? For instance, if a rule says 'Age > 80', maybe satisfying this rule should *decrease* the probability of belonging to a 'Healthy' class. By forcing all weights to be non-negative, aren't we restricting the model's expressivity? Does this mean the system relies entirely on the LLM generating only 'positive evidence' rules, and if the LLM generates a rule that correlates negatively with the target, that rule becomes useless?
Answer:
The projection of weights $\mathbf{w}_k$ to a positive subspace using $\max(\mathbf{w}_k, 0)$ is a deliberate design choice rooted in the specific semantics of how \textsf{FeatLLM} constructs features, rather than a general limitation on model expressivity. To understand this, one must look at how the features $\mathbf{z}_k^i$ are generated. As described in the "Parsing rules for feature generation" and "Inferring class likelihood" sections, the LLM acts as a feature engineer that explicitly derives rules associated with a *specific* target class. For instance, if the task is to predict "Heart Failure," the LLM is prompted to generate rules that identify conditions *indicative* of that disease (e.g., "Age > 80" implies high risk). Consequently, the resulting binary feature $\mathbf{z}_k^i$ takes a value of 1 only if the sample satisfies a rule that the LLM has already deemed as positive evidence for class $k$.

Because the feature generation process inherently filters for positive correlation during the rule creation phase (Step 2 of the reasoning instruction), allowing the downstream linear model to learn negative weights would be semantically contradictory. If the model were allowed to learn a negative weight for a rule like "Age > 80" in the context of predicting "Healthy," it would imply that satisfying a rule intended to signal danger actually reduces the likelihood of being healthy. While mathematically valid in a standard black-box model, in this framework, it suggests the LLM generated a nonsensical or spurious rule. By enforcing non-negativity via $\max(\mathbf{w}_k, 0)$, the system ensures that every active rule contributes additively to the class likelihood, adhering to the principle that "features do not reduce the likelihood of a class." This constraint simplifies the learning problem for the few-shot regime by preventing the model from trying to invert logically flawed rules; instead, if a generated rule is indeed negatively correlated or useless for the target class, the optimization process simply drives its weight toward zero, effectively ignoring it. This mechanism is confirmed in the ablation studies and quality analysis, where tuning allows the model to filter out irrelevant rules (those with weights near zero) while retaining only those that provide consistent positive evidence, thereby enhancing robustness against noise without needing complex negative interactions.

### What is the precise distinction between Step 1 and Step 2 in the Reasoning Instruction?
Question:
Section 3.1 describes a two-step reasoning process: (1) inferring causal relationships based on general knowledge without looking at examples, and (2) deducing specific rules using both Step 1 knowledge and few-shot examples.

I am struggling to visualize how this separation happens in the prompt. Does the LLM output an intermediate text block for Step 1 before seeing the examples, or are both steps part of a single Chain-of-Thought generation where the model is explicitly instructed to 'first think about general biology' before 'looking at these specific rows'? If it's a single pass, how does the model prevent the few-shot examples from contaminating the 'general knowledge' phase?
Answer:
The distinction between Step 1 and Step 2 in the reasoning instruction lies in the source of information the Large Language Model (LLM) is permitted to access and the specific cognitive task it performs at each stage, all within a single continuous generation pass. According to Section 3.1 ("Prompt Design for Extracting Rules"), the framework guides the LLM to mimic an expert human's workflow by structuring the prompt with explicit instructions that separate these phases logically, even though they occur sequentially in one output stream.

In Step 1, the LLM is instructed to infer causal relationships or tendencies between the input features and the target task solely based on its internal prior knowledge and common sense. Crucially, the prompt explicitly directs the model to perform this inference "without referring to example demonstrations." This constraint ensures that the model establishes a theoretical understanding of the domain (e.g., knowing generally that age correlates with certain diseases) before it sees any specific data points. By isolating this phase, the framework leverages the LLM's pre-trained world knowledge to form hypotheses about feature relevance without being immediately biased by the statistical noise or idiosyncrasies of the few-shot examples provided later in the context.

Step 2 occurs immediately after Step 1 in the generated text but shifts the model's focus to synthesis and deduction. In this phase, the LLM combines the general causal relationships identified in Step 1 with the actual "example demonstrations" (the few-shot training samples serialized into text) that are now visible in the prompt context. The goal here is to derive concrete, decisive rules for distinguishing classes. Because Step 1 has already primed the model to focus on semantically meaningful features based on general knowledge, Step 2 uses the specific examples to refine these ideas into executable logic rather than blindly fitting patterns to the limited data.

Regarding your concern about contamination or how this works in a single pass: The mechanism relies entirely on the instructional phrasing within the prompt rather than architectural barriers or separate API calls. The prompt includes an introductory sentence similar to Chain-of-Thought prompting, followed by explicit directives telling the model to "first think about..." (Step 1) ignoring the examples, and "then..." (Step 2) use the examples. While LLMs technically attend to all tokens in their context window simultaneously during generation, empirical results in chain-of-thought literature suggest that explicitly instructing the model to ignore specific sections until a later logical step effectively simulates a separated reasoning process. The ablation study in Section 4.2 confirms the necessity of this separation; removing Step 1 ("-Reasoning") leads to performance degradation, particularly in low-shot regimes, suggesting that without this initial grounding in general knowledge, the model is more prone to identifying spurious correlations in the few available examples. Thus, the "separation" is a logical constraint enforced by natural language instructions within a unified generative trajectory.

### How does feature bagging specifically mitigate the prompt size limitation compared to simply truncating features?
Question:
The abstract and Introduction claim that FeatLLM overcomes prompt size limitations by employing feature bagging within an ensemble. 

If I have a dataset with 200 features but my context window only allows 50, bagging means each ensemble member sees a random subset of 50 features. But doesn't this mean any single rule generated only understands interactions within that subset? How does averaging the probabilities from these 'partial-view' models recover global patterns that require seeing all 200 features simultaneously? Isn't there a risk that critical multi-feature interactions are never captured because no single bag contains all necessary features?
Answer:
The key distinction lies in shifting the LLM's role from a direct predictor that must see all data at once to a **feature engineer** that generates independent, interpretable rules, which are then aggregated by a separate, simple downstream model.

When you simply truncate features to fit a context window, you permanently discard information, forcing the model to make predictions based on an incomplete picture of the data. In contrast, \textsf{FeatLLM} uses feature bagging to create an ensemble of "weak learners," where each member operates on a random subset of features (e.g., 50 out of 200). While it is true that a single rule generated in one trial might only capture interactions within its specific subset, the framework does not rely on any single rule to solve the entire problem. Instead, it leverages the statistical power of ensembling. By running this process multiple times (e.g., $T=20$ trials) with different random subsets and high temperature sampling, the system generates a diverse pool of rules covering various parts of the feature space.

The recovery of global patterns happens in the downstream aggregation phase, not within the LLM prompt itself. Once the rules are generated and parsed into binary features (indicating whether a sample satisfies a specific rule), \textsf{FeatLLM} fits a simple linear model with non-negative trainable weights $\mathbf{w}_k$ to these features. This downstream model learns to assign importance to each rule based on the few-shot training data. If a critical global pattern requires the combination of Feature A and Feature B, and they happen to appear together in some bagged subsets, the LLM may generate a rule capturing that interaction. Even if no single rule perfectly captures a complex high-order interaction across all 200 features simultaneously, the ensemble approach relies on the principle that multiple lower-order rules or partial views can collectively approximate the decision boundary effectively when weighted correctly. The linear model essentially performs a weighted vote across hundreds of these partial perspectives, allowing the system to synthesize a robust global predictor from many local insights.

Furthermore, this approach mitigates the risk of missing critical interactions through redundancy and diversity. Because the bagging process is repeated many times with randomized feature selection and demonstration ordering, there is a high probability that important feature combinations will co-occur in at least some of the trials. The ablation studies in the paper confirm that removing the ensemble component significantly degrades performance, highlighting that the aggregation of these diverse, partial-view models is what provides the robustness needed to overcome the limitations of individual prompts. Thus, rather than trying to force one massive prompt to reason about 200 features at once—which often leads to performance declines due to lost attention or context limits—\textsf{FeatLLM} decomposes the problem into manageable sub-tasks and reconstructs the solution through learned aggregation.

### Is FeatLLM truly 'training-free' if it optimizes weights $\mathbf{w}_k$ via gradient descent?
Question:
The paper emphasizes that FeatLLM requires no model training and only needs API access. However, Section 3.2 describes optimizing trainable weights $\mathbf{w}_k$ using Adam optimizer and cross-entropy loss over 200 epochs.

While it's true we aren't fine-tuning the massive LLM backbone, we are still training a downstream linear model on the few-shot data. In strict few-shot definitions (like standard Prompt Engineering), usually no gradient updates occur at all. Does calling this 'training-free' mislead readers about the computational cost during the adaptation phase, or is there a convention where training a tiny probe layer is considered distinct from 'model training'?
Answer:
The term "training-free" in the context of FeatLLM refers specifically to the Large Language Model (LLM) backbone, distinguishing it from methods that require parameter-efficient fine-tuning (like LoRA or IA3) or full model retraining. As stated in the Introduction and Related Work sections, a primary motivation for FeatLLM is to overcome the infeasibility of applying LLM-based approaches to models that only offer inference APIs without accessible training codebases. When the authors claim the framework is "free from training constraints," they mean that the massive, pre-trained LLM remains frozen; its weights are never updated via gradient descent. The optimization process you identified in Section 3.2 applies exclusively to a simple, lightweight downstream linear model with weights $\mathbf{w}_k$, which learns the importance of the binary features generated by the LLM.

This distinction is crucial because the computational cost and accessibility profile of training a small linear probe on few-shot data differ fundamentally from training or fine-tuning a billion-parameter transformer. The paper highlights in the "Training & inference time comparison" section that FeatLLM requires only a fixed number of API queries (e.g., 30 for ensemble trials) regardless of the dataset size, whereas other methods might require extensive GPU resources for backpropagation through the LLM itself. The optimization of $\mathbf{w}_k$ using Adam over 200 epochs is a standard procedure for fitting a conventional machine learning head (similar to logistic regression) and imposes a negligible computational burden compared to LLM fine-tuning. Furthermore, the ablation study in Section 4.2 explicitly analyzes the contribution of this "-Tuning" step, showing that while summing binary features works, learning the weights $\mathbf{w}_k$ significantly improves performance as the number of shots increases by accurately estimating rule importance. Therefore, describing FeatLLM as "training-free" is consistent with the convention in literature where "training" implies updating the foundation model's parameters, while fitting a downstream classifier on extracted features is considered part of the standard inference or adaptation pipeline rather than model training.

### Why does removing feature descriptions hurt performance more in low-shot regimes than high-shot regimes?
Question:
In the Ablation Study (Section 4.2), removing feature descriptions (`-Description`) causes a significant drop in AUC when shots are low, but less so when shots are high. Conversely, `-Tuning` hurts more when shots are high.

Can someone explain the intuition here? My hypothesis is that with few examples, the LLM must rely heavily on its pre-trained priors (activated by feature names/descriptions) to guess rules. With many examples, the data itself overwhelms the priors, making descriptions less critical. But if that's true, why does weight tuning become *more* important with more data? Is it because more data allows the linear layer to better calibrate which of the many generated rules are actually signal vs noise?
Answer:
The intuition behind your observation lies in the distinct roles that **prior knowledge** and **data-driven calibration** play within the \textsf{FeatLLM} framework as the amount of available training data changes. Your hypothesis is largely correct: in low-shot regimes, the model lacks sufficient statistical evidence to learn reliable patterns from the data alone, so it must lean heavily on the LLM's pre-trained world knowledge. The feature descriptions serve as the primary bridge to activate this prior knowledge, allowing the LLM to infer plausible causal relationships (e.g., knowing that "age" correlates with "heart disease" even with only a handful of examples). When you remove these descriptions (`-Description`), the LLM loses the semantic context needed to generate meaningful rules, forcing it to guess based on sparse data or generic syntax, which leads to a sharp drop in performance.

Conversely, in high-shot regimes, the dynamic shifts because the few-shot examples themselves provide enough signal for the LLM to deduce reasonable rules even without explicit textual descriptions; the data starts to "speak for itself," reducing the marginal utility of the descriptions. However, having many examples introduces a new challenge: distinguishing between high-signal rules and noise. This is where weight tuning (`-Tuning`) becomes critical. The `\textsf{FeatLLM}` framework generates a set of binary features based on LLM-derived rules, but not all generated rules are equally valid or relevant. With ample data, the downstream linear model has enough samples to accurately estimate the trainable weights $\mathbf{w}_k$ in Equation \ref{eq:infer_prob}, effectively learning which rules are predictive and down-weighting those that are spurious or redundant. If you disable tuning in a high-shot setting, you force the model to treat every generated rule as equally important (essentially summing them up), which prevents the system from filtering out noise and capitalizing on the richer information provided by the larger dataset. Thus, descriptions are the scaffold that supports learning when data is scarce, while tuning is the mechanism that refines and calibrates that learning when data is abundant.
