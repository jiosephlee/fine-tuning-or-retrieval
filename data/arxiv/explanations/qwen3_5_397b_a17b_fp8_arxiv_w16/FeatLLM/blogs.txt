# Stop Paying for Every Prediction: How FeatLLM Slashes LLM Costs for Tabular Data

The promise of using Large Language Models (LLMs) for tabular data analysis is undeniable. With their vast repositories of world knowledge, LLMs can understand context, reason through complex relationships, and apply domain expertise that traditional machine learning models often lack. However, a significant bottleneck has prevented their widespread adoption in industrial settings: cost and latency. Most current approaches require sending every single data row to the LLM for inference, turning what should be a millisecond prediction into an expensive API call. This makes scaling to millions of rows financially and technically prohibitive.

A new framework called **FeatLLM** proposes a paradigm shift to solve this exact problem. Instead of treating the LLM as the final predictor for every sample, FeatLLM repurposes the model as an automated feature engineer. By using the LLM only during the setup phase to generate decision rules, the framework allows downstream predictions to run on simple, lightning-fast models. This approach retains the intelligence of the LLM while reducing inference costs to levels comparable with traditional algorithms like logistic regression or XGBoost.

## The High Cost of End-to-End LLM Inference

To understand why FeatLLM is necessary, we must look at how current LLM-based tabular learning methods operate. Typically, these systems serialize tabular data into text prompts and feed them directly into an LLM to get a prediction. Whether using in-context learning or parameter-efficient fine-tuning, the fundamental workflow remains the same: one query per sample.

This architecture creates three critical issues for real-world deployment. First, it is computationally expensive; running an LLM inference for every row in a large dataset quickly exhausts budgets. Second, it introduces high latency, making real-time applications impossible. Third, many high-performing proprietary LLMs only offer API access without allowing users to fine-tune the underlying weights, limiting flexibility. Furthermore, as the number of features in a dataset grows, the serialized text often exceeds the model's context window limit, causing performance to degrade or the process to fail entirely.

## Flipping the Script: The LLM as a Feature Engineer

FeatLLM addresses these limitations by changing the role of the LLM from a predictor to a creator. The core insight is that an LLM excels at understanding the *criteria* that define a specific class or outcome. For example, in a medical diagnosis task, an LLM knows that "age greater than 65" combined with "high cholesterol" strongly correlates with heart disease risk. Instead of asking the LLM to diagnose each patient individually, FeatLLM asks the LLM to write down the rules it uses to make that diagnosis.

The framework operates in two distinct phases. During the initial phase, FeatLLM leverages few-shot examples and natural language descriptions of the features to prompt the LLM. The model is guided through a structured reasoning process where it first analyzes the causal relationships between features and targets based on its internal prior knowledge. Then, using specific training examples, it derives explicit rules—such as "If income > $50k AND debt_ratio < 0.3, then classify as Low Risk."

Once these rules are generated, they are parsed into executable code. The system applies these rules to the entire dataset to create new binary features. If a data sample satisfies a specific rule generated by the LLM, that feature is marked as true (1); otherwise, it is false (0). At this point, the heavy lifting is done. The actual prediction task is handed off to a simple downstream model, such as a linear regression or a basic classifier with non-negative trainable weights. This downstream model learns the importance of each generated rule but does not require any further interaction with the LLM.

## Overcoming Context Limits with Bagging and Ensembling

One of the clever aspects of FeatLLM is how it handles datasets with hundreds of features, which would normally overflow an LLM's context window if serialized completely. The authors employ an ensemble strategy combined with feature bagging to mitigate this constraint. Rather than trying to force all features into a single prompt, FeatLLM runs multiple trials where it randomly selects subsets of features and training samples for each iteration.

In each trial, the LLM generates a unique set of rules based on that specific subset of data. These diverse rule sets are then aggregated into an ensemble model. This approach offers two distinct advantages. First, it naturally bypasses token limits by breaking large tables into manageable chunks. Second, it improves robustness through self-consistency; if the LLM hallucinates an incorrect rule in one trial due to noise or ambiguity, correct rules generated in other trials can compensate during the aggregation phase. The final prediction is derived by averaging probabilities across all ensemble members, ensuring stable performance even when individual rule sets are imperfect.

## Performance That Matches Speed

The efficacy of this approach is backed by rigorous testing across 13 diverse tabular datasets ranging from financial credit risks to medical diagnoses and agricultural yields. In few-shot learning regimes—where only a handful of labeled examples are available—FeatLLM consistently outperforms existing baselines like TabLLM and STUNT by an average margin of 10%. Remarkably, FeatLLM achieves performance comparable to conventional models trained on 32 shots while using only 4 shots of labeled data, demonstrating its ability to effectively inject prior knowledge into sparse datasets.

Perhaps most importantly for industry adoption is the drastic reduction in inference time. Because the LLM is removed from the inference loop entirely after feature generation, prediction speeds drop from seconds per sample (typical for API calls) to microseconds per sample (typical for linear algebra operations). Experiments show that FeatLLM's inference latency is on par with traditional methods like Random Forests or Logistic Regression, while other LLM-based approaches remain orders of magnitude slower due to their reliance on continuous API queries during prediction time regarding each sample .

## A Practical Path Forward for Industrial AI

FeatLLM represents a pragmatic evolution in applying foundation models to structured data problems requiring strict adherence strictly grounded within documented methodology described herein . It acknowledges that while LLMs possess unparalleled reasoning capabilities , they are inefficient engines for repetitive numerical classification tasks . By decoupling feature discovery from final inference , organizations can now leverage sophisticated language priors without sacrificing scalability or blowing their cloud computing budgets . As datasets grow larger and labeling becomes more expensive frameworks like this bridge gap between cutting-edge artificial intelligence research operational reality enabling smarter faster decisions across sectors finance healthcare beyond .



# From Text to Truth: Teaching LLMs to Write Code That Predicts Disease and Credit Risk

Large Language Models (LLMs) have revolutionized how we interact with data, demonstrating an uncanny ability to reason through complex problems using nothing but text prompts. However, applying these massive models directly to tabular data—those ubiquitous spreadsheets containing everything from patient health records to credit scores—remains fraught with challenges. Traditional approaches often ask the LLM to predict the answer for every single row of data, a method that is computationally expensive, slow, and prone to hitting token limits when datasets grow large.

A new framework called **FeatLLM** proposes a paradigm shift. Instead of treating the LLM as a direct predictor, researchers have reimagined it as an expert feature engineer. In this workflow, the LLM does not guess the final outcome; rather, it analyzes the problem context and writes logical rules in natural language. These rules are then automatically parsed into executable code to generate new, high-quality binary features. This allows a simple downstream model, such as linear regression, to achieve state-of-the-art performance in few-shot learning scenarios where labeled data is scarce.

## The Limitations of Direct Prediction

To understand the innovation behind FeatLLM, one must first recognize the bottlenecks of current LLM-based tabular learning methods. Existing techniques typically serialize tabular rows into text and feed them into an LLM to obtain a direct classification. For example, to predict if a loan applicant is high-risk, the system sends the applicant's age, income, and debt history to the LLM and waits for a "Yes" or "No."

This approach creates significant friction in real-world applications. First, it requires an API call for every single sample at inference time, making it prohibitively expensive and slow for large datasets. Second, many top-tier LLMs are only accessible via inference APIs, preventing users from fine-tuning the model weights directly. Finally, tabular datasets often contain dozens or hundreds of features. Serializing all this information into a prompt can easily exceed the context window limits of current models, causing performance to degrade or the process to fail entirely.

FeatsLLM circumvents these issues by decoupling the reasoning phase from the inference phase. The heavy lifting of understanding domain logic happens once during a setup phase, leaving the actual prediction to lightweight, traditional machine learning algorithms.

## Acting as an Expert Consultant

The core philosophy of FeatLLM is to leverage the vast prior knowledge encoded within LLMs to act as a domain expert consultant. When faced with a new task, such as predicting heart failure or credit defaults with only a handful of labeled examples (few-shot learning), humans rely on general knowledge to identify relevant patterns. An expert knows that advanced age and high cholesterol are risk factors for heart disease, even before seeing specific patient data.

FeatLLM mimics this cognitive process through a structured prompting strategy divided into two distinct reasoning steps. First, the model is asked to infer the causal relationships between features and the target variable based purely on general knowledge and feature descriptions, without looking at specific data examples yet. This step ensures the model activates its internal database of medical or financial常识 (common sense).

In the second step, the model combines this general understanding with a few provided examples (few-shot demonstrations) to derive specific decision rules. For instance, instead of vaguely suggesting that age matters, the LLM might generate a precise rule: "If Age $> 50$ AND Cholesterol Level $> 240$, then risk is High." The framework explicitly instructs the LLM to generate a fixed number of these rules per class (typically 10), ensuring a manageable output size while capturing diverse aspects of the problem space.

## Turning Natural Language into Executable Code

Generating rules in natural language is only half the battle; computers cannot execute sentences like "cholesterol is high" directly. The true technical brilliance of FeatLLM lies in its automated parsing mechanism that converts these linguistic rules into functional program code.

One might assume this requires writing rigid regular expressions to parse the LLM's output. However, natural language is notoriously variable; an LLM might say "greater than," "exceeds," or use the symbol "$>$" interchangeably. To handle this noise robustly, FeatLLM employs a clever recursive strategy: it asks another instance of the LLM to write the code itself.

The system feeds the generated natural language rules back into the LLM with instructions to create a Python function that evaluates these conditions against raw data inputs. Because modern LLMs are trained on vast corpora of code, they excel at translating semantic intent into syntactically correct programming logic. The resulting code is executed using Python's `exec()` function on the dataset. This process transforms every abstract rule into a concrete binary feature—a column of 0s and 1s indicating whether each sample satisfies that specific condition.

For example, if the LLM generates five rules for "High Credit Risk,"the original dataset expands by five new columns. A value of `1` in one of these columns means that specific row triggered that logical condition. This transformation distills complex, high-dimensional data into a simplified representation grounded in logical criteria derived from expert-like reasoning.

## Simple Models for Complex Problems

Once the dataset has been enriched with these engineered binary features, the role of the Large Language Model ends completely for that iteration. The transformed data is passed to a simple downstream classifier, such as a linear regression model or logistic regression without bias.

The mathematics here remain straightforward yet effective. Let $\mathbf{z}_k^i$ represent the vector of binary features for sample $i$ corresponding to class $k$. The model learns a set of non-negative weights $\mathbf{w}_k$ that signify the importance of each rule. The likelihood of belonging to class $k$ is computed as:

$$ \text{logit}_k^i = \max(\mathbf{w}_k，0) \cdot \mathbf{z}_k^i $$

These logits are then passed through a softmax function to produce final class probabilities:

$$ \mathbf{p}^i = \text{Softmax}([\text{logit}_{1}^i，..., \text{logit}_{c}^i]) $$

By constraining weights to be non-negative，the system ensures that satisfying a rule never decreases the likelihood of its associated class，aligning with intuitive logic where evidence supports rather than contradicts hypotheses。The model optimizes these weights using standard cross-entropy loss on just a few training samples。Because input dimensionality has been reduced from potentially hundreds of raw features（with mixed types）toa focused setof logically-derived binary flags，simple linear models can generalize exceptionally well even in extreme few-shot regimes。

# The Power of Priors: Why Your Spreadsheet Needs Common Sense More Than Big Data

In the world of machine learning, data is often king. We are taught that bigger datasets lead to better models, and that with enough examples, an algorithm can learn anything. But what happens when you don't have thousands of labeled rows? What if you are working in healthcare, where patient records are private and scarce, or in finance, where labeling a single transaction requires hours of expert review? In these "few-shot" scenarios, traditional algorithms often struggle, latching onto random noise rather than genuine patterns.

A new framework called \textsf{FeatLLM} proposes a radical shift in how we handle tabular data under these constraints. Instead of forcing a model to learn everything from scratch using limited data, \textsf{FeatLLM} injects common sense directly into the feature engineering process. By leveraging the vast prior knowledge stored in Large Language Models (LLMs), this approach allows spreadsheets to "understand" the context of their columns, filtering out spurious correlations and identifying meaningful rules that standard algorithms miss.

## The Limitation of Pure Data-Driven Learning

Traditional tabular learning methods, such as Random Forests or XGBoost, are powerful but fundamentally blind to semantics. To these models, a column named "age" and a column named "random_id_42" are mathematically identical; they are just vectors of numbers. When training data is abundant, the sheer volume of examples helps the model distinguish signal from noise. However, in few-shot regimes—where we might only have 4 or 8 labeled examples per class—these models are prone to overfitting. They easily memorize coincidental patterns, known as spurious correlations, that do not generalize to new data.

For instance, imagine a tiny dataset predicting heart disease where every patient in the training set happens to live on "Maple Street." A traditional algorithm might incorrectly conclude that living on Maple Street causes heart disease simply because it perfectly predicts the training labels. Without external knowledge to contradict this, the model fails miserably on new data from "Oak Avenue."

## Injecting Common Sense via Feature Engineering

\textsf{FeatLLM} addresses this vulnerability by changing the role of the LLM. Rather than using an LLM to predict the final outcome for every single row—a computationally expensive process that hits token limits on large tables—\textsf{FeatLLM} uses the LLM as an expert feature engineer. The system asks the LLM to act as a domain expert who understands the relationships between features and targets based on general world knowledge.

The process begins by presenting the LLM with feature names, definitions, and a handful of examples. The framework guides the model through a structured reasoning path. First, it asks the LLM to infer causal relationships based purely on prior knowledge, ignoring the specific training examples initially. For a medical task, the LLM knows inherently that advanced age correlates with higher disease risk, regardless of what the tiny training set says. Second, it combines this prior knowledge with the few available examples to derive explicit rules.

These rules are not vague suggestions; they are precise logical conditions generated in natural language, such as "If age is greater than 65 AND cholesterol is above 240." The system then parses these rules into executable code to transform the original dataset into a new set of binary features. Each new feature represents whether a specific row satisfies a specific rule derived from common sense and data patterns.

## Filtering Noise and Spurious Correlations

The true power of this approach lies in its ability to ignore irrelevant data. Because the LLM grounds its rule generation in semantic understanding, it naturally filters out columns that make no logical sense for the task at hand. In experiments involving spurious correlations, researchers tested \textsf{FeatLLM} by attaching irrelevant columns from unrelated datasets to a heart disease prediction task. While baseline models saw their performance degrade significantly as more noise was added, \textsf{FeatLLM} remained robust.

This resilience occurs because the LLM refuses to generate rules based on nonsensical connections. When prompted to find criteria for heart failure, an LLM will not prioritize a random ID number or an unrelated demographic statistic if it contradicts medical logic. The resulting binary features are therefore highly informative by design. Experiments showed that even before any statistical tuning, the majority of generated rules had an Area Under the Receiver Operating Characteristic (AUROC) score greater than 0.5 against the target labels, confirming their intrinsic relevance.

Furthermore, \textsf{FeatLLM} employs a simple downstream linear model to weigh these generated features. This step acts as a secondary filter; rules that happen to be slightly off-base receive near-zero weights during training on the few-shot data, while logically sound rules are amplified. This combination of semantic filtering by the LLM and statistical weighting by the linear model creates a defense mechanism against overfitting that pure data-driven methods lack.

## Efficiency and Real-World Applicability

Beyond accuracy, \textsf{FeatLLM} solves critical infrastructure problems associated with using LLMs for tabular data. Many existing approaches require sending every single test sample through an LLM API for inference. This is slow, expensive, and often impossible when tables contain hundreds of columns that exceed the model's context window limit.
