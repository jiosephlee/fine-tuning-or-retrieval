\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Is FeatLLM truly 'training-free' if it optimizes weights $\mathbf{w}_k$ via gradient descent?
Question:
The paper emphasizes that FeatLLM requires no model training and only needs API access. However, Section 3.2 describes optimizing trainable weights $\mathbf{w}_k$ using Adam optimizer and cross-entropy loss over 200 epochs.

While it's true we aren't fine-tuning the massive LLM backbone, we are still training a downstream linear model on the few-shot data. In strict few-shot definitions (like standard Prompt Engineering), usually no gradient updates occur at all. Does calling this 'training-free' mislead readers about the computational cost during the adaptation phase, or is there a convention where training a tiny probe layer is considered distinct from 'model training'?
Answer:
The term "training-free" in the context of FeatLLM refers specifically to the Large Language Model (LLM) backbone, distinguishing it from methods that require parameter-efficient fine-tuning (like LoRA or IA3) or full model retraining. As stated in the Introduction and Related Work sections, a primary motivation for FeatLLM is to overcome the infeasibility of applying LLM-based approaches to models that only offer inference APIs without accessible training codebases. When the authors claim the framework is "free from training constraints," they mean that the massive, pre-trained LLM remains frozen; its weights are never updated via gradient descent. The optimization process you identified in Section 3.2 applies exclusively to a simple, lightweight downstream linear model with weights $\mathbf{w}_k$, which learns the importance of the binary features generated by the LLM.

This distinction is crucial because the computational cost and accessibility profile of training a small linear probe on few-shot data differ fundamentally from training or fine-tuning a billion-parameter transformer. The paper highlights in the "Training & inference time comparison" section that FeatLLM requires only a fixed number of API queries (e.g., 30 for ensemble trials) regardless of the dataset size, whereas other methods might require extensive GPU resources for backpropagation through the LLM itself. The optimization of $\mathbf{w}_k$ using Adam over 200 epochs is a standard procedure for fitting a conventional machine learning head (similar to logistic regression) and imposes a negligible computational burden compared to LLM fine-tuning. Furthermore, the ablation study in Section 4.2 explicitly analyzes the contribution of this "-Tuning" step, showing that while summing binary features works, learning the weights $\mathbf{w}_k$ significantly improves performance as the number of shots increases by accurately estimating rule importance. Therefore, describing FeatLLM as "training-free" is consistent with the convention in literature where "training" implies updating the foundation model's parameters, while fitting a downstream classifier on extracted features is considered part of the standard inference or adaptation pipeline rather than model training.
