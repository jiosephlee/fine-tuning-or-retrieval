\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What exactly is the difference between 'mn-major' and 'k-major' layouts in the context of FP8 WGMMA?
Question:
In Section 2.2 under 'Low-precision number formats', the authors state that for FP8 WGMMA, only the 'k-major' format is supported, whereas FP16 accepts both. They define k-major as being contiguous in the inner $K$-dimension. 

In the standard attention equation $\mathbf{S} = \mathbf{Q}\mathbf{K}^\top$, if $\mathbf{Q}$ is $N \times d$ and $\mathbf{K}$ is $N \times d$, how does this layout constraint specifically affect the second GEMM ($\mathbf{P}\mathbf{V}$)? Does this mean the Value matrix $\mathbf{V}$ must be stored transposed in global memory beforehand, or is the transpose happening entirely within shared memory using the LDSM/STSM instructions mentioned later?
Answer:
The distinction between 'mn-major' and 'k-major' layouts lies in which dimension of the matrix is contiguous in memory, a constraint that becomes critical when utilizing FP8 Tensor Cores on Hopper GPUs. In the context of a General Matrix Multiply (GEMM) computing $C = A \times B^\top$, where $A$ is $M \times K$ and $B$ is $N \times K$, an operand is defined as **mn-major** if it is contiguous along the outer dimension ($M$ for $A$, $N$ for $B$), whereas it is **k-major** if it is contiguous along the inner contraction dimension ($K$). While the WGMMA instruction supports both layouts for FP16 operands stored in shared memory, the FP8 implementation strictly requires operands to be in the **k-major** format.

This constraint directly impacts the second GEMM of the attention mechanism, $\mathbf{O} = \mathbf{P}\mathbf{V}$, because the Value matrix $\mathbf{V}$ (of size $N \times d$) typically arrives in global memory with the head dimension $d$ (the $K$-dimension in this GEMM) as the contiguous stride. To satisfy the k-major requirement for FP8 WGMMA, $\mathbf{V}$ must effectively be contiguous along the sequence length dimension $N$ when loaded into shared memory. According to Section 2.2 and Section 3.3 of the paper, FlashAttention-3 does not require you to pre-transpose $\mathbf{V}$ in global memory via a separate kernel or fused preprocessing step, as those approaches are deemed too wasteful or difficult to integrate. Instead, the transpose occurs entirely within the kernel using specific hardware instructions.

The authors implement an **in-kernel transpose** where tiles of $\mathbf{V}$ are loaded from global memory into shared memory in their original layout, and then immediately transposed within shared memory (or during the move to registers) using `ldmatrix` (LDSM) and `stmatrix` (STSM) instructions. These instructions allow a warp of threads to collectively load and store data at a granularity of 128 bytes and possess a native capability to transpose layouts during the copy operation. By executing this transpose in the "producer" warpgroup, often overlapping it with the computation of previous blocks, the system ensures that the $\mathbf{V}$ tile presented to the FP8 WGMMA unit in the "consumer" warpgroup satisfies the strict k-major contiguity requirement without stalling the pipeline or requiring costly global memory reorganization. Additionally, slight register permutations are applied to align the accumulator layout from the first GEMM with the transposed operand layout of the second, ensuring mathematical correctness despite these physical data rearrangements.
