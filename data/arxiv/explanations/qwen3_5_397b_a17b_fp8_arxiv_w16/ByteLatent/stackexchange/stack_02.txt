\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### Why doesn't Byte-Pair Encoding (BPE) satisfy the 'incremental patching' property?
Question:
Section 2.4 states that BPE is not an incremental patching scheme because $f_p(\pmb{x}_{<i}) \neq f_p(\pmb{x})_{<i}$. I understand the definition formally, but I'm struggling to visualize why this happens in practice.

Does this imply that if I have the prefix 'un' and then add 'happy', the tokenization of 'un' might change depending on whether 'happy' follows? If so, how does this specifically break autoregressive generation in BLT compared to standard LLMs? Why can't we just cache the token IDs as we generate them?
Answer:
The reason Byte-Pair Encoding (BPE) fails to satisfy the "incremental patching" property lies in its fundamental reliance on global context to resolve ambiguities during the merging process, which directly conflicts with the causal nature of autoregressive generation required by BLT.

Formally, incremental patching requires that the segmentation of a prefix $\pmb{x}_{<i}$ remains identical regardless of whether future bytes $\pmb{x}_{\geq i}$ exist. In mathematical terms, a scheme is incremental if $f_p(\pmb{x}_{<i}) = f_p(\pmb{x})_{<i}$. BPE violates this because it constructs tokens by iteratively merging the most frequent adjacent byte pairs based on a static vocabulary built from corpus-wide statistics. This greedy merging process means that the boundary of a token ending at position $i$ can depend entirely on the byte at position $i+1$. A classic example is the prefix "un". If the next character is "h", BPE might merge these into a single token "unh" (as in "unhappy"), whereas if the next character is a space or a consonant like "d", "un" might remain a standalone token or merge differently. Consequently, the tokenization of the prefix changes based on the suffix, meaning $f_p(\text{"un"}) \neq f_p(\text{"unhappy"})_{<\text{"un"}}$.

This non-incremental behavior creates a critical bottleneck for the Byte Latent Transformer (BLT) architecture described in the paper. BLT relies on dynamically deciding whether to invoke its computationally expensive global Latent Transformer based on whether the current byte sequence constitutes a complete patch. In an autoregressive setting, the model generates bytes sequentially and must determine patch boundaries on-the-fly without access to future tokens. If the system used BPE as its patching mechanism, it would face a causality paradox: to know if the current sequence of bytes forms a complete patch (and thus when to run the global transformer), it would need to peek at future bytes to see if they merge with the current ones. Without this lookahead, the model cannot definitively say if a patch has ended, preventing it from correctly scheduling the compute-intensive global steps.

You asked why we cannot simply cache token IDs as we generate them. The issue is that caching assumes the ID for a sequence is finalized once generated. With BPE, the ID for the sequence generated so far is provisional; appending a new byte might invalidate the previous token boundary and require re-tokenizing the entire recent history into a different set of IDs. For instance, if you cached an ID for "un" and then generated "h", you would realize "un" was not actually a valid final token in this context, but rather part of "unh". This forces a rollback and re-computation of representations, breaking the efficient streaming inference pipeline that BLT aims to achieve. In contrast, BLT's proposed entropy-based patching determines boundaries using only past and current information (specifically, spikes in next-byte entropy), ensuring that once a patch boundary is crossed, it never needs to be revisited, thereby satisfying the condition $f_p(\pmb{x}_{<i}) = f_p(\pmb{x})_{<i}$ and enabling stable, causal autoregressive generation.
