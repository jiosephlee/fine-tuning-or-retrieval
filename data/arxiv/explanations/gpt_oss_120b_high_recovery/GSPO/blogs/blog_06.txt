# Building Simpler RL Pipelines – Using Inference Engines Directly with GSPO  

*Discover how GSPO’s reliance on sequence‑level likelihoods lets you reuse cached probabilities from inference servers (e.g., vLLM or SGLang), cutting down on recomputation overhead and simplifying distributed RL infrastructure.*

---

## 1️⃣ Why Reinforcement Learning for LLMs Usually Needs Two Passes  

When we fine‑tune a massive language model with reinforcement learning (RL), a typical algorithm such as PPO or its token‑based variant GRPO works like this:

1. **Rollout phase** – an **inference** engine generates a handful of responses \(y\) for each query \(x\).  
2. **Learning phase** – the **training** engine recomputes the *old* policy’s token‑level probabilities \(\pi_{\theta_{\text{old}}}(y_t\mid x,y_{<t})\) so it can form importance weights  

   \[
   w_{i,t}(\theta)=\frac{\pi_{\theta}(y_{i,t}\mid x,y_{i,<t})}{\pi_{\theta_{\text{old}}}(y_{i,t}\mid x,y_{i,<t})}
   \]

   and feed them into the clipped objective.

That second pass is expensive for three reasons:

* **Memory pressure** – storing all token‑wise logits from the rollout consumes gigabytes of RAM for long sequences.
* **Precision mismatch** – inference engines often run in mixed‑precision (FP16/BF16) while training uses a stricter format, leading to tiny numerical gaps that explode when applied token‑by‑token.
* **Engineering friction** – distributed setups must shuttle logits between an inference cluster (vLLM, SGLang…) and a training cluster (Megatron), adding latency and code complexity.

All this extra work stems from a *token‑level* importance correction that does not match how we actually score a response—our reward \(r(x,y)\) is assigned **once per sequence**, not per token.

---

## 2️⃣ The Sequence‑Level Insight Behind GSPO  

GSPO flips the script by moving the importance weight from tokens to entire sequences:

\[
s_i(\theta)=\Bigl(\frac{\pi_{\theta}(y_i\mid x)}{\pi_{\theta_{\text{old}}}(y_i\mid x)}\Bigr)^{1/|y_i|}
=\exp\!\Bigl(\frac{1}{|y_i|}
\sum_{t=1}^{|y_i|}
\log\frac{\pi_{\theta}(y_{i,t}\mid x,y_{i,<t})}
     {\pi_{\theta_{\text{old}}}(y_{i,t}\mid x,y_{i,<t})}\Bigr)
\]

Key properties:

* **Alignment with reward** – Both \(s_i(\theta)\) and the advantage \(\widehat{A}_i\) are defined at the *response* granularity.
* **Length normalization** – Raising the likelihood ratio to \(1/|y_i|\) bounds \(s_i(\theta)\) in a narrow numeric range regardless of response length, which dramatically dampens variance.
* **Tolerance to tiny precision errors** – Because we aggregate logs before exponentiation, small per‑token discrepancies average out instead of being amplified token‑by‑token.

Consequently, once we have a *single* scalar \(\log \pi_{\theta}(y_i \mid x)\) per response we can compute \(s_i(\theta)\). No need to keep every token’s probability around us.

---

## 3️⃣ How GSPO Lets You Use Inference Probabilities Directly  

### The traditional pipeline (two passes)

```
inference → generate y + logits_old
store y
training → recompute logits_old + logits_new → compute w_t → gradient
```

### The GSPO pipeline (single pass)

```
inference → generate y + logprob_old    ← cached
store (x, y, logprob_old)
training →
    1️⃣ feed y through current model θ → get logprob_new   (just one forward)
    2️⃣ compute s_i(θ)=exp[(logprob_new - logprob_old)/|y|]
    3️⃣ apply group advantage Ā_i and clipping → gradient
```

Because we only need:

* `logprob_old` – already returned by the inference service during rollout,
* `logprob_new` – a **single** forward call through the *current* model,

the extra “replay” forward pass disappears entirely.  

If your inference cluster already runs in mixed precision, that’s fine: a single averaged log‑probability is robust to those rounding differences. You can even keep `logprob_old` as a plain float32 number without worrying about per‑token truncation errors.

---

## 4️⃣ Practical Changes You’ll See in Your RL Infrastructure  

| Aspect | Before (GRPO/PPO) | After (GSPO) |
|--------|-------------------|--------------|
| **Data saved per rollout** | Token‑wise logits (`T × vocab`) | One scalar `log π(y|x)` per response |
| **Network traffic** | Large tensors moved between services | Tiny metadata packets |
| **GPU memory during learning** | Additional buffers for old logits | Only standard activations |
| **Precision handling** | Must re‑compute logits in training precision | Safe reuse of inference‐precision logits |
| **MoE routing tricks** | Needs “Routing Replay” to stabilize `w_t` | No routing replay needed—sequence likelihood stays stable |

The result is a dramatically slimmer end‑to‑end graph:

```
[Inference Service] ──► {x, y, logπ_old}
        │
        ▼
[Training Worker] ──► forward(y) under θ → logπ_new
        │                ──► compute s(θ)
        ▼                ──► apply clipped objective → update θ
```

You can now treat your rollout cache as an immutable “experience replay” buffer that any trainer can read without pulling heavy tensors or orchestrating synchronised routing states across GPUs.

## 5️⃣ Real World Evidence From Qwen3 Experiments  

The authors of GSPO evaluated a cold‑start Qwen3‑30B model fine‑tuned on millions of queries. Highlights relevant to pipeline simplification:

* **Training stability:** Even when splitting each rollout batch into four mini‑batches (a common source of off‑policy drift), GSPO never exhibited catastrophic collapse—something that routinely happened with GRPO when token‐level importance ratios were mis­estimated.
* **No Routing Replay:** For Mixture‑of‑Experts models, GRPO required caching expert activations (“Routing Replay”) to avoid volatility; GSPO worked out‐of‑the box because it never looks at per‑token routing decisions.
* **Efficiency gains:** Under identical compute budgets, GSPO reached higher reward curves on AIME‘24, LiveCodeBench, and CodeForces benchmarks—demonstrating that trimming away redundant passes does not sacrifice performance.

Although the paper does not publish raw timing numbers for each pass, the qualitative claim is clear: by eliminating the second “likelihood recompute” step you free up GPU cycles that are otherwise spent shuffling large tensors between clusters. That translates directly into faster iteration cycles when you spin up thousands of GPU nodes in production.

## 6️⃣ Bottom Line – What You Should Do Next  

1️⃣ **Collect sequence‐level log probabilities during rollout**  
   Most modern inference servers already expose `logits` or `logprob` APIs; ask them for `log π(y|x)` rather than per‐token scores if you want fewer bytes transferred.

2️⃣ **Store them together with your query–response pair**  
   A simple JSON line (`{"query":…, "response":…, "logp_old":…}`) is enough—no binary blobs needed.

3️⃣ **During each training step**  
   * Load a minibatch of stored pairs,
   * Run them through your current policy `θ` once,
   * Compute `s_i(θ)` using `(logp_new - logp_old)/|y|`,
   * Apply the clipped objective  

     \[
     \mathcal{J}_{\text{GSPO}} = 
     \mathbb{E}\Bigl[\min(s_i\,\widehat A_i,\;\mathrm{clip}(s_i,\!1-\varepsilon,\!1+\varepsilon)\widehat A_i )\Bigr]
     \]

4️⃣ **Enjoy cleaner code**  
   No custom “routing replay” hooks, no double forwards on the same batch, no special handling for mixed‐precision mismatches—just plain PyTorch / JAX code that mirrors standard supervised fine‐tuning plus a scalar weighting term.

By aligning the unit of optimization (the entire response) with the unit of reward—and by normalizing importance ratios across sequence length—GSPO lets you treat an inference engine as an ordinary data source rather than a heavyweight prerequisite for RL training. This dramatically reduces engineering overhead while preserving—and even improving—the final model quality.

---  

### TL;DR  

GSPO replaces tokenwise importance weights with a *sequence‐level* ratio \(s_i(\theta)\). That single scalar fully captures how far the new policy deviates from the old one over an entire answer, making it robust against tiny precision differences between inference and training engines. As a result you can reuse cached probabilities straight from vLLM/SGLang without any extra recomputation pass, shrinking memory footprints, cutting network traffic, eliminating MoE routing tricks, and simplifying your distributed RL pipeline—all while keeping—or boosting—the model’s performance on challenging benchmarks. Happy scaling!
