\title{Blogs about the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

# Double Quantization & Paged Optimizers: Cutting Memory Spikes in Half  

Large language models (LLMs) have shown remarkable abilities once they are fine‑tuned on instruction data, but the process remains notoriously resource‑hungry. A full‑precision (16‑bit) fine‑tuning run on a LLaMA‑65B model needs more than **780 GB** of GPU RAM—far beyond what any single consumer or even most professional GPUs can offer.  

Enter **QLoRA**, an efficient fine‑tuning recipe that squeezes a 65 billion‑parameter model onto a single **48 GB** GPU while preserving the same performance you would get with full‑precision training. The headline tricks—quantizing the base model to **4 bits** and using low‑rank LoRA adapters—are obvious once you read the paper. Yet there are two less visible ingredients that make this magic possible:

* **Double Quantization** – a clever way of compressing the *quantization constants* themselves.
* **Paged Optimizers** – an automatic paging scheme that prevents out‑of‑memory crashes during gradient checkpointing.

Below we unpack why these “hidden heroes” matter, how they work, and what concrete savings they bring to the table.



## The Cost Behind Block‑wise Quantization  

Quantizing a weight matrix $\mathbf{W}\in\mathbb{R}^{h\times o}$ from floating point down to a low‑bit representation is done **block‑wise**: each block of size $B$ gets its own scale factor $c$ (often called a *quantization constant*). The forward pass dequantizes each entry as  

\[
\text{dequant}(c,\mathbf{W}^{k\text{-bit}})=\frac{\mathbf{W}^{k\text{-bit}}}{c}\,,
\]

where $\mathbf{W}^{k\text{-bit}}$ holds the compressed values (e.g., NF4) and $c$ rescales them back into BFloat16 precision before matrix multiplication.  

Storing one constant per block sounds cheap, but when you multiply it by billions of parameters it adds up quickly:

* With a **blocksize $B=64$**, each constant takes **32 bits** (FP32).  
* This translates into an extra $\frac{32}{64}=0.5$ bits per weight—about **3 GB** extra storage for a 65 B model.

If you ignore this overhead you quickly run out of room even after shrinking $\mathbf{W}$ itself to four bits.



## Double Quantization: “Quantize the Quantizer”  

### What it Does  

**Double Quantization (DQ)** treats those FP32 scales $c^{\mathrm{FP32}}_2$ as ordinary tensors and compresses them a second time:

1. **First level** – weights $\mathbf{W}$ become NF4 (a normal‑distribution‑aware 4‑bit format) using a per‑block scale $c^{\mathrm{FP32}}_2$.  
2. **Second level** – each $c^{\mathrm{FP32}}_2$ is quantized again into **8‑bit floating point (FP8)** values $c^{\mathrm{FP8}}_1$. Because all scales are positive we subtract their mean first so they become symmetric around zero before FP8 quantization—a step that improves utilization of the limited FP8 range.

During inference or training we “double dequantize”:

\[
\text{doubleDequant}(c^{\mathrm{FP32}}_1,c^{\mathrm{FP8}}_1,\mathbf{W}^{\mathrm{NF4}})
=
\text{dequant}\big(\,
\text{dequant}(c^{\mathrm{FP32}}_1,c^{\mathrm{FP8}}_1),\, 
\mathbf{W}^{\mathrm{NF4}}
\,\big)
= \mathbf{W}^{\mathrm{BF16}}\!,
\]

so no extra computation is required beyond two cheap dequantizations.



### How Much Space Do We Save?  

Using an **FP8 second‑level format** with its own blocksize $B_{2}=256$ reduces the average constant overhead dramatically:

* First level alone → $0.5$ bits/parameter.
* After DQ → $\displaystyle \frac{8}{64}\;+\;\frac{32}{64\times256}\approx0.127$ bits/parameter.

The net saving per weight is therefore  

\[
0.5 - 0.127 = 0.373 \text{ bits per parameter}.
\]

For a model with $N=65\times10^9$ parameters this works out to roughly  

\[
0.373 \times N \approx 24\times10^9 \text{ bits } \approx
3~\text{GB},
\]

exactly what the authors reported as an average reduction in footprint. Crucially, this compression **does not hurt accuracy**—empirical results show identical perplexities and benchmark scores compared with an uncompressed constant layout.



## Paged Optimizers: Turning Out‑of‑Memory into Page‑Faults  

### Why Gradient Checkpointing Still Spikes  

Even when the base model fits comfortably inside GPU RAM thanks to NF4 + DQ, fine‑tuning still needs space for **optimizer state tensors** (e.g., Adam’s moment estimates) and temporary activation gradients created by gradient checkpointing. When processing long sequences or larger batches these buffers can briefly exceed available VRAM, causing an abrupt OOM error despite overall static memory usage being well within limits.



### Paging via NVIDIA Unified Memory  

**Paged Optimizers** sidestep this problem by allocating optimizer states with CUDA’s unified memory (`cudaMallocManaged`). This feature automatically pages data between GPU VRAM and host RAM:

* When VRAM pressure rises, unused chunks of the optimizer state are migrated (“evicted”) to CPU RAM without any explicit programmer intervention.
* Before an optimizer update step runs, those pages are pulled back (“paged in”) so that arithmetic proceeds normally.
* The transfer happens transparently under the hood; the training loop does not need checkpoint logic beyond what already exists for activations.



### Practical Impact  

The authors measured virtually **no slowdown** at a batch size of 16 on a 48 GB GPU—the same throughput one gets with conventional optimizers that stay entirely on device. Only extreme sequence lengths could introduce minor latency due to page faults, but even then training remains feasible where it would otherwise abort instantly.

Thus Pag​ed Optimizers provide two wins:

1. **Robustness** – you can safely run gradient checkpointing on massive models without fearing sudden OOM crashes.
2. **Simplicity** – no custom sharding or manual swapping logic is needed; CUDA’s driver handles everything.



## How These Tricks Fit Into QLoRA’s Whole Pipeline  

QLoRA combines three orthogonal ideas:

| Component | What It Stores | Memory Footprint |
|-----------|----------------|------------------|
| **NF4 weight storage** | Base model weights ($4\,{\rm bits}$ each) | ~$\tfrac14$ of FP16 |
| **Double Quantization** | Per‑block scaling constants ($<0.13\,{\rm bits}$ per weight) | Saves ~3 GB for 65 B |
| **Paged Optimizers** | Adam moments & LoRA gradients | Dynamically stays within VRAM |

All three operate simultaneously:

1️⃣ The base model lives as NF4 tensors on disk/GPU RAM—a static reduction from hundreds of gigabytes down to under ten gigabytes for LLaMA‐65B.  
2️⃣ Double Quant saves exactly those extra gigabytes hidden inside scaling factors—something easy to overlook because they’re just “metadata”.  
3️⃣ During training, Pa​ged Optimizers guarantee that moment tensors never cause an unexpected spike, letting us keep everything else fixed while only updating tiny LoRA adapters (typically < 1% of total parameters).

Together they make it possible to fine‑tune LLaMA‐65B on a single **48 GB RTX A6000**, achieving almost identical performance compared with full‐precision fine‑tuning—and doing it in roughly half a day instead of weeks.



## Takeaways  

* **Double Quantization** isn’t just an academic curiosity; it shaves gigabytes off every large model you touch by compressing something most people forget exists—the scale factors.
* **Paged Optimizers** turn “out‑of‑memory” from an abrupt failure mode into a benign paging event handled by NVIDIA’s driver.
* When paired with NF4 weights and LoRA adapters, these two techniques close the gap between research labs equipped with eight–GPU clusters and individual developers wielding one consumer GPU.
* The authors have open‑sourced everything—including custom CUDA kernels—so you can drop these tricks into your own PyTorch pipeline via the 🤗 Transformers integration (`bitsandbytes` backend).

If you’re curious about reproducing these results or trying your own instruction set on a modest workstation, start at the official repository: <https://github.com/artidoro/qlora>. The codebase already contains Double Quant support (`dq=True`) and Pager‐enabled optimizers (`paged=True`), letting you experiment without writing low‑level CUDA yourself.
