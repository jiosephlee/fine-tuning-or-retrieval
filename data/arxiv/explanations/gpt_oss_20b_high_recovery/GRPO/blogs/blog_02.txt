# Code Is a Secret Weapon For Math  

Mathematical reasoning has long been considered one *hard problem* for language models (LMs). Training an LM simply on web text yields almost perfect fluency in everyday prose,
but its ability to solve algebraic equations or prove geometric lemmas remains modest compared with the leading closed‑source systems
(GPT‑4, Gemini Ultra).  
Removing dependency on external calculator plugins changes nothing; the LM still struggles when asked for a handwritten solution  
that requires rigorous step‑by‑step derivation instead of just a lookup answer.



Below I unpack how **pre‑training on massive programming data turns this weakness into an advantage**, why it works even without calling an interpreter,
and what experimental evidence backs this claim.



--------------------------------------------------------------------
## What Makes Mathematics Harder Than “plain” Language?



| Reason | Typical hurdle | Consequence |
|--------|----------------|--------------|
| Logic flow | Nested conditionals & recursion | Requires keeping track of intermediate equations |
| Exactness | Every digit matters | Small mistakes explode into wrong answers |
| External computation | Includes factorials, double sums … | LMs tend simply *prime* “what would you get?”, rarely evaluate |

Even “self‑contained” solutions (“a human could read my answer and verify it line by line”) demand these three properties,
which are surprisingly uncommon in ordinary text.



--------------------------------------------------------------------
## From Textual Newsfeeds To Mathematical Webpages  

The first building block was assembling a clean corpus that actually *contains* meaningful mathematics.



1. **Seed corpus = OpenWebMath** – a hand curated collection (~13 M examples) whose headlines resemble those used in downstream benchmarks (`GSM8K`, `MATH`).  
2. A **fastText classifier** (θ₁) was trained on half‐positive / half‐negative paragraphs pulled randomly from Common Crawl (≈40 bn webpages).  
3. Re‑ranking all remaining webpages gives scores *p(page ≈ math)*.
4. Select top scorers – initially only ≈40 bn textual blobs survive → ≈40 b tokens captured.
5. Identify domains heavily populated by collected pages (`mathoverflow.org`, `stackexchange.com/math`, …), scrape extra positive examples,
   retrain θ₁ → more diverse → repeat four times.
6. Final corpus : **≈120 b tokens over ≈35 m distinct webpages**, multilingual (English + Chinese dominating).

This pipeline dwarfs prior public stacks (`OpenWebMath` ≈13 b) yet remains pure web data — *no scraped PDFs or @reproducible installations*.

## A Core Finding ‑ Coding Knowledge Ranks Mathematically  

***Pre‑training on four hundred billion bytes of source code before mathematics has two measurable effects***



| Experiment                         | Effect – Plain Text Reasoning | Effect – Tool‑Assisted Reasoning |
|------------------------------------|------------------------------|----------------------------------|
| ✅ Two–stage : 400 B *code* ➜ 150 B *math* | New समाधान ⟶ +6–10 percentage points ↳ beating any Early‐2023 base model           | Visualized program drafts prove easier ↳ Rises ≈10 points        |
| ❌ Two–stage : 400 B *general* ➜ 150 B *math* | No comparable lift ⇢ lack behind notation & control flow                | Same                                      |
| ✅ One–stage : 400 B *mixed* (`code+math`) | Keeps coding skill × keeps most gains – minor drop (<3 pts)   | Sustains high toolbox<|reserved_200930|>             |

> Even when later arithmetic steps demanded a program (“write Python”, “apply SymPy”), the boosts held true,
> because the LM already had practiced reasoning inside loops & functions.



### Why Does This Happen?



1. **Structural Parallelism**  
   Both mathematical proofs and clean programs exhibit repeatable patterns:
   ```python
   def solve():
       x = …
       y = f(x)
       return y                       # ∴ y = …box
   ```
   Seeing hundreds of millions of such snippets helps the network learn what *“next symbol”* means
   after a constraint (`x > y`, `∑αᵢ…`).  
   These syntactic regularities transfer fluently into deriving stepwise explanations (“Since …”) used directly during chain‑of‑thought prompting.



2. **Exact `operator` Semantics**  
   Inline operators (`+`, `−`, `/`, `×`) are encoded with precise precedence rules in almost every coder’s repo.
   While translating raw prose into computations would normally require an interpreter,
   **the LM learns an internal probability distribution over operator precedence just from seeing thousands tiny scripts** —
   imitating an “internal calculator” posted handouts telling you “apply × before +”.



3. **Debugging Feedback Loop**  
   Good programmers repeatedly comment bad outputs (“wrong subtraction”), fix bugs (“factored remainder”), then re‑run,
   effectively exposing counterexamples (**“proof failing tests”**) right inside natural language instruction commentary.

## How It Translates Into Better Benchmarks  

Across several public tests, every place where   
“plain language solution without calling Python” was scored,
models pre‑trained first on source‑code consistently beat counterparts trained only on vague web chatter.


| Benchmarks         | Pretrained (on source code) ↑ (%) | Baseline ↑ (%) |
|--------------------|-----------------------------------|----------------|
| GlobalMATH CT      | **≈51–53 %**                      | <41 %          |
| GlobalGSM8k CT     | ≈92 %                             | ≈86 %          |
| Chinese CMATH CT   | ↑ ≈12 %                           | ↓ <4 %         |

(Values rounded — see detailed tables in *DeepSeekMath* work.)  
Note that this advantage appears **without integrating an external tool**, hence proving it’s an innate upgrade baked into language representations.

## Going Beyond Code – Reinforcement Learning Pushes Further  

After instruction tuning (*CoT*, *PoT*, *tool‐integrated prompts*) was done,
the authors applied their custom agent called ***Group Relative Policy Optimization*** ("GRPO").
Key takeaways:



* GRPO removes the costly critic network used in PPO → fewer parameters trainable simultaneously → light CPU/GPU load   
* By sampling many (≈64) continuations per question, GRPO estimates a *baseline directly from group scores*.  
  This eliminates noisy per‑token value estimations highly unreliable when only last token gets reward—a frequent reality in maths prompts.



Result numerically:



| Stage                | Accuracy GTA GMAT ↩︎ (%) |
|----------------------|---------------------------|
| Instruction Tuning   | ← 54   ← 48              |
| GRPO Reinforcement*’36 epochs ×42 batches │ ≈51–52 specialized ≤59   tiny boost …︎     |

The non‑trivial lift stems mainly from sharpening output ranking (“top‑k got benefit”) rather than fundamentally regaining missed skills –
exactly fitting what nitro planners call *“making top answers appear more often”*, which explains why ⧬ majority scores went up while few‐shot transfer kept flat.
