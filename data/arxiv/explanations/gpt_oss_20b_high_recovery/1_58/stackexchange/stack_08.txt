\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### How is matrix multiplication performed with ternary weights and 8‑bit activations?
Question:
I understand that a matrix multiplication of the form $y=Wx$ can be simplified if $W\in\{-1,0,1\}$. Could someone delineate the exact algorithm (pseudocode) that avoids multiplication? For instance, does the implementation sum all elements of $x$ where $W_{ij}=+1$ and subtract the sum where $W_{ij}=-1$, all using integer addition? What is the computational complexity and memory access pattern compared to the standard \texttt{nn.Linear}?
Answer:
**Short answer**

With ternary weights the dot–product can be written as a sum of selected
activation values plus or minus other selected values.  
No multiplication is performed; the only arithmetic is a 32‑bit
(usually 16‑bit) addition or subtraction per non‑zero weight.  
The implementation therefore keeps two tiny bit‑maps per output
neuron—one bit for *sign* (+1/−1) and one bit for *presence* (0 or
non‑zero).  The kernel loads an 8‑bit activation once and adds it to
the partial sum if the weight bit is 1 or subtracts it if the sign bit
is 1.  A custom GEMM‑style kernel (the 2‑bit kernel from *Ladder* in the
paper) exploits word‑level parallelism to process dozens of those
operations in a single instruction.

---

### 1.  Algorithmic view

Let  

\[
W\in\{-1,0,1\}^{\,O\times I},\qquad x\in\mathbb Z_{8}^{\,I},\qquad 
y=W\,x\in\mathbb Z_{32}^{\,O}.
\]

For each output index \(i\),

\[
y_i=\sum_{j=1}^{I}\;W_{ij}\,x_j
     =\!\!\sum_{j:W_{ij}=+1}\!\! x_j
      \;-\!\!\sum_{j:W_{ij}=-1}\!\! x_j .
\]

Pseudocode that follows the structure used in the BitNet repo
(`BitLinear`) is:

```python
def bitlinear_forward(x, pos, neg, bias=None):
    # x    : [B, I]   8‑bit unsigned/int8
    # pos   : [O, I]  bit mask (1 ⇔ W=+1)
    # neg   : [O, I]  bit mask (1 ⇔ W=-1)
    # bias  : optional [O] int32
    B, I = x.shape
    O = pos.shape[0]
    out = np.zeros((B, O), dtype=np.int32)

    for i in range(O):
        if np.any(pos[i]):                     # fast path: skip if all zero
            out[:, i] += x[:, pos[i]].sum(axis=1)
        if np.any(neg[i]):
            out[:, i] -= x[:, neg[i]].sum(axis=1)

    if bias is not None:
        out += bias
    return out
```

The key point is that the `*` operator never appears;  the code
works with *addition* or *subtraction* only.  
In a real inference kernel the same idea is carried out in
SIMD/SMX form: each lane loads a 32‑bit word that packs 32 weight bits,
uses the corresponding 32 activation values, and performs a
masked‑add/subtract via bit‑wise operations (`_mm256_mask_add_epi32`,
`_mm256_mask_sub_epi32`, etc.).

---

### 2.  Computational complexity and cost

* **Number of arithmetic ops**  
  For a full‑precision GEMM each output entry requires \(I\)
  multiply–add pairs, i.e. \(2I\) floating‑point operations.
  With ternary weights we do at most one 8‑bit add/sub per non‑zero
  weight, so the operation count becomes

  \[
  \text{ops}_{\text{ternary}}
      \;\approx\; I\,\Pr[W\neq 0]
      \;=\; \tfrac{2}{3}I\quad\text{(if the ternary distribution is \{-1,0,1\} uniformly)} .
  \]

  Thus the arithmetic count drops by ~⅓ (no multiplications
  at all, noise from zero entries is avoided).  
  The 1‑bit case (no zeros) would drop it to \(I\) additions/subtractions.

* **Memory traffic**  
  *Weight* size: 2‑bit per weight (1 for *presence*, 1 for *sign*) vs
  16‑bit FP16 in the vanilla model: 8× reduction.  
  *Activation* size: 8‑bit vs 16‑bit FP16: 2× reduction.  
  Outputs are accumulated in 32‑bit, but these are produced once per
  token, so the main memory bandwidth advantage comes from the
  weights and activations.

  The paper reports 3.55‑times less GPU memory footprint for a 3‑B
  BitNet, which matches the theoretical 8×–2× savings once you
  include the small overhead of the bias and intermediate buffers.

* **Throughput and energy**  
  Integer addition/subtraction on modern GPUs is roughly an order of
  magnitude cheaper (in both latency and energy) than FP16
  multiply‑accumulate.  The authors quote a 71.4× arithmetic‑energy
  saving on 7 nm ASICs and a 2.71× runtime speed‑up on a single‑GPU
  inference server for a 3‑B model.  These numbers come from the
  reduced number of add/sub operations and the lower weight bandwidth.

---

### 3.  Memory‑access pattern versus `nn.Linear`

| Stage                     | `nn.Linear` (FP16) | `BitLinear` (ternary + 8‑bit) |
|---------------------------|--------------------|------------------------------|
| Weights                   | contiguous FP16 matrix | 2‑bit bitmap (`pos`,`neg`)   |
| Activations (input)       | FP16 contiguous vector | 8‑bit contiguous vector      |
| Read pattern              | weight & activation streamed in GEMM tiles | weight bits & activation bits streamed in 2‑bit words |
| Compute kernel            | GEMM (SIMD _vmulps) | custom bit‑kernel with masked add/sub |
| Cache behaviour           | Standard BLAS cache hints | More cache‑friendly due to tiny weight size |
| Bandwidth requirement     | ~2 bytes / weight + 2 bytes / input | ~0.25 bytes / weight + 1 byte / input |

Because the weight matrix is only 2 bits per element, the cache line
contains many more entries, which reduces the number of misses and
makes the kernel more memory‑bound than compute‑bound.  The
integer‑only operations, however, are so cheap that the overall
performance becomes dominated by memory bandwidth, and the net
throughput improves dramatically.

---

### 4.  Take‑away

* With ternary weights every non‑zero entry turns the 8‑bit *element‑wise
  multiplication* into a simple *add or subtract* of the activation.
* The implementation keeps two tiny bit‑maps and sums selected
  activations using vectorised masked adds/subtracts.
* The arithmetic operation count shrinks by roughly one third and
  the multiplication cost disappears; only integer addition is
  required.
* Weights and activations are packed 8‑ and 2‑times smaller than in a
  vanilla `nn.Linear`, so memory bandwidth and energy consumption
  drop correspondingly.
* Empirical results (BitNet b1.58) confirm ~2.7× faster inference and
  >3× lower GPU memory for a 3‑B model, with the same perplexity as a
  full‑precision baseline.

Thus the “no‑multiplication” claim is exact: a ternary‑weight dot
product is a signed sum of selected 8‑bit activations, and the papers’
`BitLinear` implementation implies that this sum is performed in a
high‑throughput, low‑energy, bit‑packed fashion that outperforms the
standard `nn.Linear` for large‑scale language models.
