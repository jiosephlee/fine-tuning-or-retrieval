\title{Stack Exchange of the Paper: fa3}

### What do SS-GEMM and RS-GEMM mean in FlashAttention-3, and how do they map to WGMMA sources?
Question:
In Algorithm 1 of the FlashAttention-3 paper (the forward pass without intra-consumer overlap), the authors label two GEMMs as "SS-GEMM" for computing $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^\top$ and "RS-GEMM" for updating $\mathbf{O}_i$. I assume "S" means the operand is sourced from shared memory and "R" means from registers, but I'm not entirely sure which operand is where in each call. Can someone clarify the exact meanings of SS-GEMM vs. RS-GEMM in the context of Hopper's WGMMA (e.g., which operand is in SMEM vs RMEM in each case), and how these map to the asynchronous WGMMA calls used by the paper?
Answer:
Short answer: SS-GEMM means both GEMM operands are read from shared memory (SMEM); RS-GEMM means the first operand lives in registers (RMEM) while the second is read from shared memory. In the paper’s Algorithm 1 this matches the concrete data flow: the score GEMM
$S_i^{(j)} = Q_i K_j^\top$ is SS-GEMM because both $\mathbf{Q}_i$ and $\mathbf{K}_j$ are staged into SMEM by the producer; the output-accumulation GEMM that updates $\mathbf{O}_i$ is RS-GEMM because the probability tile $\widetilde{\mathbf{P}}_i^{(j)}$ is held in registers while the $\mathbf{V}_j$ tile is in SMEM.

Why this naming and location make sense
- In the producer/consumer scheme the producer TMA loads tiles of $\mathbf{Q}$, $\mathbf{K}$, $\mathbf{V}$ into the circular SMEM buffer. The consumer warps then run WGMMA-based GEMMs that can directly read those tiles from SMEM. When you compute the raw scores $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^\top$ both inputs are exactly the SMEM tiles just loaded, so both operands are SMEM-sourced (hence “SS-GEMM”, shared-shared).
- After computing $\mathbf{S}_i^{(j)}$ the consumer performs softmax-ish work on that score tile and forms a scaled/biased probability tile $\widetilde{\mathbf{P}}_i^{(j)}$. That $\widetilde{\mathbf{P}}$ tile is kept on-chip in registers (RMEM) to avoid spilling to GMEM/SMEM, and then it is multiplied with $\mathbf{V}_j$ (which still sits in SMEM). The first operand of that GEMM therefore lives in registers while the second is in shared memory (hence “RS-GEMM”, register-shared).

How these map to WGMMA (asynchronous) usage in the paper
- The paper uses WGMMA as a shorthand for issuing asynchronous Tensor‑Core block GEMMs. For SS-GEMM you issue a WGMMA that sources both operand tiles from SMEM and accumulates into on‑thread registers (the FP32 accumulator delivered by WGMMA). The call is issued (commit) and then the consumer can wait for its completion when the subsequent softmax needs $\mathbf{S}$. In the 2‑stage pipelining they often issue that WGMMA and do not block immediately (commit but do not wait) so the tensor core can run asynchronously while other scalar work is scheduled.
- For RS-GEMM you issue WGMMA where the A (or “first”) operand resides in RMEM (the probability tile held in registers) and the B operand resides in SMEM (the $\mathbf{V}$ tile). WGMMA supports reading operands from SMEM and using register-held accumulators; in the implementation the probability tile is already arranged in the register layout expected by WGMMA (or permuted into it), so the call consumes that RMEM operand and the SMEM $\mathbf{V}$ tile and produces/register-accumulates the partial $\mathbf{O}_i$ result. Again this WGMMA is issued asynchronously (commit but not wait) to overlap with softmax work of the next iteration.

FP8 / layout caveat (how it affects SS vs RS)
- The paper stresses FP8/WGMMA layout constraints: FP8 WGMMA requires operands to be k-major in SMEM. That affects how you must load/transposition the SMEM tiles for both the SS-GEMM and the RS-GEMM second operand (the $\mathbf{V}$ tile). For SS-GEMM both Q and K tiles must be placed in conformant SMEM layout for the FP8 WGMMA; for RS-GEMM the register-held $\widetilde{\mathbf{P}}$ layout must be permuted to match how the WGMMA expects its accumulator/operand mapping and the SMEM $\mathbf{V}$ tile must be in the k-major layout. The paper describes doing an in‑kernel transpose (LDSM/STSM) and register byte‑permutes so the register operand and SMEM operand formats line up for chained asynchronous WGMMA calls.

Practical mapping to the paper’s pseudocode
- In Alg. 1 (no intra-consumer overlap) lines labeled “SS-GEMM” (computing $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^\top$) correspond to an asynchronous WGMMA that reads both Q and K from SMEM. The code “Commit and wait” means issue the WGMMA and then wait if the next steps need $\mathbf{S}$.
- The lines labeled “RS-GEMM” (updating $\mathbf{O}_i$ with $\widetilde{\mathbf{P}}_i^{(j)} \mathbf{V}_j$) correspond to a WGMMA that consumes $\widetilde{\mathbf{P}}$ from registers and $\mathbf{V}_j$ from SMEM. Because $\widetilde{\mathbf{P}}$ is produced on‑chip by the scalar softmax steps it is kept in RMEM and passed directly to WGMMA without rereading SMEM.

In short: SS-GEMM = both operands in SMEM (Q and K tiles); RS-GEMM = first operand in registers (probability tile), second operand in SMEM (V tile). The asynchronous WGMMA calls in the paper are simply the kernel-level implementation of those two cases, with commit/wait used to overlap the WGMMA (tensor‑core) execution with TMA loads and softmax work and with extra register/SMEM transposes when targeting FP8 to satisfy WGMMA layout requirements.

### How does the local softmax with running $m_i$ and $\ell_i$ yield the exact global softmax result?
Question:
The paper uses the standard FlashAttention trick of maintaining a running max $m_i$ and a running normalizer $\ell_i$ per row while streaming over blocks of keys. At each step it computes $\widetilde{\mathbf{P}}_i^{(j)} = \exp(\mathbf{S}_i^{(j)} - m_i)$, updates $\ell_i = e^{m_i^{\mathrm{old}} - m_i}\,\ell_i + \mathrm{rowsum}(\widetilde{\mathbf{P}}_i^{(j)})$, and rescales the partial $\mathbf{O}_i$. Could someone provide a short derivation showing that after processing all key/value blocks, the final $\mathbf{O}_i$ equals $\mathrm{softmax}(\alpha\mathbf{Q}\mathbf{K}^\top)\mathbf{V}$ exactly (i.e., that the running rescalings do not introduce approximation), and explain why keeping softmax intermediates in FP32 preserves numerical stability?
Answer:
Short answer: the algorithm maintains, for each query row, a mathematically exact running representation of the numerator and denominator of the row-wise softmax-weighted sum. At iteration $j$ it keeps a running maximum $m_j$ and running normalizer $\ell_j$ such that the stored partial output $O_j$ and $\ell_j$ satisfy the invariant

$$O_j = \sum_{t=1..j} \exp(S^{(t)} - m_j) V^{(t)}, \qquad \ell_j = \sum_{t=1..j} \operatorname{rowsum}\big(\exp(S^{(t)} - m_j)\big),$$

where $S^{(t)}$ denotes the score block $Q K_t^T$. When you finish all blocks ($j = T$), dividing $O_T$ by $\ell_T$ yields exactly $\operatorname{softmax}(S)\,V$ (softmax taken row-wise after subtracting the global rowwise max). Below is the short derivation of that invariant and why the in-kernel rescalings are exact (up to floating point rounding).

Derivation of the update (one row, drop row index for clarity)
Let $S^{(1)},\ldots,S^{(J)}$ be the successive blocks of scores for a fixed query row, and define the global rowwise max
$$m^* = \max_{t=1..J} \operatorname{rowmax}(S^{(t)}).$$
The target quantity we want is
$$P V = \big(\operatorname{softmax}([S^{(1)},\ldots,S^{(J)}])\big) \begin{bmatrix}V^{(1)}\\ \vdots\\ V^{(J)}\end{bmatrix}
= \frac{1}{Z} \sum_{t=1..J} \exp(S^{(t)} - m^*)\, V^{(t)},$$
with
$$Z = \sum_{t=1..J} \operatorname{rowsum}\big(\exp(S^{(t)} - m^*)\big).$$

Algorithmic invariant: after processing blocks $1..j$ the kernel keeps
$$m_j = \max_{t\le j} \operatorname{rowmax}(S^{(t)}),$$
$$\ell_j = \sum_{t\le j} \operatorname{rowsum}\big(\exp(S^{(t)} - m_j)\big),$$
$$O_j = \sum_{t\le j} \exp(S^{(t)} - m_j)\, V^{(t)}.$$

Base ($j=1$) is trivial: $m_1 = \operatorname{rowmax}(S^{(1)})$, $\ell_1 = \operatorname{rowsum}(\exp(S^{(1)}-m_1))$, $O_1 = \exp(S^{(1)}-m_1)\, V^{(1)}$.

Inductive step: suppose invariant holds for $j$ with $(m_j, \ell_j, O_j)$. Process block $j+1$, compute $s = \operatorname{rowmax}(S^{(j+1)})$ and set
$$m_{j+1} = \max(m_j, s).$$
We need to form
$$\ell_{j+1} = \sum_{t\le j+1} \operatorname{rowsum}\big(\exp(S^{(t)} - m_{j+1})\big),$$
$$O_{j+1} = \sum_{t\le j+1} \exp(S^{(t)} - m_{j+1})\, V^{(t)}.$$

Write the old terms in the new exponent base. If $m_{j+1} = m_j$ then nothing changes:
$$\ell_{j+1} = \ell_j + \operatorname{rowsum}\big(\exp(S^{(j+1)}-m_j)\big),$$
$$O_{j+1} = O_j + \exp(S^{(j+1)}-m_j)\, V^{(j+1)}.$$

If $m_{j+1} = s > m_j$ then
$$\exp(S^{(t)} - m_{j+1}) = \exp(S^{(t)} - m_j)\cdot \exp(m_j - m_{j+1})$$
for every previously-processed $t \le j$. Therefore
$$\ell_{j+1} = \exp(m_j - m_{j+1})\, \ell_j + \operatorname{rowsum}\big(\exp(S^{(j+1)} - m_{j+1})\big),$$
$$O_{j+1} = \exp(m_j - m_{j+1})\, O_j + \exp(S^{(j+1)} - m_{j+1})\, V^{(j+1)}.$$

These are exactly the update formulas used in the implementation: compute
$$\tilde P^{(j+1)} = \exp(S^{(j+1)} - m_{j+1}),$$
$$\ell \leftarrow \exp(m_j - m_{j+1})\, \ell + \operatorname{rowsum}(\tilde P^{(j+1)}),$$
$$O \leftarrow \operatorname{diag}\big(\exp(m_j - m_{j+1})\big)^{-1} O + \tilde P^{(j+1)} V^{(j+1)}.$$
(They write the rescale of $O$ as multiplying by $\exp(m_j - m_{j+1})$ before adding the new block; same algebra.)

After all $J$ blocks you have
$$O_J = \sum_{t\le J} \exp(S^{(t)} - m_J)\, V^{(t)}, \qquad \ell_J = \sum_{t\le J} \operatorname{rowsum}\big(\exp(S^{(t)} - m_J)\big).$$
Thus the final per-row output is $O_J / \ell_J = \frac{1}{Z} \sum_t \exp(S^{(t)}-m^*)\, V^{(t)}$ with $m_J = m^*$ and $Z = \ell_J$. So the procedure computes the exact algebraic softmax-weighted sum (no approximation) — the per-block rescalings are algebraically correct rearrangements of the overall sum.

Remarks on floating-point arithmetic and FP32 intermediates
The algebra above is exact in real arithmetic. In finite precision you get rounding error from exponentials, multiplications and additions. Keeping the softmax intermediates (the exponentials, the running normalizer $\ell$, and the $O$ accumulators) in FP32 instead of lower precision greatly reduces these rounding errors and avoids overflow/underflow:

- Using FP32 for the subtraction $S - m$ and then $\exp(S - m)$ avoids overflow of the exponential (because subtracting the row max puts values $\le 0$) and reduces catastrophic cancellation when summing many small terms into $\ell$. FP32 has ~7 decimal digits and dynamic range large enough that $\exp$ of typical scaled logits and sums of many exponentials are represented with far smaller relative error than in FP16/FP8.
- The recurrence $\ell_{\text{new}} = \exp(m_{\text{old}} - m_{\text{new}})\, \ell_{\text{old}} + \sum(\exp(\ldots))$ involves multiplying a potentially small scaling factor $\exp(m_{\text{old}} - m_{\text{new}})$ with $\ell_{\text{old}}$ and adding another sum. Doing those ops in FP32 reduces relative rounding and accumulation error compared to FP16, so the normalizer and numerator track the true sums more faithfully.
- For $O$ (the weighted sum), each partial contribution $\tilde P V$ is computed and accumulated; accumulating in FP32 prevents large relative truncation when the weighted values have different magnitudes, and reduces bias/variance of the final result.

So while the algebra is exact, finite-precision arithmetic introduces small numeric error; keeping the softmax intermediates in FP32 makes these errors negligibly small in practice and preserves the stability of the streaming softmax scheme. Using lower precision for the matmuls (e.g., FP16/FP8 operands and FP32 accumulators) is fine because the critical softmax exponentials and the running sums that determine the weights are kept in higher precision.

In short: the update rules are just algebraic rewritings that maintain the invariant $O_j$ and $\ell_j$ with respect to the current running max $m_j$, so after the last block dividing $O$ by $\ell$ yields exactly the row softmax times $V$ in exact arithmetic. In floating point the scheme is numerically stable if the softmax intermediates and accumulators are computed in FP32 (reducing rounding, overflow/underflow, and catastrophic cancellation).

### How does bar.sync enforce the pingpong overlap of softmax and GEMM across warpgroups without race conditions?
Question:
The paper describes a "pingpong" schedule where two consumer warpgroups alternate: while one warpgroup is doing its softmax (MFU ops), the other is executing GEMMs (WGMMA), and vice versa. They mention using bar.sync to force GEMMs of warpgroup 1 to be scheduled before those of warpgroup 2 so the softmax overlaps with GEMMs. How exactly are the barriers placed to avoid deadlocks and races? What is the ordering constraint that guarantees: (1) GEMM0/GEMM1 of warpgroup 1 start before softmax of warpgroup 1, and (2) the softmax of warpgroup 1 runs while warpgroup 2 is in WGMMA, then they swap cleanly?
Answer:
Short answer: they use a small set of explicit, stage-indexed barriers tied to the circular SMEM buffer and to the two warpgroups' roles so that every data-producer commit and every consumer release is witnessed in a single global order. Concretely, the producer writes a tile into buffer stage $s$ and “commits” it; each consumer warpgroup waits on the stage’s barrier before using that stage. The pingpong is enforced by placing a barrier pair (one barrier for the GEMM launches and one for the softmax path) at the same program points in both warpgroups so that the hardware schedules the two warpgroups’ WGMMA launches before either warpgroup proceeds to the softmax work. That common, per-stage rendezvous (bar.sync indexed by the circular buffer slot and by a pingpong phase bit) yields the ordering guarantees and removes races while avoiding deadlock because the waits are always acyclic and matched by commits/releases from the producer.

Longer explanation (intuitive + how it maps to the paper)

Think of the system as three actors per CTA: a producer warpgroup that fills circular SMEM stages with $K$/$V$ tiles and two consumer warpgroups that repeatedly (1) launch the SS-GEMM ($Q K^T$) to produce the next score tile, (2) perform softmax on the current score tile (non-GEMM, slow), and (3) launch the RS-GEMM ($P V$) to accumulate outputs. The goal of pingpong is to make sure that when consumer A is doing its softmax (compute-bound on special-function units), consumer B is running the two asynchronous WGMMA instructions so Tensor Cores are busy. We achieve that by making the GEMM launches of one warpgroup deterministically occur before the softmax entry of the other warpgroup.

There are two basic synchronization primitives used in the paper’s pseudocode and implementation: (a) producer “commit” / consumer “wait” on a given SMEM buffer stage (this is a semaphore-like notification that a tile is ready), and (b) explicit CUDA barrier instructions bar.sync that provide a global rendezvous among warps in the CTA. The crucial properties used are (i) WGMMA (Tensor Core) calls are asynchronous from the issuing warpgroup’s viewpoint (you may commit them and continue), and (ii) the implementation can issue bar.sync at chosen program points to force a particular relative ordering of issued WGMMA operations across warpgroups.

How the barriers are placed so there are no races or deadlocks

1) Per-stage buffer semantics avoid races on data. The circular SMEM buffer is indexed by stage id $j \bmod s$. The producer never overwrites a stage until the consumer has “released” it; likewise the consumer never reads a stage until the producer has committed it. This is the standard $s$-stage producer/consumer pattern in Algorithm 1: the producer “commit to notify consumer” after TMA load; the consumer “wait for $K_j$ to be loaded” before reading. Those waits are explicit and tied to the stage index, so no consumer can consume before a matching producer commit. Because each stage has a well-defined ownership timeline (producer writes → commit → consumer reads → release → producer may reuse), there are no data races on SMEM.

2) bar.sync is used to impose a cross-warpgroup ordering of GEMM launches versus softmax execution. The paper explains (Section 3.1, “Pingpong scheduling”) that they “force the GEMMs (GEMM0 and GEMM1 of warpgroup 1) to be scheduled before the GEMMs of warpgroup 2, so the softmax of warpgroup 1 will be scheduled while warpgroup 2 is performing its GEMMs.” In practice this is realized by inserting the same barrier IDs (or the same program-point rendezvous) at two program points in both consumer warpgroups: right after issuing the asynchronous WGMMA(s) and right before starting the softmax work that depends on the completed WGMMA. Both warpgroups execute the same sequence of bar.sync calls in the same control-flow order, so bar.sync establishes a global ordering of issued WGMMA operations versus subsequent softmax code.

Put another way, each consumer loop iteration contains these ordered events (matching Algorithm 2 lines):
  - Issue WGMMA for $S_{\text{next}}$ (line referenced as code:first_wgmma) and commit it (do not wait).
  - Issue WGMMA for $P_{\text{cur}} V_{j-1}$ (code:second_wgmma) and commit it (do not wait).
  - Wait for the first WGMMA to complete, then run softmax on $S_{\text{next}}$ (code:softmax).
  - Wait for the second WGMMA to complete, then finish the RS-GEMM result handling.

If you place a bar.sync between the two groups at the program point just after the WGMMA commits but before either group proceeds to the softmax work, then both warpgroups will reach that bar.sync. The hardware then guarantees that all warpgroups have reached that synchronization point before any proceed. By carefully ordering where bar.sync appears in each wargroup’s code, you force one set of WGMMA launches (from both warpgroups) to be seen by the GPU scheduler before the softmax execution of either warpgroup is allowed to proceed; in effect the barrier serializes the softmax entry relative to the pending WGMMA issuance order. The implementation chooses the barrier placement such that warpgroup 1 issues its WGMMA pair and reaches the bar.sync while warpgroup 2 is still behind in program order (or vice versa), creating the desired overlap. Because the WGMMA instructions are asynchronous, issuing them then waiting at the barrier lets Tensor Cores execute the matmuls during the other wargroup’s softmax.

Why this does not deadlock
Deadlock would occur only if there were cyclic waits with no progress (for example warpgroup A waiting for B and B waiting for A at different program points). The scheme avoids that by ensuring that all bar.sync/wait operations are always reached in the same static order by each participating warpgroup and that buffer-stage waits are matched by producer commits/releases. The circular buffer provides bounded asynchrony but no cyclic dependency because ownership of each stage moves strictly forward in the producer→consumer→release direction. The bar.syncs are used only to synchronize program points (not to wait for data that will only be produced after the barrier), so there is no cycle where A waits at barrier X for B while B waits at barrier Y for A. In other words, every bar.sync is a single rendezvous point that both warpgroups arrive at in the same loop order, so the waits are matched and acyclic.

Concrete ordering constraints that guarantee the two properties you asked about

(1) GEMM0/GEMM1 of warpgroup 1 start before softmax of warpgroup 1. This is enforced by issuing the WGMMA instructions for GEMM0/GEMM1 and immediately reaching a bar.sync (or using the circular-buffer stage commit semantics which make consumers wait until the producer has committed). Because the softmax code is placed after that bar.sync in the program order, no thread in that warpgroup will execute softmax until after the WGMMA has been issued and the bar.sync has allowed progress. The WGMMA is asynchronous and thus can run in hardware while the warps wait or run softmax, but the program order guarantee (issue WGMMA → bar.sync → softmax) guarantees the GEMMs have been launched before softmax attempts to proceed.

(2) Softmax of warpgroup 1 runs while warpgroup 2 is in WGMMA, then they swap cleanly. This is achieved by using the same per-iteration barrier layout in both warpgroups but offsetting their phase so that at the moment warpgroup 1 reaches the softmax code it has already passed the “issue WGMMA” barrier and warpgroup 2 is still in the phase that issued its WGMMA and is proceeding into the barrier wait. Because WGMMA execution is asynchronous, the Tensor Cores will be actively executing the GEMMs from warpgroup 2 while warpgroup 1 executes the softmax on the scalar units. Later iterations swap roles: warpgroup 2 will execute its softmax while warpgroup 1’s WGMMA runs. The circular buffer + per-stage bar.syncs ensure the phase offsets are consistent and there is no race on the buffer contents because release/commit semantics are observed at each stage.

Mapping to the paper’s pseudocode
Algorithm 1 shows the per-stage commit/wait semantics for producer/consumer over the $s$-stage buffer. Algorithm 2 (the 2-stage pipelined consumer) shows the exact program points where the WGMMA calls are committed without waiting (code:first_wgmma and code:second_wgmma) and where the softmax works (code:softmax) happen. The paper states that they “use synchronization barriers (bar.sync instructions) to force the GEMMs of warpgroup 1 to be scheduled before those of warpgroup 2” and that these barriers are tied to the circular buffer. In implementation terms you can think of a small set of bar.sync indices per buffer stage and per pingpong phase; both warpgroups call the same sequence of barriers, so the order of issue vs. softmax is deterministically enforced while the buffer stage ownership prevents data races and the ordered, identical barrier sequence avoids deadlocks.

Summary
The combination of (a) stage-indexed producer/consumer commits and releases on the circular SMEM buffer to avoid data races, and (b) a small set of matched bar.sync rendezvous placed at the program points immediately after WGMMA issuance and immediately before softmax, guarantees the ordering you want: GEMMs are launched before the corresponding softmax, and one wargroup’s softmax executes while the other wargroup’s asynchronous WGMMA runs. Because every wait is matched by a corresponding commit/release and both warpgroups run the same barrier sequence in the same loop order, there are no cyclic waits and hence no deadlock.

### What exactly are "commit" and "wait" for WGMMA/TMA on Hopper in this paper?
Question:
Throughout the algorithms, the authors write instructions like "Commit and wait" or "Commit but do not wait" for WGMMA, and they describe TMA loads as asynchronous with a later wait. Which exact CUDA/PTX primitives are they referring to? For example: for TMA is this tma.load followed by barrier.arrive/wait or cp.async-style wait groups? For WGMMA, is this wgmma.mma_async with proxy/barrier semantics? A mapping from the pseudocode's commit/wait to concrete Hopper instructions or programming abstractions (e.g., CUTLASS APIs) would really help.
Answer:
Short answer: in the paper the authors use “commit” to mean “issue the asynchronous operation (TMA or WGMMA) so the hardware begins it and the producer signals availability” and “wait” to mean “synchronize on completion of that asynchronously-issued operation before using its results.” Concretely on Hopper this maps to the asynchronous TMA and wgmma PTX primitives (or their CUDA/CUTLASS wrappers) plus the small synchronization primitives around them (barrier / wait APIs provided by PTX/CUTLASS). Below I give the concrete mappings and an intuitive explanation of why each primitive is used.

TMA (their “loads are asynchronous; commit / wait”)
- What the paper implements: the producer warpgroup issues TMA loads of $Q$, $K$, $V$ into SMEM, then “commits” to notify the consumer; the consumer later “waits” for the load to complete before reading SMEM.
- PTX / CUDA mapping: on Hopper you use the TMA (Tensor Memory Accelerator) asynchronous copy instructions (the PTX-level TMA load/copy variants or the corresponding CUDA driver intrinsics exposed via CUTLASS). These are issued non‑blocking: the instruction starts DMA from GMEM to SMEM and returns immediately.
- The producer-side “commit” in the paper corresponds to issuing that TMA copy and letting the producer release/announce the buffer slot (in PTX/CUTLASS you typically call the copy_async or tma.load and then arrange a notification). The consumer-side “wait” corresponds to the lightweight barrier/synchronization that ensures the TMA completed before reading SMEM (in practice implemented with the barrier / arrive/wait or bar.sync style primitive used to coordinate warps/warpgroups).
- Practical APIs: in CUTLASS you use the TMA abstraction (copy_async / commit_copy / wait_copy or similar wrappers). At PTX level the primitives are the TMA load instructions plus a synchronization primitive (paper cites the PTX TMA docs). This is conceptually the same role cp.async* plays on other architectures, but cp.async uses its own commit/wait group semantics; TMA on Hopper is the dedicated, separate hardware unit with its own completion semantics you must synchronize with (via barrier-like mechanisms exposed in the runtime or in CUTLASS).

WGMMA (their “WGMMA is asynchronous; commit but do not wait / wait later”)
- What the paper implements: in the consumer main loop they issue a WGMMA for the next $Q \cdot K^T$ and they also issue WGMMA for $P \cdot V$; they sometimes “commit but do not wait” to overlap the long Tensor Core GEMM with softmax, and later they “wait” for those WGMMA ops before using their results.
- PTX / CUDA mapping: Hopper exposes asynchronous warpgroup MMA via the WGMMA family of instructions (the PTX “wgmma.mma_async” style intrinsics described in the PTX reference the paper cites). Those instructions can be issued and later waited on; the PTX model provides commit/issue and wait/complete semantics for wgmma async ops.
- The paper’s “commit but do not wait” maps to issuing the wgmma.mma_async (or the CUTLASS wrapper) and continuing with independent work (e.g., softmax on previously-produced tile). The later “wait” maps to calling the corresponding wgmma wait/complete instruction (or CUTLASS API) that blocks until the asynchronous mma completes and results are available in registers/SMEM.
- Practical APIs: CUTLASS exposes asynchronous wgmma/WarpGemm abstractions that provide functions like execute_async / commit / wait (the exact API names vary across CUTLASS versions). At SASS/PTX the sequence is: generate the wgmma async instruction(s), then later issue the wgmma wait (or the PTX-level wait semantics described in the PTX WGMMA section). The paper explicitly cites the PTX WGMMA documentation and uses those async semantics in its code-generation analysis.

Barriers and warp/warpgroup coordination
- The algorithm requires producer/consumer coordination across warpgroups and between TMA and WGMMA. The authors mention using synchronization barriers (they reference bar.sync in the paper). In practice you use the CUDA/PTX barrier primitives (bar.sync, barrier.arrive, barrier.wait, or the corresponding cutlass::Barrier or cooperative primitives) to implement the “notify” / “wait for buffer slot” semantics used in the pseudocode.
- Example mapping: producer issues TMA copy (commit), then does barrier.arrive (or uses a CUTLASS pipeline object that internally signals a slot). Consumer performs barrier.wait (or pipeline.wait_for_stage) before reading SMEM. Similarly, to implement ping‑pong scheduling across two warpgroups you use bar.sync-style joins so the compiler/hardware schedules GEMMs/softmax in the intended overlapped order.

Other low‑level pieces mentioned in the paper
- LDSM/STSM (ldmatrix / stmatrix): these are PTX/SASS register/shared-memory matrix load/store instructions used for in-kernel transposes and layout changes for $FP8$; they are synchronous in the sense you use them directly and then operate on the registers. The paper uses them in the producer to form $k$-major tiled $V$ for $FP8$.
- Byte/permute instructions and register tricks: the $FP8$ accumulator/operand layout transformations described are implemented with byte permute and register-shuffle SASS instructions after the WGMMA accumulator is produced and before issuing the next WGMMA.

To summarize the concrete mapping you can use when reading the pseudocode:
- “Issue load … Commit” for TMA = issue the TMA asynchronous copy (CUTLASS: TMA::copy_async or CUDA/PTX TMA load) and publish the stage (barrier/notify). “Wait for … loaded” = barrier.wait or pipeline.wait for that stage.
- “Compute … using WGMMA. Commit but do not wait.” = call the async WGMMA primitive (wgmma.mma_async or CUTLASS async-wgmma wrapper) and do not call the matching wait yet. “Wait for the WGMMA” later = call the WGMMA wait/complete primitive (wgmma.mma_wait or CUTLASS wait_all / wait for that async op).
- Inter-warpgroup coordination / ping‑pong = implement with bar.sync / barrier.arrive/wait (or CUTLASS’ pipeline/barrier helper objects) so the compiler/hardware schedules the warpgroups’ GEMMs and softmaxes with the intended overlap.

Concrete examples you will find in the codebase
The authors state they implement FlashAttention-3 using CUTLASS primitives. In that code you will see:
- CUTLASS TMA copy_async / commit / wait wrappers for the GMEM->SMEM moves, and pipeline objects that manage circular buffer slots and perform pipeline.wait/pipeline.publish (these implement the paper’s commit/wait of TMA).
- CUTLASS WGMMA async wrappers (execute_async / commit / wait or wait_all) for the Tensor Core GEMMs. The SASS/PTX emitted contains wgmma.mma_async and corresponding wait instructions as described in the PTX reference the paper cites.

Why this matters (intuition)
TMA and WGMMA are separate hardware engines on Hopper. Issuing them asynchronously and only waiting when you need the data lets the GPU overlap the slow parts (memory copies, softmax exponentials) with extremely fast Tensor Core math, which is exactly the source of the paper’s speedup. The “commit but do not wait” idiom is not a new primitive: it is simply the pattern “start async op and continue; later call the op’s completion/wait primitive.” On Hopper the concrete building blocks are the TMA and WGMMA instructions (or their CUTLASS wrappers) plus the barrier/synchronization primitives that let producer and consumer agree on buffer stages.

If you want to inspect/modify the implementation: look for CUTLASS’s TMA / pipeline helpers and the WGMMA async wrappers in the FlashAttention-3 repo — those are the places where the paper’s pseudocode commit/wait map directly to real instructions and APIs.

### How should I choose the number of stages $s$ in the circular SMEM buffer, and what are the trade-offs?
Question:
Algorithm 1 uses an $s$-stage circular buffer in shared memory to pipeline TMA loads of $\{\mathbf{K}_j, \mathbf{V}_j\}$. How should $s$ be chosen on H100 in practice? What are the trade-offs in terms of: (1) SMEM footprint vs. occupancy, (2) latency hiding for TMA, and (3) added synchronization overhead? Is there a rule of thumb relating $s$ to the time of one WGMMA tile vs the TMA tile load time, or to the number of consumer warpgroups?
Answer:
Short answer: choose $s$ small (typ. $2$–$4$) so that the producer can enqueue enough TMA loads to keep all consumer WGMMA work busy, but not so large that the per-stage SMEM allocation kills occupancy or adds excessive sync bookkeeping. A practical rule of thumb is

$s \approx \operatorname{clamp}\!\left(1 + \left\lceil \frac{\text{TMA\_tile\_load\_time}}{\text{WGMMA\_tile\_time}} \right\rceil, 2, 4\right)$

subject to the hard SMEM-per-CTA constraint: $s \cdot \text{stage\_size} + \text{other\_SMEM} \le \text{SMEM\_per\_SM} / \text{CTAs\_per\_SM}$. Measure and tune if you need to push for extreme throughput.

Why this, and the trade-offs (intuitive + a few technical details grounded in the paper)

SMEM footprint vs. occupancy.
Each circular-buffer stage stores one $(K, V)$ tile (and any metadata). The per-stage cost is roughly $B_c \cdot d \cdot \mathrm{sizeof(element)}$ for $K$ plus $B_c \cdot d \cdot \mathrm{sizeof(element)}$ for $V$ (plus a few words of control). Increasing $s$ multiplies that cost, so SMEM per-CTA grows linearly with $s$. On Hopper the SMEM is limited and the scheduler will reduce CTA occupancy if a CTA’s SMEM demand is too large. Lower occupancy means fewer concurrent CTAs per SM and thus lower ability to hide other latencies (and lower aggregate throughput). So the practical constraint is: pick the largest $s$ that still lets you have enough CTAs per SM (or threads/registers) to achieve good occupancy. In practice the paper’s implementation uses small $s$ so register/SMEM pressure stays manageable.

Latency hiding for TMA.
TMA loads are asynchronous but have non-negligible latency. The circular buffer exists so the producer can issue TMA for future $(K,V)$ tiles ahead of time and the consumers can find data ready when they need it. To avoid producer stalls you want enough stages so that while the consumers and their WGMMA tiles are executing, the producer can load the next tiles. Conceptually you want $s$ large enough that the pipeline depth covers the TMA latency divided by the time between consumer consumption events. A clean formulation is to compare the time to perform one WGMMA tile (the consumer work that consumes one buffer stage) to the time to issue and complete one TMA tile load:

$\text{if }\ \text{TMA\_tile\_load\_time} \le \text{WGMMA\_tile\_time},\ s = 1$ (producer can keep up); otherwise you need roughly $\left\lceil \dfrac{\text{TMA\_tile\_load\_time}}{\text{WGMMA\_tile\_time}} \right\rceil$ stages so producer can issue loads far enough ahead. The paper exploits this by having the producer not wait during the first $s$ iterations while the buffer fills; that is the exact role of $s$ in hiding TMA latency.

Added synchronization overhead.
Each buffer stage introduces producer/consumer coordination: commit notifications, waits on $(j \bmod s)$ stages, and barrier / release operations. More stages mean slightly more bookkeeping and more potential for stalling if synchronization is not perfectly overlapped. In practice the cost of these extra syncs is small relative to WGMMA cost, but it is not zero: it adds instructions and increases the number of conditional waits and branch points in the producer/consumer loops. Also larger $s$ can exacerbate compiler/inspector complexity (and interact with register allocation), as noted in the paper’s discussion of register pressure and compiler reordering. So there is diminishing return: after you reach enough stages to hide TMA latency, increasing $s$ further produces little benefit and more overhead.

Relation to number of consumer warpgroups and WGMMA vs TMA times (rule of thumb).
Think of the system as having $P$ producer warpgroups and $C$ consumer warpgroups in the CTA (the paper uses warp-specialization and warpgroups to split producers and consumers). The producer must issue enough TMA loads to feed all $C$ consumers. A simple practical rule of thumb derived from the paper’s description is:

Make $s$ at least the number of consumer “tickets” required to keep all consumers busy while one TMA completes. Concretely set

$s \ge 1 + \left\lceil \dfrac{\text{TMA\_tile\_load\_time}}{\text{WGMMA\_tile\_time} \cdot \text{effective\_consumers\_per\_tile}} \right\rceil$

where $\text{effective\_consumers\_per\_tile}$ is the average number of WGMMA tiles that can be executed (in parallel or in pipeline interleaving) while a TMA finishes. For single-producer, multiple-consumer warp-specialization, a simpler and robust rule used in the paper is

$s \approx 1 + \left\lceil \dfrac{\text{TMA\_time}}{\text{WGMMA\_time}} \right\rceil$

and then clamp to small integers ($2$–$4$). The paper’s experiments show big wins from overlapping even with small $s$ (the 2-stage pipelining and ping-pong scheduling produced a large TFLOPs jump), so you usually do not need a large $s$.

Practical recommended procedure on H100 (step-by-step)
1) Compute per-stage SMEM: $\text{stage\_size} \approx 2 \cdot B_c \cdot d \cdot \mathrm{sizeof}(\text{float or fp8 packed}) + \text{small control words}$. Ensure $s \cdot \text{stage\_size}$ plus other SMEM fits your SM budget while leaving enough CTAs/SM to keep occupancy healthy. If it doesn’t, reduce $s$ or reduce $B_c$. 2) Microbenchmark or estimate: measure (or model from CUTLASS/SASS) the time to (a) do one WGMMA tile ($\text{WGMMA\_tile\_time}$) and (b) complete one TMA tile load into SMEM ($\text{TMA\_tile\_load\_time}$). 3) Set $s = 1 + \left\lceil \dfrac{\text{TMA\_tile\_load\_time}}{\text{WGMMA\_tile\_time}} \right\rceil$ and clamp to a small max (the paper’s practical designs use $2$ or $3$; a clamp of $4$ is conservative). 4) Validate: run the kernel and check whether the producer stalls (look at profiler timeline or SM stalls). If the producer stalls, increase $s$ (if SMEM allows) or adjust $B_c$. If occupancy drops too much, decrease $s$ and try to improve overlap by other means (e.g., ping-pong scheduling across warpgroups or the 2-stage GEMM-softmax).

Why small $s$ often suffices
The paper demonstrates that a combination of warp-specialization, ping-pong scheduling between warpgroups, and a 2-stage intra-warpgroup GEMM-softmax pipeline already captures most of the benefits on H100. Because WGMMA is extremely fast on H100 (and softmax is relatively slow), you only need a few buffer stages to mask TMA latency; making $s$ very large wastes precious SMEM and reduces occupancy for little additional latency hiding.

Summary (concise)
- $s$ trades SMEM footprint (linear in $s$) vs. ability to hide TMA latency. - Use a small $s$ ($2$–$4$) in practice on H100; start with $2$ (matches the 2-stage pipelining in the paper) and raise if producer stalls. - Rule of thumb: $s \approx 1 + \left\lceil \dfrac{\text{TMA\_tile\_load\_time}}{\text{WGMMA\_tile\_time}} \right\rceil$ but clamp to small integers and always check SMEM/occupancy constraints. - Monitor producer stalls and SMEM-induced occupancy drops; tune $B_c$, $s$, or consumer warpgroup split accordingly.

### In Algorithm 2, which operations are actually overlapped—does exp run while Tensor Cores execute WGMMA?
Question:
In the 2-stage pipeline (Algorithm 2), the authors say the second WGMMA of iteration $j$ overlaps with softmax from iteration $j+1$. In concrete terms, which specific instructions overlap on Hopper: do the MFU exponentials and FP32 FMAs for softmax and rescaling execute concurrently with the Tensor Cores running wgmma.mma_async? A brief timeline for iterations $j$ and $j+1$ showing when waits happen for $\mathbf{Q}_i\mathbf{K}_j^\top$ vs. $\widetilde{\mathbf{P}}_{\text{cur}}\mathbf{V}_{j-1}$ and when softmax starts would help me reconcile the pseudocode with hardware reality.
Answer:
Short answer: yes — exponentials and FP32 multiply-adds that implement softmax/rescale run on the MFU/CUDA cores while the Tensor Cores are executing asynchronous WGMMA, and the code explicitly issues WGMMA instructions with "commit but do not wait" so the second WGMMA of iteration $j$ (the RS-GEMM that multiplies the already-computed $\widetilde{P}_{cur}$ by $V_{j-1}$) is overlapped with the softmax work that follows from the next iteration's QK WGMMA. The software enforces correctness by explicit waits only when results are actually needed.

Explanation with a concise timeline (iterations $j$ and $j+1$)

Think of each iteration producing two GEMMs (labels follow the paper): $\mathrm{GEMM0}_j = Q_i K_j^T$ (the "first" WGMMA for block $j$) and $\mathrm{GEMM1}_j = \widetilde{P}_{cur} V_{j-1}$ (the "second" WGMMA that consumes the softmax result from the previous $S$). The 2-stage pipeline rearranges issue/wait so these overlap.

A compact timeline for iteration $j$ and the immediately following iteration $j+1$ (events in roughly issue order):

1. Wait for $K_j$ in SMEM (so $\mathrm{GEMM0}_j$ can be issued).
2. Issue $\mathrm{GEMM0}_j = Q_i K_j^T$ as a WGMMA (the code "Commit but do not wait"). This launches an asynchronous Tensor‑Core matmul; it will complete later without stalling the threadgroup immediately.
3. Ensure $V_{j-1}$ is in SMEM.
4. Issue $\mathrm{GEMM1}_j = \widetilde{P}_{cur} V_{j-1}$ as a WGMMA (also "Commit but do not wait"). This is the second Tensor‑Core matmul for iteration $j$; it is launched while $\mathrm{GEMM0}_j$ may still be in flight.
5. Now the code explicitly waits for $\mathrm{GEMM0}_j$ to complete (the WGMMA that computes $S_{next}$). Once that wait returns, the $S_{next}$ tile (the QK result for block $j$) is available in registers/SMEM.
6. Immediately compute softmax on $S_{next}$: compute rowmax, exponentials, row sums and update accumulator $\ell_i$ and $m_i$. These exponential/sum/rescale steps are implemented on the MFU/CUDA cores (exponentials on the MFU/special-function unit, FP32 FMAs/accumulates on CUDA cores) and are executed now while $\mathrm{GEMM1}_j$ (the second WGMMA) is still progressing on the Tensor Cores if it has not yet finished.
7. After softmax finishes, the code waits for $\mathrm{GEMM1}_j$ to finish (because $\mathbf{O}_i$ must be updated with its result), then performs any rescale updates that depend on the finished $\mathrm{GEMM1}_j$.
8. Copy $S_{next} \to S_{cur}$ and proceed: in the next loop iteration $j+1$ the pattern repeats ($\mathrm{GEMM0}_{j+1}$ is issued, $\mathrm{GEMM1}_{j+1}$ issued, then wait for $\mathrm{GEMM0}_{j+1}$ and do softmax on it, etc.).

Key points and why the overlap is legal and effective

- WGMMA on Hopper is asynchronous and can be launched without stalling the issuing warpgroup; results are later synchronized with an explicit wait. The algorithm uses that by issuing both WGMMA calls and only waiting when their outputs are actually required.
- Exponentials and the FP32 FMAs that implement softmax/rescaling are performed on different functional units (MFU and CUDA FP units) than the Tensor Cores. Because those units are separate, the MFU/CUDA work can proceed while Tensor Cores are busy, i.e., true hardware parallelism enabling overlap.
- The data dependency graph is respected: softmax on $S_{next}$ cannot start until $\mathrm{GEMM0}_j$ ($Q K_j^T$) completes, so the code waits for $\mathrm{GEMM0}_j$ before calling the MFU exponentials. But $\mathrm{GEMM1}_j$ does not depend on $S_{next}$; it depends on $\widetilde{P}_{cur}$ produced from the previous $S$. Therefore the second WGMMA for iteration $j$ can be running concurrently with the softmax on $S_{next}$ (which logically belongs to iteration $j+1$). That is exactly the overlap described in the paper: "the second WGMMA of iteration $j$ overlaps with softmax from iteration $j+1$."
- The algorithm enforces correctness by issuing explicit waits at the two points where outputs are consumed: it waits for $\mathrm{GEMM0}$ before softmax on $S_{next}$, and it waits for $\mathrm{GEMM1}$ before using the product to update $\mathbf{O}_i$/rescale.

Practical caveats the paper also calls out

- Compiler reordering: NVCC/SASS may reorder instructions, so the implementation checks the generated SASS to ensure the intended overlap survives optimization. The pseudocode is the logical ordering; real code uses explicit commits/waits and synchronization to enforce it.
- Register pressure and timing variability: the overlap relies on there being enough outstanding work on Tensor Cores to hide the MFU latency. If the MFU work is too large or register spilling happens, the net overlap and speedup will be reduced. The paper uses warp‑specialization and register budgeting to make the overlap practical.
- Pingpong across warpgroups: beyond intra-warpgroup overlap, the algorithm also uses warp‑specialization at CTA level so that the softmax of warpgroup A is scheduled while warpgroup B performs both GEMMs, further increasing concurrency.

Summary

Concretely on Hopper, the MFU exponentials and FP32 FMA operations that implement softmax/rescale are executed concurrently with the WGMMA Tensor‑Core instructions for the second GEMM because WGMMA is issued asynchronously and softmax runs on different execution units. The code issues $\mathrm{GEMM0}$ (QK), issues $\mathrm{GEMM1}$ ($P_{cur}\!*V_{prev}$), then waits for $\mathrm{GEMM0}$ and computes softmax on its result — that softmax therefore overlaps with $\mathrm{GEMM1}$'s Tensor‑Core work. The algorithm only waits when it must (before using a WGMMA result), so correctness is preserved while hardware units are kept busy.

### Can someone reproduce the 50% cycle estimate for exp vs matmul on H100 for head dimension 128?
Question:
The paper estimates that for FP16, head dimension $d=128$, the exponential can take roughly 50% of the cycles: there are about $512\times$ more matmul FLOPs than exp ops in the forward pass, but exp has about $256\times$ lower throughput on H100, so exp ends up taking about half the time. Could someone show this computation step by step, including: (1) counting exp ops per token per block for softmax, (2) counting matmul FLOPs for $\mathbf{Q}\mathbf{K}^\top$ and $\mathbf{P}\mathbf{V}$, and (3) plugging in the quoted H100 FP16 Tensor Core throughput vs MFU exp throughput to arrive at the 50% figure?
Answer:
Short answer: the paper’s back-of-envelope is this. For head dimension $d = 128$ the two GEMMs in the forward pass contribute $4d$ times as many arithmetic ops as there are exponentials, i.e. $4\cdot128 = 512\times$ more matmul FLOPs than exp calls. The H100 has roughly $256\times$ more FP16-Tensor‑Core matmul throughput than the special‑function (exp) throughput, so the matmul side only wins by about a factor of 2 in time; adding the other scalar softmax work (row‑max, subtract, accumulates, scalings) which is done on the same low‑throughput unit roughly doubles the non‑GEMM cost and moves the share of cycles of exp+softmax to about 50%. Below are the steps and numbers.

1) Count exponentials per token per block (softmax)
For one query (one row of $S$) you compute scores with all $N$ keys and must take an exponential for each score in that row. So exponentials per query = $N$. We treat the expensive special function here as the exp, and note there are also a few extra scalar ops per score (max, subtract, multiply-add in the softmax reduction), but the dominant special‑function count is $N$ exponentials.

2) Count matmul FLOPs for $QK^T$ and $P V$
Using the usual multiply–add FLOP convention (multiply and add = 2 FLOPs):
- Computing the row of $S$: $Q$ $(1\times d)\times K^T$ $(d\times N)$ is $N$ dot products of length $d$, i.e. $2\cdot d\cdot N$ FLOPs.
- Computing the output row $O$: $P$ $(1\times N)\times V$ $(N\times d)$ is $N$ weighted sums of $d$-length vectors, i.e. another $2\cdot d\cdot N$ FLOPs.
Total matmul FLOPs per query = $2\cdot d\cdot N + 2\cdot d\cdot N = 4\cdot d\cdot N$.
Divide by the number of exponentials $N$ to get the ratio (matmul FLOPs) / (exp ops) = $4d$. Plugging $d = 128$ gives $4\cdot128 = 512$. That is the “$\approx512\times$ more matmul FLOPs than exp ops” statement in the paper.

3) Plug in H100 throughputs and compute time shares
The paper quotes H100 FP16 Tensor Core peak matmul throughput $\approx 989$ TFLOPS (they also report achieving up to $740$ TFLOPS in practice) and an estimate for special functions (exp etc.) of $\approx 3.9$ TFLOPS (derived from “16 special-function ops per SM per cycle” × SM count × clock). The throughput ratio (matmul : exp) is therefore about $989 / 3.9 \approx 254 \approx 256\times$ (paper rounds to 256).

Time is proportional to (work) / (throughput). Let $M/E$ be the matmul-to-exp work ratio $=512$, and let $R = T_{\text{mat}} / T_{\text{exp}} \approx 256$ (the matmul is $R$ times faster). Then the relative wall-time ratio is
$$
\text{Time}_{\text{mat}} / \text{Time}_{\text{exp}} = (M / T_{\text{mat}}) / (E / T_{\text{exp}}) = (M/E)\cdot (T_{\text{exp}} / T_{\text{mat}}) = 512\cdot(1/256) = 2.
$$
So with these raw counts the matmul work would take about $2\times$ the time of the exponentials alone; equivalently the exp time would be $1/3$ of the total ($\approx 33\%$) and matmul $\approx 67\%$.

Reconciling to the paper’s “$\approx50\%$” statement
The paper’s statement that the exponential/softmax can take roughly half the cycles folds in the other non‑GEMM scalar work of softmax (rowwise max, row sums, scaling multiplications, index bookkeeping, and any FP32/FP16 conversions). Each score requires a few extra scalar operations in addition to the exp. A simple way to see the effect is to count a few extra scalar FLOPs per score — e.g. subtract/compare/accumulate and a couple of multiplies/adds — that are issued on the low‑throughput special‑function/FP cores (or on CUDA cores rather than Tensor Cores). Those extra per‑score costs are $O(N)$ and can be on the same order as the exp cost, so they effectively multiply the low‑throughput side by $\sim 2$. If you double the low‑throughput work, the time ratio becomes

$$
\text{Time}_{\text{mat}} / \text{Time}_{\text{lowthroughput}} \approx (512 / 256) / 2 = 1,
$$

so matmul and the exp+softmax scalar work are comparable and each uses $\sim 50\%$ of the cycles. In other words, the precise split depends on whether you count only exp calls (gives exp $\approx33\%$) or exp plus the scalar softmax machinery (gives roughly exp+softmax $\approx50\%$), and the paper’s “about half the time” uses the latter accounting.

Summary (numbers)
- Matmul FLOPs per query: $4\cdot d\cdot N$ → for $d = 128$ this is $512\cdot N$.
- Exponentials per query: $N$ (plus $O(N)$ extra scalar ops for softmax).
- FLOP/exp ratio = $512$.
- H100 throughput ratio $\approx 256$ (matmul:exp).
- Raw time ratio (matmul : exp) $\approx 2 : 1$ → exp $\approx 33\%$ of cycles if you count only exp.
- Including other scalar softmax ops roughly doubles the low‑throughput side → exp+softmax $\approx 50\%$ of cycles, matching the paper’s back‑of‑envelope.

So the step‑by‑step arithmetic in the paper is correct; the apparent mismatch (33% vs 50%) comes from whether you include the rest of the softmax scalar work along with the exponentials.

### Where is causal masking applied in the pipelined loop, and does it interfere with overlap?
Question:
For causal attention, where exactly is the mask applied in the overlapped 2-stage main loop? Is the mask applied as $-\infty$ to entries of $\mathbf{S}_i^{(j)}$ prior to computing $m_i$ and $\widetilde{\mathbf{P}}_i^{(j)}$? Does this introduce additional data-dependent divergence or extra waits that could break the intended overlap between WGMMA and softmax, especially for tiles that straddle the triangular boundary?
Answer:
Short answer: the causal mask is applied locally in the softmax stage (after the SS‑GEMM that produces the score tile and before computing the local row‑max / exponentials). In the 2‑stage overlapped loop you still compute each tile’s score block $S_i^{(j)}$ (or skip producing it entirely for fully‑future blocks), then mask the disallowed entries (set them to a very large negative value / logically treat them as $-\infty$) prior to computing $m_i$ and $\widetilde{\mathbf{P}}_i^{(j)}$. Doing this does not force extra cross‑warp synchronization or break the intended overlap between WGMMA and softmax.

Why, in a bit more detail and intuition grounded in the paper’s algorithm:

1) Where the mask belongs in the pipeline
The pipeline in Algorithm 2 computes a score tile (we call it $S_{cur}$ or $S_{next}$) with an asynchronous WGMMA, then runs the softmax reduction on that tile to produce a row‑normalized $\widetilde{\mathbf{P}}$ tile. Causal masking is part of the softmax computation: after the SS‑GEMM produces $S_i^{(j)}$ you apply the causal mask to the entries of that tile and then compute
$m_i = \max(m_i^{old}, \operatorname{rowmax}(S_i^{(j)}_{\text{masked}}))$
and
$\widetilde{\mathbf{P}}_i^{(j)} = \exp\!\left(S_i^{(j)}_{\text{masked}} - m_i\right).$
So the mask is logically applied to $S$ before any row‑max, exponentials, accumulation $\ell_i$, or using $\widetilde{\mathbf{P}}$ in the RS‑GEMM. This is exactly the local softmax/rescale part in lines marked code-ws:softmax_start..code-ws:softmax_end / code:softmax in the paper’s pseudocode.

2) Does this need extra waits or data‑dependent divergence?
No extra synchronization beyond what the pseudocode already needs. Two facts make this inexpensive and non‑blocking in the FlashAttention‑3 design:

- The mask is deterministic from tile indices (query block index $i$ and key block index $j$) and can be evaluated by each thread without communicating with other warps/threads. Whether an element is “future” or not is just a comparison of its (row, column) coordinates against the causal boundary, so implementing the mask is a simple elementwise operation (set to $-\infty$ or a large negative sentinel) performed locally in registers/SMEM.

- Mask application is part of the (non‑GEMM) softmax work, which the algorithm explicitly overlaps with other warpgroups’ GEMMs (and even with some in‑warpgroup WGMMAs). Because softmax (including masking, rowmax, exponentials, and scaling) runs on the separate execution resources from Tensor Cores, it is scheduled to execute while WGMMA from another stage is in flight. Masking itself is cheap (comparisons + conditional write of a sentinel) compared to exponential and reduction, so it does not introduce blocking waits on WGMMA. The only required wait is the normal one for the producing WGMMA to finish generating $S_{cur}/S_{next}$; once $S$ is available you can immediately mask and proceed with rowmax/exp without any new cross‑warp barriers.

3) Tiles that straddle the triangle boundary
For tiles that partially cross the diagonal (i.e., some columns in the tile are allowed, some are masked), you still produce the score tile via the SS‑GEMM, then apply the elementwise mask to the entries that correspond to future keys and proceed with the local reductions. This is the usual per‑tile local softmax approach. There is no data‑dependent global control flow: the mask pattern is known from tile indices, and every thread executes the same sequence of instructions (with different elements masked), so there is no extra warp divergence beyond normal per‑element branches that are already regular and cheap.

(As an optimization many implementations skip issuing the GEMM for tiles that are fully in the future (entire tile masked) and thus avoid doing wasted WGMMA work; the paper’s FLOP accounting for causal attention divides by two as an approximation of this effect. Whether you skip such tiles is an implementation choice and not required for correctness.)

4) Practical caveats
Two practical things the paper already calls out are relevant: the compiler sometimes reorders instructions and register pressure is tight. You must ensure the mask and softmax operations are scheduled in the intended place relative to asynchronous WGMMA calls (the implementation does this by issuing WGMMA asynchronously and then waiting for it before running the mask+softmax on that tile). Also, masking and softmax consume on‑chip registers/SMEM; excessive register pressure might force different tile/pipeline tradeoffs. But these are resource/optimization issues, not correctness or fundamental overlap blockers.

Conclusion: the causal mask is applied to each produced score tile before computing $m_i$ and $\widetilde{\mathbf{P}}_i^{(j)}$; it is an elementwise/local operation and does not create extra inter‑warp waits or unpredictable data‑dependent divergence that would defeat the WGMMA ↔ softmax overlap, aside from the ordinary dependency waiting for the WGMMA that produced the score tile.

### How does the in-kernel FP8 $\mathbf{V}$-tile transpose via LDSM/STSM work if transpose ops cannot split packed 8-bit pairs?
Question:
For FP8 WGMMA, the paper says only k-major operands are supported, so $\mathbf{V}$ tiles must be transposed in-kernel. The authors use LDSM/STSM, packing two 8-bit values into one 16-bit lane, but mention that the transpose variants cannot split packed 8-bit entries, necessitating register moves between LDSM and STSM. Could someone describe a concrete sequence for one $8\times8$ microtile showing: (1) how bytes are packed for LDSM, (2) what register-level shuffles or byte permutes are applied, and (3) how STSM writes the transposed k-major layout back to SMEM—all without excessive register pressure?
Answer:
Short answer: the kernel treats the $8\times8$ FP8 microtile as an $8\times8$ array of 8-bit values packed into 16-bit lanes so LDSM/STSM can move $128$ bytes at a time. LDSM brings the packed 16-bit lanes into registers unchanged (each 16-bit lane contains two adjacent FP8 bytes that must remain together for the plain LDSM/LDSM-transpose semantics). Because the transpose variants of LDSM/STSM are not allowed to split those packed 8-bit pairs, you must perform a small register-level byte permutation that re-pairs bytes across lanes so that an STSM (which also writes 16-bit lanes) will store the transposed k-major layout. The permutation can be implemented with cheap byte-permute instructions (replicated over the $128$-byte LDSM granule) and done on small sub-blocks so you never blow out register file pressure.

Below I give a concrete, implementable sequence for a single $8\times8$ microtile that follows the paper’s remarks, shows how bytes are packed for LDSM, what register-level permutes are applied, and how STSM writes the transposed k-major layout back to SMEM — and I explain how to keep register pressure low.

1) SMEM layout and LDSM packing (what LDSM actually loads)
Assume the V microtile in SMEM is an $8$ (rows in sequence-length) by $8$ (columns in head-dimension) tile of FP8 values laid out row-major in the original (mn-major) storage. To use LDSM/STSM we pack two adjacent FP8 values into one 16-bit lane so that the hardware’s 16-bit-granularity LDSM can move $128$ bytes = $64$ lanes per warpgroup (but we only illustrate one $8\times8$ microtile).

Concretely, before LDSM the $8\times8$ bytes in SMEM look like (rows $r=0\ldots7$, cols $c=0\ldots7$): $V[r,c]$ (one byte each). We pack horizontally (adjacent columns) into 16-bit lanes:
$lane[r,k] = \{\text{low\_byte} = V[r,2k],\ \text{high\_byte} = V[r,2k+1]\}$ for $k=0\ldots3$.
So each row becomes four 16-bit lanes. LDSM (non-transpose form) will gather a warp’s worth of these 16-bit lanes into registers, preserving the 16-bit lane contents. No splitting of the two bytes in a lane occurs during LDSM.

2) Goal: write the k-major (transposed) tile in SMEM so that later FP8 k-major WGMMA can read it
WGMMA requires the V tile that is contiguous along K (sequence-length) — i.e., we need the tile transposed so that what were rows become columns. But STSM (the store-side instruction) also writes 16-bit lanes; it cannot independently write the low and high bytes to different target 16-bit lanes. Therefore we must rearrange the bytes inside registers so that pairs of bytes that belong together in the target transposed layout share the same 16-bit lane. In other words, we must repack bytes across registers so that each 16-bit lane after the register permute contains the two FP8 elements that STSM will write to the desired transposed positions.

3) Register-level permutation recipe (concrete for $8\times8$)
Work on the $8\times8$ tile by splitting into two $8\times4$ subtiles (each subtile corresponds to the $4$ 16-bit lanes per row loaded by LDSM). This keeps the working set small (a few registers per thread) and avoids excessive register pressure.

Step A — LDSM load:
- Issue LDSM (non-transpose) per the PTX semantics that collectively loads the $8\times4$ 16-bit lanes (for $8$ rows $\times$ $4$ lanes each) into the warp's register file. After LDSM each register lane holds a 16-bit value equal to $\{V[\text{row},2k],V[\text{row},2k+1]\}$.

Index the loaded 16-bit words as $W[r,k]$ with $r=0\ldots7$, $k=0\ldots3$, where $W[r,k] = [\text{byte0} = V[r,2k],\ \text{byte1} = V[r,2k+1]]$.

Step B — form the transposed pairing with byte-permute:
- The transposed $8\times8$ tile needs to produce, for each target row $t$ ($0\ldots7$) and target pair index $p$ ($0\ldots3$), a 16-bit lane containing $\{V[2p,t],V[2p+1,t]\}$ or equivalent depending on the exact interleaving chosen for k-major WGMMA. (The paper shows an example permutation pattern that reorders sequence of bytes per 8-byte chunk to $\{d0,d1,d4,d5,d2,d3,d6,d7\}$.)

- Implement a register byte-permute sequence that, within each $64$-bit or $128$-bit register group, takes bytes from $W[\cdot,\cdot]$ and arranges them into lanes matching the desired output pairs. Practically on Hopper this uses instructions that can permute bytes within $128$-bit lanes (a small sequence of PTX SASS byte permutes or bitwise unpack/interleave ops). A minimal, practical implementation is:

  1. Use 16-bit unpack/interleave (e.g., pairwise unpack low/high) between registers holding adjacent rows to move low bytes into the same register word as low bytes of other rows. This step is repeated in a small tree to group bytes by target column.
  2. Use byte-level permute (PRMT or a sequence of SHFL/B.Y) to finalize the ordering inside each 16-bit word so that each word contains exactly the two FP8 bytes that must be written together by STSM.

Concretely: first do pairwise interleaves between rows $[0,1]$, $[2,3]$, $[4,5]$, $[6,7]$ to build groups; then interleave those groups to gather column-wise bytes; finally re-pair odd/even bytes to produce words $[V[0,t],V[1,t]]$, $[V[2,t],V[3,t]]$, etc. Replicate this whole permutation pattern over the $4$ lane indices $k=0\ldots3$. The permutation pattern the authors mention — changing the order to $\{d0,d1,d4,d5,d2,d3,d6,d7\}$ — is exactly this gather-by-column grouping expressed at byte granularity, and it is repeated every $8$ bytes (i.e., per $64$-bit lane), so you implement it once and it applies across the loaded $128$-byte block.

Step C — STSM store (transposed write):
- After the byte-permute, each 16-bit register lane now contains the two FP8 bytes that must be stored together in SMEM at the position corresponding to the transposed (k-major) layout. Issue STSM (transpose-enabled variant) which writes the register lanes back to shared memory. Because we prepared the 16-bit lanes correctly, STSM can write them without needing to split any bytes. The result in SMEM is the $8\times8$ tile in k-major (transposed) layout and ready for FP8 WGMMA.

4) Why two-byte packing + byte-permute rather than splitting the lanes
The constraint in the paper is that the transpose variants of LDSM/STSM cannot split 8-bit pairs packed into 16-bit lanes. If you attempted to rely on an LDSM-transpose that would send individual bytes to different registers, the hardware forbids splitting a 16-bit word’s bytes into two separate 16-bit destinations. So the only way to realize the logical transpose is to accept that LDSM will bring pairs together, then perform explicit register-level re-pairing so that STSM will write the proper 16-bit pairs corresponding to the transposed positions.

5) Keeping register pressure low
Do the whole operation on $8\times4$ subtiles (i.e., process half the microtile at a time), reuse the same small set of registers for the byte permutes, and perform the permute+STSM immediately after each LDSM load. This way you never need to hold both the entire original and transposed $8\times8$ tile in registers simultaneously. The pipeline in the paper exploits that you can perform the in-kernel transpose in the producer warpgroup and do it in the “shadow” of two WGMMAs — that is, schedule the LDSM + byte-permute + STSM so it runs while other warpgroups are executing matmuls. Also, use the lane-replicated permutation pattern (the same per-$8$-byte pattern repeated) so the implementation uses a very small, fixed sequence of permute/unpack instructions rather than a large general-purpose permute table. These choices keep the extra register cost to a few registers per thread and avoid spills.

6) Example pseudo-layout map (compact view)
- Before LDSM: SMEM rows $r$, cols $c$ are bytes $V[r,c]$.
- LDSM (per row) gives registers $R[r,k] = [V[r,2k], V[r,2k+1]]$ — four 16-bit words per row.
- Byte-permute across $R[0\ldots7,*]$ reorganizes bytes to produce registers $S[t,p] = [V[2p,t], V[2p+1,t]]$ in the order expected by STSM to place them in SMEM at (transposed) positions ($t$ is the new row index in k-major).
- STSM writes $S$ back to SMEM; the result is $V$ transposed, contiguous along $K$ (k-major) for WGMMA.

Conclusion
The kernel therefore uses LDSM to load $8\times4$ 16-bit lanes per row (preserving packed FP8 pairs), performs a tiny register-level byte-permute tree that re-pairs bytes into the 16-bit lanes required by the STSM transpose store, and then issues STSM to write the k-major tile. Doing it on half-tiles and immediately storing the result keeps register usage small; repeating the same per-$8$-byte permutation pattern makes the code compact and efficient. This is exactly the strategy summarized in the paper: pack two 8-bit FP8 values into 16-bit lanes for LDSM/STSM, use byte-permute instructions to rearrange pairs in registers (because LDSM/STSM cannot split pairs), and then STSM writes the transposed k-major layout back to SMEM so FP8 WGMMA can consume it.

### Accumulator/operand layout mismatch for FP8 WGMMA: how do the byte-permute reorderings preserve correctness?
Question:
The paper notes that FP8 WGMMA's FP32 accumulator register layout differs from the FP8 operand-A layout, so they byte-permute the accumulator (e.g., reordering bytes from d0 d1 d4 d5 d2 d3 d6 d7, then repeating every 8 bytes) to make it a valid operand to the next FP8 WGMMA. They then also permute rows of the $\mathbf{V}$ tile to compensate. Could someone explain: (1) why Hopper exposes these two different register layouts, (2) how the specific byte-permute maps columns of the logical $\mathbf{P}$ tile, and (3) how matching the $\mathbf{V}$ row permutation recovers the original matrix product $\mathbf{P}\mathbf{V}$ exactly?
Answer:
Short answer: Hopper’s WGMMA exposes different in-register packings for (a) the FP32 accumulator produced by an FP8 WGMMA and (b) the FP8 operand layout that the next FP8 WGMMA expects, because of how the hardware tiles/ packs bytes for accumulator vs operand reads. The byte-permute is simply a fast in-register reindexing that turns the accumulator’s flattened storage into the operand’s flattened storage; that reindexing permutes the logical columns of the produced P tile. If you apply the identical permutation to the rows of the corresponding V tile (i.e., multiply V on the left by the same permutation matrix), then algebraically $P_{\text{permuted}} \cdot V_{\text{permuted}} = P \cdot V$, so the final product is unchanged. Below I expand each point a bit more intuitively and with the simple math that makes correctness immediate.

1) Why Hopper exposes two different layouts
Hopper’s WGMMA/TF cores internally pack elements differently depending on the role: when the unit accumulates an FP8 GEMM it lays out the FP32 accumulator words in registers in one packing pattern (optimized for accumulation, lane mapping, etc.), whereas when the unit reads an FP8 operand from registers/shared memory it expects the bytes in a different packing (the k-major constraint and the operand tiling). This is a hardware/ABI choice: one layout is the natural order in which partial sums are produced by the accelerator, the other is the natural order the next WGMMA expects for its input operand (especially for FP8 where operands are packed tightly and the instruction assumes a particular inner-contiguity / k-major ordering). The upshot: you cannot directly feed the raw accumulator register contents of one FP8 WGMMA into the next FP8 WGMMA without rearranging bytes.

2) How the byte-permute maps columns of the logical P tile
Think of the produced P tile (a small dense matrix) being stored in registers in flattened order. The byte-permute sequence given in the paper — e.g. reorder bytes in each 8-byte chunk as $\{d0\ d1\ d4\ d5\ d2\ d3\ d6\ d7\}$ and repeat every 8 bytes — is an in-register reindexing of that flattened sequence. Flattening maps 2D indices (row, column) to a linear register order; the byte-permute therefore induces a permutation $\pi$ on the column indices of the logical P tile (or on small subgroups of columns depending on tile packing). Concretely, if the original flattening stored columns in order 0,1,2,3,4,5,6,7, the permute will produce the stored order 0,1,4,5,2,3,6,7 (as the example shows for an 8-byte group). Interpreting the permuted registers as the operand for the next WGMMA is equivalent to saying “we now treat column 2 and 3 of P as being swapped into the positions that operand-reading expects,” i.e. the byte-permute maps logical columns into the operand’s required positions. The paper’s example “columns 0 1 8 9 become the first four columns” is of this same nature but applied to the particular tile shape and packing used: the byte permutation groups and reorders subcolumns so that the operand layout constraint is satisfied.

3) Why permuting V’s rows recovers the original product P V exactly
Let $\Pi$ be the permutation matrix that represents the byte-permute acting on the columns of P. After the byte-permute we effectively have $P_{\text{permuted}} = P \Pi$ (columns of P permuted by $\Pi$). To keep the value of the matrix product unchanged we must supply V to the second GEMM in a correspondingly permuted form. If we permute the rows of V by the same $\Pi$, i.e. $V_{\text{permuted}} = \Pi^T V$ (note $\Pi$ is a permutation matrix so $\Pi^{-1} = \Pi^T$), then

$P_{\text{permuted}} \cdot V_{\text{permuted}} = (P \Pi) \cdot (\Pi^T V) = P (\Pi \Pi^T) V = P I V = P V$.

So algebraically the permutation cancels out: permuting columns of P and the matching rows of V by inverse permutations leaves the product unchanged. In practice the implementation does exactly this: the accumulator (which contains P in the hardware’s accumulator packing) is byte-permuted so it becomes a legitimate operand for the next FP8 WGMMA, and the in-kernel transpose of the V tile is arranged to apply the matching row permutation so the second GEMM computes the same logical $P \cdot V$ output.

Intuition summary: the hardware’s different packing rules mean “what a WGMMA writes in registers” ≠ “what the next WGMMA reads as an operand.” Byte-permute is a cheap local reindexing that converts between these two flattened orders. That reindexing permutes P’s columns; if you apply the inverse permutation to the rows of V, the permutation effects cancel and the mathematical product is identical. The paper implements the V-row permutation by arranging the in-kernel transpose/write so no expensive cross-thread shuffles are needed, keeping the whole flow efficient.

### Block quantization math: how are per-block FP8 scales folded into the attention computation without extra FLOPs?
Question:
The FP8 path uses per-block scales for $\mathbf{Q}, \mathbf{K}, \mathbf{V}$ (block quantization). Suppose $\mathbf{Q}_b = s_Q^{(b)}\,\hat{\mathbf{Q}}_b$ and $\mathbf{K}_c = s_K^{(c)}\,\hat{\mathbf{K}}_c$ for blocks $b,c$, with hats denoting FP8-quantized integers. Then a score block is $\mathbf{S}_{bc} = \alpha\, s_Q^{(b)} s_K^{(c)}\, \hat{\mathbf{Q}}_b \hat{\mathbf{K}}_c^\top$. How are these scales incorporated into: (1) the stable-softmax running $m_i,\ell_i$ updates, and (2) the $\mathbf{O}$ accumulation with $\mathbf{V}$ (which itself has per-block scale $s_V^{(c)}$), without adding extra GEMMs or elementwise passes? A small worked example over two K/V blocks would be great.
Answer:
Short answer: the per-block FP8 scales are multiplied into the operands (or into the FP32 interpretation of the FP8 operands) so that every GEMM/WGMMA produces already-scaled score and contribution blocks. Once the blockwise scale is folded into the GEMM inputs, the running stable-softmax quantities $m_i$ and $\ell_i$ and the accumulation of $O$ are updated exactly as in the usual FlashAttention local-softmax algorithm — no extra GEMMs or full-array elementwise passes are needed because the only extra arithmetic is a small number of scalar multiplies (one per block or one per row of the block) done in registers.

Why this is possible (intuitive + algebra). Write the FP8-block decompositions
$Q_b = s_Q^{(b)} \cdot \hat Q_b$, $K_c = s_K^{(c)} \cdot \hat K_c$, $V_c = s_V^{(c)} \cdot \hat V_c$,
and let $\alpha$ be the usual attention scale. The (row-block, col-block) score block computed in exact arithmetic is

$S_{bc} = \alpha \cdot Q_b K_c^T = \alpha \cdot s_Q^{(b)} s_K^{(c)} \cdot ( \hat Q_b \hat K_c^T )$.

Define the single scalar per-score-block
$\gamma_{bc} := \alpha \cdot s_Q^{(b)} s_K^{(c)}$.
Then the score block is $S_{bc} = \gamma_{bc} \cdot \hat S_{bc}$ where $\hat S_{bc} := \hat Q_b \hat K_c^T$ (the integer/FP8-GEMM result before accounting for scales).

The key implementation point in FlashAttention-3 is to fold $s_Q^{(b)}$ and $s_K^{(c)}$ into the GEMM pipeline so that the hardware’s GEMM/dequantization step produces $\gamma_{bc} \cdot \hat S_{bc}$ directly (or produces $\hat S_{bc}$ and then immediately multiplies the small block by $\gamma_{bc}$ in registers as part of the same producer/consumer microkernel). Concretely, on Hopper you can arrange for the FP8→FP32 operand interpretation or the post-GEMM accumulation layout to apply the scalar factor per block; therefore WGMMA produces $S_{bc}$ already scaled by $\gamma_{bc}$, without issuing a separate GEMM or a large elementwise pass over the block in global memory.

How the folded scale is used in the stable softmax running updates. FlashAttention’s fused (local) softmax maintains for each query row a running maximum $m_i$ and running normalizer $\ell_i$ (accumulated row-sum of exponentials in the numerically-stable formulation). Suppose we process two key/value blocks $c=1$ and $c=2$ for a fixed query block $b$ (query-block index suppressed). Let the two score blocks coming out of the GEMM be

$S^{(1)} = \gamma^{(1)} \cdot \hat S^{(1)}$,    $S^{(2)} = \gamma^{(2)} \cdot \hat S^{(2)}$.

The stable-softmax update for processing block $j$ (general block) is

$m_{\text{new}} = \max(m_{\text{old}}, \operatorname{rowmax}(S^{(j)}))$,
$\tilde P^{(j)} = \exp(S^{(j)} - m_{\text{new}})$,
$\ell_{\text{new}} = \exp(m_{\text{old}} - m_{\text{new}}) \cdot \ell_{\text{old}} + \operatorname{rowsum}(\tilde P^{(j)})$.

Because $S^{(j)}$ already equals $\gamma^{(j)}\cdot\hat S^{(j)}$, the code just computes $\operatorname{rowmax}(S^{(j)})$ etc. directly on the small block that sits in registers/SMEM. There is no need for extra GEMMs: the scalar $\gamma^{(j)}$ was applied before or during the GEMM result write, so the max and exp see the correct scaled values and the running $m, \ell$ math is identical to the FP16 path. The only extra arithmetic is computing $\gamma^{(j)}$ (a product of three scalars $\alpha, s_Q^{(b)}, s_K^{(c)}$) and using it to interpret the GEMM outputs; computing or loading $\gamma^{(j)}$ is $O(1)$ per block and done in registers.

How the folded scales are used in $O$ accumulation with $V$ having its own scale. The output accumulation for block $j$ in the standard local-softmax algorithm is

$O \leftarrow (\text{rescale previous } O) + P^{(j)} V^{(j)}$.

With the block scales, $P^{(j)} =$ softmax rows of $S^{(j)} = \text{softmax}(\gamma^{(j)}\cdot\hat S^{(j)})$, while $V^{(j)} = s_V^{(j)} \cdot \hat V^{(j)}$. So the contribution to $O$ from block $j$ is

$\Delta O^{(j)} = P^{(j)} V^{(j)} = s_V^{(j)} \cdot ( P^{(j)} \cdot \hat V^{(j)} )$.

Again we can fold $s_V^{(j)}$ into the GEMM that computes $P^{(j)}\cdot\hat V^{(j)}$ by applying $s_V^{(j)}$ at the time the $\hat V^{(j)}$ tile is dequantized into FP32 (or by multiplying the small RS-GEMM accumulator by $s_V^{(j)}$ before writing back). The RS-GEMM therefore produces $\Delta O^{(j)}$ already scaled by $s_V^{(j)}$; no extra full-array elementwise multiply is needed. The only extra arithmetic is the scalar multiply by $s_V^{(j)}$ done on the RS-GEMM accumulator (again $O(1)$ per block, done in registers).

Worked numeric-style example with two K/V blocks (concise). Fix a single query row (so row indices simplify). Let $\alpha = 1$ for clarity. Query block $b$ produces $s_Q^{(b)} = 0.1$, key/value blocks $c=1,2$ have $s_K^{(1)}=2.0$, $s_V^{(1)}=0.5$ and $s_K^{(2)}=0.25$, $s_V^{(2)}=4.0$. The scalar score-factors are

$\gamma^{(1)} = \alpha\cdot 0.1\cdot 2.0 = 0.2$,    $\gamma^{(2)} = \alpha\cdot 0.1\cdot 0.25 = 0.025$.

Suppose the integer-GEMM outputs (the dequantized-by-hardware $\hat S$ blocks) are

$\hat S^{(1)} = [10, 2]$,    $\hat S^{(2)} = [6, 8]$

(2 columns = two keys in each block for this toy row). The GEMM that is set up to fold scales returns

$S^{(1)} = \gamma^{(1)}\cdot\hat S^{(1)} = 0.2\cdot[10,2] = [2.0, 0.4]$,
$S^{(2)} = \gamma^{(2)}\cdot\hat S^{(2)} = 0.025\cdot[6,8] = [0.15, 0.20]$.

Process block 1 first with initial $m_{\text{old}} = -\infty$, $\ell_{\text{old}} = 0$:

$m_1 = \max(-\infty, \operatorname{rowmax}(S^{(1)})) = 2.0$.
$\tilde P^{(1)} = \exp(S^{(1)} - m_1) = \exp([0, -1.6]) = [1, e^{-1.6}]$.
$\ell_1 = 0 + (1 + e^{-1.6})$.

When accumulating $O$, the RS-GEMM for block 1 uses the already-folded V scale $s_V^{(1)}$: if $\hat V^{(1)}$ tile is (small) $[v_1, v_2]$, the RS-GEMM returns $\Delta O^{(1)} = P^{(1)}\cdot(s_V^{(1)}\cdot\hat V^{(1)})$ directly ($s_V^{(1)}$ was folded into V dequantization/GEMM). No extra elementwise multiply over the whole block is necessary.

Now process block 2:

$m_2 = \max(m_1, \operatorname{rowmax}(S^{(2)})) = \max(2.0, 0.20) = 2.0$ (no change).
$\tilde P^{(2)} = \exp(S^{(2)} - m_2) = \exp([0.15-2.0, 0.20-2.0]) = \exp([-1.85, -1.8])$.
$\ell_2 = \exp(m_1 - m_2)\cdot \ell_1 + \operatorname{rowsum}(\tilde P^{(2)})$. Since $m_1==m_2$ here, $\exp(0)\cdot \ell_1 = \ell_1$.
Finally, RS-GEMM for block 2 provides $\Delta O^{(2)} = P^{(2)}\cdot(s_V^{(2)}\cdot\hat V^{(2)})$ already scaled by $s_V^{(2)}$.

All scalar multiplications by $\gamma^{(j)}$ or $s_V^{(j)}$ are either (a) applied as part of FP8→FP32 operand interpretation before GEMM or (b) applied to the small per-block accumulators in registers immediately after GEMM. There is no need for extra global GEMMs or full-block elementwise passes.

In short: multiply the three per-block scalars into the GEMM/dequantization pipeline so the GEMM outputs are already in the correct scaled FP32 domain. Then the stable-softmax $m_i, \ell_i$ updates and the RS-GEMM accumulation of $O$ proceed unchanged and entirely locally (in registers/SMEM), so you get correct scaled attention with only $O(1)$ extra scalar operations per block (in registers) and without extra GEMMs or large elementwise passes. This is exactly the “scale each block of $S$ to account for block quantization at no computation cost” idea described in the paper.

### Incoherent processing: is the random orthogonal matrix $\mathbf{M}$ fixed per head/layer or per block, and how is it stored/applied efficiently?
Question:
To reduce outlier-induced quantization error, the paper multiplies $\mathbf{Q}$ and $\mathbf{K}$ by a random orthogonal matrix $\mathbf{M}$ (Hadamard times random signs), exploiting $(\mathbf{Q}\mathbf{M})(\mathbf{K}\mathbf{M})^\top = \mathbf{Q}\mathbf{K}^\top$. Practical questions: (1) Is $\mathbf{M}$ fixed per layer and head, or randomized per sequence/minibatch, or even per block? (2) How is $\mathbf{M}$ stored (full matrix vs. implicit Hadamard/sign seeds)? (3) Is $\mathbf{M}$ fused with rotary embedding in practice, and does this fusion complicate training/backprop (e.g., gradients through $\mathbf{M}$ are trivial, but does it affect caching or recomputation)?
Answer:
Short answer: the paper treats the orthogonal mixer $M$ as an inexpensive, deterministic transform that is applied when preparing $Q/K$ blocks for block-wise FP8 quantization; it is implemented implicitly (Hadamard $\times$ random sign diagonals) and fused with the pre-attention preprocessing (e.g., rotary embedding). $M$ is not stored as a dense $d\times d$ matrix and it is not a trainable parameter, so backprop/caching work the same as for any fixed linear preprocessing — you must ensure you use the same $M$ whenever you reuse cached $K/V$.

Explanation and practical details (grounded in the paper)

What $M$ is and why it’s used
The paper uses incoherent processing: before quantizing $Q$ and $K$ into FP8, they premultiply them by a random orthogonal matrix $M$ so that quantization errors from outliers are spread across coordinates. Because $M$ is orthogonal, the attention product is unchanged:
$(QM)(KM)^T = QK^T$.
So $M$ is a deterministic linear preprocessing step whose only role is to improve quantization behavior, not to introduce new learned parameters.

How often $M$ is chosen / applied
The text describes choosing $M$ as “the product of random diagonal matrices of $\pm 1$ and a Hadamard matrix” (the standard randomized Hadamard construction used in prior work). The paper does not propose re-sampling a new $M$ per minibatch or per iteration; instead it emphasizes fusing $M$ with other preprocessing (rotary, block quantization) and computing it cheaply. Practically this implies $M$ is fixed for the run (or at least fixed for a head/layer configuration), not randomized every sequence. You can implement different granularities (per-head, per-layer, or per-run), but the paper’s design assumes a fixed, cheaply-applied $M$ per channel/head so that the same transform is consistently applied to $Q$ and $K$ that will be compared/ cached.

How $M$ is stored and applied efficiently
The paper explicitly uses the structured construction $M = D_1 H D_2 \dots$ (Hadamard times random sign diagonals). That gives two practical benefits mentioned in the paper:

1) Storage: you do not store a full $d\times d$ matrix. You only need the random sign vectors (the diagonal $\pm 1$ masks) and knowledge of the Hadamard; that is $O(d)$ storage (or just a seed to regenerate signs), not $O(d^2)$.

2) Application cost: multiplying by $H$ (Walsh–Hadamard) can be done by the fast Walsh–Hadamard transform (FWHT) in $O(d\log d)$ time and multiply-by-signs is $O(d)$. The paper states this can be fused with the rotary embedding and with block quantization so it costs essentially nothing extra in the kernel that already touches those elements. So the implementation applies $M$ implicitly via sign flips and an FWHT-style flow rather than materializing $M$.

Fusion with rotary embedding, and effect on training / caching
The paper says explicitly that $M$ “can also be fused with the rotary embedding at no extra computation cost.” Concretely, when you already perform the rotary embedding (or other per-token linear preprocessing) you can combine the few register-level operations needed for rotary with the sign multiplications and the Hadamard steps (or reorder/nest them) inside the same kernel. That fusion means:

- No additional parameter to learn: $M$ is fixed and not trainable. Gradients flow through it like through any fixed linear transform. That is, if $x_{\text{out}} = (xM)$ is used in loss computations, autograd will compute gradients $\frac{dL}{dx} = \left(\frac{dL}{d(xM)}\right) M^T$. Because $M$ is orthogonal, numerical behavior is stable, but there are no trainable params to update.

- Backprop is trivial in the sense that the framework computes linear backward operations (or you recompute the forward transform in the backward kernel). There is no optimization complication because $M$ is fixed.

- Caching/inference: if you cache keys/values across tokens (in autoregressive inference), you must ensure consistency: either cache the transformed $K/V$ (i.e., store $KM$ and $V$ unchanged), or cache untransformed $K/V$ and reapply $M$ when you read them. Because $M$ application is cheap (FWHT + sign), you can choose either; the paper suggests fusing $M$ into preprocessing so the transformed blocks are what the attention kernel sees (so caching stores already-transformed blocks). The only practical requirement is to use the same $M$ seed for all blocks you will compare/cross-attend to (so the identity $(QM)(KM)^T = QK^T$ holds across cached segments).

Other implementation notes and tradeoffs
- Per-head vs per-layer vs per-block: the paper’s description and prior work it cites (Chee et al., Tseng et al.) use a fixed randomized orthogonal transform per head (or per projection) so that the mixing is consistent across all tokens for that head. You could choose to vary $M$ per block, but that adds bookkeeping (must apply the same $M$ to the corresponding $Q$ and $K$ blocks to preserve equality) and gives little extra benefit versus the structured sign+Hadamard version. The paper implies the practical and common choice is a fixed $M$ per head (or per projection), applied block-wise when encoding tiles for FP8 quantization.

- Memory vs compute: storing just sign vectors + using an in-kernel FWHT avoids the enormous memory cost of a full dense $M$. The paper also emphasizes fusing $M$ with rotary + block quantization so there’s no extra read/write to HBM.

- Gradients and recomputation: since $M$ is fixed, there is no parameter update and no special gradient numerics beyond multiplying by $M^T$ in the backward pass; if you cache transformed $K/V$ you avoid recomputing $M$ during inference; during training if you recompute (e.g., for checkpointing) it’s cheap.

Summary recommendation
Follow the paper’s approach: use the Hadamard $\times$ sign diagonal structure, store only sign vectors (or a seed), apply $M$ implicitly with FWHT fused into the rotary / quantization preprocessing. Use a fixed $M$ per head/projection across training and inference so caches remain consistent. This gives the quantization robustness the paper reports while adding negligible storage and compute overhead and no complication to backprop (since $M$ is fixed and linear).

### How do you pick $B_r$ and $B_c$ given the extra registers for $\mathbf{S}_{\mathrm{next}}$ in the 2-stage pipeline?
Question:
Algorithm 2 needs to keep an additional $\mathbf{S}_{\mathrm{next}}$ tile in registers to overlap softmax with GEMM, which increases register pressure by roughly $B_r \times B_c \times \mathrm{sizeof}(\text{float})$ per CTA (plus per-thread fragmentation). On Hopper, what heuristics do you use to pick $B_r$ (query rows per tile) and $B_c$ (key/value rows per tile) so that: (1) no spilling occurs, (2) occupancy is not crippled by setmaxnreg allocations to consumer warps, and (3) Tensor Cores remain fed? Any guidance for head dimensions $d\in\{64,128,256\}$?
Answer:
Short answer: treat the extra-registers cost of the 2‑stage pipeline (the live tile $S\_{{next}}$ of size $B\_r \times B\_c$ floats) as a hard budget you must fit under the per‑thread register limit and the dynamic reallocation window used by setmaxnreg. Pick $B\_r$ and $B\_c$ so that (a) the live $S\_{{next}}$ plus the other per‑thread register needs do not force spill, (b) you leave headroom for setmaxnreg to give consumer warps more registers, and (c) your tile sizes are multiples/aligned to Tensor‑Core/warp‑matrix granularities so each WGMMA sees enough work. Concretely, start with modest $B\_r$ (few query rows per tile) and make $B\_c$ the larger dimension (many key/value rows per tile) so that math intensity of the two GEMMs stays high while $S\_{{next}}$ remains small, and tune by profiling. Below I give the intuition, the constraints to check, and concrete starting choices for $d=64$, $128$, $256$.

Why this matters (intuition). The 2‑stage pipeline overlaps a future SS‑GEMM producing $S\_{{next}}$ with the current RS‑GEMM and the softmax. To break the dependency you must keep $S\_{{next}}$ live in registers; that costs roughly $B\_r \times B\_c$ floats per CTA (plus fragmentation into per‑thread slots). Registers are precious on Hopper: the paper uses dynamic register (re)allocation via setmaxnreg so producer warps can give up registers and consumer warps can get more. If you pick $B\_r$ and $B\_c$ too large, either you will (i) spill registers to local memory (huge slow down), or (ii) force setmaxnreg to favor the consumer warps so strongly that occupancy (number of active warps/warpgroups) collapses. Conversely, too small tiles under‑utilize Tensor Cores and lose TFLOPs.

Concrete constraints to enforce (what to check while tuning)
1. Per‑thread register budget: The hardware per‑thread register limit (the paper cites up to $256$ registers per thread) is an absolute ceiling. From the compiler (or SASS dump) collect the baseline register use per thread without $S\_{{next}}$; then ensure the additional per‑thread registers implied by $S\_{{next}}$ do not push any thread beyond a safe margin (see next point).
2. Headroom for setmaxnreg/occupancy: You must leave slack so consumer warps can be granted extra registers without killing occupancy. Practically, keep total register usage per thread noticeably below the $256$ limit (e.g., a margin of $\sim 10$–$20\%$) so setmaxnreg can increase consumer warps’ allocation without collapsing the number of resident CTAs/warpgroups. If you can only give consumers registers by reducing other warps to a single‑thread TMA producer role, that’s fine, but avoid configurations where the only way to get enough registers is to drop to one active CTA per SM.
3. Tensor‑Core granularity and arithmetic intensity: Choose $B\_c$ so that each WGMMA operates on $K$ length that is a multiple of the Tensor‑Core/minor‑tile size (use multiples of $8$, $16$, $32$ as appropriate) and so that the GEMM has enough FLOPs to amortize the softmax work. For FP8 you can be more aggressive with $B\_c$ because matmul throughput doubles, so you want larger $B\_c$ to keep Tensor Cores busy.
4. SMEM / TMA interaction: $B\_c$ and $B\_r$ must fit the shared memory buffering (the s‑stage circular buffer) used by TMA; the paper already balances s, SMEM size and these tiles. If your $B\_c$ grows, ensure the corresponding shared memory tile fits in the configured buffer stage.

How to translate $S\_{{next}}$ into per‑thread registers (practical rule of thumb)
$S\_{{next}}$ costs $B\_r \times B\_c$ floats per CTA. Divide that by the number of threads in the CTA to get a rough per‑thread register increment (add a little for fragmentation and any register layout padding). For example, with $128$ threads per CTA, each thread will hold roughly $\frac{B\_r \times B\_c}{128}$ floats for $S\_{{next}}$. Convert floats to registers (on Hopper a float usually occupies one 32‑bit register slot). Add this to the existing per‑thread register use reported by the compiler; if it crosses the safe threshold you will see spills.

Practical tuning procedure (fast, iteration‑based)
1. Compile the kernel and inspect the compiler's reported per‑thread register usage without $S\_{{next}}$ and with trial $S\_{{next}}$ sizes (or check SASS). 2. Run with nvprof / nsight or the CUTLASS profiling hooks and watch for register spills (local memory traffic) and occupancy (active CTAs per SM). 3. If spills occur, reduce $B\_r$ first (it reduces $S\_{{next}}$ linearly), then $B\_c$. If occupancy collapses due to setmaxnreg, reduce baseline per‑thread registers by shrinking other arrays or reduce $B\_r$, or reduce the number of consumer warps so setmaxnreg rebalancing is less aggressive. 4. Check that WGMMA throughput is high (no Tensor‑Core underutilization). If Tensor Cores are starved, increase $B\_c$ in steps aligned to TC tile sizes.

Recommended starting tiles (empirical heuristics grounded in the paper’s tradeoffs)
- $d = 64$: head dim is small so GEMMs are less heavy per row. Start with $B\_r = 16$–$32$ and $B\_c = 128$–$192$. These keep $S\_{{next}}$ modest while giving enough $K$ columns to feed Tensor Cores.
- $d = 128$: the paper often reports strong gains at hdim = $128$; start with $B\_r = 32$–$64$ and $B\_c = 128$–$256$. This balances register pressure and arithmetic intensity; the paper’s benchmarks (e.g., the $8448$ seqlen, $16$ heads, hdim=$128$ case) are consistent with these mid‑sized tiles that achieved $\sim 600+$ TFLOPs when pipelining was active.
- $d = 256$: head dim is large so each GEMM naturally has more work; prefer smaller $B\_r$ to keep $S\_{{next}}$ small. Start with $B\_r = 16$–$32$ and $B\_c = 192$–$256$ (or $256$). Larger $B\_c$ helps keep Tensor Cores saturated and amortizes softmax, while smaller $B\_r$ bounds register usage.

FP8 note. Because FP8 doubles Tensor‑Core throughput, you should bias towards larger $B\_c$ (more $K$ per iteration) to keep the Tensor Cores busy. However FP8 also forces extra layout/transpose work (in‑kernel transpose with LDSM/STSM) and register permutations of accumulators; that consumes registers and some instruction bandwidth. So for FP8 you may need to reduce $B\_r$ relative to FP16 for the same $B\_c$, or increase the per‑CTA register slack target.

Final practical tips from the paper’s design and results
- Favor making $B\_c$ the larger dimension: it increases math intensity of the GEMMs (better TC utilization) while $S\_{{next}}$ grows only linearly in $B\_r$. - Align $B\_c$ and $B\_r$ to the warp/WGMMA tile sizes (power‑of‑two / multiples of $8$/$16$/$32$) to avoid wasted work and to make LDSM/STSM transposes efficient. - Profile for two failure modes separately: (A) register spilling (look for local memory traffic), and (B) occupancy collapse when setmaxnreg gives too many regs to consumers (watch active CTAs/SM). Solve (A) by shrinking $B\_r$ or $B\_c$; solve (B) by leaving more slack in base register usage or reducing consumer warps per CTA so redistribution is cheaper. - Use the smallest $B\_r$ that still gives good GEMM tiling and enough parallelism in the query dimension; use $B\_c$ large enough to amortize softmax but not so large that the shared memory ping‑pong buffer runs out of stages.

Summary. There is no single universal $(B\_r, B\_c)$ pair — you must balance (register cost of $S\_{{next}}$) vs (Tensor‑Core efficiency). Start with the recommended ranges above, inspect the compiler register counts and runtime profiler for spills/occupancy, and iterate: reduce $B\_r$ first to relieve register pressure, increase $B\_c$ to improve TC utilization (but in multiples matching TC tile sizes), and re‑run until you satisfy (1) no spills, (2) acceptable occupancy with setmaxnreg, and (3) high TC utilization. The ranges for $d=64/128/256$ above are practical starting points consistent with the paper’s emphasis on keeping $S\_{{next}}$ small enough to avoid spilling while retaining enough GEMM work to feed Tensor Cores.

### What exactly is "k-major" for FP8 WGMMA on Hopper, and how do the attention GEMMs map to that constraint?
Question:
The paper states that FP8 WGMMA only supports k-major operands in SMEM. For a GEMM computing $A (M\times K) \times B^\top (N\times K)$, could someone define precisely what "k-major" means in terms of strides and layout? In the attention forward pass: (1) for $\mathbf{Q}\mathbf{K}^\top$ which operand(s) must be k-major, and (2) for $\mathbf{P}\mathbf{V}$, which operand must be k-major? How does this requirement lead to the need to transpose $\mathbf{V}$ tiles in-kernel if inputs are originally contiguous in the head dimension?
Answer:
Short answer: "$k$-major" means "contiguous along the inner ($K$) index of the GEMM". Concretely, for an $M\times K$ matrix stored in row-major order this is true: successive memory addresses change by one element when you move along the $K$ index, and the stride between successive $M$-rows equals $K\times\text{sizeof(elem)}$. FP8 WGMMA on Hopper accepts only operands that are $k$-major when they live in SMEM, so any tile you place into SMEM that will be used by an FP8 WGMMA must be laid out so the $K$ dimension is the contiguous (fastest) stride. Applied to attention:

1) For the SS-GEMM that computes $\mathbf{Q}\mathbf{K}^\top$ (a tile-based GEMM with operands of shapes $A:(B_r\times d)$ and $B:(B_c\times d)$ used as $A\times B^\top$): if both operands are sourced from SMEM (the SS case in the paper) then the SMEM tiles for both $\mathbf{Q}$ and $\mathbf{K}$ must be $k$-major — i.e. contiguous along the head dimension $d$ ($K = d$ in that GEMM). If one operand is in registers (an RS or SR GEMM variant), the restriction only applies to the operand that actually lives in SMEM.

2) For the RS-GEMM that computes $\mathbf{P}\mathbf{V}$ (logical shapes: $\mathbf{P}$ is $B_r\times B_c$ and a $\mathbf{V}$ tile is $B_c\times d$, giving output $B_r\times d$): the $\mathbf{V}$ tile that is loaded into SMEM must be $k$-major with respect to this GEMM’s inner dimension ($K = B_c$). In other words, the copy of $\mathbf{V}$ residing in shared memory must be contiguous along the sequence-length / key-block axis (the $B_c$ axis), not along the head axis.

Why that forces an in-kernel transpose of V tiles when inputs are head-contiguous: typical layouts produced by transformer code store tensors contiguous in the head dimension (i.e., the head/channel index $d$ is the fastest-moving dimension). For the $\mathbf{P}\mathbf{V}$ GEMM the WGMMA expects the SMEM operand corresponding to $\mathbf{V}$ to be contiguous in the inner (sequence) axis $B_c$. TMA loads cannot change which logical axis is contiguous — they move a contiguous region from global memory to SMEM preserving strides — so if $\mathbf{V}$ in global memory is contiguous in head (not in sequence), a direct TMA into SMEM will leave the SMEM tile in the wrong "$$k$$-major" orientation. Therefore you must either (a) pre-transpose $\mathbf{V}$ in global memory so the sequence axis becomes contiguous there, or (b) transpose each tile after loading it into SMEM (in-kernel) so the SMEM layout becomes $k$-major. The paper chooses (b) and implements it efficiently using warp-level matrix load/store (LDSM/STSM) and small register permutations so the tile written into SMEM is contiguous along the GEMM inner ($K$) axis that FP8 WGMMA requires.

A few intuitive wrap-ups and practical notes from the paper: "$k$-major" is purely a stride/layout constraint (which axis is fastest). FP16 WGMMA is flexible (accepts $mn$-major or $k$-major), but FP8 WGMMA is strict and demands $k$-major in SMEM — which is why attention’s natural head-contiguous layout conflicts with the required SMEM layout for the $\mathbf{P}\mathbf{V}$ GEMM and triggers the need for the in-kernel transpose of V tiles (done in producer warps with LDSM/STSM so it can be overlapped with other work).

### What exactly is the FP8 baseline for the 2.6× RMSE improvement claim, and are comparisons apples-to-apples?
Question:
In the numerical error section, the FP8 baseline is described as "per-tensor scaling, with matmul accumulator in FP32 and softmax intermediates in FP16." Meanwhile, FA-3 uses FP8 with block quantization and incoherent processing, and keeps key intermediates in FP32. To fairly interpret the 2.6× RMSE reduction: (1) are both methods using the same FP8 format (e4m3)? (2) Are the same operator precisions used for softmax, rescaling, and epilogue? (3) Is the only change per-tensor vs. per-block scaling and incoherent processing? If there are other differences (e.g., different accumulation or cast policies), can you enumerate them?
Answer:
Short answer: Yes — the FP8 format is the same ($e4m3$) and the baseline and FlashAttention-3 (FA‑3) both use FP32 accumulators for the FP8 GEMMs, but the experiments are not only differing in “per-tensor vs per-block” scaling. FA‑3 changes several operator-precision and implementation choices beyond block quantization, and those other changes are important to interpret the quoted $2.6\times$ RMSE improvement.

Details grounded in the paper

1) FP8 format
The paper explicitly states the FP8 format used is $e4m3$ (“With FP8 ($e4m3$) format…”). The “baseline FP8 attention” used for the numerical-error comparison is standard FP8 attention with per-tensor scaling; FA‑3’s FP8 experiments are also in the FP8 ($e4m3$) setting. So the numeric format ($e4m3$) is the same.

2) Operator precisions (softmax, rescaling, epilogue, accumulators)
The baseline FP8 attention (the comparator used in the numerical-error table) is described as “per-tensor scaling, with matmul accumulator in FP32 and softmax intermediates in FP16.” In contrast, FA‑3 does the following with respect to precisions:

- GEMM operands: quantized to FP8 ($e4m3$) and executed on FP8 Tensor Cores (WGMMA).
- GEMM accumulators: FP32 accumulators for the WGMMA (same as the baseline).
- Softmax and rescaling / key intermediates: FA‑3 keeps key intermediates (softmax-related quantities and rescaling steps) in higher precision — the paper emphasizes that intermediate results (e.g., softmax rescaling) are kept in FP32 for FP16 runs, and for the FP8 algorithm FA‑3 “keeps key intermediates in FP32.” This is a deliberate accuracy-preserving choice compared with the baseline’s use of FP16 for softmax intermediates.
- Epilogue / final scaling: FA‑3 performs block-wise rescaling to account for block quantization; those rescalings are integrated into the fused attention kernel and use FP32 for the reduction/normalization operations.

So, while both approaches use FP8 operands and FP32 accumulators, FA‑3 differs in the precision used to hold and process softmax/rescale intermediates (keeps them in higher precision), whereas the baseline keeps those intermediates in FP16.

3) Is the only change per-tensor vs per-block scaling and incoherent processing?
No. Per-block scaling and incoherent processing are the central numerical-accuracy techniques in FA‑3 and are a major source of the RMSE improvement, but several other implementation/precision/layout differences also matter and are part of the FA‑3 recipe:

- Block quantization (per-block scaling) instead of per-tensor scaling. This reduces quantization error for blocks that contain local outliers.
- Incoherent processing (random orthogonal mixing of $Q$ and $K$ prior to quantization). Multiplying $Q,K$ by an orthogonal transform (Hadamard + sign diagonals) spreads out outliers and substantially reduces the worst-case quantization error; it is lossless for exact arithmetic because $M M^T = I$, but it changes the distribution prior to quantization.
- Higher-precision softmax/intermediate handling. FA‑3 keeps softmax-related intermediates and rescaling state in FP32 (or otherwise higher precision) rather than FP16, which reduces exponential/accumulation error.
- In-kernel layout transforms and register shuffles needed by FP8 WGMMA. FP8 WGMMA requires k-major operand layout and the FP32-accumulator/FP8-operand layout conventions differ. FA‑3 performs in-kernel transposes of V tiles (via LDSM/STSM) and register permutations (byte permutes) to match the required layouts while avoiding extra global-memory transposes. Those transformations affect where casts happen and how partial results are stored/ordered, which in turn affect rounding behavior and error accumulation.
- Epilogue and rescaling per block. Because quantization is block-wise, FA‑3 applies block-wise scaling compensation in the epilogue (and integrates that into the local softmax reductions), rather than a single tensor-wide scale as in the baseline.
- Casting/convert points: FA‑3 inserts casts between FP8 operands, FP32 accumulators, and FP32 softmax state at different points than the baseline (e.g., it keeps certain reductions in FP32 before converting back), so the rounding noise locations differ.
- Pipeline/overlap and register usage: FA‑3’s 2-stage/3-stage pipelining and warp-specialization require extra register buffering for intermediate tiles (e.g., storing $S_{next}$ in registers). This changes the temporal locality of intermediate values (when and where they are rounded) relative to a simpler implementation, which can alter round-off accumulation even if the nominal precisions match.

Net effect and interpretation of the $2.6\times$ number
Because the format (FP8 $e4m3$) and the FP32 accumulators are the same between baseline and FA‑3, the comparison is meaningful in the sense that both use the same low-precision numerical format and the same accumulator precision for GEMM. However, FA‑3 improves accuracy by a combination of (A) block quantization, (B) incoherent mixing of Q/K prior to quantization, and (C) keeping softmax/rescale intermediates in higher precision plus block-aware epilogue corrections and careful in-kernel layout/permute handling. The $2.6\times$ RMSE improvement is therefore not attributable solely to switching from per-tensor to per-block scaling: incoherent processing and the higher-precision handling of softmax/rescaling (and the epilogue/block compensation) are key contributors.

If you want an apples-to-apples micro-ablation, the paper’s numerical-error section and ablation discussion imply you would need to compare (i) baseline per-tensor scaling + FP16 softmax intermediates, (ii) per-block scaling only, (iii) per-block scaling + incoherent processing, and (iv) per-block + incoherent + FP32 softmax intermediates / epilogue, to isolate the individual contributions. The paper reports the combined effect (block quant + incoherent processing + higher-precision intermediates) yielding the $2.6\times$ reduction.

Summary
Both methods use FP8 $e4m3$ and FP32 GEMM accumulators, so the format/accumulator comparison is consistent. But FA‑3 also changes (and documents changing) the softmax/intermediate precisions, the quantization granularity, the preprocessing (incoherent mixing), and the kernel layout/cast policies. Those additional changes—especially block quantization + incoherent processing and keeping softmax state in FP32—are essential to reach the reported $2.6\times$ RMSE improvement; the comparison is meaningful, but it is not a single-variable comparison of only “per-tensor vs per-block” scaling.

### Why is forward attention FLOPs computed as $4N^2 d H$, and why divide by 2 with causal masking?
Question:
In the benchmarking section, the forward FLOPs are given as $4\cdot \text{seqlen}^2\cdot\text{head dimension}\cdot\text{number of heads}$. Could someone derive this? My attempt: each of the two GEMMs ($\mathbf{Q}\mathbf{K}^\top$ and $\mathbf{P}\mathbf{V}$) costs about $2N^2 d$ per head, summing to $4N^2 d$ per head, then multiply by $H$. With causal masking, about half of the score matrix is not computed, hence divide by 2. Is this precisely correct when using block tiling and triangular masking, or is there a small deviation from exactly half because of tile edges?
Answer:
Your derivation is essentially correct; here is a concise, grounded derivation and the subtleties to watch for.

Cost per head (dense, multiply–add counted as 2 FLOPs)
For one head with sequence length $N$ and head dimension $d$ the two heavy matrix–matrix products are
1) $\mathbf{S}=\mathbf{Q}\mathbf{K}^\top$: $\mathbf{Q}\in\mathbb{R}^{N\times d}$ times $\mathbf{K}^\top\in\mathbb{R}^{d\times N}$ produces an $N\times N$ matrix. A dense GEMM of shape $N\times d$ by $d\times N$ costs about $2N^2 d$ FLOPs (one multiply and one add per inner product element).
2) $\mathbf{O}=\mathbf{P}\mathbf{V}$: $\mathbf{P}\in\mathbb{R}^{N\times N}$ times $\mathbf{V}\in\mathbb{R}^{N\times d}$ produces $N\times d$. That GEMM also costs about $2N^2 d$ FLOPs.

Summing these two dominant GEMMs gives $4N^2 d$ FLOPs per head. Multiplying by the number of heads $H$ yields the paper’s forward FLOPs formula
$$
\text{FLOPs}_{\text{fwd}} \approx 4\,N^2\,d\,H,
$$
which is exactly what the paper uses.

Why divide by 2 with causal masking
Causal masking means query position $i$ only attends to keys $j\le i$. The number of computed score entries becomes
$$
\sum_{i=1}^N i = \frac{N(N+1)}{2} = \frac{N^2}{2} + \frac{N}{2}.
$$
Asymptotically the quadratic term is halved, so the dominant GEMM work is roughly half: replace $N^2$ by $\frac{N^2}{2}$ and you get $\approx 2N^2 d H$. That’s why the paper divides by 2 for causal masking.

Practical caveats (tiling, masking, and lower-order terms)
The formula above is an asymptotic count under the usual assumptions: multiply–adds counted as 2 FLOPs, the softmax/scale/rowmax work is small compared to the GEMMs, and the GEMMs are implemented as dense operations only over the computed entries.

Two practical deviations you should be aware of:

1) Tile-edge effects. In a block/tile implementation (like FlashAttention variants), you operate on tiles of size $B_r\times B_c$. A triangular causal region does not align perfectly with tile boundaries: some tiles will be partially inside the causal triangle and require special handling (you must compute only a triangular subset inside the tile, or compute whole tiles and mask results). That means the actual number of multiply-adds can be slightly larger than the pure triangular count because of partially filled tiles or extra scalar work to prune results. The excess is $O(N\cdot B)$ (linear in $N$ times tile size) not $O(N^2)$, so asymptotically negligible, but it can matter for small or moderate $N$ or large tile sizes. In short: the "divide by 2" is correct asymptotically; exact FLOPs differ by lower-order terms due to tile edges and implementation choices.

2) Other operations are lower-order but present. Softmax (exponentials, reductions, scaling) and the rowmax/row-sum bookkeeping cost roughly $O(Nd)$ or $O(N^2)$ scalar operations with much smaller constant and throughput than Tensor Core GEMMs. The paper treats these as negligible when reporting TFLOPs because the matmuls dominate for large $N$ and typical $d$. Also note that in backward pass accounting the paper multiplies forward FLOPs by 2.5 because there are more GEMMs (5 vs 2) in the backward path.

Summary
The forward FLOPs formula $4N^2 d H$ comes directly from counting two dense GEMMs per head at $2N^2 d$ each. Causal masking halves the quadratic work asymptotically because only about $N(N+1)/2$ score entries are computed, hence the divide-by-2. Tile-based implementations introduce small, lower-order deviations (tile-edge partial tiles, masking overhead), but they do not change the asymptotic halving.

### What is a "persistent kernel" in this context, and why does not having one for FP8 hurt short sequences?
Question:
The discussion notes that FA-3 FP16 uses a persistent kernel and load balancing strategy, while FP8 FA-3 does not, which partly explains worse performance at short seqlens vs cuDNN FP8. Could someone explain what persistent kernels mean here (e.g., CTAs persist and pull multiple tiles/batches to amortize launch/latency), how load balancing is implemented across CTAs/warpgroups, and why the lack of persistence especially penalizes small workloads (e.g., launch overheads, underutilized SMs, poor overlap)?
Answer:
Short answer: in this paper a “persistent kernel” means a kernel that keeps its CTAs (threadblocks) alive on the SMs and has those CTAs pull (or be assigned) multiple tiles / query blocks / batches from an internal work queue instead of doing exactly one fixed, small chunk of work and returning. Persistence amortizes kernel-launch and scheduling overheads, enables dynamic load balancing (CTAs keep working until all tiles are done), and gives more opportunity to hide latency (you can overlap asynchronous TMA loads and WGMMA work across many tiles). FP16 FlashAttention‑3 uses such a persistent design; the FP8 implementation in the paper does not, and that absence explains much of the short‑sequence slowdown versus cuDNN FP8.

Why that matters (intuitively and technically)
- Kernel launch and scheduling overheads are not free. Launch + grid scheduling + CTA-to-SM placement and initial startup cost constitute a fixed latency per grid. When your overall work per CTA is small (short sequence, small number of blocks), that fixed overhead becomes a non‑trivial fraction of runtime. A persistent kernel amortizes that fixed cost because CTAs stay resident and process many tiles sequentially, so the overhead per tile goes down.
- SM utilization and occupancy. If the problem decomposes into only a few tiles (small $N$ or small batch/head count), a non‑persistent kernel that launches exactly one tile per CTA may not fill all SMs or maintain steady instruction-level concurrency on each SM. Persistent CTAs can work through many tiles in a loop, keeping tensor cores busy and letting asynchronous units (TMA and WGMMA) be overlapped smoothly.
- Latency hiding and overlap. FlashAttention‑3 relies heavily on asynchrony: TMA (async shared-memory loads), asynchronous WGMMA (Tensor Core) and separate softmax/exponent units. A persistent CTA that pulls multiple tiles allows long-running producer/consumer pipelines (circular shared-memory buffers, ping‑pong scheduling, intra-warpgroup pipelining) to be sustained across more iterations. If CTAs die quickly because they only did one or two tiles, you lose the amortized benefit of those pipelines — insufficient time to overlap exponential/softmax work against tensor‑core GEMMs.
- Load balancing and dynamic work distribution. With persistence you can implement dynamic allocation of tiles to CTAs (work queues, work stealing or simple atomic counters). That copes with heterogeneity: variable per‑tile cost (edge tiles, padding, causal masking), different resource usage across warpgroups (producer vs consumer), and skew across heads/batches. Without persistence you have to statically assign tiles to CTAs up front; with small numbers of tiles that assignment is coarse and leads to idle SMs when some CTAs finish earlier.
- Underutilization exacerbated by FP8 specifics. FP8 FlashAttention needs extra register juggling, in‑kernel transposes, and layout permutations to conform to FP8 WGMMA operand constraints. Those requirements increase register pressure and limit how many CTAs can be resident simultaneously (reducing concurrency). If you also don’t use a persistent kernel, the fewer CTAs that do run have less ability to amortize the extra per‑tile work (transposes, permutations). Moreover, FP8 doubles Tensor Core throughput vs FP16, so the imbalance between high GEMM throughput and unchanged softmax/special‑function throughput is larger: you need more continuous GEMM work to hide the comparatively slow exponent/softmax units. Persistence helps supply that continuous stream of GEMMs; lacking it, short workloads expose the imbalance and the overheads, hurting latency and throughput versus highly tuned vendor kernels (cuDNN) that do have a persistent design.

Consequence for short sequences
When sequence length is small you have few blocks per query tile. Non‑persistent FP8 kernels therefore:
1. Pay kernel launch / grid scheduling overhead per short job (dominant fraction of total),
2. Have fewer concurrent tiles to keep TMA and WGMMA saturated, so Tensor Cores and TMA are underutilized,
3. Can’t evenly distribute work when some CTAs finish earlier (static assignment leads to idle SMs),
4. Suffer more from register pressure & layout‑transform costs because they can’t amortize those costs across many iterations.

In contrast, a persistent FP16 kernel in the paper keeps CTAs alive, implements circular SMEM buffers, warp‑specialization (producer/consumer warpgroups), ping‑pong scheduling and dynamic tile pulling — all of which amortize startup costs, balance work across CTAs/warpgroups, and sustain overlap between TMA and WGMMA. That is why FP16 FA‑3 shows much better short‑sequence behavior, and why adding a persistent kernel for FP8 (the paper notes this as future work) would likely close much of the gap versus cuDNN for short seqlens.

If you want to experiment: try measuring (a) kernel launch overhead fraction and (b) SM/Tensor‑Core occupancy as you vary sequence length and per‑CTA tile count. If launch overhead and idle SM time are large at small $N$, a persistent kernel + work queue almost always helps.

### How is the in-kernel $\mathbf{V}$-tile transpose overlapped with GEMMs—who issues it and how are dependencies enforced?
Question:
For the FP8 path the paper prefers transposing $\mathbf{V}$ tiles in-kernel using LDSM/STSM, and mentions that after the first iteration the next $\mathbf{V}$-tile transpose can be issued "in the shadow of" the GEMMs on the prior $\mathbf{V}$ and current $\mathbf{K}$. Concretely: (1) is the transpose executed by the producer warpgroup or by the consumer? (2) Which synchronization primitives ensure that the consumer never reads an untransposed $\mathbf{V}$ tile (e.g., separate barriers per stage for $\mathbf{K}$ and $\mathbf{V}$)? (3) How is the circular buffer indexed so that transpose latency is hidden but buffer stages are safely reused?
Answer:
Short answers up front: the in‑kernel FP8 tile transpose is performed by the producer warpgroup, synchronization is enforced by the producer/consumer commit‑notify + per‑stage waits/barriers (the pipeline object and explicit bar.sync semantics), and the circular buffer is indexed with a fixed $s$-stage ring so the producer always writes to stage $(j \bmod s)$ and waits for that stage to be released by the consumer before reusing it — that wait combined with the consumer’s wait-for-load/commit ensures the transpose latency can be hidden while preserving safety.

Explanation (grounded in the paper)

Who issues the transpose (producer or consumer)?
The paper describes doing the LDSM/STSM based transpose in the producer warpgroup. LDSM/STSM are register‑efficient and naturally sit with the producer role (they move tiles from SMEM to RMEM and back) so the producer warpgroup performs the in‑kernel transpose of the next $\mathbf{V}$ tile after it TMA‑loads the tile into SMEM. Concretely, the producer issues the TMA load of $\mathbf{V}_j$ into the buffer stage and then invokes the LDSM/STSM register‑level transpose before “committing” that stage for consumption. This choice avoids cross‑warp register ownership shuffles and keeps the transpose close to the load path, which is what the paper argues is most efficient for FP8.

Which synchronization primitives guarantee the consumer never reads an untransposed tile?
The paper’s software model uses an explicit pipeline object around an $s$-stage circular SMEM buffer with commit/notify semantics plus explicit waits/barriers in the consumer. The primitives that enforce correctness are:

- The producer’s “commit to notify consumers” after the TMA load + in‑kernel transpose. The consumer waits for that commit before reading the tile.
- Per‑stage waits/releases: the producer will wait for the $(j \bmod s)$-th stage to be consumed before issuing a new load into that stage (so the producer cannot overwrite a stage that the consumer still needs).
- Consumer waits for the tile to be loaded (and for the commit) before using it; these are implemented as explicit waits/bar.syncs in the consumer main loop (see lines like “Wait for $\mathbf{K}_j$ to be loaded in shared memory” / “Wait for $\mathbf{V}_j$ to be loaded in shared memory”).
- The paper also uses bar.sync ordering between warpgroups to implement the ping‑pong scheduling (so GEMMs of different warpgroups are ordered to allow softmax work to execute while other warpgroups’ WGMMA runs). In short: commit/notify + per‑stage waits + bar.sync ensure the consumer never reads an untransposed tile.

How the circular buffer is indexed so transpose latency is hidden but stages are safely reused
The algorithm uses an $s$-stage circular SMEM buffer and simple modulo indexing: the producer writes stage index $(j \bmod s)$ for the $j$-th key/value block; the consumer reads from the same $(j \bmod s)$ stage. Safety and latency hiding come from two rules enforced by the pipeline object:

1. The producer never reuses a stage until it observes that the consumer has released that stage (explicit wait on “stage consumed”). That prevents overwriting live data.
2. The consumer never reads a stage until it observes the producer’s commit/notify for that stage (explicit wait on “stage loaded”). That prevents reading untransposed/unloaded data.

Because both loads/transposes and GEMMs are asynchronous (TMA and WGMMA), the producer can start loading/transposing $\mathbf{V}_{j+1}$ into stage $((j+1) \bmod s)$ while the consumer is running the GEMM that uses $\mathbf{V}_j$ and $\mathbf{K}_j$. The paper’s two‑stage pipelining further schedules the consumer so that the GEMM on the current iteration is issued (and runs asynchronously) while the softmax is computed for the previous/next iteration; this overlap hides the transpose/ TMA latency as long as $s$ is large enough to keep the pipeline full and the producer respects the $(j \bmod s)$ reuse waits.

Intuition / small concrete picture
Think of the SMEM buffer as $s$ slots in a ring. Producer: “I will write slot $(j \bmod s)$, transpose it in‑kernel, then mark it ready.” Consumer: “I will wait until slot $(j \bmod s)$ is marked ready, then use it, then mark it free.” The producer will not write to slot $(j \bmod s)$ for a later $j$ until it sees it freed. Because TMA and WGMMA are asynchronous, the producer can be doing the load+transpose for slot $(j+1)$ while the consumer’s WGMMA is using slot $j$, so the transpose cost is executed “in the shadow” of GEMMs. The explicit commit/wait/bar.sync primitives are the semantic glue that prevents races.

Practical notes from the paper
The implementation uses TMA for the HBM → SMEM transfer, LDSM/STSM for the register‑level block transpose in the producer, and WGMMA for asynchronous GEMMs. The paper emphasizes that the producer/consumer commit/wait semantics and explicit barrier (bar.sync) ordering are what make the ping‑pong and intra‑warpgroup overlaps reliable in practice, and that $s$ (the number of SMEM stages) must be chosen so the producer can get ahead enough to hide latency but not so small that a stage would be reused before being released.
