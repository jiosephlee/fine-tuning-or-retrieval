Chapter 8: Putting It Together: Kernel Construction and Practical Tuning on Hopper

# Building blocks: TMA descriptors and launches; WGMMA issue patterns; MFU usage for exp

At the heart of an efficient FlashAttention-3 kernel on Hopper are three primitive capabilities that the implementation must orchestrate: asynchronous block loads via the Tensor Memory Accelerator (TMA), asynchronous matrix‑multiply on Tensor Cores via the warpgroup-wide WGMMA instruction, and the low‑throughput but essential special functions such as exponential executed on the GPU's multi‑function unit (MFU). The algorithmic structure of FlashAttention‑3 is built around issuing these primitives in an overlapping fashion rather than treating them as blocking calls.

TMA is used to move tiles of $\mathbf{Q},\mathbf{K},\mathbf{V}$ from global memory (HBM) into shared memory (SMEM) without stalling the issuing warpgroup. Practically this means the producer warps issue TMA descriptors/loads for each tile and then commit the operation; completion is observed later by consumer warps via commit/ wait semantics (see the Barriers section). The kernel therefore needs to prepare TMA descriptors that describe the tile layout in global memory (stride, leading dimension) and launch them in advance of when the data are consumed so that the asynchronous transfer can hide global memory latency.

WGMMA is the asynchronous warpgroup GEMM primitive for Tensor Cores on Hopper. The kernel issues a WGMMA for each of the two GEMMs appearing inside the FlashAttention inner loop: the SS‑GEMM (source from SMEM/registers) that computes blocks of $\mathbf{S} = \mathbf{Q}_i\mathbf{K}_j^\top$, and the RS‑GEMM that accumulates $\tilde{\mathbf{P}}^{(j)}\mathbf{V}_j$ into the running output $\mathbf{O}_i$. On Hopper the WGMMA issues do not have to be blocking; the instruction can be committed and allowed to progress asynchronously while other warps or other instruction classes (e.g., MFU work) are scheduled. To exploit this, FlashAttention‑3 issues WGMMA calls with a commit but avoids immediate waits where possible so that overlapping with softmax/MFU work is possible.

The MFU executes relatively low‑throughput special functions such as exponential used by softmax. Because the MFU throughput is small compared to Tensor Core matmul throughput, a good kernel design schedules MFU operations to execute while the Tensor Cores are busy with WGMMA. One practical pattern is to issue a WGMMA for the next iteration's SS‑GEMM and issue a WGMMA to consume the previous iteration's $\tilde{\mathbf{P}}$ against $\mathbf{V}$, and then execute the sequence of MFU exp/multiply/add operations for the "current" block while those two WGMMA instructions proceed asynchronously. The net effect is that time spent on MFU is largely hidden under the much larger matmul work, improving overall utilization.

# Barriers and synchronization: commit, wait, bar.sync; shared-memory stage management

An asynchronous, multi‑warp kernel must be disciplined about synchronization so that consumers do not read uninitialized SMEM and producers do not overwrite SMEM still in use. FlashAttention‑3 uses three classes of primitives conceptually: commit to mark that an asynchronous operation has been launched, wait to observe completion of a particular asynchronous descriptor, and block‑level barrier synchronization (bar.sync) to coordinate warpgroups.

Within the CTA, a circular SMEM buffer with $s$ stages is used to stage incoming $\mathbf{K}$ and $\mathbf{V}$ tiles. The producer warpgroups repeatedly fill stages $(j \bmod s)$ by issuing TMA loads and then commit them; consumer warpgroups wait (via the pipeline object) for the corresponding stage to be available before starting to consume it. After consumers finish processing a stage they release it so the producer can reuse that stage. This ping‑pong or multi‑stage circular buffer ensures that producers never overwrite stages still being read and that consumers always have data ready without stalling the global memory transfer.

At the warpgroup level, flash scheduling is driven by bar.sync to force a desired ordering across warpgroups. A canonical pattern in FlashAttention‑3 is to use bar.sync to orchestrate the ping‑pong scheduling: ensure that the GEMMs (WGMMA calls) of one warpgroup occur before those of the other, so that while warpgroup A is issuing WGMMA instructions the MFU work (softmax) of warpgroup B can execute concurrently. Without bar.sync the compiler and hardware might reorder instructions in ways that eliminate the overlap.

Two additional primitives are meaningful in practice: (1) explicit wait calls for a particular TMA descriptor or WGMMA completion when a later instruction genuinely depends on the result, and (2) commits after launching WGMMA/TMA to let the hardware know the operation may proceed asynchronously. The kernel should minimize blocking waits and use them only where the data dependency is real (for example, before a WGMMA that consumes a $\tilde{\mathbf{P}}$ tile that must have been produced).

# Warp specialization patterns: producer vs consumer warpgroups; setmaxnreg budgeting

A central design choice in FlashAttention‑3 is warp specialization: dividing the warps of a CTA into producer and consumer warpgroups that have different responsibilities and resource needs. Producer warps primarily issue TMA loads and perform in‑kernel transposes (for FP8), while consumer warps perform the heavy WGMMA GEMMs and the MFU softmax operations. Specializing like this allows the kernel to tailor register and shared memory budgets to each role.

Hopper supports runtime register reallocation via the PTX primitive setmaxnreg. FlashAttention‑3 uses this to deallocate a predetermined number of registers in producer warps (which need little register space to launch TMA and LDSM/STSM transpose work) and reallocate those registers to consumer warps that will run the WGMMA and thus benefit from more RMEM. In essence, the kernel sets a smaller per‑warp register budget for producers and a larger one for consumers. This reduces register spilling in the GEMM warps and reduces the register footprint overall, improving occupancy when moderate.

When designing the split, choose the number of producer vs consumer warps so that producers can keep ahead with TMA launches (so consumer warps are not starved) while keeping enough consumer warps to saturate WGMMA throughput and hide MFU latency. The exact split is a tuning knob; the paper demonstrates practical performance gains using such warp‑specialized software pipelining.

# Tile size choices (Br, Bc, d) and occupancy vs register pressure trade-offs

Tile sizes are core tuning parameters: the query block size $B_r$, the key/value block size $B_c$, and the head dimension $d$ (given by the model). These parameters determine counts such as the number of query blocks $T_r=\lceil N/B_r\rceil$ and key blocks $T_c=\lceil N/B_c\rceil$, and drive per‑tile work and buffer sizes in SMEM and RMEM.

Larger $B_r$ and $B_c$ increase the arithmetic intensity of each WGMMA and improve Tensor Core utilization (fewer launches per unit work and larger contiguous GEMMs), but they also increase register pressure because the 2‑stage (or 3‑stage) pipelining strategy needs to hold extra intermediate buffers such as $\mathbf{S}_\text{next}$ in registers. In particular, the 2‑stage scheme requires register space of order $B_r\times B_c$ floats per threadblock to hold intermediate $\mathbf{S}$ tiles; a 3‑stage pipeline multiplies that demand. This elevated register demand reduces the number of concurrent CTAs/warpgroups that can be resident on an SM, thus lowering occupancy and possibly negating the throughput gains from larger tiles.

Conversely, small tile sizes reduce register pressure and allow higher occupancy, but diminish the ability to hide MFU latency under long WGMMA runs and increase the relative overhead of per‑tile bookkeeping (commits, waits, boundary handling). In practice FlashAttention‑3 chooses tile sizes as a balance; the paper reports configurations achieving up to 740 TFLOPs/s for FP16 on H100 by tuning these dimensions together with warp specialization and pipeline depth.

A concrete guideline from the paper's reasoning is to consider the relative cost of MFU work (exp/special functions) versus matmul work. For head dimension $d=128$ the forward pass has roughly 512× more matmul FLOPs than exponential FLOPs; because exponential throughput is approximately 256× lower than matmul throughput on H100, the exponential computes can take an appreciable fraction of execution unless hidden. Choosing $B_r,B_c$ so that individual WGMMA invocations are substantial (longer duration) gives more room to hide the MFU work, pushing overall utilization higher. Use profile‑guided tuning: if you see the MFU consuming a large portion of cycles, increase tile sizes (if register budget permits) or increase pipeline depth to better overlap.

# Persistent kernel strategies and load balancing (not yet in FP8 kernel per paper)

A persistent kernel keeps work mapped to the same SM resources across the entire invocation, avoiding kernel launch overheads and enabling fine‑grained dynamic load balancing. The paper notes that their FP16 FlashAttention‑3 uses a persistent kernel with load balancing, whereas the FP8 FlashAttention‑3 does not yet employ a persistent kernel—partly explaining why FP8 performance trails in small sequence length and causal masking scenarios.

When introducing a persistent kernel, the primary practical concerns are work partitioning and fairness. The persistent kernel typically assigns a range of queries (or query blocks) to each CTA and then dynamically steals work if CTAs finish early. This mitigates imbalances caused by sequence length variations, causal masks, or batching irregularities. For FlashAttention‑3, persistent kernels are especially useful because the per‑tile cost is nonuniform when causal masks reduce the number of key positions or when some tiles are smaller at sequence boundaries.

Load balancing also interacts with warp specialization: if some CTAs have more producer work and others more consumer work, the kernel must ensure the circular SMEM buffer and stage management do not deadlock. A common approach (used in the paper's FP16 kernel) is to keep the producer/consumer ratio fixed per CTA and ensure the pipeline object coordinates release and acquire semantics across dynamic work reassignment.

Because FP8 implementation requires in‑kernel transposes and byte permutation transforms that complicate producer work, the paper leaves FP8 without a persistent kernel for the reported results. Incorporating a persistent design for FP8 will require careful attention to in‑kernel transpose scheduling (LDSM/STSM) and register budgeting so that the persistent producer threads can keep up without starving consumers.

# Masking and variants: causal masks; MQA and GQA indexing without duplicating K/V

Real workloads require attention variants and masking. FlashAttention‑3 supports causal masks (autoregressive attention) as well as multi‑query attention (MQA) and grouped query attention (GQA). The core principle to preserve is that FlashAttention‑3 operates on blocks and avoids duplicating $\mathbf{K}$ and $\mathbf{V}$ in global memory when possible.

For causal masking, the number of key positions that each query row attends to varies by query index. FlashAttention‑3 handles this by adjusting the iteration bounds over key blocks so that for a given query block $\mathbf{Q}_i$ the consumer loop only computes contributions from those key blocks $j$ that are allowed by the causal mask. This reduces arithmetic work and memory traffic but complicates pipeline control: the consumer must know at which stage to release the SMEM stage because some stages may be skipped for causal boundary cases.

For MQA and GQA, the trick is purely in the indexing: FlashAttention‑3 follows FlashAttention‑2's approach of altering tensor indexing to index into a smaller set of $\mathbf{K}$ and $\mathbf{V}$ slices without duplicating them. In MQA, multiple queries share the same $\mathbf{K},\mathbf{V}$ so the kernel uses the same SMEM tiles for multiple query tiles; in GQA the head grouping is implemented via stride/offset arithmetic in the producer's TMA descriptors and the consumer's WGMMA operands. The shared‑memory circular buffer and warp specialization remain the same, but the producer must carefully construct TMA descriptors so that the correct grouped slices are loaded into each stage rather than naively copying full per‑head K/V tensors.

# Numerical formats: FP16/BF16 vs FP8; accumulator precision and softmax in FP32

FlashAttention‑3 supports multiple numerical formats with distinct performance and accuracy trade‑offs. FP16 (or BF16) using FP32 accumulators is the safer, high‑throughput option that preserves numerical stability by keeping the softmax intermediate reductions in higher precision. In the FP16 mode the algorithm keeps intermediate softmax results in FP32 (or at least in higher precision) to match the numerical behavior of FlashAttention‑2; the paper reports that FP16 FlashAttention‑3 has the same numerical error as FlashAttention‑2 and lower RMSE than a naive standard attention implementation because it keeps softmax intermediates in FP32.

FP8 (e4m3) yields substantially higher Tensor Core throughput on Hopper (roughly 2× compared to FP16) but imposes layout and precision constraints. Two important details must be handled:

1. Layout conformance for FP8 WGMMA: FP8 WGMMA on Hopper accepts only k‑major formats for SMEM operands, whereas FP16 WGMMA accepts both mn‑major and k‑major. Because FlashAttention naturally has $\mathbf{V}$ contiguous in the head dimension but WGMMA wants $\mathbf{V}$ tiles contiguous in the sequence length (k‑major) dimension, the kernel must perform an in‑kernel transpose of each $\mathbf{V}$ tile after TMA load. The producer warpgroups are well suited to perform this LDSM/STSM‑based tile transpose while leaving the WGMMA operands in the required layout for FP8.

2. Accumulator/operand layout mismatch and byte permutation: the FP32 accumulator layout produced by an FP8 WGMMA may not match the logical register ownership layout expected by the next WGMMA in a fused sequence. FlashAttention‑3 handles this by applying register‑level byte permutations (via byte permute instructions) to reorder the FP32 accumulator registers into the layout expected for the next WGMMA. For the logical $\mathbf{P}$ tile this manifests as a column permutation that can be compensated by writing the transposed $\mathbf{V}$ tile with a matching row permutation. These register permutations eliminate expensive cross‑thread shuffle operations and keep the pipeline efficient.

Accuracy under FP8 is improved by two algorithmic techniques: block quantization (quantize each block with its own scale instead of per‑tensor) and incoherent processing (multiply $\mathbf{Q}$ and $\mathbf{K}$ by a random orthogonal matrix $\mathbf{M}$ prior to quantization). Block quantization reduces dynamic range inside each block and is natural since FlashAttention already operates per block; incoherent processing spreads extreme outliers across coordinates so that no single quantized element is catastrophically large. The paper reports that these two measures together reduce FP8 numerical error by up to 2.6× relative to a baseline per‑tensor FP8 scheme. Finally, FlashAttention‑3 keeps softmax intermediate reductions and rescaling in higher precision (FP32) even when matmuls run in FP8, which is important to preserve numerical stability.

# Debugging and verification: inspecting SASS for intended overlap; measuring utilization

Because the kernel relies on careful asynchronous overlap, debugging and verification are essential. One effective low‑level verification is to inspect the generated SASS (the final GPU assembly emitted by the compiler). The paper notes that an analysis of SASS showed the compiler generates overlapped code as intended for the 2‑stage pipelining, so inspecting that assembly is a direct way to confirm whether WGMMA issues, commits, and non‑WGMMA MFU sequences are scheduled interleaved rather than serialized.

Beyond SASS inspection, practical runtime measurements are indispensable. Measure achieved TFLOPs/s and compare to the theoretical device peak; the paper reports FP16 runs reaching up to 740 TFLOPs/s (about 75% of theoretical on H100) and FP8 runs approaching 1.2 PFLOPs/s. If your kernel is substantially below these targets or far lower than a reference GEMM kernel, profile to see whether the MFU is the bottleneck (special‑function units consuming cycles), whether the WGMMA is not being fed enough work (too many small WGMMA launches), or whether register spilling reduces effective occupancy.

Use the FLOP accounting the paper uses to sanity‑check performance: forward pass FLOPs are

\[
4 \cdot \text{seqlen}^2 \cdot \text{head\_dim} \cdot \text{num\_heads},
\]

halved for causal masking (approximately) because roughly half of the attention matrix is skipped. For backward pass accounting multiply forward FLOPs by 2.5 (forward has 2 matmuls, backward has 5 due to recomputation). Comparing measured runtime to these FLOP counts gives a TFLOPs/s number to benchmark against published figures.

Numerical verification should compare single‑precision or FP64 reference outputs. The paper computed RMSE against an FP64 reference and showed FP16 FlashAttention‑3 and FlashAttention‑2 have about 1.7× lower RMSE than a naive standard FP16 attention because FlashAttention preserves softmax intermediates in FP32; FP8 FlashAttention‑3 with block quantization and incoherent processing is 2.6× more accurate than a baseline FP8 implementation. Use the same outlier‑heavy test distributions (e.g., base Gaussian plus rare large Gaussian spikes) if you want to stress quantization behavior.

Finally, instrument your kernel with fine‑grained timers around the TMA commits/ waits, WGMMA commits/ waits, and MFU sequences to confirm that waits are minimized and that MFU time is being overlapped. If you find stalls at wait points, that indicates pipeline sizing or producer/consumer imbalance needs retuning.

# Putting it together: practical tuning recipe

A concise tuning recipe grounded in the paper's findings:

1. Start from a working FlashAttention‑2 style fused kernel and add warp specialization: split warps into producer and consumer roles. Use setmaxnreg to shift register budget to consumers.

2. Implement a circular SMEM buffer with $s$ stages; pick $s\ge 2$ to allow pipelining. Ensure producer issues TMA loads and commits for stages while consumers acquire and release them.

3. Implement the 2‑stage WGMMA/softmax pipeline: in each consumer main loop iteration issue an SS‑WGMMA for $\mathbf{Q}_i\mathbf{K}_j^\top$ and an RS‑WGMMA for $\tilde{\mathbf{P}}_{j-1}\mathbf{V}_{j-1}$, committing but not waiting where legal, then perform MFU softmax work while those WGMMA instructions proceed. Use bar.sync across warpgroups to realize ping‑pong scheduling at the CTA level.

4. Tune tile sizes $B_r,B_c$ to balance WGMMA duration (to hide MFU) and register pressure. If the profiler shows MFU work not fully overlapped, increase tile sizes; if SASS/occupancy shows heavy register spilling, reduce tile sizes or pipeline depth.

5. For FP8, add in‑kernel transpose of $\mathbf{V}$ tiles using LDSM/STSM in the producer warps, and apply the required byte permutations on accumulators in registers so the fused WGMMA sequence conforms to FP8 operand layout constraints. Use block quantization per tile and, if outliers are common, fuse incoherent orthogonal transforms (Hadamard + diagonal signs) into the preceding embedding/rotary step.

6. Validate correctness and numerical stability by computing RMSE against an FP64 reference, and measure TFLOPs/s. Use SASS inspection to confirm the intended WGMMA/MFU interleaving, and iterate on producer/consumer ratios, $s$, and tile sizes until you approach the expected utilization targets (e.g., the paper's FP16 peaks around 740 TFLOPs/s and FP8 near 1.2 PFLOPs/s).

7. If serving diverse sequence lengths or causal masking workloads, consider implementing a persistent kernel with dynamic work stealing (as the paper's FP16 kernel does) to balance skew and avoid kernel launch overheads—port this to FP8 only after stabilizing the transpose/permute logic and register budgeting.

Following this approach organizes the kernel toward the core principle of FlashAttention‑3: exploit asynchrony and low‑precision hardware by separating producers and consumers, issuing asynchronous TMA and WGMMA operations, hiding MFU work under matmul, and controlling layout and quantization for high FP8 throughput while preserving numerical quality.
