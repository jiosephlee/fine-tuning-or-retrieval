### What do SS-GEMM and RS-GEMM mean in FlashAttention-3, and how do they map to WGMMA sources?
Question:
In Algorithm 1 of the FlashAttention-3 paper (the forward pass without intra-consumer overlap), the authors label two GEMMs as "SS-GEMM" for computing $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^\top$ and "RS-GEMM" for updating $\mathbf{O}_i$. I assume "S" means the operand is sourced from shared memory and "R" means from registers, but I'm not entirely sure which operand is where in each call. Can someone clarify the exact meanings of SS-GEMM vs. RS-GEMM in the context of Hopper's WGMMA (e.g., which operand is in SMEM vs RMEM in each case), and how these map to the asynchronous WGMMA calls used by the paper?
Answer:
Short answer: SS-GEMM means both GEMM operands are read from shared memory (SMEM); RS-GEMM means the first operand lives in registers (RMEM) while the second is read from shared memory. In the paper’s Algorithm 1 this matches the concrete data flow: the score GEMM
$S_i^{(j)} = Q_i K_j^\top$ is SS-GEMM because both $\mathbf{Q}_i$ and $\mathbf{K}_j$ are staged into SMEM by the producer; the output-accumulation GEMM that updates $\mathbf{O}_i$ is RS-GEMM because the probability tile $\widetilde{\mathbf{P}}_i^{(j)}$ is held in registers while the $\mathbf{V}_j$ tile is in SMEM.

Why this naming and location make sense
- In the producer/consumer scheme the producer TMA loads tiles of $\mathbf{Q}$, $\mathbf{K}$, $\mathbf{V}$ into the circular SMEM buffer. The consumer warps then run WGMMA-based GEMMs that can directly read those tiles from SMEM. When you compute the raw scores $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^\top$ both inputs are exactly the SMEM tiles just loaded, so both operands are SMEM-sourced (hence “SS-GEMM”, shared-shared).
- After computing $\mathbf{S}_i^{(j)}$ the consumer performs softmax-ish work on that score tile and forms a scaled/biased probability tile $\widetilde{\mathbf{P}}_i^{(j)}$. That $\widetilde{\mathbf{P}}$ tile is kept on-chip in registers (RMEM) to avoid spilling to GMEM/SMEM, and then it is multiplied with $\mathbf{V}_j$ (which still sits in SMEM). The first operand of that GEMM therefore lives in registers while the second is in shared memory (hence “RS-GEMM”, register-shared).

How these map to WGMMA (asynchronous) usage in the paper
- The paper uses WGMMA as a shorthand for issuing asynchronous Tensor‑Core block GEMMs. For SS-GEMM you issue a WGMMA that sources both operand tiles from SMEM and accumulates into on‑thread registers (the FP32 accumulator delivered by WGMMA). The call is issued (commit) and then the consumer can wait for its completion when the subsequent softmax needs $\mathbf{S}$. In the 2‑stage pipelining they often issue that WGMMA and do not block immediately (commit but do not wait) so the tensor core can run asynchronously while other scalar work is scheduled.
- For RS-GEMM you issue WGMMA where the A (or “first”) operand resides in RMEM (the probability tile held in registers) and the B operand resides in SMEM (the $\mathbf{V}$ tile). WGMMA supports reading operands from SMEM and using register-held accumulators; in the implementation the probability tile is already arranged in the register layout expected by WGMMA (or permuted into it), so the call consumes that RMEM operand and the SMEM $\mathbf{V}$ tile and produces/register-accumulates the partial $\mathbf{O}_i$ result. Again this WGMMA is issued asynchronously (commit but not wait) to overlap with softmax work of the next iteration.

FP8 / layout caveat (how it affects SS vs RS)
- The paper stresses FP8/WGMMA layout constraints: FP8 WGMMA requires operands to be k-major in SMEM. That affects how you must load/transposition the SMEM tiles for both the SS-GEMM and the RS-GEMM second operand (the $\mathbf{V}$ tile). For SS-GEMM both Q and K tiles must be placed in conformant SMEM layout for the FP8 WGMMA; for RS-GEMM the register-held $\widetilde{\mathbf{P}}$ layout must be permuted to match how the WGMMA expects its accumulator/operand mapping and the SMEM $\mathbf{V}$ tile must be in the k-major layout. The paper describes doing an in‑kernel transpose (LDSM/STSM) and register byte‑permutes so the register operand and SMEM operand formats line up for chained asynchronous WGMMA calls.

Practical mapping to the paper’s pseudocode
- In Alg. 1 (no intra-consumer overlap) lines labeled “SS-GEMM” (computing $\mathbf{S}_i^{(j)} = \mathbf{Q}_i \mathbf{K}_j^\top$) correspond to an asynchronous WGMMA that reads both Q and K from SMEM. The code “Commit and wait” means issue the WGMMA and then wait if the next steps need $\mathbf{S}$.
- The lines labeled “RS-GEMM” (updating $\mathbf{O}_i$ with $\widetilde{\mathbf{P}}_i^{(j)} \mathbf{V}_j$) correspond to a WGMMA that consumes $\widetilde{\mathbf{P}}$ from registers and $\mathbf{V}_j$ from SMEM. Because $\widetilde{\mathbf{P}}$ is produced on‑chip by the scalar softmax steps it is kept in RMEM and passed directly to WGMMA without rereading SMEM.

In short: SS-GEMM = both operands in SMEM (Q and K tiles); RS-GEMM = first operand in registers (probability tile), second operand in SMEM (V tile). The asynchronous WGMMA calls in the paper are simply the kernel-level implementation of those two cases, with commit/wait used to overlap the WGMMA (tensor‑core) execution with TMA loads and softmax work and with extra register/SMEM transposes when targeting FP8 to satisfy WGMMA layout requirements.
