\title{Stack Exchange of the Paper: fa3}

### How does the in-kernel FP8 $\mathbf{V}$-tile transpose via LDSM/STSM work if transpose ops cannot split packed 8-bit pairs?
Question:
For FP8 WGMMA, the paper says only k-major operands are supported, so $\mathbf{V}$ tiles must be transposed in-kernel. The authors use LDSM/STSM, packing two 8-bit values into one 16-bit lane, but mention that the transpose variants cannot split packed 8-bit entries, necessitating register moves between LDSM and STSM. Could someone describe a concrete sequence for one $8\times8$ microtile showing: (1) how bytes are packed for LDSM, (2) what register-level shuffles or byte permutes are applied, and (3) how STSM writes the transposed k-major layout back to SMEM—all without excessive register pressure?
Answer:
Short answer: the kernel treats the $8\times8$ FP8 microtile as an $8\times8$ array of 8-bit values packed into 16-bit lanes so LDSM/STSM can move $128$ bytes at a time. LDSM brings the packed 16-bit lanes into registers unchanged (each 16-bit lane contains two adjacent FP8 bytes that must remain together for the plain LDSM/LDSM-transpose semantics). Because the transpose variants of LDSM/STSM are not allowed to split those packed 8-bit pairs, you must perform a small register-level byte permutation that re-pairs bytes across lanes so that an STSM (which also writes 16-bit lanes) will store the transposed k-major layout. The permutation can be implemented with cheap byte-permute instructions (replicated over the $128$-byte LDSM granule) and done on small sub-blocks so you never blow out register file pressure.

Below I give a concrete, implementable sequence for a single $8\times8$ microtile that follows the paper’s remarks, shows how bytes are packed for LDSM, what register-level permutes are applied, and how STSM writes the transposed k-major layout back to SMEM — and I explain how to keep register pressure low.

1) SMEM layout and LDSM packing (what LDSM actually loads)
Assume the V microtile in SMEM is an $8$ (rows in sequence-length) by $8$ (columns in head-dimension) tile of FP8 values laid out row-major in the original (mn-major) storage. To use LDSM/STSM we pack two adjacent FP8 values into one 16-bit lane so that the hardware’s 16-bit-granularity LDSM can move $128$ bytes = $64$ lanes per warpgroup (but we only illustrate one $8\times8$ microtile).

Concretely, before LDSM the $8\times8$ bytes in SMEM look like (rows $r=0\ldots7$, cols $c=0\ldots7$): $V[r,c]$ (one byte each). We pack horizontally (adjacent columns) into 16-bit lanes:
$lane[r,k] = \{\text{low\_byte} = V[r,2k],\ \text{high\_byte} = V[r,2k+1]\}$ for $k=0\ldots3$.
So each row becomes four 16-bit lanes. LDSM (non-transpose form) will gather a warp’s worth of these 16-bit lanes into registers, preserving the 16-bit lane contents. No splitting of the two bytes in a lane occurs during LDSM.

2) Goal: write the k-major (transposed) tile in SMEM so that later FP8 k-major WGMMA can read it
WGMMA requires the V tile that is contiguous along K (sequence-length) — i.e., we need the tile transposed so that what were rows become columns. But STSM (the store-side instruction) also writes 16-bit lanes; it cannot independently write the low and high bytes to different target 16-bit lanes. Therefore we must rearrange the bytes inside registers so that pairs of bytes that belong together in the target transposed layout share the same 16-bit lane. In other words, we must repack bytes across registers so that each 16-bit lane after the register permute contains the two FP8 elements that STSM will write to the desired transposed positions.

3) Register-level permutation recipe (concrete for $8\times8$)
Work on the $8\times8$ tile by splitting into two $8\times4$ subtiles (each subtile corresponds to the $4$ 16-bit lanes per row loaded by LDSM). This keeps the working set small (a few registers per thread) and avoids excessive register pressure.

Step A — LDSM load:
- Issue LDSM (non-transpose) per the PTX semantics that collectively loads the $8\times4$ 16-bit lanes (for $8$ rows $\times$ $4$ lanes each) into the warp's register file. After LDSM each register lane holds a 16-bit value equal to $\{V[\text{row},2k],V[\text{row},2k+1]\}$.

Index the loaded 16-bit words as $W[r,k]$ with $r=0\ldots7$, $k=0\ldots3$, where $W[r,k] = [\text{byte0} = V[r,2k],\ \text{byte1} = V[r,2k+1]]$.

Step B — form the transposed pairing with byte-permute:
- The transposed $8\times8$ tile needs to produce, for each target row $t$ ($0\ldots7$) and target pair index $p$ ($0\ldots3$), a 16-bit lane containing $\{V[2p,t],V[2p+1,t]\}$ or equivalent depending on the exact interleaving chosen for k-major WGMMA. (The paper shows an example permutation pattern that reorders sequence of bytes per 8-byte chunk to $\{d0,d1,d4,d5,d2,d3,d6,d7\}$.)

- Implement a register byte-permute sequence that, within each $64$-bit or $128$-bit register group, takes bytes from $W[\cdot,\cdot]$ and arranges them into lanes matching the desired output pairs. Practically on Hopper this uses instructions that can permute bytes within $128$-bit lanes (a small sequence of PTX SASS byte permutes or bitwise unpack/interleave ops). A minimal, practical implementation is:

  1. Use 16-bit unpack/interleave (e.g., pairwise unpack low/high) between registers holding adjacent rows to move low bytes into the same register word as low bytes of other rows. This step is repeated in a small tree to group bytes by target column.
  2. Use byte-level permute (PRMT or a sequence of SHFL/B.Y) to finalize the ordering inside each 16-bit word so that each word contains exactly the two FP8 bytes that must be written together by STSM.

Concretely: first do pairwise interleaves between rows $[0,1]$, $[2,3]$, $[4,5]$, $[6,7]$ to build groups; then interleave those groups to gather column-wise bytes; finally re-pair odd/even bytes to produce words $[V[0,t],V[1,t]]$, $[V[2,t],V[3,t]]$, etc. Replicate this whole permutation pattern over the $4$ lane indices $k=0\ldots3$. The permutation pattern the authors mention — changing the order to $\{d0,d1,d4,d5,d2,d3,d6,d7\}$ — is exactly this gather-by-column grouping expressed at byte granularity, and it is repeated every $8$ bytes (i.e., per $64$-bit lane), so you implement it once and it applies across the loaded $128$-byte block.

Step C — STSM store (transposed write):
- After the byte-permute, each 16-bit register lane now contains the two FP8 bytes that must be stored together in SMEM at the position corresponding to the transposed (k-major) layout. Issue STSM (transpose-enabled variant) which writes the register lanes back to shared memory. Because we prepared the 16-bit lanes correctly, STSM can write them without needing to split any bytes. The result in SMEM is the $8\times8$ tile in k-major (transposed) layout and ready for FP8 WGMMA.

4) Why two-byte packing + byte-permute rather than splitting the lanes
The constraint in the paper is that the transpose variants of LDSM/STSM cannot split 8-bit pairs packed into 16-bit lanes. If you attempted to rely on an LDSM-transpose that would send individual bytes to different registers, the hardware forbids splitting a 16-bit word’s bytes into two separate 16-bit destinations. So the only way to realize the logical transpose is to accept that LDSM will bring pairs together, then perform explicit register-level re-pairing so that STSM will write the proper 16-bit pairs corresponding to the transposed positions.

5) Keeping register pressure low
Do the whole operation on $8\times4$ subtiles (i.e., process half the microtile at a time), reuse the same small set of registers for the byte permutes, and perform the permute+STSM immediately after each LDSM load. This way you never need to hold both the entire original and transposed $8\times8$ tile in registers simultaneously. The pipeline in the paper exploits that you can perform the in-kernel transpose in the producer warpgroup and do it in the “shadow” of two WGMMAs — that is, schedule the LDSM + byte-permute + STSM so it runs while other warpgroups are executing matmuls. Also, use the lane-replicated permutation pattern (the same per-$8$-byte pattern repeated) so the implementation uses a very small, fixed sequence of permute/unpack instructions rather than a large general-purpose permute table. These choices keep the extra register cost to a few registers per thread and avoid spills.

6) Example pseudo-layout map (compact view)
- Before LDSM: SMEM rows $r$, cols $c$ are bytes $V[r,c]$.
- LDSM (per row) gives registers $R[r,k] = [V[r,2k], V[r,2k+1]]$ — four 16-bit words per row.
- Byte-permute across $R[0\ldots7,*]$ reorganizes bytes to produce registers $S[t,p] = [V[2p,t], V[2p+1,t]]$ in the order expected by STSM to place them in SMEM at (transposed) positions ($t$ is the new row index in k-major).
- STSM writes $S$ back to SMEM; the result is $V$ transposed, contiguous along $K$ (k-major) for WGMMA.

Conclusion
The kernel therefore uses LDSM to load $8\times4$ 16-bit lanes per row (preserving packed FP8 pairs), performs a tiny register-level byte-permute tree that re-pairs bytes into the 16-bit lanes required by the STSM transpose store, and then issues STSM to write the k-major tile. Doing it on half-tiles and immediately storing the result keeps register usage small; repeating the same per-$8$-byte permutation pattern makes the code compact and efficient. This is exactly the strategy summarized in the paper: pack two 8-bit FP8 values into 16-bit lanes for LDSM/STSM, use byte-permute instructions to rearrange pairs in registers (because LDSM/STSM cannot split pairs), and then STSM writes the transposed k-major layout back to SMEM so FP8 WGMMA can consume it.
