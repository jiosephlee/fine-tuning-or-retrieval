# From FlashAttention-2 to -3: A Migration Guide for Practitioners

FlashAttention-3 (FA3) is the next step in the FlashAttention line: it rethinks the kernel and dataflow to exploit Hopper-class GPUs' asynchrony and FP8 Tensor Cores. If you already use FlashAttention-2 (FA2) or other fused attention kernels, this guide explains when and how to adopt FA3, what practical trade-offs to expect (performance and numeric), and what implementation details to watch for when integrating FA3 into PyTorch / Hugging Face stacks.

## TL;DR recommendations

- If you want the most robust drop-in improvement on Hopper H100 GPUs, start with FA3 in FP16: expect about 1.5–2.0× speedup over FA2 in the forward pass and 1.5–1.75× in the backward pass (paper benchmarks). FA3 FP16 reaches up to ~740 TFLOPs/s (≈75% utilization).
- FP8 in FA3 can deliver substantially higher peak throughput (paper reports approaching 1.2 PFLOPs/s) but requires extra attention to accuracy and layout constraints. Use FP8 when you need maximum inference throughput and you can tolerate extra engineering (quantization and layout handling) or when your workflow already includes careful FP8 validation.
- For long sequences and larger head dimensions FA3's gains are strongest; for small sequence lengths or some causal-mask configurations FP8 kernels may not outperform vendor kernels without extra tuning.
- FA3 is open-source (see the paper link / repo), and the authors plan integration with PyTorch and Hugging Face. Expect to integrate via the provided library / kernel and follow standard dispatcher or custom operator paths for model runtimes.

Below I unpack the details you should know before switching production or experimentation pipelines to FA3.

## What changed in FA3 (practical view)

FA3 combines three main ideas that affect performance and integration:

1. Producer-consumer warp-specialization + ping-pong scheduling: producer warps perform asynchronous TMA loads to shared memory while consumer warps run Tensor Core GEMMs. This reduces stalls and increases utilization on Hopper GPUs by overlapping data movement and matmuls.
2. Intra-warpgroup GEMM–softmax pipelining: FA3 breaks some of the sequential dependence between the two GEMMs and the softmax per key block by keeping a small pipeline across iterations (2-stage, optionally deeper). This overlaps expensive Tensor Core work with lower-throughput softmax/exponential operations.
3. FP8 support with layout-aware in-kernel transpose and accuracy techniques: to use FP8 Tensor Cores FA3 performs in-kernel transposes (LDSM/STSM patterns) to satisfy the FP8 k-major layout constraint and uses block quantization plus "incoherent" preconditioning (diagonal ±1 and Hadamard-style transforms) to reduce quantization error.

These changes are the reason FA3 attains much higher TFLOPs/s on Hopper compared to FA2.

## Supported settings and performance characteristics

- Hardware: FA3 is designed for GPUs with asynchronous Tensor Cores and TMA (paper focuses on NVIDIA Hopper H100). The algorithm assumes the availability of asynchronous WGMMA/TMA primitives and FP8 Tensor Core support.
- Precision: FA3 supports FP16 (safe and high-performing) and FP8. In FP16 it preserves numerical behavior comparable to FA2 (intermediate softmax scaling kept in FP32). FP8 requires block quantization and incoherent processing to keep accuracy acceptable.
- Operations: FA3 implements exact attention (no kernel-level approximation) and supports causal and non-causal attention and multi-head variants (including multi-query / grouped query) via adjusted indexing.
- Sequence lengths and head dimensions: FA3 shows larger speedups for medium-to-long sequences (1k tokens and up). The paper reports FA3 outperforming FA2 by 1.5–2× in forward pass and even beating cuDNN for medium/long sequences in many configurations.
  - Notable head-dimension observations from the paper: for large sequence lengths FA3 FP16 generally wins. For FP8, the relative position depends on head dimension:
    - head dim 64: FP8 FA3 is ahead of the competing implementation in many cases.
    - head dim 128 and 256: FP8 FA3 is roughly at par without causal masking, and can be behind when causal masking is enabled (paper footnote).
- Backward pass: FA3 accelerates the backward pass as well (paper reports 1.5–1.75× improvements versus FA2), but FP8 is typically focused on inference; for training FP16 remains the safer default.

## When to prefer FP16 vs FP8

Use FP16 when:
- You want a robust, low-hassle upgrade from FA2 for both training and inference.
- Your workloads require stable numerical fidelity and backward pass correctness (FA3 FP16 matches FA2 numerical error and keeps softmax/rescaling in higher precision).
- Sequence lengths are small-to-medium and you want consistent performance across causal and non-causal masks.

Consider FP8 when:
- You need the absolute highest inference throughput and can validate model behavior under FP8 numerics.
- Your pipeline can reliably incorporate the block quantization and incoherent processing steps (these are central to FA3’s FP8 accuracy improvement).
- You target large sequence lengths and head dims where FP8’s higher matmul throughput is beneficial.
- You accept that FP8 FA3 may need additional tuning for small sequence lengths and for causal masks (FP8 FA3 lacked a persistent kernel in the reported experiments, which affected small-seqlen and causal-mask performance).

Numerical trade-offs:
- FP16 FA3 keeps intermediate softmax computations in FP32 and matches FA2's numerical error behavior (paper reports FA2/FA3 FP16 having ≈1.7× lower RMSE than a standard attention implementation that materializes intermediates).
- Out-of-the-box per-tensor FP8 quantization performs poorly in presence of outliers. FA3’s two measures—block quantization and incoherent processing (randomized orthogonal-ish preconditioning implemented via cheap diagonal ±1 × Hadamard-like transforms)—reduce FP8 attention RMSE by up to 2.6× compared to baseline per-tensor FP8 attention.

Bottom line: FP16 = safer, simpler, very good speedups. FP8 = bigger wins possible but requires careful quantization/validation.

## What to watch out for (pitfalls and implementation caveats)

1. Layout constraints for FP8 GEMMs (k-major requirement)
   - On Hopper, FP8 WGMMA accepts only k-major input layout for operands in shared memory. FA3 solves this by doing an in-kernel transpose of V tiles (using LDSM/STSM style instructions) so that loaded tiles meet the k-major constraint without a separate global-memory transpose.
   - Practical implication: FP8 integration is more invasive than FP16. You must ensure the kernel or pre-processing step produces the required memory layout for FP8 Tensor Cores.

2. Pipeline depth vs register pressure
   - FA3’s overlapping (2-stage and optionally 3-stage) requires holding extra intermediate tiles in registers. Larger block sizes and deeper pipelines increase register usage and can cause spilling; tuning block sizes B_r/B_c and pipeline depth is necessary.
   - If you see regressions, profile register usage (and occupancy) and trade off tile sizes for pipeline depth.

3. Small sequence lengths and causal masks
   - FA3's FP16 persistent kernel yields strong performance for many lengths, but FP8 FA3 (as reported) did not include a persistent kernel or the same load-balancing optimizations and can be slower for small sequences or when causal masking halves the computation by design.
   - Causal masks change the FLOP pattern (roughly half the computed scores), which interacts with the scheduling and tile choices; test the causal-mask case separately.

4. Compiler reordering and instruction scheduling
   - FA3 relies on careful overlap of asynchronous WGMMAs and softmax computations. The actual instruction stream may be reorganized by the compiler (NVCC), so vendor-specific codegen and careful SASS inspection (or direct assembly-level control) can be necessary to ensure the desired overlapped ordering.

5. FP8 accuracy and outliers
   - Per-tensor quantization is fragile with outliers. FA3’s recommended mitigations are block quantization (one scale per block) and incoherent preprocessing (random orthogonal-like transform to spread out outliers). These can be fused with upstream ops (e.g., rotary embeddings) to avoid extra passes, but you must validate the effect on model outputs.

6. Persistent kernel considerations
   - The paper notes that their FP16 FA3 has a persistent kernel and load balancing strategy, while FP8 FA3 did not. This explains why FP8 FA3 can underperform for small seqlen/causal cases. Expect future FP8 kernels or user-tuning to address this.

## Integration notes: PyTorch and Hugging Face

- Source and integration path: FA3 is open-sourced (see the repository referenced in the paper). The authors plan to integrate FA3 into PyTorch and Hugging Face libraries to make adoption easier.
- Integration approaches:
  - Use the provided FA3 operator / kernel library as a drop-in attention operator and register it with your framework’s custom op dispatcher. This keeps your model code unchanged but substitutes the attention kernel at runtime.
  - For Hugging Face models, replacement is typically done by switching the attention kernel implementation (for example, via an optional backend or a custom runtime engine). Expect to follow the same pattern used for FA2 integration: register FA3 kernels and update the attention module to call the fused operator.
  - If you want to fuse upstream ops (rotary embeddings, block quantization, incoherent transform) to avoid extra memory passes, you will need to adapt model pre-processing or patch the attention module to perform those fused transforms. The paper notes these fusions are possible and often free in compute-bound regimes.
- Testing and validation:
  - Validate numerical closeness to an FP64 reference, especially when using FP8. The paper uses RMSE against FP64 on synthetic inputs with simulated outliers; you should do the same on representative model inputs and downstream tasks.
  - Benchmark on target hardware (H100 or other Hopper-like GPUs) and test both causal and non-causal paths, multiple head dims, and sequence lengths you care about.
- Practical deployment tips:
  - Start by switching only FP16 kernels for FA3 and verify speedups and numerical behavior. This is the lowest-risk path.
  - If moving to FP8 for inference, implement FA3’s block quantization and incoherent processing and fuse them into the preprocessing graph where possible to avoid extra memory-bound kernels.
  - Tune block sizes (B_r, B_c) and pipeline depth for your specific sequence length and head dimension. The paper’s algorithm is sensitive to register pressure and occupancy.

## Tuning knobs to profile / experiment with

- Block sizes for queries and keys/values: B_r and B_c (FA3 operates on blocks; tuning affects register use and occupancy).
- Pipeline stages: 2-stage vs 3-stage overlapping (3-stage may give better overlap at the cost of registers).
- Warp partitioning: number of producer vs consumer warps, which affects register allocation per role.
- FP8 preprocessing: block quantization block size and choice of incoherent transform (Hadamard + diagonal ±1 is the recommended low-cost choice).
- Persistent kernel enablement (FP16 kernel has one in the experiments; ensure kernel parameters enable persistent style scheduling if available).

## Validation data and numbers you can cite when discussing FA3

- Forward pass speedup vs FA2: 1.5–2.0× on H100 (varies with sequence length / head dim), FP16 up to ~740 TFLOPs/s (≈75% utilization of H100 Tensor Core peak).
- FP8 peak: experiments in paper report close to 1.2 PFLOPs/s.
- Backward pass: 1.5–1.75× speedup vs FA2.
- Numerical error: FA3 FP16 matches FA2 and is ≈1.7× lower RMSE vs a standard attention implementation that materializes intermediates (in the synthetic outlier test). FA3 FP8 with block quantization + incoherent processing reduced FP8 numerical error by ≈2.6× compared to baseline per-tensor FP8 attention in the same test.
- Causal-mask behavior: FP8 FA3 can be behind optimized vendor kernels for some head dims with causal masks (paper notes head dim 128 and 256 as examples where FP8 is at par or behind when causal masking is applied).

## Final checklist before migrating

- Verify your target GPU supports asynchronous Tensor Cores, TMA, and FP8 Tensor Core instructions (paper focused on Hopper/H100).
- Start with FA3 FP16: update runtime / custom op registry to call FA3’s FP16 kernel and run correctness/unit tests.
- Benchmark representative workloads: sequence lengths, head dims, batch sizes, both causal and non-causal.
- If moving to FP8:
  - Implement FA3’s block quantization and incoherent transform (or use the FA3 library’s implementation if provided).
  - Ensure in-kernel transpose / memory layout handling for V tiles (or provide pre-transposed V in memory if you prefer a pre-processing step).
  - Run strict numerical validation vs FP32/FP64 references for representative inputs.
- Tune block sizes and pipeline depth to match occupancy and avoid register spilling.

---

FlashAttention-3 is an important evolution of fused attention kernels: it raises the performance ceiling on modern accelerators by explicitly exploiting asynchrony and low-precision hardware, while also providing concrete tools to keep FP8 numerics practical. The safest adoption path is: swap FA2 → FA3 in FP16, profile and test, then evaluate FP8 only after validating accuracy with FA3’s block quantization + incoherent processing. For code and kernels, consult the FA3 repository linked from the paper and follow its integration notes for PyTorch / Hugging Face.
