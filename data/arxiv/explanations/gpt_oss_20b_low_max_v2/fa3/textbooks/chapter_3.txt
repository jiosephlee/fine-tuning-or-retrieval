Chapter 3: # 3. GPU Architecture and Execution Model  

Efficient attention kernels are a direct consequence of how a modern GPU exposes its compute and memory resources. In this chapter we dissect NVIDIA Hopper—the generation on which FlashAttention‑3 is optimized—to expose the properties that benign designers can leverage, and the constraints that must be respected. The discussion is organized around the four core subtopics.

---

## 3.1 Memory hierarchy: HBM, L2 cache, shared memory, registers  

A GPU’s memory system is a layered cascade of capacities and bandwidths designed to trade off latency against storage volume. Hopper’s hierarchy can be summarized in the following table:

| Layer            | Serialisation   | Typical Bandwidth (per SM) | Comment |
|------------------|-----------------|----------------------------|----------|
| Registers (RMEM) | 64‑bit words    | < 1 GHz (per SM)          | Private, zero‑latency access; each thread sees at most 256 registers |
| Shared Memory (SMEM) | Bank‑array (1 KB banks) | ~128 bytes/clock (per SM)  | Programmer‑managed cache; accessible by all threads in a CTA; supports the Tensor Memory Accelerator (TMA) |
| L2 Cache         | Hexagonally partitioned 16 KB banks per SM | Tens to hundreds of GB/s overall | Transparent caching of global memory accesses |
| Global Memory (HBM) | Multi‑channel DDR5x3            | ~25–30 TB/s on H100 SXM5  | Only source of persistent data |

The Health of an attention kernel hinges on keeping **query–key–value tile pointers** in fast memory while iterating over them many times. Because the inner loop of attention involves repeated matrix–matrix multiplications (GEMMs) that re‑use the same key/value tiles, an efficient design will stream these tiles into SMEM once per block, keep them there for the duration of that block’s work, and finally write only the output back to HBM.

However, even within SMEM not all lanes enjoy equal bandwidth: accesses must be **bank‑conflict free** across the 32 actual banks per SM, and each warp must maintain a regular stride for TMA loads to avoid stalls. Furthermore, any shared memory writes happen concurrently with other warps; excessive contention can ripple into evictions from private registers or staging regions used for softmax.

Then there is **register pressure**. An FP8 or FP16 tensor core operation in Hopper consumes dozens of registers per thread. The per‑warp register budget can be enlarged via `setmaxnreg`, but only for warps that’ s get registered as part of a special "register packing" branch—this assists warp‐specialization by granting multiplication warps more capacity than data‑movement warps.

Understanding this hierarchy allows kernel designers to choose block sizes that fit in shared memory, decide how many threads need to access CUDA’s tensor cores simultaneously, and schedule TMA operations so that they do not compete with other computations for GDDR bandwidth.

## 3.2 Thread hierarchy: threads, warps, warpgroups, threadblocks  

The execution model is orchestrated around *threads* grouped into *warps* (32 threads). These are then aggregated into *warpgroups*—four contiguous warps stitched together to harness Hopper’s Tensor Cores—and finally bundled into *threadblocks* (CTAs). Two-level scheduling governs where these inhabit:

* **CTAs → Streaming Multiprocessor (SM)**: All threads in a CTA reside on a single SM.
* **Warpgroups → Group Processing Controller (GPC)**: On Hopper each gauge controls four CTAs; this introduces an additional threadblock “cluster” level called **threadblock clusters**—an optional level that can allocate more speculative resources.

Because each warp belongs to exactly one warpgroup on Hopper, warp‐specialized kernels treat *per‑warpgroup* roles deterministically: one group may be designated as *producer*, another as *consumer*, allowing them to issue completely independent instruction streams without contention on register files or SIMD units. This clean division is what underpins FlashAttention‑3’s explicit producer–consumer pipeline.

Another subtlety lies in **warp occupancy**. The number of active warps per SM—called occupancy—directly impacts hiding latency from both TMA loads and WGMMA instruction submission. A kernel that keeps too few warps will starve delays; a kernel that oversubscribes will suffer resource conflicts. Good practice therefore pairs:
- **Large threadblocks** encapsulating many warps
- **Balanced warp counts** ensuring enough parallelism for both producer and consumer groups

Lastly, quantitative reasons for employing *persistent* threadblocks arise when the amount of sequence data exceeds what can be accommodated by a single CTA. Persistent kernels re-use CTAs over multiple tiles using explicit loops over global indices rather than relying on CUDA's grid launch overheads.

## 3.3 Warp‑specialization and asynchronous execution (TMA, WGMMA)  

Two new primitives are central to Hopper’s conception of asynchrony:

### 3.3.1 Tensor Memory Accelerator (TMA)

TMA decouples memory movement from instruction issue:

```c
__shared__ half Q_block[256][64];
{ TMA } load Q_block from global          // asynchronous
```

A single-thread dependent `__syncthreads()` after a TMA load will stall only when the subsequent **memory location** becomes live; other warps can continue executing or issuing new TMA loads without wait time. This separation empowers producers to countdown into consumers’ later computations while still satisfying data availability constraints.

### 3.3.2 WarpGroup Matrix Multiply Accumulate – WGMMA

WGMMA runs entirely inside the Tensor Core hardware but lives at the warpgroup granularity: four contiguous warps execute against each other’s operands simultaneously, exchanging partial accumulations implicitly through fused reduce operations across lanes.

The asynchronous nature shows up again here: you can issue `WGMMA(a,b)` then immediately proceed to issue other instructions like an exponential—to overlap compute with low‑throughput functions unless there is an explicit dependency on WGMMA results.

**Warp‑specialization** makes this pattern intuitive: warpgroup 0 might constantly issue `load` operations via TMA and keep its registers pristine; warpgroup 1 takes up two copies of raw query data from shared memory then performs `WGMMA` matrices regularly while also executing softmax reductions concurrently—thanks to Ture-routine dispatching each group runs at its own pace.

With these two primitives in hand we can build a producer–consumer pipeline requiring only minimal host intervention: one group writes blocks into SMEM; another group picks them up for matrix multiplication plus value accumulation—all while overlapping asynchronous transfers with computations inside the same group.

## 3.4 FP8 low‑precision Tensor Cores: layout constraints and benefits  

FP8 has become part of Hopper’s standard portfolio alongside BF16 and FP16 thanks to extremely high arithmetic density:

- **GEMM throughput:** For FP8 tensors (`e4m3`) WGMMA achieves roughly twice the FLOPS per cycle compared with FP16 or BF16.
- **Memory efficiency:** Each scalar occupies eight bits versus sixteen or thirty-two bits for higher formats.
  
But achieving this speedup requires adhering rigidly to operand layout rules:

### 3.4.1 Operands in SMEM – mn-major vs k-major

For an $M\times K$ product $A \times B^\top$ ($d = K$ equals head dimension), operands may be laid out as:
- **mn-major:** contiguous along $M$ or $N$
- **k-major:** contiguous along $K$

On Hopper:
- **FP16 WGMMAs** accept both mn-major and k-major operands.
- **FP8 WGMMAs** *only* accept operands in k-major form when sourcing from shared memory.

Since FlashAttention normally keeps whole query rows ($B_r$ rows × $d$ columns) contiguously in row-major order (`mn-major`) inside shared memory, we cannot directly feed them into an FP8 WGMMA if it expects k-major layout for B—a problem we solve by performing an **in-kernel transpose** using `ldmatrix`/`stmatrix` instructions after loading V tiles into register file (`RMEM`). The logs show these instructions broadcast 8×8 fragments efficiently across threads so that while permutation occurs we simultaneously feed Tensor Cores with properly laid-out tiles.

### 3.4.2 Accumulator layout mismatch

A second subtlety arises from how WGMMA manages intermediate accumulators in FP32 (`Q_F32 × K_F8` → accumulator). The accumulator representation differs from how operand A appears when second WGMMA multiplies by V (`P_F8 × V_F8`). The solution consists of:
1. Performing an explicit byte-permutation on registers post first WGMMA,
2. Adjusting V’s transposed layout so its rows align with accumulator columns,
3. Using CUDA's low‑level shuffle or permute primitives just once per block rather than broadcasting shuffles across all threads.

These tweaks are critical because they avoid building ad-hoc software fusion loops that would otherwise squander GPU cycles; every byte counts when you have eight tokens per register lane!

### 3.4.3 Quantization & Accuracy

While theoretical speedups exist under pure FP8 arithmetic due solely to operand size reduction, naïve scaling often produces unacceptable error because LLM weight matrices contain occasional outlier magnitudes that compress poorly under uniform scalings (`v_i → scale·v_i`).
