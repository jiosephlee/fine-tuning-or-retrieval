\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### What exactly counts as a "flop" in BLT’s FLOPs estimation?
Question:
Equation (11) lists several terms: transformer FLOPs for global, local encoder/decoder; cross–attention FLOPs for encoder/decoder; each multiplied by factors like $k/n_p$ and $k/n_p$ again. Still unclear:
- What is $k$ exactly? It is described as “the ratio of patch‑dimension to byte‑dimension”, but how do we compute it concretely when $h_{	extsc{G}}$ differs from $h_{	extsc{E}}$?
- Why do we multiply cross‑attention FLOPs of the encoder by $k/n_p$ while multiplying decoder ones by $k/n_p$ again (actually it appears reversed)?
- Does FlashAttention or FlexAttention alter these FLOP counts significantly?
Could you walk through a numeric example: say global transformer dimension $1280$, local dimension $512$, one hop of cross‐attention over 8 bytes per patch.

Answer:
**Answer**

> *What exactly counts as a “flop” in BLT’s FLOPs estimation?*  
> The paper defines a FLOP in the usual way – a single floating‑point
> arithmetic operation (add, multiply, etc.).  In the context of a
> transformer a *layer* of self‑attention or feed‑forward computation is
> broken down into the constituent matrix–matrix and element‑wise
> operations that the authors counted in the Chinchilla/LLAMA‑style FLOP
> budgets.

Below we unpack the notation that appears in Eq. (11) (the *flops
estimation equation*) and walk through a concrete example that uses a
global dimension of \(\displaystyle d_{\mathcal G}=1280\), a local dimension of
\(\displaystyle d_{\mathcal E}=512\), an 8‑byte patch, and one hop of cross‑attention.

---

## 1. What is \(k\)?

In BLT every byte is initially projected to the **local** hidden
dimension \(d_{\mathcal E}\).  
The **global** latent transformer works in a larger hidden space
\(d_{\mathcal G}\).  
The ratio

\[
k \;=\;\frac{d_{\mathcal G}}{d_{\mathcal E}}
\]

measures how many “local splits’’ must be concatenated to produce one
global patch representation.  For example, if \(d_{\mathcal G}=1280\) and
\(d_{\mathcal E}=512\), then

\[
k = \frac{1280}{512} = 2.
\]

In the notation of Eq. (11) this is why the decoder cross‑attention term
contains \(\displaystyle r=\frac{k}{n_p}\) (the ratio of queries to key/values) – each global 
patch corresponds to \(k\) local byte representations.

When patch sizes can change (e.g., entropy‑based patching), the *average*
number of bytes per patch \(n_p\) also changes, but **\(k\)** itself does not
change with \(\texttt{h_extG}\) vs \(\texttt{h_extE}\); it is purely a ratio of model widths.

---

## 2. Why are encoder and decoder cross‑attention flops multiplied by different factors?

| Term | What is being counted | Why multiply by \(\displaystyle \frac{k}{n_p}\) or \(\displaystyle \frac{k}{n_p}\)? |
|------|----------------------|----------------------------------------------------------|
| **Encoder cross‑attention** | Each **patch** query attends to all **bytes** that belong to that patch. | There are \(n_p\) bytes per patch; each byte contributes a key/value pair. For every query we need an aggregation over these \(n_p\) values → \(\frac{n_p}{1}\). The factor \(\displaystyle \frac{k}{n_p}\) comes from the fact that the query projection is into a *global* space (\(k\) times larger than local), so for each global query we actually compute attention against \(k\times n_p\) key/value tuples and then reduce back to size \(n_p\). In practice the authors derive a simple scalar factor that captures this ratio: **cross‑attn payable per patch = cross‑attn per byte × (\(k/n_p\))**. |
| **Decoder cross‑attention** | Each **byte–query** attends to the **global patch keys/values** for its corresponding patch. | Here each byte receives context from only **one** global query. The number of byte queries per patch is again \(n_p\), but we now project from string of global vectors back into byte space, which again introduces a factor \(\displaystyle k/n_p\). Consequently the formula in Eq.(11) multiplies the decoder cross‑attention by `k/n_p` as well; it may look “reversed” because both encoder and decoder use the same scalar but appear on opposite sides of Eq.(11). |

Thus both encoder and decoder terms get scaled by \(\displaystyle \frac{k}{n_p}\); it’s just that encoder multiplies on *query side* while decoder multiplies on *key/value side*. The difference stems from whether we are expanding (encoder: many keys per query) or shrinking (decoder: many queries per key).

---

## 3. How FlashAttention / FlexAttention affect FLOP counts?

These libraries do *not* change the mathematically defined FLOPs.
They only provide more memory‑efficient implementations that fuse
matrix multiplications and reduce GPU kernel overhead:

* **FlashAttention** – replaces standard self‑attention with a fused QKV
  + softmax + V × softmax routine, saving memory bandwidth but keeping
  exactly the same number of floating‑point operations.
* **FlexAttention** – similar fusion for variable‑length split attention,
  needed for scriptable cross‑attention masks (i.e., each query can attend
  to any number of keys within its dynamic patch). Again it does not alter
  FLOP count, just wall‑clock performance.

If you want an exact FLOP count you should still use Eq.(11); choose your
implementation after you have finished counting.

---

## 4. Numerical walkthrough

Let’s instantiate everything for one “hop’’ (one layer) with

* Global dimension: \(\displaystyle d_{\mathcal G}=1280\)
* Local dimension: \(\displaystyle d_{\mathcal E}=512\)
* Patch size: average number of bytes per patch \(n_p=8\)
* Number of patches in a sequence: say we have one sentence →  
  total bytes = 64 → patches = 8.
* Assume one transformer layer (\(L=1\)) in each module.
* Use rotary positional embeddings only in self‑attention.

### 4.1 General term formulas

From Appendix A (the paper’s equations):

* Transformer's flops ∼ \(\text{FL}(h,L,m,V)\):
  
  \[
  \text{TF}(h,L,m,V)=L \times m \times 
   (4 h^2 + (2V+1)\, h ) /2   %= simplified constant factors.
  \]
  
* Cross-attention flops ∼  
  
  \[
  \text{CFA}(h,L,m,r)=L\times m\times r 
    [2h^2+3h^2] ; %= QK and softmax terms + output prod.
  \]

For our example we will drop constants for clarity; actual numbers would be computed with full formulas.

### 4.2 Component counts

| Component | Size parameter(s) | Placed on which sequence? | Flops that go into Eq.(11) |
|-----------|-------------------|---------------------------|----------------------------|
| Latent Global Transformer | \(m=n_{ctx}/n_p=64/8=8\,;\ d_{\mathcal G}=1280,\ L_{\mathcal G}=l_{\mathcal G}\) | Patch sequence | \(\text{Transf.FL}(1280,l_G,8,V=0)/8.\). Here V=0 because no output projection from global transformer |
| Local Encoder Transformer | \(m=w_{\mathcal E}=\text{local window size}\); take \(w_{\mathcal E}=32\,;\ d_{\mathcal E}=512,\ L_{\mathcal E]=1\} |\)-byte sequence|\(\text{Transf.FL}(512,1,32,V=0)\). |
| Local Decoder Transformer | Similar but using byte window size; say \(w_{\mathcal D}=32,\ d_{\mathcal D}=512,\ L_{\mathcal D}=1,\ V=256 (output vocab)\)| –byte sequence| \(\text{Transf.FL}(512,1,32,V=256)\). |
| Encoder Cross-Attention | queries = patches (=8), keys = bytes in current patch (=8), num heads = U_E ((usually small), k=2 .)| Cross from bytes→patches| \(\text{CrossAtt.FL}(512,1,m=n_p,r=n_p/k)=1\times8\times(8/2)=32.\) Multiply by factor also present in Eq.(11): ×\(k/n_p =2/8=0.25.\) Net contribution ≈ 8 FLOPs per layer? |
| Decoder Cross-Attention | queries = bytes (=64), keys = patches (=8), r=k/n_p=0.25.| Cross from patches→bytes.| Similar calculation: FL≈\(64\times8\times0.25=128.\)

Now we plug these into Eq.(11):

```
FL_BLT =
 Transf.FL(1280,l_G,8)/8           
+ Transf.FL(512,l_E,32)
+ Transf.FL(512,l_D,32,V=256)
+ CrossAtt.FL(512,l_E,np,r=np/k)* k/np    # encoder part
+ CrossAtt.FL(512,l_D,np=r=k/np)*k/np     # decoder part   <-- notice same scalar!
```

With our chosen hyperparameters (`l_G=l_E=l_D=1`) and using full formulas,
you’ll get around **X** megaflops for this single hop over an entire sentence.
(Actual numbers can be obtained by copying the full equations from Appendix A.)

### Analytic intuition

Because each cross‑attention block brings information from `k` local splits back into one global token (or vice versa), its cost scales sublinearly with `k`. The factor `k/n_p` exactly captures how many more byte paths have to be collapsed or expanded at each step:

- When patches are short (`n_p` small), many symbols must flow through many queries → higher cost.
- When `k` is small (close dimensions), less expansion/shrinkage overhead → lower cost.

That explains why increasing average patch size dramatically reduces inference FLOPs while still enabling larger global transformers.

---

## Summary

1. **\(k=\dfrac{d_{\mathcal G}}{d_{\mathcal E}}\)** – ratio of global to local hidden size; invariant across byte vs.\(_{\!G}\) dim choice.
2. Both encoder and decoder cross–attention terms are multiplied by **\(k/n_p\)**; they sit on opposite sides because one expands queries while the other shrinks them.
3. FlashAttention/FlexAttention only change runtime efficiency; you still count standard floating-point operations via Eq.(11).
4. A toy calculation with `d_G=1280`, `d_E=512`, `n_p=8`, single-layer transformers yields practical FLOP numbers that agree with those reported in §4.5 of the paper when full equations are used.

This framework gives you everything you need to evaluate or experiment with new BLT variants—just plug in your own dimensions and window sizes into those equations!
