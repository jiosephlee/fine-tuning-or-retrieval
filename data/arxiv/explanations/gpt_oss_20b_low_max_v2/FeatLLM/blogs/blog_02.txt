# Rule‑Based Features From ChatGPT: The Engine Behind Few‑Shot Tabular Success

In the past decade, large language models (LLMs) have become the go‑to tool for solving complicated reasoning tasks.  What if those same models could help us learn from tiny amounts of labeled data, **without** having to run a gigantic transformer on every new record?  The answer lies in an approach called **FeatLLM**, which turns an LLM into a *feature engineer* rather than a predictive black box.  Below we unpack how this works, focusing on the prompt design, the two‑step reasoning process, and the translation of generated rules into compact binary features that a simple linear model can exploit.

---

## Why Tabular Few‑Shot Learning is Hard

Most tabular datasets contain dozens of heterogeneous columns—integers, floats, categories, dates—yet only a handful of samples are labeled.  With such *low‑shot* data we risk overfitting or learning spurious correlations that vanish once we gather more examples.  Conventional models (logistic regression, XGBoost, random forests) can still perform reasonably well, but they rely purely on the data at hand and have no way to inject domain knowledge that might exist in a large pretrained language model.

FeatsLLM solves this by asking ChatGPT (or any other LLM) to *think* like an expert scientist: “What conditions on these columns would signal disease X?”  These conditions become our new features.

---

## The Prompt – A Recipe for Rule Extraction

FeatsLLM’s prompt is carefully scaffolded into three parts.  Think of it as giving ChatGPT a short “cheat sheet” followed by *instructional coach* guidelines.

| Section | Purpose | How it’s written |
|---------|---------|------------------|
| **1️⃣ Basic Information** | Describe the task and tell ChatGPT what every column is about. |  
- A clear question: e.g., “Does this patient’s myocardial infarction history suggest chronic heart failure?”  
- Feature descriptions with type hints (`numeric`, `categorical`, `ordinal`).  
- A few dozen example lines formatted as “`f_1 is …; f_2 is …; Answer: Yes/No`.” |
| **2️⃣ Reasoning Instruction** | Encourage two‑step logical reasoning. |  
- *Step 1*: “First, think about general medical knowledge that relates these features to heart failure.”  
- *Step 2*: “Now look at the examples and write ten concrete rules that distinguish the two classes.” |
| **3️⃣ Response Instruction** | Dictate a strict format so we can parse rules automatically. |  
- Each rule must start with `Rule i:` followed by one clause per line.  
- Quantitative comparisons use symbols (`>`, `<`, `=`).  
- Logical conjunctions are expressed with plain text (`AND`, `OR`). |

By feeding all three parts together, we ensure the model first draws on its training corpus (general domain knowledge) before looking at concrete data samples to refine its hypotheses.

---

## Two‑Step Reasoning – How ChatGPT Avoids Spurious Correlations

### Step 1 – Prior Knowledge Search
ChatGPT scans its internal knowledge base for causal or correlational links between feature types and the target. For example, a medical LLM might recall that “age > 50” often co‑occurs with heart failure. This step anchors the rule search in scientifically plausible territory and filters out misleading patterns.

### Step 2 – Data‑Driven Refinement
Given those plausible connections, ChatGPT now looks at the few labeled examples and crafts **exact thresholds or category matches** that separate the classes in the sample set. It writes something like:

```
Rule 1: Age > 50
Rule 2: Prior MI history = Yes
Rule 3: Cholesterol > 200
Rule 4: Current smoker = Yes OR Diabetic = Yes
…
```

Because only a handful of examples are used, each rule must be broad enough to generalize beyond them but specific enough to capture real predictive structure.

---

## Turning Natural Language into Binary Features

Now we have a list of human‑readable rules but how do we feed them into machine learning?

1. **Parse with an LLM:**  
   The same GPT engine is employed again, this time inside the codebase. It receives:
   - The schema of admissible fields.
   - The raw training sample.
   - The textual rule set.
   It outputs tiny Python snippets such as:

   ```python
   def rule_1(x): return x["Age"] > 50
   def rule_2(x): return x["Prior_MI"] == "Yes"
   ...
   ```

2. **Execute rules per instance:**  
   For every record in both training and test sets we evaluate each rule; result → `0` or `1`. Each rule becomes one binary column—essentially a *handcrafting* step powered by language.

3. **Learn importance with a linear model:**  
   We collect all binary columns for every class (say `R = 10` rules per class). For class `k` each sample produces vector \( \mathbf{z}_k \in \{0,1\}^R\). We fit:

   \[
   \text{logit}_k = \max(\mathbf{w}_k , 0) \cdot \mathbf{z}_k,
   \quad
   p_k = \text{Softmax}([\text{logit}_1,\dots,\text{logit}_c]).
   \]

   Training uses cross‑entropy on just those few bright samples; no neural nets or gradient-based fine‑tuning are required for inference—a single matrix multiply per class!

---

## Ensemble & Bagging – Making It Robust

Because an LLM can occasionally produce noisy or redundant rules, FeatLLM repeats the whole pipeline many times (e.g., \(T=20\)). Each run uses different temperatures or random shuffles of demonstration ordering (LLMs are sensitive to order). Then we average probabilities across runs:

\[
p^{\text{final}}_k = \frac{1}{T}\sum_{t=1}^T p_k^{(t)}.
\]

This ensemble improves stability much like random forests make tree decisions stable by averaging. Importantly—it never requires running ChatGPT for **every** test record; it only queried once per ensemble.

---

## Why This Beats Conventional LLM Inference

Typical LLM pipelines for tabular data do:

- Serialize entire table row → feed into GPT → generate prediction directly.
- Must pass each record through GPT at inference time.
- Scaling fails when tables exceed prompt limits or contain many features.

FeatLLM sidesteps these bottlenecks:

- **Inference cost:** After initial rule generation (a handful of API calls), predictions use a lightweight linear model.
- **Prompt size:** During rule extraction we only send keys that appear in demonstrations; thanks to bagging only a subset of features need appear in any single prompt.
- **Training freedom:** No need for gradient updates inside GPT; you may just use public inference APIs.

In practice FeatLLM outperforms existing few‑shot baselines—including XGBoost with dozens of shots—and scales gracefully across datasets ranging from adult income prediction to synthetic sequence classification.

## Quick Summary

| Step | What Happens | Why It Matters |
|------|--------------|----------------|
| 1️⃣ Prompt Design | Context + evidence + format instructions | Locks down grammar & focuses reasoning |
| 2️⃣ Two‑Step Reasoning | Prior knowledge → check actual data → rules | Filters out noise & reduces overfitting |
| 3️⃣ Parsing Rules | Convert NLP rule statements → Python code | Automates feature construction |
| 4️⃣ Linear Weighting | Learn importance per rule via tiny logistic layer | Keeps inference cheap & fast |
| 5️⃣ Bagging / Ensembling | Multiple independent rule sets & averages probabilities | Boosts robustness & combats missing features |

## Take‑Away Messages

* An LLM can be used as a **knowledge base** rather than an end‑to‑end predictor.
* By turning latent reasoning into concrete binary tests you get:
  * Highly interpretable features (“Age>50”, “Cholesterol>200”).
  * Low‑cost inference suited to real deployments.
* FeatLLM demonstrates that *few‐shot* success in tabular learning isn’t just about clever loss functions—it’s also about leveraging humanlike reasoning patterns encoded inside large language models.

So next time you face a high‑dimensional dataset but only have limited labels, consider asking an LLM to be your feature engineer instead of your predictor—chatful precision, lean inference time, and surprisingly strong performance await!
