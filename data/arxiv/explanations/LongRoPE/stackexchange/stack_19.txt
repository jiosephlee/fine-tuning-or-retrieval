### How is passkey retrieval at 2M tokens executed within memory constraints?
Question:
For the passkey task up to 2,048k context, prefill attention is \(O(L'^2)\) compute and memory if done in one shot, which seems infeasible. Did you use chunked prefill, streaming with KV cache, or other engineering to run inference? Could you outline the exact inference procedure (batch size, precision, number of GPUs, peak memory) used to obtain the reported accuracy curves?
Answer:
Short answer: the paper does not compute a full $O(L'^2)$ prefill in one shot. Instead LongRoPE relies on standard streaming / chunked evaluation and KV caching (i.e., amortized autoregressive attention) and evaluation with sliding windows so that you never materialize a full $L'\times L'$ attention matrix. The manuscript explicitly states the method “reuses most pre‑existing optimizations” and evaluates long contexts with sliding/chunked windows (e.g., Books3 uses a sliding window of 256k). The paper does not publish a single “one-shot prefill” memory / GPU table for the passkey curves, so exact peak memory / GPU counts for inference are not given.

Why a one‑shot prefill would be infeasible (intuitive): computing full self‑attention for length $L'$ at once requires storing an $L'\times L'$ attention matrix (and K/V for every layer), so memory and compute scale as $O(L'^2)$. For $L'=2{,}048\text{k}$ that is astronomically large and impractical. In practice you avoid the $O(L'^2)$ step by never computing attention between all pairs of $L'$ tokens at once.

What the paper actually does (grounded to text)
- The evaluation setup: passkey retrieval places a five‑digit passkey uniformly at a random location across the evaluation context length and repeats 10 iterations (this is the passkey protocol used to produce the accuracy curves). For extremely long books (Books3) they used a sliding window of 256k for perplexity evaluation; search/perplexity evaluations used only a few long samples (3–5 items) rather than thousands of full‑2M sequences. These points are stated in the Experiments/Setup sections.
- The paper repeatedly says the extended models “reuse most pre‑existing optimizations” and that during inference they “dynamically adjust the corresponding RoPE rescale factors.” That implies inference is the usual streaming autoregressive pattern where RoPE parameters are adjusted per token length, but attention is computed incrementally.

How this is implemented in practice (what you should assume or implement to reproduce the curves)
- Use autoregressive streaming with a KV cache: prefill in chunks and append new tokens while retaining the cached keys and values for earlier tokens. Each new token’s attention cost is $O(L_{\text{cached}})$ for that step, and the total work across generating (or scanning) $L'$ tokens is $O(L'^2)$ in compute over the whole sequence but never requires materializing the full attention matrix in memory at once; importantly, memory usage is dominated by storing cached K/V tensors ($O(L'\cdot d_{\text{key}})$ per layer) rather than an $L'\times L'$ matrix.
- Evaluate with chunked prefill or sliding windows: when you only need to compute metrics (perplexity / whether the model outputs the passkey), you can process the long document in chunks (the paper used a sliding window size of 256k for Books3 perplexity evaluation). For passkey retrieval you can stream the prompt and the document and detect generation output as soon as the model emits the passkey.
- Use mixed precision and sharded KV/cache: run the model in fp16 (or bfloat16) and shard the KV cache across multiple GPUs (tensor / pipeline / model parallelism) so that per‑GPU KV storage remains feasible. The paper reports fine‑tuning setups (e.g., LLaMA2 fine‑tuning used global batch 32; 128k training used 8×A100 and 256k used 16×A100), and search/evaluation used only a few long samples — but it does not list the exact inference GPU count/peak memory.

What the paper does not provide (and therefore cannot be asserted as a fact)
- The paper does not give an explicit “prefill in one shot vs chunked” code path or a table with batch size, precision, number of GPUs and peak memory used to draw the passkey curves. It therefore does not report the exact per‑run peak memory numbers for the passkey experiments.

A practical recipe to reproduce the passkey curves consistent with what the paper says
1. Load the LongRoPE‑modified model weights (with dynamic RoPE rescale factors for the tested evaluation length).
2. Use fp16 / bfloat16 for model weights and activations.
3. Stream the long context in chunks (e.g., 64k–256k tokens per chunk used for the sliding window), updating the KV cache incrementally and never forming an $L'\times L'$ attention matrix.
4. Shard the model and KV cache across multiple GPUs (the paper used multi‑A100 clusters for fine‑tuning; inference commonly uses several GPUs for 7B models at million‑token lengths). Keep batch size = 1 (single sequence) for passkey retrieval evaluation to avoid extra memory pressure.
5. For passkey retrieval run 10 trials per length with the passkey placed uniformly at random and record whether the model outputs the passkey; this is exactly the evaluation protocol described.

If you want precise peak memory / GPU counts to match the paper’s curves you will need to re‑run the evaluation on your target hardware and report those numbers because the paper gives the experimental protocol (chunked evaluation, sliding windows, a few long samples, dynamic RoPE) but not a single canonical hardware/peak‑memory table for inference.

Summary: LongRoPE avoids infeasible one‑shot $O(L'^2)$ prefill by using standard streaming / chunked evaluation with a KV cache and sliding windows, adjusting RoPE factors dynamically for the target length. The paper documents the evaluation protocol (passkey placement, number of trials, sliding window size for Books3) and the training/search resources, but it does not publish exact per‑run inference GPU/peak‑memory figures — you will need to reproduce those on your hardware (use fp16, shard KV, chunk at 64k–256k, batch size 1).
