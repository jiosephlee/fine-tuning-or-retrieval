\title{Stack Exchange of the Paper: LongRoPE}

### How exactly is perplexity computed during search for samples longer than \(L'\)?
Question:
The optimization problem specifies inputs \(\mathbf{X}\) where each document length exceeds \(L'\). During fitness evaluation, do you:
- Take the first \(L'\) tokens and compute NLL on the next-token targets across that range?
- Use a sliding window of size \(L'\) and average losses across windows?
- Evaluate only on the tail to stress long-range dependencies?
Clarity on this evaluation protocol would help interpret the reported perplexities and search outcomes.
Answer:
Short answer: during search LongRoPE computes perplexity as the exponentiated average next-token negative log‑likelihood over sliding windows of length equal to the target context length $L'$. Practically they sample documents with $|\mathbf{x}|\ge L'$, apply the candidate RoPE rescale factors to the model, run the model over windows of size $L'$ (with a fixed stride used in evaluation) and average the per‑token NLLs across all tokens in those windows; perplexity = $\exp(\text{mean NLL})$. This is exactly what they describe in the Search and Experiments sections.

Why this is the protocol (intuitively and technically)
- The optimization objective in Eq. (6) is the next‑token loss $\mathcal{L}$ for inputs $\mathbf{X}$ with length at least $L'$. To estimate $\mathcal{L}$ for a candidate RoPE configuration you must evaluate next‑token probabilities on sequences of length $L'$, so the natural quantity is the average next‑token NLL over those tokens.
- Evaluating on entire long documents once would be expensive and biased by document endpoints; a sliding‑window evaluation (paper: “We evaluate perplexity at various context lengths using sliding window of 256.” and for very long Books3 evaluation they use a sliding window of 256k) produces many length-$L'$ contexts from each long document, covers different relative token positions, and yields a low‑variance estimate for perplexity while keeping per‑inference memory bounded.
- The paper’s Search setup states they pick samples with minimum length equal to the target $L'$ and compute perplexity on those samples (Search: “Perplexity is calculated using 5 random PG19 validation set samples, with a minimum length requirement of the target context length.”; for $>512\text{k}$ windows they use 3 Pile‑Books3 samples). That confirms they evaluate on full length-$L'$ contexts extracted from longer documents.

What is averaged exactly
- For each sliding window of tokens of size $L'$ they compute per‑token NLLs for the next‑token prediction targets (standard language‑model loss). They average the NLLs over all tokens in all windows used for that candidate. Perplexity is then $\exp\big(\text{mean NLL over all evaluated tokens}\big)$.
- The candidate RoPE mapping (including the “no interpolation for first $\hat n$ tokens” rule) is applied when constructing the positional encoding used for the tokens in those windows, so the evaluation reflects both per‑dimension rescale factors and the token‑position threshold.

Why this matters for interpreting search results
- Because they average NLL across sliding windows, the search score reflects performance across many relative token positions, not only the document tail. That is important because the method explicitly searches both per‑dimension $(\lambda_i)$ and per‑position $(\hat n)$ non‑uniformities: the sliding windows ensure the evaluation samples positions that test whether preserving early token RoPE (the $\hat n$ design) helps overall next‑token loss.
- When the paper reports using fewer validation samples for very large $L'$ (3 instead of 5), this makes the evaluation cheaper but slightly higher variance, so reported perplexities for giant $L'$ have more sampling noise.

Summary
LongRoPE’s search evaluates a candidate RoPE by running the model on length-$L'$ contexts extracted from longer documents via a sliding window, computing next‑token NLLs across those windows, averaging the NLLs, and reporting perplexity as $\exp(\text{mean NLL})$. This is consistent with the descriptions in the Search and Experiments sections (sample selection, sliding‑window stride, and number of validation samples).
