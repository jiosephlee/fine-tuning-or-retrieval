### How do you compute perplexity for very long contexts during search without prohibitive cost?
Question:
Evaluating perplexity at lengths like 256k or higher can be extremely expensive if done naively due to quadratic attention in the prefill. What practical steps did you take during search to keep evaluation tractable? For example:
- Do you use a sliding window and cache K/V across windows?
- Any approximations, chunked attention, or reduced precision?
- Typical wall-clock time and GPU memory for one fitness evaluation at 256k and at 2M tokens?
Answer:
Short answer: the paper avoids doing full quadratic prefill over millions of tokens by (a) evaluating perplexity on a few long samples with sliding / chunked windows (so each model eval only handles manageable window sizes), (b) drastically reducing the number of candidate evaluations via search-level optimizations (seeded initials, monotonicity constraint, smaller populations for very large targets), and (c) trading off sample count / population size when the target length grows. The paper does not claim any special KV-cache across windows or exotic approximate attention; it keeps search/evaluation tractable by engineering the search procedure and the evaluation protocol rather than changing attention internals.

Details and intuition drawn from the paper
- Sliding / chunked evaluation: when reporting perplexity at long lengths the authors use sliding windows rather than scoring an entire $2\text{M}$ sequence in a single forward pass. For most experiments they use a sliding window stride of $256$ tokens for computing perplexity (PG19 / Proof-pile evaluation). For the Books3 $2\text{M}+$ evaluation they state using a sliding window of $256\text{k}$. The practical effect is that each forward pass only attends over a limited window (the window size), so you never have to do a single attention prefill over the whole mega-sequence in one shot. Intuitively: computing loss with a sliding window turns a single huge quadratic cost into many smaller quadratic costs that are each tractable and can be batched/streamed.

- Very small sample count per candidate: during search the perplexity used as the fitness is computed on a tiny set of long validation samples. For target lengths within $256\text{k}$ they compute perplexity on 5 random PG19 validation samples (each at least the target length). For windows $>512\text{k}$ they halve the search population and compute perplexity on only 3 random Books3 samples. Reducing the number of evaluation samples reduces wall-clock cost linearly while still giving a signal good enough for evolutionary search.

- Search-level pruning and seeding to avoid wasted expensive evaluations: the evolution search is designed to dramatically reduce the number of distinct RoPE candidates that need full perplexity evaluation. The initial population includes PI/NTK/YaRN candidates (so you start near reasonable solutions), and they enforce a monotonicity constraint on the per-dimension scale factors ($\lambda_i \le \lambda_{i+1}$). That constraint both aligns with NTK intuition and eliminates vast regions of the search space so far fewer full perplexity evaluations are needed. For very large target lengths they also reduce population / mutation sizes (halved for $>512\text{k}$), further limiting expensive evaluations.

- No special approximate or chunked attention algorithm is described: the paper does not claim to change the attention mechanism to a sub-quadratic or chunked-attention implementation for search. Likewise it does not report using an explicit KV cache across sliding windows in the search description. The approach is “keep model and attention unchanged, but evaluate loss over chunked windows + reduce number of evaluations.” In other words, they reuse standard autoregressive evaluation (with existing engineering optimizations available in model runtimes) rather than invent a new attention approximation.

- Precision / hardware choices are not detailed for search: the paper gives GPU counts and training settings for fine-tuning (e.g., A100s for $128\text{k}/256\text{k}$ fine-tune setups) but does not report special reduced-precision tricks or exact per-eval memory/time numbers for fitness computation. Therefore the paper does not supply exact wall-clock or memory numbers for a single fitness evaluation at $256\text{k}$ or $2\text{M}$ tokens.

What the paper explicitly reports (so you can rely on it)
- For search of target $\le 256\text{k}$: population $P=64$, mutation/crossover sizes $16$, mutate probability $0.3$, iterations $T=40$, perplexity computed on 5 PG19 samples with minimum length = target length.
- For target $>512\text{k}$: they halve population and mutation/crossover sizes, and compute perplexity on 3 Pile-Books3 samples.
- Sliding window stride and window sizes used for evaluation: $stride=256$ for PG19/Proof-pile; Books3 evaluation uses sliding windows of $256\text{k}$.

Practical takeaways / recommendations (consistent with the paper)
If you need to reproduce a similar search without prohibitive cost, chunk your evaluation into windows, evaluate on a tiny number of representative long samples, and aggressively reduce the number of candidate evaluations by seeding & constraining the search space. If you must reduce per-eval runtime further, you can layer additional engineering (KV caching across adjacent windows, $fp16$ / $bf16$ inference, or approximate attention) — but those are not part of the LongRoPE paper itself, and would be orthogonal optimizations.

Caveat about timing/memory: the paper does not provide per-evaluation wall-clock or GPU memory figures for $256\text{k}$ or $2\text{M}$-token fitness evaluations, so I cannot give exact numbers from the paper. The concrete cost you observe will depend on model size, attention implementation, batch size and whether you apply $fp16$/$bf16$ and KV caching in your runtime.
