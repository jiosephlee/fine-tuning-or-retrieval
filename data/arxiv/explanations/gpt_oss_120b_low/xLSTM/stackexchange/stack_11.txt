\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### What are the theoretical limitations of sLSTM’s non‑parallelizability?
Question:
The paper notes that sLSTM cannot be parallelized because of memory mixing, yet they provide a fast CUDA kernel that is only twice slower than mLSTM. How does this kernel achieve parallelism across time steps (e.g., using scan operations), and what are the fundamental algorithmic barriers that prevent full parallelization?
Answer:
**Answer**

The sLSTM variant introduced in *xLSTM: Extended Long Short‑Term Memory* inherits the classic recurrent connection “hidden → hidden” that couples every time step to the next one.  
Because the cell update

$$
c_t = f_t\,c_{t-1}+ i_t\,z_t ,\qquad 
n_t = f_t\,n_{t-1}+ i_t
$$

and the gate pre‑activations (e.g. \(\tilde i_t = w_i^\top x_t + r_i h_{t-1}+b_i\)) contain a term proportional to \(h_{t-1}\), the forward computation of \(h_t\) cannot be expressed as a function of the current input alone; it needs the *exact* hidden state produced at the previous step.  This “memory mixing” creates a data‑dependency chain of length equal to the sequence length, which is why a naïve implementation must run strictly sequentially.

### How the fast CUDA kernel works

Even though the recurrence cannot be broken, one can still hide much of the latency by exploiting two ideas that are standard in high‑performance RNN implementations:

1. **Kernel‑level fusion and register tiling** – All gate pre‑activations, the exponential (or sigmoid) non‑linearities, and the two linear recurrences for \(c_t\) and \(n_t\) are computed inside a single CUDA kernel.  The kernel loads a small “tile” of the input sequence (for example 64 timesteps) into registers, computes the gates for each step, and then updates the two scalars \((c, n)\) in register space.  Because registers reside on‑chip, each step of the recurrence costs only a few arithmetic operations without any global‑memory traffic.

2. **Explicit loop unrolling over a short window** – Within a tile the recurrence is executed in a tight loop; after each tile finishes, the final \((c,n)\) values are written back to global memory and become the initial state for the next tile.  This approach is exactly what “scan” (prefix‑sum) algorithms do, except that here we have **two coupled scans** (the cell state and its normalizer).  The dependence still exists, but it is confined to a tiny number of steps that fit entirely in registers, so the GPU can keep all warps busy while waiting for memory.

Because only two scalar values have to be carried across tiles, the amount of data that must be transferred between successive kernel launches is negligible.  The overall wall‑clock time therefore scales almost linearly with sequence length, and on modern GPUs the kernel reaches *$\approx 2\times$* the throughput of the fully parallelizable mLSTM (which can be expressed as a single matrix scan without any hidden‑to‑hidden link).

### Fundamental algorithmic barriers

The speedup described above is essentially as good as one can get without breaking the recurrence:

* **Data dependency** – The hidden state \(h_{t-1}\) appears inside every gate’s affine transformation.  Any attempt to compute \(h_t\) before \(h_{t-1}\) would produce mathematically incorrect results.  This is unlike mLSTM where all gates depend only on the current input (\(x_t\)) and on a *matrix* memory that is updated additively; there is no hidden‑to‑hidden term, so one can rewrite the whole update as a *scan* over independent contributions.

* **Non‑linear coupling of two recurrences** – sLSTM maintains both a cell state \(c_t\) and a normalizer state \(n_t\).  They are updated with identical forget / input gates, so they cannot be eliminated or merged into a single linear recurrence.  The double‑scan eliminates neither dependency nor arithmetic complexity; it only lets us compute both scans together while keeping everything in fast on‑chip storage.

* **Memory mixing across multiple heads/cells** – When sLSTM is extended with several cells or heads, each head has its own hidden‑to‑hidden weight matrices \(\mathbf R_{\*}\).  Even if we could parallelise within a single head, inter‑head mixing forces an additional sequential pass because each head’s output becomes part of the next head’s input at every time step.

Because these ingredients are intrinsic to sLSTM’s design (they give sLSTM its ability to “revise storage decisions” via exponential gating), they cannot be removed without changing the model’s expressive power.  Consequently, full parallelisation—i.e. computing all timesteps simultaneously as in Transformers—is impossible for sLSTM; we are limited to *intra‑tile* parallelism implemented by tightly fused CUDA kernels.

### Bottom line

The authors’ CUDA implementation attains near‑optimal performance for an inherently sequential model by:

* fusing all per‑step operations into one register‑level kernel,
* processing short tiles of timesteps in an unrolled loop (a scan over a very small window), and
* moving only two scalar states between tiles.

These tricks reduce memory traffic and hide latency but cannot eliminate the fundamental hidden‑to‑hidden dependency that defines sLSTM.  Hence sLSTM will always remain at least *O(T)* in wall‑clock time with respect to sequence length, whereas mLSTM—by discarding memory mixing—can be written as a true parallel scan and achieves full GPU parallelism.
