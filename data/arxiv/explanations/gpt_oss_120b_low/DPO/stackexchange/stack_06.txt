\title{Stack Exchange of the Paper: "Direct Preference Optimization: Your Language Model is Secretly a Reward Model"}

### How does DPO handle the combinatorial explosion of possible completions when computing the loss over a batch of preference pairs?
Question:
The DPO loss in Eq. (6) requires evaluating \(\pi_\theta(y\mid x)\) and \(\pi_{\text{ref}}(y\mid x)\) for both the winner and loser completions of each pair. In practice, do we need to enumerate all tokens of each completion, and does this incur a large computational overhead compared to PPO which samples trajectories? How is this implemented efficiently for large models (e.g., 6B parameters) and long sequences?
Answer:
**Answer**

The DPO loss (Eq. 6) is evaluated on a *fixed* list of preference pairs  
\((x, y_{w}, y_{l})\) that have already been generated (usually once, with the
reference model \(\pi_{\text{ref}}\)).  
During fine‑tuning we never have to consider **all** possible completions of the
prompt; we only need the log‑probability that the current policy \(\pi_{\theta}\)
assigns to the two strings that appear in the dataset.  Consequently the
computation is no more expensive than a standard supervised‑learning forward
pass, and it is actually cheaper than the PPO pipeline because no trajectories
are sampled on‑the‑fly.

### What is actually computed?

For each example we need the quantities  

\[
\log \pi_{\theta}(y_{w}\mid x),\qquad
\log \pi_{\theta}(y_{l}\mid x),\qquad
\log \pi_{\text{ref}}(y_{w}\mid x),\qquad
\log \pi_{\text{ref}}(y_{l}\mid x).
\]

Because language models factorise the sequence probability into a product of
token‑level conditional probabilities, we obtain the log‑probability of the
whole completion by summing the per‑token log‑probs:

\[
\log \pi_{\theta}(y\mid x)=\sum_{t=1}^{|y|}\log
\pi_{\theta}(y_{t}\mid x, y_{<t}) .
\]

Thus, for a given pair we run a **single** forward pass of the transformer,
feeding the prompt \(x\) followed by the tokens of \(y_{w}\) (or \(y_{l}\))
and accumulating the log‑probs.  The reference model’s log‑probs are obtained
in exactly the same way; in practice they are cached from the first time the
dataset is built, so during training we only need the forward pass of the
current model \(\pi_{\theta}\).

### No enumeration of the combinatorial space

The “combinatorial explosion’’ you are worried about would arise only if we had
to marginalise over *all* possible completions of \(x\).  DPO sidesteps this
because the Bradley‑Terry preference model depends **only on the difference of
rewards** for the two observed completions:

\[
p(y_{w}\succ y_{l}\mid x)=\sigma\!\Bigl(\beta\,
\bigl[\log \tfrac{\pi_{\theta}(y_{w}\mid x)}{\pi_{\text{ref}}(y_{w}\mid x)}
      -\log \tfrac{\pi_{\theta}(y_{l}\mid x)}{\pi_{\text{ref}}(y_{l}\mid x)}\bigr]\Bigr).
\]

No other sequences enter the loss, so we never need to enumerate or sample a
large set of alternatives during training.

### Comparison to PPO

PPO also works with a fixed batch of preference data, but it first samples a
new trajectory from \(\pi_{\theta}\) at every optimisation step in order to
estimate the expected reward \(\mathbb{E}_{y\sim\pi_{\theta}}[r_{\phi}(x,y)]\).
Each PPO update therefore requires **two forward passes per token** (one for
the policy, one for the value‑function baseline) *and* a Monte‑Carlo estimate
of the return, which can be noisy and needs many samples to reduce variance.

DPO eliminates the sampling loop entirely:

* **Forward‑only**: the loss depends only on the log‑probabilities of the two
  stored completions; we never back‑propagate through a reward model or a
  value network.
* **Batchable**: the two completions for each prompt can be concatenated into
  a single batch, so a 6‑billion‑parameter model can be trained on a single
  GPU (or a small GPU cluster) using the same mixed‑precision, gradient‑
  accumulation tricks that are already standard for supervised fine‑tuning.
* **No extra variance**: the weighting term
  \(\sigma(\hat r_{\theta}(x,y_{l})-\hat r_{\theta}(x,y_{w}))\) is computed
  analytically from the same logits, so the gradient signal is deterministic
  given the batch.

### Practical implementation tricks

1. **Teacher‑forcing forward pass** – we feed the whole target string (prompt +
   completion) to the model and mask the loss so that only the completion tokens
   contribute to the summed log‑probability.  This is identical to the
   “next‑token‑prediction’’ loss used in supervised fine‑tuning.

2. **Caching reference log‑probs** – the reference model \(\pi_{\text{ref}}\) is
   usually the SFT checkpoint.  Its log‑probabilities for every \(y_{w}\) and
   \(y_{l}\) are computed once when the dataset is built and stored on disk.
   At training time we only read those scalars, which is negligible compared to
   the forward pass of \(\pi_{\theta}\).

3. **Mixed‑precision and gradient accumulation** – because the loss is just a
   sum of a few scalar log‑probabilities per example, the memory footprint is
   dominated by the activations needed to compute the logits.  Using
   FP16/BF16 and gradient accumulation lets us train 6 B‑parameter models on a
   single 48 GB GPU, similar to ordinary SFT.

4. **Column‑wise batching** – we arrange the batch as \([x, y_{w}], [x,
   y_{l}]\) pairs, which lets the transformer reuse the prompt encodings for the
   two completions (the first \(|x|\) transformer layers are identical).  Modern
   libraries (e.g. HuggingFace ‘Trainer’, DeepSpeed, or PyTorch ‘accelerate’)
   automatically share the KV‑cache for the prompt tokens, further reducing
   compute.

### Bottom line

The “combinatorial explosion’’ of possible completions does **not** appear in
the DPO training loop because the loss is evaluated only on the *observed*
winner–loser pairs.  Computing \(\pi_{\theta}(y\mid x)\) for a given
completion requires a single forward pass and a sum over its token log‑probs,
exactly the same cost as a standard supervised language‑model fine‑tune.  In
practice DPO is therefore comparable in wall‑time to ordinary SFT and
significantly cheaper and less noisy than PPO, even for 6 B‑parameter models
and sequences that are several hundred tokens long.
