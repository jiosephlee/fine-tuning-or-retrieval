\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Why is a non‑negative constraint applied to the linear weights in Eq. (2)?
Question:
The model computes `logit_k = max(w_k, 0) · z_k`. I would have expected a standard linear model with unrestricted weights. What is the intuition behind forcing weights to be non‑negative? Does this prevent rules from decreasing a class likelihood, and could it harm performance when a rule is actually indicative of the *absence* of a class? How does this design interact with the ensemble averaging across trials?

Answer:
In **Eq. (2)** the class‑specific logit is computed as  

$$
\text{logit}_k = \max(\mathbf w_k,\,0)\,\cdot \mathbf z_k ,
\qquad \mathbf z_k\in\{0,1\}^R ,
$$

i.e. each weight is first passed through a ReLU so that only **non‑negative** values can affect the logit.  
At first glance this looks unusual because a ordinary linear model would allow the weight to be either positive or negative, thereby letting a feature *decrease* the score of a class. The authors deliberately forbid this for three intertwined reasons that follow directly from the way the features are constructed.

---

### 1.  Features are **binary rule indicators**  

Each component $z_{k,r}$ tells whether the $r$‑th rule that was generated for class $k$ is satisfied by the example (1) or not (0).  
If a rule truly belongs to class $k$, then every sample that satisfies it should be *more* likely to belong to that class. Conversely, a rule that does **not** belong to class $k$ should simply have little influence; it should not actively push the prediction **away** from $k$.  
By restricting the weight to be non‑negative, the model can only *add* evidence for a class; it cannot subtract evidence on the basis of a rule that was authored for that same class.

---

### 2.  Preventing **self‑cancelling** contributions and making learning stable in the few‑shot regime  

When only a handful of labelled examples are available, estimating a negative weight reliably is difficult – a single outlier could drive a weight negative and cause the model to over‑penalise a rule that is actually useful.  
If negative weights were allowed, two rules for the same class could end up with opposite signs and cancel each other out, effectively discarding information that the LLM has already distilled into human‑readable conditions.  
The ReLU projection guarantees that every learned weight either keeps the rule (positive magnitude) or discards it (zero). This “hard‑selection” behaviour matches the intuition of *feature bagging*: rules that are not supported by the few labelled points will simply receive weight zero after training.

---

### 3.  Compatibility with **ensemble averaging** across trials  

The full FeatLLM pipeline runs many independent LLM queries (different temperatures, shuffled demonstrations, bagged subsets of columns/instances) and averages the resulting class probabilities.  
If some trial assigned a negative weight to a rule while another trial gave it a positive weight, their contributions would cancel in the ensemble average, reducing the benefit of having diverse rule sets.  
Because each trial can only assign non‑negative importance, averaging merely combines *evidence* from different rule collections; there is no risk of systematic negation across trials. In practice this makes the ensemble more robust: even if an individual trial generates a few spurious rules, those rules will be given zero weight after training and will not drag down the averaged probability.

---

### Does this prevent a rule from indicating **absence** of a class?

A rule that describes an *absence* (“age < 30”, “blood‑pressure = low”, …) is still encoded as a binary feature that is *true* when the condition holds. The model can give this feature a large positive weight, thereby raising the logit for the class whenever the absence‑type condition is met. The sign of the *semantic* statement (“absence” vs “presence”) is captured by how we write the rule, not by allowing negative weights. If we wanted to penalise a class when a certain condition holds, we would simply generate that condition as a rule for **the opposite** class; its positive weight would then act as an implicit negative influence on the original class after softmax normalisation.

---

### Summary

The non‑negative constraint on $\mathbf w_k$ is an architectural choice that aligns with how FeatLLM treats LLM‑generated rules:

* it ensures each binary rule can only contribute *positively* to its own class,
* it makes learning robust when only a few labelled examples are available,
* it avoids destructive interference between rules within a trial and between different ensemble members,
* and it does not limit expressive power because “absence” information can be encoded directly in the rule wording.

Consequently, this design helps FeatLLM turn noisy natural‑language rules into reliable, learnable features without sacrificing performance even when some rules are misleading or when rules for different classes overlap.
