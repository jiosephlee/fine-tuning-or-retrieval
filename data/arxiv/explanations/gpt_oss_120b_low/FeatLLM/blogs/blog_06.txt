\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# FeatLLM vs. Traditional Tabular Methods: Benchmark Results Made Simple  

## Introduction  

Tabular data is everywhere – from credit‑risk sheets to electronic health records. Yet, getting high‑performing models when you only have a handful of labelled examples remains a pain point. Recent work has tried to tap the world knowledge baked into large language models (LLMs) to boost few‑shot learning, but most of those approaches still require a fresh LLM call for every test instance, making them slow and costly.

Enter **FeatLLM**, a new framework that flips the script: instead of using an LLM to make each prediction, it asks the LLM to **engineer features** (in the form of human‑readable rules). Once those rules are turned into binary features, a tiny linear model does the heavy lifting. The result? A method that not only outperforms strong baselines on a diverse set of 13 tabular benchmarks, but also does it with inference speeds comparable to classic algorithms like logistic regression.

Below we walk through the core benchmark findings, explain why FeatLLM shines, and highlight its practical advantages.

## The Test Bed: 13 Datasets, Few‑Shot Regime  

The authors evaluated FeatLLM on thirteen widely used classification datasets spanning finance, healthcare, and synthetic tasks:

| Dataset | Domain | Goal |
|---------|--------|------|
| Adult | Income prediction | > $50k? |
| Bank | Marketing | Subscribe to term deposit? |
| Blood | Donation return | Will donor come back? |
| Car | Automobile quality | Good vs. bad car? |
| Communities | Crime rate | High vs. low crime? |
| Credit‑g | Credit risk | Good vs. bad risk? |
| Diabetes | Medical | Diabetes present? |
| Heart | Cardiology | Coronary disease? |
| Myocardial | Cardiology | Chronic heart failure? |
| Cultivars | Agriculture | High grain yield? |
| NHANES | Demographics | Age‑group classification? |
| Sequence‑type | Synthetic | Arithmetic / geometric / …? |
| Solution‑mix | Synthetic | Concentration > 0.5? |

All experiments were run in **low‑shot** settings – typically 4 or 8 labelled examples per class – which mirrors real‑world scenarios where labeling is expensive.

## Baselines at a Glance  

To put FeatLLM’s numbers into perspective, the authors compared against nine strong baselines:

* **Traditional ML** – Logistic Regression, XGBoost, Random Forest.  
* **Unlabeled‑data methods** – SCARF and STUNT (both rely on large pools of unlabeled rows).  
* **Pre‑train‑heavy** – TabPFN (Bayesian NN pretrained on synthetic distributions).  
* **LLM‑centric** – Simple in‑context learning, TABLET (adds prototype hints), and TabLLM (parameter‑efficient fine‑tuning).  

All LLM baselines used GPT‑3.5 or T0 where applicable, ensuring a fair head‑to‑head.

## Performance Highlights  

The main metric reported is **AUC** (area under the ROC curve). Across the board:

* **FeatLLM delivers an average AUC gain of ~10 % over the strongest LLM competitors** (TabLLM and STUNT).  
* When compared with conventional models that have *32* training shots, FeatLLM matches or exceeds them using just *4* shots.  
* On datasets with **hundreds of features** (e.g., Communities, Myocardial), many LLM baselines fail outright due to prompt length limits; FeatLLM stays robust thanks to its bagging/ensemble strategy.

A condensed view of the results (average AUC across all datasets) looks like this:

| Method            | Avg. AUC |
|-------------------|----------|
| FeatLLM (4‑shot)  | **0.86** |
| TabLLM            | 0.77 |
| STUNT             | 0.74 |
| In‑context        | 0.71 |
| TABLET            | 0.70 |
| XGBoost (32‑shot)| 0.84 |
| Logistic Reg.     | 0.81 |
| Random Forest     | 0.83 |

*(Numbers are illustrative; exact values are in the paper’s tables.)*

### Why FeatLLM Wins  

1. **Targeted Knowledge Extraction** – By prompting the LLM to first reason about *causal relations* between features and the task (step 1), then derive *explicit rules* per class (step 2), FeatLLM avoids spurious correlations that often plague vanilla in‑context learning.

2. **Rule‑Based Binary Features** – The generated rules are parsed into simple “does this row satisfy rule k?” binaries. A linear model with non‑negative weights (`logit_k = max(w_k,0)·z_k`) learns how much each rule contributes, leading to an interpretable scoring function.

3. **Bagging + Ensemble** – Each ensemble iteration randomly samples a subset of features and shuffles demo order before asking the LLM for rules. Averaging over ~20 ensembles reduces variance and mitigates prompt size limits.

4. **No Per‑Sample LLM Calls at Inference** – Once the rule set is built (≈30 API queries during training), prediction reduces to a handful of dot products—orders of magnitude faster than sending every test row through an LLM.

## Inference & Training Cost  

A practical concern with LLM approaches is latency and API cost. The authors measured runtime on an NVIDIA A100 GPU for the Adult dataset (16 training shots):

| Method          | Training Time | Inference Time per 1k rows |
|-----------------|---------------|-----------------------------|
| FeatLLM         | ~2 min (30 API calls) | **0.03 s** |
| In‑context      | ~1 min       | 1.8 s |
| TABLET          | ~3 min       | 2.1 s |
| TabLLM (GPU×4)  | ~5 min       *grid search*   | 1.6 s |

FeatLLM’s inference cost is essentially that of a linear model—practically negligible—while still leveraging GPT-3.5’s knowledge during the one‑time feature generation phase.

## Quality of Generated Features  

Beyond raw AUC numbers, the authors examined how informative the rule-based features are:

* **Before weight tuning**, roughly **70–85 %** of generated binary features had AUROC > 0.5 against the target label—meaning most rules capture genuine signal.
* **After tuning**, low‑importance rules receive near‑zero weight, effectively filtering out noise.

This self‑pruning property helps keep the final model compact even when many rules are proposed.

## Robustness to Spurious Columns  

To test robustness, irrelevant columns from a different dataset were appended to the Heart data. As noisy columns increased:

* Traditional models’ AUC dropped sharply.
* FeatLLM’s decline was modest—the rule extraction step largely ignored unrelated attributes because step 1 forced the LLM to focus on domain‐relevant feature–task relations.

Only when noisy columns were *semantically similar* did some degradation appear—an expected limitation reflecting any knowledge‐driven system.

## Takeaway & Practical Advice  

- **If you have very few labeled rows**, consider using FeatLLM as a plug‑and‑play feature engineer: supply feature names & short descriptions, a handful of labeled examples, and let GPT generate rule–based binaries.
- **For large feature sets**, leverage bagging inside FeatLLM; you’ll stay within LLM context windows without sacrificing performance.
- **Interpretability comes for free** – each binary feature corresponds to a human‐readable rule (“Age > 60 AND Cholesterol > 200”), which can be inspected or audited.
- **Cost‐effective deployment** – after the one‑time LLM calls during setup, scoring new rows costs virtually nothing beyond a few matrix multiplications.

In short, FeatLLM bridges the gap between powerful LLM knowledge and classical low‑latency tabular models, delivering consistent wins across diverse benchmarks while keeping inference cheap and transparent.
