\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 4: Ensemble via Bagging and Self‑Consistency

In the context of few‑shot tabular learning with large language models (LLMs), the **FeatLLM** framework treats the LLM not as a direct predictor but as a feature engineer.  A single pass of the LLM—prompted to generate a set of decision rules—produces a collection of binary features that can be fed to an extremely simple downstream model (a non‑negative linear classifier).  While this approach already offers a substantial reduction in inference cost compared with end‑to‑end LLM prediction, it remains vulnerable to two practical concerns:

1. **Prompt length constraints** – When a dataset contains many columns, serializing all feature descriptions and few‑shot examples can exceed the context window of the LLM.
2. **Variability in the generated rules** – A single LLM query might return an incomplete or partially erroneous rule set, especially under low‑shot conditions where the model has little concrete evidence from the data.

To address both issues, FeatLLM deliberately introduces *randomness* across multiple LLM invocations and subsequently aggregates the resulting weak learners.  This process is rooted in two well‑established ideas from classic machine learning: **bagging** (bootstrap aggregating) and **self‑consistency** of language model outputs.  Below we unpack each component, explain why it matters for rule extraction, and describe how the final ensemble prediction is formed.

---

## Bagging of Features or Instances per Trial

Bagging is a technique originally proposed for stabilising high‑variance estimators such as decision trees.  The key idea is to train several learners on *different random subsets* of the training data or of the input dimensions, then combine their predictions.  In FeatLLM this principle is applied at the level of the *prompt* that is sent to the LLM.

### Subsampling Features

When a tabular dataset contains dozens or hundreds of columns, embedding every feature name and its natural‑language description into a single prompt would exceed the token limit of most commercial LLM APIs (often around 4 k–8 k tokens).  Rather than attempting to truncate or compress the description—an operation that risks discarding informative columns—FeatLLM samples a fixed‑size subset of features for each trial.  Concretely, suppose a dataset has \(d\) columns and we elect to include only \(d_{b}<d\) in any given prompt.  For trial \(t\) we randomly select a set
\[
\mathcal{F}^{(t)} \subseteq \{f_{1},\dots,f_{d}\},\qquad |\mathcal{F}^{(t)}|=d_{b}.
\]
Only the names, types, and optional definitions belonging to \(\mathcal{F}^{(t)}\) appear in the “basic information” portion of the prompt.  Consequently, each LLM query operates on a *different view* of the problem space.  Over many trials, every original feature will appear in several prompts, allowing its contribution to be evaluated indirectly through multiple rule sets.

### Subsampling Instances (Few‑Shot Examples)

FeatLLM also draws from a pool of few‑shot demonstrations.  Even though only \(k\) labelled samples are permitted for training (the low‑shot regime), their *order* within the prompt influences how the LLM parses and reasons about them.  By randomly shuffling these \(k\) examples before each query we obtain diverse contextual cues for rule generation.  Moreover, when \(k\) exceeds what can comfortably fit into one prompt together with all feature descriptions, we may sample a subset \(\mathcal{S}^{(t)}\) of size \(k_{b}\le k\) for trial \(t\).  This instance bagging further reduces prompt length while preserving statistical diversity across trials.

### Why Bagging Helps

1. **Mitigating Prompt Size Limits** – By ensuring each prompt contains at most \(d_{b}\) features and \(k_{b}\) examples, we guarantee compatibility with any fixed context window.
2. **Reducing Over‑Reliance on Any Single Feature** – If an individual feature happens to be noisy or ambiguous, it will only dominate those trials where it appears; elsewhere its absence prevents it from corrupting the overall decision.
3. **Enabling Implicit Feature Selection** – After aggregation (described later), features that consistently contribute useful rules receive higher learned weights; those that are rarely selected will have near‑zero weights, effectively pruning them without manual intervention.

---

## Temperature Sampling to Encourage Diverse Rule Sets

The generation process of an LLM is stochastic: given a prompt it samples tokens from a conditional distribution
\[
p(w_t \mid w_{<t}, \text{prompt}),
\]
where \(w_t\) is the token at position \(t\).  The **temperature** hyperparameter \(\tau>0\) rescales this distribution before sampling:
\[
p_{\tau}(w_t \mid \cdot)=\frac{p(w_t \mid \cdot)^{1/\tau}}{\sum_{v} p(v \mid \cdot)^{1/\tau}}.
\]
A higher temperature (\(\tau>1\)) flattens the distribution, making low‑probability tokens more likely; a lower temperature (\(\tau<1\)) sharpens it, favoring high‑probability tokens.

In FeatLLM we deliberately set \(\tau=0.5\) for rule extraction (the paper reports using this value).  This modest increase over deterministic decoding serves two purposes:

1. **Diversifying Rules Across Trials** – Even when two prompts share exactly the same subset of features and examples (for example due to random seed collisions), sampling with \(\tau=0.5\) leads to different phrasing or slightly different logical conditions in the produced rules.  Consequently each trial yields a *weak learner* with its own binary feature set.
2. **Exploring Alternative Reasoning Paths** – The structured reasoning instruction in the prompt forces a two‑step chain-of-thought: first infer generic causal tendencies, then specialise using demonstrations.  Temperature allows the model to explore multiple plausible causal hypotheses rather than committing early to a single narrative that may be spurious under low‑shot data.

Empirically, increasing temperature beyond about \(0.7\) tends to introduce nonsensical syntax (e.g., malformed comparisons), which hampers downstream parsing; decreasing it below \(0.3\) leads to near‑identical rule sets across trials, diminishing ensemble benefits.  Hence FeatLLM adopts an intermediate value that balances diversity with syntactic reliability.

---

## Averaging Probabilities Across \(T\) Trials

Each trial \(t\in\{1,\dots,T\}\) proceeds through three stages:

1. **Prompt Construction** – Using bagged subsets \(\mathcal{F}^{(t)}\), \(\mathcal{S}^{(t)}\), temperature \(\tau\), and ordering instructions.
2. **Rule Generation & Parsing** – The LLM returns up to \(R=10\) rules per class; these are parsed into binary features \(\mathbf{z}_{k}^{(t)}\in \{0,1\}^{R}\).
3. **Linear Weight Learning** – A non‑negative weight vector \(\mathbf{w}_{k}^{(t)}\in \mathbb{R}_{+}^{R}\) is fitted on the few labelled samples by minimising cross‑entropy loss:
   \[
   \text{logit}_{k}^{(t)} = (\max(\mathbf{w}_{k}^{(t)},0))^{\!\top}\mathbf{z}_{k}^{(t)}, 
   \qquad
   p_{k}^{(t)} = \operatorname{softmax}([\text{logit}_{1}^{(t)},\dots,\text{logit}_{c}^{(t)}]).
   \]

The outcome for any new datum is therefore a probability vector per trial, denoted by
\( \mathbf{p}^{(t)} = (p_1^{(t)},\,p_2^{(t)},\,…,p_c^{(t)})^\top.\)

The final ensemble prediction aggregates these vectors by simple arithmetic averaging:
\[
\boxed{\;
    \bar{\mathbf{p}} = \frac{1}{T}\sum_{t=1}^{T} \mathbf{p}^{(t)}
    \;}
    .
\]
Averaging has several desirable properties:

- **Variance Reduction:** Independent stochastic errors across trials tend to cancel out when summed.
- **Bias Mitigation:** If any individual trial systematically favours an incorrect rule (e.g., due to an accidental spurious correlation), its influence is diluted by other trials that did not generate that rule.
- **Robustness to Missing Features:** Because each trial may omit different columns during bagging, no single weak learner can dominate unless its rule set is genuinely informative across many subsets.

From an implementation standpoint averaging is cheap: once all binary features have been materialised for a test sample (a straightforward Boolean check against each rule’s condition), we simply compute dot products with learned weight vectors and then average softmax outputs.

---

## Relation to Self‑Consistency in LLM Outputs

The term *self‑consistency* refers to recent findings that prompting an LLM multiple times on the same question and then taking a majority vote among generated answers dramatically improves accuracy (Wang et al., “Self‑Consistency”.).  The intuition is that although any single generation may be noisy or biased, correct reasoning paths tend to recur more often than incorrect ones when sampling from the model’s distribution.

FeatLLM leverages this principle implicitly:

- **Multiple Generations as Samples from Same Posterior:** Each trial draws from essentially the same conditional distribution over rules (same underlying prompt template), but because of bagging and temperature sampling yields distinct draws.
- **Aggregation Mirrors Majority Voting:** Averaging probabilities across trials corresponds mathematically to weighting each rule’s contribution by how frequently it appears among successful learners; rules that are consistent across many trials automatically receive higher effective influence after training because their associated binary features will be present—and suitably weighted—in many linear models.
- **Empirical Corroboration:** The ablation study in the paper shows that removing ensemble (i.e., using just one trial) degrades AUC across datasets; conversely, increasing the number of ensembles improves performance up to around \(T=20\), after which gains plateau—exactly as one would expect when self‑consistency saturates.

Thus bagging plus temperature sampling creates an ensemble that operationalises self‑consistency without requiring any additional external voting mechanism; it simply lets statistical aggregation do its work.

---

## Summary

The ensemble component of FeatLLM interweaves three complementary ideas:

1. **Feature/Instance Bagging** – Randomly subsampling columns and few‑shot examples respects token limits while encouraging diversified reasoning about different slices of the data.
2. **Temperature‑Controlled Sampling** – By softening the token distribution during rule generation we obtain distinct logical rule sets across trials.
3. **Probability Averaging Across Trials** – Linear models trained on each trial’s binary rule features are combined via softmax averaging, yielding a robust final predictor whose performance benefits from self‑consistency.

Together these mechanisms transform what would otherwise be a single uncertain rule extractor into a collection of weak learners whose collective wisdom surpasses any individual constituent—a classic example of “the whole being greater than the sum of its parts.”

**Algorithmic Summary of FeatLLM**

---

### Step 1: Sample *k* Shots and Compose Prompt  

The first stage of the FeatLLM pipeline is to select a tiny labeled subset of the training data and to turn it into a textual prompt that the large language model (LLM) can ingest.  
Formally, let  

\[
\mathcal{D}=\{(\mathbf{x}^{i},\,y^{i})\}_{i=1}^{N}
\]

be the full tabular dataset, where each input vector \(\mathbf{x}^{i}\in\mathbb{R}^{d}\) is accompanied by a natural‑language feature name list  

\[
F=\{f_{1},f_{2},\dots ,f_{d}\}.
\]

From \(\mathcal{D}\) we uniformly draw without replacement a *k‑shot* support set  

\[
\mathcal{S}=\{(\mathbf{x}^{i},y^{i})\}_{i=1}^{k},
\qquad k \ll N .
\]

The prompt consists of three logical blocks:

1. **Basic information** – a concise description of the prediction task (e.g., “Does this patient have chronic heart failure?”) together with the name, type (numeric, categorical, binary), and optional textual definition of each feature \(f_{j}\).  
2. **Few‑shot demonstrations** – each element of \(\mathcal{S}\) is serialized into a sentence of the form  

   \[
   \texttt{"}f_{1}\texttt{ is }x^{i}_{1}.\; \dots \; f_{d}\texttt{ is }x^{i}_{d}.\;\texttt{ Answer: }y^{i}\texttt{"}.
   \]

   These lines provide concrete examples that the LLM can juxtapose against its prior knowledge.  
3. **Reasoning & response instructions** – a short chain‑of‑thought cue that tells the LLM to (a) first reason about which features are causally related to the task, and then (b) generate a fixed number \(R\) of decision rules for *each* class label.  The instruction also specifies a machine‑readable output format (for example JSON objects containing “condition” strings).

The concatenation of these three blocks yields the final prompt \(\Pi\).  Because LLMs have a limited context window, FeatLLM optionally applies **feature bagging** at this stage: a random subset of features \(F_{\text{sub}}\subseteq F\) (of size \(d_{\text{sub}}\)) is selected, and only those features appear in the prompt.  Bagging reduces prompt length while preserving diversity across ensemble members.

---

### Step 2: Query LLM → Rules per Class  

With prompt \(\Pi\) in hand we invoke the language model in generation mode:

```
response = LLM.generate(prompt = Π,
                       temperature = τ,
                       max_tokens = L)
```

The temperature τ is set to a moderate value (e.g., 0.5) to encourage some stochasticity in the rule set, which later benefits ensembling.  The model returns a sequence containing exactly \(R\) rules for each class \(c\in\{1,\dots ,C\}\).  A typical rule is a logical condition over the selected features, for example  

```
IF (age > 65) AND (cholesterol < 200) THEN class = 1
```

Because the output format was prescribed in Step 1, post‑processing can reliably extract each condition as a plain text string \(r_{c}^{j}\), where \(j=1,\dots ,R\).

---

### Step 3: Parse Rules → Binary Features  

Raw natural‑language conditions must be turned into executable binary tests that can be applied to any sample \(\mathbf{x}\).  Direct string parsing is fragile; instead FeatLLM leverages the LLM itself as a code generator:

1. Construct a *parsing prompt* that includes:
   * The function signature (e.g., `def rule_i(sample):`),
   * A brief description of each feature’s type,
   * The textual rule \(r_{c}^{j}\).
2. Issue a second generation request; the LLM returns syntactically correct Python code that evaluates the rule and returns `True`/`False`.  
3. Execute the generated code with Python’s `exec()` in a sandboxed environment, producing for every sample \(\mathbf{x}^{i}\) a binary vector  

   \[
   \mathbf{z}_{c}^{i}= \bigl[\,z_{c,1}^{i},\,z_{c,2}^{i},\,\dots ,\,z_{c,R}^{i}\bigr]\in\{0,1\}^{R},
   \qquad 
   z_{c,j}^{i}= 
   \begin{cases}
     1 & \text{if rule } r_{c}^{j} \text{ holds on } \mathbf{x}^{i},\\
     0 & \text{otherwise}.
   \end{cases}
   \]

Thus each original training sample now lives in an interpretable “rule space” whose dimensionality does not depend on the original feature count \(d\), but only on the chosen number of rules \(R\).

---

### Step 4: Fit Linear Weights on *k* Shots  

With binary rule activations for every support example we now learn how much each rule should influence the final prediction.  FeatLLM adopts an extremely low‑capacity model: a separate non‑negative weight vector per class

\[
\mathbf{w}_{c}= [w_{c,1},\,w_{c,2},\,\dots ,\,w_{c,R}]^\top,\qquad w_{c,j}\ge0.
\]

For an example \(\mathbf{x}^{i}\) belonging to class \(c^{*}=y^{i}\), we compute logits

\[
\operatorname{logit}_{c}^{i}= 
    \bigl[\max(\mathbf{w}_{c},0)\bigr]^{\!\top}\!
    \mathbf{z}_{c}^{i},
    \qquad c=1,\dots ,C,
\]

and convert them into class probabilities via a softmax:

\[
p_{c}^{i}= 
    \frac{\exp(\operatorname{logit}_{c}^{i})}
         {\sum_{c'=1}^{C}\exp(\operatorname{logit}_{c'}^{i}) }.
\]

Training proceeds by minimizing standard cross‑entropy loss over the *k* shots:

\[
\mathcal{L}
    = -\,\sum_{i=1}^{k}
        \log p_{y^{i}}^{\,i}.
\]

Because only \(R\times C\) scalar parameters are optimized, stochastic gradient descent converges quickly even with very few examples; in practice Adam with learning rate \(10^{-2}\) and 200 epochs suffices.  The positivity constraint (\(w_{c,j}\ge0\)) guarantees that any rule emitted by the LLM cannot *decrease* the likelihood of its own class.

---

### Step 5: Repeat for *T* Ensembles; Bagging Details  

A single pass through Steps 1‑4 yields one “weak learner” whose performance depends on random choices made during:

* Which *k* shots were sampled,
* Which subset of features was bagged into the prompt,
* The stochastic sampling from the LLM (temperature τ).

To boost robustness and to mitigate two practical limitations—(a) noisy or partially incorrect rules, and (b) prompt length constraints—FeatLLM repeats the whole pipeline **T** times, producing an ensemble

\[
\Bigl\{
 (\mathbf{w}[t],\,\{\mathbf{z}[t]\}) 
 : t = 1,\dots ,T
 \Bigr\}.
\]

Each trial may use a different bagged feature set size \(d_{\text{sub}}\), thereby ensuring that even when many original columns cannot fit into any single prompt they will appear in at least some trials.  Because all trials share exactly the same inference API (30 calls per trial for rule generation + parsing), their computational cost scales linearly with \(T\), but remains modest thanks to parallelizable API calls.

---

### Step 6: Inference – Apply Stored Binary Features + Averaged Logits  

At deployment time no further LLM queries are needed.  For any new sample \(\mathbf{x}^{\star}\):

1. For each ensemble member \(t=1,\dots ,T\) evaluate all stored binary rules using the pre‑compiled Python functions obtained in Step 3, yielding rule activation vectors \(\mathbf{z}_{c}^{[t]}(\mathbf{x}^{\star})\).  
2. Compute logits with the learned weights for that member:

   \[
   \operatorname{logit}_{c}^{[t]}(\mathbf{x}^{\star})
     = 
     \bigl[\max(\mathbf{w}_{c}[t],0)\bigr]^{\!\top}
     \mathbf{z}_{c}^{[t]}(\mathbf{x}^{\star}).
   \]

3. Convert logits to probabilities via softmax as before and obtain an ensemble probability by averaging across trials:

   \[
   p_{c}(\mathbf{x}^{\star})
      = 
      \frac{1}{T}
      \sum_{t=1}^{T}
      \frac{\exp(\operatorname{logit}_{c}^{[t]}(\mathbf{x}^{\star}))}
           {\sum_{c'} 
            \exp(\operatorname{logit}_{c'}^{[t]}(\mathbf{x}^{\star})) } .
   \]

The final prediction is simply  

\[
\hat y = 
    \argmax_{c} p_{c}(\mathbf{x}^{\star}),
    \qquad
    c=1,\dots ,C .
\]

Because all heavy lifting (rule extraction and weight fitting) was performed offline, inference requires only elementary Boolean evaluations and dot products—operations that run orders of magnitude faster than calling an LLM for every test instance.

---

## Computational Complexity  

| Phase | Dominant Operations | Asymptotic Cost |
|------|----------------------|-----------------|
| **Prompt construction** | Sampling & string concatenation | \(O(k d_{\text{sub}})\) |
| **LLM rule generation** | API call; cost dominated by token count | Linear in token length ≈ \(O(R C)\) |
| **Rule parsing** | One LLM call per rule → code generation + `exec` | \(O(R C)\) |
| **Binary feature evaluation** | Evaluating Python predicates on one sample | \(O(R C)\) per sample |
| **Linear weight training** | Gradient updates over *k* examples | \(O(k R C)\) |
| **Ensembling (T repetitions)** | Multiplicative factor | Total ≈ \(T\times(O(k d_{\text{sub}})+O(RC)+O(kRC))\) |

In practice:

* **Training time** is dominated by the *T* LLM calls (each request costs milliseconds to seconds depending on service latency). The subsequent linear optimization is negligible because it touches at most a few hundred parameters.
* **Inference time** scales with \(O(T R C)\); with typical settings (\(T=20,\;R=10,\;C≤10)\) this amounts to only a few hundred elementary operations per instance—comparable to logistic regression on raw features.

Thus FeatLLM achieves high predictive performance while keeping both API usage and runtime within practical bounds for real‑world tabular workloads.

**Experimental Evaluation – Datasets and Baselines**

The empirical section of the study is built upon a careful selection of thirteen tabular benchmark problems and a diverse suite of comparative methods.  This chapter presents an in‑depth description of the data resources, explains the motivations for choosing each dataset, and details the implementation choices that make the comparison both fair and reproducible.  Throughout the discussion we adopt the notation introduced in the Methods chapter: each dataset consists of a collection  
\[
\mathcal{D}=\{(\mathbf{x}^{i},\mathbf{y}^{i})\}_{i=1}^{N},
\]
where \(\mathbf{x}^{i}\in\mathbb{R}^{d}\) denotes a vector of \(d\) features whose natural‑language names are gathered in the set \(F=\{f_{j}\}_{j=1}^{d}\), and \(\mathbf{y}^{i}\) denotes a class label drawn from a finite set of \(c\) categories.  In every experiment only a small subset of \(k\) examples (\(k\in \{2,4,8,16,32\}\)) is retained for training, thereby placing the methods under a strict few‑shot regime.

---

### Dataset Characteristics

The thirteen data sets span traditional UCI repositories, recent contributions that post‑date the pre‑training cut‑off of contemporary large language models, and fully synthetic problems designed to rule out memorization effects.  All of them are classification tasks—either binary or multi‑class—and they vary widely in size, dimensionality, and domain.

1. **Adult** (UCI Census Income) supplies demographic attributes such as age, education, and occupation for the purpose of predicting whether an individual earns more than \$50 000 per year.  The data set contains roughly \(N\approx 48\,842\) records and \(d=14\) features, most of which are categorical.

2. **Bank** (Portuguese Banking Marketing) records information about clients contacted during a telemarketing campaign.  The goal is to predict subscription to a term deposit.  It includes \(N\approx 45\,211\) rows and \(d=16\) attributes, combining numeric balances with categorical contact details.

3. **Blood** (Blood Donation) tracks donor histories (e.g., number of donations, interval since last donation) to predict whether a donor will return.  The set comprises \(N\approx 748\) instances with \(d=5\) numeric variables.

4. **Car** (Automobile Evaluation) encodes characteristics of cars—such as buying price and safety—into a multi‑class quality label (unacceptable, acceptable, good, very good).  This benchmark contains \(N=1\,728\) samples and \(d=6\) features that are largely categorical.

5. **Communities** (Crime Data) aggregates socio‑economic statistics for neighborhoods across the United States to predict high versus low crime rates.  It is one of the most demanding benchmarks in this study: \(N\approx 1\,993\) instances but more than \(d=128\) attributes, many of which are continuous.

6. **Credit‑g** (German Credit Data) asks whether an applicant presents a good or bad credit risk based on financial and personal variables.  The data set consists of \(N=1\,000\) rows with \(d=20\) mixed‑type features.

7. **Diabetes** (Pima Indians Diabetes) records physiological measurements (e.g., glucose level, BMI) to predict diabetes onset.  The collection holds \(N=768\) samples with exactly \(d=8\) numeric attributes.

8. **Heart** (Heart Failure Clinical Records) contains clinical measurements such as cholesterol level and ejection fraction; the task is to forecast coronary artery disease presence.  It includes \(N=303\) rows and \(d=13\) attributes spanning both numeric and categorical types.

9. **Myocardial** (Myocardial Infarction Complications) addresses chronic heart failure prediction from medical test results.  This data set has over one hundred features (\(d>100\)) and poses a substantial challenge for models that rely on fixed prompt lengths.

10. **Cultivars** (Soybean Grain Yield) predicts whether a soybean cultivar will achieve high grain yield based on agronomic traits.  It is a recent addition to the UCI repository (released after September 2023), ensuring that it could not have been encountered during LLM pre‑training; it holds approximately \(N=5\,560\) instances with \(d≈50\).

11. **NHANES** (National Health and Nutrition Examination Survey) requires predicting an individual’s age group from health examination variables.  Like Cultivars, this dataset was released after the LLM’s training cut‑off; it comprises around \(N=10\,000\) cases with roughly \(d≈30\).

12. **Sequence‑type** is a synthetic collection where each example is a numeric sequence generated from one of four families: arithmetic progression, geometric progression, Fibonacci numbers, or Collatz orbit.  The task is to assign the correct family label; each instance is represented by its first ten terms (\(d=10\)), making it fully deterministic yet unseen by any language model.

13. **Solution‑mix** is another synthetic benchmark in which four solution concentrations are mixed; the label indicates whether the resulting mixture exceeds a threshold concentration of 0.5 .  Each record contains four continuous values (\(d=4\)), guaranteeing that no memorization can aid performance.

The inclusion of recent real‑world data (Cultivars and NHANES) together with artificial problems safeguards against inadvertent leakage of training knowledge into the language model side‑information; consequently any observed gains can be confidently attributed to the reasoning capabilities of FeatLLM rather than memorized facts.

---

### Baseline Methods

To situate FeatLLM’s performance within the broader landscape of few‑shot tabular learning, nine representative baselines were selected: three classical supervised learners that ignore prior knowledge, two semi‑supervised approaches that exploit large unlabeled corpora, one pre‑training based Bayesian network method, and three recent LLM‑centric techniques.

1. **Logistic Regression (LogReg)** proceeds by fitting a linear decision function directly on the raw feature matrix \(\mathbf{X}\).  The model optimizes cross‑entropy loss with \(\ell_{2}\) regularization; hyper‑parameters are selected via grid search combined with cross‑validation on the few available shots.

2. **XGBoost** implements gradient‑boosted decision trees that iteratively improve upon residuals from previous trees.  It is highly effective for tabular problems due to its ability to capture non‑linear interactions without extensive feature engineering.

3. **Random Forest** aggregates an ensemble of decision trees trained on bootstrap samples of \(\mathcal{D}\).  Like XGBoost it leverages tree structures but without boosting; depth and number of estimators are tuned using cross‑validation.

All three classic baselines rely purely on the labeled subset; they provide a lower bound for performance when no external knowledge is available.

4. **SCARF** adopts semi‑supervised contrastive learning on an extensive pool of unlabeled tables; it learns representations that are subsequently fine‑tuned on the few labeled examples.

5. **STUNT** extends semi‑supervised learning by constructing pseudo‑labels for unlabeled instances through self‐training; its design specifically targets tabular data with mixed feature types.

Both SCARF and STUNT assume access to large unlabeled repositories that may be unrealistic in many industrial contexts; nevertheless they serve as strong comparators for methods that exploit auxiliary information beyond few labeled points.

6. **TabPFN** pre‑trains a Bayesian neural network on synthetically generated tables sampled from diverse distributions; at inference time it receives both training and test rows simultaneously and produces posterior predictive probabilities without further gradient updates.

7-9 encompass approaches that explicitly enlist large language models:

* **In‑context Learning** places few-shot examples and task description directly into an LLM prompt (here GPT‑3.5), expecting the model to output predictions for each test sample end‑to‑end.
* **TABLET** augments plain in‑context prompting with an external classifier that supplies rule prototypes; this hybrid design aims to improve reliability while still relying on LLM inference per sample.
* **TabLLM** fine‑tunes an LLM using parameter‑efficient adapters such as IA3 or LoRA on the few labeled rows before employing it for prediction; it thus incurs additional training cost but seeks higher accuracy by adapting model weights.

These three baselines share a common limitation: every test instance requires at least one forward pass through the LLM, which translates into substantial computational overhead and often runs into prompt length restrictions when many features are present.

---

### Implementation Specifics

All experiments were conducted using Python 3.10 on machines equipped with Nvidia A100 GPUs unless otherwise noted.  

*The language model backbone.*  
FeatLLM employs OpenAI’s GPT‑3.5 Turbo (model identifier `gpt-3.5-turbo-0613`) as its reasoning engine for rule extraction and code generation.  Although FeatLLM’s architecture is agnostic to the particular LLM—appendix results demonstrate similar behavior with Llama 2—GPT‑3.5 was chosen because it offers stable API access without requiring local weights or fine‑tuning infrastructure.

*Prompt parameters.*  
When calling the LLM for rule generation we set temperature \(=0.5\), allowing moderate stochasticity needed for ensemble diversity while keeping responses coherent enough for reliable parsing.  Top‑p was left at its default value \(1\).  

*Ensemble configuration.*  
Each run spans \(T=20\) independent trials; within each trial FeatLLM extracts exactly \(R=10\) binary rules per class (a value chosen after ablation studies indicated diminishing returns beyond ten).  Random seed variation influences both demonstration ordering and feature bagging—subsets of columns or rows are selected per trial so that prompt length stays within model limits even for high–dimensional data such as Communities or Myocardial.

*Linear downstream model.*  
The binary rule matrix \(\mathbf{Z}_{k}^{i}\in \{0,1\}^{R}\), defined for class \(k\), feeds into a biasless linear classifier whose parameters \(\mathbf{w}_{k}\in \mathbb{R}^{R}_{+}\)are constrained to be nonnegative by applying \(\max(\mathbf{w}_{k},0)\).  Optimization uses Adam with learning rate \(0 .01\); training proceeds for up to \(200\) epochs while monitoring cross‑entropy loss via $k$-fold cross validation on the few-shot training split to select an early stopping point.

*Baseline reproduction.*  
For fair comparison we reproduced each baseline under identical few-shot splits:

- In‐context Learning used GPT‑3.5 with identical temperature settings but no chain‐of‐thought instructions.
- TABLET added rule prototypes generated by an auxiliary decision tree trained on available shots.
- TabLLM was implemented using T0 as specified in its original paper because GPT‐based checkpoints were not publicly available for adapter tuning.
- Classical models received raw numeric encodings: categorical variables were one‐hot encoded after consulting their textual definitions supplied in $F$, matching common practice across tabular pipelines.
- SCARF and STUNT accessed external unlabeled repositories provided by their authors; their hyperparameters followed recommended defaults (e.g., number of pretraining epochs \(50\), contrastive temperature \(0 .07\)).

All baselines were evaluated using area under the receiver operating characteristic curve (AUROC), averaged over three random repetitions of train/test splits per dataset; standard deviations capture variability induced by different few-shot selections.

---

### Summary

The experimental design deliberately spans a wide spectrum—from modestly sized health records to high‐dimensional crime statistics—and juxtaposes FeatLLM against both traditional machine learners and state-of-the-art LLM‐based systems under strict few-shot constraints.  By standardizing implementation details—such as optimizer settings for downstream linear models, prompt temperature for LLM calls, and ensemble size—we ensure that performance differences can be attributed primarily to methodological innovations rather than engineering disparities.  The subsequent results chapter will reveal how FeatLLM consistently leverages its rule extraction capability to achieve superior AUROC scores while incurring only marginal inference cost compared with full LLM end-to-end baselines.

**Results: Accuracy, Efficiency, and Ablations**

# AUC Tables and Discussion of Top Performance Across Datasets  

The primary empirical evidence supporting the effectiveness of **FeatLLM** is presented through a comprehensive set of area‑under‑the‑receiver‑operating‑characteristic (AUC) scores on thirteen diverse tabular benchmarks.  Each dataset spans a different domain—ranging from classic census income prediction (Adult) and banking marketing (Bank) to medical prognostics (Heart, Myocardial) and synthetic sequence classification—thereby testing the method under a wide variety of feature types, numbers of attributes, and class distributions.  

For every dataset the experiments were run in a low‑shot regime with **k = 4** or **k = 8** randomly selected labeled instances per class.  Three independent random splits were generated, and the mean AUC together with the standard deviation was reported.  Across all settings **FeatLLM** either achieved the highest mean AUC or ranked second, outperforming every baseline by a noticeable margin.  

In particular, on the *Adult* and *Bank* datasets—both of which have over a dozen attributes and a mix of categorical and numerical columns—**FeatLLM** attained average AUCs of **0.88** and **0.91**, respectively, exceeding the best non‑LLM baseline (XGBoost) by roughly **4–5 %**.  On the high‑dimensional *Communities* and *Myocardial* tasks, where prior LLM‑based methods such as In‑Context Learning or TabLLM failed to produce any result due to prompt‑length overflow, **FeatLLM** remained functional thanks to its feature‑bagging strategy and recorded AUCs of **0.73** and **0.78**, surpassing traditional Random Forest by more than **6 %**.  

When the number of labeled shots was increased from 4 to 8, the performance gap widened modestly: the linear weight tuning stage in FeatLLM could better estimate rule importance, yielding an additional **1–2 %** absolute gain in AUC on most datasets.  Nonetheless even with just four examples FeatLLM matched or beat conventional tabular learners that required thirty‑two shots, demonstrating that its rule‑generation step harnesses the LLM’s prior knowledge effectively.

# Comparison of Inference and Training Time  

A crucial advantage of FeatLLM is its low computational overhead at inference time.  Unlike end‑to‑end LLM approaches which must invoke the language model for every test sample, FeatLLM performs the expensive LLM calls only during a brief “feature engineering” phase: each ensemble trial sends a single prompt (including few‑shot demonstrations) to the LLM API, receives ten textual rules per class, and then parses them into executable Python code.  In our experiments on the *Adult* dataset with a training set of sixteen shots, this phase required **30 API queries**, which could be parallelized across multiple workers.

After rule extraction, prediction for each test instance reduces to evaluating a set of binary indicators (whether each rule holds) followed by a dot product with non‑negative learned weights and a softmax operation—operations that are trivial on a standard CPU or GPU.  Table 1 (in the original paper) shows that FeatLLM’s total inference latency per test batch was comparable to that of Logistic Regression or Random Forest (on the order of milliseconds), whereas In‑Context Learning, TABLET, and TabLLM incurred several seconds to minutes per batch because each sample required its own LLM forward pass.

Training time also favors FeatLLM relative to fine‑tuned LLM baselines such as TabLLM.  The linear weight layer is optimized with Adam at a learning rate of 0.01 for 200 epochs; early stopping via k‑fold cross validation typically halts after fewer than fifty epochs.  Consequently the total wall‑clock time for training (including the one‑time API calls) is similar to that of conventional models and dramatically lower than TabLLM’s multi‑GPU model‑parallel training routine.

# Ablation Studies  

To isolate the contribution of each design component we performed four ablations, each removing one key element while keeping all other settings identical:

1. **-Tuning** – The linear weights were fixed to one (i.e., each rule contributed equally).  The logit for class *k* became simply \(\sum_{r=1}^{R} z_{k,r}^{i}\), where \(z_{k,r}^{i}\in\{0,1\}\) denotes satisfaction of rule *r*.  
2. **-Ensemble** – Only a single rule‑generation trial was executed; no bagging or averaging across multiple temperature samples was performed.  
3. **-Description** – Feature descriptions (natural language definitions and type hints) were omitted from the prompt; only raw feature names appeared.  
4. **-Reasoning** – The two‑step reasoning instruction was collapsed to a single step that directly asked for rules without first encouraging the model to infer causal tendencies between features and target.

The resulting AUC differences averaged over all datasets are summarised in Table 2 (original paper).  All four ablations produced statistically significant degradations relative to the full FeatLLM pipeline:

| Ablation | Mean ΔAUC (across datasets) |
|----------|-----------------------------|
| -Tuning          | –0.018 |
| -Ensemble        | –0.025 |
| -Description     | –0.021 |
| -Reasoning       | –0.027 |

The most pronounced drop stems from removing the reasoning step; this confirms that prompting the LLM to first articulate general feature–target relationships helps it avoid spurious correlations when later formulating concrete rules.

# Effect of Number of Shots on Each Ablation  

We further examined how sensitivity to labeled data changes when shots are varied from 2 up to 16.  For each ablation we plotted AUC versus number of shots (see Figure 5 in the paper).  Two consistent patterns emerged:

- **Weight tuning (-Tuning)** gains importance as more shots become available.  With only two or four examples, learning reliable weights is difficult; consequently performance loss relative to full FeatLLM is modest (~1 %).  When eight or sixteen shots are provided, tuned weights can differentiate high‑utility rules from noise, leading to an additional **2–3 %** improvement over the untuned variant.
- **Feature descriptions (-Description)** and **reasoning instructions (-Reasoning)** are most valuable in the extreme low‑shot regime (2–4 shots).  With scant data, the LLM relies heavily on its stored world knowledge; explicit textual cues about feature semantics and a structured reasoning scaffold enable it to produce more accurate rule sets.  As shot count rises, empirical evidence from examples begins to dominate, reducing dependence on these prompts; nonetheless even at sixteen shots their removal still hurts performance by about **1 %**, indicating they provide complementary information rather than being purely compensatory.

Ensembling exhibits a relatively uniform benefit across all shot levels: averaging over twenty independently generated rule sets consistently yields a ~2 % boost because random variations in temperature or demo ordering are smoothed out regardless of how many labeled examples are present.

Overall, these analyses demonstrate that each component addresses a distinct limitation—weight tuning combats over‑parameterization when data are plentiful; description and reasoning unlock latent prior knowledge when data are scarce; ensemble bagging mitigates both prompt length constraints and sampling variance—together delivering robust high‑accuracy few‑shot tabular learning with minimal inference cost.
