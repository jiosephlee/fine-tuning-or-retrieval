\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 2: Fundamentals of Large Language Models and In‑Context Learning  

Large language models (LLMs) have become the central engine behind many recent advances in natural‑language processing and, increasingly, in domains that are not purely textual.  The paper *Large Language Models Can Automatically Engineer Features for Few‑Shot Tabular Learning* demonstrates how the reasoning abilities of an LLM can be harnessed to generate high‑quality feature‑engineering rules for tabular data without ever updating the model’s parameters.  Understanding this capability requires a solid grasp of how LLMs are built, how they are prompted, and how “in‑context learning’’—the practice of teaching a model a new task by providing examples inside a single prompt—differs from conventional fine‑tuning.  The following sections lay out these foundations, discuss practical constraints such as prompt length and inference cost, and illustrate how an LLM can reason about structured data such as tables.

---

## Architecture and Pre‑training of LLMs  

At the core of every LLM lies a **transformer** architecture.  A transformer is a deep neural network whose primary building block is the self‑attention mechanism.  Each token in an input sequence is first embedded into a high‑dimensional vector; then, for every layer, the model computes attention scores that measure how much each token should attend to every other token.  By weighting and linearly combining the representations of all tokens, the model produces contextualized embeddings that capture syntactic and semantic relationships across the whole sequence.  Stacking many such layers (often dozens or even hundreds) yields a model capable of representing complex patterns in language.

Training proceeds in two stages:

1. **Self‑supervised pre‑training** – The model is exposed to massive corpora of text (books, web pages, code repositories, etc.) and learns to predict missing tokens.  Common objectives include **masked language modeling** (predicting randomly masked words) and **next‑token prediction** (generating the next word given all previous words).  Because the data are so diverse, the model acquires broad world knowledge: facts about diseases, finance, programming APIs, and countless other domains.

2. **Optional fine‑tuning or instruction tuning** – After pre‑training, a smaller amount of task‑specific data may be used to adapt the model to follow instructions more reliably (e.g., “answer with a short paragraph”).  Importantly for the present work, these additional steps are *not* required when we rely solely on in‑context learning: the pre‑trained model already contains enough knowledge to answer new tasks when given an appropriate prompt.

The end result is a parameterized function  
\[
\text{LLM}_{\theta}(\text{prompt})\; \mapsto\; \text{generated text},
\]  
where \(\theta\) denotes the (fixed) weights learned during pre‑training.  In all subsequent sections we treat \(\theta\) as immutable; every new prediction is produced only by changing the prompt.

---

## Prompting, Few‑Shot Examples, and Chain‑of‑Thought Prompting  

A **prompt** is simply a piece of text presented to the model before it generates any output.  Because LLMs are trained to continue natural language sequences, a carefully crafted prompt can steer them toward performing a desired computation.  The most powerful prompting strategies exploited in the paper are described below.

### Basic Prompt Structure  

A prompt typically contains three parts:

1. **Task description** – A concise statement that frames what we want the model to do (e.g., “Does this patient’s record indicate chronic heart failure? Yes or no.”).  Framing in natural language allows the LLM to activate its stored knowledge about medical risk factors.

2. **Feature definitions** – For each column of a table we provide its name, type (numeric, categorical, boolean), and optionally a short definition (“`age` is the patient’s age in years”).  Supplying this metadata helps the model avoid type mismatches when it later generates logical conditions such as “`age > 65`”.

3. **Few‑shot demonstrations** – A small number \(k\) of labeled examples are serialized into text using a fixed template:  
   \[
   \text{``}f_{1}\text{ is }x_{1}^{i}.\; \dots\; f_{d}\text{ is }x_{d}^{i}.\; \text{Answer: }y^{i}\text{''}.
   \]  
   These demonstrations act as concrete illustrations of how raw feature values map to labels.  Because only a handful of examples are needed (the paper experiments with as few as four), this approach is called *few‑shot* prompting.

### Chain‑of‑Thought Prompting  

The paper demonstrates that raw few‑shot examples often leave the LLM uncertain about which features truly matter.  To encourage deeper reasoning, we prepend an explicit instruction that mimics “chain‑of‑thought’’ prompting: ask the model to first reason about **causal relationships** between features and the target before attempting to write any rules.  Concretely, the instruction splits reasoning into two steps:

1. **Step 1 – Prior knowledge extraction** – The model lists plausible feature–target relations based solely on its world knowledge (“Older patients tend to have higher heart failure risk”).  
2. **Step 2 – Rule synthesis using demonstrations** – The model combines Step 1 insights with the concrete few‑shot examples to produce *rules* for each class (e.g., “If `age > 70` AND `blood_pressure > 140` then answer *Yes*”).

By structuring reasoning this way we reduce reliance on spurious correlations that may appear in tiny training sets and instead let the LLM leverage its extensive pre‑trained knowledge.

### Fixed Number of Rules  

To keep downstream processing tractable, each prompt asks for a predetermined number of rules per class (the paper adopts ten).  This prevents degenerate outputs—either too few rules that underfit or an explosion of rules that would overwhelm both parsing and downstream models.

---

## In‑Context Learning vs. Fine‑Tuning  

Both approaches aim to adapt an LLM to a new task but differ dramatically in resources required and operational constraints.

| Aspect | In‑Context Learning | Fine‑Tuning |
|--------|---------------------|--------------|
| Parameter updates | None; \(\theta\) stays fixed | Model weights \(\theta\) are updated via gradient descent |
| Data requirement | Only a handful of examples placed inside the prompt | Typically thousands of labeled examples |
| Compute cost at inference | Single forward pass per prompt (or per ensemble trial) | One forward pass after fine-tuning; training may be expensive |
| Deployment flexibility | Works with any commercial API that exposes generation (no access to internal weights) | Requires ability to write back updated weights—a limitation for closed APIs like GPT‑4 |
| Prompt length limitation | Must fit all demonstrations + instructions within context window; can become problematic with many features | Not constrained by prompt length after fine-tuning |

The **FeatLLM** framework explicitly chooses *in‑context learning* because it sidesteps two practical barriers:

1. **API‐only access:** Many state–of–the–art chat models are only available through inference APIs; they cannot be fine‑tuned by end users.
2. **Prompt size management:** By delegating rule generation to a few high-level prompts and then using bagging (randomly selecting subsets of columns), FeatLLM stays within context windows even for tables with many hundreds of attributes.

Thus FeatLLM illustrates how powerful reasoning can be extracted from an immutable LLM purely through clever prompting.

---

## APIs and Practical Constraints (Prompt Length, Inference Cost)  

When deploying an LLM via a cloud provider (e.g., OpenAI’s `gpt-3.5-turbo-0613` used in the paper), practitioners must respect two hard limits:

1. **Maximum context size** – Most chat models accept at most several thousand tokens per request (the exact number varies).  Every token used for feature names, descriptions, demonstrations, and chain-of-thought instructions consumes part of this budget.  If a table has hundreds of columns, naïvely serializing all columns would overflow the limit.

   *Mitigation strategy:* FeatLLM applies **feature bagging**, randomly selecting a manageable subset of columns for each ensemble trial.  Because each trial only needs enough columns to generate useful rules, multiple trials collectively cover all features without any single prompt exceeding the token budget.

2. **Inference latency and cost** – Each call to an LLM API incurs monetary cost proportional to generated tokens and incurs network latency.  Performing one inference per test sample would be prohibitive for large datasets.

   *Mitigation strategy:* FeatLLM extracts **static rules once**, parses them into executable Python code via another short LLM call (the parsing stage), and thereafter relies on a lightweight linear model with non‑negative weights for actual predictions.  Consequently only ~30 API calls are required regardless of how many test instances exist—a dramatic reduction compared with end-to-end approaches that query per sample.

The temperature parameter (set at 0.5 in experiments) controls randomness during rule generation; higher temperatures encourage diversity across ensemble members while still yielding coherent outputs.

---

## Examples of LLM Reasoning Over Structured Data  

To solidify intuition about how an LLM can treat tabular information as “structured prose,” consider two illustrative scenarios drawn from the paper’s experiments.

### Medical Diagnosis Example  

*Task:* Predict whether a patient has chronic heart failure.  
*Features:* `age` (numeric), `blood_pressure` (numeric), `cholesterol` (numeric), `smoker` (boolean), …  

**Prompt excerpt**

```
Task: Does this patient's record indicate chronic heart failure? Yes or no.
Feature descriptions:
- age: patient's age in years.
- blood_pressure: systolic blood pressure measurement.
- cholesterol: total cholesterol level.
- smoker: whether patient currently smokes (True/False).
...
Demonstrations:
age is 68. blood_pressure is 150. cholesterol is 210. smoker is True.
Answer: Yes
age is 45. blood_pressure is 120. cholesterol is 180. smoker is False.
Answer: No
...
Now reason step-by-step:
Step 1: Based on medical knowledge ... 
Step 2: Using these examples generate ten rules for class Yes.
```

The LLM replies with rules such as

```
Rule 1: age > 65 AND blood_pressure > 140
Rule 2: cholesterol > 200 AND smoker = True
...
```

These textual conditions directly encode domain expertise (“older patients with high blood pressure are at risk”).

### Synthetic Sequence Classification Example  

*Task:* Classify an integer sequence as arithmetic or geometric etc.  
*Features:* `first_term`, `second_term`, `third_term`, `fourth_term`.  

Because each feature has an explicit numeric meaning, Step 1 may invoke mathematical definitions (“In an arithmetic progression consecutive differences are equal”), while Step 2 extracts concrete thresholds from the few illustrated sequences (“If second_term - first_term = third_term - second_term then class = arithmetic”).

After rule generation, FeatLLM automatically converts each rule into Python functions (`def rule_i(seq): return seq[1]-seq[0] == seq[2]-seq[1]`) using another brief LLM query that parses natural language into code even when minor syntactic variations appear (“greater than” vs “>”).  

These examples demonstrate that with appropriate prompting—task framing, descriptive metadata, few-shot illustrations, and explicit chain-of-thought instructions—an LLM can effectively reason over structured tabular inputs despite being originally trained on free text.

### Summary  

This chapter has introduced the essential building blocks required to understand why large language models can serve as powerful feature engineers for tabular data:

* Their transformer backbone coupled with massive self-supervised pre-training endows them with broad factual knowledge.
* Prompt engineering—including task description, feature metadata, few-shot demonstrations, and chain-of-thought reasoning—allows us to coax that knowledge into concrete logical rules.
* In‑context learning leverages these prompts without ever modifying model parameters, making it compatible with closed‐source APIs and dramatically reducing computational cost.
* Practical constraints such as limited context windows and inference pricing motivate techniques like feature bagging and rule parsing into downstream linear models.
* Concrete examples illustrate how an immutable LLM can transform raw table rows into human‐readable conditions that subsequently become binary features usable by simple classifiers.

Armed with these concepts you will be ready to explore how **FeatLLM** builds upon them to achieve state-of-the-art few‑shot performance on diverse real-world tabular tasks while keeping inference inexpensive and interpretable.

**Problem Formulation for Few‑Shot Tabular Classification**

In this chapter we formalize the learning problem that underlies the entire FeatLLM framework.  By establishing precise notation for the data, the associated natural‑language descriptions, and the strict low‑shot constraints, we obtain a clear target for subsequent algorithmic development.  Throughout we keep the exposition deliberately general so that it applies to any tabular classification task, regardless of the domain (finance, medicine, synthetic benchmarks, etc.).  The key idea is that only a tiny number of labeled instances are available for training, yet the model may still leverage rich auxiliary information such as feature names and textual definitions.

---

### Notation: dataset 𝒟, feature set F, and class set C  

Consider a tabular data collection consisting of $N$ rows (samples) and $d$ columns (features).  Each row $i\in\{1,\dots ,N\}$ is represented by a vector  

\[
\mathbf{x}^{\,i}= \bigl(x^{\,i}_{1},x^{\,i}_{2},\dots ,x^{\,i}_{d}\bigr)^{\!\top}\in\mathbb{R}^{d},
\]

where $x^{\,i}_{j}$ denotes the observed value of feature $j$ for sample $i$.  In practice many features are categorical or ordinal; nevertheless we treat all entries abstractly as elements of suitable domains (numeric, string, or enumeration).  

The complete labeled dataset is written as  

\[
\mathcal{D}= \bigl\{(\mathbf{x}^{\,i},\; y^{\,i})\bigr\}_{i=1}^{N},
\]

where $y^{\,i}\in C$ is the class label attached to sample $i$, and $C=\{c_{1},c_{2},\dots ,c_{|C|}\}$ denotes the finite set of possible classes (binary classification corresponds to $|C|=2$).  

Each column comes with a human‑readable identifier—its **feature name**—and optionally a textual definition or description that clarifies its semantics.  Let  

\[
F=\bigl\{f_{1},f_{2},\dots ,f_{d}\bigr\}
\]

be the ordered list of these feature names.  For every $j$, we also have an optional natural‑language description  

\[
\mathrm{desc}(f_{j}) = \text{“{$f_{j}$} measures … ”},
\]

which may encode type information (e.g., “integer age in years”) or domain knowledge (e.g., “smoking status: {yes,no}”).  The presence of these descriptions is crucial for large language models (LLMs) to reason about the data without seeing many examples.

---

### k‑shot sampling and assumptions about feature descriptions  

Few‑shot learning assumes that only a small subset of $\mathcal{D}$ is available for supervised training.  Formally, let $k \ll N$ denote the **shot budget**.  We randomly draw without replacement a set  

\[
\mathcal{D}_{\text{train}} = \bigl\{(\mathbf{x}^{\,i},y^{\,i}) \mid i \in S_{\text{train}}\bigr\},
\qquad |S_{\text{train}}| = k,
\]

and treat all remaining rows as either validation or test data, depending on experimental protocol.  The randomness is stratified whenever possible so that each class in $C$ appears at least once in $\mathcal{D}_{\text{train}}$; this guarantees that the learner has a minimal basis for discriminating among classes.

Two additional assumptions are made about the auxiliary information:

1. **Availability of feature names** – every column $j$ has an unambiguous textual identifier $f_{j}$ that can be inserted verbatim into prompts presented to an LLM.
2. **Optional but useful descriptions** – while not strictly required for correctness, providing $\mathrm{desc}(f_{j})$ significantly improves the LLM’s ability to generate meaningful rules because it supplies type constraints and domain context.

These assumptions reflect the reality of most curated tabular datasets: column headings are present by definition, and documentation often accompanies them.

---

### Goal: learn a predictor using only *k* labeled instances  

Given only $\mathcal{D}_{\text{train}}$, the objective is to construct a **predictor**  

\[
h : \mathbb{R}^{d} \longrightarrow \Delta^{|C|-1},
\]

where $\Delta^{|C|-1}$ denotes the probability simplex over $|C|$ classes (i.e., $h(\mathbf{x})$ yields a valid probability distribution across $C$).  In FeatLLM this predictor consists of two stages:

1. **Feature engineering via an LLM** – from the few examples and from $F$ (plus any $\mathrm{desc}(\cdot)$), an LLM generates a set of logical conditions (“rules”) that characterize each class.  Each rule $r$ can be evaluated on any sample to produce a binary outcome $\mathbb{I}\{\mathbf{x}\models r\}\in\{0,1\}$.  
2. **Linear aggregation** – a low‑complexity model (a non‑negative linear classifier without bias) learns weights for these binary rule‑features using only $\mathcal{D}_{\text{train}}$.  The learned weights capture how informative each rule is for predicting each class.

Thus, despite having access to just $k$ labeled points, the system leverages **prior knowledge** embedded in the LLM and the explicit feature semantics to produce a usable classifier.

---

### Evaluation metrics in low‑shot regimes  

Because performance can fluctuate dramatically when only a handful of labels are available, robust evaluation requires metrics that are insensitive to class imbalance and that capture ranking quality rather than raw accuracy alone.

- **Area Under the ROC Curve (AUC)** – For binary tasks ($|C|=2$) we compute the ROC curve by varying a decision threshold on $h(\mathbf{x})_{c_{+}}$, where $c_{+}$ denotes the positive class.  The AUC measures the probability that a randomly chosen positive example receives a higher score than a randomly chosen negative example.  In few‑shot settings AUC is preferred because it does not depend on selecting a particular threshold.

- **Macro‑averaged AUC** – When $|C|>2$, we compute an AUC for each one‑vs‑rest binary problem and then average across classes.  This yields a metric that treats all classes equally regardless of their frequency.

- **Accuracy** – Defined as $\frac{1}{|\mathcal{D}_{\text{test}}|}\sum_{(\mathbf{x},y)\in \mathcal{D}_{\text{test}}}\mathbb{I}\bigl[\arg\max_{c} h(\mathbf{x})_{c}=y\bigr]$.  Accuracy is reported mainly for completeness; however, because few shots often lead to noisy decision boundaries, accuracy can be unstable.

- **Standard deviation over repetitions** – Since random selection of $\mathcal{D}_{\text{train}}$ influences results heavily, experiments are repeated multiple times (e.g., three seeds) and both mean and standard deviation of each metric are reported.  This practice guards against over‑interpreting any single lucky split.

All reported numbers in subsequent chapters adhere to these evaluation conventions, ensuring fair comparison among FeatLLM, baseline tabular learners, and other LLM‑based approaches.

--- 

By grounding our discussion in this precise problem formulation—clearly defined notation, strict few‑shot sampling, reliance on feature descriptions, and standard evaluation—we set the stage for understanding how FeatLLM transforms raw tabular data into high‑quality binary rule features and why this approach can outperform existing methods even with only a handful of labeled examples.

**Designing Prompts to Extract Decision Rules**

In this chapter we dissect the prompt engineering strategy that enables a large language model (LLM) to act as a feature engineer for few‑shot tabular learning.  The central idea of the *FeatLLM* framework is to ask the LLM to articulate, in natural language, the logical conditions that govern each class label.  Once these conditions—here called **rules**—are obtained, they are parsed into binary features that a simple downstream model can consume.  The quality of the extracted rules hinges on how the prompt is crafted.  Empirical work shows that a three‑part prompt structure—*basic information block*, *reasoning instruction block*, and *response instruction block*—produces reliable, parsable rule sets while encouraging the model to draw upon its prior knowledge rather than spurious patterns present in a tiny training set.

Below we explain each component in detail, why it matters, and how additional engineering choices such as temperature tuning and demo ordering further improve robustness.

---

### Basic Information Block: Task Description, Feature Names/Types, and Few‑Shot Examples

The first segment of the prompt supplies the LLM with all the factual context it needs before any reasoning begins.  It consists of three pieces of information.

1. **Task Description**  
   The model is told exactly what prediction is required, cast as a direct question.  For a medical dataset this might read:

   > “*Does this patient’s data indicate chronic heart failure?*”

   Framing the problem as a yes/no (or multi‑class) query aligns the LLM’s output format with the downstream classification objective and activates its knowledge about the domain (e.g., risk factors for heart failure).

2. **Feature Names, Types, and Optional Definitions**  
   Each column in the table is introduced by its natural‑language name $f_j$ together with its datatype:

   - *Numerical*: “*Age (years) – numerical*”
   - *Categorical*: “*Smoking status – categorical; values: {Never, Former, Current}*”

   When a definition is available (e.g., “*Blood pressure: systolic measurement in mm Hg*”), it is inserted after the type.  Explicitly stating types serves two purposes.  
   First, it prevents the LLM from generating syntactically invalid comparisons such as “*Age < ‘Never’*”.  Second, it guides later parsing because the rule extractor can expect numeric comparisons for numeric features and equality checks for categorical ones.

3. **Few‑Shot Demonstrations**  
   A small set of labeled examples—typically $k$ samples when performing $k$‑shot learning—is serialized into plain text using a consistent template:

   \[
   \text{Serialize}(\mathbf{x}^i,\mathbf{y}^i,F)=
   \text{``}f_1\ \text{is}\ x^i_1.\dots f_d\ \text{is}\ x^i_d.\ \text{Answer:}\ y^i\text{''}
   \]

   Each demonstration therefore reads like a short paragraph that enumerates every feature value followed by its correct label.  By placing these demonstrations after the task description but before any reasoning instructions, we give the LLM concrete evidence of how feature values map to outcomes without yet telling it how to derive rules.

The combination of an explicit problem statement, clear feature ontology, and concrete examples positions the LLM to treat the subsequent reasoning steps as an *explanation* rather than blind memorization.

---

### Reasoning Instruction Block: Two‑Step Chain‑of‑Thought (Knowledge → Rule Derivation)

Once the factual scaffolding is established, we guide the model through a disciplined reasoning process that mirrors how a human expert would approach tabular classification.

#### Step 1 – Infer Causal Tendencies from Prior Knowledge  
The model is prompted to reason *without* looking at the few‑shot examples.  An introductory sentence akin to chain‑of‑thought prompting (“*Let us think step by step.*”) signals that an internal monologue is expected.  The instruction then asks:

> “Based on your world knowledge and common sense, list which features are likely relevant to determining whether the answer is *Yes* versus *No*, and describe qualitatively how they influence the outcome.”

Because no concrete data points are referenced, the LLM must draw on its pre‑training corpus (medical textbooks, epidemiology reports, etc.).  This step serves two critical functions:

- **Prior Knowledge Extraction** – The model surfaces domain‐relevant variables (e.g., age, hypertension) before being swayed by potentially noisy correlations in the few‑shot sample.
- **Feature Filtering** – By explicitly requesting a relevance list, we discourage attention to irrelevant columns (e.g., an identifier field) that could otherwise be introduced into rule generation.

#### Step 2 – Derive Explicit Rules Using Demonstrations  
Armed with a tentative relevance set from Step 1, the model now incorporates the few‑shot examples.  The prompt asks:

> “Using the examples above and your earlier relevance list, propose $R$ concise decision rules for each class (*Yes* and *No*) that would correctly classify all demonstrated instances.”

We fix $R$ (the number of rules per class) to a modest value such as $10$.  This bound prevents an explosion of overly specific rules that would overfit the tiny demonstration set while still allowing enough expressive power to capture distinct decision regions.

The two‑step chain forces separation between *knowledge‑driven inference* and *data‑driven refinement*.  Empirically this reduces spurious rule generation caused by overreliance on idiosyncratic patterns in few examples.

---

### Response Instruction Block: Formatting Rules for Reliable Parsing

After reasoning, we must extract machine‐readable predicates from natural language text.  To make this extraction deterministic we prescribe a strict output schema.

1. **Class Header** – Each class begins with a line like `Class Yes:` or `Class No:`.
2. **Rule List** – Under each header we provide exactly $R$ numbered items:
   
   ```
   1) Age > 60 AND Smoking status = Current
   2) BloodPressure >= 140
   ...
   ```

3. **Operator Vocabulary** – We enumerate permissible relational operators (`=`, `!=`, `>`, `<`, `>=`, `<=`) and logical connectors (`AND`, `OR`).  The LLM is reminded not to use synonyms (“greater than”) because those increase parsing complexity.
4. **Feature Formatting** – Feature names must match those given earlier (case‑sensitive).  For categorical variables we require explicit equality checks against listed categories; for numerical variables we require a single comparison operator followed by a numeric constant.

A short example of a valid response might be:

```
Class Yes:
1) Age > 55 AND Cholesterol > 240
2) Diabetes = Yes
...
Class No:
1) Age <= 55 AND BloodPressure < 130
...
```

Because every rule follows an identical syntactic pattern, downstream code can reliably split on line breaks and parse each predicate into Python boolean expressions or symbolic representations.

---

### Fixed Number of Rules per Class and Handling of Feature Types

Choosing a constant $R$ simplifies both prompt length budgeting and downstream dimensionality.  In practice $R=10$ yields a good tradeoff: long enough to capture multiple facets of a class decision boundary yet short enough that concatenating all rules across classes fits comfortably within typical LLM context windows (often ≤ 4 K tokens).  

When forming rules we respect feature types explicitly:

- **Numerical Features** – The rule generator must produce an inequality involving a single threshold; multivariate linear combinations are discouraged because they would require more elaborate parsing.
- **Categorical Features** – Equality or inequality checks against predefined categories are mandated.
- **Boolean or Binary Features** – Simple presence (`Feature = True`) suffices.

If during generation an illegal type mismatch occurs (e.g., comparing a string category with “>”), downstream validation flags it and discards or corrects the rule—although such mismatches are rare when type information is clearly presented in the basic block.

---

### Prompt Engineering Tricks: Temperature, Order Randomization, and Bagging

Even with an ideal template, stochasticity in LLM decoding can be harnessed to improve robustness.

- **Temperature Settings** – A moderate temperature (e.g., $T=0.5$) encourages diverse but still coherent rule sets across repeated queries. Higher temperatures increase variability at the cost of occasional incoherence; lower temperatures produce near‑deterministic outputs but reduce ensemble diversity.
  
- **Demo Order Randomization** – The ordering of few‑shot examples subtly influences LLM attention patterns. By shuffling this order before each prompt we encourage different subsets of examples to dominate rule synthesis, which again contributes diversity among ensemble members.

- **Bagging Over Features/Instances** – For datasets with many columns exceeding token limits, each prompt can randomly select a subset of features (feature bagging) or a subset of demonstrations (instance bagging). Different bags generate distinct rule collections; averaging predictions over many bags mitigates any single bag’s myopic view.

These tricks collectively give rise to an ensemble of lightweight linear models (each trained on binary rule features).  Because each member was built from an independently generated rule set, their errors tend to cancel out—a phenomenon akin to classical ensemble learning theory where variance reduction improves generalization even under severe data scarcity.

---

### Summary

Designing prompts for rule extraction in *FeatLLM* involves meticulously supplying factual context, coaxing structured reasoning via a two‑step chain‑of‑thought process, and demanding machine‑parsable output through rigid formatting guidelines.  By fixing the number of rules per class and respecting feature type annotations we keep prompts concise enough for real LLMs while ensuring generated predicates are meaningful.  Finally, purposeful use of temperature control, demonstration order randomization, and bagging introduces beneficial diversity that fuels robust ensembling without inflating inference cost.

Through this three‑part prompt architecture, large language models are transformed from opaque end‑to‑end predictors into powerful knowledge‑driven feature engineers whose output seamlessly integrates with simple downstream classifiers—exactly what makes *FeatLLM* effective for few‑shot tabular learning.

**Parsing Natural‑Language Rules into Binary Features**

In this chapter we explain in detail how the natural‑language rules that a large language model (LLM) produces are transformed into a set of binary indicator features that can be fed to a simple downstream classifier.  The process is central to the **FeatLLM** framework: once the rules have been extracted they become the only “learned” representation of the data, and every downstream prediction reduces to evaluating whether a given sample satisfies each rule.  We therefore devote several paragraphs to each component of this pipeline, emphasizing the intuition behind design choices, the practical difficulties that arise from noisy LLM output, and the concrete steps—prompt design, code generation, safe execution, and matrix construction—that yield a clean binary feature matrix \(\mathbf{Z}_k\) for each class \(k\).

---

### 1. Challenges of Noisy LLM Output

When an LLM is asked to produce logical conditions in natural language, the resulting text is rarely perfectly formatted.  Even when the prompt explicitly requests a canonical syntax (e.g., “`age > 45`”), the model may substitute symbols for words (“greater than”, “less than”) or restructure the expression (“if age is above 45”).  Moreover, the model can insert or omit punctuation, change variable names, or combine several elementary clauses with logical connectives such as **AND** or **OR** in unpredictable ways.  

These variations matter because the subsequent parsing stage must turn each textual rule into an executable Boolean test.  A naïve regular‑expression parser that expects only “`feature OP value`” quickly fails when it encounters a phrase like “*the patient’s blood pressure is higher than 130*”.  The failure mode is two‑fold:

1. **Syntactic mismatches** – different spellings of operators (`>`, `greater than`, `more than`), ambiguous ordering (`value < feature`), or missing delimiters.
2. **Semantic ambiguity** – where a rule mixes multiple conditions (e.g., “age > 50 and cholesterol ≤ 200”) without clear grouping, making it difficult to decide how many binary features to create.

If these problems are left unresolved, the generated feature matrix would contain many missing or incorrect entries, degrading downstream performance and undermining one of FeatLLM’s selling points: reliable inference without per‑sample LLM calls.

---

### 2. Using the LLM Itself as a Parser – Code‑Generation Prompt

A key insight of FeatLLM is that the same LLM that generated the rules can also be asked to translate them into syntactically correct code.  LLMs trained on large code corpora (e.g., GitHub) have demonstrated strong ability to understand informal mathematical language and produce precise Python expressions.  By delegating parsing to the model itself we avoid hand‑crafting brittle regex pipelines and instead rely on the model’s semantic understanding.

The parsing prompt follows a simple template:

```
You are given a list of rule strings describing conditions for class k.
Convert each rule into a Python function `def rule_i(row):` that returns True
iff the row satisfies the rule. Use only built‑in Python operators.
Return all functions in one code block.
```

Crucially we also provide **context**:

- The exact names of all features (`f_1`, `f_2`, …) and their data types (numeric, categorical, boolean).  
- A short example mapping: `"age > 30"` → `"row['age'] > 30"`.  
- Instructions on handling logical operators: "`AND` should become `and`, `OR` should become `or`".  

Because we constrain the output format (a single Python code block delimited by triple backticks), we can reliably extract the generated code from the LLM’s response.  The model’s internal grammar checking naturally normalizes operator synonyms: “greater than” becomes `>`, “less than or equal to” becomes `<=`, etc.

---

### 3. Executing Generated Python Code Safely with `exec()`

Once we have obtained a string containing valid Python function definitions, we must turn it into callable objects that operate on each data row.  The straightforward way is to use Python’s built‑in `exec()` function:

```python
namespace = {}
exec(generated_code, {}, namespace)
rule_funcs = [namespace[f"rule_{i}"] for i in range(num_rules)]
```

However, executing arbitrary code returned by an external service raises safety concerns.  FeatLLM mitigates these risks in three layers:

1. **Restricted globals** – We pass an empty dictionary for both global and local namespaces to `exec()`.  Consequently, the generated code cannot import modules, access files, or invoke network calls; it can only use basic arithmetic and Boolean operators that are always available.

2. **Static analysis before execution** – A lightweight check scans `generated_code` for any disallowed keywords (`import`, `open`, `eval`, `exec`) and rejects any snippet containing them.

3. **Timeout enforcement** – Each rule function is wrapped by a tiny helper that limits execution time (e.g., using `signal.alarm` on Unix).  Since every rule is simply a Boolean expression over a row’s fields, evaluation completes in microseconds; any function exceeding a millisecond is flagged as malformed and discarded.

Through these safeguards we obtain a reliable list `rule_funcs` where each element maps a single row (represented as a dict `{feature_name: value}`) to either `True` (the rule holds) or `False`.

---

### 4. Constructing the Binary Matrix \(\mathbf{Z}_k\) for Class \(k\)

With callable rule functions in hand, translating an entire dataset \(\{ \mathbf{x}^{i} \}_{i=1}^{N}\) into binary features becomes an embarrassingly parallel operation.  For each class \(k\), FeatLLM extracts \(R\) rules (the paper fixes \(R=10\)).  We denote by

\[
\mathbf{z}^{i}_{k} = \bigl[\, r^{i}_{k,1},\, r^{i}_{k,2},\, \dots,\,
r^{i}_{k,R} \,\bigr]^\top ,\qquad
r^{i}_{k,j} \in \{0,1\},
\]

the vector of indicator values for sample \(i\).  Here \(r^{i}_{k,j}=1\) iff `rule_j(row_i)` returns `True`.  

Collecting these vectors across all \(N\) samples yields the binary matrix

\[
\mathbf{Z}_k = 
\begin{bmatrix}
--- & \mathbf{z}^{1}_{k} & ---\\
--- & \mathbf{z}^{2}_{k} & ---\\
&& \vdots\\
--- & \mathbf{z}^{N}_{k} & ---
\end{bmatrix}
\in \{0,1\}^{N\times R}.
\]

In implementation this amounts to looping over rows (`for row in dataset:`), applying each compiled rule function (`[int(f(row)) for f in rule_funcs]`), and storing the resulting list as one row of \(\mathbf{Z}_k\).  Because each rule evaluation is independent, vectorized libraries (Numba or JAX) can accelerate this step dramatically even for tens of thousands of rows.

The downstream linear classifier then uses \(\mathbf{Z}_k\) as its input feature matrix; see Equation (2) in the paper for how logits are computed from non‑negative weights applied to \(\mathbf{Z}_k\).

### 5. Handling Logical Operators (AND/OR) in Rules

The original natural‑language rules may involve multiple elementary conditions combined with logical connectors.  For instance:

> “Age > 50 **and** cholesterol ≤ 200”.

During code generation we instruct the LLM to preserve these connectors using Python’s boolean operators:

- `"AND"` → `"and"`.
- `"OR"` → `"or"`.

Thus the corresponding function becomes:

```python
def rule_0(row):
    return (row["Age"] > 50) and (row["cholesterol"] <= 200)
```

When a rule contains both AND and OR without explicit parentheses, Python follows its standard precedence (`and` binds tighter than `or`).  To avoid unintended precedence errors we ask the LLM to wrap each atomic condition in parentheses; this yields unambiguous expressions regardless of operator mixing.

In some cases a rule may be expressed as a disjunction of several conjunctions (e.g., “(A > 5 AND B = ‘yes’) OR C ≤ 10”).  The generated function will faithfully mirror this structure:

```python
def rule_3(row):
    return ((row["A"] > 5) and (row["B"] == "yes")) or (row["C"] <= 10)
```

When converting such compound expressions into binary features we retain them as *single* indicators: if any part of the disjunction holds, `rule_3(row)` evaluates to `True`, yielding a value of 1 in \(\mathbf{Z}_k\).  This design choice respects the original logical semantics: each rule encodes *one* decision criterion regardless of internal complexity.

If a user wishes instead to decompose complex rules into multiple primitive binary features (e.g., treat each conjunctive clause separately), this could be done by post‑processing after code generation—splitting on top‑level ORs—but FeatLLM’s default pipeline treats every full rule as one feature because empirical results show that preserving logical grouping often improves signal‑to‑noise ratio when training with very few labeled examples.

---

### Summary

Parsing natural‑language rules into executable binary features involves overcoming noisy textual output, leveraging the LLM itself for robust code generation, safely executing that code via restricted `exec()`, and finally assembling per‑class binary matrices \(\mathbf{Z}_k\).  By handling logical operators explicitly during code generation and preserving them in Python Boolean expressions, FeatLLM transforms high‑level expert knowledge into low‑dimensional yet highly informative representations that power its efficient linear classifier.  This pipeline eliminates per‑sample LLM calls at inference time while still reaping the benefits of massive prior knowledge encoded in large language models.
