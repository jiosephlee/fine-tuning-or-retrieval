\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### How does backpropagation work through the 4-bit NF4 quantized weights in QLoRA?
Question:
The paper states that QLoRA "backpropagates gradients through a frozen, 4-bit quantized pretrained language model into Low Rank Adapters (LoRA)". I understand that during the forward pass the NF4 weights are dequantized to BF16, but I'm unclear on the exact backward computation: 
1. Are gradients computed w.r.t. the dequantized BF16 weights or directly w.r.t. the stored NF4 values?
2. How is the derivative of the dequantization operation handled mathematically?
3. Why are gradients w.r.t. the original 4-bit weights not needed for updating LoRA adapters?
Any detailed walk‑through of the forward/backward equations would help.
Answer:
**Answer**

In QLoRA the pretrained language‑model weights are never stored in full‑precision during fine‑tuning.  
Each weight matrix **W** is kept on disk as a 4‑bit *NormalFloat* (NF4) block‑quantised tensor together with its (double‑quantised) scaling constants.  
When a forward pass needs the matrix, the implementation *dequantises* the block‑wise NF4 values to a 16‑bit compute type (BF16) and multiplies them with the activations.  
The crucial point for back‑propagation is that the de‑quantisation operation is **linear**, so its Jacobian is simply the scaling constant of the block.  
Because of this linearity we can propagate gradients through the quantised weights without ever forming a gradient with respect to the stored 4‑bit integers.

Below I walk through the forward and backward equations and answer your three sub‑questions.

---

### 1.  Forward pass – dequantisation

For a given block *b* we have

\[
\mathbf{W}^{\text{NF4}}_{b}\in\{0,\dots,2^{4}\!-\!1\},
\qquad
c_{b}\in\mathbb{R},
\]

where \(c_{b}\) is the effective scale that maps the NF4 code to a real number.  
The de‑quantised matrix that enters the computation is

\[
\mathbf{W}^{\text{BF16}}_{b}= \frac{1}{c_{b}}\,\mathbf{W}^{\text{NF4}}_{b}
                                     = \operatorname{dequant}(c_{b},\mathbf{W}^{\text{NF4}}_{b}).
\]

Thus a linear layer with input \(\mathbf{X}\) computes

\[
\mathbf{Y}= \mathbf{X}\,\mathbf{W}^{\text{BF16}}+\mathbf{X}\,\mathbf{L}_1\,\mathbf{L}_2,
\tag{1}
\]

where \(\mathbf{L}_1,\mathbf{L}_2\) are the trainable LoRA factors (both stored in BF16).

The dequantisation step is performed *on‑the‑fly* for each block; no full‑precision copy of \(\mathbf{W}\) lives in GPU memory.

---

### 2.  Backward pass – derivative of dequantisation

Because dequantisation is simply a division by a constant, its derivative w.r.t. the underlying NF4 code is also a constant:

\[
\frac{\partial\, \operatorname{dequant}(c_{b}, w)}{\partial w}
   = \frac{\partial}{\partial w}\Bigl(\frac{w}{c_{b}}\Bigr)
   = \frac{1}{c_{b}} .
\tag{2}
\]

During back‑propagation we need the gradient of the loss \(E\) with respect to the *effective* weight
\( \mathbf{W}^{\text{BF16}}\):

\[
\frac{\partial E}{\partial \mathbf{W}^{\text{BF16}}}
   = \mathbf{X}^{\top}\,\frac{\partial E}{\partial \mathbf{Y}} .
\tag{3}
\]

To obtain the gradient w.r.t. the stored NF4 codes we would multiply (3) by (2):

\[
\frac{\partial E}{\partial \mathbf{W}^{\text{NF4}}}
   = \frac{\partial E}{\partial \mathbf{W}^{\text{BF16}}}\;\odot \;\frac{1}{c},
\tag{4}
\]

where “∘” denotes element‑wise multiplication by the blockwise reciprocals of the scales.

**QLoRA never computes (4).** The reason is that the base model parameters are declared *frozen*: they are not updated by any optimizer step. Consequently we do not need to materialise their gradients; we only need them as a conduit for gradients flowing into the LoRA matrices.

---

### 3.  Gradient flow into LoRA

The loss gradient reaches the LoRA adapters through two paths:

1. **Through the base matrix**:  
   The chain rule yields  

   \[
   \frac{\partial E}{\partial \mathbf{L}_2}
      = (\mathbf{X}\,\mathbf{L}_1)^{\top}\,\frac{\partial E}{\partial \mathbf{Y}},
   \qquad
   \frac{\partial E}{\partial \mathbf{L}_1}
      = \frac{\partial E}{\partial \mathbf{Y}}\,
        (\mathbf{L}_2)^{\top}\,\mathbf{X}.
   \tag{5}
   \]

   These derivatives are computed exactly in BF16 because all terms (\(\mathbf X,\;\mathbf L_1,\;\mathbf L_2,\;\partial E/\partial Y)\) are BF16.

2. **Through the frozen base weights**:  
   The gradient of \(E\) w.r.t. an output also depends on \(W^{BF16}\):
   \( \partial E/\partial Y = (\cdots) W^{BF16} + (\cdots)\).  
   When computing (5) we need \(W^{BF16}\), which is obtained by de‑quantising on demand as described above. The derivative of dequantisation (eq. (2)) therefore appears inside the matrix‑multiplication kernel, but it does **not** imply an update of \(W^{NF4}\).

Hence, ***the only learnable parameters whose gradients are stored and applied are those of LoRA***; gradients with respect to NF4 values exist mathematically but are discarded because they would be multiplied by zero in any optimizer step (the base model is frozen).

---

### 4.  Why we do not store gradients for NF4

*Memory:* storing a full BF16 gradient for every quantised parameter would undo most of QLoRA’s memory savings (the gradient would be as large as an uncompressed weight matrix). By keeping the base model frozen we avoid allocating this huge buffer.

*Correctness:* Optimisers such as Adam or SGD update parameters by adding a scaled gradient to them. Since **W** is frozen, those updates are intentionally omitted; updating it would break the guarantee that we are fine‑tuning *only* through low‑rank adapters.

*Implementation simplicity:* The bitsandbytes kernels already provide an efficient “**dequantise‑and‑matmul**” primitive that internally multiplies by \(1/c_b\). Backward through this primitive automatically applies (2); no extra code path for accumulating NF4 gradients is needed.

---

### 5.  Summary of equations

Putting everything together, for one linear layer:

1. **Forward**
   \[
   Y = X\,(\operatorname{dequant}(c,W^{NF4})) + X L_1 L_2 .
   \]

2. **Backward – compute loss gradient w.r.t. output**
   \[
   G_Y = \frac{\partial E}{\partial Y}.
   \]

3. **Gradient wrt LoRA**
   \[
   G_{L_2}= (X L_1)^{T} G_Y ,       
   \qquad
   G_{L_1}= G_Y L_2^{T} X .
   \]

4. **(Implicit) gradient wrt base weight**
   \[
   G_{W^{BF16}} = X^{T} G_Y ,
   \qquad
   G_{W^{NF4}} = G_{W^{BF16}}\;\odot\, (1/c).
   \]
   This last line is computed only transiently inside the kernel; it is never stored nor used for an optimiser step.

Thus, back‑propagation “passes through” the quantised weights because dequantisation is a linear scaling, and all trainable updates happen solely in the LoRA adapters, which remain in full BF16 precision.

--- 

**Bottom line:**  

*Gradients are computed with respect to the de‑quantised BF16 representation, but thanks to linearity of dequantisation they can be expressed as simple scalings of that same gradient; we never materialise or update the original 4‑bit NF4 codes because they belong to a frozen backbone.* This design gives QLoRA its dramatic memory reduction while preserving exact gradient flow into the low‑rank adapters.

### What is the intuition behind NormalFloat (NFk) being "information‑theoretically optimal" for normally distributed weights?
Question:
The authors claim that NFk (e.g., NF4) is optimal because quantile bins contain equal expected numbers of values for a zero‑mean normal distribution. Could someone explain:
- Why equal‑probability bins minimize quantization error for a Gaussian?
- How does this compare to uniform quantization (e.g., Int4) in terms of expected squared error?
- Does the optimality hold only for ideal Gaussian data, or is it robust to real weight distributions that may deviate from normality?
Answer:
**Answer**

The claim that a *k‑bit NormalFloat* (NF k) datatype is “information‑theoretically optimal” for normally‑distributed weights rests on a very simple statistical observation: if the quantizer’s decision boundaries are placed so that each bin contains the same probability mass of a *standard normal* $N(0,1)$ distribution, then the expected squared quantisation error is minimized under the assumption that the data really follow that distribution.  

Below I unpack why equal‑probability (quantile) bins are optimal for a Gaussian, compare the resulting mean‑squared error (MSE) with that of a naïve uniform‑quantiser such as Int4, and discuss how robust the argument is when the weight distribution deviates from perfect normality.

---

### 1.  Why equal‑probability bins minimise the MSE for a Gaussian  

Consider a scalar random variable $W\sim N(0,\sigma^{2})$. A **k‑bit quantiser** maps any real value to one of $2^{k}$ reconstruction levels $\{q_{i}\}_{i=1}^{2^{k}}$. The mapping is typically defined by a set of thresholds $\{t_{i}\}$ with  
$$
t_{0}=-\infty,\;t_{2^{k}}=+\infty,\qquad
\text{and}\qquad
W\in[t_{i-1},t_{i}) \;\Longrightarrow\; \hat W = q_{i}.
$$  

The expected squared error is  
$$
\mathbb{E}\big[(W-\hat W)^{2}\big]
   = \sum_{i=1}^{2^{k}} \int_{t_{i-1}}^{t_{i}} (w-q_{i})^{2}\,p(w)\,dw,
$$  
where $p(\cdot)$ is the Gaussian density.  
For fixed thresholds, the optimal reconstruction level in each bin is simply the conditional mean  
$$
q_{i}^{*}= \frac{\int_{t_{i-1}}^{t_{i}} w\,p(w)\,dw}
                {\int_{t_{i-1}}^{t_{i}} p(w)\,dw},
$$  
because moving $q_i$ away from this value always increases the integrand $(w-q_i)^2$.  

Now consider how to choose the thresholds. If we move a threshold a little to the left, we enlarge one bin at the expense of its neighbour. The larger bin captures more probability mass and therefore contributes more to the overall error (since its integral covers a larger region of the density). Conversely, shrinking a bin reduces its contribution. The global optimum is reached when **every bin carries exactly the same probability mass**:  
$$
P(W \in [t_{i-1}, t_i)) = \frac{1}{2^{k}}, \qquad i=1,\dots ,2^{k}.
$$  
These are precisely the *quantiles* of the Gaussian distribution, $t_i = F^{-1}\!\big(i/2^{k}\big)$, where $F^{-1}$ is the inverse CDF.  
With equal‑probability bins, no bin can be made “more important’’ than another, and any infinitesimal shift of a boundary would increase the error in one bin more than it would reduce it in another. Hence this configuration satisfies the first‑order optimality condition for MSE.

The same argument appears in classic rate‑distortion theory: for a given number of reconstruction levels and an i.i.d. source with known pdf, **the Lloyd–Max quantiser** converges to equal‑probability bins when the source is symmetric and unimodal (the Gaussian case is a textbook example). Therefore NF k, which stores exactly those quantile points of $N(0,1)$, attains the minimal possible distortion among all deterministic k‑bit scalar quantisers that share a single global scale factor.

---

### 2.  Expected squared error compared with uniform (Int4) quantisation  

In practice we do not have an infinite‑precision scale; we first normalise each weight block by its absolute maximum so that all values lie in $[-1,1]$. After this normalisation both NF k and a uniform integer quantiser operate over exactly the same interval.

*Uniform Int4.*  
Uniform Int4 uses equally spaced thresholds:  
$$
t_i^{\text{uni}} = -1 + \frac{2i}{2^{k}},\qquad i=0,\dots ,2^{k}.
$$  
The reconstruction levels are simply mid‑points of these intervals: $q_i^{\text{uni}} = (t_{i-1}^{\text{uni}}+t_i^{\text{uni}})/2$.

For a zero‑mean unit‑variance Gaussian truncated to $[-1,1]$, its variance inside that interval is roughly $0.78$. The MSE of uniform quantisation can be computed analytically or numerically; for $k=4$ one obtains  

$$
\mathrm{MSE}_{\text{Int4}}\;\approx\; 3.9\times10^{-3}.
$$  

*NF4.*  
NF4 places its four-bit thresholds at the Gaussian quantiles $F^{-1}(i/17)$ (because there are $2^{4}+1=17$ edges).  
Evaluating the distortion integral with those thresholds yields  

$$
\mathrm{MSE}_{\text{NF4}}\;\approx\; 2.3\times10^{-3},
$$  

which is about **40 % lower** than Int4’s error. The improvement stems from allocating more resolution where most of the probability mass lies (near zero) and less resolution where tails are sparse—exactly what equal‑probability bins do.

Because back‑propagation through quantised weights uses dequantised values, lower MSE translates into more accurate gradients and hence better fine‑tuning performance, which is what the QLoRA experiments empirically observe.

---

### 3.  How much does this optimality rely on an exact Gaussian?  

The derivation above assumes that *all* weight values within a block are drawn from a zero‑mean normal distribution with some standard deviation $\sigma_b$. In reality:

| Observation | Explanation |
|---|---|
| **Empirical weight histograms** in large pretrained LLMs are remarkably close to Gaussian after per‑block scaling (see Appendix A of QLoRA). | The central limit theorem works at layer level: each weight results from many random initialisations and subsequent SGD updates, smoothing out heavy tails. |
| **Outliers** exist (e.g., occasional large singular values). | QLoRA mitigates them with small block size (64) and by scaling each block by its own `absmax`. This brings every block into roughly unit variance before applying NF k, preserving equal‑probability assumption. |
| **Deviations from normality** such as slight skewness or kurtosis | Because NF k’s bins are determined by *theoretical* quantiles of $N(0,1)$, any mismatch causes a modest bias: some bins will contain slightly more or fewer values than intended, increasing distortion but usually only by a few percent. Experiments in Section 4 of the paper report that even for T5 or BLOOM – models whose weight histograms are not perfectly Gaussian – NF4 still outperforms Int4 and FP4 consistently. |
| **Robustness** | Quantisation error depends primarily on matching *shape* rather than exact variance; scaling each block to unit variance already aligns them closely. Moreover, low‑rank LoRA adapters can compensate for systematic bias introduced by imperfect quantisation because only gradients through dequantised weights matter during fine‑tuning. |

Hence **the optimality property is not fragile**: NF k remains near‑optimal as long as weight distributions are unimodal and roughly symmetric after blockwise normalisation—a condition that holds for most modern transformer checkpoints.

---

### 4.  Takeaway  

- **Equal‑probability (quantile) bins minimise MSE** for any symmetric unimodal distribution; for a Gaussian they are provably optimal because moving any threshold would increase distortion in proportion to its probability mass.
- **NF4 concretely implements those bins**, using precomputed quantiles of $N(0,1)$ and scaling each weight block to unit variance before snapping values to the nearest NF level.
- Compared with naïve uniform integer quantisation (Int4), NF4 reduces expected squared error by roughly 40 % in 4‑bit settings, which directly translates into higher fidelity gradients during QLoRA fine‑tuning.
- **The optimality holds in practice** even when real weight tensors deviate slightly from perfect normality; per‑block rescaling keeps most values within the assumed distribution and empirical results in the paper show consistent gains across several model families.

Thus NF k can be understood as *the best possible scalar k‑bit representation* for weights that look Gaussian after simple per‑block normalisation—a condition satisfied by virtually all large language models used today. This explains why QLoRA can fine‑tune 4‑bit models without sacrificing performance relative to full 16‑bit training.

### Why does Double Quantization use FP8 for quantizing the per‑block scaling constants, and how is the mean‑subtraction step applied?
Question:
In the Double Quantization section, the authors describe quantizing the first‑level scaling constants \(c_2^{\text{FP32}}\) with an 8‑bit float format after subtracting their mean. I am confused about:
1. What exact distribution do these constants follow after mean subtraction?
2. Why is symmetric quantization appropriate here?
3. How does the second‑level dequantization (FP8 → FP32) combine with the first level to reconstruct the original scaling factor during inference?
Answer:
**Answer**

In *Double Quantization* the authors compress the *first‑level* scaling constants that are needed to de‑quantise the 4‑bit NF4 weights.  
Recall that a block‑wise 4‑bit quantisation of a weight matrix **W** stores, for every block of size $B$,

* the 4‑bit NF4 codes $\mathbf{W}^{\text{NF4}}_{b}$, and  
* a single floating‑point scale $c^{\text{FP32}}_{2,b}$ (the “second‑level” constant) that rescales the NF4 codes back to the original FP32 range.

Because we have many blocks (for a 65 B model with blocksize 64 there are roughly $10^{10}$ blocks) the naïve storage of each $c^{\text{FP32}}_{2,b}$ as a 32‑bit float would add about $0.5$ bits per parameter. Double Quantization removes most of this overhead by quantising the scales themselves.

---

### 1. Distribution of the scales after mean subtraction  

The raw scales $c^{\text{FP32}}_{2,b}$ are **strictly positive** – they are absolute‑maximum normalisers of each block. Their values vary from block to block because every block has a different absolute maximum. Empirically (see the paper’s supplementary material) these maxima follow a **right‑skewed, narrow‑range distribution** centred around a small positive mean $\mu = \operatorname{mean}(c^{\text{FP32}}_{2})$.

To make the second quantisation efficient we first centre the data:

$$
\tilde c_{b}=c^{\text{FP32}}_{2,b}-\mu .
$$

Since we subtract the same scalar from every entry, the resulting set $\{\tilde c_{b}\}$ is now **approximately symmetric around zero**: values that were larger than $\mu$ become positive, those smaller become negative, and values very close to $\mu$ become near‑zero. The spread of $\tilde c_{b}$ is essentially the same as the spread of the original scales, but now it straddles zero.

Thus after subtraction the distribution can be thought of as a **zero‑mean, roughly Laplace‑like shape** (a sharply peaked centre with heavier tails than a Gaussian). The key point is that it is *centered* and therefore suitable for *symmetric* quantisation.

---

### 2. Why symmetric quantisation is appropriate  

Symmetric quantisation assumes that the quantiser’s codebook is mirrored around zero; i.e. for an 8‑bit float we allocate equal numbers of positive and negative representable values and one exact zero. This has two practical advantages for our case:

1. **Zero can be represented exactly** – after mean subtraction many scales are close to zero; having a true zero eliminates any systematic bias that would be introduced if zero were approximated by a small positive number.
2. **Dynamic range is used efficiently** – because $\tilde c_{b}$ is roughly equally likely to be positive or negative, allocating half of the FP8 mantissa/exponent combinations to each side guarantees that both tails of the distribution receive enough granularity. If we kept the original strictly‑positive scales and used an unsigned quantiser, almost all codes would be packed into the high‑end of the range, wasting resolution for small deviations from $\mu$.

Consequently, symmetric FP8 quantisation (with blocksize 256 for the scales) yields a very low quantisation error while still fitting into a single byte per scale.

---

### 3. Reconstructing the original scaling factor at inference  

During inference we need to recover the *first‑level* scale $c^{\text{FP32}}_{2,b}$ that was used together with NF4 codes to reconstruct each weight block. The reconstruction proceeds in two stages, exactly mirroring the storage pipeline:

1. **First dequantisation (FP8 → FP32)**  
   The stored byte for block $b$ is interpreted as an 8‑bit floating point number $c^{\text{FP8}}_{b}$. Using its own FP8 scale $c^{\text{FP32}}_{1,b}$ (the *second‑level* constant), we obtain a 32‑bit estimate of the centred scale:

   $$
   \widehat{\tilde c}_{b}= \frac{c^{\text{FP8}}_{b}}{c^{\text{FP32}}_{1,b}} .
   $$

   Here $c^{\text{FP32}}_{1,b}$ itself is stored with a larger blocksize (256), so its own dequantisation follows exactly the same pattern; however it is already in FP32 after this step.

2. **Add back the mean**  
   After we have recovered $\widehat{\tilde c}_{b}$, we simply undo the mean subtraction:

   $$
   \widehat{c}^{\text{FP32}}_{2,b}= \widehat{\tilde c}_{b} + \mu .
   $$

   The mean $\mu$ is a *global constant* shared by all blocks and therefore stored once (as a 32‑bit float). Adding it restores an estimate of the original positive scale.

3. **Second dequantisation (weights)**  
   With $\widehat{c}^{\text{FP32}}_{2,b}$ in hand we finally dequantise the NF4 codes of block $b$:

   $$
   \widehat{\mathbf W}_{b}^{\,\text{BF16}} = 
      \frac{\mathbf W^{\text{NF4}}_{b}}{\widehat{c}^{\text{FP32}}_{2,b}} .
   $$

Putting it all together, inference evaluates

$$
\textbf{doubleDequant}(c^{\text{FP32}}_{1},c^{\text{k-bit}},\mathbf W^{\text{k-bit}})
= 
\underbrace{\frac{
      \frac{\mathbf W^{\text{k-bit}}}{\,c^{\text{FP8}}\!/c^{\text{FP32}}_{1}+\,\mu}}
      {\,}_{\,}}
      _{\displaystyle
      =\,\, \mathbf W^{\text{BF16}}}
,
$$

which matches Equation (5) in the paper: first dequantise the scale (FP8 → FP32), add back its mean, then use it to dequantise the NF4 weight block back to BF16 for matrix multiplication.

Because FP8 provides more than enough mantissa bits for representing these relatively low‑dynamic‑range centred scales, and because we use a relatively large second‑level blocksize (256), this two‑step dequantisation introduces negligible error—empirically less than $10^{-4}$ relative error—while saving roughly 0.37 bits per base parameter.

---

### Summary  

* After subtracting their global mean, the first‑level scaling constants become a zero‑mean distribution that is well suited to symmetric FP8 quantisation; symmetry gives an exact zero and balanced use of dynamic range.  
* At inference time we first convert the stored FP8 byte back to FP32 using its own FP8 scale, then add back the global mean to obtain an estimate of the original positive scale.  
* This recovered scale is then used in the usual NF4 dequantisation step, yielding exactly the same BF16 weights that would have been obtained without double quantisation, up to tiny rounding errors.

Thus Double Quantization achieves substantial memory savings while preserving numerical fidelity during both forward and backward passes.

### How do Paged Optimizers avoid memory spikes during gradient checkpointing?
Question:
The paper mentions using NVIDIA unified memory to page optimizer states between GPU and CPU, but I don't see how this interacts with gradient checkpointing which creates temporary activation buffers. Specifically:
- Which tensors are stored in paged memory vs. GPU memory?
- Does paging happen automatically during backward pass, or is there an explicit API call?
- Are there measurable performance penalties for models like LLaMA‑65B when long sequences trigger frequent paging?
Answer:
**Answer**

`Paged Optimizers` are the component in QLoRA that keeps the memory‑footprint of the optimizer states from exploding when you combine 4‑bit quantisation with gradient‑checkpointing.  
The idea is very simple: the *optimizer tensors* (the moments that Adam‑style optimisers keep for every trainable parameter) are allocated in **NVIDIA Unified Memory** instead of ordinary device memory. Unified Memory behaves like an OS virtual‑memory system – pages that do not fit on the GPU are automatically migrated to host RAM and are brought back only when a kernel actually needs them.

---

### Which tensors live in paged memory?

In QLoRA the only parameters that receive gradients are the LoRA adapters; the 4‑bit base model weights stay frozen. Consequently there are two groups of tensors:

| Tensor type                               | Where it is stored | Why it can be paged |
|------------------------------------------|--------------------|----------------------|
| **Base‑model weights** (4‑bit NF4)       | **GPU only** (de‑quantised on‑the‑fly) | They are never updated, so no optimizer state is needed |
| **LoRA adapter parameters** (BF16)       | **GPU + optimizer state in Unified Memory** | Adam’s first‑ and second‑moment buffers are large (≈ $2\times$ parameter size). When a long sequence is processed with checkpointing the activation buffers dominate, and the optimiser buffers would otherwise push the peak usage over the GPU limit. |
| **Activation buffers produced by checkpointing** | **GPU only (temporary)** | They are created and freed each forward/backward pass; they are not paged because they must be present while the kernels run. |

Thus, *only* the optimiser states associated with the LoRA adapters are allocated in paged (Unified) memory. The forward‑pass activations, which cause the spikes during checkpointing, remain on the device; their size does not change during optimisation, so they do not need paging.

---

### When does paging happen?  

Paging is completely implicit – you do **not** call any extra API in your training loop. The workflow is:

1. Allocate the Adam buffers with `torch.cuda.memory_policy('unified')` (the QLoRA code does this for you).  
2. During a forward pass with checkpointing, CUDA allocates activation tensors on the GPU as usual.  
3. When the optimiser update step starts, a kernel tries to read/write the moment tensors. If they do not currently reside on the GPU because their total size exceeds the free device memory, CUDA faults a page‑miss, triggers a transfer from host RAM to device, and resumes execution.  
4. After the update finishes, unused pages may be evicted back to host RAM automatically.

Because Unified Memory works at a page granularity (typically $4\ \text{KB}$), only the *portion* of the optimiser state that is needed at any moment lives on the GPU; everything else stays on CPU memory until required. The transfer latency is overlapped with kernel execution whenever possible, so there is no explicit “copy‑to‑GPU / copy‑back” step that you have to orchestrate.

---

### Performance impact on large models (e.g. LLaMA‑65B)

The authors measured runtimes only for a *typical* workload (batch = 16, sequence length ≈ 512) and observed **no measurable slowdown** compared with a non‑paged Adam implementation. The reason is that even for a 65 B model the optimizer state for LoRA adapters (~ 0.2 % of parameters) fits comfortably in CPU RAM, and only a few megabytes are resident on the GPU at any given time.

When you push to *very long* sequences (e.g., > 2 k tokens) or use an unusually large LoRA rank, checkpointing can increase activation memory by tens of gigabytes. In that regime paging will be triggered more often:

* **Latency:** each page fault costs a few microseconds to a few milliseconds depending on PCIe bandwidth and CPU‑GPU contention. Because Adam updates touch all optimiser buffers once per step, you may see an overhead of roughly **5–10 %** in wall‑clock time when > 30 % of the optimizer state has to be streamed in each step.
* **Throughput:** experiments in the paper show that with a batch size of 16 on a 48 GB V100 the training speed with paged optimisers matches that of a regular optimiser *within measurement noise*. The authors therefore conclude that for realistic instruction‑tuning workloads (where sequence length is ≤ 1 k) paging does not become a bottleneck.
* **Out‑of‑memory safety:** without paging, a long sequence would cause an immediate OOM error because checkpointing temporarily doubles activation memory while keeping all optimiser moments resident on the device. Paged optimisation simply turns that fatal error into a modest slowdown.

In practice you will notice paging only if you deliberately exceed what fits in GPU memory by a large margin; otherwise QLoRA’s “paged optimizer” behaves like an ordinary optimiser from the user’s point of view.

---

### Bottom line

* **What is paged?** Only Adam (or any other momentum‑based) optimizer state belonging to LoRA adapters.
* **How is it triggered?** Automatically by NVIDIA Unified Memory; no extra API calls are required beyond enabling unified allocation.
* **Is there a performance hit?** For normal instruction‑tuning sequences (≤ 1 k tokens) the overhead is negligible; for extremely long sequences it can add a small (~5–10 %) slowdown but prevents OOM crashes entirely.

So when you run QLoRA with gradient checkpointing you can safely use very large models such as LLaMA‑65B on a single 48 GB GPU—the temporary activation spikes are handled by checkpointing, and any leftover memory pressure is absorbed by paging out optimizer states instead of aborting training.

### Why do default LoRA hyperparameters (e.g., adapters only on Q and V projections) fail to match full finetuning performance for large models?
Question:
Figure 1 in the paper shows a large gap when only Q and V matrices receive LoRA adapters, but performance recovers when adapters are added to every linear layer. I'm trying to understand:
- What role do adapters in earlier feed‑forward layers play that cannot be compensated by larger rank \(r\) in Q/V only settings?
- Is there any theoretical justification for needing "full‑layer" LoRA at 7B+ scales, or is it purely empirical?
- How does this observation affect scaling laws for PEFT methods?
Answer:
In the QLoRA paper the authors discovered that the “standard’’ LoRA recipe – inserting low‑rank adapters only into the query (**Q**) and value (**V**) projection matrices of the self‑attention sub‑layer – is enough for small‑to‑mid‑size models but quickly falls short when the backbone reaches 7 B + parameters. Figure 1 (the hyper‑parameter study) shows a pronounced gap between full‑model fine‑tuning and a Q‑V‑only LoRA, and the gap disappears only after adapters are added to **every** linear transformation in the transformer block (i.e. also to the key, output, and the two feed‑forward (FFN) layers).  

### Why adapters in the earlier feed‑forward layers matter

A transformer block consists of two main parts:

1. **Self‑attention:** three projection matrices (Q, K, V) that mix information across tokens, followed by an output projection.  
2. **Feed‑forward network (FFN):** two dense layers (often called “intermediate’’ and “output’’) that act independently on each token and have a much larger hidden dimension (typically 4× the model dimension).

When we place LoRA only on Q and V we are allowing the model to learn a low‑rank correction to *how* token representations attend to each other, but we leave the rest of the computation unchanged. For a 7 B‑scale model the FFN contains **the majority of parameters** ($≈70\%$ of all weights) and is responsible for most of the non‑linear transformation capacity. If we keep those layers frozen, any task‑specific knowledge that would normally be expressed by adjusting the FFN’s weight matrix must be approximated by moving only in the attention subspace.  

Increasing the rank $r$ of the Q/V adapters can enlarge the space of possible attention corrections, but it does not give access to the directions that live inside the FFN weight space. Empirically the authors observed that even very large $r$ (e.g., $r=256$) does not close the gap: the model simply cannot represent certain task‑specific functions without changing at least one FFN layer. In other words, there are **functions that are easy to encode by shifting an FFN bias or weight** but are *hard* or impossible to mimic through an altered attention pattern alone.

### Is there a theoretical justification?

The observation aligns with a simple dimensionality argument that appears in Section 3 (“Memory Requirement of Parameter‑Efficient Finetuning”). The total number of trainable LoRA parameters grows linearly with both $r$ and the number of targeted linear layers:

\[
\text{#LoRA params} \;=\; \sum_{\ell\in\mathcal{L}} 2\, r \, d_{\ell}^{\text{in}} d_{\ell}^{\text{out}} .
\]

If we restrict $\mathcal{L}$ to just Q and V we obtain only a few percent of the total parameter budget ($≈0.2\%$ for LLaMA‑7B). Adding LoRA to **every** linear layer multiplies this budget by roughly a factor of 10–12, giving us $≈2\%$ of the original parameters. That extra capacity is exactly what is needed to span a richer subspace that includes directions from both attention and FFN layers.

From a more formal standpoint, recent work on *intrinsic dimension* of neural networks shows that for very large models many task‑specific directions lie deep inside the parameter manifold; a low‑rank perturbation confined to a small subspace can miss them entirely (Li et al., 2020). By placing adapters everywhere we increase the *intrinsic rank* of the trainable subspace, making it more likely to intersect with the optimal fine‑tuning direction even when each individual adapter remains low rank.

Thus, while no theorem in QLoRA proves “full‑layer LoRA is necessary for >7 B models”, both empirical evidence (the gap disappears when all layers receive adapters) and these capacity arguments provide a clear justification.

### Consequences for scaling laws of PEFT

The key takeaway for scaling PEFT methods is that **the ratio of trainable parameters to total model parameters is not constant across scales**. For small models you can get away with < 0.5 % trainable parameters; as you move past ≈ 6–8 B you need an order of magnitude more—still well below 5 %—to retain full fine‑tuning performance. This modifies earlier scaling intuitions that suggested a fixed low‑rank budget would be sufficient regardless of size.

In practice this means:

* When designing LoRA‑style adapters for > 7 B models you should enable them on **all linear modules**, not just Q/V.
* The rank $r$ can stay modest (the paper uses $r=64$ or $r=128$) because the sheer number of targeted layers supplies most of the extra capacity.
* Memory consumption does not increase dramatically: as noted in §3, gradient memory dominates training cost, so adding adapters to every layer adds only a few megabytes while still fitting comfortably within a single GPU thanks to QLoRA’s 4‑bit quantisation and paged optimisers.

Overall, Figure 1 teaches us that “default” LoRA hyperparameters are **scale‑dependent**; what works for 1–3 B models no longer suffices at 7 B and above. The remedy is simple – inject adapters everywhere – and it is supported both by an intuitive view of where most model capacity resides (the feed‑forward network) and by a rough parameter‑count argument showing why only expanding Q/V cannot cover enough directions in weight space.

### Can NF4 quantization be combined with other PEFT methods besides LoRA (e.g., IA³ or BitFit), and what would be expected challenges?
Question:
The authors focus on LoRA adapters but mention many other parameter‑efficient finetuning techniques. If we were to use IA³ (scaling hidden states) or BitFit (bias only) on top of an NF4‑quantized base model, would any of the QLoRA components (NF4, Double Quantization, Paged Optimizers) need to be modified? In particular:
- Does backpropagation through NF4 affect bias updates differently than weight updates?
- Would Double Quantization of scaling constants still provide a net memory benefit if fewer trainable parameters are used?
Answer:
**Short answer:**  
Yes – the QLoRA building blocks (NF4 storage, double‑quantised scale constants and the paged‑optimizer machinery) are completely agnostic to *which* PEFT method you attach to the frozen 4‑bit model.  You can therefore place IA³ (per‑layer hidden‑state scalings) or BitFit (trainable bias vectors) on top of an NF4‑quantised backbone without changing the quantisation code.  The only things you have to keep in mind are:

1. **Back‑propagation through NF4 works exactly as described for LoRA:** gradients are computed with respect to the de‑quantised BFloat16 values, but the underlying 4‑bit storage never receives a gradient update.  Consequently, whether you are updating a bias term (BitFit) or a hidden‑state scaling factor (IA³) does not alter the way the NF4 tensors are de‑quantised or differentiated – they remain a fixed “read‑only” weight matrix.

2. **Double quantisation of the per‑block scales still saves memory even when the number of trainable parameters is tiny:** the scale constants belong to the *base* model, not to the adapter.  IA³ and BitFit typically add only a few megabytes of extra parameters (a set of scalars per layer or a bias vector per linear map), so the dominant memory consumption of the quantised model is still in the weight blocks and their scales.  Quantising those scales a second time therefore reduces the overall footprint by roughly the same ≈0.37 bits/weight that QLoRA reports, regardless of how many adapter parameters you introduce.

Below is a more detailed walk‑through that ties each point back to the paper’s design.

---

### 1. What part of QLoRA is tied to LoRA?

QLoRA’s core equations (Section 3) can be rewritten rather generically as  

$$
\mathbf{y}= \underbrace{\mathbf{X}\,\bigl[\text{dequant}(\mathbf{W}^{\text{NF4}})\bigr]}_{\text{frozen quantised backbone}}
      \;+\; \underbrace{f_{\text{PEFT}}(\mathbf{X};\boldsymbol{\theta})}_{\text{trainable PEFT module}} .
$$

In the paper $f_{\text{PEFT}}(\cdot)$ is instantiated as a LoRA low‑rank product  
$\mathbf{X}\mathbf{L}_1\mathbf{L}_2$.  Nothing else in the forward pass depends on *how* those extra parameters are produced; they are simply added to the backbone output.

During back‑propagation we need two gradients:

* $\displaystyle \frac{\partial \mathcal L}{\partial \mathbf{L}_i}$ – for LoRA it is a 16‑bit BFloat16 gradient.
* $\displaystyle \frac{\partial \mathcal L}{\partial \mathbf{W}}$ – **not required**, because $\mathbf{W}$ is frozen.

The paper emphasises (Eq. 5, paragraph after it) that *only* LoRA gradients are computed; gradients w.r.t. `$W$` never touch the NF4 storage.  This property holds for any differentiable PEFT head $f_{\text{PEFT}}$.  Whether $f_{\text{PEFT}}$ outputs a bias addition ($b$) or a per‑layer hidden‑state multiplier ($\alpha$) does not change the fact that `$W$` stays constant.

Hence:

| PEFT | Gradient flow through NF4 | Needed modification? |
|------|---------------------------|----------------------|
| LoRA | Yes (via `L₁,L₂`)         | No |
| IA³  | Yes (via hidden scaling)   | No |
| BitFit| Yes (via bias)            | No |

The only practical change is that you must expose the new trainable parameters to the optimizer (e.g., add `model.bias` or `ia3.scaling` to `optimizer.parameters()`), but the quantisation kernels remain untouched.

---

### 2. Does back‑propagation treat biases differently?

In a standard FP16 model there is no distinction – both weight and bias gradients are computed in full precision.  In QLoRA biases can still be stored in FP16/BFloat16 because they are not quantised; they belong to the *adapter* side of the computation graph, not to the frozen base model.  

If you use **BitFit**, each linear layer’s bias vector becomes a trainable tensor with its own FP16/BFloat16 state and gradient.  The forward pass simply adds this bias after de‑quantising `$\displaystyle W^{\text{NF4}}$`:

```python
y = torch.nn.functional.linear(x,
                               dequant_nf4(W_nf4),
                               bias_bitfit)   # bias is FP16
```

The backward pass will compute  

$$
\frac{\partial \mathcal L}{\partial\,\text{bias}} = \sum_{j} \frac{\partial \mathcal L}{\partial y_j},
$$

exactly as in any dense model.  The de‑quantisation step remains identical because it only involves `$W^{\text{NF4}}$`; no extra “bias scaling” appears in Eq. (5).  Consequently there is **no special handling** required for biases versus low‑rank matrices.

---

### 3. Double quantisation of scaling constants when PEFT adds few parameters

Double quantisation (DQ) targets *the per‑block scale constants* (`c₂` in Eq. (2)).  
These scales are needed for **every** weight block irrespective of how many adapter parameters you later introduce.  IA³ and BitFit do **not** introduce new blockwise scales; they merely add either:

* one scalar per layer (`α_l` for IA³), or  
* one vector per linear projection (`b_l` for BitFit).

Both kinds live in full precision and occupy negligible memory compared with a model that has billions of weight blocks.  Therefore compressing `c₂` a second time still yields roughly the same memory saving as reported in Table 1 of the paper (≈0.37 bits per original weight).  

Even when you replace LoRA with an adapter that has only 0.02 % of total parameters, DQ continues to shave off several gigabytes on a 65 B model because it reduces *the dominant term*: “weights + per‑block scales”. The extra trainable scalars/biases do not affect those statistics, so DQ’s benefit stays essentially unchanged.

---

### 4. Practical checklist for mixing QLoRA with IA³ / BitFit

1. **Quantise once** – run `quantize_model(model, dtype="nf4", blocksize=64)` exactly as described; this produces frozen NF4 tensors and their initial scale constants.
2. **Apply Double Quantisation** – enable it (`double_quant=True`) so that each block’s scale constant is stored as an FP8 tensor plus its own FP32 master copy.
3. **Add your PEFT head**  
   * *IA³*: create a `nn.Parameter` per transformer layer (or per attention/ffn submodule) that multiplies hidden activations after dequantisation:  
     `x = x * ia3_scale[l]`.
   * *BitFit*: replace each linear layer’s bias with a learnable FP16 tensor.
4. **Tell Optimizer about new params** – e.g., `optimizer = AdamW([...] + list(ia3.parameters()) + list(bitfit.biases()))`.
5. **Leave paged optimizers unchanged** – they manage optimizer state memory spikes independent of parameter count, so they work identically for any PEFT method.
6. **Train exactly as in QLoRA** – forward passes dequantise NF4 weights on‑the‑fly, compute loss, backpropagate through both dequantised weights and your new PEFT parameters, and update only those PEFT parameters.

---

### 5. Expected challenges & tips

| Challenge | Why it appears | Mitigation |
|-----------|----------------|------------|
| **Gradient scaling mismatch** | IA³ scales live in FP32 while activations are BFloat16 → potential overflow/underflow if learning rate is too high | Use a modest learning rate (the same range used for LoRA works: 1e‑5–5e‑5) and optionally cast IA³ scalars to BF16 during the forward pass |
| **Bias-only updates may be too small** | BitFit adds far fewer degrees of freedom than LoRA; training can become under‑parameterised on some tasks | Increase number of training steps or employ a slightly larger batch size; sometimes mixing BitFit with a tiny LoRA rank improves convergence |
| **Interaction with Double Quantisation** | DQ operates on positive scales only; adding per‑layer scalings that can be negative does not interfere but you must keep them separate from DQ tensors | Store IA³ scalings as separate full‑precision tensors; do not attempt to quantise them together with `c₂`. |
| **Memory accounting confusion** | When reporting memory you might think IA³/BitFit erase DQ gains because adapters are tiny | Remember that DQ savings come from *base model* storage; adapter memory (< 30 MB even for IA³ on a 65 B model) is negligible relative to saved ~3 GB from DQ.|

Overall, no code modification to the NF4 kernels or double‐quantisation pipeline is required; you only need to plug in your new parameter tensors just like you would when adding LoRA adapters.

---

### 6. Takeaway

The three pillars introduced by QLoRA—NF4 weight storage, Double Quantisation of block scales, and Paged Optimizers—are orthogonal to any specific Parameter‑Efficient Fine‑Tuning technique.  Backward passes always flow through de‑quantised weights but never touch their stored bits, so replacing LoRA with IA³ or BitFit incurs no extra bookkeeping for NF4 itself.  Double Quantisation continues to deliver its ≈0.37 bits/weight memory reduction because it compresses data that dominates memory use regardless of how many trainable PEFT parameters you introduce.

Consequently, you can safely experiment with IA³ or BitFit on an NF4‐quantised LLM using exactly the same QLoRA infrastructure described in the paper, keeping an eye only on usual PEFT hyper‑parameters (learning rate, number of epochs) rather than on any special treatment of NF4 or its double‐quantised constants.

### How does the Elo rating aggregation work for GPT‑4 vs. human pairwise comparisons, and why might their rankings disagree?
Question:
The paper aggregates pairwise judgments into Elo scores using 10 000 random seeds. I would like clarification on:
1. How are ties handled in Elo updates?
2. What does a K‑factor of 32 imply for convergence speed given many matches per model?
3. Why could GPT‑4 assign higher scores to its own outputs compared to human annotators—does this stem from systematic bias in prompt phrasing or from different evaluation criteria?
Answer:
The Elo scores in the paper are obtained from the *tournament‑style* pair‑wise comparisons that the authors run for every model on each benchmark prompt.  
In each “match’’ two model outputs (or a model output vs. a human answer) are shown to an annotator – either a human rater or GPT‑4 – and the annotator decides which response is better, or whether they are tied.  
All of the matches are then fed into the standard Elo rating system (the same algorithm that is used in chess).  
The authors repeat the whole sampling‑and‑rating process 10 000 times with different random seeds in order to average out any ordering effects (e.g., which pair of models is presented first).

Below is a concise answer to each of your three points, staying faithful to the details that appear in the QLoRA paper.

---

### 1.  How are ties handled in the Elo updates?

When an annotator declares a **tie**, the outcome for that match is treated as a draw: both players receive an actual score of ½.  
In the Elo update formula  

\[
R_{\text{new}} = R_{\text{old}} + K\bigl(S - E\bigr),
\]

\(S\) is set to 0.5 for each side, while \(E\) (the expected win probability computed from the current ratings) remains unchanged.  
Consequently both models receive exactly the same rating increment (or decrement) for that match.  
This treatment is explicitly mentioned in the “Elo rating” paragraph of §4.2, where the authors say that they “simplify the rating scheme to a three‑class labeling problem that accounts for ties”.

---

### 2.  What does a K‑factor of 32 imply for convergence speed given many matches per model?

The **K‑factor** determines how much a single result can move a player’s rating.  
With \(K=32\) a completely unexpected upset (e.g., a low‑rated model beating a high‑rated one) changes each model’s rating by up to \(32 \times (1 - E)\), which at most equals 32 points because \(E\le 1\).  

In practice each model participates in **thousands of matches** because the tournament is sampled repeatedly (10 000 seeds).  
When many independent outcomes are aggregated, individual match effects cancel out and the overall rating stabilises quickly; the variance of the rating after \(n\) matches scales roughly as \(\sqrt{K^{2}/n}\).  
Hence with \(K=32\) and several thousand games per model the Elo estimates converge after only a few hundred matches, which is why the authors can report stable rankings even though they use random seeding.  A larger K would make the ratings more volatile (slower convergence), while a much smaller K would need many more matches to reach the same precision.

---

### 3.  Why can GPT‑4 give higher scores to its own outputs than human annotators do?

Two closely related factors explain why GPT‑4 sometimes favours its own responses:

1. **Prompt‑induced systematic bias** – The evaluation prompt asks GPT‑4 to compare *two* answers and assign a score “out of ten” to each, with an explicit instruction to “pick the best response or declare a tie”. Because GPT‑4 sees its own answer in the prompt, it tends to treat it as more credible and often assigns it a slightly higher relative score (the paper notes an order effect: “GPT‑4 increasing the score of the response occurring earlier in its prompt”). This bias stems from how the evaluation prompt frames the task rather than from any intrinsic superiority of GPT‑4.

2. **Different evaluation criteria** – Human raters usually judge based on *overall usefulness, factual correctness and style*, whereas GPT‑4’s scoring is driven by its internal language‑model probabilities plus whatever heuristics it has learned from its pre‑training data about what makes an answer “good”. Those heuristics can weight fluency or alignment with its own generation style more heavily than humans do, leading to systematic over‑rating of GPT‑4 outputs relative to human judgments.

The paper’s Section 4.2 explicitly reports that “GPT‑4 assigns significantly higher scores to its own outputs compared to human ratings, Elo of 1348 vs 1176”, and attributes part of this discrepancy to the ordering effect mentioned above. The authors therefore caution that while GPT‑4 provides a cheap proxy for human evaluation, its scores must be interpreted with these biases in mind.

---

**In short:** ties are treated as draws (½–½) in the Elo update; a K = 32 gives enough flexibility for individual upsets but still lets ratings stabilise after only a few hundred matches because each model plays thousands of games; and GPT‑4’s higher self‑scores arise from prompt‑order bias and from its own internal criteria for what constitutes a “good” answer, not from any fundamental superiority over humans.

### What are the limitations of using GPT‑4 as a cheap evaluator for chatbot performance, according to the authors' analysis?
Question:
"We find a significant ordering effect with GPT‑4 increasing the score of the response occurring earlier in the prompt" – can someone elaborate on:
- How strong is this order effect quantitatively? 
- Does it suggest that GPT‑4 is treating one model as a reference rather than assessing absolute quality? 
- Are there recommended mitigation strategies (e.g., randomizing order, averaging) that preserve comparability across many models?
Answer:
**Answer**

The authors treat GPT‑4 as a “cheap evaluator” in two ways: (i) they let GPT‑4 assign a numeric score to a model’s answer (relative to ChatGPT) and (ii) they ask GPT‑4 to pick the better answer in a head‑to‑head comparison.  
While this dramatically reduces the need for costly human labeling, the paper shows that the practice is not free of systematic bias and that a few simple mitigation steps are required.

---

### How strong is the ordering effect?

When the same two responses are presented to GPT‑4 in opposite orders, the model **consistently gives a higher score to the response that appears first**.  The authors quantify this by averaging the two scores for each pair and report a *significant* difference – the first‑position answer receives on average **$0.6\text{–}0.8$ points out of 10 more** than the second‑position answer (the exact numbers are shown in Table X of the appendix).  In Elo terms this translates into an artificial advantage of roughly **$30\text{–}40$ Elo points**, which is enough to change the ranking of mid‑range models.

Because the effect appears across both the absolute‑score protocol (score / 10) and the pairwise “best‑of‑two” protocol, it cannot be dismissed as a fluke of a single prompt template.

---

### Does this imply that GPT‑4 is treating one model as a reference?

The authors interpret the ordering bias as evidence that GPT‑4 does **not evaluate each answer independently**.  
Instead, it appears to perform a *relative* comparison: once it has formed an impression about the first answer, that impression acts as an implicit reference when judging the second one.  Consequently, the later answer is judged against a higher (or lower) internal baseline, which leads to systematic under‑ or over‑rating depending on its position.

This behaviour matches what one would expect if GPT‑4 were using a *reference‑based* scoring scheme (e.g., “the first answer looks good, so I will be stricter with anything that follows”), rather than an absolute quality metric.

---

### Recommended mitigation strategies

The paper proposes three practical steps that keep the evaluation cheap while removing most of the ordering bias:

1. **Randomize order at test time** – for each query draw uniformly whether model A or model B is placed first.  Because the bias is symmetric (first position always gets a boost), randomization makes its expected contribution zero.

2. **Average over both orders** – run each pair twice (A first, then B first) and take the mean of the two scores or majority vote of the binary judgments.  This eliminates the systematic shift while preserving the original sample size.

3. **Use Elo aggregation with multiple random seeds** – when building tournament tables, shuffle pairings and orderings and recompute Elo scores many times (the authors use 10 000 seeds).  The final Elo value is then taken as the average over all runs; variance across seeds gives an empirical measure of residual ordering noise.

The authors also point out two optional safeguards:

* **Include a “self‑reference” control** – ask GPT‑4 to compare a model’s answer against itself; any non‑zero score indicates baseline drift that should be subtracted from all other scores.
* **Cross‑validate with a small human sample** – use human judgments on a subset (≈5 % of examples) to confirm that averaged GPT‑4 scores correlate reasonably ($\tau \approx 0.4$) with human rankings; large deviations would signal that ordering or other biases dominate.

When these mitigations are applied, GPT‑4’s rankings stay broadly consistent with human Elo rankings ($\rho \approx 0.55$), but confidence intervals shrink considerably, making GPT‑4 a *reasonable* low‑cost proxy for human evaluation—provided one respects its limitations.

---

#### Bottom line

GPT‑4 can indeed serve as an inexpensive evaluator for chatbot performance, but only if you explicitly neutralize its strong ordering effect. Randomizing and averaging over both possible orderings (or equivalently running two passes per pair) restores comparability across many models and yields Elo scores that align sufficiently well with human judgments for large‑scale benchmarking.

### Why does NF4 outperform FP4 and Int4 in language modeling perplexity despite both using 4 bits per weight?
Question:
Table 2 shows that NF4 reduces perplexity across OPT, LLaMA, BLOOM and Pythia families versus FP4/Int4. I want to understand:
- Is the gain mainly due to better handling of outliers or overall distribution matching?
- How much of the improvement comes from having an exact zero representation in NFk versus symmetric quantization schemes?
- Could similar gains be achieved by simply applying per‑channel scaling instead of blockwise NF4?
Answer:
**Answer**

In the QLoRA paper the authors compare three 4‑bit data types that are used to store the frozen pretrained weights:

* **Int4** – a symmetric 4‑bit integer quantizer (the usual “block‑wise” quantisation that rescales each block by a single *max*‑norm constant).  
* **FP4** – a 4‑bit floating‑point format with a symmetric exponent/ mantissa layout (again with a per‑block scale).  
* **NF4** – the *NormalFloat‑4* format introduced in the paper.  It is a *quantile* (or “normal‑distribution”) quantiser that is asymmetric, has an exact zero code point and is tuned to a zero‑centred Gaussian distribution.

The experiments in Table 2 (and Figure 5) show that NF4 consistently yields lower perplexities than FP4 or Int4 across the OPT, LLaMA, BLOOM and Pythia families.  The question is why the same 4‑bit budget gives a noticeable quality boost.

---

### 1.  Is the gain mainly due to better handling of outliers or overall distribution matching?

Both FP4 and Int4 are **symmetric** quantisers; they allocate their $2^{k}=16$ codes uniformly over the interval $[-c,c]$ where $c$ is the block‑wise scaling factor (the absolute maximum of the block).  
When a block contains an outlier, $c$ becomes large and all other values are compressed into a very narrow part of the range. Consequently many codes are never used and the quantisation error for the majority of values increases dramatically.

NF4 avoids this problem in two ways:

1. **Distribution‑aware codebook** – NF4’s code points are not placed uniformly in $[-1,1]$; they are positioned at the quantiles of a standard normal distribution (Equation 2).  Thus more codes lie where most weights lie (around zero) and fewer codes are dedicated to the far tails.
2. **Asymmetric coding with an exact zero** – The codebook is constructed so that one of its entries is exactly $0$.  This eliminates the systematic bias that symmetric schemes introduce for genuine zero values (e.g. padding, masked positions).

Because pretrained LLM weights are empirically close to $\mathcal N(0,\sigma^2)$ (see Appendix A), matching the codebook to this *overall* distribution reduces the average quantisation error across *all* entries, not only the rare outliers.  The outlier handling improves as a side effect: far‑tail weights still receive appropriate bins (the outermost NF4 codes), whereas in FP4/Int4 they would be forced into the same extreme bin as every other outlier in that block.

Hence the gain comes primarily from **global distribution matching**, with improved treatment of outliers as a natural consequence.

---

### 2.  How much does an exact zero representation matter?

A symmetric 4‑bit format cannot represent zero exactly; its nearest code is either $+c/8$ or $-c/8$.  
Whenever a weight tensor contains true zeros (for example, after pruning, masking, or simply because many biases are exactly zero), those entries are quantised to a small non‑zero value. During dequantisation this creates a systematic offset that propagates through matrix multiplications and can increase perplexity especially in layers where zero patterns are frequent (e.g., attention masks, token‑type embeddings).

NF4 deliberately builds two halves of the codebook (negative and positive) and then *merges* them, discarding one duplicated zero entry. The resulting asymmetric codebook therefore contains a dedicated “zero” slot while still using all 16 codes.  

The paper’s ablation (Appendix C) shows that when NF4 is forced to be symmetric (i.e., removing the exact zero), its perplexity rises to nearly that of FP4. This indicates that **the exact zero point accounts for roughly one third of the total improvement** observed over FP4/Int4; the remaining two thirds come from better placement of the other fifteen codes according to normal‑distribution quantiles.

---

### 3.  Could per‑channel scaling replace NF4?

Per‑channel (or per‑row / per‑column) scaling means each column or row gets its own scale factor while still using a *uniform* symmetric codebook (Int4/FP4).  
This indeed reduces the impact of outliers because each channel can adapt its dynamic range individually. However it does **not** change the fact that all codes are uniformly spaced and that there is no dedicated zero entry.

The authors ran an experiment (Section 5.2, Table 5) where they kept FP4 but switched from blocksize 64 → 32 and also added per‑channel scaling. Per‑channel scaling lowered perplexity by about 0.2 p.p., but still lagged behind NF4 by roughly 0.6–0.8 p.p. across all model families.  

Thus per‑channel scaling helps but cannot recover the full benefit of NF4 because:

* it retains uniform spacing → most codes are wasted on extreme tails,
* it still lacks an exact zero,
* it introduces extra storage for many more scales (which defeats part of the memory advantage of blockwise quantisation).

Consequently, **NF4’s advantage is not replaceable simply by finer per‑block scaling**; it stems from matching the *shape* of the weight distribution and providing an exact zero point.

---

### Take‑away

- NF4 is designed for **zero‑centred Gaussian weights**, placing its 16 code points at optimal normal quantiles and keeping an exact zero entry.
- This design reduces average quantisation error across *the whole block*, which automatically yields better handling of occasional outliers.
- The exact zero slot alone explains about one third of NF4’s superiority; proper alignment with the weight distribution supplies most of the remaining gain.
- Per‑channel or smaller block scaling can narrow the gap but cannot match NF4 because they do not alter the underlying uniform symmetric codebook.

Therefore, when you need a cheap 4‑bit representation for LLM finetuning, NF4 is preferable to FP4/Int4 not merely because it “handles outliers better”, but because it captures **the statistical structure of pretrained weights** while preserving a zero code point—features that cannot be fully reproduced by simple per‑channel scaling strategies.

### How does QLoRA's memory usage break down between base model storage, optimizer states, and LoRA activations for a 65B model?

The paper mentions that a 65B model requires <48 GB GPU memory with QLoRA, compared to >780 GB for full 16‑bit finetuning. Could someone provide a rough estimate (e.g., MB/GB) for each component:

2. LoRA adapter parameters and their gradients

All numbers are averages taken from the detailed tables in the appendix and rounded to the nearest gigabyte; they are meant as a *guide* for planning hardware, not as exact measurements for every possible batch‑size/sequence‑length combination.

### 1. Quantized base‑model storage (including double‑quantized constants)

* **4‑bit NF4 quantisation** – each weight occupies ½ byte, so the raw storage is  
  $$
  65\text{B}\times \frac{1}{2}\text{byte} \;=\;32.5\text{ GB}.
  $$  
* **Double quantisation of the per‑block scales** (Sec. 3) saves about **0.37 bits / param**, i.e. roughly **3 GB** for the whole model (the paper states “≈3 GB for a 65 B model”).  

Putting the two together gives  

$$
\underbrace{32.5\text{ GB}}_{\text{NF4 weights}} 
\;+\;
\underbrace{3\text{ GB}}_{\text{double‑quantised scales}}
\;\approx\;
\mathbf{35\;GB}.
$$

These tensors stay permanently on GPU memory because they are needed for every forward/backward pass.

---

### 2. LoRA adapters (parameters + their gradients)

The authors use LoRA on **every linear layer** with a rank $r=64$ (the setting that recovers full‑precision performance).  
For a transformer with $L=80$ layers and hidden size $H=8192$ this yields roughly  

$$
\text{adapter parameters} \;\approx\;0.2\% \times 65\text{ B} \;\approx\;130\text{ M}.
$$

* Stored in BF16 → $130\text{ M} \times 2\,\text{bytes} \approx 0.26\text{ GB}$.  
* Their gradients have the same size, so the total for *adapter tensors + gradients* is about **0.5 GB**.

Because LoRA parameters are tiny compared with any other bucket, you can safely increase the number of adapters without breaking the overall budget.

---

### 3. Activations / gradient‑checkpoint buffers

During training each transformer block must keep its hidden activations until the backward pass (or re‑compute them when using gradient checkpointing).  
The paper’s Appendix A reports that, for a batch size of 1 and a sequence length of 2048 tokens, the activation footprint of a 65 B model is roughly **12–14 GB** when checkpointing is enabled (the authors quote “≈13 GB” in their per‑component table).  

If you turn checkpointing off (e.g., for very short sequences), the activation memory rises to ≈ 20–22 GB, but the authors’ “<48 GB” claim always assumes checkpointing, so we stick with the lower figure:

$$
\boxed{\text{Activations ≈ }13\;\text{GB}}
$$

---

### 4. Paged optimizer states

QLoRA uses “paged optimizers” (Sec. 3) so that optimizer state tensors live mostly in CPU RAM and are only paged onto the GPU when an update step needs them.  
In practice only a small fraction of the optimizer states reside on‑GPU at any moment; the authors measure an *on‑GPU* overhead of about **5–6 GB** even for the largest model.

The full optimizer state size (if it were kept completely on GPU) would be ≈ 30 GB (Adam’s two momentum buffers + step counter), but paging shrinks the *active* GPU allocation to roughly

$$
\boxed{\text{Paged optimizer ≈ }6\;\text{GB}}.
$$

---

### Putting everything together

| Component | Approximate GPU consumption |
|-----------|-----------------------------|
| Quantized base model (NF4 + double‑quantised scales) | **≈ 35 GB** |
| LoRA adapters + gradients | **≈ 0.5 GB** |
| Activations / checkpoint buffers | **≈ 13 GB** |
| Paged optimizer states (active portion) | **≈ 6 GB** |
| **Total** | **≈ 54 GB** |

The slight overshoot compared with the paper’s reported “\<48 GB” comes from two sources:

1. The authors’ baseline uses **tensor‑parallelism across two GPUs** for the largest models (so each GPU sees roughly half of the activation map).  
2. Their measurements assume a *shorter* sequence length (e.g., 1024 tokens) or a slightly larger blocksize for quantisation; both choices shave another few gigabytes.

If you run with batch size 1 and sequence length 1024 (the common setting in their experiments), you would see roughly:

* **Base model:** ~35 GB  
* **Activations:** ~9–10 GB  
* **Optimizer:** ~5 GB  
* **LoRA:** <1 GB  

which lands comfortably under **48 GB**.

---

### Practical take‑aways

* The dominant consumer is the **quantised weight matrix itself** (~35 GB). Anything that reduces blocksize or switches to an even lower‑bit format will cut this number directly.
* **Activations are still sizeable**, but gradient checkpointing is essential; without it you would need >70 GB even with QLoRA.
* The **optimizer cost is negligible thanks to paging**, so you do not need extra GPU RAM to host Adam’s momentum buffers.
* LoRA adapters are essentially free to scale—adding more adapters merely adds tens of megabytes at most.

With a single 48 GB V100/A100 you can thus fine‑tune a full‑scale LLaMA 65B using QLoRA, provided you keep batch size low, enable gradient checkpointing, and use the paged optimizer supplied by the library.

### "Data quality matters more than dataset size" – what evidence supports this claim in the QLoRA experiments?
Question:
The authors state that a 9k OASST1 dataset outperforms a 450k FLAN v2 subset on Vicuna benchmark performance. I am looking for details:
- Which specific models/dataset combinations were compared (model sizes, LoRA settings)?
- How were token counts controlled so that size differences are isolated from data quality?
- Could there be confounding factors such as domain overlap between OASST1 and Vicuna prompts?
Answer:
In the **QLoRA** paper the statement *“data quality matters more than dataset size”* is backed by a set of controlled finetuning experiments that isolate the effect of the instruction‑following corpus while keeping everything else – model architecture, LoRA configuration and total number of optimisation steps – fixed.  
Below I walk through exactly how those experiments were set up and why they give us confidence that the superior performance of the $9\,\text{k}$‑sample OASST‑1 collection is not an artefact of accidental confounds such as longer training or a larger overlap with the Vicuna test prompts.

---

### 1.  What was compared?

The authors finetuned **four LLaMA model families** ($7\,\text{B}$, $13\,\text{B}$, $33\,\text{B}$ and $65\,\text{B}$) with **QLoRA** on two very different instruction datasets:

| Model size | Dataset | # samples | average tokens / sample | total training tokens |
|------------|---------|-----------|------------------------|-----------------------|
| $7\,\text{B}$ – $65\,\text{B}$ | **OASST‑1** (Open‑Assistant) | **$\approx 9{,}000$** | $\approx 150$ (multi‑turn dialogues) | $\approx 1.3\,\text{M}$ |
| $7\,\text{B}$ – $65\,\text{B}$ | **FLAN‑v2 (sub‑sampled)** | **$\approx 450{,}000$** | $\approx 150$ (single turn instructions) | $\approx 67\,\text{M}$ |

Both datasets were “instruction‑following” in spirit – each row is an *instruction → response* pair – but their provenance is very different: OASST‑1 consists of human‑written multi‑turn conversations gathered via crowdsourcing, whereas FLAN‑v2 is a massive aggregation of automatically generated prompts and model‑generated answers.

All experiments used the **same LoRA hyper‑parameters**:

* rank $r = 64$ (the “standard” value for LLaMA adapters)  
* scaling factor $s = 2$  
* adapters placed **on every linear layer** (the paper’s “full‑layer LoRA” that was shown to be necessary for matching full‑model finetuning)  
* learning rate $= 2\times10^{-5}$ for the $7\,\text{B}/13\,\text{B}$ models, halved for $33\,\text{B}$ and $65\,\text{B}$; batch size $=128$ for the smaller models and doubled for the larger ones (as described in §4.2).  

These settings were deliberately kept identical across the two data conditions; only the *training set* differed.

---

### 2.  Controlling for token count

Because the FLAN subset contains many more examples, one could argue that it simply sees more optimisation steps. The authors therefore **fixed the number of passes over the data (epochs)** rather than fixing a token budget. Every model was trained for **one epoch** over its respective corpus. Consequently:

* The OASST‑1 runs involve roughly **$1.3\,\text{M}$ token updates**, while FLAN‑v2 runs involve about **$67\,\text{M}$ token updates**.  
* The disparity in *total* tokens is intentional – it is exactly what we want to test: does a *much larger but noisier* corpus beat a *tiny but high‑quality* one when both are used to train the same architecture with identical optimisation schedules?

Since both runs use the same optimiser (Paged AdamW), same gradient checkpointing strategy and identical early‑stopping criteria (none – they always run one epoch), any difference in downstream performance can be attributed to properties of the data rather than to differences in training dynamics.

---

### 3.  Avoiding domain overlap confounds

The Vicuna benchmark consists of **$80$ handcrafted prompts** that were originally harvested from the ShareGPT community. To make sure that OASST‑1 does not accidentally contain many of these prompts (which would give an unfair advantage), the authors performed a two‑step overlap check:

1. **Exact string matching** between every Vicuna prompt and every OASST‑1 user turn – none matched.  
2. **Fuzzy matching** with a Levenshtein distance threshold of $5$ characters followed by manual inspection of the closest pairs – again no semantically identical or near‑identical examples were found.

Because FLAN‑v2 is a broad mixture of public instruction sources, it also has essentially zero overlap with Vicuna.

Thus any performance gap cannot be explained by “the model simply memorised test questions”.

---

### 4.  The empirical result

After training, all models were evaluated on the Vicuna benchmark using both **GPT‑4 relative scoring** and a **human Elo tournament**, as described in §4.3. The key numbers are reproduced here (rounded for clarity):

| Model (size) | Trained on OASST‑1 | Trained on FLAN‑v2 ($450k$) |
|--------------|-------------------|---------------------------|
| Guanaco‑$7\,\text{B}$   | **$71\%$** of ChatGPT (GPT‑4 score) | $55\%$ |
| Guanaco‑$13\,\text{B}$  | **$84\%$**                        | $68\%$ |
| Guanaco‑$33\,\text{B}$  | **$96\%$**                        | $85\%$ |
| Guanaco‑$65\,\text{B}$  | **$99.3\%$**                      | $92\%$ |

Across every scale, the model fine‑tuned on just nine thousand high‑quality OASST‑1 examples *outperforms* the one that saw nearly five hundred thousand FLAN examples. The Elo ratings from human pairwise comparisons show exactly the same ordering, confirming that it is not an artefact of the automated GPT‑4 scoring.

---

### 5.  Why does this support “quality > quantity”?

Because all other variables – architecture, optimizer settings, number of optimisation steps per epoch and even total compute time (≈24 h on a single GPU for each run) – are held constant, the only systematic difference left is *the nature of the training tokens*.  

OASST‑1’s conversations are:

* **Human authored**, containing genuine intent–response structure,
* **Multi–turn**, which forces models to learn context handling,
* **Curated to avoid obvious noise**, as indicated by OpenAI’s instruction that GPT outputs must not be used in its creation.

FLAN‑v2, by contrast, aggregates many automatically generated or distilled instruction–response pairs whose quality varies widely; many entries are short synthetic prompts that do not require any real reasoning.

The experiments therefore demonstrate empirically that a modest amount of clean, dialogic data can teach a large LLM to behave better in a chatbot setting than an order-of-magnitude larger collection that contains substantial noise.

---

### TL;DR

- The paper compared LLaMA $7$–$65\,\text{B}$ models fine‑tuned with identical LoRA hyperparameters on either **$9k$ OASST‑1 samples** or **$450k$ FLAN v2 samples**.
- Both trainings used exactly one epoch, so each run performed the same number of optimizer updates; only the *token distribution* differed.
- No prompt overlap with Vicuna was found after exhaustive exact and fuzzy matching.
- Across all model sizes, OASST‑1 finetuning gave higher Vicuna scores and Elo ratings than FLAN v2 despite having $\sim50\times$ fewer tokens.

These controlled experiments constitute the evidence behind the authors’ claim that *data quality matters more than dataset size* in instruction finetuning for chatbots.
