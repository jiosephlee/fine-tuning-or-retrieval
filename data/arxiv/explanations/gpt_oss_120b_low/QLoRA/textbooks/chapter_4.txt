\title{A Textbook about the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

Chapter 4: Formal Definition and Training Procedure  

In this chapter we present a complete, step‑by‑step description of **QLoRA**—the method that enables the fine‑tuning of a large language model (LLM) whose parameters are stored in a 4‑bit quantized format.  We start by defining the notation used to describe a single linear layer of a frozen pretrained model together with its Low‑Rank Adapter (LoRA) augmentation.  We then derive the *double dequantization* operation that reconstructs a high‑precision weight matrix from two levels of quantized constants.  After that we walk through the forward pass, showing how the data moves through the “dequant → compute → re‑quant’’ pipeline, and finally we explain why gradients need only be computed for the LoRA parameters and how they are back‑propagated through the quantized base model.  The chapter ends with an algorithmic outline of the entire fine‑tuning loop as it is implemented in practice.

---

## 1. Notation for Quantized Weights, Scales, and LoRA Matrices  

Consider a single linear transformation inside a transformer block, e.g. the feed‑forward projection or an attention projection.  Let  

* \(\mathbf{X}\in\mathbb{R}^{b\times h}\) be the input activation matrix (batch size \(b\), hidden dimension \(h\)).  
* \(\mathbf{W}\in\mathbb{R}^{h\times o}\) be the **pretrained weight matrix** of this layer (output dimension \(o\)). In QLoRA the parameters of \(\mathbf{W}\) are **frozen**; they are never updated during fine‑tuning.  
* The matrix \(\mathbf{W}\) is stored on disk in a **4‑bit NormalFloat** format, denoted \(\mathbf{W}^{\text{NF4}}\).  Each block of size \(B\) (e.g. \(B=64\)) is quantized independently, producing a set of per‑block scaling constants \(\{c_i\}_{i=1}^{n}\).  

Because QLoRA applies *double quantization* to these scaling constants, we introduce two additional tensors:

* \(c_{2}^{\text{FP32}}\in\mathbb{R}^{n}\) – the original 32‑bit scaling factors for each block (one per block).  
* \(c_{2}^{\text{FP8}}\in\mathbb{R}^{n_{\!dq}}\) – the **quantized** version of the scaling factors, produced by a second quantization step (block size for this step is typically 256).  
* \(c_{1}^{\text{FP32}}\in\mathbb{R}^{n_{\!dq}}\) – extra 32‑bit constants needed to recover \(c_{2}^{\text{FP32}}\) from its FP8 representation.

In addition to the frozen base weights we attach a LoRA adapter to this layer:

* \(\mathbf{L}_{1}\in\mathbb{R}^{h\times r}\) and \(\mathbf{L}_{2}\in\mathbb{R}^{r\times o}\) are the low‑rank matrices (rank \(r\ll \min(h,o)\)).  
* The scalar factor \(s\in\mathbb{R}\) controls the overall contribution of the LoRA branch.

All LoRA matrices are kept in **BFloat16** (or FP16) during training; they are the only learnable parameters.

---

## 2. Double Dequantization Formula  

During inference or training we need to recover a *full‑precision* weight matrix from its compressed representation.  QLoRA does this in two stages:

1. **Recover the blockwise scales**:  
   The original per‑block scale \(c_{2}^{\text{FP32}}\) is reconstructed from its FP8 quantized form:
   \[
   c_{2}^{\text{FP32}} = \operatorname{dequant}(c_{1}^{\text{FP32}},\,c_{2}^{\text{FP8}}).
   \tag{1}
   \]
   Here \(\operatorname{dequant}(\cdot,\cdot)\) denotes standard affine de‑quantization: an integer value multiplied by a global scale and added to an offset.

2. **Dequantize the weight tensor**:  
   Given the recovered scale vector and the stored NF4 tensor, we obtain a BFloat16 weight matrix:
   \[
   \mathbf{W}^{\text{BF16}} = 
   \operatorname{dequant}\!\left(
       c_{2}^{\text{FP32}},\, 
       \mathbf{W}^{\text{NF4}}
   \right).
   \tag{2}
   \]
   This operation expands each 4‑bit value into its real value using its block’s scale.

The composition of (1) and (2) is called **double dequantization**:
\[
\boxed{
    \operatorname{doubleDequant}
    (c_{1},c_{2},\mathbf W^{\text{NF4}})
    = 
    \operatorname{dequant}
    \Bigl(
        \operatorname{dequant}(c_{1},c_{2}),\, 
        \mathbf W^{\text{NF4}}
    \Bigr)
    = 
    \mathbf W^{\text{BF16}} .
}
\tag{3}
\]

All arithmetic after this point is performed in BFloat16, which provides sufficient dynamic range for both forward and backward passes while keeping memory usage low.

---

## 3. “Dequant → Compute → Re‑Quant’’ Workflow for One Forward Pass  

For a single linear layer, QLoRA computes an output activation matrix \(\mathbf Y^{\text{BF16}}\) as follows:

### 3.1 Dequantization  

First reconstruct the full precision base weight:
```latex
\mathbf W^{\text{BF16}} = 
    \operatorname{doubleDequant}(c_1^{\text{FP32}}, c_2^{\text{k-bit}}, 
                                 \mathbf W^{\text{NF4}}).
```
The operation touches only cached tensors; no gradient tracking is required because these weights will stay frozen.

### 3.2 Forward Computation  

The final output combines two terms:

1. **Base model contribution** (frozen):
   \[
   \mathbf X^{\text BF16} \;\mathbf W^{\text BF16}.
   \]

2. **LoRA contribution** (trainable):
   \[
   s\,\,\mathbf X^{\text BF16} 
        \;\mathbf L_{1}^{\text BF16} 
        \;\mathbf L_{2}^{\text BF16}.
   \]

Putting them together yields:
```latex
\mathbf Y^{\text BF16} =
    \underbrace{\mathbf X^{\text BF16}
                 \,\operatorname{doubleDequant}(\cdot)}_{\text {base term}}
    +
    s\,\,%
    (\mathbf X^{\text BF16}\,\mathbf L_{1}^{\text BF16})\, 
      \mathbf L_{2}^{\text BF16}.
```
Both matrix multiplications are carried out with standard dense kernels that operate on BFloat16 tensors; no special quantized kernels are needed because dequantization happens once per forward pass.

### 3.3 Optional Re‑Quantization  

During training we keep *only* the LoRA parameters in optimizer state memory; therefore after computing gradients we never write back any update to `$\mathbf W^{NF4}$`. In practice there is no re‑quantization step for the base weights— they remain stored permanently as NF4 on GPU/CPU memory. If one wishes to export a newly fine‑tuned model that includes LoRA weights fused into the base matrix, one can perform a *post‑hoc* fusion:
```latex
    \widetilde{\mathbf W} = 
        \operatorname{doubleDequant}(c_1,c_2,\mathbf W^{NF4}) +
        s\,\,L_1 L_2,
```
followed by a fresh quantization if desired.

## 4. Gradient Flow: Why Only LoRA Gradients Are Needed  

During backpropagation we need derivatives of the loss \(E(\cdot)\) with respect to every parameter that will be updated. Because QLoRA keeps the base weights frozen, their gradients are discarded after they have served their purpose inside the chain rule.

The crucial observation is that to compute gradients for $\mathbf L_1$ and $\mathbf L_2$ we *must* propagate errors through the frozen base weights, i.e.
```
∂E/∂L_i = ∂E/∂Y · ∂Y/∂L_i,
```
and
```
∂Y/∂L_i = X · ∂(s·L_1L_2)/∂L_i .
```
The term $\partial Y / ∂X$ does involve $\mathbf W$, because $Y$ also contains $X\,W$. However, since $W$ does not receive an update, we do not need $\partial E/\partial W$. Instead we only need $\partial X/\partial W$, which can be computed using the *dequantized* version $\mathbf W^{BF16}$:
```latex
∂E/∂X = ∂E/∂Y · (\mathbf W^{BF16} + s·L_1L_2)^T .
```
Thus:

* **Forward pass**: dequantize once, multiply, add LoRA term.
* **Backward pass**: compute gradients w.r.t. activations using $\mathbf W^{BF16}$; those gradients flow into $\mathbf L_1$, $\mathbf L_2$, and eventually into their optimizer states.
* **No gradient storage for $\mathbf W$**: saves huge memory because $\mathbf W$ often accounts for >90 % of parameters.

Consequently, memory consumption during training is dominated by activation checkpoints and LoRA optimizer states; all storage for quantized constants (`$c_1$, $c_2$`) remains small thanks to double quantization.

## 5. End‑to‑End Algorithmic Steps  

Below is a high‑level procedural description that mirrors how QLoRA is implemented in modern PyTorch/HuggingFace pipelines augmented with NVIDIA unified memory (paged optimizers).  

| Step | Operation | Description |
|------|-----------|-------------|
| **0** | **Model Loading** | Load pretrained checkpoint in NF4 format together with its double-quantized constants (`$c_1$, $c_2$`). Load LoRA adapters (initialised randomly). Allocate optimizer state buffers using *paged* memory so that occasional spikes caused by gradient checkpointing can spill to CPU RAM without OOM errors. |
| **1** | **Batch Sampling** | Sample a mini‑batch of token sequences (e.g., length $L$, batch size $b$). Cast input IDs to BFloat16 embeddings (`$\mathbf X$`). |
| **2** | **Dequantize Layerwise** | For each linear layer $l$: <br> a) Retrieve its NF4 weight tensor $\mathbf W_l^{NF4}$ plus per‑block constants $c_{1,l}, c_{2,l}$. <br> b) Compute `$\mathbf W_l^{BF16}=doubleDequant(c_{1,l}, c_{2,l},\,W_l^{NF4})$`. <br> c) Cache `$\mathbf W_l^{BF16}$` for forward use only (no gradient tracking). |
| **3** | **Forward Pass** | Propagate activations through all transformer blocks using: <br> `$\displaystyle h = X·W + s·X·L_1·L_2$` <br>Standard dropout & layernorm remain unchanged and operate in BFloat16. |
| **4** | **Loss Computation** | Compute cross‑entropy loss between predicted logits and target tokens (teacher‐forcing). Loss is scalar `$E$`. |
| **5** | **Backward Pass** | Autograd computes `∂E/∂L_i` for all LoRA matrices while automatically using cached `$\mathbf W^{BF16}$` for any required `∂E/∂X` terms. No gradients are allocated for NF4 weights nor for `$c_1$, $c_2$`. |
| **6** | **Optimizer Update (Paged)** | For each LoRA parameter:<br> a) Retrieve its optimizer momenta from unified memory.<br> b) Apply AdamW or any chosen optimizer step in BFloat16.<br> c) Store updated optimizer states back; if GPU memory is insufficient they are automatically paged out to CPU RAM and later paged back when needed. |
| **7** | **Checkpointing & Logging** | Periodically serialize updated LoRA adapters (often together with a copy of `$c_1$, $c_2$` unchanged). Optionally fuse adapters into base weights for inference only after training completes. |
| **8** | **Repeat** | Return to step 1 until desired number of tokens or epochs have been processed. |

A few practical notes:

* **Mixed Precision:** Although everything is stored as either NF4 or FP8, computations always occur in BFloat16 because it offers enough mantissa bits to avoid overflow while still fitting comfortably on consumer GPUs.
* **Blocksize Choices:** A small blocksize (e.g., 64) for NF4 yields higher fidelity but adds more per–block scales; double quantization mitigates this overhead by compressing those scales further.
* **Paged Optimizers:** Implemented via CUDA’s Unified Memory (`cudaMallocManaged`). When GPU memory pressure rises—typically during long sequence processing—CUDA evicts rarely accessed optimizer tensors to host RAM automatically, preventing hard OOM crashes without manual checkpointing tricks.
* **Zero Gradient Overhead:** Because `$∂E/∂W$` is never materialised, backward graph size shrinks dramatically; this is why fine-tuning a 65 B parameter model fits within ≤48 GB GPU RAM when using QLoRA.

---

### Summary  

QLoRA treats an LLM’s massive weight matrix as an immutable compressed object (`NF4` + doubly quantized scales). By *dequantizing once per forward pass*, performing standard BFloat16 matrix multiplications with added low‑rank adapters, and restricting gradient storage exclusively to those adapters, QLoRA reduces both memory bandwidth and peak GPU allocation by more than an order of magnitude compared with naïve 16‑bit fine‑tuning. The formalism above—starting from notation through double dequantization, forward computation, gradient flow analysis, and finally an algorithmic outline—captures all essential components required for implementing end‑to‑end QLoRA fine‑tuning on modern hardware platforms.
