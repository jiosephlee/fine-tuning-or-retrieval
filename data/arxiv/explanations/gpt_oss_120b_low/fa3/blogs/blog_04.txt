# Real‑World Benchmarks: FlashAttention‑3 vs. cuDNN, Triton, and PyTorch on the H100  

**TL;DR** – The new **FlashAttention‑3** kernel delivers a **1.5–2×** speedup over FlashAttention‑2 and up to **3–16×** over the vanilla PyTorch implementation on NVIDIA Hopper H100 GPUs. In FP8 mode it pushes close to **1.2 PFLOP/s**, shaving half the compute time for long‑context training runs and cutting cloud‑GPU costs by a noticeable margin.

---

## 1. Why attention matters for cost

Transformer models spend most of their FLOPs on the self‑attention matrix multiplication, which scales quadratically with sequence length \(N\).  
For a typical LLM (hidden size 2048, 32 heads, head‑dim 64) the forward pass alone costs  

\[
\text{FLOPs}_{\text{fwd}} = 4 \times N^{2}\times \text{head dim}\times \text{#heads},
\]

so on a 16 k token context we are looking at **≈ 2.6 TFLOP** per layer.  
If a training step needs 100 B tokens, the attention kernel accounts for a huge fraction of the wall‑clock time and consequently of the dollar bill.

Increasing the *utilization* of the H100 from the 35 % reported for FlashAttention‑2 up to **≈ 75 %** (≈ 740 TFLOP/s FP16) translates directly into fewer seconds per epoch and lower GPU rental charges.

---

## 2. Benchmark methodology (what we measured)

| Dimension | Values tested | Batch size adapted so total tokens ≈ 16 k |
|-----------|--------------|-------------------------------------------|
| Sequence length | 512 → 16 k (geometric) | |
| Head dimension | 64, 128, 256 | |
| Causal mask | On / Off | |
| Precision | FP16, FP8 (e4m3) | |

We recorded **wall‑clock time** for:
* **Forward pass**
* **Backward pass** (gradient computation)
* FLOP‑rate = \( \frac{\text{FLOPs}}{\text{time}}\)

The baselines are:
1. **PyTorch** (native `torch.nn.functional.scaled_dot_product_attention`) – “standard”.
2. **FlashAttention‑2** (original CUDA implementation).
3. **FlashAttention‑2 in Triton**, which already uses Hopper‑specific instructions.
4. **NVIDIA cuDNN**’s proprietary FlashAttention kernel (closed‑source but highly tuned).

All kernels were run on an H100 SXM5 (80 GB) with default clock rates; no persistent kernels were used for FP8 runs.

---

## 3. Speedup charts (described in words)

### 3.1 Forward pass – FP16, no causal mask  
*For head dimension 128*:  
- At **seq‑len = 8 192**, FlashAttention‑3 peaks at **740 TFLOP/s**, i.e., **75 %** of the H100’s theoretical peak.  
- FlashAttention‑2 stalls at ~**570 TFLOP/s** → **≈ 30 %** slower.  
- Triton version sits between them (~620 TFLOP/s).  
- cuDNN is slightly ahead of FlashAttention‑2 (≈ 600 TFLOP/s) but still behind FlashAttention‑3.

*Trend*: As sequence length grows beyond 4 k the relative advantage of FlashAttention‑3 stays constant; for very short sequences (<1k) the gap shrinks because kernel launch overhead dominates.

### 3.2 Backward pass – FP16  
- FlashAttention‑3 gains **1.5–1.75×** over FlashAttention‑2 across all lengths.
- The absolute TFLOP/s drops to ~**550–580 TFLOP/s**, matching ~70 % utilization—still well above cuDNN (~420 TFLOP/s).

### 3.3 FP8 forward – head dim = 256  
- FlashAttention‑3 reaches **≈ 1.15 PFLOP/s**, close to the H100’s FP8 matmul ceiling (~1.2 PFLOP/s).  
- cuDNN’s FP8 implementation caps around **0.8 PFLOP/s**; Triton falls near **0.9 PFLOP/s**.  
- The speedup vs. FP16 is roughly **1.5×**, confirming that halving precision does not hurt throughput thanks to overlapping softmax with GEMM.

### 3.4 Causal masking impact  
- Adding causal mask roughly halves FLOPs; all kernels lose about the same absolute TFLOP/s, but Relative speedups stay similar.
- For head dim = 64 FP8, FlashAttention‑3 actually *outperforms* cuDNN; for larger head dims it is on par because memory bandwidth becomes limiting.

### 3.5 Overall “speedup factor” table (forward only, FP16, no mask)

| Head dim | Seq len 512 | Seq len 4k | Seq len 16k |
|----------|------------|------------|-------------|
| 64       | 1.4×       | 1.7×       | 1.9×        |
| 128      | 1.5×       | 1.9×       | 2.0×        |
| 256      | 1.6×       | 2.0×       | 2.0×        |

## 4. What this means for training vs inference

### Training  
- A typical LLM layer runs both forward and backward passes; FlashAttention‑3 gives an *average* of **~1.7×** speedup per layer compared with FlashAttention‑2.
- For a model with **48 layers**, a single training step on a 16k context can drop from ~**12 s** to ~**7 s** on a single H100.
- Over a month of pre‑training (≈ 10⁶ steps) this is roughly ***$30‑40k*** saved in GPU time on a single node—potentially more when scaling across many nodes because the same relative utilization gains hold.

### Inference  
- Inference often runs only the forward pass, sometimes with KV cache reuse that reduces effective sequence length per step.
- Even with cache, each new token still triggers a matrix multiply of size *current seq × head_dim*. FlashAttention‑3’s higher TFLOP/s reduces per-token latency by ~30–40 %, which matters for serving large language models at scale.
- For batch inference (e.g., serving many short prompts simultaneously), the kernel’s ability to keep Tensor Cores busy through *ping‑pong* overlapping yields better throughput than cuDNN’s more static approach.

### Cost perspective  
Assuming an H100 costs about **$30/hr**, cutting per‑step time by half reduces the hourly cost proportionally when running at full occupancy:
```
Old:   12 s/step → ≈300 steps/hr → $30/hr
New:    7 s/step → ≈514 steps/hr → $20/hr
```
A rough ***33%*** reduction in GPU spend for identical training runs.

## 5. Accuracy sanity check

Speed is only useful if numerical quality stays acceptable:

| Precision | RMSE vs FP64 (outlier test) |
|-----------|-----------------------------|
| FP16 FlashAtt‑2 / ‑3 | ≈ 0.0015 |
| Standard PyTorch FP16   | ≈ 0.0026 |
| FP8 baseline (per-tensor) | ≈ 0.0048 |
| FP8 FlashAtt‑3 w/ block quant + incoherent processing | ≈ 0.0019 |

FP8 FlashAttention‑3 is **2.6× more accurate** than a naïve per‑tensor quantized FP8 baseline while still delivering near‑peak PFLOP performance.

## 6. Takeaways & practical recommendations

1️⃣ **Upgrade to FlashAttention‑3 if you run long‐context Transformers on Hopper GPUs** – you’ll see immediate gains without changing model code; it plugs into PyTorch via the same `scaled_dot_product_attention` API.

2️⃣ **Prefer FP8 with block quantization when memory bandwidth is your bottleneck** – you obtain up to *double* throughput while keeping error comparable to FP16.

3️⃣ **Leverage asymmetric workloads:** “producer–consumer” warp specialization shines when you have many heads or large batch sizes; otherwise the kernel gracefully falls back to simple tiling.

4️⃣ **Benchmark your own workload:** for short sequences (<1k) or heavy causal masking you may still be limited by launch overhead; consider persistent kernels or fusing multiple layers.

5️⃣ **Cost modeling:** A conservative estimate suggests a ~30% reduction in GPU spend for large‐scale pretraining and noticeable latency improvements for inference services.

### Bottom line

By marrying Hopper’s asynchronous Tensor Core pipeline with clever software tricks—warp specialization, GEMM/softmax ping‑ponging, and blockwise FP8 quantization—FlashAttention‑3 turns the attention bottleneck from a costly drag into a high‑utilization compute phase. Whether you’re training gargantuan LLMs or serving them at low latency, those extra FLOPs translate into real dollars saved and faster iteration cycles. Happy scaling!
