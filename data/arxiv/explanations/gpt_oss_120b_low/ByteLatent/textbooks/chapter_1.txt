\title{A Textbook about the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

Chapter 1: Introduction to Byte‑Level Language Modeling  

In this chapter we set the stage for understanding **Byte‑Latent Transformer (BLT)**, the first tokenizer‑free large language model (LLM) that matches the performance of tokenization‑based LMs at scale while offering substantial gains in efficiency and robustness.  We first examine why the conventional practice of fixing a vocabulary of tokens is problematic, then argue why operating directly on raw bytes can alleviate those problems.  After reviewing prior attempts to train byte‑level LLMs and the obstacles that prevented them from scaling, we describe the core innovations of BLT—dynamic entropy‑driven patching, a hierarchical architecture that mixes lightweight byte‑level encoders with a global latent transformer, and a compute‑allocation strategy that adapts to data complexity.  Finally we summarize the contributions of the BLT paper and outline how the remainder of this textbook will unpack its design, training methodology, empirical findings, and broader implications.

## Limitations of Tokenization  

Most modern LLMs begin by **tokenizing** input text: a deterministic pre‑processing step that groups consecutive bytes into symbols drawn from a finite vocabulary (often built by byte‑pair encoding, BPE).  Although tokenization dramatically reduces sequence length, it introduces several systematic shortcomings.

* **Domain and modality bias.**  Tokenizers are constructed from a fixed corpus and therefore encode heuristic compression rules that reflect the statistics of that corpus.  When a model encounters text from a new domain (e.g., source code, scientific notation) or a different modality (e.g., mixed Latin/Chinese scripts), the token boundaries may split semantically coherent units or merge unrelated bytes, causing the model to waste computation on easy regions and to under‑allocate resources where predictions are hard.  

* **Sensitivity to input noise.**  Because tokenizers map raw bytes to discrete symbols, any perturbation at the byte level—such as a stray character, a misspelling, or corrupted encoding—can cause a token boundary shift that yields an entirely different token ID sequence.  Consequently downstream models become brittle: small perturbations can change many token IDs, amplifying error propagation during inference.

* **Multilingual inequity.**  Fixed vocabularies allocate a limited number of tokens to each language.  High‑resource languages (English) receive many dedicated tokens, while low‑resource languages receive few or none.  This leads to uneven representation capacity across languages and harms performance on long‑tail scripts.

* **Loss of orthographic knowledge.**  Tokenizers treat each token as an atomic unit; the model no longer sees the underlying characters or bytes that compose it.  Recent work has shown that this hampers abilities such as phonology inference or character‑level manipulation because the model cannot directly attend to sub‑token structures.

These issues are not merely aesthetic; they manifest as measurable gaps in benchmark performance, robustness under noise, and fairness across languages.

## Why Bytes? Flexibility and Robustness  

A **byte** is the smallest addressable unit in most text encodings (UTF‑8).  By feeding raw bytes directly into an LLM we obtain several advantages:

1. **Vocabulary‑free representation.**  There is no need to pre‑define a vocabulary; every possible byte value (0–255) is already known.  This eliminates vocabulary‑induced bias and guarantees coverage of any possible Unicode sequence.

2. **Uniform granularity across domains.**  Whether the data is natural language, source code, mathematical formulas, or non‑Latin scripts, each element is expressed as a series of bytes.  The model therefore does not need separate tokenizers for each domain; it treats all inputs uniformly.

3. **Robustness to corruption.**  Since each byte is processed individually, small corruptions affect only the local context rather than cascading through multiple token IDs.  The model can learn to recover from missing or altered bytes by leveraging surrounding byte information.

4. **Explicit sub‑word modeling.**  Operating at the byte level restores direct access to characters and their compositions (e.g., graphemes → phonemes).  This enables tasks that require fine‐grained orthographic reasoning, such as grapheme‑to‑phoneme conversion or character‐level manipulation benchmarks.

5. **Potential for multilingual parity.**  Because every language is ultimately represented as byte sequences, a single model can learn a unified representation without allocating separate slots in a tokenizer’s vocabulary.

The primary obstacle historically has been **efficiency**: raw byte sequences are typically four to eight times longer than token sequences for comparable text, inflating the computational cost of Transformers whose dominant cost scales with sequence length.

## Historical Attempts at Byte‑Level LLMs and Their Scaling Bottlenecks  

Early efforts at character or byte modeling focused on recurrent architectures (e.g., character RNNs) that could handle long sequences but suffered from limited parallelism and memory bandwidth constraints. With the advent of Transformers, several research lines pursued *byte‐level* models:

* **CharacterBERT / CANINE** employed convolutional or shallow Transformer layers to downsample character streams before feeding them into a deeper encoder–decoder stack. While they showed promise on multilingual tasks, their computational profiles remained dominated by per‑byte feed‐forward networks rather than attention alone.

* **ByT5** demonstrated an encoder–decoder architecture that processed raw bytes without any downsampling (“patching”). Although it achieved reasonable robustness, training required substantially more floating‑point operations because every byte participated in self‑attention.

* **MambaByte** leveraged an attention‐free recurrent state (Mamba) to alleviate per‑byte attention cost but still required all bytes to traverse deep layers during training.

* **MegaByte** introduced *static strided patching*: every \(k\) bytes are concatenated into a fixed‐size “patch” before being fed into a Transformer decoder. This reduced sequence length but allocated compute uniformly across patches; patches containing simple whitespace were treated identically to those containing complex mathematical symbols.

* **SpaceByte** refined MegaByte by splitting patches at whitespace-like bytes so that each word became one patch. This heuristic improved efficiency for natural language but could not adapt to languages without clear whitespace delimiters and still lacked dynamic allocation based on prediction difficulty.

A common theme among these works is that *the feed‑forward component*—which runs on each element independently—dominates FLOP counts when operating on very long byte sequences. Even when attention cost is reduced via sparse patterns or recurrence, the sheer number of per‑byte MLP operations makes scaling beyond hundreds of millions of parameters prohibitively expensive.

## Key Ideas of BLT: Dynamic Patching, Latent Transformer, Compute Allocation  

The **Byte Latent Transformer (BLT)** resolves the above bottlenecks through three synergistic mechanisms:

1. **Entropy‑Driven Dynamic Patching**  
   BLT first runs a lightweight *entropy model*, an auxiliary byte‐level auto‑regressive LM trained on the same data distribution. For each position \(i\) in the input stream it computes the *next‑byte entropy*
   \[
   H(x_i)= -\sum_{v\in\mathcal{V}} p_e(x_i=v \mid \mathbf{x}_{<i})\,
           \log p_e(x_i=v \mid \mathbf{x}_{<i}),
   \]
   where \(\mathcal{V}\) is the set of 256 possible bytes and \(p_e\) is the entropy model’s distribution.
   High entropy indicates low predictability (e.g., start of a new word), while low entropy signals easy continuation (e.g., within “Mozart”).  
   Patch boundaries are placed either when \(H(x_t) > \theta_g\) (a global threshold) or when entropy rises sharply relative to its predecessor,
   \[
   H(x_t)-H(x_{t-1}) > \theta_r.
   \]
   The result is *contextualized patches* whose average size reflects information density: easy regions become long patches (few Transformer steps), difficult regions become short patches (more steps).

2. **Hierarchical Architecture with Local Encoder/Decoder + Global Latent Transformer**  
   - The **Local Encoder (\(\mathcal{E}\))** is a shallow Transformer that consumes raw bytes (embedded via a \(256\times h_{\mathcal{E}}\) matrix) together with *hash n‑gram embeddings*. These embeddings capture local contexts up to eight bytes long without blowing up parameter count.
   - After each encoder layer a *cross‑attention* module aggregates byte representations belonging to the same patch into a *latent patch vector* \(p_j\).  
   - The **Global Latent Transformer (\(\mathcal{G}\))**, an autoregressive deep Transformer with \(l_{\mathcal{G}}\) layers, operates exclusively on these patch vectors using block‑causal attention; it thus processes far fewer steps than a naïve bytewise model.
   - The **Local Decoder (\(\mathcal{D}\))**, also shallow, receives the output patch vectors \(o_j\) from \(\mathcal{G}\), performs cross‑attention in reverse (patches → bytes), and finally emits probabilities over the next byte using a standard softmax over 256 classes.

   Crucially, most FLOPs are spent in \(\mathcal{G}\); because \(\mathcal{G}\) executes only once per patch rather than per byte, overall compute scales with average patch size rather than raw sequence length.

3. **Compute Allocation Aligned with Data Complexity**  
   By tying patch boundaries to next‑byte entropy, BLT automatically *allocates more transformer layers to hard predictions* (short patches) and *fewer layers to easy predictions* (long patches). This contrasts with tokenizers where every token incurs identical compute regardless of its intrinsic difficulty. The dynamic allocation yields up to **50 % fewer inference FLOPs** at fixed performance levels and enables *simultaneous scaling of model size and patch size*: larger patches consume less compute per token so saved FLOPs can be reinvested in widening or deepening \(\mathcal{G}\).

Together these components constitute a novel paradigm: instead of committing FLOPs uniformly via an immutable vocabulary, BLT adapts its computation trajectory online based on statistical uncertainty estimated from data itself.

## Summary of Contributions and Roadmap  

The BLT paper makes four principal contributions:

1. **A tokenizer‑free architecture with dynamic compute allocation**, demonstrating that byte‐level models can match or exceed BPE-based LLMs when evaluated under equal FLOP budgets.
2. **A flop‑controlled scaling study up to 8 B parameters and 4 T training bytes**, showing that Byte Latent Transformers achieve parity with Llama 3 while using up to half as many inference FLOPs.
3. **Evidence that patch size can be jointly increased with model size without violating fixed‐inference budgets**, opening a new axis for scaling LLMs beyond what tokenization allows.
4. **Empirical validation of improved robustness**, including superior performance on noisy inputs, character‐level tasks (grapheme–phoneme conversion, orthographic benchmarks), and low‑resource machine translation—tasks where traditional tokenizers struggle due to lack of subword visibility.

**Fundamentals of Patching – From Bytes to Variable‑Size Units**

---

### 1.  Notation and Basic Objects  

Consider a raw text document that has been encoded as a sequence of bytes  

\[
\mathbf{x}= \{x_{1},x_{2},\dots ,x_{n}\},\qquad x_{i}\in\mathcal{V}_{\text{byte}}=\{0,1,\dots ,255\},
\]

where \(n\) is the total number of bytes in the document.  
A **patch** is a contiguous subsequence of bytes, denoted  

\[
p_{j}= \{x_{s_{j}},x_{s_{j}+1},\dots ,x_{e_{j}}\},
\]

with start index \(s_{j}\) and end index \(e_{j}\) satisfying \(s_{j}=e_{j-1}+1\).  
The ordered collection of patches obtained from \(\mathbf{x}\) is  

\[
\mathbf{p}= \{p_{1},p_{2},\dots ,p_{m}\}, \qquad m < n .
\]

The mapping from a byte stream to patches is performed by a **patching function**  

\[
f_{p}:\;\mathcal{V}_{\text{byte}}^{\,n}\longrightarrow \mathcal{P}^{\,m},
\]

which we can think of equivalently as a binary indicator vector  

\[
b = (b_{1},b_{2},\dots ,b_{n}) , \qquad b_{i}\in \{0,1\},
\]

where \(b_{i}=1\) signals that a new patch starts at position \(i\) (by convention we set \(b_{1}=1\)).  
Given \(b\), the patches are uniquely determined by grouping consecutive bytes between successive “1” entries.

In token‑based language models, a *token* plays the same role as a patch, but the tokenization process imposes two additional constraints:

| Property | Tokens (BPE, WordPiece, …) | Patches (BLT) |
|----------|---------------------------|---------------|
| **Vocabulary** | Finite, learned prior to training (e.g., 128 k entries). | No fixed vocabulary; any byte sequence may become a patch. |
| **Determinism w.r.t. future** | Token boundaries can depend on the *future* characters (the tokenizer runs on the whole string). | Patch boundaries must be decided **incrementally**, i.e. using only the prefix seen so far. |

The lack of a pre‑computed vocabulary frees the model from the compression heuristics baked into BPE and enables *dynamic* allocation of compute, as explained next.

---

### 2.  Metrics that Influence Patch Cost  

The dominant factor in the runtime of a transformer is the number of **Transformer steps** it must execute. In BLT the large “latent” transformer processes *patches* rather than bytes; consequently its cost scales with the number of patches \(m\). Two simple derived quantities capture this relationship:

1. **Average patch size**  
   \[
   \bar{s}= \frac{n}{m},
   \]
   i.e., the mean number of bytes per patch. Larger \(\bar{s}\) ⇒ fewer patches ⇒ fewer forward‑passes through the latent transformer.

2. **FLOP impact**  
   The total FLOPs required per byte can be expressed as  

   \[
   \text{FLOP}_{\text{per byte}}=
   \frac{\text{FLOPs}_{\text{latent}}(m)}{n}
   + \text{FLOPs}_{\text{local encoder}}(n)
   + \text{FLOPs}_{\text{local decoder}}(n),
   \]

   where \(\text{FLOPs}_{\text{latent}}(m)\) grows roughly linearly with \(m\) (the latent transformer has a fixed depth but its self‑attention operates on a sequence of length \(m\)). The two local models always run on every byte, so they are independent of the patching scheme; only the latent term varies with \(\bar{s}\).  

Thus any patching strategy that yields a larger average patch size reduces inference FLOPs without changing model capacity, provided that predictive performance does not degrade.

---

### 3.  Static (Strided) Patching  

#### 3.1 Definition  

The simplest possible function \(f_{p}^{(\text{stride})}\) groups exactly \(k\) consecutive bytes into each patch:

```
for i = 1 … n step k:
    emit patch = {x_i,…,x_{i+k-1}}
```

Formally  
\(b_i = 1\) iff \(i \equiv 1 \;(\mathrm{mod}\; k)\).  
The resulting average patch size equals the stride: \(\bar{s}=k\).

#### 3.2 Implementation Advantages  

* **Deterministic and incremental:** The decision whether to start a new patch depends only on the current byte index, satisfying the incremental property automatically.  
* **Easy FLOP control:** By varying \(k\), practitioners can directly target a desired inference budget.

#### 3.3 Drawbacks  

* **Uniform compute allocation:** Every patch consumes one latent‑transformer step regardless of how hard its content is to predict. Predicting an entire block of whitespace or repetitive code receives the same amount of compute as predicting a complex mathematical expression.  
* **Inconsistent linguistic boundaries:** A word that straddles a stride boundary will be split arbitrarily, leading to different patchings for identical words appearing in different contexts—a source of inefficiency and possible degradation in downstream tasks.

These issues motivate more *data‑aware* grouping strategies.

---

### 4.  Space Patching  

#### 4.1 Heuristic Idea  

Many natural‑language scripts use spaces or other *space‑like* bytes (punctuation, line‑breaks) as clear delimiters between linguistic units such as words or tokens. Space patching respects these delimiters by ending a patch whenever a space‑like byte appears (subject to a minimal non‑space requirement). Formally

```
if x_i ∈ SPACE-LIKE and current_patch contains ≥1 non-space byte:
    start new patch at i+1
```

Here “space‑like” includes any byte that is *not*:
* a Latin alphabet character,
* a decimal digit,
* an UTF‑8 continuation byte.

#### 4.2 Linguistic Rationale  

The first byte after a whitespace typically carries high predictive uncertainty: it begins a new word whose spelling distribution is broad. Allocating an entire latent step to this region gives the model more capacity exactly where it matters most (the “hard” decision point). Subsequent bytes within the same word are usually much easier to predict once enough letters have been observed; they can be processed by cheap local encoders.

#### 4.3 Limitations  

* **Language coverage:** Not all languages use explicit spaces (e.g., Chinese, Japanese), so this heuristic may produce overly long patches on such texts, reducing dynamic allocation benefits.  
* **Rigidity:** The method cannot adapt its granularity beyond “space versus non‑space”, therefore it cannot exploit finer‐grained entropy variations inside words or code identifiers.

---

### 5.  Entropy‑Based Dynamic Patching  

#### 5.1 Motivation  

Both static and space patching rely on handcrafted rules that may not align with *information density*. A more principled approach is to let data dictate where patches should begin by measuring how uncertain the next‑byte prediction is.

#### 5.2 Training an Entropy Model  

A small autoregressive byte‑level language model, denoted \(p_{\!e}\), is trained on the same corpus used for BLT pretraining. For every position \(i\) it yields a conditional distribution over the next byte:

\[
p_{\!e}(x_i=v\,|\, \mathbf{x}_{<i}) , \qquad v\in \mathcal{V}_{\text{byte}} .
\]

From this distribution we compute the Shannon entropy

\[
H(x_i)= -\,\sum_{v \in \mathcal{V}_{\text{byte}}}
        p_{\!e}(x_i=v\,|\, \mathbf{x}_{<i})\, 
        \log p_{\!e}(x_i=v\,|\, \mathbf{x}_{<i}),
        \tag{5}
\]
which quantifies how unpredictable byte \(x_i\) is given its left context.

Because this model is lightweight (≈ 100 M parameters in our experiments), entropy values can be evaluated on‑the‑fly during data loading with negligible overhead; alternatively, for very small receptive windows they can be pre‑computed into lookup tables.

#### 5.3 Turning Entropies into Patch Boundaries  

Two thresholding schemes were explored:

| Scheme | Decision Rule | Intuition |
|-------|----------------|----------|
| **Global threshold** | Start new patch at position \(t\) if \(H(x_t) > \theta_g.\) | Treat any *absolutely* high‑entropy byte as a boundary. |
| **Approximate monotonicity** | Start new patch at position \(t\) if \\\(H(x_t)-H(x_{t-1}) > \theta_r.\) | Detect *relative* spikes within an otherwise decreasing entropy curve – often corresponding to transitions from “easy” to “hard” regions inside a word or code token.|

Both thresholds (\(\theta_g,\theta_r\)) are chosen to hit a target average patch size on a held‑out validation split; this gives precise control over FLOP budgets while still allowing dynamic variation across examples.

#### 5.4 Practical Considerations  

* **Entropy drift:** When evaluating very long contexts (e.g., whole documents), entropies can gradually decrease because the small entropy model’s hidden state accumulates information (“drift”). To mitigate this we periodically reset its hidden state at line breaks and employ the monotonicity rule, which depends only on local differences rather than absolute values.
* **Incrementality:** Because entropy at step \(i\) depends solely on preceding bytes (\(\mathbf{x}_{<i}\)), boundary decisions satisfy



\[
f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i},
\]

making entropy‑based patching compatible with autoregressive generation.

---

### 6.  Incremental vs Non‑Incremental Patching  

A patching scheme is **incremental** if it can determine whether a new patch should start using *only* information from the prefix already seen by the model; future bytes must not influence this decision. Formally,

\[
f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i} .
\tag{6}
\]

This property is essential for generation: when emitting tokens one by one, the model cannot look ahead to decide how to segment what has not yet been produced.

#### 6.1 Why BPE Fails Incrementality  

Byte Pair Encoding builds tokens by repeatedly merging *most frequent* adjacent byte pairs across an entire corpus *before* training begins. As a result:

* The token boundaries for a given prefix can change when more context follows because merging decisions are defined globally.
* Consequently,
  
  \[
  f_{\text{BPE}}(\mathbf{x}_{<i}) \neq f_{\text{BPE}}(\mathbf{x})_{<i},
  \]

so BPE does not satisfy Eq.(6). One could enforce incrementality by inserting an explicit delimiter token after each BPE token during generation, but this inflates sequence length and defeats one of BPE’s efficiency advantages.

#### 6.2 Benefits for BLT  

All three BLT patching methods—static stride, space, and entropy—are designed to be incremental:

* Stride: boundary index known purely from position.
* Space: depends only on whether current byte belongs to a space‑like class.
* Entropy: uses only past bytes via Eq.(5).

Therefore they integrate seamlessly with an autoregressive decoder and allow “on‑the‑fly” determination of whether to invoke the expensive latent transformer at each step.

---

### 7.  Comparative Summary  

| Method | Vocabulary Requirement | Average Patch Size (\(\bar{s}\)) | Incremental? | Main Control Lever |
|--------|------------------------|----------------------------------|--------------|-------------------|
| **Static (Strided)** | None | Fixed hyperparameter \(k\) | Yes | Choose stride \(k\). |
| **Space Patching** | None | Varies; roughly equals average word length (~4–6 bytes in English corpora). | Yes | Definition of “space‑like” bytes; minimal non‑space constraint. |
| **Entropy‑Based** | None (needs auxiliary LM) | Tuned via thresholds (\(\theta_g,\theta_r\)); empirical values ~4–8 bytes for our data mix. | Yes | Threshold values; optionally reset context or change monotonicity window. |
| **BPE Tokenizer** | Fixed vocabulary (e.g., 128 k tokens). | Fixed by tokenizer statistics (~3–5 bytes per token). | **No** (unless extra delimiter added). | Vocabulary size and merge schedule during pretraining phase.|

From an efficiency perspective, static stride offers predictable FLOPs but wastes compute on easy regions; space patching improves alignment with linguistic boundaries at minimal cost; entropy–based dynamic patching achieves the strongest data‑driven allocation by explicitly targeting high‐entropy bytes while still preserving incrementality required for generation.

--- 

In summary, patches constitute flexible, variable‑size computational units that replace static tokens in BLT. By formalizing patches as functions of byte entropy—or simple heuristics like whitespace—BLT can concentrate its most expensive Transformer layers precisely where prediction difficulty peaks, yielding substantial FLOP savings without sacrificing—and often improving—model performance across diverse downstream tasks.

**Architecture of the Byte Latent Transformer**

The Byte Latent Transformer (BLT) departs fundamentally from the token‑centric design that has dominated large language modeling for the past several years.  Instead of first compressing a raw byte stream into a fixed vocabulary of sub‑word tokens, BLT operates directly on the byte sequence and dynamically groups bytes into *patches* whose size is determined by the information density of the data.  This design yields three distinct computational modules:

1. a **local encoder** that ingests raw bytes and produces a compact latent representation for each patch;
2. a **global latent transformer** that processes the sequence of patch representations with full‑scale autoregressive attention; and
3. a **local decoder** that expands the latent patch outputs back to raw bytes.

The three modules are arranged in a high‑level pipeline that is executed both during pre‑training and generation (inference).  The following sections unpack each component, explain how they interact, and clarify why they are essential for achieving BLT’s claimed FLOP efficiency and robustness.

---

## 1. High‑Level Data Flow

During **training**, an input document is first segmented into patches by a *patching function* $f_p$.  The function marks the start of a new patch whenever the entropy of the next‑byte prediction, estimated by an auxiliary small byte LM, exceeds a chosen threshold (or satisfies an approximate monotonicity condition).  The result is a sequence  

\[
\mathbf{p} = \{p_1, p_2, \dots , p_m\},
\qquad m < n,
\]

where $n$ is the number of raw bytes $\mathbf{x}=\{x_1,\dots ,x_n\}$.

Each patch $p_j$ consists of a contiguous subsequence of bytes; its length is variable but on average equal to the *patch size* $s = n/m$.  The data flow then proceeds as follows:

1. **Embedding** – every byte $x_i$ is mapped to an $h_{\mathcal{E}}$‑dimensional vector via a learned lookup table $\mathbf{E}\in\mathbb{R}^{256\times h_{\mathcal{E}}}$.
2. **Hash n‑gram augmentation** – for each byte position $i$, we also compute embeddings for overlapping byte n‑grams (sizes $n=3\dots 8$) using a rolling polynomial hash; these embeddings are summed with the base byte embedding.
3. **Local encoder transformer** – the augmented byte sequence passes through $l_{\mathcal{E}}$ transformer layers that employ *local block‑causal* attention: each byte may attend only to the $w_{\mathcal{E}}$ preceding bytes, respecting document boundaries.
4. **Cross‑attention pooling** – after each encoder layer we apply a Perceiver‑style cross‑attention block that pools the byte representations belonging to patch $p_j$ into a *patch query* $q_j$.  The set $\{q_j\}_{j=1}^{m}$ forms the input to the global model.
5. **Global latent transformer** – an autoregressive transformer $\mathcal{G}$ with $l_{\mathcal{G}}$ layers processes the patch queries using *block‑causal* attention (a patch may attend only to earlier patches).  This step accounts for most of BLT’s FLOP budget because it is executed once per patch rather than once per byte.
6. **Local decoder cross‑attention** – the output patch representations $\{o_j\}_{j=1}^{m}$ from $\mathcal{G}$ are used as keys/values in a symmetric cross‑attention module that projects them back onto per‑byte queries (the current decoder hidden state).
7. **Decoder transformer** – $l_{\mathcal{D}}$ lightweight decoder layers further refine the per‑byte representations before they are projected onto the 256‑byte vocabulary via a linear output head.

During **inference**, steps 1–4 are identical up to generation of query $q_t$ for the next patch boundary.  If $q_t$ signals that we have reached a new patch, step 5 runs once more to produce the next latent patch; otherwise we remain inside the current patch and only step 6–7 are invoked, thereby saving compute on predictable regions of text.

The overall schematic is displayed in Figure 1 of the original paper: raw bytes → encoder → cross‑attention → global transformer → decoder cross‑attention → decoder → output bytes.

---

## 2. Global Latent Transformer

The *global latent transformer* $\mathcal{G}$ lies at the heart of BLT’s language modeling capability.  It receives a sequence of latent patch vectors  

\[
\mathbf{q} = \bigl(q_1, q_2,\dots , q_m\bigr) \in \mathbb{R}^{m\times h_{\mathcal{G}}},
\]

where each $q_j$ encodes all information from its underlying bytes.  

### 2.1 Layer Count and Width

BLT scales $\mathcal{G}$ independently from its local components.  In all experiments reported in the paper, $\mathcal{G}$ adopts exactly the same depth and hidden dimension as a token‑based LLM with comparable parameter count (e.g., Llama 3).  Typical configurations include:

| Model scale | $l_{\mathcal{G}}$ | $h_{\mathcal{G}}$ |
|-------------|-------------------|------------------|
| 400 M       | 12                | 768              |
| 1 B         | 24                | 1024             |
| 8 B         | 32                | 4096             |

Because $\mathcal{G}$ is invoked only once per *patch*, its overall FLOP contribution scales with ${\rm FLOPs}_{\mathcal G}\propto \frac{\text{\#bytes}}{\text{patch size}}\times l_{\mathcal G}h_{\mathcal G}^{2}$.  Consequently, increasing average patch size reduces inference FLOPs almost linearly while freeing budget for deeper or wider global models.

### 2.2 Block‑Causal Attention

Unlike standard causal attention (which can see all preceding tokens), BLT uses *block causal* masking: at position $j$, attention may attend to any earlier patch index $k\le j$, but not beyond.  This restriction respects autoregression at the granularity of patches rather than individual bytes. Mathematically, for queries $Q\in \mathbb R^{m\times d_k}$ and keys $K\in \mathbb R^{m\times d_k}$ we define

\[
\text{Mask}_{jk}= 
\begin{cases}
0 & k \le j\\
-\infty & k>j,
\end{cases}
\]

and compute attention as $\operatorname{softmax}\bigl(\frac{QK^\top}{\sqrt{d_k}} + \text{Mask}\bigr)V$.  

The block causal mask eliminates any dependence on future patches while still allowing each patch to fully attend to all earlier context, which is essential for long‑range reasoning such as code completion or multi‑turn dialogue.

### 2.3 Role in FLOP Budget

Because feed‑forward networks dominate transformer compute when depth grows, nearly all FLOPs during pretraining are spent inside $\mathcal G$.  The paper’s FLOP analysis (§ 4.5) shows that when average patch size doubles (e.g., from 4 bytes to 8 bytes), inference FLOPs drop by roughly 50 % while keeping model capacity constant—exactly what enables BLT to “scale better than tokens”.

---

## 3. Local Encoder

The encoder $\mathcal E$ must convert an arbitrarily long byte string into a compact set of patch queries in a way that is both *lightweight* (to keep overall FLOPs low) and *expressive* (to provide enough signal for $\mathcal G$).  

### 3.1 Byte Embedding Matrix

Each raw byte $b_i\in \{0,\dots ,255\}$ is embedded via a learned lookup matrix  

\[
\mathbf{x}_i = \mathbf{E}[b_i] \in \mathbb R^{h_{\mathcal E}},
\qquad
\mathbf E \in \mathbb R^{256\times h_{\mathcal E}}.
\]

The embedding dimension $h_{\mathcal E}$ is typically between 256 and 512; this modest size keeps per‑byte overhead minimal.

### 3.2 Hash n‑gram Embeddings

Byte context beyond a single symbol provides crucial disambiguation (e.g., distinguishing “th” vs “ht”). BLT augments $\mathbf{x}_i$ with *hash n‑gram embeddings*, constructed as follows:

1. For each position $i$, generate overlapping n‑grams  
   \[
   g_{i,n} = (b_{i-n+1}, b_{i-n+2}, \dots , b_i), 
   \qquad n =3,\dots ,8,
   \]
   skipping any n‑gram where $i < n$.
2. Compute a rolling polynomial hash:  
   \[
   h(g_{i,n}) = \Bigl(\sum_{k=0}^{n-1} c_k\, p^{k}\Bigr) 
        \bmod |\!E_{n}^{hash}\!|,
   \]
   where $(c_k)$ are integer values of bytes, \(p\) is a fixed prime multiplier, and \( |\!E_{n}^{hash}\!|\) denotes table size.
3. Look up an embedding vector in table \(E^{hash}_n\in\mathbb R^{|\!E_{n}^{hash}\!|\times h_{\mathcal E}}\) and sum across all considered n‑grams:
   \[
   e_i = x_i + 
        \frac1{|N|+1}
        \sum_{n=3}^{8} 
        E^{hash}_n\, [ h(g_{i,n}) ] ,
   \]
   where \(N = \{3,\dots ,8\}\).

Hashing eliminates storage blowup: despite there being \(256^n\) possible n‑grams, only a few hundred thousand entries per n‐gram length are needed, ensuring constant memory while still providing strong contextual cues.

### 3.3 Encoder Transformer Layers with Local Block‑Causal Windows

The augmented vectors $(e_i)$ pass through $l_{\mathcal E}$ transformer layers (often just one or two). Each layer uses *local block causal* attention with window size \(w_{\mathcal E}\) (e.g., 512). A token at position \(i\) can attend only to positions in  

\[
[i-w_{\mathcal E},\, i]\cap[1,n],
\]

ensuring quadratic attention cost remains proportional to \(n\, w_{\mathcal E}\) rather than \(n^2.\)

Every encoder layer also incorporates standard components: LayerNorm (RMSNorm), SwiGLU feed–forward networks, and rotary positional embeddings (RoPE) applied only within self‐attention; however no positional encodings are added inside cross‐attention because patches already encode absolute order through their sequential indices.

### 3.4 Cross‑Attention Design (Perceiver Style)

After each transformer layer we apply a Perceiver-inspired cross‐attention module that aggregates bytes belonging to each patch into a single query vector:

* **Queries** – one per patch; initialized by pooling raw byte embeddings belonging to that patch (max‐pooling in experiments).  
* **Keys / Values** – derived from the most recent encoder hidden states \(h^{(l)}_i.\)

Formally for layer $\ell$, let  
\(P^{(\ell-1)}_j = {\rm Pool}(h^{(\ell-1)}_{i: i\in p_j})\) be the initial query for patch \(j.\) Then

\[
Q^{(\ell)}_j = W_q\, P^{(\ell-1)}_j,\quad
K^{(\ell)}_i = W_k\, h^{(\ell-1)}_i,\quad
V^{(\ell)}_i = W_v\, h^{(\ell-1)}_i,
\]

and we compute multi–head attention restricted so that query \(Q_j\) attends only to keys/values whose underlying bytes lie inside its own patch \(p_j.\) The output replaces or augments \(P^{(\ell-1)}_j,\) after which it proceeds to either another encoder layer or—if this was the final encoder layer—to become input for $\mathcal G.$  

Key design choices:

* **No positional embeddings** in this module because relative order within each patch has already been captured by preceding self­attention windows.
* **Multi–head dimension** may be smaller than that of later global processing (\(U_{\mathcal E}<h_{\mathcal G}\)); after cross‐attention we concatenate heads back into full dimensionality.
* **Residual connections** ensure stable gradient flow across many patches.

### 3.5 Query Initialization Choices

Three strategies were explored:

| Strategy | Description |
|----------|-------------|
| Learned constant | Same learnable vector for every query regardless of content |
| Hash embedding | Query equals sum of hash n‑gram embeddings for bytes inside the patch |
| Max‐pool | Query obtained by max‑pooling across encoder hidden states belonging to the patch |

Empirically max‑pooling yielded slightly better downstream performance while remaining simple; hash initialization helped when combined with deeper decoders.

### 3.6 Positional Encoding Choices

Within self‐attention layers we use RoPE with large scaling factor ($\theta=500\,000$), which provides smooth relative position encoding without adding explicit learnable tables—important because patches vary in length and static absolute positions would be ambiguous across different data points. No positional encoding is added to cross‐attention because its masking already enforces strict intra‑patch locality.

## 4. Local Decoder

The decoder mirrors many aspects of the encoder but works in reverse: it starts from latent patches produced by $\mathcal G$ and reconstructs raw bytes one at a time.

### 4.1 Symmetric Cross‑Attention

In contrast to encoder cross‐attention where patches queried bytes, decoder cross‐attention lets each *byte query* attend to relevant *patch vectors*. Concretely:

* **Queries** – current per–byte hidden state $d_{l,i}$ (initially set to encoder’s final hidden vectors).
* **Keys / Values** – linear projections of all global outputs $\{o_j\}_{j=1}^m,$ duplicated across heads:
  
  \[
  K_j = W_k\, o_j,\qquad V_j=W_v\, o_j .
  \]

Since each byte belongs uniquely to one source patch, we mask queries so they can attend only to their originating patch’s key/value pair; this maintains deterministic reconstruction without leakage across patches.

The attention output updates each byte representation:

\[
d'_{l,i}= d_{l,i}+W_o\, {\rm softmax}\Bigl(\frac{
 Q_i K^\top}{\sqrt{d_k}}\Bigr)V .
\]

A residual connection surrounds this block just like in Perceiver’s original formulation.

### 4.2 Decoder Transformer Layers

After cross-attention we feed the updated byte vectors through $l_{\mathcal D}$ lightweight transformer layers with local block causal windows ($w_{\mathcal D}$ analogous to encoder). These layers refine byte predictions while staying computationally cheap because they operate over far fewer steps than would be required if every byte were processed by a full deep transformer.

### 4.3 Output Projection and Training Objective

The final decoder hidden state at position $i$, denoted $d_{L,i}\in \mathbb R^{h_{\mathcal D}}$, is projected onto logits over the full byte vocabulary:

\[
z_i = W_{\rm out}\, d_{L,i} + b_{\rm out},
    \qquad W_{\rm out}\in \mathbb R^{256\times h_{\mathcal D}} .
\]

A standard categorical cross–entropy loss is applied against target byte $x_i$:  

\[
\ell_i = -\, \log p(x_i | x_{<i}),
    \quad 
    p(x_i)= {\rm softmax}(z_i).
\]

During training this loss is summed over all bytes in a batch; during evaluation we report Bits‑Per‑Byte (BPB),

\[
{\rm BPB}= 
   \frac{\sum_i \ell_i}{\,n\,\ln(2)},
\]

which normalizes perplexity by raw byte count and thus allows fair comparison between tokenizer­-based and token­less models.

### 4.4 Interaction Between Encoder and Decoder Hidden States

Although encoding and decoding are separate modules, they share two crucial pathways:

1. **Encoder hidden states feed decoder queries:** The initial decoder queries are set equal to encoder outputs at corresponding byte positions ($d_{0,i}=h_{l_\mathcal E,i}$). This provides fine–grained context about sub‑patch structure before any global information arrives.
2. **Global latent transformer bridges them:** The latent representation flowing from encoder → cross‑attention → global transformer → decoder cross‑attention acts as an information bottleneck; augmenting it improves long–range coherence while preserving locality in both direction passes.

The cascade thus resembles an autoencoder where compression occurs at dynamic granularity determined by entropy; decompressing restores exact byte order required for language modeling loss.

## 5. Summary of Architectural Contributions

| Component | Primary Function | Key Design Choices | Effect on FLOPs |
|-----------|-----------------|--------------------|-----------------|
| Local Encoder | Transform raw bytes → compact per-patch queries | Byte lookup + hash n-gram augmentation; shallow transformer ($l_\mathcal E$); local block-causal window; Perceiver-style cross-attention | Constant per-byte cost regardless of model size |
| Global Latent Transformer | Autoregressive modeling over patches | Deep transformer ($l_\mathcal G$); block-causal mask; full self-attention over patches | Dominates total FLOPs; inversely proportional to average patch size |
| Local Decoder | Expand latent patches back → raw bytes | Symmetric cross-attention (bytes query patches); light decoder (`l_\mathcal D`); output projection onto vocabulary | Small per-byte overhead; enables exact token-free generation |

By decoupling “how much” computation (global depth/width) from “how often” it occurs (patch frequency), BLT can allocate more parameters where they matter most—on high entropy portions of text—while saving compute on trivial continuations such as whitespace or predictable code identifiers. This architecture underlies all empirical gains reported in the paper: parity with Llama 3 at compute-optimal training budgets, up-to-50% inference FLOP reduction, robust handling of noisy inputs, and superior scaling when both model size and average patch size grow together under fixed inference cost constraints.
