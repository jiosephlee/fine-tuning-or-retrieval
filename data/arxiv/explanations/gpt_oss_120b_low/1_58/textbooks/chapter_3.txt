\title{A Textbook about the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

Chapter 3: The BitNet Architecture: From FP16 Transformers to 1‑bit Linear Layers
=====================================================================

In this chapter we explore the architectural changes that turn a conventional FP16 Transformer into a 1‑bit (technically 1.58‑bit) model, focusing on the replacement of the ubiquitous `nn.Linear` layers with **BitLinear**.  We begin with a concise review of the standard Transformer block used in modern large language models (LLMs).  Then we describe how BitLinear encodes its weights in a ternary set \(\{-1,0,+1\}\), how matrix multiplication is performed using only integer additions, and why this change eliminates floating‑point multiplications.  Next we discuss how these modifications can be integrated into popular open‑source LLM toolkits such as Hugging Face Transformers, vLLM, and `llama.cpp`.  Finally we examine the limitations that arise when using a pure binary weight scheme and motivate the introduction of an additional zero value, arriving at the 1.58‑bit representation of **BitNet b1.58**.

---

## Recap of the Standard Transformer Block

A modern LLM typically follows the architecture popularized by the LLaMA family and other decoder‑only Transformers.  Each **Transformer block** consists of three main components:

1. **Linear transformations (`nn.Linear`)** – dense matrix multiplications that map an input representation \(\mathbf{x}\in\mathbb{R}^{d_{\text{in}}}\) to an output \(\mathbf{y}= \mathbf{W}\mathbf{x} + \mathbf{b}\), where \(\mathbf{W}\in\mathbb{R}^{d_{\text{out}}\times d_{\text{in}}}\) and \(\mathbf{b}\) is a bias term.  In FP16 or BF16 training these operations are performed with 16‑bit floating‑point values, leading to both a multiplication and an addition for every pair of input and weight elements.

2. **Normalization (`RMSNorm`)** – instead of the historically common LayerNorm, many recent LLMs employ RMSNorm, which normalizes a vector by its root‑mean‑square:
   \[
   \operatorname{RMSNorm}(\mathbf{x}) = \frac{\mathbf{x}}{\sqrt{\frac{1}{d}\sum_{i=1}^{d}x_i^{2}}}\odot\boldsymbol{\gamma},
   \]
   where \(\boldsymbol{\gamma}\) is a learnable scale vector and \(d\) denotes the hidden dimension.

3. **Fusion feed‑forward (`SwiGLU`)** – the feed‑forward sublayer mixes two linear projections with a gated activation known as SwiGLU:
   \[
   \operatorname{SwiGLU}(\mathbf{x}) = \operatorname{Swish}(\mathbf{W}_1\mathbf{x})\odot (\mathbf{W}_2\mathbf{x}),
   \]
   where `Swish(z)=z\sigma(z)` and \(\mathbf{W}_1,\mathbf{W}_2\) are weight matrices.

4. **Positional encoding (`Rotary Positional Embedding`, RoPE)** – rotary embeddings inject relative position information directly into the query and key vectors by rotating them in a complex plane, which preserves the linearity of attention while providing strong extrapolation ability.

All other architectural choices (e.g., bias removal, embedding dimension, number of attention heads) are inherited from the underlying LLaMA design.  The bulk of computation—and consequently energy consumption—in such models stems from the numerous `nn.Linear` operations that dominate each block’s forward pass.

## Design of BitLinear: Ternary Weight Representation and Integer Arithmetic

### 1. Weight Quantization to Ternary Values

`BitLinear` substitutes a full‑precision weight matrix \(\mathbf{W}\in\mathbb{R}^{m\times n}\) with a quantized ternary matrix \(\widetilde{\mathbf{W}}\in\{-1,0,+1\}^{m\times n}\).  The quantization proceeds in two steps:

1. **Scaling by the average absolute value**:
   \[
   \gamma = \frac{1}{mn}\sum_{i=1}^{m}\sum_{j=1}^{n}|W_{ij}|.
   \]
   This scalar captures the typical magnitude of entries in \(\mathbf{W}\).  Adding a tiny constant \(\epsilon\) avoids division by zero.

2. **Rounding and clipping**:
   \[
   \widetilde{\mathbf{W}} = 
   \operatorname{RoundClip}\!\left(\frac{\mathbf{W}}{\gamma+\epsilon},\, -1,\, +1\right),
   \]
   where
   \[
   \operatorname{RoundClip}(x,a,b)=\max\!\bigl(a,\;\min(b,\;\operatorname{round}(x))\bigr).
   \]
   Each scaled entry is rounded to its nearest integer and then clipped so that only -1, 0, or +1 remain.

The result is a **binary‑plus-zero** representation: each weight now occupies effectively 1 bit when stored as either +1 or -1, plus an additional sparsity bit to indicate zero values.  Across an entire matrix this yields an average storage cost of \(1.58\) bits per weight—the origin of the “b1.58’’ moniker.

### 2. Integer‑Only Matrix Multiplication

Consider a standard matrix multiplication required for a linear layer:
\[
\mathbf{y}= \widetilde{\mathbf{W}}\;\mathbf{x},
\]
where the input activation vector (or token batch) \(\mathbf{x}\) is quantized to **8‑bit integers** (as employed by BitNet).  Because every entry of \(\widetilde{\mathbf{W}}\) belongs to \{-1,0,+1\}, each product reduces to one of three possibilities:

* If \(w_{ij}=+1\): contribution \(= x_j\).
* If \(w_{ij}=0\): contribution \(=0\).
* If \(w_{ij}=-1\): contribution \(= -x_j\).

Thus **multiplication disappears entirely**; only sign handling (a cheap conditional or XOR) and addition are required.  The entire forward pass of `BitLinear` can therefore be expressed as a series of integer additions:

```
y_i = Σ_j (sign(w_ij) * x_j)
```

where `sign(w_ij)` is either +1, -1 or omitted for zero entries.  In hardware terms this means replacing *multiply‑accumulate* units (MACs) with *add‑only* units, drastically reducing circuit complexity, power draw, and latency.

### 3. Activation Quantization

Activations are kept at **8‑bit integer precision**, but unlike the original BitNet recipe they are symmetrically quantized to the range \([-Q_b,\;Q_b]\) for each token rather than being offset to include a zero point.  This simplification removes an extra subtraction step during dequantization and aligns well with integer addition pipelines while having negligible impact on model quality in practice.

## Advantages of Eliminating Multiplications in Matrix Multiplication

The replacement of floating‑point multiplications with integer additions yields several concrete benefits:

| Aspect | FP16 (standard Transformer) | BitLinear (ternary weights) |
|--------|----------------------------|-----------------------------|
| **Arithmetic type** | FP16 multiply + FP16 add | INT8 add (with optional sign flip) |
| **Energy per operation** | Tens to hundreds of picojoules (FP16 multiplication dominates) | A few picojoules for INT8 addition; sign handling is negligible |
| **Hardware demand** | Requires full floating‑point units; high silicon area | Can be implemented with simple adder trees; reduced silicon area permits higher parallelism |
| **Memory bandwidth** | Transfers full FP16 weight matrices (16 bits per element) | Transfers ternary weights stored in packed form (~1.58 bits per element); bandwidth reduction >10× |
| **Latency** | Scales linearly with total FLOPs; limited by MAC throughput | Dominated by addition latency; achieves speedups up to \(>4\times\) for larger models as shown empirically |

Because matrix multiplication constitutes roughly half or more of all arithmetic operations inside a decoder-only LLM, these savings translate directly into lower overall inference latency and power usage.  Empirical results from the paper show that for models larger than \(3\,\text{B}\) parameters, BitNet b1.58 attains up to **4.1× faster inference** compared with its FP16 counterpart while consuming only about **3–4× less GPU memory**.

## Integration with Existing LLM Toolkits

One pragmatic concern when introducing a new arithmetic format is compatibility with existing software ecosystems that already host large collections of pretrained models and serve them at scale.

### 1️⃣ Hugging Face Transformers

The BitNet design mirrors LLaMA’s architecture: it uses RMSNorm, SwiGLU, rotary embeddings, and removes biases—all components already implemented in Hugging Face’s `transformers` library.  To integrate `BitLinear`, developers replace each occurrence of `nn.Linear` in the model definition with a custom module inheriting from `torch.nn.Module`. The forward method simply loads pre‑quantized ternary weights (packed into byte tensors), expands them on‑the‑fly into sign masks during inference, and then performs integer addition using PyTorch’s built‑in integer kernels or custom CUDA kernels.

Because all other layers remain unchanged, loading a BitNet checkpoint follows exactly the same procedure as loading any other model: you call `from_pretrained()` pointing at a directory containing `pytorch_model.bin` (now holding ternary weights) plus configuration files indicating `bits=1.58`. The tokenizer pipeline also stays identical.

### 2️⃣ vLLM

vLLM focuses on high‑throughput serving by batching requests across GPUs while overlapping kernel execution and memory transfers. The authors incorporated BitNet b1.58 into vLLM by linking against NVIDIA’s **FasterTransformer** library—already used for FP16 inference—and adding support for the **2‑bit kernel from Ladder**, which efficiently processes ternary matrices packed into two bits per weight entry plus sparsity handling.

In practice this means vLLM can schedule “BitLinear” kernels just like regular GEMM kernels; however they consume far fewer memory bandwidth resources, allowing larger batch sizes before hitting memory limits—exactly what enables the reported *11×* increase in permissible batch size for a 70 B parameter model on two A100 GPUs.

### 3️⃣ llama.cpp

`llama.cpp` is a lightweight C/C++ inference engine targeting CPUs as well as GPUs via OpenCL/Vulkan pathways. Since BitNet replaces only linear layers while keeping everything else identical (including RoPE treatment), one can drop compiled-in `BitLinear` routines compiled from SIMD-friendly integer addition code paths (e.g., using AVX2/AVX512 intrinsics). Because ternary weights can be packed tightly—each weight occupying less than two bits—the CPU cache footprint shrinks dramatically, enabling inference on devices that previously could not accommodate full FP16 models.

Overall, by adhering closely to the LLaMA component set and exposing a straightforward configuration flag for bit width, BitNet b1.58 becomes “plug‑and‑play” across all major open-source LLM stacks without requiring bespoke training pipelines or dramatic code rewrites.

## Limitations of Pure 1‑bit (Binary) Weight Schemes

Earlier attempts at extreme quantization reduced weights to strict binary values (\{-1,+1\}). While this yields an even smaller storage cost (**exactly 1 bit per weight**) it introduces two notable drawbacks:

| Issue | Explanation |
|-------|-------------|
| **Expressivity loss** | Binary weights cannot represent “absence” of contribution; every connection either adds or subtracts its input scaled by a constant factor (the global scaling factor used during quantization). This limits the ability to filter out irrelevant features during forward propagation. |
| **Zero–point handling** | To emulate sparsity one must rely on additional mechanisms (e.g., learned masks or pruning), which complicates both training and inference pipelines.|

The inclusion of an explicit zero value in BitNet b1.58 directly addresses these concerns:

* **Feature filtering:** Zero weights allow certain rows/columns of a projection matrix to be completely ignored for particular inputs, akin to learned sparsity but without extra parameters.
* **Improved modeling capacity:** Empirically the paper demonstrates that adding zero restores performance parity with full precision models already at \(3\,\text{B}\) parameters—a regime where pure binary variants still lag behind.
* **Minimal overhead:** Storing zeros alongside +/− signs incurs only an average increase from 1 bit to \(1.58\) bits per weight because many entries naturally become zero after scaling; thus overall memory savings remain substantial.

Consequently, while pure binary quantization remains theoretically attractive for ultra‑low‐power hardware prototypes, practical large‑scale LLM deployment benefits more from the modest increase to ternary representation offered by BitNet b1.58.

### Concluding Remarks

The transition from an FP16 Transformer to a BitLinear‐based architecture exemplifies how algorithmic redesign can unlock dramatic hardware efficiencies without sacrificing modeling performance. By rigorously quantizing every weight to ternary values using an *absmean* scaling approach, eliminating floating‑point multiplications from matrix multiplication entirely, and coupling these changes with existing high‑quality components such as RMSNorm, SwiGLU, and RoPE, BitNet b1.58 achieves parity with full‐precision baselines across perplexity and downstream tasks while delivering up to fourfold speedups and multi‐fold reductions in memory usage and energy consumption.

Crucially, because these modifications sit neatly within established open‑source frameworks—Hugging Face Transformers, vLLM, llama.cpp—researchers and engineers can adopt them without reinventing tooling pipelines. The slight increase from pure binary to ternary weights resolves expressive limitations inherent in strict 1‑bit schemes while preserving most of their storage advantage; this balance underpins what the authors term “the era of 1‑bit LLMs.”  

Future work will likely explore even tighter packing (e.g., sub‑byte activation compression), specialized hardware accelerators tailored for addition‐only kernels, and extensions such as Mixture‑of‑Experts or long‐context support where the memory savings become even more critical—all building upon the solid foundation laid out by BitLinear within the BitNet family.

**BitNet b1.58: Architecture and Training Details**

## Why Add a Zero Weight? Feature Filtering and Expressive Power  

The original 1‑bit BitNet constrains every trainable weight to the binary set \(\{-1,+1\}\). While this extreme quantization dramatically reduces the amount of information that must be stored and transferred, it also forces each linear mapping to be a pure sign‑flip or sign‑preserving operation. In practice, many useful transformations in a Transformer require the ability to *suppress* certain input dimensions altogether.  

Introducing a third value, \(0\), expands the expressive repertoire of a ternary weight matrix from a mere polarity mask to a **feature‑filtering mask**. Each row of a weight matrix now decides, for every input feature, one of three actions:

1. **Preserve and amplify** the feature (\(+1\)).  
2. **Preserve and invert** the feature (\(-1\)).  
3. **Ignore** the feature completely (\(0\)).  

The “ignore” action enables the network to zero out irrelevant dimensions without needing to rely on downstream non‑linearities or attention mechanisms. This yields two concrete benefits:

- **Higher Effective Rank:** By selectively turning off dimensions, a ternary matrix can approximate a low‑rank real‑valued matrix more faithfully than a strictly binary one, because sparsity (the presence of zeros) provides an additional degree of freedom.
- **Improved Gradient Flow:** During training, gradients that would otherwise be forced to adjust the magnitude of \(\pm1\) entries can now be “parked” on zero entries, reducing noisy updates and stabilizing optimization.

Empirically, the paper reports that once models reach roughly 3 B parameters, the inclusion of zero weights allows BitNet b1.58 to match full‑precision LLaMA baselines in perplexity and downstream task accuracy. The authors thus argue that the extra \(\log_2(3) \approx 1.58\) bits per weight represent a sweet spot where memory savings are retained while expressive power is restored.

## AbsMean Quantization Function and RoundClip Operator  

Training a ternary network requires repeatedly projecting floating‑point weight tensors onto the discrete set \(\{-1,0,+1\}\). The **AbsMean quantization** scheme employed by BitNet b1.58 proceeds in two stages: scaling by an average absolute magnitude and then rounding/clipping to the allowed integer values.

Given a full‑precision weight matrix \(W \in \mathbb{R}^{n\times m}\), we first compute a scalar scaling factor \(\gamma\) that captures the typical magnitude of its entries:

\[
\gamma = \frac{1}{nm}\sum_{i=1}^{n}\sum_{j=1}^{m} |W_{ij}|.
\]

Intuitively, \(\gamma\) is the *mean absolute value* of all weights; it normalizes the distribution so that entries are centered around zero with unit average absolute deviation. Adding a small constant \(\epsilon\) (e.g., \(10^{-8}\)) prevents division by zero.

Next we form a scaled matrix:

\[
\widehat{W} = \frac{W}{\gamma + \epsilon},
\]

which typically has most elements within the interval \([-1, 1]\). The final ternarization step applies the **RoundClip** operator:

\[
\widetilde{W}_{ij}= \operatorname{RoundClip}\!\bigl(\widehat{W}_{ij},\, -1,\, 1\bigr),
\]
where
\[
\operatorname{RoundClip}(x, a, b)=
\max\!\bigl(a,\; \min\!\bigl(b,\; \operatorname{round}(x)\bigr)\bigr).
\]

The `round` function maps any real input to its nearest integer; clipping then forces any result outside \([-1, 1]\) back onto the boundary. Consequently each entry of \(\widetilde{W}\) becomes exactly \(-1\), \(0\), or \(+1\).  

Because the scaling factor is recomputed **every forward pass** (or at least every optimizer step), gradients are back‑propagated through the quantizer using *straight‑through estimation*: during back‑propagation the quantizer is treated as identity, allowing gradient flow into the underlying full‑precision accumulator \(W\) while still enforcing discrete constraints after each update.

---

## Computation of Scaling Factor \(\gamma\) (Average Absolute Weight)

The scale \(\gamma\) carries two important practical roles:

1. **Dynamic Range Normalization:** As training progresses, weight magnitudes can drift upward or downward. By normalizing each weight by \(\gamma\), we keep most scaled values near the quantization thresholds (i.e., between \(-0.5\) and \(+0.5\)), minimizing bias toward either sign.
2. **Gradient Stabilization:** Since \(\gamma\) is a simple arithmetic mean over all absolute values, it changes smoothly across steps, providing a low‑variance signal for any optimizer that might otherwise suffer from abrupt jumps caused by hard thresholding.

Algorithmically, computing \(\gamma\) is embarrassingly parallel: each processing core computes a partial sum of absolute values over its slice of \(W\); after a reduction all partial sums are summed and divided by \(nm\). The cost is negligible compared to matrix multiplication because it is an \(O(nm)\) elementwise operation without any expensive arithmetic beyond absolute value and addition.

## Activation Quantization: Symmetric int8 Range \([-Q_b,Q_b]\)

While weights are ternary, activations retain higher precision to preserve model capacity during forward propagation. BitNet b1.58 adopts an **8‑bit symmetric integer representation**, mapping real activation values to integers in

\[
[-Q_b,\; Q_b],
\]
where \(Q_b = 2^{7} - 1 = 127.\)

Key design choices differentiate this scheme from many post‑training quantizers:

- **No Zero‑Point Offset:** Traditional asymmetric quantization includes an additive offset (“zero point”) so that an integer zero corresponds to some non‑zero real value. Here we deliberately avoid any offset; instead we simply scale activations symmetrically around zero. This removes an extra arithmetic operation during dequantization and aligns nicely with hardware that implements saturating adders for signed integers.
- **Per‑Token Scaling:** For each token (i.e., for each row in the activation matrix), we compute a scale factor such that its maximum absolute value maps exactly to \(Q_b\). This per‑token approach captures token‑specific dynamic ranges while keeping implementation simple: after scaling, each element is rounded to nearest integer and clamped within bounds.
- **Compatibility with BitLinear:** Since BitLinear expects integer inputs on both sides (weights already ternary), using signed int8 activations enables pure integer arithmetic for all `nn.Linear` replacements—only additions are required, because multiplication by \(-1,0,+1\) reduces to sign inversion or pass‑through.

Empirically, this symmetric int8 quantization produces *negligible* degradation compared with full‑precision activations when combined with the ternary weight scheme; therefore BitNet b1.58 can afford this aggressive reduction without sacrificing downstream performance.

## Adopted LLaMA Components: RMSNorm, SwiGLU, Rotary Embeddings, Bias Removal  

To ensure broad compatibility with existing open‑source tooling (HuggingFace Transformers, vLLM, llama.cpp), BitNet b1.58 mirrors the architectural choices of LLaMA while substituting only those components directly impacted by quantization.

### RMSNorm  

Layer normalization stabilizes training but traditionally requires computing both mean and variance across hidden dimensions—a costly operation for integer arithmetic. **Root Mean Square Normalization (RMSNorm)** simplifies this by normalizing solely with respect to root‑mean‑square:

\[
y = \frac{x}{\sqrt{\frac{1}{d}\sum_{k=1}^{d} x_k^2}} \odot g,
\]

where \(g\) is a learned gain vector and \(d\) denotes hidden size. RMSNorm eliminates subtraction of the mean term, reducing computational overhead and making it easier to implement in fixed‑point hardware while preserving most of LayerNorm’s benefits.

### SwiGLU  

The feed‑forward sublayer in Transformers traditionally uses Gelu activation followed by a linear projection. BitNet b1.58 replaces this with **SwiGLU**, which combines Swish (a smooth sigmoid–linear product) with gated linear units:

```
h = x · W₁
g = x · W₂
output = Swish(h) ⊙ g
```

Because Swish can be approximated efficiently in integer arithmetic (e.g., via lookup tables or piecewise linear functions), SwiGLU remains amenable to efficient implementation while providing superior expressivity compared with Gelu.

### Rotary Positional Embeddings (RoPE)  

Absolute positional embeddings add overhead proportional to sequence length. RoPE encodes positions via complex rotations applied directly on query/key vectors; mathematically:

\[
q' = q \odot e^{i\, \theta_{pos}},~~k' = k \odot e^{i\, \theta_{pos}},
\]

where multiplication by complex exponentials corresponds to rotating subspaces—a operation implementable as elementwise sin/cos lookups on integers after appropriate scaling. RoPE works seamlessly with quantized activations because it does not require extra learned parameters per position.

### Bias Removal  

All linear transformations in BitNet b1.58 omit additive bias terms (`bias=False`). Biases would need additional storage (one float per output dimension) and their influence on quantized training dynamics is marginal when combined with powerful normalization layers (RMSNorm). Removing biases reduces memory usage further—a crucial consideration when every parameter contributes directly to overall model size.

Collectively these components preserve LLaMA’s strong empirical performance while aligning with BitNet’s low‑bit hardware goals.

## Pseudocode for Forward Pass of a BitLinear Layer  

Below is an illustrative Python–like pseudocode that captures how `BitLinear` operates under the 1.58‑bit regime. The code assumes tensors are stored as:

- `W_int`: ternary weight matrix stored as `int8` values in `{ -1, 0, +1 }`.
- `x_int`: activation matrix already quantized to signed `int8`.
- `scale_w`: scalar scaling factor computed as described above (kept in floating point for convenience).
- `scale_a`: per‑token activation scaling factor (float).

```python
def bitlinear_forward(x_int: Int8Tensor,
                      W_int: Int8Tensor,
                      scale_w: float,
                      scale_a: FloatTensor,
                      out_scale: float):
    """
    Compute y = x * W using only integer additions.
    Arguments:
        x_int   – shape [batch, seq_len, dim_in]   (int8)
        W_int   – shape [dim_in, dim_out]          (int8 ∈ {−1,0,+1})
        scale_w – scalar ∈ ℝ⁺ (average |W| from Eq.(3))
        scale_a – shape [batch, seq_len]          (float32)
        out_scale – desired output scale (float)
    Returns:
        y_int   – shape [batch, seq_len, dim_out] (int32 before rescaling)
    """

    # 1️⃣ Scale activations back to real domain:
    #    For each token t: x_real[t] = x_int[t] * scale_a[t]
    #    In practice we keep them as int32 after multiplication.
    x_scaled = x_int.astype(int32) * scale_a[:, None]   # broadcasting

    # 2️⃣ Perform integer matrix multiplication.
    #    Because W_int ∈ {−1,0,+1}, multiplication reduces
    #    to selective addition/subtraction.
    #    The result lives in int32 precision.
    y_int32 = matmul_int_add(x_scaled, W_int)

    # 3️⃣ Apply combined scaling:
    #    Real output y_real = y_int32 * scale_w * out_scale
    #    For subsequent layers we keep y as int8:
    y_float = y_int32.astype(float32) * scale_w * out_scale

    # 4️⃣ Requantize to int8 symmetric range [-Qb,Qb]
    max_abs = max(abs(y_float.max()), abs(y_float.min()))
    if max_abs == 0:
        return zeros_like(y_float).astype(int8)
    requant_factor = Qb / max_abs
    y_quant = round(y_float * requant_factor).clip(-Qb, Qb).astype(int8)

    return y_quant
```

Key points illustrated by this skeleton:

- **Multiplication Elimination:** Step 2 leverages that multiplying by `-1` equals subtraction and multiplying by `+1` equals addition; CPUs/GPUs can fuse this into a single sparse add kernel.
- **Two‑Stage Scaling:** The first scaling (`scale_a`) restores activations to their approximate real magnitudes; after matrix addition we apply `scale_w` together with an output rescaling factor (`out_scale`) that maps back into the int8 range required for subsequent layers.
- **Straight‑Through Gradient Flow:** During training one would keep an FP32 copy of `W` (`W_fp`) updated by SGD/Adam; after each optimizer step `W_fp` would be passed through the AbsMean quantizer producing fresh `W_int`. The pseudocode above reflects only inference; training adds gradient hooks that treat rounding as identity.

This forward path demonstrates how BitNet b1.58 achieves *“almost no multiplication”* for its dominant linear operations—an essential ingredient behind its dramatic reductions in latency and energy consumption.
