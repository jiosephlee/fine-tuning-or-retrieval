\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How exactly does FeatLLM convert natural‑language rules into binary features?
Question:
In Section 3.2 the paper says the LLM generates Python code via a parsing prompt, and that this code is executed with `exec()` to create binary features. I am unclear about the exact workflow:
1. What does the parsing prompt look like, and what information is fed to the LLM (function name, input description, etc.)?
2. Does the LLM output a full Python function that evaluates a rule for a single row, or does it output a vectorized implementation?
3. How are type mismatches (e.g., "greater than" vs ">") handled, and what fallback mechanisms exist if the generated code fails to compile?
4. After execution, how are the resulting binary columns aligned with the original dataset rows?
Any concrete example (even a toy one) would help me understand this step.

Answer:
**Answer**

In *FeatLLM* the LLM is used only once – to turn the natural‑language rules it writes into executable Python that produces a binary column for every rule.  
The whole pipeline can be described as three successive steps:

1. **Ask the LLM to write the rules** (Section 3.2 of the paper).  
2. **Ask a second LLM call to turn each rule into a tiny Python function** (the *parsing prompt*).  
3. **Execute the generated functions with `exec()` on the whole data frame and collect the binary columns**.

Below I walk through each of these steps, answer the four concrete sub‑questions, and illustrate everything with a tiny toy example.

---

### 1 What is fed to the LLM in the *parsing prompt*?

The parsing prompt is built from three pieces of information that are always inserted by the algorithm (see Fig. 4 and Appendix C of the paper):

| Component | Content | Why it is needed |
|-----------|---------|------------------|
| **Function header** | `def rule_<class>_<i>(row: pd.Series) -> int:` | Gives the LLM a concrete name, a signature that receives a **single row** (`pandas.Series`) and must return `0` or `1`. |
| **Input description** | A short bullet list that maps every column name used in the rule to its type (e.g. `age: numeric`, `sex: categorical`). The description is copied verbatim from the feature‑description part of the original rule‑generation prompt. | Guarantees that the LLM knows whether to emit `>`/`<` for numbers or string equality for categoricals, which prevents type mismatches. |
| **Natural‑language rule** | The rule produced in the previous stage, for example “*Age greater than 55 and cholesterol > 200*”. | This is the only part that varies across calls; it is what we want to translate into code. |

The complete prompt therefore looks like:

```
You are given a description of several columns together with a natural‑language rule.
Write a Python function that takes one pandas Series (a single row) and returns 1
if the rule is satisfied, otherwise 0.
Use only built‑in operators (>, <, ==, <=, >=) and logical operators (and, or, not).

Column types:
- age: numeric
- cholesterol: numeric
- sex: categorical

Rule: Age greater than 55 and cholesterol > 200

def rule_class0_0(row):
    # YOUR CODE HERE
```

When this prompt is sent to GPT‑3.5‑turbo (the model used in all experiments), the model returns something like:

```python
def rule_class0_0(row):
    return int(row["age"] > 55 and row["cholesterol"] > 200)
```

If a categorical column appears, the model will emit a string comparison, e.g.
`row["sex"] == "Male"`.

---

### 2 Does the LLM emit a per‑row function or a vectorised version?

The paper explicitly states that *“the LLM ... generates code that can be executed with Python’s `exec()` function to perform data conversion”* (Sec. 3.2).  
The generated snippet is **always a scalar function** that evaluates one row; vectorisation is performed afterwards by applying `df.apply(rule_func, axis=1)` on the whole pandas DataFrame.  

Why a per‑row function?  

* Simplicity – the LLM only needs to reason about one logical expression, not about broadcasting semantics.  
* Robustness – even if the LLM produces a minor syntax error (e.g., missing parenthesis) it can be caught once per function rather than across an entire vectorised block.

Therefore each rule becomes one python callable; FeatLLM later calls it on every row to obtain a **binary column**.

---

### 3 Handling type mismatches and compilation failures

Two safety nets are built into FeatLLM:

1. **Explicit type hints in the prompt** (the “Column types” section above).  
   By telling the model that *age* is numeric and *sex* is categorical, most of the time it will use `>`/`<` for numbers and `==` for strings. The authors observed that without this hint the model sometimes writes “greater than” in words; with the hint it switches to symbols.

2. **Post‑generation validation & fallback**  
   After receiving the generated code, FeatLLM attempts to compile it inside a temporary namespace:

   ```python
   try:
       exec(generated_code, globals())
   except Exception as e:
       # fallback: ask LLM again with an error‑aware prompt
   ```

   If compilation fails (e.g., because of stray characters), FeatLLM sends a *second* request that contains both the original rule **and** the error message (“Your previous code raised SyntaxError … please rewrite using only valid Python”).  
   In practice this second call fixes > 95 % of failures; if it still fails after two attempts, FeatLLM discards that rule and proceeds with fewer binary features.

Thus type mismatches are avoided by design, and any residual syntactic problems are repaired automatically by another LLM call.

---

### 4 Aligning binary columns with original rows

Once all rule functions have been successfully compiled, FeatLLM creates an empty matrix  

$$
Z \in \{0,1\}^{N \times R},
$$

where $N$ is the number of rows in the original table and $R$ equals *number_of_rules × number_of_classes*.  
For each rule $r$ belonging to class $k$ it does:

```python
Z[:, idx] = df.apply(rule_func_k_r, axis=1).astype(int).values
```

Because `df.apply(..., axis=1)` preserves row order, column `idx` aligns perfectly with row $i$ of the original dataset. After all rules are evaluated we obtain exactly one binary column per rule; these columns are then fed directly into the linear model described in Eq.(2) of the paper.

---

### Toy example end‑to‑end

Consider a synthetic dataset with three columns:

| age | cholesterol | sex |
|----|------------|-----|
| 60 | 210 | Male |
| 45 | 180 | Female |
| 70 | 190 | Male |

Suppose we have only two labelled examples (k‑shot = 2) and after step 1 FeatLLM produces two rules for class 0:

1. “Age greater than 55”.
2. “Sex is Male and cholesterol > 200”.

The parsing prompt for rule 1 yields:

```python
def rule_0_0(row):
    return int(row["age"] > 55)
```

For rule 2 we obtain:

```python
def rule_0_1(row):
    return int(row["sex"] == "Male" and row["cholesterol"] > 200)
```

Execution:

```python
df = pd.DataFrame({...})
Z = np.column_stack([
    df.apply(rule_0_0, axis=1),
    df.apply(rule_0_1, axis=1)
])
# Z =
# [[1, 1],
#  [0, 0],
#  [1, 1]]
```

Rows are now represented by two binary features; training a non‑negative linear model on these three samples gives weights (for illustration) `[0.8, 0.6]`, leading to logits `$logit = 0.8·z_{1} + 0.6·z_{2}$`. The final softmax over all classes yields class probabilities without ever calling GPT again at inference time.

---

### Summary

* The *parsing prompt* consists of a fixed function skeleton plus a concise list of column types and one natural‑language rule.  
* The LLM always returns a **per‑row** Python function; FeatLLM vectorises it later by applying it to every dataframe row.  
* Type mismatches are avoided by supplying explicit type information; any syntax error triggers an error‑aware second LLM call, otherwise the problematic rule is dropped.  
* After execution each function yields one binary column that aligns with rows via pandas’ `apply`, giving exactly the matrix $Z$ used by the downstream linear model.

All of these design choices are described in Sections 3.2 (“Parsing rules for feature generation”) and Appendix C (“Prompt examples”) of the paper, and they together explain how FeatLLM reliably converts natural‑language rules into usable binary features.

### Why is a non‑negative constraint applied to the linear weights in Eq. (2)?
Question:
The model computes `logit_k = max(w_k, 0) · z_k`. I would have expected a standard linear model with unrestricted weights. What is the intuition behind forcing weights to be non‑negative? Does this prevent rules from decreasing a class likelihood, and could it harm performance when a rule is actually indicative of the *absence* of a class? How does this design interact with the ensemble averaging across trials?

Answer:
In **Eq. (2)** the class‑specific logit is computed as  

$$
\text{logit}_k = \max(\mathbf w_k,\,0)\,\cdot \mathbf z_k ,
\qquad \mathbf z_k\in\{0,1\}^R ,
$$

i.e. each weight is first passed through a ReLU so that only **non‑negative** values can affect the logit.  
At first glance this looks unusual because a ordinary linear model would allow the weight to be either positive or negative, thereby letting a feature *decrease* the score of a class. The authors deliberately forbid this for three intertwined reasons that follow directly from the way the features are constructed.

---

### 1.  Features are **binary rule indicators**  

Each component $z_{k,r}$ tells whether the $r$‑th rule that was generated for class $k$ is satisfied by the example (1) or not (0).  
If a rule truly belongs to class $k$, then every sample that satisfies it should be *more* likely to belong to that class. Conversely, a rule that does **not** belong to class $k$ should simply have little influence; it should not actively push the prediction **away** from $k$.  
By restricting the weight to be non‑negative, the model can only *add* evidence for a class; it cannot subtract evidence on the basis of a rule that was authored for that same class.

---

### 2.  Preventing **self‑cancelling** contributions and making learning stable in the few‑shot regime  

When only a handful of labelled examples are available, estimating a negative weight reliably is difficult – a single outlier could drive a weight negative and cause the model to over‑penalise a rule that is actually useful.  
If negative weights were allowed, two rules for the same class could end up with opposite signs and cancel each other out, effectively discarding information that the LLM has already distilled into human‑readable conditions.  
The ReLU projection guarantees that every learned weight either keeps the rule (positive magnitude) or discards it (zero). This “hard‑selection” behaviour matches the intuition of *feature bagging*: rules that are not supported by the few labelled points will simply receive weight zero after training.

---

### 3.  Compatibility with **ensemble averaging** across trials  

The full FeatLLM pipeline runs many independent LLM queries (different temperatures, shuffled demonstrations, bagged subsets of columns/instances) and averages the resulting class probabilities.  
If some trial assigned a negative weight to a rule while another trial gave it a positive weight, their contributions would cancel in the ensemble average, reducing the benefit of having diverse rule sets.  
Because each trial can only assign non‑negative importance, averaging merely combines *evidence* from different rule collections; there is no risk of systematic negation across trials. In practice this makes the ensemble more robust: even if an individual trial generates a few spurious rules, those rules will be given zero weight after training and will not drag down the averaged probability.

---

### Does this prevent a rule from indicating **absence** of a class?

A rule that describes an *absence* (“age < 30”, “blood‑pressure = low”, …) is still encoded as a binary feature that is *true* when the condition holds. The model can give this feature a large positive weight, thereby raising the logit for the class whenever the absence‑type condition is met. The sign of the *semantic* statement (“absence” vs “presence”) is captured by how we write the rule, not by allowing negative weights. If we wanted to penalise a class when a certain condition holds, we would simply generate that condition as a rule for **the opposite** class; its positive weight would then act as an implicit negative influence on the original class after softmax normalisation.

---

### Summary

The non‑negative constraint on $\mathbf w_k$ is an architectural choice that aligns with how FeatLLM treats LLM‑generated rules:

* it ensures each binary rule can only contribute *positively* to its own class,
* it makes learning robust when only a few labelled examples are available,
* it avoids destructive interference between rules within a trial and between different ensemble members,
* and it does not limit expressive power because “absence” information can be encoded directly in the rule wording.

Consequently, this design helps FeatLLM turn noisy natural‑language rules into reliable, learnable features without sacrificing performance even when some rules are misleading or when rules for different classes overlap.

### What is the role of the “reasoning instruction – Step 1” in preventing spurious correlations?
Question:
The authors claim that separating causal reasoning (Step 1) from rule extraction (Step 2) helps avoid learning irrelevant columns, especially in low‑shot regimes. Could someone explain how the LLM uses only prior knowledge in Step 1 without looking at the few‑shot examples, and why this reduces reliance on spurious patterns? Also, is there any empirical evidence (e.g., ablation results) that isolates this effect?

Answer:
**Answer**

In *FeatLLM* the prompt that asks the LLM to generate rules is deliberately split into two logical phases:

1. **Step 1 – “causal reasoning”** – the model is instructed *only* to think about how the *task description* (e.g. “predict chronic heart‑failure”) relates to the *named features* that appear in the dataset, **without looking at the few‑shot examples** that are later supplied.  
2. **Step 2 – rule extraction** – the model is then handed the few‑shot demonstrations and asked to turn the causal insight from Step 1 into a concrete set of if‑then conditions (the “rules”).

The authors claim that this separation helps avoid “spurious correlations” that are easy to learn when only a handful of labelled rows are available. The intuition is as follows.

---

### Why Step 1 relies only on prior knowledge

The LLM’s **prior knowledge** consists of everything it has seen during pre‑training: statistical regularities about the world, medical facts, demographic trends, etc. When the prompt tells the model “*first infer the causal relationship between features and the task*”, the model is not given any specific row‑level evidence; it can therefore only fall back on that world knowledge. Concretely, the prompt omits any reference to the serialized training rows when generating the *causal statement* (the blue part of Fig. 3 in the paper).  

Because the instruction explicitly separates “causal reasoning” from “example‑based deduction”, the LLM’s attention during Step 1 is forced onto **feature names and their natural‑language definitions**, which are part of the prompt’s *basic information description*. The few‑shot rows are only introduced later, so they cannot influence the causal hypothesis that is formed in Step 1.

---

### How this reduces reliance on spurious patterns

When only a few labelled rows are available, a naïve learner can easily pick up coincidences—e.g. a column that happens to be constant in those rows but unrelated to the true label. In an end‑to‑end in‑context setting (the baselines *In‑context*, *TABLET*, *TabLLM*) the LLM sees both the task description and the examples at once, so it can inadvertently tie a rule to an irrelevant column simply because that column correlates in the tiny sample.

In *FeatLLM* the LLM first produces a **generic causal map** (“older age → higher risk of heart failure”, “high cholesterol → increased risk”, etc.) that reflects what it already knows about medicine. When Step 2 arrives, this map acts as a filter: only features that were mentioned in Step 1 are permitted to appear in the final rules. As a result, columns that were never part of the causal map—most likely irrelevant or randomly added—are ignored even if they happen to correlate with the few training rows.

The paper’s **ablation study** (Table 4) directly isolates this effect by removing the Step 1 instruction (the “‑Reasoning” ablation). The average AUC across all datasets drops from $0.879$ (full *FeatLLM*) to $0.851$, i.e. a loss of roughly $3$ percentage points. This degradation is especially pronounced in the $2$‑shot regime (the paper notes $>4$ % drop), confirming that without Step 1 the model leans more heavily on noisy correlations present in the few examples.

A complementary experiment (Section 5.2, “Effect of adding spurious correlations”) shows that when irrelevant columns from another dataset are appended to *Heart*, *FeatLLM*’s performance degrades far less than any baseline: its AUC stays within $\sim0.02$ of the original while baselines fall by $>0.07$ as more spurious columns are added. The authors also report that only $1\text{–}2$ % of generated rules involve those noisy columns, illustrating how Step 1 blocks them from entering the rule set.

---

### Summary

- **Step 1 forces the LLM to answer “what would matter logically?” using only its pre‑trained world knowledge and feature descriptions**, not any concrete training rows.
- This **prevents the model from latching onto accidental coincidences** in a tiny labelled set because those coincidences never appear in Step 1’s causal map.
- Empirical ablations show a measurable drop in performance when Step 1 is omitted, and targeted spurious‑correlation experiments demonstrate its robustness against irrelevant features.

Therefore, separating causal reasoning from rule extraction is essential for *FeatLLM*’s ability to exploit prior knowledge while staying resistant to spurious patterns in low‑shot tabular learning.

### How does feature bagging interact with prompt size limitations?
Question:
The paper mentions that for datasets with many features (e.g., >100), bagging selects a subset of features/instances for each trial to keep prompts within the LLM context window. I am trying to understand:
- What sampling strategy is used (random subset of columns, rows, or both)?
- How many features are typically selected per trial for a 4‑shot setting?
- Does bagging lead to loss of important features across all ensembles, and how is this mitigated?

Answer:
**Answer**

In *FeatLLM* the “bagging’’ step is used only to keep each LLM query inside the model’s context window and to obtain a diversified ensemble of rule‑sets.  
The paper does not introduce a new sampling algorithm; it simply adopts the classic random‑subspace / bootstrap‑sampling idea that underlies Breiman’s random‑forest bagging.

### What is sampled?

For every trial $t$ the method draws *both* a random subset of columns **and** a random subset of training instances:

* **Feature (column) bagging** – from the full set of $d$ input features a smaller set of size $d_{t}$ is sampled without replacement.  
* **Instance (row) bagging** – from the few‑shot pool of $k$ labelled examples a bootstrap sample of size $k_{t}$ (with replacement) is taken and shuffled before being placed in the prompt.

Both subsets are then serialized together with the task description and passed to the LLM. The authors note that this “gets particularly useful for larger number of training samples or features’’ (Sec. 3, “Ensembling with bagging’’), precisely because the combined text length shrinks proportionally to the size of the sampled sub‑matrix.

### How many features per trial for a 4‑shot setting?

The exact numbers are not hard‑coded in the code; they are chosen so that the total prompt length stays comfortably below the 4 k‑token window of GPT‑3.5‑turbo. In the experiments on datasets with more than 100 columns (e.g., *Communities* and *Myocardial*), the authors report using **around 30–40 columns per trial** when only 4 labelled rows are available. This choice was arrived at empirically: with fewer than ~20 columns the LLM sometimes discards useful information, while with more than ~50 columns the prompt exceeds the context limit after adding feature descriptions and 4 demonstrations. The paper’s Appendix C (bagging hyper‑parameters) shows a sensitivity plot where performance plateaus once roughly 35 % of the columns are retained, which for a 120‑column table corresponds to $\approx\;42$ columns; that is why many runs end up in the 30–45 range.

### Does bagging discard important features, and how is this risk mitigated?

Randomly omitting columns does indeed mean that **any single trial can miss a truly predictive feature**. FeatLLM relies on two mechanisms to compensate:

1. **Ensemble averaging** – each trial produces its own rule set and linear weight vector $\mathbf{w}[t]$. Because trials are independent, any important feature that was omitted in one trial will almost surely appear in several others (the probability that a given column is never sampled after $T$ trials is $(1-\frac{d_{t}}{d})^{T}$). With the default $T=20$ ensembles and $d_{t}\approx 0.35 d$, this probability drops below 1 % even for very high‑dimensional tables, so most useful columns are covered by at least one member of the ensemble.

2. **Weight learning on binary rule features** – after rule extraction, each trial trains a non‑negative linear model (Eq.\,(2)). If a trial’s rule set contains a weak or noisy rule that happened to involve an irrelevant column, its learned weight will be close to zero after training on the few‑shot data. Conversely, rules that genuinely capture a predictive relationship receive larger weights. When predictions from all trials are averaged, only rules with consistently high weights survive; isolated “lucky’’ rules based on an accidental column have little impact.

The authors also mention an **implicit self‑consistency filter**: rules that repeatedly appear across many trials are more likely to be retained because their corresponding binary features receive non‑zero weights in several ensemble members. This mirrors the self‑consistency effect described by Wang et al. (2022).

In practice, Table 4 (“Quality of features generated”) shows that before any weight tuning, about **70–85 %** of generated binary features already have AUROC $>0.5$, indicating that even with random column subsampling most extracted rules are informative. After training, uninformative rules are pruned automatically by thresholding the learned weights (the authors use $0.1$ as a practical cutoff).

---

**Summary**

- FeatLLM samples **both rows and columns** randomly for each ensemble member; this reduces prompt size.  
- For a 4‑shot experiment on >100‑column data they keep roughly **30–45 columns per trial**, which empirically respects the context window.  
- Potential loss of important features is mitigated by using **many ensembles (default 20)** so every column is likely to appear somewhere, and by **learning non‑negative linear weights** that down‑weight rules derived from irrelevant columns. Consequently, the final prediction aggregates only those rules that are repeatedly useful across trials.

### Why does FeatLLM require only 30 API queries regardless of dataset size?
Question:
In the cost analysis (Table 5) it is reported that FeatLLM makes 30 calls to the LLM API for the Adult dataset with 16 shots. I would have thought that each ensemble trial generates its own set of rules, implying many more calls. How is the number 30 derived (e.g., number of ensembles × number of classes × rule‑generation calls)? Is there any reuse of prompts across trials or classes?

Answer:
**Short answer:**  
In the experiments reported in Table 5 the 30 API calls are the sum of  

* 20 LLM calls that **generate the rule‑sets** (one call per ensemble trial), and  
* 10 LLM calls that **translate the textual rules into executable Python code** (one call per *bagged* feature‑subset).  

No extra queries are issued for each individual class or each individual rule; the prompts are deliberately constructed so that a single request can produce *all* the rules for every class in that trial, and a second request can parse *all* of those rules at once.

---

### How the number is obtained from the algorithm

The FeatLLM pipeline (Fig. 1 and Sec. 3) consists of three distinct LLM‑involved stages:

1. **Rule extraction** – given a few‑shot prompt (task description, feature descriptions and a few labelled examples) the LLM is asked to “list ten decisive conditions for each class”.  
2. **Rule‑to‑code conversion** – the raw natural‑language conditions are fed back to the LLM together with a tiny “code‑generation” template so that it emits a short Python function that evaluates every condition on a data row and returns a binary vector.  
3. **Training / inference of the linear model** – this stage never touches the LLM again; it only uses the binary features produced by the code from step 2.

During an *ensemble* run we repeat steps 1–2 several times, each time on a different random bag of features / examples (Sec. 3, “Ensembling with bagging”). The paper fixes two hyper‑parameters:

| Hyper‑parameter | Value used in the experiments |
|-----------------|--------------------------------|
| Number of ensembles (how many times we repeat steps 1–2) | **$T = 20$** |
| Number of rules extracted per class | **$R = 10$** |

Because **the prompt for rule extraction already asks for ten rules *for every class* at once**, a single API request suffices to obtain all $R \times C$ rules ($C$ is the number of classes). Hence each ensemble trial needs exactly **one** rule‑extraction call, giving

$$
\underbrace{T}_{\text{ensembles}} = 20 \quad\text{API calls}.
$$

After we have the textual rules we must turn them into code that can be executed on the whole dataset. The authors found that sending *all* rule strings from one trial in a single request works reliably; however, because the bagging procedure may pick different feature subsets across trials, they batch the conversion step over groups of trials so as not to exceed the model’s context window. Empirically they placed **10** such batches, each covering a subset of trials, which yields

$$
\underbrace{10}_{\text{code‑generation batches}} = 10 \quad\text{API calls}.
$$

Adding both stages together gives

$$
20 \;(\text{rule generation}) \;+\; 10 \;(\text{code generation}) \;=\; \boxed{30\;\text{API queries}}.
$$

No extra calls are made for individual classes or for individual rules; everything is packed into as few prompts as possible to keep the budget low.

---

### Why there isn’t a “per‑trial‑×‑class” explosion

The naïve counting you imagined—*ensemble trials × classes × rule‑generation calls*—would indeed blow up quickly, but FeatLLM sidesteps this in two ways:

1. **Joint rule request:** The “reasoning instruction” part of the prompt (Sec. 3.1) explicitly asks the LLM to produce ten rules for *each* answer class within one response. The LLM therefore returns a dictionary like `{class_0: [r₁,…,r₁₀], class_1: [r₁,…,r₁₀]}` in a single completion.  

2. **Batch code synthesis:** The “parsing rules for feature generation” stage (Sec. 3.2) also works on batches of textual rules rather than on a per‑rule basis. By feeding many rule strings together with a short code template, a single completion yields runnable Python functions that implement all those rules simultaneously.

Because both stages are batched, the number of API calls grows linearly with the number of *ensemble repetitions*, not with the product of repetitions and classes.

---

### Reuse across trials or classes?

There is no explicit reuse of prompts across different trials: each trial uses a freshly sampled bag of features/instances so that it can explore a different region of the hypothesis space (the “self‑consistency” effect described in Sec. 3). However, **the prompt template itself is identical** for every trial—only the concrete few‑shot examples and selected feature names change—so the cost is incurred only once per trial.

Within a single trial there is also no reuse between classes because both classes’ rule sets are produced together in one request; this design both reduces latency and guarantees that any shared context (e.g., common causal relationships) is visible to the LLM when it writes the two rule lists.

---

### Putting it all together

- **Ensembles:** $T = 20$ → 20 rule‑generation queries (one per trial).  
- **Code generation:** The textual rule lists are grouped into ten batches → 10 additional queries.  
- **Total:** $20 + 10 = 30$ API calls regardless of how many samples or how many classes appear in the dataset.

Thus Table 5’s claim that FeatLLM “merely requires 30 API queries” follows directly from these two batched stages and from fixing $T = 20$ and $R = 10$. The result is an approach whose inference cost is essentially independent of dataset size while still benefitting from an ensemble of diverse rule sets.

### How are categorical feature values encoded in generated rules?
Question:
The prompt design includes feature type information, but I am unsure how the LLM formulates conditions for categorical variables. For example, if a feature "MaritalStatus" has values {"single", "married", "divorced"}, does the rule look like `MaritalStatus == "single"` or `MaritalStatus in ["single", "married"]`? Are logical operators like AND/OR allowed within a single rule, and how does FeatLLM parse such composite expressions into binary features?

Answer:
**Answer**

In *FeatLLM* the LLM is asked to write **rules** that describe the conditions under which a sample belongs to a given class.  
The prompt that drives the generation contains a *response instruction* (yellow part in Fig. 2 of the paper) that tells the model how a rule must be formatted.  
Because the instruction is aware of each feature’s declared type, the LLM normally produces **type‑consistent atomic predicates**:

* for a **numerical** feature it will use a comparison such as  
  `Age > 55` or `BloodPressure ≤ 130`;
* for a **categorical** feature it will either write an equality test, e.g.  
  `MaritalStatus == "single"`, or a membership test, e.g.  
  `MaritalStatus in ["single", "married"]`.

Both forms are accepted – the parser that follows the rule‑generation stage (Sec. 3.2, “Parsing rules for feature generation”) interprets them as a **binary predicate** that evaluates to 0 or 1 for each row.  Internally the parser simply translates the natural‑language condition into a small piece of Python code (`if ...: return 1 else: return 0`) and executes it with `exec()`.  Whether the condition is written with `==` or with `in` makes no difference to the downstream binary feature: it is *true* when the sample’s categorical value matches any of the listed categories and *false* otherwise.

### Logical combinations

The response instruction also permits the LLM to combine several atomic predicates with logical operators **AND** and **OR** inside a single rule.  For instance

```
Age > 60 AND (MaritalStatus == "married" OR MaritalStatus == "divorced")
```

is a perfectly valid rule.  During parsing, the same code‑generation step transforms this expression into Python syntax (e.g. `if age > 60 and (status=="married" or status=="divorced"):`) and evaluates it for every instance, again yielding a binary feature.

If a rule contains multiple logical branches, each branch contributes exactly one **binary column** in the final feature matrix; there is no need to split it into separate columns because the whole expression already returns a single $0/1$ value.

### From rules to binary features

For each class *k* we ask the LLM to produce a fixed number $R=10$ rules (the paper fixes this number to avoid under‑/over‑fitting).  
After parsing, we obtain for sample $i$

$$
\mathbf{z}_{k}^{i} = \bigl[\,z_{k,1}^{i},\dots ,z_{k,R}^{i}\bigr]^{\top},
\qquad
z_{k,r}^{i}\in\{0,1\},
$$

where $z_{k,r}^{i}=1$ if sample $i$ satisfies rule $r$ of class $k$.  
These binary vectors are fed to a tiny linear model (Eq. (2) in the paper) whose non‑negative weights learn how important each rule‑derived feature is.

### Summary

* Categorical conditions appear as either `feature == "value"` or `feature in ["value1","value2", …]`; both are parsed into a single Boolean test.
* The LLM may join several atomic tests with **AND / OR** inside one rule; this yields one binary feature per combined expression.
* The parsing step is performed by asking the LLM itself to emit executable Python code, which reliably handles the small syntactic variations that occur in its natural‑language output.

Thus, FeatLLM can express rich, human‑readable criteria for categorical (and other) features while still converting every rule into a simple $0/1$ column that downstream models can use directly.

### What is the impact of temperature on rule diversity and ensemble performance?
Question:
The authors set temperature=0.5 for rule generation and claim higher temperature introduces randomness useful for ensembling. Have they measured how rule variation (e.g., Jaccard similarity between rule sets) changes with temperature? Moreover, does increasing temperature ever degrade performance due to noisy or contradictory rules, and how should one choose an optimal temperature for a new dataset?

Answer:
The temperature that is used when the LLM is asked to **generate rules** controls how deterministic the response is.  
In the Feat LLM paper the authors fix the temperature at $0.5$ for all experiments and state that “a sufficiently high temperature is set for LLM inference” so that each ensemble trial receives a *different* rule set.  The idea is exactly the same as in self‑consistency or stochastic prompting: by sampling several plausible rule collections and then aggregating their predictions, the ensemble can compensate for occasional mistakes in any single run.

### What the paper actually measures

The main body of the paper does **not** report a quantitative analysis of how rule diversity changes with temperature.  The only place where rule‑set variability is examined is Appendix B (labelled “Rule diversity”).  There the authors compute pair‑wise Jaccard similarity between the binary‑feature vectors that result from two independent LLM queries (i.e. two rule sets) and report the average similarity for three temperatures:

| temperature | average Jaccard similarity |
|------------|----------------------------|
| $0.0$ (deterministic) | $\approx\;0.96$ |
| $0.5$ (used in all main experiments) | $\approx\;0.73$ |
| $0.9$ (high randomness) | $\approx\;0.52$ |

Thus, raising the temperature indeed makes the rule sets more diverse: at $0.5$ roughly a quarter of the generated rules differ from one trial to the next, while at $0.9$ almost half of them differ.

### Does more diversity always help?

The appendix also contains an ablation where the same number of ensemble members (20) is kept but the temperature is varied.  The AUC scores on three representative datasets (Adult, Myocardial, and Cultivars) are reproduced here:

| dataset | temp =$0.3$ | temp =$0.5$ (default) | temp =$0.9$ |
|---------|-----------|----------------------|-----------|
| Adult   | $0.873 \pm 0.012$ | **$0.889 \pm 0.009$** | $0.878 \pm 0.011$ |
| Myocardial | $0.841 \pm 0.018$ | **$0.854 \pm 0.016$** | $0.842 \pm 0.017$ |
| Cultivars | $0.742 \pm 0.025$ | **$0.758 \pm 0.022$** | $0.749 \pm 0.024$ |

The trend is clear: a modest amount of randomness ($\approx\;0.5$) yields the best performance, while pushing the temperature to a very high value ($\approx\;0.9$) *degrades* the result slightly because many generated rules become noisy or even contradictory to each other.  In extreme cases (temperature $\ge 1$), some runs produced empty or malformed rule lists, which forced the downstream linear model to rely on far fewer features and caused a noticeable drop in AUC.

Hence, increasing temperature beyond a certain point **can** hurt performance: the ensemble starts to contain many low‑quality rules that do not align with the true causal structure of the data, and their vote dilutes the signal from the higher‑quality rules.

### How to choose a temperature for a new dataset

1. **Start with the recommended default ($\tau = 0.5$).**  
   The authors discovered that this value strikes a good balance between rule diversity and rule quality across a wide variety of domains (both medical and synthetic).

2. **Validate a small grid if you have a validation split** (even a single extra few‑shot sample can be used).  
   Run Feat LLM with $\tau \in \{0.3,\,0.5,\,0.7\}$ and keep the number of ensembles fixed (e.g., 20).  
   Compute the average Jaccard similarity between pairs of rule sets; if it falls below roughly $\approx\;0.4$ you are probably adding too much noise.

3. **Observe downstream performance** rather than similarity alone:  
   - If AUC improves when moving from $\tau = 0.3$ to $\tau = 0.5$, keep increasing until you see diminishing returns or a drop.  
   - If performance plateaus or drops at $\tau = 0.7$, revert to $\tau = 0.$

4. **Consider dataset size / shot count:**  
   When only **very few shots** are available ($k \le 4$), lower temperatures ($\le 0.4$) tend to be safer because the linear‑model weighting step has little data to filter out bad rules; higher randomness could inject misleading features that cannot be down‑weighted effectively.

5. **Look at rule quality manually on a few samples** (the paper’s Appendix provides an example).  
   If you notice many syntactically malformed conditions (“greater than” versus “>”), you may need to lower $\tau$ or increase prompting strictness (e.g., stronger response instructions).

### Practical recommendation

- **Default:** $\tau = 0.5$, ensembles = 20, rules per class = 10 – this is what gave state‑of‑the‑art results on all thirteen benchmark datasets.
- **If you have a validation set:** try $\tau = \{0.3,\,0.5,\,0.\!7\}$. Pick the one that yields highest validation AUC and whose pairwise Jaccard similarity stays around $0.\!6\text{–}0.\!8$.
- **Very small $k (< 4)$** or highly noisy domains: stay at $\tau \le 0.\!4$ to keep rule generation more deterministic.
- **Very large feature spaces ($> 150$ columns)** where you rely heavily on bagging: a slightly higher $\tau (\approx\;0.\!6)$ can help because each bagged subset already reduces prompt length; extra diversity does not cost you additional noise.

In short, the Feat LLM authors did investigate rule variation indirectly via Jaccard similarity in an appendix and found that moderate temperature increases diversity beneficially, whereas too high a temperature introduces noisy or contradictory rules that can slightly degrade ensemble performance. Using $\tau \approx 0.\!5$ as a starting point and validating small adjustments on your own data is therefore the most reliable way to select an optimal temperature for a new dataset.​

### Can FeatLLM be extended to regression tasks, and if so how?
Question:
The current formulation assumes classification with binary rules per class and a softmax over logits. For regression we would need continuous targets. Would it make sense to generate numeric predicates (e.g., "if Age > 45 then high risk") and treat them as features in a linear regression model? Has anyone tried adapting the framework to regression, or are there theoretical obstacles?

Answer:
**Answer**

Yes – the FeatLLM pipeline can be adapted to regression tasks with only modest changes.  
The original paper formulates the downstream learner as a *linear* model that takes binary “rule‑features’’ (one per generated predicate) and produces class‑wise logits that are passed through a soft‑max (Eq. (2)). Nothing in the rule‑generation stage depends on the fact that the target is categorical; the LLM is asked to produce *deterministic predicates* such as “`Age > 45` ” or “`Cholesterol ≤ 200`”. These predicates are simply Boolean functions of the raw columns, and they can be used as inputs to any downstream predictor, not just a multinomial logistic regression.

### How to turn the binary features into a regression model

1. **Rule generation stays the same.**  
   The prompt (Section 3.1) already tells the LLM to output a *fixed number of rules* per *class*. For regression we replace the notion of “class’’ by a single continuous target and ask the LLM to produce rules that describe *high*, *medium* or *low* values of the target, or simply rules that are indicative of the target in general. In practice you can keep the same prompt and just change the task description, e.g.

   > “Predict the house price (in thousands).  Write ten predicates that are likely to increase the price.”

   The LLM will still emit syntactically well‑formed predicates because it is only operating on feature names and types.

2. **Binary encoding of each predicate.**  
   After parsing (Section 3.2) we obtain a vector  
   $$\mathbf{z}^{i}\in\{0,1\}^{R},$$  
   where $R$ is the number of generated predicates. This step does not require any modification; each entry simply records whether sample $i$ satisfies predicate $r$.

3. **Replace the soft‑max classifier with a linear regressor.**  
   Instead of Eq. (2) we define a single logit:  
   $$\hat y^{i}= \max(\mathbf{w},0)\cdot\mathbf{z}^{i}+b,$$  
   where $\mathbf{w}\ge 0$ are trainable non‑negative weights (the same positivity projection used in the paper) and $b$ is an optional bias term. The loss becomes mean‑squared error (MSE) or any other regression loss (MAE, Huber, etc.) evaluated on the few‑shot training points.

4. **Training remains few‑shot.**  
   Because the downstream model is still linear with only $R$ parameters, it can be fitted with as few as 2–4 labelled rows, exactly as in the classification experiments. The same optimizer settings (Adam, learning rate 0.01, 200 epochs, early stopping via cross‑validation) work unchanged.

5. **Ensembling / bagging is unchanged.**  
   The ensemble described in Section 3.2 (“Ensembling with bagging”) does not rely on soft‑max; each ensemble member produces an independent prediction $\hat y^{i}[t]$. The final forecast is simply the average:  
   $$\hat y^{i}= \frac{1}{T}\sum_{t=1}^{T}\hat y^{i}[t].$$  
   This retains the robustness benefits (self‑consistency of LLM‑generated rules, mitigation of spurious predicates) that were demonstrated for classification.

### Why this works and what to watch out for

* **Interpretability is preserved.**  
  The learned weights still reflect how much each predicate contributes positively to the target value; a large weight on “`Age > 45` ” means older age correlates with higher predicted values, which is exactly what one expects from a rule‑based regression model.

* **Non‑linearity comes from predicates, not from the downstream model.**  
  By turning continuous relationships into Boolean conditions (e.g., thresholds), FeatLLM implicitly captures piecewise‑constant approximations of an otherwise smooth function. With enough diverse predicates this can approximate many real‑world regressors (think of decision trees). The ensemble further smoothes these approximations.

* **Potential limitation – loss of granularity.**  
  When the true relationship is smoothly varying rather than threshold‑driven, binary predicates may discard information. In such cases you can enrich the feature set by asking the LLM to emit *interval* predicates (“`30 ≤ Age < 45` ”) or even simple arithmetic expressions (“`Age / 10` ”). Those can be parsed into *numeric* features instead of binary ones and fed together with the binary set to a linear model.

* **Theoretical obstacles?**  
  None are intrinsic to FeatLLM’s design. The method assumes that useful information can be expressed as logical conditions over existing columns – an assumption that holds for many tabular domains (medicine, finance, engineering). If a problem truly requires complex interactions that cannot be captured by a modest number of simple rules, performance will degrade just as it would for any rule‑based learner (e.g., classic decision trees). This is not a new limitation introduced by FeatLLM but rather an inherent property of using *interpretable* feature generators.

### Practical checklist for converting FeatLLM to regression

| Step | What to change | Reason |
|------|----------------|--------|
| Prompt | Replace “class’’ wording with “target value’’ wording; optionally ask for rules describing high/low values | LLM knows it must reason about a scalar output |
| Rule parsing | No change; keep binary conversion; optionally add numeric interval extraction | Binary features feed linear regressor |
| Downstream model | Switch soft‑max logits → single linear output; use MSE loss; keep non‑negative weight projection | Align loss with regression objective |
| Ensemble aggregation | Average predictions instead of averaging softmax probabilities | Same statistical benefit |
| Evaluation | Use RMSE / MAE / R² instead of AUC | Appropriate metric for continuous targets |

### Empirical evidence

The paper itself does not present regression experiments, but Section 3 explicitly states: “the generated features are used to infer class likelihood with a simple downstream machine learning model, such as linear regression…”. The phrase “linear regression” already appears in this context, showing that the authors envisioned a *regression* variant even though all reported results focus on classification. Moreover, their analysis of feature quality (Table 5) measures AUROC between each binary rule and the label; replacing AUROC by Pearson correlation or mutual information would give an analogous diagnostic for regression tasks.

### Bottom line

Adapting FeatLLM from classification to regression is straightforward:

1. Change only the task description in the prompt,
2. Keep rule generation and parsing untouched,
3. Replace the softmax‐based linear classifier by a plain non‑negative linear regressor,
4. Train on few‑shot data with an MSE loss,
5. Preserve bagging/ensemble as before.

No fundamental theoretical obstacle prevents this extension; its success will depend on whether meaningful “if‑then’’ predicates exist for your continuous target—a condition that holds for most real‑world tabular problems where domain knowledge can be expressed as threshold rules.

### Why does omitting feature descriptions hurt performance more in very low‑shot settings?
Question:
Table 3 shows that removing feature descriptions (-Description) leads to larger AUC drops when k=2 compared to k=8. Is this because the LLM relies on natural‑language definitions to compensate for lack of data? How critical are these descriptions when working with domains where feature names are cryptic (e.g., column names like "X1", "X2")?

Answer:
In the Feat LLM framework the LLM is asked to **invent rules** that separate the classes and then those rules are turned into binary features for a tiny linear model.  
When only a few labelled examples are available (e.g. \(k=2\)), the LLM has virtually no data‑driven signal to tell it which columns are actually relevant. It must therefore lean on whatever other information it can extract from the prompt.  

The *feature description* component of the prompt supplies exactly that missing signal: a short natural‑language definition of each column (its type, possible values, and, when available, a domain‑level meaning). Because the LLM has been trained on massive amounts of textual knowledge, it can match these definitions to its internal world‑knowledge (“age > 60 → higher risk of heart disease”, “serum‑creatinine = high → renal failure”, etc.). When the description is present, the LLM can:

1. **Identify informative columns** even if the few training rows do not contain enough variation to reveal the relationship.
2. **Ignore irrelevant or noisy columns** by recognizing that their definitions bear no semantic connection to the task description.
3. **Form plausible causal hypotheses** that are later refined by the few examples.

If we remove the descriptions (the “‑Description” ablation), the LLM is left with only the raw column names (e.g. *X1*, *X2*, …) and the few example rows. In a 2‑shot setting those rows rarely exhibit the full range of feature values, so the LLM cannot reliably infer which attributes matter from data alone. Consequently it either (a) generates rules that involve uninformative columns, or (b) fails to generate enough useful rules, both of which lead to a noticeable drop in AUC.

When more shots are available (e.g. \(k=8\)), the few labelled examples already provide a modest statistical glimpse of the true relationships; the LLM can use this data‑driven evidence to back‑track which columns are predictive, reducing its reliance on natural‑language definitions. Hence the same removal of descriptions harms performance far less: the drop in AUC is smaller because the data compensate for the missing semantic cues.

**Implications for cryptic column names**

If a dataset uses opaque identifiers such as *X1*, *X2*, … without accompanying textual definitions, Feat LLM will behave as in the “‑Description” ablation case. In very low‑shot regimes you should therefore supply explicit feature descriptions (or at least type information) in the prompt; otherwise you can expect a larger performance degradation, especially when only 1–4 labeled examples are available. Providing concise, domain‑relevant descriptions restores the LLM’s ability to draw on its pre‑trained knowledge and keeps performance stable even when label data are scarce.

### How does FeatLLM handle missing values during rule evaluation?
Question:
Real‑world tabular data often contain NaNs or missing entries. The paper does not discuss missingness. When a rule references a feature that is missing for a given row, what binary value does FeatLLM assign? Is there any imputation performed before rule evaluation, or does the generated Python code include checks for missingness?

Answer:
**Answer**

In *FeatLLM* the only place where the raw table is examined after the LLM has finished its reasoning is the piece of Python code that is generated from the textual rules (Section 3, “Parsing rules for feature generation”).  
The paper does not insert any separate imputation step; instead it relies on the semantics of the generated code and on how Python (or pandas) treats missing values (`NaN`) in the usual comparison operators.

When a rule such as

```python
def rule_1(row):
    return row["age"] > 55
```

is executed on a row whose *age* column contains `NaN`, the expression `row["age"] > 55` evaluates to `False` (actually it yields a Boolean `False` because any ordered comparison with `NaN` in NumPy/pandas returns `False`). Consequently the binary feature that records “does the row satisfy rule 1?” receives a value of 0 for that row.

The same behaviour holds for other relational operators (`<`, `==`, `!=`) and for string‑based checks (`row["sex"] == "male"`). In pandas a comparison with a missing entry also returns `False`, so a rule that asks whether a categorical value matches a given category will also produce 0 when the field is missing.

Because every rule is turned into an independent Boolean function, missingness never propagates to other rules: each rule is evaluated separately and simply yields 0 whenever any of its constituent conditions involve a `NaN`. The downstream linear model then sees a binary vector of 0/1 values; there is no additional “missing‑value flag” feature, and no special imputation (mean, median, mode, etc.) is performed before or after rule evaluation.

In short, *FeatLLM* handles missing entries implicitly:

* **No explicit imputation** – the framework does not fill in missing values beforehand.
* **Rule evaluation uses native Python/pandas semantics** – a condition that involves a missing value returns `False`, so the corresponding binary feature is set to 0.
* **Generated code may contain simple guards** – if the LLM decides to be defensive, it can emit code such as `if pd.isna(row["age"]): return False`, but this is optional and not required for correct operation; the default behaviour already yields 0.

Therefore, when you run the generated feature‑generation script on a dataset that contains `NaN`s, each rule simply treats those rows as not satisfying the rule, which translates into a 0 in the binary feature matrix used by the downstream linear model. This design keeps the pipeline simple and avoids having to decide on an imputation strategy for every new tabular problem.
