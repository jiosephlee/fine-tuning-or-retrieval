\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# From Rules to Predictions: Simple Linear Models Powered by LLM‑Generated Features  

## Introduction  

Tabular data—think spreadsheets of customer information, medical records, or sensor logs—are everywhere, yet building accurate models when only a handful of labeled examples are available remains a tough problem. Recent research has shown that **large language models (LLMs)** carry a wealth of domain knowledge that can be tapped for “few‑shot” learning, but most approaches still require the LLM to make a prediction for every new row, which is expensive and slow.

Enter **FeatLLM**. Instead of asking the LLM to classify each sample directly, FeatLLM asks the LLM **to engineer features**: it generates human‑readable rules that capture the conditions under which a particular class should be assigned. Those rules become **binary features** (1 = the rule fires, 0 = it doesn’t) and are fed into a very lightweight downstream model—a linear classifier with non‑negative weights.  

In this post we walk through the downstream modeling stage of FeatLLM, explain how training works in a few‑shot setting, and why such a simple model can compete with heavyweight baselines like XGBoost or TabPFN.

---

## From Natural‑Language Rules to Binary Features  

The LLM is prompted with a description of the task, feature names, and a few labeled examples. It responds with a set of **rules** for each class, e.g.:

```
Class: HighRisk
Rule 1: age > 55 AND cholesterol > 200
Rule 2: smoker = yes
...
Class: LowRisk
Rule 1: blood_pressure < 120
...
```

These rules are parsed automatically (the paper even lets the LLM generate the tiny piece of Python code that evaluates them). For every data row we evaluate each rule:

\[
z_{k}^{(i)}[r] = 
\begin{cases}
1 & \text{if row } i \text{ satisfies rule } r \text{ for class } k\\
0 & \text{otherwise}
\end{cases}
\]

Collecting all rules for class \(k\) gives us a binary vector \(\mathbf{z}_{k}^{(i)} \in \{0,1\}^{R}\), where \(R\) is the fixed number of rules per class (the authors use 10).

---

## A Minimalist Linear Model  

Once the binary rule‑features are ready, FeatLLM fits a **linear model without bias** for each class:

\[
\text{logit}_k^{(i)} = \max(\mathbf{w}_k,0) \cdot \mathbf{z}_{k}^{(i)} .
\]

Key points:

* **Non‑negative weights** (`max(w_k,0)`) ensure that satisfying an LLM‑generated rule never *decreases* the probability of its own class. This matches our intuition—if a rule describes “high risk,” obeying it should not hurt the high‑risk score.
* The logits from all classes are passed through a softmax to obtain class probabilities:

\[
\mathbf{p}^{(i)} = \operatorname{Softmax}\big([\text{logit}_1^{(i)},\dots,\text{logit}_c^{(i)}]\big).
\]

Because the inputs are binary and low‑dimensional (\(c\times R\) features total), training is extremely cheap.

---

## Training in the Few‑Shot Regime  

FeasTL​M is designed for **\(k\)-shot learning**, where only \(k \ll N\) labeled rows are available (the paper experiments with as few as 4 shots). The training pipeline looks like this:

1. **Generate rules** using the LLM on the \(k\) examples (plus feature descriptions).  
2. **Parse rules → binary features** for every row in the small training set.  
3. **Optimize weights** \(\{\mathbf{w}_k\}\) by minimizing cross‑entropy loss on those \(k\) rows.  
4. Use **Adam** with learning rate 0.01 for about 200 epochs (early stopping via cross‑validation).  

Even with such tiny data, the model learns which rules are truly informative; unhelpful rules end up with weight zero after training.

---

## Why This Tiny Model Holds Its Own  

You might wonder how a linear classifier with just a few dozen binary inputs can beat sophisticated tree ensembles or neural tabular models. The answer lies in three synergistic factors:

| Factor | What FeatLLM does | Why it matters |
|--------|-------------------|----------------|
| **LLM prior knowledge** | Rules encode domain wisdom (e.g., “older patients have higher heart disease risk”). | The model starts from *good* features instead of raw columns that may be noisy or irrelevant. |
| **Rule‐based filtering** | The two‑step prompting forces the LLM to first infer causal relationships, then derive concrete conditions. | Spurious correlations present in the few examples are less likely to become rules, reducing overfitting. |
| **Ensemble & bagging** | The process is repeated many times (≈20 ensembles) with different random seeds, feature subsets, and example orderings. The final prediction averages all logits. | Diversity smooths out occasional bad rules and mitigates prompt‑size limits on wide tables. |

Empirically, FeatLLM achieves **average AUC gains of ~10 %** over strong baselines like TabLLM and STUNT, and matches XGBoost even when XGBoost sees eight times more labeled data.

---

## Practical Benefits  

1. **Fast inference** – Once the rule set is generated (a handful of API calls), predicting new rows is just a matrix multiplication and softmax; latency is comparable to classic logistic regression.  
2. **No per‑sample LLM calls** – Unlike in‑context or fine‑tuned LLM approaches that query the model for every test row, FeatLLM incurs LLM cost only during *feature generation*.  
3. **API‑only access** – The method works with black‑box LLM APIs; no need for model weights or gradient updates on the language model itself.  
4. **Scalable to many columns** – Feature bagging lets us keep prompts short even when tables have >100 attributes.

---

## Takeaway  

FeatLLM demonstrates that **the heavy lifting can be done once—by an LLM that writes sensible rules—while downstream prediction can rely on a tiny linear model**. This separation gives us interpretability (rules are human readable), efficiency (few API calls), and robustness (ensemble + non‑negative weighting).  

If you’re struggling with limited labeled data on tabular tasks, consider flipping the script: ask an LLM *how* to decide rather than *what* to decide, turn its answer into binary features, and let a simple linear model finish the job. The results speak for themselves—big improvements without big models.
