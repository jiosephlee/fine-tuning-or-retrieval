# Turning Large Language Models into Feature Engineers: The FeatLLM Breakthrough  

## Introduction  

Tabular data—think spreadsheets of patient records, credit applications, or sensor logs—still dominate many real‑world AI problems. Yet training a high‑performing model often requires *lots* of labeled examples, which can be costly or even infeasible in domains like healthcare or finance.  

Enter large language models (LLMs). Their ability to reason from a few examples has sparked a wave of “LLM‑for‑tabular” research, where the model is prompted with serialized rows and asked to predict the label directly. While impressive, those approaches have two major drawbacks:  

1. **Inference is expensive** – an LLM call is needed for every test sample.  
2. **Prompt size limits** – as the number of columns grows, the serialized prompt quickly exceeds the model’s context window, degrading performance.  

The newly proposed **FeatLLM** framework flips the script. Instead of using an LLM as a black‑box predictor, FeatLLM treats the LLM as a *feature engineer*. The model produces a compact set of human‑readable rules (e.g., “age > 65 **AND** cholesterol > 200”), parses them into binary features, and then hands those features over to a tiny downstream learner (a linear model). The result is a system that still benefits from the LLM’s world knowledge but runs at inference speeds comparable to classic tabular methods.

Below we walk through how FeatLLM works, why its two‑step prompting matters, and what makes it so much cheaper at prediction time.

## From Prompt to Rules: The Two‑Step Reasoning Strategy  

A naïve prompt that asks an LLM “given these rows, predict the label” mixes two distinct reasoning tasks:

* **Understanding the domain** – figuring out which columns are actually relevant (e.g., age matters for heart disease; zip code usually does not).  
* **Learning from the few examples** – spotting patterns specific to the current dataset.

FeatLLM separates these concerns with a structured prompt that contains three blocks:

1. **Basic Information** – task description, natural‑language definitions for every column, and a handful of few‑shot examples formatted as  
   ```
   f1 is <value>. … f_d is <value>. Answer: <label>
   ```
2. **Reasoning Instruction** – a chain‑of‑thought style cue that splits the LLM’s work into two steps:  
   *Step 1*: “Reason about which features are likely causal based on your prior knowledge.” The LLM does *not* look at the example rows here; it simply draws on what it has read about the domain (e.g., “older people have higher cardiovascular risk”).  
   *Step 2*: “Now use the provided examples together with your Step 1 insights to write explicit rules for each class.” This forces the model to ground its prior knowledge in the actual data points.
3. **Response Instruction** – explicit formatting guidelines (e.g., “Rule k: `feature_name > 45`”) so that downstream parsing can be automated.

By compelling the model to first form a *global* view of feature relevance and only then specialize with the examples, FeatLLM reduces spurious correlations that often appear when few-shot data are noisy.

## Turning Natural‑Language Rules into Binary Features  

The output of step 2 is a list of textual conditions, typically ten per class. For binary classification we might see:

```
Class 0:
1) age <= 45
2) cholesterol < 180
…
Class 1:
1) age > 55
2) blood_pressure >= 140
…
```

These rules are not yet usable by a conventional ML algorithm because they are still strings. FeatLLM solves this with an *LLM‑assisted parser*: it feeds each rule back into the same LLM (or any code‑generation model) along with a small scaffold prompting it to emit valid Python code that evaluates the condition on a pandas DataFrame. The produced snippet looks like:

```python
def rule_0_1(row):
    return int(row["age"] > 55)
```

The code is executed via `exec()` and applied to every row in the dataset, yielding a binary vector **z** ∈ {0,1}⁽ᴿ⁾ for each class (R = number of rules per class). In other words, each rule becomes a new feature indicating whether that rule is satisfied.

## Learning Simple Weights – Why Linear Suffices  

Once we have binary rule‑features, we train an extremely lightweight model: a non‑negative linear classifier per class

\[
\text{logit}_k = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k,\qquad
\mathbf{p}= \text{Softmax}([\text{logit}_1,\dots,\text{logit}_c]).
\]

Because each feature already encodes an interpretable condition, we only need to learn *how important* each rule is. The positivity constraint ensures that no rule can actively decrease a class’s score—a sensible bias when rules were generated under expert‐like guidance.

Training this linear layer is cheap (a few hundred gradient steps on the few-shot data), and at inference time it reduces to a handful of dot products—orders of magnitude faster than invoking an LLM per sample.

## Bagging & Ensembling: Robustness Without Bigger Prompts  

Two practical challenges remain:

1. **Prompt length** – large tables contain hundreds of columns; feeding them all at once would overflow most LLM contexts.
2. **Rule diversity** – any single LLM query may miss useful rules.

FeatLLM tackles both with *feature bagging* and *ensembling*. For each ensemble member it randomly samples a subset of columns and/or training examples before forming the prompt. Because each member sees only part of the data, its prompt stays well within context limits. After generating rules and training its linear head, predictions from many members (typically ~20) are averaged.

This approach yields two benefits:

* **Robustness** – if one member proposes an incorrect rule, others can compensate.
* **Scalability** – we can handle datasets with >100 columns without hitting token limits.

## How Much Faster Is It?  

A quick timing comparison on the Adult income dataset (16 training shots) illustrates the advantage:

| Method                | Training Time | Inference Time (per sample) |
|-----------------------|---------------|-----------------------------|
| In‑context LLM        | ~5 min API calls | ~150 ms (one LLM call) |
| TABLET / TabLLM       | >10 min fine‑tuning | ~120 ms |
| **FeatLLM**           | ~30 API calls + linear fit | **≈3 ms** (pure CPU) |

The inference cost drops from dozens of milliseconds per sample (requiring network latency) to virtually nothing because only a dot product over ≤200 binary features is needed.

## Empirical Highlights  

FeatLLM was evaluated on 13 diverse benchmarks ranging from classic UCI tables (Adult, Credit-g) to newer medical datasets (Myocardial infarction complications) and synthetic tasks (sequence type classification). Across all settings:

* **Average AUC gain:** ≈10 % over strong baselines such as TabLLM and STUNT.
* With just **4 shots**, performance matches conventional models trained on 32 shots.
* Adding irrelevant columns (spurious correlations) degrades other methods quickly; FeatLLM’s AUC drops only modestly because its reasoning step filters out unrelated features before rule generation.

## Why This Matters  

1. **Cost efficiency** – No need for per‑sample LLM calls or costly fine‑tuning; only a few dozen API queries during setup.
2. **Interpretability** – The extracted rules are human‑readable conditions (“blood pressure ≥ 140”) that can be inspected or audited.
3. **API friendliness** – Works with any inference‑only LLM (GPT‑3.5 turbo was used in experiments), opening doors for proprietary models that don’t expose weights.
4. **Scalable prompting** – Feature bagging sidesteps context window limits without sacrificing accuracy.

## Takeaways & Future Directions  

FeatLLM demonstrates that large language models can serve as *knowledgeable feature engineers* rather than black‑box predictors for tabular tasks. By coaxing them through a two‑step reasoning prompt, parsing their natural language rules into binary features, and training an ultra‑light downstream model, we achieve high accuracy with minimal inference cost.

Open avenues include:  

* Extending beyond rule‐based features to richer transformations (e.g., learned embeddings).  
* Scaling to larger labeled sets while preserving interpretability.  
* Systematic analysis of bias propagation from LLM knowledge into generated rules—a critical step for safety‑critical domains.

If you’re dealing with limited labeled data but have access to an LLM API, FeatLLM offers a practical recipe: let the language model do what it does best—reason about concepts—and then let classic ML take over for lightning‑fast predictions.
