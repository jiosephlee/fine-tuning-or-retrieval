\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### How does producer‑consumer warp‑specialization avoid deadlock in FlashAttention‑3?
Question:
In Algorithm 1 the authors split a CTA into producer and consumer warp‑groups and use a circular shared‑memory buffer with stages. I am confused about how the synchronization works: when a producer issues a TMA load for \(K_j,V_j\) it "commits to notify" the consumer, but the consumer may already be waiting for that same stage. How does the implementation guarantee that neither side blocks forever, especially when the number of stages \(s\) is small? Is there a specific ordering of barrier calls or a hardware guarantee that resolves this?
Answer:
**Answer**

In FlashAttention‑3 the producer‑consumer split is built on a *bounded* circular buffer that lives in shared memory.  
The buffer has **$s$** stages (the variable *s* in the code) and each stage can hold one pair of key/value tiles.  The two warp‑groups (the *producer* warp‑group that issues TMA loads and the *consumer* warp‑group that runs the GEMMs) never touch the same stage at the same time; they coordinate their access with two very inexpensive barrier primitives:

* **“notify”** – executed by the producer after a TMA load finishes.  It marks the current stage as *ready* for consumption.  
* **“release”** – executed by the consumer after it has finished using a stage.  It marks the stage as *free* for the next load.

Both barriers are implemented with a single `bar.sync` instruction whose operand is the stage index ($\text{stage} = j \% s$).  Because a `bar.sync` is a **full‑SMEM fence**, it guarantees that all stores to that stage’s memory become visible to the other warp‑group before either side proceeds past the corresponding `wait`.

---

### Why no deadlock can occur

1. **Bounded number of in‑flight tiles**  
   The producer may only have at most $s$ tiles resident in SMEM at any moment, because after issuing the load for stage $\text{stage}=k$ it immediately does `commit_notify(k)` and then proceeds to the next iteration *without waiting*.  If all $s$ stages are already occupied, the next iteration hits the line  

   ```cpp
   Wait for the (j % s)-th stage of the buffer to be consumed
   ```

   which forces the producer to stall until the consumer releases exactly that stage.  Therefore the producer never overwrites data that has not yet been consumed.

2. **Consumer progress is guaranteed**  
   The consumer reads a stage only after it has seen a corresponding notify from the producer:

   ```cpp
   Wait for $K_j$ (or $V_j$) to be loaded in shared memory
   ```

   This wait is satisfied as soon as the producer has completed its TMA for that stage and executed `commit_notify`.  Once the consumer finishes its two GEMMs (`SS‑GEMM` and `RS‑GEMM`) it executes `release(stage)`.  Because each iteration of the consumer releases exactly one stage, the number of free stages monotonically increases until the producer can resume.

3. **No circular waiting**  
   The only possible dependency cycle would be:

   *producer* → waits for a free stage → *consumer* → waits for a notified stage  

   but those two waits are on *different* stages because of the modulo arithmetic ($j \% s$).  With $s \ge 2$ (the implementation always chooses at least two stages; in practice we use three or four to hide latency) there is always a “gap” between the stage being produced and the one being consumed.  Hence when the producer blocks on a full buffer, at least one earlier stage has already been released by the consumer, breaking any cycle.

4. **Hardware guarantees**  
   The `bar.sync` instruction provides two guarantees that are crucial:

   * **Visibility** – all writes to SMEM before a `commit_notify` become visible to any thread that subsequently passes a `wait` on that barrier.
   * **Ordering** – barrier IDs are independent; a wait on barrier $k$ cannot be satisfied by a notify on barrier $k' \neq k$.  

   Because each stage uses its own barrier ID ($\text{stage} = j \% s$), there is no risk of a “late” notify satisfying a different wait.

---

### Putting it together

When a producer issues a TMA load for $K_j,V_j$ it launches an asynchronous DMA engine; this does not stall any CUDA core.  After issuing, it immediately records “stage = $j \% s$ ready” with `commit_notify(stage)`.  The consumer may already be waiting on exactly that barrier – if so, it proceeds instantly; if not, it will encounter the barrier later in its loop and will be released when the notify arrives.

Conversely, if the consumer reaches `release(stage)` before the producer has wrapped around to reuse that same stage, nothing happens: releasing an already‑free stage is simply a no‑op because all threads have already passed its corresponding barrier.

Because both sides always advance after at most one barrier per iteration, and because there are always more stages than simultaneous uses (the pipeline depth), neither side can be stuck forever.  The worst‑case latency is bounded by one round‑trip through all $s$ stages, which on Hopper corresponds to only a few hundred clock cycles—negligible compared with the time taken by an asynchronous WGMMA or TMA operation.

---

### Intuition

Think of each stage as a mail slot:  

*The producer puts a letter (the K/V tile) into slot $\text{stage}=k$ and rings a bell (`notify`).*  
*The consumer checks slot $\text{stage}=k$; if there’s a letter it reads it and later empties slot $\text{stage}=k$ (`release`).*  

With at least two slots, while one slot is being emptied another can already receive a new letter, so nobody ever waits forever.  The “bell” and “empty” operations correspond exactly to CUDA’s `bar.sync` – cheap, hardware‑guaranteed synchronisation primitives that make this reasoning robust.

Hence, even when $s$ is small (the authors use $s=2$ or $3$ in practice), the circular‑buffer protocol together with per‑stage barriers guarantees progress and eliminates deadlock in FlashAttention‑3’s producer‑consumer warp‑specialisation.

### What are the exact layout constraints for FP8 WGMMA operands and how are they satisfied?
Question:
Section 2.3 states that FP8 WGMMA only accepts k‑major operand layout, unlike FP16 which accepts both mn‑major and k‑major. The paper mentions an in‑kernel transpose of \(V\) tiles using LDSM/STSM instructions. Could someone clarify:
1) What memory stride order defines "k‑major" for a tile of shape \(B_c \times d\)?
2) How does the LDSM/STSM sequence accomplish the transpose without extra global memory traffic?
3) How are the register permutations (the \{d0 d1 d4 d5 ...\} pattern) derived from the accumulator layout?
Answer:
**Answer**

In the FP8 version of FlashAttention‑3 the only operand format that the Tensor‑Core WGMMA instruction accepts is *k‑major*.  “k‑major’’ simply means that the memory layout of a tile is contiguous in the **inner‑dimension $K$** of the GEMM (the dimension that is summed over), while striding in the outer dimension is done with a step of one element.  For a tile taken from a matrix that is stored row‑major (as the paper assumes for $\mathbf{Q},\mathbf{K},\mathbf{V}$), a $B_{c}\times d$ tile of $\mathbf{V}$ (where $B_{c}$ is the block size in the sequence‑length direction and $d$ is the head dimension) must therefore be laid out as

$$
\underbrace{v_{0,0},v_{0,1},\dots ,v_{0,d-1}}_{\text{row 0}}\;,
\underbrace{v_{1,0},v_{1,1},\dots ,v_{1,d-1}}_{\text{row 1}}\;,\dots ,
\underbrace{v_{B_c-1,0},\dots ,v_{B_c-1,d-1}}_{\text{row $B_c-1$}} .
$$

In other words, successive 8‑bit entries in shared memory correspond to moving **one step along the $K$ (sequence‑length) axis**, not along the head‑dimension axis.  This is what the authors call *k‑major*.

---

### 1.  “k‑major’’ stride order for a $B_c\times d$ tile  

If we denote by $\text{ld}$ the leading stride (the distance between two consecutive rows in memory), a k‑major tile has

$$
\text{address}(i,j)=\text{base}+i\times \text{ld}+j ,
\qquad i=0,\dots ,B_c-1,\;j=0,\dots ,d-1,
$$

with $\text{ld}=d$ for a compact tile.  The inner index $j$ advances contiguously; therefore each warp loads an entire 8‑bit column of the tile by reading consecutive bytes, which matches exactly what WGMMA expects for its operand $B$.

Contrast this with an *mn‑major* layout where the stride would be along the outer $M$ (or $N$) dimension: elements belonging to the same head dimension would be contiguous, i.e. `address(i,j)=base+i+ j*ld`.  FP16 WGMMA can handle both orders, but FP8 WGMMA is restricted to the first pattern because its internal data paths are hard‑wired to consume an 8‑bit stream that walks along the reduction dimension.

---

### 2.  In‑kernel transpose with LDSM / STSM without extra global traffic  

The tensor $\mathbf{V}$ arrives from global memory already **row‑major** (contiguous in head dimension).  To satisfy k‑major we must swap the two axes of each $B_c\times d$ tile after it has been staged in shared memory.  The paper does this entirely inside the kernel:

1. **TMA load** brings a $B_c\times d$ block of $\mathbf{V}$ from HBM into a shared–memory buffer using the normal row‑major stride.
2. A warp executes an **LDSM** (`ldmatrix`) instruction that collectively reads an $8\times8$ sub‑matrix from shared memory and deposits it into registers of all 32 threads.  LDSM always reads a *contiguous* 128‑byte region, so when we ask it to read an $8\times8$ block of *packed* FP8 values (two FP8 per half‑word), each thread receives one element of that block.
3. Immediately after, **STSM** (`stmatrix`) writes those registers back to shared memory, but STSM writes them in transposed order: what was column $c$ in the source becomes row $c$ in destination.  Because LDSM and STSM are both warp‑wide and use only registers as temporary storage, no intermediate global‑memory copy is needed.
4. By iterating this 8×8 micro‑transpose across the whole $B_c\times d$ tile (the usual tiling strategy used by CUTLASS), we obtain a k‑major layout in shared memory ready for the second WGMMA.

Since both instructions are executed by a single warp and operate on on‑chip resources only, they add essentially zero extra global memory traffic; they merely rearrange data that has already been fetched by TMA.

---

### 3.  Origin of the register permutation $\{d_0\,d_1\,d_4\,d_5\,d_2\,d_3\,d_6\,d_7\}$

When an FP8 WGMMA finishes its first GEMM ($\mathbf{Q}_i \mathbf{K}_j^{\top}$) it leaves its **FP32 accumulator** in registers with a layout that mirrors the *mn‑major* operand ordering of matrix $A$.  Fig. 9 of the paper shows that each thread holds eight consecutive accumulator words ordered as

```
a0 a1 a2 a3 a4 a5 a6 a7   (mn-major)
```

The second GEMM ($\widetilde{\mathbf P}_{ij}\,\mathbf V_j$) however expects its first operand (the “A” matrix) to be **k‑major** as described above, while its second operand (the transposed $\mathbf V_j$) already appears in k‑major form thanks to the LDSM/STSM transpose.

To make the accumulator compatible without moving data between threads we simply permute the eight words locally inside each thread.  The required permutation is exactly

```
d0 = a0
d1 = a1
d2 = a4
d3 = a5
d4 = a2
d5 = a3
d6 = a6
d7 = a7
```

or compactly `{d0 d1 d4 d5 d2 d3 d6 d7}` as written in §4.2.  
Intuitively this swaps the two groups of four columns: columns `0–3` stay where they are, columns `4–7` are interleaved so that after permutation the register file now stores columns in **column‑major order**, i.e. contiguous along $K$.  Because every thread applies exactly the same permutation, the logical matrix represented by all threads together becomes k‑major and can be fed directly into the next WGMMA.

The permutation can be implemented with a single `prmt` (byte permute) or `shfl` instruction; no extra shared memory or synchronisation is required.  This clever use of register reshaping eliminates what would otherwise be an expensive intra-warp shuffle step.

---

### Putting it together  

*   FP8 WGMMA requires operands whose *inner* dimension ($K$) is contiguous – that is **k‑major**.
*   Since $\mathbf V$ arrives in row‑major order, an **in‑kernel transpose** using warp‑wide `ldmatrix`/`stmatrix` rewrites each tile directly in shared memory into k‑major format, incurring no extra global loads or stores.
*   The accumulator produced by the first GEMM is originally laid out for mn‑major; applying the per–thread permutation `{d0 d1 d4 d5 d2 d3 d6 d7}` reshapes it into k‑major so it matches the transposed $\mathbf V_j$.  

These three steps satisfy all layout constraints while keeping all data movement on‑chip, which is why FlashAttention‑3 can exploit FP8 Tensor Cores without any additional global‐memory bandwidth cost.

### Why does overlapping softmax with WGMMA improve utilization despite data dependencies?
Question:
The paper explains that softmax is low‑throughput (exponential unit) while WGMMA is high‑throughput, and introduces a 2‑stage pipeline where the second GEMM of iteration \(j\) runs while softmax of iteration \(j+1\) runs. However, softmax needs the score matrix \(S^{(j)}\) which is produced by the first GEMM of the same iteration. How is this dependency broken? Is an extra register buffer used to hold \(S^{(j+1)}\) before softmax starts, or does the hardware allow out‑of‑order execution of these instructions?
Answer:
In the 2‑stage pipeline the apparent circular data‑dependency – *softmax of block \(j\) needs the score matrix \(S^{(j)}\) that is produced by the first GEMM of the same iteration* – is removed by **decoupling the production of the scores from their consumption**.  
The authors do this by keeping a **second copy of the scores in registers** and by exploiting the fact that the WGMMA instruction on Hopper is *asynchronous*: once a WGMMA is issued the warp can continue executing independent instructions while the Tensor‑Core unit works on the matrix‑multiply in the background.

Concretely, in the consumer warpgroup (Algorithm 4) each iteration does the following:

1. **Issue the first GEMM** `S_next = Q_i · K_j^T` with a WGMMA call and **do not wait** for its completion (`commit but do not wait`).  
   At this point the hardware already has all operands in shared memory and has started streaming them to the Tensor Cores.  

2. **Immediately issue the second GEMM** `O_i += P_cur · V_{j‑1}` (the RS‑GEMM that uses the softmax values from the *previous* block). This second WGMMA is also launched without waiting for its own operands to finish because its inputs (`P_cur` and `V_{j‑1}`) are already available in registers or shared memory.  

3. **Now wait for the first GEMM to finish**, read its output `S_next` from registers, and perform the *local softmax* (`exp`, `rowmax`, `rowsum`). The softmax therefore works on **the scores of iteration \(j\) that have just become ready**, while the Tensor Cores are already busy on the next iteration’s GEMM (`S_{j+1}`) and on the RS‑GEMM that uses those scores.

Because step 1 stores `S_next` directly into a register tile (`S_next` in the pseudocode), no global or shared memory write‑back is required before softmax can start. The register tile acts as a tiny FIFO that holds one block of scores; it is small enough to stay in each thread’s private register file, so there is no extra spill to shared memory. In effect, **the dependency is broken by buffering one block of scores in registers**.

The hardware side that makes this possible is twofold:

* **WGMMA asynchrony** – Hopper’s Tensor Cores can be launched as “fire‑and‑forget”. The issuing warp does not stall until a later explicit `wait` (or a barrier) tells it to observe the result. This lets non‑GEMM instructions (the exponential, max, and row‑sum needed for softmax) run in parallel with a still‑running GEMM from a different iteration.

* **Warp‑specialization** – The CTA is split into a producer warpgroup (which only issues TMA loads) and a consumer warpgroup (which issues WGMMA). Because only one warpgroup ever touches the registers that hold `S_next`, there are no write‑after‑read hazards; the compiler can safely reorder instructions within each warpgroup while respecting the explicit `wait` points inserted by the algorithm.

Thus, no additional global or shared buffer is required; a single register tile per threadblock suffices. The paper’s “extra \(\mathbf{S}_{\text{next}}\) must be kept in registers” comment (Section 4.2, “Register pressure”) refers exactly to this per‑iteration register buffer. By overlapping softmax of block \(j\) with both GEMMs of block \(j+1\), the Tensor Core units stay busy almost all of the time, raising utilization from ~35 % (FlashAttention‑2) to ~75 % on H100.

In summary, the dependency is broken by

* launching each GEMM asynchronously,
* storing its output locally in registers,
* deferring the softmax until after a later explicit wait,
* and overlapping these waits with other GEMM work issued for subsequent blocks.

No special out‑of‑order execution engine beyond what Hopper already provides is needed; it is simply a deliberate software pipeline built on top of asynchronous WGMMA and per‑warp register buffers.

### How is block quantization performed for FP8 attention without increasing memory bandwidth?
Question:
The authors claim that block quantization (one scale per tile) can be fused with rotary embedding at no extra cost. I don't understand how the scaling factor is applied to each block: do they quantize \(Q,K,V\) on‑the‑fly during TMA loads, or pre‑scale the tensors in global memory? If scaling is done on‑the‑fly, how is per‑block max/min computed without extra passes over the data?
Answer:
The short answer is that **the per‑tile scale is not recomputed inside the attention kernel; it is produced once (outside the kernel) and then applied “for free” while the tiles are being brought from global memory into shared memory.**  
Because FlashAttention‑3 already works on the same tile granularity that the quantiser uses (a $B_r\times d$ query tile or a $B_c\times d$ key/value tile), the scale can be attached to each tile and consumed by the TMA load without any additional bandwidth or a separate reduction pass.

### Where does the scale come from?

Block quantisation is performed **prior to the attention kernel** (the paper calls this “fused with rotary embedding”).  
The pipeline is:

1. **Pre‑processing kernel** – before we launch FlashAttention‑3 we run a very cheap kernel that walks over the $Q,K,V$ tensors once, computes the maximum absolute value of each tile (or an equivalent “range” statistic), and stores a single 8‑bit‑or‑32‑bit scale factor together with each tile.  
   - The work is linear in the number of elements and hidden‑layer memory traffic already dominates any realistic model, so this pre‑pass adds essentially no extra cost.  
   - The scale vector lives in global memory next to the original tensor (e.g. interleaved or in a separate buffer); its size is negligible (one float per $B_r$ or $B_c$ rows).

2. **Fusion with rotary embedding** – if rotary positional embeddings are applied, they are performed inside exactly the same kernel that writes out the scales.  Because rotary embedding is also memory‑bandwidth bound, stitching the two operations together does not increase the amount of data moved.

Thus when attention starts, every tile already carries its own scale.

### How is the scale applied without extra memory traffic?

FlashAttention‑3 uses Hopper’s **Tensor Memory Accelerator (TMA)** to stream tiles from HBM directly into shared memory.  The TMA instruction can be programmed to perform a *user‑defined elementwise operation* on each loaded element before it lands in SMEM.  The authors exploit this capability as follows:

* The TMA descriptor for a given tile contains a pointer to the per‑tile scale that was stored in step 1.  
* While loading a $B_r\times d$ query tile, each FP32 element $x$ is multiplied by $\frac{1}{s_{\text{tile}}}$ and then cast to FP8 (e4m3).  This “scale‑and‑cast” happens inside the TMA data path, which means **the element never has to be written back to global memory at full precision**—the only data that crosses the HBM‑SMEM boundary are already quantised FP8 values plus one scalar for the next tile.

Because the scaling is performed inside TMA, **no additional global‑memory reads or writes are incurred**: we still read exactly one tile’s worth of raw data and we still write exactly one tile’s worth of quantised data into shared memory.  The scalar itself resides in a register or shared‑memory cache that is fetched once per tile, which is negligible compared with the $B_r d$ elements transferred.

### What about computing the per‑tile max/min on‑the‑fly?

The paper emphasises that *“the quantisation can be fused with an operation right before attention … with no additional slowdown”*.  This means that during step 1 (the pre‑processing pass) we already have all the information needed to compute each block’s max/min; there is **no need to scan a block again inside the attention kernel**.  The pre‑processing pass uses a simple parallel reduction over each tile:

```cuda
// Pseudo code for one tile
float maxabs = 0;
for (int i = threadIdx.x; i < B*D; i += blockDim.x)
    maxabs = max(maxabs, fabs(src[i]));
// warp‐level reduction → one value per tile
scale[tile_id] = maxabs / fp8_max_value;
```

Because this reduction runs on‐chip and writes only one scalar per tile, its cost is hidden by the much larger cost of moving the full tensor from DRAM to SMEM later on.

### Putting it together

When FlashAttention‑3 processes a query block:

1. The consumer warpgroup issues a **TMA load** for $\mathbf{Q}_i$.  
2. The TMA engine reads $\mathbf{Q}_i$’s raw FP32 values from HBM, multiplies each by $1/s_i$ (the per‑tile scale fetched from a tiny side buffer), and casts directly to FP8 while depositing into shared memory.  
3. The same happens for $\mathbf{K}_j$ and $\mathbf{V}_j$.  

All subsequent GEMMs operate on these FP8 tiles; their results are accumulated in FP32 as required by WGMMA, and because every tile has already been scaled consistently, no extra rescaling step is needed downstream.

### Why this does not increase bandwidth

* **Data volume unchanged** – we still stream exactly one FP32 element per entry from HBM; conversion to FP8 happens after it leaves HBM, not before.
* **Scalar overhead negligible** – one float per tile adds at most a few kilobytes even for very long sequences.
* **No extra passes** – the max/min reduction was performed once before attention launch; inside the kernel we never revisit a tile just to compute its statistics.

Consequently, block quantisation incurs essentially zero additional memory traffic while providing a much tighter dynamic range than per‑tensor scaling, which explains why FlashAttention‑3 can keep its bandwidth bound even after moving to FP8 precision.

### What is incoherent processing and why does multiplying by a random orthogonal matrix reduce FP8 quantization error?
Question:
In Section 3.3 the paper introduces "incoherent processing" where \(Q\) and \(K\) are multiplied by a random orthogonal matrix \(M\) before FP8 quantization. I would like to know:
1) How does this operation preserve the exact attention output mathematically?
2) Why does spreading out values via \(M\) lead to lower quantization error in practice? Is there any theoretical bound or empirical evidence supporting this claim?
Answer:
**Answer**

In the FP‑8 version of FlashAttention‑3 the authors apply a random orthogonal matrix  

\[
\mathbf M\in\mathbb R^{d\times d},\qquad \mathbf M^{\!\top}\mathbf M =\mathbf I ,
\]

to the query and key matrices **just before** they are quantised to FP8:

\[
\widetilde{\mathbf Q}= \operatorname{Quant}_8(\mathbf Q\mathbf M),\qquad 
\widetilde{\mathbf K}= \operatorname{Quant}_8(\mathbf K\mathbf M).
\]

The term “incoherent processing’’ in the paper refers to exactly this step.  
Below we explain why it does not change the attention result and why it makes the subsequent FP8 quantisation more accurate.

---

### 1.  Exact preservation of the attention output  

The attention scores are defined as  

\[
\mathbf S = \alpha\,\mathbf Q \mathbf K^{\!\top},
\qquad \alpha = 1/\sqrt d .
\]

If we replace \(\mathbf Q,\mathbf K\) by their rotated versions we obtain  

\[
\begin{aligned}
\widehat{\mathbf S} 
&= \alpha\,(\mathbf Q\mathbf M)(\mathbf K\mathbf M)^{\!\top}               \\
&= \alpha\,(\mathbf Q\mathbf M)(\mathbf M^{\!\top}\mathbf K^{\!\top})       \\
&= \alpha\,\mathbf Q (\underbrace{\mathbf M \mathbf M^{\!\top}}_{=\mathbf I}) 
   \mathbf K^{\!\top} \\[2mm]
&= \alpha\,\mathbf Q \mathbf K^{\!\top}
   = \mathbf S .
\end{aligned}
\]

Because **\(M\) is orthogonal**, \(M M^{\!\top}=I_d\); the two rotations cancel out when the matrix product is formed. Consequently the soft‑max matrix  

\( \operatorname{softmax}(\widehat{\bf S}) = \operatorname{softmax}({\bf S}) \)

and the final output  

\( {\bf O}= {\bf P}{\bf V} \)

are unchanged.  The only place where \(M\) appears is inside the two GEMMs that compute the scores; after those GEMMs finish, \(M\) never shows up again.  Hence the algorithm is mathematically identical to the original attention, irrespective of how we later quantise the intermediate tensors.

---

### 2.  Why rotating (spreading) the values reduces FP8 quantisation error  

#### 2.1  The problem with per‑tensor scaling  

FP8 (e4m3) keeps only three mantissa bits and four exponent bits.  When a whole tensor (e.g. all of \(Q\)) is scaled by a single scalar \(s_Q^{-1}\) before conversion, the optimal scale must accommodate **the largest absolute entry** in that tensor.  If a few outlier entries are much larger than the bulk of the data (which is typical for LLM activations), the optimal scale becomes large, and most entries are forced into a narrow region of the FP8 dynamic range.  This yields a large *relative* quantisation error for the majority of elements.

#### 2.2  Block‑wise scaling mitigates but does not eliminate outliers  

FlashAttention‑3 therefore already uses *block quantisation*: each \(B_r\times d\) (or \(B_c\times d\)) block gets its own scale factor \(s_{Q}^{(b)} , s_{K}^{(b)} , s_{V}^{(b)}.\)  
This limits an outlier to affect only its own block, but if an outlier sits in a block that also contains many small numbers, those small numbers still suffer a relatively coarse quantisation step.

#### 2.3  Orthogonal rotation spreads out energy  

Multiplying a vector \(x^\top \in \mathbb R^{d}\) by a random orthogonal matrix produces  

\( y^\top = x^\top M . \)

Each component of \(y^\top = \sum_{i=1}^{d} x_i M_{i,j}\) is a sum of many signed contributions from all coordinates of \(x.\)  

*If an outlier lives in coordinate \(i_0,\)* its influence is divided among **all** output components because every column of \(M\) contains roughly equal numbers of +1/–1 (for the Hadamard‑diagonal construction used in the paper).  
Consequently, no single entry of \(QM\) or \(KM\) becomes dramatically larger than the others; instead all entries have roughly comparable magnitudes, i.e. their variance is homogenised.

From a statistical point of view this operation is akin to applying a random orthonormal basis change – it preserves Euclidean norms (\(\|xM\|_2=\|x\|_2)\) but *decorrelates* large spikes from any particular coordinate. When we subsequently compute per‑block scales, each block sees a distribution whose maximum is much closer to its typical magnitude, so the chosen scale can be tighter.

#### 2.4  Empirical and theoretical support  

*Empirically* the paper reports in §6 that FP8 FlashAttention‑3 with both block quantisation **and** incoherent processing reduces root‑mean‑square error by a factor of 2.6 compared with a baseline that uses only per‑tensor scaling (Table 3). The ablation in §6 shows that removing incoherent processing (i.e., keeping original \(Q,K,V)\) raises the error close to the baseline level.

*Theoretically* one can bound the expected quantisation error under random orthogonal mixing. Let an element of a block before rotation be distributed with variance \(\sigma^2_{\text{in}}\) and let its maximum be \(M_{\text{in}}\). After multiplication by an orthogonal matrix drawn uniformly from the set of signed Hadamard · diagonal matrices, each output entry has variance still equal to \(\sigma^2_{\text{in}}\) but its maximum satisfies  

\[
\E [\,M_{\text{out}}\,] \leq C\,(\sigma_{\text{in}}\sqrt{\log d}),
\]

where \(C<1\) is a constant that depends on the distribution of signs. In contrast, without rotation we have \(M_{\text{in}}\approx O(\sigma_{\text{in}}\sqrt{\log (Bd)})$ because a single outlier can dominate; for typical head dimensions (\(d=64{-}256)\), this reduction can be several ×. Since FP8 quantisation error is roughly proportional to
\(M / 2^{p}\) where \(p=3$ mantissa bits, reducing \(M_{\text{out}}\) directly reduces expected error.

Thus incoherent processing does not change any mathematically exact quantity in attention; it merely reshapes each block’s value distribution so that low‑precision FP8 representation captures it more faithfully.

---

### TL;DR

1. Multiplying both queries and keys by any orthogonal matrix leaves
   \((Q\,M)(K\,M)^\top = QK^\top,\)
   so every downstream operation (soft‑max, weighting of V) stays exactly the same.
2. The orthogonal matrix spreads large outliers evenly across all components,
   making each block’s dynamic range much tighter.
   With tighter per‑block ranges, FP8’s limited mantissa can represent most values more accurately,
   which experimentally reduces RMSE by about 2.6×.
   Simple probabilistic arguments about variance preservation and maximal‑value contraction give a theoretical intuition for this improvement.

Hence “incoherent processing’’ is an elegant way to keep attention mathematically unchanged while dramatically improving FP8 quantisation fidelity on hardware such as Hopper’s Tensor Cores.

### How is FLOP counting performed for forward and backward passes in the benchmark section?
Question:
The authors compute forward FLOPs as
$$4 \cdot \text{seqlen}^2 \cdot \text{head
dim} \cdot \text{num	head
ds}$$
and then halve it for causal masking and multiply by 2.5 for backward pass. Why is there a factor of 4, and why exactly 2.5 for backward? Does this account for recomputation of intermediate softmax values or any extra matrix multiplications?
Answer:
In the benchmark the authors report the number of floating‑point operations (FLOPs) that would be performed by a **naïve** implementation of exact attention – i.e. the three matrix‑multiply steps that dominate the runtime:

1. **\(QK^{\top}\)** – a GEMM with shapes \((N\times d)\times(d\times N)\);
2. **\(\operatorname{softmax}(QK^{\top})\)** – an element‑wise exponential, reduction and division (the cost of which is tiny compared with the GEMMs);
3. **\(PV\)** – a second GEMM with shapes \((N\times N)\times(N\times d)\).

For a *single* head the two GEMMs each require

\[
\underbrace{N^{2}d}_{\text{multiplications}}+\underbrace{N^{2}d}_{\text{additions}}=2\,N^{2}d
\]

floating‑point operations. Because there are two such GEMMs, the total for the forward pass of one head is

\[
4\,N^{2}d .
\]

Multiplying by the number of heads gives the formula that appears in the paper

\[
\boxed{4 \;\text{seqlen}^{2}\;\text{head‑dim}\;\text{num‑heads}}
\]

The **factor 4** therefore does **not** come from any hidden constant; it is simply “two GEMMs × (multiply + add)”.  

---

### Causal masking

When causal (or lower‑triangular) masking is applied only the entries on or below the diagonal are actually computed. The upper‑triangular half is skipped, so roughly half of the \(N^{2}\) elements are omitted. Consequently the FLOP count is divided by two:

\[
\frac{4\,N^{2}d}{2}=2\,N^{2}d .
\]

---

### Backward pass – why “\( \times 2.5 \)”?

During back‑propagation through attention we need gradients for \(Q,K,V\). As shown in § 2.1 of the paper, this requires **five** matrix multiplications:

* \(dV = P^{\top} dO\)  (1)  
* \(dP = dO\,V^{\top}\)  (2)  
* \(dS = \mathrm{dsoftmax}(dP)\)  (element‑wise, negligible)  
* \(dQ = \alpha\, dS\,K\)  (3)  
* \(dK = \alpha\, dS^{\top} Q\)  (4)

In addition, the forward pass already performed two GEMMs (the same \(QK^{\top}\) and \(PV\)). If one counts every matrix multiplication that *needs to be executed* in a standard autograd implementation, the backward pass therefore incurs

\[
5 \text{ (backward)} + 2 \text{ (forward)} = 7
\]

GEMMs, while the forward pass alone uses only 2. The ratio of backward‑to‑forward FLOPs is therefore

\[
\frac{7}{2}=3.5 .
\]

However, in practice three of those seven multiplications are *reused*: the \(QK^{\top}\) and \(PV\) results are already in registers or shared memory when we start back‑propagation, so we do **not** recompute them. Only three new GEMMs (the ones listed as (1)–(4) above that involve a fresh operand—\(dO V^{\top}, dS K, dS^{\top} Q\)) have to be executed anew.

Hence the effective number of **additional** matrix multiplies in the backward sweep is three, giving a total of

\[
2 \text{ (forward)} + 3 \text{ (extra backward)} = 5
\]

GEMMs versus 2 in the forward pass, i.e.

\[
\frac{5}{2}=2.5 .
\]

That is exactly the factor quoted by the authors: they count all FLOPs required to produce both outputs and gradients, assuming that intermediate softmax values (\(P=\operatorname{softmax}(QK^{\top})\)) are kept in registers/SMEM and not recomputed, and that only the *new* matrix products needed for gradients are performed.

---

### What about “extra” work such as softmax recomputation?

The softmax itself involves an exponential, a reduction, and a division per element of the score matrix; these operations are \(O(N^{2})\) but their arithmetic intensity is far lower than that of a GEMM (the GPU can execute roughly two orders of magnitude fewer FLOPs per second for special functions than for Tensor‑Core matrix multiplication). Because their cost is negligible compared with matrix multiplies on H100, they are omitted from the FLOP tally used for reporting TFLOP/s.

In short:

* **Factor 4** = two GEMMs × two FLOPs per multiply‑add.  
* **Division by 2** for causal masking reflects halving of the dense score matrix.  
* **Factor 2.5** for backward comes from: forward needs 2 GEMMs; backward adds three *new* GEMMs; total = 5 → \(5/2 = 2.5\).  
* No extra FLOPs are counted for recomputing softmax or intermediate values; those are assumed to be cached within the kernel as described in § 2.1 and § 3.

Thus the reported FLOP counts faithfully represent the arithmetic work performed by a conventional exact‑attention implementation on which their speed measurements are based.

### Why does FP8 FlashAttention‑3 underperform for small sequences or causal masking compared to cuDNN?
Question:
In the discussion, authors mention that FP8 FlashAttention‑3 lacks a persistent kernel and load balancing strategy, which hurts performance for short sequences and causal masks. Could someone explain what a persistent kernel is in this context, how it helps with small workloads, and why causal masking exacerbates the issue?
Answer:
**Answer**

In FlashAttention‑3 the authors split the work of a CTA (a thread‑block) into two *warp‑groups*: one warp‑group only issues loads (the *producer*), the other only issues the actual matrix‑multiply / soft‑max work (the *consumer*).  
When the whole attention kernel runs **persistently**, the same CTA stays resident on a SM for the entire length of the sequence and repeatedly processes many blocks of the Q/K/V tensors. The kernel therefore does not have to be launched again for every block; it can keep its registers, shared‑memory buffers and, most importantly, the *load‑balancing state* that tells each warp‑group which tile of K or V it should fetch next.  

A **persistent kernel** is simply a CUDA kernel that contains an internal loop over tiles of the input and never returns until all tiles have been processed. Because the kernel never exits, the scheduler does not have to re‑allocate registers or shared memory between launches, and the warp‑specialisation bookkeeping (which warps are producers vs. consumers at any moment) can be kept in registers. This reduces launch overhead and lets the GPU keep a high occupancy even when each individual tile is very small.

### Why this matters for short sequences

When the sequence length $N$ is small (e.g., a few hundred tokens) the number of tiles $T_c = \lceil N/B_c\rceil$ that each CTA must iterate over is also small. In a *non‑persistent* implementation the host would launch a separate kernel for each tile (or each group of tiles). The launch latency (a few microseconds) and the need to re‑initialise shared memory and synchronisation primitives become a non‑negligible fraction of total run time, so the achieved TFLOPs drop sharply. With a persistent kernel these per‑tile launch costs disappear; the CTA can immediately start processing the next tile while still holding its registers, so even a handful of tiles can keep the hardware busy.

### Causal masking compounds the problem

Causal masking means that for row $i$ only columns $j\le i$ are needed. In FlashAttention terminology this reduces the number of key/value blocks that a given query block must attend to from $T_c$ to roughly $i/B_c$. Consequently many of the consumer iterations become **empty** or contain far fewer GEMM rows. In a persistent kernel this simply translates into shorter inner loops, which again reduces the amount of work that can hide latency between TMA loads and WGMMA instructions. The warp‑group that is supposed to compute $\mathbf{Q}_i\mathbf{K}_j^\top$ may finish its matrix multiply quickly and then wait for the next non‑empty block; during that idle time no useful work is overlapped with the softmax / exponential pipeline, so overall utilisation falls.

Non‑causal attention (full dense mask) gives each query block a full set of $T_c$ key/value blocks, providing a steady stream of GEMM work that can be interleaved with softmax as described in §3.2 of the paper. Causal masks break this regularity, making it harder for the producer–consumer schedule to keep both warp groups busy, especially when $N$ is already small.

### How cuDNN avoids the slowdown

The cuDNN implementation that ships with H100 uses **Hopper‑specific GEMM kernels** together with an internal load‑balancing scheme that dynamically splits work across SMs even when there are few tiles. Moreover, cuDNN’s FP8 path does include a *persistent* version of its attention kernel: it keeps one or more SMs dedicated to processing all tiles while dynamically adjusting how many rows each SM handles per iteration. Because it does not rely on a strict producer/consumer division, it can still keep Tensor Cores busy when only half of the matrix is needed (as in causal masking). Consequently cuDNN’s FP8 kernels stay competitive – and sometimes faster – than FlashAttention‑3 on short sequences or with causal masks.

### Summary

* A **persistent kernel** in FlashAttention‑3 is an on‑SM loop over Q/K/V tiles that never returns to the host; it eliminates launch overhead and lets warp‑specialisation state stay resident in registers.
* For **short sequences**, there are few tiles, so launch overhead dominates unless persistence is used. Without persistence FlashAttention‑3’s performance drops sharply.
* **Causal masking** reduces the amount of work per query block, leading to many short inner loops where one warp group finishes early and stalls, further lowering utilisation.
* cuDNN’s FP8 implementation includes a persistent design and a more flexible load‑balancing strategy, so it does not suffer as much from these effects.

Thus, FP8 FlashAttention‑3 underperforms on small workloads or with causal masks because its current FP8 kernel lacks a persistent design and an adaptive load balancer; adding those would likely close the gap with cuDNN.
