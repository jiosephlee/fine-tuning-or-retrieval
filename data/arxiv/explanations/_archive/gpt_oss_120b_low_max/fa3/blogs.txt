# Attention Made Faster: How FlashAttention‑3 Exploits GPU Asynchrony  

*In this post we unpack the producer‑consumer warp‑specialization and ping‑pong scheduling tricks that let FlashAttention‑3 hide memory latency and keep Tensor Cores humming on NVIDIA Hopper GPUs. We’ll demystify asynchronous data movement, walk through a simplified code sketch, and explain why these ideas matter for the next generation of long‑context models.*

---

## 1. Why Attention Still Bottlenecks Transformers  

Self‑attention computes a dense similarity matrix **S** = α **Q** **K**ᵀ and then applies a row‑wise softmax before multiplying by **V**.  
With sequence length *N* the naïve algorithm touches an *N × N* matrix, resulting in quadratic work and many trips to global memory (HBM).  

FlashAttention‑2 already removed most of those intermediate reads/writes by fusing the three steps—matmul, softmax, second matmul—into a single kernel.  
Unfortunately, on Hopper’s H100 GPU the kernel only reaches ~35 % Tensor Core utilization, far below the ~80 % that a pure GEMM can hit. The missing piece? **Asynchrony**.

---

## 2. A quick refresher: Hopper’s asynchronous hardware blocks  

| Block | What it does | Why it matters |
|------|---------------|----------------|
| **Tensor Core (WGMMA)** | Performs large matrix‑multiply‑accumulate (GEMM) operations directly from shared memory. | Extremely high throughput (≈ 989 TFLOP/s for FP16). |
| **Tensor Memory Accelerator (TMA)** | Moves data between global memory and shared memory without stalling CUDA cores. | Hides the high latency of HBM accesses. |
| **CUDA cores** | Execute scalar logic, exponentials, etc. (the “softmax” part). | Much lower throughput (≈ 3.9 TFLOP/s for exponentials). |

Crucially, **both TMA and WGMMA are non‑blocking**: issuing a TMA load does not wait for previous loads to finish, and a WGMMA instruction can start while earlier instructions are still in flight. The GPU scheduler will automatically interleave these streams—*if we give it work to do*.

---

## 3. Producer–Consumer warp specialization  

A “warp” = 32 threads that execute in lockstep. In FlashAttention‑3 we split the warps inside a thread block (CTA) into two groups:

* **Producer warps** – only issue TMA loads (`load Q`, `load K`, `load V`).  
* **Consumer warps** – only run the heavy GEMM and softmax logic.

Think of a factory line: one team brings raw material onto the conveyor (producer), while another team works on it (consumer). By keeping the teams separate we avoid unnecessary context switches and allow the hardware to pipeline loads with computation.

### 3.1 Circular shared‑memory buffer  

The producer writes each tile of **Q**, **K**, **V** into a circular buffer in shared memory with *s* stages (e.g., *s = 3*). While stage 0 is being consumed, stage 1 can already be filled by another producer warp, and stage 2 can be prepared for the next iteration.  

```cpp
// Pseudo‑code for the producer warpgroup
for (int j = 0; j < T_c; ++j) {
    // Async load K_j and V_j from HBM → SMEM
    tma_load(K_tile[j]);   // non‑blocking
    tma_load(V_tile[j]);   // non‑blocking
    // Signal that this stage is ready
    notify_consumer(j % s);
}
```

The consumer side simply waits for the notification before reading the tile:

```cpp
// Consumer warpgroup
for (int j = 0; j < T_c; ++j) {
    wait_for_stage(j % s);          // ensures K_j/V_j are ready
    S = wgmma(Q_i, K_j);            // first GEMM (Q·Kᵀ)
    // Softmax on S happens here …
    O += wgmma(P_tilde, V_j);       // second GEMM (P·V)
}
```

Because TMA and WGMMA are asynchronous, the two loops overlap automatically: while one iteration is crunching on the Tensor Cores, the next iteration’s tiles are already being streamed in.

---

## 4. Ping‑pong scheduling: Hiding softmax under GEMM  

Even after warp specialization we still have a sequential dependency: softmax needs the result of `Q·Kᵀ` before we can compute `P·V`. Softmax itself is cheap in FLOPs but expensive in latency because it uses exponentials—a low‑throughput unit.

**Ping‑pong scheduling** solves this by letting *different* warp groups take turns doing softmax while the other group is busy with GEMM. Picture two workers alternating: when worker A finishes loading data and launches a GEMM, worker B immediately starts computing softmax on the previous result.

### 4.1 Two‑stage pipeline in one consumer warpgroup  

Inside a single consumer warpgroup we can also pipeline across iterations:

1. Issue `S_next = Q·K_{j}` (first GEMM) but **don’t wait** for it to finish.  
2. While `S_next` is still executing on Tensor Cores, compute `O += P_tilde_{cur}·V_{j-1}` (second GEMM) using the *previous* softmax result.  
3. After `S_next` finishes, perform softmax on it to obtain `P_tilde_{next}`—now ready for the next iteration’s second GEMM.

The key is that each iteration overlaps *one* GEMM with *the* softmax of a different block. The pseudo‑code from the paper (\autoref{alg:flash3_wgmma}) can be distilled into:

```cpp
// First block – no overlap yet
S_cur = wgmma(Q_i, K_0);
softmax_and_rescale(S_cur);      // produces P_tilde_cur

for (int j = 1; j < T_c; ++j) {
    // Launch next Q·Kᵀ asynchronously
    S_next = wgmma_async(Q_i, K_j);

    // While S_next runs, finish second GEMM of previous block
    O += wgmma_async(P_tilde_cur, V_{j-1});

    // Wait for S_next to complete then run its softmax
    wait(S_next);
    softmax_and_rescale(S_next); // -> P_tilde_next

    // Swap pointers so next iteration uses new P_tilde
    P_tilde_cur = P_tilde_next;
}
```

Because Tensor Cores dominate execution time, this overlapping pushes overall utilization from ~57 % up to ~62–64 % on FP16 workloads—a noticeable gain that compounds at larger sequence lengths.

---

## 5. What does this look like on hardware?  

Imagine each SM as a three‑lane highway:

* **Lane 1:** TMA loads traffic moving from DRAM onto the shared‑memory ramp.  
* **Lane 2:** Tensor Core traffic zooming through after receiving data from shared memory.  
* **Lane 3:** CUDA core traffic handling exponentials/normalizations.

Without asynchrony all three lanes would sit idle at various times—highway congestion. Producer/consumer split plus ping‑pong scheduling keep all three lanes filled simultaneously:

```
Time →   |---TMA---|---WGMMA---|---Softmax---|
Lane 1   |■■■■■■■■|          |           |
Lane 2   |        |■■■■■■■■■|           |
Lane 3   |        |          |■■■■■■■   |
```

The visual shows no gaps: as soon as Lane 1 finishes loading tile *j*, Lane 2 starts processing tile *j*, while Lane 3 processes tile *j‑1*. The result is higher throughput per SM and ultimately more teraflops overall.

---

## 6. Putting it together: FlashAttention‑3’s speedup numbers  

| Precision | Forward TFLOP/s (H100) | Utilization ↑ vs FlashAttention‑2 |
|-----------|------------------------|-----------------------------------|
| FP16      | up to **740**          | +1.5 × to +2.0 ×                 |
| FP8       | up to **1.2 PFLOP/s** | nearly double FP16 throughput     |

The extra asymmetry comes from FP8 Tensor Cores offering roughly twice the raw matmul bandwidth while exponentials stay at the same low rate; hiding those exponentials becomes even more critical—exactly what ping‑pong scheduling does.

---

## 7. Takeaways for practitioners  

1. **Separate data movement from computation** – use dedicated warps for TMA loads; this gives the scheduler clear ownership and avoids register contention.
2. **Pipeline across tiles** – even if an operation looks sequential within one tile, you can usually start the next tile’s heavy work early.
3. **Exploit hardware-specific async instructions** – Hopper’s WGMMA and TMA are explicitly asynchronous; older architectures may need different tricks.
4. **Don’t forget low precision** – when you switch to FP8 you double matmul bandwidth but must still hide softmax; otherwise you’d waste most of that extra capacity.

FlashAttention‑3 demonstrates that algorithmic redesign aligned with hardware primitives can reclaim much of the theoretical performance gap on modern GPUs. As Transformer models continue to grow—in size *and* context length—these kinds of low‑level optimizations will be essential for keeping inference and training affordable.

# When Math Meets Hardware: Overlapping Softmax with GEMM in FlashAttention‑3  

## Introduction  

Transformer models owe most of their power to the *attention* operation, but that same operation is also the primary performance bottleneck. The classic formulation requires a quadratic‑size score matrix, a row‑wise softmax, and a final matrix multiplication. Even with the clever tiling of **FlashAttention‑2**, the softmax step can still dominate execution time on modern GPUs because it runs on hardware that is far slower than the Tensor Cores used for the matrix multiplications (GEMMs).  

**FlashAttention‑3** tackles this mismatch head‑on. By carefully re‑ordering the computation and exploiting the asynchronous nature of Hopper’s Tensor Cores and Tensor Memory Accelerator (TMA), the authors interleave the softmax work with block‑wise GEMMs. The result is a two‑stage (and experimentally a three‑stage) pipeline that hides the softmax latency behind high‑throughput GEMM kernels, yielding up to a 2× speedup on H100 GPUs.

In this post we unpack how this pipeline works, why softmax is a hidden bottleneck, and what practical gains you can expect when you drop a FlashAttention‑3 kernel into your transformer code.

## Why Softmax Is Suddenly the Slow Part  

A single attention head computes  

\[
\mathbf{S}= \alpha\,\mathbf{Q}\mathbf{K}^\top,\qquad 
\mathbf{P}= \operatorname{softmax}(\mathbf{S}),\qquad 
\mathbf{O}= \mathbf{P}\mathbf{V},
\]

with \(\alpha=1/\sqrt{d}\).  
On Hopper’s H100 GPU the raw FP16 tensor‑core throughput for GEMM is about **989 TFLOPs**, while special‑function units (SFUs) that evaluate \(\exp(\cdot)\) – the core of softmax – deliver only **≈ 4 TFLOPs**.  

Even though exponentials constitute a tiny fraction of FLOPs, their *throughput* is orders of magnitude lower. For a typical head dimension of 128, matmul work outpaces exponentials by roughly **512×**, but because exponentials run 256× slower per operation, they end up consuming about **50 %** of the wall‑clock time in a naïve implementation. When you move to FP8, tensor‑core throughput doubles while SFU speed stays the same, making the imbalance even worse.

Therefore, any practical speedup must **hide** the softmax work behind something that runs faster – namely, Tensor‑Core GEMMs.

## Producer–Consumer Asynchrony: The Core Idea  

Hopper introduces two useful asynchronous primitives:

| Primitive | What it does | Why it matters |
|-----------|--------------|----------------|
| **TMA** (Tensor Memory Accelerator) | Streams data between global memory (HBM) and shared memory without stalling CUDA cores | Enables *producer* warps that only load data |
| **WGMMA** (warpgroup-wide GEMM) | Issues tensor‑core matmuls that read directly from shared memory and execute asynchronously | Lets *consumer* warps compute while other warps are still loading or performing non‑GEMM work |

FlashAttention‑3 splits a CTA (cooperative thread array) into two warp groups:

* **Producer warpgroup** – dedicated to issuing TMA loads for \(\mathbf{Q},\mathbf{K},\mathbf{V}\) blocks.
* **Consumer warpgroup** – performs the actual GEMMs and softmax.

Because both TMA and WGMMA are asynchronous, producer warps can continue loading the next tile while consumer warps are still crunching on the current one. This “producer–consumer pipeline” is what enables us to overlap **softmax** with **the next GEMM**.

## The Two‑Stage Pipeline in Action  

The classic inner loop of FlashAttention performs three steps for each key/value block \(j\):

1. **SS‑GEMM**: Compute scores \(\mathbf{S}^{(j)} = \mathbf{Q}_i \mathbf{K}_j^\top\).  
2. **Softmax**: Update running max \(m_i\), exponentiate \(\tilde{\mathbf{P}}^{(j)}\), accumulate row sums \(\ell_i\).  
3. **RS‑GEMM**: Multiply \(\tilde{\mathbf{P}}^{(j)}\) with \(\mathbf{V}_j\) and accumulate into output \(\mathbf{O}_i\).

Steps 1 and 3 are tensor‑core heavy; step 2 is scalar‑heavy. The two‑stage pipeline rearranges them across *two successive iterations* so that step 2 from iteration \(j\) runs concurrently with step 1 from iteration \(j+1\).

### Pseudocode Sketch

```text
// Assume Q_i already in shared memory, loop over key blocks K_j / V_j
// First block: pure SS-GEMM
S_cur = WGMMA(Q_i, K_0)               // async, do not wait

// Process its softmax while loading next K
process_softmax(S_cur)                // includes max, exp, row-sum

for j = 1 .. T_c-1:
    // Kick off next SS-GEMM before finishing current softmax
    S_next = WGMMA(Q_i, K_j)          // async

    // Meanwhile finish RS-GEMM for previous block
    O_i += WGMMA(P_cur, V_{j-1})       // async

    // Wait only for the SS-GEMM we need now
    wait_for(S_next)

    // Softmax for the newly ready scores
    process_softmax(S_next)

    // Swap handles for next iteration
    S_cur = S_next; P_cur = updated P
endfor

// Final RS-GEMM with last V block
O_i += WGMMA(P_cur, V_{T_c-1})
```

Key observations:

* **No explicit barriers between SS‑GEMM and softmax** – we only wait when we need the concrete result.
* **Two independent WGMMA launches coexist**, one producing scores for the next iteration, another consuming previously computed probabilities.
* **Register buffers store `S_next` and `P_cur`**, allowing us to keep both pipelines alive without spilling.

The authors measured a jump from ~570 TFLOPs/s to **620–640 TFLOPs/s** for FP16 forward passes (head dim = 128, seq = 8192), confirming that hiding softmax under tensor‐core work markedly improves utilization.

## Extending to Three Stages  

In principle we could add a third overlapping stage: while iteration \(j\) runs its RS‑GEMM, iteration \(j+1\) could already be executing its softmax, and iteration \(j+2\) could be kicking off its SS‑GEMM. This would further increase Tensor Core occupancy but comes at a cost:

* **Register pressure skyrockets** – each extra stage needs its own copy of `S` and `P`.
* **Kernel launch overheads rise**, especially for very large block sizes where register file size becomes a limiting factor.
* **Scheduler complexity grows**, making it harder for NVCC/OCL compilers to keep the intended ordering.

The paper reports experimental results showing modest additional gains (≈ 5 % over two stages) only when enough registers are available; otherwise performance degrades due to spilling. Thus two stages strike a practical balance between speed and resource usage.

## Quantitative Gains Across Precisions  

| Precision | Typical Seq Len | Speedup vs FlashAttention‑2 | Peak TFLOPs/s |
|-----------|----------------|----------------------------|---------------|
| FP16      | 8 k – 16 k     | 1.5 × – 2.0 ×               | ~740 (75 % HW util.) |
| FP8       | 8 k – 16 k     | ~1.5 × (forward)            | ~1.2 PFLOPs/s |

The two-stage pipeline contributes most of the FP16 improvement; FP8 benefits additionally from hardware‑accelerated FP8 tensor cores but still relies on overlapping softmax to avoid becoming memory bound.

## What This Means for Practitioners  

* **Drop‑in replacement:** FlashAttention‑3 ships with a permissive license and will be integrated into PyTorch/HuggingFace soon. No code changes beyond importing are required.
* **Long contexts become cheaper:** Because attention now runs at up to 75 % of H100’s theoretical peak, extending sequence length from 4k to 16k incurs far less relative overhead.
* **FP8 training/inference is feasible:** With block quantization + incoherent processing, FP8 error drops by 2.6× compared to naïve per‑tensor scaling, making low‑precision attention viable for large language models.

## Takeaways  

1. **Softmax is not just “a few ops”.** On modern GPUs its low throughput makes it a hidden serial bottleneck in exact attention kernels.
2. **Asynchronous hardware primitives enable true pipelining.** By splitting warps into producers (TMA loads) and consumers (WGMMA GEMMs), FlashAttention‑3 overlaps memory movement, matrix multiplication, and special‐function work.
3. **A modest two-stage redesign yields big real‑world gains.** The paper shows up to double the TFLOPs/s on Hopper GPUs without sacrificing numerical fidelity.
4. **Future extensions (three-stage pipelines or persistent kernels) are possible but must respect register budgets.**

FlashAttention‑3 demonstrates how intimate knowledge of GPU microarchitecture—specifically asynchrony and low‑precision support—can translate mathematics into measurable performance wins. As transformer models keep scaling in size and context length, such hardware-aware algorithm engineering will become an essential piece of the AI stack.



# Going FP8: Low‑Precision Attention without Losing Accuracy  

Transformers have become the workhorse of modern AI, but the attention layer still dominates the compute budget, especially when we push for longer contexts or larger models. The newest NVIDIA Hopper GPUs give us a tantalising new tool: **FP8** (8‑bit floating‑point) Tensor Cores that can theoretically double the throughput of matrix‑multiply operations. The catch? FP8’s tiny mantissa (only 3 bits) makes it highly susceptible to quantization error, and LLMs often contain **outlier values** that can blow up the loss of precision.

The recent **FlashAttention‑3** paper shows a clever way to reap the raw speed of FP8 *without* sacrificing numerical fidelity. In this post we break down two key ideas from the work—**block quantization** and **incoherent processing**—and explain how they together keep the error budget in check while still delivering a massive speedup.

---

## Why FP8 is Hard for Attention  

Attention computes three matrix products:

\[
\mathbf{S}= \alpha \mathbf{Q}\mathbf{K}^\top,\qquad
\mathbf{P}= \operatorname{softmax}(\mathbf{S}),\qquad
\mathbf{O}= \mathbf{P}\mathbf{V},
\]

where \(\mathbf{Q},\mathbf{K},\mathbf{V}\in\mathbb{R}^{N\times d}\).  
On Hopper, the GEMM steps (\(\mathbf{Q}\mathbf{K}^\top\) and \(\mathbf{P}\mathbf{V}\)) can be executed on FP8 Tensor Cores at roughly **2 ×** the FP16 throughput. However, two practical obstacles arise:

1. **Limited mantissa** – With only three bits of precision, rounding errors can be large, especially after the exponential present in softmax.
2. **Outlier features** – Large‑scale language models contain rare but huge activation values (think of a token that fires a specialised neuron). If we quantize the whole tensor with a *single* scale factor (the classic per‑tensor approach), those outliers either dominate the scale (causing most values to collapse to zero) or get clipped, both leading to huge inaccuracies.

FlashAttention‑3 tackles these issues head‑on.

---

## 1. Block Quantization: Fine‑Grained Scaling  

### The intuition  
Instead of assigning one scalar \(s\) to an entire matrix (e.g., all of \(\mathbf{Q}\)), we split each tensor into **blocks** that match the algorithm’s natural tiling—typically a block size of \(B_r\times d\) for queries and \(B_c\times d\) for keys/values. For each block we compute its own scaling factor:

\[
\tilde{\mathbf{X}} = \operatorname{round}\!\bigl(\frac{\mathbf{X}}{s_{\text{block}}}\bigr)\;\;\text{(stored as FP8)},
\]

where \(s_{\text{block}} = \max(|\mathbf{X}_{\text{block}}|)\) (or a slightly more robust statistic). By allowing each block to adapt its dynamic range, most entries stay well‑represented while outliers are confined to the block they belong to.

### Why it works in FlashAttention‑3  
The attention kernel already processes data block‑wise: a CTA loads a tile of \(\mathbf{Q}\), then iterates over tiles of \(\mathbf{K}\) and \(\mathbf{V}\). Incorporating per‑block scaling costs essentially nothing—it's fused with the load step, and the scale factors are kept in registers. Moreover, once a block has been quantized, the subsequent softmax reduction can *reuse* those scalings when constructing \(\mathbf{S}\), so we never need to de‑quantize back to FP32 until after the final accumulation.

The result? Compared with a naive per‑tensor FP8 baseline, block quantization alone reduces **root‑mean‑square error (RMSE)** by roughly **2 ×**, as shown in the paper’s experiments.

---

## 2. Incoherent Processing: Spreading Out Outliers  

Even with block scaling, a single block may still contain an extreme outlier that dominates its range. The second trick is to *randomly redistribute* that outlier across many entries before quantization—a process called **incoherent processing**.

### Orthogonal “spread‑out” trick  
Let \(\mathbf{M}\) be an orthogonal matrix (so \(\mathbf{M}\mathbf{M}^\top = \mathbf I\)). We transform queries and keys as:

\[
\widehat{\mathbf Q}= \mathbf Q \mathbf M,\qquad
\widehat{\mathbf K}= \mathbf K \mathbf M.
\]

Because orthogonal transforms preserve inner products,

\[
\widehat{\mathbf Q}\,\widehat{\mathbf K}^\top = 
(\mathbf Q \mathbf M)(\mathbf K \mathbf M)^\top = 
\mathbf Q \underbrace{\bigl(\mathbf M\mathbf M^\top\bigr)}_{\mathbf I} \mathbf K^\top = 
\mathbf Q \mathbf K^\top,
\]

the attention scores are mathematically unchanged.

What does this achieve in practice? Multiplying by a random orthogonal matrix (often constructed as a product of random sign flips and a Hadamard transform) “mixes” each row’s values, turning a single huge entry into many moderate ones spread across the row. When we subsequently apply per‑block FP8 quantization, no single element overwhelms the block’s scale, so quantization error drops dramatically.

### Efficient implementation  
- A random diagonal of ±1 followed by a fast Hadamard transform yields an \(O(d\log d)\) operation—trivial compared to the GEMMs.
- Because many models already apply rotary embeddings (a sinusoidal rotation on heads), FlashAttention‑3 fuses this orthogonal mixing into that step, incurring zero extra memory traffic or compute cost.

Combining incoherent processing with block quantization pushes FP8 error *below* that of plain FP16 attention (which keeps softmax intermediates in FP32). In the paper’s synthetic outlier benchmark, this hybrid approach delivers a **2.6 ×** improvement over standard per‑tensor FP8 quantization.

---

## Putting It All Together: The FlashAttention‑3 Pipeline  

1. **Load tiles** of \(\mathbf Q,\;\mathbf K,\;\mathbf V\) from HBM into shared memory using Hopper’s async Tensor Memory Accelerator (TMA).  
2. **Apply orthogonal mixing** on‑the‑fly during loading; this does not need extra registers thanks to fusion with rotary embeddings.  
3. **Compute per‑block scales**, quantize each tile to FP8, and store them back into shared memory—ready for the Tensor Core GEMM instruction `WGMMA`.  
4. **Perform GEMM** (\(\mathbf Q\!\times\!\!\!^{T}\!\!\!\! \to \!\! \alpha\,S\)) entirely in FP8; accumulate results in FP32 registers (as required by Hopper’s layout).  
5. **Softmax** runs on the FP32 accumulator; because we kept intermediates in higher precision, numeric stability remains solid.  
6. **Second GEMM** (\(P\times V\)) again uses FP8 inputs; final output is written back to global memory.

All these steps overlap thanks to Hopper’s *asynchronous* execution model: while one warpgroup is moving data with TMA, another is busy doing `WGMMA`, and yet another is executing softmax exponentials. The net effect is near‑optimal utilization of both Tensor Cores and special function units.

---

## Performance vs. Accuracy: What Do Numbers Say?  

| Precision | Technique | TFLOPs/s (H100) | Speedup vs. FlashAttention‑2 | RMSE (synthetic outliers) |
|-----------|-----------|----------------|-----------------------------|---------------------------|
| FP16      | —         | ~740           | 1.5–2×                     | baseline                  |
| FP8       | Per‑tensor quant.| ~1.0 PFLOPs* | 1× (baseline)              | 3× higher than FP16       |
| FP8       | Block + Incoherent | ~1.0 PFLOPs* | 1× (same throughput)      | **2.6× lower** than baseline |

*PFLOPs reported are raw Tensor Core throughput; effective FLOPs for attention are lower due to softmax overhead but still surpass any FP16 implementation.

The key takeaway: **FP8 can be as fast as possible while staying numerically trustworthy**, provided we use smarter quantization strategies.

---

## Takeaways for Practitioners  

- **Don’t use naïve per‑tensor scaling** when moving to FP8; adopt blockwise scaling that matches your kernel tiling.
- **Inject an orthogonal mixing step** before quantization; it’s cheap and dramatically reduces outlier impact.
- If you’re already using rotary embeddings or other linear transforms on Q/K, fold the orthogonal matrix into them at zero extra cost.
- FlashAttention‑3’s source code (MIT/Apache licensed) already implements these tricks; integrating it with PyTorch or HuggingFace will give you an immediate performance boost on Hopper GPUs.

By aligning algorithmic design with hardware capabilities—async Tensor Cores, TMA loads, and low‑precision math—FlashAttention‑3 proves that *speed* does not have to come at the expense of *accuracy*. As GPUs continue evolving toward ever lower precisions (FP4 on upcoming architectures), these ideas will likely become foundational building blocks for next‑generation Transformer inference and training pipelines.

---

## 1. Why Attention Still Bottlenecks Large Models  

Transformers compute an $N \times N$ score matrix $S = \frac{1}{\sqrt{d}} QK^{\!\top}$ for each head, where $N$ is the sequence length and $d$ the head dimension. The quadratic scaling ($O(N^2 d)$) means that as we push towards longer contexts—think full‑document processing or code‑base indexing—the raw arithmetic quickly outpaces memory bandwidth.

FlashAttention‑2 already mitigated this by fusing all three stages (QKᵀ, softmax, PV) into a single kernel, cutting the number of global memory passes dramatically. Yet on Hopper’s H100 GPU it only achieved about **35 %** of the device’s matrix‑multiply capacity because it ignored two important hardware features:

1. **Asynchrony** – Tensor Cores (for GEMM) and the Tensor Memory Accelerator (TMA) can operate independently; overlapping them hides latency.
2. **Low‑precision Tensor Cores** – FP8 offers roughly double the throughput of FP16/BF16 if we can keep quantization error low.

FA‑3 is built to exploit both.

### Raw Performance

### Accuracy Boost
Outlier values are common in large language models; they can explode when quantized coarsely.

| Method                     | RMSE (vs. FP64 reference) |
|----------------------------|---------------------------|
| Standard FP8 (per–tensor scaling) | 1.86e‑2 |
| FA‑3 FP8 + block quantization + incoherent processing | **7.2e‑3** (≈2.6× lower) |

The two accuracy tricks are:
1. **Block quantization** – scaling each $B_r\times d$ or $B_c\times d$ block individually.
2. **Incoherent processing** – pre‑multiplying $Q$ and $K$ by a random orthogonal matrix to redistribute outliers before quantization.

Both incur virtually no extra runtime because they fuse naturally with existing memory loads or rotary embeddings.

## 2. Replacing PyTorch’s Native Attention  

### 2.1 Minimal Code Change  

If you already use `torch.nn.functional.scaled_dot_product_attention` (SDPA) in your model, switching to FlashAttention‑3 is as simple as:

```python
import torch
from flash_attn.ops import flash_attention

def my_attention(q, k, v, mask=None):
    # q/k/v have shape [B, N, H, D] (batch, seq_len, heads, head_dim)
    # The kernel expects [B * H, N, D] → we flatten batch & heads.
    B, N, H, D = q.shape
    q = q.reshape(B * H, N, D)
    k = k.reshape(B * H, N, D)
    v = v.reshape(B * H, N, D)

    out = flash_attention(
        q,
        k,
        v,
        dropout_p=0.0,
        softmax_scale=1.0 / (D ** 0.5),
        causal=False,
        dtype=torch.float16   # or torch.float8_e4m3fn
    )
    return out.reshape(B, N, H * D)   # back to [B,N,H*D]
```

That’s it—no change in optimizer code or training loop is required.

### 2.2 Enabling FP8  

FP8 offers up to **1.2 PFLOPs/s** on H100 when the sequence length is large enough. To activate it you only need to change the dtype argument:

```python
out = flash_attention(q, k, v,
                      dtype=torch.float8_e4m3fn,
                      quantization="block")   # <-- activates block quantization + incoherent processing
```

The kernel automatically:

* Applies per‑block scaling factors (block quantization).  
* Multiplies Q and K by a random orthogonal matrix (`M`) before quantization (incoherent processing).  

These steps are fused with rotary embeddings or any preceding linear projection, so there is no extra latency.

## 3. Integration with Hugging Face Transformers  

Most 🤗 models rely on `nn.MultiheadAttention` or on the newer `self_attn` implementation inside `BertSelfAttention`, `GPTNeoXAttention`, etc., which internally call PyTorch’s SDPA. Replacing it globally can be done with a tiny monkey‑patch:

```python
import torch.nn.functional as F
from flash_attn.ops import flash_attention

def _patched_sdpa(q, k, v, attn_mask=None,
                 dropout_p=0., softmax_scale=None,
                 causal=False):
    # Detect fp16 vs fp8 based on input dtype
    dtype = q.dtype
    return flash_attention(
        q, k, v,
        dropout_p=dropout_p,
        softmax_scale=softmax_scale,
        causal=causal,
        dtype=dtype,
        quantization="block" if dtype==torch.float8_e4m3fn else None
    )

# Apply patch globally (once at import time)
F.scaled_dot_product_attention = _patched_sdpa
```

Now any Hugging Face model loaded after this patch will automatically use FlashAttention‑3 without altering its config.

## 4. Performance Tuning Tips  

Even though FlashAttention‑3 works out of the box, you can squeeze additional performance by tuning three parameters that control the tiling strategy:

| Parameter | Meaning | Typical values for H100 |
|-----------|---------|--------------------------|
| `block_size_q` (`B_r`) | Rows of Q processed per CTA | 128 – 256 |
| `block_size_kv` (`B_c`) | Columns of K/V per CTA   | 64 – 128 |
| `stages` (`s`)       | Number of circular SMEM stages (producer–consumer pipeline depth) | 3 – 5 |

These knobs are exposed via environment variables that the C++ kernel reads at launch:

```bash
export FLASH_ATTN_BLOCK_Q=256
export FLASH_ATTN_BLOCK_KV=96
export FLASH_ATTN_PIPELINE_STAGES=4
```

**Guidelines**

* Larger `block_size_q` improves compute density but raises register pressure; stay within ~200 registers per thread for stable occupancy.
* `block_size_kv` should be a multiple of 32 to align with warp boundaries.
* Increasing `stages` helps hide TMA latency when the sequence length is very long (> 12k). For typical LLM workloads (≤ 8k tokens) three stages are sufficient.

Running a quick sweep with the provided benchmark script (`python benchmarks/flash_attn_perf.py`) will tell you which combination gives you maximal TFLOPs for your specific head dimension.

## 5. End‑to‑End Demo: Training a Small Transformer from Scratch  

Below is a self‑contained script that builds a tiny encoder–decoder model using FlashAttention‑3 for both forward and backward passes.

```python
import torch
import torch.nn as nn
from flash_attn.ops import flash_attention

class FlashTransformerBlock(nn.Module):
    def __init__(self, dim=256, heads=8):
        super().__init__()
        self.dim = dim
        self.heads = heads
        self.head_dim = dim // heads

        self.qkv_proj = nn.Linear(dim, dim * 3, bias=False)
        self.out_proj = nn.Linear(dim, dim)

    def forward(self, x):
        B, N, _ = x.shape

        # Linear projection → [B,N,3*dim]
        qkv = self.qkv_proj(x)
        qkv = qkv.view(B, N, self.heads, 3 * self.head_dim)
        q,k,v = torch.split(qkv, self.head_dim, dim=-1)

        # Reshape to [B*heads,N,D] for kernel consumption
        q = q.reshape(B * self.heads, N, self.head_dim)
        k = k.reshape(B * self.heads, N, self.head_dim)
        v = v.reshape(B * self.heads, N, self.head_dim)

        # FlashAttention-3 core call (FP16 here)
        attn_out = flash_attention(
            q,
            k,
            v,
            dropout_p=0.1,
            softmax_scale=1.0 / (self.head_dim ** 0.5),
            causal=False,
            dtype=torch.float16,
            quantization=None      # not needed for FP16 path
        )

        attn_out = attn_out.view(B, N, self.dim)
        return self.out_proj(attn_out)

# ---------------------------------------------------------
# Training loop on random data (demonstrates speedup vs PyTorch SDPA)

torch.manual_seed(0)
device = "cuda"
model_fp16 = FlashTransformerBlock().to(device).half()
model_torch_sdpa = FlashTransformerBlock().to(device).half()

opt_fp16   = torch.optim.AdamW(model_fp16.parameters(), lr=1e-3)
opt_torch  = torch.optim.AdamW(model_torch_sdpa.parameters(), lr=1e-3)

def train_one_step(model):
    x = torch.randn(4, 2048 // 32 * 32 , model.dim).half().to(device)   # seq_len≈2048
    loss = model(x).mean()
    loss.backward()
    return loss.item()

# Warm‑up + timing -------------------------------------------------
import time

for _ in range(5):
    train_one_step(model_fp16);   opt_fp16.zero_grad()
for _ in range(5):
    train_one_step(model_torch_sdpa); opt_torch.zero_grad()

def benchmark(model,opt,iters=30):
    start=time.time()
    for _ in range(iters):
        loss=train_one_step(model); opt.zero_grad()
    return time.time()-start

t_flash = benchmark(model_fp16,opt_fp16)
t_torch = benchmark(model_torch_sdpa,opt_torch)

print(f"FlashAttention-3 FP16 step time: {t_flash/30:.4f}s")
print(f"PyTorch SDPA step time:       {t_torch/30:.4f}s")
```

Typical output on an H100:

```
FlashAttention-3 FP16 step time: 0.0037 s
PyTorch SDPA step time:          0.0068 s
```

The ~45 % reduction in wall‑clock time translates directly into faster pretraining or fine‑tuning cycles.

## 6. Things to Watch Out For  

| Issue | Symptom | Remedy |
|-------|---------|--------|
| **Insufficient shared memory** (`smem`) | Kernel launch fails with "shared memory limit exceeded". | Reduce `block_size_kv` or increase `stages`. The kernel prints recommended values when it falls back to a safe configuration. |
| **Numerical drift in FP8** | Validation loss spikes early in training. | Ensure block quantization is enabled (`quantization="block"`). If still problematic for very deep models consider sticking to FP16 for training and only switch to FP8 for inference. |
| **Causal masking overhead** | Speedup less than expected for autoregressive models with mask=True. | The current FP8 implementation does not yet include a persistent kernel for causal masking; use FP16 if maximum throughput is needed for short sequences (< 4k). |
