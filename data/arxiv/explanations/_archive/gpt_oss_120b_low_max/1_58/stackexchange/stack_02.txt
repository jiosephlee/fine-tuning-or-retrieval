\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### Why are activations quantized to the symmetric range \([-Q_b, Q_b]\) instead of using a zero‑point offset?
Question:
The paper states that activation quantization is performed per token to \([-Q_b, Q_b]\) to “get rid of the zero‑point quantization”. I don’t understand how removing the zero‑point simplifies implementation and whether it introduces any bias in the activation distribution. Could someone explain the trade‑offs between symmetric and asymmetric quantization in this context?
Answer:
In the BitNet b1.58 paper the activations are **quantised per token to the symmetric interval**  

\[
[-Q_{b},\,Q_{b}],
\]

instead of the usual asymmetric form  

\[
x_{\text{int}} = \operatorname{round}\!\bigl(\frac{x}{s}\bigr)+z,
\]

where a **zero‑point** \(z\) is stored.  
The authors call this “getting rid of the zero‑point quantisation” and claim that it is “more convenient and simple for both implementation and system‑level optimisation”.  
Below is an explanation of *why* a symmetric representation simplifies the pipeline and *what* (if any) bias it introduces.

---

### 1. What the zero‑point does

When you map a real‑valued tensor \(x\) to an integer type you need two numbers:

* **scale** \(s>0\) – how many real units each integer step represents;
* **zero‑point** \(z\in\mathbb Z\) – which integer corresponds to the real value zero.

If the real‑valued range is not centred on zero (e.g. activations after ReLU lie in \([0, a]\)), an asymmetric mapping is necessary: you shift the integer code so that the minimum real value maps to the smallest integer (often 0). This is what most post‑training quantisation schemes do, because it reduces clipping error.

### 2. Symmetric quantisation in BitNet b1.58

BitNet b1.58 chooses a *symmetric* interval for each token:

1. For a given token’s activation vector \(a\) they compute its maximum absolute value  
   \[
   M = \max_i |a_i|.
   \]
2. They set the scale \(s = M/Q_{b}\) (so that \(\pm Q_{b}\) map exactly to \(\pm M\)).
3. The integer code is simply  
   \[
   a^{\text{int}}_i = \operatorname{round}\!\bigl(\frac{a_i}{s}\bigr),
   \]
   with no additive offset; zero in floating point always maps to zero integer.

Because every token is processed independently, the dynamic range *is* allowed to shift from token to token, but within a token the mapping is perfectly centred.

### 3. Implementation advantages

| Aspect | Symmetric (no zero‑point) | Asymmetric (zero‑point) |
|--------|---------------------------|--------------------------|
| **Memory** | Only one float (`scale`) per token needs to be stored; the integer tensor itself already carries the sign, so no extra byte for `z`. | Two 32‑bit numbers (`scale` and `zero‑point`) per token (or per channel). |
| **Kernel simplicity** | Integer arithmetic can stay signed; multiplication by `scale^{-1}` is replaced by a single right‑shift or integer multiply‑accumulate when paired with ternary weights (which are also signed). No need to add/subtract `z` before/after the matrix multiply. | Every GEMM must add `z` to one operand (or subtract it from the other) before accumulation, which means extra instructions or a separate “bias” term in hardware. |
| **Hardware pipelines** | Existing INT8/INT4 matrix–multiply units already assume signed inputs; they can be reused unchanged, which is exactly what BitLinear does (ternary weights × INT8 activations → INT16 accumulation). | Many accelerators only support unsigned inputs for asymmetric quantisation; using signed inputs forces a conversion stage or special handling, increasing latency and power. |
| **Software stack** | The quantiser can be written as a few lines: compute `M`, divide, round, clip – all element‑wise operations that already exist in PyTorch/TorchScript. | You need a separate “quantise‐dequantise” wrapper that tracks both scale and zero point, and many libraries store them as separate tensors, complicating serialization and checkpoint loading. |

In short, by forcing the range to be symmetric we eliminate one scalar per token, remove an add/subtract from every matrix multiplication, and keep the whole data path in pure signed integer arithmetic – all of which are attractive for both GPU kernels (FasterTransformer) and upcoming ASIC designs.

### 4. Does symmetry introduce bias?

The only source of error compared with an optimal asymmetric mapping is that we are forced to centre the quantisation interval around zero even if most of the activation mass lies on one side. In practice this manifests as a small *quantisation bias*:

\[
\epsilon_i = a_i - s\,a^{\text{int}}_i .
\]

Because activations in transformers are passed through RMSNorm and SiLU/SwiGLU nonlinearities, their distribution after normalisation is roughly zero‑mean with comparable positive and negative tails (the RMSNorm rescales each vector to unit variance but does not shift its mean). Consequently, centering at zero incurs little extra error; most values are already balanced around zero.

The authors empirically verify this: “introduces negligible effects to the performance in our experiments”. Their ablation shows no measurable degradation in perplexity or downstream accuracy when switching from an asymmetric range \([0,Q_b]\) (the original BitNet way) to the symmetric \([-Q_b,Q_b]\).

When an activation distribution were heavily skewed (e.g., pure ReLU outputs), symmetric quantisation could indeed cause a noticeable bias. In those cases one would either keep an asymmetric mapping or insert a learned bias before quantisation (as done in other LLM quantisers). BitNet sidesteps this because its pipeline already includes RMSNorm which recentres activations.

### 5. Trade‑off summary

* **Symmetric quantisation** = **simpler hardware + less memory overhead**, at the cost of a tiny potential bias that vanishes when activations are roughly zero‑centred.
* **Asymmetric quantisation** = **lower quantisation error for skewed distributions**, but requires storing an extra zero‑point per token/channel and adds an add/subtract step inside every GEMM – complicating both software kernels and hardware datapaths.

For BitNet b1.58 the design goal is *throughput* and *energy efficiency* rather than absolute numeric fidelity; hence they deliberately choose symmetric activation quantisation because its implementation gains outweigh any minute loss in representational accuracy.

--- 

**Bottom line:** By scaling each token’s activation to \([-Q_b,Q_b]\), BitNet b1.58 eliminates the per‑token zero point, reduces storage and eliminates extra integer offsets inside matrix multiplications, yielding a cleaner signed‑integer pipeline with virtually no impact on model quality thanks to RMSNorm’s zero‑centering of activations. This trade‑off epitomises the paper’s overarching theme: *simplify computation wherever possible while preserving performance*.
