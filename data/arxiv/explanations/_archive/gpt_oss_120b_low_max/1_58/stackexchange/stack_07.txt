\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### How were latency and memory measurements performed with the 2‑bit kernel from Ladder?
Question:
"Both latency and memory were measured with a 2‑bit kernel, so there is still room for optimization…" I’m trying to understand what exactly was measured: was it the time for a single matrix‑multiply using Ladder’s kernel, or end‑to‑end inference time per token? Also, does using a 2‑bit kernel artificially inflate latency compared to an ideal 1‑bit implementation?
Answer:
In the experiments that lead to the latency and memory numbers in the paper, the authors did **not** time a single‑matrix‑multiply primitive in isolation.  
What they reported is the **time per output token** of a full forward pass of a Transformer layer (or, more precisely, of the whole model) as it would be run at inference time.  

The measurement pipeline is described in the *Results* section:

1. **Inference engine** – All numbers were obtained with NVIDIA’s **FasterTransformer** code base, which is an end‑to‑end implementation of the Transformer forward pass that includes embedding lookup, positional‑encoding, the RMSNorm / SwiGLU sub‑layers, KV‑cache handling and the final linear projection.  
2. **Kernel used for the linear layers** – For the BitNet b1.58 models FasterTransformer was linked against the **$2$‑bit kernel from Ladder** [ladder]. This kernel implements the “BitLinear” operation where the weight matrix is ternary (‑1, 0, +1) and the computation is performed with integer add‑accumulate operations; because Ladder currently provides a $2$‑bit interface (the extra bit is used for the sign) it is called a “$2$‑bit kernel”.

Consequently, each “time‑per‑token” entry in Table X (and the curves in Fig. 4) already includes all overhead that is present in a realistic inference scenario: memory accesses for activations and KV caches, the cost of converting $8$‑bit activations to the internal format, layer normalisation, etc. It is therefore an **end‑to‑end latency figure**, not a micro‑benchmark of a single GEMM.

### Why a $2$‑bit kernel?

Ladder’s current public implementation treats the ternary weight as a $2$‑bit quantity (one bit for sign, one bit for “zero vs non‑zero”). This design is convenient because it can reuse existing packed‑int kernels and still achieve most of the speedup that comes from eliminating FP16 multiplications. The authors explicitly state that *“both latency and memory were measured with a $2$‑bit kernel, so there is still room for optimization”*. In other words:

* The $2$‑bit representation is slightly less compact than an ideal pure $1$‑bit storage (which would need only one bit per weight).  
* The compute path also has to decode whether a given weight is zero before performing an add, which adds a tiny amount of logic compared with a hypothetical kernel that could directly stream a single bit and decide on‐the‐fly whether to add or skip.

Because of these extra steps, **the reported latency is a modest upper bound** on what could be achieved with a dedicated $1$‑bit accelerator or a hand‑crafted $1$‑bit kernel that completely removes even that conditional logic. In practice, however, the dominant cost in large models comes from moving data (memory bandwidth) rather than from the few extra control bits, so the gap between a $2$‑bit and an ideal $1$‑bit implementation is expected to be small—typically on the order of *$10$–$20\%$* at most, as observed in other low‑precision kernels.

### Summarising

* **What was measured?** Time per generated token (full forward pass) on GPU using FasterTransformer plus Ladder’s $2$‑bit “BitLinear” kernel; memory usage was measured simultaneously on the same stack.
* **Is it a single matmul?** No—its an end‑to‑end token latency that includes all model components.
* **Does using a $2$‑bit kernel inflate latency?** Slightly; it is not an ideal $1$‑bit implementation and therefore incurs modest overhead, but it already captures most of the speed advantage over FP16. The authors acknowledge that replacing it with a true $1$‑bit kernel could shave additional latency and further reduce memory footprint.

Thus the numbers presented are realistic inference figures for current software stacks, while leaving open room for future hardware or kernel optimisations that would bring latency even lower.
