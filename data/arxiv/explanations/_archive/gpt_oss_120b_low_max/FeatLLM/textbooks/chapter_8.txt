\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 8: **Algorithmic Summary of FeatLLM**

---

### Step 1: Sample *k* Shots and Compose Prompt  

The first stage of the FeatLLM pipeline is to select a tiny labeled subset of the training data and to turn it into a textual prompt that the large language model (LLM) can ingest.  
Formally, let  

\[
\mathcal{D}=\{(\mathbf{x}^{i},\,y^{i})\}_{i=1}^{N}
\]

be the full tabular dataset, where each input vector \(\mathbf{x}^{i}\in\mathbb{R}^{d}\) is accompanied by a natural‑language feature name list  

\[
F=\{f_{1},f_{2},\dots ,f_{d}\}.
\]

From \(\mathcal{D}\) we uniformly draw without replacement a *k‑shot* support set  

\[
\mathcal{S}=\{(\mathbf{x}^{i},y^{i})\}_{i=1}^{k},
\qquad k \ll N .
\]

The prompt consists of three logical blocks:

1. **Basic information** – a concise description of the prediction task (e.g., “Does this patient have chronic heart failure?”) together with the name, type (numeric, categorical, binary), and optional textual definition of each feature \(f_{j}\).  
2. **Few‑shot demonstrations** – each element of \(\mathcal{S}\) is serialized into a sentence of the form  

   \[
   \texttt{"}f_{1}\texttt{ is }x^{i}_{1}.\; \dots \; f_{d}\texttt{ is }x^{i}_{d}.\;\texttt{ Answer: }y^{i}\texttt{"}.
   \]

   These lines provide concrete examples that the LLM can juxtapose against its prior knowledge.  
3. **Reasoning & response instructions** – a short chain‑of‑thought cue that tells the LLM to (a) first reason about which features are causally related to the task, and then (b) generate a fixed number \(R\) of decision rules for *each* class label.  The instruction also specifies a machine‑readable output format (for example JSON objects containing “condition” strings).

The concatenation of these three blocks yields the final prompt \(\Pi\).  Because LLMs have a limited context window, FeatLLM optionally applies **feature bagging** at this stage: a random subset of features \(F_{\text{sub}}\subseteq F\) (of size \(d_{\text{sub}}\)) is selected, and only those features appear in the prompt.  Bagging reduces prompt length while preserving diversity across ensemble members.

---

### Step 2: Query LLM → Rules per Class  

With prompt \(\Pi\) in hand we invoke the language model in generation mode:

```
response = LLM.generate(prompt = Π,
                       temperature = τ,
                       max_tokens = L)
```

The temperature τ is set to a moderate value (e.g., 0.5) to encourage some stochasticity in the rule set, which later benefits ensembling.  The model returns a sequence containing exactly \(R\) rules for each class \(c\in\{1,\dots ,C\}\).  A typical rule is a logical condition over the selected features, for example  

```
IF (age > 65) AND (cholesterol < 200) THEN class = 1
```

Because the output format was prescribed in Step 1, post‑processing can reliably extract each condition as a plain text string \(r_{c}^{j}\), where \(j=1,\dots ,R\).

---

### Step 3: Parse Rules → Binary Features  

Raw natural‑language conditions must be turned into executable binary tests that can be applied to any sample \(\mathbf{x}\).  Direct string parsing is fragile; instead FeatLLM leverages the LLM itself as a code generator:

1. Construct a *parsing prompt* that includes:
   * The function signature (e.g., `def rule_i(sample):`),
   * A brief description of each feature’s type,
   * The textual rule \(r_{c}^{j}\).
2. Issue a second generation request; the LLM returns syntactically correct Python code that evaluates the rule and returns `True`/`False`.  
3. Execute the generated code with Python’s `exec()` in a sandboxed environment, producing for every sample \(\mathbf{x}^{i}\) a binary vector  

   \[
   \mathbf{z}_{c}^{i}= \bigl[\,z_{c,1}^{i},\,z_{c,2}^{i},\,\dots ,\,z_{c,R}^{i}\bigr]\in\{0,1\}^{R},
   \qquad 
   z_{c,j}^{i}= 
   \begin{cases}
     1 & \text{if rule } r_{c}^{j} \text{ holds on } \mathbf{x}^{i},\\
     0 & \text{otherwise}.
   \end{cases}
   \]

Thus each original training sample now lives in an interpretable “rule space” whose dimensionality does not depend on the original feature count \(d\), but only on the chosen number of rules \(R\).

---

### Step 4: Fit Linear Weights on *k* Shots  

With binary rule activations for every support example we now learn how much each rule should influence the final prediction.  FeatLLM adopts an extremely low‑capacity model: a separate non‑negative weight vector per class

\[
\mathbf{w}_{c}= [w_{c,1},\,w_{c,2},\,\dots ,\,w_{c,R}]^\top,\qquad w_{c,j}\ge0.
\]

For an example \(\mathbf{x}^{i}\) belonging to class \(c^{*}=y^{i}\), we compute logits

\[
\operatorname{logit}_{c}^{i}= 
    \bigl[\max(\mathbf{w}_{c},0)\bigr]^{\!\top}\!
    \mathbf{z}_{c}^{i},
    \qquad c=1,\dots ,C,
\]

and convert them into class probabilities via a softmax:

\[
p_{c}^{i}= 
    \frac{\exp(\operatorname{logit}_{c}^{i})}
         {\sum_{c'=1}^{C}\exp(\operatorname{logit}_{c'}^{i}) }.
\]

Training proceeds by minimizing standard cross‑entropy loss over the *k* shots:

\[
\mathcal{L}
    = -\,\sum_{i=1}^{k}
        \log p_{y^{i}}^{\,i}.
\]

Because only \(R\times C\) scalar parameters are optimized, stochastic gradient descent converges quickly even with very few examples; in practice Adam with learning rate \(10^{-2}\) and 200 epochs suffices.  The positivity constraint (\(w_{c,j}\ge0\)) guarantees that any rule emitted by the LLM cannot *decrease* the likelihood of its own class.

---

### Step 5: Repeat for *T* Ensembles; Bagging Details  

A single pass through Steps 1‑4 yields one “weak learner” whose performance depends on random choices made during:

* Which *k* shots were sampled,
* Which subset of features was bagged into the prompt,
* The stochastic sampling from the LLM (temperature τ).

To boost robustness and to mitigate two practical limitations—(a) noisy or partially incorrect rules, and (b) prompt length constraints—FeatLLM repeats the whole pipeline **T** times, producing an ensemble

\[
\Bigl\{
 (\mathbf{w}[t],\,\{\mathbf{z}[t]\}) 
 : t = 1,\dots ,T
 \Bigr\}.
\]

Each trial may use a different bagged feature set size \(d_{\text{sub}}\), thereby ensuring that even when many original columns cannot fit into any single prompt they will appear in at least some trials.  Because all trials share exactly the same inference API (30 calls per trial for rule generation + parsing), their computational cost scales linearly with \(T\), but remains modest thanks to parallelizable API calls.

---

### Step 6: Inference – Apply Stored Binary Features + Averaged Logits  

At deployment time no further LLM queries are needed.  For any new sample \(\mathbf{x}^{\star}\):

1. For each ensemble member \(t=1,\dots ,T\) evaluate all stored binary rules using the pre‑compiled Python functions obtained in Step 3, yielding rule activation vectors \(\mathbf{z}_{c}^{[t]}(\mathbf{x}^{\star})\).  
2. Compute logits with the learned weights for that member:

   \[
   \operatorname{logit}_{c}^{[t]}(\mathbf{x}^{\star})
     = 
     \bigl[\max(\mathbf{w}_{c}[t],0)\bigr]^{\!\top}
     \mathbf{z}_{c}^{[t]}(\mathbf{x}^{\star}).
   \]

3. Convert logits to probabilities via softmax as before and obtain an ensemble probability by averaging across trials:

   \[
   p_{c}(\mathbf{x}^{\star})
      = 
      \frac{1}{T}
      \sum_{t=1}^{T}
      \frac{\exp(\operatorname{logit}_{c}^{[t]}(\mathbf{x}^{\star}))}
           {\sum_{c'} 
            \exp(\operatorname{logit}_{c'}^{[t]}(\mathbf{x}^{\star})) } .
   \]

The final prediction is simply  

\[
\hat y = 
    \argmax_{c} p_{c}(\mathbf{x}^{\star}),
    \qquad
    c=1,\dots ,C .
\]

Because all heavy lifting (rule extraction and weight fitting) was performed offline, inference requires only elementary Boolean evaluations and dot products—operations that run orders of magnitude faster than calling an LLM for every test instance.

---

## Computational Complexity  

| Phase | Dominant Operations | Asymptotic Cost |
|------|----------------------|-----------------|
| **Prompt construction** | Sampling & string concatenation | \(O(k d_{\text{sub}})\) |
| **LLM rule generation** | API call; cost dominated by token count | Linear in token length ≈ \(O(R C)\) |
| **Rule parsing** | One LLM call per rule → code generation + `exec` | \(O(R C)\) |
| **Binary feature evaluation** | Evaluating Python predicates on one sample | \(O(R C)\) per sample |
| **Linear weight training** | Gradient updates over *k* examples | \(O(k R C)\) |
| **Ensembling (T repetitions)** | Multiplicative factor | Total ≈ \(T\times(O(k d_{\text{sub}})+O(RC)+O(kRC))\) |

In practice:

* **Training time** is dominated by the *T* LLM calls (each request costs milliseconds to seconds depending on service latency). The subsequent linear optimization is negligible because it touches at most a few hundred parameters.
* **Inference time** scales with \(O(T R C)\); with typical settings (\(T=20,\;R=10,\;C≤10)\) this amounts to only a few hundred elementary operations per instance—comparable to logistic regression on raw features.

Thus FeatLLM achieves high predictive performance while keeping both API usage and runtime within practical bounds for real‑world tabular workloads.
