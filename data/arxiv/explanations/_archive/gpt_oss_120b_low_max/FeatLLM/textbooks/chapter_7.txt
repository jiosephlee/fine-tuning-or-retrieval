\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 7: # Ensemble via Bagging and Self‑Consistency

In the context of few‑shot tabular learning with large language models (LLMs), the **FeatLLM** framework treats the LLM not as a direct predictor but as a feature engineer.  A single pass of the LLM—prompted to generate a set of decision rules—produces a collection of binary features that can be fed to an extremely simple downstream model (a non‑negative linear classifier).  While this approach already offers a substantial reduction in inference cost compared with end‑to‑end LLM prediction, it remains vulnerable to two practical concerns:

1. **Prompt length constraints** – When a dataset contains many columns, serializing all feature descriptions and few‑shot examples can exceed the context window of the LLM.
2. **Variability in the generated rules** – A single LLM query might return an incomplete or partially erroneous rule set, especially under low‑shot conditions where the model has little concrete evidence from the data.

To address both issues, FeatLLM deliberately introduces *randomness* across multiple LLM invocations and subsequently aggregates the resulting weak learners.  This process is rooted in two well‑established ideas from classic machine learning: **bagging** (bootstrap aggregating) and **self‑consistency** of language model outputs.  Below we unpack each component, explain why it matters for rule extraction, and describe how the final ensemble prediction is formed.

---

## Bagging of Features or Instances per Trial

Bagging is a technique originally proposed for stabilising high‑variance estimators such as decision trees.  The key idea is to train several learners on *different random subsets* of the training data or of the input dimensions, then combine their predictions.  In FeatLLM this principle is applied at the level of the *prompt* that is sent to the LLM.

### Subsampling Features

When a tabular dataset contains dozens or hundreds of columns, embedding every feature name and its natural‑language description into a single prompt would exceed the token limit of most commercial LLM APIs (often around 4 k–8 k tokens).  Rather than attempting to truncate or compress the description—an operation that risks discarding informative columns—FeatLLM samples a fixed‑size subset of features for each trial.  Concretely, suppose a dataset has \(d\) columns and we elect to include only \(d_{b}<d\) in any given prompt.  For trial \(t\) we randomly select a set
\[
\mathcal{F}^{(t)} \subseteq \{f_{1},\dots,f_{d}\},\qquad |\mathcal{F}^{(t)}|=d_{b}.
\]
Only the names, types, and optional definitions belonging to \(\mathcal{F}^{(t)}\) appear in the “basic information” portion of the prompt.  Consequently, each LLM query operates on a *different view* of the problem space.  Over many trials, every original feature will appear in several prompts, allowing its contribution to be evaluated indirectly through multiple rule sets.

### Subsampling Instances (Few‑Shot Examples)

FeatLLM also draws from a pool of few‑shot demonstrations.  Even though only \(k\) labelled samples are permitted for training (the low‑shot regime), their *order* within the prompt influences how the LLM parses and reasons about them.  By randomly shuffling these \(k\) examples before each query we obtain diverse contextual cues for rule generation.  Moreover, when \(k\) exceeds what can comfortably fit into one prompt together with all feature descriptions, we may sample a subset \(\mathcal{S}^{(t)}\) of size \(k_{b}\le k\) for trial \(t\).  This instance bagging further reduces prompt length while preserving statistical diversity across trials.

### Why Bagging Helps

1. **Mitigating Prompt Size Limits** – By ensuring each prompt contains at most \(d_{b}\) features and \(k_{b}\) examples, we guarantee compatibility with any fixed context window.
2. **Reducing Over‑Reliance on Any Single Feature** – If an individual feature happens to be noisy or ambiguous, it will only dominate those trials where it appears; elsewhere its absence prevents it from corrupting the overall decision.
3. **Enabling Implicit Feature Selection** – After aggregation (described later), features that consistently contribute useful rules receive higher learned weights; those that are rarely selected will have near‑zero weights, effectively pruning them without manual intervention.

## Temperature Sampling to Encourage Diverse Rule Sets

The generation process of an LLM is stochastic: given a prompt it samples tokens from a conditional distribution
\[
p(w_t \mid w_{<t}, \text{prompt}),
\]
where \(w_t\) is the token at position \(t\).  The **temperature** hyperparameter \(\tau>0\) rescales this distribution before sampling:
\[
p_{\tau}(w_t \mid \cdot)=\frac{p(w_t \mid \cdot)^{1/\tau}}{\sum_{v} p(v \mid \cdot)^{1/\tau}}.
\]
A higher temperature (\(\tau>1\)) flattens the distribution, making low‑probability tokens more likely; a lower temperature (\(\tau<1\)) sharpens it, favoring high‑probability tokens.

In FeatLLM we deliberately set \(\tau=0.5\) for rule extraction (the paper reports using this value).  This modest increase over deterministic decoding serves two purposes:

1. **Diversifying Rules Across Trials** – Even when two prompts share exactly the same subset of features and examples (for example due to random seed collisions), sampling with \(\tau=0.5\) leads to different phrasing or slightly different logical conditions in the produced rules.  Consequently each trial yields a *weak learner* with its own binary feature set.
2. **Exploring Alternative Reasoning Paths** – The structured reasoning instruction in the prompt forces a two‑step chain-of-thought: first infer generic causal tendencies, then specialise using demonstrations.  Temperature allows the model to explore multiple plausible causal hypotheses rather than committing early to a single narrative that may be spurious under low‑shot data.

Empirically, increasing temperature beyond about \(0.7\) tends to introduce nonsensical syntax (e.g., malformed comparisons), which hampers downstream parsing; decreasing it below \(0.3\) leads to near‑identical rule sets across trials, diminishing ensemble benefits.  Hence FeatLLM adopts an intermediate value that balances diversity with syntactic reliability.

## Averaging Probabilities Across \(T\) Trials

Each trial \(t\in\{1,\dots,T\}\) proceeds through three stages:

1. **Prompt Construction** – Using bagged subsets \(\mathcal{F}^{(t)}\), \(\mathcal{S}^{(t)}\), temperature \(\tau\), and ordering instructions.
2. **Rule Generation & Parsing** – The LLM returns up to \(R=10\) rules per class; these are parsed into binary features \(\mathbf{z}_{k}^{(t)}\in \{0,1\}^{R}\).
3. **Linear Weight Learning** – A non‑negative weight vector \(\mathbf{w}_{k}^{(t)}\in \mathbb{R}_{+}^{R}\) is fitted on the few labelled samples by minimising cross‑entropy loss:
   \[
   \text{logit}_{k}^{(t)} = (\max(\mathbf{w}_{k}^{(t)},0))^{\!\top}\mathbf{z}_{k}^{(t)}, 
   \qquad
   p_{k}^{(t)} = \operatorname{softmax}([\text{logit}_{1}^{(t)},\dots,\text{logit}_{c}^{(t)}]).
   \]

The outcome for any new datum is therefore a probability vector per trial, denoted by
\( \mathbf{p}^{(t)} = (p_1^{(t)},\,p_2^{(t)},\,…,p_c^{(t)})^\top.\)

The final ensemble prediction aggregates these vectors by simple arithmetic averaging:
\[
\boxed{\;
    \bar{\mathbf{p}} = \frac{1}{T}\sum_{t=1}^{T} \mathbf{p}^{(t)}
    \;}
    .
\]
Averaging has several desirable properties:

- **Variance Reduction:** Independent stochastic errors across trials tend to cancel out when summed.
- **Bias Mitigation:** If any individual trial systematically favours an incorrect rule (e.g., due to an accidental spurious correlation), its influence is diluted by other trials that did not generate that rule.
- **Robustness to Missing Features:** Because each trial may omit different columns during bagging, no single weak learner can dominate unless its rule set is genuinely informative across many subsets.

From an implementation standpoint averaging is cheap: once all binary features have been materialised for a test sample (a straightforward Boolean check against each rule’s condition), we simply compute dot products with learned weight vectors and then average softmax outputs.

## Relation to Self‑Consistency in LLM Outputs

The term *self‑consistency* refers to recent findings that prompting an LLM multiple times on the same question and then taking a majority vote among generated answers dramatically improves accuracy (Wang et al., “Self‑Consistency”.).  The intuition is that although any single generation may be noisy or biased, correct reasoning paths tend to recur more often than incorrect ones when sampling from the model’s distribution.

FeatLLM leverages this principle implicitly:

- **Multiple Generations as Samples from Same Posterior:** Each trial draws from essentially the same conditional distribution over rules (same underlying prompt template), but because of bagging and temperature sampling yields distinct draws.
- **Aggregation Mirrors Majority Voting:** Averaging probabilities across trials corresponds mathematically to weighting each rule’s contribution by how frequently it appears among successful learners; rules that are consistent across many trials automatically receive higher effective influence after training because their associated binary features will be present—and suitably weighted—in many linear models.
- **Empirical Corroboration:** The ablation study in the paper shows that removing ensemble (i.e., using just one trial) degrades AUC across datasets; conversely, increasing the number of ensembles improves performance up to around \(T=20\), after which gains plateau—exactly as one would expect when self‑consistency saturates.

Thus bagging plus temperature sampling creates an ensemble that operationalises self‑consistency without requiring any additional external voting mechanism; it simply lets statistical aggregation do its work.

---

## Summary

The ensemble component of FeatLLM interweaves three complementary ideas:

1. **Feature/Instance Bagging** – Randomly subsampling columns and few‑shot examples respects token limits while encouraging diversified reasoning about different slices of the data.
2. **Temperature‑Controlled Sampling** – By softening the token distribution during rule generation we obtain distinct logical rule sets across trials.
3. **Probability Averaging Across Trials** – Linear models trained on each trial’s binary rule features are combined via softmax averaging, yielding a robust final predictor whose performance benefits from self‑consistency.

Together these mechanisms transform what would otherwise be a single uncertain rule extractor into a collection of weak learners whose collective wisdom surpasses any individual constituent—a classic example of “the whole being greater than the sum of its parts.”
