\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 12: # Hyperparameter Sensitivity and Practical Recommendations

In the development and deployment of **FeatLLM**, two hyper‑parameters dominate the behavior of the system: the number of ensemble repetitions, denoted **\(T\)**, and the number of generated rules per class, denoted **\(R\)**.  Both control how much information is extracted from the large language model (LLM) and how that information is subsequently used by a simple downstream linear model.  Understanding their impact is essential for practitioners who wish to obtain strong predictive performance while respecting the constraints of low‑shot learning, limited prompt length, and computational budget.

In this chapter we dissect the empirical sensitivity of **\(T\)** and **\(R\)** as reported in the FeatLLM experiments, translate those findings into concrete guidelines for setting additional inference parameters (temperature and top‑\(p\)), and discuss how to choose bagging ratios when dealing with high‑dimensional tabular data.  Throughout we remain faithful to the design choices and analyses described in the original work, avoiding any extrapolation beyond what was experimentally validated.

---

## Sensitivity Plots for \(T\) (Ensemble Size) and \(R\) (Number of Rules)

### What the Experiments Show

FeatLLM leverages an *ensemble* of independently generated rule sets.  For each trial \(t \in \{1,\dots,T\}\) a fresh prompt is sent to the LLM, producing a distinct collection of binary features \(\mathbf{z}^{(t)}\).  The final class probabilities are obtained by averaging over all trials (Eq. (3) in the paper).  The authors investigated a range of values for \(T\) while keeping all other components fixed (temperature = 0.5, rule count per class \(R = 10\)).  

The **sensitivity plot** (reproduced in Figure 10 of the appendix) displays mean AUROC across the thirteen benchmark datasets as a function of \(T\).  The curve rises steeply from \(T = 1\) (a single rule set) to roughly \(T = 10\), after which improvements taper off.  By \(T = 20\) performance approaches a plateau; additional ensembles yield only marginal gains while incurring extra API calls and latency.

### Interpretation

* **Diminishing Returns:** Each ensemble member contributes new rules because of stochastic elements in LLM generation (high temperature, random demo ordering).  Early members capture most of the useful diversity; later members mostly repeat already‑observed rules, so their marginal benefit shrinks.
* **Robustness to Noise:** Even when individual rule sets contain occasional incorrect or irrelevant rules, averaging across many trials dilutes their influence.  This self‑consistency effect explains why performance is stable once \(T\) exceeds roughly ten.
* **Computational Trade‑off:** Every additional ensemble member requires one LLM query (a single API call).  On a typical commercial model such as GPT‑3.5‑turbo‑0613 this incurs both monetary cost and wall‑clock latency.  Practitioners should therefore select the smallest \(T\) that yields near‑optimal accuracy.

### Practical Recommendation for \(T\)

| Desired Scenario                                      | Recommended \(T\) |
|-------------------------------------------------------|-------------------|
| **Maximum accuracy** (no strict latency budget)      | 20–25 (the value used in the paper) |
| **Balanced speed/accuracy** (typical production use) | 10–15 |
| **Very tight latency or cost constraints**            | 5–8 (accept modest AUROC loss) |

When resources are limited, start with \(T = 10\); if validation performance is already within a few percent of the best observed value, stop increasing \(T\).

## Sensitivity Plots for \(R\) (Number of Rules per Class)

### What the Experiments Show

The parameter **\(R\)** determines how many explicit decision rules FeatLLM asks the LLM to generate for each target class in a single prompt.  The authors fixed \(T = 20\) and varied \(R\) from small values (3–5) up to larger values (15–20).  Figure 11 in the appendix reports average AUROC versus \(R\).

Key observations:

1. **Monotonic increase up to a point:** Performance improves noticeably as \(R\) grows from three to about ten rules per class.
2. **Plateau and slight decline:** Beyond ten rules, gains flatten and can even reverse slightly on some datasets.
3. **Prompt length pressure:** Larger \(R\) lengthens both the *request* prompt (the LLM must output more structured rules) and the *generated code* that parses those rules, approaching token limits for datasets with many columns.

### Interpretation

* **Information vs. Noise:** Adding more rules supplies additional binary features that could capture subtler relationships. However, each rule is derived from noisy natural‑language output; beyond a certain count, many added rules become redundant or mildly erroneous, diluting signal.
* **Overfitting Risk in Low‑Shot Regime:** With only a handful of labeled examples (e.g., four shots), a high‑dimensional binary feature vector (\(c \times R\); where \(c\) is number of classes) can easily overfit during weight training, especially when \(\mathbf{w}_k\ge0\) are learned on few points.
* **Prompt Window Limitation:** The LLM’s context window restricts total token count. When the original table already contains many features (e.g., > 100), allocating space for ten well‑formed rules per class already consumes a sizable fraction of available tokens.

### Practical Recommendation for \(R\)

| Situation                                      | Recommended \(R\) |
|-----------------------------------------------|--------------------|
| **Standard low‑shot experiments** (k ≤ 8)     | 10                 |
| **Very small datasets** (k ≤ 4)               | 8 – 10 (lean toward smaller side to avoid overfitting) |
| **Datasets with > 80 original columns**       | ≤ 8 per class; consider reducing by applying feature bagging first |
| **When prompt length approaches limit**       | Reduce to 6–8; monitor response completeness |

In practice, start with ten rules per class—as used throughout the paper—and adjust downward only if token limits are exceeded or validation suggests overfitting.

## Guidelines for Setting Temperature & Top‑\(p\)

The generation temperature controls randomness in LLM sampling; top‑\(p\) truncates probability mass to keep only the most likely tokens.

* The FeatLLM experiments employed a **temperature of 0.5** and left top‑\(p = 1.0** (the default), striking a balance between deterministic rule formulation and sufficient diversity for ensembling.
* Higher temperature (> 0.7) yielded more varied rule sets across ensembles but also increased syntactic irregularities that made parsing harder, thereby raising API usage due to additional correction calls.
* Lower temperature (< 0.2) made outputs almost deterministic; ensemble diversity collapsed, reducing the benefit of averaging across trials.

**Recommendation:**  
- Use **temperature = 0.5** as a default.  
- If you observe many parsing failures due to unconventional phrasing, lower temperature modestly (e.g., 0.4).  
- If ensemble diversity appears insufficient (e.g., most trials produce identical rule lists), raise temperature slightly (up to 0.6).  
- Keep top‑\(p = 1.0** unless you need stricter control over tail tokens; experimental evidence shows no advantage in altering it.

## Bagging Ratios for High‑Dimensional Tables

When a dataset contains a large number of columns (\(d \gg 50\)), directly feeding all feature descriptions into an LLM prompt may exceed token limits or dilute attention on relevant attributes. FeatLLM addresses this through classic *feature bagging*: each ensemble trial randomly selects a subset of columns before prompting.

### Empirical Findings

The authors report that bagging “helps reduce” prompt size while preserving performance, especially on datasets like **Communities** and **Myocardial**, which have over one hundred attributes. Although exact bagging ratios are not tabulated in the main text, qualitative analysis indicates that selecting roughly **30–40 %** of columns per trial suffices to stay within token budgets while still capturing enough signal for rule extraction.

### Practical Procedure

1. **Determine feasible token budget:** Estimate tokens needed for task description + feature names + few‑shot examples ≈ 300 tokens. Subtract from model’s context window (e.g., GPT‑3.5 turbo ≈ 4 k tokens). The remainder dictates how many feature descriptors can be safely added.
2. **Compute bag size:** Let `max_features_per_prompt` be this remainder divided by average tokens per feature description (~10–15 tokens).  
   Example: If remaining budget ≈ 1500 tokens → `max_features_per_prompt ≈ 100`.  
3. **Select ratio:** Set bagging ratio `ρ = min(1, max_features_per_prompt / d)`.  
   - For `d = 120` → `ρ ≈ 0.8`, meaning we can retain most features without bagging.
   - For `d = 300` → `ρ ≈ 0.33`, so we randomly keep about one third of columns per trial.
4. **Randomize each trial’s selection** so that across all ensembles most columns appear at least once.

### Impact on Performance

Because each trial only sees a subset of columns, any single rule set may miss relationships involving omitted attributes; however, *averaging across ensembles* restores coverage—rules derived from disparate bags complement each other. Empirically this strategy mitigates performance loss that would otherwise arise from forced truncation or omission of important columns.

## Consolidated Practical Checklist

When configuring FeatLLM for a new low‑shot tabular problem:

1. **Pick base hyper‑parameters**
   - Set `R = 10` rules per class.
   - Start with `T = 15` ensembles.
2. **Adjust for resource constraints**
   - Reduce `T` gradually (down to ~5) if API cost or latency is prohibitive; monitor validation AUROC.
   - If prompt length threatens token limits, decrease `R` toward eight or apply feature bagging with ratio `ρ` as described above.
3. **Fine‑tune sampling parameters**
   - Use temperature `= 0.5`; modify only ±0.1 if parsing stability or diversity issues emerge.
   - Keep top‑\(p = 1` unless you have strong reasons to prune low-probability tokens.
4. **Validate**
   - Run cross‑validation on your few-shot splits; plot AUROC versus `T` and versus `R` if possible—these curves generally mirror those published.
   - Check parsing success rate; if it falls below ~95 %, consider lowering temperature or simplifying rule format prompts.
5. **Deploy**
   - After training linear weights \(\mathbf{w}_k\), cache generated binary features; at inference time you only need to evaluate those simple logical conditions—no further LLM calls are required.
   - Measure end‑to‑end latency; it should be comparable to traditional models like logistic regression because prediction reduces to dot products over binary vectors.

By following these empirically grounded guidelines—derived directly from FeatLLM’s sensitivity analyses—practitioners can harness large language models as powerful feature engineers while keeping inference fast, cost‑effective, and robust even when labeled data are scarce and tables are high dimensional.
