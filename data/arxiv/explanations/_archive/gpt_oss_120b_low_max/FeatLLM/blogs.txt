# How LLMs Can Be Turned Into Feature Engineers for Tabular Data  

Large language models (LLMs) have become the go‑to tool for “few‑shot” problems: give them a brief task description and a handful of examples, and they can often produce reasonable answers without any extra training.  While this capability has been exploited for many domains, applying LLMs directly to tabular prediction tasks still faces two serious hurdles:

1. **High inference cost** – every new sample has to be sent through the LLM, which is expensive both in latency and API budget.  
2. **Prompt‑size limits** – as the number of columns grows, serializing an entire table into a text prompt quickly exceeds the model’s context window, degrading performance.

The recent **FeatLLM** framework flips the script. Instead of asking the LLM to predict each row, it asks the LLM to **engineer features** once, offline. Those features are then fed into a tiny, inexpensive downstream model (e.g., a linear classifier) that can run at production speed with negligible cost. Below is a walkthrough of how FeatLLM works, why it sidesteps the above problems, and what performance gains we can actually expect.

---

## 1. From Prediction to Feature Generation  

### 1.1 The Core Idea  
FeatLLM treats the LLM as an expert analyst that can read a few labeled examples, understand the problem description, and **output human‑readable rules** (e.g., “if Age > 60 AND Cholesterol > 200 then class = Positive”). Each rule becomes a *binary* feature: 1 if the rule holds for a given row, 0 otherwise.

Once we have this set of rule‑based features we train a **simple linear model** (no bias term) on top of them:

\[
\text{logit}_k = \max(\mathbf{w}_k,0)\cdot\mathbf{z}_k,\qquad 
\mathbf{p}= \text{Softmax}(\text{logit}_1,\dots,\text{logit}_c),
\]

where \(\mathbf{z}_k\in\{0,1\}^R\) is the vector of binary rule‑features for class \(k\), and \(\mathbf{w}_k\) are non‑negative weights learned from the few labelled rows. Because the downstream model is only a handful of parameters, training is trivial even with 4–8 shots.

### 1.2 Why This Saves Inference Time  
* The LLM is queried **once per dataset**, not once per sample.  
* After rule extraction, inference reduces to a dot product and softmax—essentially a single matrix multiplication that runs on CPU in microseconds.  
* The approach works with any LLM that provides an API; no fine‑tuning or gradient access is required.

---

## 2. Prompt Design – Guiding the LLM to Write Good Rules  

FeatLLM uses a three‑part prompt that mimics how a domain expert would tackle a new tabular problem.

| Prompt Component | What It Contains | Why It Helps |
|------------------|------------------|--------------|
| **Basic Information** | Task description (e.g., “Predict chronic heart failure?”), natural‑language feature names + type definitions, and a few serialized examples (`f1 is 45. f2 is Male … Answer: Yes`). | Gives the LLM all necessary context without overwhelming it with raw rows. |
| **Reasoning Instruction** | A chain‑of‑thought style instruction that splits reasoning into two stages: (1) infer causal relationships using general knowledge only; (2) refine those relationships into concrete rules using the few examples. | Forces the model to draw on *prior* knowledge first, reducing spurious correlations that could arise from over‑fitting tiny datasets. |
| **Response Instruction** | Explicit format constraints for each rule (e.g., `"IF feature_name > value THEN class = X"`). Also specifies how many rules per class should be emitted (default = 10). | Guarantees machine‑parsable output; eliminates ambiguous natural language that would be hard to turn into code.|

By fixing the number of rules and making the format strict, FeatLLM avoids both under‑fitting (too few features) and exploding prompt sizes.

---

## 3. Turning Textual Rules Into Binary Features  

Even with tight formatting, LLM outputs may contain slight variations (“greater than” vs “>”). Rather than building a brittle parser, FeatLLM **re‑asks the LLM** to generate short Python snippets that implement each rule:

```python
def rule_7(row):
    return row["age"] > 60 and row["cholesterol"] > 200
```

These snippets are executed via Python’s `exec()` on every row, yielding a fast binary vector \(\mathbf{z}\). This self‑consistent use of the same LLM for parsing sidesteps noisy syntax while keeping everything fully automatic.

---

## 4. Robustness via Bagging & Ensembling  

Few‑shot settings are noisy by nature. FeatLLM introduces two complementary tricks:

1. **Feature bagging** – For each ensemble member it randomly samples a subset of columns (and optionally rows) before building the prompt. This reduces prompt length for high‑dimensional tables and forces diversity among generated rule sets.
2. **Ensembling across temperature & demo order** – By increasing the sampling temperature (default = 0.5) and shuffling the order of few‑shot examples we obtain multiple plausible rule collections. The final prediction averages the softmax outputs from all members:

\[
\bar{\mathbf{p}} = \frac{1}{T}\sum_{t=1}^{T}\mathbf{p}^{(t)}.
\]

Empirically, around **20 ensemble members** strike a good balance between performance gains and API cost.

---

## 5. Empirical Highlights  

- Tested on **13 diverse classification datasets**, including classic UCI benchmarks (Adult, Credit‑g) and newer or synthetic sets not seen during LLM pretraining.
- In **4‑shot experiments**, FeatLLM’s AUC matched or surpassed conventional tabular models that required **32 shots**, demonstrating strong data efficiency.
- Compared to other LLM‑based baselines (In‑context learning, TABLET, TabLLM), FeatLLM achieved an average improvement of **~10 % AUC**, especially on datasets with > 100 columns where prompt size previously broke those methods.
- Inference latency was comparable to Logistic Regression—orders of magnitude faster than sending each row through an LLM.
- Ablation studies showed that removing any component (reasoning step, feature description, weight tuning, ensembling) consistently hurts performance; weight tuning becomes especially valuable when more shots are available.

---

## 6. When Might FeatLLM Struggle?  

- **Highly non‑rule‑like patterns**: If discriminative information lives in complex nonlinear interactions rather than simple thresholds or logical clauses, binary rules may capture only part of the signal.
- **Noisy or mislabeled few‑shots**: The initial reasoning stage relies on correct examples; severely corrupted labels could propagate errors into generated rules.
- **Very large label spaces**: Generating ten high‑quality rules per class becomes costly when \(c\) is large; current work focuses on binary or modest multi‑class settings.

Future directions include richer feature constructors (e.g., learned embeddings from code generation) and tighter integration with interpretability tools.

---

## 7. Bottom Line  

FeatLLM shows that we don’t need to treat LLMs as black‑box predictors for every row in a table. By prompting them *once* to articulate domain knowledge as explicit decision rules, we obtain:

| Benefit | Traditional LLM Prediction | FeatLLM Feature Engineering |
|---------|----------------------------|------------------------------|
| **Inference cost** | High (API call per sample) | Low (linear model only) |
| **Prompt size limitation** | Severe when \(d\) large | Mitigated by bagging & fixed rule count |
| **Interpretability** | Minimal (raw logits) | High – each binary feature corresponds to an understandable rule |
| **Performance in low‑shot regime** | Variable; often worse on many columns | Consistently top‑ranked across 13 datasets |

If you’re working with tabular data where labeling is expensive—think medical records or financial risk lists—FeatLLM offers a practical way to harvest an LLM’s world knowledge without blowing up your compute budget.

---

# From Rules to Numbers: Turning Natural‑Language Conditions into Machine‑Learning Features  

## Introduction  

Tabular data is everywhere—from credit‑risk tables in finance to patient records in healthcare. Traditionally, getting good performance from such data requires careful feature engineering or heavyweight models that need a lot of labeled examples. A recent paper, **“Large Language Models Can Automatically Engineer Features for Few‑Shot Tabular Learning”**, proposes a clever workaround: let a Large Language Model (LLM) act as a *feature engineer* instead of as the final predictor.  

The core idea behind **FeatLLM** is to prompt an LLM to generate **human‑readable logical rules** (e.g., “Age > 65 AND Cholesterol > 200”) that describe each class, then convert those rules into **binary features** (0/1 flags) that a simple linear model can consume. This two‑step prompting strategy sidesteps the expensive per‑sample LLM inference used by earlier approaches, while still harnessing the LLM’s world knowledge.  

Below we walk through how FeatLLM extracts rules, parses them into executable code, and finally turns them into numbers for a downstream linear classifier.

## The Two‑Step Prompting Strategy  

### 1️⃣ Step One – “What matters?”  
The first prompt segment asks the LLM to reason **without looking at the few training examples**. It receives:

* A concise task description (e.g., “Predict whether a patient has chronic heart failure.”)  
* Natural‑language definitions of each column (including data type and optional domain knowledge)  
* No specific labels yet—just the problem statement.  

The model is encouraged to list *causal tendencies* or *important feature relationships* based purely on its pre‑training knowledge. This step forces the LLM to draw on real‑world facts (“older people have higher heart‑failure risk”) rather than spurious patterns that might appear in a tiny training set.

### 2️⃣ Step Two – “What rules capture the classes?”  
Next, we feed the same prompt with **few‑shot demonstrations**—a handful of serialized examples like:

```
age is 72. cholesterol is 210. blood_pressure is 140. Answer: Yes
age is 45. cholesterol is 180. blood_pressure is 120. Answer: No
```

Now the LLM combines its prior knowledge (from step one) with these concrete samples to output a **fixed number of logical rules per class** (the paper uses ten). The rules are expressed in plain English, but with a strict syntax that makes later parsing reliable (e.g., “age > 65 AND cholesterol > 200”).

The two‑step design has two benefits:

1. **Noise reduction:** By separating “what matters” from “what specific patterns exist,” the LLM is less likely to latch onto irrelevant columns in the few examples.  
2. **Prompt size control:** Only the rule list (a handful of short sentences) needs to be retained for later processing, avoiding overflow of the LLM’s context window.

## From Textual Rules to Executable Code  

Even with a well‑structured rule list, natural language can be noisy—LLMs sometimes write “greater than” instead of “>”, or add extra words. Manually writing parsers for every possible phrasing would be brittle.

FeatLLM solves this by *asking the LLM again*—this time as a code generator:

1. **Compose a second prompt** that includes:  
   * The original rule sentences  
   * A brief function skeleton (e.g., `def rule_age_gt_65(row):`)  
   * Explicit instructions: “Translate each rule into Python boolean expressions using column names `age`, `cholesterol`, …”.  

2. **Run the LLM’s response** through Python’s `exec()` function, which dynamically builds a set of functions that each return `True`/`False` for a given row.

Because the LLM has been trained on massive code corpora, it can handle variations like “greater than” → `>`, “is not” → `!=`, etc., producing clean, runnable code without hand‑crafted parsers.

## Building Binary Features  

Once we have a library of rule functions, constructing features is straightforward:

```python
def apply_rules(row):
    return [int(rule(row)) for rule in rule_functions]   # binary vector per row
```

For each sample we obtain a **binary vector** whose length equals the total number of extracted rules (e.g., 10 rules × 3 classes = 30 dimensions). Each entry tells us whether that sample satisfies a particular condition.

These binary features serve two purposes:

* They embed **human‑interpretable knowledge** (the rule itself can be read back by a domain expert).  
* They provide an *informative representation* that works well even when only a handful of labeled rows are available.

## Linear Model on Top of Rule Features  

With binary features in hand, FeatLLM fits an ultra‑lightweight model—a bias‑free linear classifier with non‑negative weights:

\[
\text{logit}_k = \max(\mathbf{w}_k,0) \cdot \mathbf{z}_k ,\qquad 
\mathbf{p} = \text{softmax}([\text{logit}_1,\dots,\text{logit}_c])
\]

where:

* \(\mathbf{z}_k\) is the binary vector for class \(k\).  
* \(\mathbf{w}_k\) are learned weights (one per rule).  

Training this model on the few labeled rows is cheap (a few gradient steps), yet it allows the system to **learn which rules matter most** for the target task. Because weights are forced positive, any rule can only increase rather than decrease class likelihood—mirroring how an expert would trust only supportive evidence.

## Ensembles & Bagging: Boosting Robustness  

LLM outputs are stochastic; different runs may produce slightly different rule sets. FeatLLM turns this variability into an advantage by:

1. **Repeating the whole pipeline** (prompt → rules → code → binary features) multiple times with different random seeds and shuffled few‑shot examples.  
2. **Bagging**: for each trial it randomly selects a subset of columns or instances before prompting, keeping prompts short enough for large tables.  
3. **Averaging predictions** across all trials (the ensemble).

The ensemble mitigates occasional bad rules and helps cover more columns overall—especially useful when dealing with datasets that have more features than fit in one prompt.

## Why This Matters  

| Property | Traditional LLM‑as‑Predictor | FeatLLM (LLM‑as‑Feature Engineer) |
|----------|------------------------------|-----------------------------------|
| Inference cost per sample | One full LLM call ⇒ high latency & API bills | One linear dot product ⇒ negligible |
| Need for fine‑tuning | Often required for good accuracy | No fine‑tuning; only lightweight linear training |
| Prompt length limitation | Serialized rows + column names can exceed token limits | Only need rule list + column descriptions |
| Interpretability | Black‑box output | Explicit logical conditions readable by humans |
| Robustness to spurious columns | Vulnerable; LLM may latch onto irrelevant data | Reasoning step filters out unrelated features |

In experiments across 13 diverse tabular benchmarks, FeatLLM achieved an average **10 % AUC gain** over other few‑shot LLM baselines and matched conventional models that used eight times more labeled data.

## Takeaways  

* **Two‑step prompting** lets an LLM separate prior knowledge from data‐driven cues, producing cleaner, more relevant rules.  
* Leveraging the same LLM as a *code generator* sidesteps fragile text parsing and yields ready‑to‑run boolean functions.  
* Converting natural‑language conditions into binary features creates an interpretable bridge between language models and classical ML pipelines.  
* Simple linear models plus ensemble bagging are enough to harvest most of the performance benefit while keeping inference cheap and scalable.

If you work with tabular data where labels are scarce but you have access to strong LLM APIs, consider swapping heavyweight end‑to‑end LLM inference for this **rule‑first, number‑second** approach. It delivers strong predictive power, low latency, and human‐readable insights—all hallmarks of practical machine learning systems.



# Bagging, Ensembles, and the Fight Against Spurious Correlations in Low‑Shot Tabular Learning

## Why Few‑Shot Tabular Learning Needs a New Approach  

Tabular data—think spreadsheets of medical records, credit applications, or sensor logs—are everywhere in industry.  However, collecting a large, cleanly labeled dataset can be costly or even impossible.  In the **few‑shot** regime (often fewer than 10 labeled examples per class) traditional machine‑learning models start to overfit, and clever tricks are required to inject domain knowledge without hand‑crafting features.

Enter **large language models (LLMs)**.  Their massive pre‑training on text gives them a surprising amount of world knowledge that can be harnessed as a form of prior.  Early LLM‑based tabular methods fed every test sample through the LLM at inference time (in‑context learning or lightweight fine‑tuning).  While this works for tiny tables, it becomes prohibitively slow for real‑world workloads and breaks down when the number of columns exceeds the model’s context window.

**FeatLLM** takes a different route: instead of using the LLM as a black‑box predictor, it asks the LLM to **engineer features**—specifically, to output logical rules that capture the relationship between columns and the target class.  Those rules become binary features that feed into a light downstream model (a non‑negative linear classifier).  The key to making this pipeline robust in low‑shot settings is **bagging and ensembling**, which also act as a shield against spurious correlations.

Below we unpack how FeatLLM’s ensemble machinery works, why it matters for high‑dimensional tables, and how it mitigates noisy or irrelevant columns.

---

## From Rules to Binary Features  

The FeatLLM pipeline consists of three stages:

1. **Prompt Design** – The LLM receives a carefully crafted prompt that includes:
   * A natural‑language task description (e.g., “Does this patient have chronic heart failure?”).
   * Feature names together with brief definitions.
   * A handful of few‑shot examples serialized as text.

2. **Rule Extraction** – Using a two‑step chain‑of‑thought style reasoning, the LLM first hypothesizes which columns are likely relevant (based on its world knowledge), then derives a fixed set of logical rules (e.g., “age > 65 AND cholesterol > 200”) that separate each class.

3. **Feature Generation** – Those textual rules are parsed into executable Python code (the LLM itself writes the code).  Running the code on every row yields a binary vector **z** where each entry tells us whether the rule fires for that sample.

At this point we have transformed the original high‑dimensional table into a compact set of binary “expert” features.  But one round of rule generation is not enough to guarantee robustness—especially when we only have a few labeled points.

---

## Bagging: Random Subsets of Columns and Samples  

The classic ensemble idea behind bagging (bootstrap aggregating) is simple: train multiple weak learners on different random subsets of data and then average their predictions.  FeatLLM adapts this concept in two ways:

| What is bagged? | Why bag? |
|----------------|----------|
| **Features (columns)** | Large tables often contain dozens or hundreds of attributes.  Feeding all column definitions into a single prompt may exceed the LLM’s context window or force the model to consider irrelevant fields.  By randomly selecting a subset of columns for each query, we keep prompts short enough for any LLM and encourage diversity among the generated rule sets. |
| **Training examples** | The order in which few‑shot demonstrations appear can bias LLM output.  Randomly shuffling (or even sampling) a subset of the available labeled rows before each query produces slightly different reasoning paths, again increasing diversity. |

Each bagged query yields its own rule set (typically 10 rules per class).  Because each query sees only part of the feature space, any single rule set may miss some important relationships; however, across many bags we expect every informative column to appear in at least some queries.

---

## Ensembling: Averaging Over Many Rule Sets  

After we have **T** bagged runs (the paper uses `T = 20`), we end up with `T` independent binary feature matrices `Z^{(t)}` and corresponding weight vectors `w^{(t)}` learned from the few labeled examples via a simple non‑negative linear model:

\[
\text{logit}_{k}^{(t)} = \max(w^{(t)}_k,0) \cdot Z^{(t)}_k,
\qquad
p^{(t)} = \operatorname{Softmax}(\text{logit}^{(t)}).
\]

The final class probability is just the average across all ensembles:

\[
\hat p = \frac{1}{T}\sum_{t=1}^{T} p^{(t)} .
\]

Two properties make this averaging particularly powerful in low‑shot settings:

1. **Self‑Consistency Filtering** – If a rule is truly informative, it will appear in many bagged queries and receive consistently high weights across runs.  Noisy or hallucinated rules that only appear once get diluted by the majority vote.

2. **Robustness to Spurious Correlations** – Suppose an irrelevant column accidentally correlates with the label in our tiny training set (a classic spurious correlation).  Only those bagged runs that happen to include that column may generate rules based on it; other runs ignore it entirely.  When we average, the impact of that single misleading rule drops dramatically, often to near zero.

The paper’s experiments on the *Heart* dataset illustrate this effect: as increasingly many unrelated columns from another dataset were appended, traditional baselines (Logistic Regression, XGBoost) rapidly lost performance, while FeatLLM’s AUC degraded only marginally.

---

## Handling High‑Dimensional Tables  

Beyond spurious correlation resistance, bagging directly solves another practical pain point: **prompt length limits**. Modern LLM APIs typically allow around 8 k tokens per request; feeding a table with > 100 features plus examples can easily exceed this ceiling. By randomly selecting—say—a maximum of `m` columns per bag (the paper adjusts `m` automatically based on token budget), FeatLLM ensures every query stays comfortably within limits while still exploring the full feature space across ensembles.

This approach also reduces computation at inference time. Once all rule sets have been generated (a one‑off cost requiring only ~30 API calls for typical configurations), downstream prediction simply evaluates binary features and performs a dot product—orders of magnitude faster than sending each test row through an LLM.

---

## What Happens When Things Go Wrong?  

No method is perfect, and FeatLLM’s reliance on textual rule generation can still produce occasional mistakes:

- **Parsing Noise** – The LLM might phrase “greater than” instead of “>”, causing naïve parsers to fail. FeatLLM sidesteps this by feeding the raw rule back into the LLM with a “write Python code” instruction; its code generation handles synonyms gracefully.
- **Overfitting to Few Shots** – With extremely few labels (e.g., two per class), even bagged ensembles may latch onto random patterns. The authors observed that weight tuning becomes more important as shot count rises; when shots are minimal they rely more heavily on prior knowledge embedded in the LLM’s reasoning instructions.

Nevertheless, empirical results across 13 diverse datasets show an average gain of about **10 % AUC** over other few‑shot methods such as TabLLM and STUNT, confirming that bagging + ensembling delivers tangible robustness improvements.

---

## Takeaways for Practitioners  

1. **Treat LLMs as Feature Engineers** – Instead of using an LLM as an expensive end‑to‑end predictor, ask it to emit human‑readable decision rules.
2. **Randomize Inputs** – Bagging over columns and shuffling few‑shot examples injects necessary diversity without extra labeling effort.
3. **Ensemble Early; Train Light Later** – A cheap linear model on binary rule features can be trained in seconds; most heavy lifting happens during the one‑off rule extraction phase.
4. **Guard Against Spurious Correlations** – Averaging many weak learners dramatically reduces reliance on any single noisy rule—a crucial property when data are scarce.
5. **Scalable to Large Tables** – By controlling how many columns each prompt sees, you stay within API token limits while still covering all attributes across ensembles.

In low‑shot situations where labeling budgets are tight and tables are high dimensional, FeatLLM’s blend of **bagging**, **ensembling**, and **LLM‑driven rule generation** offers a pragmatic middle ground: harness powerful world knowledge without incurring prohibitive inference costs, and do so with built‑in protection against noisy or irrelevant columns.



# Benchmarking FeatLLM: Few‑Shot Performance Across 13 Real‑World Datasets  

Few‑shot learning for tabular data has long been a tough nut to crack. Traditional models such as logistic regression or gradient‑boosted trees need dozens, sometimes hundreds, of labeled examples before they become reliable. Recent research has shown that large language models (LLMs) can inject domain knowledge into the learning pipeline, but most existing LLM‑based methods still require an LLM call for **every** test sample, which kills latency and raises inference costs.

The paper *Large Language Models Can Automatically Engineer Features for Few‑Shot Tabular Learning* introduces **FeatLLM**, a framework that flips the script: instead of using an LLM as a black‑box predictor, it asks the LLM to **engineer new features** (binary rules) from a handful of demonstrations. Those rules are then fed into a tiny linear model that can be trained once and used for **all** downstream samples – no more per‑sample LLM calls.  

Below we walk through the experimental evaluation that puts FeatLLM head‑to‑head with both classic tabular learners and other LLM‑augmented approaches, across 13 diverse real‑world datasets.

---

## The experimental set‑up  

| Category | Datasets (13 total) | Task | Typical #features |
|----------|---------------------|------|-------------------|
| Classic UCI / Kaggle | Adult, Bank, Blood, Car, Communities, Credit‑g, Diabetes, Heart, Myocardial | Binary / multi‑class classification | 5 – 120 |
| Newer / synthetic | Cultivars, NHANES, Sequence‑type, Solution‑mix | Binary / multi‑class classification | 8 – 30 (synthetic) |

All experiments follow a **k‑shot** protocol (k = 2, 4, 8). For each k the method sees only k randomly chosen labeled rows; the rest of the dataset is used only for evaluation.  

### Baselines  

1. **Traditional ML** – Logistic Regression (LogReg), XGBoost, Random Forest.  
2. **Semi‑supervised / pre‑training** – SCARF and STUNT (use unlabeled data).  
3. **Pure LLM inference** – In‑context learning (plain prompts), TABLET (adds prototype rules), TabLLM (parameter‑efficient fine‑tuning).  
4. **Neural tabular priors** – TabPFN (pre‑trained Bayesian NN on synthetic distributions).  

All LLM baselines use GPT‑3.5 (or T0 for TabLLM) in the same way as FeatLLM; the only difference is *how* the model is queried.

---

## Performance results: AUC gains at a glance  

The key metric reported in the paper is the area under the ROC curve (AUC). Across all 13 datasets and all low‑shot settings:

| Method | Avg. AUC (k = 4) |
|--------|-------------------|
| LogReg | 0.78 |
| XGBoost | 0.81 |
| Random Forest | 0.80 |
| SCARF | 0.83 |
| STUNT | 0.84 |
| TabPFN | 0.85 |
| In‑context | 0.78 |
| TABLET | 0.80 |
| TabLLM | 0.82 |
| **FeatLLM** (ours) | **0.90** |

That translates to roughly a **10 % absolute AUC improvement** over the strongest non‑LLM baseline (TabPFN) and an even larger margin over plain LLM prompting methods. Importantly, FeatLLM achieves this with just **4 shots**, whereas conventional learners needed **32 shots** to reach comparable performance (see Figure 2 in the paper).

A few observations from the detailed tables:

* **Large feature spaces:** Datasets like *Communities* (≈115 features) and *Myocardial* stress prompt length limits of many LLM methods; FeatLLM’s bagging + ensemble strategy keeps prompts short and still extracts useful rules.
* **Synthetic data:** On *Sequence-type* and *Solution-mix*, which could not have been memorised by GPT‑3.5, FeatLLM still outperforms all baselines, suggesting genuine reasoning rather than memorisation.
* **Recent UCI releases:** *Cultivars* and *NHANES* were added after September 2023—well after GPT‑3.5’s training cut‑off—yet FeatLLM still extracts high‐quality rules thanks to its “prior knowledge + few‐shot” reasoning pipeline.

---

## Why FeatLLM shines  

### 1️⃣ Feature engineering via reasoning  
The prompt is split into three parts: basic task/feature description, a two‑step reasoning instruction (first infer causal relations from world knowledge, then refine using the few examples), and a strict response format for rule output. This forces the LLM to ignore irrelevant columns and produce concise “if … then …” conditions.

### 2️⃣ Binary rule features + lightweight linear model  
Each rule becomes a binary column (“does this record satisfy rule r?”). A non‑negative linear model learns a weight per rule, effectively ranking their importance without overfitting—crucial when only a handful of labels are available.

### 3️⃣ Bagging & ensembling for robustness & prompt limits  
For each ensemble member we:
* Randomly shuffle demonstration order,
* Sample a subset of original features,
* Raise temperature to diversify rule generation.

The resulting rule sets are combined by averaging softmax logits. This mitigates two common pitfalls:
* **Noisy rules:** Wrong rules from one trial are drowned out by correct ones from other trials.
* **Prompt overflow:** By bagging features we keep each query under the LLM’s context window even for high‑dimensional tables.

### 4️⃣ No per‑sample LLM calls at inference  
After the initial API queries (≈30 calls total for k = 4), downstream prediction boils down to a dot product—orders of magnitude faster than in‑context or TABLET which need an LLM call per test row.

---

## Ablation insights  

The authors stripped away four components to see how performance suffers:

| Ablation | ΔAUC (average) |
|----------|----------------|
| No weight tuning (`-Tuning`) | -0.04 |
| No ensembling (`-Ensemble`) | -0.07 |
| No feature descriptions (`-Description`) | -0.05 |
| No first reasoning step (`-Reasoning`) | -0.06 |

Weight tuning matters more when more shots are available; reasoning instructions are crucial in ultra low‑shot regimes because they let the LLM lean on external knowledge rather than spurious correlations in tiny data.

---

## Training & inference cost  

On *Adult* with 16 training shots:

| Method | Training time (GPU hrs) | Inference time per 10k rows |
|--------|------------------------|------------------------------|
| LogReg / XGBoost / RF | <0.1 hrs (CPU) | ≈0.02 s |
| In‑context / TABLET / TabLLM | 0.2–0.5 hrs (GPU + API) | ≈12–18 s |
| **FeatLLM** | ~0.2 hrs (API calls + tiny linear training) | ≈0.03 s |

Thus FeatLLM matches classic models’ latency while delivering dramatically higher accuracy in low‐shot scenarios.

---

## Takeaway  

FeatLLM proves that an LLM does not have to be a heavyweight predictor for every row of data; it can act as an *expert feature engineer*. By extracting rule‐based binary features in a single batch of prompts and coupling them with a tiny linear learner, FeatLLM attains:

* **~10 % absolute AUC uplift** over state‐of‐the‐art baselines,
* Robustness against spurious columns,
* Scalable inference comparable to traditional ML pipelines,
* Compatibility with any API‑only LLM (no fine‐tuning required).

For practitioners dealing with scarce labels—think medical diagnosis, credit risk assessment, or any domain where labeling is costly—FeatLLM offers a practical bridge between rich linguistic priors and fast, interpretable tabular predictions.

# Practical Guide: Deploying FeatLLM with Only API Access to GPT‑3.5  

Few‑shot tabular learning has traditionally required either a lot of labeled data or heavyweight fine‑tuning of large models. **FeatLLM** flips the script: it treats a large language model (LLM) as a *feature engineer* rather than an end‑to‑end predictor. The result is a lightweight pipeline that can be run using only the public inference API of GPT‑3.5 (or any comparable LLM), with no GPU‑intensive training steps.  

In this post we walk through the entire workflow—from crafting the prompt that coax the LLM into generating useful rules, to turning those rules into binary features, training a tiny linear model, and finally using an ensemble of such “weak learners” for robust predictions. All steps are designed to run on a standard laptop or a modest cloud instance; the only external dependency is the LLM’s API.

---

## 1. Overview of the FeatLLM Pipeline  

| Stage | What happens? | Key artifact |
|------|----------------|--------------|
| **Prompt construction** | Provide task description, feature definitions, and a handful of labeled examples. | Text prompt sent to GPT‑3.5 |
| **Rule extraction** | GPT‑3.5 returns a fixed set of logical conditions (rules) per class. | Human‑readable rule list |
| **Code generation & parsing** | A second LLM call turns each rule into executable Python code that evaluates the rule on a row. | `apply_rules(df)` function |
| **Feature creation** | Apply the code to the whole dataset → binary matrix **Z** (rows × rules). | New feature matrix |
| **Linear weight tuning** | Fit a non‑negative linear model \(\mathbf{w}\) on the few labeled rows (cross‑entropy loss). | Weight vector per class |
| **Ensemble voting** | Repeat the whole process *T* times (different random seeds, bagged subsets of columns/rows). Average class probabilities across ensembles. | Final prediction |

The heavy lifting—reasoning about which columns matter and how they interact—is done once per *ensemble member* via the LLM API. At inference time we only evaluate cheap binary features and dot‑product with learned weights.

---

## 2. Preparing Your Data  

1. **Tabular format** – A pandas `DataFrame` where each column has a clear name (`f1`, `f2`, …) and an optional textual definition (e.g., “`age` – patient age in years”).  
2. **Few‑shot labels** – Choose \(k\) rows (commonly 4–8) that cover all target classes. These will be serialized into the prompt as demonstrations.  
3. **Feature metadata** – For every column, write a concise description: type (numeric, categorical, boolean) and any domain hint you think might help the LLM (“older patients tend to have higher risk”).  

> **Tip:** Even if you lack perfect definitions, providing *some* natural language cue dramatically improves rule quality, as shown in the paper’s ablation study.

---

## 3. Prompt Design for Rule Extraction  

The prompt is split into three logical blocks; keep the same structure for every LLM call.

### 3.1 Basic Information  

```text
Task: Predict whether a patient will develop chronic heart failure.
Labels: Yes / No
Features:
- age: numeric, patient age in years.
- cholesterol: numeric, blood cholesterol level mg/dL.
- smoker: categorical {yes, no}.
- ejection_fraction: numeric, % of blood pumped per heartbeat.
...
Examples:
Sample 1: age is 67. cholesterol is 210. smoker is yes. ejection_fraction is 30.
Answer: Yes

Sample 2: age is 45. cholesterol is 180. smoker is no. ejection_fraction is 55.
Answer: No
```

*Serialisation follows*: `"f_j is <value>. ... Answer: <label>"`. Keep each example on its own line to avoid hitting token limits.

### 3.2 Reasoning Instruction  

```text
Step 1: Based on medical knowledge, describe which features are generally associated with heart failure risk.

Step 2: Using the above knowledge together with the examples, produce exactly ten logical rules that indicate a "Yes" prediction and ten rules for a "No" prediction.
```

The two‑step approach forces the model to pull out prior knowledge first (e.g., “higher age and lower ejection fraction increase risk”) before grounding it in the concrete demos.

### 3.3 Response Instruction  

```text
For each class output rules in this format:
Rule #i: IF <feature> <operator> <value> [AND <feature> <operator> <value> ...] THEN class = <Yes/No>
Provide one rule per line.
```

By fixing the formatting we make downstream parsing deterministic even when GPT occasionally varies phrasing (“greater than” vs `>`).

## 4. Calling GPT‑3.5 and Capturing Rules  

```python
import openai, json, textwrap

def query_gpt(prompt):
    response = openai.ChatCompletion.create(
        model="gpt-3.5-turbo-0613",
        messages=[{"role":"user","content":prompt}],
        temperature=0.5,
        max_tokens=1500,
    )
    return response["choices"][0]["message"]["content"]
```

Set `temperature=0.5` to encourage some diversity across ensemble members while keeping outputs sensible.

Store the raw text; later we’ll feed it back to GPT for code generation.

---

## 5. Turning Natural‑Language Rules into Executable Code  

Parsing free text can be brittle; instead we let GPT do the heavy parsing:

```python
code_prompt = f"""
You are given a list of logical rules in natural language.

Rules:
{rules_text}

Write a Python function `apply_rules(df)` that returns a DataFrame `Z`
where each column corresponds to one rule (binary 0/1 indicating if
the rule holds for that row). Preserve column names as "rule_i".
"""
code = query_gpt(code_prompt)
exec(code)   # defines apply_rules in the current namespace
Z = apply_rules(df)   # df = full dataset (including train + test)
```

Because GPT was trained on code, it reliably converts variations like “greater than” → `>` or “between X and Y” → appropriate logical combination.

---

## 6. Training the Linear Weight Model  

We now have a binary feature matrix \(Z \in \{0,1\}^{N \times R}\), where \(R =\) number of rules per class \(\times\) number of classes (typically \(10 \times C\)). The downstream model is extremely simple:

\[
\text{logit}_k = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k,\qquad
\mathbf{p}= \text{softmax}([\text{logit}_1,\dots,\text{logit}_C]).
\]

Implementation (PyTorch or NumPy):

```python
import torch, torch.nn.functional as F

Z_train = torch.tensor(Z_train.values, dtype=torch.float32)
y_train = torch.tensor(y_train.values)   # integer class ids

w = torch.nn.Parameter(torch.zeros(R))   # one weight vector per class handled together

optimizer = torch.optim.Adam([w], lr=0.01)

for epoch in range(200):
    optimizer.zero_grad()
    logits = torch.relu(w).unsqueeze(0) * Z_train   # broadcasting over classes
    logits = logits.sum(dim=1)                     # sum over rules per class
    loss = F.cross_entropy(logits.unsqueeze(0), y_train)
    loss.backward()
    optimizer.step()
```

Because we only have a few labeled rows, early stopping via k‑fold cross validation works well; usually convergence is reached within dozens of epochs.

## 7. Bagging & Ensemble Construction  

A single rule set may miss some informative columns—especially when your dataset has > 100 features and exceeds the LLM’s context window. Mitigate this by:

1. **Feature bagging** – Randomly select a subset of columns (e.g., 30 % of total) before building the prompt.
2. **Instance bagging** – Randomly shuffle or subsample your few-shot examples; order matters for LLMs.
3. **Temperature boost** – Use `temperature=0.7` for some ensemble members to increase rule diversity.

Run steps 2–6 *T* times (the paper finds \(T=20\) sufficient). After training each linear model \(\mathbf{w}^{(t)}\), obtain class probabilities \(\mathbf{p}^{(t)}\) for every test row and average:

```python
final_prob = sum(p_t for p_t in prob_list) / T
pred_class = final_prob.argmax(axis=1)
```

The ensemble smooths out occasional mis‑generated rules and compensates for any spurious columns introduced by bagging.

## 8. Full End‑to‑End Script Skeleton  

```python
def featllm_pipeline(df, label_col, k_shot=4, n_ensembles=20,
                     rule_per_class=10, bag_fraction=0.3):
    # 1️⃣ Split few-shot training rows
    train_idx = stratified_sample(df[label_col], k_shot)
    df_train = df.iloc[train_idx]
    df_test  = df.drop(train_idx)

    ensemble_probs = []
    for t in range(n_ensembles):
        # 2️⃣ Random feature bagging
        cols_subset = np.random.choice(df.columns.drop(label_col),
                                       size=int(bag_fraction*len(df.columns)),
                                       replace=False)
        # add back label column for prompt generation
        cols_prompt = list(cols_subset) + [label_col]

        # 3️⃣ Build prompt with feature defs & few-shot examples
        prompt = build_prompt(df[cols_prompt], df_train)

        # 4️⃣ Query GPT‑3.5 → raw rules
        raw_rules = query_gpt(prompt)

        # 5️⃣ Generate parsing code and exec()
        parse_code = query_gpt(make_code_prompt(raw_rules))
        exec(parse_code)

        # 6️⃣ Apply to whole dataset → binary matrix Z
        Z_all = apply_rules(df[cols_subset])

        # split Z back into train / test portions
        Z_train = Z_all.iloc[train_idx]
        Z_test  = Z_all.drop(train_idx)

        # 7️⃣ Train linear weights on Z_train & few-shot labels
        w = train_linear(Z_train.values, df_train[label_col].values)

        # 8️⃣ Compute probabilities on test set
        logits_test = np.maximum(w,0) * Z_test.values   # broadcasting
        logits_test = logits_test.sum(axis=1)
        probs_test = softmax(logits_test, axis=1)
        ensemble_probs.append(probs_test)

    final_prob = np.mean(ensemble_probs, axis=0)
    return final_prob.argmax(axis=1), final_prob
```

Replace helper functions (`stratified_sample`, `build_prompt`, `make_code_prompt`, `train_linear`, `softmax`) with your own implementations—each mirrors the descriptions above.

## 9. Practical Considerations  

| Issue | Mitigation |
|------|------------|
| **Prompt length overflow** | Use feature bagging; keep each example concise; omit rarely used columns from prompt |
| **Noisy rule syntax** | Enforce response instruction; rely on second‑stage code generation rather than manual regex |
| **Spurious correlations** | The two‑step reasoning instruction dramatically reduces reliance on irrelevant columns; ensemble further dilutes any occasional misbehaving rule |
| **API cost** | Each ensemble member performs two calls (rule extraction + code generation). With \(T=20\), total calls ≈ 40 per dataset—a few cents on most commercial APIs |
| **Latency at inference time** | After preprocessing, prediction reduces to a dot product—microseconds per sample |

Empirically (see the original FeatLLM paper), this setup yields an average AUC gain of ~10 % over strong baselines such as TabLLM or STUNT while keeping inference costs comparable to classic Logistic Regression.

---

## 10. Closing Thoughts  

FeatLLM demonstrates that you don’t need giant GPU clusters or fine‑tuning pipelines to reap benefits from LLMs in tabular domains. By reframing LLMs as “knowledgeable analysts” that write down decision rules, we can:

* Leverage their world knowledge even with only a handful of labeled rows  
* Keep runtime cheap—no per‑sample LLM calls at deployment  
* Stay within API limits thanks to bagged prompts and deterministic parsing  

Give it a try on your next low‑shot classification problem—whether it’s predicting loan defaults, medical outcomes, or equipment failures—and you’ll likely see better performance with less engineering overhead than traditional few‑shot methods.

Happy modeling!
