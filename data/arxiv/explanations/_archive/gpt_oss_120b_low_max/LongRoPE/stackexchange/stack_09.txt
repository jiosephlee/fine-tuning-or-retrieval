\title{Stack Exchange of the Paper: "LongRoPE: Extending LLM Context Window Beyond 2 Million Tokens"}

### How do the authors evaluate passkey retrieval accuracy over million‑token contexts?
Question:
The passkey task places a five‑digit number randomly inside a document up to 2048k tokens. I’m unsure how they generate prompts, query lengths, and how they determine whether the model retrieved the correct passkey (e.g., exact match vs. fuzzy match). Also, what decoding settings (temperature, top‑p) are used that might affect retrieval?
Answer:
The paper evaluates the “passkey‑retrieval” task in exactly the same way that the original PassKey benchmark introduced by [Lu et al., 2024] does.  
For each evaluation run the authors generate a synthetic document that is **much longer than the model’s original 4 k token window** (up to the target length of 2 048 k tokens).  

**How the document and prompt are built**

1. **Passkey placement.**  
   A five‑digit decimal number (e.g. “27493”) is sampled uniformly at random from $ \{00000,\dots ,99999\} $. This passkey is then inserted at a random token index that is itself drawn uniformly from the interval $ [0,\,L] $, where $ L $ is the total length of the test document (the length varies from 4 k to 2 048 k tokens). The remainder of the document is filled with “irrelevant” text taken from the PG‑19/Proof‑Pile corpora; the authors simply concatenate those long passages and treat them as distractor material.

2. **Prompt template.**  
   The prompt that is fed to the model consists of two parts:  

   - a short instruction asking the model to output *the* passkey that is hidden somewhere in the following text, and  
   - the entire synthetic document (including the hidden number).  

   The exact wording of the instruction is given in the appendix of the paper, but it is essentially:  

   ```
   The following text contains a secret five‑digit passkey. 
   Please output only that passkey.
   <long document …>
   ```

   Because the instruction is fixed and very short, it does not consume a noticeable part of the context window even when $ L $ reaches millions of tokens.

3. **Decoding settings.**  
   To make sure that any error can be attributed to a failure to locate or remember the passkey rather than stochastic sampling, generation is performed **deterministically**: temperature = 0.0 and top‑p = 1.0 (i.e., greedy decoding). No beam search or sampling tricks are used.

**How correctness is measured**

After generation, the output string is stripped of whitespace and compared against the ground‑truth five‑digit number using an **exact string match**. A retrieval is counted as correct only if every digit matches; there is no fuzzy or partial credit. The reported “passkey retrieval accuracy” for a model at a given context length is therefore

$$
\text{Accuracy} = \frac{\#\text{exact matches}}{\#\text{runs}} .
$$

The authors repeat each experiment **10 times** for each context length (the paper says “10 iterations”) and report the average accuracy across those runs. Because each run uses a new random location for the passkey, this procedure faithfully measures whether a model can attend to information that may be far away (millions of tokens) from the prompt.

In summary, the evaluation protocol consists of:

* generate a long document (4 k–2 048 k tokens) with a randomly placed 5‑digit number,
* prepend a fixed “retrieve‑the‑passkey” instruction,
* decode with temperature = 0, top‑p = 1 (greedy),
* check whether the generated token sequence exactly equals the hidden number,
* average over ten independent random placements.

Under this strict setup, LongRoPE‑augmented LLaMA2 and Mistral achieve >90 % exact‑match accuracy across essentially all tested lengths, demonstrating that their extended positional embeddings indeed allow attention to propagate information across multi‑million‑token contexts.
