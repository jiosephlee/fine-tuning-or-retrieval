\title{Stack Exchange of the Paper: "LongRoPE: Extending LLM Context Window Beyond 2 Million Tokens"}

### How does LongRoPE handle dynamic inference lengths shorter than 8k?
Question:
During inference, the authors state that if the sequence length is less than 8k they "update RoPE with the searched rescale factors." Does this mean they switch to a different set of \(\lambda_i\) learned for short contexts, or do they simply truncate the existing factors? How is this switching implemented without recomputing embeddings for each request?
Answer:
In the LongRoPE paper the “short‑context recovery’’ step is a **second positional‑interpolation pass** that is carried out **after** the model has already been fine‑tuned for the very long window (256 k → 2048 k).  
During this pass the authors *search again* for a set of RoPE‑rescale factors that are better suited to a **much smaller** maximum length (4 k or 8 k). The search is exactly the same evolutionary procedure described in Section 3.2, except that the admissible range of the scaling parameters $\lambda_i$ is tightened (the upper bound is set to a value close to 1, because little interpolation is needed when the context is short).  

What the paper means by “if the sequence length is less than 8 k we **update RoPE with the searched rescale factors**’’ is therefore:

1. **Two distinct families of $\lambda_i$ vectors are stored** in the checkpoint:  
   * one vector $\{\lambda^{\text{long}}_i\}$ that was found for the 256 k / 2048 k extension (used for any input longer than 8 k), and  
   * another vector $\{\lambda^{\text{short}}_i\}$ that was found by a separate search specifically for 4 k–8 k windows.  

2. At inference time the model looks at the *actual* input length $L_{\text{in}}$.  
   * If $L_{\text{in}} \ge 8\,\text{k}$, it applies $\{\lambda^{\text{long}}_i\}$ (the “default’’ LongRoPE scaling).  
   * If $L_{\text{in}} < 8\,\text{k}$, it swaps to $\{\lambda^{\text{short}}_i\}$.  

3. The switch is **purely a lookup**; no new forward pass or embedding recomputation is required. The RoPE implementation already multiplies each rotary angle by a scalar factor that can be changed on‑the‑fly, so swapping $\lambda_i$ simply changes a small array of constants that are consulted when building the sinusoidal terms. Because all other model parameters remain unchanged, the overhead is negligible.

Thus, LongRoPE does **not** truncate or discard part of a single $\lambda_i$ vector; it keeps two pre‑computed, separately‑searched vectors—one optimized for very long contexts and one optimized for short contexts—and selects between them according to the current request length. This design preserves the original embeddings when they are needed (the first $\hat n$ tokens are left unchanged) while still benefiting from the non‑uniform scaling discovered by the evolutionary search, all without incurring any extra per‑request computation cost beyond a constant‑time array lookup.
