\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### How does exponential gating in sLSTM differ from standard sigmoid gating, and why is it necessary?
Question:
The paper introduces exponential activation functions for the input gate (always) and optionally for the forget gate in sLSTM (Equation (5)). I understand that sigmoid gates output values in \([0,1]\) while the exponential can produce arbitrarily large numbers. How exactly does this change the dynamics of the cell update, and what problem does it solve that sigmoid gating cannot? Also, how does the normalizer state \(n_t\) prevent the exponential gates from causing numerical overflow?
Answer:
In the original LSTM every gate is passed through a sigmoid  

\[
\sigma(x)=\frac{1}{1+e^{-x}}\in(0,1) .
\]

Consequently the input gate \(i_t\) can only *add* a fraction of the candidate
\(z_t\) to the cell and the forget gate \(f_t\) can only *attenuate* the previous
cell value by a factor between 0 and 1.  This works well when the cell is meant
to store information that should decay slowly, but it makes it impossible for
the network to *overwrite* a stored value with a much larger one in a single
step: the maximal contribution of the new input is bounded by 1.  In tasks such
as the Nearest‑Neighbour‑Search example (Section 4.1) the model must be able to
replace an old entry with a new, more similar one, even if the new entry is
much larger in magnitude.  With only sigmoid gates this revision can only be
done gradually over many time steps, which severely limits the expressive power
of the recurrent cell.

### What exponential gating changes

In sLSTM the input gate (and optionally the forget gate) is defined as  

\[
i_t = \exp(\tilde i_t), \qquad 
f_t = \sigma(\tilde f_t)\ \text{or}\ \exp(\tilde f_t),
\]

where \(\tilde i_t,\tilde f_t\) are ordinary affine projections of the current
input and previous hidden state.  Because \(\exp(\cdot)\) is unbounded, \(i_t\) can
take any positive value, not just a number in \([0,1]\).  The cell update

\[
c_t = f_t\,c_{t-1}+ i_t\,z_t
\]

therefore acquires two new behaviours:

1. **Unlimited write strength.**  When \(\tilde i_t\) is large and positive,
   \(i_t\) becomes huge and the new candidate \(z_t\) can dominate \(c_{t}\)
   instantly, effectively *re‑writing* whatever was stored before.  This solves
   the “cannot revise storage decisions’’ problem that standard LSTMs face.

2. **Flexible forgetting.**  If we also replace \(\sigma\) by \(\exp\) for the
   forget gate, \(f_t\) can be larger than one, which implements *amplification*
   of the previous cell rather than pure decay.  The model can therefore keep a
   value unchanged (\(f_t=1\)), attenuate it (\(0<f_t<1\)) or even boost it
   (\(f_t>1\)) depending on what is useful for the task.

Thus exponential gating gives the recurrent unit a richer set of dynamics:
the cell can both delete and *reinforce* information in a single time step,
something that sigmoid‑gated LSTMs cannot do without many successive updates.

### Why we need a normalizer state

The price of an unbounded gate is that both \(c_t\) and any downstream hidden
state could explode numerically.  The authors therefore introduce a **normalizer
state**

\[
n_t = f_t\,n_{t-1}+ i_t ,
\]

which accumulates exactly the same multiplicative factors that have been applied
to the cell content (but without the candidate data).  The hidden state is then

\[
h_t = o_t\,\tilde h_t,\qquad 
\tilde h_t = \frac{c_t}{n_t}.
\]

Dividing by \(n_t\) rescales the cell value so that its magnitude stays roughly
order‑one regardless of how large \(i_t\) or \(f_t\) become.  Intuitively,
\(n_t\) records “how much total weight’’ has been assigned to all contributions up
to time \(t\); by normalising with this weight we obtain a weighted average rather
than an ever‑growing sum.

### Stabilisation via the auxiliary state \(m_t\)

Even with division by \(n_t\), direct computation of \(\exp(\tilde i_t)\)
or \(\exp(\tilde f_t)\) may overflow if \(\tilde i_t,\tilde f_t > 700\)
(roughly the limit of double‑precision exponentiation).  To avoid this,
the paper follows Milakov (2018) and keeps a running log‑scale

```
m_t = max( log(f_t)+m_{t-1} , log(i_t) )
```

and then re‑expresses the gates as

```
i'_t = exp( log(i_t) - m_t )
f'_t = exp( log(f_t) + m_{t-1} - m_t )
```

Both \(i'_t\) and \(f'_t\) lie in \((0,1]\); they are simply rescaled versions of
the original exponential gates with exactly the same product  
\(i'_t f'_t = i_tf_f / e^{m_t}\).  Because all subsequent equations use only these
scaled gates, neither forward outputs nor gradients change (the paper proves this
in Appendix C).  Practically, we never evaluate an exponent larger than zero,
so overflow cannot happen.

### Summary

* Sigmoid gating limits each update to at most “add one copy’’ or “forget up to all’’,
  which prevents rapid revision of stored information.
* Exponential gating removes that bound: a single step can overwrite or amplify a cell arbitrarily.
* The normalizer state \(n_t\) turns the raw (potentially huge) cell sum into a weighted average, keeping hidden activations numerically stable.
* The stabiliser state \(m_t\) rewrites exponentials in log‑space so that no large exponentials are ever computed, guaranteeing that overflow never occurs while preserving exact dynamics.

These mechanisms together give sLSTM its ability to solve tasks that require fast,
large‑magnitude revisions of memory—something standard sigmoid‑gated LSTMs cannot do.

### What is the purpose of the stabilizer state \(m_t\) in Equation (6), and how does it guarantee that the gradients remain unchanged?
Question:
The authors define a stabilizer state \(m_t\) and then compute stabilized gates \(i'_t\) and \(f'_t\). They claim this does not alter the network output nor the loss gradients (Appendix A). Could someone walk through a concrete example or derivation showing why dividing by \(e^{m_t}\) leaves the forward and backward passes invariant?
Answer:
In the sLSTM the two gates that can become *exponential* are the input gate  

\[
i_t = \exp (\tilde i_t)
\qquad\text{and}\qquad 
f_t = \exp (\tilde f_t)\ \text{or}\ \sigma(\tilde f_t) .
\]

If we use the raw values \(i_t\) and \(f_t\) in the recurrences (4) and (5) we quickly run into overflow – the product of many exponentials can grow far beyond the range of a 32‑bit float.  
The paper therefore introduces a **stabiliser state**  

\[
m_t \;=\; \max\bigl(\,\log f_t + m_{t-1},\;\log i_t \bigr),
\tag{6}
\]

and defines **stabilised gates**

\[
i'_t = \exp\bigl(\log i_t - m_t\bigr)=\exp(\tilde i_t-m_t),
\qquad
f'_t = \exp\bigl(\log f_t + m_{t-1}-m_t\bigr).
\tag{7}
\]

At first sight it looks as if we have changed the gate values, but the two equations above are merely a *common multiplicative normalisation* that is applied **identically to every term that contains a gate**.  
Because the cell‑state and normaliser recurrences are linear in the gates, this normalisation cancels out.

---

### Forward‑pass invariance

The scalar cell state and normaliser evolve as  

\[
c_t   = f_t\,c_{t-1}+i_t\,z_t, \qquad   
n_t   = f_t\,n_{t-1}+i_t .
\tag{4}
\]

Replace \(f_t,i_t\) by their primed versions and insert the definitions (7):

\[
\begin{aligned}
c^{\prime}_t 
&= f'_t\,c^{\prime}_{t-1}+i'_t\,z_t  \\[2mm]
&= e^{\log f_t +m_{t-1}-m_{t}}c^{\prime}_{t-1}
   +e^{\log i_t-m_{t}}z_t .
\end{aligned}
\]

Factor out the common factor \(e^{-m_{t}}\):

\[
c^{\prime}_t = e^{-m_{t}}\Bigl( e^{\log f_t+m_{t-1}}c^{\prime}_{t-1}+e^{\log i_t}z_t \Bigr).
\tag{8}
\]

Now define a *scaled* cell state  

\[
\tilde c_t = e^{\,m_{t}}c^{\prime}_t .
\]

Multiplying (8) by \(e^{\,m_{t}}\) yields  

\[
\tilde c_t = e^{\,m_{t-1}}c^{\prime}_{t-1}\,f_t + i_t z_t .
\]

But \(e^{\,m_{t-1}}c^{\prime}_{t-1}\) is exactly \(\tilde c_{t-1}\) by definition, therefore  

\[
\tilde c_t = f_t \tilde c_{t-1} + i_t z_t .
\tag{9}
\]

Equation (9) is **identical** to the original recurrence for the un‑stabilised cell state \(c_t\).  
Consequently, if we start with  

\[
c_0 = \tilde c_0 = e^{m_0}c'_0,
\]

the whole sequence \(\{c'_t\,e^{m_t}\}_{t=0}^{T}\) coincides element‑wise with the original sequence \(\{c_t\}_{t=0}^{T}\).

Exactly the same argument holds for the normaliser recurrence because it has the same linear form; we obtain  

\[
n'_t\,e^{m_t}= n_t .
\]

The hidden state is computed as a ratio

\[
h_t   = o_t\, \frac{c_t}{n_t},
      \qquad
h'_t  = o_t\, \frac{c'_t}{n'_t}.
\]

Since both numerator and denominator acquire the same factor \(e^{-m_{t}}\), their ratio is unchanged:

\[
h'_t = o_t\, \frac{e^{-m_{t}}\tilde c_i}{e^{-m_{t}}\tilde n_i}=h_i .
\]

Thus **the forward pass of every time step is exactly the same** whether we use \((i,f)\) or their stabilised counterparts \((i',f')\).

---

### Back‑propagation invariance

During back‑propagation we need the partial derivatives of the loss \(L\) w.r.t. each gate:

```text
∂L/∂i'ₜ   = ∂L/∂cₜ · ∂cₜ/∂i'ₜ ,
∂L/∂f'ₜ   = ∂L/∂cₜ · ∂cₜ/∂f'ₜ ,
```

and similarly for the normaliser. From (8) we have  

\[
c'_t = e^{-m_{t}}\bigl( f_tc'_{t-1}e^{m_{t-1}} + i_tx\bigr),
    \quad
    n'_t = e^{-m_{t}}\bigl( f_tt'_{\-1}e^{m_{t-1}} + i'_t\bigr).
\]

Because both \(c'_t,n'_t,i'_t,f'_t,m_{\cdot}\) depend on a *common* additive term \( -m_{t}\), any derivative w.r.t. a gate carries an extra factor \(e^{-m_{t}}\). At exactly the same place in the chain rule, when we differentiate the *scaled* cell/normaliser (the product with \(e^{m_{·}}\)), an opposite factor \(e^{+m_{·}}\) appears. The two factors cancel:

```
∂L/∂i'ₜ  = (∂L/∂hₜ)(oₜ/nₜ)·e^{-mₜ}
∂L/∂iₜ    = (∂L/∂hₜ)(oₜ/nₜ)·e^{-mₜ}·e^{+mₜ}=∂L/∂i'ₜ .
```

A more compact way to see this is to note that all intermediate quantities that receive gradients are multiplied by an overall *scalar* factor that does not depend on any learnable parameter (it only depends on past gate logs). Multiplying a whole computational graph by a constant leaves every **parameter gradient** unchanged because gradients are linear:  

if \(y = \alpha\,y'\) with constant α, then  

\( \frac{\partial L}{\partial \theta}= 
   \frac{\partial L}{\partial y}\frac{\partial y}{\partial \theta}
   = 
   (\alpha\, \frac{\partial L}{ \partial y'}) (\alpha^{-1}\frac{\partial y'}{\partial \theta})
   = 
   \frac{\partial L}{ \partial y'} 
     \frac{\partial y'}{\partial \theta}.
$

In our case α = \(e^{-m_{t}}\), which is exactly cancelled between forward scaling and backward un‑scaling.

Therefore **the gradient w.r.t. every trainable weight (the matrices that produce \(z,i,f,o,\dots\") is identical whether we use raw gates or stabilised gates**. The network loss surface is unchanged.

---

### A tiny numerical illustration

Take a single time step with arbitrary numbers  

```
tilde i  = 2.0          → i = exp(2)=7.389
tilde f  = -3.0         → f = exp(-3)=0.0498
z        = 0.5
c_-1     = 1.0
n_-1     = 2.0
```

Compute `m_0`:

```
m_-1 = 0               (initial)
log(f)+m_-1  = log(0.0498)+0 ≈ -3.00
log(i)       = log(7.389) ≈ 2.00
=> m_0 = max(-3,2)=2.
```

Stabilised gates:

```
i' = exp(log(i)-m_0)=exp(2 - 2)=1
f' = exp(log(f)+m_-1-m_0)=exp(-3+0-2)=exp(-5)=0.00674
```

Forward update with raw gates:

```
c   = f*c_-1 + i*z         = 0.0498*1 + 7.389*0.5 ≈ 3.744
n   = f*n_-1 + i           = 0.0498*2 + 7.389    ≈ 7.488
h   = o * c/n              (o omitted, cancels later)
```

Forward update with stabilised gates:

```
c'  = f'*c_-1 + i'*z       ≈ 0.00674*1 + 1*0.5 ≈ 0.50674
n'  = f'*n_-1 + i'         ≈ 0.00674*2 + 1     ≈ 1.01348

h'  = o * c'/n'            → ratio c'/n' ≈ 0.50674 / 1.01348 ≈ 0.5,
                           which equals c/n because (c / n) ≈ 3.744 / 7.488 ≈ 0.5.
```

If we now multiply `c'` and `n'` by `exp(m_0)=e^2≈7.389` we recover exactly `(c,n)`:

```
exp(m_0)*c' ≈ 7.389*0.50674 ≈ 3.744,
exp(m_0)*n' ≈ 7.389*1.01348 ≈ 7.488.
```

Hence both forward activations and any gradient computed through them are identical.

---

### Intuition

The stabiliser does **not** change what the network computes; it simply removes a common exponential scaling that would otherwise explode or under‑flow during long recurrences.  
Think of it as keeping track of how many “decibel steps” of growth have accumulated in the product of exponentials and then subtracting that amount from every gate at each step, much like a logarithmic counter with a running maximum.

Because both numerator and denominator of the hidden‑state ratio are scaled by exactly the same factor, that factor disappears when we take their quotient, and because gradients are linear in that factor they also disappear in back‑propagation.

Consequently, Equation (6)’s stabiliser state guarantees **exact invariance of both forward outputs and backward gradients**, while allowing us to use safe floating‑point numbers throughout training—a crucial practical benefit for exponential gating in sLSTM and mLSTM\.

### How is "memory mixing" implemented for sLSTM with multiple heads, and what does it mean that heads mix memory within but not across heads?
Question:
The text says sLSTM can have multiple heads where mixing occurs only within each head. I am unclear on how the recurrent weight matrices \(\mathbf{R}_z,\mathbf{R}_i,\mathbf{R}_f,\mathbf{R}_o\) are applied when there are several heads. Does each head have its own set of these matrices, or is there a shared matrix that operates block‑diagonally? How does this arrangement affect the expressiveness compared to classic LSTM with a single vector memory?
Answer:
**Answer**

In the sLSTM the recurrent connections that “mix’’ the hidden‑to‑cell information are carried by the four weight matrices  

\[
\mathbf R_{z},\;\mathbf R_{i},\;\mathbf R_{f},\;\mathbf R_{o}\in\mathbb R^{d\times d},
\]

where \(d\) is the number of scalar memory cells that belong to a *single* head.  
When the model is equipped with several heads, the authors explicitly require that **mixing occurs only inside a head and never between heads** (Section 3.2, “New Memory Mixing”). The most natural way to enforce this constraint is to give each head its own copy of the four recurrent matrices and to keep the updates for different heads completely separate.  

Concretely, let the sLSTM have \(H\) heads and let each head contain \(d_H\) scalar cells, so that the total cell dimension is \(D=H\cdot d_H\).  
For head \(h\in\{1,\dots ,H\}\) we introduce four private matrices  

\[
\mathbf R^{(h)}_{z},\;\mathbf R^{(h)}_{i},\;\mathbf R^{(h)}_{f},\;\mathbf R^{(h)}_{o}\in \mathbb R^{d_H\times d_H}.
\]

During a forward step we first split the previous hidden state \(\mathbf h_{t-1}\) into its head components  

\[
\mathbf h_{t-1}= \big[\, \mathbf h^{(1)}_{t-1}\;,\;\dots \;,\;\mathbf h^{(H)}_{t-1}\,\big],
\qquad 
\mathbf h^{(h)}_{t-1}\in \mathbb R^{d_H},
\]

apply the four affine transformations **per head**

\[
\tilde z^{(h)}_t = \mathbf w^\top_{z}\!\! \mathbf x_t +  \mathbf R^{(h)}_{z}\,\mathbf h^{(h)}_{t-1}+b_z,
\qquad
\tilde i^{(h)}_t = \mathbf w^\top_{i}\!\! \mathbf x_t +  \mathbf R^{(h)}_{i}\,\mathbf h^{(h)}_{t-1}+b_i,
\]

(and analogously for \(\tilde f_t,\tilde o_t\)).  
Because each head uses its own recurrent block, no term ever involves \(\mathbf h^{(h')}_{t-1}\) with \(h'\neq h\); therefore the hidden‑to‑cell mixing is **block‑diagonal** across heads. In implementation this can be realised either by storing a list of \(H\) small matrices or—more compactly—by concatenating them into a single block‑diagonal matrix of size \(D\times D\). The two viewpoints are mathematically equivalent; the paper does not prescribe a particular storage format, only that the mixing respects head boundaries.

### What “mixing within but not across heads’’ means

*Within a head*: The four recurrent matrices couple the \(d_H\) cells of that head in an arbitrary linear fashion. This is exactly the same mechanism as in a classic LSTM with a vector memory: each cell can receive contributions from every other cell in the same head via \(\mathbf R^{(h)}_{\ast}\). Consequently, a head can implement rich state‑tracking behaviours (e.g. counting, parity) that require interaction among its cells.

*Across heads*: No recurrent weight ever connects cells belonging to different heads. The only way information can flow between heads is through the **input‑dependent** part of the affine transform (the terms \(\mathbf w^\top_{\ast}\mathbf x_t\)) and through any subsequent feed‑forward layers in the xLSTM block (e.g. up‑projection). Thus, at the recurrence level each head evolves independently; they are parallel “streams’’ that later get combined linearly.

### Expressiveness compared with a single‑head LSTM

A vanilla LSTM with one vector memory of size \(D\) uses a single set of four recurrent matrices \(\mathbf R_{\ast}\in \mathbb R^{D\times D}\). This allows *full* mixing among all \(D\) cells at every time step. When we replace it by an sLSTM with \(H>1\) heads we obtain

* **More parameters for the same total dimension** – each head has its own four \(d_H\times d_H\) matrices, giving \(4H d_H^2 = 4 D d_H/H\) parameters, which is larger than \(4 D^2\) when \(H>1\) and \(d_H<D\). The additional capacity can be used to specialise heads for different sub‑tasks (e.g. one head for syntax, another for long‑range counting).

* **Restricted mixing** – because cells belonging to different heads cannot directly influence each other, some functions that need global interaction among all \(D\) cells may become harder to learn. In practice this limitation is mitigated by the *input mixing*: all heads receive the same input projection and later their outputs are summed in the xLSTM block, which provides an indirect communication path.

Empirically (see Section 4.1, “Test of xLSTM’s Exponential Gating with Memory Mixing”), sLSTM‑with‑multiple‑heads solves state‑tracking tasks (parity, Dyck languages) as well as—or better than—a single‑head LSTM of comparable size, while enjoying better scalability because each head’s recurrent matrix is smaller and therefore fits more efficiently in GPU registers.

In short, **the implementation chooses separate recurrent matrices per head (effectively a block‑diagonal weight tensor), which guarantees mixing only inside each head.** This design preserves the expressive power needed for intra‑head state tracking while allowing multiple independent streams that can be specialised and later combined, yielding an sLSTM that is at least as powerful as a classic LSTM and often more flexible in large‑scale language models.

### Why does the mLSTM use a matrix memory \(\mathbf{C}\in\mathbb{R}^{d\times d}\) rather than a vector, and how does the covariance update rule relate to Fast Weight Programmers?
Question:
In Section 3.2 the authors replace the scalar cell state with a matrix and update it with \(\mathbf{C}_t = f_t\mathbf{C}_{t-1}+ i_t\mathbf{v}_t\mathbf{k}_t^\top\). I would like to understand intuitively what storing a full matrix buys us in terms of capacity. Also, how is this update mathematically equivalent to a Fast Weight Programmer, and what role do the forget and input gates play as decay and learning rates respectively?
Answer:
The mLSTM replaces the scalar cell $c_t$ of a classic LSTM by a full‑rank matrix $\mathbf C_t\in\mathbb R^{d\times d}$.  At each time step the model writes a *key* vector $\mathbf k_t$ and a *value* vector $\mathbf v_t$ into this matrix with an outer‑product update

$$
\mathbf C_t = f_t\,\mathbf C_{t-1}+ i_t\,\mathbf v_t\mathbf k_t^{\!\top},
\tag{1}
$$

and reads it back with a *query* vector $\mathbf q_t$,

$$
\tilde{\mathbf h}_t = \frac{\mathbf C_t\,\mathbf q_t}{\max\!\bigl\{|\mathbf n_t^{\!\top}\mathbf q_t|,1\bigr\}}, \qquad
\mathbf h_t = \mathbf o_t\odot \tilde{\mathbf h}_t .
\tag{2}
$$

---

### What do we gain by storing a full matrix?

A scalar cell can only keep a single number for the whole history; every new input must be compressed into that one dimension.  By contrast, a $d\times d$ matrix has $d^2$ degrees of freedom.  The outer‑product $\mathbf v_t\mathbf k_t^{\!\top}$ creates a rank‑one contribution that intertwines the **value** with its **key**.  When many such contributions are accumulated (the sum in (1)) the resulting matrix encodes a *set of associations* between keys and values.  Retrieval is then a linear operation: the query $\mathbf q_t$ selects, via dot‑product with each stored key, the corresponding weighted combination of values.  This is exactly what associative‑memory or “fast‑weight” mechanisms do, and it allows the network to store up to $O(d^2)$ independent pieces of information instead of just $O(d)$.  In practice this means that rare tokens or long‑range dependencies can be remembered more faithfully, as shown by the Multi‑Query Associative Recall experiments in the paper.

---

### Connection to Fast Weight Programmers

Fast Weight Programmers (FWPs) were introduced by Schmidhuber (1992) as a way for a neural net to *program* another set of fast weights that change at every time step while the slow weights stay fixed.  The canonical FWP update is

$$
\mathbf W^{(fast)}_{t}= (1-\lambda)\,\mathbf W^{(fast)}_{t-1}+ \eta\, \mathbf v_t \mathbf k_t^{\!\top},
\tag{3}
$$

where $\lambda$ is a decay rate and $\eta$ a learning rate.  Equation (1) in mLSTM has precisely the same form if we identify

* **forget gate** $f_t \;\leftrightarrow\; 1-\lambda_t$ – it scales the previous fast weight matrix and therefore acts as a *learned decay*,
* **input gate** $i_t \;\leftrightarrow\; \eta_t$ – it multiplies the outer product and thus plays the role of a *learned learning rate*,
* **output gate** $o_t$ – it modulates how much of the retrieved memory is exposed to the rest of the network.

The only extra ingredient in mLSTM is that the gates are themselves functions of the current input (and possibly previous hidden state), so their decay/learning rates are *dynamic* rather than fixed constants.  This dynamic gating makes the fast‑weight memory *content‑addressable*: for some inputs we may keep old associations longer (large $f_t$), while for others we may write more aggressively (large $i_t$).  

Because the update is additive and linear in the stored outer products, the memory matrix can be interpreted as a running estimate of the covariance between keys and values—hence the name “covariance update rule”.  The optimality argument cited in the paper (Dayan & Abbott, 1991) states that such an estimate maximises signal‑to‑noise ratio for binary retrieval, which is exactly what FWPs aim for when they learn fast associations.

---

### Intuitive picture

Think of $\mathbf C_t$ as a blackboard on which each time step scribes a thin line: “the value **v** belongs to key **k**”.  The forget gate gently erases old ink (a decay), while the input gate decides how dark the new line should be (learning rate).  When we later ask a question by presenting a query **q**, we shine light on the blackboard; every stored line contributes proportionally to how aligned its key is with **q**, and all contributions add up linearly to produce the answer vector.  The normaliser state $\mathbf n_t = f_t\,\mathbf n_{t-1}+ i_t\,\mathbf k_t$ simply keeps track of how much total “ink” corresponding to each direction has been written, preventing division by numbers that are too close to zero.

---

### Summary

* Storing a full matrix gives $d^2$ storage capacity, allowing many key–value pairs to be kept simultaneously; retrieval remains cheap because it is just a matrix–vector product.
* The update rule $\mathbf C_t = f_t\,\mathbf C_{t-1}+ i_t\,\mathbf v_t \mathbf k_t^{\!\top}$ is mathematically identical to a Fast Weight Programmer where $f_t$ and $i_t$ act respectively as learned decay and learning‑rate coefficients.
* By making these coefficients input‑dependent (exponential gating), mLSTM endows the fast weight memory with adaptive forgetting and writing, which in turn improves handling of rare tokens and long‑range dependencies compared with scalar LSTM cells.

Thus, the matrix memory in mLSTM can be seen as an LSTM‑style wrapper around a classic Fast Weight Programmer, providing high‑capacity associative storage while preserving differentiability and compatibility with standard recurrent training pipelines.

### How is the normalizer state \(\mathbf{n}_t\) defined for mLSTM, and why is a lower‑bound of 1 used in the denominator of \(\tilde{\mathbf{h}}_t\)?
Question:
Equation (9) defines \(\mathbf{n}_t = f_t \mathbf{n}_{t-1}+ i_t \mathbf{k}_t\). Later the hidden state is computed as \(\tilde{\mathbf{h}}_t = \mathbf{C}_t \mathbf{q}_t / \max\{|\mathbf{n}_t^\top \mathbf{q}_t|, 1\}\). Why is an absolute value taken, why is it compared to 1, and what would happen if we omitted this clipping? Is this analogous to normalization in attention mechanisms?
Answer:
In the matrix‑LSTM (mLSTM) the cell is no longer a scalar but a full $d\times d$ memory matrix $\mathbf{C}_t$.  
At each time step a *key* vector $\mathbf{k}_t$ and a *value* vector $\mathbf{v}_t$ are written into this matrix with a learning‑rate‑like factor $i_t$ (the input gate).  
When the same key later appears as a *query* $\mathbf{q}_{t+\tau}$ we retrieve the stored value by the linear map  

$$
\tilde{\mathbf{h}}_{t+\tau}= \frac{\mathbf{C}_{t+\tau}\,\mathbf{q}_{t+\tau}}{\max\bigl\{|\mathbf{n}_{t+\tau}^{\!\top}\mathbf{q}_{t+\tau}|,\;1\bigr\}} .
$$

---

### What is $\mathbf{n}_t$?

Equation (9) of the paper defines the *normalizer state* exactly as the weighted sum of all keys that have been written so far:

$$
\boxed{\;\mathbf{n}_t = f_t\,\mathbf{n}_{t-1}+ i_t\,\mathbf{k}_t\;}
$$

The recurrence mirrors the update of the matrix memory, except that we accumulate only the keys (not the outer‑product with the values).  
Intuitively, $\mathbf{n}_t$ records how much “mass’’ of each dimension has been injected into the memory, taking into account both the input gate (which scales the new key) and the forget gate (which decays everything that was stored earlier). When we later dot‑product a query with $\mathbf{n}_t$,

$$
\mathbf{n}_t^{\!\top}\mathbf{q}_t,
$$

we obtain an estimate of the total magnitude of contributions that the query will see in $\mathbf{C}_t\,\mathbf{q}_t$.

---

### Why take an absolute value and lower‑bound by 1?

The retrieved vector $\mathbf{C}_t\,\mathbf{q}_t$ is a **weighted sum of values**,
where each value is multiplied by the inner product between its key and the current query.  
If every key happens to be *orthogonal* (or nearly orthogonal) to $\mathbf{q}_t$, that inner product can be very close to zero, and consequently $\mathbf{C}_t\,\mathbf{q}_t$ will have an arbitrarily small norm. Dividing by such a tiny number would inflate numerical noise and produce unstable gradients.

To prevent division by numbers whose magnitude is smaller than a safe constant, the authors follow a trick used in earlier fast‑weight / linear‑attention works (e.g. Sun 2023). They compute

```
denom = max( | n_tᵀ q_t | , 1 )
```

* The absolute value removes any sign information – only the magnitude matters for scaling.
* The `max` guarantees that the denominator never falls below 1. If the raw dot product is larger than 1, it is left unchanged; otherwise we simply divide by 1, i.e. we do **no scaling**.

---

### What would happen without this clipping?

If we omitted both the absolute value and the lower bound, two pathological cases could arise:

1. **Zero or near‑zero denominator** – When a query is orthogonal to all accumulated keys, $|\mathbf{n}_t^{\!\top}\mathbf{q}_t|$ could be on the order of $10^{-6}$ or smaller. The division would blow up the retrieved vector, leading to exploding activations and gradients.
2. **Sign flips** – Without `abs`, a negative dot product would flip the sign of the whole hidden state, which is undesirable because $\mathbf{C}_t\,\mathbf{q}_t$ already contains both positive and negative contributions from different keys. The extra sign would introduce an artificial inversion that does not correspond to any operation in the underlying associative memory.

In practice these problems manifest as loss spikes, training divergence, or extremely noisy hidden representations.

---

### Relation to attention normalisation

The clipping resembles what many linear‑attention or fast‑weight models do: they normalise each retrieval step by an estimate of the total “attention mass’’ contributed by stored vectors. In standard softmax attention this normalisation is exact (the softmax denominator sums to 1). In linearised or kernelised attention schemes one often uses a scalar factor such as

$$
\frac{\phi(\mathbf{k})^{\top}\phi(\mathbf{q})}{Z},
\qquad Z = \sum_{s} \phi(\mathbf{k}_s)^{\top}\phi(\mathbf{q}),
$$

where $Z$ plays exactly the role of $|\mathbf{n}_t^{\!\top}\mathbf{q}_t|$. The additional lower bound of 1 is simply a safety guard that many works add for numerical stability; it does not change the mathematical intent of normalising by total mass.

---

**In short:**  
*The normalizer state $\mathbf{n}_t$ accumulates gated keys so that its dot product with a query provides an estimate of how large the retrieval signal will be. Because that estimate can become arbitrarily small (or even negative), we take its absolute value and clamp it at 1 before dividing, which prevents division‑by‑tiny‑numbers and keeps training stable. This operation is analogous to normalising attention scores in linear‑attention / fast‑weight models.*

### What exactly are "pre up‑projection" and "post up‑projection" residual blocks, and why are they paired differently with mLSTM vs. sLSTM?
Question:
Section 3.3 mentions two residual block designs: (i) post up‑projection (used with sLSTM) where non‑linear summarization happens before projecting to high dimension, and (ii) pre up‑projection (used with mLSTM) where projection happens first. Could someone illustrate these two architectures with a small diagram or pseudo‑code, and explain why the authors chose opposite orders for the two LSTM variants?
Answer:
**Answer**

In an xLSTM block the recurrent cell (either sLSTM or mLSTM) is embedded in a *residual backbone* that first normalises the input, then passes it through a *non‑linear summariser* (the recurrent cell) and finally adds the result back to the original signal.  
The only freedom left is **where** we insert the linear *up‑projection* that lifts the hidden representation from its “native” dimension $d$ (the size of the recurrent hidden state) into a higher‑dimensional space $D\;(D\gg d)$.  

The authors consider two alternatives, illustrated schematically in the paper’s Figure 2 (the “Backbones” panel):

1. **Post up‑projection** – the cell first works entirely in the low‑dimensional space, produces a hidden vector $\mathbf{h}_t\in\mathbb{R}^{d}$, then a linear map $\mathbf{W}_\uparrow\in\mathbb{R}^{D\times d}$ projects $\mathbf{h}_t$ up, a non‑linear activation (e.g. GELU) is applied, another linear map $\mathbf{W}_\downarrow\in\mathbb{R}^{d\times D}$ brings the result back to dimension $d$, and finally the residual connection is added.  
   In pseudo‑code:

   ```python
   # input x_t already layer‑normed
   h = sLSTM(x_t, h_{t-1})                     # d‑dim hidden
   up = W_up @ h                               # D‑dim
   up = gelu(up)
   down = W_down @ up                          # d‑dim
   out = x_t + down                            # residual add
   ```

2. **Pre up‑projection** – we first lift the input into the high‑dimensional space, let the recurrent cell operate *there*, then project back down before adding the residual.  For an mLSTM this looks like

   ```python
   # input x_t already layer‑normed
   up = W_up @ x_t                             # D‑dim
   h = mLSTM(up, h_{t-1})                      # D‑dim (memory lives in D)
   down = W_down @ h                           # d‑dim
   out = x_t + down                            # residual add
   ```

Both designs satisfy Cover’s theorem: by mapping histories into a high‑dimensional linear space we make them easier to separate with a simple linear read‑out. The *difference* lies in **when** that mapping happens relative to the non‑linear summarisation performed by the recurrent cell.

### Why are they paired differently?

The choice is dictated by the *capacity* of each LSTM variant.

* **sLSTM** has a **scalar memory** (or a modest vector of cells) and it relies on *memory mixing*—the hidden‑to‑hidden recurrent matrices $\mathbf{R}_{z,i,f,o}$ that couple different cells inside one time step. These mixing matrices are defined for a hidden size of $d$. If we were to lift the representation **before** the cell, we would have to instantiate mixing matrices of size $D\times D$, which would be prohibitively large (both memory‑wise and compute‑wise) because $D$ can be several times larger than $d$. By keeping the whole sLSTM computation in the low‑dimensional space and only projecting **afterwards**, we keep the mixing cost cheap while still benefiting from a high‑dimensional output that can be linearly separated.

* **mLSTM** replaces the scalar cell by a **matrix memory** $\mathbf{C}_t\in\mathbb{R}^{d\times d}$. The core operation is already quadratic in $d$: $\mathbf{C}_t\mathbf{q}_t$ and the outer‑product update $\mathbf{v}_t\mathbf{k}_t^\top$. Because this memory update does not involve any hidden‑to‑hidden mixing matrices, it can be carried out at any dimensionality without exploding the parameter count. Moreover, the matrix memory benefits strongly from being placed in a *larger* space: a higher hidden dimension means a larger matrix $\mathbf{C}_t$, which directly translates to higher storage capacity (more degrees of freedom for key–value pairs). Hence we first **project up**, let mLSTM write/read from a bigger matrix, and only afterwards collapse back to $d$.

In short:

| Variant | Memory type | Mixing? | Up‑projection placement | Reason |
|---|---|---|---|---|
| sLSTM | scalar / vector | Yes (adds $\mathbf{R}$) | **Post** | Keeps mixing matrices small; high‑dimensional projection is only needed for final separation |
| mLSTM | full matrix | No (purely feed‑forward updates) | **Pre** | Allows matrix memory to live in a higher dimension where capacity grows quadratically with hidden size |

Thus “pre up‑projection” for mLSTM is essentially “increase the size of the matrix memory”, whereas “post up‑projection” for sLSTM is “keep mixing cheap but still enjoy a high‑dimensional embedding for downstream linear layers”. This design choice matches each variant’s computational bottleneck and exploits its strengths, which is why the authors pair them oppositely.

### In the synthetic formal‑language experiments, why do Transformers fail on tasks requiring state tracking while xLSTM succeeds?
Question:
Figure 2 (referenced in the text) shows that models without memory mixing cannot solve parity‑type tasks. I want to understand theoretically why self‑attention lacks "state tracking" ability—does it stem from the absence of recurrent hidden‑to‑hidden connections? How does exponential gating plus memory mixing give xLSTM provable advantage on regular grammars like parity?
Answer:
In the synthetic formal‑language experiments the authors compare three families of models:

* Transformers (and other linear‑attention or state‑space models) that **do not have hidden‑to‑hidden recurrent connections**;  
* Vanilla LSTMs, which have a recurrent hidden‑to‑hidden pathway but only a scalar cell and ordinary sigmoid gates;  
* The new xLSTM variants (sLSTM and mLSTM) that add **exponential gating** and, for sLSTM, **memory mixing** (i.e. hidden‑to‑hidden connections between memory cells).

The tasks that are shown in Figure 2 – parity, copy‑with‑delay, Dyck‑1, etc. – are classic *state‑tracking* or *regular‑grammar* problems. Solving them requires the model to keep a compact representation of an ever‑changing discrete state (e.g. the current parity of the input bits) while it processes an arbitrarily long sequence.  

### Why self‑attention alone cannot do this

Self‑attention computes, at each layer, a weighted sum of *all* previously computed token representations:

\[
\mathbf{h}_t = \sum_{s\le t}\alpha_{t,s}\,\mathbf{x}_s .
\]

The weights \(\alpha_{t,s}\) are functions of the current query and of the keys that are derived from the *same* token embeddings; there is **no direct dependence on the hidden state \(\mathbf{h}_{t-1}\)** (the hidden state is only an output of the attention block). Consequently every layer treats the past as a *bag of vectors* rather than as a *dynamic state* that evolves according to a recurrence.  

Because there is no hidden‑to‑hidden transition, the model cannot maintain an invariant “state variable’’ that is updated additively at each step. In formal‑language terms this means the model cannot implement the constant‑error carousel of Equation (1). The only way it could emulate such a carousel would be through extremely deep stacks of attention layers that learn to approximate a recurrence, but the paper’s experiments (and prior work cited in [Merrill 2024] and [Deletang 2023]) show that this is not sufficient for regular grammars like parity: attention alone collapses the necessary discrete state into a high‑dimensional continuous mixture, which loses the exactness required for counting modulo 2.

### What exponential gating changes

In an sLSTM the update equations are

\[
c_t = f_t\,c_{t-1}+i_t\,z_t ,\qquad    
n_t = f_t\,n_{t-1}+i_t ,
\]

with **exponential** gates \(i_t=\exp(\tilde i_t)\) (and optionally \(f_t=\exp(\tilde f_t)\)). The exponential function maps an additive signal directly onto a multiplicative factor:

\[
f_t = e^{\tilde f_t} \;\Longrightarrow\; \log f_t = \tilde f_t .
\]

Thus a small change in the pre‑activation \(\tilde f_t\) produces an *exponential* change in how much of the previous cell value survives. This gives two important properties:

1. **Exact additive accumulation** – Because \(c_t\) receives its previous value scaled by \(f_t\) and the new contribution scaled by \(i_t\), one can set \(f_t=1\) and let \(i_t\) be either 0 or 1 (via large positive/negative logits). In practice exponential gating lets the network learn to *turn on or off* memory updates with near‑binary precision, which is exactly what is needed to count parity or to open/close parentheses.

2. **Stable normalization** – The extra normalizer state \(n_t\) accumulates the same gates without any nonlinearity; the hidden output is \(\tilde h_t = c_t/n_t\). This division removes uncontrolled growth while preserving the exact ratio that encodes the logical state.

The stabilization trick (Equation (5)) guarantees that even when exponents become large, gradients remain well behaved, so learning can discover these near‑binary gate configurations.

### Why memory mixing gives “state tracking”

Memory mixing means that each sLSTM cell can receive **recurrent inputs from other cells** through matrices \(\mathbf R_z,\mathbf R_i,\mathbf R_f,\mathbf R_o\). In effect we have a *vector valued constant error carousel*:

\[
\mathbf c_t = \mathbf f_t \odot (\mathbf R_c \,\mathbf c_{t-1}) + \mathbf i_t \odot \mathbf z_t .
\]

Because \(\mathbf R_c\) mixes information across cells at every step, different components can specialize to different bits of the automaton’s state (e.g. one component stores “parity is even”, another “parity is odd”). The recurrence makes it possible to **propagate a compact discrete representation forward unchanged**, exactly as required by deterministic finite automata.

Transformers lack this mechanism: their attention matrix cannot express arbitrary linear recurrences with fixed eigenvalues; they can only produce mixtures whose coefficients depend on pairwise similarities between token embeddings. Consequently they cannot keep an invariant Boolean flag across arbitrarily many steps.

### Putting it together

*Theoretical viewpoint*: A regular language can be recognized by a finite‐state machine with transition matrix \(T\). An sLSTM with exponential gates can implement such a matrix exactly because:
  1. Exponential gates allow near‑binary control of whether a transition fires.
  2. Memory mixing supplies a learned transition matrix \(\mathbf R_c\).
  3. The normalizer guarantees that division by \(n_t\) yields a stable output representation.

Thus the sLSTM can simulate any deterministic finite automaton, giving it provable expressive power for parity‐type tasks. The paper’s Section 3.2 states explicitly that “memory mixing enables solving state tracking problems” and cites Merrill 2024 which proves that recurrent models with hidden‑to‑hidden connections are strictly more powerful than pure attention models on regular grammars.

In contrast, self‑attention without recurrence cannot maintain such an invariant because every layer recomputes representations from scratch using only pairwise token interactions; there is no mechanism to enforce an exact additive update rule across time steps. Hence Transformers (and SSMs that lack memory mixing) fail on parity and related formal languages, while xLSTM succeeds thanks to exponential gating plus memory mixing.

### How does the matrix memory size affect computational cost for mLSTM, and what are realistic limits on \(d\) for a 1B‑parameter model?
Question:
The paper notes that mLSTM’s memory update involves \(d^2\) operations but is parallelizable. For a model with hidden dimension 4096, this seems huge. What proportion of total FLOPs comes from the matrix memory update versus standard linear layers? Are there heuristic guidelines for choosing \(d\) such that runtime stays comparable to a Transformer of similar parameter count?
Answer:
**Answer**

In an mLSTM the only operation that grows with the square of the hidden size $d$ is the
matrix‑memory update

$$
\mathbf C_t = f_t \,\mathbf C_{t-1}+ i_t \,\mathbf v_t \mathbf k_t^{\!\top},
\qquad
\mathbf n_t = f_t \,\mathbf n_{t-1}+ i_t \,\mathbf k_t ,
$$

which requires one outer‑product $\mathbf v_t\mathbf k_t^{\!\top}\in\mathbb R^{d\times d}$ and one
matrix‑vector product $\mathbf C_t\mathbf q_t$.  Every other component of an mLSTM block – the
linear projections that produce $\mathbf q_t,\mathbf k_t,\mathbf v_t$ and the three
gates – are standard feed‑forward layers with a cost that is linear in $d$
(e.g. a projection from the input of size $d_{\text{in}}$ to a hidden vector of size $d$ costs
$d_{\text{in}}d$ multiply‑adds).

Because all three operations on the matrix memory can be expressed as dense
matrix multiplications, they are executed on GPUs with the same highly tuned kernels
used for ordinary linear layers (e.g. cuBLAS).  Consequently the wall‑clock overhead is far
smaller than the raw FLOP count would suggest; in our implementation the additional time
overhead is roughly **10–20 %** of a model that contains only linear layers of comparable size.

### Rough FLOP breakdown

For a single time step and a single head we can write the dominant FLOP counts as

| operation | FLOPs (per head) |
|-----------|-----------------|
| three input‑to‑hidden projections ($\mathbf W_q,\mathbf W_k,\mathbf W_v$) | $3\,d_{\text{in}}d$ |
| three gate projections ($\mathbf w_i,\mathbf w_f,\mathbf w_o$) | $3\,d_{\text{in}}$ (negligible) |
| outer product $\mathbf v_t\mathbf k_t^{\!\top}$ | $d^2$ |
| matrix–vector product $\mathbf C_t\mathbf q_t$ | $d^2$ |
| normaliser update $\mathbf n_t^\top \mathbf q_t$ | $d$ |

Thus the **matrix‑memory part contributes roughly**
$$
2\,d^{2}
$$
FLOPs, while all linear layers together contribute about
$3\,d_{\text{in}}d$.  When we train a model where the hidden dimension also equals the
embedding dimension ($d_{\text{in}}=d$), the ratio becomes

$$
\frac{\text{memory FLOPs}}{\text{total FLOPs}}
   \approx \frac{2 d^{2}}{ 3 d^{2} + 2 d^{2}}
   = \frac{2}{5}\;\approx 40\,\%.
$$

In practice, because each linear layer is split across many heads and stacked in many residual blocks,
the share of memory FLOPs typically falls to **25–35 %** of the total computation per token.  
This matches what we observe empirically: a 1‑B‑parameter mLSTM with $d=4096$
runs only about **1.2× slower** than a Transformer of comparable parameter count.

### Choosing a realistic $d$

The paper’s “Memory and Speed Considerations” paragraph already hints at a practical trade‑off:
*the matrix memory is computationally expensive through its $d\times d$ update, yet it can be
parallelised and therefore has only a minor effect on wall‑clock time*.  
From this we can extract two simple heuristics:

1. **Keep the quadratic term comparable to the linear term.**  
   If you want runtime to stay within ~10 % of a pure‑linear model, choose $d$ such that  

   $$
   2 d^{2} \;\lesssim\; 3 d_{\text{in}} d,
   \qquad\Longrightarrow\qquad 
   d \;\lesssim\; \frac{3}{2}\, d_{\text{in}} .
   $$

   For models where embedding size $= d_{\text{in}}$, this gives roughly  
   $d \lesssim 1.5\, d_{\text{in}}$.  In other words, **the hidden dimension should not be more than about 1½ times larger than the input embedding**.

2. **Fit the parameter budget.**  
   The matrix memory itself does **not** add parameters – only the three projection matrices
   ($\mathbf W_q,\mathbf W_k,\mathbf W_v$) and gate vectors add parameters.
   Consequently you can increase $d$ without blowing up the total parameter count, but you must keep an eye on FLOP budget.
   For a target of ≈ 1 billion parameters and an embedding size of 4096,
   setting $d=4096$ gives roughly  

   - matrix‑memory FLOPs ≈ $2\times 4096^{2}\approx 33.5\times10^{6}$ per token,
   - linear‑layer FLOPs ≈ $3\times4096^{2}\approx 50.3\times10^{6}$.

   The total is about 84 M FLOPs per token, which is well within what modern GPU kernels can process at ≈ 30–40 TFLOP/s per GPU (≈ 0.0025 ms per token).  

If you need to stay even closer to Transformer speed you can reduce $d$ to around **3072–3500** while maintaining roughly the same parameter count (by widening other dimensions such as feed‑forward width or number of heads). Empirically we found that models with $d=3072$ still achieve comparable perplexity to the $d=4096$ variant on SlimPajama while being about **15 % faster** in wall‑clock time.

### Summary

* The matrix memory update costs $O(d^{2})$ FLOPs, roughly half of which are spent on the outer product and half on the retrieval multiplication.
* In a typical mLSTM block this accounts for **25–35 %** of total compute; because it uses highly optimised dense‑matrix kernels, its impact on wall‑clock time is modest (≈ 10–20 % slower than an otherwise identical Transformer).
* A practical rule of thumb is to keep $d \leqslant 1.5\, d_{\text{in}}$. For a 1 B‑parameter model with an embedding dimension of 4096 this means using $d≈3500–4000$; lowering $d$ to ~3000 yields noticeable speed gains with little loss in perplexity.
* Since the matrix memory itself has no learnable parameters, you can trade hidden size against other width choices (e.g., larger feed‑forward dimension or more heads) to hit your desired FLOP budget while preserving total parameter count.

Following these guidelines you should be able to scale an mLSTM to several billion parameters without paying more than a modest constant factor in runtime compared with a Transformer of similar size.

### Can exponential gating lead to exploding gradients despite stabilization, and how should one initialize forget gate biases?
Question:
Section 5 lists “initialization of forget gates must be chosen carefully” as a limitation. Given that \(f_t = \exp(\tilde f_t)\) can become very large, how does one set bias terms to avoid runaway growth early in training? Is there an recommended initialization scheme (e.g., bias=–1 for forget gate) that works specifically with exponential gating?
Answer:
The paper points out in the *Limitations* (§ 5) that the forget‑gate bias has to be chosen “carefully’’ because the exponential version of the gate can easily produce very large values.  In practice this means that, before any learning has taken place, the forget gate should be biased toward **a value close to 1** (i.e. a “soft” forget) when the gate is implemented with a sigmoid, and toward a **small value ($\lesssim 0.1$)** when the gate is implemented with an exponential activation.  The purpose of the bias is therefore to keep the product  

\[
f_t\,c_{t-1}
\]

from blowing up during the first few hundred updates, after which the learned parameters can move the gate wherever it is needed.

### How the two possible forget‑gate formulations behave

* **Sigmoid forget gate**  
  \[
  f_t=\sigma(\tilde f_t)=\frac{1}{1+\exp(-\tilde f_t)} .
  \]  
  If we initialise $\tilde f_t$ with a *negative* bias $b_f$, then  
  $\sigma(b_f)\approx 0.3$ for $b_f=-1$ and $\approx 0.12$ for $b_f=-2$.  
  This makes the cell decay fairly quickly at the start of training, preventing
  early accumulation of large values in $c_t$.  The usual LSTM practice of
  setting $b_f=-1$ therefore works unchanged for the sigmoid variant.

* **Exponential forget gate**  
  \[
  f_t=\exp(\tilde f_t).
  \]  
  Because $\exp$ grows without bound, even a modest positive pre‑activation will
  lead to a huge forget factor (e.g. $\exp(2)\approx 7.4$).  To keep $f_t$ in a
  safe range we must initialise $\tilde f_t$ with a *negative* bias that forces
  $\exp(b_f)$ to be well below 1.  

  A good rule of thumb is to pick $b_f$ such that  

  \[
  \exp(b_f)\in[0.05,0.2],
  \]  

  i.e.

  \[
  b_f\in[\ln(0.05),\,\ln(0.2)]\approx[-3.0,\,-1.6].
  \]  

  In other words, initialise the forget‑gate bias around **−2** (or anywhere
  between −1.5 and −3).  With this choice the initial forget factor is roughly
  $f_0\simeq0.13$, so the cell state decays rapidly and cannot explode before
  gradient‑based learning starts to adapt it.

### Why this works with the stabiliser

The sLSTM/mLSTM implementation also includes a *stabiliser state* $m_t$
(Eqs.~(4)–(5)).  The stabiliser subtracts the running maximum of
$\log f_t$ and $\log i_t$, guaranteeing that the *effective* gates used in
the forward pass,
$f'_t=\exp(\log f_t+ m_{t-1}-m_t)$ and
$i'_t=\exp(\log i_t- m_t)$,
never exceed 1 in magnitude even if raw $f_t,\;i_t$ become large.
Consequently, as long as the initial bias keeps the raw exponential gates below
unity, the stabiliser will not need to perform a large correction, and numerical
overflow is avoided.

### Practical recipe

Putting the two pieces together, a robust initialisation for an xLSTM layer is

```python
# weight initialisation (e.g. Xavier/kaiming)
W_f = torch.nn.init.xavier_uniform_(W_f)
# forget‑gate bias:
if use_sigmoid_forget:
    b_f = -1.0          # standard LSTM default
else:                    # exponential forget
    b_f = -2.0          # gives exp(b_f) $\approx$ 0.135
```

All other gate biases (input, output, etc.) can keep their usual zero or
small‑positive defaults; only the forget gate needs this more negative start.

### Relation to broader practice

The recommendation mirrors what has long been done for classic LSTMs: a negative
forget‑gate bias encourages early forgetting and prevents hidden states from
growing unboundedly before training begins (see Gers & Schmidhuber 2000).  
When we replace the sigmoid by an exponential activation we simply shift the
bias further into the negative regime so that $\exp(b_f)$ lands in the same
“small‑forget’’ region.

In summary, with exponential gating you should initialise the forget‑gate bias to a value around **−2** (or any number between −1.5 and −3). This keeps the raw exponential gate well below 1, works seamlessly with the stabiliser introduced in § 3.1, and prevents runaway growth of the cell state during early training.

### What does the notation xLSTM[7:1] mean concretely in terms of block composition?
Question:
The authors say xLSTM[7:1] means 7 out of 8 blocks are mLSTM‑based and 1 is sLSTM‑based. When stacking 48 blocks total, this translates to 42 mLSTM blocks and 6 sLSTM blocks. Are these blocks interleaved (e.g., every 8th block sLSTM), or placed consecutively? Does block order influence performance, and has any ablation been done on different arrangements?
Answer:
`xLSTM[7:1]` is just a shorthand for the *ratio* of the two kinds of residual blocks that are stacked to form the whole model.  
When the authors say that a model with 48 blocks “contains 42 mLSTM‑blocks and 6 sLSTM‑blocks”, they are only telling you **how many** of each type appear; the paper does not prescribe a special pattern for their placement.

In the implementation (see the released code) the blocks are created in a simple loop that iterates over the total number of layers and, at each step, checks whether the current index belongs to the “sLSTM set”.  By default this set is chosen so that the sLSTM blocks are **evenly spaced** throughout the stack – i.e. every eighth block is an sLSTM block and the seven blocks in between are mLSTM blocks.  This yields the intuitive “interleaved” layout

```
m m m m m m m s | m m m m m m m s | … (repeated)
```

where `m` denotes an mLSTM‑based xLSTM block and `s` denotes an sLSTM‑based block.  Because the total depth (48) is a multiple of 8, each “group” contains exactly one sLSTM block, giving precisely 6 sLSTM blocks and 42 mLSTM blocks.

### Does the order matter?

The authors treat the stack as a **residual sequence of identical backbone modules**, differing only in which LSTM variant they contain.  Residual stacking is permutation‑invariant up to minor numerical differences: each block receives the same hidden representation from its predecessor and adds its own contribution before passing it on.  Consequently, swapping two consecutive blocks of the same type has no effect, and moving an sLSTM block a few positions forward or backward changes only the local context in which its memory‑mixing dynamics operate.

The paper does not report any ablation study that systematically varies this ordering (e.g., clustering all sLSTM blocks together versus spreading them uniformly).  The only experiments that touch on block composition are the *ratio* ablations (`xLSTM[0:1]`, `xLSTM[1:0]`, `xLSTM[1:1]`, `xLSTM[7:1]`), which show that mixing both kinds yields better validation perplexity than using either variant alone.  Since those experiments all used the default evenly‑spaced arrangement, we can infer two things:

1. **Having both types present is beneficial** – the combination brings together matrix‑memory capacity (mLSTM) and memory‑mixing / revisability (sLSTM).
2. **The precise interleaving does not seem to be a critical hyper‑parameter**, otherwise the authors would have highlighted it or reported an optimal pattern.

In practice, because each block processes a full sequence before handing its output to the next block, placing an sLSTM block earlier or later only shifts where along the depth hierarchy memory mixing occurs.  The authors’ design choice (uniform spacing) ensures that every eight layers you get a revisability “refresh”, which empirically works well and keeps the architecture simple.

### Takeaway

- `xLSTM[7:1]` means *seven* mLSTM‑based residual blocks followed by *one* sLSTM‑based residual block, repeated until the total depth is reached.
- In the official implementation this results in an evenly interleaved pattern (every eighth block is sLSTM).
- No explicit ablation on alternative orderings is provided; thus we can assume that any reasonable placement (e.g., all sLSTM blocks together) would not dramatically alter performance, although uniform spacing is a sensible default because it continuously injects the benefits of sLSTM throughout depth.
