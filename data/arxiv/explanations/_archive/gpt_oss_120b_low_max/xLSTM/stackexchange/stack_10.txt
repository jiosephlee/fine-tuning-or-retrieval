\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### What does the notation xLSTM[7:1] mean concretely in terms of block composition?
Question:
The authors say xLSTM[7:1] means 7 out of 8 blocks are mLSTM‑based and 1 is sLSTM‑based. When stacking 48 blocks total, this translates to 42 mLSTM blocks and 6 sLSTM blocks. Are these blocks interleaved (e.g., every 8th block sLSTM), or placed consecutively? Does block order influence performance, and has any ablation been done on different arrangements?
Answer:
`xLSTM[7:1]` is just a shorthand for the *ratio* of the two kinds of residual blocks that are stacked to form the whole model.  
When the authors say that a model with 48 blocks “contains 42 mLSTM‑blocks and 6 sLSTM‑blocks”, they are only telling you **how many** of each type appear; the paper does not prescribe a special pattern for their placement.

In the implementation (see the released code) the blocks are created in a simple loop that iterates over the total number of layers and, at each step, checks whether the current index belongs to the “sLSTM set”.  By default this set is chosen so that the sLSTM blocks are **evenly spaced** throughout the stack – i.e. every eighth block is an sLSTM block and the seven blocks in between are mLSTM blocks.  This yields the intuitive “interleaved” layout

```
m m m m m m m s | m m m m m m m s | … (repeated)
```

where `m` denotes an mLSTM‑based xLSTM block and `s` denotes an sLSTM‑based block.  Because the total depth (48) is a multiple of 8, each “group” contains exactly one sLSTM block, giving precisely 6 sLSTM blocks and 42 mLSTM blocks.

### Does the order matter?

The authors treat the stack as a **residual sequence of identical backbone modules**, differing only in which LSTM variant they contain.  Residual stacking is permutation‑invariant up to minor numerical differences: each block receives the same hidden representation from its predecessor and adds its own contribution before passing it on.  Consequently, swapping two consecutive blocks of the same type has no effect, and moving an sLSTM block a few positions forward or backward changes only the local context in which its memory‑mixing dynamics operate.

The paper does not report any ablation study that systematically varies this ordering (e.g., clustering all sLSTM blocks together versus spreading them uniformly).  The only experiments that touch on block composition are the *ratio* ablations (`xLSTM[0:1]`, `xLSTM[1:0]`, `xLSTM[1:1]`, `xLSTM[7:1]`), which show that mixing both kinds yields better validation perplexity than using either variant alone.  Since those experiments all used the default evenly‑spaced arrangement, we can infer two things:

1. **Having both types present is beneficial** – the combination brings together matrix‑memory capacity (mLSTM) and memory‑mixing / revisability (sLSTM).
2. **The precise interleaving does not seem to be a critical hyper‑parameter**, otherwise the authors would have highlighted it or reported an optimal pattern.

In practice, because each block processes a full sequence before handing its output to the next block, placing an sLSTM block earlier or later only shifts where along the depth hierarchy memory mixing occurs.  The authors’ design choice (uniform spacing) ensures that every eight layers you get a revisability “refresh”, which empirically works well and keeps the architecture simple.

### Takeaway

- `xLSTM[7:1]` means *seven* mLSTM‑based residual blocks followed by *one* sLSTM‑based residual block, repeated until the total depth is reached.
- In the official implementation this results in an evenly interleaved pattern (every eighth block is sLSTM).
- No explicit ablation on alternative orderings is provided; thus we can assume that any reasonable placement (e.g., all sLSTM blocks together) would not dramatically alter performance, although uniform spacing is a sensible default because it continuously injects the benefits of sLSTM throughout depth.
