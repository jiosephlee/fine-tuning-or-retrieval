\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### What exactly are "pre up‑projection" and "post up‑projection" residual blocks, and why are they paired differently with mLSTM vs. sLSTM?
Question:
Section 3.3 mentions two residual block designs: (i) post up‑projection (used with sLSTM) where non‑linear summarization happens before projecting to high dimension, and (ii) pre up‑projection (used with mLSTM) where projection happens first. Could someone illustrate these two architectures with a small diagram or pseudo‑code, and explain why the authors chose opposite orders for the two LSTM variants?
Answer:
**Answer**

In an xLSTM block the recurrent cell (either sLSTM or mLSTM) is embedded in a *residual backbone* that first normalises the input, then passes it through a *non‑linear summariser* (the recurrent cell) and finally adds the result back to the original signal.  
The only freedom left is **where** we insert the linear *up‑projection* that lifts the hidden representation from its “native” dimension $d$ (the size of the recurrent hidden state) into a higher‑dimensional space $D\;(D\gg d)$.  

The authors consider two alternatives, illustrated schematically in the paper’s Figure 2 (the “Backbones” panel):

1. **Post up‑projection** – the cell first works entirely in the low‑dimensional space, produces a hidden vector $\mathbf{h}_t\in\mathbb{R}^{d}$, then a linear map $\mathbf{W}_\uparrow\in\mathbb{R}^{D\times d}$ projects $\mathbf{h}_t$ up, a non‑linear activation (e.g. GELU) is applied, another linear map $\mathbf{W}_\downarrow\in\mathbb{R}^{d\times D}$ brings the result back to dimension $d$, and finally the residual connection is added.  
   In pseudo‑code:

   ```python
   # input x_t already layer‑normed
   h = sLSTM(x_t, h_{t-1})                     # d‑dim hidden
   up = W_up @ h                               # D‑dim
   up = gelu(up)
   down = W_down @ up                          # d‑dim
   out = x_t + down                            # residual add
   ```

2. **Pre up‑projection** – we first lift the input into the high‑dimensional space, let the recurrent cell operate *there*, then project back down before adding the residual.  For an mLSTM this looks like

   ```python
   # input x_t already layer‑normed
   up = W_up @ x_t                             # D‑dim
   h = mLSTM(up, h_{t-1})                      # D‑dim (memory lives in D)
   down = W_down @ h                           # d‑dim
   out = x_t + down                            # residual add
   ```

Both designs satisfy Cover’s theorem: by mapping histories into a high‑dimensional linear space we make them easier to separate with a simple linear read‑out. The *difference* lies in **when** that mapping happens relative to the non‑linear summarisation performed by the recurrent cell.

### Why are they paired differently?

The choice is dictated by the *capacity* of each LSTM variant.

* **sLSTM** has a **scalar memory** (or a modest vector of cells) and it relies on *memory mixing*—the hidden‑to‑hidden recurrent matrices $\mathbf{R}_{z,i,f,o}$ that couple different cells inside one time step. These mixing matrices are defined for a hidden size of $d$. If we were to lift the representation **before** the cell, we would have to instantiate mixing matrices of size $D\times D$, which would be prohibitively large (both memory‑wise and compute‑wise) because $D$ can be several times larger than $d$. By keeping the whole sLSTM computation in the low‑dimensional space and only projecting **afterwards**, we keep the mixing cost cheap while still benefiting from a high‑dimensional output that can be linearly separated.

* **mLSTM** replaces the scalar cell by a **matrix memory** $\mathbf{C}_t\in\mathbb{R}^{d\times d}$. The core operation is already quadratic in $d$: $\mathbf{C}_t\mathbf{q}_t$ and the outer‑product update $\mathbf{v}_t\mathbf{k}_t^\top$. Because this memory update does not involve any hidden‑to‑hidden mixing matrices, it can be carried out at any dimensionality without exploding the parameter count. Moreover, the matrix memory benefits strongly from being placed in a *larger* space: a higher hidden dimension means a larger matrix $\mathbf{C}_t$, which directly translates to higher storage capacity (more degrees of freedom for key–value pairs). Hence we first **project up**, let mLSTM write/read from a bigger matrix, and only afterwards collapse back to $d$.

In short:

| Variant | Memory type | Mixing? | Up‑projection placement | Reason |
|---|---|---|---|---|
| sLSTM | scalar / vector | Yes (adds $\mathbf{R}$) | **Post** | Keeps mixing matrices small; high‑dimensional projection is only needed for final separation |
| mLSTM | full matrix | No (purely feed‑forward updates) | **Pre** | Allows matrix memory to live in a higher dimension where capacity grows quadratically with hidden size |

Thus “pre up‑projection” for mLSTM is essentially “increase the size of the matrix memory”, whereas “post up‑projection” for sLSTM is “keep mixing cheap but still enjoy a high‑dimensional embedding for downstream linear layers”. This design choice matches each variant’s computational bottleneck and exploits its strengths, which is why the authors pair them oppositely.
