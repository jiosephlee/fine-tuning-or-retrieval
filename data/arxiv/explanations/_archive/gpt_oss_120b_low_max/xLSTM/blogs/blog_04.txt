# Parallelizing Recurrent Networks: How mLSTM Breaks the Sequential Bottleneck

Recurrent neural networks have long been the workhorse for sequence modeling. Their defining characteristic—*hidden‑to‑hidden* connections—forces a strict left‑to‑right processing order, which makes them difficult to accelerate on modern GPUs. The paper *xLSTM: Extended Long Short-Term Memory* introduces a new recurrent variant, **mLSTM**, that removes these hidden‑to‑hidden dependencies while keeping a true recurrent memory. In this post we unpack how mLSTM achieves GPU‑friendly parallelism, why the design still preserves the expressive power of classic LSTMs, and what this means for large‑scale language modeling.

---

## 1. Why Classic RNNs Are Hard to Parallelize

In a standard LSTM the cell update at time step *t* depends on the hidden state *hₜ₋₁*:

\[
c_t = f_t \odot c_{t-1} + i_t \odot z_t ,\qquad
h_t = o_t \odot \psi(c_t).
\]

The gate activations *(iₜ, fₜ, oₜ)* themselves are computed from both the current input **xₜ** and the previous hidden state **hₜ₋₁**. Because **hₜ₋₁** is needed to evaluate **hₜ**, each step must wait for the result of the previous one. On a GPU this results in many small, sequential kernels—far from the massive matrix multiplications that GPUs excel at.

---

## 2. The Core Idea of mLSTM: Decouple Gates from Hidden State

mLSTM keeps a recurrent *memory matrix* **Cₜ ∈ ℝ^{d×d}**, but it **removes the hidden‑to‑hidden term from the gate equations**. Concretely:

* The *input*, *forget*, and *output* gates are **pure functions of the current input** **xₜ** (plus learned biases), e.g.

\[
i_t = \exp(\mathbf{w}_i^\top \mathbf{x}_t + b_i), \qquad
f_t = \sigma(\mathbf{w}_f^\top \mathbf{x}_t + b_f) \,\text{or}\, \exp(\cdot).
\]

* No recurrent weight vectors (the *r* terms in classic LSTM) appear in these equations.

Because each gate now depends only on **xₜ**, all gate values for an entire sequence can be computed **in parallel** using a single matrix multiplication followed by an elementwise nonlinearity.

---

## 3. How Memory Is Updated Without Hidden‑to‑Hidden Connections

Even though the gates are feed‑forward, mLSTM still maintains a **temporal memory** thanks to a *covariance update rule* reminiscent of fast‑weight programmers:

\[
\mathbf{C}_t = f_t \,\mathbf{C}_{t-1} + i_t \,\mathbf{v}_t \mathbf{k}_t^\top .
\]

Here:

* **kₜ** (the *key*) and **vₜ** (the *value*) are linear projections of **xₜ**.
* The forget gate *fₜ* acts as a decay factor on the previous memory matrix.
* The input gate *iₜ* scales the outer product **vₜ kₜᵀ**, which inserts new information.

Crucially, this recurrence only involves matrix–matrix operations. When we unroll the recurrence across time, it becomes a simple **prefix sum (scan)** over the sequence of scaled outer products. Scans are well‑studied in GPU literature and can be executed with log‑depth parallel algorithms (e.g., using CUDA’s `thrust::inclusive_scan`). As a result, **the whole memory update can be performed in O(log T) parallel steps instead of O(T) sequential steps**, where *T* is sequence length.

---

## 4. Retrieval Is Also Parallelizable

The hidden output for step *t* is read from the memory matrix by a query vector **qₜ**, itself a linear projection of **xₜ**:

\[
\tilde{\mathbf{h}}_t = 
\frac{\mathbf{C}_t\,\mathbf{q}_t}{\max\!\left(|\mathbf{n}_t^\top \mathbf{q}_t|,\;1\right)},
\qquad
h_t = o_t \odot \tilde{\mathbf{h}}_t .
\]

All terms on the right are either already computed in parallel (the gates, keys, values, queries) or are simple matrix–vector multiplications that can be batched across time steps. The normalization denominator uses a separate “normalizer state” **nₜ**, which follows exactly the same scan pattern as **Cₜ**, so it can be computed jointly.

---

## 5. What Do We Gain? A Quick Comparison

| Property | Classic LSTM | mLSTM |
|----------|--------------|-------|
| Hidden‑to‑hidden connections | Yes (requires sequential processing) | No (gates are feed‑forward) |
| Memory structure | Scalar cell vector | Matrix memory (covariance) |
| Parallelism level | Limited to per‑step operations | Full sequence‑wide parallel scans and batched matmul |
| GPU utilization | Low (many small kernels) | High (large GEMM and scan kernels) |
| Expressivity | Strong but vulnerable to vanishing gradients | Retains long‑term storage via decay/additive updates; avoids vanishing gradients by design |

Empirically, the paper reports that mLSTM attains **comparable or better perplexity** than Transformers and State Space Models while maintaining linear compute cost with respect to sequence length and constant memory usage.

---

## 6. Why Does Removing Hidden‑to‑Hidden Not Hurt Performance?

One might worry that discarding hidden feedback will cripple modeling power. Two design choices keep mLSTM expressive:

1. **Matrix Memory as an Associative Store:** By storing key–value outer products, mLSTM can retrieve information based on content similarity rather than positional recurrence alone—much like attention but without quadratic cost.
2. **Exponential Gating & Normalization:** Using exponential activations for *iₜ* (and optionally *fₜ*) allows gates to amplify or suppress updates dramatically, giving the network fine control over how quickly old memories decay.

Together these mechanisms enable mLSTM to *revise* stored information (thanks to exponential forget gates) and to memorize richer structures (thanks to the high‑dimensional matrix). The hidden state becomes a readout of this associative store rather than an independent recurrent channel.

---

## 7. Practical Implications

### Faster Training & Inference
Because all time steps share the same large GEMM kernels, training scales almost identically to feed‑forward transformer blocks when using modern hardware like NVIDIA A6000 or TPU v4. During inference, mLSTM’s constant memory footprint means you can generate arbitrarily long sequences without quadratic cache growth—a long‑standing bottleneck for transformers.

### Simpler Hardware Deployments
The lack of hidden‑to‑hidden dependencies removes the need for custom scan operators on edge devices; a straightforward implementation using existing BLAS libraries suffices. This aligns with the paper’s claim that xLSTM models are “well suited for industrial applications and implementations on the edge.”

### Compatibility with Existing Architectures
mLSTM slots neatly into residual block backbones (the “xLSTM block” in the paper). You can therefore stack mLSTM blocks alongside other modules—self‑attention layers, convolutional encoders—without worrying about mismatched sequence handling.

---

## 8. Limitations to Keep in Mind

While mLSTM eliminates sequential bottlenecks, it does introduce a dense \(d\times d\) memory matrix, which increases computational load (matrix multiplications scale with \(d^2\)). The authors note that their current CUDA kernels are slower than FlashAttention by roughly fourfold; however, they also point out that this overhead is modest compared to overall wall‑clock time because all operations remain highly parallelizable.

Moreover, careful initialization of forget gates is required to prevent uncontrolled growth or excessive decay of the memory matrix—a nuance shared with any fast weight / associative memory system.

---

## 9. Closing Thoughts

The mLSTM variant demonstrates that we don’t have to choose between *recurrent memory* and *parallel efficiency*. By moving gating logic entirely onto feed‑forward paths and delegating temporal dynamics to an associative matrix store updated via a scan-friendly covariance rule, mLSTM preserves long-term dependence handling while unlocking GPU acceleration across entire sequences.

If you’re building large language models or any sequential system where inference latency matters, consider experimenting with mLSTM (or its sibling sLSTM for tasks requiring explicit hidden mixing). The open-source implementation linked in the xLSTM paper gives you a solid starting point—and perhaps a glimpse into a future where recurrent architectures regain their place alongside transformers in mainstream deep learning pipelines.
