\title{A Textbook about the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

# Introduction to Byte‑Level Language Modeling  

In this chapter we set the stage for understanding **Byte‑Latent Transformer (BLT)**, the first tokenizer‑free large language model (LLM) that matches the performance of tokenization‑based LMs at scale while offering substantial gains in efficiency and robustness.  We first examine why the conventional practice of fixing a vocabulary of tokens is problematic, then argue why operating directly on raw bytes can alleviate those problems.  After reviewing prior attempts to train byte‑level LLMs and the obstacles that prevented them from scaling, we describe the core innovations of BLT—dynamic entropy‑driven patching, a hierarchical architecture that mixes lightweight byte‑level encoders with a global latent transformer, and a compute‑allocation strategy that adapts to data complexity.  Finally we summarize the contributions of the BLT paper and outline how the remainder of this textbook will unpack its design, training methodology, empirical findings, and broader implications.

## Limitations of Tokenization  

Most modern LLMs begin by **tokenizing** input text: a deterministic pre‑processing step that groups consecutive bytes into symbols drawn from a finite vocabulary (often built by byte‑pair encoding, BPE).  Although tokenization dramatically reduces sequence length, it introduces several systematic shortcomings.

* **Domain and modality bias.**  Tokenizers are constructed from a fixed corpus and therefore encode heuristic compression rules that reflect the statistics of that corpus.  When a model encounters text from a new domain (e.g., source code, scientific notation) or a different modality (e.g., mixed Latin/Chinese scripts), the token boundaries may split semantically coherent units or merge unrelated bytes, causing the model to waste computation on easy regions and to under‑allocate resources where predictions are hard.  

* **Sensitivity to input noise.**  Because tokenizers map raw bytes to discrete symbols, any perturbation at the byte level—such as a stray character, a misspelling, or corrupted encoding—can cause a token boundary shift that yields an entirely different token ID sequence.  Consequently downstream models become brittle: small perturbations can change many token IDs, amplifying error propagation during inference.

* **Multilingual inequity.**  Fixed vocabularies allocate a limited number of tokens to each language.  High‑resource languages (English) receive many dedicated tokens, while low‑resource languages receive few or none.  This leads to uneven representation capacity across languages and harms performance on long‑tail scripts.

* **Loss of orthographic knowledge.**  Tokenizers treat each token as an atomic unit; the model no longer sees the underlying characters or bytes that compose it.  Recent work has shown that this hampers abilities such as phonology inference or character‑level manipulation because the model cannot directly attend to sub‑token structures.

These issues are not merely aesthetic; they manifest as measurable gaps in benchmark performance, robustness under noise, and fairness across languages.

## Why Bytes? Flexibility and Robustness  

A **byte** is the smallest addressable unit in most text encodings (UTF‑8).  By feeding raw bytes directly into an LLM we obtain several advantages:

1. **Vocabulary‑free representation.**  There is no need to pre‑define a vocabulary; every possible byte value (0–255) is already known.  This eliminates vocabulary‑induced bias and guarantees coverage of any possible Unicode sequence.

2. **Uniform granularity across domains.**  Whether the data is natural language, source code, mathematical formulas, or non‑Latin scripts, each element is expressed as a series of bytes.  The model therefore does not need separate tokenizers for each domain; it treats all inputs uniformly.

3. **Robustness to corruption.**  Since each byte is processed individually, small corruptions affect only the local context rather than cascading through multiple token IDs.  The model can learn to recover from missing or altered bytes by leveraging surrounding byte information.

4. **Explicit sub‑word modeling.**  Operating at the byte level restores direct access to characters and their compositions (e.g., graphemes → phonemes).  This enables tasks that require fine‐grained orthographic reasoning, such as grapheme‑to‑phoneme conversion or character‐level manipulation benchmarks.

5. **Potential for multilingual parity.**  Because every language is ultimately represented as byte sequences, a single model can learn a unified representation without allocating separate slots in a tokenizer’s vocabulary.

The primary obstacle historically has been **efficiency**: raw byte sequences are typically four to eight times longer than token sequences for comparable text, inflating the computational cost of Transformers whose dominant cost scales with sequence length.

## Historical Attempts at Byte‑Level LLMs and Their Scaling Bottlenecks  

Early efforts at character or byte modeling focused on recurrent architectures (e.g., character RNNs) that could handle long sequences but suffered from limited parallelism and memory bandwidth constraints. With the advent of Transformers, several research lines pursued *byte‐level* models:

* **CharacterBERT / CANINE** employed convolutional or shallow Transformer layers to downsample character streams before feeding them into a deeper encoder–decoder stack. While they showed promise on multilingual tasks, their computational profiles remained dominated by per‑byte feed‐forward networks rather than attention alone.

* **ByT5** demonstrated an encoder–decoder architecture that processed raw bytes without any downsampling (“patching”). Although it achieved reasonable robustness, training required substantially more floating‑point operations because every byte participated in self‑attention.

* **MambaByte** leveraged an attention‐free recurrent state (Mamba) to alleviate per‑byte attention cost but still required all bytes to traverse deep layers during training.

* **MegaByte** introduced *static strided patching*: every \(k\) bytes are concatenated into a fixed‐size “patch” before being fed into a Transformer decoder. This reduced sequence length but allocated compute uniformly across patches; patches containing simple whitespace were treated identically to those containing complex mathematical symbols.

* **SpaceByte** refined MegaByte by splitting patches at whitespace-like bytes so that each word became one patch. This heuristic improved efficiency for natural language but could not adapt to languages without clear whitespace delimiters and still lacked dynamic allocation based on prediction difficulty.

A common theme among these works is that *the feed‑forward component*—which runs on each element independently—dominates FLOP counts when operating on very long byte sequences. Even when attention cost is reduced via sparse patterns or recurrence, the sheer number of per‑byte MLP operations makes scaling beyond hundreds of millions of parameters prohibitively expensive.

## Key Ideas of BLT: Dynamic Patching, Latent Transformer, Compute Allocation  

The **Byte Latent Transformer (BLT)** resolves the above bottlenecks through three synergistic mechanisms:

1. **Entropy‑Driven Dynamic Patching**  
   BLT first runs a lightweight *entropy model*, an auxiliary byte‐level auto‑regressive LM trained on the same data distribution. For each position \(i\) in the input stream it computes the *next‑byte entropy*
   \[
   H(x_i)= -\sum_{v\in\mathcal{V}} p_e(x_i=v \mid \mathbf{x}_{<i})\,
           \log p_e(x_i=v \mid \mathbf{x}_{<i}),
   \]
   where \(\mathcal{V}\) is the set of 256 possible bytes and \(p_e\) is the entropy model’s distribution.
   High entropy indicates low predictability (e.g., start of a new word), while low entropy signals easy continuation (e.g., within “Mozart”).  
   Patch boundaries are placed either when \(H(x_t) > \theta_g\) (a global threshold) or when entropy rises sharply relative to its predecessor,
   \[
   H(x_t)-H(x_{t-1}) > \theta_r.
   \]
   The result is *contextualized patches* whose average size reflects information density: easy regions become long patches (few Transformer steps), difficult regions become short patches (more steps).

2. **Hierarchical Architecture with Local Encoder/Decoder + Global Latent Transformer**  
   - The **Local Encoder (\(\mathcal{E}\))** is a shallow Transformer that consumes raw bytes (embedded via a \(256\times h_{\mathcal{E}}\) matrix) together with *hash n‑gram embeddings*. These embeddings capture local contexts up to eight bytes long without blowing up parameter count.
   - After each encoder layer a *cross‑attention* module aggregates byte representations belonging to the same patch into a *latent patch vector* \(p_j\).  
   - The **Global Latent Transformer (\(\mathcal{G}\))**, an autoregressive deep Transformer with \(l_{\mathcal{G}}\) layers, operates exclusively on these patch vectors using block‑causal attention; it thus processes far fewer steps than a naïve bytewise model.
   - The **Local Decoder (\(\mathcal{D}\))**, also shallow, receives the output patch vectors \(o_j\) from \(\mathcal{G}\), performs cross‑attention in reverse (patches → bytes), and finally emits probabilities over the next byte using a standard softmax over 256 classes.

   Crucially, most FLOPs are spent in \(\mathcal{G}\); because \(\mathcal{G}\) executes only once per patch rather than per byte, overall compute scales with average patch size rather than raw sequence length.

3. **Compute Allocation Aligned with Data Complexity**  
   By tying patch boundaries to next‑byte entropy, BLT automatically *allocates more transformer layers to hard predictions* (short patches) and *fewer layers to easy predictions* (long patches). This contrasts with tokenizers where every token incurs identical compute regardless of its intrinsic difficulty. The dynamic allocation yields up to **50 % fewer inference FLOPs** at fixed performance levels and enables *simultaneous scaling of model size and patch size*: larger patches consume less compute per token so saved FLOPs can be reinvested in widening or deepening \(\mathcal{G}\).

Together these components constitute a novel paradigm: instead of committing FLOPs uniformly via an immutable vocabulary, BLT adapts its computation trajectory online based on statistical uncertainty estimated from data itself.

## Summary of Contributions and Roadmap  

The BLT paper makes four principal contributions:

1. **A tokenizer‑free architecture with dynamic compute allocation**, demonstrating that byte‐level models can match or exceed BPE-based LLMs when evaluated under equal FLOP budgets.
2. **A flop‑controlled scaling study up to 8 B parameters and 4 T training bytes**, showing that Byte Latent Transformers achieve parity with Llama 3 while using up to half as many inference FLOPs.
3. **Evidence that patch size can be jointly increased with model size without violating fixed‐inference budgets**, opening a new axis for scaling LLMs beyond what tokenization allows.
4. **Empirical validation of improved robustness**, including superior performance on noisy inputs, character‐level tasks (grapheme–phoneme conversion, orthographic benchmarks), and low‑resource machine translation—tasks where traditional tokenizers struggle due to lack of subword visibility.

* Chapters 2–4 dissect BLT’s constituent modules: entropy modeling for patching (§2), local encoder/decoder design (§3), and global latent transformer (§4).  
* Chapter 5 details experimental methodology—datasets, FLOP accounting, training regimes—and reproduces key scaling curves under both compute‐optimal and inference‐fixed conditions.  
* Chapter 6 explores robustness experiments: noisy prompts, phonology benchmarks, CUTE character manipulation tasks, and multilingual translation results.  
* Chapter 7 presents ablation studies that isolate the impact of n‑gram hash embeddings, cross‑attention placement, encoder depth, and various patching strategies (static stride vs whitespace vs entropy).

**Fundamentals of Patching – From Bytes to Variable‑Size Units**

---

### 1.  Notation and Basic Objects  

Consider a raw text document that has been encoded as a sequence of bytes  

\[
\mathbf{x}= \{x_{1},x_{2},\dots ,x_{n}\},\qquad x_{i}\in\mathcal{V}_{\text{byte}}=\{0,1,\dots ,255\},
\]

where \(n\) is the total number of bytes in the document.  
A **patch** is a contiguous subsequence of bytes, denoted  

\[
p_{j}= \{x_{s_{j}},x_{s_{j}+1},\dots ,x_{e_{j}}\},
\]

with start index \(s_{j}\) and end index \(e_{j}\) satisfying \(s_{j}=e_{j-1}+1\).  
The ordered collection of patches obtained from \(\mathbf{x}\) is  

\[
\mathbf{p}= \{p_{1},p_{2},\dots ,p_{m}\}, \qquad m < n .
\]

The mapping from a byte stream to patches is performed by a **patching function**  

\[
f_{p}:\;\mathcal{V}_{\text{byte}}^{\,n}\longrightarrow \mathcal{P}^{\,m},
\]

which we can think of equivalently as a binary indicator vector  

\[
b = (b_{1},b_{2},\dots ,b_{n}) , \qquad b_{i}\in \{0,1\},
\]

where \(b_{i}=1\) signals that a new patch starts at position \(i\) (by convention we set \(b_{1}=1\)).  
Given \(b\), the patches are uniquely determined by grouping consecutive bytes between successive “1” entries.

In token‑based language models, a *token* plays the same role as a patch, but the tokenization process imposes two additional constraints:

| Property | Tokens (BPE, WordPiece, …) | Patches (BLT) |
|----------|---------------------------|---------------|
| **Vocabulary** | Finite, learned prior to training (e.g., 128 k entries). | No fixed vocabulary; any byte sequence may become a patch. |
| **Determinism w.r.t. future** | Token boundaries can depend on the *future* characters (the tokenizer runs on the whole string). | Patch boundaries must be decided **incrementally**, i.e. using only the prefix seen so far. |

The lack of a pre‑computed vocabulary frees the model from the compression heuristics baked into BPE and enables *dynamic* allocation of compute, as explained next.

---

### 2.  Metrics that Influence Patch Cost  

The dominant factor in the runtime of a transformer is the number of **Transformer steps** it must execute. In BLT the large “latent” transformer processes *patches* rather than bytes; consequently its cost scales with the number of patches \(m\). Two simple derived quantities capture this relationship:

1. **Average patch size**  
   \[
   \bar{s}= \frac{n}{m},
   \]
   i.e., the mean number of bytes per patch. Larger \(\bar{s}\) ⇒ fewer patches ⇒ fewer forward‑passes through the latent transformer.

2. **FLOP impact**  
   The total FLOPs required per byte can be expressed as  

   \[
   \text{FLOP}_{\text{per byte}}=
   \frac{\text{FLOPs}_{\text{latent}}(m)}{n}
   + \text{FLOPs}_{\text{local encoder}}(n)
   + \text{FLOPs}_{\text{local decoder}}(n),
   \]

   where \(\text{FLOPs}_{\text{latent}}(m)\) grows roughly linearly with \(m\) (the latent transformer has a fixed depth but its self‑attention operates on a sequence of length \(m\)). The two local models always run on every byte, so they are independent of the patching scheme; only the latent term varies with \(\bar{s}\).  

Thus any patching strategy that yields a larger average patch size reduces inference FLOPs without changing model capacity, provided that predictive performance does not degrade.

---

### 3.  Static (Strided) Patching  

#### 3.1 Definition  

The simplest possible function \(f_{p}^{(\text{stride})}\) groups exactly \(k\) consecutive bytes into each patch:

```
for i = 1 … n step k:
    emit patch = {x_i,…,x_{i+k-1}}
```

Formally  
\(b_i = 1\) iff \(i \equiv 1 \;(\mathrm{mod}\; k)\).  
The resulting average patch size equals the stride: \(\bar{s}=k\).

#### 3.2 Implementation Advantages  

* **Deterministic and incremental:** The decision whether to start a new patch depends only on the current byte index, satisfying the incremental property automatically.  
* **Easy FLOP control:** By varying \(k\), practitioners can directly target a desired inference budget.

#### 3.3 Drawbacks  

* **Uniform compute allocation:** Every patch consumes one latent‑transformer step regardless of how hard its content is to predict. Predicting an entire block of whitespace or repetitive code receives the same amount of compute as predicting a complex mathematical expression.  
* **Inconsistent linguistic boundaries:** A word that straddles a stride boundary will be split arbitrarily, leading to different patchings for identical words appearing in different contexts—a source of inefficiency and possible degradation in downstream tasks.

These issues motivate more *data‑aware* grouping strategies.

---

### 4.  Space Patching  

#### 4.1 Heuristic Idea  

Many natural‑language scripts use spaces or other *space‑like* bytes (punctuation, line‑breaks) as clear delimiters between linguistic units such as words or tokens. Space patching respects these delimiters by ending a patch whenever a space‑like byte appears (subject to a minimal non‑space requirement). Formally

```
if x_i ∈ SPACE-LIKE and current_patch contains ≥1 non-space byte:
    start new patch at i+1
```

Here “space‑like” includes any byte that is *not*:
* a Latin alphabet character,
* a decimal digit,
* an UTF‑8 continuation byte.

#### 4.2 Linguistic Rationale  

The first byte after a whitespace typically carries high predictive uncertainty: it begins a new word whose spelling distribution is broad. Allocating an entire latent step to this region gives the model more capacity exactly where it matters most (the “hard” decision point). Subsequent bytes within the same word are usually much easier to predict once enough letters have been observed; they can be processed by cheap local encoders.

#### 4.3 Limitations  

* **Language coverage:** Not all languages use explicit spaces (e.g., Chinese, Japanese), so this heuristic may produce overly long patches on such texts, reducing dynamic allocation benefits.  
* **Rigidity:** The method cannot adapt its granularity beyond “space versus non‑space”, therefore it cannot exploit finer‐grained entropy variations inside words or code identifiers.

---

### 5.  Entropy‑Based Dynamic Patching  

#### 5.1 Motivation  

Both static and space patching rely on handcrafted rules that may not align with *information density*. A more principled approach is to let data dictate where patches should begin by measuring how uncertain the next‑byte prediction is.

#### 5.2 Training an Entropy Model  

A small autoregressive byte‑level language model, denoted \(p_{\!e}\), is trained on the same corpus used for BLT pretraining. For every position \(i\) it yields a conditional distribution over the next byte:

\[
p_{\!e}(x_i=v\,|\, \mathbf{x}_{<i}) , \qquad v\in \mathcal{V}_{\text{byte}} .
\]

From this distribution we compute the Shannon entropy

\[
H(x_i)= -\,\sum_{v \in \mathcal{V}_{\text{byte}}}
        p_{\!e}(x_i=v\,|\, \mathbf{x}_{<i})\, 
        \log p_{\!e}(x_i=v\,|\, \mathbf{x}_{<i}),
        \tag{5}
\]
which quantifies how unpredictable byte \(x_i\) is given its left context.

Because this model is lightweight (≈ 100 M parameters in our experiments), entropy values can be evaluated on‑the‑fly during data loading with negligible overhead; alternatively, for very small receptive windows they can be pre‑computed into lookup tables.

#### 5.3 Turning Entropies into Patch Boundaries  

Two thresholding schemes were explored:

| Scheme | Decision Rule | Intuition |
|-------|----------------|----------|
| **Global threshold** | Start new patch at position \(t\) if \(H(x_t) > \theta_g.\) | Treat any *absolutely* high‑entropy byte as a boundary. |
| **Approximate monotonicity** | Start new patch at position \(t\) if \\\(H(x_t)-H(x_{t-1}) > \theta_r.\) | Detect *relative* spikes within an otherwise decreasing entropy curve – often corresponding to transitions from “easy” to “hard” regions inside a word or code token.|

Both thresholds (\(\theta_g,\theta_r\)) are chosen to hit a target average patch size on a held‑out validation split; this gives precise control over FLOP budgets while still allowing dynamic variation across examples.

#### 5.4 Practical Considerations  

* **Entropy drift:** When evaluating very long contexts (e.g., whole documents), entropies can gradually decrease because the small entropy model’s hidden state accumulates information (“drift”). To mitigate this we periodically reset its hidden state at line breaks and employ the monotonicity rule, which depends only on local differences rather than absolute values.
* **Incrementality:** Because entropy at step \(i\) depends solely on preceding bytes (\(\mathbf{x}_{<i}\)), boundary decisions satisfy



\[
f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i},
\]

making entropy‑based patching compatible with autoregressive generation.

---

### 6.  Incremental vs Non‑Incremental Patching  

A patching scheme is **incremental** if it can determine whether a new patch should start using *only* information from the prefix already seen by the model; future bytes must not influence this decision. Formally,

\[
f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i} .
\tag{6}
\]

This property is essential for generation: when emitting tokens one by one, the model cannot look ahead to decide how to segment what has not yet been produced.

#### 6.1 Why BPE Fails Incrementality  

Byte Pair Encoding builds tokens by repeatedly merging *most frequent* adjacent byte pairs across an entire corpus *before* training begins. As a result:

* The token boundaries for a given prefix can change when more context follows because merging decisions are defined globally.
* Consequently,
  
  \[
  f_{\text{BPE}}(\mathbf{x}_{<i}) \neq f_{\text{BPE}}(\mathbf{x})_{<i},
  \]

so BPE does not satisfy Eq.(6). One could enforce incrementality by inserting an explicit delimiter token after each BPE token during generation, but this inflates sequence length and defeats one of BPE’s efficiency advantages.

#### 6.2 Benefits for BLT  

All three BLT patching methods—static stride, space, and entropy—are designed to be incremental:

* Stride: boundary index known purely from position.
* Space: depends only on whether current byte belongs to a space‑like class.
* Entropy: uses only past bytes via Eq.(5).

Therefore they integrate seamlessly with an autoregressive decoder and allow “on‑the‑fly” determination of whether to invoke the expensive latent transformer at each step.

---

### 7.  Comparative Summary  

| Method | Vocabulary Requirement | Average Patch Size (\(\bar{s}\)) | Incremental? | Main Control Lever |
|--------|------------------------|----------------------------------|--------------|-------------------|
| **Static (Strided)** | None | Fixed hyperparameter \(k\) | Yes | Choose stride \(k\). |
| **Space Patching** | None | Varies; roughly equals average word length (~4–6 bytes in English corpora). | Yes | Definition of “space‑like” bytes; minimal non‑space constraint. |
| **Entropy‑Based** | None (needs auxiliary LM) | Tuned via thresholds (\(\theta_g,\theta_r\)); empirical values ~4–8 bytes for our data mix. | Yes | Threshold values; optionally reset context or change monotonicity window. |
| **BPE Tokenizer** | Fixed vocabulary (e.g., 128 k tokens). | Fixed by tokenizer statistics (~3–5 bytes per token). | **No** (unless extra delimiter added). | Vocabulary size and merge schedule during pretraining phase.|

From an efficiency perspective, static stride offers predictable FLOPs but wastes compute on easy regions; space patching improves alignment with linguistic boundaries at minimal cost; entropy–based dynamic patching achieves the strongest data‑driven allocation by explicitly targeting high‐entropy bytes while still preserving incrementality required for generation.

--- 

In summary, patches constitute flexible, variable‑size computational units that replace static tokens in BLT. By formalizing patches as functions of byte entropy—or simple heuristics like whitespace—BLT can concentrate its most expensive Transformer layers precisely where prediction difficulty peaks, yielding substantial FLOP savings without sacrificing—and often improving—model performance across diverse downstream tasks.

**Architecture of the Byte Latent Transformer**

The Byte Latent Transformer (BLT) departs fundamentally from the token‑centric design that has dominated large language modeling for the past several years.  Instead of first compressing a raw byte stream into a fixed vocabulary of sub‑word tokens, BLT operates directly on the byte sequence and dynamically groups bytes into *patches* whose size is determined by the information density of the data.  This design yields three distinct computational modules:

1. a **local encoder** that ingests raw bytes and produces a compact latent representation for each patch;
2. a **global latent transformer** that processes the sequence of patch representations with full‑scale autoregressive attention; and
3. a **local decoder** that expands the latent patch outputs back to raw bytes.

The three modules are arranged in a high‑level pipeline that is executed both during pre‑training and generation (inference).  The following sections unpack each component, explain how they interact, and clarify why they are essential for achieving BLT’s claimed FLOP efficiency and robustness.

---

## 1. High‑Level Data Flow

During **training**, an input document is first segmented into patches by a *patching function* $f_p$.  The function marks the start of a new patch whenever the entropy of the next‑byte prediction, estimated by an auxiliary small byte LM, exceeds a chosen threshold (or satisfies an approximate monotonicity condition).  The result is a sequence  

\[
\mathbf{p} = \{p_1, p_2, \dots , p_m\},
\qquad m < n,
\]

where $n$ is the number of raw bytes $\mathbf{x}=\{x_1,\dots ,x_n\}$.

Each patch $p_j$ consists of a contiguous subsequence of bytes; its length is variable but on average equal to the *patch size* $s = n/m$.  The data flow then proceeds as follows:

1. **Embedding** – every byte $x_i$ is mapped to an $h_{\mathcal{E}}$‑dimensional vector via a learned lookup table $\mathbf{E}\in\mathbb{R}^{256\times h_{\mathcal{E}}}$.
2. **Hash n‑gram augmentation** – for each byte position $i$, we also compute embeddings for overlapping byte n‑grams (sizes $n=3\dots 8$) using a rolling polynomial hash; these embeddings are summed with the base byte embedding.
3. **Local encoder transformer** – the augmented byte sequence passes through $l_{\mathcal{E}}$ transformer layers that employ *local block‑causal* attention: each byte may attend only to the $w_{\mathcal{E}}$ preceding bytes, respecting document boundaries.
4. **Cross‑attention pooling** – after each encoder layer we apply a Perceiver‑style cross‑attention block that pools the byte representations belonging to patch $p_j$ into a *patch query* $q_j$.  The set $\{q_j\}_{j=1}^{m}$ forms the input to the global model.
5. **Global latent transformer** – an autoregressive transformer $\mathcal{G}$ with $l_{\mathcal{G}}$ layers processes the patch queries using *block‑causal* attention (a patch may attend only to earlier patches).  This step accounts for most of BLT’s FLOP budget because it is executed once per patch rather than once per byte.
6. **Local decoder cross‑attention** – the output patch representations $\{o_j\}_{j=1}^{m}$ from $\mathcal{G}$ are used as keys/values in a symmetric cross‑attention module that projects them back onto per‑byte queries (the current decoder hidden state).
7. **Decoder transformer** – $l_{\mathcal{D}}$ lightweight decoder layers further refine the per‑byte representations before they are projected onto the 256‑byte vocabulary via a linear output head.

During **inference**, steps 1–4 are identical up to generation of query $q_t$ for the next patch boundary.  If $q_t$ signals that we have reached a new patch, step 5 runs once more to produce the next latent patch; otherwise we remain inside the current patch and only step 6–7 are invoked, thereby saving compute on predictable regions of text.

The overall schematic is displayed in Figure 1 of the original paper: raw bytes → encoder → cross‑attention → global transformer → decoder cross‑attention → decoder → output bytes.

---

## 2. Global Latent Transformer

The *global latent transformer* $\mathcal{G}$ lies at the heart of BLT’s language modeling capability.  It receives a sequence of latent patch vectors  

\[
\mathbf{q} = \bigl(q_1, q_2,\dots , q_m\bigr) \in \mathbb{R}^{m\times h_{\mathcal{G}}},
\]

where each $q_j$ encodes all information from its underlying bytes.  

### 2.1 Layer Count and Width

BLT scales $\mathcal{G}$ independently from its local components.  In all experiments reported in the paper, $\mathcal{G}$ adopts exactly the same depth and hidden dimension as a token‑based LLM with comparable parameter count (e.g., Llama 3).  Typical configurations include:

| Model scale | $l_{\mathcal{G}}$ | $h_{\mathcal{G}}$ |
|-------------|-------------------|------------------|
| 400 M       | 12                | 768              |
| 1 B         | 24                | 1024             |
| 8 B         | 32                | 4096             |

Because $\mathcal{G}$ is invoked only once per *patch*, its overall FLOP contribution scales with ${\rm FLOPs}_{\mathcal G}\propto \frac{\text{\#bytes}}{\text{patch size}}\times l_{\mathcal G}h_{\mathcal G}^{2}$.  Consequently, increasing average patch size reduces inference FLOPs almost linearly while freeing budget for deeper or wider global models.

### 2.2 Block‑Causal Attention

Unlike standard causal attention (which can see all preceding tokens), BLT uses *block causal* masking: at position $j$, attention may attend to any earlier patch index $k\le j$, but not beyond.  This restriction respects autoregression at the granularity of patches rather than individual bytes. Mathematically, for queries $Q\in \mathbb R^{m\times d_k}$ and keys $K\in \mathbb R^{m\times d_k}$ we define

\[
\text{Mask}_{jk}= 
\begin{cases}
0 & k \le j\\
-\infty & k>j,
\end{cases}
\]

and compute attention as $\operatorname{softmax}\bigl(\frac{QK^\top}{\sqrt{d_k}} + \text{Mask}\bigr)V$.  

The block causal mask eliminates any dependence on future patches while still allowing each patch to fully attend to all earlier context, which is essential for long‑range reasoning such as code completion or multi‑turn dialogue.

### 2.3 Role in FLOP Budget

Because feed‑forward networks dominate transformer compute when depth grows, nearly all FLOPs during pretraining are spent inside $\mathcal G$.  The paper’s FLOP analysis (§ 4.5) shows that when average patch size doubles (e.g., from 4 bytes to 8 bytes), inference FLOPs drop by roughly 50 % while keeping model capacity constant—exactly what enables BLT to “scale better than tokens”.

---

## 3. Local Encoder

The encoder $\mathcal E$ must convert an arbitrarily long byte string into a compact set of patch queries in a way that is both *lightweight* (to keep overall FLOPs low) and *expressive* (to provide enough signal for $\mathcal G$).  

### 3.1 Byte Embedding Matrix

Each raw byte $b_i\in \{0,\dots ,255\}$ is embedded via a learned lookup matrix  

\[
\mathbf{x}_i = \mathbf{E}[b_i] \in \mathbb R^{h_{\mathcal E}},
\qquad
\mathbf E \in \mathbb R^{256\times h_{\mathcal E}}.
\]

The embedding dimension $h_{\mathcal E}$ is typically between 256 and 512; this modest size keeps per‑byte overhead minimal.

### 3.2 Hash n‑gram Embeddings

Byte context beyond a single symbol provides crucial disambiguation (e.g., distinguishing “th” vs “ht”). BLT augments $\mathbf{x}_i$ with *hash n‑gram embeddings*, constructed as follows:

1. For each position $i$, generate overlapping n‑grams  
   \[
   g_{i,n} = (b_{i-n+1}, b_{i-n+2}, \dots , b_i), 
   \qquad n =3,\dots ,8,
   \]
   skipping any n‑gram where $i < n$.
2. Compute a rolling polynomial hash:  
   \[
   h(g_{i,n}) = \Bigl(\sum_{k=0}^{n-1} c_k\, p^{k}\Bigr) 
        \bmod |\!E_{n}^{hash}\!|,
   \]
   where $(c_k)$ are integer values of bytes, \(p\) is a fixed prime multiplier, and \( |\!E_{n}^{hash}\!|\) denotes table size.
3. Look up an embedding vector in table \(E^{hash}_n\in\mathbb R^{|\!E_{n}^{hash}\!|\times h_{\mathcal E}}\) and sum across all considered n‑grams:
   \[
   e_i = x_i + 
        \frac1{|N|+1}
        \sum_{n=3}^{8} 
        E^{hash}_n\, [ h(g_{i,n}) ] ,
   \]
   where \(N = \{3,\dots ,8\}\).

Hashing eliminates storage blowup: despite there being \(256^n\) possible n‑grams, only a few hundred thousand entries per n‐gram length are needed, ensuring constant memory while still providing strong contextual cues.

### 3.3 Encoder Transformer Layers with Local Block‑Causal Windows

The augmented vectors $(e_i)$ pass through $l_{\mathcal E}$ transformer layers (often just one or two). Each layer uses *local block causal* attention with window size \(w_{\mathcal E}\) (e.g., 512). A token at position \(i\) can attend only to positions in  

\[
[i-w_{\mathcal E},\, i]\cap[1,n],
\]

ensuring quadratic attention cost remains proportional to \(n\, w_{\mathcal E}\) rather than \(n^2.\)

Every encoder layer also incorporates standard components: LayerNorm (RMSNorm), SwiGLU feed–forward networks, and rotary positional embeddings (RoPE) applied only within self‐attention; however no positional encodings are added inside cross‐attention because patches already encode absolute order through their sequential indices.

### 3.4 Cross‑Attention Design (Perceiver Style)

After each transformer layer we apply a Perceiver-inspired cross‐attention module that aggregates bytes belonging to each patch into a single query vector:

* **Queries** – one per patch; initialized by pooling raw byte embeddings belonging to that patch (max‐pooling in experiments).  
* **Keys / Values** – derived from the most recent encoder hidden states \(h^{(l)}_i.\)

Formally for layer $\ell$, let  
\(P^{(\ell-1)}_j = {\rm Pool}(h^{(\ell-1)}_{i: i\in p_j})\) be the initial query for patch \(j.\) Then

\[
Q^{(\ell)}_j = W_q\, P^{(\ell-1)}_j,\quad
K^{(\ell)}_i = W_k\, h^{(\ell-1)}_i,\quad
V^{(\ell)}_i = W_v\, h^{(\ell-1)}_i,
\]

and we compute multi–head attention restricted so that query \(Q_j\) attends only to keys/values whose underlying bytes lie inside its own patch \(p_j.\) The output replaces or augments \(P^{(\ell-1)}_j,\) after which it proceeds to either another encoder layer or—if this was the final encoder layer—to become input for $\mathcal G.$  

Key design choices:

* **No positional embeddings** in this module because relative order within each patch has already been captured by preceding self­attention windows.
* **Multi–head dimension** may be smaller than that of later global processing (\(U_{\mathcal E}<h_{\mathcal G}\)); after cross‐attention we concatenate heads back into full dimensionality.
* **Residual connections** ensure stable gradient flow across many patches.

### 3.5 Query Initialization Choices

Three strategies were explored:

| Strategy | Description |
|----------|-------------|
| Learned constant | Same learnable vector for every query regardless of content |
| Hash embedding | Query equals sum of hash n‑gram embeddings for bytes inside the patch |
| Max‐pool | Query obtained by max‑pooling across encoder hidden states belonging to the patch |

Empirically max‑pooling yielded slightly better downstream performance while remaining simple; hash initialization helped when combined with deeper decoders.

### 3.6 Positional Encoding Choices

Within self‐attention layers we use RoPE with large scaling factor ($\theta=500\,000$), which provides smooth relative position encoding without adding explicit learnable tables—important because patches vary in length and static absolute positions would be ambiguous across different data points. No positional encoding is added to cross‐attention because its masking already enforces strict intra‑patch locality.

---

## 4. Local Decoder

The decoder mirrors many aspects of the encoder but works in reverse: it starts from latent patches produced by $\mathcal G$ and reconstructs raw bytes one at a time.

### 4.1 Symmetric Cross‑Attention

In contrast to encoder cross‐attention where patches queried bytes, decoder cross‐attention lets each *byte query* attend to relevant *patch vectors*. Concretely:

* **Queries** – current per–byte hidden state $d_{l,i}$ (initially set to encoder’s final hidden vectors).
* **Keys / Values** – linear projections of all global outputs $\{o_j\}_{j=1}^m,$ duplicated across heads:
  
  \[
  K_j = W_k\, o_j,\qquad V_j=W_v\, o_j .
  \]

Since each byte belongs uniquely to one source patch, we mask queries so they can attend only to their originating patch’s key/value pair; this maintains deterministic reconstruction without leakage across patches.

The attention output updates each byte representation:

\[
d'_{l,i}= d_{l,i}+W_o\, {\rm softmax}\Bigl(\frac{
 Q_i K^\top}{\sqrt{d_k}}\Bigr)V .
\]

A residual connection surrounds this block just like in Perceiver’s original formulation.

### 4.2 Decoder Transformer Layers

After cross-attention we feed the updated byte vectors through $l_{\mathcal D}$ lightweight transformer layers with local block causal windows ($w_{\mathcal D}$ analogous to encoder). These layers refine byte predictions while staying computationally cheap because they operate over far fewer steps than would be required if every byte were processed by a full deep transformer.

### 4.3 Output Projection and Training Objective

The final decoder hidden state at position $i$, denoted $d_{L,i}\in \mathbb R^{h_{\mathcal D}}$, is projected onto logits over the full byte vocabulary:

\[
z_i = W_{\rm out}\, d_{L,i} + b_{\rm out},
    \qquad W_{\rm out}\in \mathbb R^{256\times h_{\mathcal D}} .
\]

A standard categorical cross–entropy loss is applied against target byte $x_i$:  

\[
\ell_i = -\, \log p(x_i | x_{<i}),
    \quad 
    p(x_i)= {\rm softmax}(z_i).
\]

During training this loss is summed over all bytes in a batch; during evaluation we report Bits‑Per‑Byte (BPB),

\[
{\rm BPB}= 
   \frac{\sum_i \ell_i}{\,n\,\ln(2)},
\]

which normalizes perplexity by raw byte count and thus allows fair comparison between tokenizer­-based and token­less models.

### 4.4 Interaction Between Encoder and Decoder Hidden States

Although encoding and decoding are separate modules, they share two crucial pathways:

1. **Encoder hidden states feed decoder queries:** The initial decoder queries are set equal to encoder outputs at corresponding byte positions ($d_{0,i}=h_{l_\mathcal E,i}$). This provides fine–grained context about sub‑patch structure before any global information arrives.
2. **Global latent transformer bridges them:** The latent representation flowing from encoder → cross‑attention → global transformer → decoder cross‑attention acts as an information bottleneck; augmenting it improves long–range coherence while preserving locality in both direction passes.

The cascade thus resembles an autoencoder where compression occurs at dynamic granularity determined by entropy; decompressing restores exact byte order required for language modeling loss.

---

## 5. Summary of Architectural Contributions

| Component | Primary Function | Key Design Choices | Effect on FLOPs |
|-----------|-----------------|--------------------|-----------------|
| Local Encoder | Transform raw bytes → compact per-patch queries | Byte lookup + hash n-gram augmentation; shallow transformer ($l_\mathcal E$); local block-causal window; Perceiver-style cross-attention | Constant per-byte cost regardless of model size |
| Global Latent Transformer | Autoregressive modeling over patches | Deep transformer ($l_\mathcal G$); block-causal mask; full self-attention over patches | Dominates total FLOPs; inversely proportional to average patch size |
| Local Decoder | Expand latent patches back → raw bytes | Symmetric cross-attention (bytes query patches); light decoder (`l_\mathcal D`); output projection onto vocabulary | Small per-byte overhead; enables exact token-free generation |

By decoupling “how much” computation (global depth/width) from “how often” it occurs (patch frequency), BLT can allocate more parameters where they matter most—on high entropy portions of text—while saving compute on trivial continuations such as whitespace or predictable code identifiers. This architecture underlies all empirical gains reported in the paper: parity with Llama 3 at compute-optimal training budgets, up-to-50% inference FLOP reduction, robust handling of noisy inputs, and superior scaling when both model size and average patch size grow together under fixed inference cost constraints.

---

# Training Procedure and Data Handling  

In this chapter we describe in depth how the **Byte Latent Transformer (BLT)** is pretrained.  We focus on the concrete choices that make it possible to compare BLT fairly with token‑based baselines while keeping the total floating‑point‑operation (FLOP) budget under control.  The discussion follows the terminology and methodology introduced in the original paper, and every component is explained from first principles so that a newcomer can understand how to reproduce the experiments or adapt them to new settings.

---

## Pretraining Corpora: Llama‑2 Mix vs BLT‑1T  

### Llama‑2 Mix  

The first corpus used for scaling‑law experiments mirrors the data employed to train the Llama 2 family of models.  It consists of roughly **2 trillion tokens** drawn from a heterogeneous collection of web pages, books, code repositories, and scientific articles.  The raw text is first **tokenized with the Llama 3 BPE tokenizer** (vocabulary size 128 K) so that it can be compared directly against BPE baselines, but for BLT the same raw bytes are retained; tokenization is only used to define a reference training schedule.

Before pretraining, each document undergoes a standard cleaning pipeline:

1. **HTML stripping** – all markup tags are removed while preserving visible text.
2. **Language detection** – documents identified as non‑Latin scripts are retained, but low‑quality language‐identification failures are filtered out.
3. **Deduplication** – exact and near‑duplicate lines are eliminated using a MinHash fingerprint with a Jaccard threshold of 0.8.
4. **Safety filtering** – any content matching a list of prohibited patterns (e.g., personal data, hate speech) is discarded.

After cleaning, each document is represented as a **byte sequence** \(\mathbf{x} = \{x_{1},\dots ,x_{n}\}\), where each \(x_{i}\) is an integer in \([0,255]\).  No further preprocessing (e.g., lowercasing) is performed because BLT aims to preserve all sub‑byte information.

### BLT‑1T Dataset  

For the large‑scale “beyond compute‑optimal” experiments a second corpus called **BLT‑1T** is assembled.  It contains roughly **1 trillion tokens** (≈ 4 trillion bytes) drawn from:

- A subset of the publicly released *Datacomp‑LM* data,
- Large web crawls filtered analogously to the Llama 2 mix,
- Additional multilingual sources to ensure broad script coverage.

The same cleaning steps described above are applied, yielding a high‑quality byte stream that matches the distribution used for BLT’s entropy model (see next section).  Importantly, all data remain **tokenizer‑free** throughout training; the only grouping operation performed later is dynamic patching.

Both corpora are stored in sharded binary files where each record contains a length field followed by the raw byte payload.  This format enables fast streaming reads during data loading and simplifies on‑the‑fly patch segmentation.

---

## Entropy Model Specifics  

Dynamic patching hinges on an auxiliary **byte‑level language model** that predicts the entropy of the next byte given its left context.  The entropy model is trained **once** on the same pretraining distribution as BLT and then frozen; its predictions are used only during dataset preprocessing to decide where patch boundaries should lie.

### Architecture  

The entropy model follows a standard transformer decoder layout with:

- **Parameter count:** \(100\text{ M}\) (≈ 14 layers),
- **Hidden dimension:** \(h_{\mathcal{E}} = 512\),
- **Feed‑forward dimension:** \(4h_{\mathcal{E}} = 2048\),
- **Number of attention heads:** 8,
- **Windowed self‑attention:** each token attends to at most the preceding \(w = 512\) bytes.

All layers employ **SwiGLU** activations, RMSNorm normalization, and rotary positional embeddings (RoPE) with \(\theta = 500{,}000\).  Because the model processes bytes directly, its input embedding matrix has shape \(\mathbb{R}^{256 \times h_{\mathcal{E}}}\).  No additional hash‑n‑gram embeddings are used for this model; they would increase FLOPs without improving entropy estimation significantly.

### Sliding Window & Lookup Table Approximation  

When the attention window is small (\(w \leq 256\)), the entropy model’s forward pass can be compiled into a compact lookup table: for each possible context hash we store the distribution over the next byte.  This reduces inference during patching to an essentially O(1) operation per byte, which is crucial because patch boundaries must be identified for millions of sequences in each training epoch.

In practice we train three variants of the entropy model (window sizes 64, 256, and 512) and find that increasing window size beyond 256 yields diminishing returns on boundary quality while increasing memory consumption.  The final experiments adopt \(w = 512\) with a straightforward forward pass rather than a lookup table because GPU memory is abundant during preprocessing.

### Training Procedure  

The entropy model minimizes standard causal cross‑entropy loss:

\[
\mathcal{L}_{\text{CE}}(\mathbf{x}) = -\sum_{i=1}^{n}\log p_{e}(x_{i}=v_{i}\mid \mathbf{x}_{<i}),
\]

where \(p_{e}\) denotes the softmax output of the model at position \(i\).  
Optimization uses AdamW with \(\beta_{1}=0.9\), \(\beta_{2}=0.95\), \(\epsilon=10^{-8}\), a learning rate of \(5\times10^{-4}\), weight decay \(0.1\), and cosine decay after linear warmup for \(2{,}000\) steps.  
Training proceeds for enough steps to achieve convergence on a held‑out validation split (typically ≈ 200 B tokens).  
Once trained, checkpoints are frozen; at runtime only the forward pass (or table lookup) is needed.

---

## Determining Entropy Thresholds for Target Patch Size  

A deterministic *patching function* \(f_{p}\) maps each byte position to either “continue current patch” or “start new patch”.  For entropy‑based patching we compute a scalar **entropy estimate**

\[
H(x_{t}) = -\sum_{v\in \mathcal{V}} p_{e}(x_{t}=v \mid \mathbf{x}_{<t})\,\log p_{e}(x_{t}=v \mid \mathbf{x}_{<t}),
\]

where \(\mathcal{V}\) is the set of 256 possible byte values.

Two simple decision rules are explored:

| Rule | Condition |
|------|-----------|
| Global threshold | \(H(x_{t}) > \theta_{g}\) |
| Approximate monotonicity | \(H(x_{t}) - H(x_{t-1}) > \theta_{r}\) |

The thresholds \(\theta_{g}\) and \(\theta_{r}\) are not arbitrary; they are calibrated so that the *expected* average patch size equals a target value (e.g., \(4.5\) bytes).  The calibration proceeds as follows:

1. Run the entropy model on a large random sample of training bytes (≈ 10 M bytes).
2. For each candidate threshold compute the resulting number of patches \(m\).
3. Derive average patch length \( \overline{s}= n_{\text{bytes}}/m\).
4. Choose thresholds yielding \(\overline{s}\) closest to desired size while keeping variance modest.

Because BLT must operate **incrementally** at inference time—i.e., it cannot look ahead—the thresholds are applied online as each byte arrives; no future context is consulted beyond what has already been processed by the entropy model.

When training on BLT‑1T we observed “entropy drift” in very long repetitive documents (e.g., multiple choice questions). To mitigate this effect we *reset* the entropy context at each newline character before recomputing entropies for the subsequent line; this keeps local entropy estimates stable across document boundaries.

---

## Batch Composition Under Variable Patch Counts  

Dynamic patching means that two training examples containing exactly the same number of bytes may produce different numbers of patches after segmentation.  Since BLT’s expensive component—the global latent transformer—operates on patches rather than bytes, it is essential to keep the number of patches per minibatch roughly constant to avoid load imbalance and excessive padding.

### Packing Strategy  

During data loading we perform **patch packing**:

1. Sample a batch of raw byte sequences until their *total byte* count exceeds a target budget (e.g., \(16\,\text{MiB}\)).
2. Apply `f_p` to each sequence independently, yielding variable numbers of patches.
3. Concatenate all patches from all sequences into a *single* packed tensor `[total_patches]`.
4. Record an index map so that later stages can reconstruct per‑example boundaries if needed (e.g., for loss masking).

Because patches belong to a single contiguous tensor, padding occurs only once at the end of each packed batch rather than per example.   The total number of patches per batch therefore stays within a narrow band around `target_patches = target_bytes / expected_patch_size`. 

### Padding & Truncation  

To guard against pathological outliers—documents that produce extremely long patches—we enforce:

- A maximum allowed patch length `max_patch_len = 32` bytes.
- If a patch exceeds this length we split it greedily at its midpoint; this maintains monotonicity without altering overall FLOP counts substantially.
- Byte sequences longer than `max_seq_len` (12 kB for Llama 2 mix; 24 kB for BLT‑1T) are truncated after tokenizing or patching respectively.
- Shorter sequences are padded with a special *null byte* (`0x00`) after they have been patched; padding tokens do not affect loss calculation because their cross‑entropy contribution is masked out.

These safeguards keep GPU memory usage predictable while preserving statistical fidelity across batches.

---

## Maintaining Constant Byte Context Length Across Models  

When comparing BLT against BPE baselines we must ensure that any performance differences stem from architectural innovations rather than merely longer effective contexts.  The paper therefore holds **average byte context length constant in expectation**, even though patch sizes differ.

### Procedure  

- For BPE models we use an established context window measured in *tokens*, e.g., `ctx_tokens = 8192`.  
- Translating this into bytes gives an expected number of bytes `E[n_{\text{bytes}}] = ctx_tokens × \overline{\text{token size}}`.  
- For BLT we fix `ctx_bytes` directly: `8 kB` when training on Llama 2 mix and `16 kB` when training on BLT‑1T.
- If after patching our sequence contains fewer patches than required for `ctx_bytes`, we pad additional “dummy” patches whose representations are zeroed out; conversely if more patches appear we simply truncate at `ctx_bytes`.

Because FLOP cost scales inversely with average patch size (`flops ∝ #patches`), fixing `ctx_bytes` ensures that any reduction in FLOPs truly reflects more efficient computation per step rather than simply processing fewer bytes overall.

---

## Optimizer Settings, Learning Rate Schedule, Weight Decay & Gradient Clipping  

All experiments share an identical optimization configuration so that FLOP budgets can be compared directly between architectures.

| Hyperparameter | Value |
|----------------|-------|
| Optimizer | AdamW |
| β₁ | 0.9 |
| β₂ | 0.95 |
| ε | \(10^{-8}\) |
| Base learning rate | \(4\times10^{-4}\) |
| Warmup steps | 2 000 |
| Learning rate schedule | Cosine decay from peak LR down to zero at end of pretraining |
| Weight decay | 0.1 |
| Gradient clipping norm | 1.0 (global norm across all parameters) |
| Batch size (in bytes) | Fixed per experiment (see Section “Batch composition”) |

The base learning rate was chosen after sweeping logarithmically between \(1\times10^{-3}\) and \(1\times10^{-4}\) on both a $400$ M and $1$ B parameter configuration; both scales exhibited optimal validation loss around \(4\times10^{-4}\). Importantly this LR is applied uniformly across all three modules (\(\mathcal{E}, \mathcal{G}, \mathcal{D}\)).  
During “distillation” experiments where BLT’s global transformer is initialized from Llama 3 weights we reduce its LR by an order of magnitude (\(4\times10^{-5}\)) while keeping encoder/decoder LR unchanged; this prevents catastrophic forgetting in already‐trained high‑capacity weights while still allowing fine‐tuning needed for byte-level tasks.

## FLOP Accounting Methodology  

Accurate FLOP accounting enables us to claim *flop‑controlled parity* with tokenizers such as Llama 3. The paper follows Chinchilla’s formulation but adapts it to three interacting modules plus cross‑attention steps.

### Forward vs Backward Passes  

For any transformer layer with hidden size \(h\), depth \(l\), sequence length \(m\), and vocabulary size \(V\), Chinchilla approximates forward FLOPs as

\[
\operatorname{FL}_{\text{FFN}} = m\,l\,[\,8h^{2} +
    4h\,d_{\text{ff}}\,],
\]
where `d_ff` denotes FFN inner dimension (typically $4h$).  
Self–attention contributes

\[
\operatorname{FL}_{\text{SA}}= m\,l\, [\,4hd_{\!k}+4hd_{\!v}+2mh^{2}+2h^{2}].
\]

Because BLT’s embedding lookup is an index operation rather than matrix multiplication its cost is considered zero FLOPs.

A backward pass roughly doubles these counts (the paper assumes *twice* forward FLOPs), so total training FLOPs per iteration equal

\[
\operatorname{FL}_{\text{train}} = 
    (\operatorname{FL}_{\text{forward}}+\operatorname{FL}_{\text{backward}})
    =3\times \operatorname{FL}_{\text{forward}}.
\]

### Module-Level Breakdown  

Let:

- \(n_{\text{ctx}}\): total number of bytes fed to one forward pass,
- \(n_{\text{p}}\): resulting number of patches,
- \(h_{\mathcal G}, l_{\mathcal G}\): hidden size / depth of global latent transformer,
- \(h_{\mathcal E}, l_{\mathcal E}, w_{\mathcal E}\): hidden size / depth / attention window for encoder,
- Similar symbols with subscript \(\mathcal D\) for decoder,
- \(k = h_{\mathcal G}/h_{\mathcal E}\): ratio between global and local hidden dimensions,
- \(V=256\): byte vocabulary used only by decoder’s final linear projection.

The total FLOPs per *byte* processed by BLT are then

\[
\begin{aligned}
    {\rm FL}_{\rm BLT}
    &= 
        \underbrace{\frac{\operatorname{Transf.\!FL}(h_{\mathcal G}, l_{\mathcal G},
                m=n_{\text{ctx}}/n_{\text p}, V=0)} {n_{\text p}}}_{%
                \text{global latent transformer per patch}}
      + 
        \underbrace{\operatorname{Transf.\!FL}(h_{\mathcal E}, l_{\mathcal E},
                m=w_{\mathcal E}, V=0)}_%
                {\text{local encoder}}
      + 
        \underbrace{\operatorname{Transf.\!FL}(h_{\mathcal D}, l_{\mathcal D},
                m=w_{\mathcal D}, V=256)}_%
                {\text{local decoder}}\\[4pt]
      &+ 
        \underbrace{\operatorname{CrossAttn.\!FL}(h_{\mathcal E},
                l_{\mathcal E}, m=n_{\text p},
                r=n_{\text p}/k)\times
                k/n_{\text p}}_
                {\text{encoder cross‐attention}}
      + 
        \underbrace{\operatorname {CrossAttn.\!FL}(
                h_{\mathcal D},l_{\mathcal D},
                m=k,\ r=k/n_{\text p}) }_
                {\text{decoder cross‐attention}} .
\end{aligned}
\]

Each term represents either an attention block or an FFN block evaluated according to Chinchilla’s formulas; ``CrossAttn`` uses analogous expressions but replaces self–attention’s quadratic term with factor \(r=\frac{\#queries}{\#keys} = k/n_p.\)

The dominant term in most configurations is the global latent transformer because it processes every *patch*. By increasing average patch size—via higher entropy thresholds—the factor `\(m=n_\mathrm {ctx}/ n_\mathrm p)\)` shrinks, yielding fewer global steps and consequently fewer FLOPs per byte during both training and inference.

### Inference FLOP Control  

For inference experiments we fix an upper bound on total FLOPs per generated token by holding `average_patch_size` constant within each budget class (e.g., “low inference flop” vs “high inference flop”). Because every generated byte either belongs to an existing patch or triggers a new latent transformer step depending on whether its position marks a boundary, inference cost becomes

\[
{\rm FL}_{true}
   = ({\rm steps~per~patch})\,\, {\rm FL}_{{}^{}}\!\!( {\rm Global})
   + ({%no~global~step})\,\, {\rm FL}_{{}^{}}\!\!( {\rm Encoder/Decoder}),
\]

allowing clean comparisons against tokenizers that always invoke their full transformer at every token step.

---

## Summary  

Training BLT requires careful orchestration across several moving parts:

1. High‑quality raw-byte corpora (Llama 2 mix or BLT‑1T), cleaned but otherwise untouched.
2. A dedicated entropy estimator—a modest transformer—trained once and kept frozen.
3  A dynamic threshold calibration system guaranteeing target average patch sizes.
4  Batch packing strategies that normalize “patch count” rather than “byte count”.
5  Explicit control over byte context lengths so that baselines receive identical amounts of information.
6  Uniform optimizer hyperparameters ensuring comparable convergence dynamics.
7  A meticulous FLOP accounting pipeline derived from Chinchilla’s formulas extended to cross-attention modules.

Together these design choices enable **flop‐controlled parity** with state-of-the-art tokenization based models such as Llama 3 while simultaneously delivering up to fifty percent savings at inference time—a central claim explored throughout the rest of this work.

# Scaling Laws for Byte‑Level Models  

In this chapter we examine the empirical scaling behavior of the **Byte Latent Transformer (BLT)** and compare it with traditional tokenization‑based large language models (LLMs).  Scaling laws describe how model performance varies as a function of model size, data quantity, and computational budget (measured in floating‑point operations, or FLOPs).  By grounding the discussion in the experiments reported in the BLT paper, we can understand how the dynamic patching mechanism reshapes these trade‑offs, why patches tend to “scale better” than tokens, and what practical implications follow for model designers.

---

## 1. The “Compute‑Optimal” Regime for BLT  

The **compute‑optimal** regime is a principle introduced by Chinchilla and formalized by Hoffmann et al. It states that, for a fixed amount of training compute \(C\) (measured in FLOPs), the optimal performance is achieved when the number of training tokens \(N\) and the number of model parameters \(\Theta\) satisfy roughly  

\[
N \;\approx\; \frac{C}{2\,\text{Cost}_{\text{forward}}},\qquad 
\Theta \;\approx\; \frac{C}{4\,\text{Cost}_{\text{forward}}}.
\]

Here \(\text{Cost}_{\text{forward}}\) denotes the FLOPs required for a single forward pass through a transformer layer on one token (or patch).  The factor of two reflects that a backward pass costs about twice a forward pass.  When these relationships hold, the model uses **just enough data** to train its parameters without under‑ or over‑fitting.

Applying this rule to BLT requires two modifications:

1. **Patch‑level cost** – The primary computational engine in BLT is the *latent global transformer* which operates on patches rather than on tokens.  Consequently we replace the per‑token cost with a per‑patch cost that depends on the *average patch size* \(\bar{s}\) (bytes per patch).  
2. **Byte‑level overhead** – BLT also runs lightweight local encoder and decoder modules on every byte.  Their FLOP contribution is added to the overall cost but does not scale with \(\Theta\) in the same way as the global transformer.

Thus, for a given total FLOP budget \(C\),

\[
C \;=\; C_{\text{global}} + C_{\text{local}} 
      \;\approx\; \underbrace{\frac{\Theta}{4}\,\text{FL}_{\mathcal{G}}(\bar{s})}_{C_{\text{global}}}
                + \underbrace{\frac{N_{\text{bytes}}}{4}\,\bigl(\text{FL}_{\mathcal{E}}+\text{FL}_{\mathcal{D}}\bigr)}_{C_{\text{local}}},
\]

where \(\text{FL}_{\mathcal{G}}(\bar{s})\) denotes the FLOPs per patch for the global transformer (which depends inversely on \(\bar{s}\)), and \(\text{FL}_{\mathcal{E}},\text{FL}_{\mathcal{D}}\) are per‑byte FLOPs of encoder and decoder respectively.  Solving these equations for \(N_{\text{bytes}}\) and \(\Theta\) yields a *BLT‑specific* compute‑optimal curve that can be compared directly with the classic Chinchilla curve for tokenizers.

---

## 2. Parameter‑Matched Experiments (1 B–8 B) on Llama 2 Data  

To test whether BLT obeys the same compute‑optimal scaling as tokenizers, researchers trained **parameter‑matched** families of models:

| Model family | Parameter count | Patch / Token regime | Training data (bytes) |
|--------------|----------------|----------------------|-----------------------|
| BPE‑Llama3   | 1 B, 2 B, 4 B, 8 B | Fixed vocabulary (≈4.4 bytes/token) | Llama 2 mixture |
| BLT‑Space    | same as BPE    | Space patching (≈6 bytes/patch)      | Llama 2 mixture |
| BLT‑Entropy  | same as BPE    | Entropy patching (≈4.5 bytes/patch)  | Llama 2 mixture |

All models received a **training FLOP budget equal to the Chinchilla optimum** for their size on the Llama 2 dataset (≈\(1.5\times10^{23}\) FLOPs for an 8 B model).  The training objective was a standard byte‐level auto‑regressive cross‑entropy; performance was measured using **Bits‑Per‑Byte (BPB)**, which normalizes loss by byte count and avoids tokenizer dependence.

### 2.1 Training FLOPs vs BPB  

Figure 1 (reproduced from the paper) plots training FLOPs on the horizontal axis and BPB on the vertical axis for each family.  The key observations are:

- **BLT matches or surpasses BPE** across all parameter regimes.  
- The entropy‑based patching (`BLT‑Entropy`) consistently sits **0.02–0.03 BPB lower** than BPE at equal FLOPs, indicating more efficient use of compute.
- Space patching (`BLT‑Space`) lags behind BPE at low FLOPs but **catches up** as model size grows, reflecting that larger patches become advantageous when the global transformer dominates compute.

These results show that *the optimal ratio of parameters to training compute derived from token models transfers well to BLT*, confirming that dynamic patching does not break the fundamental scaling law.

---

## 3. Influence of Average Patch Size on Inference FLOPs  

During inference only the global transformer is invoked **once per patch**; therefore inference FLOPs scale inversely with average patch size \(\bar{s}\):

\[
\text{Inference FLOPs} \;\propto\; \frac{\Theta}{\bar{s}}.
\]

If we double \(\bar{s}\) from 4 bytes to 8 bytes while keeping \(\Theta\) fixed, inference cost halves.  However, larger patches also reduce granularity: predictions within a patch must be generated by the local decoder, potentially sacrificing accuracy if patches become too coarse.

The paper reports three concrete trade‑offs:

| Avg. Patch Size | Inference FLOP reduction vs BPE | BPB change (ΔBPB) |
|-----------------|--------------------------------|-------------------|
| 4.5 bytes       | ~30 %                          | –0.01             |
| 6 bytes         | ~45 %                          | +0.02             |
| 8 bytes         | ~50 %                          | +0.04             |

Thus **moderate increases** (to ≈6 bytes) achieve substantial speed gains with negligible loss in modeling quality, whereas very large patches begin to hurt perplexity slightly because fine-grained byte predictions become harder for the lightweight decoder.

---

## 4. “Beyond Compute Optimal” – Training an 8 B BLT on a Larger Data Mix  

The compute‑optimal experiments deliberately limit training data to satisfy Chinchilla’s rule.  To explore *whether additional data can further improve BLT*, an **8 B BLT‐Entropy** model was trained on **BLT‑1T**, a high‑quality corpus containing roughly **4 ×10¹² bytes**—far more than required for compute optimality.

All three models (BPE Llama 3 tokenizer, BLT‑Space, BLT‑Entropy) were given *the same total FLOP budget*; therefore BLT‐Entropy simply spent more time processing extra data rather than increasing model size.

### Results on Downstream Benchmarks  

| Task                         | BPE Llama 3 | BLT‑Space | BLT‑Entropy |
|------------------------------|-------------|-----------|-------------|
| ARC‐Easy (0‑shot)            | 71.3%       | 70.1%     | **73.5%**   |
| HellaSwag (0‑shot)           | 78.9%       | 74.2%     | **81.0%**   |
| MMLU (5‑shot)                | 57.6%       | 55.8%     | **59.3%**   |
| MBPP (3‑shot, pass@1)        | 42.1%       | 38.9%     | **44.7%**   |
| HumanEval (0‑shot, pass@1)   | 18.6%       | 16.0%     | **20.2%**   |

The entropy‐patched BLT not only retained its advantage over BPE in most tasks but also *outperformed* it on four out of seven benchmarks despite receiving no extra parameters. This confirms that **dynamic allocation of compute via entropy patching yields tangible downstream benefits**, especially when ample training data is available.

---

## 5. Fixed Inference FLOP Scaling Study  

A particularly novel contribution of BLT is its ability to keep inference FLOPs *fixed* while increasing model capacity by enlarging patches—a freedom unavailable to tokenizers because token length is tied to vocabulary size.

### Experimental Design  

- Two baseline tokenizers: Llama 2 vocab (≈3.7 bytes/token) and Llama 3 vocab (≈4 bytes/token).  
- Three BLT configurations:  
  - `BLT(ps=4)` – average patch ≈4 bytes  
  - `BLT(ps=6)` – average patch ≈6 bytes  
  - `BLT(ps=8)` – average patch ≈8 bytes  
- For each configuration, model parameters were varied from **400 M** up to **8 B**, while adjusting context length so that each forward pass consumed exactly the same number of inference FLOPs.

### Scaling Curves  

Figure 2 plots BPB against total training FLOPs for each family under this *inference‐flop constraint*. The salient patterns are:

1. **Early regime:** Tokenizer models dominate when training budgets are low; their finer granularity yields slightly better BPB.
2. **Crossover:** Around \(2–3\times\) the Chinchilla optimal budget, `BLT(ps=6)` overtakes tokenizers; `BLT(ps=8)` crosses even earlier because its larger patches free up more compute for enlarging \(\Theta\).
3. **Steeper slopes:** As training FLOPs increase further, BLT curves maintain a steeper descent in BPB—evidence that *larger patches enable larger models without exceeding inference cost*, achieving better data efficiency.

These observations validate one of the paper’s core claims: **patch length scales more favorably than token length**, because increasing patch size reduces inference steps linearly while allowing a proportional increase in model depth or width.

---

## 6. Key Takeaways  

1️⃣ **Compute‐optimal scaling transfers:** When matched on parameter count and total FLOPs, entropy‐patched BLTs achieve parity or modest improvements over state‑of‑the‑art BPE models across the full 1–8 B range.

2️⃣ **Average patch size directly controls inference cost:**  
   - Doubling average patch size ≈ halves inference FLOPs under a fixed parameter budget.
   - Moderate patches (~6 bytes) give ~45 % inference savings with negligible BPB impact.

3️⃣ **Training beyond the Chinchilla optimum still helps:** An overabundance of high‑quality bytes further narrows—or even reverses—the performance gap between BLT and tokenizers on downstream tasks.

4️⃣ **Fixed‐inference scaling unlocks new regimes:** By reallocating saved inference compute from longer patches into deeper/wider global transformers, BLTs can outpace tokenizers at equal inference budgets once training exceeds roughly twice the optimal compute budget.

5️⃣ **Crossover points shrink with larger patches:** For `ps=8`, crossover occurs near \(2\times\) optimal compute; for `ps=4` it remains closer to \(3\times\). This demonstrates a clear *tradeoff curve* that practitioners can navigate based on latency constraints.

In sum, empirical evidence from extensive scaling experiments shows that *patches indeed scale better than tokens*. The dynamic entropy-driven grouping lets a Byte Latent Transformer reap both efficiency gains during inference and robustness improvements during training—all while preserving—or even exceeding—the performance ceiling set by traditional tokenizer-dependent LLMs.

# Evaluation on Downstream Tasks  

In this chapter we examine how the **Byte Latent Transformer** (BLT) performs when it is asked to solve a variety of downstream problems that are commonly used to gauge the abilities of large language models.  All experiments are carried out under a *flop‑controlled* regime: every model—whether it is a conventional BPE‑based Llama 3 baseline or one of the two BLT variants—receives the same total number of floating‑point operations during inference.  By equalising the computational budget we can attribute any differences in scores directly to architectural choices (static vs. entropy‑driven patching, the presence of a latent transformer, etc.) rather than to simply using more compute.

The evaluation suite covers four families of tasks:

1. **Classification / Multiple‑choice reasoning** – ARC‑Easy, ARC‑Challenge, HellaSwag, PIQA and MMLU (5‑shot).  
2. **Code generation** – MBPP (3‑shot) and HumanEval (0‑shot).  

These benchmarks collectively probe factual recall, commonsense reasoning, problem solving, and the ability to synthesize syntactically correct programs.  Because BLT works directly on raw bytes, we also have an opportunity to assess whether byte‑level modeling brings any systematic advantage on tasks that require fine‑grained orthographic or sub‑word knowledge.

---

## Task Suite Description  

### ARC‑Easy / ARC‑Challenge  
The *Artificial Intelligence Reasoning Challenge* (ARC) consists of multiple‑choice science questions.  The *Easy* split contains questions that most elementary‑school students can answer; the *Challenge* split is deliberately harder, requiring multi‑step inference and occasional domain knowledge.  In our experiments we use a **zero‑shot** protocol: the model receives only the question stem and the four answer options, and we select the answer with the highest log‑likelihood under the model’s distribution.

### HellaSwag  
HellaSwag asks for the most plausible continuation of a short narrative excerpt out of four alternatives.  It is designed to penalise surface‑level pattern matching by insisting that the correct continuation be highly context dependent.  Like ARC we evaluate in a zero‑shot fashion.

### PIQA  
The *Physical Interaction Question Answering* benchmark presents everyday physics problems (“Which object will break more easily …?”) and four answer choices.  Again we employ a zero‑shot log‑likelihood scoring method.

### MMLU (Massive Multitask Language Understanding) – 5‑shot  
MMLU contains over 57 subject areas ranging from elementary school mathematics to professional law.  For each question we provide **five exemplars** drawn from the same subject as few‑shot context, following the standard evaluation protocol used for Llama 3.  The model’s answer is selected by comparing per‑token log‑probabilities for each answer choice.

### MBPP (Microsoft Billion Word Programming) – 3‑shot  
Each MBPP item consists of a natural language description of a small programming problem and three exemplar solutions.  The model must generate a completing Python snippet from scratch; success is measured by exact match after execution on hidden test cases (the *pass@1* metric).  

### HumanEval – 0‑shot  
HumanEval contains short programming problems together with a reference solution and test suite.  The model is prompted only with the problem description (no exemplars) and its generated code is run against the tests; *pass@1* denotes the proportion of problems for which at least one generated sample passes all tests.

All tasks are evaluated **exactly** as described in the original papers, with no prompt engineering beyond what is required for few‑shot protocols. This ensures that any advantage observed for BLT stems from its internal representation power rather than from task‑specific prompting tricks.

---

## Quantitative Results Under Equal FLOP Budgets  

The table below summarises the outcomes when each model is allocated exactly the same *inference* flop budget (≈ 0.8 × the flops required by Llama 3’s default tokenisation pipeline).  The two BLT variants differ only in how they decide where to place patch boundaries:

| Model                | Patch Strategy | Avg. Patch Size (bytes) | ARC‑Easy | ARC‑Challenge | HellaSwag | PIQA | MMLU (5‑shot) | MBPP (3‑shot) | HumanEval |
|----------------------|----------------|------------------------|----------|----------------|-----------|------|----------------|----------------|-----------|
| Llama 3 (BPE)        | –              | 4.4 ± 0.2               | **86.2%** | **68.1%**      | **79.4%**   | **81.7%** | **71.9%**        | **73.5%**       | **44.2%** |
| BLT – Space          | whitespace      | 6.0 ± 0.5               | 78.3%   | 60.4%          | 71.2%      | 74.9%   | 66.1%           | 68.9%           | 38.7% |
| BLT – Entropy       | entropy‐threshold + monotonicity | 4.5 ± 0.3               | 84.7%   | **69.5%**      | **80.9%**   | **82.5%**   | **73.4%**        | **77.1%**       | **46.8%** |

A few observations are immediately apparent:

* **Entropy patching narrows or closes the gap to Llama 3 on almost every metric**, despite operating under fewer flops per byte because larger patches are processed less frequently.
* On *MMLU* (the most demanding multitask benchmark), BLT–Entropy actually surpasses Llama 3 by about **1½ points**, indicating that dynamic patching helps even when reasoning across many domains.
* The *Space* variant lags behind both baselines because its patches are forced to align only with space‑like bytes; this restriction prevents it from fully exploiting low entropy stretches inside words (e.g., suffixes), leading to coarser granularity where finer patches would be beneficial.

Because all models see exactly the same number of *bytes* per batch during training (the context length is adjusted inversely with average patch size), we can safely attribute these improvements to more efficient utilisation of compute rather than to exposure to longer contexts.

---

## Why Entropy Patching Helps  

### Entropy as a Proxy for Predictive Difficulty  

Entropy patching relies on a tiny auxiliary byte‐level language model that estimates
\[
H(x_i)= -\sum_{v\in\mathcal{V}} p_e\bigl(x_i=v \mid \mathbf{x}_{<i}\bigr)\,
\log p_e\bigl(x_i=v \mid \mathbf{x}_{<i}\bigr),
\]
the Shannon entropy of the next‐byte distribution given all preceding bytes \(\mathbf{x}_{<i}\).  
Intuitively, large \(H(x_i)\) signals that many distinct continuations are plausible—exactly the situation where a powerful transformer should spend extra compute.

When we plot histograms of \(H(x_i)\) for tokens that appear at different positions within *answer* strings in ARC or MMLU, two clear patterns emerge:

1️⃣ The first byte after a space or newline generally has **high entropy**, reflecting uncertainty among many possible words that could start a new clause or sentence.
2️⃣ Subsequent bytes quickly settle into low‐entropy regimes because once a word’s prefix has been identified there are far fewer viable continuations.

Entropy patching therefore creates *short* patches around high‐entropy bytes (often just one or two bytes long) and *long* patches over low‐entropy stretches such as common suffixes (“…ing”, “…tion”) or repetitive code tokens (“;;”).  This adaptive granularity has two concrete effects:

* The global latent transformer processes only those short patches where sophisticated reasoning is needed, thereby dedicating more hidden states and attention heads precisely where they matter.
* Long low‑entropy patches bypass heavy computation altogether; they are simply encoded/decoded by the lightweight local models, which consume orders of magnitude fewer flops than an additional transformer layer would.

These effects explain why BLT–Entropy not only matches but occasionally surpasses Llama 3 on tasks that contain many “hard” decision points—e.g., selecting among multiple plausible next words in MMLU or completing code scaffolds in MBPP where newline boundaries create spikes in entropy.

### Approximate Monotonicity Constraint  

In practice we augment raw entropy values with an *approximate monotonicity constraint*, i.e.
\[
H(x_t)-H(x_{t-1}) > \theta_{r},
\]
which forces patch boundaries whenever entropy rises sharply relative to its immediate predecessor.  
This rule helps keep patches contiguous within a decreasing entropy segment even if absolute entropy stays above a global threshold \(\theta_g\).  
Empirically, adding this relative criterion reduces “patch fragmentation” on structured data such as source code: long comment blocks exhibit steadily decreasing entropy after an initial high‐entropy newline token, leading to one compact patch rather than many tiny ones.

---

## Patch Size vs Data Coverage  

### Trade–off Overview  

The average patch size \(\bar{s}\) directly determines how many steps the global transformer must execute:
\[
\text{#steps} = \frac{\text{context length in bytes}}{\bar{s}}.
\]
A larger \(\bar{s}\) means fewer steps → lower inference FLOPs; however it also implies that each global step must summarise more raw bytes using only information passed through the local encoder.

Two competing forces shape performance:

| Larger Patches (`↑\bar{s}`)                              | Smaller Patches (`↓\bar{s}`)                              |
|--------------------------------------------------------|-----------------------------------------------------------|
| ✔ Fewer transformer calls → lower FLOPs                | ✔ Finer granularity → better capture of high-entropy events |
| ✔ Ability to allocate saved FLOPs toward scaling model depth/width   | ✔ Lower risk of “information bottleneck” in latent representation |
| ✘ May smooth over subtle orthographic cues (e.g., diacritics)        | ✘ More frequent visits to expensive global transformer |

Because our flop budget is fixed, increasing \(\bar{s}\) frees up compute that can be reinvested into widening or deepening the latent transformer (\(l_{\mathcal{G}}\), hidden dimension \(h_{\mathcal{G}}\)).  In our experiments with BLT–Entropy we tested average patch sizes of approximately **4½ bytes**, **6 bytes**, and **8 bytes**:

* At **4½ bytes**, performance aligns closely with Llama 3 while retaining most of its original FLOP consumption.
* At **6 bytes**, inference FLOPs drop by ~30 %, and if we concomitantly enlarge \(l_{\mathcal{G}}\) by ~20 %, overall test scores stay within ±0 – 1 point of Llama 3.
* At **8 bytes**, inference FLOPs shrink by nearly **50 %**, but without expanding model capacity we observe modest degradations on tasks rich in fine line reasoning (e.g., MMLU). When we compensate by adding an extra encoder layer and modestly enlarging hidden dimensions, scores recover and even exceed Llama 3 on code generation tasks.

Thus *patch size should be viewed as an additional degree of freedom*: given a hard inference flop ceiling, one can move along a Pareto curve trading slightly coarser patches for a larger latent transformer—and vice versa—until task performance saturates.

### Empirical Illustration: Coverage vs Difficulty  

Consider the distribution of bytes covered per patch across three datasets:

| Dataset            | Avg.\ Patch Size (BLT–Entropy) | % Bytes in “high‐entropy” patches (< 2 bytes) |
|--------------------|---------------------------------|---------------------------------------------|
| ARC (question stems)    | 4.6                              │ 22 %                                        |
| MBPP (code scaffolds)   |\(≈\)5                          │ 16 %                                        |
| FLORES multilingual text│ 4.7                              │ 19 %                                        |

Even though only roughly one fifth of all bytes belong to short high-entropy patches, those fragments disproportionately influence downstream success: removing them entirely would cause classic tokenizers to mispredict entire answer choices or code identifiers, while preserving them allows BLT’s global transformer to focus precisely on those decision points.

---

## Summary  

The downstream evaluation demonstrates that under identical inference compute budgets:

1\. **Entropy‐driven dynamic patching consistently improves over static whitespace segmentation**, narrowing or eliminating performance gaps with strong BPE baselines across reasoning, classification, and code synthesis tasks.

2\. The gains arise because entropy patching aligns computational effort with *predictive difficulty*: high‐entropy bytes trigger dedicated latent transformer steps; low‐entropy stretches are efficiently handled by cheap local modules.

3\. *Patch size* offers an orthogonal scaling knob: enlarging average patches reduces FLOPs per token but may necessitate expanding latent model capacity to maintain accuracy—an exchange not available to traditional tokenizers whose vocabulary size fixes both average token length and output projection dimensionality.

Together these findings validate the central claim of Byte Latent Transformers: moving from fixed vocabularies to a flexible byte–patch representation yields models that are both more compute‐efficient and more robust across diverse downstream challenges, while preserving—or even improving—their ability to solve complex reasoning and programming problems under realistic resource constraints.
