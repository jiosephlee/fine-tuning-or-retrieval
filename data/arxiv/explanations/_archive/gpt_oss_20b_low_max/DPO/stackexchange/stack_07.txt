\title{Stack Exchange of the Paper: "Direct Preference Optimization: Your Language Model is Secretly a Reward Model"}

### How does DPO handle high‑dimensional outputs where computing $	heta(y|x)$ directly is infeasible?
Question:
In practice, $	heta(y|x)$ is computed via autoregressive decoding where we multiply token probabilities sequentially.  The DPO loss uses $	heta(y|x)$ as a whole.  Does this imply we need to compute the full joint probability for each pair during training?  If so, what tricks (e.g., caching, log‐sum‐exp tricks) are used to make it tractable?
Answer:
**Short answer**

You *do not* need to compute the joint probability of every answer pair from scratch for every training step.  
In DPO the term \(\theta(y|x)\) that appears inside the loss is evaluated exactly as it would be during normal autoregressive sampling – by summing the log‑probabilities of the tokens that make up \(y\).  
Because the loss only ever sees two completions \((y_w,y_l)\) from a single training example, we can reuse the cached per‑token logits that were already produced when generating those completions.  
The only extra cost is a tiny \(O(|y_w|+|y_l|)\) inference pass per example, which is negligible compared to a full forward pass of the policy network.

Below is a detailed, step‑by‑step description of how this works and why it is tractable.

---

## 1. What DPO actually needs from \(\theta(y|x)\)

Recall the DPO loss (Eq. (6) in the paper):

\[
\mathcal{L}_{\text{DPO}}(\pi_{\theta};\pi_{\text{ref}})
=-\mathbb{E}_{(x,y_w,y_l)} \!\left[
  \log \sigma\!\Bigl(
      \beta\,\log\frac{\pi_{\theta}(y_w|x)}{\pi_{\text{ref}}(y_w|x)}
    - \beta\,\log\frac{\pi_{\theta}(y_l|x)}{\pi_{\text{ref}}(y_l|x)}
  \Bigr)
\right].
\]

The only places where \(\theta(y|x)=\pi_\theta(y|x)\) appears are inside the two logarithms of ratios.  
If we write a completion as a sequence of tokens \(y = (t_1,\dots ,t_L)\), then because the model is autoregressive,

\[
\pi_\theta(y|x)=
   \prod_{i=1}^{L}\pi_\theta(t_i | x, t_{<i}) .
\]

Taking logarithms turns this product into a sum:

\[
\log \pi_\theta(y|x)=
   \sum_{i=1}^{L} \log \pi_\theta(t_i | x,t_{<i}).
\]

Thus **only token‑wise log‑probabilities are needed**; we never need the global joint probability in closed form or any kind of partition function.

---

## 2. Computing the term that appears in DPO

For each training example we have a pair of completions:
- \(y_w = (w_1,\dots ,w_{L_w})\) – preferred
- \(y_l = (l_1,\dots ,l_{L_l})\) – dispreferred

We compute:

1. **Per‑token log‑probs for both completions**  
   This is exactly what you would do when you generate a sample from an LLM.  
   In practice we already have these logits because:
   - During preprocessing we asked the reference policy (e.g., a pre‑trained SFT model) to produce \(y_w,y_l\).  
   - The reference policy’s forward pass gives us all logits for each token position.
   - We then feed **the same context** and **the same sequence of tokens** through our *current* policy \(\pi_\theta\).  
     The transformer reuses all cached activations up to the *last* context token, so computing new logits for \(w_i,l_i\) costs only a few attention queries per token; no quadratic memory blow‑up.

2. **Sum these log‑probs to get sequence‑level logs**  
   \[
   s_\theta^w = \sum_{i=1}^{L_w}\!\log \pi_\theta(w_i | x,w_{<i}), 
   \qquad
   s_\theta^l = \sum_{i=1}^{L_l}\!\log \pi_\theta(l_i | x,l_{<i}).
   \]
   The reference model gives analogous sums \(s_{\text{ref}}^w, s_{\text{ref}}^l\).

3. **Form the ratio in log space**  
   Because
   \[
    \log \frac{\pi_\theta(y)}{\pi_{\text{ref}}(y)} =
    s_\theta - s_{\text{ref}},
   \]
   we can compute
   \[
     r_\theta^w = s_\theta^w - s_{\text{ref}}^w,
     \qquad
     r_\theta^l = s_\theta^l - s_{\text{ref}}^l .
   \]
   These are precisely the “implicit rewards” shown in Eq. (8).

4. **Insert into DPO loss**  
   Finally,
   \[
      u = 
        \beta (r_\theta^w - r_\theta^l),
      \qquad
      L = -\,\log\sigma(u).
   \]

All operations are simple vector sums and exponentials that fit comfortably on GPU memory, even for very long completions.

---

## 3. Why there is no expensive “partition function”

In Eq. (5) of the paper the optimal policy contains a normalising constant
\(Z(x)=\sum_y e^{r(x,y)/\beta}\).  
That sum over *all* possible completions is indeed intractable for language models and would make learning impossible.

The key insight of DPO is that when we insert this optimal policy into the Bradley–Terry preference model (Eq. (3)), that normalising constant cancels out (see the derivation around Eq. (7)).  Consequently **the objective never contains any explicit dependence on \(Z(x)\)**, and we sidestep any need to estimate it.

Operating purely with per‑completion score differences therefore avoids both high‑dimensional sums and numerical instabilities associated with very large or very small values.
For numerical safety one usually keeps all operations in log‑space as described above; there is no need for special tricks such as “log–sum–exp” because we never compute a log–sum over an exponentially large set.

---

## 4. Practical implementation tricks

Although DPO already removes the biggest bottleneck, there are minor engineering touches that help keep training fast:

| Trick | Why it helps |
|-------|--------------|
| **Reusing token logits across policy updates** | When fine‑tuning many epochs on highly similar data (e.g., many human preference pairs built from SFT samples), cache transformer activations up to context end so each new completion reuses them cheaply. |
| **Batching across prompts** | Summing disjoint sequences inside a batch keeps GPU utilisation high; you process each pair’s tokens independently but all at once with `torch.gather` / `torch.index_select`. |
| **Mixed precision (FP16/FP32)** | The inner products for logits are unaffected; thanks to automatic loss scaling you get 2× speedup without loss of accuracy on modern cards. |
| **Built‑in autograd reduction** | Instead of manually writing `logit.sum(dim=1)` you can let PyTorch’s `nn.CrossEntropyLoss` produce `-∑ logits` directly; this already implements stable tricks like adding a constant before applying softmax if you prefer `torch.log_softmax`. |
| **Vectorised temperature scaling if sampling at test time** | At evaluation you sometimes want to compare policies with different sampling temperatures; using `softmax(logits / T)` instead of manual exponentials avoids overflow/underflow automatically. |

All these changes cost negligible extra line‐count and typically cut GPU usage by a factor of 2–4 relative to an untuned naive implementation.

---

## 5. Bottom line

- **No global joint probability needed:** The DPO loss uses *sequence‑level* scores that are simply sums of token log‐probabilities.
- **Only two completions per example:** Each training step deals with exactly two sequences (the human preferred and dispreferred ones), so we only perform forward passes over two short sequences – trivial compared with typical LM training.
- **Caching & vectorisation reduce cost further:** The reference logits can be cached; per‑token computations are highly parallelisable on GPUs.
- **No hand–crafted trick needed:** Stable fixed‐point maths—working in log space—is sufficient; there’s no need for elaborate log–sum–exp or importance sampling tricks because partition functions cancel out entirely.

So while it may look like “we have to compute θ(y ∣ x) completely for each pair,” in practice it amounts to one ordinary autoregressive forward pass per completion pair plus a small amount of bookkeeping—all tractable on modern GPUs and far cheaper than any RL sampling loop would be.
