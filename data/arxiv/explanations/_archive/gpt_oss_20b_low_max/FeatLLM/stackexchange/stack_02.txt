\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does the two‑step reasoning instruction prevent the LLM from learning spurious correlations?
Question:
The paper claims that instructing the LLM first to reason about *causal* relationships between features and the task (without seeing training examples) helps avoid spurious correlations that would otherwise arise from seeing only few demonstrations.  Can someone explain concretely how this two‑step protocol affects the rule set produced by the LLM, perhaps with an example?  Does it guarantee that irrelevant columns will never appear in any generated rule?
Answer:
**Short answer**

The two‑step protocol makes the LLM decide *which* columns are causally related to the label *before* it looks at the few training examples that might contain idiosyncratic spurious patterns. By conditioning the generation of rules on the outcome of that causal‑reasoning step, the LLM is biased toward features that are known (from its pre‑training) to be relevant, and it is far less likely to invent a rule involving an unrelated column. In practice this reduces the proportion of irrelevant rules from a few percent up to only 1–2 % of all generated rules. It does **not** guarantee absolute elimination of irrelevant columns, but it makes it highly unlikely for a useless column to survive into the final rule set unless the LLM explicitly learns a causal link.

---

## 1. What happens in each step

| Step | What the LLM sees | What it is asked to do |
|------|------------------|------------------------|
| **1 – Causal reasoning** | Task description + feature names and definitions (but **no** data rows). | Infer which features *could* affect the target based on world‑knowledge (“older age → higher heart‑disease risk”). |
| **2 – Rule construction** | The same task description + feature metadata **plus** a handful of serialized examples. | Use the causal list from step 1 together with the few examples to write concrete “if‑then” rules for each class. |

Because step 2 is explicitly told to “start from what you inferred in step 1”, the LLM is nudged towards *trusting* that prior knowledge over idiosyncratic patterns that might appear in only a handful of demonstration rows.

---

## 2. How this affects the actual rule set

### A concrete illustration

Suppose we have a tiny dataset with three numeric columns

| id |  A (age)  |  B (胆固醇) |  C (height) |  label |
|----|----------|------------|-----------|--------|
| 1  |   52     |    220     |    165    |   1   |
| 2  |   28     |    180     |    165    |   0   |

The feature descriptions are:
* **A** — integer, “patient age in years”.
* **B** — integer, “low‑density lipoprotein level”.
* **C** — integer, “height in cm”.

> **Step 1 (causal reasoning)**  
> *LLM says*: “The label is likely about heart disease. Age and cholesterol are known risk factors; height does not directly influence heart disease risk.”

> **Step 2 (rule construction)**  
> *LLM writes*:  
> - `If A > 50 AND B > 200 → label = 1`  
> - `If A ≤ 50 OR B ≤ 200 → label = 0`

Notice that **C** never appears in any rule even though we fed its name into the prompt. The only way C would bubble up is if step 1 had identified it as causally relevant—which it did not because its definition (“height”) offers no causal link to heart disease.

In contrast, if we were to let the LLM perform one step only—directly ingesting both examples and task description—the LLM might notice that *both* examples share height=165 and decide a spurious rule such as:

```
If C = 165 → label matches example
```

This would be a concrete spurious correlation derived purely from accidental alignment in two training rows.

---

## 3. Does it guarantee irrelevance?

No. The mechanism relies on *probabilistic inference*; an LLM can still hallucinate a causal link for an irrelevant column if:

1. The pre‑training corpus happened to mention some weak association (e.g., “people with short height tend to be younger”).
2. The chain‑of‑thought prompt misleads it or wording is ambiguous.
3. The hallucinated link is reinforced by very noisy data where multiple spurious columns happen to co‑occur with labels.

In practice, however, empirical results reported in §4.4 of the paper show that under these conditions only ~1–2 % of generated rules involve irrelevant columns when spurious columns are injected artificially. This suggests a high filtering power but not absolute certainty.

---

## 4. Why this matters for downstream training

The binary features produced from these rules serve as inputs to a simple non‑negative linear model (§3):

$$\text{logit}_k^i = \max(\mathbf{w}_k,0)\!\cdot\!\mathbf{z}_k^i ,$$

where $\mathbf{z}_k^i$ contains one entry per rule per class. Even if a few useless rules slip through, their corresponding weight will shrink toward zero during gradient updates because they provide almost no predictive signal over the small training set ($k$–shots). This additional *weight tuning* step further prunes weak or irrelevant rules, which is why ablation studies (§4.2) show a significant drop when tuning is omitted.

---

## 5. Bottom line

- The two‑step protocol gives the LLM a chance to bring in its background knowledge of *causal relevance*, acting as an inductive bias against overfitting on tiny datasets.
- In experiments adding dozens of unrelated columns caused only minor performance loss for FeatLLM, whereas models relying only on few‑shot in‑context learning degraded sharply.
- It does not theoretically forbid any irrelevant column from ending up in a final rule; but empirically its success rate is high enough that “rule filtering by prior knowledge” works practically.

So, while you cannot mathematically prove that no irrelevant feature will ever appear, you can trust that FeatLLM’s structured prompting makes it highly unlikely—making it an excellent first line of defense against spurious correlations in low‑shot tabular learning.^{†}
