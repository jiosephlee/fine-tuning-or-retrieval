# How Language Models Are Becoming Feature Engineers – A Primer  

## Why Feature Engineering Still Matters  

In classical tabular machine learning, turning raw columns into useful signals is often the single largest barrier to good performance.  
- **Domain knowledge**: Experts decide which thresholds or interactions matter.  
- **Group‑by statistics**: One‑hot encodings, bucketization, interaction terms, and ensemble of tree‑based models are typical tricks.  
- **Manual labor**: Creating, vetting, and maintaining feature pipelines can cost weeks or months when the data catalogue expands.

When labels are scarce – the so‑called *few‑shot* regime – the risk of overfitting skyrockets.  
A single spurious correlation can dominate a model because there is no data to “see through” it.

Large Language Models (LLMs) offer a new axis of knowledge: the massive text corpora they were trained on encode domain facts, causal relationships, and common sense reasoning. The recent work **FeatLLM** turns this latent knowledge into a *feature engineer*.

---

## The Core Idea of FeatLLM  

FeatLLM reframes an LLM from an end‑to‑end predictor to a rule generator:

1. **Prompt the LLM with a short task description + few labeled examples**.  
   * Example:* “Does this patient’s blood test hint at heart failure? Yes or No.”  
2. **Ask the LLM to first reason about how features causally influence the answer** (step one).  
   *No data used yet – pure prior knowledge.*  
3. **Then, use step‑one insights + concrete examples to produce concrete decision rules** for each class (step two).  
   *Typical rule:* “If *Age* > 60 AND *C-reactive protein* > 10 mg/L → chronic heart failure.”  

The output is deliberately constrained: at most ten rules per class, each expressed in a simple “IF … THEN …” syntax that can be parsed reliably.

---

### Turning Natural‑Language Rules into Binary Features  

The LLM can be fed a second prompt telling it to write Python code that turns each rule into a boolean feature (`True`/`False`) per sample.  
```python
def rule_1(x):
    return x["Age"] > 60 and x["CRP"] > 10
```
Executing these functions across all samples produces a new binary feature matrix \(Z \in \{0,1\}^{N\times R}\), where \(R\) is the total number of rules extracted.

---

## Learning How Important Each Rule Is

Fea­tLLM does not assume every rule is equally useful.  
A tiny linear classifier learns non‑negative weights \(\mathbf{w}_k\) for each class:
\[
\text{logit}_k = \max(\mathbf{w}_k ,0)\!\cdot\! \mathbf{z}_k ,
\quad
p_k = \frac{\exp(\text{logit}_k)}{\sum_j \exp(\text{logit}_j)} .
\]
The weights come from cross‑entropy loss on the few labeled examples (4–8 shots).  
Because \(Z\) has only binary values, training is fast and highly interpretable: a large weight signals that the rule strongly boosts classification probability.

---

## Bootstrapping Robustness with Bagging & Ensembling  

The same procedure is repeated multiple times:
- Shuffle the fewshot examples (order influences LLM output).  
- Sample subsets of features or instances (feature bagging).  
- Use a higher temperature for diversity.

Each run yields its own weight vector \(\mathbf{w}[t]\). Predictions are averaged across \(T\) runs:
\[
p_k^{\,avg} = \frac{1}{T}\sum_{t=1}^{T} p_k^{(t)} .
\]
This ensemble combats three practical problems:

| Problem | Viable Solution | Why FeatLLM Works |
|---------|-----------------|-------------------|
| Curated rules might be noisy | Bagging + averaging | Spurious rules drop out if rarely activated |
| Prompt length overflows context window | Feature subsampling | Only part of columns appear in each prompt |
| Inference cost high for per-sample LLM calls | Offline generation | Features are derived once; downstream model is lightweight |

## Experimental Highlights  

| Dataset | Shots | FeatLLM Performance | Baseline Rank |
|---------|-------|---------------------|----------------|
| Adult (binary) | 4 | AUC 0.77 ± 0.01 | #1 vs Logistic & XGBoost |
| Communities (multi‑class) | 4 | AUC 0.82 ± 0.02 | #2 vs RandomForest |
| Heart (binary) | 4 | AUC 0.86 ± 0.01 | #1 vs in‑context GPT |

Key observations:

- **Out-of-the-box competitiveness**: With only 4 labeled samples FeatLLM matches or surpasses traditional methods that use 32 shots.
- **Scalability to many features**: Even datasets with ~120 attributes remained tractable due to bagging.
- **No extra training beyond linear weights**: Compared to full fine‑tuning approaches like TabLLM or TABLoQ, FeatLLM uses just ~30 LLM calls and a few hundred gradient steps on local CPU/GPU.
- **Robustness against spurious covariates**: Adding unrelated columns degraded competitors by > 5 % AUC, while FeatLLM dropped < 2 %.

---

## Why This Matters for Low‑Shot Learning

1. **Data Economy** – Only a handful of labeled examples plus the LLM’s pre‑existing knowledge can deliver strong generalization.
2. **Interpretability** – The generated rules are human readable; stakeholders can audit them for bias or clinical plausibility.
3. **Operational Simplicity** – Once the binary feature matrix is built, inference costs shrink to thin linear passes; no per‐sample API traffic.
4. **Adaptability Across Domains** – Any tabular dataset with meaningful column names/definitions can be fed directly; no need for task‑specific fine tuning or access to internal model weights.

---

## Practical Takeaways

| What you need            | How FeatLLM Helps                          |
|--------------------------|-------------------------------------------|
| Short LLM API access     | Generating rules uses only ~30 calls per run |
| Minimal coding          | Prompt templates and auto‑generated code turn rules into features |
| Low compute budget      | Training weight matrix on CPU; inference latency ≤ 10 ms per sample |
| Explainable outcome     | Each rule carries semantics; weight magnitudes rank importance |

If you routinely face costly labeling cycles and have expensive tabular data (healthcare EMRs, financial risk scores), FeatLLM offers an experimentally grounded path from raw columns straight to deployable models—without wrestling hidden gradients inside gigantic transformer blocks.

---

## Looking Ahead

FeatLLM opens doors to richer feature creation beyond binary “rule” flags:
- Constructing polynomial interactions from combinatorial rules.
- Learning probabilistic fuzzy thresholds (“Age ≈ 55 ± 3”).
- Injecting domain ontologies directly into prompts.

Furthermore, integrating fairness constraints during weight training could help guard against biases baked into LLM prior knowledge—a direction that could make applied regime trustworthy for sensitive domains.

---

## TL;DR

*Large language models aren’t just text generators—they’re latent knowledge stores.*  
FeatLLM taps into this store by asking an LLM to act as a domain expert: it reasoned about which features matter and then writes crisp decision rules. Those rules are parsed into binary features; a tiny weighted sum reflects how important each rule really is in predicting your target class—trainable with just a handful of labels and no per-sample inference through an LLM! This approach gives you competitive performance in low-shot settings while keeping inference cheap and explanations clear.

Happy modeling!
