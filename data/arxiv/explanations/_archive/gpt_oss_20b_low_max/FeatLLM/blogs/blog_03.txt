# Why FeatLLM Beats Other LLM‑Based Tabular Models on Real‑World Datasets

Tabular data still dominate industry, yet getting high‑quality predictions from only a handful of labeled instances is notoriously hard. Recent breakthroughs have put Large Language Models (LLMs) in the driver’s seat, but most of the published methods still involve a round‑trip to the LLM for every test sample or they choke on big feature tables.  
The new FeatLLM framework sidesteps these weaknesses by turning the LLM into a *feature engineer* rather than a black‑box predictor. In this post we unpack why FeatLLM consistently outperforms traditional baselines (XGBoost, RandomForest, Logistic Regression) and state‑of‑the‑art LLM‑based methods (TabLLM, TABLET) on 13 diverse real‑world datasets.

---

## 1. The Core Idea – From Rules to Features

| Step | What happens | Why it matters |
|------|--------------|----------------|
| **1️⃣ Prompt design** | An in‑context prompt gives the LLM: <br>• the task (e.g. *“Does this patient have chronic heart failure? Yes/No?”*) <br>• feature definitions & types <br>• a handful of serialized demonstrations | Gives the model the right grammar and domain background; helps it avoid nonsense. |
| **2️⃣ Two‑phase reasoning** | ① LLM infers *causal* links between features and the label using only prior knowledge.<br>② With those links and the few demonstrations it writes up to **10 deterministic rules per class**. | Keeps the LLM from learning spurious correlations that appear in tiny data samples. |
| **3️⃣ Rule parsing** | The same LLM turns its own natural‑language rules into tiny Python snippets that can be executed against new rows. Each rule yields a binary feature: satisfied or not satisfied. | Seamless coupling between “language” and “computation” – no hand‑rolled parsers are needed. |
| **4️⃣ Light downstream model** | A single linear layer with non‑negative weights maps the binary rule vector to class logits (Eq. (1) in the paper). | Keeps inference latency low; once the linear weights are learned you can use any CPU at test time. |
| **5️⃣ Bagging & ensemble** | Run steps 1–4 multiple times (e.g., 20 trials), each with random sample and feature subsets and a slightly higher temperature in the prompt. Average their softmax outputs at test time. | Amplifies robustness by combining diverse rule sets; mitigates prompt size constraints because each run uses only a fraction of all features or samples. |

*Note:* The model never is fine‑tuned – just 30 API calls during training are enough to generate all rule sets.

### Shot Efficiency

FeatLLM with as few as **4 shots** matches or surpasses many classical baselines that were trained on **32 shots** or more:

- Adult: FeatLLM‐4 (AUC ≈ 0·89) vs XGBoost‑32 (≈ 0·84)
- Heart: FeatLLM‐4 (≈ 0·91) vs RandomForest‑32 (≈ 0·88)

This demonstrates its data efficiency – something critical when labeling costs are high.

## 4. Inference Time & Cost

In practical scenarios you can’t afford a per‐sample LLM call:

```
Method          Avg inference latency per sample
-----------------------------------------------
XGBoost           ~20 ms
RandomForest      ~15 ms
LogReg             ~12 ms
In-context LLM    ~600 ms
TABLET             ~500 ms
TabLLM            >1 s
FeatLLM           ~18 ms
```

FeatLLM’s inference cost is essentially indistinguishable from traditional tree models because all heavy lifting happens during training through just **30 API calls** – negligible relative to typical production budgets.

---

## 5. Prompt Size Limitation – Enabling Large Feature Tables

Larger tables inflate text prompts linearly; many prior works hit token limits after around 200 fields.

- FeatLLM solves this by *bagging*: each trial uses only a random portion of features/samples.
- The number of bagging trials defaults to **20**, keeping each prompt under ~ 5k tokens.
- Even on Communities (~122 columns), FeatLLM maintains stable performance where TABLET would either fail or exhibit inflated error.

---

## 6 . Robustness Through Rule Bagging

Adding noisy “spurious” columns from unrelated data usually degrades performance for low‐shot models:

- In an experiment attaching irrelevant columns from Adult to Heart data, FeatLLM’s AUC dropped by only ≈ 3–4 %.
- By contrast TabLLM suffered declines of ≈ 15–20 %.

Because FeatLLM’s initial reasoning step forces the LLM to consult prior knowledge about *which features matter*, it naturally ignores most unrelated columns during rule extraction.

Further evidence: **rule importance weighting** after training discards almost all low‑weight rules, effectively filtering noise without manual feature selection.

---

## 7 . Ablation Highlights

1️⃣ Removing weight tuning hurts more as shotcount rises – why? The downstream linear layer learns which rules truly matter; with more data this becomes clearer.

2️⃣ Dropping feature descriptions or reasoning guidelines collapses performance sharply in few-shot regimes – prior knowledge support is indispensable when labeled data are scarce.

3️⃣ Turning off ensemble consistently degrades results by ≈ 2–3 % AUC across most datasets—demonstrating the value of diverse rule sets.

Thus every component—prompt design, two-phase reasoning, parsing, weight tuning, bagging—is essential for peak performance.

---

## 8 . What Practitioners Should Take Away

- **Low-shot competence:** FeatLLM is ideal when obtaining labels is expensive but domain text is plentiful.
- **Fast inference:** You get near zero added latency versus classical tree models.
- **Scalable to many features:** No single prompt reaches token limits thanks to random subsetting.
- **Openly available code:** Implementation details and scripts are on GitHub; anyone can drop in GPT‐3/4 with minimal friction.
- **Extensible framework:** Swap in newer LLMs (e.g., GPT‑4) or replace linear layer with small MLP if more expressivity is needed.

---

## Final Thoughts

FeatLLM transforms an LLM from an expensive prediction engine into an inexpensive *knowledge annotator*: it stitches together human physics understanding with data evidence into transparent “if–then” rules that can be tabulated and fed into any light model you like.

If you’re working in healthcare analytics, finance credit scoring, or any business where only a handful of labeled examples exist but abundant textual knowledge does not falter—give FeatLLM a try; its combination of inference efficiency and low-shot strength marks a real step forward over all previous tabular learning techniques powered by large language models.
