\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Foundations of Tabular Learning  

Understanding how to extract knowledge from tabular data is the first step toward interpreting the new paradigm of using large language models as feature engines.  In this introductory chapter we describe what constitutes a tabular data set, outline the traditional supervised algorithms that have been the de‑facto standard for decades, and discuss why those methods struggle when only a handful of labeled instances are available.  Finally, we review the early attempts to address these challenges by combining small‑sample learning with external signals such as unlabeled data or knowledge transfer.

---

## 1.1 Definition and Structure of Tabular Data  

A *tabular* data set is a collection of records (rows) described by a finite set of attributes (columns).  Each record is typically a point in an \(d\)-dimensional space where \(d\) is the number of columns.  Concretely, if we write \(\mathbf{x} = (x_{1}, x_{2}, \dots , x_{d})\), then \(\mathbf{x}\) is one example and the collection of all such examples forms the data matrix
\[
X \in \mathbb{R}^{N \times d},
\]
where \(N\) denotes the number of rows.

The columns can be heterogeneous in nature:

| **Type**      | **Examples**                                     | **Common Treatments**                            |
|---------------|---------------------------------------------------|---------------------------------------------------|
| Continuous    | age, income, test score                           | Standardization or min‑max scaling               |
| Categorical   | gender, occupation, diagnosis code                | One‑hot encoding or target‑mean encoding         |
| Ordinal       | education level, severity rating                   | Preserve integer ordering or encode as ordinal   |
| Text          | free‐form notes                                   | Bag‑of‑words, TF‑IDF, or pretrained embeddings   |
| Boolean       | smoke?, has‑surgery?                               | Encode as {0,1} or {True,False}                  |

Although many main­line machine learning approaches treat each column as a raw numeric value after basic preprocessing, it is important to recognize that the *meaning* of a column—its name and any accompanying description—can convey rich prior knowledge that plain numeric values cannot capture.  This “semantic” information is precisely what large language models are particularly good at interpreting.

---

## 1.2 Conventional Learning Algorithms  

Over the past decade many learners have successfully addressed tabular classification and regression tasks.  The most common are:

### Logistic Regression (LogReg)  
Logistic regression models class posterior probabilities by applying a logistic function to a linear combination of features:
\[
P(y=1|\mathbf{x}) = \sigma(\mathbf{w}^{\top}\mathbf{x} + b),
\]
where \(\sigma(z)=\frac{1}{1+e^{-z}}\).  
The model learns parameters \(\mathbf{w}\) and \(b\) by minimizing cross‑entropy loss; regularization (ridge or lasso) controls over‑fitting.

### XGBoost  
Extreme Gradient Boosting (XGBoost) is an ensemble method that constructs an additive sequence of regression trees:
\[
F_{m}(\mathbf{x}) = F_{m-1}(\mathbf{x}) + 
    \nu\, f_{m}(\mathbf{x}), \quad f_{m}\in\mathcal{T},
\]
where \(\nu\) is the learning rate and \(\mathcal{T}\) denotes the space of shallow trees.  
XGBoost uses second‑order Taylor expansion on the loss function to obtain high‑quality split decisions while being highly efficient computationally.

### Random Forest  
Random Forest builds many decision trees independently on bootstrap samples and aggregates them via majority vote:
\[
\hat{y} = \operatorname{mode}\bigl( h_{t}(\mathbf{x}) : t = 1,\dots,T\bigr),
\]
where each tree \(h_{t}\) selects random subsets of features at each split.  
This randomness decorrelates trees, reducing variance while retaining high predictive power.

Each algorithm has well–studied theoretical guarantees and empirical success on medium‑to‑large data sets.  However, they all rely on estimating numerous parameters from data—a task that quickly becomes ill posed when only a few labeled points are available.

---

## 1.3 Limitations of Small‑Sample Regimes  

In low-shot or “few-shot” scenarios (typically \(k < 32\), where \(k\) denotes the number of labeled instances available for training), several distinct issues arise:

| Issue                     | Why it Happens                                    | Consequence                                 |
|---------------------------|---------------------------------------------------|---------------------------------------------|
| **High variance**        | Parameter estimates depend heavily on disproportionate influence from noise in limited points | Overfitting; poor generalization              |
| **Curse of dimensionality** | With \(d \gg k\), many feature combinations appear sparse but may still be chosen by greedy algorithms               | Spurious correlation learning                |
| **Model capacity**       | Complex models (e.g., deep ensembles) have too many degrees of freedom relative to data                   | Overparameterization; unreliable results     |
| **Noisy labels**         | Each wrong label has larger impact on loss function                                                | Class imbalance becomes destructive         |

Because any learner’s ability to discern true signal from noise scales roughly linearly with sample size in practice, when \(k\) drops below a few dozen rows even simple linear models may begin to misbehave: their coefficients can flip sign arbitrarily or be driven by irrelevant columns.

Moreover standard pre‑processing techniques—such as imputation or scaling—can greatly distort small data sets if performed naively.  For instance, computing per-feature mean and variance on just five points yields highly unstable estimates.

In short, while conventional algorithms deliver impressive performance on sizable tabular collections, they lack mechanisms to incorporate *prior* knowledge that can compensate for missing observations in few-shot contexts.

---

## 1.4 Early Few‑Shot Techniques  

To mitigate these limitations before deep learning entered tabular research, researchers developed several heuristic remedies that adjacent knowledge sources could help:

### Bootstrapping and Resampling  
Bootstrap aggregating (bagging) creates multiple pseudo–datasets by sampling with replacement from the original training set. Even with few points, each bootstrap sample may highlight different feature interactions; an ensemble over such samples can reduce variance at moderate computational cost.

### Semi‑Supervised Learning  
When a large pool of unlabeled examples is available (\(N_{\text{unlab}} \gg k_{\text{lab}}\)), semi-supervised methods propagate information from labeled to unlabeled items. Classic algorithms include Self‑Training: iteratively assign pseudo-labels to most confident unlabeled examples and retrain; Graph CNNs that fuse label propagation with neural embeddings; Transductive SVMs such as TSVM which hyper‑plane optimization considers both labeled losses and unlabeled margins.

Semi-supervised schemes augment effective sample size without needing new annotations but rely heavily on assumptions about manifold smoothness or cluster structure—assumptions often violated in high-dimensional tabular spaces.

### Transfer Learning from Related Tasks  
Transfer methods aim to reuse knowledge learned from other prediction problems. Two main flavors exist:

1. **Multi-task Pretraining**: A neural network first trains across dozens or hundreds of benchmark tabular datasets (sometimes generating synthetic samples). The learned weights serve as initialization for new tasks; this reduces optimization difficulty in low-shot regimes. An example is TabPFN which creates synthetic "train/test" pairs by mixing pretemporal statistical distributions before training a Bayesian neural network.

2. **Feature Schema Alignment**: Some approaches synchronize feature names across datasets so that attributes with identical semantics inherit shared representations; however this demands extensive schema harmonization which rarely holds in real logistics pipelines.

These early techniques are valuable because they explicitly address sample scarcity—but they either require additional data sources unavailable in many industries (unlabeled samples), rely on complex training pipelines, or bring logistical overheads (data alignment).

---

### Closing Remarks  

Classical tabular learners excel when plenty of annotated examples exist but falter in the exciting yet restrictive world where only a handful remain. Experienced practitioners already turned teacher signals from vitamins such as semi-supervision and transfer learning into valuable allies—in short to "borrow" knowledge where possible.

The rest of this textbook will explore how recent progress in natural language processing—particularly massive pre-trained language models—provides a new source of prior knowledge: vast amounts of structured human knowledge encoded implicitly during web-scale training. When harnessed correctly—as feature generators rather than end-to-end predictors—these LLMs can dramatically elevate performance for tiny labeled corpora while keeping inference light enough for production pipelines. The forthcoming chapters dive into those methods systematically.</details>

# 2. Large Language Models: Beyond Natural Language  

Large language models (LLMs) have transformed the landscape of artificial intelligence in recent years, moving far beyond the narrow confines of natural‑language understanding and generation. They bring to bear a deep repository of knowledge — acquired through training on massive corpora of text — that can be harnessed for a variety of downstream tasks, including those that involve structured, tabular data. This chapter surveys the historical evolution of LLMs, explains how their internal representations encode useful information, reviews early attempts to apply them to structured data, and clarifies the practical obstacles that remain when leveraging commercial LLMs through an API interface.

---

## 2.1 From RNNs to Transformers and GPT‑style Models  

The precursor of modern LLMs was the family of recurrent neural networks (RNNs). Classic RNNs suffered from vanishing gradients and struggled with long‑range dependencies, which limited their capacity to capture higher‑level semantics in language. The introduction of gated architectures — such as Long Short‑Term Memory (LSTM) units and Gated Recurrent Units (GRU) — alleviated some of these challenges but did not fully solve the problem.

The true breakthrough arrived in 2017 with the Transformer architecture introduced in “Attention Is All You Need.” Transformers dispensed with recurrence entirely, relying instead on self‑attention mechanisms that provided each token with a direct connection to every other token in a sequence. This allowed models to learn contextual relationships efficiently and with remarkable parallelizability on GPUs or TPUs.

Building on Transformers, researchers proposed GPT (Generative Pre‑trained Transformer) families that emphasized “causal” attention, ensuring that each token could only attend to earlier positions. The objective was plain language modeling: given a prefix \(x_{\leq t}\), predict the next token \(x_{t+1}\). This simple unsupervised objective yields rich internal representations because the model must learn syntax, semantics, facts, and even procedural knowledge from millions of sentences.

Subsequent iterations—GPT‑2, GPT‑3, GPT‑4—scaled the architecture dramatically while keeping the same core principle: large transformers trained on big datasets with a massive number of parameters. Their successes proved that sufficient capacity combined with “few‑shot” prompting could render powerful generalization without any architectural redesign or supervision for specific tasks.

---

## 2.2 Knowledge Representation in LLMs  

Given a prompt \(\mathbf{p}\), an LLM computes a distribution over possible next tokens through:
\[
P(x_{t+1} \mid x_{\leq t}) \propto \exp\bigl(\mathbf{h}_{t}\mathbf{W}\bigr),
\]
where \(\mathbf{h}_{t}\) is the hidden state at step \(t\). Though we observe only the final output probabilities or selected continuations, many internal properties can be inferred from model weights and activations:

| Property | Origin | Manifestation |
|----------|--------|---------------|
| **Semantic similarity** | Embedding learning | Tokens that are similar occupy proximate regions in vector space |
| **Association rules** | Co‑occurrence statistics | Certain phrases or facts are strongly correlated |
| **Common sense reasoning** | Pre‑training on encyclopedic text | Ability to complete causal chains (“If X then Y”) |
| **Domain knowledge** | Presence of specialized literature | Recognizes medical terminology or financial jargon |

These capabilities have been demonstrated empirically: prompting GPT‑3 for math problems reveals latent procedural knowledge; prompting GPT‑4 for medical case classification leverages its exposure to clinical narratives. Crucially, such knowledge can be extracted *without* fine‑tuning by feeding carefully engineered prompts—a technique known as *in‑context learning*.

---

## 2.3 Prior Works on LLMs for Structured Data  

While LLMs were conceived for sequential text data, researchers soon realized they could be repurposed for tabular data by serializing rows into text streams. Three notable early approaches illustrate this idea:

### 2.3.1 Lift  
Lift proposes encoding a row as a string that lists each column name followed by its value (“age is 42; income is $50K; smoker is Yes”), together with task instructions (“Predict whether individual will buy product”). The model then reads this formatted prompt and outputs a probability for each class—essentially performing inference directly within the LLM.

### 2.3.2 AnyPredict  
AnyPredict extends Lift by allowing any type of feature description (continuous, categorical). It supplies feature definitions explicitly (“age: integer; income: nominal”) so that the LLM can interpret operators correctly (e.g., “>” versus “equals”). AnyPredict also adopts *parameter‑efficient tuning* (LoRA), modifying only a small set of adapter weights rather than fine-tuning the entire transformer.

### 2.3.3 TabLLM  
TabLLM focuses on *prompt engineering*: it provides richer context by appending an external classifier’s prototypes or rule-based hints into the prompt ("Examples where people purchased/not purchased"). TabLLM utilizes *inference-time* chain-of-thought prompting and optionally IA3 fine-tuning to adapt to specific tabular datasets while preserving most of the base model’s parameters.

All three methods share one crucial limitation: during prediction they require sending every sample (or at least a serialized version thereof) to an LLM engine via an API call—often at $0$ compute cost but still incurring significant latency and monetary expense when scaled.

---

## 2.4 Practical Constraints: API access, prompt limits, computational cost  

Deploying LLMs at scale exposes several practical bottlenecks:

1. **API Latency**  
   Commercial APIs such as OpenAI’s bear an inherent round-trip latency of tens or hundreds of milliseconds per request due to network round-trips and server queuing. In low-latency settings—e.g., real-time medical triage—this adds untenable delays when every sample must be sent through an API call.

2. **Rubric-Based Quotas**  
   Providers build usage quotas around token counts rather than number of requests. A long prompt inflates cost since tokens are charged at a per-unit rate (e.g., $0\!/\!k$.00 per thousand tokens in GPT-4). A typical tabular prompt serializing hundreds of columns can easily exceed several thousand tokens.

3. **Prompt Length Limits**  
   Most models cap input tokens: GPT-3's context window is 4 k tokens while GPT-4 can handle up to 32 k tokens under certain subscription tiers. When features proliferate – e.g., high-dimensional biomedical datasets – serializing every column outstrips these limits unless one either truncates features aggressively or divides data across multiple calls.

4. **CPU/GPU Bottlenecks**  
   When local inference is required (some regulations forbid cloud-based inference), running a large transformer demands powerful GPUs or TPUs or extensive distributed inference frameworks – often inaccessible for small research labs or edge deployments.

5. **Model Update Constraints**  
   Some providers release `cutoff dates` after which newer training data are not incorporated automatically; also vendor APIs often do not expose model checkpoints for local fine-tuning or adaptation – hindering experiment reproduction or custom adjustments.

In summary, although LLMs carry rich prior knowledge useful for tabular learning, these pragmatic constraints motivate architectural strategies that decouple prediction from live model calls—such as using the LLM only during a feature-engineering phase and thereafter leveraging inexpensive downstream classifiers.

--- 

By understanding how transformers came into being and what inexpensive prompts can elicit from them, we are ready to explore how we can convert their latent knowledge into *actionable features* for structured data scenarios—a strategy highlighted further in Chapter 3 where we introduce FeatLLM’s feature-engineering pipeline.

# 3. The Idea of Feature Engineering with LLMs

In most contemporary tabular‑learning pipelines, the cardinal task of transforming raw features into something a predictor can consume is relegated to a human expert. The expert evaluates the dataset, draws on domain knowledge, and manually engineers variables—splitting, binning, discovering interactions—that will enable the downstream model to learn useful patterns. This hands‑on method is powerful but limited by the time and knowledge that a practitioner can devote to a particular problem.  

Large Language Models (LLMs) have radically changed what machines can learn without any task‑specific training data. Their pre‑training on vast natural‑language corpora equips them with rich background knowledge and a capacity for multi‑step reasoning in a single forward pass. Because of this, it becomes natural to ask whether an LLM could be used not just for end‑to‑end prediction but as an *expert feature engineer*. In this section we explore this idea in depth: we discuss how feature engineering traditionally works, why encoders based on rules present attractive advantages, and how prior knowledge encoded in LLMs can be harnessed to recover causal relationships from limited data. Finally, we consider the operational benefits—including reduced inference latency and the elimination of per‑sample queries—that arise when feature generation is decoupled from prediction.



---

## 3.1 Human Feature Engineering vs Algorithmic Feature Engineering

Historically, building a predictive model on tabular data involved a two‑stage process:

1. **Feature Extraction and Transformation** – A data scientist defines new variables that capture domain‐specific relationships (e.g., age buckets, interactions between `sex` and `smoker`, or log transforms on skewed numeric columns).  
2. **Model Training** – A statistical or machine learning algorithm learns to map the engineered features onto target labels.

Human feature engineering relies heavily on intuition and trial‑and‑error. Domain expertise guides decisions such as “consider whether high blood pressure combined with high cholesterol increases myocardial infarction risk.” The process is iterative: after training a model one often revisits the feature set, adds or removes variables based on performance metrics or interpretability needs.

In contrast, **algorithmic feature engineering** places the burden of discovering useful representations on an algorithm rather than a person. Approaches such as decision trees or neural networks perform implicit feature construction by composing low-level attributes through layers or splits. Tree‐based ensembles implicitly discover interactions and non‑linearities but often lack interpretability; dense neural nets learn internal representations that are not readily human‐readable.

The fundamental gap lies in *interpretability* versus *automation*. The methods above automate learning from data alone but require substantial labeled information to avoid overfitting—especially problematic in low‑shot settings where only a handful of examples are available. In this scenario, standard algorithms may latch onto spurious correlations unless they are explicitly guided by external knowledge.

Enter LLMs: large language models come equipped with two assets that make them promising candidates for automating feature engineering:

| Asset | How it Helps Feature Engineering |
|-------|---------------------------------|
| **Wide background knowledge** | An LLM has seen thousands of articles about medical risk factors, economic indicators, or engineering principles during pre‑training; it can recall relationships that are not obvious from small datasets. |
| **Few‑shot reasoning capability** | Given a few exemplars and a carefully crafted prompt, the model can simulate how an expert would think through examples and generate *rules* that capture underlying logic. |

Thus the concept of using an LLM as a *feature engineer* is natural: we reduce the human effort needed for handcrafting features while still preserving interpretability through rule extraction.



---

## 3.2 Rules as Binary Features: Motivation and Benefits

A rule in tabular learning is an explicit logical predicate over one or more input columns—e.g., “`age > 60` AND `history_of_smoking = Yes`.” From any dataset instance \(\mathbf{x} \in \mathbb{R}^{d}\), one can evaluate the rule to obtain a binary value (either `0` if it is not satisfied or `1` if it is). When we consider many such rules \( \{r_{k}\}_{k=1}^{R} \), we obtain a *rule matrix* \(\mathbf{Z} \in \{0,1\}^{N\times R}\) where each column corresponds to one binary feature derived from a rule.

There are several compelling motivations for representing rules as binary features:

1. **Simplicity of Downstream Models** – With only \(0/1\) entries, logistic regression (or other linear models) becomes particularly effective because each rule has an interpretable weight that signals its importance.

2. **Interpretability & Transparency** – Because each rule is expressed in natural language (or code), practitioners can readily comprehend what drives predictions: “patients whose 'cholesterol > 240' score +2 for condition X.” This level of transparency is valuable in regulated domains such as healthcare and finance.

3. **Reduced Dimensionality Bias** – Binary features mitigate variance inflation caused by continuous variables with many distinct values; they project complex spaces into simple yes/no cues which are less prone to overfitting when data are scarce.

4. **Facilitated Ensemble Workflows** – Rules extracted under different random seeds or demonstration orders naturally differ; bagging these weak learners produces robust aggregated predictions without re‑accessing the LLM during inference.

5. **Zero Overhead at Inference** – Once rules have been determined offline (generating binary features involves only local threshold checks), there is no call back to the expensive language model at prediction time—dramatically lowering latency and cost.

By framing feature construction as rule extraction followed by binarization, we combine human ish reasoning with machine scalability.



---

## 3.3 Leveraging Prior Knowledge for Causal Inference in Tables

The key innovation in using LLMs for rule generation lies in recognizing that these models contain nontrivial *world knowledge*. For tabular predictive tasks—e.g., predicting chronic heart failure—the naive approach would be to let the model simply learn linear combinations from \(k\) training samples (\(k\) << dataset size). Instead we exploit two complementary sources:

### 3.3.1 Prior Knowledge Encoded During Pre–Training

LLMs were trained on massive text corpora consisting of encyclopedic entries, clinical notes, financial reports, recipes—the list goes on. Consequently, the embeddings internal to such models encode associations such as “older patients have higher risk of heart disease” or “high sodium intake raises blood pressure.” In practice:

- When prompted with *task descriptions* (“Is this patient at risk for condition X?”) and *feature specifications* (“`age` denotes patient age”; "`sodium_intake` denotes daily sodium intake"), the LLM interprets these terms based on its learned semantics.
- Even when no supervision data are provided for a particular dataset split (few-shot regime), these events surface because they appear repeatedly across its pretraining corpus.

### 3.3.2 Data–Driven Refinement via Demonstrations

The second engine comes from few-shot exemplars inserted into the prompt: small tables where each row lists values of features followed by ground truth labels (“Yes” or “No”). These exemplars provide concrete evidence that:
- A certain combination (e.g., “age > 60” AND “high cholesterol”) actually classifies positively,
- While another combination might be negative.

Given these snippets together with its prior knowledge base, an LLM performs *reasoned inference*: it first hypothesizes relationships (Step 1 reasoning instruction), then tests them against examples (Step 2). This reflects how humans learn: first forming hypotheses from theory then corroborating via evidence.

Formally:

1️⃣ **Causal hypothesis generation:**  
   The model outputs propositions \( r_{k} = f(\text{features}) \wedge (\text{relation}) \) based on textual semantics.

2️⃣ **Empirical validation:**  
   It evaluates \( r_{k} \) against demonstration rows; if consistent across many examples it gains confidence.

This hybrid prior + empirical approach results in robust rules even when training data are scarce.



---

## 3.4 Advantages: Reduced Latency, No Per–Sample Inference

Traditionally many LLM–based tabular pipelines operate end‑to‑end: every test sample is streamed through the language model together with serialized features to obtain predictions directly from the LLM’s language head (often approached via chain-of-thought prompting). While powerful, this architecture incurs severe drawbacks:

| Issue | Typical Impact |
|-------|----------------|
| **Inference cost** | Every example triggers an API call; latency multiplies linearly with test set size; bills skyrockets for large deployments |
| **Scalability constraints** | Current APIs limit context window size; as tables grow more columns this becomes infeasible |
| **Non-reproducibility** | Different sampling orders result in different probabilistic outputs; hard to version control predictions |

By contrast, using an LLM purely for feature engineering decouples inference cost from sample size because:

1️⃣ **One-time extraction:**  
   Rules are inferred once per training fold and stored as static functions (`if-else` predicates). Afterward all samples merely need to evaluate those predicates locally.

2️⃣ **Parallelizable processing:**  
   Rule evaluation scales trivially across CPUs/GPUs; no synchronization overhead associated with API calls.

3️⃣ **Consistent deployment:**  
   Generated rules can be saved within downstream software stacks as deterministic code modules (Python functions or SQL views), making versioning straightforward.

4️⃣ **Reduced memory footprint:**  
   Binary matrices replace dense input tables during downstream learning/decoding; storage becomes inexpensive even for large datasets.

Empirically these benefits translate into performance gains beyond baseline numbers: fewer causes of degraded accuracy due to prompt truncation and fewer artefacts introduced by tokenization errors.


--- 

In summary, swapping out manual feature crafting for systemised rule extraction performed by an LLM yields multiple intertwined advantages: it leverages both structured background knowledge and dense evidence from tiny samples while keeping downstream modeling simple and fast—precisely what practitioners need when label budgets are tight but decisions must be transparent and rapid security-compliant transformations remain untouched by costly calls to massive server engines.



---

# 4. FeatLLM: Framework Overview  

## 4.1 Problem Formalization  
In a classical supervised tabular learning problem we are given a set of \(N\) examples encoded as a collection of feature vectors \(\mathbf{x}^{i}\in\mathbb{R}^{d}\) and their corresponding class labels \(\mathbf{y}^{i}\).  In the notation used throughout the paper, a single labeled instance is written as \((\mathbf{x}^{i},\mathbf{y}^{i})\) where \(i=1,\dots,N\).  The labels are categorical, i.e., \(\mathbf{y}^{i}\in \{1,\dots,c\}\) for a \(c\)-class classification task.  

FeatLLM is specifically designed for the *few‑shot* regime.  An external “shot budget’’ \(k<N\) is chosen; only \(k\) randomly selected labeled examples are available for any downstream learning.  The model must therefore extract as much signal from every bit of these few labeled instances as possible while leveraging knowledge supplied implicitly in an LLM.  

The key objects used by FeatLLM are:  
* **Feature set**: Each column (feature) in the table has a natural‑language name, e.g., `age`, `marital_status`, and may also come with an explanatory definition or list of categorical values.  This side information \(F=\{f_j\}_{j=1}^{d}\) is supplied to the LLM so that it can reason about type, magnitude, and semantics.  
* **Rule set**: For each class \(k\in\{1,\dots,c\}\), the LLM will produce a small collection of Boolean rules \(\{r_{k,1}, r_{k,2},\dots,r_{k,R_k}\}\).  In the experiment all datasets use a fixed number of rules per class (10), so we simply denote \(R_k=R=10\).  
* **Binary feature vector**: The set of all rules applied to an unseen sample yields a concatenated binary vector 
  \[
    \mathbf{z}^i = 
      \bigl[\, z^i_{1,1},\, z^i_{1,2},\,\dots,z^i_{1,R},\, z^i_{2,1},\,\dots,z^i_{c,R}\,\bigr]
    \in \{0,1\}^{cR}
  \]
  where each entry \(z^i_{k,r}=1\) if instance \(i\) satisfies rule \(r\) for class \(k\).  If a rule does not apply (e.g., because it references an obsolete feature or contains an ambiguous condition), the entry defaults to zero.  

Given these definitions we can formally state FeatLLM’s learning objective: learn a mapping
\(f:\mathbf{x}\mapsto \mathbf{p}\)
where \(\mathbf{p}=(p_1,\dots,p_c)\in[0,1]^c\), \(\sum_{k}p_k=1\), and
for each class
\(p_k=\frac{\exp(\boldsymbol{\omega}_k^\top \mathbf{z}_k)}{\sum_{\ell}\exp(\boldsymbol{\omega}_\ell^\top \mathbf{z}_\ell)}.\)
Here \(\boldsymbol{\omega}_k`∈ℝ^R` is a *weight vector* that indicates how much each rule matters for predicting class \(k.\)

Only the weight vectors are trained; all other transformations (rule extraction and binary encoding) are performed by the LLM and remain fixed once generated.

---

## 4.2 End‑to‑End Pipeline Diagram  

```
┌─────────────────────────────────────┐          
│   ✨ FeatLLM Pipeline (Few‑Shot)     │          
├─────────────────────────────────────┤          
│   • Input: k labeled examples      │
│     + natural‑language feature     │
│       names & definitions          │
│   • Step 0: Prepare prompt          │
├─────────────────────────────────────┤
│   • Step 1: Rule Extraction        │
│     → GPT‑3.5 ← LLM ini‑context ⇅ │
├─────────────────────────────────────┤
│   • Step 2: Parse Rules → Python   │
│     Code ← LLM three‑stage prompt   │
├─────────────────────────────────────┤
│   • Step 3: Generate Binary        │
│     Features z^i                   │
├─────────────────────────────────────┤
│   • Step 4: Train Linear Model     │
│     Weights ω_k over k classes     │
├─────────────────────────────────────┤
│   • Step 5 (Optional): Repeat T    │
│     times with bagging & random    │
│     seeds → several w[t]           │
├─────────────────────────────────────┤
│   • Prediction on new data:        │
│         * Compute z^i              │
│         * For each t compute p_t^i │
│         * Average p_t^i over t      │                                
└─────────────────────────────────────┘          
```

In practice the pipeline accepts two kinds of input data:

| Component | Content | Purpose |
|-----------|---------|---------|
| **Feature description** | For every column – name, type, allowed categories (if categorical), and optional definition | Enables LLM to understand semantics and avoid type mismatches when writing rules |
| **Demonstration samples** | Serialized text version of few-shot entries and their true labels | Provides statistical cues that help refine rules from generic knowledge about the task |
| **Task question** | Natural language describing what needs to be predicted (e.g., “Does this patient have chronic heart failure? Yes or no?”) | Frames the prediction setting for both reality‑checking and prompting retrieval mechanisms |

Feeding these carefully constructed prompts into GPT‑3.5 marks the beginning of *rule extraction*. The model receives its instruction in three layers: basic information description, reasoning instruction split into two steps (“infer relation” then “derive decisive rules”), and response instruction (syntactic formatting). This structured instruction nudges GPT‑3.5 into producing a readable set of Boolean conditions written in natural language but with tight syntactical conventions so that later automated parsing succeeds.

After receiving textual rules, FeatLLM defines a parsing prompt that asks GPT‑3.5 to transform these conditions into executable Python code snippets. It supplies function signatures on input features, expected output types, and an example transformation pair. The returned code defines functions such as `apply_rule_5_age_gt_50(x)` that evaluate the rule on any arbitrary row `x`. The Python code blocks are executed using `exec()`; having captured them neatly lets FeatLLM evaluate each row efficiently online without repeated LLM calls.

The generated binary flag matrix `Z` becomes handshook into a **parameterized linear classifier**:
\[ p_k = \sigma \left( \max(\boldsymbol{\omega}_k ,0 )^\top z_k^i \right),   \quad 
\sigma(a)=e^{a}/(e^{a}+\ldots ) .\]
Here we apply ReLU to weights to enforce nonnegative contribution because any negative weight would mean “suppressing” possession of a rule – but since ruling out something on its own is rarely beneficial without other evidence, nonnegativity keeps each rule's effect monotonic.

Training only these weight vectors (via cross‑entropy loss) is extremely lightweight; we use Adam with learning rate \(0.01\) over at most \(200\) epochs – well within reach when only tens of examples are available.

Finally, to combat variance stemming from limited shots and stochasticity in rule generation, FeatLLM repeats the entire pipeline several times (`T` ensembles). Each repetition samples anew from the training subset (bagging over data or features), reinitializes temperature in GPT calls for high-entropy generation (`temp=0.8` instead of deterministic `0.5`), and shuffles demonstration order—since language models can be highly sensitive to context ordering—so that each trial produces subtly different rule sets. During inference we compute probabilities across all ensembles and average them:
\[ p_{\text{final}}(x)= \frac{1}{T} \sum_{t=1}^{T} p^{(t)}(x).\]

---

## 4.3 Key Design Choices  

### Fixed Number of Rules Per Class  
In principle the model could generate any number of conditions depending on complexity or evidence from data. However, we deliberately cap each animal at ten rules per class (\(R=10)\). Three motivations lie behind this heuristic:

1. **Prompt length control** – Each rule contributes around thirty tokens; ten per class yields roughly \(c\times30\times10 =300c\) tokens—well below typical context windows for GPT‑3.5 while still giving enough expressive power.
2. **Simulated interpretability** – Human experts often prefer concise decision tables; limiting to ten clauses ensures each eventual prediction can be traced back to under ten interpretable conditions.
3. **Computational stability** – Too many binary features inflate training dimensionality for very low‐shot data, which may lead to overfitting or unstable cross entropy gradients.

Empirically we find ≥10 clauses yield diminishing returns while increasing average number reduces accuracy in cross–dataset experiments.

### Bagging Over Features & Instances  
To curtail prompt size further—and diversify extracted knowledge—the base pipeline behaves differently depending on dataset cardinality:

- When features exceed *recall* (~2048 tokens), FeatLLM either samples a subset of columns or applies *feature‐bagging*: it randomly selects \(b_f < d\) columns to include in any given prompt run.
- Likewise it can cull training instances via *sample-bagging*, selecting random subsets of cheap examples.

Bagging introduces variety across ensemble members without overly increasing computational load; each member’s binary encoding reflects only the contained feature subset but all instances are still represented across trials via repeated sampling.

Because bagging shrinks individual prompts but preserves overall dataset breadth across ensemble members, we empirically observe robust performance even on highly dimensional tabular collections (`Communities`, `Myocardial`). A theoretical justification follows from McCarthy’s law for combinatorial generalization: given enough diverse weak learners—each built on different subspace slices—an ensemble can reconstruct arbitrarily intricate decision surfaces.

### Nonnegative Weight Projection  
Weight vectors `'w_k'` appear after training simply as linear coefficients turned hepophlogally enbiotic by forcing them onto nonnegative domain via ReLU(`w`). Two practical advantages:

* **Avoiding contradictions** – A rule satisfied by many positive examples should not ever reduce probability—ReLU guarantees this monotonic relationship.
* **Stable convex hypothesis space** – With all input features being zero/one indicators this restriction turns learning into fitting attainable multiplicative scores akin to rough sets or additive Bayesian networks.

# Conclusion

Section 4 has unpacked how FeatLLM navigates communication between raw few-shot tabular data and powerful pre-trained language models by weaving together carefully crafted prompts with automatic code generation and lightweight linear inference. Timing constraints imposed by limited shots do not thwart plausible performance: by extracting domain sprint‑style conditions from LLM salient priors—and letting those conditions drive subsequent probabilistic inference—FeatLLM reframes tabular few-shot classification as *feature engineering through reasoning*. Subsequent chapters elaborate how this perspective allows FeatLLM to outperform competing few-shot baselines while keeping inference latency minimal and compatibility with API-only access to modern large language models across domains such as finance and healthcare.</blockquote>

# 5. Prompt Engineering for Rule Extraction  

In \textsf{FeatLLM} the core of the method is the prompt that is fed to the Large Language Model (LLM) during rule extraction.  The prompt must accomplish two seemingly contradictory goals:  
1) it must be expressive enough to allow the LLM to reason deeply about the relationship between columns and the prediction task, and  
2) it must be concise and deterministic enough that the output can be parsed automatically into syntactic code that turns the rules into binary features.  

To meet these requirements we decompose a prompt into a hierarchy of three sub‑components: **Basic Information Description**, **Reasoning Instruction**, and **Response Instruction**.  Each of these sub‑components addresses a specific stage in an expert human’s workflow when engaging with a tabular data set, and each is carefully engineered so that the LLM’s internal chain‑of‑thought relies only on natural language descriptors.  The sections below unpack these components in detail, illustrate their construction, and provide practical guidance for their deployment in a real implementation.

## 5.1 Basic Information Description – Task Framing and Feature Metadata  

The first sub‑prompt collates all static knowledge that will be useful every time the LLM is queried.  By presenting this information up front, we reduce reliance on hallucination or inference from context alone; instead we hand–off clear definitions that define both *what* is being asked and *what* variables are available.

### Task framing  
The task description must be posed as an explicit question whose answer options correspond exactly to the label set \(\mathcal{Y}\).  For binary classification we usually use “Yes / No” or “True / False”, whereas for multi‑class problems we enumerate every label separated by commas or line breaks:

```
Does this patient have chronic heart failure? Yes or No.
```

For reasons of reproducibility, we repeat this sentence verbatim for all calls so that temperature or random seeds cannot alter question phrasing.

### Feature descriptors  
Every feature that may possibly contribute to a rule is listed along with its data type (continuous, categorical, ordinal, boolean etc.).  Two variants are common:

| Feature | Type | Definition (optional) |
|---------|------|------------------------|
| `age`   | continuous | Age in years |
| `sex`   | categorical | Male / Female |
| `blood_pressure` | continuous | systolic BP in mmHg |

We are careful to remain faithful to the original column names because exact string matching will later simplify parsing (see Section 5.4).  If the dataset contains an embedding‐like column (`e5_score`, `token_count`) we treat it as continuous unless domain knowledge says otherwise.

### Serialized examples  
The third part of Basic Information Description is a set of *few‑shot examples*.   Each example consists of a fully serialized row:  

\[
\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i,F)=
``\ f_1\ \text{is}\ \mathbf{x}^i_1.\dots f_d\ \text{is}\ \mathbf{x}^i_d.\ \text{Answer:}\ \mathbf{y}^i''
\]

The serialization follows exactly what was used by earlier work on tabular–to–text prompting e.g., \cite{dinh2022lift}.  It begins each feature listing with its name (`f_j`) followed by “is” and then its value (quoted if textual).  This strict syntax serves two purposes:

1. **Clarity** – The model can simply look up each “f_j is x” pair rather than parsing free text.
2. **Determinism** – When atoms are later examined by string‑matching parsers, no accidental whitespace or punctuation anomalies will undermine extraction.

For each dataset we keep \(k\) such entries (the same \(k\) used in training), randomly sampling them once per trial to preserve bagging randomness.

In short, after presenting task framing, feature list, and serialized examples the LLM has enough context to begin reasoning about how features might influence labels.

## 5.2 Reasoning Instruction – Two‑Stage Reasoning Protocol  

In contrast to most prompts that simply ask for predictions (“What is the answer?”), our prompt explicitly instructs a *reasoning process*. In particular we separate reasoning into two controlled stages:

1. **Prior Knowledge Inference** – Observe how each feature might *generally* influence the task without looking at data examples.
2. **Data‑Driven Rule Extraction** – Use the few training examples together with any causal insights gathered in Stage 1 to pin down concrete thresholds, inequalities or category combinations that distinguish one class from another.

### Stage 1: Prior Knowledge Inference  

The instruction starts with an opening sentence resembling Chain‑of‑Thought (CoT) but designed for understanding causal relations:

```
First, think about how each feature might influence chronic heart failure generally.
Do not look at any data examples yet.
State your intuition on every variable’s effect (+/- or neutral).
```

This directs the model to generate a list like:
```
- age tends to increase risk
- blood_pressure tends to increase risk
- sex: male tends slightly increased risk
- cholesterol level positive trend with risk
- smoking status' presence lowers risk
```

By forcing this reflection before seeing data we ensure that domain priors such as medical knowledge (“older age leads to higher chance of heart failure”) are baked into later rules—critical for datasets where few shots would otherwise yield spurious associations.

### Stage 2: Data‑Driven Rule Extraction  

After Stage 1 completes, instruction explicitly states:

```
Now consider each example below.
Using what you learned about causal direction,
generate exactly ten distinct rules per class.
Rules should be inequalities or membership tests,
e.g., "age > 65" or "blood_pressure < 120".
Apply only numeric thresholds or category lists.
Do not combine rules using AND/OR – keep them separate.
If you cannot formulate ten rules accurately for a class,
omit weaker ones but ensure at least six valid rules remain.
Separate rules for each class by two line breaks.
```

Key design choices here:

- *Fixed number of rules* ensures manageable prompt length while preventing under/overfitting.
- *Separation of classes* guarantees isolation of logic relevant only to each label; this also eases downstream parsing because rule blocks are well delimited.
- *Restrictions on logical operators* prevent nested clauses that would be hard for automated parsing; if complex conditions are necessary they are broken into multiple single rules.

Through this two-stage protocol we help steer the LLM away from arbitrary correlations found in few shot data because it first consults its internal knowledge base before looking at small samples.

## 5.3 Response Instruction – Standardized Output Formatting  

Even with careful reasoning instructions’, an unstructured answer still poses difficulty for downstream code generation. We therefore prescribe an output skeleton. The response template is fairly lean:

```
Class: <label>
Rule [1]: <Rule-String>
Rule [2]: <Rule-String>
...
Rule [R]: <Rule-String>

Class: <label>
...
```

A concrete example (for a binary case):

```
Class: Yes
Rule [1]: age > 60
Rule [2]: blood_pressure >= 140
Rule [3]: cholesterol <= 200

Class: No
Rule [1]: age <= 60
Rule [2]: blood_pressure < 140
Rule [3]: cholesterol > 200
```

Important formalities:

- The phrase *“Class:”* precedes each block exactly once; no extra spaces before/after capital letters.
- Each rule begins with *“Rule”*, followed by bracketed index `[n]`, colon `:` then one space and never terminates with trailing punctuation except newline.
- Rules themselves use standard comparison tokens (`>`, `<`, `>=`, `<=`, `=`) or equality lists enclosed in brackets `[A,B]` or exact strings without quotes unless they contain spaces.
- When categorical features appear they use their literal values as provided in feature definitions (“male”, “female”, “yes”, “no”).

This rigid cleanliness allows us to implement deterministic parsers: regular expressions that locate indexes directly create dictionaries mapping class→list(rules), thus ensuring zero ambiguity due to punctuation variance.

## 5.4 Practical Tips: Managing Token Limits and Temperature Tuning  

### Token limits

Large tabular data sets often cause prompt size overflow because serialized rows grow linearly with number of columns \(d\). We mitigate this via:

| Technique | Rationale | Implementation |
|-----------|-----------|----------------|
| **Feature bagging** | Reduce visible features per call ∴ fewer tokens per example. | Randomly select a subset \(S\subseteq F\) of fixed size (e.g., \(10\%\) of \(d\)) when constructing payloads. Repeat across trials so full coverage emerges through ensemble averaging. |
| **Instance bagging** | Smaller training subset reduces example length, though each still lists all selected features. | For each trial pick \(k_n<k\) labeled instances; choose training subset randomly but guarantee representation across classes. |
| **Prompt slimming** | Remove nonessential text such as elaborate introductions or repeated feature definitions on overlaps between blocks? | Keep only minimal template words; avoid hyphens…and rely more on mechanical repetition via regex placeholders rather than manual description.|

When applying bagging, keep track of which bagged subsets were chosen because later during ensemble assembly we need coherent mapping between rule indices across bags—each bag must employ the same ordering scheme (e.g., alphabetical order by feature name).

### Temperature tuning

Temperature controls randomness in generated text; setting it too low forces deterministic outputs but risks missing diverse plausible rules; setting it too high yields varied but possibly noisy outputs which may contain syntax errors difficult for parsing.

Empirically we observe:
- Temperature around **0.3–0.5** yields stable correct comparison operators while still allowing nontrivial rule values.
- Very low temperatures (<0.2) tend toward repeating identical generic rules across many classes (e.g., “age > 0”), which provide little information when tuned via weight learning.
- Introducing a small temperature offset across ensemble trials encourages rule diversity; set temperature per trial using a random uniform spread \(U(0.35,0.55)\).

Because our framework relies on learned linear weights over binary features, it can correct minor deviations in any single rule as long as other trials supply its counterpart; hence some noise tolerance is built-in.

---

In conclusion, this structured prompt engineering pipeline transforms raw tabular metadata into disciplined reasoning steps producing parseable rule tables ready for automated code generation and downstream classification models—all while preserving interpretability via explicit decision logic—and while respecting token budgets required by modern LLM APIs.\n

# 6. From Natural Language Rules to Binary Features  

In the \textsf{FeatLLM} pipeline, the first stage produces a collection of natural‑language rules – essentially short logical statements answering questions such as *“Does the patient have chronic heart failure?”* In practice, these rules look like “If age ≥ 50 and cholesterol > 200 and smoking \< 5, then Yes.”  The second and third stages of the framework hinge on turning those textual rules into **binary features** that can be fed to a lightweight downstream model. This transformation is non‑trivial for two reasons: (i) large language models (LLMs) often render mathematical and logical operators in a descriptive way (“greater than”, “less than”, “and”) that is hard to parse; and (ii) executing arbitrary code requires rigorous safety checks to safeguard the host environment.  

Below we unpack each of the challenges and describe the systematic solution adopted in FeatLLM, from designing robust prompts to safely executing the derived code with Python’s `exec()`.

---

## 6.1 Challenges of Noisy NLP Output (verbal vs symbolic operators)

### 6.1.1 The Nature of LLM Language Generation  
When prompted to generate a rule, an LLM is exposed to millions of sentences that use both symbolic notation (e.g., `>`, `<`, `&&`) and verbal descriptions (“greater than”, “less than”, “and”). The model learns to prefer whichever style it has seen most often in its training corpus. As a result, even when constrained by a response format, small variations can creep in:  

- **Operator substitution** – `"happiness > 3"` might appear as `"happiness greater than 3"`.  
- **Logical connective variation** – `"and"` could become `"along with"`, `"plus"`, or `"as well as"`.  
- **Typographical errors** – accidental missing spaces or punctuation (“`age>=50`” vs `"age >= 50"`).  

Because downstream code parsing is highly sensitive to syntax, even a single deviation can cause a syntax error or unintended logic.

### 6.1.2 Ambiguity with Categorical Features  
Rules also involve categorical values (`status == "employed"`). An LLM may phrase this as `status equals employed` or `status is employed`. While both are semantically equivalent, the resulting string needs explicit quotation marks around string literals for valid Python syntax.

### 6.1.3 Counting of Rules per Class  
Each rule belongs to a particular class label (“Yes” or “No”). Mis‑labeling can easily happen if an LLM inserts an extraneous comma or uses an unconventional label wording, further complicating automatic extraction.

---

## 6.2 Co‑prompting an LLM for Parsing Code Generation

To overcome these difficulties, we treat the LLM itself as a **semantic interpreter** rather than a simple string generator. The key idea is *co‑prompting*: we first feed the collection of rules as text into an LLM accompanied by instructions that ask it not just to paraphrase, but to produce **Python expressions** that evaluate them.

### 6.2.1 Prompt Construction

The prompt is carefully structured in four parts:

1. **Functional Header** – We define a function signature that clearly states input (a row of data in dictionary form) and output (a boolean flag). For instance:  

   ```python
   def eval_rule(row):
       """
       Returns True if row satisfies the following condition:
       ...
       """
   ```

2. **Rule List Injection** – We embed every rule exactly as written by the first LLM pass into the docstring or directly inside the function body separated by comments. This preserves recognizability for both humans and subsequent parsing steps.

3. **Explicit Translation Guidance** – We instruct the model to translate each textual rule into Python using operators `>`, `<`, `==`, `!=`, `and`, `or`. If it uses words like “greater than,” we ask it explicitly: *“Replace 'greater than' with `'>'` when constructing boolean expressions.”*

4. **Return Statement** – We ask for a final line that aggregates all individual checks with logical connectors consistent with the original rule list (e.g., using explicit parentheses).

An example snippet might look like:

```
When you see "If age ≥ 50 and sessionTime > 30 then Yes", write:
return (row['age'] >= 50) and (row['sessionTime'] > 30)
```

### 6.2.2 Controlling for Syntactic Variations

The prompt includes multiple examples where non‑parsing verbs are converted into symbols, making it clear how disambiguation should happen:

```
Input: "If smoking < 5 then No".
Output: return row['smoking'] < 5
```

By providing explicit input–output pairs, we condition the model on performing accurate substitutions.

### 6.2.3 Batch Articulation

Instead of generating code separately for each rule, we ask the model to produce **one block of code** containing all rules within an array or dictionary, yielding:

```python
rules = [
    {
        "class": "Yes",
        "expr": "(row['age'] >= 50) and (row['cholesterol'] > 200)"
    },
    ...
]
```

With this structure we can later iterate programmatically over all rules per class.

---

## 6.3 Executing Generated Code with Python exec() and Safety Considerations

Once the code block is returned as a string from the LLM, it must be executed safely so that new binary features can be computed for every data point.

### 6.3.1 Isolating Execution Context

We run `exec()` within a tightly controlled local namespace:

```python
local_vars = {}
exec(code_string, {}, local_vars)
rules = local_vars['rules']
```

Notably:

- **No built‑in map** – By passing `{}` for globals we strip access to any global functions (e.g., `open`, `os.system`). 
- **Restricted locals** – All mutable state remains encapsulated; after exec the only exposed object is `rules`.

### 6.3.2 Sanitizing Inputs

Each row supplied to `eval_rule` is represented as a plain dictionary without stray attributes:

```python
def eval_rule(row):
    return <expression>
```

Since expressions only reference keys existing in the dictionary (`row['age']`), no external variables leak into evaluation.

### 6.3.3 Preventing Infinite Loops or Delays

We also wrap every evaluation inside a timeout mechanism:

```python
import signal
def timeout_handler(signum, frame):
    raise TimeoutError("Rule evaluation timed out")

signal.signal(signal.SIGALRM, timeout_handler)
signal.alarm(1)   # one second per evaluation
try:
    result = eval_rule(row)
finally:
    signal.alarm(0)
```

This ensures that if an ill‑formed expression contains an infinite recursion or unwieldy computation, our pipeline will abort gracefully.

### 6.3.4 Unit Tests on Generated Rules

Before applying them on test data we run mini‑tests using synthetic rows covering edge cases (null values, boundary numeric values). If any test fails this flags potential code generation errors early.

---

## 6.4 Example Walkthrough

Below is a complete end‑to‑end illustration of how FeatLLM transforms one natural‑language rule into a usable binary feature.

### Step 0: Input Data Sample
```python
sample = {
    'age': 58,
    'blood_pressure': 'low',
    'cholesterol': 225,
    'smoking': 2,
}
label = 'Yes'      # ground-truth label for training sample
```

### Step 1: Rule Generation Prompt
(Provided earlier under "Prompt Design")  
The model outputs two successful rules for class “Yes”:

```
1) If age >= 50 AND cholesterol > 200 AND smoking < 5 then Yes 
2) If age >=45 AND blood_pressure == high AND cholesterol >250 then Yes
```

### Step 2: Co‑prompted Parsing Prompt  
We feed these two lines plus instructions to convert them into Python.\*

*Co‑prompted Response*:

```python
rules = [
    {"class": "Yes",
     "expr": "(row['age'] >= 50) and (row['cholesterol'] > 200) and (row['smoking'] < 5)"},

    {"class": "Yes",
     "expr": "(row['age'] >=45) and (row['blood_pressure'] == 'high') and (row['cholesterol'] >250)"}
]
def eval_rules(row):
    return any(eval(rule["expr"]) for rule in rules)
```

*(Note: The field name `'blood_pressure' == 'high'` is quoted because it’s categorical.)*

### Step 3: Safe Execution in Local Namespace
```python
local_vars = {}
exec(parsed_code_string, {}, local_vars)
eval_rules = local_vars["eval_rules"]
rules_for_yes = [r["expr"] for r in local_vars["rules"] if r["class"] == "Yes"]
```

### Step 4: Feature Extraction Loop  
For each data point across training/validation/test sets we compute whether it satisfies each rule:

```python
def feature_matrix(rows):
    features = []
    for row in rows:
        feature_row = [int(eval(rule)) for rule in rules_for_yes]
        features.append(feature_row)
    return np.array(features)

X_bin = feature_matrix([sample,...])   # shape (N_samples × R_rules_per_class)
```

Now every sample has a binary vector indicating compliance with each rule related to class “Yes”.

### Step 5: Learning Weights  
These binary vectors are fed into a small linear classifier (`np.maximum(w_k,0)` times `z_k`) which learns weights per rule via cross‑entropy loss on limited training shots.

## Key Takeaways

| Stage | Action | Key Challenge |
|-------|--------|--------------|
| Rule generation | Prompted LLM output natural language | Noise & variability |
| Co‑prompting | Ask LLM to produce Python code | Ensuring syntactic correctness |
| Exec & safety | Run generated code Ti± safety wrappers | Runtime errors / sandbox issues |
| Feature encoding | Turn rules into binary matrix | Correct mapping & scalability |

By delegating both syntactic interpretation (*co‑prompting*) and semantic execution (*sandboxed exec*), FeatLLM turns raw LLM imagination into deterministic features that can be learned efficiently even when only a handful of labeled examples are available—one of its foundational strengths outlined throughout this textbook chapter.*

**Chapter 7 – Learning Rule Importance with a Linear Classifier**

Tabular learning with large language models (LLMs) in the *FeatLLM* framework proceeds by first asking the LLM to write *rules*—conditions that a sample must satisfy in order to belong to a certain class. These rules are then turned into binary indicators and stacked into a new representation \(\mathbf{z}\). In this chapter we describe how we take this binary, rule‑driven representation and train a very simple predictor that estimates the probability that each sample belongs to each class. Because the representation is already highly informative, we can dispense with deep neural nets or complex tree ensembles and use a purely linear classifier with non‑negative weights.

Each section below develops one building block of this approach, moving from data preparation through weight optimisation and regularisation.

---

### 7.1 Feature Vector Construction \(\mathbf{z}_k^i\) per Class

After the LLM has issued a set of \(R\) rules for each possible class, we generate a *feature vector* for every sample \(i\) and every class \(k\).

\[
  \mathbf{z}_k^i \;\in\; \{0, 1\}^{R}.
\]

The \(j^{\text{th}}\) component of \(\mathbf{z}_k^i\) records whether rule \(j\) for class \(k\) is satisfied by instance \(i\). Thus, for each class we have a separate binary feature space. In practice the number of classes is small (often two or three), so we store all \(\{\mathbf{z}_k^i\}_{k=1}^c\) as columns of a matrix.

**Parsing Rules**

Because the rules are written in natural language by an LLM, they must be parsed before they can be evaluated against raw tabular data. FeatLLM does not rely on hard‑coded hand‑crafted grammars. Instead, it sends the rule text together with a small programmer description back to the same LLM. By exploiting the LLM’s ability to read prose and generate executable code, it produces a short snippet that:

1. checks the type of each feature (numeric, categorical),
2. translates operator words (“greater than”, “equals”) into standard comparisons,
3. returns `True`/`False` for each record.

The Python `exec()` function then evaluates this code on the entire data frame, turning it into binary arrays in milliseconds. This trick keeps the parsing pipeline lightweight even when hundreds of rules must be processed, while retaining robustness against minor linguistic variations.

---

### 7.2 Weight Projection to Non‑Negative Space

Once all rule indicators are available, we need a mapping from these binary features to a *logit* for each class. FeatLLM uses an element‑wise weight vector \(\mathbf{w}_k \in \mathbb{R}^R\) per class:

\[
   \text{logit}_k^i = (\mathbf{w}_k)^\top \mathbf{z}_k^i .
\]

To guarantee that satisfying more rules can never reduce the estimated probability of that class—a property that aligns with our intuition that all rules are *affirmative* conditions—we project every component of \(\mathbf{w}_k\) onto the non‑negative space:

\[
   \tilde{\mathbf{w}}_k = \max(\mathbf{w}_k,\;0)
   = (\max(w_{k,j},0))_{j=1}^R .
\tag{7.1}
\]

Thus negative weights are clamped to zero and cannot diminish logits. This is equivalent to adding an $L_\infty$ “box” constraint during training; it also reduces the risk of over‑fitting memorising spurious correlations that appear only in few training pairs.

In practice, FeatLLM applies has this projection *after* every gradient update (instead of adding an explicit penalty) because it stays differentiable except at zero—exactly what we need for back‑propagation through batches of size one or two.

---

### 7.3 Softmax Likelihood Estimation

Having computed unnormalised scores for all classes through Eqn (7.1), we turn them into probabilities using the softmax function:

\[
   p_k^i
   = \frac{\exp(\text{logit}_k^i)}{\sum_{\ell=1}^{c}\exp(\text{logit}_\ell^i)}.
   \tag{7.2}
\]

This normalisation guarantees

- $\sum_{k=1}^{c} p_k^i = 1$,
- Each $p_k^i$ lies strictly between 0 and 1,
- The logit vector’s relative differences directly control probability mass.

Because $\tilde{\mathbf{w}}_k$ are non‑negative, expensive sequences of "rule failures" cannot create malicious effects on probabilities; only rule satisfaction helps raise a class’s logit relative to its peers.

Depending on whether the problem is binary or multi‑class, Eqn (7.2) collapses or remains as is:

- **Binary classification**: Only one logit is needed; softmax reduces to logistic sigmoid
  \[
      p_{+}^i = \frac{1}{1 + e^{-\text{logit}_{+}^i}}.
  \]
- **Multi‑class**: Full softmax is applied over all $c$ logits.

Because our weight vectors are low dimensional (on the order of tens rather than thousands), these computations are dominated by tiny matrix multiplications and incur negligible cost at inference time.

---

### 7.4 Cross‑Entropy Optimization and Hyperparameters

Once logits and probabilities are defined, FeatLLM learns its weights by minimising cross‑entropy across all labelled samples:

\[
   L_{\text{CE}}
   = -\,\frac{1}{N}\sum_{i=1}^{N}\sum_{k=1}^{c}
      y_{k}^i\,\log p_k^i,
   \tag{7.3}
\]
where \(y_k^i = 1\) if sample \(i\)’s true class equals $k$, otherwise $0$. 

**Gradient Update**

The loss differentiates w.r.t each component $w_{k,j}$ exclusively through $\tilde w_{k,j}$:

If $w_{k,j} > 0$, its gradient equals partial derivative
$\partial L_{\text{CE}}/(\partial w_{k,j})$; if $w_{k,j}\leq0$, gradient
is set to zero because increasing it would not affect $\tilde w_{k,j}$.
Hence gradients naturally respect the non‑negative projection constraint without need for extra regularisation terms.

**Learning Rate & Optimiser**

A simple stochastic optimiser suffices due to tiny parameter size:
the paper uses Adam with learning rate \(r = 0.01\).
Because only one or two shots can be present in extremely low-shot scenarios,
Feeback from early epochs may be unstable; therefore FeatLLM adopts early stopping from held-out cross-validation within each few-shot fold:
run for up to 200 epochs but terminate once validation loss stops decreasing for five consecutive epochs.

**Regularisation & Early Stopping**

With such few training points, overfitting would normally dominate.
However because each bit corresponds to an interpretable rule—and many bits will stay zero because most rules do not match any sampled points—the learned weights remain sparse.
No explicit $L_1$ penalty is added; instead sparsity emerges automatically.
Early stopping further mitigates overfitting.

**Hyperparameter Summary**

| Hyperparameter | Typical Value | Rationale |
|----------------|---------------|-----------|
| Number of rules per class (\(R\)) | 10 | Adequate expressiveness without bloating prompts |
| Ensemble size (\(T)\) | 20 | Diminishing returns beyond ~20; balances diversity vs compute |
| Learning rate (Adam) | 0.01 | Fast convergence given tanh/minuscule gradients |
| Max epochs | 200 | Covers both low-shot convergence & early stop |
| Early stop patience | 5 | Lightweight yet robust |

Any changes scale linearly: doubling rules effectively doubles feature dimension and memory but leaves inference time unchanged because evaluating the linear model is still O(c × R). The same method works seamlessly whether you have two or ten classes; just extend each $\mathbf{w}_k$ accordingly.

---

### Why Does This Work?

A linear model might seem too weak compared with deep nets or boosted trees.
However, FeatLLM supplies it with highly semantically meaningful features—each binary input records that *this particular human-like condition holds*. Since human rules tend to capture causal relationships rather than arbitrary correlations, most true positives emerge automatically from satisfied conditions.
Consequently,

- **Data efficiency**: With only a handful of labelled examples you can learn reliable weights because there are no low-level interactions among raw columns—rules already encode them.
- **Interpretability**: Every weight multiplies an explicit rule; inspecting positive weights tells you exactly which conditions drive predictions.
- **Inference speed**: Evaluating $c$ dot products with at most dozens of elements is trivial compared with calling an entire transformer model per prediction.

Ultimately this simple optimisation encapsulates how FeatLLM turns linguistic knowledge into statistical power while staying computationally lightweight – exactly what engineering needs in real-world tabular problems where data quantities are scarce but domain knowledge (captured by an LLM) is plentiful.

# 8. Ensemble and Bagging Strategies

When Large Language Models (LLMs) are invoked to generate rules that will later be turned into features, the output is far from deterministic. Variations in temperature, the order of demonstration examples, or the subset of data or columns presented to the LLM can all lead to different sets of rules. Rather than treating such variability as a nuisance, the \textsf{FeatLLM} framework deliberately harnesses it as a source of diversity which, when combined using ensemble techniques, improves both robustness and accuracy. This chapter delves into the mechanics of that diversity, explains why it is beneficial for tabular data with many features, and lays out practical guidelines for implementing feature- versus instance‑bagging strategies.

---

## 8.1 Randomization Sources

Anything that reduces the predictive determinism of an LLM’s output is a candidate for generating diverse instances of rule sets. The authors of \textsf{FeatLLM} identified two particularly effective sources:

1. **Temperature**  
   Temperature controls how aggressively the LLM samples from its probability distribution over tokens. A higher temperature (e.g., 0.7–0.9) enlarges the tail of this distribution, encouraging exploration of less likely token sequences and thereby producing more varied rule templates. In contrast, a low temperature (e.g., 0.2) pushes toward high‑probability tokens, often yielding near‑deterministic results. By using a moderately high temperature during rule extraction, each call to the LLM can potentially surface a different subset of plausible rules.

2. **Example Demonstration Order**  
   In in‑context learning, the sequence in which demonstration pairs (serialized feature–label descriptions) appear can influence which associations the model foregrounds in its reasoning chain. Empirical studies have shown that swapping even a single demo can alter downstream predictions \citep{lu2022fantastically}. By randomizing demo order before each LLM query we inject another dimension of noise that leads to different rule derivations even when all other prompt items stay identical.

These randomization sources are straightforward to integrate into the prompting pipeline: one simply cycles through an outer loop that collects `T` sets of rules, each obtained by running the rule‑generation prompt with a freshly sampled temperature value and a shuffled demo list.

---

### 8.1.1 The Effect on Rule Diversity

The authors measured rule overlap across trials by inspecting how many extracted rules were reproducible when running five independent prompts with identical conditions (aside from temperature). On datasets with many features (e.g., Communities or Myocardial), only about 1–2 % of rules appeared consistently across all trials; the rest varied markedly. This low overlap indicates high diversity and suggests that each trial captures a different “view” of the tabular relationship space.

In contrast, when demonstrations were presented in a fixed deterministic order and temperature was set near zero, rule overlap approached 90 %, reflecting near‑identical outputs on successive runs. That homogeneity limits gains achievable by ensembling: imagine every learner votes the same way; their average offers no advantage over any single model.

## 8.2 Feature Bagging vs Instance Bagging

The ensemble strategy in \textsf{FeatLLM} hinges on *bagging*—drawing bootstrap samples for each learner—but it goes one step further by allowing bagging over *features* rather than just *instances*. We first explain both concepts separately and then contrast their strengths and trade‑offs.

### 8.2.1 Instance Bagging (Traditional Approach)

Instance bagging draws a random subset (with replacement) from the available training examples for each trial:

- **Procedure:** For every ensemble member \(t\), sample \(k\) training points (potentially with repetition) from the limited \(k\)-shot support set.
- **Motivation:** Each learner processes a slightly different view of the data distribution; this can mitigate overfitting when training complex models.
- **Drawback for \textsf{FeatLLM}:** With few shots (\(k\) tiny), sampling with replacement yields many duplicated examples; thus diversity is limited because every member receives almost identical demonstrations after shuffling.

### 8.2.2 Feature Bagging (Novel Idea)

Feature bagging selects subsets of columns to be presented to the LLM during rule extraction:

- **Procedure:** For every expert-run \(t\), keep only a random selection \(F^{(t)} \subseteq F\) of feature names and definitions when serializing data into prompts.\newline
   Then run rule extraction on this reduced feature set.
- **Motivation:** Since LLMs explicitly consult given column names to reason about relevance (“Does age affect risk?”), changing which columns they see forces them to discover different relationships among those visible columns.
- **Benefit for Large Feature Sets:** Datasets like Communities have > 100 attributes; fitting all silently will overflow token limits or cause performance degrade due to prompt size constraints. Feature bagging keeps prompts within permissible size while ensuring that over many trials almost all columns participate in at least one extraction.
- **Competitive Diversity:** Because each learner examines only a portion of features, they tend to produce non‐overlapping rule sets—some features will never appear in certain trials but might dominate others.

---

### 8.2.3 Hybrid Bagging Strategy

In practice \textsf{FeatLLM} often uses *both* types simultaneously:

\[
\begin{aligned}
F^{(t)} &= \text{RandomSubset}(F,\alpha)\quad (\alpha \in [0,1])\\
I^{(t)} &= \text{RandomSubset}(k\text{-shot examples},\beta)\quad (\beta \in [0,1])
\end{aligned}
\]

where \(\alpha\) controls how many columns are kept per trial and \(\beta\) regulates instance sampling proportion (< 1 when using fewer shots). Typically values like \(\alpha=\frac{1}{3}\)–\(1/4\) ensure prompt length stays within one third to half of token limits while still covering most columns over fifty bags.

The resulting ensemble members are distinct both in feature composition and review order due to shuffled demos; thereby they produce complementary rule vectors.

---

## 8.3 Why Ensembles Matter in Few‑Shot Tabular Learning

The fundamental problem addressed here is *sample scarcity*. With only a handful of labeled observations we must rely heavily on prior knowledge encoded within an LLM or derived statistical patterns from data itself.

### 8.3.1 Reducing Variance

Ensemble averaging reduces variance: if each learner’s predictions are noisy but unbiased, averaging smooths them out:

\[
p^{(i)}_{\text{ens}} = \frac{1}{T}\sum_{t=1}^{T} p^{(i)}_{t}
\]

In practice this translates into tighter calibration curves and higher AUROC values across datasets when compared to any single extractor average weight model.

### 8.3.2 Mitigating Spurious Correlations

Table robustness experiments revealed stark degradation when unrelated features were injected into Heart dataset; baselines crashed as spurious correlations bloomed whereas \textsf{FeatLLM} stayed relatively stable (\(\Delta \mathrm{AUROC} <5 %\)). The weight tuning stage penalizes rules that do not generalize well over training data—yet ensemble agreement counteracts occasional mis‐inferred rules spawning dead weights: if only one bag picks up such misleading pattern while others ignore it, its influence shrinks in final average probabilities.

## 8.4 Practical Implementation Workflow

Below is an end‑to‑end pseudo workflow illustrating how an implementation might orchestrate bagged learners.

```python
def ensemble_rule_extraction(data_X, data_y,
                            feature_definitions,
                            n_ensemble=20,
                            n_rules_per_class=10,
                            temp_mean=0.5,
                            temp_std=0.15):
    """
    Returns averaged class probabilities p_ens(x) for any new x.
    """
    # Pre-sample angles for temperature variation
    temps = np.clip(np.random.normal(temp_mean,
                                     temp_std,
                                     size=n_ensemble),
                    0., 1.)

    # Hide remaining variables behind scalar placeholders
    all_weights = []        # container for Bayesian weights
    all_ruleset_list = []   # each element: list(dictionnary[str: str])

    for t in range(n_ensemble):
        # ======== Bagging stage ========
        # Step A: Column subset
        selected_cols = np.random.choice(len(feature_definitions),
                                         replace=False,
                                         size=int(0.5 * len(feature_definitions)))
        
        # Step B: Example order randomization
        perm = np.random.permutation(len(data_X))
        X_bag = data_X[perm]
        y_bag = data_y[perm]

        # ======== Prompt construction ========
        prompt = construct_rule_prompt(
                X_bag[:n_shots], y_bag[:n_shots],
                selected_cols,
                feature_definitions,
                n_rules_per_class)
        # Provide chosen temperature 
        response_raw = call_llm(prompt,
                                temperature=temps[t])

        # ======== Parsing stage ========
        rules = parse_rules_from_llm_output(response_raw)
        all_ruleset_list.append(rules)

    # ======== Supervise linear weight learning ========
    z_matrix = build_rule_feature_matrix(data_X,
                                         all_ruleset_list)
    w_weights = train_positive_linear(z_matrix,
                                      data_y)

    # ======== Average predictions ========
    p_ens = softmax(np.dot(z_matrix[None], w_weights).mean(axis=0))

    return p_ens
```

Key details omitted include actual API calls (`call_llm`), serialization logic (`construct_rule_prompt`), syntax parsing (`parse_rules_from_llm_output`) via an internal coding routine generated by GPT itself (as described in Section 4–subsection §Inferring Class Likelihood via Rules). Importantly:

- `temp_mean` should stay around set value used during experimentation (≈ 0 ∙ 5).
- `selected_cols` size can be tuned if token budgets exceed limit.
- `n_shots` denotes few-shot sample count per dataset; must obey `k` ≤ total training size.

## 8.Conclusion

Ensemble and bagging strategies are not mere mechanical add‑ons but integral components enabling {\sf FeatLLM} to navigate scarcity and complexity inherent in few-shot tabular learning tasks:

- Randomized temperature and demo sequence create meaningful perturbations in LLM outputs.
- Feature bagging keeps promises on large attribute sets since token budgets would otherwise be violated.
- Hybrid bagging balances instance-wise variability with column-wise surprise.
- Weight tuning plus averaging tamp down spurious “rules” while preserving discriminative ones.
- Empirically validated gains confirm these design choices raise model robustness without incurring per-instance inference costs typical of pure LLM pipeline approaches.

For practitioners implementing lightweight tabular classifiers augmented by language models, an understanding of these techniques paves a path toward high performance without sacrificing efficiency—a cornerstone for real-world deployments where labeling budgets are thin and inference latency is strict.
