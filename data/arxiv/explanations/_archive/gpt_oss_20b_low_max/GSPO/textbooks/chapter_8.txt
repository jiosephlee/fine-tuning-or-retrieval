Chapter 8: # 8. Empirical Evaluation Framework

In the previous chapters we introduced Group Sequence Policy Optimization (GSPO) and argued that it solves the fundamental instability problems of prior word‑level reinforcement learning algorithms, particularly for large language models (LLMs) and sparse‑activation MoE architectures.  However, a theoretical breakthrough is only convincing when it can be demonstrated reliably across a wide range of realistic settings.  This chapter therefore lays out the experimental protocol that we used to validate GSPO on a commercial‑scale LLM, covering every aspect of the empirical study—from model selection through query management and evaluation culture to the systematic tuning of hyper‑parameters that govern the clipping mechanism.  The goal is that a reader who follows these guidelines can reproduce the reported gains or, at minimum, understand why each choice matters.

## 8.1 Model Selection

### 8.1.1 Cold‑Start Setting

The most common industrial pipeline starts from a raw pre‑trained language model that has never seen any reinforcement signals.  In this “cold‑start” scenario we treat every token sequence as equally likely before any fine‑tuning, so the initial policy \(\pi_{\theta_0}\) is obtained from the standard masked language modelling objective.  Although this approach guarantees a clean baseline, it forces RL to learn from scratch and often requires prohibitively large rollout budgets.

### 8.1.2 Pre‑Fine Tuned Base Models

In practice, RL is typically applied after a supervised fine‑tuning stage on high‑quality dialogues or instruction data.  For our experiments we use *Qwen3‑30B‑A3B‑Base*, a dense transformer pre‑trained to ~30 B parameters and then further optimized with instruction fine‑tuning to produce *Qwen3‑30B-A3B-Base*. This base model already encapsulates high‐level world knowledge, making it possible to observe RL gains in fewer iterations.

All comparisons across baselines are performed on the same base checkpoint so that any difference can be attributed to the RL algorithm alone.

## 8.2 Baselines

We compare GSPO against *Group Relative Policy Optimization* (GRPO), which is the state‑of‐the art for reward shaping without an external value model.  GRPO’s objective (Eq.~(12)) relies on token‑level importance ratios \(w_{i,t}\) that are notoriously unstable for long responses—precisely what GSPO claims to fix.

• **GRPO**: All hyper-parameters—including clipping ranges and learning rates—are tuned in an identical fashion as GSPO, so any performance gap is due solely to algorithmic differences.

• **PPO (value–based)**: We also included a conventional Proximal Policy Optimization implementation that uses a separate value network for advantage estimation, as an upper bound on performance when a powerful auxiliary model is available.

## 8.3 Query Sets and Rollout Management

RL training repeatedly samples a batch of meaningful prompts (queries) and generates responses with the current policy \(\pi_{\theta}\).  These prompts form the *query set* \(\mathcal{D}\), whose composition significantly influences both training dynamics and final downstream task performance.

| Stage | Query Set Strategy | Notes |
|-------|--------------------|-------|
| **Pre‑training** | Small curated set (~5K prompts) | Covers broad domains; ensures stability |
| **RL Stage – Initial** | Medium dataset (~25K prompts from open data) | Provides diversity but keeps input cost manageable |
| **RL Stage – Scaling** | Expanded set (~100 k prompts) derived from public conversation collections | Boosts coverage and induces data sharding during retries |
| **Mix & Recompute** | Periodic re-selection of top–performing questions (by earlier RL rounds) | Injects curriculum learning behavior |

During training each mini‑batch contains \(G\) responses per query.  In our experiments we fixed \(G=8\).  Responses are generated using temperature \(0\) geo‐sampling with token length cutoffs tuned per task: e.g., for AIME Pass@1 we used \(|y| \leqslant 500\); for LiveCodeBench we allowed up to \(800\).

Crucially, because GSPO performs clipping at sequence level, all responses in a mini-batch are evaluated together irrespective of their length differences—a design aligned with how rewards are assigned per entire sequence rather than per token.

## 8.4 Evaluation Metrics

The ultimate test of RL quality lies in downstream evaluation benchmarks that measure real problem solving ability:

* **AIME '24** – Pass@1 over \(32\) samples per problem; focuses on mathematical reasoning competency.
* **LiveCodeBench** – Pass@1 over \(8\) samples per programming prompt; tests code generation reliability.
* **CodeForces** – Elo rating computed by submitting solutions to CodeForces gym; measures practical algorithmic efficiency.

Each benchmark returns an average score across problems; higher is better.  We track these scores every training epoch as well as during inference runs with fixed evaluation queries to guard against overfitting distractions like early stopping or over-generation.

## 8.5 Hyperparameter Tuning Strategy

The most delicate parameter in both GSPO and GRPO is the clipping range \([\varepsilon_\text{left}, \varepsilon_\text{right}]\).  
Unlike token‐level PPO where \(\varepsilon\approx0.2\) is customary, GSPO’s sequence‐level ratio renders \(\varepsilon\) extremely small (on the order of \(10^{-4}\)). The reason lies in length normalization: each token contributes roughly \(\log s_{i}(\theta)/|y_i|\), so even modest deviations cause exponential growth or shrinkage when exponentiated back.

### Grid Search Procedure

For each algorithm:

1. Fix learning rate \(lr=2\times10^{-5}\).
2. Construct a two‐dimensional grid:
   * Left clip: \([10^{-5},\,10^{-4},\,10^{-3}]\)
   * Right clip: adjust proportionally such that right = left + \(\Delta\), with \(\Delta =0 if\, G=1\).
3. Sample each combination once for a rapid “fast episode” of \(5\times10^5\) gradient updates.
4. Record AIME Pass@1 after fast episode.
5. Select top candidate pair (\(\varepsilon_\text{left},\,\varepsilon_\text{right}\)).
6. Conduct full training with selected pair for \(>10^7\) updates.

In practice we found:
* GSPO – Left clip \(\approx3\times10^{-4}\), right clip \(\approx4\times10^{-4}\).
* GRPO – Left clip near \(0.2\), right clip near \(0.27\).

These values were adopted across all tasks because they led to comparable convergence speed while guaranteeing stability even in MoE models where expert activation volatility can otherwise derail training.

### Additional Hyperparameters

Other tunable variables—like batch size (5736 tokens per GPU for cold start), weight decay (\(10^{-2}\)), AdamW betas ([\(0.9,\,0.999\)\]), and rollout horizon—were held constant across baselines unless explicitly noted in footnotes because prior work showed they had diminishing returns relative to clipping adjustments.

## 8.6 Experimental Protocol Overview

Below is an end-to-end snapshot of one full experimental run:

```
Load Qwen3-30B-A3B-Base checkpoint
FOR each candidate clipping pair:
    Load base checkpoint into trainer
    FOR epoch = 1 .. N_epochs:
        Sample batch = X Minibatches from D
        FOR minibatch in batch:
            Generate G responses y_i ~ π_old
            Compute rewards r(x,y_i)
            SAMPLE adv_i = (r(x,y_i)-mean)/std
            APPLY seq-level CLIP(s_i(θ), left,right)
            UPDATE θ using AdamW
        END
        Evaluate on AIME/LiveCodeBench/CodeForces
    END
    Record best AIME Pass@1
SELECT best clipping pair
Train final model with selected hyperparams until convergence or compute limit
Save checkpoint every X steps  
```

All evaluations use deterministic sampling (temperature = 0, no top-p).  
Rollout generation employs *deterministic beam search* with width = 1 to avoid stochastic variance from sampling in pilot phases; during final fine-tuning we employ *random sampling* with temperature = 0 plus nucleus truncation (\(p=0.95\)) to emulate realistic conversational conditions.

## 8.7 Discussion of Results

The empirical charts produced by this formulation show:

* Generally smoother learning curves for GSPO than GRPO under identical compute budgets.
* Greater return per gradient step—GSPO reaches AIME Pass@1 ≈ 90% while GRPO stalls at ≈70%.
* On LiveCodeBench both achieve near-saturation around Pass@1 ≈ 45%, yet GSPO consistently requires fewer update steps.
* CodeForces Elo climbs about \(70\) points faster under GSPO, reflecting more efficient exploration of optimal algorithmic patterns.
* RS-indexed scores remain stable across checkpoints indicating no catastrophic collapse—a key highlight corroborated by adjacent table entries referencing ±100% variance reductions relative to GRPO runs.

Crucially, when using MoE-specific routing replay strategies tuned for GRPO—adding extra memory buffers and adjusting expert routing probabilities—the performance advantage shrinks but never disappears: GSPO cleanly dominates without such complexities due to its sequence-level independence from individual token likelihoods which fluctuate strongly when experts swap during updates.

In summary, this carefully engineered experimental framework demonstrates consistently superior performance tuned by minimal hyperparameter adjustments—a hallmark sign that GSPO’s conceptual shift—from token-level importance weighting to sequence-level importance ratio—is not merely an artifact of particular settings but an intrinsic algorithmic improvement amenable to large LLM workloads.

--- 

Any research group aiming to validate or extend GSPO should adopt the same methodological structure documented above: use large dense checkpoints as baselines, define well‐balanced query sets covering multiple domains, measure multi-task downstream metrics, conduct dedicated hyperparameter sweeps for clipping ranges tailored differently between token- vs sequence-level algorithms owing to their distinct likelihood scaling properties, and rely on reproducible rollout batches with deterministic seeds when probing convergence early (`fast episode`). Follow these guidelines and you will obtain clear evidence about which aspects of reinforcement learning truly cooperate—or conflict—with modern LLM architectures like MoE hybrids or backbone transformer families such as Qwen/Alpaca variants.*
