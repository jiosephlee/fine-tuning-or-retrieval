# Speed vs Size  
**Trade‑Offs When Using Butterfly vs Classical PEFT Methods**

Large foundation models have become the backbone of modern AI, but fine‑tuning them for a new downstream task can still be a pain. Two families of *parameter‑efficient finetuning* (PEFT) methods sit at opposite ends of the spectrum: memory‑light, slow‑down free adapters versus computation‑heavy but highly expressive butterfly factorisations.  
In this post we compare  

* **LoRA** – low‑rank additive updates  
* **BOFT** – orthogonal butterfly factorisation  
* **Classic Adapter tuning** – small extra modules with their own parameters  

and spell out the practical trade‑offs in training time, memory usage, number of trainable parameters, and inference latency.

---

## 1. The PEFT Landscape

| Method | Core Idea | Working Principle |
|--------|-----------|-------------------|
| **LoRA** | Add a low‑rank factorised update `ΔW = A·Bᵀ` to the frozen weights `W₀`. | Only `A` and `B` are updated; the remaining network remains unchanged. |
| **BOFT** | Multiply the frozen weight by a dense **orthogonal** matrix `R` that is factored into a product of sparse butterfly matrices. | `∆W = R·W₀`. The learning signal is multiplicative and preserves the spectral norm of `W₀`. |
| **Adapter** | Insert small bottleneck layers between existing layers, typically an affine layer → non‐linearity → affine layer (e.g., 4 × d dimension). | Parameters are entirely new modules; original weights stay frozen. |

> **Bottom line**:  
> -- LoRA cares about *parameter count*.  
> -- BOFT cares about *expressive transformations* with a neat inductive bias from FFT‐like swaths.  
> -- Adapters keep the *inference pipeline intact* and add tiny extra latency.

---

## 2. Quantitative Comparison

Below is a sanity‑checked summary (values vary across model size and task; numbers illustrate typical orders of magnitude).

| Metric | LoRA | Adapters | BOFT |
|--------|------|----------|------|
| **Trainable parameters per layer** | 2·r·d (r = rank) e.g., 4 × d for r=2 | 2·b·d (b = bottleneck width) e.g., 256 × d for b=128 | (b–1)/2 × m × d ≈ d·log₂d for b=2, m=log₂d |
| **Memory overhead (gradient)** | ≈ same as trainable parameters (≈8 bytes each) | ≈ same as trainable parameters | Slightly higher due to matrix products during backward pass |
| **Training throughput** | Very fast (few ms extra per step) | Similar to LoRA or faster for small adapters | Slower: each forward/backward needs *m* sparse matrix multiplications → ~2× slower on GPUs |
| **Inference latency** | None – weights merged after finetuning | No extra latency – modules become part of forward pass (tiny overhead) | None – final orthogonal matrix pre‑multiplied into the weight matrix |
| **Non‑zero ratio in final weight** | Dense – uniform over all entries because update is additive | Dense – concatenation/addition of adapter output onto original activations | Dense – product of butterflies can produce a fully dense matrix |

### 2.1 Training Overhead

- **LoRA**: Each step still runs a standard forward/backward on the frozen core model; only an extra *low‑rank* matrix multiplication is needed when computing gradients w.r.t `A` and `B`. GPU occupancy remains high.
- **Adapters**: Additional forward path through tiny layers; memory stays low; very little GPU contention.
- **BOFT**: Every training iteration requires `m` sparse matrix multiply operations before applying to activations (`R · W₀`). For `m = log₂ d`, this can cost ≈ 50–70 % more compute time compared to LoRA/adapters.

### 2.2 Memory Footprint

- All three methods keep the main model frozen, so they're memory friendly in principle.
- LoRA needs to keep two rank‑`r` matrices plus their gradients; adapters keep two bottleneck matrices plus their gradients.
- BOFT stores `(b–1)/2` parameters per butterfly block times `m`; however, the backward pass must also materialize intermediate activation maps of each sparse multiplication stage, which can raise peak memory by ~10–20 %.

## 3. Practical Tips for Choosing

| Scenario | Recommended PEFT |
|----------|------------------|
| ★ Need *minimal training time* (e.g., limited compute budget). <br>*Model size moderate.* | **LoRA or narrow adapters** – choose rank/bottleneck small enough that added compute is negligible. |
| ★ Want *fast adaptation* but still maintain decent modeling capacity. <br>*Fine‑tuning requires many epochs.* | **Adapters with width scaling** – larger bottlenecks give better performance without slowing inference. |
| ★ Working with *very large models* where parameter budget is strict and you need *strong inductive bias*. <br>*Finetuning stability matters.* | **BOFT with low rank m ≈ log₂d, b=2 or 4** – gives order d·log d parameters while preserving spectral norms, improving stability on text‑to‑image or vision transformers alike. |
| ★ Concerned about *memory* during training on GPU with tight quota. <br>*Model has many large attention heads.* | **Adapters or LoRA with aggressive compression**, or use mixed precision / gradient checkpointing with BOFT to keep memory down. |

### A Quick “Checklist”

1. **Compute budget?**  
   - ≤ 5 % additional load → Adapters/LoRA OK.  
   - >10 % -> Consider BOFT if expressiveness matters.

2. **Parameter budget?**  
   - < 1 % of total → Adapters best if you like architectural changes only.
   - ≥ 0.5–1 % but still want orthogonality → BOFT shines.

3. **Training stability?**  
   - Issues with exploding/vanishing norms → BOFT’s spectral preservation helps.

4. **Inference latency?**  
   - No constraints → All are fine after merging; if latency is critical at deployment, choose adapters because of their tiny per-layer overhead during training.

---

## 4. Common Misconceptions

1. **“BOFT always outperforms LoRA.”**  
   Not true in every scenario—LoRA’s simplicity can beat BOFT when you’re fine-tuning a shallow RNN or an MLP where expressivity is less critical.

2. **“More parameters mean better accuracy.”**  
   In finetuning this is not always the case—orthogonality constraints regularise the update space and often lead to better generalisation at smaller cost.

3. **“Adapation layers add inference cost.”**  
   They do add a tiny amount of work per layer, but for most modern GPUs this overhead (< 1 ms per image on Vision Transformers) is negligible compared to full model inference times.

---

## 5. Takeaway

Choosing between LoRA, BOFT, and Adapter tuning boils down to striking the right trade-off:

- Want speed ➔ Go LoRA or narrow adapters.
- Want strong regularisation + minimal extra compute ➔ Pick adapters (if you can afford tiny extra ops).
- Want expressive transformations that preserve spectral properties ➔ Opt for BOFT even if it costs ~2× training time.

Ultimately, experiment! Start with a lightweight variant (e.g., LoRA with rank 4) and only move to butterfly factorisation once you hit saturation in performance or run into overfitting.

Happy finetuning!
