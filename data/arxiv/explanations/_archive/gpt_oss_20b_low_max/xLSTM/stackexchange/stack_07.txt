\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### How are residual block architectures chosen for xLSTM blocks (post vs pre up‑projection), and what effect does this have on performance?
Question:
"sLSTM" uses post‑up‑projection blocks while "mLSTM" uses pre‑up‑projection blocks according to Section 3.4.2. What guides this design choice? Does placing up‑projection before or after recurrent processing affect numerical stability or expressivity?
Answer:
### Short‑answer  

* **sLSTM “post‑up‑projection”** – the block first processes the input in its native dimensionality, updates the scalar state, and only **then** expands the output to a higher‑dimensional “high‑space” representation via a learnable linear projection and non‑linearity.  
* **mLSTM “pre‑up‑projection”** – the block first projects the input into a high‑dimensional space, performs all matrix‑memory operations completely within that high‑dimensional space, and finally collapses back to the original dimension.  

The choice is guided by the *memory capacity* of each variant and by *parallelisation considerations*, exactly as explained in §3.4.2 of the paper.

--------------------------------------------------------------------

## Why the two blocks differ

| Block type | Key property | Reason for order |
|------------|--------------|------------------|
| **sLSTM** | **Scalar state, heavy memory mixing** (recurrent connections between hidden states) | Mixing can only be done in the low‑dimensional space; expanding to a high dimension before mixing would destroy the scalar structure and unrolls an expensive recurrence.  Putting projection *after* ensures that the sparse, highly expressive scalar state is updated first, then mapped into a richer feature space for downstream layers. |
| **mLSTM** | **Matrix state (covariance) with large storage capacity** (size $d\times d$) | Matrix updates ($\mathbf{C}_t = f_t\,\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t \mathbf{k}_t^\top$) are naturally performed in a high‑dimensional space where each entry of $\mathbf{C}$ is a potential interaction between two features.  Projecting *before* gives each key/value vector a full $d$-dimensional representation required for the outer‑product update; projecting afterward would discard valuable cross‑feature interactions learned in that higher space.  Moreover, performing these operations in a single batch across many steps enables parallel execution on GPUs, matching the efficiency of state‑space models or fast weight approaches. |

The paper explicitly states this guidance:

> “For an xLSTM block containing an sLSTM, we use **post up‑projection**… For an xLSTM block containing an mLSTM, we use **pre up‑projection** since the memory capacity becomes larger in the high-dimensional space.”  
> – §3.4.2

--------------------------------------------------------------------

## Impact on numerical stability and expressivity

### Numerical stability

*Both variants employ exponential gating,* whose large values can cause overflow or underflow unless stabilised (Eq.~(5)-(6) for sLSTM and identical stabilization in mLSTM).  
However, because only sLSTM involves hidden–hidden recurrence (memory mix), its internal computations are inherently sequential and thus more prone to accumulating round‑off error over long sequences.  By keeping projection outside the recurrent core (post up‑projection) we minimise the range of numbers that travel through this sensitive body of gates.

Conversely, mLSTM’s parallelisable structure reduces hidden-to-hidden propagation across time steps; errors do not accumulate in the same way, so its main source of instability is limited to the large matrix product during memory updates—handled by standard FP32/FP16 matrix kernels that are highly optimised on GPUs.

### Expressivity

* sLSTM’s scalar state plus exponential gating gives it powerful **state tracking** abilities: it can revise past values more readily than a fixed (“outer–product only”) memory (see §3.2).  This makes it better at tasks such as parity or nested parentheses where tracking whether a particular symbol was seen before matters.*

* mLSTM’s matrix memory provides exponential growth in storage capacity: each key/value pair contributes at most $d\times d$ non‑zero entries to $\mathbf{C}$.  We show experimentally that this gives mLSTM a clear advantage on associative recall tasks (Sec 4.1.2).  The pre non‑linear transformation ensures that this storage is used efficiently—even for very long contexts—because every key/value pair sits fully inside the high‐dimensional representation.*

Thus, both architectural choices reflect a trade‑off: **post projection keeps sLSTM lightweight but highly expressive for tracking explicit state; pre projection gives mLSTM maximal storage while keeping computation parallelisable but sacrifices some inter‑time hidden mixing.**

--------------------------------------------------------------------

## Practical takeaway

When designing an xLSTM backbone:

1. **Use post up‑projection blocks for any variant that relies heavily on hidden-to-hidden recurrence (sLSTM).**  
   This preserves state integrity and keeps numerics manageable while still allowing residual enrichment afterward.

2. **Use pre up‑projection blocks whenever you switch to matrix memories or other mechanisms that naturally live in high dimensions (mLSTM).**  
   This guarantees that all key/value interactions are captured before any dimensionality reduction step.

In practice, xLSTMs mix these two block types in ratios like `xLSTM[7:1]` or `xLSTM[1:0]` depending on desired balance between memory capacity and sequential expressiveness—a strategy empirically shown to achieve competitive perplexities on large language modelling datasets while maintaining linear time complexity with respect to sequence length.

--- 

This guidance is central to reproducing the reported performance gains of xLSTMs over Transformers and SSMs while keeping training stable across billions of parameters.+
