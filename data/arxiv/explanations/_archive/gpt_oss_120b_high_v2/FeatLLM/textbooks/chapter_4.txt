# Conventional Baselines: Logistic Regression, XGBoost, Random Forest  

In empirical studies of tabular prediction it remains customary to begin evaluation with three well‑established machine‑learning algorithms – logistic regression, gradient boosted decision trees (as implemented in XGBoost), and random forests – because they represent distinct inductive biases while being easy to train even when only a handful of labeled examples are available.  

Logistic regression treats every input column as a numeric feature whose contribution is summed linearly before applying a sigmoid function that maps the result onto a probability space. Although it makes a strong assumption that class boundaries are approximately linear, its simplicity translates into fast training and modest memory consumption—a valuable property when only $k$ labeled rows ($k \ll N$) can be drawn from an $N$‑sample dataset $\mathcal D=\{(\mathbf x^{i},\mathbf y^{i})\}_{i=1}^{N}$. In low‑shot regimes this model can nevertheless capture useful signal provided that informative columns exist and noise does not dominate – a circumstance often verified empirically using cross‑validation over very small folds ~\cite{chen2016xgboost}.  

Gradient boosted decision trees such as XGBoost construct an additive ensemble where each new tree seeks to correct the residual errors left by previously built trees ~\cite{chen2016xgboost}. This iterative refinement enables highly non‑linear decision boundaries while preserving robustness against overfitting through regularisation techniques baked into the objective function (e.g., shrinkage and column subsampling). When only a few labelled instances are supplied the method compensates by aggressively limiting tree depth and employing early stopping based on validation loss computed over the same tiny set. Consequently XGBoost frequently outperforms purely linear models on heterogeneous columns where interactions between categorical levels matter ~\citet{ho1995random}.  

Random forests aggregate a collection of fully grown decision trees trained on bootstrap re‑samples of the available data ~\citet{ho1995random}. Each tree makes an independent vote for a class label; the most frequent vote defines the final prediction. By virtue of bagging at training time random forests reduce variance without requiring any hyperparameter tuning specific to low‑shot conditions—a property appealing when time or compute resources constrain extensive hyperparameter searches.\footnote{In our experiments we performed grid search combined with $k$‑fold cross validation even when $k$ equals two or four ~\citet{kadra2021well}.} The three baselines together constitute a “classical” reference set against which newer approaches—including self‑supervised schemes and language‐model centric pipelines—are compared throughout the literature ~\citet{asuncion2007uci}.

# Self‑Supervised Pretraining  

A second direction pursued by recent research attempts to embed prior knowledge about generic tabular structure directly into model parameters before any task‐specific labels are observed. Two representative examples appear frequently in surveys of few‑shot tabular methods: **TabPFN** and **TransTab**.  

TabPFN creates synthetic training tables by sampling myriad probability distributions over feature spaces and fitting a Bayesian neural network on these generated instances ~\citet{hollmann2022tabpfn}. By exposing the network repeatedly to diverse marginal configurations—including mixtures of categorical frequency patterns, Gaussian clusters, and heavy‐tailed noise—the resulting parameters acquire an implicit understanding of how different statistical regimes manifest themselves within tabular rows. During deployment no additional optimisation is required: both training‐time examples $\{\mathbf x^{i}\}$ and test samples are concatenated into a single inference call; class probabilities are produced directly by forward propagation through the pretrained network.\footnote{This design enables “zero‑shot” operation yet also permits “few‑shot” refinement when labelled records become available.~\citet{hollmann2022tabpfn}}  

TransTab showcases an alternative route centred around **transformer architectures** that ingest column names alongside raw cell values ~\citet{wang2022transtab}. By modelling relations among columns through attention mechanisms conditioned on their textual identifiers, TransTab learns semantic embeddings capturing how certain attribute names tend co‑occur across heterogeneous tables collected during large‐scale pretraining.^[In particular the transformer learns inter‑column relationships without ever seeing actual target labels.] The pretrained encoder can then be fine‑tuned on a new task using only a couple dozen labelled rows—a scenario synonymous with low‐shot tabular learning.\footnote{The decoder component remains dormant during downstream adaptation, emphasizing transferability solely via column semantics.~\citet{wang2022transtab}}  

Both approaches exemplify **self‐supervision** because their pretraining objectives involve reconstructing masked entries or predicting distributional statistics rather than optimising classification loss on target labels – a strategy motivated by early observations that naïve semi‑supervised tricks such as pseudo‑labeling or unsupervised autoencoding often fail when feature types differ dramatically across datasets ~\citet{kadra2021well}. Nevertheless extensive benchmarking shows that while self‐supervision aids generalisation compared with naïve baselines, its benefit plateaus once very few supervised samples become available ~\citet{nam2023stunt}. In practice researchers frequently combine self‐supervision with other sources of prior information—most notably large language models—to obtain more reliable few‑shot performance.

# Unlabeled Data Augmentation Methods  

When labelled rows are scarce it is common practice to consult abundant unlabelled corpora through **semi‐supervised augmentation** techniques. Among these,
the method known as **SCARF** builds upon contrastive learning combined with domain‑aware augmentations ~\citet{bahri2022scarf}. The central idea is simple: generate altered versions (“views”) of every unlabelled row—for example by jittering numeric attributes or randomly swapping categories within categorical columns—then train an encoder so that representations derived from different views stay close while representations coming from distinct rows diverge.~\citet{bahri2022scarf} implements this objective using a pairwise loss reminiscent of SimCLR adapted for mixed discrete–continuous inputs.\footnote{\textbf{Why augment?} Augmentations expose invariances inherent in real data—for example age remains close despite small measurement noise—which helps mitigate overfitting when supervised signals are limited.~}  

During downstream evaluation SCARF freezes its encoder after joint training on unlabelled rows plus whatever sparse supervision ($k$ shots) exists; predictions are then made either using a shallow classifier trained atop those frozen representations or by directly comparing distances between labelled exemplars and test embeddings.^[The latter strategy mirrors nearest neighbour labelling.] Empirically SCARF pushes accuracy above traditional random forests under moderate $k$, yet it still lags behind more recent language‑model centric pipelines especially when relational domain knowledge encoded in natural language proves decisive—for example recognizing that “older age increases cardiovascular risk.”

# LLM‑Centric Methods  

Large language models (LLMs) encode extensive world knowledge acquired during pretraining on massive text corpora,and recent works harness this lexical expertise for **tabular reasoning** despite their native sequential nature.



### In–Context Learning Pipelines  

The most direct adaptation places raw table rows inside an LLM prompt together with an explicit *task description* (“Does this patient have diabetes?”) followed by several *few–shot demonstrations* where each demonstration consists of serialized feature–value pairs terminated by an answer label:
\[
\texttt{"}\!f_{1}\!\texttt{\ is}\!x^{i}_{1}\dots f_{d}\!\texttt{\ is}\!x^{i}_{d}\texttt{\ Answer:\ }y^{i}\texttt{"}.
\]
During inference every test row receives an identical prompt structure; hence each prediction triggers one forward pass through the model’s decoder—a process termed **in–context learning** ~\citet{dinh2022lift}. This approach avoids any model parameter updates yet gains substantial performance when $k$ is extremely small because the demonstrations implicitly convey class boundaries.\footnote{Chaining thought approximations (“chain ‑of ‑thought”) further improves reasoning stability ~\citet{wei2022emergent}} However its computational budget scales linearly with test set size because every instance must excite at least one API call.



### TABLET  

TABLET builds upon plain in–context prompting by attaching **external rule hints** generated beforehand through an auxiliary classifier – for example a lightweight decision tree trained on any available $k$ examples ~\citet{slack2023tablet}. The hints take form of prototype patterns (“Age > 60 ∧ BloodPressure ≈ High”) appended after the main task description so that the large model can condition its generation both on raw examples *and* coarse logical priors.\footnote{\textbf{Why add hints?} Hints steer attention toward potentially decisive columns while mitigating distraction caused by irrelevant variables—a symptom observed when feeding very wide tables directly into an unconstrained prompt.~} By exploiting both symbolic cues and natural language reasoning TABLET usually achieves higher AUC than vanilla in–context learning while retaining zero‐parameter updates.



### TabLLM and Parameter–Efficient Fine‐Tuning  

Another family treats the LLM itself as a *feature extractor* whose internal weights are adapted modestly using **parameter‐efficient fine‑tuning** strategies such as LoRA ~\citet{hu2021lora} or IA3 ~\citet{liu2022few}. Instead of re‑encoding every test row anew, practitioners first feed $k$ labelled rows through extended prompts containing *feature descriptions* (\textit{name}, \textit{type}, optional definition). After accumulating gradient updates confined mainly to low‑rank adapter matrices added onto frozen transformer layers, the tuned model can subsequently answer all remaining queries without reactivating expensive gradient computation.\footnote{Because adapters constitute far fewer parameters than full fine tuning they remain tractable even when only API level access permits hidden-state updates – provided such APIs expose gradient hooks.~} In benchmark experiments TabLLM surpasses pure prompting yet still requires initial exposure (“training”) phase consuming several hundred API calls—a cost acceptable for static deployments but undesirable for rapid prototyping.



### Summary Comparison  

All three families share a fundamental design choice: **the LLM participates directly during prediction time**, either once per sample (in–context), once per batch after auxiliary hint generation (TABLET), or repeatedly during a brief adaptation sweep (TabLLM). This design brings two practical consequences explored later:

*   **Per‑sample inference latency** grows proportionally with test set size because every row taxes an expensive forward pass through giant transformer stacks hosted behind commercial APIs.
*   **Prompt length restrictions** arise when many columns must be enumerated verbatim; exceeding token limits forces practitioners either to truncate potentially useful attributes or resort to column subsampling—both choices hurt predictive fidelity.

# Limitations of Existing LLM Approaches  

Although leveraging pretrained linguistic knowledge produces impressive boosts over classical baselines in extreme low‑shot settings, three intertwined drawbacks impede broader adoption.



### High Per‑Sample Inference Cost  

Across all published LLM‐centric pipelines—including those evaluated against FEATLLM—the inference phase obliges at least one external API request per test instance ~\citet{anil2023palm}. Even modestly sized validation sets therefore incite hundreds or thousands of costly queries whose response latency can exceed several seconds each depending upon cloud service load balancing.\footnote{When deploying real-time decision systems—for instance fraud detection—the cumulative delay becomes prohibitive unless massive parallelism is provisioned—a luxury rarely afforded under strict budgeting constraints.~} Consequently such methods suit offline analytics better than latency‐sensitive production environments.



### Dependence on Fine Tuning Access  

Parameter‐efficient techniques such as LoRA or IA3 presuppose **write access** into model weights either locally or via specialised APIs providing adapter injection capabilities ~\citet{kumar2019firstorder}. Yet many state-of-the-art conversational models released recently permit only read/forward APIs\null{}(e.g., GPT‑4), forbidding any gradient‐based updating whatsoever ~\citet{openai2023gpt4}. When facing such “black box” restrictions researchers cannot apply TabLLM’s adapters nor conduct even lightweight rehearsal steps required by TABLET’s hint trainer.\footnote{
A workaround would entail storing numerous prompt variants—but this merely relocates computational burden toward constructing ever larger prompts,
which brings us to another limitation… }  


### Prompt Length Bottleneck  

Standard token limits hover near four thousand words for most commercial GPT series models ~\citet{liu2023lost}. Encoding dozens—or hundreds—of column/value pairs quickly exhausts this capacity \emph{i.e.,} \(d \times (\text{name}+ \text{textual value}) \approx O(d)\). When this limit is breached many existing works resort either visual truncation (“keep first 50 columns”) or hierarchical chunking strategies whose efficacy remains anecdotal.\footnote{
Empirical results documented in Table 1 illustrate that vanilla in–context learning fails outright once datasets like *Communities* (over 100 attributes) exceed manageable prompt lengths.~} This phenomenon explains why several strong baselines—including plain prompting (\textbf{In\-Context}) and refined versions (\textbf{TABLET})—“failed” on high-dimensional tables reported in Section&nbsp;4’s experimental analysis.



### Interaction Between Limitations  

The three constraints reinforce one another: reducing token count typically involves discarding columns deemed nonessential according to naive heuristics,\ which amplifies reliance upon precise per-sample reasoning thus worsening latency budgets because more sophisticated prompting becomes necessary.\footnote{
FEATLLM mitigates this feedback loop partly via *feature bagging*, whereby a randomly chosen subset \(\mathcal S \subseteq \bigl[ d\bigr]\) feeds into each independent prompt; ensembles then aggregate diverse weak learners—as highlighted in Section&nbsp;5’s ablation study.~} Nonetheless these drawbacks remain intrinsic obstacles shared across all previous language-model mediated tabular frameworks,\ motivating research efforts seeking **feature engineering without perpetual reliance on costly forward calls**, precisely what FEATLLM proposes.


--- 

Through this survey we see how classical algorithms bring computational thrift yet lack domain awareness; self­supervised pretraining injects generic statistical priors but struggles when confronted solely with minuscule labels; semi­supervised augmentation enriches representations at extra implementation cost; finally large language models add rich encyclopedic cues—but suffer from expensive per-instance queries, inaccessible fine tuning pathways, and strict prompt budget caps. Understanding these tradeoffs equips researchers—and future practitioners—to select appropriate tools according both to resource constraints and desired interpretability before embracing newer hybrid designs such as FEATLLM which aim explicitly at turning “…the capability …into feature generation” rather than maintaining end-to-end black-box inference ~\citet{sungwon-han2024feattllm}.
