\title{A Textbook about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

Chapter 2: # 2. Foundations: Tabular Data and Few‑Shot Learning  

In order to appreciate how **FeatLLM** transforms a large language model (LLM) into an automatic feature engineer for tabular prediction, we must first become comfortable with the basic ingredients of the problem setting.  This chapter introduces the structure of tabular datasets, distinguishes between the two canonical prediction tasks—classification and regression—examines the definition and challenges of *few‑shot* (or *k‑shot*) learning, and reviews the performance measures that are routinely employed when evaluating models on tabular data.  Each notion will be presented with an eye toward intuition, because a clear conceptual grounding is essential before delving into the more intricate mechanisms described later in this text.

---  

## Tabular Datasets: Features, Types, and Names  

A **tabular dataset** is organized as a rectangular table whose rows correspond to *instances* (also called samples or observations) and whose columns correspond to *variables* (commonly called *features*).  Formally, let  

\[
\mathcal{D}= \{(\mathbf{x}^{(i)}, y^{(i)})\}_{i=1}^{N},
\]

where \(N\) is the number of labeled instances, \(\mathbf{x}^{(i)} = (x^{(i)}_{1}, x^{(i)}_{2}, \dots , x^{(i)}_{d})\) is a \(d\)-dimensional vector of feature values for instance \(i\), and \(y^{(i)}\) denotes its associated target label.  In practice each column \(j\) bears a **feature name** \(f_{j}\) that conveys its semantic meaning (e.g., “age”, “cholesterol level”).  The paper assumes that these names are available together with succinct natural‑language definitions—for instance “age is an integer representing years since birth” or “blood type is a categorical variable taking one of {A, B, AB, O}”.  Such metadata are crucial when we later ask an LLM to reason about which columns are relevant to a given prediction task.

### Numerical versus Categorical Variables  

Features come in two broad families:

1. **Numeric (continuous or discrete) features** take values on a numeric scale.  Continuous variables such as “blood pressure” can assume any real number within a physiological range, while discrete variables such as “number of prior hospital visits” take integer values but are still treated numerically by most learning algorithms.

2. **Categorical features** encode qualitative information by assigning each instance to one of a finite set of categories.  Categorical variables may be *ordinal*—where the categories possess an inherent order (“low”, “medium”, “high”)—or *nominal*, where no order exists (“city”, “state”, “country”).  In raw form these are often represented by strings or integers that serve as symbolic identifiers rather than quantities.

The distinction matters because many modeling pipelines—including those examined in the FeatLLM experiments—must treat each type appropriately when constructing rules or analyzing relationships with the target variable.

### Feature Names as Natural‑Language Prompts  

Because LLMs process text rather than raw vectors, providing **feature names** and their definitions in plain English enables the model to draw upon its vast pre‑training corpus of domain knowledge (“older individuals have higher risk of heart disease”).  In FeatLLM’s prompting scheme each feature name appears alongside its type annotation:

```
age (numeric): age in years.
cholesterol (numeric): measured concentration in mg/dL.
smoking_status (categorical): {never, former, current}.
```

These human‑readable descriptors become part of the *basic information description* supplied to the LLM before it attempts rule extraction.

## Classification versus Regression in Tabular Domains  

Once a tabular dataset is assembled, we typically aim to predict a target variable from its features.  Two broad families of supervised learning problems emerge:

### Classification  

In **classification**, the target \(y^{(i)}\) belongs to a finite set of labels \(\mathcal{C} = \{c_{1}, c_{2}, \dots , c_{K}\}\).  When \(K = 2\) we have binary classification (e.g., “diabetic / non‑diabetic”), while larger values of \(K\) correspond to multiclass problems such as predicting disease subtypes.  The learner’s objective is to produce a probability distribution over \(\mathcal{C}\), usually via a *softmax* transformation:

\[
p(y^{(i)} = c_{k} \mid \mathbf{x}^{(i)}) = 
\frac{\exp(\operatorname{logit}_{k}^{(i)})}{\sum_{\ell =1}^{K} 
      \exp(\operatorname{logit}_{\ell}^{(i)})},
\]

where each \(\operatorname{logit}_{k}^{(i)}\) is a scalar score reflecting how strongly instance \(i\)’s features support class \(c_{k}\).  In FeatLLM these logits are generated from binary rule‑based features via a simple non‑negative linear model (see Section “Inferring Class Likelihood via Rules”).

### Regression  

In **regression**, the target is continuous—in other words \(y^{(i)} \in \mathbb{R}\).  Typical examples include predicting house prices or laboratory measurements.  The model outputs a real‑valued estimate \(\hat{y}^{(i)}\), often obtained by a linear combination of features:

\[
\hat{y}^{(i)} = \mathbf{w}^{\top}\mathbf{x}^{(i)} + b.
\]

Although the primary focus of FeatLLM’s empirical study is on classification tasks (binary or multiclass), the underlying pipeline could be adapted for regression by replacing the softmax layer with an identity mapping and training using mean‑squared error loss instead of cross‑entropy.

### Why Distinguish Them?  

The distinction informs several design choices:

* **Label encoding** – For classification we must preserve categorical semantics (e.g., one‑hot encodings), whereas regression simply treats targets as scalars.
* **Loss functions** – Cross‑entropy drives probabilistic calibration for classification; mean squared error encourages accurate point predictions for regression.
* **Interpretability** – Rule‐based binary features naturally lend themselves to explaining why an instance belongs to class *c* (“age > 65 AND cholesterol > 240”).  For regression similar logical rules could indicate when “risk score” exceeds a threshold, but probabilistic interpretation differs.

## Few‑Shot Learning Definition (\(k\)-Shot) and Typical Pitfalls  

### Formal Definition  

A learning algorithm operates in a **few‑shot regime** when it receives only a tiny subset of labeled examples relative to the size of its hypothesis space.  Formally, given the complete dataset \(\mathcal{D}\), we randomly select

\[
\mathcal{D}_{\text{train}} = 
   \bigl\{ (\mathbf{x}^{(i)}, y^{(i)}) : i \in \mathcal{I}_{k} \bigr\},
   \qquad |\mathcal{I}_{k}| = k,
\]

with \(k \ll N\).  In an experimental context this selection is repeated across multiple random splits so that performance estimates remain reliable.

When dealing with multiple classes (\(K>2\)), it is common practice—in particular throughout this work—to enforce that every class appears at least once among the \(k\) training points so that each class has at least minimal supervision.

### Why Few Shots Are Hard  

With only \(k\) labelled examples per class, several difficulties arise:

1. **Statistical Overfitting** – Classical estimators such as maximum likelihood become highly variable because there are far fewer observations than parameters (e.g., many columns).  This leads models to fit noise rather than genuine signal.
2. **Spurious Correlations** – In low‑sample regimes random coincidences between irrelevant columns and labels can appear predictive by chance alone (“age” may correlate with outcomes only due to sampling fluctuation).  
3. **Insufficient Coverage** – Some regions of feature space may be completely absent from training data, making it impossible for pure data-driven methods to infer appropriate decision boundaries.
4. **Bias–Variance Trade‑off Amplified** – High variance due to limited data forces algorithms either toward overly simple models (high bias) or overly complex ones that memorize training points (high variance).

Consequently, successful few‑shot methods typically inject *inductive bias*: additional assumptions about plausible relationships that reduce reliance on scarce data alone.

### Leveraging Prior Knowledge via LLMs  

The central idea behind FeatLLM is precisely this injection of external knowledge through an LLM’s world model. By presenting few shot demonstrations together with natural language descriptions of each feature—information that resides within billions of text documents—the LLM can infer plausible causal links (“older age → higher heart disease risk”) even if those links are not evident from just \(k=4\) labeled rows. This prior knowledge acts as an auxiliary source that guides rule induction toward genuinely informative conditions while suppressing spurious ones—a capability demonstrated empirically by reduced performance degradation when noisy columns are attached.

## Evaluation Metrics for Tabular Classification  

When assessing how well a model solves a tabular prediction problem we need quantitative criteria that reflect both discriminative ability and practical considerations such as class imbalance.

### Accuracy  

The most straightforward measure is *accuracy*, defined as

\[
\text{Accuracy}= 
   \frac{\#\,(\text{correct predictions})}{N_{\text{test}}}
   = 
   \frac{\sum_{i=1}^{N_{\text{test}}}
          \mathbf{1}\!\bigl(\hat y^{(i)} = y^{(i)}\bigr)}
        {N_{\text{test}}}.
\]

While intuitively appealing, accuracy can be misleading when one class dominates because naïve predictors that always output the majority class achieve high scores without learning any meaningful pattern.

### Area Under the Receiver Operating Characteristic Curve (AUC‑ROC)

The **ROC curve** plots true positive rate (\(\operatorname{TPR}\)) against false positive rate (\(\operatorname{FPR}\)) while varying a decision threshold on predicted probabilities:

\[
\operatorname{TPR}(t)=
   \frac{\#\, (\text{positive } y^{(i)}~+~p(y^{(i)}=1|\mathbf{x}^{(i)})>t)}
        {\#\, (\text{positive } y^{(i)}}),
        \qquad
\operatorname{FPR}(t)=
   \frac{\#\, (\text{negative } y^{(i)}~+~p(y^{(i)}=1|\mathbf{x}^{(i)})>t)}
        {\#\, (\text{negative } y^{(i)}}).
}
\]

The **area under this curve**, abbreviated AUC or AUROC, summarizes overall discriminative power independent of any specific threshold:

\[
\text{AUC}= 
   \int_{0}^{1} \operatorname{TPR}(t)\,\mathrm d\, \operatorname{FPR}(t).
\]

Values range from 0 ½ (random guessing) up to 1 (a perfect ranker). Because AUC considers ranking rather than absolute probability calibration, it remains robust under severe class imbalance—exactly why all experimental tables in FeatLLM report average AUC across multiple random splits.

For multiclass problems FeatLLM computes AUC in a one‑vs‑rest fashion: each class is treated as positive while all others are negative; then macro‑averaging yields an overall score.

### Cross‑Entropy Loss During Training  

Although not strictly an evaluation metric—cross entropy serves as FeatLLM’s training objective—it also provides insight into how well calibrated predicted probabilities are relative to true labels:

\[
L_{\text{CE}} =
    -\,\frac1{|\,\mathcal D_{\text train}|}
       \sum_{(\mathbf{x},y)\in
            \mathcal D_{\text train}}
       \log p(y|\mathbf{x}),
\]

where \(p(y|\mathbf{x})=\mathrm {Softmax}({[\text {logit}_1,\dots , 
      \text {logit}_K]})_y.\)
A lower training loss generally correlates with higher AUC on held‐out data provided overfitting does not occur—a balance that is especially delicate when only \(k\) shots are available.

### Validation Strategies  

Given extremely limited labeled data per split, FeatLLM adopts **\(k_{\!FOLD}\)** cross validation on the tiny training set itself solely for early stopping: models trained over many epochs stop at the epoch where validation loss ceases improving across folds. This practice avoids overfitting while still exploiting all available labeled points during final inference after selection has been made.

## Summary  

Understanding tabular data begins with recognizing rows as observations described by named features whose types dictate how they can be processed linguistically by an LLM.  Prediction tasks split into classification—where discrete labels encourage probability modeling—and regression—where continuous outcomes call for direct value estimation.\  
Few\-shot learning formalizes situations where only \(k << N$ labeled points exist per class; such scarcity forces us to confront overfitting and spurious correlations unless we supplement data‐driven learning with external priors such as world knowledge embodied in large language models.\  
Finally, robust assessment relies on metrics like AUC–ROC that remain reliable under imbalance and provide meaningful comparisons across methods ranging from classical tree ensembles up through modern LLM–augmented pipelines like FeatLLM.\  
Armed with these foundations you will be ready to explore how FeatLLM marshals LLM reasoning into rule‐based feature generation—an approach that achieves strong few‑shot performance while dramatically reducing inference overhead compared with naïve end‑to‑end LLM usage.\
