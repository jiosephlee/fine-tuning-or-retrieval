\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How are multi‑class problems handled by FeatLLM’s rule generation?
Question:
The paper mentions generating rules "for each class" but most examples focus on binary classification. For a four‑class problem (e.g., sequence type classification), does FeatLLM generate separate rule sets per class independently, or are there shared rules across classes? How are overlapping conditions resolved when computing class logits?
Answer:
**Short answer:**  
In FeatLLM the rule‑generation step is *class‑wise*: for a problem with $c$ labels the LLM is asked to produce a fixed‑size list of rules (the paper uses ten) **separately for every label**. Each list is parsed into its own binary feature vector $\mathbf{z}^{i}_{k}\in\{0,1\}^{R}$ (where $R$ is the number of rules per class). At inference time the model computes a non‑negative linear logit for every class  

$$
\text{logit}^{i}_{k}= \bigl[\max(\mathbf{w}_{k},0)\bigr]\cdot \mathbf{z}^{i}_{k},
\qquad
\mathbf{p}^{i}= \operatorname*{\mathrm {Softmax}}\!\bigl([\text{logit}^{i}_{1},\,\dots,\,\text{
logit}^{i}_{c}]\bigr),
$$  

and the soft‑max automatically resolves any overlap: if a concrete condition appears in more than one rule list it contributes a ‘1’ to several $\mathbf{
z}^{i}_{k}$’s; the learned non‑negative weights $\mathbf{
w}_{k}$ decide how much that condition should push up each class’s logit,
and the soft‑max finally picks the most likely label.

Below is an expanded description that follows the paper’s pipeline and clarifies how multi‑class problems such as the four‑class *Sequence‑type* dataset are dealt with.

---

### 1. Rule generation is performed **per class**

Section 3.1 (“Prompt Design for Extracting Rules”) explains that the prompt contains a *response instruction* that explicitly asks the LLM to **list ten discriminative criteria for every possible answer**. The authors write:

> “we set a fixed number of rules (i.e., 10) to be extracted for **each class**.”

Consequently, when $c=4$ (arithmetic, geometric, Fibonacci, Collatz), the LLM returns four distinct sections, e.g.:

```
Class = arithmetic:
1) consecutive differences are equal
2) …
…
Class = geometric:
1) ratio of consecutive terms is constant
…
```

Each section is parsed independently – no single “global” rule list is created.

### 2. Parsing into binary features

Because the rule text is natural language, Section 3.2 (“Parsing rules for feature generation”) converts every textual rule into executable Python code with ``exec()``. The result of executing that code on a sample $\mathbf{x}^{i}$ is a **binary indicator** telling whether the sample satisfies the *k*-th rule belonging to *class* $k$. Stacking all indicators belonging to one label yields $\mathbf{
z}^{i}_{k}\in\{0,1\}^{R}$.

Thus every label has its own dedicated block of $R$ binary features; there is **no shared feature column** between labels unless two independently generated rules happen to be syntactically identical – in which case they will still occupy separate positions in two different $\mathbf{
z}$–vectors.

### 3. How overlapping conditions are handled

Overlap can happen in two ways:

1️⃣ **Identical textual rule appears in several lists** – e.g., “all terms are positive” may be useful for arithmetic **and** geometric sequences.  
2️⃣ **Different textual formulations capture essentially the same predicate** – e.g., “difference ≈ 0” vs “consecutive terms form an arithmetic progression”.

Both cases end up as separate binary entries because they belong to different $\mathbf{
z}_k$’s (or even different positions within the same vector). During training we learn a non‑negative weight vector $\mathbf{
w}_k$ for every label. Because we constrain $\mathbf{
w}_k\succeq0$ by applying ``max(w_k,0)`` before dot product (Equation 2), a satisfied rule can only increase its own label’s logit – it never directly penalises another label. If an overlapping rule fires for several classes, it adds a positive amount to all corresponding logits; whichever total becomes largest after weighting wins through the soft‑max denominator  

$$
p^{i}_k= 
    \frac{\exp(\text{
logit}^{\, i}_{
    k})}{%
    \sum_{j=1}^{c}
    \exp(\text{
logit}
^{\, i}_j)} .
$$  

In effect the model learns **how strongly an overlapping condition should favour each label** from the few‑shot examples. If “positive terms” tends to be more indicative of an arithmetic sequence than a Collatz one,
learning will give $\mathbf{
w_{\mathrm {arith}}}$ a larger entry on that rule than
$\mathbf{
w_{\mathrm {Collatz}}}$.

### 4. Ensemble / bagging does not change this principle

Section 3.2 (“Ensembling with bagging”) repeats the whole pipeline many times,
varying temperature and demo order so that different trials may propose slightly different rule sets.
Each trial produces its own set of per‑class binaries and its own weight vectors
$\{\mathbf{
w}[t]\}$;
final prediction averages the soft‑max probabilities over trials:

$$
\bar{\mathbf{
p}}^{\, i}= 
    \frac1T
    \sum_{t=1}^T 
    \operatorname*{\mathrm {Softmax}}
    \!\bigl([\,
    \text{
logit}
^{\, i}_{
        1}[t],
    …,
    \text{
logit}
^{\, i}_{
        c}[t]
    ]\bigr).
$$  

Because aggregation occurs **after** soft‑max,
any trial’s overlapping conditions are already resolved at the level of probabilities before averaging.



### 5. Experimental evidence

The authors evaluate FeatLLM on a genuine four‑class dataset (“Sequence‑type”) in Table 2/3 of
the paper and report performance comparable to conventional baselines—demonstrating that
the described procedure works unchanged for multi‑class settings without any extra engineering
or shared‐rule mechanism.



#### Takeaway

* **Separate rule sets:** FeatLLM indeed asks the LLM to emit an independent list of $R$
rules for *each* label.
* **Independent binary features:** After parsing,
every label owns its own block of binary variables;
overlap between blocks simply means multiple blocks receive a ‘1’ on some samples.
* **Resolution by learned weights + soft‐max:** Non‐negative linear weights quantify how much
each satisfied rule should boost its own label’s logit;
competing boosts are reconciled by soft‐max,
which produces normalized probabilities.
* **Ensembling keeps this structure:** Multiple stochastic generations are averaged at probability level;
they do not merge rule lists across classes.



Therefore, when you work with a four‐class problem such as sequence–
type classification you can expect FeatLLM to automatically generate four disjoint collections
of ten textual criteria each, turn them into eight hundred binary features ($4\times10$),
learn four weight vectors from your $k$–shot data,
and obtain final predictions through Equation (2). Overlapping conditions are handled naturally
by this linear–soft‐max pipeline rather than by any ad hoc conflict resolution step.
