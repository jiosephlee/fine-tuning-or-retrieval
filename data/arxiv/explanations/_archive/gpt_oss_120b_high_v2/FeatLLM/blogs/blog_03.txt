\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Turning Natural‑Language Rules into Machine‑Ready Features  

**How FeatLLM translates LLM‑generated textual rules into executable Python code, builds binary indicators for every record, and why this makes downstream models both simple and powerful.**  

---  

## The motivation: From “black‑box” predictions to “feature engineering”

Most recent methods that apply Large Language Models (LLMs) to tabular data feed every test sample through the LLM at inference time.  
While this can work, it is costly—each prediction requires a separate API call—and it quickly hits prompt‑size limits when tables have many columns.  

FeatLLM takes a different path. It asks the LLM **once** (or a handful of times) to **explain** what makes an example belong to each class. The output is a set of human‑readable “rules”, e.g.,  

> *If age > 60 **and** cholesterol > 200 then predict heart disease.*  

Once those rules are available we can treat them as **new features**: a binary flag tells us whether a given row satisfies each rule. A downstream model can then operate on this compact representation without ever calling the LLM again.  

---

## Step 1 – Prompting the LLM for textual rules  

The prompt is split into three logical blocks:

1. **Basic information** – task description, feature names/types, and a few labeled examples serialized as  
   ```
   f1 is <value>. … f_d is <value>. Answer: <label>
   ```  
2. **Reasoning instruction** – coaxing the model first to think about causal relationships between features and the target (using its world knowledge), then to derive concrete decision rules from the given examples.  
3. **Response instruction** – specifying an exact format for each rule (e.g., “IF <feature> > <threshold> THEN …”) so that later parsing is feasible.  

The prompt forces the model to output a *fixed* number of rules per class (10 in the paper) which balances informativeness against prompt length.  

---

## Step 2 – Turning natural language into executable code  

### Why parsing by hand is hard  

Even with strict response instructions, LLMs may vary their syntax:

* “>” may appear as “greater than”,  
* numeric literals may be spelled out (“one hundred”),  
* logical connectors can be written as “AND”, “and”, or even “&”.  

A handcrafted regex parser would quickly break on such variations.

### Using the LLM as a parser  

FeatLLM solves this by *re‑prompting* the same model with a **code‑generation request**:

```
You are given a list of decision rules:
1) Age greater than 60 AND Cholesterol > 200
2) ...
Write a Python function `check_rule(sample)` that returns 1 if the
sample satisfies the rule and 0 otherwise.
```

The request includes:

* The function signature (`def check_rule(sample):`),
* A description of `sample` (a dictionary mapping feature names → values),
* The list of rules extracted in Step 1.

The LLM returns ready‑to‑run Python code that explicitly compares feature values using ordinary operators (`>`, `<`, `==`, etc.). The returned string is fed to Python’s `exec()` function, which defines the function in the current runtime environment. This approach leverages the LLM’s own knowledge of programming syntax and makes it tolerant to linguistic variations in its own output.

---

## Step 3 – Generating binary features for every record  

For each class \(k\) we obtain a set of \(R\) rules \(\{r_{k,1},\dots,r_{k,R}\}\).  
Given a data point \(\mathbf{x}^i\), we evaluate every rule with the compiled functions:

\[
z_{k,r}^i = 
\begin{cases}
1 & \text{if } r_{k,r}\text{ is satisfied by }\mathbf{x}^i ,\\[4pt]
0 & \text{otherwise}.
\end{cases}
\]

Collecting all \(R\) outcomes yields a binary feature vector  
\(\mathbf{z}_k^i \in \{0,1\}^{R}\).  
Repeating this for all classes creates a concise representation that captures both **domain knowledge** (the rule logic) and **data‐driven insight** (the particular thresholds discovered from the few-shot examples).

---

## Step 4 – A tiny linear model does the heavy lifting  

With these engineered features in hand we only need a lightweight classifier. FeatLLM adopts a bias‑free linear model whose logit for class \(k\) is

\[
\text{logit}_k^{\,i}= \max(\mathbf{w}_{k},0)\cdot \mathbf{z}_{k}^{\,i},
\]

where \(\mathbf{w}_{k}\in\mathbb{R}^{R}\) are trainable non‑negative weights learned by minimizing cross‑entropy on the few labeled samples.  
The final class probabilities are obtained by softmax:

\[
\mathbf{p}^i = \operatorname{Softmax}\bigl([\text{logit}_1^{\,i},\dots,\text{logit}_c^{\,i}]\bigr).
\]

Because there are only \(c\times R\) parameters (often under one hundred), training converges within seconds even with just 4–8 labeled instances. Inference reduces to a handful of dot products—orders of magnitude faster than contacting an LLM per sample.

---

## Robustness tricks: Ensemble + bagging  

A single set of generated rules can still contain occasional noise or miss some informative patterns. FeatLLM mitigates this by:

* **Temperature sampling:** generating diverse rule sets across multiple runs,
* **Random demo ordering:** shuffling few-shot examples before each query,
* **Feature/instance bagging:** each trial sees only a random subset of columns or rows, which keeps prompts short enough for large tables,
* **Ensembling:** averaging softmax outputs from \(T\) independent trials (the paper uses \(T=20\)).  

This ensemble behaves like classic bagged decision stumps—weak learners compensate each other—while preserving FeatLLM’s low inference cost because all heavy lifting happens *once* per trial at training time.

---

## Why this step matters

| Aspect | Traditional end‑to‑end LLM inference | FeatLLM’s rule‑to‑feature pipeline |
|---|---|---|
| **API calls at test time** | One call per sample → high latency & cost | Zero calls after feature extraction |
| **Prompt length constraints** | Serialized rows quickly exceed token limits | Rules are generated once; bagging controls size |
| **Model complexity** | Large transformer needed for accurate predictions | Simple linear weights suffice |
| **Interpretability** | Hard to extract why a prediction was made | Each binary feature corresponds directly to an English rule |
| **Performance in few‑shot regime** | Often unstable or outperformed by classic models | Consistently improves AUC by ~10 % over TabLLM/STUNT |

Empirically, across 13 benchmarks ranging from classic UCI datasets (Adult, Credit-g) to newly released tables never seen during pretraining (Cultivars, NHANES), FeatLLM matches or exceeds strong baselines while requiring only 4–8 labeled points—equivalent performance that traditional methods need 32 shots to achieve.

---

## Takeaways

1️⃣ **LLMs excel at reasoning**, not at raw number crunching. By asking them *why* rather than *what*, we harvest high‑level decision logic that can be reused indefinitely.  

2️⃣ **Parsing those textual insights with another LLM call avoids brittle hand‑crafted parsers**, ensuring robustness against linguistic variation while keeping implementation simple (`exec()` on generated code).  

3️⃣ **Binary rule indicators transform any tabular dataset into an interpretable feature space**, enabling ultra‑lightweight downstream models that train in seconds and predict instantly.  

4️⃣ **Ensemble + bagging neutralizes occasional mistakes**, turning many weak “rule learners” into a strong collective predictor—mirroring classic ensemble theory but applied at the level of language–generated features.  

In short, FeatLLM shows how you can turn natural‐language explanations from an LLM into machine‐ready features, achieving state‑of‑the‑art few‑shot performance without sacrificing speed or interpretability. The approach bridges massive pretrained knowledge with decades­‑old linear modeling tricks—making advanced AI accessible even when data and compute budgets are tight.
