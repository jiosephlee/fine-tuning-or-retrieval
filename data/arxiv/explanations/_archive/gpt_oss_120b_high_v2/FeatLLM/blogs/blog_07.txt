\title{Blogs about the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

# Real‑World Impact: Using FeatLLM in Finance and Healthcare Without Massive Labels  

Large language models (LLMs) have become surprisingly good at reasoning about problems they have never seen before. The recent **FeatLLM** framework shows that we can turn this reasoning power into a practical feature‑engineering assistant for tabular data—especially when only a handful of labeled examples are available. Below we walk through how FeatLLM works and why it matters for two high‑impact domains: finance and healthcare.

## Why Feature Engineering Still Bottlenecks Tabular Learning  

Most real‑world predictive systems—credit‑risk scores, disease classifiers, churn detectors—rely on carefully crafted features. Traditionally this step demands domain experts or extensive trial‑and‑error with algorithms such as gradient boosting. In low‑shot settings (e.g., only a dozen annotated loan applications or patient records), standard models either overfit or simply cannot learn meaningful patterns.

Enter LLMs. Because they have been trained on massive corpora that include medical literature, financial regulations, and countless other sources of structured knowledge, an LLM already “knows” that **age**, **blood pressure**, or **debt‑to‑income ratio** are often predictive of health or credit outcomes. FeatLLM extracts exactly that knowledge as human‑readable rules and converts them into new binary features—without ever having to fine‑tune the LLM or send each test sample through it at inference time.

## A Bird’s‑Eye View of FeatLLM  

1. **Prompt the LLM with context**  
   - The prompt contains three parts:  
     *a.* A concise task description (e.g., “Predict whether a loan applicant will default”).  
     *b.* Natural‑language definitions of each column (“`age` is the applicant’s age in years”).  
     *c.* A few annotated examples serialized as “`age is 45 … Answer: No`”.  

2. **Two‑step reasoning**  
   - **Step 1:** The model draws on its prior knowledge to infer which columns are causally related to the target (“older applicants tend to default more”).  
   - **Step 2:** Using the few examples as anchors, the model formulates a fixed number of decision rules per class (the paper uses ten rules per class). An example rule might be “`age > 60 AND credit_score < 600`”.

3. **Parse rules into code**  
   - Even though the raw text can be noisy (“greater than” vs “>”), FeatLLM asks the same LLM to generate a short Python function that evaluates each rule on a row. The function is executed with `exec()` to produce **binary features** (`1` if a rule fires, `0` otherwise).

4. **Train a tiny downstream model**  
   - The binary feature vector \( \mathbf{z}_k \) for class \(k\) is fed into a non‑negative linear model:  
     \[
     \text{logit}_k = \max(\mathbf{w}_k ,0)\cdot \mathbf{z}_k ,\qquad 
     \mathbf{p} = \operatorname{softmax}([\text{logit}_1,\dots,\text{logit}_c]).
     \]  
   - Only a few gradient steps are needed because there are at most \(10\times c\) weights.

5. **Ensemble via bagging**  
   - The whole pipeline is repeated many times (the authors use \(T=20\) ensembles) with random subsets of features and shuffled example orders. Final predictions are obtained by averaging softmax outputs across ensembles—greatly reducing variance and handling datasets that exceed the LLM’s context window.

The result? A model that **requires only API access to an LLM**, runs inference without any additional LLM calls, and sidesteps prompt‑length limits through bagging.

## Finance – Building Credit Models with a Handful of Labels  

Imagine a regional bank launching a new micro‑loan product for gig workers. Collecting hundreds of labeled defaults would take months and cost thousands of dollars in manual review. Here’s how FeatLLM can cut that overhead:

| Step | What the bank does |
|------|-------------------|
| 1️⃣ | Write a short task description (“Will this applicant repay within 12 months?”) and provide plain English definitions for columns such as `monthly_income`, `job_type`, `loan_amount`. |
| 2️⃣ | Supply 4–8 labeled loan applications (e.g., two defaults, six repayments). |
| 3️⃣ | Call GPT‑3.5 (or any compatible LLM) once per ensemble run → obtain ten decision rules per class (“`job_type = rideshare AND monthly_income < 2500`”). |
| 4️⃣ | Let FeatLLM turn these rules into binary columns automatically. |
| 5️⃣ | Fit the tiny linear model on those binaries – usually finishes in seconds on a CPU. |
| 6️⃣ | Deploy the linear model in production; no further LLM calls are needed during daily scoring. |

### Why this matters  

* **Speed & cost:** The entire pipeline needs only ~30 API calls for an entire dataset (20 ensembles × 1 query per ensemble). That is trivial compared with running an LLM for every incoming application.  
* **Performance:** In benchmark experiments FeatLLM achieved *≈10 % higher AUC* than competing few‑shot methods such as TabLLM or STUNT, even when using just four labeled samples—roughly matching conventional models that need >30 samples.  
* **Scalability:** With bagging the method handled datasets having >100 attributes (e.g., the “Communities” crime dataset). A typical credit file rarely exceeds this size, so there’s no risk of hitting prompt limits.

## Healthcare – Risk Stratification When Data Are Scarce  

Clinical environments often face strict privacy constraints and limited annotated cases (think rare disease registries). FeatLLM can leverage medical knowledge baked into an LLM (“elderly patients have higher cardiovascular risk”, “high HbA1c indicates diabetes”) while respecting privacy:

1\. **Define the clinical question** – e.g., “Does this patient have chronic heart failure?”  
2\. **List each lab or vital sign with its unit** – e.g., `ejection_fraction` is % left ventricular ejection fraction; `creatinine` is mg/dL concentration.  
3\. **Provide 5–6 de‑identified cases** with outcomes (“Answer: Yes/No”).  
4\. **Run FeatLLM** → receives rules like “`age > 65 AND ejection_fraction < 40`”.  
5\. **Transform rules into binary features**, then fit the linear classifier on these high‑level indicators.

### Benefits for hospitals  

* **Rapid prototyping:** Clinicians can iterate over new phenotypes without waiting months for full chart abstraction pipelines.
* **Interpretability:** The extracted rules are human readable—a big advantage over black‑box trees or deep nets when explaining decisions to patients or regulators.
* **Robustness to noise:** Experiments adding irrelevant columns showed that FeatLLM’s performance dropped far less than baseline models because its reasoning step filters out spurious features early on.

## Empirical Highlights from the Paper  

* Tested on **13 diverse tabular datasets**, ranging from classic UCI benchmarks (`Adult`, `Heart`) to newly released ones (`Cultivars`, `NHANES`) and synthetic tasks (`Sequence-type`).  
* With just **4 shots**, FeatLLM matched conventional models trained on **32 shots**—an eightfold reduction in label demand.  
* Inference latency was comparable to logistic regression because only the lightweight linear model runs on production data; end‑to‑end LLM methods were *orders of magnitude slower*.  
* Ablation studies confirmed that every component—feature descriptions, two‑step reasoning, weight tuning, and ensembling—contributes positively; removing any one leads to measurable drops in AUC.

## How to Deploy FeatLLM Today  

Below is a checklist you can hand off to your data science team:

1️⃣ **Gather metadata** – column names + short plain English definitions (include type information).  
2️⃣ **Select a few labeled rows** – balance classes if possible (2–8 per class usually suffices).  
3️⃣ **Construct the prompt** – follow the three-part template described above; fix rule count at ten per class for consistency.  
4️⃣ **Call your chosen LLM API** – set temperature ≈ 0.5; repeat `T=20` times with shuffled examples for bagging.  
5️⃣ **Parse generated Python snippets** – let the same LLM produce executable code that evaluates each rule on your dataset rows.  
6️⃣ **Fit the non‑negative linear model** – use standard libraries (`scikit-learn`, `torch`) with cross‑entropy loss; early stopping via k‐fold CV helps avoid overfitting given low shot count.  
7️⃣ **Ensemble predictions** – average softmax outputs across all ensembles before thresholding for binary decisions or taking argmax for multi‑class tasks.  

All steps require only standard compute resources after Step 5; there is no need for GPU training of large models nor storage of massive checkpoints.

## Caveats & Future Directions  

* The current design focuses on *few‐shot* regimes; scaling up to thousands of labeled instances may require additional regularization or hybrid feature sets.
* Because all decisions originate from an LLM’s internal knowledge base, systemic biases present in pretraining data could surface in generated rules—a concern highlighted by the authors’ broader impact section.
* Extending rule generation beyond simple thresholding (e.g., weighted combinations or temporal patterns) could broaden applicability further.

Nevertheless, FeatLLM already demonstrates that *domain knowledge encoded in language models can replace costly manual feature engineering*, opening doors for rapid deployment of high‐performing tabular predictors in finance and healthcare where data labeling budgets are tight.
