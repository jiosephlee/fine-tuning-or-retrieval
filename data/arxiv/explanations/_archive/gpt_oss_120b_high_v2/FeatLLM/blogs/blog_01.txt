# Feature Engineering Meets GPT: Introducing FeatLLM

## Why Tabular Data Still Needs Better Few‑Shot Solutions  

Tabular datasets—think medical records, credit applications, or sensor logs—are everywhere in industry. Unlike images or text, they often contain a mix of numeric, categorical, and binary columns, each described by a human‑readable name and sometimes a definition. When we have only a handful of labeled rows (the **few‑shot** regime), traditional learners such as logistic regression or tree ensembles struggle to discover the right patterns without overfitting.

Large language models (LLMs) have shown an uncanny ability to solve new tasks by simply being shown a few examples in a prompt—so‑called **in‑context learning**. Prior work has tried feeding serialized tables directly into an LLM and letting it predict labels end‑to‑end (e.g., TabLLM, TABLET). While these methods can harness the world knowledge baked into models like GPT‑4 or GPT‑3.5, they suffer from two practical roadblocks:

1. **Per‑sample cost** – every test row needs a fresh call to the LLM, which is slow and expensive.
2. **Prompt length** – as the number of columns grows, serializing an entire table quickly exceeds the model’s context window.

**FeatLLM** flips this script: instead of using an LLM as a black‑box predictor, we ask it to act as an expert *feature engineer*. The idea is simple—let GPT generate human‑readable decision rules that capture the relationship between columns and target classes, turn those rules into binary features, and then feed those features into a tiny downstream model (often just a linear layer). Once the rules are extracted, no more LLM calls are needed at inference time.

## The FeatLLM Pipeline in Plain English  

Below is a step‑by‑step walk through what happens when you hand a new tabular task to FeatLLM.

### 1️⃣ Crafting the Prompt  

A single prompt is sent to the LLM that contains three parts:

| Part | What it contains | Why it matters |
|------|-------------------|----------------|
| **Basic information** | • Task description (“Does this patient have chronic heart failure?”)<br>• Feature names *and* optional definitions<br>• A handful of labeled examples serialized as “`f1 is … . f2 is … . Answer: …`” | Gives the model all context it needs without overwhelming it. |
| **Reasoning instruction** | • A “chain‑of‑thought” intro (“Let’s think step by step.”)<br>• **Step 1** – Infer causal relationships *without* looking at examples (e.g., “Older age increases heart disease risk”).<br>• **Step 2** – Using those relationships plus the examples, write explicit rules for each class. | Forces the LLM to draw on its prior knowledge first, then anchor its reasoning in the actual data—helps avoid spurious correlations when only a few rows are labeled. |
| **Response instruction** | • Exact JSON‑like format for each rule<br>• Guidance on how to express inequalities (“>``, `<=`”, etc.)<br>• Example output snippet | Guarantees that parsing later is straightforward despite natural language variability. |

The prompt deliberately asks for a *fixed* number of rules per class (10 in our experiments). This avoids having too many or too few features when data are scarce.

### 2️⃣ Extracting Rules  

The LLM replies with something akin to:

```
Class = Yes:
  Rule 1: age > 65 AND cholesterol > 200
  Rule 2: blood_pressure >= 140
  …
Class = No:
  Rule 1: age <= 45
  …
```

These are essentially “if‑then” criteria that encode expert knowledge plus what can be inferred from the few demonstrations provided.

### 3️⃣ Turning Rules into Binary Features  

Human readers could manually code these checks, but FeatLLM lets another short LLM pass do it automatically:

1. The extracted rule text is inserted into a second prompt that asks the model to emit valid Python code (`def rule_check(row): ...`).  
2. The generated code is executed locally via `exec()`.  
3. For every row in the original table we compute a binary vector  
   \[
   \mathbf{z}_k^i \in \{0,1\}^{R},
   \]  
   where \(R=10\) is the number of rules for class \(k\) and entry \(z_{k,j}^i\) equals 1 iff row \(i\) satisfies rule \(j\).

The result is a transformed dataset consisting solely of these binary “rule features”.

### 4️⃣ Learning How Much Each Rule Matters  

Even though many rules are sensible, some may be redundant or even noisy. FeatLLM learns their relative importance using an extremely lightweight model—typically a bias‑less linear layer applied separately per class:

\[
\text{logit}_k^i = \max(\mathbf{w}_k ,0)\;\cdot\;\mathbf{z}_k^i,\qquad 
\mathbf{p}^i = \operatorname{Softmax}\bigl([\text{logit}_1^i,\dots,\text{logit}_c^i]\bigr).
\]

Here \(\mathbf{w}_k\) are non‑negative trainable weights obtained by minimizing cross‑entropy on the few labeled rows (Adam optimizer at learning rate 0.01 for 200 epochs). The non‑negativity ensures that any generated rule can only increase—not decrease—the likelihood of its class.

### 5️⃣ Bagging & Ensembling for Robustness  

Two tricks keep FeatLLM reliable even when prompts become large or when random seeds affect rule generation:

* **Feature bagging** – each trial randomly selects a subset of columns before prompting the LLM. This reduces context length and encourages diverse rule sets.
* **Ensemble averaging** – we repeat steps 1–4 across \(T\) trials (20 in our default setup) using moderately high temperature (\(0.5\)) so that rule generation varies stochastically. Final class probabilities are simple averages of the individual trial predictions.

Bagging also acts as a defensive shield against spurious columns because any wrongly generated rule will appear in only a few ensemble members and thus carry little weight after averaging.

## What Makes FeatLLM Tick?  

### ✅ Zero Per‑Sample LLM Calls  
After the initial rule extraction stage (a handful of API requests), all predictions are made locally by evaluating binary conditions—a fraction of millisecond latency compared to costly API round‑trips.

### ✅ Works With API‑Only Models  
No fine‑tuning or custom checkpoints are required; you can plug in any chat model behind an HTTP endpoint (the paper uses `gpt-3.5-turbo-0613`). This opens up high‑performance LLMs that otherwise expose only inference APIs.

### ✅ Handles Wide Tables Gracefully  
By randomly dropping columns during each bagged trial we stay well within typical context windows (< 4 KB). Even datasets with > 100 attributes (e.g., *Communities*, *Myocardial*) remain tractable.

### ✅ Competitive Performance With Very Few Labels  

Across **13 diverse tabular benchmarks**, FeatLLM consistently lands at the top or second place among all competitors:

* On average it outperforms prior LLM methods (**TabLLM**, **STUNT**) by roughly **10 %** in AUC.
* With just **4 shots**, its accuracy rivals traditional learners that need **32 shots**.
* Ablation studies confirm every component matters—dropping reasoning prompts or feature descriptions hurts especially in ultra low‑shot settings (\(k \leq 4\)).

### 📊 Quality of Generated Features  

A sanity check measured each binary rule’s AUROC against ground truth before any weight tuning—most rules already exceed chance level (> 0.5). After training, irrelevant rules receive near‑zero weights automatically filtering them out without manual pruning.

## Peeking Under The Hood – How Much Do The Pieces Help?  

| Removed Component | Effect on Avg AUC |
|-------------------|-------------------|
| Weight tuning (`-Tuning`) | Small drop; bigger impact when more shots are available |
| Ensembling (`-Ensemble`) | Consistent degradation across all shot levels |
| Feature descriptions (`-Description`) | Noticeable loss when shots ≤ 8 |
| Reasoning step (`-Reasoning`) | Largest drop for ultra low‐shot (\(k=2\)) |

These numbers underscore two insights:

1. **Prior knowledge matters most when data are scarce** – giving GPT clear column definitions guides its rule generation.
2. **Learning rule importance becomes valuable once you have enough examples** – fine‐tuning weights provides extra lift in higher shot regimes.

## Speed & Cost Profile  

On an A100 GPU using the *Adult* dataset with only **16 labeled rows**, FeatLLM’s total runtime breaks down as follows:

| Phase | Approximate Time |
|------|-------------------|
| Rule generation & parsing (≈ 30 API calls) | < 5 seconds |
| Linear weight training (200 epochs) | ~ 0.4 seconds |
| Inference on test set | ~ 0.02 seconds |

By contrast, end‐to‐end LLM baselines suffer from multi‐second per‐sample latency because each test row triggers an additional request—even after batching they remain orders of magnitude slower than FeatLLM’s lightweight linear sweep.

## Limitations & Future Directions  

* **Scalability beyond few-shot** – FeatLLM shines when labels are extremely scarce; extending it reliably to larger training sets remains an open question.
* **Rule expressiveness** – Current implementation focuses on simple relational predicates (`>`, `<`, `=`). Richer transformations (e.g., monotonic functions or interaction terms) could capture subtler patterns.
* **Bias & Misinformation** – Since generated rules derive from an LLM’s world knowledge, any embedded societal biases may surface in rule form before ever seeing real data points; systematic auditing will be essential before deployment in high‐stakes domains like finance or healthcare.
* **Broader ensembles** – Bagging already mitigates context length issues; future work could blend FeatLLM’s rule features with conventional learned embeddings for hybrid models.

---

## Takeaway  

FeatLLM demonstrates that you don’t need to turn every prediction problem into an expensive chat with GPT. By prompting thoughtfully—first asking “what matters?” then “how do I articulate those matters?”—the language model becomes an automatic domain expert that writes down crisp decision rules. Those rules turn raw tables into tidy binary features that any lightweight classifier can consume instantly.

If you’re building ML pipelines where labeling budgets are tight but you have access to powerful chat APIs, give FeatLLM a spin: you’ll likely see higher accuracy out of far fewer labeled rows—and you’ll keep your inference costs down to essentially zero after that one time “feature engineering” chat session.
