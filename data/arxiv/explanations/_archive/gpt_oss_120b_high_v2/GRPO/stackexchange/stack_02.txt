\title{Stack Exchange of the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

### What techniques constitute “URL‑based deduplication and near‑deduplication” applied to Common Crawl?
Question:
The authors report reducing the original Common Crawl from billions of pages down to 40 B HTML pages using URL‑based deduplication and near‑deduplication, but they do not describe the exact method. Does this involve hashing URLs alone, comparing content fingerprints such as simhash/minhash, or using HTML structure similarity thresholds? Additionally, what percentage of pages were removed at each stage?
Answer:
**Answer**

The DeepSeekMath paper only says that it “employs URL‑based deduplication and near‑deduplication” in order to shrink the raw Common Crawl dump to $\approx$$\,40\,${billion} HTML pages before the fastText classifier is run. No further technical details—or any per‑stage statistics—are provided in the manuscript, so we cannot point to a concrete algorithmic configuration that the authors actually used.  

What *is* possible is to describe what “URL‑based deduplication” and “near‑deduplication” usually mean in large‑scale web‑crawling pipelines, and why those steps are typically inserted before any downstream filtering such as a language‑model classifier. This helps you understand what is likely happening under the hood even though the exact numbers remain unpublished.

---

### 1. “URL‑based” exact‑duplicate removal  

When a web crawler re–visits a site it often stores several copies of the same resource under slightly different URLs (e.g., `http://example.com/page`, `https://example.com/page`, `http://example.com/page?utm_source=twitter`).  
A typical URL deduplication stage therefore consists of three sub‑steps:

1. **Canonicalisation** – Normalise scheme/host case, drop default ports, sort query parameters alphabetically, strip known tracking parameters (`utm_*`, `fbclid`, etc.), and optionally remove fragments (`#…`).  
2. **Hashing** – Compute a fast hash (e.g., SHA‑1 or MurmurHash) of the canonicalised URL string. Identical hashes indicate *exact* duplicates.  
3. **Grouping & pruning** – Keep one representative copy for each hash and discard all others.

Because this operation works purely on the URL string it is extremely cheap (linear in the number of pages) and already eliminates a large fraction of redundancy—especially for highly trafficked domains such as news sites where identical articles are syndicated under many different URLs.

---

### 2. Near‑deduplication (content‑level similarity)

Exact‑URL matching does **not** catch copies that have been slightly edited (e.g., inserted ads, changed date stamps) or mirrored under completely different URLs. Near‑deduplication therefore works on some representation of the page’s **content**, which can be:

| Representation | Typical fingerprint | Distance metric |
|----------------|--------------------|-----------------|
| Raw text (after stripping HTML tags) | **SimHash** (64–256 bits) | Hamming distance $\le t$ |
| Token shingles (k‑grams) | **MinHash** signatures | Jaccard similarity $\ge \theta$ |
| Bag‑of‑words / TF–IDF vectors | Cosine similarity | $\ge \theta$ |
| Structured HTML tree | Hashes of tag sequences or CSS selectors | Edit distance on tree representation |

The overall workflow looks like this:

1. **Extract a canonical text payload** – Remove scripts/CSS/boilerplate, optionally keep only visible text (`<p>`, headings).  
2. **Compute a lightweight fingerprint** – SimHash is popular because it can be updated incrementally while reading a stream and supports fast Hamming‐distance look‐ups with locality‐sensitive hashing tables.  
3. **Index & compare** – Insert each fingerprint into an LSH index; for every new page retrieve existing fingerprints whose distance falls below a pre‑chosen threshold (commonly $t=3\text{--}5$ bits for a $64$-bit SimHash).  
4. **Cluster & retain** – Pages that fall into the same bucket are considered *near duplicates*. Often one keeps the highest‑quality version according to heuristics such as longer textual length, higher crawl timestamp freshness, or lower ratio of boilerplate.

Some pipelines also augment pure text fingerprints with **HTML‐structure fingerprints** (e.g., hash of the DOM tree’s tag sequence). This catches cases where two pages contain very similar text but different layout templates—useful when you want to preserve distinct formatting for tables or formulas that may be lost after plain‐text extraction).

---

### 3\. Why this matters for DeepSeekMath

The downstream fastText classifier needs a *reasonable* amount of data to score quickly—processing billions of raw HTML files would be prohibitively slow both in I/O and tokenisation time. Removing exact duplicates first eliminates obvious waste without any risk of losing information. Near‐duplicate pruning then removes highly overlapping mathematics webpages (e.g., mirrored lecture notes across university subdomains), which both reduces storage cost and curtails over‐representation of certain topics that could bias the classifier’s recall.

Because DeepSeekMath ultimately keeps only **the top–scoring** pages from the fastText model (they later rank by predicted math relevance), having a cleaner base set means those top scores are spread over a *broader* set of domains rather than being concentrated on dozens of duplicated copies.

---

### 4\. What percentage of pages were removed?

The authors state only two numbers:

* **Input size:** “billions of pages” from an unfiltered Common Crawl dump (the official WARC archive for a single month typically contains $\approx$$\,150\,${billion} raw URLs).  
* **Output size:** “40 billion HTML web pages” after both stages.

From those two figures we can infer an overall reduction factor somewhere between $\approx$$\,25\,\%$$\,${(if the original count were $\approx$$\,160\,${B})} and $\approx$$\,60\,\%$$\,${(if it were $\approx$$\,100\,${B})}. The paper does *not* break down how much was cut by exact URL de‐duplication versus how much came from near‐duplicate pruning, nor does it provide intermediate counts such as “X % removed by URL hashing → Y % remaining”.

Therefore any precise percentages—e.g., “$\approx$$\,35\,\%$$ eliminated by URL hash alone and another $\approx$$\,20\,\%$$ removed by SimHash”—would be speculation beyond what is disclosed in the manuscript.

---

### 5\. Bottom line

* The DeepSeekMath corpus construction pipeline uses two standard stages:  
&nbsp;&nbsp;1️⃣ **Exact duplicate removal** based on canonicalised URL hashing.  
&nbsp;&nbsp;2️⃣ **Near‐duplicate removal** based on lightweight content fingerprints (most commonly SimHash or MinHash) possibly combined with simple HTML structure checks.
* The authors do not publish their concrete hash functions, distance thresholds, or how they weight HTML vs plain text.
* No per‐stage statistics are given; only the final size (“40 B HTML pages”) is reported, so any exact percentage breakdown is unavailable from the paper itself.
If you need those fine‐grained details for reproducing the pipeline, you would have to contact the authors directly or wait for an accompanying code release—both are common practice for large web‐crawling projects where multiple heuristic choices can dramatically affect duplication rates.​
