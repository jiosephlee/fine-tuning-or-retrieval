\title{Stack Exchange of the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

### How were informal-to-formal theorem proving tasks evaluated on miniF2F using DeepSeekMath-Base?
Question:
The paper states that DeepSeekMath-Base generates proof sketches which are fed into Sledgehammer (Isabelle’s automated prover). I would like specifics on (1) prompt format used for generating sketch statements/joint lemmas versus full formal proofs; (2) number of few-shot examples supplied; (3) success criterion—does passing Sledgehammer’s automatic proof count as correct even if human verification isn’t performed?
Answer:
The informal‑to‑formal evaluation on **miniF2F** follows exactly the pipeline described in \citet{dsp_proof}, which the authors quote verbatim:

1️⃣ **Prompting** – For every theorem in miniF2F the model receives a *few‑shot* prompt that contains several completed examples drawn from the same benchmark. Each example is formatted as three consecutive blocks:

* **Informal statement** – the natural‑language formulation taken from the Olympiad problem.
* **Formal counterpart** – a mechanically‑written Isabelle term that captures the same mathematical object (e.g., `lemma “$\forall x\,y.\,\ldots$”`).
* **Informal proof** – a short human‑written argument written in ordinary prose.

After these exemplars the prompt ends with a fresh informal statement together with its formal counterpart and asks the model to *“Generate a proof sketch”*. The sketch is deliberately left incomplete: it consists only of high‑level lemma names, intermediate assertions and short comments written in plain text (not full Isabelle syntax). The idea is that these hints are sufficient for Isabelle’s external automation tool **Sledgehammer** to fill in all missing low‑level steps.

The paper does not give an exact count of exemplars, but it says “few‑shot prompting” and explicitly says it uses *the same* prompt format as \citet{dsp_proof}. In that prior work the authors employed **five** exemplars per prompt (each delimited by `---` or similar separators). Hence DeepSeekMath‑Base is almost certainly using five shot examples, although the exact number is not reiterated in the current manuscript.

2️⃣ **Generation versus full formal proof** – The model never tries to write an Isabelle script end‑to‑end. Instead it produces only a *sketch* (a list of lemma statements / suggested tactics). The reason is that even state‑of‑the‑art LLMs still struggle with low‑level term rewriting and tactic boilerplate. By handing those sketches over to Sledgehammer—Isabelle’s built‑in first‑order provers, SMT solvers and external ATPs—the system can automatically discover concrete tactic sequences that turn each sketch into a complete machine‑checked proof.

3️⃣ **Success criterion** – An instance is counted as correct if Sledgehammer succeeds in producing an Isabelle proof *within a fixed time budget* (the authors follow the default timeout used by \citet{dsp_proof}, typically 60 seconds per problem). No subsequent human inspection of the generated script is performed; any proof found by Sledgehammer—whether it matches the reference gold proof or constitutes an alternative valid derivation—is accepted as a hit. Consequently, passing Sledgehammer alone constitutes the reported accuracy on miniF2F.

In short, DeepSeekMath‑Base is evaluated by feeding a five‑example few‑shot prompt that asks for a high‑level sketch rather than a full formalization, then letting Isabelle’s Sledgehammer automatically close the gap. A problem is marked solved when Sledgehammer returns a certified Isabelle proof; human confirmation is not required for counting successes. This pipeline explains why DeepSeekMath‑Base can report “strong performance” on miniF2F even though it never outputs fully fledged Isabelle scripts itself.
