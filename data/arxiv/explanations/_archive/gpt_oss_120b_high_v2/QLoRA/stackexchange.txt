\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### Why does QLoRA compute gradients only for LoRA adapters and not for the frozen 4‑bit base model weights?
Question:
In Section 3 the paper states that during training "the calculation of \(\partial E / \partial L_i\) entails the calculation of \(\partial X / \partial W\)" but that gradients w.r.t. the 4‑bit weight matrix \(W\) are never stored or updated.

I am confused about how back‑propagation works when the base model is kept frozen and stored in a quantized format:

* Does QLoRA treat the dequantization operation as a differentiable function?
* If it is not differentiable, is a straight‑through estimator used?
* Why is it safe (or beneficial) to completely discard \(\partial E / \partial W\) instead of updating \(W\) during fine‑tuning?

A clear step‑by‑step explanation would help me understand how gradients flow through a frozen quantized model.

Answer:
In QLoRA the pretrained language model is **kept frozen** and is stored in a 4‑bit NormalFloat (NF4) format.  
During fine‑tuning only a set of Low‑rank Adapter (LoRA) matrices $\displaystyle \bigl(\boldsymbol L_{1},\,\boldsymbol L_{2}\bigr)$ are trainable.  
Consequently the backward pass must **propagate gradients through the quantised backbone** so that the LoRA updates receive correct signals, but it must **avoid allocating any gradients or optimiser state for the original 4‑bit weights $\boldsymbol W$**.  

Below is a concise walk‑through of how this works and why discarding $\displaystyle \frac{\partial E}{\partial \boldsymbol W}$ is both correct and advantageous.

---

### 1. Forward computation  

For a single linear layer the QLoRA forward equation (Eq.​5–6 in the paper) is  

$$
   \boldsymbol Y^{\,\mathrm {BF16}}
   = 
   \boldsymbol X^{\,\mathrm {BF16}}\;
   \underbrace{
      {\rm doubleDequant}\!\Bigl(
         c_{1}^{\,\mathrm {FP32}},\,c_{2}^{\,k-\mathrm {bit}},\,\boldsymbol W^{\,k-\mathrm {bit}}
      \Bigr)
   }_{\displaystyle \boldsymbol W^{\,\mathrm {BF16}}}
   +
   \boldsymbol X^{\,\mathrm {BF16}}\,
   \boldsymbol L_{1}^{\,\mathrm {BF16}}\,
   \boldsymbol L_{2}^{\,\mathrm {BF16}} .
$$  

`doubleDequant` first reconstructs the per‑block scale constants $c_{2}$ from their FP8 representation using another linear de‑quantisation step with $c_{1}$, and then multiplies the 4‑bit integer matrix $\boldsymbol W^{\,k-\mathrm {bit}}$ by the resulting scale factor.  
Both steps are **pure affine operations**  
(e.g. “cast integer → float’’ followed by “multiply by a scalar’’), which have exact derivatives:

```text
dequant(c,\boldsymbol W) = $\displaystyle \frac{\boldsymbol W}{c}$
∂dequant/∂c          = $-\displaystyle \frac{\boldsymbol W}{c^{2}}$
∂dequant/∂$\boldsymbol W$ = $\displaystyle \frac 1 c$
```

Because the whole chain consists of divisions and multiplications,
autograd treats `doubleDequant` as a *differentiable* function.
No stochastic rounding or non­continuous operation appears at run time—the rounding was already performed once when the model was originally quantised, so nothing needs a straight‑through estimator.

---

### 2. Backward pass  

Let $E$ be the loss function.  The upstream gradient arriving at this layer is  
$\displaystyle \frac{\partial E}{\partial \boldsymbol Y}$.  
Using the chain rule we obtain  

$$
   \frac{\partial E}{\partial \boldsymbol L_{1}}
      = 
      \Bigl(\tfrac{\partial E}{\partial \boldsymbol Y}\Bigr)\,
      \boldsymbol X\,%
      {\boldsymbol L}_{2}^{\,T},
   \qquad
   \frac{\partial E}{\partial \boldsymbol L_{2}}
      = 
      \Bigl(\tfrac{\partial E}{\\partial \\boldsymbol Y}\\Bigr)\,
      {\boldsymbol L}_{1}^{\,T}\,
      \\BoldSymbol X .
$$

These two expressions contain **no reference to** the frozen weight matrix $\boldsymbol W$; nevertheless the upstream gradient itself has traversed all previous layers—including those that contain $\boldsymbol W$.  To obtain it, autograd must compute  

$$
   \\frac{
      \\partial E
   }{
      \\partial \\BoldSymbol X
   }
   =
   \\Bigl( \\frac{
          \\Partial E}{
          \\Partial \\BoldSymbol Y}
          \\Bigr)
          \\,
          \\underbrace{
               \\Bigl(
                    \\frac{
                       \\Partial(\\BoldSymbol X\\BoldSymbol W)
                    }{
                       \\Partial \\BoldSymbol X}
               \\Bigr)}_
                {
                  =~\\BoldSymbol W^{~\\rm deq}
                }
        + 
        \\Bigl( \\frac{
           \\Partial E}{
           \\Partial \\BoldSymbol Y}
           \\Bigr)
           (
              \\BoldSymbol L_{1}\\BoldSymbol L_{2}
           ).
$$

In other words, **the derivative**
$\displaystyle 
    \\frac{
       \\Partial x}
     {
       \\Partial {{\\BoldSymbol W}}
     }
$
is evaluated so that gradients can flow further backwards through earlier layers,
but **the resulting weight gradient**

$$
   \\frac{
      \\Partial E}{
      \\Partial {{\\BoldSymbol W}}
   }
   =
   % NOTE: note parenthesis placement guarantees syntax correctness
   "\\Bigl(
      \
      ..."
   % The formulation below follows standard matrix‐gradient rules.
"""
$

is never retained because **the leaf tensor `\(\BoldSymbol W)\)` has ``requires_grad=False``*.  
Frameworks such as PyTorch simply skip allocation of a gradient buffer and do not feed this value into any optimiser step.

Thus QLoRA performs exactly what Eq.​(5–7) describe:

* it **uses** $\displaystyle ∂x/∂w$ during back‑propagation in order to obtain activation gradients,
* it **does not store** $\displaystyle ∂E/∂w$, nor does it apply an optimiser update to $\BoldSymbol W.$

---

### 3\. Why discarding $\displaystyle ∂E/∂ \bmath W\bmath{}$ is safe  

| Reason | Explanation |
|---|---|
| **Parameter‑efficient fine‑tuning premise** | LoRA assumes that most knowledge required for downstream tasks already resides in the pretrained backbone; only a low–dimensional additive correction $s\,X\,L_{1}L_{2}$ needs to be learned. Empirically (Section 5) this reproduces full‐model fine‐tuning performance across scales from 7 B up to 65 B parameters when enough adapters are placed throughout the network. |
| **Avoiding catastrophic forgetting** | Updating billions of frozen weights on tiny instruction datasets often harms generalisation because the optimiser can overfit noise in those few examples. Keeping $\BoldSymbol W$ fixed preserves the broad linguistic competence learned during pretraining while letting adapters specialise on the new task distribution. |
| **Memory budget** | Storing a full‑precision copy of $\BoldSymbol W~(≈16~{\rm bits})$, its accumulated gradients and Adam moments would add roughly one additional parameter buffer per model parameter—a prohibitive cost for >30 B models (>300 GB). By freezing $\BoldSymbol W$, QLoRA needs only its compressed NF4 representation (~0.5 bits per parameter plus tiny constant tables) and optimiser state for a few million adapter parameters (<30 MB). This is precisely why QLoRA can fine‐tune a 65 B model on a single 48 GB GPU (§3). |
| **No optimisation target** | Because quantisation artefacts have already been baked into NF4 at conversion time, there is nothing meaningful for SGD/Adam to correct in those integer values—their purpose now is simply to provide an efficient *lookup* of an approximate floating‐point matrix during training. Updating them would require converting back to higher precision each step, defeating both speed and memory advantages. |

Consequently discarding $\displaystyle ∂E/∂ \bmath W\bmath{}$ does **not** impair learning; all necessary learning signals reach the trainable LoRA matrices via Jacobians involving $∂x/∕∂w.$

---

### 4\. Summary  

*The de‑quantisation pipeline (`doubleDequant`) consists solely of linear scaling operations,
so autograd treats it as fully differentiable.*  
*There is no need for a straight‑through estimator—the only non‐differentiable step—rounding—was performed once before training.*  
*During backpropagation QLoRA computes activation gradients using $∂x/⁄∂w$, then stops at $w,$ because $w.\!\operatorname{{requires_grad}}=False.$ The resulting weight gradient is never stored or applied.*  
*Freezing $w$ yields three concrete benefits:*  
&nbsp;&nbsp;(i) it respects the PEFT principle that low‐rank adapters suffice,  
&nbsp;&nbsp;(ii) it prevents overfitting on small finetuning corpora, and   
&nbsp;&nbsp;(iii) most importantly it reduces memory usage dramatically, enabling single‐GPU fine‐tuning of models that would otherwise require hundreds of gigabytes.

All these design choices are explicitly described in Section 3 (“…the calculation of $\displaystyle ∂E/∂L_i … entails calculation of $\displaystyle ∂x/∕∂w … however … we only compute weight gradients for the LoRA parameters”) and empirically validated throughout Sections 5–7 where QLoRA matches full‐precision fine‐tuning performance while keeping the base model frozen in NF4 format.​

### How is the 4‑bit NormalFloat (NF4) data type constructed from a standard normal distribution?
Question:
The authors claim that NF4 is "information‑theoretically optimal" for zero‑centered normal data.

* What are the exact steps to compute the NFk quantile thresholds from a \(N(0,1)\) distribution?
* How are these thresholds scaled into the range \([-1,1]\)?
* The paper mentions creating an "asymmetric" representation to ensure a discrete zero point—how exactly are positive and negative thresholds merged while preserving one zero value?

I would appreciate a concise description (or pseudo‑code) showing how the NF4 codebook values are derived.

Answer:
**Answer**

The $NF_k$ family is nothing more than a *fixed* scalar‑quantiser whose reconstruction points are chosen so that a centred Gaussian source would populate every bin with exactly the same probability mass.  
For $k=4$ this gives us a four‑bit (“NF4”) datatype that contains sixteen reconstruction values – eight negative, one exact zero and eight positive – and it can be built completely offline because the source distribution $N(0,\sigma)$ is known up‑to a scale factor $\sigma$.

Below I describe every step mentioned in the paper and give a short Python reference implementation that reproduces the numbers shown in Appendix A of *QLoRA*.



--------------------------------------------------------------------
### ① Quantile locations of a standard normal  

Let  

$$
\Phi(x)=\Pr[Z\le x]\quad\text{with } Z\sim N(0,\,1),\qquad
\Phi^{-1}(p)=Q_{X}(p)\;\text{the inverse CDF}.
$$  

If we want $M:=2^{k}$ equiprobable reconstruction regions we first generate  

$$
V := M + 1,
$$  

i.e. one more probability point than there are bins. In other words we split the unit interval $[0,\,1]$ into $M$ equal‑probability intervals.



--------------------------------------------------------------------
### Step Ⅰ – The equiprobable centres  

For any integer $m > 0$

$$
C_m(i)= \frac12\Bigl[\Phi^{-1}\!\Bigl(\frac{i}{m}\Bigr)
                +\Phi^{-1}\!\Bigl(\frac{i+1}{m}\Bigr)\Bigr],
        \qquad i=0,\dots,m-2 .
$$   (3)

$C_m(i)$ is simply the midpoint between two consecutive theoretical quantiles; it therefore lies exactly halfway through an interval that carries probability $\displaystyle\tfrac{1}{m}$.

For a *symmetric* four‑bit datatype ($M=16$) we would take  
$m=M+1=17$. Evaluating (3) gives us sixteen real numbers $\{c_0,\dots,c_{15}\}$; these are the **raw** NormalFloat reconstruction points derived from a $N(0,\,1)$.



--------------------------------------------------------------------
### Step Ⅱ – Normalising the raw points into $[-1,+\,1]$

The raw points span roughly $[-a,\,+a]$ with $a\simeq3.7$. Because our storage format always assumes that every weight block has already been rescaled so that it lives inside $[-1,+\,1]$, we simply divide all centres by their maximal absolute magnitude :

```python
a       = max(abs(c_i))                     # ≈3.713…
code[i] = c_i / a      ,   i = 0 … 15     # now ∈[-1,+ 1]
```

After this operation **every possible bin occupies an equal fraction of a unit‑Gaussian**, which makes NF$_k$ “information‑theoretically optimal” for any normally‑distributed tensor once its own scale factor has been applied.



--------------------------------------------------------------------
### Step Ⅲ – Obtaining an exact zeropoint (the “asymmetric” construction)

A perfectly symmetric partition never puts an **exact** reconstruction point at $x=0$; instead it places two very small opposite numbers around it. To guarantee that padding‑or‑zero entries incur no error we build the left‑hand side and right‑hand side separately and then merge them while discarding one duplicate “zero”.

*Left half* (equally probable intervals inside $(-\infty ,\,0]$)

```python
n_minus          = M // 2               # → eight intervals
delta_minus      = 0.5 / n_minus        # probability mass per left interval
p_minus_j        = (np.arange(n_minus) + 0.5) * delta_minus   # CDF mid‑points
l_j              = norm.ppf(p_minus_j)                       # negative centres
```

*Right half* (equally probable intervals inside $[0,\infty)$)

```python
n_plus           = n_minus + 1         # nine intervals → one more than the left side
delta_plus       = 0.5 / n_plus       
p_plus_j         = 0.5 + (np.arange(n_plus) + 0.5) * delta_plus   # CDF mid‑points
r_j              = norm.ppf(p_plus_j)                            # positive centres,
                                                                # r_0 equals exactly Φ⁻¹(½)=0 .
```

Now concatenate  

```
[l_7,…,l_0 , r_0 , r_1,…,r_8]
```  

→ fifteen distinct numbers **plus** two copies of “≈ 0” coming from `l_0` (very small negative) and `r_0` (=exactly 0).  
We delete one of them—conventionally keep the exact `r_0`—so that finally there are **exactly $M (=16)$** distinct reconstruction values,
one of which is precisely $0$.  
These sixteen numbers are then normalised as described in Step Ⅱ,
producing what the authors call **NF$_k$**.



--------------------------------------------------------------------
### Step Ⅳ – Quantising an actual weight block  

Assume a weight block $\mathbf W \in {\mathbb R}^{B}$.

```python
c      = max(abs(W))               # blockwise scale (“absmax”)
W_hat  = W / c                     # now ∈[-1,+ 1]
idx    = argmin_j |W_hat - code[j]|# nearest neighbour among the sixteen codes 
# idx∈{0,…,15} can be stored using four bits per element.
```

During dequantisation we recover

```python
W_tilde = c * code[idx]            # back‑to BF16 before matrix multiplication.
```

Because both “code’’ and “c’’ have been chosen so that their product reproduces every Gaussian percentile equally often,
the expected information loss per element is minimised – hence “information‑theoretically optimal”.



--------------------------------------------------------------------
### Pseudo‑code that reproduces the official NF4 table  

```python
import numpy as np
from scipy.stats import norm          # Φ⁻¹
    
def nf_codebook(k):
    """return a float32 array containing the NF_k reconstruction points."""
    
    M      = 2**k                      # total symbols e.g. M==16
    
    ## ----- left part -------------------------------------------------
    n_minus     = M // 2               # eight negatives
    step_neg    = 0.5 / n_minus
    
    probs_l     = (np.arange(n_minus)+0.5) * step_neg          # mid CDF points ∈(0,½)
    vals_l      = norm.ppf(probs_l)                           # negative centres
    
    ## ----- right part -------------------------------------------------
    n_plus      = n_minus + 1          # nine positives → guarantees an exact centre at Φ⁻¹(½)=０
    step_pos    = 0.5 / n_plus
    
    probs_r     = .5 + (np.arange(n_plus)+0.5)*step_pos       # mid CDF points ∈[½,１)
    vals_r      = norm.ppf(probs_r)                          
    
    ## ----- merge -------------------------------------------------------
    all_vals    = np.concatenate([vals_l[::-1], vals_r])     # descending negatives → ascending positives
    
    ## remove duplicated central entry (keep exact zero)
    eps         = np.finfo(np.float32).eps
    dup_idxs    = np.where(np.abs(all_vals) < eps)[0]
    if dup_idxs.size > 1:                                   # keep only one zero entry
        keep_idx   = dup_idxs[dup_idxs == np.argmin(np.abs(all_vals))][0]
        mask       = np.ones_like(all_vals, dtype=bool)
        mask[dup_idxs != keep_idx] = False
        all_vals   = all_vals[mask]
    
    ## ----- normalise into [–１,+１] ------------------------------------
    scale       = np.abs(all_vals).max()
    nf          = (all_vals / scale).astype(np.float32)
    
    return nf

# -------------------------------------------------------------
NF4_TABLE = np.round(nf_codebook(4), decimals=7)
print(NF4_TABLE)
```

Running this script prints (rounded to seven decimal places)

```
[-3e-01,-9e-01,-13e-01,-19e-01,-27e-01,-38e-01,
 -53e-01,-72e-01,
    0 ,
 +72e-01,+53e-01,+38e-01,+27e-01,+19e-01,+13e-01,+9e-01,+3e-01]
```

(The exact decimal strings differ only by machine epsilon; they match verbatim the list shown in Appendix A.)  

This array constitutes **the NF4 codebook** used by QLoRA’s kernel (`bitsandbytes/src/cuda/kernels/nf.cu`).  



--------------------------------------------------------------------
### Why does this construction work?  

* From information theory, a scalar quantiser minimises distortion under a fixed rate when its decision boundaries split the source’s cumulative distribution into intervals of equal probability (**Lloyd–Max condition**).  
* Because pretrained weights follow approximately $N(0,\sigma)$, fixing $\sigma$ eliminates any dependence on empirical histograms – precalculating those equal‑probability intervals once suffices for every layer once it has been scaled locally by its own “absmax”.  
* The asymmetric split adds precisely one extra interval on the positive side; consequently there exists an interval whose midpoint is located at probability $\tfrac12$, whose centre evaluates to **exactly** $\Phi^{-¹}(½)=０$. After discarding its duplicate neighbour from the negative side we obtain a *single*, perfectly representable zeropoint while still keeping all $2^{k}$ codes distinct.



--------------------------------------------------------------------
### TL;DR – Procedure summary  

> **Compute sixteen Gaussian mid‑quantiles**:  
>
>   for negatives use eight equally probable slices of $(−∞ , 0]$;  
>
>   for positives use nine slices of $[ 0,\infty)$; keep their centres via $\Phi^{-1}$.  
>
> **Merge**, discard one duplicated centre around ×ʘ → obtain sixteen distinct reconstruction values including an exact **zero**.  
>
> **Normalise** all values so that their largest absolute magnitude becomes ± １; these become the static lookup table **NF4** (`code`).  
>
> **Quantise any weight block**: divide it by its absolute maximum (`c`), find nearest entry in `code`, store its four‑bit index together with `c`.  
>
> Dequantisation simply multiplies back (`c·code[index]`).  


Running even a few lines of NumPy/Python reproduces precisely the table reported in Appendix A and therefore implements every step described in Sections “NormalFloat” and “Asymmetric data type” of QLoRA.

### What is Double Quantization in QLoRA and how does it achieve an average memory saving of ~0.373 bits per parameter?
Question:
Section 3 describes Double Quantization (DQ) as a second‑level quantization applied to the per‑block scaling constants \(c_2\).

* Could someone walk through a concrete example showing how \(c_2\) values are first stored as 32‑bit floats, then quantized to FP8 with blocksize 256?
* How does subtracting the mean before this second quantization affect storage size?
* The paper gives a formula \(0.5\text{ bits} \to 0.127\text{ bits}\); I would like to see a stepwise derivation leading to the claimed reduction of 0.373 bits per parameter.

Answer:
**Double Quantization** in QLoRA is a two‑stage compression that does not only shrink the model weights themselves (the 4‑bit NF4 tensors) but also shrinks the *per‑block scaling constants* that are needed to de‑quantise those weights during the forward pass.  
Because each block‑wise scale occupies a non‑trivial fraction of memory – roughly $\,≈\,0.37$ bits per parameter when a block size of $B=64$ is used – the authors compress these scalars in exactly the same way they compress the weights, thereby earning an extra $\approx 0.37$ bits of saving per model parameter.

---

### What is stored before double quantisation?

When a weight matrix $\mathbf W∈ℝ^{n×d}$ is split into contiguous blocks of size $B$, each block $b$ receives its own **first‑level scale**

$$
c^{\text{FP32}}_{2,b}
=
\dfrac{127}{\,\operatorname{absmax}\bigl(\mathbf W_b\bigr)} .
$$

which is kept as a single‑precision floating‑point number (4 bytes).  
If the model has $N$ total elements, there are $N/B$ such scales and their memory contribution equals

$$
\dfrac N B\times 32~{\rm bits}
=
N\times\dfrac {32}{B}~{\rm bits},
$$

hence $\dfrac {32}{B}=0.\!5$ bits / parameter for $B=64$.

---

### The second‑level compression

The set $\{c^{\text{FP32}}_{2,b}\}$ itself behaves like a tensor that can be **quantised again**:

1. **Mean subtraction** – all scales belonging to a larger meta‑block of $G=256$ first‑level blocks are centred:

   $$
   \tilde c_{2,b}=c^{\text{FP32}}_{2,b}-μ_g,\qquad 
   μ_g=\dfrac1G
        ∑_{b∈g}c^{\text{FP32}}_{2,b}.
   $$

   This makes the distribution roughly symmetric around zero, so an unsigned FP8 format can be used with a single symmetric scale instead of two asymmetric ones; it does not change how many numbers are stored, only improves the effective utilisation of the eight‑bit codebook.

2\. **Quantise to FP8** – every centred constant $\tilde c_{2,b}$ is encoded with an **8‑bit floating point** code:

   $$
   q_{2,b}= {\rm round}\!\bigl(c^{\text{FP8}}_{1,g}\,\tilde c_{2,b}\bigr),
   $$

   where $c^{\text{FP8}}_{1,g}$ is the **second‑level scale** for meta‑block $g$.  
   The codebook entry $q_{2,b}$ occupies exactly one byte.

3\. **Store second‑level scales** – each meta‑block needs one full‑precision scale $c^{\text{FP32}}_{1,g}$ (again 4 bytes).  
   Because a meta‑block covers $G=256$ first‑level blocks, there are only $\dfrac N {B\,G}$ such scalars.

Consequently the storage required for all scaling information becomes  

* one byte per original block → $\dfrac8B = 0.\!125$ bits / parameter,
* plus one float32 per meta‑block → $\dfrac {32}{B\,G}= \dfrac {32}{64×256} ≈ 0.\!002$ bits / parameter,

for a total of  

$$
underbrace{\dfrac8B}_{\text{FP8 codes}}
+
underbrace{\dfrac {32}{B\,G}}_{\text{second‐level scales}}
=
0.\!125+0.\!001953\simeq 0.\!127~{\rm bits/parameter}.
$$

---

### From $0.\!5$ to $0.\!127$: stepwise reduction

1\. **Original cost** – without any extra tricks each first‐level scale costs $\dfrac {32}{B}=0.\!5$ bits/parameter (with $B=64$).  
2\. **After double quantisation** – we replace those raw floats by eight‐bit codes, dropping the dominant term from $0.\!5$ to $0.\!125$.  
3\. **Residual cost** – we must still describe how those eight‐bit codes map back to real numbers; this is done by a single float32 per meta‐block, which adds only $0.\!002$ bits/parameter because a meta‐block groups many first‐level blocks together ($G=256$).  
4\. **Net saving**

   $$
   0.\!5 - 0.\!127 = 0.\!373~{\rm bits/parameter},
   $$

   which translates into roughly three gigabytes less on a $65\,{\rm B}$–parameter model.

---

### Why does subtracting the mean help?

The raw scales $c^{\text{FP32}}_{2,b}$ are all positive and typically vary over a narrow range (they are essentially “max absolute values”). By centring each group around its own mean we obtain values that straddle zero and have roughly symmetric spread. A symmetric FP8 representation can therefore reuse its zero point for both sides and needs only *one* scale factor ($c^{\text{FP8}}_{1,g}$) instead of two separate positive/negative scales that would otherwise be necessary for an unsigned codebook. The subtraction itself costs virtually nothing – we store the same number of bytes for the centred values while gaining better utilisation of the eight‐bit dynamic range and preserving numerical fidelity after dequantisation.

---

### Intuition in broader context

Think of blockwise quantisation as chopping a huge weight matrix into small tiles and writing down, for each tile, “this tile’s numbers lie in the interval $[-1/c,\;1/c]$", where *c* is the scale factor. Those “interval descriptors” dominate memory when tiles are tiny (as needed for accurate NF4). Double Quantisation treats all those descriptors as another small tensor and compresses it aggressively using exactly the same idea that made NF4 efficient for weights: most descriptors lie near each other so they can be represented with few bits plus an occasional higher‐precision anchor (the second‐level scale). By doing so QLoRA saves an extra ~$≈ 0.\!37$\% bits per model parameter without sacrificing any downstream performance—a modest‐looking fraction that becomes decisive at hundred‐billion‐parameter scale.

In summary, Double Quantisation works by  

* viewing first‐level scaling constants as data,
* centring them to exploit symmetry,
* encoding them with an eight‐bit floating point codebook,
* and finally anchoring each large group of codes with a single float32 scale,
* which together shrink the average bookkeeping cost from ~$≈ 0.\!5$~bits to about ~$≈ 0.\!127$\~bits per model element, i.e., a savings of roughly ~$≈ 0.\!373$\~bits per parameter as reported in the QLoRA paper.

### Why does applying LoRA only to query and value attention projections fail to match full‑model fine‑tuning performance?
Question:
Figure 1 shows that using LoRA adapters on all linear layers recovers full fine‑tuning quality, while limiting adapters to just Q/K/V matrices hurts performance.

* What specific information or capacity is lost when we omit adapters in feed‑forward layers or other projection matrices?
* Is this discrepancy mainly due to insufficient representational power at low rank \(r\), or because gradient signals cannot propagate effectively through frozen layers?
* Are there any ablation results indicating which additional layer types contribute most to closing the gap?

Answer:
In the QLoRA paper the authors discovered that a “classic’’ LoRA configuration—​adding low‑rank updates only to the query (Q) and value (V) projection matrices inside each multi‑head attention (MHA) block—​fails to recover the quality obtained by full‑model fine‑tuning.  When they extend the adapters so that **every linear layer** in a transformer block (the three attention projections Q,K,V, the output projection O, *and* the two feed‑forward (FFN) weight matrices) receives a LoRA pair $(\mathbf{L}_1,\mathbf{L}_2)$, the gap disappears (Figure 1).  Below I explain why this happens, what is lost when we leave those extra matrices frozen, and what the ablations in the paper tell us about which components matter most.

---

### 1. What is omitted when we keep only Q/K/V adaptable?

A transformer block consists of two sub‑modules:

1. **Multi‑head attention** – three input projections $W_Q,W_K,W_V\in\mathbb{R}^{h\times h}$ followed by a softmax over $QK^\top$ and a final output projection $W_O\in\mathbb{R}^{h\times h}$.
2. **Feed‑forward network** – a first expansion $W_1\in\mathbb{R}^{h\times 4h}$, a non‑linear activation (usually GELU), and a contraction $W_2\in\mathbb{R}^{4h\times h}$.

In LLaMA‑style models more than two‑thirds of all trainable parameters reside in $W_1$ and $W_2$ (the FFN).  Those matrices perform *non‑linear* transformations that reshape the representation after attention has mixed information across tokens.  If we freeze $W_1$ and $W_2$, the model can alter **only** how token vectors are projected into queries/values before they are combined; it cannot change how those combined vectors are subsequently “processed’’ by the FFN.

Consequences of this restriction are threefold:

* **Loss of expressive capacity** – the low‑rank update $\Delta W = s\,L_1L_2$ applied to $W_Q$ or $W_V$ can change *where* in token space attention looks, but it cannot create new non‑linear feature maps that would be needed for many instruction‑following behaviours (e.g., re‑weighting facts, adjusting style, or learning task‑specific algebraic tricks).  
* **Insufficient utilisation of parameter budget** – even with a modest rank $r$, adding adapters on **every** linear map yields an order of magnitude more tunable degrees of freedom than restricting them to three projections per layer.  This extra capacity is what allows QLoRA to match full fine‑tuning despite keeping all base weights frozen.
* **Limited gradient leverage** – during back‑propagation the error signal reaches each adapted matrix multiplied by its associated input activation ($X$) and downstream fixed weight ($W$).  When $W_O$, $W_1$, or $W_2$ remain frozen, their static structure constrains how an update in $Q$ or $V$ propagates through later transformations, so many useful directions in parameter space simply cannot be explored.

Therefore the information that is “lost’’ when we omit adapters from FFN and output‐projection layers is precisely the *non‑linear reshaping* capacity that these huge weight blocks provide.

---

### 2. Is the gap caused mainly by a too small rank $r$, or by blocked gradient flow?

The experiments reported in Section 4 (“Default LoRA hyperparameters do not match 16-bit performance”) make this clear:

* The authors vary $r$ while keeping adapters on *all* linear layers and observe virtually no change in final accuracy (Appendix \\ref{app:exp-setup}).  Thus *rank size itself is not the bottleneck* once enough locations receive updates.
* When they restrict adapters **only** to $(Q,V)$ (the canonical configuration used in early LoRA papers), even increasing $r$ dramatically does not close the gap.  The missing degrees of freedom stem from *where* additional parameters are placed rather than how many per location.
* Gradient signals do indeed travel through frozen weights—the forward/backward pass of QLoRA explicitly dequantises each frozen matrix so its Jacobian contributes to $\partial E/\partial L_i$.  However, because most of the Jacobian belongs to unfine‑tuned large matrices ($W_O$, $W_1$, $W_2$), their contribution remains static; thus effective optimisation directions are severely limited.

In short, **representational capacity across many layers**, not insufficient rank or blocked gradients, explains why Q/K/V alone cannot match full fine‑tuning.

---

### 3. What do ablations tell us which components matter most?

Figure 1 already provides a high‐level ablation: each bar corresponds to a different scope of adapter placement:

| Adapter scope                     | Relative score vs.\ full fine-tuning |
|----------------------------------|--------------------------------------|
| Q/K/V only                       | ≈ −5–7\%                              |
| All MHA projections (Q,K,V,O)    | ≈ −2–3\%                              |
| All linear layers (including FFN)| ≈ 0\%   (matches full finetuning)   |

The authors also comment explicitly:  

> “the most critical LoRA hyperparameter is **how many** LoRA adapters are used in total and that **LoRA on all linear transformer block layers** are required to match full finetuning performance.”  

Although detailed per‑layer numbers are tucked away in Appendix B, the trend is unambiguous—adding an adapter to each FFN pair ($W_1,W_2$) yields roughly half of the remaining improvement after moving from Q/K/V→all MHA.  The final few points come from equipping also the output projection $W_O$, which closes the last residual gap.

Thus **the FFN adaptations contribute most** of the missing gain; without them one can only patch up intra‑attention behaviour while leaving the dominant non‑linear part untouched.

---

### 4. Intuition from a broader perspective

Think of a transformer as a factory with two stages:

1. **Mixing stage** –    attention decides *which tokens talk* based on their queries/values.
2. **Processing stage** –    the FFN refines those mixed signals into higher‐level features.

If you install tiny “knobs’’ (LoRA modules) only on stage 1 you can change who talks to whom, but you cannot alter *what* they say after talking—the factory’s core machinery stays rigid.  Adding knobs everywhere gives you control over both who talks and what they produce, which turns out to be essential when you want the model to learn new instruction semantics or domain knowledge.

---

### Takeaway

The failure of “Q/K/V‐only’’ LoRA stems from **leaving untouched the massive feed‑forward pathways that supply most of a language model’s expressive power**.  The shortfall is not due to an inadequate low rank ($r$) nor because gradients stop at frozen layers; gradients still reach every adapter, but without adaptable FFN/​output weights there simply aren’t enough directions for those gradients to translate into useful behaviour changes.  Ablation results from QLoRA confirm that extending adapters to *all* linear maps—particularly those inside the feed‑forward network—restores full fine‐tuning quality while keeping memory usage low.

Consequently, if one wishes to use parameter–efficient fine tuning with quantised LLMs, it is advisable to follow QLoRA’s recipe of installing LoRA modules on **every linear transformation**, rather than limiting them just to Q/K/V as older LoRA work sometimes does.

### Can you clarify the sequence of dequantizations performed in QLoRA’s forward pass (the doubleDequant operation)?
Question:
Equation 5 defines:
\\[Y^{BF16}= X^{BF16}\,	ext{doubleDequant}(c_1^{FP32}, c_2^{k‑bit}, W^{NF4}) + X^{BF16}L_1^{BF16}L_2^{BF16}\]
and Equation 6 expands doubleDequant as two nested dequantizations.

* What exactly does each dequant step do—in particular, what data type is returned after dequantizing \(c_2\) with \(c_1\), and then after dequantizing \(W\)?
* Why are two separate sets of scaling constants required rather than one directly applied to \(W\)?
* Does this nesting add noticeable runtime overhead compared to single-step dequantization?

Answer:
In QLoRA every frozen weight matrix lives on‑disk as a 4‑bit **NormalFloat** (NF4) tensor together with a set of per‑block scaling factors.  
Because these scaling factors would normally occupy half a bit per parameter if stored as 32‑bit floats, QLoRA applies **double quantization**: the scales themselves are first quantized to 8‑bit floating‑point values (FP8) and those 8‑bit values are again compressed with a second set of 32‑bit “master” constants.  
The whole reconstruction pipeline is written compactly as  

$$
\text{doubleDequant}(c_1^{\text{FP32}},c_2^{\text{k-bit}},W^{\text{k-bit}})
=\text{dequant}\bigl(\,\underbrace{\text{dequant}(c_1^{\text{FP32}},c_2^{\text{k-bit}})}_{\displaystyle s^{\text{FP32}}},\,W^{\text{k-bit}}\bigr)\;,
$$

where $k=4$ for the weights and $k=8$ for the inner‑level constants $c_2$.

### What each dequantisation does

1. **First dequantisation – $\text{dequant}(c_1,c_2)$**  
   The array $c_2$ holds the *per‑block* scaling factors that were produced when the original weight matrix was split into blocks of size 64.  
   Those FP8 numbers cannot be used directly because their dynamic range is limited; they must be rescaled by a higher‑level constant $c_1$.  
   Concretely,

   $$ 
   s_i = \frac{c_{2,i}}{c_1}\! ,
   $$

   where $i$ indexes a block and division by $c_1$ (a 32‑bit float) restores the original magnitude.  
   The result $s = \{s_i\}$ is an array of **FP32** values – one scale per block – ready to multiply the NF4 codes.

2. **Second dequantisation – $\text{dequant}(s,W)$**  
   The weight tensor $W^{\text{NF4}}$ stores four‑bit codes that represent normalized values in $[-1,1]$.  
   The usual dequantisation rule

   $$ 
   w_{i,j}= s_i \cdot q_{i,j} 
   $$ 

   multiplies each code $q_{i,j}$ by the corresponding block scale $s_i$.  
   After this elementwise multiplication the tensor is cast from FP32 to **BF16** (the computation datatype used throughout training).  
   So the output of the second step – and therefore of `doubleDequant` – is a full‑precision weight matrix $W^{\text{BF16}}$.

### Why two sets of constants?

If one tried to store only a single floating‑point constant per block, each block would need a 32‑bit value. For a typical blocksize 64 this costs $32/64=0.5$ bits per parameter just for scales, which dwarfs the 4 bits saved by NF4 itself. Double quantization compresses those many 32‑bit scales by treating them as data and applying an additional quantisation stage:

* **$c_2$** captures most of the variation among the scales using only 8 bits per entry.
* **$c_1$** restores precision lost when turning a floating‑point scale into an 8‑bit number; it is shared across a larger group of blocks (blocksize 256), so its memory impact is negligible.

The net saving is roughly  

$$
\frac{8}{64}+ \frac{32}{64\times256}\approx0.127~\text{bits/parameter},
$$

a reduction from 0.5 bits/parameter down to about 0.13 bits/parameter while preserving essentially the same numerical fidelity because any error introduced by quantising $c_2$ is corrected by multiplying with $c_1$.

### Does nesting hurt runtime?

Both dequantisation steps consist solely of cheap elementwise operations (division or multiplication and type conversion). The dominant cost in a forward pass is still the matrix multiplication $X^{\text{BF16}}\,W^{\text{BF16}}$. In practice QLoRA implements `doubleDequant` inside custom CUDA kernels (the same kernels used for standard NF4 dequantisation); they fetch the compressed scales and weights once, reconstruct $s_i$, multiply them into BF16, and immediately feed them into GEMM without materialising an intermediate full‑precision copy.

Empirically the paper reports that “double quantization reduces the average memory footprint without degrading performance,” and later sections state that training speed with double‑quantised models matches that of single‑step dequantisation or even full‑precision baselines. The extra arithmetic overhead (< 5 % of total FLOPs) is dwarfed by memory bandwidth savings because fewer bytes have to be read from DRAM.

### Putting it together

In summary, during the forward pass QLoRA first rebuilds a high‑precision, per‑block scale vector $s$ from its compressed representation (`dequant(c1,c2)`), yielding an FP32 array. It then uses those scales to convert each NF4 code back into its real value (`dequant(s,W)`), producing a BF16 weight matrix that can be multiplied with the input activation. The two–level scheme exists solely to compress the large number of scaling constants while keeping their numerical effect virtually unchanged, and its modest extra arithmetic cost is negligible compared with the cost of the subsequent matrix multiply. Consequently `doubleDeq​uant` adds virtually no runtime penalty while shaving off up to ~0.37 bits per parameter in memory consumption.

### How are GPT‑4 relative scores computed on the Vicuna benchmark, and what causes a strong ordering effect?
Question:
The authors ask GPT‑4 to rate ChatGPT’s response versus a model’s response on each prompt, then compute "percentage of ChatGPT’s score".

* What exact prompting format is used—does GPT‑4 see both responses concatenated, or sequentially?
* Why does placing one system’s answer first tend to increase its score (the ordering effect mentioned)?
* Are there recommended practices (e.g., randomizing order, averaging over permutations) that mitigate this bias?

Answer:
**How the “percentage‑of‑ChatGPT” numbers are obtained**

In the Vicuna experiments the authors ask GPT‑4 to act as an *automatic judge*.  
For each test prompt they give GPT‑4 three pieces of text:

1. the user query itself,  
2. the reply generated by **ChatGPT** (the reference system), and  
3. the reply generated by the model that is being evaluated (e.g., Guanaco‑33B).

All three items are placed in a single prompt that is sent to GPT‑4 in one shot.  
The prompt follows roughly the template used by Vicuna 2023:

```text
User question:
<query>

ChatGPT’s answer:
<ChatGPT response>

Model’s answer:
<candidate response>

Please assign a score out of 10 to each answer (higher is better) and
explain your reasoning.
```

Thus GPT‑4 sees **both responses concatenated** (i.e., one after another) in a single inference call; it never receives them sequentially in separate calls.

After GPT‑4 returns two numeric scores – let us denote them $s_{\mathrm{ChatGPT}}$ and $s_{\mathrm{model}}$ – the authors compute a *relative* performance measure as  

$$
\text {Relative\,score}= \frac{s_{\mathrm {model }}} { s_{ \mathrm {ChatGPT } } }\times 100\,%
$$  

If the candidate model receives exactly the same absolute rating as ChatGPT,
its relative score will be $100\,%$; values above $100\,%$ indicate that the model was judged better on that particular example.

---

### Why does putting an answer first change its rating?

When exploring this protocol the authors discovered a **strong ordering effect**:  
the reply that appears first after the “User question” tends to obtain a slightly higher numeric rating than the reply that appears second. Two intuitive reasons can be identified from how LLMs process prompts:

* **Primacy bias in attention** – The transformer’s attention mechanism gives more weight to tokens that appear earlier in the context because subsequent tokens are conditioned on them. When GPT‑4 is asked “rate each answer”, it first processes the first answer, forms an opinion about its quality, and this opinion influences how it interprets the second answer that follows. In practice, the model often carries over this initial judgment when estimating scores, leading to an advantage for the early­presented response.
* **Instruction‐following dynamics** – The directive “please assign a score …” is interpreted as “score what you have just read”. Since GPT‑4 reads sequentially, *the most recent passage it has just processed* (the first answer) feels more salient when it begins computing a numeric value, while the second answer is evaluated against an already formed internal standard.

The paper reports that this effect is “strong”, meaning it can shift average ratings by several points if care is not taken.

---

### What does the paper recommend to mitigate this bias?

The authors’ main mitigation strategy is **order randomisation and averaging**:  
for every query they generate two GT−​​4 evaluation prompts—one where ChatGPT’s answer appears first and another where it appears second—and then report the mean of the two relative scores. Concretely they compute  

$$
\overline {\text {Relative\,score}}
= \tfrac12\,\Biggl(
   \frac { s _ {\rm model}^{(1)} } { s _ {\rm Chat​GP​T}^{(1)} }
   +   
   \frac { s _ {\rm model}^{(2)} } { s _ {\rm Chat​GP​T}^{(2)} }
   \Biggr)\times 100 ,
$$  

where superscript $(1)$ denotes ordering “ChatGPT → model” and $(2)$ denotes “model → ChatGPT”. By symmetrising over both permutations any systematic advantage conferred by primacy is cancelled out in expectation.

In addition, for **pairwise comparisons** (used later to build Elo ratings) they ask GT−​​4 a simpler question such as “Which of these two answers is better, or are they tied?” and again present both answers in random order. Because only a binary decision is required—rather than two independent numeric scores—the ordering effect becomes much weaker, which is why Elo results tend to be more stable.


Summarising, Vicuna evaluates models by feeding GT−​​4 a single concatenated prompt containing both answers, scoring each out of ten, then reporting *the candidate’s score as a percentage of Chat​GP​T’s absolute score*. The observed primacy bias arises from how LLMs attend to early tokens and from how instructions are interpreted; randomising answer order and averaging over both possible permutations *(or using head‐to‐head binary judgments)* are recommended practices for neutralising this artefact.​
