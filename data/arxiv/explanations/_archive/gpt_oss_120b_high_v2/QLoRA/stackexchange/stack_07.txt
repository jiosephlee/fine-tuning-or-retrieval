\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### Can you clarify the sequence of dequantizations performed in QLoRA’s forward pass (the doubleDequant operation)?
Question:
Equation 5 defines:
\\[Y^{BF16}= X^{BF16}\,	ext{doubleDequant}(c_1^{FP32}, c_2^{k‑bit}, W^{NF4}) + X^{BF16}L_1^{BF16}L_2^{BF16}\]
and Equation 6 expands doubleDequant as two nested dequantizations.

* What exactly does each dequant step do—in particular, what data type is returned after dequantizing \(c_2\) with \(c_1\), and then after dequantizing \(W\)?
* Why are two separate sets of scaling constants required rather than one directly applied to \(W\)?
* Does this nesting add noticeable runtime overhead compared to single-step dequantization?

Answer:
In QLoRA every frozen weight matrix lives on‑disk as a 4‑bit **NormalFloat** (NF4) tensor together with a set of per‑block scaling factors.  
Because these scaling factors would normally occupy half a bit per parameter if stored as 32‑bit floats, QLoRA applies **double quantization**: the scales themselves are first quantized to 8‑bit floating‑point values (FP8) and those 8‑bit values are again compressed with a second set of 32‑bit “master” constants.  
The whole reconstruction pipeline is written compactly as  

$$
\text{doubleDequant}(c_1^{\text{FP32}},c_2^{\text{k-bit}},W^{\text{k-bit}})
=\text{dequant}\bigl(\,\underbrace{\text{dequant}(c_1^{\text{FP32}},c_2^{\text{k-bit}})}_{\displaystyle s^{\text{FP32}}},\,W^{\text{k-bit}}\bigr)\;,
$$

where $k=4$ for the weights and $k=8$ for the inner‑level constants $c_2$.

### What each dequantisation does

1. **First dequantisation – $\text{dequant}(c_1,c_2)$**  
   The array $c_2$ holds the *per‑block* scaling factors that were produced when the original weight matrix was split into blocks of size 64.  
   Those FP8 numbers cannot be used directly because their dynamic range is limited; they must be rescaled by a higher‑level constant $c_1$.  
   Concretely,

   $$ 
   s_i = \frac{c_{2,i}}{c_1}\! ,
   $$

   where $i$ indexes a block and division by $c_1$ (a 32‑bit float) restores the original magnitude.  
   The result $s = \{s_i\}$ is an array of **FP32** values – one scale per block – ready to multiply the NF4 codes.

2. **Second dequantisation – $\text{dequant}(s,W)$**  
   The weight tensor $W^{\text{NF4}}$ stores four‑bit codes that represent normalized values in $[-1,1]$.  
   The usual dequantisation rule

   $$ 
   w_{i,j}= s_i \cdot q_{i,j} 
   $$ 

   multiplies each code $q_{i,j}$ by the corresponding block scale $s_i$.  
   After this elementwise multiplication the tensor is cast from FP32 to **BF16** (the computation datatype used throughout training).  
   So the output of the second step – and therefore of `doubleDequant` – is a full‑precision weight matrix $W^{\text{BF16}}$.

### Why two sets of constants?

If one tried to store only a single floating‑point constant per block, each block would need a 32‑bit value. For a typical blocksize 64 this costs $32/64=0.5$ bits per parameter just for scales, which dwarfs the 4 bits saved by NF4 itself. Double quantization compresses those many 32‑bit scales by treating them as data and applying an additional quantisation stage:

* **$c_2$** captures most of the variation among the scales using only 8 bits per entry.
* **$c_1$** restores precision lost when turning a floating‑point scale into an 8‑bit number; it is shared across a larger group of blocks (blocksize 256), so its memory impact is negligible.

The net saving is roughly  

$$
\frac{8}{64}+ \frac{32}{64\times256}\approx0.127~\text{bits/parameter},
$$

a reduction from 0.5 bits/parameter down to about 0.13 bits/parameter while preserving essentially the same numerical fidelity because any error introduced by quantising $c_2$ is corrected by multiplying with $c_1$.

### Does nesting hurt runtime?

Both dequantisation steps consist solely of cheap elementwise operations (division or multiplication and type conversion). The dominant cost in a forward pass is still the matrix multiplication $X^{\text{BF16}}\,W^{\text{BF16}}$. In practice QLoRA implements `doubleDequant` inside custom CUDA kernels (the same kernels used for standard NF4 dequantisation); they fetch the compressed scales and weights once, reconstruct $s_i$, multiply them into BF16, and immediately feed them into GEMM without materialising an intermediate full‑precision copy.

Empirically the paper reports that “double quantization reduces the average memory footprint without degrading performance,” and later sections state that training speed with double‑quantised models matches that of single‑step dequantisation or even full‑precision baselines. The extra arithmetic overhead (< 5 % of total FLOPs) is dwarfed by memory bandwidth savings because fewer bytes have to be read from DRAM.

### Putting it together

In summary, during the forward pass QLoRA first rebuilds a high‑precision, per‑block scale vector $s$ from its compressed representation (`dequant(c1,c2)`), yielding an FP32 array. It then uses those scales to convert each NF4 code back into its real value (`dequant(s,W)`), producing a BF16 weight matrix that can be multiplied with the input activation. The two–level scheme exists solely to compress the large number of scaling constants while keeping their numerical effect virtually unchanged, and its modest extra arithmetic cost is negligible compared with the cost of the subsequent matrix multiply. Consequently `doubleDeq​uant` adds virtually no runtime penalty while shaving off up to ~0.37 bits per parameter in memory consumption.
