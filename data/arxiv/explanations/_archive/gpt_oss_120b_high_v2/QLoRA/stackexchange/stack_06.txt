\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### What is the effect of blocksize choice (e.g., 64 versus larger sizes) on both quantization error and memory overhead in block‑wise 4‑bit quantization?
Question:
Blockwise quantization splits a weight matrix into blocks of size \(B\). The authors use \(B=64\) for weights and \(B=256\) for scaling constants.

* How does decreasing \(B\) improve utilization of all 2⁴ bins for normally distributed weights?
* Conversely, why does a smaller blocksize increase memory consumption due to more scaling constants per parameter?
* Is there an analytical tradeoff curve that predicts optimal \(B\) given a target memory budget?

Answer:
In **QLoRA** the weight matrix is first split into contiguous blocks of size $B$.  
Each block is independently scaled by a **quantisation constant** $c_i$ and then
the centred‑normal NF4 codebook is applied.  
Two consequences follow directly from this design:

1. **Why a smaller $B$ makes the four‑bit bins more uniformly occupied**  
   NF4 was constructed under the assumption that the values being quantised
   follow a zero‑mean Gaussian $\mathcal N(0,\sigma^{2})$.  
   When the whole matrix is normalised with a single global scale,
   an occasional outlier forces $|c|$ to become large enough to fit that
   outlier into the $[-1,1]$ interval. All other (typically much smaller)
   weights are then squeezed into a narrow sub‑range and only a few NF4
   levels receive most of the mass – some levels contain almost no entries.  

   By chopping the matrix into blocks we give every outlier its **own**
   scale factor. Within a modest‑sized block (the authors use $B=64$)
   the extreme‑value statistics of a Gaussian tell us that

$$
\max_{j\,in\,block}|w_{j}|\;\approx\;\sigma\,\sqrt{2\,\log B},
$$

   i.e.\ the range grows only like $\sqrt{\log B}$.  
   Consequently the rescaling factor $c_i$ is close to $\sigma^{-1}$
   for all blocks, so after normalisation each NF4 bucket contains roughly
   $\tfrac{1}{2^{4}}$ of the elements – exactly what “information‑theoretic
   optimality’’ means in the paper (§ “NormalFloat Quantisation’’).  
   If $B$ were made very large, $\sqrt{\log B}$ would increase, making
   $c_i$ too generous and many buckets would again be empty.
   Conversely, if $B$ were too tiny ($<16$), there would be insufficient
    samples inside a block to estimate $c_i$ reliably – fluctuations would
    cause *over‑allocation* of some buckets and *under‑allocation* of others.
    Empirically the authors found that $B\simeq64$ gives good enough
    occupancy while keeping the number of constants manageable.

2. **Why a smaller $B$ costs more memory**  
    Each block needs one scaling constant. If we store it as a naïve
    32‑bit float, the extra bits per weight are simply

$$
\dfrac{32~\text{bits}}{B}.
$$

    For $B=64$ this is $0.5~\text{bits}/\text{parameter}$,
    exactly what § “Double Quantisation’’ reports (“quantisation constants add
    $\tfrac{32}{64}=0.5$ bits per parameter on average”).  
    When we halve $B$, this term doubles; when we increase $B$, it shrinks 
    linearly with $1/B$.  

    The QLoRA pipeline mitigates this cost by **double‑quantising** the 
    constants themselves: an FP8 codebook ($8\,\text{bits}$) is applied with 
    a second‑level blocksize $S=256$. The resulting per‑parameter overhead 
    becomes

$$
\underbrace{\tfrac{8}{B}}_{\text{first level}}
+\underbrace{\tfrac{32}{BS}}_{\text{second level}}
=
\tfrac{8}{B}+ \tfrac{32}{256\,B}
=
0.125+\tfrac{0.125}{B},
$$

    i.e.\ only about 0.13 bits/parameter for $B=64$. The authors quote “a reduction 
    of 0.373 bits per parameter”, which matches this calculation:
    
$$
0.5 - 0.13 \;\simeq\; 0.37 .
$$

3. **A simple analytical trade‑off**  
    The paper does not give an explicit optimisation formula,
    but both effects can be expressed analytically and combined:

*Quantisation error.*  
If we treat each NF4 level as a uniform scalar quantiser placed over a range 
determined by the maximum absolute value in a block,
the step size $\Delta_i$ is roughly

$$
\Delta_i \;\approx\
\dfrac{2\,c_i^{-1}}{2^{k}-1}
=
O\!\Bigl(\dfrac{\sqrt{\log B}}{2^{k}}\Bigl),
\qquad k=4,
$$

so that an L₂ reconstruction error per weight behaves like

$$
E_{\text {rec}}(B)\;\approx\
C_e\,\dfrac{\log B}{2^{2k}}
=
C_e\,\dfrac{\log B}{256},
$$

with some constant $C_e$ that depends on $\sigma^{2}$.
Thus **error grows only logarithmically** with the blocksize.
