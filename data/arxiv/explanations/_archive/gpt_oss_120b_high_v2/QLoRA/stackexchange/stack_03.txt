\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### What is Double Quantization in QLoRA and how does it achieve an average memory saving of ~0.373 bits per parameter?
Question:
Section 3 describes Double Quantization (DQ) as a second‑level quantization applied to the per‑block scaling constants \(c_2\).

* Could someone walk through a concrete example showing how \(c_2\) values are first stored as 32‑bit floats, then quantized to FP8 with blocksize 256?
* How does subtracting the mean before this second quantization affect storage size?
* The paper gives a formula \(0.5\text{ bits} \to 0.127\text{ bits}\); I would like to see a stepwise derivation leading to the claimed reduction of 0.373 bits per parameter.

Answer:
**Double Quantization** in QLoRA is a two‑stage compression that does not only shrink the model weights themselves (the 4‑bit NF4 tensors) but also shrinks the *per‑block scaling constants* that are needed to de‑quantise those weights during the forward pass.  
Because each block‑wise scale occupies a non‑trivial fraction of memory – roughly $\,≈\,0.37$ bits per parameter when a block size of $B=64$ is used – the authors compress these scalars in exactly the same way they compress the weights, thereby earning an extra $\approx 0.37$ bits of saving per model parameter.

---

### What is stored before double quantisation?

When a weight matrix $\mathbf W∈ℝ^{n×d}$ is split into contiguous blocks of size $B$, each block $b$ receives its own **first‑level scale**

$$
c^{\text{FP32}}_{2,b}
=
\dfrac{127}{\,\operatorname{absmax}\bigl(\mathbf W_b\bigr)} .
$$

which is kept as a single‑precision floating‑point number (4 bytes).  
If the model has $N$ total elements, there are $N/B$ such scales and their memory contribution equals

$$
\dfrac N B\times 32~{\rm bits}
=
N\times\dfrac {32}{B}~{\rm bits},
$$

hence $\dfrac {32}{B}=0.\!5$ bits / parameter for $B=64$.

---

### The second‑level compression

The set $\{c^{\text{FP32}}_{2,b}\}$ itself behaves like a tensor that can be **quantised again**:

1. **Mean subtraction** – all scales belonging to a larger meta‑block of $G=256$ first‑level blocks are centred:

   $$
   \tilde c_{2,b}=c^{\text{FP32}}_{2,b}-μ_g,\qquad 
   μ_g=\dfrac1G
        ∑_{b∈g}c^{\text{FP32}}_{2,b}.
   $$

   This makes the distribution roughly symmetric around zero, so an unsigned FP8 format can be used with a single symmetric scale instead of two asymmetric ones; it does not change how many numbers are stored, only improves the effective utilisation of the eight‑bit codebook.

2\. **Quantise to FP8** – every centred constant $\tilde c_{2,b}$ is encoded with an **8‑bit floating point** code:

   $$
   q_{2,b}= {\rm round}\!\bigl(c^{\text{FP8}}_{1,g}\,\tilde c_{2,b}\bigr),
   $$

   where $c^{\text{FP8}}_{1,g}$ is the **second‑level scale** for meta‑block $g$.  
   The codebook entry $q_{2,b}$ occupies exactly one byte.

3\. **Store second‑level scales** – each meta‑block needs one full‑precision scale $c^{\text{FP32}}_{1,g}$ (again 4 bytes).  
   Because a meta‑block covers $G=256$ first‑level blocks, there are only $\dfrac N {B\,G}$ such scalars.

Consequently the storage required for all scaling information becomes  

* one byte per original block → $\dfrac8B = 0.\!125$ bits / parameter,
* plus one float32 per meta‑block → $\dfrac {32}{B\,G}= \dfrac {32}{64×256} ≈ 0.\!002$ bits / parameter,

for a total of  

$$
underbrace{\dfrac8B}_{\text{FP8 codes}}
+
underbrace{\dfrac {32}{B\,G}}_{\text{second‐level scales}}
=
0.\!125+0.\!001953\simeq 0.\!127~{\rm bits/parameter}.
$$

---

### From $0.\!5$ to $0.\!127$: stepwise reduction

1\. **Original cost** – without any extra tricks each first‐level scale costs $\dfrac {32}{B}=0.\!5$ bits/parameter (with $B=64$).  
2\. **After double quantisation** – we replace those raw floats by eight‐bit codes, dropping the dominant term from $0.\!5$ to $0.\!125$.  
3\. **Residual cost** – we must still describe how those eight‐bit codes map back to real numbers; this is done by a single float32 per meta‐block, which adds only $0.\!002$ bits/parameter because a meta‐block groups many first‐level blocks together ($G=256$).  
4\. **Net saving**

   $$
   0.\!5 - 0.\!127 = 0.\!373~{\rm bits/parameter},
   $$

   which translates into roughly three gigabytes less on a $65\,{\rm B}$–parameter model.

---

### Why does subtracting the mean help?

The raw scales $c^{\text{FP32}}_{2,b}$ are all positive and typically vary over a narrow range (they are essentially “max absolute values”). By centring each group around its own mean we obtain values that straddle zero and have roughly symmetric spread. A symmetric FP8 representation can therefore reuse its zero point for both sides and needs only *one* scale factor ($c^{\text{FP8}}_{1,g}$) instead of two separate positive/negative scales that would otherwise be necessary for an unsigned codebook. The subtraction itself costs virtually nothing – we store the same number of bytes for the centred values while gaining better utilisation of the eight‐bit dynamic range and preserving numerical fidelity after dequantisation.

---

### Intuition in broader context

Think of blockwise quantisation as chopping a huge weight matrix into small tiles and writing down, for each tile, “this tile’s numbers lie in the interval $[-1/c,\;1/c]$", where *c* is the scale factor. Those “interval descriptors” dominate memory when tiles are tiny (as needed for accurate NF4). Double Quantisation treats all those descriptors as another small tensor and compresses it aggressively using exactly the same idea that made NF4 efficient for weights: most descriptors lie near each other so they can be represented with few bits plus an occasional higher‐precision anchor (the second‐level scale). By doing so QLoRA saves an extra ~$≈ 0.\!37$\% bits per model parameter without sacrificing any downstream performance—a modest‐looking fraction that becomes decisive at hundred‐billion‐parameter scale.

In summary, Double Quantisation works by  

* viewing first‐level scaling constants as data,
* centring them to exploit symmetry,
* encoding them with an eight‐bit floating point codebook,
* and finally anchoring each large group of codes with a single float32 scale,
* which together shrink the average bookkeeping cost from ~$≈ 0.\!5$~bits to about ~$≈ 0.\!127$\~bits per model element, i.e., a savings of roughly ~$≈ 0.\!373$\~bits per parameter as reported in the QLoRA paper.
