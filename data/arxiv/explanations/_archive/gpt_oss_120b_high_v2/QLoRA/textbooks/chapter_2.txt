# Decoder‑only, Encoder‑only, and Encoder‑Decoder Transformer Families  

Large language models (LLMs) are built from the transformer architecture introduced by \citet{vaswani2017attention}.  Three broad families of transformers appear repeatedly in the QLoRA study because they serve distinct training objectives and downstream tasks.  

Decoder‑only transformers predict the next token in a sequence given all preceding tokens; this formulation is called causal language modeling.  Models such as LLaMA \citep{touvron2023llama}, which are central to QLoRA’s experiments, fall into this family.  The decoder stack consists solely of self‑attention layers whose attention mask blocks information flow from future positions, ensuring that at inference time tokens are generated one after another in left‑to‑right order.  

Encoder‑only transformers ingest an entire input sequence at once and produce contextualized representations without any autoregressive constraint.  RoBERTa‑large \citep{liu2019roberta}, used in the comparison between QLoRA and full‑model finetuning on GLUE \citep{wang2018glue}, exemplifies this family.  Because every token can attend to every other token, encoder‑only models excel at discriminative tasks such as classification or token‐level tagging where a single hidden vector per token is sufficient for downstream heads.  

Encoder‑decoder transformers combine both components: an encoder converts an input sequence into a set of latent vectors, and a decoder autoregressively generates an output sequence conditioned on those latent vectors via cross‑attention mechanisms.  The T5 family \citep{t5}—employed by QLoRA when evaluating Super‑NaturalInstructions—belongs here.  This design supports text‐to‐text problems ranging from translation to instruction following because it can both encode instructions and generate responses while preserving causality only where needed (in the decoder).  

Understanding these families clarifies why QLoRA needs a unified approach that works across all three architectures: the low‑rank adapters are inserted into every linear transformation—whether it appears inside purely self‑attention layers (decoder), purely feed‑forward layers (encoder), or cross‑attention projections (encoder‑decoder).  

# Parameter‑Efficient Finetuning Overview  

Finetuning a gigantic pretrained model modifies all its millions or billions of parameters using backpropagation on task‐specific data.  For a LLaMA 65B model this naïve approach demands more than $780\,\text{GiB}$ of GPU memory when performed in half precision (bfloat16), a requirement far beyond the capacity of a single consumer GPU.\footnote{The memory figure follows directly from the values reported in Section 1 of the QLoRA paper}  

Parameter‐efficient finetuning (PEFT) mitigates this cost by freezing the vast majority of pretrained weights and introducing only a modest collection of new trainable tensors—often called adapters—that capture task‐specific knowledge.\footnote{In QLoRA Section 2 we treat these adapters as Low‑Rank Adapters (LoRA) \citep{hu2021lora}} Because the frozen backbone stays unchanged during gradient descent, its storage cost does not increase when training; only the additional adapter parameters consume extra memory and are themselves small enough that their gradients fit comfortably within typical GPU budgets.\footnote{In Section 2 it is emphasized that “the memory footprint of LoRA is so minimal” that many adapters can be placed throughout a model without harming overall consumption}  

The QLoRA work demonstrates that an appropriately sized set of LoRA modules—when combined with a quantized base model—can replicate full‐model performance while keeping peak memory below $48\,\text{GiB}$ on a single GPU.\footnote{The $48\,\text{GiB}$ figure appears repeatedly as “the average memory requirements… reduced … <48 GB”.} This shift makes instruction tuning of very large models accessible outside industrial compute clusters.\footnote{Section 1 claims this “marks a significant shift in accessibility”.}  

# Mathematical Formulation of LoRA Adapters  

Consider one linear transformation inside a transformer layer,
\[
\mathbf{Y}= \mathbf{X}\,\mathbf{W},
\]
where $\mathbf{X}\in\mathbb{R}^{b\times h}$ denotes the input activation matrix, $\mathbf{W}\in\mathbb{R}^{h\times o}$ represents the pretrained weight matrix, $b$ is the batch size, $h$ is the hidden dimension entering the projection, and $o$ is its output dimension.\footnote{This notation matches Equation (3) in Section 2 (“Low-rank Adapters”).}  

LoRA augments this projection by adding a low‑rank update,
\[
\mathbf{Y}= \mathbf{X}\,\mathbf{W}\;+\; s\,\mathbf{X}\,\mathbf{L}_1\,\mathbf{L}_2.
\]
Here $\mathbf{L}_1\in \mathbb{R}^{h\times r}$ and $\mathbf{L}_2\in \mathbb{R}^{r\times o}$ are freshly initialized trainable matrices whose rank $r\ll \min(h,o)$,\footnote{Section 2 defines $r$ as “the projection dimension”.} while $s$ is a scalar multiplier controlling the overall magnitude of the adaptation.\footnote{Equation (3) uses exactly this formulation}. The product $\mathbf{L}_1\mathbf{L}_2$ has rank at most $r$, so it can represent only a thin subspace relative to $\mathbf{W}$. Nevertheless, by injecting this term into every linear layer—and optionally repeating it across many layers—the model can learn task‐specific directions without ever touching $\mathbf{W}$.  

The number of trainable elements contributed by one LoRA module equals $(h+r)+(r+o)=r(h+o)$ after accounting for both matrices jointly—a dramatic reduction compared with $h\times o$ elements originally present in $\mathbf W$. For instance, if $h=o=4096$ and $r=64$, one adapter introduces only about $0.06\,\%$ of the weight count yet can convey sufficient expressive power when deployed across all transformer blocks.\footnote{The exact percentages vary across model scales but match discussion in Section 2 regarding “0.2 %”.}  

# Memory Consumption Analysis for PEFT Versus Full‑Model Updates  

PEFT reshapes where memory is spent during training.  The frozen backbone still occupies GPU RAM to hold its quantized weights—for QLoRA using NF4 \citep[see Section 3]{...} this amounts to roughly $5\,\text{GiB}$ for a $7\,\text{B}$ parameter model.\footnote{Section 2 reports “the 4‑bit base model consumes 5,\!048 MB”.}  

Activations generated during forward passes dominate peak usage because their gradients must be retained until backpropagation can occur (unless checkpointing removes them). In raw terms – before any optimization – storing activation gradients for every linear layer costs on the order of hundreds of megabytes even for modest batch sizes.\footnote{
Section 2 provides concrete numbers: “the LoRA input gradients have a memory footprint
of 567 MB while … gradient checkpointing reduces … to an average
of 18 MB per sequence.”
}
Gradient checkpointing however trades compute for space by recomputing portions of activations during backward passes; after applying it QLoRA’s non‑parameter overhead collapses from several hundred megabytes down to roughly tens of megabytes per sequence length.\footnote{
The same paragraph notes that after checkpointing “the … average [is] 18 MB per sequence”.
}

The adapters themselves are tiny compared with either activations or frozen weights:\ footnote{
Section 2 states “the LoRA parameters take up only 26 MB”.
}
a $7\,\text B$ model using adapters amounting to $0.2\,\%$ of its parameters stores just tens-of-megabytes worth at training time.\footnote{
“0\.2 %” appears several times regarding common adapter budgets.
}

Summarizing these components yields total GPU demand well below half fifty gigabytes:
\[
\underbrace{\textstyle5~\text GiB}_{\substack{\text{{Base model}\\(NF4)}}}
+
\underbrace{\textstyle0.{06}\,\text GiB}_{\substack{\text{{Adapter}\\weights}}}
+
\underbrace{\textstyle0.{02}\,\text GiB}_{\substack{\text{{Activation\\gradients}\\(\!$\!$with\\checkpoint)}}
}
<48~\text GiB .
\]
By contrast full fine‑tuning would retain all full‐precision weight gradients ($>$500 GiB) plus activations (\>100 GiB), resulting in more than $780\,GiB$ – precisely what QLoRA avoids.\footnote{
Numbers follow directly from Section 1 (“regular 16­-bit finetuning … requires >780 GB”).}
Thus PEFT eliminates almost all extra memory beyond storing frozen parameters plus modest auxiliary tensors.

# Principles of Block‑Wise Scalar Quantization  

Quantization reduces numerical precision by mapping continuous values onto a discrete set defined by fewer bits per entry—a process essential for fitting very large tensors onto limited GPU memory.\footnote{
Section “Block-wise k-bit Quantization” frames this formally.
}  
A naïve global scaling that divides every tensor element by its absolute maximum would allocate all available code points across an entire layer’s distribution:
\[
 \mathbf X^{\, \text{k-bit}}=
   \operatorname*{\mathrm {round}}\!\bigl(c^{\, \text {FP32}}\cdot \mathbf X^{\, \text {FP32}}\bigr).
 \tag{$1$}
\]
Here \(c^{\, \text {FP32}}=\dfrac{\displaystyle 2^{k-1}\!-\!1}{|\!\operatorname {absmax}(\mathbf X^{\, \text {FP32}})\!|}\) rescales values so that after rounding they lie within $\bigl[-(2^{k-1}\!-\!1),\, +(2^{k-1}\!-\!1)\bigr]$, which matches an unsigned symmetric integer range such as $\bigl[-127,\dots ,127\bigr]$ when $k=8$.  
Dequantization simply reverses this operation,
\[
   \operatorname {dequant}(c^{AF}, \,\mathbf X^{k}) 
    = \frac{\mathbf X^{k}} {c^{AF}}
    = \mathbf X^{\, \text {FP32}},
    \tag{$2$}
\]
as guaranteed by Equation (2) from Section Background.\footnote{
I.e., Eq.~(2) holds verbatim.
}

If any single outlier carries extreme magnitude relative to most entries (“the outlier issue”), applying Equation (1)’s universal scale squashes almost all other numbers into just a few central bins—information loss becomes severe.
Blockwise quantization resolves this by first partitioning each weight tensor into contiguous sub–tensors (“blocks”) each containing \(B\) elements,
which are then independently rescaled using their own constant \(c_i=\dfrac {2^{k-1}-1}{|\!\operatorname {absmax}(X_i)\!|}\).
Formally,
let 
\(n=\frac {b\times h}{B}\)
be the number
of blocks resulting from flattening $\mathbf X$, then
each block \(i=1,\dots,n\) yields its own pair 
$(c_i,\;\mathbf X_i^{k})$, producing
an overall quantized tensor comprising $(c_1,\dots,c_n)$ plus  
the stacked low–bit representation.
Due to independent scalings,
every bin receives roughly equal usage within each block,
so even heavy tails do not dominate any single scale.
This principle underlies both integer encodings such as Int8/(Int4)\
and floating point encodings such as FP8/(FP4); each merely differs
in how bit patterns map onto numeric values once scaled via its own
\(c_i$\,. 

# Quantize–Dequantize Pipeline for Integer and Floating‑Point Formats  

At runtime QLoRA stores **only** two pieces per block:
(a) The low‑bit payload ($k=4$, e.g., NF4 or FP4),
and (b) its accompanying scale factor(s) ($c_i$, possibly further quantized).
When an operation needs that weight—for instance multiplying an activation
matrix $\mathbf X^\mathrm {BF16}$ against a frozen linear layer—the system
first reconstructs full precision values:
```math
   \tilde {\!\mathbf W}= 
   {\displaystyle 
   {\operatorname {dequant}}\bigl(c_{i}^{(1)}, 
      {\operatorname {dequant}}\bigl(c_{i}^{(2)}, 
         \mathbf W^\mathrm {k{-bit}}\bigr)\bigr)},
```
where \(c_{i}^{(2)}\) may itself be stored in compressed form (Double Quantization – Section 3).  
For simple integer schemes like Int8,
\(c_{i}^{(2)}=c_{i}^{(1)}=c_i^\mathrm {FP32}\); dequantizing proceeds directly via Equation (2).
For floating point schemes such as FP4,
the payload already encodes mantissa/exponent bits;
the dequant step interprets these bits according to IEEE-like rules,
then multiplies by its blockwise scale \(c_i^\mathrm {FP32}\).

After dequantisation both operands live in bfloat16 (“Brain Float”) –
the computation data type prescribed throughout QLoRA.
Matrix multiplication therefore enjoys full half‐precision accuracy even though weights occupy merely four bits on storage.
Crucially,
backpropagation never needs gradients w.r.t.~these frozen weights;
the chain rule evaluates
$\partial E/\partial (\tilde {\!\mathbf W})$
through dequantisation steps,
but since $\tilde {\!\mathbf W}$ remains fixed,
only gradients flowing into adapter matrices $\mathbf L_1,\;\mathbf L_2$ persist.
Consequently,
memory allocated for optimizer state concerns merely BF16 adapter variables,
while storage savings stem entirely from keeping $\tilde {\!\mathbf W}$ compressed.
This separation between **storage datatype** ($k$–bit NF4 or FP4)
and **computation datatype** (BF16)
is what enables QLoRA’s dramatic reduction
from hundreds of gigabytes down to tens—without sacrificing predictive quality.
The remaining sections built upon these foundations explore how NF4’s optimality
for normally distributed weights further improves empirical fidelity,
how Double Quantization trims even the scale constants themselves,
and how Paged Optimizers keep training stable when occasional spikes arise during gradient checkpointing—all rooted firmly in these basic mechanisms introduced above.
