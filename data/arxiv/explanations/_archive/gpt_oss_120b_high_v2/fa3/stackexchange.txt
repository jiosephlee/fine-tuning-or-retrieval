\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What exactly is producer–consumer asynchrony in FlashAttention‑3 and how does warp‑specialization implement it?
Question:
In Section 3 the authors say they split warps into producer and consumer groups and use a circular shared memory buffer to hide latency. I am unclear about three points: (a) what operations belong to a producer versus a consumer, (b) how the circular buffer coordinates loads of Q/K/V with computation, and (c) why this scheme improves occupancy on Hopper compared to the fully synchronous design used in FlashAttention‑2.
Answer:
**Producer–consumer asynchrony in FlashAttention‑3**

The key idea behind “producer–consumer asynchrony’’ is to let two groups of warps inside a thread‑block run on different hardware pipelines at the same time: one group only issues memory‑movement instructions (the *producers*), while the other group only issues arithmetic instructions that use the data already resident in shared memory (the *consumers*). On Hopper this works because the Tensor Memory Accelerator (TMA) that copies tiles from global memory into shared memory is completely independent of the Tensor‑Core pipeline that executes the warp‑group‑wide matrix‑multiply‑accumulate instruction WGMMA. The two pipelines can accept new work every cycle without having to wait for one another, so a careful software pipeline can keep both pipelines busy throughout the attention kernel.

---

### Which work belongs to which warp group?

At the beginning of a CTA the query tile $\,\mathbf{Q}_i\,$ is loaded once from global memory into shared memory. After this one‑time load every warp that will later perform arithmetic needs no further access to $\,\mathbf{Q}_i\,$; therefore the *producer* warpgroup is free to give up all its registers and devote itself solely to issuing further loads. Inside the main loop over key/value blocks ($\,j = 0,\dots,T_c-1\,$) the **producer**:

* issues a TMA transfer that brings $\,\mathbf{K}__j\,$ and $\,\mathbf{V}_j\,$ from HBM into a slot of a shared‑memory circular buffer,
* optionally performs an in‑kernel transpose of $\,\mathbf{V}_j\,$ when FP8 layout constraints demand it,
* signals (via an atomic flag or barrier) that the slot now contains valid data.

Because only a single thread per warpgroup needs to drive a TMA operation, most threads in the producer group are idle from the arithmetic point of view; they therefore keep their register usage extremely low.

The **consumer** warpgroup does everything that depends on those tiles:

* waits until $\,\mathbf{K}_j$ is present,
* executes an SS‑GEMM (`WGMMA`) that computes $\,\displaystyle \mathbf S^{(j)} = \mathbf Q_i\,\mathbf K_j^{\top}$,
* runs the row‑wise softmax “reduction’’ on $\,\displaystyle \mathbf S^{(j)}$: update the running maximum $m_i$, exponentiate $\displaystyle \bigl(\!\mathbf S^{(j)}-m_i\bigr)$, accumulate row sums $\,\ell_i$, and form $\,\widetilde{\!\!\!\;\widehat{\!\!\!\;\;\ }\!\!\!{\bf P}}^{(\,j\,)}$,
* waits until $\,\displaystyle \!\!\!\;\widehat{\!\!\!}{ {\bf V}}_ j$ is present,
* executes an RS‑GEMM (`WGMMA`) that adds $\,\displaystyle \widetilde{\!\!\!{\bf P}}^{( j )}{\bf V}_ j$ into the partial output $\,{\bf O}_ i$,
* finally releases the buffer slot so that the producer may overwrite it with the next $\, j+s$ tile.

All arithmetic steps use WGMMA, which reads its operands directly from shared memory; thus once a tile is resident there no further global‑memory traffic is required for that iteration.

---

### How does the circular shared‑memory buffer orchestrate loads and computation?

Think of the buffer as a ring of $\,s\$ stages each capable of holding one pair $( {\bf K},{\bf V} )$. The producer writes into stage `j % s` while it reads ahead by up to $\,s\$ tiles; after stage `j % s` has been filled it sets a flag that allows any consumer waiting on that stage to start its work. The consumer reads from exactly the same stage index; once it finishes both GEMMs for tile $j$ it clears the flag (or calls `release`) which tells the producer that this slot may be reused. Because stage indices repeat modulo $s$, after the first $\,s\$ iterations both producers and consumers are continuously busy:

```
iteration 0   load K0,V0 → stage0   ← consumer uses stage0
iteration 1   load K1,V1 → stage1   ← consumer uses stage1
...
iteration s   load Ks,Vs → stage0   ← consumer uses stage0
```

The “pipeline object’’ mentioned in Algorithm 1 simply implements these flag checks with lightweight `bar.sync` instructions. Crucially, `TMA` launches are **asynchronous**, so when a producer issues `TMA.load(K_j)` it does not stall waiting for previous loads or for any pending `WGMMA`. Likewise `WGMMA` launches are asynchronous: after issuing an SS‑GEMM​ the consumer can immediately proceed to schedule softmax work while the hardware matrix engine starts pulling data from shared memory in parallel.

---

### Why does this improve occupancy on Hopper compared with FlashAttention‑2?

FlashAttention‑2 follows a fully synchronous model: every warp in a CTA performs both data movement and arithmetic in lockstep. At each iteration it must:

1. wait for all global–memory loads of $\,{\bf K}_ j,{\\bf V}_ j$ to finish,
2. execute two GEMMs interleaved with softmax,
3. issue another global–memory load.

Because global–memory latency dominates (especially when L2 miss rate grows with long sequences), step 1 stalls all Tensor Core units while they sit idle waiting for their operands. On Hopper this results in low overall SM utilization – experiments in the paper quote only ~35 % TFLOPs whenever attention becomes bandwidth bound.

By separating producers from consumers we eliminate step 1’s stall for compute warps:

* **Memory pipeline stays full** – producers keep feeding new key/value tiles every cycle without needing any synchronization with consumers beyond flag checks.
* **Tensor‐Core pipeline stays full** – consumers always have a ready tile in shared memory, so they can issue WGMMA instructions back‐to‐back.
* **Register pressure is reduced** – producers retain only a few registers (they need none for GEMM accumulators), allowing ``setmaxnreg`` to give consumers more registers for their accumulator fragments and intermediate softmax values.
* **Hardware pipelines truly overlap** – while one warpgroup’s Tensor Cores multiply matrices, another warpgroup’s CUDA cores evaluate exponentials and row reductions; both pipelines run concurrently because they belong to different warpgroups within the same SM.

The net effect is an increase in active instruction issue slots per clock cycle, which manifests as higher *occupancy*: more warps are simultaneously resident without being blocked by memory accesses, leading to measured utilization rising from roughly one third of peak FLOPs in FlashAttention‐2 up to three quarters in FlashAttention‐3 (≈ 740 TFLOPs/s on an H100).

In short, “producer–consumer asynchrony’’ leverages Hopper’s distinct TMA and Tensor‐Core pipelines by assigning them permanently separate warpgroups and coordinating their interaction through a lightweight circular shared‐memory buffer. This decoupling hides global‐memory latency behind matrix multiplication work and frees up registers where they are needed most, thereby achieving substantially higher occupancy than any fully synchronous design such as FlashAttention‐2.

### How does ping‑pong scheduling overlap GEMM and softmax across warpgroups in FlashAttention‑3?
Question:
The paper introduces a ping‑pong schedule where one warpgroup performs softmax while another runs WGMMA GEMMs. I would like a step‑by‑step illustration of which iteration’s softmax is paired with which iteration’s matrix multiplication, and why this pattern yields higher Tensor Core utilization than the original FlashAttention‑2 loop.
Answer:
**Answer**

In FlashAttention\-3 the inner loop that processes a key/value block $j$ is no longer executed “one\-thing\-after\-another’’ as it was in FlashAttention\-2.  
Instead the kernel runs two warp‑groups inside each CTA --- let us call them $WG_A$ and $WG_B$.  
One warp‑group always drives a Tensor\-Core matrix multiply (the **WGMMA** instruction), while the other warp‑group executes the rowwise operations that belong to the softmax (exponentials, row sums, scaling). After every iteration the two groups swap roles; this alternating behaviour is what the authors call **ping‐pong scheduling**.

Below is a concrete walk­through of one CTA processing a query tile $\mathbf Q_i$ together with all key/value tiles  
$\{\mathbf K_j,\;\mathbf V_j\rbrace _{\, j=0}^{T_c-1}$.  
For clarity we denote  

* $S^{(j)}=\;\mathbf Q_i\,\mathbf K_j^{\,\top}\;$   (the “SS‐GEMM’’);  
* $\displaystyle 
   \widetilde{\!\mathbf P}^{(j)}=\exp\bigrl(S^{(j)}-m_i\bigr)$ (the unnormalised softmax);  
* $\ell_i$ (the running row sum);  
* $\displaystyle {\bf O}_i$ (the partial output).

The steps executed by the **consumer** warp group are listed exactly as they appear in Algorithm 2 of the paper.  
All calls to **WGMMA** are asynchronous: they enqueue a Tensor Core operation and return immediately; an explicit ``wait’’ instruction later forces completion when its result is needed.

---

### Iteration 0 – priming the pipeline  

Both warps load $\bf Q_i$, $\bf K_0$, and $\bf V_0$ from global memory into shared memory via TMA.  
$WG_A$ issues  

$$
S_{\rm cur}= \bf Q_i\, {\bf K}_0^{\,\top}
$$

with a **WGMMA** (SS‐GEMM). The kernel immediately proceeds to ``commit’’ this instruction but does *not* stall – $WG_B$ can already start preparing the reduction variables $m_i,\;\ell_i$.  
When hardware finally delivers $S_{\rm cur}$, $WG_B$

* updates the running maximum   
  $$ m_i = {\rm row\:max}\bigl(S_{\rm cur}, m_i\bigr); $$  
* computes   
  $$ \widetilde{\!\bf P}_{\rm cur}= \exp(S_{\rm cur}- m_i); $$  
* updates   
  $$ 
     \ell_i
       = e^{\, m^{\rm old}_i-m_i}\,\ell_i
         + {\rm row\:sum}\!\bigl(\widetilde{\!\bf P}_{\rm cur}\bigr).
   $$  

At this point no value matrix has been used yet; therefore $WG_B$ finishes its work without any dependence on another GEMM.

---

### Iteration $j>0$ – steady state  

Assume that after iteration&nbsp;$j{-}1$ we already have  

* a completed SS‐GEMM   
  $$ S_{\rm cur}= {\bf Q}_i\,{\bf K}_{\, j-1}^{\,\top}; $$  
* its associated “softened’’ tile $\widetilde{\!\bf P}_{\rm cur}$;  
* a ready value tile ${\bf V}_{\, j-1}$.

The next loop body unfolds as follows:

| Step | Performed by | What is launched / waited for                               | How it overlaps |
|------|---------------|-------------------------------------------------------------|----------------|
| a    | $WG_A$        | ``WGMMA(${\bf Q}_i,\ {\bf K}_j^{\,\top})'' →&nbsp;$S_{\rm next}$           | *Start* SSD‐GEMM for block&nbsp;$j$, independent of everything else |
| b    | $WG_B$        | ``wait($V_{ j-1 } )'' then ``WGMMA($\<tilde{}\!{\bf P}_{\<cur}>$, ${\<V>}{\< j-1}> )'' →&nbsp;$ΔO                  | While SSD‐GEMM runs, consume ${\<V>}{\< j-1}>$, launch second RMUL (RS‐GEMM). |
| c    | $WG_B$        |\hbox{``wait(SS–GEMM)}'' → obtain&nbsp;$S_{\rm next}$.                     | After receiving&nbsp;$S_{\rm next}$ compute *softmax* for block&nbsp;$j{-}1$: update&nbsp;$m_i,\;\ell_i,\;\widetilde{{\<P}>}_{\<next>}$. |
| d    | $WG_B$        |\hbox{``wait(RS–GEMM)}'' → add&nbsp;$ΔO$ into ${\<O>} _ i$. Then rescale   
   $$ 
      {\bf O}_i
       = {\rm diag}\Bigl(e^{\, m^{\: {\rm old}}_i-m _ i }\Bigr){^{-1}}
         \cdot {\bf O}_i .
   $$                              | RS–GEMM finishes while step&nbsp;c may already be underway ⇒ both outstanding simultaneously because their sources differ ($S_{\rm next}$ vs.~${V}_{ j-1 } )$. |
| e    | Both groups   &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;(release shared memory buffers for tiles&nbsp;$K_j,V _ { j-1 }$, advance circular buffer index.)&nbsp;&nbsp;&nbsp;(tiny sync via ``bar.sync``). |

The key observation is that *the softmax belonging to block&nbsp;$j{-}1*$ (**step c**) runs *while* *the SSD‐GEMM belonging to block&nbsp;$j*$ (**step a**) occupies Tensor Cores. Likewise *the RS‐GEMM belonging to block&nbsp;$j{-}1*$ (**step b**) overlaps exactly with that same SSD‐Gemm. In other words,

```
softmax(j−1)    ↔   SS−Gemm(j)
RS−Gemmm(j−1 ) ↔   SS−Gemmm(j)
```

When all CTA blocks have been traversed, an epilogue performs one final RS‐Gemm 
(`ΔO` using 
$\widetilde{{\<P>}}\!_\textrm{{last}}\cdot {\bf V}_{{last}}$
) followed by global rescaling based on
the last max/row­sum pair.

Because each half of a “ping’’ ($WG_A$: matrix multiply,
while $WG_B$: softmax/RS‐Gemmm)
is immediately followed by a “pong’’ where their roles swap,
there is never a moment where *all*
Tensor Cores sit idle waiting for exponentials.
Stalls occur only at explicit ``wait’’ instructions guaranteeing data correctness;
they are short because latency hides behind work issued by the opposite warp group.



--- 

### Why utilisation rises compared with FlashAttention‐2  

FlashAttention‐2 executes exactly one phase per iteration

```text
SS–Gemmm → wait → softmax → wait → RS–Gemmm → wait …
```

During every *softmax* phase only a few special­function units (MFU)
are active while all Tensor Cores sit idle.
On an H100 these two kinds of units differ by roughly an order
of magnitude: FP16 matrix multiplication delivers 
$\approx 989~{\rm TFLOP/s}$ whereas special functions such
as ``exp’’ deliver only 
$\approx 3.9~{\rm TFLOP/s}$.  
Consequently roughly half of each kernel’s wall time
is spent doing work that cannot run on Tensor Cores,
which explains why FlashAttention 2 attains only 
$\approx 35~\$%\,$Tensor­Core utilisation on Hopper.



In FlashAttention 3
the ping–pong schedule turns this sequential pattern into
a *two-stage pipeline*:  

* Stage A – launch WGMMA for ${Q}{K}^{^\top}_ {\, j };$  
* Stage B – simultaneously perform exponential/row‑sum reduction
for block&nbsp;$ j{-}1 $
plus an RS Gemmm using tiles already produced earlier.

Since both stages run on disjoint functional units,
their latencies overlap completely:
while MFUs evaluate exponentials,
WMAs feed fresh data into Tensor Cores;
when exponentials finish,
TFLOPs continue unabated on	the next pending Gemmm.
In practice this raises observed FLOP throughput from about 
$570~{\rm TFLOP/s}$ (FlashAttention 2 FP16,
head dim&nbsp;$128$, seq len&nbsp;$8192)$
to roughly 
$620\dots640~{\rm TFLOP/s}$—
an improvement corresponding to 
$\approx 75~\$%\,$utilisation
of H100’s FP16 tensor cores,
close to what an optimal dense Gemmm would achieve.



The benefit scales precisely because every additional interleaving reduces idle time proportionally
to​​the ratio between tensor­core throughput and special­function throughput.
When FP8 kernels double matrix­multiply bandwidth while exponential throughput stays unchanged,
pipelining becomes even more critical;
FlashAttention 3’s ping–pong scheme preserves most of those extra cycles
for useful multiplies instead of letting them waste time in exponentiation stalls.



--- 

### Summary  

Ping pong scheduling splits one CTA into two dedicated warp groups
that alternately act as producer (launching an asynchronous WGMMA Gemmm
for *the next* key block)
and consumer (performing softmax on *the previous*
Gemmm result and applying its weights to *the previously loaded*
value block).
Concretely,

* softmax for block&nbsp;$j{-}1$
overlaps with SS ⊙ Gemmm for block&nbsp;$j$,  
* RS ⊙ Gemmm that uses
   $\displaystyle
      \widetilde{{\<P>}}{}^{({ j{-}1 })}
   $
also overlaps with that same future SS ⊙ Gemmm.

By arranging these dependencies across iterations rather than within one iteration,
all tensor cores stay busy almost continuously and special functions run hidden underneath.
This hardware-aware restructuring lifts effective utilisation from roughly one third
in FlashAttention 2 up toward three quarters on Hopper GPUs—and explains most
of empirical speedup reported in the paper.

### What do SS‑GEMM and RS‑GEMM stand for in Algorithm 1?
Question:
In Algorithm 1 lines 9–15 the authors label two GEMM calls as SS‑GEMM and RS‑GEMM respectively. Are these abbreviations meant to indicate "shared–shared" versus "register–shared" operand locations, or something else? How does this affect register pressure and memory traffic?
Answer:
**Short answer:**  
In *FlashAttention‑3* the two tags simply describe **where the left‑hand matrix of the WGMMA instruction lives** when a block $\times$ block GEMM is issued:

* **SS‑GEMM** – “*Shared $\to$ Shared*”. Both tiles that participate in the multiplication are read directly from **shared memory** (SMEM). In Algorithm 1 this is used for the query–key product  
  $\displaystyle \mathbf S^{(j)}_i=\;\mathbf Q_i\,\mathbf K_j^{\top}$.

* **RS‑GEMM** – “*Register $\to$ Shared*”. The left operand has already been materialised in **registers** (after soft‑max), while the right operand still sits in **shared memory**. This form is used for the probability–value product  
  $\displaystyle \mathbf O_i=
      \operatorname{diag}\!\bigl(e^{\,m_i^{\text {old}}-m_i}\bigr)^{-1}
      \!\,\mathbf O_i
      +\,\widetilde{\!\mathbf P}_i^{(j)}\,\mathbf V_j.$

The letters do **not** refer to “shared–shared vs. register–shared” as a generic description of *all* operands; they only indicate where **the first input** of the WGMMA comes from (the second input is always taken from SMEM).

---

### Why this distinction matters

#### 1. Register pressure  
*SS‑GEMM* needs only enough registers for accumulation (the usual FP32 accumulator used by Tensor Cores). Since both inputs are streamed straight out of SMEM by WGMMA, no extra per‑thread storage is required.

*RS‑GEMM* forces each consumer warpgroup to keep an entire tile of the softmax probabilities $\widetilde{\!\mathbf P}_{{i}}^{(j)}$ live in its private register file until it has been multiplied by $\displaystyle V_j$. For a block size $B_r\times B_c$ this adds roughly  

$$
B_r\,B_c\times\operatorname{sizeof}(\texttt{float})
$$  

bytes per threadblock. On Hopper this extra usage would reduce occupancy if all warps kept their full set of registers, so *FlashAttention‑3* deliberately **reallocates registers** between producer and consumer warpgroups with ``setmaxnreg``: producer warps give up many regs because they only issue TMA loads; consumer warps take them back to hold $\widetilde{\!\mathbf P}$.

#### 2. Memory traffic  
With *SS‑GEMM* no extra movement beyond what was already done when loading $\displaystyle Q_i$ and $\displaystyle K_j$ into SMEM via TMA occurs – WGMMA pulls tiles straight out of SMEM onto Tensor Cores.  

With *RS‑GEMM* we avoid an additional write–read round‑trip that a naïve implementation would incur if it stored $\displaystyle \widetilde{\!\mathbf P}$ back to shared (or global) memory before multiplying by $V$. Because $\displaystyle \widetilde{\!\mathbf P}$ stays resident in regs, each key/value block incurs **one load of $V_j$** but zero extra store / load of intermediate probabilities. Consequently global‐memory traffic stays at the theoretical minimum needed for attention (the three reads of $Q,K,V$ plus one write of $O$).

#### 3. Interaction with asynchrony & warp specialization  
Hopper’s Tensor Cores execute *asynchronously*: a WGMMA launched by a consumer warp can run while another warpgroup issues TMA loads for the next key/value pair. The *SS/RS* distinction fits naturally into this pipeline:

*Producer* warps load $K_j,V_j$\;\;$\rightarrow$\;\;signal ready $\rightarrow$\;\;consumer warps start an **SS‑GEMM** ($QK^{\top}$). As soon as all rows of softmax are available, they hold $\displaystyle \widetilde{\!\mathbf P}$ in regs and issue an **RS‑GEMM** ($\displaystyle \widetilde{\!\mathbf P}V$) *without waiting* for any further store/load operations. Meanwhile producer warps begin loading $K_{j+1},V_{j+1}$. Thus computation on Tensor Cores overlaps with data movement and with lightweight non‑matmul work (exponential, reduction), which is exactly what “producer–consumer asynchrony” aims at.

---

### Broader perspective

The naming convention mirrors earlier FlashAttention papers where “S’’ denotes “operand residing in *shared memory’’’’ – a location that can be consumed by asynchronous WGMMAs without copying – whereas “R’’ denotes “operand already materialised in *registers’’.’’ The choice between these two paths is a classic GPU performance trade‑off:

- **More data movement → lower register usage → higher occupancy**, but potentially higher bandwidth consumption.
- **More data kept close (registers) → higher occupancy cost**, yet reduction of intermediate traffic and enabling deeper software pipelining.

On modern GPUs such as Hopper these tradeoffs become visible because Tensor Core throughput far outpaces special‐function units (exponential), making every saved load/store worthwhile when overlapping becomes possible.

---

### TL;DR

- **SS‑GEMM** = both tiles supplied directly from *shared memory*. Used for $QK^{\top}$; low register usage.
- **RS‑GEMM** = left tile supplied from *registers*, right tile still from *shared memory*. Used for $\displaystyle \widetilde{\!\mathbf P}V$; incurs extra register pressure but eliminates an extra shared‐memory roundtrip.
- The distinction drives how much register space consumer warps reserve (`setmaxnreg`), how many loads/stores occur, and ultimately enables the asynchronous pipeline that gives FlashAttention‑3 its \(1\dfrac12{-}2\times\) speedup on H100.

### Why is softmax a performance bottleneck on H100 despite its low FLOP count?
Question:
The authors state that exponential units deliver only ~3.9 TFLOP/s while Tensor Cores deliver ~989 TFLOP/s for FP16 matmul on H100. Could someone explain why softmax can occupy up to half of execution cycles even though it performs far fewer floating point operations than GEMM, and how overlapping it with async WGMMA resolves this imbalance?
Answer:
**Answer**

The reason why the soft‑max step can dominate the runtime of attention on an H100 even though it contains far fewer arithmetic operations than the two matrix‑multiplications is that the two parts of the algorithm run on completely different hardware pipelines whose peak throughputs differ by two orders of magnitude.

On Hopper every FP16 *GEMM* is carried out by the Tensor‑Core array. A single Tensor‑Core can issue eight fused‑multiply‑add (FMAD) operations every clock cycle, and because an H100 contains 132 streaming multiprocessors (SMs) running at 1.83 GHz this yields a theoretical peak of roughly  

$$
989\,;\;\text{TFLOP/s}
$$

for FP16 matrix multiplication. By contrast, the exponential required for soft‑max is not executed by a Tensor‑Core but by the **special‑function unit (SFU)** inside each SM. The SFU can perform at most sixteen independent transcendental operations per SM per clock tick, which translates into an effective ceiling of  

$$
3.9\,;\;\text{TFLOP/s}
$$

for the whole device when counting an exponential as one floating‑point operation. In other words, although computing an exponential costs only a single “flop” in an abstract operation count, the *hardware* that implements it can sustain only about $4/989\,≈\,0.4\,\%$ of the rate of a Tensor‑Core FMAD.

In the attention forward pass each block $B_r\times B_c$ of scores $\mathbf S=\mathbf Q\,\mathbf K^{!\top}$ produces exactly $B_rB_c$ exponentials (one per element). For a typical head dimension $d=128$ we have roughly $512\times$ more FMADs than exponentials in a single block, but because FMADs run at ≈ 256× higher throughput than exponentials their *wall‑clock* contribution is comparable: roughly half of the cycles are spent executing $\exp(\cdot)$ while the other half wait for or perform tensor‑core GEMMs. This explains why FlashAttention‑2 attains only ~35 % utilization on an H100—most of the compute resources sit idle while the SFU works through its exponential queue.

The paper solves this imbalance by **hiding** the low‑throughput soft‑max work behind the high‑throughput matrix multiplies using **asynchronous WGMMA** (warpgroup‑wide matrix‑multiply‑accumulate) together with *warp‑specialization*. A WGMMA instruction launches a tensor‑core GEMM but does **not** stall the issuing warp; execution proceeds until an explicit wait is inserted or until a dependent value is read back from registers. The authors therefore restructure the inner loop so that each iteration performs three steps:

1. Issue $\mathbf S_{\text{next}}=\mathbf Q_i\,\mathbf K_j^{!\top}$ with a WGMMA and **do not wait** for its result.
2. While that GEMM is still running, load $\mathbf V_{j-1}$, compute $\tilde{\mathbf P}_{\text{cur}}=\exp(\mathbf S_{\text{cur}}-m_i)$ and accumulate $\mathbf O_i←\mathbf O_i+\tilde{\mathbf P}_{\text{cur}}\,\mathbf V_{j-1}$.
3\. Only after both asynchronous GEMMs have completed does the code read back $\mathbf S_{\text{next}}$ and launch the exponential for the next block.

Because step 1 belongs to *producer* warps (which issue only tensor‑core work or TMA loads) and step 2 belongs to *consumer* warps (which execute floating‑point logic such as max reduction, subtraction, exponentiation and division), both units are kept busy at all times—a classic **producer–consumer pipeline** sometimes called “ping‑pong scheduling”. The explicit `bar.sync` barriers enforce just enough ordering so that data dependencies are respected while still allowing overlapped execution across iterations.

With this two‑stage pipeline each block’s soft‑max cost is amortized over two successive GEMMs: while one pair of tensor cores computes $\mathbf Q_i\,\mathbf K_{j+1}^{!\top}$, another pair already finishes $\tilde{\mathbf P}_j\,\mathbf V_j$ and feeds its exponentials into registers. Consequently the fraction of cycles spent inside the SFU drops dramatically—from roughly 50 % down to under 15 % in practice—allowing overall attention throughput to climb from ≈ 570 TFLOP/s (the level reported for FlashAttention‑2) up to **620–640 TFLOP/s** for FP16 forward passes and even higher when FP8 tensor cores are used.

In summary:

*The apparent paradox stems from measuring performance in FLOP/s while ignoring that different operations run on hardware pipelines with wildly different peak rates.*  
*Soft‑max contains few FLOPs but those FLOPs must be serviced by an SFU whose maximum rate is ≈ 250× lower than that of Tensor Cores.*  
*By restructuring attention into a producer–consumer pipeline that runs GEMMs asynchronously via WGMMA while simultaneously executing exponentials on another warp group, FlashAttention‑3 hides almost all of this low‑throughput work under high‑throughput tensor‑core work.*  
*The result is a much higher utilization of the H100’s compute fabric—up to 75 % of its theoretical FP16 peak—and consequently a dramatic reduction in overall latency.*

### How is block quantization applied when converting Q, K, V tensors to FP8?
Question:
Section 4 describes block quantization where each tile gets its own scaling factor before casting to FP8. I am unsure how these per‑tile scales are stored during execution, whether they are kept in registers or SMEM, and exactly where the scale multiplication takes place before feeding operands into WGMMA.
Answer:
**Answer**

In FlashAttention‑3 the tensors $Q,K,V$ are first split into the same rectangular tiles that the attention kernel already processes (a query tile $Q_i∈{\mathbb R}^{B_r\times d}$, a key/value tile $K_j,V_j∈{\mathbb R}^{B_c\times d}$).  
Block‑quantisation means that **each tile gets its own floating‑point scale** $s^{Q}_i,\;s^{K}_j,\;s^{V}_j$; *the elements are multiplied by this factor* **before** they are rounded‑to‑FP8 and written to shared memory (SMEM). The purpose is exactly what the paper calls “block quantisation”: outlier values are confined inside a single small region rather than contaminating an entire tensor‑wide dynamic range.

---

### Where are the per‑tile scales kept?

The kernel already contains a circular SMEM buffer that holds up‑to $s$ pending tiles (`stage = j % s`).  
Because only $s$ tiles can be alive at any moment, holding one extra 32‑bit float per pending operand costs at most a few hundred bytes, far less than&nbsp;the bandwidth budget.  

* **During production**  
&nbsp;&nbsp;&nbsp;&nbsp;The producer warpgroup loads a tile with TMA, runs an intra​warp reduction to obtain  

​$$
a_{\max}= \max_{(r,c)}|\,{\text{tile}}_{rc}\,},
$$  

&nbsp;&nbsp;&nbsp;&nbsp;and computes  

​$$
s=\frac{{{\text{FP8}}_{\max}}}{a_{\max}}\,. 
$$  

This scalar lives initially in a register (`float curScale`).  
Immediately afterwards every element belonging to this tile is multiplied by $s$
and casted to FP8; ...

```cuda
__shared__ float qScale[s];
__shared__ float kScale[s];
__shared__ float vScale[s];

// producer writes
qScale[stage] = curScale;
```

* **During consumption**  
&nbsp;&nbsp;&nbsp;&nbsp;The consumer warpgroup reads the three scalars belonging to *the pair* $(i,j)$ right before issuing WGMMA:

```cuda
float qs = qScale[stage];   // scale of current Q‑tile
float ks = kScale[stage];   // scale of current K‑tile
```

For $Q_i$, this value does not change while we sweep over all key blocks,
therefore after it has been read once it can be hoisted into a register that lives
for *the whole inner loop* (`float qsReg`).  
The key–scale $k_s$ changes every iteration and is therefore fetched from SMEM
at each step (the latency is hidden because loading happens concurrently with other work).

### What is incoherent processing with an orthogonal matrix M and why does it preserve attention results?
Question:
The paper multiplies both Q and K by a random orthogonal matrix M prior to FP8 quantization (“incoherent processing”). I understand M · Mᵀ = I guarantees exact preservation of Q·Kᵀ mathematically, but I am confused whether applying M changes distribution of individual elements enough to improve quantization error without affecting downstream computations such as rotary embeddings.
Answer:
**Incoherent processing** in *FlashAttention‑3* is simply a random orthogonal mixing that is performed **just before** the FP8 quantisation of the query and key matrices.  
Concretely the authors draw a matrix  

$$
\vect M=\vect D_{1}\,\vect H\,\vect D_{2},
$$

where $\vect D_{1},\,\vect D_{2}$ are diagonal matrices whose entries are independent signs ($\pm 1$) and $\vect H$ is a Hadamard matrix. Because $\vect H$ is orthogonal ($\vect H\vect H^{!\top}=I$) and $\vect D_{i}\vect D_{i}^{!\top}=I$, their product $\vect M$ satisfies  

$$
\vect M\,\vect M^{!\top}=I .
$$

The algorithm therefore replaces  

$$
\vect Q \leftarrow \vect Q\vect M , \qquad 
\vect K \leftarrow \vect K\vect M
$$

before the values are scaled, rounded‑to‑nearest‑even and stored in FP8 format.



### Why does this leave the attention result unchanged?

The self‑attention scores are obtained from the inner–product matrix  

$$
\vect S = \alpha\, \vect Q\,\vect K^{!\top},
  
\a lpha=\frac{1}{\sqrt{d}},
$$

and all subsequent operations (row‑wise softmax, multiplication by $\vect V$) use only $\vect S$. If we insert the same orthogonal matrix on both sides we obtain  

$$
(\vect Q\vect M)\bigl(\vect K\vect M\bigr)^{!\top}
   = \vect Q\,(\underbrace{\vect M\,\vect M^{!\top}}_{=I})\,\vect K^{!\top}
   = \vect Q\,\vect K^{!\top}.
$$

Hence every entry of $\vect S$ – and therefore every entry of the final attention output  

$$
\vect O=
      \operatorname{softmax}\bigl(\alpha\,\vect Q\,\vect K^{!\top}\bigr)\,\vect V
$$  

– is exactly the same as if we had omitted $\vect M$.  
The proof works irrespective of finite‑precision arithmetic because the mixing happens **before** any rounding takes place; after mixing we still compute the exact dot products (in FP32 accumulator) before casting back to FP8.



### What does multiplying by $\boldsymbol{\!M}$ achieve?

Although $\vect S=\alpha\,QV^{T}$ does not change, the **distribution of the individual entries** in $Q'M=QM$ and $K'M=KM$ does change dramatically:

* Each component of $Q'M_{i,j}$ becomes a sum of roughly $d/2^{k}$ randomly signed entries from row $i$ of $Q$. Large “outlier’’ values that appear only in a few coordinates of $Q$ are therefore spread over many positions with alternating sign.
* The resulting vectors have almost identical second‑order statistics – their variances become nearly uniform across rows and columns – which means that within any block used for **block‑wise quantisation** the dynamic range shrinks considerably.
* When we later scale each block to fit into FP8’s limited exponent–mantissa range (3 mantissa bits, 4 exponent bits), fewer entries hit the clipping threshold and the rounding noise becomes roughly isotropic rather than being dominated by a few huge spikes.
* Empirically this “random rotation’’ reduces the root‑mean‑square error of FP8 attention by a factor of about $2.6\times$ compared with naïve per‑tensor scaling (see Table 3 in §5.3).

In other words, incoherent processing does not alter the mathematically relevant inner products but *decorrelates* the data so that low‑precision representation harms them less.



### Does it interfere with downstream operations such as rotary embeddings?

Rotary positional embeddings (RoPE) are also linear maps acting on the head dimension:

```latex
$\tilde Q_{i}=R(\theta_{i})\,({Q}_{i}),   
~~
$\tilde K_{i}=R(\theta_{i})\,({K}_{i})$
```

where each $R(\theta_{i})$ is an orthogonal block‑diagonal matrix consisting of $2\times 2$ rotations. Because both RoPE and the mixing matrix $\vect M$ are linear, they can be **composed** without changing semantics:

```latex
$R(\theta_{i})(Q_{i}\,M)=(R(\theta_{i})\,M)\,Q_{i}.$
```

The composition $R'(\theta_{i})=R(\theta_{i})\,M$ is itself an orthogonal transform, so the inner products after RoPE remain invariant:

```latex
$(R'(\theta_{i})\,Q_{i})(R'(\theta_{i})\,K_{j})^{T}
   = Q_{i}\,M\,M^{T}\,K_{j}^{T}
   = Q_{i}\,K_{j}^{T}. $
```

The authors exploit precisely this property: they fuse the fast Walsh–Hadamard transform implementing $\vect H$ with the memory‑bound RoPE kernel so that no extra arithmetic or latency is incurred. Consequently incoherent processing propagates transparently through any subsequent linear operation that treats all heads symmetrically.



### Practical cost

Applying a dense orthogonal matrix would be $O(d^{2})$, which would nullify any speedup from using Tensor Cores. The chosen construction (${\pm 1}\,\mathrm{diag}\times H\times {\pm 1}\,\mathrm{diag}$) admits an $O(d\,log d)$ implementation via an *in‑kernel fast Hadamard transform* (often called “butterfly’’ or “FWHT’’). This extra work occupies only a few warp cycles – negligible compared with the GEMMs whose throughput dominates overall runtime.



### Summary

Incoherent processing consists of premultiplying queries and keys by a random orthogonal matrix prior to FP8 quantisation. Because an orthogonal transform preserves inner products ($(QM)(KM)^{T}=QK^{T}$), it leaves every downstream computation—including softmax and value weighting—exactly unchanged. At the same time it spreads rare large activations across many positions, making each block’s value distribution tighter and enabling much more faithful FP8 representation when combined with block‑wise scaling. The technique commutes with other linear head‑dimensional operations such as rotary positional embeddings, can be realised cheaply with a fast Hadamard transform, and therefore delivers substantial numerical accuracy improvements without any loss of model behaviour.
