\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### How does Double Quantization reduce the memory overhead of quantization constants?
Question:
The paper describes quantizing the first‑level constants $c_2^{	ext{FP32}}$ to 8‑bit floats and then applying a second level of constants $c_1^{	ext{FP32}}$. Can someone explain how this two‑stage process halves the average bits per parameter? A simple calculation with block sizes 64 for $W$ and 256 for $c_2$ would be helpful.
Answer:
**Double quantization in QLoRA**

In QLoRA the weight tensor \(\mathbf{W}\) is stored as 4‑bit NormalFloat (NF4).  
To apply this tensor you first need a *scaling constant* for every block of size \(B_{\!W}=64\):

\[
c_{2}^{\text{FP32}}\in\mathbb{R}^{n},\qquad n=\frac{|\mathbf{W}|}{64}
\]

Here the constant is a 32‑bit floating‑point number, so the constants alone occupy

\[
\frac{32}{64}=0.5\ \text{bits per parameter}
\]

(there are \(1/64\) as many constants as parameters).  
This often dominates the memory budget when training very large models.

**The second quantisation step**

Instead of keeping each \(c_{2}^{\text{FP32}}\) in full precision, QLoRA treats them as values to be quantised again.  
The idea is simple: round the \(c_{2}\)s onto a lower‑precision grid and store that rounded value in 8‑bit floats (FP8). Because the constants themselves are positive and normally distributed, we first center them by subtracting the mean so that symmetric quantisation can be used efficiently.

Let  

* \(B_{c}=256\) be the block size used for the second quantisation (i.e. we gather \(256\) consecutive \(c_{2}\) values and quantise them together),
* \(c_{1}^{\text{FP32}}\) be the new scaling constants for these 256‑value blocks.

The bookkeeping looks like this:

```
      c1 (32‑bit float) ──► scaling factor for block Bc
               │
               ▼
      c2 (32‑bit float…) ──► FP8   ← store 8‑bit encoded values
```

**Memory saving calculation**

*Each original weight block* (\(B_{\!W}=64\)) used **one** 32‑bit constant:  
\(0.5\,\text{bits per parameter}\).

After double quantisation we have:

1. **FP8 table** – one FP8 entry per original weight (\(N_{\mathbf W}\) entries).  
   Each entry needs \(\frac{8}{|W|}\) bits per parameter:
   \[
   \frac{8}{64} = 0.125\ \text{bits per parameter}.
   \]

2. **Higher‑level constants** – one 32‑bit constant per block of 256 old constants.  
   There are \(\frac{|W|/64}{256} = \frac{|W|}{64\times256}\) of them, so each contributes
   \[
   \frac{32}{64\times256}=0.0078125\ \text{bits per parameter}.
   \]

Adding the two parts gives

\[
0.125 + 0.0078125 = 0.\,1328125
     = 0.\,127
     ~\text{bits per parameter (rounded)}
\]

Which is roughly **half of the original 0.5 bits** – a reduction of about **0.373 bits per parameter**, or ~\(3~\text{GB}\) saved on a 65B model.

**Intuition**

You can think of it as replacing a large “house” of constants with a small “garage” that holds just enough ‘keys’ to open all the houses in a neighbourhood:

* The *first level* gives each weight its own key (the big, cheap-to-store FP8 value).
* The *second level* tells you how to transform those keys into something that works for a whole neighbourhood of weights (the tiny FP32 scale factor for each group of 256 keys).

Because almost all weights are accessed through these small, repeated patterns, you get an enormous memory saving while still being able to reconstruct the exact scaling needed during dequantisation.

This two‑stage strategy is therefore what makes Double Quantisation an effective trick to halve the average bits required to store all the unwieldy quantisation constants in QLoRA.
