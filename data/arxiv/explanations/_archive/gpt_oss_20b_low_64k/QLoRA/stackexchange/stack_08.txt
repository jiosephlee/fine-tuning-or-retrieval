\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### `NFk` construction uses two ranges with one zero removed – what are the practical consequences?
Question:
The NFk datatype is built by interpolating $2^{k-1}$ negative and $2^{k-1}+1$ positive Chebyshev points and then removing one zero. Why remove one zero instead of keeping both? What impact does this have on symmetry of quantization bins, handling of padding tokens, or representational bias?
Answer:
**Why NFk removes one zero**

The NormalFloat (NF) data‑type is built by taking the quantiles of a standard normal distribution and mapping each quantile to a distinct integer code.  
For *k* bits we would normally have \($2^{k}\$) distinct code values.  If we tried to split the range symmetrically, we would end up with

* \($2^{k-1}\$) negative codes (including one “zero” that lies exactly at the centre of the negative side),
* \($2^{k-1}\$) positive codes, also containing a “zero” at the centre of the positive side.

Thus the set of target values would contain two identical entries at \(*0*.  
Because the two halves are generated independently, each half contains its own *0*, so naïvely we would duplicate that value twice.

The authors therefore **remove one of the two zeros**: after computing the two sets of quantiles, they merge them into a single set of \($(2^{k}+1)\$) points and drop one occurrence of zero.  This yields a packed code space that:

* uses all \($2^{k}\$) distinct k‑bit patterns,
* has a unique exact representation for *0*, and
* keeps the quantiles equally populated—i.e., each bin contains on average the same number of weights.

In short, discarding one duplicate zero gives an asymmetric scheme that is still symmetric about zero (the missing value is exactly the centre point that both halves share), while allowing every k‑bit code to be mapped to a real number without waste.

---

### Practical consequences

| Aspect | What happens if both zeros are kept | What happens after removing one zero |
|--------|------------------------------------|--------------------------------------|
| **Bit‑pattern utilisation** | Two different bit patterns would map to *0*, leaving an unused slot for a small non‑zero value, effectively wasting one code. | All \($2^{k}\$) bit patterns are used for distinct values; no slot is wasted. |
| **Zero‑point handling** | Having two discrete zeros could lead to ambiguous dequantisation – two different indices imply the same real value. In practice this makes padding tokens (which are exactly zero) map to **two** different codes, which can break deterministic behaviour in attention masks or loss computation. | A single, clean zero point means that all exact zeros—whether coming from padding or true weight values—are encoded identically, leading to consistent behaviour during forward and backward passes. |
| **Quantisation bias** | Duplicate zeros would skew the statistical symmetry: as both halves independently contain a zero bin, more weight mass could accumulate in that bin than for other bins (since both halves have “extra room” for it). This creates a subtle representational bias where very small magnitudes are over‑represented compared to intermediate magnitudes. | Removing one zero restores uniformity of bin widths in terms of probability mass; each bin corresponds to an equal fraction of the normal’s support. The representation error becomes strictly tied to clipping at the extremes rather than an artifact of an over‑filled central bin. |
| **Symmetry of bins** | With two exact zeros, the central region would be under‑represented (there are only \(2^{k-1}-1\) truly negative + \(2^{k-1}-1\) truly positive bins plus two identical zeros). The histogram of real values would look slightly skewed around 0. | The bin distribution is perfectly symmetric: already \($q_0 = -q_{2^k-1}\$) and there’s exactly one \($q_{mid}=0\$. Every interval has the same probability mass, which keeps mean error centred around 0 and preserves symmetry of quantisation noise. |
| **Padding tokens** | If padding tokens map to one of two possible codes for 0 during quantisation, downstream layers may see different weight tensors or masks depending on which encoding is chosen in each instance, introducing stochasticity or instability when computing losses or applying attention masks. | Padding vectors are always encoded with the same code; all runs see identical tensors irrespective of batch reordering, which simplifies implementation and improves reproducibility across GPUs and time steps. |
| **Hardware implementation** | An irreversible mapping from two codes to a single number would require logic to detect “both‑zero” pattern and collapse it, complicating lookup tables or dequantisation kernels on GPUs/TPUs. | A straight table lookup from code → value works for every code uniquely; no special handling needed for a duplicate pattern, making CUDA kernels simpler and faster.

---

### Intuition

Think of the 4‑bit NF quantiser as a lookup table \(\{0,\dotsc,15\} \to {\mathbb R}\).  
If we kept both zeros then indices 7 and 8 might both return 0 when dequantised – effectively we’d have 15 distinct reals stored in 16 codes, wasting one slot.

By removing one zero we rename either index 7 or index 8 so that it maps to a tiny positive (or negative) value instead. The resulting table still looks symmetric around 0:
```
code : value
0   : q_min
⋮
6   : q_-ε
7   : 0          <-- unique centre
8   : +ε
⋮
15 : q_max
```
Now every input value can be represented by exactly one code and every code can become part of an activation gradient without ambiguous mapping.

Because LLM weights are roughly Gaussian after training frozen blocks have been normalised by their absolute maximums, this asymmetric but symmetric mapping keeps most weight mass in carefully chosen bins while guaranteeing an accurate representation for exactly zero—an exact matches is especially important when many entries are padding or come from dropout masks.

---

### Bottom line

Removing one duplicate zero

1. **Satisfies information‑theoretic optimality** – every k‑bit pattern represents a distinct real number under a normal prior.
2. **Keeps symmetry** – ensures equal distribution per bin around mean = 0.
3. **Guarantees deterministic padding token handling** – all paddings use exactly one encoding.
4. **Avoids artificial bias** – prevents over‑winning central bins for small magnitudes.
5. **Simplifies hardware implementation** – no special case needed when dequantising.

Thus this design choice gives NFk its claimed elegance: it honours both theory (equal probability per bin) and practice (unambiguous bit usage and stable training/inference).
