# Bytes, Not Tokens: Why the New BLT Architecture Is a Game‑Changer

Large‑language models (LLMs) have long been glued to a static sub‑word vocabulary – a tokenizer that chops raw text into a fixed set of “tokens.”  
The **Byte Latent Transformer** (BLT) flips this paradigm on its head. By letting the model *learn* how to group bytes on the fly, BLT gains efficiency, robustness, and a fresh perspective on tokenization itself.

---

## 1. The Core Idea: Dynamic Patching of Raw Bytes

Traditional LLMs start with two steps that shape the entire learning process:

1. **Tokenize** – insert a fixed lookup table that maps sequences of bytes to a limited set of sub‑word tokens.
2. **Predict** – run a Transformer on the token sequence.

BLT replaces (1) with **dynamic patching**, where the model decides *where* to stop and form a new unit while training and inference are happening.

### 1.1 From Tokens to Patches

* **Tokens**: fixed, pre‑defined byte groups; every token consumes one Transformer step regardless of its internal complexity.
* **Patches**: variable‑sized groups of bytes formed based on *entropy* statistics of the upcoming byte.

The key is that BLT uses an auxiliary **entropy model** – a small byte‑level LM trained on the same data – to measure how uncertain the next byte will be:

\[
H(x_i)=\sum_{v\in\mathcal{V}}p_e(x_i=v \mid \mathbf{x}_{<i})\log p_e(x_i=v \mid \mathbf{x}_{<i}).
\]

A high entropy at position \(i\) signals that the model needs more context; BLT will start a new patch there.

### 1.2 Three‑Tier Architecture

```
Bytes  ──► Local Encoder  ──► PATCHERS ──► Global Latent Transformer
                                                      │
                     ──◄ Local Decoder ◄───────────────────
```

* **Local Encoder** (few layers): turns raw bytes into fast, low‑dimensional “patch embeddings”.
* **Global Latent Transformer** (many layers): processes few patch embeddings per document, saving compute.
* **Local Decoder** (few layers): expands patch outputs back into byte sequences.

Because the global model sees *much fewer steps*, BLT can afford to bulk up its depth without blowing up flops during inference.

---

## 2. Why Moving Away from Fixed Vocabularies Matters

| Behavior | Token‑Based Models | Byte‑Level Models (BLT) |
|----------|-------------------|------------------------|
| **Domain / Modality Shifts** | Training data domain far outside the tokenizer’s training data → hard to generalize | Works out of the box because there’s no machine‑learned token bias |
| **Input Noise (misspellings, random case changes)** | Tokenizer may split noisy input into new tokens → unpredictable attention pattern | Tokens are just byte groups; noisy input still maps to similar embedding paths |
| **Orthographic Understanding** | Knows sub‑word spellings but cannot “see” inside tokens | Every character is explicit; easier for tasks like G2P or character manipulation |
| **Multilingual Coverage** | Needs language‑specific tokenizer merges → uneven token sizes | Same byte logic applies across all scripts |

Essentially, by removing the hard boundary imposed by a fixed vocabulary, BLT rests solely on *raw data statistics*, offering implicit coverage across languages and noise levels.

---

## 3. Concrete Gains from Dynamic Patching

### 3.1 Better Efficiency

In classic Transformers, every token triggers ~\(O(k^2)\) self–attention flops for \(k\) tokens.  
BLT slides this cost onto *after* patch creation:

- Average patch size can be tuned upward (e.g., 8 bytes vs 4 by default).
- Fewer global steps → up to 50 % fewer flops at inference while keeping or improving overall performance.

### 3.2 Robustness Results

On noisy benchmarks where letters are shuffled or discarded:

- BLT models outperform token-based baselines by an average + 8 accuracy points.
- Superior performance on character manipulation tasks (CUTE benchmark: +25 points).
- Better low‑resource translation across many language families, particularly those with rare glyphs.

### 3.3 Bridge Between Tokenization and Pure Byte Modeling

Historically, pure byte transformers such as ByT5 or MambaByte were too slow because they retained every byte step in attention.  
BLT keeps *the best of both worlds*: it still engineers artificial boundaries _(patches)_ but lets those boundaries adapt to data complexity via entropy signals—turning what would have been needless compute into strategic savings.

---

## 4. How is Bandwidth Managed?

Because patch size is not fixed:

1. The training pipeline packs patches so that each batch sees a consistent number of patches (n_p).
2. The latent transformer’s context length ends up being smaller: \(n_{ctx}/n_p\).
3. During inference we *reset* local encoder stride if an input is short; otherwise use longer strides for bulk processing.

As scale grows (from 400 M up to 8 B parameters), BLEPs (bits per byte) stay competitive with Llama 3 models trained under perfect compute optimality, while idle FLOPs drop dramatically when moving from short patches to longer ones.

---

## 5. Wider Implications for Future LLM Design

1. **New Scaling Dimension** – For a fixed inference budget you can now grow both model size AND average patch size simultaneously—a “two‐axis” scaling space previously absent in token architectures.
2. **Easier Transfer Learning** – Tiny entropy models can be pre‑trained once and reused across domains; you bootstrap fast and stable patching without reconfiguring tokenizers.
3. **Unified Text Representation** – Because every byte is processed in situ, multilingual corpora no longer demand language‑specific vocabularies; lower–resource scripts get included naturally.
4. **Potential Open Source Sprint** – The community now has an opportunity to experiment with varied entropy thresholds or fully end‐to‐end learned patching rules instead of precomputed static values.

---

## 6. Quick Takeaway

BLT demonstrates that a transformer can do *everything* it used to outside sub‑word preprocessing—learn how many bytes make sense together versus stand alone—while staying as efficient as token‐based models and even outperforming them in domain robustness and long‐tail generalization.

So next time you remember that “tokenizer” step as a necessary evil for speed, think again: maybe that layer can be replaced by learning itself how to chunk data most intelligently—because sometimes *bytes* speak louder than tokens.



# Patch‑wise Scaling: How Dynamic Byte Patches Outperform Traditional Tokens

Large language models (LLMs) usually ignore the raw bytes of a file and instead rely on a fixed tokenizer that groups those bytes into token vocabularies. Byte‑level models—those that learn directly from the raw byte stream—have long promised better robustness and universality, but their adoption was stalled by a brutal trade‑off: longer sequences mean far more computation. The **Byte Latent Transformer (BLT)** turns this trade‑off on its head by dynamically grouping bytes into *patches* whose size depends on the data’s entropy. In this post we’ll unpack BLT’s three patching schemes, explain why larger context‑aware patches give the model more leverage, and show how this leads to scaling gains that beat traditional token‑based LLMs.

---

## 1. From Tokens to Patches

| Approach | Fixed? | Size Determined By | Compute Allocation |
|----------|--------|--------------------|-------------------|
| **Tokenization** (BPE, SentencePiece) | Yes | Static vocabulary | One step per token, regardless of complexity |
| **Strided Patching** | Yes (fixed stride) | Pre‑defined `k` bytes | One step per block; no context awareness |
| **Space Patching** | Yes | Whitespace bytes | One step per word; aligns with linguistic boundaries |
| **Entropy Patching** | No (dynamic) | Next‑byte entropy in a tiny language model | One step per *high‑uncertainty* boundary |

Tokens are convenient: every subword is a word‐piece in a lookup table, and because the vocabulary is static, transformer layers can operate over fixed‑size sequences. But every token pays the same computational bill, even if it represents a trivial “good” guess for the next byte. Strided or space patching improve upon this by grouping similar bytes together, yet their size remains fixed. Entropy patching is where BLT truly shines: it uses a lightweight *entropy model* to see where the next byte predictions become uncertain, and creates boundaries there so that only those “hard” segments trigger the expensive global Transformer.

---

## 2. Building Dynamic Patches

### 2.1 The Entropy Model

BLT trains a small byte‑level autoregressive LM on the same data as the main model. For each position `i` it computes:

\[
H(x_i) \;=\;\sum_{v \in \mathcal{V}} p_e(x_i=v|\mathbf{x}_{<i}) \log p_e(x_i=v|\mathbf{x}_{<i})
\]

Here `p_e` is the entropy model’s softmax distribution over the 256 possible bytes. `H(x_i)` measures how surprised the model is about each upcoming byte.

### 2.2 Two Entropy–Based Boundary Rules

1. **Global Threshold** – Start a new patch if `H(x_t) > θ_g`.
2. **Monotonic Jump** – Start a new patch if `H(x_t) – H(x_{t-1}) > θ_r`.

Both rely on inexpensive integer thresholds inferred from validation data to match an average patch size target (e.g., 4–8 bytes). The monotonic rule also mitigates “entropy drift” caused by long repetitive contexts.

### 2.3 Space & Strided Baselines

* **Space Patching**: split at every whitespace or “space‑like” byte; essentially one patch per word.
* **Strided Patching**: every fixed `k` bytes (e.g., k = 4 or 6).

Both are zeroth‑order heuristics with no perception of data uncertainty.

---

## 3. Why Larger Context Means Less Compute

In a standard tokenised Transformer, each token triggers a full pass through the model—even if its next byte is trivial (“e” after “E”). In BLT there is an expensive *global Latent Transformer* that processes *patch representations*. Whenever a patch contains many low–entropy bytes—say an entire HTML tag or repeated code comment—the global model sees only one update for 30 bytes of input rather than 30 updates for each byte.

The cost of processing one patch roughly equals:

\[
\underbrace{\text{Local Encoder Flops}}_{\text{per-byte}} \;+\;
\underbrace{\text{Cross-Attention Flops}}_{\text{per-patch}} \;+\;
\underbrace{\text{Global Transformer Flops}}_{\text{per-patch}}
\]

When patches grow larger **the per‑byte cost vanishes**, leaving only one call to cross-attention and one step through the global stack—both linear in *n_p*, not *n_b*. Thus compute scales more weakly with data length than tokens do.

---

## 4. Empirical Scaling: Patch > Token

A careful study comparing BLT and tokenised models under matched training flops revealed several key findings:

| Metric                     | Tokenised BPE Llama 3 | BLT Entropy (∼5 bytes/patch) | BLT Space (∼6 bytes/patch) |
|----------------------------|-----------------------|------------------------------|----------------------------|
| Bits/Byte @ 8B params      | -0.34 bp/byte          | -0.35 bp/byte                | -0.33 bp/byte              |
| Inference FLOPs / Byte     | 193 GFlops             | ≈144 GFlops                  | ≈120 GFlops                |
| Char–noise robustness      | +4 points              | +8 points                    | +7 points                  |

The numbers translate into:

* **Up to 50 % inference FLOP savings** with only marginal loss (or even gain) in downstream task performance.
* A clear Δ in robustness: BLT consistently outperforms on noisy inputs because it never forgets that it processes raw bytes.
* When *patch size* increases to ~8 bytes under entropy patching, inference flops fall further while scaling trends become steeper—the larger you can pad without hurting learning dynamics, the more you reallocate compute laterally to grow the global Transformer layers.

In other words, BLT’s dynamic patches let us decouple “how much we look” from “how many steps we take”, which is impossible when using tokens tied to a hard vocabulary.

---

## 5. Practical Takeaways for Building Your Own Byte Models

1. **Start Small with Entropy Patching**
   * Train a tiny auto‑regressive LM (~100 M params) on your corpus.
   * Pick thresholds to achieve ~5–6 bytes per patch; adjust at training time if context grows too long.

2. **Include Hash n‑gram Embeddings**
   * Store all length‑3 to length‑8 n‑grams in a hash table (~500K entries).
   * Adds about +0.01 bits/byte improvement with negligible extra compute.

3. **Keep Encoder Light**
   * One or two encoder layers are enough when combined with cross-attention.
   * Add richer decoder layers only if you need high-fidelity byte generation.

4. **Balancing Training Budget vs Inference**
   * For modest budgets (< 500 B flops), keep patches small (~5 bytes).
   * For higher budgets (> 1 T flops), iterate thresholds upward—each additional FLOP saved locally can be invested in another global layer depth.

5. **Robustness Matters**
   * If your downstream applications involve noisy text (OCR scars, touch‑typed typos), carbon-copy your optimizer updates from pre-trained tokenizers and fine-tune with entropy patches – you’ll gain > 8 robustness points across standard benchmarks.

---

## 6. Future Directions

* **End-to-End Patch Learning**  
   Instead of relying on an external entropy LM, train a lightweight network jointly with the main model to predict boundary masks directly from past context—warming up on static patches as pretraining would give you quickly converging results while remaining fully end-to-end.

* **Hybrid Token-Byte Approaches**  
   Use very large patches (~30–50 bytes) for highly predictable sections (structured logs) but fallback to dynamic patches when encountering natural language bursts—this selective routing could squeeze even more compute out of existing hardware.

* **Hardware Co-design**  
   The irregular attention masks used for dynamic patches suggest specialized accelerators that can fuse cross-attention and local Transformers further—organizations investing in HPC may find batching gains here significant.

---

## TL;DR

Forget static token vocabularies if you want efficient, robust LLMs:

- **Dynamic entropy patches let you pay compute only where prediction uncertainty is high**.
- Longer patches dramatically reduce inference FLOPs without hurting accuracy.
- BLT matches or exceeds tokenised baselines at comparable training cost and stays robust under noisy inputs.
- Use simple striding as baseline; experiment with space or entropy patching for best results.
- Scaling studies across 400 M–8B parameters show clear advantages up to an inference budget that matches today’s huge LLM use cases.

If your project needs both speed and resilience, consider adopting BLT’s dynamic patching strategy—or at least experiment with entropy-based boundaries in your own byte-level transformer!



# Behind the Scenes of BLT’s Two‑Tier Transformer Design

Large language models (LLMs) usually start with a **tokenizer** that greedily groups bytes into a fixed vocabulary of sub‑words. This step is a bottleneck: the same amount of compute is spent on every token, even though some tokens contain far more “information” than others. The Byte Latent Transformer (**BLT**) sidesteps tokenization entirely and replaces it with a learned, dynamic *patching* scheme. At its core lies a two‑tier architecture:

1. A **lightweight local encoder/decoder** that turns raw bytes into *patch* embeddings.
2. A **powerful global latent transformer** that runs only on these patches.

Below we unpack how each component works, how they interlock, and why this design gives BLT both efficiency and strong performance.

---

## 1. Why split the work? The “bytes → patches → tokens” flow

Traditional transformers consume sequences of tokens. Every token yields one position in the attention matrix, so the computational cost grows linearly with the number of tokens. If an input string contains 8 000 bytes, but the tokenizer produces 2 000 tokens, the model still processes 2 000 positions.

BLT thinks differently:

| stage | input | output | purpose |
|-------|-------|--------|---------|
| **Local Encoder** | raw bytes (size *n*) | patch embeddings (size *m*) | compress **in‑sequence** information into fewer items |
| **Global Transformer** | patch embeddings (size *m*) | higher‑level patch representations | capture long‑range relations across patches |
| **Local Decoder** | patch representations (size *m*) | raw bytes (size *n*) | generate actual text or regress on byte sequences |

Because patches are *variable* in length—short where bytes are unpredictable, long where they are repetitive—the local encoder can reduce the number of global transformer steps dramatically without losing any detail.

---

## 2. The Local Encoder – from bytes to latent patches

### 2.1 Lightweight transformer + cross‑attention

The encoder is a shallow stack: only a handful of transformer layers (often 1–3). Each layer consists of:

1. **Byte‑wise self‑attention** over a fixed window (e.g., 512 bytes). This captures local context.
2. **Cross‑attention** that pools information from all bytes belonging to a deterministically defined patch into a *single* vector per patch.

Unlike standard transformers, this cross‑attention operates on **dynamic masks**: it knows which bytes belong to which patch at inference time because patch boundaries were already computed during preprocessing.

### 2.2 Hash n‑gram embeddings

To give every byte a richer context before the transformer steps, BLT augments each byte embedding with hashed n‑gram signals:

- For each position \(i\), we form all n‑grams \(g_{i,n}\) for \(n\in\{3,\dots,8\}\).
- Each n‑gram is hashed via a simple rolling polynomial hash.
- The hash index points into an embedding table \(E^{hash}_n\) that stores a learned vector per hash bucket.

These embeddings are summed with the raw byte embedding:

\[
e_i \;=\; x_i \;+\; \sum_{n=3}^{8} E^{hash}_n(\text{Hash}(g_{i,n})) .
\]

Because many different n‑grams collide in the same bucket, this is far cheaper than full character‑level lookup tables yet still injects substantial contextual knowledge (“this byte often follows an e… sequence”) before any attention happens.

### 2.3 Cross‑attention mechanics

Suppose we have \(m\) patches and each patch at some layer contains \(\ell_j\) bytes. Let \(h_{l-1,i}\) be the byte representation after layer \(l-1\). For patch \(j\):

1. **Query** \(Q_j = W_q(P_{l-1,j})\) where \(P_{l-1,j}\) is the pooled representation for that patch (initially taken as the mean of its byte embeddings).
2. **Keys/Values** are all relevant byte representations:
   \[
   K_i = W_k(h_{l-1,i}), \quad V_i = W_v(h_{l-1,i}) .
   \]
3. Apply attention only over those keys/values that belong to patch \(j\):
   \[
   O_{l,j} = W_o \biggl(\text{softmax}\Bigl(\frac{Q_j K^\top}{\sqrt{d_k}}\Bigr)V\biggr).
   \]
4. Add residual and pass to next transformer layer.

After several such layers, we obtain enriched patch embeddings \(p_j \in \mathbb{R}^{h_{\mathcal{E}}}\) ready for the global stage.

---

## 3. The Global Latent Transformer – modelling long context

Once we have compressed our raw bytes to \(m\) latent vectors, we hand them off to a standard transformer stack—except now each vector represents dozens (or hundreds) of bytes.

Key design choices here:

- **Block‑causal mask**: Like GPT‑style transformers but applied per patch instead of per token.
- **Rotary Positional Embeddings** for self‐attention.
- **SwiGLU feed‑forward layers**, mirroring modern LLMs.
- **Size advantage**: Because every patch requires one global step, reducing average patch size reduces FLOPs linearly in contrast to token models where each token inevitably consumes one step regardless of its content.

The result is a scalable “backbone” that absorbs most computational cost but still scales well when averaged over fewer positions thanks to longer patches.

---

## 4. The Local Decoder – reconstituting raw bytes

Generating text means mapping back from latent vectors to concrete bytes. The decoder mirrors the encoder but in reverse:

1. Begins with embeddings derived from the final global representation for each patch.
2. Uses cross‑attention first: queries are byte embeddings from previous decoder layer; keys/values come from current patch representation.
3. Then runs a few small transformer layers on these *byte* sequences per patch.
4. Finally applies a linear head plus softmax over all 256 possible byte values at each position—making this operation independent of any external vocabulary.

Because decoding occurs only when needed—i.e., when generating or predicting new text—the decoder is rarely executed compared to the global model during pre‑training on static data.

---

## 5. Cross-attention as the glue

Both encoder and decoder rely heavily on cross-attention to fuse information inside each dynamic patch:

- In the encoder, it condenses harvested local context into one vector succinctly fed to global layers.
- In decoder, it expands global instructions back out into fine-grained byte predictions.

Without cross-attention, each syntax structure would either be lost (encoder) or significantly more expensive to decode (decoder). Importantly, since cross-attention respects dynamic masks per patch rather than ordinary fixed masks, it can be implemented efficiently using specialized libraries like FlexAttention or FlashAttention variants without sacrificing speed.

---

## 6. Balancing efficiency and performance

### Efficiency gains

| component | traditional token-based model | BLT  |
|-----------|---------------------------------|------|
| Number of positions processed  | ≈ #tokens ≈ N/avg_token_bytes (~4–5 bytes/tok.) | #patches ≈ N/avg_patch_size (6–8 bytes/pat.) |
| Global compute cost  | proportional to #tokens          | proportional to #patches |
| Encoder/decoder overhead  | negligible (embed lookup) 	   	   | small constant due to lightweight nets |

Typical findings show up to ~50 % fewer FLOPs at inference for comparable or better performance once enough data and parameters are provided.

### Performance gains

Because BLT consumes raw bytes end-to-end:

- It can learn fine-grained orthographic features such as morpheme boundaries or character casing patterns that sub-word models often miss.
- Its dynamic parsing lets it allocate more contextual modeling capacity precisely where entropy spikes—e.g., at word starts following spaces—leading to better reasoning and generalization.
- For multilingual low-resource tasks or noisy inputs, BLT outperforms tokenizer-based baselines thanks to directly seeing every byte in context without being crippled by limited vocabularies.

The two-tier design achieves this without sacrificing scalability: as models grow larger we can increase average patch size while keeping inference FLOPS bounded, enabling higher-capacity transformers under fixed compute budgets—a trade-off not possible with fixed-token vocabularies because they tie resource consumption directly to number of tokens seen.

---

## 7. Quick takeaways

| Question | Answer |
|----------|--------|
| Do I need a tokenizer? | No – BLT learns its own grouping through entropy-based & learnable patches |
| How many extra parameters does it add? | Only a handful for local encoder/decoder; most capacity lives in large latent transformer |
| Does it require special hardware? | Standard GPUs; just need efficient implementations for masked cross-attention |
| Can I use it as-is for my own training? | Yes – open-source code available; tune hyperparameters like `avg_patch_size`, `entropy_threshold`, `nlp_layer_count` |

--- 

### Final thought

BLT’s two-tier design is reminiscent of human processing: our brains first chunk streams of sensory input into manageable units (chunks), then interpret these chunks at higher semantic levels while occasionally diving back into lower detail when needed. By mirroring this approach—and doing so cleanly with modern transformer tooling—BLT demonstrates that moving past entrenched tokenization opens new horizons for LLM scaling and robustness without demanding dizzying amounts of compute or data investment.



# Scaling LLMs on Raw Bytes: What the 8B BLT Experiment Reveals

Large language models (LLMs) have the habit of starting every training run with a tiny, hand‑crafted tokenizer: a static sub‑word dictionary that groups bytes into “tokens” before the Transformer even sees the data. While tokenizers bring the short‑term benefit of cutting sequence length in half—or more—researchers have long argued that they add unrelated biases, create robustness problems, and constrain how much compute can be shifted to where it really matters.

The **Byte Latent Transformer (BLT)** breaks out of that cycle. It removes tokenization altogether and works directly on raw bytes. The key novelty is a *dynamically sized patch*—a learnable grouping of bytes whose length is decided during training by the entropy of the next-byte prediction. In practice this means that simple, low‑entropy stretches (e.g., a repeated string “12345”) are packed into longer patches, while unpredictable parts (e.g., the first character of a new word) are split into smaller patches so the high‑capacity Transformer can focus its attention where it matters most.

A recent paper reports an 8 B‑parameter BLT trained on **4 trillion bytes** (≈ 1 trillion English tokens) and asks: *does this “raw‑byte” model earn a spot beside tokenized giants like Llama 3?* The answer isn’t a straight line but a nuanced, data‑driven narrative that shows BLT holding its own and even outperforming tokenized baselines in some key regimes.

## The experimental setup at a glance

| Model | Params | Trained bytes | Tokenizer | Avg. patch size | Inference FLOPs per token |
|-------|--------|---------------|-----------|------------------|---------------------------|
| Llama 3 (BPE) | 8 B | 15 T tokens | 128k vocab | – | 1x (baseline) |
| BLT‑Entropy 8B | 8 B | 4 T bytes | – | ≈ 4.5 bytes/patch | ~0.78x |
| BLT‑Space 8B   | 8 B | 4 T bytes | – | ≈ 6 bytes/patch | ~0.63x |

All three models were trained with **the same flop budget** (≈ 1.15×10¹⁹ FLOPs) and evaluated on the same downstream benchmarks: common‑sense reasoning (ARC‑Easy/Challenge), factual knowledge (MMLU), code generation (HumanEval), and multilingual translation (FLORES).

The critical ingredient that allowed BLT to be compared fairly was an *entropy‑based patching scheme* trained from a lightweight byte LM. Once the entropy model had produced a threshold per data point, patches were created on-the-fly during data loading—no replayable rule needed.

## Where BLT shines

### 1. Tokenization‑free but still training‑flop optimal

Previous byte‑level models were famously outperformed by BPE models when matched for training FLOPs up to ~400 M parameters. The BLT experiment flips that trend: at **8 B parameters**, BLT’s Bits‑per‑Byte (BPB) is *comparable* to Llama 3’s perplexity-scoring on raw tokens, even though it processes raw bytes directly.

The scaling study shows that when you **control for compute** rather than parameter count alone, BLT matches or surpasses BPE models across all tested sizes (1–8 B). Dynamic patching lets the model save computation on predictable sequences without throwing anything away.

### 2. Flop efficiency at inference

One advantage of tokenization is that every step costs roughly the same; you process one BPE token regardless of how many underlying bytes it contains. For BLT this is no longer true—every patch triggers only one call to the global Latent Transformer, plus a few lightweight cross-attention operations.

Because most natural text has low entropy in long stretches—think inside “passwords” or logs—the average patch size climbs to around **6–8 bytes** without harming performance. Relatively longer patches translate directly into fewer global transformer steps: *≈50% fewer FLOPs per output byte* compared with tokenized baselines, while retaining competitive downstream skill.

### 3. Robustness to noise and character-level mastery

A side effect of dropping tokenization is increased resilience against character scrambling:

- When faced with garbled inputs (random case flipping, repeated characters, or dropped letters), BLT retained an average **+8 points** over tokenized rivals.
- On strict character manipulation tasks like **CUTE**, BLT outperformed tokenized Llama by more than **25 points**, achieving near-perfect scores on spelling challenges.
- In low-resource translation experiments (FLORES‑101), BLT gained up to **+2 BLEU** when translating into English from typographically diverse scripts—all while being trained on fewer total tokens.

These points reinforce one core hypothesis: *bytes give the model direct access to symbol-level structure*, which more subtly shapes long-tailed or noisy data better than abstract subwords.

### 4. A new scaling dimension

Because patches are not part of a fixed vocabulary, you can simultaneously grow both:

- **Model size** – make your global Transformer deeper.
- **Patch size** – pack more bytes per step and cut compute.

With a fixed inference FLOP budget this means you can train larger models that still compute efficiently at inference time—a tradeoff impossible for tokenizers.

In experiments where batch sizes were held constant but average patch size was increased from 4.5️⃣ to 8️⃣ bytes, **BLT’s scaling curve steepened dramatically**: it surpassed tokenised baselines at about two orders of magnitude less compute than would otherwise be required.

## Why does dynamic patching matter?

Think about standard English text: after predicting “M” in “Mozart”, subsequent characters are highly predictable; prediction entropy drops dramatically across the rest of the word. If you forced those remaining characters into one fixed-size chunk, you'd keep paying full Transformer cost for something trivial.

BLT’s entropy-driven algorithm looks ahead *one byte*, signals whether this lookahead is hard or easy based on entropy:

```
H(x_i) = - Σ_v p(v|x_<i) log p(v|x_<i)
```

If H is high ➜ start new patch; if it stays low ↓ ➜ continue packing. Two heuristics were tried:

1. A hard global threshold.
2. A relative increase exceeding a small margin (`H_t - H_{t-1} > θ_r`).

Both scalably reduced sequence length while keeping enough context for downstream tasks—unlike static strided pooling where chunk boundaries cut arbitrary words in half or concatenate unrelated symbols.

## Caveats and next steps

While promising, BLT does carry some open questions:

- **Out-of-domain generality**: More languages with non-Latin scripts require careful adaptation of hash-gram tables; initial results show benefits but larger training windows may be needed.
- **Architectural tuning**: Scaling laws for byte-level models haven't been fully derived yet; future work could shift from simply matching BPE curves to optimizing purely for byte inputs.
- **Implementation maturity**: Current code uses FlexAttention for dynamic masking but necessitates custom kernels; real wall-clock speedups still lag behind production BPE pipelines.

Nevertheless, these hurdles feel far below typical engineering thresholds once you've broken free from tokenizer constraints—the potential performance gains alone justify them.

## Bottom line

The 8 B BLT experiment shows:

| Aspect          | Tokenized BPE         | Byte Latent Transformer |
|-----------------|-----------------------|------------------------|
| Bits-per-byte   | Comparable             | Comparable / Slightly better |
| FLOPs / output   | Baseline                | ~0.75× baseline                |
| Robustness      | Lower                   | Higher across noisy + character tasks |
| Scaling freedom | Fixed tokens            | Simultaneous growth of model & patch size |

If you’re building or evaluating LLMs where compute budgets at inference are tight—or where robustness to noisy input matters—moving away from fixed vocabularies toward dynamically sized byte patches may well be your next big optimization step. The raw‐byte world isn’t just theoretically interesting; with careful design it’s practically competitive—even superior—in key areas where today’s state-of-the-art expect tokenization as a non-negotiable prerequisite.



# Robustness at the Byte Level: How BLT Beats Tokenized Models on Noisy Text

Large language models (LLMs) have become almost ubiquitous in everyday NLP pipelines.  Yet, whenever the input text is corrupted—by typos, unusual casing, or a script unseen during training—their performance can drop sharply.  The culprit is usually the tokenizer: sub‑word units act as a fixed “compression gate,” and once the raw bytes have been mapped to a single token, any perturbation inside that token is essentially invisible to the model.

The **Byte Latent Transformer (BLT)** flips this paradigm on its head.  By working directly with raw bytes and learning *dynamic patches* of variable length, BLT allocates more compute where the data is genuinely ambiguous and far less where it is predictable.  On several benchmarks that test character‑level acuity and low‑resource translation, BLT not only matches but *outperforms* tokenization‑based counterparts such as Llama 3.

Below we walk through the key evidence from three concrete benchmarks—CUTE, G2P, and FLORES‑101—and explain why byte‑level modeling gives BLT a decisive edge.

---

## 1. CUTE: Mastering Character Manipulation

CUTE (Character Understanding Through Expected Prompts) probes an LLM’s ability to *manipulate* text at the character level: inserting, deleting, reversing… etc.  Tokenizers hide most of these low‑level operations inside multi‑byte tokens; a model trained only on these tokens cannot learn to “move a character” because it never sees the character in isolation.

| Model | CUTE Accuracy (Avg) |
|-------|---------------------|
| LLaMA 3 (BPE) | 23.4 % |
| BLT‑Entropy (entropy‑based patching) | **48.9 %** |

BLT’s superior performance is especially striking on *spelling* variants: when swapping upper‑case / lower‑case letters, removing random characters, or repeating characters five times in a row — tasks that are deliberately noisy or adversarial — BLT never flounders.  The underlying reason? The local encoder in BLT receives raw byte embeddings plus hashed n‑gram context, so every character—even one that does not belong to any learned token—is represented faithfully from the ground up.

A short demo illustrates this:

```python
prompt = "Transl8te th1s sentence into enGlish."
# BPE model skips over unknown subwords like "Transl8te"
# BLT model recognizes "8" as a separate byte and predicts
# that it should be "ate".
```

The model’s per‑character confidence curves stay smooth even when we deliberately insert random noise (spelling errors, shuffled case).  That robustness translates into higher downstream scores on car­acter‑level tasks.

---

## 2. G2P: Grapheme-to-Phoneme with Zero Fear

Predicting phonemes from graphemes is notoriously tolerant of orthographic noise: many languages have inconsistent spelling–pronunciation relations.  A tokenization pipeline often normalizes characters before feeding them into a transformer; while this helps standard sequences, it also erases contextual cues that can disambiguate homographs.

BLT attends to every byte directly; the local encoder’s cross‑attention aggregates context over entire patches while keeping a fine‑grained view of each byte.  Consequently:

| Model | G2P Accuracy @5 shot |
|-------|-----------------------|
| LLaMA 3 | 57.2 % |
| BLT‑Entropy | **64.5 %** |

In practice, when given an English word like *“cough”*, LLaMA would treat “…f” as part of its neighbourhood subword “gh” and emit an incorrect pronunciation heap (“kawf”).  BLT distinguishes between the historical `f` and `gh` bytes inside a patch and correctly outputs /kɔːf/.  

When evaluated on the phonology benchmark for German and Spanish—a notoriously irregular segment—BLT again delivers superior scores with a smaller relative gap compared to tokenized models.

---

## 3. FLORES‑101: Low-Resource Language Pair Handling

Tokenizers are constructively biased toward high‑frequency patterns in well-resourced corpora like English or Chinese.  For rare languages (e.g., Irish Gaelic or Uyghur), few tokenizers include appropriate subword statistics at all. As a result, some languages end up sharing tokens that cross linguistic boundaries or suffer from spurious merges.

In FLORES‑101’s extensive set of over twenty-one low-resource languages assessed in both directions (source → target and target → source), BLT shows remarkable gains:

| Language Family | BLEU↑ (LLaMA 3) | BLEU↑ (BLT‑Entropy) |
|-----------------|-----------------|---------------------|
| Indo-Aryan     | +0.7 pts        | +1.4 pts            |
| Austronesian   | +0.4 pts        | +0.9 pts            |
| Afro-Asiatic   | +0.6 pts        | +1.3 pts            |
| Overall score   | +0.5 pts        | **+1.1 pts**        |

Why does this happen? Because each byte belongs to *exactly* one language in most writing systems; there’s no semantic pressure to share subwords across unrelated scripts unless explicitly forced by training data mixture strategies. A ByteLatent model can detect when a contiguous block of bytes constitutes an idiom or language identifier through its entropy patching routine and preserve that integrity without forcing those bytes into an external vocabulary bucket.

Additionally, due to dynamic patching based on next-byte entropy, BLT tends to form shorter patches when encountering unfamiliar scripts (high entropy) and longer patches for regular patterns—effectively giving more capacity where needed without blowing up overall compute cost.

---

## How Does Blt Get This Harder Work Right?

There are three architectural pearls that enable BLT’s robustness:

1. **Entropy-Based Patching**  
   Instead of blindly grouping bytes by fixed size or whitespace rules, BLT splits sequences at positions where a small auxiliary byte LM predicts high uncertainty for the next byte (`H(x_i)` > threshold).  
   This ensures *harder* boundaries get finer granularity so more attention mass can be committed there later by the global latent Transformer.

2. **Hash N-Gram Augmentation**  
   Each byte’s embedding is enriched with hashed embeddings over lengths \(n = \{3,\dots,8\}\). Think of it as giving each character its own “neighbor signature.” Even if a tokeniser would merge `"cat"` into one atomic unit, BLT individually remembers `"ca"`, `"at"`, etc., allowing correct composition later.

3. **Two-Stage Local–Global Interaction**  
   A light-weight local encoder transforms bytes into patch representations quickly; then a heavyweight latent Transformer processes these patches autoregressively across document boundaries (“block-causal” masking).  
   Because global attention only activates at patch boundaries—which are sparse compared to every byte—most of the compute goes where it matters most.

---

## Takeaway

Byte-level modeling isn’t just an academic curiosity; it has practical implications for any application that must gracefully handle noisy inputs or low-resource content:

- **Character Noise Resilience** – No more catastrophic failures when users type in all caps or slip typos.
- **Enhanced Orthographic Awareness** – The model carries explicit information about case shifts, diacritics, and even phonetic patterns.
- **Improved Low-Resource Translation** – By avoiding polluting subword vocabularies with out-of-distribution patterns, it better captures pure linguistic signal even with few training examples.

In short: When you care about robustness—be it for user-facing chatbots scrubbing text for casual chat or for mission-critical medical record parsing—a Byte Latent Transformer gives you *more compute dollars yielding cleaner surfaces*. If your next project needs resilience without building entirely new tokenizers from scratch, consider sliding into (or layer them upon!) CLM based on raw bytes instead!



# From Llama 3 to BLT: The Art of “Byte‑ifying” a Pre‑Trained Model  

Large‑language models have come to rely on sub‑word tokenizers (BPE, SentencePiece, etc.) to keep sequence lengths short and training tractable.  But tokenization introduces its own biases: it can make models fragile to misspelled words, limit the ability to process low‑resource languages or user‑generated text in unexpected scripts, and tie the representational capacity of the model to a fixed vocabulary size.  

The recent *Byte Latent Transformer* (BLT) paper shows that a tokenizer‑free architecture can not only match token‑based LLaMA 3 performance at scale — but also offers *better* efficiency and robustness when trained from scratch.  What is more fascinating for practitioners is a simple two‑step pipeline that lets you **”byte‑ify”** an existing LLaMA 3 checkpoint with almost no extra training.  In this post we walk through that distillation process, why it works, and what practical benefits it brings.

## Why “byte‑ify” a pre‑trained model?

1. **Jump-starting training** – BLT needs a global transformer that processes *patches*, not individual bytes.  Rather than randomly initializing this large component from scratch, we can copy weights from LLaMA 3’s well‑tuned transformer layers.  
2. **Retaining knowledge** – LLaMA 3 already knows common phrasing, world facts, and has learned to predict the next token efficiently.  By reusing its weights we preserve that knowledge; only the *representation space* changes from tokens to patches.  
3. **Reducing compute** – Training BLT from scratch takes thousands of GPU‐hours per billion parameters when feeding raw bytes.  Freezing the global layer(s) and only fine‑tuning a small token‑to‑patch encoder/decoder gives practical speedups (orders of magnitude fewer training steps).  

The distillation works because BLT’s global transformer is architecturally identical to LLaMA 3’s (same depth, same number of heads, same rope embeddings).  Only the input connectivity changes: instead of an embedding table for bytes or tokens, BLT uses a lightweight encoder that converts sequences of bytes into *latent patch vectors*.  As long as the dimensionality matches, we can copy over weights wholesale.

## The two‑phase pipeline

| Phase | Goal | Key Operations |
|-------|------|----------------|
| **1️⃣ Initialize** | Transfer knowledge from	LLaMA 3 into BLT | • Replace LlaMA's token embedding table with a *byte* hashing layer.<br>• Copy all encoder weights (except embedding layer) into BLT’s latent transformer.<br>• Keep the number of parameters (and hidden dimensions) identical so that no architectural mismatches arise. |
| **2️⃣ Fine‑tune** | Adapt the encoder/decoder so they can translate between raw bytes and latent patches | • Initialize the encoder with a tiny few Transformer blocks (< 5 layers).<br>• Train a *small entropy LM* (≈ 100M params) jointly (or separately in a data loader pass) to generate patch boundaries using byte entropy.<br>• Let only encoder/decoder learn: freeze the latent transformer during early epochs (or use a very small learning rate afterward). |

**Implementation tips**

- **Hash embeddings for bytes** – The paper uses 500K unique byte n‑gram hashes (n = 3…8).  In practice you can start with 200K; experiments show diminishing returns beyond ≈ 300K.
- **Entropy model** – A tiny byte MLM (512 hidden units, 14 layers) with a sliding window of 512 bytes is usually enough to supply patch boundaries consistent with those used during LLaMA training.
- **Optimizer settings** – Use AdamW with weight decay = 0.1; start with LR = 4e-4 for encoder/decoder and keep LR ten× smaller for the frozen latent transformer if you choose not to freeze it at all.
- **Batch size & context length** – Preserve per-batch byte count from your LLaMA training run; BLT will automatically segment dynamically based on patching algorithm.

## Practical benefits

| Benefit | Explanation |
|---------|-------------|
| **Speedy convergence** | Turning on few hundred million BS training steps instead of MB? evaluation on large corpora yields ~2× speedup in wall‐clock time while achieving similar perplexity/ BPB gains as full retraining. |
| **Scalable inference budget** | Because BLT groups bytes into longer patches when entropy is low, you can increase average patch size (say from 4 bytes → 8 bytes) without changing batch size or memory requirements, but cutting inference flops by ~50%. |
| **Robustness to noise & low‑resource data** | Byte representations expose each character directly; in noised datasets BF-LTs function better than tokenized models (see §5 robustness in paper). |
| **Easy “tokenizer‑free” downstream fine-tuning** | Once you have a byte‑aware base model you can fine-tune it on specialized corpora (URLs, logs, code dumps) without reintroducing token‐level mistakes or degenerate OOV issues. |

## Experiments & results

A short ablation in the paper compared:

- ✅ Bare LLaMA 3 baseline
- ⚓️ BLT initialized with frozen latent transformer + small encoder/decoder
- 🚀 Full retraining of BLT from random

Key numbers:

| Model | Tokens seen / SBLE | Bits-per-byte BPB | Noisy HellaSwag accuracy |
|-------|--------------------|-------------------|--------------------------|
| LLaMA 3 (64B vocab) | 15 TB (`𝑁≈1e13` tokens) | 1.02 | 63% |
| Distilled BLT (same Δ param.) | 15 TB + small encoder/decoder | ~1.00 (0.2 % better BPB) | +8 pp (~71%) |
| Full retrained BLT | Same Δ param., full layer train | ~0.99 (0.5 % better BPB)| +10 pp |

The modest cost—adding just an extra few million parameters for the encoder/decoder—delivers noticeable gains even over all-token BPE models.

## Checklist: Going from LLaMA 3 to “Byte‑ified”

1. **Prepare raw byte dataset** matching your downstream domain.
2. **Set up entropy model**, train or load pre–trained lightweight byte LM.
3. **Build hash embeddings** for byte n–grams.
4. **Initialize BLT’s global transformer** with frozen LLaMA weights.
5. **Fine–tune encoder/decoder**, possibly first freezing then unfreezing latent layer if needed.
6. Evaluate across BPB and downstream tasks; adjust patching hyperparameters (`θ_g`, `θ_r`) until average patch size matches your target inference budget.

## Future research directions

- Learn patch boundaries *end-to-end* via auxiliary loss instead of an external entropy model—might reduce preprocessing overhead.
- Explore multi-task training where one head predicts entropy while another predicts next byte: joint learning could improve both performance and efficiency.
- Test scaling beyond 8B parameters: as GPUs get bigger this architecture may exceed tokenized models even more strongly because local encoders do not grow linearly.

---

### TL;DR

By simply copying over the bulk of LLaMA 3’s transformer weights into BLT’s latent module and then adding a light encoder–decoder pair plus an entropy LM, you can quickly obtain a byte‑level language model that preserves or even improves upon tokenized baselines while offering better inference cost control and robustness to noisy inputs ‑ all without starting from scratch.

Happy “byte‑ifying”!



# Future Directions for Byte‑Level LLMs – What’s Next for BLT?

Byte‑level language models are finally catching up to their token‑based cousins, thanks to the Byte Latent Transformer (BLT). The paper shows that a carefully engineered “patching” mechanism and a lightweight local encoder/decoder make byte‑level training tractable at the 8 B‑parameter, 4 T‑byte scale. Yet, BLT is still a first‑generation technology. The authors point to several open research avenues that could push byte‑centric LLMs further:

| Open Question | Why it matters | What the paper says |
|---------------|----------------|---------------------|
| End‑to‑end patch boundary learning | Patch boundaries are currently derived from a pre‑trained entropy model; end‑to‑end learning could reduce overhead and improve adaptability. | The authors note that their entropy model is *lightweight* and *static*. Learning patch borders jointly with the main LM might allow the network to discover more optimal segmentations and avoid a separate pruning step. |
| Scaling laws specific to BLT | Existing scaling relationships were derived for BPE transformers. BLT’s architecture—especially its dynamic patch size—may violate those assumptions. | In the Conclusion they admit that “calculating scaling laws for BLT could lead to more favorable trends.” |
| Architectural tweaks at even larger scales | BLT works up to 8 B parameters, but it is unknown how its components behave as we push past that. What local–global split or embedding size will be optimal? | Ablations show that the local encoder can be *extremely lightweight* (one layer) while the decoder needs more capacity. There is a hint that deeper global layers would be more beneficial for larger models. |
| Hardware acceleration (GPU, FPGA, specialized ASIC) | Current implementations rely on software libraries (Flash/​Flex‐Attention). A custom accelerator that natively supports dynamic, multi‑head cross‑attention over variable patch sizes could deliver huge speedup for both training and inference. | The paper mentions that FlexAttention was used because of the dynamic masks; however, speed gains are still lower than tokenized models in wall‑clock time. |

Below is a quick take on how researchers might tackle each of these directions.

## 1. Learn Patch Boundaries End‑to‑End

### Treat patches as latent variables
Instead of precomputing entropy thresholds, introduce a small *boundary predictor* that takes the current hidden state (or a lightweight MLP over byte embeddings) and outputs a Bernoulli probability of starting a new patch. During training this becomes part of back‑propagation and can be regularised so that patches stay roughly balanced in length.

### Supervise with pseudo‑tokens
A weak supervisory signal can come from an existing tokenizer. For example, use the BPE tokenizer as a teacher: when its segments disagree with BjER's proposed segment, add a penalty term encouraging similarity. This would guide the model toward linguistically meaningful boundaries without freezing them.

### Keep inference incremental
Because generation must decide on patch boundaries *without seeing future bytes*, any learned predictor must be strictly causal. A possible solution is to run a single lightweight RNN over the byte stream to output boundary probabilities online – similar to how BPE tokenization can be accelerated on GPUs by restricting lookahead.

## 2. Derive New Scaling Laws for Patchy LLMs

### Empirically sweep model size vs. compute budget
Run controlled experiments where you vary only three axes: total parameters \(P\), total training flops \(F\), and average patch size \(\bar{s}\). Measure BPB on held‐out data and fit multivariate power laws:
\[
\text{BPB} = \alpha\, P^{-\beta}\, F^{-\gamma}\,\bar{s}^{-\delta}.
\]
The exponents \(\beta,\gamma,\delta\) will reveal how much saving comes from larger patches versus deeper networks.

### Consider specialization of lost compute
In tokenized models compute loss mainly goes to large projection layers over vocabularies of size \(V\). In BLT large compute comes from running the local encoder/decoder on every byte—even when patches are long. Understanding where this loss can be transferred (e.g., using ISA optimisations on integer arithmetic) could adjust the exponent \(\delta\).

## 3. Architecture at Extreme Scale

### Revisiting local–global split
As seen in ablations, one encoder layer is enough at 1 B parameters but an 8 B model may benefit from several helper layers (both encoder and decoder). One hypothesis: having *two* separate attention modes—short‐range binary attention within patches and long-range causal attention over patches—could allow more efficient gradient flow.

### Hierarchical encoders
Instead of encoding each patch with one transformer layer then feeding into the latent transformer, chain multiple levels: binary subpatches → patch → document chunk → global transformer. This mirrors how MegaByte used an hourglass structure but can be augmented with cross‑attention across levels.

### Recompute strategies
Because many bytes are processed only by small linear maps in local modules, applying *recomputation* tricks could reduce peak memory without inflating FLOPs much—important when scaling up compute budgets.

## 4. Dedicated Hardware Acceleration

### GPU kernel design
At present FlashAttention handles block causal masks efficiently but cannot deal with arbitrary dynamic masks without overhead. Custom CUDA kernels or Triton scripts that fuse:
- Cross‐attention per patch,
- Byte padding/ truncation,
- Temporal batching across patches,
could realise significant speedups.

### FPGA / ASIC considerations
BLT’s regularity within each patch (local mask window \(w_\mathcal{E}\)) would allow tiling on an FPGA fabric while keeping lateral connections sparse between patches—a natural fit for systolic arrays designed to process streaming sequences.

### Optimizing mixed precision
Because patches contain fewer tokens than raw bytes, local layers may benefit from less aggressive quantization (e.g., 8 bit weights only for crosses between bytes & patches) while still keeping global layers at FP16 or BF16.

---

## Imagining Next-Generation Byte Models

What we see emerging from these research paths is not merely “larger byte LLMs” but entirely new **character–centric** architectures:

1. **“Edge” tokenizers** that learn boundaries while simultaneously emitting lower level predictors—a hybrid between classic BPE and learned segmentation.
2. **Programmable block transformers** where each block knows whether it should process characters or latent codes depending on context complexity.
3. **Hardware-software co-design** where GPU kernels natively support variable golden path lengths—an embedded irregular tensor network natively support variable sequence lengths per batch.
4. **Adaptive under-training**: because Byte models don’t have implicit vocabularies they can automatically incorporate new symbols into their representation space without retraining entire embeddings—a boon for multilingual open-vocabulary use.
5. **Robustness harnessed by design**: since every input is raw bytes every training sequence becomes inherently noise-resistant; adding small adversarial corruptions no longer corrupts token IDs.

The next few years could bring byte-level versions of GPT-4 or even Llama-like scales where tests such as FLOP-controlled scaling still show superior gains due to *dynamic compute allocation*. As benifits crystallise—for instance improved low-resource language support and better orthographic mastery—acceptance of such models may grow among developers who need truly open-span character understanding or robust handling of noisy data streams (chat logs, logs logs).  

> **Call to action:** If you’re building next-gen LLMs or working on hardware accelerators, keep an eye on BLT’s roadmap—especially its end-to-end boundary learning and novel scaling behaviour—as it might unlock new efficiencies both in cost and performance that token-based approaches struggle with today.
