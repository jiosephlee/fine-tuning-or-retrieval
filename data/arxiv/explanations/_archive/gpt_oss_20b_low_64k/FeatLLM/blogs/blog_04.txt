# Ensembling by Bagging Rules: Making LLMs Robust to Noise and Prompt Size Limits

Modern tabular data rarely come in tidy spreadsheets. They can contain dozens, even hundreds of columns, each with a different data type and an idiosyncratic meaning. When we try to hand–code a feature‑engineering workflow for such data, the task quickly becomes tedious and error‑prone. On top of that, many state‑of‑the‑art few‑shot learning systems use large language models (LLMs) at inference time, forcing every prediction to travel through a gigantic neural net. This is costly and, more importantly, violates the prompt‑size limits that LLM APIs impose.

The *FeatLLM* framework tackles both problems in one elegant move: **bagging** the data to build **ensembles of rule sets**. Below we unpack how this idea works, why it matters for noisy or high‑dimensional tabular sets, and what it means for real‑world deployments.

---

## 1. Why rules instead of raw features?

FeapLLM’s core idea is simple: let the LLM do the heavy lifting *once*—to derive a handful of interpretative *rules* that capture the relationship between features and the target label. For example, on a heart‑disease dataset the model might output:

> “Rule 1: *If age > 60 AND systolic blood pressure > 140 then risk = high.*”

Instead of training a deep network on raw columns, FeatLLM truncates these natural‑language conditions into binary features that indicate whether each rule applies to a given sample. Then a lightweight linear model learns how much each rule contributes to the final probability.

Advantages:

| **Reason** | **Conventional Approach** | **Rule‑Based FeatLLM** |
|------------|--------------------------|------------------------|
| Inference cost | Every sample runs a 175B parameter model | A tiny 2‑layer perceptron |
| Prompt size | Must serialize all columns per sample | Only the **few chosen columns** that sit inside each rule |
| Noise robustness | All columns influence logits directly | Only rules that survive filtering are learned |

So far so good… except when our dataset threatens to overflow an LLM’s token budget or riddles us with irrelevant features.

---

## 2. The problem of prompt size and spurious correlations

Large language models (GPT‑3.5, GPT‑4…) are great at **understanding context**, but only up to their native *context window*: ~4K tokens for GPT‑3.5-turbo/0613 and ~32K tokens for GPT‑4-turbo-1106 (depending on the API level). A tabular record with 200 numeric columns, each converted to a “`feature_i is value`” string, can easily burn through this budget.

Separately, tabular learning is notorious for picking up *spurious correlations*, especially in low‑shot settings where every single datapoint carries undue influence. An LLM that naively concatenates many columns will hallucinate rules that exploit noise rather than true signal.

Both challenges point to one solution: **reduce data per query without losing information**.

---

## 3. Bagging = random subsets; ensembles = averaging

### 3.1 How bagging works in FeatLLM

1. **Randomly sample K examples from the training set** (the few shots we have).  
2. **Randomly sample M column indices** (from the full feature set).  
3. Feed those K examples + M columns into an LLM query with a carefully crafted prompt (see next section).
4. Parse the returned “rules” into binary features for *all* samples in the dataset.
5. Train (or simply weight) a lightweight classifier on those binary features.
6. Repeat steps 1–5 T times → you get **T distinct models** each trained on different subsets of data/columns.

Notice: because each query contains only M columns, its text length is drastically shorter than if we fed all d columns at once.

### 3.2 Preventing prompt overflow

Suppose `d = 200`. If we can only fit `M = 20` columns without hitting token limits, each query focuses on a *subset* of possible relationships (e.g., age vs blood pressure vs cholesterol). Over T=20 iterations you end up covering all columns multiple times but never exceed context limits in any single run.

This strategy is analogous to “feature bagging” in Random Forests: each tree sees only part of the attribute space and learns its own weak hypothesis which we later ensemble.

### 3.3 Mitigating spurious correlations

Because each subset contains a random mix of potentially noisy and informative columns, many *spurious* rules will be generated across ensembles but are unlikely to:
- Appear consistently across many bagged models.
- Receive high importance weights when training the linear wrapper.

During ensembling we average probabilities from all T models—this is essentially a *vote* by diverse rule sets that have seen different feature contexts. The net effect:

- Rules invented from truly predictive patterns show up repeatedly → higher summed weight.
- Noise‑only rules vanish as their contribution gets washed out by averaging.

Empirical studies on synthetic datasets where unrelated noise columns were injected show FeatLLM’s performance degrades far less than other baselines that process all features directly through an LLM or use classical tree ensembles alone.

## 4. Prompt design inside each bagged query

A key part of FeatLLM’s success is how it instructs the LLM to produce rules from sparse information:

1. **Basic info block** – task question (“Does this patient have high BP?”), column names + definitions (value type + short description), plus K serialized examples (“Feature X is …; Answer: Yes”).

2. **Reasoning instruction block** – two steps:
   - Step 1: Identify causal or statistically meaningful connections between features and target using *general knowledge*, not demos.
   - Step 2: Using demos & Step 1 insights, craft up to `R=10` explicit rules per class using concise syntactic templates (`if <condition> then class`).

3. **Response format block** – enforce numbered list with `<condition>` expressed using standard operators (`>`, `<`, `==`) so parsing can be deterministic.

The reasoning instruction gives the LLM room to apply its world knowledge while keeping focus away from idiosyncratic noise in special columns—a real boon when dealing with domain‐specific jargon that might otherwise mislead raw feature embeddings.

## 5. Setting it up step by step

Below is an annotated pseudocode sketch illustrating one bagged iteration:

```python
def bagged_iteration(data, feature_defs):
    # Random subsets
    shots = random.sample(data.train_samples, K)          # e.g., K=4
    cols   = random.sample(range(len(feature_defs)), M)   # e.g., M=20

    cfg = {
        'shots': shots,
        'cols': cols,
        'feature_defs': [feature_defs[i] for i in cols]
    }

    prompt = build_prompt(cfg)
    response = llm_generate(prompt,
                            temperature=0.5,
                            max_tokens=512)

    rules = parse_rules(response)
    binary_features = generate_binary_features(data.all_samples, rules)

    # Linear weight learning / inference
    w = train_linear_weights(binary_features[shots], y[shots])
    probs = softmax(binary_features @ np.maximum(w,0))
    return probs
```

Running this loop `T` times gives you an array of probability maps which you simply average for final predictions.

## 6. Real-world implications

### 6.1 Lower cost & latency
- Once training finished (a handful of API calls), inference involves only simple matrix multiplications.
- No per‐sample LLM routing → dramatic savings on compute credits or API calls (especially valuable with paid GPT APIs).

### 6.2 Scalability
- Works seamlessly with high-dimensional datasets (`d > 200`) because each query uses only `M` columns.
- If your corporate dataset grows over time, you can retrain FeatLLM faster thanks to its lightweight downstream learner.

### 6.3 Interpretability
- Each rule is human-readable; you can audit which conditions matter most via learned weights.
- Lawful compliance audits become easier compared to blackbox deep nets trained directly on raw tables.

### 6.4 Robustness
- Real datasets often possess hidden biases or stray engineered variables.
- Bagging+ensembling tends to dilute contamination from isolated spurious features—leading methodology for industry deployments where label noise cannot be avoided entirely.

## 7. Takeaway checklist

| ✅ | What does FeatLLM do differently? |
|----|-----------------------------------|
| Use LLMs as day‑one feature engineers → rules instead of raw numbers |
| Apply two-step reasoning prompt → leverages prior knowledge before seeing data |
| Generate multiple rule sets via bagging → each covers different feature subsets |
| Adaptively limit prompt length | Only M relevant columns per query |
| Ensemble simple linear models → low latency prediction |
| Naturally filter out noisy correlations | Cross-model consistency boosts signal |

If you’re building a low‑shot tabular predictor and want to keep costs low while staying robust against noisy data and API token limits, give this bagged–rule ensemble approach a try!
