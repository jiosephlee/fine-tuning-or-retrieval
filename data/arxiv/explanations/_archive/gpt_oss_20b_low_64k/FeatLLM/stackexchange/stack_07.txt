\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### What is the justification for applying a ReLU-like maximum on weights in Eq. (1)?
Question:
$w_k$ are trained weights applied to binary rule features, and they project them into non‑negative space using $	ext{max}(w_k,0)$. Why not allow negative weights? How does enforcing non‑negativity help with interpretability or prevent negative influence from noisy rules?
Answer:
In the FeatLLM pipeline the rules generated by the LLM are turned into binary features \(z_k^i\in\{0,1\}^R\).  
To map these binary features to a class score a very light‑weight linear model is trained:

\[
\text{logit}_k^i=\max(\mathbf{w}_k,0)\!\cdot\! \mathbf{z}_k^i ,\qquad 
\mathbf{p}^i=\text{Softmax}\bigl([\text{logit}_1^i,\dots ,\text{logit}_c^i]\bigr).
\]

The authors explicitly state that the weights are “projected into a positive subspace, **to ensure that the features generated by the LLM do not reduce the likelihood of a class during learning**” (Section 3.3).  The rationale behind this design choice can be unpacked in three ways:

1. **Interpretability of rule contributions**  
   Each component of \(\mathbf{z}_k^i\) indicates whether a particular rule is satisfied.  A positive weight means that satisfying that rule can only increase – never decrease – the evidence for class \(k\).  If negative weights were allowed, a rule that happens to fire would lower the score for its own class, which would be counter‑intuitive from an interpretability standpoint: rules are intended to *support* a decision rather than *negate* it.  The non‑negative restriction makes it straightforward to read off that a high weight signals an “important” or “reliable” rule.

2. **Robustness against noisy or spurious rules**  
   In low‑shot regimes many generated rules are either weakly informative or purely coincidental.  Allowing negative weights gives the optimization routine too much freedom: it could learn to penalize seemingly useful rules if they happen to fire in the few training examples, simply because doing so reduces loss locally.  This is especially risky when some rules are irrelevant but happen to coincide with removed training samples; a negative weight could then push the model toward an unintended bias.  Constraining weights to be non‑negative ensures that only *supportive* evidence matters and any irrelevant rule will be weighted down to zero rather than given a negative influence.

3. **Stability of learning with highly sparse inputs**  
   The binary feature vector is extremely sparse (most entries are zero).  In such a setting, estimating both positive and negative parameters with very few samples is statistically ill‑posed: the optimiser may drift arbitrarily in either direction because many rules are never triggered in the observed data.  Non‑negativity turns the problem into a simpler non‑negative least‑squares / logistic regression, which has a unique optimum and reduces variance during training.

Empirically, the ablation study in Table 5 confirms that removing this “tuning” step (which includes applying \(\max(\cdot,0)\)) leads to noticeable performance deterioration across all datasets—especially when shots increase and more accurate weight estimation is possible (Table 5 discussion). This reflects exactly what we expect from an optimisation that allows both signs: it can overfit noisy signals and reduce overall predictive power.

For those familiar with classical ensemble methods such as boosting or additive tree models, one can also view non‑negative weights as analogous to additive contributions: each accepted rule adds evidence for its class, mirroring how tree ensembles add leaf node scores without subtracting from other classes.

In short, projecting the learnable weights onto \([0,\infty)\) is not an arbitrary regularisation trick; it is engineered so that:

- every rule’s contribution can be interpreted as *favouring* its associated class,
- noisy or accidental rule firings cannot corrupt predictions by reversing their effect,
- learning remains stable in a highly low‐shot environment where feature supports are sparse.

All these considerations align with FeatLLM’s broader goal of leveraging LLM prior knowledge while keeping downstream computation minimal and robust.
