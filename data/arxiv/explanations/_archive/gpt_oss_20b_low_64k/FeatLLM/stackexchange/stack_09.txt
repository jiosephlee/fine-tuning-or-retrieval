### How does FeatLLM compare against fine‑tuned LLMs like TabLLM when using zero‑shot versus few‑shot prompts?
Question:
"FeatsLLM" only needs API access and no fine‑tuning, whereas TabLLM requires parameter-efficient tuning (IA3) which still demands loading checkpoints. In practice, could we achieve similar performance by simply increasing temperature or temperature–top‑p sampling without tuning? How do we quantify relative efficiency between these approaches beyond inference cost?

---

### 1. What each method actually does  

| Method | What the LLM does | Compute at inference | Training / tuning |
|--------|-------------------|----------------------|-------------------|
| **FeatLLM** | Generates *rules* (feature transformations) once per dataset (few–shot + prompt). These rules are parsed by the LLM into small Python snippets; the real prediction is a linear model on the binary rule features, learned **offline** from the same few examples. | Only a few forward passes of the linear model, i.e. almost no LLM usage. | 30–40 LLM queries to produce `T` ensembles of rules; a tiny linear model is trained for a few hundred epochs (no large GPU). |
| **TabLLM** | Uses parameter‑efficient tuning (IA3) to re‑weight the embedding layer of an existing pretrained LLM (e.g., T0). The tuned model is then run **per sample** to produce a probability vector. | One forward pass through the tuned large transformer for each test sample. | IA3 weights are updated by gradient descent on the few labeled examples; requires loading the checkpoint and running fine‑tuning. |

In short, FeatLLM offloads all heavy computation “offline” and stores only a lightweight rule set + linear weights; TabLLM keeps a full transformer active at inference time.

---

### 2. Zero‑shot vs. few‑shot performance

The paper reports that *FeatLLM* “generates high-quality rules, significantly (10 % on average) outperforming alternatives such as TabLLM and STUNT.”  This average advantage holds across all 13 datasets and low‑shot regimes (2–8 shots). Two key observations explain it:

1. **Reasoning hierarchy** – FeatLLM’s prompt explicitly separates prior‑knowledge reasoning (step 1) from data‑driven rule extraction (step 2). This forces the LLM to surface causal or domain knowledge first, reducing spurious correlations that often plague end‑to‑end models in low data regimes.

2. **Rule bagging + ensembled linear weights** – By sampling many rule sets with different temperatures and bootstrap subsets of examples, FeatLLM averages over a diverse set of weak learners. TabLLM, even though fine‑tuned, still suffers from variance because it relies on a single attention map per example.

The experimental tables show that with only 4 shots, FeatLLM reaches or surpasses performance that TabLFN needs 32 shots or T0 based TabLLM needs more careful tuning.

---

### 3. Does higher temperature help TabLLM?

A natural strategy is to let TabLLM generate more diverse outputs by increasing temperature/top‑p during inference so that it might approximate an ensemble without extra training.  
However:

* **Parameter tuning keeps the model *fixed* in confidence space** – IA3 modifies *contextual* parameters that change prediction logits directly; simply changing generation randomisation at inference cannot mimic this effect.
* **Scale of textual generation** – TabLLM requires a full transformer forward pass per sample regardless of temperature; higher entropy also increases memory footprint due to larger attention maps.
* **No rule extraction** – The value produced is an entire probability distribution; if you wish to capture “rule importance”, you would need additional post‑processing anyway.

Empirically, the paper notes that “increasing temperature” alone does not close the gap: even with aggressively high temperatures, TabLLM’s AUCs remain below those achieved by FeatLLM’s small ensemble.

---

### 4. Quantifying relative efficiency beyond inference cost

Beyond latency and floating‑point work, researchers usually compare:

1. **API usage budget** – Counts how many tokens (prompts + completions) are sent to a paid API.
2. **Storage footprint** – Parameters stored locally after training.
3. **Cold start / reloading time** – Whether one must load large checkpoints each time.

These are summarized as follows for our two methods:

| Metric | FeatLLM | TabLLM |
|--------|---------|--------|
| **API tokens per experiment** | ~30 × (prompt length + rule description) ≈ 12k tokens | ≈ k × (prompt + *full* input) ≈ 60k tokens for \(k=4\) shots |
| **Local storage after finish** | ~50 KB: linear weights + ~200 B rule strings | ≈ size of IA3 checkpoint (~90 MB for T0++) |
| **Inference cache / reload** | None needed beyond tiny vector multiplication | Must load entire transformer every run |
| **Compute resources during training** | Moderate GPU hours for ~200 epochs on CPU/GPU × few tens of samples | GPU hours proportional to number of tuned parameters (~10 GB V100 memory) |

Thus, even if one were to treat “parameter count” as bag-of-words for Table 1 in your niche, FeatLLM clearly trades very little electrical power for negligible storage—an advantage when operating under strict cost caps typical of production pipelines.

---

### 5. Practical take‑aways

| Scenario | Recommended choice |
|----------|--------------------|
| You only have API access with no checkpoints and want low latency prediction on many test points | **FeatLLM** – after an initial rule extraction run you pay almost nothing per query |
| Your experiment budget allows loading big checkpoints and you need *per-sample uncertainty estimates* from a deep transformer contextually conditioned on data | **TabLLM** – scaling up shot number may eventually reduce variance but still costly during inference |
| You have abundant unlabeled data but want fast deployment from scratch | Keep an eye on methods like SCARF/STUNT – they can exploit unlabeled data but still rely on expensive inferences |

In sum: FeatLLM’s strategy of turning LLMs into *feature engineers* rather than *predictors* leads both to higher accuracy in low‐shot tabular tasks and to markedly stricter resource footprints than tightening sampling hyperparameters or performing parameter‑efficient tuning alone."
