\title{A Textbook about the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

Chapter 2: # 2. The Baseline: FlashAttention‑2

The FlashAttention line of work provides a concrete blueprint for accelerating the core self‑attention computation of large sequence models on contemporary GPUs.  It tackles the quadratic complexity in both time and memory that arises from forming the full key–value interaction matrix \(\mathbf{S}=\mathbf{Q}\mathbf{K}^\top\).  By tiling both latent and query dimensions and fusing all intermediate operations into a single CUDA kernel, FlashAttention‑2 eliminates expensive global‑memory traffic that would otherwise dominate performance.  Yet, despite these clever optimisations, the latest generation of NVIDIA GPUs – Hopper (H100) – still shows a noticeable gap between the theoretical throughput of dedicated Tensor‑Core units and the actual utilisation achieved by the algorithm.  In this chapter we trace the evolution from naive implementations to FlashAttention 2, exposing each design decision that offers speed, and then identify specific shortcomings that motivate the proposed FlashAttention 3.

## 2.1 From naïve attention to tensor‑core kernels

### Naïve implementation

A straightforward GPU implementation of self‑attention first materialises the score matrix \(\mathbf{S}\) and subsequently stores it in high‑bandwidth DRAM (HBM).  For head dimension \(d\) and sequence length \(N\), this requires \(\Theta(N^2d)\) multiply–accumulates and \(\Theta(N^2)\) floating‑point elements in memory.  The three stages

1. **Score matrix generation**: \(\mathbf{S} = \alpha\,\mathbf{Q}\mathbf{K}^\top\).
2. **Softmax**: \(\mathbf{P} = \mathrm{softmax}(\mathbf{S})\).
3. **Value aggregation**: \(\mathbf{O} = \mathbf{P}\mathbf{V}\).

force a **global memory ping‑pong**: scores are written to DRAM, softmax reads them back, writes probabilities back, then value multiplication reads again.  Even with aggressively scheduled streams, this approach quickly saturates global memory bandwidth on long sequences because \(N^2\) dominates.

### Early GPU acceleration attempts

A first optimisation is to move all arithmetic onto dedicated tensor cores: express score generation as a single gemm and value aggregation as another gemm.  Modern GPUs expose specialised SIMD instructions (e.g., NVIDIA’s WMMA or WGMMA for Hopper) that can perform thousands of multiply–accumulates per cycle when all operands are contiguous in memory.  Yet, unless one can remove intermediate writes to global memory, these tensor cores cannot be fully utilised.  The bottleneck becomes **memory traffic**, not compute.

### The blockwise tiling idea

The key observation is that each query vector interacts only with a *local* chunk of keys (a block of size \(B_c\)).  If we process queries in blocks of size \(B_r\), we can compute partial scores \(S^{(j)} = \mathbf{Q}_i\,\mathbf{K}_j^\top\) for each key block \(j\) incrementally:

- Load query block \(\mathbf{Q}_i\) once into shared memory.
- For every key block \(j\), load \(\mathbf{K}_j,\mathbf{V}_j\) into shared memory.
- Compute partial score matrix \(S_i^{(j)}\).
- Update running softmax statistics (row maxima, sum).
- Accumulate partial outputs.

Because only one key block resides in shared memory at any time, every matrix multiplication accesses registers or shared memory rather than global memory, which eliminates the score write–read ping‑pong.

This *blockwise* formulation forms the backbone of FlashAttention 2’s acceleration strategy.

## 2.2 The local softmax fusion technique

### Conventional softmax pipeline

Standard practice first computes a **full** score matrix before performing any reduction across rows (to obtain row maxima or sums for normalisation).  This full matrix occupies gigabytes for long sequences; it cannot fit in shared memory and forces two global‑memory passes for reduction.

### Local softmax extension

FlashAttention 2 introduces a *local* version of softmax that can be done inside each tile without ever materialising the full score matrix:

1. **Per‑block max**: For every partial score matrix \(S_i^{(j)}\), compute its row maxima.
2. **Running maximum update**: Maintain an array \(m_i\) storing the running maximum per row across processed blocks.
3. **Exponentiation & sum**: Compute exponentials \(\exp(S_i^{(j)} - m_i)\) on-the-fly while accumulating row sums into an auxiliary vector \(\ell_i\).
4. **Rescaling**: During value aggregation (\(O=\tilde P\,V_j+R^{-1}O_{\text{prev}}\)) use the current running maximum to rescale previously accumulated output by a factor of
   \[
   R_i = \exp(m_i^{(old)} - m_i).
   \]
   This keeps intermediate values properly normalised without explicitly forming probabilities.

Thus all operations that traditionally produced large intermediate matrices are now performed per block entirely in registers or shared memory; only the final output and per‑row log‑sum‐exponential (\(L_i=m_i+\log(\ell_i)\)) are written back to HBM.

### Correctness intuition 

The multiplicative‐rescaling trick relies on the identity
\[
e^{a-b}\,\Bigl(e^{c-b} + e^{d-b}\Bigr)
=
e^{a-c}\Bigl(e^{c-d}+e^{c-c}\Bigr),
\]
which ensures that scaling by a factor computed from old maxima does not disturb later exponentiations as long as we keep track of cumulative sums accurately.  A careful proof is given in subsequent sections but intuitively the algorithm is equivalent to computing probabilities row-wise with full batch normalisation because row maxima encode exactly which term dominates each exponential.

## 2.3 Parallelisation over query/sequence dimensions in FlashAttention‑2

FlashAttention 2 boosts parallelism by dedicating one CUDA threadblock per tuple \((i,b)\), where:

- \(i\) indexes blocks along the *query* dimension (\(T_r = \lceil N/B_r\rceil\)).
- \(b\) indexes blocks along the *key/value* dimension (\(T_c = \lceil N/B_c\rceil\)).

Within each threadblock, a warpgroup loads a query block once into shared memory while another warpgroup streams key/value blocks one by one through TMA (Tensor Memory Accelerator).  

Because all required data for a given pair \((i,b)\) reside on-chip during execution, there is *no* need for transactions on HBM except at entry/exit points:

- The query block is loaded once.
- Each key/value block is streamed once.
- Each output fragment is streamed back once after accumulation.

This design yields high occupancy intrinsically: every SM handles multiple query blocks concurrently thanks to warp scheduling; further scaling comes from parallelism across heads (*nheads*) and batch (*b*).  The result is an algorithm where compute density (operations per byte transferred) far exceeds typical software implementations.

Nevertheless, FlashAttention 2 still represents an *asymmetric* use of hardware resources: Tensor Cores perform matrix multiplies at very high throughput but have relatively low latency for other ops such as exponentials needed for softmax; overlapping these events was not inherent to the design.

## 2.4 Performance gaps on Hopper GPUs: occupancy vs. matrix‑multiplication kernels

On recent GPUs such as Hopper (H100), performance measurements show that FlashAttention 2 attains only around 35 % utilisation of peak GFLOPs when compared to dedicated GEMM kernels that fully exercise Tensor Cores under optimal conditions (~80–90 %).  Two distinct contributors explain this gap:

1. **Instruction-level stalling** – In FlashAttention 2 every iteration involves:
   - A *score* GEMM using WGMMA.
   - A softmax argument involving exponential and addition performed by a different hardware unit (the special-function unit).
   - A *value* GEMM using WGMMA again.
   These three interleaved phases are strictly sequential within a loop iteration; thus Tensor Cores engage only in fractions of cycles while other units idle waiting for data or results.
   
2. **Register pressure & scheduling overhead** – Warpgroups responsible for loading data via TMA use many registers for staging buffers; meanwhile tensor-core warps also consume significant register space due to operands held in registers across iterations.  Compiler reordering and barrier insertion add additional overheads—especially in hops where negotiations between warps must synchronize across SM.

Because Hopper introduces true *asynchrony*—both TMA and WGMMA can run concurrently with other warps—there exists untapped potential if Warp groups could exchange duties more aggressively than they currently do.

## 2.5 Summary of open questions for higher utilisation

At this baseline stage several gaps remain open:

| Open Question | Why it Matters | Possible Direction |
|---------------|----------------|--------------------|
| Can we hide softmax latency behind concurrent GEMM? | Exponentials are orders-of-magnitude slower than Tensor Core multiplication | Overlap compute-step by pipeline-mesh / warp-specialization |
| What hardware units are underutilised? | TMA stalls waiting for producer waves | Producer-consumer specialization with FIFO shared-memory buffers |
| How to leverage new FP8 support? | FP8 doubles throughput but has stricter layout constraints | Block quantisation + layout-aware WGMMAs |
| Can we form larger work‐groups efficiently? | Larger TILE sizes reduce kernel launch overheads but increase register pressure | Persistent kernels + dynamic register reallocation |
| How does causal masking affect parallelism? | Masking breaks symmetry between queries/key blocks | Dynamic scheduling alternating mask coherence |

Answering these questions formed the motivation behind FlashAttention‐3’s new contributions—producer–consumer asynchronous overlap via warp-specialization, an intra-warpvector GEMM/softmax pipeline that hides special function latency under WGMMA execution, and an FP8 extension built around layout-aware quantisation schemes—culminating in an algorithm capable of utilising up to ~75 % of Hopper’s peak arithmetic capability while preserving exact numerical accuracy over standard implementations.
