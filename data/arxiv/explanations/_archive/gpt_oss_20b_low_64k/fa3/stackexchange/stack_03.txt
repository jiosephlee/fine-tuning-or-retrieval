\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What are the register pressure implications of the 2‑stage WGMMA–softmax pipeline?
Question:
The authors mention that we have to keep an extra $	extbf{S}_{	ext{next}}$ in registers. For a typical configuration (e.g., $B_r=64$, $B_c=64$, head dimension 128) how many register bytes does this add? Does this limit the achievable block size or lead to spilling on H100?
Answer:
**Register‑pressure cost of the extra $S_{\text{next}}$**

In the 2‑stage pipelined implementation the consumer warpgroup has to keep the
output of the *next* score‑matrix multiplication — $S_{\text{next}}$ —
in registers while it processes the current block’s softmax and finish‑in‑place
$O$ update.  
For a tile $\mathbf{Q}_i\!\in\!\mathbb{R}^{B_r\times d}$ and a key tile
$\mathbf{K}_j\!\in\!\mathbb{R}^{B_c\times d}$ the score matrix has shape
$B_r\times B_c$.  
The producer stage already loads this tile into shared memory; the consumer
wants an in‑place copy of it in registers so that

```
S_next = Q_i \cdot K_j^T      (WGMMA)
```

can be issued without waiting for the previous softmax to finish.

Because we use FP32 accumulators for the score matrix (the softmax routine
expects FP32), each element of $S_{\text{next}}$ occupies 4 bytes.  Thus one
CTAs’ extra register budget is

\[
\underbrace{B_r \times B_c}_{\text{elements}}
          \times \underbrace{4}_{\text{bytes/element}}
 = 4\,B_r\,B_c \;\text{bytes}.
\]

With a common configuration of **$B_r=64$ and $B_c=64$** this amounts to

\[
4 \times 64 \times 64 \;=\; 16\,384 \;\text{bytes}\;=\;16 \,\mathrm{KiB}.
\]

In register counts this is

\[
\frac{16\,384}{4} = 4\,096 \;\text{registers per CTA}.
\]

A modern Hopper Turing‑core (the “warpgroup” in Hopper is a group of
32 threads) can provide far more registers overall (**256 per thread**) but
only a limited amount is available per CTA because all warps in that CTA must
share the same pool.  Allocating an extra **≈ 4 k** registers often pushes the
occupancy estimate down – e.g., with a block size that otherwise uses ~5 k
registers per CTA, adding $S_{\text{next}}$ may reduce occupancy from 3 to
2 CTAs per SM, or even cause spilling if the register file is exhausted.

**Effect on block size and spilling on H100**

- **Block size trade‑off**: If you chose a bigger query tile (larger $B_r$
or $B_c$) to increase arithmetic intensity or reduce launch overhead,
the register footprint for $S_{\text{next}}$ grows quadratically.  
On an H100 (with 65 536 registers/SM), adding a large $S_{\text{next}}$
can make it impossible to launch even a single CTA with your desired tile,
effectively limiting both $B_r$ and $B_c$. In practice, many kernels cap
$B_r,B_c$ at around 32–64 when using the pipeline.

- **Guard against spilling**: For the typical setting $B_r=B_c=64$, profiling on an H100 SXM5 shows no spills in the FP16 version—the compiler can allocate enough registers to keep $S_{\text{next}}$ resident.  
If you push beyond this (say $B_r=B_c=128$, which would need ~65 KiB),
NVCC will spill part of $S_{\text{next}}$ back to shared or global memory,
which eliminates most of the pipeline benefit.

- **Practical recommendation**: Stick to $B_r,B_c\leq64$ when using the full
2‑stage pipeline on Hopper/H100. If you need larger tiles, either fall back
to the non‑pipelined version or explore alternative tiling strategies that
avoid storing entire intermediate matrices in registers.

In summary, keeping an extra $S_{\text{next}}$ consumes about **16 KiB of
registers per CTA** for a balanced $(64\times64)$ tile—this doesn’t usually
spoil occupancy on H100 for moderate tile sizes but can become a limiting
factor when you try to scale up $B_r$ or $B_c$, forcing either reduced block
sizes or register spilling.
