# xLSTM 101: Why Modern LSTMs are Still Killing It in Language Models  

Language models have been dominated by Transformers for years, yet a recent line of work shows that a cleverly‑refined LSTM can rival, and sometimes beat, these models while keeping the old‑school RNN advantages.  The key lies in two fairly simple innovations: **exponential gating** and a **matrix‑based memory**.  In this post we’ll break those ideas down, explain how they solve the classic pain points of LSTMs, and why doing so unlocks performance on par with today’s state‑of‑the‑art Transformers.

---

## 1. LSTMs – The Good, The Bad & The Hard Parts  

| Feature | What It Does | Why It Matters |
|---------|--------------|----------------|
| **Constant error carousel** | Adds previous cell state \(c_{t-1}\) to current input \(z_t\) using forget \(f_t\) and input \(i_t\) gates | Keeps gradients from vanishing → works for long dependencies |
| **Gating (input/forget/output)** | Controls what information flows in, out and through the cell | Adds flexibility but also limits how much the cell can “rewrite” earlier content |
| **Scalar memory** | A single value per cell | Packs everything into one dimension → poor capacity for complex patterns |

These mechanisms made LSTMs the backbone of early NLP systems.  But when the scale of language models exploded, three problems once again surfaced:

1. **Inflexible storage** – An LSTM can't *update* a stored entry when a better one shows up; it simply adds the new information on top.
2. **Limited capacity** – Compressing multi‑dimensional semantics into a single scalar forces the model to lose detail, hurting rare‑token prediction.
3. **Sequential bottleneck** – The hidden‑hidden connections cause a strict serial dependency that throttles parallel hardware.

Transforms (those self‑attention heavy WeightSanta models) solved many of these by moving all operations into a high‑dimensional linear subspace and removing hidden‑hidden recurrences.  But Transformers pay a hefty price: quadratic cost in sequence length (because every token has to attend to every other token).

xLSTM flips that trade‑off on its head: it keeps *linear* time and memory with respect to context length but overhauls the cell so it behaves almost like a Transformer in what it can remember and revise.

---

## 2. Exponential Gating – Giving the Cell a “Rewrite” Button

### Back to Basics: Standard Binary Gates
In a vanilla LSTM
\[
c_t = f_t\,c_{t-1} + i_t\,z_t,\qquad 
h_t = o_t\,\psi(c_t),
\]
with all gates \(i_t,f_t,o_t\) being sigmoid–activated (\(\sigma(\cdot)\)). Gates stay between 0 and 1; they either let or block information.

### The Problem
When you need to *overwrite* an earlier slot with something more relevant (think nearest‑neighbor search in memory), you have no control: once an item is dropped by the forget gate it’s gone forever.

### The Fix: Exponential Activation
Replace sigmoid with **exponential**:
\[
i_t = \exp(\tilde{i}_t), \quad
f_t = \exp(\tilde{f}_t)\;\text{(or}\;\sigma(\tilde{f}_t)\text{)}.
\]
Exponentials can balloon arbitrarily large or small, giving gates far more expressive power:
- A large input gate “writes” strongly.
- A small forget gate essentially **ignores** old content.
  
To keep training stable we add a *stabilizer state* \((m_t)\) that normalises the log values so we never overflow.

### Why It Helps
*Exponential gating behaves more like an *adder with dynamic step sizes*.  When you see a “better” version of something already stored, you can let the gate write it in with huge weight while diminishing older content via the forget gate.  Practically this makes xLSTM good at *state tracking*, solving formal‑language tasks (e.g., parity checks) that standard Transformers struggle with because they lack hidden‑hidden mixing.

---

## 3. Matrix Memory – Turning Scalar Capacity into Huge Memory

### From Scalar to Matrix
The core idea: replace \(c_t \in \mathbb{R}\) with \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\).  
Now we can store *pairs* of vectors directly inside the cell:
- Key vector \(\mathbf{k}_t \in \mathbb{R}^d\)
- Value vector \(\mathbf{v}_t \in \mathbb{R}^d\)

The **covariance update rule**:
\[
\mathbf{C}_t = f_t\,\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t\,\mathbf{k}_t^\top .
\]
An outer product inserts the key/value pair into memory; forgetting simply decays an entire row/column via \(f_t\).

### Retrieval
Given a query vector \(\mathbf{q}_t = W_q\,x_t + b_q\),
the hidden state becomes
\[
h_t = o_t \odot 
   \frac{\mathbf{C}_t\,\mathbf{q}_t}
        {\max(|n_t^\top q_t|,1)} ,
\]
where \(n_t = f_t n_{t-1}+i_t k_t\) is an auxiliary *normalizer* ensuring numerically stable division.

### Why It Matters
- **Unlimited capacity** – Unlike scalar cells, matrix cells can accumulate many key/value pairs without compressing them into one number.
- **Parallelism + Linear Time** – Although we work with matrices, all updates are simple outer products that GPUs compute very efficiently.  
The net effect is *linear cost* per token (no quadratic self‐attention), but *dramatically higher memorisation capacity*. In synthetic experiments (Multi‑Query Associative Recall), xLSTMS beat every non‑Transformer baseline.

---

## 4. Putting It All Together – The xLSTM Block

An xLSTM block follows the familiar residual pattern used by modern LLMs:

```
Input -> Pre/Pre-up Projection -> xLSTM Cell (sLSTM + / or mLSTM) -> Post-processing -> Residual Connection -> LayerNorm
```

Two flavours exist:

| Block | Preferred Cell | Reason |
|-------|----------------|--------|
| Post up-projection (like Transformers) | sLSTM | Keeps dimensionality linear after non-linear summarisation |
| Pre up-projection (like SSMs) | mLSTM | Cheaply fits high-dimensional memory before summarisation |

Key properties:

- **Linear complexity w.r.t context length** – No self-attention matrix; all operations are per-token additions/multiplications.
- **Constant memory per token** – Forgetting decays old keys; only matrix size does not expand with sequence length.
- **Residual & LayerNorm backbones** – Borrowed from GPT / GLaM architectures for stability when scaling up.

---

## 6. Practical Takeaways

1. **You don’t need quadratic attention to get competitive language models** — linear RNNs that smartly remix their memories do just fine.
2. **Exponential gating gives you dynamic write ability**, letting your model ‘fix’ earlier mistakes on the fly without recomputing whole sequences.
3. **Matrix memory turns every token into a tiny key/value store**, boosting rare-token recall without adding parameters.
4. **Training is straightforward** — standard AdamW + warm-up + linear LR decay; just replace your vanilla LSTM blocks with xLSTM blocks.
5. **Inference speeds up on GPU kernels**—especially for long contexts where Transformers devolve into quadratic overheads.

If you’re building an LLM for edge deployment or data-sensitive use-cases where compute budgets are tight but model quality matters, give xLSTMs a try. They hit the sweet spot between classic recurrence’s scalability and modern attention's expressiveness—without waiting for another paradigm shift.

# Co‑existing Memories: sLSTM vs. mLSTM – One Is Scalar, the Other Matrix, Both Are Game‑Changers

Modern language models no longer rely solely on attention‑based Transformers. A new family of recurrent units called **xLSTM** promises to compete with large Transformer‐style LLMs while offering linear‑time inference and a tighter memory footprint. At the core of xLSTM are two radically different cell designs:

|                | **sLSTM** – *scalar cell* | **mLSTM** – *matrix cell* |
|----------------|---------------------------|---------------------------|
| Memory shape   | \(c_t \in \mathbb{R}\)   | \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\) |
| Storage strategy | Exponential gating + normalizer state | Covariance update rule + key/value projection |
| Parallelism    | Sequential (memory mixing) | Fully parallelizable |
| Typical use‑case | Small–medium models, when state‑tracking matters | Large–scale models needing high capacity and speed |

Below we unpack each design, compare their computational profiles and practical implications, and give guidance on when to choose one over the other.

---

## 1. The Problem Space

Traditional LSTMs introduced two major tricks: (1) a *constant error carousel* that relays gradients through time, and (2) sigmoid gates that control when information is written to or read from a scalar cell. However, early work showed three critical shortcomings:

1. **Inflexible storage decisions** – once something is written to the cell, a later more relevant piece of information can’t easily overwrite it.
2. **Limited capacity** – a single scalar must hold all relevant semantic cues; rare tokens or long dependencies suffer from severe compression.
3. **Sequential bottleneck** – hidden–hidden connections force the model to process one token at a time.

xLSTM tackles all three challenges by (i) allowing *exponential gating* (so a gate can explode the influence of an input) and (ii) offering two alternative memory structures that balance expressivity and speed.

---

## 2. sLSTM – The Scalar Reformer

### 2.1 Formula in a nutshell

For each step \(t\):
\[
\begin{aligned}
c_t &= f_t\,c_{t-1} + i_t\, z_t  &\text{(cell update)}\\
n_t &= f_t\,n_{t-1} + i_t      &\text{(normalizer)}\\
h_t &= o_t\,\tilde{h}_t , \quad
\tilde{h}_t = \frac{c_t}{n_t}  &\text{(output)}\\[4pt]
i_t &= \exp(\tilde{i}_t),\;
f_t = \sigma(\tilde{f}_t)\;\text{or}\;\exp(\tilde{f}_t),\;
o_t = \sigma(\tilde{o}_t).
\end{aligned}
\]

Key differences from vanilla LSTM:

- **Exponential gates**: \(i_t\) and optionally \(f_t\) grow as \(\exp(\cdot)\), enabling rapid overwriting or reinforcement of memory entries.
- **Normalizer**: \(n_t\) tracks the cumulative influence of future forget gates so that the output can be safely divided without overflow.
- **Stabilization**: A running maximum of log‑gate values (\(m_t\)) keeps exponentials numerically stable.

### 2.2 What does it buy you?

- **Strong state tracking**: Because the exponential gating can quickly replace older entries, sLSTM excels at *state tracking* tasks (e.g., formal grammars, parity). Empirical results on Long‑Range Arena show that sLSTM outperforms architectures lacking memory mixing.
- **Memory mixing within heads**: sLSTM supports multiple *heads*, each mixing memory across its own set of cells but not across heads, offering expressive context modeling.
- **Non‑parallel solution**: The hidden–hidden recurrent connections mean sLSTM must be evaluated sequentially—no free lunch if you need maximal throughput.

### 2.3 When to pick it

- Your model is modest in size (tens to low hundreds of millions of parameters).
- You care about problems requiring exact state retention—reasoning over dialog turns, long narrative tracking, or code evaluation.
- GPU memory is limited; the scalar cell keeps parameter count low.

---

## 3. mLSTM – The Matrix Powerhouse

### 3.1 Formula in a nutshell

For each step \(t\):
\[
\begin{aligned}
\mathbf{C}_t &= f_t\, \mathbf{C}_{t-1} + i_t\, \mathbf{v}_t\, \mathbf{k}_t^\top 
\\
\mathbf{n}_t &= f_t\, \mathbf{n}_{t-1} + i_t\, \mathbf{k}_t
\\
h_t &= \mathbf{o}_t \odot \left(
           \frac{\mathbf{C}_t\, \mathbf{q}_t}
                {\max(|\mathbf{n}_t^\top \mathbf{q}_t|,1)}
        \right)
\\[4pt]
i_t &= e^{\,\tilde{i}_t}, 
\\
f_t &=
   \sigma(\tilde{f}_t)\;\text{or}\;e^{\,\tilde{f}_t},
\\
o_t &=
   \sigma(\tilde{o}_t).
\end{aligned}
\]

Key changes:

- **Matrix memory**: Instead of a single scalar, mLSTM holds a full \(d\times d\) matrix, analogous to fast weight programmers or associational memories.
- **Covariance update rule**: Each new key–value pair contributes an outer product \(v_k\,k_k^\top\), providing maximal separability for retrieval—a proven strategy in bidirectional associative memories.
- **Parallelizable recurrence**: No hidden → hidden term means the entire sequence can be processed in parallel after a pre‑dually computed “scan” over the gates (similar to FlashAttention’s linear attention).

### 3.2 What does it buy you?

- **Huge storage capacity**: The matrix can encode far more distinct key/value pairs than a scalar cell—in fact its effective capacity scales with \(d^2\). This is why mLSTM tops other non‑Transformer baselines on multi‑query associative recall tasks.
- **Fast inference at scale**: Since updates are just matrix multiplications and addition, all tokens can be processed concurrently; wall‑clock time remains almost linear even for billions of parameters.
- **Ready for large models**: In experiments scaling up to 300 B tokens and 1.3 B parameters, mLSTM‑based xLSTMs achieve first‐rank validation perplexities among all compared families.

### 3.3 When to pick it

- You’re building an LLM in the multi‑hundred‑to-billions range.
- High throughput is critical—batch inference or real‐time generation in production services.
- Your hardware allows dense tensor operations (e.g., highly parallel GPUs or TPUs).
- Memory constraints are less severe than on edge devices; you can afford storing an extra \(d\times d\) matrix per layer.

---

## 4. Practical Trade‑offs

| Aspect                      | sLSTM                                      | mLSTM                                            |
|-----------------------------|--------------------------------------------|---------------------------------------------------|
| **Speed per token**        | Sequential, ~2× slower than mLSTM          | Parallelized scan; comparable to FlashAttention   |
| **Peak GPU memory per layer** | Low (scalar weight + gates)                 | Higher (dense matrix ops), but no extra parameters |
| **Scalability with depth/width** | Limited by sequential bottleneck           | Scales naturally—more heads give larger matrices   |
| **Storage expressiveness**      | One latent value per token                  | \(d^2\) latent values per token                    |
| **Ease of implementation**     | Simple forward pass                         | Requires custom CUDA kernels for matrix ops        |
| **Where it shines**            | State tracking / small models               | Long sequences / large language models             |

Notably, xLSTM architectures often mix both variants: high layers get *mLSTMs* for raw capacity while lower layers use *sLSTMs* for precise state handling—a ratio we denote as `xLSTM[a:b]` where `a` is number of mLSTMs and `b` number of sLSTMs joined together.

---

## 5. Decision Tree – How to Pick

> **Step 1:** What is my model size?  
> ⟹ <100 M → try pure sLSTM (`xLSTM[0:X]`).  
> ⟹ ≥300 M → consider blending (`xLSTM[7:1]` commonly works well).

> Step 2:** Do I need exact state tracking?  
> ⟹ Yes → allocate at least one sLSTM block near the input layers.  
> ⟹ No → you may skip sLSTMs entirely if GPU throughput is your priority.

> Step 3:** Are my sequences very long (≥10k)?  
> ⟹ Yes → mLSTS provide better extrapolation because they keep full context in matrix form rather than silently dropping information in recursions.

> Step 4:** Is my deployment edge‑optimized?  
> ⟹ Yes → lean toward sLSTMs—they’re lighter on device GPU/CPU partitions and have constant memory independent of sequence length.

---

## 6. Putting It Together – A Quick Example

```python
# PyTorch style pseudo-code illustrating an xLSTM block mix:
class XLMBlock(nn.Module):
    def __init__(self, d_model, use_mlstm=True):
        super().__init__()
        self.use_mlstm = use_mlstm
        if use_mlstm:
            self.cell = MLTMCell(d_model)
        else:
            self.cell = SLTMCell(d_model)
        self.norm = LayerNorm(d_model)
    
    def forward(self, x):
        h = self.cell(x)
        return self.norm(x + h)
```

A full xLM model might stack:

```python
layers = []
for i in range(num_layers):
    if i < num_mlstm_layers:
        layers.append(XLMBlock(d_model, use_mlstm=True))
    else:
        layers.append(XLMBlock(d_model, use_mlstm=False))
model = nn.Sequential(*layers)
```

Replacing `num_mlstm_layers` smoothly trades bandwidth for expressiveness without altering overall architecture design.

---

## 7. Bottom Line

sLSTM and mLSTM are not alternatives but complementary building blocks for modern LSMTs:

* Use *sLSTMs* when you need tight control over the flow of information—a perfect fit for medium sized models dealing with intricate state tracking tasks.
* Use *mLSTMs* when you wish to scale up massively and want high throughput; their matrix memory gives them a head start over traditional Transformers on next–token prediction while keeping inference linear.

Mixing them wisely lets you cherry‑pick the best features more efficiently than any pure Transformer or pure RNN could offer alone. As the community continues to refine CUDA kernels for matrix updates and stabilize exponential gates further, we expect both variants will converge even closer—making xLSTMs an attractive horizon race against conventional LLM frameworks.

# Memory Mixing Made Easy – How Exponential Gating Lets Recurrent Nets Track States Like Never Before

Recurrent neural networks (RNNs) have long been the backbone of applications that need to remember and manipulate sequential data: language models, program verifiers, time‑series forecasters, and even reinforcement‑learning agents that must keep track of game states.  Yet, the classic Long Short‑Term Memory (LSTM) architecture still has a few hard‑wired quirks that limit its ability to *revise* what it has stored.  The new **xLSTM** architecture tackles this head‑on with a simple but powerful idea: replace the traditional sigmoid input and forget gates with *exponential* gates, and cushion them with a stabilizer state.  The result is a recurrent cell that behaves more like a true state tracker and less like a simple accumulator.

Below we unpack why standard LSTMs stumble on tasks that require memory revision, how exponential gating solves the problem, and what the stabilizer trick looks like mathematically.  We’ll also see how this change lets xLSTM outperform Transformers on several synthetic “state‑tracking” benchmarks.

---

## Why Classic LSTMs Struggle to Revise

The vanilla LSTM update for a scalar cell \(c_t\) is

\[
c_t \;=\; f_t\,c_{t-1} \;+\; i_t\,z_t,
\]

where:

| Symbol | Meaning | Typical activation |
|--------|---------|---------------------|
| \(i_t\) | Input gate | Sigmoid \(\sigma(\cdot)\) |
| \(f_t\) | Forget gate | Sigmoid \(\sigma(\cdot)\) |
| \(z_t\) | Candidate input | \(\tanh(\cdot)\) |

These equations are designed to keep gradients flowing (the *constant error carousel*) but they impose a **hard algebraic form**:

1. **Additive updates only** – once a value is added, it can only be weighted by \(f_t\) each subsequent step.  
2. **Multiplicative decay** – forgetting is a simple scalar multiplication; there’s no way to *boost* earlier content when a better version arrives later.

A concrete illustration comes from the *Nearest Neighbor Search* task in the paper: you give the model a reference vector \(v_\text{ref}\), then present it with a stream of vectors \(v_1\!\to\!v_M\). At the end you ask for the value associated with whichever vector was *closest* to \(v_\text{ref}\).  With an LSTM you can store each \(v_i\) as part of the final hidden state, but if a later vector is closer you can’t *overwrite* or *amplify* that memory—until you reach the very last time step. As shown in the experiment (Figure 1 of the paper), standard LSTMs fail to revise their choice reliably.

In other words: **LSTMs are great at accumulating evidence but poor at revising decisions when newer evidence is stronger**.

---

## Exponential Gating: The Key to Revision

xLSTM replaces both input and forget gates with exponential functions:

\[
i_t \;=\; e^{\,\tilde i_t}, 
\qquad
f_t \;=\;
\begin{cases}
\sigma(\tilde f_t), & p < \tau_1\\[3pt]
e^{\,\tilde f_t}, & p \ge \tau_2
\end{cases}
\]

where \(\tilde i_t,\, \tilde f_t\) are linear preactivations as in normal LSTMs.  Two properties follow immediately:

1. **Unbounded positive values** – an exponential can grow arbitrarily large compared to a sigmoid bounded in \((0,1)\).  
2. **Dynamic weighting** – if an input gate suddenly becomes large (e.g., because its preactivation spikes), its contribution can dominate all prior hidden information.

The cell update now reads

\[
c_t = f_t\,c_{t-1} + i_t\,z_t.
\]

Because both \(f_t\) and \(i_t\) may be very large, a single time step can completely overwrite previous content if \(i_t \gg f_{t} c_{t-1}/ z_t\).  This *revision capability* turns the LSTM into something closer to a deterministic state machine: it can decide “yes, I’ll forget everything I had before and store this new chunk because it’s now far more relevant”.

---

## The Stabilizer Trick: Keeping Things in Numerical Control

Exponentials are great for revision but disastrous for numerical stability: products like \(e^x \times e^y = e^{x+y}\) explode very quickly, leading to overflows or NaNs during training.  xLSTM introduces an auxiliary variable called the **stabilizer state**:

```text
mₜ = max( log(fₜ) + mₜ₋₁ , log(iₜ) )
```

Using `mₜ`, we rescale our gates:

```text
i′ₜ = exp( log(iₜ) - mₜ )   = exp( 𝑖̃ₜ - mₜ )
f′ₜ = exp( log(fₜ) + mₜ₋₁ - mₜ )
```

Crucially:
- `i′ₜ` and `f′ₜ` are derived from `iₜ`/`fₜ` by subtracting (or adding) a common term `mₜ`.  
- Because all terms in `mₜ` come from logged values of gates, the difference stays bounded even if individual logs are huge.

This trick guarantees that **shifting large multiplicative values into an additive stabilizer keeps forward activations and gradients well behaved**, while preserving exactly the same overall computation as before substitution. The authors formally prove (in Appendix A of their paper) that replacing `i_f` by `i′_f` does not alter loss or gradients—so training proceeds without any side effects.

---

## Memory Mixing Reloaded

The addition of exponential gating unlocks another benefit: **memory mixing across “heads” or “cells” becomes much more expressive**.

An sLSTM block can stack several scalar memory cells side‑by‑side (like traditional multi‑head LSTMs). Each cell’s hidden output feeds back into other cells via recurrent matrices (the old memory‑mixing mechanism). With exponential gates:
- When one cell’s input gate explodes above others’, it can dominate mixing suddenly.
- Forget gates can selectively decay specific cells while keeping others intact.

Thus sLSTM now behaves *not just like an RNN*, but like a full-fledged state tracker capable of selective overwriting—super useful for tasks such as:

| Task | Why revision matters |
|------|----------------------|
| Code execution | A function call may change variable bindings; earlier value must be replaced by newer one. |
| Narrative coherence | A character’s allegiance might flip midway; previous references must be updated dynamically. |
| Multi‑query recall | When new queries arrive, earlier memories should be pruned or reordered based on relevance. |

Experiments in the paper ran sLSTM on formal language problems that require dynamic state changes (parity checks, nested bracket matching). Classic Transformers or State Space Models without memory mixing failed completely—confirming that mere architectural depth cannot substitute for true state revisability.

---

## Practical Takeaways

1. **Exponential gating is optional but highly recommended** when your application expects out‑of‑sequence updates or memory revision.
2. The stabilizer trick is essential for training stability; without it exponential gates would blow up.
3. For scalability you may choose between:
   - **sLSTM** (scalar cells, memory mixing enabled)—great for expressivity but requires careful CUDA implementation.
   - **mLSTM** (matrix cells, no mixing)—parallelizable and hits massive memory capacities via covariance updates.
4. Even though mLSTM removes memory mixing entirely, its matrix storage gives it plenty of “room” to remember many key–value pairs—useful for associative recall tasks.

---

### Future Directions

The paper hints at several promising extensions:
- Better CUDA kernels for mLSTM could bring its speed up close to FlashAttention.
- Combining sLSTM heads cleverly might emulate transformer self‑attention while retaining true revision capabilities.
- Exploring other stabilization strategies (e.g., softplus instead of pure logs) could further ease training or allow deeper architectures.

But already today—thanks to exponential gating and its stabilizer trick—recurrent nets are back in business as genuine state trackers capable of traversing complex sequential reasoning without sacrificing speed or scalability.

# Scaling to 16 k Tokens: xLSTM’s Linear Speed vs. Transformers’ Quadratic Bottleneck

When the world of conversational AI grew out of research papers and hobby projects, the first language models that people kept talking about were **Recurrent Neural Networks (RNNs)**. Among RNNs, the most successful family was the **Long‑Short‑Term Memory (LSTM)** network, made famous by its ability to remember information over long distances and its practical stability for training.

Fast forward a few years and we have **Transformers**—models that learn attention patterns in parallel and, in theory, can see any distance in a single layer. In practice they have become the standard for Large Language Models (LLMs). The catch? Transformers pay a computational price that grows *quadratically* with the context length. If you want a model that can read 16 k tokens at once—a useful ability for long documents or code completion—you quickly hit memory wall after memory wall.

Enter **xLSTM**, a recent and promising revision of the classic LSTM cell. By re‑thinking gating, adding matrix‑valued memories, and carefully structuring residual layers, xLSTM keeps a *constant memory* per token and scales *linearly* with sequence length. The result? A model that can use longer contexts without stopping generating or crashing from OOM errors.

In this post we’ll walk through the key ideas behind xLSTM’s efficiency and then dive into concrete benchmark numbers that show how it compares head‑to‑head with Transformers on both inference throughput and training cost.

---

## 1. Why Transformers Slow Down on Long Sequences

Transformers ride on self‑attention: every token queries every other token to build a context‑aware representation. Mathematically this is an $O(L^2)$ operation where $L$ is the sequence length.

| Section | Operation | Complexity |
|---------|-----------|------------|
| Attention score matrix | $QK^\top$ | $O(L^2d)$ |
| Weighted sum of values | $S V$ | $O(L^2d)$ |

Consequences:

1. **Memory blowup** – For $L = 16{,}384$ and model dimension $d = 1{,}024$, you need more than **260 GB** of intermediate activations to store the attention matrix together with gradients.
2. **Long training times** – The warm‑up linear‑attention tricks sieve large parts of the quadratic term, but they still need to touch most pairs $(i,j)$ at least once.
3. **Inference bottlenecks** – Even with clever caching tricks, production inference on batches larger than 1–2 tokens gets heavily slowed by the quadratic cost per step.

---

## 2. How xLSTM Keeps Things Linear

xLSTM revamps traditional LSTMs along two axes:

### a) Exponential Gating & Normalization  
- Put an *exponential* activation on the input gate ($e^{\tilde{i}_t}$) instead of a plain sigmoid.
- Introduce a **normalizer state** $n_t$ that aggregates future forget gates; it keeps the cell content bounded without sacrificing “forgetting” capabilities.

### b) Matrix Memory Update  
- Replace the scalar cell state $c_t \in \mathbb{R}$ with a full matrix $\mathbf{C}_t \in \mathbb{R}^{d\times d}$.
- Update rule: $\displaystyle \mathbf{C}_t = f_t\,\mathbf{C}_{t-1} + i_t\, \mathbf{v}_t \mathbf{k}_t^\top$
- Retrieve via $\displaystyle \tilde{\mathbf{h}}_t = \frac{\mathbf{C}_t \mathbf{q}_t}{\max\{|\mathbf{n}_t^\top\mathbf{q}_t|,\;1\}}$

The key insight: because all updates are **matrix multiplications**, they can be batched per token rather than pairwise across tokens—exactly what you’d do for hidden _stochastic transitions_ in an RNN.

#### Parallelizing mLSTM  
While sLSTM retains hidden–hidden mixing (so it stays sequential), mLSTM is fully parallelizable: you compute $\mathbf{C}_t$ for all positions independently using an efficient scan algorithm or through CUDA kernels akin to FlashAttention’s scan. In practice this gives:
- A linear overall time complexity $O(Ld^2)$.
- A memory footprint that *does not grow* with $L$: at each step you store just one matrix $\mathbf{C}_t$, not all pairwise interactions.

# From Small Blocks to Big Models – The Anatomy of an xLSTM Architecture  

Large‑scale language models are usually built from a handful of repeating **building blocks**.  
With the new *xLSTM* family you can keep that modular spirit while turning a vanilla LSTM into a modern, billion‑parameter model that matches – or even beats – Transformers on many benchmarks.  

In this post we walk through the three core ideas that make xLSTM work:

1. **Residual backbones** that give the model depth and stability  
2. **Pre‑/post‑up‑projection blocks** that decide where the heavy lifting happens  
3. **Stacking sLSTM / mLSTM cells** to build an end‑to‑end LLM

Along the way you’ll see diagram sketches and short code snippets for PyTorch and JAX (or Haiku), so you can start prototyping right away.

---

## 1. Residual Backbones – The “Glue” Between Layers  

All state‑of‑the‑art language models (GPT, Llama, Mamba…) share a simple recipe: a stack of *residual blocks* arranged in a pre‑LayerNorm style.  
An xLSTM block lives inside this scaffold; the residual connection lets gradients flow easily through many layers and gives the network an inductive bias toward identity transformations – exactly what we want when we replace the Transformer self‑attention with an LSTM cell.

```
┌─────────────────────┐
│     LayerNorm(x) ──►  ──► (adds into residual later)
│                       │
│   [Block]             │
│                       │
└───┬───────────────────┘
    ▲                 ▲
    │                 │
...│                 ...          ←  N Stacked Blocks
```

The block itself will contain one *sLSTM* or *mLSTM* cell together with some feed‑forward and projection logic that we’ll discuss next.

---

## 2. Pre- vs Post-Up‑Projection: Where Does the Heavy Work Happen?  

### Pre‑Up‑Projection (used for mLSTM)

For matrix‑memory cells we “project up” **before** any non‑linearity:  

```
x ──► lin_proj ↑ d_hidden*H  ──►   …(mLSTM cell) …   ──► lin_proj ↓ d_hidden
```

*Why?*  
The mLSTM’s memory is a $d \times d$ matrix. Operating directly in a high dimensional space gives it a larger storage capacity and keeps memories well separated, which is exactly what covariance updates want.

### Post-Up‑Projection (used for sLSTM)

With scalar memory cells we keep everything in the native hidden dimension as long as possible, then only **after** computing the gated cell state do we expand to a higher dimension:

```
x ──► lin_proc ↓ d_hidden  ──►  sLSTM cell   ──► lin_proj ↑ d_hidden*H  ──► lin_proj ↓ d_hidden
```

The extra projection at the end turns small gates into useful high‐dimensional features while keeping the recurrent path cheap (because memory mixing relies on scalar hidden dynamics).

---

## 3. Two Families of Cells – sLSTM & mLSTM  

| Feature | sLSTM | mLSTM |
|---------|-------|-------|
| Memory Shape | scalar $c \in \mathbb{R}$ | matrix $\mathbf C \in \mathbb{R}^{d\times d}$ |
| Gating | exponential input & forget gates + stabilizer | exponential input & forget gates + stabilizer |
| Parallelism | no; requires sequential memory mixing | fully parallelizable |
| Use of Heads | multiple heads *within* each head – no cross-head mixing | multiple heads equivalent to multiple cells |

### Exponential Gating & Normalizer

Both cells replace traditional sigmoid gates with an *exponential* activation:

```python
i_t = exp( W_i @ x_t + b_i )
f_t = exp( W_f @ x_t + b_f )   # or σ for numerical stability
```

Because large exponentials can overflow, we keep a running “stabilizer” $m_t$:

```text
m_t = max( log(f_t) + m_{t-1}, log(i_t) )
i'_t = exp( log(i_t) - m_t )
f'_t = exp( log(f_t) + m_{t-1} - m_t )
```

These stabilized gates are mathematically equivalent to their original forms but numerically safe.

### sLSTM Forward Pass

```python
c_t = f_t * c_{t-1} + i_t * z_t              # cell state update
n_t = f_t * n_{t-1} + i_t                    # normalizer
h_t = o_t * ψ( c_t / n_t )                   # hidden state (ψ = tanh)
```

### mLSTM Forward Pass

```python
C_t   = f_t * C_{t-1} + i_t * v_t @ k_t.T     # outer-product update
n_t   = f_t * n_{t-1} + i_t * k_t             # normalizer vector

h̃_t  = C_t @ q_t / max( |n_t.T @ q_t| , 1 )   # key–value retrieval
h_t   = o_t ∘ h̃_t                              # elementwise product with output gate
```

> **Tip:** In PyTorch you can use `torch.einsum("biv,bjv->bij", v, k)` for the covariance update; this is heavily GPU optimized.

---

## 4. Stacking into a Full Model  

You see how everything fits together in one block? The full architecture is just many of these blocks linearly stacked:

```
token_embed -> [Block 1] -> [Block 2] -> … -> [Block N] -> final projection → logits ↦ probability distribution.
```

When building a large language model you choose:

| Choice | What it buys you |
|--------|------------------|
| **$N$ (number of blocks)** | Depth increase → better abstraction but more compute |
| **$d_{\text{hidden}}$** | Width of hidden representations |
| **$H$ (up-projection factor)** | Higher dimensional space for richer feature interaction |
| **Ratio s/m** (`xLSTM[7:1]` etc.) | Mix heavy parallel matrices with lightweight scalar cells |

In code (simplified PyTorch):

```python
class XLMSTokenEmbedding(nn.Module):
    def __init__(self, vocab, d_embed):
        super().__init__()
        self.embed = nn.Embedding(vocab, d_embed)

class XLMSTokenHead(nn.Module):
    def __init__(self, d_head, vocab):
        super().__init__()
        self.out = nn.Linear(d_head, vocab)

class XLMSTransformerBlock(nn.Module):
    def __init__(self, cell_cls, dim, proj_factor):
        super().__init__()
        self.norm = nn.LayerNorm(dim)
        if issubclass(cell_cls, SLstm):          # post-up-projection block
            self.pre_proj  = nn.Linear(dim, dim)
            self.cell      = cell_cls(dim)
            self.post_proj = nn.Linear(dim*proj_factor, dim)
        else:                                   # pre-up-projection block (mLSTM)
            self.pre_proj  = nn.Linear(dim*proj_factor, dim)
            self.cell      = cell_cls(dim)
            self.post_proj = nn.Linear(dim, dim)

    def forward(self, x):
        y = self.norm(x)
        y = self.pre_proj(y)
        y = self.cell(y)
        y = self.post_proj(y) if hasattr(self.cell,'post_proj') else y
        return x + y                       # residual connection

class XLmModel(nn.Module):
    def __init__(self, vocab, num_blocks=48,
                 dim=2048,b=4,norm='pre',whole_ratio=(7,1)):
        super().__init__()
        ratio_s,l_m=(whole_ratio[0],whole_ratio[1])
        block_specs=[]
        for i in range(num_blocks):
            if i%ratio_s<ratio_s:          # sLSTM block slot
                block_specs.append(SLstm)
            else:
                block_specs.append(Mlstm)
        layers=[XLMSTokenEmbedding(vocab,dim)]
        layers+= [XLMSTransformerBlock(cls=cell,d=dim,b=b) for cell in block_specs]
        layers.append(XLMSTokenHead(d_head=dim,vocab=vocab))
        self.net=nn.Sequential(*layers)

    def forward(self, tokens):
        return self.net(tokens)              # logits before softmax
```

> **JAX users** can replace `nn` with Haiku’s `hk.RNNCore` variants and use `jax.vmap` to automatically vectorise over batch dimension.

## 5. Practical Tips & Common Pitfalls

| Tip | Why it matters |
|-----|----------------|
| **Start small** (e.g., < 5 M params) before scaling up to billions; fine‑tune gradient clipping & learning rate schedules from Transformers.* | All modern LLMs use similar tricks (`warmup`, AdamW). |
| **Use mixed precision (`torch.cuda.amp`)** but avoid automatic mixed precision on older GPUs where `ln`/`exp` might blow up. Micro-batch sizes of ~ 8–16 are usually safe.* | The exponential gates are more sensitive to float32 vs float16 errors. |
| **Cache queries & keys** in inference mode if you need multi-head decoding (`torch.compile`). | Helps accelerate generation by avoiding repeated projection costs. |
| **Parallelise the matrix memory** with `torch.bmm` instead of loops; FlashAttention‑style scan can be used for *suppressing overflow* during covariance updates.* | This keeps wall clock time low even at large dimensions $d$. |
| **Track normalizer state `$n_t$` carefully**; if it underflows machine epsilon both `i` and `f` vanish prematurely.* | In early training rounds it’s common to add small epsilons to denominators as shown in Eq.~(13). |

# Future Proofing AI: Why Recurrent Architectures Like xLSTM Are Here to Stay

## The Rise and Limitations of Attention‑Heavy Models

When the Transformer burst onto the scene in 2017, it seemed to promise that everything else would become obsolete. Its parallelisable self‑attention layer, coupled with an ever‑growing number of parameters, produced text models that could write poems, answer questions, and even draft code. The gains were undeniable: a single feedforward pass through a multi‑head attention matrix can capture token–token interactions across an entire sequence, no matter how long that sequence may be.

But as soon as we start looking beyond the research lab, a few fundamental problems bite back:

| Challenge | What Transformers struggle with | Impact |
|-----------|---------------------------------|--------|
| **Memory footprint** | Quadratic growth in the attention map (`O(L²)` where `L` is the sequence length). | On embedded or edge devices you quickly run out of GPU/TPU memory. |
| **Compute cost** | Each token addition scales SGNN (self‑attention) linearly in `L²`. | Energy consumption goes up quickly; latency is high for long contexts. |
| **Explainability** | Attention weights are often noisy and don’t map cleanly to causal reasoning. | Difficult to debug or certify systems in safety‑critical domains. |
| **Training data explosion** | Scaling up demands huge amounts of computation – billions of parameter updates per second. | Sustainability concerns; training carbon footprints are huge. |

In practice, this means that a Transformer fine‑tuned on a 12 GB GPU can easily overrun a mid‑tier server or smartphone, and even if it runs, its internal state is hard to interrogate. Researchers have tried *linear attention*, *sparse retrieval*, *state‐space models*, and even *fast weighted programmers* to mitigate these issues, but each comes with trade‑offs – either weakening representation power or imposing custom hardware tricks.

## The Case for Revisiting Recurrence

Recurrent neural networks (RNNs) are not new: they predate LSTMs by over twenty years and were the backbone of early language models. The classic LSTM introduced *gates* – input, forget, and output – so that the recurrent cell could selectively store or forget information over long horizons. Despite their older lineage, LSTMs have shown:

- **Long‑range context handling**: thanks to their gating we can keep crucial features persistent over thousands of tokens.
- **Linear time complexity**: each time step processes in constant time (`O(d)`) regardless of context length.
- **Energy efficiency**: recurrent layers consume less floating point operations than quadratic attention.

However, vanilla LSTMs still suffer from three pain points:

1. **Limited storage** – each cell holds a single scalar value; complex memories end up condensed into noise.
2. **Inflexible revising** – once a key/value pair is stored it’s hard to overwrite it efficiently.
3. **Sequential execution required** – hidden‐to‑hidden connections prohibit data parallelisation on modern GPUs.

Recent work has started to patch these holes one by one. An excellent example is the *xLSTM* architecture, which adds two transformative ingredients to standard LSTMs: exponential gating and matrix‑based memory.

### Exponential Gating

Gates traditionally use sigmoid activations (`σ(x) = 1/(1+e^{-x})`), which saturate quickly and limit how sharply we can set a gate to “on” or “off”. Exponential gating (`exp(x)`) lets us push gates into arbitrary regimes while preserving differentiability:

```text
input gate   i_t = exp(ẑ_i)
forget gate  f_t = σ(ẑ_f)  OR exp(ẑ_f)
```

To avoid overflow issues when multiplying many exponentials across steps, xLSTM introduces a *stabiliser state* that normalises these terms on‐the‐fly:

```
m_t = max(log(f_t)+m_{t-1}, log(i_t))
i'_t = exp(ẑ_i - m_t)
f'_t = exp(log(f_t)+m_{t-1} - m_t)
```

This trick guarantees that repeated multiplicative updates never blow up or vanish—a pivotal trait for very long sequences.

### Matrix Memory (mLSTM)

Instead of storing a single number per cell, xLSTM’s matrix variant (mLSTM) keeps a full `d × d` memory tensor `C`. When a new key/value pair arrives (`k_t`, `v_t`), it updates memory via an outer product:

```
C_t = f_t·C_{t-1} + i_t·v_t·k_t^T
```

Retrieval then boils down to a matrix–vector multiply with an incoming query `q_t`:

```
h_t = o_t ⊙ (C_t·q_t / max{|n_t^T q_t|, 1})
```

Because the update rule only involves simple matrix operations—no non‑linear interactions—the recurrence can be expressed entirely parallelised across all time steps (a scan operation). In effect, we get **constant sequence‑length memory** but still maintain **rich storage capacity**, much like fast weight programmers but with built–in decay (`f_t`) and learning rate (`i_t`).

### New Memory Mixing & Heads

xLSTM’s sLSTM variant keeps the classic scalar cells but introduces *memory mixing* through multiple recurrent matrices applied between hidden states and gate vectors:

```
z_i ← W_z·x_t + R_z·h_{t-1}
i_i ← W_i·x_t + R_i·h_{t-1}
...
```

Each such mixing step operates across multiple *heads*. Unlike Transformers where heads are independent (no cross‑head mixing), sLSTM lets heads share inter‐cell state while still keeping hidden‐to‐hidden connections localized within each head—this gives us richer dynamics without blowing up parallelisation costs.

## Why xLSTM Shines for Long‑Term Deployment

| Feature | How xLSTM Helps | Edge Impact |
|---------|-----------------|-------------|
| **Linear context cost** | Cell update + matrix multiplication scales as `O(d)` + `O(d²)` but independent of length. | Far fewer FLOPs per token → lower latency; no need to store huge attention maps. |
| **Compact memory footprint** | No per‑token KV cache; just one `d × d` matrix held in device RAM/VRAM. | Fits easily into modest GPUs/NPUs; suits mobile/IoT deployments. |
| **Energy efficiency** | Avoids repeated dot products across all pairs; uses simple algebraic operations per time step. | Small battery life savings for continuous NLP services on phones or wearables. |
| **Explainability & Debugging** | Gates can be inspected directly (`i`, `f`, `o`) ; matrix memory reveals what keys/values are being stored via principal component analysis or energy norms. | Easier model introspection—valuable for regulated industries (finance, healthcare). |
| **Long‑range reasoning** | Exponential gating + matrix memory allows revising stored pairs efficiently; retains relevance over thousands of steps. | Enables apps that need co-reference tracking or dialogue history retention without resorting to large KV buffers. |

The experimental evidence backs this up: on benchmark suites such as Long Range Arena and Multi‑Query Associative Recall, xLSTM consistently matches or outperforms Transformers and State Space Models while keeping inference latency comparable or lower than pure RNN variants like RWKV.

## Deployment Scenarios Where xLSTM Wins

### 1. Live Dialogue Bots on Smartphones

A conversational agent needs to maintain context over many turns but cannot afford two dozen megabytes of KV cache on-device. With xLSTM you keep all state in a single static tensor; the model can run at ~30 ms per token on an A14 GPU—well below user perceptible delays.

### 2. Real‑Time Code Analysis on Edge Devices

Static code analyzers often need to parse source files that may span millions of tokens (think large monorepos). Instead an mLSTM variant stores key/value pairs as matrices so that you can instantly retrieve information about variables seen earlier without retaining every token embedding.

### 3. Energy-Constrained Scientific Simulations

When modeling physical systems (e.g., weather forecasts) quality hinges upon long historical contexts (~hundreds of time steps). A linear-memory LSTM keeps historical patterns without bloating compute budgets—making continuous event forecasting possible even in satellite onboard processors.

### 4. Regulatory Auditing Systems

Governments require AI components whose decision process is auditable at the neuron level for fairness checks when dealing with credit scoring or medical diagnosis. ## Practical Considerations & Limitations

While xLSTM shows promising metrics, it comes with some caveats:

- The current CUDA kernels for mLSTM are not yet tuned like FlashAttention—custom implementation yields ~4× slower runtime at scale.
- The `d × d` matrix update incurs heavier unrolling complexity; for extremely wide models you may hit GPU register pressure.
- Restraining input dimensionality (<256) might seem low compared to today’s thousands-of-dimension embeddings—yet experiments suggest performance remains strong even at high dims once gates are tuned properly.
- Careful initialization of forget gates is mandatory; otherwise gradient flow decays too rapidly during training.

These issues are engineering hurdles rather than algorithmic limitations: a future version of xLSTM can adopt fused kernels for matrix updates similar to how FlashAttention unrolled self-attention into one GPU kernel.

## Bottom Line

Attention-heavy models have undeniably dominated recent progress in natural language processing thanks mainly to their parallelism on modern GPUs and their flexible representation ability sparked by self-attention maps. Yet they carry fundamental penalties when you look beyond the training loop: quadratic memory usage, lack of constant-time inference for arbitrarily long contexts, less intuitive interpretability, and difficult adaptation on energy-constrained devices.

Extended LSTMs (xLSTMs) revisit recurrence not simply as “cheap history”, but as a powerful structure that marries gated control with matrix-based storage—two innovations that resolve many classical LSTM shortcomings while preserving their key virtues: linear compute cost and flexible backpropagation.

If you're building AI systems where deployment matters as much as raw accuracy—think embedded NLP services, real-time scientific simulators, or regulated financial tools—the future proofing promise lies in architectures like xLSTM that keep small footprints *and* support arbitrarily long contexts without heavy compute overheads.

For researchers preparing next-generation language models beyond fast transformers, exploring xLSTMs' explicit control signals may also open new avenues toward mechanistic understanding: every gate jump offers insight into how learned representations evolve over time—a window inching us closer toward explainable—but powerful AI systems capable of CPU / GPU mixed workloads while retaining decades-long heritage.
