# Co‑existing Memories: sLSTM vs. mLSTM – One Is Scalar, the Other Matrix, Both Are Game‑Changers

Modern language models no longer rely solely on attention‑based Transformers. A new family of recurrent units called **xLSTM** promises to compete with large Transformer‐style LLMs while offering linear‑time inference and a tighter memory footprint. At the core of xLSTM are two radically different cell designs:

|                | **sLSTM** – *scalar cell* | **mLSTM** – *matrix cell* |
|----------------|---------------------------|---------------------------|
| Memory shape   | \(c_t \in \mathbb{R}\)   | \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\) |
| Storage strategy | Exponential gating + normalizer state | Covariance update rule + key/value projection |
| Parallelism    | Sequential (memory mixing) | Fully parallelizable |
| Typical use‑case | Small–medium models, when state‑tracking matters | Large–scale models needing high capacity and speed |

Below we unpack each design, compare their computational profiles and practical implications, and give guidance on when to choose one over the other.

---

## 1. The Problem Space

Traditional LSTMs introduced two major tricks: (1) a *constant error carousel* that relays gradients through time, and (2) sigmoid gates that control when information is written to or read from a scalar cell. However, early work showed three critical shortcomings:

1. **Inflexible storage decisions** – once something is written to the cell, a later more relevant piece of information can’t easily overwrite it.
2. **Limited capacity** – a single scalar must hold all relevant semantic cues; rare tokens or long dependencies suffer from severe compression.
3. **Sequential bottleneck** – hidden–hidden connections force the model to process one token at a time.

xLSTM tackles all three challenges by (i) allowing *exponential gating* (so a gate can explode the influence of an input) and (ii) offering two alternative memory structures that balance expressivity and speed.

---

## 2. sLSTM – The Scalar Reformer

### 2.1 Formula in a nutshell

For each step \(t\):
\[
\begin{aligned}
c_t &= f_t\,c_{t-1} + i_t\, z_t  &\text{(cell update)}\\
n_t &= f_t\,n_{t-1} + i_t      &\text{(normalizer)}\\
h_t &= o_t\,\tilde{h}_t , \quad
\tilde{h}_t = \frac{c_t}{n_t}  &\text{(output)}\\[4pt]
i_t &= \exp(\tilde{i}_t),\;
f_t = \sigma(\tilde{f}_t)\;\text{or}\;\exp(\tilde{f}_t),\;
o_t = \sigma(\tilde{o}_t).
\end{aligned}
\]

Key differences from vanilla LSTM:

- **Exponential gates**: \(i_t\) and optionally \(f_t\) grow as \(\exp(\cdot)\), enabling rapid overwriting or reinforcement of memory entries.
- **Normalizer**: \(n_t\) tracks the cumulative influence of future forget gates so that the output can be safely divided without overflow.
- **Stabilization**: A running maximum of log‑gate values (\(m_t\)) keeps exponentials numerically stable.

### 2.2 What does it buy you?

- **Strong state tracking**: Because the exponential gating can quickly replace older entries, sLSTM excels at *state tracking* tasks (e.g., formal grammars, parity). Empirical results on Long‑Range Arena show that sLSTM outperforms architectures lacking memory mixing.
- **Memory mixing within heads**: sLSTM supports multiple *heads*, each mixing memory across its own set of cells but not across heads, offering expressive context modeling.
- **Non‑parallel solution**: The hidden–hidden recurrent connections mean sLSTM must be evaluated sequentially—no free lunch if you need maximal throughput.

### 2.3 When to pick it

- Your model is modest in size (tens to low hundreds of millions of parameters).
- You care about problems requiring exact state retention—reasoning over dialog turns, long narrative tracking, or code evaluation.
- GPU memory is limited; the scalar cell keeps parameter count low.

---

## 3. mLSTM – The Matrix Powerhouse

### 3.1 Formula in a nutshell

For each step \(t\):
\[
\begin{aligned}
\mathbf{C}_t &= f_t\, \mathbf{C}_{t-1} + i_t\, \mathbf{v}_t\, \mathbf{k}_t^\top 
\\
\mathbf{n}_t &= f_t\, \mathbf{n}_{t-1} + i_t\, \mathbf{k}_t
\\
h_t &= \mathbf{o}_t \odot \left(
           \frac{\mathbf{C}_t\, \mathbf{q}_t}
                {\max(|\mathbf{n}_t^\top \mathbf{q}_t|,1)}
        \right)
\\[4pt]
i_t &= e^{\,\tilde{i}_t}, 
\\
f_t &=
   \sigma(\tilde{f}_t)\;\text{or}\;e^{\,\tilde{f}_t},
\\
o_t &=
   \sigma(\tilde{o}_t).
\end{aligned}
\]

Key changes:

- **Matrix memory**: Instead of a single scalar, mLSTM holds a full \(d\times d\) matrix, analogous to fast weight programmers or associational memories.
- **Covariance update rule**: Each new key–value pair contributes an outer product \(v_k\,k_k^\top\), providing maximal separability for retrieval—a proven strategy in bidirectional associative memories.
- **Parallelizable recurrence**: No hidden → hidden term means the entire sequence can be processed in parallel after a pre‑dually computed “scan” over the gates (similar to FlashAttention’s linear attention).

### 3.2 What does it buy you?

- **Huge storage capacity**: The matrix can encode far more distinct key/value pairs than a scalar cell—in fact its effective capacity scales with \(d^2\). This is why mLSTM tops other non‑Transformer baselines on multi‑query associative recall tasks.
- **Fast inference at scale**: Since updates are just matrix multiplications and addition, all tokens can be processed concurrently; wall‑clock time remains almost linear even for billions of parameters.
- **Ready for large models**: In experiments scaling up to 300 B tokens and 1.3 B parameters, mLSTM‑based xLSTMs achieve first‐rank validation perplexities among all compared families.

### 3.3 When to pick it

- You’re building an LLM in the multi‑hundred‑to-billions range.
- High throughput is critical—batch inference or real‐time generation in production services.
- Your hardware allows dense tensor operations (e.g., highly parallel GPUs or TPUs).
- Memory constraints are less severe than on edge devices; you can afford storing an extra \(d\times d\) matrix per layer.

---

## 4. Practical Trade‑offs

| Aspect                      | sLSTM                                      | mLSTM                                            |
|-----------------------------|--------------------------------------------|---------------------------------------------------|
| **Speed per token**        | Sequential, ~2× slower than mLSTM          | Parallelized scan; comparable to FlashAttention   |
| **Peak GPU memory per layer** | Low (scalar weight + gates)                 | Higher (dense matrix ops), but no extra parameters |
| **Scalability with depth/width** | Limited by sequential bottleneck           | Scales naturally—more heads give larger matrices   |
| **Storage expressiveness**      | One latent value per token                  | \(d^2\) latent values per token                    |
| **Ease of implementation**     | Simple forward pass                         | Requires custom CUDA kernels for matrix ops        |
| **Where it shines**            | State tracking / small models               | Long sequences / large language models             |

Notably, xLSTM architectures often mix both variants: high layers get *mLSTMs* for raw capacity while lower layers use *sLSTMs* for precise state handling—a ratio we denote as `xLSTM[a:b]` where `a` is number of mLSTMs and `b` number of sLSTMs joined together.

---

## 5. Decision Tree – How to Pick

> **Step 1:** What is my model size?  
> ⟹ <100 M → try pure sLSTM (`xLSTM[0:X]`).  
> ⟹ ≥300 M → consider blending (`xLSTM[7:1]` commonly works well).

> Step 2:** Do I need exact state tracking?  
> ⟹ Yes → allocate at least one sLSTM block near the input layers.  
> ⟹ No → you may skip sLSTMs entirely if GPU throughput is your priority.

> Step 3:** Are my sequences very long (≥10k)?  
> ⟹ Yes → mLSTS provide better extrapolation because they keep full context in matrix form rather than silently dropping information in recursions.

> Step 4:** Is my deployment edge‑optimized?  
> ⟹ Yes → lean toward sLSTMs—they’re lighter on device GPU/CPU partitions and have constant memory independent of sequence length.

## 6. Putting It Together – A Quick Example

```python
# PyTorch style pseudo-code illustrating an xLSTM block mix:
class XLMBlock(nn.Module):
    def __init__(self, d_model, use_mlstm=True):
        super().__init__()
        self.use_mlstm = use_mlstm
        if use_mlstm:
            self.cell = MLTMCell(d_model)
        else:
            self.cell = SLTMCell(d_model)
        self.norm = LayerNorm(d_model)
    
    def forward(self, x):
        h = self.cell(x)
        return self.norm(x + h)
```

A full xLM model might stack:

```python
layers = []
for i in range(num_layers):
    if i < num_mlstm_layers:
        layers.append(XLMBlock(d_model, use_mlstm=True))
    else:
        layers.append(XLMBlock(d_model, use_mlstm=False))
model = nn.Sequential(*layers)
```

Replacing `num_mlstm_layers` smoothly trades bandwidth for expressiveness without altering overall architecture design.

---

## 7. Bottom Line

sLSTM and mLSTM are not alternatives but complementary building blocks for modern LSMTs:

* Use *sLSTMs* when you need tight control over the flow of information—a perfect fit for medium sized models dealing with intricate state tracking tasks.
* Use *mLSTMs* when you wish to scale up massively and want high throughput; their matrix memory gives them a head start over traditional Transformers on next–token prediction while keeping inference linear.

Mixing them wisely lets you cherry‑pick the best features more efficiently than any pure Transformer or pure RNN could offer alone. As the community continues to refine CUDA kernels for matrix updates and stabilize exponential gates further, we expect both variants will converge even closer—making xLSTMs an attractive horizon race against conventional LLM frameworks.
