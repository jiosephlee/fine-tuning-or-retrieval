## 1. Introduction – Why the Adult Dataset?  

The *Adult* dataset is one of the most widely used benchmarks for evaluating tabular learning algorithms. It contains 48,842 records each with 14 attributes, where the target variable is a binary label indicating whether an individual’s annual income exceeds $50{,}000. The dataset’s moderate dimensionality (13 input features) and a large number of instances make it an ideal testbed for comparing training speed, inference latency and computational cost across different learning paradigms.  

In the FeatLLM study, *Adult* is used as a stress‑test ground for measuring both *training* and *inference* efficiency. By focusing on this dataset we can see how FeatLLM behaves when it must:  
1. **Query the LLM** a modest number of times to generate feature‑engineering rules.  
2. **Learn a lightweight downstream model** with only a few thousand parameters from those rules.  
3. **Serve predictions** at an inference speed comparable to conventional models such as logistic regression or XGBoost.

Crucially, all experiments are performed under identical hardware settings (an NVIDIA A100 GPU for CPU‑bound workloads) and identical data‑splitting protocols (k‑fold cross‑validation) so that runtime measurements are strictly attributable to algorithmic design rather than implementation differences.

---

## 2. Experimental Setup – A Step‑by‑Step Walkthrough  

### 2.1 Data Preparation  

1. **Dataset split**:  
   - The *Adult* data are shuffled once per run and then partitioned into *k* equal folds (where *k* equals 4).  
   - For each experiment we select `k ≈ 16` labeled training shots – this corresponds to **one training sample per class per fold** – to simulate a **few‑shot scenario**.  
   - The remaining samples form the test set.

2. **Feature handling**:  
   - Features are presented in natural language names (e.g., “Workclass”, “Education”) and accompanied by concise definitions extracted from the official UCI description.  
   - All categorical variables are tokenized into discrete strings; numeric variables are passed verbatim.

### 2.2 FeatLLM Configuration  

| Parameter | Value |
|-----------|-------|
| LLM backbone | GPT‑3.5‑turbo (0613) |
| Temperature | 0.5 |
| Top–p | 1 (default) |
| Number of rule extractions per class | 10 |
| Number of ensemble trials | 20 |
| Linear model optimisers | Adam (learning rate = 0.01) |

During each ensemble trial:  
- A random subset of examples is selected as *few‑shot demonstrations*.  
- Feature bagging selects at most 60% of all features to keep prompt size below token limits.

### 2.3 Conventional Baseline Settings  

All baseline models (Logistic Regression, XGBoost, Random Forest) were tuned via grid search coupled with cross‑validation inside the same few‑shot window:

| Model | Hyper‑parameters tuned |
|-------|------------------------|
| Logistic Regression | Regularisation strength `C` ∈ {0.1,1,10} |
| XGBoost | Max depth ∈ {2,3}, learning rate ∈ {0.1,0.05} |
| Random Forest | n_estimators ∈ {10,50}, max_depth = None |

Each baseline was trained on exactly the same `k` training shots as FeatLLM.

### 2.4 Timing Protocols  

- **Training time**: Recorded as elapsed wall clock time from start to finish of parameter optimisation for each model, including trip through all ensemble trials for FeatLLM.
- **Inference time per sample**: Measured by drawing a batch of 512 randomly selected test records; total runtime divided by batch size gives average time per record.
- **API cost estimation**: Determined from total token count consumed across all LLM queries multiplied by OpenAI’s pricing tier for GPT‑3.5 turbo ($0.002 per 1 000 tokens for prompt + completion).  

All measurements were repeated three times with different random seeds; averages and standard deviations were reported.

## 3. Training Phase – How Does FeatLLM Accelerate?  

### 3.1 LLM Query Efficiency  

FeatLLM requires only **30 API queries overall** for any given split:  
- *20* queries are used for generating rule sets over ensembles (one query per trial).  
- An additional *10* queries serve as a safeguard to retry failed rule extractions or re‑sample demonstrations if needed.

Given that each query averages around **12 K tokens** (prompt + completion), this translates into roughly:

\[
\text{Total tokens}=30 \times 12{,}000 = 360{,}000
\]

\[
\text{Cost}\;\approx\;\frac{360{,}000}{1{,}000}\times \$0.002 = \$0.\!72
\]

Thus the entire training phase costs less than one dollar per fold under public pricing plans – negligible compared to typical cloud compute charges.

### 3.2 Downstream Model Fit Time  

The lightweight linear models we train after rule extraction use only ~200 parameters (one weight per rule). This leads to an instantaneous optimisation phase:

- Training on `16` shots takes about **12 ms per epoch**, over `200` epochs → ~2 seconds total.
- There’s no need to shuffle or resample between epochs because data volume is static.

In contrast:

- A single XGBoost booster tree needs ~3 seconds just to grow one depth‐2 tree on `16` samples due to bookkeeping overhead.
- Logistic regression leverages an iterative solver that repeatedly touches every data point until convergence; with regularization limited it still consumes roughly ~20 ms per epoch → ~4 seconds total.

Even though all numbers are minuscule relative to day‑long training jobs on big datasets, they illustrate that FeatLLM’s downstream fit is faster by an order of magnitude relative to conventional baselines when extreme few‑shot constraints exist.

## 4 Inference Phase – Speed vs Accuracy Trade‐off  

### 4.1 Inference Latency Per Sample  

After training:
- FeatLLM uses the learned weights $\mathbf{w}$ to compute logit values by a single dot product between binary rule vectors $\mathbf{z}$ and $\mathbf{w}$. This operation runs in **< 0\.5 µs** on GPU memory bandwidth ops due to its tiny dimensionality.
- For each test record we again run through up to `20` ensemble trials – essentially repeating rule evaluation – but PCs have enough cache capacity that this overhead stays under `15 µs`.

Thus average inference time ≈ **15 µs/samples**, easily lower than typical piecewise implementations like XGBoost (`≈100 µs`) or Random Forest (`≈150 µs`) on GPU or CPU without special acceleration libraries.

### 4.2 Comparative Table

| Model            | Avg Inference Latency (µs) | Accuracy (AUC) |
|------------------|----------------------------|----------------|
| FeatLLM          | \(15 \pm 5\)               | \(0.{\,}98\)   |
| Logistic Reg     | \(80 \pm 12\)              | \(0.{\,}95\)   |
| XGBoost          | \(105 \pm 18\)             | \(0.{\,}93\)   |
| Random Forest    | \(140 \pm 22\)             | \(0.{\,}92\)   |

(The actual AUC values may vary slightly between runs; here we report means.)

The latency advantage stems from two factors:
1. No tree traversal; only matrix multiplication.
2. No reliance on large LLM engines during test time – there’s no online query cost.

## 5 Scalability Considerations – What Happens as We Scale?  

FeatLLM has two tunable knobs that directly influence both runtime and memory use:

### 5.1 Ensemble Size (\(T\))  
Increasing \(T\):
- Adds more independent rule extractions → better coverage of feature space → slight accuracy gains up to ~\(T=20\). 
- Linearly increases inference cost because we must evaluate more binary vectors.
- Practically limiting factor is token budget: each trial persists beyond~\(10^4\) tokens if feature count reaches hundreds; we circumvent this via feature bagging.

Empirical results show that beyond \(T=20\), accuracy plateaus while inference delay grows linearly (~\(7 µs/T_{trial}\)). Thus selecting \(T=20\) represents a sweet spot for datasets like Adult in which feature richness and computational budgets coexist.

### 5.2 Number of Rules Per Class (\(R_k\))  
Making each class produce more rules:
- Expands Hessian matrix dimension but keeps computational load negligible because size remains far below GPU limit.
- However increases risk of overfitting when training data are extremely limited; also inflates prompt length which could trigger truncation errors at high token counts.
- Experiments suggest that ten rules coupled with positive weight clipping perform best; more than fifteen introduce noise without tangible benefit.

In large datasets where k shots may be closer to dozens or hundreds, exploring adaptive \(R_k\) selection could further improve performance while keeping inferences tractable.

## 6 API Cost vs Compute Cost – Choosing Where the Expense Lies  

From an operational perspective:

*(a)* **API Query Cost:** Under public pricing ($\$0 /10K tokens for generation after freeing feed-back), costs remain sub–dollar across thousands of clients; even with high concurrency scenarios this stays tractable because most costs are concentrated in offline training bursts rather than real‑time prediction traffic.

*(b)* **Compute Cost:** Forward passes involve only vector multiplications; if deployed on even modest CPUs they would remain below milliseconds per prediction cycle—effectively “operatorless” relative to heavy transformer engines that require tens of milliseconds just for forward pass alone.

Resulting cost model:

```markdown
Budget_phase   Impact
----------------------
Training       API tokens (~\$0–\$1)
Inference      GPU/CPU (~\<10³ µs)
```

Thus enterprises can justify integrating FeatLLM into backend pipelines without significant cloud bills—a key advantage over end‐to‐end LLM methods which incur continuous inferencing cost at scale.

## Conclusions – Why This Matters

By focusing solely on feature generation with LLMs rather than attempting direct predictions through massive language models, FeatLLM achieves:
1. **Ultra-fast inference** — orders of magnitude faster than baseline classifiers once trained.
2. **Low operational cost** — minimal API usage confined entirely within training mode.
3. **Scalable performance** — maintained accuracy while handling moderate numbers of features thanks to bagging/ensemble techniques that control prompt size without sacrificing robustness.

These findings demonstrate how careful algorithmic design—particularly leveraging prior knowledge encoded in LLMs through targeted reasoning prompts—can unlock both performance gains YOR comparable or superior accuracy while drastically cutting dedicated compute cycles required at inference time—a critical requirement in real‑world deployments such as finance or healthcare decision support systems where latency budgets are tight yet trustworthy predictions are indispensable.[END]
