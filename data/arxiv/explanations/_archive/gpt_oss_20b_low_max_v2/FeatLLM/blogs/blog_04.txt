# From Spurious Correlations to Robust Predictions:  
## The Safety Net of Bagging + Inference Rules

In few‑shot tabular learning the data are thin, the feature space is fat, and the temptation to overfit is high. A single set of hand‑crafted rules or a lone model can fall prey to noise: a handful of coincidental “spurious” columns that happen to correlate with the label in the tiny training set but have nothing to do with the underlying science.  
The *FeatLLM* framework tackles this problem head‑on by turning an LLM into a **feature engineer** and pairing that with a simple but powerful **bootstrap‑ensemble** (bagging). Below we explain why this combo works, how it protects against spurious correlations, and why it is especially effective on datasets like Heart Disease where irrelevant features can easily mislead a learner.

---

## 1.  LLM as a Rule Factory

* **Rule‑oriented prompts** – FeatLLM supplies the LLM with:
  1. A task description (e.g., “Does this patient suffer from coronary artery disease? Yes or no?").
  2. Feature names and definitions.
  3. A handful of labeled examples serialized into text.

* **Two‑step reasoning** – The prompt forces the LLM to first talk about how *features* *conceptually* influence the answer (drawing on its vast knowledge of medical literature).  
  Then it refines this intuition using the concrete few shots to generate concrete “if‑then” rules per class.

* **Parsing into computeable features** – The generated rules are automatically turned into python code by another LLM call. Running that code produces a binary feature vector per sample: `1` if the rule holds, `0` otherwise.

The end result is a transformed dataset \(\mathbf{Z}\) where each row consists of *testable* conditions extracted from LLM reasoning rather than raw numeric columns.

---

## 2. Why Bagging Helps

### 2.1 Diversity in Rule Generation

If we asked the LLM once for rules, we would get one deterministic set—variables we call *nominal rules*.  
Feasibility constraints (prompt size limits) and stochasticity in language models demand more experimentation:

* **High temperature** -> Heavier exploration of rule space.
* **Random shuffling of few‑shot demos** -> Encourages different reasoning paths.

Bagging then means we do the entire procedure repeatedly (say \(T=20\) times). Each run selects:
- A random subset of training instances (bootstrapped sample).
- A random subset of available features if feature count is huge.
- Possibly a different temperature or order.

Consequently, each replica produces a slightly different rule set and thus a different binary matrix \(\mathbf{Z}^{(t)}\).

### 2.2 Averaging Out Noise

Consider an irrelevant column \(X_{\text{spam}}\) that by pure chance splits the tiny training set nicely. In one bootstrap sample it will appear; in another it might be absent or will be weighted less by honest rules because other columns are more predictive.

When we average predictions over all replicas:

\[
\hat{\mathbf{p}} = \frac{1}{T} \sum_{t=1}^{T} \text{softmax}\!\bigl(\max(\mathbf{w}^{(t)},0)\cdot \mathbf{Z}^{(t)}_k\bigr),
\]

any spurious rule that only appears in a small number of replicas contributes little to the final probability. In effect, bagging acts as a *regularizer* that suppresses overfitting to noise.

## 3. An Eye‑Opening Example: The Heart Disease Dataset

The Heart dataset asks whether an individual will develop coronary artery disease based on 14 clinical measurements (age, chest pain type, resting blood pressure, etc.). It is notoriously sensitive to irrelevant variables because:

- Many medical datasets contain dozens of generated features from external data sources.
- In low‑shot regimes (e.g., only four labeled samples) random chance can create strong associations between unrelated columns and disease status.

### 3.1 Baseline Vulnerability

Imagine using plain logistic regression trained on all raw columns with 4 shots:

| Feature | Correlation | Rating |
|---------|-------------|--------|
| Resting BP | +0.28 | Moderate |
| Cholesterol | +0.31 | Moderate |
| **GPA → Age** | ±0.42 | High spurious |

Because GPA was invented for an unrelated project, its accidental split hits appearance under limited data; thus logistic regression could overfit to it and produce slick but unreliable predictions.

### 3.2 FeatLLM’s Protection

With FeatLLM:

1. The LLM first writes down knowledge: `Age > 50 AND ChestPainType = I -> ↑Risk` (a medically sound rule).
2. When added to bootstraps that do not include GPA, no rule referencing GPA appears; when GPA is present, it simply floods outlier traffic – but since its associated weight will be near zero after training on labeled examples, its effect is muted.
3. After repeating this over 20 bags, any rogue GPA–disease correlation vanishes in averaged predictions.

Empirically, FeatLLM’s performance degrades by less than \(3\%\) when adversarial columns from unrelated domains are injected—whereas logistic regression can tumble by \(>10\%\).

## 4. Practical Takeaways for Data Scientists

| Question | What FeatLLM Does |
|----------|-------------------|
| **How to build robust low‑shot models?** | Use an LLM as a rule generator; then ensemble via bagging without repeating inference per test point. |
| **Do I need access to full model weights?** | No—weights are only fitted locally on simple linear models after rule extraction; inference costs are comparable to classic RF/LogReg runs once rules are built. |
| **Can I reuse rules for new datasets?** | Potentially; if later tasks share similar domain knowledge, you can cache rule templates but be aware that bootstrapping hardware is cheap enough each time. |
| **Will bagging choke my compute budget?** | Only during training: about \(T\times\) fewer than \(200\) API calls versus thousands needed for sample‑wise LLM inference in other methods like TableLMM or In‑Context Predictors.|

## 5️⃣ Bottom Line

The union of *rule‑based feature engineering* and *bootstrapped ensembling* gives FeatLLM a built‑in safety net against overfitting in details you cannot see—spurious correlations lurking in otherwise innocuous columns.  
On challenging datasets such as Heart Disease where label scarcity is brutal and confusing signals abound, FeatLLM not only matches but surpasses state‑of‐the‑art baselines while keeping inference light and interpretability intact.
