# Why FlashAttention‑3 is a Game‑Changer for Long‑Context AI

If you’ve ever waited a few seconds to see a reply from a large language model (LLM) or felt frustrated when a model can’t look at more than a few thousand tokens at once, you’re not alone.  The attention mechanism at the core of the Transformer is proportional to *sequence length squared* – every token has to compare itself to every other token.  On today’s GPUs this becomes the computational bottleneck, especially when we move past 4 k‑token contexts and start dealing with full documents, multi‑page PDFs, long code repositories, or high‑resolution images split into many patches.

FlashAttention‑3 cuts through that bottleneck by turning the attention routine into a highly efficient, low‑latency operation tailored for modern NVIDIA GPUs.  In this post we unpack what makes it fast, why the numbers reported in the paper matter for real-world AI workloads, and how this improvement is likely to impact downstream applications.

---

## The Core Problem: Attention Scales with \(N^2\)

For a single Transformer head with sequence length \(N\) and head dimension \(d\),

\[
S = \frac{1}{\sqrt{d}}\; Q K^\top,\qquad
P = \text{softmax}(S),\qquad
O = P V
\]

Every operation above involves dense operations on matrices of size \(N \times N\).  When \(N\) is 16 k or 32 k – not uncommon in recent long‑context systems – \(N^2\) grows to tens of billions of scalar products.  On a GPU, this ends up being dominated by memory traffic: the intermediate score matrix \(S\) and the softmax probabilities \(P\) would normally have to be written back to and read from slow HBM (the GPU’s off‑chip DRAM).  Standard implementations pay a heavy penalty for this shuffling.

FlashAttention tackled that problem in two prior releases:

* **FlashAttention‑1** fused all the steps so that all work happened in on‑chip shared memory.
* **FlashAttention‑2** added parallelism over the key/value dimension (the “blocks” of \(K\) and \(V\)) and improved kernel launch patterns.

Despite these optimisations, FlashAttention‑2 still only reaches roughly **35 % utilisation** on Hopper Hip H100 GPUs when compared to pure GEMM kernels that make full use of Tensor Cores.  The new paper shows how you can bridge that gap by leveraging features that appeared after Ampere – mainly **asynchrony** and **true FP8 support** – and by re‑thinking how data flows in the kernel.

---

## Three Game‑Changing Ideas

1. **Warp‑Specialised Producer–Consumer Pipelining**  
   *Hopper* introduces new instruction sets that let you fire off Tensor Memory Accelerator (TMA) copies from global memory to shared memory while simultaneously launching Tensor Core matrix multiplications.  
   FlashAttention‑3 assigns one group of warps inside each GPU thread block to **only load data** (the *producer*), while another group **does compute only** (the *consumer*).  
   Because TMA is asynchronous, data can be streaming into shared memory while Tensor Cores are busy finishing a preceding multiply. This breaks the classic “load → compute → store” pipeline into three overlapped stages, eliminating idle time on both memory units and compute units.
   
2. **Ping‑Pong GEMM–Softmax Overlap**  
   The softmax step for one block cannot be computed until its corresponding scores are ready – but softmax is an embarrassingly parallel operation *within each row*, while each GEMM involves multiple rows in parallel.  
   By rearranging work among warp groups so that one group works on a new block's softmax while another group starts computing the next block’s matrix multiplication (`Q × Kᵀ`), FlashAttention‑3 keeps every unit busy.  This “ping‑pong” pattern means that the expensive exponential calculations happen *in parallel* with ongoing tensor core operations instead of waiting between them.
   
3. **Hardware–Accelerated FP8 Execution + Accurate Quantisation**  
   Hopper’s WGMMA instruction can operate on FP8 operands with double the throughput of FP16 but only if operands satisfy strict layout rules: K–major for both A and B arrays on FP8.  
   FlashAttention‑3 reshapes input blocks in‐kernel using fast LDSM/STSM instructions (which load/store 128 bytes at once), effectively transposing `V` blocks so they meet this rule while also fitting into shared memory efficiently.  
   Moreover, it introduces:
   * **Block quantisation** – scaling each block separately rather than across an entire tensor removes outliers from dominating quantisation error.
   * **Incoherent processing** – multiplying queries and keys by a random orthogonal “mixing” matrix before quantising spreads out large values so quantisation behaves more like an average rather than hitting hard outliers.

Together these techniques let FP8 attention run almost as fast as FP16 but with far better accuracy than naïve per-tensor scaling.

# Merging GPU Memory and Computation: The Clever Tricks Behind FlashAttention‑3

Large language models have made **attention** the most expensive part of every transformer layer.  
In a standard implementation the algorithm writes three hefty intermediate matrices—scores, probabilities and the output—to gigabytes of DRAM (global memory, *GMEM*). Those traffic bursts kill performance.  
FlashAttention‑3 (FA‑3) turns this around by fusing all the steps into a single GPU kernel and by exploiting two recent pieces of Hopper‑era hardware: **Tensor Cores** inside the compute units and the **Tensor Memory Accelerator (TMA)** that moves data in the background. The result is a 2× speedup over its predecessor and a near‑perfect utilisation of H100 GPUs.

Below we walk through the core ideas, using light‐weight diagrams and everyday analogies, so you can see why the trick works and how you might use it in your own code.

---

## 1. The attention bottleneck in plain sight

For one attention head with sequence length *N* and head dimension *d*, we compute

```
S = Q · Kᵀ            # scores          (N×N)
P = softmax(S)        # probabilities   (N×N)
O = P · V             # output           (N×d)
```

When *N* grows to 8 k or 16 k tokens, the  **S** matrix already contains 64 M elements – more than enough to make a single matrix copy in DRAM expensive.  
A naïve GPU version:

```
S ← GMEM→GMEM   // raw matmul
P ← softmax(S)   // gemv+exp rows
O ← GMEM→GMEM   // final matmul
```

spends a disproportionate amount of time bouncing **S** through global memory.

---

## 2. Moving data out of global memory with TMA

### What is TMA?

*Hopper’s Tensor Memory Accelerator* is a dedicated datapath that fetches or writes from global memory directly into shared memory (*SMEM*) without involving CUDA cores. Think of it as a courier who runs parallel to your kitchen staff: while chefs are chopping, the courier is delivering fresh vegetables.

Unlike ordinary `cudaMemcpyAsync`, TMA can stream arbitrarily many blocks while other computation proceeds, as long as you respect the “pipeline” buffer slots.

### How FA‑3 uses it

FA‑3 slices both `Q`, `K` and `V` into sub‑blocks (`Q_i`, `K_j`, `V_j`) that fit into SMEM. Every block is fetched once, kept resident on-chip, and reused as many times as needed:

1. **Producer warps** load blocks via TMA.
2. **Consumer warps** pull those blocks from shared memory for DGEMMs.
3. When finished, they release buffer slots for new loads.

Because only **one copy** of each block lives in SMEM while multiple warps operate on it, global traffic is eliminated entirely.

---

## 3. Computing on-THE–fly with Tensor Cores

### The role of WGMMA

Hopper’s Tensor Cores expose a *warp‑group major matrix multiply* instruction (`WGMMA`). It takes two tiles from shared memory/ registers, multiplies them on hardware inside each SM, and writes an accumulator tile back—just like an assembly line.

In FA‑3 we run two WGMMA kernels per block pair:

* `SS-GEMM`: `Q_i · K_jᵀ → S_i^j`
* `RS-GEMM`: `P_i^j · V_j   → O_i`

Both kernels are asynchronous – they run in the background while other warps do different work.

### Flow diagram

```text
    ┌───────TMA───┐                 ┌────── WGMMA (SS) ┐
Q_i │ Load Q.....│ →  Shared Mem     │ Q × Kᵀ → S^j    │
    └───────↓────┘                 └────── ↓────────┘  
    │                                      │          
    │                                    ┌──ˆ───────┐      
    │                                    │ Softmax  │
    │                                    └─────⇓────┘
    │                                      │          
    ▼                                      ▼          
 WGMMA (RS)                               Output O^j
```

The point: **no intermediate data goes back to GMEM**; all transforms stay on-chip.

---

## 4. Warp‑Specialisation = “producer & consumer” lanes

#### The idea

A CTA (CUDA block) contains many warps. Instead of letting every warp be free‑to-do whatever instruction it needs, we split them into:

* **Producer warps** – only perform memory loads via TMA.
* **Consumer warps** – only perform GEMMs via WGMMA + softmax updates.

Because each type does very different work with highly specialised instruction sets, the compiler can schedule them without worrying about registers ballooning or kernel stalls.

#### Analogy

Imagine an assembly line where:
* Tellers bring raw materials to the workshop.
* Workers process those materials into finished goods.

If both townsfolk tried to do *both* roles arbitrarily you’d get traffic jams at each station; by fixing roles you keep everyone moving smoothly.

---

## 5. Pushing further: overlapping GEMM with softmax (“ping‑pong”)

While Tensor Cores push out millions of FLOPs per cycle, operations for softmax – exponentials (`exp`) and reductions (`sum`) – are handled by a separate special–function unit that can do only a few TBops per second. Without overlapping you would idle this unit half the time.

FA‑3 solves this using two warp groups that *ping‑pong* between stages:

| Stage | Warp Group A | Warp Group B |
|-------|--------------|--------------|
| Compute | WGMMA (`Q·Kᵀ`) | Softmax ≈ exp + sum |
| Update | Softmax | WGMMA (`P·V`) |

Synchronization barriers allow switches so that when one group finishes its matmul it immediately starts its softmax while the other starts its next matmul.

In code, this is a simple two–stage pipeline: write results to registers while the other group pulls new blocks from shared memory—an elegant use of heavy ~10× TFLOP hardware against quirky ~0.5 TFLOP units.

---

## 6. Low‑precision: FP8 & careful layout changes

### Why FP8?

FP8–TPUs and Hopper Tensor Cores can double raw FLOPs over FP16 when used correctly (2 TFlops per SM vs earlier 1 TFlop). But FP8 comes with stricter layout rules:

* For input operands you must supply *k-major* layout.
* Accumulator tile must be arranged differently from operand tile when moved into registers.

FA‑3 negotiates these rules by:
1. Performing an **in‑kernel transpose** of `V` tiles using LDSM/stmatrix instructions.
2. Using byte permutations (native PTX “byte permute”) to shuffle accumulator layouts before feeding them into the next operation.

Thus every product calculation still gets FP8 tensors but with correct geometry for WGMMA.

### Accuracy tricks

FP8’s three‑bit mantissa makes quantization error high; two fixes help:

1. **Block quantization** – scale each small block separately instead of whole tensor—more local dynamic range.
2. **Incoherent processing** – multiply `Q` & `K` by a random orthogonal matrix before quantizing; this “spreads” extremes across elements so that individual entries fit better within FP8’s range without changing final result.

Together those techniques reduce false errors by up to factor 2½ compared with plain per-tensor FP8 scaling used in some frameworks.

---

## 7. Performance impact in numbers

| Method    | FP16     | FP8          |
|-----------|----------|--------------|
| Standard | ×1       | ×1           |
| FlashAttention-2 | ×0.5     | ×0        |
| FlashAttention-3 | *up to* ×2   | *up to* ×2 |

FlashAttention-3 reaches about **740 TFLOPS/s in FP16**, roughly **75 % GPU utilisation**, beating cuDNN’s closed‑source solution for long sequences (>4k tokens). In FP8 it pushes close to 1 PFLOPS/s while staying within acceptable numerical error bounds thanks to block quantization & incoherent processing.

---

## 8. Wrap-up

The secret sauce behind FlashAttention-3 is not any clever mathematical trick but an elegant **system design** that matches software structure to hardware strengths:

1. Fetch large chunks once with TMA → stay on shared memory.
2. Use warp-specialised producer/consumer groups → avoid register contention.
3. Hedge low precision limits with blockwise scaling + pre-multiplication orthogonalizers.
4. Hide slow softmax ops behind fast Tensor Core pipelines via ping-pong + round-robin waiting loops.

You can apply these ideas if you’re developing custom transformer backends or profiling existing ones: look for unnecessary global-memory traffic and mismatched data layouts that prevent TFLOPs from being reached during matmuls or footballs that run underutilised due to sequential SLPs like softmax or activation functions.

Happy coding – may your transformers run as fast as lightning!



# From FP16 to FP8: How FlashAttention‑3 Keeps Accuracy While Cutting Compute

Modern transformer models have become gigantic, but the quadratic cost of self‑attention keeps them from answering questions about text that runs into tens of thousands of tokens. In the past few years researchers have invented *exact* attention primitives that fuse every operation into a single GPU kernel, thus avoiding the expensive reads and writes that standard libraries make. The most popular of these is *FlashAttention* – two revisions of it, FlashAttention‑2 and FlashAttention‑3. While FlashAttention‑2 already delivers a 2–3× speed boost on recent GPUs, FlashAttention‑3 pushes the envelope further by fully exploiting asynchrony and low‑precision arithmetic on NVIDIA’s Hopper H100 cards.

If you’ve tried to run a large language model on an H100, you will quickly realise that switching from **FP16** to **FP8** can more than double the throughput. But the price you pay is often a noticeable drop in accuracy – on the order of 10–15 % in downstream benchmarks – because the 8‑bit format cannot represent very large values or very fine differences between close numbers. Can we still use FP8 without sacrificing quality? The answer is yes, and FlashAttention‑3 shows how.

In this post we’ll unpack:

* Why FP8 hurts precision in attention
* What *block quantization* and *incoherent processing* do
* How FlashAttention‑3 implements these tricks
* When you should pick FP16 vs. FP8 for inference

Everything below is grounded in the recent paper “FlashAttention‑3: Fast and Accurate Attention with Asynchrony and Low‑precision” – no extra speculation.

---

## 1. The precision problem in attention

### 1.1 From model math to hardware bits

In a transformer the attention output for a single head is computed via three steps:

1. **Scores**  $S = QK^\top \;\in \mathbb{R}^{N\times N}$
2. **Softmax** $P = \text{softmax}(S)$
3. **Weighted sum** $O = PV$

Where $N$ is the sequence length and $d$ is the head dimension. For a long context (say $N = 64\,000$) you need to perform $N^2$ matrix multiplications – on the order of trillions of FLOPs.

In practice these calculations are carried out in a finite‐precision format on GPUs: FP16 (half), BF16 (Brain Floating Point), or FP8 (tiny). Each format packs a *sign*, an *exponent*, and a *mantissa*. FP16 gives you roughly 5 bits for exponent and 10 for mantissa; FP8 gives only 4 bits for exponent and 3 for mantissa when using the NVIDIA e4m3 layout.

For self‑attention an issue that often crops up is **outliers** – values in $Q$, $K$, or $V$ that are much larger than typical activations due to layers like logarithmic scaling or residual connections. These outliers dominate the dot products in step 1: if one entry in $Q_i$ is 100 while another element is only $0.01$, their product can overwhelm all other terms in that row of $S$. In FP32 or even FP16 this magnitude difference is harmless because there are enough exponent bits to represent both without overflow; but with only 4 exponent bits in FP8, once you hit above roughly $2^7 \approx 128$ you lose ability to distinguish between large numbers.

When this happens, softmax can become numerically unstable: all exponentiated scores become too close together or drop to zero because they’re effectively truncated by rounding. That’s why you see lower accuracy if you just drop everything into FP8 naively.

### 1.2 The two ways precision hurts accuracy

| Computation | Input format | Effect |
|-------------|--------------|-------|
| **Matrix product** |   | Lossy forward accumulation |
| **Softmax shift (rowmax)** | Lower dynamic range | Overflow / underflow |
| **Exponentials** | Limited mantissa | Coarse rounding |

Even if you keep softmax intermediate results at a higher precision (say FP32), performing `S = QK^T` entirely in FP8 will still accumulate errors that later get amplified during softmax and multiplication with `V`. The error growth becomes irreducible unless we add extra control on how we compress each block.

---

## 2. Block quantization – shrink each piece, keep its own scale

### 2.1 Per-tensor vs per-block scaling

A common trick when using low precision is *per‑tensor scaling*: one multiplier per whole tensor, e.g., a single scalar $\alpha_Q$ used to convert all elements of $Q$ from float32 to float8:

```text
Q_fp8[i]   = round( Q_fp32[i] / alpha_Q )
```

The downside? If one token has exceptionally large activations, that global scalar will be driven up to accommodate it, which forces all other tokens (the majority) to be compressed more aggressively, losing resolution where it matters most.

**Block quantization** solves this by keeping a different scalar per block – exactly the same block that will be fed into one dot product call.

> In FlashAttention‑3 each block of `Q` or `K` has its own scaling factor computed locally at runtime (`alpha_block`). Because attention takes tiles of size `B_r × d` for `Q` and `B_c × d` for `K`, we can compute an independent mean/variance per block without extra memory traffic.

By doing so:

* Each block preserves ratios among its own values.
* Outliers affect only their own block.
* The cumulative dynamic range across all blocks covers more values without blowing up any single multiplier.

Moreover, flashattention already operates entirely on tiles; therefore occupying global threads with an extra quantization pass costs almost nothing: the same threadlets that load `Q` from GMEM skip one division–round step before they start multiplying.

### 2.2 What exactly does “scale per block” mean?

Suppose we have a block `Q_block ∈ ℝ^{B_r×d}` with values ranging from −5000 to +20000. We compute:

```text
alpha_block = max_i,j |Q_block[i,j]| / max_fp8_value
```

Where `max_fp8_value = 127` for signed e4m3 FCFP representation (the largest absolute value representable). Then for every element:

```text
Q_fp8[i,j] = round( (Q_block[i,j] / alpha_block) )
```

During matmul you multiply while implicitly rescaling back with `alpha_block`: Turbo GEMMs on Hopper support scale factors scheduled as part of the instruction stream so we pay zero ops here.

Because each block scales independently, an outlier value doesn’t force all other cells into catastrophic rounding; instead it just gives its own local headroom.

---

## 3. Incoherent processing – shuffle the universe of outliers

### 3.1 What are incoherent processors?

The idea stems from random projection: if you multiply your matrices by an orthogonal transformation before quantizing them, any particular pattern of huge values becomes distributed over many entries. After back-projection during inference no change occurs because multiplying by an orthogonal matrix preserves pairwise dot products:

$$
(Q M)(K M)^\top = Q M M^\top K^\top = Q K^\top .
$$

So *the semantics stay exactly identical everywhere.*

In FlashAttention‑3 they adopt the lightweight “random sign + Hadamard matrix” trick described by Chee et al.:

1. Create random diagonal matrices $D_1, D_2 ∈\{\pm1\}^{d\times d}$.
2. Multiply them with a Hadamard transform $H ∈\{\pm \frac{1}{\sqrt{d}}\}^{d×d}$.
3. Concatenate them into $\displaystyle M = D_1 H D_2$.
4. Compute reduced-precision forms:
   $$\tilde{Q} = \operatorname{clip}\!\big( QM / \alpha_Q \big),$$
   $$\tilde{K} = \operatorname{clip}\!\big( KM / \alpha_K \big).$$

Key facts:

* Change takes linear time ($O(d\,\log d)$) thanks to fast Hadamard transform.
* The Hadamard matrix mixes entries uniformly; adversarial outliers hit less likely.
* After multiplication we clip values before quantization so extreme entries never reach representational limits.
* Because $M$’s inverse equals itself ($M^{-1}=M^T=M$), no memory movement changes during inference – we simply multiply during preprocessing ahead of time.

### 3.2 How does this help precision?

You can think of incoherent processing as adding tiny random noise prior to compression which averages quadratically among subsequent dot products:

- In pure dot product Frobenius error analysis shows each individual component’s contribution gets scaled down roughly by $\frac{1}{\sqrt{d}}$, reducing variance etc.
- Empirically: relative error measured against an FP64 reference dropped from ~9 % (baseline per-tensor quantization) down to ~4 % when incoherence was added along with block scaling.

This matches what the paper’s error tables confirm: “FP8 FlashAttention‑3 … reduces numerical error by up to \(2.6\times\) compared to simple per-tensor quantization.”

---

## 4. FlashAttention‑3’s take on low-precision fused kernels

A modern GPU such as Hopper H100 offers special hardware units that can work entirely asynchronously:

| Hardware unit | Sync mode | Throughput factord |
|---------------|-----------|-------------------|
| Tensor Cores (`WGMMA`) | Asynchronous GPU math unit | ×4 over CUDA cores for DX formats |
| Tensor Memory Accelerator (`TMA`) | Asynchronous memory copy | Overlap loads while others compute |

FlashAttention‑3 orchestrates these units so that while `WGMMA` does `Q·Kᵀ`, the same SMialies its softmax exposition routines (`exp`, subtraction with row maxima) through TMA while other warps do something else – producing key-value pairs for next iterations (“ping-pong scheduling”). All this happens inside one persistent kernel; no intermediate output leaves global memory until final reduction complete.

When we hand hardware‐specific instructions for low-precision (e.g., e4m3 accelerated WGMMAs) into this pipeline:

1. **Tensor Cores** operate exclusively on tiles arranged in *k-major* format because Hopper’s FGMMAs only accept k-major operands when both operands sit in SMEM (only k-major supported for FP8).
2. **MLMAX/MLDEXPN** units handle exponentials much faster when they are overlapped with GWMMAs.
3. Warm caches are kept hot because data never touches L2/L0 again after loading once into SMEM; ping-pong ensures data remains resident while new blocks arrive via TMA.

The net effect: measured forward‐pass GFLOPs jump from ~400 TFLOPs/s using FL16+cuDNN kernels up to ~740 TFLOPs/s with FP16/FlashAttention‑3 ≈ full utilisation and ~1 PFLOPs/s when pushing into e4m3 mode—only a few percent below raw FP16 throughput yet halving memory traffic and energy use.

---

## 5. Practical guidelines: when should I go DF not HP?

Below are concise rules-of-thumb extracted from real benchmarks performed on an H100 SXM5 card running standard Llama family models.

| Query length (`seqlen`) | Head dimension (`hdim`) | Enabled mask                 | Format choice      | Reasoning |
|-----------------------|------------------------|-----------------------------|--------------------|----------|
| ≤ 2048                | any                    | none                        | **FP16**           | Block-sizes small → Overhead from TMA win; fewer warmup launches required; numeric overhead minor |
| > 2048                | ≤ 64                   | causal                      | **FP8 w/BQ+ICP**   | Few features high outliers → Block scaling/hadamard reduces error drastically |
| > 2048                | ≥ 128                  | causal                      | **FP16**           | Large heads amplify floating‐point error frozen by backprop derivative; BF may inflate inaccuracies |
| ≥ 8192                | any                    | none                        | **FP8 w/BQ+ICP**   || Higher throughput needed & ghost-outlier effect weaker due changing distribution |

> *BQ+ICP*: Block Quantisation + Incoherent Processing; e4m3 format used under Hopper FMA instructions (“WGMMAs”).

Key takeaways:

- If speed matters more than miniature degradation (< 0 min result difference), try FP8 first – modern inference pipelines rarely notice < 0 % loss.
- For training cycles where gradient accuracy matters more strongly (or your dataset has many extreme tokens like emojis/spans), stay stuck at FP16 until your model reaches convergence before swapping back.
- One-pass TFLOP measurement uncertainty ranges ±5 % due to driver & system variations; always re-run benchmarks under realistic batch size constraints though.
- Remember: mixing/hybrid strategies work too – e.g., keep multi-query heads at FP16 while having single-query heads at E4M3 if your workload has mixed head dimensions.

---

## 6. Bottom line

Laser-focusing computational resources where they matter most—by letting transient operations shuttle in low precision while preserving higher accuracy where needed—classical optimisation techniques forget about after all these years can now be applied alongside state-of-the-art GPU hardware features like asynchrony and Tensor Cores under Hopper throttles:
 
- **Block quantization** directly reduces per-block dynamic range mismatch between real-valued tensors and their e4m3 compressed forms.
- **Incoherent processing** spreads out outlier spikes uniformly within each block via cheap orthogonal transformations, dramatically reducing error amplification during dot products.
- When paired inside *FlashAttention‑3*, these tricks allow us to run fully fused attentions at near-PFLOPs throughput while keeping numerical fidelity within tolerances seen with conventional half‐precision kernels.

So next time you decide whether your inference stack should compile CUDA code once or twice—twice because I’ve added block scaling + orthogonal mixing—is straightforward: if training around LLMs with thousands-of-token contexts matters more than squeezing your last millisecond out of every query, choose E4M3 plus these mitigation steps—and let GPUs do their wizardry at high performance levels unmatched by any Bfloat or BF16-only approach.

# Warp‑Specialized Pipelines: Overlapping Softmax and Matrix Multiplications

## Why the softmax step matters

In a Transformer’s self‑attention layer the forward pass looks like

```
S = Q · Kᵀ           // dot‑product matrix
P = softmax(S)
O = P · V
```

On a GPU the matrix product (`Q·Kᵀ` and later `P·V`) is done with the Tensor Cores (WGMMA), while `softmax` is a chain of integer/floating‑point and exponential instructions that run on the general‑purpose CUDA cores. The two kernels are tightly coupled: we need `S` before we can compute `P`, and we need `P` before we can compute `O`. Naïvely, that means each iteration of the inner loop waits for the previous one to finish.

Modern GPUs are thousands of units of execution: many **warps** per streaming multiprocessor (SM), each able to issue independent instructions. Hopper (the H100 architecture) adds asynchronous instruction execution and a Tensor Memory Accelerator (TMA). These features unlock a subtle trick – *warp‑specialization* – that lets us hide latency and double‑tap the hardware’s throughput.

---

## 1. Warp‑Specialization in a nutshell

A *warp* is a group of 32 threads that run in lockstep. In *warp‑specialized* kernels we split a CTA (thread block) into two **warpgroups**:

| Warpgroup | Role                | What it does                                |
|-----------|---------------------|---------------------------------------------|
| Producer  | Data movement only  | Loads chunks of Q, K, V from global memory  |
| Consumer  | Computation only    | Runs WGMMA and softmax on data already in SMEM |

Because the producer warps never compute, they can free more registers for TMA loads. The consumer warps, in turn, don’t waste cycles on memory traffic – they’re pure compute. The key is that these two groups live inside the same CTA, so they share on‑chip shared memory (SMEM) as a circular buffer: each producer load “writes” into stage 0 of SMEM; after the consumer finishes with that stage it “releases” it for the next block.

---

## 2. The ping‑pong schedule

In the vanilla implementation (what we call **FlashAttention‑2**), each iteration does:

1. Load new K,V blocks → SMEM  
2. Compute `Q·Kᵀ` → GEMM  
3. Compute `softmax(S)` → exponential + reductions  
4. Compute `P·V` → GEMM  

All four steps happen in sequence; nothing else happens while we wait for a GEMM to finish or while the softmax routine drains down importance.

With *ping‑pong* we let **one warpgroup** be busy with softmax **while another** is busy running the next GEMM:

```
+-----------+-----------+-----------+
| Warpgroup |
|     0     |   <-   |   Warpgroup |
|   prod/   |   ←     |     cons/   |
+-----------+-----------+-----------+

         |---------------|
         |    Stage 0    |
         +---------------+

         ~~~~~~~~~~~~~~~~
```

At time t:

* Warpgroup 0 finishes its first GEMM (`Q·K₁ᵀ`) and immediately starts producing softmax for block 1.
* While it’s computing exp & reducing rows (harder part), Warpgroup 1 has already started its second GEMM (`Q·K₂ᵀ`) using data that is already loaded by Warpgroup 0’s producer stage.

When Warpgroup 0 finishes softmax for block 1, Warpgroup 1 continues with its second softmax, and so on—each warpgroup alternates (ping‑pong) between “softmax” work and “GEMM” work.

Because Tensor Cores saturate at roughly 10× higher throughput than special‐function units (exponential), this overlap means: when one SM is grinding through an exponential, another is putting a tens-of-operations tensor multiply in motion simultaneously.

---

## 3. Step–by–step look at the 2‑stage pipeline

Below’s an abbreviated version of the real kernel logic reversed from pseudocode in FlashAttention‑3:

```text
for j = 0 … T_c-1
    // Step A – prefetch next K,V into SMEM
    wait_for( K_j ).postload()
    wait_for( V_j ).postload()

    // Step B – overlap his own e.g.
    if j > 0:
        // use earlier K_block to launch GEMM1
        launch WGMMA compute(P_prev = Q · K_{j-1}ᵀ)
        // concurrent: while GEMM1 starts,
        // consumers execute softmax on previous score block
        // which was produced by Step B of j-1

    // Step C – start second GEMM now that V_{j-1} ready
    if j > 0:
        launch WGMMA compute(O += P_prev · V_{j-1})
```

The first iteration (`j=0`) is special because there is no “previous” block yet; we treat it separately. After this warm-up, from `j=1` onward each iteration performs *two* overlapping WGMMA launches:

* **GEMM1** – produce the next probability tile (`Q·K_jᵀ`).  
* **GEMM2** – consume previous probability tile to accumulate output (`P_{j-1}·V_{j-1}`).

The softmax part sits right between them: once GEMM1 finishes for block `j`, its result becomes input to softmax; while that softmax runs, WGMMAs for block `j+1` are already running.

---

## 4. How this saves time

Consider FP16 on an H100:

| Operation      | FLOPs           | Expected TFLOPs/s per SM          |
|----------------|-----------------|-----------------------------------|
| MatMul (WGMMA) | ~123 million    | ~989 TFLOPs/s                     |
| Exponential    | ~2 million      | ~3.9 TFLOPs/s                     |

If you sit idle after every matmul just looking for exponents you waste more than half an SM’s compute budget. By interleaving exponents under an ongoing matmul you achieve near full utilization:

```
TPU Utilization ≈ Time(matmul) / Time(matmul + extra_exponential)
```

Unit tests on production workloads show roughly **10–15 % absolute gains** in FLOP throughput per SM when ping‑ponging versus serial execution—512 GFLOPs higher “back‐of‐the‐envelope” on large heads.

---

## 5. Summary & Takeaways

* **Warp‑specialization** lets us separate data movement from computation without interference.
* The *ping‑pong schedule* literally pings one warpgroup to compute softmax while bouncing another onto an asynchronous Tensor Core matmul.
* Overlap reduces idle time: when a Tensor Core sits waiting for exponents or reduces, other warps keep flying.
* A two–stage pipelined design—first WARPGROUP S produces scores and reduces them; second WARPGROUP S consumes those reduced → continues computing next block—creates steady state performance where every warp group always has something useful to do.
* On modern Hopper GPUs this results in up to **70–80 % theoretical TFLOPs utilization**, easily beating hand‑tuned handcrafts built only around SSE or BF16 logic.

The *FlashAttention‑3* kernel embodies these ideas beautifully; developers interested in reimplementing or tweaking attention kernels should familiarize themselves with warp‑specialized pipelines before improvising any other optimization tricks.

# FlashAttention‑3 in Action: Benchmarks You Can Trust  

In the world of large language models, the self‑attention layer is both a blessing and a curse: it unlocks contextual reasoning, yet it is the computational choke‑point. The FlashAttention family of kernels tackles this head on, and the newest addition – FlashAttention‑3 – brings a fresh mix of asynchrony and low‑precision arithmetic to squeeze even more performance out of NVIDIA’s Hopper H100 GPUs. In this post we walk through the numbers, translate the raw TFLOPs into everyday inference times, and see how the new kernel stacks up against cuDNN and Triton.

---

## 1. What changed in FlashAttention‑3?  

- **Warp‑specialized asynchronous pipelines** – one warp group ‘produces’ data (loads queries, keys, values), a distinct group ‘consumes’ it (does matrix multiplies and softmax). The two run in lockstep, keeping the Tensor Core busy while the softmax unit does its work.  
- **Ping‑pong GEMM/softmax overlap** – by staggering two consecutive matrix multiplications (Q × Kᵀ and P × V) across warps, we hide almost all of the exponential operations inside the high‑throughput Tensor Core compute.  
- **FP8 support with block quantization & random orthogonal masking** – enables us to hit ​1.2 PFLOPs/s on H100 while keeping numerical error 2½× smaller than naïve per‑tensor FP8 attention.

These changes are not just theoretical: the benchmarks below show real speedups for a variety of workload settings.

---

## 2. The experimental setup  

| Item | Value |
|------|-------|
| Hardware | NVIDIA H100 SXM5 (80 GB) |
| Driver/Toolkit | CUDA 11.8 + cuDNN 9 |
| Workloads | 2–head or multi‑head attention with head sizes 64/128/256 |
| Sequence lengths | 512 → 16 k tokens (batch size adjusted to keep total tokens ≈ 16k) |
| Measurement | GPU wall‑time for forward pass + backward pass (where applicable) |

We compare four kernels:

1. **Standard PyTorch attention** – naïve implementation that materialises \(\mathbf{S}\) and \(\mathbf{P}\) in global memory.  
2. **FlashAttention‑2** – earlier warp‑parallel version that still leaves Tensor Core idle at times.  
3. **FlashAttention‑3 (FP16)** – full asynchrony pipeline in FP16 precision.  
4. **FlashAttention‑3 (FP8)** – same pipeline but using FP8 Tensor Cores with block quantization & incoherent processing.

---

## 3. Forward pass: raw TFLOPs

The core metric we report is *throughput*: the GeForce/H100 GPU’s theoretical peak is ≈ 9 TFLOPs for FP16 matrix multiplies and ≈ 18 TFLOPs for FP8 on Hopper. In practice, FlashAttention‑3 reaches:

| Head size | Seq len | FP16 TFLOPs/s | FP8 TFLOPs/s |
|-----------|---------|---------------|--------------|
| 64        | 4 096   | 620           | *–*          |
| 128       | 4 096   | 740           | *–*          |
| 256       | 4 096   | 580           | *–*          |
| 128       | 8 192   | **740**       | *–*          |
| 128       | 16 k    | **730**       | *–*          |

(Values are averages over three runs; error bars < 1%.)

A few things stand out:

- **75 % utilisation** for FP16 at long sequences – that’s comparable to an optimal GEMM kernel and far above FlashAttention‑2’s ≈ 35 %.  
- With **FP8**, when we push to sequence lengths ≥ 8k we hit ~1.2 PFLOPs/s, essentially saturating half of the H100’s theoretical FP8 capacity.

---

## 4. Causal masking vs dense

Causal masks are common in autoregressive models; they drop roughly half of the triangular entries from \(\mathbf{S}\). That reduces compute but also hurts memory locality.

> **Result:** For causal masking in FP16, FlashAttention‑3 remains ~10–15% faster than cuDNN’s bespoke kernel for seq len ≥ 8k, whereas non‑causal gains can be >30%. FP8 shows an even larger stride: at seven thousand tokens it outpaces cuDNN by ~25% while maintaining numerical error < 2× that of a naïve per-tensor FP8 implementation.

The kernel’s ability to keep Tensor Cores saturated even when half of the matrix is zeroed explains this resilience.

---

## 5. Backward pass performance

Gradient computation is even harder: we must reverse three GEMMs plus additional softmax derivatives.

> **Benchmarks** (forward + backward):

| Head size | Seq len | Acceleration over FlashAttention‑2 |
|-----------|---------|-----------------------------------|
| 128       | 4 096   | +1.5×                              |
| 128       | 8 192   | +1.6×                              |

The extra factor comes from overlapping *backward* softmax operations with corresponding matrix multiplications via the same ping‑pong strategy used in forward flow.

---

## 6. From FLOPs to LLM inference time

We often care about real end‑to‑end inference latency rather than raw throughput. Let’s translate these numbers into a typical transformer block cost:

```text
FlOps per token = K · d · h · seq_len
Inference time = FlOps / TFLOPs
```

For a BERT‐style block with \(h=12\), \(d=64\), seq_len=512:

- **Standard PyTorch:** ~12 ms
- **FlashAttention‑2:** ~7 ms
- **FlashAttention‑3 (FP16):** ~3½ ms
- **FlashAttention‑3 (FP8):** ~2 ms

At longer context (seq_len=4096), FlashAttention‑3 collapses latency from ~120 ms → ~28 ms (FP16) or ~20 ms (FP8). That means real-world inference on pasting multiple documents together becomes more tractable.

---

## 7. Accuracy check

Speed is only part of the story; we must ensure output fidelity stays high.

By generating synthetic Q/K/V tensors with heavy “outliers” (0.1% of entries boosted by an extra Gaussian noise ±10), we compute RMSE against an exact double‐precision reference:

- **FP16 FlashAttention-2 / -3:** similar RMSE (~0.7e−03).
- **FP8 baseline (per-tensor scaling):** RMSE ≈ 0.28e−02.
- **FP8 FlashAttention-3 with block quantization & incoherent processing:** RMSE ≈ 0., only 0·110e−02 → factor ≈ 2½ smaller than baseline.

Thus, the high precision engine does not sacrifice correctness even when operating in aggressive FP8 mode.

---

## 8. Takeaway checklist

> • _Use FW+FF_?  
>   For modern LLMs on H100, switch to FlashAttention‑3 if you need ≤20 ms per forward pass on long context (>8192 tokens).

> • _FP16 vs FP8_?  
>   If you’re OK with a tiny bit more error but need max throughput, go FP8 with block quantization; otherwise stay in FP16 for guaranteed accuracy.

> • _Causal masking_?  
>   Even masked workloads see roughly same acceleration; don’t worry about choosing between 💥 vs 🦙 modes.

> • _Backpropagation overhead_?  
>   Expect similar speedups (~1½×) as forward; no additional plug‐in needed beyond setting the correct `use_fp32_softmax` flag.
