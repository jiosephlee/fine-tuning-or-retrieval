# Warp‑Specialized Pipelines: Overlapping Softmax and Matrix Multiplications

## Why the softmax step matters

In a Transformer’s self‑attention layer the forward pass looks like

```
S = Q · Kᵀ           // dot‑product matrix
P = softmax(S)
O = P · V
```

On a GPU the matrix product (`Q·Kᵀ` and later `P·V`) is done with the Tensor Cores (WGMMA), while `softmax` is a chain of integer/floating‑point and exponential instructions that run on the general‑purpose CUDA cores. The two kernels are tightly coupled: we need `S` before we can compute `P`, and we need `P` before we can compute `O`. Naïvely, that means each iteration of the inner loop waits for the previous one to finish.

Modern GPUs are thousands of units of execution: many **warps** per streaming multiprocessor (SM), each able to issue independent instructions. Hopper (the H100 architecture) adds asynchronous instruction execution and a Tensor Memory Accelerator (TMA). These features unlock a subtle trick – *warp‑specialization* – that lets us hide latency and double‑tap the hardware’s throughput.

---

## 1. Warp‑Specialization in a nutshell

A *warp* is a group of 32 threads that run in lockstep. In *warp‑specialized* kernels we split a CTA (thread block) into two **warpgroups**:

| Warpgroup | Role                | What it does                                |
|-----------|---------------------|---------------------------------------------|
| Producer  | Data movement only  | Loads chunks of Q, K, V from global memory  |
| Consumer  | Computation only    | Runs WGMMA and softmax on data already in SMEM |

Because the producer warps never compute, they can free more registers for TMA loads. The consumer warps, in turn, don’t waste cycles on memory traffic – they’re pure compute. The key is that these two groups live inside the same CTA, so they share on‑chip shared memory (SMEM) as a circular buffer: each producer load “writes” into stage 0 of SMEM; after the consumer finishes with that stage it “releases” it for the next block.

---

## 2. The ping‑pong schedule

In the vanilla implementation (what we call **FlashAttention‑2**), each iteration does:

1. Load new K,V blocks → SMEM  
2. Compute `Q·Kᵀ` → GEMM  
3. Compute `softmax(S)` → exponential + reductions  
4. Compute `P·V` → GEMM  

All four steps happen in sequence; nothing else happens while we wait for a GEMM to finish or while the softmax routine drains down importance.

With *ping‑pong* we let **one warpgroup** be busy with softmax **while another** is busy running the next GEMM:

```
+-----------+-----------+-----------+
| Warpgroup |
|     0     |   <-   |   Warpgroup |
|   prod/   |   ←     |     cons/   |
+-----------+-----------+-----------+

         |---------------|
         |    Stage 0    |
         +---------------+

         ~~~~~~~~~~~~~~~~
```

At time t:

* Warpgroup 0 finishes its first GEMM (`Q·K₁ᵀ`) and immediately starts producing softmax for block 1.
* While it’s computing exp & reducing rows (harder part), Warpgroup 1 has already started its second GEMM (`Q·K₂ᵀ`) using data that is already loaded by Warpgroup 0’s producer stage.

When Warpgroup 0 finishes softmax for block 1, Warpgroup 1 continues with its second softmax, and so on—each warpgroup alternates (ping‑pong) between “softmax” work and “GEMM” work.

Because Tensor Cores saturate at roughly 10× higher throughput than special‐function units (exponential), this overlap means: when one SM is grinding through an exponential, another is putting a tens-of-operations tensor multiply in motion simultaneously.

---

## 3. Step–by–step look at the 2‑stage pipeline

Below’s an abbreviated version of the real kernel logic reversed from pseudocode in FlashAttention‑3:

```text
for j = 0 … T_c-1
    // Step A – prefetch next K,V into SMEM
    wait_for( K_j ).postload()
    wait_for( V_j ).postload()

    // Step B – overlap his own e.g.
    if j > 0:
        // use earlier K_block to launch GEMM1
        launch WGMMA compute(P_prev = Q · K_{j-1}ᵀ)
        // concurrent: while GEMM1 starts,
        // consumers execute softmax on previous score block
        // which was produced by Step B of j-1

    // Step C – start second GEMM now that V_{j-1} ready
    if j > 0:
        launch WGMMA compute(O += P_prev · V_{j-1})
```

The first iteration (`j=0`) is special because there is no “previous” block yet; we treat it separately. After this warm-up, from `j=1` onward each iteration performs *two* overlapping WGMMA launches:

* **GEMM1** – produce the next probability tile (`Q·K_jᵀ`).  
* **GEMM2** – consume previous probability tile to accumulate output (`P_{j-1}·V_{j-1}`).

The softmax part sits right between them: once GEMM1 finishes for block `j`, its result becomes input to softmax; while that softmax runs, WGMMAs for block `j+1` are already running.

---

## 4. How this saves time

Consider FP16 on an H100:

| Operation      | FLOPs           | Expected TFLOPs/s per SM          |
|----------------|-----------------|-----------------------------------|
| MatMul (WGMMA) | ~123 million    | ~989 TFLOPs/s                     |
| Exponential    | ~2 million      | ~3.9 TFLOPs/s                     |

If you sit idle after every matmul just looking for exponents you waste more than half an SM’s compute budget. By interleaving exponents under an ongoing matmul you achieve near full utilization:

```
TPU Utilization ≈ Time(matmul) / Time(matmul + extra_exponential)
```

Unit tests on production workloads show roughly **10–15 % absolute gains** in FLOP throughput per SM when ping‑ponging versus serial execution—512 GFLOPs higher “back‐of‐the‐envelope” on large heads.

---

## 5. Summary & Takeaways

* **Warp‑specialization** lets us separate data movement from computation without interference.
* The *ping‑pong schedule* literally pings one warpgroup to compute softmax while bouncing another onto an asynchronous Tensor Core matmul.
* Overlap reduces idle time: when a Tensor Core sits waiting for exponents or reduces, other warps keep flying.
* A two–stage pipelined design—first WARPGROUP S produces scores and reduces them; second WARPGROUP S consumes those reduced → continues computing next block—creates steady state performance where every warp group always has something useful to do.
* On modern Hopper GPUs this results in up to **70–80 % theoretical TFLOPs utilization**, easily beating hand‑tuned handcrafts built only around SSE or BF16 logic.

The *FlashAttention‑3* kernel embodies these ideas beautifully; developers interested in reimplementing or tweaking attention kernels should familiarize themselves with warp‑specialized pipelines before improvising any other optimization tricks.
