\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### How does FP8 WGMMA’s k‑major constraint affect memory layout for value tensors in FlashAttention‑3?
Question:
Section 3.3 states that FP8 WGMMA only accepts k‑major operands and that a value tile must be contiguous in the sequence length dimension. Since typical value tensors are stored contiguous along the head dimension, how does FlashAttention‑3 achieve the required layout without expensive preprocessing? Can you walk through the in‑kernel transpose using LDSM/STSM and explain why it works for FP8 but not for FP16?
Answer:
**Short answer**  
For FP8 Tensor‑Core “WGMMA” only **k‑major** operands are accepted.  
In self‑attention we only need the **value** tiles to be k‑major – i.e. contiguous in the sequence‑length dimension – while the **head** dimension is laid out contiguously in memory (the usual “head‑major” layout).  
FlashAttention‑3 therefore loads a *block* of values into shared memory and, before the **second** WGMMA (the Rs‑GEMM that multiplies the softmax‑rescaled scores by \(V\)), it **transposes that block in‑kernel** so that its indexing becomes k‑major. The transpose is done with the LD/STM matrix intrinsics (LDSM/STSM), which efficiently copy 8×8 tiles of 128 bytes while performing a row–column swap. Because each tile is isolated, the transpose can run concurrently with the two WGMMA operations on adjacent key/value blocks (the “ping‑pong” overlap). That is why no expensive preprocessing kernel is needed.

The same trick does **not** work for FP16 because, contrary to FP8, FP16 WGMMA happily accepts both mn- and k‑major operands. Therefore FlashAttention‑3 keeps the value tiles in their natural head‑major layout for FP16, avoiding the transpose altogether.

---

## 1.  Why FP8 needs k‑major

From *Section 3.3* of the paper:

> “Given a GEMM call to multiply \(A\times B^{\top}\) for an \(M\times K\) matrix \(A\) and an \(N\times K\) matrix \(B\), we say that the \(A\) or \(B\) operand is **mn‑major** if it is contiguous in the outer \(M\) or \(N\) dimension, and **k‑major** if it is instead contiguous in the inner \(K\)-dimension. Then for FP16 WGMMA both mn‑major and k‑major input operands are accepted … but for **FP8 WGMMA only the k‑major format is supported**.”

In multi‑head attention each head has its own projected tensors:
\(Q,K,V \in \mathbb{R}^{N\times d}\).
Typical layouts store all heads contiguously along the second dimension—i.e., a *head‑major* layout:
\[ V \;=\;[\; v_0,\;v_1,\;...,\,v_{\text{heads}-1}\;] \]
So when we slide a block of values through shared memory, they are contiguous along *heads*, not along *sequence length*.  
For FP8 we must have them contiguous along *sequence length* to be fed into WGMMA as k‑major.

---

## 2.  In‑kernel transpose with LDSM/STSM

The tensor core instruction set offers two matrix load/store intrinsics:

* `ldmatrix` (LDSM): warpwise load an 8×8 tile of 16 bit entries from shared memory into registers.
* `stmatrix` (STSM): warpwise store an 8×8 tile from registers back to shared memory.

Although documentation specifies 16-bit entries, when packed two FP8 values into a 16-bit word one can still use these intrinsics; each word then holds two consecutive 8-bit elements.

Because LDSM/STSM perform a *row↔column* copy during load/store, we can perform a **transpose‐by‐copy** on an 8×8 block:

```
LDSM   // load rows r0..r7 from shared -> registers R0..R7
// perform byte permutations so that R0..R7 now contain columns c0..c7
STSM   // store columns as rows back to shared
```

The critical point is that this operation requires only a few register moves and no shuffle instructions across threads—something that would otherwise spill into GPU registers and hurt occupancy.

When executing FlashAttention-3:

1. **Producer warps** load \(K_j,V_j\) blocks from global memory into shared memory using TMA.
2. For values (\(V_j\)) before they are consumed by the **second GEMM**, a _shadow_ threadgroup—usually part of the same CTA—executes LDSM//STSM on that block.
   The transformed block now has its *sequence length* axis as the outermost index (k-major).
3. The consumer warps then invoke `WGMMA` for \(\tilde{P}_i^{(j)}V_j\). Because `V_j` is now k‑major, FP8 WGMMA accepts it without error.

All this happens while overlapping with previous GEMM iterations (ping‐pong scheme), so no extra kernel launch or transfer stalls occur.

---

## 3.  Why zero cost for FP16

FP16 WGMMA supports both orientations, so FlashAttention-3 simply feeds `V` directly to WGMMA without any transpose:

```
WGMMA_QK = Q_i × K_j^T          // SS-GEMM
WGMMA_PV = Ptilde × V_j          // RS-GEMM
```

If `V` were in head-major form, WGMMA would still read it correctly because CUDA’s Tensor Core instruction automatically reinterprets operand layout based on access stride. Hence there is no need for an extra LDSM/STSM step and no register budget spent on transpositions.

In contrast, skipping the transpose for FP8 would trigger a validation error at launch time: “FP8 Tensor Core expects k-major operand”, which explains why FlashAttention-3 can run efficiently only with this small in-kernel tile transpose.

---

## 4.  Summary

- **FP8 restriction:** Only k-major operands → value tiles must be contiguous across sequence length.
- **Typical layout:** Head-major → conflict with requirement.
- **Solution:** Load a value tile → transpose it *in-core* using warp-wise LDSM/STSM → feed to second WGMMA.
- **Overlap:** Transpose runs concurrently with preceding GEMMs thanks to asynchronous warp-specialized pipelines.
- **No preprocessing kernel needed:** All work performed inside the persistent CUDA kernel’s shared memory.
- **FP16 case:** No need for transpose because Tensor Cores accept both layouts; therefore CPU/GPU register pressure stays lower.

Thus FlashAttention‑3 satisfies FPGA’s layout constraints for FP8 while keeping memory traffic minimal and retaining full asynchrony benefits—a design choice that would not be necessary (and would even be wasteful) for FP16.
