# From Code to Calculus: Why Programming Skills Boost Mathematical AI

Large language models (LLMs) are often praised for their ability to reason, but the underbelly of that reasoning is a well‑structured chain of training steps. A recently published paper on *DeepSeekMath* (a 7‑billion‑parameter model) offered a clear‑cut experiment that challenges the intuitive belief we might have about mathematics and coding: **the tokens that teach a model to write code are also the tokens that help it solve long, multi‑step math problems**. In this post we unpack the evidence, explain why this linkage exists, and consider what it could mean for AI‑powered learning tools.

---

## 1. The Experiment in a Nutshell

The authors compared several training regimes on a small 1.3‑B parameter model—

| Regime | Training data | Key result |
|--------|---------------|------------|
| **Code ➜ Math** | 400 B code tokens, then 150 B math tokens | Best performance on *GSM8K* and *MATH* **with** program use |
| **General ➜ Math** | 400 B generic language tokens, then 150 B math tokens | Worse than the code‑first regime on programmatic tasks |
| **Math only** | 150 B math tokens | Poor on programmatic tasks |
| **Mix (one‑stage)** | 400 B code + 150 B math tokens in one pass | Gains in both coding and math without program use |

Key take‑aways:

- **Code pre‑training improves “tool‐aided” math reasoning**—the model becomes better at writing Python scripts that calculate intermediate values or solve equations.
- **Even without using Python**, acquiring code experience still nudges the model forward on pure math reasoning, but less dramatically.
- When code and math data are interleaved from the start, the model avoids “catastrophic forgetting” – a common pitfall where adding new data undoes what you’ve already learned.

---

## 2. Why Code Tokens Should Mushroom Math Skill

You might ask: “These appear unrelated—coding is procedural; math is about symbols.” The deep link lies in the **linguistic structure** both domains share:

1. **Stepwise Decomposition**  
   Both writing a program and solving a textbook example involve breaking down problem statements into smaller sub‑tasks and expressing them sequentially.

2. **Explicit Syntax and Formalization**  
   Programming demands precise syntax (`for`, `if`, `{}`), just as mathematical proofs do (`∴`, `∃`, `∀`). Exposure to rigid formal languages train the model’s prediction head to keep track of context boundaries.

3. **Dependency Tracking**  
   Variables in code must be defined before use; similarly, every algebraic step depends on previously established facts. Models that learn variable scoping tend also to “remember” earlier reasoning steps more reliably.

4. **Error Signaling**  
   Compilers throw syntax errors; mathematicians spot logical fallacies. Both force the model to learn patterns that signal dissonance between an expected and an actual result.

In short, training on code feels like teaching an LLM how to think in systems: clarify input → outline operations → compute → verify.

---

## 3. The Stakes for Educational AI

### A) Screener Bots vs Tutor Bots

- **Screeners** need crisp answers quickly; they can benefit from a model that can *auto–solve* with Python when possible.
- **Tutors** need explanatory text and stepwise guidance; having a foundation in procedural logic helps produce clearer justifications.

The experiments suggest that models inheriting coding discipline naturally become better at constructing coherent solution narratives—a useful property for automatic grading or interactive tutoring systems.

### B) Multilingual Reach

The paper also reported *multilingual* gains (English + Chinese). Since many programming languages look similar across locales (e.g., `for`, `while`), the same structural lessons spill over into multiple human languages. That means one core training strategy can help creators offer high‑quality learning material worldwide without retraining separate language towers.

### C) Tool Integration Is No Longer Future‑Proof

In AI‑in‑education demos, we’re moving towards *“tool–integrated” reasoning*: an LLM writes Python or calls a symbolic engine to get intermediate results. A model grounded in coding habits will seamlessly pull its own toolset into conversations—reducing hallucination risk when computing with numbers or algebraic expressions.

---

## 4. Caveats & Next Steps

While striking, these findings raise some prudential questions:

1. **Overreliance on Code Equivalence?**  
   The study used standard open‑source repos and web snippets as code data. The quality varies wildly; if we polluted the dataset with poorly written scripts, we might see adverse effects.

2. **Model Capacity Matters**  
   Mixing code + math data at scale seems beneficial for larger models but led to forgetting for very small ones (1 B params). Scaling up likely smooths this trade‑off.

3. **Beyond Python**  
   Future work could diversify programming languages—JavaScript, R, Julia—in order to see if domain specialists impute deeper subject knowledge into mathematical domains like statistics or differential equations.

4. **Curriculum Design for Students**  
   If coding helps, should early secondary education embed introductory programming before high school calculus? Continuous research could quantify how learning sequence affects conceptual mastery.

---

## 5. Bottom Line

The DeepSeekMath paper does not merely decorate numbers on a leaderboard; it offers a concrete insight: **“learning how to write programs trains an LLM how to methodically solve mathematical problems.”**

For practitioners building AI tutoring platforms:

- Add diverse coding data early in your pre‑training pipeline.
- Keep your curriculum selves bilingual or multilingual for wider impact.
- Leverage program-of-thought prompts to unlock richer explanation style while preserving precision.

Ultimately, this convergence of code and calculus points toward one big picture: AI models excel when they practice *structured problem solving*—whether it takes the form of shell commands or integration by parts—and learning from one discipline enriches another.*

# Mining Math from the Web: Building a 120‑Billion‑Token Corpus in Minutes

Large language models that can do math are only as good as the data they see.  The headline result in the *DeepSeekMath* paper is that a 7 B‑parameter model, pre‑trained on **120 B tokens of web‑extracted mathematical text**, beats most open‑source peers on the competition‑level MATH benchmark.  How did the authors pull off that data avalanche?  Below is a walk‑through of their pipeline, distilled into actionable steps that anyone can follow to build a high‑quality, domain‑specific corpus from Common Crawl.

> **TL;DR** –  
> *Seed → fastText → filter → collect → annotate → iterate.*  
> 4 iterations yield a clean, multilingual math corpus that is far larger than any other publicly available collection and gives a 7 B model performance comparable to closed‑source giants.

---

## 1. The starting point: a tiny but rich seed

The authors began with **OpenWebMath** – a curated set of ~15 B tokens that already crawled math websites.  This collection served two purposes:

1. **Positive examples** for an initial classifier.
2. **Reference for sanity‑checks** later (to detect contamination).

Because OpenWebMath focuses on instructional math content (forums, tutorials, exercises), it is highly representative of the style and vocabulary we want downstream models to learn.

---

## 2. Train a lightweight fastText recognizer

FastText – the language detection library from Facebook – was chosen for its speed and simplicity.

| Parameter | Value | Why? |
|-----------|-------|------|
| Vector dim | 256 | Enough to encode subtle math terminology. |
| Learning rate | 0.1 | Fast convergence on small data. |
| ngram max | 3 | Captures multi‑word phrases like “square root” or “logarithmic function.” |
| Min word freq | 3 | Filters out noise while keeping rare technical terms. |
| Epochs | 3 | Keeps training under minutes on modern GPUs. |

**Training data split**

- **400 k positive samples** (randomly drawn from OpenWebMath).  
- **400 k negative samples** (random Common Crawl pages chosen to be non‑mathy).

Sufficient positive/negative pairs give the model just enough contrast to start distinguishing maths pages without overfitting.

---

## 3. Reduce the search space with deduplication

Common Crawl is gigantic: tens of billions of URLs across countless languages.  
The authors first trimmed it down:

- **URL‑based deduplication** – identical host+path entries collapsed.
- **Near‐deduplication** – aggressive heuristic to remove near-duplicates (e.g., mirrored sites).

Result: ~40 B distinct HTML pages – still huge but tractable for one pass through fastText.

---

## 4. Recall mathematical pages

Now every page in the reduced crawl is scored by fastText; only the top scorers survive.

> **Note about contamination** – Before keeping anything, they ran a *contamination filter*: any fragment that matched exactly a substring from any evaluation benchmark (GSM8K, MATH, CMATH, AGIEval) in a sliding window of size 10 was discarded. This guarantees test data never leaks into training.

The first pass produced roughly **40 B tokens**, but the authors kept it conservative – only top‑ranked pages were used in experiments and no more than ~56% of these tokens were retained after filtering.

---

## 5. Identify “math domains” and improve diversity

The first batch still missed many valuable sites because fastText had learned only from OpenWebMath’s narrow distribution.  

To augment it:

1. **Domain analysis** – group all URLs by their base domain (`example.com`).  
2. For each domain compute what percentage of its pages were already selected.
3. Domains with >10% capture ratio were labeled *math‐rich* (e.g., `mathoverflow.net`, `planetmath.org`).  
4. For these domains manually annotate the most characteristic URL patterns that truly contain math content (`/questions`, `/theorems`, etc.).  
5. Pull every unrecall’d page under those patterns into the seed set and retrain fastText.

This loop was iterated four times; after each iteration rapid diminishing returns were observed – by the fourth round >98% of pages that could be captured had already been included.

The result? A corpus comprising **35.5 M distinct webpages**, totaling ~120 B tokens!  This size exceeds Minerva’s math subset by ~7× and OpenWebMath by ~9×.

---

## 6. Multilingual hygiene

Because *Common Crawl* contains many languages, simply pulling everything would bias towards English signals and hurt non‑English performance, especially Chinese which is pausable for many open models.

During preprocessing:

- Split tokens by language indicator (e.g., ICU language tag).
- Retain all non‑English tokens but put them through an extra quality filter (shorter token lists are discarded).
- Verify that word frequency distributions for Chinese show realistic mathematical terminology – e.g., `微积分`, `线性代数`.  

This approach improved Chinese benchmark scores (MGSM‑zh, CMATH) without hurting English performance.

---

## 7. Quick sanity checks before pre‑training

To ensure the corpus genuinely enriches reasoning rather than just bulk:

1. Fine‑tune a cheap **1–2 B parameter** checkpoint on each candidate corpus (OpenWebMath, MathPile, Proof-Pile-2, etc.) for ~150 B token stages.
2. Evaluate on eight *low‑shot* math benchmarks using chain-of-thought prompting.
3. Compare accuracy curves over token budget.

Result: Models trained on DeepSeekMath consistently outranked those trained on Proof-Pile-2 or MathPile even when those corpora were smaller or more heavily curated for arXiv content.

---

## Recap: The pipeline you can copy

```bash
# Step-by-step recipe
# ---------------------------------------------

# 1️⃣ Seed selection
seed_corpus="OpenWebMath"

# 2️⃣ Prepare seed positives/negatives
positive=$(shuf -n400000 "$seed_corpus")
negative=$(shuf -n400000 "common_crawl_urls.txt")

# 3️⃣ Train fastText
fasttext supervised -input <(echo "$positive") -input <(echo "$negative") \
   -dim 256 -lr .1 -epoch 3 -wordNgrams 3 -minCount 3 -output math_finder

# 4️⃣ Dedup Common Crawl
dedupe common_crawl_html.txt > deduped_crawl.txt

# 5️⃣ Recall
fasttext predict-prob --verbose=1 math_finder.bin < deduped_crawl.txt \
   > recall_scores.txt

# 6️⃣ Filter top-k per day / domain logic
bash filter_top.sh recall_scores.txt > selected_pages.txt

# 7️⃣ Contamination check
python contam_check.py selected_pages.txt evaluated_benchmarks/

# 8️⃣ Add new domains if recall low:
for domain in $(detect_low_density_domains selected_pages.txt); do
   annotate_pattern "$domain"
   add_to_seed "$domain"
done
train_fasttext_again()
```

The trick lies in *iterating*: keep swapping newly annotated samples back into training until recall saturates.

---

## Why this matters beyond math

While DeepSeekMath focuses on mathematics—the field where structure matters deeply—the same recipe applies to any niche domain:

- **Legal** – start with statutes & case law.
- **Biomedical** – begin with PubMed abstracts tagged as “review”.
- **Finance** – seed with analyst reports tagged “earnings”.

You’ll just need to adapt:
- The initial seed corpus,
- Domain heuristics for selection,
- Language filters peculiar to your niche.

And remember: measure early with quick few-shot benchmarks; if your finetuned model lands plateauing early, iterate again.

---

## Takeaway

DeepSeekMath’s success reveals two key insights:

1. **Web extraction + smart filtering beats massive arXiv dumps** – common web pages carry far more untapped reasoning signals when captured correctly.
2. **Iterative supervision + multilingual attention pays off** – gathering diverse mathematical voices not only avoids overfitting to English but gives cross-lingual transfer gains.

With this guidance you’re now equipped to turn raw Common Crawl into your own domain goldmine—a key ingredient for pushing LLM reasoning beyond what closed models can do today. Happy mining!



# Group Relative Policy Optimization (GRPO): Reinforcement Learning Made Lean for LLMs

**TL;DR** – GRPO is a tiny tweak to the classic Proximal Policy Optimization (PPO) that removes the value‑function critic and replaces it with a simple *group‑based baseline*. The result is a memory‑friendly reinforcement‑learning pipeline that gives 5–10 % absolute gains on hard math benchmarks such as GSM8K and competition‑level MATH, all while keeping the training speed of a 7 B language model.

---

## 1. Why RL Matters for Math‑heavy LLMs

Large language models (LLMs) have excellent few‑shot reasoning abilities, but they still stumble on problems that require many logical steps:

| Benchmark | 7 B LLM baseline (CoT) | After RL (PPO / GRPO) |
|-----------|------------------------|-----------------------|
| GSM8K     | 77 %   | 88–90 % |
| MATH      | 46–50 % | 51–52 % |

Reinforcement learning (RL) fine‑tuning boosts the policy toward higher‑reward outputs by learning from its mistakes. In this space, PPO dominates because of its clipped surrogate objective and stable training. However, PPO carries a major drawback for our use case: **the actor‑critic architecture blows up GPU memory**.

---

## 2. Classical PPO in a Nutshell

PPO trains an *actor* (the LLM policy $\pi_\theta$) and a *critic* $V_\psi$ that estimates the expected reward for every token generation step. The standard objective is

\[
\mathcal{J}_{\text{PPO}}(\theta) 
= \mathbb{E}\!\left[ \sum_{t} \min\!\left(
\frac{\pi_\theta(o_{t}\mid q,o_{<t})}{\pi_{\theta_{\text{old}}}(o_{t}\mid q,o_{<t})}\,
A_t,\;
\text{clip}\!\left(
\frac{\pi_\theta(o_{t}\mid q,o_{<t})}{\pi_{\theta_{\text{old}}}(o_{t}\mid q,o_{<t})},1-\varepsilon,1+\varepsilon
\right) A_t
\right)\right]
\]

where:
* $q$ – question prompt,
* $o_t$ – token at step $t$,
* $A_t = r_t - V_\psi(o_{<t})$ – *advantage*, i.e. how much better this token was than the critic’s estimate.

The critic has to be a separate neural network of comparable size to the policy. For a 7 B model, this means extra **4–7 GB** of parameters per GPU batch – untenable when you already have to generate multiple outputs per question.

---

## 3. The Key Insight: Reward is Comparative

In math reasoning, the *reward model* used during RL doesn’t output an absolute score for each token; it scores complete answers and returns **relative** preferences:

- “Answer A beats Answer B” → reward difference $\Delta r = r_A - r_B$.
- Our training data is pairwise comparisons between two outputs on the **same** question.

This relative nature means we can estimate a useful baseline *without* building a separate neural value function. If we generate several candidate answers for the same question, averaging their rewards gives us exactly the baseline we need.

---

## 4. GRPO Formulation

### 4.1 Group Sampling

For each question $q$, sample **$G$ outputs**  
$\{o_1,\dots,o_G\} \sim \pi_{\theta_{\text{old}}}(\cdot \mid q)$
using simple greedy or nucleus sampling.

### 4.2 Reward Normalization

Compute rewards $\{r_1,\dots,r_G\}$ using a pretrained reward model (trained on pairwise preference data). Normalize them within the group:

\[
\tilde{r}_i = \frac{r_i - \overline{r}}{\sigma}
,\quad
\overline{r} = \frac{1}{G}\sum_j r_j,\;
\sigma = \sqrt{\frac{1}{G-1}\sum_j(r_j-\overline{r})^2}
\]

The centered reward $\tilde{r}_i$ becomes our **advantage** for every token in output $o_i$:
$\hat A_{i,t} = \tilde{r}_i$.

### 4.3 Objective Without Critic

GRPO now maximizes:

\[
\mathcal{J}_{\text{GRPO}}(\theta)
=
\E_{q,\,o_1,\dots,o_G}
\Bigg[
   \frac1G
   \sum_{i=1}^G
   \frac1{|o_i|}
   \sum_{t=1}^{|o_i|}
   \min
   \Big(
      \frac{\pi_\theta(o_{i,t}\mid q,o_{i,<t})}{\pi_{\theta_{\text{old}}}(o_{i,t}\mid q,o_{i,<t})}
      \hat A_{i,t},
      ~
      \text{clip}\big(
         \frac{\pi_\theta(o_{i,t}\mid q,o_{i,<t})}{\pi_{\theta_{\text{old}}}(o_{i,t}\mid q,o_{i,<t})},
         1-\varepsilon,\,1+\varepsilon
      \big)\hat A_{i,t}
   \Big)
   - \beta\, D_{\rm KL}(\pi_\theta\,||\,\pi_{\rm ref})
   \Bigg]
.\]

Key differences from PPO:

| Feature | PPO | GRPO |
|---------|-----|-------|
| Critic \(V_\psi\) | Yes (separate net) | No |
| Baseline | learned \(V_\psi(o)\) | group average reward |
| Advantage | \(A_t = r_t - V_\psi(o)\) | \(A_t = r_i - mean(r)\) |
| Extra memory | high | low |

Because we evaluate only *full answers*, not per-token values, we avoid training or storing a value network entirely.

---

## 5. Practical Implementation Details

- **Batch size:** 1024 questions  
- **Group size \(G\):** 64 outputs per question (more than enough to estimate a stable group mean).  
- **Learning rates:** policy \(1\times10^{-6}\), reward model \(2\times10^{-5}\).  
- **KL penalty coefficient \(β\):** 0.04 to keep the policy from drifting too far from its reference (the last SFT checkpoint).  
- **Iterative RL loop:** after each overall RL epoch, re-train the reward model on newly generated answer pairs (10 % replayed history). This prevents reward drift as the policy improves.

---

## 6. Empirical Gains

On DeepSeekMath—an open‑source large language model fine‑tuned with chain‑of‑thought instruction data—the following improvements were observed after applying GRPO:

| Benchmark | Before GRPO | After GRPO |
|-----------|-------------|------------|
| GSM8K     | **82.9 %** CoT accuracy & self-consistency | **88.2 %** |
| MATH      | **46.8 %** competition-level accuracy & self-consistency | **51.7 %** |
| CMATH     | —           | **88.8 %** |

These results meet or surpass many proprietary counterparts (e.g., Gemini Ultra, GPT‑4’s “code interpreter” variant uses tool‑based solvers only when necessary).

---

## 7. Why Group Baselines Work in Token‐Reward Tasks

The conventional justification for using an explicit value function is variance reduction—the critic’s estimate of expected future rewards smooths out noisy per-token rewards. In math reasoning tasks where:

1. The *reward* comes from a *process score* calculated only at answer completion;  
2. We have access to many competing outputs for an identical prompt;  

the group mean captures precisely the expected reward conditioned on that prompt *without needing temporal abstractions*. Since all tokens within an answer receive the same advantage $\hat A$, variance is naturally reduced by construction: any token that occurs in more successful outputs inherits higher gradient push.

Hence, dropping the critic does not harm learning stability; it simply saves resources and avoids training an additional neural module that would otherwise overfit on limited per–token data.

---

## 8. Things to Watch Out For

| Possible Pitfall | Mitigation |
|------------------|------------|
| Low group diversity → biased baseline | Keep $G$ large enough, random seed varied across batches |
| Reward model miscalibration → noisy gradients | Retrain reward model periodically with fresh pairs; apply temperature scaling |
| KL too small → policy drift into unsafe territory | Tune β or use adaptive KL smoothing |

Because GRPO relies heavily on relative rewards, it inherits any bias present in the reward model—further research into uncertainty modeling may strengthen robustness.

---

## 9. Final Takeaway

GRPO demonstrates that *a clever baseline estimator can replace an entire neural critic* without sacrificing performance on complex reasoning tasks. For practitioners who love PPO but hate its memory footprint, GRPO offers an immediate win:

```python
# pseudo-code sketch of one GRPO update step
for q in batch_questions:
    o_samples = sample_n_outputs(policy_old, q, G=64)
    r_scores   = [reward_model(q, o) for o in o_samples]
    mean_r, std_r = np.mean(r_scores), np.std(r_scores)
    advs       = [(r-mean_r)/std_r for r in r_scores]
    # attach adv to every token in each output
    # compute clipped surrogate loss as in PPO but without V_phi
```

The rest follows exactly like classical PPO—only fewer tensors and no extra backward pass on a critic network.

In short: **GRPO gives you PPO’s gains with roughly half the GPU usage and without extra ‘value’ bookkeeping**, making reinforcement learning more accessible to medium‑scale LLMs targeting mathematics and other structured reasoning tasks.

# Open‑Source Math Machines on Speed‑Dial: DeepSeekMath vs GPT‑4 & Gemini Ultra

In the last year the AI community has seen a wave of *math‑centric* language models that try to fold symbolic reasoning, algebra, and calculus into the same framework that powers ChatGPT. The most fabled of these are GPT‑4 and Gemini‑Ultra – large closed‑source beasts that deliver remarkable zero‑shot accuracy on benchmarks such as MATH and GSM8K. But a new open‑source contender, **DeepSeekMath 7B**, is closing the gap with half the number of parameters. Below we unpack the numbers, the tricks that make it possible, and a quick sanity check of how far open–source models like DeepSeekMath are from their proprietary counterparts.

---

## 1. A Quick Snapshot of the Benchmarks

| Benchmark | Modality | DeepSeekMath‑Instruct 7B (no tools) | DeepSeekMath‑RL 7B (no tools) | GPT‑4 | Gemini Ultra |
|-----------|----------|---------------------------------------|---------------------------------|--------|-------------|
| GSM8K (English) | QM | **64.2 %** | **88.2 %** | 90 %+ | 90 %+ |
| MATH (English, competition level) | QM | **50.5 %** | **51.7 %** | 55–60 % | 55–60 % |
| MGSM‑zh (Chinese) | QM | **63.3 %** | – | – | – |
| CMATH (Chinese) | QM | **84.6 %** | **88.8 %** | **~93 %** | **~93 %** |

*All percentages represent top‑answer accuracy without relying on external tools or code execution.*

Two statistics deserve extra focus:

1. **Self‑Consistency Gains**: Sampling 64 independent “tries” for a problem boosts accuracy from *DeepSeekMath‑Instruct*’s ~51 % to *DeepSeekMath‑RL*’s ~60 %. This is more than a simple statistical bump; it shows the model internally generates a richer set of coherent solutions that can be aggregated.
2. **Scale vs Quality Paradox**: A 7B‐parameter DeepSeekMath peaks near the performance of a 70B closed model such as GPT‑4 or Gemini Ultra on many tasks. That indicates that raw parameter count alone is not the sole determinant of mathematical prowess.

---

## 2. The Secret Sauce Behind the Numbers

### 2.1 A Massive, High‑Quality Math Corpus

The heart of DeepSeekMath is its **120B token `DeepSeekMath Corpus`**, harvested from Common Crawl:

- **Iterative FastText Selector**: Starts with an OpenWebMath seed, trains a fastText classifier, then discovers more math pages across Common Crawl’s trillions of URLs in successive rounds.
- **Rigorous Decontamination**: Removes any snippet that shares a 10‑gram overlap with questions from GSM8K, MATH, CMATH or AGIEval, ensuring benchmark leakage is practically zero.
- **Multilingual Breadth**: Unlike many predecessors that cherry‐pick English documents, this corpus contains chunked Chinese pages as well—about half as many tokens as English.

When pre‑trained side by side with smaller corpora (OpenWebMath @13B or MathPile @9B), five times more data yields noticeably higher test accuracy—especially in cross‑language tasks.

### 2.2 Code Training First, Then Math

An intuitive but underappreciated observation: *pre‐training on source code before math training benefits both with and without tool use*. Code style forces the model to learn step‐by‐step procedural thinking—a valuable scaffold for symbolic reasoning.

In experiments, a two‑stage pipeline:

```
400B code tokens → 150B math tokens
```

outperforms pure math pre-training alone when applied to GSM8K/MATH with Python execution. Even mixing code tokens into one stage helps maintain coding ability while still improving math without tools—a win–win for small routers.

### 2.3 Reinforcement Learning via Group Relative Policy Optimization (GRPO)

Traditional PPO requires a value network and keeps track of per‑token rewards—a costly setup for LLMs that only get a reward at the end of an answer.

GRPO sidesteps this by:

- Sampling G outputs for each question;
- Using their average reward as a *baseline*;
- Computing token advantages relative to this group average;
- Adding an explicit KL penalty against a reference model.

This reduces memory overhead tenfold compared to vanilla PPO and gives approximately +5–6 % accuracy on GSM8K and +4–5 % on MATH after just one iteration.

---

## 3. Why Open‌-Source Models Are Leaping Ahead

### 3.1 Optimized Data Selection Matters More Than Size

Take Minerva (540B) vs DeepSeekMath (7B):

- Minerva relies heavily on arXiv papers (~80 %) plus some web data.
- ArXiv content did not help math benchmarks in our tests; it even hurt certain multi-choice problems.
- DeepSeekMath’s cleaning pipeline nets high precision Web text with exact math formatting—far from noisy arXiv LaTeX clutter.

The result: *the same or better training quality produced by fewer GPUs*.

### 3.2 Module Hybridization Helps General Reasoning

During pre-training, DeepSeekMath mixed in a minority amount of non-math data (natural language + GitHub code). Surprisingly, this boosted non-math benchmarks like MMLU-STEM and BBH—trajectory confirming that rich mathematical reasoning enhances general language understanding.

### 3.3 Latency & Model Size Trade-Offs

At ~70 ms inference latency on an A100 GPU pointwise decoding time per token dropped below 0.16ms for DeepSeekMath compared to GPT‑4’s ~400ms in hosted APIs—critical for real-time tutoring or low-latency educational apps.

---

## 4. Benchmarks in Practice: Few-Shot vs Zero-Shot

| Model            | Zero-Shot Q/A Accuracy (MATH) | Few-Shot Q/A Accuracy |
|------------------|--------------------------------|------------------------|
| DeepSeekMath-Instruct   | ~50 %                         | ~50 %                 |
| GPT-4             | ~55–60 %                       | >70 %                 |
| Gemini Ultra      | ~55–60 %                       | >70 %                 |

The gap narrows quickly when you give GPT/ Gemini a few example solutions—their few-shot adaptability is still broader due to larger latent space volume—but for everyday Math tutoring where users rarely paste chain-of-thought prompts, DeepSeekMath's performance is solid even at zero-shot.

---

## 5. What’s Still Missing?

While open-source models like DeepSeekMath have caught up on *quantitative* problems:

- **Geometry & Proofs** still lag behind closed models; issues like triangle angle sums or ellipse properties tend to trip them up.
- **Higher-Level Algebraic Reasoning** beyond contest-level arithmetic sometimes produces logically sound but numerically wrong steps.
- The self-consistency approach only improves *Maj@K*, not *Pass@K*, indicating RL mainly stabilises high-quality outputs rather than improving base inference.

Future research likely will involve incorporating tree-search decoding and better process-reward signals (reward per inference step) to push those metrics up.

---

## 6. Bottom Line: Open Source Is Now Competitive

If you’re developing an educational chatbot or an assistive math tutor today:

1. Use ***DeepSeekMath-Instruct*** as your base if latency and size are critical.
2. Spin up an off-the-shelf ***GRPO-based RL*** fine-tuning if you have GPU cycles; even one iteration can deliver up to +10 percentage points on GSM8K/MATH without extra instructions or tool integration.
3. Pair it with case-specific *tool integration*, e.g., SymPy calls, when needed—for problem sizes approaching contest level handfuls of variables.

In short—to map out today's frontier:

* “Closed Like GPT‑4/Gemini” — advanced geometry + few-shot empowerment  
* “Open Source Like DeepSeekMath” — competitive quantitative reasoning + better latency + open-source freedom  

So let’s celebrate how far open-source math LLMs have come while remembering there’s still some geometry left to conquer!



# Beyond Benchmarks: Strengths & Gaps in Modern Math LLMs

## What the paper tells us

DeepSeekMath is a new 7‑billion‑parameter language model that was built on top of a code‑trained backbone, DeepSeek‑Coder‑Base‑v1.5. The authors invested **500 B tokens of training** and—most importantly—added a gigantic *math‑specific* corpus extracted from Common Crawl:
- **120 B tokens** of math‑related web pages (the DeepSeekMath corpus)
- 10 % from arXiv, 20 % from GitHub code, and the remaining 70 % from general Common Crawl in English and Chinese.

After standard instruction tuning, the authors performed reinforcement learning with *Group Relative Policy Optimization* (GRPO), which replaces the critic used in traditional PPO with a group‑based baseline. The result is a model that scores **51.7 % on the competition‑level MATH benchmark**—the best open‑source result we know of—and **80–90 % on GSM8K** using chain‑of‑thought prompting.

However, the paper also reports some honest limitations that are easy to miss when just looking at headline numbers.

## Strengths that matter

| Benchmark | Baseline (open‑source) | DeepSeekMath #7B | Gap |
|-----------|------------------------|------------------|-----|
| GSM8K (chain‑of‑thought) | 82.9 % | **88.2 %** (GRPO) | +5.3 |
| MATH (competition level) | 46.8 % | **51.7 %** (GRPO) | +4.9 |
| CMATH (Chinese) | 84.6 % | **88.8 %** (GRPO) | +4.2 |
| MiniF2F autoformalisation | modest but improved over baseline | Substantial jump |

A few takeaways:

1. **Math pre‑training matters** – The 120B-token corpus outperforms smaller, curated math corpora like OpenWebMath or MathPile almost everywhere, even with a tiny 7B model.
2. **Code training helps Math** – The backbone is a code model; experiments show that code fine‑tuning improves both tool‑integrated reasoning (Python programs) and pure reasoning.
3. **Reinforcement learning pays off** – GRPO boosts performance over instruction tuning alone without adding a costly critic network.

The big moral is that you can squeeze impressive math capability out of a 7B model if you feed it the right data and then polish it with RL.

## Gaps that are not covered by the numbers

### Geometry remains weak
The authors ran preliminary tests: *“the model cannot handle problems related to triangles and ellipses”*. Geometry is notoriously sensitive to symbolic manipulation and spatial reasoning—areas where even GPT‑4 shows streaks of weakness compared to domain‐specific theorem provers. It appears that the **math corpus, though large, underrepresents pure geometry material**, especially high‑school topics like Euclidean constructions or advanced trigonometry.

### Theorem proving is still a long way off
On the MiniF2F benchmark the model shows *“strong few-shot autoformalisation”*, but that’s an emerging area and still falls behind specialized theorem provers or larger closed‐source models like PaLM or GPT‑4 (when paired with external tools). The experimental section notes “geometry and theorem-proof are relatively weaker than closed models”.

### Few-shot performance lags
A quick pass on few-shot settings reveals no dramatic gains over zero-shot: “GPT-4 could improve its performance with few-shot inputs, while DeepSeekMath shows similar performance in zero-shot and few-shot evaluation.” This indicates that either:
- The token budget for prompting isn’t large enough for coaching.
- Or the architecture lacks robust *prompt steering* capabilities typically superior in larger models.

### Resource footprint
While GRPO removes the critic and saves memory, RL training still requires massive sampling of multiple outputs per prompt (64 in experiments). This is nontrivial for research groups without dedicated GPU clusters.

## Where to expand the corpus next

The success story of DeepSeekMath hinges on two facts: 1) high‑quality math data exist abundantly on the web; 2) picking it efficiently boosts reasoning skills dramatically.

To keep climbing past GPT-4 on competition‐level MATH or to close geometry/theorem gaps, future work should target richer content sources:

### 1️⃣ Curated geometry datasets
* Online textbooks (`geometry.com`, `mathsisfun.com`), 
* Problem sets from AoPS or Art of Problem Solving school,
* Derivative-based trigonometry notes from Khan Academy,
* Euclidean proofs from Wikipedia or dedicated geometry wikis.

Integrating these into a dedicated *Geometry Corpus* would directly address the sparsity shown in modern benchmarks.

### 2️⃣ Formal mathematical libraries as data
The paper briefly touches on arXiv but notes limited benefit when used alone. However, patches of arXiv papers that include detailed proofs or derivation steps could be harvested selectively:
- Extract sections annotated as `Proof:` or `Derivation:` using regex and NLP heuristics.
- Perform semantic cleaning to strip references/LaTeX formatting.
- Store them as additional training tokens focusing on formal reasoning patterns.

This would give the model exposure to rigorous stepwise deduction not found in ordinary web pages.

### 3️⃣ Enriched process rewards for RL
GRPO currently assigns rewards at the end or at each discussion step. A *process reward* trained on explicit intermediate correctness checks could guide fine-grained step selection:
- Collect human-annotated “good vs bad” substeps.
- Train a reward model that scores each token’s contribution to reaching an intermediate state (e.g., after applying an identity).

Fine-grained RL could help rebuild geometry capacity where many steps involve algebraic manipulations interlaced with spatial reasoning.

### 4️⃣ Multilingual expansion beyond English–Chinese
The present work includes both languages but heavy reliance on English content measured by token counts skews learning towards Western mathematicians’ notation styles. Adding non-Latin alphabets (e.g., Arabic numerals scripts, Cyrillic terms used in analytic geometry texts) will reduce language bias and improve global usability.

## Practical guidance for research groups

If you’re looking to build or extend an LLM’s math skills:

1. **Start with a large web crawl**: Use fastText or efficient boosters like BM25+semantic embeddings to collect pages tagged with math-related keywords (`integral`, `matrix`, `proof`, etc.).  
2. **Iterate your selector**: Each round add manually annotated URLs back into your seed set; train a new classifier; recall more pages—repeat until marginal gains drop below ~2%.  
3. **Keep contamination low**: Run exact n-gram matches against all benchmark texts; remove any overlap longer than 10 tokens—a standard practice in many recent papers (cf., DeepSeek approach).  
4. **Schedule RL pulse-ups**: After instruction tuning just before deploying your final checkpoint, run a single reinforcement sweep with GRPO or PPO but use *only* labeled questions you already have; this ensures policy stays stable while gaining more precise output distribution refinement.

## Takeaway

DeepSeekMath exemplifies how carefully curated math data + code-based pretraining + lightweight reinforcement learning can elevate an LLM into “borderline GPT‑4” territory on compositional numeric reasoning tasks—all within a 7B parameter budget.

Whether you’re building industry GPT interfaces or experimenting in academia, keep an eye on:
- The shape of your training corpus,
- Whether you fine-tune on code,
- How you reward complex reasoning steps during RL.

Most importantly, no matter how high your benchmark score looks, examine subdomains like geometry or theorem proving directly—you might find hidden weaknesses lurking beneath those pretty numbers. These gaps are just as critical for safe deployment as they are for academic curiosity.\n\nHappy training!
