# When LSTMs Go Big: How xLSTM Pushes the Limits of Recurrent Architecture  

## Why “just an LSTM” never sounded so good again

For almost three decades the Long‑Short‑Term Memory (LSTM) was the go‑to building block for anything that had to remember a sequence.  It kept a *cell state* \(c_t\) that could be updated additively and was protected from exploding or vanishing gradients by its three gates:

\[
c_t \;=\; f_t\,c_{t-1}\;+\;i_t\,z_t , \qquad
h_t \;=\; o_t\,\psi(c_t) .
\]

These equations were elegant, but they come with three hard limits:

| Limitation | What happens in practice |
|------------|--------------------------|
| **No revision** | Once a token is stored it can’t be overwritten when a newer, more relevant one appears (think finding the closest match in a long sequence). |
| **Tiny memory** | The cell is a single scalar.  All the information – grammar, entities, sentiment – needs to fit into that one number. |
| **Sequential only** | The hidden state propagates step‑by‑step, so processing long texts is slow and memory‑heavy. |

When Transformers arrived in 2017 they sidestepped all three issues: attention gives instant access to any past position, multi‑head self‑attention provides huge representational capacity, and the feed‑forward layers let you parallelise over the entire context.  The Transformer’s success turned many developers into “mask my recurrency.”

xLSTM shows that a *recurrent* architecture can still compete if it addresses those problems head on.

## Building blocks of xLSTM: exponential gating & matrix memory

xLSTM keeps the familiar LSTM skeleton but augments it in two decisive ways.

### 1. Exponential gating + stabilisation

Instead of squashing gate values through a sigmoid (which keeps them in \([0,1]\)), xLSTM lets both the input \(i_t\) and forget \(f_t\) grow exponentially:

\[
i_t \;=\;\exp(\tilde{i}_t), \qquad 
f_t \;=\;\sigma(\tilde{f}_t)\;\text{or}\;\exp(\tilde{f}_t).
\]

An exponential gate can become huge – risk of overflow is real – so xLSTM adds a tiny *stabiliser* \(m_t\):

\[
m_t = \max\!\bigl(\log f_t + m_{t-1},~\log i_t\bigr),
\]
followed by  
\(i'_t=\exp(\tilde{i}_t-m_t)\) and  
\(f'_t=\exp(\log f_t + m_{t-1}-m_t)\).

The net effect?  
- The gates can **quickly turn on or off** more aggressively than sigmoids, letting the cell remember new information or forget old data with great flexibility.  
- Because exponentials are *additive* under logarithms, the cell state update remains essentially the same shape as an ordinary LSTM but behaves more like a *constant error carousel* that can outperform its predecessor on tasks that require *state tracking* (e.g. parity checks or formal grammar recognition).

We call an LSTM variant that uses only this scalar analysis **sLSTM** (scalar).  sLSTM keeps memory mixing (hidden → cell interactions), which introduces sequence order but also forces sequential computations.

### 2. Matrix memory & covariance update

The second breakthrough is to replace the single scalar cell with a full \(d\times d\) matrix \(\mathbf{C}_t\).  Intuitively each element of \(\mathbf{C}\) now stores a *co‑occurrence* between key and value vectors:

- Every time step we receive a key \(\mathbf{k}_t\in\mathbb{R}^d\) and value \(\mathbf{v}_t\in\mathbb{R}^d\).
- We simply add their outer product to the matrix:

  \[
  \mathbf{C}_t = f_t\,\mathbf{C}_{t-1}\;+\; i_t\,(\mathbf{v}_t\,\mathbf{k}_t^{\!\top}) .
  \]

This rule is known as the *covariance update*, because it increments the pairwise covariance of keys and values.  It’s optimal for retrieving a stored value by multiplying with a query vector:

\[
h_t = o_t\,{\color{gray}\odot}\;
    \frac{\mathbf{C}_t\,\mathbf{q}_t}
         {\max(|\,n_t^{\!\top}\mathbf{q}_t|,\;1)} ,
    \qquad
    n_t = f_n\,n_{t-1} + i_n\,\mathbf{k}_t .
  \]

The normaliser \(n_t\) prevents numerical instability when the query aligns poorly with any key.

Because everything now lives in matrix form, there are **no hidden–hidden connections** – all updates are purely linear operations on matrices – meaning we can compute many steps *in parallel* (think FlashAttention style kernels).  We call this variant **mLSTM** (matrix).

## Two flavours of xLSTM blocks

xLSTM builds its deep networks from two types of residual blocks:

| Block type | When to use | What it does |
|------------|-------------|--------------|
| **sLSTM block** | Use when you need *state tracking*. | Keeps sequential gates and mixes memories across time steps via hidden–hidden connections (post up‑projection style). |
| **mLSTM block** | Use when you need large storage capacity and parallelism. | Uses matrix memory without mixing; uses pre up‑projection style to exploit higher dimensionality. |

A typical xLSTM architecture mixes them – for example \(xLSTM[7:1]\) means eight blocks where seven are mLSTMs and one is an sLSTM.

Because all blocks are wrapped in residual connections with pre‑LayerNorm (the same trick used in GPT‑3/LLama), training large scales is stable and comparable to modern transformers.

## How does it compare to “classic” models?

### Performance on synthetic tasks

On formal language benchmarks that require precise state tracking (parity, bracket matching), xLSTMs outperformed vanilla Transformers, State‑Space Models (SSMs), even other recurrent models like RWKV or Mamba.

On associative recall tasks – where you have to remember up to 256 key/value pairs over sequences of length ≈2000 – mLSTMs were especially strong thanks to their matrix memory. Even small‐sized models outperformed large transformers on these tests.

### Language modeling benchmark

When trained on **15 B tokens** from SlimPajama:

| Model | Params (≈ 350 M) | Validation perplexity |
|-------|------------------|------------------------|
| GPT‑3 style Transformer | 350 M | 30.4 |
| mBERT/LLama transformer | 350 M | 29.8 |
| Mamba (SSM based) | 350 M | 30.1 |
| xLSTM[7:1] (our choice) | • | **28.9** |

xLSTM not only beat all competitors at this scale but also showed a **better scaling slope**: every doubling of parameters yielded slightly larger gains than seen in transformer baselines.

On an even larger data set (**300 B tokens**) and across four model sizes (125 M–1.3 B):

- xLSTMs maintained lower perplexity across all sizes.
- For downstream benchmarks like ELUQA or OpenBookQA they ranked first or second among every model family.
- In the PALOMA benchmark spanning over five hundred domains, almost all individual datasets had lower perplexities for the best xLSTM variation.

### Inference speed & throughput

Because the memory usage per token is constant (unlike quadratic‐memory Transformers), xLSTMs scaled linearly with context length during generation—much better than LLM transformers whose runtime grows roughly quadratically when past key/value caches are not reused efficiently.

For comparable model sizes:

| Model | Generation time per token (ms/Batch=1 / Prefill=16) |
|-------|---------------------------------------------------|
| LLama (Transformer) positive cache ✓ | ~22 ms |
| Mamba (SSM)                            | ~14 ms |
| RWKV (Recurrency)                     | ~12 ms |
| **xLSTM[7:1]**                        | ~11 ms |

Across larger batch sizes, xLSTMs achieved higher decoding throughput because their constant-memory operation compresses better into GPU registers.

## What remains to learn?

xLSTMs are not perfect yet:

1. The sLSTM variant still needs sequential loops due to memory mixing—CPU‐bound kernels slow it down relative to fully parallel mLLMS.
2. Matrix updates are expensive (\(O(d^2)\)), though they’re parameter‐free and highly vectorisable.
3. Careful initialization of forget gates is critical for stability.
4. Further hyperparameter tuning could squeeze even more performance out of both variants.

Nonetheless produce results indicate this approach could bridge recurrent architectures and transformer power—especially where long-range context handling or efficient implementation on edge devices matters most.

## Takeaway

xLSTM proves that by rethinking two central ingredients—gates *and* memory shape—you can give an LSTM modern relevance again:

- Exponential gating lets it overwrite what is less relevant, thereby solving classic “state tracking” problems.
- A matrix‐based covariance memory gives it far larger storage capacity without increasing parameters.
- Residual stacking keeps training straight forward while enabling billions of parameters.

In short: **Recurrent networks can still scale recklessly well**, even rivaling Transformers at huge model sizes—and sometimes faster too!  

Feel free to check out their open source implementation at <https://github.com/NX-AI/xlstm> if you’d like to experiment with versus your own transformer architectures.



# Beyond the Memory Cell: The New Matrix Memory That Lets Models Learn Like Humans

The long‑staying memory of a neural network is usually a one‑dimensional *scalar* that tries to hold every bit of useful information.  xLSTM turns that idea on its head by replacing the single scalar with an entire *matrix*.  This change unlocks a true associative memory that behaves much closer to the way we humans remember key–value pairs (e.g. the kettle’s temperature and the time it was set).  In this post we’ll unpack how this matrix memory works, why it is a natural fit for long‑term recall tasks, and how it stacks up against the usual Transformer attention.

---

## 1. From “one number” to “full table”

### 1.1 The classic LSTM cell

A traditional LSTM cell holds a single value \(c_t \in \mathbb{R}\) that is updated at each time step:

\[
c_t = f_t\,c_{t-1} + i_t\, z_t .
\]

- **Forget gate** \(f_t\) decides how much of the past to keep.
- **Input gate** \(i_t\) decides how much new information \(z_t\) to add.

While clever gates let LSTMs survive long dependencies, packing *everything* into a one‑dimensional tube makes it very hard to remember many distinct facts simultaneously.

### 1.2 Swapping in a matrix

xLSTM replaces the scalar \(c_t\) with a square matrix \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\). Think of \(\mathbf{C}_t\) as an *association table*: each column corresponds to a key (the “thing you’re looking for”) and each row corresponds to its value (the “answer you want”). Updating this table uses a *covariance* style rule:

\[
\boxed{\mathbf{C}_t = f_t\, \mathbf{C}_{t-1} + i_t\, \mathbf{v}_t\, \mathbf{k}_t^\top}
\]

- \(f_t\) is still a decay term (think “forgetting older facts over time”).
- \(i_t\) is a learning rate (how strongly you want to store the current pair).
- \(\mathbf{k}_t \in \mathbb{R}^d\) is the **key** vector.
- \(\mathbf{v}_t \in \mathbb{R}^d\) is the **value** vector.

The outer product \(\mathbf{v}_t\,\mathbf{k}_t^\top\) writes the pair into every cell where `key` meets `value`. Imagine flipping through a notebook: when you see an entry “$k$ = spring”, you write “$v$ = 79 °C” underneath it – pushing two dots together into a grid.

---

## 2. Associative memory in action

### 2.1 Retrieval as dot product

Later on, given a **query** vector \(\mathbf{q}\), we can pull out the associated value by:

\[
\tilde{\mathbf{h}}_t = 
    \frac{\mathbf{C}_t\,\mathbf{q}_t}
         {\max(\lvert \mathbf{n}_t^\top \mathbf{q}_t\rvert ,\, 1)} ,
\]
where \(\mathbf{n}_t\) is a normalizer that keeps track of gate strengths.

In plain words:
1. Multiply each column of the matrix by what matches your query.
2. Sum across columns – this gives exactly the weighted value you are looking for.

That’s identical in spirit to textbook *Hopfield* or *vector‑symbol binding* memories used in cognitive science: key–value pairs are stored once and can be flexibly retrieved later.

### 2.2 Why this beats Transformer attention

Standard Transformer attention also stores key–value pairs through two linear layers that project hidden states into keys and values. When retrieving, it computes attention weights:

```text
score = softmax(K · Q^T / √d)
output = score · V
```

The scaling factor forces every key–value combination to be considered: typical Attention has an exponential memory in the coding dimension but still treats every item independently because of the softmax normalization.

xLSTM’s matrix memory has two advantages:

| Property | Transformer Attention | xLSTM Matrix Memory |
|----------|-----------------------|---------------------|
| **Storage** | Implicit in linear projections; needs dense parameters per token | Explicit outer‑product updates; no extra parameters |
| **Update rule** | Back‑propagated per token | Simple covariance update – can be parallelized |
| **Recall accuracy** | Soft weighting → blur between similar keys | Exact dot product → sharper bindings |
| **Scaling with sequence length** | Quadratic unless approximated | Purely linear; grows only with model size |

Experiments on *multi‑query associative recall* show xLSTM consistently beating Transformers even when Transformers use massive hidden sizes. In practice this means xLSTM can remember dozens or even hundreds of key–value pairs (think code variables, names with dates, or menu items with price tags) without erasing older facts.

---

## 3. An everyday analogy: “Finding your keys”

Imagine you always keep your house keys in the same drawer: *insert your hand into the drawer’s first slot (key)* and pull out whatever you have stored there (value). Every time you get home, put your keys back – but wrap them around another slot if you have found new ones. After years of practice your brain has built an internal map from slot numbers (keys) to objects (values). Even if you open many drawers at once, you still instantly pick out what you’re looking for because all associations are wired into that map.

In neural terms:

- The drawer slots → rows/columns of \(\mathbf{C}\).
- Inserting/updating keys → outer‑product updates.
- Pulling out an object quickly → matrix multiplication with query vector.
- Forgetting old items → multiplicative decay gate \(f_t\).

That’s exactly what xLSTM does—not with hand‑in‐drawer metaphors but with vectors and matrices that run nanoseconds inside GPUs.

---

## 4. When does the matrix win?

| Scenario | Requires |
|----------|----------|
| Long span code interpretation (e.g., tracking variable definitions across thousands of lines) | Exactly replacing older bindings with newer ones → inner‑product updates |
| Reading comprehension that relies on spotting entities over huge passages | Recalling specific facts without mixing contexts → associative recall |
| Multi‑task settings where distinct topics need separate storages | Partitioned matrices help prevent interference |

Because each update is independent of sequence length, models can train on enormous corpora while retaining high fidelity at very long contexts—critical for next‑gen language models aiming at arbitrary prompt lengths.

---

## 5. Bottom line

Replacing a single memory scalar with a full matrix gives models:

1. **True associative storage** – like if your brain had endless drawers labeled by words.
2. **Linear compute cost vs sequence length** – no quadratic blowup as seen in self‑attention.
3. **Strong performance on recall-heavy tasks** – demonstrated against large Transformers and other state‑of‑the‑art RNNs/SSMs.

The result? A family of language models—xLSTMs—that can match or surpass modern Transformers while offering simpler, more interpretable inner mechanics resembling human short‑term memory.

If you're building systems that need to keep track of many facts over long horizons or want an architecture that scales gracefully with data volume rather than context length, watching xLSTM’s matrix memory trick will be worth it—and soon may become standard practice in future language models!



# Why Exponential Gating Is the Secret Sauce Behind Fast, Accurate Language Models  

In the age of transformers, a lot of people still wonder why the humble LSTM hangs on the sidelines.  The answer isn’t that LSTMs are obsolete – it’s that they *are* powerful, but only when we give them the right tricks to work at a modern scale.  
The paper “xLSTM: Extended Long Short‑Term Memory” shows that the missing ingredient is an **exponential gate**.  Added to the classic LSTM it unlocks three hard‑wired LSTM advantages that transformers simply can’t match:

1. **On‑the‑fly revision** – we can overwrite previously stored values when a more relevant cue arrives.  
2. **True state tracking** – long–range dependencies such as counting or pattern matching are easy once gates can blow up instead of cap themselves with a sigmoid.  
3. **Parallelizable memory** – a matrix memory that is updated by a simple covariance rule lets us squeeze many key‑value pairs into a single layer without paying for extra parameters.

Below we unpack how exponential gating works, why it matters for real‑world language modeling, and how to implement it safely in TensorFlow / PyTorch.



--------------------------------------------------------------------

## 1. Gates Revisited: From Sigmoid to Exponential

|  Classic LSTM   |      xLSTM (sLSTM)      | Intuition |
|--------------|------------------------|-----------|
| `i_t = σ(⋯)`, `f_t = σ(⋯)` | `i_t = exp(⋯)`, `f_t = σ(⋯)` or `exp(⋯)` | Gates can become arbitrarily large → *carry‑over* and *overwrite* are not capped |
| `c_t = f_t c_{t-1} + i_t z_t` | same Δ but with new stabilizer | Normalizing growth with a *normalizer state* (`n_t`) keeps values bounded |

### The classic problem
With the sigmoid gate (`σ(x)=1/(1+e^{-x})`) incoming signals are always squashed between 0 and 1.  This protects gradients but also means:

- Every new input has a fixed *share* of the cell state – we can’t burst through previous memory when new evidence arrives.
- Forgetting is slow: jumping from a stored value to something newer requires many steps because we can only *scale* by at most 1 each time.

### Exponential gates fix this

Two consequences follow:

1. **Unbounded updates** – `i_t = exp(⋯)` allows a gate to grow as big as necessary to overwrite or amplify stored data.
2. **Rapid decay / rewrite** – `f_t = exp(⋯)` can quickly kill old information when new context is more relevant.

But crazy exponentials cause numeric overflow during training if left unchecked.

--------------------------------------------------------------------

## 2. Stabilizing the Exponential

The trick is to add an auxiliary **stabilizer state `m_t`**, which tracks the largest log‑gate among all past timesteps:

```
m_t   = max( log(f_t) + m_{t-1} , log(i_t) )
```

Using this we define new gates:
```python
i'_t = exp(log(i_t)   - m_t)
f'_t = exp(log(f_t)+ m_{t-1} - m_t)
```
By subtracting the maximum logrisk from every exponentiation we keep all exponentials in a finite range.  
The stabilizer itself is differentiable, so gradients flow unchanged – you get exactly the same expressive power as un‑stabilized gates but without exploding numbers.

--------------------------------------------------------------------

## 3. On‑the‑Fly Memory Revision

Consider the classic “Nearest Neighbor Search” test:  

*You have a reference vector and must scan a long sequence to find the most similar item ever seen.*  
An ordinary LSTM cannot rewrite its stored vector once it has committed to one.\  
With exponential gating the cell can *reinstate* a newer match instantly:

```
c_t = f'_t c_{t-1} + i'_t z_t
```

If a later input is closer to the reference than anything before, `i'_t` will become huge while earlier `c_{t-1}` gets decayed by `f'_t`.  The final hidden state carries only the best match.  
This property is central to tasks where you must keep track of which context lives far ahead – e.g., counting repetitions or identifying which slot in a dialogue history caused an error.

--------------------------------------------------------------------

## 4. Matrix Memory (mLSTM): Scaling Beyond Scalars

An ordinary LSTM stores its book‑keeping in a single scalar per hidden dimension; this forces every semantic feature into one number.

The **mLSTM** replaces that scalar with a *matrix*.  
At each timestep you store a key–value pair `(k_t, v_t)` via an outer product update:

```
C_t   = f'_t C_{t-1} + i'_t v_t k_t^T
n_t   = f'_t n_{t-1} + i'_t k_t          # normalizer
h_t   = o'_t ⊙ ( C_t @ q_t / max(|n_t^T q_t|, 1) )
```

Because every key influences *all* dimensions of all values, you get maximal capacity without extra parameters—just matrix multiplication time, which is highly GPU‑friendly.

--------------------------------------------------------------------

## 5. Memory Mixing & Parallelism

A vanilla LSTM mixes memory across time steps because each hidden state feeds back into every gate.  This serial dependency makes parallel processing impossible.

The xLSTM family introduces two strategies:

| Variant | Mixing? | Parallel? |
|---------|--------|-----------|
| sLSTM   | Yes (over heads & cells) | No — use fast CUDA kernels |
| mLSTM   | No (no hidden–hidden gates) | Yes — trivial parallel scan |

The combination gives you:
- **sLSTM blocks** for tasks requiring true sequential context (e.g., regular grammar verification).  
- **mLSTM blocks** for ultra fast inference and scalable memory on very large models.

In practice we stack both types in an xLSTM architecture: most layers are mLSTM for speed and capacity; occasional sLSTM layers preserve strong state‑tracking abilities.

--------------------------------------------------------------------

## 6. Real‑World Impact – Two Test Cases

### A. Long Context Handling
When training on sequences up to **2 k tokens**, xLSTMs keep perplexity low even when evaluated at **16 k tokens**—a key advantage over standard transformers whose quadratic self‑attention degrades sharply beyond their trained context length.

### B. Rare Token Prediction
On Wikitext‑103 rare tokens account for >70 % of perplexity drop in vanilla LSTMs because scalar cells saturate quickly.
With exponential gating and matrix memory, xLSTMs recover performance on those tokens by preserving richer embeddings throughout training.

--------------------------------------------------------------------

## 7. Minimal Code Example (PyTorch)

```python
import torch
import torch.nn as nn
import math

class ELIF(nn.Module):
    """Exponential activations with stabilizer."""
    def __init__(self, dim):
        super().__init__()
        self.w_i = nn.Linear(dim, dim)
        self.w_f = nn.Linear(dim, dim)
        self.m      = torch.zeros(dim).to('cuda')   # stabilizer

    def forward(self, x):
        # raw logits
        i_raw = self.w_i(x)
        f_raw = self.w_f(x)

        # first pass: compute unscaled gates
        i     = torch.exp(i_raw)
        f     = torch.sigmoid(f_raw)          # or exp(f_raw) if desired

        # store log values for stabilizer
        logf   = torch.log(f + 1e-8)
        logi   = torch.log(i + 1e-8)

        # update stabilizer
        self.m      = torch.max(logf + self.m.clone(), logi)

        # stable gates
        i_stab   = torch.exp(logi - self.m)
        f_stab   = torch.exp(logf + self.m - self.m)

        return i_stab, f_stab
```

Combine this ELIF module inside your LSTM cell definition; all other operations remain unchanged from Vanilla LSTM.

## 8. How Does It Stack Against Transformers?

If you compare validation perplexity on standard corpora (15 B train tokens):

| Model | Params | Val Perplexity |
|-------|--------|----------------|
| GPT‑3 (Transformer) | ~350M | ~38 |
| Mamba (State Space) | ~350M | ~37 |
| xLSTM[7:1] (mix of s/m) | ~350M | **33** |

xLSTMs even beat big transformers with comparable parameter budgets while being fully linear in input length and amenable to aggressive scaling laws—so larger models should yield even larger gains.

Moreover:

* **Inference speed:** Unlike quadratic attention cost in transformers, xLSTMs run linearly; e.g., at 1.3B parameters they reach roughly twice throughput compared to GPT‑4 sized LM counterparts.
* **Memory:** Constant per‑token memory makes them well-suited for edge deployment or low‑budget servers where GPU memory is limited.

--------------------------------------------------------------------

## 9. Takeaways & Future Work

* Exponential gating frees LSMTs from sigmoid bottlenecks → instant revision & robust state tracking.
* Matrix memory eliminates parameter overhead while vastly expanding capacity.
* An elegant stabilizer keeps training else inside numeric limits.
* Combining s/L towards Ultra-fast m/L gives scalable yet expressive architectures.

While current CUDA kernels for sLSTM are about twice slower than mLSTM and not yet tuned for FlashAttention speeds, bounding these gaps is straightforward once we have mature multi-GPU libraries around matrix attention tricks.

If you’re building next–generation language models, revisiting gated RNNs isn’t just nostalgia—it’s an aggressively competitive alternative brought alive by exponential gating.
