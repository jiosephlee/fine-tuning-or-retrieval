\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### "Scales beyond 33B/65B"—what practical barriers remain for QLoRA at >100B parameters?
Question:
"QLoRA enables full fine‑tuning on single GPUs for up to 65B", but still leaves open questions about higher scales: memory needed for storing/checkpointing activations; impact of larger block sizes; potential degradation of double quantization accuracy. What specific GPU memory limits or compute bottlenecks might arise if we tried QLoRA on a hypothetical 200B frozen base model?
Answer:
**The central point of QLoRA is that quantizing a frozen base model to 4 bits and training only a tiny Low‑Rank Adapter set removes most of the memory that mattered for full‑precision finetuning.  In practice the 48 GB GPU barrier that limits ordinary 16‑bit finetuning of 65 B‑parameter models is broken into a handful of manageable pieces:**

| What is limiting a *real* 200 B‑parameter QLoRA run | Why it arises in the paper | Practical mitigation |
|---|---|---|
| **Storage of the frozen weights** | The base model itself occupies *≈ 1 GB per 10B parameters* at 4‑bit NF4 (cf. §3.2). For 200 B this is ≈200 GB, far beyond a single GPU, but the weights are never loaded in full on the device – they live in (or are streamed to) CPU or NVMe storage and only the current block is dequantized on‑the‑fly into BF16 before use. | Use NVMe‑backed paging or host memory with coherent access; rely on the same *paged optimizers* strategy that keeps optimizer states resident in GPU RAM while deques of weight blocks flow from disk. |
| **Activation store** | When back‑propagating through the frozen forward pass you need a copy of all intermediate activations (attention scores, layernorms, etc.). In a full‑precision run these can consume several hundred GB for a 65 B model even with checkpointing. QLoRA reduces them by: <br> • **Checkpointing** – gradients only the adapter parameters (typically < 1 % of total params) need full activation buffers; <br> • **Paged optimizers** – optimizer state spikes due to long sequences are evicted to CPU. | The paper shows that a 48 GB GPU is enough for 65 B because activations + optimizer spill is < 25 GB at any moment. For ≥200 B you would need roughly four times as much GPU memory if you kept the same blocksize because activation size scales linearly with parameter count and hidden dimension. A realistic approach is either (i) increase batch size / sequence length while using *gradient checkpointing + float‑16 adapter grads* to keep per‑batch activations ≈ 25–30 GB, or (ii) slice each Transformer block into *smaller blocks* (e.g., blocksize 32 instead of 64) so each FMU retrieves fewer parameters at once, trading off extra kernel launches for reduced in‑flight activation volume. |
| **Quantization constants** | The first quantization step for each weight block stores an FP32 scale `c₂`. With a blocksize of 64 this costs an extra 0.5 bits/param; DQ reduces it to ~0.127 bits/param by compressing these scales again to FP8 over larger blocks (256). For a model twice as big you double that overhead, but it is still modest relative to raw weights (~3–4 GB extra). | Keep the same double‑quantization scheme; if you further reduce blocksize for activations you might increase `c₂` overhead slightly but still stay well below the budget. |
| **Adapter size & rank** | QLoRA relies on *all* linear layers being adorned with LoRA adapters so that no gradient flows through any original weight matrix – only the tiny `L₁·L₂` matrices are trained. The paper argues that ~0.2 % of parameters suffices for full performance when adapters are placed everywhere; going larger always decreases memory little compared with full‑weight updates but increases parametrization linearly with rank `r`. For >200 B we’d still want `r≈8–16` to keep adapter trainable memory under ~5–10 GB even on a single GPU. | If you plan higher ranks or more adapters per layer, compute adapter storage as `(#layers × hidden × r)` and confirm it stays within your residual budget; otherwise reduce `r` or drop adapters from some auxiliary layers (e.g., feed‐forward reductions). |
| **Compute – GEMM cost and kernel launch overhead** | Quantized forward passes require two dequantizations per multiplication: dequantizing weights from NF4 → BF16 and then computing BF16×BF16 GEMM. For larger models this multiplies compute cycles linearly with parameter count; however, since all workloads are low‐bit there’s no extra precision penalty once data is lifted to BF16 in registers. The paper demonstrates that latency stays comparable to full‑precision runtimes up to 65 B when batched appropriately and fused kernels used (< 20 % slow‐down). | For >200 B you will likely hit PCIe / NVLink bandwidth limits when streaming large numbers of small weight blocks concurrently; solution: increase blocksize to reduce number of kernel launches (trade off activation memory), or fuse multiple small `c₂` constants into one larger buffer so each dispatch transfers fewer pages. |

---

### Bottom‑line practical constraints

1. **GPU RAM (~48–80 GB)**  
   - Needed to hold one entire transformer block’s *activations + adapter grads (+optimizer spikes)* simultaneously.
   - If you keep blocksize large (64) and sequence length moderate (< 512), a single modern RTX 3090 can handle a ≈150–200 B model by streaming weight blocks from NVMe.

2. **CPU / NVMe bandwidth**  
   - Each forward pass loads ≤80 MB (for one attention head across all layers) per token stream; when batching many tokens this becomes a major latency bottleneck.
   - Use NVMe direct DMA + incremental streaming built into bitsandbytes/µDKC kernels; otherwise expect walltime penalties > 50%.

3. **Block size selection**  
   - Smaller blocks → finer quantization precision but higher overhead in weight fetches → more kernel launches → higher latency.
   - Larger blocks → coarser bin distribution → slightly higher quantization error—yet the paper shows DQ mitigates this well up to 65 B.
   - For >200 B we recommend experimenting with *blocksize = 256* for weights and *blocksize = 512* for constants—for first stage tuning then gradually reducing if precision drops.

4. **Double Quantization limits**  
   - The paper empirically reports no loss through DQ up to NF4 at 65 B.
   - At ≥200 B there may be an increased variance in phrased loss because some blocks contain many outliers—use *blockwise kurtosis monitoring* to detect whether re‑quantizing `c₂` at FP8 remains safe.

5. **Adapter rank & learning rates**  
   - With larger models scaling logarithmically improves generalisation—however memory grows linearly in rank.
   - The authors suggest halving learning rate and doubling batch size when going from 33 B -> 65 B; analogous scaling would be necessary beyond that—e.g., lr=1e-6, batch=32 sorts-of working up to ~200 B.

### Putting all together

A workable recipe for a ≈200 B QLoRA run on an RTX 3090:

1. **Weight storage** – Store all NF4 weights on NVMe using bitsandbytes direct mapping.
2. **Per-layer blocksize** – Use size 256 for weight chunks, size 512 for first-level scale constants.
3. **Activation checkpointing** – Enable gradient checkpointing with stage “full” so that only Lora grads sit on GPU RAM.
4. **Paged optimizers & fused kernels** – Activate paged optimizers and compile fused WMMA kernels that handle simultaneous dequant+MATMUL+adapter update.
5. **Batch sizing** – Start with batch = 8, seq len = 512 tokens; monitor peak RAM (~20–25 GB); if still under budget increase batch or seq length gradually.

The expected peak GPUMem ≈25 –30 GB plus ~5–7 GB adapter params → comfortably within one card even after accounting for constant overheads.

### Summary

QLoRA’s ability to finite‑tune up to ~65 B on a single high‑end GPU hinges on three pillars: freezing all base weights at NF4, storing them sparsely on disk, and pushing only tiny LoRA updates through a backward pass while keeping activations checkpointed and optimizers paged out when necessary.

Scaling past that to ~200 B is conceptually straightforward but comes down to three concrete engineering knobs:

- **GPU RAM budget** – The logic scales linearly; you’ll need roughly double the volatile heap unless you partition hidden states more aggressively.
- **Block size & fetch strategy** – Larger blocks help keep GPU idle time low but may introduce minor quantization noise; DQ continues to work but monitor outlier statistics.
- **Bandwidth management** – Weight streaming becomes the bottleneck more quickly; either use faster NVMe SSDs or accelerate by allocating multiple GPUs in EV-Link mode so each loads distinct subsets of weight blocks.

Because QLoRA’s core ideas do not alter during scaling, once those knobs are set correctly you should observe no degradation in fine‑tuning quality—even at >100 B parameters—provided you stay mindful of those practical infra limits.*
