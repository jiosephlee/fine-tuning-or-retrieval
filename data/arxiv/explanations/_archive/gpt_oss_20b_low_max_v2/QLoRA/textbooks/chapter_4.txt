\title{A Textbook about the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

Chapter 4: # 4. QLoRA Overview and Design Goals

In this chapter we lay out the foundation of **QLoRA** (Quantized Low‑Rank Adapters).  QLoRA is a training recipe that marries two ideas that have independently proved effective in the literature: *block‑wise low‑bit quantization* of a pretrained language model, and *parameter‑efficient fine‑tuning* with Low‑Rank Adapters (LoRA).  The combination delivers **dramatic memory savings while preserving full 16‑bit training performance**.  We proceed by dissecting the logical flow of a QLoRA training step, clarifying the data types used for storage versus computation, and showing how gradients are routed only to the adapter parameters.

> **Why QLoRA matters**  
> Regular 16‑bit fine‑tuning of a 65B parameter model needs well over 700 GB of GPU memory—far beyond what is available on commodity hardware.  By freezing the base model’s weights, quantizing them to a highly efficient 4‑bit representation, and iteratively training only a tiny set of adapter weights, QLoRA reduces this requirement to under 48 GB on a single large GPU, while still matching or exceeding the performance obtained by full fine‑tuning.

---

## QLoRA Pipeline Architecture

At its core, QLoRA follows **the same high‑level forward/backward loop** as conventional neural network training, except that two distinct transformations act on the base weights:

1. **Storage‑to‑Compute conversion** – we store each weight matrix in a compact 4‑bit format (the “NormalFloat” data type), but every forward or backward operation requires first converting that compact representation back into a higher‐precision form suitable for linear algebra.

2. **Adapter insertion** – we augment every linear projection in the transformer block with an additional low‑rank term.  This term is trainable; all other parameters remain frozen.

The architectural diagram would look like:

```
Input Token Embeddings          ─────►
                                      │
                                   LayerNorm
                                      │
                                 ┌────▼─────────┐
                                 │ Pretrained   │
                                 │ (quantized)  │
                                 │  Matrix W_Q4 │
                                 └────▲───────▲─┘
                                      │       │
                +----------------——–+dx−−+   │ dequantization
                |                                ▼ 
              LoRA                           Linear Projection
              (trainable)                    (h × h) weight matrix
                                 ┌────►   ▲    ▲
                                 |       |    |
                                 ▼       |    |
                               Residual                  ───►
```

In words: the original transformer projection \( \mathbf{X}\mathbf{W} \) is still applied at every layer, but the effective weight matrix is now 

\[
\mathbf{W}_{\text{eff}}=\underbrace{\text{dequant}\bigl(C_1,C_2,\mathbf{W}^{\text{NF4}}\bigr)}_{\text{frozen base}}
     \;+\;
s\,\underbrace{\mathbf{L}_1\mathbf{L}_2}_{\text{adapter}},
\]

where \(C_1,\ C_2\) are the two levels of quantization constants introduced later.

---

## Storage Data Type versus Computation Data Type

*Storage data type* refers to how an individual tensor is serialized into GPU memory; *computation data type* denotes what precision is used during matrix multiplications.

- **Storage:**  
  The base model’s weight tensors are stored in **4‑bit NormalFloat (NF4)** format.  
  NF4 packs each component into a nibble; the bits encode an equal‑frequency mapping onto values derived from the standard normal distribution.  
  This choice gives optimal “information theoretic precision” for typical pretrained weight statistics (zero‑mean Gaussian with moderate variance), yielding better empirical behaviour than plain int4 or float4.

- **Computation:**  
  All arithmetic involving these tensors uses **BFloat16 (BF16)** precision.  
  BF16 offers lower memory usage than FP32 while providing almost identical dynamic range and enough headroom for gradients and activations that can become large during backpropagation.

Because BF16 only fits twice as many bits per element as NF4, swapping between storage and compute incurs minimal overhead: each forward call invokes a *double dequantization* routine that reconstructs \(\mathbf{W}\) from its compressed representation into BF16 buffer on‑the‑fly.

---

## Forward Pass with Double Dequantization

The double dequantization routine performs two consecutive “dequant” operations:

1. **Dequantize first‐level constants:** The first quantization step scaled each block of \(\mathbf{W}\) by a constant \(c_1^{\text{FP32}}\).  
   Since these constants themselves occupy space, they are later re‐quantized itself into an **FP8** format (`c2`), allowing reuse of their own scaling.

2. **Dequantize NF4 weights:** Each block of NF4 weights \(\mathbf{W}^{\text{NF4}}\) was stored with respect to its second constant \(c_2^{\text{k-bit}}\).  

Mathematically:

\[
\begin{aligned}
Z &= \text{dequant}(c_2^{\text{k-bit}},\, \mathbf{W}^{\text{k-bit}}),\\
\mathbf{\hat W} &= \text{dequant}(c_1^{\text{FP32}},\, Z).
\end{aligned}
\]

The routine `doubleDequant(c1,c2,W)` exactly implements this sequence:

```python
def doubleDequant(c1_fp32, c2_kbit, W_nf4):
    # First level: dequant from FP8 constants to real numbers
    Z = dequant(c2_kbit_scaled, W_nf4)          # -> BF16
    # Second level: dequant from FP32 constant to final BF16 weight tensor
    return dequant(c1_fp32, Z)                 # -> BF16
```

With `c2_kbit_scaled` already centered around zero via mean subtraction (since all \(c_2>0\)), `dequant` applies an affine transformation that maps integer codes to floating values belonging to `[-1,+1]`, then rescales them by the remaining constant `c1`.

During evaluation or inference only one dequantization step is needed because gradients are absent; however during training both steps must be executed for every mini‑batch.

---

## Adapter Forward in BF16 Precision

Once the base projection has been computed from its compressed representation:

\[
\mathbf{y}_{Q} = \mathbf{x}\,\rm K\,,
\quad K=\texttt{doubleDequant}(c_1,c_2,\mathbf{W}^{NF4}), 
\]

we add the LoRA term:

\[
\mathbf{y}_{LF} = s\, \bigl( \mathbf{x}\,\mathbf L_1\bigr)\,\mathbf L_2,
\quad s>0.
\]

All three tensors involved—input \(\mathbf{x}\), low-rank factors \(\mathbf L_1,\mathbf L_2\)—are stored and processed in BF16 because their sizes are modest (~\(r\times h + r\times o)\); storing them in lower precision would degrade adapter expressiveness more noticeably than storing them in higher precision.

The *full* effective output is then

\[
Y = \underbrace{\mathbf{x}K}_{Q} + 
    \underbrace{s\,(\mathbf xL_1)L_2}_{LF},
    \quad Y\,:\,\mathbb R^{b\times o}.
\]

No higher precision than BF16 is required for any part of this computation because even the final output will subsequently be used only by other modules which themselves work in BF16/FP32 internally.

---

## Backward Pass Details (Gradients Only for Adapters)

The key memory saving mechanism lies in whom we update during backpropagation:

- The frozen base weights \(K = C^{-1}_1C^{-1}_2\,W^{NF4}\) are never modified; therefore their gradients are always zero.
- The only learnable parameters are the LoRA factors \(L_1,L_{addr}>0}\).

During backpropagation we still need derivatives with respect to *all given inputs*, including \(K^T*\epsilon_x$, where \(\epsilon_x=\partial E/\partial Y$ is the gradient from downstream layers*. However we do **not** store or propagate gradients for \(K$ itself; these derivatives simply pass through when computing gradients w.r.t. input $\mathbf x$ but they never touch $K$’s parameters. 

Formally one can write for any batch:

```python
# Forward:
y_q   = x @ K            # computed using doubleDequant(K)
y_lag = s * ((x @ L1) @ L2)
y     = y_q + y_lag

# Backward:
eps_y     = grad(loss_out)

eps_x_q   = eps_y @ K.T                # derivative wrt input through frozen path
eps_La = ... compute via chain rule using eps_y and current states

update(L1,L2)          # apply optimiser based on eps_La only
```

Because the `eps_La` term does not involve computing gradients through `K`, we avoid both storage of intermediate gradient tensors for `K` and any extra computation outside adapter matrices. Moreover, due to *gradient checkpointing* employed on activation memories within transformer layers, only backpropagated activations through these short paths need to be kept alive until the adapter update step finishes; thus overall memory cost stays bounded at roughly that of executing a regular BF16 forward pass plus a handful of additional parameter updates.

In practice this results in:

- Adapter input gradients averaging ~18 MB per sequence after checkpointing (when mixed with batch size).
- Total LoRA parameters ≪ 100 MB even at 65B scale.
- Base model running as normal but in compressed memory (~5 GB for an uncompressed 65B model vs < 48 GB net).

These figures match those reported in Section 3 of the paper: changing encoder/decoder choice or defaults may slightly alter exact numbers but never upends fundamental principles outlined here.

## Recap of Key Design Choices

| Component | Rationale | Practical Impact |
|-----------|-----------|------------------|
| 4-bit NF4 | Optimised for Gaussian distribution; equal–frequency bins | Higher accuracy than plain int/float quants |
| Two–level constants | Reduce memory spent on per–block scaling | ≈ 0.37 bits/param saving |
| Double dequantisation | Guarantees correct mapping from storage → compute | No performance loss despite compression |
| LoRA adapters everywhere | Keeps encoder/decoder geometry unchanged | Enables full accuracy recovery |
| BFloat16 computation | Sufficient dynamic range + less float-overhead vs FP32 | Minor runtime penalty |
| Optimiser Paged Memory | Evicts spike buffers automatically | Avoids OOM without manual tuning |

Together they yield a tight trade: raw parameters live compressed yet remain fully usable during gradient flow thanks to carefully designed dequant layers; local adapters capture fine–grained learning capacity efficiently.

In summary, QLoRA’s core innovation lies not just in compressing weights but coupling that compression with an adaptable low–rank bridge that restores expressive power during training while keeping GPU footprint minimal—exactly what read it needs over next chapters: how we see these design choices playing out across real models and tasks before handing them down to large language model practitioners who hope to run sizable systems on modest hardware.
