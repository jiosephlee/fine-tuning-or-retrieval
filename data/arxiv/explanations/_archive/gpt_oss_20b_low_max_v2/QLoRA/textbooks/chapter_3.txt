\title{A Textbook about the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

Chapter 3: # 3. Low‑Rank Adapter (LoRA) Finetuning Theory

Large language models (LLMs) routinely contain billions of parameters, yet only a tiny fraction of them need to be altered in order to adapt a model to a new task or domain.  Parameter‑Efficient Finetuning (PEFT) methods such as Low‑Rank Adapters (LoRA) exploit this observation by leaving the pre‑trained weights untouched while inserting a small set of trainable parameters into the network.  This chapter dissects LoRA from first principles, explains its mathematical formulation, contexts in which it is applied, and its memory footprint relative to conventional finetuning.  The discussion is built entirely on the concepts presented in the *QLoRA* paper, without recourse to external sources.

---

## 3.1 LoRA Linear Projection Augmentation

In a transformer layer several linear transformations are performed: attention‐query/key/value projections, and the two matrices in the feed‑forward block.  Each of these operations has the form

\[
\mathbf{Y} \;=\;\mathbf{X}\mathbf{W},
\]

where \(\mathbf{X}\in \mathbb{R}^{b\times h}\) is the input tensor (batch size \(b\), hidden dimension \(h\)) and \(\mathbf{W}\in \mathbb{R}^{h\times o}\) is a weight matrix whose columns encode output features of dimension \(o\).

LoRA augments this projection by inserting an additional *low‑rank* term inside the forward pass:

\[
\boxed{\;\mathbf{Y}\;=\;\mathbf{X}\mathbf{W}
      +s\,\mathbf{X}\mathbf{L}_1\,\mathbf{L}_2\;}
      \qquad(\text{Equation }1)
\]

- \(\mathbf{L}_1\in \mathbb{R}^{h\times r}\) is the first factor matrix.
- \(\mathbf{L}_2\in \mathbb{R}^{r\times o}\) is the second factor matrix.
- \(r\ll h,o\) is called the *rank*.
- \(s>0\) is a scalar that rescales the added term so that its magnitude is commensurate with that of the original projection.

The idea is straightforward: we keep all pre‑trained weights frozen (\(\mathbf{W}\)) and learn only two small matrices \(\mathbf{L}_1,\mathbf{L}_2\).  Because we odd‐out all weight “updates” into a low‑rank contribution, we drastically reduce the number of trainable parameters while preserving most of the expressive power necessary for downstream tasks.

---

## 3.2 Rank‑r Matrix Factorization and Scaling Factor \(s\)

The second term in Equation 1 can be viewed as a rank‑\(r\) approximation of an arbitrary correction matrix \(\Delta \in \mathbb{R}^{h\times o}\):

\[
s\,\mathbf{L}_1\,\mathbf{L}_2 \;\approx\; \Delta.
\]

By constructing \(\Delta\) as a product of two skinny matrices, we enforce that any adjustment carried out by LoRA lies within an \(r\)-dimensional subspace.  The parameter count for this subspace equals

\[
n_{\text{LoRA}} = r(h+o),
\]

which can be orders of magnitude smaller than \(ho = n_{\text{full}}\), the number of entries in a conventional weight matrix.

The scalar \(s\) plays an essential calibrating role.  In practice, randomly initialised LoRA factors might have magnitudes significantly larger or smaller than those of \(\mathbf{W}\).  An empirically chosen \(s=0.01$–$0.05$ brings the LoRA term to a comparable scale, ensuring that it starts as a subtle perturbation during training and grows only when beneficial.

---

## 3.3 Backpropagation Through Frozen Weights to Adapters

Because all original weights are frozen, gradients never flow into them during training.  Instead, gradients with respect to each parameter are accumulated only for the LoRA factors:

1. **Forward pass**  
   Compute
   \[
   \tilde{\mathbf{Y}}=\underbrace{\mathbf{X}\,\hat{\mathbf{W}}}_{=\hat{\!D}}\;+\;
   s\,(\underbrace{\mathbf X\,{\bf L}_1}_{A})\,{\bf L}_2,
   \]
   where we denote by \(\hat{\!D}=\mathbf X\,{\bf W}\) the contribution from frozen weights.

2. **Loss computation**  
   Evaluate a loss function \(E(\tilde{\bf Y})\), e.g., cross-entropy on language modeling or instruction following.

3. **Backward pass**  
   Compute gradients w.r.t.\ LoRA factors using standard chain rule:
   - For \({{\bf L}_2}\):
     \[
     \frac{\partial E}{\partial {\bf L}_{2}}
       = s\,{\bf L}_{1}^\top\,({A}^\top\,g),
     \]
     where \(g=\partial E/\partial {\tilde{\bf Y}}\).
   - For `{{bf L}_1}`:
     \[
     \frac{\partial E}{\partial {\bf L}_{1}}
       = s\,({A}^\top g)\, {\bf L}_{2}^\top .
     \]
   The gradients for $\hat W$ do **not** exist because $\hat W$ is frozen; any backpropagation through $\hat D$ stops at $\hat W$.

4. **Optimization update**  
   Apply an optimizer (Adam, SGD, …) only to $\{{\bf L}_1,{ {\bf L }_2},{s}\}$.  Since these tensors are very small compared with $W$, back‑propagating through them incurs far less memory consumption than updating every entry of $W$.

### Splitting Gradients Across Layers

In practice LoRA adapters are inserted in every linear block of each transformer layer:
- Query projection
- Key projection
- Value projection
- Value-to-next-layer feed-forward head
- Feed-forward intermediate layer

For each block we instantiate its own $(r,h,o)$ pair and possibly its own scalar $s$.  The total number of adapters roughly equals twice the number of layers (two per attention head block).  Because each adapter still contains only $O(r(h+o))$ parameters, even on a gigantic model such as LLaMA 65B this overhead remains moderate (typically ~0.1 %–0.5 % of all model parameters).

## 3.4 Memory Footprint Analysis: LoRA vs Full Finetuning

Memory consumption during training stems from three sources:

| Source | Full finetuning | LoRA finetuning |
|--------|-----------------|------------------|
| Model weights | Stored once + gradient copies (fp16/float32) | Frozen weights stored once (fp16/float32); adapters stored fp16 |
| Activations | Required for all forward paths | Same amount as full training (save checkpointing effects) |
| Optimizer states | Need per-weight state (moments, etc.) | Need per-adapter state |

Because adaptor tensors are tiny compared with full-weight matrices, their optimizer states occupy negligible space (< 30 MB for a typical 7B model).  

To quantify this effect we can use typical numbers reported in *QLoRA*’s memory analysis:

| Model Size | Full FP16 fine‐tune requirement | LoRA FP16 fine‐tune requirement |
|------------|---------------------------------|-----------------------------------|
| 7 B       | ~32 GB                          | ~12 GB                            |
| 33 B      | ~760 GB                         | ~48 GB                            |
| 65 B      | >780 GB                         | <48 GB                            |

Notice how **LoRA reduces estimated GPU memory by an order of magnitude** even when all weights are kept unfrozen but serviced at lower precision inside QLoRA’s quantized base model.

The critical point is that **the majority of the memory consuming component remains activations**—training from scratch or finetuning does not reduce their footprint dramatically unless one uses techniques such as activation checkpointing or reduced precision activations.  However, enabling backpropagation through quantized base weights eliminates large gradient footprints associated with full‐size weight tensors and thus allows training on single GPUs even for huge models.

## 3.5 Hyperparameter Choices

### Rank \(r\)

- A too small rank may underfit: the low-rank subspace cannot capture complex task-specific corrections.
- A too large rank increases memory consumption before it becomes wasteful.
- Empirical guidance in *QLoRA* suggests setting \(r=8~10~16~32~64~128~256~,~512,\dotsc.\), with diminishing returns beyond \(r=64.\)

### Adapter Placement

- **All Transformer Blocks:** Empirical studies show that inserting adapters *everywhere* maximises performance equivalence with full fine-tuning; limited placement (e.g., only query/key/value projections or only feed-forward layers) yields noticeable drops at larger scales.
- **Prompt Tuning vs LoRA:** Prompt tuning adds trainable embeddings at input—effective at small scale but often inferior for large models where richer parameterization via adapters becomes necessary.

### Scalar Scaling \(s$

- Typical values: \(s=0.01,\;0.05,\;0.\)
- If too large → unstable training; if too small → slow convergence.
- Some implementations let models learn an adaptive $s$ or set it per-layer based on maximum norm estimation.

### Batch Size & Sequence Length

The tradeoff between batch size and sequence length governs both GPU occupancy and PEFT benefits:
- Larger batch → more parallelism but higher activation memory.
- Longer sequences increase gradient checkpointing spikes – mitigated by *paged optimizers* introduced in *QLoRA*, which spill optimizer states to CPU when GPU runs low on RAM.

By carefully coordinating these hyperparameters one can achieve **full fidelity finetuning performance**—matching standard 16-bit full finetuning—while staying within limited GPU budgets (8–48 GB).

## Section Summary

Low-Rank Adapter finetuning reconstitutes what would otherwise be costly full-scale weight updates into inexpensive updates over tiny low-rank matrices and scalars. Its key technical ingredients—the linear augmentation scheme, rank-based factorization, careful scaling, selective backpropagation through frozen weights, and judicious hyperparameter selection—allow researchers to adapt colossal transformer models without overwhelming computational resources. In subsequent sections we explore how these ideas operate when paired with aggressive quantization in QLoRA: revealing that quantized bases plus LoRA adapters can jointly recover full-fidelity performance while preserving extreme memory efficiency across megabyte-to-terabyte model sizes.
