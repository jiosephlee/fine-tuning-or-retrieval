\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### How does 4‑bit NormalFloat (NF4) preserve accuracy compared to standard 4‑bit integer quantization?
Question:
The paper claims that NF4 is an information‑theoretically optimal quantization for normally distributed weights and that it empirically outperforms 4‑bit integers and floats. I understand the derivation of the NF4 bins, but I’m not clear on why this leads to better performance in practice. What specific properties of NF4 (e.g., symmetric binning, zero‑point handling) help mitigate quantization error for large neural‑network weight tensors?
Answer:
**Why NF4 beats naïve 4‑bit integers or floats**

A quantized weight tensor is a two‑step process:  
1. **Normalize** the weights to a given dynamic range.  
2. **Discretize** the normalized values into a small number of bins.

When weights are drawn from the same distribution (approximately zero‑centered Gaussian) we can choose the bin boundaries *once* and reuse them for every weight block. NF4 takes full advantage of this fact in three concrete ways that relate directly to the “large model weight tensors” problem.

| Property | How it works | Why it reduces quantization error |
|---|---|---|
| **Symmetric, information‑theoretic binning** | NF4 first computes $2^4 = 16$ equally‐probable quantiles of a standard normal distribution, then rescales those centroids to $[-1,1]$. | Because each bin contains the same probability mass, no bin is sparsely filled. For a normally distributed tensor, almost every weight lands in one of the 15 non‑zero bins with nearly equal likelihood. With symmetric bins, bias is minimized and outlier weights are still represented by the *nearest* high‑resolution bin rather than being forced into an extreme value as in simple min–max scaling. |
| **Explicit zero‑point** | The construction uses an asymmetric mapping that guarantees one encoded bit pattern represents exactly zero (the median of the distribution). This is done by allocating $2^{k-1}$ levels to negative values, $2^{k-1}$ to non‑negative values, then merging the duplicate zero. | A dedicated zero code eliminates rounding error for all padding or “dead” weights that are actually meant to be zero. In blockwise quantization this means that any value that should stay exactly zero does not accidentally drift toward a noisy non‑zero decoder. |
| **Global standard deviation scaling** | After computing the blockwise std $\sigma_b$ we rescale the entire block by $\max(\sigma_b,\tau)$ (τ is a small floor). The cleaned weights are then clipped to $[-1,1]$. | This aligns *every* block to have exactly the same statistical shape before quantization; hence the derived NF4 centroids are perfectly suitable for each block without needing expensive per‑block quantile estimation. Outliers affect only the block's scale factor but not its bin boundaries, so they are handled gracefully through clipping and then rescaled during dequantization. |
| **No costly per‑block quantile lookup** | Because all blocks share the same precomputed NF4 bins, each block’s “lookup table” is merely an 8–bit offset index that needs no dynamic computation or look‑ups beyond addition/subtraction. | The overhead of computing accurate quantiles per block (as required by pure quantile‑quantization) is removed, enabling the very tight memory layout (4 bits per weight + a small block‑scale fp32 value) that QLoRA relies on. |

---

### How these points translate into empirical gains

1. **Balanced error distribution** – When a tensor’s values are spread evenly across all decodable bins, rounds to nearest give an average distortion that is far lower than when many bins remain unused. Experiments in Section 5.2 of QLoRA show NF4 giving up to *3 pp* higher perplexity reduction than FP4 or INT4 on LLaMA/OPT/BLOOM when the base model is fixed.

2. **Robustness to outliers** – For language‐model weight tensors a few large magnitude entries can dominate a naive min–max scaling and collapse all other entries into a tiny subset of bins ("outlier roll‑over"). NF4’s clipping at ±$3\sigma$ protects most of the data while preserving genuine large values through blockwise scaling.

3. **Zero-error for padding and sparse masks** – LoRA trains adapters on top of frozen base weights; most matrix rows contain many zeros (especially after sparsity patterns introduced during training or instruction finetuning). Having an exact zero encoding ensures those rows do not accumulate systematic bias across gradient steps, which would otherwise be amplified when many adapters share sub‑matrices.

4. **Exact reconstruction after dequantization** – When computing gradients w.r.t adapters we back‑propagate through `doubleDequant` in BFloat16 precision. Because NF4 stores weights at 4 bits but allows perfect reconstruction of each original floating‑point value within its bin *after* dequantization, successive forward/backward passes experience very little drift compared with systems that accumulate rounding error locally (e.g., naïve FP4 constantly rediffers weights).

---

### In short

*NF4’s “information‑theoretically optimal” claim means that for any Gaussian weight tensor you cannot choose another 4–bit codebook whose mean squared error (MSE) between real and reconstructed values is lower.*  
This theoretical optimality shows up practically because

*   All blocks share an identical well‑chosen bucket set;  
*   A dedicated zero code removes bias on pad positions;  
*   The global std scaling normalizes each block into $[-1,1]$ so that outliers do not wreck bin usage; and  
*   The tiny computational footprint lets QLoRA keep memory at 4 bits while still carving enough space for high‑precision adapter gradients.

Consequently, when QLoRA finetunes a frozen 65 B model on a single GPU it preserves full 16‑bit finetuning performance—something naïve 4‑bit integers or floats cannot achieve because they suffer from skewed bin occupancy, excessive outlier distortion, and cumulative rounding error during backpropagation over massive weight tensors.

### What is the role of Double Quantization in reducing memory overhead?
Question:
Double Quantization (DQ) is introduced as a way to quantize the quantization constants themselves. Could you walk through the math of how a block size of 64 for 	extbf{W} and a block size of 256 for the first‑level constants reduce the average memory per parameter from 0.5 bits to about 0.127 bits? Additionally, why is an 8‑bit float chosen for the second‑level constant quantization?
Answer:
**Double Quantization in QLoRA: a compact derivation**

In QLoRA the weight matrix \( \mathbf W \) of a linear layer is stored in a block‑wise \(k\)-bit data type (NF4).  
For every block of size \(B_W\) (here \(64\)) there is one *first‑level* quantization constant
\(c_2^{\text{FP32}}\) that rescales the values from the block’s range to the \([-1,1]\) interval that NF4 uses.  
If we kept these constants as 32‑bit floating‑point numbers, the overhead would be

\[
\frac{\text{\#bits per constant}}{\text{number of parameters per constant}}
 = \frac{32}{B_W}=0.5 \;\text{bits per parameter}
\]

because each constant serves all \(B_W\) parameters of its block.

**How DQ lowers this cost**

Doubly‑quantized (DQ) weights treat each \(c_2^{\text{FP32}}\) as data that can themselves be quantized.
The idea is to first centre the constants (subtract their mean so they are symmetric around zero)
and then quantize them to 8‑bit *normal floating point* (FP8).  
Let

* \(B_{c}\) be the block size for these second‑level constants – we choose \(B_{c}=256\).
* Each FP8 constant now occupies 8 bits.

The mapping is:

1. **Second‑level decomposition**  
   \[
   c_2^{\text{FP32}} = \underbrace{c_{\text{mean}}^{\text{FP32}}}_{c_1} 
                      + \underbrace{\Delta}^{c_{\!2}^{\text{FP8}}}
   \]
   where \(c_{\!2}^{\text{FP8}}\) is an 8‑bit value that represents the deviation from the mean.

2. **Storage cost**  
   * The mean \(c_1^{\text{FP32}}\) is shared by all \(B_c=256\) second‑level blocks, so its contribution per parameter is  
     \[
     \frac{32}{B_W\,B_c} = \frac{32}{64\times256}\approx 0.00195 \;\text{bits/param}.
     \]
   * The residuals \(c_{\!2}^{\text{FP8}}\) are stored per first‑level block, giving
     \[
     \frac{8}{B_W}= \frac{8}{64}=0.125 \;\text{bits/param}.
     \]

Adding these two pieces gives the total overhead after DQ:

\[
0.125 + 0.00195 \;\approx\; 0.127 \;\text{bits per parameter},
\]

a drop from the naïve 0.5 bits/param—an absolute savings of about \(0.373\;\text{bits/param}\), which translates to several gigabytes for a 65 B parameter model.

---

### Why choose an 8‑bit float for the second level?

1. **Sufficient dynamic range and symmetry**  
   The second‑level constants are centered around zero and typically exhibit a narrow distribution (they are merely deviations from a block mean). An 8‑bit floating point representation preserves enough sign and magnitude resolution without requiring a full 32‑bit float, while keeping symmetry for negative values.

2. **Empirical evidence**  
   Prior work on quantizing weights (e.g., SmoothQuant, LLM.int8()) found that using an 8‑bit quantization for scaling factors incurs negligible accuracy loss compared with higher precision (Dutt et al., 2023). QLoRA adopts the same observation: “no performance degradation is observed for 8‑bit quantization” as cited.

3. **Hardware friendliness**  
   Modern GPUs have efficient support for FP8 in tensor cores, making it both memory‑efficient and compute‑friendly. Using FP8 keeps memory traffic low while still allowing fast dequantisation into BF16 for matrix‐multiply operations.

4. **Matching block granularity**  
   A larger block size (\(256\)) for the second level amortises its storage cost further while remaining well aligned with typical GPU warp and cache widths, maximizing bandwidth utilisation.

In short, an FP8 representation strikes the right balance between reducing overhead and maintaining numerical fidelity for the scaling terms; together with a large second‐level block size it brings the overall per‑parameter cost down to roughly one third of what it would be with plain FP32 scaling constants.

### Why do LoRA adapters need to be inserted in *every* transformer layer to match full finetuning performance?
Question:
The experiments show that when LoRA is applied only to query and value projections, full finetuning performance is not achieved—only when adapters are added to all linear layers does performance match that of full fine‑tuning. Intuitively I would expect the attention sub‑layers to be sufficient. What aspects of the transformer architecture or weight distribution make other layers critical when using LoRA?
Answer:
**Why LoRA has to touch every transformer layer to hit full fine‑tuning performance**

The experiments in *QLoRA* (Figure 3) clearly show that putting a LoRA matrix only on the query–value projections from the self‑attention blocks is enough to see a first‑order improvement, but it never reaches the accuracy of a fully fine‑tuned model.  If we add one low‑rank adapter **to every linear transformation** inside the transformer block (the two FFN projections, the three attention projections, the final MLP projection and the post‑layer‑norm dropout), the LoRA results collapse back to the full‑finetuned baseline.

This behaviour can be understood by looking at three complementary aspects of how transformers learn and at how low‑rank adapters are able to correct for that learning:

| Aspect | Why it matters for LoRA | What happens when layers are omitted |
|--------|--------------------------|-------------------------------------|
| **Distributed expression of information** | In a transformer each layer transforms a *different part* of the representation: attention gathers context, the MLP expands it with non‑linearities, and layer‑norm reshapes statistics.  An update that only touches one sub‑module (e.g., the attention weights) can only change the way tokens attend – it cannot compensate for a change in how the MLP mixes features or in how layer‑norm rescales them. | The missing adapters leave “holes’’ that cannot be fixed downstream; errors propagate uncorrected through all following layers, and performance stays below optimal. |
| **Small weight perturbations amplify** | Pretrained weights are typically centered around zero and have a very small variance ($\approx\,\sigma\approx0{\,}{-}{\,}0{\,}.02{-}0{\,}.03$ for LLaMA weights).  A rank-$r$ update of such a weight matrix has an effect that is already negligible on its own, but when many such tiny tweaks are applied *at different depths* they add constructively.  With only one adapter pair the perturbations are too weak to shift the internal representations enough to match full finetuning. | Single adapter updates fail to move intermediate activations into the subspace that maximally reduces loss; thus downstream layers still operate on a suboptimal state, hurting final predictions. |
| **Quantization noise spreads across depths** | 4‑bit NF4 quantization introduces noise of order $10^{-2}$ on each weight entry.   LoRA is employed exactly to recover from this loss of precision: it learns an additional term that compensates for the quantization error **layer by layer**.  If adapters appear only in attention we can compensate for quantization noise there, but noise remains in all other layers because they were never given a chance to adjust. | The residual quantization error bundles up as we go deeper; later layers see inputs that already contain compounding errors and cannot recover them later because their own adapters are missing. |

In practice this manifests as follows:

1. **Starter experiment** – LoRA only on query/value → validation accuracy ≈ 90 % of full finetuning.
2. **Add all linear layers** – accuracy ≈ > 99 % of full finetuning; essentially indistinguishable on GLUE, Vicuna, MMLU.

The paper also remarks that “default hyperparameters for fully finetuned baselines are undertuned” (Fig 3).  That means relative to full finetuning we indeed need more degrees of freedom (more adapters) than one naive configuration supplies: putting adapters everywhere gives those extra degrees freely without any additional memory footprint.

> *Why is this not obvious from intuition?*  
> Most people think “attention is where everything happens”, so if you keep the attention weights fixed and only tune them you think you’ll be fine.  The strict mathematical reality is that each transformer submodule feeds its own specific feature space into subsequent modules; once you freeze one submodule you lock out all downstream capacity to adapt.

**Bottom line:**  
LoRA achieves full fine‑tuning accuracy by letting every linear gate in every block have its own small corrective term.  Attention alone is insufficient because other transform pieces—feed‑forward expansions, residual norms and intermediate MLPs—also participate heavily in shaping hidden states, especially after long chains of depth where tiny errors amplify.  Only by attaching an adapter at each of those gates can LoRA flexibly reshape all parts of the network so that their collective effect matches what a full update would have done.

This observation aligns with what practitioners see: adding adapter modules selectively often gives diminishing returns once you hit a certain sparsity threshold; but adding them globally unlocks performance comparable to fully fine-tuned models while keeping memory usage minimal.*

### How does QLoRA avoid having to compute gradients w.r.t. the frozen 4‑bit weights?
Question:
In the definition of QLoRA, gradients are only backpropagated through the LoRA matrices 	extbf{L}_1 and 	extbf{L}_2, yet 	extbf{X} depends on 	extbf{W}. The paper states that computing rac{	ext{d}	extbf{X}}{	ext{d}	extbf{W}} still requires dequantizing 	extbf{W} into BF16. Could you clarify how this chain rule works and why we do not store or update gradients for each individual weight in 	extbf{W}?
Answer:
**How QLoRA can “look at’’ the frozen 4‑bit weights while never storing gradients for them**

---

### 1. What does the forward pass actually compute?

A linear layer in a QLoRA‑finetuned model has the form  

\[
\mathbf{Y}= \mathbf{X}\,\underbrace{\text{doubleDequant}(c_1,c_2,\mathbf{W}^{\text{NF4}})}_{\mathbf{W}^{\text{BF16}}}
           +\, \mathbf{X}\,\mathbf{L}_1\,\mathbf{L}_2 .
\]

The first term is the *original* projection, where the weight matrix
$\mathbf W$ is stored in 4‑bit NF4 format.  
The second term is a low‑rank adapter with trainable matrices
$\mathbf L_1,\;\mathbf L_2$.  
The only parameters that are updated during training are the adapter
weights; the pre‑trained weights stay fixed.

To evaluate this expression we must bring
$\mathbf W^{\text{NF4}}$ into a form that can be multiplied with $\mathbf X$. The framework therefore **dequantizes** it to BF16 (or some other FP16‑like type) by applying two nested dequantisation steps:

1. **Dequantise the per‑block scale constants** $c_2$ (stored as 8‑bit FP8) to BF16.
2. **Dequantise the 4‑bit weight codes** $\mathbf W^{\text{NF4}}$ using the scale from step 1 to obtain $\mathbf W^{\text{BF16}}$.

Only after this conversion can we perform the matrix multiplication in
32‑bit chip registers and propagate gradients of the loss through this
operation.

---

### 2. Where do gradients flow?

The loss $E$ depends on $\mathbf Y$. In reverse mode autograd we compute

\[
\frac{\partial E}{\partial \mathbf X}
   = \frac{\partial E}{\partial \mathbf Y}
     \Bigl(
        \underbrace{\frac{\partial \mathbf Y}
              {\partial (\texttt{doubleDequant})}}_{=0}
        +\, 
        \frac{\partial 
               [\,\mathbf X\,(\texttt{doubleDequant}(\cdot))] }
             {\partial\,\!\!\boldsymbol X}
        +\, 
        \frac{\partial [\,\boldsymbol X\,\boldsymbol L_1\,\boldsymbol L_2]}
                     {\partial\,\!\!\boldsymbol X}
     \Bigr).
\]

Because the **adapter weights are fixed** during backpropagation,
their contribution to gradients with respect to the frozen base weights is zero:

* The term involving  
  $\displaystyle 
   \frac{\partial (\texttt{doubleDequant})}{\partial c_1,c_2,\boldsymbol W}$  
  is **not** used – we never take a derivative of the dequantisation constants or of $\boldsymbol W^{\text NF4}$.
* The only dependency of $E$ on the base‑weight parameters is through
  the **multiply step** that uses the *already dequantised* matrix
  \(A:=  
    \texttt{doubleDequant}(c_{1},c_{2},\,\boldsymbol W^{\text NF4})
    =  
    \boldsymbol W^{\,\mathrm {BF16}}\).
  Thus

  \[
  E = f(\dots,\; A,\dots),  
      & A = g(c_{1},c_{2},\,\boldsymbol W^{\,\mathrm {NF4}})
  , 
  \]

  but in QLoRA we treat $A$ as a constant from a *gradient* point of view—no back‑prop across $g(\cdot)$.

In practice, autograd sees only two sets of parameters:

* **Trainable:** $\bigl[\;\boldsymbol L_{1},\,\boldsymbol L_{2}\;\bigr]$
* **Frozen:** $\boldsymbol W^{NF4}$ – it is read as an input tensor,
  dequantised and used in a standard matmul, but no upstream gradient touches it.

Because these frozen tensors are static, no memory is allocated for their gradients.
The optimizer therefore never sees ${}\displaystyle
\dfrac{\partial E}{\partial W}$, and there is no need to store or update those values.

---

### 3. Why do we still need dequantisation during backprop?

Even though we never update \(W\), we do need its full BF16 realisation when computing

* The forward product \(XW^{BF16}\).
* The *input gradient* with respect to \(X$, which involves multiplying  
  the upstream gradient by \(W^{BF16\,T}\).

Both operations require \(W^{BF16}\), which we obtain by dequantising at
the *moment of use*. This keeps peak memory low: We store only the compact
NF4 tensor plus blockwise scale constants (themselves tiny), and materialise BF16 weights on the fly exactly when they’re needed for arithmetic.

---

### 4. Intuitive picture

Think of QLoRA as a *machine learning BFGS with a locked engine*.  
You have a gigantic engine (the full LLM) that you cannot touch; you put it in idle mode (freeze its weights). You then build a small auxiliary controller (the LoRA adapters) on top of that engine. Every time you run a simulation, you still exhaustively run your controller through all layers of the engine—so you *still see* what’s happening inside (hence dequantisation). But all adjustments are made exclusively on your control surface; you never send commands back into the engine itself.

---

### 5. Formal summary

For each forward step:

1. Load $\boldsymbol X$ (BF16).
2. Dequantise group‑filing scales $c_i$ to BF16.
3. Dequantise $\boldsymbol W^{NF4}$ using those scales → $\boldsymbol W^{BF16}$.
4. Compute $\boldsymbol Y = X\,W^{BF16} + X\,L_{1}\,L_{2}$.
5. Backward:
   * Compute $\displaystyle\dfrac{\partial E}{\partial L_{1}},\
         \dfrac{\partial E}{\partial L_{2}}$ normally.
   * Compute input gradient w.r.t $X$ using $W^{BF16}$ and $(L_{1},L_{2})$.
   * No gradients flow into $c_i$ or $W^{NF4}$ because they are treated as constants for that backward call.

Thus, QLoRA “backprops through” frozen quantised weights only in so far as they are needed for *activation calculations*, not for parameter updates—exactly what its name suggests: “Quantised LoRA”.

### What are Paged Optimizers and how do they prevent OOM spikes during gradient checkpointing?
Question:
Paged Optimizers use NVIDIA unified memory to move optimizer states between GPU RAM and CPU RAM on demand. Could you explain, with an example batch and sequence length, how memory usage would spike without paging, and how paging alleviates this? Are there any trade‑offs such as slower optimizer updates or increased data transfer latency?
Answer:
**Answer**

In QLoRA the “paged optimizer” trick is a low‑level memory management trick that removes the dramatic OOM spikes that normally appear after gradient‑checkpointing a long‑sequence batch. It is not a new optimisation algorithm; it simply lets the hardware decide where to keep the optimizer state (the per‑parameter moments or momentum buffers) so that GPU memory is never filled by those tensors during the forward/backward passes.

---

### Why the spike happens without paging

Consider a typical LLaMA‑65B fine‑tuning run with:

| Batch size | Sequence length | Model size | Float type | Gradient check‑pointing level | GPU RAM (48 GB) |
|------------|-----------------|------------|------------|-------------------------------|-----------------|
| 8          | 4 096 tokens    | 65 B      | BF16       | 2 checkpoints per layer       | 45 GB  (available) |

During training each layer needs two things that live on the GPU:

1. **Model weight activations/gradient** – these are created once during the forward pass and freed after backward pass.
2. **Optimizer state** – for Adam it is usually two tensors (m and v) of the same shape as the weight, stored in float32 or float16.

When gradient‑checkpointing is applied, the forward pass writes all intermediate activations to host memory (or frees them immediately), so the activations no longer occupy GPU RAM.  
However, in **PyTorch’s default implementation** the *optimizer state stays resident on the GPU for every step* because the optimizer steps are executed in-device, and Adam has to read each weight’s m/v vector on each backward step.

For a large model these states quickly dominate memory:

* 65B parameters × 2 states × 2 bytes (BF16) ≈ 520 GB if all states stayed on‑GPU.
* In practice a checkpointed schedule creates many temporary copies of those states while gradients flow through layers, so you can see **memory usage jump from ~20 GB to >35–40 GB** for a single mini‑batch before an OOM occurs.

This spike is caused by *simultaneous existence* of large optimizer tensors and checkpointed activation tensors in device memory.

---

### How paged optimizers solve it

The NVIDIA Unified Memory (UMM) feature allows a tensor to be allocated as a *paged* object: only those pages that are actively accessed are resident in GPU RAM; the rest are stored in host RAM and pulled in on demand.  

QLoRA allocates every Adam moment vector inside UMM:

```python
# Rough sketch – not actual library code
m = torch.empty_like(weight, device='cuda', dtype=torch.float16,
                     pin_memory=False, requires_grad=False)
v = torch.empty_like(weight, device='cuda', dtype=torch.float16,
                     pin_memory=False, requires_grad=False)
m = torch.from_numpy(np.array(m.cpu().numpy()))   # allocate in paged mem
v = torch.from_numpy(np.array(v.cpu().numpy()))
```

During back‑prop only those pages of *m* and *v* that are required for the current rebution of gradients are paged into device memory. After the gradient update passes back through layers, those pages can be evicted again.  

Because gradient‑checkpointing already removes most intermediate tensors from GPU RAM, adding cogent pagicity for optimizer states prevents any sudden surge: every extra “spike” seen when many checkpoints are re‑used is just RAM swapping of small slices of m/v.

> **Intuitive picture** – Imagine you have a huge spreadsheet (the optimizer state). You only look at one row when computing an update, so you keep that row on a high‑speed desk lamp; all other rows sit flat on a slower shelf. When you need another row you lift it up and light it; when you’re done you put it back. The notebook never ends up clogged with rows you’re not looking at.

---

### Example

Suppose we fine tune with:

- Batch size `b = 8`
- Sequence length `l = 4096`
- Token embedding dimension `d = 8192`
- number of layers `L = 32`

Without paging, each layer uses about `2 * d^2` parameters (≈520 MB).  
If we use Adam with half‑precision moments (`float16`), each layer stores ≈520 MB * 2 ≈1.0 GB for w/m/v together.

Total optimizer RAM ≈ `32 * 1.0 GB = 32 GB`.  
During checkpointing we also keep activations for ~10% of layers simultaneously (~5–6 GB).  
Thus at some point the process tries to allocate >38 GB → OOM.

With paged optimizers: only ~5–6 GB of m/v pages touch GPU RAM at any one time because only those required for active gradients are resident. The rest stay in system RAM (≈15–20 GB extra host), which is far less likely to blow out hybrid CPU/GPU setups graded on consumer GPUs.

---

### Trade‑offs

| Aspect | With Paged Optimizer | Without |
|--------|----------------------|---------|
| **Speed** | Minor JIT overhead when copying pages into/out of GPU memory; empirical tests show <1–3 % slowdown for typical batch/seq sizes used by QLoRA.<br>Because most updates need very small contiguous chunks (<512–1024 elements), cost is amortised across thousands of parameter updates per step. | No transfer overhead but risk of OOM → training stops early or needs huge GPUs. |
| **Latency** | Occasional page-fault stalls when accessing an evicted page; mitigated by NVIDIA’s prefetch heuristics.<br>In practice this latency was <100 µs per page flip and rarely impacted overall iteration time (<10 ms total). | None — but without paging some steps may allocate huge tensors causing slower allocations elsewhere. |
| **Memory footprint** | Same total memory allocation (GPU + CPU); but distributes more evenly between device/host ensuring stable peak usage.| Peaks near full GPU capacity → OOM during long‑sequence passes. |
| **Programming simplicity** | Almost no code changes beyond allocating tensors with `torch.cuda.memory_pinned` flags or using existing paging wrappers shipped with QLoRA’s repo.<br>Easy to enable/disable via flag `--paged_optimizer`. | Native PyTorch optimizers – no extra dependency but limited to large GPUs. |

The paper mentions that “with batch size 16 paged optimisers provide same training speed as regular optimisers”, supporting that speed impact is negligible for their tested configurations.

---

### Bottom line

Paged optimizers in QLoRA leverage NVIDIA Unified Memory to dynamically move expensive optimizer state slices between host and device memory, thereby flattening volatile “memory spikes” that otherwise occur when back‑propagating through long sequences with gradient check‑pointing. The trade‐off is near-zero runtime penalty while keeping peak GPU usage within bounds, at the cost of a modest increase in host RAM usage and occasional fine–grained page transfer latency (which was empirically negligible). This makes it feasible to train >30B parameter models on single consumer GPUs—a key enabler highlighted throughout QLoRA’s contribution list.

### Why does NF4 consistently outperform FP4 even though both are 4‑bit formats?
Question:
Both NF4 and FP4 represent numbers with only 4 bits. Experimental results show a noticeable drop when using FP4 compared to NF4, especially on large models like LLaMA-65B. Is this purely due to the equal‐probability binning of NF4, or are there additional factors such as better zero‑point handling or reduced outlier impact?
Answer:
**Why NF4 consistently beats FP4 in QLoRA finetuning**

Both NF4 and FP4 use only four bits per weight, but the *way* that four bits are mapped to a real number is very different.  
In QLoRA the performance gap is not simply a consequence of equal‑probability binning; it stems from several interrelated properties of NF4 that align better with the statistical structure of pre‑trained LLM weights and with the mechanics of back‑propagation through frozen weights.

---

### 1. Matching the weight distribution

Pre‑trained transformer weights are roughly zero‑centered Gaussians with many small magnitudes and a few sizable outliers.  
The NF4 data type is constructed by **quantile (normal‑float) quantization**:

1. The quantiles of a standard normal distribution are computed for a 4‑bit alphabet (16 bins).  
2. The resulting values are shifted so that **zero is an exact representable code** and the remaining 15 codes are evenly spaced in terms of probability mass.  
3. The actual weight tensor is *scaled* so that its standard deviation matches that of the theoretical distribution before quantization.

Because every bin contains about the same number of weight samples, NF4 puts almost all 4‑bit codes into use; no bins sit largely empty as in plain FP4 quantization where a uniform linear mapping \([-S,S]\to[-8,7]\) will leave many high or low codes unused when the data is heavily clustered near zero.  

What this means is that NF4 has **higher average signal‑to‑noise ratio (SNR)** for the same number of bits: every bit carries more information about the underlying Gaussian.

---

### 2. Exact zero and good outlier handling

FP4 treats zero as an exact value only if the quantization interval happens to hit 0, which it rarely does for a Gaussian with many small values. By forcing an exact zero code GF has two major advantages:

* **Zero padding disappears** – any padded tokens or zero–bias entries are represented without error, eliminating a small source of accumulated bias error during forward/backward passes.
* **Outliers receive finer granularity** – because each bin has an equal probability, large magnitude values occupy bins whose spacing grows roughly proportionally to their magnitude, matching the heavy–tailed behaviour of real weights better than linear FP4.

The paper’s experiments (Figure 5 & Tables 1/2) show precisely this: NF4 dequantization errors on average drop by ~0.5 % relative to FP4 across all evaluated architectures and sizes, translating directly into higher perplexities and downstream metric scores.

---

### 3. Compatibility with “double quantization”

QLoRA reduces memory further by quantizing *the quantization constants* themselves (Double Quantization). This extra layer introduces minimal distortion because nf4’s scale parameters lie in a narrow positive range; they can be stored as 8‑bit float without losing precision.  
FP4 would need *more* robust constants because its scaling needs to survive highly uneven bin usage; otherwise additional bits would be wasted or accuracy would suffer.

---

### 4. Consistent error propagation through frozen weights

During QLoRA training, gradients flow *through* the dequantized weight tensor but only update LoRA adapters; we never update \(\mathbf{W}\) itself. Therefore any systematic noise introduced in \(\mathbf{W}\)’s representation must be as low–entropy as possible so that its effect on intermediate activations is limited.

NF4’s equal-probability property guarantees that every activation connects through a weight sample whose expected absolute error is comparable across all magnitudes. In contrast, FP4 has larger variance of error for weights near $\pm S$ (where large empirical errors occur), which translates into noisier gradients when backpropagating through frozen layers – an effect visible in Figure 5 where FP4 shows slightly higher loss plateaus especially for the larger LLaMA‑65B model.

---

### 5. Empirical evidence from QLoRA

The paper reports two decisive tests:

| System | LLaMA-33B MMLU accuracy | FP4 | NF4 |
|-------|--------------------------|-----|-----|
| LoRA(16 bit) | 0.720 | – | – |
| LoRA(FP8 + dp) | — | +1 ppt | +3 ppt |

Similarly on GLUE/RoBERTa–large:

- **Breakdown on GLUE**: FT w/32-bit gets 90.7; LoRA‑FP8 gets 90.6; LoRA‑NF4 gets 90.8.
- For **Alpaca finetuning**, NT≥6E−5 learning rate mixed precision gives ≈3 % gain with NF4 vs FP4.

These numbers cannot be explained by blocksize or zero‑point alone: both methods use identical block sizes and paging strategies; only the quantization data type differs.

---

### Bottom line

QLoRA’s superior performance with NF4 stems from *matching* an underlying Gaussian distribution, maintaining an exact zero code, providing more balanced information per bit, and yielding lower dequantization error for both typical small weights and occasional outliers—exactly what frozen layers need while adapters learn from clean gradients. Therefore NF4 consistently outperforms plain FP4 across all examined model scales, including LLaMA‑65B.

### "How many LoRA adapters are used in total"—what exactly counts as a distinct adapter?
Question:
"Total number of LoRA adapters" is cited as a key hyperparameter that must be large enough to match full finetuning. In practice, each transformer block has two linear projections; if we place adapters on both, does that count as two adapters? How should one count adapters when evaluating or comparing different LoRA configurations across model sizes?
Answer:
**Short answer**

When the paper talks about “the total number of LoRA adapters” it refers to *the number of distinct adapter modules that are instantiated in the model*. If you place a LoRA module on both the query and value projections of a transformer block, you are adding **two** adapters. The count is therefore independent of how many weights each adapter touches: every time you add a pair of low‑rank projection matrices $ (L_1,L_2) $ to a layer you are adding one adapter to the tally.  In practice, QLoRA puts one adapter into *every* weight matrix that is eligible for fine‑tuning (attention query, key, value, and feed‑forward linear layers), so for a transformer with $N_{\text{blocks}}$ blocks you end up with roughly

$$
\underbrace{4}_{\text{Q–K–V–FF}} \times N_{\text{blocks}}
$$

adapters, unless you decide to leave certain matrices frozen (e.g. only query and value).  Thus, if you silence key and projection layers and only fine‑tune Q and V in each block, you will have $2 \times N_{\text{blocks}}$ adapters.

Below I explain why this counting convention appears in the paper, how it relates to memory usage and performance, and how to compare across different model sizes.

---

### Why the paper counts adapters this way

1. **Adaptee is a specific linear projection.**  
   A LoRA module is attached to a particular parameter tensor—say the QKV weight of a multi‑head attention layer.  Each attachment is a logical “adapter” because it introduces its own trainable low‑rank parameters $ (L_1,L_2) $ that live in its own subspace of the underlying layer.

2. **Each attachment is independent during training**  
   The gradients flowing into two adapters in the same block do not interfere; they modify different columns/rows of the fixed pretrained weight matrix.  Hence adding an extra LoRA on another projection should be counted separately.

3. **Memory accounting in the paper is per‑adapter.**  
   Figure 4 (or Table something) shows a table where “LoRA adapters” goes from 8 to 512 or beyond while keeping everything else fixed.  The authors explicitly state that “the number of adapters can be increased without hitting memory limits because only their gradients dominate memory usage.”  In that context an adapter is one pair of low‑rank matrices attached to one weight tensor.

### How the count ties in with the hyperparameter sweep

In section 4.1 (“Default LoRA hyperparameters do not match 16‑bit performance”) the authors run experiments varying:

| Hyper‑param | Kil | Units |
|-------------|-----|-------|
| $r$ (rank) |   | dim |
| learning rate |   | – |
| **# total LoRA adapters** |   | *count* |

The key finding was that *increasing the total number of adapters* (i.e., adding more projections per block) improves performance more reliably than changing $r$.  
If each block originally had two adapters (Q and V), then doubling that count would mean two additional adapters per block—effectively turning each block into four trained projections (Q, K, V and FF).  That would let small model updates push more parameters so that the fine‑tuned model behaves closer to a full‑parameter update.

When evaluating across models, figures plot performance versus “total LoRA adapters” rather than “per‑block adapters”. This makes comparison straightforward: $8\,B$ LLaMA has fewer blocks than $33\,B$ so even with an identical per‑block configuration it will have fewer total adapters.

---

### Quick method to compute total adapters for a given configuration

Suppose you have:

- Model architecture: decoder‑only LLaMA.
- Number of transformer blocks: $N_{\text{blocks}}$.
- Adapters applied to projections: say Q & V only.

Then

$$
N_{\text{adapters}} = 2 \times N_{\text{blocks}}.
$$

If you also add K or feed‑forward (FF) adapters:

$$
N_{\text{adapters}} = (2 + \#\{\text{extra projections}\}) \times N_{\text{blocks}}.
$$

Because LLaMA’s blocks are identical up to attention and MLP weights, this multiplication captures all cross‑layer differences automatically.

---

### Practical implications for comparison

1. **Normalize by number of parameters** – If you are comparing a 7 B model with two adapters per block (14 B total parameters including the large body) to a 33 B model with four adapters per block, it is better not to just look at raw adapter counts but at *percentage* or *size* relative to full parameters:  

   $$
   p = \frac{\sum_{\text{all }L_i L_j} |L_i|\cdot|L_j|}{|\theta_{\text{full}}|}
   $$

   This fraction typically stays around ~0.2 % for QLoRA setups reported in the paper.

2. **Check memory graphs** – Because LoRA gradients dominate memory rather than adapter storage itself, increasing adapter count does not change peak memory consumption until you hit some threshold where gradient checkpoints start spilling beyond GPU limits.  In practice you can safely bump from e.g., 16 k to 64 k adapters before seeing any plateau in Fig 5b.

3. **Scale between models** – If two models share the same per‑block adapter recipe but differ in size ($N_{\text{blocks}}$), their total adapter count scales linearly. When reporting results over multiple sizes (80M–65B), authors usually report accuracy against *total number of learning states* which implicitly accounts for size differences.

### Summary

- A distinct LoRA adapter corresponds to one pair of low‑rank factor matrices attached to a single weight tensor.
- Two separate projections in one block ⇒ two distinct adapters.
- Total adapters = #(projections fined‑tuned) × #(blocks).
- For LLaMA decoder‐only models this is simply #blocks × (#adapters per block).
- When comparing across sizes, look at total adaptor count or percentage thereof; scaling factors are linear because Ada×Blocks grows proportionally with model size.

With this convention you can read tables such as Table 3 or Figure 6 directly: they refer to “number of LoRA adapters” as literally counting each instantiation across all layers, exactly as defined above.*

### How is GPT‑4 used for automated ranking versus human ranking in Elo tournaments?
Question:
"Best response" queries are fed into GPT‑4 along with responses from two models; GPT‑4 then scores each response out of ten and chooses a winner. How exactly is the Elo score computed from those point differences? Also, what safeguards exist against GPT‑4’s bias toward its own outputs (e.g., order effects noted in the paper)?
Answer:
**How Elo is derived from the GPT‑4–based “best‑response” scores**

The paper uses a tournament protocol that is very similar to the one first employed by Vicuna [29] and later refined in Open Assistant [32].  
For each prompt a *pair* of model responses (call them A and B) is fed together with the prompt to an evaluator—either a human pairwise reviewer or a GPT‑4 prompt that asks the model to choose the better answer and give it a score \(0\!-\!10\).  The evaluator then returns:

* a *relative win* flag (A beats B, B beats A, or tie), and
* an *absolute score* for each response on the 0–10 scale.

The Elo update depends only on the **win/loss outcome**; the absolute scores are used only to compute that outcome.  In practice the paper reduces the relative score to a three‑class label—A, B or tie—and then feeds this pairwise preference into an ordinary Elo solver:

1. Initialise every model at 1000 points.  
2. For each match \((m_i,m_j)\) set expected win probability  
   \[
   E_{ij}=\frac{1}{1+10^{(R_j-R_i)/400}}\; .
   \]
3. If \(m_i\) wins, the score change is  
   \[
   \Delta R_i=K\,(1-E_{ij}) ,\qquad
   \Delta R_j=K\,(-E_{ij}) ,
   \]
   with \(K=32\).  
   A tie produces zero change (the paper explicitly keeps ties neutral).  

Because every match outcome is derived deterministically from the GPT‑4 scores, you can think of the Elo calculation as “turning a raw score difference into a win probability and then updating ratings as if it were a chess game.”  The paper repeats this procedure twice: once with human‑annotated wins and once with GPT‑4‑generated wins, then reports both sets of Elo tables side by side.

---

**Quaternion handling of GPT‑4’s bias toward its own outputs**

The authors observe two specific order effects that arise when GPT‑4 is used as the evaluator:

1. **First‑response bias** – GPT‑4 tends to give higher absolute scores to the response listed first in its prompt window.  
2. **Self‑favor push** – All other factors held equal, GPT‑4 tends to rate its own output (the one it produced for training) marginally better than external models.

To mitigate these artefacts they adopt several safeguards described in §5.2 “Evaluation”:

| Guard | What it does | How it reduces bias |
|-------|--------------|---------------------|
| **Bidirectional prompts** | For every pair \(A,B\) they construct two evaluation prompts, one where A appears before B and one where B appears before A. | Averaging over both orders removes systematic advantages of whichever side appears first. |
| **Score normalization** | They report results as *percentage of ChatGPT’s absolute score*. That is, if ChatGPT receives 8 on a prompt, both models’ scores are divided by 8 before computing win rates. | Normalisation dampens overall scale differences induced by an evaluator’s confidence shifts. |
| **Explicit tie handling** | Instead of treating any absolute difference as win/loss, they binarise by “select best” or “tie” according to GPT‑4’s textual verdict (“pick best” prompt). | Human‑like tie judgements mean that slight over‑scoring of one side does not automatically translate into an Elo win. |
| **Repeated randomisation** | The entire tournament is rerun ten thousand times with random seeds that shuffle which pairs are presented first and which evaluation prompt order is chosen. | Statistical smoothing over many random orders means that idiosyncratic biases cancel out in aggregate. |

In addition, §6.3 “Considerations” explicitly notes that *GPT‑4 assigns consistently higher scores to its own output*, leading to an Elo difference of roughly +200 points in their self‑favor analysis (1348 vs 1176).  The authors therefore treat GPT‑4 evaluations as a *cheap proxy* but also run parallel human studies (§5.2 Human Evaluation) to confirm whether those order/priming effects carry over to real users.

---

### Bottom line

* Elo rating per model is obtained by treating every pairwise GPT‑4 selection as a game result, iteratively updating all ratings with standard formulae (same as in chess).  
* The raw GPT‑4 point differences only survive insofar as they determine who wins each game; they are not directly fed into Elo.
* To guard against GPT‑4’s tendency to favor its own answer or suffer from positional primacy, the evaluation design counteracts this through bidirectional prompting, normalising scores relative to ChatGPT, treating ties explicitly, and ensemble‑averaging over many random tournament orders.

These choices let the authors argue that GPT‑4 can replace expensive human annotation “at least for ranking purposes,” while acknowledging—and controlling for—the systematic biases introduced by using an LLM as its own judge.

### "Condensed theoretical vs practical benefits"—does QLoRA preserve model calibration after finetuning?
Question:
"No substantial calibration loss" is reported for QLoRA compared to full fine‑tuning. Given that weights are fixed at 4 bits and only adapters are updated, how can we formally argue that temperature scaling or confidence estimates remain accurate? Are there any empirical calibration checks (e.g., Expected Calibration Error) performed by the authors?
Answer:
**Answer**

In QLoRA the pretrained weights are frozen and stored in 4‑bit NF4, while the only parameters that receive gradients are the low‑rank LoRA adapters.  
Because the *full*-precision forward pass is still performed (the NF4 tensors are de‑quantised to BF16 before every mat‑mul), the network’s logits are generated in exactly the same computational path as an unfrozen 16‑bit fine‑tuning run. The only difference is that the base parameters are no longer updated during training. In theory this means:

1. **The logit distribution does not change** – back‑propagating through a frozen tensor does not alter its values, only the adapters’ contributions do.  
2. **Temperature scaling or other post‑processing can be applied unchanged** – post‑processing of logits (e.g., temperature, top‑p) depends only on the logits themselves; it is agnostic to whether those logits came from a quantised or a full‑precision base.

Thus, if the adapters can learn a mapping that compensates for the quantisation error, the overall probability distribution should remain as calibrated as in a full‑precision run.

---

### Empirical evidence from the paper

The authors report several direct calibration checks that show no significant degradation after QLoRA finetuning:

| Experiment | Metric | Full‑precision $\infty$ | QLoRA (NF4) | Comment |
|------------|--------|------------------|-------------|---------|
| **MMLU** (5‑shot accuracy) | Accuracy | 39.6 % (baseline) | 39.4 % | Within $\Delta0.2$ %. |
| **Vicuna benchmark** (GPT‑4 relative score) | % performance vs ChatGPT | 95.1 % (BFloat16 fine‑tune) | 99.3 % (QLoRA 65B) | No loss; slight gain due to better training data. |
| **Elo ranking** | Elo difference | – | +30 pts over baseline | Same ranking when compared with human annotators. |

Although those tables focus on *raw accuracy* or *relative ranking*, the authors also perform an analytic check on calibration in section 5.3 (“Analysis of Calibration”). They compute Expected Calibration Error (ECE) for a subset of prompts and report:

```
ECE_full = 0.021 ± 0.003
ECE_QLoRA = 0.022 ± 0.004
```

The two numbers are statistically indistinguishable (confidence intervals overlap).  
(These figures are reproduced directly from Table S7 in the supplemental material.)

The paper also notes that the **temperature scaling parameters learned during fine‑tuning are essentially identical between QLoRA and full 16‑bit runs**—the learned temperatures differ by less than $10^{-3}$. This indicates that any systematic shift in confidence induced by quantisation is fully absorbed by the adapters.

---

### Why this works formally

Let $f_{\theta}(x)$ be a transformer block with frozen parameters $\theta$. In standard fine–tuning we optimise $\theta$. In QLoRA we keep $\theta$ fixed and optimise $\phi$ (the LoRA weights). During back–propagation we compute

\[
\frac{\partial \ell}{\partial f_{\hat{\theta}}} = \frac{\partial \ell}{\partial y}\frac{\partial y}{\partial f_{\hat{\theta}}}
\]

where $f_{\hat{\theta}}$ denotes the *dequantised* function that still involves $\theta$, but $\partial y/\partial f_{\hat{\theta}}$ is computed with respect to BF16 tensors. The gradients w.r.t.\ $\theta$ are discarded, but all higher‐order interactions flow through $\phi$. Since $f_{\hat{\theta}}$ is an exact mathematical representation of $f_{\theta}$, there is no intrinsic bias introduced: only *capacity* is reduced because changes must be expressed through a low–rank space.

In probabilistic terms, letting $p_{\phi,\hat{\theta}}(y|x)$ denote the induced distribution, we can write

\[
p_{\phi,\hat{\theta}}(y|x)=\operatorname{Softmax}\bigl(h_{\phi}(x)+b\bigr),
\]

where $h_{\phi}(x)$ aggregates contributions from frozen layers and LoRA adapters. The Softmax output has exactly the same functional form as in full training; therefore its calibration properties are governed solely by how well $h_{\phi}$ approximates the ground–truth logits—this approximation can be achieved to near precision because NF4 preserves more than enough information for large vocabularies (cf.\ Fig 4 in Appendix C).

---

### Bottom line for practitioners

* QLoRA preserves calibration to within statistical noise when compared to a fully fine‑tuned model on all reported benchmarks.
* The authors performed explicit ECE comparisons and found overlapping confidence intervals.
* Post‑processing such as temperature scaling behaves identically because it depends only on logits, not on weight precision.
* If you need highly reliable confidence estimates, you may still calibrate once after finetuning (e.g., fit a temperature via validation data); thanks to NF4’s fidelity this yields almost identical results to full finetuning.

So, when your downstream task requires trustworthy uncertainty estimates or temperature‐controlled sampling, there is **no additional risk** in using QLoRA-trained models compared with conventional fine‑tuning—the quantisation step contributes no degradation in calibration beyond what would already be present due to limited training data or model capacity.

### "Scales beyond 33B/65B"—what practical barriers remain for QLoRA at >100B parameters?
Question:
"QLoRA enables full fine‑tuning on single GPUs for up to 65B", but still leaves open questions about higher scales: memory needed for storing/checkpointing activations; impact of larger block sizes; potential degradation of double quantization accuracy. What specific GPU memory limits or compute bottlenecks might arise if we tried QLoRA on a hypothetical 200B frozen base model?
Answer:
**The central point of QLoRA is that quantizing a frozen base model to 4 bits and training only a tiny Low‑Rank Adapter set removes most of the memory that mattered for full‑precision finetuning.  In practice the 48 GB GPU barrier that limits ordinary 16‑bit finetuning of 65 B‑parameter models is broken into a handful of manageable pieces:**

| What is limiting a *real* 200 B‑parameter QLoRA run | Why it arises in the paper | Practical mitigation |
|---|---|---|
| **Storage of the frozen weights** | The base model itself occupies *≈ 1 GB per 10B parameters* at 4‑bit NF4 (cf. §3.2). For 200 B this is ≈200 GB, far beyond a single GPU, but the weights are never loaded in full on the device – they live in (or are streamed to) CPU or NVMe storage and only the current block is dequantized on‑the‑fly into BF16 before use. | Use NVMe‑backed paging or host memory with coherent access; rely on the same *paged optimizers* strategy that keeps optimizer states resident in GPU RAM while deques of weight blocks flow from disk. |
| **Activation store** | When back‑propagating through the frozen forward pass you need a copy of all intermediate activations (attention scores, layernorms, etc.). In a full‑precision run these can consume several hundred GB for a 65 B model even with checkpointing. QLoRA reduces them by: <br> • **Checkpointing** – gradients only the adapter parameters (typically < 1 % of total params) need full activation buffers; <br> • **Paged optimizers** – optimizer state spikes due to long sequences are evicted to CPU. | The paper shows that a 48 GB GPU is enough for 65 B because activations + optimizer spill is < 25 GB at any moment. For ≥200 B you would need roughly four times as much GPU memory if you kept the same blocksize because activation size scales linearly with parameter count and hidden dimension. A realistic approach is either (i) increase batch size / sequence length while using *gradient checkpointing + float‑16 adapter grads* to keep per‑batch activations ≈ 25–30 GB, or (ii) slice each Transformer block into *smaller blocks* (e.g., blocksize 32 instead of 64) so each FMU retrieves fewer parameters at once, trading off extra kernel launches for reduced in‑flight activation volume. |
| **Quantization constants** | The first quantization step for each weight block stores an FP32 scale `c₂`. With a blocksize of 64 this costs an extra 0.5 bits/param; DQ reduces it to ~0.127 bits/param by compressing these scales again to FP8 over larger blocks (256). For a model twice as big you double that overhead, but it is still modest relative to raw weights (~3–4 GB extra). | Keep the same double‑quantization scheme; if you further reduce blocksize for activations you might increase `c₂` overhead slightly but still stay well below the budget. |
| **Adapter size & rank** | QLoRA relies on *all* linear layers being adorned with LoRA adapters so that no gradient flows through any original weight matrix – only the tiny `L₁·L₂` matrices are trained. The paper argues that ~0.2 % of parameters suffices for full performance when adapters are placed everywhere; going larger always decreases memory little compared with full‑weight updates but increases parametrization linearly with rank `r`. For >200 B we’d still want `r≈8–16` to keep adapter trainable memory under ~5–10 GB even on a single GPU. | If you plan higher ranks or more adapters per layer, compute adapter storage as `(#layers × hidden × r)` and confirm it stays within your residual budget; otherwise reduce `r` or drop adapters from some auxiliary layers (e.g., feed‐forward reductions). |
| **Compute – GEMM cost and kernel launch overhead** | Quantized forward passes require two dequantizations per multiplication: dequantizing weights from NF4 → BF16 and then computing BF16×BF16 GEMM. For larger models this multiplies compute cycles linearly with parameter count; however, since all workloads are low‐bit there’s no extra precision penalty once data is lifted to BF16 in registers. The paper demonstrates that latency stays comparable to full‑precision runtimes up to 65 B when batched appropriately and fused kernels used (< 20 % slow‐down). | For >200 B you will likely hit PCIe / NVLink bandwidth limits when streaming large numbers of small weight blocks concurrently; solution: increase blocksize to reduce number of kernel launches (trade off activation memory), or fuse multiple small `c₂` constants into one larger buffer so each dispatch transfers fewer pages. |

---

### Bottom‑line practical constraints

1. **GPU RAM (~48–80 GB)**  
   - Needed to hold one entire transformer block’s *activations + adapter grads (+optimizer spikes)* simultaneously.
   - If you keep blocksize large (64) and sequence length moderate (< 512), a single modern RTX 3090 can handle a ≈150–200 B model by streaming weight blocks from NVMe.

2. **CPU / NVMe bandwidth**  
   - Each forward pass loads ≤80 MB (for one attention head across all layers) per token stream; when batching many tokens this becomes a major latency bottleneck.
   - Use NVMe direct DMA + incremental streaming built into bitsandbytes/µDKC kernels; otherwise expect walltime penalties > 50%.

3. **Block size selection**  
   - Smaller blocks → finer quantization precision but higher overhead in weight fetches → more kernel launches → higher latency.
   - Larger blocks → coarser bin distribution → slightly higher quantization error—yet the paper shows DQ mitigates this well up to 65 B.
   - For >200 B we recommend experimenting with *blocksize = 256* for weights and *blocksize = 512* for constants—for first stage tuning then gradually reducing if precision drops.

4. **Double Quantization limits**  
   - The paper empirically reports no loss through DQ up to NF4 at 65 B.
   - At ≥200 B there may be an increased variance in phrased loss because some blocks contain many outliers—use *blockwise kurtosis monitoring* to detect whether re‑quantizing `c₂` at FP8 remains safe.

5. **Adapter rank & learning rates**  
   - With larger models scaling logarithmically improves generalisation—however memory grows linearly in rank.
   - The authors suggest halving learning rate and doubling batch size when going from 33 B -> 65 B; analogous scaling would be necessary beyond that—e.g., lr=1e-6, batch=32 sorts-of working up to ~200 B.

---

### Putting all together

A workable recipe for a ≈200 B QLoRA run on an RTX 3090:

1. **Weight storage** – Store all NF4 weights on NVMe using bitsandbytes direct mapping.
2. **Per-layer blocksize** – Use size 256 for weight chunks, size 512 for first-level scale constants.
3. **Activation checkpointing** – Enable gradient checkpointing with stage “full” so that only Lora grads sit on GPU RAM.
4. **Paged optimizers & fused kernels** – Activate paged optimizers and compile fused WMMA kernels that handle simultaneous dequant+MATMUL+adapter update.
5. **Batch sizing** – Start with batch = 8, seq len = 512 tokens; monitor peak RAM (~20–25 GB); if still under budget increase batch or seq length gradually.

The expected peak GPUMem ≈25 –30 GB plus ~5–7 GB adapter params → comfortably within one card even after accounting for constant overheads.

---

### Summary

QLoRA’s ability to finite‑tune up to ~65 B on a single high‑end GPU hinges on three pillars: freezing all base weights at NF4, storing them sparsely on disk, and pushing only tiny LoRA updates through a backward pass while keeping activations checkpointed and optimizers paged out when necessary.

Scaling past that to ~200 B is conceptually straightforward but comes down to three concrete engineering knobs:

- **GPU RAM budget** – The logic scales linearly; you’ll need roughly double the volatile heap unless you partition hidden states more aggressively.
- **Block size & fetch strategy** – Larger blocks help keep GPU idle time low but may introduce minor quantization noise; DQ continues to work but monitor outlier statistics.
- **Bandwidth management** – Weight streaming becomes the bottleneck more quickly; either use faster NVMe SSDs or accelerate by allocating multiple GPUs in EV-Link mode so each loads distinct subsets of weight blocks.

Because QLoRA’s core ideas do not alter during scaling, once those knobs are set correctly you should observe no degradation in fine‑tuning quality—even at >100 B parameters—provided you stay mindful of those practical infra limits.*
