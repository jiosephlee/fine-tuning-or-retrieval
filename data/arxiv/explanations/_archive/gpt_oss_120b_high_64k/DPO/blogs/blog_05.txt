# Step‑by‑Step Guide: Implementing Direct Preference Optimization in Your Project  

*If you’ve been following the latest developments in RL‑from‑human‑feedback you’ve probably heard about **Direct Preference Optimization (DPO)** – a surprisingly simple way to turn preference data into a fine‑tuned language model without any reinforcement learning loop. In this post we walk through everything you need to run DPO yourself: preparing preference pairs, picking a reference policy, coding the loss in PyTorch/Transformers, tuning the KL‑strength hyperparameter β, and monitoring the training process.*  

---

## 1. What DPO Is – In a Nutshell  

Standard RLHF pipelines consist of three stages:

1. **Supervised fine‑tuning (SFT)** – gives you a decent baseline LM (`π_ref`).  
2. **Reward modelling** – fits a reward network `r_φ(x,y)` to human pairwise preferences using a Bradley‑Terry likelihood.  
3. **RL fine‑tuning** – typically PPO maximises `r_φ` while penalising large KL‐divergence from `π_ref`.

DPO collapses steps 2 and 3 into a **single maximum‑likelihood objective** that directly updates the policy `π_θ`. The key insight is that under the KL‑constrained RL problem the optimal policy has the closed form  

\[
\pi_r(y\mid x)=\frac{1}{Z(x)}\: \pi_{\text{ref}}(y\mid x)\,
\exp\!\Bigl(\frac{1}{\beta}\,r(x,y)\Bigr) .
\]

Rearranging gives an *implicit* reward  

\[
r(x,y)=\beta\Bigl(\log\frac{\pi_r(y\mid x)}{\pi_{\text{ref}}(y\mid x)}+\log Z(x)\Bigr),
\]

and because Bradley‑Terry only cares about **differences** `r(x,y₁)-r(x,y₂)`, the partition term `Z(x)` cancels out. Plugging this into the likelihood of human preferences yields the **DPO loss**

\[
\boxed{
\mathcal L_{\text{DPO}}(\theta)=
-\;\mathbb E_{(x,y_w,y_l)\sim\mathcal D}
\Bigl[
\log\sigma\!\Bigl(
   \beta\,\log\tfrac{\pi_\theta(y_w|x)}{\pi_{\text{ref}}(y_w|x)}
 - \beta\,\log\tfrac{\pi_\theta(y_l|x)}{\pi_{\text{ref}}(y_l|x)}
   \Bigr)
\Bigr]
}
\tag{1}
\]

where `σ` is the logistic sigmoid and `β>0` controls how strongly we penalise deviation from `π_ref`. In practice we define an *implicit reward*  

\[
\hat r_\theta(x,y)=
   \beta\,(\log \pi_\theta(y|x)-\log \pi_{\text{ref}}(y|x))
\]

and **the loss reduces to**  

\[
-\log\sigma(\hat r_\theta(x,y_w)-\hat r_\theta(x,y_l)).
\]

No separate reward network is required and no sampling loop (as in PPO) appears – we just need log‑probabilities of two completions under two frozen models.

## 2. Preparing Preference Data  

### 2.1 Required format  
Each training example must contain:

| Field | Meaning |
|-------|---------|
| `prompt` (`x`) | The context we condition on (e.g., a user query). |
| `win` (`y_w`)   | The **preferred** continuation (human label “better”). |
| `lose` (`y_l`) | The **dispreferred** continuation. |

A convenient storage option is **JSON Lines** (`*.jsonl`):

```json
{
  "prompt": "Write a short poem about autumn.",
  "win":   "Leaves fall crimson and gold as breezes sigh.",
  "lose":  "Autumn is cool."
}
```

### 2.2 Collecting labels  
*Human annotation:* Show annotators two model outputs side by side and ask “Which response is more helpful / correct / safe?”  
*Proxy labeling:* For quick experiments you can reuse an existing classifier (sentiment analysis for sentiment control, ROUGE score for summarization quality) to generate synthetic preferences – exactly what the paper does for its controlled sentiment experiment.

### 2.3 Splitting & batching  
- **Train / validation split:** e.g., 90 % / 10 % of examples.
- **Batch size:** limited by GPU memory because each example needs *four* forward passes – `π_ref` + `π_θ` on both win and lose completions.
- Use HuggingFace’s `datasets` library (`load_dataset('json', data_files='prefs.jsonl')`) which streams batches efficiently.

---

## 3. Choosing & Preparing a Reference Model  

The reference policy `π_ref` should be *the model you want to stay close to*. Typical choices:

| Scenario | Recommended reference |
|----------|------------------------|
| You already have an SFT checkpoint for your task → use it directly (`π_ref = π_SFT`). |
| No SFT available → train a tiny “reference” by **supervised fine‑tuning only on wins** (`Preferred‑FT`). This guarantees that both `π_ref` and later `π_θ` share the same token distribution baseline. |
| You want a *generic* base LM → take a pretrained checkpoint (e.g., `gpt2-large`) and treat it as your reference; later you’ll effectively be learning from scratch but still benefit from ΔKL regularisation.*

**Important:** Keep `π_ref` frozen during DPO training (no gradient propagation). In code this simply means calling `.eval()` on it or wrapping it inside `torch.no_grad()` blocks.

## 4. Coding the DPO Loss in PyTorch  

Below is a minimal end‑to‑end script that works with any HuggingFace auto‑model (GPT‑2 family shown). It assumes you have two models loaded:

```python
import torch
import torch.nn.functional as F
from transformers import AutoTokenizer, AutoModelForCausalLM

# -------------------------------------------------
# 1️⃣ Load models & tokenizer
# -------------------------------------------------
model_name = "gpt2-large"                 # replace with your SFT checkpoint
tokenizer = AutoTokenizer.from_pretrained(model_name)
policy   = AutoModelForCausalLM.from_pretrained(model_name).to("cuda")
reference = AutoModelForCausalLM.from_pretrained(model_name).to("cuda")
reference.eval()                          # freeze grads automatically

# -------------------------------------------------
# 2️⃣ Helper to obtain full‑sequence log probability
# -------------------------------------------------
def seq_logprob(model, inputs):
    """
    inputs : dict returned by tokenizer(..., return_tensors='pt')
    Returns : Tensor of shape (batch,) containing sum(log p(token_i))
    """
    with torch.no_grad() if model is reference else torch.enable_grad():
        outputs = model(**inputs)
        # shift logits & labels so each token predicts next token
        shift_logits = outputs.logits[..., :-1, :].contiguous()
        shift_labels = inputs["input_ids"][..., 1:].contiguous()
        # log softmax → log prob per token
        log_probs = F.log_softmax(shift_logits, dim=-1)
        # gather prob of actual next token
        token_logprob = log_probs.gather(-1,
                                         shift_labels.unsqueeze(-1)).squeeze(-1)
        # sum over sequence length → seq log prob
        return token_logprob.sum(dim=-1)

# -------------------------------------------------
# 3️⃣ DPO training loop (simplified)
# -------------------------------------------------
beta = 0.1                         # <-- tune this!
optimizer = torch.optim.AdamW(policy.parameters(), lr=5e-6)

for epoch in range(num_epochs):
    for batch in dataloader:       # each batch yields prompt/win/lose strings
        # Tokenize concatenated prompt+completion for each variant
        win_inputs   = tokenizer(batch["prompt"], batch["win"],
                                 truncation=True,
                                 padding="longest",
                                 return_tensors="pt").to("cuda")
        lose_inputs  = tokenizer(batch["prompt"], batch["lose"],
                                 truncation=True,
                                 padding="longest",
                                 return_tensors="pt").to("cuda")

        # ---- log probs under both models ----
        lp_ref_win   = seq_logprob(reference, win_inputs)          # frozen
        lp_ref_lose  = seq_logprob(reference, lose_inputs)

        lp_pol_win   = seq_logprob(policy, win_inputs)            # trainable
        lp_pol_lose  = seq_logprob(policy, lose_inputs)

        # ---- implicit rewards ----
        r_win   = beta * (lp_pol_win   - lp_ref_win)
        r_lose  = beta * (lp_pol_lose  - lp_ref_lose)

        # ---- DPO binary cross entropy loss ----
        loss = -F.logsigmoid(r_win - r_lose).mean()   # Eq.(1)

        optimizer.zero_grad()
        loss.backward()
        optimizer.step()

    print(f"Epoch {epoch} | loss {loss.item():.4f}")
```

### Key implementation notes  

1. **Why two forward passes per example?** We need both policies’ probabilities on win and lose completions; they cannot be reused because we want separate gradients only for `policy`.  
2. **Numerical stability:** Using `log_softmax` avoids underflow when computing long sequence probabilities.  
3. **Batching tip:** Concatenating prompt + completion before tokenisation lets us reuse attention caches if you enable FlashAttention or GPTQ‐style caching later on.  
4. **Gradient flow:** The block around `reference` uses `torch.no_grad()` automatically because we never call `.backward()` on its outputs—this saves memory.

## 5. Tuning the KL Strength ‑ β  

The scalar β trades off reward maximisation against staying near `π_ref`. Think of β as “how far are we allowed to wander?”

| β value | Behaviour |
|--------|------------|
| **Very small (< 0.05)** | Policy stays almost identical to reference; improvements are slow but stable → good for high‑stakes safety domains where drift is unacceptable. |
| **Moderate (≈ 0.1–0.5)** | Good balance – many papers including the original DPO experiments used β=0.1 or β=0.5 for models up to 6 B parameters.| 
| **Large (> 1)** | Aggressive updates; you may achieve higher reward but KL explodes quickly → risk of mode collapse or “reward hacking”. |

### Practical tuning workflow  

1️⃣ **Pick a target KL budget** – e.g., average per-token KL ≤ 3 nats matches typical PPO settings in the literature.`seq_KL = (lp_pol - lp_ref).mean()` can be logged each step.

2️⃣ **Run short grid search** over `[0.05, 0.1, 0.5]`. Plot reward vs KL on validation set; pick the curve that dominates others (the “Pareto frontier”). The authors found β=0 .05–0 .5 gave clean frontiers across tasks.

3️⃣ **Fine‐tune around promising β** – once you see stable training it’s cheap to add ±20 % around that value.

4️⃣ **Early stopping rule:** Stop when validation win rate plateaus *and* average KL starts creeping above your budget.

## 6. Debugging & Monitoring  

### Metrics to watch each epoch  

| Metric | How to compute | Why it matters |
|--------|-----------------|----------------|
| **DPO loss** (`-logsigmoid`) | already printed | sanity check that loss decreases |
| **Avg KL** (`(lp_pol - lp_ref).mean()`) | custom after each batch | ensures your β works as intended |
| **Reward proxy** | run an external classifier / GPT‑4 scorer on sampled generations | sanity check that preferences are being honoured |
| **Win rate on held‑out prefs** | Compare pairwise predictions using Eq.(1) ➜ proportion where model assigns higher implicit reward to wins | direct measure of preference alignment |
| **Sample quality** | Generate a few prompts at test time and inspect manually | catches pathological degeneration early |

Use TensorBoard or Weights & Biases:

```python
writer.add_scalar("loss", loss.item(), global_step)
writer.add_scalar("kl", kl.item(), global_step)
writer.add_scalar("val_win_rate", val_rate, epoch)
```

### Common pitfalls & fixes  

- **Naïve probability ratio without weighting:** If you drop the sigmoid weighting term (`σ(...)`) or use just `(lp_pol_win - lp_pol_lose)` you get *unlikelihood* training that can collapse diversity—exactly what Fig 8 of the paper flagged as degenerate.
- **Mismatched tokenizers between ref & policy:** Ensure both models share exactly the same tokenizer instance; otherwise logged probabilities are incomparable.
- **Running out of GPU memory:** For long prompts consider truncating preferentially at max length or moving one of the forward passes (`reference`) onto CPU if you’re okay with slower throughput.
- **Zero KL but no improvement:** Means β too low – increase it gradually until you see a non‑trivial KL rise coupled with higher win rate.
- **Reward over‑optimization:** At very high β you may start overfitting specific preference pairs (“reward hacking”). Inspect generated texts—look for repetitions or overly generic content—and reduce β if needed.

## 7️⃣ End‑to‑End Checklist  

Before launching full training:

1️⃣ Prepare preference data (`prompt`, `win`, `lose`). Verify at least a few hundred examples per task—you can start small (~5 k) for debugging before scaling up (~100 k).  
2️⃣ Freeze a decent SFT checkpoint as your reference; if none exists fine‑tune one on just wins (`Preferred‑FT`).  
3️⃣ Set up reproducibility: fix random seeds (`torch.manual_seed`, Python’s `random`, NumPy), enable deterministic cudnn if needed (`torch.backends.cudnn.deterministic=True`).  
4️⃣ Choose an initial β (e.g., 0.1) and learning rate (~5e−6 works well for GPT‑2‐large). Consider gradient clipping (`torch.nn.utils.clip_grad_norm_(policy.parameters(), max_norm=1.`)).  
5️⃣ Run one epoch on a tiny subset; print out loss + avg KL + win rate—if loss goes down but KL stays ~0 check whether your reference logits are accidentally being fed into grad mode!  
6️⃣ Scale up epoch count & batch size; monitor trends with Dashboard. Save checkpoints every few epochs so you can roll back if validation performance drops suddenly.

---

## 8️⃣ Scaling Up – What Happens When You Go Bigger?  

The original DPO experiments ranged from GPT‑2‐large (~800 M) up to LLaMA‐like models (~6 B). The algorithm itself remains unchanged:

* No extra memory overhead beyond storing two parallel forward passes per example.
* Training time roughly doubles compared to standard supervised fine‐tuning because of those extra passes—a modest cost relative to PPO’s many sampling steps.
* The KL penalty continues to behave similarly across scales; larger models may require slightly larger β values (the authors reported good results with β≈0 .5 at 6 B).

If you plan to fine-tune >10 B parameters consider mixed precision (`torch.cuda.autocast`) and gradient checkpointing (`model.gradient_checkpointing_enable()`); both are compatible with DPO because we never need second‐order gradients.

## 9️⃣ TL;DR – Quick Reference Code Snippet

```python
# Assume:
#   policy      -> trainable LM copy of ref
#   reference   -> frozen SFT LM 
#   beta        -> strength hyperparameter

def dpo_step(batch):
    # tokenize prompt+win / prompt+lose jointly
    win_inp   = tokenizer(batch["prompt"], batch["win"],
                          truncation=True,
                          padding="longest",
                          return_tensors="pt").to(device)
    lose_inp  = tokenizer(batch["prompt"], batch["lose"],
                          truncation=True,
                          padding="longest",
                          return_tensors="pt").to(device)

    # Log-probabilities under both models
    lp_r_win   = seq_logprob(reference , win_inp )
    lp_r_lose  = seq_logprob(reference , lose_inp)
    lp_p_win   = seq_logprob(policy     , win_inp )
    lp_p_lose  = seq_logprob(policy     , lose_inp)

    # Implicit rewards per Eq.(1)
    r_win   = beta * (lp_p_win - lp_r_win)
    r_lose  = beta * (lp_p_lose - lp_r_lose)

    # Binary cross entropy surrogate loss
    loss = -F.logsigmoid(r_win - r_lose).mean()

    optimizer.zero_grad()
    loss.backward()
    optimizer.step()
    return loss.item()
```

Plug this into any training loop – that’s essentially all there is!

## 🎉 Wrap Up

Direct Preference Optimization shows that aligning large language models can be reduced to *just another supervised learning problem*: compute two sets of log-probabilities and apply a logistic cross‑entropy loss weighted by β. By avoiding separate reward modeling and costly PPO rollouts you gain:

* Faster iteration cycles (no sampling loop during training).  
* Fewer moving parts → far more stable convergence curves—as demonstrated by the clean frontiers presented in the original paper’s Figure 1a/b.
* A clear analytical link between preferences and policy updates thanks to Eq.(1).

Give it a try on your own task—whether it’s sentiment steering, summarization refinement or single-turn dialogue—by following this guide step by step. If anything feels off during training, first check your KL numbers and make sure your reference probabilities are truly frozen; most bugs trace back there.

Happy aligning! 🚀
