\title{Blogs about the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

# Scaling Without Tokens: How BLT Matches Llama 3 at 8 B Parameters  

*An analysis of the flop‑controlled scaling experiments that demonstrate parity with token‑based LLMs while cutting inference cost by up to 50 %.*  

---  

## Why look beyond tokens?  

Almost every large language model today still relies on a **tokenizer** – a heuristic pre‑processor that groups raw bytes into a fixed vocabulary before any learning happens.  
The tokenizer introduces several inefficiencies:

* Every token receives the same amount of computation, even though predicting a space is far easier than predicting the first character of a new word.  
* A larger vocabulary improves compression **but** forces a bigger embedding table and output projection, limiting how much we can change token length without paying extra memory cost.  
* Tokenizers are brittle to noisy input (misspellings, corrupted bytes) and can bias multilingual performance because different scripts are split unevenly.

The **Byte Latent Transformer (BLT)** removes this static vocabulary completely. Instead of tokens it works directly on **bytes**, grouping them into *patches* whose length is decided dynamically by the model itself. The result is an architecture that can allocate compute precisely where it’s needed—and crucially, one that can be scaled while keeping the inference budget fixed.



## Training‑side parity: matching Llama 3 flops‑for‑flops  

### The experiment  

* Models were trained on the same raw byte corpus used for Llama 3 (≈2 trillion tokens ≈ 4 trillion bytes).  
* Four sizes were considered – from **1 B** up to **8 B** parameters – each paired with an *optimal* number of training FLOPs as prescribed by the Chinchilla/Llama 3 scaling law (the “compute‑optimal” regime).  
* For every BPE baseline a **BLT** counterpart was built that has an identical **global latent transformer** (§ Architecture) and comparable local encoder/decoder capacities. The only difference is how input is chunked (static BPE tokens vs dynamic byte patches).

### What was measured?  

* **Bits‑per‑byte (BPB)** – the tokenizer‑independent analogue of perplexity – served as the language‑modeling metric.
* Total **training FLOPs** were counted exactly according to the standard transformer FLOP formulae (feed‑forward + attention), plus the cheap cross‑attention layers used by BLT’s encoder/decoder.
* The *training curve* therefore plots BPB versus cumulative FLOPs for each model size.

### Findings  

| Model family | Parameter range | Training FLOPs vs BPB |
|--------------|----------------|-----------------------|
| Llama 3 BPE | 1 – 8 B | Consistent decrease in BPB as FLOPs increase |
| **BLT** | **1 – 8 B** | **Matches or slightly outperforms** BPE curve across all sizes |

In other words, despite never seeing a token dictionary, **BLT reaches the same predictive quality as Llama 3 when given the same amount of training computation**. This is the first time a pure byte‐level Transformer has closed the gap in a *flop‑controlled* setting.



## Inference efficiency: saving up to half the FLOPs  

### Patches versus tokens  

During generation each step of a traditional Transformer processes one **token** → one forward pass through the whole network.  
BLT processes one **patch**, which may contain many bytes:

\[
\text{average patch size}= \frac{\text{#bytes}}{\text{#patches}}
\]

Because the expensive *global latent transformer* runs only when a new patch starts, larger patches directly reduce its invocation frequency. The paper reports that an average patch length of **8 bytes** cuts inference FLOPs by **≈ 50 %** compared with a typical Llama 3 token (~4 bytes).

### Fixed‑inference scaling study  

To test whether we can *grow* the model while keeping this cheaper inference budget constant:

1. Start from two baseline configs (~0.4 B and ~3.6 B parameters) using the standard Llama 2 tokenizer.
2. Build flop‑equivalent **BLT–Entropy** models whose *average* patch lengths are **6 bytes** and **8 bytes**, respectively.
3. Train each family under increasing total FLOP budgets (≈ 0×, 2×, 5× … times the compute‑optimal amount).
4. Measure downstream accuracy after each budget point (MMLU, HellaSwag etc.).

The resulting curves show two clear phenomena:

* For *low* training budgets, conventional BPE models still hold an advantage—simply because they already have more capacity per step.
* As soon as we exceed roughly **2–2.5×** the compute‐optimal budget, **BLT overtakes** its BPE counterpart *and continues rising more steeply*.  
* The larger‐patch (**8 bytes**) variant crosses over even earlier and maintains its lead throughout higher budgets.

Thus **the saved inference FLOPs from longer patches can be reallocated to deepen/widen the global transformer**, giving us strictly better performance under exactly the same deployment constraints.



## Growing both model *and* patch size – a new scaling axis  

### Why tokenizers block this move  

With subword vocabularies there is an inherent trade‑off:

\[
\text{Longer tokens} \;\Rightarrow\; \text{fewer steps} \;\but\;
\text{larger embedding / output matrix}
\]

Increasing vocabulary size inflates memory proportionally (`|V| × hidden_dim`), making it unattractive once you hit several hundred thousand entries (Llama 3 uses ≈128k tokens).

### Patches have no hard limit  

A *patch* is simply “a contiguous run of bytes” defined on‑the‑fly by an entropy threshold:

\[
H(x_t)= -\!\!\sum_{v\in\mathcal V} p_e(v\,|\,x_{<t})\log p_e(v\,|\,x_{<t}) ,
\qquad
\text{newPatch}(t)=
\begin{cases}
H(x_t)>\theta_g \\[-2pt]
\text{or } H(x_t)-H(x_{t-1})>\theta_r .
\end{cases}
\]

No matter how long a patch becomes there is no extra entry added to an embedding table—the encoder just pools byte embeddings via lightweight cross‑attention (§ Encoder). Consequently:

* We can safely push `average patch size` from ~4 bytes (entropy‐based) up to ≥ 8 bytes without blowing up memory.
* Each extra byte absorbed into an existing patch costs essentially nothing beyond cheap local encoding/decoding.
* The saved global‐transformer steps are then spent expanding its depth (`l_𝒢`) or width (`h_𝒢`). Experiments report roughly a **20× increase in global parameters** while only doubling the local encoder/decoder weights when moving from 0.4 B → 8 B total parameters—showcasing how most extra capacity lands where it matters most (the latent transformer).

The practical outcome is evident in Figure … of the paper: at **7–8 B parameters**, BLT models using an average *patch size = 8 bytes* surpass tokenized baselines even though they started slightly behind at lower scales.



## Putting it all together  

| Aspect | Tokenizer‐based LLMs | Byte Latent Transformer |
|--------|---------------------|--------------------------|
| **Training front** | Same FLOP budget → comparable BPB only after ≈2× optimal steps | Same FLOP budget → identical or better BPB across all scales |
| **Inference cost** | Fixed per token → limited ability to reduce FLOPs | Inverse relation `FLOPs ∝ 1 / averagePatchSize`; up to ≈50 % reduction |
| **Scalability axis** | Only parameter count & data volume | Parameter count + *patch length*, unconstrained by vocab size |
| **Robustness side effects** | Sensitive to misspellings/noise | Direct byte access improves character‐level tasks & low‑resource languages |

The experiments demonstrate that removing the tokenizer does not force us into an efficiency cliff—it actually opens up a clear path toward *cheaper inference without sacrificing—and sometimes improving—accuracy.*



## Takeaway & Outlook  

The Byte Latent Transformer proves that “tokenless” does not mean “inferior”. By letting next‑byte entropy dictate where computation should happen, BLT attains:

1️⃣ **Training parity** with state‑of‑the‑art tokenized models at up to **8 B parameters** under identical FLOP budgets.  
2️⃣ Up to **50 % fewer inference FLOPs**, thanks to longer dynamic patches.  
3️⃣ A genuine new degree of freedom—**growing both model capacity *and* average patch length simultaneously**, something impossible under fixed vocabularies.

Future work could tighten these gains further by learning the patching function end‑to‑end (instead of precomputing entropies) or by initializing BLT’s global transformer from pre‑trained tokenizers (“byte‑ifying” existing models). Either direction would make large language modeling both more efficient *and* more robust—all without ever writing another line of tokenizer code again.

The codebase powering these results is openly available at <https://github.com/facebookresearch/blt>. Feel free to clone, experiment with your own entropy thresholds, or try out larger patches on your preferred hardware—there’s plenty of room left on this byte‐level frontier!
