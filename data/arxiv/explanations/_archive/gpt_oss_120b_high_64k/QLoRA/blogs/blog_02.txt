# Inside NF4 and Double Quantization: The Technical Magic Behind QLoRA’s Memory Savings  

Large language models (LLMs) have become the workhorse of modern NLP, but their sheer size makes fine‑tuning a nightmare on ordinary hardware. QLoRA cracks this problem wide open by **quantizing** a frozen pretrained model to 4 bits while still allowing gradients to flow through it into tiny LoRA adapters. Two clever tricks make this possible:  

1. **NormalFloat (NF4)** – a 4‑bit data type that is information‑theoretically optimal for the *normally distributed* weights that LLMs naturally exhibit.  
2. **Double Quantization** – a second‑level compression that shaves the scaling constants (the “quantization constants”) down to just a few bits.  

In this post we unpack the intuition, math, and empirical payoff of each innovation. By the end you’ll see why these seemingly tiny engineering details translate into **gigabytes** of saved GPU memory without any loss in downstream performance.

---

## 1. Why 4‑bit Quantization Needs Careful Design  

Standard block‑wise k‑bit quantization works by splitting a weight tensor into small blocks (often 64 elements) and representing each block with two pieces of data:

* **Quantized values** – stored with *k* bits per element (here k = 4).  
* **Scaling constant** *c* – the factor that maps the integer code back to floating point during de‑quantisation.

The forward pass simply does  

\[
\mathbf{W}^{\text{FP16}} \;\approx\; \frac{\mathbf{W}^{\text{int}_k}}{c},
\]

and back‑propagation uses the de‑quantised float matrix while only updating LoRA parameters.

If we naïvely choose the integer representation (e.g., unsigned Int4 or IEEE Float4), we waste bits on values that rarely appear in LLM weights—especially outliers—because those distributions are far from uniform. This is where **NF4** shines.

---

## 2. NormalFloat (NF4): Matching the Weight Distribution  

### 2.1 The Core Insight  
Empirically, pretrained transformer weights are *zero‑centered* and closely follow a normal distribution \(\mathcal{N}(0,\sigma^2)\). In such a case an *information‐theoretic* optimum is to allocate equal probability mass to each quantization bin—exactly what **quantile quantisation** does.

Intuitively:

* If each bin contains roughly the same number of values, we use every bit pattern efficiently.
* The bin boundaries are placed where the underlying density changes little, minimizing average distortion.

### 2.2 Constructing NFk (k = 4)  

1. **Compute theoretical quantiles** of a standard normal \(N(0,1)\).  
   For a k‑bit code we need \(2^k+1\) breakpoints \(\{q_i\}\), where  

   \[
   q_i = Q_X\!\left(\frac{i}{2^k+1}\right), \qquad i = 0,\dots ,2^k,
   \]

   and \(Q_X(\cdot)\) is the normal quantile function.
2. **Create symmetric bin centers** by averaging consecutive quantiles:

   \[
   v_i = \frac{1}{2}\!\Bigl(Q_X\!\bigl(\tfrac{i}{2^k+1}\bigr) + Q_X\!\bigl(\tfrac{i+1}{2^k+1}\bigr)\Bigr), \quad i=0,\dots ,2^k-1.
   \]

3. **Force an exact zero representation** – because many tensors contain padding or bias terms that are exactly zero, we need one codeword to map precisely onto zero. We therefore split the positive/negative halves asymmetrically (using \(2^{k-1}\) negative codes and \(2^{k-1}+1\) positive codes) and drop one duplicate zero entry.
4. **Normalize into \([-1,1]\)** – both the weight block and the codebook are linearly scaled so their ranges match before clipping/clamping to the nearest code.

All together this yields **k‑bit NormalFloat (NFk)**; for our setting \(k=4\), giving us **NF4** with sixteen well‑placed levels that mirror a Gaussian PDF.

### 2.3 Why NF4 Beats Float‑Int Quantisation  

| Data type | Average distortion on Gaussian data | Empirical perplexity (LLaMA family) |
|-----------|------------------------------------|--------------------------------------|
| Int8 (8 bits) | Baseline | — |
| FP8 (8 bits) | Slightly higher | — |
| **Int4 / Float4** | ≈ 2× worse than NF4 | Higher PPL |
| **NF4** | Minimal – matches theoretical optimum | Lowest PPL among all 4‑bit variants |

The paper reports *significant* gains over both Int4 and Float4 across many models (OPT, BLOOM, Pythia, LLaMA), confirming that aligning quantisation bins with the weight histogram pays off in practice—not just theory.

## 3. Double Quantization: Squeezing Out Scaling Overhead  

### 3.1 The Hidden Cost of Scaling Constants  

A typical block size of 64 elements means each block needs its own scaling constant *c*. If we store *c* as a full‑precision float32 we incur an extra  

\[
\frac{32\,\text{bits}}{64}=0.5~\text{bits per weight}
\]

—roughly **3 GB** for a 65B‑parameter model! That overhead dwarfs even our compact NF4 representation.

### 3.2 Two‑Stage Compression  

Double Quantization treats these *c* values as another tensor to be quantised:

1. **First level:** Original weights → NF4 + float32 scaling constants *c₂*.  
2. **Second level:** Quantise each *c₂* itself using an **8‑bit float** format (FP8) with a larger block size (e.g., 256). Because scaling constants are always non‑negative we subtract their mean first so they become centred around zero—allowing symmetric FP8 bins.
3. Store both:
   * The FP8 codes for *c₂*.  
   * A “meta” scaling factor *c₁* (still float32) that rescales groups of FP8 entries back to real values.

Mathematically,

\[
c_{{\text{real}}} = c_1^{\text{FP32}} \times c_2^{\text{FP8}},
\]

where \(c_2^{\text{FP8}}\) is obtained via dequantisation from its stored codebook.

### 3.3 Memory Savings in Numbers  

For a blocksize of 64:

* Original overhead: \(0.5~\text{bits/param}\).  
* After double quantisation:
  
  \[
  \underbrace{\frac{8\,\text{bits}}{64}}_{0.125}
   + 
   \underbrace{\frac{32\,\text{bits}}{64\times256}}_{0.002}
   \;\approx\;0.127~\text{bits/param}.
  \]

That’s a reduction of **≈ 0.37 bits per parameter**, translating into ~3 GB saved on a 65B model—a decisive margin when your GPU only has 48 GB of RAM left for everything else.

Crucially—empirically—the authors observed *no degradation* in downstream tasks (Vicuna benchmark scores remain unchanged), confirming that FP8 resolution is more than sufficient for scaling constants.

---

## 4. Putting It All Together: QLoRA’s End‑to‑End Pipeline  

When fine‑tuning an LLM with QLoRA:

1️⃣ Load the pretrained checkpoint → apply **NF4** blockwise quantisation (blocksize = 64).  
2️⃣ For each weight block store its NF4 codes plus **double‑quantised scaling constants** (FP8 + meta‐scale).  
3️⃣ Insert LoRA adapters at *every* linear layer (the memory cost here is negligible compared to activations).  
4️⃣ During forward/backward passes:
   * De‑quantise on-the-fly from NF4 → BF16 using both levels of scalars.
   * Compute gradients only w.r.t LoRA parameters; base weights stay frozen.
5️⃣ Optimiser state tensors are kept in NVIDIA’s unified memory via **paged optimisers**, eliminating occasional OOM spikes caused by gradient checkpointing on long sequences.

The result? A single GPU can fine‑tune a **65 billion parameter model** within <48 GB while achieving *identical* performance to full ‑16‑bit fine‑tuning—something previously requiring >780 GB!

## 5. Empirical Impact Across Model Scales  

| Model | Bits used after QLoRA | GPU RAM needed | Vicuna relative score vs ChatGPT |
|-------|-----------------------|----------------|-----------------------------------|
| LLaMA 7B | NF4 (+ DQ) | ~5 GB | ≈ 97% |
| LLaMA 33B | NF4 (+ DQ) | ~21 GB | ≈ 98% |
| LLaMA 65B | NF4 (+ DQ) | ~48 GB | ≈ 99% |

Across >1,000 experiments covering sizes from 80M up to 65B parameters, QLoRA **consistently reproduces full‑precision results**, confirming that:

* The *information loss* introduced by NF4 is fully recovered by LoRA adapters.
* Double Quantisation’s compression does not harm convergence or final quality.
* Memory savings scale linearly—larger models benefit even more because scaling constants dominate their storage cost at higher dimensions.

## 6️⃣ Takeaways & Future Directions  

* **Data‑aware quantisation beats naïve fixed bins** – aligning bit patterns with Gaussian weight statistics yields maximal utilisation of each codeword.
* **Double Quantisation shows how “meta” compression can unlock otherwise hidden savings** – once you compress the compressors you shave off enough space to fit massive models on modest hardware.
* The combination enables researchers without multi‑GPU clusters to experiment with instruction tuning at scales previously inaccessible.
* Open questions remain:
  - Could we push beyond four bits? Preliminary work suggests three‑bit base models plus LoRA might still recover quality.
  - Are there alternative PEFT methods (e.g., IA³ or prompt tuning) that synergise even better with NFk?
  - How does NFk behave for non‑Gaussian weight distributions such as those after heavy regularisation or pruning?

The answer may reshape how we think about “training large” models: perhaps it’s not about throwing ever more GPUs at full precision matrices but rather about smarter numeric encodings coupled with lightweight adapters—just like QLoRA demonstrates today.

--- 

**TL;DR:** By tailoring the four‐bit representation to match the Gaussian shape of LLM weights (**NF₄**) and compressing per‐block scaling factors through a second layer (**Double Quantisation**), QLoRA trims >0.35 bits per parameter—a multi‐gigabyte saving—while preserving every ounce of downstream accuracy. This technical wizardry turns “fine‑tune a trillion‐parameter beast” from an exclusive corporate privilege into something anyone with a single modern GPU can attempt.
