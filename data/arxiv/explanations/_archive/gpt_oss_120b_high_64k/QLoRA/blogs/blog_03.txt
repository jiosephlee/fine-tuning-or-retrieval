# Paged Optimizers Explained: Tackling Gradient Checkpointing Spikes in Large‑Scale Fine‑tuning  

Fine‑tuning today’s massive language models pushes the limits of every GPU on the market. Even after compressing a 65 billion‑parameter model down to 4 bits per weight (the **NF4** format introduced by QLoRA), training can still run out of memory because **gradient checkpointing** creates short-lived “memory peaks.”  
QLoRA solves this problem with a surprisingly simple trick: *Paged Optimizers*. By letting CUDA’s **Unified Memory** automatically swap optimizer states between GPU VRAM and system RAM, QLoRA keeps those spikes under control without sacrificing speed.  

In this post we walk through why those spikes happen, how traditional solutions try (and often fail) to handle them, and exactly how QLoRA’s paged optimizers make single‑GPU fine‑tuning of gigantic models possible.

---

## Why Gradient Checkpointing Still Causes Memory Spikes  

When you train a transformer you typically need three kinds of data living at once:

| Item | Typical Size | Where it lives |
|------|--------------|----------------|
| **Model weights** | Hundreds of gigabytes (full precision) | GPU VRAM |
| **Activation buffers** | Proportional to batch × sequence length | GPU VRAM |
| **Optimizer state** (e.g., Adam’s momentum & variance) | ≈ 2 × number of parameters × 4 bytes | GPU VRAM |

Storing *all* activations throughout the forward pass would blow up VRAM even for a 7 B model. **Gradient checkpointing** alleviates this by discarding most intermediate tensors and recomputing them later during back‑propagation. The trade‑off looks clean—less static memory—but it introduces **transient peaks**:

1️⃣ The forward pass finishes → activations are freed.  
2️⃣ The backward pass starts → previously discarded layers are *recomputed* while gradients from earlier layers are still alive.  
3️⃣ Right before an optimiser step runs, both **recomputed activations** *and* **optimizer moments** coexist in VRAM.

For long sequences or larger batch sizes these temporary allocations can easily exceed the available device memory—even if your base model fits comfortably after quantisation.  

---

## A Quick Primer on NVIDIA Unified Memory  

CUDA’s *Unified Memory* creates a single virtual address space shared between CPU RAM and GPU VRAM. From the programmer’s point of view you allocate a tensor once (`managed` allocation) and let the driver decide where it lives at any moment:

* If a kernel needs a page that currently resides in main memory, the driver **page‑faults** into VRAM over PCIe automatically.  
* When VRAM becomes scarce, rarely accessed pages are evicted back to RAM without any explicit copy call from your code.

Think of it as “swap” for GPUs—exactly what operating systems have been doing for CPUs forever—but tightly integrated into the hardware scheduler so latency stays low enough for high‑performance workloads.

---

## How QLoRA Turns the Optimiser into a “Paged” Object  

The idea behind *Paged Optimizers* is straightforward: store all **optimizer moments** (Adam’s `m` and `v`, or any other auxiliary buffers) in *managed* CUDA memory instead of permanent device memory. Here’s what happens step‑by‑step during a typical iteration:

1️⃣ **Initial allocation** – When constructing the optimiser QLoRA requests managed tensors:
```python
# pseudo‑code illustrating the idea
optim = torch.optim.AdamW(model.parameters(), lr=5e-5)
optim = qlora.PagedOptimizer(optim)   # wraps moments into managed memory
```
   Under the hood each moment tensor is created with `torch.cuda.memory_managed()` (`torch.empty(..., device='cuda', pin_memory=False)` plus a flag), which tells CUDA “this buffer may migrate”.

2️⃣ **Forward pass** – Only the forward computation touches dequantised weights (`BF16`). No optimiser state is required yet, so all managed buffers stay dormant in RAM.

3️⃣ **Backward pass & checkpoint recompute** – As soon as a layer’s gradients become available CUDA checks whether there is enough free VRAM:
   * If needed, portions of the optimiser moments are **paged out** automatically onto host RAM.
   * The recomputed activations occupy VRAM temporarily without exceeding capacity because some optimiser pages have already been displaced.

4️⃣ **Optimizer step** – Right before updating parameters PyTorch issues reads/writes over every moment tensor:
   * CUDA detects that these pages live in host RAM → it **pages them back** into VRAM.
   * Because an optimiser step touches every parameter once linearly, paging incurs essentially one bulk transfer per iteration—a cost that is dwarfed by the matrix multiplications themselves.

5️⃣ **Repeat** – After applying updates all moments go back into managed storage, ready for the next iteration’s potential page‑outs again.


### What Makes This Work Remotely Better Than Manual Offloading?

| Approach | Code complexity | Multi‑GPU support | Overhead pattern |
|----------|-----------------|-------------------|------------------|
| Manual `.to('cpu') / .to('cuda')` offload | High (explicit bookkeeping) | Needs custom collective ops | Variable spikes each time you flip |
| DeepSpeed ZeRO Stage 3 | High (process groups & partitioning) | Designed for many GPUs | Communication cost dominates |
| **QLoRA Paged Optimizer** | Minimal wrapper around any existing optimiser | Single‑GPU focused (no inter‑node sync) | One bulk copy per iteration → negligible |

In short: by relying on a feature already baked into modern CUDA drivers you avoid reinventing complex sharding mechanisms while still gaining protection against OOM crashes on a single consumer/professional card.

## Real‑World Impact – Training “Guanaco” on One GPU  

The authors released a family of instruction-tuned chatbots called **Guanaco**, ranging from 7 B up through 65 B parameters. Training details illustrate why paged optimizers matter:

* **Memory budget:** < 48 GB VRAM thanks to NF4 weight storage + double quantisation (`c₂` constants compressed from 0.5 bits/param → ≈ 0​.​127 bits/param).  
* **Batch size:** A modest batch size of 1–16 was used depending on model scale; nonetheless long prompt sequences (> 1024 tokens) triggered checkpoint recompute spikes that would have exceeded available VRAM without paging.
* **Throughput:** For LLaMA‑65B (`batch_size=16`) benchmark runs showed *no measurable slowdown*: training speed matched that of an identical configuration using regular (non‑paged) AdamW because paging only occurs during short update windows.
* **Result:** The largest Guanaco‐65B model reached **99.3 %** of ChatGPT performance on Vicuna while being fine‑tuned in ≈ 24 hours on a single RTX A6000 (48 GB). Without paged optimisers the job would have crashed repeatedly under identical hyperparameters.



---

## How Much Host RAM Do You Need?

Even though optimiser moments live mainly in system RAM most of their data fits comfortably thanks to two tricks introduced alongside paging:

1️⃣ **Double Quantisation** compresses per‑block scaling factors from 32 bits → FP8 (`c₂`) then applies another tiny blockwise quantisation (`c₁`). This saves roughly $0.\!127$ bits per parameter instead of $0.\!5$ bits—a reduction equivalent to ~3 GB for a 65 B model.
2️⃣ Only adapter parameters (**LoRA**) receive gradient updates; base‐model weights remain frozen after dequantisation, so their own Adam moments are never allocated at all.

Consequently ‑–a typical server equipped with ≥ 256 GB DDR4 will comfortably host all required moment buffers even for the biggest public LLMs supported by QLoRA.

## Quick Checklist if You Want To Try Paged Optimisers

| ✅ Item | Why It Matters |
|------|----------------|
| Use a recent CUDA driver (> 11.x) that fully supports Managed Memory page faulting.| Older drivers may fall back to synchronous copies causing stalls or OOMs.| 
| Allocate your optimiser through `qlora.PagedOptimizer` (or set `optim="paged_adam"` if using 🤗 Transformers Trainer).| Guarantees moments live in managed space.| 
| Enable `gradient_checkpointing=True` in your trainer config.| Without checkpointing you’ll already be at peak usage even before paging helps.| 
| Keep an eye on host RAM utilisation (`htop`, Windows Task Manager).| Managed tensors reside permanently in host RAM—even if they’re idle.| 
| Test with short sequences first before scaling up.| Guarantees your pipeline works before hitting edge cases.|

That’s essentially all you need—no exotic distributed setup nor custom kernel modifications.

## Limitations & Open Questions  

While paged optimisers dramatically increase robustness, they aren’t a silver bullet:

* **Latency spikes:** If your workload performs many tiny optimiser steps (e.g., micro-batching), frequent page‐ins could become noticeable because each step forces another roundtrip over PCIe.
* **Hardware dependence:** Unified Memory works best on recent NVIDIA GPUs that support full *on-demand page migration*. Older cards may fall back to slower software faults.
* **Memory pressure on CPU:** Very large models (>100 B) would push host requirements into multiple terabytes—a scenario where additional techniques such as hierarchical paging or swap-to-disk become necessary.
* **Multi‑GPU extensions:** Uniﬁed Memory currently stays within one physical device context; extending this idea across several GPUs would require coordinated paging strategies or adopting ZeRO‐style sharding alongside our approach.



---

## Takeaways  

1️⃣ Gradient checkpointing saves static activation memory but introduces brief peaks where recomputed tensors coexist with optimiser moments—a common cause of OOM failures at scale.  
2️⃣ QLoRA solves this by placing ALL optimiser state into CUDA’s *managed* memory pool so pages can be evicted automatically whenever VRAM runs low—a technique dubbed **Paged Optimizer**.  
3️⃣ The method needs only a lightweight wrapper around ordinary PyTorch optimisers; no extra software stacks nor multi‑GPU orchestration are required.  
4️⃣ Empirically it lets researchers fine‑tune LLaMA‑65B on a single RTX™ A6000 (48 GB) without slowing down training—the resulting Guanaco models compete head‑to‑head with commercial chatbots such as ChatGPT/GPT‑4 despite being trained solely on open datasets.  

If you’ve ever watched your notebook crash midway through an epoch because “CUDA out of memory,” give paged optimisers a try—the next generation of large‐scale fine­tuning may simply be a few lines of code away.
