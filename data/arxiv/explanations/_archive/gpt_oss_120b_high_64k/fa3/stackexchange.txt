\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### Why does FlashAttention‑2 achieve only ~35% hardware utilization on H100 GPUs?
Question:
The paper states that FlashAttention‑2 reaches only about 35 % utilization on the Hopper H100 GPU while optimized GEMM kernels achieve 80–90 %. I understood that FlashAttention‑2 already eliminates intermediate global memory writes/reads by fusing all operations into a single kernel. What architectural or algorithmic factors prevent higher occupancy/utilization on H100? Is it mainly due to not using Hopper‑specific Tensor Core instructions, or are there deeper reasons related to the synchronous execution model?
Answer:
`FlashAttention‑2` already removes the *global*‑memory traffic that dominates a naïve attention implementation, but on a Hopper H100 it still reaches only about one third of the peak FLOP rate ($\approx 35\,\%$).  

The shortfall comes from two intertwined sources that are described explicitly in the paper:

1. **The kernel follows a purely synchronous schedule**  
   In the forward pass `FlashAttention‑2` processes a query‑block $Q_i$ by iterating over key/value blocks $(K_j,V_j)$. For each block it first issues an “SS‑GEMM’’  

   $$
   S_i^{(j)} = Q_i K_j^{\!\top},
   $$  

   then waits for that matrix multiply to finish before computing the local softmax $\widetilde P_i^{(j)}=\exp(S_i^{(j)}!-\!m_i)$ and finally launches an “RS‑GEMM’’  

   $$
   O_i \gets O_i + \widetilde P_i^{(j)} V_j .
   $$  

   The algorithm therefore inserts a **hardware barrier after every GEMM** (`wait` statements in Alg.~1). While one threadgroup is busy executing the exponential‑and‑sum part of softmax, all Tensor Cores that could be performing the next multiply sit idle; conversely while a GEMM is running the special‑function unit (SFU) that implements `exp` is starved. Because on an H100 an FP16 tensor‑core can deliver $\approx 989\,\text{TFLOP/s}$ whereas the SFU can sustain only $\approx 3{-}4\,\text{TFLOP/s}$ for exponentials, even a modest amount of unoverlapped softmax work can consume roughly half of the wall‑clock time. The net effect is a cycle‑level underutilisation that shows up as $\sim 35\,\%$ hardware utilisation.

   `FlashAttention‑3` removes this bottleneck by **splitting producer and consumer roles into separate warps**, issuing TMA loads asynchronously, and overlapping the second GEMM of iteration $j$ with the softmax computation for iteration $j+1$ (“ping‑pong’’ scheduling). This two‑stage pipeline hides the low‑throughput special‑function work inside tensor‑core activity and raises utilisation to $\approx 75\,\%$.

2. **The implementation does not exploit Hopper’s new Tensor‑Core instruction set**  
   The original `FlashAttention‑2` kernels were written for Ampere’s HMMA/Tensor Core interface and therefore run on an H100 using older microcode paths (“AMPERE” kernels). Although HMMA still works on Hopper, it does not take advantage of **WGMMA**—the warpgroup‑wide instruction introduced in Hopper that can fetch operands directly from shared memory and launch completely asynchronous matrix multiplies. WGMMA offers a higher issue rate and relaxes layout constraints (the operand layout restrictions described in § 3.3). As noted in § 1 (“Partially, this may be attributed … not using Hopper–specific instructions”), using HMMA instead of WGMMA reduces the effective FLOP throughput per SM by roughly a factor of two compared with an optimised GEMM kernel that does use WGMMA (e.g., cuDNN 9 or ThunkerKitten).

   Moreover, `FlashAttention‑2` treats its data tiles as mn‑major or k‑major without regard for the stricter k‑major requirement imposed by FP8 WGMMAs, so it cannot benefit from FP8 tensor cores either—a loss that becomes noticeable when one looks at peak utilisation numbers derived from FP16 runs alone.

Together these two factors explain why an otherwise “memory‑optimal’’ algorithm still stays at only about $35\,\%$ utilisation on an H100:

* **Synchronous sequencing** forces long idle periods while waiting for softmax or for shared–memory loads;
* **Legacy instruction selection** prevents each active cycle from generating maximum tensor‑core work;
* The relatively small per‑block GEMMs ($B_r\times B_c$) used by `FlashAttention‑2` also limit how many warps can be kept busy once those synchronisation stalls are removed—hence optimised kernels increase both tile size *and* instruction efficiency whereas `FlashAttention‑2` does neither.

The authors verify this diagnosis empirically: when they replace the HMMA calls with Hopper’s WGMMA, introduce producer–consumer warp specialization, and overlap GEMM with softmax (`FlashAttention‑3`), they observe TFLOP/s rising from $\approx 350\,\text{TFLOP/s}$ ($\approx 35\,\%$) up to $\approx 740\,\text{TFLOP/s}$ ($\approx 75\,\%$). In short, `FlashAttention‑2` is limited not simply by its fusion trick but by a combination of **a purely synchronous execution model** and **the lack of Hopper‑specific asynchronous Tensor Core primitives**, both of which prevent it from keeping the massive H100 compute resources fully occupied.

### How does producer‑consumer asynchrony via warp‑specialization work in FlashAttention‑3?
Question:
Section 3 describes a "producer‑consumer" scheme where some warps act as producers (issuing TMA loads) and others act as consumers (performing WGMMA GEMMs). I am confused about how the warps are split, how data movement and computation are synchronized, and what role the circular SMEM buffer plays. Could someone walk through a concrete example of a CTA where warp 0 loads Q tiles while warp 1 computes the first GEMM, highlighting where barriers are placed?
Answer:
**Answer**

In FlashAttention‑3 one CTA works like a tiny “assembly line’’ : a few warps only move data from global memory into shared–memory buffers (the **producers**) while another set of warps immediately starts the matrix multiplications that consume those buffers (the **consumers**).  
The whole scheme is built on three ingredients that already exist on Hopper:

* **TMA** – an async copy unit (Tensor‑Memory‑Accelerator) that can fetch tiles from HBM straight into shared memory without stalling the arithmetic cores.  
* **WGMMA** – a warp‑group‐wide Tensor‑Core instruction that reads its operands directly from shared memory and launches an asynchronous GEMM on the Tensor Cores.  
* A **circular SMEM buffer** of depth $s$ (normally 2 or 3) that lets the two groups work on different slots at the same time.  

Below I walk through a concrete CTA that processes one query block $Q_{i}$ while two warpgroups are present:  

&nbsp;&nbsp;&nbsp;&nbsp;$\,$warpgroup&nbsp;$A$\;(warps&nbsp;$0\!-\!3)=${\bf producer}, $\,$warpgroup&nbsp;$B$\;(warps&nbsp;$4\!-\!7)=${\bf consumer}.  

All “wait’’ statements in Algorithm 1 correspond to **hardware barriers** – either a CP–async fence/​wait pair or a PTX ``bar.sync''.  
The pseudo–code already shows where those barriers are placed; I will annotate them with the low–level operations used on Hopper.



---------------------------------------------------------------------

### 1️⃣ CTA initialisation

```text
// both groups enter the same kernel
if (warpgroup == PRODUCER) {
    // free most registers – only one thread per warp issues the TMA
    setmaxnreg(...);                     // shrink RMEM footprint
} else {                                 // CONSUMER group
    setmaxnreg(...);                     // enlarge RMET footprint for WGMMAs
    Oi $\gets$ 0 ; mi $\gets$ $-\infty$ ; li $\gets$ 0 ;
}
pipeline $\gets$ initialise_circular_buffer(s);
```

*The “pipeline’’ object holds three per–stage flags in shared memory:*  

&nbsp;&nbsp;&nbsp;&nbsp;$\,$`\verb|ready_Q[stage]|`,   `\verb|ready_KV[stage]|` – set by the producer after an async copy finishes.  
&nbsp;&nbsp;&nbsp;&nbsp;$\,$`\verb|free[stage]|`                – set by the consumer after it has finished reading a stage.



---------------------------------------------------------------------

### 2️⃣ Producer loop – issuing TMA loads

```text
// ---- PRODUCER ----
// Load the query tile once (outside the key/value loop)
TMA_load(Q_i) $\rightarrow$ SMEM[stage = 0];          // cp.async_ca ...;
cp.async_fence();                                      // guarantee ordering inside this warpgroup
signal_ready_Q(0);                                     // store flag, visible to all warps

for j = 0 … Tc – 1 {                                   // Tc = $\lceil N/B_c\rceil$ key blocks
    // Wait until slot $(j\bmod s)$ has been freed by the consumer
    while (!free[(j % s)]) __nanosleep();            // implemented as bar.wait

    // Issue async copies of $K_{j}$ and $V_{j}$ into *the same* circular slot.
    TMA_load(K_j) $\rightarrow$ SMEM_K[(j % s)];
     T MA_load(V_j) $\rightarrow$ SMEM_V[(j % s)];
    cp.async_fence();                                 // enforces ordering of these two copies

     signal_ready_KV(j % s);                          // set ready_KV flag for this slot
}
```

#### Key points  

&bull; The *producer* never calls any arithmetic instruction – only one thread per warp invokes an asynchronous copy (`cp.async.ca`).  
&bull; Because CP async works independently of other threads it does **not** stall when another warp starts a GEMM.  
&bull; The circular depth $s$ guarantees that there is always at least one free slot (`free[(j\bmod s)]`). When $s=2$, this gives us a classic “ping–pong’’ double buffer.



---------------------------------------------------------------------

### 3️⃣ Consumer loop – overlapping two WGMMAs per iteration

```text
// ---- CONSUMER ----
// Wait until Q has arrived in slot 0
while (!ready_Q(0)) __nanosleep();
load_Q_from_SMEM(slot = 0);                // now Q lives in registers

for j = 0 … Tc – 1 {
     // ----- step A : SS‑GEMM ($Q\times K_{j}^{\,\top}$) -----
     while (!ready_KV(j % s)) __nanosleep();   // wait for K$_{j}$/V$_{j}$ in this slot

     // Launch first WGMMa asynchronously;
     // operands read directly from SMEM_K[(j % s)].
     wgmma_SS(Q_i_regs , SMEM_K[(j % s)], S_cur);   // no __syncthreads yet

     // ----- step B : RS‑GEMM ($\tilde P_{\, j}\times V_{\, j}$) -----
     // While S_cur is still being reduced by the Tensor Core,
     // we already queue the second multiplication using $\tilde P_{\, j-1}$ computed earlier.
     wgmma_RS(Ptilde_prev , SMEM_V[((j-1)%s)], Oi_regs);

     //-----------------------------------------------------------------
     //-- Explicit synchronization points – these are exactly where --
     //-- “commit / wait’’ statements appear in Algorithm 1          --
     //-----------------------------------------------------------------
     cp.async_wait_all();                    // guarantee both WGMMAs finished

     // Now S_cur is resident in registers → softmax update:
     mi_{\mathrm{old}} $\gets$ mi;
     mi           $\gets$ max(mi_{\mathrm{old}}, rowmax(S_cur));
     Ptilde_{\mathrm{cur}} $\gets$ exp(S_cur - mi);
     li           $\gets$ exp(mi_{\mathrm{old}} - mi)\,*\,li + rowsum(Ptilde_{\mathrm{cur}});

     // Rescale O$_i$ before it will be used again:
     Oi_{\mathrm{regs}} $\gets$
          diag(exp(mi_{\mathrm{old}} - mi))^{-1}\,\cdot\,Oi_{\mathrm{regs}}
          + Ptilde_{\mathrm{cur}}\;\cdot\,SMEM_V[(j % s)];

     // Release this circular slot so the producer may overwrite it:
     free[(j % s)] $\gets true;
}
```

#### Where barriers appear  

| Line in pseudocode                                    | Low‑level barrier                                                                                 |
|-------------------------------------------------------|----------------------------------------------------------------------------------------------------|
| *“wait for $(j\bmod s)$th stage …”*                | spin on `${free[j\bmod s]}` – implemented as a cooperative fence (`bar.wait`)                    |
| *“Commit and wait” after each WGMMa*                | ``cp.async_wait_all()`` + an implicit ``bar.sync`` orchestrated by the pipeline object          |
| *“Release stage”*                                    | store ``$\displaystyle free[j\bmod s]=true$$`` which will be observed by the producer’s next iteration |

Because **WGMMA** itself is asynchronous, we can launch **two** WGMMAs back‑to‑back (`SS` followed immediately by `RS`). Only after both have been queued do we issue one single wait (`cp.async_wait_all`). This single stall hides almost all Tensor‐Core latency while allowing softmax work (`exp`, row‐max, scaling) to run on normal CUDA cores during those cycles.



---------------------------------------------------------------------

### 4️⃣ Whole timeline (one query block)

| Time | Producer warps                              | Consumer warps                                                            |
|------|---------------------------------------------|---------------------------------------------------------------------------|
| $t_{0}$   | Issue TMA($Q_{0}$)\;$\rightarrow$\;slot 0            | idle (waiting for flag)                                                 |
| $t_{1}$   | Flag `\verb|ready_Q(0)|` set                      | sees flag ⇒ loads $Q_{i}$ into registers                                 |
| $t_{2}$   | Issue TMA($K_{0},V_{0})$\;\rightarrow$\;slot 0      | launches **SS‐GEMM** ($Q_{i}\!\times K_{0}^{\,\top}$)                 |
| $t_{3}$   | Issue TMA($K_{1},V_{1})$\;\rightarrow$\;slot 1 *(slot 1 was free)* | while SS‐GEMM runs, queues **RS‐GEMM** using $\tilde P_{\,{-}1}\!\times V_{0}$ |
| $t_{4}$   | …                                           | after both WGMMAs finish (`cp.async_wait_all`) performs softmax update ⇒ produces $\tilde P_{\,0}$      |
| $t_{5}$   | …                                           | launch next SS‐GEMM ($Q_{i}\!\times K_{1}^{\,\top}$) **before** finishing softmax of previous iteration ⇒ pipelining       |
| …         | continues alternating between slots 0/1 …          | continues alternating between SS/RS WGMMAs                              |

Because each group works on different slots of the circular buffer, there is never a write–read hazard: producers only write to a slot whose “free’’ flag has been cleared by consumers, and consumers only read from slots whose “ready’’ flag has been set by producers.



---------------------------------------------------------------------

### 5️⃣ Why this improves utilisation  

On Hopper an H100 Tensor Core can sustain ≈ 989 TFLOP/s FP16 matmul whereas special–function units (exp, max) only deliver ≈ 4 TFLOP/s. In FlashAttention‑2 those cheap operations were serialized with every GEMM, causing ~50 % of cycles to be spent outside Tensor Cores.  

The producer–consumer split decouples them:

+ While one warp group’s Tensor Cores execute an $A\,B^{\,\top}$ multiplication,
+ another warp group’s CUDA cores execute exponential/normalisation,
+ yet another set of warps use TMA to keep feeding fresh tiles.

All three activities occupy disjoint hardware resources, so latency from global‐memory fetches or exponentials gets hidden behind high‑throughput matrix multiply. The double‐buffered circular SMEM eliminates stalls caused by overwriting data still needed by a running GEMM.



---------------------------------------------------------------------

### TL;DR ‑ Core takeaways  

* A CTA is divided into two **warp groups** ― producers issue *asynchronous* TMA copies into a **circular shared–memory buffer**, consumers read those buffers with *asynchronous* WGMMA instructions.  
+ The circular buffer depth $s$ provides double/triple buffering; each slot has three flags (`ready_Q`, `ready_KV`, `free`) realised with lightweight PTX barriers (`bar.wait`, `bar.sync`, `cp.async_fence/wait`).  
+ Within every iteration the consumer launches two WGMMAs back‐to‐back (`SS` then `RS`) without waiting between them; only after both have been queued does it insert one global wait (`cp.async_wait_all`). This creates an overlap between matrix multiply and softmax work (“ping–pong’’ scheduling).  
+ Because memory movement and arithmetic run on separate hardware units concurrently, the kernel reaches ~75 % of H100’s theoretical FP16 throughput versus ~35 % for FlashAttention‑2.

This explains precisely how Warp Specialization implements the producer–consumer asynchrony described in Section 3 and why it gives FlashAttention‑3 its large speedup.

### What is the “s‑stage circular SMEM buffer” used in the algorithm?
Question:
Algorithm 1 mentions initializing a pipeline object to manage barrier synchronization with an "s‑stage circular SMEM buffer". How is this buffer organized across stages, what does the parameter s represent, and how does it enable overlapping loads of K/V tiles with computation? Also, why is a circular buffer preferred over a linear queue in this context?
Answer:
In the forward‑pass kernel of **FlashAttention‑3** the work on a query‑block $\mathbf Q_i$ is split between two warp­groups inside a single CTA:  

* a *producer* warp­group issues the asynchronous Tensor‑Memory‑Accelerator (TMA) copies that bring a key tile $\mathbf K_j$ and the matching value tile $\mathbf V_j$ from global memory into shared memory, and  
* a *consumer* warp­group reads those tiles from shared memory and executes the two WGMMAs (the “SS‑GEMM’’ $\mathbf Q_i\mathbf K_j^{!\top}$ and the “RS‑GEMM’’ $\widetilde{\mathbf P}_i^{(j)}$\,$\mathbf V_j$) together with the soft‐max updates).

The coordination between the two warp‐groups is realised through an **$s$-stage circular SMEM buffer**:

### Organization of the buffer

Shared memory allocated for the CTA is divided into *$s*$ equal slots (or stages).  
Each slot stores one key tile **and** one value tile:

$$
\text{slot}_p = \bigl\{\,\mathbf K_{p},\,\mathbf V_{p}\,\bigr\},
\qquad p = 0,\dots,s-1 .
$$

The size of one slot is exactly the amount of shared memory needed for a
$B_c\times d$ key tile plus a $B_c\times d$ value tile (with $B_c$ the
key‐block size). Consequently the whole buffer occupies $s$
times this size; $s$ cannot exceed what fits in the per‐CTA shared–memory
budget.

### What $s$ means

The integer $s$ is the *pipeline depth*: at any moment up to
$s$ tiles may be “in flight’’—already loaded in SMEM but not yet
consumed by the consumer warp‐group.
When $s=2$ we have ordinary double‐buffering; larger values give a deeper
software pipeline so that more load operations can overlap with more GEMM
operations.

Because TMA copies are asynchronous, after issuing a load into
slot $(j\bmod s)$ the producer does **not** wait for its completion.
Only when all $s$ slots have been filled does it start re‐using slot 0,
hence “circular’’ rather than “linear’’ growth.

### Enabling overlap of K/V loads with computation

Consider iteration $j$. The producer writes $\bf K_j,\bf V_j$
into slot $(j\bmod s)$. As soon as those copies finish it raises a flag
that the consumer watches (`bar.sync`). While the consumer processes
slot $j​$(computes $\mathsf S_i^{(j)}=\mathsf Q_i\,K_j^{!\top}$,
performs softmax, then evaluates $\widetilde{\mathsf P}_i^{(j)}V_j)$,
the producer is already busy loading the next tiles
$\bf K_{j+1},\,V_{j+1}$ into slot $((j+1)\bmod s)$,
and possibly also tiles further ahead if $s>2$

Thus every GEMM execution can be paired with an overlapping TMA load,
hiding most of the DRAM‐to‐SMEM latency behind Tensor‐Core work.
The `bar.sync` instructions guarantee that each consumer reads only after
the corresponding load’s flag has been set, while `release` statements free
the slot for reuse by later producers.

### Why a circular buffer instead of a linear queue?

* **Static allocation:** A CTA can allocate only statically sized shared‐memory
regions. A circular buffer partitions that static region once at kernel launch,
whereas a linear queue would need dynamic head/tail pointers and possibly
shifts or extra bookkeeping each time it reaches the end.
* **Constant‐time addressing:** Indexing a circular buffer requires only a
modulo operation (`idx = j % s`) which maps directly to an offset known at
compile time. No pointer arithmetic or data movement is needed as would be
required when popping from a conventional FIFO.
* **Minimal synchronization overhead:** The pipeline object can embed a simple
binary flag per stage (`ready/consumed`). When an entry leaves stage $p$,
the same flag can be cleared so that the producer may immediately reuse precisely
that same physical SMEM region without any global coordination.
* **Better register usage:** Because every warp‐group knows exactly which slot it
will read/write next (`(j % s)`), no extra registers are needed to keep track of an ever-
growing list of pending tiles—only one counter per warp‐group suffices.
* **Performance:** Reusing the same physical storage avoids any implicit cache line
eviction that could arise from moving data around in a linear queue,
and it matches well with Hopper’s TMA instruction set where source/destination
addresses are specified once per transfer.

In short, the **$s$-stage circular SMEM buffer** is a collection of $s$
fixed‐size shared‐memory slots arranged in a ring.  The parameter $s$
controls how many key/value tiles may reside simultaneously in shared memory,
which directly determines how many load operations can stay ahead of computation.
By letting producers write into one slot while consumers read from another,
the algorithm achieves full overlap between DRAM transfers (via TMA) and Tensor‐Core GEMMs,
and its circular nature makes this pipelining cheap in both control logic and shared‐memory usage.

**Answer**

In *FlashAttention‑3* the “ping‑pong” schedule is nothing more than a two‑stage software pipeline that lets the cheap soft–max work run at the same time as a heavyweight WGMMA (the Hopper‑specific warp–group matrix–multiply–accumulate).

The key ingredients are  

* **two warp–groups** inside each CTA – `\(WG_0\)` and `\(`\(WG_1\)\)` – each specialised either as “producer” (only TMA loads) or “consumer” (only computation);  
* a **circular shared–memory buffer** with *s* slots that is guarded by a single CUDA barrier (`bar.sync`);  
* **asynchronous** WGMMA instructions – they are queued onto the Tensor–Core engine and return control immediately, so a warp can continue issuing other instructions while the MMA is still running;  
* **explicit ordering** points (`bar.arrive`, `bar.wait`) that guarantee that a consumer never reads a buffer slot before the producer has finished writing it, and that no two warp–groups ever try to use the same slot at the same instant.

Below I walk through one iteration of the pipeline, showing exactly which operation lives on which warp–group and how the barriers keep everything moving without deadlock.

---

### 1. The data flow under a circular buffer  

Assume a CTA processes a query tile `\(Q_{i}\)` (`\(B_{r} \times d\)`).  
The key/value matrices are split into `\(T_{c} = \lceil N / B_{c} \rceil\)` blocks `\(K_{j}, V_{j}\)`.  
The buffer has *s* stages (`\(stage = j\bmod s\)`).

For every stage \(j\) we have  

| Stage | Producer action | Consumer action |
|------|-----------------|----------------|
| `load_KV(j)` | TMA copies `\(K_{j}\), \(V_{j}\)` `\(\to\)` shared memory slot *stage* | — |
| `SS_GEMM(j)` | — | WGMMA computes `\(S_{i}^{(j)} = Q_{i}\,\cdot\,K_{j}^{\top}\)` |
| `softmax(j)` | — | row‑max reduction `\(\to\)` exponentials `\(\to\)` scaled row sum |
| `RS_GEMM(j)` | — | WGMMA computes `\(O_{i} \gets O_{i} + \tilde{P}_{i}^{(j)}\,\cdot\,V_{j}\)` |

The consumer never touches a slot until it has been marked **available** by an  
`bar.arrive(stage)` issued by the producer after the TMA completes.  
Conversely, once a consumer finishes using slot *stage*, it signals  
`bar.arrive(stage)` again so that the producer may reuse it for the next block.  
Because *stage* advances monotonically (`\(j\!\to\! j+1\)`) there is no circular wait – every dependency points forward in time.

---

### 2. Two‑warp‑group ping‑pong  

The above table describes only one logical consumer thread–block.  
In FlashAttention‑3 we split that consumer into **two physical warp–groups**
that run alternately:

| Warp‑group | Work done in iteration *j* |
|------------|----------------------------|
| **WG<sub>0</sub>** | **Softmax** of block \(j\) (`softmax(\(j\))`) **and** RS GEMM of block \(\,j{-}1\,\) (`RS_GEMM(\(j{-}1\))`). |
| **WG<sub>1</sub>** | **SS GEMM** of block \(\,j{+}1\,\) (`SS_GEMM(\(j{+}1\))`). |

Thus while WG<sub>0</sub> is busy evaluating exponentials and normalising rows,
WG<sub>1</sub> has already launched an asynchronous matrix multiply for
the next key block. When WG<sub>0</sub> finishes its softmax it immediately switches role:
it now launches its own SS GEMM for block \(\,j{+}2\,\), while WG<sub>1</sub> …  

This “ping–pong” exchange continues until all key/value blocks have been processed.

#### Step‑by‑step schedule (simplified timeline)

```
cycle    WG0                         WG1
-----------------------------------------------------------------
t0   load Q_i   <- TMA                –               (producer work)
t1   wait K_0      <- bar.wait(0)      –               (wait for first KV)
t2   Scur = Q_i·K_0^T   <- WGMMA           –               (async)
t3   bar.arrive(0)                  –               (slot 0 free)
t4   // ----> softmax of Scur ----> //               (low-throughput)
t5   // ----> rescale O_i            //               (uses ℓ,m)
t6   load K_1,V_1 <- TMA                –               (producer fills slot 1)
t7   // ----------- overlap -----------             
t8   Snext = Q_i·K_1^T <- WGMMA        <-─┐              (async)
t9   wait V_0      <- bar.wait(0)     │              (need V_0 for RS_GEMM)
t10  O_i += Ṕ_cur·V_0 <- WGMMA       │              (async)
t11  bar.arrive(0)                  │              (slot 0 reclaimed)
t12  // ----> softmax of Snext ---->│              (WG0 continues)
t13  // ----> rescale O_i            │
t14  load K_2,V_2 <- TMA                │
t15  …                               │
```

* The **asynchronous** calls (`WGMMA`) at t2, t8 and t10 do not stall
the warp; they merely enqueue work onto the Tensor Core engine.  
* At t4–t5 WG<sub>0</sub> runs exponentials, reductions and row scaling –
operations that use only scalar pipelines.  
* At t8–t10 WG<sub>1</sub> already started its own matrix multiply
(`SS_GEMM(\(j{+}1\))`) **while**
WG<sub>0</sub> is still finishing softmax for block \(j\).
That is exactly what we call “hidden” softmax.  
* The barriers appear only when a shared‐memory slot changes ownership:
`bar.wait(stage)` before reading a tile,
`bar.arrive(stage)` after finishing its use.
Because both warp groups always operate on different stages
(`\(stage=j\bmod s\)` vs `\(stage=(j{+}1)\bmod s\)`)
there is never a situation where WG<sub>0</sub> waits for something
that can only be produced by WG<sub>1</sub>`after wg<sub>​…​>`—hence no deadlock.  
* When all blocks have been consumed an epilogue rescales the final output
`\(\displaystyle O_{i} \gets O_{i}\big/\ell_{i}\)`
after a final `bar.wait` ensures that every pending RS GEMM has completed.

### 3. Why “ping–pong” works on Hopper  

Hopper’s Tensor Cores execute WMAs completely independently from CUDA cores.
A regular CUDA instruction stream cannot see inside an enqueued WMAs;
it simply continues issuing later instructions.
Consequently an instruction such as an exponential can be scheduled immediately
after an WMAs without waiting for its result – unless we explicitly insert
a barrier.

The algorithm therefore  

* issues **WGMAs first**, letting them run in parallel;
* does **all low‑throughput work** that depends only on registers (`softmax`);
* finally inserts a `.bar.wait` only when it needs data produced by the WMAs
(e.g., reading back row‐wise maxima).

Because each barrier synchronises only one direction of data flow,
both sides keep making progress and utilisation climbs from ≈35 % up to ≈75 %
(see Fig.​ 4 of the paper).

```
                                   │ bar.arrive / bar.wait

      ┌──────────────►─────────────────────────────────────►───────────────┐
      │                                                                  │
      │    WG₀                         WG₁                           │
      │    ──────────────────────       ───────────────────────       │
      │    Softmax(j)                 SS_GEMM(j+1)                     │
      │    RS_GEMM(j−¹)               …                               │
      │                                                                  │
      └──────────────────────────────────────────────────────────────────┘

Each iteration advances both groups by one block; after one full cycle they “ping”
and “pong” their roles. The explicit barriers guarantee that no group ever reads
a tile before it has been written, while asynchronous WMAs hide all idle cycles,
producing exactly the overlap illustrated in Fig 5 of FlashAttention​−​3.
```

In short, ping pong scheduling achieves simultaneous execution of  

`\(\displaystyle softmax(j)\;\!+\;\!RS_{\text{GEMM}}(j{-}1)\;\;\leftrightarrow\;\;
SS_{\text{GEMM}}(j{+}1)\)`  

by assigning those two halves to different warp groups,
using a circular shared‐memory buffer guarded by lightweight CUDA barriers.
Because every dependency points forward (\(j{\rightarrow} j{+}1\)) and because WMAs are truly async,
the schedule never deadlocks and avoids long stalls—hence why FlashAttention​−​3 attains up to 2× higher TFLOPs on H100.

### Why does exponential throughput become a bottleneck despite its lower FLOP count?
Question:
"The H100 has 989 TFLOPS of FP16 matmul but only 3.9 TFLOPS of special functions such as exponential" – given that softmax involves far fewer FLOPs than the matmul (e.g., 512× less), why can exponentials still dominate half of the execution cycles? How does the difference between FLOP count and unit throughput lead to this situation, especially when moving from FP16 to FP8 where matmul throughput doubles but exponential throughput stays constant?
Answer:
The short answer is that “FLOP count” tells you how many arithmetic operations an algorithm needs, whereas “TFLOPS” tells you how many **operations per second** each functional unit on the GPU can deliver.  
On Hopper these two numbers are wildly different for matrix‑multiply versus special‑function units, so an operation that performs far fewer FLOPs can nonetheless consume a comparable fraction of the wall‑clock time.

### How many FLOPs does attention really do?

In a single head the forward pass computes  

\[
\mathbf{S}=QK^{\top}\qquad 
\mathbf{P}= {\operatorname {softmax}}\!\bigl(\mathbf{S}\bigr)\qquad 
\mathbf{O}=PV .
\]

If we tile the computation into blocks of size \((B_{r}\!\times d)\) for \(Q\) and \((B_{c}\!\times d)\) for \(K\) (the same tiling is used for \(V)), then  

* One block‑wise GEMM \(QK^{\top}\) performs \(2\,B_{r}dB_{c}\) floating‑point multiply‑adds.  
* The second GEMM \(PV\) performs another \(2\,B_{r}dB_{c}\).

Counting a multiply‑add as **two** FLOPs (the convention used throughout the paper), the two GEMMs together require  

\[
\vphantom{\underbrace{}{}}\underbrace{4\,d}_{\text{factor}}\;\times B_{r}B_{c}
\]

floating‑point operations.  

The softmax itself needs only one exponential per element of \(\mathbf{S}\), i.e.\ \(B_{r}B_{c}\) exponentials plus inexpensive subtract‑and‑divide steps.  

Consequently the **ratio** between GEMM FLOPs and exponentials is  

\[
\frac{\text {GEMM FLOPs}}{\# {\rm exp}}=4d .
\]

With a common head dimension \(d=128\) this gives a factor of **\(4\times128=512\$** – exactly what the authors report in § “Pingpong scheduling”.

### Why do those $\displaystyle \approx 500\times$ more FLOPs not dominate runtime?

Peak throughputs on an H100 are not uniform:

| Unit                                      | Peak TFLOPS (FP16) |
|-------------------------------------------|---------------------|
| Tensor‑Core matrix multiply               | $\displaystyle \approx 989$ |
| Special‑function unit (exp, log, …)      | $\displaystyle \approx 3.9$ |

Thus a single Tensor‑Core can finish about  

```tex
\[ 
\dfrac{989}{3.9}\;\approx\:255
``` 

times as many floating‑point operations per second as the special‑function unit can finish exponentials.

If we write the wall‑clock time spent on each part as  

```tex
\[ 
T_{\text{GEMM}} = \frac{\!\# {\rm FLOPs}_{\,{\rm GEMM}}\!}{989},
   \qquad
T_{\exp }       = \frac{\!\# {\rm exp}\!}{3.9},
``` 

and substitute  

```tex
\[ 
\!\# {\rm FLOPs}_{\,{\rm GEMM}} = 512\, \!\# {\rm exp}
``` 

we obtain  

```tex
\[ 
T_{\text G E M M}= 
   \frac{512\, \!\# {\rm exp}}{989}
   \;\simeq\:2.1\,T_{\exp } .
``` 

In other words **the GEMM part only runs about twice as long as the exponential part**, even though it does five hundred times more arithmetic work.  
Because everything else in softmax (the max reduction, subtraction, division) costs negligible cycles compared with an exponential, the exponential accounts for roughly one half of the total execution cycles in practice – exactly what Table&nbsp;1 and Fig.&nbsp;6 of the paper observe for FP16 with \(d=128.\)

### What happens when we switch from FP16 to FP8?

Hopper adds native FP8 tensor‑core instructions which double matrix‑multiply throughput while leaving the special‑function unit unchanged – it still delivers only $\displaystyle \approx 3.9\$ TFLOPS for exponentials because there is no separate “FP8 exp” path. Consequently the disparity widens:

* **FP8 GEMM peak** $\displaystyle (\;2\times 989)\;\approximately\:1978\$ TFLOPS,
* **Exp peak**                 $\displaystyle \approximately\:3.9\$ TFLOPS.

The ratio between attainable rates jumps from $\displaystyle (\;\approximately\:255)\;$to $\displaystyle (\;\approximately\:510)\;$.
Even though the absolute number of exponentials stays identical, its share of wall–clock time therefore grows: now almost all of the forward pass time is spent waiting for those slow exponentiations unless we hide them behind GEMMs.

### How FlashAttention‑3 deals with it

The authors exploit exactly this imbalance:

1\. **Warp–specialised producer/consumer pipelines** let one warpgroup load data while another issues tensor–core WGMMA instructions.  
2\. **Two–stage pipelining** overlaps a block’s softmax (including its exponentials) with the next block’s GEMM so that every cycle spent in a tensor core is paired with work on a special–function unit.  
3\. When using FP8 they retain this overlap; however because exp throughput does not increase, “hiding’’ becomes even more valuable—otherwise exponentials would dominate > 60 % of cycles.

Even with perfect overlap you cannot exceed the slower unit’s capacity; therefore after all possible hiding has been performed,
the overall speed is bounded by whichever unit runs longest—in practice still close to half of the cycles are spent in exponentiation for FP16 and an even larger fraction for FP8 unless additional hardware support for low–precision special functions appears.

### Take–away

The apparent paradox stems from confusing **operation count** with **hardware rate**: attention requires $\displaystyle \approximately\:500\$ fewer exponentials than matrix–multiply FLOPs, but Hopper’s tensor cores are $\displaystyle \approximately\:250\$ times faster than its special–function unit, making those few exponentials consume roughly half of execution time at FP16 precision and an even larger share at FP8 precision. FlashAttention‑3 mitigates this by tightly interleaving softmax with asynchronous GEMMs, but it cannot eliminate it entirely because the underlying hardware limits remain unchanged.​

### What are WGMMA instructions and how do they differ from earlier HMMA/Tensor Core calls?
Question:
"WGMMA" stands for warp‑group‑wide matrix multiply‑accumulate introduced in Hopper. How does its programming model differ from the older `hmma`/`mma` intrinsics used on Ampere? In particular, what changes are required in kernel code to switch from HMMA to WGMMA, and how does WGMMA enable asynchronous execution?
Answer:
**Short answer** – WGMMA is a new Tensor‑Core instruction introduced with NVIDIA’s Hopper architecture that lets a *warp‑group* (four contiguous warps) issue a single matrix‑multiply‑accumulate operation. It differs from the older HMMA/​MMA intrinsics of Ampere in three important ways:

1. **Scope of the operation** – HMMA works per‑warp; every warp independently multiplies a $64\times 64$ (or $128\times 64$) tile that lives entirely in its own registers/shared memory. WGMMA aggregates the registers of four warps and computes a larger tile (e.g.\ $128\times 128$ or $256\times 256$) in one instruction, so fewer instructions are needed and the hardware can keep more Tensor‑Core lanes busy.

2. **Asynchronous execution** – On Hopper the Tensor‑Core pipeline is decoupled from the normal CUDA‑core pipeline. A WGMMA instruction returns control to the issuing warp‑group immediately; the actual multiply‑accumulate proceeds in parallel with any subsequent instructions (e.g.\ loads through the Tensor Memory Accelerator or soft‑max exponentials). With HMMA the compiler inserts an implicit “wait” after every call because the legacy Tensor‑Core pipeline blocks the issuing warp.

3. **Layout constraints & low‑precision support** – WGMMA supports FP8 directly but imposes a stricter “k‑major” layout on its operands, whereas HMMA accepted both mn‑major and k‑major layouts for FP16/BF16. Consequently a kernel that switches to WGMMA must reshape one of its matrices (normally V) before it reaches shared memory or perform an in‑kernel transpose using LDSM/STSM.



### What you have to change in kernel code

When you port an existing Ampere kernel that uses `hmma`/`mma` intrinsics to Hopper’s `wgmma`, the transformation is essentially a change of *thread‑group organization* plus a few architectural‐specific calls:

1. **Split the CTA into producer/consumer warp‑groups**  
   In FlashAttention‑3 the CTA is divided into two warp‑groups: one set of warps only performs TMA loads (`producer`) while the other set only issues WGMMAs (`consumer`). This split can be expressed with PTX’s `setmaxnreg` directive which temporarily reduces register count for producer warps so that more registers become available for consumer warps that need them for matrix fragments.

2. **Replace every HMMA call with a WGMMA call**  
   In user code this means swapping something like  

   ```cpp
   // Ampere
   __hmma16816(...);      // implicit wait after it
   ```  

   with  

   ```cpp
   // Hopper
   wgmma_m64n64k64_fp16(...);   // async – no implicit wait
   ```  

   The exact name depends on datatype and tile size (`wgmma_m128n128k64_fp8`, etc.). If you use CUTLASS / cuTensorCore abstractions you simply change the template arguments from `<tHmma>` to `<tWgmma>`; CUTLASS automatically emits the proper PTX.



3. **Adjust operand layout**  
   For FP8 you must ensure that both A and B operands are stored *k‑major* in shared memory (contiguous in K). A common way, as described in § 4\.2 of FlashAttention‑3, is to let the producer warp‑group transpose V on‑the‐fly after loading it into SMEM using `ldmatrix`/`stmatrix`. For FP16 you can keep either layout, but keeping everything k\-major eases code reuse across precisions.



4. **Remove stale synchronisation**  
   Because WGMMA does not block, any `__syncthreads()` placed immediately after an HMMA becomes unnecessary and actually harms performance. Instead insert explicit barriers only where data movement between producer/consumer groups must be ordered, e.g.:

   ```cpp
   // After loading Q/K/V into SMEM
   bar.sync [0];          // tell consumer group data is ready
   // Consumer group:
   wgmma(...);            // launch async GEMM
   // … continue issuing TMA loads for next tiles …
   ```



5. **Add explicit “wait” when you really need results**  
   The consumer eventually needs the accumulator before it can apply softmax scaling or write out O. At those points you insert either a `bar.sync` that synchronises on the same buffer stage used by producers, or leverage CUDA’s “asynchronous collective” API (`cuda::pipeline`). In FlashAttention‑3 this appears as “Commit and wait” after each WGMMAs which really maps to a fence that ensures prior WGMMAs have completed before using their output.



### How asynchrony translates into speed

In AMPERE’s synchronous model each iteration of attention’s inner loop looked roughly like  

```
load K_j,V_j → __syncthreads()
S = Q_i · K_j^T        // hmma
softmax(S)
O += P·V_j            // hmma
```

Every `hmma` stalled the warp until its result was ready, so while the second GEMM was running no other work could be issued by that CTA – even though the GPU had idle tensor‐core pipelines waiting for new data.



With WGMMA these steps become  

```
load K_j,V_j → async TMA               // producer warps keep loading
S_next = Q_i · K_{j+1}^T ← wgmma async // consumer issues next GEMM early
softmax(S_cur)                         // runs while previous wgmma finishes
O += P_cur·V_j ← wgmma async           // overlaps with softmax of next block
```

Because each WGMMAs lives in its own hardware queue, a CUDA core can start exponentials (`expf`) as soon as it has received `S_cur`, while another set of Tensor Cores already works on `S_next`. The paper reports an improvement from ~570 TFLOP/s (HMMA path) to ~620–640 TFLOP/s when merely adding this ping–pong scheduling; full two–stage pipelining pushes utilization up to ~740 TFLOP/s (≈75 % of H100’s peak).

In practice this means:

* **Higher occupancy:** Four warps jointly feed one Tensor Core instruction, so register pressure per thread declines compared with allocating an entire fragment per warp.
* **Better latency hiding:** While one WGMMAs stalls waiting for its inputs, another independent WGMMAs already runs; softmax—previously a bottleneck because its throughput is roughly two orders of magnitude lower than Tensor Cores—gets overlapped almost completely.
* **Cleaner code path:** Producer/consumer split mirrors classic CPU producer–consumer pipelines but at CUDA‐warp granularity; no explicit double buffering of shared memory beyond what already existed for HMMA, just an extra circular buffer stage advertised by `setmaxnreg`.



### Putting it together

To convert an existing Ampere‐based attention kernel:

1. Refactor CTA layout into two logical warp groups.
2. Replace every `hmma` intrinsic with its matching `wgmma` variant (CUTLASS makes this almost one line change).
3. Adjust tensor storage so that all GEMM operands respect WG​M​M​A’s k\-major constraint—typically by adding an LDSM/STSM based transpose inside the producer group.
4. Remove hidden synchronisation after each matmul and introduce explicit barriers only where inter‑group data dependencies exist.
5. If targeting FP8, also add block quantization / incoherent processing as described in § 4\.2, because WG​M​M​A only accepts k\-major FP8 tiles.



The net effect is an attention kernel whose matrix multiply stage runs asynchronously with both data movement (via TMA) and non‑matmul work (softmax), achieving up to twice the utilization observed with older HMMA based kernels on H100 GPUs—as demonstrated by FlashAttention‑3’s experimental results.​
