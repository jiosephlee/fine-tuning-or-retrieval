\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### Why does FlashAttention‑2 achieve only ~35% hardware utilization on H100 GPUs?
Question:
The paper states that FlashAttention‑2 reaches only about 35 % utilization on the Hopper H100 GPU while optimized GEMM kernels achieve 80–90 %. I understood that FlashAttention‑2 already eliminates intermediate global memory writes/reads by fusing all operations into a single kernel. What architectural or algorithmic factors prevent higher occupancy/utilization on H100? Is it mainly due to not using Hopper‑specific Tensor Core instructions, or are there deeper reasons related to the synchronous execution model?
Answer:
`FlashAttention‑2` already removes the *global*‑memory traffic that dominates a naïve attention implementation, but on a Hopper H100 it still reaches only about one third of the peak FLOP rate ($\approx 35\,\%$).  

The shortfall comes from two intertwined sources that are described explicitly in the paper:

1. **The kernel follows a purely synchronous schedule**  
   In the forward pass `FlashAttention‑2` processes a query‑block $Q_i$ by iterating over key/value blocks $(K_j,V_j)$. For each block it first issues an “SS‑GEMM’’  

   $$
   S_i^{(j)} = Q_i K_j^{\!\top},
   $$  

   then waits for that matrix multiply to finish before computing the local softmax $\widetilde P_i^{(j)}=\exp(S_i^{(j)}!-\!m_i)$ and finally launches an “RS‑GEMM’’  

   $$
   O_i \gets O_i + \widetilde P_i^{(j)} V_j .
   $$  

   The algorithm therefore inserts a **hardware barrier after every GEMM** (`wait` statements in Alg.~1). While one threadgroup is busy executing the exponential‑and‑sum part of softmax, all Tensor Cores that could be performing the next multiply sit idle; conversely while a GEMM is running the special‑function unit (SFU) that implements `exp` is starved. Because on an H100 an FP16 tensor‑core can deliver $\approx 989\,\text{TFLOP/s}$ whereas the SFU can sustain only $\approx 3{-}4\,\text{TFLOP/s}$ for exponentials, even a modest amount of unoverlapped softmax work can consume roughly half of the wall‑clock time. The net effect is a cycle‑level underutilisation that shows up as $\sim 35\,\%$ hardware utilisation.

   `FlashAttention‑3` removes this bottleneck by **splitting producer and consumer roles into separate warps**, issuing TMA loads asynchronously, and overlapping the second GEMM of iteration $j$ with the softmax computation for iteration $j+1$ (“ping‑pong’’ scheduling). This two‑stage pipeline hides the low‑throughput special‑function work inside tensor‑core activity and raises utilisation to $\approx 75\,\%$.

2. **The implementation does not exploit Hopper’s new Tensor‑Core instruction set**  
   The original `FlashAttention‑2` kernels were written for Ampere’s HMMA/Tensor Core interface and therefore run on an H100 using older microcode paths (“AMPERE” kernels). Although HMMA still works on Hopper, it does not take advantage of **WGMMA**—the warpgroup‑wide instruction introduced in Hopper that can fetch operands directly from shared memory and launch completely asynchronous matrix multiplies. WGMMA offers a higher issue rate and relaxes layout constraints (the operand layout restrictions described in § 3.3). As noted in § 1 (“Partially, this may be attributed … not using Hopper–specific instructions”), using HMMA instead of WGMMA reduces the effective FLOP throughput per SM by roughly a factor of two compared with an optimised GEMM kernel that does use WGMMA (e.g., cuDNN 9 or ThunkerKitten).

   Moreover, `FlashAttention‑2` treats its data tiles as mn‑major or k‑major without regard for the stricter k‑major requirement imposed by FP8 WGMMAs, so it cannot benefit from FP8 tensor cores either—a loss that becomes noticeable when one looks at peak utilisation numbers derived from FP16 runs alone.

Together these two factors explain why an otherwise “memory‑optimal’’ algorithm still stays at only about $35\,\%$ utilisation on an H100:

* **Synchronous sequencing** forces long idle periods while waiting for softmax or for shared–memory loads;
* **Legacy instruction selection** prevents each active cycle from generating maximum tensor‑core work;
* The relatively small per‑block GEMMs ($B_r\times B_c$) used by `FlashAttention‑2` also limit how many warps can be kept busy once those synchronisation stalls are removed—hence optimised kernels increase both tile size *and* instruction efficiency whereas `FlashAttention‑2` does neither.

The authors verify this diagnosis empirically: when they replace the HMMA calls with Hopper’s WGMMA, introduce producer–consumer warp specialization, and overlap GEMM with softmax (`FlashAttention‑3`), they observe TFLOP/s rising from $\approx 350\,\text{TFLOP/s}$ ($\approx 35\,\%$) up to $\approx 740\,\text{TFLOP/s}$ ($\approx 75\,\%$). In short, `FlashAttention‑2` is limited not simply by its fusion trick but by a combination of **a purely synchronous execution model** and **the lack of Hopper‑specific asynchronous Tensor Core primitives**, both of which prevent it from keeping the massive H100 compute resources fully occupied.
