# From Text to Tensors: Turning LLM‑Generated Rules into Binary Features

When you ask a large language model (LLM) to “explain why this patient has heart failure,” it will reply with a list of natural‑language conditions—something you could read as a doctor’s note.  For a machine learning pipeline, however, we need something far more rigid: a set of numeric columns that say *yes* or *no* for each condition.  The **FeatLLM** framework bridges this gap by converting the messy text it produces into clean binary features that any downstream model can ingest.  Below is a walk‑through of that transformation pipeline, from prompt engineering to executable Python code and finally to a tiny linear classifier.

---

## 1. Why Binarise Rules at All?

In classic tabular learning we feed a model raw columns like “age” or “blood pressure.”  
FeatLLM asks an LLM to **engineer new columns** by summarising its domain knowledge into logical rules such as:

```
If age > 65 AND cholesterol > 200 → high risk of heart failure.
```

If we could turn each rule into a **binary flag**—`1` when the rule holds for a row, `0` otherwise—we end up with a feature matrix that explicitly encodes high‑level concepts.  A simple linear model can then learn how much weight to give each flag without ever seeing the original raw columns again during inference.  This yields two practical benefits:

* **Speed** – inference reduces to a dot product, no per‑sample LLM calls.
* **Interpretability** – each weight directly tells you how useful its underlying rule is.

---

## 2. The Noisy Nature of LLM Output

Even with carefully crafted prompts, an LLM’s answer is not always syntactically uniform:

* `>` may appear as “greater than”.
* Logical connectors may be spelled out (“and”, “or”) or replaced by symbols (`&`, `|`).
* Extra words or punctuation can sneak in (“If … then …”).

If we tried to parse such strings manually with regular expressions, we would quickly drown in edge cases.  FeatLLM sidesteps this by letting **the LLM parse its own output**—a trick that leverages its code‑generation abilities.

---

## 3. Two‑Stage Prompting: From Rules to Python

### 3️⃣ Stage 1 – Ask the LLM for Rules

A prompt is built from three parts:

1. **Basic information** – task description (“Predict chronic heart failure?”), feature definitions (“age is an integer”), and a few labeled examples serialized as text.
2. **Reasoning instruction** – first infer generic relationships (e.g., “older people have higher risk”) then combine these priors with the provided examples.
3. **Response instruction** – demand exactly ten rules per class and prescribe a fixed JSON‑like format:

```json
{
  "class": "positive",
  "rules": [
    "age > 65 and cholesterol > 200",
    "...",
    "..."]
}
```

The result is a *human‑readable* list of conditions that capture what the LLM thinks matters for each label.

### 🛠️ Stage 2 – Ask the LLM to Translate Rules into Code

We feed those raw strings back into another prompt that tells the model:

> “Given the column names `age`, `cholesterol`, … write a Python function `apply_rules(row)` that returns a list of 0/1 values indicating whether each rule is satisfied.”

Because GPT‑type models have been trained on billions of lines of code, they can reliably emit something like:

```python
def apply_rules(row):
    r = []
    r.append(int(row["age"] > 65 and row["cholesterol"] > 200))
    r.append(int(row["blood_pressure"] < 120))
    # ...
    return r
```

Notice how we do **not** try to hand‑craft parsers—the model itself normalises synonyms (“greater than” → `>`), adds parentheses where needed, and respects data types thanks to our earlier feature descriptions.

---

## 4. Executing the Generated Code (`exec()`)

The snippet returned by the LLM is now pure Python text.  
In FeatLLM we safely execute it with Python’s built‑in `exec()`:

```python
namespace = {}
exec(generated_code, {}, namespace)
apply_rules = namespace["apply_rules"]
```

We then run `apply_rules` over every row in the original table:

```python
Z = np.array([apply_rules(row) for row in dataset])   # shape = (N, R)
```

Here `Z` contains **binary features** (`0`/`1`) for all `R` rules extracted for a particular class (`R = 10` in our experiments).  
If there are `c` classes we repeat the process independently and obtain matrices `Z₁,…,Z_c`.

---

## 5. From Binary Flags to Class Probabilities

With binary matrices at hand we only need a lightweight classifier.  
FeatLLM uses a **non‑negative linear model** per class:

\[
\text{logit}_k^{\,i} \;=\; \max(\mathbf{w}_k,\;0)\;\cdot\;\mathbf{z}_k^{\,i},
\qquad
\mathbf{p}^{\,i} \;=\;\mathrm{Softmax}\bigl([\text{logit}_1^{\,i},\dots,\text{logit}_c^{\,i}]\bigr).
\]

* $\mathbf{z}_k^{\,i}\in\{0,1\}^{R}$ – binary flags for sample $i$ under class $k$.
* $\mathbf{w}_k$ – trainable weight vector learned on the few labeled shots.
* The `max(...,0)` projection forces all weights positive so that satisfying an additional rule never hurts a class score.

We optimise cross‑entropy loss on the *k*-shot training set (often as few as four examples). Because there are only $R$ parameters per class (e.g., $10$), training converges within seconds on an ordinary CPU/GPU.

---

## 6. Ensembling & Bagging (Optional Boost)

To reduce variance from any single set of rules, FeatLLM runs the whole pipeline multiple times:

* **Temperature** is raised during rule generation so different wording / rule sets appear.
* **Bagging** randomly selects subsets of columns or samples before each run,
rendering each trial slightly different.
* Final prediction averages softmax outputs across all trials (`T ≈ 20` works well).

Even if one run produces an outlier rule, it gets diluted by the ensemble—a classic wisdom from random forests transplanted onto language models.

---

## 7. Putting It All Together – A Mini‑Pipeline Sketch

```python
def featllm_pipeline(dataset, few_shot_examples):
    # ---- Stage 1: generate textual rules per class ----
    raw_rules = query_llm_for_rules(few_shot_examples)

    # ---- Stage 2: translate rules -> python ----
    python_code = query_llm_for_parsing(raw_rules)

    # ---- Execute generated code -> binary features ----
    exec(python_code)                     # defines apply_rules()
    Z = np.array([apply_rules(row) for row in dataset])

    # ---- Train lightweight linear model ----
    w = train_nonneg_linear(Z, labels)

    # ---- Predict on new data ----
    logits = np.maximum(w,0) @ Z.T
    probs = softmax(logits.T)
    return probs
```

The entire inference path after step 2 consists only of matrix multiplications—no more costly API calls or GPU‐bound transformer passes.

---

## 8. Takeaways for Practitioners

| What you get | Why it matters |
|--------------|----------------|
| **Human‑readable rules** from an LLM | Direct interpretability; you can inspect which conditions matter |
| **Binary feature matrix** | Works with any downstream learner (logistic regression, SVMs) |
| **Tiny training cost** | Only learns ≤ 10 weights per class |
| **Fast inference** | Eliminates per‑sample LLM queries |
| **Robustness via ensemble** | Handles noisy or ambiguous rule generations gracefully |

If you’re already using LLMs for tabular prediction (e.g., via *in‑context learning* or *parameter‑efficient tuning*), consider switching half of your workflow to *feature engineering*: let the model tell you what matters once, convert those insights into tidy tensors, and let classical ML do what it does best—quickly turning numbers into predictions.

--- 

By treating language models as expert *feature engineers* rather than end‑to‑end predictors, FeatLLM demonstrates how blurry natural language can be distilled into crisp binary tensors ready for production pipelines—all without ever fine‑tuning the massive model itself.
