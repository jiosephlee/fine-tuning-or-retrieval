\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Why does FeatLLM enforce non‑negative weights when aggregating rule‑based binary features?
Question:
In Section 3.2 the paper defines the class logit for sample \(i\) as
\[
\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i,
\]
where \(\mathbf{z}_k^i\) is the binary vector indicating which of the \(R\) rules for class \(k\) are satisfied and \(\mathbf{w}_k\) are trainable weights. The authors say that projecting the weights into a positive subspace ensures that "features generated by the LLM do not reduce the likelihood of a class during learning." I am not convinced I understand why negative weights would be problematic here – could a rule legitimately be indicative of **not** belonging to a class? How would allowing negative weights affect interpretability or performance? What alternatives might exist (e.g., using a bias term or regularization)?
Answer:
In **FeatLLM** every rule that the language model writes is turned into a *binary* feature  

$$
\mathbf{z}^{i}_{k}\in\{0,1\}^{R},
$$  

where $R$ is the number of rules extracted for class $k$ and $((z^{i}_{k})_{r}=1)$ iff sample $i$ satisfies the $r$‑th rule of that class.  The downstream predictor is a linear model without a bias term  

$$
\text{logit}^{i}_{k}= \max(\mathbf{w}_{k},0)\cdot \mathbf{z}^{i}_{k},
\qquad 
\mathbf{p}^{i}= \operatorname{softmax}\big(\text{logit}^{i}_{1},\,dots ,\,\text{logit}^{i}_{c}\big),
$$  

where $\max(\mathbf{w}_{k},0)$ denotes element‑wise ReLU applied to the trainable weight vector $\mathbf{w}_{k}$.  
The authors explicitly state that “projecting these weights into a positive subspace ensures that the features generated by the LLM do **not** reduce the likelihood of a class during learning.’  

### Why are only non‑negative contributions allowed?

A rule produced for class $k$ is meant to describe **positive evidence** that a sample belongs to that class – e.g., “age $> 60$", “blood pressure $\ge 140 mmHg$”. The corresponding binary feature is therefore an indicator *that such evidence holds*. If we permitted $\mathbf{w}_{k,r}<0$, then whenever the condition were true it would *decrease* $\text{logit}^{i}_{k}$. In other words a feature intended as “support” would become a “penalty”, which contradicts the semantic role given by the prompt (“derive decisive rules … distinguish classes”).  

Because each rule lives inside its own “class‑specific” bucket, any lack of support is already encoded implicitly: when a rule is **not** satisfied its feature value is 0, contributing nothing to $\text{logit}^{i}_{k}$. Thus negativity is unnecessary – zero already represents “no positive evidence”. If one really wants an “anti‑evidence” clause such as “if chest pain = No then NOT heart disease”, it should be expressed explicitly as another rule (“chest pain = No”) whose binary indicator belongs either to the opposite‐class set or to its own dedicated bucket. In this way every learned weight can stay non‑negative while still capturing both sides of a relationship.  

### What would happen if negative weights were allowed?

1. **Interpretability loss** – With unrestricted signs the magnitude of $w_{k,r}$ no longer has an immediate meaning. A large positive weight still signals an important supportive rule, but a large *negative* weight signals an important *contra*-evidence rule hidden inside a feature labelled as “support”. To understand what drives predictions one would have to examine both sign and value, making it harder for users (especially domain experts) to read off which conditions favor a class.  

2. **Higher variance in low‑shot regimes** – In the few‑shot setting only a handful of labeled examples guide learning. Gradient descent can easily assign strong negative values to rules that happen, by chance, to co‑occur with the opposite label in those few examples (spurious correlations). Since such values actively suppress logits they can destabilise training and lead to overly confident yet wrong predictions. Constraining all coefficients to be non‑negative halves the hypothesis space and acts as a strong inductive bias aligned with how the features were constructed, thereby reducing overfitting.  

3\. **Monotonicity guarantees** – The ReLU projection guarantees **monotonicity**: adding any satisfied rule cannot lower the score for its own class. This property matches intuition from many interpretable models such as weighted voting schemes or additive rule ensembles (RuleFit, Bayesian Rule Lists), where each active clause contributes positively toward its target label.  

The paper’s ablation study (“‑Tuning”) shows degradation when this component is removed, confirming that letting arbitrary signs creep in harms performance on average across datasets.  

### Could other design choices achieve similar goals?

Yes. One could keep unrestricted weights but add mechanisms that mitigate their drawbacks:

* **Bias terms** – Adding a per‑class intercept $b_{k}$ would allow systematic upward or downward shifts without needing any particular feature to act negatively. However this does not solve sign ambiguity inside $\mathbf{w}_{k}$; it merely supplies a global offset.  
* **Explicit complementary features** – For every generated clause one could also create its logical negation (“not …”) as an extra binary variable. Then every coefficient may safely stay non‑negative because both directions are represented explicitly.  
* **Regularisation enforcing positivity** – Instead of hard clipping via ReLU one might penalise negative entries with an extra term $\lambda\,\sum_{r}\max(-w_{k,r},0)$. This needs an extra hyper‑parameter $\lambda$ and complicates optimisation—something the authors deliberately avoid given their emphasis on minimal tuning.  
* **Constrained optimisation** – Solving $\min_{\mathbf w\,\ge\,0}\mathcal L(\mathbf w)$ directly (e.g., using projected gradient descent) yields exactly the same effect as applying ReLU after each update; however writing it explicitly adds implementation overhead while offering no practical benefit beyond what their simple $\max(\cdot ,0)$ already provides.  

In practice these alternatives trade simplicity against additional hyper‑parameters or larger prompt lengths (the extra complementary features double dimensionality). The authors chose hard non‑negativity because it preserves **interpretability** (weights become “importance scores”), keeps **training stable** in low‑shot contexts, and incurs negligible computational cost—exactly what FeatLLM aims at: an inexpensive downstream linear model whose parameters can be learned from very few examples without sacrificing clarity about what each LLM‑derived rule contributes.  

### Summary

FeatLLM treats every LLM‑generated clause as *positive evidence* for its associated class; consequently it constrains the downstream linear coefficients to be non‑negative by applying an elementwise ReLU projection $\max(\mathbf w_{k},0)$. This design guarantees that satisfying any extracted rule can only increase—or leave unchanged—the logit for its own class, preserving a clear interpretation (“how much does this condition help?”), limiting variance when data are scarce, and preventing accidental penalisation caused by spurious correlations in few‑shot training data. Allowing negatives would break this semantic alignment, make explanations harder to read and increase susceptibility to overfitting; alternatives exist (bias terms, complementary rules, regularisation), but all introduce extra complexity while offering little practical advantage over the simple positivity constraint adopted in the paper.[NO SHADOW POPUP SELF]
