# Meet FeatLLM – Turning AI Into an Expert Feature Engineer  

Large language models thrive when they get freely written prompts telling them what they're supposed to do next.  
What people usually do with those same models is ask them *for every single input* whether it belongs to a certain class—a black‑box prediction that must go through the model again during testing time.  
This makes tabular learning with LLMs expensive and limits their real‑world impact because every prediction demands another expensive remote API call\.  

**FeatLLM** flips that paradigm around.  
Instead of using an LLM to predict labels one sample at a time, it lets the model *write* a set of interpretable decision rules from just a handful of labeled examples\.  
Once those rules are extracted they become reusable binary features that any lightweight classifier can consume during inference\.  
This architecture eliminates per‑sample calls to the language model while still tapping into its vast background knowledge and reasoning abilities\.  

Below we walk through how this simple idea unlocks accurate few‑shot tabular learning—even on datasets unseen during pre‑training—and why it’s a practical next step forward for leveraging big models on everyday data‑science problems​.



--------------------------------------------------------------------------

## Why “feature engineering” matters when data is scarce  

* **Tabular data come in diverse shapes** – numerical counts, categorical codes, dates… traditional deep nets aren’t always competitive when there are few labeled examples*​.  
* **Domain knowledge is often buried** in plain language (e.g., “old patients are more likely to have heart disease”), which large language models have absorbed while being trained on millions of documents\.  
* **Standard few‑shot approaches** struggle because they either ignore this prior knowledge or demand costly fine‑tuning\.  
* **Feature engineering bridges that gap** – human‑readable decision thresholds distilled into binary features synthesize both data evidence and background knowledge into something compact yet powerful\.  

FeatLLM uses exactly this intuition: let an LLM deduce *what* conditions matter instead of *directly answering* whether they apply.



--------------------------------------------------------------------------

## The FeatLLM pipeline at a glance

```
    Few labeled examples  ──> prompt → LLLL ⟶   ← →   ──> set of “rules”
           │                        │
           ├─► parsing   ─►   new binary features
           │                        │
           v                        v
    Linear classifier  ──► weights ← training (few samples)
          /
     ensemble +
```

1. **Rule extraction** – A carefully designed prompt (three stages) nudges GPT‑3\texttt{-turbo} (or any equivalent) into writing ten class‑specific rules based purely on its conceptual understanding *and* the handful of demo examples provided.\<br>
2. **Rule parsing** – Those natural‑language sentences are fed back into GPT‑3\texttt{-turbo} which outputs tiny Python snippets that test each condition against new rows.\<br>
3. **Binary feature creation** – Executing those snippets produces a sparse matrix \(Z\in\{0,1\}^{N\times R}\), one column per inferred rule.\<br>
4. **Lightweight classification** – A non‑negative linear model scores every rule:  

\[
\text{logit}_{k}^{(i)} = \bigl[\max(0,\mathbf w_{k})\bigr] \!\cdot\! \mathbf z_{k}^{(i)},
\qquad
p_{k}^{(i)} = 
    \frac{\exp(\text{logit}_{k}^{(i)})}
         {\sum_{\ell=1}^{c}\exp(\text{logit}_{\ell}^{(i)})},
\]

where \(\mathbf z_{k}^{(i)}\) masks whether sample \(i\) satisfies rule set \(k\)\,. Both the weights and their associated sparsity pattern are learned only on the few labeled shots.\<br>
5. **Bagged ensemble** – The whole process is replicated \(T=20\) times with different random seeds / demonstration order / temperature settings so each run proposes slightly different sets of rules.\<br>
   Final probabilities are simply averaged over all \(T\), which greatly dampens variance stemming from occasional wrong rule guesses.

## Prompt design – letting the LLM reason like an expert  

Three pillars structure each prompt sent to the LLM keyed for clarity:

| Component | Purpose | Key example |
|-----------|---------|-------------|
| **Basic information** | Facts about task, label meanings and column descriptions | “The task is ‘Does this patient have anemia?’” plus “BMI is continuous … Gender is one‐of {Male,Female,…}.” |
| **Reasoning instruction** | Forces chain of thought consisting of *Step 1*: hypothesize feature–label relationships based purely on priors;<br>*Step 2*: tighten these ideas using dark‐examples → concrete class rules.| “First list causal insights… Then use demos below.” |
| **Response instruction** | Guarantees machine‐parseable format ready for coder |\nClass A:\n1️⃣ ``Age > 60`` … |

The instruction hierarchy encourages *no spurious association* that may look plausible statistically yet clash with world knowledge—a crucial defense when working with≤ 8 training samples.



--------------------------------------------------------------------------

## How parsing turns language into code  

Rules may be rendered slightly differently each time (“age ≥ 60” versus “age > 60”); if you naïvely parsed punctuation you would get errors\\. Instead the original wording along with function signatures (“`def age_gt_60(row):`”) is supplied back into GPT‑3\n\n∴ it writes—without you writing a parser—a minimal piece such as

```python
def age_gt_60(row):
    return row['Age'] > 60
```

This snippet then feeds directly into Python’s ```exec()```, turning every incoming record into tens-of-binary-rule tests automatically—all done once during training regardless of test set size.

## What makes early experiments successful?

### Benchmarks

Fea t LL m was evaluated on thirteen real & synthetic classification tasks ranging from adult income attribution (\# Adult), heart disease prediction (\# Heart), cannabis yield estimation (\# Cultivars), drug effects (\# Sequence-type), up through intricate socio-economic interactions (\# Communities).  

Key observations detailing four–shot versus thirty–shot regimens:

| #Shots | Avg up/down compared w/ conventional ML |
|--------|----------------------------------------|
| 4 shots | Reach accuracy equal/above XGBoost trained on *all* data |
| 32 shots (+35 %, usual teacher scale) | Duplicate complex baseline performances |
| FeatLLM (4 shots) | +~10 % AUROC over TabLLM / Stunt around all datasets |

The experiments required roughly thirty API calls per run—far fewer than approach requiring one call per input sample—yet achieved superior rankings across all eleven lib free baselines plus commonly deployed large-model baselines such as In‑Context Learning & TableT.



### Ablation study highlights

Removing any component led to measurable drops:
* Smoothing weights disabled → raw count votes → ~−4 % AUROC\,,
* Omitting Ensemble → reliance on single noisy rule set → ~−7 % AUROC\,,
* Skipping Feature Descriptions or Step‑1 Reasoning → produced many junk rules → ~−9 % AUROC\,,
showing each part is essential.



### Robustness against misleads

When irrelevant columns were appended randomly ("Adult" attributes added into the Heart dataset), most approaches suffered steep falls—upwards of 15 % drop—whereas Fea t LMM dropped only about 4–5 %. This indicates its internal mechanism penalizes cues incompatible with world priors even before seeing lots of data.



### Training / Inference Cost Comparison 

A single 16–shot Adult experiment dated ***9-Jul-24***:
| Model | Training Time (minutes) | Inference Latency (ms/sample) |
|-------|------------------------|--------------------------------|
| Logistic Regression | < 1 | < 1 |
| XGBoost | ≈ 30 | ≈ 5 |
| In‑Context Learning | ≈ 300 | ≈ 800 |
| TableT / TabLLM | ≈ 1800 (>40 GPU sweeps) | ≈ 2500 |
| **Feat-LMM** | ~23 (30 API calls ± delay)| < 2 |

Thus Fea t LMM offers **competitive inference speed**, while still enjoying near–state-of-the-art accuracy.



### How good are its generated features?

For each unique rule we evaluated marginal AUROC vs label:
```
Feature example : Age>70    AUROC ≈ .73
Feature example : BMI<18   AUROC ≈ .45
```
On average over all datasets:
* Before learning weights ~80 % rare columns had AUROC > .50,
* During training many low-value weights dropped below .1 threshold,
while keeping >70 % useful ones—
shows out-of-the-box rule quality while further sharpening via linear weights.

## Takeaways & Practical Recommendations
  
* If you have tiny labeled sets (< 10 rows), let any surface-tuned GPT encode domain heuristics instead of predicting raw cases—this halves your average inference cost while delivering robust predictions.\n\nBoth steps map nicely onto existing pipelines:\n• Create CSV → craft small cue sheet + few demos ↔ feed prompt<br>• Receive JSON list ↔ plug empty parser<br>• Train lightweight linear lightness ↔ deploy stateless microservice<br>\nAll done without ever touching hidden layers or entrenched checkpoints beyond untrained GPT‐style queries.\n\nYou need only carry out several dozen queries during model bootstrap (~30·ensemble runs); thereafter your downstream deployment sees no cost overhead beyond trivial CPU decompression.<br>\n\nThis boils away one main roadblock facing big-model adoption today—the extreme latency you endure when you have millions/thousands individual predictions per minute.“​


--------------------------------------------------------------------------

## Looking ahead  

Because every trained linear model simply learns non-negative weights over sparse oracle features we can stack further extensions very naturally:

* Mixed-value rule families — thresholds turned continual scores rather than step functions,
* Grouped inter-rule interactions tuned along weaker tree patterns,
* Apply dynamic pruning during inference if memory budgets shrink.\n\nNotably our tests were performed entirely under API-only access using GPT‐3½ ‑ turbo ‑0613—not fine-tuned checkpoints—showing any comparable modern foundation model could run existing Specs under identical constraints.\n\nFea t LMM’s primary future enhancements will therefore focus on two axes:\n• scaling up beyond merely dozens x58 inner encoder tokens i.e.​ larger column subsets or full high-dimensional records;\n• integrating fairness awareness so that extracted heuristics overlook sociological biases inherent in pre-trained corpuses.\n\nIn short…, making ​large models act like domain experts who handcraft useful dichotomies has become substantially cheaper—and it's already delivering higher accuracy than legacy few-shot learners whenever managing heterogeneous tables.​

In multi-modal modern machine learning twinned keys—the fine-grained interpretability kept engineering SARS University Big Data — Transformers remain powerful when instructed correctly—but too much reliance on end-to-end black box predictions turns slow invoice processors chaotic because nearly every execution costs network hop time^. If instead you ask your model how it would write human-interpretable decision logic applies once-over all inputs meanwhile feed resulting logic into a tiny ML engine you effectively mutely harness priori wisdom out-of-the-box without ever touching your entire thousand-step lookup table design​. That’s exactly what **Feat\-LMM** does—and tests demonstrate it consistently beats other state-of-the-art _few-shot_ tabular approaches both in speed and accuracy​.
