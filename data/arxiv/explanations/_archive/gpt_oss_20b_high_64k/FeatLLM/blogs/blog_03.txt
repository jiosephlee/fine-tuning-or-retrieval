# RuleSoup to BinaryBarrels  
*Converting Generated Rules into Transformative Features*

---

## Why do we bother turning “rules” into data columns?

Large Language Models (LLMs) can understand pragmatic relationships between tabular columns and target labels even with only a handful of annotated rows. Their natural‑language output is very human‑readable – often resembling short decision‑rules such as  
```
If patient age > 60 and blood pressure > 140 then chronic heart failure likelihood ↑ .
```
But downstream learners like XGBoost or logistic regression expect numeric arrays, not prose snippets.  

**FeatLLM** solves exactly this gap: it asks an LLM *to write* tiny Python programs that evaluate those prose‑rules over every row and yield one‑hot fields (“rule satisfied” → 1, otherwise 0). Once those binary bars exist for every sampled study case, ordinary machine‑learning head(s) can run fast and side‑scroll‐free against fresh data *without further chat*.  

Below is a walk‑through of how FeatLLM takes raw rule strings – produced after a few‑shot context – straight through heap–level conversion until a trained θ vector produces prediction probabilities whenever you want.



---

## The pipeline in a nutshell

| Step | What happens | Key trick |
|------|--------------|-----------|
| **Generate ≈ 10 rule strings per class** | The LLM threads two–step reasoning — first its commonsense causal map between column types & task description; next it warms up on few labeled demos → k “if … then …” statements | Fixed cardinality keeps prompts short |
| **Ask the same LLM again** | Give it those raw clauses plus a skeleton function signature → it prints executable Python logic that will test each clause against a row | Leverages its training on structured programming sites |
| **Execute the program** | Run `exec()` once → get runtime API `check_rules(row)` returning an array `[b₁,…,b_R]` | No custom parsers needed |
| **Stack arrays per instance** | For every row ∈ training set build `zᵢ = [b₁,…b_R]`—a binary feature vector aligned with its own label | All predictor inputs become purely numeric |
| **Train tiny head** | Learn nonnegative weights \( \mathbf w\in\mathbb R_+^R \) so `logitᵢ = \mathbf w·zᵢ`. Softmax follows → probabilities | One line loss + SGD → no extra fine-tune |
| **Ensemble / bag massaging** | Repeat above three steps T times (`T≈20`). Each trial draws random subsets of examples/features and samples high‐temperature responses → diverse rule baskets |\( \hat p_{\text{final}} = \frac{1}{T}\sum_{t}\hat p^{t} \)|



---

## Step 1 – Speaking naturally about knowledge extraction

The initial prompt contains three parts:

1️⃣ **Basic info** – task wording (eg “Does patient show chronic heart failure?”), feature names & definitions + quick demo rows formatted as `"age is … ; gender is … ; Answer : Yes/No"`  

2️⃣ **Reasoning instruction** – chain‑of‑thought header plus two substeps  
   *#* Establish causal tendencies solely from prior knowledge  
   *#* Quote demos + reasons → final “required rules” (exactly ten)  

3️⃣ **Response instruction** – enforce an output skeleton so every clause has “feature_name operator value” format plus logical connectors (`AND`, `OR`). This alleviates downstream ambiguities when coming straight out from GPT’s diversified tokenization.



---

## Step 2 – Turning prose clauses into callable logic

Because the string grammar varies — humans occasionally write “greater than” instead of “>”— crafting hand‑written parsers becomes brittle (`regex` fails on incidental capitalisation).  

FeatLLM sidesteps this by *asking GPT* again:
```
Define python function parse_rule(row):
   # Inputs:
   #   row – dict mapping column names → values
   # Outputs:
   #   list[int] – one element per previously printed clause
   
   # YOUR METADATA HERE (name/typing/etc)
   
  # CLUES:
# CONDITION_1 : ...
# CONDITION_2 : ...
...
```

The GPT fills INLISP placeholders like  

```python
def parse_rule(row):
    r1 = int(row.get('Age') > 60)
    r2 = int(row.get('Hypertension') == True)
    ...
    return [r1,r2,...]
```

This self‑contained function is dumped back as plain text → fed into Python’s `exec()` once during initialisation (`exec(code)`), registering `parse_rule` instantly.



---

## Step 3 – Building binary barns

Once you have `parse_rule`, simply iterate over your small training set (`k`–shot):  

```python
Z = np.array([parse_rule(r) for r in train_rows])      # shape [k,R]
Y = np.array(train_labels)                             # shape [k]
```

Now every instance lives purely in an R-dimensional boolean space (*binary barrels*) ready for stochastic optimisation.



---

## Step 4 – Learning importance weights

A conventional linear head suffices:

For sample \( i \),

```math
\text{logit}_k^i \;\;\triangleq\;\;\max(\mathbf w_k,\mathbf0)\cdot \mathbf z_{k}^i ,
\\[4pt]
\mathbf p^i \;\;\triangleq\;\;\text{Softmax}\!\bigl([\,\text{logit}_1^i,\dotsc,\text{logit}_c^i\,]\bigr)
```

where \( \mathbf w_k \in \mathbb R^{R} \) are learned via standard cross‑entropy optimisation (Adam lr = 0.01).  
Constraining weights non‑negative guarantees no “mixing‐down” odds when a single satisfying rule flares up.



---

## Step 5 – Ensembling bags for robustness

Two partner sources publish wrong answers occasionally:
* Random draws of training rows  
* High temperature surface sampling gives varied yet plausible clauses  

By bootstrapping RuleBag × SampleBag repeatedly you get \( T \) independent heads \( h_t(\cdot) \).  
A full classification becomes 

```python
p_final(z) = mean([h_t(z) for t in range(T)])
```

In practice `T ≈ 20` balances performance gains against extra cost—each head still only does one dot product.



---

## Why this matters beyond fancy prompts

| Problem ↑ | Conventional solution | FeatLLM address |
|-----------|-----------------------|----------------|
| Oracle evaluation costs ↑ (N × T calls)| Feed whole batch back through GPT ➜ expensive | GPT called only during few‐shot calibration (≈30 API calls total) |
| Latency driving factor ⥤ Substitute big transformer with tiny matrix ops |
| Prompt length saturated when many columns ➜ Bagged/partial serialization removes excessive tokens |
| Spurious correlations biting with limited samples ➜ Reasoning split & prior knowledge filtering shrinks irrelevant clauses |

Benchmarks across 13 datasets showed average gains ≈ 10 % AUC over state-of-the-art tabular baselines while keeping inference time essentially identical to logistic regression.



---

## Practical tips & sanity checks

- **Validate your snippets** before full training—print first few outputs (`Z[:5]`) to catch malformed selectors (`row.get(...)` typo).
- The function returned by GPT might wrap conditions inside unexpected parentheses—Python treats them same anyway.
- If you observe *“zero variance*’s hidden dimensions*, increase \( T \); diversity will surface more useful clauses.
- For symbolic feature types (e.g., dates), ask GPT explicitly about their internal representation so your predicate uses proper comparison operators (%y%m…).

If you truly lean toward interpretability—each VIP feature equals *“Clause‐X satisfies”*—your model becomes trivially explainable even when embedded inside larger pipelines.
