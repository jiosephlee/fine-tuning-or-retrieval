## Why attention keeps running into cost walls  

Transformer models live on a single player called **self‑attention**  
(and its variants), whose computational cost scales like  
\( O(N^2)\) with the sequence length \(N\).  
Even a modest body‐weight model looking at a few thousand tokens ends
up forming scores \(\mathbf{S}\in\mathbb {R}^{N\times N}\); feeding every one
of those scores through an exponential before multiplying back against the
\(N\times d\) value matrix makes this layer soak up almost all floating‑point work during inference or training.

Adding layer depth, increasing head dimension \(d\), or extending downstream
tasks requires longer contexts – iterating over billions of token pairs blows
past bandwidth limits afforded by classical GPU memories even while fanout‑heavy multi‑head attends profitably exploit SIMD parallelism.

## Confronting Hopper’s untapped potential  

The Hopper branch shipped a couple crucial changes worth noting:

* **Tensor Memory Accelerator (TMA)** – dedicated engine that pulls fragments straight into shared memory asynchronously  
* **Warp‐group Matrix Multiply Accumulate (`WGMMA`)** – async tensor core instruction whose latency can be hidden behind any other thread activity  
* **FP8 support** – taking advantage of *four* bits exponent + *three* mantissa bits gives theoretically twice TP95s per multiply  

FlashAttention v2 never called any of these “async” arms sparingly – its producer‐consumer logic remained strictly cyclic,
leading it onto only ~35 % utilisation measured against pure GEMM kernels even on our best GPU.

## Building Firefox’s third storm   

FlashAttention 3 rewrites its core therefore saw three sweeping upgrades,
each designed directly around Hopper's architectural gifts.



### ■ Warp‐specialisation turns CUDA cores into dedicated pipelines  

* Each CTA splits its threads into two **warp groups**
    * Producer warps purely issue `TMA` loads into shared buffer cells  
    * Consumer warps own `WGMMA`s – every single multiply is already streaming data live  
* A small circular buffer synchronized via `bar.sync` lets producers pry ahead,
   releasing stalls underground native register budgets (`setmaxnreg`) so consumer lanes stay immediately occupied  

This fork removes an invisible wait every time image fetches finish,
cutting pathway latency nearly linearly proportional  
to twice the packed tile size.



### ■ Two–stage interleaving hides slow maths behind fast rows  

Inside every consumer loop two distinct jobs clash -

1. Compute \( \mathbf{S}^{(j)} =\mathbf{Q}\mathbf{K}_{j}^{\,T}\);
   Finish → find row maxima→ garbage feed exp() chain    
\[ \tilde{\mathbf P}^{(j)}=\exp(\mathbf S^{(j)} -m_j)\]  
   Crank sum–components → carry top‑k statistics  

2. Compute \( \mathbf O_i+=\tilde{\mathbf P}^{(j)}\,\mathbf V_j\)

Operational analysis found FLOPs for special functions (`exp`) lagged Tensor Core brewhouse ventuly~10× customised spec (
HNS says ∼990 TFLoP/s smooth matrix work versus ≈4 TFLoP/s pure exponents),
but doing those two tasks end exchange would oblige sitting idle otherwise.
Hence PW returns → merge multiplies ‑ recapture riches →

> **Ping‑pong schedule**  
> While consumer lane greedily runs \(QK^T_{j+1}\),
> another lane silently evaluates exponentials thrown off previous tile –
> freeing tensor cores for ongoing work without shadowing anything.



### ■ FedMe APC : getting space back via controlled low precision  

Entering real life models forces intensity artificitism –
most LP efforts obey per-tensor coefficient constants
and invariably lose accuracy wherever activations stray far out,
especially troublesome during language model training when silent few entries explode huge magnitude (“outliers”).

FlashAttention 3 adopts **block quantization + incoherent processing**

* Quantise \(\mathbf Q,\mathbf K,\mathbf V\) independently *per driver block*
    * After signing a bias offset check move new scale factor straight into score matrix-backed recurrence,
      preserving aggressive adoptive error control without extra bandwidth costs  
* Apply an inexpensive orthonormal spreader \(M\simeq D\,H\,D'\)
    * Random rows flipped (\(\pm\,1\)) + FastHadamard propagate mixes entries;
      CO[,\,] knowledge ensures dot products stay invariant,
      simultaneously balancing statistics so quantizers absorb fewer extreme tails



With these tricks Flash sits comfortably around **FP8 tensor core utilisation fully saturatiously near capacity**, raising total FLOP count towards its theoretical max while preserving fidelity bounds.

# Warp‑Specialization Made Simple – Boosting GPU Performance with Producer/Consumer Warps  

Modern deep‑learning workloads spend most of their time on *attention*.  
On GPUs attention scales quadratically with sequence length, turning it into a bottleneck even for modestly sized models.  
Recent work proof‑reading *FlashAttention* turns attention into a streamlined kernel that touches global memory only once per batch element.  
The newest iteration – *FlashAttention‑3* – pushes this idea further by taking advantage of **warp–specialisation** together with the new asynchronous capabilities introduced in NVIDIA’s Hopper “H100” GPUs (Tensor Memory Accelerator – TMA and Wave‑group GEMM – WGMMA).  

Below we walk through what *producer/consumer* warps really are, why separating their responsibilities gives a measurable \(1\!\times\!5\)–\(2\,\times\) lift, and how it all fits into an efficient attention primitive you can drop into PyTorch today.  

---

## What Are Warpgroups, Producers, and Consumers?

In CUDA’s execution model a <b>warp</b> contains 32 lanes that fire together deterministically every cycle (“SIMT”).  
When several warps operate together on one **CTA** (`threadblock`) you get a **warpgroup** – e.g., on Hopper four contiguous warps share certain resources such as specialised tensor cores or memory engines via an *asynchronous pipeline*.  
These specialized resources do **not** burst simultaneously unless told explicitly by the lane codes executing in different warps—you’re free to engineer different “jobs” per warpgroup inside one CTA.

A **producer** warp merely issues data movement commands:
```
    // asynchronously copy GMEM → SMEM with Tensor Memory Accelerator
    tma_load(Q_block)
    tma_load(K_block)
    tma_load(V_block)
```
while a **consumer** warp immediately starts computing afterwards:
```
    // run Wave-group GEMM using Tensor Cores
    result = wgmma(Q_block , K_blockᵀ )

    // expose overlapping softmax later …
```
Because producer and consumer touch distinct pieces of hardware—in Hopper’s case TMA is an independent engine whereas Tensor Cores work exclusively inside processing lanes—the two can run simultaneously without stalling each other.



---

## Why Does Separating Producers From Consumers Pay Off?

| Reason | What Happens Without Specialisation | What Happens With Specialisation |
|--------|--------------------------------------|------------------------------------|
| **Latency hiding** | Compute stalls waiting for magically fetched key/value tiles | A consumer keeps busy while producers warm up the next batch of keys/values |
| **Register pressure balance** | All threads hoard registers competing against TCA simulator ⟶ more spills | Different groups allocate their own register budgets (`setmaxnreg`) → fewer spills |
| **Unit-level island architecture** | Mixed workload leaves cache/Tex buses idle | Dedicated engines work at full throughput → better utilisation |
| **Pipeline depth freedom** | Data needs coming back before next matrix product → “single smoker” pattern | A coordinate explorer cave lifts residual pipeline depth (\(s\)-stage circular buffer) |
| **Asynchronicity exploitation** | Single threadblock LB and unwind horizon | Multiple workers interlock `bar.sync` gates making TURN right before hazards |

By forcing model designers into two clean pipelines—one handling loading and packing data via TMA and another doing math via WGMMA—the overall throughput jumps well past ordinary mathematical maxima suggested simply by counting FLOPs.



---

## How `FlashAttention‑3` Arranges Producer/Consumer Warps

Imagine an assembly line that never stops moving items because Work–stations always have something ready for somebody else:

1. **Setup**  
   • One CTA owns an \(N\times d_\text{head}\) query slice \(Q_i\).  
   • Two “specialised” warpshorts form an unsigned `producer group`. They repeatedly pull blocks \(K_j,V_j\) (while keeping \(Q_i\) resident).

2. **Producer Loop**  
   ```text
   Wait until staged KB/VB free;
   launch async_tma_load(K_j), async_tma_load(V_j);
   notify consumer group when done.
   ```
   Inside Halo’s runtime Each receptive slot “\[j % s\]” is a circular stage enabling parallelism across keys collected ahead 

3. **Consumer Loop** – classic flash routine  
  
   ```text
   Acquire Q_i;
   For each key block j:
     // first hard GEMM
     S_cur = wgmma(Q_i , K_jᵀ);   
     // local-softmax internals  
     update row-max + exponentiate → P_tilde_j;
     // second GEMM 
     O_i += wgmma(P_tilde_j , V_j);    
     // release cyclic buffers …
   ```

   Importantly every step waits only when absolutely necessary (`bar.sync`). When `S_cur` finishes early we immediately start pulling next block `K_(j+1)` while `P_tilde_j` burns through its multiply–accumulate fanout—this turns three traditionally serial operations into three overlapped streams.


### Ping–Pong Scheduling Across Warpgroups

The heartbeats between two separate producer constraints allow us even higher concurrency—this is called “ping‑pong” scheduling.
While **Warpgroup A** pulls agreeably `K_next`, producing raw scores,
**Warpgroup B** simultaneously multiplies its current probabilities against remembered values.
Effectively both halves share µseconds’ worth of *idle* cycles otherwise forever spent waiting yawn-shifts.

# **FP8 At Scale – Why Low‑Precision Significantly Speeds Attention Without Losing Accuracy**

Large language models routinely process dozens of thousands of tokens at once.
Because self‑attention grows quadratically with sequence length, even a single
token‑to‑token operation can dominate overall runtime.
Recent work has shown that you can **guarantee exact attention** while hiding
intermediate tensors inside fast on‑chip memory—see Dao et al.’s *FlashAttention*,
the first technique that fused all the needed GEMMs, reductions, and
softmax into one kernel.
The newest revision—*FlashAttention‑3*—takes full advantage of the newest NVIDIA
Gorilla‐grade Hopper GPUs.
One pillar of this improvement is **low‑precision arithmetic**, especially the
new `FP8` (`e4m3`) tensor cores introduced for Hopper.
In this post we walk through why these cores work so well for attention,
how they can be used without losing mathematical fidelity,
and what experiments underlie the reported performance gains.



--------------------------------------------------------------------

### Why an FPGA‐like single‐pass kernel can still benefit a lot from more lanes  

The mathematical core of each Transformer head remains unchanged:

```text
S   = α ⊙ Q · Kᵀ          # raw scores (α = 1/√d)
P₁ = softmax_row_gemm( S )
O   = P₁ · V              # output
```

The only way you can accelerate this without approximation is by  
**eliminating loads/store traffic between global memory (HBM)**,
and by **fusing every required operation into one shader launch**.
When you do this you inevitably rely on two kinds of specialised GPU
units:

| unit | what it does | where Hopper shines |
|------|--------------|--------------------|
| **Tensor Memory Accelerator (TMA)** | DMA from DRAM → SMEM with zero host involvement | *Async*, so CPU thread can launch loads without waiting |
| **Warpgroup Matrix Multiply Accumulate (WGMMA)** | A TMAC‐style execution engine that runs a gigantic small GEMM per warpgroup | *Async*, accepts either **FP32**, **BF16**, or now **FP8** operands |

Because both units are truly asynchronous,
you’re no longer bound by “latency first” scheduling—
you simply arrange your code so that computation keeps marching forward
while data slowly falls into place.



--------------------------------------------------------------------

### From “barely used” tensor cores to *double* throughput  

On prior Ampere GPUs the best workloads logged roughly `989 TFLOPS` per SM
in fp16 GEMMs.
Hopper’s `WGMMA`, when tuned correctly, pushes ~`1980 TFLOPS`
≈ twice the peak throughputs reported for older generations.
What makes it instantaneous fast here is an innocuous change in data layout:
the hardware now accepts only **k‑major** formatted operands when running in `FP8`.
This means an operand must be laid out so its inner dimension (`k`)
is contiguous—something that *FlashAttention‑3* handles automatically via an
in‑kernel transpose powered by LDM/STM operations.



--------------------------------------------------------------------

### The accuracy problem you get when you pack everything into just eight bits  

An `e4m3` number stores only four bits for an exponent;
the biggest representable value after rounding downwards sits around $10^5$,
a lot smaller than what normal model activations sometimes touch.
A straight “quantise every tensor once” strategy quickly breaks down:
you promptly run into overflow or loss‐of‐significant‐digit problems—especially
when your head has occasional “outliers” (`σ ≈ 10`) that dwarf most other entries.


#### Block quantisation  

A *per‑tensor* scale factor squashes all blocks behind a single global value.
If one block contains an extreme value ($>10^4$), every other entry in the same block ends up rounded too aggressively.
Instead *FlashAttention‑3* assigns its own scale per *matrix tile*:  

```text
scale_Q[i]   := max_i |Q_tile[i]|     # determined at load time
scale_K[j]   := max_j |K_tile[j]|
scale_V[j]   := max_j |V_tile[j]|
```

Each tile now gets its own generous dynamic range, drastically cutting the amount
of information lost during conversion from fp32 → fp8 without any extra register pressure.



#### Uncoherent processing  

Even after tiling you can still get unlucky—a cluster of “large” entries may sit inside one tile simply because training data happened right.
To decorrelate this effect we multiply both `Q` and `K` by a fixed random *orthogonal*
matrix `$M$`.  
Since `$M·Mᵀ = I$`, you never change any word‐exact dot product:

```text
(Q·M)(K·M)ᵀ = Q(M·Mᵀ)Kᵀ = QKᵀ            # mathematically identical!
```

What changes is what hits the limits of `e4m3`.  
Each entry becomes an *average* over many original elements weighted by ±１,
greatly dampening spectacular peaks while preserving distribution shape.
Because this mix happens in fp32 before division into subtiles,
the subsequent per‑tile scaling becomes far tighter—and your relentless cast back down goes far better.



--------------------------------------------------------------------

# Ping‑Pong Scheduling — The Art of Overlapping Softmax with Matrix Multiplications  

Deep learning models deploy transformers everywhere today—from chatbots that muster knowledge from whole books, to computer vision systems that stitch dozens of high‑resolution frames together. At their core lies *self‑attention*, a quadratic‑time operation whose performance has become a limiting factor whenever you push past tens of thousands of tokens or pixels.  

FlashAttention, introduced more than a year ago, already sped up attention dramatically by fusing its three constituent kernels—query/key dot product, local softmax, and value reduction—into a single CUDA launch that exchanges global‑memory traffic for much cheaper shared‑memory traffic. However–the key‐softmax bottleneck remained stubbornly slow on modern GPUs such as NVIDIA’s Hopper H100 chip.”  

Enter *Ping‑Pong scheduling*, a scheduler pattern built atop Hopper’s independent execution units (Tensor Cores for matrix multiplication & a separate specialized function unit for logarithms/exponentials). By interleaving these operations across warps inside a single threadblock you effectively hide the expensive exp calls behind parallel matrix multiplications—a trick that pays off milliseconds per inference call on large contexts.”

---

## Self‑Attention Revisited  

For one-head multi‑head attention you usually write  

```text
S      = α · Q · Kᵀ                            # matrix product
P      = softmax(S)                            # row‑wise exponentials + normalisation
O      = P · V                                 # another matrix product
```

A naive implementation stores `S` and `P` out backends, whereas FlashAttention keeps *everything* in shared memory and uses one custom kernel per head/query tile.  
The hardest part here turns out missing great parallelism—not because `Q·Kᵀ` itself is slow (it saturates Tensor Cores easily), but because `softmax` involves an exponential per element followed by a row sum—a pair of special–function calls run on a tiny functional core group far below Tensor Core throughput.



---

## Hopper’s Two Independent Engines  

The new Hopper architecture exposes three distinct pipelines inside an SM:

| Pipeline | Typical latency | Rough CPU ≈ |
|---------|-----------------|------------|
| **Tensor Cores** (`WGMMA`) | Gemmas live ~32 instructions | ~64 GFLOPS per SM |
| **Special Function Unit** (`exp`, `log`) | One exp ≈ few clock cycles | ~3 TFLOPS total |
| **Tensor Memory Accelerator** (`TMA`) | Invisible load pipe | Adds ion data bandwidth |

These work **asynchronously** – you fire once an operation starts it runs independently until completion causing no blockage for other routines that share registers or shared memory.



---

## Warp Specialization & Producer–Consumer Roles  

One trick before sizing the scheduler itself was *warp specialization*: split the 32 threads inside a crop-ready CTA into two mini squads.
* **Producer warps** do all memory fetches (`load Q_i`, `load K_j`, `load V_k`) via TMA.
* **Consumer warps** perform arithmetic (`WGMMA` + handcrafted reductions).

Because producers never touch registers beyond what has been loaded, compilers feel free to allocate more registers thus reducing spills for consumers—particularly important when swapping metaphorical thunks back into shared memory.



---

## Ping‑Pong Scheduling Decoded  

Imagine a single query tile \(Q_i\) being scored against every key/value block pair \((K_j\,,V_j)\).  
At iteration \(j\) three distinct overlapping stages normally exist:

| Stage | CPU ⊙ GPU Action |
|-------|------------------|
| Zero‐order (+κ) | Load \(K_j,V_j\). |
| First GEMM offline | \(S^{(j)}=Q_i·K_j^\top\). |
| SoftMax loop | Compute \(m_i^{(j)}=\mathrm{row}_{\!\! \mathrm{max}}(S^{(j)})\), \(l_i^{(j)}=\mathrm{rowsum}\!\big(e^{S^{(j)}−m_i}\big)\). |
| Second GEMM offline | \(O^{(j)}=\tilde{P}^{(j)}·V_j\). |

The original FlashAttention pipeline awaited *every* preceding operation before firing its successor—a statically serialized recipe where a few milliseconds get wasted driving down essential \(exp\) calls while Tensor Cores sit idle.



### “Ping”  
WarpGroup 0 precomputes \(S^{(0)}=Q·K_0^\top\) while WarpGroup 1 already works on accumulating \(O^{(-1)}=V_{−1}\cdot ...\)—note there is no prior dependency so it simply waits optimal waits until its job has room on SMEM.



### “Pong”  
Once WarpGroup 0 finishes transversing its first key block and reports its result losslessly back through registers into WarpGroup 1’s workspace,
WarpGroup 0 immediately kicks off its second GEMM (\(O^{(0)}=...\)) ― while WarpGroup 1 simultaneously starts loading \(K_1,V_1\).  
This staggered handshake continues roundabout until all key/value blocks finish.



In language proper this pattern amounts only *two* little synchronisation fences per iteration (“bar.sync” statements), yet each fence lets one warp group **fire its entire gemma pipeline** while another is doing slow exponents required for the underway soft max mathematical toil.



---

## Concrete Pipeline Inside One WarpGroup  

To turn this idea into code there are three tricks balanced neatly indoors your CTA:

1. **Two‐Stage Sliding Window**  
   * Keep `S_cur` produced by last iteration alive in registers until you need it later.*
   * While MATLAB calculates `S_next`, you roll out softened-out old scores through your value matrix.*

2. **Overlapping Eager Special Functions**  
   * Crucially `exp(sublim)` zero systems (~3 TFLOPS total over whole SM grid) get overlapped behind eagerly streaming TE…*

3. **Barrier–Guarded Commit**  
   * At key moments insist both FFTs finish before you commit their results back onto shared memory*  

```text
// illustrative pseudo cycle
For every key/value column pair j:
```

## What’s happened behind those meters?

### Blending GPU de­tails into software design

The Hopper architecture brings four features that were largely untapped by existing attention kernels:

| Feature | Why it matters | How it’s leveraged |
|---------|----------------|--------------------|
| **Tensor Memory Accelerator (TMA)** | Asynchronous loads from global memory into SMEM cut latency stalls | Warp groups dedicated solely to TMA moves allow concurrent data loading while other warps crunch numbers |
| **Warp‑group WGMMA** | A fused GEMM instruction that runs concurrently with logic units | Allows overlapping soft‑max exponentiation with matrix multiplications – “pingpong” scheduling |
| **FP8 Tensor Cores** | Roughly twice the FLOP capacity over FP16/BF16 spent inside an SM | Requires special operand layouts → solved via register permutation + intra-kernel transpose |
| **Register dynamism (`setmaxnreg`)** | Warps that build matrices get more register budget while TMA-warps need none | Gives best possible occupancy without sacrificing TMA latency hiding |

By splitting the CTA’s warps into producers/consumers (`warp‑specialisation`) and feeding tightly interleaved computation stages (`two-phase pipeline`), almost every cycle sees either tensor multiplication going down a WGMMA pipe or softmax circuitry firing off on registered partial sums.
That’s how they squeeze Thomson-Hopper FLOPS almost onto its roofroom.



### Making exploitation possible without re-elaborating tensors

The authors show that even though Tile-based GEMMs preserve register layout both directions (\(mn\)-major letters vs \(k\)-major needed by FP8 WGMMAs), they’re reconcilable via simple byte-swaps inside register files.
Therefore they avoid expensive transposes outwards — they pull data straight into SMEM knowing Cores will interact correctly.
