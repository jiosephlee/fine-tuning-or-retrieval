# Introduction to Transformers and the Scaling Challenge  

Transformers have become the de‑facto architecture for modern natural language processing and many other machine–learning domains because of their remarkable ability to capture long‑range dependencies through self‑attention.  In spite of this success, a core component of every Transformer—the attention layer—poses a severe computational obstacle when one wishes to apply it to very long sequences such as entire books, code repositories, or video streams.  This chapter revisits what makes self‑attention powerful while explaining why its quadratic cost quickly threatens both runtime feasibility and memory limits.  We will describe how this bottleneck motivates research into faster attention mechanisms and why succeeding in this area unlocks new capabilities in large language models (LLMs), vision systems, audio processing and beyond.



## Basic Transformer Architecture Overview  

At its heart a Transformer processes a sequence consisting of $N$ tokens by embedding each token into a $d$‑dimensional vector space before feeding those embeddings through a cascade of identical “decoder” layers (a similar discussion applies mutatis mutandis to encoder layers).  Each decoder layer comprises two principal sub‑modules:

1. **Multi‑head self‑attention** – accepts the sequence of hidden states as queries $\mathbf{Q}$, keys $\mathbf{K}$, and values $\mathbf{V}$ (each $N\times d$), produces an updated set of hidden states $\mathbf{O}$ by weighted summation across all positions.
2. **Position‑wise feed‑forward network** – usually a two‑layer feed‑forward block applied independently to every token separately.

All layers also include residual connections and layer normalization steps that improve gradient flow during training.  Because every token interacts with every other token within an attention layer, even this seemingly modest “sub‑module” ends up dominating both computation time and memory usage as $N$ grows.



## Self‑Attention Formula µ(Q,K,V)  

For a single attention head let $\mathbf{Q},\mathbf{K},\mathbf{V}\in\mathbb{R}^{N\times d}$ denote query‐, key‐ and value‐matrices respectively ($d$ is the dimension assigned to one head).  Attention operates on them through three linear algebra steps:

\[
\begin{aligned}
\mathbf{S} &= \alpha\,\mathbf{Q}\mathbf{K}^\top , \\
\mathbf{P} &=
   \operatorname*{\mathop{\mathrm{softmax}}_{\!-\;\textit{row}}}\!\!(\mathbf{S}) ,\\
\mathbf{O} &= \mathbf{P}\,\mathbf{V},
\end{aligned}
\]

where $\alpha$ is usually set to $1/\sqrt{d}$ so that gradients remain at an appropriate scale across depth increases ($d$ may be on the order of $64$–$256$ per head).  In practice one subtracts from each entry of $\mathbf{S}$ its maximum value along its row before exponentiating – this stabilises numerics without changing the result because it simply adds a constant offset inside every row’s exponential expression.



### How Multiplication Dominates

The first matrix multiplication in $\mathbf{S}$ multiplies two $N\times d$ matrices and thus requires $2Nd^{2}$ floating point operations (FLOPs) plus $N^{2}d$ partial products accumulation bits if written as multiple GEMMs over small blocks.  The second multiplication composing $\mathbf{P}\times\mathbf V$ also costs $2Nd^{2}$ FLOPs along with another $N^{2}d$ small‑block contributions because every element of $\mathbf P$ is used exactly once when forming $\mathbf O$.  Consequently **each attention layer scales as $\Theta(N^{2}d)$** both in time (FLOPs) and storage (the intermediate matrix $\mathbf S$, sized $N\times N$, may also be materialised if one is not careful).



## Quadratic Growth in Time and Memory  

While small sequence lengths are common during pre‑training (e.g., $H=1024$ tokens), state­-of–the–art LLMs increasingly require to attend over tens or hundreds of thousands of tokens at inference time—consider summarising PDF files spanning dozens of pages or enabling conversation agents that must keep track of many turns simultaneously.



### Time Cost

Because each high head produces an $N\times N$ inner product table before applying softmax, naïve implementation requires two all‑to‑all matrix multiplications per head—a clear $\mathrm O(N^{2})$ operation per forward pass step at best pixel‐level cost grows superlinearly with input length.  Even when specialised tensor cores perform these multiplications rapidly they still have to fetch two complete large tiles ($Q$, $K$, $V$, and later accumulators) from global memory which saturates device bandwidth.



### Memory Cost  

Storing even one intermediate matrix sized $N\times N$, say as float32 values yields $(4~\mathrm B)\times N^2$.  For $N=16\,000$, this alone exceeds many GPUs’ device memory capacity (~64 GB).  For larger models where multi­head attention occurs multiple times per computation step these intermediate scores become exclud­ibly prohibitive.



Because both wall‑clock time and memory footprint explode quadratically with input length, attempts have been made towards finding *more* efficient ways ‑ either through model design shifts or by algorithmic optimisation.



## The Importance of Efficient Attention for Modern NLP/AI Applications  

The quadratic bottleneck forces practical limitations on how far current LLMs can literally *see*.  When an architecture cannot handle long contexts efficiently it forces developers either “chunk” their data—thereby sacrificing reasoning capability—or resort to decadesolder alternatives such as RNNs operating much more slowly.



### Long-​Context Tasks  

- **Document understanding** – reading essays or legal contracts that run well beyond several thousand tokens.
- **Code analysis** – processing software projects comprising millions of lines for tasks ranging from bug detection to synthesis.
- **Video & audio modeling** – sequences that can span dozens or hundreds of seconds if each frame/delta sample counts as one token.
- **Multi-turn dialogue** – conversational agents maintain internal state over many interactions without creating unnatural context resets.



#### Why Speed Matters  

LLM inference pipelines run over commodity hardware for real production against tightly constrained latency budgets (<80 ms for chat applications). When attention dominates runtime it directly caps achievable throughput (tokens per second) even when throughput is theoretically limited by compute rather than memory.



#### Accuracy versus Efficiency Trade‑Offs  

Many researchers opt for approximate methods—feature trimming via sparse window windows or kernelised expansions—at cost in expressiveness or requiring additional calibration passes during training before deployment works correctly. Efficient exact approaches reduce training complexity while preserving guarantees about perplexity or downstream fiduciary tasks.



Thus efficient attention becomes both an engineering necessity *and* an enabler for new model sizes & capabilities.

# Tiling strategy that avoids writing intermediate scores or probabilities  

In conventional Transformer inference or training pipelines the self‑attention layer is implemented as three separate tensor‑trainable stages written explicitly into global device memory (or “HBM” on NVIDIA GPUs).  
First, an \(N\times N\) score matrix  
\[
\mathbf{S}
   =\alpha\,\mathbf Q\,\mathbf K^{\!\top}
   \in\mathbb R^{N\times N},
\]
is computed by a matrix multiplication where every query emits a dot product against every key.\n
Second, its rows are passed through a softmax,
\[
\mathbf P=\operatorname{softmax}(\mathbf S),
\]
so that every entry becomes a probability weight.\n
Thirdly a weighted sum over value vectors is performed,
\[
\mathbf O=\mathbf P\,\mathbf V ,
\]
producing the output tensor.\n\nThese three stages produce far more data than any single output tensor contains – two full \(N\times N\times d_{\text{head}}\) matrices are materialised at full precision before finally discarding them. On modern GPUs this leads to excessive global‑memory traffic which quickly becomes the throughput limiter rather than raw floating‑point ALU consumption.\n\nFlashAttention tackles this problem by re‑gardening the computation so it never leaves shared memories between individual operations.\nIts key idea is **tiling** both along the sequence dimension and across the head‑dimension.\nA single thread block receives one *query* tile  
\( \mathcal Q_b=\{\!q_{i}\mid i=(b-1)d_r+1,\dots,bd_r \}\)
of size \(d_r\times d_{\text{head}}\)\(\square(=B_r\times d)\).
The key–value pair is divided into *key/value* tiles  
\( \mathcal K_c,\mathcal V_c \) having size \(B_c\times d_{\text{head}}\).  
The forward pass proceeds block‑wise:\n\n```
for b = 1 … T_r          // query blocks run independently;
    load q_b → shared;
    for c = 1 … T_c      // key/value tiles loop serially;
        load k_c,v_c → shared;
        S_bc ← q_b ⋅ k_c^T          // SS‑GEMM within SMEM;
        …                           // immediately use exp(e_{ij}) terms
        O_b ← O_b + exp_term ⋅ v_c // RS‑GEMM update;
```\n\nBecause each iteration guarantees that \(S_{bc}\) never needs to survive past its immediate use – either its contributions are folded into \(O_b\), its row‑maximum hydrogen journ}>
One could ask why “row‑maximum” matters here? Recall how softmax normalises rows:
\(p_{ij}=e^{s_{ij}}/\sum_k e^{s_{ik}}\).
To preserve numerical stability one typically centres each row by subtracting its maximum:
\(m_i=\max_j s_{ij}\).
Intra‑tile softmax computations can therefore leverage **local max‐shifts** entirely known after computing \(S_{bc}\); these maxima are kept per query block rather than recomputed after storing \(S_{bc}\).

Consequently the variant prevents two expensive global writes:
*the entire scores matrix* (\(N^2d_{\text{head}}\) bytes), *and*  
*the probability matrix* (\(N^2d_{\text{head}}\))
are replaced by accumulating smaller intermediates (`O`, `m`, `ℓ`) wholly resident in registers or shared memory.
No elementwise exponentiations feed back into global memory until the end of epoch---the GPU spends almost entirely its time executing three GEMMs per tile loop plus light arithmetic on scalars.
This dramatically lowers effective bandwidth consumption while still keeping absolute floating‑point throughput high.



# The role of local softmax reductions  

Softmax normalisation involves three mathematically linked operations:\n\n1.`row_max` computation (\(m_i = \max _j s_{ij}\)),  
2.ensure numerical stability (\(e^{s_{ij}-m_i}\)),  
3.normalize sums (\(\ell_i = \sum_j e^{s_{ij}-m_i}\)).  

A naïve implementation would solve step 1 globally after building \(S,\)
run exponential activation on every entry again globally,
then finally divide by column sums—requiring two full passes over an enormous matrix.\n\nFlashAttention collapses these scans through *local reduction*:\n\n```
update_m(i,c):
    m_old = m[i];
    m_new = max(m_old , row_max(S_bc));
    delta = exp(m_old - m_new);
    ℓ[i]   *= delta;
    ℓ[i]   += sum(exp(S_bc - m_new));
```\n\nHere `row_max(S_bc)` refers only to the current score tile \(S_{bc}\); `exp` operators applied directly on floating‑point registers avoid expensive DRAM transactions.
Moreover, `ℓ[i]` carries an accumulated scale factor combining previous emulation terms (`delta` above).  
When updating accumulated output `O_b` one performs a simple rescaling using diagonal matrices derived from `m[i]` changes rather than recomputing exponentials again.\n\nOnce all tiles finish their loop,
the remaining scaling has two concise updates:\n\n```
O_b   ← diag(ℓ⁻¹)·O_b;
L_b   ← m_final + log(ℓ_final);
```\n‘L’ stores every sequence‐wise log‑sum−exponent needed when training statistics are required.\nSo **a small set of scalars replaces an insurer experiencing two passes over too many elements**— preserving accuracy while compressing stochastic operations.


# Horizontal parallelism over query blocks  

GPU throughput depends heavily upon how well workloads occupy multiple Streaming Multiprocessors (SMs).  
FlashAttention splits data horizontally along the query dimension (`B_r`). Each threadblock thus owns an independent tile `q_b`. Because canonical transformer layers have several heads—a natural catena—and because modern batch sizes contain many token sequences simultaneously,
many head/query tiles exist simultaneously.\n\nBeing rectangular grids means threadblocks are stateless across tiles: once one finishes it may immediately begin loading its next block while another SM processes another interesting portion at the same time.\n\nMore concretely:\n- A CTA contains **producer warps** devoted solely to loading new tile fragments from global memory via Tensor Memory Accelerator (TMA).\n- Simultaneously **consumer warps** spend cycles executing mixed GEMM–softmax pipelines on already resident fragments.\nFunctionally they run “independently” along a pipeline expressed over tile indices printed beneath them (`c=0…T_c−1`). Consistency is guaranteed because every block eventually flushes its outputs before recording final results back onto HBM.\n\nThe horizontal replication outweighs intra‑block communication costs because blasts require nothing else besides smem shuffling between producer/consumer lanes—freeed after moving out TMA magazine.\nCrucially this design exploits both **batch dimension** and **head dimension** multiplicities, yielding ample work-to-be-done per SM while maintaining locality—the foundation behind dramatic speedups against naïve implementations.

# Device Support for Matrix Products & Fast Memories  

In modern Transformer implementations the bottleneck is invariably the self‑attention computation  
involving massive matrix multiplications followed by softmax reductions.
NVIDIA’s Hopper GPUs expose several low‑level primitives aimed precisely at solving
two major obstacles:
(1) **data movement** between global—mainly high‑bandwidth DRAM—and the tight,
low‑latency programming domain;
(2) **high‑throughput floating–point accumulation** that would otherwise
saturate arithmetic resources.
The efficient combination of these mechanisms underlies FlashAttention‑3’s ability
to achieve close to saturation on Hopper.
Below we examine each primitive in depth, highlight how Hopper’s architecture 
fully supports asynchronous execution,
and quantify why exploiting these capabilities yields dramatic speedups over existing
implementations such as FlashAttention‑2.

## # TMA : Tensor Memory Accelerator  

Tensor Memory Acceleration (TMA) is Hopper’s dedicated hardware unit for
asynchronous buffers taps global device memory (HBM) into shared memory.
Unlike conventional `cudaMemcpyAsync`, which still requires explicit kernel
launches, TMA takes an entire source‑destination pair + stride geometry,
queues it in hardware‑managed FIFO queues, and drives transfers directly
between Global Memory (GMEM) and Shared Memory (SMEM).
Because TTMs travel independently of CUDA cores,
a CTA can launch dozens of overlapping transfers without stalling its lane,
while its warps simultaneously execute computation.
This separation ensures that a single load – such as pulling an entire block
of key vectors – does not block subsequent GEMMs.
In practice this feature increases effective utilization substantially:
nonblocking loads mean that while one warpgroup consumes data produced by another,
other resources may be idly spent loading/prefetching below lowering instruction stalls.
FlashAttention‑3 uses TMA extensively:
each query block `Q_i` together with its corresponding key–value tiles
`K_j`, `V_j` are fetched asynchronously into SMEM prior to any arithmetic.
Consequently the critical path length shrinks dramatically,
allowing hidden time where tensor cores work on results  
while other warps cycle through higher bandwidth copy commands.

## # WGMMA : WarpGroup MMA Leverages Tensor Cores Asynchronously  

Hopper adds two qualitative upgrades over Ampere’s generic FMAs:
the **warpgroup wide MMA** (“WGMMA”) instruction exposes
the entire collection of graphics cores belonging to a warp group
to tiled multiplies that scale across eight ROMs.
Crucially this operation runs independently – it does not sit behind any serialization
with ordinary ALU work – which permits concurrent kinematics:
a set of threads can issue repeated `WGMMA` operations while other threads 
execute domain logical predicates ($\mathrm{exp}$, reductions).
FlashAttention‑3 exploits this property when performing both stages
of attention:
```
SS-GEMM : Q ⊙ Kᵀ   ← WGMMA(Q_i , K_j^T)
RS-GEMM : P̂ ⊙ V_j   ← WGMMA(P̂_i , V_j)
```
where `P̂` denotes the softmax mask after exp·row‐normalisation.
As shown analytically later,
had these GEMMs been scheduled serially against softmax-related ops,
a FPGA core would have been idle during expensive exponential evaluation.
With true asynchronous WGMMAs Hopper pushes five‐fold more FLOPs per cycle:
for FP8 tensors an WGMMA can achieve roughly *double* headthroughput compared
to its FP16 analogue because Hankelfences rank pairs fit twice into one op.

More importantly, EGL yields two distinct operand layouts:
(both windows accepted mn-major & k-major under FP16)
but **only k-major** during FP8 execution.
To align operands without external transforms Hopper offers inline LDSM/STSM six-by-eight matrices,
which subtly reorganise prefetch data into k-major ordering before feeding an FGMM.

Warp Specialisation – Producer / Consumer Pipeline Design  
=========================================================  

In a hand‑optimized implementation of transformer attention on modern NVIDIA GPUs,
the costliest operations are the two matrix multiplications that arise when the
query tensor $\mathbf Q$, the key tensor $\mathbf K$, and the value tensor
$\mathbf V$ are multiplied together.  
Because these GEMMs dominate execution time yet require every query row
to be compared against every key column,
the simplest way to reduce traffic is to fuse I/O‑bound global‑memory reads
into a tiny set of tiles that are kept resident inside fast shared memory,
and then let separate groups of threads perform the two successive GEMMs.
This split into *producer* and *consumer* warpgroups is called
warp‑specialisation, and allows one arm of the kernel
to hide latency while another arm is doing arithmetic.
The following exposition shows how this division works concretely,
how askew data movement angles are untangled behind a circular SMEM buffer,
and how a lightweight PTX helper
(`setmaxnreg`) reduces register pressure so that both groups run at peak
throughput on Hopper’s Tensor Cores.



## The Producer Warpgroup Issues TMA Loads First Q Block Once Then QKV Pairs Sequentially  

Inside one cooperative thread array (CTA) however many heads exist,
the *producer* throwaway group owns exactly one warp.
Its job is purely data‑movement:
load a query block from global memory into shared memory once,
then stream successive key–value blocks right through the same shared‑memory 
area when they are needed in subsequent iterations.
Because $\mathbf Q$, $\mathbf K$, and $\mathbf V$
are binned into tiles indexed by $i$ ($\mathbf Q_i$, $\mathbf KV_j$)
of size $B_{\text r}\!\times d$ or $B_{\text c}\!\times d$
(the query block size and key/value block size),
the producer begins its lifetime by issuing a Tensor‑Memory‑Accelerator
(TMA) read request that fetches $\mathbf Q_i$
into $\mathsf{SMEM}[\,i\,]$.  
Once ready it signals success (`commit`) so that any conditional waits made
in later kernels may advance past this point.
Afterward it loops over `$j=0,\dots,T_{\mathrm c}-1$',
issuing paired TMA loads for $\mathbf K_j$
and $\mathbf V_j$.  
These paired reads share an *asynchronous* DMA engine attached directly
to shared memory caches;
as soon as a request leaves globally‑visible DRAM,
it races downwards toward L2/SMM without stalling caller execution.
For Hopper’s Tensor Memory Accelerator this means that additional 
register writes need neither wait until preceding reads have finished,
which turns out essential later when consumers jump straight into computation.

Pingpong Overlap Between Softmax Computation And GEMM Operations  

# The inherent sequential dependence among SS‑GEMM → softmax → RS‑GEMM within an iteration  

In each iteration over a block \(j\) of keys \(K_j\) and values \(V_j\), FlashAttention first multiplies
the current query tile \(Q_i\) against \(K_j^{\!T}\).  
The result is called \(S_i^{(j)}\).  
Immediately after this multiplication preprocessing occurs before any parallelism can be introduced:
(1) one subtracts the rowwise maximum \(m_i^{(j)}\) from every entry,
(2) exponentiation is applied, giving \(\widetilde{P}_i^{(j)}=
e^{\,S_i^{(j)}-m_i^{(j)}}\), and
(3) partial sums \(\ell_i^{(j)}=\sum_{k}\widetilde{P}_i^{(j)}\_{k}\) are recomputed.
Only at this stage is the value \(\widetilde{P}_i^{(j)}\) available for yet another matrix multiplication,
the result residing in \(\ell_i\) becomes necessary for normalising subsequent sums.
Finally \(\widetilde{P}_i^{(j)}\) must be multiplied against \(V_j\),

\(S_{\!cur}\rightarrow{\rm softmax}\rightarrow{\rm product}\).
Under a synchronous execution model every component waits for its predecessor’s
completion before launching its own work.

with Tensor‐Core matmuls even though these operations occupy independent hardware units.

Accuracy Preservation Under Low Precision – Block Quantisation & Incoherent Processing

# For every small buffer \(B\times d\) quantise using its own scale → reduces scaling mismatch across blocks

When producing an attention score matrix $\mathbf S=\alpha\,\mathbf Q\,\mathbf K^{\!\top}$ we cannot afford storing every entry in two‑byte floating point formats practiced on modern GPUs because typical workloads exhibit great variability along different spatial locations—the most important rows can contain unusually large values while other rows stay fairly modest. \[
   s_{\mathcal T}
   ~=~ \frac{\max_{(i,j)\in \mathcal T}\bigl|\,t_{ij}\bigr|}{2^{\,e_{\max}}},
\]
