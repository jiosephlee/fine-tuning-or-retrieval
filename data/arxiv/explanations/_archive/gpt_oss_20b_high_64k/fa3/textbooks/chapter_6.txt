# The inherent sequential dependence among SS‑GEMM → softmax → RS‑GEMM within an iteration  

In each iteration over a block \(j\) of keys \(K_j\) and values \(V_j\), FlashAttention first multiplies
the current query tile \(Q_i\) against \(K_j^{\!T}\).  
The result is called \(S_i^{(j)}\).  
Immediately after this multiplication preprocessing occurs before any parallelism can be introduced:
(1) one subtracts the rowwise maximum \(m_i^{(j)}\) from every entry,
(2) exponentiation is applied, giving \(\widetilde{P}_i^{(j)}=
e^{\,S_i^{(j)}-m_i^{(j)}}\), and
(3) partial sums \(\ell_i^{(j)}=\sum_{k}\widetilde{P}_i^{(j)}\_{k}\) are recomputed.
Only at this stage is the value \(\widetilde{P}_i^{(j)}\) available for yet another matrix multiplication,
the result residing in \(\ell_i\) becomes necessary for normalising subsequent sums.
Finally \(\widetilde{P}_i^{(j)}\) must be multiplied against \(V_j\),
producing a contribution \(\Delta O_i^{(j)}=\widetilde{P}_i^{(j)} V_j\)
to the output tile \(O_i\).  

Because every phase depends directly on previous outputs—
the second matrix multiply requires \(\widetilde{P}_i^{(j)}\), which cannot appear until
both subtraction and exponentiation are complete—this loop contains a strict data dependency chain
\(S_{\!cur}\rightarrow{\rm softmax}\rightarrow{\rm product}\).
Under a synchronous execution model every component waits for its predecessor’s
completion before launching its own work.
Resulting threadblocks idle whenever the exponent operation cannot keep pace
with Tensor‐Core matmuls even though these operations occupy independent hardware units.
This serialisation yields an imbalance that degrades overall utilisation,
especially visible when comparing raw GFLOPs required for multiplication against
ferocious limits imposed by special-function throughput on Hopper GPUs where,
for example,
exponential evaluation furnishes merely a few tera‐operations per second
compared against several hundred tera‐operations per second for matrix multiply:
\(F_{\rm exp}\approx3\,{\rm TFLOP/s}\ll F_{\rm WMMA}\approx989\,{\rm TFLOP/s}\).  

Hence any opportunity delivering concurrent progress on both paths without violating data availability
is critical, motivating pipelined execution schemes capable of overlapping computations tiled
across key-value blocks while one pair produces data necessary for another pair’s subsequent step.


# Two‑stage pipeline idea where product matrix (\(\pi\)) from iteration \(j\) feeds runs while next SS‑GEMM runs ahead  

A simple yet powerful way to break this dependency chain is to consider two iterations linked through hidden registers,
forming what FlashAttention refers to informally as a “two–stage” pipeline.
During the processing of block \(j\), \(Q_iK_j^{T}\)—the first WWCR—is launched.
The kernel does **not** immediately wait for its result;
instead it commits the asynchronous query choose into shared cache,
then immediately issues a second WMMA call evaluating \(Q_iK_{j+1}^{T}\).
By leaving both computations outstanding simultaneously,
the kernel keeps all Tensor Cores busy even whilst computing intermediate entries.
In parallel, once vector \(V_j\) reaches SMem,
the partial sum produced during previous hard SUM (\(\Delta O_i^{(j)}\))
is fed into a subsequent RTxW GMMA equation synchronously.
When both WMMA operands finish,
softmax evaluation proceeds entirely on L3 registers—
subtracting rowwise maxima accumulated until current stage,
calculating exponentials and row sums—all performed entirely outside SRAM access cycles.
Because these softmax calculations consume roughly half a cycle per scalar compared
to multi–fop Tensor Core operations,
their delay hides behind succeeding iterations’ primary multiplication pipelines),
thereby diminishing idle kilometres created by serial reservations.


Concretely expressible along pseudo operational steps:
1| Compute ‑ `S_cur ← Q × K_j^T`,
   launch asynchronously;
2| Launch `S_next ← Q × K_{j+1}^T`, also asynchronous;
3| While awaiting `S_next`, temporarily keep buffer values present;
4| Execute RS–WGMMA `O ← O + P_cur × V_j`;
5| Return accompanying statistics (`m`, `ℓ`) back into registers;
6| Proceed loop onto subsequent index pair `(j+1 , j+2)` following exactly the same schedule.



A fundamental point is that all kernel stages remain valid because new values required by later iterations never reach register storage until all depended constants complete.
When holding partial sums through registers prone to overflow–wise early‐flush,
FP32 accumulator space prevents catastrophic precision loss –
but small detail crucially bearing on quantisation conditions addressed later.
