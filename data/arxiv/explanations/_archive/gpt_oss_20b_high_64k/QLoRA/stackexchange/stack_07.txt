Answer:
**How Paged Optimizers keep a 65 B‑parameter model from blowing up the GPU**

When we train gigantic transformers with very long sequences three different kinds of data live on-device at the same time  

| data                     | why it appears                                                      | typical peak                                                                                  |
|--------------------------|----------------------------------------------------------------------|------------------------------------------------------------------------------------------------|
| **activations**          | produced while running the forward ∧ backward passes                | split into “chunks” by gradient checkpointing : only one chunk is kept at any instant          |
| **gradients**            | accumulated during reverse-mode autodiff                              | partly co-resident with the current chunk – usually small                                   |
| **optimizer state**      | momentum / Adam “momentum” / “exp-avg-square” tensors              | one copy per parameter – far larger than an activation chunk                                 |

The very last column is what matters most for an OOM spike.



--------------------------------------------------------------------

### Why gradient checkpointing itself does not solve everything

Checkpointing does relieve you from keeping all activations together.
It keeps only *one* slice in RAM while it recomputes everything else.
Consequently every slice needs **auxiliary CPU/GPU workspace** during back-propagation –
e.g., a temporary tensor that accumulates partial gradients inside an operation or space reserved 
inside cuBLAS.
When you process a big mini-batch (`batch_size ⋅ seq_len` is huge) those temporaries can add 
up more than the size of a single slice.
If you want a handful ($C ⋅{\approx}32)$ slices simultaneously 
in flight,   
the combined workspace suddenly grows 
by tens of gigabytes – enough to overflow a 48 GB card.



--------------------------------------------------------------------

### Enter NVIDIA Unified Memory

Unified Memory (“UM”) lets CUDA decide *which* CUDA address ranges stay 
in device RAM and *which* parts fan out into host RAM.
Practically speaking:

• The tensor allocation request (`cudaMallocManaged`) 
asks that CUDA manage that block internally.

• If the device runs out of free RAM while executing kernels,
CUDA will asynchronously move blocks marked ​“managed’’ away 
from the GPU into system DRAM.

• When some kernel later touches one    
of those blocks,    
a *page-fault* causes CUDA (“pages”) it back immediately.

• Importantly—the programmer never has access 
to driver flags;
all we do sees tag nothing special locally.


In QLoRA’s *Paged Optimizer*,  
all ​“optimizer state’’ tensors (moments kept  
by Adam/Warmup/LoRA) are allocated via UM:
```python
for group in optimizer.param_groups:
    for p in group['params']:
        # Make every auxiliary tensor manager-policed.
        p.data = p.data.to('cuda', non_blocking=True)
        # Allocate supported state also onto managed heap …
```

The reason this works well  
is that an updater kernel touches every optimizer tensor   
only ∎ once per whole mini-batch whereas    
an activation chunk gets touched many times during repeated substeps —   
placing bulk buffers safely outside device RAM  
until needed later.
