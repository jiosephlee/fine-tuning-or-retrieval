\title{A Textbook about the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

Motivation behind Efficient Finetuning  

In recent years large‑language models (LLMs) have become highly versatile when trained on big corpora and fine‑tuned on domain‐specific tasks~\citep{min2021metaicl,wei2021finetuned,ouyang2022training,wang2022super,wang2022self,liu2022few}. Yet even state‑of‑the‑art pretrained models often fail when confronted with specialised dialogue or narrow domain questions unless they undergo instruction following finetuning~\citep{ouyang2022training,bai2022training}. The difficulty arises primarily from the computational scale required during back‑propagation when updating every weight in a multi‑billion parameter network.\par

# Need for Task–Specialized Behaviour  
Finest tuning during supervised instruction following turns off‑the‑shelf general knowledge into an agile agent capable of answering user prompts coherently while adhering to constraints imposed by data distribution or safety requirements~\citep{ouyang2022training,bai2022training}. Each target task—whether it concerns medical knowledge extraction or dialog management—introduces implicit priors absent from generic pretraining corpora. Empirical studies demonstrate dramatic gains when models receive carefully curated instruction–response pairs~\citep{bai2019openimprove}. Consequently researchers who wish to employ an LLM for any new application typically must retrain all network parameters against an annotated dataset tailored for that application.\par

# Memory Bottleneck During Gradient Descent  
The most serious barrier stems from how gradients propagate during back‑propagation through gigantic weight tensors.\par 
Given a linear projection $\mathbf X\,\mathbf W$, scaling factor $\mathbf X$ remains untouched while $\mathbf W$ is updated by computing $\partial E/\partial \mathbf W$. Each forward pass already stores $\mathbf W^{BF16}$ along with intermediate activations used during backpropagation; retrieving these tensors necessitates holding several copies simultaneously in device SRAM~--- often dwarfing the storage needed merely for weights themselves.\par 
In practice even parameter–efficient strategies like Low‑rank Adapters leave most of their memory burden fixed—the majority resides in storing *activations* rather than additional learnable parameters~(cf.~Section “Memory Requirement of Parameter‐Efficient Finetuning” where \$567\$ MB allocated just for adapter gradients versus \$26\$ MB expressly required for adapter weights itself). Consequently adding additional adapters improves expressivity almost linearly without appreciable memory penalty.\par 
Beyond activation savings, naive full‑parameter trellises cause infeasible latency spikes whenever minibatches contain long sequence lengths—a phenomenon known colloquially as “memory spike”. To avert out‑of‑memory errors researchers had historically resorted either to aggressive gradient checkpointing~(which trades compute time) or huge multi‑GPU clusters—in short, neither were realistic options on consumer hardware.\par

# Typical Full‑Parameter Finetune Resource Estimates  
To quantify these barriers let us focus upon LLaMA’s largest public release—a \$65B\$ component tokenizer architecture.\par 
Calibration experiments reported during publication reveal that fully updating every weight field while retaining a conventional bfloat16 precision requires **more than \$780\$ GB** of contiguous GPU memory (\textit{i.e.,}\ $\mathrm{\langle54{\rm B}\rangle}$ out of which approximately \$25$\mathrm{k}\!GB$ resides just within weight tensors themselves). This number also subsumes considerably larger buffers generated during backward passes and optimizer state maintenance.\par 
For models two orders smaller (for instance \$7B\$) even with aggressive checkpointing an individual machine fails past sequences longer than several hundred tokens if naively updated throughout.\par These figures underscore why almost every large model team resorts now either to distributed training frameworks (~50 GPUs) or “parameter‐efficient” patchworks that tolerate reduced accuracy penalties over feasibility gains.\par

Foundations of Model Quantisation  

The goal of model quantisation is simplest one word: **shrinking memory without losing too much accuracy**.\nLow‑precision representations replace the expensive floating‑point tensors that traditionally inhabit GPUs or accelerators with far more compact alternatives such as packed binaries or custom fractional formats while still enabling reliable inference at roughly the same speed.\nIn what follows we dissect how this transformation happens step by step—from a naive mapping onto a fixed number of bit symbols all the way up to how it changes a model’s overall bit‑budget.\n\n# Conventional \(k\)-bit Integer/Floating‑Point Conversion\n\nWhen an attacker first introduces an ensemble primitive called “\(k\)-bit representation”, what really changes is twofold:\n1) **the dynamic range** covered by that representation and 2) **the granularity** you have over those ranges.\nWhile floating‑point implies two parts—a sign bit, an exponent field and hidden mantissa—the word “integer” here simply means *nearest‐Neighbour hyperplane partition*.\nFor classic signed \(8\)-bit integers you can represent every odd number between \(-128\) and \(+127\); note how your step size equals \(1/(2^7)\!-\!1/(2^7)\sim1/128\). Any operation performed directly on an array encoded this way would immediately change its meaning.\nHence the standard remedy is **normalisation**.\nGiven any floating‑point matrix \(X^\mathsf {FP\,16}\) (or typically \(X^\mathsf {FP\,32}\)) you look at its maximum absolute entry,\[\n      \operatorname {absmax}(X)=\max _i |x_i|,\]\nand then rescale every value so that it falls squarely within a chosen target symbol space.\nIf you target signed eight‑bit integers whose span equals \([-127,+127]\) you will create a cheap scalar \(c^\mathsf {FP\,16}\), commonly dubbed a *scale*:\[\n        X^\mathsf {Int\,8}= {\rm round}\!\bigl(c^\mathsf {FP\,16}\!\cdot X^\mathsf {FP\,16}\bigr),\qquad {\rm where }~~c^\mathsf {FP\,16}=\frac{127}{\,{\rm absmax}(X)}.\]\nNote three implicit benefits:\n• All entries become an exact multiple once rounded\n• The choice \(127/\operatorname {absmax}(X)\) guarantees you never print larger integer symbols than your dtype allows\n• A single scalar can magically describe roughly eleven decimal orders if your floating‑point mantissa happens to live inside \(a_{\mathcal N}=~[-1,+1]\).\nYou retrieve your approximate real relation simply by division again:\[\n     {\rm dequant}\bigl(c^\mathsf {FP\,16},~X^\mathsf {Int\,8}\bigr)=\frac {X^\mathsf {Int\,8}} {c^\mathsf {FP\,16}},\]which roughly maps back toward exactly what you started with before you popped it off its cryptographic shell.\nThus always remember:\n*In practice one never truly enfranchises \(k\)-bit integer arithmetic*;\nsummation/cross‑product operations happen later at higher mantissa precision (often BFLOAT16), while the inset relational abscissa acting only during forwarding/caching remains handwoven.

Parameter Efficient Fine–Tuning via Low‑Rank Adapters  

# Low‑Rank Adapter Algebraic Form  
The core idea behind low‑rank adapter (LoRa) finite‑tuning is reformulating an existing linear projection $\mathbf{W}\in\mathbb R^{h\times o}$ so that its trainable portion occupies far fewer degrees of freedom than $\mathbf{W}$ itself has. If $h$ denotes the hidden dimensionality and $o$ denotes the output dimensionality—as occurs throughout transformer layers—then directly optimizing $\mathbf{W}$ would demand $h\times o$ weights and incurs exact same update costs and storage overheads as fully fine‑tuned training.  

A typical linear call computes  
\[
\mathbf{Y}\leftarrow \mathbf{X}\mathbf{W},
\]
with $\mathbf{X}\in\mathbb R^{b\times h}$ representing $b$ tokens batched together \(b\) being sequence length plus potentially multi‑turn dialogue contribution).  
In loRa fashion an extra “adapter” term is superimposed on top of the primal computation:
\[
\boxed{
    \mathbf{Y}
    ~=~
    \underbrace{\mathbf{X}\mathbf{W}}_{\text{Frozen pre‑trained}}
    ~=~
    \underbrace{\bigl(\mathbf{X}\mathbf{W}\bigr)}_{\text{fixed}}
    ~=~
    \underbrace{\bigl(\mathbf{X}\bigr)
                +s\,\bigl(\,\mathbf{X}\,\underbrace{\mathbf {L}_{1}}_{\in\,\mathbb R^{h\times r}}\,
                \underbrace{\mathbf {L}_{2}}_{\in\,\mathbb R^{r\times o}}\bigr)}_{\text{$s$ scales $\boldsymbol{s}$},
}
\]
where $r$ (\emph{$r \ll h,o$}) is called the rank and $s$ is an optional scalar that serves either as an initial scaling factor or simply absorption control for magnitude corrections if desired (\emph{s}=0 would nullify the adapter). The product $\mathbf {L}_{1}\mathbf {L}_{2}$ supplies precisely $h\times r+r\times o$ learnable coefficients—potentially two orders smaller than even a compressed version ($8$‑bit) representation would require—yet provides nontrivial flexibility for adapting an otherwise dormant tensor appropriately toward task data distributions without unfreezing heavy core parameters.  

Mathematically this decomposition relies upon standard matrix identities – any matrix product can trivially be represented with one higher-dimensional intermediate vector – viewed here through low dimensional mapping windows $(h\times r)$ and $(r\times o)$. Crucially, during back‑propagation scan directions go entirely through frozen $\mathbf W$, which stays untouched while computing gradients that flow straight into $\partial E/\partial \!\boldsymbol L_{1}$ and $\partial E/\partial \!\boldsymbol L_{2}$ alone (where $E$ represents loss). This backward path eliminates any run-time dependency on large cache demands concerning $\partial E/\partial \!\boldsymbol W$.  

Within *QLoRa* every oscillator employs this lowest rank augmentation over **every** transform layer uniformly – both query/key/value projection heads inside attention cells and ordinary feed‑forward positionwise fully connected maps – avoiding any layer where inherent representation freedom is sacrificed while keeping adapter capacities compact enough that modern GPUs can gently host them in parallel along existing advancement streams.

**NormalFloat (NFk): A Distribution Aware Integer Data Type**

# Computing Gaussian Quantiles \(q_{i}\)

The foundation of NormalFloat lies in exploiting the statistical regularity observed across transformer weight tensors. If a tensor’s elements are drawn from a zero‑centered Gaussian distribution \(N(0,\sigma)\), then every length‑\(b\times h\) block shares a well‑defined shape under any scaling factor applied uniformly across the block. Because the sign symmetry guarantees an identical distribution before and after sign change, we can describe all possible element magnitudes using a single cumulative density function (CDF). Consequently it becomes tractable—contrary to ill‑estimated “first‑stage” “blockwise” methods—to compute *exact* percentiles once and reuse them across all blocks via a simple look‑up table.

To create a \(k\)-bit data type whose bins contain an equal amount of probability mass we compute
\[
q_{i}
~=~\frac{1}{2}\!\left(Q_{N(0,\,1)}\!\left(\tfrac{i}{\,2^{\,k}+\,1\,}\right)
                         ~+~Q_{N(0,\,1)}\!\left(\tfrac{i+\,1}{\,2^{\,k}+\,1\,}\right)\right),
\quad i=0,\dotsc ,2^{\,k}-1,
\]
where \(Q_{N(0,\,1)}(\cdot)\) is the inverse CDF of a unit‑variance standard normal variable.
The arithmetic above simply averages two neighbouring theoretical percentiles so that every term corresponds precisely to the midpoint between two probability masses. Tapping this list yields precisely \(w_{\min},w_{\min+\delta}, \dotsc ,w_{\max}\) spaced so that all intervals capture equal likelihood under the underlying normal model. Thus our resulting bins honor an *information‑theoretically optimal* allocation scheme—each bin absorbs roughly \(\tfrac{100}{2^{\,k}}\%\) of samples when confronted with truly Gaussian data—ensuring minimal mean‑square distortion per bit spent.

Because transformer weights are batched/flattened naturally into blocks during inference or training, each block shares its own scale factor yet shares these global indices \(q_i\); the work above therefore lends itself perfectly well into blockwise stateful or state‑free “hash map” implementations where each stored integer simply refers back through this table during decompression rather than storing floating point densities themselves.

# Asymmetrised Zero‑Point Construction

A naïve choice would force us onto a symmetric binary interval such as
\[
[-M,M],~M=2^{\,k-}\!-\!1,
\]
yet it would inevitably suffer two fundamental ailments:
firstly there would be no literal numeric token representing exact zero—critical when padding tensors are diffused across multiple blocks; secondly symmetric intervals waste one entry by overlapping on both signs when allocating an odd number of bins.
To solve this problem without sacrificing our quantity‑optimality guarantees we construct an **asymmetric** scheme whereby negative numbers occupy exactly half the bin space while positive numbers receive one additional bin so that one copy can encode true zero separately.

Because both lists share a unique ‘zero’ element at i=0,
we discard one duplicate so that every eventual integer encoding contains a single exact–zero symbol occupying its own codeword.
