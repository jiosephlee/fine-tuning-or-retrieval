### `ℝ≥0 ¾ INT`: Is every coefficient truly stored on one physical bit?
Question:
If every weight belongs exclusively to {-− − − '+', '+', '-'} settles what amounting hardware footprint follows – is storing '- +' effectively achieved via two bits (log₂ 3 ≈ 1․58 ) even while advertised as ‘bit‑compressed’?
Answer:
**Short answer:**  

Yes – every coefficient of BitNet b\(^{158}\)\ can be represented by one *ternary* value 
$\{-\,1,\;\hbox{}{},\<+>\,\}$,
which theoretically requires $\log_{2}3\simeq 1．58$ bits on average.
In practice a physical implementation needs at least **two whole bits**
to encode those three distinct states; the “bit‑compressed” tag refers
to the fact that two real–world (*binary*) bits store information
equivalent to less than one full‑precision floating‑point word
(16 bits).

-------------------------------------------------------------------  

### Why can’t we pack a “– +” with just one physical bit?

A single binary digit can represent exactly **two**
combinations (“0” and “1”).  
The set $\{-\, (\hbox{}{}, +)\}$ contains **three**
distinct elements – more than a single bit can distinguish without loss
of information.
Therefore any hard‑wired storage scheme must provide at least  

$$
\lceil\,\log_{2}3\,\rceil = 2
$$  

binary cells per parameter.



### What BitNet b\(^{158}\) actually does

The authors implement their custom `BitLinear` layer by **packing two
ternary weights into each byte**:

| Byte slice | Pattern | Value |
|------------|---------|-------|
| `00`       | 00      |  0 |
| `01`       | 01      | + ¹ |
| `10`       | 10      | − ¹ |

(The pattern `11` remains unused or could serve as a sentinel.)
Thus a single byte holds four parameters,
reducing storage from  
$4\times 16=64$ bits (four FP16 numbers)
to  
$4\times 2=8$ bits –
an $8\times$ saving compared with FP16 and approximately
$\displaystyle12.5\,{\%}$ of the original size or an eight–fold reduction
in memory footprint for weights alone.



During inference they employ an integer–only matrix multiplication
kernel (the Ladder **2-bit** routine).
Because all multiplications collapse to sign adjustments and conditional additions—no real multipliers—the arithmetic energy drops dramatically while latency improves due
to heavily reused cheap adder circuitry.



### How this matches the “$\log_{2}(3)$” claim

If we compute the *average* number of canonical binary digits needed
when storing three equiprobable symbols,

$$
H=-\
   \sum_{i=1}^{3}
   {\tfrac13}
   \,\log_{2}{\,{\tfrac13}}
     =    {\log}_{2}(3)
     ~=~    {\color{red}{~}}\boxed{{Alternately:\;
        {\color{darkblue}{14.\overline7}}\}}%
$$   

That value tells us what we would attain if we could perform
entropy coding on a stream made purely of these trits—
essentially lossless compression exploiting statistical redundancy
across parameters globally (e.g., Huffman coding).
BitNet enforces an *exact* mapping from each trit without global reorder;
physically it still uses fixed two–bit slots for alignment and timing reasons on GPUs/CPUs or ASICs where unaligned accesses are slow or impossible.



Consequently every weight itself occupies precisely **two logical digital cells**, which is twice more than an ideal single-bit scalar would use if entropy coding were available—but it still corresponds roughly *(in terms of raw bits)* to   
$
c\simeq\dfrac23\,(\log_{2}3)\times32~{\rm bytes}
$
for typical batch sizes when counting both coefficients and accompanying shift/offset lookups.
