# Beyond The Paper – What’s Next for Orthogonal Finetuning?

After introducing *Orthogonal Finetuning* (OFT) as a principled way to preserve hyperspherical energy while adapting diffusion‑based image generators, the community is left with several concrete challenges.  
Below we dig into three key directions that naturally progress from the work and outline what needs to happen before OFT can become a turnkey solution for every downstream task.

---

## 1. Speeding Up the Cayley Transform

**What happens in OFT?**  
The core of OFT is learning an orthogonal matrix \(\mathbf{R}\) per layer:

\[
\mathbf{z}= (\mathbf{R}\!\cdot\!\mathbf{W}^{\!\circ})^\top \!\mathbf{x}, \qquad 
\mathbf{R}= (\mathbf{I}+\mathbf{Q})(\mathbf{I}-\mathbf{Q})^{-1},
\]

where \(\mathbf{Q}\) is skew–symmetric.  
The under‑lying *Cayley transform* gives us an implicit way of enforcing \(\mathbf{R}^\!\top \! \mathbf{R}=\mathbf{I}\). While elegant mathematically, computing \((\mathbf{I}-\mathbf{Q})^{-1}\) at every iteration incurs a tangible overhead – especially for large latent‑space dimensions (\(d=512\), \(d^2/2\simeq 1\times10^5\) parameters).  

### Why this matters
- **Scalability** – on a 2048‑dimensional model the inverse costs 8× more ops.
- **Memory footprint** – a dense inverse requires extra GPU buffers.
- **Training time** – longer per‑epoch times make hyper‑parameter sweeps impractical.

### Hands‑on solutions that deserve exploration

| Approach | Strengths | Trade‑offs |
|--------|-----------|------------|
| **Truncated Neumann series** <br>\(\displaystyle \mathbf{R}\approx \mathbf{I}+2\!\mathbf{Q}+4\!\mathbf{Q}^2+\dots+\!k\bigl(2\bigr)^k \!\! \mathbf{Q}^k\) | Fast, no inversion; good if $\|\mathbf{Q}\|<1$ | Accuracy limited by order \(k\); sometimes diverges if $\|\mathbf{Q}\|\!\geq\,1$ |
| **QR decomposition** <br>\(\bigl[\hat{\mathbf Q},\,e\,]\!=\!{\rm QR}(\tilde{\boldsymbol W})\) | Exact orthogonality at every step | Adds two extra loops (QR + recombination); precision unstable when matrices are ill‑conditioned |
| **Householder reflections / Givens rotations**<br>Constructing \(r_i = \exp({{\rm skew}}_i)\) | Low‑dimensional updates when \(r_i\)'s are sparse | Implementation complexity rises with number of layers |
| **Learned “soft” orthogonality** <br>Penalty term \(|| \mathbf R^\top \! \rright - {\bf I}||_F^2\) | No inversion; flexible schedule | Requires careful tuning of penalty weight |

A pragmatic hybrid strategy would starts training with a low‑order Neumann rollout (fast!) and gradually transitions to exact QR or Householder steps once training stabilises. Library support from modern autograd engines (Broadcasting on NVIDIA AMP or Intel MKL’s `LAPACK` wrappers) will also alleviate inversion costs.

## 2. Composing Multiple Orthogonal Matrices Across Tasks

A compelling claim in the original work is that *the product of two learned orthogonal matrices remains orthogonal*. This opens up an entire toolbox:

```text
R_taskA = learn_from_A()        # optimised for task A
R_taskB = learn_from_B()        # optimised for task B

R_combined = R_taskA @ R_taskB   # still in O(d)
```

### Why this is exciting

- **Model multiplexing** – We could drop one set of weights at inference and apply `R_taskB` after `R_taskA` without retraining.
- **Zero‑shot transfer** – Suppose we’re only fine–tuned on “dog” images but someone asks for “cat” images too. A simple concatenation could produce plausible cat generations.
- **Compositional specification** – Combining (`photo realistic` @ `Canny control`) yields an image obeying both constraints simultaneously without re‑optimising from scratch.

### Practicalities & pitfalls

| Issue | Implications | Prospective workaround |
|-------|--------------|------------------------|
| **Non‑commutativity**<br>\( R_A R_B \neq R_B R_A \) | Order matters; fails if tasks intervene unexpectedly | Record both orders as separate checkpoints |
| **Accumulated numerical drift** | Multiplying many matrices can lead to rounding errors that slowly break exactness | Periodic reorthonormalisation via polar decomposition |
| **Expression capacity vs interference**<br>Two tasks may attack different semantics individually but misbehave when combined | Overlaps in latent subspaces produce artefacts | Multi‑task loss that monitors “task loss” postcompose then re‑fine tune |

A concrete next step would be benchmarking *serial composition* against *joint training*. If serial composition can match joint performance while preserving inferencing overhead, it could become the default workflow in production pipelines where new user requests arrive incrementally.

## 3. Steering Clear of Block‑Diagonal Biases

The paper’s *efficient* parametrisation leverages block–diagonal orthogonals:

```text
R = diag(R1 , … , Rr)
```

This cuts down parameter count from \(O(d^2)\) to \(O(d^2/r)\), but at a cost:

- **Channel isolation** – Each block only rotates a set of neurons (or feature maps). If semantic axes cross these blocks loose couplings get suppressed.
- **Limited expressiveness** – The model cannot learn joint rotations across blocks without incurring extra parameters or losing strict cheapness.
- **Bias towards depthwise correspondence** – When every block matches one channel (as done for convolutions), we essentially perform depthwise linear layers which may not capture global context shifts needed for some controls.

### How far do we need to go?

| Idea | Methodology | Expected Benefit |
|------|-------------|------------------|
| **Shared shortcuts across blocks**<br>E.g., learn one global rotation `G` appended after sub-blocks |\( R_{\text{shared}} = G\,diag(R_1,\dots,R_r)\)| Captures coarse global transformations without many parameters |
| **Low–rank coupling matrix**<br>Attach a rank‑\(k\) outer product between blocks |\( diag(R_1,\dots,R_r)+Z₁Z₂^\top|\)| Adds minimal degrees of freedom for cross‐block coordination |
| **Randomised block splitting**<br>Use random assignments for each fine-tune run and average results |\(\mathbb E[\,Diag(\cdot)\,]\)| Mitigates any particular splitting bias |

An empirical roadmap would start with those two tweaks—one adds a tiny “global spine”, the other PLL-like coupling—and measuring changes in *hyperspherical energy* and *DINO/CLIP fidelity* relative to vanilla block–diagonal OFT. If strong gains appear with negligible parameter growth (say < 3 % more trainable weights), this becomes a go‑to patch for any deployment looking for both speed and quality.

## Bottom Line – An Engineering Checklist

| Question | What To Do | Why It Matters |
|-|-|-|
| Is my training fast enough? | Adopt truncated Neumann approximation until convergence region, then flip back to QR or Householder updates | Reduces per–epoch wall clock time by ~30% on typical GPUs |
| Will my downstream tasks compose nicely? | Store learned `R`s per task and test multiplicative combinations before deployment | Enables modular fine‑tuning pipeline without hot restarts |
| Am I hurting performance with over‐constrained blocks? | Fine–tune shared or low‐rank couplings; roll back if no improvement on CLIP metrics | Prevents structural bias that limits semantic shift capacity |

With these concrete steps you’re ready not just to paste OFT into your code base but also push it toward practice‑ready usage across dataset scaleups and multi–task pipelines—an essential blend that turns “orthogonally nice verbs” into measurable production improvements.
