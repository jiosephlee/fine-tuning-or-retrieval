# Byte Latent Transformers – Reimagining Language Models Without Tokens  

Large language models have been built around one immutable design choice: **tokenization**.  
Sub‑word vocabularies such as BPE or GPT’s SentencePiece group arbitrary sequences of bytes into an ever‐larger “dictionary” which is fixed before training starts. The fixing of this dictionary has profound implications:

| Reason | Consequence |
|--------|-------------|
| Tokens are defined by heuristic compression rules | They provide no guarantee that two identical words will always be represented by the same stream of nodes |
| Every token receives an equal share of compute | A punctuation mark that is trivial to predict consumes as much time as a novel word |
| Only the token surface matters | Subtle typographic quirks or orthography do not directly drive training statistics |

These weaknesses surface in multiple ways—from poor handling of noisy inputs and low‑resource languages to an opaque decision boundary on where model capacity should be allocated[^1].

Enter **Byte Latent Transformers** (BLT): a new class of architectures that drop tokenization entirely and learn directly from raw bytes while **grouping those bytes into dynamically sized “patches”** that act as the model’s main computational units. In doing so they simultaneously match state–of–the–art performance and reduce inference cost by up to half while becoming significantly more robust.



---

## How does BLT “patch” the byte stream?  

A *patch* is a contiguous run of raw UTF‑8–encoded characters whose length is decided on **the fly**, according to how hard it is for an inexpensive model to predict the next byte inside that run.  
The process uses a tiny auxiliary *entropy model*—a 100 M parameter byte predictor trained on the same data that the main BLT will learn from—to estimate uncertainty `H(x_i)` for each upcoming byte:
```
H(x_i) = Σ_{v∈V} p_e(v | x_<i) · log p_e(v | x_<i)
```
If `H(x_i)` exceeds one of two constraints

```
Global:     H(x_t) > θ_g          … triggers large boundary
Relative:   H(x_t) - H(x_{t-1}) > θ_r … captures sudden spikes
```

a new patch starts at position `t`. The result is a string
that collapses predictable regions into long stretches while carving out short patches around high‑entropy bits such as word beginnings or code delimiters.



### Why this helps

* **Dynamic compute allocation** – A long predictable region becomes half as many
transformer steps as it would be if every single byte were processed independently.
* **Higher information density** – Patches group together information outwardly similar
across contexts so the latent transformer can focus its expressiveness where it matters most.
* **No fixed vocabulary pressure** – The number and size of patches adapt freely,
unshackled from complicating tradeoffs between embedding table size and sequence length.



---

## The three–stage BLT pipeline  

1. **Local Encoder (`ℰ`)**  
   * Tiny transformer (≈1 layer on BPE baseline scales)  
   * From “raw” byte embeddings plus hash‐based n‑gram skeletons (`g_{i,n}` = last `n` bytes,
`n=3…8`) builds an encoded vector per active patch via lightweight cross‐attention  
   * Aggregate “query” pooling followed by `ℰ_C` transforms → initial latent vector

2. **Latent Global Transformer (`𝔾`)**  
   * Full weather-size autoregressive transformer operating **only over patches**  
   * Block‐causal attention ensures sequence order within documents but stops reusing past context beyond the current document’s bound  
   * Contains most FLOPs—when its forward call is avoided by keeping many patches longer,
overall inference cost shrinks dramatically

3. **Local Decoder (`𝔻`)**  
   * Mirrors the encoder but runs in reverse direction  
   * Cross‐attention pulls probability mass back from latent vectors onto individual
bytes first, then a tiny decoder transformer produces actual output bytes  

Each module contributes modestly scaled multi‐head self/ cross attention =
\(O(n_{\text{patches}}\,d^2)\),
but because `n_p` can be ⩽ ~10× larger than `n` for a standard NFT type tokenizer,
the net runtime scales more favorably.

## Flexibility beyond conventional limits  

Because element length is not tied to vocab choice,
training developers can trade two knobs:

* Under tighter inference budgets → increase average patch size (e.g., go from ~4½ → ~8 bytes).  
Inverse relation means roughly half your compute budget just shifts into bigger local encoders which are cheap in comparison with lattice self-attention over every byte.

* Under ample pre‐training compute →
grow both encoder depth and canonical sequence length simultaneously—classic scaling tricks become available without stochastic flavor changes.

## Path forward – how can we build upon this?  

1. **End-to-End dynamic boundary learning**  
   Instead of relying on an externally trained entropy model,
   attach a lightweight “bypass classifier” module that predicts whether a boundary should appear at every position during training.
2. **Hybrid decoders**  
   Combine BLT’s decoder with language modeling heads directly used in generation pipelines ;;
   exploring simpler putative streaming decoding methods could leverage longer patches during generation without extra context swapping overheads.
3. **Hardware co-design**  
   Patchwise attention has non-uniform memory footprints; custom CUDA kernels or specialized ASICs could accelerate it further than standard FlashAttention implementations currently do.[²]
4. **Leveraging pretrained transformers**  
   The authors demonstrate initializing global weights from an existing tokenised LLaMA model (“byteifying”) substantially cuts pretrain flops.
   Fine-tuning other larger families will likely discover distributed benefits w.r.t scalability.


While these open questions depict soft edges along plenty more instruments awaiting fine tuning,

**BLTs represent the next brass section in large language modeling—a robust chord replacing brittle punctuation phrases with reliably deep entry points straight on raw transcendence data._**

# Inside the BLT Architecture – From Bytes to Patches and Back Again  

Large language models normally rely on a fixed‑size tokenizer that turns every piece of text into a bag of sub‑word symbols before feeding it into a Transformer network.  
In **Byte Latent Transformer** (BLT), that static preprocessing step disappears altogether. Instead a tiny neural module learns how *to group* individual UTF–8 bytes into flexible **patches** whose size is chosen on the fly from an entropy estimate computed by a separate “small” language model.  
Below is an unpacking of how three interconnected blocks cooperate—**the Local Encoder**, **the Global Latent Transformer**, and **the Local Decoder**—to turn raw input streams into fast multimodal contextual knowledge while keeping inference costs low.



--------------------------------------------------------------------

## 1️⃣ The Overall Pipeline  

| Stage | What It Does | Key‑Structure | Input / Output |
|-------|--------------|---------------|----------------|
| **Local Encoder** | Turns every incoming byte into a rich vector that remembers its local neighbourhood | Lightweight transformer + *cross‑attention* pool | Byte‑level hidden state (`h_E`) + an aggregate “patch vector” (`p`) |
| **Global Latent Transformer** | Models dependencies between **patches** instead of individual bytes | Large autoregressive Transformer (`ℰG`) | Generates an updated version of each patch (`o`) |
| **Local Decoder** | Maps those patched outputs back down into raw byte predictions | Light transformer + *cross‑attention* back onto decoding positions | Probability vector over 256 UTF‑8 symbols |

During training all three components are computed simultaneously thanks to pre‑computed **entropy‐based boundaries** that decide which groups of consecutive bytes form one patch.



--------------------------------------------------------------------

## 2️⃣ Local Encoder – ‘Seeing’ Each Byte With Context  

1. **Byte Embedding + Hash n‑gram augmentation**  
   * Every UTF–8 symbol receives an index‑based lookup vector (`x_i`).  
   * To give the encoder a sense of surrounding conventions—like “pre‑punc” prefixes—we build *hash* n‑grams covering lengths 3–8 around position `i`. Each hashed gram looks up one more embedding from a table `E_n_hash`.  
   * The enriched vector  
     `e_i = x_i + Σ_n E_n_hash( Hash( g_{i,n} ) )`  
     is then normalised so that the extra grams do not dominate magnitude-wise.
   * The function `Hash()` is a simple rolling polynomial hash followed by modulo arithmetic—cheap enough that it can be done once during data loading.
     
2. **Local Self‐Attention Layers** live inside a very short receptive window (`w_E`, e.g., 512 bytes). They act rhythmically over the raw stream handling both left–to–right causal ordering and relative locality—exactly what you would expect when learning digraphs, morphemes, or syntax fragments.
   
3. **Cross‑Attention Pool Across Each Patch**  
   * After each self‑attention block we run a separate *cross‑attention* submodule whose purpose is sweetly specific:
     * For every slot `j` corresponding to a dynamic patch boundary identified earlier,
       * initialise its query vector by pooling (`avg` or `max`) all hidden states belonging strictly inside that part.
       * Keys/Values come exclusively from those same hidden states so information can’t leak across natural boundaries.
     * Multiple heads help serendipitously capture orthographic nuances such as capitalization patterns versus case folding.
   * After several layers this pool reflects an integrated “latent texture” of everything happening inside its own slice.
   * Finally these pooled vectors feed directly into the global transformer, holding the shape expected there (`h_G` dimensionality).


This whole subnetwork operates dozens × faster than treating every symbol individually because it prunes most redundancy early—think compressed padding courtesy of order‐lowering.



--------------------------------------------------------------------

## 3️⃣ Global Latent Transformer – Unpacking Contextual Knowledge  

The global module sees apertures—not individual symbols—but already rich latent summaries produced above:

```
Input : [ p_1 , p_2 , ..., p_m ]          // m < original byte count
Mask   : block‐causal ("no future" within document)
Self‐Attention : multi‐head QKV
Feed‐Forward   : SwiGLU
```

*Because it walks over far fewer tokens*, this component typically dominates compute budgets during training, similarly to ordinary large LMs—but crucially now every step deals with an informative chunk rather than an opaque single character.


### Why autoregressive on patches?

1. **Fewer Steps → Fewer Interactions**  
   Every step in the transform chain has constant cost depending mainly on hidden width and number of heads—not sequence length—so cutting fragment count yields big O savings.
   
2. **Dynamic Virus Note**  
   Self‑attentions are restricted up-to-current-patch so causality remains intact even when consecutive generated tokens are created within different branches triggered by unpredictability estimates.
   
3. **Training Keeps It Fair**  
   All other experiments used exactly the amount of training FLOPs predicted for tokenized Llama 3 so comparisons aren’t biased toward either architecture.



--------------------------------------------------------------------

## 4️⃣ Local Decoder – Bringing Predictions Back Into Bytes  

After a global pass generates new latent vectors `o_j`, they undergo another round of **cross‑attention**, this time opposite Direction:

* Queries are derived from the last set produced by the encoder (the raw byte hidden states).  
* Keys/Values come from linearly projecting every whole patched encoded action through a small network (`ℰ_C`).  

The decoder then runs several lightweight self‑attention layers again over those intermediate representations while listening again only locally inside each slice—it’s basically untidying what was previously tidied up during encoding.



--------------------------------------------------------------------

## 5️⃣ Cross–Attention Mechanics Summarised  

Both encoder and decoder share essentially identical mechanics—it’s only orientation that flips:

```
Similarly arranged computational graph:

    Q = Linear(Probing(Qprev))          // Query per latent spot / Query per byte
    K/V = Linear(OtherSideData)         // Keys/Values span many positions
    Attend(pathed mask)                 // Limits look‑ahead info
    Output = Residual(Q + Attention(Q,K,V))
```

Normally you would worry about endianness in CCP style systems — here it translates simply into gating which part of one sequence sees which part of another while respecting newly defined boundaries.


Important distinctions you've probably seen elsewhere:
* No position embeddings happen during cross‑attention */
* Multi head count equals total model dimension coming out smaller than expected ➜ keep firing power modest
* Pooling initialization lets us sidestep having separate “bag vectors” altogether


--------------------------------------------------------------------

## 6️⃣ Automatic Patching via Entropy Estimators  

Static stride grouping (- every K) tends hostage computation invariants—and sometimes misaligns well-known linguistic junctures like word starts endings ‑ especially troublesome when dealing with noisy symptomatics like OCR errors.”ສ 
Instead BLT hooks in a tiny “entropy” language model trained right alongside everything else:
1) Run it under table lookup mode over small windows (≤512 bytes).
2) Compute uncertainty measure at each position,
3) If next-byte entropy crosses an empirically tuned threshold OR rises sharply compared against its neighbour,
   carve out a new patch there!
This algorithm guarantees two things:
* More computation gets bundled where prediction difficulty spikes,
* Very long stretches shrink down wherever symbols become predictable—think “http://” URL tails.


Since this grouping happens before batching happens it perfectly balances inference-only FLOPs against training budget evenly across block sizes.



--------------------------------------------------------------------

## 7️⃣ What Makes BLT Superior Over Tokenizers  

| Property | BLT Advantage |
|----------|---------------|
| Compute Control | Reduce number-of-step penalty dramatically because fewer AND richer steps |
| Robustness | Raw symbol exposure lowers sensitivity against obfuscations such as added spaces / rotated case |
| Long-Tail Handling | Since there’s no prebuilt vocabulary limitting low‑frequency symbols—every potential byte pattern stays trainable |
| Scaling Flexibility | Patch size can grow without ending up dented vocab embedding size unlike Tokenizer breaking rentability curve |

Tied together these skills mean even near comparable parameter counts (~8 B), BLT shaves off ~50 % slow functions per generated token whilst on its way scoring at parity—or even beating tokenized rivals thanks largely biting higher quality training runs.



--------------------------------------------------------------------

## 8️⃣ Summary & Takeaway  

BLT demonstrates one practical blueprint for rethinking LLM pipelines:

1. Think pixels → tokens → blocks → tokens…what if you joined pixels directly but smartly chunked them first?
2. Let tiny side networks decide chunk boundaries handfuls apart—use existing entropy levels.
3. Embed context via lightweight hash-ngram tricks instead of huge BPE tables.
4. Keep two light encoders / decoders braced against costy global latents—all layered cleanly with cross‑attention gatekeeping leakage.
5. You obtain tireless generalisation while buying runtime perks compared with legacy tokenizers.

Future iterations could train boundary detectors end‑to‑end instead of relying on pre-built entropy nets—or borrow pre-trained mainstream LMs’ weights partly—as recent distillations hint at worthwhile speed           gains without sacrificing perplexity edges.

# Scaling That Matters  
**BLT Meets Llama 3 While Slashing Inference Flops**

---

Large language models (LLMs) almost always depend on an upfront tokenization step that groups raw bytes into a large fixed vocabulary (e.g., bpe).  
Though convenient, this pre‑processing introduces indirections that hurt long‑tail language modeling, robustness to noise and efficiency at scale.  
The **Byte Latent Transformer (BLT)** breaks this bottleneck by learning directly from raw bytes while preserving the expressive power of modern Transformers—only collapsing the input into *dynamic patches* whose sizes are dictated by local information density instead of arbitrary heuristics or a static dictionary.



## What Is the Byte Latent Transformer?

BLT embeds its inputs through three intertwined blocks:

| Module | Role | Key Feature |
|--------|------|-------------|
| **Local Encoder** | Maps every input byte into an intermediate representation and pools those bytes into *patch embeddings* | Lightweight Transformer (`l_E << l_G`) + per‑patch cross‑attention |
| **Global Latent Transformer** | Generates predictions in *patch* space | Autoregressive transformer (`l_G`) – “large” network run only once per patch |
| **Local Decoder** | Decodes patched predictions back into raw bytes | Mirrors the encoder’s lightweight stack |

The encoder’s cross‑attention first pools byte representations for each patch \(p_j\); the pooled query attends **only** the keys/values corresponding to those very bytes.  
During decoding these roles are reversed – each byte attends a fixed set of nearby keys derived from its previous state combined with global patches.



## Dynamically Building Patches

Hash‑based n‑gram embeddings give each byte a glimpse of its context without extra computation:
\[e_i = x_i+\sum_{n=3}^{8}E_n^{\text{hash}}\!\bigl(\text{Hash}(g_{i,n})\bigr).\]

### From Stride to Entropy  
Four patentable segmentations were compared:

| Scheme | How boundaries are chosen | Typical Average Patch Size |
|--------|---------------------------|----------------------------|
| Strided \(k\) bytes | Constant stride \(k\)   | Fixed \(k\) |
| Whitespace | New slice after any space‑like byte | (~4–5 bytes) |
| Entropy‐based | Next‑byte entropy > threshold or > relative increase over past byte \(H(x_t)>θ_g\) or \(H(x_t)-H(x_{t−1})>θ_r\) | Adjustable via threshold |

The *entropy* strategy introduces **free routing**—a glue between data complexity and compute budget—without immanent bias toward any particular language or representation.



## Compute‑Optimal Training Study

Training was conducted on two corpora:

* **Llama 2 Mix** – cleaned & filtered > 2 trillion tokens (hence >>4 trillion bytes).
* **BLT‑1 T** – newly gathered 1 trillion tokens enriched with Datacomp samples.

For each configuration (400 M–8 B parameters) we performed *compute‑optimal* pretraining—matching the ratio prescribed by Metalearning approaches fine tuned for BPE transformers—and measured bits-per-byte ($BPB$).

### Key Observations

1. **On par or superior performance:** Across every scale blt matched or outperformed a BPE counterpart trained under identical flop budgets (compare → Figure 5(a)).  
   This is the first evidence that *byte‑only transformers can be profitably trained at scale*.  

2. **Static/whitespace variants fall short:** MegaByte‑style fixed strides and SpaceByte loss much information relative to BPE’s adaptive attention distribution [[See Figure 5(b)]].

## Fixed Inference Cost Scaling

Model size alone does not fully capture deployment cost: inference flops dominate serving expenses because they scale linearly with sequence length (# latent steps).  
To probe this factor directly we held *total inference flops constant* while varying two knobs simultaneously—global model depth (`l_G`) and average patch size (`n̄`).

| Model type | Avg Patch Size | Expected → ↓↓ Inference Flops |
|------------|-----------------|--------------------------------|
| Tokenisation‐based   | ≈​4–4½ bytes           | Reduce computational windows only if vocab grows significantly |
| BLT Entropy 8          | ≈​8 bytes               |-> <50% fewer latent steps          |

These experiments revealed a sharp advantage for blt when `n̄` ≥ 6:

* At moderate flop budgets (< 2× optimum), tokenization reigned supreme because there were relatively few steps left for the large global network.
* Crossing ≈ 2× optimum budgets tilts performance in striking favour of blt—its ability to launch fewer but larger patches lets us arm a bigger global transformer without bloating inference costs indefinitely.
* The *crossing point moves closer* as overall model size grows—an enticing sign that push‑ups beyond today’s 8 B horizon would strengthen blt’s edge further.

# More Than Tokens  
### Why Bytes Make Bl<sup>T</sup> Robust to Noise and Low‑Resource Languages  

Large language models today are usually built around a fixed vocabulary—the classic “token” space obtained via byte‑pair encoding (BPE), WordPiece or SentencePiece. While tokens help compress data efficiently, they also impose hard inductive biases that hurt generalization when faced with unexpected inputs or very few samples per language family.  

The Byte Latent Transformer (**Bl<sup>T</sup>**) removes this bottleneck altogether: it learns directly from raw UTF‑8 streams yet keeps computation tractable through dynamic “patch” stepping based on next‑byte entropy estimates. As a consequence Bl<sup>T</sup> excels wherever character granularity matters—noisy prompts, grapheme–phoneme prediction and multilingual coding meet starkly different signal statistics compare well against token‑heavy architectures like LLaMA 3.

## Robustness Against Input Noise  

Robust engineered systems must resist accidental corruptions introduced during collection or transmission—a quality naturally suited towards byte‑level processing because every bit has equal importance. To diagnose Curiously Bl<sup>T</sup>'s resilience we subjected seven popular classification benchmarks (ARC‑Easy/Challenge, HellaSwag, PIQA…) to five exhaustive perturbation regimes applied either against prompts alone or against completions alone:

| Perturbation | Example |
