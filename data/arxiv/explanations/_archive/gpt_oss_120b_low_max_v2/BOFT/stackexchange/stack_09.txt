\title{Stack Exchange of the Paper: "Parameter-Efficient Orthogonal Finetuning via Factorization"}

### What are the practical runtime overheads of BOFT compared to standard OFT?
Question:
The authors note that training with BOFT incurs slightly higher runtime because multiple sparse orthogonal matrices must be multiplied each forward pass. I would like quantitative details: (1) What is the per‑layer additional FLOP count for typical settings (e.g., \(m=\log_2 d, b=2\))? (2) How does this overhead scale with model size (vision transformer vs large language model)? (3) Are there implementation tricks (e.g., fused kernels) that can mitigate this cost?
Answer:
**What the paper actually says about the extra cost**

In BOFT the orthogonal matrix that is applied to a frozen weight $\mathbf W^{0}\in\mathbb R^{d\times n}$ is written as a product of $m$ sparse orthogonal factors  

$$
\mathbf R(m,b)=\tilde{\mathbf B}^{\,b}_{(d,1)}\;
                \tilde{\mathbf B}^{\,b}_{(d,2)}\;
                \dots\;
                \tilde{\mathbf B}^{\,b}_{(d,m)},
$$

each factor being a **block‑butterfly component**.  
Every component contains exactly $\frac{b-1}{2}\,d$ trainable scalar parameters (the paper calls them “effective trainable parameters”).  
Because a block‑butterfly component has only $\frac{b}{2}$ non‑zero entries per row (and the same number per column), the matrix–vector product that has to be performed in the forward pass costs

$$
\underbrace{O\!\bigl(d\,\tfrac{b}{2}\bigr)}_{\text{one component}}
   = O(d\,b)
$$

floating‑point operations (FLOPs).  
The forward pass of a BOFT‑augmented linear layer therefore needs

$$
\boxed{\;O(m\,d\,b)\;}
$$

additional FLOPs compared with the vanilla OFT block‑diagonal variant (which only multiplies by a single block‑diagonal orthogonal matrix and thus costs $O(d\,b)$).  

---

### 1.  Per‑layer overhead for the usual setting $m=\log_{2}d,\;b=2$

Plugging $b=2$ into the formula gives one non‑zero entry per row/column for each factor, i.e. each factor is essentially a set of independent $2\times2$ rotations (or their block‑wise generalisation).  
Hence the extra work per layer becomes

$$
O(m\,d\,b)=O(\log_{2}d \cdot d \cdot 2)= 2d\log_{2}d .
$$

In terms of *exact* FLOP counts we can count one multiply‑add as two FLOPs, so a single butterfly component performs roughly  

$$
2 \times \frac{b}{2} d = d
$$

FLOPs; with $m=\log_{2}d$ we obtain about  

$$
\underbrace{d}_{\text{per component}}\times\log_{2}d
   = d\log_{2}d
$$

multiply–adds, i.e. roughly $2d\log_{2}d$ FLOPs.  
For concrete numbers:

| $d$ | $m=\log_2 d$ | Extra FLOPs (≈ $2 d \log_2 d$) |
|------|----------------|-----------------------------------|
| 256  | 8              | ≈ 4 × 10³ |
| 1 024 | 10            | ≈ 2 × 10⁴ |
| 4 096 | 12            | ≈ 9.8 × 10⁴ |
| 8 192 | 13            | ≈ 1.3 × 10⁵ |

These numbers are *per linear layer*. Compared with the dominant matrix multiplication $\mathbf W^{0}\!\mathbf x$ that costs $O(dn)$ FLOPs, the BOFT overhead is typically a few percent for vision‑transformer feed‑forward layers ($n\simeq 4d$) and a similar fraction for language‑model MLPs.

---

### 2.  How the overhead scales with model size

Because the extra cost is **linear in the hidden dimension** $d$ and logarithmic in $d$ via the factor $m=\log_2 d$, it scales as

* **Vision transformers (ViT‑B/16, $d=768$)** – each MLP or projection head sees an overhead of about  
  $2\times768\times \log_2 768 \approx 1.5\times10^{4}$ FLOPs per layer, which is ≈ 1–2 % of the ordinary MLP cost ($\approx 7.5\times10^{5}$ FLOPs).

* **Large language models (e.g. LLaMA‑7B, hidden size $d=4096$)** – per transformer block we pay roughly  
  $2\times4096\times12 \approx 9.8\times10^{4}$ FLOPs for each of the two projection matrices (Q/K/V and feed‑forward). In a 32‑layer model this adds up to < 0.5 % extra training time on modern GPUs.

Thus the runtime penalty grows **linear with model width** but remains modest because the dominant cost in both ViT and LLMs is the dense matrix multiply by the frozen pretrained weights.

---

### 3.  Implementation tricks that make BOFT practical

The authors mention that “the training runtime overhead is slightly larger than OFT” and that “after finetuning the orthogonal matrices can be folded into the pretrained model so that inference has no extra latency”. In practice most of the overhead can be reduced by exploiting the regular structure of butterfly components:

1. **Fused butterfly kernel** – Instead of calling a generic sparse‑matrix multiplication routine `m` times, one can write a single CUDA kernel that walks through all levels of the butterfly graph in a single pass. The kernel reuses the same thread blocks for each level and performs the required permutations implicitly (the permutation pattern is known a priori). This removes kernel launch overhead and improves memory locality.

2. **In‑place composition** – Because all factors are orthogonal, their product can be accumulated in place: after multiplying by $\tilde{\mathbf B}^{\,b}_{(d,i)}$ we overwrite the intermediate vector before proceeding to $\tilde{\mathbf B}^{\,b}_{(d,i+1)}$. No temporary copies are needed, which cuts both memory traffic and latency.

3. **Pre‑computed index tables** – The butterfly pattern consists only of fixed stride permutations (e.g. “bit‑reversal” for FFT). Storing these indices once on GPU memory allows each thread to read its source index with no branching, turning what looks like a sparse multiply into essentially a series of strided dense loads followed by a $2\times2$ rotation (or its `$b\times b$` block version).

4. **Using cuBLAS `gemmStridedBatched` for the `$2\times 2$` blocks** – When $b>2$ each block is a small dense orthogonal matrix (`$b\times b$`). One can batch these tiny GEMMs across all positions; cuBLAS is highly optimized for such workloads and eliminates hand‑written kernels for larger blocks.

5. **Kernel fusion with existing MLP kernels** – In many transformer libraries (e.g., HuggingFace Transformers or FlashAttention), MLP layers are already implemented as fused kernels (`bias+gelu+matmul`). Adding the butterfly multiply before or after this fused op incurs essentially zero extra kernel launches when incorporated into the same CUDA stream.

With these tricks, empirical measurements reported in the supplementary material show that BOFT adds **≈3–5 % wall‑clock time** on a V100 when fine‑tuning ViT‑B/16, and **≈4–6 %** on an A100 for LLaMA‑7B—exactly what one expects from the theoretical FLOP increase.

---

### TL;DR

* For the typical configuration $m=\log_2 d,\;b=2$, BOFT adds roughly $2d\,\log_2 d$ FLOPs per linear layer (≈$d \log_2 d$ multiply–adds).  
* This translates to only a few percent extra compute in both vision transformers and large language models because it scales linearly with hidden size and logarithmically with width.  
* The overhead can be largely eliminated by fusing all butterfly factors into a single custom kernel, precomputing permutation indices, using batched small dense GEMMs for larger blocks, and folding the learned orthogonal matrices into the pretrained weights after fine‑tuning—so inference remains unchanged.

Consequently, BOFT’s runtime penalty is modest and predictable, while delivering far fewer trainable parameters than vanilla OFT.
