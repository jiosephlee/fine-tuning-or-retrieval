\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### Why does overlapping softmax with GEMM improve utilization despite softmax’s data dependencies?
Question:
Section 3.2 describes a 2‑stage pipeline where softmax for iteration $j+1$ overlaps with the second WGMMA of iteration $j$. I understand that GEMM throughput is much higher than exponential throughput, but I’m unclear how the dependencies (softmax needs $S_{cur}$ from the first GEMM, and the second GEMM needs $	ilde P_{cur}$ from softmax) are broken. How does keeping $S_{next}$ and $	ilde P_{cur}$ in registers allow these operations to proceed concurrently? A step‑by‑step timeline of kernel instructions would clarify this.
Answer:
The key to the 2‑stage pipeline in FlashAttention‑3 is that the two operations that look sequential on paper – the first GEMM ( $S_{\text{cur}} = Q\,K_j^{\top}$ ) and the soft‑max that follows it – are *physically* executed on different warpgroups and on different hardware units.  
Because the Hopper Tensor Cores (exposed as the `WGMMA` instruction) are **asynchronous** and can pull their operands directly from shared memory, a warp that is waiting for a soft‑max to finish does not have to idle while another warp is issuing a new GEMM. The only thing that has to be preserved across iterations is the data that later stages need: the current score tile $S_{\text{cur}}$ and the already‑computed soft‑max tile $\widetilde P_{\text{cur}}$. Both of these can be kept in registers, which are private to each thread and therefore do not interfere with the shared‑memory loads performed by the producer warpgroup.

Below is a walk‑through of one iteration of the inner loop in **Algorithm 2** (the consumer warpgroup).  
For clarity I will label each step with the hardware resource that actually executes it:

| Cycle (conceptual) | What happens | Where the data lives | How asynchrony breaks the dependency |
|--------------------|--------------|----------------------|--------------------------------------|
| **0** | The warpgroup has already finished loading `K_j` from global memory into shared memory. | `K_j` sits in SMEM, `Q_i` is already in SMEM. | – |
| **1** | **Issue** `WGMMA` to compute `S_next = Q_i · K_jᵀ`. The instruction is launched but **not waited for** (`commit‑but‑don’t‑wait`). | The operand tiles stay in SMEM; the partial result `S_next` is streamed into a set of registers (`S_next_reg`). | Because `WGMMA` works asynchronously, the warp can continue issuing other instructions while the Tensor Core works on this multiplication. |
| **2** | Meanwhile, the previous iteration’s value `V_{j‑1}` has already been loaded into SMEM by the producer warpgroup. The consumer now **issues** a second `WGMMA`: `$O_i \leftarrow O_i + \widetilde P_{\text{cur}} \cdot V_{j‑1}$`. Again it is committed without waiting. | $\widetilde P_{\text{cur}}$ was produced in the *previous* iteration and resides in registers; $V_{j‑1}$ lives in SMEM. The product is accumulated directly into the output register file (`O_i_reg`). | The two GEMMs are independent: they use disjoint operand tiles (`K_j` vs. $V_{j‑1}$) and distinct output registers, so they can run concurrently on separate Tensor Core pipelines (or sequentially but overlapped with non‑Tensor‑Core work). |
| **3** | Now we **wait for** the first GEMM (`S_next`) to finish. When it does, its register tile contains the raw scores for block $j$. | `S_next_reg` now holds valid numbers. | The wait point is placed *after* we have already started the second GEMM, so no idle time remains. |
| **4** | **Softmax stage**: using `S_next_reg` we compute  
  $m_i = \max(m_i^{\text{old}}, \text{rowmax}(S_{\text{next}}))$  
  $\widetilde P_{\text{next}} = \exp(S_{\text{next}} - m_i)$  
  $\ell_i = \exp(m_i^{\text{old}}-m_i)\,\ell_i + \text{rowsum}(\widetilde P_{\text{next}})$.  
All of these operations are simple elementwise arithmetic and an exponential, which run on the CUDA cores (the “special‑function unit”). They operate entirely on data that lives in registers (`S_next_reg`, $m_i$, $\ell_i$). | Registers only. | Because this work is happening on a completely different functional unit than the Tensor Cores, it can occupy cycles that would otherwise be wasted while waiting for matrix multiplication results. |
| **5** | **Wait for** the second GEMM (`O_i += \widetilde P_{\text{cur}}\cdot V_{j‑1}`) to finish, then **rescale** `$O_i$` by the factor $\exp(m_i^{\text{old}}-m_i)^{-1}$. This rescaling also uses only registers. | `O_i_reg`, $\widetilde P_{\text{cur}}$ (still in registers), scaling factor from step 4. | Again there is no stall: as soon as both productions are ready (the softmax result from step 4 and the accumulation from step 2), they are combined immediately. |
| **6** | Finally we *rotate* buffers: copy `S_next_reg → S_cur_reg`, move `\widetilde P_next_reg → \widetilde P_cur_reg`, and release the shared‑memory slots used for `K_j` and `V_{j‑1}` so that the producer warpgroup can load `K_{j+1}` / `V_{j}`. | All data needed for the next iteration is now in registers; shared memory is free for new loads. | The next loop iteration can start at step 1 without any dependency on what happened earlier, because all cross‑iteration state lives in registers. |

In short, **the dependency chain looks like this when drawn naïvely**

```
S_cur  →  softmax  →  \tilde P_cur  →  second GEMM  →  O_i
   ↑                                            ↓
   └─────── first GEMM (needs S_cur) ────────────┘
```

but after introducing two *register buffers* (`S_next_reg` and `\tilde P_cur_reg`) we obtain three *pipelines* that run in lock‑step:

```
pipeline A (first GEMM):    S_cur → S_next
pipeline B (softmax):       S_next → \tilde P_next
pipeline C (second GEMM):   \tilde P_cur → O_i
```

Because each pipeline uses a different hardware engine (Tensor Core vs. CUDA cores) and because all data that must be handed from one pipeline to another stays inside each thread’s register file, no thread ever has to wait for a global memory operation or for another warpgroup’s instruction stream. The only synchronisation points are lightweight *barriers* that tell a warpgroup “the tile you need has been produced”, which on Hopper are essentially a few nanoseconds.

### Why registers make this possible

*Registers are private* – they do not need any coherence protocol between warps; once a warp writes a value into its own register file, another warp cannot see it until it is explicitly copied into shared memory or global memory. By keeping both $S_{\text{next}}$ and $\widetilde P_{\text{cur}}$ in registers we avoid any such copy, eliminating both latency and bandwidth pressure.

*Register capacity is limited*, which is why FlashAttention‑3 carefully chooses block sizes ($B_r,B_c$) so that a tile of scores ($B_r\times B_c$) fits comfortably in per‑thread registers after being split among the 32 threads of a warp (each thread holds roughly $B_r B_c/32$ elements). If a tile were larger than what can be kept in registers, we would have to spill to shared memory and reintroduce a real dependency.

### Connection to broader concepts

What FlashAttention‑3 does here is essentially a classic *software pipeline*: each stage produces data needed by the next stage but does so early enough that while stage i works on iteration k, stage i+1 can already start work on iteration k+1 using its own private buffer. In CPU literature this pattern appears as “loop‐carried dependence breaking” with double buffering; on GPUs it becomes even more powerful because different functional units can truly operate concurrently.

The technique also mirrors what compilers do for *producer–consumer* pipelines on heterogeneous architectures: separate queues for compute vs. special function units, with explicit synchronization only at queue boundaries. By exposing those queues explicitly through warp specialization (`producer` warps issuing TMA loads, `consumer` warps issuing WGMMAs), FlashAttention‑3 lets us write exactly those synchronization points instead of relying on an opaque compiler schedule.

---

**Bottom line:**  
The apparent serial dependency between softmax and GEMM disappears once we store each iteration’s intermediate score tile (`S_next`) and its softmaxed version (`\tilde P_cur`) in per‑thread registers. This enables two asynchronous WGMMAs (the first producing scores for iteration $j+1$, the second consuming softmaxed scores from iteration $j$) to overlap with each other and with elementwise/exponential work performed by CUDA cores. The result is much higher Tensor‑Core utilization—up to 75 % on H100—without sacrificing correctness because all cross‑iteration data movement stays inside fast register space.
