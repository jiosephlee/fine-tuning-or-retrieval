\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### What are the computational trade‑offs between FeatLLM’s 30 API calls and a single end‑to‑end LLM inference per sample?
Question:
The paper states that FeatLLM requires only 30 API queries irrespective of test set size, whereas in‑context baselines query per test sample. Could someone break down the time/money cost of those 30 calls (including temperature setting) compared to, say, 10 000 test samples processed with an LLM at 0.02 $/1K tokens? How does this scale with dataset size?
Answer:
**Answer**

In *FeatLLM* the LLM is only consulted during a short “feature‑engineering” phase.  
All of the heavy lifting – turning the generated rules into binary columns and
training a tiny linear model – is done locally on the user’s machine.  
Consequently the total number of API calls is fixed (30 in the paper) no matter how many test‑time rows you have.

---

### How many tokens are actually sent to the API?

A single “rule‑generation” query consists of three parts (Section 3.1 of the paper):

1. A **task description** (≈ 30 tokens),
2. A few‑shot *demonstration* block (the authors use 4–8 examples; each example is a
   serialized row, roughly 40 tokens on average),
3. A **reasoning instruction** and **response format** (≈ 50 tokens).

The authors report that each query stays well under the GPT‑3.5‑turbo context window
(4 K tokens) and that the LLM’s answer (≈ 10 rules) adds another ≈ 150 tokens.
Putting these numbers together gives about **500 tokens per call**.

$$
\text{Tokens per call} \;\approx\; 5\times10^{2}
$$

Since *FeatLLM* makes **30 calls**, the total token consumption for the whole
feature‑engineering stage is roughly

$$
30 \times 5\times10^{2} = 1.5\times10^{4}\;\text{tokens}.
$$

---

### Monetary cost

OpenAI’s public pricing for *gpt‑3.5‑turbo* (the model used in the experiments) is
\$0.02 per 1 000 input + output tokens.

$$
\text{Cost}_{\text{FeatLLM}} = 
\frac{1.5\times10^{4}}{10^{3}} \times \$0.02 \;\approx\; \$0.30 .
$$

That amount is paid **once**, regardless of whether you later evaluate 100, 1 000,
or 100 000 test instances.

---

### What does a naïve in‑context baseline cost?

The baselines that treat the LLM as an end‑to‑end predictor must send every test
sample through the model.  A typical serialized row contains:

* feature names + values → ≈ 150 tokens,
* a short “question” prompt → ≈ 30 tokens,
* plus the model’s answer (the class label) → ≈ 5 tokens.

So each test sample costs roughly **185 tokens**.

For a dataset with *N* test rows, the token count is

$$
\text{Tokens}_{\text{baseline}} \approx 185 \times N .
$$

At \$0.02 per 1 K tokens this yields

$$
\text{Cost}_{\text{baseline}} \approx 
\frac{185\,N}{10^{3}} \times \$0.02 = 
\$3.7\times10^{-3} \, N .
$$

*Example*: with **10 000** test rows

$$
\text{Cost}_{\text{baseline}} \approx 
\$3.7\times10^{-3}\times10^{4}
= \$37 .
$$

In contrast, *FeatLLM* still costs only about **\$0.30**, a more than **100×**
reduction.

---

### Time cost / latency

*FeatLLM* performs the 30 API calls **sequentially** in the paper, which on a
typical internet connection takes roughly **1–2 s per call** (including server
queueing).  Hence the whole engineering phase finishes in **≈ 30–60 seconds**.
After that, inference on each test row is just a dot product with a handful of
binary features, i.e. micro‑seconds per row on a CPU.

For the naïve baseline, each test row incurs a full forward pass through the LLM.
Even assuming an optimistic **200 ms latency per request**, processing 10 000
rows would take **≈ 33 minutes**, plus the same monetary cost computed above.

---

### Scaling behaviour

| #test rows | FeatLLM cost | FeatLLM time | Naïve baseline cost | Naïve baseline time |
|-----------|--------------|--------------|----------------------|---------------------|
| 100       | ≈ \$0.30     | ≈ 30–60 s    | ≈ \$0.37             | ≈ 20 s              |
| 1 000     | ≈ \$0.30     | ≈ 30–60 s    | ≈ \$3.7              | ≈ 3 min             |
| 10 000    | ≈ \$0.30     | ≈ 30–60 s    | ≈ \$37               | ≈ 33 min            |
| 100 000   | ≈ \$0.30     | ≈ 30–60 s    | ≈ \$370              | ≈ 5½ h              |

The *FeatLLM* column stays essentially flat because its cost depends only on
the fixed number of engineering queries, not on dataset size.
The baseline column grows linearly with *N* both in dollars and wall‑clock time.

---

### Take‑away

*FeatLLM* amortises a single, modest LLM bill (≈​\$0.3) over any number of test
samples and reduces latency from seconds per row to negligible CPU time.
When you have thousands or more rows, this translates into savings of tens to
hundreds of dollars and orders‑of‑magnitude faster inference—exactly why the
paper emphasises “only 30 API queries irrespective of test set size”.
