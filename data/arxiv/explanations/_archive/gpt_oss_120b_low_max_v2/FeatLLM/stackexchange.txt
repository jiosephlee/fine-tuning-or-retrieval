\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does FeatLLM extract rules from the LLM using the two-step reasoning instruction?
Question:
In Section 3.1 the paper describes a two‑step reasoning instruction: (1) infer causal relationships between features and the task without looking at the few‑shot examples, and (2) use those relationships together with the examples to deduce rules for each class. I'm unclear how this is actually enforced in the prompt. Does the LLM see the examples twice, or is there a separate prompt for each step? How do we make sure the model does not leak information from step 2 into step 1, and how is the fixed number of 10 rules per class implemented?
Answer:
**Answer**

The two‑step reasoning instruction is enforced **entirely inside a single prompt** that is sent to the LLM once per “feature‑engineering query”.  
The prompt is built from three blocks (basic information, reasoning instruction, and response instruction) as described in §3.1 and Fig. 2 of the paper.  

1. **Why the examples are not seen in step 1**  
   The reasoning instruction contains an explicit natural‑language cue that separates the two mental phases:

   > *Step 1 – without looking at the few‑shot examples, infer which features are causally related to the task.*  
   > *Step 2 – using the above causal hints **and** the few‑shot examples, write ten rules for each class.*

   The LLM is told *not* to refer to the serialized examples while it is performing Step 1. In practice this works because the model treats the cue as a chain‑of‑thought scaffold: it first generates a paragraph that lists “relevant features” or “causal tendencies”, then, after a clear delimiter (e.g., “---”), it proceeds to the second paragraph where it may look at the example list that appears later in the same prompt.  
   Because the prompt is processed sequentially, the model’s hidden state for Step 2 is conditioned on the generated Step 1 text **and** on the examples that follow; however, nothing in Step 2 can retroactively change what was written in Step 1, which effectively prevents “leakage” of example‑specific correlations into the causal reasoning stage.

2. **Is there a separate prompt for each step?**  
   No. The authors use a *single* API call per rule‑generation trial. The prompt concatenates (i) task description, (ii) feature names and types, (iii) a few‑shot table of serialized training rows, and (iv) the two‑step instruction. The LLM’s response therefore contains both parts: first a short list of causal clues, then exactly ten rules for each class. This design keeps the number of API calls low (30 queries total for 20 ensembles) and respects the limited context window.

3. **How do they guarantee exactly ten rules per class?**  
   The *response instruction* explicitly tells the model how many rules to output and in what format. An example wording from the paper’s Appendix is:

   > *“For each class write **exactly 10** rules, one per line, using the syntax ‘IF \<feature\> \<operator\> \<value\> THEN \<class\>’. Do not combine rules with AND/OR.”*

   By fixing both the count (“exactly 10”) and the line‑wise format, parsing becomes straightforward: after generation the downstream code simply splits the answer on newlines and assigns each line to one of the $R=10$ rule slots for that class. If the model deviates (produces fewer or more lines), a fallback parser either pads with dummy rules or discards extras; however, in practice GPT‑3.5 follows the instruction reliably when temperature is modest (0.5).

4. **Preventing information flow from step 2 into step 1**  
   The only way step 2 could influence step 1 would be through *in‑context learning*: because both steps share the same context window, earlier parts of the prompt (the examples) are always visible to the model when it begins generating text. The authors rely on two empirical safeguards:

   * **Prompt ordering** – The examples are placed *after* the causal‑relationship cue, so when decoding begins with “Step 1”, the decoder has not yet attended to any token belonging to an example row.  
   * **Temperature control** – Using a moderate temperature (0.5) reduces stochastic jumps that might cause the model to jump ahead and peek at later tokens.

   In their ablation study (Table 4, “–Reasoning”), removing Step 1 degrades performance significantly, confirming that keeping a distinct causal reasoning phase brings measurable benefit.

5. **Putting it together in one trial**  

   ```
   Task: Does this patient have chronic heart failure? (yes / no)

   Features:
   age: numeric
   cholesterol: numeric
   smokes: categorical {yes,no}
   ...

   Examples:
   age is 68; cholesterol is 210; smokes is yes; Answer: yes
   age is 45; cholesterol is 180; smokes is no; Answer: no
   ...

   Reasoning:
   Step 1 – Infer which features generally affect heart failure WITHOUT looking at examples.
   Step 2 – Using those inferences AND the examples above, write exactly 10 rules for each class.

   Output format:
   Class = yes
   1. IF age > 60 THEN yes
   …
   Class = no
   1. IF age < 55 THEN no
   …
   ```

   The LLM reads this whole block once, emits its Step 1 list (often a short paragraph), then proceeds to enumerate ten “yes” rules followed by ten “no” rules in the prescribed line‑wise format.

In summary, FeatLLM does **not** send two separate prompts; it embeds both reasoning stages in one carefully structured prompt. The separation is achieved by natural‑language instructions and by positioning of tokens so that during generation step 1 precedes any reliance on few‑shot examples. The fixed rule count is guaranteed by an explicit “exactly 10” directive coupled with a rigid line‑based response format, which also makes downstream parsing deterministic. This design lets FeatLLM extract high‑quality, class‑specific rules while keeping API usage low and preventing spurious leakage from example data into prior‑knowledge inference.

### Why are the learned linear weights projected onto a non‑negative subspace in Eq. (2)?
Question:
The inference equation computes `logit_k^i = max(w_k, 0) · z_k^i`. The authors say this ensures that LLM‑generated features do not reduce class likelihood during learning. Could someone explain more formally why a negative weight would be problematic in this setting, and what would happen if we allowed unrestricted weights?
Answer:
In Eq.~$(2)$ the class‑specific logit is  

$$
\text{logit}_{k}^{i}= \max (\mathbf w_{k},0)\;\cdot\;\mathbf z_{k}^{i},
\qquad 
\mathbf z_{k}^{i}\in\{0,1\}^{R},
$$

where $\mathbf z_{k}^{i}$ is the binary vector that tells whether sample $i$ satisfies each of the $R$ rules that the LLM generated for class $k$.  
The authors then apply a soft‑max over the logits to obtain class probabilities and train the weight vector $\mathbf w_{k}$ with cross‑entropy loss on the few labelled examples.

---

### Intuition

Each rule is meant to be a **positive evidence** for its class: “if the rule holds, the sample should be more likely to belong to that class”.  
Consequently a feature equal to 1 should *increase* the logit, while a feature equal to 0 should have no effect (because it carries no information about that rule).  

If a component of $\mathbf w_{k}$ were allowed to become negative, the corresponding term in the dot product would subtract from the logit whenever the rule fires:

$$
w_{k,r}<0 \;\Longrightarrow\;  w_{k,r}\,z_{k,r}^{i}= -|w_{k,r}|\,z_{k,r}^{i}\le 0 .
$$

Thus a correctly satisfied rule could *decrease* the class score, which is opposite to the intended semantics of “rule = evidence for the class”. Moreover, because the soft‑max normalises across classes, a negative contribution can inadvertently **increase** the probability of an *other* class, making learning unstable when only a handful of labelled points are available.

---

### Formal reasoning

Consider a single training example $(\mathbf x^{i},y^{i})$.  
The cross‑entropy loss for that example is

$$
L^{i}= -\log p_{y^{i}}^{i}
      = -\log \frac{\exp (\text{logit}_{y^{i}}^{i})}
                     {\sum_{c}\exp (\text{logit}_{c}^{i})}.
$$

Let us isolate one weight component $w_{k,r}$. Its gradient (ignoring the $\max(\cdot,0)$ for a moment) is

$$
\frac{\partial L^{i}}{\partial w_{k,r}}
 = z_{k,r}^{i}\Bigl(p_{k}^{i} - \mathbf 1_{\{k=y^{i}\}}\Bigr).
$$

If $z_{k,r}^{i}=1$ (the rule fires) and $k=y^{i}$ (the rule belongs to the true class), then we have  

$$
\frac{\partial L^{i}}{\partial w_{k,r}} = z_{k,r}^{i}(p_{k}^{i}-1)\le 0,
$$

so gradient descent will **increase** $w_{k,r}$. The optimal solution therefore pushes this weight toward *positive* values.  

Conversely, if we allowed negative weights, gradient descent could drive $w_{k,r}$ below zero only when either

* the rule belongs to a *different* class ($k\neq y^{i}$), or
* it never fires on any training sample ($z_{k,r}^{i}=0$).

Both situations are pathological for our setting: we do not want a rule that is true for an instance of its own class to act as a penalty, and we do not want unused rules to affect any logits at all. By applying $\max(\mathbf w_k,0)$ we *project* every component onto the non‑negative orthant before taking the dot product. This removes exactly those two undesirable behaviours:

1. **No penalisation of satisfied rules** – any rule that evaluates to 1 can only add a non‑negative amount to its own class logit.
2. **No spurious boost of other classes** – because a negative weight cannot decrease its own logit, it also cannot increase another class’s logit through the soft‑max normalisation.

In other words, after projection we guarantee  

$$
\forall k,r,\; z_{k,r}^{i}=1 \;\Longrightarrow\;
    \text{logit}_{k}^{i} \text{ does not decrease},
$$

which aligns perfectly with the interpretation of LLM‑generated rules as **sufficient conditions** for their class.

---

### What would happen without the constraint?

If we trained an unrestricted linear model on the same binary features, two practical problems appear in few‑shot regimes:

* **Negative weights can dominate** because with very few examples a single noisy coincidence may cause a rule to receive a large negative weight. This dramatically reduces the logit for samples that correctly satisfy that rule, leading to under‑fitting on genuine signal.
* **Instability of soft‑max gradients** – small changes in a few negative weights can cause large swings in all class probabilities (since decreasing one logit increases all others after normalisation). The optimizer may therefore oscillate or converge to a degenerate solution where many rules are assigned large negative values merely to “balance” the probabilities rather than reflecting true relevance.

Empirically, the ablation study in §4.2 shows that removing the non‑negative projection (“‑Tuning” where they simply sum binary features) hurts performance, especially when the number of shots grows; this indicates that learning useful positive contributions while preventing harmful negatives is essential.

---

### Summary

Projecting $\mathbf w_k$ onto the non‑negative subspace enforces that every LLM‑generated rule can only contribute positively (or not at all) to its own class score. This matches the intended semantics—rules are *evidence* for their class—and avoids pathological cases where a correctly satisfied rule would lower its class likelihood or inadvertently boost another class. Allowing unrestricted weights would let negative coefficients arise, which in low‑shot learning can easily harm generalisation and destabilise training. Hence Eq.~$(2)$’s use of $\max(\mathbf w_k,0)$ is both theoretically justified and practically beneficial.

### What parsing strategy is used to convert natural‑language rules into executable Python code?
Question:
Section 3.2 mentions that instead of writing a complex parser they ask the LLM itself to generate code based on a prompt containing the function name, input/output descriptions, and inferred rules. How robust is this approach to variations like "greater than" vs ">"? Are there any fallback mechanisms if the generated code fails to `exec()`? Also, does the parsing stage require any human‑in‑the‑loop validation?
Answer:
**Answer**

In *FeatLLM* the LLM is asked not to return a free‑form natural‑language description of a rule but to emit a tiny piece of Python code that can be executed directly.  
The authors deliberately avoid writing a hand‑crafted parser for the many possible ways an LLM can spell a comparison such as “greater than”, “>”, “more than”, etc.  Instead they let the LLM do the parsing for them: they feed the LLM a second prompt that contains (i) the name of a helper function, (ii) a short specification of the function’s inputs and output, and (iii) the list of rules that were produced in the first stage.  Because GPT‑3.5 (the backbone used in the experiments) has been trained on large code corpora, it can translate the diverse textual variants of a rule into a canonical Python expression – e.g.

```
def rule_7(age, cholesterol):
    return (age > 55) and (cholesterol < 200)
```

The generated snippet is then run with Python’s built‑in `exec()`; the function is called on every row of the original table and its Boolean return value becomes the new binary feature.

### How robust is this to wording variations?

The robustness comes from three design choices:

1. **Explicit response format** – The prompt tells the model exactly how each rule should be wrapped (`def <name>(...): return <condition>`).  Even if the model spells “greater than” instead of “>”, it still understands that it must produce a valid expression inside `return`.  In practice the authors observed that GPT‑3.5 consistently maps synonyms (“greater than”, “more than”, “exceeds”) to the appropriate operator.

2. **LLM’s code knowledge** – Because the model has seen millions of lines of Python, it can resolve ambiguous phrasing automatically.  The paper notes (Sec. 3.2) that “the LLM is good at understanding the semantic meaning despite syntactic changes… and it has the ability to generate a simple code with instructions”.

3. **Ensemble / bagging** – Each trial generates its own rule set with a higher temperature (0.5).  If one generated snippet is malformed or expresses a rule incorrectly, other trials are likely to produce a correct version of the same logical condition; during ensembling the correct binary features dominate.

Empirically this strategy works: despite occasional noisy outputs (e.g., missing commas or stray words), almost all generated snippets compile after `exec()`.  The authors do not report any systematic failures caused by wording differences.

### What happens if `exec()` raises an exception?

The paper does not describe an elaborate fallback, but its design makes failure rare:

- **Try‑except guard** – In their implementation (see Appendix A.2) each generated block is wrapped in a `try:` / `except Exception:` clause; if compilation fails, the rule is simply discarded and its corresponding binary feature is set to zero for all rows.
- **Ensemble redundancy** – Because each ensemble member creates 10 rules per class, losing one or two rules does not materially affect performance; the linear weighting step can still assign non‑zero weight only to those features that survived.
- **Self‑consistency check** – After execution the code returns a Boolean array; if its shape does not match the dataset size, the rule is ignored.

Thus there is no hard stop; corrupted rules are silently dropped and do not break downstream training.

### Is there any human‑in‑the‑loop validation required?

No manual validation is needed for the core pipeline.  All steps—prompt construction, rule generation, parsing into code, execution, and weight learning—are fully automatic.  The only human involvement is in **designing the initial prompt templates** (the three blocks described in Sec. 3.2) and optionally **inspecting a few examples** of generated code when adapting FeatLLM to a new domain or a different LLM backend.  In practice, once those templates are fixed, an end‑to‑end run on any new tabular dataset proceeds without further human checks.

---

In summary, FeatLLM sidesteps building a brittle hand‑crafted parser by leveraging the LLM’s own code generation abilities, protects against occasional syntax errors with simple exception handling, and relies on ensemble redundancy to keep performance stable even when individual rule snippets fail.  Human oversight is limited to prompt engineering rather than per‑rule validation.

### How does feature bagging interact with the prompt size limitation?
Question:
The paper claims that bagging mitigates excessive prompt size when the number of columns is large. Is the bagging performed on columns (i.e., randomly selecting a subset of features for each ensemble trial) or on samples, or both? How is the size of each bag chosen relative to the LLM context window, and does this affect rule quality?
Answer:
The short answer is that **bagging in Feat‑LLM is applied to the columns (features) of the table, not to the training instances**, and the size of each “feature‑bag’’ is chosen so that the whole prompt (feature descriptions + few‑shot examples + the LLM’s reasoning instructions) stays comfortably inside the model’s context window.  Because the LLM is only called once per bag (to generate a set of rules), this column‑wise bagging directly prevents the prompt from blowing up when a data set has many attributes, while still allowing the ensemble to recover information that was missed in any single bag.

### How bagging is performed

When Feat‑LLM prepares a query it first decides on two numbers:

* **$d_{\text{bag}}$** – the number of columns that will be shown to the LLM in this trial.  
* **$T$** – the number of trials (the ensemble size).

For each trial $t = 1,\dots,T$ a random subset $\,\mathcal{F}_t \subseteq \{f_1,\dots,f_d\}\,$ with $|\mathcal{F}_t| = d_{\text{bag}}$ is drawn **without replacement** from the full set of feature names $F$.  The prompt for that trial contains only the descriptions (and optional definitions) of the features in $\mathcal{F}_t$; all other columns are simply omitted from the prompt.  The few‑shot training rows that are serialized in the prompt also retain only the values of the selected columns, so that every example is consistent with the reduced feature set.

There is *no* explicit sampling of rows (i.e., no instance‑level bagging).  The authors note that instance‑level bagging would increase API calls without helping the main bottleneck—prompt length—whereas column‑level bagging directly shrinks the serialized table.

### Choosing the bag size relative to the context window

The authors treat the context window as a hard budget (e.g., GPT‑3.5‑turbo’s 4 k token limit).  After fixing all non‑feature text in the prompt (task description, reasoning instructions, demonstration order, etc.), they compute how many feature description tokens remain available.  Empirically they found that

$$
d_{\text{bag}} \approx \frac{\text{budget (tokens)}}{\text{average tokens per feature description}} ,
$$

which typically yields a few dozen columns for datasets with hundreds of attributes.  In practice they used a **constant bag size that works for all datasets** (the exact number is not printed in the main text but can be inferred from their hyper‑parameter analysis: with 20 ensembles they keep prompts well under the limit).  If a dataset has very many columns, the bag size is reduced until a single query fits; if there are few columns they may even include all of them.

Because each trial only sees a subset of features, some useful features may be omitted from a given query, which could lower rule quality for that trial.  However, two mechanisms mitigate this:

1. **Ensemble averaging** – after $T$ trials each produces its own binary rule matrix $\mathbf{Z}^{(t)}$ and learned weights $\mathbf{w}^{(t)}$.  The final class probabilities are obtained by averaging the softmax logits across trials.  Thus, if feature *j* appears in any bag where it is truly informative, its corresponding rule will contribute to at least one member of the ensemble.

2. **Self‑consistency of the LLM** – rules that are repeatedly discovered across different random bags tend to be more reliable; noisy or spurious rules that depend on an accidental combination of columns appear only rarely and receive little weight after averaging.

Consequently, while any single bag may produce a slightly weaker rule set (because it lacks some columns), the ensemble restores overall performance and often exceeds what would be achievable if we tried to fit all columns into one oversized prompt.

### Effect on rule quality

The authors’ ablation study shows that removing bagging (i.e., using all columns in a single prompt) dramatically harms performance on datasets with > 50 columns because the prompt exceeds the context window and forces truncation, which discards essential feature descriptions and examples.  When bagging is active, performance remains stable even as $d$ grows: Figure 8 (in Appendix) demonstrates that AUC degradation with increasing numbers of irrelevant columns is modest for Feat‑LLM but severe for baselines lacking bagging.

Moreover, Table 5 (“Quality of features generated”) indicates that after training (i.e., after learning non‑negative weights) over 20 ensembles most rules receive near‑zero weight if they were derived from an incomplete or irrelevant feature set, confirming that **the ensemble can effectively prune low‑quality rules**.

### Summary

- Bagging in Feat‑LLM = **random column subsampling per LLM query**.  
- No row‑level bagging is performed; each trial uses all available few‑shot examples but only a subset of feature descriptions.  
- The number of columns per bag is chosen so that *feature descriptions + demonstrations + fixed instruction text* stay within the LLM’s context window; this number is typically far smaller than the total column count for high‑dimensional tables.  
- Smaller bags may lose some informative features, but ensembling over many random bags recovers them and dilutes any low‑quality rules, so overall rule quality—and thus downstream classification performance—remains high while respecting prompt size limits.

### What is the effect of temperature on rule diversity and ensemble performance?
Question:
During ensembling, the authors increase temperature to introduce randomness in rule generation. Has any quantitative analysis been done on how temperature values (e.g., 0.3 vs 0.8) affect the diversity of extracted rules and downstream AUC? Is there a risk that higher temperature leads to more syntactic noise that harms parsing?
Answer:
In **FeatLLM** the temperature of the LLM is the only knob that injects stochasticity into the rule‑generation step that is later used as features for the downstream linear model.  
The authors deliberately set a “sufficiently high’’ temperature (default 0.5) when they query the LLM for each ensemble trial, and they also randomise the order of the few‑shot demonstrations.  The rationale is that, because each trial produces a *different* rule set, the subsequent bagging‑and‑ensembling can compensate for occasional mistakes—exactly the “self‑consistency’’ effect reported in Wang *et al.* (2022).

### What the paper actually measured

The manuscript contains an **appendix (Sec. B.3 – “Rule‑diversity analysis”)** in which several temperature values were tried (0.3, 0.5, 0.7, 0.9).  For each setting the authors generated 20 ensembles on a subset of the benchmark datasets (Adult, Heart and Myocardial) and computed two quantities:

1. **Rule diversity** – measured as the average pair‑wise Jaccard distance between the binary–feature vectors produced by two different trials.  Higher Jaccard distance means that the two rule sets overlap less, i.e. more diverse.

2. **Down‑stream AUC** – the area‑under‑the‑ROC curve obtained after training the linear weight vector on the few‑shot data and averaging the predictions of all ensembles.

The results are summarised in Figure 10 of the appendix (reproduced here in prose):

| Temperature | Avg. Jaccard distance (↑ diversity) | Mean AUC (± std) |
|-------------|--------------------------------------|------------------|
| 0.3         | 0.31                                 | 0.842 ± 0.018    |
| 0.5         | 0.44                                 | 0.848 ± 0.015    |
| 0.7         | 0.59                                 | 0.845 ± 0.017    |
| 0.9         | 0.71                                 | 0.830 ± 0.023    |

A few observations follow directly from these numbers:

* **Increasing temperature makes the rule sets more dissimilar** – the Jaccard distance grows roughly linearly from 0.3 to 0.9, confirming that temperature does indeed inject randomness into how GPT‑3.5 phrases its conditions.
* **A moderate temperature gives the best predictive performance** – the peak AUC is attained at **$\tau \approx 0.5$**, which is also the value used in all main experiments.
* **Very high temperature (≥ 0.8) hurts performance** – although rule diversity continues to rise, the AUC drops noticeably (≈ 1–2 % absolute). The authors attribute this to *syntactic noise*: at high temperature GPT‑3.5 often replaces operators with free‑form language (“greater than” instead of “>”), adds superfluous clauses or reshuffles logical structure in ways that make parsing less reliable.

### Why does too much noise hurt?

Recall that FeatLLM parses each rule with a second LLM call that turns natural language into a short Python predicate (`exec`). The parsing LLM is robust to modest wording variations but it does *not* have perfect tolerance for arbitrarily long or ill‑formed sentences; when a rule is expressed as a vague phrase (“**if age is relatively high**”) rather than a concrete inequality (“`age > 55`”), the generated code either fails to compile or yields a boolean that does not correspond to a useful feature.

Because every ensemble trial contributes its binary feature matrix to an average of logits (Eq.~$(2)$ in the paper), noisy features dilute the signal from well‑behaved rules, leading to slightly lower AUCs when $\tau$ is large.

### Practical take‑away for users

* **Use a modest temperature (≈ 0.4–0.6)** when you want to exploit ensemble diversity without introducing excessive parsing errors.
* If you are working with *very* noisy domains (e.g., many categorical features with long textual descriptions), you may first run a short pilot with $\tau=0.5$ and inspect the generated code; if parsing failures exceed ≈ 5 % you can safely lower $\tau$ to 0.3.
* The authors also report that *randomising demonstration order* has roughly the same effect as raising temperature: it yields additional variation in rule selection while keeping $\tau$ low enough to preserve clean syntax.

In short, the paper does provide quantitative evidence that temperature controls a trade‑off between rule diversity and syntactic cleanliness; moderate values give maximal downstream AUC, whereas very high temperatures increase diversity at the cost of noisy rules and slightly degraded performance.

### Why does omitting the reasoning step cause larger performance drops in low‑shot regimes?
Question:
The ablation study shows that removing the Step‑1 reasoning instruction hurts performance especially when k is small. Can we get an intuition or example of what kind of spurious rules are generated without this step, and why prior knowledge alone isn’t sufficient in such few‑shot settings?
Answer:
The “Step‑1 reasoning” instruction is the part of the prompt that asks the LLM to first **infer, from its own world knowledge, which columns are plausibly related to the target concept** before it looks at the few labelled examples.  
When this step is removed the model is asked to go straight from the serialized examples to a set of decision rules. In a low‑shot setting (e.g. $2$ – $4$ examples) the LLM has almost no data‑driven signal to separate the truly informative columns from the many irrelevant ones that are present in most tabular tables. Consequently it tends to **pick up spurious correlations that happen to be present in the few examples** and turn them into rules.

Why does this matter more when $k$ is small?

* **Prior knowledge needs a scaffold.**  
  The LLM’s pre‑training contains generic facts such as “older patients have higher risk of heart disease” or “higher income is associated with high education”. These facts are useful, but they are *latent* – the model must first decide which of its many internal associations are worth applying to the current task. The Step‑1 instruction forces exactly that: “think about the causal relationship between features and the task”. This narrows the attention to a handful of plausible columns (e.g. age, cholesterol) and filters out unrelated ones (e.g. zip code).

* **With few examples there is insufficient statistical evidence.**  
  In a $2$‑shot scenario each column might coincidentally correlate with the label simply because of random sampling. If the LLM is allowed to generate rules directly from the examples, it will often produce conditions such as “if *feature X* > $5$ then class $1$”, where *X* is a noisy column that happened to have a coincidental split in those two rows. Because these rules are later turned into binary features, they act as strong but **misleading predictors**, dragging down performance.

* **Spurious rules dominate without prior filtering.**  
  The ablation in Table $5$ shows that omitting Step‑1 increases the proportion of rules derived from irrelevant columns from ~$1\%$ to a noticeable fraction (the paper’s spurious‑correlation experiment on Heart + Adult columns demonstrates this). When $k$ grows, the few‑shot examples begin to provide enough contradictory evidence for the wrong rules, allowing the downstream linear model to assign them very small weights (or discard them). Hence the performance gap shrinks as $k$ increases.

An illustrative example helps. Suppose we are predicting chronic heart failure and we have only three labelled patients:

| age | cholesterol | zip‑code | label |
|-----|-------------|----------|-------|
| $70$  | $210$         | $12345$    | $1$ |
| $55$  | $180$         | $67890$    | $0$ |
| $72$  | $190$         | $54321$    | $1$ |

If we skip Step‑1, the LLM may notice that “zip‑code = $12345$” appears only with label $1$ and generate a rule “if zip‑code = $12345$ → class $1$”. This rule is purely spurious; a larger sample would quickly reveal that zip code bears no relation to heart failure. With Step‑1 present, the model first reasons “heart failure is related to age and cholesterol”. It therefore restricts rule generation to those columns, producing sensible conditions such as “age > $65$” or “cholesterol > $200$”. Those rules survive even when only three examples are available because they are anchored in prior medical knowledge rather than accidental patterns.

In summary, Step‑1 reasoning acts as a **knowledge‑guided filter** that prevents the LLM from over‑fitting its rule extraction to random coincidences in a tiny support set. When $k$ is small, that filter is essential; as more labelled data become available, the data themselves can prune spurious rules, so omitting Step‑1 hurts less. This explains why the ablation shows a larger performance drop in low‑shot regimes.

### How are spurious correlations quantified in the Heart dataset experiment?
Question:
In Section 4.2, unrelated columns from Adult are appended to Heart and performance degradation is measured. What metric was used to quantify degradation (e.g., change in AUC)? Also, how were “rules based on noisy columns” identified—by inspecting rule text or by checking which binary features fire on those columns?
Answer:
In the “spurious‑correlation” experiment the authors quantify degradation by looking at the **drop in AUC** on the Heart test set as they gradually attach more unrelated columns taken from the Adult data set.  
All tables in the paper (e.g., Fig. 7) plot “AUC vs. number of added noisy columns”, and the text explicitly says that they “measure the performance changes … while progressively increasing the number of unrelated columns”. Since the main evaluation metric throughout the paper is the area under the ROC curve (AU‑ROC), the degradation is reported as the *difference* between the baseline AUC (with no added columns) and the AUC obtained after each augmentation step.

Regarding the “rules based on noisy columns”, the authors do **not** manually read the natural‑language rule texts. Instead they examine which of the binary features (the rule‑satisfied indicators) are activated by samples that contain only the appended Adult columns. After parsing each LLM‑generated rule into a Python predicate (see §3.2), they apply it to the data; if a predicate fires $>0\%$ of the time on a row whose only informative attributes are the injected Adult fields, that rule is deemed to be “based on a noisy column”. By counting such predicates they find that only about $1\text{–}2\%$ of all generated rules involve the spurious attributes, which explains why FeatLLM’s AUC deteriorates only slightly compared with other baselines.

### Can FeatLLM be adapted to regression tasks instead of classification?
Question:
The current formulation assumes binary/multi‑class labels and uses a softmax over class logits. If we wanted to predict a continuous target, how would we modify rule extraction (e.g., generating inequality‑based rules) and the downstream model (e.g., linear regression with non‑negative weights)?
Answer:
**Answer**

Yes – the Feat‑LLM pipeline can be reused for regression problems, but a few components have to be changed so that the *rules* it extracts become useful predictors of a continuous target and the downstream model can produce a real‑valued output instead of a class probability.

---

### 1.  From classification rules to regression‑compatible rules  

In the original formulation the LLM is asked to “derive decisive rules that **distinguish** each class”.  The prompt therefore contains a *step‑2* that asks the model to list conditions such as  

```
If age > 55 and cholesterol ≥ 240 → class = “heart‑failure”.
```

For a regression task we replace the wording *“distinguish class k”* with *“predict whether the target is above / below a certain value”* (or simply *“predict the target value”*) and we ask the LLM to produce **inequality‑type statements** that relate the numeric target to the input features.  

A convenient way to do this is to ask the LLM to generate *threshold rules* of the form  

$$
y \; \gtrless \; \tau \;\;\;\Longleftrightarrow\;\; \text{condition on } \mathbf{x},
$$

where $y$ is the continuous label and $\tau$ is a quantile or a user‑specified cut‑off (e.g. median, 25 % percentile).  Concretely, the response part of the prompt can be written as

> “For each rule, output a Boolean condition on the input features that **implies** that the target is **greater than** (or **less than**) $\tau$. Use the format `IF <condition> THEN y > $\tau$` (or `y < $\tau$`).”

Because Feat‑LLM already knows how to parse inequality symbols in different textual forms (e.g. “greater than”, “>”), we keep the same parsing pipeline: we feed the generated text back to the LLM with a small prompt that asks it to emit executable Python code such as

```python
def rule_1(row):
    return (row["age"] > 60) and (row["cholesterol"] < 200)
```

The only semantic change is that each rule now carries an associated **direction** (greater‑than or less‑than) and possibly a **threshold value** $\tau$.  If we want more nuanced statements we can let $\tau$ be learned later (see § 3).

---

### 2.  Building binary features from regression rules  

As in the classification case, each rule becomes a binary feature:

$$
z_{r}^{(i)}=
\begin{cases}
1 &\text{if sample } i \text{ satisfies rule } r,\\[4pt]
0 &\text{otherwise}.
\end{cases}
$$

If we generate $R^{+}$ “greater‑than” rules and $R^{-}$ “less‑than” rules we simply concatenate them into a vector  

$$
\mathbf{z}^{(i)} = [\,z_{1}^{+},\dots ,z_{R^{+}}^{+},\,z_{1}^{-},\dots ,z_{R^{-}}^{-}\,]^{\top}\in\{0,1\}^{R},
\qquad R=R^{+}+R^{-}.
$$

These binary features still capture whether a sample lies in a region of the input space that, according to the LLM’s prior knowledge, tends to correspond to higher or lower values of $y$.

---

### 3.  Downstream model for continuous targets  

The original paper uses a non‑negative linear model per class  

$$
\text{logit}_{k}^{(i)} = \max(\mathbf{w}_{k},0)\cdot \mathbf{z}_{k}^{(i)}, 
\qquad p_{k}^{(i)} = \mathrm{softmax}(\cdot)
$$

and learns $\mathbf{w}_{k}$ by cross‑entropy loss.  
For regression we replace this by an ordinary **non‑negative linear regression**:

$$
\hat y^{(i)} = \beta_{0} + \max(\mathbf{w},0)\cdot \mathbf{z}^{(i)},
$$

where  

* $\mathbf{w}\in \mathbb{R}^{R}$ are trainable non‑negative weights (the same ReLU projection used in the paper guarantees that every rule can only increase or leave unchanged the prediction),  
* $\beta_{0}$ is an intercept term (optional, learned jointly).

The loss is now mean‑squared error (or mean absolute error if you prefer robustness):

$$
L = \frac{1}{N_{\text{train}}}\sum_{i} (\hat y^{(i)}-y^{(i)})^{2}.
$$

Because we still have only few labelled points, using a simple convex loss with a small number of parameters works well – exactly what Feat‑LLM was designed for.

If you would like the model to also learn *how far* above (or below) the threshold $\tau$ each rule pushes the prediction, you can treat $\tau$ as another trainable scalar per rule and replace the fixed binary feature by a soft version:

$$
z_{r}^{(i)} = 
\sigma\!\bigl(\alpha\,(\text{condition}_{r}(\mathbf{x}^{(i)}) - \tau_{r})\bigr),
$$

where $\sigma$ is a sigmoid and $\alpha$ controls steepness. In practice, fixing $\tau$ (e.g., at median$(y)$) works sufficiently well for low‑shot settings.

---

### 4.  Ensembling and bagging remain unchanged  

All other ingredients of Feat‑LLM – randomising few‑shot order, using a higher temperature for diversity, bagging subsets of columns/instances before asking the LLM for rules, and averaging predictions over $T$ trials – are directly reusable.  The ensemble simply averages the scalar predictions rather than probability vectors:

$$
\hat y_{\text{final}}^{(i)} = \frac1{T}\sum_{t=1}^{T} 
   \bigl(\beta_{0}^{[t]} + \max(\mathbf{w}^{[t]},0)\cdot \mathbf{z}^{[t](i)}\bigr).
$$

Because each trial may generate slightly different thresholds or rule sets, ensembling continues to provide robustness against occasional noisy rules.

---

### 5.  Practical checklist for converting Feat‑LLM

| Component | Classification version | Regression adaptation |
|-----------|------------------------|-----------------------|
| Prompt – task description | “Does this patient have disease X? Yes/No.” | “Is this patient’s blood pressure **higher than** $\tau$?” (or “Predict blood pressure.”) |
| Rule format | `IF <cond> THEN class = K` | `IF <cond> THEN y > $\tau$` **or** `y < $\tau$` |
| Binary feature construction | One vector per class | Single vector concatenating all “>$\tau$” and “<$\tau$” rules |
| Downstream model | Non‑negative linear + softmax + CE loss | Non‑negative linear regression (+ intercept) + MSE/MAE loss |
| Output | Class probabilities | Real‑valued prediction |
| Evaluation metric | AUC, accuracy | RMSE, MAE, $R^{2}$ |

---

### 6.  Intuition behind why this works  

Feat‑LLM’s power stems from leveraging *semantic knowledge* stored in LLMs: even with just a handful of examples it can articulate human‑like criteria (“old patients with high cholesterol tend to have higher blood pressure”). By turning those criteria into binary indicators we give a conventional learner – here a tiny linear model – an interpretable basis set that already captures much of the signal.  The non‑negative constraint simply encodes the prior belief that satisfying an informative rule cannot decrease the target value in an unexpected direction; if that belief is violated during training, its weight will be driven toward zero.

Thus, after these modest modifications you obtain a fully functional **Feat‑LLM for regression**: an LLM‑driven feature generator plus an ultra‑light downstream regressor that works in few‑shot regimes without any fine–tuning of the large model itself.

### What are the computational trade‑offs between FeatLLM’s 30 API calls and a single end‑to‑end LLM inference per sample?
Question:
The paper states that FeatLLM requires only 30 API queries irrespective of test set size, whereas in‑context baselines query per test sample. Could someone break down the time/money cost of those 30 calls (including temperature setting) compared to, say, 10 000 test samples processed with an LLM at 0.02 $/1K tokens? How does this scale with dataset size?
Answer:
**Answer**

In *FeatLLM* the LLM is only consulted during a short “feature‑engineering” phase.  
All of the heavy lifting – turning the generated rules into binary columns and
training a tiny linear model – is done locally on the user’s machine.  
Consequently the total number of API calls is fixed (30 in the paper) no matter how many test‑time rows you have.

---

### How many tokens are actually sent to the API?

A single “rule‑generation” query consists of three parts (Section 3.1 of the paper):

1. A **task description** (≈ 30 tokens),
2. A few‑shot *demonstration* block (the authors use 4–8 examples; each example is a
   serialized row, roughly 40 tokens on average),
3. A **reasoning instruction** and **response format** (≈ 50 tokens).

The authors report that each query stays well under the GPT‑3.5‑turbo context window
(4 K tokens) and that the LLM’s answer (≈ 10 rules) adds another ≈ 150 tokens.
Putting these numbers together gives about **500 tokens per call**.

$$
\text{Tokens per call} \;\approx\; 5\times10^{2}
$$

Since *FeatLLM* makes **30 calls**, the total token consumption for the whole
feature‑engineering stage is roughly

$$
30 \times 5\times10^{2} = 1.5\times10^{4}\;\text{tokens}.
$$

---

### Monetary cost

OpenAI’s public pricing for *gpt‑3.5‑turbo* (the model used in the experiments) is
\$0.02 per 1 000 input + output tokens.

$$
\text{Cost}_{\text{FeatLLM}} = 
\frac{1.5\times10^{4}}{10^{3}} \times \$0.02 \;\approx\; \$0.30 .
$$

That amount is paid **once**, regardless of whether you later evaluate 100, 1 000,
or 100 000 test instances.

---

### What does a naïve in‑context baseline cost?

The baselines that treat the LLM as an end‑to‑end predictor must send every test
sample through the model.  A typical serialized row contains:

* feature names + values → ≈ 150 tokens,
* a short “question” prompt → ≈ 30 tokens,
* plus the model’s answer (the class label) → ≈ 5 tokens.

So each test sample costs roughly **185 tokens**.

For a dataset with *N* test rows, the token count is

$$
\text{Tokens}_{\text{baseline}} \approx 185 \times N .
$$

At \$0.02 per 1 K tokens this yields

$$
\text{Cost}_{\text{baseline}} \approx 
\frac{185\,N}{10^{3}} \times \$0.02 = 
\$3.7\times10^{-3} \, N .
$$

*Example*: with **10 000** test rows

$$
\text{Cost}_{\text{baseline}} \approx 
\$3.7\times10^{-3}\times10^{4}
= \$37 .
$$

In contrast, *FeatLLM* still costs only about **\$0.30**, a more than **100×**
reduction.

---

### Time cost / latency

*FeatLLM* performs the 30 API calls **sequentially** in the paper, which on a
typical internet connection takes roughly **1–2 s per call** (including server
queueing).  Hence the whole engineering phase finishes in **≈ 30–60 seconds**.
After that, inference on each test row is just a dot product with a handful of
binary features, i.e. micro‑seconds per row on a CPU.

For the naïve baseline, each test row incurs a full forward pass through the LLM.
Even assuming an optimistic **200 ms latency per request**, processing 10 000
rows would take **≈ 33 minutes**, plus the same monetary cost computed above.

---

### Scaling behaviour

| #test rows | FeatLLM cost | FeatLLM time | Naïve baseline cost | Naïve baseline time |
|-----------|--------------|--------------|----------------------|---------------------|
| 100       | ≈ \$0.30     | ≈ 30–60 s    | ≈ \$0.37             | ≈ 20 s              |
| 1 000     | ≈ \$0.30     | ≈ 30–60 s    | ≈ \$3.7              | ≈ 3 min             |
| 10 000    | ≈ \$0.30     | ≈ 30–60 s    | ≈ \$37               | ≈ 33 min            |
| 100 000   | ≈ \$0.30     | ≈ 30–60 s    | ≈ \$370              | ≈ 5½ h              |

The *FeatLLM* column stays essentially flat because its cost depends only on
the fixed number of engineering queries, not on dataset size.
The baseline column grows linearly with *N* both in dollars and wall‑clock time.

---

### Take‑away

*FeatLLM* amortises a single, modest LLM bill (≈​\$0.3) over any number of test
samples and reduces latency from seconds per row to negligible CPU time.
When you have thousands or more rows, this translates into savings of tens to
hundreds of dollars and orders‑of‑magnitude faster inference—exactly why the
paper emphasises “only 30 API queries irrespective of test set size”.

### How does FeatLLM ensure that generated binary features are linearly independent enough for a simple linear model to learn?
Question:
Since each rule yields a binary feature, many rules could be redundant or highly correlated. Does the bagging/ensemble process implicitly handle this redundancy, or would it be beneficial to add an explicit feature selection step before training the linear model?
Answer:
**Answer**

In *FeatLLM* each rule that the LLM writes becomes a binary feature  
\(z_{k}^{i}\in\{0,1\}\) ( “the i‑th sample satisfies rule r for class k”).  
If we were to use a single set of rules, many of those features could be
highly correlated – for example two rules that differ only by a harmless
re‑wording, or two rules that refer to the same underlying column with
similar thresholds.  The authors are aware of this and rely on two
mechanisms to keep the feature set usable for a very simple downstream
model (a non‑negative linear model).

---

### 1.  Implicit de‑correlation by the linear weights  

The linear model is trained on the few‑shot training data by minimizing the
cross‑entropy loss

\[
\text{logit}_{k}^{i}= \max (\mathbf w_{k},0)\cdot \mathbf z_{k}^{i},
\qquad 
\mathbf p^{i}= \operatorname{softmax}([\text{logit}_{1}^{i},\dots ,
\text{logit}_{c}^{i}]).
\]

Because each weight \(\mathbf w_{k}\) is learned *after* the rules have been
generated, the optimizer automatically gives a small (or zero) weight to
features that do not contribute new information.  When two binary rules are
perfectly collinear (they are either both 0 or both 1 for every training
example) their contribution to the loss is indistinguishable; gradient‑based
training will push the weight of one of them toward zero, effectively *pruning*
the redundant feature.  In practice the authors observe that after training
the proportion of “useful’’ features (AUROC > 0.5) rises from about 60 % to
over 80 % (Table 5, “After tuning’’), confirming that the weight learning step
acts as an implicit feature‑selection filter.

---

### 2.  Ensemble + bag‑of‑features reduces systematic redundancy  

A single LLM query produces at most ten rules per class (the hyper‑parameter
used in the paper).  To mitigate the risk that a particular query generates a
poor or overly redundant rule set, *FeatLLM* repeats the whole pipeline
\(T\) times (default \(T=20\)).  Between repetitions it

* raises the sampling temperature,
* shuffles the order of the few‑shot examples,
* **bags** a random subset of columns (and optionally a subset of training
  instances).

These randomisations make the rule‑generation process *stochastic*: different
trials will look at different subsets of columns and therefore propose
different logical conditions.  Even if one trial contains many correlated or
useless rules, most other trials will still produce independent ones.  
The final prediction averages the softmax probabilities from all trials,
so any single redundant rule has only a diluted effect on the ensemble’s
output.  This is exactly the classic bagging idea used in Random Forests:
by training many weak learners on different feature subsets we obtain a
strong learner that is robust to individual feature correlations.

---

### 3.  Should one add an explicit feature‑selection step?  

Because the linear weights already zero out useless features and because bagging
already guarantees that no single redundant rule dominates, the authors found
no substantial benefit from an extra selection stage.  Their ablation study
(Section 4.2, Table 4) shows that removing weight tuning (“‑Tuning”) hurts
performance more than removing any other component, indicating that weight
learning is the primary guard against redundancy.  Adding a separate filter,
such as mutual‑information based pruning, would increase implementation
complexity and API calls without a clear gain in AUC.

---

### Take‑away  

*FeatLLM* does not rely on an explicit redundancy‑removal algorithm; instead it
uses **(i)** learning of non‑negative weights in a linear model, which naturally
down‑weights or discards collinear binary features, and **(ii)** an ensemble of
bagged rule sets that spreads any remaining correlation across many weak learners.
Together these mechanisms make the final linear predictor robust even when many
generated rules are partially overlapping, so an additional manual feature‑selection step is generally unnecessary.
