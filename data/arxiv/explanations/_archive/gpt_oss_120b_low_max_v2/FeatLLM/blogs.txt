# Turning Language Models into Feature Engineers: The FeatLLM Breakthrough  

## Introduction  

Tabular data—think spreadsheets of customer records, medical lab results, or sensor logs—powers countless real‑world applications. Yet training a high‑performing model on a new table often requires many labeled examples or careful manual feature engineering. Recent research has shown that large language models (LLMs) can bring a surprising amount of prior knowledge to bear on such problems, but most approaches treat the LLM as a black‑box predictor: every new sample has to pass through the LLM, which is costly, slow, and limited by prompt length.  

**FeatLLM** flips this script. Instead of asking the LLM “what’s the label for this row?”, we ask it “what rules or criteria would you use to decide the label?” The LLM then generates a handful of human‑readable rules, which are turned into binary features (e.g., “Age > 50 and Smoker = Yes”). A tiny downstream model—often just a linear classifier—learns how important each rule is. The result is a system that retains the reasoning power of an LLM while enjoying the speed and simplicity of traditional tabular learners.

Below we walk through the key ideas behind FeatLLM, how it works in practice, and why it matters for anyone who needs accurate predictions from limited data.

## Why Existing LLM‑Based Tabular Methods Struggle  

Most prior work on “language‑interfaced” tabular learning follows one of two patterns:

1. **Serialize the whole table** (feature names + values + task description) into a text prompt and feed it to an LLM for each query.  
2. **Fine‑tune** a language model on many tables or use parameter‑efficient adapters (LoRA, IA3) before inference.

Both routes have drawbacks:

* **Inference cost** – Every test row triggers a full forward pass through the LLM, which can be expensive and adds latency.  
* **Prompt size limits** – Tables with dozens or hundreds of columns quickly exceed the token window, forcing truncation or hurting performance.  
* **Training requirements** – Fine‑tuning needs access to model weights and can be impossible when only an API (e.g., GPT‑4) is available.

FeatLLM sidesteps these issues by treating the LLM as a *feature engineer*, not an end‑to‑end predictor.

## The Core Idea: Extract Rules, Not Predictions  

The method consists of three logical stages:

1. **Prompt the LLM to generate rules** that separate each class.  
2. **Parse those rules into executable code** that creates binary features for every data point.  
3. **Train a simple downstream model** (a non‑negative linear classifier) on the new binary features.

Because the rules are generated only once (using a few labeled examples), inference later involves evaluating a set of Boolean conditions—something that runs in milliseconds on any CPU.

### 1️⃣ Prompt Design – Guiding the LLM’s Reasoning  

Fea tLLM’s prompt is deliberately structured like how a human analyst would approach a new prediction task:

* **Basic information** – A concise task description (e.g., “Will this patient develop chronic heart failure?”), natural‑language explanations of each feature (type, possible values), and a handful of labeled examples serialized as “`f1 is 45, f2 is Yes … Answer: No`”.
* **Two‑step reasoning instruction** –  
  * *Step 1*: “Explain which features are generally relevant to this problem.” This pushes the LLM to draw on its world knowledge (e.g., older age increases heart disease risk).  
  * *Step 2*: “Given the examples above, produce ten concrete decision rules for each class.” By separating prior knowledge from data‑driven patterns, the model avoids latching onto spurious correlations that appear in the tiny few‑shot set.
* **Response formatting** – Explicit templates tell the LLM how to list each rule (e.g., `Rule 1: Age > 60 AND Cholesterol > 200`). This deterministic format makes downstream parsing reliable despite occasional linguistic variations (“greater than” vs “>”).

The result is a set of **10 rules per class**, each expressed as a logical condition over the original columns.

### 2️⃣ Turning Rules into Features  

Natural language rules must be converted into machine‐readable binary columns. Rather than writing brittle regular expressions, FeatLLM hands the rule text back to an LLM with a prompt that asks it to emit straightforward Python code:

```python
def rule_1(row):
    return (row["Age"] > 60) and (row["Cholesterol"] > 200)
```

The generated code is executed via `exec()`; for every row we compute `z_k = [rule_1(row), ..., rule_R(row)]`, where `R = 10`. Thus each original sample gains *R* new binary features per class.

### 3️⃣ Learning from Rules – A Tiny Linear Model  

Not all rules are equally useful. FeatLLM fits a non‑negative linear model for each class:

\[
\text{logit}_k = \max(\mathbf{w}_k ,0) \cdot \mathbf{z}_k,
\qquad
\mathbf{p}= \text{Softmax}([\text{logit}_1,\dots,\text{logit}_c]),
\]

where `\mathbf{w}_k` are learnable weights (trained with ordinary cross‑entropy on the few labeled rows). The positivity constraint guarantees that satisfying a rule never *reduces* a class’s probability—a sensible inductive bias when rules come from expert knowledge.

### Ensembling & Bagging – Making It Robust  

A single run of rule extraction can miss relevant columns or produce noisy rules. FeatLLM mitigates this in two ways:

* **Temperature sampling** – Setting temperature = 0.5 yields diverse rule sets across multiple API calls.  
* **Feature bagging** – For each ensemble member we randomly select a subset of columns and/or few‑shot examples before prompting. This reduces prompt length for large tables and encourages varied reasoning paths.

After `T` ensemble trials (default = 20), predictions are averaged across models, delivering both higher accuracy and resilience to occasional bad rule generations.

## How Well Does It Work?  

The authors evaluated FeatLLM on 13 diverse classification datasets ranging from classic UCI benchmarks (Adult, Credit‑g) to newer or synthetic tables not seen during LLM pretraining (NHANES, Sequence‑type). Key findings:

| Metric | FeatLLM (4‑shot) | Conventional ML (32‑shot) | Best prior LLM baseline |
|--------|------------------|---------------------------|--------------------------|
| Average AUC improvement over baselines | +10 % | — | — |
| Inference latency per row | ~1 ms (CPU) | ~1 ms (CPU) | 10–100× slower due to per‑sample LLM calls |
| Sensitivity to irrelevant columns | Minimal degradation | Noticeable drop | Large drop |

In low‑shot regimes (2–8 labeled rows), FeatLLM matches or exceeds traditional models trained on four times as many examples. Moreover, because only ~30 API calls are needed to generate all rule sets, cost remains modest even with paid LLM endpoints.

Ablation studies confirm that each component matters:

* Removing weight tuning hurts performance more as shot count rises (the linear model learns nuanced rule importance).  
* Dropping reasoning instructions reduces accuracy especially when shots are very few—prior knowledge becomes crucial.  
* Skipping feature descriptions also degrades results in low‑shot settings because the LLM loses contextual cues about column types.

## Why This Matters for Practitioners  

1. **Speed at inference time** – After an initial “feature engineering” step, prediction reduces to evaluating Boolean conditions and a dot product—fast enough for real‑time systems.  
2. **No fine‑tuning needed** – Only API access to an LLM is required; no gradients are computed on the language model itself. This opens the door to using closed‑source services like GPT‑4 without worrying about proprietary weight files.  
3. **Scalable to wide tables** – Bagging lets us handle hundreds of columns without blowing up prompt size, something serializing whole tables cannot do reliably.  
4. **Interpretability by design** – The extracted rules are human readable; stakeholders can audit why a prediction was made (“Age > 70 AND PriorStroke = Yes”).  
5. **Data efficiency** – In domains where labeling is expensive (healthcare, finance), getting high performance from just 4–8 examples can dramatically lower project cost.

## Limitations & Future Directions  

While FeatLLM shines in few‑shot settings, several open challenges remain:

* **Rule expressiveness** – Current rules are simple conjunctions/disjunctions; capturing complex nonlinear interactions may require richer program synthesis techniques.  
* **Bias in LLM knowledge** – Since the generated rules reflect whatever patterns exist in the LLM’s training corpus, hidden societal biases could propagate into predictions if not inspected carefully.  
* **Large training sets** – When thousands of labeled rows become available, traditional tree ensembles may outperform rule‑based linear models; integrating FeatLLM’s features into larger learners could be fruitful.

The authors propose extending FeatLLM beyond binary/multiclass classification—to regression tasks and richer feature types—and investigating tighter coupling between rule generation and downstream model capacity.

## Takeaway  

FeatLLM demonstrates that large language models need not be black-box predictors for tabular data. By coaxing them to *explain* their reasoning as logical rules, we can harvest high-quality features once, train an ultra-lightweight downstream model, and reap both speed and interpretability benefits—all while requiring only a handful of labeled examples and simple API calls.

If you’re wrestling with scarce labels or unwieldy tables, give FeatLLM a try: let the LLM do the heavy lifting up front, then let your favorite lightweight classifier handle inference at lightning speed.



# Why Few‑Shot Tabular Learning Matters and How FeatLLM Solves It  

## The Problem: Tiny Labeled Datasets  

In many real‑world settings—think medical diagnosis, credit scoring, or industrial monitoring—collecting a large, high‑quality labeled table is expensive or even impossible. Often we only have a handful of examples (2, 4, 8 …) for a new prediction task. Traditional machine‑learning pipelines (logistic regression, random forests, XGBoost) struggle in this “few‑shot” regime: with so little data they quickly overfit to noise and fail to capture the true relationships between columns and the target label.

A common remedy is to inject **prior knowledge**. If a model already knows that “older age increases heart disease risk” or that “high cholesterol is linked to diabetes,” it can make better predictions even when only a few labeled rows are available. Large language models (LLMs) such as GPT‑3.5 have already absorbed massive amounts of domain knowledge from web text, making them natural candidates for providing that extra boost.

## Existing LLM‑Based Approaches: What’s Missing?  

Recent work has indeed tried to feed tabular data into an LLM as plain text, asking the model to predict the label directly (in‑context learning) or to fine‑tune it on a few examples. While promising, these methods suffer from three practical drawbacks:

1. **Per‑sample LLM inference** – Every new row must be sent through the LLM, leading to high latency and cost.  
2. **Prompt length limits** – Serializing a table with many columns quickly exceeds the LLM’s context window, degrading performance or making the query impossible.  
3. **Dependency on fine‑tuning APIs** – Some top‑performing LLMs are only accessible via inference endpoints; they cannot be fine‑tuned, which blocks methods that rely on parameter updates.

In short, we have powerful models but an inefficient way of using them for tabular prediction.

## The Insight: Let the LLM Engineer Features Instead of Predict  

Instead of treating the LLM as a black‑box predictor for every row, **FeatLLM** asks a different question: *“What logical conditions (rules) would let me decide the class?”*  
If the model can articulate statements such as “Age > 65 AND cholesterol > 200 → high risk”, those statements can be turned into **binary features** (true/false for each rule). Once we have this engineered feature set, any lightweight classifier—e.g., a linear model—can map them to class probabilities.

This shift brings several advantages:

* **Zero per‑sample LLM calls** – After the rules are extracted once (using only a few-shot prompt), all subsequent predictions use only the cheap linear model.  
* **Prompt size no longer a bottleneck** – The rule extraction prompt contains only the few demonstrations and feature descriptions, not the entire test set.  
* **Works with API‑only LLMs** – No fine‑tuning is required; just a handful of API calls to obtain the rules.

## How FeatLLM Works – Step by Step  

### 1️⃣ Prompt Design: Structured Reasoning  

FeatLLM crafts a three‑part prompt for the LLM:

1. **Basic information** – Task description (e.g., “Does this patient have chronic heart failure?”), natural‑language feature names & definitions, and a few serialized training examples (`f1 is 45. … Answer: Yes`).  
2. **Reasoning instruction** – A chain‑of‑thought style cue splits reasoning into two stages:  
   * *Step 1:* Infer general causal tendencies from background knowledge alone (no examples).  
   * *Step 2:* Use both the inferred tendencies and the few-shot examples to generate **10 explicit rules per class** (the number is fixed for stability).  
3. **Response instruction** – Tell the LLM exactly how to format each rule (e.g., `feature > value`) so that downstream parsing is reliable.

The two‑step reasoning forces the model to rely on its prior knowledge first, then fine‑tune that understanding with the actual data points—helpful when only a few rows are available.

### 2️⃣ Turning Rules into Binary Features  

The raw natural‑language rules are noisy (“greater than” vs “>”). Rather than write a brittle parser, FeatLLM feeds each rule back into the same LLM with a short code‑generation prompt (`def check(row): return row["age"] > 65`). The model returns runnable Python code that evaluates whether any given row satisfies each rule. Executing this code yields a binary vector  

\[
\mathbf{z}_k^i \in \{0,1\}^{R},
\]

where \(R\) is the number of rules per class and \(k\) indexes the class.

### 3️⃣ Learning Simple Weights  

A linear model without bias consumes these binary features:

\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,
\qquad
\mathbf{p}^i = \text{Softmax}\big([\text{logit}_1^i,\dots,\text{logit}_c^i]\big).
\]

Training simply optimizes cross‑entropy on the few labeled rows, learning which rules are truly informative (negative weights are clamped to zero so rules never hurt a class). This step is extremely cheap—just a handful of gradient steps.

### 4️⃣ Bagging & Ensembling for Robustness  

To mitigate two remaining challenges—prompt length for very wide tables and variability in generated rules—FeatLLM repeats the whole pipeline multiple times:

* Randomly **bag** a subset of columns or examples before prompting (reducing prompt size).  
* Use a higher temperature during rule generation to encourage diverse rule sets across runs.  

The resulting linear models are averaged at inference time (standard ensemble voting), which smooths out occasional bad rules and further improves accuracy.

## Performance Highlights  

Across 13 diverse benchmark datasets (including classic UCI tasks like Adult and Credit‐g as well as recent or synthetic tables not seen during LLM pretraining), FeatLLM consistently outperformed strong baselines:

| Dataset | 4‑shot AUC (FeatLLM) | Best non‑LLM baseline | Avg improvement |
|---------|----------------------|-----------------------|-----------------|
| Adult   | 0.89                 | XGBoost (0.84)        | +5% |
| Myocardial | 0.93              | TabLLM (0.81)         | +12% |
| Cultivars | 0.87               | RandomForest (0.78)   | +9% |

On average FeatLLM gains about **10 % AUC** over modern few‑shot tabular methods such as TabLLM and STUNT, while requiring **orders of magnitude less inference time** because only the initial rule extraction uses the LLM.

Ablation studies confirm that every component matters:

* Removing weight tuning hurts performance more as shots increase (the linear model can better exploit many rules).  
* Dropping feature descriptions or the two‑step reasoning harms low‑shot performance—the LLM loses valuable prior knowledge cues.  
* Skipping ensembling lowers robustness especially on wide tables.

## Why This Matters in Practice  

1. **Fast, cheap predictions** – After an initial handful of API calls (< 30), you can serve millions of rows with a trivial linear model on CPU/GPU.  
2. **Works with restricted APIs** – No need for LoRA or other fine‑tuning tricks; any closed‑source endpoint that supports text completion suffices.  
3. **Scales to many features** – Feature bagging keeps prompts within context limits even when tables have > 100 columns.  
4. **Interpretability out of the box** – The extracted rules are human readable; analysts can inspect which logical conditions drive each prediction.

## Looking Ahead  

FeatLLM currently focuses on low‑shot classification using rule‐based binary features. Future directions include:

* Extending to regression tasks by generating quantitative transformations rather than boolean rules.  
* Exploring richer feature families (e.g., interaction terms, embeddings) while retaining interpretability.  
* Systematically auditing how biases present in LLM knowledge affect generated rules and downstream decisions.

## Takeaway  

Few‑shot tabular learning is indispensable when labels are scarce but decisions still matter urgently. By rethinking what we ask an LLM—“Give me good features,” not “Predict every row”—FeatLLM turns massive pretrained knowledge into compact, reusable rule sets that dramatically boost performance while staying practical for production use cases. If you’re grappling with tiny labeled tables and have access to an LLM API, give FeatLLM’s rule extraction pipeline a try; you’ll likely see higher accuracy with far lower inference cost than sending every row through an LLM directly.



# Inside the Prompt: How FeatLLM Guides LLMs to Write Rules  

Large language models (LLMs) have proven themselves as powerful “reasoners” that can tackle novel tasks with just a few examples.  The recent **FeatLLM** framework pushes this ability further: instead of asking the LLM to predict a label for every row of a table, it asks the model to **engineer new features**—in the form of human‑readable rules—that later feed a tiny linear classifier.  

The secret sauce lies in a carefully crafted **three‑part prompt** that nudges the LLM through a structured reasoning pipeline:

1. **Basic Information Description**  
2. **Reasoning Instruction**  
3. **Response Format Instruction**  

Below we unpack each component, explain why it matters, and show how together they turn a black‑box LLM into an automated feature engineer.

---

## 1. Basic Information Description – Setting the Stage  

The first chunk of the prompt resembles the “problem statement” you would give a human analyst:

* **Task definition** – A natural‑language question that clearly states what we want to predict, e.g., *“Does this patient’s record indicate chronic heart failure? Yes or no.”*  
* **Feature list with definitions** – Every column name (`f_1 … f_d`) is accompanied by its type (numeric, categorical, boolean) and, when useful, a brief definition drawn from the dataset’s metadata. For categorical columns we may also enumerate possible categories.  
* **Few‑shot examples** – A handful (typically 4–8) of serialized rows are shown together with their ground‑truth labels. The serialization follows a simple pattern such as  

\[
\text{“}f_1\ \text{is}\ x_1.\ \dots\ f_d\ \text{is}\ x_d.\ \text{Answer:}\ y\text{”}
\]

Providing these ingredients does two things: it tells the LLM *what* it is looking at, and it supplies concrete instances that anchor its subsequent reasoning.

---

## 2. Reasoning Instruction – Guiding the Thought Process  

Simply dumping the description and examples into an LLM often yields shallow answers that hug the surface statistics of the few examples. FeatLLM instead injects a **two‑step chain‑of‑thought instruction**:

### Step 1 – Infer Prior Knowledge  
The prompt asks the model to “think about which features are generally related to the target” *without* looking at the few‑shot rows. Because LLMs have absorbed massive amounts of domain knowledge from their pretraining data (e.g., “older patients are at higher risk for heart disease”), this step extracts *general* causal intuition about the problem.

### Step 2 – Derive Rules Using Examples  
Armed with its prior beliefs, the model now examines the provided examples and writes down **explicit decision rules** for each class (e.g., “If age > 65 AND cholesterol > 200 then class = Yes”). By separating prior knowledge from data‑driven pattern extraction, FeatLLM reduces the risk of latching onto spurious correlations that only appear in the tiny training set.

The prompt also fixes a **maximum number of rules per class (10)**. This prevents two extremes: under‑specifying (too few rules → underfitting) or over‑specifying (too many rules → bloated prompts). Moreover, by explicitly mentioning feature types in this section, we reduce type‑mismatch errors such as comparing a categorical variable with a numeric threshold.

---

## 3. Response Format Instruction – Making Output Machine‑Friendly  

Even a well‑reasoned LLM can produce output that’s hard to parse programmatically—different punctuation, varied phrasing (“greater than” vs “>”), or inconsistent bullet styles. To guarantee that downstream code can automatically turn each rule into a binary feature, FeatLLM adds a **response guideline**:

* Each class must be preceded by a header like `Class: Yes` or `Class: No`.  
* Every rule must follow a strict template:  

```
Rule <i>: <feature> <operator> <value>
```

* Logical connectors are limited to `AND` within a rule; cross‑rule disjunction is handled by separate rules rather than nesting complex expressions.

Because the LLM is also trained on code, this constrained format is easy for it to obey while still allowing natural language flexibility where needed.

---

## Why This Prompt Design Works  

### • Encourages Structured Thinking  
The three sections mirror how an expert would approach tabular prediction: understand what’s being asked, recall domain knowledge, then apply it to concrete cases. The explicit reasoning steps coax the model into first leveraging its broad world knowledge before over‑fitting to few examples.

### • Controls Prompt Length  
Large tables can quickly exceed context windows if we try to serialize all rows at once. By separating *feature description* (which is static) from *few‑shot demonstrations* (which stay tiny) and by limiting rule count, FeatLLM stays well within token limits even for datasets with hundreds of columns.

### • Guarantees Parseable Output  
A deterministic response format eliminates post‑hoc cleaning pipelines and lets us feed each rule straight into Python code (`exec`) that evaluates whether a row satisfies it. This yields a binary vector \(\mathbf{z}_k^i \in \{0,1\}^R\) for class \(k\), which downstream logistic regression can handle efficiently.

### • Facilitates Ensemble & Bagging  
Because every LLM query only returns a modest set of rules, we can repeat the whole prompting process multiple times with different random seeds (temperature = 0.5) and different shuffles of the few‑shot examples. Bagging—randomly subsetting columns or rows for each trial—creates diverse rule sets that are later averaged, mitigating occasional mis‑rules and boosting robustness.

---

## From Rules to Predictions – A Quick Recap  

1. **Prompt → LLM → Rules** (binary conditions per class).  
2. **Parse → Python code → Binary features** \( \mathbf{z}_k^i \).  
3. **Linear model with non‑negative weights** computes logits  

\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,
\qquad
\mathbf{p}^i = \text{Softmax}([\text{logit}_1^i,\dots,\text{logit}_c^i]).
\]

4. **Cross‑entropy loss** on the few shot samples learns \(\mathbf{w}_k\).  
5. **Ensemble averaging** across \(T\) bagged runs yields final probabilities.

All heavy lifting is done *once* at training time; inference simply evaluates binary rules—no per‑sample LLM calls required.

---

## Takeaways  

- **Prompt engineering matters:** By decomposing the task into three logical blocks we steer an otherwise generic LLM into disciplined feature generation.  
- **Leverage prior knowledge:** The first reasoning step extracts world‑level causal cues that low‑shot data alone cannot reveal.  
- **Structure output for automation:** Precise response instructions turn natural language into executable code without brittle parsing hacks.  

FeatLLM demonstrates that large language models need not be black boxes for every prediction; with a well‑designed prompt they can act as *expert analysts*, producing reusable rules that power lightweight downstream models—opening doors for cost‑effective, low‑latency tabular learning in real-world settings such as finance or healthcare.



# From Rules to Binary Features: Turning Natural Language into Machine‑Learnable Signals  

## Introduction  

Tabular data—think spreadsheets of patient records, credit applications, or sensor logs—are the backbone of countless real‑world AI systems. Yet getting high‑quality predictions from a handful of labeled examples remains a hard problem. Recent work shows that large language models (LLMs) can bring their world knowledge to bear on these tasks, but most approaches still treat the LLM as a black‑box predictor that must be queried for every new sample.  

**FeatLLM** takes a different route. Rather than asking the LLM “what’s the label for this row?”, we ask it “what rules would tell you the label?”. The LLM spits out natural‑language conditions (e.g., “age > 65 AND blood‑pressure > 140”), we turn those conditions into tiny pieces of executable code, and finally we compile the results into a set of binary features. A simple linear model then learns how much each rule should count toward each class. The whole pipeline reduces inference cost dramatically while preserving (or even improving) predictive performance.

Below we walk through each stage of this pipeline, from prompting the LLM for rules to training a lightweight classifier on the resulting binary signals.

## 1. Prompting the LLM to Generate Rules  

### Structured Prompt  
Featurizing an LLM’s knowledge starts with a carefully crafted prompt that mimics how a human analyst would approach a new tabular problem:

1. **Basic Information** – A concise description of the task (e.g., “Predict whether a patient will develop chronic heart failure”), a list of feature names with their types/definitions, and a few serialized few‑shot examples (`feature1 is value1 … Answer: Yes/No`).  

2. **Reasoning Instruction** – A two‑step chain‑of‑thought instruction:  
   *Step 1* asks the model to reason about which columns are *a priori* relevant based solely on its background knowledge (no training examples).  
   *Step 2* asks it to refine that intuition using the provided examples and to produce **10 explicit rules per class** (the number was chosen empirically; see the paper’s ablation).  

3. **Response Instruction** – Clear formatting constraints so the output can be parsed automatically (e.g., each rule on its own line, using `>`/`<`/`=` for numeric comparisons and `==` for categorical equality).

The prompt deliberately separates **knowledge extraction** (Step 1) from **empirical rule fitting** (Step 2), discouraging the model from latching onto spurious correlations in the few-shot data.

### Example Output  

```
Class: Yes
1) age > 70
2) cholesterol >= 250
3) blood_pressure > 140 AND smoker == Yes
...
Class: No
1) age <= 45
2) cholesterol < 180
...
```

These human‑readable rules are what we later turn into machine features.

## 2. Parsing Natural‑Language Rules into Executable Code  

The raw textual rules are not yet machine‑readable. Direct string parsing can be brittle—LLMs may write “greater than” instead of “>”, add extra spaces, or reorder logic. FeatLLM sidesteps this by *leveraging the LLM itself* as a parser:

1. **Create a secondary prompt** that includes:
   - The original rule list.
   - A short function skeleton (`def apply_rules(row): ...`) describing inputs (`row` as a dict of column values) and expected boolean outputs.
   - Explicit instructions to emit pure Python code that evaluates each rule and returns a list of binary indicators.

2. **Send this prompt back to the LLM** (still using GPT‑3.5 in the paper). Because the model has been trained on massive amounts of code, it reliably converts phrases like “greater than” → `>`, “AND” → `and`, and handles type casting automatically.

3. **Execute the generated snippet with Python’s `exec()`** in a sandboxed environment. The resulting function maps any row to a vector `z ∈ {0,1}^R`, where `R = 10 × #classes` is the total number of extracted rules.

This “code‑as‑intermediate” step removes most parsing errors without hand‑written regexes, making the pipeline robust to variations in LLM output.

## 3. From Rules to Binary Features  

Each row now has an associated binary vector:

\[
\mathbf{z}_k^i = \big[\,\text{rule}_{k,1}(\mathbf{x}^i),\dots,\text{rule}_{k,R}(\mathbf{x}^i)\,\big] \in \{0,1\}^{R},
\]

where \(k\) indexes the target class and \(\mathbf{x}^i\) is the original feature vector. Intuitively, entry \(\mathbf{z}_k^i[j]=1\) tells us that row \(i\) satisfies rule \(j\) for class \(k\).

Because these features are *highly interpretable* (each is just “does this patient meet condition X?”), they also provide immediate insight for domain experts—a nice side effect often missing in deep tabular models.

## 4. Light‑Weight Linear Model on Binary Features  

The binary matrix \(\mathbf{Z}\) is fed into an extremely simple classifier:

\[
\text{logit}_k^i = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k^i,
\qquad 
\mathbf{p}^i = \text{softmax}\big(\text{logit}_1^i,\dots,\text{logit}_c^i\big),
\]

where:
- \(\mathbf{w}_k \in \mathbb{R}^R_{\ge 0}\) are learnable weights (non‑negative via a ReLU projection).
- The dot product counts *weighted* rule satisfactions.
- Softmax turns logits into class probabilities.

Training is just standard cross‑entropy minimisation on the few available labeled rows (the same rows used in the prompting stage). Since only \(R\) parameters per class need learning, convergence is fast even with as few as four shots.

### Why Not Skip Training?  
A naive baseline would simply sum satisfied rules per class (i.e., set all weights to 1). The paper’s ablation shows this works reasonably well when shots are extremely scarce, but learns substantially better importance estimates once more labeled points become available—especially for datasets with many overlapping or noisy rules.

## 5. Ensembling & Feature Bagging  

Two practical challenges arise:

1. **Prompt Length Limits** – Large tables can exceed the context window if we list every column in one go.
2. **Rule Diversity** – A single LLM query may miss useful patterns.

FeatLLM addresses both with an ensemble:
- **Bagging**: For each ensemble member we randomly select a subset of columns and/or training examples before prompting.
- **Temperature Sampling**: We run the LLM at temperature 0.5, encouraging varied rule sets across members.
- **Aggregation**: After training separate linear models on each member’s binary features, we average their softmax outputs at inference time.

Empirically, performance plateaus after ≈20 ensemble members; beyond that additional members yield diminishing returns while increasing API cost modestly.

## 6. Benefits Over Traditional LLM‑Based Tabular Methods  

| Aspect | Traditional In‑Context Tabular Models | FeatLLM |
|--------|---------------------------------------|---------|
| **Inference Cost** | One LLM call per test row (slow, expensive) | Zero LLM calls after feature generation |
| **API Requirements** | Needs fine‑tuning or repeated calls → often unavailable for closed APIs | Only requires a handful of API queries during setup |
| **Scalability** | Prompt size grows linearly with number of columns; quickly hits limits | Bagging keeps each prompt small; ensemble mitigates information loss |
| **Interpretability** | Model internals opaque | Each binary feature corresponds to an explicit natural-language rule |
| **Performance (few‑shot)** | Often lags behind classic ML baselines | Matches or surpasses conventional models with ≤4 shots |

In benchmark experiments across 13 heterogeneous datasets, FeatLLM delivered an average AUC gain of ≈10 % over strong baselines such as TabLLM and STUNT, while keeping inference latency comparable to logistic regression.

## 7. Practical Takeaways  

- **Prompt Design Matters**: Splitting reasoning into “knowledge first, data second” yields cleaner rules.
- **Leverage LLMs for Code Generation**: Using the same model as a parser dramatically reduces brittle string handling.
- **Keep Rules Binary**: Binary indicators simplify downstream learning and keep interpretability intact.
- **Ensemble Early**: Slight randomization at rule generation time yields robust performance without blowing up API usage.
- **Fine‑Tune Light Weights Only**: Even with as few as four labeled examples, learning non‑negative rule weights improves results over simple counting.

## Conclusion  

Turning natural language conditions into binary signals bridges the gap between an LLM’s rich world knowledge and conventional machine learning pipelines. FeatLLM demonstrates that a modest number of API calls can produce high‑quality features that enable ultra‑lightweight classifiers to thrive in low‑shot regimes—making AI more accessible for domains where data labeling is costly but expert knowledge already exists in text form.

If you’re working with tabular data and have access to an LLM API, try swapping your traditional end‑to‑end prompting for this “rule → binary feature → linear model” workflow. You’ll likely see cheaper inference, clearer explanations, and competitive—or even superior—prediction quality. Happy modeling!



# Bagging and Ensembling with LLM‑Generated Features: Boosting Robustness at Scale  

Large language models (LLMs) have become go‑to tools for few‑shot learning, but most current pipelines still rely on **one LLM query per data point**. That design is expensive, hits prompt‑size limits, and can be brittle when the model drifts into noisy or spurious rules.  

The recent **FeatLLM** framework flips this paradigm: instead of using the LLM as a black‑box predictor, it treats the LLM as an *expert feature engineer*. By prompting the model to output decision rules (e.g., “age > 45 AND cholesterol > 200”), FeatLLM turns those natural‑language rules into binary features that a tiny downstream model (a linear classifier) can consume. The real magic, however, lies in **how FeatLLM makes those rules robust**, especially when dealing with high‑dimensional tabular data. Below we unpack three core tricks—feature bagging, temperature‑induced diversity, and ensemble averaging—that together let FeatLLM scale to dozens or hundreds of columns while staying fast and reliable.

---

## 1. From a Single Prompt to Many: Why Bagging Matters  

When a dataset has many attributes (think the *Communities* or *Myocardial* benchmarks with > 100 columns), simply stuffing all feature names and definitions into one prompt blows past the LLM’s context window. Moreover, a monolithic prompt makes it hard for the model to focus on the truly informative columns; irrelevant fields can drown out useful signals.

**FeatLLM’s solution:** *feature bagging*.  
Instead of sending every column at once, FeatLLM repeatedly samples a random subset of features (e.g., 30 % of the columns) and builds a fresh prompt around that subset. Each bagged prompt goes through the same two‑step reasoning process:

1. **High‑level causal inference** – “What kinds of attributes usually matter for this medical diagnosis?” – leveraging the LLM’s world knowledge.
2. **Rule extraction** – using the few labeled examples to anchor those high‑level hints into concrete conditions.

Because each bag contains a different slice of the data, the LLM produces **different rule sets** that are each tuned to a particular perspective on the problem. This mitigates two pain points:

* **Prompt length:** smaller bags stay well within the model’s token limits.  
* **Feature coverage:** across many bags, every column gets a chance to be examined, reducing the risk that a useful predictor is permanently ignored.

---

## 2. Temperature‑Induced Diversity: Letting the LLM “Think Differently”  

Even with feature bagging, if we always query the LLM with temperature = 0 (deterministic decoding), each bag would yield an identical set of rules every time we repeat the experiment. That defeats the purpose of ensembling—there would be no diversity to average over.

FeatLLM deliberately **raises the temperature** (e.g., to 0.5) when generating rules. A higher temperature injects stochasticity into token selection, which translates into:

* Slight variations in phrasing (“> 45” vs “greater than 45”).  
* Different logical groupings (sometimes combining conditions with *AND*, other times with *OR*).  
* Occasionally proposing alternative thresholds that still make sense given domain knowledge.

These stochastic outputs are *not* random noise; they are plausible alternatives drawn from the same underlying knowledge base. When later parsed into binary features, each variant offers an additional weak signal that can be weighted up or down during training.

---

## 3. Ensemble Averaging: Turning Weak Learners into a Strong One  

After we have **T** bagged rule sets (the paper uses T = 20 as a default), each set yields a binary feature vector \(\mathbf{z}_k^i\) for every class \(k\). A simple linear model – essentially a weighted sum followed by Softmax – turns those binaries into class probabilities:

\[
\text{logit}_k^i \;=\; \max(\mathbf{w}_k,0) \cdot \mathbf{z}_k^i,\qquad
\mathbf{p}^i = \text{Softmax}([\text{logit}_1^i,\dots,\text{logit}_c^i]).
\]

Crucially, **the weights \(\mathbf{w}_k\) are learned from the few labeled examples**, so they automatically down‑weight noisy or irrelevant rules while amplifying those that truly correlate with the target.

To combine multiple bagged models, FeatLLM simply **averages their probability vectors**:

\[
\bar{\mathbf{p}}^i = \frac{1}{T}\sum_{t=1}^{T} \mathbf{p}^{i}_{[t]} .
\]

This averaging brings two benefits:

1. **Robustness to mis‑generated rules.** If one bag’s LLM call produces an outright wrong rule (e.g., “blood pressure < 0”), its impact is diluted across the ensemble.
2. **Self‑consistency bias.** Rules that appear in many bags tend to be more reliable; their associated features receive higher effective weight after averaging.

The result is a lightweight yet powerful predictor whose inference cost is comparable to classic linear models—no per‑sample LLM calls at all.

---

## 4. Putting It All Together: Scaling to Large Tabular Problems  

Here’s how FeatLLM handles a real‑world scenario step by step:

| Step | What Happens | Why It Helps |
|------|--------------|--------------|
| **a) Sample Feature Subset** | Randomly pick \(p\%\) of columns (bagging). | Keeps prompts short; guarantees eventual coverage of all columns across repetitions. |
| **b) Build Prompt** | Insert task description, feature names & types, and k‑shot examples. | Gives LLM both prior knowledge and empirical evidence. |
| **c) Generate Rules (Temp = 0.5)** | LLM outputs ~10 binary conditions per class in a fixed format. | Stochasticity yields diverse rule families without extra engineering. |
| **d) Parse & Execute Code** | Send rules back to LLM for simple Python code that turns them into binaries. | Handles linguistic quirks (“greater than” vs “>”) automatically. |
| **e) Fit Linear Model** | Train non‑negative weights on these binaries using cross‑entropy loss (few shots). | Learns which rules truly matter; filters out spurious ones. |
| **f) Repeat T Times & Average** | Steps a–e are repeated T times; final prediction = average of Softmax outputs. | Ensembles over many weak learners → stable, high‑performing classifier. |

Because all heavy lifting happens *once* during preparation (≈30 API calls in experiments), deployment is essentially just matrix multiplication—a fraction of a millisecond per record.

---

## 5. Empirical Takeaways  

- **Accuracy boost:** Across 13 diverse datasets, FeatLLM outperforms traditional few‑shot baselines by ~10 % AUC on average, even when only 4 labeled examples are available.
- **Prompt size resilience:** Datasets with > 100 features still achieve strong performance thanks to bagging; alternatives like plain in‑context learning often crash or degrade sharply.
- **Noise resistance:** Adding irrelevant columns (spurious correlations) hurts other models dramatically; FeatLLM’s performance stays nearly flat because its rule extraction stage ignores unrelated attributes early on.
- **Speed:** Inference time matches conventional linear models and is orders of magnitude faster than per‑sample LLM querying pipelines (e.g., TabLLM or TABLET).

---

## 6. Practical Tips for Practitioners  

1. **Pick a sensible bag size:** Roughly 30–50 % of total columns works well—large enough to give context but small enough for token limits.
2. **Use temperature ≈ 0.5:** Higher values increase diversity but can also produce malformed rules; lower values make ensembles too similar.
3. **Fix rule count per class:** The authors found 10 rules per class strike a good balance between expressive power and overfitting risk.
4. **Enable early stopping on linear weights:** With very few shots, limiting training epochs prevents noise amplification.
5. **Monitor rule quality:** A quick AUROC check on generated binaries (“Before tuning”) can flag pathological prompts before committing compute.

---

## 7. Looking Ahead  

FeatLLM demonstrates that an LLM does not need to sit in the inference loop forever—it can act as an *offline knowledge distiller*, converting rich textual priors into concrete tabular features that traditional ML models can consume efficiently. The combination of feature bagging, temperature-induced stochasticity, and ensembling offers a template for any scenario where you must wrangle large feature spaces under tight latency or API budgets.

Future directions might include:

- Extending beyond binary rule features to richer transformations (e.g., discretization bins or learned embeddings).  
- Integrating domain‐specific constraints directly into the prompting logic for even tighter rule relevance.  
- Exploring adaptive bag sizes that focus more sampling effort on columns whose importance remains uncertain after early rounds.

For now, though, FeatLLM provides a practical recipe: let your LLM *think* about what matters, extract those thoughts as reusable features, and then let classic linear algebra finish the job—fast, scalable, and robust enough for real-world tabular workloads.

### Why FeatLLM Wins  

1. **Targeted Knowledge Extraction** – By prompting the LLM to first reason about *causal relations* between features and the task (step 1), then derive *explicit rules* per class (step 2), FeatLLM avoids spurious correlations that often plague vanilla in‑context learning.

2. **Rule‑Based Binary Features** – The generated rules are parsed into simple “does this row satisfy rule k?” binaries. A linear model with non‑negative weights (`logit_k = max(w_k,0)·z_k`) learns how much each rule contributes, leading to an interpretable scoring function.

3. **Bagging + Ensemble** – Each ensemble iteration randomly samples a subset of features and shuffles demo order before asking the LLM for rules. Averaging over ~20 ensembles reduces variance and mitigates prompt size limits.

4. **No Per‑Sample LLM Calls at Inference** – Once the rule set is built (≈30 API queries during training), prediction reduces to a handful of dot products—orders of magnitude faster than sending every test row through an LLM.

* Traditional models’ AUC dropped sharply.

- **If you have very few labeled rows**, consider using FeatLLM as a plug‑and‑play feature engineer: supply feature names & short descriptions, a handful of labeled examples, and let GPT generate rule–based binaries.

# Practical Guide: Deploying FeatLLM in Real‑World Applications

In the past year, large language models (LLMs) have moved from research curiosities to production workhorses. One of the most exciting recent advances is **FeatLLM**, a framework that treats an LLM as an *automatic feature engineer* for tabular data. Instead of sending every new sample through the LLM at inference time, FeatLLM extracts human‑readable decision rules once, converts them into binary features, and then fits a tiny linear model. The result is a few‑shot learner that is both **data‑efficient** and **fast** enough for real‑world pipelines.

If you’re a data scientist or ML engineer considering FeatLLM for a new project, this post walks you through the end‑to‑end deployment steps:

1. **Pick an LLM API that fits your constraints**  
2. **Prepare your tabular dataset (including feature descriptions)**  
3. **Design the in‑context prompt and tune the hyper‑parameters**  
4. **Run the rule extraction and parse the generated code**  
5. **Train the downstream linear model**  
6. **Package everything for production**  

Let’s dive in.

---

## 1. Choosing an LLM API

FeatLLM works with any text‑generation endpoint that supports:

| Requirement | Why it matters |
|------------|----------------|
| **Deterministic temperature control** (e.g., `temperature=0.5`) | Guarantees reproducible rule sets across experiments and enables ensemble diversity when you raise temperature deliberately. |
| **Reasonable context window** (≥ 8 k tokens) | Even with feature bagging, each prompt can contain dozens of feature descriptions plus a few‑shot exemplars. |
| **Code generation capability** | FeatLLM asks the model to output small Python snippets that turn natural‑language rules into executable predicates. |

Popular choices include:

* **OpenAI’s GPT‑3.5 Turbo / GPT‑4** – stable, widely available, good code generation.
* **Claude (Anthropic)** – similar performance on reasoning tasks; check pricing for bulk calls.
* **Llama 2 (via hosted providers)** – open‑source alternative; ensure the provider exposes a “completion” endpoint with temperature control.

If you need to stay within a strict budget, start with GPT‑3.5 Turbo; its token cost is low and it already achieves the 10 % average AUC gain reported in the FeatLLM paper.

---

## 2. Preparing Your Tabular Data

### 2.1 Gather Feature Names and Definitions
FeatLLM relies on *natural‑language* descriptions of each column (e.g., “`age` – patient’s age in years”, “`cholesterol` – total cholesterol level (mg/dL)”). Even a one‑sentence definition helps the LLM focus on relevant variables during rule extraction.

*If you lack documentation:*  
- Pull column names from your schema.  
- Write concise definitions manually or generate them with a quick LLM call (prompt: “Describe the column `XYZ` given these example values”).

### 2.2 Select a Few‑Shot Subset
Choose \(k\) labeled rows (the paper shows strong results with as few as 4–8 shots). Ensure each class appears at least once; otherwise the LLM cannot infer class‑specific rules.

### 2.3 Serialize Samples for Prompting
Follow the format used in FeatLLM:

```
f1 is <value1>. f2 is <value2>. … fd is <valued>. Answer: <label>
```

Keep each example on its own line; this deterministic layout makes it easier for the LLM to parse.

---

## 3. Prompt Engineering & Hyper‑Parameter Tuning

FeatLLM’s prompt has three logical blocks:

1. **Basic Information** – task description, feature list with types, few‑shot examples.
2. **Reasoning Instruction** – two‑step chain of thought: first infer causal relationships from prior knowledge, then derive concrete rules.
3. **Response Instruction** – explicit JSON‑like template that tells the LLM how to format each rule (e.g., `"rule_id": "R1", "condition": "age > 60"`).

### Key Hyper‑Parameters

| Parameter | Typical Value | Effect |
|-----------|----------------|--------|
| `num_rules_per_class` | 10 | Too few → under‑fitting; too many → noisy features and longer prompts. |
| `num_ensembles` | 20 | More ensembles improve robustness but increase total API calls linearly. |
| `temperature` | 0.5 (default) for base runs; increase to 0.7–0.9 when you want more diverse rule sets for ensembling. |
| `bagging_fraction` | 0.7 of columns per ensemble | Reduces prompt size on high‑dimensional tables and introduces randomness helpful for ensemble diversity.|

A quick grid search on a validation split of your few‑shot set can pinpoint a sweet spot—typically AUC plateaus after ~15 ensembles and ~10 rules per class.

---

## 4. Extracting and Parsing Rules

### 4.1 Sending the Prompt
Perform a batch request for each ensemble iteration:

```python
response = openai.ChatCompletion.create(
    model="gpt-3.5-turbo",
    temperature=0.5,
    messages=[{"role": "system", "content": prompt}],
)
raw_rules = response["choices"][0]["message"]["content"]
```

Store `raw_rules` for each ensemble; they will later be parsed independently.

### 4.2 Turning Natural Language into Executable Code
Even though FeatLLM already forces a structured format, minor syntax variations (“greater than” vs “>”) still appear. The simplest pipeline is:

1. Feed `raw_rules` back to the same LLM with a *code generation* prompt that asks:  
   *“Given these rule strings, write a Python function `apply_rules(df)` that returns a binary matrix where each column corresponds to one rule.”*
2. Execute the returned snippet safely using `exec()` inside a sandboxed environment (e.g., `restrictedpython` or Docker).

The function will produce a NumPy array \(\mathbf{Z} \in \{0,1\}^{N \times R}\) where \(R = \text{num\_rules\_per\_class} \times \text{num\_classes}\).

---

## 5. Training the Downstream Linear Model

With binary rule features in hand, training is trivial:

```python
import torch
import torch.nn.functional as F

# Z: shape (num_samples, R)
# y: integer class labels
weights = torch.nn.Parameter(torch.rand(R), requires_grad=True)

optimizer = torch.optim.Adam([weights], lr=0.01)

for epoch in range(200):
    logits = torch.clamp(weights, min=0) * Z   # elementwise product per class handled later
    probs = F.softmax(logits.view(-1, num_classes), dim=1)
    loss = F.cross_entropy(probs, y)
    optimizer.zero_grad()
    loss.backward()
    optimizer.step()
```

Key points:

- **Non‑negative projection (`clamp(weights, min=0)`)** ensures rules never *hurt* a class’s score.
- Because there are only ~10 × C parameters per ensemble, convergence occurs within seconds on CPU.
- After training, discard any rule whose weight falls below a threshold (e.g., 0.1). This automatically prunes weak or spurious rules.

Combine predictions from all ensembles by averaging their softmax vectors—this yields the final probability distribution used in production.

---

## 6. Production Integration

### 6️⃣ Model Artifacts to Store
| Artifact | Format |
|----------|--------|
| Feature description JSON | Human readable metadata |
| Rule matrix (`R × C`) + weights per ensemble | Serialized NumPy (`*.npz`) |
| Inference function (`apply_rules`) | Python module or compiled Cython version |
| Ensemble averaging logic | Simple wrapper script |

Version these artifacts with Git tags or an MLOps platform like MLflow so you can roll back if downstream drift appears.

### ⚡ Runtime Flow
1. Incoming record → convert to Pandas DataFrame row.
2. Call `apply_rules(row)` → binary vector.
3. Multiply by learned weights → logits → softmax.
4. If you have multiple ensembles, repeat steps 2–3 and average probabilities.
5. Return prediction / probability to downstream service.

Since step 2 is pure Python (or compiled), latency is on the order of milliseconds—comparable to classic tree models and drastically lower than sending each sample through an LLM.

### Monitoring & Retraining
- Track *rule usage*: proportion of samples activating each rule gives insight into whether certain rules become obsolete.
- Set up periodic re‑extraction (e.g., monthly) if data distributions shift; reuse existing hyper‑parameters to keep cost low (≈ 30 API calls per re‑run).

---

## TL;DR Checklist

- **API selection:** Choose an LLM with temperature control & code generation.
- **Feature docs:** Write concise natural-language definitions for every column.
- **Few-shot samples:** Ensure at least one example per class.
- **Prompt design:** Follow FeatLLM’s three‐part layout; fix number of rules (=10).
- **Ensemble settings:** Use ~20 ensembles + feature bagging (~70 % columns per ensemble).
- **Rule parsing:** Leverage the same LLM to output clean Python predicates; execute safely.
- **Linear training:** Non‑negative weights + cross‑entropy; train ≤ 200 epochs.
- **Deploy:** Store rule matrices & weights; runtime inference ≈ ms per record.

By treating an LLM as a *knowledgeable analyst* rather than an end‑to‑end predictor, FeatLLM gives you high accuracy in low‑shot regimes while keeping inference cheap and explainable—exactly what production teams need when data labeling budgets are tight but domain expertise lives inside massive pretrained models.

Happy feature engineering! 🚀
