# From 16‑bit to 1.58‑bit: How BitNet b1.58 Shrinks LLMs Without Losing Accuracy  

Large language models (LLMs) have become the workhorse of modern NLP, but their ever‑growing size brings hefty memory, latency, and energy costs. Recent progress in quantization shows that we can trim the bits used to store model parameters—sometimes dramatically—while keeping the model useful. The newest milestone is **BitNet b1.58**, a transformer whose every weight is ternary (‑1, 0, +1). Despite using only **1.58 bits** per parameter on average, it matches full‑precision (FP16/BF16) LLaMA baselines in perplexity and downstream task performance.  

In this post we walk through the core ideas that make this possible: the ternary quantization scheme, why the extra “0” value matters, and how the resulting model sidesteps the usual trade‑off between bit‑width and accuracy.

---

## Why Go Below 2 Bits?  

Standard LLMs store weights as 16‑bit floating‑point numbers. Most of the compute in a transformer is spent on matrix multiplications inside `nn.Linear` layers, which require costly FP16 multiplies and adds. By collapsing the weight space to a tiny set of integer values we replace those multiplications with cheap integer additions.  

A pure 1‑bit model would restrict weights to {‑1,+1}. That eliminates multiplications altogether but also removes a way to **filter** information: every input dimension contributes either positively or negatively, never “off”. BitNet b1.58 adds a third option, **0**, which lets the network explicitly drop irrelevant features at each layer. The result is a *ternary* representation that behaves like a “soft” sparsity pattern while still needing almost no multiplication.

---

## Ternary Quantization: From Real Weights to {‑1, 0, +1}

Training starts with full‑precision weights \(W\in\mathbb{R}^{n\times m}\). To force them into the ternary set we apply an **absmean quantizer**:

\[
\gamma = \frac{1}{nm}\sum_{i,j}|W_{ij}| \quad\text{(average absolute magnitude)}
\]

\[
\widetilde{W}_{ij}= \operatorname{RoundClip}\!\left(\frac{W_{ij}}{\gamma+\epsilon},\, -1,\, 1\right)
\]

where  

\[
\operatorname{RoundClip}(x,a,b)=\max\bigl(a,\;\min\bigl(b,\;\operatorname{round}(x)\bigr)\bigr)
\]

and \(\epsilon\) is a tiny constant for numerical stability.  

The scaling by \(\gamma\) normalizes the weight distribution so that most entries land near zero after division; rounding then snaps each entry to the nearest integer in \{-1,0,+1\}. Because \(\gamma\) is recomputed each step, the quantizer adapts as training progresses, preserving gradient flow while keeping the weights ternary.

### Activation Quantization

Activations stay in 8‑bit integer format (INT8). Unlike BitNet’s original scheme that shifts activations into \([0,Q_b]\), BitNet b1.58 scales them symmetrically to \([-Q_b,Q_b]\) per token. This removes the need for a zero‑point offset and simplifies hardware implementation without measurable loss in accuracy.

---

## Zero Weights Aren’t “Empty”: The Role of Sparsity

The added zero value gives each linear layer a built‑in **feature selector**:

* **Noise reduction** – If an input dimension consistently harms predictions, its weight can become zero, preventing it from affecting downstream layers.
* **Effective sparsity** – Even though every weight is stored (as 2 bits for sign + an extra bit for “is zero”), many of them become zero during training, yielding fewer active MAC operations.
* **Better representational capacity** – With three possible states per weight we get roughly \(\log_2(3) \approx 1.58\) bits of information per parameter—hence the name *b1.58*. This modest increase over pure 1‑bit gives enough flexibility to recover accuracy losses that would otherwise appear.

Empirically, this design choice pays off: starting at just 3 B parameters, BitNet b1.58’s perplexity on WikiText‑2 and C4 aligns with its FP16 LLaMA counterpart, and downstream zero‑shot benchmarks (ARC-Easy/Challenge, Hellaswag, Winogrande, PIQA, etc.) are within a few percentage points—often indistinguishable when model size grows beyond 3 B.

---

## Performance Gains: Speed, Memory & Energy

| Metric (3 B model) | FP16 LLaMA | BitNet b1.58 |
|-------------------|------------|--------------|
| Perplexity (WikiText‑2) | ~8.5 | ~8.5 |
| GPU memory (GiB) | 14 | **4** (≈3.5× less) |
| Token latency (ms) | 12 | **4.5** (≈2.7× faster) |
| Energy per matmul (7nm estimate) | 1× | **0.014×** (~71× savings) |

Key observations:

* **Latency** improves because a ternary matrix multiply reduces to integer additions; on GPUs this translates into fewer hardware cycles.
* **Memory** shrinks dramatically: storing 2 bits per weight versus 16 bits yields a >8× raw reduction; after accounting for metadata and activations we still see >3× savings.
* **Energy** consumption drops by more than an order of magnitude for matrix multiplication—the dominant operation in LLM inference.

These advantages amplify with scale: a 70 B BitNet b1.58 runs roughly **4× faster** than a 70 B FP16 LLaMA model while using far less memory; throughput on dual A100s rises almost tenfold thanks to larger batch sizes fitting into GPU RAM.

---

## Training at Scale: The Token Budget Matters

BitNet b1.58 was trained from scratch on the RedPajama corpus for **100 B tokens**, matching the token budget of the reproduced FP16 baselines. When extended to **2 T tokens**, following StableLM‑3B’s data recipe, the ternary model outperformed StableLM on every evaluated task (Winograde, PIQA, SciQ, LAMBADA, ARC‑Easy). This demonstrates that reduced precision does not hinder learning dynamics provided enough data is supplied.

---

## What This Means for Future LLMs

* **New scaling law:** A 13 B BitNet b1.58 is more efficient than a 3 B FP16 model; a 30 B ternary model beats a 7 B full‑precision one; even a 70 B b1.58 surpasses a 13 B FP16 baseline in latency, memory and energy.
* **Edge & mobile deployment:** With sub‑4 GiB memory footprints for multi‑billion parameter models and CPU‑friendly INT8 activations, ternary LLMs become viable on devices previously incapable of running any transformer at all.
* **Hardware opportunities:** The near‑absence of multiplications opens up specialized accelerators (e.g., LPUs à la Groq) that can implement dedicated INT8 add pipelines and massive parallel SRAM arrays tailored for ternary weights.
* **Mixture-of-Experts & long context:** Ternary weights reduce inter‑chip communication overhead in MoE architectures and cut KV‑cache size by half (activations are already INT8), paving the way for native long‑sequence support.

---

## Takeaway

BitNet b1.58 proves that *fewer bits do not inevitably mean weaker models*. By carefully designing a ternary quantizer and leveraging the expressive power of zero weights, we can compress every parameter down to an average of **1.58 bits** while preserving—and sometimes even improving—accuracy on standard LLM benchmarks. The resulting speedups, memory savings, and energy reductions are substantial enough to rewrite deployment economics for both cloud-scale inference and edge devices.

If you’re interested in experimenting with ternary LLMs yourself, look for implementations integrated with HuggingFace Transformers or vLLM; they already include BitLinear layers that handle the quantization logic out of the box.

*The era of ultra‑low‑bit LLMs has arrived—welcome to the world of 1.58‑bit transformers.*

## Why “1‑bit” Matters  

Large language models (LLMs) have exploded in size, but the cost of running them grows roughly linearly with the number of floating‑point operations (FLOPs) and the amount of data that must be moved from DRAM to the accelerator. Traditional LLMs store every weight as 16‑bit floating point (FP16/BF16). The **BitNet** family takes a radical step: it reduces each weight to a *ternary* value {‑1, 0, +1}.  

Because the three values can be encoded in **1.58 bits** (the extra “0” adds a tiny amount of information), matrix multiplication no longer needs multiplications—just integer additions. The result is a dramatic drop in:

| Metric | FP16 LLM | BitNet b1.58 |
|--------|----------|--------------|
| Weight size per parameter | 2 bytes | ≈0.2 bytes |
| Dominant operation | FP16 multiply‑add | INT8 add |

That’s a **>70× reduction in arithmetic energy** for the core multiply‑add step.

## How Does BitNet Achieve This?  

### Ternary Weights (+0 Support)  

The original pure 1‑bit models could only store {‑1,+1}. BitNet b1.58 adds a zero, which serves two purposes:

1. **Feature Filtering:** Zero weights effectively prune connections during inference, giving the model more expressive capacity without extra bits.
2. **Sparsity Benefits:** The extra state enables better alignment between the quantized weights and the underlying distribution of learned parameters.

The quantization pipeline works as follows:

\[
\widetilde{W}= \mathrm{RoundClip}\!\left(\frac{W}{\gamma+\epsilon},\,-1,\,1\right), \qquad
\gamma = \frac{1}{nm}\sum_{i,j}\lvert W_{ij}\rvert,
\]

where `RoundClip` forces every entry into {‑1,0,+1}. Because we scale by the *average absolute value* (`absmean`), the ternarization preserves the overall magnitude of each matrix.

### 8‑bit Activations  

While weights are ternary, activations stay in INT8 instead of full precision. This keeps the dynamic range sufficient for transformer non‑linearities while still cutting activation bandwidth by **half** compared to FP16.

### Compatibility with LLaMA Stack  

BitNet b1.58 swaps every `nn.Linear` for a custom `BitLinear`, but otherwise inherits LLaMA’s RMSNorm, SwiGLU, rotary embeddings, and bias‑free design. This means you can drop it into popular pipelines (HuggingFace 🤗 Transformers, vLLM, or even `llama.cpp`) with minimal code changes.

---

## Benchmarks: Perplexity & Zero‑Shot Accuracy  

The paper trained models on **100 B tokens** from RedPajama and evaluated them on standard benchmarks (ARC‑Easy/Challenge, Hellaswag, Winogrande, PIQA, OpenbookQA, BoolQ). Highlights:

- **Perplexity:** Starting at 3 B parameters, BitNet b1.58 matches FP16 LLaMA perplexity on WikiText2 and C4.
- **Zero‑Shot Accuracy:** Gaps shrink as models grow; at 13 B BitNet the average score is within *0.2%* of its FP16 counterpart.
- **Throughput:** On two A100 80GB cards with pipeline parallelism, a 70 B BitNet processes **~9×** more tokens per second than a 70 B FP16 LLaMA.

These results confirm that *the reduction in bits does not sacrifice quality*—it merely removes wasted floating‑point arithmetic.

## Real‑World Impact: What Does This Mean for Practitioners?  

### Faster Prototyping & cheaper inference  
If you’re running an API that serves millions of requests daily, moving from an FP16 LLM to BitNet b1.58 can cut your GPU bill by roughly **⅓** for the same latency target.

### Deployments on Edge & Mobile  
With weights stored at ~0.2 bytes each and activations at 8 bits, even a 7 B BitNet fits comfortably inside modern high‑end smartphones (≈15 GB total footprint). That opens doors for on‑device assistants that never need to talk to the cloud.

### Future Hardware Opportunities  
Because matrix multiplication reduces to integer additions only, designers can build *LPUs* (logic processing units) that omit floating‑point units entirely—think “digital ASICs for language” rather than GPUs designed for graphics.

## The Takeaway  

The era of “bigger is better” for LLMs is giving way to “smaller bits are smarter.” **BitNet b1.58 demonstrates a new scaling law:** as you increase model size *and* adopt ternary weights + INT8 activations, you simultaneously improve performance *and* slash inference cost dramatically.

- A **13 B** ternary model beats a **3 B** FP16 model in latency, memory usage, and energy.

If you’re building next‑generation AI services—whether in cloud data centers or on edge devices—consider flipping the switch to **1.58‑bit LLMs** today. Your servers will run faster, your GPUs will stay cooler, and your carbon footprint will shrink—all without compromising on language understanding.

# Inside BitLinear: Re‑engineering the Transformer’s Workhorse for Integer‑Only Math  

## Introduction  

The linear layer (`nn.Linear`) is the beating heart of every Transformer‑based Large Language Model (LLM). It performs the bulk of the computation in the form of dense matrix multiplications, which are expensive in both energy and latency when using 16‑bit floating‑point formats (FP16/BF16).  

The recent **BitNet b1.58** paper shows that we can replace this workhorse with a radically different module called **BitLinear**. By constraining weights to the ternary set \(\{-1,0,1\}\) and keeping activations at 8 bits, matrix multiplication collapses into a series of integer additions. This seemingly modest change unlocks massive gains in speed, memory footprint, and energy consumption, and paves the way for specialized hardware that operates almost entirely on integer arithmetic.

In this post we break down how BitLinear works, why the **absmean quantization** function is key, how activations are handled, and what this redesign means for future accelerators.

## From `nn.Linear` to BitLinear: What Changes?  

A standard `nn.Linear` computes  

\[
Y = XW^{\top} + b,
\]

where \(X\) (batch × seq_len × in_dim) and \(W\) (out_dim × in_dim) are floating‑point tensors and \(b\) is a bias (often omitted in modern LLMs). The operation consists of:

1. **FP16 multiplication:** each element of \(X\) multiplies a weight element.  
2. **FP16 addition:** results are summed across the input dimension.  

Both steps dominate the power draw of modern GPUs because floating‑point multiply‑accumulate units are orders of magnitude more energy hungry than simple integer adders.

**BitLinear** rewrites this computation as  

\[
Y = \operatorname{IntAdd}\bigl( X_{\text{int8}} \odot \widetilde{W}_{\{-1,0,1\}} \bigr),
\]

where:

* \(\widetilde{W}\) holds **ternary** values only.  
* \(X_{\text{int8}}\) stores activations as signed 8‑bit integers.  
* The “multiplication” \(\odot\) reduces to either adding, subtracting, or skipping a term based on the weight’s sign (or zero).  

Consequently, **no FP16 multiplications are needed**, and the entire GEMM (general matrix multiply) reduces to a handful of integer additions – a dramatically cheaper operation on silicon.

## The Absmean Quantization Function  

To force every weight into \(\{-1,0,1\}\) while preserving as much information as possible, BitNet b1.58 uses an **absmean quantizer**:

\[
\gamma = \frac{1}{nm}\sum_{i,j}|W_{ij}|,
\qquad
\widetilde{W}_{ij}= \operatorname{RoundClip}\!\left(\frac{W_{ij}}{\gamma+\epsilon},\, -1,\,1\right),
\]

where:

* \(W \in \mathbb{R}^{n\times m}\) is the full‑precision weight matrix.  
* \(\gamma\) is the **average absolute magnitude** of all weights – a single scalar that captures the typical scale of the tensor.  
* `RoundClip` first rounds to the nearest integer and then clamps to the interval \([-1,1]\).  
* A tiny constant \(\epsilon\) avoids division by zero.

Intuitively, dividing by \(\gamma\) normalizes the whole matrix so that most entries fall inside \([-1,1]\). After rounding, each entry becomes -1, 0, or +1. The zero value is crucial: it lets the network *filter* irrelevant features without incurring any addition cost during inference.

### Why “absmean” Works  

Unlike per‑channel or per‑tensor min‑max scaling used in post‑training quantization (which often harms accuracy), absmean preserves **relative weight magnitudes** across rows and columns because every element shares the same scale factor. Empirically the paper shows that this simple scheme yields no measurable loss in perplexity when models reach 3 B parameters or larger.

## Activation Handling: 8‑bit Signed Integers  

The original BitNet design quantizes activations to unsigned integers in \([0,Q_b]\) and then adds a zero point. BitNet b1.58 simplifies this further:

* Activations are directly scaled to **signed** int8 in \([-Q_b,Q_b]\).  
* No zero‑point offset is needed; we just clip after rounding.

Mathematically:

\[
A_{\text{int8}} = \operatorname{RoundClip}\!\left(\alpha X,\; -Q_b,\; Q_b\right),
\]

with a single scale factor \(\alpha\) computed per token (or per batch). This avoids extra add operations during dequantization and aligns perfectly with the ternary weight format: an activation multiplied by -1 becomes a subtraction; multiplied by +1 becomes an addition; multiplied by 0 is omitted altogether.

## Why This Redesign Is Hardware‑Friendly  

### Minimal Multiplication Units  

ASICs and FPGAs allocate large silicon area for floating‑point multipliers because they cannot be avoided in conventional LLMs. With BitLinear:

* Multipliers disappear from the GEMM path.
* Only **integer adders**, which are tiny and can be massively parallelized, remain.
* Memory bandwidth dominates less because each weight now occupies **2 bits** (theoretical 1.58 bits after packing), allowing more weights to sit on chip caches.

### Simpler Data Paths  

The absence of scaling factors for each weight eliminates dynamic range handling logic (e.g., exponent alignment). The quantization pipeline reduces to:

```
load weight (2 bits) → decode to {-1,0,+1}
load activation (int8)
if weight == 0 → skip
else if weight == 1 → accumulate activation
else → accumulate -activation
```

Such a deterministic flow maps cleanly onto systolic arrays or tensor cores that natively support integer add/subtract streams.

### Energy Savings  

Based on the energy model from *EnergyCost* and *PokeBNN*, INT8 addition consumes roughly **0.01 pJ**, while an FP16 multiply–accumulate can exceed **0.7 pJ** on a 7 nm process—a >70× improvement per operation. Because GEMM accounts for >80% of LLM FLOPs, BitLinear translates into **71× lower arithmetic energy** for matrix multiplication alone.

### Memory Bandwidth Reduction  

A ternary weight packed at 2 bits means an effective compression factor of **8×** compared with FP16 (16 bits). When combined with int8 activations (4× compression), total data movement per GEMM drops by over **30×**, easing pressure on DRAM‑to‑SRAM transfers—a known bottleneck for large models.

## Real‑World Impact: Benchmarks from BitNet b1.58  

| Model | Weight Format | Activation | Perplexity (WikiText2) | Speedup vs FP16 | Memory reduction |
|------|---------------|------------|------------------------|----------------|-------------------|
| 3 B  | ternary (-1/0/1) | int8 | ≈ 5.2 (matches FP16) | 2.7× | 3.6× |
| 7 B  | ternary          | int8 | ≈ 4.9               | 3.4× | 4.2× |
| 70 B | ternary          | int8 | ≈ 4.5               | 4.1× | 5.5× |

These numbers come directly from the paper’s Table 1 and Figures 2–4: even at massive scales (>70 B parameters), BitLinear retains full‑precision quality while delivering multi‑fold speedups and slashing memory usage.

## Looking Ahead: From BitLinear to Dedicated Accelerators  

The architectural shift introduced by BitLinear invites a new class of “**integer‑only LLM chips**”. Designers can:

* Build ultra‑dense weight SRAMs that store packed ternary tensors.
* Deploy wide SIMD lanes devoted exclusively to signed‐add–subtract operations.
* Eliminate floating‑point units completely for inference pipelines.
* Optimize data movement pipelines for packed weight streams, enabling “on‑the‑fly” decoding of ternary values without decompressing them into larger registers.

Early prototypes such as Groq’s LPUs already hint at how specialized compute units can dramatically accelerate inference workloads; BitLinear makes it possible to push that specialization even further—down to a *single bit* representation plus an explicit zero.

## Conclusion  

BitLinear demonstrates that we do not need high‑precision arithmetic to preserve LLM quality once we rethink quantization at its core. By quantizing weights with an absmean function into ternary values and using signed int8 activations, matrix multiplication becomes pure integer addition—dramatically cheaper in both silicon area and energy.

For practitioners, swapping `nn.Linear` for `BitLinear` is as simple as changing one import line if you’re using the open‑source LLaMA codebase integrated with HuggingFace or vLLM. For hardware architects, it opens a clean path toward dedicated integer‐only accelerators that can host models up to dozens of billions of parameters on far smaller power budgets.

The era of “all LLMs are in ~1½ bits” is not just a clever slogan; it’s a concrete engineering recipe that reshapes both software stacks and silicon design—starting with one humble linear layer called **BitLinear**.



# Deploying LLMs on the Edge: Why 1.58‑bit Models Are a Game‑Changer for Mobile AI

Large language models (LLMs) have become the backbone of everything from chat assistants to code generators. Yet their impressive capabilities come at a steep cost: billions of parameters stored in 16‑bit floating‑point tensors, massive matrix‑multiplication workloads, and hefty memory bandwidth requirements. For cloud‑only deployments this is acceptable, but when we want LLMs to live on a smartphone, an IoT sensor, or any edge device, those costs explode.

A recent paper, **“The Era of 1‑bit LLMs: All Large Language Models are in 1.58 Bits”**, introduces **BitNet b1.58**, a transformer whose every weight is ternary ( -1, 0, +1 ). In other words, each parameter requires only **1.58 bits** on average. The authors demonstrate that from 3 B parameters upward, this ultra‑low‑precision model matches the perplexity and zero‑shot task performance of a full‑precision FP16 LLaMA baseline while slashing latency, memory usage, and energy consumption.

Below we translate those findings into concrete implications for edge AI. We’ll explore how the reduced memory footprint and power draw enable realistic on‑device scenarios—offline translation, privacy‑preserving personal assistants, and more—while staying compatible with existing CPUs and NPUs.

---

## 1. From 16 bits to 1.58 bits: What changes on the device?

### 1.1 Dramatically smaller model size  
A 7 B FP16 model occupies roughly  

\[
7 \times 10^9 \times 16\ \text{bits} \approx 14\ \text{GB}.
\]

BitNet b1.58 stores the same number of parameters using only 1.58 bits each:

\[
7 \times 10^9 \times 1.58\ \text{bits} \approx 1.4\ \text{GB}.
\]

That’s a **10× reduction** in storage. For a typical smartphone with 12–16 GB of RAM, a full‑size LLM is impossible to load; a 1.58‑bit version comfortably fits even when other apps are running.

### 1.2 Faster inference due to multiplication‑free matmuls  
The core linear layers in a transformer become **integer additions** when weights are ternary:

\[
Y = XW \quad\rightarrow\quad Y = X(+1) - X(-1) + 0.
\]

No floating‑point multiplications are needed; hardware can execute these additions in a single cycle on most CPUs/NPUs. The paper reports up to **4× speedup** for a 70 B model compared with FP16 baseline when running on GPU kernels optimized for 2‑bit operations.

### 1​.​3 Lower bandwidth and energy  
Moving data from DRAM to on‑chip SRAM dominates inference latency on mobile SoCs. Cutting weight size by an order of magnitude reduces this traffic proportionally. Using an energy model for 7 nm silicon, the authors estimate **~71× less energy** per matrix multiplication compared with FP16 arithmetic.

For battery‑powered devices this translates directly into longer runtimes for AI features or lower thermal output—both critical for user experience.

---

## 2. Compatibility with existing mobile hardware

### CPUs  
Most modern mobile CPUs already support SIMD integer instructions (e.g., ARM NEON). Since BitNet b1.58 operates with **8‑bit activations** and **ternary weights**, it can be implemented with existing integer vector units without any special accelerator.

### NPUs / DSPs  
Neural processing units typically provide dedicated INT8 MAC units but often lack efficient FP16 support due to area constraints. BitNet’s reliance on **INT8 additions** (the weight sign can be applied via simple conditionals) fits perfectly into the NPU execution model, allowing developers to run inference without re‑architecting their pipelines.

### Specialized accelerators  
The paper mentions projects like Groq’s LPUs that already target low‑precision kernels. A dedicated **2‑bit matrix multiply kernel** (as used in their experiments) could be integrated into future edge ASICs, delivering even higher throughput while retaining the same memory savings.

---

## 3. Realistic edge use cases enabled by 1.58‑bit LLMs

### Offline translation on smartphones  
Current on‑device translation relies on compact encoder–decoder models that sacrifice accuracy for size. A **3 B BitNet b1.58** model can sit comfortably in RAM and run at real‑time speeds (≈30–40 ms per token on a modern flagship phone). Users could translate text locally without sending data to the cloud—enhancing privacy and reducing latency.

### Personal assistants that never leave the device  
Privacy concerns drive demand for assistants that process voice commands entirely offline. With ternary weights and INT8 activations, a **5 B BitNet b1.58** assistant fits within the memory budget of most high‑end phones and can execute conversational prompts in under half a second, all while drawing less than half the power of an equivalent FP16 model.

### IoT sensors with natural language interfaces  
Think smart thermostats or industrial controllers that accept spoken commands but lack an internet connection. A **2 B BitNet b1.58** model occupies <400 MB and can run on modest ARM Cortex‑M microcontrollers equipped with an NPU (e.g., Edge TPU). This opens the door to “talk-to‑your‑sensor” experiences without cloud reliance.

### On-device content moderation  
Edge devices can pre-filter user-generated text before it reaches servers—crucial for compliance in regulated environments (healthcare, finance). Because BitNet b1.58 preserves perplexity and zero‑shot task performance from the full‑precision baseline, moderation models remain accurate while incurring minimal overhead.

The shift from FP16 to **1.58‑bit ternary weights** isn’t just a clever quantization trick—it reshapes the entire cost profile of large language models. # Future Hardware for 1‑bit LLMs: From GPUs to Custom LPUs  

## Why 1‑bit LLMs are a hardware game‑changer  

Large language models have become the workhorse of modern NLP, but their massive floating‑point matrices still dominate compute, memory bandwidth, and energy budgets. The recent **BitNet b1.58** paper shows that we can squeeze *every* weight down to a ternary set \(\{-1,0,+1\}\) – effectively 1.58 bits per parameter – while keeping activations at 8 bits.  

The trick that makes this possible is a **“almost no multiplication”** matrix multiply. With ternary weights the product \(w \times a\) reduces to three cases:

| \(w\) | Operation on activation \(a\) |
|------|------------------------------|
| \(-1\) | Negate \(a\) (i.e., \(-a\)) |
| \(0\)  | Skip (add 0) |
| \(+1\) | Pass through (add \(a\)) |

Thus the expensive FP16/FP32 MAC (multiply‑accumulate) collapses into a cheap integer addition plus an optional sign flip. For chip designers, this means:

* **Multipliers can be eliminated** from the inner loops of transformer linear layers.  
* **Logic for sign‑flip and zero‑skip** is far cheaper in area and power than a full‑precision multiplier array.  
* **Memory bandwidth requirements drop dramatically** because each weight now needs only 2 bits of storage (the extra “zero” state is encoded efficiently).  

These observations open a whole new design space for accelerators that are *tailored* to the BitNet computation paradigm.

---

## Existing attempts: Groq’s LPUs  

Groq’s **Tensor Streaming Processor (TSP)**, sometimes marketed as an LPU (Language Processing Unit), already departs from the traditional SIMD/GPU model. Its key ideas—massive on‑chip SRAM, a streaming dataflow, and a focus on deterministic latency—align well with what 1‑bit LLMs demand:

* **Streaming execution** keeps weights close to the compute units, reducing DRAM traffic—a problem that BitNet solves at the algorithmic level already.
* **Fixed‑function pipelines** for matrix multiply can be replaced with *ternary‑weight pipelines*, saving silicon real estate.
* **Energy per operation** reported by Groq (sub‑femtojoule per INT8 add) suggests that a dedicated ternary‑weight engine could push energy down another order of magnitude.

Groq’s hardware thus serves as a proof‑of‑concept: when you remove multipliers and shrink weight storage, you can achieve both higher throughput and lower power.

---

## Sketching a silicon implementation for ternary weights  

Below is a high‑level blueprint of what a **BitNet‑optimized accelerator** could look like.

### 1. Weight storage layout  

* **2‑bit encoding per weight**: Use two bits `(b1,b0)` where `00 → -1`, `01 → 0`, `10 → +1`. The pattern `11` can be reserved for control or error detection.
* **Packed into SRAM banks**: Because each weight occupies only 2 bits, a 128 KB SRAM bank can hold 512 k weights—enough for several transformer heads.
* **Row/column tiling**: Align tiles with the attention heads so that fetching an entire tile yields contiguous memory accesses.

### 2. Compute engine  

| Block | Function | Implementation notes |
|------|----------|----------------------|
| **Sign‑flip unit** | Turns an INT8 activation into its negation when `w = -1`. | Simple bitwise NOT + add‑one (two’s complement). Can be merged with the adder tree to avoid extra latency. |
| **Zero‑skip logic** | Drops the addition when `w = 0`. | A mask generated from the weight bits gates the adder inputs; no energy is spent on those lanes. |
| **INT8 adder array** | Accumulates contributions from all active lanes. | Use wide tree adders; carry‑save techniques keep latency low because there is no multiplication involved. |
| **Accumulator registers** | Store partial sums (often in 32‑ or 48‑bit to avoid overflow). | Same as in conventional GPUs, but with fewer read/write ports because each lane contributes at most one add per token. |

Because every lane performs either “add”, “add −”, or “skip”, the datapath can be *reconfigured* at runtime based on the weight pattern, leading to dynamic power gating for inactive lanes.

### 3. Activation handling  

Activations stay in INT8 form throughout the network (the paper uses 8‑bit activations). The pipeline therefore requires:

* **8‑bit quantizer/dequantizer blocks** at model boundaries (embedding layer, final projection).  
* **Saturation logic** to prevent overflow when accumulating many INT8 adds; this is where wider accumulators pay off.

### 4. Interconnect & memory hierarchy  

* **On‑chip network-on-chip (NoC)** optimized for *broadcast* of activations to many weight tiles – essentially a multicast tree that mirrors the attention pattern.
* **Tile‐level prefetchers** that fetch the next weight block while the current block is being processed – similar to classic GPU prefetch but with much smaller bandwidth requirements.

### 5. Programmability  

Even though the hardware is highly specialized, providing a thin software layer (e.g., a custom PyTorch/XLA backend) enables existing model code to run unchanged:

```python
model = BitNetB158.from_pretrained('bitnet-b1.58-7b')
output = model.generate(input_ids)
```

The backend would translate `nn.Linear` calls into calls to our ternary engine, automatically handling sign/zero masks.

---

## What performance gains can we expect?  

The BitNet paper reports a **71× reduction in arithmetic energy** for matrix multiplication on a 7 nm process when moving from FP16 MACs to INT8 adds with ternary weights. Translating this to silicon:

| Metric | FP16 GPU (baseline) | BitNet Ternary Engine (estimated) |
|--------|--------------------|-----------------------------------|
| MAC per second per mm² | ~10 TOPS/mm² | ~0 (no MACs) → ~70 TOPS/mm² equivalent add throughput |
| Energy per operation | ~10 pJ/MAC | ~0.14 pJ/add |
| Memory bandwidth needed for weights | 16 bits/param | 2 bits/param |

Thus, a chip that dedicates half its die area to ternary compute could *outperform* a comparable GPU in LLM inference speed while consuming less than one tenth of the power.

---

## Future directions and research challenges  

1. **Mixed precision pipelines** – While weights are ternary, some intermediate layers (e.g., layer norms) still need higher precision. Designing efficient bridges between INT8/FP16 pipelines remains open.

2. **Sparse zero handling** – The presence of zeros invites *structured sparsity*: if many weights are zero within a tile, we can skip entire rows/columns, further cutting compute and memory traffic.

3. **Algorithm–hardware co‑design** – Training methods that encourage more zeros (e.g., L₀ regularization) could amplify hardware benefits, creating a feedback loop between model sparsity and silicon efficiency.

4. **ASIC vs FPGA prototyping** – Early prototypes on high‑capacity FPGAs can validate sign‑flip/zero-skip microarchitectures before committing to ASIC masks.

5. **Toolchain integration** – Extending existing compilers like TVM or XLA to emit ternary kernels will lower adoption friction for developers.

---

## Closing thoughts  

The BitNet b1.58 results prove that *you don’t need full floating point precision* to match state-of-the-art LLM performance—ternary weights plus 8‑bit activations are enough if you train them correctly. For chip architects this is an invitation to rethink decades of GPU design assumptions: eliminate multipliers wherever possible, shrink weight storage dramatically, and build streaming dataflows that keep everything on chip.

Projects such as Groq’s LPUs already hint at what’s possible when you prioritize deterministic latency and memory locality over raw FLOPs. The next logical step is an accelerator whose very core is built around “add or skip” instead of “multiply‐and‐accumulate”. When such hardware becomes mainstream, we will finally see truly *cost‑effective*, *energy‑frugal*, and *accessible* large language models—from data centers down to edge devices.

The era of “almost no multiplication” has arrived—let’s build the silicon that fits it.



# Beyond Quantization: Training Large Language Models Directly in 1.58 Bits  

## Introduction  

Quantizing a pretrained language model to a lower precision (4‑bit, 2‑bit, …) has become the go‑to recipe for squeezing inference cost out of massive Transformers. The workflow is simple: train a full‑precision model, then apply post‑training quantization tricks such as smooth‑quant or GPTQ, and you get a smaller, faster model.  

But recent work on **BitNet b1.58** shows that this two‑step approach may be leaving performance on the table. Instead of “train‑then‑compress,” the authors train the whole model *from scratch* with **ternary weights** \(\{-1,0,1\}\), which corresponds to an average of **1.58 bits per weight**. The result is a model that matches (and sometimes exceeds) its FP16 counterpart on perplexity and downstream tasks while consuming dramatically less memory, latency, and energy.  

In this post we unpack why training directly at 1.58 bits is fundamentally different from post‑training quantization, what technical hurdles it raises, and how the BitNet b1.58 paper overcomes them.

## Post‑Training Quantization vs. From‑Scratch Low‑Bit Training  

| Aspect | Post‑Training Quantization | From‑Scratch 1.58‑bit Training |
|--------|---------------------------|--------------------------------|
| **When the model sees low precision** | After the full‐precision network has already converged | Throughout every forward & backward pass |
| **Typical bitwidth** | 4 bits (sometimes 2 bits) for weights/activations | Ternary weights (−1, 0, +1) + 8‑bit activations |
| **Gradient flow** | Not relevant – gradients are computed in full precision | Must estimate gradients through a discrete quantizer |
| **Performance ceiling** | Limited by quantization error on a fixed representation | Model learns a representation that *is* low‑bit |
| **Hardware friendliness** | Still needs dequantization kernels; mixed‑precision ops | Almost no multiplication – integer addition only |

The key insight is that quantization error is *inherent* when you try to map a high‑capacity FP16 solution onto a low‑bit space after training. In contrast, training with ternary weights forces the optimizer to shape the solution *inside* that low‑bit space from day one, allowing it to discover weight patterns that are inherently robust to the discrete set \(\{-1,0,1\}\).

## Core Challenges of Training at 1.58 Bits  

### 1. Discrete Weight Space  
Standard backpropagation relies on differentiable operations; rounding a weight to \{-1,0,1\} is non‑differentiable. This makes gradient estimation tricky.

### 2. Scale Ambiguity  
Ternary weights have no magnitude information beyond sign and sparsity (the zero). Without proper scaling, activations can either blow up or vanish.

### 3. Optimization Stability  
Training large Transformers is already finicky; adding discrete constraints can cause exploding/vanishing gradients or dead neurons.

### 4. Compatibility with Existing Transformer Building Blocks  
Components such as RMSNorm, SwiGLU and rotary embeddings were designed with floating point arithmetic in mind.

## Solutions Proposed in BitNet b1.58  

### AbsMean Quantization  
The authors introduce an **absmean** quantizer that first normalizes the weight matrix by its average absolute value \(\gamma\):

\[
\gamma = \frac{1}{nm}\sum_{i,j}|W_{ij}|
\]

Then each element is scaled by \(\frac{W}{\gamma+\epsilon}\) and rounded/clipped to \{-1,0,+1\}:

\[
\widetilde{W}= \text{RoundClip}\!\left(\frac{W}{\gamma+\epsilon},-1,1\right)
\]

This operation retains a global scaling factor (\(\gamma\)) that restores magnitude information lost by ternarization while keeping each individual weight strictly ternary.

### Straight‑Through Estimator (STE) for Gradients  
During backpropagation the quantizer is treated as an identity function – i.e., gradients are passed unchanged to the underlying full‑precision “shadow” weights before rounding them again for the next forward pass. This classic STE trick sidesteps nondifferentiability while still nudging the real parameters toward better ternary approximations.

### 8‑Bit Activations & Symmetric Quantization  
Activations are kept at 8 bits and quantized symmetrically around zero (range \([-Q_b,Q_b]\)). By avoiding a zero-point offset the implementation becomes simpler and incurs negligible accuracy loss.

### LLaMA‑Style Architecture Tweaks  
To ensure drop‑in compatibility with open-source ecosystems (HuggingFace, vLLM, llama.cpp), BitNet b1.58 adopts LLaMA’s RMSNorm, SwiGLU, rotary positional embeddings and removes bias terms altogether. Removing biases reduces unnecessary parameters that would otherwise waste precious bits.

### Efficient Integer Kernels  
Matrix multiplications turn into *integer addition* operations because multiplying by \(-1\), \(0\), or \(+1\) is equivalent to adding/subtracting or skipping terms. The paper plugs in a 2‑bit kernel from Ladder, showing real speedups on NVIDIA GPUs without any custom hardware.

## Empirical Evidence: Why Training Directly Wins  

- **Perplexity Matching:** Starting at 3 B parameters, BitNet b1.58’s validation perplexity on WikiText2 and C4 equals that of an FP16 LLaMA model trained under identical data (100 B tokens).  
- **Zero‑Shot Task Parity:** On benchmarks like ARC-Easy/Challenge, Hellaswag, Winogrande and BoolQ, the 3.9 B BitNet model matches or surpasses a 3 B FP16 baseline while using ~3× less memory and being ~2½× faster per token.  
- **Scaling Benefits:** At larger scales (70 B), BitNet b1.58 becomes over **4× faster** than FP16 LLaMA with proportionally lower memory usage—thanks to the linear growth of nn.Linear cost with model size being replaced by cheap integer adds.  
- **Energy Savings:** Modeling energy consumption per matrix multiply shows a **71× reduction** on a 7 nm process when using ternary weights versus FP16 multiplication/addition.

These results illustrate that *the representation learned under ternary constraints is not weaker*; rather it adapts to make effective use of sparsity (the zeros) and sign information (±1). Post‑training quantization cannot retroactively introduce such sparsity patterns because they were never part of the original optimization landscape.

## Broader Implications  

### Mixture‑of‑Experts (MoE) Becomes Viable  
MoE models typically suffer from huge memory footprints due to many expert parameters. With 1.58‑bit weights they can fit on far fewer chips and avoid costly inter‑chip traffic—potentially unlocking trillion‑parameter MoEs on commodity hardware.

### Longer Contexts on Fixed Hardware  
Reducing activations from FP16 to INT8 halves KV cache size, effectively doubling achievable context length for the same GPU memory budget.

### Edge & Mobile Deployment  
A ternary weight matrix fits comfortably into SRAM; integer addition pipelines are already present in many low‑power CPUs/NPUs, opening doors for true on‑device LLM inference.

### New Hardware Design Space  
Since multiplication disappears from the main compute path, future ASICs could be built around ultra‑efficient adders and bitwise selectors—think “LPUs” à la Groq but specialized for ternary matrix products.

## Takeaways  

- **Training directly at low bitwidth isn’t just a compression trick; it’s a fundamentally different learning regime** that lets models discover architectures inherently suited for discrete weights.
- The main technical hurdle—non‑differentiable quantization—is solved effectively with absmean scaling plus an STE.
- Empirical results show *parity or superiority* over full precision models at far lower latency, memory and energy costs.
- This paradigm shift could reshape everything from data center inference economics to on-device personal assistants.

If you’re building the next generation of LLMs and care about real-world deployment cost, looking beyond post‑training quantization toward native low‑bit training like BitNet b1.58 may be the most promising path forward.
