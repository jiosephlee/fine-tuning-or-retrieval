\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### How does incremental patching differ from BPE tokenization in terms of determinism during generation?
Question:
The paper defines incremental patching as satisfying \(f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i}\). It then claims BPE does not satisfy this property because tokenization can depend on future bytes. Could someone provide a concrete example where a prefix yields different BPE tokenizations depending on its continuation, and contrast that with how BLT decides patch boundaries at generation time without seeing future bytes?
Answer:
The property  

\[
f_{p}(\mathbf{x}_{<i}) \;=\; f_{p}(\mathbf{x})_{<i}
\]

means that once we have seen a prefix \(\mathbf{x}_{<i}\) we can decide, **without looking at any later bytes**, whether the next byte starts a new unit (a *patch* in BLT) or belongs to the current one.  
BPE tokenisation does **not** have this property, because the greedy BPE algorithm decides where a token ends by examining the *future* of the current byte: it merges the longest sub‑string that appears in the learned merge table, and that sub‑string can change when more bytes are appended.

Below is a minimal worked‑out example that illustrates how the same byte prefix can be tokenised differently depending on what follows.

---

### A BPE example

Assume a toy BPE vocabulary that contains the following merges (written in order of priority):

```
e r   →  er
er s →  ers
t h   →  th
the   →  the
```

and the initial symbol set consists of all single bytes (so every character is a token before any merges are applied).

Consider the input string (bytes shown as characters for readability)

```
… er s …
```

#### 1. Prefix “er”

If we only see the first two bytes **“er”**, the greedy BPE algorithm works as follows:

1. Look for the highest‑priority merge that appears in the current sequence.
2. “er” is present, so we merge it → token **“er”**.

Thus the prefix *“er”* is tokenised as `[er]`.

#### 2. Longer continuation “ers”

Now look at the longer string **“ers”**. The algorithm proceeds:

1. The highest‑priority merge still present is “er”, so we first merge “er” → `[er] s`.
2. After this merge, “ers” no longer appears as a contiguous pair, so no further merges apply.

The final tokenisation of *“ers”* is `[er] [s]`.

#### 3. Even longer continuation “the”

Consider a different continuation, *“the”*:

```
… er t h e …
```

Running BPE on the full prefix **“erthe”** gives:

1. The pair “th” is a merge, so we first obtain `… er th e …`.
2. The pair “the” (higher in priority than “th”) now appears, so we merge it → `… er [the] …`.
3. No more merges apply.

Now the prefix *“erthe”* is tokenised as `[er] [the]`.

---

We see that the *same two‑byte prefix “er”* yields three different tokenisations depending on what bytes follow it:

| continuation | BPE tokens for prefix |
|--------------|-----------------------|
| end of string | `[er]`                |
| “…s…”       | `[er] [s]`            |
| “…the…”     | `[er] [the]`          |

Consequently

\[
f_{\text{BPE}}(\mathbf{x}_{<2}) \neq f_{\text{BPE}}(\mathbf{x})_{<2},
\]

so BPE does **not** satisfy incremental patching.

The root cause is that BPE’s merge table encodes a *global* compression scheme; the decision to keep “er” as a single token or to split it depends on whether a longer merge (“the”, “ers”, …) becomes possible later.

---

### How BLT’s incremental patching works

BLT defines a patching function \(f_{p}\) that is *deterministic given only the past*.  
During generation each byte \(x_{i}\) is examined by an entropy estimator (the small byte‑LM described in §3.3). The estimator computes

\[
H(x_i)= -\sum_{b\in\mathcal V} p_e(b\mid \mathbf{x}_{<i})\log p_e(b\mid \mathbf{x}_{<i}),
\]

and compares \(H(x_i)\) (or its change from \(H(x_{i-1})\)) to a fixed threshold. If the entropy exceeds the threshold, BLT declares that a *patch boundary* occurs **right after** \(x_i\); otherwise it continues accumulating bytes into the current patch.

Crucially, this rule uses only \(\mathbf{x}_{<i+1}\) – i.e. it looks at the *next‑byte prediction* given everything seen so far – and never inspects \(\mathbf{x}_{>i}\). The boundary decision is therefore made **incrementally**: once a patch has been closed, its representation is fed to the global latent transformer; later bytes cannot retroactively change where previous boundaries were placed.

Because entropy is a deterministic function of the prefix (the small LM’s parameters are fixed after training), we have

\[
f_{p}(\mathbf{x}_{<i}) = f_{p}(\mathbf{x})_{<i},
\]

exactly satisfying the definition in Eq. (1). No matter how long we later continue the sequence, the already emitted patches remain unchanged.

---

### Contrast

* **BPE**: segmentation depends on future bytes because merges are defined over *any* subsequence that appears later. A prefix can be re‑segmented when more context arrives, breaking incrementality.
* **BLT incremental patching**: segmentation depends only on a locally computed statistic (next‑byte entropy) that is fully determined by past bytes. Once a boundary is placed, it never moves, guaranteeing deterministic generation step‑by‑step.

Thus, while both schemes group raw bytes into larger units, only BLT’s patching meets the formal incremental property required for *online* generation without looking ahead. This distinction underlies BLT’s claim that its patching is deterministic during inference, whereas BPE tokenisation inherently cannot be.
