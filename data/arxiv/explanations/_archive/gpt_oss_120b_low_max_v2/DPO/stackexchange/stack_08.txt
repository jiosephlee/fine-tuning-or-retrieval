\title{Stack Exchange of the Paper: "Direct Preference Optimization: Your Language Model is Secretly a Reward Model"}

### Is DPO compatible with transformer architectures that use tied token embeddings for logits and rewards?
Question:
Many language models share embeddings between token output logits and any additional heads (e.g., a scalar reward head). Since DPO treats the policy logits directly as part of the loss, are there any architectural constraints or modifications needed when using tied embeddings? Does sharing affect the implicit reward definition?
Answer:
**Short answer:**  
Yes, Direct Preference Optimization works perfectly with the usual “tied‑embedding” architecture in which the same weight matrix is used both to turn token IDs into hidden vectors (the input embedding) and to map the final hidden state back to a vocabulary distribution (the output‑logits matrix). No special architectural change is required, and the sharing of embeddings does **not** alter the definition of the implicit reward that DPO learns.

---

### Why tying the embeddings is harmless for DPO  

The DPO objective (Eq. (9) in the paper) is defined only in terms of the **policy probabilities**  

$$
\pi_{\theta}(y\mid x)=\prod_{t}\frac{\exp \bigl(z_{t}(y_t)\bigr)}{\sum_{v}\exp\bigl(z_{t}(v)\bigr)},
$$

where $z_{t}(v)$ are the logits produced by the transformer at generation step $t$.  
All that DPO needs is a differentiable way to compute $\log \pi_{\theta}(y\mid x)$ for any candidate completion $y$; it never looks inside the network that produced those logits.

In a typical decoder‑only transformer we have

* an **input embedding matrix** $E \in \mathbb{R}^{|V|\times d}$ that converts token IDs into vectors,
* a **decoder stack** that processes these vectors,
* an **output projection matrix** $W_{\text{out}} \in \mathbb{R}^{d\times |V|}$ that maps the final hidden state back to a vocabulary logit vector.

When we *tie* embeddings we set $W_{\text{out}} = E^{\top}$. This constraint only reduces the number of free parameters; it does not change the functional mapping from hidden states to logits – it simply forces that mapping to be the transpose of the input embedding.

Since DPO’s loss depends **solely on the logits $z_{t}$** (and on the reference model’s logits, which are computed in exactly the same way), any linear relationship between hidden states and logits—including one that arises from a tied matrix—is fully compatible. The gradient flow from Eq. (10) in the paper  

$$
\nabla_{\theta}\!\mathcal{L}_{\text{DPO}}
 = -\beta\,\mathbb{E}_{(x,y_w,y_l)}\!\Bigl[
    \sigma\bigl(\hat r_{\theta}(x,y_l)-\hat r_{\theta}(x,y_w)\bigr)
    \bigl(\nabla_{\theta}\!\log\pi_{\theta}(y_w|x)-\nabla_{\theta}\!\log\pi_{\theta}(y_l|x)\bigr)
 \Bigr]
$$

is computed exactly as if the output projection were an independent matrix; the only difference is that during back‑propagation the same weight tensor receives updates both from the embedding side and from the output side. In practice this just means that a single shared parameter matrix gets larger gradients, which most deep‑learning frameworks handle automatically.

---

### Does sharing affect the *implicit* reward?

The implicit reward used by DPO is defined (Eq. (8)) as  

$$
\hat r_{\theta}(x,y)=\beta \log \frac{\pi_{\theta}(y|x)}{\pi_{\text{ref}}(y|x)} .
$$

Notice that $\hat r_{\theta}$ depends **only on the ratio of two probabilities**, i.e. on how much more (or less) likely our current policy makes a token sequence compared with the reference policy. The internal parameterisation of those probabilities—whether they arise from tied or untied embeddings—is irrelevant; any two policies that assign identical probabilities will yield identical rewards, regardless of how those probabilities were obtained.

Consequently, tying embeddings does not introduce any bias or scaling to $\hat r_{\theta}$. The only thing that could change is the *capacity* of the model: if tying embeddings severely limits expressivity for a particular task, performance may suffer, but this is a generic modeling concern, not a DPO‑specific issue.

---

### Practical considerations

| Aspect | What you need to do |
|--------|--------------------|
| **Model definition** | Declare a single embedding matrix and reuse its transpose for the output head (exactly as most libraries do). |
| **Reference model** | The reference policy $\pi_{\text{ref}}$ should be instantiated with exactly the same weight‑tying configuration; otherwise probability ratios will be inconsistent. |
| **Training loop** | No extra code beyond what DPO already requires (compute $\log \pi_\theta(y)$, compute the weighted cross‑entropy loss, back‑propagate). |
| **Memory / speed** | Tied embeddings actually *save* memory because you store one matrix instead of two; training speed is unchanged. |

If you happen to start from a checkpoint that was trained with *untied* embeddings, you can still apply DPO: simply keep those two matrices separate during fine‑tuning—DPO will still work. However, if you later wish to re‑tie them (e.g., for inference optimization), you must first ensure that both matrices have converged to roughly transposes of each other; otherwise re‑tying would alter the logits and thus change the policy.

---

### How this fits into the broader picture

The compatibility of DPO with tied embeddings mirrors what we already know about conventional supervised fine‑tuning: any loss that depends on token‑level log‑probabilities (cross‑entropy, KL‑divergence, etc.) works unchanged under weight tying because they are functions of *the distribution* over tokens, not of hidden representations themselves. DPO can be viewed as a *re‑parameterized* version of RLHF where the “reward” lives inside that distribution ratio; all standard tricks used for language‑model training—gradient checkpointing, mixed precision, LoRA adapters—carry over unchanged.

---

### TL;DR

* DPO requires only accurate token probabilities from both current and reference policies.
* Sharing (“tying”) input and output embeddings changes nothing about those probabilities; it merely reduces parameters.
* The implicit reward $\hat r_\theta(x,y)$ depends on probability ratios, so it is invariant to whether embeddings are tied.
* No architectural modifications are needed; just make sure both policies use the same tying scheme.
