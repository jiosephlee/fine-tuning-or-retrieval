\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What are the exact layout constraints for FP8 WGMMA operands and how does the in‑kernel transpose satisfy them?
Question:
Section 4.2 says FP8 WGMMA only accepts k‑major operand layout, while Q, K, V are stored contiguously in the head‑dimension. The authors propose an in‑kernel transpose using LDSM/STSM instructions. I am unclear on:
1) What does "k‑major" mean for a tile of V in memory?
2) How does loading a tile with LDSM/STSM change its layout from mn‑major to k‑major?
3) Why is an additional register permutation needed after the first GEMM accumulator before the second GEMM? A step‑by‑step description of these transformations would help.
Answer:
**Answer**

In the FP8 version of FlashAttention‑3 the two GEMM calls that constitute one attention block are executed with the **WGMMA** instruction.  WGMMA can only consume *k‑major* tiles when the operands are FP8; the accumulator (which is kept in FP32) follows a different layout that is “mn‑major”.  Because the value matrix **V** is stored in global memory with the head dimension (the *d*‑axis) contiguous, we have to reshape each tile of **V** so that the *sequence‑length* axis becomes the fast‑moving dimension before it reaches the Tensor Core.  The paper solves this with an **in‑kernel transpose** that uses the warp‑wide `ldmatrix` / `stmatrix` (LDSM/STSM) instructions.  Below I walk through what “k‑major” means, how LDSM/STSM achieve the transpose, and why a register permutation is still required before the second GEMM.

---

### 1.  What “k‑major” means for a V‑tile

Consider a tile of **V** that participates in the second GEMM  

\[
\mathbf{O}_i \;\;+=\;\; \tilde{\mathbf P}_i^{(j)} \,\mathbf{V}_j^{\top},
\qquad 
\tilde{\mathbf P}_i^{(j)}\in\mathbb{R}^{B_r\times B_c},\;
\mathbf{V}_j\in\mathbb{R}^{B_c\times d}.
\]

The GEMM is written as $A\times B^{\top}$ with  
$A=\tilde{\mathbf P}_i^{(j)}$ (size $M\times K$) and  
$B=\mathbf{V}_j$ (size $N\times K$, where $K=d$).  
For WGMMA the *inner* dimension of each operand – the **K** axis – must be contiguous in memory.  In other words, consecutive elements of a row (or column, depending on whether we are looking at $A$ or $B$) must belong to the same K‑index.  

When we speak of a *k‑major* layout we mean:

* The **fastest‑changing index** in memory is the K dimension.
* Strides along M (or N) are multiples of K, i.e. a whole K‑vector is stored contiguously before moving to the next M (or N) index.

For **V**, whose natural storage order is *(sequence, head)* → *(N, d)*, the fast index is *d*.  That layout is **mn‑major** (contiguous in M = sequence length).  To satisfy k‑major we need to store each tile as *(head, sequence)* → *(d, B_c)* so that successive bytes step through the K (head) dimension.

---

### 2.  From mn‑major to k‑major with LDSM/STSM

A warp consists of 32 threads.  The `ldmatrix` (`LDSM`) instruction can load a **128‑byte** block from shared memory into registers and simultaneously *transpose* it if we request the “transpose” variant (`ldmatrix.trans`).  The basic primitive works on an $8\times8$ matrix of **16‑bit** elements, but we can pack two FP8 values into one 16‑bit lane and therefore treat an $8\times8$ block of FP8 as four packed lanes.

The sequence of operations for one tile of **V** is:

1. **Load** a $B_c\times d_{\text{tile}}$ fragment from shared memory with `ldmatrix`.  
   The fragment is read in **mn‑major** order because that is how it was written by TMA.  
2. **Apply the transpose variant** (`ldmatrix.trans`).  This swaps row and column indices inside each 128‑byte chunk, turning an $8\times8$ block that was laid out as  
   \[
   \begin{bmatrix}
   v_{0,0}&v_{0,1}&\dots &v_{0,7}\\
   v_{1,0}&v_{1,1}&\dots &v_{1,7}\\
   \vdots & & &
   \end{bmatrix}
   \]
   into  
   \[
   \begin{bmatrix}
   v_{0,0}&v_{1,0}&\dots &v_{7,0}\\
   v_{0,1}&v_{1,1}&\dots &v_{7,1}\\
   \vdots & &
   \end{bmatrix}.
   \]
   Because each FP8 value occupies half a 16‑bit lane, the transpose operates on pairs of values but preserves their relative order inside each pair.
3. **Store** the transposed fragment back to shared memory with `stmatrix`. The destination location is chosen so that afterwards the tile resides in *k‑major* order: consecutive bytes now march along the head dimension.

Effectively we have performed an **in‑kernel tilewise transpose** without any extra global memory traffic: data stays inside SMEM while being reshaped by the warp‐wide matrix load/store units.  Since each warp handles a distinct sub‑tile, no inter‑warp synchronization beyond the usual barrier on SMEM occupancy is needed.

---

### 3.  Why a register permutation follows the first GEMM

After computing

```
S_cur = Q_i * K_j^T          // first WGMMA
```

the accumulator registers contain a fragment of the **softmax numerator** $\tilde{\mathbf P}_i^{(j)}$.  In FP8 mode this accumulator lives in FP32 registers and follows the *mn‑major* layout described in Fig. 5 of the paper: within each thread’s register bank the eight values are ordered as

```
d0 d1 d2 d3 d4 d5 d6 d7
```

where *d* indexes rows of $\tilde{\mathbf P}$.  The second GEMM needs these values multiplied by a **V** tile that has just been reshaped to k‑major order (fast head index).  The Tensor Core expects its *A* operand (the left matrix) to be laid out as

```
d0 d1 d4 d5 d2 d3 d6 d7
```

i.e. columns are permuted in groups of four (see Fig. 6).  This mismatch stems from two facts:

1. The FP8 WGMMA’s accumulator layout differs from its FP16 counterpart because FP8 accumulators are kept in FP32 while operands are stored as packed FP8.
2. The in‑kernel transpose produces exactly the column permutation required for **V**, but it does **not** change how $\tilde{\mathbf P}$ is stored after the first GEMM.

Therefore we insert a small register‐shuffle step after `S_cur` has been reduced to `tilde_P_cur`.  Using byte–permute instructions (`prmt.b64`, `prmt.b32`) we reorder each thread’s eight FP32 values into the pattern demanded by WGMMA’s second operand.  This costs only a handful of ALU cycles and does not increase register pressure appreciably because the fragment already resides in registers.

Once `tilde_P_cur` has been permuted, its layout matches exactly what `V_next` (the transposed tile loaded via LDSM/STSM) expects: both now present their columns contiguously across threads.  Consequently a second WGMMA call

```
O_i += tilde_P_cur * V_next^T
```

can be issued immediately without any cross‑thread shuffles or further memory copies.

---

### Putting it all together – step‑by‑step

| Step | Action | Layout effect |
|------|--------|----------------|
| 0 | TMA loads `Q_i`, `K_j`, `V_j` from global memory into SMEM | All three are mn‑major (`seq × head`) |
| 1 | Producer warp issues `ldmatrix.trans` on `V_j` → registers → `stmatrix` back to SMEM | `V_j` becomes k‑major (`head × seq`) inside SMEM |
| 2 | Consumer warp executes first WGMMA: `S_cur = Q_i × K_j^T` | Accumulator (`tilde_P_cur`) lives in registers with mn‑major ordering |
| 3 | Register permutation (`prmt`) rearranges `tilde_P_cur` to k‑major ordering | Now compatible with next operand layout |
| 4 | Consumer warp launches second WGMMA: `O_i += tilde_P_cur × V_j^T` | Both operands are k‑major → Tensor Core can consume them |
| 5 | Softmax reduction uses `S_cur` → updates running max/scale; results are stored back in FP32 registers | No layout change needed |
| 6 | Loop repeats: next `K_{j+1}` and transposed `V_{j}` are ready while previous softmax runs asynchronously (ping–pong), thanks to warp specialization |

In short:

* **k‑major** means “contiguous in the inner dimension K”. For a V tile this requires storing values with head index fastest.
* The warp‐wide LDSM/STSM pair performs a tiled transpose inside shared memory; this flips the mn→k major order without leaving SMEM.
* Because only one operand (**V**) is transposed automatically, we must manually permute the accumulator produced by the first GEMM so that its column order matches the transposed V before feeding it into the second GEMM.

With these three transformations—tilewise in‑kernel transpose, register permutation, and asynchronous pipelining—the FP8 version of FlashAttention‑3 satisfies all WGMMA layout constraints and can keep both Tensor Cores fully occupied while softmax runs on separate hardware units.
