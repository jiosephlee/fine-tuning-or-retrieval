\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### How is the 2‑stage GEMM‑softmax pipeline implemented without violating data dependencies?
Question:
Algorithm 2 shows overlapping of two WGMMA calls with softmax of the next block. The pseudocode mentions "commit but do not wait" for the first GEMM while softmax for the previous block proceeds. In practice, how are CUDA barriers or warp synchronizations used to enforce that the softmax uses only completed S_cur and that O_i accumulation uses only ready \tilde{P}_cur? Are there hidden dependencies that could cause race conditions on registers or shared memory?
Answer:
In the 2‑stage pipeline the only thing that can *actually* go wrong is that a soft‑max step starts before the score tile **Scur** produced by the previous WGMMA has been written back to registers, or that the “right‑side’’ GEMM (the multiplication of $\,\widetilde P_{\text{cur}}\, $ with the value tile) uses a $\,\widetilde P\,$ that has not yet been materialised.  
The paper solves both problems with two complementary mechanisms:

1. **WGMMA is already asynchronous** – a WGMMA instruction only issues a Tensor‑Core micro‑kernel; the issuing warp does not stall until the result is needed later in the program.  The hardware therefore provides a *completion flag* that can be queried with a `bar.sync`‑style barrier (or, in PTX, the `wgmma.wait` primitive).  The compiler (or the hand‑written PTX wrapper) inserts a `bar.sync` after each WGMMA that is *required* for subsequent non‑matmul work.  In Algorithm 3 line 9 (`Compute S_next … Commit but do not wait`) the programmer deliberately omits this wait; the next softmax step (line 13) contains an explicit `wait` for that same WGMMA, which is exactly the “commit‑but‑don’t‑wait → wait later’’ pattern described in the text.

2. **Producer–consumer warp specialization and a circular SMEM buffer** – the CTA is split into a *producer* warpgroup (which only issues TMAs) and a *consumer* warpgroup (which only issues WGMMAs and the soft‑max arithmetic).  Because each warpgroup has its own register file, there is no risk of two warps writing to the same register at the same time.  The only shared state is the SMEM buffer that holds the freshly loaded $\,K_j\,$ and $\,V_j\,$ tiles.  The buffer is managed by a lightweight barrier object (`pipeline object` in Alg. 1).  When a producer finishes loading a tile it calls `commit` which simply writes a flag into a per‑stage slot of this object; the consumer checks that flag with `wait`.  The “release’’ operation at the end of an iteration clears the flag so that the next producer iteration can reuse that SMEM slot.

Putting these two pieces together, the execution order of one iteration looks like this (using the notation of Alg. 3):

*   **Step A** – issue `WGMMA(Q_i, K_j)` for tile *j*.  
    The instruction returns immediately; a *completion token* `tok_Snext` is stored locally.
*   **Step B** – issue `WGMMA( \tilde P_{\text{cur}}, V_{j-1})`.  
    Its token `tok_O` is also stored but not waited on yet.
*   **Step C** – `bar.sync` on `tok_Snext`; now we are sure that `S_next` is resident in registers, so we can safely compute  
    $$  
        m_i,\;\tilde P_{\text{next}},\;\ell_i  
    $$  
    (the soft‑max arithmetic).  This step does not touch any shared memory, only registers.
*   **Step D** – `bar.sync` on `tok_O`; after it finishes we rescale the accumulated output $\mathbf O_i$ and release the SMEM slots for $K_j$ and $V_{j-1}$.

Because each token is waited on **exactly once**, there is no possibility for a race: a later iteration cannot start its soft‑max until its preceding score tile has finished, and a later GEMM cannot start until its preceding value tile has been loaded (the consumer explicitly waits for that load with another barrier).  All other operations—exponentials, reductions, scaling—run on pure registers, so there are no shared‑memory hazards.

In practice these barriers compile down to a handful of SASS instructions:

```asm
// after WGMMA
        WMMA_WAIT     %p0, %tid.x           // set predicate p0 when result ready
// softmax code
        @%p0   ...                       // guarded by predicate -> equivalent to bar.sync
```

The compiler also emits `bar.sync` instructions when it sees dependent registers across warpgroups; this is why the authors note that they verified “the SASS code shows overlapped execution as expected” (§ 3.2).

Finally, note that register pressure is handled by allocating an extra buffer for `S_next` (the “next’’ score tile) only for the consumer warpgroup; this buffer lives entirely in registers, so no other warps can overwrite it inadvertently.  The circular SMEM buffer guarantees that producer warps never write into a slot that a consumer still needs because each slot’s lifecycle is guarded by those same barriers.

Thus, hidden dependencies are eliminated by:

* explicit per‑WGMMA completion tokens,
* barrier synchronisation between producer/consumer warpgroups,
* register‑only temporaries for softmax intermediates,
* and strict ordering of SMEM slot release.

These mechanisms together enforce that every softmax sees a fully computed $\mathbf S_{\text{cur}}$ and every right‑side GEMM sees a ready $\tilde{P}_{\text{cur}}$, preventing any race condition while still allowing full overlap of GEMM and softmax work.
