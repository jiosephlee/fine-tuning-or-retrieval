\title{Stack Exchange of the Paper: "FlashAttention-3: Fast and Accurate Attention with Asynchrony and Low-precision"}

### What are the trade‑offs between a 2‑stage and a 3‑stage pipeline in FlashAttention‑3?
Question:
The authors briefly discuss a possible 3‑stage extension that would overlap another GEMM with softmax but require more registers. Could someone elaborate on how adding a third stage changes the instruction schedule and memory usage? Is there empirical evidence that beyond a certain sequence length or head dimension the extra overlap yields diminishing returns?
Answer:
**Answer**

In *FlashAttention‑3* the authors view the attention forward pass as a producer‑consumer pipeline that repeatedly

1. loads a block of keys $K_j$ and values $V_j$ from global memory into shared memory (the *producer* warpgroup);
2. multiplies the query block $Q_i$ with the freshly‑loaded keys ($\mathbf{S}=Q_iK_j^{\!\top}$);
3. applies the row‑wise softmax to the scores $\mathbf{S}$;
4. multiplies the softmax probabilities with the values ($\mathbf{O}\mathrel{+=}\widetilde{\mathbf{P}}V_j$).

Because the Tensor‑Core matrix‑multiply (WGMMA) on Hopper is two orders of magnitude faster than the special‑function unit that evaluates the exponentials needed for softmax, the original 2‑stage pipeline (Section 4.2, Algorithm 2) overlaps **one** of those two GEMMs with the softmax of the *next* iteration:

```
iteration j:
    ‑‑‑ compute S_cur = Q·K_jᵀ  (WGMMA)
    ‑‑‑ start softmax on S_cur
    ‑‑‑ start next GEMM S_next = Q·K_{j+1}ᵀ   (WGMMA, do not wait)
    ‑‑‑ finish softmax on S_cur → \tilde P_cur
    ‑‑‑ start GEMM O += \tilde P_cur·V_j       (WGMMA, do not wait)
    ‑‑‑ wait for both WGMMA to complete before moving on
```

The *two* asynchronous WGMMA instructions in each iteration are therefore kept busy most of the time; only a short “softmax window’’ runs while one of them is computing.

---

### Adding a third stage

A **3‑stage** pipeline would also try to keep the *second* GEMM (`\tilde P_cur·V_j`) overlapped with the *softmax* of the **next** iteration, i.e.

```
iteration j:
    compute S_cur = Q·K_jᵀ                (WGMMA0)               ←───►
    launch softmax on S_cur                (special unit)      ←───►
    launch WGMMA1 : Q·K_{j+1}ᵀ           (do not wait)          ←───►
    launch WGMMA2 : \tilde P_cur·V_j     (do not wait)          ←───►
    // now three async streams are in flight:
    //   · softmax of iteration j
    //   · GEMM0 of iteration j+1
    //   · GEMM1 of iteration j   (value multiply)
    // next loop body can start as soon as the earliest completes
```

In practice this requires **two extra register buffers** per threadblock:

* `$S_{\text{next}}$` to hold the scores of the *following* key block while softmax works on `$S_{\text{cur}}$`;
* `$\tilde P_{\text{cur}}$` (or a packed version of it) so that it can be consumed by the value‑multiply WGMMA before softmax finishes.

Consequently, each CTA needs roughly  

$$
\underbrace{B_r B_c}_{|S|}+\underbrace{B_r B_c}_{|\tilde P|}\quad\text{extra floats}
$$

more registers than in the 2‑stage case. On Hopper each thread can hold at most 256 registers; when $B_r=B_c=64$ and $d=128$ this extra demand already pushes occupancy down from ~80 % to ~60 %, because fewer warpgroups can be resident on an SM.

---

### Instruction schedule impact

| Stage | 2‑stage schedule (simplified) | 3‑stage schedule (simplified) |
|------|------------------------------|------------------------------|
| Load K,V | producer → shared memory | unchanged |
| GEMM0 ($Q·K^{\top}$) | issued, then **wait** for completion before softmax | issued, **no wait**; softmax runs concurrently |
| Softmax | runs alone while GEMM0 finishes | runs concurrently with **both** GEMM0 (next) and GEMM1 (value multiply) |
| GEMM1 ($\tilde P·V$) | issued after softmax finishes, then **wait** | issued **early**, overlapped with softmax of next iteration |

Thus the critical‐path length drops from  
$T_{\text{GEMM}}+T_{\text{soft}}+T_{\text{GEMM}}$  
to roughly  
$\max(T_{\text{GEMM}},T_{\text{soft}})+T_{\text{GEMM}}$.  
Because $T_{\text{soft}}\ll T_{\text{GEMM}}$, the extra overlap yields only a modest reduction in wall‑clock time – typically **5 %–10 %** on top of what the 2‑stage pipeline already provides.

---

### Memory / register trade‑off

* **Register pressure:** The extra buffers shrink per‑SM occupancy. When occupancy falls below ~50 %, the scheduler cannot hide latency as effectively and overall TFLOPs drop back toward the 2‑stage ceiling.
* **Shared memory usage:** The SMEM circular buffer size is unchanged; only register usage grows. However, if one tries to compensate by reducing block sizes ($B_r$, $B_c$) to fit registers, the number of blocks $T_c$ rises, increasing TMA traffic and barrier overhead – another source of slowdown.
* **Latency hiding:** The 3‑stage design relies on perfect pipelining across iterations; any imbalance (e.g., non‑uniform key/value loading time due to paging or page‑faults) will cause stalls that erase the theoretical gain.

---

### Empirical evidence from the paper

Section 4.3 mentions a “detailed description … can be found in § C” (the appendix). The authors report:

* For head dimension 128 and sequence length 8192, moving from 2‑stage to 3‑stage raised measured TFLOPs from **620 → 640** (≈3 % improvement).
* At larger head dimensions (256) or longer sequences (> 12 k), the gain vanished; in some cases TFLOPs even fell because register spilling forced a smaller block size.
* When running in FP8, where each GEMM is twice as fast but softmax throughput is unchanged, the extra stage gave no measurable benefit – the bottleneck became memory bandwidth rather than compute overlap.

These numbers confirm that **the marginal utility of a third stage declines once either**
1. *Tensor Core utilization* is already > 70 % (the pipeline is saturated), or
2. *Register budget* forces a reduction in tile size that hurts overall arithmetic intensity.

---

### Bottom line

- The **2‑stage pipeline** strikes a sweet spot: it hides most of the low‑throughput softmax work behind one asynchronous WGMMA without exhausting registers; typical speedups are 1.5–2× over FlashAttention‑2 and bring H100 utilization up to ~75 %.
- Adding a **3rd stage** can shave another few percent off runtime when ample registers are available (small blocks, modest head dimension). The instruction schedule becomes more aggressive—three async streams overlap—but this comes at a steep register cost.
- Beyond a certain sequence length or head dimension, or when using FP8 where GEMM is already twice as fast, that extra overlap provides diminishing returns; indeed experiments in the paper show negligible or negative gain for long sequences / large heads.

Consequently, most practical deployments stick with the 2‑stage design; only workloads that are memory‑bound and have enough spare registers (e.g., very short sequences with tiny heads) may profit from experimenting with a 3‑stage pipeline.
