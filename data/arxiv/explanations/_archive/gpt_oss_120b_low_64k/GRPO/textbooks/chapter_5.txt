\title{A Textbook about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

Chapter 5: # Training DeepSeekMath‑Base 7B

In this chapter we describe in depth how the DeepSeekMath‑Base 7B model was constructed, the design choices that informed its training pipeline, and the empirical capabilities it exhibits after pre‑training.  The discussion follows directly from the experimental methodology and results reported in the DeepSeekMath paper, allowing a newcomer to understand why each component matters for mathematical reasoning and how it contributes to the overall performance of the model.

---

## Data Mixture Proportions

DeepSeekMath‑Base 7B is built on top of the code‑oriented foundation model **DeepSeek‑Coder‑Base‑v1.5 7B**.  After initializing from this checkpoint, the model undergoes a massive continual pre‑training phase consuming **500 billion tokens**.  The token stream is deliberately composed of several distinct sources so that the model simultaneously learns mathematical concepts, programming idioms, and general natural‑language proficiency:

| Source | Approximate Share of Tokens |
|--------|-----------------------------|
| DeepSeekMath Corpus (web pages filtered for mathematical content) | **56 %** |
| AlgebraicStack (large collection of mathematically oriented source code) | **4 %** |
| arXiv papers (scientific articles) | **10 %** |
| GitHub code (general software repositories) | **20 %** |
| Common‑Crawl natural‑language text (English and Chinese) | **10 %** |

The dominant portion—more than half of all tokens—comes from the **DeepSeekMath Corpus**, a 120 billion‑token dataset harvested from Common Crawl through an iterative fastText‐based classifier.  This corpus contains multilingual mathematical exposition (primarily English and Chinese), problem statements, derivations, and informal proofs, providing rich contextual signals for quantitative reasoning.

The inclusion of **AlgebraicStack** and **GitHub** code ensures that the model retains strong programming knowledge, which later enables effective tool‐integrated reasoning (e.g., writing Python programs to solve equations).  Although arXiv papers make up a non‑trivial 10 % of the mix, ablation experiments in the paper showed that they do not noticeably improve downstream math performance; nevertheless they are retained to keep a broad scientific language exposure.

Finally, a modest share of generic natural language from Common Crawl balances the representation of everyday discourse in both English and Chinese, preventing over‑specialization on math web pages and supporting general language understanding tasks such as MMLU.

---

## “Two‑Stage” vs. “One‑Stage” Training Insights

A central question explored by the authors is whether **code pre‑training should precede math pre‑training (“two‑stage”) or be interleaved with it (“one‑stage”)**.  Two families of experiments are reported:

1. **Two‑Stage Regime**  
   - *Stage 1*: Train on a large corpus of code tokens (≈ 400 B tokens).  
   - *Stage 2*: Continue training on pure math tokens (≈ 150 B tokens).  

   A control variant replaces the first stage with generic natural language rather than code.

2. **One‑Stage Regime**  
   - *Mixed*: Simultaneously expose the model to both code and math tokens (400 B code + 150 B math) without a clear separation between stages.  

### Findings

- **Program‑aided reasoning**: Code pre‑training dramatically improves the ability to generate correct Python programs for GSM8K and MATH when evaluated with program‑of‑thought prompting.  The two‑stage approach yields the strongest gains because the initial code phase builds robust syntactic and execution semantics that are then refined by math data.
- **Catastrophic forgetting**: When only two stages are used, pure math fine‑tuning can degrade coding performance because the model “forgets” some of what it learned during the first stage.  Mixing code and math tokens in a single stage mitigates this forgetting, preserving coding abilities while still delivering solid mathematical performance.
- **Reasoning without tools**: Even without tool use, code pre‑training provides modest improvements to chain‑of‑thought reasoning; however, for a small 7 B model the one‑stage mixed regime can slightly underperform compared with two distinct stages because the model’s capacity is insufficient to fully assimilate both domains simultaneously.

Overall, the authors adopt a hybrid approach for DeepSeekMath‑Base: they start from a code‐trained checkpoint (DeepSeek‑Coder) and then perform an extended mixed training run where mathematics dominates but coding signals remain present throughout.

## Optimizer Settings, Learning‐Rate Schedule, and Batch Size

Training such a large token budget requires careful hyperparameter choices to ensure stability while maximizing learning efficiency.  All experiments—both for evaluating corpus quality and for training DeepSeekMath‐Base—use essentially the same configuration, differing only in learning‐rate magnitude and batch size due to scale.

- **Optimizer**: AdamW with momentum parameters \(\beta_{1}=0.9\) and \(\beta_{2}=0.95\); weight decay set to \(0.1\).  This combination is standard for large language models because it balances fast convergence with regularization against overfitting on any single data source.
- **Learning‐Rate Schedule**: A multi‑step decay schedule is employed:
  - Warmup for \(2{,}000\) steps during which the learning rate linearly rises to its peak.
  - After warmup, learning rate stays near peak until \(80\%\) of total training steps have passed; then it decays to \(31.6\%\) of its peak value.
  - In the final \(10\%\) of training, it further decays to \(10\%\) of the peak.
- **Peak Learning Rate**: For DeepSeekMath‑Base training, the maximum learning rate is set to \(4.2 \times 10^{-4}\).  This is slightly lower than the \(5.3 \times 10^{-4}\) used in smaller preliminary experiments to avoid destabilizing updates when mixing many high‑frequency symbols from code and mathematics.
- **Batch Size & Context Length**: A massive batch size of **10 million tokens per update** is used, with each example truncated or padded to a context length of \(4{,}096\) tokens.  The large batch improves gradient estimation across diverse data domains while keeping GPU memory usage tractable via gradient accumulation techniques provided by the HAI‐LLM training framework.

These settings collectively allow training at roughly **5–6 tokens per parameter per second**, making it feasible to process half a trillion tokens within several weeks on modern GPU clusters.

## Quantitative Reasoning Results

After completing pre‑training, DeepSeekMath‑Base 7B is evaluated on several high‐profile quantitative reasoning benchmarks using few–shot chain‑of‑thought prompting.  The numbers reported in the paper illustrate how a modestly sized open model can rival far larger proprietary systems.

| Benchmark | Task Type | Accuracy (DeepSeekMath‑Base 7B) |
|-----------|-----------|--------------------------------|
| GSM8K (grade school word problems) | Free response | **64.2 %** |
| MATH (competition level) | Free response | **36.2 %** |
| CMATH (Chinese grade school) | Free response | Competitive lead over prior open models |

Key observations:

- On **MATH**, DeepSeekMath‑Base surpasses all open-source base models by more than ten percentage points and even exceeds Minerva 540B—a closed model more than seventy times larger in parameter count.
- Performance on GSM8K indicates that chain‐of‐thought reasoning benefits strongly from exposure to high‐quality web mathematics text; scores approach those of specialized instruction–tuned variants despite using only base pre‑training.
- The multilingual nature of the corpus yields noticeable improvements on Chinese benchmarks (CMATH), confirming that inclusion of non–English math webpages reduces language bias.

These results underscore that *data quality* and *domain relevance* can compensate for raw parameter scale when building mathematical reasoning abilities.

## Program‑of‑Thought Evaluation with Python Tools

Beyond pure textual reasoning, many modern benchmarks assess whether LLMs can generate executable programs that solve problems—a paradigm known as **Program‑of‑Thought (PoT)** or **Program Aided Language Models (PAL)**.

The authors evaluate DeepSeekMath‑Base on GSM8K and MATH using few–shot PoT prompts that ask the model to write a short Python snippet employing standard libraries such as `math` or `sympy`.  After generation, each program is executed; its output is compared against the ground truth answer.

Results show:

- DeepSeekMath‑Base outperforms Llama 2–based baselines like Llemma 34B on both datasets.
- The advantage appears most pronounced when problems involve intricate algebraic manipulation or combinatorial counting—tasks where symbolic libraries excel.
- The underlying reason is twofold: (1) prior code training feeds accurate syntax and API usage patterns; (2) extensive math text exposure teaches appropriate algorithmic strategies that translate naturally into short programs.

Thus PoT evaluation demonstrates that DeepSeekMath not only reasons abstractly but also *operationalizes* its knowledge via executable code.

## Formal Theorem Proving (miniF2F + Isabelle)

Formal proof automation tests whether a model can bridge informal mathematical statements to machine-checkable formal proofs—a considerably stricter requirement than free‐form answer generation.

The evaluation pipeline follows prior work:

1. For each miniF2F problem (an informal Olympiad‐level statement), a few shot prompt asks DeepSeekMath‑Base to produce a *proof sketch* in natural language plus an Isabelle proof skeleton.
2. The generated sketch is fed into Isabelle’s `Sledgehammer` tool, which attempts to fill missing details automatically.
3. Success is measured by whether Isabelle verifies a complete proof after this automation step.

DeepSeekMath‑Base achieves strong few–shot performance relative to competing open models (“the prior state-of-the-art Llemma 34B”), indicating:

- A solid grasp of formal mathematical vocabulary thanks to extensive web data.
- Ability to produce syntactically correct Isabelle commands—the product of both math text exposure and prior coding proficiency.
- Transferability: even though no explicit formal proof data were used during pre-training, exposure to LaTeX fragments on web pages appears sufficient for basic proof construction capability.

This experiment highlights that large-scale math web mining can lay groundwork for more rigorous symbolic reasoning tasks.

## General Language Understanding, Reasoning, and Coding

Mathematical pre-training should not come at the expense of broader linguistic competence.  The authors therefore benchmark DeepSeekMath‑Base across three families of tasks:

### Natural Language Understanding – MMLU
MMLU (“Massive Multitask Language Understanding”) comprises 57 multiple–choice subjects spanning STEM, humanities, social sciences, etc.  
DeepSeekMath Base exhibits sizable gains over its predecessor DeepSeek-Coder on STEM categories (e.g., MMLU-STEM), confirming that mathematical exposure improves factual recall and conceptual comprehension beyond pure arithmetic.

### Multi-Step Reasoning – BBH
BIG-Bench Hard includes difficult puzzles requiring logical chaining across many steps (e.g., “Logical Deduction”, “Hyperbaton”).  
DeepSeekMath Base beats Mistral 7B substantially; this uplift suggests that dense structured reasoning patterns learned from mathematics transfer to generic logical tasks.

### Coding – HumanEval & MBPP
HumanEval asks models to synthesize correct Python functions given docstrings; MBPP presents short programming problems with unit tests.  
Because DeepSeekMath Base’s training mixture retained > 20 % code tokens (GitHub + AlgebraicStack), its performance on these benchmarks matches that of its predecessor despite additional math focus—demonstrating *no catastrophic loss* in coding ability.

Collectively these evaluations support one central claim made in the paper: *math pre-training enhances general reasoning while preserving—or even slightly improving—coding skills*.

## Summary

Training DeepSeekMath‑Base 7B illustrates a disciplined approach toward building mathematically capable language models:

1. **Data composition** places mathematics at the core while preserving substantial programming context and multilingual natural language exposure.
2. Empirical studies differentiate between two-stage versus one-stage curricula; they reveal that starting from strong code knowledge accelerates downstream quantitative reasoning while mixed training avoids catastrophic forgetting.
3. Optimizer choices—AdamW with carefully tuned decay schedules—and very large batch sizes ensure stable learning across heterogeneous data sources.
4. After half a trillion token updates, DeepSeekMath Base attains competitive scores on GSM8K, MATH, CMATH; excels at program-of-thought tasks; shows promising formal proof generation; and retains strong performance on general language understanding (MMLU), multi-step reasoning (BBH), and coding benchmarks (HumanEval/MBPP).

These results validate the authors’ central thesis: *high-quality web mathematics data combined with efficient training strategies can yield state-of-the-art reasoning abilities even in modestly sized open-source models*.
