\title{Blogs about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

# Teaching LLMs to Think Like Mathematicians: Chain‑of‑Thought, Program‑of‑Thought, and Tool‑Integrated Reasoning  

Large language models (LLMs) have gotten remarkably good at answering factual questions, but solving a math problem is a very different beast.  A good solution usually requires **multiple reasoning steps**, sometimes **symbolic manipulation**, and often the assistance of a **computer algebra system** or a short Python script.  The DeepSeekMath team tackled this by training an instruction‑tuned model—**DeepSeekMath‑Instruct 7B**—with three complementary prompting styles:

1. **Plain Chain‑of‑Thought (CoT)** – step‑by‑step natural‑language reasoning.  
2. **Program‑of‑Thought (PoT)** – writing and executing Python code to do the heavy lifting.  
3. **Tool‑Integrated Reasoning** – mixing textual reasoning with calls to external tools (e.g., a calculator or symbolic library) inside the same prompt.

Below we unpack each paradigm, show how it is represented in the training data, and explain why the combination gives DeepSeekMath its strong performance on benchmarks such as GSM8K and the competition‑level MATH dataset.

---

## 1. Chain‑of‑Thought (CoT): “Let Me Think Out Loud”

### What it looks like  
A CoT prompt asks the model to *explain every intermediate logical step* before presenting the final answer.  A typical example from the training set:

```
Q: A rectangle has width 5 cm and length 12 cm. What is its area?
A: To find the area of a rectangle we multiply width by length.
   Area = width × length
   Substituting the given values: Area = 5 × 12
   Multiplying gives 60.
   Therefore, the area is 60 cm².
```

### Why CoT matters  
- **Explicit reasoning trace**: The model learns to generate a logical skeleton that can be inspected or corrected.
- **Few‑shot transfer**: Even when presented with a new problem type, the model can reuse the “multiply width and length” pattern it has seen many times.
- **Benchmark boost**: On GSM8K, DeepSeekMath‑Instruct reaches 88 % accuracy with plain CoT; on MATH (a much harder competition benchmark) it climbs above 50 %, surpassing all other open‑source 7B models.

### Training details  
The authors curated ~776 K examples that pair a problem with a CoT solution, mixing English datasets (GSM8K, MATH, MathInstruct, Lila-OOD) and Chinese K‑12 problems.  The data were tokenized up to a 4 K context length and used for supervised fine‑tuning (SFT) for only 500 steps—enough for the model to internalize the “think step by step” pattern without overfitting.

---

## 2. Program‑of‑Thought (PoT): “Let Me Write a Little Code”

### What it looks like  
PoT replaces natural language calculations with short Python snippets that are executed during evaluation. A PoT example:

```
Q: Compute the sum of the first 100 positive integers.
A:
```python
def triangular_number(n):
    return n * (n + 1) // 2

result = triangular_number(100)
print(result)
```
The program prints **5050**, so the answer is 5050.
```

### Why PoT matters  
- **Exact arithmetic**: Python’s `int` type handles arbitrarily large numbers without rounding errors, which is crucial for many GSM8K and MATH problems.
- **Symbolic libraries**: By allowing imports such as `sympy`, the model can perform differentiation, solve equations, or simplify expressions—tasks that are error‑prone when done purely in text.
- **Higher ceiling on hard problems**: In program-aided evaluation (i.e., running the code), DeepSeekMath‑Base already outperforms prior state-of-the-art open models like Llemma 34B. After instruction tuning, the PoT capability stays strong.

### Training details  
The PoT portion of the dataset contains both **program-only** solutions (just code) and **mixed** solutions where a textual explanation surrounds the code block. The same 776 K SFT examples include about one third PoT entries in each language. During fine‑tuning, prompts are truncated at a code token boundary to avoid cutting off important syntax.

---

## 3. Tool‑Integrated Reasoning: “Let Me Call a Calculator”

### What it looks like  
Tool integration goes beyond raw code; it treats an external utility as a *first-class* part of the dialogue. A typical training instance might look like:

```
Q: What is sin(π/6)?
A: I will use Python's math library.
>>> import math
>>> answer = math.sin(math.pi/6)
>>> print(answer)
0.5
So sin(π/6) = 0.5.
```

Or in a more abstract form:

```
Q: Solve x^2 - 5x + 6 = 0.
A: Use SymPy to factor the polynomial.

```python
import sympy as sp
x = sp.symbols('x')
poly = x**2 - 5*x + 6
roots = sp.solve(poly, x)
print(roots)
```

The solver returns `[2, 3]`, so x = 2 or x = 3.
```

### Why tool integration matters  
- **Unified workflow**: The model learns when to *think* in words and when to *delegate* an operation to an external tool.
- **Better generalization**: Even if a problem type was unseen during training, a well‑trained model can still call `math.sqrt` or `sympy.integrate` correctly.
- **Benchmark impact**: When tool use is allowed during evaluation, DeepSeekMath‑Instruct reaches nearly **60 % accuracy on MATH**, eclipsing all open-source baselines that either lack tool support or cannot reliably format calls.

### Training pipeline  
The same instruction set used for CoT and PoT was enriched with “tool tags” (`>>>`, code fences) that signal an execution step. The authors deliberately mixed Chinese and English problems so that token-level patterns for tool calls appear in both scripts—helpful for multilingual benchmarks like CMATH and MGSM-zh.

---

## Putting It All Together

### Multi‑style fine‑tuning → Multi‑style competence  
DeepSeekMath‑Instruct does not pick one style over another; instead it *jointly* learns all three from the same corpus. This gives it flexibility at inference time:

- If a downstream system only permits plain text answers (e.g., an offline API), the model can revert to CoT.
- If an environment supports Python execution (as many evaluation harnesses do), it can output PoT or tool‐integrated code.
- If users want brevity but correctness, they can ask explicitly for a tool call (“use Python to compute …”).

### Empirical gains on key benchmarks  

| Benchmark | No tool (CoT only) | Tool allowed (PoT / Tool‐integrated) |
|-----------|-------------------|--------------------------------------|
| GSM8K    | **88 %** (CoT)    | ~90 % (PoT improves minute edge)   |
| MATH     | **51 %** (CoT)    | **~60 %** (tool‐integrated)          |
| Chinese CMATH | ~84 %          | ~88 %                                 |
| SAT / OCW | noticeable lift over baseline models |

These numbers are *significant*: they put DeepSeekMath‑Instruct ahead of any open‐source model under 70 B parameters and within striking distance of closed models such as GPT‑4 or Gemini Ultra on pure reasoning tasks.

### Why does this work?  

1. **Data diversity** – By exposing the model to multiple reasoning modalities, it learns richer latent representations of mathematical concepts.
2. **Code pre‑training advantage** – The base model started from DeepSeek-Coder-Base-v1.5; its existing familiarity with programming constructs made PoT learning smoother.
3. **Self‐consistency via sampling** – Even though not part of instruction tuning directly, sampling multiple outputs and picking consistent answers further pushes accuracy (the paper reports self-consistency over 64 samples reaching 60.9 % on MATH).

---

## Takeaways for Practitioners

- **Collect mixed CoT/PoT data** rather than focusing solely on one style; even modest amounts (~776 K examples) are enough when combined with high‑quality math pretraining.
- **Include multilingual examples** if you care about non‑English benchmarks; tool syntax stays English (`import sympy`) while surrounding text can be Chinese or any other language.
- **Leverage existing code pretrained checkpoints**—starting from a coder model dramatically speeds up PoT learning and improves overall reasoning ability.
- **Design your inference pipeline to detect tool calls**, execute them safely, and feed back results; this simple loop turns a text generator into an effective problem solver.

---

## Closing Thoughts

DeepSeekMath demonstrates that teaching LLMs *how* to think—stepwise narration, writing concise programs, and calling external utilities—can together close much of the gap between open-source models and proprietary giants on tough math benchmarks.  

If you’re building an AI tutor, an automated proof assistant, or any system that needs reliable quantitative reasoning, consider adopting all three paradigms in your instruction tuning pipeline. The synergy they provide is now empirically validated on some of the hardest publicly available math tests—proof that LLMs can indeed be taught to think like mathematicians.
