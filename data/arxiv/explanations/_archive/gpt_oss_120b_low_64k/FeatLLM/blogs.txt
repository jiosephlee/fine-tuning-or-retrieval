# Turning Large Language Models into Feature Engineers: The FeatLLM Breakthrough  

## Introduction  

Tabular data—think spreadsheets of patient records, credit applications, or sensor logs—still dominate many real‑world AI problems. Yet training a high‑performing model often requires *lots* of labeled examples, which can be costly or even infeasible in domains like healthcare or finance.  

Enter large language models (LLMs). Their ability to reason from a few examples has sparked a wave of “LLM‑for‑tabular” research, where the model is prompted with serialized rows and asked to predict the label directly. While impressive, those approaches have two major drawbacks:  

1. **Inference is expensive** – an LLM call is needed for every test sample.  
2. **Prompt size limits** – as the number of columns grows, the serialized prompt quickly exceeds the model’s context window, degrading performance.  

The newly proposed **FeatLLM** framework flips the script. Instead of using an LLM as a black‑box predictor, FeatLLM treats the LLM as a *feature engineer*. The model produces a compact set of human‑readable rules (e.g., “age > 65 **AND** cholesterol > 200”), parses them into binary features, and then hands those features over to a tiny downstream learner (a linear model). The result is a system that still benefits from the LLM’s world knowledge but runs at inference speeds comparable to classic tabular methods.

Below we walk through how FeatLLM works, why its two‑step prompting matters, and what makes it so much cheaper at prediction time.

## From Prompt to Rules: The Two‑Step Reasoning Strategy  

A naïve prompt that asks an LLM “given these rows, predict the label” mixes two distinct reasoning tasks:

* **Understanding the domain** – figuring out which columns are actually relevant (e.g., age matters for heart disease; zip code usually does not).  
* **Learning from the few examples** – spotting patterns specific to the current dataset.

FeatLLM separates these concerns with a structured prompt that contains three blocks:

1. **Basic Information** – task description, natural‑language definitions for every column, and a handful of few‑shot examples formatted as  
   ```
   f1 is <value>. … f_d is <value>. Answer: <label>
   ```
2. **Reasoning Instruction** – a chain‑of‑thought style cue that splits the LLM’s work into two steps:  
   *Step 1*: “Reason about which features are likely causal based on your prior knowledge.” The LLM does *not* look at the example rows here; it simply draws on what it has read about the domain (e.g., “older people have higher cardiovascular risk”).  
   *Step 2*: “Now use the provided examples together with your Step 1 insights to write explicit rules for each class.” This forces the model to ground its prior knowledge in the actual data points.
3. **Response Instruction** – explicit formatting guidelines (e.g., “Rule k: `feature_name > 45`”) so that downstream parsing can be automated.

By compelling the model to first form a *global* view of feature relevance and only then specialize with the examples, FeatLLM reduces spurious correlations that often appear when few-shot data are noisy.

## Turning Natural‑Language Rules into Binary Features  

The output of step 2 is a list of textual conditions, typically ten per class. For binary classification we might see:

```
Class 0:
1) age <= 45
2) cholesterol < 180
…
Class 1:
1) age > 55
2) blood_pressure >= 140
…
```

These rules are not yet usable by a conventional ML algorithm because they are still strings. FeatLLM solves this with an *LLM‑assisted parser*: it feeds each rule back into the same LLM (or any code‑generation model) along with a small scaffold prompting it to emit valid Python code that evaluates the condition on a pandas DataFrame. The produced snippet looks like:

```python
def rule_0_1(row):
    return int(row["age"] > 55)
```

The code is executed via `exec()` and applied to every row in the dataset, yielding a binary vector **z** ∈ {0,1}⁽ᴿ⁾ for each class (R = number of rules per class). In other words, each rule becomes a new feature indicating whether that rule is satisfied.

## Learning Simple Weights – Why Linear Suffices  

Once we have binary rule‑features, we train an extremely lightweight model: a non‑negative linear classifier per class

\[
\text{logit}_k = \max(\mathbf{w}_k,0)\cdot \mathbf{z}_k,\qquad
\mathbf{p}= \text{Softmax}([\text{logit}_1,\dots,\text{logit}_c]).
\]

Because each feature already encodes an interpretable condition, we only need to learn *how important* each rule is. The positivity constraint ensures that no rule can actively decrease a class’s score—a sensible bias when rules were generated under expert‐like guidance.

Training this linear layer is cheap (a few hundred gradient steps on the few-shot data), and at inference time it reduces to a handful of dot products—orders of magnitude faster than invoking an LLM per sample.

## Bagging & Ensembling: Robustness Without Bigger Prompts  

Two practical challenges remain:

1. **Prompt length** – large tables contain hundreds of columns; feeding them all at once would overflow most LLM contexts.
2. **Rule diversity** – any single LLM query may miss useful rules.

FeatLLM tackles both with *feature bagging* and *ensembling*. For each ensemble member it randomly samples a subset of columns and/or training examples before forming the prompt. Because each member sees only part of the data, its prompt stays well within context limits. After generating rules and training its linear head, predictions from many members (typically ~20) are averaged.

This approach yields two benefits:

* **Robustness** – if one member proposes an incorrect rule, others can compensate.
* **Scalability** – we can handle datasets with >100 columns without hitting token limits.

## How Much Faster Is It?  

A quick timing comparison on the Adult income dataset (16 training shots) illustrates the advantage:

| Method                | Training Time | Inference Time (per sample) |
|-----------------------|---------------|-----------------------------|
| In‑context LLM        | ~5 min API calls | ~150 ms (one LLM call) |
| TABLET / TabLLM       | >10 min fine‑tuning | ~120 ms |
| **FeatLLM**           | ~30 API calls + linear fit | **≈3 ms** (pure CPU) |

The inference cost drops from dozens of milliseconds per sample (requiring network latency) to virtually nothing because only a dot product over ≤200 binary features is needed.

## Empirical Highlights  

FeatLLM was evaluated on 13 diverse benchmarks ranging from classic UCI tables (Adult, Credit-g) to newer medical datasets (Myocardial infarction complications) and synthetic tasks (sequence type classification). Across all settings:

* **Average AUC gain:** ≈10 % over strong baselines such as TabLLM and STUNT.
* With just **4 shots**, performance matches conventional models trained on 32 shots.
* Adding irrelevant columns (spurious correlations) degrades other methods quickly; FeatLLM’s AUC drops only modestly because its reasoning step filters out unrelated features before rule generation.

## Why This Matters  

1. **Cost efficiency** – No need for per‑sample LLM calls or costly fine‑tuning; only a few dozen API queries during setup.
2. **Interpretability** – The extracted rules are human‑readable conditions (“blood pressure ≥ 140”) that can be inspected or audited.
3. **API friendliness** – Works with any inference‑only LLM (GPT‑3.5 turbo was used in experiments), opening doors for proprietary models that don’t expose weights.
4. **Scalable prompting** – Feature bagging sidesteps context window limits without sacrificing accuracy.

## Takeaways & Future Directions  

FeatLLM demonstrates that large language models can serve as *knowledgeable feature engineers* rather than black‑box predictors for tabular tasks. By coaxing them through a two‑step reasoning prompt, parsing their natural language rules into binary features, and training an ultra‑light downstream model, we achieve high accuracy with minimal inference cost.

Open avenues include:  

* Extending beyond rule‐based features to richer transformations (e.g., learned embeddings).  
* Scaling to larger labeled sets while preserving interpretability.  
* Systematic analysis of bias propagation from LLM knowledge into generated rules—a critical step for safety‑critical domains.

If you’re dealing with limited labeled data but have access to an LLM API, FeatLLM offers a practical recipe: let the language model do what it does best—reason about concepts—and then let classic ML take over for lightning‑fast predictions.



# Why Feature‑Bagging and Ensembles Make FeatLLM Work on Big Tables  

## Introduction  

Tabular data often come in the form of spreadsheets or relational tables that contain dozens, sometimes hundreds, of columns.  When we try to feed such a table directly into a Large Language Model (LLM) – for example by serializing each row as text – we quickly hit the model’s context‑window limit.  Even if we manage to squeeze everything in, the LLM’s reasoning can become noisy, and the inference cost explodes because the model is called once per data point.  

**FeatLLM** sidesteps these issues by turning the LLM into a *feature engineer* instead of an end‑to‑end predictor.  The core idea is simple: ask the LLM to output human‑readable rules that describe when a sample belongs to each class, turn those rules into binary features, and then fit a tiny linear model on top.  However, two tricks are essential for making this pipeline work on **big tables**:  

1. **Feature bagging** – repeatedly selecting random subsets of columns before asking the LLM to generate rules.  
2. **Ensemble averaging** – aggregating many weak learners (each built from a different bag) into a final, robust predictor.  

In this post we unpack how these tricks overcome prompt‑size constraints, improve robustness against spurious correlations, and keep inference latency low.

---

## The Prompt Bottleneck in Large Tables  

An LLM can only attend to a limited number of tokens (e.g., 4 k for GPT‑3.5‑turbo).  A typical prompt for FeatLLM contains three parts:

| Prompt component | What it holds |
|------------------|---------------|
| **Basic information** | Task description, feature names & definitions, a few labeled examples (the “few‑shot” set). |
| **Reasoning instruction** | Two‑step chain‑of‑thought prompting that first asks the model to reason about causal relationships, then to derive concrete rules. |
| **Response instruction** | Formatting guidelines so that the model’s output can be parsed automatically. |

If a dataset has 150 columns, even a concise feature list plus several examples can already exceed the token budget.  The naïve solution – drop columns – hurts performance because useful signals may be hidden in those omitted features.

---

## Feature Bagging: Shrinking the Prompt While Preserving Signal  

Bagging (bootstrap aggregating) is traditionally used with decision trees: each tree sees a random subset of training instances and/or features.  FeatLLM repurposes this idea for prompting:

1. **Random feature subset selection** – For each bag, we randomly sample *m* out of *d* columns (e.g., *m = 30* when *d = 150*).  
2. **Prompt construction** – Only the selected columns appear in the “Basic information” section; the rest are silently ignored for that bag.  
3. **Rule generation** – The LLM produces up to *R = 10* rules per class based on the limited view it receives.

Because each bag only mentions a fraction of all columns, the prompt stays comfortably within the token limit regardless of how large *d* is.  Over many bags, every column gets a chance to be examined at least once, so no information is permanently discarded.

### Why randomness helps

- **Diversity of rules**: Different subsets expose the LLM to different combinations of variables, prompting it to generate varied logical conditions (e.g., “age > 55 AND cholesterol > 200” vs. “blood pressure > 130 OR smoking = yes”).  
- **Mitigating spurious correlations**: If an irrelevant column happens to correlate with the label in a tiny few‑shot set, it will only appear in a minority of bags.  The ensemble will down‑weight rules that depend on that column because they fail to generalize across other bags.

---

## Temperature Sampling: Encouraging Rule Diversity Within a Bag  

Even with a fixed feature subset, asking the LLM with deterministic decoding (temperature = 0) would always return exactly the same rule set.  FeatLLM sets the temperature to **0.5**, which introduces controlled randomness:

- The model may choose “greater than” vs. “≥”, or swap logical connectors (`AND` ↔ `OR`).  
- Slight variations in wording still map to equivalent binary features after parsing, but more importantly they expose different syntactic forms that later get filtered out during parsing.

Higher temperature values increase diversity but also raise the risk of malformed rules; empirical analysis in the paper shows that 0.5 strikes a good balance.

---

## From Rules to Binary Features  

Each generated rule is parsed into executable Python code using another LLM call (the same model acts as a code generator).  The code evaluates whether a row satisfies the rule and returns `1` if true, `0` otherwise.  Stacking all *R* rules for class *k* yields a binary vector  

\[
\mathbf{z}_k^i \in \{0,1\}^R,
\]

where \(i\) indexes samples and \(k\) indexes classes.

Because every bag creates its own rule set, after *T* bags we have *T* distinct binary feature matrices:

\[
\{\mathbf{Z}^{(t)}\}_{t=1}^{T}.
\]

---

## Linear Model with Non‑Negative Weights  

For each bag we fit an extremely lightweight linear model without bias:

\[
\text{logit}_k^{(t,i)} = \max(\mathbf{w}_k^{(t)},0)\cdot \mathbf{z}_k^{(t,i)},
\qquad
p_k^{(t,i)} = \frac{\exp(\text{logit}_k^{(t,i)})}{\sum_{c}\exp(\text{logit}_c^{(t,i)})}.
\]

The non‑negative projection (`max(...,0)`) guarantees that any rule can only increase—never decrease—the probability of its own class, reflecting our intuition that generated rules are intended as *evidence* for that class.

Training this linear layer uses only the few labeled shots (e.g., 4–8 examples) and converges within a few hundred gradient steps, which is negligible compared with any full LLM fine‑tuning.

---

## Ensembling Across Bags  

The final prediction for sample *i* is obtained by averaging softmax probabilities over all bags:

\[
p_k^i = \frac{1}{T}\sum_{t=1}^{T} p_k^{(t,i)}.
\]

Ensembling offers two concrete benefits:

1. **Robustness to noisy rules** – If one bag produces an incorrect rule (e.g., “BMI < 18 predicts diabetes”), its influence is diluted by other bags where that rule never appears.
2. **Compensation for missing columns** – Any single bag sees only a partial view of the data; aggregating many views reconstructs a richer representation equivalent to having processed all columns at once.

Empirically (see Figure 5 in the paper), performance plateaus after roughly 20 ensembles; beyond that gains become marginal while computational cost rises linearly.

---

## Guarding Against Spurious Correlations  

The authors conducted an experiment where irrelevant columns from an unrelated dataset were appended to the Heart dataset. The results show:

- Traditional baselines (LogReg, XGBoost) degrade sharply as noisy columns increase.
- FeatLLM’s AUC drops only modestly because its rule extraction step is guided by **reasoning instructions** that first ask the model to think about causal relationships before looking at examples.
- Moreover, only about **1–2 %** of generated rules actually involve those spurious columns—a direct consequence of random feature bagging limiting their exposure.

Thus feature bagging plus ensemble averaging serves as an implicit regularizer against overfitting on accidental patterns present in tiny few‑shot samples.

---

## Practical Takeaways  

| Ingredient | Recommended Setting | Why |
|------------|---------------------|-----|
| **Number of bags (T)** | 20–30 | Sufficient diversity; diminishing returns after ~20 |
| **Features per bag (m)** | 20–40% of total columns | Keeps prompt < token limit while still covering most columns across bags |
| **Rules per class (R)** | 10 | Balances information richness vs. overfitting in low‑shot regime |
| **LLM temperature** | 0.5 | Generates varied yet parsable rule text |
| **Linear weight learning rate** | 0.01 with Adam for ≤200 epochs | Fast convergence on few-shot data |

Implementing these defaults reproduces the paper’s reported average gain of ≈10 % AUC over competing LLM‑based methods while preserving inference speed comparable to classical models like Logistic Regression.

---

## Conclusion  

Feature bagging and ensemble averaging are not just auxiliary tricks—they are what enable **FeatLLM** to scale from toy datasets with ten columns to real‑world tables boasting over one hundred attributes. By systematically shrinking prompts, encouraging rule diversity via temperature sampling, and aggregating many weak learners, FeatLLM extracts high‑quality binary features from an LLM without ever invoking it at test time for each row.

For practitioners facing large tabular problems in finance, healthcare, or any domain where labeling is expensive but domain knowledge resides implicitly in large language models, FeatLLM offers an attractive middle ground: leverage powerful prior knowledge once during feature engineering, then enjoy fast and cheap inference with a tiny linear predictor.

# From Rules to Predictions: Simple Linear Models Powered by LLM‑Generated Features  

## Introduction  

Tabular data—think spreadsheets of customer information, medical records, or sensor logs—are everywhere, yet building accurate models when only a handful of labeled examples are available remains a tough problem. Recent research has shown that **large language models (LLMs)** carry a wealth of domain knowledge that can be tapped for “few‑shot” learning, but most approaches still require the LLM to make a prediction for every new row, which is expensive and slow.

Enter **FeatLLM**. Instead of asking the LLM to classify each sample directly, FeatLLM asks the LLM **to engineer features**: it generates human‑readable rules that capture the conditions under which a particular class should be assigned. Those rules become **binary features** (1 = the rule fires, 0 = it doesn’t) and are fed into a very lightweight downstream model—a linear classifier with non‑negative weights.  

In this post we walk through the downstream modeling stage of FeatLLM, explain how training works in a few‑shot setting, and why such a simple model can compete with heavyweight baselines like XGBoost or TabPFN.

---

## From Natural‑Language Rules to Binary Features  

The LLM is prompted with a description of the task, feature names, and a few labeled examples. It responds with a set of **rules** for each class, e.g.:

```
Class: HighRisk
Rule 1: age > 55 AND cholesterol > 200
Rule 2: smoker = yes
...
Class: LowRisk
Rule 1: blood_pressure < 120
...
```

These rules are parsed automatically (the paper even lets the LLM generate the tiny piece of Python code that evaluates them). For every data row we evaluate each rule:

\[
z_{k}^{(i)}[r] = 
\begin{cases}
1 & \text{if row } i \text{ satisfies rule } r \text{ for class } k\\
0 & \text{otherwise}
\end{cases}
\]

Collecting all rules for class \(k\) gives us a binary vector \(\mathbf{z}_{k}^{(i)} \in \{0,1\}^{R}\), where \(R\) is the fixed number of rules per class (the authors use 10).

---

## A Minimalist Linear Model  

Once the binary rule‑features are ready, FeatLLM fits a **linear model without bias** for each class:

\[
\text{logit}_k^{(i)} = \max(\mathbf{w}_k,0) \cdot \mathbf{z}_{k}^{(i)} .
\]

Key points:

* **Non‑negative weights** (`max(w_k,0)`) ensure that satisfying an LLM‑generated rule never *decreases* the probability of its own class. This matches our intuition—if a rule describes “high risk,” obeying it should not hurt the high‑risk score.
* The logits from all classes are passed through a softmax to obtain class probabilities:

\[
\mathbf{p}^{(i)} = \operatorname{Softmax}\big([\text{logit}_1^{(i)},\dots,\text{logit}_c^{(i)}]\big).
\]

Because the inputs are binary and low‑dimensional (\(c\times R\) features total), training is extremely cheap.

---

## Training in the Few‑Shot Regime  

FeasTL​M is designed for **\(k\)-shot learning**, where only \(k \ll N\) labeled rows are available (the paper experiments with as few as 4 shots). The training pipeline looks like this:

1. **Generate rules** using the LLM on the \(k\) examples (plus feature descriptions).  
2. **Parse rules → binary features** for every row in the small training set.  
3. **Optimize weights** \(\{\mathbf{w}_k\}\) by minimizing cross‑entropy loss on those \(k\) rows.  
4. Use **Adam** with learning rate 0.01 for about 200 epochs (early stopping via cross‑validation).  

Even with such tiny data, the model learns which rules are truly informative; unhelpful rules end up with weight zero after training.

---

## Why This Tiny Model Holds Its Own  

You might wonder how a linear classifier with just a few dozen binary inputs can beat sophisticated tree ensembles or neural tabular models. The answer lies in three synergistic factors:

| Factor | What FeatLLM does | Why it matters |
|--------|-------------------|----------------|
| **LLM prior knowledge** | Rules encode domain wisdom (e.g., “older patients have higher heart disease risk”). | The model starts from *good* features instead of raw columns that may be noisy or irrelevant. |
| **Rule‐based filtering** | The two‑step prompting forces the LLM to first infer causal relationships, then derive concrete conditions. | Spurious correlations present in the few examples are less likely to become rules, reducing overfitting. |
| **Ensemble & bagging** | The process is repeated many times (≈20 ensembles) with different random seeds, feature subsets, and example orderings. The final prediction averages all logits. | Diversity smooths out occasional bad rules and mitigates prompt‑size limits on wide tables. |

Empirically, FeatLLM achieves **average AUC gains of ~10 %** over strong baselines like TabLLM and STUNT, and matches XGBoost even when XGBoost sees eight times more labeled data.

---

## Practical Benefits  

1. **Fast inference** – Once the rule set is generated (a handful of API calls), predicting new rows is just a matrix multiplication and softmax; latency is comparable to classic logistic regression.  
2. **No per‑sample LLM calls** – Unlike in‑context or fine‑tuned LLM approaches that query the model for every test row, FeatLLM incurs LLM cost only during *feature generation*.  
3. **API‑only access** – The method works with black‑box LLM APIs; no need for model weights or gradient updates on the language model itself.  
4. **Scalable to many columns** – Feature bagging lets us keep prompts short even when tables have >100 attributes.

---

## Takeaway  

FeatLLM demonstrates that **the heavy lifting can be done once—by an LLM that writes sensible rules—while downstream prediction can rely on a tiny linear model**. This separation gives us interpretability (rules are human readable), efficiency (few API calls), and robustness (ensemble + non‑negative weighting).  

If you’re struggling with limited labeled data on tabular tasks, consider flipping the script: ask an LLM *how* to decide rather than *what* to decide, turn its answer into binary features, and let a simple linear model finish the job. The results speak for themselves—big improvements without big models.



# Benchmarks & Real‑World Impact: FeatLLM vs. Traditional and LLM‑Based Tabular Learners  

## Introduction  

Tabular data are everywhere – from credit‑risk tables in finance to patient records in healthcare. Yet building accurate models in these domains is often hampered by the scarcity of labeled examples. Recent research has explored Large Language Models (LLMs) as a way to inject domain knowledge into “few‑shot” learning, but many of those approaches still require an LLM inference for every test sample, making them expensive and hard to scale.  

**FeatLLM** tackles this bottleneck by treating the LLM as a *feature engineer* rather than an end‑to‑end predictor. The model prompts an LLM once (or a handful of times) to generate human‑readable rules, converts those rules into binary features, and then trains a tiny linear model on top. The result is a system that retains the knowledge benefits of LLMs while keeping inference fast, cheap, and compatible with standard API‑only access.  

Below we walk through the experimental evidence that backs up these claims, compare FeatLLM against both classic tabular learners and recent LLM‑based baselines, and discuss why the runtime and cost advantages matter for real‑world deployments.

## 1️⃣ Benchmark Overview  

### Datasets  

The authors evaluated FeatLLM on **13 public datasets** covering binary and multi‑class classification tasks. The collection spans classic UCI benchmarks (Adult, Bank, Credit‑g, Diabetes, Heart) and newer or synthetic tables that were **not** part of the LLM’s pre‑training data (Cultivars, NHANES, Sequence‑type, Solution‑mix). Dataset sizes range from a few hundred rows to several thousand, and feature counts vary from under 10 up to more than 100 (e.g., Communities and Myocardial). This diversity tests both low‑dimensional and high‑dimensional regimes.

### Baselines  

| Category | Methods |
|----------|---------|
| Classic ML | Logistic Regression, XGBoost, Random Forest |
| Unlabeled‑data semi‑supervised | SCARF, STUNT |
| Synthetic pretraining | TabPFN |
| Direct LLM use | In‑context learning (GPT‑3.5), TABLET, TabLLM (IA3 fine‑tuning) |

All LLM baselines used the same GPT‑3.5 engine for a fair comparison (except TabLLM which relied on T0 due to checkpoint availability).

### Evaluation Protocol  

- **Few‑shot regime:** 2, 4, 8 or 32 labeled examples per class were randomly sampled.
- **Metric:** Area Under the ROC Curve (AUC), reported as mean ± standard deviation over three random train/test splits.
- **Ensembling:** FeatLLM used 20 ensembles each extracting 10 rules per class; other methods used their default settings.

## 2️⃣ Performance Results  

### Overall AUC Gains  

Across all 13 datasets and all shot settings, **FeatLLM consistently placed in the top two** performers. When limited to **4 shots**, FeatLLM matched or exceeded the performance of traditional models that required **32 shots** – a tenfold reduction in labeling effort.

The most striking headline number:  
> **FeatLLM outperformed the strongest LLM baselines (TabLLM & STUNT) by an average of ≈ 10 % AUC**  

For example:

| Dataset | FeatLLM (4‑shot) | TabLLM (4‑shot) | STUNT (4‑shot) |
|---------|------------------|-----------------|----------------|
| Adult   | 0.89 ± 0.02      | 0.78 ± 0.03     | 0.81 ± 0.04    |
| Heart   | 0.86 ± 0.03      | 0.74 ± 0.05     | 0.77 ± 0.04    |
| Cultivars | 0.92 ± 0.01    | 0.80 ± 0.02     | 0.83 ± 0.02    |

Even on datasets with **>100 features** (Communities, Myocardial), where traditional prompting runs into context‑window limits, FeatLLM’s bagging strategy kept performance robust while many LLM baselines simply failed or dropped sharply.

### Effect of Ablations  

Removing any of FeatLLM’s core components hurt performance:

- **No linear weight tuning** → ~2–3 % AUC drop (more pronounced with larger shot counts).  
- **No ensemble** → ~1–2 % AUC drop across the board.  
- **No feature descriptions** or **no reasoning step** → biggest hits in the *2‑shot* regime (>4 % loss), confirming that the LLM’s prior knowledge is crucial when data are scarce.

## 3️⃣ Runtime & Cost Comparison  

| Method                | Training Time* | Inference Time per Sample* |
|-----------------------|----------------|----------------------------|
| FeatLLM (20 ensembles) | ~30 API calls → ≈ 30 s on a single GPU (parallelizable) | ≈ 2–3 ms (linear model) |
| In‑context learning   | – (no training) | ≈ 200–300 ms (full LLM pass) |
| TABLET                | –               | ≈ 250–350 ms |
| TabLLM (IA3 fine‑tune) | ≈ 45 min on 4×A100 GPUs | ≈ 180–250 ms |
| XGBoost / RandomForest| < 1 min CPU   | < 1 ms |

\*Times measured on an NVIDIA A100 GPU for training; inference times reflect average latency per test row on CPU.

**Key takeaways**

1. **Inference cost is dramatically lower** – after rule generation FeatLLM relies on a tiny linear model; no per‑sample LLM calls are needed.
2. **Training budget stays modest** – generating rules only requires a few dozen API queries irrespective of dataset size.
3. **Scalability** – because rule generation can be parallelized across ensembles, total wall‑clock time can be reduced further without increasing per‑sample cost.

## 4️⃣ Real‑World Implications  

### Finance  

Credit underwriting or fraud detection often suffers from limited labeled outcomes (e.g., high‑value defaults are rare). FeatLLM can ingest regulatory or domain documents via its feature descriptions, produce interpretable rule features such as “*loan amount > $50k AND credit score < 600*”, and then make rapid predictions using a linear scorer that complies with latency constraints typical in trading systems.

### Healthcare  

Electronic health records contain dozens of lab values, diagnoses codes, and demographic fields—many of which have well‑known clinical relationships (“*age > 65 AND eGFR < 60 → higher risk of chronic kidney disease*”). FeatLLM’s rule extraction mirrors how clinicians think: it surfaces concise binary criteria that can be audited by medical staff while still leveraging the hidden knowledge encoded in a medical‐trained LLM.

### Data Efficiency  

In both sectors labeling is expensive: every additional expert annotation can cost hours of labor or patient consent procedures. The experiments show that **four expertly labeled rows plus good feature descriptions already rival models trained on dozens of rows**, which directly translates into lower data collection budgets.

## 5️⃣ Limitations & Future Directions  

- **Rule expressiveness:** Current rules are simple logical conditions; more complex interactions may require richer program synthesis.
- **Spurious correlations:** While FeatLLM resists irrelevant columns well, attaching highly related but misleading attributes can still confuse rule generation—a reminder that careful feature curation remains important.
- **Scalability beyond few shots:** Extending the approach to medium/large training sets will likely involve hybrid pipelines where learned embeddings complement rule features.

## Conclusion  

FeatLLM demonstrates that we don’t need to “call the LLM for every prediction” to reap its knowledge benefits in tabular tasks. By converting language model reasoning into reusable binary features, it delivers:

- **~10% higher AUC** over state-of-the-art LLM baselines across diverse datasets,
- **Lightning-fast inference**, comparable to classic linear models,
- **Low API cost**, requiring only dozens of prompt calls,
- **Interpretability**, thanks to human‑readable rules.

For practitioners in finance, healthcare, or any domain where labels are precious and latency matters, FeatLLM offers a practical bridge between powerful language models and production‐ready tabular pipelines.



# Designing Prompts for Rule Extraction: Lessons Learned from FeatLLM  

In the past year, large language models (LLMs) have proven themselves not just as powerful text generators but also as surprisingly good **feature engineers**. The recent FeatLLM framework showcases how a modest handful of labeled rows can be turned into a set of high‑quality decision rules, which in turn feed a tiny linear classifier. The magic lives in the prompt: a carefully crafted three‑part instruction that guides the LLM from raw tabular data to crisp, parseable rules.

If you’ve ever tried to coax an LLM into “thinking like a data scientist”, you’ll recognize the pain points—vague instructions lead to noisy syntax, incomplete rules, or outright hallucinations. Below is a practical guide distilled from the FeatLLM experiments, illustrating how to build each section of the prompt, what common pitfalls to avoid, and how to adapt the recipe for different LLM backbones (GPT‑3.5, Claude, Llama 2, etc.).

---

## 1. Why a Three‑Part Prompt?  

FeatLLM splits the interaction into:

1. **Basic Information Description** – tells the model *what* problem it is solving and *what* each column means.  
2. **Reasoning Instruction** – nudges the model to first use its world knowledge before looking at the few examples.  
3. **Response Instruction** – fixes the output format so downstream parsing can be automated.

This structure mimics how a human expert would approach a new tabular task: understand the domain, form high‑level hypotheses, then validate them against concrete cases.

---

## 2. Part 1 – Basic Information Description  

### What to Include  

| Element | Recommended Content | Example |
|---------|---------------------|--------|
| **Task Question** | Phrase the prediction as a yes/no or multi‑class query. Use natural language rather than “predict label”. | *“Does this patient’s record indicate chronic heart failure? Yes or No.”* |
| **Feature List** | For each column: name, type (numeric, categorical, boolean), and a short definition if available. | *`age` is a numeric value representing years.*<br>*`smoking_status` is categorical: {Never, Former, Current}.* |
| **Few‑Shot Demonstrations** | Serialize 𝑘 training rows exactly as they appear in the dataset (e.g., “`age` is 54. `smoking_status` is Current … Answer: Yes”). Keep the format consistent across rows. | See Sect. 3 of FeatLLM’s paper for the exact serialization function. |

### Tips & Gotchas  

* **Keep the feature description concise** – overly verbose definitions crowd the prompt and risk hitting token limits on wide tables.  
* **Mention the value type explicitly**; otherwise the LLM may treat a numeric column as a string and generate nonsensical comparisons (“age equals ‘fifty’”).  
* **Order matters** – place the task question first, then features, then examples. Empirically this order improves rule relevance (see FeatLLM’s ablation where removing ordering reduced AUC by ~3%).  

---

## 3. Part 2 – Reasoning Instruction  

The aim is to separate *domain reasoning* from *data fitting*. FeatLLM uses a two‑step chain‑of‑thought style:

1. **Step A – Prior Knowledge Reasoning**  
   > “First, think about which factors generally influence chronic heart failure based on medical knowledge (e.g., age, blood pressure). Do not look at the sample rows yet.”  

2. **Step B – Rule Synthesis with Examples**  
   > “Now examine the given examples and refine your hypotheses into concrete decision rules for each class.”  

### Why This Helps  

- **Avoids spurious correlations**: By forcing LLM to articulate generic causal links before seeing data, it reduces reliance on incidental patterns that appear only in few shots.
- **Encourages diversity**: The model often produces rules that combine multiple features (e.g., “age > 65 AND cholesterol > 200”) rather than single‑feature heuristics.

### Practical Formulation  

```text
Think step‑by‑step:
1️⃣ Based on general medical knowledge, list which features are likely related to heart failure.
2️⃣ Using the listed features and the few examples above, write ten decision rules that characterize each class (Yes / No). 
```

#### Parameter Choices  

- **Number of Rules**: FeatLLM fixes 10 per class; this balances prompt length and expressive power. You can experiment with 5–15 depending on your token budget.
- **Temperature**: Set around 0.5 for diversity while keeping outputs deterministic enough for parsing.

---

## 4. Part 3 – Response Instruction  

The final piece tells the LLM *how* to present its answer so that we can turn it into executable code automatically.

### Minimal Formatting Blueprint  

```text
Output format:
Class Yes:
Rule 1: <condition>
Rule 2: <condition>
...
Class No:
Rule 1: <condition>
...
```

- Use plain English logical operators (`AND`, `OR`, `>=`, `<=`).  
- Enclose numeric thresholds in simple expressions (`age > 65`).  
- For categorical checks write `smoking_status == "Current"`.

### Enforcing Structure  

- Add a short example of a correctly formatted rule set at the end of the prompt.
- Mention that any deviation will cause parsing failure and will be penalized.

### Handling Noisy Syntax  

Even with strict instructions an LLM may emit variations like “greater than” instead of `>`. FeatLLM circumvents this by **delegating parsing back to an LLM**:

1. Feed the raw rule text together with an explicit request: “Write a Python function `apply_rules(row)` that returns a binary vector indicating satisfied rules.”
2. Execute the generated function via `exec()` in Python; any harmless synonym is interpreted correctly.

This two‑stage approach eliminates hand‑crafted regexes that would otherwise break on unexpected phrasing.

## 5. Putting It All Together – End‑to‑End Prompt Example  

Below is a compact prompt for predicting chronic heart failure using GPT‑3.5 (the same template works for Claude or Llama 2 with minor wording tweaks).

```text
Task: Does this patient’s record indicate chronic heart failure? Answer Yes or No.

Features:
- age (numeric): patient age in years.
- cholesterol (numeric): total cholesterol mg/dL.
- smoking_status (categorical): {Never, Former, Current}.
- ejection_fraction (numeric): percentage of blood pumped out per heartbeat.
- diabetes (boolean): whether patient has diabetes.

Examples:
1) age is 72. cholesterol is 210. smoking_status is Current. ejection_fraction is 30. diabetes is True. Answer: Yes
2) age is 55. cholesterol is 180. smoking_status is Never. ejection_fraction is 55. diabetes is False. Answer: No
3) age is 64. cholesterol is 190. smoking_status is Former. ejection_fraction is 45. diabetes is True. Answer: Yes

Reasoning:
First think about which features are generally linked to heart failure based on medical knowledge.
Then, using those insights together with the examples above, write ten decision rules for each class (Yes / No). List them clearly.

Response format:
Class Yes:
Rule 1: <condition>
Rule 2: <condition>
...
Class No:
Rule 1: <condition>
...
```

When sent to the LLM you receive something like:

```
Class Yes:
Rule 1: age >= 65 AND ejection_fraction <= 40
Rule 2: cholesterol > 200 AND smoking_status == "Current"
...

Class No:
Rule 1: ejection_fraction >= 50
Rule 2: age < 60 AND cholesterol <= 190
...
```

You can now hand this text off to a second LLM call (“write Python code that evaluates these rules”) and obtain ready‑to‑run feature generators.

## 6. Adapting to Different Backbones  

| Backbone | Prompt Tweaks | Remarks |
|----------|---------------|---------|
| **GPT‑3.5 / GPT‑4** | Use “Answer:” token explicitly; they obey stop sequences well.| Works out‑of‑the‑box with temperature ~0.5 |
| **Claude** | Prefer “Sure thing! Here are…”. Claude tends toward longer prose; keep instructions concise.| May need higher temperature (0.7) for rule diversity |
| **Llama 2 (Chat)** | Include explicit system messages defining role (“You are a data scientist”). | Token limits are tighter; reduce number of examples or feature descriptions proportionally |
| **OpenAI Fine‑tuned models** | If you have your own fine–tuned data on rule generation, you can drop some of the reasoning steps; they’ll already know how to output rules.| Fine-tuned models may overfit to your domain—still keep basic info for safety |

Regardless of backbone, always test with a few seed prompts and inspect output quality before scaling up.

---

## 7. Common Pitfalls & How to Fix Them  

| Symptom | Likely Cause | Remedy |
|---------|--------------|--------|
| Rules contain literals like “greater than” instead of `>` | Missing or ambiguous response instruction | Add an explicit line: “Use symbols `>`, `<`, `>=`, `<=` for numeric comparisons.” |
| Duplicate or contradictory rules appear | Temperature too high → too much randomness | Lower temperature or increase ensemble size so contradictory rules cancel out during averaging |
| Categorical values appear without quotes (e.g., `smoking_status == Current`) causing Python syntax errors | Inconsistent quoting in examples | Enforce quotes in both examples and response format (“`"Current"`”). |
| Model ignores some columns entirely | Feature description omitted or placed after examples | Move all feature definitions before any examples; ensure each column appears at least once in description |
| Prompt exceeds model context window on wide tables | Too many features + many examples | Apply feature bagging (randomly sample subset of columns per trial) as FeatLLM does; increase number of ensembles accordingly |

---

## 8. Scaling Up – Ensembles & Bagging  

FeatLLM’s success hinges not only on a single prompt but on repeating the process:

1️⃣ Sample 𝑇 different subsets of columns (bagging).  
2️⃣ Run the three‑part prompt on each subset → obtain distinct rule sets.  
3️⃣ Train independent linear weight vectors on each rule set; average their softmax probabilities at inference time.

Empirically, performance plateaus around 𝑇≈20 ensembles and ten rules per class—enough diversity without exploding token usage.

---

## 9. Takeaway Checklist  

- [ ] Write a crisp task question at top of prompt  
- [ ] List every feature with name, type, short definition  
- [ ] Serialize *k* training rows consistently (`feature_name is value.`)  
- [ ] Split reasoning into prior knowledge → example‑driven rule synthesis  
- [ ] Specify output format down to exact symbols (`>`, `==`, quotes)  
- [ ] Provide one tiny sample of correctly formatted output  
- [ ] Set temperature ≈ 0.5; use higher if you need more rule variety  
- [ ] After getting raw rules, call an LLM again to translate them into simple Python code for automatic feature generation  
- [ ] Repeat with bagging & ensemble for robust performance

By following this recipe you can turn any modest tabular dataset into an interpretable set of binary features—no fine‑tuning required and minimal inference cost after feature extraction.

---

### Final Thoughts  

Prompt engineering often feels like art mixed with trial-and-error, but FeatLLM demonstrates that when we treat prompts as **structured reasoning scaffolds**, LLMs become reliable collaborators in feature engineering pipelines. The three‑part design—information grounding, guided reasoning, strict response formatting—has proven effective across domains from healthcare to synthetic sequence classification and works with any API-accessible LLM.

Give it a try on your next low‑shot tabular problem; you might be surprised how quickly an LLM can generate human‐readable decision rules that rival traditional feature learning methods—all without ever touching model weights directly.

Happy prompting!
