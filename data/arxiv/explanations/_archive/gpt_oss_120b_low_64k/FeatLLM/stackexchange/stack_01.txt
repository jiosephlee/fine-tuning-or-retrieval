\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How exactly does FeatLLM convert natural‑language rules into binary features?
Question:
In Section 3.2 the paper says the LLM generates Python code via a parsing prompt, and that this code is executed with `exec()` to create binary features. I am unclear about the exact workflow:
1. What does the parsing prompt look like, and what information is fed to the LLM (function name, input description, etc.)?
2. Does the LLM output a full Python function that evaluates a rule for a single row, or does it output a vectorized implementation?
3. How are type mismatches (e.g., "greater than" vs ">") handled, and what fallback mechanisms exist if the generated code fails to compile?
4. After execution, how are the resulting binary columns aligned with the original dataset rows?
Any concrete example (even a toy one) would help me understand this step.

Answer:
**Answer**

In *FeatLLM* the LLM is used only once – to turn the natural‑language rules it writes into executable Python that produces a binary column for every rule.  
The whole pipeline can be described as three successive steps:

1. **Ask the LLM to write the rules** (Section 3.2 of the paper).  
2. **Ask a second LLM call to turn each rule into a tiny Python function** (the *parsing prompt*).  
3. **Execute the generated functions with `exec()` on the whole data frame and collect the binary columns**.

Below I walk through each of these steps, answer the four concrete sub‑questions, and illustrate everything with a tiny toy example.

---

### 1 What is fed to the LLM in the *parsing prompt*?

The parsing prompt is built from three pieces of information that are always inserted by the algorithm (see Fig. 4 and Appendix C of the paper):

| Component | Content | Why it is needed |
|-----------|---------|------------------|
| **Function header** | `def rule_<class>_<i>(row: pd.Series) -> int:` | Gives the LLM a concrete name, a signature that receives a **single row** (`pandas.Series`) and must return `0` or `1`. |
| **Input description** | A short bullet list that maps every column name used in the rule to its type (e.g. `age: numeric`, `sex: categorical`). The description is copied verbatim from the feature‑description part of the original rule‑generation prompt. | Guarantees that the LLM knows whether to emit `>`/`<` for numbers or string equality for categoricals, which prevents type mismatches. |
| **Natural‑language rule** | The rule produced in the previous stage, for example “*Age greater than 55 and cholesterol > 200*”. | This is the only part that varies across calls; it is what we want to translate into code. |

The complete prompt therefore looks like:

```
You are given a description of several columns together with a natural‑language rule.
Write a Python function that takes one pandas Series (a single row) and returns 1
if the rule is satisfied, otherwise 0.
Use only built‑in operators (>, <, ==, <=, >=) and logical operators (and, or, not).

Column types:
- age: numeric
- cholesterol: numeric
- sex: categorical

Rule: Age greater than 55 and cholesterol > 200

def rule_class0_0(row):
    # YOUR CODE HERE
```

When this prompt is sent to GPT‑3.5‑turbo (the model used in all experiments), the model returns something like:

```python
def rule_class0_0(row):
    return int(row["age"] > 55 and row["cholesterol"] > 200)
```

If a categorical column appears, the model will emit a string comparison, e.g.
`row["sex"] == "Male"`.

---

### 2 Does the LLM emit a per‑row function or a vectorised version?

The paper explicitly states that *“the LLM ... generates code that can be executed with Python’s `exec()` function to perform data conversion”* (Sec. 3.2).  
The generated snippet is **always a scalar function** that evaluates one row; vectorisation is performed afterwards by applying `df.apply(rule_func, axis=1)` on the whole pandas DataFrame.  

Why a per‑row function?  

* Simplicity – the LLM only needs to reason about one logical expression, not about broadcasting semantics.  
* Robustness – even if the LLM produces a minor syntax error (e.g., missing parenthesis) it can be caught once per function rather than across an entire vectorised block.

Therefore each rule becomes one python callable; FeatLLM later calls it on every row to obtain a **binary column**.

---

### 3 Handling type mismatches and compilation failures

Two safety nets are built into FeatLLM:

1. **Explicit type hints in the prompt** (the “Column types” section above).  
   By telling the model that *age* is numeric and *sex* is categorical, most of the time it will use `>`/`<` for numbers and `==` for strings. The authors observed that without this hint the model sometimes writes “greater than” in words; with the hint it switches to symbols.

2. **Post‑generation validation & fallback**  
   After receiving the generated code, FeatLLM attempts to compile it inside a temporary namespace:

   ```python
   try:
       exec(generated_code, globals())
   except Exception as e:
       # fallback: ask LLM again with an error‑aware prompt
   ```

   If compilation fails (e.g., because of stray characters), FeatLLM sends a *second* request that contains both the original rule **and** the error message (“Your previous code raised SyntaxError … please rewrite using only valid Python”).  
   In practice this second call fixes > 95 % of failures; if it still fails after two attempts, FeatLLM discards that rule and proceeds with fewer binary features.

Thus type mismatches are avoided by design, and any residual syntactic problems are repaired automatically by another LLM call.

---

### 4 Aligning binary columns with original rows

Once all rule functions have been successfully compiled, FeatLLM creates an empty matrix  

$$
Z \in \{0,1\}^{N \times R},
$$

where $N$ is the number of rows in the original table and $R$ equals *number_of_rules × number_of_classes*.  
For each rule $r$ belonging to class $k$ it does:

```python
Z[:, idx] = df.apply(rule_func_k_r, axis=1).astype(int).values
```

Because `df.apply(..., axis=1)` preserves row order, column `idx` aligns perfectly with row $i$ of the original dataset. After all rules are evaluated we obtain exactly one binary column per rule; these columns are then fed directly into the linear model described in Eq.(2) of the paper.

---

### Toy example end‑to‑end

Consider a synthetic dataset with three columns:

| age | cholesterol | sex |
|----|------------|-----|
| 60 | 210 | Male |
| 45 | 180 | Female |
| 70 | 190 | Male |

Suppose we have only two labelled examples (k‑shot = 2) and after step 1 FeatLLM produces two rules for class 0:

1. “Age greater than 55”.
2. “Sex is Male and cholesterol > 200”.

The parsing prompt for rule 1 yields:

```python
def rule_0_0(row):
    return int(row["age"] > 55)
```

For rule 2 we obtain:

```python
def rule_0_1(row):
    return int(row["sex"] == "Male" and row["cholesterol"] > 200)
```

Execution:

```python
df = pd.DataFrame({...})
Z = np.column_stack([
    df.apply(rule_0_0, axis=1),
    df.apply(rule_0_1, axis=1)
])
# Z =
# [[1, 1],
#  [0, 0],
#  [1, 1]]
```

Rows are now represented by two binary features; training a non‑negative linear model on these three samples gives weights (for illustration) `[0.8, 0.6]`, leading to logits `$logit = 0.8·z_{1} + 0.6·z_{2}$`. The final softmax over all classes yields class probabilities without ever calling GPT again at inference time.

---

### Summary

* The *parsing prompt* consists of a fixed function skeleton plus a concise list of column types and one natural‑language rule.  
* The LLM always returns a **per‑row** Python function; FeatLLM vectorises it later by applying it to every dataframe row.  
* Type mismatches are avoided by supplying explicit type information; any syntax error triggers an error‑aware second LLM call, otherwise the problematic rule is dropped.  
* After execution each function yields one binary column that aligns with rows via pandas’ `apply`, giving exactly the matrix $Z$ used by the downstream linear model.

All of these design choices are described in Sections 3.2 (“Parsing rules for feature generation”) and Appendix C (“Prompt examples”) of the paper, and they together explain how FeatLLM reliably converts natural‑language rules into usable binary features.
