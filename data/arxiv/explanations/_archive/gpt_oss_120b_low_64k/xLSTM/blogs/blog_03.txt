# Memory Matters: Scalar vs. Matrix Memories in sLSTM and mLSTM  

*In the original LSTM, each cell stores a single scalar value. The new xLSTM family expands that idea in two directions: a scalar‑based sLSTM that adds exponential gating and a matrix‑based mLSTM that behaves like a fast‑weight associative memory. Below we break down the differences, why the matrix memory helps with rare‑token prediction, and what practical trade‑offs you should keep in mind when choosing between them.*

---  

## Why revisit LSTM memory at all?  

The classic LSTM update  
\[
c_t = f_t \, c_{t-1} + i_t \, z_t ,\qquad   
h_t = o_t \,\psi(c_t)
\]  
stores information in a **single scalar** \(c_t\). This design solved the vanishing‑gradient problem but it also imposed three well‑known limits:

1. **Irreversible storage decisions** – once a value is written, the model can’t easily “overwrite” it later.  
2. **Limited capacity** – everything must be compressed into one number per cell, which hurts rare‑token prediction where subtle cues get lost.  
3. **Sequential bottleneck** – hidden‑to‑hidden connections force strictly serial processing.

The xLSTM paper addresses each of these points with two new building blocks:

| Variant | Memory shape | Key idea | Primary benefit |
|---------|--------------|----------|-----------------|
| **sLSTM** | Scalar \(c_t\) (still one number per cell) | Exponential gating + a *normalizer state* that lets the network revise past writes | Enables *memory mixing* and state tracking that vanilla LSTMs lack |
| **mLSTM** | Matrix \(\mathbf{C}_t \in \mathbb{R}^{d\times d}\) | Covariance (outer‑product) update → *fast‑weight associative memory* | Vast storage capacity; dramatically improves rare‑token prediction and long‑range recall |

Below we dive into how each works.

---  

## sLSTM: Scalar Memory with Exponential Gating  

### The core change  
Instead of the usual sigmoid gates, sLSTM lets the **input gate** be an exponential function:
\[
i_t = \exp(\tilde{i}_t), \qquad 
\tilde{i}_t = \mathbf{w}_i^\top\mathbf{x}_t + r_i h_{t-1}+b_i .
\]
The forget gate can stay sigmoid or also become exponential. Because exponentials can explode, the authors introduce a *stabilizer state* \(m_t\) that rescales \(i_t\) and \(f_t\) on the fly, preserving numerical stability without changing the gradients.

### Normalizer state & revisable storage  
A new auxiliary variable
\[
n_t = f_t n_{t-1} + i_t
\]
tracks the cumulative “strength” of past gates. The hidden output is then normalized by this tally:
\[
h_t = o_t \,\frac{c_t}{n_t}.
\]
If a later input is more relevant, its larger \(i_t\) will increase both the numerator (new content) and denominator (total gate mass), effectively *re‑weighting* earlier information. This solves the “cannot revise storage decisions” problem that standard LSTMs suffer from—see the Nearest Neighbour Search experiment in the paper.

### Memory mixing (the hidden‑to‑hidden connection)  
When multiple scalar cells are stacked, sLSTM allows **memory mixing** via learned recurrent matrices \(\mathbf{R}\) that connect hidden states back into each cell’s input and gates. Although this preserves sequential dependence (no full parallelism), it gives the network extra expressive power for tasks that require tracking complex state (e.g., parity or nested brackets).  

---  

## mLSTM: Matrix Memory as a Fast‑Weight Associative Store  

### From key–value pairs to an outer product  

In mLSTM each time step produces a *key* \(\mathbf{k}_t\) and a *value* \(\mathbf{v}_t\). The memory matrix updates by adding their outer product:
\[
\mathbf{C}_t = f_t\,\mathbf{C}_{t-1} + i_t\, \mathbf{v}_t\,\mathbf{k}_t^\top .
\]
If we ignore gating (\(f_t=1,i_t=1\)) this is exactly the classic **Bidirectional Associative Memory** rule introduced in the 1970s. The forget gate acts as a decay term; the input gate controls how much of the new outer product is written—mirroring learning‑rate and weight‑decay dynamics in fast‑weight programmers.

### Retrieval via matrix–vector multiplication  

A query vector \(\mathbf{q}_t = \mathbf{W}_q \mathbf{x}_t + b_q\) reads from memory:
\[
\tilde{\mathbf{h}}_t = 
\frac{\mathbf{C}_t \,\mathbf{q}_t}
{\max\bigl(| \mathbf{n}_t^\top \mathbf{q}_t|, 1\bigr)},
\qquad
h_t = o_t \odot \tilde{\mathbf{h}}_t,
\]
where the normalizer state
\[
\mathbf{n}_t = f_t\,\mathbf{n}_{t-1} + i_t\, \mathbf{k}_t
\]
plays the same role as in sLSTM: it rescales the dot product to avoid division by near‑zero values.

### Why does this help rare tokens?  

Rare tokens often appear only a handful of times during training, so a model needs to *remember* them with high fidelity across long gaps. A scalar cell can only keep a compressed summary; if many different tokens compete for that single slot, information gets blended and rare signals fade.  

A matrix memory, however, stores **pairs of vectors** directly. Each key/value pair occupies its own rank‑one subspace inside \(\mathbf{C}\). When a query aligns with a stored key, the corresponding value pops out with minimal interference from unrelated keys—a property that translates into **higher signal‑to‑noise ratio** for infrequent items. The paper’s Wikitext‑103 experiments confirm this: mLSTM dramatically reduces perplexity on low‑frequency token bins compared with both vanilla LSTM and sLSTM.

### Parallelism advantage  

Because there is no hidden‑to‑hidden recurrence (no mixing), all updates in mLSTM can be expressed as batched matrix multiplications:
- Compute keys/values/queries for every time step in parallel.
- Perform a cumulative scan of \(f_t\,\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t\,\mathbf{k}_t^\top\) using prefix sums.
- Apply one final matrix–vector product for retrieval.

In practice this yields GPU-friendly kernels similar to FlashAttention’s approach—linear time in sequence length and constant memory usage per token.

## Capacity vs. Computational Cost: When to Use Which?  

| Aspect | sLSTM (scalar) | mLSTM (matrix) |
|--------|----------------|----------------|
| **Memory capacity** | Limited to one number per cell; good for short‑term dependencies. | Up to \(d^2\) stored dimensions (outer products); excels at long‑range associative recall. |
| **Rare‑token handling** | Modest improvement via exponential gating; still compresses heavily. | Significant boost; each rare token can retain its own key/value subspace. |
| **Parallelizability** | Requires sequential hidden‑to‐hidden passes → slower on GPUs (≈2× slower than mLSTM). | Fully parallelizable across time steps; overhead dominated by dense matrix ops (≈4× slower than FlashAttention but still linear). |
| **Compute cost per step** | Small (few vector ops). | Higher: \(O(d^2)\) for outer product update & matrix–vector retrieval. |
| **Best suited for** | Tasks needing explicit state tracking or fine‑grained mixing (e.g., formal language grammars, parity). | Tasks where sheer storage matters—large vocabularies, associative recall, rare token prediction, long context language modeling. |

In practice most large‐scale xLSTM models blend both: an architecture like **xLSTM[7:1]** stacks many mLSTM blocks for raw capacity while sprinkling occasional sLSTM blocks to give the network explicit state tracking abilities.

---  

## Takeaway  

The move from a scalar cell to a matrix memory isn’t just a cosmetic change; it fundamentally alters how an RNN stores and retrieves information:

* **Scalar sLSTM** keeps the classic LSTM’s simplicity but augments it with exponential gates and a normalizer so that past decisions can be revised on the fly.
* **Matrix mLSTM** brings fast‐weight associative memory into modern deep learning, allowing billions of parameters to act like an external key–value store while staying fully recurrent and linear in sequence length.

If your application struggles with rare words, long‐range dependencies, or needs an “infinite” associative cache, consider leaning on mLSTM’s matrix memory despite its heavier compute footprint. When you need tight control over state transitions—say for program execution or formal grammar parsing—sprinkle in some sLSTM blocks for their superior mixing capabilities.

The xLSTM paper shows that combining both yields models that match or outperform Transformers on large language modeling benchmarks while retaining linear time/space scaling. So yes, *memory truly matters*, and choosing between scalar and matrix memories gives you another powerful lever to push RNNs back into the spotlight.
