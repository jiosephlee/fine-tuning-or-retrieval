# Building xLSTM Blocks: Residual Connections, Up‑Projection, and Scaling to Billions of Parameters  

*In this post we walk through the core building unit of the new **xLSTM** family – the xLSTM block. We explain why residual stacking is crucial, compare the two up‑projection strategies (pre‑ vs. post‑), and show how these design choices let us train recurrent models with **linear‑time** complexity while keeping the expressive power of deep RNNs. All details are grounded in the “Extended Long Short‑Term Memory” paper.*  

---  

## 1. Why a New Block for LSTMs?  

The classic LSTM introduced in the early 1990s solved the vanishing‑gradient problem with a **constant error carousel** and three gates (input, forget, output). Despite decades of success, vanilla LSTMs still suffer from three practical limitations:  

1. **Irreversible storage decisions** – once a value is written to the scalar cell it cannot be easily overwritten later.  
2. **Limited capacity** – a single scalar per cell forces heavy compression, which hurts rare‑token prediction.  
3. **Sequential bottleneck** – hidden‑to‑hidden connections (the “memory mixing” step) prevent parallel computation across timesteps.  

xLSTM answers these problems by (i) using **exponential gating** (which lets gates grow or shrink multiplicatively without saturating), (ii) introducing richer memory structures (a scalar sLSTM and a matrix mLSTM), and (iii) embedding these cells inside **residual blocks with up‑projection**. The result: a recurrent architecture that scales like modern Transformers but retains the state‑tracking capabilities of RNNs.

---  

## 2. The Anatomy of an xLSTM Block  

An xLSTM block is a modular wrapper around either an **sLSTM** or an **mLSTM** cell. The block performs three high‑level operations:

1. **Non‑linear aggregation of past information** – the recurrent cell summarizes everything seen so far.  
2. **Projection to a higher dimension** – we lift the hidden representation into a space where linear separation of histories becomes easier (Cover’s theorem).  
3. **Residual shortcut** – the original hidden state bypasses the non‑linear path and is added back, stabilizing training for very deep stacks.

Visually, an xLSTM block looks like this:

```
input → [Recurrent cell] → Linear ↑ → Nonlinearity → Linear ↓ → + (residual) → output
```

The key design choice lies in **where** we apply the up‑projection (`↑`) and down‑projection (`↓`).  

### 2.1 Post Up‑Projection (sLSTM)  

- The recurrent cell first works **in its native dimensionality** (e.g., 1024).  
- After producing its hidden output `h_t`, we *project up* to a higher dimension `d_h` (`Linear ↑`), apply an activation (e.g., GeLU), then *project down* back to the original size before adding the residual connection.  

Why this order for sLSTM?  
- sLSTM retains **memory mixing** across cells, which is inherently sequential; keeping this mixing in the low‑dimensional space keeps the matrix multiplications cheap.  
- The subsequent high‑dimensional embedding only needs to separate *already mixed* histories, so a post‑up projection suffices.

### 2.2 Pre Up‑Projection (mLSTM)  

- For mLSTM we first *project up* the input before feeding it into the recurrent cell (`Linear ↑ → mLSTM`).  
- The matrix memory (`C_t ∈ ℝ^{d×d}`) lives in this expanded space; after the cell produces its output we *project down* (`Linear ↓`) and add the residual shortcut.  

Why pre‑up for mLSTM?  
- mLSTM’s memory is a full matrix; its capacity grows quadratically with the hidden size `d`. By moving to a larger space we give the covariance update rule more “room” to store distinct key–value pairs without hitting saturation early.  
- Because mLSTM has **no hidden‑to‑hidden mixing**, it can be parallelised across timesteps (the recurrence reduces to simple matrix scans). Placing the up‑projection before the recurrence preserves this parallelism.

## 3. Residual Stacking – From One Block to Billions of Parameters  

A single xLSTM block is powerful, but deep language models need dozens to hundreds of layers. The solution is straightforward: **stack blocks using pre‑LayerNorm residual connections**, exactly as modern Transformers do.

### 3.1 Pre‑LayerNorm Residual Path  

Each block follows the pattern

```
y = LayerNorm(x)
z = xLSTMBlock(y)
output = x + z
```

*Why LayerNorm first?*  
- Normalising before any non‑linear operation stabilises gradients across very deep stacks, preventing the explosion or vanishing that plagued early deep RNNs.  
- It also makes it easy to share hyperparameters (learning rate, weight decay) across all layers.

### 3.2 Mixing sLSTM and mLSTM Blocks  

The paper introduces a notation `xLSTM[a:b]` meaning “a parts mLSTM, b parts sLSTM”. For example, `xLSTM[7:1]` uses seven mLSTM blocks and one sLSTM block per 8‐layer segment. Empirically:

- **mLSTM dominates** because its matrix memory gives huge capacity while being parallelizable.
- A few **sLSTM blocks** improve state tracking by allowing memory mixing—useful for tasks that require explicit sequence state (e.g., code evaluation).

When scaling to billions of parameters, you typically keep a constant ratio (e.g., 7:1) and simply increase:
- Hidden dimension `d` (which enlarges both scalar and matrix memories),  
- Number of blocks `N` (deepening the stack), or  
- Model width via multi‑head configurations.

All three knobs increase parameter count roughly linearly while preserving *linear* training time with respect to sequence length, because each timestep still involves only one pass through the recurrent update plus two cheap linear projections.

---  

## 4. Linear‑Time Training Meets Expressive Recurrence  

Traditional RNNs already have linear time complexity (`O(T)` for sequence length `T`). What changes with xLSTM?  

| Component | Complexity w.r.t `T` | Comments |
|-----------|----------------------|----------|
| Recurrent update (`c_t`, `C_t`) | `O(T·d)` for sLSTM; `O(T·d²)` for mLSTM | Matrix ops are highly parallel on GPUs, keeping wall time low |
| Up/Down projection | `O(T·d·d_h)` | Done once per layer; `d_h` is chosen moderately larger than `d` |
| Residual addition & LayerNorm | `O(T·d)` | Negligible overhead |

Because every operation is a *scan* or a *batched matrix multiply*, GPUs can pipeline many timesteps together, yielding throughput comparable to linear Transformers such as GLA or RetNet while retaining true recurrence (no cache of past key/value pairs needed).  

Furthermore, exponential gating eliminates sigmoid saturation, so gradients flow without attenuation even over very long sequences—critical when training on billions of tokens.

## 5. Putting It All Together – A Minimal Code Sketch  

Below is a PyTorch‑style pseudo implementation that captures the core ideas:

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class XLSTMSBlock(nn.Module):
    def __init__(self, d_model, d_hidden, kind='m'):   # kind='s' or 'm'
        super().__init__()
        self.norm = nn.LayerNorm(d_model)
        self.kind = kind

        if kind == 's':                     # scalar sLSTM
            self.rnn = ScalarSLSTMCell(d_model)
            self.up   = nn.Linear(d_model, d_hidden)
            self.down = nn.Linear(d_hidden, d_model)
        else:                               # matrix mLSTM
            self.up   = nn.Linear(d_model, d_hidden)
            self.rnn = MatrixMLSTMCell(d_hidden)   # operates in high dim
            self.down = nn.Linear(d_hidden, d_model)

    def forward(self, x):
        y = self.norm(x)                     # pre‑LayerNorm
        y = self.up(y)                       # pre or post proj handled by ctor
        h = self.rnn(y)                      # recurrent step (scan internally)
        h = self.down(h)
        return x + h                         # residual add
```

A full model stacks many such blocks:

```python
class XLSTMLanguageModel(nn.Module):
    def __init__(self, vocab_sz, d_model=1024,
                 n_blocks=48,
                 ratio_m=7):                # e.g., 7:1 m:s ratio
        super().__init__()
        self.embed = nn.Embedding(vocab_sz, d_model)
        self.blocks = nn.ModuleList()
        for i in range(n_blocks):
            kind = 'm' if i % (ratio_m+1) != ratio_m else 's'
            self.blocks.append(XLSTMSBlock(d_model,
                                           d_hidden=2048,
                                           kind=kind))
        self.out = nn.Linear(d_model, vocab_sz)

    def forward(self, ids):
        h = self.embed(ids)
        for blk in self.blocks:
            h = blk(h)
        return self.out(h)
```

Training proceeds exactly like any autoregressive model: feed token IDs, compute cross‑entropy loss on next token predictions, and use AdamW with learning‑rate schedules common to LLM training.

## 6. Scaling Outlook – From Hundreds of Millions to Billions  

Empirical results from the xLSTM paper show:

| Tokens | Params | Validation PPL |
|--------|--------|----------------|
| 15 B   | 350 M | ~8.9 (best among Transformers/SSMs) |
| 300 B  | 1.3 B| ~6.3 (outperforms Llama 13 B and Mamba 1 B) |

Key observations:

- **Exponential gating + matrix memory** give consistent PPL gains across all scales.
- Even with modest hardware (single A100 GPU), training remains feasible because memory usage grows *constant* with sequence length.
- For inference, xLSTM’s linear scaling means generation time grows linearly with context size—unlike quadratic growth in vanilla Transformers—making it especially attractive for long prompts (>8k tokens).

---  

## 7. Takeaways  

1️⃣ **Residual stacking + up/down projection** gives deep recurrent networks stable gradients and high expressive power—mirroring what made Transformers so successful.

2️⃣ **Pre vs. post up‑projection** aligns with each variant’s strengths: keep sLSTM’s mixing cheap by projecting after recurrence; give mLSTM’s matrix memory room by projecting before recurrence.

3️⃣ **Linear-time training & inference** are retained despite adding sophisticated gating and memory structures; modern GPUs can handle the extra matrix operations efficiently.

4️⃣ When scaled to billions of parameters, xLSTM matches or exceeds state-of-the-art Transformers and State Space Models on language modeling benchmarks while preserving true recurrence—opening doors for tasks that demand explicit state tracking such as code execution or long‐range reasoning.
