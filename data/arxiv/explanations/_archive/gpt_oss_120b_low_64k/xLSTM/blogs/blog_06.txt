# Practical Tips for Training xLSTM Models on Real Data

In the past year the **xLSTM** family (sLSTM + mLSTM) has emerged as a strong alternative to Transformers and State‑Space Models for large‑scale language modeling. The paper *xLSTM: Extended Long Short‑Term Memory* shows that, once equipped with exponential gating, matrix memories and residual backbones, xLSTMs match or beat state‑of‑the‑art baselines even at the 1 B‑parameter scale.  

However, moving from a research prototype to a production‑grade model that processes billions of tokens uncovers a set of engineering hurdles. Below we distill the most useful lessons from the paper’s “Limitations” section, organize them into concrete recommendations, and add a few practical tricks that have proven helpful when training xLSTMs beyond 1 B parameters.

---

## 1. CUDA Kernels – Speed vs. Parallelism

### 1.1 mLSTM: Parallel but Heavy

* **What hurts speed?**  
  mLSTM stores a full matrix $\mathbf{C}\in\mathbb{R}^{d\times d}$ and updates it with a rank‑1 outer product $\mathbf{v}_t\mathbf{k}_t^\top$ each timestep. Although the operation can be expressed as standard matrix multiplications (hence parallelizable), the naïve kernels used in the reference implementation are roughly **4× slower** than highly tuned attention kernels such as FlashAttention.

* **How to mitigate?**  
  - **Fuse the update and decay:** Compute $f_t\mathbf{C}_{t-1} + i_t\,\mathbf{v}_t\mathbf{k}_t^\top$ in a single GEMM+AXPY kernel rather than two separate calls.  
  - **Leverage cuBLASLt / cuTensorCore:** When $d$ is a multiple of 8 or 16, enable tensor‑core math (`torch.cuda.amp.autocast`) to accelerate the $d\times d$ multiply.  
  - **Batch multiple timesteps:** For long sequences you can process small windows (e.g., 8–16 steps) with a custom scan kernel; this reduces kernel launch overhead while preserving the linear recurrence.

### 1.2 sLSTM: Memory Mixing Costs

* **Why is sLSTM slower?**  
  The hidden‑hidden connections required for memory mixing prevent straightforward parallelization; every step depends on the previous hidden state.

* **Practical workaround:**  
  The authors provide a fast CUDA implementation that keeps most data in registers and uses an in‑place scan (`torch.cumsum`). In practice this implementation is **≤ 2×** slower than mLSTM, which is acceptable for models where the scalar memory is crucial (e.g., tasks that need explicit state tracking).  
  - Profile with NVIDIA Nsight Systems to ensure the kernel stays compute‑bound rather than memory‑bound.  
  - If your application can tolerate losing explicit mixing, consider swapping sLSTM blocks for mLSTM blocks after a certain depth (the paper’s xLSTM[7:1] configuration does exactly that).

## 2. Gate Initialization – Stabilizing Exponential Gates

Exponential gating (`i_t = \exp(\tilde{i}_t)`, `f_t = \exp(\tilde{f}_t)`) dramatically increases expressivity but also introduces risk of overflow or vanishing gradients.

### Recommended Initialization Scheme

| Gate | Bias Initialization | Reason |
|------|--------------------|--------|
| Input gate $i_t$ | $\log(0.1)$ (≈ −2.3) | Starts with a small learning rate on new information; the stabilizer state `m_t` will quickly adapt if stronger updates are needed. |
| Forget gate $f_t$ | $\log(0.9)$ (≈ −0.1) if using exponential forget; otherwise sigmoid bias = +1 (≈ 0.73) | Guarantees gentle decay at the beginning of training, preventing runaway growth of $\mathbf{C}$ or scalar memory. |
| Output gate $o_t$ | $0$ (sigmoid bias = 0 → $o_t\approx0.5$) | Keeps hidden activations moderate until later layers learn useful gating patterns.

### Stabilizer State (`m_t`)

The paper introduces a stabilizer:
```python
m_t = max(log(f_t) + m_{t-1}, log(i_t))
i'_t = exp(log(i_t) - m_t)
f'_t = exp(log(f_t) + m_{t-1} - m_t)
```
Implement this directly in your forward pass (no extra parameters). It rescales both gates so that their product never exceeds numerical limits, while preserving exact gradients.

## 3. Managing Matrix Memory Size

The matrix memory dimension `d` determines both capacity and computational cost:

* **Memory capacity vs. compute:**  
  For language modeling, `d = √(hidden_dim)` works well (e.g., hidden size = 2048 ⇒ `d≈45`). This keeps $\mathbf{C}$ manageable (< 2 kB per layer) while still enabling rich key/value associations.

* **Scaling beyond 1 B parameters:**  
  - **Chunked memory:** Split $\mathbf{C}$ into several smaller blocks (e.g., four $d/2 \times d/2$ matrices) and treat each as an independent head. This reduces per‑kernel load and improves cache locality.
  - **Sparse updates:** If your hardware supports sparse matrix ops, apply dropout to outer‑product updates (`v_t k_t^T`) so only a fraction of entries are written each step; this leaves the “signal” intact while cutting FLOPs roughly proportionally to dropout rate.

* **Preventing overflow for long contexts:**  
  When processing sequences longer than those seen during training (e.g., > 16k tokens), monitor `||\mathbf{C}_t||_F`. If it grows beyond a preset bound (e.g., `10^4`), rescale both $\mathbf{C}_t$ and the normalizer $\mathbf{n}_t$ by a constant factor (`*0.5`) to keep retrieval numerically stable.

## 4. Mixed‑Precision Pitfalls

The authors trained all models in mixed precision but warned about instabilities for certain RNN variants:

* **Critical sections:**  
  - The stabilizer state `m_t` must be kept in **float32**; otherwise rounding errors can destroy the max operation and break gate scaling.
  - The matrix memory $\mathbf{C}$ can safely be stored in FP16 because it is only used inside GEMM kernels that internally up‑cast to FP32 on NVIDIA GPUs.

* **Loss scaling strategy:**  
  Use PyTorch’s native `torch.cuda.amp.autocast` combined with a static loss scale of `2^{15}` for early epochs, then switch to dynamic scaling once gradients stabilize.

* **Gradient clipping:**  
  RNNs are notorious for exploding gradients despite exponential gating’s stabilizer, so apply global norm clipping at `0.5`–`1.0`. This works well with AMP because clipping happens after loss scaling is removed.

## 5. Hyperparameter Tuning at Scale

Below are empirically validated defaults for models ≥ 1 B parameters; start from them before embarking on grid searches.

| Hyperparameter | Suggested Value | Why |
|----------------|-----------------|-----|
| Learning rate (AdamW) | $3\times10^{-4}$ → cosine decay | Larger LSTMs benefit from an initially higher LR because gating adapts quickly; cosine decay prevents overshooting later stages |
| Weight decay | $0.01$ | Regularizes both linear layers and projection matrices |
| Warmup steps | `$0.01 \times \text{total steps}` | Gives gates time to settle before aggressive updates |
| Dropout (attention & residual) | $0.1$–$0.15$ | Controls overfitting on long‑range dependencies |
| Number of heads (mLSTM) | `$d // head_dim`` where `head_dim = 64` | Keeps each head’s key/value vectors within a manageable size for efficient GEMM |
| Block composition (`xLSTM[a:b]`) | `7:1` for deep models (> 12 layers), `3:1` for shallow prototypes | More mLSTM blocks bring parallelism; a few sLSTM blocks preserve state‑tracking abilities |

**Tuning tip:** Increase the proportion of sLSTM blocks only when you observe systematic failures on “state tracking” synthetic tasks (e.g., parity or nearest‑neighbor search). Otherwise keep sLSTM to ≤ 10 % of total blocks to retain high throughput.

## 6️⃣ End‑to‑End Checklist

Before launching a multi‑billion token run:

1️⃣ Verify CUDA kernels: run a short benchmark (`torch.backends.cuda.enable_cudnn = True`) and confirm that mLSTM throughput is within ~75 % of FlashAttention on an equivalent tensor shape.

2️⃣ Initialize gates according to Table 2 and enable stabilizer logic.

3️⃣ Set matrix memory dimension `d` so that `$d^2 \leq$ ~10⁶` elements per layer (≈4 MiB at FP16).  

4️⃣ Enable AMP with FP32 stabilizer & FP16 memory; add gradient clipping (`max_norm=0.75`).  

5️⃣ Choose block composition `xLSTM[7:1]` for > 12 layers, otherwise start with `xLSTM[3:1]`.

6️⃣ Run a sanity check on a synthetic “Nearest Neighbor Search” task – make sure MSE drops below the baseline LSTM after ~10k steps.

7️⃣ Launch full‐scale training with cosine LR schedule, monitor both validation perplexity and the Frobenius norm of each $\mathbf{C}$ matrix; apply rescaling if norms exceed thresholds.

---

## Closing Thoughts

Training xLSTMs at scale is no longer an academic curiosity; with careful engineering they achieve competitive perplexities while retaining linear time/memory cost—an attractive proposition for edge deployment or any scenario where GPU memory is at a premium. By following these practical guidelines—optimizing CUDA kernels, initializing exponential gates safely, handling matrix memories efficiently, leveraging mixed precision wisely, and tuning hyperparameters deliberately—you can tame the complexity of xLSTMs and unlock their expressive power in real‑world language modeling projects.

Happy training! 🚀
