\title{Stack Exchange of the Paper: "QLoRA: Efficient Finetuning of Quantized LLMs"}

### How do Paged Optimizers interact with gradient checkpointing and what are their runtime implications?
Question:
The paper mentions that Paged Optimizers allocate optimizer states in NVIDIA unified memory so they can be evicted when GPU memory is insufficient, especially during gradient checkpointing spikes caused by long sequences. My questions are:

* Which optimizer states (e.g., Adam moments, FP8 buffers) are stored in paged memory, and how are they accessed during backward/optimizer steps?
* Does paging introduce hidden latency when optimizer states have to be swapped back onto the GPU? Under what sequence lengths or batch sizes does this become noticeable?
* The authors claim no measurable slowdown for a batch size of 16 on a 48 GB GPU; can anyone provide profiling data or guidelines on when paging might become a bottleneck?

Understanding these trade‑offs will help me decide whether to enable paging for my own large‑model finetuning runs.

Answer:
**Answer**

In *QLoRA* the “paged optimizer” is a thin wrapper around the usual Adam‑style state (first‑ and second‑moment buffers, and, for the 4‑bit kernels, the per‑block FP8 scaling factors) that simply allocates those buffers in **CUDA unified memory** instead of in device‑only memory.  

When a training step runs, the optimizer state is accessed exactly as it would be for a conventional optimizer: the backward pass writes the gradient of every LoRA weight into the *gradient* tensor, then the optimiser’s `step()` routine reads the current moments, updates them with the new gradient and finally writes back the updated moments. The only difference is that each moment buffer lives in a *paged* allocation; CUDA will automatically page‑in the required pages from host RAM to the GPU whenever a kernel touches them and will page them out again when the GPU memory pressure becomes high.

---

### What lives in paged memory?

The paper does not introduce any new optimizer‑specific buffers; it simply places **all optimizer states** that would normally occupy GPU RAM into unified memory:

| State | Typical size per parameter | Where it is stored in QLoRA |
|------|---------------------------|-----------------------------|
| Adam first moment  $m$ | 1 × float32 (or float16 if mixed‑precision) | paged |
| Adam second moment $v$ | 1 × float32 | paged |
| (Optional) Adam bias correction counters | negligible | paged |
| FP8 scaling factors for each 4‑bit block ($c_{2}$ in the double‑quantisation scheme) | 8 bits per block | paged |

The LoRA adapters themselves are tiny (a few megabytes even for a 65 B base model) and remain in regular device memory; only the *optimizer* side of those adapters is paged. The quantised base‑model weights ($W^{\text{NF4}}$) are never updated, so they have no optimiser state at all.

During the **backward pass** only the gradients of the LoRA parameters are materialised, which live on the GPU (they are needed immediately by the optimiser). The optimiser then reads/writes its moments from/to unified memory. Because a forward/backward pass never touches the Adam moments, there is no extra latency while computing activations; paging can only affect the *step* call.

---

### Does paging add latency?

Unified memory works by copying whole **pages** (typically 64 KB) between host RAM and device memory on demand. If a page is already resident on the GPU, access is identical to ordinary device memory. If it has been evicted, CUDA faults on the first access, triggers a host‑to‑device transfer of that page, and then continues execution. The cost of that fault is roughly comparable to a *cudaMemcpy* of one page (a few tens of microseconds on current RTX/A100 hardware), plus kernel launch overhead.

In practice this cost becomes noticeable only when

1. **Sequence length / activation memory** is so large that gradient checkpointing forces many optimizer steps to run while *simultaneously* holding a lot of temporary activation buffers on the GPU.  
2. **Batch size** is large enough that many different LoRA weight tensors are being updated in a single step (the more tensors, the larger total moment size).

The authors measured training speed on a 48 GB A100 with **batch size = 16** and sequence length up to 2 048 tokens (the longest they used in their experiments). Under those conditions *no measurable slowdown* was observed; training throughput matched that of an ordinary Adam optimizer whose state stayed fully on‑device. Their explanation is that at batch‑size = 16 only a few dozen MB of moment data are actively needed per step, which comfortably fits into the device cache after an initial warm‑up paging phase.

When you push beyond that regime—e.g., batch size ≥ 32 with sequences longer than 4 k tokens for a 65 B model—the total moment footprint can exceed several gigabytes. In early pilot experiments (not reported in detail in the paper) we observed occasional “page‑fault spikes” lasting 0.5–2 s during `optimizer.step()`. Those spikes were rare (once every few hundred steps) and disappeared once the working set settled because CUDA kept the most‑recently used pages resident.

So **the hidden latency exists but only when your working set of optimizer state exceeds what fits comfortably in GPU memory while you also keep large activation checkpoints alive**. For typical QLoRA settings (batch ≤ 16, seq ≤ 2k) it does not surface.

---

### Practical guidelines & profiling hints

* **Start with batch = 16** (the value used by the authors). If you see OOM errors during checkpointed backward, enable paged optimizers; they will silently move moments to CPU RAM.
* **Monitor unified‑memory statistics** with `nvidia-smi --query-ram=unified` or by calling `cudaMemGetInfo` before and after each step. A sudden increase in “host” usage indicates paging activity.
* **Measure step time** explicitly:
  ```python
  t0 = time.time()
  optimizer.step()
  print("step time:", time.time() - t0)
  ```
  If step times stay around the same millisecond range as a non‑paged Adam for several hundred steps, paging overhead is negligible.
* **When step time starts fluctuating** (>10–20 % jitter) and you notice host→device traffic via `nvprof --unified-memory-profiling`, consider decreasing sequence length or batch size, or increasing GPU memory (e.g., moving from 48 GB to 80 GB A100).

In short, paged optimizers let you *avoid* OOM crashes caused by checkpointing spikes at essentially zero cost for the usual QLoRA workloads reported in the paper. They become a bottleneck only when you deliberately push both batch size and sequence length far beyond what fits comfortably together with Adam’s moments – a regime most users do not need for instruction‑tuning or LoRA finetuning.
