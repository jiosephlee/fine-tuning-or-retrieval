# Dynamic Patching 101: How Entropy‑Based Byte Groups Make LLMs Faster

Large language models (LLMs) have traditionally relied on a **tokenizer** that maps raw bytes to a fixed vocabulary of sub‑word tokens. While this works well, every token – no matter how easy or hard to predict – incurs the same amount of computation in the transformer. The recent **Byte Latent Transformer (BLT)** flips that assumption on its head by grouping bytes into *patches* whose size is chosen *dynamically* based on how uncertain the next byte is. In this post we walk through the three patching strategies explored in the BLT paper—static stride, whitespace, and entropy‑based—show why entropy‑based patching shines, and quantify the inference‑flop savings it brings.

---

## Why “patches” instead of “tokens”?

- **Tokens** are pre‑computed groups of bytes (often 3–5 bytes on average) that a model treats uniformly.  
- **Patches** are groups created *on‑the‑fly* during data loading. Their length can vary from a single byte in a chaotic region to dozens of bytes in predictable text.
- The key insight: *Prediction difficulty is not uniform.* Predicting the first character of a new word, a code symbol, or a numeric expression is far harder than filling in the rest of an already‑known word. By allocating more transformer steps exactly where uncertainty spikes, we can keep overall compute low while preserving or even improving model quality.

---

## The three ways to slice a byte stream

### 1. Strided (static) patching – “k‑bytes per patch”

The simplest baseline groups every *k* bytes together, e.g. *k* = 4 or 6. This approach has two major drawbacks:

1. **No adaptivity:** A low‑entropy stretch (e.g., a long run of spaces) still forces the global transformer to run, wasting flops.
2. **Inconsistent tokenization:** The same word can be split differently depending on its position, breaking any notion of linguistic coherence.

Because the patch size is fixed, the number of transformer steps (`#patches = #bytes / k`) is easy to compute, but the efficiency gains are modest at best.

### 2. Whitespace (space) patching – “break after every space‑like byte”

Space patching improves on static stride by using *natural linguistic boundaries*. Whenever a space‑like byte (any non‑latin character, digit, or UTF‑8 continuation byte) appears, a new patch starts.

Pros:

- Guarantees that words stay intact across patches.
- Places more compute after spaces where next‑byte uncertainty typically peaks.

Cons:

- **Language bias:** Not all languages separate words with visible spaces (e.g., Chinese, Japanese).  
- **Fixed granularity:** All words receive the same amount of compute regardless of their internal difficulty; long technical terms still get just one patch.

### 3. Entropy‑based patching – “let uncertainty decide”

The most sophisticated strategy measures **next‑byte entropy** using a tiny auxiliary byte‑level language model (the *entropy model*). For each position *i* in the stream we compute

\[
H(x_i)= -\!\sum_{v\in\mathcal{V}} p_e(x_i=v \mid \mathbf{x}_{<i})\,
\log p_e(x_i=v \mid \mathbf{x}_{<i}),
\]

where \(p_e\) is the probability distribution over the 256 possible bytes predicted by the entropy model. High entropy means the model is unsure about what comes next; low entropy indicates predictability.

Two practical heuristics turn this scalar field into patch boundaries:

| Heuristic | Formula | Intuition |
|-----------|---------|-----------|
| **Global threshold** | \(H(x_t) > \theta_g\) | Whenever entropy exceeds a fixed cut‑off we start a new patch. |
| **Monotonicity check** | \(H(x_t)-H(x_{t-1}) > \theta_r\) | Detects sharp jumps in uncertainty within an otherwise smooth region (e.g., moving from “the ” to “c”). |

During data loading we scan the byte stream once, flagging boundary positions that satisfy either rule. The result is a *variable‑length* patch sequence where easy stretches collapse into long patches and hard stretches are broken into many short ones.

#### Why entropy works better than heuristics

- **Data driven:** The entropy model has actually seen the training distribution, so its uncertainty reflects real statistical difficulty rather than hand‑crafted rules.
- **Fine granularity:** Even inside a word, rare suffixes or domain‑specific symbols trigger new patches.
- **Language agnostic:** No reliance on spaces, so scripts without explicit word delimiters are handled naturally.

---

## From entropy to flop savings

The total forward/backward FLOPs for BLT are dominated by three components:

1. **Local encoder/decoder** – lightweight byte‑level transformers that run on every byte (constant cost per byte).
2. **Cross‑attention** – bridges bytes and patches; cost scales with `#patches`.
3. **Global latent transformer** – large autoregressive model that processes *only* patches; cost scales with `#patches`.

If `n_ctx` is the number of bytes in context and `n_p` is the average patch size, then `#patches = n_ctx / n_p`. The global transformer FLOPs per byte roughly become

\[
\text{FL}_{\text{global}} \propto \frac{1}{n_p}.
\]

Thus *doubling* the average patch size cuts global FLOPs in half while leaving the local encoder/decoder cost unchanged.

### Quantitative findings from BLT

| Patch strategy | Avg. patch size (bytes) | Inference FLOPs ↓ vs token baseline |
|----------------|------------------------|--------------------------------------|
| Strided k=4    | 4                      | ~10 % |
| Space          | 6                      | ~30 % |
| Entropy (monotonic) | 4.5               | ~45 % |
| Entropy (high threshold → larger patches) | 8 | ~50 % |

The paper reports up to **50 % fewer inference FLOPs** for entropy‑patched models while maintaining performance comparable to Llama 3 (a state‑of‑the‑art tokenizer‐based LLM). Importantly, these savings do not come from reducing model size; instead they free up FLOPs that can be reinvested into making the global latent transformer deeper or wider—leading to better scaling without sacrificing latency budgets.

## Putting it all together: The BLT pipeline

```
raw bytes ──► entropy model computes H(x_i)
                │
                └─► dynamic patch boundaries → patches
                        │
   ┌────────────────────┴─────────────────────┐
   │                                          │
Local Encoder (lightweight)            Local Decoder (lightweight)
   │                                          │
Patch representations ──► Global Latent Transformer (big)
   │                                          │
   └─────────────────────► Reconstruct bytes──► output
```

During generation, the model first decides “Am I at a patch boundary?” using the same entropy criterion applied incrementally (the decision depends only on past bytes). If yes, it invokes the expensive global transformer; otherwise it proceeds with only cheap local modules.

---

## Final thoughts

Entropy‑based dynamic patching shows that we can move away from rigid token vocabularies without paying an exorbitant compute price. By letting *predictive uncertainty* dictate where heavyweight processing occurs, BLT achieves:

- **Significant inference‐flop reductions** (up to 50 %).
- **Better scaling**: larger models can be trained within a fixed inference budget by simply increasing average patch size.
- **Improved robustness**: raw byte access preserves orthographic details that tokenizers discard, helping with noisy inputs and low‑resource languages.

The take‑away for practitioners is clear: if you’re building an LLM for domains where latency matters—or if you want a model that gracefully handles any script—consider an entropy‑driven patching front end. It’s a small change in preprocessing that unlocks big gains downstream.
