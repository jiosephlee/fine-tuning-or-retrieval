\title{Stack Exchange of the Paper: "Byte Latent Transformer: Patches Scale Better Than Tokens"}

### Why does the paper claim that BPE tokenizers cannot satisfy the incremental patching property?
Question:
In Section 2.5 the authors define incremental patching as $f_p(\mathbf{x}_{<i}) = f_p(\mathbf{x})_{<i}$ and say BPE violates this because the same prefix can be tokenized differently depending on future bytes. Could someone give a concrete example with a short string that shows this behavior? Additionally, is there a known modification (e.g., using a delimiter token) that makes BPE incremental, and what would be the trade‑offs of such a modification?
Answer:
**Answer**

The incremental‑patching property requires that the sequence of *patches* that we obtain from a prefix of the input is exactly the prefix of the patch sequence we would obtain from the full input.  
Formally, for a patching function \(f_{p}\),

\[
f_{p}(\mathbf{x}_{<i}) \;=\; \bigl(f_{p}(\mathbf{x})\bigr)_{<i}\qquad\forall i .
\]

If this holds we can decide, while we are reading the bytes, whether a new patch begins or not – we never have to look ahead.

BPE (byte‑pair‑encoding) violates the equation because the way it groups the first few bytes depends on what comes **after** those bytes.  Below is a minimal concrete illustration that follows exactly the tokenizer used in the paper (the Llama 3 BPE vocabulary of size 128 K).

---

### A concrete example

Consider three short strings that share the same three‑byte prefix:

```
s₁ = "ab"
s₂ = "abc"
s₃ = "abx"
```

Suppose the BPE vocabulary contains the following tokens (these are realistic for a large‑vocabulary BPE):

| token | byte sequence |
|-------|---------------|
| `ab`  | 0x61 0x62 |
| `abc` | 0x61 0x62 0x63 |
| `a`   | 0x61 |
| `b`   | 0x62 |
| `c`   | 0x63 |
| `x`   | 0x78 |
| …     | … |

Now run the standard greedy BPE algorithm on each string:

* **Tokenising `s₁ = "ab"`**  
  The longest matching token at the first position is `ab`.  
  → token sequence = `[ab]`.

* **Tokenising `s₂ = "abc"`**  
  At position 0 the longest match is now `abc`, because three bytes are available.  
  → token sequence = `[abc]`.

* **Tokenising `s₃ = "abx"`**  
  The longest match at position 0 is again `ab`; after that we are left with `x`.  
  → token sequence = `[ab, x]`.

Now look at the *prefix* consisting only of the first two bytes, i.e. the byte string “ab”.  
If we apply \(f_{p}\) to this prefix (ignoring what follows) we obtain

\[
f_{p}("ab") = [ab].
\]

But this is **not** always a prefix of the full tokenisation:

* For `s₁` it is: `[ab]` is exactly the whole token list → property holds.
* For `s₂` it is *not*: `[ab]` is **not** a prefix of `[abc]`. The full tokenisation has merged the third byte into a larger token, so the patch boundary that would have been placed after “ab” disappears.
* For `s₃` it *is* a prefix: `[ab]` precedes `[x]`.

Thus, depending on what byte follows “ab”, that same two‑byte prefix can be split into one patch (`[ab]`) or be merged into a longer patch (`[abc]`). The mapping from bytes to patches is therefore *non‑incremental*.

The same phenomenon occurs with any BPE vocabulary that contains multi‑byte tokens overlapping shorter ones – which is precisely why BPE was designed as a compression scheme: it prefers longer merges when possible. Consequently, you cannot decide locally (from a prefix only) whether a new patch starts.

---

### Making BPE incremental

The paper mentions one simple way to recover incrementality: **insert an explicit delimiter token after every patch**. Concretely, you could augment the vocabulary with a special “\(\langle\text{patch}\rangle\)” symbol and post‑process every BPE output so that after each ordinary token you insert this delimiter. When generating, you stop reading bytes once you have emitted a delimiter; no future bytes are needed to know where the current patch ends.

**Effect of this modification**

| Aspect | With delimiter (incremental) | Original BPE (non‑incremental) |
|--------|-----------------------------|--------------------------------|
| **Byte‑to‑patch determinism** | Each byte decides locally whether it ends a patch (the delimiter tells you). | Patch boundaries may shift when more bytes become visible. |
| **Sequence length** | Increases because every token is followed by an extra symbol; average length grows roughly by a factor \(1+\frac{1}{\text{average tokens per segment}}\). In practice for Llama 3’s average 4‑byte token, length increases by ≈ 25 %. | Minimal overhead – only the tokens themselves. |
| **Model cost** | Larger input dimension for both embedding and final projection layers (the delimiter adds one more entry to the vocabulary). More decoding steps overall because each original token now occupies two steps in the transformer. | Smaller embedding table; fewer transformer steps per byte‑stream. |
| **Compatibility with existing checkpoints** | Not compatible – you would need to re‑train or fine‑tune with the new token set. | Directly reusable with pre‑trained checkpoints. |
| **Benefit for BLT‑style dynamic compute** | Enables true incremental patching, so at generation time you can decide “do I need to invoke the latent transformer?” without peeking ahead. This matches the assumption of Section 2.5 and lets BLT keep its flop‑control guarantees. | You cannot safely make that decision; you would have to run a look‑ahead predictor or accept occasional mis‑patches. |

In practice, adding a delimiter doubles the number of *patch decisions* that must be made by the model, which erodes part of BLT’s efficiency gains. The paper therefore prefers genuine dynamic patching (entropy‑based or whitespace) that already satisfies incrementality without an artificial overhead.

---

### Summary

*BPE’s greedy longest‑match rule makes its token boundaries depend on future bytes; therefore identical prefixes can be tokenised differently once more context arrives, violating incremental patching.*  
A simple fix—adding an explicit delimiter token after every BPE unit—restores incrementality but at non‑negligible cost in sequence length and model parameters. The BLT authors opt instead for true byte‑level patching schemes (entropy or whitespace) that are naturally incremental and avoid those trade‑offs while still allowing dynamic allocation of compute.*
