# Finetuning LLMs on a Single GPU: Meet QLoRA

For almost every large language model (LLM) you’ve read about it’s still a bit of a moonshot to *fine‑tune* it once you’ve got more than a handful of books into your GPU’s memory. Even clan‑size community members who want to tailor models for a specific task often end up waiting days on expensive cloud clusters.  
**QLoRA** flips that story on its head. By tightly coupling three careful engineering tricks—compressing the base model to 4 bits with an information‑theoretic data type, using low‑rank adapters instead of updating every weight, and letting an operating system skeleton alleviate memory spikes—it becomes possible to train even a 65‑B parameter model on a single 48‑GB NVIDIA card while keeping prediction quality right where it would have been if you had used full‑precision weights.

Below is a light‑weight walk through why this works and what it means for curious researchers and docker‑hobbyists alike.

---

## The Fundamental Problem

*Typical fine‑tuning* of an LLM boils down to storing two large tensors in RAM:

1. **The entire base network** – for LLaMA 65 B it already occupies **~780 GB** in 16‑bit precision.
2. **Gradients and optimizer states** – another bulk of memory that can spike during back‑propagation with long contexts or when gradient checkpointing kicks in.

The bottleneck isn’t really the compute; it’s simply the sheer weight because GPUs today have at most ~48 GB of VRAM. Even “lightweight” parameter‑efficient methods like LoRA still carry heavy activation gradients unless we find clever ways to shrink those tensors *without* drowning out signal fidelity.


---

## QLoRA’s Three Pillars

### 1. 4‑bit NormalFloat (NF4)

Most prior work turns model weights into integers or floating points in fewer bits, but those schemes just minimize bit usage—they don’t always match what the original data practices needed.  
NLF4 comes from *quantile quantization*: if weights are roughly normal **N(0, σ)** then dividing their range into equal–probability bins gives an optimal discretisation.  

- **Step 1:** Estimate the quantiles of a unit normal distribution once offline—say `q_i = (Q( i/(2^k+1) ) + Q( (i+1)/(2^k+1) )) / 2`.  
- **Step 2:** Scale them into the fixed interval `[−1,+1]`.  
- **Step 3:** When we load a weight tensor `W`, we rescale its *absolute maximum* into `[−1,+1]` before mapping each value onto its nearest `q_i`.  

Because zero is exactly represented and all bins carry equal probability mass, NF4 retains more “information per bit” than plain int8 or fpmacros used elsewhere. Empirically NF4 matches full-precision results where plain FP4 or INT4 would drop ~0.5–1 % accuracy.



### 2. Double Quantization

In block-wise quantization every block carries its own scale factor `c`. In naive 32-bit floats this means adding **0.5 bits/param** overhead when block size is only 64—a hefty bill over billions of weights.  

Double Quantization removes that cost by *quantizing* those `c` values themselves:

| Layer | C type | Block size | Bits per param |
|-------|--------|------------|----------------|
| Base weight | NF4 | 64 | ~0.125 |
| Scale `c` | FP8 loosely stored | 256 | ~0.004 |
| Root scale `c_root` | FP32 | – | negligible |

You end up shaving roughly **0.37 bits per parameter**, which translates to almost **3 GB less VRAM** for the flagship model.



### 3. Paged Optimizers

When training few-shot tasks or long conversations even with checkpointing, gradient accumulation can blast VRAM spikes that temporarily exceed capacity—even if the *average* memory stays within limits. NVIDIA’s Unified Memory lets us allocate optimizer states into “paged” space that spills onto host RAM when needed, then resurfaces when an update phase begins.

In practice this technique behaves like transparent “ghosting” of hard-to-pay money fragments: you see no slowdown most of the time (speed legally equals non-paged optimizers), but you recover from sudden checksums that would otherwise kill training.



---

## Low-Rank Adapters – Keep Only What You Need

The backbone innovation behind *parameter efficient fine-tuning* is *LoRA*. Instead of updating millions of tensor elements we add:

\[
\mathbf{Y} = \mathbf{X}\mathbf{W} + s\,\mathbf{X}\mathbf{L}_1\mathbf{L}_2,
\]

where `W` stays frozen and only two tiny matrices `L_1`, `L_2` and scalar `s` get updated during backpropagation.

QLoRA applies LoRA at **every linear module** inside each transformer block—query/key/value projections as well as feed-forward matrices—and uses generous `r` values so gradients are directed precisely where learning matters most.
For LLaMA 65 B this still doubles runtime per step versus pure inference but keeps activation gradients feasible because they propagate through compressed kernels rather than fully recomputed high-dimensional tensors.



---

## Why It All Works Together

1. **Compression + PyTorch BFloat16 Arithmetic**  
   Weight kernels are first loaded as NF4 → dequantised → BFloat16 → evaluated → re-quantised if needed for backproplying through the frozen layer.
2. **Seeded Precision Guarantees**  
   Theoretical analysis shows NF4 closes any precision gap relative to naïve FP8 or int8 after adapter training—a vital guarantee because we never directly modify base parameters.
3. **Super Abundant Adapters**  
   Since adapter memory lives far below GPU thresholds (~75 MB out of ~48 GB), coding around regular LoRA hyperparameters continues to yield nearly identical results as full weight fine-tuning – provided we insert an adapter everywhere and keep an appropriate learning rate schedule.
4. **Memory Yield ⟹ Feasible Scalability**  
   For instance, LLaMA 65 B now requires only ~48 GB total during QLoRA training—a path previously limited to server‐grade pipelines for >780 GB VRAM machines.

## Beyond Numbers – A Release That Close the Chatbot Gap

Running these tricks on real data produced the **Guanaco** family:

| Model | Base Params | Training Time @ 24/48 GB GPU | Relative Score vs ChatGPT (Vicuna Benchmark) |
|-------|-------------|------------------------------|---------------------------------------------|
| Guanaco 7 B | 7 B | <12 h single consumer GPU | ≈ 80% |
| Guanaco 33 B | 33 B | <24 h single consumer GPU | ≈ 95% |
| Guanaco 65 B | 65 B | <24 h single professional GPU | ≈ 99% |

The best Guanaco reached almost chat‑GPT parity in both quantitative tests (MMLU accuracy drop <3%) and head-to-head Elo tournaments against commercial systems wrapped around GPT–4 evaluation code—an effort far less heavy-weight than contractor bills for reinforcement learning knobs.

## Quickstart Guide & Practical Tips

```bash
# After cloning repo
pip install -r requirements.txt
# Convert your pretrained checkpoint into NF4
python tools/convert_nf4.py --model llama --save_path llama_nf4
# Launch training
python scripts/train_qlora.py \
    --model_path llama_nf4 \
    --dataset oasst-v1 \
    --adapter_size r=64 \
    --learning_rate 3e-5 \
    --batch_size 8 \
    --epochs 3 \
    --use_paged_optimizer
```

**What else?**

* Use mixed–precision (`bf16`) throughout except for stored weights/concepts.
* For GPUs below 24 GB adapt blocksize upwards (128 blocks → less constants).
* Keep learning‑rate scaling: halving LR on every doubling-size jump retains stability.

## Final Thoughts – Democratizing Dialogue Models

Put simply: with QLoRA you turn technology that once looked like only large cloud stacks can host into an everyday lab setup:

- New‐budding research labs can tune their favorite open crown jewels without pricey multiprocessing.
- Hobbyists who bought a RTX‑3080 now can run code close enough to GPT–3 quality locally.
- Edge scenarios might even live with tiny fractions of frozen models plus split–client adapters – something very reminiscent of app‑store modding where code stays small but behaviour adapts deep inside your pocket phone.

Let’s celebrate this bleeding-edge shift that unshackles millions from infrastructure constraints while still sinking state-of-the-art performance directly into the open web stack—one compression trick at a time!
