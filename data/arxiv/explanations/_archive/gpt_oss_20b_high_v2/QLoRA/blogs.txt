# Finetuning LLMs on a Single GPU: Meet QLoRA

For almost every large language model (LLM) you’ve read about it’s still a bit of a moonshot to *fine‑tune* it once you’ve got more than a handful of books into your GPU’s memory. Even clan‑size community members who want to tailor models for a specific task often end up waiting days on expensive cloud clusters.  
**QLoRA** flips that story on its head. By tightly coupling three careful engineering tricks—compressing the base model to 4 bits with an information‑theoretic data type, using low‑rank adapters instead of updating every weight, and letting an operating system skeleton alleviate memory spikes—it becomes possible to train even a 65‑B parameter model on a single 48‑GB NVIDIA card while keeping prediction quality right where it would have been if you had used full‑precision weights.

Below is a light‑weight walk through why this works and what it means for curious researchers and docker‑hobbyists alike.

---

## The Fundamental Problem

*Typical fine‑tuning* of an LLM boils down to storing two large tensors in RAM:

1. **The entire base network** – for LLaMA 65 B it already occupies **~780 GB** in 16‑bit precision.
2. **Gradients and optimizer states** – another bulk of memory that can spike during back‑propagation with long contexts or when gradient checkpointing kicks in.

The bottleneck isn’t really the compute; it’s simply the sheer weight because GPUs today have at most ~48 GB of VRAM. Even “lightweight” parameter‑efficient methods like LoRA still carry heavy activation gradients unless we find clever ways to shrink those tensors *without* drowning out signal fidelity.


---

## QLoRA’s Three Pillars

### 1. 4‑bit NormalFloat (NF4)

Most prior work turns model weights into integers or floating points in fewer bits, but those schemes just minimize bit usage—they don’t always match what the original data practices needed.  
NLF4 comes from *quantile quantization*: if weights are roughly normal **N(0, σ)** then dividing their range into equal–probability bins gives an optimal discretisation.  

- **Step 1:** Estimate the quantiles of a unit normal distribution once offline—say `q_i = (Q( i/(2^k+1) ) + Q( (i+1)/(2^k+1) )) / 2`.  
- **Step 2:** Scale them into the fixed interval `[−1,+1]`.  
- **Step 3:** When we load a weight tensor `W`, we rescale its *absolute maximum* into `[−1,+1]` before mapping each value onto its nearest `q_i`.  

Because zero is exactly represented and all bins carry equal probability mass, NF4 retains more “information per bit” than plain int8 or fpmacros used elsewhere. Empirically NF4 matches full-precision results where plain FP4 or INT4 would drop ~0.5–1 % accuracy.



### 2. Double Quantization

In block-wise quantization every block carries its own scale factor `c`. In naive 32-bit floats this means adding **0.5 bits/param** overhead when block size is only 64—a hefty bill over billions of weights.  

Double Quantization removes that cost by *quantizing* those `c` values themselves:

| Layer | C type | Block size | Bits per param |
|-------|--------|------------|----------------|
| Base weight | NF4 | 64 | ~0.125 |
| Scale `c` | FP8 loosely stored | 256 | ~0.004 |
| Root scale `c_root` | FP32 | – | negligible |

You end up shaving roughly **0.37 bits per parameter**, which translates to almost **3 GB less VRAM** for the flagship model.



### 3. Paged Optimizers

When training few-shot tasks or long conversations even with checkpointing, gradient accumulation can blast VRAM spikes that temporarily exceed capacity—even if the *average* memory stays within limits. NVIDIA’s Unified Memory lets us allocate optimizer states into “paged” space that spills onto host RAM when needed, then resurfaces when an update phase begins.

In practice this technique behaves like transparent “ghosting” of hard-to-pay money fragments: you see no slowdown most of the time (speed legally equals non-paged optimizers), but you recover from sudden checksums that would otherwise kill training.



---

## Low-Rank Adapters – Keep Only What You Need

The backbone innovation behind *parameter efficient fine-tuning* is *LoRA*. Instead of updating millions of tensor elements we add:

\[
\mathbf{Y} = \mathbf{X}\mathbf{W} + s\,\mathbf{X}\mathbf{L}_1\mathbf{L}_2,
\]

where `W` stays frozen and only two tiny matrices `L_1`, `L_2` and scalar `s` get updated during backpropagation.

QLoRA applies LoRA at **every linear module** inside each transformer block—query/key/value projections as well as feed-forward matrices—and uses generous `r` values so gradients are directed precisely where learning matters most.
For LLaMA 65 B this still doubles runtime per step versus pure inference but keeps activation gradients feasible because they propagate through compressed kernels rather than fully recomputed high-dimensional tensors.



---

## Why It All Works Together

1. **Compression + PyTorch BFloat16 Arithmetic**  
   Weight kernels are first loaded as NF4 → dequantised → BFloat16 → evaluated → re-quantised if needed for backproplying through the frozen layer.
2. **Seeded Precision Guarantees**  
   Theoretical analysis shows NF4 closes any precision gap relative to naïve FP8 or int8 after adapter training—a vital guarantee because we never directly modify base parameters.
3. **Super Abundant Adapters**  
   Since adapter memory lives far below GPU thresholds (~75 MB out of ~48 GB), coding around regular LoRA hyperparameters continues to yield nearly identical results as full weight fine-tuning – provided we insert an adapter everywhere and keep an appropriate learning rate schedule.
4. **Memory Yield ⟹ Feasible Scalability**  
   For instance, LLaMA 65 B now requires only ~48 GB total during QLoRA training—a path previously limited to server‐grade pipelines for >780 GB VRAM machines.

# Cracking the 4‑bit Code: NF<sub>4</sub> Quantization Explained  

Large language models need a lot of memory, but you don’t have to give up their size to fit them on consumer GPUs.  
Enter **QLoRA** – a method that keeps a gigantic model inside a single 48‑GB card by turning all its weights into a *four‑bit* representation while training only tiny *LoRA adapters*.  
At the heart of this breakthrough is **NormalFloat (𝑁𝐹₄)**, a four‑bit data type that is *information‑theoretically optimal* for normally distributed weights, plus a clever “double‑quantization” trick that slims memory even further without hurting performance.  

> Who says you need full precision? Thousands of models trained today use two to three times less GPU memory than before – all while matching or beating full‑precision baselines.

---

## Why Ordinary Float or Integer Quantization Fall Short

Quantizing weights means replacing high‑precision values (usually FP32 or BF16) with a small set of codes—e.g., eight int8 bins or sixteen float16 bins.  
The typical recipe is:

1. **Choose a large block** of parameters (say 64 elements)
2. **Find an overall scale** `c` that maps the block’s range into the chosen low‑precision space  
   \[
   X^{\text{Int8}}=\text{round}\!\Bigl(\frac{127}{\left|\!\!|X|\!\!\right|_{\max}}\,X\Bigr)
   \]
3. **Store** the tiny integer tensor and its scale `c`.

The problem?  
Because real LLM weights are *normally distributed* around zero (`~N(0,\sigma)`), most numbers cluster near the center while occasional outliers stretch far into the tails.  
A fixed uniform scale forces many tiny numbers into one bin (tiny bin loss) and leaves large values spread thinly across a few bins (large bin loss).  With too few bits you can’t serve both extremes well—so accuracy suffers when you finetune through those coarse buckets.



---  

## Meet NormalFloat (𝑁𝐹ₖ): Bits Designed for a Normal Distribution

Instead of imposing an arbitrary uniform grid, NormalFloat builds the bin boundaries around **exactly** how many samples fall in each segment if your data were drawn from a standard normal distribution `N(0,1)`.  

### Building a four‑bit NormalFloat

1. Pick `k = 4` → We need \(2^k = 16\) distinct codes.
2. Compute the theoretical \(2^k+1 = 17\) equi‑probable quantiles of `N(0,1)`:
   \[
   q_i=\frac{1}{2}\!\bigl(Q\!(i/17)+Q\!((i+1)/17)\bigr),\quad i=0,\dots ,15,
   \]
   where \(Q(\cdot)\) is the normal inverse CDF.
3. These `q_i` give us mids **but not zero**—the exact value `0` only exists once in an asymmetric set.
4. Merge positive and negative halves into an **asymmetric** range \([-1,1]\):  
   *10* negative codes, *6* positive codes, everything symmetrically spaced around zero—and ensure one explicit zero code exists so padding stays exact.

*Result:* each code represents exactly \(1/16\) probability mass under `N(0,1)`. That’s why it’s mathematically optimal – it reduces entropy loss per bit.



### When You Apply It

Before storing any weight block:

1. **Rescale** its absolute maximum so its values sit inside `[−1 , +1]`.  
   That is equivalent to “normalize \(\sigma\)” so that after rescaling every weight has exactly the same distribution shape as our NormalFloat design.
2. Quantize using the precomputed `q_i` lookup—no heavy per‑tensor statistic needed.
3. Store both integers (the four bits per weight) *and* a small float scale `c`.

During training / inference you immediately dequantize back into BF16 for arithmetic; adapters receive gradients directly through these dequantized blobs.



---  

## Why NF<sub>4</sub> Beats Regular Int<sub>4</sub> / FP<sub>4</sub>

- **Empirical evidence** from billions‑of‑parameter baselines (OPT/LLAMA/BLOOM/Pythia):
  * Zero‑shot perplexity drops by ~10–20% vs Int<sub>4</sub>.  
  * MMLU accuracy aligns perfectly with full‑precision fine‐tuned results when coupled with LoRA adapters.
- **Theoretical intuition:** All bins have equal expected counts for normally distributed weighting – fewer unused bins → lower effective noise per element.
- In practice it lets QLoRA recover full sixteen‑bit performance even when only adapters are updated—a huge win when you can’t afford to update the entire network.



---  

## Double Quantization – Two Layers of Congestion Relief

Every base block needs its own scaling constant `c₂`. Even if each constant is stored in full FP32, together they add roughly \(0.5\) bits per parameter just because of many blocks – ~3 GB extra on a 65 B model!  

Double Quantization brings another layer:

```
┌─ c₁ : FP32      ──┐
│                  │
└─ c₂ : FP8         │   ← second-level scalars
                  WeightBlock : NF₄
```

1. Encode each first‐level scalar `c₁` with normal scaling as before; store them as HF8 after subtracting their mean (mean centering because they're always positive).
2. Store these eight‑bit values along with small second‐level scalars (`c₂`) in every block’s metadata.
3. When you dequantize:
   * First convert dequantized float from `c₂`;
   * Then multiply by the dequantized weight `[NF₄]`.

***Result*** – average memory per parameter drops from ~0.5 bits to just ~~0.127 bits, i.e., **≈ 0½ bits save per param**, or ~3 GB saved on top of already seen reductions.



---  

## How QLoRA Uses NF<sub>4</sub> & Double Quantization

| Stage               | Operation                                                                                  | Data type          |
|---------------------|--------------------------------------------------------------------------------------------|--------------------|
| Weight loading      | Dequantize stored NF<sub>4</sub> block + first/second scales                                 | BF16 (for compute) |
| Forward pass        | Matrix multiply + add LoRA update [\(XW + X L_1L_2\)]                                       | BF16               |
| Backward pass       | Gradients flow through dequantized base – only LoRA matrices receive updates                | BF16               |
| Optimizer state     | Stored via paged allocator → spills extra peak memory automatically                        | N/A                |

Because adapters are low‑rank (~[h→r→o] factors), they capture just enough extra capacity while keeping parameter count down to < 2% of the base size—yet they lift expressive power back up right where you cared most.



---  

## Results That Prove It Works

| Model Scale | Baseline Finetune | QLoRA (𝑁𝐹₄) | Performance Gap |
|-------------|-------------------|--------------|----------------|
| LLaMA 7B   | Full BF16         | ≈ same       | < 0%           |
| LLaMA 33B – 65B | Full BF16 impossible (needs >780 GB) | ✅ matches     | ≈ 0%           |

Across every benchmark visited in the paper—GLUE, MMLU, Vicuna prompts—QLoRA with NF<sub>4</sub> achieved accuracy within one percentile point of fully trained rivals while never exceeding GPU limits that would otherwise rule out training at all.



---  

## Take Two & Three: Implications Beyond Memory Savings

* **Training speed** – Dequantizing during forward passes costs nothing apart from bandwidth; adapters still get concise gradients so updates remain fast (~10–15% slower than float32 due <10× smaller LR needs).  
* **Device reachability** – A consumer RTX 3080 or even smartphone GPU can now train models ≥33 B once you set up pagination tricks; publication proved “7B trains in <12h on one GPU”.
* **Security & privacy** – Because adapters contain all expertise learned during finetuning while base stays frozen & quantized offline, one can ship pretrained kernels separately from user data––a clean split between front end & privacy safe containers.



---  

## TL;DR

* Large language models’ weights follow an almost perfect Gaussian curve → classic bit‐packing loses excessive precision at tails.
* **NormalFloat (𝑁𝐹ₖ)** uses theoretical normal quantiles to allocate equal probability mass per bin → mathematically optimal for Gaussian data → little noise added when we shrink to four bits.
* Trivial extra step (**Double Quantization**) crams down pointer overhead from blockwise scaling down by ~¾ bit per param → saves several gigabytes worth of GPU mem without hurting throughput or quality.
* When paired with LoRA adapters we form **QLoRA**, which finetunes massive (~65B) models on single GPUs while preserving cutting‑edge inference quality nearly identical to full-fine-tuned BF16 versions.

So next time someone asks whether you can drop precision without breaking your chatbot's brainpower… say “Tell me more about NormalFloat!”



# Adapter Layers Redefined  
## How Low‑Rank LoRa Lets Massive Models Be Fine‑Tuned On a Single GPU  

Large language models (LLMs) have become the workhorse behind everything from autocomplete assistants to scientific simulation drivers.  
The problem is *how* you improve one… You can re‑train every single weight, but that easily spills out over hundreds of gigabytes of GPU RAM—a luxury most researchers don’t have left over for ink‑drenched training loops again or newer architectures.  

Enter **Low‑Rank Adapter Networks**, or **LoRa** _(short for *Low‑rank Adaptation*)_.  
Traditionally they let you tweak a model while speaking **few terabytes** less—to roughly **just a few megabytes**—by injecting tiny extra matrices into each linear projection rather than learning fresh copies of the massive weight tensors themselves.  

Below I’ll unpack exactly how this works inside a transformer encoder/decoder layer, why the whole network needs an adapter at *every* block if you want top‑line performance, and how **QLoRa** tames low‑bit quantization loss back into sweet \(80–95\,\%\) status.


-----------------------------------------------------------------------

### The Linear Projection Inside a Transformer Block  

Every transformer layer boils down—at its core—to several matrix multiplies of the form  

\[
    \mathbf Y = \underbrace{\mathbf X}_{(b\times h)}\,\underbrace{\mathbf W}_{(h\times o)} ,
\]

where \(b\) denotes batch size, \(h\) hidden size, \(o\) output size and \(h=o=512…,2048…,\) depending on the model scale (e.g., \(h=2048\) for most recent LLaMA variants).  
In multi‑head attention there are four such projections per head: *Q*, *K*, *V*, *O*.  
In feed‑forward nets two matrices apply—the first expands hidden states into a larger hidden space before folding them back down.



-----------------------------------------------------------------------

### Low‑Rank Adapters Do The Heavy Lifting For You

Instead of replacing **every** element of \(\mathbf W\), LoRa augments it by a product of two tiny rank-\(r\) tensors:

```text
    Y = X * W                                 (the Frozen model)
      + s * X * L1 * L2                        (the trainable update)
```

Formally,

\[
    {\color{slateblue}\!Y}
        = {\color{slateblue}\!X}({}^{h\times o}\!W)
        + s\, {\color{slateblue}\!X}{({}^{h\times r}\!L_{1})({}^{r\times o}\!L_{2})}
            \tag{1}
\]

* **\(W\)** remains unchanged during training – it’s our “backbone”.
* **\(L_{1}, L_{2}\)** are freshly learned parameters capturing what changes your task really needs.
* **\(s\)** is usually set near unity as an overall scaling factor – disabling learned scale rarely hurts!

Because \(r << h,o\), committing new parameters costs almost nothing:
a single adapter replaces millions of base parameters with just tens or hundreds of thousands.



-----------------------------------------------------------------------

#### The “Why so Tiny?” Trick  

Suppose we trained everything normally:
8 B parameters = ~30 GB raw FP32 storage._

If instead we store entire base matrix \(W\) in half‑precision **BF16**, we cut it down to ~15 GB,
and then add a handful of megabytes worth of $$`L`s''.  
During back‐propagation we still read through the original columns but never write back into them—
all updates flow solely into Leibniz’ `-*`—so IO stays cheap.



-----------------------------------------------------------------------

### Why Every Layer Needs its own Adapter  

At first glance it may feel wasteful—or even unnecessary—to sprinkle one little block after each linear job inside your encoder/decoder stack:

| Scenario | Result |
|----------|--------|
| Only Q/V "*bells"* tweaked | +~5–10 % drop relative Throughput precooked IF MBew |
| All six linear maps adapted | Matches full‐fine tune accuracy |

A careful sweep over many datasets confirms this pattern:
*The amount matters more than rank.*  
Increasing \(r\) beyond 💡~64 delivered diminishing returns while adding little new capacity because the backbone already honors most contextual signals—and attacks missed knobs would otherwise appear elsewhere in network Flows.*

To reach near‐full‐precision scores on tasks such as GLUE or MMLU (`99 %+` leaderboard perms when base evaluated under FP32 control), one must install **one” smalladapter per block** – it refuels gradients everywhere they would otherwise vanish.



-----------------------------------------------------------------------

### Low–Bit Quantisation Still Awaits Recovery  

Quantising all 66 B parameters down from FP32 → **NF4** shrinks pebble tanks massively (\(~5× reduction ↔ ∼1GB storage\$)).  
But raw clean weight replacement alone degrades language modelling perplexity roughly **10–15 pp**—far too slew for any practical chatbot task.



#### Enter **QLoRa**

QLoRa plugs exactly where it hurts:
it keeps the *base* frozen—quantised––and learns just enough “change” through its deep network of adapters so that barometer forces JUMP back around -0 ppm differences 🙂


```text
Step 0 – Quantise backbone W ⟶ NF4   // NormalFloat=optimal ≈ best bin balance
Step 1 – Per‐block Conv w:.12 bits    // DoubleQuant → recolour constants C₁,C₂⟶FP8
Step 2 – High prec de‐quant   → BF16 // Compute edge multiplications without detaching bits
Step 3 – Backprop via fake grads!   // Grad w.r.t base NEVER materialised
Step 4 – Minifluff Adapters     ✨ // Full frontier captured within millions
```

Technically it reads


```math
Y^{BF16}
   = X^{BF16}\,\texttt{doubleDequant}(c_1,c_2,W^{NF4})
   + X^{BF16} L₁^{BF16} L₂^{BF16}
```

Where `doubleDequant` pulls NF4 weights and two subsequent scaling tables (**C₂** compressed UTF‑8 style into FP8 blocks/256 plus further encoding into FP32 tower _C₁_) back up into BF16 perf last moment gleaned HF lib support – all offline.

### Why Is “NormalFloat” Better Than Standard INT/BF?

Facings highlight here:

* pre-trained weights follow a near Gaussian distro (zero centred normal).  
* Classical uniform bit-depth `INT8` leaves heavy tails unevenly distributed causing large rounding error on outliers that happen frequently among language statistics.  
* `NFk` selects bin boundaries exactly where the integral distribution gives equal counts—a true information‑theoretic optimum for Gaussians[^normal].

In mind map terms:

```text
MF11 ➜ BinCount Estim ➜ BitBuckets fairness 👌
Int8 ➜ Naive floor/ceil ➜ Poor tail handling 😩
```

Result displayed statistically:
on several heads (3B → 13B OPT/LLaMA/BLOOM/Pythia) naive int–rounding _fails_, while NF✓ yields gains up until ×4 bit compression without noticeable perplexity jump ▲.

## What is Guanaco?

“Guanaco” is an open‑source chatbot built by finetuning the LLaMA family of large language models with **QLoRA**—a method that allows training a multi‑billions‑parameter model using only a single consumer or professional GPU while preserving full \(16\mbox{-bit}\) quality during inference and training.



**Key facts**
| Model | Size | Training time* | Relative performance |
|-------|------|----------------|----------------------|
| Guanaco 65 B | \(65\cdot10^9\) | ~24 h on a single \(48\mbox{–}\,\text{GB}\) GPU | **≈ 99 %** vs ChatGPT on the Vicuna benchmark |
| Guanaco 33 B | \(33\cdot10^9\) | ~12 h on \(24\mbox{–}\,\text{GB}\) GPU | ≈ 90–95 % vsChatGPT |

\*Training time refers only to supervised cross‑entropy finetuning with a single run over a representative dataset.



> **Bottom line:** With QLoRA you can train state‐of‐the‐art chatbots on hardware anyone owns today—and some even fit inside a pocket.

## How was Quito-powered fine‑tuning performed?

The researchers used **OASST1**, a massive collection of multi‑turn user/assistant conversations harvested through an “Open Assistant” platform that explicitly forbids machine‑generated data from OpenAI models.



The general strategy:
1. Quantize every weight tensor into **NF\(4\)** (NormalFloat four–bit), which packs normally distributed weights into equal‑probability bins.
2. Apply **double quantization** so that *the scale values themselves*—normally stored as float32—are stored in floating‑point8 format.
3. Insert Low–Rank Adaptors everywhere in the transformer stack (“adapters everywhere”).  
   In forward pass each projector becomes  
   \[
   Y = X \cdot W_{\text{nf}} + X \cdot L_1 \cdot L_2 .
   \]
   Gradients flow through the dequantized `\(W_{\text{nf}}\)` only once per token.
4. Use **paged optimizers** based on NVIDIA’s unified memory so large optimizer states spill out of GPU RAM automatically.


Because only a tiny fraction (< 0·02%) of parameters are updated, memory remains below a single modern GPU’s capacity even when processing long stories.

### Automatic scoring with **GPT‑4**

The test procedure mirrors what was first proposed by Vicuna developers:

1. For each query produce three responses:
   - The query’s own assistant reply,
   - A ChatGPT reply,
   - A reply from each candidate system.
2. Prompt GPT‑4:
   
   ```
   You will see three responses A,B,C.
   Rate each out-of ten how well it answers honestly.
   State your rationalisation.
   
   Return s_A,s_B,s_C and explanation.
   ```

3. Compute relative score

# Paging into Profit: Optimizer Memory Tricks for Big LLM Training

## The Memory Challenge When Finetuning Gigantic Models

Training an unmodified language model is already a highly demanding task – a 13 B‑parameter transformer takes dozens of gigabytes just to hold its weights in VRAM while it processes a few thousand tokens per batch. When we move up into the tens‑of‑billions regime, the raw weight tensor alone can demand almost ninety‑plus gigabytes on an otherwise “standard” consumer card like an RTX 4090 or a professional A6000. Beyond this direct footprint comes a second, often larger, wave of memory usage coming from **optimizer state** (momentum buffers, learning‑rate schedules, etc.) and from back‑propagated **activations** that have to be kept until gradients are accumulated.

One common technique is **gradient checkpointing**, which frees much of the activation buffer by recomputing intermediate tensors during back‑propagation instead of storing them all at once. Even after checkpointing the trainer still has to keep two copies of each weight – one *frozen*, quantized layer and one tiny set of adapters that are actually updated – and all the per‑parameter optimizer buffers associated with those adapters. While those adapters add hardly any weight parameters (often less than one percent), their backward gradients can become swamped by large spike events caused by long sequences or very small mini‑batches; the resulting storage needs can still exceed what a single GPU offers.

In short, scaling finetuning beyond ~8–10 B parameters normally requires either multi‑GPU data parallelism or an expensive PCIe-wide machine cluster – an ordeal even for research labs.

## Unified Memory Paging – The Unconventional Trick

NVIDIA GPUs ship a feature called **Unified Memory** that seamlessly moves pages of data between device (GPU) RAM and host (CPU) RAM whenever either side would otherwise run out of space. For everyday code this usually feels invisible – the runtime decides when to copy something across the PCIe bus and keeps the developer amazed at how smooth it is. When we link this mechanism directly into our optimizer implementation we obtain something far more powerful than just moving tensors around at runtime: we let *optimizer state itself spill out* onto system memory without any manual engineering effort or configuration headaches.

The part where Paged Optimizers shine is during *growing integral operations*, such as during occurrences of large sequence lengths or bursty training patterns that trigger enormous spikes in activation gradients. In such moments an optimizer would normally blow out the card’s VRAM ‑ never mind your weight store! By letting a fraction or even all of those spikes be stored in RAM behind the scenes, we essentially **extend VRAM capacity without changing hardware** while keeping all GPU computations residing where they most efficiently operate.

Notably:
* The paging happens automatically – no plumbing needed around your training loop.
* Transfers are performed asynchronously under NVIDIA’s Unified Memory driver so compute is rarely stalled.
* The logic is deliberately lightweight enough that performance penalties are negligible when workloads stay within typical operating regions (i.e., batch‐sizes ≤ 16–32).

## How Paged Optimizers Work Inside QLoRA

QLoRA builds its base model by storing weights in very low‑precision 4‑bit tensors (NF4). During forward passes those weights are reconstituted into BFloat16 (BF16) calls so that modern GPUs still reap their compute speedup while keeping control precision high enough for gradient flow through frozen layers using LoRA adapters.

When you add **paged optimization**, you replace your usual AdamW‐style updater with one whose internal cache lives partially on host memory:

```python
from bitsandbytes.optim import PagedAdamW   # provided by bitsandbytes library
optimizer = PagedAdamW(qlora_model.parameters(), lr=2e-5)
```

The optimizer stores *half* its state stuffed into VRAM and *the remaining* half is swapped out under demand onto CPU RAM via unified memory virtual pages. Thus even if backward pass momentarily requires more than 48 GB worth of filter–adaptive buffers (e.g., when fine-tuning an LLaMA 65 B model on an RTX 6000 24 GB board), your code never fails – battles against “out-of-memory” errors simply lead to short periods where GPU traffic goes up rather than crashes overwrite data structures entirely.

Apart from offering escapes during rare peaks, QLoRA also shows comparable wall‑time performance against non-page‑backed full precision fine-tuning when batch size stays modest; theory predicts identical algebraic complexity while experiments demonstrate close-to-identical CPU-to-GPU transfer overhead because Unified Memory already does lazy paging under sparsity conditions typical for object detection operators used inside transformer ops (softmax + matmul).

Take Guanaco’s upstream implementation: finetune LLaMA up through 65 B w/ NF4+loRA+paged AdamW on single machine:

## From Fundamental Scores To Game Theory Ranking

### How Elo Works  

For any two models \(A,B\), denote their current ratings \(R_A,R_B\).  
Their expected score advantage is given via logistic function

\[
P(A\,|\,R_A,R_B)=
    \frac{1}{1+10^{-(R_A-R_B)/400}}
\]

After observing which system actually won (*the ground truth derived either from voters or raw win rate against ChagPT*), we update their ratings

\[
R'_A = R_A + K(S_A-P(A\,|\,R_A,R_B)),\\ 
S_A =
    \begin{cases}
      1,& A\,wins\\[2pt]
     {\tfrac12},& tie\\[2pt]
      0,& A\,loses
    \end{cases}
\]

where \(K=32\) controls sensitivity.”
