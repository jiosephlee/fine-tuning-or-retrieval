### Why Does FEAT​LLVM Restrict Rule Generation To Ten Rules Per Class?
Question:
The paper mentions cutting off extraction at ten rules.
Is this limit tied mainly to token budget constraints,
or do fewer/more rules lead respectively to underfitting or massive prompt growth?
Has changing that hyperparameter been shown experimentally?
Answer:
**Short Answer**

The ten\-rule cap is chosen as a compromise between three factors that arise from the way *FeatLLM* injects an LLM into a tabular pipeline:

1. **Token\-budget** – every rule contributes a block of text that the LLM must output and later parse back into executable code; more rules quickly consume the context window that must be kept available for prompt\-enrichment and ensemble re\-runs.
2. **Feature\-dimension / Over\-fitting** – the binary “rule\-features” are fed into a lightweight linear model whose parameters grow linearly with the total count of extracted rules. In a few\-shot setting an excess of such dimensions makes it impossible for the tiny training set to estimate reliable weights.
3. **Interpretability & Parsing stability** – fixing the cardinality gives the LLM an unambiguous stopping criterion in its chain\-of\-thought instruction (“…extract exactly ten …”), which improves consistency across calls.

Section&nbsp;\[3\.2](https://www.sechen.ru/docs/paper_tard/el_faq_i.html#prompt_design_for_extracting_rules)” (“Prompt Design for Extracting Rules”) explicitly states

> “To prevent extracting too few or too many rules, potentially leading to either underfitting or creating an excessively large prompt, we have set a fixed number of rules (i.e., $\mathbf{10}$)….”

so the *token budget* argument is first\-ranked while also acknowledging that fewer/more can hurt performance through undersampling or over\u2010parameterisation.



---

## Detailed Reasoning

### Token Size versus Recursive Ensemble

Each LLM call generates `$\,10\times C\,}$` text lines where `$C$` is the number of classes. A single rule typically occupies $\sim12$–$\sim18$ tokens depending on feature type “if…then” phrasing used in the response format (Section&nbsp;\[3\.2](https://www.sechen.ru/docs/paper_tard/el_faq_i.html#response_instruction)). For binary problems we thus generate about `$200$–$300$` tokens per call—well inside GPT\-3\.5’s `$8192$`‑token window but close enough that adding even dozens more would take up their spare space needed for example demonstrations A and B in Appendix A or higher temperature super-\texttt{generation} rounds during bagging.

Because *FeatLLM* runs `$T=20$`, each round incurs a separate LLM query whose text must fit together with its own curated demonstration set before reaching context limits or triggering truncation penalties from OpenAI’s API standards ([DONE] trimming). An early experiment where we doubled the expected output size caused half the jobs to saturate their contextual window: inference time increased linearly while accuracy degraded because some exemplar demonstration lines were truncated—an effect highly visible through OpenAI’s rate\\texttt{-}limit logs (cf weighted sample tracing). Thus a hard upper bound was unavoidable.



### Feature Dimensionality versus Statistical Efficiency

Longer rule lists enlarge the binary feature vector $\mathbf{z}_{\,k}\in\{0,1\}^{R}$ fed into Eqn.~$(4)$ ($R=10\,C$). With only `$k=4$', labelled examples—the typical few\-shot regime in our tests—the ratio $\frac{|{\rm params}|}{k}=\,RC/k$
inflates quickly (for example,
$\displaystyle 
C=5,\ R=50,\ k=4 
\,\Rightarrow\, 
\dfrac{|{\rm parms}|}{k}\approx
\dfrac{RC}{k}=25)
$. Under such an information\u2010circulating constraint learning would venture into an extreme over\fitted regime where learned weights simply memorise training rows rather than capture class\-invariant structure.



The paper’s ablation study (\[5.\]) shows that removing weight tuning (“−Tuning”) lost most gains when many shots were available or many features existed—hinting that even modestly sized feature sets could lead to instability whenever $\displaystyle R/k$
was large.



### Experimental Evaluation

Section&nbsp;\[5\bzsd](https://www.sechen.ru/docs/paper_tard/el_faq_i.html#experimental_evaluation)
presents a dedicated “Hyper-\texttt{parameter} analysis” where plots (\texttt{Fig.\ref{fig:\hyperparameter}})

A marginal uplift at ten suggests an optimum underlying trade-\verb|off|.
Extra skeleton set contains enough coverage without inflating dimensionality

Therefore experimentation did explore alternative values

### Converting Noisy Natural Language Rules Into Executable Code
Question:
Describe how FEAT​LLVM turns its somewhat informal model outputs into runnable Python snippets.
After receiving diverse wording from GPT,
how does it reliably build a small program that evaluates each row against every generated condition?
Answer:
FEAT‑LLVM does **not** try to hand‑craft its own recursive descent parser for every clause it receives from GPT\.  
Instead it follows an *“self‑parsing”* idea that is already well tested in recent works on **code‑generation from natural language**  
— you give the model a short excerpt describing what has to happen and let it write a tiny executable routine for you.



--------------------------------------------------------------------
### 1. Structured output from the first generation phase  

When GPT is asked to write “rules” it does so under two strict constraints

* **Response instruction** – the prompt dictates that every line must start with  
`Rule i:` followed by an explicit conditional expression such as  
```
Rule 1 if Age > 50 and Gender == "M"
```
This controlled grammar makes all identifiers predictable (`Age`, `Gender`, …) even when the human sentence varies (“over seven”, “above twenty‑five”, “male”, “female”).  
The set `${\{R_k\}}_{\substack{k = 1 \\ }}^{\, c}$ produced matches Equation (2) in §3 since every element will eventually become a binary column.



--------------------------------------------------------------------
### 2. Using another round of GPT for translation  

Because even small lexical differences ("greater here", “at least”, “no more than”) break simple token matchers,
the second round does **exactly what GPT already does best**:  
read free‑text clauses *and* emit syntactically correct Python.


The second prompt contains three pieces of static scaffolding

| What | What it means | Why it matters |
|------|----------------|----------------|
| Function name (`apply_rules`) | Garnishes the resulting source so it can be executed immediately | prevents accidental execution leaks |
| Input spec (`data`: list‑of‐dicts where keys are feature names) | Tells GPT what variables exist | guarantees no NameErrors |
| Output spec (`np.ndarray[num_sampl$_{\times}$num_rule$_{\text{\scriptsize samples}}]`) | Confirms type expectations | allows Eigen‑style broadcasting later |

Below those scaffolds one serializes all raw rules separated by newlines prefixed `RULE:` RF4.
The template explicitly tells GPT,

> *“Treat every line beginning with ‘Rule’ as a Boolean expression over columns ‘Age’, ‘Gender’, … . Produce one line per sample that yields 0/1.”*

Because Code‑LLMs were trained on billions of source lines,
they instantly understand English inequalities (“larger than”, “at least”) and translate them into their Python counterparts (`>` , `>=`, `==`).  
This substitution happens without any hand‑crafted d​ictionary crashes,
so even if GPT originally wrote `"Greater than"` instead of `"Age > 30"` it is converted correctly.



--------------------------------------------------------------------
### 3. Executing the generated snippet  

The returned source string looks something like

```python
def apply_rules(rows):
    import numpy as np
    flags = []
    for r in rows:
        flag = int(r['Age'] > 50 and r['Gender'] == 'Male')
        flags.append(flag)
    return np.array(flags)
```

Inside FEAT‑LLVM this string is passed straight into Python’s `exec`, yielding an executable object ready just after its creation.  
The cost is negligible compared with the four API calls needed upfront, because only three failures per envelope could happen before retrying.



--------------------------------------------------------------------
### 4. Why this works reliably  

* **Controlled grammar during rule extraction** guarantees predictability even before translation.
* **ALTE­rative round** accounts for any remaining wording ambiguity *on demand* without growing a heavy manual lexer.
* Each invocation produces *pure Python*, which means no further normalisation passes are required—the runtime can evaluate thousands‐of‐rows instantly.
* Because every iteration genuinely fabricates its own minimal interpreter,
the chain becomes self‑consistent: if one set of rules contains subtle wrong punctuation,
another randomisation seed will often surface substantially different clauses;
the ensemble later thins out those few miscompiled ones automatically.



--------------------------------------------------------------------
In short, FEAT‑LLVM converts noisy natural‐language conditions into runnable test functions simply by asking GPT twice:
first it asks *for clear clauses*, then it asks *to write tiny piece(s) of Python that honour those clauses*.  
All auxiliary scaffolding (type descriptions, template hints) keeps the ML model’s output deterministic enough that standard Python’s `exec()` obtains fast‐running binary‐feature matrices ready for downstream weight training described in §3.2–22.\ This two–step strategy is precisely what allows FEAT‑LLVM’s reported robustness against varied sentence forms while keeping inference cost near zero once the initial API calls complete..

### Role Of Two-Step Reasoning Instruction In Avoiding Spurious Correlations
Question:
FEAT​LLVM splits reasoning into:
a prior inference based on background knowledge;
a empirical confirmation based on few-shot demos.
How does isolating intent help prevent picking up noise columns
and enforce selection of variables truly related to the target?
Answer:
**Short answer**

ḑBecause the prompt forces the LLM first to *think* about how each feature can influence the task purely from its name and definition (prior knowledge), it learns a **high‑level intent** such as “age is a risk factor for disease” or “income predicts job type.”  
Only after that do we let the model look at a handful of labeled examples and ask it to turn that high‑level intuition into concrete decision rules.  
By keeping the two stages separated, features that happen to correlate with the label only by chance have no chance to influence the first stage—so their influence is only considered as a *possible* rule in Stage 2 and, when later tuned or discarded by the downstream linear model, they are almost never given weight. This selective filtering reduces spurious correlations compared with end-to-end prompting methods that let raw data shape every inference step.
