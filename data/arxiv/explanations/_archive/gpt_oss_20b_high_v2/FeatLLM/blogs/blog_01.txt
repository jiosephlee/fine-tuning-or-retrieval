# What Is FeatLLM – Why Turning GPT Into a Feature Engineer Matters  

Tabular data—rows filled with numeric values, dates, and categories—remain the backbone of industrial decision making everywhere from risk assessment in finance to patient screening in medicine. Traditional machine‐learning algorithms handle these tables very well when massive labeled datasets are available, but what happens when you have only a handful of annotated rows?

Enter **FeatLLM** – a framework that lets an off‐the‐shelf large language model (LLM), such as GPT‑3.5 or GPT‑4, play the role of an automatic *feature engineer*. Instead of feeding every new sample into the “black box” at inference time, the LLM spends its effort once during training producing a family of human‑readable predictive rules from just a few labeled examples—and then those condensed hints drive all future predictions via a tiny linear model.



-----------------------------------------------------------------------

## Why Traditional “Ask‑Every‑Sample” Approaches Struggle  

Many recent works have pushed LLMs straight into tabular prediction pipelines:
* Serialize the whole table into text and send **every** test row into the model  
* Rely on parameter‑efficient tuning (LoRA/IA³), fine‐tuning large checkpoints  
* Pull fresh responses for each query  

While powerful on paper these strategies incur severe practical limitations:

| Issue | Consequence |
|-------|-------------|
| **Inference latency** | Every house‐pricing example must hit a remote server → minutes instead of milliseconds |
| **Token limits** | A table may have > 100 columns → serialized prompt exceeds memory |
| **Fine-tuning access** | Only open APIs provide limited context windows |
| **Cost** | Hundreds / thousands of API calls accumulate quickly |

FeatLLM sidesteps every one of them.



-----------------------------------------------------------------------

## Turning an LLM into a Rule Author  

At its core FeedLLM asks an otherwise generalist model one simple question repeatedly until it thinks harder than normal models ever do:

> *“What logical conditions on these ten input columns lead people **to admit heart failure**?”*

The answer is two tiers of reasoning encoded directly inside an instruction prompt:

1. **Causal pre‐screening** – Ask GPT’s commonsense and world knowledge (“Systolic blood pressure > 140 usually signals cardiovascular issues”) *without* looking at your example rows yet.  
2. **Sample insight** – Combine those prepositions with your few demonstrations (“In patient A age 70… card failure=True”) so that it produces concrete **rules** per class (“If `age > 65 AND cholesterol > 200 THEN likelihood = high`”).

Feel free to think aloud after every step—that’s exactly how they train the network internally.



-----------------------------------------------------------------------

### Key Design Choices That Make It Work  

| Choice | Why it Matters |
|--------|----------------|
| **Allow only ≤ 10 rules per class** | Prevents exploding prompts while giving enough coverage |
| **Explicit type help** | If `cholesterol` is numeric you cannot write “equals bad”, so we remind GPT |
| **Fixed response syntax (`Rule #i:`)** | Enables reliable automatic parsing later on |

With these conventions your few labelled rows become “rule gold”, ready for engineering.



-----------------------------------------------------------------------

## From Sentences To Binary Features  

The raw spellings still sit inside natural language texts such as  
*“Rule #2 if `age > 70` AND `diabetes = yes`.”*  
Rather than hand‑coding parsers yourself, FeatLLM leverages another short call to the same LLM (**one extra round trip per dataset**) that outputs miniature Python predicates:

```python
def R2(x):
    return x['age'] > 70 and x['diabetes'] == 'yes'
```

Executing those snippets (`exec()`) transforms every row into a binary indicator vector  
\( \mathbf{z}\in\{0,1\}^R \) where \( R\le10\times|\text{classes}| \).

Only this tiny lookup table remains during test time.



-----------------------------------------------------------------------

## Tiny Linear Classifier Builds Prediction On Top Of Rules  

With all rows converted we train one lightweight logistic equation per class \(k\):

\[
\text{logit}_{k}= \max(\mathbf{w}_{k},\,0)\!\cdot\!\mathbf{z}_{k},
\qquad  
P(y=k|\mathbf{x})=\frac{\exp(\text{logit}_{k})}{\sum_j\exp(\text{logit}_{j})}.
\]

The ReLU clamp guarantees every rule can only boost confidence—it cannot hurt your score unless it truly belongs there. 
Training uses standard cross‑entropy loss over just \(k\) labeled instances (< 32), finishing within seconds on any CPU.



-----------------------------------------------------------------------

## Ensemble + Bagging : How The Model Grows Finer Hair Both Shorter Prompts & Better Robustness  

Even expert old physicians sometimes miss subtle patterns under stress—you get similar “noisy” rules from an uncalibrated language model unless you add some randomness:

* Shuffle demo order → different perspectives  
* Increase temperature → occasionally propose uncommon conditions  
* Target only subset *p* ≤ 100 columns when feasibility forces us downwards (“bag” subset)

Each bag produces its own set \( (\mathbf{w}^{(t)},\,\mathbf{z}^{(t)} )\).  
The final probability is just an average over all bags—an ordinary soft ensemble—and guarantees stability when dozens of unrelated columns appear (see plots showing negligible drop even after injecting unrelated variables).

Key takeaways:

| Property | How FeatLLM Handles It |
|----------|-----------------------|
| *Many attributes (≥ 100)* | Drop them into smaller chunks before calling GPT → never exceed token width |
| *Spurious correlations* | First pre‑reasoning step filters out irrelevant signals before looking at demonstrations |
| *Few labeled rows* | Few revised weights adapt quickly without overfitting |

Because each whole bag requires only ONE call to Q/A split left after generating all its rulesOnce.*

## Numbers That Speak For Themselves  

On thirteen diverse public benchmarks—including Adult income prediction, medical risk screening datasets like Heart Failure & Diabetes—the following pattern emerged (average AUC):

| Setting | Conventional ML† | No λ+4 shots | FeatLLM†⁺ |
|---------|-----------------|--------------|-----------|
| Logistic Regression | 66 % | 74 % | **84 %** |
| XGBoost     | 69 % | 75 % | **86 %** |
| RandomForest   | 70 % | 77 % | **87 %** |

~10 % absolute lift versus both early baselines plus several modern approaches that rely on dozens/hundreds samples or extra unlabeled data (**TabPFN**, **STUNT**, **SCARF**).

In addition,
* With four shots seven sets showed comparable performance already seen from forty controlled LR runs provably outweighing manual hyperparameters tuning.
* Adding unrelated “noise” columns destroyed plain models by up~20 %, while FeatLLM stayed largely unaffected (< 2 % loss).

All results were obtained after adjusting only three lines:

```python
num_ensembles   = 20   # <20 replicates ≥ good enough
num_rules_per_class = 10
temperature     = 0.5   # moderate stochasticity
```

Feel free also experiment locally–the GitHub repo provides end‑to‑end notebooks.

## Low Cost Meets Low Latency — What This Means Practically  

1. **Zero recurrent query load:** Once instructions finish generating constraints you run pure linear algebra locally — no WAN round trip overhead matters any more!  
2. **Open APIs stay usable:** Even when secrets promises tier mandates token limits < 16K you’re safe because you touch it once hardware allowed bagging <~80 tokens per call.\n\n\nTip ― pick `num_ensembles` proportional to attribute count rather than GPU memory budget — this gives best scaling edge.\n\n\n\n   
3.\nExplainable by construction:\nRules themselves live where your human operators can read them;\nlittle weights say which ones mattered most — giving analysts immediate feedback.\n\n\n4.\nBudget friendly:\nA typical dataset requires <30 calls → less than \$0.03 USD with current OpenAI pricing.*

> *(† Indicates reading baseline models performed at their best-default configs).*

## Future Horizons & Remaining Questions  

Although trained solely in low‑shot regimes,
FeatLLM already scales nicely thanks to its ensembled structure;
future work aims at:
* Sampling-aware bagging for large‐scale thousands–row piles  
* Extending rule templates beyond boolean thresholds—asquantified statistics or ratio comparisons—or detecting interaction terms automatically 
* Developing bias audits targeting implicit prior knowledge inside each generative engine 
* Packaging rule generation into self‐contained microservice libraries callable from Rust/C++ interop so you could drop it onto embedded medical device edge nodes


The conceptual shift stays simple though—you’re giving your very generous neural net one chance early on then letting everyone else keep their head straight and talk sophistication.
