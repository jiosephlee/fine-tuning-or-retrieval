# From Binary Rules to Accurate Predictions With a Tiny Linear Classifier  

In many industries—from finance to healthcare—model developers routinely face two hard problems at once:

1. **Scarce labeled data** – You might only have a handful of annotated patient records left after a costly annotation contract ends.  
2. **Strict latency limits** – On‑prem EHR deployments often require milliseconds‑level inference without relying on an expensive GPU‑based cloud API call for every new record.

Classic approaches tackle either one of these issues successfully but rarely both together:  

*Tree ensembles* (XGBoost, Random Forests) excel when you have abundance of data, yet they expose you to prohibitive run‑time cost and require re‑inference calls into a large language model for every timestamped prediction if you want them “smart” enough at low-data regimes.  
*Few‑shot learning* driven directly by Large Language Models (LLMs) runs into severe bottlenecks too – each prediction demands another call into the black box, which is costly both monetarily and chronologically.

**FeatLLM** flips the script entirely—you ask an LLM *once*, for it builds your own lightweight set of boolean conditions (“rules”), turn them into binary features and feed those straight into a tiny non‑negative linear classifier trained locally on your handful of labels. In practice this brings three irresistible benefits:

| Benefit | What you get | What you avoid |
|---------|--------------|----------------|
| **Zero runtime overhead from an LLM** | Predictions are pure CPU dot products | Repeated expensive queries |
| **Near‑state‑of‐the‑art accuracy** | Matches or beats dozens of tree models |\>0 % loss on classic benchmark sets even in 4‑shot regimes |
| **Explanatory clarity** | Each output traceable back to one or more human‑readable segments | “Black‑box” behavior |

Below is how this magic happens under the hood.



## How FeatLLM Thinks About Tabular Data 

At its core FeatLLM follows three simple steps:

1. **Ask the LLM** – present it only the *few* samples you have plus annotated column definitions, construct carefully templated prompts so it answers “What are the defining conditions (rules) that isolate class k?”  
2. **Parse those conditions** back into executable python checks (`age > 60`, `gender == 'F'`) that produce a **binary vector** \( \mathbf{z}_k^{(i)} \in\{0,1\}^{R}\) for each sample \(i\) and each target class \(k\).  
3. **Learn how much each rule matters** – fit onto \< K samples a tiny *non‑negative* linear model:
\[
\text{logit}_{k}^{(i)} = \max (\mathbf{w}_{k},0)\!\cdot \!\mathbf{z}_{k}^{(i)},
\qquad
\mathbf{p}^{(i)} = \mathrm{Softmax}\!\bigl(\![\,\text{logit}_{1}^{(i)},\dots,\text{logit}_{c}^{(i)}\,]\bigr).
\]
The weights \( \mathbf{w}_{k} \geqslant0 \) are learnt locally via cross‑entropy loss over your labelled pool.



## Engineering Prompts That Harvest Code‑Ready Rules 

The first hurdle is getting an LLM (*e.g.*, GPT‑3.5 chat API wrapped behind `gpt-3.5-turbo-0613`) to output cleanly parsable logic instead of prose full of synonyms (“greater than”, “more than”). The authors carved their prompt into **three deliberate blocks**:

| Block | What it contributes | Why it matters |
|-------|---------------------|----------------|
| **Basic Information Δ** | Provides concise task wording (`Does this record indicate disease X?`), column types and brief useful definitions — plus rebuilt examples serialized like "`age is 37 … smoking_status is Yes`". | Anchors the model’s world‐view inside your specific domain before seeing any noisy data |
| **Reasoning Instruction λ** | Forces the model first to reason purely from its knowledge base (“Explain what probably signals disease X”), then uses the few actual examples just like human experts refine their intuition using evidence ("this case shows ...") | Cuts spurious correlations by separating generative world knowledge from empirical pattern fitting |
| **Response Instruction ↗️** | Dictates exact response syntax (`Rule 1: If… then …`, `Rule 2:`…) and not more than ten per class – so automatic parsing is trivial even if tiny grammatical deviations sneak in | Keeps token length manageable even when column count > 100 |

With these constraints people shouted out nothing more than **“Generate ten decisive yes/no conditions that separate every target class.”**

When fed through GPT‑3 quickly (< 30 seconds total) this step delivered smooth Boolean formulas ready for conversion.



## Turning Language Into Code — Self‑Generated Parsers  

Instead of writing custom NLP parsers that choke on phrase variance (`>`, `greater than`, `above`), FeatLLM gives another pass through GPT jurisdictionally located right after prompt injection,

```text
Define function evaluate_rules(data_row):
    # Output pure Python evaluator using these rules:
```

The model’s remarkable internal understanding guarantees subtle variations collapse into mathematically identical statements—a handwritten regex hew every condition accurately enough that running `exec()` on short snippets finishes in<100 µs per row.



## Why Non–Negative Linear Weights?

Classic logistic regression would allow negative weights allowing one satisfied rule—e.g., “blood pressure too high”—to possibly undermine probability if paired oddly with other conditions (a “double negative”). In static Silicon Valley hierarchies private sub-models interpret logical AND–OR equivalently regardless sign orientation—but if you stay strictly non‐negative you ensure **any satisfied rule can only help** bring probability closer towards its true label value without risking unintended cancellations induced by noise or token variation semantics.



## Dealing With Too Many Features — Bagging ➜ Ensemble

Tabular data often carry hundreds of columns which exceed input limits when serialising all simultaneously with prompt completion facilities such as GPT‐3 default max tokens = 4096 tokens (~≈130 columns). FeatLLM tackles this elegantly:

1. Randomly sample either rows (*instance bagging*) or select subsets of columns (*feature bagging*) before handing each subproblem off to the large language backbone.
2. Run this process \(T\) times (\(T=20\) yields little diminishing returns).
3.`Average` returned probabilities across all trials:
\[
P_{\text{final}}^{(i)} = \frac1T\!\sum_{t=1}^T P_t^{(i)} ,
\]
making bad choices ‘averaged out’ while reinforcing consensus among consistent rules—a classic self-consistency trick disguised inside a bagged ensemble.



## Results That Pack Power Into Speed 

The authors ran seven points experiments across fourteen widely varied public datasets—from demographics (“Adult”) through medical record schemas (“Myocardial”) up until synthetic “Sequence-Type” concepts—and measured Area Under ROC curve after each method’s left‑to‐right fairness esti­mation using only \(k=\mathrm{\bf4}\) labelled points versus standard alternatives which often used up close \$16 shots:

| Precision | Class Choice | Model             | Avg AUROC (k=4 shots) |
|-----------|--------------|-------------------|--------------------|
| ⭐️       | Five 클래스     | FeatLLM           | **0·87 ± .08** |
| ⓧ       | Multi-class   | XGBoost           | .80 ± .06         |
| ⓧ       | Binary        | Intelligent GBDT️({rule})     | .77 ± .03        |

Even though FeatLLM rolls out roughly ten binary fields instead of thousands inside a boosted tree ensemble, it consistently gains ~10 percentage points over conventional baselines at equivalent sample budgets—a puzzle answered by its focused encoding plus positive weighting filter against noisy correlations.



### Ablation Highlight   

Removing any critical component degraded performance significantly:

- Dropping weight tuning → loss ≈ −0·15 integration units  
- Turning off ensembling → −0·08 AUROC  
- Omitting feature descriptions → −0·065 AUROC at very low shots  
- Skipping first-step reasoning instruction → ∼ −0·05 AUROC



### Speed & Cost Analysis  

On an M600 GPU cluster called out in experiment logs,

```txt
Training                  : ≈ 30 calls × ~15 s/api ≈ 8 min total
Inference on weighted arcade : < 0·2 ms / row
Inference via XGBoost® : ≈ 14× slower under same CPU load
```

In practice FeatLLM means “once I boot up my local environment I never hit any external coins again”.



## Final Takeaway — When Smaller Is Powerful  

Rule extraction wrought through uncapped large language reasoning coupled with light computational envelopes merges two worlds previously seen as orthogonal:

*The future finance-banking microcredit score card sits inside my laptop*⁂  
*or an instant patient risk assessment feeds the next chart update digitally without hitting a public ML endpoint.*

This combination works well because clinical knowledge embedded deep inside GPT doesn't need verification beneath"—the few example pages are just fine-tuning evidence whereas machine reading technology converts it into machine-checkable conditions automatically.



> 🏁 Bottom line – if your domain supplies expert written attribute descriptions coupled with just tens or hundreds rows worth annotated outcomes then let an untuned large language model sing out ten order–looking logical predicates;
while your own laptop’s dot‐product engine hammers them together under positivity constraint—and you’ll outrun even massive decision trees without touching >\,K budget.
