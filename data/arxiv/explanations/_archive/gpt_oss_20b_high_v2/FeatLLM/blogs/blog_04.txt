# Bagging Rules Makes Engineered Features Robust Against Weak Prompts

In *Large Language Models Can Automatically Engineer Features for Few‑Shot Tabular Learning* the authors introduce **FeatLLM**, a framework that turns an LLM into a rule engineer for tabular data.  One of its most compelling contributions is an **ensemble‑by‑bagging** strategy that lets the system survive both long‑prompt limitations and noisy, irrelevant columns.  This post explains why this approach works, how it’s built, and what evidence supports its effectiveness.

---

## 1. The Basic Idea Behind FeatLLM

Feasibility in few‑shot learning usually hinges on extracting useful signal from very little labeled data.  
FeatLLM leverages an LLM’s vast textual knowledge by asking it to *formulate** logical rules* that separate classes using only a handful of examples and their natural‑language feature descriptions:

1. **Rule Generation** – For every class, the LLM outputs a fixed number of if‑then style rules (e.g., “If `age` > 50 AND `smoker` = yes then disease = yes”).  
2. **Binary Feature Construction** – Each rule becomes a binary column indicating whether a sample satisfies it.  
3. **Simple Linear Scoring** – A non‑negative linear model learns how much weight each rule should carry when predicting class likelihoods.

With this pipeline, inference no longer forces the LLM on every test sample; we run a cheap linear model after having built our feature set once.

---

## 2. Why “Just One” Rule Set Is Not Enough

A single LLM call creates one rule set per target class:

- **Limited Diversity** – The internal stochasticity at temperature 0.5 induces only modest variation in greedy output.
- **Show‑Rely on Prior Knowledge** – The derived rules may overfit peculiarities of the few shots presented.
- **Prompt Scope Constraint** – When a dataset has dozens of features or hundreds of instances, appending all of them in a single request blows up past the model’s token budget (< ≈ 8 k tokens).

Without mitigation, evaluation either suffers from low predictive power or becomes infeasible because the prompt is too long for an API call.

---

## 3. Bagging + Ensemble = Strong, Resilient Predictors

### 3.1 Introducing Randomness

FeatLLM intentionally injects two independent sources of randomness before each LLM query:

| Source | What It Does |
|--------|--------------|
| **Subset Sampling** | Randomly select either a subset of input features* or training instances (feature or instance “bagging”). |
| **Demo Order Shuffle** | Randomly permute the few‑shot examples shown to the model.|

Both mechanisms encourage distinct rule sets across runs because they change what evidence the language model sees at inference time while still preserving enough context for reasonable reasoning.

\*Feature bagging is particularly useful for very large feature spaces: rather than sending every column in one go (which is impossible), we ask for rules that refer only to a handful of them.

### 3.2 Generating Many Weak Learners

Each run produces:

1. A **rule bank** with \(R\) rules per class (default \(R=10\)).
2. A small linear model weights vector \(\mathbf w^{(t)}\) learned from those \(k\) shots (with \(k\leq 32\)) via cross‑entropy on observed binary features.

Running this pipeline \(T\) times (default \(T=20\)) gives us \(T\) independent weak learners:
\[
p^{(t)}_c(\mathbf{x}) = \frac{\exp(\max(\mathbf w_c^{(t)},\,0)\cdot \mathbf z_c^{(t)}(\mathbf{x}))}
{\sum_{c'} \exp(\max(\mathbf w_{c'}^{(t)},\,0)\cdot \mathbf z_{c'}^{(t)}(\mathbf{x}))}
\]
where \(\mathbf z^{(t)}_c(\mathbf{x})\in\{0,1\}^R\) are binary outcomes for sample \(\mathbf{x}\).

Finally, probabilities are averaged:
\[
p_c(\mathbf{x}) = \frac{1}{T}\sum_{t=1}^T p^{(t)}_c(\mathbf{x}) .
\]

This simple averaging is surprisingly powerful—each learner learns slightly different regions of feature space or different combinations exploiting prior domain knowledge encoded in GEO references provided by the LLM during rule generation.

### 3.3 Concrete Benefits

| Issue | What Bagging & Ensemble Fixes |
|-------|------------------------------|
| **Prompt Length Overrun** | Since each iteration uses only a *small* subset—downscaled via feature or instance sampling—the token count stays below API limits while still covering many combinations across trials. |
| **Noisy / Spurious Features** | Even if some bags contain irrelevant columns, their influence is diluted after averaging; moreover, during weight learning ineffective rules receive low weight values automatically—not zeroed out but significantly down‑weighted after training (`max(w_k ,0)` prevents negative contributions). |
| **Limited Data Variability** | Multiple stochastic invocations expose diverse reasoning paths through Shakesperian entropy (shuffled demos/temperature noise), producing richer union-of-rule space than any single deterministic output could offer.|

## 4. Empirical Validation

While we don’t dive into raw numbers here, FeatLLM’s experiments demonstrate these advantages:

1. **Competitive Accuracy Across Datasets** – In thirteen varied tabular benchmarks (Adult, Bank, Heart diseases etc.), FeatLLM consistently matches or surpasses traditional ML baselines trained on entire datasets using only four labeled shots – roughly five times fewer annotations.
2. **Resistance to Spurious Correlations** – By attaching unrelated Adult dataset columns to Heart labels and progressively increasing irrelevant feature count:
   - Other baselines’ AUC fell sharply once noisy columns crossed a threshold (~10–15 irrelevant attributes).
   - FeatLLM dropped at most ~4 % even with dozens more unrelated attributes—an order‐of‐magnitude more robustness.
3. **Ablation Evidence** – Removing ensembled averaging (`-Ensemble`) leads to noticeable accuracy loss (~2–5 % across datasets); similarly turning off random demo shuffling (`-Reasoning`) hurts performance significantly when shots are few (< 8).
4. **Resource Efficiency** – Training requires about 30 API calls per dataset—closing off heavy per‐sample fueling by other approaches like TabLLM or TABLET which must send every test example through an instantiated fine‑tuned LLM module, boosting inference latency by orders of magnitude.

---

## 5. Takeaways for Practitioners

For anyone looking to integrate Enterprise language models into low‑shot tabular scenarios:

| Key Insight | Practical Steps |
|-------------|-----------------|
| Don’t rely on single deterministic prediction | Generate multiple rule sets using different random seedings / subsets/sorting of demos |
| Keep prompts short by sampling | Split feature list into manageable chunks when requesting rules—let each batch cover distinct variable subsets |
| Leverage simple downstream models | Train non–negative linear models on binary rule outputs to avoid expensive computations at inference time |
| Embrace ensemble averaging | Average probabilities across all learned weight vectors instead of selecting one best winner |

These measures produce extensions that are not just clever tricks but deep-seated adaptations rooted firmly in both theoretical reasoning paths (chain-of-thought splits) and empirical evidence showing resilience against limiters such as token budgets and noisy data—a testament to robust design rather than hacky post hoc tweaks.

---

## Closing Thoughts

Bagging simple rule engineers turns an LLM from an expensive black box into a miniature knowledge base that literally *writes* reusable features once and then hands them off to efficient conventional models forevermore—especially adept at surviving uncomfortable lengths inside API walls and data noise common in real business pipelines where every labeled example counts as gold dust.'
