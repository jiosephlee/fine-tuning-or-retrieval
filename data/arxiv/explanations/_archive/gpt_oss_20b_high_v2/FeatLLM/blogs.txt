# What Is FeatLLM – Why Turning GPT Into a Feature Engineer Matters  

Tabular data—rows filled with numeric values, dates, and categories—remain the backbone of industrial decision making everywhere from risk assessment in finance to patient screening in medicine. Traditional machine‐learning algorithms handle these tables very well when massive labeled datasets are available, but what happens when you have only a handful of annotated rows?

Enter **FeatLLM** – a framework that lets an off‐the‐shelf large language model (LLM), such as GPT‑3.5 or GPT‑4, play the role of an automatic *feature engineer*. Instead of feeding every new sample into the “black box” at inference time, the LLM spends its effort once during training producing a family of human‑readable predictive rules from just a few labeled examples—and then those condensed hints drive all future predictions via a tiny linear model.



-----------------------------------------------------------------------

## Why Traditional “Ask‑Every‑Sample” Approaches Struggle  

Many recent works have pushed LLMs straight into tabular prediction pipelines:
* Serialize the whole table into text and send **every** test row into the model  
* Rely on parameter‑efficient tuning (LoRA/IA³), fine‐tuning large checkpoints  
* Pull fresh responses for each query  

While powerful on paper these strategies incur severe practical limitations:

| Issue | Consequence |
|-------|-------------|
| **Inference latency** | Every house‐pricing example must hit a remote server → minutes instead of milliseconds |
| **Token limits** | A table may have > 100 columns → serialized prompt exceeds memory |
| **Fine-tuning access** | Only open APIs provide limited context windows |
| **Cost** | Hundreds / thousands of API calls accumulate quickly |

FeatLLM sidesteps every one of them.



-----------------------------------------------------------------------

## Turning an LLM into a Rule Author  

At its core FeedLLM asks an otherwise generalist model one simple question repeatedly until it thinks harder than normal models ever do:

> *“What logical conditions on these ten input columns lead people **to admit heart failure**?”*

The answer is two tiers of reasoning encoded directly inside an instruction prompt:

1. **Causal pre‐screening** – Ask GPT’s commonsense and world knowledge (“Systolic blood pressure > 140 usually signals cardiovascular issues”) *without* looking at your example rows yet.  
2. **Sample insight** – Combine those prepositions with your few demonstrations (“In patient A age 70… card failure=True”) so that it produces concrete **rules** per class (“If `age > 65 AND cholesterol > 200 THEN likelihood = high`”).

Feel free to think aloud after every step—that’s exactly how they train the network internally.



-----------------------------------------------------------------------

### Key Design Choices That Make It Work  

| Choice | Why it Matters |
|--------|----------------|
| **Allow only ≤ 10 rules per class** | Prevents exploding prompts while giving enough coverage |
| **Explicit type help** | If `cholesterol` is numeric you cannot write “equals bad”, so we remind GPT |
| **Fixed response syntax (`Rule #i:`)** | Enables reliable automatic parsing later on |

With these conventions your few labelled rows become “rule gold”, ready for engineering.



-----------------------------------------------------------------------

## From Sentences To Binary Features  

The raw spellings still sit inside natural language texts such as  
*“Rule #2 if `age > 70` AND `diabetes = yes`.”*  
Rather than hand‑coding parsers yourself, FeatLLM leverages another short call to the same LLM (**one extra round trip per dataset**) that outputs miniature Python predicates:

```python
def R2(x):
    return x['age'] > 70 and x['diabetes'] == 'yes'
```

Executing those snippets (`exec()`) transforms every row into a binary indicator vector  
\( \mathbf{z}\in\{0,1\}^R \) where \( R\le10\times|\text{classes}| \).

Only this tiny lookup table remains during test time.



-----------------------------------------------------------------------

## Tiny Linear Classifier Builds Prediction On Top Of Rules  

With all rows converted we train one lightweight logistic equation per class \(k\):

\[
\text{logit}_{k}= \max(\mathbf{w}_{k},\,0)\!\cdot\!\mathbf{z}_{k},
\qquad  
P(y=k|\mathbf{x})=\frac{\exp(\text{logit}_{k})}{\sum_j\exp(\text{logit}_{j})}.
\]

The ReLU clamp guarantees every rule can only boost confidence—it cannot hurt your score unless it truly belongs there. 
Training uses standard cross‑entropy loss over just \(k\) labeled instances (< 32), finishing within seconds on any CPU.



-----------------------------------------------------------------------

## Ensemble + Bagging : How The Model Grows Finer Hair Both Shorter Prompts & Better Robustness  

Even expert old physicians sometimes miss subtle patterns under stress—you get similar “noisy” rules from an uncalibrated language model unless you add some randomness:

* Shuffle demo order → different perspectives  
* Increase temperature → occasionally propose uncommon conditions  
* Target only subset *p* ≤ 100 columns when feasibility forces us downwards (“bag” subset)

Each bag produces its own set \( (\mathbf{w}^{(t)},\,\mathbf{z}^{(t)} )\).  
The final probability is just an average over all bags—an ordinary soft ensemble—and guarantees stability when dozens of unrelated columns appear (see plots showing negligible drop even after injecting unrelated variables).

Key takeaways:

| Property | How FeatLLM Handles It |
|----------|-----------------------|
| *Many attributes (≥ 100)* | Drop them into smaller chunks before calling GPT → never exceed token width |
| *Spurious correlations* | First pre‑reasoning step filters out irrelevant signals before looking at demonstrations |
| *Few labeled rows* | Few revised weights adapt quickly without overfitting |

Because each whole bag requires only ONE call to Q/A split left after generating all its rulesOnce.*



-----------------------------------------------------------------------

On thirteen diverse public benchmarks—including Adult income prediction, medical risk screening datasets like Heart Failure & Diabetes—the following pattern emerged (average AUC):

# Crafting Rules With Language Models  
## The Two–Step Reasoning Process  

Large language models have been shown capable of answering surprising questions without ever being trained directly on that task.  
A recent line of work has turned this ability into *feature engineering* for low‑shot tabular problems—calling it **FeatLLM**—and it hinges on a single idea that seems simple but is surprisingly powerful: *first ask an LLM what it knows about how columns relate to one another, then let it use a handful of labeled rows to turn those ideas into concrete decision rules.*

Below I unpack how FeatLLM builds this two‑step chain‑of‑thought prompt and why it matters when you only have a handful of samples.



--------------------------------------------------------------------

## Why Turn an LLM Into a Human‑Like Rule Writer?

Imagine you’re given a small patient record dataset and asked “Does this person probably suffer from chronic heart failure?”  
Without many labeled examples you risk inventing *spurious correlations*—for example you might mistakenly think “if blood glucose > 150 mg/dL → yes” purely because one lucky row had both high glucose and heart failure even though glucose isn’t related clinically.



The trick behind FeatLLM is **separating prior knowledge from data‑driven evidence**:

| Prior Knowledge | Few‑Shot Data |
|-----------------|---------------|
| What doctors believe about risk factors | Concrete rows we hand‑label |
| How numerical thresholds normally behave | Which thresholds actually work here |

If an LLM first thinks aloud about **generic causal links** among columns based only on what it has read during pre‑training—and *doesn’t* look at any examples yet—it will naturally ignore irrelevant features.  
Later, when you give it just eight rows expressed in natural language, it can refine those links into *explicit logical conditions* that distinguish each class.



--------------------------------------------------------------------

## Prompt Design – Three Blocks That Work Together  

In practice FeatLLM structures its query into three self‑contained blocks so that every step stays clear enough for the model *and* easy enough later to turn back into executable code.



### 1) Basic Information Description  

This is what you always give an LLM before asking any question:\n\n
- **Task statement** formulated as a clear yes/no question.\n\n
- **Column catalogue** – each feature name followed by its type (numeric versus categorical) and optionally its definition.\n\n
- **Serialized examples** – chosen few labeled rows written out word‑for‑word so the model sees exactly what constitutes “an answer.”  
For instance:

```
Age is 65., Smoker is Yes., HeartRate is 110., Answer: Yes
Age is 30., Smoker is No., HeartRate is 72., Answer: No
```



### 2) Reasoning Instruction – The Two–Step Chain  

A *chain‑of‑thought* style cue tells the model how **to think before talking**:\n\n  

**Step 1 – Prior Knowledge Check:**  
> “Think normally about how each feature relates to heart failure before looking at any training rows.”

This forces the model’s first draft answer onto *generic causality* (“high age tends towards failure”, “smoking increases risk”), ignoring random overlaps in our limited data.



**Step 2 – Data‑Guided Refinement:**  
> “Now look at these eight rows together with your prior thoughts and write ten logical rules that would tell whether the answer should be ‘Yes’ or ‘No’.”

Two things happen here immediately:\n\n - Existing patterns become anchored by concrete evidence.\n - Because only ten rules are requested per class, everything has room for meaning while keeping later prompts short.



### 3) Response Instruction – Enforce Parseable Form  

The last block tells the model exactly **how much grammar matters**:\n\n  

```text
Class Yes:
    Rule 1 = …
    Rule 2 = …
    …
Class No:
    Rule 1 = …
```

By giving exact wording (“Class …”, “Rule … =”), FeatLLM ensures people who implement downstream parsers won’t deal with special cases where apostrophes or pluralities change rendering.



--------------------------------------------------------------------

## From Natural Language Rules To Binary Features  

Once you receive those neat rule lists you cannot just paste them straight into code—humans who read midway often miss subtle modifiers (“greater than” vs “more than”).  
Instead FeatLLM forwards *the text back* into another request whose sole purpose is code generation:\n\n
```python
def check_rules(row):
    #Parsed booleans below follow pattern produced earlier.
    return (
        row["Age"] >70 and row["Smoker"]=="Yes",   # Rule 1 (“Yes”)
        row["HeartRate"] >120                      # Rule 2 (“Yes”)
        ...
    )
```

Executing those tiny snippets produces a matrix `Z` where `Z[i,k]` equals `1` if row *i* satisfies any rule assigned to class *k*. In computational terms this becomes a very small linear classifier whose trainable weights are forced nonnegative, meaning “satisfied → more likely”.

Because all parsing happens through automatic code generation fed back into GPT itself, there’s almost no manual transcription error.



--------------------------------------------------------------------

## Why This Two–Step Route Is Superior  

1. **Fewer Spurious Rules** – By asking the model first what it knows globally you force it *away* from randomly correlated columns present among your few samples.\n\n2. **Tight Prompt Size** – Fixing exactly ten rules per class keeps inputs shorter than many other approaches which serialise all original columns.\n\n3. **Robustness Through Bagging** – FeatLLM repeats the whole process several times using different random shuffles and temperatures, creating distinct sets of rules which then get ensembled normally (probabilities averaged). This encourages consistency (“rule writes itself across trials”), much like how humans double‑check calculations.\n\n4. **Low Inference Cost** – After these offline queries you’re left with a tiny linear model running locally everywhere. No ARI’s shine every time you read a new record!\n\nSeveral ablation studies in their work showed dropping either Step 1 or Step 2 degrades scores noticeably—exactly what you'd expect if either the global perspective or data grounding was missing.



--------------------------------------------------------------------

## Putting It All Together – A Quick Walkthrough  

Below’s an outline you’d send via GPT‑3.5 API (pseudo‑text cleanly showing tone used in FeatLLM):

```
Task:
“Does this patient's record indicate chronic heart failure? Yes or No?”

Feature descriptions:
• Age – numeric
• Smoker – categorical {Yes, No}
• HeartRate – numeric
• BloodGlucose – numeric
…

Examples (8 shots):
• Age is 68., Smoker is Yes., HeartRate was 117..., Answer: Yes.
…
(7 more lines)

Reasoning instruction:
First think generally about these features' relation with heart failure without looking at any examples.
Then look at these eight rows together with your thoughts above,
and write exactly ten logical conditions under Class Yes,
and ten under Class No,

Response instruction:
For each class write Class Yes:, Class No:. Then list Rule # = condition...
Make sure conditions match syntax accepted by Python parser.
```

When GPT finishes you’ll see something like:

```
Class Yes:
Rule 1 = Age > 65 AND Smoker == "Yes"
Rule 2 = HeartRate > 110 AND BloodGlucose > 140
...
Class No:
Rule 1 = Age < 50 OR Smoker == "No"
...
```

Those entries are now fed back through another prompt asking GPT to translate them into an `if …:` Python function—a reliable executor.


--------------------------------------------------------------------

## Takeaways For Practitioners  

* If your budget allows only surface‐level access (`API`s) without gigantic training runs, turn your LLM into an *expert linguist* who writes human interpretable decision logic instead of acting as black box predictor.*

* Keep your prompts modular: basic definition block → reasoning instruction → response formatting.*

* Even though ten rules seemed arbitrary at first glance—you’ll find validating them shows little loss while keeping everything well within token limits.*

* Finally remember variable keeping across runs leads to ensemble improvements without needing another forward pass through GPT per new data point.*

With these points ironed out work begins quickly—the rest consists mainly stylistically polishing code functions generated by GPT.”



# From Binary Rules to Accurate Predictions With a Tiny Linear Classifier  

In many industries—from finance to healthcare—model developers routinely face two hard problems at once:

1. **Scarce labeled data** – You might only have a handful of annotated patient records left after a costly annotation contract ends.  
2. **Strict latency limits** – On‑prem EHR deployments often require milliseconds‑level inference without relying on an expensive GPU‑based cloud API call for every new record.

Classic approaches tackle either one of these issues successfully but rarely both together:  

*Tree ensembles* (XGBoost, Random Forests) excel when you have abundance of data, yet they expose you to prohibitive run‑time cost and require re‑inference calls into a large language model for every timestamped prediction if you want them “smart” enough at low-data regimes.  
*Few‑shot learning* driven directly by Large Language Models (LLMs) runs into severe bottlenecks too – each prediction demands another call into the black box, which is costly both monetarily and chronologically.

**FeatLLM** flips the script entirely—you ask an LLM *once*, for it builds your own lightweight set of boolean conditions (“rules”), turn them into binary features and feed those straight into a tiny non‑negative linear classifier trained locally on your handful of labels. In practice this brings three irresistible benefits:

| Benefit | What you get | What you avoid |
|---------|--------------|----------------|
| **Zero runtime overhead from an LLM** | Predictions are pure CPU dot products | Repeated expensive queries |
| **Near‑state‑of‐the‑art accuracy** | Matches or beats dozens of tree models |\>0 % loss on classic benchmark sets even in 4‑shot regimes |
| **Explanatory clarity** | Each output traceable back to one or more human‑readable segments | “Black‑box” behavior |

Below is how this magic happens under the hood.



## How FeatLLM Thinks About Tabular Data 

At its core FeatLLM follows three simple steps:

1. **Ask the LLM** – present it only the *few* samples you have plus annotated column definitions, construct carefully templated prompts so it answers “What are the defining conditions (rules) that isolate class k?”  
2. **Parse those conditions** back into executable python checks (`age > 60`, `gender == 'F'`) that produce a **binary vector** \( \mathbf{z}_k^{(i)} \in\{0,1\}^{R}\) for each sample \(i\) and each target class \(k\).  
3. **Learn how much each rule matters** – fit onto \< K samples a tiny *non‑negative* linear model:
\[
\text{logit}_{k}^{(i)} = \max (\mathbf{w}_{k},0)\!\cdot \!\mathbf{z}_{k}^{(i)},
\qquad
\mathbf{p}^{(i)} = \mathrm{Softmax}\!\bigl(\![\,\text{logit}_{1}^{(i)},\dots,\text{logit}_{c}^{(i)}\,]\bigr).
\]
The weights \( \mathbf{w}_{k} \geqslant0 \) are learnt locally via cross‑entropy loss over your labelled pool.



## Engineering Prompts That Harvest Code‑Ready Rules 

The first hurdle is getting an LLM (*e.g.*, GPT‑3.5 chat API wrapped behind `gpt-3.5-turbo-0613`) to output cleanly parsable logic instead of prose full of synonyms (“greater than”, “more than”). The authors carved their prompt into **three deliberate blocks**:

| Block | What it contributes | Why it matters |
|-------|---------------------|----------------|
| **Basic Information Δ** | Provides concise task wording (`Does this record indicate disease X?`), column types and brief useful definitions — plus rebuilt examples serialized like "`age is 37 … smoking_status is Yes`". | Anchors the model’s world‐view inside your specific domain before seeing any noisy data |
| **Reasoning Instruction λ** | Forces the model first to reason purely from its knowledge base (“Explain what probably signals disease X”), then uses the few actual examples just like human experts refine their intuition using evidence ("this case shows ...") | Cuts spurious correlations by separating generative world knowledge from empirical pattern fitting |
| **Response Instruction ↗️** | Dictates exact response syntax (`Rule 1: If… then …`, `Rule 2:`…) and not more than ten per class – so automatic parsing is trivial even if tiny grammatical deviations sneak in | Keeps token length manageable even when column count > 100 |

With these constraints people shouted out nothing more than **“Generate ten decisive yes/no conditions that separate every target class.”**

When fed through GPT‑3 quickly (< 30 seconds total) this step delivered smooth Boolean formulas ready for conversion.



## Turning Language Into Code — Self‑Generated Parsers  

Instead of writing custom NLP parsers that choke on phrase variance (`>`, `greater than`, `above`), FeatLLM gives another pass through GPT jurisdictionally located right after prompt injection,

```text
Define function evaluate_rules(data_row):
    # Output pure Python evaluator using these rules:
```

The model’s remarkable internal understanding guarantees subtle variations collapse into mathematically identical statements—a handwritten regex hew every condition accurately enough that running `exec()` on short snippets finishes in<100 µs per row.



## Why Non–Negative Linear Weights?

Classic logistic regression would allow negative weights allowing one satisfied rule—e.g., “blood pressure too high”—to possibly undermine probability if paired oddly with other conditions (a “double negative”). In static Silicon Valley hierarchies private sub-models interpret logical AND–OR equivalently regardless sign orientation—but if you stay strictly non‐negative you ensure **any satisfied rule can only help** bring probability closer towards its true label value without risking unintended cancellations induced by noise or token variation semantics.



## Dealing With Too Many Features — Bagging ➜ Ensemble

Tabular data often carry hundreds of columns which exceed input limits when serialising all simultaneously with prompt completion facilities such as GPT‐3 default max tokens = 4096 tokens (~≈130 columns). FeatLLM tackles this elegantly:

1. Randomly sample either rows (*instance bagging*) or select subsets of columns (*feature bagging*) before handing each subproblem off to the large language backbone.
2. Run this process \(T\) times (\(T=20\) yields little diminishing returns).
3.`Average` returned probabilities across all trials:
\[
P_{\text{final}}^{(i)} = \frac1T\!\sum_{t=1}^T P_t^{(i)} ,
\]
making bad choices ‘averaged out’ while reinforcing consensus among consistent rules—a classic self-consistency trick disguised inside a bagged ensemble.



## Results That Pack Power Into Speed 

The authors ran seven points experiments across fourteen widely varied public datasets—from demographics (“Adult”) through medical record schemas (“Myocardial”) up until synthetic “Sequence-Type” concepts—and measured Area Under ROC curve after each method’s left‑to‐right fairness esti­mation using only \(k=\mathrm{\bf4}\) labelled points versus standard alternatives which often used up close \$16 shots:

| Precision | Class Choice | Model             | Avg AUROC (k=4 shots) |
|-----------|--------------|-------------------|--------------------|
| ⭐️       | Five 클래스     | FeatLLM           | **0·87 ± .08** |
| ⓧ       | Multi-class   | XGBoost           | .80 ± .06         |
| ⓧ       | Binary        | Intelligent GBDT️({rule})     | .77 ± .03        |

Even though FeatLLM rolls out roughly ten binary fields instead of thousands inside a boosted tree ensemble, it consistently gains ~10 percentage points over conventional baselines at equivalent sample budgets—a puzzle answered by its focused encoding plus positive weighting filter against noisy correlations.



### Ablation Highlight   

Removing any critical component degraded performance significantly:

- Turning off ensembling → −0·08 AUROC  
- Omitting feature descriptions → −0·065 AUROC at very low shots  
- Skipping first-step reasoning instruction → ∼ −0·05 AUROC

Rule extraction wrought through uncapped large language reasoning coupled with light computational envelopes merges two worlds previously seen as orthogonal:

# Bagging Rules Makes Engineered Features Robust Against Weak Prompts

In *Large Language Models Can Automatically Engineer Features for Few‑Shot Tabular Learning* the authors introduce **FeatLLM**, a framework that turns an LLM into a rule engineer for tabular data.  One of its most compelling contributions is an **ensemble‑by‑bagging** strategy that lets the system survive both long‑prompt limitations and noisy, irrelevant columns.  This post explains why this approach works, how it’s built, and what evidence supports its effectiveness.

---

## 1. The Basic Idea Behind FeatLLM

Feasibility in few‑shot learning usually hinges on extracting useful signal from very little labeled data.  
FeatLLM leverages an LLM’s vast textual knowledge by asking it to *formulate** logical rules* that separate classes using only a handful of examples and their natural‑language feature descriptions:

1. **Rule Generation** – For every class, the LLM outputs a fixed number of if‑then style rules (e.g., “If `age` > 50 AND `smoker` = yes then disease = yes”).  
2. **Binary Feature Construction** – Each rule becomes a binary column indicating whether a sample satisfies it.  
3. **Simple Linear Scoring** – A non‑negative linear model learns how much weight each rule should carry when predicting class likelihoods.

With this pipeline, inference no longer forces the LLM on every test sample; we run a cheap linear model after having built our feature set once.

---

## 2. Why “Just One” Rule Set Is Not Enough

A single LLM call creates one rule set per target class:

- **Limited Diversity** – The internal stochasticity at temperature 0.5 induces only modest variation in greedy output.
- **Show‑Rely on Prior Knowledge** – The derived rules may overfit peculiarities of the few shots presented.
- **Prompt Scope Constraint** – When a dataset has dozens of features or hundreds of instances, appending all of them in a single request blows up past the model’s token budget (< ≈ 8 k tokens).

Without mitigation, evaluation either suffers from low predictive power or becomes infeasible because the prompt is too long for an API call.

---

## 3. Bagging + Ensemble = Strong, Resilient Predictors

### 3.1 Introducing Randomness

FeatLLM intentionally injects two independent sources of randomness before each LLM query:

| Source | What It Does |
|--------|--------------|
| **Subset Sampling** | Randomly select either a subset of input features* or training instances (feature or instance “bagging”). |
| **Demo Order Shuffle** | Randomly permute the few‑shot examples shown to the model.|

Both mechanisms encourage distinct rule sets across runs because they change what evidence the language model sees at inference time while still preserving enough context for reasonable reasoning.

\*Feature bagging is particularly useful for very large feature spaces: rather than sending every column in one go (which is impossible), we ask for rules that refer only to a handful of them.

### 3.2 Generating Many Weak Learners

Each run produces:

1. A **rule bank** with \(R\) rules per class (default \(R=10\)).
2. A small linear model weights vector \(\mathbf w^{(t)}\) learned from those \(k\) shots (with \(k\leq 32\)) via cross‑entropy on observed binary features.

Running this pipeline \(T\) times (default \(T=20\)) gives us \(T\) independent weak learners:
\[
p^{(t)}_c(\mathbf{x}) = \frac{\exp(\max(\mathbf w_c^{(t)},\,0)\cdot \mathbf z_c^{(t)}(\mathbf{x}))}
{\sum_{c'} \exp(\max(\mathbf w_{c'}^{(t)},\,0)\cdot \mathbf z_{c'}^{(t)}(\mathbf{x}))}
\]
where \(\mathbf z^{(t)}_c(\mathbf{x})\in\{0,1\}^R\) are binary outcomes for sample \(\mathbf{x}\).

Finally, probabilities are averaged:
\[
p_c(\mathbf{x}) = \frac{1}{T}\sum_{t=1}^T p^{(t)}_c(\mathbf{x}) .
\]

This simple averaging is surprisingly powerful—each learner learns slightly different regions of feature space or different combinations exploiting prior domain knowledge encoded in GEO references provided by the LLM during rule generation.

### 3.3 Concrete Benefits

| Issue | What Bagging & Ensemble Fixes |
|-------|------------------------------|
| **Prompt Length Overrun** | Since each iteration uses only a *small* subset—downscaled via feature or instance sampling—the token count stays below API limits while still covering many combinations across trials. |
| **Noisy / Spurious Features** | Even if some bags contain irrelevant columns, their influence is diluted after averaging; moreover, during weight learning ineffective rules receive low weight values automatically—not zeroed out but significantly down‑weighted after training (`max(w_k ,0)` prevents negative contributions). |
| **Limited Data Variability** | Multiple stochastic invocations expose diverse reasoning paths through Shakesperian entropy (shuffled demos/temperature noise), producing richer union-of-rule space than any single deterministic output could offer.|

---

## 4. Empirical Validation

While we don’t dive into raw numbers here, FeatLLM’s experiments demonstrate these advantages:

1. **Competitive Accuracy Across Datasets** – In thirteen varied tabular benchmarks (Adult, Bank, Heart diseases etc.), FeatLLM consistently matches or surpasses traditional ML baselines trained on entire datasets using only four labeled shots – roughly five times fewer annotations.
2. **Resistance to Spurious Correlations** – By attaching unrelated Adult dataset columns to Heart labels and progressively increasing irrelevant feature count:
   - Other baselines’ AUC fell sharply once noisy columns crossed a threshold (~10–15 irrelevant attributes).
   - FeatLLM dropped at most ~4 % even with dozens more unrelated attributes—an order‐of‐magnitude more robustness.
3. **Ablation Evidence** – Removing ensembled averaging (`-Ensemble`) leads to noticeable accuracy loss (~2–5 % across datasets); similarly turning off random demo shuffling (`-Reasoning`) hurts performance significantly when shots are few (< 8).
4. **Resource Efficiency** – Training requires about 30 API calls per dataset—closing off heavy per‐sample fueling by other approaches like TabLLM or TABLET which must send every test example through an instantiated fine‑tuned LLM module, boosting inference latency by orders of magnitude.

## 5. Takeaways for Practitioners

For anyone looking to integrate Enterprise language models into low‑shot tabular scenarios:

| Key Insight | Practical Steps |
|-------------|-----------------|
| Don’t rely on single deterministic prediction | Generate multiple rule sets using different random seedings / subsets/sorting of demos |
| Keep prompts short by sampling | Split feature list into manageable chunks when requesting rules—let each batch cover distinct variable subsets |
| Leverage simple downstream models | Train non–negative linear models on binary rule outputs to avoid expensive computations at inference time |
| Embrace ensemble averaging | Average probabilities across all learned weight vectors instead of selecting one best winner |

These measures produce extensions that are not just clever tricks but deep-seated adaptations rooted firmly in both theoretical reasoning paths (chain-of-thought splits) and empirical evidence showing resilience against limiters such as token budgets and noisy data—a testament to robust design rather than hacky post hoc tweaks.
