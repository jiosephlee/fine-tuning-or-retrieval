\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### Converting Noisy Natural Language Rules Into Executable Code
Question:
Describe how FEAT​LLVM turns its somewhat informal model outputs into runnable Python snippets.
After receiving diverse wording from GPT,
how does it reliably build a small program that evaluates each row against every generated condition?
Answer:
FEAT‑LLVM does **not** try to hand‑craft its own recursive descent parser for every clause it receives from GPT\.  
Instead it follows an *“self‑parsing”* idea that is already well tested in recent works on **code‑generation from natural language**  
— you give the model a short excerpt describing what has to happen and let it write a tiny executable routine for you.



--------------------------------------------------------------------
### 1. Structured output from the first generation phase  

When GPT is asked to write “rules” it does so under two strict constraints

* **Response instruction** – the prompt dictates that every line must start with  
`Rule i:` followed by an explicit conditional expression such as  
```
Rule 1 if Age > 50 and Gender == "M"
```
This controlled grammar makes all identifiers predictable (`Age`, `Gender`, …) even when the human sentence varies (“over seven”, “above twenty‑five”, “male”, “female”).  
The set `${\{R_k\}}_{\substack{k = 1 \\ }}^{\, c}$ produced matches Equation (2) in §3 since every element will eventually become a binary column.



--------------------------------------------------------------------
### 2. Using another round of GPT for translation  

Because even small lexical differences ("greater here", “at least”, “no more than”) break simple token matchers,
the second round does **exactly what GPT already does best**:  
read free‑text clauses *and* emit syntactically correct Python.


The second prompt contains three pieces of static scaffolding

| What | What it means | Why it matters |
|------|----------------|----------------|
| Function name (`apply_rules`) | Garnishes the resulting source so it can be executed immediately | prevents accidental execution leaks |
| Input spec (`data`: list‑of‐dicts where keys are feature names) | Tells GPT what variables exist | guarantees no NameErrors |
| Output spec (`np.ndarray[num_sampl$_{\times}$num_rule$_{\text{\scriptsize samples}}]`) | Confirms type expectations | allows Eigen‑style broadcasting later |

Below those scaffolds one serializes all raw rules separated by newlines prefixed `RULE:` RF4.
The template explicitly tells GPT,

> *“Treat every line beginning with ‘Rule’ as a Boolean expression over columns ‘Age’, ‘Gender’, … . Produce one line per sample that yields 0/1.”*

Because Code‑LLMs were trained on billions of source lines,
they instantly understand English inequalities (“larger than”, “at least”) and translate them into their Python counterparts (`>` , `>=`, `==`).  
This substitution happens without any hand‑crafted d​ictionary crashes,
so even if GPT originally wrote `"Greater than"` instead of `"Age > 30"` it is converted correctly.



--------------------------------------------------------------------
### 3. Executing the generated snippet  

The returned source string looks something like

```python
def apply_rules(rows):
    import numpy as np
    flags = []
    for r in rows:
        flag = int(r['Age'] > 50 and r['Gender'] == 'Male')
        flags.append(flag)
    return np.array(flags)
```

Inside FEAT‑LLVM this string is passed straight into Python’s `exec`, yielding an executable object ready just after its creation.  
The cost is negligible compared with the four API calls needed upfront, because only three failures per envelope could happen before retrying.



--------------------------------------------------------------------
### 4. Why this works reliably  

* **Controlled grammar during rule extraction** guarantees predictability even before translation.
* **ALTE­rative round** accounts for any remaining wording ambiguity *on demand* without growing a heavy manual lexer.
* Each invocation produces *pure Python*, which means no further normalisation passes are required—the runtime can evaluate thousands‐of‐rows instantly.
* Because every iteration genuinely fabricates its own minimal interpreter,
the chain becomes self‑consistent: if one set of rules contains subtle wrong punctuation,
another randomisation seed will often surface substantially different clauses;
the ensemble later thins out those few miscompiled ones automatically.



--------------------------------------------------------------------
In short, FEAT‑LLVM converts noisy natural‐language conditions into runnable test functions simply by asking GPT twice:
first it asks *for clear clauses*, then it asks *to write tiny piece(s) of Python that honour those clauses*.  
All auxiliary scaffolding (type descriptions, template hints) keeps the ML model’s output deterministic enough that standard Python’s `exec()` obtains fast‐running binary‐feature matrices ready for downstream weight training described in §3.2–22.\ This two–step strategy is precisely what allows FEAT‑LLVM’s reported robustness against varied sentence forms while keeping inference cost near zero once the initial API calls complete..
