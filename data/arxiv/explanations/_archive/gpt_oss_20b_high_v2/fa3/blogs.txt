# Warp Specialisation – Turning GPU Latency Into Lightning Attention  

Modern Transformer models spend most of their time computing scaled dot‑product attention:
$$\mathbf{S}= \alpha\,\mathbf{Q}\mathbf{K}^{\mathsf{T}},\qquad  
\mathbf{P}=\text{softmax}(\mathbf{S}),\qquad  
\mathbf{O}= \mathbf{P}\,\mathbf{V},$$
where $\alpha = d^{-1/2}$ and all matrices have shape $(N\times d)$ per head ($N$ = sequence length). On today’s GPUs this operation is usually dominated by fast Matrix‑Multiply Accumulators (Tensor Cores) together with relatively slow global‑memory traffic and low‑throughput `exp()` instructions needed for softmax. When the implementation forces every step to complete sequentially — first load everything into shared memory, then run one dot product per block — a significant fraction of compute power sits idle waiting for data or waiting operators that have been stalled behind the latest memory transfer or exponential evaluation.  

FlashAttention‑3 tackles this bottleneck head‑on by **warp‑specialising** inside every cooperative thread array (CTA). In a nutshell we separate each CTA into two logical groups:

| Group | Role | Typical PTX commands |
|-------|------|---------------------|
| **Producer** | Load query/key/value tiles with Tungten Memory Accelerator (`TMA`) | `tma_async_load` |
| **Consumer** | Drive Tensor Core GEMMs (`WGMMA`) and execute rowwise softmax | `wmma_sync`, scalar arithmetic |

Separating these roles lets each group execute its “best” instruction set concurrently while still sharing a shared-memory buffer that horizontally streams tiles through the GPU pipeline.


---

## 1\. Why split a CTA into producer & consumer warps?

In Hopper GPUs both **TMA** (`tma_async_load`) and **WGMMA** (`wmma_sync`) are *asynchronous*. They start their work immediately once issued, then hand control back so other streams can start without blocking I/O or compute units:

```text
producer : tma_async_load(Q); tma_async_load(Kj,Vj);
          notify_consumer();
consumer : wait_for(Kj,Vj);
          s_ij ← Q * Kjᵀ ;          // WGMMA
          p_ij ← exp(s_ij – mᵢ);
          Oᵢ ← Oᵢ + p_ij * Vj     // second WGMMA
```

Had we kept all threads together, every iteration would have carried three barriers:
1️⃣ wait until MMAs finished  
2️⃣ wait until exponentials were ready  
3️⃣ wait until registers were flushed back into global memory  

This serial chaining leaves Tensor Cores idle half the time because they’re blocked waiting either for data (`tma`) or an unready exponential lane (`exp`). By letting half the warps perform pure data movement while the other half sink real computation into Tensor Cores, most cycles now spend doing something useful.


---

## 2\. The circular shared‑memory buffer 

A single CTA processes several blocks ($B_c$) of keys & values ($K_j$, $V_j$). Between two successive “consumer” iterations there are only two states inside shared memory:

| state | contents             |
|-------|----------------------|
| Stage *s* | current pair $(K_w,V_w)$ |
| Stage *(s+1)%S* | next pair $(K_{w+1},V_{w+1})$ |

With this circular buffer there is always one stage ready when a consumer finishes its second GEMM while another stage is being filled by producers overnight “ping‑ponging” through stages $0…S−1$. With $\verb|maxNRegs$ you simply dictate how many registers each group claims—consumers need more because they own GEMM operands plus partial sum accumulators (`Oᵢ`, `$mᵢ$`, `$ℓᵢ$`), whereas producers keep their footprint tiny (just one sign bit per resource).


---

## 3\. Ping‑Pong scheduling across trigonometric functions

Softmax’s exponential operation is performed on a separate ASIC that provides only ∼4 TFLOPS even on Hopper’s top fanout board — far below what Tensor Cores deliver (~1 TFLOP per half-cycle). Rather than idle those units behind slow matmul spikes, FlashAttention‑3 lets one vibrational group finish an exponential sweep “on top” while its neighbour simultaneously drives another GEMM forward:

```
Stage j         |      Stage j+1
producing K_{j+1}/V_{j+1}
-----------→-----
compute S_{j+1} = Q • K_{j+1}ᵀ            // async WGMMA wakes immediately
softmax(...)             // pipelined against next GEMM
compute O_{i} += P_{j}•V_{j}
```

In effect we double–use every clock cycle such that Tensor Core throughput becomes almost fully saturated while special-function pipes throttle along side them.


---

## 4\. Low‐precision acceleration (FP8)

Once the producer–consumer separation worked out cleanly we can harness Hopper’s newest FP8 Tensor Cores by satisfying their stricter layouts:
* V tiles must be **k‑major** in SMB/loading strides,
* Intermediate accumulators must be laid out `(0–9)` versus `(0–9)` distinct shuffle order,
so before launching any PP stream we perform an *in–kernel transpose*. This relies purely on LDSM/STSM instructions that collapse eight-by-eight blocks directly into registers without explicit shuffling — effectively turning each twice as many primed occupants into efficient accumulators without paying an extra synchronization penalty.

# Softmax Meets Matrix Multiplication There Goes Your Bottleneck  

## Why attention still chokes

Transformer models have made astonishing strides because their self‑attention layer lets every token talk directly to every other token.  
In mathematical notation an attention head takes three tensors  
\[
\mathbf{Q},\,\mathbf{K},\,\mathbf{V}\;\in\;\mathbb{R}^{N\times d}
\]
and produces an output tensor
\[
\mathbf{O}= \operatorname{softmax}\!\bigl(\tfrac1{\sqrt d}\,\mathbf{Q}\mathbf{K}^{\top}\bigr)\,\mathbf{V}.
\]
A single forward pass does two large matrix multiplications followed by a row‑wise softmax that fuses exponentials,
normalisation factors, and another matrix multiplication.\[
    \text{GFLOPs} =4\,N^2\,d .
\]

While a generous batch size lets GPUs execute many small matmuls in parallel, the core problem remains that **softmax sits entirely outside the high‑throughput Tensor Core engine** it needs the full score matrix \(\mathbf{s}=\mathbf{Q}\mathbf{K}^{\top}\) before it can run an exponential—a burst that requires the slow “special function unit” (SFU). On an H100 the tensor core delivers well over \(900\,\text{TFLOPs}\) while exponentials run below \(4\,\text{TFLOPs}\). Thus a naïve kernel often carries dozens of seconds worth of latency waiting for a tiny percent‑of‑work step that forces most threads idle.”

FlashAttention‑1 already eliminated this problem by fusing all intermediate tensors into one streaming kernel so there were no global‑memory reads/writes between consecutive operations. Yet even on Hopper GPUs “FlashAttention‑2” still turned out only **35 % GPU utilisation** despite Tensor Cores working hard—far below what an optimized GEMM achieves (≈ 80–90 %).  

What’s missing?

* Explicitly exploiting **asynchronous execution** baked into Hopper’s TMA copies & WGMMA matmul units  
* Systematic overlap between “slow” softmax and “fast” matmul  
* Ability to run everything once in **low precision** without blowing up errors  

That’s what FlashAttention‑3 brings.



--------------------------------------------------------------------

## The new sauce – Warp‑specialisation + pipelining

### Producer–consumer warps  

In Hopper each streaming multiprocessor has four **warpgroups** (32×4 threads) that you can assign distinct roles:

| Warpgroup | Role | Primary work |
|-----------|------|--------------|
|producer | load | Asynchronously copies tiles \(Q_i,K_j,V_j\) from GMEM → SMEM via TMA |
|consumer | compute | Runs SS‑GEMM (\(Q_i K_j^{\top}\)), SHARP‑softmax reductions, RS‑GEMM (\(\tilde P_i V_j\)) using WGMMA |

Because TMA copies online run concurrently with Tensor Core work you immediately get **overlap between data movement and computation** without any special bar`rier` stalls.



### Ping‑pong scheduling across warpgroups  

With two consumer warpgroups you can let “warp A” finish its SS‑GEMM on key tile \(j+1\) while “warp B” immediately starts its RS‑GEMM on value tile \(j-1\). At the same time each remaining warp group executes **the softmax branch** belonging purely to its own iteration stepping over already computed scores. In pseudo language

```
for j=0 … Tc:
    producer copies Kj,Vj async
    consumer_A SS-GEMM Kj --------------------        // async
    consumer_B RS-GEMM Vj---------------------        // async
    consumer_B softmax Kj async-----------------
    consumer_A wait/SWAPH -------------------------------------------------
```

This keeps both sets of Tensor Cores busy while SFU work gets hidden underneath them—exactly what would happen if you had a kitchen where someone burns toast while someone else cooks spaghetti 🎯



### Two‑stage intra-warpgroup pipeline  

Inside one consumer group even tighter overlap is possible. After computing scores \(S_{\text{cur}}\), you simultaneously start computing \(S_{\text{next}} = Q_iK_{j+1}^{\top}\) while feeding current \(\tilde P_{\text{cur}}\) into RS‑GEMM against \(V_{j-1}\). Switching which operation runs when requires only a few extra registers (`S_next` buffer), so register pressure stays manageable yet almost eliminates stalls caused by waiting on previous RS-GEMMs.



--------------------------------------------------------------------

## Pushing it further into low precision – FP8 everywhere

Larger GPUs increasingly expose **FP8 Tensor Cores**, which give roughly double FLOP rate versus FP16 without eating more power or die area—a boon particularly when you’re working with gigantic contexts where otherwise computation scales as \(O(N^2)\).

Two issues arise:

1. **Operand layout constraints** – GPTools’&nbsp;(FP8）WGMMA accepts operands only in k-major form while ordinary index ordering is mn-major.​  
   Solution: After loading a tile \(V_j\) into shared memory perform an **in-kernel tile transpose** using LDSM / STSM instructions that swap row-major ↔ column-major views at the register level—this relocates data without resorting either extra host passes or coalesced Global Memory store penalties.



2. **Accumulators live in FP32**, whereas operands are FP8 → mismatch between register layout expected by WGMMA makes the result wrong unless permuted carefully.\*
   By applying a byte-hack permutation (`d0 d1 d4 d5 …`) matching WGMMA’s accumulated fragment pattern you convert register contents recorded from one FMAMASICGPU session so they become legal inputs for subsequent ones.



These rewrites let us run both SS‑GEMMs and RS‑GEMMs entirely in FP8 inside one persistent kernel description despite differing operand shapes.



--------------------------------------------------------------------

## Accuracy tricks that make it *not* horribly noisy  

FP8 leaves little room for large values—an overshoot turns into wild quantisation errors suited poorly when Large Language Models have super-large activations (“outliers”). Two engineering tricks tame this danger:

* **Block quantisation** – Each query/key/value tile gets its own scale factor instead of one global scatterer. Because FlashAttention already streams data blockwise this costs essentially zero time yet keeps errors sharply bound locally.\*
* **Incoherent processing** – Multiply both `$Q$` and `$K$` together with a fixed random orthogonal transform `$M$` before quantising.\[
            (\!QM)(KM)^{\top}=\!QK^{\top}
          \]  
Dozens of researchers have shown this spreads extreme entries across many cells so MT VH ``gestgles'' leaving fewer badly scaled items per tile—purely arithmetic gymnastics protected our core equation level accuracy.



Experimentally this combination cuts RMSE down **≥ × 2 technique versus standard per-tensor FP8**.

# FP8 Transformers Made Practical – Block Quantisation + Random Orthogonalisation Yields Petaflop Speed & Accuracy

## What problem does this solve?

Modern transformers still find themselves stuck behind attention – it needs every token pair in a sequence, so those quadratic cost tensors grow rapidly when you add context length or widen model width. On today’s GPUs the compute pattern is dominated by two ideas that can be optimised yet are easy to overlook:

* **Data movement** – most prior work keeps intermediate matrices (`S`, `P`) in global memory.
* **Precision** – Hardware now offers *FP 8* Matrix‑Multiply units that roughly double the raw GOPS over former *FP 16* units, but naïve quantisation simply explodes your numerical errors when a handful of huge values appear (“outliers”) ❤

If you could get rid of the intermediate reads/writes *and* harness duplicated arithmetic power without losing accuracy, you would get a real boost both upfront FLOP count and downstream quality.


## The FlashAttention‑3 idea stack

FlashAttention‑3 integrates several layers of GPU‑specific optimisation drawn straight from Hopper’s new feature set:


| Layer | Idea | Benefit |
|-------|------|---------|
| Memory | Using *Tensor Memory Accelerator* (TMA) loads directly into shared memories while masking latency – swapping producer warps (the loaders) against consumer warps (the matmuls)+softmax logic through warp‑specialisation | Keeps SM emotes idle time hidden without extra copy passes |
| Compute | Overlap a GEMM stage (`Q × Kᵀ`) with softmax computation on the *next* batch thanks to asynchronous WGMMA execution | Each token row spends fewer cycles idle |
| Precision | Run everything through WGMMA’s *FP 8 target*, supplied two additional adaptations |
|   | • **Block quantisation** – each `Q`, `K`, `V` tile gets its own scaling factor |
|   | • **Incoherent processing** – pre‑multiply both `Q` & `K` by a cheap random orthogonal matrix before quantising |

And all together you plate an algorithm that runs straight through one persistent kernel that does *no materialise* intermediate matrices – what once took PBreads time can finish almost instantly.


## Big picture bandwidth savings

Typical transformer heads need two matrix multiplies per query row (`Q×Kᵀ` → scores ; scores × `V`). In flash form those two multiplies happen fully fused *inside shared memory*, removing any read/write cycle back-to-back across GDRAM.



Instead you see something along these lines (*run your head alive*) :

```
load Q[i]         → // async TMA
load K[j], V[j]   → // async TMA
WGMMA(Q[i], K[j]ᵀ)   // async matmul → scores
// -- while scores hidden in reg/
softmax(scores + reduce⍈ // simple rowwise normalising
WGMMA(softmax_scores × V[j]) // next matmul → partial output    
// repeat until key blocks exhausted
final rescale           // divide accumulated sums
write output O[i]
```

Notice how every kernel launch never touches global mem twice.



## Why Block Quantisation matters

Up‐to‑date manifolds treat data uniformly – one scalar stores how the whole head should map int↔fp… When your head contains just a handful of absurdly huge activations (*≈10× larger than most entries*), one single scale tears everyone apart : massive rounding offsets leak later into softmax exponentials → wrong probabilities → wrong gradients.


Block‑by‑block scalars let each tile adapt itself:


```math
S_{block} = Q_{block}\cdot K_{block}^{T}\\[4pt]
scale(Q)   = \frac{q_{\max}}{127},    % per block \\
scale(K)   = \frac{k_{\max}}{127}
```

Quantising thereafter needs almost none extra bandwidth—because flash already loads tiles incrementally—the tiny scale array costs nothing compared against most praxis.



## Incoherent processing dispels outliers

How does a bright dagger fix it *without changing linear algebra*? Put simply,

```math
Q' = Q\,M ,   K'= K\,M .
```

Selecting an orthogonal matrix `M` preserves dot products due directly depening from maths


```math
Q'\,(K')^{T}=QM\,M^{T}\!K^{T}=QK^{T}.
```

Therefore final self-attention remains untouched while composition marks allow every element inside `Q·Kᵀ` roam more uniformly among bits — so fewer amplitudes hit extreme mantissa limits when forced into f∈[−128,+127].  
Blend‑in cost comes almost for free ‑ it’s just an inexpensive Hadamard transform (O(d log d) operations), easily fused into any rotary embedding or projection routine.

# FlashAttention – The New Standard for Fast Long‑Context Models

Long‐sequence Transformers are exploding – models that read tens of thousands of tokens,
high‑resolution images, or thousands of lines of code now routinely appear in research and products.
The bottleneck that has kept these workloads under control is **attention** itself:
computing all pairwise dot‑products between queries (`Q`) and keys (`K`) scales quadratically
with sequence length (`N`). A single attention layer turns a simple `O(Nd)` matrix multiply into
`O(N²d)` floats per layer – a cost that grows far faster than any other operation in a Transformer.

_**FlashAttention‐2**, introduced in 2023, cut through this wall by fusing all intermediate
steps (`S = QKᵀ`, softmax, `PV`) into a single kernel so that intermediate matrices never touch
global memory again.* Unfortunately*, even when run on NVIDIA’s newest Hopper H100 GPUs,
the kernel was still stuck open‑circuit at only ≈35 % utilisation compared with “shopstick”
GEMMs that reach ≈80–90 %.  
The reason was simple – FlashAttention‑2 did not take advantage of two major new hardware
capabilities that Hopper brought:

| Capability | Why it matters |
|------------|----------------|
| **Full tensor‑core asymmetry** | Each warp group has its own asynchronous tensor core that can stream data directly out of shared memory while other warps issue loads concurrently (`TMA`). |
| **FP8 production targets** | Hopper’s `WGMMA` instruction doubles throughput per SM when operating on `FP8` rather than `FP16/BF16`. |

Enter **FlashAttention‑3** – an overhaul rather than an increment.
It exploits both asynchrony *and* low‑precision results in order
to squeeze maximum performance out of modern GPUs while remaining fast enough for production workloads.

---

## Core Ideas Behind FlashAttention‑3

### 1️⃣ Warp‑Specialized Producer/Consumer Pipelines

A CUDA CTA typically contains many warps.
By splitting them into **producers** (responsible solely for moving data into shared memory)
and **consumers** (solely performing compute), each warp group works *in parallel* even though they share the same registers and local storage.
Using CUDA’s `setmaxnreg` you can give every producer warps very few registers –
they just sit waiting until data arrives – while consumer warps get large register windows:
`; wgmma` instructions grab all their inputs directly from shared memory without any extra latency stalls.
This word “specialisation” turns an otherwise sequential bottleneck into two concurrent pipelines:
warp groups load query blocks (`Q_i`), key/value blocks (`K_j`, `V_j`) synchronised through a tiny circular staging buffer while others do matrix multiplies underneath.


### 2️⃣ Intra‐Warp Overlap Between Softmax & GEMMs (“Pingpong” Scheduling)

Even after hiding memory latency,
the two passes within each attention tile still ran largely serially:
  
* Perform `S = Q Kᵀ`.
* Compute rowwise softmax(`S`) → `P`.
* Accumulate `O += P V`.

The first two steps are independent while the last consumes output from step one.
In practice exponentiation is extremely cheap compared with tensor‑core multiplies:
on an H100 you can perform roughly `989 TFLOPS` of `FP16` matrix multiplies versus only around
`4 TFLOPS` worth of exp operations – the latter would sit idle if we didn’t overlap them!

FlashAttention‑3 introduces a **two‑stage pipeline**:
while one warp group finishes its second multiply (`P V`), another warp group eliminates its own softmax,
continued feeding fresh key/value tiles into tensor cores every clock cycle.
Picture it as a ping‑pong scene where two stage machines trade inventory before passing it off;
the compute engine is constantly busy even while “exp” calls flicker past.



### 3️⃣ Full Leveraging Of Hopper’s `FP8 WGMMA`

If you already enjoy top numbers with *full precision*, you’re probably disappointed
when converting your model weights down merely half bit-width.
Hopper’s tensor cores make pure *binary* multiplication trivial – 
but you’re constrained by layout rules:
the operand feeding into `WGMMA` must be **k-major** –
contiguous along the inner dimension – whereas usual tensors are stored **mn-major**
(first dimension then head dimension).
Contrary to early attempts requiring pre‐transpose kernels,
FlashAttention‑3 performs an *in‐kernel tile transpose* using PTX’s fast load / store *matrix*
instructions (`LDSM`, `STSM`). That way each key/value fragment appears directly where
tensor cores expect it without touching global memory twice.


Because FG mm's accumulator lives as an FMAC inner product it has yet another layout quirk:
its registers contain columns interleaved differently than those coming out of operand A.
A lightweight register permutation followed immediately after computation swaps columns so future multiplies line up correctly – no shuffle instructions, no wasted cycles.



#### Reducing Quantisation Error – Block Quantisation + Incoherent Processing

Simply packing whole tensors into `EF4M3(e4m3)` format would introduce huge error because LLMs contain many outliers (e.g., occasional activations two orders larger than neighbours).
FlashAttention‑3 therefore introduces two techniques widely useful elsewhere when moving down precision:

| Technique | What it does | Why it matters |
|-----------|--------------|----------------|
| **Block quantisation** | One scale factor per tiny tile instead of once per entire head tensor | Keeps dynamic range local; vastly reduces clipping in dot products |
| **Incoherent transformation** | Multiply both Q & K by random orthogonal map before quantising → keeps QQᵀ invariant | Spread exceptions across tiles ; each entry becomes mixture over many original entries → less catastrophic rounding |

Taken together this gives more than **× 4 reduction** in root mean square error over naïve per‑tensor scaling while still achieving `≈Y PFLOPs`.
