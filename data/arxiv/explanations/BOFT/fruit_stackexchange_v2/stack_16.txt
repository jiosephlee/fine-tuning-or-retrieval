### What is the actual runtime complexity of applying BOFT at training time?
Question:
The paper argues BOFT trades space for time. For input vector multiplication $y=\mathbf{R}(m,b) x$, what is the precise flop count as a function of $d$, $m$, and $b$? Is it $O(dm)$ for $b=2$ and $O(dbm)$ for blocks, or something else? How does this compare to a dense $d\times d$ multiplication ($O(d^2)$) and to LoRA's extra low-rank term addition ($O(dr)$)?
Answer:
Short answer: Applying BOFT’s orthogonal transform <|endoftext|> to a vector $x$ costs $O(d m)$ <|endoftext|> operations (linear in $d$ and linear in $m$), not $O(d b m)$. More concretely, one butterfly component (the block-butterfly block used in <|endoftext|> has $O(d)$ nonzeros, so <|endoftext|> a length-$d$ vector by one component takes $O(d)$ <|endoftext|> and $O(d)$ adds; doing that for $m$ components yields about $m\cdot(2d)$ <|endoftext|> and a similar number of adds. In common flop conventions (counting one <|endoftext|> and one add as 2 flops) this is $\approx 4 d m$ flops. By contrast a dense $d\times d$ matrix–vector <|endoftext|> costs <|endoftext|> ($\approx 2 d^2$ flops) and LoRA’s extra <|endoftext|> term $BAx$ costs $O(d r)$ ($\approx 2 d r$ flops).

Why this is true (intuitive + technical): <|endoftext|> represents the full orthogonal matrix $R$ as a product of $m$ <|endoftext|> “butterfly” components. Each component is a blockwise arrangement of many small $2\times2$ (or $2b\times2b$ in the block variant) mixing blocks; the pattern is extremely <|endoftext|> so that each component has only $O(d)$ nonzero entries (you can verify from the paper’s construction that one component contributes about $2d$ nonzeros). <|endoftext|> a vector by a <|endoftext|> matrix with $N_{\text{nz}}$ nonzeros takes $O(N_{\text{nz}})$ <|endoftext|> <|endoftext|> and $O(N_{\text{nz}})$ additions; therefore each component costs $O(d)$ work and the whole product costs $m$ times that, i.e. $O(d m)$.

Notes tying to the paper’s parameter counts and tradeoffs: BOFT’s effective number of trainable parameters scales as $\frac{1}{2}(b-1) d m$ (the paper’s formula). The runtime cost of applying <|endoftext|> to a vector depends on $m$ (the number of components) and $d$ (the dimension) but not <|endoftext|> on $b$ in the sparse-matrix sense — increasing $b$ increases the number of trainable parameters per component (hence can improve <|endoftext|> but does not change the fact that each component is $O(d)$ <|endoftext|> so the <|endoftext|> matvec cost stays $O(d)$ per component. That’s why the paper says <|endoftext|> trades space for time: you reduce parameter count (compared to a dense orthogonal with <|endoftext|> params) by using many <|endoftext|> <|endoftext|> incurring an $O(m)$ runtime overhead during training.
