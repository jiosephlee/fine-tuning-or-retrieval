Practical Guide and Recipes

# Choosing m and s under storage cap and layer width

When you bring the butterfly orthonormal routine into a pretrained linear array, two design knobs dominate the tradeoffs: the count of composed stages, which we call $m$, and the tile width inside each stage, which we call $s$. These two choices set how many tunable entries are introduced, how much arithmetic the update requires while tuning, and how flexible the final orthonormal operator can be.

A compact bookkeeping expression that is helpful to keep in mind is that the total tunable entry count grows linearly with the layer width and linearly with $m$, and it also scales with $(s-\text{one})$. A convenient symbolic form you can use while planning is
$\displaystyle \frac{\text{one}}{\text{two}}\,(s-\text{one})\,m\,n$,
where $n$ denotes the input dimension of the linear array you are adapting. Reading that expression intuitively: when $s$ is small the extra degrees of freedom per tile are small, and increasing $m$ multiplies how many of those tiles appear in sequence.

Rule of thumb guidance from the experiments and simulations in the source study:

- If storage for tunable entries is very tight, pick a small tile width (prefer $\text{two}$) and a moderate stage count. With tile width set to $\text{two}$ and stage count chosen near the logarithm (base two) of the layer width, the tunable entry budget follows the familiar near-$n\log n$ scaling that the butterfly arrangement can deliver.
- If you want fewer arithmetic steps while tuning (less runtime during adaptation), pick a smaller $m$ and a larger tile width. Larger tiles give more expressiveness per stage but increase the per-stage tunable footprint.
- If you want the densest possible final operator for a fixed tunable storage cap, prefer smaller $s$ and larger $m$. This tends to yield better approximation of a fully general orthonormal operator for the same tunable-entry budget.

When planning, convert your storage allowance into a tunable-entry cap, then solve the symbolic relation above for feasible $(m,s)$ pairs. If you prefer, start with $s=\text{two}$, increase $m$ until the tunable-entry count reaches your cap, and only then experiment with larger $s$ if runtime during tuning becomes the limiting factor.

# Where to insert BOFT in transformer blocks and in diffusion U‑Nets

The orthonormal butterfly routine multiplies a frozen pretrained linear array on the left with a learned orthonormal operator that is shared across the neurons of that layer. In practice this makes the routine naturally fit at any place where a linear mapping is used and where preserving the angular relations among neuron vectors is desirable.

In transformer stacks common insertion sites are the projection arrays inside the attention model and the two linear sublayers inside the feedforward subnetwork (the part often called the positionwise feedforward or MLP). In attention modules, applying the routine to the query and key projection arrays tends to be especially impactful when the new task primarily requires reorienting how the model computes similarity. In the feedforward subnetwork, applying the routine to the first projection (the expansion from model width to inner width) gives a strong lever to manipulate intermediate features while retaining the original spectral scale of the pretrained array.

For encoder–decoder and decoder‑only setups you can treat each linear mapping as a candidate; when in doubt, prefer the first linear in a two‑stage MLP or the attention projections that are closest to the output used in the target task.

For diffusion U‑Nets the same insertion idea applies: apply the orthonormal routine to the linear arrays in the residual blocks and to the cross‑attention projections that fuse conditioning signals. In the source experiments these positions yielded significant gains while preserving stable dynamics during sampling.

A practical prioritization when you want to limit tunable entries is to start with a small set of locations that are most task‑proximal (the projections right before task heads, cross‑attention injectors, or the first dense mapping in the MLP) and expand the set only if adaptation performance is insufficient.

# Default choices by modality and model scale

While every use case benefits from a short tuning sweep, the following defaults are a compact starting point that reflect the empirical findings in the source study.

Vision models (image encoders, image classification backbones)
- Small to moderate model widths (hundreds to low thousands): start with $s=\text{two}$ and $m$ around $\lceil \log_{\text{two}}(n/s)\rceil$; this yields very compact tunable footprint and often preserves the pretrained spectral behavior.
- Very wide models (several thousands): still prefer $s=\text{two}$ for storage parsimoniousness; increase $m$ so the composed operator can cover the necessary mixing.

Language models (decoder stacks and encoder‑decoder)
- For medium language stacks, put the routine on key linear projections in attention and on the expansion linear in the MLP. Default $s=\text{two}$, and set $m$ so the tunable-entry count is roughly on par with light additive updates that the model team might already be comfortable with.
- For very large language stacks, the small tile width plus more stages is the common strategy: it keeps per‑layer tunable entries modest while allowing sufficient flexibility overall.

Diffusion generative models (U‑Nets for image synthesis)
- Cross‑attention heads and early residual blocks are prime targets. Again, $s=\text{two}$ with moderate $m$ gives a compact, high‑quality adaptation.

These defaults are intentionally conservative: small tile width and moderate stage count yield a strong regularizing prior, often improving generalization while keeping tuning stable.

# Combining BOFT with low‑precision storage and other compact adapters

The orthonormal butterfly routine composes multiplicatively with the frozen pretrained array. This makes it naturally compatible with several other compact adaptation tricks.

Low‑precision storage. If you keep the pretrained arrays in low precision for storage economy, the multiplicative routine can be trained normally because the learned orthonormal operator is a separate set of tunable entries. Two practical approaches work well:
- Keep the pretrained arrays in the same low‑precision format during tuning, and train the tunable entries in higher precision when you perform the small inversions needed for the orthonormal mapping. Use higher numeric precision for the local linear algebra that enforces orthonormality while keeping the bulk storage compact.
- Alternatively, fuse the learned orthonormal operator into the pretrained array after tuning and then re-quantize the fused array for deployment. Fusion eliminates any extra cost at serving time.

Combining with additive compact updates. The multiplicative orthonormal routine does not conflict with additive two‑factor updates (the family that updates a pretrained array by adding a product of two small arrays). If your workflow already uses an additive compact adapter, you can:
- Train the multiplicative routine while keeping the additive adapter frozen, or
- Train both simultaneously, allowing the multiplicative routine to reorient the pretrained space and the additive adapter to provide small residual corrections.
Empirically, using both can sometimes improve final performance, since the multiplicative part preserves spectrum and coarse geometry while the additive part supplies fine localized change.

When combining methods keep an eye on total tunable‑entry budget and on numerical precision during orthonormal enforcement steps.

# Runtime and memory: tuning overhead versus deployment parity

Two practical performance notes come from the source study.

Tuning time. Because the orthonormal operator is composed as a small sequence of staged arrays, each update requires applying that sequence during the forward and backward passes. This composition yields a modest runtime overhead during adaptation compared with an approach that only updates a single small additive term. The overhead grows with $m$ because each composed stage incurs arithmetic and gradient work.

Memory in tuning. The tunable entries described earlier are typically a small extra memory footprint compared with keeping the pretrained arrays in memory. However, automatic differentiation needs to keep intermediate activations for the composed stages during the backward pass; for very large $m$ this can increase peak memory use. Two practical mitigations are checkpointing of intermediate stage activations and using the smaller tile width ($s=\text{two}$) which reduces per‑stage activation size.

Deployment (serving). A useful property is deployment parity: after tuning finishes you can multiply the learned orthonormal operator into the frozen pretrained array and store only the fused array for serving. That means the adaptation introduces no extra cost at run time if you perform fusion and then reformat the fused array into your deployment precision. In short: modest extra cost while tuning, zero overhead after fusion for serving.

# Debugging tips: loss of orthonormality, NaN issues in inversion, numeric fixes

Because the routine keeps each stage orthonormal via a rational mapping that inverts an array like $(I - Q)$ where $Q$ is skew‑symmetric, a few numerical pathologies can arise during tuning. Here are practical checks and remedies.

Monitor orthonormality. Periodically compute the deviation metric $\|R^\top R - I\|_F$ for a few representative adapted operators during tuning. If this deviation grows, consider the mitigations below. Avoid the banned practice of trusting final loss alone to detect drift.

Small step sizes for the skew update. Use conservative learning gains for the variables that parameterize the skew‑symmetric $Q$ arrays. When those gains are too aggressive the mapping inversion can approach singularity and cause instabilities.

Add a tiny diagonal jitter. If you see near‑singular inversion when forming $(I-Q)^{-1}$, add a tiny multiple of the identity to the term being inverted: invert $(I-Q+\varepsilon I)$ with $\varepsilon$ set to a tiny scalar like $10^{-6}$ in double precision. This stabilizes the solver and prevents dramatic condition number blowups.

Use higher precision for inversion. If your training stack supports mixed precision, allocate the inversion and any orthonormal checks to higher precision (for example running those few linear solves in FP64 or FP32 while the bulk model stays in a lower format). This keeps the core cost small but helps numerical robustness.

Clip skew entries. If NaN appears, as an emergency measure clip the entries of the skew variable $Q$ to a bounded range before computing the rational mapping. Clipping bounds the condition number growth and can recover training.

Periodic reinitialization of stages. If a stage has drifted badly, replace that stage with the identity operator $I$ for a short warmup and then resume tuning. Replacing with $I$ restores the original pretrained orientation for that stage while leaving other stages intact.

Watch learning rate interaction with other adapters. If you combine the multiplicative routine with additive adapters, ensure their learning settings are balanced. The rational mapping is more sensitive to large, rapid moves in its tunable entries than many additive updates.

When you see NaN in gradients, trace whether it originates in the inversion step, in exceptionally large activations after composition, or in an unrelated part of the model. Isolating the routine by running a small model or a tiny batch often reveals the root cause quickly.

# Worked example: an eight‑wide linear array with $m=\text{three}$ and $s=\text{two}$ — shapes and tunable counts

This minimal worked example illustrates shapes and the tunable‑entry tally in concrete terms. Suppose the linear array you are adapting maps an input vector of width $n=\text{eight}$ to some output. You choose stage count $m=\text{three}$ and tile width $s=\text{two}$.

Structure of stages. Each stage is a tiled operator that is identity‑like except for per‑tile small orthonormal tiles of size $s\times s$. With $n=\text{eight}$ and tile width $s=\text{two}$ there are $\text{four}$ tiles per stage (since eight divided by two yields four tiles). Each tile contributes tunable degrees of freedom that, for an $s=\text{two}$ orthonormal tile, equals one free scalar per tile when using a skew‑symmetric two‑by‑two parametrization and the Cayley‑style rational mapping.

Tunable‑entry count. Using the bookkeeping formula in words, the total tunable entries are one half times $(s-\text{one})$ times $m$ times $n$. Substituting $s=\text{two}$, $m=\text{three}$ and $n=\text{eight}$ gives the final tunable count of twelve. In plain terms, this tiny setup introduces twelve learnable scalars that implement a composed orthonormal reorientation for the eight‑wide layer.

Shapes during forward pass. Conceptually, the composed operator is the composition of three staged tiled operators. During a forward apply you perform three small tiled applies of shapes that each read an $n$‑length vector and write an $n$‑length vector. Internally each tile handles a pair of coordinates at a time when $s=\text{two}$, so the arithmetic per stage is small while the composition across stages yields a surprising mixing effect across the full eight coordinates.

Practical takeaways from this toy count. Twelve tunable scalars for an eight‑wide array is extremely compact and illustrates why the butterfly composition can provide rich reorientation for little storage cost. Scaling this pattern to realistic widths yields the familiar near‑$n\log n$ economy when $s=\text{two}$ and $m$ is chosen near the logarithm of the width.

# Final practical checklist

- Convert your allowable tunable‑entry budget into a target and select $(m,s)$ that satisfy $\frac{\text{one}}{\text{two}}\,(s-\text{one})\,m\,n \le$ budget.
- Start by applying the routine to the most task‑proximal linear arrays (attention projections and the first linear in MLPs). Expand only if needed.
- Default start: $s=\text{two}$; set $m$ so tunable budget is respected. Tune conservatively at first.
- During tuning use higher precision for the inversion steps and include a tiny jitter $\varepsilon$ on the inverted term if instability appears.
- After tuning, fuse the learned operator into the pretrained array and reformat for deployment to avoid any serving cost.
