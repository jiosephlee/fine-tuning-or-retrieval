Chapter 3: # Chapter 3: Prompt Engineering for Rule Extraction

## Introduction to Prompt Architecture in FeatLLM

The core innovation of the \textsf{FeatLLM} framework lies not merely in the application of a Large Language Model (LLM) to tabular data, but in the precise architectural design of the prompts that guide the model's behavior. Unlike traditional approaches that treat LLMs as black-box predictors requiring end-to-end inference for every single sample, \textsf{FeatLLM} repositions the LLM as an automated feature engineer. Its primary objective is to distill the "criteria" or underlying logic that determines class membership from a small set of labeled examples. To achieve this, the system must compel the LLM to move beyond pattern matching and engage in structured reasoning that mimics an expert human analyst. This chapter details the tripartite structure of the prompt design employed in \textsf{FeatLLM}, which is meticulously crafted to extract high-quality, interpretable rules. These rules serve as the foundation for generating new binary features, which are subsequently fed into a lightweight downstream model. The success of this pipeline depends entirely on how effectively the prompt orchestrates three distinct phases: providing basic contextual information, guiding a two-step reasoning process to isolate causal relationships, and enforcing strict formatting constraints to ensure deterministic parsing.

# Component 1: Basic Information Description (Task Framing and Feature Serialization)

The first critical component of the prompt architecture is the provision of "Basic Information," which serves as the foundational context for all subsequent reasoning. This section acts as the interface between raw tabular data and the linguistic capabilities of the LLM, ensuring that the model possesses all necessary metadata before attempting any analysis. In \textsf{FeatLLM}, this component is explicitly divided into three elements: a clear task description, detailed feature definitions, and serialized example demonstrations. The task description is framed as a direct question to anchor the model's attention on the specific prediction goal. For instance, rather than simply stating "predict heart failure," the prompt asks, "Does this patient's myocardial infarction complications data indicate chronic heart failure? Yes or no?" This interrogative format primes the LLM to seek a definitive binary or categorical answer, aligning its internal state with a classification objective rather than open-ended generation.

Following the task definition, the prompt includes rigorous descriptions of each feature present in the dataset. Since tabular data often contains heterogeneous variable types—ranging from continuous numerical values to discrete categorical labels—the LLM must be informed about these characteristics to avoid logical errors during rule construction. The feature description specifies the value type and may optionally include domain-specific definitions derived from external knowledge bases or dataset documentation. For categorical variables, it is particularly important to list possible categories within this section so that any generated rules reference valid states rather than hallucinated values. This explicit grounding prevents type mismatches later in the process and ensures that any condition derived by the model is semantically sound relative to the actual data schema available in real-world applications like healthcare or finance.

The third element of this component involves "serialization," which converts selected training samples into natural language text for inclusion in few-shot demonstrations. Because LLMs operate on token sequences rather than structured matrices, rows and columns must be flattened into readable sentences without losing informational integrity. \textsf{FeatLLM} adopts a standardized serialization format consistent with prior literature on language-interfaced tabular learning. Mathematically, given a sample $\mathbf{x}^i$ with $d$ dimensions and corresponding feature names $F = \{f_j\}_{j=1}^{d}$, along with its ground-truth label $\mathbf{y}^i$, the serialization function transforms this tuple into a textual narrative:
$$
\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = "\ f_1\ \text{is}\ \mathbf{x}^i_1.\ ... \ f_d\  \text{is}\  \mathbf{x}^i_d.\ \ \text{Answer:}\  \mathbf{y}^i\ "
$$
This format creates a coherent story for each example demonstration (e.g., "Age is 65. Cholesterol is High... Answer: Yes"), allowing the LLM to observe concrete instances where specific feature combinations lead to specific outcomes. By embedding these serialized examples alongside task and feature descriptions, \textsf{FeatLLM} provides a complete microcosm of the problem domain within a single prompt window. This comprehensive setup ensures that when the model proceeds to generate rules, it does so with full awareness of what constitutes a valid input and what constitutes a correct output, laying a stable groundwork for complex reasoning tasks even in low-shot regimes where labeled data is scarce.

# Component 2: Reasoning Instructions (Chain-of-Thought Integration)

Once basic information is established, \textsf{FeatLLM} introduces "Reasoning Instructions" designed to enforce a logical progression similar to Chain-of-Thought prompting techniques used in advanced reasoning tasks. The central hypothesis driving this design is that immediate rule generation from raw data often leads models to latch onto spurious correlations—coincidental patterns present in small datasets but invalid generally—to satisfy their predictive drive instantly. To counteract this tendency toward superficial pattern recognition, \textsf{FeatLLM} decomposes the inference process into two distinct sequential steps within a single prompt interaction. This structural separation forces the LLM to pause its generative impulse and first construct an abstract understanding of causality before committing to concrete operational rules.

The first step of this guided reasoning process instructs the LLM to infer causal relationships or general tendencies between features and target classes without referencing any specific example demonstrations yet provided in few-shot mode. During this phase, relying solely on its vast pre-trained knowledge base and common sense reasoning capabilities stored within its parameters allows the model to activate relevant domain priors—for example, recognizing that older age generally correlates with higher cardiovascular risk regardless of specific patient records seen moments ago. By isolating this step from empirical evidence initially contained in few-shot examples, \textsf{FeatLLM} leverages external world knowledge encoded during pre-training while filtering out noise
