# Chapter 1: Foundations of Tabular Learning and the LLM Revolution

## The unique challenges of tabular data: heterogeneity and low-shot regimes

Tabular data remains the backbone of many real-world applications, ranging from healthcare diagnostics to financial risk assessment, yet it presents distinct challenges that differentiate it from other data modalities like images or natural language. The primary difficulty lies in the heterogeneous nature of tabular datasets, where a single table can contain a mixture of numerical, categorical, and textual features, each with its own scale, distribution, and semantic meaning. Unlike images, which have a uniform grid structure, or text, which follows sequential linguistic rules, tabular data lacks a universal structure that allows for straightforward generalization across different domains. This heterogeneity makes it exceptionally difficult to design universally applicable data augmentation strategies. For instance, techniques that work well for augmenting image data by rotating or cropping pixels cannot be directly applied to a column representing "credit score" or "blood pressure" without risking the introduction of semantically invalid samples. Consequently, standard deep learning approaches often struggle to find robust representations when faced with this diversity, particularly when the available labeled data is scarce.

The scarcity of labeled data defines the low-shot regime, a scenario where only a handful of examples are available for training a model. In such settings, traditional machine learning models face a high risk of overfitting or learning spurious correlations—coincidental patterns in the training data that do not reflect true causal relationships. For example, a model might incorrectly associate a specific hospital ID with a disease outcome simply because that hospital appeared frequently in the small training set, rather than learning the actual medical indicators of the disease. While unsupervised pre-training and self-supervised learning have shown promise in other domains by leveraging vast amounts of unlabeled data to learn general representations, these strategies have not been notably effective in few-shot tabular settings. The difficulty in defining meaningful reconstruction objectives or contrastive learning tasks for heterogeneous tabular columns limits the ability of these methods to impart appropriate inductive biases when labeled examples are extremely limited. Therefore, there is a critical need for methods that can leverage external sources of information to guide learning effectively without relying on massive quantities of task-specific labeled data.

## Overview of traditional few-shot learning techniques (pre-training, augmentation, transfer learning)

To address the limitations of training from scratch with minimal data, researchers have developed several traditional few-shot learning paradigms focused on extracting generalizable representations. One prominent approach involves semi-supervised learning and unsupervised pre-training on large quantities of unlabeled tabular data. Methods in this category often employ techniques such as masking parts of the data and using reconstruction objectives to force the model to learn underlying structures. Alternatively, some approaches utilize contrastive learning objectives where augmented views of the same sample are pulled closer in the embedding space while different samples are pushed apart. However, as noted earlier, the heterogeneous nature of tabular features makes finding universally applicable augmentations challenging. Strategies like random masking or value corruption may not preserve the semantic integrity of complex categorical variables or inter-column dependencies, leading to suboptimal feature representations that fail to generalize well in low-shot scenarios.

Another significant line of research focuses on transfer learning across diverse tabular datasets. The premise here is that knowledge gained from solving many different tabular tasks can be transferred to new tasks with few examples. Models like TransTab attempt to learn semantic relationships between columns by analyzing column names and table structures across a broad range of datasets during pre-training. Similarly, TabPFN utilizes a Bayesian neural network pre-trained on synthetic data generated by mixing various distributions to capture prior knowledge about different types of tabular problems. These models aim to provide good initializations or priors that allow for rapid adaptation to new tasks with minimal fine-tuning or even zero-shot inference. While these approaches have demonstrated success in surpassing traditional tree-based methods like Random Forests or XGBoost in certain few-shot settings by leveraging prior knowledge from diverse distributions, they still rely heavily on the assumption that the target task shares sufficient structural similarity with the pre-training distribution. Furthermore, these methods often require significant computational resources for pre-training and may not fully capture domain-specific nuances that are not represented in their synthetic or broad pre-training corpora.

## The rise of LLMs in reasoning and their application to structured data

The emergence of Large Language Models (LLMs) has introduced a paradigm shift in how we approach reasoning tasks across various domains. Trained on extensive and diverse text corpora containing vast amounts of human knowledge, LLMs possess an unprecedented ability to generalize to unseen tasks without requiring task-specific fine-tuning through mechanisms known as in-context learning. By simply providing a task description and a few examples within an input prompt, LLMs can "attend" to important features and infer complex relationships based on their rich prior knowledge. This capability suggests that LLMs can act as expert domain specialists capable of understanding context and reasoning about problems that would traditionally require deep human expertise. For instance, an LLM can leverage its internal knowledge base regarding medical conditions to understand that older age might correlate with higher risks for certain diseases, even if this specific correlation is not explicitly present in the few training samples provided for a particular prediction task.

Recognizing this potential, recent efforts have extended the utilization of LLMs into the domain of tabular learning by serializing structured data into natural language text formats suitable for model input. These approaches typically involve converting rows and columns into descriptive sentences—such as "Age is 45," "Blood Pressure is high"—and feeding them into the LLM alongside feature definitions and task descriptions. The LLM then uses its reasoning capabilities to infer relationships between features and target labels directly within the prompt context or through parameter-efficient fine-tuning techniques like LoRA or IA3. This integration allows models to harness external world knowledge that is absent from raw numerical tables alone. For example, when predicting disease outcomes, an LLM can utilize its pre-trained understanding of pathology to weigh features more intelligently than a standard algorithm might based solely on statistical correlations found in limited training data. This has proven effective in low-shot regimes where conventional models struggle due to lack of data volume but where semantic understanding can bridge the gap between sparse examples and accurate predictions.

# Chapter 2: The FeatLLM Framework: Conceptual Overview

### Core Philosophy: Shifting from End-to-End Prediction to Automated Feature Engineering

The fundamental innovation of the \textsf{FeatLLM} framework lies in a paradigm shift regarding how Large Language Models (LLMs) are utilized within the domain of tabular learning. Traditional approaches to leveraging LLMs for tabular data often treat the model as a black-box predictor, where the LLM is queried directly for every single data sample to generate a final classification or regression output. In these end-to-end methods, the LLM must process serialized tabular data, feature descriptions, and task instructions for each individual inference request. While effective in some contexts, this approach introduces significant computational costs and latency, as it requires an API call for every prediction. Furthermore, it is heavily constrained by the context window limits of the LLM; as the number of features in a dataset grows, the serialized text representation often exceeds the allowable prompt size, rendering the method infeasible or causing a degradation in performance.

\textsf{FeatLLM} departs from this conventional trajectory by reassigning the role of the LLM from a direct predictor to an automated feature engineer. Instead of asking the LLM to predict whether a specific patient has heart failure based on their raw data points, \textsf{FeatLLM} asks the LLM to act as an expert analyst who understands the underlying criteria or "rules" that distinguish different classes. The model leverages its vast prior knowledge and reasoning capabilities to infer causal relationships or tendencies between features and target labels. For instance, rather than memorizing specific data points, the LLM generates logical rules that describe conditions under which a class is likely to occur, such as "if age is greater than 60 and cholesterol is high, then risk is elevated." These rules are then translated into new binary features that indicate whether a given sample satisfies specific conditions. By shifting the burden of complex reasoning to a one-time feature generation phase, \textsf{FeatLLM} transforms the problem into one where a simple downstream model can operate on these engineered features. This philosophy allows the framework to harness the rich semantic understanding of LLMs without being tethered to their inference bottlenecks during deployment.

### The Two-Stage Process: Rule Extraction and Likelihood Inference

The operational workflow of \textsf{FeatLLM} is structured into two distinct but interconnected stages: rule extraction and likelihood inference. The first stage focuses on extracting decisive rules that define each class using an in-context learning approach. This process begins with a carefully designed prompt that guides the LLM through a structured reasoning path mimicking an expert human analyst. The prompt first provides basic information, including task descriptions, feature definitions with value types, and few-shot examples serialized into natural language text. Crucially, the reasoning instruction component directs the LLM to perform a two-step analysis: first, it infers general causal relationships between features and the target task based on prior knowledge without looking at specific examples; second, it uses these general insights alongside few-shot demonstrations to deduce specific rules for each class. To ensure robustness and manageability, the framework instructs the LLM to generate a fixed number of rules (typically ten) per class. These rules are formulated in natural language but are structured to be easily parsed later.

Once these rules are generated by the LLM, they undergo a parsing process where they are converted into executable program code. Because LLM outputs can contain syntactic variations (e.g., using "greater than" instead of "$>$"), \textsf{FeatLLM} leverages another round of LLM interaction specifically designed to translate these natural language rules into Python code snippets that can be executed against raw data samples. When executed on a dataset, this code transforms each sample into a set of binary features; for each rule associated with a class $k$, a new feature $\mathbf{z}_k^i$ is created which takes the value $1$ if sample $i$ satisfies the rule and $0$ otherwise. This effectively replaces or augments the original high-dimensional input space with a new space defined by logical criteria derived from expert-like reasoning. The second stage involves inferring class likelihoods using these newly generated binary features. Rather than relying on complex deep learning architectures or further LLM queries, \textsf{FeatLLM} employs a simple linear model with non-negative trainable weights to estimate probabilities. The model learns how much importance to assign to each generated rule based on few-shot training data, optimizing weights $\mathbf{w}_k$ via cross-entropy loss to maximize prediction accuracy. This separation ensures that once rules are discovered and weights are tuned, no further interaction with an expensive LLM API is required for inference on new data points.

### The Role of Simple Downstream Models vs. Complex LLM Inference

A critical architectural decision in \textsf{FeatLLM} is the reliance on simple downstream machine learning models for final prediction once features have been engineered by the LLM. In contrast to methods like TabLLM or STUNT that may require fine-tuning large parameters or performing heavy computations during inference, \textsf{FeatLLM} utilizes lightweight models such as linear regression (specifically implemented here as a linear layer without bias followed by softmax). The mathematical formulation involves computing logits for each class $k$ as $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$, where $\mathbf{z}_k^i$ represents the vector of binary rule-satisfaction features for sample $i$, and $\mathbf{w}_k$ represents the learned importance weights for those rules. By projecting weights into a positive subspace using $\max(\mathbf{w}_k, 0)$, the model ensures that satisfying a rule generated by an expert-like process never decreases the likelihood of that class occurring; it only contributes positively or neutrally to the prediction score. These logits are then passed through a softmax function to produce final class probabilities $\mathbf{p}^i$.

The strategic advantage of this design is twofold: efficiency and interpretability regarding feature importance. Because the heavy lifting of understanding domain semantics and identifying relevant patterns has already been offloaded to the LLM during training (the feature engineering phase), there is no need for complex non-linear transformations during inference on new samples. A simple dot product operation suffices because the binary features themselves encode complex logical conditions (e.g., "Age > 50 AND Income < 30000"). This drastically reduces inference latency compared to end-to-end approaches where every query must traverse billions of parameters within an LLM. Furthermore, this setup allows for rapid training; since only small weight vectors need optimization rather than entire neural networks or large language models fine-tuning processes like LoRA or IA3 are unnecessary unless one wishes to adapt them specifically for other tasks not covered here). The simplicity also facilitates debugging and analysis; practitioners can inspect which specific rules (features) received high weights during training versus those filtered out due to low relevance (weights near zero), providing insight into what criteria drove successful predictions without needing access to internal attention mechanisms of opaque neural networks).

### Key Advantages: API-Only Access, Elimination of Per-Sample Queries, and Robustness

The \textsf{FeatLLM} framework offers several distinct advantages over existing state-of-the-art methods in few-shot tabular learning, primarily centered around accessibility and scalability regarding data dimensions. First and foremost is its requirement for only API-level access to Large Language Models. Many contemporary approaches necessitate access to model weights for parameter-efficient fine-tuning techniques such as LoRA or IA3, which restricts their application to open-source models like T0 while excluding top-tier proprietary models like GPT-4 that are only available via inference APIs due to security policies or licensing restrictions imposed by providers like OpenAI or Google DeepMind). By relying solely on in-context learning prompts without any gradient updates or fine-tuning steps requiring internal model access), \textsf{FeatLLM} remains compatible with any state-of-the-art closed-source model accessible through standard APIs). This democratizes access cutting-edge capabilities allowing researchers practitioners alike benefit from latest advancements without needing specialized hardware resources typically required local deployment massive models).

# Chapter 3: Prompt Engineering for Rule Extraction

The efficacy of the \textsf{FeatLLM} framework relies fundamentally on its ability to transform a Large Language Model (LLM) from a direct predictor into an expert feature engineer. This transformation is achieved not through model fine-tuning, but through a meticulously designed prompt engineering strategy that guides the LLM to extract "rules"—specific conditions associated with each answer class—from a limited set of few-shot examples. The core objective of this prompt design is to replicate the cognitive process of a human domain expert who first understands the problem context, then leverages general knowledge to hypothesize relationships, and finally derives concrete decision criteria from observed data. By structuring the input prompt into three distinct components—basic information description, reasoning instructions, and response instructions—the framework ensures that the LLM filters out uninformative features, avoids spurious correlations, and generates rules that are both semantically meaningful and programmatically parseable. This structured approach is critical for converting natural language reasoning into binary features that can be effectively utilized by a simple downstream machine learning model.

# Component 1: Basic Information Description (Task Formulation, Feature Definitions, Serialization)

The foundation of the prompt design lies in the "Basic information description" component, which serves as the contextual anchor for the LLM's reasoning process. This section provides all essential data required to solve the specific tabular learning task without overwhelming the model with unnecessary noise. It begins with a clear formulation of the task as a specific question, such as "Does this patient's myocardial infarction complications data indicate chronic heart failure? Yes or no?". This explicit task definition ensures the LLM understands the target variable and the nature of the prediction required. Following the task description, the prompt includes detailed definitions for each input feature. These descriptions specify the value type of each feature (e.g., numerical or categorical) and may include optional definitions explaining what a feature represents in real-world terms. For categorical variables, it is particularly important to provide examples of possible categories within this description to ground the LLM's understanding of the data space.

To bridge the gap between raw tabular data and natural language processing, \textsf{FeatLLM} employs a specific serialization strategy to convert training samples into text format suitable for inclusion in the prompt. This serialization follows a standardized pattern where each sample is described as a series of statements linking feature names to their values, culminating in the ground-truth label. Mathematically, for a sample $\mathbf{x}^i$ with label $\mathbf{y}^i$ and a set of feature names $F = \{f_j\}_{j=1}^{d}$, the serialization is defined as:
\begin{align}
\text{Serialize}(\mathbf{x}^i,\mathbf{y}^i, F) = ``\ f_1\ \text{is}\ \mathbf{x}^i_1.\ ... \ f_d\  \text{is}\  \mathbf{x}^i_d.\ \ \text{Answer:}\  \mathbf{y}^i\ ”
\end{align}
This format allows few-shot examples to be presented clearly within the prompt context. By providing these serialized examples alongside feature definitions and task descriptions, the LLM is equipped with both general domain knowledge (via feature definitions) and specific empirical evidence (via serialized samples). This dual input is crucial for enabling the model to distinguish between features that are genuinely predictive and those that are merely coincidental in small datasets. The basic information description thus acts as a controlled environment where the LLM can access prior knowledge while being grounded in the specific data distribution of the current task.

# Component 2: Reasoning Instructions (Chain-of-Thought Integration)

To prevent the LLM from simply memorizing patterns or identifying spurious correlations within the few-shot examples, \textsf{FeatLLM} incorporates "Reasoning instructions" that guide the model through a structured cognitive process inspired by Chain-of-Thought prompting techniques. Rather than asking for rules immediately after presenting data, this component explicitly divides the inference process into two distinct logical steps. The first step instructs the LLM to infer causal relationships or tendencies between features and the target task without referencing any specific example demonstrations. This forces the model to rely entirely on its internal prior knowledge and common sense derived from its pre-training corpus. For instance, in a medical diagnosis task, this step might lead the model to recall general medical knowledge about risk factors before looking at any patient records. This separation ensures that general domain expertise is extracted first, providing an inductive bias that helps filter out irrelevant columns before they can influence rule generation based on limited data points.

The second step of this reasoning process integrates empirical evidence with prior knowledge. Here, the LLM is instructed to use both its initial causal inferences from Step 1 and provided few-shot example demonstrations to deduce decisive rules for distinguishing classes. By anchoring rule extraction in prior knowledge first, this two-step approach significantly reduces the risk of overfitting to noise or coincidental patterns present in small training sets ($k$-shot regimes). The reasoning instructions act as a cognitive scaffold, ensuring that every rule generated has some basis in either established domain logic or strong empirical evidence from multiple examples. Furthermore, during rule formulation within this step, instructions explicitly direct the LLM to refer back to feature types defined in basic information description section. This cross-referencing mechanism prevents type mismatches and ensures logical consistency between features (e.g., ensuring numerical comparisons are only applied to numerical variables). The result is a set of rules that are not just statistically correlated with labels but are also semantically grounded in how an expert would reason about the problem domain.

# Step-by-step Reasoning: Inferring Causal Relationships Before Deducing Specific Rules

The sequential nature of reasoning—inferring causal relationships before deducing specific rules—is perhaps the most critical innovation in mitigating spurious correlations in few-shot tabular learning. In traditional few-shot settings where models directly map inputs to outputs based on limited examples, there is a high probability that random noise or irrelevant features will appear correlated with labels purely by chance due to sample size constraints (\cite{bartlett2021deep}). By mandating that Step 1 occurs independently of example demonstrations, \textsf{FeatLLM} forces a "sanity check" against general world knowledge before any specific data patterns are considered. If a feature appears frequently in positive examples but contradicts established causal logic (e.g., "age" being negatively correlated with heart disease risk when general knowledge suggests otherwise), Step 1 helps flag this discrepancy before Step 2 attempts to codify it into a rule.

This decoupling allows for more robust feature selection even when training data is scarce (\(k < N\)). When moving to Step 2, where actual sample data is introduced alongside prior knowledge hypotheses, only those relationships supported by both logic and observation are likely to be solidified into final rules. For example, if an LLM hypothesizes in Step 1 that high blood pressure increases heart failure risk (based on prior knowledge), it will then look specifically for evidence supporting this hypothesis in Step 2 using few-shot samples rather than searching blindly for any correlation across all columns including irrelevant ones like "zip code" or "patient ID". This targeted search reduces computational complexity within reasoning space and improves signal-to-noise ratio significantly compared to methods that treat all features equally during inference # Chapter 4: From Natural Language Rules to Binary Features

The transition from abstract reasoning to concrete data transformation represents a critical juncture in the \textsf{FeatLLM} framework. Once the Large Language Model (LLM) has successfully engaged in the two-step reasoning process to infer causal relationships and deduce decisive rules for distinguishing classes, these rules exist only as natural language text. For the framework to function as an automated feature engineer, these textual descriptions must be converted into executable logic that can process raw tabular data. This conversion is not merely a formatting exercise; it is a complex parsing problem where the semantic intent of the LLM must be preserved despite the inherent variability of natural language generation. The goal of this stage is to transform a set of human-readable conditions, such as "age is greater than 60 and cholesterol is high," into a computational mechanism that outputs a binary indicator for every sample in the dataset. This chapter details the methodology for navigating the noise inherent in LLM outputs, leveraging meta-prompting strategies to generate robust Python code, and constructing the final binary feature vectors that serve as input for the downstream linear model.

# The Challenge of Parsing Noisy Natural Language Outputs from LLMs

The primary obstacle in automating feature engineering with LLMs lies in the discrepancy between the structured requirements of programming and the flexible, often inconsistent nature of natural language generation. Although \textsf{FeatLLM} employs specific response instructions to guide the LLM toward a standardized format for its rules, the output inevitably contains syntactic noise and variability. Even with strict formatting constraints, an LLM may exhibit subtle deviations that break rigid parsing algorithms designed for deterministic inputs. For instance, while a rule might be intended to express a numerical threshold, the model might output "greater than" in one instance and use the mathematical symbol "$>$" in another. Similarly, logical operators might be expressed as "and," "&," or simply implied through sentence structure. This variability is not random error but a reflection of how LLMs are trained on diverse text corpora where multiple valid representations exist for the same concept.

Attempting to parse this output using traditional string-matching or regular expression techniques is fraught with failure risks. A parser designed to look specifically for "$>$" will fail to interpret "greater than," leading to incomplete feature extraction or runtime errors that halt the entire pipeline. Furthermore, LLMs may introduce minor syntactic changes based on their internal probability distributions during inference, such as reordering clauses or using synonyms for variable names that were provided in the prompt. These variations create a "noisy text" environment where the semantic meaning remains clear to a human reader but is opaque to a rigid code interpreter. The challenge, therefore, is not just to extract data but to interpret intent across a spectrum of linguistic expressions without losing precision. If this parsing step fails or produces incorrect logic, the resulting binary features will be meaningless, rendering the subsequent machine learning training ineffective regardless of how sophisticated the downstream model may be.

# Meta-prompting: Using an LLM to Generate Python Code from Natural Language Rules

To overcome the limitations of rigid parsing strategies, \textsf{FeatLLM} adopts a meta-prompting approach that leverages the very same capabilities that made LLMs effective at rule generation: their ability to understand semantic meaning and generate code. Instead of building complex external parsers to translate natural language into code, the framework instructs a second instance (or a subsequent call) of an LLM to perform this translation directly. This method capitalizes on the fact that modern LLMs are trained on vast corpora of code and possess an intrinsic understanding of programming syntax and semantics. By framing the task as "convert these natural language rules into executable Python functions," we shift the burden of syntactic normalization from a brittle algorithmic parser to a flexible neural network that can generalize across different phrasings.

The meta-prompting process involves constructing a specific input prompt that includes three key components: function signatures (defining input and output types), descriptions of what each rule should accomplish based on class definitions, and the raw natural language rules generated in the previous stage. The prompt explicitly instructs the LLM to write Python code that takes tabular data rows as input and returns binary values indicating whether each rule is satisfied. Because LLMs are adept at handling semantic equivalence—understanding that "less than 50" implies "$< 50$" regardless of how it is phrased—they can generate consistent code even when their own previous outputs were inconsistent in terminology. This approach effectively uses an LLM as its own compiler, translating its own reasoning artifacts into machine-executable instructions while preserving logical integrity. It allows the system to bypass manual rule-writing or complex regex maintenance, creating a fully automated loop from reasoning to execution.

# Executing Generated Code Safely Using Python's `exec()` Function

Once the meta-prompting step yields Python code snippets representing each rule, these snippets must be integrated into the data processing pipeline to transform raw tabular samples into binary features. In \textsf{FeatLLM}, this execution is handled using Python's built-in `exec()` function, which allows for dynamic execution of code strings at runtime. The generated code typically defines functions or logical blocks that iterate over dataset samples and evaluate conditions against feature values. By passing these dynamically generated strings into `exec()`, the framework can instantiate custom evaluation logic tailored specifically to the rules discovered by the LLM for that particular task without requiring recompilation or hard-coded logic updates for every new dataset or rule set discovered during inference trials.

The use of `exec()` introduces considerations regarding safety and scope management within production environments; however, within controlled research settings like \textsf{FeatLLM}, it provides unparalleled flexibility for handling diverse rule structures discovered across different domains (e.g., healthcare vs finance). The generated code is executed within an isolated namespace where only necessary variables (such as sample data vectors) are accessible, minimizing security risks associated with arbitrary code execution in this specific context. Upon execution, these functions process each sample $\mathbf{x}^i$ from the dataset $\mathcal{D}$ and return boolean outcomes which are immediately cast into integers (0 or 1). This dynamic execution capability ensures that even if an LLM generates slightly unconventional but logically sound Python syntax—such as using list comprehensions versus explicit loops—the system can still successfully evaluate them against real-world data points, ensuring robustness against minor coding style variations while maintaining high fidelity in rule application.

# Constructing Binary Feature Vectors ($z_k^i$) Based on Rule Satisfaction

The ultimate output of this translation phase is a structured set of binary feature vectors that replace or augment original tabular inputs for downstream modeling purposes. For every sample $\mathbf{x}^i$ in our dataset $\mathcal{D}$ and for each target class $k$, we construct a vector denoted as $\mathbf{z}_k^i$. If we assume there are $R$ rules extracted by the LLM for class $k$, then $\mathbf{z}_k^i$ becomes an $R$-dimensional vector where each element corresponds to one specific rule: $\mathbf{z}_k^i \in \{0, 1\}^R$. An element $z_{k,r}^i = 1$ indicates that sample $i$ satisfies rule $r$ associated with class $k$, while $z_{k,r}^i = 0$ indicates non-satisfaction. This transformation effectively discretizes continuous or categorical relationships identified by prior knowledge into explicit boolean flags that capture whether specific criteria are met by individual data points across all classes simultaneously forming part of our expanded feature space ready for probabilistic inference via linear models later described in Section~\ref{Sec:training}.
