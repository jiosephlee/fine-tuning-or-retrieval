\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does FeatLLM technically resolve the prompt size limit when dealing with datasets containing >100 features?
Question:
The paper mentions that existing LLM-based tabular methods fail when the serialized text length becomes too long due to a high number of features (e.g., the 'Communities' dataset with >100 attributes). The authors claim FeatLLM overcomes this using 'feature bagging'. 

However, I am confused about the mechanics here. If the LLM needs to understand the relationship between *all* features and the target to generate valid rules, doesn't selecting a subset of features for each prompt iteration mean the LLM might miss critical interactions involving features excluded from that specific batch? How does the ensemble of these partial views mathematically guarantee that no global interaction patterns are lost?
Answer:
FeatLLM resolves the prompt size limitation not by attempting to force all features into a single context window, but by reframing the problem as an ensemble of "weak learners," where each learner operates on a randomized subset of features (bagging). You are correct that a single prompt iteration cannot capture every possible global interaction if features are excluded; however, the framework relies on the statistical principle that while individual rule sets derived from partial feature subsets may be incomplete or biased toward local correlations, the aggregation of many such independent trials converges toward the true decision boundary.

Technically, FeatLLM implements this by running the rule-generation pipeline $T$ times (where $T=20$ in their experiments). In each trial, a random subset of features and/or training instances is selected to construct a compact prompt that fits within the LLM's token limits. The LLM then extracts a fixed number of rules (e.g., 10) based solely on this reduced view. Crucially, these rules are converted into binary features and fed into a simple linear model where weights $\mathbf{w}_k$ are learned via gradient descent to maximize class likelihood. Because this process is repeated with different random seeds and feature bags, distinct trials will discover different subsets of valid rules—some capturing interactions between Feature A and B in one trial, while another trial captures Feature C and D.

The "guarantee" against losing critical global patterns lies in this ensemble mechanism rather than any single prompt's completeness. As stated in the paper, if an important interaction involves two features that happen to be separated in a specific bagged subset, that specific trial will simply fail to generate that specific rule. However, across hundreds of combinations over $T$ trials, highly probable and meaningful feature interactions are statistically likely to appear together in enough subsets to be rediscovered by the LLM multiple times. The final prediction averages the probabilities from all $T$ weighted models. This approach leverages the LLM's self-consistency property: rules that reflect genuine underlying data logic tend to recur across different randomizations, while spurious or noise-driven rules remain isolated and get diluted during averaging. Thus, FeatLLM trades the depth of a single exhaustive analysis for the breadth of multiple shallow analyses, effectively bypassing the quadratic memory constraints of full-feature serialization while maintaining robustness through voting.

### What is the justification for constraining weights to be non-negative in Equation 2?
Question:
In Section 3.2, the authors define the logit calculation as:
$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$
The paper states: "By projecting these weights into a positive subspace, we can ensure that the features generated by the LLM do not reduce the likelihood of a class during learning."

This seems counter-intuitive. In standard logistic regression or linear classifiers, negative weights are essential to indicate that a feature is evidence *against* a class (i.e., reducing probability). Since $\mathbf{z}_k^i$ represents whether a rule for class $k$ is satisfied, shouldn't satisfying a rule always increase probability? Or did I misunderstand how the binary features are constructed? If a rule is 'Age < 30' for 'Heart Disease', wouldn't satisfying it actually decrease likelihood? Does this constraint force every generated rule to be strictly positive evidence?
Answer:
The justification for constraining weights to be non-negative in Equation~2 stems directly from the specific semantic construction of the binary features $\mathbf{z}_k^i$ within the \textsf{FeatLLM} framework. Unlike standard tabular learning where raw numerical features can naturally encode inverse relationships (where a higher value decreases the probability of a class), \textsf{FeatLLM} transforms the input into binary indicators representing whether a specific **rule** for class $k$ is satisfied.

As described in Section~3.2, the Large Language Model is prompted to explicitly generate rules that identify conditions under which a sample belongs to class $k$. Consequently, the feature vector $\mathbf{z}_k^i$ contains a $1$ only if the sample meets a criterion deemed supportive of class $k$, and $0$ otherwise. In this design, a "true" feature activation inherently signifies evidence *for* the class, not against it. Therefore, assigning a negative weight to such a feature would logically imply that satisfying a condition intended to support class $k$ actually reduces its likelihood, which contradicts the generative intent of the rule extraction process. By enforcing $\mathbf{w}_k \geq 0$, the model ensures that the contribution of any activated rule is additive, aligning with the interpretation that satisfying more valid rules for a class should monotonically increase its predicted score before normalization by Softmax.

Regarding your intuition about negative evidence (e.g., "Age < 30" decreasing heart disease likelihood), this logic is handled by the rule generation phase rather than the weighting phase. If "Age < 30" is indeed protective against heart disease, an expert-like LLM reasoning process (guided by Step~1 in Section~3.1) would simply not generate "Age < 30" as a rule for predicting "Heart Disease." Instead, it would likely generate "Age > 30" or similar conditions as positive evidence for that class, or perhaps generate "Age < 30" as a rule for the complementary class ("No Heart Disease"). Thus, every binary feature passed to Equation~2 is semantically guaranteed to be positive evidence for its respective target class, rendering negative weights unnecessary and potentially harmful to the model's consistency with its own generated logic.

### Clarification on the two-step reasoning process vs. Chain-of-Thought in Prompt Design
Question:
The paper describes a specific prompt design where Step 1 involves inferring causal relationships using *only* prior knowledge (no examples), and Step 2 derives rules using examples + Step 1 results.

I am struggling to see how this differs fundamentally from standard Chain-of-Thought (CoT) prompting where examples usually contain both data and logic. Why is explicitly separating 'prior knowledge inference' from 'data-driven rule deduction' necessary? Could this separation cause issues if the LLM's prior knowledge conflicts with the few-shot data provided in Step 2? For instance, if common sense says Feature A implies Class B, but all few-shot examples show Feature A implying Class C, how does Step 2 override Step 1?
Answer:
The distinction between FeatLLM's two-step reasoning process and standard Chain-of-Thought (CoT) lies primarily in the explicit decoupling of **general prior knowledge** from **data-specific evidence**, a design choice intended to mitigate spurious correlations in low-shot tabular learning. In standard CoT prompting, the model typically reasons through a mix of provided examples and internal knowledge simultaneously, which can lead the model to latch onto coincidental patterns present in the few-shot examples rather than true causal mechanisms. FeatLLM addresses this by forcing Step 1 to rely exclusively on the LLM's pre-trained world knowledge to hypothesize causal relationships between features and targets before seeing any data. Only in Step 2 does the model integrate these hypotheses with the actual few-shot examples to derive concrete rules. According to the paper, this separation allows the LLM to act as an expert feature engineer who filters out uninformative features early, preventing the identification of noise as signal.

Regarding your concern about conflicts between prior knowledge and contradictory few-shot data, the framework relies on a **downstream trainable linear model** to resolve these discrepancies rather than expecting the LLM alone to perfectly override its own priors during generation. If common sense suggests Feature A implies Class B, but all few-shot examples show Feature A implying Class C, Step 1 might initially generate a rule favoring Class B based on general knowledge. However, when these rules are converted into binary features and fed into the linear model (Eq. $2$ in the paper), the optimization process learns weights ($\mathbf{w}_k$) that reflect the actual statistical correlation in the training data. If a rule derived from prior knowledge contradicts the few-shot evidence, its corresponding weight will be driven toward zero or remain negligible during training, effectively filtering out that specific rule from influencing the final prediction. The paper notes that this mechanism allows irrelevant or conflicting rules to be "automatically filtered out" during tuning, ensuring that data-driven signals dominate when sufficient evidence exists in the few-shot set, while still benefiting from prior knowledge when data is extremely sparse. Thus, Step 2 does not necessarily force an immediate textual override of Step 1 within the prompt; instead, it creates a hypothesis space that is subsequently pruned by empirical performance on the provided samples.

### Is there a risk of circular dependency when using an LLM to parse its own generated rules?
Question:
In Section 3.2 ('Parsing rules for feature generation'), the authors acknowledge that LLM-generated rules have noisy syntax (e.g., writing 'greater than' instead of '>'). To solve this, they construct a new prompt asking an LLM to convert these natural language rules into executable Python code.

This feels like using an LLM to fix errors made by an LLM. If the initial rule generation contains semantic hallucinations or logical flaws, won't the second LLM call simply propagate or even amplify these errors rather than correcting them? Is there any mechanism mentioned for validating that the generated Python code actually implements the intended logic before execution?
Answer:
No, the paper explicitly argues against the risk of error amplification by implementing a dual-layer defense mechanism consisting of statistical weighting and ensemble aggregation, rather than relying solely on the second LLM call to correct semantic flaws. While the authors acknowledge that LLM-generated rules contain syntactic noise (e.g., using "greater than" instead of "$>$") and rely on a secondary LLM prompt to translate these natural language rules into executable Python code, they do not claim this translation step validates the *logic* of the rule itself. Instead, the system handles potential semantic hallucinations or logical errors through the downstream training phase described in Section 3.2. Once the rules are converted to binary features, a linear model with non-negative trainable weights ($\mathbf{w}_k$) is optimized via cross-entropy loss on the few-shot training data. Crucially, this optimization process allows the model to learn the importance of each rule; if a generated rule is logically flawed or semantically incorrect, its corresponding weight will naturally converge toward zero (or remain negligible), effectively filtering it out during inference as noted in the "Quality of features" analysis where irrelevant rules are discarded post-tuning.

Furthermore, the framework mitigates residual risks through an ensemble strategy involving bagging and high-temperature sampling. By repeating the entire rule-generation and parsing pipeline multiple times (e.g., $20$ trials), FeatLLM leverages the principle of self-consistency: while individual runs may produce hallucinated or erroneous rules, correct patterns tend to emerge consistently across different trials. The final prediction averages probabilities derived from these diverse weak learners, ensuring that isolated errors in specific rule generations do not dominate the final output. Therefore, rather than creating a circular dependency where one LLM blindly fixes another's mistakes, FeatLLM treats LLM outputs as a pool of candidate hypotheses that are rigorously validated and weighted by traditional machine learning algorithms trained on actual data labels.

### Why does FeatLLM outperform TabLLM if TabLLM uses parameter-efficient fine-tuning?
Question:
TabLLM (one of the baselines) uses parameter-efficient tuning techniques like IA3 or LoRA on top of an LLM. Intuitively, fine-tuning allows a model to adapt its internal representations specifically to the task distribution.

FeatLLM relies entirely on in-context learning for feature generation and then switches to a simple linear model for prediction. Despite lacking direct gradient updates on the base model parameters relative to the specific tabular task, FeatLLM reportedly outperforms TabLLM significantly in few-shot regimes. Is this purely due to better feature representation (the rules), or is there something inherent about fine-tuning large models on tiny tabular datasets that causes catastrophic forgetting or poor convergence?
Answer:
The primary reason FeatLLM outperforms TabLLM in few-shot regimes is not necessarily because fine-tuning causes catastrophic forgetting, but rather because FeatLLM avoids the severe **overfitting** risks inherent in updating massive model parameters on extremely sparse data, while simultaneously leveraging the LLM's pre-trained world knowledge more effectively through a structured reasoning pipeline.

While TabLLM employs parameter-efficient fine-tuning (PEFT) techniques like LoRA or IA3 to adapt the LLM to the specific tabular distribution, doing so with only a handful of examples (few-shot) creates a high variance scenario where the model rapidly fits noise or spurious correlations present in the tiny training set. In contrast, FeatLLM treats the LLM strictly as a feature engineer using **in-context learning**. By prompting the LLM to explicitly derive logical rules (e.g., "$\text{age} > 60 \land \text{cholesterol} > 200$") based on both its vast pre-trained priors and the few provided examples, FeatLLM extracts interpretable, semantically meaningful features before passing them to a lightweight linear model. This decoupling allows the system to utilize the LLM's general knowledge without forcing its billions of parameters to shift slightly toward a dataset that is statistically insufficient to justify such updates.

Furthermore, FeatLLM incorporates an **ensemble mechanism with bagging**, which significantly enhances robustness in low-data settings. The paper notes that by running multiple rule-generation trials with randomized seeds and subsets of data, FeatLLM aggregates diverse hypotheses, filtering out incorrect rules generated in individual runs. This "wisdom of crowds" approach stabilizes predictions far better than a single fine-tuned trajectory in TabLLM. Additionally, TabLLM faces practical limitations regarding prompt size and context windows when dealing with high-dimensional tabular data; FeatLLM circumvents this by generating compact binary features derived from rules, allowing it to scale efficiently even when the raw feature count is large. Ultimately, FeatLLM succeeds because it aligns the strengths of LLMs—reasoning and knowledge retrieval—with a simple learner that can generalize well from engineered features, whereas TabLLM struggles to find a stable optimization path when trying to adapt a giant model to microscopic data signals.

### "Spurious Correlations" Analysis: How does Bagging help filter noise if noise is consistent across trials?
Question:
In Section 4.2 ('Effect of adding spurious correlations'), FeatLLM shows robustness against added irrelevant columns. The explanation given is that forcing consideration of prior knowledge prevents generating rules based on irrelevant columns.

However, later in Section 3.2 regarding Ensembling/Bagging, it mentions that randomness is introduced via temperature and shuffling demonstrations. If an irrelevant column happens to correlate strongly with the target in a specific random subset of data (due to chance in low-shot settings), isn't it possible for multiple independent trials to independently discover and encode this spurious correlation as a 'rule'? Would averaging probabilities across ensembles truly eliminate this if multiple models agree on false positives?
Answer:
The concern that bagging might fail to filter spurious correlations if multiple independent trials coincidentally agree on a false pattern is valid in theory, but **FeatLLM** mitigates this risk through a combination of structural priors and statistical dilution rather than relying solely on the randomness of the ensemble.

As detailed in Section 4.2, the primary defense against spurious correlations is not the ensemble mechanism itself, but the **two-step reasoning instruction** embedded in the prompt design (Section 3.1). Before the LLM examines the few-shot examples to derive rules, it is explicitly instructed to infer causal relationships based on **prior knowledge** alone. This forces the model to establish a conceptual grounding for what constitutes a relevant feature before looking at the data distribution. Consequently, even if an irrelevant column happens to correlate perfectly with the target in a specific low-shot subset (a chance alignment), the LLM is guided to reject it if it lacks semantic plausibility according to its pre-trained world knowledge. The paper notes that rules based on such noisy columns accounted for only $1$–$2$\% of the total generated rules, demonstrating that this "prior-knowledge-first" constraint effectively filters out most spurious patterns before they ever enter the ensemble pool.

Regarding your specific worry about multiple trials converging on a false positive: while it is theoretically possible for stochastic sampling (via temperature and shuffled demonstrations) to occasionally reinforce a wrong rule, the ensemble method functions as a **probabilistic filter**. The framework relies on the principle of self-consistency, where true signals are expected to emerge across diverse subsets of data and feature combinations, whereas spurious correlations—being artifacts of specific random splits—are unlikely to persist consistently across $T$ independent trials with different bagged subsets and demonstration orders. Even if a few erroneous rules slip through in individual trials, they appear sporadically rather than systematically. During the final aggregation step (Eq.~2), these inconsistent false positives contribute minimally to the averaged probability distribution compared to robust rules that appear frequently across trials. Furthermore, the downstream linear model learns non-negative weights ($\mathbf{w}_k$) via optimization; if a rule consistently correlates poorly with the ground truth across the ensemble's aggregated features, its learned weight will naturally diminish toward zero during training, effectively neutralizing its impact regardless of how many times it appeared in generation. Thus, bagging reduces variance and amplifies signal consistency, while the reasoning architecture and weight tuning act as orthogonal safeguards against systematic hallucination of noise.
