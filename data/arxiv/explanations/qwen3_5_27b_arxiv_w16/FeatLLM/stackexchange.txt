\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### How does the 'max' operation in the logit equation enforce non-negative weights?
Question:
In Section 3.2, the paper defines the logit for class $k$ as:

$$\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$$

I am confused about the mathematical implication of this. Does this mean the trainable parameter $\mathbf{w}_k$ is allowed to be negative during the optimization process (e.g., via Adam), and then simply clipped to zero before the dot product? Or does this imply a specific constraint is applied to the loss function to keep $\mathbf{w}_k$ strictly non-negative? 

The text says 'By projecting these weights into a positive subspace, we can ensure that the features generated by the LLM do not reduce the likelihood of a class.' If $\mathbf{w}_k$ were negative, wouldn't that just mean the feature is negatively correlated with the class? Why is it necessary to force all weights to be non-negative in a few-shot setting?
Answer:
The $\max(\mathbf{w}_k, 0)$ operation in the logit equation serves as a projection step that ensures the final contribution of any generated rule to the class likelihood is non-negative, without imposing a hard constraint on the trainable parameters during the optimization process. Specifically, the trainable weight vector $\mathbf{w}_k$ is allowed to take negative values during gradient descent (e.g., via Adam), but these negative values are effectively clipped to zero immediately before being multiplied by the binary feature vector $\mathbf{z}_k^i$. Mathematically, this means that if the optimizer attempts to learn a negative weight for a specific rule, that rule's contribution to the logit becomes exactly zero rather than reducing the score for that class.

This design choice is crucial because the features $\mathbf{z}_k^i$ are binary indicators derived from rules generated by an LLM, where a value of $1$ signifies that a sample satisfies a specific condition associated with class $k$. In this context, a rule generated for class $k$ is semantically intended to be evidence *for* that class. If a standard linear model were used without this projection, the optimizer could theoretically learn a negative weight for such a rule, implying that satisfying the condition actually *decreases* the probability of belonging to class $k$. This would create a logical contradiction where an LLM-derived rule for "Class A" acts as evidence against "Class A." By enforcing non-negativity via the max operation, the framework ensures inductive bias: any rule extracted for a specific class can only increase or maintain its likelihood, never decrease it. This prevents the model from learning spurious negative correlations where valid rules are treated as anti-evidence, which is particularly important in few-shot settings where data scarcity makes it easy to overfit to noise or contradictory patterns. The paper explicitly notes that this projection ensures features "do not reduce the likelihood of a class," effectively treating the learned weights as importance scores that can be zeroed out (ignored) but never inverted.

### Clarification on 'Feature Bagging' vs. 'Instance Bagging' in FeatLLM
Question:
The paper mentions using ensemble methods and 'feature bagging' to mitigate prompt size limitations (Introduction and Section 3.2). 

In standard Random Forests, bagging usually refers to sampling instances (rows) with replacement. However, here it seems like they are sampling features (columns) or subsets of rules because of LLM context window limits.

Specifically, does 'feature bagging' in FeatLLM mean:
1. Randomly selecting a subset of the original tabular columns ($d$ features) to include in the prompt for rule generation?
2. Or does it refer to selecting a subset of the *generated* rules after they are created?

The text says: 'repeatedly generating features in conjunction with feature bagging... select a subset of features or instances for each trial'. This phrasing is slightly ambiguous. If we only feed a subset of original columns to the LLM, how do we ensure that important features excluded from that specific trial's prompt don't get missed entirely in that iteration?
Answer:
In the context of FeatLLM, "feature bagging" specifically refers to your first interpretation: randomly selecting a subset of the original tabular columns (features) to include in the prompt for rule generation, rather than sampling from the set of rules after they have been generated.

The paper explicitly addresses this in Section 3.2 under "Ensembling with bagging," stating that the method adopts bagging to "select a subset of features or instances for each trial." This is done directly to mitigate the challenge of excessive prompt size, which arises when the number of features ($d$) in a dataset is large enough that serializing all feature descriptions and data instances exceeds the LLM's context window. By feeding only a random subset of these $d$ features into the LLM for a specific trial, the framework ensures that the prompt remains within manageable limits while still allowing the model to leverage its prior knowledge on different combinations of variables.

Regarding your concern about missing important features in a single iteration, FeatLLM relies on the ensemble mechanism to resolve this. The framework repeats the entire rule-generation process $T$ times (e.g., 20 trials), where each trial uses a different random subset of features and potentially a different ordering of few-shot examples. While any single trial might exclude a critical feature, the probability that an important feature is excluded across *all* trials is negligible. Consequently, robust rules involving that feature are likely to be generated in at least some trials where it was included in the prompt. The final prediction aggregates the probabilities from all $T$ trials, effectively combining these diverse "weak learners" into a strong ensemble. As noted in the paper, this approach ensures that even if individual trials suffer from incomplete feature coverage, the collective ensemble nullifies this impact by capturing relationships across the full feature space over multiple iterations.

### Why parse LLM-generated rules into code using an LLM instead of using regex?
Question:
In Section 3.2 ('Parsing rules for feature generation'), the authors state: 'To address the challenges of parsing noisy text... we leverage the LLM itself... The generated code is executed using Python's exec() function.'

They mention that LLMs might substitute symbols like '$>$' with 'greater than'. While I understand this creates syntactic noise, I am confused why they chose to use another LLM call to generate Python code rather than using a robust natural language parser or regular expressions.

Is it because writing a regex for every possible natural language variation of comparison operators is too brittle? If so, doesn't this approach introduce a new failure mode where the *second* LLM call (the code generator) hallucinates invalid Python syntax or logic errors? How do they handle exceptions when `exec()` fails?
Answer:
The authors chose to use an LLM for parsing rather than regular expressions or rigid natural language parsers because the output of the first LLM call is semantically rich but syntactically noisy, making it extremely brittle to parse with static rules. As noted in Section 3.2, even with strict formatting instructions, the LLM may substitute standard symbols like `$>$` or `$<$` with natural language phrases such as "greater than" or "less than," or vary its phrasing in unpredictable ways. Writing a robust regular expression to cover every possible linguistic variation of comparison operators, logical conjunctions, and feature references would be prohibitively complex and fragile; a single deviation in the LLM's phrasing would cause the regex to fail.

By leveraging a second LLM call to translate these noisy natural language rules into executable Python code, the authors exploit the model's semantic understanding and its training on vast code corpora. This approach effectively treats the parsing task as a translation problem: "Here is a rule in natural language; write a Python function that implements it." While this does introduce a new failure mode where the code generator might hallucinate invalid syntax or logic, the authors mitigate this risk through their ensemble strategy described in Section 3.2. Since \textsf{FeatLLM} generates rules and parses them multiple times (using bagging and high-temperature sampling), individual parsing failures are treated as outliers. If `exec()` fails on a specific generated code snippet due to syntax errors, that specific trial simply contributes no valid features for that iteration, while other trials likely produce correct code. The final prediction aggregates results from many such trials, ensuring that occasional hallucinations do not derail the overall performance. This ensemble approach effectively filters out the noise introduced by both rule generation and code parsing, providing a more robust solution than attempting to force perfect syntactic consistency from the initial LLM output via rigid parsing rules.

### Does FeatLLM violate data leakage constraints on datasets released after pre-training?
Question:
The paper evaluates FeatLLM on datasets like 'Cultivars' and 'NHANES', explicitly stating they were added to UCI after September 2023 and thus were not part of GPT-3.5's pre-training.

However, FeatLLM relies heavily on 'prior knowledge' extracted from the LLM (Section 1 and 3.1). If an LLM hasn't seen these specific datasets during training, how can it possibly infer valid causal relationships or rules for them based on 'prior knowledge' alone?

For example, if I ask an LLM about a specific soybean cultivar dataset it has never seen, how does it know which features are predictive without seeing examples? Is it relying purely on general agricultural knowledge (which might be generic), or is there an assumption that column names alone contain enough semantic information for zero-shot rule generation? This seems contradictory to their claim that they are extracting task-specific criteria.
Answer:
No, FeatLLM does not violate data leakage constraints on datasets released after pre-training, because the framework is explicitly designed to combine the LLM's general prior knowledge with specific information provided in the prompt, rather than relying solely on memorized dataset statistics.

The core of your concern lies in how an LLM can infer valid rules for a dataset it has never seen. The paper clarifies that FeatLLM operates through a two-step reasoning process within the prompt (Section 3.1). In the first step, the LLM is instructed to infer causal relationships or tendencies between features and the target based **only** on general world knowledge and common sense, without looking at any data examples. This leverages the semantic meaning embedded in column names and feature descriptions (e.g., knowing that "age" or "blood pressure" generally correlates with heart disease risk) which is part of the model's pre-training corpus. In the second step, the LLM uses this general reasoning alongside **few-shot examples** provided directly in the prompt to deduce specific rules for that particular dataset.

Crucially, for datasets like 'Cultivars' and 'NHANES' which were added to UCI after September 2023 (post-dating GPT-3.5's training), FeatLLM does not assume the LLM knows the specific data distribution or spurious correlations of those tables. Instead, it relies on the LLM's ability to understand domain concepts (e.g., agricultural factors affecting soybean yield or demographic variables affecting age groups) from its general training, and then refines these into actionable rules using the few labeled samples serialized in the prompt. The paper explicitly states that this approach allows the model to "utilize both prior knowledge and the knowledge from the data" (Introduction), meaning the specific task adaptation comes from the few-shot examples provided at inference time, not from memorization of the dataset itself. Furthermore, any rules generated that do not align with the actual data distribution are filtered out during the subsequent training phase of the simple linear model (Section 3.2), where weights are learned to maximize performance on the provided few-shot samples, effectively correcting any generic assumptions made by the LLM that do not hold for that specific unseen dataset.

### Interpretation of 'Spurious Correlations' experiment: Why did performance drop only slightly?
Question:
In Section 4.2 ('Effect of adding spurious correlations'), the authors attach irrelevant columns from the Adult dataset to the Heart dataset and observe that FeatLLM degrades less than baselines.

They claim: 'This is likely because our framework forces the consideration of the relationship between the task and features based on prior knowledge... preventing the generation of rules based on irrelevant columns.'

However, they also admit later: '\textsf{FeatLLM} can also learn spurious correlations... if columns from closely related data are randomly attached.'

I am confused about the mechanism here. If I add a column named 'Income' (from Adult) to a Heart disease prediction task, wouldn't an LLM with medical prior knowledge immediately recognize that 'Income' is not medically relevant and refuse to generate rules for it? Or does it generate rules anyway but assign them low weights during training?

If it generates rules for irrelevant columns but filters them out later via weight tuning ($\mathbf{w}_k$), isn't that just standard feature selection? How is this different from XGBoost handling irrelevant features?
Answer:
The slight performance drop you observed in the spurious correlations experiment arises because \textsf{FeatLLM} employs a two-stage defense mechanism: semantic filtering during rule generation and statistical filtering during weight tuning, whereas standard models like XGBoost rely solely on the latter.

When an irrelevant column like "Income" is added to the Heart dataset, the LLM does not necessarily "refuse" to generate a rule for it in a binary sense, but the probability of it generating a *plausible* rule is drastically reduced by the specific "Reasoning instruction" in the prompt. As described in Section 3.1, the framework forces the LLM to first infer causal relationships based on prior knowledge (Step 1) before deriving rules from data examples (Step 2). Since "Income" has no known medical causal link to heart disease in the LLM's pre-trained knowledge base, the model is guided to exclude it from the set of decisive rules. The paper confirms this by noting that rules based on noisy columns accounted for only $1$-$2\%$ of the total generated rules, meaning most irrelevant features are filtered out at the source rather than being generated and then ignored.

However, as you correctly noted, if columns from *closely related* datasets are attached (e.g., adding "Education" which might correlate with "Income" and lifestyle factors), the LLM might indeed generate spurious rules because its prior knowledge could conflate these correlations. In these cases where a spurious rule is generated, \textsf{FeatLLM} relies on the second line of defense: the trainable linear model with weights $\mathbf{w}_k$. As detailed in Equation 1 and Section 3.2, these weights are optimized via cross-entropy loss on the few-shot training data. If a rule based on an irrelevant feature does not consistently predict the target label in the few available samples, its corresponding weight $\mathbf{w}_k$ will converge toward zero (or be pruned if below a threshold).

The key distinction from XGBoost or standard feature selection lies in *when* and *how* this filtering occurs. XGBoost treats all input features as equally valid candidates for splitting nodes initially; it must learn through gradient descent that a feature provides no information gain, which is difficult in low-shot regimes where noise can easily be mistaken for signal (overfitting). In contrast, \textsf{FeatLLM} uses LLM prior knowledge to pre-filter the feature space semantically before any numerical optimization begins. This effectively reduces the hypothesis space for the downstream linear model, making it much harder for spurious correlations to dominate when training data is scarce. The slight degradation you see represents the small fraction of cases where either (a) the LLM's prior knowledge was insufficient to reject a plausibly correlated but irrelevant feature, or (b) the few-shot data was too limited for the linear model to drive that specific weight to zero completely.

### Mathematical justification for using Softmax across classes with independent binary rule sets
Question:
In Equation 1, the probability vector $\mathbf{p}^i$ is computed by applying Softmax over logits derived from independent binary feature sets $\mathbf{z}_k^i$ for each class $k$:

$$\mathbf{p}^i = \text{Softmax}({[\text{logit}_{1}^i, ..., \text{logit}_{c}^i]})$$

where $\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$.

My confusion lies in how these logits interact. Since $\mathbf{z}_1^i$ and $\mathbf{z}_2^i$ are derived from completely different sets of rules generated specifically for Class 1 and Class 2 respectively, isn't there no direct competition between them until Softmax forces one?

If Class 1 has very strong rules (high sum) and Class 2 has weak rules (low sum), Softmax will push probability toward Class 1. But what if both classes have high sums because both sets of rules are satisfied by different attributes? Does this formulation implicitly assume mutual exclusivity even though binary classification usually implies $P(y=0) + P(y=1) = 1$, whereas here we seem to be modeling two independent scores before normalizing?

Is there a risk that if both classes satisfy many high-weight rules simultaneously due to overlapping feature definitions in natural language, the model becomes unstable?
Answer:
The mathematical formulation in Equation 1 is justified by the fundamental requirement of the classification task to produce a valid probability distribution where the sum of probabilities across all classes equals one, effectively enforcing mutual exclusivity for the final prediction. While your intuition is correct that the binary feature sets $\mathbf{z}_k^i$ for each class are generated independently based on distinct rule sets, these logits represent raw "scores" or evidence strength rather than independent probabilities. Without the Softmax normalization, a sample could theoretically satisfy strong rules for multiple classes simultaneously (e.g., having a high logit for both Class 1 and Class 2), resulting in unnormalized scores that cannot be directly interpreted as a likelihood of belonging to a specific class in a multi-class setting.

The Softmax function serves as the necessary mechanism to convert these independent evidence scores into a competitive probability space. By exponentiating the logits and normalizing by the sum of all exponentiated logits, Softmax ensures that $\sum_{k=1}^c p_k^i = 1$. This forces a relative comparison: even if both Class 1 and Class 2 have high sums of satisfied rules, the class with the *higher* weighted sum will receive a disproportionately higher probability, while the others are suppressed. This is not an assumption that the rules themselves are mutually exclusive in reality, but rather a mathematical necessity to output a single class prediction from independent scoring mechanisms. The paper explicitly notes that this linear model with non-negative weights ($\max(\mathbf{w}_k, 0)$) learns the importance of each rule, and the subsequent Softmax operation aggregates these weighted evidences into a coherent decision boundary.

Regarding your concern about instability when multiple classes satisfy many high-weight rules simultaneously, this scenario is precisely what the training process via cross-entropy loss is designed to resolve. During training on few-shot samples, if two classes consistently receive high scores for ambiguous samples, the gradient descent will adjust the weights $\mathbf{w}_k$ to maximize the logit of the true label relative to others. If a sample truly belongs to Class 1 but triggers strong rules for Class 2 due to overlapping features (spurious correlations), the loss function penalizes this configuration, driving down the weights associated with those misleading rules for Class 2 or boosting those specific to Class 1. Furthermore, FeatLLM employs an ensemble approach with bagging across multiple trials; this aggregation smooths out individual instances where rule overlap might cause instability, as incorrect or noisy rules generated in one trial are likely compensated by correct rules in others, leading to robust final probabilities.
