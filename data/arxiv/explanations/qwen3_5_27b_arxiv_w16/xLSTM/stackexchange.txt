### What is the precise role of the normalizer state $\mathbf{n}_t$ in mLSTM retrieval, and why is absolute value necessary?
Question:
Reading Section 3.3 on mLSTM, I'm trying to understand the mechanics of retrieving information from the matrix memory $\mathbf{C}_t$. The hidden state is calculated as:

$$ \tilde{\mathbf{h}}_t = \mathbf{C}_t \mathbf{q}_t / \max \left\{ |\mathbf{n}_t^\top \mathbf{q}_t|, 1 \right\} $$

Where $\mathbf{n}_t$ is updated recursively as a weighted sum of keys: $\mathbf{n}_t = f_t \mathbf{n}_{t-1} + i_t \mathbf{k}_t$. 

My confusion lies in two parts:
1. Intuitively, if $\mathbf{C}_t$ stores outer products of values and keys ($v k^T$), shouldn't multiplying by a query $q$ naturally retrieve values proportional to similarity? Why do we need to explicitly divide by a normalizer involving keys?
2. Why is taking the absolute value inside the denominator critical? If $\mathbf{n}_t^\top \mathbf{q}_t$ becomes negative, wouldn't that just flip the sign of the retrieved vector? Does this relate to numerical stability near zero or something deeper about covariance updates?
Answer:
The normalizer state $\mathbf{n}_t$ in the mLSTM serves as a dynamic denominator that accounts for the cumulative "weight" of all stored keys, ensuring that the retrieved hidden state represents a proper weighted average of values rather than a raw accumulation of outer products. While the cell state $\mathbf{C}_t$ accumulates terms of the form $i_\tau f_{\dots} \mathbf{v}_\tau \mathbf{k}_\tau^\top$, simply multiplying this matrix by a query $\mathbf{q}_t$ yields a numerator where every stored value is scaled by its corresponding key-query similarity *and* its historical gating weights. Without division by $\mathbf{n}_t^\top \mathbf{q}_t$, the magnitude of the retrieved vector would grow arbitrarily large as more items are added to memory, regardless of whether those items are actually similar to the current query. By dividing by $\sum_\tau (\text{gate\_product}) (\mathbf{k}_\tau^\top \mathbf{q}_t)$, which is exactly what $\mathbf{n}_t^\top \mathbf{q}_t$ computes, the model effectively normalizes the retrieval operation so that the output magnitude reflects the relative relevance of matching memories rather than the sheer count of stored memories. This mirrors the normalization in standard attention mechanisms, preventing saturation and maintaining stable gradients during training.

The use of the absolute value $|\cdot|$ in the denominator, specifically within $\max \left\{ |\mathbf{n}_t^\top \mathbf{q}_t|, 1 \right\}$, is primarily a safeguard for numerical stability and robustness against cancellation effects inherent in covariance-based updates. Although keys and queries often have zero mean due to layer normalization (as noted in Section 3.3), their dot product with the accumulated normalizer state can theoretically become negative or extremely close to zero if opposing signals cancel each other out or if noise dominates. If $\mathbf{n}_t^\top \mathbf{q}_t$ were allowed to cross zero or approach it without protection, the division could produce extreme spikes (division by near-zero) or invert the direction of the retrieved vector unexpectedly (sign flipping), leading to unstable training dynamics or exploding activations. The absolute value ensures that we normalize by the *magnitude* of the alignment signal regardless of its sign, treating strong anti-alignment similarly to strong alignment in terms of scaling down potentially noisy retrievals. Furthermore, hard-capping this minimum at $1.0$ guarantees that even if no meaningful correlation exists between current queries and past keys (resulting in a near-zero dot product), the model defaults to returning a scaled version of $\mathbf{C}_t \mathbf{q}_t$ without blowing up numerically, allowing gradients to flow smoothly through non-retrieved states.

### Clarification on 'memory mixing': Why does sLSTM require it for state tracking while mLSTM does not?
Question:
The Introduction states that one major limitation of standard LSTMs is their inability to revise storage decisions, which xLSTM fixes with exponential gating. It also mentions that sLSTM retains 'memory mixing' (recurrent connections between hidden states and gates/cell inputs), whereas mLSTM abandons it to become fully parallelizable.

Later, in Related Work (Section 4), it says: "Conceptually... these approaches [Retention, RWKV] do not allow memory mixing. Memory mixing enables to solve state tracking problems..."

I am confused about the distinction here. If mLSTM has a matrix memory capable of associative recall (Key-Value pairs), isn't that sufficient for tracking entities or states over long sequences? Why is the explicit recurrent connection (mixing previous hidden states into current gate calculations) strictly necessary for 'state tracking' tasks like parity checks or code evaluation, but seemingly unnecessary for associative recall tasks handled by mLSTM?
Answer:
The distinction lies in the fundamental difference between **associative recall** (looking up stored information) and **state tracking** (maintaining a dynamic, evolving internal counter or condition), which requires the model to continuously refine its own decision-making logic based on its immediate history. While mLSTM excels at associative recall through its matrix memory and Key-Value mechanism, it lacks the specific architectural feature—memory mixing—that allows a model to recursively update its gating decisions based on the *previous* hidden state.

As explicitly stated in the Related Work section, models like Retention and RWKV, which share mLSTM's matrix memory but lack memory mixing, "do not allow memory mixing," and consequently struggle with state tracking problems. The paper defines memory mixing as the recurrent connections ($r_z, r_i, r_f, r_o$) that feed the previous hidden state $h_{t-1}$ directly into the calculation of the current cell input and gates ($z_t, i_t, f_t, o_t$). This feedback loop is critical for tasks like parity checking or code evaluation because these tasks often require the model to maintain a precise logical state (e.g., "odd" vs. "even") that depends on the cumulative history of operations. Without memory mixing, the gates at time $t$ are determined solely by the current input $\mathbf{x}_t$ and fixed parameters; they cannot dynamically adjust their storage strategy based on what happened in step $t-1$.

In contrast, sLSTM retains these hidden-hidden connections. This allows sLSTM to effectively act as a finite-state machine where the transition probabilities (controlled by the gates) depend on the current internal configuration of the network itself. When solving a parity check, for instance, sLSTM can use $h_{t-1}$ to determine whether to flip a bit in its memory or ignore it, creating a chain of dependencies that pure associative recall cannot easily replicate. mLSTM sacrifices this capability specifically to achieve full parallelizability; by removing the dependency of gates on $h_{t-1}$, it transforms into a system where updates can be computed simultaneously for all time steps using scan algorithms or parallel matrix operations. Therefore, while mLSTM's matrix memory provides superior capacity for storing distinct Key-Value pairs (associative recall), it is architecturally incapable of the recursive state refinement required for complex logical tracking unless paired with an sLSTM block that provides this missing mixing mechanism.

### Why does xLSTM use Post Up-Projection for sLSTM but Pre Up-Projection for mLSTM blocks?
Question:
In Section 3.4 ('xLSTM Blocks'), the authors describe two residual block architectures based on when they apply non-linearity relative to dimensionality expansion (up-projection):

1. **Post up-projection**: Non-linear summary in original space -> map up -> activate -> map down (used for sLSTM).
2. **Pre up-projection**: Map up -> non-linear summary in high-dim space -> map down (used for mLSTM).

The justification given is: "For an xLSTM block containing an mLSTM, we use the pre up-projection block since the memory capacity becomes larger in the high-dimensional space."

Could someone elaborate on why increasing dimensions *before* processing helps mLSTM's matrix memory specifically? Does this relate to how covariance matrices behave in higher dimensions (perhaps avoiding rank deficiency or improving separation)? Conversely, why would doing this *after* processing be better or safer for sLSTM's scalar memory?
Answer:
The choice between pre and post up-projection in xLSTM stems directly from the fundamental difference in how sLSTM and mLSTM manage memory capacity and the theoretical implications of Cover's Theorem regarding pattern separation.

For the **mLSTM**, which utilizes a matrix memory $\mathbf{C} \in \mathbb{R}^{d \times d}$ updated via a covariance rule ($\mathbf{C}_t = f_t \mathbf{C}_{t-1} + i_t \mathbf{v}_t \mathbf{k}_t^\top$), the authors explicitly choose **pre up-projection** to maximize storage efficiency. According to Cover's Theorem, patterns that are not linearly separable in a low-dimensional space become more likely to be linearly separable when mapped into a higher-dimensional space. By expanding the input dimension *before* the non-linear summarization occurs inside the mLSTM block, the model operates in this expanded feature space where distinct historical contexts can be more effectively distinguished. Crucially, because the mLSTM stores information as outer products of keys and values ($\mathbf{v}\mathbf{k}^\top$), performing this operation in a higher-dimensional space significantly increases the effective rank and capacity of the resulting memory matrix. If one were to use post up-projection for mLSTM, the non-linear summary would occur in the lower-dimensional original space, compressing information prematurely and reducing the diversity of patterns available for the subsequent high-dimensional matrix updates, thereby underutilizing the matrix memory's potential capacity.

Conversely, for the **sLSTM**, which relies on a scalar (or vector) memory cell with memory mixing via recurrent connections, **post up-projection** is preferred. The sLSTM already incorporates "memory mixing," allowing it to dynamically combine hidden states across time steps to handle state-tracking tasks. In this architecture, applying non-linear transformations in the original dimension first allows the recurrent dynamics to refine and mix these representations effectively before they are projected into a high-dimensional space for final activation and projection back down. Since sLSTM does not rely on forming high-rank covariance matrices to store associative memories like mLSTM does, it benefits more from keeping its internal recurrent loop compact and focused on refining scalar/vector summaries before expanding dimensions for classification or next-token prediction logic. Essentially, sLSTM prioritizes dynamic state refinement through mixing in its native space, whereas mLSTM prioritizes maximizing geometric separation capacity by operating entirely within an expanded latent space during its update cycle.

### Is there a contradiction between mLSTM's 'constant memory complexity' claim and its quadratic update cost?
Question:
In Section 3.5 ('Memory and Speed Considerations'), the paper states: "Contrary to Transformers, xLSTM networks have a linear computation and a constant memory complexity with respect to the sequence length." 

However, immediately after describing mLSTM, it notes: "The memory of mLSTM does not require parameters but is computationally expensive through its $d \times d$ matrix memory and $d \times d$ update." Here, $d$ represents the feature/embedding dimension.

If I interpret 'constant memory complexity' as O(1) with respect to sequence length $T$, that makes sense because we don't store all past tokens like Transformers do.
But I am confused about whether this implies O(1) computation per step too? The update involves adding an outer product ($v k^T$) which is O($d^2$). If we stack many layers or increase width significantly, isn't this effectively quadratic in model width? Is there a nuance between 'sequence length complexity' vs 'model parameter/width complexity' that I am missing here?
Answer:
There is no contradiction in the paper's claims because the authors are explicitly distinguishing between complexity relative to **sequence length** ($T$) and complexity relative to **feature dimension** ($d$). When the paper states that xLSTM has "constant memory complexity" and "linear computation," it specifically qualifies these metrics "with respect to the sequence length." In this context, "constant" means $O(1)$ regarding $T$, implying that as you feed more tokens into the model, the memory footprint of the internal state does not grow (unlike Transformers, which require storing all past keys and values, leading to $O(T)$ memory). Similarly, the computation per new token remains constant regardless of how long the history is, resulting in linear total computation $O(T)$ for a sequence of length $T$.

Your observation regarding the $d \times d$ matrix update is correct; this operation indeed incurs a computational cost proportional to $d^2$ per time step. However, this quadratic dependence is on the model's width (the embedding dimension), not on the sequence length. The paper acknowledges this trade-off directly in Section 3.5 ("Memory and Speed Considerations"), noting that while the matrix memory is "computationally expensive through its $d \times d$ matrix memory and $d \times d$ update," it trades off memory capacity against computational complexity in terms of width. Crucially, because this heavy lifting involves standard matrix operations that can be executed in parallel on GPUs, the authors argue that it has only a "minor effect on the wall clock time." Therefore, the claim of linear computation holds true for scaling sequence length, while acknowledging that increasing model width increases the constant factor of computation per step quadratically.
