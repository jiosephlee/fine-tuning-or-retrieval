\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### Is there a contradiction between mLSTM's 'constant memory complexity' claim and its quadratic update cost?
Question:
In Section 3.5 ('Memory and Speed Considerations'), the paper states: "Contrary to Transformers, xLSTM networks have a linear computation and a constant memory complexity with respect to the sequence length." 

However, immediately after describing mLSTM, it notes: "The memory of mLSTM does not require parameters but is computationally expensive through its $d \times d$ matrix memory and $d \times d$ update." Here, $d$ represents the feature/embedding dimension.

If I interpret 'constant memory complexity' as O(1) with respect to sequence length $T$, that makes sense because we don't store all past tokens like Transformers do.
But I am confused about whether this implies O(1) computation per step too? The update involves adding an outer product ($v k^T$) which is O($d^2$). If we stack many layers or increase width significantly, isn't this effectively quadratic in model width? Is there a nuance between 'sequence length complexity' vs 'model parameter/width complexity' that I am missing here?
Answer:
There is no contradiction in the paper's claims because the authors are explicitly distinguishing between complexity relative to **sequence length** ($T$) and complexity relative to **feature dimension** ($d$). When the paper states that xLSTM has "constant memory complexity" and "linear computation," it specifically qualifies these metrics "with respect to the sequence length." In this context, "constant" means $O(1)$ regarding $T$, implying that as you feed more tokens into the model, the memory footprint of the internal state does not grow (unlike Transformers, which require storing all past keys and values, leading to $O(T)$ memory). Similarly, the computation per new token remains constant regardless of how long the history is, resulting in linear total computation $O(T)$ for a sequence of length $T$.

Your observation regarding the $d \times d$ matrix update is correct; this operation indeed incurs a computational cost proportional to $d^2$ per time step. However, this quadratic dependence is on the model's width (the embedding dimension), not on the sequence length. The paper acknowledges this trade-off directly in Section 3.5 ("Memory and Speed Considerations"), noting that while the matrix memory is "computationally expensive through its $d \times d$ matrix memory and $d \times d$ update," it trades off memory capacity against computational complexity in terms of width. Crucially, because this heavy lifting involves standard matrix operations that can be executed in parallel on GPUs, the authors argue that it has only a "minor effect on the wall clock time." Therefore, the claim of linear computation holds true for scaling sequence length, while acknowledging that increasing model width increases the constant factor of computation per step quadratically.
