\title{A Textbook about the Paper: xLSTM}

Chapter 8: Computation and Memory: Complexity, Parallelism, and Throughput

# Time and memory complexity vs sequence length

Analyzing a sequence model requires two complementary resources: the time (compute) it needs to process a sequence of length $T$, and the working memory it needs during that processing. The xLSTM family (sLSTM and mLSTM) was designed with these constraints in mind and, as described in the paper, exhibits fundamentally different scaling behavior with respect to the sequence length than standard Transformer attention.

For an xLSTM architecture the operations that depend on the sequence length are the recurrent updates performed once per token. Because each token produces a bounded number of algebraic updates to the internal memory, the total computation over a sequence of length $T$ grows linearly in $T$. We can summarize this as
- time complexity over a sequence: $O(T \cdot C)$,
- memory complexity with respect to $T$: constant (independent of $T$),

where $C$ denotes the per-step computational cost that depends on the internal state dimension(s) but not on $T$. The paper emphasizes that xLSTM networks therefore have linear computation and constant memory complexity with respect to the sequence length.

To make the dependence on model dimension explicit for the two xLSTM variants: mLSTM maintains a matrix memory of size $d \times d$, and the dominant per-step operations are an outer-product update and a matrix–vector retrieval. These scale as $O(d^2)$ per step, so the total time over a sequence of length $T$ is
- for mLSTM: time $O(T d^2)$ and memory $O(d^2)$ (constant in $T$).

sLSTM, like many scalar-cell recurrent models, has per-step cost that is dominated by vector–matrix products and recurrent mixing; these are also on the order of $O(d^2)$ per step in practice, giving total time $O(T d^2)$ and memory that is constant in $T$ (though the exact constant differs from mLSTM because sLSTM stores scalar cells rather than a dense matrix).

By contrast, standard Transformer attention (as used in training) builds pairwise token interactions that make its compute and working-memory costs grow quadratically with the context length. Informally,
- Transformers (attention): compute and working-memory cost grow as $O(T^2)$ (quadratic in $T$),

which is the central reason why Transformers become costly on very long contexts. The xLSTM design deliberately avoids this quadratic dependence by keeping an internal, compressive memory that does not grow with $T$.

# Comparison to attention (quadratic in context length) and KV caches

Transformer attention incurs an explicit quadratic dependence on the context length when computing pairwise attention weights between tokens; this is the classic bottleneck that motivates many linearized attention and SSM approaches. The paper contrasts this with xLSTM’s constant-in-$T$ memory and linear-in-$T$ compute.

In generation (autoregressive decoding) Transformers typically use a key–value (KV) cache: previously computed keys and values are stored so the model does not recompute them, which reduces recomputation but still increases working memory with the number of past tokens. The paper’s inference experiments mention using a static key–value cache for the Llama Transformer baseline. Even with a KV cache, the Transformer’s working memory grows with the number of cached tokens and that growth constrains the batch sizes and throughput usable in decoding. In the experimental comparison reported, this manifests as markedly different wall-clock scaling: the paper shows that xLSTM and other recurrent models have approximately linear increases in generation time as the context grows, while the Transformer (Llama) shows a quadratic trend in the same experiment (Figure referenced in the paper). Practically, the paper reports that, for batch size 1 and a 16-token prefill, recurrent models (including xLSTM) scale linearly and are more favorable for long generation contexts, while the Transformer’s quadratic nature becomes the limiting factor.

A key operational consequence is throughput under constrained device memory: because xLSTM memory is constant in $T$, it can admit much larger decoding batch sizes than the Transformer implementation used in the experiments and thus achieve higher maximal throughput. The paper’s measurements report that xLSTM achieves the highest throughput and can use much higher batch sizes than Llama precisely because of this constant-memory property.

# Matrix memory compute patterns (d by d) and parallelization

mLSTM elevates the scalar LSTM cell to a matrix memory $\mathbf{C}_t \in \mathbb{R}^{d\times d}$. The forward-update equations that determine the per-step compute in mLSTM are:

\[
\mathbf{C}_t \;=\; f_t \, \mathbf{C}_{t-1} \;+\; i_t \, \mathbf{v}_t \, \mathbf{k}_t^\top,
\]
\[
\tilde{\mathbf{h}}_t \;=\; \frac{\mathbf{C}_t \, \mathbf{q}_t}{\max\{|\mathbf{n}_t^\top \mathbf{q}_t|, 1\}},
\qquad
\mathbf{h}_t \;=\; \mathbf{o}_t \odot \tilde{\mathbf{h}}_t,
\]
together with the normalizer update
\[
\mathbf{n}_t \;=\; f_t \, \mathbf{n}_{t-1} \;+\; i_t \, \mathbf{k}_t.
\]

From these equations the dominant low-level linear-algebra kernels are clear:
- a scalar scale of the previous matrix: $f_t \, \mathbf{C}_{t-1}$ (a scaled copy of a $d\times d$ matrix),
- an outer product addition: $i_t \, \mathbf{v}_t \, \mathbf{k}_t^\top$ (rank-1 update),
- a matrix–vector multiply for retrieval: $\mathbf{C}_t \, \mathbf{q}_t$ (a dense $d\times d$ times a $d$-vector),
- a small vector dot product for normalizer-based scaling.

Each such kernel is standard linear algebra: the outer-product update is $O(d^2)$ and the matrix–vector product is also $O(d^2)$ in arithmetic. Crucially, these operations do not involve explicit, per-token growth in stored state: the single matrix $\mathbf{C}_t$ is updated in place and its size is fixed to $d^2$, so memory does not scale with the number of tokens processed.

These kernels map well to GPU hardware because they are dense, regular, and parallelizable. The outer-product update and the matricial retrieval can be implemented using parallel matrix kernels (e.g., batched matrix–vector or rank-1 updates) and can leverage highly optimized BLAS-like primitives or custom CUDA kernels. The paper underlines this; it states that mLSTM is "fully parallelizable" and its computations can be done in parallel on GPUs, so the wall-clock overhead becomes modest despite the $d^2$ arithmetic.

There is a trade-off implied by this design: the matrix memory increases the expressive storage capacity compared to scalar-cell LSTMs (allowing richer associative memory), but it also raises the per-step arithmetic cost from vector-scale operations to dense $d\times d$ arithmetic. The paper frames this explicitly as a trade between memory capacity and computational complexity.

# sLSTM vs mLSTM runtime and batching characteristics

sLSTM and mLSTM differ sharply in two respects that affect runtime and batching:

1. Parallelizability. sLSTM retains memory mixing via recurrent (hidden-to-gate) connections between time steps. These hidden–hidden dependencies enforce an inherently sequential dependency: the computation at time $t$ uses information computed at time $t-1$ in a way that cannot be algebraically flattened into a single parallel matrix update across time steps. Consequently, sLSTM is not directly parallelizable over tokens in the same way as mLSTM. The paper therefore treats sLSTM as sequential and notes that it cannot use the same kind of parallel reformulation that makes mLSTM amenable to parallel GPU kernels.

2. Practical runtime and kernel engineering. Despite sLSTM’s sequential nature, the authors implemented a highly optimized CUDA kernel with GPU memory optimizations at the register level, achieving a runtime that is typically less than two times slower than their parallel mLSTM implementation. This indicates that careful low-level engineering can mitigate some of the sequential-model runtime penalties. On the other hand, the mLSTM implementation in the paper was not fully kernel-optimized; the authors report that their current mLSTM implementation is about four times slower than FlashAttention or the scan implementation used in Mamba. The key takeaway is that algorithmic parallelizability (mLSTM) puts a method in the same class as attention in terms of being able to exploit high-performance kernels, but the realized wall-clock performance depends heavily on kernel optimization effort.

Batching behavior follows from the above. Because mLSTM computations for different tokens and batches can be expressed as dense matrix operations, they are straightforward to batch: multiple sequences can be handled in the same kernel launch with typical GPU throughput benefits. sLSTM’s sequential dependence means it is harder to fully exploit cross-token parallelism, but per-batch parallelism across independent sequences remains possible, and register-level optimizations can make its per-step latency small enough that batch throughput is still competitive. The experiments in the paper show that, in practice, the optimized sLSTM kernel is within a relatively small constant factor of the mLSTM wall-clock time.

# Length extrapolation and large-batch decoding advantages

Two practical consequences of xLSTM’s constant-in-$T$ memory and linear-in-$T$ compute are (1) stable extrapolation to longer contexts at inference time and (2) favorable decoding throughput when generation batch sizes are scaled.

Length extrapolation: The paper presents language-modeling experiments where models trained with a context length of 2048 were evaluated at much longer contexts (up to 16384). xLSTM models maintained low perplexities out to these longer contexts, outperforming the other compared models in this extrapolation test. Because the xLSTM internal memory does not grow with $T$, increasing the context window at inference time does not inflate the working memory footprint nor force recomputation of an ever-growing attention matrix; this helps maintain both accuracy and practical feasibility when using long contexts.

Decoding throughput and batch sizing: In generation, practical throughput depends not only on arithmetic per token but also on how much device memory is needed for the model state and any cached context. The paper reports that xLSTM can use much larger decoding batch sizes than the Transformer baseline in their experiments because xLSTM’s memory does not grow with the context length. This enables higher decoding throughput: in the reported experiments xLSTM achieves the highest throughput and can make efficient use of larger batch sizes, while the Transformer baseline is constrained by the KV cache and attention memory growth, which caps the practical batch size and thus reduces throughput. The generation-time plots in the paper show linear runtime scaling for xLSTM and other recurrent models and quadratic scaling for Llama (Transformer), which reinforces the noted practical advantages for long-context generation and high-throughput decoding.

# Implementation pathways toward FlashAttention-like kernels

The paper points to clear engineering directions for improving xLSTM’s wall-clock performance, especially for mLSTM: because the mLSTM core operations are standard dense linear algebra (rank-1 updates, matrix–vector products, scalings), there is an opportunity to implement highly optimized, fused CUDA kernels in the spirit of FlashAttention and other attention-optimized approaches. The authors explicitly state that mLSTM "is parallelizable analog to FlashAttention or GLA" and that "faster CUDA kernels could be obtained in the vein of FlashAttention."

Concretely, the engineering opportunities the paper suggests are:
- Reformulate the mLSTM recurrence into a parallel version that expresses batches of outer-product updates and matvec retrievals in large, fused GPU kernels. The paper notes that because mLSTM has no memory mixing across time steps, the recurrence admits such a parallel reformulation.
- Implement fused kernels that combine scaling, rank-1 update accumulation, and retrieval into single passes to reduce memory traffic and kernel-launch overhead; these are the same high-level ideas that make FlashAttention fast for attention.
- For sLSTM, leverage register-level and memory-layout optimizations for the sequential scan (as the authors did) to reduce latency per step; highly tuned sequential kernels can narrow the gap with parallel implementations.

The paper documents a current state where mLSTM is already parallel in principle but the available kernels are not yet optimized (about four times slower than FlashAttention in their tests), while the sLSTM benefits from a specialized CUDA kernel that brings its runtime close to mLSTM's. This highlights that further kernel-level work—both for the dense matrix operations of mLSTM and for the optimized sequential scan of sLSTM—can materially change the practical trade-offs between these variants.

# Summary: trade-offs, where xLSTM fits, and practical guidance

xLSTM offers a distinct operating point among sequence models:

- Complexity vs. sequence length: xLSTM is linear in time and constant in working memory with respect to the sequence length $T$, while attention-based Transformers are quadratic in $T$ during training and require increasing working memory when using KV caches in generation.
- Capacity vs. per-step cost: mLSTM trades a larger per-step compute cost ($O(d^2)$ arithmetic due to a $d\times d$ matrix memory) for greater storage capacity and fully parallelizable kernels; sLSTM keeps scalar cells and memory mixing, which helps expressivity but imposes sequential dependencies that complicate parallelization.
- Practical performance depends on kernel engineering: With optimized kernels (the “FlashAttention-like” path), mLSTM can realize its parallel-computation potential and close the wall-clock gap to attention. Meanwhile, a well-engineered sequential kernel for sLSTM can make it only modestly slower in practice (the paper reports sLSTM less than two times slower than their mLSTM implementation).

In short, xLSTM’s constant-memory, linear-time design gives it practical advantages for long-context inference and high-throughput decoding, and its matrix-memory mLSTM variant is particularly amenable to further performance gains via dedicated GPU kernel engineering. The experiments reported in the paper already demonstrate these practical benefits: xLSTM maintains extrapolation performance to long contexts, exhibits linear generation-time scaling (versus quadratic for Llama), and attains higher decoding throughput because it can utilize larger batch sizes thanks to constant memory usage.
