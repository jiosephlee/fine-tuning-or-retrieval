\title{Blogs about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

# Code Before Math: The Hidden Link Between Programming and Problem‑Solving in LLMs  

The intuition that “coding = coding” has been a standing assumption among many researchers: if you train a language model on large code corpora, you only expect better source‑code generation, not a boost to other forms of reasoning.  
DeepSeekMath – the 7‑billion‑parameter model that pushed open‑source math‑reasoning past the 50 % line on MATH – turns that intuition on its head.  Its creators ran a series of experiments that put **code tokens** in front of, or **mixed with**, later math training, and measured the outcomes on five families of tasks:

* **Tool‑agnostic step‑by‑step solutions** (chain‑of‑thought)
* **Tool‑integrated (Python) solutions** (program‑of‑thought / tool use)
* **Problem–solving in a foreign language (Chinese)**  
* **General language understanding** (MMLU/BBH)  
* **Programming benchmarks** (HumanEval/MBPP)

Below is a compact walk‑through of their design, results, and the practical take‑aways.

---

## 1. Why the “code first” hypothesis is worth testing

Large language models consist largely of *statistical regimens*: patterns in text are memorised and interpolated in subtle ways.  Code and mathematics share several high‑level structural features: 

* Both are **composable** – algebraic formulas can be rewritten as pure functions, and code is literally declarative syntax for computation.
* Both contain nested **control flows** – recursion in mathematics is equivalent to loops; symbol manipulation mirrors data structures.
* Both demand **precision** at the token level – an off‑by‑one error in either domain ruins the final answer.

If a model has already spent two–hundred billion token updates learning to parse Lua or Jupyter notebooks, it *has* already tuned its embeddings to recognise and manipulate small units of logic in a reliable manner.  This pre-training can scaffold later reasoning across languages because each logical decomposition is a shared cognitive primitive.

---

## 2. Experimental frames

| Training strategy | Stage 1 | Stage 2 | Tokens used |
|-------------------|---------|---------|-------------|
| **Two‑stage** | 400 B code tokens | 150 B math tokens | independent |
| **One‑stage mixing** | 400 B code + 150 B math tokens | – | joint |
| **Control** | 400 B generic text tokens | 150 B math tokens | independent |

All models started from DeepSeek-Coder-Base-v1.5 (7 B).  
The dataset split was identical across strategies – only the order or mix of tokens differed.  

The training budget for each strategy was the same: ~150 B tokens dedicated to “math” content, all others being code or generic language.

---

## 3. What we measured

| Metric | “Code → Math” | “Math only” | “Code + Math mix” |
|--------|---------------|-------------|-------------------|
| GSM8K (CoT) % correct | 70 → *51* → *53*? No, *51%* for base; improvements measured below |
| GSM8K (PoT) % correct | +5% +10% from baseline after code? etc |
| MATH (CoT) % correct | +3% over baseline, ~5% over math only |
| MATH (PoT) % correct | >+20% improvement with code before maths |
| MMLU/BBH overall accuracy | Increases by ~4–6 points with code pre-training |
| HumanEval / MBPP score | Remains roughly constant or slightly raises |

A few key observations emerged:

1. **Code improves tool ≥ code augmentation improves neither tool nor reasoning**  
   Adding code tokens *before* math training gave far superior jump in Python program generation compared to putting them after or mixing them.  

2. **Without tools, code helps but not as much**  
   Pure chain‑of‑thought solutions without tool use improved modestly after code first training; performance gains were noticeably lower than those for PoT.

3. **Catastrophic forgetting is mitigated by mixing**  
   Running two stages caused sharp drops in coding benchmark scores after finishing math–only fine‐tuning—in line with classic forgetting literature. Mixing code & math in one pass preserved coding proficiency while still reaping reasoning benefits.

4. **Cross‐lingual gains**  
   For Chinese math benchmarks such as CMATH and Gaokao-MathQA, models that had seen code *first* achieved higher precision than those that trained on texts only—suggesting transferable structural knowledge.

---

## 4. Why does this happen?

### The “structured token storage” theory

When you train on millions of lines of Python syntax, your embedding layers implicitly learn how *syntax trees' shapes correlate with function semantics*.  During subsequent math pre-training you’re essentially saying: “here's a function; give me its formal definition.” The model has already been primed to imagine such mappings quickly.

### Improved tokenisation flow

Code uses fewer digit sequences but more identifiers and operators (`+`, `==`, `math.sqrt`). Mixed training accentuates the representational capacity for these ‘mathematical’ symbols; consequently the tokenizer/embedding pipeline becomes more attuned to numeric expressions even when they sit inside prose.

### Mitigation of data noise

Publicly scraped mathematical web pages often contain colloquial commentary or assistant help lines that don’t reflect clean reasoning steps. Code pages are less noisy—they are versioned by copiers and come with syntactic discipline—so regularising on them gives the optimisation algorithm a more stable prior when stepping into noisy maths data.

---

## 5. Practical guidance

If you’re building an open‐source LLM that needs to excel at both coding *and* maths:

1. **Structure your pre–training stages**: Marry a large code corpus first, then append an ample quantity of curated mathematical web data.
2. **Preserve joint synapses**: Instead of freezing the decoder after stage one, let gradient flow continue across both stages so that symbol representations adapt jointly.
3. **Mitigate forgetting during mixing**: If you have limited compute budget for one pass, weight-code tokens heavier early stages before gradually tapering them out—this mimics curriculum learning where structured primitives lay groundwork for high‐level reasoning.
4. **Add cross‐lingual goodies early**: Include Chinese mathematical pages alongside English code if you expect bilingual performance; it'll harvest similar structural benefits across languages.
5. **Monitor all downstreams continually**: Don’t just look at math benchmarks—keep an eye on HumanEval / MMLU / BBH because impacts may bleed back into these areas.

---

## 6. Summary

DeepSeekMath shines not because it was buried under billions of minutes of rehearsal on mathematical equations alone; it was because it first dialed up its internal syntax engine with billions of lines of real-world programming practice—and then leveraged those bones to bolt new reasoning muscles efficiently.

The moral? *Train models where skills overlap first.* A universe where logic and computation dance together yields an architecture capable not just of solving equations, but also explaining them step by step—or generating precisely executed scripts to check their answers automatically.*
