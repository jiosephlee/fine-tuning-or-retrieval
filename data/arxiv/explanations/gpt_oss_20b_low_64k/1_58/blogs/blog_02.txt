# From Floating‑Point to Int8: The Compute Revolution Behind BitNet b1.58  

## 1.  Why the shift to 1‑bit weights matters  
Large Language Models (LLMs) have become the de‑facto backbone of contemporary AI systems.  Each Transformer layer is dominated by a handful of dense matrix multiplications (the \emph{nn.Linear} blocks).  In a conventional FP16 model these multiplications require a floating‑point multiply followed by an addition for every pair of elements.  The energy cost and silicon area of floating‑point units dwarf those of integer arithmetic, and the bandwidth demand for moving 16‑bit numbers across the memory hierarchy is significant.  

Lower‑bit quantisation has long been explored for inference: switching from FP16 to BF16 or even 4‑bit formats saves memory but still keeps the heavy FP multiply in place because most libraries perform a *mixed* precision kernel (int‑to‑int accumulation before casting back to float).  BitNet b1.58 removes this mixed flavour entirely by forcing every weight into the ternary set \{-1, 0, +1\}.  Consequently, every product in a matrix multiplication vanishes:  

\[
x \times w = 
\begin{cases}
x    & w=+1\\
-x   & w=-1\\
0    & w=0
\end{cases}
\]

Only integer addition remains – an operation that contemporary GPUs and ASICs can perform orders of magnitude faster and far more energy‑efficiently than floating‑point multiply/add.

## 2.  From theory to practice – The BitLinear layer  
BitNet replaces the standard \texttt{nn.Linear} with a custom \texttt{BitLinear}.  
* **Weights** are *absmean* quantised: each tensor is divided by its mean absolute value,
\[
\gamma = \frac{1}{nm}\sum_{ij}|W_{ij}|,
\]
then rounded to the nearest integer in \{-1, 0, +1\}.  
* **Activations** are kept in INT8 and scaled uniformly per token so that no zero‑point offset is required; this keeps the math simple while preserving expressivity.

Because every weight is ternary, the multiplication phase collapses into a *conditional add/subtract/zero* operation which modern accelerators can implement as a few back‑to‑back adders and comparators.  The resulting kernel (`2-bit` kernel from Ladder) runs on pure integer hardware, eliminating all floating‐point units from the critical path.

## 3.  Latency savings – a tangible speedup  
The time per output token is dominated by matrix multiplication inside each Transformer block.  
| Model | Size | Latency per token (ms) | Speedup vs FP16 |
|-------|------|------------------------|----------------|
| LLaMA FP16 | 3 B | ~2.5 | – |
| BitNet b1.58 | 3 B | ~0.9 | **2.8×** |
| BitNet b1.58 | 7 B | ~10 | **4×** |
| BitNet b1.58 | 70 B| ~70 | **4 ×** |

The speedup grows with model size because FP16 multiplies scale linearly with the number of parameters while BitNet’s additions do not – they are limited only by parsing the ternary filter mask.

## 4.  Memory bandwidth – less data, same payload  
Floating–point models require twice as many bytes per weight as INT8 models:

- FP16 weights: \(2^{11}\) bits per element (≈2 B).  
- Ternary weights: ⌈log₂(3)⌉ ≈ 2 bits ⇒ effectively one Int8 per two real coefficients after packing.

In practice BitNet uses a packed representation where two ternary values share one byte (“bits / value” ≈ 0.5). Even if we ignore packing optimisations, memory usage drops by roughly \(3.5\times\) compared with FP16 (see Table~\ref{tab:ppl}).  

Reduced bandwidth translates directly into lower DRAM–to–SRAM traffic:

- **DRAM traffic** for a single forward pass shrinks by >70 %.  
- **SRAM utilisation** doubles, permitting larger batch sizes on the same card.

## 5.  Silicon power – an order‐of‐magnitude drop  
GPU chips report energy per operation for FP and INT as follows (typical values on a modern GPU):

| Operation | Energy (aJ/op) |
|-----------|----------------|
| FP16 mul   | ~12          |
| FP16 add   | ~5           |
| INT8 add   | ~0·15        |

In an LLM forward pass each matrix multiplication involves \(N^2\) ops; replacing three fp ops with a single int add leads to a net reduction:

\[
E_{\text{BitNet}} \approx \frac{0·15}{12+5} \approx \frac{0·15}{17} \approx **0·009\,aJ/op**
\]

This translates into a reported **71×** reduction in arithmetic–operations energy consumption on state‑of‑the‑art \(7\,nm\) silicon for comparable model sizes (Figure 3). When considering end‑to‑end inference over many tokens, total power draw drops from several kilowatts to sub‑kilowatt levels while maintaining identical perplexity.

## 6.  Throughput – more requests per watt  
Benchmarking on two A100 GPUs running pipeline parallelism shows that a \(70\,B\) BitNet can serve up to eleven times as many requests per second as its FP16 counterpart at the same batch size limit (Table 4). This throughput increase stems from both lower latency and lower memory footprint per token.

## 7.  One extra bit – why “b1.58”?  
The “11” in *b1.58* comes from adding a zero value to standard binary quantisation:

- Binary (\{-1,+1\}) needs one bit per weight → \(w=8\log_2(2)=8\,bits/\!\theta=8\,bits/\text{sparsity}\).
- Adding zero gives ternary weights, which effectively require \(log_2(3)\approx1·58$ bits when encoded with a two–bit representation and yet offer feature filtering for free.

This small overhead pays off by enabling *explicit sparsity*, which further reduces both compute and memory usage at inference time because many matrix entries become exactly zero and can be skipped or compressed on‐the‐fly.

## 8.  Implications beyond inference  
* **Edge / mobile:** The low memory footprint and reliance on pure INT arithmetic makes BitNet ideal for CPU‐only or lightweight GPU deployments where power budget is tight.
* **Long sequences:** With activations already in INT8 (and future work targeting INT4), KV caches double their usable length without extra bandwidth penalties.
* **Hardware design:** Companies such as Groq have demonstrated specialized LPUs for LLMs; a dedicated *BitUnit* that implements ternary weight logic would reduce silicon area even further than current mixed‑precision cores.

## 9. Conclusion  
BitNet b1.58 proves that moving from floating point to an integer paradigm is not merely a compression trick but an *architectural innovation*. By forcing all weights into \{-1, 0, +1\} we eliminate expensive multiplications entirely, achieve sizeable latency reductions, cut memory bandwidth usage by over threefold, and drop energy consumption by more than an order of magnitude—all without compromising language modelling performance beyond what full FP16 baselines deliver at comparable scale.

This compute revolution invites new hardware designs tailored to integer linear algebra and encourages wider adoption of deep learning workloads on cost‑constrained platforms—from data centers to edge devices—paving the way toward truly ubiquitous AI services without sacrificing quality or sustainability."
