# From Small Blocks to Big Models – The Anatomy of an xLSTM Architecture  

Large‑scale language models are usually built from a handful of repeating **building blocks**.  
With the new *xLSTM* family you can keep that modular spirit while turning a vanilla LSTM into a modern, billion‑parameter model that matches – or even beats – Transformers on many benchmarks.  

In this post we walk through the three core ideas that make xLSTM work:

1. **Residual backbones** that give the model depth and stability  
2. **Pre‑/post‑up‑projection blocks** that decide where the heavy lifting happens  
3. **Stacking sLSTM / mLSTM cells** to build an end‑to‑end LLM

Along the way you’ll see diagram sketches and short code snippets for PyTorch and JAX (or Haiku), so you can start prototyping right away.

---

## 1. Residual Backbones – The “Glue” Between Layers  

All state‑of‑the‑art language models (GPT, Llama, Mamba…) share a simple recipe: a stack of *residual blocks* arranged in a pre‑LayerNorm style.  
An xLSTM block lives inside this scaffold; the residual connection lets gradients flow easily through many layers and gives the network an inductive bias toward identity transformations – exactly what we want when we replace the Transformer self‑attention with an LSTM cell.

```
┌─────────────────────┐
│     LayerNorm(x) ──►  ──► (adds into residual later)
│                       │
│   [Block]             │
│                       │
└───┬───────────────────┘
    ▲                 ▲
    │                 │
...│                 ...          ←  N Stacked Blocks
```

The block itself will contain one *sLSTM* or *mLSTM* cell together with some feed‑forward and projection logic that we’ll discuss next.

---

## 2. Pre- vs Post-Up‑Projection: Where Does the Heavy Work Happen?  

### Pre‑Up‑Projection (used for mLSTM)

For matrix‑memory cells we “project up” **before** any non‑linearity:  

```
x ──► lin_proj ↑ d_hidden*H  ──►   …(mLSTM cell) …   ──► lin_proj ↓ d_hidden
```

*Why?*  
The mLSTM’s memory is a $d \times d$ matrix. Operating directly in a high dimensional space gives it a larger storage capacity and keeps memories well separated, which is exactly what covariance updates want.

### Post-Up‑Projection (used for sLSTM)

With scalar memory cells we keep everything in the native hidden dimension as long as possible, then only **after** computing the gated cell state do we expand to a higher dimension:

```
x ──► lin_proc ↓ d_hidden  ──►  sLSTM cell   ──► lin_proj ↑ d_hidden*H  ──► lin_proj ↓ d_hidden
```

The extra projection at the end turns small gates into useful high‐dimensional features while keeping the recurrent path cheap (because memory mixing relies on scalar hidden dynamics).

## 3. Two Families of Cells – sLSTM & mLSTM  

| Feature | sLSTM | mLSTM |
|---------|-------|-------|
| Memory Shape | scalar $c \in \mathbb{R}$ | matrix $\mathbf C \in \mathbb{R}^{d\times d}$ |
| Gating | exponential input & forget gates + stabilizer | exponential input & forget gates + stabilizer |
| Parallelism | no; requires sequential memory mixing | fully parallelizable |
| Use of Heads | multiple heads *within* each head – no cross-head mixing | multiple heads equivalent to multiple cells |

### Exponential Gating & Normalizer

Both cells replace traditional sigmoid gates with an *exponential* activation:

```python
i_t = exp( W_i @ x_t + b_i )
f_t = exp( W_f @ x_t + b_f )   # or σ for numerical stability
```

Because large exponentials can overflow, we keep a running “stabilizer” $m_t$:

```text
m_t = max( log(f_t) + m_{t-1}, log(i_t) )
i'_t = exp( log(i_t) - m_t )
f'_t = exp( log(f_t) + m_{t-1} - m_t )
```

These stabilized gates are mathematically equivalent to their original forms but numerically safe.

### sLSTM Forward Pass

```python
c_t = f_t * c_{t-1} + i_t * z_t              # cell state update
n_t = f_t * n_{t-1} + i_t                    # normalizer
h_t = o_t * ψ( c_t / n_t )                   # hidden state (ψ = tanh)
```

### mLSTM Forward Pass

```python
C_t   = f_t * C_{t-1} + i_t * v_t @ k_t.T     # outer-product update
n_t   = f_t * n_{t-1} + i_t * k_t             # normalizer vector

h̃_t  = C_t @ q_t / max( |n_t.T @ q_t| , 1 )   # key–value retrieval
h_t   = o_t ∘ h̃_t                              # elementwise product with output gate
```

> **Tip:** In PyTorch you can use `torch.einsum("biv,bjv->bij", v, k)` for the covariance update; this is heavily GPU optimized.

## 4. Stacking into a Full Model  

You see how everything fits together in one block? The full architecture is just many of these blocks linearly stacked:

```
token_embed -> [Block 1] -> [Block 2] -> … -> [Block N] -> final projection → logits ↦ probability distribution.
```

When building a large language model you choose:

| Choice | What it buys you |
|--------|------------------|
| **$N$ (number of blocks)** | Depth increase → better abstraction but more compute |
| **$d_{\text{hidden}}$** | Width of hidden representations |
| **$H$ (up-projection factor)** | Higher dimensional space for richer feature interaction |
| **Ratio s/m** (`xLSTM[7:1]` etc.) | Mix heavy parallel matrices with lightweight scalar cells |

In code (simplified PyTorch):

```python
class XLMSTokenEmbedding(nn.Module):
    def __init__(self, vocab, d_embed):
        super().__init__()
        self.embed = nn.Embedding(vocab, d_embed)

class XLMSTokenHead(nn.Module):
    def __init__(self, d_head, vocab):
        super().__init__()
        self.out = nn.Linear(d_head, vocab)

class XLMSTransformerBlock(nn.Module):
    def __init__(self, cell_cls, dim, proj_factor):
        super().__init__()
        self.norm = nn.LayerNorm(dim)
        if issubclass(cell_cls, SLstm):          # post-up-projection block
            self.pre_proj  = nn.Linear(dim, dim)
            self.cell      = cell_cls(dim)
            self.post_proj = nn.Linear(dim*proj_factor, dim)
        else:                                   # pre-up-projection block (mLSTM)
            self.pre_proj  = nn.Linear(dim*proj_factor, dim)
            self.cell      = cell_cls(dim)
            self.post_proj = nn.Linear(dim, dim)

    def forward(self, x):
        y = self.norm(x)
        y = self.pre_proj(y)
        y = self.cell(y)
        y = self.post_proj(y) if hasattr(self.cell,'post_proj') else y
        return x + y                       # residual connection

class XLmModel(nn.Module):
    def __init__(self, vocab, num_blocks=48,
                 dim=2048,b=4,norm='pre',whole_ratio=(7,1)):
        super().__init__()
        ratio_s,l_m=(whole_ratio[0],whole_ratio[1])
        block_specs=[]
        for i in range(num_blocks):
            if i%ratio_s<ratio_s:          # sLSTM block slot
                block_specs.append(SLstm)
            else:
                block_specs.append(Mlstm)
        layers=[XLMSTokenEmbedding(vocab,dim)]
        layers+= [XLMSTransformerBlock(cls=cell,d=dim,b=b) for cell in block_specs]
        layers.append(XLMSTokenHead(d_head=dim,vocab=vocab))
        self.net=nn.Sequential(*layers)

    def forward(self, tokens):
        return self.net(tokens)              # logits before softmax
```

> **JAX users** can replace `nn` with Haiku’s `hk.RNNCore` variants and use `jax.vmap` to automatically vectorise over batch dimension.

## 5. Practical Tips & Common Pitfalls

| Tip | Why it matters |
|-----|----------------|
| **Start small** (e.g., < 5 M params) before scaling up to billions; fine‑tune gradient clipping & learning rate schedules from Transformers.* | All modern LLMs use similar tricks (`warmup`, AdamW). |
| **Use mixed precision (`torch.cuda.amp`)** but avoid automatic mixed precision on older GPUs where `ln`/`exp` might blow up. Micro-batch sizes of ~ 8–16 are usually safe.* | The exponential gates are more sensitive to float32 vs float16 errors. |
| **Cache queries & keys** in inference mode if you need multi-head decoding (`torch.compile`). | Helps accelerate generation by avoiding repeated projection costs. |
| **Parallelise the matrix memory** with `torch.bmm` instead of loops; FlashAttention‑style scan can be used for *suppressing overflow* during covariance updates.* | This keeps wall clock time low even at large dimensions $d$. |
| **Track normalizer state `$n_t$` carefully**; if it underflows machine epsilon both `i` and `f` vanish prematurely.* | In early training rounds it’s common to add small epsilons to denominators as shown in Eq.~(13). |
