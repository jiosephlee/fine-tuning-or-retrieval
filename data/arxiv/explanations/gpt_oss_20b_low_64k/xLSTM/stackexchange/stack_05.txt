\title{Stack Exchange of the Paper: "xLSTM: Extended Long Short-Term Memory"}

### How does the xLSTM block architecture decide between pre‑up‑projection and post‑up‑projection?
Question:
The authors mention using post up‑projection blocks for sLSTM and pre up‑projection blocks for mLSTM due to 'memory capacity becomes larger in the high‑dimensional space'. I am not sure what dictates this choice. Does employing pre up‑projection reduce computational cost for matrix memories? What are the trade‑offs between these two residual block designs?
Answer:
**Short‑answer**  
In an xLSTM block the *pre‑up‑projection* (the high‑dimensional projection comes first) is used with **mLSTM**.  The *post‑up‑projection* (the high‑dimensional projection comes after the recurrence) is used with **sLSTM**.  The decision is driven by two facts:

1. **Where the memory lives** – sLSTM stores a scalar (or a small vector) per time step, so the costly matrix/matrix operations that define the memory are inexpensive.  The main computational burden is the recurrent mix of the hidden state across dimensions (the “memory mixing”).  Making this mixing *after* the high‑dimensional up‑projection would force a large dense matrix–matrix product on every time step, which would completely lose the efficiency that came from keeping the memory low dimensional.

2. **Where the large‑dimensional representation must be stored** – mLSTM replaces each scalar cell by a full \(d\times d\) matrix \(\mathbf{C}\).  Operating directly in this space is essential: all updates and retrievals are matrix multiplications of size \(d\times d\).  If we were to do the high‑dimensional projection *after* a small scalar or vector recurrence, we would have to first collapse back to the low‑dimensional space and then re‑expand, which would negate the benefit of having a matrix memory in the first place.  The pre‑up‑projection therefore keeps all computations in the high‑dimensional space until the final linear mapping back to the model dimension, matching what mLSTM already does.

Below I unpack these points in more detail, compare cost and memory implications, and touch on broader architectural concerns.

---

## 1. The two residual backbones

| block | order of operations | intuition |
|------|---------------------|-----------|
| **post up‑projection** | Compute recurrent transformation in  \(d\) dimensional space → project to \(D\) → nonlinear → project back to \(d\) | Keep recurrence cheap (small state); use high‑dimensional space only to learn richer transformations once per layer |
| **pre up‑projection** | Project input to \(D\) → recurrent transformation in \(D\) → project down to \(d\) | All heavy matrix work happens inside the recurrence; fits naturally with a full \(D\times D\) memory such as mLSTM |

The *xLSTM* paper adopts this convention throughout: every sLSTM block uses post up‑projection; every mLSTM block uses pre up‑projection.

---

## 2. Why post for sLSTM?

### Small state → cheap recurrence
The sLSTM cell implements

\[
c_t \leftarrow f_t c_{t-1} + i_t z_t , \qquad 
h_t \leftarrow o_t \,\psi(c_t/n_t),
\]

with scalar (or tiny vector) gate values and a scalar cell state.  Even when several sLSTM cells are concatenated into a vector \(\mathbf{c}_t \in \mathbb{R}^d\), all operations remain linear or elementwise in that small dimension. The heavy lifting—the nonlinearity and dimension change—is postponed until after that cheap recurrence.

If we moved the projection *after* this recurrence, every step would require a dense matrix–matrix product of size \(d\times D\), which would blow up both compute and memory because we’d be performing it for every element of the sequence during training or inference.

### Memory mixing at low cost
sLSTM relies on “memory mixing” via recurrent weight matrices applied to hidden states from earlier time steps.  These matrices are of size \(d\times d\); keeping them small keeps GPU register pressure low and lets us perform many unroll steps with minimal overhead.  Post up‑projection lets us keep this mixing local and fast.

---

## 3. Why pre for mLSTM?

### Matrix cell lives in high dimension
The mLSTM cell stores a full \(d\times d\) matrix \(\mathbf{C}_t\). Its update rule is

\[
\mathbf{C}_t = f_t\, \mathbf{C}_{t-1} + i_t\, \mathbf{v}_t \mathbf{k}_t^\top .
\]

Both terms involve full matrix–matrix products or outer products; they are natural when everything is already expressed in dimension \(d=D\). If we tried to apply a tiny recurrence first (as post would do), we would have to map a low‐rank update into a full matrix after every time step—a costly Von Neumann bottleneck with no gain.

### Parallelizability
mLSTM can be reorganised into a purely parallel form (scan‐free formulation: see Appendix C). All dependence on previous time steps is captured by successive matrix multiplications that can be batched across time steps or treated as one big GEMM. This architecture assumes that all intermediate tensors remain in dimension \(D=d_\text{model}\). A pre‐up‑projection keeps everything inside this space until the very end.

### Exponential gating interactions
Both sLSTM and mLSTM use exponential gates (\(i_t = e^{\tilde i_t}\), \(f_t = e^{\tilde f_t}\)). In mLSTM these gates scale entire rows/columns of matrices; applying them before any dimensionality reduction ensures that their effects distribute correctly across all dimensions of \(\mathbf{C}_t\).

---

## 4. Computational cost & memory trade–offs

| aspect | post (used with sLSTM) | pre (used with mLSTM) |
|--------|------------------------|-----------------------|
| *Matrix size in recurrence* | \(d\times d\) (tiny) | \(D\times D\) (large) |
| *Number of large GEMMs per step* | < 1 (only during up/down projections) | ~ 1–2 (updates/retrievals inside recurrence) |
| *Parallelisation* | Poor – sequential due to hidden‐hidden mixing | Good – entire recurrence parallelisable |
| *Memory footprint* | Linear in sequence length (small states stored per step) | Also linear but larger per step due to D×D state |
| *Wall–clock overhead* | Lower when D≫d because only two projections cost significant time | Higher per step but amortised by parallel scans; overall still competitive for large models |

The paper’s ablation experiments (“Memory and Speed Considerations” section) confirm this: sLSTMs are < 2× slower than parallel mLSTMs despite allowing sequential computation because their small states keep register pressure low. Conversely, mLSTMs incur a few GEMM operations per step but benefit from GPU’s massive parallelism; when batch sizes grow, their throughput overtakes transformers quite easily.

---

## 5. Bottom line for choosing between them

- **Use post up‑projection when your recurrent unit has only small internal state** (scalar or few dimensions). This keeps each time step cheap while still benefiting from an expressive high‑dimensional feature map after the recurrence.
  
- **Use pre up‑projection when your recurrent unit itself lives in that high dimensionality**—e.g., you’re accumulating outer products or full covariance matrices. Moving everything into that space before unrolling allows you to exploit efficient large GEMMs and keep all heavy operations inside one contiguous tensor kernel.

In xLSTM this mapping becomes almost automatic:  
- **sLSTM → Post** – because its core is scalar/low‐dimensional.  
- **mLSTM → Pre** – because its core is already a full high‐dimensional matrix.

---

### Closing remark

This design choice is not arbitrary but rooted in where expensive operations actually occur inside each variant of LSTM. By aligning the projection order with those mathematical needs, xLSTM blocks keep both compute and memory close to minimal while still leveraging powerful high-dimensional transformations where they matter most—mirroring what transformers do but matching LSTMs’ sequential strengths.
