Chapter 13: # 13 Practical Aspects and Implementation Details  

In this chapter we turn the theoretical machinery of Direct Preference Optimization (DPO) into a concrete training recipe that can be reproduced by other researchers and practitioners. The core ideas of DPO—optimizing a language‑model policy directly from pairs of human‑labeled preferences—eliminate the Monte‑Carlo sampling and policy‑gradient updates that dominate conventional RL‑HF workflows.  What remains, however, is a sensible choice of reference policy, a principled way to set the KL‑conservativeness parameter \( \beta \), and a concrete training schedule that fits within the memory budgets of modern GPUs.  We therefore enumerate concrete design decisions that make DPO both tractable and easy to reproduce, while pointing out the computational savings it brings compared with an end‑to‑end PPO loop.

## 13.1  Reference Policy \(\pi_{\text{ref}}\) : From SFT or a Likelihood Proxy  

The DPO objective (Eq. (6) in the paper) requires a *reference* distribution \(\pi_{\text{ref}}(\cdot\mid x)\).  In practice this plays two distinct roles:

1. **Regularization anchor** – it defines the KL‑constraint that keeps the fine‑tuned policy close to a sensible baseline.
2. **Baseline for importance weighting** – in Eq. (6) the term
   \[
   \log\frac{\pi_{\theta}(y\mid x)}{\pi_{\text{ref}}(y\mid x)}
   \]
   appears inside a logistic function; this implicitly normalises the log‑probability ratios.

Because DPO never samples from \(\pi_{\theta}\) during training, all these operations can be carried out offline on precomputed logits from \(\pi_{\text{ref}}\).  Two practical ways to obtain \(\pi_{\text{ref}}\) are common.

### 13.1.1  Initialise with an SFT Model  

When a supervised fine‑tuned (SFT) model is available for the task at hand, the **simplest recipe** is to set
\[
\pi_{\text{ref}} = \pi^{\text{SFT}},
\]
i.e., use exactly the SFT checkpoint that will later be updated by DPO.  
Practitioners frequently have an SFT model because many open‑source RLHF pipelines already publish one; GPT‑2/7B, Llama‑2/7B, or Vicuna variants frequently come with an SFT checkpoint tuned on instruction following or summarisation data.  
You only need to keep the *policy stack* (the same transformer block rows used both for inference and fine‑tuning).  
Because \(\pi_{\text{ref}}\) remains frozen throughout training, you can pre–seed its logits once per prompt and reuse them across all batches – an important memory saver when you process thousands of preference pairs.

### 13.1.2  Replay‑Likelihood Proxy when SFT is Unknown  

In many downstream tasks or low‑resource settings no SFT model exists at all – for example, when fine‑tuning on an entirely new domain while only having human preferences over outputs generated by a large generic LM (such as GPT‑3 or Llama‐2).  
In this case, we approximate \(\pi_{\text{ref}}\) by *maximum likelihood* on the preferred outputs:
\[
\pi_{\text{ref}}
\:=\:
\arg\max_{\pi}\;
\mathbb{E}_{(x,y_{w})\sim\mathcal{D}}\!\left[\log\,\pi(y_{w}\mid x)\right].
\]
Because each preference pair supplies us with one *positive* completion \(y_{w}\), we can run a single supervised pass over all pairs using cross‑entropy loss (with standard label smoothing, if desired).  
Weights are subsequently accumulated for each token in \(y_{w}\), producing logits that mirror how often humans liked that trajectory under whatever generating LM was used in the preference collection.

This *quick fit* delivers a reasonable reference policy:

- It is **consistent** with positive completions so that Bayesian KL regularisation does not push too aggressively away from human‐favoured language.
- It performs well empirically – we observe only marginal differences in final performance when using either method if you are working in a domain where you have sufficient data.

Once you have \(\pi_{\text{ref}}\), freeze its parameters; no further updates are made to it during DPO training.

## 13.2 Choosing the KL Scale β  

The scalar \( \beta > 0 \) controls how strongly you penalise deviation from \(\pi_{\text{ref}}\).  A small value forces \(\pi_{\theta}\) to stay near the reference, preventing catastrophic mode collapse; a large value pushes hard towards higher reward but risks drifting into unrewardful regions of logit space where the reward model was poorly estimated.

A handful of practical guidelines have emerged from empirical work:

| Criterion                                    | Typical β Range          |
|----------------------------------------------|--------------------------|
| Very conservative policy (no drift allowed) | \(0.05–0.1\)             |
| Balanced reward vs elasticity              | \(0.5–1.0\)              |
| Aggressive pursuit of high reward           | \(5–10\)                 |

**Why these numbers?**  
Let us derive an intuitive scale by examining Eq. (6)'s logistic term:
\[
\sigma\!\left(
    \beta\, 
    \log 
    \frac{\pi_{\theta}(y_w)}{\pi_{\text{ref}}(y_w)}
    -
    \beta\, 
    \log 
    \frac{\pi_{\theta}(y_l)}{\pi_{\text{ref}}(y_l)}
    \right).
\]
The log–ratio typically ranges between \(-10\) and \(+10\) for token probability differences of roughly orders of magnitude apart at moderate temperature settings (\(T=0.7–1.\)).  
If we choose β ≈ 1 this yields inputs into σ comparable to raw logits, yielding gradients in the flat middle part of σ (~0.25–0.75).  
If β ≈ 5 these inputs blow up toward |5×10|=50 yielding almost saturated gradients: either huge increases for favored tokens or essentially zero gradients for disfavored tokens – which may cause fast collapse or sudden spikes in loss.

Therefore picking β≈ 1 is often an excellent starting point: it preserves sensitivity while keeping gradients stable across diverse prompt spaces.

**Practical tuning strategy:**  
- **Warm start** with β = 0.5; observe whether rewards improve rapidly while KL stays bounded.
- **Plot** reward vs KL over initial epochs; if reward climbs but KL explodes quickly, reduce β accordingly.
- **Stop after ~100–200 steps** once reward stabilises; most tasks reach near optimum within this window.

Learning curves generally exhibit diminishing returns after ~500 steps; beyond that point additional gradients aggregate slowly because every preference pair already contributes maximal (or zero) impact due to saturated σ activation.

## 13.3 Mini‐Batching and Training Schedule  

Unlike policy gradient methods which require on‐policy rollouts at every training step, DPO learns entirely offline:

1. **Precompute logits:** For each prefix \(x^{(i)}\), sample two completions \(y_1,y_2~{\sim}\,\pi_\text{ref}\), store their token IDs and corresponding log probabilities under both models.
2. **Preference labelling:** Human annotators compare these two completions and tag one as preferred.
3. **Batching:** Collect all labeled pairs into a dataset \(\mathcal{D}\).

During training we simply iterate over mini‐batches sampled uniformly from \(\mathcal{D}\). 

### Hyperparameters

| Parameter            | Default Value | Comments                                                                          |
|----------------------|---------------|-----------------------------------------------------------------------------------|
| Batch size           | 64            | Works well on V100/RTX 4090 @ ~12GB VRAM; adjust down to ~32 if memory tight |
| Sequence length      | Fixed by dataset’s max token full length | Truncate longer completions > `max_seq_len`                                 |
| Learning rate (SGD/AdamW) | \(3\times10^{-5}\)| Decay optional but seldom required                                     |
| Max training steps   | 500           | In most tasks converging before hit                                        |
| Gradient accumulation | ≥ 1          | Use as needed to hit effective batch size without exceeding VRAM              |

#### Why no sampling loop?  

Because DPO has no *on‐policy* requirement, each update uses deterministic gradient calculations through `logπθ` evaluated on stored sequences only once per epoch—overhead is minimal: every stack trace reduces to evaluating cross‐entropy between two probability ratios per token pair—completely parallelisable across GPUs:

```python
# pseudo code
for step in range(num_steps):
    batch = next_dataloader_batch()                # {(x,w,l): Logits(w), Logits(l)}
    # calculate ratio logs using inserted θ logits
    ratio_w = logprobs_theta(batch.w - batch.w_ref)
    ratio_l = logprobs_theta(batch.l - batch.l_ref)
    # logistic centered weight
    label_weights = sigmoid(betatilde*(ratio_w - ratio_l))
    # gradient update via autograd on binary cross entropy
```

Memory consumption is dominated by storing per-token logprob stacks for all pairs — roughly `batch_size × seq_len × num_tokens × floats`—which is far smaller than storing floating point samples plus RL rollouts used in PPO (where sequences must be re-generated after each policy update).

### Training Steps vs Data Size  

In real-world preference sets such as TL;DR (~90k pairs), even taking just 50% of them yields stable convergence within ~300 steps given batch size 64: more steps do not significantly increase win rates because preferences saturate earlier than rewards would do in RL loops where sampling introduces extra variance.

### Computing gradients efficiently  

Since we take gradients w.r.t both token probabilities simultaneously for `preferred` and `dispreferred` sequences, we can fuse operations:

- Use batched torch `einsum` or TRAX’s internal fused kernels.
- Cache `log(pi_ref)` at dataset load time so they ‘slide’ through during training without recomputation.

All together this results in **an order-of-magnitude** saving over PPO: one PPO epoch might involve dozens of forward passes per step (+critic updates + importance sampling adjustments). With DPO you perform one forward pass per batch plus a swift backward pass.

## 13.4 GPU Memory Savings Relative to PPO Loops  

PPO-based RLHF typically needs:

| Stage                        | Memory Footprint                                        |
|------------------------------|---------------------------------------------------------|
| Reference LM + policy LM     | Two separate transformer dfs → ~2× parameter memory     |
| Rollout buffer               | Store episodes (+states/actions/rewards); usually ≥  BER..GB |
| Critic network + target      | Multi-head network; additional parameters               |

During each PPO iteration you must **recompute** samples using both policies: first generate synthetic trajectories with `πθ_n` then evaluate rewards using `rφ`. Even if you initialise `πθ` from `π^SFT`, memory usage spikes because it dominates VRAM: you cannot keep two full models active concurrently without partitioning across multiple GPUs or employing offloading tricks.

By contrast:

- DP o keeps only one copy of the transformer (*policy*) alive during fine-tuning.
- All “reference” values are precomputed and stored as static tensors (`logᵣ`, possibly compressed).
- No rollouts enlarge memory footprint beyond what already holds BPTT buffers for standard language modeling losses.
- Because DPO uses ordinary cross‑entropy loss evaluated on static batches, gradient computation reuses cached activation tensors without infinite iteration loops – total VRAM requirement essentially equals `<recommended_batch> × <seq_len> × <token_dim>` plus tiny overheads (<4 GB for typical large LM).

Therefore, DPO comfortably fits onto single mid-range GPUs for models up to ∼7B parameters, whereas PPO would typically require multi-GPU setups or aggressive offloading to achieve similar scalability.

## 13.5 Additional Practical Tips

- **Prompt truncation vs padding:** Ensure your dataset’s prefixes identify which tokens can be dropped arbitrarily – always pad sequences up to maximum length with mask so your loss ignores padded positions.
- **Gradient clipping:** Empirically we usually clip max norm at \( ||g||_2 = 5.\)
- **Log-softmax stability:** Compute ratios via subtractive trick:
  ```
  r_hat = beta *(logits_theta - logits_ref)   # per token
      = beta * torch.log_softmax(logits_theta / logits_ref)
  ```
- **Checkpointing:** Save `πθ` every ten epochs; since no environment sim is involved cutting small checkpoints does not impede rollback.
- **Batch shuffling:** Randomly shuffle preference pairs each epoch to avoid bias toward early sampled prefixes.
- **Learning rate scheduler:** Optional linear warmup over first five epochs followed by cosine annealing helps avoid early oscillation sometimes observed when many short prefixes contribute disproportionately high gradients.

With these implementation choices in place researchers now have a clear path from paper theory—equation derivations—to reproducible experiments that give competitive or better alignment than state-of-the-art RLHF while using markedly less computational resources._END_
