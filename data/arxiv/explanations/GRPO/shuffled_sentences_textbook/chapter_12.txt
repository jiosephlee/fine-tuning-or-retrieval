In short, code training helps tool-based reasoning strongly and helps CoT when used as a preparatory stage before math training; but naive mixing can harm CoT unless model capacity or the training regime is adjusted. Two variants are described: training on only $150\mathrm{B}$ math tokens (pure math one-stage), and training on a combined corpus mixing $400\mathrm{B}$ code tokens with $150\mathrm{B}$ math tokens in one continuous stage. In the two-stage experiments, the $400\mathrm{B}$-token code stage alone produced noticeable gains on program-aided problem solving; adding a subsequent $150\mathrm{B}$ math stage further improved PoT performance. In other words, simply training on arXiv material alone did not transfer into better performance on the downstream math benchmarks used in this study. In the one-stage or mixed-condition, code and math tokens are interleaved or sampled from a single combined corpus in a single training pass. However, the single-stage mixed training (simultaneous exposure to code and math tokens) mitigates this catastrophic forgetting: by exposing the model to both distributions continually, the model maintains coding performance better than the sequential two-stage pipeline. Contrary to common assumptions, the arXiv-only trained models did not show improvements on the evaluated math benchmarks; in many cases they exhibited no notable gains or even deterioration. This suggests a tension between preserving code behavior and maximizing textbook-like natural-language reasoning when model capacity is constrained. Empirically, code training had a clear positive effect on PoT-style performance. This negative result appeared consistently across different task types: quantitative reasoning datasets such as GSM8K and MATH, multiple-choice STEM items like MMLU-STEM, and formal mathematics tasks measured by miniF2F. This outcome suggests that arXiv content, at least processed and incorporated in the ways tested here, is not an effective replacement for the carefully selected web-scraped math content that DeepSeekMath used. The authors explicitly tested whether arXiv-only corpora improve mathematical reasoning by training on two arXiv-dominated datasets: MathPile (an $8.9\,$B-token corpus with over 85% arXiv content) and ArXiv-RedPajama (a $28.0\,$B-token cleaned arXiv corpus). This indicates that code exposure helps the model learn structures that later permit more efficient acquisition of mathematical reasoning in natural language form. Concretely, one condition trains for $400\mathrm{B}$ tokens of code and then $150\mathrm{B}$ tokens of math. Large models may be better able to extract and generalize the formal, dense content of arXiv papers; therefore, the current negative result should not be taken as definitive for all scales. To test this hypothesis in a controlled way, the authors designed comparative pre-training experiments that isolate the effect of code exposure from other factors. In the context of code and math pre-training, the concern is twofold: (1) will math-focused fine-tuning erase code ability, and (2) can we design training schedules that keep or even enhance both competencies? For CoT-style (no-tool) reasoning, the picture is nuanced. In summary, the paper's arXiv ablations caution against assuming that all mathematically rich corpora are equally useful. Second, model scale matters. But the authors are explicit that further work is required: to test different tasks, mixing strategies, processing methods, and larger model scales before forming general conclusions about arXiv's role in math pre-training. Across both two-stage and one-stage settings, exposure to code tokens substantially improved the models' ability to write correct Python programs for math problems such as those in GSM8K and MATH. The experiments used models up to $7\,$B (and $1.3\,$B) parameters. The authors emphasize several important caveats to the arXiv findings. Two distinct experimental paradigms were used: two-stage training and one-stage (mixed) training. First, the negative result for arXiv-only training is limited to the specific benchmarks, processing pipelines, and model scales explored. The intuition behind this hypothesis is that code embodies structured, symbolic manipulation, precise control flow, and explicit step-by-step computation — properties that overlap with the procedural aspects of mathematical problem solving. A control variant replaces the first-stage code tokens with general-domain text of the same scale (also $400\mathrm{B}$ tokens) followed by the same $150\mathrm{B}$ math tokens. In the two-stage setup, a base model (DeepSeek-LLM with $1.3\,$B parameters) undergoes a long first stage of training on code tokens followed by a second stage on mathematical web tokens. Under the two-stage regimen, the initial code training provided moderate improvements in pure textual chain-of-thought performance, and importantly it accelerated the effectiveness of the following math-only stage so that the best CoT results arose from the code-then-math pipeline. These map to two facets of capability: tool-aided, computation-heavy reasoning (PoT) and verbalized multi-step reasoning (CoT). This mixed approach tests whether simultaneous exposure avoids forgetting of code capabilities while still granting math benefits. The empirical takeaway is that selecting and engineering a math-focused training corpus from web sources, rather than relying solely on arXiv content, led to superior performance in the examined settings. Nevertheless, mixed training came with the aforementioned trade-off: while it preserves code skill, it did not match the best CoT (no-tool) math performance achieved by the two-stage code-then-math schedule on the $1.3\,$B model. It implies that not all mathematical text is equally useful for the target benchmarks; web math pages curated by the authors' fastText-based selection pipeline (the DeepSeekMath Corpus) were empirically more beneficial. Third, processing choices for arXiv (how LaTeX is converted, whether macros, bibliographies, or math markup are retained or removed) likely influence downstream utility. It remains an open question whether the benefits (or harms) of arXiv content would change at much larger model sizes. The two arXiv variants used differed in processing: MathPile is an aggregated corpus with heuristics, while ArXiv-RedPajama had many LaTeX artifacts removed. The experiments show that a straightforward two-stage pipeline — long code training followed by math training — can induce forgetting of coding skills. Thus code pre-training appears to directly transfer to program-writing accuracy and reliability. "Catastrophic forgetting" refers to the phenomenon where a model that is fine-tuned on a new dataset loses performance on skills learned earlier. This isolates whether code specifically — rather than just more pre-training — is helpful. However, in the mixed one-stage condition where code tokens and math tokens are trained together (mixing $400\mathrm{B}$ code with $150\mathrm{B}$ math in a single stage), CoT performance without tools degraded relative to the two-stage code-then-math approach. Using these controlled recipes makes it possible to observe (1) whether a preceding code stage confers advantage on later math-only evaluations, (2) whether mixing code and math in a single stage prevents catastrophic forgetting of code skill, and (3) how these strategies affect both program-assisted and purely textual reasoning abilities. The experiments suggest neither was especially helpful for the evaluated benchmarks, but they cannot rule out that alternative processing pipelines could yield different outcomes. The authors therefore recommend careful consideration of model size and training strategy: for smaller models, a two-stage approach (code then math) may best boost CoT, whereas mixed training can be used when preserving code skill is a priority or when the target is PoT. The study evaluates two distinct forms of mathematical problem solving: program-of-thought (PoT) where the model writes executable programs (e.g., Python) that are run to produce exact answers, and chain-of-thought (CoT) where the model produces step-by-step natural-language reasoning without tool execution. ArXiv content (scientific preprints) is commonly assumed to be rich in mathematical material and has often been included in math-oriented corpora. They performed two experiment sets: training DeepSeek-LLM $1.3\,$B for $150\mathrm{B}$ tokens and training DeepSeek-Coder-Base-v1.5 $7\,$B for $40\mathrm{B}$ tokens on these arXiv-only corpora. The authors conjecture that when model capacity is limited (here, the experiments used a $1.3\,$B parameter model), simultaneously learning both domains can produce interference: the model cannot fully absorb both code paradigms and the nuanced natural-language reasoning patterns of math in one shot. In addition, mixed training synergizes coding and program-aided mathematical reasoning, improving PoT outcomes while preserving code competence. The experiments did not evaluate whether arXiv tokens might help other kinds of tasks (for example, "informalization" or converting formal statements into natural-language explanations), nor did they test mixings of arXiv tokens with other data sources where positive interactions might occur.
