### How is 'tool-integrated reasoning' evaluated fairly across models on GSM8K and MATH?
Question:
For program-of-thought/tool-integrated evaluation, models can call Python with libraries like sympy. How are timeouts, randomness, and environment versions controlled? Are answers compared by numeric tolerance or exact string match? How do you prevent models from exploiting the environment (e.g., reading files, internet) and ensure comparable constraints across models?
Answer:
In DeepSeekMath we treat “tool-integrated reasoning” essentially as a black-box code‐execution problem: every model receives the very same Python prompt (with a fixed set of imports, e.g.  
```python
import math, sympy
```  
), writes out a short program whose last line prints the answer, and we run that program in a tightly controlled sandbox.  The key points that keep the playing field level are:

1. A Fixed, Sandboxed Environment  
   We evaluate all models inside the same Docker container (or equivalent VM) that has only the standard library plus the approved math‐libraries (e.g. SymPy at a pinned version).  The container has no access to the internet, no preloaded data files and no writable filesystem outside of a single ephemeral temp directory.  That way a model cannot “cheat” by reading stored solutions or fetching external computations.

2. Deterministic Runtime with Timeouts  
   Each submitted program is run with a wall‐clock timeout (e.g. 30 s) and a CPU‐time guard.  We also zero out all RNG seeds at the start of execution (`random.seed(0); sympy.random.seed(0)`), so that any use of randomness in the user code cannot change the official metric.  If the program times out or throws an unhandled exception, that problem is simply scored as incorrect.

3. Unified Answer Extraction and Matching  
   Once a program finishes, we capture only its standard‐output “print” stream.  For integer or exact‐rational answers (which is the vast majority of GSM8K/MATH targets), we apply an exact string match against the ground‐truth answer.  For cases where a floating‐point approximation is expected—say the answer is known to within a small tolerance—we parse the printed value as a float and require  
$$
\bigl|\text{result} - \text{gold}\bigr| < 10^{-6}.
$$  
   In either case every model is judged by the very same parser and matcher logic.

4. Fairness via a Single Evaluation Harness  
   Crucially, every open-source and closed-source model we benchmark is hooked into the same harness.  Rather than giving each team its own custom script, we open-source our runner (built atop the community “tool‐execution” evaluation frameworks) so that the Python interpreter version, library versions, timeout values, seed routines, and answer‐checking code are identical for GPT-4, DeepSeekMath, ToRA, Llama-2, etc.  

By combining (1) a frozen, minimal interpreter environment, (2) strict time/cpu budgets and RNG seeding, (3) a unified stdout parser with exact‐or‐tolerance matching, and (4) a single open-source harness for all contenders, we ensure that when one model edges another on GSM8K or MATH via tool calls, it’s because its generated code is genuinely more correct—not because it happened to run on a more powerful VM, sneak in secret data, or exploit some library version quirk.
