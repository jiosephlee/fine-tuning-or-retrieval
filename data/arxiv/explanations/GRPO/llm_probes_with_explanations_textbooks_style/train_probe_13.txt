Chapter: Mixed Code-and-Math Training for Robust Program-Aided Mathematical Reasoning

# Introduction
This chapter explores a central empirical insight from the DeepSeekMath study: when the primary objective is program-aided mathematical reasoning while avoiding deterioration of coding capabilities, the most suitable training strategy is to jointly mix code and math during training. This conclusion is drawn from controlled experiments that compare two-stage and one-stage training recipes using code and mathematical data, and it is situated within the broader design of DeepSeekMath, which targets strong mathematical reasoning through large-scale math pre-training, instruction tuning with chain-of-thought and program-of-thought formats, and reinforcement learning with Group Relative Policy Optimization.

The key notion is that program-aided mathematical reasoning—where the model writes and executes code, often Python, to solve problems—benefits substantially from exposure to code during training. However, naive sequencing of code first and math second can lead to catastrophic forgetting of coding ability. In contrast, mixing code and math tokens in a single-stage training runs counter to that forgetting and, at the same time, synergistically enhances program-aided problem solving. The study’s detailed ablations on a 1.3B-parameter model provide the evidential basis for this conclusion and clarify the trade-offs between different training regimes.

# Program-Aided Reasoning and Catastrophic Forgetting
Program-aided mathematical reasoning refers to the model’s ability to solve problems by writing programs that compute intermediate quantities or final answers. In the evaluations reported in DeepSeekMath, this ability is probed using program-of-thought prompting, where models are prompted to produce Python code that leverages libraries such as math and sympy to carry out nontrivial computation. The resulting programs are executed, and their outputs are treated as answers.

A fundamental difficulty in training models for such program-aided behavior is catastrophic forgetting. Catastrophic forgetting occurs when a model trained on a task \(A\) subsequently undergoes further training on task \(B\) and loses performance on \(A\). In the context of DeepSeekMath’s experiments, code pre-training substantially boosts the model’s ability to write and reason with code, which is critical for program-aided mathematics. However, if this is followed by a stage of math-only training, the model’s coding ability can degrade, a phenomenon clearly observed in the two-stage recipe that trains code first and math second. This is particularly problematic when the target application depends on code execution as part of reasoning, because the representation and generation skills necessary for correct program synthesis become less reliable after extended math-only exposure.

The DeepSeekMath experiments therefore ask two linked questions. First, does code training actually help program-aided mathematical reasoning? Second, if code helps, how can we preserve that benefit while avoiding forgetting when we also want to improve mathematical reasoning through math training? The answers hinge on how code and math are scheduled and combined during training.

# Training Recipes: Two-Stage Versus One-Stage
The study contrasts two-stage and one-stage training settings using a shared base architecture. In both cases the starting point is a general pre-trained model with 1.3B parameters, denoted as DeepSeek-LLM 1.3B, trained under a consistent optimization scheme. The training recipes vary which tokens are used and in what order.

In the two-stage setting, there are two main variants. The first variant performs code training for \(400\mathrm{B}\) tokens and then math training for \(150\mathrm{B}\) tokens. This setup is designed to test whether code pre-training provides a foundation that accelerates or amplifies subsequent math training, and whether it strengthens program-aided reasoning. The second variant replaces the first-stage code with \(400\mathrm{B}\) tokens of general text, again followed by \(150\mathrm{B}\) tokens of math, as a control to quantify the specific effect of code.

In the one-stage setting, there are also two variants. One variant trains solely on \(150\mathrm{B}\) tokens of math. The other trains on a mixture of \(400\mathrm{B}\) code tokens and \(150\mathrm{B}\) math tokens in a single-stage process, interleaving the two sources throughout. The mixed recipe is specifically designed to combat catastrophic forgetting by maintaining a continuous presence of code while the model acquires mathematical knowledge and problem-solving patterns. This continuous presence is hypothesized to anchor the coding representations and generation behaviors that underlie program-aided reasoning, while still providing rich mathematical context that teaches the model to apply code to math problems.

# Empirical Findings: Why Mixed Training Wins for Program-Aided Math
The reported experiments support three connected findings. First, code training clearly benefits program-aided mathematical reasoning. Under the two-stage setting, the code-only first stage already significantly enhances the ability to solve GSM8K and MATH problems with Python via program-of-thought prompting. The subsequent math stage yields additional gains. This confirms that learning to write and reason with code is a strong enabler for program-aided mathematical problem solving.

Second, while code pre-training helps, a math-only second stage leads to forgetting of coding skills. This forgetting is evident in the degradation of coding performance after the code-to-math sequence. From the perspective of program-aided math, this is a serious liability: the model’s emerging mathematical knowledge is no longer paired with equally strong code-writing ability, which undermines the overall effectiveness of program-of-thought strategies.

Third, and most central to this chapter, mixing code and math in a one-stage training process simultaneously mitigates forgetting and synergizes program-aided mathematical reasoning. When code and math tokens are interleaved throughout training, the model retains its coding abilities while continuing to strengthen its mathematical competence. In concrete terms, the mixed recipe preserves coding performance and improves performance on tasks that require writing code to solve math problems. In other words, the continuous co-presence of code serves as a stabilizing signal that prevents the erosion of program synthesis capabilities, while the co-present math data teaches the model to apply those capabilities effectively to mathematical contexts.

The study also observes a trade-off: combining code and math in a single stage can compromise mathematical reasoning without tool use in the 1.3B setting. The authors conjecture that this is due to limited model capacity at that small scale, which may constrain the model’s ability to fully assimilate both domains simultaneously. Nevertheless, for the specific goal of program-aided mathematical reasoning without forgetting, the mixed recipe is the best fit among those tested because it directly optimizes for the joint competence required by program-of-thought prompting.

# Intuition: How Mixed Training Preserves and Enhances Tool Use
The intuition behind the effectiveness of mixed training is straightforward. Program-aided reasoning requires the model to master two intertwined abilities: mathematical understanding and code generation. If training concentrates exclusively on math after a long code phase, the optimization dynamics draw the model’s parameters toward patterns that are optimized for natural language mathematical exposition but are less optimized for code production. Over many tokens, this drift manifests as forgetting.

By contrast, when code tokens remain a persistent part of the training signal, the model is continually reminded to maintain and refine its coding representations. The math tokens co-occurring in training then shape how those coding representations are deployed in mathematical contexts, yielding a form of grounded skill transfer: the model not only remembers how to write code, it learns how to write code that solves math problems. This joint pressure aligns especially well with the program-of-thought evaluation setting used in DeepSeekMath, where responses must take the form of executable programs that produce correct answers.

Viewed through this lens, the mixed recipe can be seen as a representation-preserving regularizer on top of math training. The code distribution acts as an anchor that reduces the distance between the current model and a competent code generator, thereby preventing the drift that would otherwise occur in a math-only second stage. At the same time, the math distribution guides the model to establish the mapping from mathematical descriptions to computational workflows expressed in code. The result is a stable regime that improves the model’s ability to use tools while keeping the underlying tool-use skill intact.

# Practical Guidance within the Paper’s Scope
Within the scope of the ablations reported in DeepSeekMath, the recipes show a clear pattern. If the target application emphasizes program-aided solving of math problems, and one cannot accept a decline in coding capability, then mixing code and math tokens during training is the appropriate choice. This choice is supported by the observed mitigation of catastrophic forgetting and by the improved performance on program-aided evaluations.

If, instead, the priority is maximal performance on mathematical reasoning without tools, the two-stage recipe with code followed by math can be advantageous, as it boosts downstream no-tool math performance after the math stage. However, this comes with the cost of degrading coding capabilities and, by extension, weakening program-aided reasoning relative to a mixed regime. The DeepSeekMath findings thereby present a clear trade-off: mixed training for robust program-aided performance without forgetting, and code-then-math training if the emphasis is on non-tool mathematical reasoning and one is willing to sacrifice coding performance.

# Relation to Broader Findings in DeepSeekMath
The mixed-training insight sits within a larger narrative. The paper shows that high-quality math data mined from web sources at scale can deliver strong mathematical reasoning, even for smaller models, and that starting from a code-pretrained base improves reasoning with and without tools. It also shows that arXiv-only training, despite its common use in math-related pre-training, did not yield notable gains on the evaluated mathematical benchmarks for the settings tested.

Downstream, instruction tuning with chain-of-thought, program-of-thought, and tool-integrated data further strengthens reasoning. Reinforcement learning using GRPO then provides additional improvements, including in program-aided settings, while optimizing memory usage relative to PPO by eliminating the critic and using group-based baselines. These components are complementary: the pre-training mixture shapes the base capabilities, instruction tuning teaches format-specific behaviors, and RL refines the output distribution toward preferred solutions. Within this pipeline, the mixed code-and-math training specifically addresses the foundational requirement for program-aided mathematics without forgetting.

# Limitations and Open Questions
The conclusion favoring mixed code-and-math training for program-aided math without forgetting is based on the presented experimental settings, notably the 1.3B-parameter ablation. The paper explicitly notes that mixing code and math in one stage compromised mathematical reasoning without tool use at this smaller scale, plausibly due to capacity constraints. It remains an open question how these trade-offs evolve with larger models or with different mixtures, schedules, and data balances. The study also highlights that arXiv-only pre-training did not improve the reported benchmarks under tested conditions, while leaving open the possibility that other tasks, data combinations, or model scales could change the outcome.

Finally, although reinforcement learning improved overall performance when applied after instruction tuning, the paper’s analysis suggests that much of the improvement manifests as better robustness of the output distribution rather than fundamental capability gains, raising the question of how best to combine pre-training mixtures, instruction strategies, and RL to jointly improve core skills and output reliability in program-aided mathematical reasoning.

# Conclusion
DeepSeekMath’s ablations provide clear evidence that, if the primary goal is strong program-aided mathematical reasoning without sacrificing coding ability, the most appropriate training recipe among those tested is to mix code and math in a single-stage training process. This mixed regime mitigates catastrophic forgetting of coding while synergistically enhancing the model’s capacity to solve math problems via code. While two-stage code-then-math training benefits no-tool mathematical reasoning, it does so at the expense of coding performance, which undermines program-aided methods. By preserving coding strength and aligning it with mathematical problem-solving, mixed code-and-math training offers a pragmatic and empirically validated path for building models that excel at program-of-thought reasoning without forgetting.
