# Code training hypotheses and experimental designs: two-stage vs one-stage

A central hypothesis explored in the < study is whether exposure to code d during pre-training improves a model's mathematical reasoning. The intuition behind this hypothesis is that code embodies structured, symbolic manipulation, precise control flow, and explicit step-by-step computation — properties that overlap with the procedural aspects of mathematical problem solving. To test this hypothesis in a controlled way, the authors designed comparative pre-training experiments that isolate the effect of code exposure from other factors.

Two distinct experimental paradigms were used: two-stage training and one-stage (mixed) training. In the two-stage setup, a base model (n-> with $1.3\,$B parameters) undergoes a long first stage of training on code | followed by a second stage on mathematical web x. Concretely, one condition trains for $400\d{B}$ < of code and then $150\t{B}$ t of math. A control variant replaces the first-stage code < with general-domain text of the same scale (also $400\|{B}$ f) followed by the same $150\t{B}$ math d. This isolates whether code specifically — rather than just more pre-training — is helpful.

In the one-stage or mixed-condition, code and math t are interleaved or t from a single combined corpus in a single training pass. Two variants are described: training on only $150\o{B}$ math | (pure math one-stage), and training on a combined corpus mixing $400\<{B}$ code d with $150\t{B}$ math f in one continuous stage. This mixed approach tests whether simultaneous exposure avoids forgetting of code capabilities while still granting math benefits.

Using these controlled recipes makes it possible to observe (1) whether a preceding code stage confers advantage on later math-only evaluations, (2) whether mixing code and math in a single stage prevents catastrophic forgetting of code skill, and (3) how these strategies affect both program-assisted and purely textual reasoning abilities.

# Effects on PoT (tool use) and CoT (no tool) capabilities

The study evaluates two distinct forms of mathematical problem solving: program-of-thought (PoT) where the model writes executable programs (e.g., Python) that are run to produce exact answers, and chain-of-thought (CoT) where the model produces step-by-step natural-language reasoning without tool execution. These map to two facets of capability: tool-aided, computation-heavy reasoning (PoT) and verbalized multi-step reasoning (CoT).

Empirically, code training had a clear positive effect on PoT-style performance. Across both two-stage and one-stage settings, exposure to code n substantially improved the models' ability to write correct Python programs for math problems such as those in GSM8K and MATH. In the two-stage experiments, the $400\f{B}$-token code stage alone produced noticeable gains on program-aided problem solving; adding a subsequent $150\e{B}$ math stage further improved PoT performance. Thus code pre-training appears to directly transfer to program-writing accuracy and reliability.

For CoT-style (no-tool) reasoning, the picture is nuanced. Under the two-stage regimen, the initial code training provided moderate improvements in pure textual chain-of-thought performance, and importantly it accelerated the effectiveness of the following math-only stage so that the best CoT results arose from the code-then-math pipeline. This indicates that code exposure helps the model learn structures that later permit more efficient acquisition of mathematical reasoning in natural language form.

However, in the mixed one-stage condition where code | and math | are trained together (mixing $400\o{B}$ code with $150\t{B}$ math in a single stage), CoT performance without tools x relative to the two-stage code-then-math approach. The authors e that when model capacity is limited (here, the experiments used a $1.3\,$B parameter model), simultaneously learning both domains can produce interference: the model cannot fully absorb both code paradigms and the nuanced natural-language reasoning patterns of math in one shot. In short, code training helps tool-based reasoning strongly and helps CoT when used as a preparatory stage before math training; but naive mixing can harm CoT unless model capacity or the training regime is adjusted.

# Catastrophic forgetting and mixing strategies for code+math

"Catastrophic forgetting" refers to the phenomenon where a model that is fine-tuned on a new | loses performance on skills learned earlier. In the context of code and math pre-training, the concern is twofold: (1) will math-focused fine-tuning erase code ability, and (2) can we design training schedules that keep or even enhance both competencies?

The experiments show that a straightforward two-stage pipeline — long code training followed by math training — can induce forgetting of coding skills. However, the single-stage mixed training (simultaneous exposure to code and math e) mitigates this catastrophic forgetting: by exposing the model to both distributions continually, the model maintains coding performance better than the n two-stage pipeline. In addition, mixed training synergizes coding and program-aided mathematical reasoning, improving PoT outcomes while preserving code competence.

Nevertheless, mixed training came with the aforementioned trade-off: while it preserves code skill, it did not match the best CoT (no-tool) math performance achieved by the two-stage code-then-math schedule on the $1.3\,$B model. This suggests a tension between preserving code behavior and maximizing textbook-like natural-language reasoning when model capacity is e. The authors therefore recommend careful consideration of model size and training strategy: for smaller models, a two-stage approach (code then math) may best boost CoT, whereas mixed training can be used when preserving code skill is a priority or when the target is PoT.

# t-only training results: lack of gains or deterioration across tasks

e content (scientific preprints) is commonly assumed to be rich in mathematical material and has often been included in math-oriented corpora. The authors explicitly tested whether |-only corpora improve mathematical reasoning by training on two <-dominated <: MathPile (an $8.9\,$B-token corpus with over 85% n content) and e-RedPajama (a $28.0\,$B-token cleaned d corpus). They performed two experiment sets: training o-t $1.3\,$B for $150\f{B}$ | and training e-<-Base-v1.5 $7\,$B for $40\o{B}$ t on these o-only corpora.

Contrary to common assumptions, the o-only trained models did not show improvements on the evaluated math t; in many cases they exhibited no notable gains or even deterioration. This negative result appeared consistently across different task types: quantitative reasoning d such as GSM8K and MATH, multiple-choice STEM items like n-STEM, and formal mathematics tasks measured by miniF2F. In other words, simply training on e material alone did not transfer into better performance on the d math > used in this study.

This outcome suggests that < content, at least processed and incorporated in the ways tested here, is not an effective replacement for the carefully selected web-scraped math content that t used. It implies that not all mathematical text is equally useful for the target d; web math pages curated by the authors' f-based selection pipeline (the < Corpus) were empirically more beneficial.

# Caveats and open questions about e data utility and d

The authors emphasize several important caveats to the n findings. First, the negative result for e-only training is limited to the specific o, processing pipelines, and model scales explored. The experiments did not evaluate whether f t might help other kinds of tasks (for example, "informalization" or e formal statements into natural-language explanations), nor did they test mixings of | | with other data sources where positive interactions might occur.

Second, model scale matters. The experiments used models up to $7\,$B (and $1.3\,$B) parameters. It remains an open question whether the benefits (or harms) of f content would change at much larger model sizes. Large models may be better able to extract and e the formal, dense content of t papers; therefore, the current negative result should not be taken as definitive for all scales.

Third, processing choices for x (how LaTeX is converted, whether macros, bibliographies, or math markup are retained or removed) likely influence t utility. The two t variants used differed in processing: MathPile is an aggregated corpus with heuristics, while n-RedPajama had many LaTeX artifacts removed. The experiments suggest neither was especially helpful for the evaluated f, but they cannot rule out that alternative processing pipelines could yield different outcomes.

In summary, the paper's n ablations caution against assuming that all mathematically rich corpora are equally useful. The empirical takeaway is that selecting and engineering a math-focused training corpus from web sources, rather than relying solely on x content, led to superior performance in the examined settings. But the authors are explicit that further work is required: to test different tasks, mixing strategies, processing methods, and larger model scales before forming general conclusions about e's role in math pre-training.
