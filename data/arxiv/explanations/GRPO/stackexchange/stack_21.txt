### Does training with tool-integrated data harm "no tool" performance or vice versa?
Question:
The SFT dataset includes chain-of-thought, program-of-thought, and tool-integrated reasoning examples. 
- When evaluating "without tool use," how do you prevent the model from attempting tool calls or producing code? Do prompts explicitly forbid tools, or is a different format used? 
- Did mixing tool-integrated data into SFT degrade pure text CoT performance, or did it transfer positively?
Answer:
Short answer: When evaluating “without tool use” the authors simply prompt and evaluate the model to produce self‑contained text (CoT) solutions rather than tool-invoking/code outputs — i.e., they use CoT-style prompts (no tool templates nor execution pipeline) and disallow program execution. The paper reports no evidence that including tool-integrated training examples harmed pure text CoT performance; if anything, the mixed SFT (CoT + PoT + tool-integrated) together with prior code/math pretraining produced strong CoT results, and RL trained on CoT data further improved CoT performance.

Explanation grounded in the paper
1) How “without tool use” evaluation is done
The paper contrasts two evaluation settings explicitly: “we evaluate models’ ability to generate self-contained text solutions without tool use” and a separate setting “where models are allowed to integrate natural language reasoning and program-based tool use.” For the “without tool use” setting they use few‑shot chain‑of‑thought prompting (CoT). That means evaluation prompts ask the model for step‑by‑step textual reasoning and the model is not put into the tool‑execution/code‑interpreter loop. Practically, this is done by using CoT few‑shot prompts (no program templates, no code execution or tool hooks, and no plugin/CI pipeline that would run code). The paper does not describe any exotic blocking mechanism; it relies on evaluating with different prompt formats and by not running any program execution when measuring answers. They also applied decontamination to ensure no benchmark leakage when assembling training data.

2) Does mixing tool-integrated data into SFT hurt pure text CoT?
The paper’s SFT corpus intentionally contains a mix of CoT, PoT (program‑of‑thought), and tool‑integrated examples (total $\approx 776\text{K}$ examples). DeepSeekMath‑Instruct (trained on that mixed SFT) shows very strong performance under the “tool disallowed” CoT evaluation: it “demonstrates strong performance of step‑by‑step reasoning” and outperforms all open‑source models on MATH in the no‑tool setting (Table references in the paper). Furthermore, the RL stage (GRPO) was run using only CoT‑format instruction‑tuning data (they explicitly say the RL used only chain‑of‑thought format questions from GSM8K and MATH) and produced further improvements on both in‑domain CoT benchmarks (GSM8K, MATH) and out‑of‑domain tasks. That indicates two things: (a) mixing tool examples in SFT did not prevent the model from learning to produce high‑quality textual CoT answers, and (b) CoT‑only RL can further refine CoT behavior even when the underlying SFT contained mixed formats.

Why mixing likely didn’t hurt (intuitive view)
Programmatic and tool‑integrated examples teach highly structured stepwise decomposition, explicit variable manipulation, and precise mapping from problem statement to operations. Those skills are beneficial for producing coherent chain‑of‑thought even when the final answer is pure text. Also the base model was initialized from a code‑trained checkpoint (DeepSeek‑Coder) and the paper shows code pretraining generally helps both program‑aided and pure text mathematical reasoning. So mixed SFT + code‑aware pretraining tends to transfer beneficially to CoT outputs rather than degrade them.

Caveats and practical notes
The paper does not claim a formal ablation isolating “only CoT SFT” versus “mixed SFT” with identical pretraining; they report that their mixed SFT leads to strong no‑tool CoT performance. It’s still possible in other settings that excessive emphasis on tool templates could bias generation toward code-like forms unless the evaluator (prompt) explicitly requests plain text and the execution/PKG pipeline is disabled. So if you want to be strict in your evaluations, use explicit CoT prompts, remove any tool‑invocation templates from the prompt set, and disable code execution at inference time.

Summary
To evaluate “without tools” the authors use CoT prompting and do not execute code or present tool templates; they do not report any degradation of pure text CoT performance after mixing tool‑integrated examples into SFT. The mixed SFT (with PoT/tool examples) plus code‑oriented pretraining seems to transfer positively to CoT reasoning, and RL trained on CoT data further boosts CoT performance.
