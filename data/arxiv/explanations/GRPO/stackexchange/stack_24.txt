### What memory savings does GRPO achieve relative to PPO in practice?
Question:
The paper claims GRPO reduces memory use by removing the critic. 
- On a 7B policy with context length 1024 and \(G=64\), what is the actual memory reduction vs PPO (peak VRAM, activations)? 
- How much of this saving is from removing value head parameters vs not backpropagating through a value network? 
- Does the saving depend strongly on sequence length or batch composition?
Answer:
Short answer: the paper does not publish a single factual VRAM number, but the dominant source of GRPO’s memory savings (relative to a typical PPO setup used for LLMs) is eliminating the extra value model’s activations and backward pass across $G$ sampled rollouts, not the tiny parameter count of a value head. For a $7\text{B}$ policy with context $1024$ and $G=64$ the savings can be large and scale roughly proportional to sequence length and the number of sampled outputs; depending on how the critic was implemented you should expect anywhere from a modest ($\sim 10\text{--}30\%$) to a substantial ($\sim 30\text{--}60\%$ or more) reduction in peak GPU memory. Below I explain why, give a back-of-the-envelope breakdown of the contributors, and point out what to profile in practice.

Why GRPO saves memory (intuitively)
The paper’s GRPO removes the separate critic/value-function model and uses group-mean baselines computed from sampled outputs instead. In RL for LLMs the memory cost comes from a few places: (1) model parameters and optimizer states, (2) activations that must be retained to compute gradients during the backward pass, and (3) any additional buffers needed for sampling, reward computation, and advantage estimation. If you remove a full separate value network (often comparable in size to the policy), you remove both its parameters/optimizer states and, more importantly, all of the activations that would have to be stored for backprop over each sampled output. For typical settings (many sampled outputs per prompt, long contexts) the activation/backprop memory dominates, so removing the critic yields the biggest wins.

Which part of the saving dominates
Removing the value-head parameters (i.e., turning a shared trunk + tiny linear value head into nothing) saves very little memory. A linear value head is usually a tiny fraction of a $7\text{B}$ model’s parameters, so parameter savings alone are negligible.

Not backpropagating through a value network is the big win. If you would have trained a separate value model (or a duplicate policy trunk with a value head), then for every sampled rollout you must run the value network forward and keep activations for backward pass (or store them in checkpointing/ recompute), and you must hold optimizer states and gradients for that model. With $G = 64$ sampled outputs per question, that cost multiplies across samples. GRPO avoids storing/propagating through that entire second-model computation, so the activation + optimizer/GPU buffers saved are the main component.

Back-of-the-envelope / qualitative estimate
The paper gives the configuration you asked about: a $7\text{B}$ policy, max length $1024$, $G = 64$ (they use $64$ samples per question). The authors also emphasize memory reduction by “forego[ing] the critic model.” I will outline two representative critic implementations and the corresponding expected impact; these are order-of-magnitude estimates (you should profile your exact setup to get real numbers).

1) Typical expensive case — separate full-size critic (another $7\text{B}$):
If PPO used an independent $7\text{B}$ value network, that roughly doubles model parameters and optimizer state memory (params + Adam moments). Parameter memory doubling alone could add tens of GB (a $7\text{B}$ model in fp16 is on the order of $13\text{--}15\ \mathrm{GB}$ of parameters; optimizer states for Adam can multiply that by $\sim 2\text{--}3$). But more important is activations: for each sampled output you need activations proportional to (sequence length $L$) $\times$ (hidden state size) $\times$ (bytes) to backprop through the value model. With $G = 64$ sampled outputs per prompt, the activation memory scales roughly as $G \times L \times$ per-token-activation-size. So removing the critic in this scenario can approximately halve (or better) peak VRAM usage — realistic ballpark: $\sim 30\text{--}60\%$ reduction in peak VRAM compared to PPO with a separate full-size critic. The larger the $G$ and $L$, the closer you get to the high end of that range.

2) More common/lightweight case — shared trunk with a small value head:
Many implementations tie the value head to the policy trunk and only add a small linear head. In that case the extra parameter cost is minor, and if training the value requires computing per-token value estimates you still may need to store the trunk activations for the backward pass through the same trunk multiple times (policy updates and value updates). But because the trunk is shared the incremental parameter/optimizer cost is small. Memory saving from removing the critic here is lower — perhaps $\sim 10\text{--}30\%$ reduction — because you still need most of the model’s activations for policy gradient and you may only avoid a relatively small extra backward pass or a small extra head’s optimizer state.

Which memory term scales most with $L$ and $G$
Activation memory required for backprop scales roughly linearly with sequence length $L$ and with the number of sequences you need to keep activations for (which here is proportional to the number of sampled outputs $G$ times batch size). Thus the GRPO saving is roughly proportional to $G \times L$: doubling either $G$ or $L$ roughly doubles the activation cost that a second value network would impose. That’s why the paper’s configuration ($G = 64$, $L = 1024$) is exactly the regime where removing the critic yields big savings.

Dependence on batch composition
Yes — the saving depends strongly on how you compose your batch. If you sample many outputs per prompt (large $G$) and use long contexts (large $L$), the critic’s activation memory is multiplied and the savings from removing it are larger. If instead you use small $G$ (e.g., $G = 4$) or short sequences, the critic becomes less of a memory driver and the savings shrink. Also if you use larger policy batch sizes (more prompts per batch) that multiplies memory for everything and can change where the peak occurs; again the proportional benefit of removing a full separate critic remains larger when per-sample work (i.e., $G\times L$) is large.

Practical takeaways and what to profile
The paper’s GRPO design deliberately removes the critic to reduce memory and compute. To get a concrete number in your setting you should profile peak GPU memory for two local runs: (a) standard PPO with your intended critic implementation (either a full separate value model or a shared trunk + head), and (b) GRPO (no critic). Profile with the exact $G$, $L$, batch size, optimizer/precision (fp16, bf16), and gradient accumulation you intend to use. Key quantities to compare are: peak VRAM, activations stored, and optimizer state size. From the paper’s description, if your PPO would have used a full-size separate value network and you are in the high-$G$, long-context regime (like $G=64$, $L=1024$), you should expect a substantial reduction (tens of percent) in peak VRAM primarily due to avoided activations/backprop for the critic. If your PPO used only a tiny value head on a shared trunk, expect smaller but still meaningful savings because GRPO also avoids extra backward steps and duplicated optimizer buffers.

Closing summary
GRPO’s memory advantage comes almost entirely from not needing to run and backpropagate a value network over $G$ sampled rollouts; the parameter count of a value head is small in comparison. The saving scales roughly linearly with sequence length $L$ and number of samples $G$, and depends on batch size and whether the critic was implemented as a full separate model or a small head. The paper doesn’t give exact VRAM numbers, so for exact peak-VRAM figures in your environment you should benchmark PPO versus GRPO with your precise model, precision, batch, and $G/L$ settings.
