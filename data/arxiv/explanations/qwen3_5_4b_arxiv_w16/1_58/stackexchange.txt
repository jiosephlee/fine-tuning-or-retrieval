\title{Stack Exchange of the Paper: "The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits"}

### Why does adding the value 0 to the ternary weights {-1, 0, 1} allow the representation to reach 1.58 bits instead of just 1 or 2 bits?
Question:
The abstract states that BitNet b1.58 uses ternary weights {-1, 0, 1} and calls this '1.58 bits'. However, in standard information theory, a ternary state (3 levels) would occupy $\log_2(3) \approx 1.585$ bits. But isn't this mathematically just rounding $\log_2(3)$? I understand that the paper refers to it as '1.58', but is there a specific reason to stop at this decimal approximation? If I have a weight of -0.5 which rounds down to -1, does that mean I'm wasting half a bit's worth of information compared to a binary system where I can't represent that intermediate state? Can someone explain if '1.58 bits' is a precise theoretical claim or just a label for the ternary alphabet?
Answer:
The designation "1.58 bits" in BitNet b1.58 is indeed grounded in standard information theory, and it represents the theoretical entropy of a ternary (3-level) symbol system rather than a labeling convention for a binary system or an arbitrary rounding.

The value 1.58 is derived from the logarithm of the size of the alphabet used to represent each weight parameter. In BitNet b1.58, every weight $W_{ij}$ is constrained to the set $\{-1, 0, 1\}$. According to Shannon's information theory, the amount of information $H$ contained in a discrete source with $M$ possible equiprobable outcomes is given by $\log_2(M)$ bits. Since this model uses a ternary alphabet ($M=3$), the maximum information capacity per weight parameter is exactly $\log_2(3)$, which calculates to approximately $1.584962...$ bits. This value explains why the paper refers to the architecture as "1.58 bits"; it is numerically approximating the theoretical limit of information density achieved by using three distinct values instead of just two (binary).

Your intuition regarding intermediate values like $-0.5$ is mathematically sound but misapplied to this specific architectural constraint; adding 0 does not introduce intermediate states like $-0.5$, nor does it waste half a bit. The transition from the original 1-bit design (weights $\{-1, +1\}$) to BitNet b1.58 involves expanding the discrete alphabet from a binary set ($M=2$) containing $\log_2(2)=1$ bit of information to a ternary set ($M=3$). By equipping each parameter with an additional "zero" option, the model gains enough expressive power to effectively utilize 3 distinct states per parameter, thereby matching its information capacity to $\log_2(3)$ bits rather than being limited to 1 bit. This expansion allows the weights to encode richer features—such as the explicit filtering capability mentioned in the abstract which turns off connections entirely via zero—without requiring floating-point precision or higher bit-widths like 3-bit systems ($\log_2(4)=2$).

Therefore, calling the weights "half two" or "almost two" would also be technically accurate in binary terms ($\approx 1.96$ bits for four states including zero), but "1.58 bits" provides a more precise description that aligns directly with entropy calculations ($\log_2(3)$). The paper uses this specific terminology to emphasize that while these are low-bit integers suitable for hardware optimization similar to 1-bit systems, they theoretically offer an information density closer to $16/9$ bits than traditional binary models do, enabling performance parity with 16-bit floats while maintaining integer-only compute operations as described in their design involving rounding and clipping functions.

### How exactly does SORTFLOW's 'in-chip communication' optimize the memory transfer for sparse weights compared to full precision models?
Question:
The paper claims that 1-bit LLMs enable better in-chip communication because they only store weights in SRAM (or on-chip memory) rather than transferring them from DRAM for every operation like full-precision LINEAR layers do. I see the argument that you load sparse tensors once and update them, but in a device like LINEAR which selects one existing weight per column at every step, isn't that still technically accessing weight memory many times (e.g., once per head/token)? How is accessing those weights inherently more expensive in terms of power and latency than accessing dense weights in SRAM? Is it primarily about the elimination of the DRAM bottleneck during initialization versus retrieval?
Answer:
The optimization of in-chip communication in the 1.58-bit LLM architecture described by BitNet b1.58 addresses the fundamental memory-hierarchy bottleneck prevalent in standard full-precision models, specifically the cost of moving weights between DRAM (system memory) and on-chip SRAM (SRAM). In a conventional full-precision ($\text{FP16}$) model, the weights are massive in size (e.g., a 70B parameter model requires roughly 112 GB of floating-point memory), which exceeds the capacity of typical SRAM found on accelerators like GPUs. Consequently, during inference, the system must frequently transfer the entire weight matrix from slow, high-volume but low-bandwidth DRAM into fast, low-volume SRAM for every forward pass. This "weight loading" process dominates latency because it requires reading large datasets repeatedly across wide data buses.

In contrast, the 1.58-bit LLM drastically reduces the weight memory footprint. By quantizing all weights to ternary values $\{-1, 0, 1\}$ as defined by the $ \widetilde{W} = \mathrm{RoundClip}(\frac{W}{\gamma + \epsilon}, -1, 1) $ quantization function in the paper, a parameter that would previously require 2 or more bits is stored in at most 1.58 bits. This reduction lowers the total parameter size by an order of magnitude or more. Critically for hardware implementation, this reduction enables a specific architectural choice: storing these compressed weights directly within SRAM rather than fetching them from DRAM prior to computation. As stated in the abstract and Section I, "The process of transferring model parameters from DRAM to the memory of an on-chip accelerator... can be expensive," whereas with 1-bit models, "This can significantly reduce the cost and time of loading weights from DRAM."

Regarding your specific concern about sparse tensor access patterns similar to LINEAR layers where a single weight is selected per token per head: while both architectures involve selecting specific elements during inference, the cost difference lies entirely in *where* those elements reside. In a standard LINEAR layer with $\text{FP16}$ weights selected dynamically during training or inference (often called sparse matrix-vector multiplication), those weights still exist as large arrays that likely reside in off-chip memory or require serial access through bandwidth-constrained channels if spread across large tile banks. Even if pre-loaded into SRAM, searching or managing such sparseensembles can still incur overhead related to metadata management and non-coalesced memory accesses if not perfectly optimized beforehand.

However, BitNet b1.58 shifts this paradigm by simplifying the storage abstraction itself. Because every weight is structurally constrained to $\{-1, 0, 1\}$, it can be efficiently packed into bit-aligned block storage structures like "bit-level sparseness mapping" or simple concatenated bit-planes within high-bandwidth SRAM fabrics. The paper notes that this enables "almost no multiplication operations," relying instead on integer additions which are inherently cheaper and faster to execute on dedicated logic units when inputs are binary/ternary. This allows hardware designers to view a block of bits as a dense conceptual matrix that can be streamed contiguously through SRAM ports without decompressing or shuffling data between memory levels during the critical dot-product phases (the equivalent of accessing "existing weights"). Furthermore, because GitNet b1.58 removes biases and uses simpler lateral components like RMSNorm as described in Section II ("LLaMA-alike Components"), it reduces constant overheads that force stateful management of auxiliary data structures that might otherwise necessitate additional DRAM fetches for bias vectors or scale factors that float-point models handle frequently with high precision updates. Thus, the optimization is not merely about retrieval frequency but about enabling a fundamental shift where compliance with ternary constraints allows weights to reside permanently on-chip in SRAM structures optimized for bit-parallelism, eliminating the need for repetitive DRAM-server interactions inherent in higher-precision matrix operations on general-purpose accelerators.

### What prevents directly encoding floating-point values across {-2, -1, 0, 1, 2} into ZNIST's ternary latent space without massive loss of expressivity?
Question:
The intuition given is that by encoding floating-point vectors into SIGN-Magnitude latent space and then converting those vectors back via ZNIST to ternary vectors with {-2,-1,0,1,2}, we only incur loss on floating-point addition during latent processing. But why doesn't this approach simply work better with BINARY latent space (0 or 1 per dimension per token) instead of SIGN-Magnitude? If SIGN-Magnitude adds extra dimensions compared to BINARY (which only needs one bit per feature + sign), shouldn't SPECIFIC TO TOKEN activation loss be significantly lower with BINARY? Why is ZNIST specifically designed around SIGN-Magnitude here?
Answer:
The primary reason \text{sign-magnitude} is preferred in ZNIST for latent processing over pure binary, despite the intuition that binary requires fewer dimensions, lies in the specific mechanics of gradient propagation and how activation values are reconstructed from ternary densifying codes. When recovering primitive values from ternary residues, \text{sign-magnitude} provides a more stable and lossless inference of the original signal compared to the ambiguity that can arise in pure binary representations for unattended features.

\text{Sign-magnitude} is critical because it explicitly models the directionality of changes in activation space. The ZNIST design leverages the fact that most training inputs have a mean close to zero, allowing latent vectors to most frequently occupy regions maintainable by dense three-element signatures from sparse ternary residue values. In this regime, \text{sign-magnitude} serves as a direct compression without negative-bin coefficients, directly dictating precision performance without instigating spurious \text{\-(zero-point)} latency during training. In contrast, binary encoding introduces significant representation variance: while a unary-heavy density allows some values to be propagated via false-length re-computation without topology collapses, binary resolution often lacks the explicit directional head required for greedy search optimization without introducing significant representational variance or ambiguity in gradient updates.

Furthermore, quantization noise introduced by \text{sign-magnitude} can be effectively managed through count-based smoothing at inference time, which ensures that rare inputs with complex features do not disproportionately degrade model performance. This aligns with the paper's finding that maintaining low bit widths requires careful handling of the activation manifold; by allowing zeros (via ternary densifying), BitNet b1.58 achieves greater mobility for information in feature space than binary alone could provide within similar constraints. The explicit inclusion of zero in ternary weights also facilitates better feature filtering compared to binary-only systems, though this remains a key architectural detail distinct from the core latent space decision favoring \text{sign-magnitude} for its balance of sparsity and gradient reliability during backpropagation through dense blocks. Ultimately, while binary offers theoretical dimension reduction for fixed features, \text{sign-magnitude} preserves the directional integrity necessary for maintaining perplexity and task accuracy across scale sizes as described in the results section of the paper.

### Is an effective channel width of 'less than one Qubit' physically possible for hardware design based on the current state of charge control electronics?
Question:
The paper mentions achieving this efficiency with an effective channel width much lower than one Qubit per tensor gate element given modern transistor technology developments like Simple FinFETs. I am struggling to reconcile this with energy scaling relations: hasn't single-electron tunneling current already become dominant in very small transistors (hence the low energy vs bandwidth trade-off)? If we are trying to reduce channel widths further below specific dimensions where single-electron effects dominate or introduce significant variability due to device-to-device fluctuations in charge storage control circuits, would noise and variability—not energy savings—become the limiting factor instead? How are trade-offs being managed when approaching sub-unit-cell geometries for weight storage?
Answer:
Based on the provided paper, the discrepancy between high energy efficiency claims and the limitations of single-electron transistor physics arises from a misunderstanding of what "effective channel width" means in this context. The paper does **not** claim that the channel physical width of a transistor shrinks below the dimension required for single-electron tunneling.

Instead, the "effective channel width" concept refers to **logical sparsity and value density** within the data representation, not the lithographic gate width of the silicon devices. The paper explains that by quantizing every parameter to a ternary set $\{-1, 0, 1\}$ (requiring only $1.58$ bits), the model drastically reduces the capacity required to store weights in on-chip memory (SRAM) and reduces the number of active bits during computation. This reduction leads to computational savings because many operations involve adding zeros or simple integer additions rather than precise floating-point multiplications.

Crucially, regarding your concern about single-electron tunneling and noise: while it is true that as transistors physically shrink, variability and quantum effects increase, modern semiconductor manufacturing allows for significantly larger physical gate widths than those limited by single-electron effects while still maintaining nanometer-scale feature sizes for process nodes (e.g., $7$nm). The energy savings described in Figure \ref{fig:energy} ($71.4$ times reduction in arithmetic energy) are attributed to algorithmic efficiency—specifically replacing expensive FP16 multiplications with cheaper INT8 additions—rather than leveraging quantum mechanical states in the transistor itself. The trade-offs between bandwidth savings and noise are managed because silicon transistors operate far above the regime where single-electron tunneling dominates logical errors; they operate in a classical charge regime where variations can be averaged out or control compensated, allowing for stable logic switching even with highly compressed data representations. Thus, hardware designers can utilize standard advanced-node transistors effectively without needing to resort to exotic nanomaterials or counteract quantum fluctuations specifically for data compression; the benefits come from representing less information per unit of data volume within these stable devices.

Answer:
The question regarding why non-linear processing is constrained during write-back (training) rather than handled entirely at inference time stems from a fundamental misunderstanding of what post-training quantization aims to achieve and how the provided paper, "The Era of 1-bit LLMs," defines its own architecture.

First, it is crucial to clarify that the paper describes **BitNet b1.58** as a model trained from scratch with specific low-precision constraints, not merely a post-training quantized version of a full-precision model like SmoothQuant. The paper states in Section 2 that the model has "1.58-bit weights and 8-bit activations" and explicitly mentions using an `absmean` quantization function during training to constrain weights to $\{-1, 0, +1\}$. Because the weights are hard-constrained to ternary values $\{-1, 0, +1\}$ throughout training, the model's property function does not have access to finer-grained gradients or continuous values; it must learn representations directly in this discrete manifold. Consequently, the "non-linear processing" (specifically activations passed through functions like SwiGLU or RMSNorm) cannot be arbitrarily constrained later because the underlying weight space that shapes those activations was already frozen into discrete steps during training. If one were to rely solely on inference-time clipping for non-linearities without adjusting the training process to align with such constraints, the model would fail because its learned parameters do not interact correctly with cutoff activation values.

Secondly, regarding your mention of SMOOTQUANT: SMOOTQUANT is a technique designed for **post-training** quantization where the model is originally trained with full precision (FP32/FP16), and rounding errors introduced during weight scaling are mitigated by smoothing the non-linear activation functions *during* the quantization phase (often involving dynamic gradients or specific loss terms) so that gradients can still flow effectively through the smoothed operations. However, BitNet b1.58 operates under a different paradigm; it is an architecture designed where weights are permanently ternary $\{-1, 0, +1\}$. In this specific design, the inclusion of a $0$ value allows for explicit feature filtering, which changes how information flows compared to standard binary networks without zero nodes.

The paper explicitly details that \text{BitNet b1.58} reduces activations from 16 bits down to **8 bits** during both training and inference. This choice is strategic: reducing activations after they leave a layer (via write-back) allows them to be quantized anywhere in the range $[-Q_b, Q_b]$ without needing zero-point adjustment complexities often found when clamping activations *within* non-linear layers at epoch end or test time. By quantizing activations outside specific non-linear functions (i.e., not strictly inside every individual activation-dependent layer operation in a way that would destroy gradient flow), the model avoids performance degradation caused by biases in flattened functions or specific thresholds that would arise if every single non-linearity were tied directly to an extreme quantization floor/ceiling.

Finally, your concern about handling constraints entirely at inference time ignores two key factors highlighted in this work:
1.  **Hardware Trade-offs**: The goal of BitNet b1.58 is drastic reduction in energy consumption and memory usage by replacing FP32/BF16 operations with simple integer addition and negligible multiplication logic ($O(1)$). If complex smoothing operations or adaptive thresholds were required at inference time based on activation magnitudes (as might be necessary if trainable smoothing were omitted), it would undo the computational efficiency gains promised by removing multiplications from \textit{nn.Linear}.
2.  **Training Paradigm Shift**: As noted in Section 2 ("All Large Language Models are in 1.58 Bits"), this work posits that we can train LLMs fundamentally differently—using ternary weights—to match full-precision performance on standard tasks while offering massive energy savings over billions of tokens trained on datasets like RedPajama. Relying on heuristic smoothing at inference only could match performance for small models but fails at scale because it does not change how data actually flows through the network structure during its development cycle or deployment efficiency compared to native support for long sequences via reduced activation precision ($8$ vs $16$ bits).

In summary, non-linearity handling is intrinsically linked to how BitNet b1.58 was trained with ternary weights; attempting to decouple these into simple post-training inference clips would break the equivalence between 1.58-bit and full-precision tasks observed in their experiments because the signal propagation path depends on those specific structural constraints being present from training onwards rather than being retrofitted later for computational shortcuts only achievable at much higher energy costs or batch sizes not supported by typical deployment scenarios described in Section 3 ("Native Support of Long Sequence").
