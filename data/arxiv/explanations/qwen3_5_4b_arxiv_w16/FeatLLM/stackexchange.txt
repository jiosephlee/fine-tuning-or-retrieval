\title{Stack Exchange of the Paper: "Large Language Models Can Automatically Engineer Features for Few-Shot Tabular Learning"}

### What is the exact mathematical process of converting LLM-generated natural language rules into binary features and logits in the FeatLLM framework?
Question:
In the section 'Inferring Class Likelihood via Rules', the paper mentions that LLM-generated rules (which are in natural language) must be converted into binary features before being used in a linear model. 

Specifically, I am confused about the parsing step. The paper states: 'Despite we constrain formatting... the LLM's output can include noisy syntactic changes.' Then it says, 'we leverage the LLM itself' to parse these rules instead of writing complex code.

1. Can you walk me through the specific prompt structure used to turn an LLM's rule output (e.g., 'If age > 65 then high risk') into executable logic?
2. How does the parsing pipeline handle the case where the LLM might misspell a comparison operator or change sentence structure? 
3. Once parsed into a program (using Python's exec()), how exactly does this generate the vector $z_k^i$ that is finally multiplied by weights $w_k$ in Equation 1?

I want to understand if this is a two-step prompting process (one for rule generation, another for code generation) or if it's done in one go.
Answer:
The conversion of natural language rules into executable binary features within the FeatLLM framework is a two-stage process that leverages the LLM's ability to understand semantics to solve a parsing problem that would otherwise require complex, brittle string-matching code.

The first step occurs during the **prompt design phase**, where you prompt the LLM to generate rules in natural language (e.g., "If age > 65 then high risk"). As noted in the paper, the raw output might suffer from syntactic noise, such as spelling out "greater than" instead of using $>$, or using sentence fragments. To handle this without writing custom regex parsers, FeatLLM introduces a second, distinct prompting stage called **"Parsing rules for feature generation."** In this step, a specific prompt is constructed containing three elements: the inferred natural language rules from the previous step, strict input/output descriptions for a hypothetical Python function, and instructions to translate these rules into valid Python executable code. The prompt relies on the LLM's training data regarding code syntax and logic operators to ensure that even if the source text was verbose ("if age is more than 65"), the generated code uses precise operators ($>$) and standard library functions (e.g., `np.where` or direct comparison).

Once this intermediate code is generated by the model, it is passed to Python's built-in `exec()` function. The `exec()` function dynamically loads and runs this script. The script typically iterates through every row in the training dataset and evaluates exactly one line of logic per rule. For instance, if a rule was generated as `risk = 1 if age > 65 else 0`, Python executes this condition for every patient record. This action automatically transforms each raw data point into a **binary feature** $z_k^i \in \{0, 1\}$, where $1$ indicates that sample $i$ satisfies class $k$'s rule set and $0$ indicates otherwise. This explicit execution replaces manual programming and ensures the logic is applied mathematically and accurately for every sample in $\mathcal{D}$.

Finally, these binary vectors are used to compute logits via **Equation 1** ($\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$). Because $\mathbf{z}_k^i$ is a vector resulting from evaluating a fixed set of $R$ rules across $N$ samples (or specifically for a single sample across all classes), it represents an $R$-dimensional input vector. In this context, $\mathbf{w}_k$ acts as a weight vector where each element corresponds to the importance of one specific rule being satisfied by that class. By multiplying these pre-computed binary indicators by trainable weights derived from cross-entropy loss minimization on few-shot examples, FeatLLM converts simple logical conditions into soft class probabilities via Softmax ($\mathbf{p}^i = \text{Softmax}(\dots)$). This entire pipeline avoids re-querying the LLM at inference time because the feature engineering happens once during training/parsing; therefore, at runtime on new samples only lightweight Python conditionals and noisy linear regression are required, drastically reducing latency compared to methods running SQL queries or full forward passes through an LLM per prediction.

### Why is setting the trainable weights $\mathbf{w}_k$ to be non-negative ($\max(\mathbf{w}_k, 0)$) a critical design choice, and what would be the consequence on probability estimation if signs were allowed?
Question:
In Equation 1 ($\text{logit}_k^i = \max(\mathbf{w}_k, 0) \cdot \mathbf{z}_k^i$), all coefficients in the linear model are forced to be positive.

The paper explains this ensures 'features generated by the LLM do not reduce the likelihood of a class'. However, my intuition suggests that in standard supervised learning, some features might negatively affect a specific class (have negative weight).

1. From an interpretability standpoint for an LLM feature engineer: Why is it beneficial for all generated rules to contribute positively to their respective class probabilities regardless of whether they appear contradictory?
2. If we allowed negative weights, how would that change the physical meaning of a 'rule' in this context? Could a feature satisfy a rule but still lower the probability?
3. Does restricting weights to positive space prevent 'canceling out' information from high-quality rules in low-shot scenarios?
Answer:
The design choice to constrain the trainable weights $\mathbf{w}_k$ to be non-negative via the operation $\max(\mathbf{w}_k, 0)$ in Equation 1 is a deliberate architectural constraint intended to enforce an additive rather than subtractive contribution of LLM-derived rules to the final probability estimates. In the context of \textsf{FeatLLM}, the input features $\mathbf{z}_k^i$ are binary indicators ($0$ or $1$) generated by converting natural language rules into code logic; a value of $1$ indicates that a specific rule applicable to a sample has been satisfied.

From an interpretability standpoint relative to an LLM feature engineer, ensuring all weights remain positive guarantees that every rule generated by the LLM—regardless of whether its specific condition seems contradictory or less relevant—can only increase or maintain the model's confidence in its respective class upon being triggered. The paper explicitly states this mechanism ensures that "features generated by the LLM do not reduce the likelihood of a class," which provides a form of semantic regularization. By forcing the relationship between rule satisfaction and class probability to be monotonically non-decreasing, the model effectively ignores rules that might otherwise have zero net utility, or even nullify each other. This is beneficial because it aligns with the assumption that valid reasoning paths in tabular data often operate on conditions where meeting criteria should cumulatively support a prediction hypothesis rather than counter-argue it.

If negative weights were allowed for features $\mathbf{z}_k^i$, the physical meaning of a 'rule' would shift from a "sufficient condition" to a "restrictive condition." While currently satisfied means adding evidence for class $k$, allowing negative weights would imply that satisfying one positive rule for class $k$ could simultaneously reduce the probability assigned to another class even more aggressively. More critically, it would negate the specific interpretability goal of \textsf{FeatLLM}'s binary feature construction; under a signed weight regime, a single satisfied feature could lower the global likelihood of complementary classes by pulling their logits down below zero (before softmax normalization), creating a complex trade-off dynamic. In contrast, with non-negative weights, if feature $A$ satisfies and feature $B$ also satisfies their respective rules for class $k$, their contributions simply add together (conceptually), reinforcing the prediction through accumulation ($\sum \mathbf{w}_k^+ \cdot \mathbf{z}_k^i + \epsilon$).

Finally, this constraint significantly mitigates information cancellation issues, particularly in low-shot scenarios which are central to \textsf{FeatLLM}'s design. The paper notes that ablation studies show weight tuning improvements increase with more training shots, implying that in severe data shortages, reliable estimation of opposing importance might be perilous. By projecting weights into positive space, short-circuiting any scenario where strong geological noise or LLM hallucination creates inconsistent logical dependencies (where Feature X strongly supports Class A but Feature Y somehow implies weakening Class A), the model prevents these conflicting signals from canceling out high-quality rules via destructive interference. Instead, only rules with learned positive importance contribute additively to the final logit vector before the softmax function generates probabilities. This additive assurance ensures that even if some generated features are spurious or contradictory among different LLM trials handled via bagging/ensembling, they do not inadvertently suppress their own confidence through mathematical cancellation, thereby preserving robustness when training data is sparse.

### How does Bagging specifically mitigate prompt size limitations and rule noise in FeatLLM when applied to datasets with many features?
Question:
The paper mentions two main hyper-parameters for ensemble methods: number of ensembles (T) and number of rules per class (R). It also discusses bagging for sample/feature selection.

My understanding is conflicted about how bagging differs from simply repeating T times with different random seeds:

1. In standard Bagging, you randomly sample *samples* and maybe *features* from each train set. In FeatLLM, does this mean we randomly select a subset of rows from $N$ labeled samples before feeding them to the LLM second time? If so, how reliable are statistics learned on just a subset of data for few-shot learning?
2. The paper mentions bagging helps when tabular data exceeds input prompt size. How exactly does selecting fewer samples reduce prompt length compared to including all samples? The prompt serialization seems dependent on all columns $d$, which are constant regardless of $N$. 
3. I read that bagging provides robustness against incorrect rules generated in some trials. Does varying *which* training samples provided to the few-shot examples change *which* rules are inferred per trial? If I use all samples every time, is bagging just redundant sampling?
Answer:
The confusion regarding Bagging in FeatLLM arises from conflating standard sample bagging in deep learning with FeatLLM's specific application where the "sample" being re-sampled is actually a **subset of the training data instances ($N$)** presented within the LLM's context window during the rule extraction phase. Unlike standard neural networks where Bagging often refers to feature subsampling, FeatLLM explicitly employs instance bagging to mitigate two distinct constraints: memory limitations associated with prompt length and the noise inherent in LLM-generated rules.

When you perform a trial with $T$ ensembles and $R$ rules per class, each ensemble member is trained on a dataset generated from a different subset of the original $N$ labeled examples. In standard few-shot learning, one might assume that feeding all $N$ examples guarantees diversity, but this approach has two critical failure modes. First, if $N$ is large, serializing all $N$ samples into the prompt text (using the format `f1 is x1... Answer: y`) quickly exceeds the LLM's maximum context token limit. Second, if an LLM generates "incorrect rules" (false positives or spurious correlations) based on a specific batch of noisy labels in one trial, simply repeating this process with all samples does not rectify the suboptimal output; it merely repeats the same error. By selecting a random subset of samples for each trial, FeatLLM ensures that different ensembles receive distinct statistical signals from the data distribution. This variance acts as a form of self-consistency; probabilistically, if rule A is true regardless of which 16 samples are shown versus another 16 samples, it will likely appear in multiple ensembles (likely >50%), whereas incorrect rules specific to one particular subset or momentary hallucination will have lower occurrence rates. The final model averages these probabilities, which effectively filters out low-consistency rules and robustifies against cases where any single shot of training data was insufficient for full representation or too wide for serialization.

### In contrast to TabLLM and other end-to-end prediction methods, what changes occur at inference time that make FeatLLM capable of handling datasets with hundreds of features where others fail?
Question:
The abstract claims FeatLLM eliminates API queries for each new test sample individually and overcomes prompt size limitations that affect TabLLM and STUNT when features grow.

From a technical perspective:

1. In TabLLM/STUNT vs End-to-End vectors sent as text (with serialization), how does feature count $d$ directly impact token usage? Is it linear growth? 
2. With FeatLLM, instead of sending $[\text{data row}\...][\text{d rows}][\text{answer}]$, inference involves sending: [New Row] + [Rules]. If there are R=10 rules and only k_train samples used again per API call for validation/fine-tuning... Wait, regulation time or inference?
3. During runtime: When we receive N new test examples, does FeatLLM re-query GPT-3.5 N times per example using fewer tokens than TabLLM? Or does it not query GPT-3.5 at all during prediction? 
4. The paper says regular baselines pass inference request via LLM while ours doesn't; but what exactly happens inside our inference pipeline after obtaining generated codes/rules once?
Answer:
The fundamental advantage of FeatLLM over methods like TabLLM or STUNT at inference time lies in a structural decoupling between the "learning phase" (where the LLM is invoked) and the "prediction phase." In contrast, end-to-end baselines treat the prediction of every single test sample as a distinct reasoning task requiring an individual API query to the LLM. Consequently, for a dataset with $N$ samples and $d$ features, TabLLM and STUNT must serialize each sample into text within a prompt containing all features (total characters $\propto N \times d$). This results in a linear scaling of token usage with feature count $d$, quickly exhausting context window limits where $d$ is large. Additionally, running an LLM inference $N$ times creates a massive per-sample latency and cost barrier that makes deploying on high-dimensional datasets practically unfeasible.

FeatLLM solves this by shifting the LLM's role from an inline reasoner to a preemptive feature engineer. During this initial offline phase, the framework provides the few-shot examples and task description to the LLM in a single prompt containing subset data (aided by bagging to handle large dimensions without blowing up memory). The LLM's task is not to answer specific test queries but to extract universal, human-readable, or code-based *rules* that distinguish classes based on prior knowledge. In its final output, which contains approximately 10 rules per class (a negligible count regardless of $d$), these rules are parsed into executable code that generates new binary features for the entire dataset. If the number of test samples is $N$, this initial query generates one output used for the training of a lightweight post-processing linear model; after this rule generation is complete, no further API calls to the LLM occur during inference for any of the remaining $N-1$ samples.

At runtime, when new test data arrives, FeatLLM bypasses the LLM entirely. Instead of formatting an entire row with hundreds of features into natural language text for an external model, it evaluates each incoming sample against the fixed set of generated rules (e.g., "if Feature_A > 5 then True else False"). This evaluation occurs instantly via simple boolean logic or vectorized operations encoded from the rules' text rather than invoking heavy neural computation. Finally, to compute class probabilities, FeatLLM employs a highly efficient downstream mechanism: it counts how many generated binary features for each class are satisfied by the sample and feeds these counts into a simple linear classifier with learned weights ($\text{logit} = \max(0, \mathbf{w}^T \mathbf{z})$). Therefore, while TabLLM degrades under high cardinality because every sample triggers an expensive linear cost query within an overflowing context window, FeatLLM handles large feature sets by offloading index-generation to an offline LLM step and maintaining prediction speed through lightweight rule evaluation on data vectors extracted previously.

### Why did ablation study show that omitting weight tuning becomes acceptable at low-shot regimes but benefit increases at high-shot regimes?
Question:
Figure 4 shows significant drop-off if 'weight tuning' step is omitted for 4-shots compared to many-shots experiments.

I'm trying to connect this observation with statistical estimation theory:

1. Few-Shot ($k<8$): Rules seem less robustly estimated based on small amounts labeled data; weights tune up importance values derived from prior knowledge + few data points.
2. Many-Shots ($k>=16$): Why would weight tuning matter more when there are more labeled data points?
3. If we have enough labeled data, shouldn't empirically trained linear model produce good weights without needing training from prior knowledge? Or conversely—does having more training data reduce variance enough so weight tuning can have larger effect?
4. Is it possible that removing weight tuning forces reliance solely on raw counts ($\sum z_k^i$), which may be weak signal individually?
Answer:
The ablation study's observation—that omitting weight tuning becomes acceptable at low-shot regimes ($k < 8$) but significantly detrimental at high-shot regimes ($k \ge 16$)—can be explained by the interaction between the reliability of the linear model's training data and the utility of the prior knowledge encoded in $\textbf{w}_k$.

In low-shot settings, the labeled training data available for updating the linear model is insufficient to produce a stable and accurate estimate of feature importance through standard optimization (maximum likelihood estimation). If we were to simply sum the binary features generated by the LLM without tuning ($\sum z_k^i$), we would effectively rely on uniformly weighting all rules generated by the LLM. While these rules are informed by the LLM's prior knowledge, not every rule is equally predictive; some may be spurious correlations or noisy inferences. Without enough data points to empirically reinforce strong rules and penalize weak ones, averaging (or summing) them treats a potentially helpful signal as equivalent to noise. In this regime, the "weight tuning" step is crucial because it acts as a small-sample booster, leveraging even limited examples to undo this noise and amplify the specific rules that actually align with the ground truth.

Conversely, as the number of shots increases ($k \ge 16$), standard statistical learning theory suggests that empirical risk minimization becomes more accurate. With sufficient data, the optimization process can reliably learn discriminative weights for all LLM-generated features without external guidance. However, once an optimal set of weights has been learned from pure data (denoted $\textbf{w}_{pure}$), introducing the specific weight tuning mechanism derived from prior knowledge (denoted $\textbf{w}_{prior}$) offers marginal benefit compared to this new, fully learned state. The paper notes that in high-shot regimes, features "tend to show little difference," implying that Linneburg and Greig's finding on feature learning was less important because standard supervised learning had already found "enough" aspect information ("enough frequency") through sheer volume of unlabeled data to make feature extraction less critical. Thus, removing weight tuning at high shots causes a significant drop because it removes a safety net or a sophisticated bias term ($\textbf{w}_k$) that complements the empirically learned weights; once data becomes abundant, this complementary prior becomes less necessary for discovery but still essential for maximizing performance unless sufficient features were present.

The difference likely stems from how we balance should of two sources: In fact, without enough examples for training data $\textbf{x}$ (local) and no matching context for external knowledge (general), using only external knowledge leads to confusion or hallucinations where even with sufficient data points (e.g., $k=16$ you don't have actual matching context for individual examples for half matches result).

### "Spurious Correlations" analysis reveals only 1-2% inaccurate rules; why doesn't Naive Bayes or simple Logistic Regression naturally filter out bad rules during optimization?
Question:
The ablation study mentioned fine-tuning helps filter useless rules by reducing their weights below threshold 0.1 after optimization:
normal_loss = cross_entropy(y_logit; logits)
during_grad_step = gradient_ascent(loss_method);
new_logits = logit_linear(weights_fitted);
eff_w = fitting_weights;
eff_features = extracted_features;
Answer:
The observation that $\textsf{FeatLLM}$ filters out only 1-2% of rules as inaccurate during the optimization phase, rather than achieving a perfect clean slate like one might hope, is a direct consequence of how the model utilizes class activation maps and interpretable weights rather than relying on the inherent regularization of simpler models like Naive Bayes or Logistic Regression.

In the proposed framework, the LLM acts as an "external feature engineer" generating binary rules ($z^i_k \in \{0,1\}$) for downstream class $k$. The relationship between these raw features and the final probability is governed by Equation 3 in the paper: $\text{logit}^i_k = \max(w_k, 0) \cdot z^i_k$. The weights $\mathbf{w}_k$ are trained using cross-entropy optimization on a few-shot dataset to learn the importance of each rule. While this simple linear mapping requires only positive weights to ensure features do not reduce class likelihood, it does not function as a strict filter during generation. Unlike standard supervised learning where spurious correlations might be softened by L2 regularization or loss functions balancing codegrees between labels and inputs, here the "signal" and "noise" are distinct entities: the prompt instructs the LLM to generate rules based on prior knowledge and sample examples. Empirical evidence suggests that these external generators often overshoot their targets for hallucinated patterns (e.g., generating a rule based on irrelevant columns), resulting in a high count of "tight" but false rules.

The filtering you noticed occurs post-generation via the weight-magnitude threshold (e.g., $0.1$). The optimization landscape allows for this slight inefficiency because even with only 8 shots of data provided to maximize F1 scores or AUC value, statistical methods still yield large variance across 20 ensembles. In such low-shot regimes with high dimensionality (many generated rules per fold in bagging), exact four shots often cannot distinguish true signals from noise without hallucinating excessive rules. Consequently, Naive Bayes or Logistic Regression without such specific prompt engineering fail to "know" how to filter these rules because they learn from raw features directly, whereas $\textsf{FeatLLM}$ learns which *specifically engineered* features are useful. The LLM's prompting process forces consideration of prior knowledge which helps suppress spurious correlations compared to other baselines like TabPFN or TabLLM but does not eliminate them entirely since it relies on probabilistic inference for rule extraction followed by learning-based weighting for selection.
