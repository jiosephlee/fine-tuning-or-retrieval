# Hiding Softmax in the Output: The 2-Staged Efficiency Hack

The Transformer architecture has become the backbone of modern artificial intelligence, driving breakthroughs from natural language processing to multimodal analysis. However, as models scale to handle longer contexts and larger datasets, the attention mechanism—inherent in Transformers—becomes a computational bottleneck. Standard attention scales quadratically with sequence length, and even optimized implementations like FlashAttention-2 struggle to utilize the full potential of modern GPUs like the NVIDIA H100, often achieving only 35\% utilization. This limitation stems not just from algorithmic design but from fundamental mismatches between software logic and hardware execution capabilities. Newer architectures, particularly the Hopper GPU family, introduce capabilities that were previously underutilized, specifically the asynchronous nature of Tensor Cores and dedicated memory units, alongside emerging low-precision formats like FP8. \textsc{FlashAttention-3}, a recent advancement in attention optimization, leverages these hardware features to push performance boundaries significantly higher than its predecessors.

The core challenge addressed by \textsc{FlashAttention-3} lies in the disparity between the throughput speeds of different mathematical operations within the attention kernel. Modern GPUs excel at matrix multiplication but struggle with non-matmul operations such as exponentials required for calculating softmax probabilities. In a standard并行ized implementation following a synchronous model, these operations must execute sequentially or wait for data dependencies to resolve. Consider an attention pass over a sequence block of length $N$. The computation involves first calculating similarity scores via $\mathbf{S} = \alpha\mathbf{Q}\mathbf{K}^\top$, then applying row-wise softmax to obtain weights $\mathbf{P} = \mathrm{softmax}(\mathbf{S})$, and finally computing the output $\mathbf{O} = \mathbf{P}\mathbf{V}$. Within this inner loop, calculating $\mathbf{S}$ (a Simple GEMM) is extremely fast, followed immediately by adding those results to accumulators for $\mathbf{O}$ (Re-scaling GEMM). Between these matrix multiplications sits the softmax operation on the scores $\mathbf{S}$ just computed. Because hardware accelerators have specialized units where matmul throughput can be nearly 100 times faster than units handling exponentials and logarithms, waiting for softmax to finish before starting the next matmul cycle creates massive idle time on Tensor Cores.

\textsc{FlashAttention-3} resolves this bottleneck by abandoning strict sequential dependency enforcement in favor of producer-consumer asynchrony and warp-specialization techniques specific to the Hopper GPU execution model. The architecture supports dividing workgroups into "producers" that handle data movement via Tensor Memory Accelerators (TMA) and "consumers" that perform computation via Tensor Cores (WGMMA). By splitting threads into distinct warps based on their role, designers can hide latency during data loading while computation proceeds independently on other data units on the chip. This setup allows for a clever pipelining strategy where one warpgroup executes its softmax calculations while another simultaneous warpgroup computes its upcoming matrix multiplications for subsequent blocks of keys and values.

This approach transforms how software pipelines interleave standard CUDA kernels with hardware-specific GEMM instructions. In traditional designs, a warp block would complete its entire sequence calculation—computing scores for $j$ blocks of keys ($\mathbf{K}_0\dots\mathbf{K}_{j-1}$), opening them up so softmax runs across all scores at once before moving to output multiplication. While efficient logically correct in pure software code, this planbook strategy misses out on parallel opportunities because intermediate results are serialized across different arithmetic types. \textsc{FlashAttention-3} instead adopts a staggered 2-stage pipeline within a single warpgroup's context window. As outlined in their proposed algorithmic framework \cref{alg:flash3_wgmma}, each iteration $j$ produces partial scores $\mathbf{S}_{cur}$ which are immediately processed locally rather than waiting for global summation before being decomposed back into iterations $j+1$ through $j_{total}-1$. The key insight lies in overlapping instruction queues: while one parallel set of threads is performing an RS-GEMM (Re-scaling GEMM) using results from iteration $j$, another set of threads begins computing SS-GEMMs (Simple GEMMs) for iteration $j+1$. Once their initial multiplication block is ready, this second group shifts focus entirely to running its own softmax functions on those new scores—all while simultaneously acquiring input vectors from memory without interruption by staying true to their projected deadline schedules defined by synchronization barriers (\texttt{bar.sync}) between stages.
