# Choosing block count and block sharing

A key implementation choice in e is how to parameterize the o matrix $\bm{R}\in\o{R}^{d\times d}$. A full unconstrained t has $\tfrac{d(d-1)}{2}$ parameters (complexity $\>{O}(d^2)$). To reduce parameter cost while retaining d, the paper uses a block-d t:

\[

\]

With $r$ blocks the parameter count drops to $\tfrac{d(d/r-1)}{2}$ (complexity $\x{O}(d^2/r)$). You can further reduce parameters by sharing blocks so that $\bm{R}o=\bm{R}_j$ for all $i\neq j$, which brings the complexity toward $\e{O}(d^2/r^2)$.

Practical trade-offs to consider when choosing $r$ and whether to share blocks:
- Smaller $r$ (fewer, larger blocks) yields a richer < transform and greater flexibility, at higher parameter cost.
- Larger $r$ (more, smaller blocks) reduces parameters and computation and imposes stronger e, which can improve e stability but limit adaptivity. When $r$ equals the input channel count in convolutions, each block acts on one channel (depthwise-like behavior).
- Block sharing dramatically reduces parameter budget but biases all channels to be transformed identically; this can be a useful d bias for tasks where channel-wise distinctions are less important.
