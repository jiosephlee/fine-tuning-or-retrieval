### No inference overhead claim: any caveats when pre-multiplying $R$ into $W^0$?
Question:
The paper states there is no inference overhead because one can precompute $W = R W^0$ and discard $R$. Are there scenarios where $R$ was shared across multiple layers or blocks such that pre-multiplication changes memory layout or weight tying in unexpected ways? Also, when using block sharing across $R$ blocks, does this impact how you fold $R$ into $W^0$ if multiple layers share the same $R$ parameters (e.g., you would still materialize separate $W$ per layer, losing the sharing at inference)?
Answer:
Short answer: functionally nothing breaks — folding an orthogonal matrix $\mathbf{R}$ into pretrained weights $\mathbf{W}^0$ (computing $\mathbf{W}=\mathbf{R}\mathbf{W}^0$) produces an equivalent forward operator and therefore does not change inference results — but there are practical caveats around memory, weight-tying semantics and numerical/layout choices you should be explicit about. Below I explain the different scenarios, the consequences, and practical options.

If $\mathbf{R}$ is layer-shared but the pretrained weights $\mathbf{W}^0$ differ per layer. In training you may learn a single $\mathbf{R}$ and apply it to multiple distinct $\mathbf{W}^0_{\ell}$ (layers indexed by $\ell$), i.e. $\mathbf{W}_{\ell}=\mathbf{R}\mathbf{W}^0_{\ell}$. At inference you can precompute each $\mathbf{W}_{\ell}$ and discard $\mathbf{R}$. This is algebraically identical to keeping $\mathbf{R}$ in the graph: the runtime matmul $\mathbf{R}\mathbf{W}^0_{\ell}$ has been done ahead of time. The functional behavior is unchanged, but two practical consequences follow:

1) Memory: storing a single $\mathbf{R}$ (plus the $\mathbf{W}^0_{\ell}$ if you kept them) is more compact than storing every folded $\mathbf{W}_{\ell}$ only if you still keep $\mathbf{W}^0_{\ell}$ or can reuse $\mathbf{R}$ compactly. If you precompute and store the distinct $\mathbf{W}_{\ell}$, you lose the memory savings that sharing $\mathbf{R}$ provided during training. In other words: folding preserves inference speed but may increase stored parameter volume compared to keeping a single shared $\mathbf{R}$ and the original $\mathbf{W}^0_{\ell}$.

2) Weight tying semantics: many frameworks allow true parameter sharing by multiple layers pointing at the same tensor. If you relied on a single tensor object $\mathbf{R}$ being used at multiple places, replacing it by distinct precomputed $\mathbf{W}_{\ell}$ changes that sharing relationship. If you care about preserving a single shared folded matrix for multiple layers, you must either (a) fold once into a single tensor and set multiple layers to reference that same tensor, or (b) keep $\mathbf{R}$ and perform the $\mathbf{R}\mathbf{W}^0_{\ell}$ multiplication at load time (or lazily) instead of materializing separate $\mathbf{W}_{\ell}$ tensors. If you do nothing, inference is still correct, but the parameter graph no longer shares a single object.

If $\mathbf{R}$ is shared across multiple blocks (block-sharing) or you use block-diagonal $\mathbf{R}=\mathrm{diag}(\mathbf{R}_1,\ldots,\mathbf{R}_r)$. The same points above apply at block granularity. When you fold a block-diagonal $\mathbf{R}$ into a layer weight $\mathbf{W}^0$, you multiply each block into the corresponding rows of $\mathbf{W}^0$ yielding $\mathbf{W}=\mathbf{R}\mathbf{W}^0$. If the same block $\mathbf{R}_i$ was shared across many layers during training, folding produces distinct $\mathbf{W}$ per layer (unless the $\mathbf{W}^0$ were identical). So block-sharing reduces train-time parameters and computation, but folding can make those shared blocks become many unique concrete weights at inference unless you explicitly reuse the same folded block memory. Again: correctness preserved, sharing/memory footprint may not be.

Practical numerical and layout considerations. Folding is a simple dense matrix multiply and is cheap to do once at deployment, but keep in mind floating-point rounding: $\mathbf{R}\mathbf{W}^0$ computed in FP32 then stored in FP16 may not be bit-identical to performing the same operations inside a different runtime ordering. Also if $\mathbf{R}$ was Cayley-parameterized and computed at high precision and then multiplied, numerical stability of the Cayley inverse was a training-time concern; at inference you only use the final $\mathbf{R}$ so this is minor. Finally, folding changes memory layout of weight tensors (different strides/contiguity) which can influence low-level kernel performance; most frameworks handle this but you may want to ensure tensors are in the preferred memory layout (e.g., contiguous) after folding.

Recommendations depending on your goal. If you want zero extra compute and do not care about storing extra per-layer parameters, simply precompute $\mathbf{W}_{\ell}=\mathbf{R}\mathbf{W}^0_{\ell}$ for every layer and replace weights in the model. If you want to preserve the memory savings of shared $\mathbf{R}$ at inference (for example because the set of $\mathbf{W}^0_{\ell}$ are huge and you want to store only $\mathbf{R}$ plus a small base), either keep a single shared folded tensor and make all relevant layers reference it (only possible if the folded tensor is identical for those layers), or keep $\mathbf{R}$ and compute $\mathbf{R}\mathbf{W}^0_{\ell}$ at model-load time or lazily on first use (this trades a little startup compute for lower storage). If you must maintain parameter-tied semantics (for frameworks or tooling that check shared-identity), explicitly set layer weight references to the same folded object; otherwise tying will be lost.

Summary: folding $\mathbf{R}$ into $\mathbf{W}^0$ is mathematically valid and preserves inference behavior as the paper states. The only real caveats are practical: you may lose the storage/weight-tying advantages of a single shared $\mathbf{R}$ (since folding yields distinct $\mathbf{W}$ per layer unless you explicitly reuse the same folded tensor), and you should be mindful of minor numerical/layout effects. Choose folding-at-deploy, lazy-materialization, or explicit shared-folded tensors depending on whether you prioritize minimal inference compute, minimal storage, or preserving sharing semantics.
