\title{A Textbook about the Paper: "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models"}

Chapter 3: # Constructing the DeepSeekMath Corpus

Large‐scale mathematical reasoning requires a training set that is both extensive **and** faithful to genuine mathematical discourse. In DeepSeekMath, we addressed this challenge by developing an end‑to‑end extraction pipeline that mined an ever‑growing assortment of mathematics‑rich web pages from Common Crawl (CC). The process required careful curation at every step—starting from seed data creation, crafting a lightweight yet powerful classifier with fastText, iteratively recalling new content while safeguarding against duplication, selectively retaining only the highest quality samples within a predetermined token budget, and finally decontaminating any inadvertent overlap with downstream benchmarks. Each component was designed to be reproducible while ensuring linguistic durability for downstream large language models (LLMs).

---

## # Seed Corpus: OpenWebMath & Initial FastText Labeling Examples

The foundation of any successful web‑scraping strategy lies in a **seed corpus** with high precision—pure signals that teach the system what “math content” looks like before it dives into an unstructured search space. We leveraged **OpenWebMath** \citep{openwebmath}, an existing curated collection of shortmathematical texts harvested from reputable Q&A sites such as Math Stack Exchange and MathOverflow. This dataset provides dense mathematical expressions interleaved with natural language explanations—exactly what LLMs will later encounter during fine‑tuning or inference.

To bootstrap our classifier we paired **positive** samples from OpenWebMath with **negative** samples drawn uniformly at random from CC’s raw archive:
- **Positive set:** \textbf{500 k} unique snippets deemed highly mathy.
- **Negative set:** \textbf{500 k} arbitrary CC webpages devoid of overt mathematics by design (transparent negatives).

The stark contrast between these two sets gave us unmistakable signal vectors for what constitutes a mathematics‑oriented document—without requiring manual labeling beyond this initial split.



---

## # FastText Classifier Configuration (dims 256 → vectors)

FastText—an efficient bag‑of‑character adapters into word embeddings—was chosen because it can ingest thousands of text windows while maintaining constant memory consumption and lightning speed on commodity GPUs. Its architecture is linear: two matrices
\[
W^{\text{in}}, W^{\text{out}} \in \mathbb R^{V\times d},
\]
where \(V\) is vocabulary size and \(d=256\) was settled empirically through an ablation study balancing representational capacity against overfitting risk on web noise.

Key hyperparameters:
| Parameter | Value | Rationale |
|---|---|---|
| Vector dimension (\(d\)) | \(256\) | Strong enough to differentiate mathematical notation yet compact enough for rapid joins over billions of documents |
| Learning rate (\(\eta\)) | \(0.1\) | Allows quick convergence given the relatively small labelled budget |
| Max n‑gram length | \(3\) | Captures short character bigrams plus tri‑grams capturing common symbols \(\{=,\sqrt{},etc.\}\) |
| Min word count (“minn”) | \(3\) | Prunes ultra‑rare tokens that would contribute noise |
| Epochs | \(3\) | Faster training tuned for one pass over \(1\,\text{M}\) labeled samples |

With these settings we trained a binary classifier outputting
\(p(y=\textit{math}\mid x)\)
for any input snippet \(x\). The clean output scores were then forwarded into the next pipeline stage performing *recall*.



---

## # Iterative Recall: Domain Grouping + Near Deduplication (~40 B HTML pages)

Processing raw CC is infeasible without prefiltering because billions of crawled URLs compress into millions if accounting for redundant copies or near duplicates (e.g., paginated discussions). We therefore employed a two‑stage reduction:

1. **URL-based Deduplication**  
   All identical URLs were collapsed into unique entries—a trivial `[URL] → [content]` mapping whose hash ensures nothing is retained twice.
2. **Near‐Duplicate Pruning**  
   Using shingle hashing techniques—sliding windows over character sequences—we compared documents pairwise and merged any exceeding an overlap threshold (\(\approx92\,\%\)). This eliminated echo effects caused by subtitle variations or auto-generated signatures typical on forum threads.

The result was roughly **40 billion HTML documents**, which served as the search space over which our fastText scorer could operate.



*Recall Phase*  
Each document received a *mathness* score from FastText; documents were sorted descendingly into buckets across many thresholds corresponding to different effective token budgets:
- **Topʹs JSON** (top-ranked list).
  
During each *iteration*, we increased both our training corpus breadth and quality:

| Iteration | New Positive Source | Approximate Size After Recall |
|---|---|---|
|0 – Baseline|OpenWebMath seeds alone|~13 billion sents balanced|
|1 – First pass|FastText recall + dedupe set|≈30 billion sents|
|2 – Domain expansion|Identified domains >10% coverage→manual anthology addition e.g., `mathoverflow.net/questions`|≈50 billion sents|
|3 – Penultimate refine |Re‑train FastText further on enriched positives→unchanged majority coverage.|≈100 billion sents|
|4 – Final sweep |Stop when <2 % new domain found.|≈120 billion sents|

After four passes we amassed around **35 million** distinct webpages registering roughly **\(120\,\mathrm{B}\)** tokens following content cleanup.

## # Top–Scoring Page Filtering & Token–Budget Decisions (40 B → 120 B)

A raw list sorted by fastText score is essentially unbounded; we thus had to decide *how many* documents made it into pre‑training data while respecting GPU budgets during model training phases later on. To do so:

1. **Token Counting per Page**  
   For each ranked document we performed whitespace tokenization following the `DeepSeek` model's vocabulary (including math symbols), obtaining token counts \(t_i\).  
2. **Cumulative Sliding Window**  
   We maintained a cumulative sum
   \[
   S(k)=\sum_{i=1}^{k}t_i ,
   \]
   stopping once \(S(k)\approx B_{\max}\), where \(B_{\max}\in \{40\,\mathrm{b},80\,\mathrm{b},120\,\mathrm{b},160\,\mathrm{b}\}\).
3. **Early Selection Strategy**  

   In practice our first *training experiment* evaluated each budget variant “in isolation” by feeding models trained solely on that slice into downstream tests such as GSM8K or MATH after just one epoch.
   
4. **Adopted Budget**  
   The empirical curve revealed diminishing returns beyond ~\(80\,\mathrm{b}\); however due to additional safety margins in later stages where float‐point accelerators become routine, we settled finally on keeping roughly
   \[
       B_{\max}=120\,\mathrm{b}
   \]
   tokens—a tenfold expansion beyond OpenWebMath’s original size while still within realistic compute budgets.



*Why Top–Scoring First?*  
FastText assigns higher scores preferentially when characteristic mathematical patterns appear—multiple symbol clusters or explicit equation formatting—which directly correlate with higher reasoning quality in downstream tasks such as formal theorem proving or dynamic calculation scripting.



---

## # Decontamination Against Benchmark Passages Using Exact n‑Gram Blocking

A delicate pitfall when mining web text for mathematics datasets is *benchmark contamination*. If any paragraph employed verbatim during training matches exactly some prompt–answer pair in later evaluation suites like GSM8K or MATH, then test results would reflect memorization rather than genuine reasoning—a serious integrity violation across academic VE research.

To preclude this risk we applied stringent look‑ahead filtering:

1. **Benchmark Token Sets:**  
   All benchmark passage strings were preprocessed identically—tokenized under `DeepSeek`’s vocabulary—and stored in hash maps keyed by substrings.
2. **Exact N-Gram Blocking Routine**  
   For every candidate webpage:
   - Extract all consecutive subsequences up to length \(L=10\).
   - Check whether any :subsequence appears fully inside any benchmark passage.
    
    If either condition satisfied,
    - If whole phrase length \(\geq10\,guds,\) discard entire page.
    - If page length is <10 and shares ≥ 3‐grams … also discard.
    
    This loop ensures even very short question/answer fragments do not slip through.
    
3. **Deduplication After Blocking**  
    Since near‐duplication had already been performed earlier
    we rechecked blocks only on surviving documents,
    avoiding unnecessary rehashes.
4. **Resultant Corpus Integrity**  
    Post decontamination inspection confirmed no known benchmark excerpt remained,
    while keeping ~\(118\,\mathrm{b}\) useful math tokens—no more than
    a negligible loss relative to raw recall output.
