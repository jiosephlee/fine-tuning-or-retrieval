# DeepSeekMath Made Simple — A New Era For Open‑Source Math Solvers  

**Why this matters**  
Solving contest‑level physics‑style algebra problems has traditionally been a playground for large closed‑source systems like GPT‑4 or Gemini Ultra – models that cost tens of millions of dollars just to run once a week.  
DeepSeekMath flips that script by showing that a **only‑seven‑billion‑parameter** language model can achieve comparable accuracy *in‑house* without needing a chain of external tools or a voting ensemble.



-----------------------------------------------------------------------

## What’s Behind A “Self‑Contained” Math Solver?

Mathematical proofs are highly structured – every line follows logically from every previous one, often involving sub‑steps written in plain English as well as formal expressions (e.g., “algebraically solving \(x^2 -3x+2=0\)").  
Getting a language model right requires **two key ingredients**:

| Ingredient | Why it matters |
|------------|----------------|
| **Quality super‑large data** | A domain‑specific pre‑train corpus forces the transformer to learn both how problems are phrased & how calculations are carried out stepwise |
| **Targeted instruction fine‑tuning** | Pairing problems with human solutions teaches the model to *think* aloud rather than spit out an instantaneous answer |

DeepSeekMath builds precisely these two layers while sidestepping burdensome tooling (Python execution rigs, external calculators) entirely.


-----------------------------------------------------------------------

## Building The Sizeable, High‑Quality Corpus

### From Common Crawl Where Mathematics Lurks

The authors began with **OpenWebMath**, a gold standard collection of curated web pages containing textbook‐style problems spread across many languages (English & Chinese).  
Using this set as seeds they trained a fastText classifier, then repeatedly mined new pages from Common Crawl → Refinement → Decontamination → Repeat analogously until reaching **120 billion tokens** worth of mathematical text (≈ 35 million pages).

Noteworthy points along this pipeline  

* **Iterative enrichment:** After each round new domains were identified (“mathoverflow.net”, “projecteuclid.org”, etc.) then added back into seed set → more diverse recall.
* **Benchmark protection:** Any page containing a stretch matching any substring longer than ten grams from leading public benchmarks (GSM8K, MATH…) was dropped outright.
* **Zero unsupervised bias:** No proprietary datasets injected – everything came originally public through CC mining + carefulto filtering.


### How It Compares To Other Corpora

| Corpus | Size | Language diversity | Notes |
|--------|------|--------------------|-------|
| **DeepSeekMath** | **120 b** | Multilingual (Chinese & English dominate) | Largest alone among public math corpora |
| OpenWebMath | 13 b | Mostly English | Our starting seed |
| MathPile | ~9 b | Mostly arXiv/Latex-heavy | Dominated by papers |
| Proof-Pile‑2 | ~38 b | Mixed sources incl papers & OEIS |
    
The sheer volume combined with natural language versus formal latex balance gives us an edge over past efforts that relied mainly on arXiv tokens (the authors report little benefit there).

## Which Model Is This?

1️⃣ **Base:** Initialized off *DeepSeek-Coder-Base-v1.5*, a popular code training backbone comprising its own backprop network tuned on billions of repo snippets → gives the transformer a solid foundation in syntax rules beneficial for both code and symbolic algebra states.

2️⃣ **Pre‑train:**  

* Token mix = ~56 % original Data workspace + *deepseekmath* + code repository + ⋯ checksum  
* Total tokens = **500 B**, super‐gigaphorically covering all possible problem styles while staying single-host friendly  

The curve climbs steeply – see how far more learning comes at roughly one full pass over each repeated block instead of early saturation seen when training only smaller domain corpora.


3️⃣ **Instruction Tuning:**  

A curated SFT set (~776 k examples) spans both English+Chinese problems tied together through three answer styles  
– chain-of-thought (**CoT**) blurting down every intermediate calculation  
– program-of-thought (**PoT**) letting Python libraries verify heavy arithmetic
– tool-integrated format covering “call API” surfaces  

Fine-tuned over only `500` SFT iterations → *Drop-in prompt* ready!

> ## Result snapshot
> 
> • **Self-contained CoT accuracy**  
> ‑ GSM8K ‑~81–82 %\ higher than other open nodes  
> ‑ MATH ‑42–46 %\ ⁠(a sharp jump over baseline)

> • **Tool-inclusive PoT accuracy**

## Reinforcement Learning That Actually Works

Typical post‐SFT boosting uses Proximal Policy Optimization (PPO). Yet PPO inflates memory budget twice because it trains an extra value network alongside policy parameters… impossible on many commodity GPU farms when your backbone is already pushing limits.

### Enter Group Relative Policy Optimization (GRPO)

A tiny tweak produces massive savings while keeping novelty power intact:
* No separate critic → use only current batch’s average reward as #baseline  
* For each question `q`, generate `G` different candidate solutions `o₁…o_G` via staggered sampling  
* Rewards compare pairs *inside* each group → lock relative standings (`hat A_{i,t}` derived directly from `r_i−mean(r)`)  

Result:
| Phase           | Accuracy@Community Benchmarks |
|-----------------|-------------------------------|
| SFT‐only        | ≈48 %-50 %\ (on GSM8K/MATH)   |
| GRPO @SFT NetID | ≈88–89\,[%] GSM8K & ≈52\,[%] MATH |

Furthermore:
* Graded end-token reward replaced classic KL penalty ➜ eliminates dependence on large critic architecture.
* Memory footprint shrank roughly by half compared to vanilla PPO — enabling realistic >300 band width runs even at early sweet spot GPUs.

Hence Zero‐tool LLM reaches subject parity against “hidden” beasts while staying completely deterministic internally.

## How Does This Compare To The Big Names?

Quantitative benchmark reference points limitedly spelled out inside paper excerpt ≈:

In plain words our openly available system now sits at the tail end (*but nothing behind*) graphically lined up next door to mainstream commercial labs’ tall houses — badly defined competitive line approximating GPT‑4’s edge even without any stack overflow calculators or custom Python engines pulling re-run scores.

## Why No External Tools Are Needed At All

Most modern research solves maths by combining LLM outputs with heavy symbolic engines underneath (“Tool use as adjunct”). While powerful, this blurs attributable skill patterns since algorithms feed each other back into less transparent loops—harder reproducibility!

With our series:
1️⃣ Every step is purely generated inside Transformer hidden states (\(O(32k)\) context)
2️⃣ Chain-of-thought remains downstream logic tied strictly into token logits.
3️⃣ Hidden rewards ↔ policy adjustments happen inside blockwise loops thanks to GRPO’s non-replayer critics.
4️⃣ Multi-language pronunciations leveraged directly during pre-train / instruction tag excision make prompt design almost frictionless following usual parrot prompts (`What’s x plus y?`, `请解释步骤.`).

Hence verdict — web authors concertedly embedded high-quality math within single token stream realize near-one-shot answer quality formerly reserved for compute-heavy pipelines.

## Things Still On The Horizon  

Although learning curves are steeled already…

* Geometry/graphical reasoning segments remain weaker compared to closed‐source greats – likely reflects current corpus imbalance skew toward algebraic narrative over diagrammatic proofs.
* Cross-language width has improved dramatically yet Chinese tier puzzles sometimes capture mistakes left unchanged during SFT reliance 🔤
* The shift toward automated proof generators (`MiniF2F`, `Isabelle`s Sledgehammer`) demonstrates promise yet exposes limited ability against theorem prover integration given current token lengths.
* Further exploration into high‐quality process reward models might reduce redundancy seen from outcome supervision alone––although early experimentation demonstrates additive benefits already consistent across seeds.
  

Dedicated future work includes higher-frequency prompt trees (`TreeSearch`) coupled with efficient inference acceleration (#Speculative & #FastPRED), arguably unlocking absolute leaps ahead.\[See Related Section D/A]\

## TL;DR Highlights For Practitioners

<details>
<summary>A quick bullet cheat-sheet</summary>

• Build your own huge math corpus via fastText classification + iterative CC mining → aims ~120\,b tokens.<br>
• Initialize off any strong coding backend (`v1`, ``v1†``). Code pre-training synergizes—strengthens both raw mechanical reasoning and basic coding head defaults.<br>
• Post-pretrain super-fine-tune using chain-of-thought pairs (~776k).<br>
• Wrap PDE MINIS `<3` style groups ⇒ execute GRPO using *no separate critic*. Only one vectorization pass per request ⚡️<br>
• Outcome & process fine-grained reward function boosts success up to ≥52 % across contest-style tasks.<br>
• No Python runtime/Geneva scoring outwardly required—the Transformer decides all._</details>

## Final Thoughts

The core takeaway remains unambiguous:
**Size alone does not guarantee mastery when your dataset speaks mathematics fluently**, nor does expert codification automatically translate into symbolic insight—unioned under Center!
 
By leveraging public crunchy records thoughtfully curated via best practices exemplified above while weaving an innovative reinforcement strategy (`GRPO`) we’ve collapsed decades’ worth distance between free-access solutions and formerly locked heuristics powered by infusions of finely tuned vocabulary straps (<~5 Gb parameters!). Spearheading continued interest at Redwood basement labs may soon see repeated iterations producing top quartile readers employing entirely offline deterministic logic powering real student help apps worldwide—all driven entirely in software you ship yourself.\n\nHappy math hacking!
