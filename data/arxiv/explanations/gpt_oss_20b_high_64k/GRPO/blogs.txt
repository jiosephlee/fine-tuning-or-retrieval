# DeepSeekMath Made Simple — A New Era For Open‑Source Math Solvers  

**Why this matters**  
Solving contest‑level physics‑style algebra problems has traditionally been a playground for large closed‑source systems like GPT‑4 or Gemini Ultra – models that cost tens of millions of dollars just to run once a week.  
DeepSeekMath flips that script by showing that a **only‑seven‑billion‑parameter** language model can achieve comparable accuracy *in‑house* without needing a chain of external tools or a voting ensemble.



-----------------------------------------------------------------------

## What’s Behind A “Self‑Contained” Math Solver?

Mathematical proofs are highly structured – every line follows logically from every previous one, often involving sub‑steps written in plain English as well as formal expressions (e.g., “algebraically solving \(x^2 -3x+2=0\)").  
Getting a language model right requires **two key ingredients**:

| Ingredient | Why it matters |
|------------|----------------|
| **Quality super‑large data** | A domain‑specific pre‑train corpus forces the transformer to learn both how problems are phrased & how calculations are carried out stepwise |
| **Targeted instruction fine‑tuning** | Pairing problems with human solutions teaches the model to *think* aloud rather than spit out an instantaneous answer |

DeepSeekMath builds precisely these two layers while sidestepping burdensome tooling (Python execution rigs, external calculators) entirely.


-----------------------------------------------------------------------

## Building The Sizeable, High‑Quality Corpus

### From Common Crawl Where Mathematics Lurks

The authors began with **OpenWebMath**, a gold standard collection of curated web pages containing textbook‐style problems spread across many languages (English & Chinese).  
Using this set as seeds they trained a fastText classifier, then repeatedly mined new pages from Common Crawl → Refinement → Decontamination → Repeat analogously until reaching **120 billion tokens** worth of mathematical text (≈ 35 million pages).

Noteworthy points along this pipeline  

* **Iterative enrichment:** After each round new domains were identified (“mathoverflow.net”, “projecteuclid.org”, etc.) then added back into seed set → more diverse recall.
* **Benchmark protection:** Any page containing a stretch matching any substring longer than ten grams from leading public benchmarks (GSM8K, MATH…) was dropped outright.
* **Zero unsupervised bias:** No proprietary datasets injected – everything came originally public through CC mining + carefulto filtering.


### How It Compares To Other Corpora

| Corpus | Size | Language diversity | Notes |
|--------|------|--------------------|-------|
| **DeepSeekMath** | **120 b** | Multilingual (Chinese & English dominate) | Largest alone among public math corpora |
| OpenWebMath | 13 b | Mostly English | Our starting seed |
| MathPile | ~9 b | Mostly arXiv/Latex-heavy | Dominated by papers |
| Proof-Pile‑2 | ~38 b | Mixed sources incl papers & OEIS |
    
The sheer volume combined with natural language versus formal latex balance gives us an edge over past efforts that relied mainly on arXiv tokens (the authors report little benefit there).


-----------------------------------------------------------------------

## Which Model Is This?

1️⃣ **Base:** Initialized off *DeepSeek-Coder-Base-v1.5*, a popular code training backbone comprising its own backprop network tuned on billions of repo snippets → gives the transformer a solid foundation in syntax rules beneficial for both code and symbolic algebra states.

2️⃣ **Pre‑train:**  

* Token mix = ~56 % original Data workspace + *deepseekmath* + code repository + ⋯ checksum  
* Total tokens = **500 B**, super‐gigaphorically covering all possible problem styles while staying single-host friendly  

The curve climbs steeply – see how far more learning comes at roughly one full pass over each repeated block instead of early saturation seen when training only smaller domain corpora.


3️⃣ **Instruction Tuning:**  

A curated SFT set (~776 k examples) spans both English+Chinese problems tied together through three answer styles  
– chain-of-thought (**CoT**) blurting down every intermediate calculation  
– program-of-thought (**PoT**) letting Python libraries verify heavy arithmetic
– tool-integrated format covering “call API” surfaces  

Fine-tuned over only `500` SFT iterations → *Drop-in prompt* ready!

> ## Result snapshot
> 
> • **Self-contained CoT accuracy**  
> ‑ GSM8K ‑~81–82 %\ higher than other open nodes  
> ‑ MATH ‑42–46 %\ ⁠(a sharp jump over baseline)
> 
> • **Tool-inclusive PoT accuracy**   
> ‑ 61–65 %\ for Python-aware attendees

## Reinforcement Learning That Actually Works

Typical post‐SFT boosting uses Proximal Policy Optimization (PPO). Yet PPO inflates memory budget twice because it trains an extra value network alongside policy parameters… impossible on many commodity GPU farms when your backbone is already pushing limits.

### Enter Group Relative Policy Optimization (GRPO)

A tiny tweak produces massive savings while keeping novelty power intact:
* No separate critic → use only current batch’s average reward as #baseline  
* For each question `q`, generate `G` different candidate solutions `o₁…o_G` via staggered sampling  
* Rewards compare pairs *inside* each group → lock relative standings (`hat A_{i,t}` derived directly from `r_i−mean(r)`)  

Result:
| Phase           | Accuracy@Community Benchmarks |
|-----------------|-------------------------------|
| SFT‐only        | ≈48 %-50 %\ (on GSM8K/MATH)   |
| GRPO @SFT NetID | ≈88–89\,[%] GSM8K & ≈52\,[%] MATH |

Furthermore:
* Graded end-token reward replaced classic KL penalty ➜ eliminates dependence on large critic architecture.
* Memory footprint shrank roughly by half compared to vanilla PPO — enabling realistic >300 band width runs even at early sweet spot GPUs.

Hence Zero‐tool LLM reaches subject parity against “hidden” beasts while staying completely deterministic internally.

## How Does This Compare To The Big Names?

Quantitative benchmark reference points limitedly spelled out inside paper excerpt ≈:
∎ **GPT‑4 / Gemini Ultra** _(closed)_ ∼70–75 % top-tier performance  
∎ **DeepSeekMath-RL** ≈52 % on competition‐level MATH (+98 points better than existing published open ropes)  
∎ **Self-consistency boosting** leads us further ahead → <span>60 &#x25;</span>MATH when sampling ≈64 outputs per prompt 

In plain words our openly available system now sits at the tail end (*but nothing behind*) graphically lined up next door to mainstream commercial labs’ tall houses — badly defined competitive line approximating GPT‑4’s edge even without any stack overflow calculators or custom Python engines pulling re-run scores.


-----------------------------------------------------------------------

## Why No External Tools Are Needed At All

Most modern research solves maths by combining LLM outputs with heavy symbolic engines underneath (“Tool use as adjunct”). While powerful, this blurs attributable skill patterns since algorithms feed each other back into less transparent loops—harder reproducibility!

With our series:
1️⃣ Every step is purely generated inside Transformer hidden states (\(O(32k)\) context)
2️⃣ Chain-of-thought remains downstream logic tied strictly into token logits.
3️⃣ Hidden rewards ↔ policy adjustments happen inside blockwise loops thanks to GRPO’s non-replayer critics.
4️⃣ Multi-language pronunciations leveraged directly during pre-train / instruction tag excision make prompt design almost frictionless following usual parrot prompts (`What’s x plus y?`, `请解释步骤.`).

Hence verdict — web authors concertedly embedded high-quality math within single token stream realize near-one-shot answer quality formerly reserved for compute-heavy pipelines.

## Things Still On The Horizon  

Although learning curves are steeled already…

* Geometry/graphical reasoning segments remain weaker compared to closed‐source greats – likely reflects current corpus imbalance skew toward algebraic narrative over diagrammatic proofs.
* Cross-language width has improved dramatically yet Chinese tier puzzles sometimes capture mistakes left unchanged during SFT reliance 🔤
* The shift toward automated proof generators (`MiniF2F`, `Isabelle`s Sledgehammer`) demonstrates promise yet exposes limited ability against theorem prover integration given current token lengths.
* Further exploration into high‐quality process reward models might reduce redundancy seen from outcome supervision alone––although early experimentation demonstrates additive benefits already consistent across seeds.
  

Dedicated future work includes higher-frequency prompt trees (`TreeSearch`) coupled with efficient inference acceleration (#Speculative & #FastPRED), arguably unlocking absolute leaps ahead.\[See Related Section D/A]\

# Mining Mathematics From The Web  

In large‑language‑model development there is one special class of knowledge – mathematics – where depth of reasoning rarely equals breadth of facts. GPT‑4 or Gemini Ultra can answer many arithmetic questions because they **see** plenty of them during pre‑training, but open‑source models lag far behind even while sized several hundred times larger in memory and compute consumption than their closed‑source counterparts.  

A team at DeepSeek addressed this imbalance by turning one of the biggest public datasets ever built – **Common Crawl** – into a clean, multimodal “math corpus” containing **120 billion tokens** across dozens of languages (English & Chinese dominate). Their approach combined a simple supervised learner (fastText) with an iterative data‑engineering spiral that keeps pulling new pages while shedding noise and benchmark contamination until every page left would only add value.


---

## Why pulling maths out of Common Crawl matters

* **Scale:** Existing open‑source maths corpora rarely exceed two dozen billions of tokens – far smaller than many general‑purpose corpora vetting an entire public web index each day.
* **Quality:** Simply taking every ``math'' page harms reasoning ability – you end up memorising huge PEG sub‐sets rather than learning how *to* reason through proofs or genuine problem solving traits needed for synthetic evaluation sets such as *GSM8K*, *MATH*, *CMATH*.
* **Renewability:** Keyword‑based extraction (e.g., “math”) often misses higher level knowledge such as geometry insights buried under vernacular scripting sites or forum threads hidden behind “calculus” titles.


DeepSeek built an extractable pipeline that continually iterates over three core concerns:
1) find mathematically relevant fragments;
2) prune harmful duplications;
3) guarantee no overlap with the evaluation benches themselves.


---

## The pipeline – step by step

Below is an overview you can implement yourself if you wish – the process stayed around five days' worth of compute on commodity GPU hardware (~108 TB raw ingested).

| Step | Action | Tool / Model | Notes |
|------|--------|--------------|-------|
| **1** | Create an initial seed set | `OpenWebMath` (≈ 13 billion page tokens) | A hand–curated set covering many textbook‐style explanations |
| **2** | Train a fastText keyword detector | `fasttext.train_supervised()` | *Parameters:* size = 256 dimensional vectors, LR = 0.1, n‑gram up to 3 words, minimum word freq = 3 over 3 epochs |
| **3** | Deduplicate raw crawl | URL–based+near duplicate hash hashing | Reduces raw CC down from >40 billion URLs → ≈ 40 billion HTML files |
| **4** | Retrieve docs via classifier | scoreᵢ ← fasttext.predict(prob).top() | Choose top scoring set until max token budget reached (`∼40 billion` first round). |
| **5** | Evaluate retained pages scaling choices | Pre‑train small debug models on `(40  → 80 → 120 → 160)` token subsets | Keeps tuning very quickly – drop earlier if growth plateaus |
| **6** | Spot domains missed because seeds weren’t diverse | Identify domains where `>10%` footprints were recovered during Step‑4 | Typical winners show reddit/js sidebars linked to long discussion threads |
| **7** | Manually annotate URLs rich in math content (e.g., `/questions` subfolders) | Add each annotated page back into new seed set | Expands variety without sacrificing curation quality |
| **8** | Retrain fastText with expanded seeds → Step‑4 again *for a different chunk* of CC data | Repeat until plateau (~four iterations) | Stop when next round would increase coverage by <2%, i.e., already seen ​≥ 98% |

### Decontaminating against eval benchmarks

Common practice now requires scrubbing any text fragment that could leak solutions into your training set—especially since large training corpora unwittingly contain entire exam question transcripts!

* Find every substring whose length ≥10 characters appears verbatim in any problem set used later (`GSM8K`, `MATH`, `CMATH`, `AGIEval`);
* Remove every whole web snippet containing such match;
* For shorter fragments (<10 characters), search only against exact `≥ 3` trigrams—this avoids accidentally excising legitimate context around names or symbols that happen to appear close together only by chance.

This strict decontamination guarantees no hidden memorized answers float through transformer weights during downstream inference.



---

## What does the finished corpus look like?

* **Size:** Around ​35 million unique webpages → ≈​120 billion scientific/mathematical tokens  
* **Languages:** English and Chinese dominate; additional slivers exist from Spanish and French hosts thanks to CC’s global footprint  
* **Multilingual richness:** Because CC is served globally it naturally contains statements written in dozens of scripts – all fed through fastText’s character n‑grams indiscriminately  
* **Production sanity:** Removing duplicate near‐identical pages saves GPU memory during pre‑training—pre‑trained models experience fewer catastrophic interference effects when later finetuned


---


## Why does it work?

[Benchmarks](#evaluation-results — see below) show deep advantage versus competing corpora (`MathematicsPile`, `OpenWebMath`, `Proof-Pile–2`). In short:

1. **Coverage matters more than size alone** – DeepSeek’s train range was exhausted latehandly while others spent taking repeated passes through fewer items capped at <30 billion text units;
2. **Fine voice tuning empyricists far better reflect human problem sets** – our seed Vectors were conceptually close enough so that hierarchical grouping during later SFT stages produced many rules backed up posteriorly from sparsely observed datapoints;
3.Aligns directly with inference tasks where solutions must walk ∼5–12 logical steps—how best done is efficient vocabulary spotting + cluster searching across discoverable yet distinct actinage binding cues.

# Coding Trains Math Skills Too

> “Code training” isn’t just game‑development slang—it actually boosts mathematical problem solving.  
> In this post we break down two sets of multi‑stage experiments that show why starting a large language model (LLM) from a deep coder gives its later math instruction time an extra edge.



## Why Zipping Between Code & Math Matters

Large language models typically learn everything together—text, instructions, answers—but when you want them to crack hard numbers or prove equations you hit a wall.  
The authors of **DeepSeekMath** put one theory to test:

> **Code bugs are tiny puzzles**  
>   *Programming* forces you to think in *precise, step‑wise* terms—writing correct syntax is one thing, debugging is another.  
> If an LLM has already learned how browsers catch “if mismatches” before it learns arithmetic rules, it carries over a procedural mindset that works well on long chain‑of‑thought problems.



## Two Kinds of Multiplatform Trials

The experiments split into two families—each telling us what happens when you combine coding data *before* or *alongside* mathematical data.



### 1. Two‑Stage Curriculum

| Stage | Tokens | Purpose |
|-------|--------|---------|
| **First** | **400 B** – Unsupervised code | Teach raw syntax & logical flow |
| **Second** | **150 B** – Maths | Layer arithmetic & proof patterns |

**What happened?**

* After the first phase alone, the model was already better at writing working Python scripts for short questions—for example GA–<boosted probability by ~15 % versus a model trained only on natural language>.
* A second maths pass sharpened its ability to *reason stepwise* while still using tools—GSM8K jumps from roughly 70 % → 85 %, and MATH climbs from near 40 % → 55 % accuracy.
* A control line trained first on generic text instead of code saw far weaker gains after maths fine‑tuning (~25 % less on GSM8K), proving that coding itself matters.



### 2. One‑Stage Hybrid Mix

| Distribution | Tokens | Aim |
|--------------|--------|-----|
| Code + Maths | **400 B + 150 B** blended together | Full‑stack learning within one continuous loop |

**Observations**

* Mixing inside a single pass kills the “catastrophic forgetting” you see when switching phases—the model keeps its programming chops while still catching new maths logic.
* Resulting programs solve more guided Python problems—upward shift similar to two‑stage heights (~+10 % over pure‐math baseline).
* For pure non‑toolmath styles (answers written out without executing Python), blending was even slightly worse than two stages alone—likely because a ~1–1.3 B parameter model cannot fully absorb both streams simultaneously.



## Digging Into Why Coding Helps

1. **Procedural Discipline** – Code forces “do something until something else” loops; maths problem solving often follows similar bootstrapped procedures (e.g., algebraic substitution).
2. **Error Signal Clarity** – A compiler raises *exactly* where you went wrong; reward signals during continued pre‑training reflect precise failures instead of vague natural language confusion.
3. **Logical Unit Testing** – Executable snippets let the model see if each intermediate step actually gives the correct output—a positive reinforcement signal not present when just reading text.



## Practical Takeaways for Anyone Building Math LLMs

1. **Start With Code First?**  
   *Good enough.* If your hardware allows it, begin by spending a substantial portion (≈40 % ) your pre‑training budget teaching coding sequences before doing mathematics modules—especially if you plan tool–integrated reasoning soon afterward.
2. **Mix It Up When Capacity’s High**  
   *When you have ≥10–12 B parameters,* start blending coding & maths rather than staging them sequentially—this avoids forgetting while still hearing both signals cleanly.
3. **Match Scale With Strategy**  
   Small models (“LLM‑small”) shine under staged curriculum; medium models are tolerant of mix‐in; huge models like GPT‑4 can handle either without aggressive changes.
4. **Don’t Forget Non‑Toolmath Losses**  
   Even if your end goal is toolable maths (Python + SymPy), keep some plain question answering batches alive—they help build commonsense grounding necessary for open domain problems.



## Bottom Line

When DeepSeekMath’s authors mapped out “what happens if we give an LLM years’ worth of compiler-minded practice before pushing it into arithmetic wars,” they found:

* Coding provides a robust scaffolding for structured problem solving,
* Two stages give clean separation but risk forgetting,
* One stage adds synergy – especially when replayed against powerful reward regimes such as GRPO,
* And crucially—cooking up massive amounts of mathematically oriented web data alone isn’t enough unless accompanied by a generous share of solid code examples.

So next time you think “let’s train an LLM end straight on mathematics,” remember: the best recipes bake in some karma from coding first—because those tiny syntax errors turn out being golden nuggets for higher‑level number crunching!
