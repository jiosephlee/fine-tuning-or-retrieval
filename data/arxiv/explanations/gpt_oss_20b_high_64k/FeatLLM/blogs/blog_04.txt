# Fast & Light On the Bottom Line  
**Why a Simple Linear Weight Is All You Need**

---

## TL;DR  
“We don’t feed every new record into an expensive language‑model at test time.”  
Instead **FeatLLM** lets GPT‑style models create *rules* once, turns those rules into binary flags, and trains a tiny non‑negative linear classifier over those flags – all within seconds – yet it beats heavyweight baselines on dozens of real‑world tabular tasks.

---

## TL;DR – Key Points

| Item | What It Means |
|------|---------------|
| **No per‑sample inference** | After a single round of rule extraction you never hit an LLM again during deployment |
| **Rule‑based binary features** | Each example becomes an array of `0/1` counters telling whether it satisfies *10* extracted conditions |
| **Linear classifier with ReLU weights** | A handful of positive weights collapse deep trees or ensembles into one cheap dot product |
| **Ensemble by bagging** | Repeat the off‑line process 20× → diverse rule sets → tighten predictions while staying lightweight |
| **Low total cost** | Training < few minutes on CPU “or” even less than a typical logistic regression run |

---

## Why Skip Heavy Models?

In traditional “few‑shot” tabular learning you either

* **Fine‑tune** large transformers – which is impossible if you only have API access,
* Or **re‑invoke** an LLM every time you feed a new row – a latency nightmare,
* Or use standard tree ensembles that still spend time building many splits even when data are scarce.

Fea_tLLM flips this paradigm:

```text
1️⃣ Prepare a prompt → GPT generates *rules*
2️⃣ Parse those rules → New binary columns per example
3️⃣ Train shallow nu­merical model     ← DONE!
```

Once step 1–2 are finished there’s no more interaction with GPT when predicting users’ queries – we simply evaluate a dot product and apply Softmax. The whole pipeline runs inside milliseconds compared with seconds–minutes cost driven by remote API calls in other approaches such as In‑Context Learning or TabLLM.

---

## Step 1 – Turning Domain Knowledge Into Rules

### How Do We Ask GPT?

A prompt *mirrors* how an expert would solve the task:

1. **Basic Information** –  
   *Task description* (“Does this patient have chronic heart failure?”),  
   *Feature name + type* (e.g., `"Age is numeric"`),  
   *A few labeled examples* serialized as text (`f_1 is … f_d is … Answer:`).

2. **Reasoning Instruction** –  
   First ask GPT “What relationships between features might influence chronic heart failure?”  
   Then follow up “Using those relationships plus the examples above write ten concise conditions that determine chronic heart failure.”

3. **Response Instruction** –  
   Force alphabetical “Rule 1…Rule 10” list style so parsing boilerplate becomes tractable even when GPT switches `>` → “greater than”.

The prompt size stays far below most token limits because we extract just ten rules per target class, regardless whether your table has ≈ 50 features or ≈ 200!

### What Do The Rules Look Like?

```text
Rule 1 → Age > 50 AND SystolicBP ≥ 140
Rule 2 → NoHistoryOfDiabetes OR MorphMetabolicSymptoms == “Present”
…
```

No real code yet—just readable plain text that obviously encodes boolean logic.



---

## Step 2 – From Text Rules To Binary Features

After GPT spits out these sentences we do two things automatically:

1. **Code Generation Prompt**  
   Give GPT another tiny prompt that says “Write Python code that takes a row dict and returns `True` iff this rule holds.”  

   Example output returned from GPT:

   ```python
   def R_1(row):
       return row['Age'] > 50 and row['SystolicBP'] >= 140
   ```

2. **Execute With `exec()`**  
   `exec()` loads all functions into memory once per dataset split; then every record is passed through each function producing a `0/1`.

Because all parsing is itself done by GPT—the same family that produced the rules—you avoid brittle regex logic while still keeping speed ~ microseconds per record.



---

## Step 3 – Learn *What Matters*

Now each example has become a vector

\[
\mathbf{z}_k^i \in \{0,1\}^{R}
\]

for every class \(k\) (we keep R = 10).  
A surprisingly expressive machine learning model is all you need:

\[
\text{logit}_k^i = \underbrace{\max(\mathbf{w}_k,\mathbf{0})}_{\text{non‑negative}}\cdot \mathbf{z}_k^i,
\qquad 
p_k^i = \operatorname{Softmax}\bigl(\![\,\text{logit}_1^i,\dots,\text{logit}_c^i\,]\!\bigr).
\]

Few notable design choices:

* **ReLU‐style weights** (`max(…,0)`) guarantee that satisfying an extracted rule never *reduces* your confidence for its target class.
* The number of parameters equals \(c \times R\) (e.g., \(2\times10=20\)) – unplugged & instantly trainable even on old CPUs.
* Training objective = cross‑entropy over < 8 labeled samples → ≈ 200 epochs converge within seconds.



---

## Boosting Robustness With Ensembles

Repeatedly running step 1–3 fresh gives us diverse sets of rules because:

* We shuffle order of demo examples before every query;
* We run the generator at slightly higher temperature;
* And optionally bag subset limited rows/features each time (`feature bagging`).

With \(T=20\) trials we average their predicted probabilities,

\[
p^{(t)}_k{}(x)=… \quad \Longrightarrow \quad 
p^{\text{final}}_k(x)=\frac{1}{T}\sum_{t=1}^{T} p^{(t)}_k(x).
\]

This delivers almost all performance gains usually obtained by deep neural nets while keeping complexity low.

## Performance Snapshot

Across **13 popular datasets**, Fea_tLLM consistently finished first OR second versus eleven competitive baselines—including sophisticated non–few–shot systems like TabPFN—by roughly **+10 % AUC on average** when bootstrapped with only four shots (directly comparable to hundredshifted conventional methods like XGBoost trained fully).

| Modality | Best‑case Rank | Typical AP Increase vs Baseline |
|----------|----------------|----------------------------------|
| Logistic Regression | #6 | ‑ |
| XGBoost            | #5 | ‑ |
| Fea_tLLM             | #2⁐ | +10 % AUC |

*(Numbers are rounded averages reported by authors.)*

Importantly, compared services such as In‑Context Learning or TabLLM had nightmarish inference times because they asked the LLM *every* prediction step — while our entire dot product finished in < 0.5ms per record.

## Why It Works Well In Low‐Shot Settings

| Insight | Resulting Benefit |
|---------|-------------------|
| Rules capture *highly informative discrete events*. | Fewer samples needed – they’re semantically richer than raw columns |
| Weight tuning learns *relative importance*. | Catastrophic generalization prevented even when some derived flags are noisy |
| Ensembling diversifies coverage across columns & records.| Resistant to spurious correlations even after appending unrelated columns |

An optional qualitative test added unrelated “Adult” columns to Heart data: Fea_tLLM’s accuracy stayed nearly constant while many baselines fell dramatically.

## Get Started Quickly

Fea_tLLM relies only on public APIs:

```bash
pip install openai pandas numpy torch lightning
```

```python
from feattlm import FeatLLMPipeline

pipe = FeatLLMPipeline(
    llm="gpt-3.5-turbo",
    n_rules_per_class=10,
    n_ensembles=20,
    batch_size=64,
)

pipe.fit(X_train, y_train)
preds = pipe.predict(X_test)
```

Under `<5` minutes it enlightens your dataset’s hidden logic—and then stays there forever.

## Takeaway

You don’t need big nets if you equip them with *good* engineered features—and good engineers can be virtual appliances fed through an LLM once! By letting an LLM discover semantic conditions instead making predictions directly, Fea_tLLM turns its generous prior knowledge into compact binary flags . A tiny non‑negative weight system then efficiently scopes those conditional signals at test time airlessly leaving your downstream hardware unburdened and latency eliminated.
