# Prompt Perfected  
## A Two‑Step Reasoning Journey from Data to Rules  

When a tabular data set is small—often fewer than ten labeled examples—classic supervised learning models stumble on noise and spurious patterns.  
Large language models (LLMs) have shown an uncanny ability to draw on encyclopaedic knowledge without ever seeing a specific table before training.  
The key question becomes *how* do we get those priors into an efficient tabular learner without making every inference call through a gigantic inference engine?

**FeatLLM** answers this by turning an LLM into an *expert feature engineer*.  
Its secret sauce is a meticulously crafted prompt consisting of three parts:

| Component | Purpose | What it looks like |
|-----------|---------|--------------------|
| **Basic Information** | Supplies task description, feature names/titles + types and any useful definitions or value lists | “Does *X* indicate chronic heart failure? Yes / No” + serialized examples |
| **Reasoning Instruction** | Forces an *intermediate* causal‐mapping step familiar one would perform before writing code | “First think about which features might influence heart failure based on medical lore...” |
| **Response Instruction** | Imposes rigid formatting so downstream parsing is trivial | “List ten match ≤ rule‑sets numbered 1–10.” |

The magic happens when you separate *world‑level intuition* from *data‑driven evidence* inside a single instruction set—a two‑step chain-of-thought broken down into causality + real‑world experiments.




### 1️⃣ Step One – Causal Groundwork

In most prompts for few‑shot classification you simply drop example pairs into a long string and ask the model “Which label fits?”.  
Fealt­tempts a different route:

> **Ask GPT**  
> _“Think about what types of variables are most likely related to chronic heart failure based purely on your prior knowledge.”_

This coaxed reflection encourages GPT‑3.5’s internal ‘expert’ deliberation module normally activated during inference over large corpora—so you already hit ground-truth associations such as **age → risk**, **blood pressure → risk**, or **chronic diseases → risk** without seeing any instance data yet.



### 2️⃣ Step Two – Coupling Prior Knowledge With Small Data

Now GPT receives the same static prompts plus four serialized example rows
that contain every feature name followed by its value plus ground‑truth label (“Answer = Yes/No”).  
It is instructed explicitly *to heed* the causal‐mapping discovered earlier while analysing these tiny datasets:

> _“Now articulate ten decision rules that would discriminate ‘Yes’ from ‘No’ subjects based on these four samples.”_

Because GPT was nudged toward causal variables first, it rarely spins up meaningless conditions like “ID % = 17” purely because that id happens coincidentally appear in all four examples.



### 3️⃣ Structured Output – Rules Ready For Code  

Super important: every rule must look mechanically identical so I can churn them automatically into Python truth tests later.  

A well‑formed template generated by FeatLLM resembles this:

```
Rule №1: IF Age ≥ 55 AND SystolicBP > 180 THEN Yes
Rule №2: IF Age < 55 AND Diabetes == True THEN No
…
Rule №10:
```

Nothing odd—only one atomic condition per rule—so even if GPT slightly rephrases “greater than” as “more than”, the parser still recognises it.

## Why Two Steps Prevent Spurious Correlations  

Experiments hidden behind Benchmark figures reveal that when they omit either:
* Feature descriptions (*the column metadata*) or  
* The first crosstalk‐style causal deduction,

the average accuracy drops noticeably—even before training any downstream classifier—especially when training labelled shots ≤ 8.  
By contrast keeping both survived tests where **unrelated columns** were appended arbitrarily (*e.g.* Adult income columns added to Heart data). Across such augmentation experiments **FeatLLM’s performance degraded minusculely**, whereas baseline end‑to‑end LLM predictors suffered huge drops from noisy colinearities.

## From Human‑Read Rules To Machine‑Fast Predictions  

After these hard‑coded logical sentences appear you let GPT perform one more tiny request:



```text
Write python code that turns these ten string rules into binary features.
For each row input:{row_dict}
Output:{binary_features}
```

Because GPT sees only one small JSON payload it outputs clean temporary functions such as:

```python
def check_rule_01(row):
    return row['Age'] >= 55 and row['SystolicBP'] > 180
```

You execute every `check_rule_*` against all samples (`exec()`), thereby creating a **binary matrix** $Z$ where $Z_{ij}=1$ iff sample $i$ satisfies rule $j$.  

Now it’s just ordinary supervised linear regression on those binary features—but there’s a twist: uniqueness hints keep weights nonnegative:

$$
\logit_k^i \;\leftarrow\;\bigl[\max(\mathbf{w}_k,\mathbf0)\bigr]\cdot \mathbf{z}_k^{\,i},
\qquad   
p_k^i = \mathrm{softmax}\bigl(\{\logit_1^i,\dots,\logit_c^i\bigr).
$$

Training `w` requires *only* cross‑entropy over your handful of labeled rows—no further calls to an external LLM are needed at deploy time! Prediction latency thus collapses from minutes (for an end‑to‑end GPT call) down to microseconds.

## Ensemble & Bagging — Guard Power Against Limited Window Size  

For high–dimensional tables (>100 columns) your serialized prompt may exceed token limits. FeatLLM solves it simply:


| Technique | How → Result |
|-----------|--------------|
| Randomly pick %⨉ (`γ`) × N rows per round   | Shorter prompts       |
| High temperature (+∈) during generation   | More diverse rules    |
| Bag whether you choose subset `F′ ⊂ F`    | Reduce chance zero overlap |

Run $T$ independent trials (typical $T ≈20$), learning weights $\{\mathbf w^{(t)}\}$ which together capture many views of the task space,
and finally average their softmax outputs—the ensemble gives robustness parity with loop-other-state-of-the-art while keeping an individual model tiny.

## Takeaways — When Should You Build With FeatLLM?

| Situation                           | FeatLLM Advantage                                   |
|-------------------------------------|------------------------------------------------------|
| < 10 labeled rows                   | Utilises world knowledge → far better generalisation|
| Needs cheap deployment              | Single forward pass through tiny linear layer        |
| Many features × limited context window | Feature bagging + grouping cuts don’t overflow Δt      |
| Want interpretability              | Final rules are human readable                       |

If you’re working on medical outcome prediction, finance risk scores—or even synthetic problems—you can bake everything you have into a deterministic textbox *once*, run a single lightweight inference during deployment—and still beat state‑of‐the‑art laterals such as TabPFN or STM-based variants while saving GPUs.

### 🚀 How To Try It Today  

[source](https://github.com/Sungwon-Han/FeatLLM)

1. Pick whatever RESTful language model you’ll access—GPT‑3’s turbo works perfectly.
2. Feed it your dataset through FeatLLM’s recommended prompt template.
3. Let it spit ten concise rules per class.
4. Wrap them up automatically via one Linenagle call (`exec`) producing $Z$.
5. Fit `w` over your read samples (`torch`, `sklearn`, or pure numpy).
6. Deploy — negligible cost energy €25 / month vs ~€600/month spent just calling API for each row.
