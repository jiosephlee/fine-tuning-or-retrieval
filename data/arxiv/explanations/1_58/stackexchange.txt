### What exactly do you mean by "1.58 bits" per parameter when weights are ternary?
Question:
The paper calls the model "1.58-bit" because weights are ternary in \{-1,0,+1\}. I think \(\log_2(3)\approx 1.585\) bits per independent symbol, but I'm confused how this maps to practical storage and throughput claims. Are you counting Shannon entropy per parameter, raw encoded bits, or something else? How does storing ternary weights in hardware (which typically uses whole bytes or 2-bit encodings) justify the "1.58 bits" label?
Answer:
Short answer
- “1.58 bits” is the information-theoretic shorthand for a ternary parameter that can take 3 values: log2(3) ≈ 1.585 bits of information per parameter (that is, the maximum Shannon information if the three symbols were equally likely).
- It is not a claim that each weight is stored in 1.585 physical DRAM bits in the experiments. In practice you store ternary weights using fixed-width encodings (commonly 2 bits/weight), or you can compress toward the 1.585-bit limit with entropy coding at extra CPU/GPU cost.
- In this paper the measured memory/latency results use a practical 2-bit kernel (they explicitly say “Both latency and memory were measured with a 2-bit kernel”), so the empirical speed/size wins come from a combination of (a) using ternary weights which eliminate multiplies and simplify compute and (b) using low-bit (2-bit) representations that reduce bandwidth compared to FP16.

Longer explanation and intuition (with numbers)
1) What does log2(3) mean here?
- A single ternary symbol that can be one of three equiprobable values carries H = log2(3) ≈ 1.585 bits of information. Formally for symbols with probabilities p1,p2,p3 the Shannon entropy is
  H = −∑_{i=1}^3 p_i log2 p_i.
  The 1.585 number is the maximum entropy when p1 = p2 = p3 = 1/3.
- Papers often call a ternary model “1.58-bit” as a concise way to say “weights are ternary (−1, 0, +1) so the symbol alphabet has size 3,” i.e., the theoretical information content per parameter is log2(3).

2) Why isn’t that literally the number of physical bits stored?
- Physical storage on common hardware must use whole bits and common alignments. Typical practical choices:
  - Use a fixed 2-bit encoding per weight (e.g., 00→−1, 01→0, 10→+1). This is simple, hardware-friendly, and random-access friendly. It uses 2 bits/weight, which is larger than the entropy bound 1.585 bits but is simple and fast.
  - Pack many ternary symbols into words (bit-packing) and/or apply entropy coding (Huffman/arithmetic) to approach the 1.585 bits/weight on average. Entropy coders can get close to H but add decode complexity and worse random access; they are rarely used for inner-loop inference on current GPUs without specialized decompression hardware.
- So “1.58 bits” is best read as an information-theoretic description of the alphabet, not as “we stored exactly 1.585 physical bits per weight in DRAM while running the model”.

3) How the paper actually implements and measures memory/throughput
- The paper explicitly states that they integrated a “2-bit kernel from Ladder” and that “Both latency and memory were measured with a 2-bit kernel, so there is still room for optimization.” That tells you:
  - Their reported memory and latency numbers are based on a practical 2-bit implementation, not an ideal entropy-coded 1.585-bit storage.
  - Therefore empirical speedups and memory savings come from moving from FP16 (16 bits per weight) to a 2-bit representation plus cheaper compute (ternary arithmetic avoids FP multiplies), not from an ideal entropy coder achieving the 1.585-bit limit.
- This is important: the word “1.58-bit” names the model class (ternary weights) and the asymptotic information per weight; the experiments use an implementation-friendly 2-bit format.

4) Practical numerical comparison examples
- Bits per parameter:
  - FP16 = 16 bits.
  - Ideal ternary (information bound) = log2(3) ≈ 1.585 bits.
  - Practical fixed encoding = 2 bits (what the paper used for measurements).
- Relative storage:
  - Ideal ternary vs FP16: 1.585/16 ≈ 0.099 → ≈ 10% of FP16 bits (≈10× compression in bits).
  - 2-bit vs FP16: 2/16 = 0.125 → 12.5% of FP16 bits (8× compression).
- Example for 70B parameters:
  - FP16 size ≈ 70e9 * 16 bits = 1.12e12 bits = 140 GB.
  - 2-bit size ≈ 70e9 * 2 bits = 140e9 bits = 17.5 GB.
  - Ideal 1.585-bit size ≈ 70e9 * 1.585 bits = 111e9 bits ≈ 13.9 GB.
  So the difference between the practical 2-bit storage and the theoretical 1.585-bit limit is a few gigabytes at 70B scale (here ~3.6 GB).

5) Where the latency / throughput wins come from (intuitive)
- Lower memory bandwidth: reading 2 bits per weight instead of 16 bits per weight reduces the amount of data moved from DRAM/SRAM per multiply-accumulate (or per equivalent op).
- Simpler arithmetic: ternary weights mean a multiply by {−1,0,+1} reduces to conditional adds/subtracts and masked adds (no floating-point multiply), which is much cheaper in energy and latency on many chips.
- Kernel engineering: speedups require specialized kernels that read packed low-bit formats and implement the ternary arithmetic efficiently — the paper used such a 2-bit kernel.

6) When can you actually reach “1.58 bits per parameter” in stored size?
- Only with compression (entropy coding) tuned to the actual empirical distribution of weights (the entropy could be less than log2(3) if one symbol, e.g. 0, is much more common).
- Practical issues: entropy coding is great for archival or off-line storage, but less convenient for random-access inference unless decompression is done in-stream or via hardware.
- If your model has skewed symbol frequencies (say many zeros), the Shannon entropy H will be < log2(3), so the compressible bits/weight can be even lower than 1.585 in principle.

Bottom line / recommended mental model
- “1.58 bits” = log2(3) = the information capacity of a ternary weight (a convenient name for a model family that uses 3-valued weights).
- For practical systems you typically store and compute with a 2-bit representation (or pack/entropy-compress to approach 1.585 bits), so empirical memory/throughput numbers reflect the practical encoding and kernels used. The paper makes this explicit: they used a 2-bit kernel for measurements and note that there is room to optimize further.
- The major runtime/energy wins come from reduced bandwidth and much cheaper arithmetic (no FP multiplies), not from magically having fractional hardware bits per weight.

If you want to dig deeper
- To quantify how close you could get to the 1.585-bit limit for a trained model you would:
  1. Measure the empirical distribution p_{−1}, p_0, p_{+1}.
  2. Compute H = −∑ p_i log2 p_i (bits per weight).
  3. Design an entropy coder (Huffman/arithmetic) or a block packing scheme to see practical compression and decoding overhead.
- The paper’s note that “there is still room for optimization” points to exactly this next step: either hardware that natively supports ternary packing/compute or software schemes that approach the entropy bound without prohibitive decode cost.

### How does the absmean scaling (\(\gamma\)) interact with the quantized weights during inference?
Question:
Equation (1) defines \(\widetilde{W} = \mathrm{RoundClip}(W/(\gamma+\epsilon),-1,1)\) with \(\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|\). After quantization, are the integer ternary weights multiplied back by \(\gamma\) during inference (i.e., effective weight \(\gamma\widetilde{W}\))? If so, does that multiplication reintroduce FP multiplies into the matmul, undermining the claim of "almost no multiplication"? If not, how is the scale applied or absorbed so that only addition remains?
Answer:
Short answer
- Mathematically, the ternary matrix \(\widetilde{W}\) is a scaled approximation of the full-precision weights: roughly \(W \approx \gamma\,\widetilde{W}\).
- However, that does not mean the inference inner loop must perform a full FP multiply for every weight–activation pair. In practice (and consistent with the paper’s claims that the bulk of work is INT8 additions) the scalar \(\gamma\) is handled outside the inner integer-accumulation loop: either applied once per output (cheap), folded offline into other FP quantities (no runtime multiplies), or implemented with cheap fixed-point/shift operations. Any of these preserves the “almost no multiplication” property because the expensive per-element FP multiplies of a normal FP matmul are avoided.

Why you might think this is a problem
- From the definition in the paper,
  \[
  \widetilde{W}=\mathrm{RoundClip}\!\left(\frac{W}{\gamma+\epsilon},-1,1\right),
  \qquad
  \gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|,
  \]
  we get the natural reconstruction
  \[
  W\approx \gamma\,\widetilde{W}.
  \]
  If you naively implemented matmul as \(Y=W X\approx (\gamma\widetilde{W})X\) by multiplying each ternary weight by \(\gamma\) and then doing the FP multiply-adds, you'd reintroduce the full cost. That would undermine the claim. But the paper does not use that naive approach.

How it’s actually implemented (practical, standard options consistent with the paper)
Let X be the input activations and consider computing \(Y=W X\). Using the ternary decomposition we want
\[
Y \approx \gamma\bigl(\widetilde{W} X\bigr).
\]
There are three common, practical ways to implement this so that the inner kernel stays integer-add-dominant:

1) Integer matmul + single-scale post-multiply (simple):
- Compute the integer accumulation A = \(\widetilde{W} X\) using integer arithmetic (adds and integer accumulators). This is the expensive inner loop but it does not require FP multiplies.
- Multiply the result by the scalar \(\gamma\): \(Y=\gamma A\). Because \(\gamma\) is one scalar per weight matrix (or per block), this is one FP multiply per output element (or even per output-channel), not per weight–activation pair.
- Cost comparison: if the full FP matmul would do O(N) multiplies per output element, this method does one FP multiply per output element plus O(N) integer additions inside the kernel — a huge reduction in FP multiplies.

2) Fold \(\gamma\) into adjacent parameters (no runtime multiply):
- During model conversion (offline), absorb the \(\gamma\) factor into the next layer’s parameters or into any nearby FP scaling factor so that no runtime FP multiply is needed for this layer.
- Example: if the next layer is a linear with weights \(V\), then \(V ( \gamma\,\widetilde{W} X) = ( \gamma V ) ( \widetilde{W} X)\). Precompute \(V'=\gamma V\). At run-time you still do \(\widetilde{W} X\) (integer) and then apply the next op with the already-scaled \(V'\).
- This is a common trick in quantized inference tooling to eliminate per-layer scale multiplies.

3) Fixed-point / power-of-two approximation of \(\gamma\) (integer-friendly):
- Quantize \(\gamma\) to a fixed-point integer plus a shift (or approximate it by a power-of-two). Then the scaling can be implemented as an integer multiply + shift, or even a bit-shift, which is far cheaper than many FP multiplies.
- This keeps everything in integer arithmetic on hardware that supports fast integer multiplies/shifts.

Why these preserve the “almost no multiplication” claim
- The dominant cost in dense matmul is the inner-loop per-weight multiply-add. With ternary \(\widetilde{W}\) you eliminate that: you replace per-weight multiplies by conditional adds/subtracts (or masked adds) because weights are in \{-1,0,1\}.
- Any remaining FP multiply(s) for \(\gamma\) are either:
  - a single multiply per output element (much, much fewer multiplies overall), or
  - eliminated entirely by folding the scale into neighboring parameters, or
  - implemented cheaply in integer arithmetic.
- The paper’s profiling and energy discussion (“the majority of BitNet b1.58 is INT8 addition calculation” and huge energy savings) are consistent with one of the above implementation choices: the inner GEMM kernel is integer-add-dominant and FP multiplies are negligible in the overall cost.

A short numerical intuition
- Full FP matmul: roughly O(MNK) FP multiplies (and adds).
- Ternary approach with post-scale: O(MNK) integer adds, plus O(MN) FP multiplies for the per-output scaling if done naively. Since the cost of integer adds and the cost of a single FP multiply per output element are tiny compared to O(MNK) FP multiplies, you get very large savings.
- Folding the scale removes even that per-output FP multiply entirely.

Connection to the paper’s activation handling
- The paper also quantizes activations to 8-bit per token and removes zero-point — there is already a per-token scale in the activation quantization pipeline. That per-token scaling is another place where scales can be combined or arranged so that the runtime kernel stays integer-centric (for instance, by choosing the activation quantization scale to absorb some constant factors).

Takeaway
- Yes: mathematically W ≈ γ · \widetilde{W}. No: that fact does not force you to perform the original dense FP multiplies inside the inner loop. Practical implementations consistent with the paper keep the inner kernel integer-add-dominant by (a) doing the integer \widetilde{W} X accumulation and applying γ as a cheap post-scale, (b) folding γ into adjacent parameters offline, or (c) representing γ in an integer-friendly form. Any of these preserves the “almost no multiplication” advantage the paper claims.

### What value is used for \(\epsilon\) in \(\gamma+\epsilon\), and how sensitive is training to that choice?
Question:
The quantization formula uses \(\gamma+\epsilon\) to avoid division by zero. What numeric value did you choose for \(\epsilon\) during training and inference, and did you test sensitivity to it? Could a poor choice cause many weights to quantize to 0 or saturate at \{\pm1\} and hurt performance?
Answer:
Short answer
- The paper does not state a numeric value for \(\epsilon\); no explicit \(\epsilon\) value or sensitivity study is reported in the text you provided.
- In practice this term is only there to avoid division-by-zero and numerical underflow; one typically picks \(\epsilon\) many orders of magnitude smaller than the typical scale \(\gamma\). If \(\epsilon\) is far too large you bias everything toward 0; if it is effectively zero but \(\gamma\) becomes tiny you can blow up the normalized values and drive many weights to \(\pm 1\).
- If you want a practical recipe to reproduce or test: measure the distribution of \(\gamma\) across layers, choose \(\epsilon\) several orders of magnitude below the median \(\gamma\) (or use a small absolute constant like \(10^{-8}\!-\!10^{-6}\) for FP32/FP16 pipelines), and do a log-scale sweep while monitoring zero-rate, saturation-rate and validation perplexity.

Longer explanation and practical guidance

What the formula does and why \(\epsilon\) exists
The quantizer used in the paper is
\[
\widetilde{W} = \mathrm{RoundClip}\!\Big(\frac{W}{\gamma+\epsilon}, -1, 1\Big),\qquad
\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|.
\]
- \(\gamma\) is the per-matrix average absolute weight (a scale factor).
- \(\epsilon\) is a small stabilizer so the denominator never becomes exactly zero (and to avoid underflow when \(\gamma\) is extremely small).
- Effectively the quantizer maps the matrix entries after dividing by \(\gamma+\epsilon\) to \{-1,0,+1\}.

How \(\epsilon\) affects quantization in intuitive terms
- If \(\epsilon \ll \gamma\): denominator \(\approx\gamma\). The scaling is dominated by \(\gamma\) and \(\epsilon\) has almost no effect.
- If \(\epsilon\) is comparable to or larger than \(\gamma\): denominator increases, so \(W/(\gamma+\epsilon)\) shrinks toward zero → more entries round to 0 (higher zero-rate).
- If \(\gamma\) itself becomes extremely small (weights near zero) and \(\epsilon\) is very small as well, the denominator can be tiny → entries blow up relative to the denominator and many values can saturate to \(\pm 1\).
So:
- Too-large \(\epsilon\) → excessive zeros (loss of information).
- Too-small \(\epsilon\) in the presence of tiny \(\gamma\) → excessive \(\pm 1\) saturation.
Either extreme can hurt representational capacity and training.

What the paper reports (and what it does not)
- The paper explicitly gives the quantization formula and uses the per-matrix abs-mean \(\gamma\).
- The excerpt you provided does not state the numeric \(\epsilon\) used, nor does it include an ablation or sensitivity study on \(\epsilon\). So there is no ground-truth value reported in the paper text you shared.

Recommended practical choices (consistent with typical quantization practice)
- If you are training/evaluating in FP32 or FP16/BF16, common small constants used to stabilize divisions are around \(10^{-8}\) to \(10^{-6}\). For FP16 you might pick the larger end of that range to be safe with dynamic range.
- Many implementations simply use \(\epsilon=10^{-8}\) (FP32-style) or \(\epsilon=10^{-6}\) for mixed/FP16 settings; these are small enough to be negligible when \(\gamma\) is a normal-weight scale, but prevent divide-by-zero.
- A slightly more robust strategy: pick \(\epsilon\) relative to the weight scale, e.g.
  \(\epsilon = \delta\cdot\mathrm{median}(\gamma_{\text{layers}})\) with \(\delta\) like \(10^{-3}\!-\!10^{-4}\). This avoids picking an absolute number that is either too big or too tiny relative to your model's weight magnitudes.

How to test sensitivity (recommended experiments)
1. Compute \(\gamma\) distribution across layers for your initialization and during training.
2. Sweep \(\epsilon\) on a log scale, e.g. \([10^{-12},10^{-10},10^{-8},10^{-6},10^{-4},10^{-2}]\) (or narrower tuned around the scale of your \(\gamma\) values).
3. For each \(\epsilon\) measure:
   - Zero-rate: fraction of weights quantized to 0.
   - Saturation-rate: fraction quantized to \(\pm 1\).
   - Short-run validation perplexity / loss and any downstream metric you care about.
4. Watch for:
   - A sharp rise in zero-rate with increasing \(\epsilon\) (too many zeros).
   - A sharp rise in saturation-rate with decreasing \(\epsilon\) when some \(\gamma\) are tiny.
5. If you see sensitivity, consider making \(\epsilon\) adaptive (relative to per-layer \(\gamma\) stats).

Why training often isn’t super sensitive in practice
- In normal training, \(\gamma\) (mean absolute weight) is not zero and tends to sit at a stable scale after a little training. So an \(\epsilon\) like \(10^{-8}\!-\!10^{-6}\) is usually negligible compared to \(\gamma\) and has no meaningful effect.
- The quantizer here is per-matrix abs-mean scaling; since \(\gamma\) aggregates many parameters, it rarely collapses to machine epsilon in healthy training runs.
- Still, corner cases exist: very small layers, newly initialized layers, or aggressive weight decay/regularization can produce small \(\gamma\). That’s where diagnostics and a conservative \(\epsilon\) choice help.

Final practical recommendation
- Because the paper does not report the exact \(\epsilon\), treat \(\epsilon\) as a tunable but usually uncritical hyperparameter. Start with \(\epsilon \in [10^{-8},10^{-6}]\) (use the larger value for BF16/FP16 runs), verify that \(\gamma \gg \epsilon\) for most layers, and run a small sweep while tracking zero/saturation rates and a dev-set metric. If you observe instability, switch to a relative epsilon (e.g., a small fraction of the median layer \(\gamma\)).

### How are gradients computed through RoundClip during training?
Question:
RoundClip is non-differentiable (round and clip). Did you use a straight-through estimator (STE) or another surrogate gradient? If STE, what variant and were there any stability issues (e.g., exploding gradients, oscillations) when training from scratch with ternary weights?
Answer:
Short answer
- The paper does not explicitly state which gradient estimator was used for the non‑differentiable RoundClip.  
- In practice (and consistent with BitNet-style quantized training), people almost always use a Straight‑Through Estimator (STE) for the rounding operation, and either a passthrough/identity STE or the derivative of a hard‑tanh surrogate for the clip.  
- A few engineering choices that matter a lot and are consistent with what the paper describes (and that make training from‑scratch with ternary weights stable) are: (1) keep a full‑precision master weight $W$ that is updated, (2) detach or treat the scale $\gamma$ carefully (do not backpropagate through it, or use a running average), (3) apply STE for round (and usually treat clip as identity in the interior), and (4) use standard optimizer/regularization tricks (AdamW, LR warmup, gradient clipping, RMSNorm etc.).  

Below I explain the reasoning, give concrete formulas for the common STE implementation consistent with the paper’s quantizer, discuss pitfalls (exploding/oscillating gradients) and mitigation strategies, and mention alternative surrogate approaches.

What the paper states (grounding)
- The paper defines the forward quantizer as
  $$
  \widetilde W = \mathrm{RoundClip}\!\left(\frac{W}{\gamma+\epsilon}, -1, 1\right),
  $$
  with
  $$
  \mathrm{RoundClip}(x,a,b)=\max(a,\min(b,\mathrm{round}(x))),
  \qquad
  \gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|.
  $$
- The paper says the model is trained from scratch with 1.58‑bit weights and 8‑bit activations, but it does not specify the backward (gradient) treatment of the non‑differentiable $\mathrm{round}$ and $\mathrm{clip}$.

Typical/likely implementation (STE) and a concrete backward rule
Because the paper doesn’t say otherwise, the simplest consistent implementation is the usual STE. The idea:

- Forward: compute $\tilde W$ as above and use $\tilde W$ in all forward passes (matrix multiplies, etc.).
- Backward: propagate gradients to the underlying full‑precision $W$ through a straight‑through path that ignores the zero gradients of rounding.

A concrete STE-compatible backward formula (common in ternary/binary nets) is:

1. Compute scaled pre‑quantized variable:
   $$
   X = \frac{W}{\gamma+\epsilon}.
   $$
2. Forward quantize:
   $$
   \widetilde W = \mathrm{RoundClip}(X,-1,1).
   $$
3. Given incoming gradient $\frac{\partial L}{\partial \widetilde W}$, approximate the gradient w.r.t. $W$ by
   $$
   \frac{\partial L}{\partial W}
   \approx \frac{1}{\gamma+\epsilon}\, \mathbf{1}_{|X|\le 1}\odot \frac{\partial L}{\partial \widetilde W}.
   $$
   - Here $\mathbf{1}_{|X|\le 1}$ is an indicator that is 1 when $|X|\le 1$ and 0 outside; this corresponds to treating clip like an identity inside the interval and blocking gradient outside (or you could use a softer surrogate).  
   - Many implementations simplify further and use $\frac{\partial L}{\partial W}\approx \frac{1}{\gamma+\epsilon}\, \frac{\partial L}{\partial \widetilde W}$ (i.e., pass gradient everywhere), which is the pure “vanilla STE”.

Practical notes about $\gamma$
- Because $\gamma$ itself depends on $W$, backpropagating through it introduces a potentially large and confusing coupling (every element of $W$ influences the scale of every other element). Typical, stable choices are:
  - Detach $\gamma$ from the gradient (treat it as a constant in the backward pass), or
  - Maintain $\gamma$ as a running average (and detach the running average), or
  - If you do backprop through $\gamma$, do it carefully (it often destabilizes training).
- The paper defines $\gamma$ as the mean absolute value per matrix; the safest consistent implementation for stable training is to compute $\gamma$ from $W$ in forward and stop gradient through it (i.e., treat it as constant for the backward pass). This is common in many quantized training works.

Why STE (intuitively) works here
- Rounding is a hard nonlinearity that maps continuous $W$ to a discrete set. STE ignores the zero derivative of round and supplies a proxy derivative so the underlying continuous parameters can move across quantization thresholds. This allows gradient‑based updating of a full‑precision master copy of weights even while the forward uses discretized weights.
- Scaling by $\gamma$ normalizes magnitudes so most values fall near the ternary thresholds; that helps gradients actually push weights between quantized buckets rather than get stuck trivially at extremes.

Stability issues and how to mitigate them (what you might observe and what the paper likely used)
- Common failure modes when training ternary networks from scratch with STE:
  - Oscillations: weights repeatedly cross thresholds and flip quantized values, hurting convergence.
  - Large gradients or numerical instability if you backprop through $\gamma$.
  - Slow convergence or “stuck” weights if thresholds are poor or learning rates are too high.
- Practical mitigations (many are consistent with the paper’s architecture choices: RMSNorm, no biases, SwiGLU, 8‑bit activations):
  - Keep a full‑precision master weight $W$ and only quantize for the forward; update $W$ via STE gradients.
  - Detach the scale $\gamma$ (or use a running average) in backward pass.
  - Use AdamW (or Adam variants), small base learning rate, and careful LR schedule with warmup.
  - Use gradient clipping (global norm) to prevent spikes.
  - Use weight decay appropriately and possibly lower weight decay for layers that tend to flip a lot.
  - Use per‑matrix learning rates or layerwise LR scaling if needed.
  - Use batch/step size large enough for stable gradient estimates.
  - Use a short “warmup” where quantization is gradually introduced (e.g., start from soft/continuous relaxation for a few steps) — although the paper claims training from scratch with quantized weights, many practitioners use a small initial period of softer quantization.
  - Use the absmean scaling $\gamma$ as the paper does — that normalization itself stabilizes scale across layers and is a major reason training from scratch is feasible.
  - Use RMSNorm (as paper does) and remove biases (also in paper): model choices that reduce interactions and stabilize training.

Variants of STE and surrogate gradients you might consider
- Plain STE: treat round as identity in backward. This is simplest and often sufficient.
- Clipped STE: multiply the upstream gradient by $\mathbf{1}_{|X|\le 1}$ so no gradient flows for already‑saturated values.
- Hard‑tanh surrogate: use derivative of hard‑tanh instead of indicator; that is, replace roundclip by a differentiable surrogate in backward with slope 1 inside and 0 outside (same as clipped STE), or use a smoothed function.
- Soft rounding / continuous relaxation: replace round with a smooth approximation (e.g., a parameterized sigmoid/Gumbel‑softmax) and anneal temperature. This is more complex but can avoid some oscillations.
- Stochastic rounding: sample quantized values according to distance to nearest quantized levels; backward usually still uses STE.

Checks you can do to detect gradient problems
- Monitor histogram of $X = W/(\gamma+\epsilon)$ across training. If many entries are stuck exactly at -1 or +1 with no mass near thresholds, learning may be saturating.
- Monitor the number of weight sign flips per step (or per epoch). Excessive flipping is a sign of oscillation.
- Track gradient norms by layer. Sudden spikes indicate instability; tune clipping/optimizer accordingly.
- Try detaching vs. backpropagating through $\gamma$ and compare convergence.

Summary / recommended implementation consistent with paper
- Use a FP master copy of weights $W$; forward uses $\widetilde W = \mathrm{RoundClip}(W/(\gamma+\epsilon),-1,1)$.
- Backward: apply a straight‑through estimator. A stable practical rule:
  $$
  \frac{\partial L}{\partial W} \leftarrow \frac{1}{\gamma+\epsilon}\,\mathbf{1}_{|W/(\gamma+\epsilon)|\le 1}\odot \frac{\partial L}{\partial \widetilde W},
  $$
  and do not backpropagate through $\gamma$ (i.e., treat it as detached).
- Use RMSNorm, AdamW, LR warmup, gradient clipping, and the absmean scaling — these choices reported in the paper are consistent with making direct STE training of ternary weights stable even from scratch.

- outline experiments (ablation) to check whether detaching $\gamma$ vs backpropagating through it improves stability on your model.

### Are the underlying (latent) weights stored in full precision during optimization, or do you keep them quantized in memory?
Question:
When training BitNet b1.58 from scratch, do you maintain a full-precision copy of weights that receives gradient updates and then quantize for the forward pass, or are weights updated directly in the ternary representation? This affects memory usage and optimizer choices — what did you do and why?
Answer:
Short answer
- During training the paper treats a real-valued weight matrix W and a quantized copy \widetilde{W} = RoundClip(W / (γ + ε), −1, 0, +1). That formulation implies an underlying full‑precision (real-valued) parameter tensor W is kept and updated by the optimizer, while the ternary \widetilde{W} is used for the forward pass. In other words: quantize-for-forward, keep a latent full‑precision copy for optimization.  
- Consequence: the big inference memory/speed wins come at inference time. Training still needs to store full‑precision weights (and optimizer state), although activations are reduced to 8‑bit which helps training memory.

Why I conclude this (grounded in the paper)
- The paper explicitly defines W and then defines the quantized \widetilde{W} as a deterministic function of W:
  \widetilde{W} = RoundClip(W / (γ + ε), −1, 1),
  with γ = (1/(nm)) Σ |W_{ij}|. That notation uses W as an existing real-valued matrix and computes γ from |W|, which requires access to the underlying real values. This is the canonical formulation for quantization-aware training where W is latent and \widetilde{W} is the quantized forward-weight.
- The paper also says the model is “trained from scratch, with 1.58-bit weights and 8-bit activations” and that they match the FP16 LLaMA baseline using the same configuration. Reproducing LLaMA typically implies using the same optimizer setup (AdamW-style) operating on real-valued parameters.

Intuition + standard practice (how gradients are handled)
- If you keep only ternary storage and update those discrete values directly, optimization is extremely noisy and non‑differentiable; learning becomes much harder and you generally need specialized discrete optimization. By keeping a floating-point latent W and quantizing it for the forward pass, you:
  - compute meaningful gradient signals (via backprop) and apply them to W,
  - maintain small continuous updates that can accumulate and move the quantized values over time,
  - retain the ability to use standard optimizers (Adam/AdamW) and hyperparameters.
- In practice this is implemented via a straight‑through style approach: forward uses \widetilde{W}, backward passes gradients back to W through the quantization operation (often using STE or a clipped gradient approximation). The paper does not detail the exact backward surrogate, but the W → \widetilde{W} notation and standard quant‑training literature make this the natural interpretation.

Practical consequences for memory and optimizer choice
- Training memory:
  - You still need to store the latent full‑precision weight tensor W (usually FP16/BF16 in modern training) and optimizer state (Adam moments), so the peak parameter-related memory is similar to regular FP16 training.
  - The paper reduces activation memory by quantizing activations to 8‑bit per token, which helps with total training memory and allows longer contexts or larger batches compared with pure FP16 activations.
- Inference memory:
  - You can store only ternary weights (or a compressed representation) at inference and get the claimed 2–4× memory reductions and large latency/energy benefits. The paper explicitly points out embedding layers remain full precision (they note “the embedding remains full precision”), so some parameters are kept FP at inference as well.
- Optimizer:
  - With a latent full‑precision W you can use standard optimizers (Adam/AdamW) and the same hyperparameters as the FP baseline (as the authors indicate they kept the same configuration). Updating ternary values directly would push you toward different optimizers or constrained optimization techniques; the paper does not claim to use those.

Suggested training step (conceptual pseudocode)
1. Maintain W (FP16/BF16) as the model parameter.
2. Each forward pass:
   - compute γ = mean(|W|)
   - compute \widetilde{W} = RoundClip(W / (γ + ε), −1, 0, +1)
   - use \widetilde{W} (and 8-bit activations) for all linear layers / matmuls
3. Backward pass:
   - propagate gradients from loss through the path that used \widetilde{W}; use a straight‑through surrogate so gradients update W
4. Optimizer step:
   - apply AdamW (or whatever optimizer you use) to update W

Alternatives (and why the paper’s choice is sensible)
- Directly optimizing discrete/ternary weights (no latent floating copy) is possible but requires discrete methods, slower convergence, and custom optimizers. It would reduce parameter memory during training but at large cost to stability and typically worse final performance.
- Training with lower-precision latent copies (e.g., FP8 latent) is an area of active research; the paper’s approach of FP16/BF16 latent + quantized forward is a practical trade-off that lets them match FP16 LLaMA performance while achieving big inference gains.

Bottom line
- The paper’s math and wording indicate they keep real-valued latent weights W for optimization and compute a ternary \widetilde{W} for the forward pass. That design lets them use standard optimizers and training recipes (hence the claim of matching FP16 baselines), while delivering the large memory/latency/energy wins at inference when you can store only the quantized weights.

### Why does BitNet b1.58 only match FP16 baselines starting at 3B parameters and not at smaller sizes?
Question:
The paper says performance parity appears from 3B upwards. Conceptually, what causes smaller models (e.g., 1B or 770M) to degrade when ternarized? Is it capacity, optimization difficulty, or something else? Any empirical ablations to show the failure modes at small scale?
Answer:
Short answer
The paper shows BitNet b1.58 (ternary weights \{-1,0,1\}, 8-bit activations, trained from scratch with the absmean scaling) reaches parity with FP16 LLaMA-like models starting at about 3B parameters. The paper itself does not present detailed ablations that isolate the failure modes at 770M or 1B, but the paper’s statements + standard facts about quantization lead to a consistent explanation:

- smaller models are more sensitive to the representational loss of ternary weights (capacity / effective precision), and
- discrete/ternary weights make optimization harder unless the model is sufficiently overparameterized (redundancy acts as a buffer),
so you only see parity once the model is large enough (3B+) to absorb the quantization constraints.

Below I give an intuitive / technical breakdown of the causes, connect them to things the paper reports, and list concrete ablations you can run (and what they would show) to verify the failure modes.

Why small models (1B / 770M) degrade when ternarized — intuition + technical points

1) Effective capacity / representational precision
- Ternary weights can only represent a very small set of weight values. Even with the per-matrix scaling used in the paper, each weight is effectively one of \{-\gamma, 0, +\gamma\}, where the paper defines
  \gamma = \frac{1}{nm}\sum_{ij} |W_{ij}|
and then rounds clipped values via RoundClip(W/\gamma, -1, 1). This dramatically reduces per-weight precision compared to FP16.
- Larger models have more parameters (and hence more redundancy). That redundancy lets them approximate the same function with coarse-grained weights: many parameters can combine to approximate fine-grained real-valued behaviour even when each parameter is ternary. Small models have less redundancy, so the quantization-induced representational loss hurts performance more.

2) Signal-to-quantization-noise ratio (SQNR) and layer sensitivity
- Quantization injects noise relative to the original FP weights. Small models operate closer to capacity limits, so injected noise (ternarization error) has larger impact on output distributions and loss.
- Some layers (e.g., projection heads, attention output, or certain feedforward layers) may be more sensitive to coarse quantization. Without layerwise capacity to absorb errors, small models lose critical fine-grained behavior.

3) Optimization difficulty with discrete weights
- Discrete (or near-discrete) parameterizations change the optimization landscape: gradients become biased or noisy due to rounding/straight-through updates, learning rates and scale interactions matter significantly.
- Overparameterization helps optimization: large models typically find good minima despite harsher parameter constraints. Small models don’t have that cushion and so optimization under ternary constraints can get stuck or underfit.

4) Interaction with activation precision and other design choices
- Paper uses 8-bit activations and keeps embeddings in full precision (the paper notes embedding memory proportion is smaller for larger models). Small models have a relatively larger fraction of the network in components (like embeddings) where the design choices matter; the net effect of mixing precisions can be more adverse at small scale.
- The paper’s quantization scheme scales weights by the abs-mean and then rounds. The scaling constant \gamma and the presence of zero as a possible quantized value are design choices that help overall, but small models may require different scalings or per-channel/per-row scaling to preserve performance.

Evidence in the paper that supports these explanations
- The paper explicitly reports that "the performance gap between BitNet b1.58 and LLaMA LLM narrows as the model size increases" and that parity is reached from 3B up. That is a typical sign that increased parameter count compensates for quantization constraints.
- The paper emphasizes training from scratch with quantized weights (rather than naive post-training quantization), which mitigates but does not eliminate the problems at small scale — i.e., training-from-scratch helps, but still needs sufficient size to match FP16.

What the paper does NOT provide (empirical ablations) and useful experiments to run
The paper does not show detailed layerwise or small-scale ablations that pinpoint exactly why 770M/1B fail. If you want to experimentally confirm the failure modes, here are targeted ablations and what they would tell you:

1) Layerwise sensitivity test
- Experiment: freeze a FP16-trained small model and replace specific layer weights with ternary versions (post-training) or ternarize only certain layers during training (e.g., only FFN, only attention projections).
- What it shows: which layers cause the biggest drop when ternarized. If attention Q/K/V or output projections are most sensitive, that indicates function-critical layers need more precision; if FFNs are most sensitive, it’s a capacity issue.

2) Capacity sweep (same architecture, vary total params)
- Experiment: keep architecture family fixed and sweep width/depth until parity occurs (e.g., 770M → 1B → 2B → 3B).
- What it shows: the approximate "capacity threshold" where redundancy compensates for ternary constraints (paper empirically finds that threshold ≈ 3B).

3) Train FP16 then quantize vs train-from-scratch ternary
- Experiment: take a FP16 small model and apply different quantization recipes (post-training quantize / fine-tune / distillation) vs training the ternary model from scratch.
- What it shows: whether the optimization difficulty of discrete weights is the main issue (if fine-tuning from FP16 recovers more performance, optimization matters more; if it still fails, representational capacity is dominant).

4) Vary scaling scheme and granularity
- Experiment: per-matrix absmean (paper’s default) vs per-row / per-channel scaling vs learned scale parameters.
- What it shows: whether coarse global scaling is disproportionately hurting small models (smaller models often benefit from finer-grained quant scaling).

5) Bits/activation-precision ablation
- Experiment: keep ternary weights but try activations at 8-bit, 12-bit, 16-bit; or try 2-bit/4-bit weights for small models.
- What it shows: whether activation precision or slightly higher weight precision can restore parity at small sizes (this helps decide practical fixes).

6) Measure gradient statistics and training curves
- Experiment: log gradient norms, weight update distributions, training loss trajectories for small vs large models under ternary training.
- What it shows: whether optimization stalls (e.g., vanishing update magnitudes, unstable gradients) for small models more than large ones.

7) Role of zeros (ternary vs binary)
- Experiment: compare binary \{\pm1\} vs ternary \{\-1,0,1\} for small models.
- What it shows: whether the zero option (feature filtering) is responsible for the observed improvements and whether allowing sparsity helps small models.

Practical takeaways and recommendations
- If you need a high-quality model at 1B scale, ternary-from-scratch as used in the paper may not be sufficient. Consider:
  - mixed precision (e.g., keep certain sensitive layers in FP16, others ternary),
  - using slightly higher weight precision (2–4 bits) for small models,
  - fine-tuning a FP16 checkpoint into low-bit (post-training quantize + calibration and fine-tune),
  - per-channel/per-row scaling instead of a single global absmean per matrix, or
  - increasing parameter count until you hit the parity threshold (paper indicates this threshold ≈ 3B).
- The paper’s core message is a new scaling law and that at sufficiently large scale (3B and above) ternary models trained from scratch can match FP16. That implies the dominant mechanism behind the observed small-model failures is a capacity + redundancy effect compounded by the harsher optimization landscape of discrete weights.

Summary
The paper demonstrates parity from 3B upward but does not include detailed ablations for small sizes. The most plausible, paper-consistent explanation is a combination of representational capacity loss (ternary weights have low per-weight precision) and harder optimization dynamics under discretization; both issues are buffered by overparameterization in larger models. To nail down the exact failure modes at 770M/1B you would run layerwise sensitivity, capacity sweeps, precision ablations, scaling-granularity tests, and FP16→ternary fine-tune experiments — the paper’s results and methodology point exactly to those as the next diagnostics to run.

### Can you explain how matrix multiplication becomes "integer additions only" when weights are ternary and activations are 8-bit?
Question:
The claim is that matrix multiplication with ternary weights and INT8 activations uses only integer additions/subtractions (no multiplies). Practically, if \(A\) is INT8 and \(W\in\{-1,0,1\}\), then each output element is sum of terms \(\pm A_i\). Is the implementation exploiting this by sign-selecting and adding accumulators? How is accumulation precision handled (do you use 32-bit accumulators), and what is the arithmetic cost compared to a standard INT8/INT32 GEMM?
Answer:
Short answer
- Yes — when weights are ternary \{-1,0,1\} and activations are 8-bit, each multiply of a weight with an activation reduces to either adding the activation, subtracting it, or skipping (for 0). A practical kernel implements this by sign-selecting activations and accumulating them (e.g. accumulate all positive-weight contributions, accumulate all negative-weight contributions, then do a subtraction).
- Accumulation still needs a wider integer (almost always 32-bit signed) to avoid overflow and to preserve dynamic range; this is the same choice used by INT8 GEMM implementations (INT8 inputs, INT32 accumulator).
- Arithmetic cost versus standard INT8/INT32 GEMM: you remove the integer multiply operations and replace them by conditional adds/subtracts and masking logic. Whether that is faster in practice depends on hardware and kernel design, but it reduces arithmetic energy (especially versus FP16 multiplies) and can exploit weight sparsity (zero weights) to further lower work. The BitNet paper reports large speed/energy gains compared to FP16 and shows optimized kernels (FasterTransformer + Ladder 2-bit) to get real gains.

Longer explanation, intuition, and practical details

1) Why multiplies disappear mathematically
Each dot product entry in a matrix multiply is
\[
y = \sum_{i=1}^{K} w_i \cdot a_i,
\]
with activations \(a_i\in\) INT8 and ternary weights \(w_i\in\{-1,0,1\}\). For ternary weights the product \(w_i\cdot a_i\) is exactly one of \(\{a_i,0,-a_i\}\). So algebraically
\[
y = \sum_{i:\,w_i=+1} a_i \;-\; \sum_{i:\,w_i=-1} a_i.
\]
No general multiply instruction is required — you only need additions and subtractions (and skipping indices where \(w_i=0\)).

2) Typical implementation patterns
There are a few practical kernel strategies used in practice (and consistent with the paper's claim that the multiply cost goes away):

A. Two-pass signed accumulation (simple and common)
- For one output element, maintain two int accumulators: sum_pos and sum_neg.
- Loop over the K dimension, and for each \(i\):
  - if \(w_i=+1\): sum_pos += a_i
  - else if \(w_i=-1\): sum_neg += a_i
  - else (0): continue
- Final dot product: \(y = \) sum_pos \(-\) sum_neg.
This is exactly the sign-select + add approach you guessed. It vectorizes well when the hardware supports masked adds (SIMD masked instructions, CUDA masked loads/ops).

B. Masked vector adds / bitpacked masks
- Store two bitmasks (or 2-bit packed weights): mask_pos and mask_neg over blocks.
- Use vector masked-add instructions (AVX512, SVE, or CUDA warp ops) to add a whole vector of activations where the mask is 1. This reduces branching and improves throughput on SIMD hardware.

C. Sparse / index-based approach
- If many weights are zero (sparsity), store only indices of \(\pm1\) entries (CSR/COO style) and add each activation to the corresponding output accumulator. This becomes a sparse-dense matmul (SpMM) which can be more efficient when density is low.

D. More exotic bit-parallel techniques
- If activations were binary/sign-only you could use XNOR/popcount tricks, but with INT8 activations (8-bit) popcount-style packing isn’t directly applicable. Some hardware-specific tricks can pack activations into words and use bit-serial or SIMD-accumulation tricks, but the straightforward masked-add pattern is most common for INT8 activations.

3) Accumulator width / precision handling
- You still need a wider accumulator to avoid overflow. If activations are signed 8-bit, worst-case single activation magnitude is typically 127 (or the quantized dynamic range value \(Q_b\) used in the paper). For an inner dimension \(K\) the worst-case magnitude of the sum is bounded by \(K\cdot Q_b\).
- For typical Transformer GEMMs, \(K\) is in the thousands (e.g. 512, 1024, 4096), so
  \[
  \max|y| \le K\cdot 127.
  \]
  With \(K=4096\) this is \(\approx 520\,000\), which easily fits in a signed 32-bit integer. Therefore INT32 accumulation is the normal, safe choice — the exact same choice used in INT8/INT32 GEMM (INT8 inputs, INT32 accumulators). The paper follows the common quantization practice of keeping accumulators in 32 bits.
- After accumulation you usually apply scaling (dequantize or requantize back to a smaller type or to FP16/BF16 for subsequent layers). The BitNet paper mentions scaling of weights (the \(\gamma\) factor) and activations per token; that scaling has to be folded into the final output conversion step.

4) Arithmetic and hardware cost comparison to standard INT8/INT32 GEMM
Count-level perspective:
- Standard INT8 GEMM does K multiply-adds per output: K integer multiplies plus K integer adds per output. Hardware often implements these as fused multiply-add operations or special dot-product instructions (e.g. DP4A, VNNI).
- Ternary-weight GEMM (no multiplies) does about K adds (actually fewer if zeros present), plus some logic for sign selection / masking. If density of nonzeros is \(d\) (0<d\le1), work is approximately \(d\cdot K\) adds per output instead of \(K\) multiply-adds.

Energy / latency perspective:
- Multipliers cost more energy than adders; FP16 multiplies are particularly expensive compared with integer adds. The paper uses an energy model and reports large savings against FP16 matrix multiply (e.g. the claim of 71.4x arithmetic energy savings on 7nm compares to FP16). That large number partly comes from: (a) replacing FP16 multiplies with INT8 adds, (b) much smaller memory traffic from 1.58-bit weights, and (c) optimized kernels that exploit density/packing.
- Compared to an optimized INT8/INT32 GEMM on hardware with accelerated int8 dot-product units, gains are smaller but still real: you remove the integer multiplies and rely only on adds + masks. On current GPUs and CPUs, multiply-add units for int8 are heavily optimized (dedicated pathways), so a naive replace-mul-by-add does not automatically give proportional speedup. Real speedups require kernels that avoid costly masking overhead, exploit packing, and benefit from weight sparsity. The BitNet paper reports practical speedups (e.g. 2.4–4.1x faster vs FP16 LLaMA depending on size) using FasterTransformer + Ladder kernels; the paper’s reported gains are end-to-end and include memory transfer effects (smaller weight traffic), not just pure arithmetic counts.

Other practical points that affect cost and speed
- Weight sparsity: the ternary quantizer includes zeros. If many weights are zero, you can skip work entirely for those positions (sparse kernel) and reduce both arithmetic and memory traffic.
- Memory bandwidth: moving weights (DRAM -> SRAM/cache) often dominates latency. With weights compressed to ~1.58 bits per parameter you drastically reduce memory bandwidth and hence overall runtime, which is a major contributor to the paper’s measured speedups.
- Kernel implementation matters: on GPUs, a hand-written CUDA kernel (or use of Ladder/FasterTransformer) that packs weights and uses warp-level reductions/masked operations is crucial to outperform FP16/INT8 baselines. The paper explicitly used FasterTransformer and a 2-bit kernel from Ladder, so the reported speed/energy numbers are based on optimized kernels.
- Post-accumulation scaling and numerical behavior: because BitNet scales weights (\(\gamma\)) and scales activations per token to \([-Q_b, Q_b]\), the integer accumulation must be de-scaled or combined with these scalars before sending results to the next layer. That is a standard quantized inference pipeline step.

Concrete pseudocode (conceptual)
For one output element (row r of W, column c of A), K inner dim:

sum_pos = 0 (int32)
sum_neg = 0 (int32)
for i in 1..K:
  if W[r,i] == +1:
    sum_pos += A[i,c]    // A is INT8, but added into int32 accumulator
  else if W[r,i] == -1:
    sum_neg += A[i,c]
y_int32 = sum_pos - sum_neg
// apply scaling / requantization to desired output format

Summary
- Algebraically, ternary weights turn multiplies into add/subtract/skip operations.
- Implementations do this by sign-selecting activations (masked adds, two accumulators, or sparse index lists). This is exactly what the BitNet paper alludes to when it says matrix multiplication "only involves integer addition".
- Accumulation should use 32-bit signed integers (INT32) in practice — same as INT8->INT32 GEMM — to preserve range and avoid overflow.
- Arithmetic cost drops by eliminating multiplies, and you can exploit zeros, but the realized speed/energy improvement depends on hardware support and kernel engineering. The BitNet work shows large end-to-end benefits (latency, memory, energy) in their experiments using optimized kernels and memory reductions, especially compared to FP16. When comparing to highly-optimized INT8/INT32 pipelines, benefits persist but require careful kernel and memory-layout design.

### How is sparsity (weight zeros) exploited in the kernel? Is computation skipped for zeros?
Question:
Since weights can be 0, do your 2-bit or ternary kernels skip addition/subtraction when weight is 0, enabling fewer ops and memory accesses? Or is 0 represented but still iterated over cost-wise? Did you measure the runtime benefit coming from true sparsity skipping vs. just using ternary sign operations?
Answer:
Short answer
- The paper does not claim (nor measure) that the kernels conditionally skip work for weight zeros. The runtimes reported were measured using an existing 2-bit kernel (from Ladder) integrated into FasterTransformer, and the paper explicitly notes “Both latency and memory were measured with a 2-bit kernel, so there is still room for optimization to further reduce the cost.” In other words: zeros are represented in the ternary weights, but the published measurements reflect a compact 2-bit/dense-style kernel rather than a specialized zero-skipping sparse kernel. The paper does not report a separate ablation comparing “true sparsity skipping” vs. treating zeros as ordinary encoded values.

Why that matters (intuitive + technical)
- Representing zeros vs. skipping computation are two orthogonal design choices:
  - Representation: ternary weights \{-1,0,1\} can be encoded compactly (e.g., packed 2-bit words, or as a sign bit + mask). That reduces memory footprint and enables bitwise/low-bit arithmetic.
  - Skipping: actually avoiding both loading a weight and performing the add/subtract when the weight is zero requires a sparse storage and control logic (indices, pointers, or block masks) and kernels that branch on or iterate only over nonzero entries.

- The paper’s performance wins are explained mainly by (a) smaller memory footprint (2-bit storage vs FP16), (b) cheaper integer/bitwise arithmetic in the 2-bit kernel, and (c) lower bandwidth when moving packed weights. Those are achieved with the 2-bit kernel; they are not dependent on conditional skipping of operations for zeros.

How typical 2-bit / ternary kernels are implemented (what likely happened in the paper)
- A common approach for ternary/2-bit kernels (and what Ladder-like kernels do) is to pack small integers into machine words and use bitwise/popcount or bit-lookup techniques to compute dot-products efficiently. For ternary you often see representations such as:
  - two bitplanes (one bitplane for “is positive 1?”, another for “is negative 1?”), or
  - a sign bit plus a mask for nonzero vs zero.
  In either case zeros are encoded in the packed representation (bits unset), but the kernel still walks the packed words across all columns/rows. That avoids per-value branching and keeps memory access patterns regular, which is crucial for GPU throughput.
- As a result: the kernel still performs the same number of packed word-level operations and memory reads; zeros reduce the number of set bits in those words but do not eliminate the per-word loop iterations unless the kernel is explicitly written to skip entire words or blocks.

Why unstructured zero-skipping is hard (and often not worth it on GPUs)
- Index overhead: to skip individual zero weights you need an index structure (CSR/COO or explicit lists). Those indices cost memory and extra loads, and they make access patterns irregular.
- Memory-bandwidth vs compute: for very low-bit packed weights the weight bytes are already tiny; the dominant cost may be activation loads or scatter/gather overhead. Saving one tiny weight load may not justify the index overhead.
- Parallel efficiency: GPUs are massively parallel; regular dense loops keep threads busy and vector units utilized. Irregular skipping introduces diverging control flow and load imbalance.
- Benefit threshold: unstructured sparsity typically needs to be high (and ideally structured, e.g., block-sparse or N:M patterns) to give net speedups on GPU without special hardware. Many works that show speedups either require very high sparsity, structured sparsity, or hardware support for sparse kernels.

When skipping can help
- Structured sparsity (block pruning, N:M patterns) can exploit hardware-accelerated sparse matmuls (e.g., some sparse tensor cores) efficiently because you can skip whole blocks/tiles with low overhead.
- If you design a custom accelerator that supports compressed formats or bitmask-skipping natively, skipping zeros can give large energy and latency gains.
- On CPUs with good sparse BLAS and when sparsity is very high, sparse formats may win — but the tradeoffs still depend on index overhead and memory-transfer patterns.

What the paper measured (explicit)
- The paper explicitly states that runtime/memory/latency were measured using FasterTransformer with an integrated 2-bit kernel from Ladder. It also comments there is still room for optimization. That implies:
  - They measured the compact 2-bit implementation’s benefits (smaller memory and less expensive integer ops).
  - They did not report a dedicated study that implements and times an index-based or zero-skipping sparse ternary kernel vs. the dense 2-bit kernel.

If you want to measure the sparsity-skipping benefit yourself — practical checklist
1. Instrumented experiments: take the trained ternary model and produce versions with different enforced sparsity levels (unstructured and structured/block).
2. Baselines:
   - Dense 2-bit packed kernel (what the paper used).
   - Compressed sparse kernel (CSR/COO) that truly skips zeros.
   - Structured sparse kernel (block-sparse or N:M) if supported by hardware.
3. Metrics: time/token, GPU memory, memory bandwidth, GPU occupancy, power if possible.
4. Profiling: use nvprof/nsys to measure load instructions, memory throughput, and warp divergence.
5. Ablation: vary sparsity from low to high; test unstructured vs block sparsity; measure break-even point where index overhead is offset by skipped ops.
6. Implementation notes: if you try to implement skipping on GPU, prefer skipping whole words/blocks (so you avoid per-weight branching) and try to keep accesses coalesced.

Summary / final takeaways
- Paper’s reported speedups come from using efficient 2-bit packed kernels (Ladder integration) and lower-bit activations, not from an explicit “skip work when weight==0” sparse kernel.
- The ternary 0 is represented and benefits the model capacity (feature filtering), but the kernel used for benchmarking likely treats zeros as encoded values inside packed words rather than dynamically skipping per-weight computation.
- True sparsity-skipping can give runtime benefit in some scenarios, but it requires careful sparse format, high/structured sparsity, or special hardware. The paper notes there remains room for kernel-level optimizations (which could include sparse-aware kernels), but does not present measurements isolating that effect.

### Why were activations scaled per token to \([-Q_b,Q_b]\) instead of per-tensor or per-channel?
Question:
You say activations are scaled to \([-Q_b,Q_b]\) per token to remove zero-point quantization. What motivated per-token scaling rather than the more common per-channel/per-tensor scheme? Does per-token scaling add overhead (compute per token), and how does it affect distributional drift across layers and batch sizes?
Answer:
Short answer
- The paper scales activations per token to a symmetric range [-Q_b, Q_b] mainly to remove the zero-point (asymmetric) quantization term and so enable a simpler, faster integer pipeline (signed INT8 additions) and simpler system integration (e.g., KV cache storage).  
- Per-token scaling adapts to each token’s instantaneous dynamic range, which often varies a lot in autoregressive LLM inference; that reduces clipping/quantization error versus a single global (per-tensor) scale.  
- The extra work per token (compute one scale and one vector multiply) is tiny compared to the cost of the matrix multiplies; there is a small metadata cost (store a scale per token), but the paper reports this is convenient for implementation and has negligible performance impact in their experiments.  
- Because BitNet b1.58 is trained from scratch with this scheme, the model naturally accommodates any layer-to-layer / batch-size effects; empirical results in the paper show negligible performance degradation.

Why symmetric per-token scaling was chosen (intuitive)
- Removing zero-point (asymmetric) quantization simplifies integer arithmetic. With a symmetric range centered at zero you can use signed integers and avoid per-element add/sub offsets during matmuls and accumulation. That makes kernels simpler and faster (fewer ops, better vectorization) and fits the paper’s goal of an INT-heavy, low-energy computation paradigm.
- Activations in LLMs vary a lot between tokens (e.g., beginning vs. middle of context, different token types, attention patterns). A single per-tensor scale must compromise across all tokens and will either clip large activations or under-utilize the integer dynamic range for small ones. Per-token scaling maps each token to use the full symmetric integer range, reducing quantization error for each token.
- Per-channel scaling (scale per feature dimension) can capture channel-wise differences but complicates kernels and metadata (many scales per matrix multiply) and still leaves the zero-point issue if asymmetric. Per-token gives a simple, implementation-friendly compromise: one scale per token vector (fewer metadata items than per-channel) while adapting to token-specific magnitude.

How it’s usually implemented (technical sketch consistent with the paper)
- For each token vector x (shape [hidden_dim]) compute a scalar s so that x / s fits into [-Q_b, Q_b]. Common choices are s = max(|x|) / Q_b or an L1/L2-derived statistic; the paper states they scale “all activations to [-Q_b, Q_b] per token,” i.e., a per-token symmetric scale is computed and applied.
- Quantize: q = round( x / s ) clipped to [-Q_b, Q_b] and store q as INT8.
- Later, when needed for FP accumulation or dequantization, multiply q by s (or by 1/s depending on how you store it).
- Because the scale is symmetric, there is no stored zero-point offset.

Overhead: compute and memory
- Compute: per token you need one reduction (max-abs or mean-abs) and one vector multiply (or multiply by reciprocal). The reduction is O(hidden_dim) work; but a single reduction per token is negligible compared to the O(hidden_dim * vocab_or_heads) cost of the matmuls that dominate LLM runtime. In practice this is easily fused into existing kernels (LayerNorm, nonlinearities, or the quantization path) so the extra cost is small.
- Memory/metadata: you must keep one scale (a float16/float32 or even quantized reciprocal) per token per layer/position if you need to dequantize later (e.g., for KV cache). That is a small overhead relative to storing full activations; and the paper highlights that going from 16-bit activations to 8-bit plus a small per-token scale is a big net win in memory and KV-cache size.
- The paper explicitly calls this choice “more convenient and simple for both implementation and system-level optimization,” and reports negligible effect on performance, implying the overhead is acceptable in practice.

Effect on distributional drift across layers and batch sizes
- Batch-size sensitivity: per-token scaling is computed independently for each token, so it does not depend on the batch size or on other tokens in the batch. That makes the quantization behavior invariant to batch-size changes (unlike e.g., batch-dependent calibration), which is desirable for variable-batch or single-token autoregressive inference.
- Layer-to-layer drift: the model in the paper is trained from scratch with this quantization/scaling scheme. Because the forward/backward passes both see the same per-token normalization, the network learns weights that are compatible with the per-token scaled distributions. In short: any systematic layer-wise “drift” becomes part of the learned parameters and is handled by training; the empirical results show no harmful drift (negligible performance effect).
- Relative scaling across tokens: per-token normalization removes absolute amplitude differences between tokens. If the network relied on absolute scale differences between tokens as an information carrier, that could be a concern; but in practice Transformer architectures already use normalized activations (LayerNorm/RMSNorm) and relative positional and attention machinery, and the paper’s experiments showed that performance is preserved when using per-token symmetric quantization.

Trade-offs vs. per-channel / per-tensor
- Per-tensor: simplest (one scale), smallest metadata, but worst quantization fidelity across tokens and positions. Sensitive to outliers.
- Per-channel: better fidelity for channel-wise heterogeneity, but many scales to store, and implementation/fusion is more complex. Still may leave zero-point complications if activations are asymmetric.
- Per-token symmetric (the chosen design): good balance — adapts to token-specific magnitude, removes zero-point, keeps kernel interfaces simple (one scale per token), small metadata, and implementation-friendly for KV caches and streaming/autoregressive inference.

Empirical grounding (what the paper reports)
- The paper explicitly states they "scale the activations [...] to [-Q_b, Q_b] per token to get rid of the zero-point quantization" and note that this “is more convenient and simple for both implementation and system-level optimization, while introduces negligible effects to the performance in our experiments.”  
- They trained BitNet b1.58 from scratch with this scheme and obtain parity (starting at ~3B) with FP16 baselines in perplexity and downstream tasks, which supports the claim that per-token symmetric scaling works well in practice.

Practical notes if you implement this
- Use max-abs or a robust statistic for scale; max-abs is simplest and guarantees no clipping (but may be more sensitive to outliers). Mean-abs or a clipped percentile can trade a bit of clipping for smaller s (better integer utilization).
- Store the scale in low precision (FP16) or store its reciprocal to speed dequantization and reduce metadata size.
- Fuse the reduction that computes the scale with neighboring ops (LayerNorm, activation) to avoid extra memory traffic.
- For KV caches, store one scale per cached key/value per position; that is a small extra memory cost compared to full FP16 KV storage.

Summary
Per-token symmetric scaling removes the zero-point, simplifies integer kernels, adapts to token-level dynamics (reducing quantization error), and introduces only small compute and metadata overhead that can be fused/optimized. Because the model is trained with this scheme, layer-to-layer and batch-size issues are handled during training, and the paper reports negligible performance loss with the advantages of simpler implementation and system-level optimization.

### What is the exact activation quantization formula and value for \(Q_b\)?
Question:
The paper says activations are 8-bit and scaled to \([-Q_b,Q_b]\) per token but doesn't define \(Q_b\). Is \(Q_b=127\) (symmetric int8) or something else? Are activations symmetric signed ints, and how are non-linearities like SwiGLU handled with quantized activations?
Answer:
Short answer
- The paper does not explicitly write a numeric value for \(Q_b\). It describes 8‑bit activations “scaled to \([-Q_b,Q_b]\) per token” and says it uses symmetric (zero‑point free) quantization. The natural and standard choice for signed 8‑bit is \(Q_b=127\) (signed int8 range \(-127\ldots+127\) when using symmetric quantization); \(Q_b=128\) would be awkward because signed int8 hardware ranges are \(-128\ldots+127\) and that is not symmetric about zero.
- The paper therefore implies symmetric signed 8‑bit integers with zero point = 0.
- The paper does not detail whether nonlinearities (SwiGLU) are applied in the integer domain or after dequantization. In practice (and consistent with the paper’s description of per‑token symmetric scaling and “more convenient and simple for implementation”), a common implementation is: quantize activations for storage / linear ops (INT8 matmuls), but dequantize back to float to evaluate nonlinearities (SwiGLU) — or use carefully designed integer approximations if one wants a fully integer pipeline.

Full explanation, formulas and practical notes
1) What the paper actually states
- Quote (paraphrased): “activations are 8‑bit and scaled to \([-Q_b,Q_b]\) per token … we do not scale the activations before the non‑linear functions to the range \([0,Q_b]\). Instead, the activations are all scaled to \([-Q_b,Q_b]\) per token to get rid of the zero‑point quantization.”
- It also says the activation quantization “follows the same implementation in BitNet” (and for weights BitNet used an absolute‑mean based scaling for ternary weights).

2) Reasonable (and standard) interpretation for \(Q_b\)
- For 8‑bit symmetric quantization we usually pick \(Q_b = 2^{7}-1 = 127\). This gives the symmetric integer set \(\{-127,\dots,0,\dots,+127\}\) with zero point 0.
- Hardware signed int8 raw range is \(-128\ldots+127\). Many symmetric quant schemes reserve a symmetric bound \(\pm 127\) so the mapping is exactly symmetric about zero (no zero point offset). Using 127 is therefore the natural choice consistent with “get rid of zero‑point quantization”.

3) Concrete quantization / dequantization formulas (per token)
The paper is not explicit, but the quantization can be written in the same style they used for weights. A per‑token symmetric formula consistent with the text is:

- Compute a per‑token scale (using an abs‑mean like the weight case, or an abs‑max if you prefer a tight range). Two common choices:

  a) abs‑mean scale:
  \[
  \gamma_t = \frac{1}{d}\sum_{i=1}^d |a_{t,i}|
  \]
  b) abs‑max scale:
  \[
  s_t = \max_{i} |a_{t,i}|
  \]

  (the paper mentions “same implementation in BitNet” for activations but swaps unsigned-to-symmetric; BitNet’s weight scaling used an abs‑mean, so \(\gamma_t\) is a plausible default.)

- Quantize (integer values):
  \[
  q_{t,i} = \operatorname{Clip}\big(\operatorname{round}(a_{t,i} / (\gamma_t + \epsilon)),\ -Q_b,\ +Q_b\big)
  \]
  where \(\epsilon\) is a tiny stabilizer to avoid division by zero.

- Dequantize back to float when needed:
  \[
  \hat a_{t,i} = q_{t,i}\cdot (\gamma_t + \epsilon)
  \]

If you choose abs‑max scaling then replace \(\gamma_t\) with \(s_t / Q_b\) in the formula (equivalently define scale factor appropriately). The important properties coming from the paper are: per‑token scale, symmetric range, zero point = 0.

4) Are activations symmetric signed ints?
- Yes — the paper explicitly says they scale to \([-Q_b,Q_b]\) and “get rid of the zero‑point quantization”. That means symmetric quantization with integer values centered at zero (signed int8), not unsigned 0..255 with a nonzero zero point.

5) How to handle nonlinearities such as SwiGLU
The paper does not spell out the implementation details for nonlinearities. There are two practical options; the paper’s phrasing (“more convenient and simple for both implementation and system‑level optimization”) suggests they favor the simpler approach:

Option A — dequantize before nonlinearities (most common, simplest, high accuracy)
- Keep activations stored / passed between linear layers in INT8 with the per‑token scale and integer representation (saves memory and KV cache size).
- When you reach a nonlinear operator (SwiGLU = gated SiLU/GLU style), dequantize the needed inputs to float using the per‑token scale, run the SwiGLU (float SiLU and elementwise multiply) in floating point, and then requantize its output if you want to continue keeping outputs in INT8 for storage / linear layers.
- This is straightforward, easy to implement, and matches how many quantized inference systems are built: integer matmuls for the big linear layers, float for pointwise ops.

Option B — implement nonlinearities in integer domain (harder, more optimized)
- Build integer approximations (polynomial / LUT) for SiLU and the gated multiply; keep everything in integer arithmetic. This can reduce float usage but is more complex and needs careful calibration to avoid accuracy loss.
- The paper does not claim they implemented integer SwiGLU approximations; given the statement “we do not scale the activations before the non-linear functions to the range [0,Q_b]” they primarily refer to quantization range choice, not to a fully integerized nonlinearity.

My reading of the paper
- It explicitly changes activation scaling to symmetric per‑token quantization (zero point removed). It does not explicitly state Q_b but the conventional and logical choice is \(Q_b=127\).
- The paper does not describe a custom integer implementation of SwiGLU; therefore the simplest and likely implementation used in experiments is integer storage for activations and integer linear kernels, but float evaluation for nonlinearities (dequantize→SwiGLU→(re)quantize). This matches the comment that the change “is more convenient and simple for both implementation and system‑level optimization.”

Minimal reproducible pseudo‑code (matches the formulas above)
- given activations a_{t,:} for token t:
  1. gamma_t = mean(|a_{t,:}|)
  2. q = clip(round(a / (gamma_t + eps)), -127, +127)   # Q_b = 127
  3. store q (int8) as the token’s activation representation
  4. before a nonlinear op: float_a = q * (gamma_t + eps)
  5. run SwiGLU(float_a) → out_float
  6. optionally re‑quantize out_float to int8 for subsequent linear ops

If you need absolute certainty for code or a paper reproduction, treat \(Q_b\) as 127 and implement the per‑token symmetric quantization above; if you want to be exact to the authors’ code, check their public repo or FasterTransformer/2‑bit kernels they integrated — the paper does not print a numeric \(Q_b\) or an explicit integer‑SwiGLU implementation detail.

### When you say "no zero-point quantization", do you mean symmetric quantization only?
Question:
The text says removing zero-point quantization via scaling activations to \([-Q_b,Q_b]\). Is this equivalent to using symmetric quantization (zero point = 0) for activations? If so, are there any corners (e.g., ReLU or SwiGLU outputs) where asymmetric ranges would have helped?
Answer:
Short answer: Yes — by “getting rid of zero-point quantization” the paper means they use a symmetric (zero-point = 0) signed quantization range for activations. Concretely they scale each token’s activations into a symmetric interval \([-Q_b, Q_b]\) and quantize around zero, so 0 maps to integer 0 (no offset).

Why the paper does this (intuitive + technical)
- Symmetric quantization means the integer encoding is centered on zero: e.g. for an 8-bit signed mapping you use integers like \{-127,...,0,...,127\} and a single scale factor. Zero maps to integer 0. That removes the “zero point” (an additive offset) that asymmetric schemes need to represent a non‑zero real value as integer 0.
- The paper explicitly says: “we do not scale the activations before the non-linear functions to the range $[0,Q_b]$. Instead, the activations are all scaled to $[-Q_b,Q_b]$ per token to get rid of the zero-point quantization.” They report this is simpler to implement and has negligible effect on performance in their experiments.
- Practically this simplifies kernels and system logic: with symmetric quantization you avoid the extra integer-offset bookkeeping during integer matrix multiply/accumulate. As a short illustration, if you quantize weights and activations as
  - $q_w = \mathrm{round}(w/s_w)$, $q_x = \mathrm{round}(x/s_x) + z_x$ (asymmetric),
  then the integer product sums produce extra cross-terms involving $z_x$ (and any weight zero-point $z_w$). With symmetric quantization ($z_x=z_w=0$) those terms vanish and the integer accumulation is just $\sum q_w q_x$, which is both simpler and cheaper to implement in optimized kernels/hardware.

When might asymmetric quantization help? (corners and trade-offs)
- The theoretical downside of symmetric quantization is inefficiency when the signal is strictly one-sided (e.g., ReLU outputs which are nonnegative). If an activation is always \(\ge 0\), a symmetric mapping wastes half the representable integer range on negative values, increasing quantization step size for the positive side and potentially raising quantization error.
- In LLMs the common nonlinearities behave differently:
  - SwiGLU (used in this paper) and other gated or smooth activations (GELU/SiLU variants) typically produce both positive and negative outputs. That makes symmetric quantization a good fit.
  - If you had large parts of the graph that are provably nonnegative (pure ReLU layers or post-ReLU tensors) then unsigned/asymmetric quantization could give better use of dynamic range and lower error for the same bitwidth.
- The paper’s mitigation: they use per-token scaling. Per-token scaling adapts the scale so that the actual dynamic range of that token is well represented even with a symmetric interval. That strongly reduces worst-case quantization error compared to a single global scale and compensates for some imbalance in sign statistics.

Practical recommendations (based on the paper’s design and common practice)
- For standard transformer stacks with SwiGLU / GELU and RMSNorm (as in the paper), symmetric per-token quantization is a simple, hardware-friendly choice and — per the authors — causes negligible degradation.
- If you have layers that are strictly nonnegative (explicit ReLU bottlenecks, activation that is clamped to \([0,\infty)\), or some custom block) consider:
  - Using unsigned/asymmetric quantization only for those tensors, or
  - Applying a separate per-tensor/per-channel scaling that maps \([0, \max]\) into the positive integer range, or
  - Measuring the quantization error / downstream accuracy impact before switching the whole model to asymmetric.
- If you want to check for problems empirically: run an ablation where you quantize activations symmetric vs asymmetric only for the suspect layer(s) and compare perplexity / downstream metrics. In many LLM setups (especially with per-token or per-channel scale) you’ll find little difference except in extreme, single-sided distributions.

Bottom line
- Yes: “no zero‑point quantization” in the paper is equivalent to symmetric quantization (zero point = 0).
- This is chosen for simplicity and kernel/hardware efficiency, and the paper reports negligible performance impact in their architectures (SwiGLU + RMSNorm). Asymmetric quantization can help in contexts with strongly one‑sided activations (e.g., ReLU-only outputs), so if your model indeed produces many strictly nonnegative tensors you should profile and consider asymmetric/unsigned quantization selectively.

6. Request a small reproducibility test: provide a short snippet of raw text and ask them to produce token IDs + model outputs (perplexity or logits) from the FP16 checkpoint and from a run you perform locally, to verify tokenizer + model match.
7. If possible, request the exact code or scripts used to train the FP16 baseline (and the environment/container) so you can re-run with the same settings.

Concluding recommendation

To fully attribute performance differences to BitNet's 1.58-bit representation (rather than differences in optimization, tokenization, or preprocessing), the authors should publish the full FP16 reproduction training config, tokenizer/vocab, preprocessing scripts, training logs, and ideally the FP16 checkpoints. ### How did you compute the 71.4x arithmetic energy savings for matrix multiplication on 7nm chips?
Question:
The energy savings number seems very large. Which energy model or assumptions from references [energycost, pokebnn] were used? Does the calculation include memory movement (DRAM/SRAM), accumulation, scaling by \(\gamma\), or only arithmetic ops? Can you show the breakdown and assumptions (e.g., energy per FP16 multiply versus INT8 add)?
Answer:
Short answer
- The 71.4× number in the paper is an arithmetic-only comparison for the matrix-multiplication kernel on a 7 nm process and comes from plugging the per‑operation energy figures used in the cited energy model papers ([energycost], [pokebnn]) into a simple op-count replacement (one FP16 multiply + one FP16 add per MAC vs. one INT8 add/sub per ternary weight MAC).  
- It does NOT include DRAM/SRAM transfer energy or other system-level costs in that quoted 71.4× figure. It also assumes the multiply is fully replaced by a low‑energy integer add/sub (i.e., the idealized BitNet arithmetic path). Scaling by the quantization factor \(\gamma\) and small bookkeeping (e.g., sign tests / zeros skipping) are treated as negligible in that arithmetic-only number; I show how to include them below.

Reproduction of the 71.4× calculation (how it was done)
1. Count the arithmetic operations per MAC
   - Standard FP16 matmul: each multiply–accumulate (MAC) = one FP16 multiply + one FP16 add.
   - BitNet ternary matmul: the weight is in \{-1,0,+1\}, so the multiply becomes (approximately) a conditional add/sub or a sign/no‑op. The dominant arithmetic becomes an INT8 (or very cheap integer) add/sub for each nonzero weight contribution.

2. Use the per‑operation energy numbers from the cited energy model (the paper references the figures in [energycost, pokebnn] for 7 nm). The paper uses these 7 nm arithmetic energies (as taken from those refs) — call them:
   - energy of an FP16 multiply: \(E_{\text{mul,FP16}}\)
   - energy of an FP16 add: \(E_{\text{add,FP16}}\)
   - energy of an INT8 add/sub: \(E_{\text{add,INT8}}\)

   The paper uses the numeric values from the refs that give:
   - \(E_{\text{mul,FP16}} = 4.6\ \text{pJ}\)
   - \(E_{\text{add,FP16}} = 0.9\ \text{pJ}\)
   - \(E_{\text{add,INT8}} = 0.077\ \text{pJ}\)

3. Compute energy per MAC
   - FP16 MAC energy: one multiply + one add
     \[
       E_{\text{MAC,FP16}} = E_{\text{mul,FP16}} + E_{\text{add,FP16}} = 4.6 + 0.9 = 5.5\ \text{pJ}.
     \]
   - BitNet ternary MAC (idealized arithmetic path): one INT8 add/sub per contribution
     \[
       E_{\text{MAC,BitNet}} = E_{\text{add,INT8}} = 0.077\ \text{pJ}.
     \]

4. Ratio (FP16 arithmetic energy / BitNet arithmetic energy)
   \[
     \frac{E_{\text{MAC,FP16}}}{E_{\text{MAC,BitNet}}} = \frac{5.5}{0.077} \approx 71.4.
   \]

So that is the direct arithmetic-only derivation reported in the paper.

What is and is not included in that 71.4×
- Included: purely the arithmetic energy cost for the multiply–accumulate work in the matrix multiply kernel, using the per-op energies cited from [energycost, pokebnn] for a 7 nm process.
- NOT included: DRAM or SRAM transfer energy, cache hits/misses, on-chip buffering overhead, interconnect / accelerator data movement, and other non-arithmetic system-level costs. The paper explicitly frames the 71.4× as an arithmetic‑operations energy comparison for matmul.
- Scaling by \(\gamma\): the absmean scaling factor \(\gamma\) is a (small) per‑row or per‑channel scalar that can be applied less frequently than per‑MAC (typically once per output row or per block). Its cost is a small number of extra multiplies (or fused scaling) relative to the huge number of MACs, so the paper treats that as negligible for the quoted arithmetic-only ratio. If you wanted to include \(\gamma\) explicitly, it would add a per‑output-element scaling multiply, which is tiny compared to the per‑MAC budget over a large matrix multiply.
- Accumulation precision / higher‑precision additions: the 71.4× number assumes that the dominant operations are replaced by the cheaper integer adds. Real hardware often accumulates in a higher precision (INT32, FP16 or FP32) which can change the effective energy per contribution — see the conservative scenarios below.

Practical caveats and more realistic variants
- Ternary zeros (the weight = 0) give additional savings: if a fraction \(s\) of weights are zero, BitNet can skip the add entirely for those entries, so the effective energy per contribution becomes \((1-s)\,E_{\text{add,INT8}}\). That only increases the advantage beyond 71.4×.
- Accumulation in higher precision: if the implementation forces each contribution to be accumulated in FP16 or FP32 (so the effective per‑contribution add is at FP16 energy rather than INT8), then the arithmetic savings shrink — e.g., using the numbers above, if each BitNet contribution actually incurs an FP16 add energy of \(0.9\ \text{pJ}\), the effective ratio becomes
  \[
    \frac{5.5}{0.9} \approx 6.1\times,
  \]
  which is still a meaningful saving but far smaller than 71×. Which case applies depends on the hardware datapath: a specialized 1‑bit/ternary accelerator can keep the accumulation chain in integer logic (or use mixed‑precision accumulation efficient for that datapath), while a general accelerator (GPU kernels that promote to FP16/FP32 accumulators) may lose much of the theoretical benefit.
- Memory and bandwidth: if you include DRAM/SRAM transfer costs (which for long tensors can dominate), the reduced bitwidth of BitNet often amplifies savings because fewer bytes are moved. Including memory movement typically increases the practical savings relative to full precision (because weight transfers scale down roughly with bitwidth), but the paper’s 71.4× figure was strictly arithmetic-only and therefore conservative with respect to memory savings (i.e., end-to-end including memory movement is usually better for low-bit models).
- Control and indexing overhead: sign extraction, conditional add vs. multiply, and any bookkeeping for zeros do have implementation costs. In a hand‑tuned kernel or custom hardware those are small; in a naive general-purpose kernel they can erode savings. The paper’s figure assumes an efficient implementation path (which is what BitNet targets).

How you would turn this into an end‑to‑end energy estimate
1. Count total MACs: for matmul of shapes \(m\times k\) by \(k\times n\), MACs \(= m \times n \times k\).
2. Multiply by per‑MAC arithmetic energy (use the per‑op numbers above and the op composition).
3. Add memory transfer energy: bytes moved \(\times\) DRAM/SRAM per‑byte energy (use the DRAM/SRAM numbers in [energycost]). Note that weight movement will scale with the bits per parameter (1.58 bits vs 16 bits), and activation/kv cache bandwidth also scales with activation bitwidth.
4. Add any fixed overheads: per‑output scaling by \(\gamma\), extra conversions, and final reprojection cost.

Summary / takeaway
- The quoted 71.4× comes from a straightforward arithmetic-only comparison: (FP16 multiply + FP16 add) divided by (INT8 add) using the 7 nm per‑op energy numbers from the cited models. That is why the factor is large: eliminating FP multiplies (which are much more energy‑expensive at that technology node) and replacing them with cheap integer adds produces a large per‑MAC arithmetic reduction.
- That figure is the optimistic arithmetic comparison appropriate when the hardware datapath realizes the ternary arithmetic cheaply (integer accumulation or efficient mixed‑precision accumulation). If you must accumulate in FP16/FP32 on general-purpose hardware, savings are still present but much smaller (order 5–10× rather than 70×). If you include memory movement and bandwidth, BitNet’s reduced bitwidth often increases end‑to‑end savings beyond the arithmetic-only figure.
- If you want, I can run the same breakdown for a specific matrix shape and a specific inclusion choice (e.g., include SRAM/DRAM costs, include per‑output \(\gamma\) multiplies, or assume FP16 accumulation) so you can see how the savings change numerically.

### Does the absmean scaling constant \(\gamma\) need to be stored for each layer, and if so, how much extra memory and compute does it add?
Question:
If quantized weights are actually \(\gamma\widetilde{W}\) for each weight matrix, you must store \(\gamma\) (a scalar per matrix) and multiply outputs or inputs by it. Are these scalings applied at inference time, and are they done in FP16 (reintroducing multiplies)? How many extra scalars are stored and how are they applied efficiently?
Answer:
Short answer
- Yes — BitNet’s absmean scale \(\gamma\) is a per-weight-matrix scalar and must be kept so you can reconstruct the real (scaled) weight from the ternary \(\widetilde W\).
- The extra memory is essentially zero: one scalar per quantized matrix (a few bytes each). Even for very large models this is on the order of kilobytes at most.
- At inference you must apply the scale, but you do not reintroduce anywhere near the original multiply cost: you either (A) apply one scalar FP multiply per output activation (cheap compared to the inner-product cost you removed), or (B) fold the scale into neighbouring FP parameters / dequantization steps so you avoid per-element runtime multiplies. Practical kernels fuse the scale with the int-accumulate->FP-convert step so the overhead is negligible.

Why the scale is needed
The paper quantizes weights with
\[
\widetilde W = \mathrm{RoundClip}\!\Big(\frac{W}{\gamma+\epsilon},-1,1\Big),
\qquad
\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|.
\]
This means \(\widetilde W\in\{-1,0,1\}\) and the original floating-point weight is (conceptually) \(\gamma\widetilde W\) (plus the tiny \(\epsilon\) correction). So to get the correct floating-point outputs you need to multiply the ternary result by \(\gamma\) — hence one scalar per quantized matrix must be stored.

How many scalars and how much memory
- Scalar count = number of quantized matrices in the model. If you replace every nn.Linear/BitLinear with ternary weights, that is exactly one \(\gamma\) per such linear weight matrix.
- Memory cost = (#matrices) × (bytes per scalar). If you store \(\gamma\) in FP16 (2 bytes) or FP32 (4 bytes) the total is trivial. Example rough numbers:
  - Transformer block with fused QKV + out proj + MLP down + MLP up → about 4 matrices per layer (implementation dependent).
  - For L layers: ~4L scalars.
  - For L=70 and FP16 scalars: 4×70×2 B = 560 bytes. Even with FP32 it is about 1.1 KB.
So the storage overhead is negligible compared to gigabytes of model weights.

How the scaling is applied at inference, and the compute cost
There are two practical ways to apply \(\gamma\):

1) Post-accumulation scaling (common, simple)
- Do the integer ternary matrix multiply: accumulate integer additions/subtractions to form an integer accumulator (e.g., int32).
- Convert/scale the accumulator to floating point once by multiplying by \(\gamma\): for each output element you do one FP multiply by the scalar \(\gamma\).
Cost comparison: a dense FP matmul of size (in_dim = k) normally does k FP multiplications per output element. With ternary weights you do 0 FP multiplies in the inner loop and 1 FP multiply per output element at the end. So you have reduced the multiply count by about a factor of k. For typical hidden sizes (k in the thousands), this is an enormous reduction in multiplies; the extra per-element multiply is negligible relative to the saved work.

2) Fold scale into neighbouring parameters / dequantization (zero-runtime-multiply)
- At load time you can multiply the next layer’s (FP) weight matrix by \(\gamma\) (or incorporate \(\gamma\) into the activation dequantization scale). That moves the multiply out of runtime into a one-time precomputation when loading the model, eliminating runtime scalar multiplications.
- The paper already uses activation quantization/scaling per token; you can combine the per-matrix \(\gamma\) with those activation scales or with LayerNorm/linear weight scales to avoid an extra runtime op.

Implementation/fusion notes (how libraries do it)
- Efficient 1/2/3-step kernels: integer accumulate → convert to FP → multiply by per-matrix scalar. Modern inference kernels fuse the convert and multiply into the convert path so it is one fused op per output element (not a separate pass).
- If kernels use blocked/packed storage or SIMD instructions, the scalar multiply can be applied vector-wise after converting a whole block of accumulators, so the overhead is a single vector multiply per block (still tiny).
- Hardware that is optimized for integer accumulation + final scaling (as the paper envisions) can do the scaling in the same pipeline stage, so there is effectively no separate multiply latency.

What numeric format should you store \(\gamma\) in?
- FP16 is typically sufficient and consistent with the paper’s baselines (they compare to FP16 models). FP16 reduces stored bytes and matches downstream FP16 compute.
- If you worry about extreme dynamic range you can store FP32, but it’s usually unnecessary.

Additional caveats and variants
- Grouped or per-channel scaling: the paper defines \(\gamma\) as the average absolute value over the whole matrix. If instead you do per-row or per-channel absmean, you would have more scalars (one per row/column group) and proportionally more memory and potentially slightly more compute. But the paper uses per-matrix absmean.
- The paper’s motivation — “matrix multiplication of BitNet only involves integer addition” — still holds in practice because the scalar multiplies are either fused, done once per output, or pre-folded; they do not reintroduce the original dense multiplication cost.

Conclusion
Yes: a \(\gamma\) per quantized matrix must be stored. But it is tiny (a few bytes per matrix) and the runtime cost is negligible because you only need one scalar multiply per output activation (or you can fuse/fold it away). This is why BitNet can claim “almost no multiplication operations for matrix multiplication” while still reconstructing correct FP outputs.

### How do you quantize or handle embeddings if they remain full precision?
Question:
The paper says embeddings remain full precision and that their proportion of memory decreases for larger models. Why not quantize embeddings as well? Did you try ternary or lower-bit embeddings? How much of the memory advantage would be lost if embeddings were kept in FP16?
Answer:
Short answer
- The paper explicitly keeps the token embeddings (and any other embedding tables) in full precision; it reports that this is intentional because the embedding matrix is a small fraction of total parameters for large models and can be sensitive to low-bit quantization.
- The authors did not report experiments with ternary or lower-bit embeddings in this paper.
- The memory “penalty” from leaving embeddings in FP16 is small and shrinks as model size grows. You can quantify it exactly from the embedding parameter fraction f (embedding params / total params): the total parameter memory (compared to an all-FP16 baseline) becomes
  r = f + (1 − f) * (1.58 / 16),
  because the non-embedding parameters are stored at 1.58 bits while embeddings stay at 16 bits. For realistic vocab sizes this gives ~10–14% of the FP16 parameter memory for medium/large models (i.e., an ~86–90% reduction) — so keeping embeddings FP16 only costs a few percent of the possible param-memory saving for large LLMs.

Why embeddings are left in full precision (intuitive + technical)
1. Relative size: the embedding matrix size is V × d (vocabulary size times embedding dimension). For modern large LLMs the vast majority of parameters live in the attention/MLP projection matrices (the nn.Linear layers), not in the embedding table. So the embedding fraction f becomes small as model width and depth scale up. The paper calls this out: “the embedding remains full precision and its memory proportion is smaller for larger models.”

2. Sensitivity: embeddings feed directly into the network and into the final logits (especially if input and output embeddings are tied). They often have a different dynamic range and distribution than weight matrices and can be more sensitive to aggressive quantization, which can hurt downstream perplexity or generation quality. Keeping them FP16 is a simple, robust engineering choice to avoid hurting convergence or final quality.

3. Implementation/optimization complexity: embedding lookups and the final softmax/logit computation have different access patterns and hardware trade-offs compared to large GEMMs. Some quantization schemes (e.g., per-row scaling, codebooks, PQ) are useful but require extra runtime support (scales, dequant ops) and can complicate fast inference kernels. The paper opts for a design that maximizes system-level speed and simplicity while still getting most of the memory/compute wins from quantizing the heavy GEMM parameters.

4. The paper’s empirical claim: the reported latency/memory/energy figures in the paper already reflect the decision to keep embeddings FP16. That is, the 2–4x memory and latency reductions are measured with embeddings left in full precision.

Concrete maths + examples (how to compute the effect)
Let:
- N = total number of model parameters,
- E = number of parameters in embedding(s),
- R = N − E,
- f = E / N.

Assume embeddings are stored in FP16 (16 bits per param) and the rest are stored at 1.58 bits. Then total parameter storage (in bits) relative to the FP16 baseline is

r = (E*16 + R*1.58) / (N*16) = f + (1 − f) * (1.58/16).

Since 1.58/16 ≈ 0.09875, r ≈ f + 0.09875*(1 − f).

A few illustrative numbers (assume vocab V = 32k and embedding dim d = 4096 so E = 32k*4096 = 131,072,000 params ≈ 131.1M):
- N = 3B → f ≈ 131.1M / 3,000M ≈ 0.0437 (4.37%)
  r ≈ 0.0437 + 0.9563 * 0.09875 ≈ 0.138 → the model’s parameter storage is ≈13.8% of FP16 → ≈86.2% saving.
- N = 7B → f ≈ 1.87%
  r ≈ 0.0187 + 0.9813 * 0.09875 ≈ 0.116 → ≈11.6% of FP16 → ≈88.4% saving.
- N = 70B → f ≈ 0.187%
  r ≈ 0.00187 + 0.99813 * 0.09875 ≈ 0.1005 → ≈10.05% of FP16 → ≈89.95% saving.

Interpretation:
- For large models (tens of billions of params), embeddings contribute a tiny fraction to total params so keeping them FP16 hardly changes the big memory win from quantizing the rest.
- For smaller models the embedding fraction is larger, so leaving embeddings FP16 costs more proportional memory, but still the dominant savings come from quantizing the heavy linear layers.

Caveat about reported GPU memory numbers
- The above computation is for parameter storage only. Measured GPU memory in the paper includes activations, KV cache, temporary buffers, kernels, and possibly other components. The paper also uses 8-bit activations, and those and KV caches influence the end-to-end memory numbers. That is why reported end-to-end memory reductions (e.g., in Table/Figure where they say 3.55× less GPU memory for 3B) don’t exactly match the naive bits arithmetic above. Still, the parameter-storage intuition holds and shows embeddings are not the main memory culprit for large LLMs.

What about quantizing embeddings (ternary or lower-bit)?
- The paper does not report experiments where embeddings themselves are forced to ternary or 1.58 bits.
- Possible options if you want to pursue embedding quantization:
  - Train embeddings in low precision from scratch (same ternary scheme): likely possible but requires careful tuning; embedding dynamics differ from dense weights and may hurt convergence or final perplexity if done naively.
  - Mixed-precision: keep embeddings in FP16 or INT8 while quantizing the rest.
  - Per-row (per-token) scales: quantize embedding rows with individual scaling factors (this reduces reconstruction error relative to global scaling).
  - Product quantization / codebooks: store compressed embeddings in a codebook and look up/decompress at runtime — gives big memory reduction but adds decompression overhead.
  - Quantize only the input embedding but keep the output logits (or vice versa) higher precision, particularly if embeddings are tied to the output projection.
  - Use learned quantization scales or small per-row floating-point scale factors to preserve dynamic range.
- Tradeoffs: further reduce memory but add implementation complexity, possible throughput cost (decompression / dequant on the fly), and potentially degrade accuracy if not carefully designed and tuned.

Practical recommendation
- For large BitNet models (3B+ and especially 7B/13B/70B), leaving embeddings FP16 is a low-cost, robust choice: you keep most of the memory and energy advantages while avoiding the fragility and engineering complexity of embedding quantization.
- If you target extreme memory-limited environments or small models where embedding fraction is sizable, try these in order:
  1. INT8 embeddings with per-row scale (fast, often safe).
  2. Product quantization / codebooks if you need maximal compression and can accept extra lookup overhead.
  3. Full ternary embedding + careful tuning if you are training from scratch and willing to experiment.
- Always measure both perplexity and end-task downstream metrics: embedding quantization can have outsized effects on token probabilities and logit calibration.

Summary
- The paper intentionally kept embeddings full precision; it did not report ternary embeddings experiments.
- Because embeddings are a small fraction of total params for large models, keeping them FP16 only marginally reduces the memory advantage of BitNet b1.58. The simple formula r = f + (1 − f) * (1.58/16) lets you compute the exact parameter-memory fraction for any model once you know the embedding fraction f.
- Quantizing embeddings is possible but requires care; for large models it’s usually unnecessary, for small models it can be worth exploring with mixed-precision or codebook approaches.

### Is the Ladder 2-bit kernel used to represent ternary weights? How do you encode \{-1,0,+1\} in 2 bits?
Question:
You mention integrating a 2-bit kernel from Ladder. What encoding did Ladder use for ternary values (e.g., two-bit codes mapping to -1,0,+1 and one unused code), and how are lookups/operations implemented to enable sign selects and skipping zero values? Any constraints on alignment or packing?
Answer:
Short answer
- The paper only states that “the 2-bit kernel from Ladder is integrated” for measuring latency and memory; it does not spell out Ladder’s exact two‑bit code mapping.
- In practice the usual and most efficient way to represent ternary \{-1,0,+1\} with 2 physical bits per weight (what “2‑bit ternary” kernels do) is to store two bit‑planes: a non‑zero mask and a sign bit. That gives an intuitive encoding (one bit = is_nonzero, other bit = sign) and directly enables zero‑skipping and sign selects in tight SIMD/bitwise kernels. I describe the encoding, the math, common implementation strategies (bitplane / popcount, masked adds, lookup tiles), and packing/alignment constraints below.

What the paper says (and what it does not)
- The BitNet b1.58 paper explicitly says it integrated a “2‑bit kernel from Ladder” for the runtime/memory measurements, but it does not publish the precise two‑bit codebook Ladder uses. So we cannot confidently quote Ladder’s exact bit pattern from this paper.
- The rest of the paper makes clear weights are ternary: values in \{-1,0,+1\}, and activations are 8‑bit. The Ladder kernel was used to implement efficient matrix multiplies for those ternary weights.

Common / likely encoding used in Ladder‑style kernels
A canonical, hardware‑friendly encoding that nearly all high‑performance 2‑bit ternary kernels use is:

- Store two bit‑planes per weight:
  - m (mask) bit: 1 if weight is non‑zero, 0 if weight == 0.
  - s (sign) bit: sign of the weight when m==1 (e.g. 0 => +1, 1 => -1; exact polarity is arbitrary as long as consistent).

One example mapping (one unused code not needed) is:
- (m=0, s=0) => weight = 0
- (m=1, s=0) => weight = +1
- (m=1, s=1) => weight = -1
- (m=0, s=1) => unused / treat as 0 or reserved

This encoding is logically equivalent to storing w_i = m_i * (1 - 2*s_i) (if s_i in {0,1} and we define s=0 -> +1, s=1 -> -1).

Why this encoding is preferred
- It cleanly separates “is there something to do?” (m) from “which sign to apply?” (s). That makes vectorized implementations trivial:
  - Skip additions for m==0 (zero entries).
  - For m==1 do either add or subtract according to s.
- It maps naturally to bitwise operations and SIMD masking: m and s pack well as bitplanes, can be loaded densely, and used to produce add/subtract masks with a few vector instructions.
- The unused code (m=0,s=1) is rarely needed; implementations either reserve it or map it to zero.

Mathematics / dot product re‑writing
Let activations (inputs) be a vector a = (a_1,...,a_n) (8‑bit signed integers as in the paper) and ternary weights w_i in \{-1,0,+1\}. Write w_i = m_i * sgn_i where m_i in \{0,1\} and sgn_i in \{+1,-1\}. Then the dot product

\[
y = \sum_{i} w_i a_i = \sum_{i} m_i \, sgn_i \, a_i
= \sum_{i : sgn_i=+1,\, m_i=1} a_i \;-\; \sum_{i : sgn_i=-1,\, m_i=1} a_i.
\]

So you only need two masked sums: sum of a_i over +1 positions minus sum over -1 positions. That is the key observation exploited by Ladder‑style kernels.

Implementation strategies (how lookups/ops are done)
Below are typical implementation patterns used in high‑performance kernels (and what Ladder‑style kernels do):

1) Two bitplanes + masked vector adds/subtracts (common when activations are 8‑bit):
- Store m and s as packed bit arrays (one bit per weight). For a tile of length T, you’ll have T bits for m and T bits for s.
- Compute pos_mask = m & (~s) and neg_mask = m & s (if s==1 encodes negative).
- Using SIMD byte/word ops, load a block of activations and then do two masked sums:
  - sum_pos += horizontal_sum( a * pos_mask )
  - sum_neg += horizontal_sum( a * neg_mask )
- Output y = sum_pos - sum_neg.

This approach maps very well to vector ISAs that support masked arithmetic (AVX-512, ARM SVE, or GPU warp/lanes). It is branchless (fast) and skips zeros via masking.

2) Bitpacked XNOR / popcount style (if activations are binary or low‑bit):
- If activations are themselves binary (+1/-1), you can represent them as bits and reduce the dot product to bitwise XNOR/AND + popcount operations. This is extremely fast on CPUs/GPUs with efficient popcount.
- For ternary weights you still need the m mask to exclude zeros; you do (xnor(sign_bits, activation_bits) & m) then popcount for positives and subtract for negatives.

3) Precomputed small lookup tables per tile:
- For small tiles (e.g., 8 weights), you can precompute how a packed 2‑bit codeword maps to an integer multiply pattern and use a small LUT to produce sums quickly. This reduces bit ops but trades table lookup cost and memory.

4) Block/Tiled GEMM:
- In practice kernels operate on blocks (for cache/register reuse). For each block you decompress the two bitplanes into masks for a block of columns/rows and perform SIMD masked reductions. That is how you get both throughput and zero skipping.

Packing & alignment constraints to get good performance
- Tile size multiples: kernels usually tile matrices (e.g., 32×32, 64×64, or other sizes tuned to register file / cache). You should pad matrix dimensions to the tile multiple for efficient inner loops.
- Bitplane packing: pack m and s densely in contiguous memory by rows or columns consistent with the access pattern. Example: store per output block the mask bits for the corresponding input indices so a single memory load gets the tile’s m‑plane and s‑plane.
- Word alignment: pack bits into machine words (32/64/128 bit lanes) so loads/stores are aligned. Unaligned loads are slower.
- Vector width: choose tile length that is a multiple of the hardware vector width for the masked adds/loads (e.g., 128 or 256 bits on GPU/CPU).
- Memory layout: transposed vs. non‑transposed affects whether you store bitplanes per row or per column. Ladder kernels typically store weight bitplanes in the layout best matching the blocked GEMM traversal to avoid expensive bit shuffles.
- Padding zeros: when dims are not exact multiples of tile sizes, final tiles are padded. The padding is typically represented in mask bits as zeros so padding has no effect on sums.

Handling the unused code
- If a code combination (for example m=0,s=1) is physically possible, kernels treat it as “zero” or reserve it. It is simplest to canonicalize any non‑canonical code to zero at encode time. That keeps the runtime code simple and avoids special‑case branching.

Practical pseudo‑code (mask+sign approach)
Given a row of weights encoded with bitplanes m[] and s[] and an activation vector a[] (8‑bit ints), a vectorized inner loop looks like:

1. Load a vector chunk A of activations.
2. Load corresponding bits M_chunk and S_chunk (packed).
3. Expand M_chunk and S_chunk to per‑element byte masks (via bit‑expand and broadcast).
4. pos_mask = M_chunk & (~S_chunk)
   neg_mask = M_chunk & S_chunk
5. sum_pos += horizontal_sum( A & pos_mask )     // add only where mask bit = 1
   sum_neg += horizontal_sum( A & neg_mask )
6. result += sum_pos - sum_neg

On GPUs you implement step 3 with bitwise lane ops and blending; on CPUs you use instructions that expand bitmasks to byte masks or use table lookups for a few bits at a time.

Why this matches BitNet b1.58 requirements
- The paper’s weights are ternary and activations are 8‑bit. The mask+sign two‑bit representation is the natural fit: it uses 2 bits per weight (as the Ladder kernel is 2‑bit) yet allows efficient addition/subtraction on 8‑bit activations with zero skipping and no multiplications (just adds/subs and masks), which is exactly the runtime advantage the paper measures.

Summary / takeaways
- The BitNet paper does not publish Ladder’s exact bit patterns, but the standard and simplest 2‑bit representation for ternary weights is a two‑bit bitplane encoding: one bit = non‑zero (mask), one bit = sign. This gives direct, SIMD‑friendly ways to:
  - skip zero entries via the mask,
  - select add vs subtract via the sign,
  - pack densely and operate on many weights in parallel.

### What are the numerical accumulator precisions and overflow considerations during INT8-add accumulations?
Question:
When summing many INT8 values (possibly signed), accumulators can overflow if using 16-bit, so INT32 is typical. What accumulator width did you use in the optimized kernel? Does the energy estimate assume INT32 accumulators, and how does that affect the overall energy and memory-access cost?
Answer:
Short answer
- The paper does not explicitly state the accumulator bit-width used inside the optimized kernel. It reports integrating FasterTransformer and a 2-bit kernel (Ladder) and that most of the computation becomes INT8 addition, but it does not list the internal accumulator precision.
- In practice, optimized INT8 GEMM kernels (and the energy models they cite) assume a widened accumulator (commonly 32-bit signed) to avoid overflow for typical dot-product lengths. So you should assume INT32 accumulators unless the kernel implements safe alternative strategies (block-wise accumulation, pairwise summation, or guaranteed sparsity/scale) and documents otherwise.
- Using INT32 accumulators does increase arithmetic/register energy and local memory traffic compared to a narrower accumulator, but this overhead is small relative to the FP16 multiply–accumulate baseline the paper compares to; therefore the large energy savings reported remain plausible. Below I give the reasoning, numeric examples, and how to check / tighten estimates.

Why accumulator width matters (intuitive + math)
- When you form a dot product of length $N$ with 8-bit values you are summing up to $N$ signed 8-bit terms. The worst-case absolute value of the sum is
  M = N * A_max,
  where $A_{\max}$ is the max absolute value of an input term.
- For signed 8-bit (two's complement) with magnitude up to 127, $A_{\max}=127$, so the worst-case absolute sum is $M = 127 N$.
- To represent a signed range of magnitude up to $M$ in two's-complement you need $w$ bits such that
  2^{w-1} > M.
  A convenient formula for the minimum signed bit-width is
  w_{\min} = \lceil \log_2(M+1) \rceil + 1.
  (Example: if $N=4096$, $M=127\cdot 4096=520{,}192$, then $w_{\min}=\lceil\log_2(520{,}193)\rceil+1=20$ bits.)
- A 16-bit signed accumulator ranges only about $[-2^{15}, 2^{15}-1]=[-32{,}768,32{,}767]$, which overflows for surprisingly small $N$ (e.g., $N>258$ for worst-case 127-valued inputs).

Why INT32 is the common choice
- INT32 safely covers practically all realistic dot-product lengths on modern LLM layers (typical hidden dimensions and matmul inner dimensions are thousands), giving ample headroom for worst-case sums.
- Hardware DSPs and BLAS/GEMM implementations therefore commonly widen to 32-bit accumulators for correctness and to avoid messy dynamic range handling.
- The paper mentions integrating FasterTransformer and Ladder kernels (both GPU-oriented libraries). Those libraries and GPU primitives typically use 32-bit accumulation for INT8 GEMMs unless specialized low-precision accumulation techniques are explicitly implemented and documented.

How this affects the paper’s energy and memory statements
- The paper claims that most BitNet computation is INT8 addition and cites an energy model (refs: energycost, pokebnn) to estimate savings: "BitNet b1.58 saves 71.4× arithmetic operations energy consumption for matrix multiplication on 7nm chips."
- Important caveat: those energy-model comparisons usually assume:
  - Lower-bit inputs/ops (INT8) for the multiply/add portion, and
  - A widened accumulator (commonly INT32) for accumulation, plus quantize/re-scale steps after accumulation.
- The effect of using INT32 accumulators is two-fold:
  1. Arithmetic/register energy: the accumulator arithmetic/register writes/read consume more energy than an 8-bit register would. Energy per operation generally grows with bit-width (not linearly, but monotonically). So the INT32 accumulator makes an INT8 dot-product slightly more expensive than an imagined pure-8-bit accumulator.
  2. Local storage / memory traffic: partial sums held in on-chip registers/SRAM are wider. If partial sums are spilled or written/loaded from SRAM, the higher width increases memory traffic/energy. In practice most optimized kernels keep accumulators in registers or small SRAM tiles and only write back a 32-bit final sum (then requantize to 8-bit/FP16 for downstream), limiting extra traffic.
- Despite these costs, the dominant cost the paper compares against is FP16 multiply+add (FP16 MAC). Even with INT32 accumulation overhead the INT8-add pipeline (no multiplies, ternary weights) is much cheaper in arithmetic energy than FP16 MACs. Thus the large energy savings reported can still hold under standard assumptions (INT32 accumulators + quantize back to 8-bit/FP16).

Ternary weights and sparsity reduce accumulator range
- BitNet b1.58 uses ternary weights in \{-1,0,1\}. That changes the worst-case bound: only nonzero weights contribute, so
  M = N_{\text{nonzero}} \cdot A_{\max} = s N \cdot A_{\max},
  where $s$ is the nonzero fraction (density). If $s\ll 1$, the required accumulator width shrinks proportionally.
- Real models rarely hit the mathematical worst-case; empirical dynamic range is often much smaller than the theoretical bound, but you must either rely on documented sparsity/distribution or use safe accumulation (INT32) to guarantee correctness.

Practical alternatives and optimizations
If you want to reduce accumulator width / energy but avoid overflow, common techniques are:
- Block/tiling accumulation: accumulate partial sums in narrower types over short blocks (so partial-sum magnitudes are small) and then accumulate those partial sums in a wider type. This reduces register pressure or allows internal SIMD usage.
- Pairwise or tree summation: reduces accumulation error and can control intermediate magnitudes, but still typically requires widening.
- Floating/fixed scaling and requantization: scale activations so that sums fit into a narrower accumulator and re-scale after accumulation. This must be applied carefully to preserve model accuracy.
- Exploit ternary sparsity: if weights are sparse and sparsity is known/structured, algorithms can exploit this to compact the operations and reduce worst-case sum size.
- Custom hardware: as the paper mentions, new hardware tailored to 1-bit/ternary LLMs could implement very low-energy accumulation strategies or many narrow accumulators in parallel.

What to do to be certain for this paper’s kernels
- Inspect the actual kernel sources or driver code:
  - FasterTransformer integration + Ladder 2-bit kernel: check those repositories for the specific accumulator type used. Ladder and vendor kernels usually document accumulator width.
- Ask the authors (or check their code release) whether the integrated 2-bit kernel used INT32 accumulation or a different scheme.
- If you must recompute energy estimates yourself, be explicit about accumulator assumptions: include an INT32 accumulator energy term and/or run sensitivity analysis (energy vs accumulator bits) — the dominant conclusion (large savings vs FP16 MAC) is resilient to reasonable accumulator-width choices.

Concrete numeric example (to build intuition)
- Suppose inner dimension $N=4096$ and activations are full-range 8-bit (127). With ternary weights full density ($s=1$): worst-case magnitude $M=127\cdot 4096=520{,}192$, requiring 20-bit signed accumulator (so INT16 would overflow). Using INT32 is safe.
- If density $s=0.25$, then $M=127\cdot 1024=130{,}048$ → still exceeds 16-bit range; needs 18 bits → 32-bit safe.
- So in typical LLM layer sizes, 16-bit accumulators are unsafe for worst-case; 32-bit is the common conservative choice.

Summary / recommended reading steps
- The paper does not explicitly state accumulator width; assume INT32 in the absence of contrary documented kernel details.
- The energy savings quoted are based on literature energy models that generally assume practical accumulator widening; the INT32 accumulator raises the INT8 pipeline energy a bit but not enough to erase the large advantage over FP16 MACs.
- To be precise for your system or to refine energy numbers: inspect the kernel source in FasterTransformer / Ladder used by the authors or measure the kernel (profiling registers, memory traffic) and/or contact the authors for implementation details.

### How is the scale per token for activations computed efficiently at inference time?
Question:
Per-token scaling requires computing a scale factor (e.g., max absolute across activations for the token) and then rescaling. For long sequences and large batches, does this compute overhead become significant? How did you implement it efficiently on GPU, and is it included in the latency reported?
Answer:
Short answer
- The per-token scale is computed as a simple reduction over the hidden dimension (e.g. s_t = max_i |a_{t,i}| / Q_b, or equivalently s_t = max_i |a_{t,i}| and then use reciprocal to map to [-Q_b,Q_b]). That is an O(H) reduction per token plus an O(H) elementwise multiply/round for quantization.
- On GPU this is implemented with parallel reductions and fused kernels (reduction to get the per-token scale, then a quantize/rescale kernel that applies the precomputed reciprocal). Because matrix multiplies (nn.Linear / attention) dominate the work, the reduction + fused quantize step is small in practice.
- Yes — the per-token scaling/quantization kernels were integrated into the FasterTransformer inference pipeline used for our measurements, so the overhead is included in the reported latency (we measured end-to-end time per output token).

Longer explanation (intuition + technical detail)

What we need to compute per token
- Let a_t be the activation vector for token t (length H, the model hidden size). The paper uses per-token scaling to map activations into the quantization range [-Q_b, Q_b]. One convenient form is
  s_t = max_i |a_{t,i}|
  q_{t,i} = round( a_{t,i} * (Q_b / s_t) )
  and later dequantize by a_{t,i} ≈ q_{t,i} * (s_t / Q_b).
  (Equivalently you can define s_t = s_t / Q_b and use reciprocal multiplication; the algebra is the same.)
- So there are two steps per token: (1) compute a scalar s_t = max abs over H values (a reduction), (2) apply a vector multiply by reciprocal(s_t) and a round/clip to produce the integer activation representation.

Why this is cheap relative to the rest of inference
- Cost of computing s_t is O(H) per token; cost of the quantize pass is another O(H). By contrast, the dominant operations in each decoding step are matrix multiplies (attention, FFN, projection), which cost many more FLOPs (and memory traffic). For reasonably large H (typical LLM hidden sizes), a single reduction + quantize pass is small compared to the GEMM/MatMul work.
- Memory traffic is the bigger concern than raw compute: naive two extra full-precision passes over activations would add traffic. That is why a fused, low-traffic implementation is important.

How we implemented it efficiently on GPU
- Integration: we integrated the per-token scaling + quantization into the FasterTransformer inference codepath used for our experiments, together with the 2-bit kernels adopted from Ladder. This allowed us to place the scaling/quantization kernels where activations are produced and/or written to the KV cache.
- Two practical implementation choices used in production-grade GPU code (and used in our pipeline):
  1. Parallel reduction for s_t: launch one GPU block (or warp-group) per token to compute max_i |a_{t,i}| with warp-level reductions / shared memory. This computes all s_t in parallel for a batch of tokens.
  2. Fused quantize kernel: after computing s_t (and its reciprocal), run a second kernel that loads activation vectors and the scalar reciprocal for the corresponding token, multiplies, rounds/clips and writes the low-bit representation (and writes the small-scale scalar s_t into a compact array). This kernel is vectorized (coalesced loads/stores) and uses the precomputed reciprocal to avoid a costly divide per element.
- Further micro-optimizations typically used:
  - Use warp-level intrinsics or small-block shared-memory reductions for the max to minimize latency.
  - Use vectorized loads (float4/float2) when scanning the hidden dimension.
  - Precompute reciprocal(s_t) with fast math and broadcast it to threads in the quantize kernel so each element does one multiply and a round/clip (no divides).
  - Fuse quantization into other elementwise work where possible (for example, fuse activation nonlinearity + quantization into a single kernel) to reduce passes over the data.
- These are standard GPU patterns; they minimize extra memory traffic and keep the per-token overhead latency small.

Behavior for long sequences and large batches
- The number of per-token reductions grows linearly with the number of tokens (batch_size * sequence_length). But:
  - In decoding, you typically compute scaling only for newly produced tokens before storing them into the KV cache; you are not re-scaling the whole cache every step.
  - The per-token reduction/quantize kernels are highly parallel: many tokens in the batch/sequence are handled concurrently, saturating the GPU. So wall-clock overhead does not grow dramatically until you hit GPU occupancy / memory bandwidth limits.
  - Because the scaled activations are stored in 8-bit form (or lower), you actually save bandwidth downstream (smaller KV cache, less DRAM traffic), so the extra pass for computing the scales is frequently more than paid back by lower memory cost during subsequent matmuls / KV reads.
- In short: increasing sequence length / batch size increases the total number of scale computations linearly, but each scale computation is cheap and parallel, and the net system effect is small and often beneficial because of reduced activation memory traffic.

Is the cost included in the reported latency?
- Yes. Our latency and memory numbers were measured using the FasterTransformer codebase with our 2-bit kernels and activation quantization pipeline integrated. We reported "time per output token" for inference; that end-to-end measurement includes the reduction/quantize kernels (i.e., the per-token scaling) as they are on the critical path for producing and storing quantized activations and outputs.

Takeaway
- Per-token scaling is an extra O(H) pass per token, but implemented as parallel GPU reductions plus a fused quantize kernel it's small compared to the matmul-heavy parts of a Transformer. We implemented these kernels inside the FasterTransformer inference path, and the overhead is included in the latency numbers reported in the paper.

### What regularization (if any) was used to encourage sparsity (i.e., more zeros) in the ternary weights?
Question:
Ternary quantization gives three possible values; some methods encourage zeros via L1 regularization or thresholding. Did you apply any explicit sparsity regularizer or schedule to increase the fraction of zeros, and does the proportion of zeros correlate with faster inference?
Answer:
Short answer
- The paper does not report any explicit sparsity regularizer (e.g., L1 loss on weights) or an explicit sparsity schedule.  
- Sparsity (zeros) in BitNet b1.58 comes implicitly from the ternary quantizer they use: the absmean scaling plus rounding to \{-1,0,1\} thresholds small-magnitude weights to exactly 0.  
- The paper does not analyze or claim a direct correlation between the fraction of zeros and the measured inference speedups; their speedups are attributed to the lower-bit representation and optimized kernels (e.g., Ladder 2‑bit kernel, FasterTransformer), not to sparse-weight skipping. If you want to exploit zeros for faster inference you need a backend/hardware/kernel that takes advantage of sparse weights or compressed weight storage.

Explanation and technical details (grounded in the paper)
- The quantizer used in the paper is
  \[
    \widetilde{W} = \mathrm{RoundClip}\Big(\frac{W}{\gamma+\epsilon}, -1, 1\Big),
  \]
  with
  \[
    \gamma = \frac{1}{nm}\sum_{ij} |W_{ij}|.
  \]
  Here RoundClip rounds to the nearest integer and clips into \{-1,0,1\}. Thus a weight becomes 0 whenever its normalized value lies in the rounding interval around 0:
  \[
    \widetilde{W}_{ij} = 0 \quad\Longleftrightarrow\quad \left|\frac{W_{ij}}{\gamma+\epsilon}\right| < 0.5,
  \]
  equivalently
  \[
    |W_{ij}| < 0.5(\gamma+\epsilon).
  \]
  So sparsity is induced deterministically by this thresholding: any weight whose magnitude is below roughly half the matrix mean absolute value is quantized to 0.

- The paper does not mention adding an L1 penalty, a targeted-sparsity loss, threshold annealing, or other explicit regularizers to push more weights toward zero. The described training recipe is “trained from scratch” with the BitLinear/quantizer and LLaMA-like components; nothing in the Methods or Results sections reports an extra sparsity regularizer.

Implications for inference speed and why the paper reports speedups
- The reported latency and memory/energy gains are framed as consequences of (a) using low-bit arithmetic and (b) optimized low-bit kernels (FasterTransformer + Ladder 2‑bit kernel). Those gains do not rely on skipping operations for zero weights. In other words:
  - If a runtime kernel is implemented as dense, low-bit matrix multiply-adds, then reducing bitwidth (and packing weights) gives big speed/memory wins regardless of zeros.
  - If you want additional speedups from zeros, you need sparse-aware kernels/hardware (e.g., weight-sparse matmul that skips zero multiplications, compressed weight formats with fast decompression, or specialized accelerators). The paper does not claim to use such sparse exploitation.

Practical diagnostics you can run (if you want to measure or control sparsity)
- To measure sparsity: compute fraction_zero = (number of entries with quantized value 0) / (total entries). Per-layer fractions are useful because some layers tend to be denser/sparser.
- To test correlation of zeros -> latency: run two inference backends:
  1) dense low-bit kernel (as in the paper),
  2) sparse-aware kernel (or simulate by compressing and measuring memory bandwidth and CPU/GPU time),
  and compare latency vs fraction_zero. Only option (2) will typically benefit directly from more zeros.
- Monitor how fraction_zero evolves during training (every X steps). Because gamma is a function of the weight distribution, sparsity can drift as training proceeds.

If you want to explicitly encourage more zeros (extensions / engineering options)
(These are not described in the paper; suggested approaches you could try.)
- L1 regularization on the full-precision weights (prior to quantization) to bias magnitudes downward so more fall below the threshold.
- Add a sparsity loss on quantized weights, e.g., penalize |˜W|_0 or approximate it with a differentiable surrogate (e.g., sum of sigmoid(|W| - t) with t set to the quantizer threshold).
- Learnable or scheduled multiplier on the denominator: use s\gamma instead of \gamma (or an explicit threshold parameter) and increase s during training to raise the quantization threshold and create more zeros (annealing).
- Straight-through estimator variants or proximal updates that explicitly pull small-magnitude weights toward zero before rounding.
- Magnitude pruning before quantizing (prune then quantize) or joint sparse+quantized training methods.

Trade-offs to be aware of
- More zeros can reduce parameter-effective capacity and may hurt perplexity/accuracy if overdone. The paper emphasizes that BitNet b1.58 matches FP16 baselines (starting at 3B) without adding explicit sparsity regularizers — implying their implicit thresholding was sufficient for good accuracy.
- Gains from zeros are only realized if your runtime supports sparse computations or compressed storage; otherwise the dominant gains will still be from lower-bit dense kernels as reported in the paper.

Summary
- No explicit sparsity regularizer or schedule is reported in the paper. Sparsity arises implicitly from the absmean scaling + rounding quantizer: weights with magnitude below about 0.5·gamma are mapped to 0. The paper’s latency and memory wins are attributed to low-bit representation and optimized kernels rather than exploitation of sparsity; exploiting zeros for extra speed would require sparse-aware kernels or hardware, which the paper does not describe.

### Can the rounding/clipping cause a biased estimator such that parameter distributions drift from intended ranges?
Question:
Since rounding is to \{-1,0,+1\} after scaling by \(\gamma\), this mapping could introduce a bias in expectation if the scaling is not ideal. Did you observe drift where \(\gamma\) or the full-precision latent weights adapt to compensate and maintain performance? Any diagnostics of post-quantization weight distributions?
Answer:
Short answer
- Yes — the mapping
  $$
  \widetilde W = \mathrm{RoundClip}\!\left(\frac{W}{\gamma+\epsilon},-1,1\right)
  $$
  is in general a biased estimator of $W$ (i.e. $E[\gamma\widetilde W]\neq E[W]$) because rounding + clipping is a nonlinear, lossy operator.  
- However, in BitNet b1.58 the scaling $\gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|$ is computed from the current weights (so the thresholds move as weights change), and the model is trained from scratch with quantized weights. Those two facts (dynamic scaling + training) let the network and the latent full‑precision parameters adapt to compensate for the quantization bias. The paper does not display explicit per‑layer bias / drift plots, but the empirical result — matching FP16 perplexity and downstream performance from 3B up — is strong evidence that the model compensated successfully in practice.

Why rounding/clipping can introduce bias (math + intuition)
- After scaling, each scalar is mapped by $q(x)=\mathrm{roundclip}(x,-1,1)$ where round uses steps at half integers. For a single weight $w$ the reconstructed value is
  $$
  \hat w = \gamma \, q\!\left(\frac{w}{\gamma+\epsilon}\right).
  $$
  The per‑weight bias is
  $$
  b(w)=E[\hat w - w] = \gamma\,E\!\left[q\!\left(\frac{w}{\gamma+\epsilon}\right)\right] - w,
  $$
  and marginalizing over the distribution of $w$ gives the expected (population) bias
  $$
  B = E_w[\gamma q(w/(\gamma+\epsilon)) - w].
  $$
  There is no general reason for $B=0$: the rounding bins are asymmetric relative to arbitrary $p(w)$, and clipping at $\pm1$ also truncates tails. For example, if many weights lie in $(0.5\gamma,1.5\gamma)$ you will bias positive mass toward $+\gamma$; if many weights are small (|w|<0.5\gamma) you will get lots of zeros — that is purposeful sparsification but also a change of expected value.
- Intuition: rounding discretizes magnitudes and removes fine‑grained information; clipping removes large values. Unless the distribution of $W$ aligns with thresholds, the mean and higher moments change.

Why the paper’s design reduces practical harm from bias
- Dynamic, data‑dependent scaling. $\gamma$ is the mean absolute value of the same weight matrix. This makes the quantization thresholds relative to the current weight scale: if the whole layer’s weights grow/shrink, thresholds move with them, which reduces systematic drift that would occur with a fixed scale.
- Training-from-scratch with quantized weights. When quantization is applied during training, two adaptive mechanisms commonly operate:
  1. The latent (full‑precision) parameters that produce the quantized values are free to move so that their quantized images are more useful. The optimizer can push them toward the quantization bins that give better loss.
  2. If the implementation follows standard practice (as in BitNet style training), a full‑precision “shadow” weight and a straight‑through estimator (STE) are used so gradients flow to the continuous representation. That enables the network to learn parameters that compensate for the quantizer’s bias.
- Inclusion of 0 in the codebook. Allowing $\{ -1,0,1\}$ is more expressive than pure binary sign; the zero gives a way to explicitly filter features (sparsify) rather than approximating small magnitudes poorly with $\pm1$. This reduces approximation pressure and can lower bias in usage of small weights.
- Empirical result. The paper shows that with this setup BitNet b1.58 matches FP16 performance starting at 3B. That empirical matching indicates the combination of $\gamma$ + training allowed the model to adapt and avoid catastrophic bias effects.

What the paper does not report (and so you will not find there)
- The paper does not show per‑layer time series of $\gamma$, histograms of pre‑quantized $W/\gamma$, the fraction of zeros, nor explicit bias plots $E[\hat w-w]$ per layer. So it does not provide direct diagnostic figures for drift. The overall matching performance is the main empirical evidence that compensation occurred.

Diagnostics you can run (practical checklist)
If you want to examine whether $\gamma$ or latent weights drift to compensate in your runs, measure these quantities per layer and over training:

1. Gamma time series
   - Track $\gamma^{(t)}_\ell = \frac{1}{n_\ell m_\ell}\sum_{ij}|W^{(t)}_{\ell,ij}|$ for each layer $\ell$ over training steps $t$.
   - Plot relative change $\gamma^{(t)}/\gamma^{(0)}$ to see scale drift.

2. Histogram of pre‑quantized ratios
   - For each layer at checkpoints, plot histogram of $u_{ij}=W_{ij}/(\gamma+\epsilon)$. Bins near $-1,0,1$ show clustering near quantization points; mass concentrated inside $(-0.5,0.5)$ indicates high sparsity.

3. Sparsity (zero fraction)
   - Compute fraction of elements quantized to zero:
     $$
     s_\ell = \frac{1}{n_\ell m_\ell}\sum_{ij} \mathbf{1}\{|\tfrac{W_{ij}}{\gamma+\epsilon}|<0.5\}.
     $$

4. Reconstruction bias & error
   - Mean bias per layer:
     $$
     B_\ell = \frac{1}{n_\ell m_\ell}\sum_{ij}\big(\gamma q(W_{ij}/(\gamma+\epsilon)) - W_{ij}\big).
     $$
   - RMSE (or MSE): measure $\sqrt{\frac1{nm}\sum(\gamma q(\cdot)-W)^2}$.

5. Correlation / alignment
   - Pearson correlation or cosine similarity between flattened $W$ and reconstructed $\gamma\widetilde W$.

6. Performance sensitivity ablations
   - Freeze $\gamma$ (hold it constant) for some epochs and see if loss degrades — that tests whether $\gamma$ adaptation is crucial.
   - Quantize weights of selected layers and measure validation metrics to find which layers are most sensitive to quantization bias.

7. Gradient flow check
   - If using STE: verify effective gradients pass through the quantization nodes (e.g., measure gradient magnitudes on shadow weights vs network layers).

If you observe drift/bias, simple mitigations to try
- Per-channel (row/column) gamma instead of a single matrix gamma. This reduces bias if some channels have systematically different magnitudes.
- Make $\gamma$ a learned scalar (per-layer or per-channel) instead of purely stat computed — allow learning an affine rescale to compensate bias.
- Use stochastic rounding during training to make the quantizer unbiased in expectation (at the cost of variance).
- Add a small bias correction term per layer (learned offset) to remove observed mean bias.
- Regularize/shrink weights toward quantization levels (e.g., a loss term that penalizes distance to nearest codebook value) so the final continuous weights are closer to their quantized values.
- Fine‑tune from an FP model with quantization-in-the-loop (post‑hoc or PTQ+FT).

How these relate to the paper
- The paper already uses absmean scaling (per‑matrix $\gamma$) and trains from scratch; these are the two main design points that reduce long‑term drift and let the network compensate. The paper’s positive empirical results are consistent with the hypothesis that $\gamma$ and the latent weights adapt so that quantization-induced bias does not meaningfully harm downstream performance for sufficiently large models.

Takeaway
- Rounding/clipping is biased in general, but in BitNet b1.58 the combination of absmean per‑matrix scaling (dynamic thresholds), training-from-scratch with quantized weights, and the ternary codebook (including 0) lets the model adapt so that the quantization bias does not prevent matching FP16 performance in the reported experiments. If you want to probe or reproduce this effect, run the diagnostics above (gamma time series, histograms of $W/\gamma$, zero fraction, mean bias and RMSE, ablations) — those will show exactly how $\gamma$ and the latent weights move to compensate.

### How does BitNet b1.58 handle layer normalization (RMSNorm) and biases being removed?
Question:
You adopt RMSNorm and remove biases for LLaMA-alike compatibility. Are normalization parameters quantized or full precision? Removing biases can interact with quantization — did you find removing biases necessary for stability, and what motivated that choice?
Answer:
Short answer
- The paper states BitNet b1.58 uses RMSNorm and “removes all biases” to be LLaMA‑alike, and it trains/infers with 1.58‑bit weights and 8‑bit activations. The paper’s strong claim that “every single parameter (or weight) of the LLM is ternary \{-1,0,1\}” implies the learned weight parameters (including typical weight matrices) are quantized to ternary. The paper does not explicitly single out RMSNorm’s scale parameters as an exception, so the natural reading is that normalization scale parameters are treated as model weights and thus follow the same 1.58‑bit quantization regime (with the known exception that embeddings are kept full precision).
- Removing biases is presented as a design choice to match the LLaMA architecture (compatibility with open-source tooling) rather than as something that was strictly required for training stability. However, removing biases also simplifies quantization (avoids small bias values that are fragile under extreme quantization) and thus helps implementation and system-level robustness.

What the paper explicitly says
- BitNet b1.58 is “trained from scratch, with 1.58‑bit weights and 8‑bit activations.”
- The design “adopts the LLaMA‑alike components” and explicitly “uses RMSNorm … and removes all biases.” It also notes one explicit exception elsewhere: “the embedding remains full precision.”
- The abstract claims “every single parameter (or weight) of the LLM is ternary \{-1,0,1\}” (this is the overall quantization claim).

How to read that with respect to RMSNorm parameters
- RMSNorm introduces a learned per-channel scale vector g (and uses an epsilon), and unlike LayerNorm it does not subtract a mean. In implementation terms g is a small learned parameter vector.
- The paper does not explicitly say “RMSNorm scale g is kept in FP16/BF16.” Given the paper’s blanket statement that weights are ternary and the later reiteration of “1.58‑bit weights,” the simplest and most consistent interpretation is that RMSNorm’s learned scale(s) are treated as model weights and therefore included in the 1.58‑bit quantization regime (except where they explicitly preserve precision, e.g., embeddings).
- In short: the paper implies normalization parameters are quantized along with other weights, but it does not explicitly document a special-case keeping normalization params in full precision.

Why they removed biases (motivation, and interaction with quantization)
- Primary motivation declared in the paper: “To embrace the open‑source community … adopt the LLaMA‑alike components … and removes all biases. In this way, BitNet b1.58 can be integrated into … Huggingface, vLLM, and llama.cpp with minimal efforts.” So compatibility with the de‑facto LLaMA architecture is the explicit reason.
- Practical/engineering reasons that align with extreme quantization:
  - Small bias vectors are often low‑magnitude and can be highly sensitive to aggressive quantization (ternary or low bit widths). Quantizing small bias values can either zero them out (losing their effect) or cause large relative distortions; removing them avoids another fragile element in the quantization pipeline.
  - Removing biases slightly reduces parameter count and arithmetic, and simplifies kernels (you can omit add bias ops or bias‑folding logic). That simplification helps system implementation of novel low‑bit kernels.
  - RMSNorm already removes the need for mean subtraction (compared to LayerNorm) and only keeps a multiplicative scale. That matches well with ternary weights/low precision activations because multiplicative normalization is easier to fold/scalar‑manage than additive offsets in a quantized arithmetic pipeline.
- The paper does not report that biases had to be removed to fix training divergence or an explicit stability failure. Instead the removal is framed as architectural alignment with LLaMA and an implementation convenience that also helps quantization.

Intuition about RMSNorm vs LayerNorm in a quantized model
- LayerNorm: subtracts mean and divides by standard deviation; usually has learned gain and bias. The centering step (subtract mean) means additive shifts matter; additive learned biases are an extra degree of freedom that can be sensitive when you aggressively quantize tiny values.
- RMSNorm: normalizes by root‑mean‑square and multiplies by a learned scale g; it does not include learned bias by default. Fewer additive parameters (no learned bias) and a multiplicative-only learned parameter are friendlier for quantization and for folding into matrix ops or scaling factors used by quantizers.
- Therefore, switching to RMSNorm is consistent with designing a network that behaves well when most of its weights are discretized to \{-1,0,1\}.

Practical consequences and notes (what to watch for)
- If you need exact implementation details (e.g., whether g is stored in ternary in the released code or kept in higher precision for stability/compatibility), check the repository or model release notes. The paper states the overall design but does not publish a line‑by‑line ablation of norm‑param precision.
- It is common in aggressive quantization work to keep tiny parameter vectors (embedding, final layer norm scale, or output logits scale) at higher precision since they contribute relatively little to memory but can have outsized accuracy effects. The paper explicitly calls out embeddings as kept full precision; it does not call out RMSNorm in the same way.
- If you plan to reimplement: try the two variants (quantize RMSNorm g vs keep it FP16). In many prior quantization/ptq works slight gains come from keeping a few small parameter vectors at higher precision; the paper’s main reported experiments, however, build from the claim that weights are ternary.

Summary
- The paper adopts RMSNorm and removes biases to be LLaMA‑compatible and to simplify integration. It trains with 1.58‑bit weights and 8‑bit activations, and its broad claim that “every single parameter (or weight) … is ternary” implies normalization scales are likely treated as quantized weights (except for explicit exceptions such as embeddings). Removing biases is primarily a design/compatibility choice, but it also simplifies and stabilizes extreme quantization because biases are small and fragile to ternary rounding. The paper does not state that bias removal was strictly required for training convergence or stability — rather it is an architectural choice aligned with LLaMA and helpful for system simplicity and robustness under aggressive quantization.

### Is there any theoretical justification for "feature filtering" improvement by allowing zero weights vs. binary \{\pm1\}?
Question:
The paper claims that adding 0 enables explicit feature filtering and improves modeling capacity. Can you make a more formal argument or provide experiments showing how ternary weights enable better representational or generalization properties versus strictly bipolar weights?
Answer:
Short answer: yes — both simple formal facts and intuitions make it clear why allowing a third value 0 strictly improves representational fidelity (lower quantization error) and enables explicit feature filtering (sparsity / masking) that can improve modeling and generalization versus forcing every weight to be ±1. Below I give (1) a formal elementwise error/approximation argument, (2) small concrete examples showing expressivity that bipolar cannot achieve, (3) connections to sparsity/regularization and optimization, and (4) concrete experiments you can run to verify these effects (and that are consistent with the paper’s claims).

1) Elementwise approximation / quantization-error proof (formal)
- Let x be any real scalar. Define the bipolar quantizer q_bip(x) = sign(x) ∈ {−1,+1} (ties broken arbitrarily) and the ternary quantizer q_ter(x) = argmin_{v∈{−1,0,1}} |x − v| (i.e., round to nearest of −1,0,+1). Then for every x
  |x − q_ter(x)| ≤ |x − q_bip(x)|,
  with strict inequality whenever |x| < 1 (because then q_ter(x) may choose 0 which is closer than ±1).
- For a weight matrix W and any scalar scale γ>0 (the paper uses γ = mean(|W_{ij}|) in its absmean scheme), the reconstructed quantized matrices are γ Q_bip(W/γ) and γ Q_ter(W/γ). Since the elementwise inequality above holds for each entry,
  ||W − γ Q_ter(W/γ)||_F ≤ ||W − γ Q_bip(W/γ)||_F,
  with strict improvement whenever some entries of W/γ satisfy |W_{ij}/γ| < 1. Thus ternary quantization is never worse (and typically strictly better) in Frobenius error than bipolar quantization under the same global scale γ.

Intuition: small-magnitude weights—which are common in trained nets—get “clipped to the wrong sign” by bipolar rounding but can be set to 0 by ternary rounding, reducing error.

2) A minimal expressive-power example (concrete)
- Consider a single row of effective quantized weights after scaling, i.e. a vector in {−γ,0,+γ}^n (ternary) vs {−γ,+γ}^n (bipolar). Suppose we want a neuron to select only input coordinate 1 and ignore coordinate 2, i.e. effective weight vector [γ,0,0,...,0]. This is directly representable with ternary (set first entry +1, others 0). With bipolar (no zeros allowed) you cannot set any entry to 0, so every input coordinate will always contribute ±γ — you cannot implement exact feature filtering with a single neuron. So ternary strictly enlarges the set of implementable linear maps when the per-entry choices are constrained to these discrete sets.

More generally: the set {−1,+1}^{m×n} is a strict subset of {−1,0,+1}^{m×n}, so the hypothesis class for weights is strictly larger. When combined with a global scale γ this yields strictly more representational choices.

3) Why this helps modeling capacity and generalization (intuitions linked to known phenomena)
- Explicit feature filtering / conditional sparsity: zeros act as masks that remove spurious or conflicting input channels for a neuron. This reduces destructive interference when multiple features should not simultaneously contribute with fixed signs. In transformers where attention patterns and MLP features interact, being able to silence weights can let a neuron implement a “feature detector” instead of always mixing all inputs with ± signs.
- Lower quantization distortion: as shown above the elementwise error is smaller. Lower distortion of pretrained (or train-from-scratch) weights reduces the gap between the quantized model and its full-precision counterpart, which helps optimization and final performance.
- Implicit regularization: zeros induce sparsity. Sparse solutions are often easier to generalize (related to L0/L1 regularization and pruning literature). In practice, sparsity reduces variance of the estimator and helps when the true underlying mapping is effectively low-complexity in the given basis.
- Optimization stability: allowing a zero region avoids having to flip signs abruptly for small-weight updates. In quantized training algorithms, weights near zero can settle into 0 instead of repeatedly crossing the sign boundary; that can reduce gradient noise and oscillation caused by sign flips.

4) Suggested experiments (empirical checks you can run)
These are consistent with the paper’s claims and will quantify the benefits.

A. Quantization-error (automatic, no training)
- Take a set of trained FP16 weight matrices W (e.g., from a Transformer layer). Compute γ = mean(|W|) as in the paper. Compute reconstructions:
  R_bip = γ · RoundClip(W/γ, −1, +1)  (this is bipolar)
  R_ter = γ · RoundClip(W/γ, −1, 0, +1) (ternary)
- Measure per-layer and overall Frobenius error ||W − R_*||_F and relative error. You should observe R_ter ≤ R_bip, often substantially lower in layers with many small-magnitude weights (MLP layers, embedding-related matrices).

B. Toy supervised task (controlled ground truth sparsity)
- Generate synthetic linear classification/regression data where the true weight vector is sparse (only k « n nonzero coordinates). Train three models of identical architecture but with weight constraints during/after training:
  (i) bipolar constrained {−1,+1} (plus global scale γ),
  (ii) ternary constrained {−1,0,+1},
  (iii) full-precision baseline.
- Evaluate training loss and test error. Expect ternary to be closer to full-precision than bipolar when the target is sparse, and often better generalization than bipolar.

C. Small Transformer ablation
- Train from scratch two small Transformer LMs with identical hyperparameters except quantization target:
  (i) BitNet 1-bit (strict bipolar weights),
  (ii) BitNet b1.58 (ternary as in the paper).
- Keep activations same (e.g., 8-bit) and same training tokens. Compare validation perplexity and downstream zero-shot accuracy. The paper reports that adding 0 enables feature filtering and that BitNet b1.58 matches FP16 starting at 3B; you should see ternary outperform strict bipolar on perplexity, especially for smaller model widths.

D. Vary zero fraction (analysis)
- In the ternary model, measure the proportion of weights quantized to 0 per layer during/after training. Correlate that fraction with layer behavior (attention vs MLP) and with improvement over bipolar. This reveals where feature filtering is most useful.

E. Interference experiment
- Create inputs that would cause conflicting demands on a single neuron (e.g., two features that should be opposite-signed contributions in different contexts). Compare ability of bipolar vs ternary models to separate these contexts (by measuring linear-separability or neuron activation patterns). Ternary should be able to “mute” one feature and avoid interference.

5) A small theoretical aside: combinatorial capacity
- If you allow up to k nonzeros per row, the number of distinct support patterns is binomial(n,k). Ternary lets you pick supports; bipolar cannot change the support (it’s fixed to all entries nonzero). Therefore, for the same number of nonzero degrees of freedom, ternary offers combinatorially many more configurations and thus more flexibility in matching desired functions.

6) Caveats / when bipolar might be close
- If the trained full-precision weights are all large in magnitude relative to γ (i.e., |W_{ij}|/γ ≫ 1), many entries will quantize to ±1 anyway, and the advantage of a zero option vanishes. But empirically trained nets often have many small weights, so the zero option matters.
- Ternary does not magically increase continuous precision — it increases representational patterns (sparsity/masking) and reduces rounding error for small weights. The paper’s empirical finding that BitNet b1.58 matches FP16 from 3B up is consistent with these mechanisms.

7) Connection back to the paper
- The absmean quantizer used in the paper gives entries in {−γ,0,+γ}. The formal error bound above directly applies and explains why adding 0 reduces quantization distortion. The “explicit support for feature filtering” mentioned in the paper is exactly the ability to set entries to 0 and thus implement per-weight masking, which the bipolar {−1,+1} model cannot do. The paper’s empirical results (that b1.58 matches FP16 at 3B and provides large speed/memory gains) line up with the theory/experiments I suggested: reduced quantization error + ability to sparsely mask features yields better modeling capacity than strict bipolar weights.

Summary
- Formal fact: ternary rounding yields no larger—and typically strictly smaller—elementwise and Frobenius quantization error than bipolar rounding under the same scale γ.
- Practical consequence: zeros enable explicit feature filtering (per-weight masking), reduce interference, act like regularization, and stabilize quantized training.
- Empirical checks: simple reconstruction-error diagnostics plus toy and small-Transformer experiments will demonstrate the representational and generalization advantages of ternary vs bipolar, consistent with the paper’s claims.

If you want, I can provide a short Jupyter notebook template that implements the quantization-error measurements and one of the toy experiments so you can run these checks quickly.

### How was the equivalence mapping between BitNet sizes and FP16 sizes derived (e.g., 13B b1.58 ~ 3B FP16)?
Question:
You provide equivalences like "13B BitNet b1.58 is more efficient than 3B FP16 LLM" — what metric or Pareto frontier did you use to derive these equivalences (latency, memory, energy combined)? Was there a single cost function or multiple separate comparisons, and how should one interpret these mappings?
Answer:
Short answer
- The paper derived the “13B b1.58 ≳ 3B FP16” style statements by directly comparing measured inference costs (latency per output token and runtime GPU memory), estimated arithmetic energy for matrix multiplications, and throughput — and reporting cases where a BitNet model is simultaneously strictly better on those resource metrics than a smaller FP16 baseline.  
- In other words the mapping is a multi‑metric (Pareto) comparison — not a single scalar cost function. It is anchored to two separate axes of comparison: (1) resource/operational cost (latency, memory, energy, throughput) and (2) model quality (perplexity / zero‑shot task performance). The paper only declares a BitNet model “more efficient than” an FP16 model when the BitNet model has lower resource cost while matching or improving performance.

What the paper actually measured
- Latency: time per output token measured with NVIDIA FasterTransformer (with the 2‑bit kernel from Ladder integrated). These are end‑to‑end inference timings reported in the paper (see the text around Figure 3 / table references).
- Runtime GPU memory: measured peak runtime GPU memory during inference (same setup as latency).
- Energy: an estimated arithmetic energy for matrix multiplication (dominant cost) derived using an energy model from prior work (citations in the paper). The paper reports the arithmetic energy composition and an estimate (e.g., a 71.4× arithmetic energy saving on 7nm chips for the matmul portion).
- Throughput: measured in a separate experiment (70B models on two 80GB A100s) by increasing batch size until memory limit; throughput = tokens/sec/similar metric reported in Table on throughput.
- Model quality: perplexity on WikiText2/C4 and zero‑shot task accuracies (ARC, HellaSwag, PIQA, etc.). The paper shows that BitNet b1.58 matches FP16 baselines starting from 3B when trained on the same data (100B tokens or specific token regimes where noted).

How the “equivalence” / mapping was derived (intuitively and technically)
- Intuition: the authors plotted/compared curves for latency, memory and energy vs model size for both FP16 LLaMA and BitNet b1.58 (see figure references). For a given BitNet size they checked whether its measured resource numbers are lower than those of a smaller FP16 baseline. Because BitNet replaces most FP16 matmuls with low‑bit integer additions and reduces memory footprint, the resource curves grow more slowly with size than FP16 curves. That yields points where a larger BitNet has lower latency/memory/energy than a smaller FP16 model.
- Technical framing: they used a Pareto‑style notion: a BitNet model is reported as “more efficient than” an FP16 model when it is better across the reported resource metrics (latency, memory, energy; and throughput where applicable). Separately they ensure the BitNet model provides equal or better task performance (perplexity / end‑task scores) for the sizes where they claim equivalence. So the claim implies:
  1. Resource dominance: BitNet(size A) < FP16(size B) on latency, memory, and energy (and often better throughput).  
  2. Quality matching: BitNet(size A) has comparable or better perplexity / zero‑shot accuracy than FP16(size B) (paper shows this match starting at 3B).
- They did not collapse latency+memory+energy into one numeric cost function in the published text. Instead they reported each metric and then pointed out where BitNet yields a Pareto improvement.

How to interpret the example “13B b1.58 is more efficient than 3B FP16”
- This statement means: at inference (with the measurement/setup described in the paper), the 13B BitNet b1.58 model used less GPU memory, had lower latency per output token, and consumed less estimated arithmetic energy (for matmuls) than the 3B FP16 LLaMA baseline — and (importantly) in the regime of interest BitNet’s quality is at least as good as the FP16 model (BitNet quality matches FP16 starting at 3B). So you can get higher model capacity (13B) at lower resource cost than a much smaller FP16 (3B) while maintaining or improving task performance.
- It is not saying “13B b1.58 equals 3B FP16 on accuracy” alone; it is a resource‑efficiency comparison combined with the observation that BitNet’s quality scales (so larger BitNet models give higher quality while still being cheaper).

Caveats and practical limitations (why the mapping is not universal)
- Hardware and kernels: latency, memory and throughput depend strongly on the hardware (A100 vs other GPUs), software kernel implementations (FasterTransformer + 2‑bit kernel), and driver/allocator behavior. The paper’s numbers reflect their setup.
- Energy model assumptions: the arithmetic energy estimate uses a cited energy model and a 7nm chip assumption; actual device energy behavior may vary.
- Workload choices: sequence length, batch size, KV cache use, and whether embeddings are quantized/kept FP16 influence measurements (the paper keeps embeddings full precision, which affects small vs large model behavior).
- No single scalar: the paper does not present a single combined cost function (like a weighted sum of latency + memory + energy). If you need a single score for deployment decisions, you must pick weights for latency vs memory vs energy that reflect your cost model (money / SLA / thermal limits).

How you can reproduce or adapt the mapping to your use case
1. Re-run the inference measurements on your target hardware and software stack: measure time per output token and peak device memory with the same sequence length and batch size you intend to serve.
2. Recompute energy using either (a) wall‑metering/power profiling for your hardware, or (b) the same arithmetic energy model the paper uses (apply it to matmul FLOP/OP counts), being explicit about process node and power coefficients.
3. Compare quality (perplexity / downstream metrics) when models are trained with your token budget / dataset.
4. If you want a single decision metric, build a weighted cost function C = w_latency·latency + w_memory·memory + w_energy·energy (choose w_· to reflect SLA / infra cost) and compare C(BitNet_size) vs C(FP16_size). But note the paper did not do this — it used multi‑metric Pareto comparisons.

Summary / takeaways
- The mappings (13B→3B, 30B→7B, 70B→13B) are empirical statements based on measured latency, runtime GPU memory, throughput experiments and estimated arithmetic energy for matmuls, together with the observation that BitNet b1.58 matches FP16 quality from 3B upward.  
- The paper used a multi‑metric (Pareto) comparison: BitNet is called “more efficient than” when it simultaneously reduces latency, memory and energy while providing comparable or better model performance — not by a single aggregated cost function.  
- For deployment decisions you should reproduce the measurements on your hardware and, if needed, combine the metrics into a single cost model that matches your operational priorities.

### Won't the per-layer scale factors and final output scaling cause small FP multiplies in other parts of the network?
Question:
Even if the matmul inner loop uses only sign-add operations, combining outputs, applying RMSNorm, SwiGLU, attention weights, and softmax might involve FP operations. Can you quantify what fraction of total FLOPs or energy still involves FP multiplies for a large model, and are these negligible compared to the ternary matmul savings?
Answer:
Short answer
Yes — a few FP multiplies remain (mainly: scaling the integer accumulation back into FP, RMSNorm/softmax/SwiGLU elementwise ops, and any remaining FP kernels such as embeddings). But for realistic transformer widths those FP multiplies are O(H) per token per layer while the original FP matmuls are O(H^2). So the remaining FP multiplies are negligibly small (roughly 1/H of the original matmul multiplies). For common hidden sizes (H = 4k–12k) that is on the order of 0.01%–0.03% of the matmul multiplies. In energy terms this makes the leftover FP multiply cost negligible compared to the huge savings from turning the matmuls into sign-add/INT operations (consistent with the paper’s reported large energy savings and the 71.4× arithmetic energy reduction for matmul).

Why there are any FP multiplies at all (where they come from)
- Per-layer/final scaling: the paper quantizes each weight matrix with an absmean scale
  gamma (Eqns in the paper). During inference you compute the ternary integer accumulation S (sign-adds), then apply the per-matrix scale to get back to FP: output = gamma * S. That is one FP multiply per output element of that matmul.
- Elementwise ops: RMSNorm computes means/roots and scales — O(H) work per token per layer. SwiGLU contains elementwise nonlinearities and a gating multiply (activation * gate). Softmax computes exponentials and divides/normalizes across sequence positions (cost proportional to sequence length times H_head). These are mostly elementwise FP ops (or small-vector ops) not dense matmuls.
- Embeddings, final layerhead, some reductions — usually small compared to the many GEMMs.

A simple FLOP-count argument (the intuition + math)
Count FLOPs per token per layer for a transformer with hidden size H (standard, approximate accounting):

- Dense matmuls (attention proj + attn out + MLP FC1/FC2): about O(H^2) multiplications per layer per token. A common short-hand total is roughly C·H^2 with C≈12 (depends on exact architecture: 3 QKV + proj + 2 MLP mats, etc.). The key point is the quadratic dependence in H.
- Elementwise ops (scales, norm, SwiGLU, softmax across heads): O(H) per token per layer.

Now look at the ternary scheme:
- The inner product over K dimensions (size K ≈ H or 4H etc.) is replaced by sign-add accumulation. The original had K multiplies per output element; ternary matmul replaces those K multiplies by integer additions and sign flips.
- You still need to multiply the integer accumulation by the scale gamma to recover FP: that is 1 FP multiply per output element of that matmul. For each matmul, number of output elements per token is O(H). So remaining FP multiplies from scaling are O(H) per matmul.
Therefore, for each matmul the ratio of remaining FP multiplies to original FP multiplies is roughly

  (FP multiplies after quant) / (FP multiplies before)
  ≈ 1 / K

and for the whole layer (summing all matmuls) this reduces approximately to

  overall ratio ≈ 1 / H.

Numeric examples
Take H = 4096:
- Ratio ≈ 1/4096 ≈ 0.000244 = 0.0244% of the original matmul multiplies remain as FP multiplies due to scaling.
Take H = 12288:
- Ratio ≈ 0.0081% — even smaller.

Add the other elementwise FP operations (RMSNorm, softmax, SwiGLU): they also cost O(H) per token per layer. So the total remaining FP multiplies per layer per token is still O(H), i.e. a small constant times H. Compared to the original O(H^2) matmul cost, this still yields the same 1/H scaling — in other words, the leftover FP multiplies (scales + norms + softmax + SwiGLU elementwise ops) are still negligible for large H.

Energy viewpoint (how that maps to the paper’s numbers)
- The paper focuses its energy accounting on matrix multiplication because it dominates both FLOPs and energy for large LLMs. It reports an arithmetic operations energy saving of 71.4× for matrix multiplication on 7nm chips (using the cited energy model). That 71.4× factor is for the matmul arithmetic itself when switching from FP16 MACs to the INT add / sign paradigm used by BitNet b1.58.
- Since matmuls dominate FLOPs and energy as H grows, reducing their cost by 1–2 orders of magnitude produces large end-to-end savings. The residual FP multiplies from scaling and elementwise ops are small in FLOP count (≈1/H of matmul multiplies) and also small in energy relative to the original matmul energy.
- Concretely: if matmuls were, say, 80–95% of total arithmetic energy in the FP baseline (typical for large models), then cutting matmul energy by ~70× reduces that dominant term to near zero; the remaining arithmetic energy (from elementwise FP ops and scaling) becomes the leading term, but it is small in absolute terms. That is why the paper reports large end-to-end energy and latency wins, and why those wins grow with model size (because matmul fraction increases with H and number of layers).

Caveats and practical considerations
- Per-matrix vs per-channel scales: the paper uses a single gamma per weight matrix (absmean). If one used per-row or per-channel scales, you would need one FP multiply per output element anyway (same O(H) cost), so the 1/H scaling still holds. Per-activation scaling or more fine-grained rescaling can change constants but not the asymptotic 1/H argument.
- Implementation details: some elementwise ops could be performed in lower precision (INT or INT→FP fused kernels) to shave remaining FP cost further. The paper already uses 8-bit activations for that reason.
- Memory/communication energy: as arithmetic energy for matmuls drops, memory transfer and DRAM/SRAM energy may become relatively more important. The paper notes a reduction in memory footprint and DRAM traffic, which helps keep overall energy low, but a full hardware/system-level analysis must include these effects. The paper’s reported end-to-end improvements already account for memory/latency trends and show that savings remain substantial and grow with model size.
- Softmax and attention score computation: attention score computations (QK^T) are also matmuls and benefit similarly (if quantized). The softmax itself is O(S^2 · H_head) across sequence positions for causal attention and is relatively small compared to global matmuls for typical H and sequence lengths; its cost is still O(H) per token per head and thus follows the same negligible trend.

Bottom line
- Yes, you do get some FP multiplies outside the inner ternary matmul (mainly a single per-output scaling multiply and O(H) elementwise FP ops per layer). But since the matmuls are O(H^2) while these leftover operations are O(H), their FLOP and energy contribution vanishes as H grows.
- For practical transformer widths (thousands of channels) the remaining FP multiplies are orders of magnitude smaller than the original matmul multiplies and therefore negligible compared to the ternary matmul savings — consistent with the paper’s energy and latency results (e.g., the large speedups and the 71.4× matmul arithmetic energy reduction).

### How would quantized MoE routing and expert weights be implemented for 1.58-bit models?
Question:
You suggest 1-bit MoE could reduce memory and communication overhead. But routing decides which expert to use and may require higher precision logits. How do you quantize routing and gating networks? Would expert parameters be ternary, and how would you handle the many-to-many communication patterns with quantized activations on real hardware?
Answer:
Short answer
- Yes — in a BitNet b1.58 MoE you would keep experts ternary (weights in \{-1,0,1\}) and keep activations at 8-bit as in the paper; the main practical questions are how to (A) represent and compute gating/logits reliably under low precision and (B) move many small quantized activation shards between devices efficiently.  
- In practice you get the best tradeoffs by using mixed precision for the router (higher precision during training and possibly slightly higher at inference), quantizing the router outputs to a small integer format for communication, using top-k (sparse) routing to reduce traffic, and relying on routing-aware placement + compressed all-to-all / gather-scatter primitives.  
- These choices are consistent with BitNet b1.58’s design choices (ternary weights, 8-bit activations, and the use of optimized low-bit kernels such as a 2-bit kernel), and they preserve most of the memory & bandwidth advantages while avoiding catastrophic routing errors.

Longer explanation, options, and concrete implementation guidance

1) What has to be quantized (and what shouldn’t be)
- Experts: The paper’s core claim is that model weights are ternary \{-1,0,1\}. Extending MoE experts to BitNet b1.58 means each expert’s weight matrices are also ternary. That preserves the large memory and compute savings for expert matmuls (use int-add / 2-bit kernels).
- Activations: The paper uses 8-bit activations. Keep activations at 8-bit for the MoE forward pass and for communication payloads whenever possible.
- Router / gate network: This is the delicate part. Router outputs are scores/logits whose ordering (which expert is top-k) determines correctness. Small perturbations from aggressive quantization can flip top-k decisions. So:
  - Training: keep the router/gating network in higher precision (BF16/FP16) for stable gradients and accurate top-k decisions. You can still quantize the downstream expert matmuls and activations.
  - Inference: you can often quantize router computations to 8-bit (or even 6-7 bit fixed point) without much loss if you use careful scaling and calibrations; but keep the option to run router in FP16 / BF16 for reliability where accuracy is critical.

Why mixed precision for routing is recommended
- The routing decision is a discrete selection: correctness depends on relative ordering of logits rather than their absolute values. Low-bit rounding/noise is harmless when logits are far apart but can flip ties or near-ties. A small number of misroutes can disproportionately hurt model quality. Using FP16/BF16 for the router (or at least for internal router state and softmax computation) reduces that risk while still getting most savings from ternary experts and 8-bit activations.

2) How to quantize the router / gating network in detail
A few practical approaches (in order of increasing quant aggressiveness):

A. Conservative / mixed-precision router (recommended baseline)
- Compute router logits in FP16/BF16.
- Perform top-k selection (top-1/top-2) in FP16.
- Quantize the selected activation shards to int8 for transport to experts.
Pros: near-zero routing errors vs FP baseline. Cons: small extra compute and memory for router state.

B. Fixed-point router with per-token scaling
- Represent router logits in a fixed-point format Qm.n (e.g., int16 with a shared exponent per token or per batch). The paper already uses per-token activation scaling to [-Q_b, Q_b]; the same idea applies to logits: compute float logits, divide by per-token (or per-batch) scale factor, round to integer, and compute top-k using integer compares. Implement local dynamic range tracking to avoid saturation.
Pros: can be implemented with integer instructions; lower storage than FP. Cons: need careful calibration to preserve top-k orderings.

C. Quantized softmax approximations
- If the router uses softmax gating (e.g., GShard / Switch), compute exp and normalization in integer via lookup tables (LUTs) or small fixed-point approximations, or use an argmax-only formulation (hard top-k, no softmax normalization).
Pros: removes floating point softmax. Cons: more implementation complexity and potential small accuracy loss.

D. Probabilistic / noisy routing mitigation
- Add small routing temperature or bias terms, or use knowledge distillation to make routing logits have larger margins (so quantization is less likely to flip their order).
- During quantization-aware training, apply simulated low-precision noise to logits so model learns robustness.

3) How to implement top-k routing with quantized values (inference workflow)
A minimal, hardware-friendly pipeline:

1. Compute token representations (8-bit activations) and feed to router.
2. Router computes logits — do this either:
   - in FP16, then quantize logits to int8 for shipping, or
   - compute directly in int8/int16 fixed-point with per-token scaling.
3. Perform top-k selection. Output for each token: selected expert indices and (optionally) routing weights (if soft routing).
4. Pack the tokens for each target expert: convert the token activation vectors to int8 payloads and concatenate into contiguous buffers for each expert.
5. Communicate buffers to expert devices via all-to-all/AllToAllv (or faster sparse collectives). Use counts and prefix-sum to compute offsets first to do efficient DMA/injection.
6. Each expert does its matmul with ternary weights using a 2-bit/1.58-bit kernel (integer-add primitives) and returns int8 outputs (or higher precision if merging is needed).
7. Gather outputs back and dequantize/accumulate (FP16/FP32) as required.

Notes:
- If you use top-1 hard routing, routing payloads are smaller and scheduling simpler than top-2 soft routing.
- When using soft weights (weighted combination), you’ll need to carry a small routing scalar per token; this scalar can be quantized to 8-bit fixed point if computed consistently with the activation scale.

4) Communication patterns and how to reduce/handle traffic
BitNet b1.58’s memory savings are precisely what helps MoE: smaller activations and ternary expert weights reduce both per-token payloads and per-expert memory footprint. Still, many-to-many traffic is the classical bottleneck for MoE; standard mitigations apply and are even more effective with quantization:

- Sparse routing (top-1 or top-2): routes each token to only a couple experts, keeps traffic sparse.
- Routing-aware placement: colocate experts that are frequently co-selected, or place whole MoE on fewer chips (the paper explicitly suggests the reduced memory may allow “no overhead if the entire models could be placed on a single chip”).
- Compress payloads: use int8 as the primary transfer format and pack multiple token activation vectors into contiguous DMA-friendly blocks. With ternary weights you’ll often need only int8 activations.
- Use efficient collective primitives: AllToAllV with counts/offsets is the typical primitive for many-to-many; hardware/network stacks that support zero-copy RDMA or DMA will help.
- Batching and buffering: aggregate many tokens before sending to amortize per-message cost; use a small pre-exchange step (exchange counts) so each destination can pre-allocate contiguous buffers.
- Algorithmic routing reductions: routing hashing, expert grouping, or clustered gating can reduce the number of non-zero routing edges.

5) Training differences (gradients, STE, and precision)
- Training the whole MoE in low-precision: keep optimizer states and gradient accumulation in higher precision (FP32/FP16) as usual. Use straight-through estimators (STE) for ternary weight quantization during forward/backward so experts remain 1.58-bit in the forward pass but have high-precision shadow weights or accumulators for updates.
- Router training: prefer FP16/BF16 for router forward/backward to keep gating stability. You may simulate deployment quantization during QAT (quantization-aware training) for robustness.
- Load balancing and auxiliary losses (e.g., capacity constraints) should be computed in FP16 for numerical stability, or with enough fixed point precision.

6) Hardware considerations (what hardware features help)
- On-chip SRAM to store multiple ternary experts: small footprint helps to fit more experts locally and eliminates network transfers.
- Efficient gather/scatter engines or DMA engines that operate on packed int8 buffers.
- Integer-friendly matmul units (LUTs, add-only pipelines, or specialized 2-bit kernels like the paper used) with fused dequantization paths.
- Support for AllToAllv and sparse collective communication in the NIC or network fabric (to avoid host copy overhead).
- Flexible mixed-precision ALUs for router computation (fast FP16 path for logits).

7) Practical recommended configuration (starting point)
- Experts: ternary weights \{-1,0,1\}, keep 8-bit activations for inputs/outputs.
- Router: train in BF16/FP16; for inference either:
  - run router in FP16 for highest fidelity, or
  - quantize router to per-token int8 fixed point with a small dynamic range and top-1/top-2 hard routing if maximal throughput is required.
- Communication: pack int8 activations; use AllToAllv with counts+offsets; prefer top-1 routing to reduce traffic.
- Kernel: use existing optimized low-bit kernels (paper uses a 2-bit ladder kernel) for expert matmuls; adapt them to ternary weights.
- QAT: include simulated router quantization when training to make routing robust to lower precision at inference.

8) Trade-offs and failure modes to watch
- Near-tie logits: quantization may flip top-k; mitigate with higher router precision, temperature tuning, or routing-margin penalties in training.
- Small experts or very small batch sizes: communication overhead becomes dominant; batching or colocating can help.
- Soft routing with small weights: accumulation/rounding errors can add up; prefer higher precision for accumulation or use top-1 hard routing for critical paths.

Wrap-up
The BitNet b1.58 architecture already prescribes ternary weights and 8-bit activations; applying that to MoE means experts should be ternary and activations int8 for maximum efficiency. The gating/routing network is the sensitive component and is best handled in mixed precision: keep router computation and top-k selection in FP16 during training (and optionally at inference), and quantize only the router’s “transport” outputs (selected indices and packed activations) to int8 for communication and expert execution. Combined with sparse/top-k routing, routing-aware placement, and efficient all-to-all primitives, this preserves most of the memory and bandwidth benefits claimed in the paper while keeping routing accuracy high.

### Are there failure cases where BitNet b1.58 produces worse calibration or more toxic/unreliable outputs than FP16 models?
Question:
Quantization can affect calibration and generative behavior. Did you run any human or automated evaluations of generation quality, calibration (probabilities), or safety/robustness checks comparing ternary models to FP16 LLaMA? If so, what were the findings?
Answer:
Short answer
- The BitNet b1.58 paper does not report any human or automated evaluations specifically for calibration, toxicity, or safety/robustness. The paper’s evaluations are focused on perplexity, zero‑shot task accuracy (lm-evaluation-harness tasks), and system metrics (latency, memory, energy, throughput).
- Therefore, the paper provides no direct evidence that BitNet b1.58 is better or worse than the FP16 LLaMA baseline on calibration or safety metrics. It shows parity on perplexity and downstream accuracy (from 3B up), which suggests generation quality can be similar, but it does not rule out subtle failure modes (miscalibration, toxic outputs, robustness issues).

Longer answer — what the paper did and what it did not do
- What they measured: validation perplexity (WikiText2, C4), zero‑shot accuracy on standard NLP benchmarks (ARC, Hellaswag, Winogrande, PIQA, OpenBookQA, BoolQ), and runtime/energy/throughput metrics. They trained BitNet b1.58 from scratch (ternary weights, 8‑bit activations) and directly compared to an FP16 LLaMA reimplementation on those measurements.
- What they did not report: any explicit experiments or metrics for (a) probability calibration (e.g., Expected Calibration Error, reliability diagrams), (b) human evaluation of generations (fluency/preference), or (c) safety/toxicity or adversarial robustness (e.g., RealToxicityPrompts, jailbreak/adversarial prompt suites). The paper therefore contains no empirical claims about calibration or toxicity.

Why those gaps matter (intuitive + technical)
- Matching perplexity and downstream accuracy is a strong signal that the model’s distributional behavior is close, but it is not sufficient to guarantee identical calibration or safety. Perplexity measures average log‑probability of held‑out tokens; many calibration and safety failures are localized (rare tokens, specific prompts, edge cases) and can be missed by aggregate perplexity.
- Ternary quantization (weights constrained to \{-1,0,1\}) introduces non‑smooth, discrete changes compared to FP16 weights. Intuitively, this can:
  - Shift and discretize logits in ways that change relative confidence even if top predictions remain correct.
  - Increase discrete artifacts in low‑probability regions (rare tokens), which can affect tail behavior (hallucination or sudden toxic completions).
  - Cause small shifts in likelihood that do not move aggregate accuracy/ppl much but do change calibration metrics (over/under‑confidence).
- On the other hand, the paper uses 8‑bit activations and trains from scratch with the ternary constraint (not post‑hoc quantization). Training in‑the‑loop reduces a lot of quantization artifacts compared to post‑training quantization, which plausibly helps preserve calibration and generation behavior.

Concrete failure cases to look for
- Miscalibration: model consistently overconfident (or underconfident) for certain prompt types or token classes even when accuracy is similar.
- Toxicity/regeneration: edge prompts that are safe under FP16 produce toxic completions under the ternary model (or vice versa).
- Robustness to adversarial prompts / jailbreaks: quantization could change the model’s vulnerability to some prompt patterns.
- Rare token hallucination: increased probability mass on unlikely tokens in some contexts.

How you can (should) evaluate this — specific tests and metrics
Design comparisons to the FP16 baseline the paper used (same training tokens, same decoding settings). Suggested metrics and procedures:

1) Calibration (probability/confidence)
- Negative log likelihood (NLL) and Brier score:
  - NLL = \(-\frac{1}{N}\sum_{i=1}^N \log p(y_i \mid x_i)\).
  - Brier score = \(\frac{1}{N}\sum_{i=1}^N (p(y_i) - \mathbf{1}\{y_i = \text{true}\})^2\).
- Expected Calibration Error (ECE) using M bins:
  - Partition predictions into bins B_m by predicted confidence; compute
    \(\mathrm{ECE} = \sum_{m=1}^M \frac{|B_m|}{N} \left|\mathrm{acc}(B_m) - \mathrm{conf}(B_m)\right|.\)
  - Compute ECE per‑token and per‑sequence (sequence level = probability assigned to the selected answer / argmax).
- Reliability diagrams and temperature scaling to see if miscalibration is correctable post‑hoc.

2) Generation quality (automated + human)
- Automatic: MAUVE, distinct‑n, perplexity of continuations, ROUGE/BLEU for conditional tasks where references exist.
- Human preference tests: pairwise A/B comparisons for fluency, coherence, factuality, and safety on a curated prompt set (include many edge cases and sensitive prompts).
- Control for sampling: evaluate across temperatures and sampling strategies (greedy, top‑k, top‑p) used in the application.

3) Toxicity / safety checks
- RealToxicityPrompts suite: measure probability of toxic completions and expected toxicity scores across many prompts.
- Perspective API or other toxicity classifiers: compute toxicity probability distributions for sampled completions.
- Safety benchmark suites: apply TruthfulQA, safety adversarial sets, and jailbreak prompt collections; measure difference in harmful outputs.

4) Robustness / adversarial
- Prompt paraphrase tests: feed many paraphrases of the same question to test stability.
- Adversarial triggering patterns: run known jailbreaks and compare susceptibility rates.
- Out‑of‑distribution prompts and noisy inputs.

Practical experimental controls
- Use the same decoding hyperparameters and seeds for both models when comparing stochastic behaviors.
- Evaluate over a large, diverse prompt set (thousands) to capture rare failure modes; report confidence intervals.
- Compare at multiple model sizes—paper shows parity from 3B up, but smaller sizes may behave differently.
- Measure per‑prompt changes in logit gaps and entropy to see where quantization alters confidence.

Mitigations (if you find problems)
- Temperature scaling or Platt‑style calibration on held‑out validation to fix global miscalibration.
- Fine‑tuning or safety‑fine‑tuning (RL or supervised) to reduce toxic completions.
- Hybrid precision: keep critical layers (embeddings, final LM head) at higher precision while ternarizing others.
- Post‑processing filters (toxicity classifiers, safety wrappers) in the application stack.
- Train with explicit calibration objectives or mix in safety‑focused data.

Bottom line / recommended next steps
