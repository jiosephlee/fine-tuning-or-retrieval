\title{Stack Exchange of the Paper: The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits}

### Why is a ternary weight alphabet described as 1.58 bits? Do real systems actually store 1.58 bits per weight?
Question:
The paper says every weight takes values in {-1, 0, +1} and calls the model '1.58-bit' because log2(3) ≈ 1.585. In practice, memory is byte-addressable and kernels typically pack into whole numbers of bits. Are the weights actually stored in 2 bits per parameter during runtime, or is there a custom packing scheme that approaches 1.58 bits on average? If 2-bit storage is used, how should we interpret '1.58 bits' in the reported memory savings?
Answer:
Short answer: "$1.58$ bits" is the information-theoretic cost per weight ($\log_2(3) \approx 1.585$) because each weight takes one of three values $\{-1,0,+1\}$. In real systems you almost always store them in whole-bit units at runtime (commonly $2$ bits per weight for fast kernels). The paper uses the shorthand $1.58$-bit to describe the representational entropy/capacity of the weights and the ideal compression limit, while the practical memory/latency numbers come from an implementation that uses efficient $2$‑bit kernels and packing/engineering tradeoffs.

Why the authors say $1.58$ bits
The number comes from basic information theory: a ternary variable with three equiprobable symbols carries $\log_2(3) \approx 1.585$ bits of information. Calling the model "$1.58$-bit" highlights that each parameter only needs three distinct states, i.e., far less information than a $16$-bit float.

Why real systems don’t store fractional bits directly
Physical storage is byte-addressable and hardware typically handles whole-bit lanes efficiently ($8$, $16$, $32$ bits) or specially engineered small lanes (e.g., $2$-bit, $4$-bit kernels). You cannot place $1.585$ bits per weight exactly in memory without variable-length encoding or cross-weight packing + decoding. So in practice inference implementations either:
- Use $2$ bits per weight packed into words (fast and simple for GPU kernels), or
- Use a compressed checkpoint format on disk (Huffman/arithmetic coding, bit‑packing plus metadata) that approaches the entropy limit for storage, but adds decoding cost at load time.

Entropy vs stored bits
"$1.58$ bits" is the theoretical lower bound (average information per weight) assuming an optimal code and the true symbol distribution. If the ternary distribution is uniform, optimal lossless compression could approach $1.585$ bits/weight; if the distribution is skewed (e.g., many zeros) the entropy is even lower and compression beats $1.585$ bits. But runtime speed/latency and hardware constraints usually favor fixed-width encodings ($2$ bits/weight) rather than entropy-coded streams.

What the paper actually does
The paper explicitly says they measured latency and memory with a $2$-bit kernel from Ladder integrated into FasterTransformer. That implies practical inference uses $2$-bit packed representations and $2$-bit arithmetic kernels. The "$1.58$-bit" label is therefore a descriptive, information-theoretic naming (and a claim about representational capacity and potential compression), while the measured memory/latency savings reflect the real implementation choices ($2$-bit kernels, packing, activation precisions, embedding exceptions, and other runtime overheads).

How to interpret reported memory savings
When the paper reports, for example, "$3.32\times$ less memory" or similar, those are empirical numbers based on their implementation ($2$-bit kernels, $8$-bit activations, etc.), not simply raw $16 / 1.585 = 10.1\times$ arithmetic. So treat "$1.58$-bit" as the model’s per-parameter entropy; treat the reported memory/latency gains as implementation-level, measured wins after packing and system engineering. If they had used entropy coding for storage and perfectly ideal packing everywhere, you could get closer to the $\log_2(3)$ factor, but that’s rarely compatible with high-throughput GPU inference.

Practical guidance
For checkpoints and distribution, you can compress ternary weights on disk with Huffman/arithmetic coding to approach $1.585$ bits/weight (or less if skewed). For inference you normally use fixed $2$-bit packed formats and optimized kernels for speed; the practical savings are what matter most and are what the paper reports.

Summary: "$1.58$ bits" = information-theoretic description ($\log_2(3)$). Runtime storage is typically $2$ bits/weight for speed and hardware convenience; the paper’s memory/latency claims are based on that practical implementation, so the label is accurate conceptually but not a literal claim that every weight is stored as $1.585$ physical bits in RAM during inference.

### Does BitNet b1.58 keep any parameters in full precision (e.g., embeddings, RMSNorm gains), or are truly all weights ternary?
Question:
The abstract claims 'every single parameter (or weight) of the LLM is ternary {-1, 0, 1}', but in the Results section it says 'the embedding remains full precision.' Also, RMSNorm typically has learned scale parameters. Are token embeddings, positional embeddings/rotary parameters, RMSNorm scales, and SwiGLU gates all ternary in BitNet b1.58? If not, which components are exceptions, in what precision are they stored/used, and how much do they contribute to the overall memory footprint?
Answer:
Short answer: the paper explicitly calls out token embeddings as an exception (they “remain full precision”), and all nn.Linear-style weight matrices replaced by BitLinear are ternary $\{-1,0,1\}$ with 8-bit activations. The paper does not explicitly say that every tiny learned scalar/vector (RMSNorm scale, rotary frequency parameters, SwiGLU internal gates if implemented as per-layer matrices, etc.) was quantized to ternary, so you should assume embeddings are full-precision and the large matrix weights are ternary; the paper is silent about some small per-layer params.

Why I say this: the abstract makes the broad claim “every single parameter (or weight) … is ternary”, but the Results/Memory discussion explicitly states “the embedding remains full precision” and repeatedly contrasts the large-memory savings coming from quantizing the many large linear layers. In the architecture section they say they adopt LLaMA-alike components (RMSNorm, SwiGLU, rotary) and “remove all biases,” and they describe replacing nn.Linear by BitLinear and using the absmean ternary quantizer for weights. They also state activations are 8-bit. Those are the explicit, reliable claims in the paper:

- All large matrix weights (the BitLinear layers that replace nn.Linear) are quantized to ternary $\{-1,0,1\}$ via the absmean RoundClip scheme.  
- Activations are quantized to 8-bit.  
- Embeddings are explicitly kept full precision (the paper says this directly and uses this to explain why embedding memory share shrinks with model size).  
- Bias terms are removed.  
- The paper does not state that RMSNorm scales, rotary embedding parameters, or other small learned vectors were quantized; it only lists the component names (RMSNorm, SwiGLU, rotary) but gives no per-parameter-precision table.

Practical implications / memory contribution: embeddings are the main remaining FP component, but their relative memory share declines as model size grows (the paper notes this). Concretely, for typical transformer LLMs the embedding matrix size is roughly $\text{vocab\_size} \times d_{\text{model}}$. If embeddings are kept at FP16/BF16 (2 bytes per element), they will dominate memory for small models (e.g., a 3B model) more than for very large models (70B), where the many weight matrices (now ternary) would otherwise dominate. The authors use this exact observation to explain why BitNet’s speedup and memory gains grow with model size — the full-precision embedding is a relatively small leftover cost at big scales.

What the paper does not resolve and what you should check if you need exact accounting: the authors don’t explicitly state the precision of RMSNorm gain parameters, the rotary parameter storage format, or any tiny per-layer scalars. Those are typically tiny (vectors of length $d_{\text{model}}$ or small parameter lists) and so have negligible impact on total memory compared to embeddings and linear layers, but if you need byte-exact memory accounting (for an implementation or hardware design) you should consult the code release / ask the authors. The paper’s main empirical and systems claims are grounded in (1) ternary BitLinear weights, (2) 8-bit activations, and (3) full-precision embeddings being the only called-out FP remainder.

If you want a conservative engineering assumption: treat embeddings and any per-layer scalar gains (RMSNorm scale, rotary freq tables) as full precision (FP16/BF16) and all linear layer weights as ternary. That matches the explicit statements in the paper and gives near-identical memory/latency conclusions as the authors report.

### How exactly is the absmean quantization with RoundClip applied and updated during training?
Question:
The quantization is defined as \(\widetilde{W} = \mathrm{RoundClip}(W/(\gamma+\epsilon), -1, 1)\) with \(\gamma = \frac{1}{nm}\sum_{ij}|W_{ij}|\). Do they compute \(\gamma\) once per forward pass per weight matrix, or is it updated less frequently (e.g., per step or per epoch)? Is \(\gamma\) computed per-tensor, per-row, or per-column? How sensitive is performance to the choice of per-tensor vs per-channel scaling?
Answer:
Short answer: in this paper $\gamma$ is a per-weight-matrix (per-tensor) scale computed from the current full-precision weights $W$ and used to quantize that matrix in the forward pass; $\gamma$ therefore changes as the underlying weights change (i.e. it is recomputed regularly as training proceeds — effectively each forward that uses that matrix). The authors present the quantizer as "scale by the average absolute value of the weight matrix" ($\gamma = \frac{1}{nm}\sum_{i,j} |W_{ij}|$), which strongly implies per-matrix scaling rather than per-row or per-column, and the experiments and description use that per-matrix (per-tensor) choice.

Why this is the natural interpretation and how it behaves during training. The formula for $\gamma$ is defined directly from the entries of $W$, so whenever $W$ changes (by optimizer updates) $\gamma$ changes as well; in practice this is computed from the current $W$ at quantization time (i.e. each forward pass that needs the quantized weights). Computing $\gamma$ per-forward is cheap (a single elementwise absolute + mean over the matrix) and keeps the quantizer matched to the current weight distribution, which stabilizes training because the ternary thresholds remain adaptive to the scale of the weights. If you instead froze $\gamma$ for many steps or computed it only per epoch you would be applying a stale scale to a changing $W$ and that can degrade training dynamics unless you compensate elsewhere.

Why the paper uses per-tensor (intuitive reasoning). Using the mean absolute value over the whole weight matrix is simple, parameter-efficient and enforces a single scale for all elements of that linear layer, which fits the BitNet design goal of extreme quantization simplicity (ternary weights across the matrix). Per-tensor scaling also integrates naturally with system-level kernels and the claimed runtime/memory advantages.

Per-row / per-column (per-channel) scaling — tradeoffs and sensitivity. The paper does not report experiments comparing per-tensor vs per-channel $\gamma$ for weight quantization, so there is no empirical number in the text about sensitivity. Generally, per-channel scaling can improve representational fidelity when different output channels (rows/columns) have systematically different magnitudes (this is common in convolutional layers and sometimes beneficial in linear layers). The trade-off is extra metadata (one $\gamma$ per channel) and more bookkeeping in kernels. Given the paper’s claim and design choice, they found the per-matrix absmean sufficient to reach parity with $FP16$ at scale (starting around $3\text{B}$), which indicates that for their architecture and training regime performance is not critically sensitive to not using per-channel scaling.

Practical recommendation (consistent with the paper). Implement $\gamma$ as a per-weight-matrix scalar computed from the current FP weights and recompute it whenever you quantize that matrix (i.e. each forward that needs the quantized weights). Use the per-tensor absmean by default (as in the paper); if you suspect large per-channel magnitude variation in your model (or you want to squeeze slightly better accuracy at the cost of extra complexity), try a per-channel version in an ablation to see if it yields meaningful gains for your architecture and dataset.

If you need to experiment: compare (a) per-tensor $\gamma$ recomputed every forward (paper default), (b) per-channel $\gamma$ recomputed every forward, and (c) per-tensor $\gamma$ updated less frequently (e.g. once per step or epoch). The paper’s formulation and results support option (a) as the intended and effective choice.

### What gradient estimator is used to backpropagate through RoundClip and the ternary quantization?
Question:
The paper quantizes weights via a non-differentiable RoundClip. During training from scratch with 1.58-bit weights, what estimator is used for gradients? Is it a straight-through estimator (STE), and if so, what exact form (e.g., identity through the rounding and clipping range and zero outside)? Do they keep a latent real-valued weight copy for updates, or are updates applied directly in the ternary space?
Answer:
The paper does not explicitly state the gradient estimator used for backpropagating through the RoundClip quantizer. They give the forward quantization precisely:

\[
\widetilde{W} = \mathrm{RoundClip}\!\left(\frac{W}{\gamma+\epsilon}, -1, 1\right),\qquad
\mathrm{RoundClip}(x,a,b)=\max(a,\min(b,\mathrm{round}(x)))
\]

but there is no accompanying paragraph that describes the backward / gradient path or an implementation snippet in the text.

Given that omission, the only safe statements are: (1) the paper does not specify the estimator, and (2) the usual, well-established practice for training networks with non-differentiable quantizers (and what BitNet-style papers normally use) is to employ a straight-through estimator (STE) and to keep a latent real-valued copy of the weights that is updated by SGD/Adam. I therefore summarize the likely (and practical) design they almost certainly used, explain why, and point out how you can confirm it.

What is almost certainly done (practical/standard choice)
- A latent full-precision weight tensor $W$ (the one in the equations) is maintained and updated by the optimizer. The quantized weights $\widetilde{W}$ are obtained from $W$ by the RoundClip transform and used in the forward pass (and in inference).
- For the backward pass a Straight-Through Estimator is used: the gradient is propagated from the loss through $\widetilde{W}$ back to $W$ as if the quantization were the identity. Concretely, a common implementation makes the backward derivative $d\widetilde{W}/dW$ equal to $1$ (or $1$ inside the clipping interval and $0$ where a hard clip saturates), i.e. the gradient w.r.t. $\widetilde{W}$ is passed to $W$ directly. This lets the optimizer nudge the real-valued $W$ so the rounded values change over training.

Why this is the practical choice
- Without a latent real-valued copy and STE, it is essentially impossible to train: pure discrete updates in ternary space make gradient-based optimization intractable or noisy. Maintaining $W$ and using STE preserves gradient flow and is the standard method in quantized-net literature.
- The STE is simple and empirically effective for rounding-based quantizers; BitNet and other low-bit quantization training papers follow the same pattern (round forward, identity-ish backward).

Edge detail about the clipping behavior
- There are two common variants seen in code: (a) pure STE for round+clip that simply treats $\mathrm{RoundClip}(x)$ as $x$ in the backward pass (derivative $1$ everywhere), and (b) an STE that respects clip saturation so the backward pass zeroes gradients outside the clipping bounds. The paper does not say which variant they used. Both variants are used in the literature; variant (a) is simpler and more typical for rounding operations, while (b) can be used to discourage parameters from moving into saturated regions.

What to do to confirm
- Check the project code / repo or FasterTransformer / Ladder kernels they integrated — the authors say they use BitNet and Ladder kernels and these codebases often reveal the exact backward behavior. If no code is available, ask the authors or look for a supplementary implementation. Empirically you can also probe training behavior: if a latent full-precision copy is used you will see smooth changes in pre-quantized $W$ and discrete jumps in $\widetilde{W}$; pure discrete updates would make optimization very unstable.

In short: the paper omits the explicit backward rule, but the standard, almost-certain implementation is STE with a latent full-precision weight copy that is updated by the optimizer. If you need absolute certainty for reproducibility, check their code or ask the authors which STE variant (identity everywhere vs. zero outside clip) they used.

### How are activations quantized to 8-bit 'per token' and how is the scale handled across layers and KV cache?
Question:
The paper states activations are 8-bit and 'scaled to [-Q_b, Q_b] per token' to avoid zero-point quantization. Does 'per token' mean a separate symmetric scale per sequence position (i.e., per row in the batch*time dimension), or per token per channel? How is the scale tracked and applied across consecutive layers, especially around non-linearities (SwiGLU) and attention softmax? What precision is used to store the KV cache, and is the same per-token scaling applied to cached keys/values across timesteps?
Answer:
Short answer: In this paper “per token” means one symmetric (zero-centered) scale scalar per token position (i.e., per row of the $\text{batch}\times\text{time}\times\text{hidden}$ matrix), not a separate scale per channel. The implementation implication is that every token’s entire hidden vector is quantized with the same symmetric scale value; that scale is carried alongside the 8-bit integers and combined (multiplicatively) with weight scales when you do subsequent linear layers. Nonlinearities and softmax are evaluated in higher precision (or after applying the appropriate scale), and the KV cache is stored in the 8-bit form together with the per-token scale for that timestep so cached keys/values can be re‑scaled correctly when reused.

Explanation and reasoning grounded in the paper
The paper explicitly says “the activations are all scaled to $[-Q_b,Q_b]$ per token to get rid of the zero-point quantization.” That wording most naturally reads as: for each token position you compute a single symmetric scaling factor and map the full hidden vector of that token into the symmetric 8-bit range. This avoids having to store a zero-point (an additive offset), which complicates integer arithmetic and storage. Using one scale per token is cheap (one float per token) and is exactly what “per token” is used to mean in similar quantization schemes.

How scales are tracked and used across layers
When an activation vector $x$ (floating) is quantized per token you have
$x_{int8} = \mathrm{Quantize}\left(\frac{x}{s_x}\right)$ in the integer domain and you store $s_x$ (a scalar) alongside the int8 vector. For a linear layer with (possibly quantized) weights $W$, the matrix multiply in real math is
$y = W x$.
If $x$ is stored as int8 with scale $s_x$ and $W$ is represented with its own scale $s_W$ (or as low-bit weights with an implicit scale), then the accumulated integer product yields an integer accumulator $A$ such that
$y_{\text{float}} = s_W \, s_x \, A$
so the output scale $s_y = s_W \, s_x$ (possibly times any rescaling introduced by the accumulator normalization) — equivalently you attach a new per-token scale for $y$. In practice you either (a) keep the output in quantized form and store $s_y$ per token, or (b) dequantize to float for downstream ops and recompute scales as needed. The paper’s description (8-bit activations, per-token symmetric scale) implies they keep a scale per token and propagate/compute the correct combined scale when composing layers.

What happens around nonlinearities (SwiGLU) and softmax
Nonlinearities pose two choices: dequantize, apply the nonlinearity in float, then requantize (storing a new per-token scale); or implement the nonlinearity in integer with scale bookkeeping. The paper does not give a low-level microkernel description, but its text emphasizes simplicity (“more convenient and simple for both implementation and system-level optimization”) and that they do not scale activations before nonlinear functions to $[0,Q_b]$. That implies the practical route is to keep symmetric int8 + per-token scale, dequantize to float (or to a higher internal accumulator precision like FP16/BF16) when applying nonlinear functions such as SwiGLU, then requantize the result back to int8 with a freshly computed per-token scale. For attention softmax, numerical stability and the need for exponentials/normalization strongly favour performing softmax in floating precision: you dequantize the attention logits (apply the stored scales), run softmax in float, and then (if you need to) quantize the resulting attention weights/outputs back to int8 with a new per-token scale. The paper’s discussion of accuracy and system simplicity is consistent with doing nonlinearities and softmax in higher precision rather than doing complex integer approximations.

KV cache precision and scaling across timesteps
The paper explicitly notes that reducing activations from 16 bits to 8 bits helps KV cache memory and that these 8-bit activations “allow the context length to be doubled given the same resources.” That suggests the KV cache is stored in its compressed (8-bit) form with the same per-token symmetric scale stored for each cached timestep. When you later reuse cached keys/values for a new attention query, you either dequantize using the stored per-token scale(s) (restore float keys/values for the attention), or you incorporate the scale into the attention matmul by multiplying accumulators by the stored scales. Concretely: if $K_t$ and $V_t$ were quantized with scale $s_t$ at timestep $t$, the system must keep $s_t$ so when computing e.g. $Q\cdot K^{T}$ you account for $s_Q \, s_t$ in the dot-products. The paper mentions potential for further lossless compression, but the described approach is to store int8 + per-token scale for cache entries.

What the paper does and what is left unspecified
The paper gives the macro design: 8-bit activations, symmetric per-token scaling, and keeping nonlinearities/attention consistent with that choice. It deliberately emphasizes system-level convenience and avoids zero-point arithmetic. It does not publish microkernel-level details such as: whether they fuse multiply–accumulates to delay dequantization, what accumulator bit width is used in each kernel, or whether some nonlinearities are approximated in integer in some optimized runtimes. Those are implementation choices compatible with the paper’s design: storing one float scale per token, propagating scales multiplicatively through linear layers, dequantizing for nonlinear ops and for softmax, and saving cached $K/V$ in int8 plus per-token scales for later use.

Summary
The phrase “per token” = one symmetric scale per token position (one scalar per row of hidden activations). That scale is stored and combined with weight scales to produce output scales when you do linear layers; nonlinearity and softmax are handled in higher precision after applying the scale (then requantized if you want to keep 8-bit activations); the KV cache is kept in the 8-bit + per-token-scale format so cached entries can be rescaled correctly when reused. The paper intentionally chooses symmetric per-token scaling to avoid zero-point complexity and to simplify system-level kernels, but the exact low-level fusion/accumulator choices are left to implementation.

### Where do multiplications remain in BitNet b1.58, and what is the exact compute pathway for a ternary matmul?
Question:
The paper says 'almost no multiplication operations' and that most compute becomes INT8 additions. For a linear layer \(y = \widetilde{W}x\) with \(\widetilde{W} \in \{-1,0,1\}^{m\times n}\), is the computation implemented as conditional adds/subtracts of \(x\), plus a final rescale by \(\gamma\)? If weights are encoded using a 2-bit kernel from Ladder, how is the multiply-by-\(-1\) implemented efficiently? Where precisely do any remaining multiplications occur (e.g., scaling by \(\gamma\), activation rescaling, layernorm, softmax), and in what precision?
Answer:
Short answer: the vast majority of per-layer multiply operations disappear inside the ternary matmul and are replaced by integer additions and a few cheap integer subtractions/bit-ops. The remaining true multiplications are the small per-matrix (or per-block) rescale(s) introduced by the quantization (the $\gamma$), and the usual FP math in non-linear/normalization primitives (RMSNorm, SwiGLU internal FP ops, softmax). In practice those scalar rescalings are done in the model floating precision (FP16/BF16 in this paper) while the ternary matmul itself is implemented with integer accumulation (INT32/INT8 pipeline). Below I explain the exact compute pathway and how “multiply by $-1$” is implemented efficiently.

How a ternary linear is computed (intuitive + exact pathway)
For a linear layer with quantized weight matrix $\widetilde W\in\{-1,0,1\}^{m\times n}$ and input vector $x$, the product
$$ y=\widetilde W x $$
can be seen elementwise as adding or subtracting selected entries of $x$ (or skipping them). Concretely you can split $\widetilde W$ into two binary mask matrices $P$ and $N$ where $P_{ij}=1$ iff $\widetilde W_{ij}=+1$ and $N_{ij}=1$ iff $\widetilde W_{ij}=-1$. Then
$$ y = (P\odot x)\mathbf{1} - (N\odot x)\mathbf{1} $$
which in implementation becomes: compute sum of selected inputs for the +1 positions, compute sum of selected inputs for the -1 positions, then subtract. No per-element FP multiply is needed.

Typical optimized kernel implementation does exactly that (or an equivalent bit-packed trick): bitpack/encode the two masks (2 bits per weight or one bit per sign and one bit for zero), use masked integer adds (or popcount-style accumulation) to compute the two partial sums, then do one integer subtraction per output entry. So the per-weight "multiplication" reduces to either an integer add (if $+1$) or an integer add that later contributes to the negative sum (if $-1$), or nothing (if $0$).

How “multiply by -1” is implemented
Multiply-by $-1$ is handled without a per-element multiply: weights with value $-1$ are routed into the negative accumulator instead of the positive one. At the output we compute positive_sum $-$ negative_sum. On typical hardware this is implemented either as (a) two masked integer accumulation loops plus one integer subtraction per output, or (b) a single accumulation where sign bits flip the add/subtract direction (e.g., conditional add/subtract using integer ALU), or (c) bitwise tricks for binary-packed kernels (xnor/popcount style for bipolar) when applicable. The Ladder 2-bit kernel integration mentioned in the paper is a packed/optimized 2-bit implementation that exposes exactly these mask and accumulate operations; it doesn’t introduce FP multiplies per weight.

Where multiplications remain and in what precision
The paper is explicit that almost all matrix multiplication work becomes INT additions. The remaining multiplications are:

1. The quantization scaling by $\gamma$ used to normalize raw weights before rounding:
   - During quantization/training this $\gamma$ is computed as $\displaystyle \gamma=\frac{1}{nm}\sum_{ij}|W_{ij}|$. That computation is done in floating precision (training uses FP16/BF16 internals or FP32 for stable statistics), and the application of the scale is a floating multiply when mapping back to real-valued outputs (see next point).
2. Dequantization / final rescale after integer accumulation:
   - After the INT accumulation (often done in INT32 to avoid overflow), the accumulated integer outputs are typically converted back to a floating representation and multiplied by the learned/global scale $\gamma$ (or a per-block scale) to restore the proper magnitude. That scalar multiply is a true FP multiply; in this paper the model training and baseline are FP16/BF16, so this rescale is done in FP16/BF16 (or often promoted to FP32 for numerical stability then cast back).
3. Activations’ per-token scaling:
   - BitNet b1.58 scales activations to $[-Q_b, Q_b]$ per token (to avoid zero-points). Any small scale factor associated with that can be applied as an integer scale in inference or as an FP multiply depending on the implementation; the paper treats activations as 8-bit, so the kernel pipeline usually performs integer requantization + an eventual FP multiply when converting back for primitives that need FP inputs.
4. Nonlinearities and normalization:
   - Components such as RMSNorm, SwiGLU internal projections (if they are kept in low-bit they still require some FP ops for gating), softmax, and other normalization/attention scalings are performed in FP16/BF16 (the paper follows LLaMA-like components and retains those in floating precision). Softmax especially requires exponentials and divides (FP operations).
5. Any remaining per-layer bias terms (paper removes biases, but if present) and embedding layers:
   - The paper removes biases and leaves embeddings in full precision; embeddings and token projection layers that remain FP will involve FP multiplies.

Precision summary and typical accumulation flow
In a deployed, optimized inference kernel the sequence is usually:
- Inputs: activations quantized to INT8 (paper uses 8-bit activations).
- Weights: ternary encoded as 2-bit (packed) kernels (e.g., Ladder 2-bit kernel).
- Multiply-replace: perform integer accumulation (INT32 accumulators) by masked adds (no per-weight FP multiplies).
- Requantize / dequantize: convert INT32 accumulator to FP16/BF16 and multiply by $\gamma$ (FP16/BF16 multiply) or perform integer rescaling if the system supports it exactly.
- Downstream: pass floats to RMSNorm / softmax / SwiGLU which run in FP16/BF16.

Why energy and FLOP claims hold
Because per-weight multiplies are removed and replaced by integer add/subtract and bit-manipulation, the dominant arithmetic inside the big \emph{nn.Linear} blocks becomes integer add/subtract and a few integer subtractions at the final stage. The only remaining FP multiplies are low in count (one per output element for rescale $\gamma$, and the usual FP ops in small modules). That explains the large per-matrix energy savings claimed in the paper.

Practical notes
The exact numeric choices (accumulator width INT32, perform dequantization in FP16 vs FP32, layout of 2-bit encoding) are implementation details and the paper integrates the 2-bit Ladder kernel and FasterTransformer to realize the integer-accumulate + FP rescale pipeline. In practice many optimized kernels keep accumulation as INT32, do a single FP multiply by $\gamma$ for each output row or block (done in FP16/BF16), and keep the rest of the transformer primitives in FP16/BF16.

In short: ternary matmul = conditional integer adds (plus one integer subtraction per output), multiply-by-$-1$ is implemented as routing to negative accumulation (no per-element FP multiply), and the only remaining FP multiplies are small-count scalings (quantization/dequantization by $\gamma$) and the usual FP math in RMSNorm/softmax/SwiGLU, typically in FP16/BF16.

### What accumulation precision is used for ternary matmuls? Is INT8 addition sufficient without overflow?
Question:
A dot product involves summing up to \(n\) terms, which commonly requires INT32 accumulators to avoid overflow and preserve accuracy. The paper states the majority of BitNet b1.58 arithmetic is INT8 additions. Are partial sums kept in INT32 and then requantized, or are there techniques to keep accumulation in INT8 safely? Can the authors clarify the precise accumulator width for the main GEMM kernels?
Answer:
Short answer: the paper does not explicitly state the accumulator bit-width, but in practice you must use wider (typically INT32) accumulators for the ternary GEMMs; plain INT8 accumulation will overflow except in very constrained settings, so the usual implementation accumulates into 32 bits and then requantizes back to 8 bits.

Why: a dot product of length $n$ sums $n$ terms. In BitNet b1.58 the weights are ternary $\{-1,0,1\}$ and activations are 8-bit scaled values in $[-Q_b,Q_b]$. The magnitude of each product term is at most $Q_b$, so the worst-case absolute partial sum is bounded by
$$
S_{\max} \le n \cdot Q_b.
$$
To avoid overflow you need accumulator bits to represent values up to $\pm S_{\max}$, i.e. roughly $\lceil\log_2(n Q_b)\rceil+1$ bits (one bit for sign). For any realistic GEMM block or layer dimension (e.g. $n$ in the hundreds or thousands and $Q_b$ typically a power-of-two-ish 8-bit dynamic range), that quickly exceeds 8 bits and is well within the range where INT32 is the safe and standard choice on both CPU and GPU.

Practical/implementation points consistent with the paper and common practice: the paper reports using FasterTransformer and a 2-bit kernel from Ladder. Those libraries and GPU integer-GEMM hardware normally take 8-bit inputs but accumulate into 32-bit registers (or use fused int8->int32 accumulation), then perform a requantization/rescaling step to store the output as 8-bit. The paper’s energy/compute counts saying “majority is INT8 addition” refers to the dominant operand width (weights/activations) and the simple arithmetic pattern (add/sub instead of FP mul-add), not that all accumulations stay at INT8.

There are techniques that can reduce accumulator width if you really need to: block-wise or hierarchical accumulation with intermediate requantization (accumulate small blocks into INT16/INT32, requantize, then continue), stochastic or pairwise accumulation to reduce dynamic range, or algorithmic compensation that keeps dynamic range small. But these add complexity and potential accuracy loss; for a production-quality LLM aiming to match FP16 performance (as BitNet b1.58 does), the straightforward, numerically safe route is int8 operands + int32 accumulation followed by requantization.

So: unless the authors explicitly state a nonstandard accumulator scheme (they do not), assume int32 partial sums in the GEMM kernels, then requantize to int8 for storage/output.

### Why does adding the zero weight improve 'feature filtering' and modeling capacity relative to binary weights?
Question:
The paper claims the inclusion of 0 in weights leads to explicit support for feature filtering and significantly improves performance over 1-bit (binary) models. Can you provide an intuitive explanation or formal argument for why allowing zero improves representational capacity or optimization? Do you have measurements of learned weight sparsity over training (e.g., ternary distribution over {-1, 0, 1}) and ablations that correlate sparsity with downstream performance?
Answer:
Short answer: allowing a weight value of $0$ gives the model an explicit, learned way to turn off (filter) individual features or input channels. That both increases representational capacity relative to strict $\{-1,+1\}$ binary weights and makes optimization easier in practice. The paper argues this qualitatively and shows big empirical gains (BitNet b1.58 matches FP16 starting at 3B), but it does not publish detailed per-weight ternary histograms or a dedicated ablation that correlates learned sparsity with downstream accuracy—so some of the empirical verification you ask for is not in the paper.

Why zero helps (intuitive explanation). A binary $\{-1,+1\}$ weight can only flip sign and scale (by a global scaling factor), so every input dimension always contributes (either positively or negatively) to the output. Introducing $0$ gives a third action: completely ignore a feature. That turns each weight into a tiny learned gate (allow / block) in addition to controlling polarity. Intuitively, this supports two behaviours that are hard for pure binary weights:

1. Feature filtering / gating. When a weight is $0$ the corresponding input/component is removed from the linear combination. This is qualitatively different from just flipping sign — it can remove noisy or irrelevant features and thus reduce interference between features, which is especially useful in deep nets where many linear maps stack.

2. Sparse, selective representations. $0$ enables sparse effective connectivity: the network can route information through a small subset of pathways per token or neuron. Sparse routing increases effective capacity because the same parameter matrix can implement many different (sparser) linear maps, reducing crosstalk and improving feature reuse.

A short formal-ish view. Let $W$ be a quantized weight matrix and $x$ an input. With ternary weights we can write
$W = S \circ M$
where $S \in \{-1,+1\}^{n\times m}$ gives signs and $M \in \{0,1\}^{n\times m}$ is a mask ($\circ$ is elementwise product). Then $W x = S \circ (M x)$. The mask $M$ lets the model choose a subspace of input coordinates to use for each output dimension. In contrast, binary weights correspond to $M$ all-ones, so the model can only change signs but not select coordinates. Counting representational possibilities: for a matrix with $k$ entries, binary has $2^k$ configurations, ternary has $3^k$ — a strictly larger discrete hypothesis space. More usefully, the mask dimension produces combinatorial choices of which input columns participate, enabling simpler sparse linear maps that can approximate functions with fewer interfering terms.

Optimization benefits. From an optimization perspective, $0$ allows the training dynamics to reduce harmful contributions smoothly (via straight-through gradients or other surrogate gradients) by moving entries toward zero before deciding sign flips. That can reduce gradient noise and instability that arises when the only option is flipping sign. Practically, sparsity can also stabilise deeper networks by reducing effective layerwise magnitudes and interactions.

Link to the paper. The paper implements ternary quantization via an abs-mean scale and RoundClip to $\{-1,0,1\}$, and reports that BitNet b1.58 matches FP16 performance from 3B up while keeping large system-level gains. The authors explicitly claim the extra $0$ value gives “explicit support for feature filtering” and “significantly improves performance over 1-bit (binary) models.” Those empirical results are the primary evidence provided.

What the paper does and does not give you about sparsity measurements. The manuscript does not include per-layer or global histograms of learned weights over $\{-1,0,1\}$, nor an ablation that varies the induced sparsity (e.g., by regularisation or by forcing different $0/\pm1$ ratios) and plots downstream accuracy versus sparsity. So while the paper shows end-to-end improvement of the ternary design versus full-precision and versus prior 1-bit BitNet in aggregate metrics (perplexity, zero-shot tasks, latency/memory/energy), it does not publish the detailed ternary-distribution statistics you asked for.

Recommended experiments / diagnostics to run (so you or future work can quantify the claim). To make the connection concrete, measure per-layer and global fractions $p_{-1}, p_0, p_{+1}$ over training checkpoints and plot them against validation perplexity. Run ablations that (a) force different target sparsity levels (e.g., add $L_1$ on pre-quantized weights or thresholding) and (b) compare performance when you collapse $0$ into $+1$ or $-1$ (i.e., enforce pure binary) while keeping the same training recipe. Also inspect per-token / input-dependent activation sparsity to see whether $0$-weights correlate with reduced feature interference. These diagnostics will show whether performance improvements track increasing or decreasing sparsity and reveal which layers benefit most from filtering.

Summary. The extra $0$ increases the discrete hypothesis space and gives an explicit masking / gating mechanism that enables feature filtering and sparser routing, which both improve representational efficiency and make optimization less brittle than pure sign flips. The paper demonstrates the practical benefit (better accuracy/efficiency trade-offs) but does not include the detailed ternary-distribution or sparsity vs. performance ablation plots you requested; running the measurements and ablations above would directly quantify the role of learned zeros.

### How is quantization applied around SwiGLU and RMSNorm, and are those parameters/activations also quantized?
Question:
The architecture uses RMSNorm and SwiGLU. Are the RMSNorm weights (scales) and SwiGLU projection weights ternary as well? Are the activations feeding into and coming out of the SwiGLU nonlinearity quantized to 8-bit with symmetric per-token scales? How is numerical stability ensured for the RMS normalization and the GELU-like nonlinearity under 8-bit activation quantization?
Answer:
Short answer: yes — in BitNet b1.58 all trainable parameters (including the RMSNorm scale parameters and the SwiGLU linear projections) are constrained to the ternary set $\{-1,0,1\}$, and activations are quantized to 8 bits with a symmetric per-token scale. The paper does not give low-level kernel details for the internal arithmetic of RMSNorm or the nonlinearity, but it explains the quantization design choices that make these components numerically stable in practice.

What the paper explicitly states
The model is trained from scratch with "$1.58$-bit weights and $8$-bit activations." The paper replaces every nn.Linear with BitLinear and uses an "absmean" quantizer that scales a weight matrix by its average absolute value $\gamma$ and then $\mathrm{RoundClip}(\dots,-1,1)$ to produce $\{-1,0,1\}$ weights:
$$
\widetilde{W} = \mathrm{RoundClip}\!\left(\frac{W}{\gamma+\epsilon}, -1, 1\right),
\qquad
\gamma = \frac{1}{nm}\sum_{ij} |W_{ij}|.
$$
Because RMSNorm scale parameters and every linear projection in the Transformer are trainable parameters, they are part of this global "every parameter" quantization: they are ternary. The paper also states activations are quantized "to $[-Q_b, Q_b]$ per token" (symmetric per-token scale) to avoid zero-point complications.

Why this design helps numerical stability (intuitive + technical)
1) Symmetric per-token activation scaling preserves signed activation dynamics. Many normalization layers and nonlinearities (RMSNorm and SwiGLU/Swish-like activations) rely on the sign and relative magnitude of activations. By scaling activations per token to a symmetric range around zero, quantization keeps positive/negative balance and roughly preserves the shape of the activation distribution presented to RMSNorm and to the SwiGLU nonlinearity.

2) The absmean weight scaling normalizes each weight matrix by its average absolute magnitude before rounding. That prevents systematic under- or over-scaling of matrix outputs that would otherwise push activations into saturation when followed by nonlinearities. The explicit small $\epsilon$ in the denominator also avoids division-by-zero issues.

3) RMSNorm itself is inherently simpler than LayerNorm: it computes root-mean-square over the hidden dimension and applies a learned scale (here ternary). RMS uses an RMS denominator $\sqrt{\operatorname{mean}(x^2)+\delta}$ which, combined with the per-token activation scale and a small stability constant $\delta$ (standard practice / hinted by $\epsilon$ elsewhere in the paper), keeps the denominator away from zero and stabilizes the division even when inputs are low-bit.

What the paper does not (explicitly) promise and how it is typically handled in practice
The paper does not spell out whether the RMS computation (the mean of squared activations, the sqrt, and the final division) is performed in 8-bit integer arithmetic end-to-end, nor does it give the exact accumulator precision used in kernels. In practice, high-quality quantized implementations typically do one of the following for stability and accuracy: (a) accumulate sums (means of squares) in a higher precision accumulator (FP16 or FP32) even when inputs are 8-bit, (b) perform the division/sqrt in FP16/FP32 and then requantize, or (c) dequantize a small slice to floating point for the normalization step and re-quantize the normalized activations. Any of these choices preserve numerical stability while keeping most heavy matmuls in low precision.

Because the paper targets system-level speedups, the symmetric per-token quantization and the removal of zero-points simplify integer kernels and make it straightforward to do higher-precision accumulation only where needed (normalization and sqrt). The combination of per-token scaling (reduces dynamic-range mismatch), absmean weight scaling (keeps linear outputs in reasonable range), and a small stability constant for normalization is the mechanism the authors rely on to ensure stability for RMSNorm and SwiGLU under 8-bit activations.

If you need implementation guidance
If you implement this yourself, follow the paper’s quantization rules for weights and per-token symmetric activations, remove biases (as the paper does), and ensure RMSNorm’s mean-of-squares and sqrt use at least FP16 accumulation (or a fused op that internally uses FP16/FP32) before rescaling back to 8-bit. That mirrors the practical compromise implied by the paper: most compute in 8-bit for efficiency, but do the small number of numerically sensitive ops in higher precision to keep the model stable.

Summary
RMSNorm scales and SwiGLU projection weights are ternary in BitNet b1.58, activations are 8-bit with symmetric per-token scales, and numerical stability is achieved by (a) per-token symmetric scaling of activations, (b) absmean normalization of weight matrices with $\epsilon$, and (c) the usual practical choice to perform the few numerically sensitive operations (mean-of-squares, sqrt, division) with higher-precision accumulation or fused kernels — a detail the paper does not fully specify but is standard and consistent with the design choices they describe.

### What is Q_b for 8-bit activations and does per-token symmetric scaling impact cross-token operations?
Question:
When scaling activations to [-Q_b, Q_b], is Q_b set to 127 for signed int8? If each token uses its own symmetric scale, how does this interact with operations that mix tokens, like attention softmax across a sequence? Do you rescale to a common dynamic range before attention scores are computed, or are scores computed in higher precision after dequantization?
Answer:
Short answer: Yes — for symmetric signed $int8$ you take $Q_b = 127$. And you do not try to run softmax across differently scaled tokens in raw $int8$: when tokens with per-token symmetric scales must be mixed (e.g. $QK^T$ and softmax across the sequence) the usual approach is to bring the values to a common numeric domain (effectively apply the per-token scale factors into the accumulation or dequantize to higher precision) and then compute the dot-products / softmax in higher precision ($FP16/FP32$) rather than directly mixing differently scaled $int8$ integers.

Why $Q_b = 127$
The paper says activations are scaled to the symmetric range $[-Q_b, Q_b]$ “to get rid of the zero-point quantization.” For an $8$-bit signed integer dtype ($int8$) the representable symmetric range is $[-128, 127]$, but symmetric quantization normally uses the positive maximum as $Q_b = 127$ so that zero maps exactly to integer $0$ and the range is symmetric in magnitude. So when they say $8$-bit activations scaled to $[-Q_b, Q_b]$ the practical choice is $Q_b = 127$.

Why you must handle per-token scales before cross-token ops
The paper quantizes activations “per token” (per-token symmetric scale). That means the integer values for token $i$ implicitly represent $ \text{real values} = (scale_i)\cdot(\text{int8\_values}_i)$. If you then mix activations from different tokens in the same operation (for example computing attention scores $QK^T$ where $Q$ and $K$ come from different tokens or computing softmax over sequence positions), you cannot correctly accumulate integer values directly unless all terms share the same scale. Two correct implementation strategies exist:

1) Fold the per-token scales into accumulators / weights and do integer matmul with a common scale factor. If you want to keep integer kernels you can multiply the $int8$ inputs by their per-token scale factors (or equivalently multiply the accumulator after integer matmul by the product of scales) so that all contributions are in a common real-domain scale before applying nonlinearities. In practice this often means computing integer matmul to $int32$ accumulators and then multiplying the $int32$ accumulator by a floating-point scaling factor before applying softmax. That is numerically equivalent to dequantizing the activations for the matmul but lets you preserve an integer kernel for much of the work.

2) Dequantize per-token activations to $FP16/FP32$ before any cross-token mixing and compute $QK^T$ and softmax in $FP16/FP32$. This is simpler and very common: convert each token chunk to floating point by multiplying $int8$ by its per-token scale, then run the attention computations in floating point. Softmax and normalization are sensitive to dynamic range and numerical stability, so running them in $FP16/FP32$ after dequantization is the safer and usual choice.

Which the paper implies / what is practical
The paper states activations are $8$-bit and “scaled to $[-Q_b, Q_b]$ per token” to remove zero-point for simplicity and system-level optimization, but it does not claim softmax or attention are performed directly in $int8$ across different token scales. Given standard practice and the paper’s emphasis on compatibility with existing toolkits (FasterTransformer, vLLM, etc.), the pragmatic implementation is to apply per-token scale factors into the computation so that attention score computation and softmax happen in higher precision (or at least with a single common scale applied to the accumulators). In short, you either rescale (via multiplying accumulators) to a common dynamic range before computing softmax, or you dequantize to $FP16/FP32$ and compute attention scores in floating point. Doing the softmax in higher precision after dequantization is the more robust and commonly used choice.

Practical note
If you want to maximize integer throughput, you can keep matmuls in low-precision ($int8 \rightarrow int32$ accumulators) and postpone floating conversions to after accumulation, but you must account for per-token scales consistently (multiply the accumulator by $scale_Q \cdot scale_K$). For simplicity and numerical safety—especially for softmax and normalization—dequantizing to $FP16/FP32$ before attention is the easiest and safest route.

Summary: $Q_b = 127$ for signed $int8$; per-token symmetric scales must be reconciled before cross-token operations, and the standard solution is to fold scales into accumulators or dequantize and compute attention/softmax in higher precision.

### How fair is the latency comparison given BitNet b1.58 uses a 2-bit optimized kernel while FP16 uses standard kernels?

Why this matters (intuitively). Short answer: the $71.4\times$ figure is an arithmetic‑only estimate for matrix multiply energy (ALU/MAC style work) computed from prior energy models on $7\ \mathrm{nm}$ process nodes. It does not account for the full memory hierarchy costs (SRAM/DRAM transfers, caches, KV cache for decoding, embedding I/O, control overhead). In the paper the end‑to‑end energy reductions (reported for $512$ tokens) are much smaller than $71.4\times$ because memory and other non‑arithmetic costs remain and therefore the real system is partially memory‑bound; the bit‑model’s advantage grows with model size and token count as the fraction of time/energy spent in matrix multiplies increases.

Why: what the paper actually says
The manuscript explicitly states that the energy estimate is focused “mainly on the calculation for matrix multiplication” and cites prior energy models ([energycost, pokebnn]). The $71.4\times$ claim is introduced with the phrase “saves $71.4$ times arithmetic operations energy consumption for matrix multiplication on $7\ \mathrm{nm}$ chips.” That wording and the citation indicate they compared per‑operation energy numbers ($\mathrm{FP16}$ multiply+add vs $\mathrm{INT8}$/add or equivalent $1$-bit ops) from an energy model and applied it to the arithmetic FLOPs of matmul. The paper does not say that the $71.4\times$ includes SRAM/DRAM access or other system costs.

What is excluded (and why it matters)
Memory hierarchy costs are not included in that arithmetic‑only figure. DRAM fetch energy (and repeated reads for weights/activations or KV cache) can be many orders of magnitude larger per byte than an ALU op; SRAM/register accesses also cost non‑negligible energy. Control overheads (non‑nn.Linear layers, embeddings, norm/activation, data movement between chips) are also excluded from the arithmetic‑only estimate. Because inference is not pure compute — especially at short sequence lengths or when KV caches dominate — those excluded terms can dominate total energy and reduce the realized end‑to‑end saving.

How this shows up in the paper’s end‑to‑end numbers
The paper reports measured latency, memory, throughput and also “end‑to‑end energy cost for models with $512$ tokens.” It states that BitNet b1.58 becomes increasingly energy‑efficient as model size increases because the percentage of nn.Linear (matrix multiply) grows with model size; conversely for small models or short sequences the relative cost of non‑matmul components (embeddings, KV cache, memory transfers) is larger. The paper does not give a numerical breakdown of arithmetic vs memory energy fractions, nor does it show the raw end‑to‑end energy numbers in the excerpt you provided, but the narrative and the other metrics (e.g., $2\text{--}4\times$ latency speedups, $3\times$ memory reduction, up to $8\text{--}9\times$ throughput at scale) imply end‑to‑end energy savings are substantially smaller than $71.4\times$ and are consistent with being limited by memory and other costs.

Practical intuition and how to check/recompute
If you want to reproduce or sanity‑check the $71.4\times$ arithmetic number: take the cited per‑op energy constants for $\mathrm{FP16}$ multiply+add and for the $1$-bit/$\mathrm{INT8}$ addition scheme at $7\ \mathrm{nm}$, multiply each by the appropriate FLOP count for the matmul kernels used in the model, and form the ratio. That gives the arithmetic savings reported. To get an end‑to‑end estimate that can be compared with the paper’s measured totals you must also add per‑byte energy for DRAM and SRAM accesses (and multiply by the number of bytes moved), plus energy for activations, KV cache, embedding loads, and other kernels. Typical empirical results from other works show arithmetic savings of tens$\times$ often collapse to a few$\times$ overall when memory and I/O are included — exactly the qualitative behavior the paper describes: very large arithmetic wins but modest overall wins unless computation dominates.

What to conclude
The $71.4\times$ is a useful indicator of the fundamental arithmetic efficiency of BitNet’s matrix multiply on a $7\ \mathrm{nm}$ process, but it is not a claim about whole‑system energy. The measured, end‑to‑end energy reductions reported for the $512$-token experiments are necessarily smaller and depend strongly on model size and sequence length; they improve (closer to the arithmetic advantage) as the proportion of work that is matmul increases. The paper would need to provide (or you would need to compute) a detailed breakdown of SRAM/DRAM accesses, KV cache size/access pattern, and per‑op counts to turn the $71.4\times$ arithmetic figure into an accurate full‑system energy prediction.

### Why choose ternary {-1, 0, +1} rather than a 2-bit set like {-2, -1, +1, +2} or learned ternary thresholds?
Question:
The paper uses RoundClip on W/(gamma+epsilon) to snap to {-1,0,+1}. Did you compare against other low-bit alphabets with 2 bits of dynamic range, or ternary with learned thresholds and scales per channel? What guided the choice of the absmean normalization and uniform ternary thresholds versus per-channel learned scales that might better match weight distributions?
Answer:
Short answer: the paper chooses symmetric ternary $\{-1,0,+1\}$ with a single absmean scale because it gives a practical balance of representational power (zero enables feature filtering), training/hardware simplicity, and good empirical performance when training from scratch. Per-channel learned thresholds or a different 2-bit alphabet (e.g. $\{-2,-1,+1,+2\}$) would add storage/compute complexity and implementation friction without a clear win; the paper uses absmean + uniform rounding as a simple, stable recipe that matches the observed weight statistics well enough for the model sizes where they report parity with FP16.

Why ternary $\{-1,0,+1\}$ is attractive (intuitions tied to the paper)
The paper frames BitNet b1.58 as a 1-bit/ternary architecture designed for two practical goals: extreme compute/memory efficiency and competitive modeling ability. Adding 0 (so weights can be exactly zero) is an important design choice: it enables explicit feature filtering/sparsity in the weight matrices, which is a powerful and hardware-friendly form of pruning built into the representation. A symmetric ternary alphabet is also easy to implement in integer-only kernels and leads to very simple multiplication behavior: a multiply by +1, -1 or 0 is just sign, negation, or zeroing—cheap on hardware.

Why absmean scaling + uniform thresholds were chosen
The quantizer in the paper scales each weight matrix by the average absolute value
\[
\gamma = \frac{1}{nm}\sum_{ij}|W_{ij}|
\]
and then applies RoundClip to map to $\{-1,0,+1\}$. This “absmean” normalization is attractive for a few reasons that the paper emphasizes: it is extremely cheap to compute (one scalar per weight matrix), it is robust (average absolute value tracks the overall scale of the weight distribution), it preserves symmetry around zero (no zero-point fiddling), and it avoids per-channel bookkeeping. The paper also points out that activations are scaled per token to a symmetric range to avoid a zero-point, again leaning on symmetry and simplicity. In short, absmean + uniform thresholds is a minimal, stable recipe that requires only one extra scalar per matrix and integrates cleanly with the BitLinear operator and system-level optimizations.

Why the authors likely did not use per-channel learned thresholds or a 4-value alphabet
The paper does not report a direct comparison with per-channel learned thresholds/scales or alternate 2-bit alphabets, so we can only infer the rationale from their design goals and the empirical results they present. Per-channel learned scales or thresholds would increase complexity in three ways: extra parameters (one scale/threshold per output channel or per row/column), extra storage and memory traffic (scalars must be stored and loaded), and extra compute to apply non-uniform scaling or dequantization at runtime. For extreme-efficiency hardware and for integration into simple INT-add kernels, those costs matter.

A 4-value symmetric alphabet like $\{-2,-1,+1,+2\}$ (or any non-uniform spacing) provides higher dynamic range per weight but also increases quantization granularity and potentially the variance of the effective weight distribution after quantization. That may require different training hyperparameters or more elaborate scale estimation. Crucially, the paper trains from scratch with the ternary scheme and demonstrates parity with FP16 at reasonably large model sizes; that empirical success reduces the motivation to add complexity. Also, using $\{-1,0,+1\}$ preserves a small integer set that maps nicely to efficient integer accumulation and simple bit-packed storage; more distinct magnitudes break some of those hardware advantages unless you pay for additional encoding/scale logic.

Broader conceptual trade-offs
This is the familiar trade-off in quantization: per-tensor vs per-channel scales, symmetric vs asymmetric quantizers, and fixed vs learned codebooks. Per-channel learned scales usually reduce quantization error (they tailor the dynamic range to each channel) and are common in high-accuracy low-bit post-training quant methods. But they come with storage/engineering costs and complicate fast kernels. The paper opts for the minimal route that still achieves strong results when training the architecture end-to-end with the quantized constraint baked in, rather than doing expensive post-training calibration.

What the paper does not claim and what you might try next
The paper does not present ablations comparing ternary vs other small alphabets or learned thresholds. If you want to evaluate this yourself, reasonable ablations are: (1) per-channel absmean vs per-matrix absmean; (2) learned multiplicative scales per channel (trained jointly) with the same RoundClip thresholds; and (3) different 2-bit codebooks (symmetric $\{-2,-1,+1,+2\}$, asymmetric sets, or learned codebooks). Key metrics to track are validation perplexity, sparsity (fraction of zeros), hardware-relevant costs (extra scalar storage and per-inference ops), and stability of training. My expectation guided by the paper’s design is that per-channel scales will reduce quantization error but give modest accuracy gains at the cost of system complexity, and that more complex alphabets may not justify the hardware/implementation trade-offs given the strong results already achieved with the simple ternary scheme.

Summary
The paper prioritizes a simple, symmetric ternary alphabet with an inexpensive absmean scale because it preserves hardware efficiency, yields useful sparsity (0 as a filter), and is sufficient to match FP16 at scale when training from scratch. Per-channel learned thresholds or richer 2-bit alphabets could further reduce quantization error in theory, but they introduce extra parameters, runtime complexity, and hardware friction; the paper does not report those comparisons and instead presents an empirical recipe optimized for the practical goals of efficiency and ease of integration.

### How is attention softmax computed under 8-bit activations: quantized or in higher precision?
Question:
Attention involves computing \(QK^T / \sqrt{d}\), softmax, and then a weighted sum with \(V\). In BitNet b1.58, are Q, K, V projections ternary while Q, K, V activations are int8? Is the dot-product and softmax computed in FP16/FP32 after dequantizing activations, or performed partly in integer arithmetic? What precision and scaling is used to ensure numerical stability for softmax and to avoid underflow/overflow?
Answer:
Short answer: in BitNet b1.58 the projections (weights) are ternary $\{-1,0,+1\}$ implemented via BitLinear, activations are quantized to signed $8$-bit per the paper, and the bulk of the matmuls are implemented as integer additions/accumulations. However, the numerically sensitive softmax is not left purely in tiny integers — in practice the integer accumulation is paired with scaling and the softmax (and the division by $\sqrt{d}$) is handled in higher precision ($\text{FP16}/\text{FP32}$) after applying the appropriate scale. The paper does not give a full low-level kernel spec, but the text and the integration choices (FasterTransformer + Ladder 2-bit kernel) make this mixed integer+$\text{FP}$ pipeline the intended design.

Why this is the natural implementation and how it maintains numerical stability. The paper states weights are ternary via the absmean quantizer and activations are scaled to a signed range $[-Q_b, Q_b]$ per token to remove zero point. That gives you, for each token, an integer activation value $a_i$ in $\text{int8}$ and a known per-token scale $s_a$ so the true activation is $x_i = s_a \cdot a_i$. The ternary weight can be represented as $w_j \in \{-1,0,1\}$ with its own scale $\gamma$ (the absmean). When you compute the attention pre-softmax scores you need the quantity

$$S = \frac{Q K^T}{\sqrt{d}}.$$

If $Q$ and $K$ come from BitLinear with ternary weights and $\text{int8}$ activations, an efficient implementation computes the integer dot products (sums of products of small integers) using integer additions/accumulators. Converting that integer accumulator to the real-valued dot product is then a single scale multiplication:

$\text{real\_dot} = s_q \cdot s_k \cdot \text{int\_dot},$

where $s_q$ and $s_k$ are the scales of $Q$ and $K$ produced by their per-token/per-layer quantization (and $\text{int\_dot}$ is the integer accumulator). Then you divide by $\sqrt{d}$. That division and the softmax exponentiation/subtraction (the max trick) are numerically sensitive and are normally done in floating point ($\text{FP16}$ or $\text{FP32}$). In other words, the workflow that the paper implies and that is standard in similar low-bit LLM kernels is: do the heavy integer accumulation for throughput/energy, then dequantize the accumulator to FP and run the normalization and softmax in FP to avoid underflow/overflow.

Concrete numerical-stability points you should expect and why they matter. Softmax is unstable if you exponentiate large positive or negative numbers or if your dynamic range is very small so everything underflows. Practically this is avoided by (a) computing scores in FP after applying the integer→real scale, (b) using the subtraction-by-max trick before exponentiation:
$\mathrm{softmax}(x)_i = \frac{\exp(x_i - \max_j x_j)}{\sum_j \exp(x_j - \max_j x_j)},$
and (c) using $\text{FP16}$ or $\text{FP32}$ for the exponentials and sums. Using $\text{FP16}$ for the softmax is common and usually sufficient; $\text{FP32}$ can be used if extreme precision is required. The paper’s emphasis that “the majority of BitNet b1.58 is INT8 addition calculation” together with their integration into FasterTransformer and a 2-bit kernel implies a mixed integer accumulation + FP post-processing approach rather than a fully integer softmax pipeline.

What the paper explicitly gives you to implement this correctly. The two relevant facts in the paper are: (1) weights are ternary via an absmean scale $\gamma$, and (2) activations are scaled per token to a signed int8 range $[-Q_b, Q_b]$ (so you have a per-token activation scale). Those two scales let you recover the real-valued dot product from an integer dot product with a single multiplication, after which you divide by $\sqrt{d}$ and run max-subtract + exp + normalization in FP. That pattern preserves numerical stability and avoids integer underflow/overflow in the exponentials.

Practical check / where to look in code. The paper reports using FasterTransformer and the Ladder 2-bit kernel; these codepaths typically implement integer matmuls with dequantize-to-FP accumulators before softmax. If you need to be certain for a given build, inspect the attention kernel in the FasterTransformer/Ladder integration: look for integer-accumulate -> multiply-by-scale -> cast-to-FP -> softmax steps. If you’re reimplementing, follow the integer-accumulate + single-scale dequantization + FP softmax recipe described above.

Summary: ternary weights + $\text{int8}$ activations feed fast integer accumulators; the integer dot-products are rescaled (using weight and activation scales) and then the division by $\sqrt{d}$, max-subtraction and softmax exponentials/sums are done in FP ($\text{FP16}$ or $\text{FP32}$) to ensure numerical stability. The paper doesn’t give low-level kernel bit-for-bit code, but its design and cited tooling (FasterTransformer, Ladder) point to precisely this mixed integer→FP approach.

### What optimizer, learning rate schedule, and regularization are used to stabilize training from scratch with ternary weights?
Question:
Training from scratch with 1.58-bit weights can be tricky. Short answer: the paper does not publish a full low-level training recipe (optimizer, exact LR schedule, warmup steps, clip thresholds, etc.). Because your question asks how to stabilize training from scratch with ternary weights, I’ll give a concise, practical recipe and rationale that is consistent with the methods and constraints described in the paper, and that follows common practice when training quantized / discrete-weight LLMs from scratch. Treat this as recommended best-practices (not as something stated in the paper).

Recommended optimizer and core hyperparameters
Use AdamW (or an adaptive-moment optimizer with decoupled weight decay) with stable betas and an EPS tuned for reduced-precision gradients. AdamW is the de-facto choice for large Transformer training and is robust when paired with appropriate LR scheduling and weight decay. Typical starting settings that work well in practice are betas = $(0.9,\,0.95)$, eps = $10^{-8}$ (sometimes raised to $10^{-6}$ when training with aggressive quantization), and weight decay in the $0.01$–$0.1$ range (often $0.1$ for base LLaMA-style recipes, lowered for very small models). Lion can be used experimentally, but AdamW is the safer default if you want reproducibility.

Learning rate schedule and warmup
Use a linear warmup followed by cosine (or linear) decay. Warmup is important to prevent early-step instability with discrete weights and straight-through updates. For $3\text{B}$–$13\text{B}$ models a warmup of a few thousand steps (e.g., $2\text{k}$–$10\text{k}$ steps) is typical; scale up warmup proportionally with batch size and model size. Peak LR depends on total batch size: with very large effective batch sizes you can use higher peak LR; a safe baseline is in the $1\times10^{-4}$ to $3\times10^{-4}$ range for medium-sized LLaMA-like models when using AdamW. After warmup, cosine decay to a small final LR (or to zero) over the full training budget is standard.

Weight decay, layerwise LR, and parameter groups
Use decoupled weight decay (AdamW). Exclude scale parameters of RMSNorm and perhaps rotary embedding parameters from weight decay. Many LLaMA-style recipes use per-parameter-group settings (e.g., zero weight decay on normalization and embedding scale parameters). Optionally apply layer-wise LR decay (slightly lower LR for earlier layers) if you have found it helpful in FP training; it can help with stability but is not strictly required.

Gradient handling (clipping, accumulation)
Clip by global norm if you see occasional spikes; a typical global norm clip of $1.0$–$5.0$ is a reasonable safety net. Use gradient accumulation to reach a stable effective batch size when GPU memory limits your per-GPU batch. Large effective batch sizes are helpful to stabilize quantized training.

Regularizers and quantization-specific tricks
The paper’s quantizer uses an absmean scale and RoundClip to $\{-1,0,1\}$; to stabilize training around this discrete mapping you should:

- Use Straight-Through Estimator (STE) for backprop through the rounding; that is the usual implementation choice for ternary/1-bit models and is consistent with BitNet-style quantizers.
- Optionally use stochastic rounding during the early phase or when updating scale factors; stochastic rounding can reduce bias from rounding and sometimes helps convergence.
- Keep a floating-point shadow copy of weights for optimizer updates (update FP weights, quantize for forward). Training BitLinear commonly maintains FP weights and quantizes them each forward pass; this is required because the optimizer still needs continuous parameters to accumulate momentum.
- Consider a small amount of additive noise to gradients or to weights early on (temporary regularization) if you observe dead neurons or collapsed ternary patterns.
- Use periodic re-scaling or explicit clamping on the absmean scale $\gamma$ so it doesn’t collapse to tiny or huge values.

EMA and checkpoints
EMA (exponential moving average) of weights is helpful for evaluation stability and final model quality in many LLM recipes. It’s optional for training stability itself but gives a smoother final checkpoint for evaluation. If you use EMA, keep a decay in the $0.999$ or $0.9999$ range (tuned for step count).

Activation precision and other components
The paper uses 8-bit activations; that choice reduces activation noise relative to even lower precision and helps stability. Keep the non-weight parts (embeddings, RMSNorm parameters) in FP16/BF16 where possible. Removing biases (as in the paper) simplifies the parameter set.

Differences vs FP16 LLaMA recipes
The main differences you’ll likely need relative to an FP16 LLaMA recipe are (1) smaller peak LR or longer warmup to accommodate the discrete projection and STE dynamics, (2) maintaining FP shadow weights and careful handling of the quantizer scale, and (3) being prepared to use stochastic rounding or small noise early on if you see poor exploration of ternary states. Otherwise the macro structure (AdamW, warmup + cosine decay, weight decay, clipping) follows FP16 practice.

Monitoring and failure modes
Watch for these signals: rapid loss spikes early (increase warmup, enable clipping), collapse to mostly zeros or mostly $\pm 1$ (adjust scale $\gamma$ schedule, add stochastic rounding or noise), optimizer instability (increase eps or reduce peak LR), and divergence after checkpoint restores (try EMA or smaller LR).

If you can live without a specialized kernel, you can emulate inference by dequantizing weights to int8/float at load time, but you will lose the memory/speed benefits the paper reports.

Main caveats you should expect
1) Custom kernels are required for the reported speed/memory gains. The paper’s latency/memory numbers come from FasterTransformer + Ladder 2‑bit kernel. Using plain PyTorch or vanilla llama.cpp without an optimized 2‑bit implementation will not reproduce those gains and may even hurt performance (overheads from emulation or dequantization).

2) Build/extension work. For vLLM you’ll need either a PyTorch custom op that uses the Ladder kernel or a FasterTransformer-backed inference path. For llama.cpp you need to implement a GGUF loader/field and a CPU kernel for ternary matmuls (or emulate). These generally require custom build flags and linking to your kernel libs.

3) Attention/KV cache and activations. The paper uses 8‑bit activations and keeps LLaMA‑alike attention (RoPE, RMSNorm). The quantization emphasis is on linear layers; attention logic and KV cache semantics remain compatible but you need to ensure your runtime’s KV cache datatype (often float16 or int8) matches the model’s expected precision for correctness and to get memory benefits. Lossless KV cache compression to 4 bits is future work per the paper, not something already provided.

4) Checkpoints are quantization‑aware. BitNet is trained from scratch in the ternary regime (absmean quantization); you should not rely on post‑training quantization to reach the same accuracy. If you start with an FP16 LLaMA and post‑quantize, results may be worse than the paper’s trained BitNet checkpoints.

5) Export format gaps. Community runtimes have different expectations (tensor layouts, scale factors, per‑row vs per‑matrix scales, metadata). You will likely need a conversion tool that stores the ternary weights plus any scaling (the paper uses $\gamma = \frac{1}{nm}\sum_{ij} |W_{ij}|$ and RoundClip semantics), and adapt loaders for GGUF/GGML/HF. The paper does not show a ready GGUF exporter, so that conversion is on you unless the authors release tooling.

6) Hardware and numerical paths. The paper’s best results assume GPU kernels optimized for ternary/add-only style arithmetic. On CPU or general GPU backends without those kernels, you won’t see the same energy/latency gains.

Summary recommendation
If your goal is to reproduce the paper’s runtime/efficiency: use FasterTransformer with the Ladder 2‑bit kernel as they did (the paper tested that stack). If you want to run in vLLM/Hugging Face, prepare a custom BitLinear HF module or a conversion that maps ternary weights to an op that calls the Ladder kernel via a custom PyTorch extension; build vLLM against that. If you want to run on llama.cpp, expect to add a GGUF loader for ternary weights and write a CPU ternary matmul kernel (or temporarily emulate at higher precision while you develop a native kernel).

The paper promises “minimal effort” because the architecture and metadata are LLaMA‑compatible, but “minimal” here means minimal model redesign — you still need runtime glue (a kernel/plugin and loader/format adapter) to realize the reported speed/memory benefits.

### In MoE scenarios, which tensors dominate inter-chip traffic and how much does 8-bit activation quantization help?
Question:
The Discussion suggests 1.58-bit LLMs reduce MoE communication overhead. For top-k routing, most all-to-all traffic is activations. If activations are already 8-bit, what is the measured bandwidth reduction compared to FP16 for realistic MoE setups (number of experts, capacity factor)? Are router logits and auxiliary losses computed in higher precision? Any empirical throughput/latency measurements showing the reduction in all-to-all time with BitNet b1.58?
Answer:
Short answer: the paper states (and is consistent with standard MoE implementations) that activation tensors dominate the inter‑chip (all‑to‑all) traffic under top‑k routing, and switching activations from FP16 to 8‑bit cuts activation bandwidth roughly in half. If activations are already the dominant fraction of communicated bytes, that yields close to a $2\times$ reduction in all‑to‑all bandwidth and roughly similar reduction in all‑to‑all time. BitNet b1.58 itself does not publish a direct, measured all‑to‑all timing breakdown for MoE with BitNet b1.58, nor an explicit router‑logits precision statement, so the rest below explains how to get the quantitative estimate and what the paper does and does not report.

Why activations dominate (intuitive + formula)
Top‑k MoE routing sends routed activations (the token hidden vectors or the per‑expert micro‑batches) between devices. The size of that traffic is proportional to the number of routed tokens times the hidden dimension times the bytes per element. Concretely, if you route $N$ routed tokens of hidden size $D$, the payload is $N\cdot D\cdot B$ bytes (where $B$ is bytes/activation). Weights and other metadata are either kept local or shipped less frequently, so when top‑k routing dispatches many tokens the activation terms are the largest term in the all‑to‑all. That is exactly the statement the paper makes in its MoE discussion.

Quantitative reduction from FP16→INT8 activation packing (simple arithmetic)
FP16/BF16 use 2 bytes per element; an 8‑bit activation format uses 1 byte. So for the activation portion alone you get:
$\text{bandwidth\_activation\_ratio} = \dfrac{B_{\text{int8}}}{B_{\text{fp16}}} = \dfrac{1}{2} = 0.5$.
So activation bandwidth is halved.

Effect on overall all‑to‑all bandwidth/time depends on fraction $f$ of communicated bytes that are activations. If activations are fraction $f$ (e.g., $f\approx 0.8\text{--}0.95$ in typical top‑k MoE setups where many tokens are dispatched), the total communicated bytes shrink to $f\cdot 0.5 + (1-f)\cdot 1$ of the original. For example:
- If $f = 0.9$, total bandwidth $\approx 0.9\cdot 0.5 + 0.1\cdot 1 = 0.55 \Rightarrow$ a $\approx 1.82\times$ reduction.
- If $f = 0.8$, total bandwidth $\approx 0.8\cdot 0.5 + 0.2\cdot 1 = 0.6 \Rightarrow$ a $\approx 1.67\times$ reduction.
So “about $2\times$” for activation‑dominated cases and somewhat less if non‑activation bytes are material.

Realistic MoE parameters (E, capacity factor, top‑k) and where this matters
The paper does not give a per‑MoE benchmark with explicit expert count $E$ and capacity factors showing all‑to‑all times. But in realistic MoE deployments (top‑k routing with $k=1$ or $2$, capacity factor $1.25$–$1.5$, many tokens routed to experts across devices), the routed activation volume scales with token count$\times D \times k \times \text{capacity}$. For bigger $D$ and larger sequence lengths the activation fraction $f$ increases, making the INT8 win closer to $2\times$. If your MoE sharding sends some weight shards or auxiliary scalars too, those are small compared to routed activations except in extreme tiny $D$ cases.

Router logits, auxiliary losses precision
The paper describes BitNet b1.58 as using 1.58‑bit weights and 8‑bit activations and otherwise LLaMA‑alike components. It does not explicitly state the numerical precision used for router logits or auxiliary loss accumulators in MoE setups. In practice, router logits and gating computations are usually kept in higher precision (FP16/BF16) for numerical stability and accurate softmax/routing probabilities; the paper does not contradict that practice but does not document an MoE implementation detail. My recommendation (consistent with common practice and what the paper implies by keeping non‑linear components LLaMA‑alike) is to keep router logits and aux‑loss accumulators in FP16/BF16 while quantizing the routed activation payload to INT8 for transfer.

Empirical throughput/latency measurements in the paper
BitNet b1.58 reports end‑to‑end latency, memory, energy and throughput gains versus FP16 LLaMA across dense (non‑MoE) models: examples include $2.4\text{--}4.1\times$ speedups and $3.3\text{--}3.6\times$ memory reductions for certain sizes and an $8.9\times$ higher throughput for 70B on two A100s. However, the paper does not publish a MoE all‑to‑all timing breakdown nor a direct measurement of “all‑to‑all time reduced by INT8 activations” for MoE specifically (no BitNet b1.58 MoE microbenchmarks or detailed network traffic traces are included). So you will not find an explicit measured number for BitNet b1.58 MoE all‑to‑all time in the paper.

How to measure in your setup (practical guidance)
To get an empirical number for your hardware/ MoE sharding: instrument the all‑to‑all/collective (e.g., NCCL alltoall or custom RDMA) and run two configurations that are identical except activation payload byte width (FP16 vs INT8). Use the same $E$, capacity factor, top‑$k$, $D$ and batch/seq length. Measure bytes sent and wall‑clock time of the collective. You should see activation bytes cut $\approx 50\%$ and collective time drop by roughly the same factor if the network is the bottleneck; if compute or collectives metadata dominates you’ll see a smaller end‑to‑end drop, consistent with the $f$ formula above.

Summary
The paper asserts activations dominate MoE inter‑chip traffic and quantizes activations to 8 bits. That change isolates a roughly $2\times$ reduction in activation bandwidth and, for activation‑dominated MoE setups (high $D$, many routed tokens, realistic capacity factors), translates to an overall all‑to‑all bandwidth/time reduction on the order of $1.6\text{--}1.9\times$ in typical cases. The paper does not publish router‑logits precision for MoE nor direct MoE all‑to‑all timing measurements for BitNet b1.58; router logits are typically kept in FP16/BF16 in practice for numerical stability. If you need exact measured timings for your topology and sharding, instrument the collective and compare FP16 vs INT8 activation payloads as described.

### How were latency numbers measured: prefill vs decode, sequence lengths, batch sizes, and sampling overhead?
Question:
The paper reports 'time per output token' using FasterTransformer. Was this measured in the decode phase with KV cache, or averaged across prefill+decode? What sequence length and batch size were used, and were tokens generated with greedy or with sampling (which can add overhead)? Are the reported speedups consistent across a range of batch sizes and context lengths, or do they vary significantly?
Answer:
Short answer: the paper gives some measurement facts (FasterTransformer backend; “time per output token”; throughput measured with sequence length $512$; energy/ end-to-end energy reported for $512$ tokens; batch size for throughput found by increasing until OOM) but it does not state explicitly whether the reported “time per output token” is measured only during autoregressive decoding with KV cache (decode-only) or averaged over prefill+decode, nor does it state the decoding sampling strategy (greedy vs sampling) or the exact batch/sequence settings used for every latency number. Because those details are not fully specified in the paper, you must treat some specifics as missing or inferred.

What is explicitly stated in the paper
The authors report latency and memory using the FasterTransformer codebase and say they “reported the time per output token, as it is the major cost for inference.” They also state that latency and memory numbers were measured with a $2$-bit kernel. For throughput experiments with the $70\mathrm{B}$ models on two $80\ \mathrm{GB}$ A100 GPUs they used pipeline parallelism and a sequence length of $512$, and they “increased the batch size until the GPU memory limit was reached” to report maximum batch size / throughput. They also report end-to-end energy for models with $512$ tokens.

What is not stated (and why it matters)
The paper does not explicitly say whether the “time per output token” is:
- measured only during the autoregressive decode phase with an existing KV cache (i.e., per-token decoding time, which excludes the initial prefill cost), or
- an average over the whole request including prefill (the cost to process a full context) plus the subsequent decode tokens.

This matters because prefill (attention over the full context to fill KV caches) is $O(L^2)$ in compute and can dominate latency for long contexts, while per-token decode with KV caching is typically much cheaper (roughly $O(1)$ per token for attention cost aside from the incremental KV updates). If you care about interactive latency, decode-with-KV is the relevant metric; if you care about a single long-batch inference (one-shot evaluation), prefill+decode matters.

The paper also omits the decoding sampling strategy (greedy vs. sampling with top-k/top-p). Sampling adds overhead: decoding code paths that call random sampling and possible CPU/GPU transfers can increase per-token latency relative to pure greedy argmax. It likewise does not list the exact batch sizes and context lengths used for each of the reported “time per token” numbers (except for the throughput experiment and the $512$-token energy/end-to-end number).

Reasonable inference from the paper
Given the language “time per output token, as it is the major cost for inference” and their use of FasterTransformer (which is commonly used to benchmark autoregressive decode with KV cache), it is plausible that the reported per-token times are measured during the decode phase with KV caching enabled (i.e., per-token generation after prefill). This is consistent with the typical LLM benchmarking practice where people quote “time per output token” for autoregressive generation. However, this is an inference — the paper does not say it explicitly.

What they do show about scaling and variation
The paper shows that speedups increase with model size (e.g., BitNet $b1.58$ is $2.71\times$ faster at $3\mathrm{B}$ and up to $4.1\times$ at $70\mathrm{B}$). That implies the relative benefit is larger when matrix-multiply dominated layers occupy more compute — so speedups will generally depend on model size. They also claim BitNet reduces activation size ($16$-bit $\to$ $8$-bit) and KV cache memory, enabling longer effective contexts for the same memory; that suggests latency and memory advantages for longer contexts too, but the paper does not provide a sweep of latency vs. context length or of per-token speedup across batch sizes. For throughput they explicitly varied batch size until OOM, using sequence length $512$, and show large batch-size advantages ($70\mathrm{B}$ BitNet supports up to $11\times$ the batch size of FP16 $70\mathrm{B}$ in that test).

Practical implications and recommended follow-ups
If you need definitive answers for experimental comparison or replication, request these specific measurements from the authors or reproduce them yourself with FasterTransformer. At minimum ask or measure: (1) prefill time (process full prompt/context) and decode-only per-token time with KV cache, reported separately; (2) the context length(s) used for each latency number (e.g., $1,\,128,\,512,\,2048$ tokens); (3) batch sizes used for latency (usually batch=$1$ is relevant for interactive latency) and for throughput; (4) decoding strategy (greedy vs sampling with top-k/top-p) and the sampling parameters; and (5) whether measurements include host/GPU synchronization and token-level CPU-side operations (sampling, logits postprocessing), since these add overhead. If you re-run tests, compare both prefill+decode and decode-only, and sweep batch sizes and context lengths to reveal where speedups vary.

One-line summary
The paper reports per-token time using FasterTransformer and gives throughput/energy details for sequence length $512$, but it does not explicitly state whether the per-token latency is decode-only with KV cache or averaged with prefill, nor which sampling mode was used; speedups are shown to increase with model size and are likely context/batch-dependent, so for precise comparisons you should ask the authors or re-run controlled experiments that separate prefill and decode, sweep context lengths, and fix decoding mode (greedy vs sampling).

### Does adding zeros reduce energy further than binary weights, and why does the paper say energy is 'the same' as 1-bit?
Question:
Intuitively, allowing 0 should skip some additions compared to binary {-1, +1}, potentially reducing energy further. However, the paper states 'it has the same energy consumption as the original 1-bit BitNet.' Are zeros actually skipped in kernels, and if so, why would the energy be the same? Is the statement meant in an asymptotic or worst-case sense rather than measured practice?
Answer:
Short answer: No contradiction — adding a $0$ value can reduce work in principle, but in the way BitNet b1.58 is implemented and measured in the paper it doesn’t translate into lower arithmetic energy than the original $1$-bit BitNet. When the authors say “the same energy consumption as the original $1$-bit BitNet” they mean under their computation model and current kernels/hardware choices (the $2$-bit kernel they use and the arithmetic-energy model they cite), not that zeros can never reduce energy in every possible implementation.

Why that is true in practice (intuitive + technical):

1) Energy model / what they measure
The paper’s energy claims focus on arithmetic energy for matrix multiply (they explicitly use an energy model from prior work). That model compares the cost of $\mathrm{FP16}$ multiply+add vs integer additions used by BitNet. It treats the bit-width and operation types ($\mathrm{FP16}$ MUL/ADD vs integer ADDs) as the main determinants. Moving from $\{-1,+1\}$ to $\{-1,0,+1\}$ does not change the fundamental operation type used in their kernels (still integer add-style computation), so the arithmetic-energy numbers are essentially the same under that model.

2) Kernel implementation: sparse-aware skipping is not automatic
A ternary weight matrix can in principle skip contributions where the weight is $0$. But that requires either:
  - a sparse representation (store indices of nonzeros and use sparse matmul), or
  - a kernel that detects zeros and avoids the multiply/add per zero (or a specialized compressed/bitpacked sparse routine/hardware).
The paper uses an efficient $2$-bit dense kernel (Ladder / FasterTransformer) and measures latency/energy with that. Those kernels treat the weight matrix as dense $2$-bit values and compute using integer-add style routines; they do not dynamically skip per-element operations for zeros. So the presence of zeros does not remove per-weight arithmetic in that implementation.

3) Memory and control overheads reduce savings
Even if you could skip adds for zeros, practical savings can be small unless sparsity is high and the system is designed for it. Fetching weights from DRAM/SRAM and controlling branches or indirect indexing for sparse ops adds energy and latency. Many hardware/accelerator designs find that the cost of index handling, memory access patterns, and control outweighs the saved add for moderate sparsity. The paper’s discussion acknowledges that most cost is in nn.Linear and memory transfer; their kernels and energy accounting thus reflect density-preserving implementations.

4) How +/-1 is handled
In many $1$-bit implementations the multiplication by $\{-1,+1\}$ is implemented as a sign-flip (a conditional negation) or by using bitplanes and integer accumulation. Those implementations are already very cheap compared to FP multiplies. Replacing some sign flips with “skip” for zeros only changes the control/dataflow; it does not necessarily reduce the dominant integer-addition or memory-transfer energy in the current kernel.

What the statement is really saying
The claim is effectively: under our chosen implementation ($2$-bit dense kernel, FasterTransformer integration) and under the cited arithmetic-energy model, BitNet b1.58’s arithmetic-energy for matrix multiplications is the same order/quantity as the original $1$-bit BitNet. This is not a universal physical law — it’s an empirical/theoretical statement relative to their energy accounting and implementation choices, not a claim that zeros can never save energy in an alternative hardware kernel.

When zeros would actually reduce measured energy
If you want measured lower energy from zeros you need one (or more) of:
  - sparse/CSR-style storage and sparse matmul kernels that avoid loading and accumulating zeros, and hardware that makes indexed loads cheap,
  - hardware that implements ternary operations natively (e.g., skip wires or gating logic for zero weights) so that both fetch and arithmetic are cheaper,
  - very high sparsity so the benefit outweighs indexing/control overhead.
Without those, adding $0$ mostly helps modeling (filtering) but not the arithmetic-energy numbers in the measured/dense-kernel setup used in the paper.

Bottom line: the paper’s “same energy consumption as original $1$-bit BitNet” is grounded in their chosen kernels and energy model (dense $2$-bit kernel + integer-add energy accounting). Zeros can save energy in principle, but only if you change the compute/memory/kernel/hardware assumptions to exploit sparsity; the paper did not assume or measure that case.

### What happens to training dynamics when many weights quantize to 0—do parameters get 'stuck' and how are they reactivated?
Question:
With ternary quantization, weights near zero can flip to exactly 0. Are there mechanisms (e.g., latent FP shadow weights updated in FP, or STE ranges) that allow such weights to move away from 0 later if needed? Do you observe any dead-weight phenomena or training instabilities caused by massed zeros early in training?
Answer:
Short answer: in BitNet b1.58 training you do not permanently “kill” a parameter just because it rounds to 0 in one forward pass. The paper makes the weights ternary with an explicit scale (the absmean $\gamma$) and trains the network from scratch with quantized weights in the forward path; the usual and practical way to train such a quantized model is to keep (and update) full‑precision latent weights and propagate gradients through the quantization step with a straight‑through style estimator. Together, the learned scale $\gamma$ and the latent FP weights let coordinates that are currently rounded to 0 move away from 0 later if needed, and the authors report no catastrophic dead‑weight failures—models match FP16 performance at larger sizes and training scales.

Why that works (intuitive + technical):

1. Quantization with an adaptive scale prevents a fixed hard threshold. BitNet b1.58 first divides each weight matrix by
   $$
   \gamma = \frac{1}{nm}\sum_{ij}|W_{ij}|
   $$
   and then applies $\mathrm{RoundClip}(\cdot,-1,1)$. This makes the decision boundary for mapping to $-1,0,+1$ relative to the typical magnitude of that matrix. If all weights are small (early in training), $\gamma$ is small and the scaled values can still fall into the nonzero bins; conversely if weights grow, $\gamma$ rescales so the ternary assignment remains meaningful. Because the quantization threshold is tied to the running value of $\gamma$, sparsity is adaptive rather than a fixed “once-zero-always-zero” rule.

2. Latent full‑precision parameters + STE (implicit in any practical training-from-scratch ternary scheme). The paper states the model is trained from scratch with $1.58$-bit weights and gives the quantization mapping, so in practice you keep real‑valued weights $W$ and compute $\widetilde W$ via the RoundClip formula for forward. Gradients are propagated back to $W$ (commonly via a straight‑through estimator or clipped/approximated gradient through round/clip). That means a coordinate that evaluated to exactly $0$ in the forward pass still receives gradient signal (via the estimator) and the underlying real weight can change in subsequent updates, enabling reactivation.

3. Empirical outcome reported in the paper. The experiments show BitNet b1.58 matches FP16 perplexity and end‑task performance starting from the $3$B scale, and scales up to $70$B with large latency/memory gains. Those results imply no pervasive dead‑weight pathology that prevents learning: if many weights had been irreversibly stuck at $0$ and unable to be reactivated, the model would very likely underperform, especially at smaller sizes or early token budgets.

What you might see in practice and diagnostics to run. It’s normal to see transient high sparsity early on (many coordinates rounding to $0$) as the network discovers which connections are useful, but two mechanisms prevent permanent deadness: the latent FP weights can move under gradient updates, and $\gamma$ rescales the quantizer so the mapping boundaries shift over training. If you’re worried about stuck zeros in your implementation, monitor per‑layer ternary sparsity over time, check gradients for coordinates that are zeroed, and verify you are updating latent FP weights (not replacing them with pure ternary values). If you do observe dead weights, common remedies are slightly larger learning rates for the latent weights, biasing scale updates, annealing the clipping/rounding (soft quantization to hard over time), or adding small noise to the latent weights to help escape plateaus.

Bottom line: BitNet b1.58’s design (absmean scaling + training from scratch) together with the practical use of latent FP weights and STE-style updates makes quantized-to-zero weights reactivatable; the paper’s reported results indicate no catastrophic dead‑weight phenomenon affecting final performance.
