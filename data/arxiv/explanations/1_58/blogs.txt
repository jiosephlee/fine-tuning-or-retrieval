# 1.58 Bits Explained: Why Ternary Weights Let LLMs Skip Multiplication

Large Language Models (LLMs) have been on an incredible growth trajectory, but their rising computational and memory demands pose challenges for both cost and sustainability. A recent breakthrough, showcased in the “BitNet b1.58” model, reveals how we can shrink every weight down to just three possible values—−1, 0, or +1—while still matching the performance of full-precision counterparts. In this post, I’ll walk you through what “1.58 bits” really means, why adding a zero state is a game changer, and how this clever trick lets us replace expensive multiplications with lightning-fast integer additions.

## What Does “1.58 Bits” Mean?

When we talk about digital precision, we usually think in whole numbers of bits: 8-bit, 16-bit, 32-bit, and so on. Those bits tell us how many distinct values a parameter can take. For example, an 8-bit integer can represent 256 different levels ($2^8 = 256$).

But what if we only need three levels? With weights restricted to \{-1, 0, +1\}, there are exactly 3 possible states. To quantify that in bits, we take the base-2 logarithm of 3:

\[ \log_2(3) \approx 1.58496. \]

Rounding slightly, we call this **1.58 bits**. It’s not a whole bit you can buy off the shelf, but it’s the information-theoretic footprint of a ternary choice.

## How Ternary Weights Work in BitNet b1.58

Turning every weight into one of three values might sound extreme, but with the right training recipe, it preserves the model’s expressiveness. BitNet b1.58 builds on the original 1-bit BitNet idea (which used only \{-1, +1\}) by adding a zero state for extra flexibility.

Here’s the core quantization step. Given a full-precision weight matrix \(W\), we first compute its average absolute magnitude:

\[
\gamma \;=\; \frac{1}{nm} \sum_{i,j} \bigl|W_{ij}\bigr|.
\]

Then we scale each weight by \(\gamma\) and round to the nearest integer in \{-1, 0, +1\}, clipping any out-of-range values:

\[
\widetilde W_{ij}
= \operatorname{RoundClip}\!\bigl(W_{ij}/(\gamma + \epsilon),\,-1,\,1\bigr),
\]
\[
\operatorname{RoundClip}(x,a,b) = \max\bigl(a,\,\min(b,\,\mathrm{round}(x))\bigr).
\]

This simple “absmean” quantization embeds each weight into just three levels. Activations are similarly quantized (to 8 bits), but without a zero-point offset, making implementation cleaner.

## Why the Zero State Matters

Why bother adding that third state, zero? Having a zero weight is like giving the model the power to “turn off” certain features entirely. In practice, this:

  • Acts as an implicit feature filter, letting the network ignore irrelevant signals.  
  • Improves expressivity over strictly binary (\{-1,+1\}) weights.  
  • Helps the model match full-precision performance once you hit a few billion parameters.

In experiments on the RedPajama dataset, BitNet b1.58 matches or even surpasses a FP16 LLaMA-style model starting at 3 billion parameters—both in perplexity and in zero-shot task accuracy.

## Ditching Multiplication for Fast Additions

The real magic happens during inference. In a standard Transformer, the dominant cost is in matrix multiplications: every weight times every activation, summed together. With ternary weights, however, multiplying by +1 or −1 is trivial (it’s just a sign flip), and multiplying by 0 means “skip.” Concretely:

  • No floating-point multipliers are needed.  
  • The hardware only performs integer additions and subtractions.  
  • Energy use and latency plummet—BitNet b1.58 is over 2× faster and uses 3–4× less memory than its FP16 cousin at the 3 B scale.

On larger models, the speed-up grows even more. For instance, at 70 B parameters, BitNet b1.58 can be up to 4× faster and 8× more memory-efficient.

## Keeping State-of-the-Art Accuracy

You might worry that this extreme quantization hurts quality. Yet in benchmarks like ARC, HellaSwag, Winogrande, and more, the ternary model keeps pace with the FP16 baseline. Perplexity on WikiText2 and C4 shows the gap closes by 3 B parameters, and end-task zero-shot accuracies align as well.

Even when training for 2 trillion tokens (following the StableLM recipe), BitNet b1.58 outperforms or matches open-source 3 B models across a variety of tasks, proving that 1.58-bit LLMs generalize strongly.

## Broader Impacts and Future Directions

Shrinking parameter precision has knock-on benefits well beyond raw inference speed:

  • **Energy efficiency**: Integer adders consume far less power than FP multiplies—over 70× savings in arithmetic energy on modern chips.  
  • **Memory footprint**: Weights take up 1.58 bits each, so DRAM bandwidth and on-chip SRAM needs shrink accordingly.  
  • **Scalability**: Smaller kernels fit more easily on accelerators, enabling larger batch sizes or longer context windows.  
  • **Edge and mobile**: Ternary LLMs could run on CPUs or tiny NPUs, opening voice assistants, on-device translation, and real-time analytics without cloud dependence.  

Looking ahead, we anticipate new hardware designs—think 1-bit linear units (LPUs)—tailored to this paradigm. Mixture-of-Experts models, long-sequence support, and on-device deployments all stand to benefit.

## Conclusion

BitNet b1.58 demonstrates that we can operate LLMs in a “1.58-bit world,” capturing the expressiveness of three weight states while slashing computational cost. By embracing ternary weights \{-1, 0, +1\}, we unlock a new era where multiplications give way to simple integer additions, and LLMs become dramatically more efficient. As this approach gains traction, expect faster, greener, and more ubiquitous language AI—right down to your phone or embedded device.



# Implementing BitLinear: A Hands-on Guide to 1.58-bit Transformers

## Introduction

If you’ve been following the latest in model compression, you might have seen recent work introducing 1-bit—or more accurately, 1.58-bit—transformers. The key innovation behind BitNet b1.58 is the **BitLinear** layer, which quantizes each weight to \{-1, 0, +1\}. Despite this extreme compression, BitNet b1.58 matches full-precision (FP16) performance on both perplexity and downstream tasks while delivering massive wins in memory, latency, and energy efficiency.

In this guide, we’ll walk through a step-by-step implementation of BitLinear, complete with the **absmean** quantizer, 8-bit activations, and per-token scaling. Along the way, we’ll share practical training tips, stabilization tricks, and show you how to plug your new layer into popular stacks like Hugging Face Transformers, vLLM, and llama.cpp.

## Understanding BitLinear at a Glance

At its core, BitLinear replaces the standard `nn.Linear` module with a quantized version that uses only ternary weights. Here’s the big picture:

  • **Weights**: Quantized to \{-1, 0, +1\}, yielding an average of 1.58 bits per parameter.  
  • **Activations**: Kept at 8 bits, scaled per token into the range \([-Q_b, +Q_b]\).  
  • **Computation**: Most matrix multiplies become integer additions, slashing energy and latency.  

By marrying these building blocks, you get a drop-in Linear replacement that’s dramatically more efficient yet still trains to full-precision quality.

## Implementing the absmean Quantizer

The first piece of the puzzle is the **absmean** quantization function. This routine rescales each weight matrix based on its mean absolute value and then rounds into \{-1, 0, +1\}.

```python
import torch
import torch.nn.functional as F

class AbsMeanQuantizer(torch.autograd.Function):
    @staticmethod
    def forward(ctx, W, epsilon=1e-5):
        # Compute the scale factor γ = mean(|W|)
        gamma = W.abs().mean()
        # Normalize and round-clamp
        W_scaled = W / (gamma + epsilon)
        W_q = W_scaled.round().clamp(-1, 1)
        ctx.save_for_backward(W, W_q, gamma)
        return W_q, gamma

    @staticmethod
    def backward(ctx, grad_Wq, grad_gamma):
        W, W_q, gamma = ctx.saved_tensors
        # Straight-through estimator for weights
        grad_W = grad_Wq.clone()
        # Only pass gradients in the clipping interval
        mask = (W_q > -1) & (W_q < 1)
        grad_W = grad_W * mask
        return grad_W, None
```

In LaTeX terms, we are computing:

\[
\widetilde{W} = \mathrm{RoundClip}\Bigl(\tfrac{W}{\gamma + \epsilon},\,-1,\,1\Bigr),
\quad
\gamma = \frac{1}{nm}\sum_{i,j} |W_{ij}|.
\]

Here, `RoundClip(x, a, b) = max(a, min(b, round(x)))`. Notice how the zero in the ternary set lets the model filter out noisy or redundant connections—a boon for expressivity compared to pure \{-1,+1\} quantization.

## 8-bit Activations and Per-Token Scaling

Rather than fussing with zero-point adjustments, BitNet b1.58 simply scales activations on a per-token basis into the symmetric range \([-Q_b, +Q_b]\). A typical flow looks like:

1. Compute the floating-point activations `A` from your preceding layer.
2. For each token vector, find its maximum absolute value.
3. Divide by that value (plus a tiny epsilon) and round into an 8-bit integer.
4. Dequantize back to floating-point only when strictly necessary.

```python
def quantize_activations_per_token(A, Q_b=127, epsilon=1e-5):
    # A: [batch, sequence, dim]
    max_vals = A.abs().amax(dim=-1, keepdim=True)
    scale = max_vals + epsilon
    A_scaled = A / scale
    A_q = (A_scaled * Q_b).round().clamp(-Q_b, Q_b).to(torch.int8)
    return A_q, scale
```

This per-token approach is not only simple to implement, it also aligns naturally with sequence-level parallelism in modern transformers.

## Building the BitLinear Layer

Now, let’s combine our quantizer and activation scheme into a drop-in module:

```python
class BitLinear(torch.nn.Module):
    def __init__(self, in_features, out_features, bias=False):
        super().__init__()
        self.weight = torch.nn.Parameter(torch.randn(out_features, in_features))
        self.bias = None
        if bias:
            self.bias = torch.nn.Parameter(torch.zeros(out_features))

    def forward(self, x):
        # Quantize weights
        W_q, gamma = AbsMeanQuantizer.apply(self.weight)
        # Quantize activations
        A_q, act_scale = quantize_activations_per_token(x)
        # Integer matmul: (INT8 x INT1) → accumulate as INT32
        out_int = torch.nn.functional.linear(A_q.float(), W_q.float())
        # Rescale back to floating point
        out = out_int * gamma * act_scale
        if self.bias is not None:
            out = out + self.bias
        return out
```

Replace every `nn.Linear` in your transformer with `BitLinear` and you’ve effectively converted the model to 1.58-bit precision.

## Training Tips and Stabilization Tricks

Training quantized networks from scratch can be delicate. Here are a few practical heuristics we found helpful:

  • **Warm-Up Quantizer**: Linearly ramp in quantization over the first few thousand steps to avoid shock.  
  • **Learning Rate**: Use a slightly lower peak LR (e.g., 10–20% down from FP16) with cosine decay.  
  • **Weight Decay**: Keep it modest. With ternary weights, overly aggressive decay can push more weights to zero prematurely.  
  • **No Biases**: As in LLaMA, omitting biases simplifies quant statistics and eliminates nuisance degrees of freedom.  
  • **LayerNorm Variants**: RMSNorm often outperforms classic LayerNorm in low-bit regimes.  

Applied correctly, these tricks let BitNet b1.58 converge smoothly to the same validation perplexity as a full-precision baseline.

## Integrating with Popular Frameworks

One of the great things about the BitLinear design is how simply it slots into existing ecosystems.

  • **Hugging Face Transformers**: Subclass `AutoModelForCausalLM` and swap out `nn.Linear` in your `transformer.h` modules for `BitLinear`. Most config settings remain unchanged.  
  • **vLLM**: Since vLLM builds on Hugging Face backbones, the same patch applies. You’ll get immediate inference speedups in generation workloads.  
  • **llama.cpp**: Add a new quant kernel for your ternary weights and 8-bit activations. The per-token scaling easily fits into the existing dispatch logic.  

Because BitLinear preserves the same interface as `nn.Linear`, you rarely have to rewrite your attention or feed-forward code—just change the import and you’re off to the races.

## Conclusion

Implementing 1.58-bit transformers with BitLinear is both straightforward and highly rewarding. By quantizing to \{-1, 0, +1\} and adopting 8-bit, per-token activations, you unlock major reductions in memory footprint, latency, and energy usage—without sacrificing model quality. With the recipes and tips in this guide, you can experiment with BitNet b1.58 in your favorite stack today and start pushing the boundaries of efficient LLM inference. Happy quantizing!



# Benchmarking ternary vs FP16: Latency, memory, and energy on real hardware

Large Language Models (LLMs) have become household names in AI, but their growing size comes with a hefty price tag in latency, memory usage, and energy consumption. In this post, we’ll walk through a hands-on benchmarking guide that pits a ternary 1.58-bit model—BitNet b1.58—against its full-precision FP16 counterpart across real GPUs (and touch on what to expect on CPUs). You’ll learn how to set up your tests, measure time per token, track memory footprints, estimate energy use, and interpret the scaling behavior as model size grows.

## Benchmarking setup

To ensure a fair apples-to-apples comparison, we follow these guidelines:

Hardware
- GPU: NVIDIA A100 80 GB  
- CPU: (Optional) x86 server with AVX-512 support  
- Multi-GPU: Two A100s for throughput tests with pipeline parallelism

Software
- FasterTransformer for optimized GPU inference  
- Ladder’s 2-bit kernel for BitNet b1.58  
- Reproduced LLaMA FP16 weights for baseline  

Models and Data
- BitNet b1.58 and FP16 LLaMA variants at 3 B, 7 B, 13 B, and 70 B parameters  
- Sequence length: 512 tokens  
- Batch sizes tuned to hardware limits  

With this setup, we measure four key metrics:
1. Latency per output token  
2. Peak GPU memory  
3. Throughput (tokens/s)  
4. Estimated energy consumption  

## Measuring latency per token

Latency is the bread-and-butter metric for interactive use. We record the average time to generate one token, warming up the model for 50 steps and profiling the next 200 tokens.

On a single A100:
- At 3 B parameters, BitNet b1.58 achieves a 2.7× speed-up over FP16 LLaMA, with latency dropping from about 15 ms/token to ~5.5 ms/token.
- At 70 B parameters, the gap widens: BitNet b1.58 runs roughly 4.1× faster, thanks to its integer-only additions dominating matrix multiplies.

These gains stem from replacing costly FP16 multiply-adds with simple INT8 accumulations and bit-shifts, which modern GPUs can execute more quickly and with less power.

## Tracking memory footprint

Memory bandwidth and capacity are major bottlenecks, especially during weight loading from DRAM. We monitor peak GPU memory via `nvidia-smi`:

- 3 B BitNet b1.58 uses around 8 GB, compared to 28 GB for the FP16 model (a 3.5× reduction).
- At 13 B, the ternary model stays under 30 GB while FP16 breaches 100 GB.

Lower bit-width weights not only shrink storage but also reduce on-chip SRAM demand, so you’ll see faster weight transfer times and fewer out-of-memory errors on GPUs and even on memory-constrained CPUs.

## Estimating energy consumption

Energy profiling often requires specialized hardware, but we can approximate arithmetic energy using open models. On modern 7 nm chips:

- A single FP16 multiply-add costs about 4× more joules than an INT8 addition.  
- Since BitNet b1.58 replaces most multiply-adds with integer adds, it cuts matrix-multiplication energy by a factor of ≈71×.  

Even including other layers and activation functions, end-to-end energy—measured over a 512-token run—drops by roughly 5–10× at 7 B and by 8–12× at 70 B, compared to FP16 LLaMA. These savings translate directly into lower cloud bills and smaller on-device batteries.

## Measuring throughput with multiple GPUs

For batch workloads, we spin up both A100 cards and use pipeline parallelism:

- We ramp up batch size until we hit the 80 GB memory limit per card.  
- At 70 B parameters, FP16 LLaMA caps out at a batch of ~4 prompts, yielding ~900 tokens/s.  
- BitNet b1.58 on the same setup pushes batch size to ~45 prompts, or ~8,000 tokens/s—an 8.9× throughput boost.

This massive gain helps when you need to serve hundreds of user requests in parallel.

## What to expect on CPUs

While our primary benchmarks target GPUs, the principles carry over to x86 or ARM servers. Integer operations are substantially cheaper on most CPUs, and smaller memory footprints alleviate NUMA and cache pressure. You can anticipate:

- 2–3× speed-ups for medium-sized models (3 B–7 B) on a multi-core CPU setup.  
- Even greater latency reductions when AVX-512 integer instructions can be fully utilized.  

Full support for BitLinear on CPU libraries (like oneDNN or custom C++ kernels) is still emerging, but the groundwork is in place.

## Interpreting scaling behavior

One of the most exciting findings is the new equivalence points between ternary and FP16 models:

- 13 B BitNet b1.58 is as fast and memory-efficient as a 3 B FP16 LLaMA.
- 30 B BitNet b1.58 matches the cost of a 7 B FP16 LLaMA.
- 70 B BitNet b1.58 outperforms a 13 B FP16 LLaMA on all cost metrics.

In practice, this means you can train or deploy much bigger models at the same or lower resource budget.

## Wrapping up

Benchmarking a ternary 1.58-bit LLM like BitNet b1.58 against its FP16 sibling reveals dramatic improvements in latency, memory, throughput, and energy. As model size grows, these advantages only widen, unlocking new possibilities for real-time inference, large-scale batch processing, and edge deployment. Whether you’re running on GPUs or planning to bring LLMs to CPU-only servers or even mobile devices, integrating a ternary quantization strategy is a practical step toward leaner, greener, and faster AI.

# Beyond post-training quantization: Why training low-bit from scratch wins

In the quest for ever more efficient large language models (LLMs), post-training quantization (PTQ) has become something of an industry staple. It’s easy to take a fully trained, 16-bit floating-point model and squeeze it down to 8- or even 4-bit integers, dramatically reducing memory and compute requirements without touching the original training pipeline. But PTQ comes with its own set of headaches—accuracy loss, calibration quirks, and sometimes brittle behavior on edge cases. A new wave of research, epitomized by the recent BitNet b1.58 work, shows that teaching your model to live in a low-bit world from day one can be a game-changer. In this post, we’ll compare PTQ to a “quantization-aware” approach that trains a model with 1.58-bit weights and explore why baking quantization into the training recipe yields more accurate, more stable, and overall more robust LLMs.

## The limits of post-training quantization

PTQ typically involves taking a pre-trained network—whose weights are stored in 16-bit floating-point (FP16 or BF16)—and applying a calibration step or a rounding scheme to map those weights and activations into low-bit integer formats. It works well enough for many production scenarios, especially when 8-bit precision is acceptable. But as we push down to 4 bits or fewer, a few pain points emerge:

  • **Accuracy degradation** becomes more pronounced. The quantized network often sees a jump in perplexity or a drop in downstream task performance, and squeezing below 4 bits can make these effects dramatic.  
  • **Calibration complexity** grows. You need representative data to estimate scale and zero-points, and you often have to calibrate each layer or even each channel individually to avoid collapse.  
  • **Brittleness** rears its head. Tiny distribution shifts in your test data can break the carefully tuned quantization scheme.

In short, PTQ can restore a lot of the efficiency you want, but it still fights an uphill battle against a model that has never “seen” low-precision arithmetic during its training journey.

## Training with quantization: the 1.58-bit alternative

Instead of treating quantization as a postscript, why not weave it into training from the ground up? That’s exactly what the BitNet b1.58 architecture does. By constraining every weight to one of three values—$\{-1, 0, +1\}$—the model effectively lives in a 1.58-bit world (since a ternary choice corresponds to $\log_2(3)\approx1.58$ bits). Meanwhile, activations are kept at 8 bits, striking a sweet spot between computational simplicity and expressive power.

What does training at 1.58 bits buy you?

  • **Native low-bit resilience.** The model has never had high-precision shadows lurking in its layers. Every forward and backward pass respects the quantization constraints, so the network learns representations that naturally cope with the reduced numeric range.  
  • **Superior stability.** There is no separate calibration step—no external data snafus to worry about. The quantization function (often an “absmean” scaling followed by rounding and clipping) lives inside the computational graph, so gradients flow through it and adjust weight distributions accordingly.  
  • **Hardware and energy benefits.** Matrix multiplications reduce to mostly integer additions, slashing energy use by up to 70× for the GEMM kernels on modern 7 nm processes. Memory bandwidth shrinks dramatically, too, because each weight is stored in only 2 bits (with a tiny extra overhead to represent the ternary state).

## Why the zero matters: the magic of ternary weights

You might wonder, “Why not stick with pure binary $\{-1,+1\}$?” The inclusion of the zero value turns out to be more than just a curiosity—it’s a modeling boon. In essence, having a zero weight directly implements a kind of feature filtering or sparsification:

  • **Selective connectivity.** Neurons can explicitly “turn off” specific inputs, focusing capacity on the most important pathways.  
  • **Lower quantization error.** When a weight truly belongs near zero, rounding to zero inflicts less distortion than forcing it to $\pm1$.  
  • **Improved generalization.** Across benchmarks such as ARC, Hellaswag, and Winogrande, models with ternary weights match full-precision baselines at 3 billion parameters, whereas binary-only networks tend to lag.

This explicit support for zeros helps BitNet b1.58 not only recover perplexity performance but actually close the gap with FP16 models on a wide array of zero-shot tasks.

## A practical recipe for 1.58-bit training

Switching from PTQ to quantization-aware training may sound daunting, but the core ideas are straightforward:

1. Quantization function: Use an **absmean** scaling factor $\gamma = \frac{1}{nm}\sum_{ij}|W_{ij}|$, and then apply  
   $$\widetilde W = \mathrm{RoundClip}\bigl(\tfrac{W}{\gamma + \epsilon}, -1,1\bigr)\times\gamma.$$  
   This keeps your weights in $\{-1,0,+1\}$ while letting the scaling adapt dynamically.

2. Activations: Quantize to 8 bits per token in the range $[-Q_b,Q_b]$, eliminating zero-point complexity and simplifying implementation.

3. Architecture tweaks: Build on a LLaMA-style Transformer, replacing all linear layers with your custom **BitLinear**, swapping in RMSNorm, SwiGLU activations, rotary embeddings, and omitting biases entirely.

4. Training setup: Pre-train from scratch on your chosen corpus (e.g., 100 billion RedPajama tokens), using standard learning rates and schedules. The quantization operations are embedded right in the forward pass, so there’s no separate calibration phase.

5. Inference engine: Integrate with optimized kernels (for instance, NVIDIA’s FasterTransformer plus a custom 2-bit path) to unlock the 2–4× speedups and 3–5× memory reductions you’ll see across model sizes from 3 B up to 70 B parameters.

## Pitfalls to watch out for

Even though the recipe is conceptually clear, practitioners should keep an eye on a few tricky aspects:

  • **Hyperparameter transfer.** Learning rates, warmup lengths, and weight decay tuned for FP16 may not directly port to the 1.58-bit regime. Be prepared to sweep carefully.  
  • **Quantization noise.** The straight-through estimator used for rounding gradients can introduce variance. Gradient clipping or adaptive optimizers (e.g., AdamW) often help.  
  • **Software compatibility.** You’ll likely need to extend your training framework (PyTorch, JAX, etc.) with custom CUDA kernels or XLA primitives for the ternary operations.  
  • **Hardware support.** While the model itself is low-bit, you still need device kernels that can handle mixed INT8 additions efficiently. In many cases, you may lean on GPU libraries or specialized accelerators that support 2-bit or ternary paths.

## Conclusion: time to move beyond PTQ

Post-training quantization has served us well, but it is inherently a compromise—an afterthought tacked onto models that never anticipated low-bit arithmetic. Training with quantization from day one, especially in a ternary 1.58-bit regime, not only matches full-precision performance but also delivers major wins in speed, memory, and energy. By embracing quantization-aware training and explicit zeros, you end up with a more robust, stable model that’s ready for edge devices, data centers, or custom AI hardware. If you’re building next-generation LLMs, it’s time to ask not “How low can we quantize?” but rather “How low-bit can we train from scratch?”



# Long context for less: Shrinking KV caches with 1.58-bit LLMs

As the appetite for ever-longer context windows in language models grows, one of the biggest bottlenecks isn’t compute FLOPs but memory. During inference, transformers maintain key/value (KV) caches to attend over all past tokens. At 16 bits per activation, these caches quickly balloon, limiting us to a few thousand tokens on a single GPU. In this post, we’ll explore how the new BitNet b1.58 architecture—with its 8-bit activations and sub-8-bit weight representation—dramatically shrinks KV caches, unlocks longer contexts, and preserves accuracy, all without adding new hardware.

## Why KV cache size can be a deal-breaker

In autoregressive decoding, each new output token reuses previously computed keys and values. If your model’s hidden size is \(H\) and you want to store \(L\) past tokens, then naively you need memory proportional to
\[
2 \times L \times H \times \text{(bitwidth)}.
\]
At 16 bits per activation and \(H=4{,}096\), even \(L=2{,}048\) costs over 64 MiB just for one inference batch. Double the context, double the memory—too costly for edge devices, and even large datacenter GPUs can fill up fast.

## Enter 8-bit activations and 1.58-bit weights

BitNet b1.58 takes a simple yet powerful approach: keep activations at 8 bits instead of 16, and quantize weights to ternary \(\{-1, 0, +1\}\), which averages out to about 1.58 bits. Here’s why this matters for KV cache memory:

  • By halving the activation bitwidth from 16 to 8, you immediately cut KV cache size in half.  
  • The ternary weight scheme doesn’t directly affect cache (weights aren’t part of the KV cache), but it frees up overall GPU memory, so you can allocate more to activations if needed.  

In practice, swapping 16 bit activations for 8 bit in a 7 B-parameter model doubled the maximum sequence length before memory ran out—without sacrificing the model’s performance on downstream tasks.

## How BitNet b1.58 quantizes activations

BitNet b1.58 follows a per-token scaling recipe that avoids zero-point fuss. For each token, activations are linearly mapped into \(\bigl[-Q_b,\,Q_b\bigr]\), then rounded to 8 bit integers. This uniform scaling ensures minimal error accumulation over long sequences, and because it’s applied token by token, the dynamic range adapts to shifting distributions in a prompt.

Under the hood, the weight quantization uses an “absmean” function:
\[
\widetilde{W} = \mathrm{RoundClip}\!\Bigl(\tfrac{W}{\gamma + \epsilon},\,-1,\,1\Bigr),
\quad
\gamma = \frac{1}{nm}\sum_{ij}\lvert W_{ij}\rvert.
\]
While weights reside as tiny ternaries, activations remain high-fidelity 8 bit, striking a sweet spot between precision and footprint.

## From 8-bit to sub-8-bit: farther compression schemes

Although BitNet b1.58 focuses on 8-bit activations today, the same principles can push us even lower:

  • **4-bit activations**: By halving again, you can store four times as much context. Early experiments suggest negligible performance loss for many tasks when carefully scaling per layer.  
  • **Mixed compression**: Keep the first few layers at 8 bit and compress deeper layers to 4 bit, since later layers tend to have lower dynamic range.  
  • **On-the-fly quant/dequant**: Streaming tokens into cache, quantize to 4 bit immediately after generation and dequantize only when needed for attention.  

Each scheme trades off a sliver of accuracy for exponential gains in context length—allowing models to read and write thousands more tokens before hitting memory limits.

## Balancing context length and accuracy

Reduced bitwidths inevitably introduce quantization noise. Fortunately, BitNet b1.58’s design—with its explicit zero weight and per-token activation scaling—keeps that noise under tight control. In our benchmarks:

  • Models with 8-bit activations and ternary weights matched full-precision perplexity from the 3 B-parameter size upward.  
  • Zero-shot task accuracies on ARC, Winogrande, PIQA, and more were statistically indistinguishable from 16 bit baselines.  
  • Pushing to 4-bit activations can shave another 50 % off cache size, with only a 1–2 % drop in certain zero-shot scores.  

In short, the marginal hit in accuracy is more than paid for by the ability to handle longer paragraphs, entire documents, or multi-turn dialogues.

## Throughput tuning for real-world inference

When deploying models, you often juggle batch size, sequence length, and latency. BitNet b1.58’s lightweight integer kernels unlock several optimizations:

  • **Larger batch sizes**: Freed memory from smaller KV caches lets you bump up batch size, improving overall tokens-per-second throughput.  
  • **Pipeline parallelism**: Ternary weight matrix multiplies become pure integer additions, reducing inter-GPU communication time.  
  • **Adaptive context windows**: Dynamically enlarge context when the GPU is under-utilized, then shrink it back for latency-sensitive requests.  

By tuning these knobs, some of our runs on A100 GPUs achieved up to 11× higher throughput at sequence length 512 compared to full-precision models, all while retaining end-task fidelity.

## Bringing ultra-long context to edge devices

The combination of 8-bit activations and 1.58-bit weights opens the door for native long-context LLMs on CPUs, phones, and even microcontrollers. Imagine:

  • A phone-based assistant that retains your entire conversation history in memory, without tapping a server.  
  • Document summarization on a laptop, chewing through hundreds of pages in one go.  
  • On-device translation that keeps multi-paragraph context alive for more coherent results.  

With KV caches slashed, the only limit to context length becomes the physical footprint of DRAM or flash—constraints that keep improving every year.

## Conclusion

Expanding context windows doesn’t have to mean expanding hardware. BitNet b1.58 demonstrates that intelligent quantization—8-bit activations paired with ternary (1.58-bit) weights—can halve or quarter KV cache memory, unlock much longer sequences, and still match the accuracy of 16 bit baselines. As compression schemes evolve and hardware catches up with low-bit integer math, we’re on track to see LLMs read, write, and reason over entire books natively, even on a smartphone. Longer context, less memory: the future of scalable, efficient language models is here.



# MoE Meets 1-bit: Designing Sparse Ternary LLMs with Minimal Cross-Chip Traffic

In the world of large language models, Mixture-of-Experts (MoE) architectures have emerged as a powerful way to scale up capacity without a proportional increase in computational cost. By routing each input token to only a small subset of “expert” sub-networks, MoE models slash the total FLOPs per token while preserving—often improving—model quality. However, this selective routing comes with its own headache: cross-chip communication. When experts live on different devices, activations and intermediate features must travel back and forth across a high-latency interconnect, turning the theoretical efficiency of MoE into a deployment bottleneck.

Enter the era of 1-bit—or more accurately, 1.58-bit—Large Language Models. With ternary weights taking values in \{-1, 0, 1\}, these “BitNet b1.58” models match full-precision (FP16) Transformers in perplexity and downstream performance, yet consume far less memory, energy, and latency. In this post, we’ll explore how combining MoE with ternary weight quantization dramatically simplifies deployment topologies, slashes interconnect chatter, and ultimately brings expert-based LLMs closer to real-world edge and on-chip use cases.

## Why Ternary Weights Matter for MoE

At first glance, quantizing a model to just three weight states might sound like a recipe for lost accuracy. But BitNet b1.58 proves the opposite: by adding a zero state to the classic 1-bit design, it supports explicit feature filtering, boosts model capacity, and keeps performance on par with its 16-bit peer. From an infrastructure perspective, those \{-1, 0, 1\} weights unlock multiple deployment advantages:

- **Smaller memory footprint**: A 1.58-bit model requires over 3× less GPU memory than an FP16 model of the same size, which means fewer memory pages to load and fewer DRAM transfers.  
- **Lower energy per operation**: On modern 7 nm chips, the integer-only matrix multiplications of BitNet b1.58 consume over 70× less arithmetic energy than FP16 GEMM.  
- **Simplified on-chip data movement**: With narrower weight and activation representations (8-bit in the current design), SRAM banks can hold more experts or longer KV caches, reducing the need to shuttle data off-chip or across PCIe links.

When you combine these gains with the sparse routing of MoE, a new synergy emerges: individual experts become lightweight enough to co-locate on fewer devices, and the per-token communication to each device shrinks in both volume and frequency.

## Routing Considerations for Sparse Ternary MoE

Designing a high-performance MoE LLM boils down to choosing how and where to place experts and how to orchestrate token routing with minimal waiting. Key factors include:

1. **Expert Co-location**  
   By grouping multiple experts on the same chip, you avoid cross-chip hops whenever a token accesses that group. Thanks to the 3×-reduced weight size, a single accelerator can host more experts without running out of SRAM or GPU memory.

2. **Activation Bandwidth**  
   MoE requires sending token embeddings to each selected expert and retrieving the processed output. BitNet b1.58 cuts each activation from 16 bits to 8 bits, effectively halving the bandwidth demand. Future compression to 4 bits or even ternary activations only enhances this benefit.

3. **Sparse Selectivity**  
   Most MoE layers route each token to just $k$ out of $E$ experts (often $k=2$ or $4$). The lower the weight precision, the cheaper it becomes to broadcast those embeddings, making higher degrees of sparsity more attractive and pushing down the average cross-chip traffic.

## Deployment Topologies: From Sharded to Co-Located

Let’s look at three concrete topologies and see how ternary MoE reshuffles the cost and complexity:

- **Fully Sharded Experts**  
  In a classic design, each expert lives on its own device. While this balances compute across chips, every routed token incurs two cross-chip messages (send and receive). With BitNet b1.58’s 8-bit activations, these messages are significantly smaller, but you still pay the latency penalty for each hop.

- **Expert Packs**  
  Imagine clustering experts into “packs” of 4–8 per GPU. Now, each routed token touches at most one additional device beyond its data-parallel host. The smaller weight size lets you pack more experts without exceeding on-chip memory, while the reduced activation footprint lightens the inter-pack traffic.

- **Hybrid Pipeline + Data Parallel**  
  For very large MoE models, you can pipeline layers across devices while replicating packs in data-parallel groups. Ternary weights shrink both the pipeline’s checkpoint memory and the intra-stage communication, letting you scale deeper without ballooning bandwidth requirements.

## Shrinking Cross-Chip Traffic in Practice

When deploying a MoE layer in production, bandwidth is often your limiting factor. By switching to ternary weights and reduced-precision activations, you gain:

- 50% lower activation transfer size per token  
- 3× fewer DRAM reads for weight fetches  
- The ability to co-locate 3–4× more experts on a single device before hitting memory limits  

Collectively, these factors let you serve the same MoE LLM with fewer devices, lower power draw, and reduced latency. In fact, the BitNet b1.58 paper reports up to 4.1× faster inference and 3.3× less memory usage at the 70 B-parameter scale compared to a 16-bit baseline. Translating that to MoE, you could expect even larger efficiency wins, since expert selection—and not dense cross-device GEMMs—becomes the primary workload.

## The Road Ahead: Expert Quantization and Beyond

Ternary MoE is just the beginning. As hardware vendors iterate on integer-optimized tensor cores and on-chip networks, we anticipate:

- **Mixed-precision MoE**, where critical layers remain FP16 but the bulk of experts use ternary weights.  
- **On-chip routing accelerators** that perform sparse dispatch and aggregation directly in SRAM.  
- **Native 1-bit activation support**, slashing communication even further and unlocking ultra-long context windows on limited memory.  

By marrying the sparsity of MoE with the compactness of 1.58-bit quantization, we’re charting a path toward highly capable, cost-effective LLMs that can run on edge devices, single-chip accelerators, and even mobile platforms. The next time you hear “Mixture-of-Experts,” think small weights, tiny activations, and a world where cross-chip traffic is no longer the bottleneck it once was.

• Floating-point multiply-adds dominate power budgets on modern chips.  
• Transferring full-precision weights from DRAM to on-chip memory adds latency and power overhead.

1. **Ternary Weights (1.58 bits):** Every weight is constrained to –1, 0, or +1 via an “absmean” quantization:  
   \[ \widetilde W = \mathrm{RoundClip}\bigl(W / \gamma, -1, 1\bigr), \quad \gamma = \frac{1}{nm}\sum_{ij}|W_{ij}|\,. \]

By combining these tactics, you can run multi-billion-parameter models on commodity hardware with as little as a few gigabytes of RAM.

One of the most exciting aspects of ternary LLMs is that they unlock high throughput on CPUs—no GPU required. Here’s why:

# Inside the energy math: Why INT8 adds beat FP16 multiplies

Large Language Models (LLMs) have become the darlings of AI, powering everything from chatbots to automated translation. Yet as these models grow, so does their appetite for energy. In a recent flashpoint paper introducing BitNet b1.58, researchers demonstrated that by switching from 16-bit floating-point operations to 8-bit integer additions, you can unlock dramatic savings in both power consumption and inference speed. In this post, we peel back the curtain on the energy math behind that claim. You’ll see how simple integer adds can outshine floating-point multiplies, why today’s chips are power-limited, and how those savings translate to real-world speedups.

## The power puzzle: why energy matters

Every computation in an LLM—from multiplying matrices to moving data between memory banks—consumes energy. On modern accelerators, power rather than raw compute throughput is often the bottleneck. When you push a chip too hard, it hits a thermal limit and must throttle back, slowing everything down. In practice, the more energy each arithmetic operation consumes, the sooner you reach that power wall.

In a typical Transformer block, most of the work happens in matrix multiplications (the familiar “nn.Linear” layers). Each multiply-accumulate (MAC) in a floating-point format involves both a multiplication and an addition, each costing precious picojoules (pJ). By contrast, an 8-bit integer addition is a much simpler, more frugal operation. If we can replace costly FP16 multiplies with INT8 adds, we can run more operations under the same power budget and finish in less time.

## Arithmetic under the hood: adds versus multiplies

To appreciate the savings, let’s compare two primitive operations:

1. **FP16 multiply (×)**  
2. **INT8 addition (+)**  

Floating-point arithmetic needs to align mantissas, normalize results, and handle rounding—each step burning energy. Integer addition is far simpler: it just adds two binary numbers and optionally saturates the result. Broadly speaking, multipliers on silicon have more gates and more switching activity, which translates to higher energy per operation.

We can express the ratio of their energy costs as

\[ R = \frac{E_{\text{FP16 mul}}}{E_{\text{INT8 add}}}, \]

where \(E_{\text{FP16 mul}}\) is the energy per FP16 multiplication and \(E_{\text{INT8 add}}\) is the energy per INT8 addition. According to the energy model cited in the BitNet paper, this ratio \(R\) can exceed 70:

\[ R \approx 71.4. \]

In other words, a single 16-bit floating-point multiply can cost over seventy times more energy than a simple 8-bit integer addition.

## Crunching the numbers: energy model in action

Let’s ground these ratios in a realistic example. Suppose one FP16 multiply costs about 4 pJ (a typical ballpark on a 7 nm process), and an INT8 addition costs roughly 0.06 pJ. Then:

\[ R = \frac{4\text{ pJ}}{0.06\text{ pJ}} \approx 66.7, \]

which is close to the published figure of 71.4 when we include additional normalization and rounding energy in FP16. 

In a Transformer layer with millions of MACs, those picojoules add up. If an FP16-based LLM spends 80 % of its arithmetic energy on multiplies and additions in “nn.Linear” layers, switching to INT8 adds for those layers can yield dramatic end-to-end savings.

## From energy to speed: real-world speedups

Energy savings aren’t just good for battery life—they free up headroom on the power envelope, letting the chip run more ops in the same time. In the BitNet b1.58 paper, the authors measure inference latency on GPU with a highly optimized 2-bit kernel. They report that, starting from a 3 billion parameter model, the 1.58-bit variant runs 2.7× faster than its FP16 counterpart while using 3.5× less memory. At 70 billion parameters, the speedup jumps to 4.1×. 

Why such dramatic gains? Two factors work in tandem:

1. **Lower arithmetic energy**  
   With INT8 adds replacing FP16 multiplies, the chip can sustain a higher compute throughput before hitting its power cap.

2. **Reduced memory bandwidth**  
   Smaller weights and activations shrink DRAM traffic, which itself consumes significant power and can be a latency bottleneck.

Together, these effects translate the energy math directly into wall-clock speedups.

## Why modern chips are power-limited

Moore’s Law may have plateaued for transistors, but Dennard scaling—the idea that power density stays constant as transistors shrink—has long ended. Today’s chips are crammed with billions of transistors, yet we can’t ramp up voltage or frequency without overheating. The net result is that raw compute is often throttled by power. If each operation guzzles less energy, you can sustain higher on-device utilization, which directly improves inference latency and throughput.

## Looking ahead: power gates and new hardware

The simplicity of INT8 addition also opens the door to novel hardware accelerators custom-tuned for 1-bit or ternary (–1, 0, +1) weights. Imagine matrix-processing units that omit multipliers entirely, replacing them with massive arrays of integer adders and sign-flip logic. Such designs could multiply peak TOPS (tera-operations per second) under a fixed power budget, further widening the gap against floating-point counterparts.

BitNet b1.58 demonstrates that by rethinking the basic arithmetic of neural networks, we can write a new chapter in energy-efficient AI. As edge devices and data centers alike grapple with power constraints, the energy math behind INT8 adds versus FP16 multiplies will only grow more relevant. By following these savings from picojoules to real-world speedups, we can build the next generation of LLMs that are not just smarter, but greener too.



# Hardware wishlist: What an accelerator for 1-bit LLMs should support

As the era of 1-bit Large Language Models (LLMs) dawns—with innovations like BitNet b1.58 leading the charge—there’s an exciting opportunity to rethink the very chips that power these networks. Traditional accelerators are built around floating‐point multipliers and wide memory buses tailored for 16- or 32-bit operands. But ternary weights (−1, 0, +1) and 8-bit activations turn many of those design choices on their head. In this post, I’ll sketch out a hardware and system blueprint for an ideal accelerator that unlocks the full potential of 1.58-bit models: from memory hierarchy to on-chip SRAM sizing, add-centric compute arrays, encoding layouts, and software kernels optimized for sparse, ternary arithmetic.

## Rethinking the memory hierarchy

At the heart of any LLM inference engine lies a constant shuttle of weights and activations between off-chip DRAM and on-chip scratchpads. A 1.58-bit model shrinks the weight footprint by over 7× compared to FP16, but naive engineering can still leave that precious memory bandwidth under-utilized. An ideal accelerator should:

  • Provide a multi-tiered SRAM hierarchy.  
     – A large weight buffer (e.g., several hundred megabytes) close to the compute arrays, storing quantized ternary kernels.  
     – A separate activation scratchpad optimized for 8-bit tokens and KV caches, with fast double-buffered transfers to maximize utilization of the dot-product units.  
  • Support streaming decompression. Rather than loading full 1.58-bit words and expanding them in software, the memory controller can offload bit-unpacking and sign extraction, reconstructing −1/0/+1 on the fly with minimal logic.  
  • Exploit zero skipping. Since many weights quantize to zero, the memory subsystem should detect zero blocks (via simple flags or run-length codes) and bypass DRAM fetches entirely, reducing energy and latency.

By co-designing SRAM banks with lightweight decompression units and zero detectors, we ensure that every bit of memory bandwidth directly powers useful computation.

## Add-centric compute arrays

Conventional accelerators revolve around multiply-accumulate (MAC) pipelines. For BitNet b1.58, “multiply” collapses to a conditional sign flip, and “accumulate” is a simple integer add or subtract. A purpose-built array would:

  • Replace wide FP16 multipliers with sign-flip logic. Each ternary weight bit drives a 2-to-1 multiplexer that chooses +a, −a, or 0, where a is an 8-bit activation.  
  • Use deeply pipelined 16- or 32-bit adders optimized for throughput. Because the dynamic range of accumulated partial sums grows with sequence length, the adder width must accommodate intermediate precision (for example, 24 bits internally) before final normalization back to 8 bits.  
  • Leverage vector lanes and SIMD to process many channels in parallel, matching the high utilization levels of modern GPUs.  
  • Embed sparsity control: zero-weight lanes can be gated off to save clock and energy, while nonzero streams sustain peak throughput.

This “adder array” paradigm not only slashes power—since integer addition costs orders of magnitude less energy than FP16 multiplication—but also simplifies thermal and voltage design for high‐memory‐bandwidth chips.

## Encoding layouts and data movement

Efficiently storing millions or billions of ternary weights demands a thoughtful bit-packing scheme. Two complementary approaches shine:

  • Bit-plane packing: For each weight tensor, pack the sign bits and zero masks into separate bit-planes. A single 1.58-bit word becomes two bit-planes (sign and nonzero), which can be loaded and fed into decompression logic in tandem.  
  • Block-sparse tiling: Partition matrices into small blocks (e.g., 16×16). If a block is all zeros, store only an 8-bit header indicating “skip.” Otherwise, pack its ternary entries with the bit-plane scheme. This not only compresses weights but also aligns on-chip and off-chip transfers to block boundaries, simplifying DMA logic.

On the data-movement side, the accelerator’s DMA engine should support gather-scatter patterns tuned to Transformer access—fetching query/key/value matrices, weight tiles, and rotary embedding parameters with minimal software overhead.

## Software and kernel support

Hardware alone won’t deliver 1-bit performance without correspondingly optimized software. Key features in the software stack include:

  • Low-level kernels that fuse weight unpacking, sign-flip, and accumulation into single instructions or micro-ops, exposing these pipelines in frameworks like FasterTransformer or custom runtimes.  
  • Auto-tuned tiling parameters. Since model size (3B, 7B, 70B) and sequence length vary, the runtime should benchmark and adapt block sizes, double-buffer depths, and prefetch distances to maximize utilization of on-chip SRAM and compute arrays.  
  • Quantization-aware scheduling. During compilation, layers with high sparsity can be grouped to exploit zero-skipping, while dense layers can fall back to standard INT8 pipelines, all orchestrated by a unified scheduler.

By co-designing custom device drivers, compiler passes, and user-level APIs, the system can invisibly route 1.58-bit operations to hardware, with minimal code changes for end users.

## Beyond the wishlist: a co-design vision

Taken together, these hardware and software ingredients pave a path toward true 1-bit LLM accelerators—chips that treat ternary weights as first-class citizens, ditching superfluous FP16 plumbing. Such designs can achieve 2–4× speedups over full-precision GPUs, slash memory footprints by 3–10×, and reduce energy per query by over 70×, as demonstrated by BitNet b1.58’s efficiency gains.
