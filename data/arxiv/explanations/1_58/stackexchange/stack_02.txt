### Does BitNet b1.58 keep any parameters in full precision (e.g., embeddings, RMSNorm gains), or are truly all weights ternary?
Question:
The abstract claims 'every single parameter (or weight) of the LLM is ternary {-1, 0, 1}', but in the Results section it says 'the embedding remains full precision.' Also, RMSNorm typically has learned scale parameters. Are token embeddings, positional embeddings/rotary parameters, RMSNorm scales, and SwiGLU gates all ternary in BitNet b1.58? If not, which components are exceptions, in what precision are they stored/used, and how much do they contribute to the overall memory footprint?
Answer:
Short answer: the paper explicitly calls out token embeddings as an exception (they “remain full precision”), and all nn.Linear-style weight matrices replaced by BitLinear are ternary $\{-1,0,1\}$ with 8-bit activations. The paper does not explicitly say that every tiny learned scalar/vector (RMSNorm scale, rotary frequency parameters, SwiGLU internal gates if implemented as per-layer matrices, etc.) was quantized to ternary, so you should assume embeddings are full-precision and the large matrix weights are ternary; the paper is silent about some small per-layer params.

Why I say this: the abstract makes the broad claim “every single parameter (or weight) … is ternary”, but the Results/Memory discussion explicitly states “the embedding remains full precision” and repeatedly contrasts the large-memory savings coming from quantizing the many large linear layers. In the architecture section they say they adopt LLaMA-alike components (RMSNorm, SwiGLU, rotary) and “remove all biases,” and they describe replacing nn.Linear by BitLinear and using the absmean ternary quantizer for weights. They also state activations are 8-bit. Those are the explicit, reliable claims in the paper:

- All large matrix weights (the BitLinear layers that replace nn.Linear) are quantized to ternary $\{-1,0,1\}$ via the absmean RoundClip scheme.  
- Activations are quantized to 8-bit.  
- Embeddings are explicitly kept full precision (the paper says this directly and uses this to explain why embedding memory share shrinks with model size).  
- Bias terms are removed.  
- The paper does not state that RMSNorm scales, rotary embedding parameters, or other small learned vectors were quantized; it only lists the component names (RMSNorm, SwiGLU, rotary) but gives no per-parameter-precision table.

Practical implications / memory contribution: embeddings are the main remaining FP component, but their relative memory share declines as model size grows (the paper notes this). Concretely, for typical transformer LLMs the embedding matrix size is roughly $\text{vocab\_size} \times d_{\text{model}}$. If embeddings are kept at FP16/BF16 (2 bytes per element), they will dominate memory for small models (e.g., a 3B model) more than for very large models (70B), where the many weight matrices (now ternary) would otherwise dominate. The authors use this exact observation to explain why BitNet’s speedup and memory gains grow with model size — the full-precision embedding is a relatively small leftover cost at big scales.

What the paper does not resolve and what you should check if you need exact accounting: the authors don’t explicitly state the precision of RMSNorm gain parameters, the rotary parameter storage format, or any tiny per-layer scalars. Those are typically tiny (vectors of length $d_{\text{model}}$ or small parameter lists) and so have negligible impact on total memory compared to embeddings and linear layers, but if you need byte-exact memory accounting (for an implementation or hardware design) you should consult the code release / ask the authors. The paper’s main empirical and systems claims are grounded in (1) ternary BitLinear weights, (2) 8-bit activations, and (3) full-precision embeddings being the only called-out FP remainder.

If you want a conservative engineering assumption: treat embeddings and any per-layer scalar gains (RMSNorm scale, rotary freq tables) as full precision (FP16/BF16) and all linear layer weights as ternary. That matches the explicit statements in the paper and gives near-identical memory/latency conclusions as the authors report.
