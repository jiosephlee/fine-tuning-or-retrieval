\title{Stack Exchange of the Paper: The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits}

### Why is a ternary weight alphabet described as 1.58 bits? Do real systems actually store 1.58 bits per weight?
Question:
The paper says every weight takes values in {-1, 0, +1} and calls the model '1.58-bit' because log2(3) ≈ 1.585. In practice, memory is byte-addressable and kernels typically pack into whole numbers of bits. Are the weights actually stored in 2 bits per parameter during runtime, or is there a custom packing scheme that approaches 1.58 bits on average? If 2-bit storage is used, how should we interpret '1.58 bits' in the reported memory savings?
Answer:
Short answer: "$1.58$ bits" is the information-theoretic cost per weight ($\log_2(3) \approx 1.585$) because each weight takes one of three values $\{-1,0,+1\}$. In real systems you almost always store them in whole-bit units at runtime (commonly $2$ bits per weight for fast kernels). The paper uses the shorthand $1.58$-bit to describe the representational entropy/capacity of the weights and the ideal compression limit, while the practical memory/latency numbers come from an implementation that uses efficient $2$‑bit kernels and packing/engineering tradeoffs.

Why the authors say $1.58$ bits
The number comes from basic information theory: a ternary variable with three equiprobable symbols carries $\log_2(3) \approx 1.585$ bits of information. Calling the model "$1.58$-bit" highlights that each parameter only needs three distinct states, i.e., far less information than a $16$-bit float.

Why real systems don’t store fractional bits directly
Physical storage is byte-addressable and hardware typically handles whole-bit lanes efficiently ($8$, $16$, $32$ bits) or specially engineered small lanes (e.g., $2$-bit, $4$-bit kernels). You cannot place $1.585$ bits per weight exactly in memory without variable-length encoding or cross-weight packing + decoding. So in practice inference implementations either:
- Use $2$ bits per weight packed into words (fast and simple for GPU kernels), or
- Use a compressed checkpoint format on disk (Huffman/arithmetic coding, bit‑packing plus metadata) that approaches the entropy limit for storage, but adds decoding cost at load time.

Entropy vs stored bits
"$1.58$ bits" is the theoretical lower bound (average information per weight) assuming an optimal code and the true symbol distribution. If the ternary distribution is uniform, optimal lossless compression could approach $1.585$ bits/weight; if the distribution is skewed (e.g., many zeros) the entropy is even lower and compression beats $1.585$ bits. But runtime speed/latency and hardware constraints usually favor fixed-width encodings ($2$ bits/weight) rather than entropy-coded streams.

What the paper actually does
The paper explicitly says they measured latency and memory with a $2$-bit kernel from Ladder integrated into FasterTransformer. That implies practical inference uses $2$-bit packed representations and $2$-bit arithmetic kernels. The "$1.58$-bit" label is therefore a descriptive, information-theoretic naming (and a claim about representational capacity and potential compression), while the measured memory/latency savings reflect the real implementation choices ($2$-bit kernels, packing, activation precisions, embedding exceptions, and other runtime overheads).

How to interpret reported memory savings
When the paper reports, for example, "$3.32\times$ less memory" or similar, those are empirical numbers based on their implementation ($2$-bit kernels, $8$-bit activations, etc.), not simply raw $16 / 1.585 = 10.1\times$ arithmetic. So treat "$1.58$-bit" as the model’s per-parameter entropy; treat the reported memory/latency gains as implementation-level, measured wins after packing and system engineering. If they had used entropy coding for storage and perfectly ideal packing everywhere, you could get closer to the $\log_2(3)$ factor, but that’s rarely compatible with high-throughput GPU inference.

Practical guidance
For checkpoints and distribution, you can compress ternary weights on disk with Huffman/arithmetic coding to approach $1.585$ bits/weight (or less if skewed). For inference you normally use fixed $2$-bit packed formats and optimized kernels for speed; the practical savings are what matter most and are what the paper reports.

Summary: "$1.58$ bits" = information-theoretic description ($\log_2(3)$). Runtime storage is typically $2$ bits/weight for speed and hardware convenience; the paper’s memory/latency claims are based on that practical implementation, so the label is accurate conceptually but not a literal claim that every weight is stored as $1.585$ physical bits in RAM during inference.
