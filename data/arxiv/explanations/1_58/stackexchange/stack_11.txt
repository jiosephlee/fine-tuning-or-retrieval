\title{Stack Exchange of the Paper: The Era of 1-bit LLMs: All Large Language Models are in 1.58 Bits}

### How fair is the latency comparison given BitNet b1.58 uses a 2-bit optimized kernel while FP16 uses standard kernels?
Question:
The results use FasterTransformer with the Ladder 2-bit kernel for BitNet b1.58. For FP16 baselines, what kernels and fused ops were enabled? Were both sides equally optimized (e.g., tensor cores, fused attention, flash-decoding)? Could kernel maturity explain part of the 2.4x–4.1x speedups, or do the authors have ablations controlling for kernel-level optimizations?
Answer:
Short answer: The paper does not provide enough implementation detail to conclude that the reported $2.4\times$–$4.1\times$ latency wins are purely due to the $1.58$-bit algorithm rather than differences in low-level kernel engineering. Because BitNet measurements explicitly use FasterTransformer + the Ladder $2$-bit kernel while the paper omits which FP16 kernels/fused ops were enabled, kernel maturity and different fusion/ tensor-core usage could plausibly account for a substantial fraction of the reported speedups. The authors do not publish the ablations needed to rule that out.

Why this matters (intuitively). In modern LLM inference the wall-clock token latency is dominated by a few well-engineered kernels: the large matrix multiplies (GEMMs) and fused attention/decoder kernels plus the KV cache management. The same high-level model implemented with two different low-level backends can show large latency differences because one backend uses: tensor cores / cuBLASLt tuned GEMMs, highly tuned int8/$2$-bit kernels (Ladder), fused attention (FlashAttention), fused MLP/WiGLU, and optimized decoding loops (flash-decoding). These micro-optimizations change memory traffic, kernel launch overhead, and compute utilization; they are orthogonal to the algorithmic bit-width. So if BitNet is measured with a mature $2$-bit Ladder kernel and the FP16 baseline is measured with an untuned or generic FP16 path, the comparison will conflate algorithmic gains (less work per op, less memory bandwidth) with engineering gains (better kernels).

What the paper says and does not say. The Methods/Results state: “measured using the FasterTransformer codebase” and “The $2$-bit kernel from Ladder is also integrated for BitNet b$1.58$.” The paper does not specify for the FP16 baseline whether the authors used FasterTransformer’s best FP16 kernels (cuBLASLt-backed, tensor-core enabled GEMMs), whether they enabled fused attention (e.g., FlashAttention or FasterTransformer fused attention), fused MLPs/activation, flash decoding / fused softmax & sampling, or other fused ops. There are no kernel-level ablations or profiler breakdowns in the paper.

How large an effect kernel maturity can have. Empirically in LLM work, switching from a generic implementation to a fully-optimized stack (tensor cores + cuBLASLt + fused attention/MLP + optimized decoding) often yields single-digit to several-times speedups depending on model size, batch, and sequence length. Ladder’s published $2$-bit kernels are themselves heavily optimized; comparing them to an FP16 run that does not similarly use the best FP16 primitives will overstate the model-level advantage.

What to ask the authors or to measure yourself to get a fair comparison. The minimal controlled experiments that would make the comparison convincing are:

1. Report exactly which FP16 kernels were used (FasterTransformer variant, cuBLAS/cublasLt versions, whether tensor cores were enabled, compute capability, and algorithm selection).  
2. Enable the same system features on both sides where applicable: use FasterTransformer FP16 optimized kernels (tensor cores/cuBLASLt), enable fused attention and fused MLP for FP16 if available, and ensure identical decoding loops (flash decoding vs. non-fused).  
3. Provide an ablation table that incrementally turns on the same kernel optimizations for FP16 (e.g., baseline FP16 -> FP16 + fused attention -> FP16 + fused attention + fused MLP -> FP16 + all fused/tuned kernels) to show how much each contributes.  
4. Microprofile the runtime breakdown (percent time in GEMM, attention, memory copy, decoding overhead) for both BitNet and FP16 (Nsight or nvprof). If BitNet’s win comes mostly from much faster GEMMs due to $2$-bit kernels, that is a kernel advantage; if the win remains after FP16 uses its best kernels, that supports an algorithmic advantage from lower-bit arithmetic and lower memory traffic.  
5. Run experiments on the same hardware, same batch/seq lengths, and report peak SM utilization and achieved TOPS to show hardware utilization differences.

Conclusion. As presented, the paper documents an appealing overall system result but lacks the kernel-level parity evidence needed to attribute the $2.4\times$–$4.1\times$ speedups uniquely to the $1.58$-bit representation. Kernel maturity and fusion differences could explain a nontrivial part of the gains. A fair, convincing latency comparison requires matching the FP16 baseline to the same level of low-level optimization and publishing the ablations / profiles described above.
