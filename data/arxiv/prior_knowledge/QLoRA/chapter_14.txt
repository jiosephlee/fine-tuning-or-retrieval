Introduction

Graphics Processing Units (GPUs) are the workhorses behind modern high-throughput numerical computing, and they are particularly valuable when you need to implement custom numerical kernels such as low-bit arithmetic or highly-tuned matrix multiply (matmul) routines. This chapter introduces the low-level concepts you need to design, implement, and profile efficient GPU kernels. We begin by explaining the core CUDA programming model: threads, blocks, warps, and kernels. Next we examine the memory hierarchy available on modern GPUs—global memory, shared memory, constant memory, and registers—and how each affects latency and throughput. We then cover essential performance concerns that come up in kernel design: coalesced memory access, occupancy, and bank conflicts. Building on that foundation, we walk through the high-level approach to implementing custom matmul kernels and low-bit compute kernels, emphasizing algorithmic choices and mapping to hardware. The chapter concludes with practical tooling and profiling techniques using nvprof and Nsight, and how to integrate custom CUDA kernels into higher-level deep learning frameworks such as PyTorch.

# CUDA programming model: threads, blocks, warps, kernels

At the heart of CUDA programming is a simple abstraction: parallel execution of many lightweight threads. A CUDA program launches kernels, each kernel being a function that executes in parallel across many threads. Threads are grouped into blocks, and blocks are organized into a grid. This hierarchical organization is designed to map efficiently onto the GPU’s hardware: thread blocks are scheduled onto streaming multiprocessors (SMs), and threads within a block can cooperate via fast shared memory and synchronization primitives.

A kernel is written as a function annotated to run on the device. When you launch a kernel you specify the grid size (number of blocks) and block size (number of threads per block). For example, you might launch a 2D grid of 2D thread blocks to map naturally to a matrix. Each thread can compute its unique global index using built-in variables such as \( \texttt{blockIdx.x} \), \( \texttt{threadIdx.x} \) and the block dimension \( \texttt{blockDim.x} \). The common pattern for a linear index in 1D is
\[
\texttt{int idx = blockIdx.x * blockDim.x + threadIdx.x;}
\]
which assigns each thread a distinct element of an array or tile to process.

Threads in a block can synchronize with \texttt{__syncthreads()} and can share data via shared memory. Blocks are independent: there is no built-in synchronization across blocks in the same kernel launch (except via kernel termination). This independence allows blocks to be scheduled in any order or concurrently, facilitating scalability across variable numbers of SMs.

A warp is a hardware scheduling unit. On NVIDIA GPUs, a warp consists of 32 threads (this number has been consistent for many architectures). The GPU executes instructions in a Single-Instruction Multiple-Thread (SIMT) fashion at warp granularity: all threads in a warp execute the same instruction at the same clock, although control divergence can cause some threads to be masked out temporarily. Because execution happens per-warp, understanding and controlling divergence is crucial: if threads within a warp take different control-flow paths, the warp will serialize execution of the diverging paths, which reduces effective throughput.

Thread/block sizing choices strongly influence resource usage and performance. A block size must be a multiple of the warp size for best utilization—commonly multiples of 32. The maximum number of threads per block is hardware dependent (often 1024). Choosing block dimensions to expose sufficient parallelism, while keeping per-thread resource usage (registers and shared memory) low enough to allow multiple blocks per SM, is the essential balancing act for performance.

# Memory types: global, shared, constant, registers, and their performance characteristics

Modern GPUs provide a layered memory hierarchy with distinct latencies, bandwidths, sizes, and access patterns. Understanding these memory types and their tradeoffs is vital to implement efficient kernels.

Global memory (device DRAM) is large (several GBs) and accessible by all threads, persistent across kernels, and coherent for loads/stores by the device. Global memory has the highest latency (hundreds of cycles) and can be the performance bottleneck unless accesses are scheduled and coalesced. Global memory bandwidth is very high (hundreds of GB/s on recent GPUs), but this bandwidth is only achieved if access patterns are aligned and coalesced to the memory subsystem.

Shared memory is a fast, on-chip, explicitly-mounted scratchpad local to a thread block. Each SM has a limited amount of shared memory (tens to hundreds of KB). Access latency is orders of magnitude lower than global memory (single-digit to tens of cycles) making it ideal for reuse of data within a block. Because shared memory is explicitly managed by the programmer (you load data from global memory into shared memory), it enables tiling strategies that reduce global memory traffic. Shared memory is partitioned into banks; bank conflicts occur when multiple threads in a warp access different addresses that map to the same bank, causing serialization—this concept is covered later.

Registers are the fastest memory resource and are private to each thread. Registers hold local variables and are crucial for performance. The number of registers per thread is hardware-limited; if a kernel requires more registers than available, the compiler spills variables to local memory, which is actually stored in global memory and is slow. The per-thread register count, together with shared memory usage, implicitly limits the number of concurrent threads (occupancy) per SM. Optimizing to reduce register pressure (e.g., by reusing variables, using smaller data types, or restructuring code) can increase occupancy and potentially throughput.

Constant memory is a small read-only memory space that is cached and optimized for broadcasting the same value to many threads. It’s ideal for small lookup tables or invariants. Constant memory access is cached per SM; if all threads in a warp read the same address, the access is efficient (served by cache or special constant broadcast), but if threads read different addresses, accesses may be serialized.

Texture memory and surface memory are additional GPU-specific read-only caches with specialized addressing and interpolation capabilities, historically used for graphics but sometimes exploited for irregular data access patterns in compute workloads. The details are similar to constant memory in that they provide cached reads but have separate caches and addressing behavior.

Performance characteristics in summary: registers are fastest but limited and private; shared memory is very fast and low-latency but limited per-block and requires careful bank-aware access; constant memory is fast for broadcasted reads; global memory is large and high-bandwidth but high-latency and must be accessed in an aligned, coalesced fashion to achieve peak throughput.

# Coalesced memory access, occupancy, and avoiding bank conflicts

Achieving high memory throughput requires attention to three interrelated concepts: coalesced global memory access, occupancy, and avoiding shared memory bank conflicts.

Coalesced memory access refers to aligning and grouping global memory accesses from threads in a warp so they can be serviced by as few memory transactions as possible. On modern GPUs, the memory subsystem services memory in aligned segments (e.g., 128B cache-line-like transactions), and if the 32 threads of a warp each access consecutive elements in an array with element size that nicely fits into the segment (for example, 4-byte floats in a tightly packed array), the hardware can service that access with a small number of transactions. If accesses are strided, scattered, or misaligned, each thread might generate a separate transaction or the hardware might have to load multiple cache lines, reducing effective bandwidth. To coalesce memory:

- Organize data in Structure of Arrays (SoA) rather than Array of Structures (AoS) when threads read the same field across many elements.
- Use contiguous memory layouts and let threads within a warp access consecutive addresses.
- Align arrays to appropriate byte boundaries and use data types (e.g., 32-bit or 64-bit) that match the desired access width.

Occupancy is the ratio of active warps on an SM to the maximum number of possible active warps. Higher occupancy can hide instruction and memory latencies: while one warp stalls waiting for memory, another can execute. However, occupancy is not a magic number—beyond a certain point, increasing occupancy yields diminishing returns, and sometimes lower occupancy with better per-thread resource utilization (less shared memory or registers) is preferable. Occupancy is constrained by per-thread register usage, per-block shared memory allocation, threads per block, and hardware limits. Use tools (see profiling section) to check occupancy. When optimizing, consider whether the kernel is memory-bound (limited by memory throughput) or compute-bound (limited by arithmetic throughput) — memory-bound kernels often benefit more from higher occupancy to hide long loads, while compute-bound kernels may not.

Shared memory bank conflicts occur because shared memory is physically divided into banks so multiple simultaneous accesses to different banks can proceed in parallel. If multiple threads in a warp access the same bank but different addresses, accesses serialize. On many NVIDIA architectures, there are 32 banks each mapped to successive 32-bit words, so stride-1 access by threads 0..31 maps to distinct banks and is conflict-free. However, if each thread reads index \(i \times s\) with stride \(s\) equal to the number of banks, then all threads map to the same bank leading to full serialization. To avoid bank conflicts:

- Organize shared arrays so that thread index maps to distinct banks when threads access unique elements. For example, store tiles in row-major order when threads map to columns.
- Add padding to shared memory arrays to shift the mapping and avoid common strides aligning to bank count: e.g., declare shared arrays with a small extra column offset so that element addresses do not collide across threads.
- Use vectorized loads/stores when possible to reduce per-thread accesses and better align data across banks.

When using shared memory collaboratively (e.g., in tiled matmul), carefully selecting tile dimensions to align with bank counts and warp sizes is essential for avoiding conflicts and enabling efficient cooperative loads.

# Implementing custom matmul kernels and low-bit compute kernels (conceptual overview)

Matrix multiplication is a canonical example where careful mapping of computation to GPU hardware yields orders-of-magnitude speed differences. The core idea behind high-performance matmul is blocking (tiling): partition matrices into tiles that fit into fast memory (shared memory or registers), load those tiles from global memory into fast memory once, and then perform many compute operations on the fast memory to amortize the cost of global loads.

Consider the multiplication \( C = A \times B \) with \( A \) of size \( M \times K \), \( B \) of size \( K \times N \), and \( C \) of size \( M \times N \). A common approach is to assign each thread block to compute a tile of \( C \) of size \( T_M \times T_N \). Within the block, threads cooperate: they load subtiles of \( A \) and \( B \) of size \( T_M \times T_K \) and \( T_K \times T_N \), respectively, into shared memory, then each thread computes its portion of the output tile by performing inner products over the loaded values, accumulating into registers. This strategy reduces global memory traffic from \( O(MKN) \) loads to fewer loads per tile. The tile sizes \( T_M, T_N, T_K \) are chosen to balance shared memory capacity, register usage, and coalescing.

Warp-level primitives and newer hardware features let you go further. NVIDIA provides warp-level matrix multiply-accumulate (WMMA) APIs and specialized Tensor Cores that perform mixed-precision matrix-multiply operations (e.g., FP16 inputs with FP32 accumulation) at very high throughput. When you cannot use hardware tensor cores (e.g., custom low-bit arithmetics), you can still optimize by mapping compute to warps and exploiting register-level tiling: each warp loads small micro-tiles into registers and performs many accumulations without using shared memory, or uses shared memory only to coordinate partial products across warps.

Low-bit compute kernels (e.g., 1-bit, 2-bit, 4-bit) change the multiplication and accumulation paradigm because operands are packed and arithmetic cannot be performed directly with standard floating-point instructions. Implementing low-bit kernels usually involves the following conceptual steps:

1. Data layout and packing: Pack multiple low-bit values into a standard word (e.g., pack sixteen 4-bit values into a 64-bit word). Choose a memory layout that allows coalesced loads of packed words by threads in a warp.

2. Unpacking and expansion: Upon loading a packed word, unpack into an efficient compute representation. For small bitwidths, this can often be done with bitwise operations (shifts and masks) and vectorized instructions. Unpack either into small integers stored in registers or into wider types used by the compute kernel. Unpacking may be interleaved with computation to avoid storing a full expanded buffer.

3. Bit-serial or specialized arithmetic: For very low bitwidths, you can implement bit-serial multiplication (process one bit-plane at a time) or take advantage of bitwise operations (e.g., popcount on AND for binary inner products). For example, binary matrix multiply can be implemented by computing XNOR between bits and counting ones (population count), then converting popcount to equivalent dot-product scores. Bit-serial approaches trade compute for memory: they reduce memory footprint at the cost of performing multiple passes over the data or performing additional bit operations.

4. Accumulation and casting: Accumulate results in an appropriate wider type to avoid overflow and to maintain precision. For example, accumulate multiple binary dot products into 32-bit integers, then scale and cast to floating point if needed.

5. Avoiding memory and arithmetic bottlenecks: Because unpacking and bit manipulations can be compute-heavy, you must carefully pipeline loads, unpacking, and arithmetic to keep arithmetic units busy while overlapping memory latency. Use shared memory to stage packed words or partial results if it improves access patterns. For kernels that combine low-bit inputs with higher-precision accumulators (mixed precision), ensure conversions are done efficiently and in-chunk to reduce overhead.

As a concrete conceptual example, imagine computing a matrix product where A and B are stored in 4-bit unsigned packed format. A high-performance kernel might:

- Assign each block to a tile of \( C \). Within the block, decide a micro-tile per thread (say each thread computes a \( 4 \times 4 \) subtile) and a micro-tile per warp.
- In a loop over \( K \) in steps of \( T_K \), each warp coalesced-loads packed words of A and B into registers. Each thread performs bit-manipulation to unpack its portion into four 8-bit integers using masks and shifts.
- Use vectorized integer multiply-accumulate (if available) or convert to FP16 and use vectorized FP16 FMA to accumulate partial results into registers. If using integer accumulation, widen to 32 bits to prevent overflow.
- Use shared memory only when necessary to transpose or reorganize tiles for coalescing when next iteration requires different layout.
- Write final tile values back to global memory with coalesced stores, possibly converting back to the desired output type.

Design decisions depend heavily on the target GPU architecture. If your architecture supports 8-bit or 4-bit tensor cores (some vendors are adding such features), you might offload blocks of low-bit computation to those specialized units; otherwise, you must emulate using integer or floating instructions.

Beyond arithmetic, performance-critical matmul kernels must also manage synchronization and parallelism granularity. Use hierarchical parallelism: grid -> blocks -> warps -> threads. When necessary, exploit warp-synchronous programming: within a warp, threads can coordinate using register shuffle operations (e.g., \texttt{\_\_shfl\_sync}) to exchange values without using shared memory, which reduces shared memory pressure and avoids bank conflicts. These shuffle or ballot operations are especially useful for reductions and small transpositions.

Finally, correctness and numerical stability considerations remain. Low-bit quantization often involves scaling factors, zero-points, and asymmetry handling. Implementing quantized matmul requires injecting these dequantization and requantization steps correctly and efficiently. For example, a quantized inner product might be
\[
\text{acc} = \sum_{k} (\alpha_A (a_k - z_A)) (\alpha_B (b_k - z_B))
\]
which expands to terms involving sums of \(a_k b_k\), sums of \(a_k\), sums of \(b_k\), and constant offsets. Rewriting the computation to exploit algebraic simplifications often reduces the number of passes over the data and avoids extra global memory fetches.

# Tooling and profiling: nvprof, Nsight, and GPU performance counters

Profiling is indispensable for diagnosing bottlenecks and guiding optimization. Modern GPU tools provide timeline views, kernel-level metrics, and hardware performance counters. Two widely used NVIDIA tools are nvprof (legacy) and Nsight (current). Additionally, CUPTI (CUDA Profiling Tools Interface) lets you access low-level performance counters programmatically.

nvprof (older CLI profiler) can collect per-kernel timing and counters like global memory throughput, achieved occupancy, and achieved instructions per cycle. It can give a quick summary of which kernels consume the most time and a set of counters such as \texttt{gld\_throughput}, \texttt{gst\_throughput}, \texttt{shared\_load\_transactions}, etc. However, nvprof has been deprecated in favor of Nsight tools on newer platforms; nevertheless, the concepts are the same: collect metrics, identify hot kernels, and drill down.

Nsight Systems and Nsight Compute are NVIDIA’s modern profiling suite. Nsight Systems gives a system-wide timeline, showing CPU and GPU activity, kernel launch latencies, memory copies, and how kernels and memory transfers overlap. This is useful to verify that kernel launches and data transfers are pipelined effectively. Nsight Compute, in contrast, focuses on kernel-level analysis: it provides detailed metrics for specific kernels (latency, achieved occupancy, instruction throughput, memory throughput) and can show instruction-level hotspots and source-level annotations.

GPU performance counters provide low-level hardware event counts (cache hits/misses, number of warps issued, branch divergence metrics, memory transactions). These counters are the backbone of kernel-level analysis: e.g., a high number of global memory transactions or low L2 cache hit rate signals a memory-bound kernel or poor data locality. High issue stalls or many warp stalls waiting for memory indicate latency-bound behavior. Use these counters to determine whether to focus on reducing memory traffic, improving coalescing, or increasing arithmetic intensity.

A typical profiling workflow is:

1. Identify hot code paths by measuring overall runtime and per-kernel time. Use coarse-grained tools first.
2. For a hot kernel, run Nsight Compute to collect kernel metrics: occupancy, achieved occupancy, achieved FLOPs (if supported), global load/store throughput, L2 and L1 cache hit ratios, shared memory throughput, and warp execution efficiency.
3. Interpret metrics: if memory throughput is near peak but achieved FLOPs are low, you are memory-bound. If FLOPs are near theoretical peak but occupancy is low, consider lowering register/shared usage to increase concurrency or unrolling to better use compute units. If there are many shared memory bank conflicts, look at shared memory access patterns.
4. Inspect source-level and instruction-level profiling to identify specific lines or instructions that dominate cycles, and use guided optimization suggestions that many profiling tools offer.
5. Iterate: modify code (e.g., change tile size, reorder loops, add padding to shared memory), re-profile, and compare metrics.

When collecting counters, be mindful of overhead. Collecting many counters in a single run can slow execution and perturb timing. Instead, first collect a small set of key metrics, then collect more detailed counters in targeted runs. Nsight Compute provides pre-configured sections for common problems (memory bottlenecks, instruction bottlenecks, occupancy issues) which simplifies the process.

Finally, automatic roofline analysis is a powerful conceptual tool. The roofline model plots achievable performance as a function of arithmetic intensity (FLOPs per byte of memory traffic). It helps you see whether a kernel is memory- or compute-bound and how close it is to theoretical maxima. Profiling metrics let you estimate arithmetic intensity and achieved bandwidth, and you can compare these to device peak numbers to understand headroom.

# Interfacing custom kernels with deep learning frameworks (PyTorch extensions)

Once you have a working and optimized CUDA kernel, integrating it into a deep learning framework like PyTorch lets you use it in higher-level models, autograd, and training pipelines. PyTorch supports custom CUDA extensions via two main pathways: the legacy C++/CUDA extension mechanism (using setuptools+torch.utils.cpp_extension) and the more modern torch.custom_function / torch.autograd.Function hooking to define forward/backward with custom CUDA kernels. There is also support for JIT compilation via torch.utils.cpp_extension.load which compiles on-the-fly.

Key integration steps:

1. Building the extension: Write device-side (.cu) and host-side (.cpp) code that wraps the kernels with a C++ interface. Use the PyTorch C++ API (ATen) to manipulate tensors on the host and to ensure that tensors passed to CUDA kernels have correct device placement and layout. The extension build process typically compiles the .cu files with nvcc and links them into a Python-callable module. The helper function torch.utils.cpp_extension.load automates compilation and import during development.

2. Tensor layout and strides: PyTorch tensors have metadata (shape, strides, dtype). Your kernel should either require a specific contiguous layout (e.g., row-major contiguous) or handle arbitrary strides. Requiring contiguous tensors simplifies kernels and ensures coalescing, but requires checks and possibly temporary contiguous copies which incur overhead. Document expected layouts and add runtime checks to give clear error messages if a user passes non-contiguous data.

3. Memory management and streams: Respect CUDA streams for concurrency. Use the stream associated with the current PyTorch context when launching kernels to ensure correct synchronization with other PyTorch operations. You can query the current stream via the C++/CUDA API or use provided helpers. Also, avoid using global state that could conflict with other parts of the program.

4. Autograd support: If you want backward passes to be computed by custom kernels, implement a subclass of torch.autograd.Function in Python (or provide a custom C++ autograd operator) where the forward method calls your compiled kernel and the backward method computes gradients by calling kernels or reusing forward code. You must carefully handle saved tensors and context to ensure memory is not freed prematurely. For more advanced extensions, implement custom autograd C++ operators and register them with PyTorch’s dispatcher for maximum performance.

5. Mixed precision and types: PyTorch supports various dtypes (float32, float16, int8, etc.). Ensure your kernels handle correct casting and accumulation rules. For example, when implementing a low-bit kernel, the input tensors might be stored in packed byte arrays; you will likely accept a torch.Tensor with dtype=torch.uint8 or torch.int8 for packed data and expose an API that indicates pack format. Provide CPU fallbacks or explicit errors if the device is not CUDA or if requested types are unsupported.

6. Testing and validation: Implement unit tests that check correctness over a variety of shapes, sizes, edge cases (small dimensions, non-multiples of tile sizes), and dtypes. Include randomized tests and compare results to a reference CPU implementation (even if slow) to ensure correctness. Verify gradients numerically when implementing backward. Good tests are essential before optimizing for performance.

7. Packaging and distribution: For sharing code, consider building wheels with precompiled binaries targeting specific CUDA versions or distributing source with a build step. Be explicit about supported CUDA toolkits and compute capabilities. When possible, isolate device-specific code behind runtime checks so that non-supported architectures fail gracefully.

Practical example: A PyTorch extension for a custom low-bit matmul might expose a function matmul_q4(A_packed, B_packed, out, scaleA, scaleB, zero_pointA, zero_pointB, stream=None) where A_packed and B_packed are uint8 tensors that pack multiple 4-bit values per byte. The extension wrapper unpacks metadata, ensures tensors are on the right device and contiguous if necessary, and launches the CUDA kernel on the desired stream. The backward method either reconstructs the gradient via separate kernels or uses mathematical transformations (e.g., compute gradients via dequantization and use existing high-performance matmul for the gradient computation when possible).

In summary, a careful interface that respects tensor metadata, stream semantics, dtype conventions, and gradient behavior will integrate your custom kernels cleanly into PyTorch and make them usable by researchers and practitioners.

Conclusion

Low-level GPU kernel development requires understanding both algorithmic structure and hardware characteristics. The CUDA programming model gives you the tools to express parallelism at thread/block/warp levels, while the memory hierarchy (registers, shared memory, global memory, constant memory) provides tradeoffs between speed and capacity. Achieving performance demands attention to coalesced memory access, occupancy, and bank conflict avoidance. Implementing custom matmul and low-bit kernels involves careful tiling, packing/unpacking strategies, and mapping compute to registers and warps. Profiling with tools like Nsight and examining performance counters allow data-driven optimization. Finally, integrating kernels into frameworks such as PyTorch requires careful attention to API, dtype, and autograd semantics. Armed with these concepts and techniques, you will be able to read research implementations, design your own efficient low-bit kernels, and iterate toward fast, correct GPU code.
