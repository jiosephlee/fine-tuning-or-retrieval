Introduction

Training large neural networks on GPUs poses a set of memory-management challenges that are often the primary constraint on model scale, batch size, and sequence length. Modern GPU accelerators provide tremendous compute throughput, but their on‑device RAM (often 16–80 GB on mainstream devices and up to several hundred GB on specialized hardware) is a limited resource relative to the size of models and the data they process. This chapter explains how memory is used during training, why certain factors such as sequence length or batch size cause memory to grow rapidly, and what techniques exist to reduce the peak memory footprint so that larger models or longer inputs can be trained on limited GPU RAM. We emphasize intuition behind the technical mechanisms and provide mathematical and systems perspectives so you can read and evaluate research and system implementations.

# GPU memory hierarchy and capacity constraints

GPUs have a memory hierarchy and architecture that affects how data is stored and moved. At the top is the GPU device RAM (often called VRAM or global memory). This is accessed directly by GPU kernels and provides the highest bandwidth and lowest latency compared to anything off device. Typical sizes for consumer GPUs are 8–24 GB, for datacenter GPUs 40–80 GB, and for specialized accelerators sometimes larger. Lower in the hierarchy are caches inside the GPU (registers, L1, L2) and, external to the GPU, the host CPU RAM (DRAM) and storage (NVMe, HDD). Communication between host RAM and GPU RAM goes over an interconnect (PCIe, NVLink, NVSwitch), whose bandwidth and latency are orders of magnitude worse than intra‑GPU memory accesses.

Because training requires storing many large arrays simultaneously, the limited GPU RAM becomes the first bottleneck. During the forward and backward pass a typical training iteration needs to hold: (1) model parameters, (2) optimizer state (e.g., momentum, second moments), (3) activations needed for backpropagation, and (4) temporary workspace for kernels. Each of these consumes memory; their sum must fit in device RAM at the same time or the program will fail with an out‑of‑memory (OOM) error.

To quantify, let $P$ be the number of model parameters, each stored as a 32‑bit float when using standard training. The memory for parameters alone is approximately $4P$ bytes. Many optimizers keep additional per‑parameter tensors. For example, Adam stores two extra 32‑bit tensors of the same size, so optimizer states add roughly $8P$ bytes. Thus parameters plus Adam optimizer states require about $12P$ bytes. Activations are data dependent: for a minibatch of size $B$ and sequence length $L$, and activation dimension $d$, the forward activations across layers can roughly sum to $O(B L d)$ bytes (times precision). Training also often uses workspace memory for fused kernels or FFTs; these can create transient spikes in the required memory.

Another important detail is fragmentation and allocator overhead. GPU memory allocators may fragment memory across allocations of different sizes, meaning the peak "virtual" sum of required memory may be smaller than what a real allocator needs to find contiguous blocks. Fragmentation can make memory tight earlier than raw sums indicate. Also, some frameworks reserve fixed pools of memory to speed allocation, which changes the effective available memory.

Capacity constraints therefore are not just about total bytes but about how those bytes are used concurrently, the precision of tensors (float32 vs float16), and the behavior of allocators and kernels. Designing for large‑scale training requires both mathematical accounting and system‑level strategies to minimize the simultaneous residency of large tensors.

# Activation memory and why sequence length matters

Activations are the intermediate outputs produced by each layer during the forward pass. During backpropagation, gradients for parameters depend on these activations, so frameworks often need to keep them alive until the corresponding backward computation is executed. For many models, especially sequence models like Transformers, activation memory dominates the total memory footprint.

Consider a Transformer with $N$ layers and hidden size $d$. For a minibatch with batch size $B$ and sequence length $L$, a single layer's activations for the whole minibatch occupy about $B \times L \times d$ elements. Across $N$ layers, the forward activations stored for backward pass are on the order of $N \times B \times L \times d$. Using 16‑bit precision halves this compared to 32‑bit, but the dependence on $L$ is linear. Thus if you double the sequence length, activation storage doubles as well. This is why sequence length often becomes the bottleneck for memory when training large language models or Transformer variants.

The reason sequence length has such a strong effect is structural: most layers operate on the full sequence at once (self‑attention computes interactions across tokens), and intermediate representations for all tokens must be available for computing gradients. Moreover, some operations internally create temporary tensors whose dimensions scale with $L$, e.g., attention score matrices that are $L \times L$. For models using relative positional encodings or attention with pairwise state, peak memory can grow even faster than linear in $L$ if temporary $L \times L$ tensors are created.

Batch size $B$ similarly multiplies activation memory. In practice, practitioners manage the tradeoff between batch size and sequence length subject to the memory budget. For example, one may reduce batch size to accommodate longer sequences, but small batch sizes can hurt optimization stability or throughput.

Another subtle contributor is activation checkpointing policies and the granularity at which activations are stored. Frameworks may keep the full activation for every layer or can save only certain checkpoints (layers) and recompute the rest during backward. The frequency and placement of these checkpoints determine the activation memory profile and the extra compute cost during backward pass. Choosing the optimal checkpointing schedule depends heavily on which tensors are large (often those scaling with $B \times L$) and which recomputation steps are cheap compared to the cost of additional memory movement.

Finally, certain model architectures or operations increase activation footprint in nonobvious ways. For instance, layer normalization and residual connections cause simultaneous use of activations from multiple sources; concatenation layers create additional copies if not implemented in place; and autograd frameworks sometimes retain references to intermediate variables if the user inspects them or if custom hooks are registered. All these effects can increase activation residency and make sequence length constraints stricter.

# Gradient checkpointing (activation recomputation) to trade compute for memory

Gradient checkpointing, also called activation recomputation, is a family of techniques that deliberately discard some forward activations and recompute them during backward pass to reduce memory at the cost of extra computation. The baseline tradeoff is straightforward: by storing fewer values during forward, you reduce peak memory because there are fewer tensors to keep alive; then during backward you re-run forward computations for subgraphs to recover the needed activations and proceed with gradient computation.

A simple checkpointing strategy is to divide a model into $K$ segments and only store the activations at the boundaries between segments. During backward, for each segment you recompute the forward activations from the saved boundary activation to obtain the intermediate activations required by the backward computations within that segment. If the model has $N$ layers and you choose $K$ checkpoints roughly every $N/K$ layers, peak stored activations fall from $O(NBLd)$ to $O((N/K)BLd)$ for internal activations plus the $K$ boundary activations. The extra compute cost is proportional to the amount of recomputation: each segment's forward is run once during the original forward and again during the backward, roughly doubling computation for those layers. There are also multi‑level checkpointing schemes that reduce recomputation cost while still lowering memory by trading multiple recomputation steps with logarithmic strategies.

Formally, if the cost (in FLOPs) of running a layer forward is $F$, and we break the network into $K$ equal segments, then the recomputation overhead is approximately $(K-1)/K$ additional forward work per layer in the regions that are recomputed (depending on strategy). In the extreme, storing only the input of the network as the single checkpoint (so $K=1$) means you must recompute the entire forward pass during backward, roughly doubling the forward cost.

Choosing where to place checkpoints is a key design choice. Uniform segmentation is simple and often effective, but optimal placement can use an estimate of memory footprints and compute costs per layer so that segments balance recomputation cost and memory savings—layers that are cheap to compute but produce large activations are good candidates for recomputation; layers that are expensive to compute or produce small activations are better to keep.

Checkpointing interacts with other memory components. For example, recomputation reduces activation memory but can increase temporary workspace usage and peak convolution or attention workspace during recomputed forward passes. Moreover, checkpointing complicates debugging and profiling because the forward path is executed multiple times; one must ensure nondeterministic operations or any randomness are handled consistently (e.g., by fixing RNG state or seeding properly before recomputation).

There are also algorithmic variants. In addition to layerwise checkpointing, reversible networks (e.g., RevNets) are designed so that inputs to a layer can be reconstructed from its outputs using a deterministic inverse, eliminating the need to store activations for certain components entirely. Reversible models trade architectural complexity for memory savings without recomputation overhead in the same way, but they constrain model design and sometimes make implementing certain operations more difficult.

Practical frameworks expose checkpointing hooks or APIs that let users wrap sequences of layers with checkpointing semantics. These frameworks often provide automated heuristics that compute a checkpointing schedule based on model graph structure and estimated memory use. When using checkpointing in production, you should monitor both memory and time: checkpointing can allow training that otherwise would be impossible, but it increases runtime and can change the optimal learning rate or batch size choices due to altered throughput.

# Sharding and model parallelism approaches (tensor/split sharding)

When a single GPU cannot hold the whole model (parameters plus states), parallelism across multiple GPUs becomes necessary. Data parallelism replicates the model across devices and splits batches, which is effective when parameters fit on each device. Model parallelism and parameter sharding strategies are used when even a single replica is too large or when you want to reduce per‑GPU memory by distributing the model across devices.

Sharding comes in several flavors. Parameter sharding, sometimes called state sharding or optimizer state sharding, partitions parameter tensors and their associated optimizer state across devices so that no single device stores all parameters. If you have $M$ devices and shard parameters evenly, each device stores roughly $1/M$ of the parameter storage. A popular recent technique is Fully Sharded Data Parallel (FSDP), which shards both parameters and optimizer states and uses all‑reduce or other communication patterns to synchronize gradients or to gather parameters only when needed (e.g., during the forward pass).

Tensor model parallelism splits individual large tensors (weights) across devices. For instance, consider a large weight matrix $W$ of shape $d_{\text{out}} \times d_{\text{in}}$. You can partition $W$ along the output dimension into $W = [W_1; W_2; \ldots; W_M]$ where each device stores a block $W_i$ of shape $d_{\text{out}}/M \times d_{\text{in}}$. During forward propagation, each device computes its partial output $o_i = W_i x$ and then the partial outputs are concatenated (or reduced) to obtain the full output. This reduces memory for the weight by $1/M$ per device but requires communication to assemble outputs or inputs depending on the split. There are alternative splits: splitting across the input dimension or splitting along both dimensions (2D or 3D parallelism) to trade communication and computation patterns.

Pipeline parallelism splits layers across devices in a sequential pipeline: some layers live on GPU 0, the next on GPU 1, and so on. Inputs flow through the pipeline during forward, and gradients flow backwards. Pipeline parallelism reduces per‑device memory for activations (each device holds activations only for the layers it owns) and parameters, but introduces pipeline bubbles—idle periods where devices wait for data—and complicates scheduling. Micro‑batching (splitting a batch into micro‑batches) is typically used to keep the pipeline filled and achieve high device utilization.

Hybrid strategies combine sharding and model parallelism forms. For example, tensor parallelism may be used inside a node where fast interconnect is available (NVLink), with pipeline parallelism across nodes. The choice depends on communication bandwidth, latency, and the structure of the model. Tensor sharding minimizes memory by partitioning the largest tensors; parameter sharding reduces optimizer state so that training with expensive optimizers like Adam becomes feasible at scale.

Communication patterns are critical: all‑reduce, all‑gather, reduce‑scatter, and point‑to‑point collectives are used to keep distributed tensors consistent or to assemble pieces. Communication overhead can offset memory gains if not managed carefully. Efficient implementations overlap computation with communication (e.g., start an all‑reduce for gradient shards while computing other gradients) to hide latency and improve throughput.

From a memory perspective, sharding changes the accounting: a parameter of size $P$ stored across $M$ devices means each device holds $P/M$, but activations may not partition the same way and may still need to be gathered or redistributed, so one must account for temporary memory during communication. Sharding is particularly powerful when combined with careful scheduling, mixed precision, and optimizer state management to squeeze the highest model capacity per device.

# Offloading optimizer states to CPU RAM and host/device transfers

Optimizer states (e.g., momentum and second moments in Adam) can easily outsize the model parameters themselves. For large models, storing these per‑parameter states on GPU can be the largest consumer of memory. Offloading optimizer state to host CPU RAM is a practical strategy: keep the model parameters and immediate activations on GPU for speed, but store the relatively inert optimizer buffers in host memory, fetching them to GPU only when they are needed for updates.

The logic is that optimizer states are accessed less frequently than activations or parameters during a single iteration. In synchronous optimizers, during each parameter update, you need the corresponding optimizer state to compute the new parameter value. If you partition the parameter set into chunks that fit on GPU together with their optimizer states, you can stream these chunks from CPU to GPU, update them, and write them back. This chunking approach transforms the memory footprint from "store entire optimizer state on GPU" to "store only the currently active chunk" plus some buffer to hide transfer latencies.

However, offloading incurs host‑device transfer overheads over PCIe or other interconnects. These transfers can be bandwidth limited and introduce latency that can reduce throughput. To mitigate this, efficient offloading systems use asynchronous transfers and double buffering: while the GPU works on one chunk, the system prefetches the next chunk and writes back the previous chunk, overlapping data movement with computation. Prefetching and pipelining are essential to hide transfer costs. Additionally, reducing the precision of optimizer states (for example storing second moments in float16 instead of float32) can reduce transfer sizes, though care must be taken to avoid numerical instability.

There are two main patterns for offloading: eager offload and demand‑driven offload. Eager offload continuously streams optimizer states so that the GPU always has the data it needs before update, while demand‑driven offload fetches states just in time. Designing the chunk size matters: too small and overheads of many small transfers dominate; too large and you reintroduce memory pressure and latency spikes.

From an API and implementation standpoint, frameworks like ZeRO Stage 2/3 (Zero Redundancy Optimizer) and DeepSpeed provide integrated offloading strategies that combine sharding and host offloading. They manage transfer scheduling, memory pinning (to avoid extra copies), and overlapping so that model training proceeds with minimal throughput degradation. These systems also manage consistency and fault tolerance across multiple devices and nodes.

One must be aware of system effects: if CPU memory becomes the bottleneck or if PCIe bandwidth is saturated, offloading may reduce GPU memory pressure but degrade wall‑clock performance. Additionally, frequent transfers can increase energy consumption and system noise. In practice, offloading is most effective when GPU memory is the scarcer resource relative to host memory and when the interconnect is reasonably fast (NVLink > PCIe Gen3 > PCIe Gen4, with NVLink offering lower latency and higher bandwidth).

# CUDA Unified Memory basics and page migration concepts (OS‑level paging)

CUDA Unified Memory (UM) provides a programming model where CPU and GPU share a single virtual address space. Instead of explicitly allocating separate host and device buffers and writing explicit cudaMemcpy calls, the programmer allocates unified memory using APIs such as cudaMallocManaged. The runtime and operating system then manage migration of pages between host and device as they are accessed, making it conceptually easier to write code that transparently moves data.

Under the hood, Unified Memory relies on page faulting and migration mechanisms. Memory is partitioned into pages (commonly 4 KB or larger depending on system). When the GPU accesses a page that currently resides in host memory, the GPU triggers a page fault. The runtime then migrates that page to device memory (if space is available), updating page tables and possibly evicting other pages back to the host. This migration is managed by the CUDA driver and may use OS primitives. Unified Memory can also take advantage of hardware support for on‑demand paging on some platforms, which reduces migration overhead by pushing the page fault handling into the device.

Page migration simplifies programming but has two important performance caveats. First, page faults and migrations are expensive, often much slower than explicit cudaMemcpy operations for predictable data movement. If your algorithm causes a working set that does not fit entirely on device memory and the access pattern frequently touches a large number of different pages per kernel invocation, you will incur many page migrations and stall GPU execution while pages are moved. Second, because migration is reactive (triggered by access), it is harder to overlap data transfer with computation. In contrast, explicit prefetching (cudaMemPrefetchAsync) can be used to hint the runtime to move pages ahead of use, allowing overlapped transfers when access patterns are known.

Unified Memory also has a notion of residency: pages are resident either on host or device. The runtime maintains which pages are resident where and chooses what to evict when device memory fills. Eviction policies are heuristic and not as controllable as manual allocation and transfer, which can make performance nondeterministic and sensitive to small code changes. Page size and page table granularity also matter: larger pages reduce the number of faults but increase the amount of data migrated per fault, potentially moving unused data unnecessarily.

UM can be especially helpful in prototyping or in situations where the memory working set slightly exceeds device memory and access patterns are somewhat localized, because it allows training to proceed without complex manual offloading code. However, for large‑scale training where predictable high throughput is essential, explicit management (manual offload, pipelining, and sharding) often delivers far better performance because it allows the developer or system to control when and how much data moves over the interconnect and to maximize overlap between communication and compute.

Modern CUDA also provides explicit APIs to prefetch and set memory advice, enabling a hybrid approach: allocate unified memory but perform cudaMemPrefetchAsync to move data proactively and use cudaMemAdvise to hint that certain pages will be accessed primarily by the device or the host. This gives more control while keeping the single address space convenience.

Finally, note that Unified Memory’s performance characteristics vary by platform and driver. Systems with high bandwidth interconnects and hardware support for on‑demand page migration see better performance, while systems with slow CPU‑GPU links may perform poorly if Unified Memory triggers frequent migrations. When using UM, profile page fault counts and migration activity; tools like NVIDIA Nsight or nvprof can reveal page fault overheads and guide whether UM is appropriate or whether manual strategies will be required.

Conclusion

Memory management is central to scaling deep learning training on GPUs. Understanding how memory is consumed—parameters, optimizer states, activations, and temporary workspace—lets you reason about where to optimize. Activation size grows linearly with batch size and sequence length, making long sequences a frequent memory bottleneck. Checkpointing trades compute for memory and is an effective technique to lower peak activation residency. Sharding and model parallelism distribute memory across devices so that models larger than a single GPU can be trained; the choice between tensor sharding, pipeline parallelism, and parameter/state sharding depends on model structure and interconnects. Offloading optimizer states to CPU RAM reduces on‑device memory at the cost of transfers, requiring careful overlapping to hide latency. Unified Memory provides a convenient abstraction for shared address space but relies on page migration and can have unpredictable performance for large working sets. Combining these strategies—precision reduction, checkpointing, sharding, and managed offload—with careful profiling and scheduling is the practical path to training very large models on clusters of GPUs with limited memory per device.
