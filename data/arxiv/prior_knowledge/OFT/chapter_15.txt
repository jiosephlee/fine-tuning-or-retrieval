Introduction

Modern generative models—large pretrained transformers and their finetuned variants—are powerful but also expensive and finicky. When evaluating new finetuning methods, architectures, regularizers, or parameter-efficient techniques, we must design experiments that allow fair, informative, and reproducible conclusions. This chapter gives concrete guidance for choosing baselines, creating dataset splits and few-shot protocols, designing ablation studies, reporting variability and failures, and making experiments computationally reproducible. The emphasis is on intuition and practical rules so that your results are credible, comparable, and useful to other researchers.

# Selecting baselines and ensuring fair comparisons (matching parameter budgets/targets)

Good baselines are the backbone of experimental claims. A baseline should represent the best reasonable alternative under comparable resource and design constraints. The key principle is fairness: when claiming superiority of a method, compare to baselines that have matched or transparently documented budgets in the aspects that matter for your claim. Commonly relevant budgets are total trainable parameter count, inference latency, wall-clock/GPU-hours, floating-point operations (FLOPs) during training, and memory usage.

Start by deciding the primary resource your method targets. If you propose a parameter-efficient finetuning recipe (e.g., adapters, LoRA), your central claim likely concerns reductions in the number of trainable parameters. In that case match baselines on trainable parameter count. If your method claims to reduce inference latency, match baselines on wall-clock latency at inference using the same hardware and batch sizes. If the claim is improved sample-efficiency, match baselines on the number of labeled examples and report curves of performance vs examples. Often more than one budget matters; explicitly state which budget you matched and why the matching is the right lens for the claim.

How to match budgets in practice:
- Trainable parameter budget: compute the number of parameters changed during finetuning. For adapter-style methods, explicitly calculate trainable parameters per layer and multiply by the number of layers. For example, a single-layer adapter with input dimension $d$ and bottleneck dimension $b$ has $d\cdot b + b\cdot d = 2bd$ weights (plus biases). If you place two such adapters per transformer layer, multiply accordingly. Compare to full finetuning (all parameters trainable) and to other parameter-efficient baselines with the same or slightly higher/lower counts.
- FLOPs or GPU-hours: If your claim concerns compute efficiency, measure total training FLOPs or GPU-hours and match baselines on that. FLOPs for a forward+backward step can be estimated from model size and sequence length; multiply by number of steps and batch size. Report both wall-clock time on the specific hardware and the estimated FLOPs to allow cross-hardware comparison.
- Latency/memory: For inference claims, measure throughput and latency on the same hardware, with the same batch sizes and implementation tricks (e.g., kernel fusion, quantization). If you compare methods requiring different runtimes (e.g., a sparse method), ensure the deployment environment is consistent.

When you cannot perfectly match a budget, be transparent: report the budgets for each method, and provide sensitivity analyses showing how performance varies with budget (e.g., performance vs parameter count curve). This helps reviewers and readers extrapolate fairness.

Choosing baseline algorithms: include strong, well-tuned versions of standard methods. For finetuning transformers these often include: full finetuning, layer-wise finetuning (top $k$ layers), adapters, LoRA, prompt tuning, and any recent competitive methods on the same task. Use the authors’ recommended hyperparameters for baselines when possible, and if you change them, document why.

Finally, consider an "oracle" or upper bound where appropriate: for example, performance when training with far more data or compute. This contextualizes how much headroom remains and whether a small improvement is meaningful.

# Dataset splits, few-shot protocols, and data-efficiency experiments

Data splits are deceptively important. A standard split has three parts: training, validation (development), and test. The training set is used to fit parameters; the validation set is used to choose hyperparameters and early stopping; the test set is held out and used only for unbiased final evaluation. Never tune or report results on the test set.

For finetuning large generative models, particularly with few-shot or data-limited regimes, you must be explicit about how few-shot examples are selected. There are two common few-shot paradigms:

1. In-context few-shot (prompting): provide $k$ examples in the input to a frozen base model. The selection of in-context examples, their ordering, formatting, and prompt templates can dramatically affect results. To be fair, evaluate over multiple random draws of in-context examples and report mean and variance. If prompts are hand-crafted, include ablations of prompt wording and justify choices.

2. Finetuning few-shot (parameter updates): when you finetune on small numbers of labeled examples, the randomness in example selection matters. Report average performance over multiple randomly sampled training sets of size $k$ (e.g., 5–20 seeds for each $k$). Do not cherry-pick samples that favor your method.

Data-efficiency experiments should be presented as learning curves: plot performance against number of fine-tuning examples on a log or linear scale as appropriate. A single point at one $k$ is weak evidence; a curve shows whether your method systematically improves sample efficiency. When plotting, include standard error bars (see the section on reporting variance) and ensure axes are labeled clearly.

When splitting data for validation and multiple tasks, use nested splits if hyperparameter selection could leak information to the test set. A typical protocol: for each random sample of the $k$-shot training set, set aside a small validation set (or use cross-validation) to choose hyperparameters, then evaluate the selected model on an unseen test set. If the dataset is so small that holding out validation examples is impractical, use cross-validation or repeated holdout with aggregated results.

Additionally, be careful with pretraining overlap: ensure no test examples were seen during pretraining of the base model. This is especially relevant for large models trained on scraped web text. If overlap is suspected, either remove overlapping examples or report them separately.

# Ablation studies: hyperparameters, parameter counts, and block/rank choices

Ablation studies aim to isolate the effect of each design choice. The best ablations are systematic, controlled, and interpretable. The general approach is to vary one factor at a time while holding others fixed (the ceteris paribus principle). When interactions are suspected, consider factorial designs or more modern techniques like random forests or ANOVA to analyze interactions.

Hyperparameter ablations: Hyperparameters (learning rate, batch size, weight decay, dropout, optimizer type) can dramatically change results. Always perform a hyperparameter search for each baseline and the proposed method under matched tuning budgets. A fair approach is to allocate an equal search budget (number of trials and compute) to each method and use identical search strategies (grid, random, or Bayesian). Report the search space, the number of trials, and how the chosen hyperparameters were selected (e.g., based on validation loss or downstream metric). Present heatmaps or sensitivity plots for learning rate and other crucial hyperparameters to show stability.

Parameter count ablations: When you propose a parameter-efficient technique, evaluate how performance scales with parameter budget. For adapter or LoRA methods, vary the bottleneck size or low-rank $r$ and plot performance vs total trainable parameters. This allows readers to see trade-offs and where diminishing returns begin. Provide formulas for parameter counts so others can reproduce them. For example, adding a LoRA update to a weight matrix $W \in \mathbb{R}^{d\times d}$ with rank $r$ costs $\Delta P = 2rd$ parameters (for two matrices $A\in\mathbb{R}^{d\times r}$ and $B\in\mathbb{R}^{r\times d}$), ignoring biases.

Block and rank choices in modular adapters: Many parameter-efficient modules have discrete design choices such as where to insert them (attention vs MLP blocks), whether to tie parameters across layers, and the internal bottleneck rank $r$ or block size. For each such dimension, run ablations varying one design choice while fixing others. Typical axes to explore include:
- Position: insert only in MLPs, only in attention, both, or interleaved.
- Sharing: per-layer independent adapters vs shared adapter across layers vs grouping layers into blocks.
- Rank or bottleneck: ranks $r\in\{1,4,8,16,32,64\}$ or bottleneck sizes $b$ across a geometric range.
- Initialization: zero initialization vs small random initialization; some methods are sensitive to initialization.

Whenever possible, present a 2D surface (e.g., performance vs rank and learning rate) or multiple curves to show trade-offs. If you cannot explore all combinations due to compute limits, prioritize the most plausible design choices and explain why others were deprioritized.

Statistical rigor in ablations: for each ablation point, run multiple seeds (see the next section) to quantify variance. If interactions are complex, consider a small factorial design (e.g., 2-level factorial with core factors) that estimates both main effects and pairwise interactions.

# Reporting standard deviations, multiple seeds, and failure cases

Variability is real and must be reported. Single-seed results are unreliable, especially in low-data regimes and when finetuning large models.

Number of seeds: At minimum, run experiments with at least 3 independent seeds, but 5–10 is preferable for robust estimates if resources permit. The choice depends on the variance observed; if variance is high, more seeds are necessary. When reporting many hyperparameter configurations or ablation points, try to standardize on a fixed number of seeds across all runs.

Reporting format: For each reported metric, give the mean and a measure of spread, typically standard deviation or standard error. For example, report results as: mean ± standard deviation over $N$ seeds. If you display curves, include error bands representing $\pm$ standard error or a bootstrap confidence interval. For a metric $m$ over $N$ independent seeds with sample mean $\bar{m}$ and sample standard deviation $s$, the standard error is
\[
\mathrm{SE} = \frac{s}{\sqrt{N}}.
\]
A 95% confidence interval under approximate normality is $\bar{m} \pm t_{0.975, N-1}\cdot \mathrm{SE}$.

Statistical testing: When claiming superiority, perform a statistical test appropriate for paired or unpaired comparisons. For paired experiments (same random seeds and data splits for both methods), a paired t-test is often appropriate. For more general comparisons or non-normal distributions, a non-parametric test like the Wilcoxon signed-rank test is safer. Always report effect sizes and p-values, and be mindful that small p-values are easier to obtain with large samples; focus on practical significance (magnitude of improvement) and confidence intervals.

Failure cases and negative results: Report failure modes transparently. If some seeds catastrophically diverge or result in collapsed output, note the frequency and conditions (e.g., high learning rate, particular dataset). If a hyperparameter search often fails for a baseline but not your method, that is an important part of the story. Include examples of qualitative failures (e.g., hallucinations, output truncation) and, where relevant, metrics that capture these issues (e.g., calibration, factuality scores, toxicity detectors).

Visual diagnostics: Include plots of per-seed learning curves rather than just final points. This reveals whether improvements are from faster convergence, better asymptotic performance, or reduced variance across seeds.

# Computational considerations and reproducible code/seed reporting

Reproducibility extends beyond seeds and averages to the computational environment and code. Modern ML stacks have many non-deterministic components (cuDNN algorithms, asynchronous kernels, hardware differences). The goal is practical reproducibility: enough information and artifacts that others can reproduce the high-level results or rerun experiments to verify claims.

Environment and code: Tag every experiment with a code commit hash and provide a link to the repository. Include environment specifications (e.g., a requirements.txt, Pipfile, or conda environment.yml). For low-level reproducibility, document:
- Framework and major library versions (PyTorch/TensorFlow, CUDA, cuDNN).
- Hardware used (GPU model(s), CPU, number of GPUs).
- OS and kernel version when relevant.

Random seeds: Document all sources of randomness and how you set seeds. Common seeds include:
- Python's builtin RNG: random.seed(s)
- NumPy: np.random.seed(s)
- Framework RNGs: torch.manual_seed(s), torch.cuda.manual_seed_all(s)
- Any library-specific RNGs (e.g., JAX, TensorFlow)
Record the seed values used for each independent run, and ideally provide a table or file listing seed-to-checkpoint mappings.

Deterministic flags and performance trade-offs: Many frameworks provide deterministic modes (e.g., torch.use_deterministic_algorithms(True)). These reduce nondeterminism but may degrade performance or prevent certain kernels from running. Document whether deterministic modes were used and, if not, explain the trade-off. If determinism is impossible, provide multiple independent seeds and show that results are robust despite nondeterminism.

Exact scripts and checkpoints: Provide the training and evaluation scripts used to run experiments, with exact command lines for each run. Publish model checkpoints for the best models and for representative seeds where possible. If publishing full checkpoints is impossible due to size or policy, provide fine-grained saved metrics and seed-to-checkpoint mappings.

Compute reporting: For each experiment specify:
- Number of GPUs and type, wall-clock time, and total GPU-hours.
- Batch sizes, sequence lengths, number of training steps, and optimizer settings.
- Any special implementation details that affect runtime (e.g., mixed precision, gradient accumulation, distributed data parallel settings).

Reproducing results across hardware: Provide FLOPs estimates and theoretical compute counts (e.g., number of multiply-adds per forward/backward) in addition to wall-clock times so that others can approximate runtimes on different hardware.

Packaging experiments: Use reproducibility-friendly tools like containerization (Docker), environment lock files (pip-tools, poetry), or workflow definitions (Makefile, shell scripts, or orchestration via reproducibility frameworks). Include a README that gives step-by-step instructions to reproduce key results, e.g., "To reproduce Figure 3, run script experiments/figure3.sh with commit hash X, using 4x A100-40GB GPUs."

Practical checklist
- State precisely which budget(s) you matched for fair comparison, and provide budget numbers for every method.
- Publicly release code, hyperparameter files, and random seeds for all reported runs.
- Use at least 3–5 seeds (preferably more) and report mean±std or confidence intervals.
- Split datasets into train/val/test carefully; use nested validation when tuning on small data.
- Provide learning curves (performance vs examples, vs steps), not just final numbers.
- For ablations, vary one factor at a time and include parameter-count and rank ablations for parameter-efficient methods.
- Report compute in both wall-clock and normalized compute units (FLOPs or GPU-hours).
- Document environment (framework, CUDA, cuDNN), hardware, and commit hash; supply scripts and checkpoints.

Conclusion

Reproducible, fair experimentation in generative model research demands discipline and transparency. Thoughtful baseline selection, rigorous data-splitting protocols, systematic ablations, honest reporting of variance and failures, and careful computational documentation transform research claims from anecdote to evidence. Applying the principles in this chapter will make your results more credible, easier to compare with others, and far more useful for the community.
