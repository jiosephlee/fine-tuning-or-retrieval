Chapter 1: Linear Algebra and Matrix Computation for Machine Learning

Introduction

Linear algebra is the language of modern machine learning. Models, inputs, weights, and operations are naturally represented as vectors and matrices, and understanding the algebraic operations and their computational properties is crucial for both theoretical insight and practical implementation. In this chapter we develop the foundational linear algebra concepts used throughout neural networks and machine learning systems, with an emphasis not only on the mathematical operations but also on the computational cost, memory organization, and implementation strategies that matter when models become large. The chapter covers vector and matrix operations and shapes (including broadcasting), the inner workings and cost of matrix multiplication (GEMM), the role of optimized BLAS libraries and kernels, the effect of memory layout on performance, strategies such as batching and tiling for handling large matrices, and basics of numerical precision and rounding errors. The treatment aims to provide intuition and concrete rules that will help you read and understand machine learning papers and implement efficient code for large models.

# Vectors and matrices: operations, shapes and broadcasting

Vectors and matrices are the basic data structures of linear algebra. A vector is a one-dimensional array of numbers, often written as a column vector $v \in \mathbb{R}^n$ with components $v = \begin{bmatrix}v_1 \\ v_2 \\ \vdots \\ v_n\end{bmatrix}$. A matrix is a two-dimensional array $A \in \mathbb{R}^{m \times n}$ where $m$ is the number of rows and $n$ is the number of columns. We write $A = [a_{ij}]$ where $a_{ij}$ denotes the element in row $i$ and column $j$.

Basic operations on vectors and matrices include addition, scalar multiplication, dot products, matrix-vector products, and matrix-matrix products. Two matrices $A$ and $B$ can be added only if they have the same shape, producing a matrix $C$ with elements $c_{ij} = a_{ij} + b_{ij}$. Scalar multiplication multiplies every element by a scalar $\alpha$, producing $\alpha A$.

The dot product of two vectors $u, v \in \mathbb{R}^n$ is defined as $u^\top v = \sum_{i=1}^n u_i v_i$. This is a scalar and is the fundamental building block of matrix multiplication.

The matrix-vector product $y = A x$ (with $A \in \mathbb{R}^{m \times n}$ and $x \in \mathbb{R}^n$) yields a vector $y \in \mathbb{R}^m$ with entries $y_i = \sum_{j=1}^n a_{ij} x_j$. Interpretationally, each row of $A$ is taken as coefficients to compute a dot product with $x$.

Matrix-matrix multiplication generalizes this: given $A \in \mathbb{R}^{m \times n}$ and $B \in \mathbb{R}^{n \times p}$, their product $C = AB$ is in $\mathbb{R}^{m \times p}$ with entries $c_{ik} = \sum_{j=1}^n a_{ij} b_{jk}$. This operation composes linear maps and appears everywhere in neural networks (weight layers, attention, covariance computations, etc.).

Shapes and compatibility rules are essential. The inner dimensions must match for multiplication: in $AB$, $A$ has shape $(m,n)$ and $B$ has shape $(n,p)$; the result has shape $(m,p)$. For elementwise operations, shapes must match exactly, except when broadcasting is used.

Broadcasting is an important convenience in numerical libraries (NumPy, PyTorch, TensorFlow). Broadcasting allows operations between arrays of different shapes by implicitly expanding one or both arrays along dimensions of size 1 to match the other. The basic broadcasting rule is: align the arrays on their trailing dimensions; for each dimension, the sizes must be equal or one of them must be 1; the result has the maximum size along each dimension.

For example, adding a bias vector $b \in \mathbb{R}^n$ to every row of a matrix $X \in \mathbb{R}^{m \times n}$ can be written $X + b$, where $b$ is treated as shape $(1, n)$ and broadcast down the $m$ dimension. If $b$ has shape $(n,)$ and $X$ has shape $(m,n)$, broadcasting implicitly treats $b$ as $(1,n)$ and expands it to $(m,n)$ without copying data in many implementations. Broadcasting is very convenient, but it is important to be aware when expansions create new memory or when they are handled lazily by the framework.

Broadcasting can also work on higher-rank tensors. Suppose $A$ has shape $(B, H, W)$ and $s$ has shape $(H, 1)$. Aligning trailing dimensions, you can broadcast $s$ to shape $(B, H, W)$ by expanding the last two dimensions appropriately. Mistakes with shape alignment are a frequent source of bugs, so always check shapes explicitly.

Understanding shapes and broadcasting is particularly important in neural networks because minibatches introduce an extra dimension (commonly the first dimension). If $X$ is a batch of inputs with shape $(N, d)$ and $W$ is a weight matrix with shape $(d, k)$, the forward pass of a linear layer is $Y = X W$, producing shape $(N, k)$. Adding a bias vector $b$ of shape $(k,)$ uses broadcasting: $Y = X W + b$ produces $(N,k)$.

Finally, note that some operations expect column vectors or row vectors; e.g., the gradient of a scalar with respect to a column vector is often represented as a column vector. Conventions vary across disciplines and libraries, so be explicit about shapes when deriving formulas or writing code.

# Matrix multiplication (GEMM) and complexity analysis (FLOPs)

Matrix multiplication is central to machine learning workloads. The generic matrix-matrix multiplication (often called GEMM — GEneral Matrix-Matrix multiply) implements $C = \alpha A B + \beta C$ where $\alpha$ and $\beta$ are scalars. GEMM is both a mathematical operation and a highly optimized kernel in numerical libraries.

To understand computational cost we count floating point operations (FLOPs). For a straightforward algorithm that computes $C = A B$ with $A \in \mathbb{R}^{m \times n}$ and $B \in \mathbb{R}^{n \times p}$, each element $c_{ik}$ requires $n$ multiplications and $n-1$ additions, so roughly $2n-1$ FLOPs. For large $n$ the dominant term is $2n$, so a common approximation is that the total FLOPs for computing $C$ is $2 m n p$.

Thus the asymptotic complexity of dense matrix multiplication is $O(m n p)$ arithmetic operations, and when $m=n=p=N$ for square matrices, the cost is approximately $2N^3$ FLOPs. This cubic scaling quickly becomes the computational bottleneck in large models.

Aside from operation counts, we should consider arithmetic intensity, which is the ratio of FLOPs to memory traffic (bytes moved). High arithmetic intensity means more computation per byte read/written, which helps amortize memory access costs and enables high utilization of floating point units on modern hardware. GEMM typically has high arithmetic intensity because each fetched matrix element can be reused many times in inner products, especially when optimized with blocking/tiling. This is why GEMM can approach peak performance on CPUs and GPUs when implemented well.

Counting FLOPs precisely matters when benchmarking or estimating runtime. If a kernel implements $C \leftarrow \alpha A B + \beta C$, the total FLOPs are: multiplications for $A B$ of approximately $2 m n p$, plus scaling $C$ by $\beta$ (one multiplication per entry: $m p$ multiplications), and adding $A B$ to $\beta C$ (one addition per entry: $m p$ additions). So total approximate FLOPs become $2 m n p + 2 m p$. For large $n$ the $2 m n p$ term dominates.

Note that some algorithms (e.g., Strassen's algorithm) reduce the asymptotic arithmetic count below $O(n^3)$ for very large matrices, but they introduce numerical complexity, larger constants, and are rarely used in typical deep learning workloads where matrices have shapes favorable to highly-optimized blocking and parallelization. For practical purposes, dense GEMM implementations that exploit hardware characteristics are the tool of choice.

When discussing neural networks, multiply-accumulate operations (MACs) are often counted rather than FLOPs. A multiply-accumulate is one multiplication followed by an addition, and is sometimes counted as one FLOP in some ML literature. To avoid confusion: here we count both multiplication and addition as separate FLOPs so the standard dense multiplication of square $N \times N$ matrices costs about $2 N^3$ FLOPs.

# BLAS libraries and optimized kernels

Because GEMM is so fundamental and compute-intensive, numerical linear algebra libraries provide highly-optimized implementations. The Basic Linear Algebra Subprograms (BLAS) is a standard API that defines routines at three levels: Level 1 (vector operations), Level 2 (matrix-vector operations), and Level 3 (matrix-matrix operations, including GEMM). Implementations of BLAS exploit low-level optimizations, multi-threading, vector instructions (SIMD), and architecture-specific tuning.

Common BLAS implementations include:

- OpenBLAS: an open-source, high-performance BLAS implementation optimized for many CPU architectures.
- Intel MKL: Intel's Math Kernel Library, a proprietary, highly-optimized library for Intel CPUs, often achieving near-peak performance.
- cuBLAS: NVIDIA's BLAS implementation for GPUs, optimized for CUDA and GPU memory hierarchies.
- BLIS: a framework for building BLAS-like libraries with modular micro-kernels and a focus on portability and tunability.

These libraries provide a GEMM routine that is the workhorse for many machine learning frameworks. They are tuned to exploit cache hierarchies, vector units, and multiple cores. On GPUs, libraries like cuBLAS and CUTLASS use specialized kernels that leverage many threads and shared memory to achieve high throughput.

At a lower level, optimized kernels are implemented as micro-kernels that operate on small blocks (e.g., 8x8, 16x16) and are carefully written to align with SIMD register widths, prefetching, and pipeline scheduling of the processor. The library orchestrates how data is moved between main memory, caches, registers, and vector units, and uses blocking to maximize data reuse.

When using high-level ML frameworks (TensorFlow, PyTorch, JAX), these libraries are called under the hood for dense linear algebra. Understanding that a GEMM call will dispatch to a BLAS implementation helps you reason about performance: matrix sizes that match kernels' preferred block sizes and using contiguous memory will tend to run faster.

Some libraries also provide mixed-precision kernels (e.g., FP16 inputs with FP32 accumulation on GPUs) that trade numerical precision for throughput; these are particularly important for deep learning training where accelerators have specialized units for lower-precision math (Tensor Cores on NVIDIA GPUs, for example).

Finally, BLAS implementations expose multi-threaded parallelism. The effective use of cores depends on matrix sizes: very small matrices may not saturate all cores efficiently, while very large matrices benefit from multi-threaded GEMM. Libraries typically expose environment variables or configuration APIs to set the number of threads and tune behavior.

# Memory layout (row-major vs column-major) and cache effects

Memory layout — the order in which multi-dimensional array elements are stored in linear memory — has a large effect on performance. The two common conventions are row-major and column-major. In row-major layout (used by C, NumPy default), elements in the same row are contiguous: a matrix $A \in \mathbb{R}^{m \times n}$ stores $a_{11}, a_{12}, \dots, a_{1n}, a_{21}, \dots$. In column-major layout (used by Fortran, MATLAB), elements in the same column are contiguous: $a_{11}, a_{21}, \dots, a_{m1}, a_{12}, \dots$.

Why does this matter? Modern CPUs and GPUs access memory most efficiently when accesses are contiguous or have predictable strided patterns that fit into caches and prefetchers. Cache lines fetch contiguous bytes (commonly 64 bytes on CPUs). If your algorithm accesses elements contiguously in memory order, then successive accesses will often hit in the cache and be very fast. If access patterns hop with large strides, then each access may miss the cache and cause expensive loads from main memory.

Consider the inner loop of a naive matrix multiplication that iterates over the inner dimension $j$ and accesses $a_{ij}$ and $b_{jk}$. If $A$ is stored row-major and the algorithm iterates $j$ in the innermost loop while fixing $i$, access to $a_{ij}$ is contiguous (good). But access to $b_{jk}$ will be strided across rows of $B$ if $B$ is row-major (bad). To get good locality for both operands, implementations reorganize loops or use transposed views so inner accesses are contiguous for both arrays. This is one reason why BLAS libraries consider both row-major and column-major layouts and provide optimized paths for various transposition flags.

Cache effects are not limited to contiguous access; they depend on reuse patterns. The key principle is temporal and spatial locality. Temporal locality means recently used data is likely to be used again soon; spatial locality means nearby data addresses are likely to be used soon. Blocking and tiling techniques leverage both by arranging computation so small tiles of data fit in cache and are reused multiple times before being evicted.

Alignment and padding can also matter. Aligning data to cache-line boundaries, padding rows to multiples of SIMD widths, and avoiding cache-line contention (false sharing) in multi-threaded programs all affect performance. When arrays are strided (e.g., when taking subviews or transposes without copying), the stride value can cause inefficient memory access; some libraries will copy/transposes to a contiguous buffer before computation when that gives better performance.

On GPUs, memory coalescing plays a similar role. Threads are grouped into warps (e.g., 32 threads) and accesses by threads in a warp are fastest when consecutive threads access consecutive memory addresses. Blocked and tiled GPU kernels are designed to ensure coalesced loads and to use shared memory to reduce global memory traffic.

Understanding memory layout and cache behavior helps explain why some seemingly equivalent implementations have vastly different performance. When writing performance-sensitive code, prefer accessing arrays in memory order, use contiguous arrays when possible, and rely on optimized libraries that handle low-level blocking and caching strategies.

# Batching, streaming, and tiling strategies for large matrices

When matrices are so large that they do not fit entirely in fast memory (L1/L2/L3 caches or GPU on-chip memory), or when workload parallelism needs to be balanced, strategies such as batching, streaming, tiling (blocking), and out-of-core computation are used to manage computation and memory transfer efficiently.

Batching is ubiquitous in machine learning. Instead of processing one input at a time, inputs are grouped into minibatches, producing a batch dimension $N$. For a linear layer, the computation becomes $Y = X W$ with $X$ shape $(N, d)$ and $W$ shape $(d, k)$, producing $(N,k)$. Batching increases arithmetic intensity by allowing reuse of $W$ for $N$ inputs, and it improves hardware utilization by providing larger contiguous workloads for optimized GEMM kernels. Batch size is a tunable hyperparameter: larger batches give better throughput up to the point where memory capacity or diminishing returns limit gains.

Tiling (blocking) decomposes matrices into smaller submatrices (tiles) so that each tile fits in a particular level of the memory hierarchy (L1 cache, L2 cache, shared memory on GPUs). For GEMM, a common blocking scheme splits $A$, $B$, and $C$ into tiles of sizes that yield good reuse. For example, dividing matrices into blocks of sizes $M_b \times K_b$ for $A$ and $K_b \times N_b$ for $B$ lets each block multiplication perform $2 M_b K_b N_b$ FLOPs using data loaded once into faster memory. The library orchestrates loops over tile indices and calls micro-kernels on tiles to maximize reuse.

Tiling parameters are chosen based on the hardware: register capacity and vector widths determine micro-kernel dimensions, while cache sizes and associativity guide larger blocking choices. Good tiling reduces memory bandwidth pressure by increasing temporal reuse, which increases arithmetic intensity and overall throughput.

Streaming or pipelining refers to techniques where data is moved in and out of fast memory in streams while computation proceeds, overlapping communication and computation. On GPUs and distributed systems, asynchronous memory prefetching and DMA transfers allow overlapping of compute with data movement. For very large matrices that do not fit in device memory (e.g., parameters too large for a single GPU), models may be sharded across multiple devices and streaming is used to load parts of weights on demand. Techniques such as gradient checkpointing trade compute for memory by recomputing activations instead of storing them, which is another form of streaming computation vs storage trade-off.

Out-of-core computation refers to algorithms that operate when data does not fit in main memory (RAM) and must reside on disk or remote storage. For example, very large datasets for training may require streaming minibatches from disk. Out-of-core matrix multiplication can be implemented by partitioning matrices into blocks stored on disk and reading blocks into memory as needed. I/O becomes the performance bottleneck in such cases, so organizing access patterns to be sequential and to maximize reuse of loaded blocks is critical.

Batched GEMM is another important opportunity. Many workloads involve many small matrix multiplications (e.g., operations per attention head or per sequence position). Rather than launching many separate GEMM calls that each incur kernel launch overhead and poor utilization, libraries and hardware provide batched GEMM interfaces that perform many small multiplications in a single call, often with better parallelism and throughput.

In distributed-memory environments, parallel matrix multiplication distributes tiles among processes and uses collective communication (e.g., broadcast, reduce) to exchange submatrices. Algorithms such as Cannon's algorithm, SUMMA (Scalable Universal Matrix Multiplication Algorithm), and 2.5D/3D algorithms optimize communication patterns and minimize the volume of exchanged data. For very large models trained across many machines, these distributed algorithms and communication-reducing techniques (e.g., overlapping communication with computation, gradient compression, asynchronous updates) are critical.

In summary, batching, tiling, and streaming are strategies for improving data locality, increasing arithmetic intensity, and managing memory and communication limits. The right choice depends on hardware constraints (cache sizes, memory bandwidth, interconnects), matrix sizes and shapes, and whether the workload involves many small operations or a few very large ones.

# Basic notions of numerical precision and rounding errors

Numerical precision and rounding errors are fundamental in practice. Computers represent real numbers approximately using floating point formats defined by IEEE 754 or hardware-specific variants. The standard single-precision float (binary32, often written FP32) uses 1 sign bit, 8 exponent bits, and 23 fraction (mantissa) bits, giving about 7 decimal digits of precision. Double precision (binary64, FP64) uses 1 sign bit, 11 exponent bits, and 52 mantissa bits, giving about 16 decimal digits of precision.

Floating point arithmetic is not exact: rounding occurs when the true real result cannot be represented in the finite format. The machine epsilon, denoted $\varepsilon$, characterizes the relative spacing of representable floating point numbers: for binary32, $\varepsilon \approx 1.19 \times 10^{-7}$, and for binary64, $\varepsilon \approx 2.22 \times 10^{-16}$. A useful property is that the result of a single floating point addition or multiplication is the exact mathematical result rounded to the nearest representable number (assuming round-to-nearest mode), introducing a relative error on the order of $\varepsilon$.

Accumulation of rounding errors can be significant in long computations. For example, summing many numbers in naive order can accumulate rounding error; summing from smallest to largest magnitude or using pairwise summation improves numerical accuracy. In matrix multiplications, accumulation of many products into one sum can lead to loss of precision. To mitigate this, libraries sometimes use a higher-precision accumulator (e.g., accumulate FP16 multiplications in FP32) or algorithms like Kahan summation for scalar sums.

Mixed precision is widely used in deep learning: computation is performed in lower precision (e.g., FP16, bfloat16) to accelerate throughput and reduce memory usage, while some quantities (like accumulated sums or master weights) are kept in higher precision (FP32) to preserve numerical stability. bfloat16 (brain floating point) is a 16-bit format with the same exponent width as FP32 but fewer mantissa bits, allowing it to represent a wide dynamic range but with reduced precision. This makes it suitable for training deep networks where gradients can have large dynamic range.

Rounding modes and non-associativity are important. Because floating point addition is not associative, $(a + b) + c$ may differ from $a + (b + c)$. This means that parallel implementations that change the order of operations for performance can also change results slightly. In machine learning, such differences are usually acceptable within tolerance, but in some sensitive algorithms or for debugging reproducibility, they matter.

Underflow and overflow are other concerns. Overflow occurs when a result exceeds the largest representable value and typically leads to Inf. Underflow occurs when a nonzero result is smaller in magnitude than the smallest representable normalized number and may be flushed to subnormal numbers or zero, potentially causing loss of significance. Choosing appropriate initialization, scaling gradients, or using normalization layers can help avoid extremes.

Condition number quantifies sensitivity of a function to input perturbations. For a matrix $A$, the condition number for inversion (in a given norm) is $\kappa(A) = \|A\| \|A^{-1}\|$. If $\kappa(A)$ is large, small perturbations in $A$ or rounding errors may cause large relative errors in computed solutions (e.g., solving linear systems). In ML, badly conditioned covariance matrices or ill-scaled loss landscapes can make optimization numerically challenging. Regularization, normalization, and careful choice of algorithms help.

When designing computations for hardware, be aware of hardware-specific behaviors. GPUs may have different floating point modes, fused multiply-add (FMA) operations that perform $a \times b + c$ with a single rounding, and specialized units (e.g., Tensor Cores) that compute in one precision and optionally accumulate in another. FMA reduces rounding error because it does one rounding instead of two. However, FMA also changes the exact numerical value relative to separate multiply and add steps, and thus can change reproducibility across platforms.

Finally, testing numerical stability is important. Use condition numbers, compare results computed in higher precision, and monitor for NaNs or Infs. When using mixed precision, maintain master copies of parameters in higher precision when necessary and use loss scaling techniques to avoid underflow in gradients.

Conclusion

In this chapter we covered the linear algebra foundations essential to machine learning: the basic structures of vectors and matrices, shapes and broadcasting rules, the central role and cost of matrix multiplication (GEMM), the critical importance of BLAS libraries and optimized kernels, memory layout and cache effects, practical strategies for batching and tiling large computations, and basic numerical precision issues. Together these concepts form the backbone of efficient implementations of neural networks and other machine learning algorithms. Mastery of these ideas will help you read research papers that discuss computational cost, memory trade-offs, and implementation choices and will enable you to design and optimize your own large-scale models.
