Chapter 12: Inference Kernels, Libraries and Deployment Frameworks

Introduction

Large language model (LLM) research has matured to the point where the quality of a model is only part of the engineering problem—getting that model to run quickly, cost-effectively, and reliably in production is equally important. This chapter covers the software components and kernel implementations that are commonly used to optimize LLM inference and deployment. We examine both the low-level building blocks that accelerate linear algebra and attention calculations and the higher-level runtimes and frameworks that orchestrate batching, memory management, and distributed execution. You will learn how quantized kernels trade off precision for efficiency, how specialized libraries like FasterTransformer and cuBLAS are used in practice, and how different parallelism strategies affect latency and throughput. We conclude with practical benchmarking methods for measuring latency, throughput, and memory usage so you can compare designs and tune systems for production constraints.

# High-performance inference libraries (FasterTransformer, cuBLAS, oneDNN)

High-performance inference libraries provide heavily optimized implementations of the core computations used by transformer models: matrix multiplication, layer normalization, activation functions, softmax, and fused attention kernels. These libraries are typically implemented in CUDA for NVIDIA GPUs, in C/C++ with CPU intrinsics for x86, or using vendor-specific APIs. Their goal is to maximize utilization of hardware resources—compute units, memory bandwidth, cache—and to hide the complexity of low-level optimization from model engineers.

cuBLAS is NVIDIA's high-performance linear algebra library. It implements matrix-matrix and matrix-vector operations such as general matrix multiply (GEMM). GEMM is the backbone of transformer inference because attention and feed-forward layers can be expressed as a series of matrix multiplies. cuBLAS exposes routines that support single-precision (FP32), half-precision (FP16), and mixed-precision modes (FP16 compute with FP32 accumulation). Using cuBLAS is essential to get near-peak FLOPS on NVIDIA GPUs. A typical optimization is to use batched GEMMs to amortize kernel launch overhead when many small matrix multiplies are required, or to reshape operations so that large GEMMs are used even for seemingly small logical operations.

oneDNN (formerly MKL-DNN) is Intel's performance library optimized for x86 CPUs. It provides kernels tuned for cache hierarchies, AVX-512 or AVX2 vector units, and threading. When deploying LLMs on CPUs—either on-prem or edge servers—oneDNN provides the primitives to achieve high throughput. It offers fused operators (for example, fused matmul + bias + activation) to reduce memory traffic and improve cache efficiency, which is crucial since CPU memory bandwidth is often the main bottleneck.

FasterTransformer (developed by NVIDIA) is a specialized library that implements transformer-specific kernels: fused attention, rotary position embeddings, fused layer normalization, and optimized MLP blocks. FasterTransformer combines custom CUDA kernels and cuBLAS/cuBLASLt calls to minimize memory movement and kernel launch overhead. A defining feature is operator fusion: combining multiple operations into a single custom kernel to reduce memory reads/writes. FasterTransformer also implements beam search, sampling, and other inference-time algorithms in highly-optimized ways. Libraries like FasterTransformer are targeted at inference workloads and expose APIs or model converters to run models trained in PyTorch or TensorFlow with minimal rework.

An important practical note is that these libraries are complementary. cuBLAS provides the primitive building blocks; FasterTransformer builds on those primitives to provide transformer-level optimizations. oneDNN plays the analogous role for CPU deployments. When integrating such libraries, you must manage data formats (row-major vs column-major), tensor layouts (batch-first vs sequence-first), and memory alignment to ensure kernels run in their optimal regimes.

# Quantized kernel implementations (INT8, 2-bit kernels, ladder-style kernels)

Quantization reduces the numerical precision of model weights and/or activations to reduce memory footprint and accelerate computation. Quantized kernels implement arithmetic in low-precision formats such as INT8, INT4, or even 2-bit representations, often with carefully designed scaling and accumulation strategies to preserve accuracy. The major motivation is twofold: smaller memory usage enables larger effective batch sizes or longer context lengths, and integer arithmetic can be faster on specialized hardware or utilize more efficient memory bandwidth.

INT8 quantization replaces 32-bit or 16-bit floating-point weights with 8-bit integers and uses scale factors to map between the floating-point range and integer range. There are two common quantization schemes: symmetric and asymmetric. Symmetric quantization uses a single scale factor and maps zero to zero, while asymmetric uses both scale and zero-point offsets. A typical forward pass through a quantized GEMM will use INT8 multiply-and-accumulate with FP32 or FP16 accumulation to avoid overflow and preserve dynamic range. Many GPUs provide tensor cores or specialized instructions for INT8 GEMM with mixed-precision accumulation; when available, these can provide significant speedups.

Aggressive quantization goes beyond INT8 to INT4 or 2-bit representations. 2-bit kernels store each weight using two bits, which yields four levels. At this extreme, quantization error must be managed carefully; simple uniform quantization often causes large accuracy degradation. Techniques to mitigate this include per-channel quantization (different scales for each output channel), block-wise quantization (scales applied to small blocks of the weight matrix), and learned or non-uniform quantization where the quantization levels are chosen to minimize reconstruction error. Ladder-style kernels are a practical approach for very low-bit quantization. A ladder or hierarchical quantization scheme represents a weight as a sum of low-bit components: for example, a 4-bit ladder might represent a weight as the sum of two 2-bit components with different scales. This allows incremental reconstruction of higher precision from cheaper low-precision operations. Ladder schemes often enable fast matrix multiply by performing several low-bit GEMMs and summing the results with appropriate scaling.

Another class of techniques is quantization-aware re-scaling and calibration. For example, outlier suppression or outlier-aware quantization treats a small number of very large values as exceptions and stores them in higher precision while quantizing the bulk of the tensor to low precision. This hybrid approach often recovers much of the accuracy while retaining most of the space and speed gains.

Implementing quantized kernels requires modifications beyond simple type casts. Memory packing, alignment, and packing multiple low-bit values into 32-bit words are necessary. Kernels often implement bespoke loops that unpack groups of weights into SIMD or tensor-core-friendly formats. On GPUs, one must also consider instruction-level support: without hardware INT4/INT8 support, gains may be limited. Finally, quantization interacts with operators such as softmax and layer normalization; activations frequently need to be kept in higher precision or handled with careful rescaling to avoid numerical instability.

# Model serving frameworks and high-throughput runtimes (vLLM, Triton)

Model serving frameworks provide the runtime orchestration that turns an optimized model kernel into a production-grade service: they handle batching, scheduling, concurrency, model loading, memory management, and client-facing APIs. Two prominent examples in the LLM ecosystem are vLLM and NVIDIA Triton.

vLLM is a high-throughput, low-latency inference runtime specifically designed for transformer-based models. vLLM focuses on maximizing GPU utilization by dynamically batching requests, implementing efficient token-generation scheduling, and minimizing memory overhead. One of its key ideas is sequence-level batching with flexible scheduling that allows multiple concurrent requests with different current sequence lengths to share computation. Since autoregressive generation appends tokens one at a time, naive handling creates many small single-token computations; vLLM groups these across requests to form larger GEMMs and improves throughput while preserving per-request latency requirements. vLLM also provides memory-efficient attention kernels, request prioritization, and strategies to manage GPU memory when multiple models or multiple versions of a model are resident.

NVIDIA Triton Inference Server is a general-purpose, multi-framework inference serving solution. Triton supports models from TensorFlow, PyTorch, ONNX Runtime, and custom backends, and it provides features such as request batching, multi-model deployment, model versioning, and metrics. Performance-wise, Triton simplifies deployment by offering configurable batching policies (dynamic batch sizing, timeout-based batching), concurrency limits, and GPU memory pooling. Triton also integrates with server-side optimization techniques—CUDA streams, CUDA graph capture, and hardware-specific backend optimizations—to reduce CPU overhead and latency jitter. Its plugin architecture allows teams to incorporate custom optimized kernels or runtimes (for example, calling FasterTransformer or a custom CUDA kernel) while maintaining a consistent management plane.

Both vLLM and Triton exemplify different design philosophies: vLLM is a specialized runtime optimized for autoregressive workloads with deep attention to scheduling nuances, while Triton is a broader platform for many model types and deployment patterns. Choosing between them depends on the use case: dedicated LLM serving with a need for the maximum possible throughput and token-level scheduling often benefits from vLLM, whereas heterogeneous production environments with many models of varying types often use Triton for its operational features.

In addition to these, other commercial and open-source serving solutions (KServe, MLflow, custom microservices) play roles in deployment stacks. Integration points to watch for include model format compatibility (ONNX, TorchScript), memory residency across model versions, and the ability to leverage GPU memory serialization to reduce cold-start times.

# Lightweight inference runtimes (llama.cpp) and edge deployment patterns

Not all deployments target data-center GPUs; many require running models on CPUs or resource-constrained devices. Lightweight runtimes such as llama.cpp have become influential because they implement compact, dependency-light inference pipelines for transformer models, often using well-engineered C/C++ code and quantized kernels to run on consumer hardware.

llama.cpp started as a minimal reimplementation of inference for LLaMA-family models, focusing on portability and efficiency on CPUs. Its implementation includes low-level, cache-friendly GEMM routines, packing formats for quantized weights, and custom routines for attention and sampling. It also implements various quantization schemes (INT8, 4-bit, etc.) and supports multi-threading across CPU cores. The project popularized the idea that, with careful optimization and aggressive quantization, useful LLMs can run locally on laptops and even mobile devices without GPUs.

Edge deployment patterns built on such lightweight runtimes typically trade model size and precision for latency and energy efficiency. Strategies include model pruning, distillation to smaller models, quantization-aware retraining, and offloading part of the computation to a cloud when necessary (hybrid inference). For devices with GPUs (mobile NPUs, integrated GPUs), specialized kernels and hardware-accelerated libraries may be used. For truly constrained devices, one might use very small transformer variants (hundreds of millions to a few billion parameters) and low-bit quantization to fit memory and compute budgets.

A critical operational aspect of edge deployment is the management of model updates and privacy. Lightweight runtimes must include mechanisms to securely download new model weights, validate integrity, and minimize storage churn. When privacy is a concern, running inference locally (on-device) avoids sending data to cloud services, but this increases the importance of robust, efficient inference kernels to meet responsiveness and battery constraints.

# Parallelism strategies: data, model, and pipeline parallelism (GPipe)

Large models frequently exceed the memory and compute capacity of a single device, necessitating parallelism across multiple devices. The three primary parallelism strategies are data parallelism, model parallelism, and pipeline parallelism. Each strategy has different trade-offs in communication cost, memory duplication, and scheduling complexity.

Data parallelism is the simplest conceptually: keep a full replica of the model on each device and split mini-batches of input data across devices. Each device computes forward and backward passes for its subset, then a reduction (all-reduce) synchronizes gradients across replicas. Data parallelism scales well for training when the model fits a single device, because communication costs scale with model size (for gradient synchronization) but computation scales with batch size. For inference, data parallelism is useful for increasing throughput when the model already fits on a device and different requests can be handled independently.

Model parallelism splits the model's parameters across devices. A common form is tensor parallelism: for a matrix multiply where the weight matrix $W \in \mathbb{R}^{d_{\text{out}} \times d_{\text{in}}}$, you can partition $W$ column-wise or row-wise across devices and perform local partial GEMMs followed by an all-reduce or concatenation. Tensor parallelism reduces per-device memory but introduces inter-device communication at each layer. Another variant is expert-based parallelism (MoE—mixture of experts) where different parameters are targeted to different devices based on routing; this can reduce computation per device but adds routing overhead.

Pipeline parallelism partitions the model into stages arranged sequentially across devices. Each device holds contiguous layers (for example, layers 1–6 on device A, layers 7–12 on device B). Inputs flow through the pipeline: device A computes forward on a micro-batch then sends intermediate activations to device B. Pipeline parallelism reduces memory usage per device and allows scaling deeper models that do not fit on a single accelerator. However, naive pipelines have poor device utilization because only one device is active for parts of the schedule. GPipe introduced micro-batching and careful scheduling to overlap computation across stages. By splitting the batch into $M$ micro-batches, pipeline execution resembles an assembly line, improving utilization: while stage 1 processes micro-batch 3, stage 2 processes micro-batch 2, and so on. The communication pattern and scheduling are critical to reduce bubbles (idle periods) and to constrain memory for activations.

Hybrid approaches combine these strategies. For example, Megatron-LM uses tensor parallelism inside layers and pipeline parallelism across layer groups, together with data parallelism across replicas. When building a distributed inference system, you choose a combination depending on the target hardware, model architecture, and latency vs throughput targets. For autoregressive inference, pipeline parallelism can be less attractive because generation is inherently sequential at the token level; tensor parallelism is often preferred as it allows layer computations to be split while minimizing the latency-critical inter-stage communication.

Important performance equations to keep in mind are simple throughput and latency relationships. If $T_{\text{comp}}$ is computation time per request and $T_{\text{comm}}$ is communication time per request introduced by parallelism, the end-to-end latency roughly scales as
$T_{\text{latency}} \approx T_{\text{comp}} + T_{\text{comm}}$.
Throughput, measured in tokens/sec or requests/sec, is inversely related to the per-request time when the system is saturated:
$\text{Throughput} \approx \frac{1}{T_{\text{latency}}}$ (for single-stream systems) or more generally
$\text{Throughput} \approx \frac{B}{T_{\text{comp}} + T_{\text{comm}}}$,
where $B$ is the effective batch size (or number of concurrent micro-batches). Parallelism choices change $T_{\text{comm}}$ and how $B$ can be scaled without increasing $T_{\text{comp}}$ beyond device limits.

# Benchmarking practices: measuring latency, throughput, and memory usage

Rigorous benchmarking is essential to make trustworthy claims about performance and to guide optimization decisions. Benchmarking LLM inference has several dimensions: latency (especially tail latency), throughput (tokens/sec or queries/sec), and memory usage (peak GPU/CPU RAM). It is important to design benchmarks that reflect realistic workloads rather than synthetic best-case setups.

Latency should be measured at the client-observed level and should report distributions, not just means. In conversational systems, the 50th, 95th, and 99th percentile latencies are informative: average latency can be dominated by outliers and does not capture user experience. For autoregressive models, measure both partial metrics (time to first token) and full-response latency. Instrument the end-to-end path including network overhead and request queuing as these components are often substantial in production.

Throughput measures how many tokens or requests can be processed per unit time under sustained load. To measure throughput accurately, saturate the system with a realistic mix of request sizes and measure steady-state performance after warm-up. Report both maximum achievable throughput and throughput at acceptable latency thresholds. Many inference runtimes trade latency for throughput via batching; therefore, throughput numbers without latency constraints can be misleading.

Memory usage has multiple meanings: model parameter memory, activation memory during inference, and transient workspace allocated by libraries. Measure peak GPU memory usage during a representative run, and account for memory fragmentation and caching overhead. Tools like NVIDIA's nvprof, nvstats, or device APIs can measure GPU memory usage, while OS-level tools and custom instrumentation are used for CPU RAM. When quantized kernels are used, report the stored model size and the runtime expansion (for example, if weights are packed, unpacking or accumulation buffers may be required).

When designing benchmark workloads, include variability representative of production: diverse prompt lengths, a realistic distribution of batch sizes, and concurrent client patterns. Synthetic microbenchmarks (single prompt repeated) are useful to measure kernel-level maximums but do not reflect queuing, scheduling, or startup behaviors. Report warm-up effects separately: CUDA JIT compilation, kernel caches, and memory allocation can make the first few requests slower than steady-state. Use reproducible scripts with seeds and fixed model checkpoints and specify hardware, driver versions, and library versions to ensure comparability.

Common pitfalls in benchmarking include neglecting CPU overhead, ignoring data serialization costs, and failing to measure tail latencies. Also be careful when using simulated parallelism or emulation; results may not transfer to real multi-device systems because network fabric and synchronization have significant impacts. If reporting energy or cost metrics, measure GPU power draw with device APIs or external meters and normalize results per token or per response.

Finally, when comparing across frameworks or kernels, ensure you use equivalent numerical precision and model fidelity. Quantized kernels may reduce model size and increase speed but at some cost in accuracy—report accuracy metrics (perplexity, token-level accuracy, or downstream task performance) alongside performance. This allows a fair assessment of trade-offs.

Conclusion

Efficient LLM inference is a multi-layered engineering discipline. Low-level libraries like cuBLAS, oneDNN, and FasterTransformer provide the raw computational power through optimized kernels and operator fusion. Quantized kernels—INT8, 4-bit, 2-bit and ladder-style schemes—shrink memory and accelerate computation but require careful design to maintain accuracy. Model serving frameworks and runtimes like vLLM and Triton orchestrate batching, scheduling, and memory management, while lightweight runtimes such as llama.cpp make on-device inference feasible. Parallelism strategies (data, model, pipeline) enable scaling beyond single-device limits but introduce communication and scheduling trade-offs. Finally, rigorous benchmarking practices are necessary to measure latency, throughput, and memory usage meaningfully and to guide practical deployment decisions. Mastery of these components is essential for anyone seeking to translate state-of-the-art LLMs into production systems.
