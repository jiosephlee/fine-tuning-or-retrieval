# Introduction

Measuring and reporting system-level performance of large language models (LLMs) is essential for both research and engineering. Performance metrics such as throughput, latency, and memory footprint determine whether a model can be deployed in a real system, how it will scale, and what optimizations make sense. Equally important are energy measurements and fair comparison across different precisions and implementations. This chapter explains how to define these metrics rigorously, how to set up reproducible benchmarking experiments, how parallelism choices affect results, and how to interpret trade-offs between latency, memory, energy, and accuracy. The explanations emphasize intuition and practical procedures so you can both run measurements and correctly interpret results in papers and system reports.

# Definitions: throughput (tokens/sec), latency (time per token), memory footprint

Throughput and latency are related but distinct ways to describe time cost.

Throughput is a rate: how many tokens the system can produce (or consume) per unit time. We typically report throughput as tokens per second. If you generate $N$ tokens in $T$ seconds, the average throughput is
$${\text{throughput}} = \frac{N}{T} \quad\text{tokens/sec}.$$
Throughput is most meaningful in contexts where the system is continuously processing many items (e.g., a batch of user requests, or long generation).

Latency is the time experienced for an individual request or token. There are two common latency notions: sequence latency and per-token latency. Sequence latency is the total wall-clock time to produce an output sequence of length $L$ (for example, the time to generate 128 tokens). Per-token latency is often expressed as time per token; this can be the average per-token time within a sequence, or the marginal time to produce the next token during autoregressive generation. If the sequence generation time is $T$ for $L$ tokens, the average per-token latency is
$${\text{avg latency per token}} = \frac{T}{L} \quad\text{seconds/token}.$$
However, for interactive systems the important quantity is often the time to produce the next token after previous tokens are available (the incremental latency), which includes any synchronous overheads like model loading or barrier synchronization.

When reporting latency, be explicit about what is included: model forward pass only, full token sampling (including softmax/top-k/top-p), tokenization/detokenization, communication overheads, and any batching delays. Distinguish between cold-start latency (including model load and JIT compilation) and steady-state latency after warmup. Also report latency percentiles (median, 95th, 99th) rather than only mean or minimum, because tail latencies matter for user experience.

Memory footprint refers to the resident memory used during inference or training. For inference, the major components are:

- Model parameters (weights), which take $P$ bytes equal to the number of parameters times bytes per parameter depending on precision (e.g., 2 bytes for FP16, 1 byte for INT8 if applicable).
- Activation memory: intermediate tensors (attention keys/values, hidden layer outputs) that depend on sequence length $L$ and batch size $B$. Attention mechanisms typically require $O(L^2)$ memory for naive attention matrices, while optimized causal attention implementations store only keys/values $O(L)$ per layer but still accumulate stored KV tensors across timesteps for autoregressive decoding.
- Workspace and scratch memory: temporary memory used by kernels, convolution/linear workspaces (cuBLAS/cuDNN), and fused operations.
- Overheads from the runtime: memory allocators, CUDA contexts, and memory reserved but unused by the application (fragmentation and allocator thresholds).
- (If measuring training) optimizer state and gradients, which can be several times larger than the model weights.

A precise memory measurement is the peak resident set size (RSS) or device memory allocated at any point during the run. Report both the peak and a breakdown where possible: parameters, activations, optimizer states, and workspace.

# Benchmarking setups: sequence length, batch size, hardware configuration

Benchmarking is only meaningful when the experimental conditions are explicit and representative. Key axes are sequence length, batch size, and the hardware/software configuration.

Sequence length affects both compute and memory, especially for attention. Many LLM costs scale with sequence length $L$ roughly as $O(L)$ for per-step KV storage and $O(L^2)$ for direct pairwise attention if computed naïvely. When benchmarking, choose sequence lengths that reflect your use case: short (e.g., 1–32 tokens) for interactive scenarios, medium (e.g., 128–512) for conversational contexts, and long (e.g., 2k–64k) for long-context models. Always report which tokenization was used so that "128 tokens" is reproducible.

Batch size determines statistical multiplexing: larger batches improve throughput by amortizing kernel launches, but increase per-sequence latency and memory footprint. Distinguish between micro-batching for pipeline parallelism and user-visible batch size. For interactive, single-user latencies, report batch size 1 results. For throughput-oriented server benchmarks aiming for cost-efficient throughput, report the maximum sustainable throughput at larger batch sizes. When reporting throughput as a function of batch size, present a curve that shows where throughput saturates and where memory limits are reached.

Hardware configuration matters heavily: GPU/TPU model, CPU, memory speed, interconnect (PCIe vs NVLink), and system power settings. Report model name (e.g., NVIDIA A100 40GB), clock settings (if modified), CUDA/cuDNN/cuBLAS versions, framework versions, and whether power management or boost modes were enabled. For multi-GPU or multi-node setups, report the interconnect topology (NVLink, InfiniBand), bandwidth, and topology details that could affect cross-device communication.

Reproducibility tips: fix seeds for deterministic kernels where possible, disable GPU frequency scaling if you want stable measurements, run with a consistent thermal environment, and repeat runs to measure variance. Always separate cold-start effects by doing a warmup phase (e.g., discard the first N runs) and report steady-state numbers with confidence intervals.

# Using pipeline/model parallelism during measurement

Model and pipeline parallelism change how compute and communication are scheduled, which influences both throughput and latency in nontrivial ways. Two common schemes are data parallelism and model parallelism; model parallelism itself can be subdivided into tensor/model sharding (splitting layers across devices) and pipeline parallelism (splitting a sequence of layers into stages executed on different devices).

With pipeline parallelism, layers are grouped into stages across devices. To reach high throughput, implement micro-batching and schedule multiple micro-batches in flight to fill pipeline stages. The steady-state throughput scales linearly with the number of pipeline stages when filled, but pipeline fill and drain introduce amortized startup and shutdown latency. Specifically, if you have $S$ stages and $M$ micro-batches in flight, the ideal steady-state throughput benefits once $M \ge S$. However, the time to produce the first output token is roughly the sum of per-stage processing times (pipeline depth), so pipeline parallelism can worsen single-request latency even while increasing throughput.

Model parallelism that shards tensors (e.g., tensor parallelism) introduces synchronous collective operations inside layer execution (e.g., all-reduce for gradients / weight synchronization or all-gather for partitioned outputs). These collectives add latency per layer but allow larger models than a single device memory could host. When measuring, distinguish between the added per-layer overhead (which shows up as increased latency per token or per sequence) and the ability to fit larger models, which may otherwise be impossible.

Practical measurement recommendations:

- Measure both throughput and end-to-end latency for pipeline-configured runs. Report the micro-batch size and the number of in-flight micro-batches for pipeline runs.
- For interactive latency-focused applications, measure the single-stream case (one request at a time) with pipeline stages idle except for the request, so you capture startup and pipeline bubble costs.
- For throughput-focused scenarios, measure steady-state throughput under sustained load with sufficient micro-batches to fill the pipeline. Report how long you ran the sustained load and show that throughput was stable.
- Account for communication overheads explicitly. Measure the fraction of time spent in compute versus communication (e.g., using profiling tools or traces). This helps to reason about scaling behavior when adding more devices.

Be aware of hidden costs like increased memory consumption for activation checkpointing, additional buffering for pipeline scheduling, and fragmentation from many small allocations across devices. For fairness, when comparing implementations with and without pipeline parallelism, present both per-device and aggregate system-level metrics.

# Measuring energy: arithmetic-only estimates vs end-to-end measurements

Energy consumption is central to cost and environmental impact. There are two broad classes of energy estimates: arithmetic-only (modeling energy from compute) and end-to-end (measuring wall power draw). Each has strengths and limitations.

Arithmetic-only estimates compute the energy by counting floating-point operations (FLOPs) and multiplying by an energy-per-FLOP constant. If a run requires $F$ FLOPs, and if you assume an average energy per floating-point operation $e_{\text{FLOP}}$ (joules per FLOP), then
$${\text{estimated energy}} = F \cdot e_{\text{FLOP}}.$$
This approach can be useful to compare algorithms abstractly because it isolates computational work independent of the hardware stack. It is also straightforward to compute from model architecture details and known counts for matrix multiplies and attention operations. However, arithmetic-only estimates ignore memory movement, activation storage, idle device power, CPU overhead, and inefficiencies of the implementation. Memory access energy can dominate compute energy especially for memory-bound kernels; moving data over PCIe or DRAM costs orders of magnitude more energy than arithmetic in some cases. Thus arithmetic-only estimates can be highly misleading when used as the sole metric.

End-to-end measurements capture real power usage by measuring actual wall power during runs and integrating over time to obtain energy. Popular measurement methods include:

- On-server power distribution unit (PDU) readings: many datacenter PDUs provide per-outlet energy usage. These are accurate for whole-server energy but may include other components like fans and disks.
- On-board sensors via vendor APIs: NVIDIA Management Library (NVML) provides per-GPU power draw estimates with a sampling frequency. Intel RAPL provides package/cpu power readings. These are useful for attributing power to specific devices.
- External power meters (e.g., Yokogawa, Monsoon) that measure wall power or device power directly. These are often the most precise but require instrumentation.
- Host-level tools (e.g., ipmitool) or cloud provider monitoring metrics, which can provide coarse-grained measurements.

When performing end-to-end measurements, adopt the following practices. Measure baseline idle power with the same system state but without running the model. Subtract idle power from active measurements to obtain the incremental power used by inference. Ensure that measurements capture the full lifecycle of the workload, including warmup and steady-state; report energy per token as
$${\text{energy per token}} = \frac{\text{measured energy}}{\text{number of tokens produced}}.$$
Use sufficient sampling frequency and duration to reduce noise; repeat experiments and report mean and variance.

Combine arithmetic-only and end-to-end measurements when possible. Compute an estimate of the fraction of energy coming from compute versus memory/communication by instrumenting time spent in compute kernels and collecting energy counters if the hardware exposes component-level measurements. This can clarify whether algorithmic reductions in FLOPs would meaningfully reduce energy or whether the run is dominated by memory transfer and idle power.

# Comparative reporting and normalization across precisions and implementations

Comparing systems or implementations requires careful normalization so that differences are attributable to algorithmic or hardware choices, not measurement artifacts.

First, define a canonical workload. Use the same model checkpoint, tokenizer, prompt, sequence length, sampling parameters (e.g., temperature, top-p), and batch size across runs. For generation benchmarks, fix random seeds when possible to ensure identical token sequences; note that non-deterministic kernels and different precisions can still produce divergent outputs, so equality of outputs is not always achievable.

Precision (FP32, FP16, BF16, INT8, etc.) affects both speed and model accuracy. When comparing precision modes, report both performance metrics (throughput, latency, memory, energy) and accuracy or output quality metrics (e.g., perplexity, task accuracy). For some lower-precision modes, post-training quantization may change outputs sufficiently to hurt accuracy; report whether calibration or fine-tuning was applied. When normalizing performance across precisions, consider reporting effective throughput normalized to equivalent accuracy: for instance, the tokens/sec at which the model achieves at least X% of baseline accuracy. This helps assess whether performance gains come at unacceptable quality degradation.

Implementations (frameworks, kernel libraries) differ in kernel fusion, memory layout, and communication optimizations. When comparing implementations, ensure consistent software stacks where possible (same CUDA and driver versions). If comparing across different hardware generations, consider normalizing by peak theoretical FLOPS or memory bandwidth, but be wary: theoretical peaks are rarely achieved. Instead, prefer microbenchmarks that measure achieved FLOPS and bandwidth for the key kernels (e.g., GEMM throughput at the shapes used) and report those numbers as context.

Normalization strategies:

- Per-token normalization: energy or time per token is usually the most portable metric when token lengths vary.
- Per-1k-tokens or per-1M-tokens can make small numbers easier to report.
- Accuracy-normalized metrics: divide performance metrics by an accuracy measure or report Pareto frontiers (see next section).
- Hardware-normalized metrics: express results per TFLOP of achieved compute or per watt of idle-subtracted power. This can help judge software efficiency independent of hardware capability.

When presenting comparisons, include confidence intervals from repeated runs and report both mean and percentile tail values for latency. Show aggregated plots (e.g., throughput vs latency vs memory) and tabular breakdowns. Document all measurement details: random seeds, warmup counts, measurement durations, software and driver versions, and how energy was measured and normalized.

# Interpreting trade-offs: Pareto efficiency in latency, memory and accuracy

Design and optimization of LLM systems inherently involve trade-offs among latency, memory, throughput, energy, and accuracy. Pareto efficiency is a useful concept: a configuration is Pareto-optimal if no other configuration is strictly better in all considered dimensions. Presenting Pareto frontiers helps stakeholders choose a point that matches application priorities.

Consider three axes: latency (L), memory footprint (M), and accuracy (A). Many optimizations improve one axis at the cost of another. For example, quantization reduces memory (M) and often increases throughput/reduces latency (L), but may reduce accuracy (A). Activation checkpointing reduces memory but increases compute and latency. Pipeline parallelism increases throughput but can increase single-request latency and memory overhead for buffers. Distillation reduces model size and often improves latency while maintaining some or most of the accuracy, but comes at the cost of a separate training step.

To reason about trade-offs quantitatively, plot configurations in the multidimensional space and compute Pareto frontiers. For instance, for fixed hardware, plot latency vs accuracy and mark which points are dominated. Points on the frontier represent the best achievable latency for a given accuracy level; designers can then pick the operating point consistent with application constraints (e.g., maximum acceptable latency or minimum required accuracy).

When evaluating Pareto efficiency:

- Always include multiple metrics; a single aggregated metric can hide trade-offs. However, composite metrics (e.g., energy per correct prediction) can be insightful if well-justified.
- Be cautious with aggregate metrics that combine heterogeneous units; normalization and weighting must be explicit.
- Consider application-level metrics. For example, in question-answering, accuracy measured via exact match or F1 may better capture utility than perplexity.
- For latency-sensitive applications, tail latency (e.g., 99th percentile) is often more important than mean latency. A configuration with low mean but high tail may be unacceptable.
- Memory constraints may dictate algorithmic choices: if the model must fit in a certain device memory, only configurations that satisfy $M \le M_{\text{device}}$ are feasible.

In practice, present trade-offs as a set of plots and tables: throughput vs latency, memory vs latency, energy vs accuracy, and a combined Pareto plot when dimensions are reduced to two or three. Also provide narrative guidance: for interactive systems with tight latency budgets, prefer optimizations that reduce per-token latency even if throughput or energy is suboptimal; for batch throughput scenarios, favor pipeline parallelism or larger batch sizes to maximize cost-efficiency.

# Example measurement protocol

To make the ideas concrete, here is a practical, repeatable protocol for measuring inference latency, throughput, memory, and energy for an autoregressive LLM in a single-GPU setting. You can extend it to multi-GPU with additional steps to control micro-batching and pipeline settings.

1. Hardware and software recording. Log hardware model, GPU type, driver and CUDA versions, framework versions, and power settings. Fix scheduler governors if possible.

2. Model and workload. Specify the model checkpoint, tokenizer, prompt, sequence length $L$, batch size $B$, sampling strategy, and number of tokens to generate per sample.

3. Warmup. Run $W$ warmup iterations and discard them (e.g., $W=10$). Warmup allows JIT compilation and kernel autotuning.

4. Steady-state measurement. Run $N$ measured iterations (e.g., $N=200$) and record per-iteration wall-clock times. From these, compute mean throughput, median latency, and 95th/99th percentiles.

5. Memory. Monitor peak device memory (e.g., using nvidia-smi or framework allocator hooks) during the measured iterations. Report peaks and a breakdown if available.

6. Energy. Measure wall power with a PDU or use NVML per-GPU power counters sampled at high frequency during measured iterations. Record idle power before starting and subtract it. Integrate power over time to get energy per run, then divide by number of tokens to get energy per token. Repeat multiple times and report mean and standard deviation.

7. Repeat across batch sizes and sequence lengths. For each configuration, repeat steps 3–6 to build curves of throughput vs batch size and memory vs sequence length.

8. Reporting. Include the raw timing histograms, energy traces, and the full configuration metadata. When comparing precisions or implementations, ensure identical workloads and report any calibration or fine-tuning applied.

# Conclusion

Rigorous measurement methodology for throughput, latency, memory, and energy is crucial to evaluate and compare LLM systems. Definitions must be precise, experimental setups reproducible, and parallelism effects carefully characterized. Energy should be measured end-to-end when possible and augmented with arithmetic estimates to explain where energy is spent. Comparative reporting requires normalization across precisions and implementations and clear reporting of workloads and hardware. Finally, interpret results through the lens of trade-offs and Pareto efficiency to select configurations that meet real application constraints. Following the practices in this chapter will make your measurements credible, reproducible, and actionable.
