Introduction

Web-scale content discovery and filtering is a common problem in many applications: building domain-specific corpora, monitoring news and social media for mentions of a topic, creating training sets, or pre-filtering candidate pages for a heavier downstream NLP pipeline. Full neural rankers and expensive language models give excellent accuracy but are often too slow or too costly to run over billions of web pages. Lightweight classifiers — in particular the family of models inspired by fastText — offer a pragmatic middle ground: simple, fast, memory-efficient, and surprisingly effective when used with careful feature engineering and systems-level design.

This chapter explains the design and use of fastText-style classifiers and related tools for retrieval and filtering at scale. We begin with the simple bag-of-words and shallow embedding paradigm that underlies fastText, then describe fastText’s model details including n-gram features and common training hyperparameters. We then tackle precision versus recall tradeoffs when these classifiers are used for retrieval, strategies for using seeds and mining hard negatives, techniques to scale classifiers to billions of pages, and finally methods for ranking, thresholding and selecting the top-k results for downstream use. Throughout, emphasis is on intuition and practical choices you will see in research and engineering pipelines.

# Bag-of-words and shallow embedding classifiers

At the heart of fastText and many similarly lightweight systems is a simple idea: represent a document by a (possibly weighted) bag of sparse features and learn a linear classifier on top of low-dimensional embeddings of those features. This design contrasts with deep sequence models: instead of modeling word order with multiple layers and attention, we compress the document into a fixed-size vector and apply a simple linear layer to predict labels.

Concretely, suppose the vocabulary has $V$ distinct tokens (words or tokenized character n-grams). A document is represented as a multiset of tokens $t_1,\dots,t_n$. A naive bag-of-words (BoW) feature vector $x\in\mathbb{R}^V$ has $x_i$ equal to a count or TFIDF weight for token $i$, but that high-dimensional vector is expensive. Shallow embedding classifiers reduce dimensionality by learning an embedding matrix $W\in\mathbb{R}^{V\times d}$ that maps each token $i$ to a dense vector $w_i\in\mathbb{R}^d$. The document vector $z$ is the average (or weighted sum) of its token embeddings:
\[
z = \frac{1}{n}\sum_{j=1}^{n} w_{t_j}.
\]
A linear classifier uses $z$ to score $C$ possible classes with weight matrix $U\in\mathbb{R}^{C\times d}$ and bias $b\in\mathbb{R}^C$:
\[
s = U z + b,
\]
and typically applies a softmax to get class probabilities:
\[
\hat{p}_c = \frac{\exp(s_c)}{\sum_{c'} \exp(s_{c'})}.
\]

Intuition: averaging embeddings loses word order but retains information about which words appear and their relative importance. When tasks depend more on the presence of topical words than on precise syntactic structure (e.g., “Is this page about cardiology?”), the BoW+embedding approach works extremely well. It also has favorable statistical and computational properties: fewer parameters than deep models, convex-ish optimization surface for the linear part, and inference cost proportional to the number of tokens rather than model depth.

There are a few simple variants that improve robustness. Using weighted averages (e.g., TF-IDF or subsampling frequent words) discounts ubiquitous words. L2-normalizing $z$ or applying batch normalization stabilizes training. Representing features not just as whole words but as character n-grams (described below) gives robustness to morphology and typographical variants. Finally, despite the simplicity, these models are trained end-to-end: embeddings and classifier weights are learned jointly from labeled data by optimizing cross-entropy (or another loss), often using stochastic gradient descent (SGD).

# fastText: model architecture, n-gram features, training hyperparameters

fastText is an efficient implementation of the shallow embedding classifier family with several practical improvements. The core supervised fastText model uses an embedding layer, an averaging (or sum) operation, and a linear classifier (softmax). Its design choices target speed and robustness.

Model architecture. The supervised fastText architecture consists of three logical layers. First, the input is tokenized; each token (and optionally token n-grams) maps to a row of the embedding matrix $W\in\mathbb{R}^{V\times d}$. Second, the embeddings for tokens present in the document are aggregated into a fixed-size document vector $z$, commonly by average:
\[
z = \frac{1}{|D|}\sum_{i\in D} w_i,
\]
where $D$ is the set (or multiset) of features extracted from the document. Third, a linear classifier produces scores $s = U z + b$ for $C$ classes. For multiclass problems distribution over labels is given by the softmax. For multilabel problems with possibly many true classes per example, a one-vs-all logistic setup or independent sigmoid outputs can be used.

N-gram features. A key practical innovation in fastText is the use of token n-grams as additional features. Instead of relying on word order modeling, n-grams capture short local contexts and morphological structure: for the word sequence “financial market risk”, 1-grams include “financial”, “market”, “risk”; 2-grams include “financial_market” and “market_risk”. fastText typically uses character-level n-grams for robustness to misspelling and morphology (e.g., the token “running” might generate character 3-grams “run”, “unn”, “nni”, “nin”, “ing”), or word n-grams for phrase features.

fastText uses a hashing trick to store n-grams compactly and allow a fixed-size feature space. For every n-gram, a hash value maps it into one of $B$ buckets; multiple n-grams can collide into the same bucket, which introduces noise but keeps the memory footprint bounded. The number and size of n-grams (e.g., character n from 3 to 6) and the number of hashed buckets are important hyperparameters.

Losses and output approximations. For multiclass classification with many classes, computing softmax normalization over all $C$ classes at each update is expensive. fastText supports strategies such as hierarchical softmax (a binary tree over classes allowing $O(\log C)$ normalization) and negative sampling for skip-gram training. In the supervised case, hierarchical softmax is particularly useful when the number of labels is large. For moderate number of labels, plain softmax (with efficient matrix operations) is fine.

Training hyperparameters. Several hyperparameters control both accuracy and resource use.

- Embedding dimension $d$: common values are 50, 100, 300. Larger $d$ increases capacity but slows training and inference and raises memory. For many topical classification tasks, $d=100$ is a good tradeoff.

- Learning rate $\eta$: initial learning rate and decay schedule. fastText uses SGD with a learning rate schedule that decays linearly with the number of processed samples. Typical initial rates are $0.05$ to $0.5$ depending on dataset size.

- Epochs: number of passes over training data. fastText is typically trained for a small number of epochs (5–30), since it is fast. More epochs help with small datasets but can overfit when data is large.

- Min word count (minCount): tokens with frequency below this are ignored. This reduces noise and vocabulary size.

- Word n-grams / char n-grams: which ranges to include, e.g., word n-grams up to length 2 or character n-grams of length 3–6.

- Bucket size for hashed n-grams: number of hash buckets, e.g., $10^6$.

- Loss/softmax strategy: plain softmax vs hierarchical softmax vs one-vs-all. For extremely many labels, hierarchical softmax helps.

- Regularization: weight decay or L2 penalty is less common; instead, controlling model size and using dropout-like tricks (subsampling tokens) is more common.

- Negative sampling size (for unsupervised or skip-gram pretraining): number of negative samples per positive.

Training is typically done with asynchronous multi-threaded SGD; fastText implements lock-free updates to the embedding matrix and classifier weights to exploit multiple CPU cores. Because updates are local and gradients are small, this yields good speed without severe optimization instability in practice.

# Precision vs recall tradeoffs in classifier-based retrieval

When using classifiers as retrieval filters, your objective is not simply to minimize classification error on a holdout set but to find relevant pages while controlling the volume of candidates. This reframes evaluation and model choices in terms of precision (how many retrieved items are actually relevant) and recall (what fraction of all relevant items you retrieved).

Define the basic metrics. For a binary label of interest, let TP be true positives, FP false positives, and FN false negatives. Precision and recall are:
\[
\text{Precision} = \frac{\text{TP}}{\text{TP} + \text{FP}},\qquad
\text{Recall} = \frac{\text{TP}}{\text{TP} + \text{FN}}.
\]
In retrieval use, precision controls the amount of noise you pass to downstream systems; recall controls coverage of relevant material.

A simple classifier outputs a real-valued score $s(x)$; choosing a decision threshold $\tau$ yields a binary decision. Moving $\tau$ trades precision for recall: raising $\tau$ reduces FP and typically harms recall; lowering $\tau$ increases recall but also increases FP. The precision-recall (PR) curve plots precision vs recall for all $\tau$ and is typically more informative than ROC when classes are highly imbalanced (which is common with web-scale retrieval — relevant pages are rare).

For pipeline design, the tradeoff you choose depends on downstream costs. If human reviewers curate the final set, you might insist on high precision to reduce human time. If you plan an expensive reranker downstream (say, a transformer-based ranker), you might tolerate lower precision in the classifier stage to ensure high recall, and then rely on the reranker to clean up. In general it is common to use a two-stage cascade: a high-recall, cheap filter followed by a high-precision expensive scorer.

Calibration and decision rules. Classifier scores are not necessarily calibrated probabilities; the numeric score ordering usually matters for ranking, but thresholds need calibration. Calibration methods such as Platt scaling (logistic regression on the scores) or isotonic regression can map scores to better probability estimates. When you care about precision at a specific recall level (or vice versa), you can pick a threshold on validation data that achieves the required metric and then use that threshold in production, while monitoring for distribution shifts.

Imbalanced classes and extreme prevalence. Web retrieval often means relevant pages are one in a million. In such regimes, even tiny false positive rates yield huge absolute numbers of negatives to process. Precision at scale can be dominated by such prevalence: a classifier with 99.9% precision may still deliver thousands of false positives when applied to billions of pages. Therefore, you must think about absolute volumes as well as relative metrics. Techniques include cascade thresholds, per-domain or per-source heuristics, and combining multiple orthogonal filters (e.g., keyword whitelist + classifier) to reduce the input stream to manageable size.

Evaluation metrics for retrieval differ from standard classification metrics. Precision@k measures the precision among top $k$ scored items. Recall@k measures fraction of total relevant items found in top $k$. F1 balances precision and recall. For ranked outputs where relevance has graded judgments, use NDCG (normalized discounted cumulative gain). Importantly, choose metrics that reflect downstream costs, and validate thresholds with held-out data that matches the production distribution as closely as possible.

# Using positive and negative seeds; iterative hard-negative mining

When you don’t have a large labeled dataset, a common practical approach for retrieval is to start with a small set of seed examples: a few positive documents for the topic and optionally negative seeds (documents known not to belong). Seeds can be hand-written queries, example URLs, or curated positive/negative documents.

Supervised learning with seeds. With few seeds, a standard supervised classifier will overfit. One solution is to treat seeds as positive examples and use a large sample of unlabeled web pages as negatives (assuming most unlabeled documents are negative for the rare topic). Alternatively, use weak supervision: generate noisy labels by keyword matching or distant supervision, and then train on this noisy dataset.

Hard-negative mining. Initial classifiers trained on seeds often make systematic mistakes: they score some irrelevant pages highly because they share surface tokens with positives. Hard-negative mining addresses this by iterating: (1) train a classifier on current positives and negatives, (2) run the classifier over a large unlabeled corpus and collect the highest-scoring negatives (false positives), (3) add those hard negatives to the negative training set, and (4) retrain. This process forces the classifier to learn finer distinctions that separate positives from common confounders.

Hard-negative mining requires careful bookkeeping: manually reviewing mined negatives can be costly, so you might mix automatically mined negatives with a small number of human-labeled checks. If you add too many noisy negatives you can bias the model or harm recall; a common strategy is to add a moderate number of the top-ranked negatives per iteration and to downweight uncertain labels.

Using multiple seed types. Positives are often heterogeneous; if you only seed with one subtype of the topic, the classifier will specialize. To encourage breadth, include diverse positives that cover subtopics, style variations, and multiple domains. Negative seeds are most useful when they represent typical confusers — e.g., pages that use the same common phrases but are off-topic. You can also include “domain-negative” seeds (entire sites or domains that are known to be irrelevant) to avoid repeated false positives from the same sources.

Semi-supervised and self-training variants. Besides explicit hard-negative mining, self-training uses the classifier’s confident predictions on unlabeled data as pseudo-labeled examples and then retrains. Self-training risks confirmation bias: errors in confident predictions get amplified. Hard-negative mining is a targeted form of self-training that explicitly focuses on negatives the classifier finds confusing, which tends to be safer and more effective for retrieval tasks.

# Scaling classifiers to billions of web pages

Applying a classifier to billions of pages demands careful engineering to make prediction fast, memory-efficient, and parallelizable. Here are the major considerations and common techniques.

Model compactness. The runtime memory footprint should be small enough to fit either in RAM across available machines or in a memory-mapped file read efficiently. fastText-style models are compact: an embedding matrix $W$ of size $V\times d$ and classifier matrix $U$ of $C\times d$ dominate memory. You reduce memory by lowering $V$ (prune low-frequency features), lowering $d$, using quantization (e.g., 8-bit/4-bit embeddings), and hashing features into a fixed-size bucketed space. Embedding quantization (scalar or vector quantization) can shrink size while preserving accuracy.

Feature extraction throughput. Tokenization and n-gram hashing must be extremely fast. Use efficient streaming tokenizers, avoid complex normalization steps at prediction time, and precompute features where possible. For fetching pages, strip large binary blobs and focus on relevant text fields (title, meta description, first N KB) to reduce I/O and processing.

Parallelism and sharding. Distribute the corpus across many worker machines or map tasks; each worker loads the model and processes its shard. fastText supports multi-threaded prediction; for massive scale you typically run many processes across a cluster. Using a parameter server is usually unnecessary for pure inference since the model is read-only; instead, store a single serialized binary model and memory-map it on workers to save memory and speed startup.

Batched and asynchronous inference. Batch several documents per call to take advantage of matrix-matrix operations for computing embeddings and classifier scores. Even though each document has variable length features, you can treat the batch as a sparse matrix multiply. Use asynchronous I/O to hide network or disk latency while CPU computes predictions.

Two-stage cascades. Very commonly, a cascade is used: an ultra-cheap heuristic (regex, keyword whitelist, or tiny Bloom filter) first removes obviously irrelevant pages; the shallow classifier runs next; finally, an expensive re-ranker or human review happens. Cascades reduce average cost while maintaining high recall if designed carefully.

Indexing and candidate generation. Instead of scoring every page, you can pre-index pages by frequent topical keywords, domain, or precomputed embedding clusters. Candidate generation retrieves a small set of plausible pages and then the classifier scores them. This is essentially an inverted-index retrieval stage followed by classification, reducing the number of full-document evaluations.

Handling updates and model rollout. Models change — new seeds, new negative mining, and new labels. Use rolling updates, A/B testing, and shadow runs to measure production behavior before switching thresholds. For continuous streams (news, social media), perform periodic re-indexing or incremental scoring; for the static web, re-score new or changed pages only.

Monitoring and scale-aware thresholds. At web scale, even small changes in precision can produce large absolute differences in number of outputs. Monitor both relative metrics (precision, recall) and absolute volumes (items per hour/day). Implement circuit-breakers (e.g., if selected pages exceed a safety budget, raise the threshold) and backpressure mechanisms for downstream consumers.

Fault-tolerance and robustness. Failures in prediction should not halt the crawl pipeline. Make the predictor stateless and idempotent where possible and provide graceful degradation (e.g., fallback to keyword filter) if the model fails to load.

# Ranking, thresholding and selecting top-k results

Once you have classifier scores for a large set of candidate pages, the final step is to produce a ranked and sized output set that meets your application goals: maybe a daily top-100 list, or all pages above a precision target.

Sorting and top-k selection. The simplest approach is to sort all items by score and take the top $k$. However, sorting billions of scores is expensive in time and memory. Practical approaches:

- Partial top-k algorithms: use a min-heap (priority queue) of size $k$ per worker. As you stream scores, maintain the heap; this is $O(n \log k)$ time and constant memory $O(k)$ per worker. For distributed shards, each worker returns its local top-$k$, and a final merge step combines them to produce the global top-$k$.

- Sampling + reranking: sample a subset for scoring and only fully score candidates that pass a coarse filter.

- Approximate nearest neighbors or locality-sensitive hashing (when candidate scores derive from dot-products between query and page embeddings) can retrieve approximate top-k faster.

Thresholding for recall vs budget. If you need to limit outputs to a budget (e.g., at most $B$ pages/day), you can set a score threshold so that expected volume equals the budget. Using a validation set and score distribution estimates, choose threshold $\tau$ such that:
\[
\mathbb{E}[\#\{\text{selected items}\}] = \sum_{i} \Pr(s_i \ge \tau) \approx B.
\]
This requires monitoring to ensure distribution drift between validation and production doesn’t cause over- or under-generation. If the distribution shifts, use adaptive thresholds that adjust based on recent throughput.

Per-class thresholds and class priors. For multiclass or multilabel tasks, different classes can have different score distributions and different desired precision/recall tradeoffs. Use per-class thresholds chosen on validation to meet class-specific precision or recall requirements. When selecting top-$k$ across classes, you may want to downsample from very common classes to ensure coverage across classes.

Calibration and reranking. If the downstream consumer expects probabilities or calibrated scores, apply calibration techniques to the classifier outputs before thresholding. Often the best final ordering is produced by a more expensive reranker that uses richer features (page structure, link graph, freshness, metadata). The shallow classifier’s role is to produce a set of candidates; the reranker provides the final ordering based on more precise features. This two-stage approach combines high recall from the lightweight model with high precision from the reranker.

Diversity and deduplication. For many retrieval tasks you want diversity across sources or subtopics. Simple score-based selection tends to clump: many top items may be near-duplicates or from the same domain. Incorporate deduplication and diversity constraints into the selection process: remove near-duplicates using shingling or embedding similarity, and apply heuristics or constrained optimization (e.g., reserve quotas per domain) to ensure a diverse top-$k$.

Evaluation of ranked outputs. Use precision@k, recall@k, mean average precision (MAP), and NDCG to assess ranked outputs. For pipelines that will be run periodically, track longitudinal metrics to detect degradation. If you care about absolute counts (e.g., how many unique events were covered), measure coverage and redundancy (how many different pages discuss the same event) as separate metrics.

Putting it together: a typical retrieval flow. A common architecture is a three-stage pipeline. First, a cheap syntactic filter (keywords, URL patterns, domain blocks) reduces the full web to a modest candidate set. Second, a fastText-style classifier scores candidates and filters them to a larger-but-still-manageable set chosen by threshold or top-$k$. Third, an expensive reranker (or human review) produces the final high-precision set. Iterative hard-negative mining and per-class thresholding are used during training to tune the middle stage to the desired balance of recall and noise.

Conclusion

fastText-style classifiers combine simplicity, speed, and competitive accuracy for topical classification and retrieval at scale. Their shallow embedding architecture, augmented with n-gram features and hashing, captures enough textual signal for many domain filtering tasks while remaining cheap to train and run. Making these models work at web scale requires attention to precision-recall tradeoffs, realistic evaluation metrics, smart use of seeds and hard-negative mining, and systems techniques for compact models and parallel inference. When used as the candidate generator in a cascade, they are an indispensable tool for engineers and researchers building domain-specific corpora and large-scale retrieval systems.
