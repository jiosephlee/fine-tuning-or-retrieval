Introduction

Constructing large-scale text corpora from web sources is foundational for modern natural language processing (NLP) and language model training. Web-scale corpora provide the raw diversity and volume required for robust language models, but the web is noisy, redundant, and filled with content that can harm model quality or violate evaluation assumptions. This chapter explains practical techniques for extracting, organizing, cleaning, and validating web-derived text at scale. We will describe how to access major web dumps like Common Crawl, how to remove exact and near-duplicates, how to group and reason about domains, how to iteratively build corpora from seeds, and how to avoid contaminating evaluation benchmarks. We also cover language identification, multilingual handling, metrics for data quality, and the role of human-in-the-loop processes. Throughout, the aim is to give you both conceptual intuition and practical methods you could apply in research or production.

# Common Crawl: structure, formats (WARC/HTML) and practical access

Common Crawl is a widely used public web archive that offers monthly crawls of a large portion of the open web. It is distributed as a set of WARC (Web ARChive) files and auxiliary formats. Understanding the structure of Common Crawl and the formats it uses is the first step to building web-scale corpora.

A WARC file is a container format that stores HTTP request and response records as a sequence of records. Each WARC record includes metadata (headers) and a payload, which for a successful fetch is the HTTP response body (often HTML). Typical WARC records of interest are response records containing an HTML page, but there are also request records, metadata records, and revisit records (which indicate that a URL was not re-fetched because the content is identical to a previously fetched resource). Alongside WARC files, Common Crawl usually provides WET files (WARC Extracted Text) and WAT files (WARC Metadata). WET is particularly convenient for text extraction because it contains plain extracted text with minimal markup, but WET can lose structural information present in the HTML (sections, links, tags). WAT contains JSON-like metadata such as extracted links, content-type, and HTTP headers; it is useful for filtering by MIME type or for link graphs.

Common Crawl's files are hosted on public cloud storage (e.g., AWS S3 with open access) and are indexed by a CDX-like index. Practically, you can access Common Crawl by (1) downloading WARC/WET/WAT files directly from the CC bucket, (2) streaming records via AWS S3 APIs, or (3) using third-party tools and wrappers (e.g., the Common Crawl Python library, scrapy-based pipelines). For efficient large-scale processing it is common to run distributed jobs (Spark, Dask, Cloud Dataflow) that iterate over a set of WARC files, apply extraction and filtering logic, and write out cleaned text shards. The CDX index helps locate which WARC contains a particular URL or timestamp. When working with Common Crawl, keep in mind the large size: a single monthly crawl may be many terabytes compressed. Using cloud-side processing (co-locating compute with cloud storage) is often much faster and cheaper than downloading files locally.

Important practical concerns include: handling compressed WARC blocks (usually gzip and sometimes brotli), dealing with non-HTML payloads (images, PDFs, binary files), and respecting robots.txt (Common Crawl already respects robots during crawling, but downstream filtering may still want to exclude certain content types). Also be aware of WARC revisit records which indicate duplicate fetches; handling revisit records properly can reduce redundant processing.

# Deduplication and near-deduplication (URL-based, fingerprinting, shingling)

Deduplication eliminates repeated content that would otherwise bias language models and waste storage and compute. There are multiple levels of deduplication: URL-based filtering, exact-byte fingerprinting, and near-duplicate detection using shingling and locality-sensitive hashing. Each serves a different purpose and has different computational costs and tradeoffs.

URL-based deduplication is the simplest. Many crawlers revisit the same URL or serve identical content under multiple URLs (including tracking parameters, session IDs). Canonicalization heuristics help: normalize the scheme to lowercase, remove default ports (":80" for HTTP), remove or canonicalize query parameters (blacklist analytics parameters like "utm_*"), and apply the Public Suffix List (PSL) or domain heuristics (see next section) to group hostnames. Basic canonicalization reduces immediate redundancy, but it does not detect cases where different URLs host the same content (mirror sites, content served with different query strings, or saved copies on other sites).

Exact or near-exact fingerprinting is next. The simplest fingerprint is a cryptographic hash (e.g., SHA-1, SHA-256) of the full text or normalized text. If two documents have identical normalized text, their hashes will match and you can drop one. Normalization steps often include lowercasing, whitespace collapsing, removing HTML tags, and ignoring certain boilerplate sections like navigation or footers if possible. However, exact hashing misses near-duplicates that are largely the same but have small differences (e.g., different dates, short header/footer variations, or additional tracking snippets).

For near-duplicate detection, shingling is the classical method. A k-shingle (or k-gram) is a contiguous sequence of k tokens (words or characters). For a document \(D\), compute the set of shingles \(S(D)\). Two documents have high overlap if their shingle sets are similar. The Jaccard similarity is a common measure:

Jaccard(D_1, D_2) = \frac{|S(D_1) \cap S(D_2)|}{|S(D_1) \cup S(D_2)|}.

Computing exact Jaccard for all pairs is infeasible at web scale, so we use sketching: MinHash and locality-sensitive hashing (LSH). MinHash builds a compact signature of \(m\) integers such that the probability two signatures match at a given coordinate is equal to the Jaccard similarity. In practice you compute a MinHash signature vector of length \(m\) per document, and then use LSH to bucket documents with similar signatures. SimHash is another approach suited to cosine similarity on high-dimensional frequency vectors; it produces a single compact fingerprint (usually 64 bits) where Hamming distance approximates similarity. SimHash is fast and memory-efficient and has been used in large web deduplication systems (e.g., Google and others).

Choice of shingle size \(k\) and signature length \(m\) affects sensitivity. Smaller \(k\) (like 3-character shingles) can detect small overlaps and is sensitive to minor edits; larger \(k\) (like 10-word shingles) focuses on larger textual similarity. Typical token-based shingle sizes are \(k=5\) to \(k=10\) (words) for near-duplicate detection of paragraphs and documents. For MinHash, lengths \(m=128\) or \(m=256\) offer a practical tradeoff between accuracy and storage.

In production, deduplication is typically multi-stage: canonicalize URLs and filter by domain rules, remove exact duplicates with cryptographic hashes of normalized text, and then run approximate near-duplicate detection with MinHash/LSH or SimHash. Use streaming/partitioned implementations to scale: compute signatures in a Map step, group by LSH buckets in a shuffle, and then within each bucket compute pairwise comparisons to confirm and delete duplicates.

# Domain-based grouping and heuristics for domain identification

Grouping by domain is a powerful organizational step when building corpora. Domains often indicate source characteristics (news site, forum, social media) and content quality. However, identifying and grouping domains correctly requires more nuance than simply taking the hostname.

Start by parsing hostnames using the Public Suffix List (PSL). The PSL allows you to split hostnames into the registrable domain ("example.com") and subdomain components ("news.example.com"). For many tasks you want to group at the registrable domain level: treat all "example.com" subdomains the same. But there are important exceptions: multi-tenant sites (e.g., "user.github.io", "blogspot.com" subdomains) often host distinct user content and should sometimes be treated individually or excluded depending on policy. The PSL helps detect "co.uk" vs "com" nuances and avoids grouping "example.co.uk" incorrectly.

Heuristics for treating subdomains differently include size, signaling, and trust metrics. For example, very large hostnames with thousands or millions of pages under distinct subdomains (e.g., "subdomain.user.example.com") could be user-generated content platforms and often have variable quality. Recognize well-known content hosts (GitHub, StackOverflow, Medium) and treat them with tailored filters: either include (if you want the high-quality programming text) or exclude (if they are near-evaluation data or noisy HTML).

Another group of heuristics concerns paywalled or low-content domains: domain-level detection of content length distribution, median document size, and link density can signal thin pages or aggregators (e.g., link directories, auto-generated content). You can compute per-domain statistics such as average tokens per document, proportion of duplicate content, and language distribution. Domains with consistently very short documents or extremely high duplication are often better excluded.

Reputation and age are additional useful signals. Domain age (from WHOIS or historical crawls) and external backlink counts can indicate established sources. Conversely, newly registered domains or domains that appear only in a single crawl with churn may be ephemeral low-quality scraping farms. You can also use MIME type distributions and URL patterns to label domains (e.g., presence of RSS feeds, typical blog paths like "/category/", or e-commerce patterns like "/product/").

Finally, maintain allow-lists and blocklists of domains that are important for policy (e.g., block illegal content or exclude common test/benchmark sites to prevent contamination). Domain grouping plus per-domain heuristics lets you apply selective sampling: cap the number of documents per domain to avoid over-representation (for example, cap to \(N\) documents per domain per crawl), or apply stratified sampling to ensure desirable domain diversity.

# Seed corpora and iterative data mining pipelines

Building a high-quality corpus is often an iterative process starting from a seed set of domains or documents. A seed corpus can be a curated collection of high-quality sites (newsrooms, academic journals, curated blogs) or a small set of target documents for a particular domain (medical texts, legal decisions). From seeds you can expand retrieval using link-following, focused crawling, or information retrieval techniques.

A simple iterative pipeline: start with a seed list of URLs. Crawl outward by following links from those pages (depth-limited), collecting candidate pages. Score each candidate using heuristics (similarity to seed texts using TF-IDF or semantic embeddings, domain heuristics, language ID, content-length thresholds). Accept pages above a threshold and add their outgoing links to the crawl frontier. Repeat until convergence or until quota limits are reached. This focused crawling approach biases collection toward relevant content while keeping noise down.

Another approach uses IR-style retrieval: index web extracts or a snapshot and run queries derived from the seed corpus. For example, extract frequent n-grams or topics from the seeds, and retrieve web pages with high BM25 or embedding similarity scores. This is effective when you have a large snapshot (Common Crawl) and want to extract subcorpora matching a topic or register.

Iterative mining also helps with filtering: initial runs produce candidate corpora, which you deduplicate, profile (compute language and quality metrics), and then adjust heuristics or thresholds. For example, if you see too much boilerplate from a CMS, add rules to strip that CMS's navigation. If you find many near-duplicate mirrors, tighten MinHash thresholds or add canonicalization rules. Iteration allows you to converge on a balance between recall (getting a lot of relevant pages) and precision (excluding irrelevant or harmful pages).

When running iterative pipelines at web scale, design for idempotency, checkpointing, and reproducibility. Maintain provenance metadata (crawl timestamp, source WARC filename/offset, domain) so you can reproduce or retract items. Use quotas and caps (per-domain and per-host) to prevent "rich get richer" effects where a few domains dominate the corpus.

# Benchmark contamination: n-gram matching, exact substring filtering and thresholds

A critical concern when building corpora for training language models is preventing benchmark contamination — i.e., ensuring that text from evaluation benchmarks does not appear in training data. If a model sees evaluation examples during training it will perform artificially well on those benchmarks and mislead assessment of generalization. Preventing contamination requires careful filtering that balances removing benchmark content with preserving legitimate adjacent content.

The simplest contamination check is exact substring matching. For each benchmark example (or the benchmark's corpus), you can search your candidate training corpus for exact matches of strings longer than a threshold length. A naive strategy is to reject any document that contains any exact match of an entire benchmark example (for instance, exact match of a passage). However, benchmarks vary widely: some benchmarks are short (single-sentence prompts) and can appear widely in the web; others are long and specific (full articles). Exact matching alone is insufficient when near-copies or paraphrases are present.

N-gram matching is a widely used practical technique. For each candidate training document and each benchmark, compute overlapping n-grams (contiguous sequences of \(n\) tokens). If a document shares more than \(t\) n-grams of length \(n\) with any benchmark example, mark it as contaminated. Typical choices are \(n=13\) tokens for strict exactness (commonly cited in previous work), or smaller values like \(n=5\) for more conservative filtering. The threshold \(t\) can be set to 1 (any \(n\)-gram match triggers exclusion) or higher. Using larger \(n\) reduces false positives (common phrases are less likely to match) but increases false negatives (short matches may still indicate contamination). Counting unique n-grams versus occurrences can improve robustness.

To formalize, let \(B\) be the set of benchmark texts, and for an integer \(n\) define for any text \(T\) the set of n-grams \(G_n(T)\). For a document \(D\), compute

overlap(D, B) = \max_{b \in B} \frac{|G_n(D) \cap G_n(b)|}{|G_n(b)|}.

You can declare \(D\) contaminated if overlap exceeds a threshold \(\tau\) (e.g., \(\tau = 0.5\)). Alternatively, simpler absolute thresholds (at least \(t\) matching \(n\)-grams) are common.

Exact substring filtering can be implemented efficiently with inverted indexes (index n-grams from the training corpus and query with benchmark n-grams), or with Bloom filters for approximate detection when resources are constrained. For very large corpora, hashing n-grams and using MinHash-like signatures can accelerate detection with low memory overhead, but beware of false positives from hash collisions.

There are trade-offs: aggressive filtering (small \(n\) and low \(\tau\)) reduces contamination risk but may remove a lot of legitimate data and bias the training distribution. Conservative filtering may leave contamination. Best practice is to (1) identify core benchmarks that are high-risk, and filter thoroughly for those; (2) maintain logs of excluded documents for audit; and (3) when in doubt, remove borderline documents or adjust training/evaluation splits to ensure no overlap. Some organizations maintain explicit allow-lists for content known to be okay and blocklists for common sources of benchmark leakage (e.g., GitHub code with readme files that are used in code-eval benchmarks).

Note that paraphrases and near-copies are harder to detect. Using fingerprinting on lowercased, whitespace-normalized texts can catch small variations; shingling with small \(k\) and MinHash can detect more approximate matches. Semantic similarity measures (embedding-based retrieval) can identify paraphrases but are computationally expensive and risk false positives (similar but not identical content). Consider layered approaches: exact/exact n-gram filtering first, then targeted embedding checks for high-value benchmarks.

# Language identification, multilingual corpora handling

Language identification (langid) is the gatekeeper for putting text into the correct language buckets. For multilingual corpora you must detect language reliably at scale, filter mixed-language documents, and decide policies for multilingual mixed-content pages.

Modern langid models are fast and accurate when the text is reasonably long (hundreds of characters). Popular tools include fastText language identification models, Google's CLD3, and langdetect. For short texts (less than 50 characters) accuracy degrades, so many pipelines require minimum character or token lengths for automatic labels. A common approach is to compute per-document language probabilities and require a minimum confidence threshold (e.g., 0.9) to assign the language. For documents failing the threshold, mark as "unknown" or perform additional heuristics.

Special situations demand attention. Web pages often contain code snippets, lists of product names, or multilingual navigational elements that confuse langid models. Pre-filtering steps like removing code blocks, tables, or boilerplate metadata can improve accuracy. For pages with substantial content in more than one language (for example, bilingual articles), you may split into segments and process each separately. Language segmentation can be done by sliding-window langid, where you run langid on overlapping windows to identify language switches. If a page has a dominant language proportion exceeding a threshold (e.g., 80% of windows), label the page as that language; otherwise, split or discard.

For building multilingual corpora, decide whether you want monolingual buckets (one language per document) or to allow multilingual documents. Monolingual training often improves model quality for individual languages; multilingual corpora support cross-lingual transfer but require more careful balancing. When assembling multilingual corpora, track per-language quotas to avoid over-representation of resource-rich languages like English. Sampling strategies include temperature-scaling of language frequencies or fixed caps per language.

Be aware of script vs language confusions: languages sharing scripts (e.g., English and many Western European languages) can be misclassified for short texts; languages with unique scripts (e.g., Devanagari, Cyrillic) are easier to separate. Also consider transliterated content (e.g., Arabic written in Latin letters) which can be mis-detected. Creating language-specific tokenizers or normalization pipelines can help downstream tasks.

Finally, for low-resource languages, web data can be extremely noisy. Consider additional quality checks (domain heuristics, higher confidence thresholds, manual verification) before including such text in training sets.

# Data quality metrics and human-in-the-loop refinement

Measuring data quality is crucial: you want objective metrics to guide filtering and resources for targeted human review. Quality metrics fall into several categories: statistical metrics, linguistic metrics, provenance metrics, and downstream performance metrics.

Statistical metrics include document length distributions (tokens, characters), vocabulary size, entropy estimates, and token frequency tails. Extremely short documents or documents with unusually repetitive tokens often indicate boilerplate or spam. Compute per-domain and global statistics and visualize them to spot outliers.

Linguistic metrics include perplexity under language models, POS tag distributions, and presence of non-linguistic content (lots of punctuation, emojis, or code). For a candidate language \(L\), you can measure how well a pretrained language model for \(L\) fits the text. High perplexity suggests off-domain or noisy content. Character-level statistics (ratio of letters to digits, proportion of non-ASCII) also indicate quality or language mismatch.

Provenance metrics cover domain age, crawl frequency, and duplication rates. Domains with high duplication or very low content diversity are lower value. Tracking the fraction of documents from top-k domains reveals concentration bias; a few domains dominating the corpus suggests the need for capping.

Downstream performance metrics are the ultimate test: does adding or removing a subset of the corpus improve validation performance on held-out tasks? Use small controlled experiments where you train models with and without suspect data and measure changes on validation sets. Ablation studies reveal whether particular domains or document types are helpful or harmful.

Human-in-the-loop refinement operationalizes these metrics. Use automatic scorers to rank candidate documents by suspicion (low language confidence, high repetitive token fraction, high n-gram overlap with benchmarks, etc.). Present top suspicious documents to annotators in batches. Annotators can label reasons (spam, boilerplate, copyrighted text, policy-violating content). Use these labels to train classifiers that generalize the human decisions to the whole corpus. Active learning helps: pick documents where the classifier is uncertain to ask humans, thereby improving the model with fewer annotations.

Maintain clear annotation guidelines to ensure consistency: define what counts as "useful prose" versus "list of links", how to handle code and tables, and how to treat copyrighted or sensitive content. Keep annotator interface simple but include provenance metadata (URL, domain, snippet, language) so reviewers can judge context.

Finally, periodically re-run human-in-the-loop cycles as the web changes and new domains appear. Combining automated scoring with targeted human review scales well: automatic filters handle the bulk, and humans refine edge cases and help retrain the automated models.

# Putting it together: a sample end-to-end pipeline and practical tips

An end-to-end web-corpus pipeline typically follows these stages: ingestion, extraction, canonicalization, language ID, deduplication, quality filtering, contamination filtering, sampling/stratification, and storage with provenance. Concretely, one might:

1. Ingest WARC files from Common Crawl.
2. Extract raw HTML and produce text using robust parsers; optionally produce WET for text-only processing.
3. Canonicalize URLs and compute per-document metadata (domain, path, content length).
4. Run language ID with confidence thresholds and split multilingual documents as needed.
5. Normalize text (lowercasing optional, whitespace normalization, remove boilerplate) and compute an exact hash for exact dedupe.
6. Compute shingles and MinHash/SimHash signatures and perform near-duplicate grouping; remove or collapse duplicates according to policy.
7. Run benchmark contamination filters: n-gram/substring matching against benchmark corpora; remove matching docs using well-chosen \(n\) and thresholds.
8. Compute quality scores (perplexity, character statistics, domain heuristics) and filter or downweight low-quality documents.
9. Sample documents to create balanced datasets across languages and domains, capping per-domain contributions.
10. Store final corpus shards with rich provenance metadata and maintain logs of excluded material for audits.

Practical tips: stream processing is your friend—avoid loading entire warc files into memory. Use hashed counters and sketch structures (Count-Min Sketch, HyperLogLog) to compute high-level metrics efficiently. Keep reproducibility in mind: store versions of seed lists, regular expressions, and thresholds. Automate checks for benchmark contamination whenever new benchmark suites are added or when you update training data. And document everything: transformations, filters, and the provenance pipeline are essential for auditability, compliance, and scientific reproducibility.

Summary

Building web-scale corpora is a balance of scale, accuracy, and caution. Tools like Common Crawl provide accessible raw material, but deduplication, domain heuristics, iterative mining, and careful contamination prevention are necessary to produce useful training datasets. Language identification and multilingual handling ensure proper language-specific processing, while data quality metrics and human-in-the-loop refinement keep the pipeline adaptive and robust. By combining automated scalable algorithms (hashing, MinHash, LSH, langid) with principled heuristics (PSL-based domain grouping, per-domain caps) and targeted human oversight, you can construct corpora that support credible research and production-grade language models.
