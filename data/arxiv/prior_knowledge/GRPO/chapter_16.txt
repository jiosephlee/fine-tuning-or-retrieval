# Introduction

Training large language models (LLMs) at scale involves more than just choosing a loss function and an optimizer. Practical engineering choices—including how you partition work across devices, how you manage memory, how you batch long sequences, and how you organize experiments and evaluations—determine whether a project is feasible, how fast it runs, and how reliable the results are. This chapter examines these infrastructure and efficiency considerations in depth. It is written for students who have the theoretical background in deep learning and want to understand the engineering tradeoffs and techniques used in modern large-scale training pipelines, including reinforcement learning (RL) components such as actor/critic or value networks.

Throughout the chapter, we use concrete intuitions and simple formulas to explain how costs scale, and we describe practical patterns and pitfalls that appear in real systems. We also cover reproducibility and large-scale evaluation, which are essential for scientific rigor and for safely deploying models.

# Model and data parallelism strategies (tensor, pipeline, sequence)

When your model grows beyond the memory or compute capacity of a single accelerator, you must partition the work across devices. The main dimensions of parallelism used in LLM training are data parallelism, tensor (operator) parallelism, pipeline parallelism, and sequence (or activation) parallelism. Each has different tradeoffs in communication, memory, and ease of implementation.

Data parallelism is the simplest: each device (or worker) holds a complete replica of the model parameters and processes a different minibatch of data. Gradients are aggregated (commonly with all-reduce) and parameters are updated synchronously or asynchronously. Data parallelism scales computation linearly with the number of replicas, but requires memory for a full parameter replica on each worker. The principal communication cost is the gradient reduction each update step. If the model parameters are size $P$ (in bytes), then each optimizer step typically communicates $O(P)$ across devices.

Tensor (operator) parallelism splits the tensors that represent parameters and activations within individual layers across devices. For example, in a fully connected layer with weight matrix $W \in \mathbb{R}^{d_{out}\times d_{in}}$, you can partition $W$ horizontally or vertically so that different devices hold disjoint slices. This reduces the memory per device for parameters and enables training of larger models without replicating the full parameter set. However, tensor parallelism requires fine-grained synchronous communication during forward and backward passes because activations and gradients must be exchanged across the partition boundaries. The communication volume per operator is proportional to activation or gradient slice sizes, and latency sensitive operations can reduce efficiency if the network interconnect is not fast.

Pipeline parallelism partitions the model across stages: each stage contains a contiguous set of layers and is placed on one or more devices. Inputs are microbatched and streamed through the staged pipeline: while stage 1 is processing microbatch 3, stage 2 can process microbatch 2, and stage 3 microbatch 1, etc. Pipeline parallelism reduces parameter memory per device and achieves overlap between computation and communication, but introduces pipeline "bubbles" (startup and drain phases) that reduce utilization. The effective throughput depends on the number of microbatches and the balance of stage compute times. One insightful formula for pipeline efficiency is that with $S$ stages and $M$ microbatches, the idealized utilization fraction is approximately $1 - \frac{S-1}{M}$; so you need $M \gg S$ to approach full utilization.

Sequence (activation) parallelism, sometimes called sequence or token parallelism, splits the sequence length dimension of activations across devices. Consider a transformer that processes sequence length $L$ and batch size $B$, producing activations of size $B\times L\times d_{model}$. If $L$ is large (e.g., 32k tokens), splitting $L$ among devices reduces activation memory and per-device compute. Sequence parallelism is particularly useful with attention layers since self-attention operates across tokens. Efficient sequence parallelism often relies on careful communication patterns to compute attention across partition boundaries and may use streamed or blocked attention to reduce global communication.

In practice, modern LLM training uses hybrid approaches. For instance, one may combine tensor parallelism (to shard large matrices), pipeline parallelism (to stage many layers), and data parallelism (for overall scaling). Frameworks such as DeepSpeed (ZeRO and pipeline), FairScale, and PyTorch FullyShardedDataParallel (FSDP) provide building blocks for these hybrids. Choosing the right mix depends on the model size $P$, per-device memory, network bandwidth, and the target throughput.

# Memory footprint of actor/critic/value models and cost tradeoffs

In RL fine-tuning of LLMs—such as reinforcement learning from human feedback (RLHF)—you often add auxiliary networks like value or critic models, or you run actor models to generate trajectories and compute rewards. These additions affect the memory footprint and cost behavior in several ways.

First, the parameter sizes of actor, critic, and value models contribute to total parameter storage and optimizer state. If you maintain separate networks for policy (actor) and value, total parameter memory is roughly $P_{actor}+P_{value}$. Often, practitioners share backbone weights and attach small heads for value or reward modeling to reduce overhead. Sharing reduces memory and synchronizes representations, but can complicate gradient flows and training stability.

Second, RL workflows require storing activations and intermediate values for trajectories during backpropagation through time or for policy gradient estimators. For a sequence length $L$, batch size $B$, and model hidden dimension $d$, the activation memory scales approximately as
\[
M_{act} \approx B \times L \times d \times s,
\]
where $s$ is the bytes per element (e.g., 2 for float16). This can be large when $L$ is long (dialogues, rollouts) or when you accumulate multiple timesteps for temporal credit assignment. Actor-critic algorithms often need value targets stored and may compute generalized advantage estimation (GAE) with time dependencies, which further increases memory pressure.

Third, optimizers and state (e.g., Adam) add multiplicative memory overhead. Adam keeps first and second moment estimates, so optimizer state memory can be roughly $2\times P$ (for the moments) plus $P$ for parameters. Techniques such as optimizer state sharding (ZeRO stage 1/2), parameter sharding (ZeRO stage 3), or single-precision vs mixed-precision storage can make a large difference. For example, ZeRO stage 3 shards parameters, gradients, and optimizer states across data-parallel ranks, reducing per-device memory for a model of size $P$ by a factor roughly equal to the number of data-parallel processes.

Cost tradeoffs include compute vs memory vs communication. If you keep separate actor and critic without sharing, you double parameter storage and computation; if you share, you reduce memory but must weigh the impact on policy performance. Activation checkpointing (recompute) can save activation memory at the cost of extra compute; this is often acceptable when activations dominate memory but compute is abundant. Similarly, mixed precision reduces memory and increases throughput, but can require careful loss scaling and maintenance of master parameters in full precision to preserve numerical stability.

Finally, RL data generation (rollouts) can dominate runtime: generating trajectories by running the actor model in inference mode may be far faster or slower than gradient updates depending on batch sizes and sampling strategies. Consider whether to generate on-accelerator (fast, but uses GPU memory) or offload to CPU/gRPC workers to decouple generation from training. Each choice changes hardware utilization and monetary cost.

# Efficient training frameworks and throughput optimizations

To achieve high throughput, you must optimize both computation and communication. Several software frameworks and algorithmic techniques help.

Frameworks: DeepSpeed, FairScale, and PyTorch FSDP provide sharded optimizers, activation checkpointing, pipeline utilities, and mixed precision support. NVIDIA's Megatron-LM implements tensor parallelism and pipeline parallelism with optimized kernels. These frameworks integrate optimized kernels for fused matrix multiplications, layer norm, and attention. They often rely on NCCL for collective communication and exploit high-performance interconnects (NVLink, InfiniBand).

Throughput optimizations include mixed precision (FP16/bfloat16), kernel fusion, and operator-level autotuning. Mixed precision halves memory bandwidth for activations and can double throughput on hardware with FP16 Tensor Cores, given careful loss scaling and master (FP32) weights. Kernel fusion reduces launch overhead and memory traffic by combining consecutive elementwise or small matrix operations into single kernels.

Gradient accumulation is critical when per-device memory limits the batch size. Accumulate gradients across microbatches to reach an effective global batch size $B_{eff} = B_{micro} \times N_{accum} \times N_{replicas}$. This allows maintaining a desired learning rate schedule and optimizer behavior while avoiding small per-device batch inefficiencies. However, gradient accumulation increases the staleness of optimizer states and may complicate synchronization for sharded optimizers.

Communication optimizations include overlapping communication with computation, using asynchronous collectives, and compressing communicated tensors. For example, with tensor parallelism you can arrange compute so that while a device computes its local matmul, gradients from previous layers are being all-reduced. Overlap effectiveness depends on the network topology and the ability to reorder operations. Communication compression (quantization or sparsification) can reduce volume but must preserve numerical fidelity; it is more common in inference or in very large-scale synchronous SGD with tolerant algorithms.

Memory optimization techniques include activation checkpointing (recomputation), which trades compute for memory by storing only a subset of activations and recomputing intermediate activations during backward pass. A common pattern is to checkpoint at transformer block boundaries so that only the inputs to some blocks are stored, and the internal activations are recomputed. Checkpointing reduces peak memory to roughly
\[
M_{peak} \approx \frac{M_{act}}{k} + M_{params} + M_{optim},
\]
where $k$ is the number of checkpoint segments (larger $k$ means more recomputation). Partitioning optimizer state across devices (ZeRO) prevents any single device from holding the full optimizer states. Combining these techniques properly is a primary way to train very large models on finite hardware budgets.

# Context window sizing and batching with long contexts

The context window length $L$ is a major driver of memory and compute. Transformer self-attention has $O(L^2)$ compute and memory in the naive implementation, so doubling $L$ can quadruple cost. Thus choosing $L$ and batching strategies is a fundamental tradeoff between model capability and efficiency.

When $L$ is modest, the standard approach is to pack multiple sequences per batch to fill the GPU memory and utilize compute. But as $L$ grows (e.g., 4k, 8k, 32k tokens), naive batching quickly becomes infeasible. Several techniques are used to manage this:

Sequence packing: Pack shorter sequences into the same batch tensor so that wasted padding is minimized. Packing requires bookkeeping to restore original sequence boundaries for loss computation, and can complicate attention masks, but it dramatically improves utilization when many sequences are shorter than $L$.

Sliding windows and chunking: For long continuous contexts (documents), process them in overlapping windows. For example, split a 100k-token document into windows of size $L$ with overlap $o$, and feed them as sequential training examples. This preserves locality and reduces memory per step, albeit losing some global attention across windows. Overlaps ensure token context is not abruptly cut off.

Memory-efficient attention: Use approximate attention mechanisms that reduce the asymptotic cost from $O(L^2)$ to $O(L\log L)$ or $O(L)$, such as locality-sensitive hashing (LSH) attention, sparse attention patterns, or linearized attention kernels. These approaches trade exactness for scalability and are beneficial when global exact attention is infeasible. Evaluate their empirical effect carefully, since approximation can impact final performance.

Batching strategies with long contexts include dynamic batching—grouping sequences of similar lengths to minimize padding—and microbatching to feed pipeline stages. For large $L$, using sequence parallelism (token sharding) can distribute the activation memory across devices, enabling larger context windows without approximation. However, this increases inter-device communication for attention.

Another practical consideration is training-sampling distribution: if you frequently train on shorter contexts but want the model to handle long contexts at inference, you may need curriculum or fine-tuning with longer sequences to ensure attention patterns generalize. Also consider inference vs training costs: long contexts can be expensive at inference, so you might use specialized long-context inference kernels or offload parts of the context lookup to CPU memory for retrieval-augmented models.

# Checkpointing, reproducibility and experiment management

Checkpointing and reproducibility are essential for both development and scientific reliability. Checkpoints let you recover from failures and carry out long-running experiments; reproducibility ensures that results can be verified and compared.

A checkpoint should include the model parameters, optimizer state, learning rate scheduler state, random number generator (RNG) states for CPU and GPU, and any training metadata (step number, seed, config). When using mixed-precision training, store the full-precision master weights. For sharded training (e.g., ZeRO stage 3), design checkpoint formats that can be reassembled for inference or resume training on different hardware topologies. Atomic and consistent checkpointing is important: partial or inconsistent checkpoints make resumption difficult. Many frameworks provide coordinated checkpointing APIs that quiesce optimizer operations and write consistent shards to storage.

Reproducibility requires controlling sources of nondeterminism: RNG seeds for weight initialization, data shuffling, dropout, and environment stochasticity (in RL). Use deterministic algorithms where possible. For example, in PyTorch you can set torch.backends.cudnn.deterministic = True, but this may reduce performance because some cuDNN algorithms are nondeterministic yet faster. Document the tradeoff and always log the seed and software/hardware versions (framework versions, CUDA, cuDNN, driver versions).

Experiment management systems (e.g., MLflow, Weights & Biases, Sacred) keep track of hyperparameters, configurations, code commits, and artifacts such as checkpoints and logs. Use version control for configuration files and experiment scripts; embed experiment IDs in logs; and store metadata in a consistent schema. This bookkeeping enables debugging, comparisons across runs, and proper ablation studies. For large collaborative projects, standardize naming conventions and retention policies for checkpoints to control storage costs.

Finally, consider reproducible evaluation. For RL, ensure that environment seeds, action sampling seeds, and reward-model versions are fixed or logged. When resuming training, verify that resuming from a checkpoint yields consistent losses and metrics in early steps; differences often reveal hidden nondeterminism or missing state saves.

# Evaluation at scale and logging of RL metrics

Measuring progress reliably in large-scale training—and particularly in RL—requires robust evaluation pipelines and careful logging. RL introduces additional complexities: stochastic rollouts, delayed rewards, reward model drift, and variance in policy gradients.

First, establish a set of offline evaluation datasets and metrics for supervised tasks and for reward models. For RL, define evaluation episodes or standardized prompts and seed them to ensure comparability between checkpoints. Evaluate across multiple seeds for each checkpoint to estimate variance; report mean and confidence intervals. When budgets are limited, use a nested strategy: frequent lightweight evaluations (short episodes or fewer seeds) for quick feedback, and periodic heavy evaluations (many seeds, long episodes) for rigorous assessment.

Track both optimization metrics (training loss, policy gradient estimates, KL divergence between policy and reference, value loss) and downstream performance metrics (task-specific scores, human preference rates, safety metrics). RLHF workflows typically log: policy loss, value loss, reward model loss, average reward per rollout, KL penalty or constraint values, and episode lengths. Use consistent sampling temperature and decoding strategy during evaluation to avoid conflating sampling variation with policy quality.

Logging systems should store scalar metrics, histograms, and raw traces of episodes (sampled trajectories, prompts, responses). For RL, saving sampled trajectories is vital for debugging reward hacking, mode collapse, or distributional shifts. Maintain a versioned reward model and log which reward model evaluated which episodes, so that apparent gains are not artifacts of reward-model drift.

Scaling evaluations involve fleet orchestration: generating thousands of rollouts may require many inference workers. Use asynchronous logging pipelines to avoid backpressure on training. Aggregate logs centrally and produce dashboards that visualize key metrics over wall-clock time and number of environment steps. Implement alerting rules for anomalous trends (e.g., sudden drop in reward, explosion in KL). For rigorous comparison, maintain a reproducible "test harness" with fixed seeds and environments that run outside the main training cluster.

Finally, apply statistical rigor. When comparing two policies, compute effect sizes and confidence intervals. Beware of cherry-picking checkpoints; instead report performance over a moving window or averaged over a range of seeds and steps. For RLHF where humans are involved, design evaluation with inter-rater reliability measures and blind tests to reduce bias.

# Conclusion

Efficient large-scale training of LLMs and RL components is the product of careful tradeoffs across parallelism strategies, memory management, communication optimization, batching strategies for long contexts, and well-engineered experiment and evaluation practices. No single technique suffices: modern systems combine tensor, pipeline, and data parallelism; use activation checkpointing and optimizer sharding to fit models into memory; and adopt robust logging and reproducibility practices to ensure scientific validity. Understanding the scaling laws and the concrete cost models (parameters, activations, optimizer states, communication) helps make principled choices about architecture and infrastructure as you move from research prototypes to production-scale models.
