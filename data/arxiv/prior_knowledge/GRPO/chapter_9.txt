Introduction

Large language models (LLMs) have shown remarkable ability to generate fluent text, answer questions, and perform tasks across domains. A critical frontier in using these models effectively is getting them to perform complex, multi-step reasoning rather than giving a single memorized or surface-level answer. This chapter explores three closely related approaches to eliciting stepwise or programmatic reasoning from LLMs: Chain-of-Thought (CoT) prompting, Program-of-Thought (PoT) prompting, and tool-integrated reasoning where models call external interpreters or libraries during generation. We will examine motivations, prompting techniques, how to design templates and solution structures, methods for evaluating the intermediate steps and final answers, sampling strategies like self-consistency, and the practical tradeoffs between verbosity, correctness, and evaluation complexity. The focus is on intuition, reproducible methods, and understanding how these approaches are evaluated in research and applied systems.

# Chain-of-thought (CoT): motivation and few-shot prompting

Chain-of-thought (CoT) refers to eliciting an explicit sequence of intermediate reasoning steps from an LLM rather than asking it to directly provide a final answer. The motivation for CoT is that many reasoning tasks—mathematics, multi-hop question answering, logical puzzles, and planning—are easier for models when they generate an explicit argument or chain of reasoning. Humans solve such problems by breaking them into steps; similarly, providing or inducing stepwise reasoning gives the model a structure to decompose the task, which often yields higher-quality final answers.

CoT can be elicited via prompting in several ways. One widely used way is few-shot prompting with examples that include explicit step-by-step solutions. In a few-shot CoT prompt, the prompt contains several input-output pairs where each output contains both intermediate reasoning steps and a final answer. For example:

"Q: There are 3 red balls and 2 blue balls. If I pick two balls without replacement, what's the probability both are red?
A: First compute the number of ways to pick 2 red balls: choose(3,2)=3. Number of total ways: choose(5,2)=10. So probability = 3/10. Answer: 3/10."

The presence of these worked-out examples primes the model to produce a similar stepwise chain when given a new question. The key idea is that the model learns a latent pattern of "explain intermediate steps, then give the final answer" from the demonstrations. Few-shot CoT is effective particularly with large models (e.g., models with billions of parameters); empirical results show that larger models are more likely to adopt CoT behavior from prompts and that the gains are significant on many reasoning benchmarks.

In addition to few-shot examples, prompts can explicitly instruct the model to "think step by step" or "show your reasoning." While such direct instructions can help, they are usually most effective when paired with a few-shot pattern. The combination of instruction plus demonstration aligns the model both with the task objective and with the desired output structure. However, there are caveats: generating chains-of-thought can increase token usage, may reveal incorrect reasoning that nonetheless leads to a correct answer, and in zero-shot settings simple instructions sometimes cause the model to hallucinate reasoning. Therefore, designing CoT prompts requires care and evaluation (which we will discuss later).

# Program-of-thought (PoT): instructing models to write executable programs

Program-of-thought (PoT) shifts from free-form natural-language chains to having the model produce an explicit program or a sequence of program-like steps that, when executed, perform the reasoning or computation. The idea is that writing code is a precise, structured, and executable form of reasoning. The model's output is not merely an explanation but a program in a language such as Python that computes the answer.

PoT has several advantages. First, programs are executable, which enables deterministic verification: if the model emits a program, we can run it and check whether it yields the expected result. This reduces ambiguity compared to natural-language chains. Second, the structure of code enforces modularity and clarity: variables, control flow, and functions can encapsulate subproblems. Third, code allows the model to leverage existing libraries and numerical precision (floating point arithmetic, big integers, symbolic math) which may be superior to the model's internal approximations.

A simple PoT example for an arithmetic problem might be:

"def solve():
    x = 3
    y = 5
    return x * y
# Answer: 15"

When designing PoT prompts, demonstrations should include programs that follow a consistent structure: parsing input, defining helper functions, performing computations, and printing or returning the final answer. Few-shot PoT prompts show the model examples of both the problem and a short, well-documented program that leads to the solution. Because programming languages have strict syntax, PoT can reduce the variance of possible outputs and make downstream verification easier.

However, PoT also has limits. Writing correct code requires the model to handle details such as edge cases, data types, and library imports. For some tasks the mapping from natural reasoning to efficient, correct code is nontrivial. Moreover, if the model generates syntactically invalid code or uses unavailable libraries, execution will fail. Despite these issues, PoT is powerful, especially when combined with a runtime that can execute and test generated programs, and when used for problems where precise computation is critical.

# Tool-integrated reasoning: invoking interpreters/libraries during generation

Tool-integrated reasoning refers to setups where the LLM is allowed to call external tools—interpreters, calculators, search engines, databases, or domain-specific libraries—during generation. The model either generates tool invocations explicitly (e.g., a call to a Python interpreter) or interfaces via an orchestration layer that executes tools on the model's behalf and returns results as additional context. The key idea is to augment the model's internal reasoning with computation, retrieval, or verified outputs that are difficult to produce reliably from language alone.

There are several interaction patterns. In the simplest synchronous pattern, the model emits a special token sequence like "<python>...</python>", the orchestrator runs the contained code, and the output is appended to the context; then the model continues generation to use the computed result. Another pattern is a conversational tool API where the model produces a structured tool call, e.g., {"tool": "calc", "expr": "12/5"}, and the system returns the result. More advanced systems allow multi-step tool usage, where the model plans a sequence of tool calls, interprets results, and conditionally makes further calls.

Tool integration has major benefits. It provides access to high-precision computation, symbolic manipulators (e.g., sympy), external knowledge (search), or domain-specific solvers (SMT solvers, theorem provers). This enables models to handle tasks they could not solve using only internal weights. It also supports verification: the model can programmatically check intermediate claims, compare different computation strategies, and refine outputs.

However, integrating tools requires careful control flow, error handling, and protocol design. The model must learn to format tool invocations correctly, to interpret tool outputs, and to decide when to call tools. The orchestration layer must manage latency, security, and deterministic replay (for reproducibility). When tools are used interactively, the model's incentives must be aligned: for instance, if a model's objective is to produce plausible-looking text, it might overuse tools or misuse them unless constrained. Nonetheless, tool integration is a powerful way to marry LLM flexibility with the correctness and performance of specialized systems.

# Designing CoT/PoT prompts and solution templates

Good prompt and template design is central to coaxing useful stepwise reasoning from LLMs. Several principles guide design: clarity of structure, consistency across examples, concise yet complete intermediate steps, use of variable names and small subroutines, and alignment between the prompt and the evaluation criteria.

For CoT prompts, examples should display clear intermediate steps that show reasoning granularity appropriate to the task. If steps are too terse, the model might skip crucial logic; if too verbose, the model may introduce unnecessary detail and increase token cost and error surface. A well-designed CoT example includes explicit computations, declarations (e.g., "Let x = ..."), short justifications for each step, and a final clearly labeled answer. Consistency is important: if every example uses "Step 1", "Step 2", etc., or a predictable phrasing like "First..., Next..., Therefore...", the model learns a template that generalizes to new inputs.

For PoT, templates should enforce code structure. Use small helper functions for repeated subroutines, include a deterministic entry point (e.g., a function called "solve" or a "main" block), and demonstrate input parsing and output formatting. Example programs should avoid extraneous libraries unless necessary, and should include comments that link code to reasoning (e.g., "# compute number of ways to choose 2 red balls"). The prompt can instruct the model to produce only valid code in a specified language and to return the final answer in a specified format (for example, final output printed as "ANSWER: <value>"). This reduces ambiguity for the orchestrator and downstream evaluators.

Templates can also incorporate checks and assertions. For PoT, show examples where the code verifies intermediate invariants or runs unit tests. For CoT, include examples where the chain references a small calculated value that is recomputed or checked. Including examples of error handling teaches the model to be robust: for instance, demonstration that the program checks for division by zero or handles integer versus float distinctions.

Finally, consider the cognitive load of your templates. Humans reading the chains will benefit from clear variable naming and modular structure; automated checkers will benefit from standardized final-answer markers. If model size or response length is a concern, use templates that strike a balance between sufficient detail and concision. Iteratively validate prompt designs: run them on held-out problems, analyze failure modes, and refine the templates based on empirical results.

# Evaluating step-by-step solutions vs. final-answer-only scoring

Evaluation of models that produce chains or programs can target either the final answer (does the output match the correct result?) or the chain itself (are the intermediate steps correct and logically coherent?). Each approach has benefits and pitfalls.

Final-answer-only scoring is simple to implement: compare the model's final answer with the ground truth and calculate accuracy. This aligns with many practical goals where only the final outcome matters. However, it ignores the reasoning process and can reward lucky guesses or incorrect chains that, by coincidence, lead to the right answer. Final-answer scoring is also insensitive to partially correct reasoning that could be valuable for interpretability or for building systems that combine human and machine reasoning.

Step-by-step evaluation assesses the correctness and coherence of intermediate steps. This can involve checking each step for factual and logical correctness, verifying intermediate computations, or executing the program that the model produced (in the PoT case) and verifying that it aligns with an intended specification. Evaluating chains provides richer diagnostics: it tells you where the model goes wrong, whether errors are local or systemic, and whether the chain is trustworthy to a human verifier.

The challenge with stepwise evaluation is that it is more labor-intensive and often requires domain-specific checkers. Natural-language steps can be ambiguous, making automatic verification hard. One approach is to convert natural steps into executable checks (e.g., parse arithmetic expressions and evaluate them), but this requires building extraction and parsing mechanisms that generalize. For PoT, evaluating programs is easier: run tests or assert properties. But care must be taken to sandbox execution to avoid security issues.

Hybrid strategies combine both: evaluate the final answer automatically, and sample a subset of chains for manual or automated stepwise evaluation. Another useful practice is to use programmatic checks when possible—e.g., re-run computations, cross-validate with alternative methods, or run unit tests. The choice of evaluation method should reflect the application: in scientific or safety-critical domains, stepwise verification is essential; in casual QA, final-answer accuracy may suffice.

# Self-consistency sampling for CoT

Self-consistency is a sampling strategy designed to improve the reliability of CoT by aggregating multiple sampled reasoning chains. The core idea is to draw several independent reasoning traces from the model (by sampling multiple times with temperature > 0) and then aggregate final answers by majority vote or other consensus rules. The intuition is that although individual reasoning chains can be noisy, correct answers tend to appear more frequently across diverse sampled chains; sampling explores multiple plausible chains and leverages redundancy to amplify correct conclusions.

Formally, let the model define a conditional distribution p(chain, answer | input). Self-consistency samples K chains {c_1, ..., c_K} from this distribution and extracts their respective final answers {a_1, ..., a_K}. The aggregated answer is then chosen as argmax_a count(a), or via weighted voting if confidence scores are available. The approach requires models to be capable of producing diverse but often-correct chains when sampled, and it relies on the hypothesis that the correct answer will be a mode of the conditional distribution.

Self-consistency often substantially boosts accuracy compared to a single greedy CoT sample because it mitigates the effect of any single flawed chain. It is particularly effective when the model sometimes reasons correctly but can be led astray by sampling or surface-level heuristics. Practical considerations include selecting K (tradeoff between computation cost and robustness), choosing sampling temperature (higher temperature increases diversity but may increase noise), and deciding how to break ties (e.g., use confidence scoring or fallback to the model's greedy output).

There are limitations. Self-consistency presumes that the model's distribution places appreciable mass on correct chains; if the model rarely generates correct reasoning, aggregation won't help. Also, sampling more increases cost linearly. Self-consistency also interacts with the evaluation metric: majority voting on final answers ignores distribution of partial correctness across chains and may mask consistent but subtly wrong reasoning. Despite these caveats, self-consistency is an effective and widely used practical technique to make CoT more reliable.

# Tradeoffs: verbosity, correctness, and evaluation complexity

Eliciting stepwise reasoning introduces tradeoffs among verbosity, correctness, and evaluation complexity that must be managed in system design.

Verbosity: Chains and programs are longer than concise final answers. This increases token costs for both input and output, which raises inference latency and monetary cost in API-based deployments. Verbosity also increases cognitive load for human readers and makes automated parsing more challenging. However, verbosity can improve interpretability and allow human reviewers to audit the model's logic. To manage verbosity, design concise templates, limit unnecessary detail, and use programmatic forms (PoT) where concise code can encode complex logic compactly.

Correctness: Richer outputs can improve correctness because the model has intermediate steps to ground computation and because tools can verify execution. But verbosity can also introduce more opportunities for mistakes: more steps means more things that can go wrong. CoT might expose flawed reasoning that accidentally leads to a correct answer, while PoT can fail due to syntactic or runtime errors. Tool integration can improve correctness via verified computations, but relies on correct tool invocation and accurate interpretation of tool outputs. Practitioners should weigh whether the marginal improvement in final-answer correctness justifies the additional complexity and cost.

Evaluation complexity: Evaluating intermediate reasoning is more expensive than checking final answers. Natural-language steps are hard to verify automatically; programs are easier but require sandboxed execution, test cases, and careful specification of expected behavior. When models use external tools, reproducing results requires capturing tool versions and randomness seeds, increasing reproducibility complexity. Evaluation complexity also affects research: rigorous evaluation of CoT and PoT models needs human annotation, automated verification pipelines, or both, which are resource-intensive.

When designing systems, consider the application requirements. For high-stakes tasks (medicine, law, scientific analysis), the extra cost and complexity of stepwise reasoning and verification are often justified by the need for transparency and correctness. For lower-stakes applications (informal Q&A), a single-shot final-answer approach may be adequate. A hybrid approach is common: use CoT/PoT during development and evaluation to improve models, but deploy more concise outputs in production with targeted verification for critical cases.

Conclusion

Chain-of-thought, program-of-thought, and tool-integrated reasoning are complementary techniques for getting LLMs to perform complex reasoning reliably. CoT provides human-readable chains that aid interpretability and guide the model through multi-step problems. PoT leverages the precision and executability of code to reduce ambiguity and enable verification. Tool integration augments the model with computational and retrieval capabilities that are otherwise beyond its internal representation. Designing effective prompts and templates, choosing appropriate evaluation strategies, and applying sampling techniques like self-consistency are all practical levers to enhance performance. Understanding and managing the tradeoffs among verbosity, correctness, and evaluation complexity determines how these methods should be applied in research and in production systems.
