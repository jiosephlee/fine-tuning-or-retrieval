Introduction

Representing local context efficiently is a central challenge in many natural language processing and machine learning applications. When processing raw text, bytes, or characters, one common approach is to extract n-gram features: contiguous sequences of tokens (where tokens can be bytes, characters, or words). N-grams capture local structure and provide useful signals for tasks such as language modeling, classification, and retrieval. However, storing explicit vectors for every possible n-gram becomes infeasible as the vocabulary or alphabet grows. To address this, practitioners use compact parameterizations such as hashing-based representations and sparse embeddings. This chapter develops the theory and practice of n-gram construction over bytes and characters, explains rolling polynomial hashes (RollPolyHash) and how to implement them efficiently, explores hash embedding tables and methods to handle collisions, compares frequency-based representations to hashed n-gram representations, and finally discusses normalization and how to integrate these sparse features with learned dense embeddings. The presentation emphasizes intuition, algorithmic detail, and practical considerations so you can both implement these techniques and read research papers that use them.

# n-gram construction over bytes/characters

An n-gram is a contiguous subsequence of length $n$ extracted from a sequence. When the sequence is over characters or bytes, n-grams capture short local patterns such as prefixes, suffixes, morphemes, or subword fragments. Formally, given a sequence of tokens $t_1, t_2, \dots, t_L$, an n-gram is any subsequence $(t_i, t_{i+1}, \dots, t_{i+n-1})$ for $1 \le i \le L-n+1$. If tokens are bytes (values in $[0,255]$) or Unicode characters (encoded as code points), the set of possible n-grams is large: for an alphabet of size $A$, there are $A^n$ possible n-grams.

Constructing n-grams over bytes or characters has several advantages. First, it avoids reliance on a fixed word vocabulary and therefore naturally handles rare words, misspellings, and morphological variants. Second, byte- or character-level n-grams capture subword structure that can be helpful for languages with rich morphology or when working across multiple languages. Third, n-grams provide features at different granularities: small $n$ (e.g., $n=1,2,3$) captures local patterns like character frequencies and short prefixes, while larger $n$ captures longer substrings.

In practice, one often extracts n-grams of multiple lengths simultaneously. For example, a common choice might be all n-grams for $n \in \{3,4,5\}$. Extracting overlapping n-grams results in a bag-of-n-grams representation: each distinct n-gram is counted (or otherwise aggregated) across positions. For classification tasks, you might represent a document as a sparse vector whose entries correspond to n-gram types and whose values are counts or binary indicators.

However, because the raw number of distinct n-grams can be huge, directly indexing them with a dictionary from the n-gram to a parameter vector is expensive in memory. This motivates compact alternatives: hashing the n-grams into a fixed-size table, using frequency-based pruning, or learning sparse embeddings keyed by hashed indices. Before discussing hashed tables, we need an efficient way to compute an integer identifier for each n-gram: that is where rolling polynomial hashes come in.

# Rolling polynomial hashes (RollPolyHash) and implementation

A rolling polynomial hash provides a fast way to compute a numeric fingerprint for each substring of a sequence. The idea is to treat each token as a numeric value and compute a polynomial in a base $B$ modulo a large integer $M$. For a token sequence $t_1, t_2, \dots, t_L$, define the polynomial hash of the length-$n$ substring starting at position $i$ as
$H(i,n) = \left(\sum_{k=0}^{n-1} t_{i+k} B^{n-1-k}\right) \bmod M$.
This is essentially interpreting the substring as a base-$B$ number. The "rolling" property refers to the ability to update $H(i,n)$ to $H(i+1,n)$ in constant time without recomputing the whole polynomial, using arithmetic operations and precomputed powers of $B$.

To show the update formula, write $H(i,n)$ explicitly and manipulate:
$H(i,n) = \left(t_i B^{n-1} + t_{i+1} B^{n-2} + \dots + t_{i+n-1} B^{0}\right) \bmod M$.
When sliding one step:
$H(i+1,n) = \left(t_{i+1} B^{n-1} + t_{i+2} B^{n-2} + \dots + t_{i+n} B^{0}\right) \bmod M$.
One can compute $H(i+1,n)$ from $H(i,n)$ by first subtracting the contribution of $t_i$, multiplying by $B$, and adding the new token $t_{i+n}$:
$H(i+1,n) = \left((H(i,n) - t_i B^{n-1}) \cdot B + t_{i+n}\right) \bmod M$.
To perform this efficiently, precompute $B^{n-1} \bmod M$ and reduce intermediate results modulo $M$ to avoid overflow. Many implementations use $M$ equal to a machine word modulus (e.g., $2^{64}$) and rely on wrapping arithmetic, which is efficiently implemented in hardware. Using a large prime $M$ (e.g., a 64-bit prime) can improve theoretical guarantees about collisions, but modulo $2^{64}$ arithmetic with randomly chosen $B$ is also common and practically effective.

When implementing RollPolyHash, several practical details matter. First, choose the base $B$ to be an odd number larger than the alphabet size (for bytes, $B > 256$). Randomizing $B$ (selecting it randomly once at initialization) reduces adversarial collisions when inputs may be constructed by an attacker. Second, choose modulus $M$ carefully. If you use 64-bit unsigned integers and rely on wraparound, the modulus is implicitly $2^{64}$, and arithmetic is fast. If you prefer a prime modulus, choose a 64-bit prime and implement 128-bit intermediate multiplication to avoid overflow when multiplying two 64-bit numbers. Third, compute power values $B^k \bmod M$ once for all needed $k$ up to the maximum n-gram length. These powers are reused during rolling updates. Fourth, handle character/byte values appropriately: for example, use the numeric byte value in $[0,255]$ for bytes, or use a fixed byte encoding (e.g., UTF-8) for characters and hash over bytes; alternatively, map Unicode code points to integers and treat them as tokens.

A simple implementation sketch in pseudocode for rolling over bytes with modulus $M=2^{64}$:

Initialize an unsigned 64-bit base B (random odd number > 256).
Compute pow = B^{n-1} (as 64-bit wraparound).
Compute initial hash h for first window of length n:
h = 0
for k from 0 to n-1:
    h = h * B + byte[i+k]  (wraparound)
For each subsequent position i:
    h = (h - byte[i] * pow) * B + byte[i+n]  (wraparound)
    // h now represents hash of window starting at i+1

This code relies on wraparound semantics; subtraction and multiplication are performed modulo $2^{64}$ automatically in typical unsigned arithmetic. If you use a prime modulus, replace wraparound with explicit modular arithmetic.

Beyond simple polynomial hashes, you may want to combine multiple hash functions to reduce collisions (e.g., two independent polynomial hashes with different bases and moduli). Another common trick is to mix the polynomial hash with a final avalanche function or a non-linear mixing step (for example, multiply by a large odd constant and then apply bitwise xors and shifts) to improve distribution properties.

The rolling hash lets you compute n-gram fingerprints for all positions in linear time $O(L)$ (plus the cost of precomputing powers). Once you have a numeric fingerprint for every n-gram, you can feed those fingerprints into a hash table, embedding table, or other downstream structure.

# Hash embedding tables and collision handling

Hash embedding tables map hashed n-gram identifiers to dense parameter vectors. Instead of maintaining a dictionary keyed by explicit n-grams (which could be enormous), one allocates a fixed-size table of $H$ slots, each containing an embedding vector of dimension $d$. Given the rolling hash value of an n-gram, you compute an index into the table, typically by taking the hash modulo $H$, and look up the embedding at that index. This approach is memory efficient because memory scales with $H \times d$ rather than the number of unique n-grams in the data.

The main issue with hash embedding tables is collisions: multiple distinct n-grams may map to the same slot. Collisions introduce noise, since the same embedding parameters will be used for different n-grams. How harmful collisions are depends on the task, the rate of collisions (determined by $H$ relative to the number of distinct n-grams), and whether collisions are systematic (adversarial) or random. Several strategies exist to manage and mitigate collisions.

One straightforward strategy is to select $H$ large enough that collisions are rare (e.g., target load factor much less than 1). However, large $H$ increases memory usage. A more compact approach is to use multiple hash tables or multiple "factors" per n-gram. In the multiple-hash scheme, for each n-gram you compute $k$ different indices (using different hash seeds or different hash functions) and store separate embeddings in each of the $k$ tables. When computing the n-gram embedding, you either concatenate the $k$ embeddings or sum/average them. This reduces the expected collision interference because for another n-gram to collide on all $k$ indices is exponentially less likely. Some papers call this the "hashing trick with multiple feature maps" or "multi-probe hashing."

Another technique is to store not only the embedding in each slot but also a small signature or tag derived from the hash. For example, keep a 16-bit fingerprint in addition to the embedding. During lookup, compare the stored fingerprint with the query fingerprint; if they mismatch, treat the slot as empty or only partially trust it. This reduces false positives (mistakenly believing the slot corresponds to the queried n-gram), at the cost of extra memory for the signatures. This idea is closely related to cuckoo filters or quotient filters in probabilistic data structures.

Cuckoo hashing and open addressing schemes can also be used to reduce collisions in storing explicit parameters for n-grams. If you want exact mapping but still conserve memory, store only the most frequent n-grams explicitly in a dictionary and use a hash table with chaining or open addressing. Less frequent n-grams are handled by a fallback hashed embedding table. In hybrid setups, you might reserve explicit slots for high-frequency n-grams and use hashed embeddings for the long tail.

Training with collisions requires care. When multiple n-grams share a slot, gradients from all occurrences will accumulate into the same parameters, effectively coupling their representations. If these n-grams are semantically unrelated, that coupling can harm performance. Regularization can help: weight decay or dropout applied at the embedding level can reduce overfitting due to noisy gradients. Another technique is to use per-slot adaptive learning rates (e.g., using Adam or per-parameter AdaGrad) which can help balance updates from different n-gram sources.

Evaluation strategies can reveal whether collisions are problematic. Monitor the distribution of indices touched during training and the hit count per slot. If a few slots receive many different n-grams, consider increasing $H$, using multiple hash functions, or storing signatures and selectively isolating highly contended slots.

Finally, when hashing across multiple n-gram lengths, it can be beneficial to separate table ranges by length. That is, allocate distinct hash tables (or disjoint index ranges) for each $n$ value. This prevents substrings of different lengths from colliding in the same pool and ensures, for example, that 3-grams aren’t overwriting embeddings that would otherwise represent 5-grams. Separating by length slightly increases memory overhead but often improves empirical performance.

# Frequency-based vs hashed n-gram representations

There are two broad paradigms for representing n-gram features: frequency-based (explicit) representations and hashing-based (compact) representations. Understanding the trade-offs helps choose the appropriate approach for a given application.

Frequency-based representations explicitly index n-gram types and store their counts or weights. The simplest version is a bag-of-n-grams vector where each dimension corresponds to one n-gram type and its value is the frequency in the instance. Frequency-based methods are straightforward and interpretable: you can inspect which n-grams are the most informative, prune by frequency, and apply statistical smoothing. Frequency-based models are well-suited for smaller vocabularies or when you have abundant memory, and they facilitate sparse linear models (e.g., logistic regression with sparse input). They are also used in feature selection pipelines where you might compute information gain, mutual information, or chi-squared scores for each n-gram and keep only the top $K$ features.

However, frequency-based representations suffer from the curse of dimensionality when the set of possible n-grams is large. The storage requires a dictionary mapping each seen n-gram to an index and memory proportional to the number of unique n-grams you choose to keep. Moreover, infrequent n-grams may cause statistical estimation problems and large feature tables increase the time for reading/processing.

Hashed n-gram representations use a hash function to map n-grams into a fixed-size index space. The main advantage is constant memory footprint determined by the table size rather than the number of unique n-grams observed. This makes hashed representations attractive for large-scale and streaming applications, where you cannot afford to store a huge dictionary. The hashing trick can be applied to counts (store hashed counts) or to embeddings (store hashed parameter vectors).

The trade-offs between frequency-based and hashed representations include the following. Frequency-based approaches avoid collisions entirely and thus preserve individual n-gram identity, which can be crucial for interpretability and when specific rare n-grams have outsized importance. Hash-based approaches sacrifice identity by allowing collisions, which injects randomness and possible interference. On the flip side, hashing often improves generalization by pooling parameters across similar or related n-grams through accidental sharing, and it significantly reduces memory and often computational overhead. In practice, many systems use hybrid strategies: reserve explicit entries for the most frequent n-grams and use hashing for the long tail. That way, the head (high-frequency, high-impact n-grams) is modeled exactly, while the tail is handled compactly.

Another dimension of comparison is update cost and adaptivity. In online or streaming settings, hashed representations are easy to maintain as the data distribution evolves because there is no need to change a dictionary or shift indices. Frequency-based dictionaries require dynamic resizing and reindexing if you want to add new entries. From a distributed systems perspective, hashing simplifies parameter sharding and lookup since the index space is fixed and readily partitionable.

In summary, frequency-based representations are precise and interpretable but memory-heavy, while hashed n-gram representations are memory-efficient and scalable but introduce collisions that must be managed. Practical systems often combine the strengths of both approaches by using explicit indices for the frequent items and hashed tables for the long tail.

# Normalization and integration with learned embeddings

Raw n-gram features (counts or hashed embeddings) often need normalization and careful integration to work well with learned dense embeddings in modern neural architectures. Normalization controls the scale of features, prevents rare or extremely frequent n-grams from dominating learning, and improves numerical stability. Integration concerns how to combine sparse n-gram-derived vectors with dense learned representations such as word embeddings, character CNN outputs, or transformer token embeddings.

Normalization strategies start with local normalization of counts. The simplest is term frequency (TF), where for an instance you normalize each n-gram count by the total number of n-grams in that instance, yielding relative frequencies. Another common technique is TF-IDF (term frequency–inverse document frequency), which downweights common n-grams that appear across many documents and upweights rarer, more discriminative n-grams. TF-IDF is particularly effective in linear models because it balances the global importance of features.

When n-grams are mapped to embeddings, normalization can be applied to the embedding aggregation step. Suppose an instance has a multiset of n-gram embeddings $\{e_1, e_2, \dots, e_m\}$ where each $e_j \in \mathbb{R}^d$ is obtained from a hash table. A common aggregation is the mean: $\bar{e} = \frac{1}{m} \sum_{j=1}^m e_j$. Averaging controls for variable-length inputs and is stable. Alternatives include sum (which preserves length information), max pooling (which picks dominant signals per dimension), and learned attention-weighted sums where attention weights over n-grams are computed by a small neural network. If counts are used, weighted sums like $\sum_j c_j e_j$ should be normalized by $\sum_j c_j$ or by a root-scaling such as $\sqrt{\sum_j c_j}$ to avoid large variance across examples.

When using hashed embeddings, it is important to consider the effect of collisions on normalization. If two n-grams share the same slot, their embeddings get mixed; averaging over many embeddings makes the mixing less harmful because the noise is averaged out. Conversely, when an instance contains repeatedly the same hashed index (e.g., repeating a common substring), summing without normalization can amplify the influence of that index and the unrelated n-grams that collide with it. In such cases, per-index frequency clipping (capping counts at a maximum value) or using logarithmic scaling of counts can help.

Integration with learned dense embeddings often involves concatenation or summation. For example, a token-level model might produce a learned word embedding $w \in \mathbb{R}^d$ and an n-gram-derived vector $\bar{e} \in \mathbb{R}^d$. A simple integration is to sum them elementwise: $h = w + \bar{e}$. Summation keeps dimensionality fixed and enables the model to use both sources directly. Alternatively, concatenation $h = [w; \bar{e}] \in \mathbb{R}^{2d}$ allows a subsequent layer to learn interactions between the two modalities. Another design is to project both into a shared space with learned linear layers before combining, i.e., $h = \mathrm{ReLU}(W_w w + W_e \bar{e} + b)$, which gives the model flexibility to weight and transform each source appropriately.

Regularization when integrating sparse and dense features is important. Because hashed embeddings are typically trained jointly with the rest of the model, they may have different effective learning rates and dynamics. It is common to use different optimizers or different hyperparameters (learning rate, decay) for sparse hashed embeddings versus dense parameters. For example, embeddings may require lower learning rates or per-parameter adaptive rates to avoid instability from high variance updates. Additionally, applying dropout to the aggregated n-gram vector or to individual hashed indices during training can improve robustness to collisions.

Another practical consideration is batching and computational efficiency. Lookups into large sparse tables can be memory-bound; to make training efficient on GPUs, fetch necessary embedding rows in a compact contiguous buffer per batch. If many examples in a batch share hashed indices, deduplicate indices to reduce repeated reads. Libraries and frameworks often provide optimized sparse embedding lookup primitives that handle partial prefetching and gradient accumulation efficiently.

Finally, when combining features from multiple n-gram lengths or multiple hashing schemes, normalization across lengths is useful. For instance, shorter n-grams occur more frequently than longer ones, so you might apply length-specific weighting or normalization factors so that 3-grams do not drown out 5-grams. You can learn these weights as scalar parameters per length or set them heuristically (e.g., inverse proportional to average frequency per length).

Summary and practical checklist

n-gram features over bytes and characters provide powerful local context signals that are language-agnostic and robust to rare words. Rolling polynomial hashes let you compute compact numeric fingerprints of n-grams efficiently in linear time. Hash embedding tables provide a memory-efficient way to parameterize n-gram representations at scale, but require careful collision handling: increase table size, use multiple hashes, store small fingerprints, reserve explicit slots for frequent n-grams, or use hybrid dictionaries. Frequency-based representations preserve identity and interpretability but are costly in memory; hashed representations trade some fidelity for scalability. Normalize counts and aggregated embeddings (TF, TF-IDF, mean pooling), apply per-length normalization, and consider different optimization hyperparameters for hashed embeddings. Integrate sparse n-gram-derived vectors with learned dense embeddings via summation, concatenation, or learned projections, and use regularization and careful batching to ensure efficient and stable training. By balancing these design choices, you can build compact, effective models that leverage local character- and byte-level signals while remaining practical for large-scale tasks.
