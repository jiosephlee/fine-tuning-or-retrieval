Introduction

Tokenization is the step that converts raw text into the discrete units a model actually consumes. Although it may appear as a mundane preprocessing detail, the choice of tokenization method strongly shapes model capacity, generalization, multilingual behavior, and even bias. In this chapter we develop a unified view of tokenization and subword methods used in modern language models. We start by grounding the discussion in how characters are represented on computers (UTF-8 and bytes), then survey the design space of vocabularies (word, subword, byte-level), explain widely used algorithms (Byte-Pair Encoding and SentencePiece/unigram), and analyze practical trade-offs such as vocabulary size and embedding-table cost. Finally, we examine failure modes and social/linguistic issues introduced by tokenization, and compare incremental (streaming) and non-incremental tokenization. The goal is not only to explain algorithms but to build intuition about why choices matter and how they interact with model architecture and evaluation.

# UTF-8 encoding and byte-level representation

Before designing tokenizers, we must understand the substrate: how text is represented in memory. Computers store text as sequences of code units (usually bytes). Unicode assigns each character a code point, e.g. the Latin letter “a” is U+0061, the Greek letter alpha is U+03B1, and the emoji “😊” is U+1F60A. Unicode is an abstract mapping from characters and glyphs to code points; to actually store text we use an encoding such as UTF-8, UTF-16, or UTF-32. UTF-8 is by far the most common on the web and in modern NLP tooling.

UTF-8 encodes each Unicode code point as a sequence of one to four bytes. ASCII characters (U+0000 through U+007F) are single-byte and have the same encoding as their ASCII values. Many common characters in European languages take two bytes, while less common symbols and most emoji require three or four bytes. Concretely, the number of bytes is determined by the high bits of the first byte and continuation bytes that begin with specific bit patterns. The important point for tokenization is that text can be viewed at different granularities: as a sequence of Unicode code points (characters), as a sequence of bytes, or as a sequence of encoded code units in some other representation.

There are two immediate implications. First, normalization matters: Unicode has multiple ways to represent the same visible string. For example, an accented character like “é” can be represented as a single code point U+00E9 (precomposed) or as the letter “e” (U+0065) followed by the combining acute accent (U+0301). Tokenizers typically apply Unicode normalization such as NFC (Normalization Form C) or NFKC to choose a canonical form before tokenization; whether to use compatibility normalization like NFKC depends on whether distinctions such as font or formatting should be preserved. Second, one can build tokenization strategies that operate at the byte level (each byte is an atomic token), at the code-point level (each Unicode character), or at higher linguistic levels like words or subwords. Byte-level tokenization avoids Unicode normalization pitfalls and ensures every possible input maps to a sequence of atomic tokens, but it yields longer token sequences and different semantics for model embeddings.

Finally, when designing or evaluating tokenizers, it is useful to think in terms of how many atomic units an average sentence becomes under different encodings. Because UTF-8 uses multiple bytes for many characters, byte-level vocabularies will generate longer sequences than code-point-level tokenizers for non-ASCII languages. This interacts with model context length and computational cost, so the encoding choice should be considered jointly with model architecture.

# Word, subword, and byte-level vocabularies

A vocabulary is the set of atomic units (tokens) a tokenizer maps text to. The traditional extremes are word-level vocabularies and character/byte-level vocabularies; modern practice mostly uses subword vocabularies that balance the trade-offs.

Word-level vocabularies treat whole words as tokens. In English, tokens might be “the”, “cat”, “sat”, etc. The advantage is interpretability and short token sequences: an average sentence has only tens of tokens rather than hundreds. However, pure word vocabularies imply very large vocabularies to cover morphological variation, named entities, typos, and cross-lingual items. Because vocabulary construction is typically performed on training corpora, word-level models suffer from out-of-vocabulary (OOV) tokens: words not in the vocabulary need special handling (e.g., an UNK token), which harms generalization. Word-level models also struggle with agglutinative or morphologically rich languages where a productive morphology yields many forms from a single lemma.

Character-level or byte-level vocabularies use a small atomic set: characters (Unicode code points) or bytes (values 0–255). The strengths are complete coverage (no OOV), compact vocabulary size, and robustness to spelling errors and rare words. The drawback is longer sequences and potentially slower learning: the model must learn to compose characters into morphological and lexical structures, which can require deeper or more data-hungry representations. Byte-level tokenization is language-agnostic and avoids Unicode normalization issues because it deals only with raw bytes; it has become more common with some transformer models because it guarantees determinism and coverage.

Subword vocabularies aim to capture the best of both worlds. They split words into frequently occurring subword pieces (morphemes, affixes, common syllables, or arbitrary frequent substrings) and include whole words when they are frequent enough. Subword tokens reduce sequence length compared to characters while avoiding the open-vocabulary problem of word-level tokenizers. They also allow models to generalize to unseen words by composing known subwords. Typical subword approaches are statistical: they learn a vocabulary by optimizing frequency or likelihood objectives on a corpus, often with hyperparameters controlling vocabulary size and whether to include a special marker for word boundaries. Subword tokenizers can be tuned to capture morphological regularities but may split words in unintuitive ways for certain languages and names.

Choosing between these vocabularies is not purely technical but practical: word-level vocabularies can be attractive for constrained-domain systems with limited lexicons, byte/character-level vocabularies are useful for robust multilingual or noisy input, and subword vocabularies are the common default for large general-purpose models because they balance coverage, efficiency, and compositionality.

# Byte-Pair Encoding (BPE) and SentencePiece

Byte-Pair Encoding (BPE) and SentencePiece (with its unigram model) are two of the most widely used algorithms for creating subword vocabularies. They take different conceptual approaches but both produce a fixed-size vocabulary of subword units and a deterministic tokenization algorithm.

BPE is a greedy, frequency-driven merging algorithm adapted from data compression. The training process begins by representing the training corpus as sequences of atomic symbols: commonly characters (or sometimes bytes) with a special end-of-word marker appended to preserve word boundaries. The algorithm then repeatedly merges the most frequent adjacent pair of symbols into a new symbol. Each merge increases the vocabulary by one. If you start with an initial vocabulary of characters and want a final vocabulary of size $V$, you perform $V - |\text{chars}|$ merges. After training, the merges define a set of rules; to tokenize a new word you apply the merges greedily to combine characters into the largest possible learned subword units. BPE naturally favors merging substrings that are frequent across the corpus, so common words become single tokens while rare or morphologically complex words remain decomposed.

Two practical variants are important. First, the initial alphabet can be bytes (byte-level BPE) rather than Unicode characters. Byte-level BPE avoids normalization and ensures any input byte sequence can be tokenized, but it uses more initial tokens for multi-byte characters. GPT-2 popularized byte-level BPE by mapping bytes to printable glyphs and learning merges on the byte sequences. Second, some implementations reserve special markers to denote token starts or ends (for example, a whitespace-marker prefix) so that the model can more easily detect word boundaries; this affects model behavior, particularly for languages where whitespace is not a clear word delimiter.

SentencePiece takes a different approach. It was created to provide a language-agnostic tokenizer that operates directly on raw text (without requiring pre-tokenization into words). SentencePiece supports two models: BPE and the unigram language model. The unigram model treats tokenization as a probabilistic segmentation problem. Training begins with a large seed vocabulary of candidate subwords (often all substrings up to a certain length) and estimates probabilities for each subword such that the likelihood of the training corpus under the unigram model is maximized. The algorithm then prunes low-probability subwords until the vocabulary reaches a target size. At tokenization time, SentencePiece uses dynamic programming (Viterbi) to find the segmentation of a string that maximizes product of subword probabilities (or equivalently minimizes negative log-likelihood). The unigram model has the attractive property that the marginal probability model can yield multiple plausible segmentations and supports subword regularization (stochastic sampling of segmentations during training), which can improve robustness.

Both BPE and SentencePiece often include special handling for unknown characters, whitespace normalization, and special tokens like <unk>, <pad>, <s>, </s>. They differ in determinism and flexibility: BPE produces a deterministic greedy segmentation based on learned merges, while SentencePiece unigram produces an optimal segmentation under a probabilistic model and can yield alternative segmentations for regularization. In practice, the choice often comes down to tooling, multilingual considerations, and whether byte-level operation is required.

# Vocabulary size trade-offs and embedding table implications

One of the most consequential hyperparameters in tokenizer design is vocabulary size $V$. This choice directly affects model parameters, computational cost, representational granularity, and generalization.

The most immediate cost is the embedding matrix. A standard embedding table has shape $V \times d$, where $d$ is the model embedding dimension. If embeddings are stored in 32-bit floats, the memory cost is approximately $4 V d$ bytes. For example, with $V = 50{,}000$ and $d = 1{,}024$, the embedding table alone is about $4 \times 50{,}000 \times 1{,}024 \approx 195$ MB. Large vocabularies therefore increase model size linearly and can become a bottleneck for models deployed on memory-constrained hardware. Quantization or shared embedding/softmax factors can mitigate cost, but the underlying trade-off remains.

Smaller vocabularies have lower memory cost and shorter token-to-embedding lookup latency. However, if the vocabulary is too small, tokens become too coarse or too fine depending on whether you reduce subwords or shift toward characters/bytes. Very small vocabularies (character/byte-level) yield longer token sequences, which raises compute cost in the transformer self-attention layers (cost roughly quadratic in sequence length for dense attention). Conversely, very large vocabularies (word-level or huge subword sets) reduce sequence length but increase embedding costs and model output dimensionality at the softmax layer. The softmax layer or language modeling head often shares weights with the embedding table; a larger vocabulary inflates both storage and per-step computation for computing logits and losses.

There is also a statistical trade-off. Larger vocabularies allow frequent words to be represented as single tokens, which can simplify learning and improve fluency for those words. But including many infrequent tokens reduces the frequency with which each token appears during training, which can make it harder for the model to learn good embeddings for rare tokens. Subword methods attempt to mediate this by allocating many tokens to frequent substrings and using composition for rare items.

Vocabulary size interacts with downstream tasks too. For sequence labeling or token-level supervision, different tokenization can change loss alignment and metric interpretation. For multilingual models, increasing vocabulary size can be necessary to cover diverse scripts without excessive fragmentation, but naive increases can favor high-resource languages unless careful balancing is applied during vocabulary construction.

Predicting the optimal $V$ depends on constraints. For single-language English models, values in the tens of thousands are common. Multilingual models sometimes use vocabularies of hundreds of thousands, but many large multilingual models instead keep $V$ in the tens of thousands and rely on subword sharing and byte-level techniques to cover many scripts. Practical considerations—GPU memory, batch size, model size, and target latency—often determine the right trade-off.

# Tokenization sensitivity, biases, and multilingual issues

Tokenization is not neutral; it encodes inductive biases about language and can introduce unintended asymmetries that affect fairness, robustness, and linguistic coverage.

First, tokenization affects model performance across groups. If subwords were learned on a corpus skewed toward particular dialects, names, or orthographies, those terms will be represented as single tokens while underrepresented names or morphological variants will be split into multiple subwords. As a result, the model can learn to handle the frequent forms more accurately, while struggling with rarer ones. For example, if a tokenizer sees “Washington” frequently but not a particular African or South Asian name variant, the latter may be split awkwardly into many subwords, which can degrade model predictions and bias outcomes in downstream tasks like named-entity recognition or machine translation.

Second, tokenization can encode sociolectal and orthographic biases. Languages with productive compounding (German) or complex morphology (Finnish, Turkish) may be penalized by tokenizers trained primarily on English, resulting in excessive fragmentation. Scripts such as Chinese or Japanese do not rely on whitespace, so tokenizers that use whitespace-based pre-tokenization often fail unless they include script-specific processing. Similarly, right-to-left scripts and scripts with complex shaping (Arabic) have normalization issues that must be handled carefully.

Third, ambiguity in segmentation can have semantic consequences. Splitting certain phrases or hyphenations differently can change the model’s learned representations and downstream decisions. Consider the tokenization of a phrase like “pro-choice”: if it is tokenized as a single token for some contexts but split across others, a classifier trained on token-level patterns might behave inconsistently.

Fourth, robustness to adversarial inputs and misspellings is influenced by tokenization granularity. Character/byte-level tokenizers are more robust to typos because a single misspelling does not create a wholly unknown token. Subword tokenizers can be brittle if a small alteration causes a different segmentation that the model hasn’t seen. Conversely, word-level tokenizers collapse different surface forms into separate tokens, increasing fragility.

For multilingual models, special care is required. There are two general approaches: a shared vocabulary across languages, or per-language vocabularies with language-specific tokenizers. Shared vocabularies encourage parameter sharing and transfer across languages but can bias the vocabulary toward scripts and languages that dominate the training corpus. Rare scripts may end up with many small subword pieces, increasing sequence length and reducing per-language model capacity. Per-language tokenizers avoid cross-language interference but complicate deployment and increase the number of tokenizer artifacts.

Mitigations include balanced sampling during vocabulary construction, explicit script-aware tokenization, using byte-level tokenization to guarantee coverage, and post-hoc vocabulary pruning or merging. Evaluating tokenization fairness requires measuring tokenization statistics across subpopulations (average token length per word, fraction of unknown bytes, average number of subwords per name) and incorporating those diagnostics into model selection.

# Incremental vs. non-incremental tokenization

Tokenization can be performed in two operational modes: non-incremental (batch) tokenization, where the entire input string is available and segmented in one pass, and incremental (streaming) tokenization, where characters/bytes arrive over time and the tokenizer must produce tokens or partial tokens to feed a streaming model such as an autoregressive decoder or a real-time system.

Most standard tokenizers are non-incremental: they see a full word or sentence and apply greedy merges (BPE) or dynamic programming (unigram) to find an optimal segmentation. Non-incremental tokenization can use lookahead (e.g., merge rules that depend on following characters) and normalization across the whole input. This is appropriate for batch processing and for training models where the entire context is available.

Incremental tokenization is required when latency or streaming constraints apply. Consider an autoregressive language model running in a dialog system: the user types in characters one-by-one and the system wants to begin generating completions before the user finishes. Incremental tokenization must decide when a prefix is tokenizable and which tokens are finalized versus provisional. This raises two issues: atomicity and consistency.

Atomicity concerns whether tokens are emitted only when they are finalized and will never change given future input. For example, in a greedy BPE-based tokenizer, input “uni” might remain a partial token that later merges with incoming characters to form “unicorn”. If the tokenizer emits a token prematurely, later characters could change its segmentation, leading to inconsistency between token sequences seen by the model in streaming versus batch modes. Incremental tokenizers often maintain a buffer for partial subwords until boundary conditions are met (such as whitespace or a deterministically final symbol).

Consistency is about ensuring that incremental tokenization yields the same token sequence as non-incremental tokenization when the full input is received. Achieving this can be nontrivial for probabilistic models like SentencePiece unigram, which may choose optimal segmentation only after seeing future characters. One strategy is to restrict the tokenizer to deterministic, left-to-right segmentation rules for incremental use. Another is to allow "finalization" markers and revise emitted tokens retrospectively, though revising tokens can be awkward for models and downstream state.

For autoregressive decoders that generate tokens (not characters), incremental tokenization of the incoming stream should align with the model’s token boundaries. When operating at the byte-level, every byte is atomic so the tokenizer can emit tokens deterministically as bytes arrive; the model must then handle longer contexts. For subword tokenizers, careful engineering is required: for example, many chat systems do not start model generation until the user indicates completion (pressing Enter) to avoid tokenization ambiguity.

Additionally, incremental tokenization interacts with caching and incremental inference. Transformer-based decoders often cache past key/value pairs keyed by token index. If tokenization revisions occur (previously emitted tokens are replaced), the cache must be updated accordingly, which is costly. Therefore, practical streaming systems prefer tokenizers that guarantee that once a token is emitted it will not be resegmented. This constraint should influence tokenization algorithm choice in low-latency deployments.

# Putting it together: practical recommendations and open questions

Designing tokenizers involves trade-offs across expressivity, memory, compute, fairness, and engineering complexity. For many large-scale, single-language models, subword tokenizers (BPE or SentencePiece) with vocabulary sizes in the tens of thousands offer a good balance. For multilingual coverage or to avoid Unicode pitfalls, byte-level BPE or byte-based SentencePiece can be attractive because they guarantee coverage without per-script heuristics. For low-latency streaming applications, ensure tokenization is incremental-safe—either by deferring generation until token boundaries are stable or by using an atomic-token representation such as bytes or characters.

When choosing vocabulary size, perform calculations for embedding table memory ($\approx 4 V d$ bytes for 32-bit floats), the expected change in average sequence length, and how those affect transformer compute (self-attention cost scales roughly as $O(L^2 d)$ for a sequence length $L$). Profile the end-to-end system: a smaller $V$ that increases $L$ might be worse than a larger $V$ that fits memory but reduces sequence length.

Beware tokenization-as-bias: evaluate tokenization behavior on held-out demographic and linguistic slices. Measure the average number of subwords for names, low-resource languages, and morphological variants; inspect whether certain groups systematically get longer tokenizations or more UNK-like behavior. Consider augmenting tokenizer training data or using script-aware techniques to mitigate disparities.

Open research questions remain. How much can purely byte-level models close the efficiency gap with subword models given architectural innovations? Can tokenization be learned jointly with model parameters in an end-to-end differentiable way that remains computationally practical? How to build tokenizers that are both multilingual and fair across many underrepresented languages without exploding vocabulary size? Advances in subword regularization, adaptively growing vocabularies, and compressed embedding structures (e.g., product quantization, factorized embeddings) continue to shift the trade-off frontier.

Summary

Tokenization is a foundational design choice that touches algorithmic, engineering, and ethical aspects of NLP systems. Understanding UTF-8 and byte representations grounds you in the substrate on which tokenizers operate. Choosing between word, subword, and byte-level vocabularies requires balancing coverage, sequence length, and embedding costs. Algorithms like BPE and SentencePiece provide practical ways to learn subword vocabularies, each with distinct properties. Vocabulary size directly impacts model parameters via the embedding table, and tokenization can embed biases that affect fairness and multilingual performance. Finally, incremental tokenization introduces additional constraints required by streaming and low-latency systems. Careful measurement, evaluation across linguistic slices, and conscious engineering choices are required to build reliable and equitable tokenization pipelines.
