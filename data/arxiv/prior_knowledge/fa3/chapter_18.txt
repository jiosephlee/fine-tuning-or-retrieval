Introduction

GPUs have become the dominant platform for accelerating dense linear algebra and attention-like operations used in machine learning. Achieving high performance on modern GPUs requires more than just mapping a mathematical formula like matrix multiply or scaled dot-product attention onto a stream of CUDA threads; it requires carefully engineered software that exposes the right parallelism, manages memory hierarchy, and maps computations to specialized hardware primitives such as tensor cores and fast shared memory. This chapter surveys the software ecosystem and optimized libraries that researchers and engineers rely on to implement high-performance GEMM (general matrix–matrix multiply) and attention kernels. We will look at the building blocks and design patterns provided by low-level libraries such as CUTLASS, platform-optimized offerings like cuDNN, high-level kernel-generation frameworks such as Triton, and how these components integrate with frameworks like PyTorch. Finally, we will discuss the trade-offs between portability and hardware-specific optimizations and practical considerations when designing or choosing an implementation.

# CUTLASS: building blocks for high-performance GEMM primitives

CUTLASS (CUDA Templates for Linear Algebra Subroutines and Solvers) is a CUDA C++ template library from NVIDIA that exposes reusable, composable building blocks for implementing high-performance GEMM and related primitives. Its design reflects the canonical structure of a high-performance GPU GEMM: multi-level tiling of the computation, explicit management of data movement through memory hierarchy (global memory, shared memory, registers), use of fast hardware instructions (SIMT loads/stores, warp-level primitives, and tensor core instructions), and a flexible epilogue stage for applying post-processing like scaling, activation, or bias-add.

At the heart of CUTLASS is the decomposition of GEMM into several conceptual layers. The outermost layer divides the output matrix $C$ into tiles that are computed by cooperative thread blocks (CTAs). Each CTA loops over the $K$ dimension in blocks, loading fragments of $A$ and $B$ from global memory into shared memory, and then performing a sequence of inner micro-kernels that multiply fragments of $A$ and $B$ to update accumulators held in registers. This multilevel tiling—grid-level, block-level, warp-level, and register-level—lets the implementation balance parallelism, data reuse, and resource constraints (shared memory and registers).

CUTLASS formalizes this through a set of parameterized components. A typical CUTLASS GEMM is specified by types that describe:

- The data types for $A$, $B$, $C$, and accumulator (for example, float16 inputs with float32 accumulation).
- The threadblock tile shape (for example, $128 \times 128$ for the CTA).
- The warp tile shape and the instruction-level tile shape (e.g., $16 \times 16$ for a tensor core instruction).
- The memory layouts (row-major, column-major, interleaved layouts).
- The epilogue functor that maps raw accumulators to final outputs (scaling, activation, elementwise ops).

These templates let library authors explore many combinations of tile shapes and data layouts without rewriting kernels. CUTLASS also provides a library of highly tuned micro-kernel primitives that encapsulate the warp- and instruction-level implementation details, including explicit implementations targeting NVIDIA tensor core instructions (WMMA/ mma.sync) and vectorized SIMT math.

From an implementation viewpoint, two aspects are critical. First, data movement is optimized to maximize reuse: each piece of data loaded into shared memory is reused by multiple threads and warps before being evicted. Second, compute is organized to exploit warp synchronous instructions and tensor cores for high throughput. CUTLASS uses warp-level matrix multiply accumulators combined with careful instruction scheduling to ensure high utilization of compute units. The epilogue stage is also explicit: after accumulation, the epilogue reads accumulators and writes results back to global memory, applying scaling, bias, activation, and formatting. This separation lets one mix-and-match compute and post-processing efficiently.

CUTLASS also provides a performance model and a set of benchmarking utilities to search the parameter space of tile sizes and blocking strategies. Since modern GPUs have many architectural knobs (shared memory per SM, warp size, tensor core throughput), CUTLASS’s composable approach enables portability across GPU generations by retuning those parameters. In practice, CUTLASS forms the basis for many production GEMM implementations and higher-level libraries: vendors, research groups, and third-party frameworks either use CUTLASS directly or take inspiration from its modular design.

# cuDNN and vendor-optimized primitives for attention/GEMM

cuDNN (CUDA Deep Neural Network library) is NVIDIA’s highly optimized collection of GPU primitives tailored for deep learning. Where CUTLASS provides building blocks and templates, cuDNN provides ready-to-use, production-quality primitives that are heavily tuned and validated across a wide range of networks and hardware. cuDNN includes implementations for convolutions, RNNs, batch normalization, activation functions, and more recently, attention primitives and optimized GEMM routines that are used as the underlying computation for many layers.

Vendor-optimized libraries like cuDNN have several distinguishing characteristics. First, they are delivered as precompiled, closed-source kernels with carefully tuned kernels for specific hardware generations. These kernels take advantage of hardware-specific instructions (such as tensor cores with specific dot-product instruction encodings), memory subsystem behavior, and scheduling strategies that may not be expressible in high-level code without exposing architecture internals. Second, cuDNN exposes multiple algorithmic variants for many operations and a heuristic/auto-tuner that picks the best variant at runtime based on tensor shapes, data types, and profiling information. For example, a convolution might be implemented via FFT, GEMM-based lowering, Winograd, or direct convolution depending on the best throughput and memory trade-offs.

In the attention domain, cuDNN has started to provide fused attention primitives that implement the full scaled dot-product attention or portions thereof as a single kernel or a set of tightly integrated kernels. Fusing the softmax, scaling, and matmul operations reduces memory traffic: instead of materializing large intermediate tensors in global memory, intermediate results are kept in registers or shared memory for immediate consumption. This is crucial for attention where the $QK^T$ matrix (for queries $Q$ and keys $K$) can be large, and reading/writing it multiple times is expensive.

Vendor libraries also exploit specialized numerical formats and operations. Mixed-precision computing—e.g., using $FP16$ or $BF16$ inputs with $FP32$ accumulation—provides higher arithmetic throughput while maintaining accuracy. Tensor cores offer higher throughput for mixed-precision matrix multiply-accumulate operations, but getting peak performance requires mapping data layouts and tile sizes to the tensor core instruction shapes. Vendor libraries include these mappings and assembly-level kernels where necessary.

The price of vendor tuning is, however, decreased transparency and sometimes limited flexibility. When a user needs to implement slightly non-standard behavior—for example, an unusual attention variant or a custom activation fused into the epilogue—the vendor primitive may not support it directly. Some libraries address this by offering extensible epilogue hooks or by exposing lower-level primitives (e.g., matmul backends) that can be assembled by user code. Nonetheless, when the required functionality matches the vendor-provided operations, the performance is often superior because the vendor kernels are optimized to exploit the microarchitectural details that are difficult for a third party to reproduce.

# Triton and other high-level kernel-generation frameworks

Triton is a high-level language and compiler for writing custom GPU kernels that aims to make it easier to express data-parallel computations while still enabling high performance comparable to handwritten CUDA. The key idea behind Triton is to provide a model where a developer writes kernel logic in a Python-embedded DSL that resembles cooperative SPMD programming; the compiler then lowers this description to efficient CUDA or NVVM code, handling many low-level optimizations automatically.

Triton’s programming model revolves around the notion of a kernel that operates on large, blocked portions of a tensor. The programmer indexes into input and output tensors with symbolic "program IDs" that represent slices of the work, and Triton generates code that computes those tiles. Behind the scenes, Triton maps these tiles to hardware threads and warps, inserts vectorized loads and stores, schedules shared memory usage, and can generate code that uses warp-level matrix-multiply instructions. Triton also performs a variety of static and dynamic analyses to select loop unrolling factors, prefetching schedules, and memory layout transformations.

One strength of Triton is expressivity: it is straightforward to implement fused kernels that eliminate intermediate memory traffic (for example, a fused attention kernel that computes $QK^T$, applies scaled softmax, and multiplies by $V$ without storing $QK^T$ to global memory). Because Triton expresses kernels at a higher level, common patterns like reduction, broadcasting, and strided memory accesses are easier to implement correctly and concisely. Triton also provides an autotuning infrastructure and heuristics to pick tile sizes and other parameters for a given GPU.

Other high-level kernel-generation frameworks include TVM (with its tensor expression language and schedule primitives), Halide (and GPU backends), and MLIR-based approaches that allow flexible lowering and optimization. TVM is particularly focused on tensor algebra and scheduling: a user expresses the computation as an index-based tensor expression and then applies schedule primitives (blocking, vectorization, compute-at, etc.) to transform the computation for the target hardware. TVM’s auto-scheduler can search the schedule space to find performant variants. MLIR-based toolchains are emerging to represent higher-level operations and progressively lower them through dialects to GPU dialects that map to LLVM/ NVVM.

These frameworks share common trade-offs. They provide easier programmability and faster development for new kernels compared to writing raw CUDA, and they often include auto-tuning to help find good parameters. However, they must capture a sufficiently rich set of transformations and have a back-end capable of generating code that competes with hand-tuned assembly or vendor kernels. For kernels that require exploiting tiny architectural quirks or newly introduced instructions, framework maintainers must update the back-end to expose those capabilities. In practice, Triton and TVM have enabled rapid iteration in research and production for attention and customized GEMM-like operations because they dramatically reduce development effort while achieving strong performance.

# PyTorch integration points, kernels and extensions

PyTorch is a leading deep learning framework that exposes multiple integration points for accelerated kernels, enabling both runtime use of vendor libraries and user-defined extensions. Understanding where custom kernels and optimizations fit into PyTorch is crucial for deploying high-performance attention and GEMM routines.

At the core of PyTorch’s compute backend is ATen, the tensor library implementing operations on CPU and GPU (through CUDA). ATen provides the C++ API that underlies PyTorch tensors and operations. Many high-performance primitives in PyTorch ultimately route through ATen to call into vendor libraries (cuDNN, cuBLAS) or custom kernels implemented in CUDA/C++.

There are several mechanisms for extending PyTorch with custom kernels:

- C++ extensions (torch::autograd::Function and cpp extension). Developers can write CUDA kernels and wrap them in C++ code that integrates with PyTorch’s dispatcher and autograd. The extension is compiled into a shared library and can be loaded at runtime. This approach gives full control over implementation details, memory management, and gradient computation, and is the typical route for shipping production kernels.

- JIT / TorchScript and custom operator registration. PyTorch allows registering custom operators (ops) that can be invoked from Python, traced or scripted by the JIT, and serialized in TorchScript. Custom ops can be implemented in C++/CUDA and registered with the dispatcher, which allows them to be exported in models and used in production runtimes such as LibTorch.

- CUDA kernel wrappers via Python APIs (e.g., using Numba or Triton). Some researchers prototype kernels using Python-embedded kernel compilers such as Triton or Numba, and then call these kernels from PyTorch. While prototyping is fast, production workloads often prefer C++ extensions for stability and deployment.

- Fused kernels and graph compilers. Projects like PyTorch’s JIT graph fuser and TorchInductor aim to lower high-level graph fragments into optimized fused kernels. The JIT fusion stack attempts to fuse elementwise and reduction patterns into single kernels to reduce memory traffic and overhead. Newer backends target GPU code generation and may call Triton or generated CUDA kernels.

PyTorch also provides utilities for memory format and layout management (e.g., channels-last layout), custom memory allocators, and stream and event management to orchestrate asynchronous kernels and overlapping of compute and data movement. For GEMM and attention, integration often involves calling into cuBLAS/cuDNN for standard shapes, while custom fused attention kernels are shipped as extensions when vendor primitives are insufficient. Registration through the dispatcher ensures the custom operator is called transparently in Python code and ties into autograd by providing forward and backward implementations.

Performance-sensitive integration also requires careful handling of concurrency and streams. PyTorch’s default behavior executes kernels on the current CUDA stream of the tensor; custom kernels must honor stream semantics, use asynchronous APIs appropriately, and avoid synchronization unless necessary. Memory alignment, padding, and tensor contiguity are other practical concerns: custom kernels often expect tensors in a particular layout or alignment to leverage vectorized loads or tensor core instruction alignment constraints.

Finally, packaging and distribution matter. For a kernel to be used widely, it must be compiled against multiple CUDA/toolkit versions and GPU architectures. Prebuilt wheels (manylinux with bundled CUDA) or on-install compilation scripts are common distribution strategies, each with trade-offs between ease-of-use and compatibility.

# Considerations for portability vs hardware-specific optimizations

One of the central tensions in GPU kernel design is the trade-off between portability and leveraging hardware-specific optimizations to extract maximal performance. Portability implies writing code that runs correctly and reasonably efficiently across different GPU vendors and generations. Hardware-specific optimizations, by contrast, exploit idiosyncratic features—special instructions, memory subsystem characteristics, or instruction encodings—to achieve peak throughput, but can be brittle across architectures.

Portability can be pursued at multiple levels. The highest-level approach is to rely on vendor libraries (cuBLAS, cuDNN) and portable frameworks (oneAPI, ROCm libraries for AMD) so that the same high-level API runs across hardware with vendor-provided backends implementing the optimal kernels. Another portable route is to use compiler-driven frameworks such as TVM, Triton, or MLIR-based pipelines that can retarget different backends and perform autotuning per-architecture. These approaches reduce the burden on the developer but often do not reach the absolute peak that a hand-tuned, vendor-specific kernel can attain.

Hardware-specific optimization strategies deliver higher performance by mapping computations to particular primitives. Examples include using NVIDIA tensor core instructions (e.g., mma.sync) to perform mixed-precision $M \times N$ multiply-accumulate operations in the $8 \times 8$ or $16 \times 16$ shapes supported by the instruction, or leveraging specialized memory instructions (like LDG with cache hints) and carefully chosen shared memory bank layouts to minimize bank conflicts. Hand-tuned kernels may include inline PTX or SASS-level tuning, use of cooperative groups for warp-shared communication, and manual scheduling to hide latencies in a way that generic compilers do not.

However, hardware-specific code has maintenance and portability costs. An implementation tuned for the memory hierarchy and instruction set of one GPU generation may underperform or even be incorrect on another generation if assumptions about register pressure, warp scheduling, or tensor core shapes change. Moreover, the introduction of new numeric formats (e.g., BF16, TF32) and specialized hardware units requires reworking kernels to exploit them. For multi-vendor portability, the challenge is greater: AMD and NVIDIA have different ISA, transcendent performance knobs, and libraries.

Practical strategies to balance the trade-offs include:

- Layered design: implement operations in layers so that the highest-level logic is portable while a backend-specific implementation implements the hot inner loops. For example, express attention in terms of high-level primitives (GEMM + softmax + GEMM) and provide fast paths that call vendor-optimized fused primitives when available; otherwise, fall back to a portable generic implementation.

- Autotuning and parameterized kernels: write parameterized kernels (as CUTLASS does) and run autotuning at install time or first run to pick tile sizes and unroll factors tuned to the particular GPU. This gets much of the benefit of hand tuning without hardcoding parameters.

- Expose architecture-specific code paths behind a single API: let the runtime select between portable code and highly tuned kernels based on device properties. This is the approach used by cuDNN: many algorithms are available and the library picks the best one for given shapes and device.

- Use intermediate abstractions: MLIR and other IRs can express transformations and lowerings in a device- and instruction-aware way. If the backend is kept up-to-date, then code can be retargeted with lower effort.

- Keep correctness and numerical stability as first-class goals: hardware-specific optimizations often change numerical ordering and can affect reproducibility. Mixed-precision or fused operations should include user-configurable options for deterministic or more accurate variants when needed.

- Plan for maintainability: maintain a testing and benchmarking harness that continuously runs kernels across target architectures. Because hardware evolves, continuous integration that runs performance regression tests and correctness tests across multiple GPUs is critical.

A concrete example of this tension is implementing attention for transformer models. A naive, portable implementation computes $S = Q K^T$ (an $M \times N$ matrix), applies scaled softmax across appropriate axes, and computes $O = \text{softmax}(S) V$. This code is straightforward and portable but incurs significant memory traffic. A hardware-specific optimized kernel fuses these operations, keeps intermediate $S$ tiles in shared memory or registers, and uses tensor cores for the matrix multiply, achieving much lower memory bandwidth and higher throughput. But that fused kernel must be rewritten to exploit different tensor core shapes or instruction encodings on a new GPU generation or a different vendor’s accelerator.

In summary, the choice between portability and specialization depends on constraints: if you must support many hardware targets and prefer maintainability, favor portable frameworks and autotuning; if you need peak performance on a narrow set of hardware, invest in specialized kernels and vendor-tuned libraries. In production systems, the pragmatic approach is hybrid: provide portable fallbacks while shipping specialized kernels for the dominant hardware in your deployment.

Conclusion

High-performance GEMM and attention implementations sit at the intersection of algorithmic design and low-level hardware engineering. Libraries like CUTLASS expose composable building blocks that capture effective tiling and data movement strategies, while vendor libraries such as cuDNN provide battle-tested, highly optimized kernels for common patterns. High-level code generators like Triton and TVM speed up development and allow researchers to implement and tune fused kernels without writing raw CUDA, and frameworks like PyTorch provide the integration points to bring these kernels into real models. Understanding the architectural primitives—shared memory, warp-level operations, tensor cores, and the trade-offs in tiling, accumulation precision, and memory layout—is essential for reading research papers and contributing new kernels. Finally, thoughtful engineering is required to balance portability against the desire for hardware-specific performance, and the right balance often combines autotuning, layered designs, and vendor-optimized code paths.
