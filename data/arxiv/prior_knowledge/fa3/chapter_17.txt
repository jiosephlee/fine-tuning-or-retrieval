Introduction

Measuring and understanding the performance of GPU kernels is essential for designing high-performance code, comparing different algorithms, and interpreting results in research. GPUs are highly parallel processors whose performance depends on a complex interplay of arithmetic throughput, memory subsystem behavior, instruction-level efficiency, and software-level choices such as blocking, data layout, and kernel launch configuration. This chapter presents a practical and principled approach to quantifying GPU performance. We begin by defining how to count operations and express throughput in TFLOPs, then move to utilization metrics that relate achieved performance to hardware peaks. After that we discuss how to design benchmarks and parameter sweeps (batch size, sequence length, attention head dimension) so comparisons are fair and informative. We present the main profiling tools available for NVIDIA and other vendors, explain which hardware counters and measurements matter, and conclude with methods for ablation studies and controlled experiments that isolate cause and effect. Throughout the chapter we emphasize intuition and reproducible experimental design so that results are both accurate and meaningful.

# Measuring throughput: TFLOPs and the counting of operations

When people say a kernel achieves "X TFLOPs", they are reporting the rate at which floating-point operations were executed, converted into trillions of floating-point operations per second. TFLOPs is a common shorthand for raw arithmetic throughput, but careful interpretation requires two steps: (1) accurately counting the number of floating-point operations performed by the kernel, and (2) dividing that count by the measured execution time.

Counting operations requires a clear definition of what you consider to be a floating-point operation. Typically, each fused multiply-add (FMA) is counted as two floating-point operations because it performs one multiply and one add. Some vendors' peak FLOPs specifications already count FMA as two operations; therefore use the same convention when comparing against peak. For example, if your kernel executes $N_{\text{FMA}}$ FMA instructions and $N_{\text{other}}$ other floating-point operations (adds, multiplies, divides, etc.), then a common FLOP count is
\[
\text{FLOPs} = 2\cdot N_{\text{FMA}} + N_{\text{other}}.
\]
It is important to be explicit about this convention in any report.

How do we obtain $N_{\text{FMA}}$ and $N_{\text{other}}$? There are several approaches: (a) analyze the arithmetic in the algorithm and compute counts symbolically, (b) examine the compiled assembly or intermediate representation to count issued FP instructions, or (c) use vendor tools that estimate FLOP counts based on kernel instrumentation. The most robust approach for research is to perform analytical counting from the algorithm and then validate with profiling. For example, consider a dense matrix-matrix multiply of dimensions $M\times K$ times $K\times N$. Each output element is
\[
C_{i,j} = \sum_{k=1}^K A_{i,k} \cdot B_{k,j},
\]
which requires $K$ multiplies and $K-1$ adds, often implemented with FMA to yield $K$ FMA operations per output (i.e., $2K$ FLOPs under the FMA-as-two convention). Therefore the total FLOP count is
\[
\text{FLOPs}(GEMM) = 2 M N K.
\]
For more complex kernels (convolutions, attention, layer norm, activation functions), list the arithmetic per output and multiply by the number of outputs.

Once you have a FLOP count, measure the elapsed time $T$ for the kernel under realistic conditions (warm-up iterations to avoid first-call overhead, correct input sizes, pinned memory when necessary), and compute
\[
\text{TFLOPs} = \frac{\text{FLOPs}}{10^{12} \cdot T}.
\]
Be cautious about measuring time: use precise GPU timers (events on CUDA with cudaEventRecord + cudaEventElapsedTime, or profilers that report device time) rather than host wall-clock time if kernels are asynchronous.

Counting alone is not sufficient to judge efficiency. Often the arithmetic count assumes ideal use of FMAs while actual kernel execution may include non-FMA operations, type conversions, or predicated instructions (masked execution) that reduce effective FLOP throughput. Similarly, kernels that rely heavily on mathematical library functions (e.g., transcendental functions) will have different instruction mixes and latency characteristics. Always document the instruction mix and validate your analytical FLOP count against low-level instruction traces or profiler-reported operation counts where possible.

# Utilization metrics: achieved vs theoretical peak

A natural question after measuring TFLOPs is: how close is that to the hardware's theoretical maximum? Utilization metrics express achieved performance as a fraction of theoretical peak throughput or bandwidth. They help locate bottlenecks: if arithmetic utilization is low but memory bandwidth usage is small, then some other inefficiency (divergence, serialization, scheduling, register pressure) may be involved.

The first baseline is the theoretical peak FP throughput. For an NVIDIA GPU, the vendor publishes peak arithmetic rates per precision (FP32, FP16, BF16, TF32, FP64) in terms of operations per second assuming all execution units are kept busy with FMAs. For example, if the peak is $P_{\text{peak}}$ FLOPs/s in your precision and your kernel achieves $P_{\text{achieved}} = \text{FLOPs} / T$, arithmetic utilization is
\[
U_{\text{arith}} = \frac{P_{\text{achieved}}}{P_{\text{peak}}}.
\]
Interpret this number carefully. A low $U_{\text{arith}}$ might reflect a kernel that is memory-bound rather than compute-bound. To decide which bottleneck dominates, compare arithmetic intensity to the machine balance using the roofline model.

The roofline model links arithmetic intensity (AI) to achievable performance. Arithmetic intensity is defined as
\[
\text{AI} = \frac{\text{FLOPs}}{\text{bytes transferred}},
\]
where "bytes transferred" should reflect data movement that limits performance, often measured as bytes read/written from global memory. Given a memory bandwidth limit $B_{\text{mem}}$ (bytes/s), the memory-bound performance ceiling is $B_{\text{mem}} \cdot \text{AI}$. The roofline plot places AI on the horizontal axis and achievable performance on the vertical axis; the roofline itself is the minimum of the compute peak line and the memory-bound line. A kernel lies on or below the roofline; if a kernel's achieved performance lies close to $B_{\text{mem}} \cdot \text{AI}$, it is memory-bound. If it is significantly below both the memory and compute roofs, the kernel may be limited by latency, instruction mix, thread-level inefficiencies, or other microarchitectural effects.

Beyond arithmetic utilization, other utilization metrics are important:
- Memory bandwidth utilization: the fraction of peak global memory bandwidth used by the kernel. Use profiler counters or microbenchmarks to obtain $B_{\text{achieved}}$ and compute $U_{\text{mem}} = B_{\text{achieved}} / B_{\text{peak}}$.
- SM (streaming multiprocessor) occupancy: the fraction of maximum active warps or threads resident on each SM. Occupancy is a measure of how many warps are available for latency hiding. Low occupancy can reduce the ability to overlap memory latency, but occupancy is neither necessary nor sufficient for high performance—well-tuned kernels may achieve high throughput at modest occupancy by maximizing instruction-level parallelism and register reuse.
- Active warps per SM and warp schedulers utilization: hardware counters report average active warps or warp stalls; these indicate under-utilization from divergence or serialization.
- Achieved instructions per cycle (IPC) and delivered memory transactions per cycle: comparing IPC to a reference maximum IPC suggests instruction pipeline utilization.

When reporting utilization, include the measured hardware peak assumptions: was tensor core usage counted at FMA-with-fused-accumulate rate? Are specialized units (tensor cores, FP16 pipelines) included? For mixed-precision or tensor-core kernels, the theoretical peak arithmetic rate often exceeds standard FP32 peaks; ensure the FLOP counting convention matches that peak.

In addition to raw ratios, provide multiple complementary metrics together: TFLOPs, memory bandwidth usage, arithmetic intensity, occupancy, IPC, and relevant latency or stall counters. This combined view helps identify whether you should optimize memory accesses, tile sizes, data movement, or arithmetic scheduling.

# Benchmark design: varying batch, sequence length, and head dim

Designing benchmarks for GPU workloads requires covering the range of problem sizes and parameter regimes that matter in practice. For deep learning and transformer-like workloads, key parameters include batch size, sequence length, and attention head dimension (head dim). These parameters strongly influence arithmetic intensity, memory access patterns, and kernel launch parallelism. A fair and informative benchmark systematically varies these parameters and reports their impact.

Batch size affects two things: the total amount of parallel work and the steady-state cost of kernel launches. Larger batches raise the total number of independent work-items (e.g., more matrix rows to process), increasing parallelism and often leading to better utilization of the GPU. Small batch sizes can leave many CUDA cores idle or cause kernels to be memory-latency-bound because there are not enough threads to hide latencies. When benchmarking, sweep batch sizes from small (e.g., 1, 2, 4) to large (e.g., 64, 128, 1024) depending on the application. Report both per-batch latency and throughput (examples/sec or tokens/sec) as both metrics matter: real-time inference cares about latency at small batch, while training commonly emphasizes throughput at large batch.

Sequence length (e.g., the number of tokens in transformers) changes the size of intermediate matrices in attention and affects both compute and memory. For attention, complexity often scales as $O(L^2)$ memory and computation per layer when computing full attention over a sequence of length $L$. Short sequences may allow efficient blocking and increased cache reuse; very long sequences change the working set so that memory bandwidth and capacity become limiting. When reporting results for transformer kernels, sweep sequence lengths that reflect realistic workloads (e.g., 16, 64, 128, 512, 2048) and show where performance drops or transitions between compute-bound and memory-bound regimes.

Head dimension is the size $d$ of each attention head; attention uses matrices of shape $L \times d$ and the per-head compute often scales with $d$. Small head dimensions may lead to underutilization of vector units and diminished ability to use tensor cores (which often prefer particular tile sizes and minimum operand shapes). Large head dimensions increase arithmetic intensity and often improve utilization but can raise register pressure and shared memory use in kernels, possibly increasing occupancy pressure or forcing spilling. Vary $d$ across powers of two and other common values (e.g., 32, 64, 128, 256) to see how kernel implementations handle preferred tile sizes.

Beyond sweeping single parameters independently, consider combined sweeps because interactions matter. For instance, small batch and large sequence might behave differently than large batch and small sequence in terms of tiling and cache reuse. Present performance as heatmaps or multiple plots that fix one parameter while varying two others, so readers can see interactions.

Other important benchmarking considerations:
- Warm-up iterations: discard the first few iterations to avoid including one-time setup costs (kernel compilation, memory allocation, caching).
- Multiple trials: report mean and standard deviation over several runs to indicate variability, especially important for latency-sensitive benchmarks.
- Synchronized timing: ensure kernel times are measured with device synchronization (e.g., cudaEvent) to avoid host-device asynchronous semantics obscuring true GPU time.
- Hardware and software configuration: report GPU model, driver version, CUDA toolkit, cuDNN/cuBLAS versions, clock rates (boost states), power limits, and thermal conditions. Subtle differences (power cap, ECC, GPU mode) can affect results materially.
- Avoid including data transfer time from host to device unless comparing full end-to-end systems; if you do include transfers, be explicit and report both on-GPU kernel time and end-to-end time.

Finally, when comparing two implementations, ensure both are compiled with equivalent optimization levels, use the same runtime (e.g., same CUDA version), and have identical numerical precision and algorithmic trade-offs. Differences in numerical choices (e.g., FP32 vs mixed precision) can change both performance and numerical results; report these details.

# Profiling tools (Nsight, nvprof, CUPTI, vendor tracers) and counters

Profiling is the essential bridge between observed performance and root causes. A variety of tools are available, providing different levels of visibility, overhead, and usability. On NVIDIA GPUs, popular options include NVIDIA Nsight Systems and Nsight Compute, the legacy nvprof (deprecated), and the low-level CUPTI (CUDA Performance Tools Interface) for custom instrumentation. Other vendors offer analogous tools (e.g., ROCm’s rocprof/roctracer, Intel VTune/oneAPI for discrete GPUs). This section surveys the tools and the critical counters to examine.

Nsight Systems provides system-wide tracing with low overhead suitable for end-to-end application profiles. It shows kernel launch timelines, CPU/GPU overlap, memory copies, and multi-process behavior. Use Nsight Systems to identify high-level inefficiencies: frequent small kernel launches, host-side stalls, synchronization overhead, or pipeline bubbles. The timeline view clarifies whether the GPU is idle between kernels due to host-side synchronization or kernel dependencies.

Nsight Compute is a kernel-level profiler that reports detailed device metrics and source/assembly inspection. It can show instruction statistics, achieved occupancy, memory throughput per cache level, stall reasons, and the distribution of instructions across types. Use Nsight Compute to inspect "hot" kernels at the instruction level and to obtain counters such as:
- sm__sass_thread_inst_executed_op_fadd_pred_on (or equivalent): number of FP add instructions executed.
- sm__sass_thread_inst_executed_op_fmul_pred_on: number of FP multiply instructions.
- sm__pipe_tensor_cycles_active: time tensor cores were active (for architectures supporting tensor cores).
- l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum: bytes read from global memory at L1 or texture cache level.
- dram__bytes.mean: total DRAM bytes transferred.
- sm__cycles_elapsed: elapsed cycles on an SM.
- sm__warps_active.avg.pct_of_peak_sustained_active: active warps percentage for occupancy insights.
These counters are vendor-specific and their names change across architectures and Nsight versions; the profiler UI usually offers human-readable abstractions (e.g., "Throughput", "Memory Workload", "SM Efficiency").

nvprof was the older command-line profiler that offered easy collection of many counters and trace outputs. Although deprecated, it is still used in some legacy contexts. CUPTI is the programmatic interface that underlies NVIDIA’s profilers; it allows you to subscribe to events, collect counters, and build custom tracers and tools. For research, CUPTI is valuable when you require automated data collection or need to capture a custom set of metrics across many runs.

Interpreting counters requires care. For example, global memory read/write bytes reported by the profiler might count cacheable accesses at multiple cache levels. Distinguish between L1, L2, and DRAM counters when reasoning about memory bandwidth. On modern GPUs, L1 cache and L2 cache behavior greatly affect performance; profiler-reported L2 hit rates and per-cacheline transfer sizes are often the key to understanding why a kernel is memory-bound.

Counters to prioritize:
- FLOP-related counters: number of FP operations executed, tensor core active cycles, integer operation counts (to identify conversion or index overhead).
- Memory counters: DRAM bytes read/written, L2 requests/hits, L1 transactions, cache hit/miss ratios.
- Occupancy/warp counters: active warps per SM, warp replays (due to divergent branches), warp execution efficiency.
- Pipeline and stall counters: memory dependency stalls, execution dependency stalls, structural hazards.
- Bandwidth and latency counters: average DRAM latency, achieved DRAM bandwidth.

A typical profiling workflow is:
1. Use Nsight Systems to find the top kernels and overall application behavior.
2. Use Nsight Compute on the hottest kernel(s) to collect detailed counters and source/assembly annotations.
3. If necessary, instrument code with CUDA events for custom timing or use CUPTI to capture counters programmatically for many runs.
4. Iterate by modifying kernels and re-profiling to validate improvements.

If you use other vendors' hardware, learn the equivalent tools and counters. ROCm tools provide similar metrics, but names and measurement semantics differ. Always corroborate profiler numbers with simple microbenchmarks: for example, verify reported memory bandwidth with a STREAM-like kernel or validate achieved FLOPs with a matrix multiply of known FLOP count.

# Ablation studies and controlled experiments

Ablation studies and controlled experiments are the scientific methodology for attributing observed performance differences to specific design choices. The goal is to change one factor at a time, measure the impact, and rule out confounding factors. Good ablations are reproducible, statistically powered, and targeted at key hypotheses.

Begin by formulating clear hypotheses: for example, "Using tile size 32 reduces global memory traffic and improves TFLOPs by 20% for head dim 64", or "enabling fp16 mixed precision with loss scaling maintains numerical fidelity while doubling arithmetic throughput". Each hypothesis should be testable with a controlled experiment.

Design your experiments to isolate the variable of interest. If comparing two kernel implementations, ensure they are identical except for the feature under test: same data layout, same numerical precision, identical input data, same GPU frequency/power settings, same compilation flags. When you change a single implementation detail (e.g., enabling shared-memory double buffering), measure before and after under identical conditions.

Use multiple repetitions to quantify variability. GPU runtimes can vary due to clock throttling, thermal effects, OS jitter, or background processes. For latency-sensitive measures, run each configuration for many iterations and report statistics: mean, median, standard deviation, and ideally confidence intervals. For throughput benchmarks, report sustained throughput over a long run rather than a single short measurement to avoid transient artifacts.

When an ablation yields a significant performance change, perform complementary measurements to explain why. If enabling a feature improves TFLOPs but increases DRAM traffic, then the improvement may come from increased locality or better instruction scheduling; inspect memory and instruction counters to verify. Use roofline reasoning: did arithmetic intensity change? Did bandwidth utilization change? Did occupancy increase? Presenting these correlated metrics strengthens the causal claim.

Factorial and sensitivity studies help when multiple parameters interact. A full factorial experiment sweeps all combinations of a small set of parameters (e.g., tile sizes A, B, C and prefetch counts X, Y) and reports interaction effects. For larger parameter spaces, use one-factor-at-a-time sweeps combined with occasional factorial points to detect interactions. Consider using response surface or design-of-experiments techniques if you have many parameters and want to build a predictive model of performance.

Document all environmental and experimental settings for reproducibility: GPU model, number of GPUs used, CUDA version, compiler flags, temperature/power constraints, and whether ECC is enabled. When reporting results, include baseline measurements (e.g., vendor library performance like cuBLAS/cuDNN) so readers can contextualize improvements.

Be wary of overfitting to a narrow benchmark. An optimization that benefits a single shape may harm others. Use parameter sweeps described earlier to demonstrate robustness. If an optimization requires special-case code paths for particular sizes, report both specialized and general-case performance and the frequency of those sizes in real workloads.

Finally, interpret ablation results conservatively. Correlation is not causation unless the experiment is well-controlled. If a change reduces performance variability, that is an important observation that may indicate mitigation of a non-deterministic bottleneck (e.g., reduced contention). Provide plausible microarchitectural explanations supported by profiler counters and, where possible, provide microbenchmarks that isolate specific mechanisms (e.g., a kernel that exercises only shared-memory vs only global memory paths).

Conclusion

Measuring and understanding GPU performance is both an art and a science. Accurate FLOP counting, thoughtful utilization metrics, systematic benchmark design, informed use of profiling tools, and carefully controlled ablation studies together provide the evidence needed to make reliable performance claims. Always be explicit about measurement conventions (FMA counting, precision), report complementary metrics (TFLOPs, memory bandwidth, occupancy), and document the experimental environment for reproducibility. With these practices, you can move from anecdotal performance statements to rigorous, interpretable, and reproducible performance analyses suitable for research and production optimization.
