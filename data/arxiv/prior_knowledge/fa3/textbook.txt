Introduction

Attention mechanisms, as used in modern sequence models, are built on a surprisingly compact set of linear-algebraic operations. To read research papers about attention or to derive new variants, you must be comfortable thinking of vectors, matrices, and batches as single algebraic objects and you must be able to manipulate them with rules such as associativity and distributivity. This chapter develops that foundation. We introduce consistent notation, review the core matrix and vector operations (multiplication, transpose, dot product), and then extend those ideas to batched and block matrix views that mirror how attention is implemented efficiently. We show how row-wise operations and reductions like rowmax and rowsum are used to compose the softmax attention, explain block-tiling notation used to reason about multi-head attention, and discuss the role of scaling factors (in particular the factor $1/\sqrt{d}$) and normalization. Finally, we collect the basic algebraic properties that are used repeatedly when manipulating attention formulas.

The chapter aims for intuition and careful attention to shapes and indices: when reading or writing formulas for attention, small shape mistakes or misunderstandings of which axes are summed vs. broadcasted are the most common errors. Wherever useful, examples and a few small calculations illustrate how the pieces fit together.

# Matrix and vector operations (multiply, transpose, dot-product)

Vectors and matrices are the fundamental data objects in linear algebra. A vector is typically a one-dimensional array of numbers and a matrix is a two-dimensional array. We will use the following conventional notation throughout:

- Lowercase bold letters such as $\mathbf{x} \in \mathbb{R}^d$ denote column vectors of length $d$.
- Uppercase letters such as $A \in \mathbb{R}^{m \times n}$ denote matrices with $m$ rows and $n$ columns.
- The element in the $i$th row and $j$th column of $A$ is $A_{ij}$.
- The transpose of $A$ is $A^\top\in\mathbb{R}^{n\times m}$, with $(A^\top)_{ji}=A_{ij}$.

Matrix multiplication is the operation that composes linear maps and is central to attention. If $A\in\mathbb{R}^{m\times n}$ and $B\in\mathbb{R}^{n\times p}$, their product $C=A B$ is a matrix in $\mathbb{R}^{m\times p}$ with entries
$$
C_{ik} = \sum_{j=1}^{n} A_{ij}\,B_{jk}.
$$
The inner summation over the shared index $j$ is the defining feature of matrix multiplication: the column dimension of the left factor must match the row dimension of the right factor.

When one of the factors is a vector, matrix multiplication reduces to familiar operations. If $\mathbf{v}\in\mathbb{R}^n$ (a column vector) and $A\in\mathbb{R}^{m\times n}$, then the product $A\mathbf{v}\in\mathbb{R}^m$ is a linear combination of the columns of $A$ with weights given by the entries of $\mathbf{v}$:
$$
(A\mathbf{v})_i = \sum_{j=1}^{n} A_{ij}\,v_j.
$$
If instead we have a row vector $\mathbf{u}^\top\in\mathbb{R}^{1\times m}$ and a matrix $A\in\mathbb{R}^{m\times n}$, then $\mathbf{u}^\top A\in\mathbb{R}^{1\times n}$ is a linear combination of the rows of $A$.

The dot product (also called inner product) of two vectors $\mathbf{x},\mathbf{y}\in\mathbb{R}^d$ is
$$
\mathbf{x}\cdot\mathbf{y} = \mathbf{x}^\top \mathbf{y} = \sum_{i=1}^{d} x_i y_i,
$$
a scalar. The dot product appears repeatedly in attention: attention scores are typically computed as dot products between query and key vectors.

Transpose plays a key role in changing a perspective from rows to columns. For example, if $X\in\mathbb{R}^{n\times d}$ contains $n$ row-vectors (for instance, $n$ token representations each of dimension $d$), then $X^\top\in\mathbb{R}^{d\times n}$ contains those same vectors as columns. This view is convenient because the product $X X^\top\in\mathbb{R}^{n\times n}$ contains all pairwise dot-products between rows of $X$:
$$
(X X^\top)_{ij} = X_{i:}\cdot X_{j:} = \sum_{k=1}^{d} X_{ik} X_{jk},
$$
where $X_{i:}$ denotes the $i$th row of $X$.

Two special cases are useful to keep in mind. First, the multiplication of a matrix with its transpose, $A A^\top$, forms a symmetric positive semidefinite matrix containing pairwise dot products of rows. Second, the product $A^\top A$ gives dot products of columns.

In attention, we often compute $QK^\top$ where $Q\in\mathbb{R}^{n\times d}$ is a matrix of query vectors (one row per token) and $K\in\mathbb{R}^{m\times d}$ is a matrix of key vectors. The result $QK^\top\in\mathbb{R}^{n\times m}$ has entries
$$
(QK^\top)_{ij} = Q_{i:}\cdot K_{j:},
$$
the dot-product score of query $i$ with key $j$. Understanding shapes is critical: $Q$ is $n\times d$, $K^\top$ is $d\times m$, and the product is $n\times m$.

# Batch and block matrix views

Practical neural network implementations operate on batches of sequences and often compute multiple attention heads in parallel. Thinking of these batched and multi-head computations as block matrices or higher-rank tensors clarifies how algebraic operations extend and how they are implemented efficiently.

A common representation is to treat a batch of $B$ sequences, each of length $n$, where each token is represented by a $d$-dimensional vector, as a single tensor $X\in\mathbb{R}^{B\times n\times d}$. This is a 3-D array, but many algebraic manipulations can be described using a block-matrix view. For example, consider stacking the $B$ matrices $X^{(b)}\in\mathbb{R}^{n\times d}$ (for $b=1,\dots,B$) vertically to form a tall matrix
$$
\widetilde{X} = \begin{bmatrix}
X^{(1)}\\[4pt]
X^{(2)}\\[4pt]
\vdots\\[4pt]
X^{(B)}
\end{bmatrix}
\in\mathbb{R}^{Bn\times d}.
$$
This block stacking makes certain operations simpler to write as a single matrix multiplication: a shared linear map $W\in\mathbb{R}^{d\times d'}$ applied to every example in the batch corresponds to $\widetilde{X}W\in\mathbb{R}^{Bn\times d'}$, which is equivalent to independently applying $W$ to each $X^{(b)}$.

When there are multiple attention heads, each head can be seen as a separate linear transformation on the $d$-dimensional token vectors. Suppose there are $h$ heads and each head has dimension $d_h$, typically with $h d_h = d$. The query, key, and value projections can be represented in a single matrix using block columns. For instance, a combined projection for queries can be written as
$$
W_Q = \begin{bmatrix} W_{Q,1} & W_{Q,2} & \cdots & W_{Q,h} \end{bmatrix}
\in\mathbb{R}^{d\times (h d_h)},
$$
where each $W_{Q,\ell}\in\mathbb{R}^{d\times d_h}$ maps the input to the $\ell$th head's query space. Applying $W_Q$ to $X\in\mathbb{R}^{n\times d}$ gives $X W_Q \in \mathbb{R}^{n\times (h d_h)}$, which can be interpreted as concatenated queries for all heads. Reshaping this result into $(n,h,d_h)$ or $(h,n,d_h)$ layouts is an implementation detail; algebraically, we treat it as partitioning columns into $h$ blocks.

In some derivations it is convenient to view batched multi-head computations as block matrices across both batch and head dimensions. For example, if we form block-diagonal matrices that place each head or each batch entry on the diagonal, then independent computations become a single big block-diagonal multiplication. Concretely, suppose we have $h$ independent $n\times n$ attention score matrices $S_1,\dots,S_h$. The block-diagonal matrix
$$
\operatorname{blkdiag}(S_1,\dots,S_h)
=
\begin{bmatrix}
S_1 & 0 & \cdots & 0\\[4pt]
0 & S_2 & \cdots & 0\\[4pt]
\vdots & \vdots & \ddots & \vdots\\[4pt]
0 & 0 & \cdots & S_h
\end{bmatrix}
\in\mathbb{R}^{hn\times hn}
$$
encapsulates the $h$ independent self-attention computations as a single matrix multiplication on suitably stacked inputs. Using block matrices for reasoning is especially helpful when proving identities that mix heads or batches, because it reduces many cases to ordinary matrix algebra.

The tensor view and the block-matrix view are equivalent descriptions; one chooses whichever makes a derivation clearer. The tensor view is natural for describing shapes such as $(B,h,n,d_h)$ used in implementation; the block/block-diagonal view is handy for algebraic manipulations that rely on standard matrix rules.

# Row-wise operations and reductions (rowmax, rowsum)

Attention uses operations that act independently on rows (or columns) of a matrix. Two common row-wise reductions are rowmax and rowsum. Precise understanding of these operations and of broadcasting rules is important when writing formulas for softmax attention and its numerically stable implementations.

Let $A\in\mathbb{R}^{n\times m}$. Define the row-wise maximum vector $\operatorname{rowmax}(A)\in\mathbb{R}^n$ by
$$
\operatorname{rowmax}(A)_i = \max_{1\le j\le m} A_{ij}.
$$
Similarly, the row-wise sum vector $\operatorname{rowsum}(A)\in\mathbb{R}^n$ is
$$
\operatorname{rowsum}(A)_i = \sum_{j=1}^{m} A_{ij}.
$$
These vectors collect a scalar per row; using them in further computations requires attention to broadcasting: for example, to subtract the row maximum from each element in its row, one writes
$$
B_{ij} = A_{ij} - \operatorname{rowmax}(A)_i.
$$
In matrix notation, this subtraction is often implemented by expanding (or broadcasting) $\operatorname{rowmax}(A)$ to an $n\times m$ matrix by repeating the vector across columns, but algebraically we treat it as a per-row operation.

Row-wise reductions are central to the numerical stability of the softmax function. The row-wise softmax of $A\in\mathbb{R}^{n\times m}$ produces a matrix $P\in\mathbb{R}^{n\times m}$ whose $i$th row is a probability distribution over the $m$ columns:
$$
P_{ij} = \frac{\exp(A_{ij})}{\sum_{k=1}^{m}\exp(A_{ik})}.
$$
Computationally, it is standard to shift each row by its maximum before exponentiating to avoid overflow:
$$
P_{ij} = \frac{\exp(A_{ij} - \operatorname{rowmax}(A)_i)}{\sum_{k=1}^{m}\exp(A_{ik} - \operatorname{rowmax}(A)_i)}.
$$
Here the subtraction $A_{ij} - \operatorname{rowmax}(A)_i$ is a row-wise subtraction. The denominator is just $\operatorname{rowsum}(\exp(A - \operatorname{rowmax}(A)))_i$.

Another useful row-wise operation is normalization by the rowsum. Given nonnegative $B\in\mathbb{R}^{n\times m}$ where each row sums to a positive number, the row-normalized matrix is
$$
\widetilde{B}_{ij} = \frac{B_{ij}}{\operatorname{rowsum}(B)_i}.
$$
That is, each row is divided by its sum, turning each row into a probability distribution.

Row-wise max and sum also appear when computing attention outputs. If $P\in\mathbb{R}^{n\times m}$ are attention weights and $V\in\mathbb{R}^{m\times d}$ are value vectors (rows of $V$), then the attended outputs are computed as a weighted row-combination:
$$
\operatorname{Out} = P V \in\mathbb{R}^{n\times d},
$$
where the $i$th output row is $\sum_{j=1}^{m} P_{ij} V_{j:}$. Note that each row of $P$ is a weights vector applied to the rows of $V$.

Understanding which operations reduce along which axes and how the results broadcast back across other axes is essential. In attention formulas, pay careful attention to whether reductions are over keys (columns of the score matrix) or over queries (rows), as this determines the shape and location of normalization factors such as denominators of softmax.

# Block matrices and tiling notation

Block matrices and tiling notation give concise ways to represent structured matrices built from smaller blocks. This is particularly useful for multi-head attention and for describing how weights are shared or partitioned across heads.

A block matrix partitions a matrix into submatrices. For example, partitioning an $m\times m$ matrix into four blocks yields
$$
M = \begin{bmatrix}
A & B\\
C & D
\end{bmatrix},
$$
where $A\in\mathbb{R}^{p\times p}$, $B\in\mathbb{R}^{p\times (m-p)}$, etc. Block multiplication follows the same rules as ordinary multiplication, with block sums and products:
$$
\begin{bmatrix}
A & B\\
C & D
\end{bmatrix}
\begin{bmatrix}
E & F\\
G & H
\end{bmatrix}
=
\begin{bmatrix}
AE+BG & AF+BH\\
CE+DG & CF+DH
\end{bmatrix},
$$
provided the inner block dimensions match. This property allows reasoning about independent components and mixing between blocks.

Tiling notation is often used to describe repeating a smaller matrix across rows and/or columns. If $U\in\mathbb{R}^{n\times m}$ is a small matrix and we tile it vertically $p$ times and horizontally $q$ times, we obtain a large matrix denoted by
$$
\operatorname{tile}(U; p,q) = \begin{bmatrix}
U & U & \cdots & U\\[4pt]
U & U & \cdots & U\\[4pt]
\vdots & \vdots & \ddots & \vdots\\[4pt]
U & U & \cdots & U
\end{bmatrix}
\in\mathbb{R}^{pn\times qm}.
$$
Tiling appears when broadcasting a row vector into a full matrix for row-wise subtraction or when forming repeated structures in block-diagonal or block-constant matrices.

Multi-head attention frequently uses a concatenation followed by a reshaping (or the reverse). Stacking $h$ matrices $M_1,\dots,M_h$ of the same shape horizontally yields a block-row
$$
\begin{bmatrix} M_1 & M_2 & \cdots & M_h \end{bmatrix}.
$$
When each $M_\ell$ is a projection for head $\ell$, this concatenation can be applied in one matrix multiplication and then reshaped into separate heads. Conversely, to apply different matrices to different heads without interaction, one can build a block-diagonal matrix
$$
\operatorname{blkdiag}(M_1,\dots,M_h)
$$
and multiply it by a vertically stacked input.

The notation and intuition of blocking and tiling allow compact expressions for shared vs. independent computations. For example, suppose you have a shared linear projection $W$ that should be applied to each of $h$ heads independently. You can represent the full projection as a tensor of shape $(h,d,d_h)$ or as the block matrix
$$
I_h \otimes W \in\mathbb{R}^{h d \times h d_h},
$$
where $\otimes$ denotes the Kronecker product and $I_h$ is the $h\times h$ identity. The Kronecker product constructs a block-diagonal matrix with $W$ on each diagonal block and zeros elsewhere, succinctly expressing independent identical transforms.

Block matrices are also used to reason about attention masks. An attention mask that forbids attention from later tokens to earlier tokens in causal attention can be encoded as a binary block-triangular mask matrix $M\in\{0, -\infty\}^{n\times n}$, where $M_{ij}=-\infty$ when position $i$ should not attend to position $j$. Using block notation, one can compose these masks with tiled batch or head dimensions by simple repeated blocks.

# Scaling factors and normalization (e.g., 1/sqrt(d))

A crucial numeric and statistical detail in dot-product attention is scaling the raw dot products by a factor $1/\sqrt{d}$, where $d$ is the dimensionality of the query and key vectors. The standard scaled dot-product attention computes attention weights from query matrix $Q\in\mathbb{R}^{n\times d}$ and key matrix $K\in\mathbb{R}^{m\times d}$ as
$$
S = \frac{Q K^\top}{\sqrt{d}}.
$$
Why is the factor $1/\sqrt{d}$ important? It helps keep the magnitudes of the dot products in a regime where the softmax function has reasonable gradients.

To see the intuition, consider entries of $Q$ and $K$ as random with zero mean and variance $\sigma^2$ and assume (for intuition) that different dimensions are independent. Then the dot product of two $d$-dimensional vectors is a sum of $d$ independent terms, so its variance grows roughly linearly with $d$:
$$
\operatorname{Var}(\mathbf{q}\cdot\mathbf{k}) \approx d \sigma^4.
$$
Without scaling, as $d$ increases the raw dot products become larger in magnitude, so after exponentiation in softmax they either vanish or explode: large positive scores dominate, making the softmax outputs near one-hot, while large negative scores vanish. Scaling by $1/\sqrt{d}$ normalizes the variance to be independent of $d$:
$$
\operatorname{Var}\!\left(\frac{\mathbf{q}\cdot\mathbf{k}}{\sqrt{d}}\right) \approx \sigma^4,
$$
keeping the logits in a consistent scale for all $d$ and helping to stabilize gradients during training.

More generally, normalization and scaling are used across attention and neural networks to control the distribution of activations. Layer normalization, batch normalization, and similar techniques are applied to stabilize optimization. In attention, one often additionally scales projections or output layers to ensure consistent variance. For example, the output of multi-head attention concatenates $h$ heads each of dimension $d_h$. When recombining these heads with a learned matrix $W_O\in\mathbb{R}^{(h d_h)\times d}$, one may initialize $W_O$ so the variance of the output does not depend on $h$. These concerns underlie many architectural choices and initialization schemes.

There is also a more algebraic viewpoint: scalar multiplication distributes over matrix multiplication. Thus scaling the score matrix by $1/\sqrt{d}$ is equivalent to scaling either $Q$ or $K$:
$$
\frac{Q K^\top}{\sqrt{d}} = \left(\frac{Q}{\sqrt{d}}\right) K^\top = Q \left(\frac{K}{\sqrt{d}}\right)^\top.
$$
This identity is helpful when reasoning about where to place the scaling in implementations or in derivations: one may choose to scale the projections themselves rather than the scores, depending on convenience.

# Basic properties used in attention algebra (distributivity, associativity)

Writing and simplifying attention formulas relies on a handful of algebraic properties of matrices and scalars. These properties are the same as for ordinary algebra but applied with attention to dimensions and transposes. Here we collect the most used ones and illustrate how they appear in attention.

Associativity of matrix multiplication: Given matrices $A\in\mathbb{R}^{m\times n}$, $B\in\mathbb{R}^{n\times p}$, and $C\in\mathbb{R}^{p\times q}$, the product is associative:
$$
(A B) C = A (B C).
$$
Although the products produce the same final matrix, the parenthesization affects intermediate shapes and computational cost. In attention, associativity is used to regroup computations, for example when rewriting $P V$ where $P$ depends on $QK^\top$; one can sometimes push sums or factors through parentheses to enable more efficient evaluation.

Distributivity of matrix multiplication over addition: For conformable matrices,
$$
A(B+C) = AB + AC, \qquad (A+B)C = AC + BC.
$$
This is useful when decomposing attention computations into a sum of simpler terms. For example, if keys are expressed as a sum of two components $K = K^{(1)} + K^{(2)}$, then
$$
Q K^\top = Q (K^{(1)})^\top + Q (K^{(2)})^\top,
$$
so attention can be linearized over additive components of the keys.

Scalar multiplication: For a scalar $\alpha$, matrices satisfy
$$
(\alpha A)B = \alpha (A B) = A(\alpha B).
$$
This property underpins the placement of the $1/\sqrt{d}$ scaling factor: you can equivalently scale $Q$, $K$, or the product.

Transpose identities: The transpose reverses the order of multiplication:
$$
(A B)^\top = B^\top A^\top.
$$
This identity helps when converting between row-wise and column-wise perspectives. For example, if $X\in\mathbb{R}^{n\times d}$, then $(X W)^\top = W^\top X^\top$.

Trace and cyclicity (used less often but helpful): The trace of a product is invariant under cyclic permutations:
$$
\operatorname{tr}(A B C) = \operatorname{tr}(B C A) = \operatorname{tr}(C A B).
$$
While trace seldom appears directly in standard attention equations, it is used when reasoning about similarity measures and when deriving gradients.

Elementwise (Hadamard) product: Denoted by $\odot$, the Hadamard product is defined per-element. For $A,B\in\mathbb{R}^{n\times m}$,
$$
(A\odot B)_{ij} = A_{ij} B_{ij}.
$$
Although attention primarily uses matrix multiplication, elementwise operations appear in masks (multiplying by binary masks), in applying nonlinearities like dropout, and in scaling factors applied per position.

Broadcasting rules: While not a pure algebraic law, understanding broadcasting is essential for correct formulas. A row-wise vector $r\in\mathbb{R}^n$ can be broadcasted to an $n\times m$ matrix by repeating across columns; similarly a column vector can be repeated across rows. Algebraic manipulations with reductions rely on consistent broadcasting: for instance, dividing a matrix by a rowsum vector means dividing each row by its corresponding scalar.

Probability-normalization identities: When attention weights are produced by softmax, they satisfy row-wise normalization:
$$
P \mathbf{1}_m = \mathbf{1}_n,
$$
where $\mathbf{1}_m\in\mathbb{R}^m$ is the all-ones vector and $P\in\mathbb{R}^{n\times m}$ has rows that sum to 1. This identity is often used to simplify expressions such as $P \mathbf{v}$ when $\mathbf{v}$ has special structure.

Putting these properties together gives great flexibility in rearranging attention formulas. For example, given $P=\operatorname{softmax}(QK^\top/\sqrt{d})$ and $O = P V$, one can reason about gradients, approximations, and low-rank decompositions by distributing, grouping, and transposing factors. The algebraic rules guarantee the manipulations are valid provided the shapes remain compatible.

Introduction

The Transformer is a neural network architecture built almost entirely from attention mechanisms and simple feed-forward layers. At the heart of the Transformer is the attention operation, which allows the model to dynamically weight and aggregate information from different positions in a sequence. Understanding attention — how queries, keys, and values are constructed, how multiple attention heads work in parallel, how numerical scaling and softmax are applied, and how masking controls information flow — is essential to understanding the Transformer encoder/decoder layers and modern large language models (LLMs). This chapter explains these concepts in a connected way, with careful attention to the shapes and computations you will encounter in code and research papers.

# Self-attention: queries (Q), keys (K), values (V) and attention output

Self-attention is an operation that produces a representation of each position in a sequence by attending to all positions in that same sequence. The basic ingredients are three sets of vectors for each position: queries, keys, and values. Intuitively, a query asks "what information do I want right now?", while keys describe "what information does each position offer?" and values are the content that will be aggregated according to how well keys match the query.

Concretely, suppose you have a sequence of $T$ input vectors (for example, token embeddings, or the outputs of a previous layer) arranged into a matrix $X \in \mathbb{R}^{T \times d_{\text{model}}}$. Self-attention begins by producing three linear projections of $X$:
\[
Q = XW_Q,\qquad K = XW_K,\qquad V = XW_V,
\]
where $W_Q, W_K, W_V \in \mathbb{R}^{d_{\text{model}} \times d_k}$ (often $d_k$ is equal to $d_v$, but we will denote head key and value dimensionalities generically as $d_k$ and $d_v$). Here $Q, K \in \mathbb{R}^{T \times d_k}$ and $V \in \mathbb{R}^{T \times d_v}$.

For a single query vector $q_i$ (the $i$-th row of $Q$), we compute its compatibility with each key $k_j$ (the $j$-th row of $K$) by a similarity function. The most common choice is the dot product. The unnormalized attention score from position $i$ to position $j$ is
\[
\text{score}(i,j) = q_i \cdot k_j = q_i^\top k_j.
\]
Collecting all scores yields the score matrix $S = QK^\top \in \mathbb{R}^{T \times T}$, where $S_{ij}$ is how compatible position $i$'s query is with position $j$'s key.

These raw scores are converted into positive weights via a softmax (we will cover the exact axis later). The attention weights applied to the values produce the output at each position:
\[
\text{Attention}(Q,K,V) = \operatorname{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V.
\]
This produces an output matrix in $\mathbb{R}^{T \times d_v}$, where each output vector is a weighted sum of the rows of $V$, with weights determined by how well $q_i$ matched each $k_j$.

Several points are important to internalize. First, attention is content-dependent: different queries will attend to different keys, so representations can dynamically aggregate context. Second, self-attention is permutation-sensitive through positional encodings or other position-aware mechanisms (the raw dot product does not encode positions by itself). Third, the matrices $W_Q,W_K,W_V$ are learned weights, so the model learns how to form queries, keys, and values that are useful for the task.

# Multi-head attention: parallel heads and concatenation

Multi-head attention extends this idea by computing several independent attention "heads" in parallel and then combining their outputs. The motivation is that different heads can specialize to capture different kinds of relationships: one head might focus on short-range syntactic relations, another on long-range topical information, another on coreference, and so on.

Formally, if we use $H$ heads, we learn separate projection matrices for each head: for head $h$ we have
\[
Q^{(h)} = XW_Q^{(h)},\qquad K^{(h)} = XW_K^{(h)},\qquad V^{(h)} = XW_V^{(h)}.
\]
Each projection typically maps into a smaller subspace so that the total computational budget is comparable to a single-head attention with dimension $d_{\text{model}}$. A common design is to set each head dimension to $d_k = d_v = d_{\text{model}}/H$, so that concatenating $H$ heads returns to dimension $d_{\text{model}}$.

Each head computes its own attention:
\[
\text{head}_h = \operatorname{softmax}\!\left(\frac{Q^{(h)} {K^{(h)}}^\top}{\sqrt{d_k}}\right)V^{(h)} \quad\in\mathbb{R}^{T \times d_v}.
\]
After computing all $H$ heads, we concatenate their outputs along the feature dimension and apply a final linear projection:
\[
\text{MultiHead}(X) = \text{Concat}(\text{head}_1,\dots,\text{head}_H)W_O,
\]
where $\text{Concat}(\cdot)\in\mathbb{R}^{T \times (H d_v)}$ and $W_O \in \mathbb{R}^{(H d_v) \times d_{\text{model}}}$. If $d_v = d_k = d_{\text{model}}/H$ then the concatenated dimension is $d_{\text{model}}$, making $W_O$ a square $d_{\text{model}}\times d_{\text{model}}$ matrix in the common configuration.

Why multiple heads? There are a few practical and conceptual reasons. First, splitting features into multiple subspaces allows each head to focus on different subspaces of the representation space and thus capture multiple relationships simultaneously. Second, using smaller per-head dimensions keeps computational cost and parameter counts manageable while providing representational diversity. Finally, because each head forms its own set of similarity scores and weightings, the model can represent more complex, multi-faceted attention patterns than a single head could.

# Scaling and softmax application (row-wise softmax)

Two numerical details in the attention formula deserve close attention because they materially affect learning dynamics and the semantics of the weights: scaling by $\sqrt{d_k}$ and the axis of the softmax.

Scaling: The raw dot products $q_i^\top k_j$ grow in magnitude as the dimensionality of the vectors $d_k$ increases. If those dot products are too large in magnitude, the subsequent softmax will push probabilities close to the edges (very small or very large), leading to tiny gradients during learning (saturation). To counteract this effect, the Transformer paper divides the dot products by $\sqrt{d_k}$, producing
\[
S = \frac{QK^\top}{\sqrt{d_k}}.
\]
This scaling keeps the variance of the scaled dot products roughly constant with respect to $d_k$ under typical random-initialization assumptions, stabilizing gradients and training.

Softmax application and row-wise normalization: After scaling, we apply a softmax to convert scores into nonnegative weights that sum to 1. Importantly, the softmax is applied row-wise across keys for each query. Concretely, if $S \in \mathbb{R}^{T \times T}$, then for each query position $i$ we define
\[
A_{i,:} = \operatorname{softmax}(S_{i,:}) = \frac{\exp(S_{i,:})}{\sum_{j=1}^{T} \exp(S_{i,j})}.
\]
Thus $A_{i,j}$ is the attention weight from query position $i$ to key position $j$, and the weights across $j$ for a fixed $i$ sum to 1. The final output matrix is $A V$, where each row is a convex combination of the rows of $V$ with the corresponding row of $A$ as weights.

This row-wise softmax means attention is computed per output position: each output vector is a weighted sum over all value vectors, and the weights are specific to that output position. In many implementations that process batches, we compute softmax along the last axis corresponding to key positions.

Practical note on stability: In implementations, for numerical stability we often subtract the maximum score in each row before exponentiating:
\[
\operatorname{softmax}(s) = \frac{\exp(s - \max_j s_j)}{\sum_j \exp(s - \max_j s_j)}.
\]
When introducing masks (next section) we typically add a large negative number (like $-10^{9}$) to scores that should be ignored before applying softmax so that their normalized weight becomes effectively zero.

# Causal (autoregressive) masking vs. non-causal attention

Masking controls which key positions each query can attend to. There are two principal regimes in Transformer models, with different masks: non-causal (bidirectional) attention and causal (autoregressive) attention.

Non-causal (bidirectional) attention: In encoder stacks and in models that allow each position to see the whole sequence (for example, BERT-style models used for masked-language-model pretraining), attention is non-causal: each query is allowed to attend to all key positions. The mask in this case is typically all zeros (no positions masked), so attention weights are computed over all positions. This lets the representation for each position use information from both left and right contexts. Non-causal attention is appropriate when you want contextualized representations that can use future as well as past context and when you are not generating autoregressively.

Causal (autoregressive) masking: In decoder stacks and in autoregressive LLMs where the model must predict the next token given only previous tokens, attention must be causal: position $i$ may only attend to positions $\le i$. In practice, this is implemented by adding a mask matrix $M \in \{0,-\infty\}^{T\times T}$ to the scaled score matrix before the softmax:
\[
\tilde S_{ij} = \frac{q_i^\top k_j}{\sqrt{d_k}} + M_{ij},
\]
where $M_{ij} = 0$ if key position $j$ is allowed for query $i$, and $M_{ij} = -\infty$ (or a very large negative number) if it is disallowed. For causal masking, $M_{ij} = -\infty$ for $j>i$ so that after softmax, $A_{i,j} = 0$ for all $j>i$. This ensures that when computing the representation or prediction for position $i$, information from future positions cannot leak in.

Which mask to use depends on task: encoder-only or masked-language-modeling objectives use non-causal attention for full-context representations; decoder-only autoregressive LLMs use causal masking so generation is left-to-right consistent. There are also encoder-decoder models (original Transformer for translation) where the encoder uses non-causal attention and the decoder uses both causal self-attention (so the decoder cannot see future positions of the target sequence) and encoder-decoder cross-attention where decoder queries attend to encoder keys/values (and these cross-attention computations are usually non-causal since the encoder produced the whole source sequence).

# Computation graph and where attention sits in Transformer blocks

The attention mechanism is a module inside a Transformer block. A full Transformer layer combines attention with residual connections, layer normalization (or pre-norm variants), and a position-wise feed-forward network. There are two canonical block forms in the original Transformer: encoder blocks and decoder blocks.

Encoder block (one layer): The standard encoder layer contains a self-attention sublayer followed by a feed-forward sublayer, each wrapped by residual connections and layer normalization. Using the "post-norm" notation from the original paper, the computations are:
\[
\begin{aligned}
\text{SA\_out} &= \operatorname{MultiHead}(X), \\
X' &= \operatorname{LayerNorm}(X + \text{SA\_out}), \\
\text{FF\_out} &= \operatorname{FFN}(X'), \\
X_{\text{next}} &= \operatorname{LayerNorm}(X' + \text{FF\_out}).
\end{aligned}
\]
Here $\operatorname{FFN}$ is a two-layer position-wise feed-forward network applied independently at each position: usually $\operatorname{FFN}(x) = \max(0,xW_1 + b_1)W_2 + b_2$ (ReLU or GELU nonlinearity) with an inner dimension larger than $d_{\text{model}}$.

Decoder block (one layer): The decoder layer contains three sublayers in sequence: causal self-attention, encoder-decoder cross-attention, and the feed-forward network. Each sublayer has its own residual connection and layer norm:
\[
\begin{aligned}
\text{CausalSA\_out} &= \operatorname{MultiHead}_{\text{causal}}(Y), \\
Y' &= \operatorname{LayerNorm}(Y + \text{CausalSA\_out}), \\
\text{CrossAtt\_out} &= \operatorname{MultiHead}_{\text{cross}}(Y', \, K_{\text{enc}}, \, V_{\text{enc}}), \\
Y'' &= \operatorname{LayerNorm}(Y' + \text{CrossAtt\_out}), \\
\text{FF\_out} &= \operatorname{FFN}(Y''), \\
Y_{\text{next}} &= \operatorname{LayerNorm}(Y'' + \text{FF\_out}).
\end{aligned}
\]
In the cross-attention step, queries come from the decoder (the target-side representations), while keys and values come from the encoder outputs ($K_{\text{enc}},V_{\text{enc}}$). Cross-attention is typically non-causal with respect to source tokens.

Placement in computation graph: In the overall Transformer (stacking multiple layers), attention modules appear at each layer, allowing interactions between positions at every depth. The residual connections mean that the gradient flows both through the attention sublayer and directly from the output to the input, easing optimization. In pre-norm variants, the layer norm is applied before attention and feed-forward sublayers; both formulations are used in practice and affect stability and performance.

During autoregressive generation with causal masking, another important computation-graph consideration is caching: when generating token by token, key and value projections for previously generated tokens can be cached so that we do not recompute them every step. This changes the computation graph during inference: each new step computes the new query and its scores versus cached keys, rather than recomputing all keys and values for the whole sequence.

# Practical dimensions: batch, sequence length, head dimension, hidden dimension

Understanding the tensor shapes that flow through attention is critical for implementing and debugging models and for reasoning about computational and memory cost.

Typical symbols and meanings:
- $B$: batch size (number of sequences processed in parallel).
- $T$: sequence length (number of tokens per sequence; may vary and be padded).
- $H$: number of attention heads.
- $d_{\text{model}}$: hidden dimension of the model (also called model width).
- $d_k$: dimensionality of keys and queries for each head (often $d_k = d_{\text{model}}/H$).
- $d_v$: dimensionality of values for each head (often $d_v = d_{\text{model}}/H$).

A standard pipeline in code uses batched tensors. The input embedding tensor typically has shape $(B, T, d_{\text{model}})$. The per-head linear projections can be computed with a single linear layer that maps $d_{\text{model}}$ to $H \times d_k$ and is then reshaped. Concretely, one common pattern is:

1. Compute combined projections: Let $W_Q^{\text{all}} \in \mathbb{R}^{d_{\text{model}} \times (H d_k)}$. Then
\[
Q_{\text{flat}} = X W_Q^{\text{all}} \in \mathbb{R}^{B \times T \times (H d_k)}.
\]
2. Reshape into heads: reshape $Q_{\text{flat}}$ to $Q \in \mathbb{R}^{B \times H \times T \times d_k}$. Similarly for $K$ and $V$.

3. Compute attention scores per head: for each head, compute the scaled dot-product along the sequence length dimension. Implemented with batched matmuls:
\[
S \in \mathbb{R}^{B \times H \times T \times T},\qquad S_{b,h,i,j} = \frac{Q_{b,h,i,:} \cdot K_{b,h,j,:}}{\sqrt{d_k}}.
\]
4. Apply mask and softmax along the last axis (the key index $j$), producing attention weights $A \in \mathbb{R}^{B \times H \times T \times T}$.

5. Weight the values: perform batched matmul $A V$ per head to obtain outputs $\text{head\_out} \in \mathbb{R}^{B \times H \times T \times d_v}$.

6. Concatenate heads: reshape to $(B, T, H d_v)$ and apply the output matrix $W_O$ to produce $(B, T, d_{\text{model}})$.

Memory and compute costs: The dominant cost is forming the score tensor $S$ which is size $B \times H \times T \times T$, and the matrix multiplications that involve $T\times T$ work. Thus both compute and memory scale as $O(B H T^2 d_k)$ or, substituting typical equalities $d_k = d_v = d_{\text{model}}/H$, $O(B T^2 d_{\text{model}})$. This quadratic dependence on sequence length $T$ is important: doubling $T$ increases time and memory roughly fourfold for these attention computations, which motivates many efficient-attention approximations when $T$ is very large.

Examples of common dimensions: in many transformer models $d_{\text{model}}$ is 512, 768, 1024 or larger. For $d_{\text{model}}=768$ and $H=12$, each head has $d_k = 64$. For $d_{\text{model}}=1024$ and $H=16$, each head has $d_k = 64$ as well. The inner dimension of the FFN is often $d_{\text{ff}}=4 d_{\text{model}}$ (e.g., 3072 for $d_{\text{model}}=768$). Batch sizes $B$ and sequence lengths $T$ are chosen according to hardware and task needs; during pretraining, $T$ may be 1024 or 2048 or larger, while during inference for LLMs $T$ is often limited by memory constraints.

# Putting it together for large language models

Large language models are typically decoder-only stacks of many Transformer layers operating autoregressively, with causal masking enforced in all self-attention sublayers. At each generation step during training, the model is typically fed an entire sequence and trained to predict the next token at each position; causal masking ensures each prediction only uses leftward context. During inference, token-by-token generation uses caching of projected keys/values to avoid recomputing past values; mathematically the same attention equations apply but the computation graph and batching differ.

In practice, engineers and researchers must pay attention to the precise tensor shapes, the placement of layer norms (pre-norm vs post-norm), caching strategies for inference, numerical stability (scaling and stable softmax), and masking semantics (e.g., padding masks to ignore padding tokens, causal masks for autoregression, and attention masks for sparsity patterns). Multi-head attention gives expressive capacity while keeping the per-head computation small; scale and softmax choices ensure stable training; masks enforce the directional constraints required by the task; and the integration into the Transformer block with residuals and feed-forward networks yields deep, trainable stacks.

Summary

This chapter covered the mechanics and intuition behind self-attention and multi-head attention, the reason for scaling and the row-wise softmax, the role and implementation of causal versus non-causal masks, where attention sits inside Transformer encoder and decoder blocks, and the practical tensor dimensions you will encounter when implementing or reading about these models. With these concepts and the dimension-aware view of the computations, you should be able to read Transformer-based papers with clarity and implement attention modules in modern deep-learning frameworks.

Introduction

Attention layers are a central building block in modern deep learning architectures for sequence data, especially transformers. During training we need not only the forward computation that produces outputs from queries, keys, and values, but also the backward computation that yields gradients with respect to parameters and inputs. This chapter derives the backward pass of the canonical scaled dot-product attention module, explains the softmax derivative in a form suitable for efficient implementation, shows compact matrix formulations of the gradient computations, and discusses the practical trade-offs between storing intermediate quantities versus recomputing them during the backward pass. Emphasis is placed on intuition, computational structure, and the memory/computation trade-offs that determine implementation choices in real systems.

We use the standard attention notation throughout. Let $Q\in\mathbb{R}^{B\times n_q\times d}$ be the queries, $K\in\mathbb{R}^{B\times n_k\times d}$ the keys, $V\in\mathbb{R}^{B\times n_k\times d_v}$ the values (where $d_v$ may equal $d$), and $B$ the batch size. The attention scores (pre-softmax) are
$S = \frac{1}{\sqrt{d}}\,Q K^\top \in\mathbb{R}^{B\times n_q\times n_k}$,
the attention probabilities (after softmax over keys for each query) are
$P = \mathrm{softmax}(S)$ (softmax applied along the $n_k$ dimension for each query), and the output is
$O = P V \in\mathbb{R}^{B\times n_q\times d_v}$.
We will derive gradients in the order natural for backpropagation: given $\frac{\partial \mathcal{L}}{\partial O}$, compute $\frac{\partial \mathcal{L}}{\partial V}$, $\frac{\partial \mathcal{L}}{\partial P}$, $\frac{\partial \mathcal{L}}{\partial S}$, $\frac{\partial \mathcal{L}}{\partial Q}$ and $\frac{\partial \mathcal{L}}{\partial K}$, and discuss matrix forms and implementation issues.

# Chain rule applied to attention: dO → dV, dP, dS, dQ, dK

We start from the final output relationship $O = P V$. Suppose the loss $\mathcal{L}$ produces an upstream gradient $\mathrm{d}O \equiv \frac{\partial \mathcal{L}}{\partial O}\in\mathbb{R}^{B\times n_q\times d_v}$. By the chain rule the gradients flow through the multiplication $O = P V$ to $V$ and to $P$.

The gradient with respect to $V$ is the standard matrix product gradient:
$\mathrm{d}V = P^\top \,\mathrm{d}O$,
where the transpose operates on the $n_q$ and $n_k$ axes respectively: for each batch,
$\mathrm{d}V[b] = P[b]^\top \,\mathrm{d}O[b]$,
so $\mathrm{d}V\in\mathbb{R}^{B\times n_k\times d_v}$. Intuition: each value vector $V_{j}$ contributes to many outputs $O_i$ weighted by attention probabilities $P_{ij}$, so the gradient on a particular $V_j$ accumulates across queries $i$ via the weights $P_{ij}$.

The gradient with respect to $P$ is
$\mathrm{d}P = \mathrm{d}O\, V^\top$,
again in batch form: $\mathrm{d}P[b] = \mathrm{d}O[b]\,V[b]^\top$, giving shape $\mathbb{R}^{B\times n_q\times n_k}$. Intuition: changing a probability $P_{ij}$ affects all components of the output $O_i$ by scaling the contribution of $V_j$; the inner product between $\mathrm{d}O_i$ and $V_j$ gives the sensitivity.

Next we must propagate through the softmax: $P = \mathrm{softmax}(S)$, applied across the key dimension for each query. Given $\mathrm{d}P$ we need $\mathrm{d}S$. This step requires the softmax Jacobian-vector product, which we discuss in the next section.

After obtaining $\mathrm{d}S$, we propagate through $S = \frac{1}{\sqrt{d}} Q K^\top$. Gradients with respect to $Q$ and $K$ follow the usual matrix-product rules:
$\mathrm{d}Q = \frac{1}{\sqrt{d}}\,\mathrm{d}S\,K$,
$\mathrm{d}K = \frac{1}{\sqrt{d}}\,\mathrm{d}S^\top Q$,
where again the batch and axis shapes must be respected (for batch element $b$, $\mathrm{d}Q[b] = \frac{1}{\sqrt{d}} \,\mathrm{d}S[b]\, K[b]$ and $\mathrm{d}K[b] = \frac{1}{\sqrt{d}}\,\mathrm{d}S[b]^\top Q[b]$). Intuitively, $\mathrm{d}S_{ij}$ tells how sensitivity to changing the dot product between query $i$ and key $j$ translates into changes for $Q_i$ and $K_j$. The symmetric algebraic structure mirrors forward computation but with roles swapped: $\mathrm{d}Q$ multiplies the score-gradient by the keys; $\mathrm{d}K$ multiplies the transposed score-gradient by the queries.

We have thus the full chain:
1. From $\mathrm{d}O$ get $\mathrm{d}V = P^\top \mathrm{d}O$ and $\mathrm{d}P = \mathrm{d}O\,V^\top$.
2. From $\mathrm{d}P$ get $\mathrm{d}S$ via the softmax Jacobian-vector product.
3. From $\mathrm{d}S$ get $\mathrm{d}Q = \frac{1}{\sqrt{d}} \mathrm{d}S\,K$ and $\mathrm{d}K = \frac{1}{\sqrt{d}} \mathrm{d}S^\top Q$.

All steps are standard matrix multiplications and pointwise operations, so they can be implemented efficiently using batched GEMMs and elementwise kernels.

# Derivative of softmax (vector Jacobian-product form)

The softmax is the nonlinear step that requires careful treatment. Consider a single query $i$ and the corresponding pre-softmax score vector $s\in\mathbb{R}^{n_k}$ and probability vector $p=\mathrm{softmax}(s)$ where
$p_j = \frac{\exp(s_j)}{\sum_{t}\exp(s_t)}$.
We are given an upstream gradient $z = \frac{\partial \mathcal{L}}{\partial p}\in\mathbb{R}^{n_k}$ (this is the slice of $\mathrm{d}P$ for query $i$). We want $\frac{\partial \mathcal{L}}{\partial s}$.

The Jacobian of softmax is the matrix
$\frac{\partial p_i}{\partial s_j} = p_i(\delta_{ij} - p_j)$,
so the full Jacobian is $\mathrm{J} = \mathrm{diag}(p) - p p^\top$. Directly forming $\mathrm{J}$ is wasteful for large $n_k$, but we only need the product $\mathrm{J}^\top z$ (or $\mathrm{J} z$ since $\mathrm{J}$ is symmetric). The vector-Jacobian product simplifies to a numerically and computationally efficient expression:
$\mathrm{d}s = \mathrm{J}\, z = \big(\mathrm{diag}(p) - p p^\top\big) z
= p \odot \big(z - (p^\top z)\mathbf{1}\big).$
Here $\odot$ is elementwise product and $\mathbf{1}$ is the all-ones vector. In words, subtract the scalar $p^\top z$ from each component of $z$, then elementwise multiply by $p$. This formula uses only elementwise operations and a single dot product, not the full dense $n_k\times n_k$ Jacobian.

For clarity, write the scalar
$\alpha = p^\top z = \sum_{j} p_j z_j$,
then
$\mathrm{d}s_j = p_j \big(z_j - \alpha\big)$ for each $j$. This formula preserves the properties of the softmax Jacobian: the sum of components of $\mathrm{d}s$ is zero (because $\sum_j \mathrm{d}s_j = \sum_j p_j(z_j - \alpha) = \alpha - \alpha = 0$), reflecting invariance to adding a constant to all components of $s$.

We apply this formula for every query independently: for batch element $b$ and query index $i$ compute the scalar $\alpha_{b,i} = \sum_j P[b]_{ij}\, \mathrm{d}P[b]_{ij}$ and then
$\mathrm{d}S[b]_{i,:} = P[b]_{i,:} \odot\big(\mathrm{d}P[b]_{i,:} - \alpha_{b,i}\mathbf{1}\big).$
This gives an efficient, memory-friendly way to compute $\mathrm{d}S$ without forming full Jacobians.

Two additional practical notes: (1) Softmax is usually implemented with a numerical stabilization shift in the forward pass, e.g. subtracting $\max_j s_j$ before exponentiation. During backward, the stabilization does not change the above Jacobian product result; you must ensure the same shifted $s$ are used if recomputing. (2) The softmax Jacobian is symmetric positive semidefinite but singular (it has one zero eigenvalue corresponding to the constant vector), which is reflected in the zero-sum property above.

# Efficient formulations of attention gradients (matrix forms)

We now assemble the previous scalar/vector expressions into compact matrix forms that are used in high-performance implementations. Using batch-matrix notation and exploiting BLAS-level matrix multiplications leads to implementations that run nearly as fast as forward attention.

Recall the forward formulas:
$S = \frac{1}{\sqrt{d}} Q K^\top,\quad P = \mathrm{softmax}(S),\quad O = P V$.

Given $\mathrm{d}O$, the simplest matrix gradients are:
$\mathrm{d}V = P^\top \mathrm{d}O$,
$\mathrm{d}P = \mathrm{d}O\,V^\top$.

Compute $\mathrm{d}S$ by applying the softmax vector-Jacobian product across the query axis. If we denote elementwise multiplication by $\odot$ and row-wise operations, it is convenient to compute
alpha = rowwise_sum(P \odot \mathrm{d}P) (shape $B\times n_q\times 1$) so that for each row (query) $\alpha_{b,i} = \sum_j P_{ij}\mathrm{d}P_{ij}$.
Then
$\mathrm{d}S = P\odot(\mathrm{d}P - \alpha)$.
This is purely elementwise plus one reduction per query row.

Finally,
$\mathrm{d}Q = \frac{1}{\sqrt{d}} \mathrm{d}S\, K$,
$\mathrm{d}K = \frac{1}{\sqrt{d}} \mathrm{d}S^\top Q$.

Putting these into a staged implementation yields a small number of high-efficiency operations: two GEMMs for $\mathrm{d}V$ and $\mathrm{d}P$, an elementwise softmax-backprop kernel computing $\alpha$ and $\mathrm{d}S$, and two more GEMMs for $\mathrm{d}Q$ and $\mathrm{d}K$. Concretely:

1. GEMM: compute $\mathrm{d}V[b] = P[b]^\top \mathrm{d}O[b]$ (cost $\sim 2 n_q n_k d_v$ flops per batch item).
2. GEMM: compute $\mathrm{d}P[b] = \mathrm{d}O[b] V[b]^\top$ (cost $\sim 2 n_q d_v n_k$).
3. Elementwise: compute $\alpha_{b,i} = \sum_j P_{b,ij}\mathrm{d}P_{b,ij}$ and $\mathrm{d}S_{b,ij} = P_{b,ij}(\mathrm{d}P_{b,ij} - \alpha_{b,i})$ (cost $\sim 2 n_q n_k$).
4. GEMM: compute $\mathrm{d}Q[b] = \frac{1}{\sqrt{d}} \mathrm{d}S[b] K[b]$ (cost $\sim 2 n_q n_k d$).
5. GEMM: compute $\mathrm{d}K[b] = \frac{1}{\sqrt{d}} \mathrm{d}S[b]^\top Q[b]$ (cost $\sim 2 n_k n_q d$).

Note that the two last GEMMs often have the same cost and can be implemented as one batched pair of GEMMs or two depending on the framework. These operations mirror the forward pass GEMM costs and are typically well optimized on GPUs/TPUs.

If multiple attention heads are present, the same formulas apply independently per head, and implementations batch across heads. When attention is followed by linear projections (e.g., to compute Q,K,V from input tokens with learned weight matrices), the gradients $\mathrm{d}Q,\mathrm{d}K,\mathrm{d}V$ are further backpropagated to those weights in standard ways (GEMM-based).

One more efficient formulation worth noting concerns memory bandwidth and rearrangements: instead of materializing full $P$ or $S$ for all batches and heads, some implementations compute attention on the fly per-block or per-head and reuse streamed data. The matrix forms above provide the mathematical basis; engineering choices decide whether full tensors are resident in memory or streamed and recomputed.

# Recomputation vs. storing intermediates: trade-offs

Implementations of neural network backpropagation must decide which intermediate values from the forward pass to keep in memory for the backward pass, and which to recompute when needed. This is a classic time-memory trade-off. Attention layers present notable choices because the forward pass computes both the large attention matrix $S$ of shape $(B\times n_q\times n_k)$ and the probability matrix $P$ of the same shape. For long sequences these matrices can dominate memory consumption. On modern accelerators, storing $P$ for all layers, heads, and batches can be the primary memory cost, limiting maximum batch size or sequence length.

There are three main strategies:

1. Store everything needed for backward. This is the simplest and fastest approach: keep $P$ and possibly $S$ in memory so the backward pass can use them directly. Backward then performs the minimal amount of recomputation. Memory cost is high because $P$ has shape roughly $O(B n_q n_k)$ per head.

2. Recompute some intermediates during backward. Save less during forward (for example, only keep $Q,K,V$ or even just $Q$ and $K$) and recompute $S$ and $P$ during the backward pass when needed. Recomputation increases compute (you re-run the forward dot-products and softmax) but reduces memory. In extreme, one can keep only inputs and recompute all intermediate activations. This is often done by gradient checkpointing schemes.

3. Mixed strategies and block recomputation. Break the sequence into blocks and store/recompute at block granularity. For example, split $n_k$ into chunks and either store probabilities for some chunks or recompute chunks on demand. This can balance memory and compute to match hardware constraints.

Quantitatively, suppose storing $P$ would cost M bytes. Recomputation requires redoing the forward GEMM(s) that produced $S$ and $P$, costing additional FLOPs proportional to the forward attention cost (roughly $2 n_q n_k d$ flops for computing $QK^\top$ plus cost for softmax). If compute is abundant but memory is scarce, recomputation is attractive. If compute is the bottleneck (e.g., inference time constraints or cost-sensitive training), storing more intermediates is preferable.

A common practical choice for transformers is to store $P$ during the forward pass for training so backward is fast. For very long sequence training (e.g., long-context transformers), researchers often adopt recomputation or exact blockwise attention methods to avoid storing the dense $P$.

Recomputation has other subtleties. If softmax is numerically stabilized by subtracting per-row maxima, recomputation must use the same shift to match the original forward outputs (or recomputation will produce slightly different floating-point results, which is usually acceptable except in some deterministic debugging scenarios). Also, if dropout is applied to $P$ in forward, recomputation must use the same random mask (or the mask must be stored) to ensure the backward pass uses the identical stochastic forward path.

# Implications for memory usage and computational cost in backward pass

We now summarize how the backward pass affects memory and computational cost and give concrete formulas to reason about trade-offs.

Memory usage:
- Inputs and parameters: the backward pass needs access to inputs $Q,K,V$ (unless those are recomputed), and neural-network parameters (projection matrices). These costs are typically $O(B n d)$ where $n$ is sequence length and $d$ dimensionality.
- Activations to store for backward: storing $P$ costs $B n_q n_k$ floats per head. If $n_q=n_k=n$ and there are $h$ heads, storing all $P$ tensors costs $B h n^2$ floats; for sequence lengths of thousands and 32-bit floats, this is large.
- Temporaries during backward: $\mathrm{d}P$, $\mathrm{d}S$, and $\mathrm{d}O$ are similarly sized to $P$ and $S$, but many frameworks free temporaries as soon as they are used. The peak memory depends on which tensors are live simultaneously—usually peak includes $P$, $Q$, $K$, $V$, and $\mathrm{d}O$.

Computational cost:
- Forward attention computes $S$ ($\sim 2 B h n^2 d$ flops for all heads), computes softmax (cost $O(B h n^2)$ elementwise), and computes $O = P V$ ($\sim 2 B h n^2 d_v$ flops).
- Backward attention per the matrix-form steps requires roughly as many GEMM flops as forward plus small overhead for softmax backprop. Specifically, backward GEMMs are: $P^\top \mathrm{d}O$ and $\mathrm{d}O V^\top$ and two GEMMs for $\mathrm{d}Q$ and $\mathrm{d}K$, each comparable in cost to a corresponding forward GEMM. Summing, backward flops are roughly 2× the forward GEMM cost (a factor close to 2–3 overall when counting full attention forward + backward). Softmax backward is negligible relative to GEMMs.

Trade-off summary:
- If you store $P$ and $S$ (or at least $P$), backward requires no re-evaluation of $S$ or $P$ and so uses only the GEMMs listed above. This minimizes recomputation but maximizes memory.
- If you drop $P$ after forward and choose to recompute it during backward, you must re-run the forward GEMM ($QK^\top$) and softmax to get $P$ before computing $\mathrm{d}P$. That adds roughly one forward attention cost back into the total computational cost, making training more expensive in FLOPs but saving memory. In practice recomputing $S$ also requires $Q$ and $K$ to be available; if $Q$ and $K$ were themselves checkpointed (not stored), more recomputation cascades back.
- Blockwise or chunked recomputation reduces peak memory to $O(B h n b)$ where $b$ is block size, at the cost of proportionally more recomputation and memory traffic.

Rule-of-thumb numbers: for single-head attention with $n=1024$, $d=64$, $B=8$, storing $P$ (float32) costs 8*1024*1024*4 bytes ≈ 32 MiB per head. For 16 heads this becomes half a GiB. This demonstrates why attention memory grows rapidly with $n$ and motivates recomputation or reduced-precision storage (e.g., float16 or bfloat16) in practice.

Practical considerations
- Mixed precision (float16/bfloat16) halves memory use and accelerates compute on compatible hardware, but care is needed for softmax stability and for any reduction/scalar accumulation which may require higher precision.
- Checkpointing frameworks allow trading recomputation for memory automatically: users mark subsequences to checkpoint, and the framework recomputes forward activations as needed in backward.
- Reversible architectures avoid storing many intermediates by making the forward transformation invertible. Attention is not strictly invertible in the general case due to softmax non-invertibility (information loss), so reversibility for transformer layers requires special design.

Conclusion

Backpropagation through attention is straightforward in algebraic terms: propagate gradients through matrix multiplications and a softmax. The efficient, numerically stable softmax Jacobian-vector product $ \mathrm{d}s = p\odot(\mathrm{d}p - (p^\top \mathrm{d}p)\mathbf{1})$ makes it possible to compute $\mathrm{d}S$ without forming large Jacobian matrices. The backward procedure can be expressed as a small set of batched GEMMs and elementwise operations, making it amenable to highly optimized kernels.

From a systems perspective, the main design tension is memory versus computation: storing attention probabilities $P$ reduces recomputation and speeds backward but may be infeasible for long sequences; recomputation and checkpointing reduce memory at the cost of extra FLOPs. Understanding these formulas and trade-offs is essential for implementing and reasoning about training time and memory use in large transformer models, and for interpreting research that proposes memory- or compute-efficient attention variants.

Introduction

Many machine learning algorithms, especially those in classification and probabilistic modeling, rely heavily on exponentials and the softmax function. These functions are simple and elegant in mathematics, but their naive implementation on digital computers can lead to serious numerical issues: overflow, underflow, loss of precision, and unstable gradients. This chapter explains the underlying causes of these problems and presents principled, practical ways to mitigate them. We begin by focusing on numerical issues with exponentials and then introduce the log-sum-exp trick (rowwise max subtraction) that is central to stable softmax implementations. We then cover basics of floating-point precision and accumulation error so you can reason quantitatively about how errors appear and grow. Next, we analyze the stability of softmax and describe concrete mitigation techniques used both at inference and during training. Finally, we examine how errors propagate through matrix multiplications and reduction operations (sums, maxima), because softmax is almost always embedded inside larger chained computations in neural networks. Throughout, emphasis is on intuition, clear derivations where helpful, and practical advice for writing numerically robust code.

# Numerical issues with exponentials and overflow/underflow

The exponential function grows and decays extremely quickly. For a real scalar input $x$, $\exp(x)$ is roughly multiplicative in $x$: doubling $x$ squares $\exp(x)$. This rapid growth causes two main numerical failure modes on finite-precision machines: overflow (values exceed the largest representable floating-point number) and underflow (values become indistinguishable from zero).

Consider a common floating-point format, IEEE 754 single precision (float32). The largest finite representable value is about $3.4 \times 10^{38}$, and the smallest positive normalized value is about $1.17 \times 10^{-38}$. Exponentials cross these limits quickly: $\exp(88.7) \approx 3.4 \times 10^{38}$, so $\exp(100)$ overflows to infinity in float32. On the negative side, $\exp(-100) \approx 3.7 \times 10^{-44}$ underflows to zero (unless subnormal representation is used). In double precision (float64), these thresholds are around $\exp(709)$ for overflow and $\exp(-745)$ for underflow.

Overflow is catastrophic: an operation that yields $\infty$ can infect subsequent computations and produce NaNs (not-a-number) when combined with other infinities or when used in operations like subtraction or multiplication by zero. Underflow is less dramatic but still problematic: values may be flushed to zero; when a tiny exponential is used to compute normalized probabilities, zero terms can make the normalization incorrect and destroy gradient information during training.

Beyond overflow/underflow, exponentials amplify relative differences. Suppose we have two numbers $a$ and $b$ with $a > b$ and compute $\exp(a)$ and $\exp(b)$. If $a-b$ is large, $\exp(b)$ may be negligible compared to $\exp(a)$, so a sum like $\exp(a)+\exp(b)$ is numerically indistinguishable from $\exp(a)$, losing information about $\exp(b)$. This is an instance of catastrophic cancellation when later subtracting two nearly equal large numbers, or simply the loss of small contributions in a sum dominated by a large term. This matters in softmax and log-sum-exp because we often take logarithms of sums of exponentials or normalize exponentials to form probabilities.

Finally, approximating exponentials by polynomial or table methods can introduce relative approximation error that depends on the magnitude of the argument. Many libraries implement exp with careful range reduction and polynomial approximations to guarantee small relative error over practical ranges, but even small relative errors can become important when exponentials are used inside reductions or gradients.

# Rowwise max subtraction (log-sum-exp trick)

A central tool for stabilizing computations that involve sums of exponentials is the log-sum-exp trick. The identity at the heart of the trick is algebraic and exact:

For any real vector $z = (z_1,\dots,z_n)$ and scalar $m = \max_i z_i$,
\[
\log\!\left(\sum_{i=1}^n e^{z_i}\right) \;=\; m + \log\!\left(\sum_{i=1}^n e^{z_i - m}\right).
\]

Subtracting $m$ from each exponent shifts the largest exponent to zero, so all terms $e^{z_i - m} \in (0,1]$. This prevents overflow when some $z_i$ are large positive values (which would make $e^{z_i}$ huge) and reduces underflow of the smaller terms because they are closer to the largest term in magnitude. Numerically, computing $\exp(z_i - m)$ avoids taking exponentials of very large or very negative numbers, provided $m$ captures the largest magnitude in the row or vector.

Practically, when computing $\log\sum_i e^{z_i}$, one should compute $m = \max_i z_i$, then compute the sum $s = \sum_i \exp(z_i - m)$, and finally return $m + \log(s)$. If $m$ is $+\infty$ or NaN, care must be taken, but for finite finite-precision inputs this routine is robust. It ensures the argument to the exponentials lie in a numerically safe range, typically $(-\infty, 0]$, and the sum $s$ lies between $1$ and $n$ (since each term is at most $1$ and at least $0$), so $\log(s)$ is bounded and well-conditioned.

Rowwise max subtraction is especially important when applying softmax across rows (or batches): softmax is often computed as $p_i = \frac{\exp(z_i)}{\sum_j \exp(z_j)}$, and naively computing the numerator and denominator separately suffers from the overflow/underflow issues discussed earlier. A stable implementation computes $m=\max_j z_j$ and then $p_i = \frac{\exp(z_i - m)}{\sum_j \exp(z_j - m)}$. This form is algebraically identical to the original softmax but numerically far more robust.

There are further refinements. When computing both the log-likelihood and its gradient, it is often preferable to compute and return $\log\! \sum_i \exp(z_i)$ using the trick, and then derive the normalized probabilities by exponentiating the shifted values and dividing by $s$. Another variant is the use of log-softmax directly: compute $\log p_i = z_i - m - \log s$, which is numerically stable and avoids taking exponentials if downstream code needs log-probabilities.

Rowwise subtraction is performed per vector (row) when softmax is applied across rows of a matrix: compute $m_k = \max_j Z_{k,j}$ for each row $k$, subtract $m_k$ from that row, exponentiate, and normalize. Doing the subtraction per row (or per logical softmax dimension) is essential; subtracting a global max across the whole matrix will not correctly bound the per-row exponentials and can over- or under-correct.

# Precision and accumulation error basics

Understanding numerical stability requires familiarity with floating-point arithmetic and the sources of rounding and accumulation error. Floating-point numbers represent real numbers with finite precision, typically as $(-1)^s \times (1.f) \times 2^{e}$ in normalized form, where $f$ is the fractional bits and $e$ the exponent. The key parameter is machine epsilon $\epsilon_{\text{mach}}$, the distance between $1$ and the next representable float. For IEEE 754 binary32 (float32), $\epsilon_{\text{mach}} \approx 2^{-23} \approx 1.19\times 10^{-7}$. For binary64 (float64), $\epsilon_{\text{mach}} \approx 2^{-52} \approx 2.22\times 10^{-16}$.

A commonly used model for floating-point arithmetic is the IEEE-style relative error model for basic operations: the computed result of an arithmetic operation $\circ$ on exact real operands $x$ and $y$ is
\[
\text{fl}(x \circ y) = (x \circ y) (1 + \delta),
\]
with $|\delta| \le \epsilon_{\text{mach}}$ (sometimes $u$ is used instead of $\epsilon_{\text{mach}}$). This model abstracts rounding as a small relative multiplicative perturbation. For sums and subtractions, however, absolute errors and cancellation play a larger role: when adding numbers of different magnitudes, the smaller ones can be effectively ignored due to rounding—a phenomenon called loss of significance or catastrophic cancellation.

Accumulation error occurs when many operations are chained, such as summing $n$ numbers or performing large matrix multiplications. If one sums $n$ positive floating-point numbers naively in sequence, the relative error can grow roughly on the order of $n \epsilon_{\text{mach}}$. More precisely, if $S$ is the true sum and $\widehat{S}$ is the computed sum using naive pairwise addition in floating point, one can often bound
\[
\widehat{S} = S (1 + \theta_n),
\]
where $|\theta_n| \le n \epsilon_{\text{mach}} + O(n \epsilon_{\text{mach}}^2)$. This bound is pessimistic but useful: for very large $n$, or for low-precision arithmetic, the accumulated error can become significant.

Subtraction of nearly equal numbers is especially dangerous. If $x$ and $y$ are close and of opposite sign, computing $x-y$ can lose most significant digits. For example, if $x = 1.234567$ and $y = 1.234566$ in decimal, their difference $1\times 10^{-6}$ retains only a few meaningful digits relative to the full precision. In floating-point arithmetic, such cancellation amplifies relative error in subsequent divisions or multiplications.

There are techniques to mitigate accumulation error. Reordering summation to add smaller magnitude terms first can reduce rounding loss; Kahan summation (compensated summation) stores a running compensation term to capture lost low-order bits, reducing the error to $O(\epsilon_{\text{mach}})$ independent of $n$ for many practical inputs. More advanced algorithms like pairwise summation (recursive divide-and-conquer) provide error bounds that scale like $O(\log n)$ in the number of operations rather than $O(n)$. In parallel computing, reduction trees inherently implement pairwise summation, which is numerically better than a long sequential sum.

For nonlinear functions like exponential and logarithm, we must consider both the local conditioning and the propagation of input errors. If $y = \exp(x)$ and $x$ has a small absolute perturbation $\Delta x$, then $\exp(x+\Delta x) = \exp(x) \exp(\Delta x) \approx \exp(x) (1 + \Delta x)$ for small $\Delta x$. Thus a small absolute error in $x$ becomes a relative error in $\exp(x)$ about $|\Delta x|$. If $\Delta x$ is relative, errors can be magnified further when $x$ is large. Therefore careful control of absolute and relative input perturbations is important before applying exponential.

# Stability of softmax and mitigation techniques

Softmax maps a vector $z \in \mathbb{R}^n$ to a probability vector $p \in \mathbb{R}^n$ with components
\[
p_i = \frac{e^{z_i}}{\sum_{j=1}^n e^{z_j}}.
\]
From a purely mathematical perspective, softmax is well-behaved: it is continuous, differentiable, and invariant to adding the same scalar to all components (translation invariance). However, numerical issues arise from the exponentials and the normalization denominator.

The principal numerical hazards are: overflow when some $z_i$ are large positive; underflow when some $z_i$ are large negative; loss of precision in computing probabilities when one component dominates the sum; and unstable gradients when backpropagating through softmax and the cross-entropy loss.

A stable forward implementation uses the rowwise max subtraction trick: let $m = \max_i z_i$ and compute
\[
\tilde{z}_i = z_i - m,\qquad \tilde{p}_i = \frac{e^{\tilde{z}_i}}{\sum_j e^{\tilde{z}_j}}.
\]
Because $\max_i \tilde{z}_i = 0$, all exponentials are in $(0,1]$, preventing overflow. The denominator lies in $[1,n]$, and numerical precision for the relative probabilities $\tilde{p}_i$ is improved because the dominant term is at most $1$ rather than an enormous number. For log-probabilities, compute
\[
\log p_i = \tilde{z}_i - \log\!\Big(\sum_j e^{\tilde{z}_j}\Big),
\]
again using the same numerically bounded values.

When training classifiers with a softmax plus cross-entropy loss, it is numerically better to combine softmax and negative log-likelihood into a single stable operator rather than computing softmax probabilities and then taking logs. The loss for a single example with true class index $k$ is
\[
L = -\log p_k = -z_k + \log\!\left(\sum_j e^{z_j}\right).
\]
Use the log-sum-exp trick to compute this stably as
\[
L = -(z_k - m) + \log\!\Big(\sum_j e^{z_j - m}\Big).
\]
Many frameworks implement "softmax cross entropy with logits" that accept the raw logits $z$ and compute the loss directly in a numerically stable manner. This avoids constructing probabilities near zero (which would become $-\infty$ under $\log$) and avoids overflow.

On the backward pass, the derivative of the loss $L$ with respect to $z_i$ for the cross-entropy target is
\[
\frac{\partial L}{\partial z_i} = p_i - y_i,
\]
where $y$ is the one-hot vector for the correct class. If probabilities $p_i$ are computed stably as described, the gradient computation is likewise stable. However, when using extremely low-precision arithmetic (e.g., float16 or bfloat16), care is needed because $p_i$ values that should be small positive numbers may round to zero, causing the gradient to be exactly $-y_i$ for those entries and eliminating small gradient signals. Remedies include computing softmax in higher precision (e.g., cast logits to float32, compute softmax, then cast back), or using compensated summation for the denominator.

Temperature scaling is another practical technique. Softmax can be generalized with a temperature parameter $\tau > 0$:
\[
p_i = \frac{e^{z_i/\tau}}{\sum_j e^{z_j/\tau}}.
\]
Large $\tau$ smooths the distribution (less peaked), while small $\tau$ makes it more peaked. From a numerical point of view, very small $\tau$ amplifies differences and can cause underflow/overflow; very large $\tau$ brings the exponent close to one, which can cause loss of discriminative precision in exponent computations. Typically, temperature is used for model behavior reasons rather than numerical stability, but when tuning it be aware of numerical effects.

Another common trick is to use log-softmax when downstream code needs log-probabilities, rather than computing softmax then taking log. Log-softmax implemented via log-sum-exp is the stable choice:
\[
\log p_i = z_i - m - \log\!\Big(\sum_j e^{z_j - m}\Big).
\]
This avoids exponentiation entirely if one only needs logs. In automatic differentiation systems, a combined primitive for log-softmax can also provide more stable backward gradients.

For extreme precision constraints (mixed precision training), one may want to compute the reductions involved in the denominator in higher precision than elementwise exponentials. A common pattern is: compute shifted logits $\tilde{z}$ in float32, compute exponentials in float32, accumulate the denominator in float32 (or float64 if needed), then normalize. Using higher precision for accumulations reduces rounding in sums and avoids zeros from underflow. Some hardware supports mixed precision with fast lower-precision elementwise ops and higher-precision accumulation (e.g., Tensor Cores with fp16 multiply-accumulate into fp32). When this is not available, explicitly casting to a higher-precision accumulator before summing is beneficial.

Finally, in some rare cases where one expects extreme dynamic range (very large logits), one can clip logits before applying softmax (e.g., clamp to a reasonable range like [-100, 100]) as a last resort, accepting a small bias to avoid infinities or NaNs. Mostly, the max subtraction trick makes clipping unnecessary.

# Error propagation through matmuls and reductions

Softmax and exponential computations are typically embedded into broader linear algebra pipelines: logits are often the result of a matrix multiplication $Z = XW + b$, then softmax is applied rowwise over $Z$. Errors introduced in earlier stages propagate and sometimes amplify through matrix multiplications (matmuls) and reductions. Understanding how these errors behave helps design stable software and analyze failure modes.

Matrix multiplication has well-studied backward and forward error analyses. Let $A\in\mathbb{R}^{m\times k}$ and $B\in\mathbb{R}^{k\times n}$ and consider computing the product $C = AB$. A standard backward error result for floating-point matrix multiplication (under the usual model of rounding to nearest) states that the computed $\widehat{C}$ satisfies
\[
\widehat{C} = (A + \Delta A)(B + \Delta B)
\]
for some perturbations $\Delta A, \Delta B$ satisfying
\[
\|\Delta A\| \le \gamma_k \|A\|,\qquad \|\Delta B\| \le \gamma_k \|B\|,
\]
where $\gamma_k = cu \, k + O(u^2)$ for unit roundoff $u$ and a small constant $c$ depending on the algorithm. This backward error formulation means the computed product is exact for slightly perturbed inputs; equivalently the forward error is bounded relative to the condition of the multiplication. One can also derive a forward error bound
\[
\|\widehat{C} - C\| \le \gamma_k \, \|A\| \, \|B\| + O(u^2),
\]
which shows error grows roughly linearly with the inner dimension $k$ and with the sizes of $A$ and $B$.

Practically, this means that long inner dimensions or very large-magnitude entries amplify rounding errors in matmul. Many deep networks use matmuls with large $k$ (e.g., embedding dimensions) so small rounding errors can accumulate to meaningful absolute errors. If those outputs are fed into softmax, the relative placement of logits may change slightly, potentially altering which index is the maximum, significantly affecting the normalized probabilities. However, because softmax is translation invariant, small uniform perturbations to an entire row do not change the softmax; non-uniform perturbations matter.

Reductions such as sum and max also have numerical considerations. Summing $n$ numbers with naive sequential accumulation has error scaling roughly like $O(nu)$ as mentioned. Pairwise summation reduces that to $O(\log n \, u)$, and compensated (Kahan) summation can reduce it further. For softmax normalization denominator $s = \sum_j e^{\tilde{z}_j}$, using a numerically stable summation algorithm makes the computed $s$ have small relative error, which in turn keeps probabilities accurate.

Max reduction is more benign: computing $m = \max_i z_i$ requires comparisons and assignments, and comparing floating-point numbers is exact in the sense that the maximum of finite representable numbers is itself exactly representable among them. However, if the logits are noisy due to earlier rounding, the identity of the argmax can change, and this matters because the rowwise subtraction uses the maximum index but only the maximum value; small perturbations can change which element is maximum if scores are very close. When several logits are nearly tied, softmax can be highly sensitive: tiny perturbations can reorder logits and lead to different normalized probabilities. This is an intrinsic conditioning issue: the softmax output is ill-conditioned near ties. There is no numerical trick to make this region well-conditioned; it is a property of the function.

Error propagation in chained operations can be analyzed using the standard first-order perturbation approach. Suppose the true logits are $z$ and due to earlier steps we have computed $\widehat{z} = z + \Delta z$ with $\|\Delta z\|$ small. For softmax, the output is $p(z)$ and the perturbed output is $p(z+\Delta z)$. Using a first-order Taylor expansion,
\[
p(z+\Delta z) \approx p(z) + J_p(z)\,\Delta z,
\]
where $J_p(z)$ is the Jacobian matrix of partial derivatives of softmax. The Jacobian elements are
\[
\frac{\partial p_i}{\partial z_j} = p_i(\delta_{ij} - p_j).
\]
The operator norm of $J_p(z)$ can be bounded: since the softmax maps into simplex, one can show $\|J_p(z)\|_2 \le 1/2$ for the 2-norm (the maximum singular value of the Jacobian is at most $1/2$), though the exact bound depends on the norm used. This means small perturbations in logits produce at most modest-magnitude changes in probabilities in a linearized sense. However, individual components can change by up to about $p_i$ in magnitude times the perturbation norm; if $p_i$ is near 1, small changes in logits still only affect the small components modestly, but if probabilities are diffuse, gradients are less damped.

A practical example: suppose the norm of the perturbation satisfies $\|\Delta z\|_{\infty} \le \eta$. Then, using Lipschitz bounds derived from the Jacobian, one can show that for each $i$,
\[
|p_i(z+\Delta z) - p_i(z)| \le 2 \eta,
\]
for appropriately normalized arguments; precise constants depend on the norm and distribution. The take-away is that bounded perturbations in logits produce bounded perturbations in softmax outputs, but when logits are nearly tied, a tiny $\Delta z$ can flip the ordering and change $p$ significantly.

Because matrix multiplications and reductions often occur on the same hardware, another key consideration is mixed-precision arithmetic. Many accelerators perform the multiply-accumulate in higher precision than the storage format (for example, accumulate in float32 while inputs are float16). This reduces accumulation error in matmuls and sums. When hardware does not do this automatically, software can emulate higher-precision accumulation by casting to a wider dtype for the accumulation step.

When distributing matmuls across multiple processors, reduction order matters. A large distributed sum implemented as tree reduction (pairwise combining partial sums) is both faster and numerically better than a long chain of sequential adds. Similarly, when normalizing exponentials across a large dimension, performing pairwise summation during reduction reduces error.

Finally, consider backpropagation: gradients flow backward through matmuls and softmax. Errors in forward pass values can affect gradient computation. Automatic differentiation systems typically re-evaluate some intermediate quantities in higher precision or rely on numerically stable primitives (e.g., use log-sum-exp in the forward pass and utilize stable adjoints in the backward pass). If you implement custom ops, make sure backward formulas mirror the stability of the forward ones: use stable expressions such as using probabilities computed from shifted logits rather than exponentiating large numbers in the gradient formula.

Summary and practical checklist

- Always use rowwise max subtraction (log-sum-exp trick) when computing log-sum-exp, softmax, or cross-entropy from logits.
- Compute softmax (or at least the denominator sum) in higher precision than the input dtype when using low-precision storage (cast to float32 for accumulation).
- Use log-softmax if downstream code needs log-probabilities to avoid unnecessary exponentiation and loss of precision.
- For sums over many terms, prefer pairwise summation or compensated summation to naive sequential addition.
- Be aware that softmax is ill-conditioned when logits are nearly tied; small perturbations can reorder maxima and change probabilities.
- In mixed-precision training, prefer fused or library primitives that handle accumulation in higher precision rather than ad-hoc low-precision implementations.
- When debugging NaNs or infinities, trace back to exponentials of large arguments or zero divisions in normalization; adding max subtraction and clamps often pinpoints the issue.

With these principles, you can reason about numerical behavior in models that use softmax and exponentials, implement stable primitives, and recognize when numerical issues originate from earlier linear algebraic operations.

# Introduction

Floating-point arithmetic is the lingua franca of numerical computing and machine learning. Modern neural networks are trained and executed on specialized hardware that uses a range of floating-point formats, from the 32-bit IEEE-754 standard to newly adopted low-precision types such as 16-bit, 8-bit, and mixed formats. Choosing a floating-point format involves tradeoffs among dynamic range (the largest and smallest representable magnitudes), precision (how finely different values can be distinguished), storage bandwidth, arithmetic throughput, and numerical stability. This chapter explains the structure and semantics of common floating-point formats, the ways in which reduced exponent or mantissa width affects computation, and how hardware and software mitigate precision and range limitations through rounding, subnormals, special values (infinity and NaN), and mixed-precision accumulation.

We begin with the well-known IEEE-754 single-precision format (FP32), because it establishes terminology and semantics used for all other formats. We then examine two half-precision formats widely used in machine learning—IEEE half (FP16) and the brain floating point format (BF16)—and explain their different compromises. Emerging low-precision formats such as FP8 variants (commonly e4m3 and e5m2) are covered next, with emphasis on how exponent and mantissa bit allocation shapes the dynamic range and quantization error. We cover the important operational details: rounding modes, subnormal numbers, infinities, and NaNs. Finally, the chapter addresses mixed-precision computation and accumulator precision, the strategies hardware and algorithms use to maintain numerical correctness and learning stability when operands are stored in low precision.

# IEEE-754 basics and FP32 semantics

IEEE-754 is a family of standards that defines formats and behavior for floating-point arithmetic to promote portable, predictable numerical computation. The most commonly used IEEE-754 formats are binary32 (FP32), binary16 (FP16), and binary64 (FP64). We focus first on FP32 because it is the conventional default in scientific computing and the reference for lower-precision variants.

An IEEE binary floating-point number is composed of three fields: a sign bit $s$, an exponent field of width $E$ bits, and a fraction (mantissa or significand) field of width $M$ bits. For FP32, $E = 8$ and $M = 23$. The bit layout is: one sign bit, 8 exponent bits, and 23 fraction bits, for a total of 32 bits.

The value represented by a non-special, normalized FP32 number is
\[
(-1)^s \times (1.f) \times 2^{e - b},
\]
where $f$ is the fractional part represented by the $M$ fraction bits (so $1.f$ denotes the binary significand in the range $[1,2)$), $e$ is the unsigned integer value of the exponent field, and $b$ is the bias, equal to $2^{E-1} - 1$ (for FP32, $b = 127$). The exponent field encodes a signed exponent using offset (biased) representation, which conveniently allows lexicographic ordering of bit patterns to correspond to numerical order for positive numbers.

There are three classes of floating-point encodings determined by the exponent field:

1. If $1 \le e \le 2^E - 2$ (i.e., exponent not all zeros or all ones), the number is normalized and the value follows the formula above.
2. If $e = 0$ and the fraction $f \neq 0$, the number is subnormal (also called denormal). For subnormals the implicit leading 1 is not present; instead the significand is $0.f$ and the exponent is taken as $1-b$, so the value is
   \[
   (-1)^s \times (0.f) \times 2^{1-b}.
   \]
   Subnormals allow representation of magnitudes smaller than the smallest normalized number, providing gradual underflow to zero at the cost of reduced precision.
3. If $e = 0$ and $f = 0$, the value is signed zero ($+0$ or $-0$ depending on $s$). If $e = 2^E - 1$ (all ones) and $f = 0$, the value is $\pm \infty$. If $e = 2^E - 1$ and $f \neq 0$, the value is a NaN (Not a Number), which propagates invalid or indeterminate results.

FP32 numeric characteristics arise directly from these bit widths. The largest finite normal value is approximately
\[
(2 - 2^{-M}) \times 2^{2^{E-1} - 2}
\]
and the smallest positive normal value is
\[
2^{1-b} = 2^{-(2^{E-1}-2)}.
\]
For FP32, the dynamic range spans roughly $1.18 \times 10^{-38}$ to $3.4 \times 10^{38}$. The machine epsilon (unit roundoff) is the gap between 1 and the next representable number, which for a binary format with $M$ fraction bits is $2^{-M}$. For FP32, machine epsilon is $2^{-23} \approx 1.19 \times 10^{-7}$, and this governs relative rounding error bounds for basic arithmetic when rounding to nearest.

Understanding FP32 semantics is crucial because many lower-precision formats are defined either by truncating FP32 fields or by matching FP32 exponent width (as in BF16). Most software and hardware provide guarantees for basic arithmetic like rounding to nearest ties-to-even, correctly rounded fused multiply-add (FMA) in some implementations, and well-defined behavior for special values, which allow portable numeric reasoning and algorithm design.

# Half-precision formats: FP16 vs BF16 (representation and tradeoffs)

Half-precision formats reduce storage and computation costs by compressing sign, exponent, and fraction fields into 16 bits. Two prevalent 16-bit floating-point formats in machine learning are IEEE binary16 (commonly called FP16 or FP16 IEEE) and the brain float format BF16. Although both use 16 bits, they adopt different splits between exponent and fraction, yielding different dynamic range and precision tradeoffs.

IEEE FP16 uses $E = 5$ exponent bits and $M = 10$ fraction bits, plus 1 sign bit. The bias is $b = 2^{4} - 1 = 15$. The FP16 representation supports normalized numbers for $1 \le e \le 30$, subnormals for $e = 0$, and special values for $e = 31$. The significand has 10 fraction bits so the machine epsilon is $2^{-10} \approx 9.77 \times 10^{-4}$ (roughly three decimal digits of precision). The dynamic range of FP16 is significantly smaller than FP32: the largest finite FP16 number is about $6.55 \times 10^4$ and the smallest positive normalized number is about $6.10 \times 10^{-5}$. Subnormals allow representation down to approximately $5.96 \times 10^{-8}$. FP16 provides reasonable precision for many inference tasks but can be insufficient for some training workloads because of the narrower dynamic range and coarser relative precision.

BF16 (brain floating point 16) takes a different approach: it uses the same exponent width as FP32 but fewer mantissa bits. In BF16, $E = 8$ and $M = 7$ (with 1 sign bit), effectively matching the FP32 exponent field but reducing precision. The bias is $b = 127$, the same as FP32. Because BF16 shares FP32's exponent width, it preserves FP32's dynamic range (same largest and smallest finite normal magnitudes) but carries only $7$ fraction bits, so machine epsilon is $2^{-7} \approx 7.8125 \times 10^{-3}$. That means BF16 has coarser step size than FP32 but can represent very large and very small magnitudes the same way as FP32.

These two design choices reflect different practical tradeoffs. FP16 emphasizes precision relative to magnitude (more mantissa bits) at the cost of dynamic range, whereas BF16 sacrifices precision to preserve range. In deep learning, dynamic range is often critical because gradients and activations can be extremely small or large during training. BF16's preservation of exponent width avoids many overflows/underflows that would otherwise occur with FP16, and it allows code paths that assume FP32-like scaling to operate more robustly when mantissa precision is sufficient. However, BF16's coarse rounding can degrade optimization when precise small updates accumulate (e.g., subtle gradient steps). Conversely, FP16's greater mantissa precision reduces rounding error when values are within its narrower range, potentially improving representational fidelity in inference where extremes are uncommon.

The practical effect is that BF16 has been favored in many hardware accelerators for training because it permits aggressive memory and compute reduction without frequent overflow/underflow, whereas FP16 is commonly used in inference pipelines and in specialized mixed-precision schemes that use FP32 accumulators to mitigate FP16's dynamic-range shortcomings.

# Emerging low-precision formats: FP8 variants (e4m3, e5m2) and reduced mantissa/exponent tradeoffs

As hardware designers push for ever higher throughput and lower memory footprints, 8-bit floating-point formats (FP8) have emerged as an attractive option. FP8 types compress values to 8 bits and are often used internally on accelerators for matrix multiplication and deep learning inference, or as activation/weight storage. Because 8 bits is a very small budget, designers must carefully choose how many bits to allocate to the exponent and mantissa. Two common FP8 variants in current hardware and literature are e4m3 and e5m2; these names indicate the number of exponent bits (e) and mantissa bits (m).

The e4m3 format uses $E = 4$ exponent bits and $M = 3$ fraction bits (plus 1 sign bit). The bias is $b = 2^{E-1} - 1 = 7$. With 3 mantissa bits, the machine epsilon is $2^{-3} = 0.125$, which is coarse but often enough for representing activations after appropriate scaling. The exponent width of 4 bits provides a modest dynamic range: the exponent field values $e = 1$ to $14$ correspond to normalized numbers with exponents from $-6$ to $7$ (i.e., values roughly between $2^{-6}$ and $2^8$ when accounting for fraction range). The largest finite e4m3 value is approximately $(2 - 2^{-3}) \times 2^{2^{3} - 2} = (2 - 0.125) \times 2^6 = 1.875 \times 64 \approx 120$, so dynamic range is limited but useful for many normalized activation patterns when combined with layer scaling or normalization.

The e5m2 format places $E = 5$ exponent bits and $M = 2$ mantissa bits. The bias becomes $b = 15$. With 2 mantissa bits, machine epsilon is $2^{-2} = 0.25$, coarser than e4m3. The larger exponent width increases dynamic range substantially; e5m2 can represent significantly larger and smaller magnitudes than e4m3. This larger range may reduce overflow and underflow events but does so at the expense of coarser quantization steps. That means small relative differences between nearby values are lost more readily in e5m2 than in e4m3.

These two FP8 variants illustrate the central design tension: give more exponent bits to widen dynamic range (reduce overflow/underflow) or give more mantissa bits to reduce quantization error (improve precision). Depending on the target workload, one or the other can be preferable. For example, when representing network activations that vary broadly in scale during inference, e5m2's wider range might reduce saturation. In contrast, when computations are performed after normalization layers or with careful scaling, e4m3's extra mantissa bit can provide more accurate relative values.

Because FP8 dynamic ranges are small, practical deployments often apply pre-scaling to tensors: multiplying by a power-of-two scaling factor (which is exact in binary floating point) before casting to FP8, then dividing the result back when necessary. This approach effectively shifts the exponent range used by that tensor and is widely used in quantization-aware training or inference pipelines to compress values without losing relevant information. Another strategy is to use FP8 only for certain parts of the computation (weights, activations), while keeping accumulators, gradients, or parameters in higher precision.

When designing numerical algorithms for FP8, it is crucial to consider where rounding errors and overflow/underflow are most harmful. Matrix multiply kernels often accumulate many products; a low-precision product can be tolerated if the accumulator is wide enough. Therefore, hardware often supports mixed-precision accumulation where inputs are FP8 but the inner-product accumulation is carried out in FP16, BF16, or FP32. This allows leveraging the throughput benefits of FP8 while protecting the final result from catastrophic precision loss.

# Rounding modes, subnormal numbers, infinities and NaNs

Floating-point arithmetic must map infinitely many real numbers and the outputs of arithmetic operations into a finite set of representable values. Rounding rules determine how results are snapped to representable values, and IEEE-754 specifies several standard rounding modes. The default and most commonly used is round-to-nearest, ties-to-even, which rounds to the nearest representable value; when a result is exactly halfway between two representable numbers, the tie is broken by choosing the one with an even least-significant bit in the significand. This reduces bias in rounding over repeated operations. Other modes include round-toward-zero, round-toward-positive-infinity, and round-toward-negative-infinity; these are useful in interval arithmetic, financial applications, and in controlling conservative approximations.

Stochastic rounding—a non-IEEE but practically useful technique—randomly rounds a value with probability proportional to its distance to the two nearest representable numbers. In small-gradient contexts it can prevent systematic bias introduced by deterministic rounding, improving convergence in low-precision training. Some hardware and software frameworks provide stochastic rounding as an option for training, although it is less common in inference.

Subnormal numbers (also called denormals) extend representation below the smallest normalized number. For a format with $M$ fraction bits and exponent bias $b$, the smallest positive normalized number is $2^{1-b}$. Subnormals allow representation down to $2^{1-b-M}$ because the implicit leading one is removed and the fraction behaves as $0.f$. Subnormals provide gradual underflow: values that would otherwise flush directly to zero can be represented with reduced precision, which helps preserve relative ordering of tiny values and can prevent catastrophic cancellation in some algorithms. However, handling subnormals may be slow on some hardware, leading to performance-sensitive systems choosing to flush subnormals to zero (FTZ) for speed. Flushing to zero can be acceptable in many machine-learning workloads, but can also change numerical behavior subtly.

Infinities and NaNs are special encodings for overflow and undefined operations, respectively. An overflow—when an operation yields a magnitude greater than the largest finite representable value—results in $\pm \infty$ according to the sign. Operations like division by zero (e.g., nonzero divided by zero) also produce infinities. NaNs indicate invalid or indeterminate results, such as $0/0$ or $\infty - \infty$. The IEEE standard distinguishes between quiet NaNs (qNaN), which silently propagate through computations, and signaling NaNs (sNaN), which are intended to raise exceptions when used. In machine learning, NaNs are often harmful because they can poison entire tensors through subsequent operations; debugging NaN sources can be a major practical concern. Some hardware aggressively propagates NaNs, while other systems may encode special behavior to avoid propagation in certain kernels.

Understanding these behaviors is important when converting to low-precision formats. If rounding causes many operations to overflow to infinity or underflow to zero (or flush subnormals), the numerical behavior of the algorithm can be materially altered. When designing quantization or mixed-precision strategies, it is important to monitor the frequency of special events and to use wider ranges (e.g., BF16 exponents) or pre-scaling to keep values safely within representable bounds.

# Mixed-precision computation and accumulator precision

Mixed-precision computation combines different floating-point formats in a single computation to balance performance and accuracy. A canonical example in machine learning is using low-precision formats for storage and arithmetic (e.g., FP16 or FP8) while using higher-precision accumulators (e.g., FP32) for reductions or parameter updates. The most common mixed-precision workflow during training is: keep model weights in high precision (FP32 or BF16), store activations and intermediate results in a low-precision format for memory bandwidth efficiency, perform matrix multiplications using low-precision operands but a higher-precision accumulator, and use higher precision in the optimizer for computing updates.

The need for higher-precision accumulators arises because many linear algebra operations perform sums of many products, and rounding errors accumulate across these sums. Consider a dot product of $n$ terms:
\[
s = \sum_{i=1}^n x_i y_i.
\]
If each product is computed with low precision and accumulated in the same low precision, the error can grow roughly proportionally to $n$ times the unit roundoff of that precision, potentially yielding substantial relative error. Using a wider accumulator reduces roundoff per addition and the effective error growth, preserving convergence properties during training. Many hardware units implement fused multiply-add (FMA) operations that compute $a \times b + c$ with a single rounding at the end; if $c$ and the accumulator are in higher precision, the internal precision of the FMA helps produce more accurate partial sums. For example, NVIDIA’s Tensor Cores originally supported FP16 inputs with FP32 accumulation, which allowed fast matrix multiplications with robust accuracy. The fused multiply-add property is particularly important because it converts $n$ rounding events into approximately $n$ exact multiply-add operations followed by a single rounding in higher precision, improving numerical stability significantly.

Accumulator precision is not just about correctness; it determines when low-precision formats are practically usable. For FP8, it is common to perform the element-wise multiplications in FP8 (or emulated with slightly higher internal precision) but to accumulate results in FP16, BF16, or FP32. The accumulator must be wide enough to represent the maximal possible sum without overflow and with sufficient precision to avoid destructive cancellation. For instance, if the product values are of order $1$ and there are $10^4$ terms, an accumulator must be able to represent values around $10^4$; an 8-bit exponent may overflow quickly, so moving accumulation to FP32 prevents overflow. Moreover, keeping the accumulator in FP32 sometimes removes the need for frequent rescaling or block-wise accumulation steps.

Mixed-precision training has algorithmic considerations as well. When weights are stored in low precision, small gradient updates can vanish if they are below the representable quantization step. A typical approach is to maintain a master copy of model parameters in FP32 while keeping a lower-precision copy for forward and backward passes. Gradients are computed in mixed precision and applied to the FP32 master weights; the low-precision copy is refreshed from the master weights periodically. This strategy preserves small parameter updates while still exploiting the memory and compute benefits of low-precision arithmetic. Optimizers like Adam, which maintain second-moment estimates, also benefit from being maintained in higher precision to avoid numerical instability.

Another tactic to reduce rounding error is block-wise or hierarchical accumulation. Instead of summing all $n$ products in low precision, divide the sum into blocks of size $k$ where each block's partial sum is computed in higher precision; then sum the partial sums in higher precision as well. This reduces error and can be tuned to hardware limitations (register widths, SIMD lane widths). Pairwise summation and Kahan compensated summation are algorithmic strategies for reducing error in accumulation. Kahan summation keeps a running compensation variable to capture lost low-order bits; while effective in software, it is more expensive and often hard to map onto specialized hardware pipelines, so hardware designers prefer to increase accumulator precision or leverage FMA.

The choice of rounding mode during accumulation also matters. Round-to-nearest is usually best for reducing bias, but stochastic rounding in accumulation can improve convergence in low-precision training by preventing systematic loss of small values. Some recent research shows that stochastic rounding or small-bias-preserving rounding schemes can enable successful training even with extremely low-precision formats if used appropriately in gradients and accumulators.

Finally, numerical stability considerations should guide when and where to use low precision. Layers that are scale-sensitive (e.g., softmax over a wide dynamic range, normalization layers) or operations that compute small differences between large numbers are more sensitive to precision loss. Practical mixed-precision systems often use precision-aware heuristics: compute these sensitive operations in FP32 or BF16, while using FP16/FP8 for bulk linear algebra. Profiling and careful validation are essential to ensure the model's accuracy is not degraded by precision changes.

# Conclusion

Floating-point formats define the rules of engagement for numerical computation in machine learning. Understanding the semantics of IEEE-754 FP32 provides a baseline for reasoning about numerical errors, while half-precision formats FP16 and BF16 show different ways to trade precision for dynamic range. Emerging FP8 designs push these tradeoffs further, forcing careful algorithm and hardware co-design. Rounding modes, subnormals, infinities, and NaNs determine how out-of-range and indeterminate results behave, and choices such as flushing subnormals can have both performance and numerical consequences. Mixed-precision techniques—using low-precision storage and arithmetic with higher-precision accumulation or master copies—allow most of the computational workload to benefit from reduced memory and increased throughput, while preserving the numerical fidelity needed for reliable training and inference. When reading research papers or designing systems, always examine exponent and mantissa widths, accumulator behavior, rounding policies, and which tensors are kept in higher precision; these details critically shape both performance and correctness.

Introduction

Quantization is the process of mapping continuous or high-precision numerical values to a smaller set of discrete values. In machine learning, quantization is widely used to reduce the memory footprint, bandwidth, and computational cost of tensors (weights, activations, gradients) while attempting to retain model accuracy. Practical quantization techniques must balance competing objectives: low bit-width for efficiency, small accuracy loss, and robustness across different layers and workloads. This chapter focuses on practical quantization approaches for tensors, strategies to choose quantization ranges, how to handle outliers, stochastic or biased quantization variants, and metrics to evaluate quantization quality. The goal is to give you intuition and concrete formulas so you can both implement quantization schemes and read research papers that propose new quantization methods.

# Per-tensor vs per-channel/per-block quantization

The simplest form of quantization applies the same scaling and zero-point to all elements of a tensor; this is known as per-tensor quantization. Suppose we have a floating-point tensor $X$ with elements $x$. In an affine quantization model we map real value $x$ to an integer $q$ via
\[
q = \operatorname{round}\left(\frac{x}{S}\right) + Z,
\]
where $S>0$ is a scale factor and $Z$ is a zero-point (typically an integer) chosen so that the real zero maps exactly to $q=Z$. Recovering the approximate real value is done by
\[
\hat{x} = S (q - Z).
\]
Per-tensor quantization sets a single scale $S$ and zero-point $Z$ for the entire tensor. The principal advantage is simplicity: storage overhead is minimal (two scalars) and the resulting integer arithmetic can be highly efficient because all elements share a uniform interpretation. Per-tensor quantization works well when the dynamic range of values across the tensor is relatively uniform.

However, many neural network tensors are heterogeneous: channels (e.g., output channels of a convolution layer) can have widely different magnitudes or distributions. Per-channel quantization addresses this by assigning a separate scale (and optionally zero-point) to each channel. For a weight tensor with shape $(C_{\text{out}}, C_{\text{in}}, K_h, K_w)$, per-channel quantization would use a scale $S_c$ for each output channel $c$. The quantization and dequantization for element $x_{c,i,h,w}$ become
\[
q_{c,i,h,w} = \operatorname{round}\left(\frac{x_{c,i,h,w}}{S_c}\right) + Z_c,\qquad
\hat{x}_{c,i,h,w} = S_c (q_{c,i,h,w} - Z_c).
\]
Per-channel quantization generally yields lower quantization error than per-tensor when channel-wise distributions differ, and it has become standard for weight quantization in many quantized inference frameworks because storage overhead (one scale and zero-point per channel) is small relative to kernel size. It also lets integer matrix multiplication routines leverage channel-wise scaling either by pre-scaling accumulators or applying post-scaling per channel.

Between these extremes lies per-block quantization, where the tensor is partitioned into blocks (contiguous or structured groups of elements), and each block has its own scale and zero-point. Per-block is more flexible than per-tensor and less granular than per-channel; it offers a trade-off between compression/compute complexity and quantization error. For example, a long embedding matrix might be split into blocks of 128 columns, each block quantized separately. Per-block quantization can capture localized variability (e.g., different parts of a vocabulary) while keeping overhead modest.

Choosing between per-tensor, per-channel, and per-block depends on the tensor's role and distribution, the available hardware support, and the acceptable trade-off between memory/compute and accuracy. Per-channel is highly effective for weights of convolution and fully connected layers. For activations, per-tensor quantization is more common because activations change with input and per-channel activation quantization requires either additional runtime statistics or more complex accumulator management. Per-block is especially useful for very large tensors (embeddings, attention matrices) where full per-channel quantization would be costly.

# Static vs dynamic range scaling

Range scaling determines the scale factor $S$ and possibly zero-point $Z$ used in quantization. Two broad strategies appear in practice: static (offline) scaling and dynamic (runtime) scaling. Static scaling uses calibration data or statistics gathered ahead of inference to compute ranges, while dynamic scaling computes ranges on the fly for each tensor instance during inference.

In static scaling, one runs representative input data (a calibration set) through the unquantized model and records per-layer statistics, typically minimum and maximum values or something like a percentile-based bound. The scale $S$ is then chosen from those statistics. For symmetric uniform quantization without zero-point, a common choice is
\[
S = \frac{\max(|x_{\min}|,|x_{\max}|)}{2^{b-1}-1},
\]
where $b$ is the bit-width for signed quantization. Using calibration allows static scales to reflect the data distribution seen in typical operation and yields reproducible behavior; there is no runtime overhead to measure ranges. However, it can fail when real-world inputs differ substantially from calibration data. It also cannot adapt to per-batch or per-input shifts that sometimes occur in dynamic workloads.

Dynamic scaling measures the range for each tensor instance at runtime, e.g., computing $\min(x)$ and $\max(x)$ for the current activation tensor. The scale is then computed per batch or per inference pass. Dynamic scaling can adapt to changing input distributions and potentially preserve accuracy better than static scaling in the presence of distribution shift. The downside is runtime overhead: the min/max pass adds memory accesses and compute and may require special support to keep latency low. Dynamic scaling can also introduce instability if ranges vary widely from batch to batch; this can increase variance in quantized outputs.

A middle ground uses hybrid approaches: collect statistics offline but adjust them at runtime with lightweight heuristics. Typical hybrid techniques clamp the dynamic range using calibrated bounds: if the runtime max exceeds the calibrated max, you may clip (clamp) values to the calibrated max or increase the scale with some smoothing to avoid large jumps. Another practical hybrid is to use running estimates (exponential moving averages) of per-layer ranges computed across observed batches, thus enabling gradual adaptation.

Beyond min/max, other choices for scale computation reduce sensitivity to outliers. For instance, one can use percentile-based bounds: choose $x_{\min}=p_{0.1\%}$ and $x_{\max}=p_{99.9\%}$ where $p$ denotes a percentile, ignoring extreme tails that may be caused by rare spikes. The scale then targets the bulk of the distribution. When combined with clipping, this can reduce quantization noise for the majority of values while handling outliers explicitly (see the outlier strategies section).

In short, static calibration is efficient and stable when calibration data matches deployment data; dynamic scaling adapts but costs runtime overhead; hybrid methods try to get the best of both worlds.

# Block quantization and its motivations

Block quantization partitions tensors into small blocks and quantizes each block independently, often using per-block scale and zero-point parameters. The size and arrangement of blocks depend on the tensor shape and hardware characteristics. Block quantization is motivated by several practical considerations.

First, many large tensors exhibit local correlations: nearby rows, columns, or contiguous memory regions often have similar statistical properties. Per-block quantization exploits this locality to achieve lower quantization error than per-tensor methods without the full parameter overhead of per-element or per-channel quantization. For example, in an embedding matrix, the representations for semantically related tokens may cluster in contiguous index ranges, making block quantization effective.

Second, block quantization enables efficient mixed-precision and structured compression strategies. Some implementations store low-precision integer values compactly (e.g., 4 bits per weight) and also store a per-block scale. Decoding during inference then applies the per-block scale to reconstruct approximate floating values. Blocks provide a unit for vectorized dequantization and can align well with SIMD widths or cache lines, improving memory throughput. Additionally, blocks can be chosen to match compute tiles used by low-precision matrix multiplication kernels, minimizing overhead from scale application.

Third, block quantization supports specialized encoding strategies that reduce storage further. For instance, a common approach with 4-bit quantization is to pack 16 4-bit values into a 64-bit word for storage and then apply per 16-value-block scaling at runtime. Some advanced schemes also store a small high-precision “residual” per block to compensate for systematic bias introduced by coarse quantization. Block-based residual correction combines a low-bit base quantization with a small high-precision correction term per block, yielding accuracy close to higher-bit formats with most of the storage savings.

Finally, blocks make it easier to handle outliers. One approach is to detect outlier elements within a block (values that exceed the block’s representable range) and keep them in higher precision separately, while quantizing the rest to low precision. This hybrid maintains compact representation for the majority of elements while preserving accuracy for a few extreme values.

Designing block size is a practical trade-off. Smaller blocks reduce quantization error and outlier influence but increase overheads (more scales to store, more metadata, potentially less efficient memory access patterns). Larger blocks decrease overhead but can worsen error. The right block size depends on the tensor's structure and the target hardware. For embeddings and attention matrices, block sizes like 64-256 columns are common; for convolutional kernels, per-channel (equivalent to blocks of one channel) often suffices.

# Stochastic/biased quantization variants

Most of the quantization schemes described so far are deterministic and introduce a deterministic rounding error. An alternative is stochastic quantization, where the quantizer randomly chooses between neighboring quantized levels according to probabilities that ensure an unbiased expectation. For uniform scalar quantization with step size $S$, given a real value $x$ with normalized coordinate $u = x/S$, let $\lfloor u \rfloor = k$ and fractional part $r = u - k$. Stochastic rounding maps $x$ to $k$ with probability $1-r$ and to $k+1$ with probability $r$. The expectation of the quantized value is exactly $u$, so the dequantized expectation is unbiased:
\[
\mathbb{E}[\hat{x}] = S \mathbb{E}[q] = S u = x.
\]
Stochastic rounding can be beneficial in training, particularly when gradients are small relative to quantization steps; unbiased stochastic rounding preserves expected gradients and mitigates bias accumulation. It also helps to avoid deterministic truncation that could lead to convergence problems when many small updates cancel out deterministically.

However, stochastic quantization increases variance: each quantized realization deviates randomly from the true value, and variance can slow convergence or degrade inference determinism. In inference, stochastic quantization is less common because it introduces nondeterminism and may complicate debugging. Some production systems use stochastic quantization during training but switch to deterministic rounding for inference after finalizing scale parameters.

Biased quantization intentionally introduces a systematic bias because it reduces variance or improves a different objective (e.g., minimax error). One example is midpoint rounding with tie-breaking toward even integers (banker’s rounding) or deterministic floor/ceil rounding. Another biased variant is quantization with clamping and asymmetric ranges where zero-point is forced to an integer to preserve sparsity patterns; this introduces bias but can maintain properties useful for integer inference kernels.

A hybrid approach is dithered quantization, where small random noise (dither) is added to the signal before deterministic rounding and subtracted after dequantization if possible. If the dither has certain statistical properties, it can decorrelate quantization error from the signal, yielding desirable noise characteristics. Dithering produces an unbiased estimator of the original signal if the dither is known and removed, but in many practical implementations the dither is not removed, so it behaves similarly to stochastic rounding with controlled properties.

In summary, stochastic quantization provides unbiased expectation and can aid training, but increases variance and nondeterminism. Biased quantization simplifies implementation and reduces variance at the cost of systematic error. Choice depends on whether you value unbiasedness for gradient preservation or low variance and determinism for inference.

# Error metrics: RMSE, relative error, worst-case error

Quantization quality is measured by several metrics; choosing the right metric depends on the downstream sensitivity of the model and the distribution of values.

Root-mean-square error (RMSE) is a common overall measure of quantization distortion. For a set of $N$ values $x_i$ and dequantized approximations $\hat{x}_i$, RMSE is
\[
\operatorname{RMSE} = \sqrt{\frac{1}{N}\sum_{i=1}^N (x_i - \hat{x}_i)^2}.
\]
RMSE aggregates squared errors and emphasizes large deviations due to the squaring operation. It correlates well with mean-squared-error (MSE) objectives and is useful when error energy matters (e.g., in least-squares contexts). RMSE is scale-dependent: larger magnitude tensors naturally produce larger RMSE even if relative error is small, so it is often useful to normalize RMSE by the signal energy or the dynamic range.

Relative error provides scale-invariant assessment. One per-element relative error is
\[
e_i^{\text{rel}} = \frac{|x_i - \hat{x}_i|}{|x_i| + \epsilon},
\]
where $\epsilon$ is a small constant to prevent division by zero. A global relative metric can be the mean relative error,
\[
\text{MRE} = \frac{1}{N}\sum_{i=1}^N e_i^{\text{rel}},
\]
or the median relative error, which is robust to outliers. Relative error is particularly informative when small absolute values are important proportionally — for instance, when quantizing gradients or probabilities. Be cautious: relative error becomes unstable near zero, hence the need for $\epsilon$ or ignoring near-zero elements in analysis.

Worst-case error, or minimax error, focuses on the largest single deviation:
\[
\text{Worst-case} = \max_{i} |x_i - \hat{x}_i|.
\]
Worst-case metrics are relevant when a single large error can catastrophically affect downstream computation, for example in control loops or when quantization error can push an activation into a different activation regime (e.g., across a ReLU threshold). Minimizing worst-case error often motivates uniform-range calibration or explicit outlier handling.

Beyond these basic statistics, other error measures provide richer information. Peak signal-to-noise ratio (PSNR) is often used in signal processing:
\[
\text{PSNR} = 10 \log_{10}\left(\frac{\max_i x_i^2}{\operatorname{MSE}}\right).
\]
For tensors with signed values, a more appropriate numerator is the squared maximum absolute value. Signal-to-quantization-noise ratio (SQNR) characterizes power ratios. When pairs of tensors are used in downstream linear algebra (e.g., matrix multiplications), one can measure the error after the operation (e.g., MSE of the product) rather than elementwise error, which can be more predictive of final model accuracy.

Distribution-aware metrics are also useful. For example, computing the cumulative distribution function (CDF) of absolute errors or relative errors allows inspection of quantile errors: what fraction of elements have error below a target. Reporting 90th or 99th percentile absolute or relative error communicates tail behavior better than mean statistics.

Finally, it’s important to measure the impact of quantization on end-to-end model metrics (accuracy, F1, BLEU, etc.) because low RMSE does not guarantee negligible effect on task performance, and some layers are more sensitive than others. Sensitivity analysis by quantizing one layer at a time while keeping others in full precision is a practical way to identify layers that require finer quantization or special treatment.

# Strategies for handling outlier activations

Outliers — a small number of elements with magnitudes much larger than the bulk of the distribution — are a major practical problem for quantization. If scale factors are set by absolute min/max, a single outlier can blow up the dynamic range and force coarse resolution for most elements, increasing quantization noise. Several strategies have been developed to mitigate outliers.

Clipping (or truncation) is the simplest approach: identify a cap $C$ and clamp values to the interval $[-C, C]$ before quantization. Choosing $C$ can be based on percentiles computed during calibration (e.g., clip at the 99.9th percentile) or heuristic multiples of the standard deviation. Clipping reduces dynamic range and improves resolution for the majority of values, at the cost of introducing systematic bias for clipped elements. In many networks, clipping a tiny fraction of activations has negligible effect on final accuracy because those outliers are not critical. However, aggressive clipping can harm performance if important signal resides in the tails.

Outlier-aware hybrid precision stores outliers at higher precision while keeping the majority of values low precision. The mechanism is: during quantization, mark elements exceeding a chosen threshold as outliers and keep them in, say, 16-bit or 32-bit float, while quantizing the rest to 8-bit or lower. At inference, operations must combine the quantized bulk and sparse high-precision outliers. For dense matrix operations, this can be implemented as the sum of a low-precision multiply-plus-accumulate for the quantized portion and a sparse high-precision contribution for the outliers. This approach maintains accuracy while keeping most of the storage and compute benefits but requires more complex kernels to handle mixed precision.

Block-level outlier handling detects blocks whose local ranges are dominated by a few extreme elements and treats them specially. For example, a block might be quantized normally if its max absolute value is within an acceptable bound; otherwise, the block could either be split, use a larger bit-width, or keep a small mask of outliers with higher precision. This is attractive because outliers are often localized, and block-level handling reduces metadata overhead relative to per-element marking.

Statistical transformations can reduce the influence of outliers before quantization. For instance, applying a channel-wise or per-block mean subtraction or whitening transforms the distribution so that tails are less heavy. Batch normalization layers already help by normalizing activation distributions during training, though at inference batch statistics may not be available. Logarithmic or power-law transforms compress dynamic range (e.g., using $x \mapsto \operatorname{sign}(x)\log(1+|x|)$) but are nonlinear and complicate arithmetic during inference.

Quantization-aware training (QAT) offers another route. During training, simulate quantization (including clipping and stochastic rounding) and allow the network to adapt weights so that activations become more quantization-friendly. Networks trained with QAT often learn to avoid producing extreme outliers or to make the signal robust to the induced distortion. Although QAT adds training complexity and time, it is highly effective and widely used when low-bit precision is required.

Finally, heuristics like per-sample or per-batch normalization, or the use of activation functions that limit extreme values (e.g., scaled Tanh instead of unbounded ReLU) can reduce outliers. Still, any modification must be evaluated for its effect on model performance.

Conclusion

Practical quantization combines statistical modeling of tensor distributions, careful selection of quantization granularity (per-tensor, per-channel, per-block), choice between static and dynamic range strategies, and specific mechanisms to handle outliers. Stochastic and biased quantization schemes provide different trade-offs between bias and variance, and error metrics such as RMSE, relative error, and worst-case error help quantify distortion in complementary ways. Understanding these techniques and their trade-offs is essential to implementing robust quantized models and interpreting research that proposes new quantization methods. When designing or evaluating a quantization pipeline, always measure both tensor-level distortion and end-to-end model metrics, and consider hybrid approaches (block quantization, outlier-aware storage, QAT) that address the practical realities of modern neural network workloads.

Introduction

Randomized orthogonal transforms are a family of simple, computationally efficient linear maps that preserve Euclidean geometry while redistributing mass across coordinates. They are widely used in signal processing, compressive sensing, randomized numerical linear algebra, and machine learning to reduce quantization error, make data more "incoherent" with respect to simple bases, and control the influence of outliers. The key features are twofold: (1) they are orthogonal or nearly orthogonal so they preserve lengths and inner products, and (2) they can be implemented quickly with structured transforms such as the Hadamard transform combined with random diagonal sign matrices. In this chapter we build intuition and mathematical understanding of these transforms. We begin with the formal notion of orthogonality for matrices and explore invariance properties. We then study random diagonal sign matrices and their effect on vectors and distributions. Next we introduce the Hadamard transform, its recursive definition, and the fast $O(d\log d)$ implementation. We bring the ideas together in structured random orthogonal transforms (random signs composed with Hadamard) and close with concrete use-cases: how such transforms produce incoherent representations and reduce quantization error and the influence of outliers.

# Orthogonal matrices and invariance properties (M M^T = I)

An orthogonal matrix $M \in \mathbb{R}^{d\times d}$ is defined by the property
$M M^{T} = I$, where $I$ is the $d\times d$ identity matrix. Equivalently, $M^{T}M = I$. This condition means that the columns (and rows) of $M$ form an orthonormal basis of $\mathbb{R}^{d}$. Orthogonality implies several important geometric invariances that make orthogonal matrices extremely useful.

First and most basic, orthogonal matrices preserve Euclidean norms. For any vector $x\in\mathbb{R}^{d}$,
\[
\|Mx\|_{2}^{2} = (Mx)^{T}(Mx) = x^{T}M^{T}Mx = x^{T}x = \|x\|_{2}^{2},
\]
because $M^{T}M=I$. Thus orthogonal transforms do not amplify or shrink the overall energy of a vector; they only rotate and reflect the coordinate system. This property is crucial when we want to manipulate coordinates (for example to make them "more uniform") without changing overall magnitudes or inner products.

Second, orthogonal matrices preserve inner products. For any vectors $x,y\in\mathbb{R}^{d}$,
\[
\langle Mx,My\rangle = (Mx)^{T}(My) = x^{T}M^{T}My = x^{T}y = \langle x,y\rangle.
\]
Thus distances and angles are preserved exactly. This strong invariance means that downstream algorithms that rely on geometry (nearest neighbors, orthogonal projections, or many numerical linear algebra algorithms) will see the same pairwise geometry after the transform.

Third, orthogonal matrices have spectral norm equal to one and determinant with absolute value one. Since all singular values of an orthogonal matrix are one, $\|M\|_{2} = 1$; and $\det(M) = \pm 1$, reflecting whether the orthogonal matrix is a rotation (determinant $+1$) or a reflection combined with rotation (determinant $-1$).

Finally, orthogonal matrices are invertible and their inverse is simply the transpose: $M^{-1} = M^{T}$. This makes it trivial to reverse transforms applied to data. Together, these invariances make orthogonal transformations ideal pre-processing steps where we want to change coordinate representation while preserving geometric structure.

# Random diagonal sign matrices and their effect

A particularly simple class of orthogonal matrices is diagonal sign matrices. Let $D$ be a $d\times d$ diagonal matrix with diagonal entries $D_{ii} = s_{i}\in\{\pm 1\}$. Then $D D^{T} = D^{2} = I$, because each diagonal entry squared is one. Thus any sign diagonal matrix is orthogonal. Random diagonal sign matrices arise when the signs $s_{i}$ are chosen independently at random, usually Rademacher variables with $\Pr(s_{i}=+1)=\Pr(s_{i}=-1)=1/2$.

At a deterministic level, multiplying a vector $x$ by $D$ simply flips the sign of some coordinates: $(Dx)_{i} = s_{i} x_{i}$. Because $D$ is orthogonal, norms and inner products are preserved exactly. However, randomizing signs has powerful distributional consequences.

If $s_{i}$ are independent Rademacher variables and $x$ is a fixed vector, then each coordinate of $Dx$ becomes a random variable that is $+x_{i}$ or $-x_{i}$ with equal probability. This has the effect of symmetrizing any deterministic bias in the coordinates. When combined with other transforms such as the Hadamard matrix (see below), random signs break unwanted structure: for example, they remove consistent alignment between a fixed basis (like the standard basis) and the input vectors. Random sign flips also make different coordinates independent in sign, which can simplify concentration analyses.

There are important moment and tail properties to note. For fixed $x$, the coordinate-wise distribution of $Dx$ is bounded by $|x_{i}|$. By Hoeffding or Bernstein inequalities, linear functionals of the random sign vector behave sub-Gaussianly. For example, if $a\in\mathbb{R}^{d}$ is fixed, then
\[
\langle a, Dx\rangle = \sum_{i=1}^{d} a_{i} s_{i} x_{i}
\]
is a sum of independent mean-zero terms, and its tails can be bounded in terms of $\sum_{i} (a_{i}x_{i})^{2}$. This underpins many randomized algorithms: random sign matrices render inner products and sums amenable to concentration inequalities.

Random sign matrices also reduce coherence between input vectors and coordinate axes. If a vector $x$ is sparse or has a few very large coordinates, applying a random sign diagonal alone does not change magnitudes, but when followed by a dense orthogonal mixing (like a Hadamard transform) the large entries get spread across many coordinates. Even on their own, random sign flips are used in variance reduction and preprocessing steps because they remove deterministic sign patterns that might increase worst-case error in subsequent algorithms.

# Hadamard transform: definition and fast O(d log d) implementation

The (Walsh-)Hadamard transform is a structured orthogonal matrix with entries $\pm 1$ and a recursive construction that supports extremely fast matrix-vector multiplies. For dimensions that are powers of two, the Hadamard matrix $H_{d}$ of size $d\times d$ is defined recursively. The base case is $H_{1} = [1]$. For $d = 2k$ (with $k$ a power of two half the dimension), define
\[
H_{2k} = \begin{bmatrix}
H_{k} & H_{k} \\
H_{k} & -H_{k}
\end{bmatrix}.
\]
Equivalently, for $d=2^{m}$, $H_{d}$ is the $m$-fold Kronecker product of $H_{2} = \begin{bmatrix}1 & 1\\ 1 & -1\end{bmatrix}$ with itself. By construction, $H_{d}H_{d}^{T} = d I$, i.e., $H_{d}$ is orthogonal up to scaling. It is standard to work with the normalized Hadamard matrix $\tfrac{1}{\sqrt{d}} H_{d}$ so that $(\tfrac{1}{\sqrt{d}}H_{d})(\tfrac{1}{\sqrt{d}}H_{d})^{T} = I$.

The Hadamard transform maps an input vector $x\in\mathbb{R}^{d}$ to $H_{d}x$ via a sequence of pairwise additions and subtractions defined by the recursion. The critical computational fact is that this can be done in $O(d\log d)$ arithmetic operations using a divide-and-conquer algorithm analogous to the fast Fourier transform (FFT). The algorithm, often called the fast Walsh–Hadamard transform (FWHT), proceeds in $\log_2 d$ stages. At each stage, it replaces blocks of the current array by pairwise sums and differences, halving the effective block size each time.

Concretely, if $d=2^{m}$ and we index coordinates from $0$ to $d-1$, the FWHT can be implemented in-place as follows. For stage $r=0,\dots,m-1$, let the block size be $2^{r+1}$. For each block and each index within the first half of the block, replace the pair $(u,v)$ by $(u+v,u-v)$. After $m$ stages this produces $H_{d}x$. Each stage performs $d$ additions/subtractions, so the total number is $d \log_2 d$. If one uses normalized Hadamard $\frac{1}{\sqrt{d}}H_{d}$, a final scaling by $1/\sqrt{d}$ is required.

The FWHT is numerically stable for integer or floating-point arithmetic of reasonable precision because it only uses additions and subtractions and involves no division except for the final normalization. It is memory friendly and can be implemented in place. If $d$ is not a power of two, one can embed the vector into a slightly larger power-of-two-size vector by zero-padding or use other orthogonal transforms with similar properties (discussed below).

The Hadamard transform also has a simple spectral interpretation: it diagonalizes certain convolution-like operations and converts correlations across certain combinatorial patterns into coordinate-wise products. But the central practical property for our purposes is that $H_{d}$ is very structured (only $\pm 1$ entries), orthogonal up to scaling, and extremely fast to apply.

# Structured random orthogonal transforms (signs + Hadamard)

A powerful and commonly used structured random orthogonal transform is the composition of a random diagonal sign matrix and a normalized Hadamard matrix. One common form is
\[
T = \frac{1}{\sqrt{d}} H_{d} D,
\]
where $D$ is a random diagonal with Rademacher entries and $H_{d}$ is the $d\times d$ Hadamard matrix. Because $D$ is orthogonal and $\tfrac{1}{\sqrt{d}}H_{d}$ is orthogonal, their product $T$ is orthogonal. This transform has three useful features: randomness (through $D$), uniform mixing (through $H_{d}$), and computational efficiency (the product $T x = \tfrac{1}{\sqrt{d}}H_{d}(Dx)$ can be computed in $O(d\log d)$ time via FWHT).

Why include the random diagonal $D$ at all, since $H_{d}$ is already orthogonal and mixes coordinates? The reason is that $H_{d}$ alone has a fixed structure and can be coherent with certain inputs. For example, if the input vector $x$ equals a row of $H_{d}$, then $H_{d}x$ will be sparse (it will align strongly), causing undesired concentration in a few coordinates after transformation. Randomizing signs before applying $H_{d}$ breaks such alignments: drawing $D$ at random virtually guarantees that $Dx$ will not align systematically with $H_{d}$’s fixed structure. In many probabilistic analyses this sign randomization is crucial to obtain concentration results that are uniform over all inputs.

The structure can be extended further. One widely used variant is the Subsampled Randomized Hadamard Transform (SRHT). The SRHT is typically written as
\[
S = \sqrt{\frac{d}{m}} R \, \frac{1}{\sqrt{d}} H_{d} D,
\]
where $D$ is as above, $H_{d}$ is the normalized Hadamard, and $R$ is an $m\times d$ sampling matrix that selects $m$ rows uniformly at random (sometimes with replacement, sometimes without) or performs randomized subsampling. The factor $\sqrt{d/m}$ normalizes expected norms. The SRHT is an efficient way to map a $d$-dimensional vector to an $m$-dimensional sketch while approximately preserving geometry (with Johnson–Lindenstrauss-style guarantees), and it can be applied in $O(d\log d)$ time to form the $m$-vector $Sx$.

The appeal of structured random transforms like $H_{d}D$ and SRHT is that they combine the distributional advantages of dense random orthogonal matrices (which are conceptually ideal but costly: e.g., draws from the Haar distribution require $O(d^{3})$ operations to sample and $O(d^{2})$ to apply) with much lower computational cost. Whereas a dense random orthogonal matrix mixes all coordinates with random correlations, $H_{d}D$ achieves similar mixing properties while being deterministic and fast up to a simple random sign diagonal. Analysis shows that for many downstream tasks (approximate matrix multiplication, randomized SVD, Johnson–Lindenstrauss embeddings), SRHTs can replace Gaussian or Haar matrices at a large improvement in speed and memory while retaining comparable probabilistic guarantees, up to logarithmic factors in $d$.

Structured transforms can be generalized beyond Hadamard: one can use randomized Fourier transforms (multiply by random signs then FFT), discrete cosine transforms, and other orthonormal bases with fast algorithms. The common recipe is random diagonal (or random permutations and diagonal) plus a fast orthogonal transform.

# Use-cases: incoherent processing and reducing quantization error

Incoherent processing

A central concept that explains much of the utility of randomized orthogonal transforms is incoherence. A system is called coherent if some signals align strongly with a small subset of basis vectors (i.e., energy is concentrated in a few coordinates). Incoherence, on the other hand, means energy is spread more uniformly across coordinates. Many algorithms—compressed sensing, sparse recovery, compressed learning, and randomized linear algebra—perform best when signals are incoherent relative to the measurement basis.

Randomized orthogonal transforms convert coherent representations into incoherent ones. Consider a vector $x$ with one very large coordinate and the rest small. If one measures $x$ in the standard basis, that large coordinate dominates. But if we apply $T=\tfrac{1}{\sqrt{d}}H_{d}D$ and measure $Tx$, then with high probability the vector $Tx$ has entries of size about $\|x\|_{2}/\sqrt{d}$ (up to modest fluctuations). Intuitively, the Hadamard mixing distributes the energy of the large coordinate across all outputs, and the random sign prevents adversarial cancellation patterns. More formally, for fixed $x$, the coordinates $(Tx)_{i}$ are mean-zero random variables whose variances sum to $\|x\|_{2}^{2}$ and are typically of size about $\|x\|_{2}^{2}/d$. Concentration inequalities (Chernoff/Hoeffding/Khintchine-type bounds) then show that with high probability no coordinate exceeds, say, $C\|x\|_{2}/\sqrt{d}$ for a modest constant $C$.

This property is exploited in compressed sensing when one wants to measure sparse signals: by making measurements incoherent with the sparsifying basis, one satisfies conditions (like the restricted isometry property) that guarantee stable recovery. In randomized numerical linear algebra, when computing low-rank approximations, one applies SRHT to the columns of a matrix to produce sketches that are well spread so that uniform column sampling suffices to capture global structure.

Reducing quantization error and handling outliers

Another important use-case is reducing quantization error. Quantization maps continuous-valued coordinates to a finite set of levels (for storage, transmission, or limited precision arithmetic). The error introduced by scalar quantization of a coordinate depends on that coordinate’s magnitude: larger magnitudes typically produce larger absolute quantization errors, or require more bits to represent to a given relative accuracy. If a vector has a few large entries (outliers), scalar quantization applied coordinate-wise will produce large absolute errors on those coordinates, possibly dominating overall error.

By applying an orthogonal transform that spreads the mass (such as $T=\tfrac{1}{\sqrt{d}}H_{d}D$), the mass of the large entries is redistributed over many coordinates. After the transform, every coordinate is smaller in magnitude and more uniform, so uniform scalar quantization produces much smaller maximum absolute error and often smaller mean squared error. Because the transform is orthogonal, the overall energy is preserved; thus when we invert the transform after quantizing the transformed vector, the expected reconstruction error is comparable to the quantization noise energy but no longer concentrated in a few coordinates. In simple terms, orthogonal randomization converts a hard worst-case quantization problem (dominated by a few large entries) into an average-case problem where error is spread evenly and hence controlled.

A quantitative view: suppose you uniformly quantize each coordinate of $y = Tx$ with step size $\Delta$. The squared quantization error per coordinate is at most $(\Delta/2)^{2}$, so the total squared error after quantization in the transformed domain is at most $d(\Delta/2)^{2}$. When we apply the inverse orthogonal transform (its transpose), the squared error remains the same (orthogonality preserves norm). If the transform has successfully reduced the dynamic range of coordinates, one can choose $\Delta$ smaller than what would have been necessary for the original coordinates to achieve the same overflow avoidance, reducing total error. This is the basic mechanism by which transforms such as randomized Hadamard reduce quantization error given a fixed bit budget.

Outlier mitigation follows the same logic. A sensor spike or adversarial large coordinate becomes spread into many small perturbations after transform and is therefore easier to tolerate by downstream algorithms that average or perform robust aggregation. Additionally, randomization helps against structured adversaries: because the diagonal sign is chosen at random, an adversary that knows only the transform class but not the specific random signs cannot concentrate its attack onto coordinates that remain extreme after transform.

Other practical uses

Beyond the two main uses above, randomized orthogonal transforms are used in many practical tasks. They accelerate sketching algorithms for least squares and low-rank approximation: applying an SRHT to a tall matrix before subsampling rows or columns yields sketches that preserve the column space. They serve as randomized preconditioners to improve the conditioning of least squares problems. They are used to implement fast, low-distortion Johnson–Lindenstrauss embeddings: mapping $x$ to a small number of randomly sampled Hadamard coordinates gives a dimension-reduced vector that preserves pairwise distances with high probability. They are also used in randomized feature maps and for fast randomized SVD computations. The unifying theme is that randomness plus a structured, fast mixing operation provide most of the statistical benefits of dense random matrices at dramatically reduced computational and storage cost.

Conclusion

Randomized and fast orthogonal transforms are a compact, powerful toolkit: orthogonality provides exact geometric invariants; random diagonal signs provide randomness that breaks alignment and enables concentration; the Hadamard transform supplies rapid, uniform mixing with a provably fast $O(d\log d)$ algorithm. Compositions of these elements yield practical transforms such as $\frac{1}{\sqrt{d}}H_{d}D$ and SRHT that are both analyzable and computationally attractive. These transforms produce incoherent representations, reduce quantization error and the impact of outliers, and accelerate many randomized linear algebra and signal processing algorithms. Understanding their algebraic properties, probabilistic behavior, and efficient implementations is essential for both theoretical analysis and practical deployment in modern data processing systems.

Introduction

Modern graphics processing units (GPUs) are highly parallel processors designed to deliver very high throughput for data-parallel workloads. Deep learning attention mechanisms, with their combination of massive matrix multiplies, indexed memory accesses, and reductions, stress many aspects of GPU design. To tune attention implementations and to read research about GPU-optimized attention (for example, sparse or approximate attention kernels), you need a clear mental model of the GPU hardware blocks that do the work and the memory system they rely on. This chapter describes the hardware building blocks most relevant to attention workloads: streaming multiprocessors (SMs) and their resources, the multi-level memory hierarchy from high-bandwidth DRAM down to registers, the trade-offs between bandwidth and capacity at different levels, how memory banking and coalescing affect access efficiency, and how GPUs hide memory latency through massive concurrency. The goal is to provide practical intuition and enough detail so you can understand why certain kernel designs are fast, why others are slow, and what levers you can use to improve performance.

# Streaming Multiprocessors (SMs) and their resources

A GPU chip is organized into multiple streaming multiprocessors (SMs). Each SM is an independent block that issues and executes instructions for many threads in parallel. Conceptually an SM is a vector machine that implements Single-Instruction Multiple-Thread (SIMT) execution: multiple threads execute the same instruction stream in lockstep when they belong to the same warp. A warp is a fixed-size group of threads (commonly 32 threads on NVIDIA architectures) that share the instruction pointer. The SM fetches and decodes instructions, issues them to arithmetic units, manages local memory such as registers and shared memory, and performs memory operations to higher levels of the memory hierarchy.

Key resources inside an SM include compute units (scalar ALUs, floating-point units, and specialized units such as Tensor Cores), a register file, shared memory (often called SMEM or scratchpad memory), and per-SM caches and scheduling hardware. Each of these resources is sized and organized to support many active warps simultaneously. The register file supplies operands to the processing units; shared memory allows fast inter-thread communication and data reuse within a thread block (CUDA block); and special functional units accelerate matrix operations and mixed-precision kernels frequently used in attention implementations.

The SM scheduler is central to GPU performance. It maintains a set of active warps and decides which warp’s next instruction to issue each cycle. Because memory operations have high latency, the scheduler switches to another ready warp when the current one stalls, seeking to keep execution units busy. This switching is very cheap compared to a CPU context switch because thread state is already resident in the SM (registers and program counter). The number of warps that can be active at once on an SM is limited by resource constraints: the number of available registers, the amount of shared memory allocated per block, and hardware limits on threads per SM and blocks per SM.

These resource limits give rise to the important concept of occupancy. Occupancy is the ratio of active warps (or threads) on an SM to the maximum possible. Higher occupancy generally gives more opportunity to hide latency, but occupancy is not the only determinant of performance; sometimes low-occupancy code that uses registers heavily and performs many computations per byte transferred can still be optimal. For attention kernels, occupancy is a useful guide because attention often mixes large memory transfers with compute—managing registers and shared memory to maximize useful concurrency is a standard tuning task.

SM-level resources are allocated per thread block (or cooperative group). When you launch kernels that implement attention operations (for instance, blocked matrix multiply or tiled softmax), you choose tile sizes so that each block’s shared memory and register usage allow enough blocks/warps to be resident on each SM to hide memory latency without oversubscribing limited resources.

# Memory hierarchy: global memory (HBM), L2 cache, shared memory (SMEM), registers

GPUs implement a hierarchical memory system that trades off capacity, bandwidth, and latency. From largest and slowest to smallest and fastest, the typical levels relevant to attention are: global DRAM (typically HBM), L2 cache (device-wide), per-SM caches (sometimes L1 data cache or texture cache), shared memory (SMEM), and registers. Understanding the properties of each level is essential because attention kernels often have different working-set sizes and reuse patterns that make them bottleneck at different levels.

Global memory: On modern GPUs global memory is implemented with high-bandwidth memory (HBM) stacks or GDDR memory. HBM provides very high aggregate bandwidth (hundreds to thousands of GB/s across the device) but comparatively large latency (hundreds of cycles or more). Global memory is coherent only at certain granularity and is accessible by all SMs. Because of its high latency, achieving close-to-peak bandwidth requires memory accesses from many threads to be organized to exploit wide buses (see memory coalescing below). The global memory capacity is large enough to hold model parameters and activations for attention networks in many settings.

L2 cache: Between DRAM and the SMs sits a device-wide L2 cache. L2 reduces DRAM traffic when multiple SMs request the same data or when a single SM reuses data across time beyond SM-local caches. L2 capacity and bandwidth moderate the pressure on global DRAM and can often capture substantial reuse for attention kernels, especially when queries, keys, and values are reused or when positional encodings are shared. However, L2 is smaller than DRAM and typically slower than SMEM or registers.

Per-SM caches and L1: Some GPU architectures include a per-SM L1 data cache or a configurable cache/shared memory region. This layer is useful for small amounts of cross-warp reuse or to accelerate random reads within a block. However, L1 sizes are limited and often optimized for streaming or spatial locality patterns, so random indexing (e.g., scatter-gather) can still miss frequently.

Shared memory (SMEM): Shared memory is an explicitly-managed on-chip scratchpad that resides inside each SM. It offers very low latency (tens of cycles) and high bandwidth when accesses are bank-aligned and conflict-free. Shared memory is the primary mechanism for data reuse within a thread block: for example, tiling matrix multiply and accumulating partial results by loading tiles of queries/keys/values into SMEM to be reused by many threads. Because shared memory is explicitly managed by software, kernel code must load from global memory into SMEM and then synchronize threads (e.g., with a barrier) before using the shared tile. The size per SM is limited (tens to hundreds of kilobytes), so careful tiling is required to balance usage with occupancy.

Registers: Registers are the fastest memory available and are private to each thread. They provide per-thread storage for scalar and vector temporaries and can be read and written at single-cycle latencies. Register files are large in aggregate but finite per SM; a kernel that uses too many registers per thread will reduce the number of resident threads and thus occupancy. Compilers try to keep frequently used variables in registers, but spilling to local memory (which is mapped to device memory) occurs if register pressure is too high—spilling is expensive and can transform fast register accesses into global-memory-like accesses.

When designing attention kernels, you often choose which data to keep in registers (per-thread small temporaries), which to place in shared memory (tiles reused by many threads within the block), and which to stream from global memory. For example, in a blocked attention implementation, a tile of keys and values might be loaded into SMEM so that many queries can be matched to the same tile of keys without repeated DRAM reads.

# Bandwidth vs capacity trade-offs across memory tiers

Every memory tier provides a trade-off between capacity and bandwidth (and latency). Registers are tiny per thread but provide the highest bandwidth and lowest latency. Shared memory offers more capacity and still high bandwidth. Caches have more capacity than SMEM and reduce DRAM accesses but are slower and often less predictable for random access. DRAM provides the largest capacity and high raw bandwidth, but with the highest latency. These trade-offs govern how you balance data placement and algorithm structure.

An intuitive way to reason about performance is the roofline model. Define peak compute throughput C_peak (e.g., in floating-point operations per second) and peak memory bandwidth B_peak (bytes per second) for the bottleneck level (e.g., global memory). For a kernel with arithmetic intensity I (flops per byte transferred), the achievable throughput is approximately:

$Throughput = \min\left(C_{peak},\; B_{peak} \times I\right)$.

If $I$ is small, the kernel is memory-bound: increasing compute capability will not help because data cannot be fed fast enough. If $I$ is large, the kernel is compute-bound. For attention kernels, the arithmetic intensity depends on how much reuse you can achieve. Naive attention implementations that read the entire key and value matrices for each query can have low intensity, whereas blocked attention that reuses key tiles across many queries increases $I$ by amortizing memory read cost over many operations.

Bandwidth and capacity also interact: a larger on-chip buffer (more shared memory) lets you hold bigger tiles and increase reuse, raising arithmetic intensity and shifting the kernel from memory-bound toward compute-bound. But shared memory is finite; allocating more SMEM per block reduces how many blocks can be active, which can lower occupancy and thus the ability to hide latency. Similarly, using more registers per thread can decrease occupancy. Thus there is a three-way trade-off: capacity (registers/SMEM) versus concurrency (occupancy) versus per-thread throughput. An optimal kernel configuration balances these to avoid both memory starvation and idle compute units.

Quantitatively, suppose loading a tile of size $T$ bytes into shared memory costs $T/B_{DRAM}$ seconds, and that tile supports $F$ floating-point operations. Then the amortized cost per flop is $(T/B_{DRAM})/F = 1/(I \times B_{DRAM})$ where $I = F/T$ is the arithmetic intensity for that tile. Making $T$ larger increases $F$ proportionally (if reuse is possible), increasing $I$ and reducing memory cost per flop, up to the point where SMEM capacity or occupancy becomes limiting.

# Banking, bank conflicts, and memory coalescing

Efficient use of on-chip and off-chip memory requires understanding how accesses are organized physically. Two important concepts are banked shared memory and coalesced global memory accesses.

Shared memory is usually divided into banks: multiple independent memory banks that can service concurrent accesses in parallel, increasing aggregate bandwidth. For example, a common organization is 32 banks, and each bank serves 32-bit (4-byte) words addressed with certain mapping rules. If multiple threads within a warp access different addresses that fall into different banks, the accesses are serviced in parallel. However, if two or more threads access different addresses that map to the same bank in the same cycle, a bank conflict occurs. The hardware must serialize these accesses, resulting in multiple cycles for what could otherwise have been a single-cycle operation. The severity of a bank conflict depends on how many accesses map to the same bank; with $k$ accesses to the same bank, the cost generally becomes proportional to $k$.

To reason about bank conflicts, you need the bank mapping function. A simple mapping for 32 banks and 4-byte words is:

$bank = \left(\frac{address}{4}\right) \bmod 32$.

So consecutive 4-byte words map to consecutive banks. However, when threads access 8-byte or larger elements (e.g., 64-bit floats), the mapping can change if the hardware supports wide accesses; some architectures collapse adjacent banks or use different bank-width rules. In attention kernels, when you store a tile of keys or values in shared memory, organize the layout so that threads in a warp access different banks when reading columns or rows. Padding is often used: adding a small offset to the row stride so that successive rows start in different banks, avoiding systematic collisions.

Global memory coalescing is another critical performance factor. Modern GPUs fetch global memory in wide transactions (cache lines or segments). If threads in a warp access addresses that fall within the same aligned segment and are arranged in a regular pattern, the hardware can coalesce the individual thread requests into a small number of wide transactions, maximizing DRAM efficiency. If accesses are scattered so that each thread’s address falls in a different segment, the result is many small transactions and poor effective bandwidth.

For typical 32-thread warps and 128-byte segment sizes, coalescing means that if the warp’s addresses fall within one or a small number of 128-byte segments, they can be fetched together. Many libraries organize data so each thread reads consecutive elements (e.g., each thread reads an element from an array with stride 1 across threads), which naturally coalesces. Attention workloads often perform strided or indexed loads (for example, gathering keys corresponding to specific indices). To coalesce such gathers, you can reorder data, use permutation-free layouts, or implement software gather strategies where multiple threads cooperate to fetch contiguous blocks into shared memory and then each thread extracts its needed element.

Bank conflicts in shared memory and poor coalescing in global memory both reduce effective bandwidth. Avoiding both requires careful layout and access pattern design. For instance, in a tiled attention kernel where each block loads a $T \times T$ tile of the key matrix into SMEM, store the tile with a row stride equal to the number of banks or add padding columns so that columns accessed by consecutive threads map to different banks. Likewise, when each warp wants to fetch a contiguous vector from global memory, make sure those vectors are laid out so that consecutive threads reference consecutive memory addresses.

# Latency hiding through concurrency

One of the defining features of GPU performance philosophy is latency hiding. Individual DRAM accesses may take hundreds to thousands of cycles. Rather than trying to reduce that latency (which is expensive and limited by physics), GPUs rely on massive concurrency: while one warp waits for memory, many other warps can run. The SM scheduler switches between warps every cycle or few cycles, so if you have enough independent work (enough active warps), the compute units remain busy and overall throughput can be high despite high individual access latencies.

This is why occupancy matters. With low occupancy (too few active warps), a memory stall in one warp may leave the SM underutilized because there is insufficient other ready work to schedule. With higher occupancy, there are more warps that can execute while others wait for memory. However, occupancy is not the only way to hide latency. Modern architectures also support techniques like instruction-level parallelism (ILP), prefetching, and asynchronous copies (e.g., CUDA’s cp.async) that let a thread launch a memory copy into shared memory and continue doing other work while the transfer proceeds.

To reason about latency hiding quantitatively, consider a simple model. Let $L$ be the average latency (in cycles) for a global memory access and let $T_{warp}$ be the number of cycles of useful work a warp can perform between dependent memory accesses. If a single warp issues a memory request and then is stalled for $L$ cycles, you would need roughly $W \approx L / T_{warp}$ independent warps to cover the latency (ignoring other overheads). In practice, because each warp may have several outstanding memory operations and because instruction pipelines overlap, fewer warps may suffice, but this formula gives intuition: larger latency or smaller per-warp work requires more warps.

Blocking and tiling increase $T_{warp}$ by letting each warp do more compute per loaded data chunk. For example, loading a tile of keys into shared memory and performing many dot products with different queries increases the amount of computation per tile load, reducing the number of times you must wait for DRAM per flop and lowering $W$ required. As noted earlier, raising $T_{warp}$ increases arithmetic intensity, shifting the kernel off the memory roofline.

There are practical mechanisms to overlap data movement and computation. Double-buffering is a common pattern: while the warp or block computes on tile A already in shared memory, it issues loads for tile B into another region or via asynchronous copy primitives. After finishing work on A, it switches to B while B is being filled. This pipeline reduces idle time. On more advanced GPUs, hardware support for asynchronous copies (memcpy-like device instructions) lets the SM manage data transfers with less CPU synchronization, making it easier to overlap.

However, there is a subtle interplay between latency hiding and resource allocation. Increasing per-block shared memory (to enable larger tiles and hence increase computation per load) may reduce the number of blocks that can be resident and therefore reduce the number of independent warps available for scheduling across the SM. The optimum lies where the product of per-block work and the number of resident blocks yields sufficient concurrency to mask latencies without wasting precious per-thread or per-block capacity.

Finally, there are algorithmic strategies to reduce stalls beyond simple concurrency. For attention, these include reordering computations to fuse operations (e.g., combining softmax and matrix multiply steps to reduce intermediate memory traffic), using mixed precision and Tensor Cores to increase computational throughput per memory byte, and reorganizing data such that high-reuse paths leverage shared memory and cache. Profiling tools that report achieved occupancy, memory throughput, and stall reasons are invaluable for pinpointing whether your kernel is latency-limited, bandwidth-limited, or compute-limited.

Conclusion

To design and analyze fast attention implementations on GPUs, you must understand the SM microarchitecture and the memory hierarchy: what resources are available, how capacity and bandwidth trade off across levels, and how access patterns interact with hardware features like banked shared memory and coalesced global transactions. Latency hiding via large numbers of warps and asynchronous data movement permits high throughput despite long DRAM latencies, but achieving that requires balancing shared memory and register usage against occupancy and tiling to maximize arithmetic intensity. With these principles in mind, reading and implementing research about attention (e.g., block-sparse attention, flash attention, or fused softmax kernels) becomes a matter of mapping algorithmic choices to hardware realities—choosing tiling, thread mappings, memory layouts, and synchronization points that make the best use of the SMs and the memory system.

Introduction

GPUs are designed to execute thousands of threads concurrently. To program them efficiently, you must understand how a GPU organizes those threads, how groups of threads are scheduled on hardware, and how limited on-chip resources (registers, shared memory, warp slots) constrain concurrency. This chapter explains the CUDA execution model (threads, warps, thread blocks/CTAs, and grids), how warps and blocks are scheduled on Streaming Multiprocessors (SMs), what "occupancy" means and how registers and shared memory affect it, and advanced coordination primitives such as cooperative groups and cluster scheduling ideas. We will also examine register allocation limits and the practical trade-offs between resource usage, occupancy, and per-thread performance. Wherever possible I will give concrete formulas and worked examples so you can compute occupancy for a kernel and reason about how to change a kernel configuration to run faster.

# CUDA execution model: threads, warps (32 threads), blocks (CTAs), grids

CUDA programs describe many lightweight threads that execute the same kernel function. The threads are organized hierarchically.

A thread is the basic unit of execution. Each thread has its own private registers and private portion of local memory (if register pressure forces spills). Threads are given unique indices (via built-in variables like $threadIdx$, $blockIdx$) so each thread can process different data.

A block, also called a Cooperative Thread Array (CTA) in older terminology, is a group of threads that can cooperate via fast on-chip shared memory and synchronize with barrier operations such as __syncthreads(). A block is the unit of scheduling onto an SM: the runtime maps whole blocks onto individual SMs. A block has a specified number of threads (e.g., 256 threads per block). Blocks are independent of one another: there is no implicit synchronization between different blocks in the same grid (except via kernel launch boundaries) unless you use special APIs for cooperative launch.

A grid is the collection of all blocks that a single kernel launch creates. A kernel launch executes a grid of blocks, and the runtime distributes blocks across SMs.

Warps are the critical hardware scheduling unit. A warp is a group of 32 threads (on current NVIDIA GPUs) that execute instructions in lockstep under the Single Instruction Multiple Thread (SIMT) model. When you write a kernel, the hardware groups threads into warps based on their thread indices. For example, threads with consecutive thread indices within a block are placed in the same warp. The warp size is fixed (32 on Nvidia GPUs). Conceptually, a warp executes one instruction at a time; if threads in the warp take different control-flow paths, the warp serializes those paths and masks out inactive lanes — a phenomenon known as divergence.

To summarize, an SM executes a number of warps from one or more blocks. The number of threads per block and the number of blocks that can be active on an SM are limited by hardware resources (registers, shared memory, maximum threads per SM, and maximum blocks per SM). When we program, we choose block size (threads per block) and grid size (number of blocks) to expose sufficient parallelism and to make effective use of the SM resources.

# Warp and block scheduling on SMs

Scheduling determines which warps run on an SM at any moment. Understanding scheduling helps explain how GPUs hide latency and why occupancy and warp distribution matter.

Warp-level scheduling: The SM holds a set of warp slots that represent ready-to-execute warps. Each warp slot contains the context needed to execute a warp: program counter, register file pointers, and any state for active/inactive lanes. If a warp is ready (its instruction operands are available and it is not waiting on a memory load or a barrier), the warp scheduler issues one or more instructions for that warp in a given cycle. Modern SMs typically issue multiple instructions per cycle using several warp schedulers and instruction dispatch units. The scheduler aims to keep functional units busy by switching among ready warps; this switching is fast because the warp contexts are resident on-chip.

Latency hiding: GPUs hide long-latency operations (like global memory loads) by switching to another ready warp while one warp waits for data. To hide latency effectively you need enough independent warps that are ready to execute. If all warps on an SM are waiting for memory, the SM stalls.

Warp-level divergence and reconvergence: Since all 32 threads in a warp execute the same program counter, branch divergence causes the scheduler to execute each taken path sequentially while disabling (masking) threads not on the current path. Divergence reduces effective parallelism within the warp and increases instruction count. NVIDIA’s hardware and compilers use techniques such as branch reconvergence points to limit the cost of divergence, but controlling divergence by algorithm design (e.g., avoid data-dependent per-lane branching) is important for performance.

Block scheduling: Blocks are the unit of mapping onto SMs. The runtime places a block on an SM only if the SM has sufficient free resources to host the block (registers, shared memory, available warp slots, and within maximum blocks and threads constraints). Once placed, the threads in the block run to completion on that SM (subject to preemption abilities of newer GPUs) or until a kernel completes. Multiple blocks can be resident on a single SM; the scheduler interleaves warps from all resident blocks to improve latency hiding.

Scheduling policies: Internally, SMs use policies to select which ready warp to issue next. A simple policy is round-robin among ready warps; more advanced policies may prioritize warps based on memory vs. compute characteristics, favoring memory-bound warps less often than compute-bound warps to balance throughput. The important programmer-facing takeaway is that the scheduler interleaves warps and exploits warp-level parallelism to hide latency — therefore, distributing your threads across many warps helps keep the scheduler options large and hides memory latency.

# Occupancy: registers, shared memory, and maximum active warps

"Occupancy" is a commonly used metric in CUDA programming. Occupancy is the fraction of the hardware’s maximum number of warps that are actively resident on an SM. High occupancy generally gives the warp scheduler more warps to choose from and therefore better ability to hide memory and execution latencies. However, occupancy is not a universal predictor of performance: beyond a certain point, adding occupancy has diminishing returns, and sometimes reducing per-thread resource usage (to increase occupancy) can worsen performance because it forces additional spilling or reduces instruction-level parallelism. Nonetheless, occupancy is a useful concept to reason about constraints that determine how many blocks and warps can be active.

The number of active blocks and warps on an SM is constrained by several hardware limits and kernel resource requirements:

- Maximum warps per SM, denoted $W_{max}$. (Typical values: 64 warps → 2048 threads on many architectures, but this number varies by GPU generation.)
- Maximum threads per SM, $T_{max}$.
- Maximum blocks (CTAs) per SM, $B_{max}$.
- Total registers available per SM, $R_{SM}$.
- Total shared memory (scratchpad) per SM, $S_{SM}$.

A kernel configuration specifies:
- Threads per block, $t$.
- Registers per thread (as allocated by the compiler), $r$.
- Shared memory per block, $s$.

From these, you can compute the number of warps per block:
- $w_b = \lceil t / 32 \rceil$.

Then the maximum number of blocks that can be resident on an SM, given each resource constraint, is the minimum of the following ceilings/floors:

- Register constraint: you need $r \cdot t$ registers per block. Therefore
  $$
  B_{reg} = \left\lfloor \frac{R_{SM}}{r \cdot t} \right\rfloor.
  $$
- Shared memory constraint:
  $$
  B_{shm} = \left\lfloor \frac{S_{SM}}{s} \right\rfloor.
  $$
- Warp-slot constraint:
  $$
  B_{warp} = \left\lfloor \frac{W_{max}}{w_b} \right\rfloor.
  $$
- Thread-constraint:
  $$
  B_{thread} = \left\lfloor \frac{T_{max}}{t} \right\rfloor.
  $$
- Block-count constraint $B_{max}$ set by the hardware.

Thus the number of resident blocks per SM is
  $$
  B_{resident} = \min\left(B_{reg}, B_{shm}, B_{warp}, B_{thread}, B_{max}\right).
  $$
The number of active warps per SM is
  $$
  W_{active} = B_{resident} \cdot w_b.
  $$
Finally occupancy is
  $$
  \text{Occupancy} = \frac{W_{active}}{W_{max}} \times 100\%.
  $$

Worked example. Suppose a GPU has $R_{SM}=65536$ registers, $S_{SM}=65536$ bytes of shared memory, $W_{max}=64$ warps per SM, $T_{max}=2048$ threads per SM, and $B_{max}=16$ blocks per SM (these are typical-to-example numbers; check the specific GPU manual for exact values). Your kernel uses $t=256$ threads per block, each thread uses $r=32$ registers, and the block requests $s=8192$ bytes of shared memory.

Compute intermediate quantities:

- $w_b=\lceil 256/32\rceil = 8$ warps per block.
- Registers per block $= r \cdot t = 32 \cdot 256 = 8192$ registers.
- $B_{reg} = \lfloor 65536 / 8192 \rfloor = \lfloor 8 \rfloor = 8$ blocks.
- $B_{shm} = \lfloor 65536 / 8192 \rfloor = 8$ blocks.
- $B_{warp} = \lfloor 64 / 8 \rfloor = 8$ blocks.
- $B_{thread} = \lfloor 2048 / 256 \rfloor = 8$ blocks.

So $B_{resident} = \min(8,8,8,8,16) = 8$ blocks. Then $W_{active} = 8 \cdot 8 = 64$ warps which saturates $W_{max}$, so Occupancy $= 100\%$.

If you increase $r$ to $48$ registers per thread, then registers per block $=48\cdot256=12288$. $B_{reg} = \lfloor 65536/12288\rfloor = \lfloor 5.33\rfloor = 5$ blocks. That reduces $W_{active} = 5\cdot8 = 40$ warps and Occupancy $= 40/64 = 62.5\%$. Thus higher per-thread register allocation can lower occupancy.

Practical notes about occupancy:

- There are often "granularity" effects: registers are allocated in hardware at certain grain sizes, and shared memory can sometimes be allocated per block in multiples of a bank or tile size. The hardware may round up actual allocations, so the effective $r$ and $s$ used in occupancy formulas may differ slightly from compiler-reported values.
- Achieving 100% occupancy is not always necessary. If your kernel is compute bound and has enough instruction-level parallelism to keep arithmetic units busy, you may not need many warps to hide latency; sometimes a moderate occupancy (e.g., 50-75%) yields the best performance. Conversely, memory-bound kernels often benefit from as many warps as possible.
- Use NVIDIA’s occupancy calculator (or nvcc --ptxas-options=-v output) to estimate the impacts of changing block size or of compiler options that reduce registers (e.g., --maxrregcount) or alter shared memory usage.

# Cooperative groups and cluster scheduling concepts

As algorithms grow more sophisticated, there is demand for synchronization and cooperative programming patterns beyond per-block barriers. Cooperative groups and cluster scheduling concepts enable new ways to coordinate threads across different granularities and, in some cases, across multiple SMs.

Cooperative groups introduced by CUDA provide a structured API to form and manage collections of threads. They let you create groups at different scopes: thread block groups, warp-level groups, and grid-wide groups (with additional launcher support). For example, you can form a group that contains exactly the threads in a warp, which makes warp-synchronous programming portable and cleaner. You can also create subgroups of threads within a block for pipelined algorithms or hierarchical synchronization. The API provides primitives for barrier synchronization within the group, for performing collective operations (reductions, ballots), and for querying group membership.

Cooperative kernel launches (cooperative launch) and grid-wide synchronization: Standard CUDA kernels allow synchronization only inside a block using __syncthreads() because blocks are scheduled independently and may be placed on different SMs. Cooperative groups allow the creation of a grid-wide group when the runtime can guarantee that all blocks in the grid will be resident simultaneously across the GPU. With a cooperative launch (e.g., cudaLaunchCooperativeKernel or cooperative groups API), the runtime ensures that the entire grid can be scheduled simultaneously or that it manages the launch such that grid-wide synchronization is well-defined. This enables explicit global synchronization across all threads in a grid without terminating the kernel. Cooperative launch requires enough SM resources to host the whole grid concurrently and may be subject to system limitations; it is typically used for algorithms that need global barriers between iterative phases.

Cluster scheduling and larger aggregates: Cluster scheduling refers to the idea of grouping multiple SMs or groups of blocks into a unit that executes together for coordinated work. When you form a cooperative grid that needs all blocks to be resident, you are effectively asking the scheduler to keep a cluster of SMs occupied simultaneously by the grid. Some advanced runtime/hardware systems also support features like multi-GPU cooperative launches or partitioned scheduling that let multiple kernels share SMs with certain affinity. These facilities are more advanced and can vary across GPU generations and drivers.

Warpgroups is a term used informally in some contexts to mean a logical grouping of several warps for scheduling or locality purposes. In hardware, grouping warps that access nearby data into the same SM or the same memory subsystem can improve cache locality. Although you cannot explicitly force specific warps to stay together purely via CUDA code, you can structure blocks and their thread indexing so that threads accessing common data are placed into the same block (and thus likely the same SM for the duration of their execution).

Practical programming patterns with cooperative groups:

- Warp-level primitives: Use warp-level collectives (e.g., intrinsics like __shfl_xor) to implement fast reductions or exchange values across lanes in a warp without using shared memory. These work because lanes in a warp execute in lockstep.
- Subgroups within a block: Use cooperative groups to form subteams that can synchronize independently inside a block. This helps implement hierarchical algorithms: do a per-subgroup reduction with fast shuffles, then a cross-subgroup reduction using shared memory and block-level synchronization.
- Grid synchronization: Use cooperative launch only when you really need global barriers across all blocks. It is powerful for iterative algorithms (e.g., multi-pass graph algorithms) but reduces flexibility because the runtime must commit resources to make the grid resident.

# Register allocation limits and their impact on kernel configuration

Registers are the fastest storage available to threads and play a crucial role in per-thread performance. The compiler allocates registers per thread to hold local variables, live values across instructions, and spilled temporaries. The number of registers used per thread, $r$, directly affects occupancy because registers are allocated from a finite pool per SM.

Compiler allocation and spilling: The CUDA compiler attempts to minimize registers while respecting correctness and performance. You can inspect the compiler's register usage via compiler output flags (e.g., nvcc’s verbose ptxas output lists registers per kernel). If a kernel needs more registers than can be allocated, the compiler may spill some values to local memory, which resides in device DRAM; accesses to spilled locals thus become high-latency memory operations, dramatically reducing performance. Therefore, reducing registers to increase occupancy is a trade-off: forcing the compiler to use fewer registers (via --maxrregcount) may increase occupancy but can cause spilling; the net performance effect must be measured.

Register allocation granularity: The hardware often allocates registers in units (for example, a warp-aligned block or some multiple per thread), which means that the effective register usage may be rounded up. Also, certain architectures might have more registers per SM or change the number of warps per SM; always consult the architecture’s programming manual for exact values.

How register count influences block sizing: Suppose you want to pick threads per block $t$. Register usage $r$ affects how many blocks you can put on an SM via $B_{reg}=\lfloor R_{SM}/(r\cdot t)\rfloor$. Sometimes you can increase $t$ (more threads per block), which increases $w_b$ and may reduce $B_{warp}$ (since each block consumes more warp slots). Other times you may reduce $t$ to increase the number of resident blocks, but smaller block sizes can reduce the ability to exploit shared memory or to amortize per-block overhead.

Balancing registers vs. shared memory: Many kernels can trade shared memory usage for registers (or vice versa). For example, you might load intermediates into shared memory instead of keeping them in registers to reduce register pressure (but then shared memory usage $s$ increases and could reduce $B_{shm}$). Each resource competes to limit $B_{resident}$. The optimal trade-off is kernel-dependent; profiling and occupancy calculation are required to find the best compromise.

Example of the impact of register spilling: Imagine a kernel that needs 64 registers per thread, but the device has $R_{SM}=65536$ registers and $t=256$. Then registers per block $=64\cdot256=16384$, and $B_{reg}=\lfloor 65536/16384\rfloor=4$ blocks per SM. If the compiler spills and uses 80 registers’ worth of stack traffic, the spill memory creates additional global memory accesses inside the kernel: each spilled read or write costs many cycles and may drastically raise memory traffic, collapsing performance regardless of occupancy. Because of this, aggressive attempts to maximize occupancy by forcing very small register counts often hurt more than they help.

Practical guidelines:

- Inspect the compiler’s reported register usage for your kernel and test variants that reduce registers (for example, by refactoring code, using smaller data types, or applying --maxrregcount) while measuring whether spilling occurs.
- Use the occupancy calculation described earlier to estimate whether registers or shared memory are the limiting factor. If registers limit occupancy and you can reduce $r$ without causing spills, you may improve occupancy and thus hide more latency.
- Prefer writing code that allows the compiler to optimize register allocation (e.g., avoid long-lived large arrays in registers, break complex expressions into smaller temporaries where beneficial) rather than relying solely on compiler knobs.

# Putting it together: mapping parallel work to hardware resources

Mapping your parallel algorithm to hardware involves choosing grid and block sizes and organizing data and computation with an eye to how the runtime and hardware use resources. The principles below summarize the earlier concepts and provide a practical recipe.

1. Expose enough parallelism. The grid must contain far more threads than there are physical cores so that the scheduler can hide latency. A good starting point is to have at least a few hundred warps per SM across the entire grid, but what matters is that the SMs are kept busy by blocks that can be scheduled and by warps inside those blocks that can be interleaved.

2. Pick block size to match algorithmic locality and hardware warp size. Because the warp size is 32, pick thread-block sizes as multiples of 32 to avoid partially-filled warps. Common choices are 128, 256, or 512 threads per block depending on shared memory needs and register pressure.

3. Calculate occupancy to identify the limiting resource. Use the formulas for $B_{reg}$, $B_{shm}$, $B_{warp}$, $B_{thread}$ and compute Occupancy. If occupancy is very low because of registers, consider reducing $r$ through algorithm refactoring; if shared memory is the limit, consider whether you can reorganize data access to use less shared memory or reduce per-block shared memory footprint.

4. Reduce divergence and favor warp-synchronous constructs when appropriate. Avoid divergent branches in the inner loop of a warp; use warp-level intrinsics for fast intra-warp communication.

5. Use cooperative groups for finer-grained synchronization and to express hierarchical parallelism. If you need global synchronization across blocks, consider cooperative launch only when necessary and when your system can commit the resources required for the full-grid residency.

6. Measure and iterate. GPU performance is sensitive to details. Use profiling tools (Nsight Compute, nvprof legacy, or similar) to measure stalls due to memory, instruction dependency, or lack of active warps. Optimize the bottlenecked resource first.

Example workflow: Suppose you write a matrix multiplication kernel. You start with an algorithm that uses 256 threads per block and 16 KB of shared memory per block. The compiler reports 40 registers per thread. Using the occupancy formulas you determine that shared memory allows 4 blocks per SM but registers allow 6 blocks per SM; thus shared memory is the bottleneck. You could try to reduce shared memory by changing tiling size (use smaller tile per block), or you could keep shared memory the same but reduce threads per block (which changes $w_b$ and shifts the balance). After selecting a candidate configuration, run the kernel and profile memory throughput and compute utilization. If memory stalls dominate, try increasing occupancy by reducing $r$ if possible; if compute units are underutilized, try increasing work per thread (unrolling) or using more threads per block so that the SM can issue more independent instructions per warp.

Conclusion

Understanding the CUDA execution model, how warps and blocks map to SMs, and how registers and shared memory determine occupancy is essential to writing high-performance GPU kernels. The warp is the core scheduling unit; blocks are the mapping unit to SMs; occupancy is determined by hardware limits and kernel resource demands. Cooperative groups and cooperative launches expand the programming model to allow finer-grained synchronization and grid-wide coordination, but they require careful consideration of resource residency. Finally, register allocation and spills have a pronounced impact on performance: the balance between per-thread resource usage and global concurrency must be tuned with profiling and iterative testing. With these concepts and the occupancy formulas, you can analyze kernels, predict bottlenecks, and make informed kernel-configuration choices.

Introduction

Modern GPUs are designed not only to perform massive amounts of arithmetic in parallel, but also to move data efficiently between different levels of the memory hierarchy and with the host. To achieve high sustained throughput, GPU hardware exposes a number of asynchronous and concurrent units that can operate in parallel: compute units execute arithmetic and control, while separate memory engines and DMA/copy engines move data independently. Software that understands and exploits this asynchrony can overlap data movement and computation to hide latency and increase utilization. The principal software techniques for doing this are double buffering (also called ping-pong buffering), circular buffering, and software pipelining across iterations. These techniques are widely used in high-performance GPU code and form the basis of many research papers and production kernels.

This chapter explains the hardware background (the asynchronous units you can rely on), develops the producer-consumer overlap pattern, describes double buffering and circular buffers in depth, shows how to construct software pipelines across iterations, and analyzes the trade-offs you must manage: register pressure, synchronization cost, and pipeline depth. Throughout, the emphasis is on intuition and on writing code and designs that are robust on real GPUs.

# Asynchronous units on GPUs

To reason about overlapping work we must first understand the units that can run concurrently on a GPU. GPUs are heterogeneous systems that typically separate concerns across different specialized engines. At a coarse level you can think of three categories of units:

1. Compute units (SMs/CUs/cores): These execute shader or CUDA kernels and operate on data in registers, shared/local memory, L1 caches, and the compute-side caches. They schedule thousands of threads or warps and hide instruction and memory latency by context switching among threads.

2. Memory engines and DMA/copy engines: These engines are responsible for transferring large blocks of data between system memory (host DRAM) and device memory, between different memory spaces on the device, or between device memory and special devices. They operate independently of the compute units, often under the control of the GPU driver or a runtime API. On modern GPUs there are one or more copy engines that can perform asynchronous copies while the SMs are computing.

3. Host-to-device command/PCIe/NVLink path: The hardware and drivers implement command submission and data movement paths between the CPU and GPU. While not a "unit" inside the GPU die, the host path and the driver/runtime shape how and when kernels and copies are launched, and whether they are synchronous or asynchronous.

In addition to these broad categories, GPUs also provide finer-grained asynchronous capabilities. For example, modern APIs give you streams (or command queues) that let you issue kernels and memory transfers into separate logical sequences; the hardware and driver then try to schedule operations from different streams concurrently if they target different engines and do not have explicit dependencies.

An important practical point is that different kinds of work map to different internal engines. A large device-to-device copy is typically handled by a copy engine that will move data without occupying SMs. A kernel launch occupies compute resources. If copy engines and compute engines are truly independent, the runtime and hardware can perform copies concurrently with kernels, enabling overlap. However, there are constraints: some copies may require host interaction; PCIe or NVLink bandwidth is limited; and not all GPUs have multiple concurrent copy engines. Furthermore, even when the hardware supports concurrency, driver- and runtime-level serialization (for example, issuing a synchronous API call) can eliminate the available overlap. Therefore, understanding both the hardware units and the software runtime behavior is essential.

From an operational standpoint, consider two orthogonal resources: compute throughput and memory bandwidth/transfer engines. The achievable throughput for a pipeline that alternates compute and copy stages depends on both the time to compute a tile $T_{comp}$ and the time to transfer the next tile $T_{transfer}$. If the hardware can overlap them fully, the iteration latency can approach $\max(T_{comp}, T_{transfer})$ rather than $T_{comp} + T_{transfer}$. This simple observation underlies why asynchronous units matter: they let you hide the larger of the two latencies inside the other, improving overall throughput.

# Overlapping data movement and computation (producer-consumer patterns)

Overlapping data movement and computation is fundamentally a producer-consumer problem. One stage (the producer) prepares data, typically by copying it into a memory region local to the compute units (device memory, or shared memory, or registers). Another stage (the consumer) computes on that prepared data. If the producer and consumer must occur sequentially for a given data item, and there is no concurrency, then total time is the sum of produce and consume times. But if the producer can work on item $i+1$ while the consumer works on item $i$, then we can hide producer latency under consumer latency and vice versa. The classic approach is to separate the work into tiles or chunks so that the producer produces tile $i+1$ while the consumer processes tile $i$. The net steady-state throughput becomes limited by the slower of the two stages.

To make the overlap effective you must ensure two things. First, the producer and consumer must be able to run concurrently on separate hardware resources. This usually means using an asynchronous memory-copy API (so the copy engine is used for transfers) and queuing compute kernels in a stream or queue that the compute units will execute. Second, the program must arrange its data structures so that the consumer can begin on tile $i$ while tile $i+1$ is being produced. Typically this requires separate buffers for different tiles and some synchronization mechanism to indicate readiness.

A simple example is iterative processing of a large dataset that does not fit entirely in the GPU device memory. The host stages send chunks to the device; the device computes a kernel for each chunk and writes the results back. If the host issues asynchronous copies of the next chunk while the device is computing on the current chunk, the copy engine and compute units can work in parallel. This requires pinned host memory for efficient DMA, asynchronous copy APIs, and non-blocking kernel launches in different streams.

Producer-consumer patterns also apply entirely on-device. For example, one kernel produces intermediate results into device memory, and a second kernel consumes those results. If the GPU supports concurrent kernel execution, and if the kernels are launched into separate streams without implicit synchronization, the second kernel can begin when its data is ready while other kernels or copies continue. On the finer-grain side, a single kernel can have a producer thread block that loads data into shared memory while other thread blocks prefetch the next block into different shared-memory slots. The kernel itself must carefully coordinate such in-kernel producers and consumers using shared-memory synchronization primitives (barriers or atomics).

Correct and efficient producer-consumer overlap relies on carefully reasoning about dependencies. The consumer for tile $i$ must not start before the producer for tile $i$ has completed its data transfer or writing into the buffer. Conversely, the producer must not overwrite a buffer that the consumer is still reading. This is why double buffering or circular buffering patterns are essential: they provide multiple buffer slots so that producer and consumer can use different slots concurrently and only synchronize for the slot being exchanged.

# Double buffering, circular buffers and ping-pong buffers (general patterns)

Double buffering is the simplest form of buffering used to decouple producer and consumer stages. The idea is to allocate two buffers (often called ping and pong) and alternate their roles. While the producer fills ping, the consumer processes pong; on the next iteration they swap. Because the producer never writes into the buffer the consumer is currently reading, no fine-grained mutual exclusion is required for the data itself — only a small synchronization to swap roles when both are ready. This pattern is easy to implement, intuitive, and remarkably effective at hiding latency.

A typical double-buffering loop looks like this in concept: the host issues an asynchronous copy of tile 0 into buffer A and then issues the kernel to process buffer A. Immediately after launching the kernel (but in a way that respects ordering where necessary), the host issues an asynchronous copy of tile 1 into buffer B. When the kernel finishes processing buffer A, buffer A becomes free and the host can start copying tile 2 into it while the kernel processes buffer B, and so on. In steady state, one copy and one kernel are active at the same time, and the throughput is limited by the slower of the copy and the kernel.

Double buffering generalizes naturally to on-device use where the producer and consumer are within the device. For example, a kernel might alternate between two shared-memory regions, loading the next tile into one while computing on the other. Alternation can be implemented via a single bit index that is toggled each iteration. Synchronization to protect buffer reuse is then just a barrier or an atomic flag depending on the concurrency granularity.

Circular buffers generalize double buffering by having more than two slots, typically $N$ slots cyclically reused. A circular buffer allows deeper pipelining: at any moment, different slots can be in different stages of the pipeline (being filled, being processed, being written back). The key state variables are a head index indicating the producer position and a tail index indicating consumer position, with rules ensuring that head does not overtake tail in a way that would overwrite unread data.

The more slots you provide, the more slack you have to tolerate variance in stage durations. For example, if copies have variable latency or compute time fluctuates, a 2-slot buffer may stall when the producer overruns the consumer momentarily. A larger circular buffer smooths such bursts, at the cost of larger memory footprint and potentially more complex synchronization.

When implementing circular buffers there are several concerns. First is memory coherence and visibility: the hardware and API must guarantee that when the producer completes writing a slot, the consumer will see consistent data. This is normally assured by the API semantics of asynchronous copy completion and kernel launch completion. Second is the synchronization mechanism: simple integer counters with atomic increments are often adequate, but on GPUs you may need to be careful about atomic operation costs or the lack of lightweight CPU-style mutexes. Third is pointer arithmetic and wrap-around: using modulo arithmetic to index the buffer is straightforward but must be implemented carefully to avoid expensive modulo operators inside hot loops — often a power-of-two length and bitmasking are used for efficiency.

The ping-pong name is common in image and stream processing: one buffer is "pinged" while the other is "ponged". When implementing on the GPU, ping-pong buffers are frequently used with shared memory across thread blocks that cooperatively load data. On architectures where thread blocks cannot be synchronized globally within a kernel, ping-pong patterns inside a single block with __syncthreads-style barriers are safe; across blocks, one must rely on kernel boundaries or finer-grain synchronization mechanisms (device-level barriers if available) to ensure safety.

Practical implementation tips include: align buffers to the natural DMA alignment to maximize throughput; use pinned host memory for host-to-device copies; keep buffer sizes large enough to amortize launch and transfer overheads but small enough to fit in memory and to expose parallelism; and use profiling tools to confirm that copy engines are active concurrently with compute.

# Software pipelining across iterations

Software pipelining takes the producer-consumer idea further by decomposing the computation into stages and arranging work so that multiple iterations are concurrently in flight at different pipeline stages. This is analogous to instruction-level pipeline in a CPU but at the granularity of data tiles or loop iterations. Instead of completing one iteration entirely before starting the next, the implementation overlaps the stages of different iterations to reduce idle time and increase instruction-level and pipeline-level parallelism. Software pipelining is particularly powerful on GPUs because kernels and copies both have significant setup and latency, so overlapping them reduces the proportion of time spent in unavoidable latency.

Consider a loop that for each tile performs: copy input to device, pre-process, compute kernel, post-process, and copy output back to host. Sequential execution does these steps one tile at a time. Software pipelining breaks these into stages and schedules them so that while the kernel runs on tile $i$, the pre-processing runs for tile $i+1$, the input copy runs for tile $i+2$, and the output copy for tile $i-1$ may be in flight as well. Formally, if there are $S$ stages, we can schedule up to $S$ iterations concurrently once the pipeline is filled, and the throughput approaches the maximum stage time rather than the sum of stage times.

To reason about software pipeline performance we use initiation interval and latency. The initiation interval (II) is how frequently a new iteration is started (in time or in hardware occupancy). An ideal pipeline has II equal to the maximum stage latency divided by the number of parallel hardware resources available to that stage. Latency is the total time for an iteration to pass through all stages, but in steady state the throughput is about $1/{\rm II}$. On GPUs, the limiting stage is often memory transfer or a compute kernel whose occupancy is constrained by registers and shared memory; the pipeline design should place these heavy stages so that they do not contend for the same hardware resources excessively.

A canonical software-pipelined loop on a GPU with two buffers might look like this (conceptually):

1. Issue asynchronous copy of tile 0 into buffer A.
2. Launch kernel to process buffer 0 (A).
3. While kernel for tile 0 is running, issue asynchronous copy of tile 1 into buffer B.
4. When kernel for tile 0 completes, issue asynchronous copy of result 0 out, and launch kernel for tile 1 while issuing copy of tile 2 into buffer A, and so on.

If you expand this pattern to more buffers and split the kernel into multiple stages (for example, a pre-load stage that prepares data into shared memory and a compute stage that uses it), you increase concurrency. In a more sophisticated design, you can implement a stage where multiple operations are pipelined within a single kernel (e.g., loop unrolling and stage reordering) so that loads for iteration $i+2$ are issued while arithmetic for iteration $i$ occurs. GPUs are good at hiding memory latency inside threads, so the benefit of such intra-kernel pipelining depends on how well the thread-level parallelism and memory-access pattern can be exploited.

When designing a software pipeline you must consider startup and drain phases. The pipeline does not produce the full steady-state throughput until the first few stages are started (startup). Likewise, at the end you will need to drain the pipeline. For long-running loops these transients are negligible, but for short loops or many small tasks, the overhead can be significant and may reduce the benefit of pipelining.

Software pipelining is not only about concurrency of copy and compute; it also applies to overlapping different kinds of compute stages. For example, you can partition computation into a lightweight stage that organizes data and a heavyweight stage that does floating-point work, scheduling them so that the lightweight stage for a later tile runs concurrently with the heavyweight stage for an earlier tile, provided they do not compete for exclusive resources. Doing this effectively requires careful mapping to streams, buffer slots, and synchronization points.

# Trade-offs: register pressure, synchronization, and pipeline depth

Software pipelining and buffering are powerful, but they introduce trade-offs. The principal dimensions to consider are register pressure, synchronization overhead, and pipeline depth (number of in-flight iterations or buffer slots). Balancing these factors is critical to achieving high performance on GPUs.

Register pressure is often the limiting factor inside kernels. When you implement pipelining inside a single kernel — for example, by unrolling loop iterations and keeping data for multiple iterations in registers or shared memory — you increase the number of live variables and thus the register usage per thread or per warp. Higher register usage reduces the maximum number of warps or thread blocks that can be resident on an SM simultaneously (occupancy). Reduced occupancy can harm the GPU’s ability to hide latency and may negate gains from pipelining. Therefore, you must weigh the benefit of keeping data in fast registers against the cost of losing occupancy. As a rule of thumb, try to keep register usage moderate and use shared memory or device memory with double buffering if registers would cause occupancy to fall below an effective threshold.

Synchronization cost is the next concern. Overlap between producer and consumer requires synchronization to ensure that the consumer does not read incomplete data and that the producer does not overwrite buffers in use. Synchronization mechanisms include host-side waits for copy completion, device-side kernel completion events, stream-ordering semantics, and atomic operations. Each synchronization point has latency and sometimes serializing effects. For instance, forcing synchronization between kernels by issuing a blocking API call kills concurrency and negates pipelining benefits. Likewise, too-frequent fine-grained synchronization inside a kernel (for example, many barriers) can stall parts of the pipeline. Effective designs minimize synchronization by using a small number of well-placed synchronization events and by relying on the semantics of asynchronous APIs (for example, using events to detect copy completion rather than polling or blocking).

Pipeline depth (number of slots) interacts with both register pressure and synchronization complexity. A deeper pipeline (larger $N$ in an $N$-slot circular buffer) allows more iterations to be in flight and can smooth out variance in stage durations. However, more slots mean more memory allocated for buffers, and when slots are allocated in fast memory (registers or shared memory) the resource cost can limit concurrent thread blocks or increase register pressure. Additionally, managing a deep circular buffer requires more complex indexing and possibly more metadata (producer and consumer counters), which may introduce additional atomic operations if multiple producers or consumers exist.

There is also an important trade-off between latency and throughput. Pipelining increases throughput by keeping resources utilized, but it also increases the latency an individual data element experiences (it must wait in the pipeline). In low-latency applications this may be unacceptable even if average throughput improves. Conversely, batch-oriented high-throughput workloads generally benefit from deeper pipelines.

Another less obvious trade-off is the possibility of resource contention between copy engines and memory-system demand generated by kernels. Even though hardware copy engines and SMs are separate, they share the same device memory and memory controllers. Aggressively overlapping copies with heavy compute may create contention for DRAM bandwidth, leading to slower copies or slower memory loads from kernels. Therefore, empirical tuning is necessary: sometimes partial overlap (or throttling copy concurrency) yields better end-to-end performance.

Finally, complexity and maintainability are practical trade-offs. Software pipelining increases code complexity; multi-buffer management, event handling, and careful ordering of operations complicate debugging. You should weigh the performance benefits against increased susceptibility to bugs and portability concerns across GPU architectures and runtimes.

Conclusion and practical suggestions

To summarize, modern GPUs provide asynchronous units — compute and copy engines — that can be leveraged through streams, asynchronous copies, and careful buffering to overlap data movement and computation. Producer-consumer patterns, implemented via double buffering or circular buffers, are simple and effective ways to decouple stages. Software pipelining generalizes these ideas by overlapping multiple iterations across multiple stages to approach the throughput of the slowest stage. However, achieving the theoretical gains requires attention to trade-offs: register pressure, synchronization overhead, pipeline depth, and memory-system contention.

Practically, a sensible approach to optimization is iterative: start with a correct sequential implementation, measure the dominant latencies (compute vs transfer), introduce asynchronous copies and a two-buffer ping-pong pattern, verify overlap with profiling tools, then increase buffer depth or split kernels into stages if needed. Monitor register usage and occupancy, and be prepared to move some state from registers to shared memory or device memory if occupancy falls too low. Use events and non-blocking APIs for synchronization, and always validate correctness under concurrency. With these methods and careful measurement, you can exploit GPU asynchrony to substantially increase throughput on real workloads.

Introduction

Modern GPUs achieve high throughput by running thousands of threads concurrently and relying on fast on-chip memory and carefully coordinated data movement. Synchronization primitives are essential tools programmers use to coordinate computation and memory accesses among threads so that data dependencies are respected and correctness is maintained. However, synchronization comes at the cost of reduced parallelism and potential stalls, so choosing the right primitive and pattern is critical for both correctness and performance.

This chapter explains the commonly used synchronization facilities on NVIDIA GPUs (CUDA) and the patterns that arise when coordinating producers and consumers of data. We start by contrasting coarse-grained barriers (the well-known CUDA intrinsic __syncthreads) with newer fine-grained barrier instructions (bar.sync) and describe when each is appropriate. Next we examine producer-consumer coordination and the commit/wait semantics needed to make data visible and safe to consume. We then cover atomic operations and the memory ordering constraints they impose, including CUDA’s memory fences. Cooperative groups provide more flexible grouping and barrier variants; we describe their API and semantics. Finally, we analyze the performance impacts of synchronization and present practical techniques for minimizing stalls and preserving latency hiding.

# __syncthreads vs fine-grained barrier instructions (bar.sync)

The simplest and most widely used intra-block synchronization primitive in CUDA is __syncthreads(). It is a barrier that synchronizes all threads in a thread block (a CTA, cooperative thread array). When a thread executes __syncthreads(), it waits until every thread in the block has reached that call. Only after all threads have arrived does execution proceed past the barrier for any thread. __syncthreads() also acts as a memory fence for shared memory accesses: memory stores to shared memory performed by threads before the barrier are guaranteed to be visible to threads after the barrier (subject to the usual rules about compiler reordering). Because it applies to the entire block and is implemented at the CUDA language level, __syncthreads() is simple to use and reason about.

Despite its simplicity, __syncthreads() has limitations. First, it synchronizes the whole block, even if only a subset of threads need to coordinate; this can waste time when threads that do not participate are forced to wait. Second, the barrier is at the lexical level: control flow must guarantee that all threads in the block will eventually execute the same __syncthreads() call, otherwise the program may deadlock. Branch divergence that leads to some threads skipping a barrier while others execute it causes undefined behavior. Third, __syncthreads() is fairly coarse-grained relative to what the hardware supports.

To address finer-grained synchronization needs, NVIDIA GPUs expose lower-level barrier instructions such as bar.sync. bar.sync is an assembly-level (SASS) instruction that supports more flexible barrier semantics: it allows barriers to be named and reused, and can synchronize arbitrary subsets of threads within a block when combined with masks that indicate participating lanes (warps/threads). The bar.sync instruction takes an identifier for the barrier slot and a mask identifying which threads should be synchronized on that barrier; only threads that participate in the same barrier id and mask will wait on one another. With bar.sync you can implement multiple independent synchronization points in a kernel without requiring all threads to rendezvous at the same place, and you can use different barriers concurrently (so long as hardware resources permit).

Key differences summarized:

- Scope: Both __syncthreads() and bar.sync operate within a block (CTA) in typical usage. However, bar.sync can synchronize fine-grained subsets when used with masks, whereas __syncthreads() always includes the entire block.
- Expressiveness: __syncthreads() is a high-level CUDA intrinsic with implicit semantics. bar.sync is an explicit, lower-level barrier that can be named and reused, enabling multiple barriers and composable synchronization patterns in the same block.
- Safety and readability: __syncthreads() is safer for most developers because the compiler enforces some of the required properties (e.g., lexical placement). bar.sync requires careful programming to avoid deadlock and to ensure participating threads match the mask and barrier id.
- Implementation and performance: bar.sync maps more directly to hardware mechanisms and can reduce stalls by avoiding unnecessary synchronization of threads that do not need to participate. However, improper use can hurt performance because hardware has a limited number of barrier slots and resources.

Practical guidance: prefer __syncthreads() for typical intra-block synchronization where all threads must coordinate, especially when code clarity and correctness are priorities. Use bar.sync (or cooperative-group barriers that expose similar functionality) when you need multiple simultaneous barriers, want to synchronize only subsets of threads, or require more compact, lower-level control for advanced algorithms. When using bar.sync, ensure that participating threads arrive at barriers deterministically to avoid deadlocks and verify that hardware supports the number of barrier slots your algorithm requires.

# Producer-consumer coordination and commit/wait semantics

Producer-consumer coordination is a common pattern on GPUs: some threads (producers) generate data and write it to memory, while other threads (consumers) read that data and operate on it. Ensuring consumers see consistent and fully-written data requires explicit synchronization and memory visibility control.

At a basic level, there are two requirements for correct producer-consumer interaction: (1) the consumer must not read before the producer has finished writing the data, and (2) the consumer must see the final values written by the producer (no stale or partial values). Achieving these requirements on GPU hardware typically combines barriers, memory fences (threadfence), and ordering semantics on atomics.

A common pattern within a CTA uses shared memory and __syncthreads(): producers write to shared memory, then execute __syncthreads() to commit their writes; consumers execute __syncthreads() before reading shared memory. Because __syncthreads() acts as a barrier plus a shared-memory fence, this pattern ensures that all shared-memory writes done prior to the barrier are visible to all threads after the barrier. For example, when a block performs a staged transpose or reduction, producers can write partial results into shared memory and all threads can safely read them after a single __syncthreads().

When the producer and consumer are in different CTAs (inter-block communication) or when memory is in global memory, barriers like __syncthreads() cannot coordinate across CTAs. In that case, explicit commit/wait semantics are required. The producer typically writes data to global memory and then performs a memory fence to ensure stores are committed to a coherence domain, and finally writes a flag indicating completion. The consumer polls (or waits) on that flag, and once it sees the flag set it performs any required memory fence before reading the data.

A simple pattern in global memory:

1. Producer writes data payload to global memory.
2. Producer executes a write fence (e.g., __threadfence() in CUDA) to ensure writes are visible outside the producing thread/warp/CTA.
3. Producer writes a release flag to global memory (often via an atomic store or a normal store with appropriate semantics).
4. Consumer spins on the flag (busy-wait, possibly with backoff).
5. When consumer sees the flag set, it executes an acquire fence (e.g., no-op in some models, or explicit check plus __threadfence) and then reads the payload.

The purpose of the fence before setting the flag is to prevent reordering of payload stores and the flag store: on weakly ordered memory systems, without a fence the store of the flag might become visible to other agents before the payload stores complete, causing consumers to read incomplete data. The fence ensures the correct commit ordering: payload stores are globally visible before the completion flag.

A more robust implementation uses atomics with release/acquire semantics so that the act of setting the flag is both the notification and the synchronization primitive. In CUDA, atomic operations on global memory can include memory ordering guarantees; for example, using atomicExch() or atomicCAS combined with __threadfence_system() for system-wide visibility when communicating across GPUs or with the host. If the consumer uses an atomic load with acquire semantics (or the atomic read ordering provided by the API), it will properly observe the writes that happened-before the flag write.

Polling (busy-wait) on the GPU is generally expensive: spinning threads consume SM resources and can degrade the GPU’s ability to hide memory latency by keeping other warps resident. For cross-CTA synchronization, consider redesigns that avoid frequent spinning: use streaming multiprocessor (SM) cooperation via cooperative groups (grid-level synchronization when available), or restructure the algorithm so that producers and consumers are within the same CTA (use shared memory) or use multiple kernel launches with the producer kernel finishing before the consumer kernel starts (kernel launch acts as a global barrier).

It’s also important to consider partial writes and atomicity of payload elements. If a payload consists of multiple words, the producer must ensure that consumers do not observe a partially updated multi-word object. Techniques include writing to a separate buffer region and then swapping pointers with an atomic pointer swap, or using version counters that allow consumers to detect in-progress writes: write payload, increment version, write version again (or use a pair of version counters) in a protocol that allows consumers to detect consistent snapshots.

# Atomic operations and memory ordering constraints

Atomic operations are the foundation for fine-grained synchronization and mutual exclusion on shared memory locations. On GPUs, atomics allow threads to safely update shared or global memory without races by ensuring read-modify-write sequences appear atomic with respect to other threads.

There are several categories of atomic operations: simple read/modify/write atomics (add, sub, min, max, and, or, xor), compare-and-swap (CAS) variants (atomicCAS), exchange (atomicExch), and specialized atomics for floating point or 64-bit types. In CUDA, atomics can operate on shared memory (fast, per-CTA) and on global memory (moderate latency and cross-CTA visibility). Atomics on shared memory are usually much lower latency since they remain on-chip; global atomics may require cache coherence or system-level handling.

Beyond atomicity, memory ordering semantics determine how atomic operations and surrounding loads/stores are seen by other threads. On weakly ordered architectures (including GPUs), loads and stores can be observed in different orders by different threads unless explicitly constrained. Memory fences and ordered atomic operations establish “happens-before” relationships that guarantee visibility.

Key memory ordering concepts:

- Sequential consistency (SC): The strictest ordering model where all operations appear to execute in a single global interleaving consistent with program order. Full SC is expensive and rarely the default on modern hardware for performance reasons.
- Release-acquire semantics: A common relaxed model where a store with "release" semantics ensures that all prior writes by the releasing thread become visible before the release, and a load with "acquire" semantics ensures that subsequent reads by the acquiring thread see writes that happened before the release. Release-acquire is sufficient for most producer-consumer patterns.
- Fences: Explicit instructions (e.g., __threadfence(), __threadfence_block(), __threadfence_system() in CUDA) that ensure different degrees of visibility. __threadfence_block() ensures visibility to all threads in the block. __threadfence() ensures visibility to all threads on the device (global memory), and __threadfence_system() ensures visibility to the entire system (CPU and other devices) if supported.

In CUDA, atomic operations on global memory generally act as both atomic updates and memory ordering points, but their exact semantics depend on the operation and the CUDA version/architecture. For cross-CTA communication, the recommended pattern is to use a memory fence to commit stores and then use an atomic or ordered store to signal completion. For example, a producer doing:

1. write payload to global memory
2. __threadfence()  // ensure payload stores are visible to other SMs
3. atomicExch(&flag, 1)  // publish-complete

A consumer can then poll atomicExch/atomicCAS or read the flag atomically, and the atomic read that observes the value will synchronize with the prior release.

It is important to understand that normal (non-atomic) global stores are not sufficient to coordinate across CTAs without explicit fences because the hardware might reorder stores and loads across threads. Additionally, atomics may impose coherency costs: global atomic operations may go through caching structures with serialization, and a high contention atomic can become a performance bottleneck as threads serialize on updates to the same location.

Another important atomic consideration is size and alignment. Many architectures guarantee atomicity only for certain sizes (32-bit, 64-bit) and require specific alignment; trying to atomically update larger multi-word structures requires custom protocols (double-compare-swap emulation or versioning). Atomic operations on floating-point types may have non-intuitive behavior in terms of rounding and associativity; use them with care when exact reproducibility is required.

Finally, some modern CUDA APIs and PTX support explicit memory ordering qualifiers on atomics, like acquire and release variants. Where available, prefer using appropriate acquire/release atomics rather than global fences when you only need a specific ordering between the producer and consumer events; they can be more efficient and easier to reason about.

# CUDA cooperative groups and barrier variants

CUDA cooperative groups is a programming abstraction introduced to give developers more flexible and structured ways to express synchronization and collective operations. Instead of being restricted to block-level barriers (e.g., __syncthreads()), cooperative groups allows the programmer to form arbitrary groups of threads (subgroups) and apply collective operations like barriers, broadcasts, and shuffles scoped to those groups.

A cooperative group is an object that represents a group of threads; typical group types include:

- thread_block: corresponds to a CTA (the block).
- tiled_partition: divides a thread_block into smaller tiles (subgroups) of a given tile size, allowing thread-level synchronization within the tile.
- coalesced_group or warp-level groups: represent threads that form a warp or a part of a warp (hardware dependent).
- grid_group: represents all threads in the grid (requires special launch options and hardware support).

The cooperative groups API provides methods such as sync(), which acts like a barrier for that group, and collective communication operations like all_reduce, broadcast, and permute. For example, a group.sync() will block the calling threads in that group until every thread in the group reaches the call; it also provides the memory-fence semantics required to make shared memory visible to group members.

One of the major advantages of cooperative groups is composability: you can build algorithms that synchronize only the threads that need to coordinate. This improves programmability and performance by avoiding unnecessary waiting. For instance, divide a block of 256 threads into four tiles of 64 threads each and use group.sync() on the 64-thread tile when only that subset needs to coordinate. Internally these group-level barriers can map to bar.sync or warp-level primitives.

Grid-wide synchronization (synchronizing all threads across all CTAs in a kernel) is supported by cooperative groups through the grid_group, but it comes with important constraints. Grid sync requires launching the kernel in special cooperative mode (cooperative launch) and the GPU driver and hardware must support it. Grid-sync is powerful because it provides a true global barrier within a single kernel, enabling multi-stage algorithms without the overhead of launching multiple kernels. But it limits scheduling flexibility and can block forward progress if some CTAs are preempted or if resources are insufficient to keep all CTAs resident.

There are also barrier variants in CUDA and cooperative groups beyond simple full-group barriers. These include:

- Single-wait barriers: the traditional barrier where each participating thread waits until all have arrived.
- Release/acquire style barriers: these can be implemented with atomics and fences where a thread publishes completion and others acquire that state without requiring all threads to wait collectively.
- Non-blocking progress-friendly primitives: e.g., using warp-level shuffles and ballots to share minimal control data instead of blocking.

When designing synchronization with cooperative groups, consider these trade-offs: group size, the cost of forming groups, mapping of group operations to hardware barriers, and whether the cooperative launch constraints (for grid sync) are acceptable. Cooperative groups make it simpler to write correct and efficient code by enabling explicitly scoped synchronization and collective operations that better reflect algorithm structure.

# Impacts of synchronization on performance and latency hiding

While synchronization is necessary for correctness, it can hurt performance in several ways. Understanding how synchronization interacts with GPU hardware and scheduling is essential to designing high-performance kernels.

First, synchronization reduces available parallelism. When a thread or warp blocks on a barrier or a spin-wait, it consumes SM resources (registers, shared memory, and sometimes warp slots) that could otherwise be used to schedule other warps. On GPUs, hiding memory latency relies heavily on having many ready warps to switch to when one warp stalls. If too many threads block waiting on synchronization, the SM may run out of ready work, exposing memory latency and lowering throughput.

Second, barriers can force serialization. Some synchronization primitives (especially global atomics or heavy contention on a single variable) serialize updates and degrade potential concurrency. If many threads frequently update the same atomic location, the updates will serialize and the code will be bound by atomic throughput rather than arithmetic or memory bandwidth.

Third, branching and deadlock risks increase. Lexical barriers like __syncthreads() require all threads in a block to reach the barrier; divergent control flow can lead to situations where some threads skip the barrier, causing the program to deadlock or produce undefined results. Fine-grained barriers such as bar.sync or cooperative group sync reduce this risk by allowing careful subgroup synchronization, but they require careful design to ensure the right threads participate.

Fourth, spin-waiting is wasteful. Active polling on a flag in global memory keeps warps busy and can block other work on the SM. Spin-wait loops that include memory loads with limited scheduling opportunities (e.g., tight loops without yields) do not allow the GPU’s warp scheduler to hide latency effectively. Techniques that reduce or eliminate spin-waiting—such as event-driven notification, rearchitecting to use multiple kernel launches, or using atomic-backed queues with limited contention—can improve efficiency.

Strategies to mitigate synchronization overhead and preserve latency hiding:

- Minimize synchronization scope: Use warp-level primitives (shuffle, ballot) and cooperative groups with small subgroup sizes when you only need to communicate within a warp or a small tile. Warps are scheduled as units and warp-level operations are usually low-latency.
- Reduce the number of synchronizations: Combine multiple synchronization points into one when possible, and avoid redundant barriers.
- Use lock-free algorithms and data structures: Where possible, design algorithms that avoid global locks or heavy atomics. For instance, use parallel-prefix, batch updates, or multi-buffering to reduce contention.
- Avoid hot spots on atomics: Instead of many threads contending on a single atomic counter, partition work across multiple counters or use hierarchical aggregation (local counters in each block, then reduce).
- Use memory fences selectively: Fences like __threadfence_system() can be expensive; prefer narrower fences or atomic release/acquire semantics when sufficient for correctness.
- Use cooperative kernel launches wisely: Grid-synchronization can avoid kernel launch overhead, but it requires cooperative launch support and may reduce overall throughput if it limits concurrency. Balance the convenience of grid sync with its scheduling implications.
- Design for occupancy: Ensure that synchronization and shared-memory usage do not reduce occupancy to the point where latency cannot be hidden. Sometimes using fewer shared-memory buffers or using fewer registers per thread raises occupancy and helps hide latency; other times the computation itself benefits more from fewer threads with more local resources. Profile and experiment.
- Prefer asynchronous pipelines: Overlap production and consumption via double buffering and pipelined execution where producers write buffer A while consumers read buffer B, swapping buffers with minimal synchronization. This allows useful work to proceed while synchronization occurs infrequently.
- Use backoff and exponential sleep in spin loops: If you must poll, implement a backoff strategy (e.g., execute some independent work or use __nanosleep-like instructions where available) to reduce bus contention and allow other warps to run.

Real-world example: suppose a kernel must perform a staged computation where each CTA produces a block of results that other CTAs must consume. You could implement this as many small kernel launches (producer kernel(s) then consumer kernel(s))—each launch provides implicit global synchronization but incurs launch overhead. Alternatively, use cooperative groups with a grid-wide barrier (__syncthreads() is insufficient across CTAs) to avoid launch overhead. The cooperative approach reduces CPU overhead but might limit scheduling and resource allocation on the GPU. The right choice depends on the algorithm’s sensitivity to launch latency, the availability of cooperative launch support, and the amount of inter-CTA synchronization required.

Conclusion

Synchronization on GPUs ranges from simple block-wide barriers to low-level barrier instructions and atomics with explicit memory orderings. Each primitive has different trade-offs in expressiveness, safety, and performance. For intra-block coordination, __syncthreads() and warp-level intrinsics are simple and efficient when used correctly. For finer-grained or cross-CTA coordination, bar.sync, atomics with release/acquire semantics, and cooperative groups provide greater flexibility but require careful programming to avoid deadlock, serialization, and loss of latency hiding.

When designing algorithms, think first about minimizing synchronization, then about scoping it tightly, and finally about choosing the most appropriate primitive given the hardware and performance constraints. Profile kernels to find synchronization hotspots, and iterate: often a small redesign (double buffering, hierarchical aggregation, or using warp-level communication) yields large performance gains while preserving correctness.

Introduction

Matrix multiplication is one of the most important building blocks across scientific computing, machine learning, graphics, and signal processing. Because of this ubiquitous importance, modern processors include specialized hardware units that implement matrix-multiply-and-accumulate operations much more efficiently than a sequence of scalar multiply-add instructions. On many GPUs these units are called "Tensor Cores" or "matrix-multiply engines"; they implement fused multiply-add operations on small matrix tiles at very high throughput and are the workhorses behind the practical performance of deep learning training and inference. This chapter explains the hardware and software concepts behind tensor cores, how large matrix multiplications are decomposed into tile operations, the principal programming interfaces and abstractions (notably WMMA and its successors), layout constraints for operands and accumulators, and the precision modes supported by modern tensor cores (FP16, BF16, FP8 and related mixed-precision behaviors). The goal is to give you the intuition needed to read research papers and implement high-performance tiled GEMM kernels that leverage tensor cores.

# Overview of Tensor Cores and hardware-accelerated matmul

Tensor cores are specialized functional units inside GPUs (and some accelerators) that execute small, fixed-size matrix-multiply-and-accumulate operations extremely quickly. Instead of performing scalar multiply-adds one at a time, a tensor core performs many multiply-accumulate operations in parallel, typically implementing a fused operation of the form
$C \mathrel{+}= A \times B$
where $A$, $B$, and $C$ are small dense matrices (tiles), and the entire tile multiply-accumulate is performed in hardware with very high throughput and a hardware-controlled accumulation order.

A few points clarify why specialized hardware helps so much. First, the cost of matrix multiplication in conventional scalar code is primarily arithmetic with a regular memory-access pattern; by grouping arithmetic into tile-level operations, the hardware can exploit fine-grained parallelism, use wide datapaths, and apply high-throughput fused multiply-add (FMA) units. Second, the hardware can rearrange the order of operations and pipeline the multiply and accumulate stages, reducing latency and increasing utilization. Third, dedicated matrix-multiply hardware can implement mixed-precision paths and specialized data conversions (for example, convert inputs from a lower-precision storage format to a higher-precision accumulator) inside the datapath to give both high performance and acceptable numerical behavior.

Different GPU microarchitectures implement tensor cores with slightly different tile sizes, operand data types, arithmetic semantics (e.g., whether accumulation is performed in FP32), and interface primitives. For instance, early NVIDIA tensor cores implemented a $4\times4\times4$ warp-level primitive inside each core and exposed this via warps using APIs such as WMMA; later generations moved to larger tiles such as $16\times16\times16$ or combinations like $32\times8\times16$, improving throughput for particular shapes used in neural networks. The essential abstraction is the same: a hardware primitive computes a small matrix multiply-and-accumulate $D \leftarrow D + A \times B$ where $A$, $B$, and $D$ are tile-shaped matrices stored in registers or shared memory, and the hardware performs many multiply-adds in one fused operation.

Because tensor cores perform many arithmetic operations per instruction, they change the roofline balance between compute and memory bandwidth. Effective use of tensor cores requires exposing enough arithmetic intensity at the tile level and arranging data movement so that tiles for $A$, $B$, and accumulator $C$ are available in fast memory (registers or shared memory) when the hardware primitive is invoked.

# Tile-based matmul decomposition and GEMM primitives

Large matrix multiplications are typically expressed as general matrix-matrix multiply (GEMM) operations:
$C \leftarrow \alpha A B + \beta C$,
where $A$ is an $M\times K$ matrix, $B$ is a $K\times N$ matrix, and $C$ is an $M\times N$ matrix. To map this computation efficiently to tensor cores, the large matrices are decomposed into tiles that match the hardware primitive size. The decomposition is conceptually straightforward: partition the $M\times N$ output matrix $C$ into a grid of tiles of size $M_t \times N_t$, partition $A$ accordingly into tiles of size $M_t\times K_t$, and $B$ into tiles of size $K_t\times N_t$. The tile multiplication primitive then computes
$C_{i,j} \mathrel{+}= A_{i,k}\times B_{k,j}$
for each tile triple $(i,k,j)$, looping over $k$ (the reduction dimension) in tile strides. This is exactly the blocking/tiling strategy long used to optimize cache usage on CPUs, but now the key is to choose tile sizes that match tensor-core shapes.

A typical hardware primitive is characterized by a triplet of dimensions $(M_t, N_t, K_t)$ describing the tile sizes: $A_{tile}$ has shape $M_t\times K_t$, $B_{tile}$ has shape $K_t\times N_t$, and $C_{tile}$ has shape $M_t\times N_t$. The hardware computes $C_{tile} \mathrel{+}= A_{tile}\times B_{tile}$. For example, a tensor core that implements a $16\times16\times16$ primitive accepts $A$ and $B$ tiles of those dimensions and performs $16\cdot 16\cdot 16 = 4096$ multiply-accumulate operations per tile invocation. The whole GEMM is then a triple loop over tile indices:
for i in 0..M/M_t:
  for j in 0..N/N_t:
    C_tile = load C[i,j]
    for k in 0..K/K_t:
      A_tile = load A[i,k]
      B_tile = load B[k,j]
      C_tile += matmul_tile(A_tile, B_tile)
    store C_tile

This tiled decomposition has several important implications. First, the innermost tile multiplication should be highly optimized and mapped to a single tensor-core instruction (or a small number of them), so that the hardware can execute thousands of such tiles in parallel across warps and SMs. Second, the data movement of tile loads/stores must be carefully arranged to amortize the cost of moving tiles from DRAM into shared memory or registers. On GPUs, a common approach is to stage tiles of $A$ and $B$ into shared memory using coalesced loads by all threads in a CTA/block, then have threads within the warp cooperatively load fragments from shared memory into registers and invoke the tensor-core instruction. Third, because tensor cores apply a fixed tile shape, the overall GEMM dimensions $M$, $N$, and $K$ must be rounded up or handled with edge code to accommodate tiles near the matrix boundaries.

In addition to simply partitioning $M$ and $N$ into $M_t$ and $N_t$ tiles, one must also consider how warps map to tiles. Modern GPUs use a warp (a group of 32 threads) as the unit that issues a tensor-core operation. WMMA and related APIs present the hardware primitive as a warp-level matrix operation: each warp holds fragments of $A$, $B$, and $C$ in its register state, executes a single warp-level instruction to perform the tile matmul, and updates the fragment of $C$ in registers. This naturally leads to mapping one or more tiles per warp: a warp can compute a $M_t\times N_t$ tile (or multiple tiles) depending on the tile size and warp mapping.

The GEMM primitive at the tile level can therefore be seen as a micro-kernel which, when scheduled and tiled properly across warps and threadblocks, forms the basis of high-performance batched or pointwise matrix multiplication on GPUs.

# Programming interfaces: WMMA/WGMMA concepts (tile sizes, operands, accumulators)

To expose tensor-core functionality to software, hardware vendors provide programming interfaces that let kernels specify tile operations succinctly. On NVIDIA GPUs a long-standing interface has been WMMA (Warp Matrix Multiply and Accumulate). WMMA provides a high-level abstraction in CUDA to create "fragments" representing small matrix tiles in registers, load data into fragments from memory, perform a warp-level matrix multiply-accumulate, and store fragments back to memory. The WMMA API is explicit about tile sizes, operand types, and accumulator types.

The basic WMMA programming model has these elements. First, a fragment object represents the contents of a tile (for $A$, $B$, or $C$). The fragment has a compile-time shape $(M_t, N_t, K_t)$ and data-type (for example FP16 for inputs, FP32 for accumulators). Second, explicit intrinsics load a fragment from memory or shared memory into registers (for example wmma::load_matrix_sync), perform a matrix multiplication and accumulation (wmma::mma_sync), and store the accumulator back to memory (wmma::store_matrix_sync). The mma_sync operation is the key: it instructs the warp to execute one or more tensor-core instructions that compute $D \leftarrow D + A \times B$ on the associated fragments.

WMMA details depend on architecture and API version. For example, early WMMA supported fragment shapes such as $(16,16,16)$ with FP16 operands and FP32 accumulators on Turing/Ampere; later APIs exposed more shapes and data types (BF16, FP8), and introduced variants that accept different operand layouts (row-major or column-major) and vectorized loads. The programmer writes code that partitions matrices into tiles compatible with the fragment shape, loads them into fragments (possibly from shared memory), calls mma_sync, and writes results.

WGMMA (warp-level generalized matrix-multiply and accumulate) is an evolution of WMMA-like concepts aiming for greater flexibility in primitive shapes and layout control. Where WMMA exposes a fixed set of fragments and shapes, WGMMA or newer PTX-level instructions may provide multiple tile shapes (for instance options like $32\times8\times16$), support different element sizes, and expose ways to control tiling across lanes within a warp more flexibly. These newer interfaces also allow more efficient use of threads within a warp by reinterpreting which lanes hold which fragment elements, enabling larger macrokernels or different packing strategies.

From a programming standpoint, using WMMA/WGMMA entails the following conceptual steps: choose a tile shape that matches the hardware primitive and your global tiling, partition the matrices accordingly, implement cooperative loads of tiles into fast memory, convert memory layout to the fragment layout expected by the primitive (if needed), create fragments for $A$, $B$, and $C$, call the matrix multiply-accumulate primitive (mma_sync or its successor), and finally write the accumulator fragments to global memory. Error handling and boundary conditions (when $M$, $N$, or $K$ are not multiples of the tile sizes) require special-case code or padding.

The efficiency of WMMA-style code depends on aligning the software tiling and thread mapping to the hardware warp and lane mapping: which lane holds which element of a fragment, how fragments map to registers, and how the hardware schedules multiple tensor-core operations per cycle. High-performance libraries and compilers automate much of this, but understanding the primitive-level shapes is necessary to reason about register pressure, shared-memory reuse, and effective occupancy.

# Operand layout constraints (mn-major vs k-major) and accumulation semantics

A crucial detail when using tensor cores is the required memory layout of the operand tiles and the semantics of accumulation. The hardware primitive expects operands in a specific layout — this is often stated in terms that distinguish the "mn" dimensions (the two dimensions of the output tile $C$, namely $M_t$ and $N_t$) from the reduction/k dimension ($K_t$). Two common layout orientations for the input operands are described as "mn-major" and "k-major"; these terms indicate which dimension is contiguous in the memory mapping or in the lane mapping for the fragment.

To be precise, consider the operands to the tile matmul: $A$ of shape $M_t \times K_t$ and $B$ of shape $K_t \times N_t$. For $A$, an "mn-major" orientation (sometimes called row-major with respect to the output tile mapping) arranges elements so that the $M_t$ dimension is contiguous in the fragment mapping that the warp uses; lanes within a warp correspond to different $(m,k)$ indices with $m$ varying fastest or similar. Conversely, a "k-major" orientation arranges elements so the $K_t$ (the reduction dimension) is the fastest-varying in the fragment layout. Which orientation is preferred depends on how the hardware implements the multiply-accumulate internally. For instance, some tensor cores prefer $A$ to be in mn-major and $B$ in k-major so that successive vector lanes supply elements in the order the MAC array consumes them.

This is not just an implementation quirk: using the wrong layout or failing to pack data appropriately may lead to the inability to issue the tensor-core instruction directly, requiring extra permutation or scalar fallback work. WMMA/WGMMA APIs typically allow the programmer to specify the operand layout (row-major or column-major, or mn-major vs k-major) when loading fragments. When staging tiles in shared memory it is common to write them into shared memory in the layout expected by the primitive so that the subsequent fragment load is a simple copy and does not require lane shuffles.

Accumulation semantics are equally important. The primitive semantics are usually:
D := D + A * B,
where $D$ is the accumulator tile. Several practical considerations follow. First, the location and precision of $D$ matter. Many tensor cores accept $A$ and $B$ in a low-precision format (e.g., FP16 or BF16) but perform accumulation in a higher precision (commonly FP32) to improve numerical stability. This mixed-precision design reduces round-off error in the accumulation even while storing operands in compact formats, and it is the primary reason many neural-network workloads use FP16 weights/activations but accumulate in FP32.

Second, some hardware implements saturation or clamping semantics when writing accumulators back to a lower-precision storage format; if you store the accumulator $D$ to FP16 memory, the values will be converted (rounded and possibly clamped) from the internal accumulator type. That means when performing a full GEMM with a scalar $\beta$ multiplying the previous $C$, you often load $C$ into an accumulator fragment (possibly converting it to FP32), perform the tiled accumulations into that accumulator in FP32, and only when storing back to memory convert to the desired outbound format.

Third, the reduction order inside the tile may be unspecified in terms of associativity; fused multiply-add operations are typically used in hardware and the order in which products are summed determines rounding error differences. For example, summing sequentially along $k$ in increasing order may produce slightly different results than summing in a pairwise or tree-like fashion. This means that numerical reproducibility is not guaranteed across different tile shapes or different scheduling of the tiles, and algorithm designers should be aware when exact reproducibility is required.

Finally, tile-level operations are implicitly synchronized at the warp level: all lanes in the warp participate in loading and consuming fragment elements. When multiple tiles are mapped to the same warp (or when multiple warps cooperate for a larger tile), careful synchronization and consistent layout are required to ensure fragments are constructed correctly.

# Precision modes supported by Tensor Cores (FP16/BF16/FP8) and performance implications

One of the most powerful features of tensor cores is their support for multiple input and accumulator precisions. Modern tensor cores support a combination of input data formats and accumulator precisions, typically including FP16 (IEEE half-precision), BF16 (bfloat16), and more recently FP8 variants. Each precision mode offers a different trade-off between dynamic range, precision (number of significant bits), memory footprint, and ultimately performance.

FP16 (IEEE 754 half precision) provides approximately 11 bits of significand (10 fraction bits + implicit leading 1) and 5 exponent bits. FP16 has limited dynamic range and precision compared to FP32, but it halves the storage and memory bandwidth compared to FP32. Many tensor cores accept FP16 operands and perform accumulation either in FP16 (rarely) or in FP32 (more commonly for numerical stability). When FP16 inputs are accumulated in FP32, the result benefits from wider accumulator precision while still saving bandwidth and storage on inputs. This mixed FP16/FP32 mode is extensively used in deep learning training (where gradients and activations are often stored in FP16, but weight updates or accumulation use FP32 or master copies in FP32).

BF16 (bfloat16) is a format with the same exponent width as FP32 (8 bits) but fewer significand bits (7 bits). The larger exponent range compared to FP16 gives BF16 better dynamic range, which helps avoid overflow/underflow in deep neural networks, while still reducing bandwidth by half. Many tensor cores support BF16 input with FP32 accumulation. Because BF16 preserves the FP32 exponent range but reduces precision, it often gives accuracy comparable to FP32 for many neural-network workloads, especially when accumulation is in FP32.

FP8 is a further reduced-precision format that has recently been adopted experimentally in accelerator hardware to cut memory and bandwidth further. There are several FP8 encodings (for example E4M3 and E5M2: exponential bits / mantissa bits), each trading between dynamic range and precision. The very small mantissa in FP8 leads to coarser quantization and the potential for significant rounding noise. To make FP8 useful in practice, hardware and software typically require per-tensor or per-channel scaling factors before conversion and may perform accumulation in a higher precision (BF16 or FP32). Some tensor cores can accept FP8 operands and do accumulation in FP16 or FP32 internally, but using FP8 successfully usually requires quantization-aware training or other compensation techniques to preserve model quality.

Performance implications of these precision modes are substantial. Because tensor cores compute many multiply-accumulate operations per cycle, arithmetic throughput often scales inversely with operand bitwidth: lower-precision operands allow more simultaneous multiply units or more lanes per cycle. For instance, an architecture may deliver twice the TFLOPS for FP16 operand matmuls compared to FP32, and for FP8 it might increase further. However, the realized speedup in end-to-end applications depends on more than just arithmetic throughput: memory bandwidth, memory layout conversions, and additional overhead (scaling and quantization steps for FP8) can limit gains.

Some practical consequences:

- When inputs are stored in FP16 or BF16 but accumulators are in FP32, there is additional conversion cost when loading fragments into accumulator registers. Hardware usually implements fast conversion inside the tensor-core pipeline, but the software must account for mismatches when staging data in shared memory (e.g., storing FP16 tiles then loading them into fragments). The internal conversion hardware often makes this cost small compared to the arithmetic saved.

- Mixed-precision training patterns take advantage of FP16 (or BF16) for activations and gradients while keeping a "master" copy of weights in FP32. Updates are applied in FP32 to the master copy and then re-quantized to FP16 for forward/backward propagation. This approach captures the dynamic range and numerical stability benefits of FP32 while using FP16 for the expensive matmul operations.

- FP8 can provide even greater memory savings, which is attractive for very large models, but it requires careful dynamic range management. Per-channel scaling (so weights in different output channels use different scales) is a common technique. When tensor cores support FP8, they still typically perform accumulation in a wider format, which helps recover some accuracy. Research into FP8 training shows that with appropriate scaling and learning-rate adjustments, models can be trained to near-FP32 quality with FP8 matmuls; however, the software complexity increases.

- Numerical stability: using lower precision for inputs increases rounding error in the product $A \times B$ as each multiplicand is less precise. Accumulation in higher precision reduces the accumulation error but cannot fully eliminate the initial quantization error. Algorithms that are sensitive to rounding (for example, requiring exact numerical reproducibility or orthogonality constraints) may require additional algorithmic changes (mixed-precision iterative refinement, Kahan summation-like techniques, or keeping critical state in higher precision).

Finally, the peak FLOPS numbers advertised for tensor cores are contingent on using the supported precision modes. A common guideline when designing kernels is to maximize arithmetic utilization by choosing tile sizes and thread mappings that saturate tensor-core throughput while ensuring that memory subsystem and register pressure do not choke performance. Using lower-precision operands increases arithmetic density but also tightens the need for correct scaling and numerical handling.

Conclusion

Understanding tensor cores requires thinking at two levels simultaneously: the hardware primitive (tile-shaped fused multiply-accumulate) and the software tiling and data-movement strategy that supplies tiles to the primitive efficiently. Programming interfaces such as WMMA and its successors expose warp-level matrix-fragment constructs that let one express tile matmuls concisely, but correct and high-performance usage depends on matching tile sizes, operand layouts (mn-major vs k-major), and accumulation semantics. The variety of supported precisions (FP16, BF16, FP8, with FP32 accumulation) enables large performance and memory gains but brings trade-offs in numerical accuracy and algorithm design. Mastery of these details is essential to implement high-performance GEMM and to interpret and reproduce results from research that relies on hardware-accelerated matmul.

Introduction

Modern high-performance computing and machine learning workloads place enormous stress on memory systems. The arithmetic throughput of dense matrix multiply units and tensor cores has grown faster than raw memory bandwidth, so the ability to move data efficiently between DRAM, on-chip shared memory, and registers is often the limiting factor for performance. To address this, modern GPUs and accelerators expose specialized hardware and instructions designed to accelerate common memory patterns: dedicated asynchronous copy engines, warp-level matrix load/store primitives, permutation and shuffle instructions for in-register rearrangement, and strategies for making loads and stores coalesced and aligned. This chapter explains these mechanisms in depth, why they matter, and how to use them effectively. The goal is to provide the intuition and practical guidelines a student needs to read and implement research code that relies on aggressive memory optimization.

# Tensor Memory Accelerator (TMA) / Async high-performance copy engines

A Tensor Memory Accelerator (TMA) or more generally an asynchronous high-performance copy engine is a hardware unit that performs large, structured copies between device memory (DRAM) and a fast on-chip buffer (often called shared memory or an on-chip scratchpad) without tying up the compute cores. The key idea is to treat such copies as independent DMA-like transactions that can be launched by the program and then progress in the background while compute continues. This lets you hide memory latency and increase overall utilization.

TMA works best when the transfer pattern is regular and tile-shaped: copying a contiguous 2D tile from global memory into shared memory (or vice versa) with a specified element layout and alignment. The hardware uses wide memory requests and banking/coalescing rules to maximize DRAM bandwidth while minimizing the number of transactions. On GPUs the interface typically exposes asynchronous copy instructions (for example, NVIDIA's cp.async or dedicated TMA opcodes) that accept source/destination addresses, tile dimensions, and other parameters. The instruction queues the copy and returns immediately; completion is later synchronized using either explicit wait instructions or implicit mechanisms associated with barriers.

Two operational points are important. First, these engines are optimized for throughput, not for small random accesses. Launching many tiny transfers can be less efficient than performing a single larger transfer. Second, TMA transfers are often subject to alignment constraints. For peak DRAM efficiency, source addresses and tile widths are usually required to be aligned to a multiple of the memory transaction size (e.g., 128 bytes or a warp width times element size). Violating these constraints can cause extra DRAM transactions and degrade performance significantly.

From a programming model perspective, you treat TMA as a producer-consumer pipeline: a producer thread block launches a copy to bring the next tile into shared memory, then performs computation on the current tile while the copy engine loads the next tile. Synchronization is required to ensure the data is visible before use; most APIs provide a "wait" instruction that blocks until the requested transfer completes. By overlapping computation with memory movement, you can hide memory latency and saturate bandwidth.

TMA semantics also often support layout conversions during the copy: for example, converting from row-major global memory into specialized tiled layouts in shared memory that are better suited to tensor cores. When supported, this avoids an explicit in-kernel transpose and moves expensive layout work into the copy engine where it can be performed more efficiently.

# LDSM and STSM (ldmatrix / stmatrix) style warp-level matrix load/store

Warp-level matrix load/store instructions (illustratively called LDSM/STSM or ldmatrix/stmatrix in some ISAs) provide a mechanism to move small submatrices between global or shared memory and the registers of a warp in a single instruction. Unlike scalar loads which move one value per thread, a warp-level matrix load moves an entire tile into a set of registers distributed across the threads of a warp in a cooperative manner. Similarly, a store writes a tile from registers back to memory.

The fundamental advantage is twofold. First, these instructions can perform reordering or packing while moving data, producing a register layout that matches the operand layout expected by matrix units (e.g., tensor cores). This avoids costly per-element shuffles. Second, because the instruction is warp-synchronous, the hardware can generate the optimal set of memory transactions and place data directly into the per-thread registers, minimizing intermediate buffering.

To understand how ldmatrix works, consider a warp of 32 threads working cooperatively to load a 16x16 tile of 16-bit values into registers. The instruction specifies the tile shape and the leading dimension in memory. Internally, the hardware issues vectorized reads from the memory subsystem and routes the returned bytes so that each thread receives the specific subset it should own. Often the register-level result is a sequence of vector registers (for example, each thread may get 8 32-bit registers holding packed pairs) arranged so that subsequent operations (like tensor core instructions) can consume them without further rearrangement.

Because these operations are warp-level, the programmer needs to ensure the threads execute them in lockstep. Typically you issue ldmatrix/stmatrix within a warp and then immediately use the loaded registers while synchronized. When combined with TMA or asynchronous copies into shared memory, ldmatrix provides the final step to move the tile into the register layout expected by the accelerator.

There are important constraints and failure modes. These instructions are usually optimized for fixed tile sizes that match tensor core requirements (e.g., 8x8, 16x16) and expect specific alignments. Using irregular sizes or misaligned addresses can either be unsupported or produce slower sequences. Also, because the load is warp-cooperative, you cannot use it if only a subset of warp threads contains valid work, unless you pay attention to masking and conditional execution.

# Byte-permute and shuffle instructions for register rearrangement

Even after using warp-level loads, you will often need to permute data within registers to align with computational primitives. Byte-permute and shuffle instructions are the basic in-register building blocks for such rearrangement. These operations reorder bytes, words, or larger lanes inside a register or across registers in a warp with low latency.

Byte-permute (sometimes called bpermute, permute, or shuffle bytes) operates inside a vector register and can extract or rearrange any byte positions into a new vector. Because it works at byte granularity, it is flexible enough to implement arbitrary packing and endianness conversion. Shuffle instructions (such as shfl, shfl.down/up/xor in some GPU ISAs or pshufb/punpck in x86 SIMD) move whole lanes or words between threads in a warp or between lanes within a SIMD register. These are especially useful for implementing transposes, interleaving, or broadcasting.

Intuitively, think of registers as small arrays. Byte-permute lets you take arbitrary bytes from the array and assemble them into a new ordering. Shuffle across threads lets warp-thread 0 obtain data originally held by warp-thread 8, for example. Combined, these primitives allow arbitrary reshaping of tiles once they are in registers.

Using these instructions effectively requires attention to instruction latency, throughput, and the size of reorganization you need. Fine-grained permutes that touch every byte can be done with a handful of instructions, but complex multi-step rearrangements can become a bottleneck if done naively. A common pattern is to perform coarse rearrangement first using inter-thread shuffles (which move whole lanes cheaply) and then do fine-grained byte or word permutes inside each thread. This minimizes cross-thread communication and keeps the fastest instructions in the hot path.

# Coalesced load/store strategies and in-kernel transpose basics

Coalesced loads and stores are essential for achieving high memory throughput. At a high level, coalescing means organizing memory accesses so that a group of adjacent threads (often a warp) issue requests that can be combined into as few aligned DRAM transactions as possible. For example, if each of 32 threads in a warp reads a 4-byte float from successive addresses, the hardware can combine these into a single 128-byte transaction, yielding optimal bandwidth.

Achieving coalescing requires careful attention to data layout, element size, thread indexing, and alignment. Data should be stored in memory in a layout where the fastest-varying dimension maps to thread index within a coalescing group. For 2D tiles, the natural mapping is to assign consecutive threads to consecutive elements in a row if the matrix is row-major and the row stride is 1.

However, many algorithms naturally access data in column-major order or need tiles for which threads desire column-oriented access. In such cases, naively issuing loads will be uncoalesced: each thread may access a distant memory address, causing many small transactions and low bandwidth. This is where in-kernel transpose strategies come in.

An in-kernel transpose means performing a reshape of a tile after loading it so that the access pattern for the next operations becomes contiguous. A typical approach loads a tile from global memory into shared memory in a coalesced fashion (e.g., reading rows), performs a barrier, and then reads from shared memory in the transposed order into registers for computation. Shared memory is used because it supports random and fine-grained accesses at much higher bandwidth and lower latency than global memory. The classic shared-memory transpose avoids bank conflicts by adding padding to the shared-memory tile (for example, allocating a tile of width $W+1$ when the natural width is $W$) so that threads reading transposed addresses do not collide on the same bank.

When designing in-kernel transpose code, you must balance several factors. The tile size should be chosen so that the shared-memory tile fits comfortably in the available shared memory while being large enough to amortize the cost of synchronization. Bank conflict avoidance is critical: simple padding usually suffices, but you must know the shared-memory bank width and mapping. Additionally, choose thread mapping to memory so that the initial loads are perfectly coalesced and the subsequent shared-memory reads are efficient.

# When to use pre-processing transpose vs in-kernel transpose

Deciding whether to transpose data ahead-of-time (pre-processing transpose) or to transpose inside the kernel (in-kernel transpose) depends on workload characteristics, memory bandwidth, reuse, and the cost of extra memory writes.

Pre-processing transpose means reorganizing the data in global memory before the main computation, so that subsequent kernels see data in the ideal layout. This can be worth it when the same data is reused many times across kernels or iterations. The upfront cost of an extra write is amortized by the performance benefits during many subsequent reads. Pre-processing also simplifies kernels because they can assume ideal alignment and coalescing, and it may allow using hardware-accelerated copy engines to perform the transpose efficiently once and for all.

In contrast, in-kernel transpose avoids additional writes to DRAM by performing the transpose on-chip as data is loaded. This is often preferable when the tile is used only once or a small number of times, as writing the transposed version to memory would double memory traffic. In-kernel transpose leverages shared memory and warp-level cooperativity and is an attractive option when shared memory capacity and the warp-synchronous facilities (like ldmatrix and shuffles) are available.

Several practical rules of thumb guide the choice. If your data tile will be read multiple times (for example, in many GEMM micro-tiles across iterations of an algorithm), consider pre-transposing if the number of reads times the benefit exceeds the cost of one extra write. If the data is streaming and used only once, prefer in-kernel transpose or warp-level reorganization to avoid extra DRAM writes. Also consider whether the hardware provides efficient offload engines that can perform the transpose with low overhead; a TMA that supports layout conversion can be a compelling reason to pre-process data at load time rather than doing more expensive manual transposes later.

Finally, consider development complexity and portability. In-kernel transpose code can be intricate, with careful attention to bank conflicts and warp mappings; a pre-processed layout can simplify many kernels and make algorithmic reasoning easier. Conversely, pre-processing increases storage footprint and may complicate interoperability with other components expecting the original layout.

Conclusion

Specialized memory engines and data-movement instructions are powerful tools for closing the gap between computational throughput and memory bandwidth. Asynchronous copy engines like TMA let you overlap large structured transfers with computation and sometimes perform layout conversions on the fly. Warp-level matrix load/store primitives map tiles directly into register layouts suitable for matrix accelerators. Byte-permute and shuffle instructions allow low-latency in-register rearrangement. Coalesced load/store patterns and careful in-kernel transpose design make efficient use of DRAM and shared memory. Choosing between pre-processing and in-kernel transposes is a question of reuse, memory traffic, and hardware capabilities. Understanding these mechanisms and tradeoffs is essential to achieving close-to-peak performance on modern accelerators and to reading research that pushes memory systems to their limits.

Introduction

Memory tiling and blocking lie at the heart of high-performance implementations of dense linear algebra and attention mechanisms. Modern accelerators are orders of magnitude faster in arithmetic than in off-chip memory bandwidth, which means that the design of an algorithm's data movement — how and when data enters on-chip buffers, how long it is reused, and how it is staged between registers, shared memory, and global memory — often determines the ultimate performance. This chapter examines practical tiling strategies for matrix multiplication and attention layers, with particular attention to the three roles tile sizes play: the sequence dimension (time or tokens), the head dimension (feature width per attention head), and the blocking choices that trade compute for memory bandwidth. We explain circular and shared memory buffering, multi-stage buffering, producer/consumer warp partitioning, buffer life-cycles, and register tiling, all framed to give you the intuition and concrete knobs you will see in performance-oriented research papers and libraries.

We assume you are familiar with the basic mathematics of matrix multiplication and attention. For matrix multiplication we will use the notation $C = A \cdot B$ with $A$ of size $M \times K$, $B$ of size $K \times N$, and $C$ of size $M \times N$. For attention we will use the common Query/Key/Value (Q/K/V) notation where queries $Q$ and keys $K$ have shapes $(S, H)$ per head (sequence length $S$, head width $H$), producing attention weights of shape $(S, S)$ per head and a final output of shape $(S, H)$ per head after multiplying weights by $V$. Throughout, we will indicate per-head dimensions and per-block sizes explicitly. The goal is to show how to set tile sizes for queries, keys, and values (and for matmul in general), how to balance compute and bandwidth, and how to manage on-chip buffers and warp roles to achieve high throughput.

# Tile sizes for queries, keys, values (block sizes in sequence and head dimensions)

Choosing tile sizes in attention is a two-dimensional decision: you must tile both across the sequence axis (tokens, length $S$) and the head/feature axis (dimension $H$). Effective tile sizes determine how much data is read into on-chip buffers at once and how many arithmetic operations can be performed per byte moved from global memory.

Consider a single attention head with queries $Q$ and keys $K$ of shapes $(S, H)$. A direct computation of attention weights is a matrix multiplication $W = Q \cdot K^\top$, where $W$ is $(S, S)$. Computing an output row of $W$ for a particular query token $i$ involves computing dot products between $Q_i$ (a row vector of length $H$) and all $K_j$ for $j = 1 \dots S$. If you tile purely in the sequence direction, say processing $T_s$ query tokens at a time (a query tile of height $T_s$) and $T_s$ key tokens at a time (a key tile of width $T_s$), then the raw arithmetic reuse for $Q$ and $K$ is improved: one tile of keys loaded once can be reused by $T_s$ queries. However, this ignores the head dimension, which controls the length of the inner dot-product reductions.

To capture both axes, we introduce a tile shape $(T_s^Q, T_s^K, T_h)$ where $T_s^Q$ is the number of query tokens processed together, $T_s^K$ is the number of key tokens processed together, and $T_h$ is the width in the head (the number of feature elements of $Q$ and $K$ processed together in the reduction). In practice, many implementations use symmetric tiling in sequence for queries and keys (i.e., $T_s^Q = T_s^K = T_s$) to simplify indexing and to balance work between tiles; however, asymmetry can make sense for causal attention or when sequence lengths differ.

What are useful magnitudes for these tile sizes? The head dimension $H$ is often in the range 32 to 128 in common transformer models. Suppose $H = 64$. If you pick $T_h = 64$, you carry out full-width dot products inside registers or shared memory, which minimizes outer-loop bookkeeping but increases the temporary storage required. If $T_h = 16$, then each reduction requires four micro-tiles in $H$, which increases the number of passes over the key tiles but reduces per-tile storage and may improve occupancy because each thread or warp handles a smaller register footprint.

The sequence tile $T_s$ interacts directly with on-chip shared memory and cache capacity. Each key tile of $T_s$ entries consumes $T_s \cdot T_h$ elements (per head) to hold a block of keys in shared memory. If you intend to hold both a block of keys and a block of queries simultaneously in shared memory for reuse, the combined memory requirement per head is roughly $T_s^K \cdot T_h + T_s^Q \cdot T_h$. If the platform has $S_{SM}$ bytes of available shared memory per multiprocessor and you map $W$ warps/threads to that SM, you must choose $T_s$ and $T_h$ so that the product times element size fits within $S_{SM} / W$ (after accounting for other usages). This simple capacity constraint often dominates tile size selection.

A second consideration is the arithmetic intensity within a tile: how many floating-point operations (FLOPs) are performed per byte fetched from global memory. For a tile that multiplies a query tile of $T_s^Q \times T_h$ by a key tile of $T_s^K \times T_h$ (to accumulate $T_s^Q \times T_s^K$ partial scores), the number of multiply-accumulate operations is $2 \cdot T_s^Q \cdot T_s^K \cdot T_h$ (multiply and add counted as two FLOPs) while the bytes brought from global memory (assuming no reuse outside the tile) are roughly $(T_s^Q + T_s^K) \cdot T_h \cdot b$ where $b$ is bytes per element. Thus the arithmetic intensity is:

$I_\text{tile} = \frac{2 \cdot T_s^Q \cdot T_s^K \cdot T_h}{(T_s^Q + T_s^K) \cdot T_h \cdot b} = \frac{2 \cdot T_s^Q \cdot T_s^K}{(T_s^Q + T_s^K) \cdot b}$.

Notice that $T_h$ cancels out here; the intensity for computing the partial score matrix depends only on sequence tile sizes and element size when both tiles share the same $T_h$ reduction. This shows why tiling in the sequence axis is the main lever for arithmetic intensity in attention score computation: increasing $T_s^Q$ and $T_s^K$ increases the number of dot products per loaded element. However, $T_h$ remains important because it determines how many times we must iterate over $K$ and $Q$ tiles to complete a full dot-product reduction for a single pair $(i, j)$. If $H$ is large and $T_h$ is small, each pair will require multiple passes and thus more reads/writes for intermediate accumulation (if not stored entirely on-chip).

In summary, pick $T_h$ so that each warp or thread can hold its working reduction in registers (minimize register spilling) and so that shared memory usage per block fits hardware limits. Pick $T_s$ to increase arithmetic intensity while respecting shared memory and occupancy constraints. Typical empirical choices in GPU implementations are $T_h$ in the range 16–64 and $T_s$ in the range 8–64 depending on sequence length and head width. For very long sequences, larger $T_s$ are favored to reduce off-chip traffic, while for short sequences, smaller $T_s$ and larger $T_h$ can maximize warp utilization.

# Blocking for compute vs blocking for memory bandwidth

Blocking can be oriented toward maximizing compute utilization or toward reducing memory traffic. The optimal blocking depends on whether your kernel is compute-bound or memory-bound. The roofline model is a concise way to think about the tradeoff. The roofline states that achievable performance $P$ is:

$P = \min\{P_\text{peak}, I \cdot B\}$,

where $P_\text{peak}$ is peak FLOPs/sec, $B$ is peak memory bandwidth (bytes/sec), and $I$ is arithmetic intensity (FLOPs per byte). If $I \cdot B < P_\text{peak}$, your kernel is memory-bound; otherwise it is compute-bound.

Blocking for compute aims to increase instruction-level parallelism, use fused multiply-adds and vector units efficiently, and reduce kernel launch or synchronization overheads. For example, if $H$ and $T_s$ are such that a single tile contains many small matrix-multiply operations that can be fused and scheduled without global memory access, the kernel will exploit compute resources well. Register tiling (explained below) is a compute-oriented blocking: it packs multiple output elements into registers and accumulates them so that arithmetic units are kept busy.

Blocking for memory bandwidth emphasizes maximizing arithmetic intensity $I$ by increasing reuse of each loaded byte. For attention, sequence blocking is the key lever: if you enlarge $T_s$, each loaded key vector of length $T_h$ is reused by $T_s$ different queries. The memory-oriented approach may sacrifice some compute locality or reduce occupancy, but it can multiply the effective bytes-to-FLOPs ratio so as to move from memory-bound to compute-bound.

To choose between compute-blocking and memory-blocking, first estimate where your kernel lies on the roofline. Measure or look up $P_\text{peak}$ and $B$. Compute the baseline intensity for a naive implementation and see whether $I \cdot B$ is below or above $P_\text{peak}$. If memory-bound, increase $T_s$ (sequence tiling) or reuse more data in shared memory/caches. If compute-bound, reduce the register pressure per thread by decreasing $T_h$ or reduce per-block shared memory to increase occupancy. Compute-bound kernels benefit from larger micro-tiles per thread or warp so that the arithmetic pipeline is saturated; memory-bound kernels benefit from larger macro-tiles that increase reuse.

There is also a hybrid direction: multi-stage tiling that first maximizes reuse in shared memory (to raise $I$) and then maximizes compute inside registers (to approach $P_\text{peak}$). For attention, this often results in two-level tiling: a large sequence tile $T_s^\text{macro}$ that increases amortized reuse, and a smaller per-warp micro-tile $(t_s, t_h)$ that fits into registers and gets accumulated efficiently. The macro-tile trades extra shared-memory usage and more complex scheduling for higher arithmetic intensity; the micro-tile trades compute efficiency for reduced buffer pressure.

Finally, note that the choice of blocking must respect algorithmic constraints like causality in autoregressive attention. Causal masking can prevent symmetric reuse across queries and keys, forcing asymmetric tiling (for example, small key tiles when computing early tokens). In such cases, the effective arithmetic intensity varies across positions and you must adopt adaptive tiling strategies or accept lower performance for masked segments.

# Circular/shared memory buffering and multi-stage buffering

Circular buffers and multi-stage buffering are techniques to sequence data through multiple layers of on-chip memory so as to hide latency and maximize reuse. In streaming or tiled matrix-multiply and attention kernels, the pattern is often: read a tile from global memory to shared memory, stage it across multiple compute steps (for reuse by multiple consumers), and then evict it when no longer needed. Circular buffering is a disciplined way to manage a fixed number of these on-chip tiles in FIFO order without costly index movement.

A circular buffer for tiles reserves a contiguous region of shared memory divided into slots, each large enough to hold one tile (for example, one key tile). The producer writes incoming tiles into the next available slot modulo the number of slots. Consumers read tiles from the buffer using the same modulo arithmetic. If the buffer contains $R$ slots, you can overlap up to $R-1$ producer operations with consumer operations without overwriting unread tiles. The typical rationale is to allow a multiple-stage pipeline where while one tile is being produced (loaded from global memory), another is being consumed for computation and another might be being written back or prepared.

Multi-stage buffering refers to using more than two levels of storage: global memory $\rightarrow$ L2/cache $\rightarrow$ shared memory $\rightarrow$ registers. On GPUs, it is common to implement a two-stage pipeline within the SM: global memory accesses are issued while computation proceeds on previously loaded tiles in shared memory, and registers hold the micro-tile accumulators. A multi-stage buffering scheme might explicitly stage tiles through two shared-memory banks or double-buffer at the shared memory level: one bank is used by the compute stage while the other bank is filled with the next tile from global memory. Then the roles swap. Double-buffering hides global memory latency and allows continuous warps execution without idling for loads.

Circular buffering generalizes double buffering. Suppose you want to pipeline across $S_p$ steps (for example, to match prefetch depth or to sustain a deeper pipeline that hides both memory latency and scheduling latency). You reserve $S_p$ slots. The producer will load tile index $k$ into slot $(k \bmod S_p)$, and consumers will consume tiles at the appropriate time; careful synchronization ensures a tile is not overwritten before all consumers finished. Synchronization is typically implemented by barriers at warp-block level or by atomic counters for asynchronous pipelines, but the highest performance implementations use intra-block synchronization primitives (e.g., __syncthreads on CUDA) combined with careful scheduling so that producers and consumers work in lockstep, eliminating atomic overhead.

Multi-stage buffering is especially useful when different tiles are accessed at different granularities by different consumers. In attention, one might read key tiles to compute partial dot-products for many different query micro-tiles. A design might stage a key tile into shared memory, let several warps compute different rows or columns that access that tile, and only then evict it. If the consumers are partitioned across warps and the producer is a subset of warps, circular buffering allows continuous generation of tiles while consumers progress through multiple tiles in sequence.

Finally, note the interplay between tile size, shared-memory bank conflicts, and alignment. To maximize effective throughput, tile layouts in shared memory should avoid bank conflicts (e.g., by padding rows to a multiple of the bank width) and should allow coalesced global memory loads into contiguous shared memory slots. When you design circular buffers and multi-stage buffering, consider memory alignment and padding as an essential part of achieving the expected reuse and bandwidth.

# Producer/consumer partitioning of warps and buffer life-cycle

Modern GPU kernels often partition threads or warps into producers and consumers to implement streaming pipelines. The producer warps are responsible for loading data from global memory into shared memory buffers and for possibly transforming it (e.g., transposition, scaling), while consumer warps perform the compute work using the shared tiles and accumulate results into registers. Partitioning warps reduces contention for memory and compute resources and enables pipelined execution where producers and consumers overlap.

A typical life-cycle of a buffer in this pattern has phases: allocate, fill (produce), consume (compute), complete, and release. When a producer writes a tile into shared memory, it marks the slot as filled. Consumers read the filled tile and perform multiple operations (e.g., compute dot products with multiple query micro-tiles). Only after all consumers that need the tile have processed it is the slot safe to overwrite. Therefore, buffer slots must be managed with reference counts or with a deterministic usage schedule that guarantees no consumer will attempt to read an overwritten slot.

Partitioning warps into dedicated producers and consumers can simplify life-cycle management because the roles are fixed and scheduling can be made deterministic. For example, assign the first $P$ warps in a block as producers that perform global loads into a per-block circular buffer. The remaining $C$ warps are consumers that repeatedly read from the buffer and compute. By ensuring that the consumption pattern is regular (for instance each consumer processes $n$ micro-tiles in sequence), you can compute exactly how many producers’ tiles must be kept in the buffer before reuse, allowing you to size the circular buffer precisely.

A key practical point is the synchronization between producers and consumers. If producer warps are ahead of consumers, they must wait before overwriting slots. If producers are behind, consumers may stall waiting for tiles. To avoid both, many implementations use a schedule where producer and consumer pointers advance in lockstep modulo the slot count. For example, in a two-stage double buffering scheme, after producers write slot 0 and slot 1 in sequence, consumers process slot 0 then slot 1, then producers overwrite slot 0 while consumers process slot 1. A general circular buffer with $S_p$ slots can sustain a pipeline of depth $S_p$ without stalls if the latency of loading and consumption is matched appropriately.

Another important partitioning style is to have each warp both produce and consume but for different tiles: each warp loads the tile it will later consume. This reduces synchronization complexity because ownership is local, but it reduces opportunities for sharing loaded tiles across warps and therefore may increase global memory traffic. In attention, because one key tile is reused by many queries, it is often better to have specialized producers load a shared key tile for multiple consumer warps, maximizing reuse.

For correctness and performance, consider corner cases: partial tiles (when sequence length is not a multiple of $T_s$) require masking and might reduce reuse, and misbalanced roles (too few producers) can create starvation of consumers. Empirical tuning often finds a sweet spot where the number of producer warps and consumer warps is chosen to balance load latency and compute capacity, and the circular buffer depth is sized to match the global memory latency and the number of consumers reusing each tile.

# Register tiling and exchanging intermediate tiles across stages

Register tiling packs small sub-tiles of the output and partial reductions into registers, minimizing accesses to shared memory and maximizing arithmetic throughput. Registers are the fastest storage on a processor, so keeping frequently updated accumulators there reduces latency and bandwidth to other on-chip memories. For matrix multiplication and attention, register tiling commonly takes the form of each thread computing and keeping a micro-tile of the output matrix $C$ (or of the attention outputs) of size $r_m \times r_n$, where $r_m$ is the number of rows of $C$ handled by the thread and $r_n$ is the number of columns. The thread iterates over the reduction dimension $K$ (or $H$ for attention), loading small portions of $A$ and $B$ into registers and performing fused multiply-adds into the register accumulators.

A canonical approach uses a two-level tiling pattern: the outer tile is a shared-memory tile of size $(M_b, N_b)$ that holds a block of $A$ and $B$ to be reused by multiple threads; inside that, each warp or thread computes micro-tiles of size $(r_m, r_n)$ entirely in registers. The register micro-tile size is constrained by the number of registers per thread and the need to avoid spilling into local memory (which would significantly degrade performance). For example, on an architecture with 255 registers per thread (an extreme example), you might be able to hold many accumulators; on more common hardware with 64–128 registers per thread, micro-tiles are smaller and must be tuned.

Register tiling also interacts with exchanging intermediate tiles across stages. In multi-stage pipelines, a thread or warp may produce intermediate partial accumulators for one stage that are needed by another stage. Instead of writing those partials back to shared memory, the kernel can exchange them directly among warps using register-level shuffle operations or small shared-memory handoffs. Modern GPUs provide warp shuffle (shuffle) instructions that allow threads within a warp to read each other's registers without going through shared memory. This enables exchanging sub-tiles inside a warp very efficiently: one thread holds some columns, another holds complementary columns, and they use shuffle instructions to assemble complete rows or columns for the next computation stage.

When exchange must happen across warps (not just within a warp), small shared-memory staging is often used because inter-warp register exchanges are not directly supported. In that case, keep the exchanged tile as small as possible to limit shared memory traffic. A common pattern is for each warp to compute partial results into registers, write them into a small shared-memory tile (often double-buffered), and then synchronize so other warps read them into registers for the next stage. These patterns allow multi-stage algorithms (e.g., computing attention scores, applying softmax, and then multiplying by values) to be implemented with minimal global memory traffic: the intermediate attention scores or softmax-normalized weights never leave on-chip if they are small enough to be held in registers or shared memory.

A concrete example in attention is the per-query accumulation of weighted sums of values. After computing attention weights for a query micro-tile against many key tiles, a thread can accumulate a micro-tile of the output vector into registers. Once the full reduction over keys is complete, threads may need to normalize the accumulated outputs (for example by dividing by the softmax denominator) or perform a final rearrangement. If the normalization factor is computed separately (e.g., the sum of exponentials across keys), it must be communicated to the threads that hold the output accumulators. A typical pattern is: threads compute partial sums for the softmax denominator and store them in shared memory; a warp-reduce computes the denominator, and the result is broadcast into registers (via shuffle or a read from shared memory) for final normalization. Because the denominator is a single scalar per query micro-tile or a small vector per micro-tile, this exchange is cheap compared to global memory.

When designing register tiling, be careful about numerical accumulation order: long reductions performed in registers can accumulate rounding error. If numerical accuracy is critical, consider pairwise summation or Kahan-style accumulators at the cost of additional instructions.

Finally, register tiling must be considered together with occupancy. Very aggressive register tiling uses many registers per thread and can reduce the number of threads or warps that can reside concurrently on an SM (occupancy), which can hurt the ability to hide memory and instruction latencies. There is a tradeoff: more registers per thread reduce off-chip and shared-memory traffic but can increase latency exposure if occupancy drops too low. On many GPUs, moderate register tiling combined with multi-stage shared-memory buffering achieves the best balance.

# Putting it all together: a worked-through attention tiling pipeline

To consolidate the concepts, consider an attention kernel for a single head that computes outputs $O$ from $Q$, $K$, $V$, with sequence length $S$ and head width $H$. A high-performance pipeline might be organized like this:

1. Choose a macro sequence tile $T_s^\text{macro}$ to maximize arithmetic intensity given shared memory and the number of consumers. Let $T_h^\text{macro}$ be a reduction chunk to balance register usage. For example, $T_s^\text{macro} = 32$, $T_h^\text{macro} = 32$ for $H = 64$.

2. Partition thread blocks so that each block is responsible for $T_s^\text{macro}$ query tokens and cooperatively loads key tiles of size $T_s^\text{macro}$ into a circular shared-memory buffer. Within the block, reserve a circular buffer with $S_p = 2$ or $4$ slots (double or quadruple buffering) depending on global memory latency and load time.

3. Assign the first $P$ warps in the block as producers that issue coalesced global loads into the next available slot, performing any required transpose into the shared-memory layout optimized to avoid bank conflicts. Producers advance the producer pointer modulo $S_p$.

4. Assign consumer warps to repeatedly read the latest filled slot(s) and compute partial attention scores for their assigned query micro-tiles. Each consumer maintains register micro-tiles of size $(r_s, r_h)$ where $r_s$ is the number of query rows per thread and $r_h$ is the number of output elements per thread. Consumers use warp-shuffle within the warp to exchange loaded register values, reducing the need to touch shared memory for intra-warp communication.

5. For each loaded key tile, consumers compute partial dot products across $T_h^\text{macro}$ and accumulate into registers. After progressing across all reduction chunks needed to cover $H$, the consumers have full attention logits or partial sums for softmax. If softmax is required, perform a numerically stable reduction in registers and possibly a small shared-memory exchange to compute the normalizing denominator. Use intra-warp shuffle or small shared-memory arrays to broadcast the denominator back into registers.

6. Multiply normalized attention weights (which can be held in registers or small shared memory) by corresponding value tiles. Values can be streamed similarly through the circular buffer or read on demand; because weights are used immediately by the same consumers who computed them, keeping weights in registers avoids a write/read back to shared memory.

7. Once the consumer accumulators contain final outputs for their micro-tiles, write them back to global memory with coalesced stores.

This pipeline uses macro-tiling to boost arithmetic intensity, multi-stage buffering and circular buffers to hide latency and permit reuse, register tiling and intra-warp exchange to minimize on-chip traffic, and producer/consumer partitioning to balance memory and compute work. Properly tuned, such a design can be memory-bandwidth efficient (high reuse of keys and values) while also allowing compute units to remain busy.

Conclusion

Tiling, blocking, and buffer management are the engineering levers that convert an algorithm's arithmetic potential into realized throughput on modern accelerators. The right tile sizes in the sequence and head dimensions balance reuse, register pressure, and shared-memory capacity. Deciding whether to emphasize compute-blocking or memory-blocking depends on where the kernel sits on the roofline, but the best designs usually combine both by multi-stage tiling: increase sequence tile sizes to amplify arithmetic intensity while using register micro-tiling to saturate compute units. Circular and multi-stage buffering hide latency and manage buffer life-cycles, while producer/consumer warp partitioning provides a disciplined way to orchestrate loads and computation. Register tiling and intra-warp exchanges keep the hottest data in registers and minimize slower on-chip accesses. Together these techniques form the toolkit for implementing high-performance matmul and attention kernels; mastering them will allow you to analyze and reproduce the optimizations you encounter in research papers and production libraries.

# Introduction

Softmax is a core building block in machine learning models, from classification heads to attention mechanisms in transformers. The softmax of a vector $x\in\mathbb{R}^n$ produces a probability distribution
\[
\operatorname{softmax}(x)_i = \frac{e^{x_i}}{\sum_{j=1}^n e^{x_j}}.
\]
When batches and high-dimensional vectors are involved, computing softmax efficiently becomes critical for overall system throughput. On GPUs, throughput is limited not only by arithmetic throughput but also by memory bandwidth, instruction throughput for special functions, and the ability to map reductions and data movement to the hardware’s parallel structure (warps, thread blocks, and shared memory). This chapter explains how to implement softmax efficiently on GPUs. We cover parallel row-wise reduction patterns used to compute row maxima and sums, numerical stabilization using the subtract-max/trick and log-sum-exp, how exponential evaluation interacts with special-function units (SFUs) on GPUs, approximation strategies for $e^x$ and their trade-offs, and techniques that minimize memory traffic by performing local reductions.

Throughout, emphasize intuition, correctness, and the practical trade-offs of performance versus numerical accuracy. The goal is that after reading this chapter, you will be able to read GPU softmax code in libraries like cuDNN, Triton, or custom kernels, and understand why they are written that way and what alternatives exist.

# Row-wise reduction patterns (max, sum) implemented in parallel

Softmax applied to a matrix is typically computed row-wise: for a matrix $X\in\mathbb{R}^{B\times N}$ with $B$ rows (batch size) and $N$ columns (vector length), we want to compute softmax for each row independently. GPUs provide massive single-instruction multiple-thread parallelism, but reductions (max, sum) need coordination across threads that collectively own the elements of a row. The key idea is to map each row to a group of threads that cooperate to compute reductions hierarchically and in parallel across rows.

There are several common mapping strategies:

- One thread per element: launch $B\times N$ threads; each element is processed by one thread. Threads cooperate within a warp or block to perform reductions using warp intrinsics or shared memory. This mapping is simple but can be limited by the cost of collective communication when $N$ is small.

- One warp per row: assign one warp (commonly 32 threads on NVIDIA) to each row. Each thread in the warp processes several columns (strided or contiguous) and the warp uses fast warp-level primitives (like shuffle or ballot) to implement reductions. This works well when $N$ is comparable to or larger than a warp size; throughput is high because warp intrinsics avoid shared memory and synchronization barriers.

- Multiple warps per row: for very long rows, multiple warps are assigned to the same row. Each warp computes a local reduction over its assigned columns, then a second-level reduction combines the warp-level results. This requires shared memory and cross-warp synchronization (block-level barriers), but it scales to large $N$.

- Multiple rows per block: assign a thread block to process several rows. Threads are partitioned into subgroups (possibly warps) that operate on different rows. This maximizes the reuse of shared memory and reduces kernel launch overhead.

Whatever mapping is chosen, a hierarchical reduction pattern minimizes latency and leverages fast intra-warp communication. A typical two-level approach is:

1. Local reduction per thread: each thread accumulates a local max or partial sum over the elements it loads into registers. This reduces register-to-register work and amortizes memory loads.

2. Warp-level reduction: threads within a warp combine their local results using warp shuffles (e.g., XOR-shuffle tree) to compute a warp-local max or sum. Warp shuffles are preferable because they avoid shared memory and are very low-latency.

3. Block-level reduction (if necessary): when multiple warps participate in the same row, the warp results are written to shared memory and a single warp performs a reduction on those warp results, or a tree reduction using atomic or synchronization with __syncthreads() is used.

Max and sum have slightly different properties. Maximum is an idempotent associative operation that is stable under parallel reductions; sums require careful ordering if numerical reproducibility is desired, but associative summation is acceptable for many ML workloads. For softmax numerical stability, computing the exact order is less important than having consistent accuracy.

To illustrate concretely, imagine one warp per row. Each thread t in the warp computes
\[
\text{local\_max}_t = \max_{k=0}^{K-1} x_{i, t+kw}
\]
where $w$ is warp size and $K=\lceil N/w\rceil$ is the number of elements per thread. Then the warp-level max is computed by repeated shuffle-xor:
\[
\text{warp\_max} = \max\left(\text{local\_max}_t, \text{local\_max}_{t\oplus 16}, \ldots\right).
\]
The same pattern applies to computing sums, though numeric accumulation in 32-bit floats leads to some rounding errors when $N$ is large; in those cases one might use pairwise summation or FP16-compute/FP32-accumulation to balance performance and accuracy.

Key performance considerations include reducing synchronization points, minimizing shared-memory bank conflicts when shared memory is used, and ensuring coalesced global memory loads so threads in a warp read contiguous addresses when possible. For row-major storage and one warp per row, contiguous columns are loaded by consecutive threads, giving coalesced accesses. When rows are very short (smaller than warp size), it is often better to pack multiple rows per warp to maintain occupancy.

# Numerically stable softmax: subtracting row max and log-sum-exp

Directly computing $e^{x_i}$ can overflow or underflow for large positive or negative $x_i$. A standard stabilization is to subtract the maximum value in the row before exponentiating:
\[
\operatorname{softmax}(x)_i = \frac{e^{x_i}}{\sum_j e^{x_j}} = \frac{e^{x_i - m}}{\sum_j e^{x_j - m}},
\]
where $m=\max_j x_j$. This subtraction does not change the result but keeps exponents in a numerically safer range, typically preventing overflow when entries are large. When computing log-likelihoods or log-softmax, the log-sum-exp trick provides a stable computation of $\log\sum_j e^{x_j}$ as
\[
\log\sum_j e^{x_j} = m + \log\sum_j e^{x_j - m},
\]
where $m$ is the same row max. This formula avoids exponentiating large positive numbers and keeps the sum under control.

On GPUs, implementing this numerically stable pattern requires two reductions per row: one to find $m$ and another to compute the sum of $e^{x_j - m}$. A typical kernel structure is:

1. Compute the row maximum $m$ using the row-wise reduction pattern described above.

2. Subtract $m$ from each element, exponentiate, and compute the row sum $s = \sum_j e^{x_j - m}$, again via parallel reduction.

3. Compute the final normalized outputs by dividing each exponentiated element by $s$ (or computing $x_i - m - \log s$ for log-softmax).

Because the same value $m$ is needed by all threads processing a row, it is often written to shared memory or a per-row output array between steps. When multiple warps process a row, the availability of $m$ typically requires an explicit synchronization (for example, writing $m$ into shared memory and calling __syncthreads()), or using a two-kernel approach where the first kernel writes the row maxima into global memory and the second kernel reads maxima and finishes the exponentiation and normalization. A two-kernel approach increases global memory traffic but can simplify synchronization and increase modularity.

The log-sum-exp variant is especially important for loss computation in classification and for numerical stability during training with mixed precision. When using FP16 inputs with FP32 accumulation, subtracting the row max and using FP32 accumulation for the exponentials and sum gives much better stability than pure FP16 arithmetic.

It is also useful to consider the range after subtraction: if $x_j - m$ is less than some negative threshold (e.g., less than -20 in FP32), then $e^{x_j - m}$ is tiny and contributes negligible mass to the sum. Implementations can exploit this by clamping or skipping very small exponentials for speed, at small accuracy cost—this is more relevant in approximate or sparse-softmax contexts.

# Efficient evaluation of exponentials and special function unit constraints

The exponential function $e^x$ is not a single-cycle operation on GPUs. GPU architectures typically include specialized functional units (SFUs) capable of evaluating transcendental functions like exponentials, logarithms, reciprocal square roots, and trigonometric functions. However, SFU capacity per multiprocessor is finite; issuing many exponential instructions can saturate SFUs and limit throughput.

Hardware SFUs often support a small number of operations per cycle; solicitations beyond that must wait, effectively serializing some fraction of the work. Moreover, in older or lower-power GPUs, SFU throughput can be a major bottleneck if every thread issues exponentials. Therefore, software strategies aim to reduce the number of exponentials computed, amortize SFU usage, or replace expensive exponentials with approximations that use cheaper arithmetic and produce acceptable error.

Another constraint is that SFU implementations typically have specific latency and throughput characteristics. Latency could be in the range of tens of cycles; warp scheduling hides latency by switching to other warps, but if the kernel has insufficient parallelism (insufficient active warps) or memory-bound behavior, SFU latency becomes a limiting factor. Architectures with Tensor Cores or matrix instructions might rely less on SFUs for some workloads, but softmax is inherently elementwise plus reductions and does not map directly to matrix multiply units.

Given SFU constraints, practical implementations take a few approaches:

- Reduce the number of exponentials: compute exponentials only when needed, e.g., avoid exponentiating very small values that will underflow to zero, or use a threshold below which you treat $e^{x} \approx 0$.

- Use vectorized or fused kernels: fusing the subtraction, exponentiation, and multiply-adds reduces global memory traffic and allows better instruction overlap. Since each thread performs multiple operations per loaded element, the relative cost of exponents is amortized.

- Use approximate exponentials implemented as sequences of arithmetic operations (polynomials, rational approximations, or table lookup + interpolation), which can be executed on integer and FP units rather than SFUs. These approximations must be chosen carefully to trade off accuracy and the number of FP operations.

- Leverage hardware intrinsics where available: some GPU programming models expose fast approximate exponent or exp2 intrinsics (e.g., __expf in CUDA returns a faster, sometimes lower-precision exponential). Know your environment and test numerical errors for your application.

It is also important to consider mixed precision: computing $e^{x}$ in FP32 while inputs are FP16 reduces exponent inaccuracy relative to FP16 exponent evaluation. Often, exponentiation is the dominating cost; replacing $e^x$ with an approximation reduces the pressure on SFUs and reduces instruction scheduling constraints. But approximations incur error and may require compensated accumulation in the sum to avoid bias.

# Approximation methods for exponentials and trade-offs

Approximating the exponential function trades accuracy for performance. Several classes of approximations are commonly used in GPU softmax kernels: polynomial approximations (like Taylor or minimax polynomials), rational approximations (Padé approximants), table lookup with interpolation, and bit-manipulation tricks exploiting floating-point representations.

Polynomial approximations approximate $e^x$ over a limited interval with a polynomial
\[
e^x \approx \sum_{k=0}^p a_k x^k.
\]
Chebyshev or minimax polynomials minimize maximum error on the interval and often need fewer terms for a given error bound than simple Taylor series. The advantage is using only multiply-add operations, which GPUs can perform quickly. The downside is that the approximation interval is finite; you must first reduce the argument to a small interval (range reduction) and then apply the polynomial. Range reduction typically uses the identity $e^x = 2^{x/\ln 2} = 2^n \cdot e^r$ where $x/\ln 2 = n + r$ and $r\in[-1/2,1/2]$, so $n$ is an integer and $r$ is small. Computing $2^n$ is cheap if you can manipulate floating-point exponents or use fast integer shifts, but careful handling is needed to avoid rounding errors.

Rational approximations use a ratio of polynomials:
\[
e^x \approx \frac{p(x)}{q(x)}.
\]
Rational approximations can achieve high accuracy with lower degree polynomials than pure polynomials, but they require division which is relatively expensive on GPUs. However, one can compute reciprocal via fast reciprocal approximations plus Newton iterations to improve accuracy; this often remains faster than SFU exponentials for well-chosen degrees.

Table lookup plus interpolation partitions the domain into small intervals, stores precomputed values (and perhaps derivatives) in a table, and interpolates. This is attractive when the table can fit in shared memory or registers and when the same table entries are reused by many threads. The cost is memory for the table and potential shared memory conflicts. For softmax, where the distribution of inputs may concentrate around certain ranges, adaptive tables can be effective.

Bit-manipulation tricks use the floating-point representation directly. For single-precision floats, a fast approximation to $2^x$ or $e^x$ can be achieved by constructing a float from an integer exponent and fractional part using the IEEE 754 layout; this yields a crude approximation and is often combined with one or two Newton or polynomial refinements. These tricks are very fast but can be lower precision and must be validated for a given tolerance.

Each approximation has trade-offs:

- Accuracy vs. Cost: Higher accuracy requires higher polynomial degree, more table entries, or extra refinement iterations, increasing instruction count or memory usage.

- Branching and divergence: Some approximations use conditional code (e.g., special handling for large negative arguments). Branch divergence across threads in a warp reduces efficiency; it is preferable to use branchless approximations or to structure code to minimize divergence.

- Range reduction cost: The overhead of reducing the argument to a suitable interval and reconstructing the scale factor must be accounted for. For example, computing $n = \operatorname{round}(x / \ln 2)$ involves a multiply and convert-to-int operation.

- Accumulated error in softmax: Because softmax is normalized, multiplicative scaling errors in exponent approximations can partially cancel if applied uniformly, but additive errors in the exponent domain can bias probabilities. When approximations are used in both numerator and denominator, relative error patterns matter. It's common to verify that any approximation yields small relative errors in the computed softmax probabilities; sometimes an approximation is acceptable for forward pass but not for backward pass gradients, so separate strategies may be used (higher precision for backward).

- Determinism and reproducibility: Approximate exponentials may be non-deterministic across devices or compiler versions if they rely on hardware-specific intrinsics, which can be a concern for debugging or testing.

In practice, a common pattern is to use a low-degree minimax polynomial for $e^x$ on a small interval combined with an efficient range reduction that uses fast integer operations for scaling. An alternative is to use the hardware intrinsic for exponent when high accuracy is needed or when SFU is not the bottleneck; modern GPUs often have improved transcendental throughput.

When choosing an approximation, profile the kernel: if SFU throughput is the bottleneck and acceptable accuracy permits an approximation, replace $e^x$ with an approximation. Otherwise, use hardware exponentials. Benchmark across representative inputs to ensure correctness in the intended application.

# Minimizing memory traffic when computing softmax (local reductions)

Memory bandwidth is often the primary limiter of GPU kernels. Softmax involves reading the input matrix, writing a few per-row scalars (like the max and sum), and writing the normalized outputs. If done naively, this can result in multiple passes over global memory: one pass to compute maxima, a second to compute exponentials and sums, and a third to write the outputs. Minimizing memory traffic by performing as much as possible in registers and shared memory reduces global loads/stores and increases arithmetic intensity.

Key strategies to reduce memory traffic include:

- Fused kernels: Combine the compute stages (max reduction, exponentiation, sum reduction, final normalization) into a single kernel. This avoids writing intermediate scalars to global memory between steps if all cooperating threads reside in the same block and can exchange data via shared memory or registers. Fusing reduces kernel launch overhead and global memory traffic, at the cost of potentially larger kernel complexity.

- Local reductions and streaming: Each thread reads multiple elements into registers and computes local maxima and partial sums before performing inter-thread reductions. By keeping as much state in registers as possible, you avoid reloading elements from global memory. For example, a thread may load a contiguous chunk of 8 or 16 elements, compute their local max in registers, then participate in warp-level reduction to compute the row max. Later, it reuses the same register values to compute exponentials (after loading $m$ into a register) or may have to reload values if registers were spilled. Therefore, balance the number of elements per thread against register pressure.

- Using shared memory to stage blocks of rows: When multiple warps in a block process the same row or neighboring rows, loading a tile of the input into shared memory enables multiple threads to reuse the data without extra global loads. This tiling is particularly effective when computing softmax over the columns and subsequent layers will reuse the same data.

- Two-phase reductions with partial sums stored in shared memory: In multiple-warp-per-row scenarios, each warp computes a warp-local sum and writes it to shared memory. A single warp then reduces the shared-memory array to produce the total sum. Because writes to shared memory are much cheaper than global memory, this pattern saves bandwidth.

- Avoiding unnecessary writes: If softmax outputs are immediately consumed by another fused layer (e.g., a matrix multiply for attention), fuse that layer to consume exponentiated elements directly from registers without writing them back to global memory. This producer-consumer fusion eliminates writes of intermediate arrays.

- Memory access patterns and coalescing: Structure threads so that global memory accesses are coalesced. For row-major layout and one warp per row, consecutive threads load consecutive columns for a single row, leading to coalesced accesses. If the matrix is stored transposed or the mapping is different, adjust the kernel mapping to keep coalesced loads.

An example of a feasible fused single-pass softmax kernel for moderate row sizes follows this flow. Each thread loads a contiguous chunk of elements into registers, reduces to compute a local max, and then participates in a warp-level reduction to obtain the row max $m$. Without returning to global memory, each thread computes exponentials of its locally held elements shifted by $m$, accumulates a local sum, and participates in a warp-level reduction to compute the row sum $s$. Finally, each thread normalizes its locally held exponentials by dividing by $s$ and writes the normalized outputs back to the output array. This entire sequence reads each input value exactly once and writes each output value exactly once, minimizing global memory traffic.

However, some constraints can prevent a fully fused single-kernel approach: if a row spans multiple blocks, or if the grid configuration maps one block per row but the number of rows exceeds the number of SMs leading to diverse scheduling, you might need a multi-kernel approach, in which case write-back of intermediate scalars (like maxima) to global memory is unavoidable. Even then, minimize the amount written: write only one scalar per row for the max and one scalar for the log-sum-exp if necessary.

Finally, consider precision and storage format: using FP16 halves memory traffic compared to FP32, but exponentiation in FP16 has smaller dynamic range; often compute in FP32 accumulation while loading/storing in FP16 to get the best trade-off between memory bandwidth and numerical stability—this is the mixed-precision approach commonly used in modern frameworks.

# Putting it together: an example design and practical guidelines

Combining the preceding ideas yields practical designs for different row lengths and GPU characteristics.

For short rows (N <= warp size): pack multiple rows per warp so that each warp still has enough work. Use warp-level reductions exclusively (shuffle instructions) to avoid shared memory. Keep everything in registers: load element(s), compute local max, compute warp max, subtract, exponentiate with an approximate or hardware exponential depending on SFU load, compute warp sum, normalize, and write outputs.

For medium rows (warp size < N <= several thousand): one warp or multiple warps per row works. Use warp-level reductions for local chunks and a block-level reduction for warps across the row. Fuse the entire softmax into one kernel to avoid multiple passes. Use FP32 accumulation for exponentials even when inputs are FP16. Use an efficient polynomial approximation for $e^x$ if SFU is a bottleneck and accuracy allows it. Use shared memory to store warp partial sums, but avoid frequent global memory writes.

For very long rows (N very large): split rows into tiles processed by blocks or multiple kernel launches. Each tile produces partial sums and partial maxima; combine tile results in a second stage. You may have to write intermediate tile maxima to global memory, then launch a small kernel to reduce them and broadcast the results. To minimize memory traffic, combine this with tiling so each tile reads its portion once and writes only its normalized outputs.

Practical code-level guidelines:

- Favor warp shuffles for intra-warp reductions; they are faster and avoid shared memory bank conflicts.

- Keep register pressure reasonable: holding too many elements per thread may cause register spilling, which hits local memory (global memory) and defeats the optimization.

- Measure the SFU throughput: profile with representative inputs to determine whether exponentials are the bottleneck; if so, evaluate approximate exponentials.

- Use fused kernels where possible: when softmax is immediately followed by another operation (attention dot-product), fuse them to reduce memory traffic.

- Use mixed precision wisely: compute critical reductions (max, sum) in FP32 even if inputs are FP16, and convert outputs back if needed.

- Test numerically: verify that approximation and precision choices do not degrade training or inference behavior unacceptably. Check both forward outputs and backward gradients if training.

- Consider caching per-row constants and broadcasting them efficiently: store row maxima and log-sum-exp values in shared memory or registers for fast access by threads in the row.

By understanding the structure of softmax, the hardware limits (SFU and memory bandwidth), and the available primitives (warp shuffles, shared memory, fast arithmetic), you can design kernels that compute softmax both quickly and stably. The appropriate choices depend on row length, desired accuracy, and the particular GPU generation. Implementations in major libraries represent years of engineering to balance these trade-offs; use them as references, but knowing these principles allows customizing softmax for new architectures or application-specific constraints.

# Introduction

Modern machine learning workloads, particularly large-scale neural networks, are dominated by operations that move and transform large tensors. The latency and throughput of these workloads are often limited not by raw arithmetic throughput but by memory bandwidth and memory access patterns: reading and writing intermediate results to global device memory (for example, GPU DRAM) can dominate runtime and energy use. Kernel fusion, operator fusion, and memory elimination are families of techniques that combine multiple logical operators into a single, physically executable kernel that computes the same result while avoiding unnecessary intermediate global memory traffic.

This chapter explains the principles behind fusion, describes common staged fusion patterns, and examines the concrete example of fusing the sequence matmul → softmax → matmul that appears in scaled-dot-product attention. We develop the intuition for how fusion reduces memory bandwidth pressure, why it sometimes exposes new local-memory algorithms (such as block-level reductions) that make fused softmax possible, and what trade-offs arise in practice. The chapter concludes with a set of general examples of fused kernels found in ML workloads and guidance on where fusion is most beneficial.

# Principles of Operator Fusion and Staged Fusion Patterns

Operator fusion means combining two or more logical operators into a single implementation that executes without writing intermediate results to global memory. At a high level, there are two distinct but related goals: eliminating intermediate global reads/writes (memory elimination) and exposing data reuse opportunities between operators to keep data in fast on-chip storage (registers, shared/local memory). A fused kernel implements the composition of operators, so data produced by one logical operation can flow directly into the next without passing through DRAM.

There are a number of fusion strategies, ranging from simple sequential fusion to more sophisticated staged fusion patterns that pipeline computation and communication. The simplest approach is pointwise fusion: if operator $A$ produces a tensor $X$ and operator $B$ consumes $X$ elementwise (or with a simple local neighborhood), then a fused kernel computes both operations per element and writes only the final result to memory. For example, fusing an elementwise activation with a subsequent elementwise scaling avoids writing the activation output to DRAM. Pointwise fusion is cheap and widely used by compilers because it preserves simple data access patterns.

More interesting is staged fusion for non-pointwise operators, where operators have different data access shapes and data reuse patterns. In staged fusion, the computation is decomposed into stages that map onto the memory hierarchy: each stage reads needed inputs from global memory into on-chip buffers, performs local computation producing intermediate values stored in registers or shared memory, and then directly forwards those intermediates to the next stage within the same kernel. Staged fusion often uses a tiling or blocking decomposition: the kernel processes a tile of output elements at a time so that all intermediate data for that tile can remain on-chip. The classic example is fusing a matrix multiplication followed by a batched pointwise operation: the matmul computes sub-blocks of the product into local buffers; the pointwise stage applies the operation to the sub-block and writes the final values back.

An important aspect of staged fusion is the staging sequence and synchronization model. Within a single kernel, you can have sequential stages without global synchronization: threads in a block or workgroup cooperate through shared memory or registers. If the next stage requires that all threads across the device finish the previous stage before beginning, fusion is impossible without adding synchronization points (which GPUs do not provide globally inside a single kernel). Therefore, staged fusion is typically applied at the granularity that fits the programming model: within thread blocks/wavefronts or within streams of data that can be processed in a pipelined manner. Pipelined staged fusion can also interleave computation and communication: some hardware allows a producer to stream data to the consumer within the same kernel using asynchronous copies or direct memory access to shared buffers.

Compiler frameworks implement fusion by analyzing the computation graph and discovering producer-consumer relationships, data shapes, and aliasing constraints. A key condition for fusion is that the fused code must preserve semantics, including floating-point associativity and numerical precision boundaries. When these constraints hold, compilers generate fused kernels by composing loop nests, adjusting iteration orders, and inserting local buffering.

# Benefits of Fusing Matmul + Softmax + Matmul in Attention

Attention mechanisms, particularly the scaled-dot-product attention used in transformers, naturally form a chain of three heavy operators: a matrix multiplication to compute raw attention scores, a softmax over each row (or sequence position) of those scores, and another matrix multiplication to compute the weighted sum of values. Concretely, given query matrix $Q \in \mathbb{R}^{N\times d}$, key matrix $K \in \mathbb{R}^{M\times d}$, and value matrix $V \in \mathbb{R}^{M\times d_v}$, the attention output $O$ is computed as

$S = Q K^\top / \sqrt{d},$
$\text{P} = \operatorname{softmax}(S)$ (applied row-wise),
$O = \text{P} V.$

Naively implementing this sequence as three kernels writes $S$ to global memory, reads it back to compute $\text{P}$, writes $\text{P}$ out, and then reads $\text{P}$ to compute $O$. The intermediate tensors $S$ and $\text{P}$ are large (size $N\times M$), so the memory bandwidth and capacity pressure can be huge, especially for long sequences. Fusing all three operators avoids these global memory round-trips.

The primary benefit is memory-bandwidth reduction. Consider the amount of global memory traffic in the unfused baseline: computing $S$ touches $Q$ and $K$ to form $S$, writing $S$ out consumes $2|S|$ bytes (write) plus subsequent read $|S|$ for softmax (assuming single-precision, but counting symbolically in units of tensor elements). After softmax, writing $\text{P}$ and later reading it for $O$ adds more traffic. In a fully fused kernel, each element of $S$ is computed, used immediately in the softmax computation, and then the resulting normalized probability is multiplied by the corresponding $V$ row contribution, all while $S$ and $\text{P}$ are stored in registers or shared memory and never spilled to global memory. Hence the global memory cost is reduced to roughly just reading $Q$, $K$, and $V$ once and writing $O$ once, plus some small overheads for sharing tiles of $K$ and $V$ in fast on-chip memory.

Beyond pure bandwidth savings, fused matmul-softmax-matmul enables algorithmic transformations that are not possible when operators are separated by global accesses. For example, stability tricks for softmax and certain blocking strategies require access to the entire row of $S$ or to compute per-row maxima. When $S$ is held locally for a tile, we can compute the row maximum, subtract it, exponentiate, sum, normalize, and then immediately accumulate into $O$ without ever materializing full $S$. This permits the common numerically-stable softmax implementation that first subtracts the row maximum:

$\text{P}_{ij} = \frac{\exp(S_{ij} - \max_k S_{ik})}{\sum_k \exp(S_{ik} - \max_k S_{ik})}.$

Fusing lets this multi-pass computation happen with data resident on-chip across the passes.

The attention case also benefits from reduced latency and improved caching locality. When $K$ and $V$ are large, bringing relevant tiles of $K$ and $V$ into shared memory once and reusing them across multiple queries reduces the global memory footprint and increases arithmetic intensity. On GPUs, where memory hierarchy favors reusing on-chip data, these locality gains translate into substantial speedups.

Finally, fusing can reduce peak device memory usage. Inverse memory pressure is crucial when training or running large models; eliminating the need to allocate buffers for intermediates like $S$ and $\text{P}$ allows fitting larger batch sizes or sequence lengths under the same memory budget. This is one of the practical reasons fused attention kernels are common in high-performance transformer libraries.

# Trade-offs: Code Complexity, Register Pressure, and Compiler Effects

While fusion delivers tangible benefits, it also introduces trade-offs that must be carefully managed. The first and most visible one is code complexity. A fused kernel must implement the combined semantics of multiple operators including their edge cases, numerically stable variations, broadcasting semantics, and maybe backward passes (for training). This complexity increases development and maintenance burden. Moreover, fused kernels are frequently hand-optimized for a specific hardware's memory hierarchy and threading model; this reduces portability and makes changes (e.g., supporting a new datatype or a variant of softmax) more expensive.

A second trade-off is register pressure. Registers are the fastest storage but are a limited resource per thread. Fusing operations tends to increase the number of live variables simultaneously required within a thread or threadblock: intermediate accumulators from a matmul, temporary exponentials and sums for softmax, and partial reductions for the final matmul must all coexist. If the compiler assigns more registers per thread than the hardware prefers, it reduces occupancy — the number of concurrent warps or threads that can be resident — which can reduce throughput even if arithmetic intensity is high. Thus a fused kernel can, paradoxically, run slower than separated kernels when register pressure forces lower occupancy or when spilled registers cause additional local memory accesses.

The effect of fusion on the compiler pipeline is another key trade-off. Automatic fusion by compilers (e.g., XLA, TVM, or vendor-specific kernels) must reason about loop transformations, memory layouts, and constraints like aliasing and atomicity. Aggressive fusion can inhibit later compiler optimizations: for example, fusing two loops with incompatible access patterns may preclude vectorization, loop unrolling, or SIMD-friendly reorderings. Conversely, well-planned fusion can expose opportunities for vectorization or instruction-level parallelism by presenting larger contiguous computations to the backend.

Another compiler-related issue is numerical behavior. Floating-point arithmetic is not associative, so changing loop ordering or grouping operations (e.g., combining reductions) can produce different results. For most ML training/inference tasks the small numerical differences are acceptable, but for some workloads reproducibility or strict numerical properties are required. Therefore, some frameworks restrict fusion to operations where semantics remain within acceptable bounds.

There are also debugging and profiling difficulties. Fused kernels obfuscate the correspondence between high-level operators and low-level code, making it harder to attribute performance bottlenecks or correctness issues to a specific stage. Profilers and hardware counters may attribute stalls to the fused kernel as a whole, complicating tuning. Additionally, fused kernels tend to be more brittle under microarchitectural changes: a small change in tensor shapes can change tiling choices, register allocation, or control flow, and this may break performance assumptions.

Finally, hardware limitations impose constraints. GPUs, TPUs, and other accelerators differ in the sizes and latencies of their local storage, the cost of synchronization, and how efficiently they can implement certain patterns (e.g., warp-shuffles vs. shared memory). A fusion strategy tuned for one architecture may be suboptimal on another. Thus while fusion is a powerful tool, its benefits must be balanced against these practical concerns.

# Local (Block) Reductions Enabling Fused Softmax

A critical ingredient for fusing softmax with matmuls is the ability to compute reductions locally within thread blocks without materializing full intermediate matrices. Softmax requires two kinds of row-wise reductions: the maximum per row (for numerical stability) and the sum of exponentials per row (for normalization). In classical implementations, these reductions are computed over an entire row that may be too large to fit in registers of a single thread, but they can be computed in a tiled, hierarchical manner.

The typical approach is block-wise reduction with two passes localized to a tile. Consider processing a tile of the attention score matrix $S$ corresponding to a subset of rows and columns. Each thread block is assigned to a tile covering rows $i \in R$ and columns $j \in C$. Within the block, threads compute partial products $S_{ij} = \sum_{k} Q_{ik} K_{jk}$ for the columns $j \in C$. The block performs an intra-block reduction to compute the partial maxima over $j \in C$ for each row $i \in R$; these partial maxima are stored in shared memory or registers. Across all column tiles covering full range of $j$, the final row maximum $\max_j S_{ij}$ can be obtained by reducing the partial maxima produced by each tile sequentially.

This outlines a multi-pass strategy: the kernel iterates over column tiles consecutively. When processing a new column tile, the block first computes partial scores for that tile, updates the running maximum for each row, then computes exponentials shifted by the current running maximum. However, because the true global maximum for row $i$ may come from a later tile, one must be careful to maintain correct numerical normalization. A numerically stable incremental aggregation method for exponentials and maxima is to use the log-sum-exp identity combined with pairwise composition. Given a running maximum $m$ and a running sum of exponentials $s = \sum_j \exp(S_{ij} - m)$ for processed columns, and given a new partial maximum $m' = \max_{j\in C'} S_{ij}$ and sum $s' = \sum_{j\in C'} \exp(S_{ij} - m')$ for the new tile, one can combine them as:

$m_{\text{new}} = \max(m, m')$,
$s_{\text{new}} = s \cdot \exp(m - m_{\text{new}}) + s' \cdot \exp(m' - m_{\text{new}})$.

This two-variable reduction (maximum and scaled sum) can be kept in registers for each row within a block and updated tile-by-tile. It avoids having to store the raw $S$ entries for the whole row. After all tiles have been processed, $s_{\text{new}}$ holds the correct denominator and $m_{\text{new}}$ the correct offset, so one can normalize exponentials computed earlier or, better, recompute exponentials for final normalization as needed but often you can do a two-pass approach: in the first pass accumulate $m$ and scaled $s$, and in a second pass compute normalized weights by reprocessing tiles and generating $\exp(S_{ij} - m_{\text{final}}) / s_{\text{final}}$ on the fly. The important point is that both passes operate on tiles that fit in shared memory or registers, so no full-row storage is required.

An even more efficient approach fuses the final accumulation into $O$ by updating the output while reprocessing tiles: once $m_{\text{final}}$ and $s_{\text{final}}$ are known (after the first pass), the kernel replays the tiles, recomputes the normalized probabilities for the tile, and immediately multiplies by the corresponding $V$ tile and accumulates into the output buffer in registers or shared memory. This two-pass tile-iterative pattern computes the same result as computing all of $S$ explicitly but only touches global memory for $Q$, $K$, $V$, and $O$. The transient $S$ and $P$ live in fast on-chip storage or are recomputed as needed.

Block reductions rely on efficient intra-block communication primitives. GPUs provide thread synchronization within a block and fast shared memory that allows threads to cooperate. Many architectures also have warp-level shuffles or specialized instructions for reductions. Efficient fused implementations carefully map rows to threads so that each thread maintains per-row state (e.g., $m$ and $s$) and uses vectorized loads and stores for K/V tiles. They also use loop unrolling and prefetching to hide latency. The key idea is that the row-wise reductions required by softmax can be implemented incrementally and locally, enabling softmax to be fused into a larger kernel that computes attention.

# Examples of Fused Kernels in ML Workloads (General Patterns)

Fused kernels appear across a wide range of ML workloads. Below are general patterns and representative examples to build intuition for how fusion is applied in practice.

One common pattern is matmul + elementwise activation + dropout. In training, you often compute $Y = \operatorname{dropout}(\phi(XW + b))$ where $\phi$ is an activation like GELU or ReLU. Fusing the bias-add, activation, and dropout into the matmul kernel avoids writing the intermediate $XW + b$ and reduces global memory traffic. Additionally, fusion enables computing the dropout mask on-the-fly and applying it directly to the activation outputs before writing the final tensor, also simplifying or eliminating separate RNG kernel launches for masks.

Another pattern is batch normalization fused with convolution. Convolution produces per-channel statistics which batchnorm then normalizes and scales. A fused convolution + batchnorm kernel computes the conv outputs per output channel and immediately applies the normalization using the running mean and variance and learned scale and offset, writing only the normalized outputs. Training variants often require computing mean/variance across batches, so a fused kernel may perform local accumulation for these statistics and then update the global statistics via a reduction step. The benefit is both memory elimination and fewer synchronization points.

Layer normalization fused with preceding affine transforms or residual addition is also common. Layernorm computes per-sample mean and variance over channels; fusing it with the preceding linear transform avoids an extra write-out of the intermediate activation. For inference-only settings, fused implementations often precompute scale and bias to minimize per-sample computation.

The transformer attention fusion (matmul + softmax + matmul) we covered earlier is the most prominent example, but there are variants: multi-head attention fuses these operations across heads or uses shared K/V tiles across head groups to amortize memory cost. Some implement a single-kernel multi-head attention where multiple heads share tiles of K and V that fit in shared memory.

Gradient computations during training also benefit from fusion. For example, the backward pass of attention involves matmuls and elementwise operations whose consumer-producer relationships mirror the forward pass. Fusing parts of the backward computation reduces DRAM traffic for large intermediates (like gradients w.r.t. softmax inputs), and fused backward kernels are a crucial optimization in training runtimes.

Reduction + broadcast fusion is another pattern seen in loss computations. For example, computing cross-entropy loss often requires taking a log-softmax followed by a gather and reduction to a scalar. A fused kernel can compute log-softmax row-wise, multiply by target one-hot, and reduce per-sample losses in a tiled way, avoiding storing the full log-probabilities.

Sequence models often benefit from fusing recurrent updates: in an LSTM cell, the linear combinations that produce gates followed by nonlinearities and pointwise multiplies can be fused into a single kernel that computes the inputs, applies sigmoid/tanh, and computes the cell update and hidden state, writing only the final hidden states. This reduces both memory and kernel-launch overhead.

Finally, there are cross-operator fusions that exploit algebraic identities. For instance, combining a matmul and a following scale-and-add (i.e., fused multiply-accumulate with residual connection) is common: compute $Y = \alpha(XW) + \beta Z$ within one kernel. This pattern reduces memory traffic for both $XW$ and $Y$ and can improve precision by performing accumulations coherently.

Across all these examples, the recurring theme is identifying producer-consumer chains where the producer's output is either transient or can be recomputed cheaply and structuring the fused kernel to keep intermediates on-chip. Practical fused kernels use tiling, double-buffering, and local reductions to manage the memory hierarchy. They also carefully balance register usage and occupancy, often exposing tuning knobs for tile size and vector width to trade off between on-chip storage, instruction-level parallelism, and cache behavior.

# Conclusion

Kernel and operator fusion are powerful techniques to reduce memory traffic, improve locality, and increase the effective arithmetic intensity of ML workloads. Staged fusion patterns — especially when leveraging tiling and block-local reductions — make it possible to fuse complex operator sequences like matmul → softmax → matmul in attention, eliminating large intermediate tensors and improving runtime and memory efficiency. However, fusion introduces practical trade-offs: increased code complexity, register pressure, compiler interactions, and potential numerical differences. Effective fusion balances these concerns through careful algorithm design, hardware-aware implementation, and sometimes selective fusion controlled by performance modeling or autotuning. Understanding these principles allows a practitioner to read and reason about high-performance ML kernels and to design kernels that extract maximum performance from modern accelerators.

Measuring and understanding the performance of GPU kernels is essential for designing high-performance code, comparing different algorithms, and interpreting results in research. GPUs are highly parallel processors whose performance depends on a complex interplay of arithmetic throughput, memory subsystem behavior, instruction-level efficiency, and software-level choices such as blocking, data layout, and kernel launch configuration. This chapter presents a practical and principled approach to quantifying GPU performance. We begin by defining how to count operations and express throughput in TFLOPs, then move to utilization metrics that relate achieved performance to hardware peaks. After that we discuss how to design benchmarks and parameter sweeps (batch size, sequence length, attention head dimension) so comparisons are fair and informative. We present the main profiling tools available for NVIDIA and other vendors, explain which hardware counters and measurements matter, and conclude with methods for ablation studies and controlled experiments that isolate cause and effect. Throughout the chapter we emphasize intuition and reproducible experimental design so that results are both accurate and meaningful.

# Measuring throughput: TFLOPs and the counting of operations

When people say a kernel achieves "X TFLOPs", they are reporting the rate at which floating-point operations were executed, converted into trillions of floating-point operations per second. TFLOPs is a common shorthand for raw arithmetic throughput, but careful interpretation requires two steps: (1) accurately counting the number of floating-point operations performed by the kernel, and (2) dividing that count by the measured execution time.

Counting operations requires a clear definition of what you consider to be a floating-point operation. Typically, each fused multiply-add (FMA) is counted as two floating-point operations because it performs one multiply and one add. Some vendors' peak FLOPs specifications already count FMA as two operations; therefore use the same convention when comparing against peak. For example, if your kernel executes $N_{\text{FMA}}$ FMA instructions and $N_{\text{other}}$ other floating-point operations (adds, multiplies, divides, etc.), then a common FLOP count is
\[
\text{FLOPs} = 2\cdot N_{\text{FMA}} + N_{\text{other}}.
\]
It is important to be explicit about this convention in any report.

How do we obtain $N_{\text{FMA}}$ and $N_{\text{other}}$? There are several approaches: (a) analyze the arithmetic in the algorithm and compute counts symbolically, (b) examine the compiled assembly or intermediate representation to count issued FP instructions, or (c) use vendor tools that estimate FLOP counts based on kernel instrumentation. The most robust approach for research is to perform analytical counting from the algorithm and then validate with profiling. For example, consider a dense matrix-matrix multiply of dimensions $M\times K$ times $K\times N$. Each output element is
\[
C_{i,j} = \sum_{k=1}^K A_{i,k} \cdot B_{k,j},
\]
which requires $K$ multiplies and $K-1$ adds, often implemented with FMA to yield $K$ FMA operations per output (i.e., $2K$ FLOPs under the FMA-as-two convention). Therefore the total FLOP count is
\[
\text{FLOPs}(GEMM) = 2 M N K.
\]
For more complex kernels (convolutions, attention, layer norm, activation functions), list the arithmetic per output and multiply by the number of outputs.

Once you have a FLOP count, measure the elapsed time $T$ for the kernel under realistic conditions (warm-up iterations to avoid first-call overhead, correct input sizes, pinned memory when necessary), and compute
\[
\text{TFLOPs} = \frac{\text{FLOPs}}{10^{12} \cdot T}.
\]
Be cautious about measuring time: use precise GPU timers (events on CUDA with cudaEventRecord + cudaEventElapsedTime, or profilers that report device time) rather than host wall-clock time if kernels are asynchronous.

Counting alone is not sufficient to judge efficiency. Often the arithmetic count assumes ideal use of FMAs while actual kernel execution may include non-FMA operations, type conversions, or predicated instructions (masked execution) that reduce effective FLOP throughput. Similarly, kernels that rely heavily on mathematical library functions (e.g., transcendental functions) will have different instruction mixes and latency characteristics. Always document the instruction mix and validate your analytical FLOP count against low-level instruction traces or profiler-reported operation counts where possible.

# Utilization metrics: achieved vs theoretical peak

A natural question after measuring TFLOPs is: how close is that to the hardware's theoretical maximum? Utilization metrics express achieved performance as a fraction of theoretical peak throughput or bandwidth. They help locate bottlenecks: if arithmetic utilization is low but memory bandwidth usage is small, then some other inefficiency (divergence, serialization, scheduling, register pressure) may be involved.

The first baseline is the theoretical peak FP throughput. For an NVIDIA GPU, the vendor publishes peak arithmetic rates per precision (FP32, FP16, BF16, TF32, FP64) in terms of operations per second assuming all execution units are kept busy with FMAs. For example, if the peak is $P_{\text{peak}}$ FLOPs/s in your precision and your kernel achieves $P_{\text{achieved}} = \text{FLOPs} / T$, arithmetic utilization is
\[
U_{\text{arith}} = \frac{P_{\text{achieved}}}{P_{\text{peak}}}.
\]
Interpret this number carefully. A low $U_{\text{arith}}$ might reflect a kernel that is memory-bound rather than compute-bound. To decide which bottleneck dominates, compare arithmetic intensity to the machine balance using the roofline model.

The roofline model links arithmetic intensity (AI) to achievable performance. Arithmetic intensity is defined as
\[
\text{AI} = \frac{\text{FLOPs}}{\text{bytes transferred}},
\]
where "bytes transferred" should reflect data movement that limits performance, often measured as bytes read/written from global memory. Given a memory bandwidth limit $B_{\text{mem}}$ (bytes/s), the memory-bound performance ceiling is $B_{\text{mem}} \cdot \text{AI}$. The roofline plot places AI on the horizontal axis and achievable performance on the vertical axis; the roofline itself is the minimum of the compute peak line and the memory-bound line. A kernel lies on or below the roofline; if a kernel's achieved performance lies close to $B_{\text{mem}} \cdot \text{AI}$, it is memory-bound. If it is significantly below both the memory and compute roofs, the kernel may be limited by latency, instruction mix, thread-level inefficiencies, or other microarchitectural effects.

Beyond arithmetic utilization, other utilization metrics are important:
- Memory bandwidth utilization: the fraction of peak global memory bandwidth used by the kernel. Use profiler counters or microbenchmarks to obtain $B_{\text{achieved}}$ and compute $U_{\text{mem}} = B_{\text{achieved}} / B_{\text{peak}}$.
- SM (streaming multiprocessor) occupancy: the fraction of maximum active warps or threads resident on each SM. Occupancy is a measure of how many warps are available for latency hiding. Low occupancy can reduce the ability to overlap memory latency, but occupancy is neither necessary nor sufficient for high performance—well-tuned kernels may achieve high throughput at modest occupancy by maximizing instruction-level parallelism and register reuse.
- Active warps per SM and warp schedulers utilization: hardware counters report average active warps or warp stalls; these indicate under-utilization from divergence or serialization.
- Achieved instructions per cycle (IPC) and delivered memory transactions per cycle: comparing IPC to a reference maximum IPC suggests instruction pipeline utilization.

When reporting utilization, include the measured hardware peak assumptions: was tensor core usage counted at FMA-with-fused-accumulate rate? Are specialized units (tensor cores, FP16 pipelines) included? For mixed-precision or tensor-core kernels, the theoretical peak arithmetic rate often exceeds standard FP32 peaks; ensure the FLOP counting convention matches that peak.

In addition to raw ratios, provide multiple complementary metrics together: TFLOPs, memory bandwidth usage, arithmetic intensity, occupancy, IPC, and relevant latency or stall counters. This combined view helps identify whether you should optimize memory accesses, tile sizes, data movement, or arithmetic scheduling.

# Benchmark design: varying batch, sequence length, and head dim

Designing benchmarks for GPU workloads requires covering the range of problem sizes and parameter regimes that matter in practice. For deep learning and transformer-like workloads, key parameters include batch size, sequence length, and attention head dimension (head dim). These parameters strongly influence arithmetic intensity, memory access patterns, and kernel launch parallelism. A fair and informative benchmark systematically varies these parameters and reports their impact.

Batch size affects two things: the total amount of parallel work and the steady-state cost of kernel launches. Larger batches raise the total number of independent work-items (e.g., more matrix rows to process), increasing parallelism and often leading to better utilization of the GPU. Small batch sizes can leave many CUDA cores idle or cause kernels to be memory-latency-bound because there are not enough threads to hide latencies. When benchmarking, sweep batch sizes from small (e.g., 1, 2, 4) to large (e.g., 64, 128, 1024) depending on the application. Report both per-batch latency and throughput (examples/sec or tokens/sec) as both metrics matter: real-time inference cares about latency at small batch, while training commonly emphasizes throughput at large batch.

Sequence length (e.g., the number of tokens in transformers) changes the size of intermediate matrices in attention and affects both compute and memory. For attention, complexity often scales as $O(L^2)$ memory and computation per layer when computing full attention over a sequence of length $L$. Short sequences may allow efficient blocking and increased cache reuse; very long sequences change the working set so that memory bandwidth and capacity become limiting. When reporting results for transformer kernels, sweep sequence lengths that reflect realistic workloads (e.g., 16, 64, 128, 512, 2048) and show where performance drops or transitions between compute-bound and memory-bound regimes.

Head dimension is the size $d$ of each attention head; attention uses matrices of shape $L \times d$ and the per-head compute often scales with $d$. Small head dimensions may lead to underutilization of vector units and diminished ability to use tensor cores (which often prefer particular tile sizes and minimum operand shapes). Large head dimensions increase arithmetic intensity and often improve utilization but can raise register pressure and shared memory use in kernels, possibly increasing occupancy pressure or forcing spilling. Vary $d$ across powers of two and other common values (e.g., 32, 64, 128, 256) to see how kernel implementations handle preferred tile sizes.

Beyond sweeping single parameters independently, consider combined sweeps because interactions matter. For instance, small batch and large sequence might behave differently than large batch and small sequence in terms of tiling and cache reuse. Present performance as heatmaps or multiple plots that fix one parameter while varying two others, so readers can see interactions.

Other important benchmarking considerations:
- Warm-up iterations: discard the first few iterations to avoid including one-time setup costs (kernel compilation, memory allocation, caching).
- Multiple trials: report mean and standard deviation over several runs to indicate variability, especially important for latency-sensitive benchmarks.
- Synchronized timing: ensure kernel times are measured with device synchronization (e.g., cudaEvent) to avoid host-device asynchronous semantics obscuring true GPU time.
- Hardware and software configuration: report GPU model, driver version, CUDA toolkit, cuDNN/cuBLAS versions, clock rates (boost states), power limits, and thermal conditions. Subtle differences (power cap, ECC, GPU mode) can affect results materially.
- Avoid including data transfer time from host to device unless comparing full end-to-end systems; if you do include transfers, be explicit and report both on-GPU kernel time and end-to-end time.

Finally, when comparing two implementations, ensure both are compiled with equivalent optimization levels, use the same runtime (e.g., same CUDA version), and have identical numerical precision and algorithmic trade-offs. Differences in numerical choices (e.g., FP32 vs mixed precision) can change both performance and numerical results; report these details.

# Profiling tools (Nsight, nvprof, CUPTI, vendor tracers) and counters

Profiling is the essential bridge between observed performance and root causes. A variety of tools are available, providing different levels of visibility, overhead, and usability. On NVIDIA GPUs, popular options include NVIDIA Nsight Systems and Nsight Compute, the legacy nvprof (deprecated), and the low-level CUPTI (CUDA Performance Tools Interface) for custom instrumentation. Other vendors offer analogous tools (e.g., ROCm’s rocprof/roctracer, Intel VTune/oneAPI for discrete GPUs). This section surveys the tools and the critical counters to examine.

Nsight Systems provides system-wide tracing with low overhead suitable for end-to-end application profiles. It shows kernel launch timelines, CPU/GPU overlap, memory copies, and multi-process behavior. Use Nsight Systems to identify high-level inefficiencies: frequent small kernel launches, host-side stalls, synchronization overhead, or pipeline bubbles. The timeline view clarifies whether the GPU is idle between kernels due to host-side synchronization or kernel dependencies.

Nsight Compute is a kernel-level profiler that reports detailed device metrics and source/assembly inspection. It can show instruction statistics, achieved occupancy, memory throughput per cache level, stall reasons, and the distribution of instructions across types. Use Nsight Compute to inspect "hot" kernels at the instruction level and to obtain counters such as:
- sm__sass_thread_inst_executed_op_fadd_pred_on (or equivalent): number of FP add instructions executed.
- sm__sass_thread_inst_executed_op_fmul_pred_on: number of FP multiply instructions.
- sm__pipe_tensor_cycles_active: time tensor cores were active (for architectures supporting tensor cores).
- l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum: bytes read from global memory at L1 or texture cache level.
- dram__bytes.mean: total DRAM bytes transferred.
- sm__cycles_elapsed: elapsed cycles on an SM.
- sm__warps_active.avg.pct_of_peak_sustained_active: active warps percentage for occupancy insights.
These counters are vendor-specific and their names change across architectures and Nsight versions; the profiler UI usually offers human-readable abstractions (e.g., "Throughput", "Memory Workload", "SM Efficiency").

nvprof was the older command-line profiler that offered easy collection of many counters and trace outputs. Although deprecated, it is still used in some legacy contexts. CUPTI is the programmatic interface that underlies NVIDIA’s profilers; it allows you to subscribe to events, collect counters, and build custom tracers and tools. For research, CUPTI is valuable when you require automated data collection or need to capture a custom set of metrics across many runs.

Interpreting counters requires care. For example, global memory read/write bytes reported by the profiler might count cacheable accesses at multiple cache levels. Distinguish between L1, L2, and DRAM counters when reasoning about memory bandwidth. On modern GPUs, L1 cache and L2 cache behavior greatly affect performance; profiler-reported L2 hit rates and per-cacheline transfer sizes are often the key to understanding why a kernel is memory-bound.

Counters to prioritize:
- FLOP-related counters: number of FP operations executed, tensor core active cycles, integer operation counts (to identify conversion or index overhead).
- Memory counters: DRAM bytes read/written, L2 requests/hits, L1 transactions, cache hit/miss ratios.
- Occupancy/warp counters: active warps per SM, warp replays (due to divergent branches), warp execution efficiency.
- Pipeline and stall counters: memory dependency stalls, execution dependency stalls, structural hazards.
- Bandwidth and latency counters: average DRAM latency, achieved DRAM bandwidth.

A typical profiling workflow is:
1. Use Nsight Systems to find the top kernels and overall application behavior.
2. Use Nsight Compute on the hottest kernel(s) to collect detailed counters and source/assembly annotations.
3. If necessary, instrument code with CUDA events for custom timing or use CUPTI to capture counters programmatically for many runs.
4. Iterate by modifying kernels and re-profiling to validate improvements.

If you use other vendors' hardware, learn the equivalent tools and counters. ROCm tools provide similar metrics, but names and measurement semantics differ. Always corroborate profiler numbers with simple microbenchmarks: for example, verify reported memory bandwidth with a STREAM-like kernel or validate achieved FLOPs with a matrix multiply of known FLOP count.

# Ablation studies and controlled experiments

Ablation studies and controlled experiments are the scientific methodology for attributing observed performance differences to specific design choices. The goal is to change one factor at a time, measure the impact, and rule out confounding factors. Good ablations are reproducible, statistically powered, and targeted at key hypotheses.

Begin by formulating clear hypotheses: for example, "Using tile size 32 reduces global memory traffic and improves TFLOPs by 20% for head dim 64", or "enabling fp16 mixed precision with loss scaling maintains numerical fidelity while doubling arithmetic throughput". Each hypothesis should be testable with a controlled experiment.

Design your experiments to isolate the variable of interest. If comparing two kernel implementations, ensure they are identical except for the feature under test: same data layout, same numerical precision, identical input data, same GPU frequency/power settings, same compilation flags. When you change a single implementation detail (e.g., enabling shared-memory double buffering), measure before and after under identical conditions.

Use multiple repetitions to quantify variability. GPU runtimes can vary due to clock throttling, thermal effects, OS jitter, or background processes. For latency-sensitive measures, run each configuration for many iterations and report statistics: mean, median, standard deviation, and ideally confidence intervals. For throughput benchmarks, report sustained throughput over a long run rather than a single short measurement to avoid transient artifacts.

When an ablation yields a significant performance change, perform complementary measurements to explain why. If enabling a feature improves TFLOPs but increases DRAM traffic, then the improvement may come from increased locality or better instruction scheduling; inspect memory and instruction counters to verify. Use roofline reasoning: did arithmetic intensity change? Did bandwidth utilization change? Did occupancy increase? Presenting these correlated metrics strengthens the causal claim.

Factorial and sensitivity studies help when multiple parameters interact. A full factorial experiment sweeps all combinations of a small set of parameters (e.g., tile sizes A, B, C and prefetch counts X, Y) and reports interaction effects. For larger parameter spaces, use one-factor-at-a-time sweeps combined with occasional factorial points to detect interactions. Consider using response surface or design-of-experiments techniques if you have many parameters and want to build a predictive model of performance.

Document all environmental and experimental settings for reproducibility: GPU model, number of GPUs used, CUDA version, compiler flags, temperature/power constraints, and whether ECC is enabled. When reporting results, include baseline measurements (e.g., vendor library performance like cuBLAS/cuDNN) so readers can contextualize improvements.

Be wary of overfitting to a narrow benchmark. An optimization that benefits a single shape may harm others. Use parameter sweeps described earlier to demonstrate robustness. If an optimization requires special-case code paths for particular sizes, report both specialized and general-case performance and the frequency of those sizes in real workloads.

Finally, interpret ablation results conservatively. Correlation is not causation unless the experiment is well-controlled. If a change reduces performance variability, that is an important observation that may indicate mitigation of a non-deterministic bottleneck (e.g., reduced contention). Provide plausible microarchitectural explanations supported by profiler counters and, where possible, provide microbenchmarks that isolate specific mechanisms (e.g., a kernel that exercises only shared-memory vs only global memory paths).

Conclusion

Measuring and understanding GPU performance is both an art and a science. Accurate FLOP counting, thoughtful utilization metrics, systematic benchmark design, informed use of profiling tools, and carefully controlled ablation studies together provide the evidence needed to make reliable performance claims. Always be explicit about measurement conventions (FMA counting, precision), report complementary metrics (TFLOPs, memory bandwidth, occupancy), and document the experimental environment for reproducibility. With these practices, you can move from anecdotal performance statements to rigorous, interpretable, and reproducible performance analyses suitable for research and production optimization.

Introduction

GPUs have become the dominant platform for accelerating dense linear algebra and attention-like operations used in machine learning. Achieving high performance on modern GPUs requires more than just mapping a mathematical formula like matrix multiply or scaled dot-product attention onto a stream of CUDA threads; it requires carefully engineered software that exposes the right parallelism, manages memory hierarchy, and maps computations to specialized hardware primitives such as tensor cores and fast shared memory. This chapter surveys the software ecosystem and optimized libraries that researchers and engineers rely on to implement high-performance GEMM (general matrix–matrix multiply) and attention kernels. We will look at the building blocks and design patterns provided by low-level libraries such as CUTLASS, platform-optimized offerings like cuDNN, high-level kernel-generation frameworks such as Triton, and how these components integrate with frameworks like PyTorch. Finally, we will discuss the trade-offs between portability and hardware-specific optimizations and practical considerations when designing or choosing an implementation.

# CUTLASS: building blocks for high-performance GEMM primitives

CUTLASS (CUDA Templates for Linear Algebra Subroutines and Solvers) is a CUDA C++ template library from NVIDIA that exposes reusable, composable building blocks for implementing high-performance GEMM and related primitives. Its design reflects the canonical structure of a high-performance GPU GEMM: multi-level tiling of the computation, explicit management of data movement through memory hierarchy (global memory, shared memory, registers), use of fast hardware instructions (SIMT loads/stores, warp-level primitives, and tensor core instructions), and a flexible epilogue stage for applying post-processing like scaling, activation, or bias-add.

At the heart of CUTLASS is the decomposition of GEMM into several conceptual layers. The outermost layer divides the output matrix $C$ into tiles that are computed by cooperative thread blocks (CTAs). Each CTA loops over the $K$ dimension in blocks, loading fragments of $A$ and $B$ from global memory into shared memory, and then performing a sequence of inner micro-kernels that multiply fragments of $A$ and $B$ to update accumulators held in registers. This multilevel tiling—grid-level, block-level, warp-level, and register-level—lets the implementation balance parallelism, data reuse, and resource constraints (shared memory and registers).

CUTLASS formalizes this through a set of parameterized components. A typical CUTLASS GEMM is specified by types that describe:

- The data types for $A$, $B$, $C$, and accumulator (for example, float16 inputs with float32 accumulation).
- The threadblock tile shape (for example, $128 \times 128$ for the CTA).
- The warp tile shape and the instruction-level tile shape (e.g., $16 \times 16$ for a tensor core instruction).
- The memory layouts (row-major, column-major, interleaved layouts).
- The epilogue functor that maps raw accumulators to final outputs (scaling, activation, elementwise ops).

These templates let library authors explore many combinations of tile shapes and data layouts without rewriting kernels. CUTLASS also provides a library of highly tuned micro-kernel primitives that encapsulate the warp- and instruction-level implementation details, including explicit implementations targeting NVIDIA tensor core instructions (WMMA/ mma.sync) and vectorized SIMT math.

From an implementation viewpoint, two aspects are critical. First, data movement is optimized to maximize reuse: each piece of data loaded into shared memory is reused by multiple threads and warps before being evicted. Second, compute is organized to exploit warp synchronous instructions and tensor cores for high throughput. CUTLASS uses warp-level matrix multiply accumulators combined with careful instruction scheduling to ensure high utilization of compute units. The epilogue stage is also explicit: after accumulation, the epilogue reads accumulators and writes results back to global memory, applying scaling, bias, activation, and formatting. This separation lets one mix-and-match compute and post-processing efficiently.

CUTLASS also provides a performance model and a set of benchmarking utilities to search the parameter space of tile sizes and blocking strategies. Since modern GPUs have many architectural knobs (shared memory per SM, warp size, tensor core throughput), CUTLASS’s composable approach enables portability across GPU generations by retuning those parameters. In practice, CUTLASS forms the basis for many production GEMM implementations and higher-level libraries: vendors, research groups, and third-party frameworks either use CUTLASS directly or take inspiration from its modular design.

# cuDNN and vendor-optimized primitives for attention/GEMM

cuDNN (CUDA Deep Neural Network library) is NVIDIA’s highly optimized collection of GPU primitives tailored for deep learning. Where CUTLASS provides building blocks and templates, cuDNN provides ready-to-use, production-quality primitives that are heavily tuned and validated across a wide range of networks and hardware. cuDNN includes implementations for convolutions, RNNs, batch normalization, activation functions, and more recently, attention primitives and optimized GEMM routines that are used as the underlying computation for many layers.

Vendor-optimized libraries like cuDNN have several distinguishing characteristics. First, they are delivered as precompiled, closed-source kernels with carefully tuned kernels for specific hardware generations. These kernels take advantage of hardware-specific instructions (such as tensor cores with specific dot-product instruction encodings), memory subsystem behavior, and scheduling strategies that may not be expressible in high-level code without exposing architecture internals. Second, cuDNN exposes multiple algorithmic variants for many operations and a heuristic/auto-tuner that picks the best variant at runtime based on tensor shapes, data types, and profiling information. For example, a convolution might be implemented via FFT, GEMM-based lowering, Winograd, or direct convolution depending on the best throughput and memory trade-offs.

In the attention domain, cuDNN has started to provide fused attention primitives that implement the full scaled dot-product attention or portions thereof as a single kernel or a set of tightly integrated kernels. Fusing the softmax, scaling, and matmul operations reduces memory traffic: instead of materializing large intermediate tensors in global memory, intermediate results are kept in registers or shared memory for immediate consumption. This is crucial for attention where the $QK^T$ matrix (for queries $Q$ and keys $K$) can be large, and reading/writing it multiple times is expensive.

Vendor libraries also exploit specialized numerical formats and operations. Mixed-precision computing—e.g., using $FP16$ or $BF16$ inputs with $FP32$ accumulation—provides higher arithmetic throughput while maintaining accuracy. Tensor cores offer higher throughput for mixed-precision matrix multiply-accumulate operations, but getting peak performance requires mapping data layouts and tile sizes to the tensor core instruction shapes. Vendor libraries include these mappings and assembly-level kernels where necessary.

The price of vendor tuning is, however, decreased transparency and sometimes limited flexibility. When a user needs to implement slightly non-standard behavior—for example, an unusual attention variant or a custom activation fused into the epilogue—the vendor primitive may not support it directly. Some libraries address this by offering extensible epilogue hooks or by exposing lower-level primitives (e.g., matmul backends) that can be assembled by user code. Nonetheless, when the required functionality matches the vendor-provided operations, the performance is often superior because the vendor kernels are optimized to exploit the microarchitectural details that are difficult for a third party to reproduce.

# Triton and other high-level kernel-generation frameworks

Triton is a high-level language and compiler for writing custom GPU kernels that aims to make it easier to express data-parallel computations while still enabling high performance comparable to handwritten CUDA. The key idea behind Triton is to provide a model where a developer writes kernel logic in a Python-embedded DSL that resembles cooperative SPMD programming; the compiler then lowers this description to efficient CUDA or NVVM code, handling many low-level optimizations automatically.

Triton’s programming model revolves around the notion of a kernel that operates on large, blocked portions of a tensor. The programmer indexes into input and output tensors with symbolic "program IDs" that represent slices of the work, and Triton generates code that computes those tiles. Behind the scenes, Triton maps these tiles to hardware threads and warps, inserts vectorized loads and stores, schedules shared memory usage, and can generate code that uses warp-level matrix-multiply instructions. Triton also performs a variety of static and dynamic analyses to select loop unrolling factors, prefetching schedules, and memory layout transformations.

One strength of Triton is expressivity: it is straightforward to implement fused kernels that eliminate intermediate memory traffic (for example, a fused attention kernel that computes $QK^T$, applies scaled softmax, and multiplies by $V$ without storing $QK^T$ to global memory). Because Triton expresses kernels at a higher level, common patterns like reduction, broadcasting, and strided memory accesses are easier to implement correctly and concisely. Triton also provides an autotuning infrastructure and heuristics to pick tile sizes and other parameters for a given GPU.

Other high-level kernel-generation frameworks include TVM (with its tensor expression language and schedule primitives), Halide (and GPU backends), and MLIR-based approaches that allow flexible lowering and optimization. TVM is particularly focused on tensor algebra and scheduling: a user expresses the computation as an index-based tensor expression and then applies schedule primitives (blocking, vectorization, compute-at, etc.) to transform the computation for the target hardware. TVM’s auto-scheduler can search the schedule space to find performant variants. MLIR-based toolchains are emerging to represent higher-level operations and progressively lower them through dialects to GPU dialects that map to LLVM/ NVVM.

These frameworks share common trade-offs. They provide easier programmability and faster development for new kernels compared to writing raw CUDA, and they often include auto-tuning to help find good parameters. However, they must capture a sufficiently rich set of transformations and have a back-end capable of generating code that competes with hand-tuned assembly or vendor kernels. For kernels that require exploiting tiny architectural quirks or newly introduced instructions, framework maintainers must update the back-end to expose those capabilities. In practice, Triton and TVM have enabled rapid iteration in research and production for attention and customized GEMM-like operations because they dramatically reduce development effort while achieving strong performance.

# PyTorch integration points, kernels and extensions

PyTorch is a leading deep learning framework that exposes multiple integration points for accelerated kernels, enabling both runtime use of vendor libraries and user-defined extensions. Understanding where custom kernels and optimizations fit into PyTorch is crucial for deploying high-performance attention and GEMM routines.

At the core of PyTorch’s compute backend is ATen, the tensor library implementing operations on CPU and GPU (through CUDA). ATen provides the C++ API that underlies PyTorch tensors and operations. Many high-performance primitives in PyTorch ultimately route through ATen to call into vendor libraries (cuDNN, cuBLAS) or custom kernels implemented in CUDA/C++.

There are several mechanisms for extending PyTorch with custom kernels:

- C++ extensions (torch::autograd::Function and cpp extension). Developers can write CUDA kernels and wrap them in C++ code that integrates with PyTorch’s dispatcher and autograd. The extension is compiled into a shared library and can be loaded at runtime. This approach gives full control over implementation details, memory management, and gradient computation, and is the typical route for shipping production kernels.

- JIT / TorchScript and custom operator registration. PyTorch allows registering custom operators (ops) that can be invoked from Python, traced or scripted by the JIT, and serialized in TorchScript. Custom ops can be implemented in C++/CUDA and registered with the dispatcher, which allows them to be exported in models and used in production runtimes such as LibTorch.

- CUDA kernel wrappers via Python APIs (e.g., using Numba or Triton). Some researchers prototype kernels using Python-embedded kernel compilers such as Triton or Numba, and then call these kernels from PyTorch. While prototyping is fast, production workloads often prefer C++ extensions for stability and deployment.

- Fused kernels and graph compilers. Projects like PyTorch’s JIT graph fuser and TorchInductor aim to lower high-level graph fragments into optimized fused kernels. The JIT fusion stack attempts to fuse elementwise and reduction patterns into single kernels to reduce memory traffic and overhead. Newer backends target GPU code generation and may call Triton or generated CUDA kernels.

PyTorch also provides utilities for memory format and layout management (e.g., channels-last layout), custom memory allocators, and stream and event management to orchestrate asynchronous kernels and overlapping of compute and data movement. For GEMM and attention, integration often involves calling into cuBLAS/cuDNN for standard shapes, while custom fused attention kernels are shipped as extensions when vendor primitives are insufficient. Registration through the dispatcher ensures the custom operator is called transparently in Python code and ties into autograd by providing forward and backward implementations.

Performance-sensitive integration also requires careful handling of concurrency and streams. PyTorch’s default behavior executes kernels on the current CUDA stream of the tensor; custom kernels must honor stream semantics, use asynchronous APIs appropriately, and avoid synchronization unless necessary. Memory alignment, padding, and tensor contiguity are other practical concerns: custom kernels often expect tensors in a particular layout or alignment to leverage vectorized loads or tensor core instruction alignment constraints.

Finally, packaging and distribution matter. For a kernel to be used widely, it must be compiled against multiple CUDA/toolkit versions and GPU architectures. Prebuilt wheels (manylinux with bundled CUDA) or on-install compilation scripts are common distribution strategies, each with trade-offs between ease-of-use and compatibility.

# Considerations for portability vs hardware-specific optimizations

One of the central tensions in GPU kernel design is the trade-off between portability and leveraging hardware-specific optimizations to extract maximal performance. Portability implies writing code that runs correctly and reasonably efficiently across different GPU vendors and generations. Hardware-specific optimizations, by contrast, exploit idiosyncratic features—special instructions, memory subsystem characteristics, or instruction encodings—to achieve peak throughput, but can be brittle across architectures.

Portability can be pursued at multiple levels. The highest-level approach is to rely on vendor libraries (cuBLAS, cuDNN) and portable frameworks (oneAPI, ROCm libraries for AMD) so that the same high-level API runs across hardware with vendor-provided backends implementing the optimal kernels. Another portable route is to use compiler-driven frameworks such as TVM, Triton, or MLIR-based pipelines that can retarget different backends and perform autotuning per-architecture. These approaches reduce the burden on the developer but often do not reach the absolute peak that a hand-tuned, vendor-specific kernel can attain.

Hardware-specific optimization strategies deliver higher performance by mapping computations to particular primitives. Examples include using NVIDIA tensor core instructions (e.g., mma.sync) to perform mixed-precision $M \times N$ multiply-accumulate operations in the $8 \times 8$ or $16 \times 16$ shapes supported by the instruction, or leveraging specialized memory instructions (like LDG with cache hints) and carefully chosen shared memory bank layouts to minimize bank conflicts. Hand-tuned kernels may include inline PTX or SASS-level tuning, use of cooperative groups for warp-shared communication, and manual scheduling to hide latencies in a way that generic compilers do not.

However, hardware-specific code has maintenance and portability costs. An implementation tuned for the memory hierarchy and instruction set of one GPU generation may underperform or even be incorrect on another generation if assumptions about register pressure, warp scheduling, or tensor core shapes change. Moreover, the introduction of new numeric formats (e.g., BF16, TF32) and specialized hardware units requires reworking kernels to exploit them. For multi-vendor portability, the challenge is greater: AMD and NVIDIA have different ISA, transcendent performance knobs, and libraries.

Practical strategies to balance the trade-offs include:

- Layered design: implement operations in layers so that the highest-level logic is portable while a backend-specific implementation implements the hot inner loops. For example, express attention in terms of high-level primitives (GEMM + softmax + GEMM) and provide fast paths that call vendor-optimized fused primitives when available; otherwise, fall back to a portable generic implementation.

- Autotuning and parameterized kernels: write parameterized kernels (as CUTLASS does) and run autotuning at install time or first run to pick tile sizes and unroll factors tuned to the particular GPU. This gets much of the benefit of hand tuning without hardcoding parameters.

- Expose architecture-specific code paths behind a single API: let the runtime select between portable code and highly tuned kernels based on device properties. This is the approach used by cuDNN: many algorithms are available and the library picks the best one for given shapes and device.

- Use intermediate abstractions: MLIR and other IRs can express transformations and lowerings in a device- and instruction-aware way. If the backend is kept up-to-date, then code can be retargeted with lower effort.

- Keep correctness and numerical stability as first-class goals: hardware-specific optimizations often change numerical ordering and can affect reproducibility. Mixed-precision or fused operations should include user-configurable options for deterministic or more accurate variants when needed.

- Plan for maintainability: maintain a testing and benchmarking harness that continuously runs kernels across target architectures. Because hardware evolves, continuous integration that runs performance regression tests and correctness tests across multiple GPUs is critical.

A concrete example of this tension is implementing attention for transformer models. A naive, portable implementation computes $S = Q K^T$ (an $M \times N$ matrix), applies scaled softmax across appropriate axes, and computes $O = \text{softmax}(S) V$. This code is straightforward and portable but incurs significant memory traffic. A hardware-specific optimized kernel fuses these operations, keeps intermediate $S$ tiles in shared memory or registers, and uses tensor cores for the matrix multiply, achieving much lower memory bandwidth and higher throughput. But that fused kernel must be rewritten to exploit different tensor core shapes or instruction encodings on a new GPU generation or a different vendor’s accelerator.

In summary, the choice between portability and specialization depends on constraints: if you must support many hardware targets and prefer maintainability, favor portable frameworks and autotuning; if you need peak performance on a narrow set of hardware, invest in specialized kernels and vendor-tuned libraries. In production systems, the pragmatic approach is hybrid: provide portable fallbacks while shipping specialized kernels for the dominant hardware in your deployment.

Conclusion

High-performance GEMM and attention implementations sit at the intersection of algorithmic design and low-level hardware engineering. Libraries like CUTLASS expose composable building blocks that capture effective tiling and data movement strategies, while vendor libraries such as cuDNN provide battle-tested, highly optimized kernels for common patterns. High-level code generators like Triton and TVM speed up development and allow researchers to implement and tune fused kernels without writing raw CUDA, and frameworks like PyTorch provide the integration points to bring these kernels into real models. Understanding the architectural primitives—shared memory, warp-level operations, tensor cores, and the trade-offs in tiling, accumulation precision, and memory layout—is essential for reading research papers and contributing new kernels. Finally, thoughtful engineering is required to balance portability against the desire for hardware-specific performance, and the right balance often combines autotuning, layered designs, and vendor-optimized code paths.
