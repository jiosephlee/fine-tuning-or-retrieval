Introduction

Many choices in modern neural network design are driven by trade-offs between the number of trainable parameters, the amount of computation required, the memory footprint during training and inference, and the latency that users experience. Structured parameterizations—such as low-rank factorizations, block-diagonal matrices, and butterflylike fast transforms—allow model designers to trade off parameter count for additional staged computations. This chapter develops the tools to reason quantitatively about those trade-offs. We will show how to count parameters for common structures, analyze the time complexity of forward and backward passes (including staged products), account for memory usage during training, compare latency constraints at inference and training time, and place these results in the language of asymptotic complexity (e.g., $O(d^2)$, $O(d\log d)$, $O(d)$) while being careful about the constants. We will also discuss practical profiling concerns—FLOPs, memory bandwidth, and cache behavior—and end with design principles for allocating a parameter budget across layers.

# Counting trainable parameters for various structures (dense, low-rank, block-diagonal, butterfly-like)

Counting parameters is the first step in understanding model size. For an input dimension $d$ and output dimension $m$, a dense (fully connected) linear layer has a weight matrix $W\in\mathbb{R}^{m\times d}$ and typically a bias vector $b\in\mathbb{R}^{m}$. The total number of trainable parameters is
\[
\text{Params}_\text{dense} = m\cdot d + m = m(d+1).
\]
When $m=d$, this is $d^2 + d$, and we often drop the bias in asymptotic counts, writing $O(d^2)$.

Low-rank parameterizations reduce parameter count by representing $W$ as a product of two smaller matrices: $W = U V$ with $U\in\mathbb{R}^{m\times r}$ and $V\in\mathbb{R}^{r\times d}$ where $r$ is the rank parameter chosen such that $r \ll \min(m,d)$. The number of parameters is
\[
\text{Params}_\text{LR} = m r + r d + m \approx r(m+d).
\]
When $m=d$ and $r\ll d$, this is approximately $2rd$, giving a multiplicative parameter reduction of $\approx r/d$ relative to a dense $d\times d$ layer. The rank $r$ controls expressivity: a low-rank matrix can only represent linear maps in a subspace of dimension at most $r$ on either side, so parameter saving comes at the cost of representational flexibility.

Block-diagonal structures partition the full matrix into independent smaller blocks. Suppose $W$ is block-diagonal with $B$ blocks each of size $s\times s$, and $B s = d$ (for simplicity assume $m=d$). Each block has $s^2$ parameters, so
\[
\text{Params}_\text{blk-diag} = B\cdot s^2 = d s.
\]
Because $s = d/B$, this is $d^2 / B$. As $B$ increases, parameter count decreases. A block-diagonal matrix cannot represent dense cross-block interactions, so it imposes sparsity at the block level.

A more sophisticated structured class is butterfly-like matrices, which are parameter-efficient factorizations inspired by the fast Fourier transform and related algorithms. A classic butterfly factorization represents a dense $d\times d$ matrix as a product of $L$ sparse factors, each factor having $O(d)$ nonzero entries arranged in a regular pattern such that the product realizes transforms in $O(d\log d)$ time. For example, for $d=2^k$, the radix-2 butterfly has $L=k=\log_2 d$ stages, and each stage is block-sparse with exactly $d$ nonzero parameters (often arranged as $d/2$ $2\times 2$ blocks). The parameter count is therefore
\[
\text{Params}_\text{butterfly} = O(d\log d).
\]
More concretely, if each stage has $d$ parameters and there are $\log_2 d$ stages, then $\text{Params} = d\log_2 d$, plus biases if present. Butterfly-like parameterizations can approximate a wide class of linear maps (in many practical settings they are expressive enough for learned transforms) but they trade parameters for staged multiplications: instead of one dense matmul, we compute $\log d$ sparse stages.

It is useful to summarize with a few special-case numbers when $m=d$: dense has $\Theta(d^2)$ parameters, rank-$r$ has $\Theta(rd)$, block-diagonal with block size $s$ has $\Theta(d s)$ or $\Theta(d^2/B)$, and butterfly-like has $\Theta(d\log d)$. These counts are exact up to minor additions for biases. When counting parameters in practice, one must also include optimizer states (e.g., momentum, Adam estimates) which typically scale proportionally with trainable parameters (we will cover this in the memory section).

# Time complexity of forward and backward passes for staged products

Time complexity describes how many arithmetic operations (FLOPs) are needed to compute forward and backward passes. The forward pass for a dense $m\times d$ layer requires $m d$ multiply-adds (counting a multiply and an add as two FLOPs is conventional; here we will count a multiply-add as two FLOPs unless stated otherwise). Thus, the dense forward cost is $O(md)$ FLOPs; for square layers with $m=d$ this is $O(d^2)$.

A low-rank forward pass with $W=UV$ computes $y=U(Vx)$. The cost is $O(rd + mr)$ FLOPs: $Vx$ costs $rd$ and multiplying by $U$ costs $mr$. For $m=d$ and $r\ll d$, this is $O(rd)$, which is a multiplicative saving over $O(d^2)$ by a factor $r/d$.

For block-diagonal matrices with $B$ blocks of size $s$, we perform $B$ independent matmuls each costing $O(s^2)$, so total cost is $O(B s^2) = O(d s)$. If $s$ is constant or grows slowly with $d$, forward cost is substantially less than $O(d^2)$. Importantly, block-diagonal operations parallelize naturally over blocks, which matters for implementation on many-core hardware.

Butterfly-like staged products consist of $L$ sparse stages, each costing $O(d)$ FLOPs, giving a forward cost of $O(d\log d)$ when $L=O(\log d)$. The per-stage operations are often small dense operations (like $2\times 2$ multiplies) that are applied across the $d$ elements. Ripple effects appear in implementation: although theoretical FLOPs are $O(d\log d)$, each stage’s operations may be memory-bound or incur nontrivial overheads, which we will discuss later.

Backward pass complexity typically mirrors forward complexity but with constant factors that depend on whether intermediate activations are cached during the forward pass. For a dense layer, backward propagation requires computing gradients with respect to weights, inputs, and biases. Naively, the backward pass costs approximately 2–3 times the forward cost: computing the gradient with respect to weights requires an outer product of the output gradient and the input (cost $O(md)$), computing the gradient with respect to inputs requires a matmul with the transposed weight ($O(md)$), and other bookkeeping adds more. In many frameworks, the backward pass requires roughly 2–4 times the forward FLOPs depending on whether optimized fused kernels are available.

For staged factorizations like low-rank or butterfly, the backward pass follows the chain rule through the factorization. For $W=U V$ we must compute gradients through $Vx$ then through $U$; the work is about $O(rd + mr)$ for forward plus roughly the same for backward, so total training-time cost is about twice the forward cost (again constants depend on implementation). For an $L$-stage butterfly, each forward stage computes $x^{(i+1)} = A^{(i)} x^{(i)}$ for $i=0,\dots,L-1$. Backpropagating through the product requires traversing the stages in reverse and doing another $L$ stages of similarly cheap operations. Thus training cost is approximately a factor of 2 overhead relative to inference FLOPs (forward-only), plus any extra costs for gradient accumulation or weight updates. If intermediate activations are recomputed instead of cached (a memory vs computation trade-off), the backward pass may perform additional forward-like operations, increasing computational cost to $>2\times$ the forward FLOPs.

An important practical consideration is that staged factorizations can change the balance between compute-bound and memory-bound regimes. Dense matmuls are highly optimized and achieve high arithmetic intensity, so they are often compute-bound on modern GPUs. Sparse or many small staged operations may be memory-bound or kernel-launch-bound, causing effective throughput to be lower than what FLOP counts would suggest.

# Space complexity and memory footprint during training

Memory usage during training comes from several sources: model parameters, optimizer states, stored activations (needed for backpropagation), gradients, and miscellaneous buffers. Counting all of these gives the total memory footprint.

Model parameters scale with the parameter count discussed earlier. If a model has P parameters and we store each parameter in 32-bit float, parameters alone require $4P$ bytes. Many practitioners use 16-bit (float16 or bfloat16) to reduce memory; in that case parameters take $2P$ bytes. Optimizers like SGD with momentum require one additional buffer of the same size (e.g., momentum term), while Adam requires two additional buffers (first- and second-moment estimators), leading to an optimizer state overhead of 1–3 times the parameter memory, depending on optimizer choice. Thus, an Adam-trained model stores about $3P$ parameter-size buffers: the parameters themselves and two moments.

Activations are often the dominant memory consumer, especially for deep networks and large batch sizes. For a given layer with activation dimension $d$ and batch size $B$, storing the forward activations for backprop requires $B\cdot d$ numbers (again times 4 bytes for float32, etc.). In a network with $L$ layers, naive storage of all activations costs $O(B\sum_l d_l)$. Techniques such as activation checkpointing (recompute activations during backprop rather than cache them all) trade increased computation for reduced memory. Checkpointing can reduce memory from $O(L)$ to $O(\sqrt{L})$ or even $O(1)$ additional layers cached depending on strategy, at the cost of recomputing some forward passes during backward.

For structured layers, there are additional memory nuances. Low-rank layers have fewer parameters and hence smaller optimizer states, but their intermediate activations (e.g., $Vx$ of size $r$ per example) may be smaller too, so per-layer activation memory can drop. Block-diagonal layers store and operate on per-block activations which may be more cache-friendly. Butterfly layers store activations at each stage; if we cache all stage outputs, activation memory is proportional to $B\cdot d\cdot L = O(B d \log d)$ for a $\log d$-stage butterfly. To reduce memory, one often caches only the input and recomputes intermediate stage outputs during backward, again trading time for space.

Gradients with respect to parameters are usually accumulated over the batch and stored in the same format as parameters (another $P$). In frameworks that compute gradient updates on-the-fly and discard intermediate copies, gradients need not multiply memory excessively, but optimizer states remain.

A compact formula for approximate total training memory is:
\[
\text{Mem}_\text{train} \approx \alpha P + \beta B\sum_{l}d_l + \gamma,
\]
where $\alpha$ accounts for parameter + optimizer state factor (e.g., $\alpha\approx 3$ for Adam with float32), $\beta$ converts activations to bytes (4 bytes per float32) and includes overhead for any cached intermediate stage activations, and $\gamma$ accounts for temporary buffers and model metadata. This formula highlights two levers: reducing $P$ reduces parameter and optimizer-state memory linearly, while reducing per-layer activation size or batch size $B$ reduces activation memory linearly.

# Latency considerations at inference vs training

Latency requirements differ dramatically between inference and training. Inference latency is often measured per example or per small micro-batch and must be minimized for real-time applications. Training latency is generally amortized over large batches and many iterations, so throughput (examples per second) and total wall-clock convergence time are the primary metrics.

Structured parameterizations can reduce parameter storage and required memory bandwidth at inference, but they may increase the number of sequential stages (depth of computation) and thus the critical path for latency. Consider a butterfly transform with $L=\log d$ stages: even though total FLOPs are $O(d\log d)$, if the stages must be executed sequentially because later stages depend on earlier outputs, the inference latency per example will include the sum of latencies of all $L$ stages. For small $d$, or when parallelism across batch or vector lanes is limited (e.g., CPU with limited SIMD width), increased number of sequential stages can increase wall-clock latency. On highly parallel hardware like GPUs, each stage can still be parallelized across many elements, and the sequential dependency cost can be amortized, making butterfly transforms attractive.

Dense matmuls typically have fewer sequential stages (one big matmul) and can leverage highly optimized kernels like cuBLAS which fuse many operations, minimizing kernel-launch overhead and latency. Low-rank factorizations add an extra matmul ($Vx$ then $U$), so they add a single extra sequential stage. If each stage is large and parallelized over the batch, the added latency may be negligible.

Training latency per step is dominated by backward passes and weight updates, and large batch sizes can hide sequential staging costs by parallelizing across examples. However, staged factorizations that require caching many intermediate activations can increase memory usage and thus force smaller batch sizes, which in turn hurt throughput and convergence properties. Additionally, frequent small kernels in butterfly stages can incur kernel launch overheads during training, which matters more when training is distributed across many small workers or on CPUs.

Thus, when choosing a structured parameterization, match the structure to the hardware and the latency constraints: if low per-example latency is critical and the hardware favors large fused kernels, prefer parametrizations with few sequential stages or ensure that stages are sufficiently large to utilize parallelism. If overall throughput and memory reduction are the priority, staged factorizations like butterfly may be better.

# Asymptotic analyses (O(d^2), O(d log d), O(d)) and constants

Asymptotic notation (Big-O, Theta) succinctly describes scaling but hides constants that can be decisive in practice. We must therefore interpret asymptotic claims carefully and consider both the leading term and its prefactor. Here we classify common structured layers by asymptotic FLOPs and parameter counts, and explicitly mention typical constants.

Dense square layer: parameters $P_\text{dense}=\Theta(d^2)$ and forward FLOPs $\text{FLOPs}_\text{dense} \approx 2d^2$ (counting multiply and add separately). Backprop roughly $4$–$6d^2$ FLOPs depending on implementations. The constant factors are large: a single dense matmul's prefactor is large but its arithmetic intensity is also high, which keeps it efficient.

Low-rank layer: parameters $P_\text{LR}=\Theta(rd)$ and forward FLOPs $\text{FLOPs}_\text{LR} \approx 2rd$ (again multiply-add counted). Backward multiplies this by about 2. Constants here are modest; performance depends on $r$. When $r$ is large relative to hardware vector width or batch size, matmuls can stay efficient. If $r$ is too small, overheads reduce utilization.

Block-diagonal layer: parameters $P_\text{blk}=\Theta(d s)$ where $s$ is block size, and forward FLOPs are $\Theta(d s)$. If $s$ is small (constant), the asymptotic is linear in $d$. The per-block matmul prefactor is smaller than a large dense matmul, and utilization depends on $s$ relative to vectorization width. For small blocks, per-block kernels may be memory- or overhead-bound.

Butterfly-like layer: parameters $P_\text{butt}=\Theta(d\log d)$ and forward FLOPs $\text{FLOPs}_\text{butt}=\Theta(d\log d)$ with small constant per stage. For a radix-2 butterfly, if each stage applies $d/2$ independent $2\times 2$ multiplies, the per-stage cost is $c d$ with $c$ around 8 FLOPs per element in a multiply-add accounting, giving total $\approx 8 d \log_2 d$ FLOPs. Compare this with dense $\approx 2 d^2$. For moderately large $d$, $8 d\log d \ll 2 d^2$, but the advantage depends on the constants and the efficiency of executing many small operations. When hardware supports fused batched small-matrix kernels efficiently, butterfly-like approaches are attractive; otherwise their practical speedup may be lower than asymptotic ratios suggest.

Asymptotic memory: dense $O(d^2)$ for parameters, low-rank $O(rd)$, block-diagonal $O(ds)$, butterfly $O(d\log d)$ for parameters. Activation memory for layers with width $d$ and batch $B$ scales as $O(Bd)$ and is independent of weight parameterization, except for staged products that require storing intermediate stage outputs (which add an $O(Bd\log d)$ term if all stages are cached).

Asymptotic constants matter because two architectures with the same Big-O can have very different wall-clock performance. For example, a block size $s=256$ vs $s=16$ both give $O(d s)$ parameters, but the larger block can utilize GPUs better, reducing runtime. Always complement asymptotic reasoning with single- and multi-threaded profiling for the target hardware.

# Practical profiling: FLOPs, memory bandwidth, and cache effects

Asymptotic FLOP counts are necessary but insufficient to predict runtime. Practical profiling must account for memory bandwidth, cache hierarchy, kernel launch overheads, and parallelization. Performance can be categorized into compute-bound vs memory-bound regimes depending on arithmetic intensity (FLOPs per byte of memory transferred).

Arithmetic intensity for a dense matrix-vector product $y=Wx$ with $W\in\mathbb{R}^{d\times d}$ and single input vector is low: each element of $W$ is read once and contributes to few FLOPs, so the operation is often memory-bound for large $d$ unless batching is used. However, dense matrix-matrix multiply (GEMM) with batch size $B$ turns the operation into a matrix-matrix product of $d\times d$ times $d\times B$ which increases arithmetic intensity and allows compute-bound execution. This is why training with large batch sizes saturates GPUs better.

Butterfly and other staged sparse transforms often have small per-stage arithmetic intensity because each stage reads and writes many small elements and performs few FLOPs per byte. They can be limited by memory bandwidth or by cache misses if the data layout does not align with stage access patterns. Cache-friendly layouts that ensure contiguous access and reuse of hot data can substantially improve performance. For example, performing $2\times 2$ block multiplies in a butterfly in a loop that streams through contiguous memory can exploit SIMD lanes and caches; doing the same with scattered indices will incur many cache misses and poor throughput.

Kernel launch and synchronization overheads are important on GPUs and CPUs. A single large GEMM amortizes launch costs over many FLOPs. Many small kernels (as in many-stage butterfly with small block sizes) incur repeated kernel launches, leading to overhead proportional to the number of stages and tasks. One mitigation is to fuse multiple stages into a single kernel where possible or to implement specialized batched micro-kernels.

Memory bandwidth becomes critical when storing or reading optimizer states and gradients. If the optimizer must read large parameter buffers and write updated states each step, the step time may be limited by reading/writing memory rather than performing arithmetic. For example, Adam requires reading parameters and two moment buffers and writing them back—three reads and three writes proportional to $P$ each step—so the per-step memory traffic is significant.

Profiling recommendations: measure both FLOPs and memory traffic on target hardware. Tools like nvprof, Nsight Systems, and CPU profilers can show kernel times, memory throughput, and kernel launch counts. Compare achieved FLOPs to peak FLOPs of the hardware and measure bandwidth utilization. If achieved FLOPs are low while bandwidth is high, the operation is memory-bound; if bandwidth is low and FLOPs are far from peak, kernel launch or latency overhead may be the bottleneck. Use micro-benchmarks of batched small-matrix multiplies and staged transforms to estimate realistic throughput rather than relying on theoretical FLOP counts.

# Design considerations for parameter-budget allocation across layers

Given a fixed parameter budget (memory, or maximum number of trainable parameters), how should one allocate parameters across layers? There is no one-size-fits-all answer, but several principles guide good trade-offs.

First, consider the sensitivity of different layers to parameter reduction. Empirically in many networks, earlier layers closer to input often benefit from higher width to capture diverse low-level features, while middle layers might be more redundant and thus amenable to low-rank or structured compression. In transformers, the feedforward (MLP) layers often dominate parameter count; compressing those layers via low-rank factorizations or parameter sharing can yield large savings with small accuracy loss. Conversely, attention layers' projection matrices might be more sensitive to compression.

Second, allocate parameters where they produce the largest effective capacity gain. Using a simple model of expressivity, adding parameters to a bottleneck layer that constrains information flow often yields more benefit than adding parameters where capacity is already in surplus. This suggests using smaller but carefully structured layers in some places and preserving full dense parameterizations in critical layers.

Third, match structural choices to layer dimensions. Low-rank factorizations are most effective when the effective rank of the true mapping is low. Block-diagonal parameterizations make sense when the input can be partitioned into relatively independent groups (e.g., channels in certain convolutional designs). Butterfly-like transforms are well-suited when we want global mixing with low parameter cost and when hardware can execute many small stages efficiently.

Fourth, consider optimizer and memory costs. If memory is the binding resource, prefer parameterizations that reduce optimizer state (e.g., low-rank) or use memory-efficient optimizers (SGD with momentum has less per-parameter overhead than Adam). If compute is the bottleneck, prefer parameterizations that allow larger fused ops. For example, a block-diagonal choice with large block sizes may use more parameters than a butterfly but run faster due to better kernel utilization.

Fifth, balance depth and width. Given a parameter budget, one can increase depth (more layers) with narrower layers, or increase width with fewer layers. Deeper networks often have better expressivity per parameter, but they can also increase activation memory and training instability. Optimal allocation depends on task, data regime, and training recipe.

Finally, adopt an empirical, iterative approach: profile candidate architectures on target hardware to measure real wall-clock throughput, memory usage, and learning curves. Small theoretical advantages can be lost in implementation inefficiencies; therefore iterative tuning—varying rank $r$ in low-rank layers, block size $s$ in block-diagonal, or number of stages $L$ in staged factorizations—guided by profiling and validation loss is essential.

Concluding remarks

Complexity analysis provides crucial quantitative guidance when selecting structured parameterizations. Counting parameters, computing forward/backward FLOPs, and estimating memory footprints give first-order predictions; asymptotic classes indicate scalability. However, the constants, hardware characteristics (compute vs memory-bound behavior), kernel implementation details, and latency constraints often determine practical performance. Use the analyses in this chapter to make informed initial design choices, then profile and iterate on the specific hardware and task to reach the best trade-off between parameter count, computation, and memory.
