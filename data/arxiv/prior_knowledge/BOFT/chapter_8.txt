Introduction

Large pretrained models, especially in natural language processing and computer vision, have reshaped how we approach downstream tasks. However, these models often contain hundreds of millions to trillions of parameters. When a practitioner wants to adapt such a pretrained model to a new task, fine-tuning the entire parameter set is often wasteful in computation, storage, and engineering complexity. Parameter-efficient finetuning (PEFT) refers to a family of methods that adapt pretrained models to new tasks while updating only a small fraction of the model’s parameters. The goal is to achieve comparable task performance to full-model fine-tuning while dramatically reducing the number of trainable parameters, memory footprint for storing task-specific weights, and often the required compute and communication for multi-task or multi-user deployments.

This chapter presents the motivations for PEFT, contrasts full fine-tuning with parameter-efficient alternatives, and surveys representative methods: adapter modules, prompt and prefix tuning, low-rank adaptation (LoRA), minimal approaches like BitFit, and orthogonality-informed approaches. We also explain how to evaluate and compare these methods in practice using metrics such as the number of trainable parameters, held-out performance, inference latency, and storage/serving considerations. The aim is to provide intuitive explanations, formal formulations where helpful, and concrete practical considerations so that you can read and critically assess research in this area.

# Problem statement: why parameter-efficient finetuning is needed

The canonical problem setting is as follows. A large model M with parameter vector or tensor set denoted by $\Theta \in \mathbb{R}^P$ has been pretrained on a large generic corpus. We want to adapt M to a downstream task T (for example, sentiment classification or question answering) where we have task-specific data $\mathcal{D}_T$. A straightforward strategy is to initialize a task-specific model with $\Theta$ and then gradient-update all parameters to minimize a task loss $\mathcal{L}_T(\Theta)$. This is the full fine-tuning approach. But there are multiple reasons why updating all $P$ parameters is often undesirable.

First, storage: If each task requires its own full copy of $\Theta$, then storing weights for many tasks becomes impractical. For a model with $P=1$ billion parameters and 16 bytes per parameter (typical for fp16 plus optimizer states), each task copy can cost gigabytes. In practical multi-task or multi-client settings (for example, enterprise where many customers want customized models), this quickly becomes prohibitive.

Second, compute and memory during training: Updating all parameters requires backpropagating through the entire model and maintaining gradients and optimizer state for each parameter. This increases GPU memory usage and can slow training, especially for large models that are already pushing hardware limits.

Third, multi-task efficiency and modularity: When many tasks share a common pretrained backbone, it is attractive to keep the backbone fixed and swap in small task-specific modules. This supports rapid switching between tasks and reduces risk of destructive interference between tasks.

Fourth, privacy and continual learning: In scenarios where task-specific data cannot be centralized or must remain private, sending a small task-specific update (e.g., a lightweight adapter) rather than a full model may be more feasible. Similarly, in continual learning, restricting updates to a small subset of parameters can reduce catastrophic forgetting by limiting interference with representations that are useful for many tasks.

Finally, deployment and latency: Some PEFT approaches can be implemented to preserve inference-time efficiency or to require only small added costs compared to the base model. They allow rapid delivery of task-specific functionality with minimal re-deployment of the full model and make it practical to serve personalized models on devices with constrained storage.

In short, PEFT addresses practical bottlenecks—storage, compute, modularity, and privacy—by seeking adaptation methods that change the smallest possible part of the model while keeping performance high.

# Fine-tuning vs full retraining: costs and trade-offs

Full fine-tuning (updating all parameters $\Theta$) is conceptually simple and often yields strong performance because the entire representational capacity of the model is available for the new task. In many benchmark settings, full fine-tuning is a strong baseline. However, it carries several concrete costs.

Compute cost: Full fine-tuning requires forward and backward passes through the entire model. For a model with $P$ parameters and typical dense matrices, the time complexity per token or per minibatch scales with model size. If resources are limited, full fine-tuning may be infeasible. Furthermore, large optimizers (Adam, Adagrad) maintain state per parameter, increasing memory overhead.

Storage cost: Each fine-tuned task demands a copy of the updated parameters. If you have $N$ tasks, naively storing $N$ copies of $\Theta$ multiplies storage.

Overfitting and sample efficiency: Large models can overfit small datasets when fully updated. With limited task data, updating only parts of the model or adding constrained adaptation modules often reduces overfitting and improves generalization.

Infrastructure and deployment complexity: Deploying many fully-fine-tuned models requires distributing large files and possibly re-serving the model for each task. In contrast, PEFT approaches can share the core model and load only small task-specific changes.

On the trade-off side, PEFT methods generally update a much smaller parameter subset $\Delta \Theta$ with size $p \ll P$. The potential advantages include lower training memory footprint, cheaper communication and storage for task-specific updates, and better modularity. The risk is performance degradation: if $\Delta \Theta$ is too small or insufficiently expressive relative to task requirements, the adapted model may underperform full fine-tuning.

A nuanced view: many modern PEFT methods aim to match or closely approach full fine-tuning performance while using orders-of-magnitude fewer trainable parameters. Empirically, for many NLP tasks, methods like adapters, LoRA, and prompt tuning can produce performance near full fine-tuning for popular benchmarks. However, the effectiveness depends on task complexity, data size, and the match between the PEFT method’s inductive biases and the required adaptation. For instance, tasks requiring substantial representational shift in early layers may be harder to adapt using only small low-rank updates applied in later layers.

Finally, consider latency: some PEFT methods may increase inference latency because they inject extra computation (for example, adapter subnetworks). Others, like prompt or prefix tuning, can be implemented with negligible inference overhead if implemented as fixed tokens or cached keys/values. Thus, trade-offs must account for the intended deployment scenario: model serving, on-device personalization, or frequent re-training.

# Adapter modules: addition of small subnetworks

Adapter modules are among the earliest and most intuitive PEFT techniques. The core idea is to insert small task-specific subnetworks—adapters—into the layers of a frozen pretrained model. The pretrained weights remain fixed; only the adapter parameters are trained. This creates a lightweight, modular way to adapt the model.

Architecturally, adapters are typically placed inside transformer blocks between the sublayer normalization and residual connections or between the feed-forward and attention sublayers. A common design is a two-layer bottleneck MLP: a down-projection from the transformer hidden dimensionality $d$ to a smaller bottleneck dimension $r$, a nonlinearity (such as ReLU), then an up-projection back to $d$. Formally, given an input hidden vector $h \in \mathbb{R}^d$, an adapter computes

$adapter(h) = W_{up} \sigma(W_{down} h)$

where $W_{down} \in \mathbb{R}^{r \times d}$, $W_{up} \in \mathbb{R}^{d \times r}$, and $\sigma(\cdot)$ is a nonlinearity. The adapter output is added as a residual to the original hidden representation:

$h' = h + adapter(h)$.

The number of parameters per adapter is $r \cdot d + r \cdot d = 2rd$, which for $r \ll d$ is small. Because adapters are inserted at multiple layers (often every transformer layer, sometimes multiple per layer), the total trainable parameter count grows linearly with depth but remains far below full-model size.

Intuitively, adapters learn task-specific corrections that map the pretrained representation space into the task-relevant subspace and then map back, preserving the original representation as a strong prior. The bottleneck enforces an information-limited update that reduces overfitting and encourages compact task-specific transformations.

Practical variants and considerations: Many papers explore variants: varying the placement (after attention, after feed-forward), choice of nonlinearity, adding layer normalization inside adapters, or using parameter-efficient initialization like zero initialization for $W_{up}$ (so that adapters initially behave like identity by producing zero output). Zero initialization often stabilizes training by starting from the behavior of the original pretrained network and gradually introducing task-specific deviations.

Adapters also support multi-task and multilingual setups elegantly: for each task you store a small set of adapter weights and swap them in at inference time while keeping the backbone fixed. This enables compact multi-task models that only differ in adapter parameters. Moreover, techniques like adapter fusion aim to compose multiple adapters to handle new tasks by combining previously learned adapters.

Limitations: While adapters are generally effective, their extra compute during inference (the forward computation through the adapter MLP) may add latency. The trade-off between parameter savings and computational cost per forward pass should be considered. Also, one must choose the adapter size $r$ carefully to balance performance and parameter efficiency.

# Prompt tuning and prefix tuning for transformer models

Prompt tuning and prefix tuning operate by optimizing input or internal prompts rather than changing the model weights. These methods exploit the fact that transformer models condition on input tokens or internal key/value pairs. By prepending learned tokens or key/value vectors that are trained per task, these methods steer the model’s behavior while leaving pretrained parameters frozen.

Prompt tuning (input-space): Here we learn a small sequence of continuous vectors, often called virtual tokens, that are prepended to the token embeddings of every input. If the model’s embedding matrix maps tokens to vectors in $\mathbb{R}^d$, a learned prompt is a matrix $P \in \mathbb{R}^{m \times d}$, where $m$ is the number of prompt tokens. During forward passes, the prompt vectors are treated like regular token embeddings. Only $P$ is trained while the rest of the model remains unchanged. The effective input sequence becomes $[P; x_1; x_2; \dots; x_n]$.

Intuition: The learned prompt vectors provide a continuous conditioning context that can steer the model's internal activations toward task-specific behaviors. Because $m$ is small (often dozens), the number of trainable parameters is small. Prompt tuning works particularly well with very large pretrained language models where the model can absorb significant instruction-like conditioning via a small number of tokens.

Prefix tuning (internal-space): Prefix tuning generalizes this idea into the attention mechanism. Instead of adding virtual tokens at the input, prefix tuning learns small sets of continuous key and value vectors that are prepended to the keys and values in each attention layer. Let the attention in a transformer layer compute attention between queries $Q \in \mathbb{R}^{n \times d_k}$ and keys $K \in \mathbb{R}^{(m+n) \times d_k}$ and values $V \in \mathbb{R}^{(m+n) \times d_v}$. Prefix tuning learns $K_{prefix} \in \mathbb{R}^{m \times d_k}$ and $V_{prefix} \in \mathbb{R}^{m \times d_v}$ per layer. The prefix vectors are concatenated to the layer’s keys and values, changing the attention outputs. Only the prefix vectors are trained. Because these vectors live inside attention, they can have more direct influence on the model’s multi-head attention patterns than input-space prompts.

Key properties and trade-offs: Prompt and prefix tuning are extremely parameter-efficient: a handful of prompt tokens or small prefix lengths correspond to a small number of parameters relative to the whole model. They can be adapted and swapped quickly, enabling many task-specific prompts for a single shared backbone.

However, these methods typically rely on the pretrained model’s ability to use the extra conditioning effectively. Prompt tuning is most successful with very large models (e.g., hundreds of millions to billions of parameters), where the model’s representation space is rich and flexible. For smaller base models, prompt tuning may degrade more versus adapters or LoRA. Another limitation is that input-space prompt tokens may alter tokenization or length-dependent behaviors and can be sensitive to prompt length and initialization strategies. Prefix tuning, by adding per-layer key/value vectors, can have larger memory costs if one needs distinct prefixes for many layers and tasks.

Initialization strategies: Prompt vectors can be initialized randomly, by sampling from the embedding distribution, or by copying embeddings of natural tokens (e.g., task-relevant words). Prefixes often benefit from careful initialization and may use a small MLP to map a lower-dimensional prompt into per-layer key/value vectors, reducing parameter count and enforcing shared structure across layers.

Practical use: Prompt and prefix tuning excel when you need ultra-low storage per task (kilobytes to megabytes) and have a large powerful backbone. They enable fast personalization and ensemble-like combinations (e.g., concatenating prompts), but may be less robust than adapter/LoRA approaches when tasks require deeper representational changes.

# Low-rank adaptation (LoRA): formulation and practice

Low-rank adaptation (LoRA) provides another effective and mathematically principled route to PEFT. The central idea is to restrict updates to certain weight matrices to lie in a low-rank subspace during adaptation. Instead of changing a pretrained weight matrix $W_0 \in \mathbb{R}^{d_o \times d_i}$ directly, LoRA parameterizes the change as a product of two low-rank matrices:

$\Delta W = A B$

where $A \in \mathbb{R}^{d_o \times r}$ and $B \in \mathbb{R}^{r \times d_i}$ with $r \ll \min(d_o, d_i)$. The adapted weight used at inference becomes

$W = W_0 + \alpha \cdot \Delta W = W_0 + \alpha A B$

where $\alpha$ is a scaling factor (sometimes set to $1$ or tuned as a hyperparameter). During PEFT, $W_0$ is frozen and only $A$ and $B$ are trained.

Why low-rank? Many meaningful updates to a large parameter matrix can be well approximated with a low-rank correction, particularly if the kinds of transformations needed for a task share structure. Constraining the update to low rank reduces the number of trainable parameters from $d_o \cdot d_i$ to $r(d_o + d_i)$, which can be orders of magnitude smaller when $r$ is small.

Where to apply LoRA: In transformers, LoRA is often applied to the large projection matrices inside attention and feed-forward networks—commonly the query, key, value, or output projection matrices of multi-head attention. For example, updating the query projection $W_q$ as $W_q + \alpha A_q B_q$ allows the attention behavior to change in a structured way.

Practical implementation details:

- Freeze the original weight: $W_0$ stays constant throughout adaptation. This enables inexpensive storage of task-specific adapters: only store $A$ and $B$ (and optionally $\alpha$) for each task.

- Merge at inference or keep separate: For inference, one can either keep $W_0$ and compute $(W_0 + \alpha A B)x$ on the fly, or precompute and merge the low-rank correction into the dense weight to avoid extra computation. Merging is possible when you allow changed weights, but if you need to keep the base model unchanged and load many task-specific LoRA updates at runtime, you can compute the product $A(Bx)$ cheaply because $A$ and $B$ are small.

- Initialization: Initialize $A$ and $B$ with small values (e.g., $B$ randomly, $A$ zeros, or scaled random initializations) so the model’s initial behavior remains close to the pretrained model and training is stable.

- Rank selection: Choosing $r$ trades off parameter budget and expressivity. Small $r$ reduces parameters but may underfit; larger $r$ increases capacity but reduces parameter efficiency. Typical values vary depending on layer dimensionalities and tasks, but experiments often show that small ranks (e.g., $r$ between 4 and 64) work well for many NLP tasks.

Intuition: LoRA constrains the space of possible weight updates to a subspace spanned by the columns of $A$ and rows of $B$. This acts as a structured prior; if the optimal adaptation for a task lies near that subspace, LoRA achieves near-full-fine-tuning performance with far fewer trainable parameters. The product $A B$ can produce directional changes to the mapping learned by $W_0$ without altering $W_0$ itself.

Advantages: LoRA is computationally efficient because computing $\Delta W x$ can be done as $A (B x)$, which costs $O(r(d_i + d_o))$ per vector rather than $O(d_o d_i)$. It fits well into existing checkpoints: storing $A$ and $B$ per task is cheap, and adapters can be composed by summing multiple low-rank updates.

Limitations and caveats: LoRA’s expressivity depends on $r$ and on which matrices are adapted. If a task needs changes outside the spanned subspace, LoRA might be insufficient. Also, when merging updates for inference, you must either maintain multiple merged copies (one per task) or perform on-the-fly cheap computations using the low-rank factors.

# BitFit and other minimal-parameter approaches

BitFit is an extreme example of minimalist PEFT. The idea behind BitFit is to only fine-tune the bias terms in a pretrained model while keeping all other parameters frozen. For a linear layer with weights $W$ and bias $b$, activations are $Wx + b$. BitFit freezes $W$ and updates only $b$ during adaptation. Since the number of bias parameters is tiny compared to the full model, BitFit is extremely parameter-efficient.

Intuition: Bias terms shift activation thresholds and can produce meaningful changes in network behavior. Updating biases can produce global shifts in feature responses that can sometimes adapt the model enough for simple or label-shift tasks. BitFit is particularly appealing when task data is small or when storage constraints are extreme.

Performance and limitations: Empirically, BitFit yields surprisingly strong results on some tasks, often outperforming simple baselines and sometimes approaching more complex PEFT methods on certain classification or sequence-labeling tasks. However, it generally lags behind adapter and LoRA approaches for tasks that require changes in directional mappings or richer structural transformations of representations. Because biases represent a very constrained parameter space, they may be insufficient for tasks requiring representation learning rather than only threshold adjustments.

Other minimal approaches include:

- Layer normalization affine term tuning: Fine-tuning only the scale and shift parameters within layer norm layers (often two scalars per hidden dimension). This is a light-weight alternative to BitFit with slightly more capacity.

- Tuning only final classification head: For many classification tasks, training only the final linear head appended to a frozen backbone is a basic PEFT baseline.

- Sparse updates: Instead of restricting to bias or norm parameters, some methods pick a small subset of all weights (e.g., 1% of weights via top-gradient magnitude) and fine-tune only those. Such sparsity-based approaches can be competitive if selection is done with good heuristics or iterative pruning.

- Adapter hybrids at minimal scale: Tiny adapters or per-layer scalings (learned scalar multipliers on outputs) are sometimes used to get a middle ground.

These minimal approaches are simple and compute-light, and they can serve as practical baselines. Their performance is task-dependent: they can be effective when the pretrained model already encodes most needed structure and only small adjustments are required. For tasks demanding substantial representational changes, richer PEFT methods like adapters or LoRA may be necessary.

# Orthogonality-based finetuning approaches (concepts without specific novel methods)

Orthogonality-based finetuning is a conceptual family rather than a single dominant algorithm. The core idea is to restrict or bias parameter updates to be orthogonal (or near-orthogonal) to certain subspaces so as to prevent catastrophic forgetting, reduce interference with pretrained knowledge, or maintain favorable numeric properties.

One common conceptual goal is to update parameters in the subspace orthogonal to the dominant pretrained directions so that the pretrained behavior is preserved as much as possible while still allowing adaptation. Formally, suppose a layer’s weights or activations have principal directions identified by a subspace spanned by matrix $U$. Then one can constrain updates $\Delta \Theta$ to satisfy $U^\top \Delta \Theta \approx 0$, meaning that updates do not align with those dominant pretrained directions.

Why orthogonality might help: Pretrained models learn features that are broadly useful; updating along those directions can overwrite general capabilities. By constraining updates to orthogonal directions, one hopes to preserve these broadly useful features while enabling task-specific tuning in the complementary subspace. This is especially relevant in continual learning where preserving previous tasks is important.

Mechanisms to induce orthogonality:

- Constrained optimization: Add a penalty term to the adapted loss that encourages orthogonality to some reference subspace, for example $\lambda \|U^\top \Delta \Theta\|^2$. Optimizing with this regularization biases updates away from $U$.

- Projection-based updates: Compute gradient updates then project them onto the orthogonal complement of $U$ before applying them. If $P_\perp = I - U U^\top$ denotes the projector onto the orthogonal complement, update as $\Delta \Theta \leftarrow P_\perp \Delta \Theta$.

- Low-rank orthogonal parameterizations: Parameterize updates as products of matrices constrained to be orthonormal in some modes, which can help preserve numerical stability and gradient flow.

- Preserving Fisher information directions: In methods inspired by elastic weight consolidation (EWC), directions with large Fisher information are considered important and are protected; updates orthogonal to these directions reduce forgetting.

Practical considerations and limitations: Orthogonality constraints can be beneficial for multi-task learning, continual learning, and settings where preserving pretrained behavior is crucial. But computing subspaces (e.g., principal components or Fisher directions) may be costly and noisy. Also, orthogonality constraints might limit expressivity and make certain tasks harder if they require changing the protected subspace. One must balance preservation with adaptability.

In PEFT specifically, orthogonality ideas can be combined with low-rank approaches: for example, choose the columns of $A$ in LoRA to lie in a subspace orthogonal to certain principal components, or apply projection steps to adapter updates. Orthogonality-based priors can also be applied to prompt vectors or to the optimization trajectory (e.g., limiting parameter updates to orthogonal complements of previous tasks’ update spaces).

Although not as commonly packaged into a single off-the-shelf method as adapters or LoRA, orthogonality remains a useful conceptual tool for designing conservative, low-interference adaptation schemes and for analyzing why certain PEFT methods preserve pretrained capabilities better than others.

# Metrics for comparing PEFT methods (parameter count, performance, latency)

Evaluating PEFT methods requires multiple complementary metrics because the goal is to balance efficiency and effectiveness. Here are the principal metrics and considerations:

1. Trainable parameter count: This is the most basic measure of parameter efficiency. Report the number of parameters that are updated during adaptation (and sometimes the number of additional parameters introduced). Present this both as an absolute number and as a fraction of the base model’s total parameters $P$. For example, “updates 0.1% of parameters (1M parameters)”.

2. Storage per task: This measures how much disk or memory is needed to store task-specific state. For adapters, this includes adapter weights per task; for LoRA, the $A$ and $B$ matrices; for prompt tuning, the prompt vectors. Storage is important when you maintain many task-specific models. Note that some methods require storing multiple tensors across layers, affecting the total.

3. Performance (task metric): The primary use-case quality metric is downstream task performance (e.g., accuracy, F1, BLEU). Compare to baselines: frozen backbone with head tuning, BitFit, full fine-tuning, and other PEFT methods. Report the performance gap between PEFT and full fine-tuning. Include statistical significance where appropriate and report results across multiple tasks to identify method sensitivity.

4. Inference latency and computational overhead: Some PEFT methods add computation at inference time. Measure the increased latency and FLOPs relative to the base model (both per-token and end-to-end for entire examples). For example, adapters introduce per-layer MLP computation; prompt tuning can increase sequence length and thus attention cost; LoRA can be implemented with low overhead if computed as $A(Bx)$ but may still add cost in certain implementations. For deployment, actual wall-clock latency on target hardware matters more than theoretical FLOPs.

5. Training memory and time: Measure GPU memory consumption and wall-clock training time. PEFT methods that freeze most weights save memory by avoiding optimizer state for frozen parameters. For some methods, training time is reduced because fewer parameters are updated, but this depends on how the method interacts with compute kernels and whether the base model is frozen.

6. Convergence behavior and stability: Report how quickly the method converges and whether it requires special tricks (e.g., warm restarts, careful initialization, or learning rate schedules). Methods that are brittle to hyperparameters are harder to adopt in practice.

7. Robustness and generalization: Evaluate robustness to distribution shifts, adversarial inputs, or small training datasets. Some PEFT methods generalize better on low-data regimes due to their inductive biases, while others may overfit.

8. Composability and modularity: Consider whether the method supports storing multiple task-specific modules that can be composed, fused, or switched at inference time. Adapter-based approaches and prompt-based approaches are often very modular; LoRA supports additive composition of low-rank updates.

9. Compatibility with quantization and model compression: For deployment, compatibility with quantized base models matters. Some PEFT modules may be easier to quantize or implement on devices. Report whether the method works with int8 quantized backbones or requires special treatment.

10. Privacy and communication cost: For federated or privacy-sensitive settings, compute the size of updates transmitted between client and server. Smaller parameter counts help reduce communication overhead.

Experiment design recommendations: When comparing methods, evaluate on a diverse suite of tasks (classification, generation, sequence labeling, etc.), across different base model sizes, and report per-task and aggregate results. Present trade-off curves: performance vs. number of trainable parameters, or performance vs. added inference FLOPs. Ablations on hyperparameters (adapter size $r$, prompt length $m$, LoRA rank) help identify practical operating points.

In summary, there is no single metric that completely captures a PEFT method’s utility. A combination of parameter count, storage cost, downstream performance, inference/training overhead, and operational considerations (modularity, robustness, compatibility) gives a fuller picture. Good reporting enables stakeholders to choose the method that best fits their constraints and priorities.

Conclusion

Parameter-efficient finetuning techniques enable practical deployment and adaptation of very large pretrained models by controlling the number of trainable parameters and the way task-specific information is stored. Adapters, prompt/prefix tuning, LoRA, BitFit, and orthogonality-informed approaches each offer different inductive biases and trade-offs. Adapters provide modular subnetworks inserted into model layers. Prompt and prefix tuning manipulate inputs or attention contexts to steer frozen models. LoRA constrains updates to low-rank subspaces for expressive yet compact adaptation. BitFit and similar minimal approaches update only a tiny set of parameters when small adjustments suffice. Orthogonality-based ideas aim to protect pretrained knowledge by directing updates to orthogonal subspaces.

Choosing a PEFT technique depends on the task’s complexity, available compute and storage, deployment latency requirements, and need for modularity or privacy. Evaluation should measure not only parameter counts but also downstream performance, latency, memory usage, and operational concerns. With thoughtful design and evaluation, PEFT makes it feasible to leverage powerful pretrained models across many tasks without incurring the costs of full retraining.
