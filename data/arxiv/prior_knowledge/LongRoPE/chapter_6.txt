# Introduction

Language modeling sits at the heart of modern natural language processing. At its core, a language model assigns probabilities to sequences of tokens; training such models and evaluating their behavior requires careful formulation of objectives, metrics, and evaluation protocols. In practice we train models using next‑token prediction with cross‑entropy loss, we measure model quality using metrics such as perplexity, and we must design evaluation procedures that cope with documents whose length exceeds the model's context window. This chapter explains the next‑token prediction objective and its optimization via cross‑entropy, develops the definition and intuition behind perplexity, and then covers practical evaluation protocols for long sequences: sliding windows, chunking, overlapping windows, and the correct aggregation of log‑probabilities. We also examine task formulations used to probe long‑context understanding (for example, passkey retrieval) and discuss statistical issues that arise when reporting results: sample size, variability, and how to assess significance.

Throughout the chapter we will use tokens as atomic units (subwords, bytes, or characters) and treat probabilities over token sequences. Mathematical expressions are written in LaTeX for precision. The goal is practical understanding: you should be able to read research that reports perplexity numbers and long‑context evaluations, reproduce those results, and reason about their statistical reliability.

# Next‑token prediction objective and cross‑entropy loss

The most common training objective for contemporary autoregressive language models is next‑token prediction. Given a sequence of tokens $x_1, x_2, \dots, x_T$, an autoregressive model defines a factorized joint distribution
\[
p_\theta(x_1, x_2, \dots, x_T) = \prod_{t=1}^T p_\theta(x_t \mid x_{<t}),
\]
where $x_{<t}$ denotes the prefix $(x_1,\dots,x_{t-1})$ and $\theta$ denotes the model parameters. Training encourages the model to assign high probability to the true next token at each position given the preceding context.

To operationalize this, we minimize the (average) negative log‑likelihood of the training data under the model. For a single sequence $x_{1:T}$ this objective is
\[
\mathcal{L}(\theta; x_{1:T}) = -\sum_{t=1}^T \log p_\theta(x_t \mid x_{<t}).
\]
Dividing by $T$ gives the average negative log‑likelihood per token. When training on a dataset consisting of many sequences, we average this loss over sequences and typically minimize it via stochastic gradient descent or variants thereof.

Cross‑entropy loss is the same quantity expressed relative to the empirical distribution of next tokens given contexts. Let $q(x_t \mid x_{<t})$ be the true conditional distribution (which in practice is a delta at the observed token). The cross‑entropy between the empirical distribution $q$ and the model $p_\theta$ at a single step is
\[
H(q, p_\theta) = -\sum_x q(x)\log p_\theta(x).
\]
Since $q$ places all mass on the observed token $x_t$, this reduces to $-\log p_\theta(x_t \mid x_{<t})$. Averaging across positions and examples yields the expected cross‑entropy loss.

It is useful to connect cross‑entropy to the Kullback–Leibler (KL) divergence. If we had access to the true distribution $p^\star$ over full sequences, the expected negative log‑likelihood under $p_\theta$ would be
\[
\mathbb{E}_{x\sim p^\star}[-\log p_\theta(x)] = H(p^\star) + D_{\mathrm{KL}}(p^\star\|p_\theta),
\]
where $H(p^\star)$ is the entropy of the true distribution and $D_{\mathrm{KL}}$ is nonnegative. Minimizing expected negative log‑likelihood is therefore equivalent to minimizing KL divergence to the true distribution; the irreducible lower bound is the entropy $H(p^\star)$. In practice the empirical cross‑entropy computed on data is the training objective and the test cross‑entropy estimates how close $p_\theta$ is to the data distribution, up to sampling error and dataset mismatch.

A few practical points about next‑token training deserve emphasis. First, the objective naturally handles variable‑length sequences and conditions on arbitrary prefixes. Second, if the model uses teacher forcing (feeding ground truth prefixes during training), training and evaluation differ: during autoregressive generation the model conditions on its own previous predictions; however, cross‑entropy training remains the standard because it provides stable gradients and direct probabilistic interpretation. Third, when training on long documents, practitioners often segment data into fixed‑length windows (possibly overlapping) both for computational tractability and for aligning batches; we will revisit how segmentation affects evaluation later.

# Perplexity: definition, interpretation, and calculation

Perplexity is the most common single‑number metric used to summarize how well a language model predicts text. It directly relates to cross‑entropy and has an intuitive interpretation as "effective branching factor" — the average number of choices the model is uncertain between at each token.

Formally, for a model $p_\theta$ and a test sequence $x_{1:T}$, the average negative log‑probability (base $e$) per token is
\[
\mathrm{NLL} = -\frac{1}{T}\sum_{t=1}^T \log p_\theta(x_t\mid x_{<t}).
\]
Perplexity is defined as the exponential of this average negative log‑probability:
\[
\mathrm{Perplexity} = \exp(\mathrm{NLL}) = \exp\left(-\frac{1}{T}\sum_{t=1}^T \log p_\theta(x_t\mid x_{<t})\right).
\]
If logs are computed in base 2, people sometimes report $2^{\mathrm{cross\mbox{-}entropy}}$, but the base choice only rescales the cross‑entropy; perplexity is usually presented as a positive real number independent of base when the same base is used consistently.

Intuition for perplexity can be gained from simple examples. If at every position the model assigns probability $1/V$ uniformly across a vocabulary of size $V$, then $p_\theta(x_t\mid x_{<t}) = 1/V$ and NLL $=\log V$, so perplexity $=V$. Thus perplexity equals vocabulary size for a uniform model. If the model is more confident and assigns higher probability to the true token, perplexity decreases. A perplexity of $10$ suggests that on average the model is as uncertain as choosing uniformly among 10 equally likely tokens.

Perplexity also has an interpretation in terms of compression. The expected negative log‑likelihood is the expected number of nats (if natural log used) required to encode each token under Shannon coding using the model's predicted distribution. Perplexity $\exp(\text{NLL})$ then expresses the average codebook size exponentiated back into the token space: lower perplexity corresponds to shorter expected code length, and thus better modeling for compression.

Calculating perplexity in practice requires care when sequences cross evaluation boundaries or when stateful models (e.g., caches) are used. When evaluating on a corpus of multiple sequences, we compute the total negative log‑probability summed across all tokens in the corpus and divide by the total number of tokens. That is, for dataset sequences indexed by $i$ with lengths $T_i$, total NLL is
\[
\mathrm{NLL}_{\mathrm{dataset}} = -\frac{1}{\sum_i T_i}\sum_i \sum_{t=1}^{T_i} \log p_\theta(x_{i,t}\mid x_{i,<t}),
\]
and perplexity is $\exp(\mathrm{NLL}_{\mathrm{dataset}})$. This weighted averaging ensures that longer sequences contribute proportionally.

Finally, attention must be paid to tokenization. Perplexity depends on token granularity: character‑level models will have different perplexities than subword models. Therefore comparisons of perplexity are only meaningful when tokenizer and evaluation data are identical. In research reports always specify tokenization, the exact test set, and whether the model had access to context beyond sequence boundaries.

# Sliding‑window evaluation protocols for long sequences

Modern large language models typically have a maximum context length $L$: they can attend to at most $L$ previous tokens when predicting the next token. Many evaluation datasets contain documents much longer than $L$, so we need protocols that measure model performance on long sequences while respecting the model’s context limit. Sliding‑window evaluation is the most straightforward and widely used approach.

In the sliding‑window protocol, you move a fixed‑size window of length $L$ across a long sequence and evaluate the model’s next‑token probabilities for tokens that fall inside each window, typically excluding tokens for which preceding context is truncated in undesired ways. Concretely, consider a long sequence $x_{1:N}$ with $N \gg L$. For offsets $s = 0, \Delta, 2\Delta, \dots$ (where $\Delta$ is step size, commonly 1 or a smaller stride), define a window $x_{s+1:s+L}$ (indices capped at $N$). For each window, compute the model’s conditional probabilities for tokens in some target subset of positions inside that window, for example the last $K$ tokens or the single token immediately following the window, depending on the evaluation objective.

There are multiple choices to make that affect interpretation and comparability:

- Window stride $\Delta$: Setting $\Delta=1$ yields maximal overlap: every token (except those in the initial prefix) is evaluated with full preceding context up to $L$ tokens. Larger strides reduce computation but evaluate each token fewer times. Common practice is to use $\Delta=1$ when aiming for exact perplexity across the corpus, or use larger strides for efficiency when approximations suffice.

- Which tokens are scored within each window: One can score only the final token (the token at position $s+L$) in each window, or score a chunk of trailing tokens. Scoring only the final token maps cleanly to streaming generation evaluation, while scoring multiple tokens per window is more efficient but requires careful aggregation to avoid double‑counting.

- Warm‑up context and document boundaries: When a window starts near the beginning of a document, the available context may be less than $L$. You must decide whether to treat missing tokens as absent context (i.e., evaluate with shorter context) or to prepend special tokens or padding; both decisions affect computed probabilities.

Sliding‑window evaluation approximates the ideal where each token is evaluated using all available context up to $L$ tokens. It naturally handles long documents by always giving the model the nearest $L$ preceding tokens. However, because windows overlap, many tokens will be evaluated multiple times under different contexts; this requires a principled way to aggregate scores, discussed in a later section.

There are variants of sliding‑window evaluation tailored to different experimental goals. For example, if you want to measure performance as a function of context length, you can evaluate tokens using windows truncated to different context sizes and then plot metrics (cross‑entropy, accuracy) versus context length. If the interest is in the model’s ability to use distant information, you can ensure the golden token’s last occurrence in context appears at a specific distance behind the target and then measure log‑probability gain relative to shorter contexts.

In summary, sliding‑window evaluation provides a practical, principled way to evaluate models on long sequences given finite context length. Choices of stride, scoring positions, and handling near‑boundaries must be made explicit and kept consistent across models to ensure fair comparisons.

# Chunking, overlapping windows, and aggregation of log‑probs

When applying sliding windows to evaluate long sequences, overlapping windows naturally lead to multiple predictive probabilities for the same token. Aggregating these multiple evaluations into a single corpus‑level metric requires care to avoid bias. The appropriate aggregation depends on what quantity you want to estimate.

The simplest and most statistically principled approach for computing overall perplexity on a long sequence is to compute the log‑probability of each token under the model using exactly the context that would be available in real usage, and to sum those log‑probabilities once per token. If the evaluation uses a sliding window with stride $1$ and for each position $t$ you use the window $x_{t-L+1:t}$ (or the longest available prefix up to $L$ tokens), then each token $x_t$ will be scored exactly once and the total log‑probability is simply $\sum_t \log p_\theta(x_t\mid x_{<t})$. This yields exact perplexity for the corpus under the constraint of maximum context length $L$.

However, for computational reasons one often scores multiple tokens per window or uses larger strides. Suppose one evaluates windows with stride $\Delta$ and within each window scores the last $K$ tokens. Then most tokens may be scored multiple times by different windows. Naively averaging log‑probabilities from different windows for the same token can distort the estimated likelihood because log‑probabilities are not additive across different conditioning contexts. Instead, a consistent method is to choose, for each token, exactly one context to use for scoring — typically the context that uses the most preceding information (i.e., the window that includes the longest available prefix). Practically this means that when windows overlap and you score trailing chunks, you should keep for each token the log‑probability produced by the window in which that token appears with the largest available left context. If you step with stride $\Delta < K$, that rule naturally picks the evaluation from the later window that contains more context.

Another valid aggregation technique is to assign weights to each token’s log‑probabilities so that each token contributes exactly once to the total. For instance, if each token is scored multiple times, you can average the log‑probabilities across evaluations of the same token and include that average once. Yet averaging log‑probabilities across contexts yields a different estimator than choosing the largest‑context evaluation: averaging treats each context equally, while choosing the largest context approximates actual deployment where the most context available is used for prediction. Which is appropriate depends on the evaluation goal; for perplexity relative to the model's use with maximum context, prefer the largest‑context selection.

More formally, let $\mathcal{C}(t)$ be the set of contexts under which token $x_t$ is scored (each context is a prefix with length at most $L$). Each scoring yields a log‑probability $\ell_{t,c} = \log p_\theta(x_t\mid c)$ for $c\in\mathcal{C}(t)$. We need a rule to produce a single $\hat{\ell}_t$ from $\{\ell_{t,c}\}$. Two common choices are:

1. Max‑context rule: $\hat{\ell}_t = \ell_{t,c^\star}$ where $c^\star$ is the context with largest length. This yields an estimate of the log‑probability under maximal available context and is usually recommended when evaluating models with fixed maximum context length.

2. Averaging rule: $\hat{\ell}_t = \frac{1}{|\mathcal{C}(t)|}\sum_{c\in\mathcal{C}(t)} \ell_{t,c}$. This yields the average performance across contexts, which may be of interest if you want to measure performance under a particular streaming or batching regime.

In either case, after selecting or aggregating per‑token log‑probabilities we compute the corpus NLL as $-\frac{1}{N}\sum_{t=1}^N \hat{\ell}_t$ and perplexity as $\exp(\mathrm{NLL})$.

There is a further subtlety when contexts overlap and the model has stateful components beyond the attention context (for example, a recurrent cache or mutable internal state that depends on predictions). During evaluation, you should ensure that the model's state corresponds to conditioning on the ground‑truth prefix rather than on its own predictions; that means using teacher forced contexts for scoring. If the model uses any external cache or memory that would be present during generation, you must decide whether to initialize or populate that memory during evaluation and keep this protocol consistent across models.

Finally, chunking strategies can improve computational efficiency. Instead of sliding by one token, you can chunk the sequence into contiguous segments (chunks) of length $C$ and within each chunk score all tokens using context that includes up to $L$ prior tokens (which may include tokens from previous chunks). Chunking with careful bookkeeping of which tokens have already been evaluated using larger context reduces redundancy and maintains correctness. Practically, implementers often process windows that cover an evaluation block and ensure that each token's log‑probability stored comes from the window with the largest left context that was computed.

# Task formulations for long context evaluation (e.g., passkey retrieval)

Evaluation of long‑context capability goes beyond measuring perplexity: researchers design tasks that require the model to retrieve or use information from far back in a document. One illustrative task is passkey retrieval: a document contains a secret token or phrase (a passkey) deep in the context, and later the model is asked to reproduce or use that passkey. Designing such tasks requires careful control so that success genuinely indicates use of long context rather than exploiting spurious cues or shortcut patterns.

A typical passkey retrieval experiment proceeds as follows. Construct documents composed of some distractor content followed by a unique passkey string inserted at position $i$, and then an instruction or query at position $j>i$ that asks for the passkey or depends on it. During evaluation, the model is given the prefix up to the query and asked to generate or score candidate responses. If the model assigns high probability to the correct passkey (or outputs it when sampled greedily), this is evidence it retained or retrieved the passkey from memory despite intervening distractors.

Several design choices affect the interpretation of results. First, the uniqueness and unpredictability of passkeys: choose passkeys that do not appear elsewhere in pretraining data, or use synthetic random strings per example, to avoid memorization confounds. Second, the location of the passkey relative to the query determines the effective dependency length; by varying $j-i$ you can measure how performance degrades with distance. Third, distractor content matters: if distractors include tokens unintentionally correlated with the passkey, the model might exploit such correlations rather than actual retrieval. Randomized distractors reduce this risk.

Evaluation may be performed as generation (does the model produce the passkey?), as likelihood scoring (does the model assign higher probability to the correct candidate relative to distractors?), or as multiple choice. Likelihood‑based scoring is often preferable for precise measurement: compute the log‑probability the model assigns to the correct passkey sequence conditioned on the prefix and compare it to alternative strings. This yields a rank or cross‑entropy metric independent of decoding stochasticity.

Passkey retrieval is one of a family of long‑context tasks. Others include:

- Lookup tasks: a document contains key–value pairs; later the model is asked to output the value for a specific key. Difficulty scales with the number of pairs and the distance between insertion and lookup.

- Coreference and reasoning tasks: a long story establishes entities and relations early, and the model must resolve references or answer questions that depend on information introduced long before.

- Copying/denoising tasks: the model is trained or evaluated on its ability to reproduce substrings that appear far in context, measuring raw memory rather than reasoning.

- Streaming QA and summarization: the model must integrate information spread across long documents to answer questions or produce condensed summaries.

When reporting results on such tasks, specify the data generation procedure, how passkeys were sampled, whether multiple examples share the same passkey distribution, how ties and partial matches are handled, and whether the model had access to any retrieval index or external memory. It is also informative to present performance versus distance curves (accuracy or log‑probability as a function of the gap between passkey and query) and to compare to simple baselines (e.g., always guessing the most frequent token) to contextualize results.

Finally, be mindful of evaluation artifacts: if the model has an explicit mechanism like attention windows or chunked caches, performance might be sensitive to where chunk boundaries fall. Design experiments to average over such alignments or to control them explicitly.

# Statistical considerations: sample size, variability, and significance

Reporting a single number (perplexity or accuracy) is insufficient to characterize model behavior reliably. Any empirical evaluation is subject to sampling variability because test sets are finite and tasks include randomness (e.g., random passkeys or distractors). Proper statistical practices help determine whether observed differences are meaningful and reproducible.

First, sample size matters. For metrics like perplexity and average log‑probability, the standard error decreases with more evaluated tokens. If the per‑token variance in log‑probability is $\sigma^2$, then the standard error of the mean NLL over $N$ tokens is approximately $\sigma/\sqrt{N}$. In practice $\sigma$ can be estimated from the sample of per‑token log‑probabilities. For accuracy metrics (binary correctness per example), the standard error of the mean accuracy $p$ over $M$ independent examples is $\sqrt{p(1-p)/M}$. Thus to halve the standard error you must quadruple the number of examples; this scaling often explains why large evaluation sets are necessary to detect modest improvements.

Second, independence assumptions are often violated. Tokens within a document are correlated; examples generated from the same source or with similar structure can induce dependence. When using long documents, if you treat every token as an independent sample you will underestimate variability. A safer approach is to compute per‑document averages and treat documents as the independent units for variance estimation, or to use block bootstrap methods that respect intra‑document correlation.

Third, confidence intervals and significance testing help determine whether differences between models are due to chance. For continuous metrics like NLL, compute a paired difference for each independent evaluation unit (e.g., document) between models A and B; the mean and standard error of these paired differences yield a t‑statistic and a confidence interval. Paired tests are more powerful than unpaired ones because they control for per‑example difficulty. If the per‑document differences are not approximately normally distributed, use nonparametric methods (e.g., the Wilcoxon signed‑rank test) or bootstrap confidence intervals.

Bootstrap resampling is particularly useful: resample evaluation units with replacement many times (e.g., 1000 bootstrap samples), recompute the metric difference for each resample, and use the empirical distribution to obtain confidence intervals. Ensure you bootstrap at the correct level (documents or examples) rather than tokens if dependencies exist within documents.

Fourth, correct handling of multiple comparisons matters. When comparing many models, contexts, or tasks, the chance of observing apparently significant differences by luck increases. Control the family‑wise error rate (e.g., Bonferroni correction) or the false discovery rate (e.g., Benjamini–Hochberg) when reporting multiple hypothesis tests.

Fifth, report effect sizes, not just p‑values. For instance, a statistically significant decrease in perplexity of 0.5% might be irrelevant in practice if it does not translate to perceptible improvements in downstream tasks. Present absolute and relative changes (e.g., perplexity from 12.0 to 11.8 is a relative improvement of 1.7%) and, where applicable, relate these to downstream task performance or human‑observable differences.

Sixth, account for evaluation noise due to randomness in task generation. For synthetic long‑context tasks like passkey retrieval with random passkeys, variance across trials can be large, so use a sufficiently large number of random seeds or examples. When evaluating generation metrics that involve sampling, either fix sampling seeds or run multiple generation replicates and aggregate.

Lastly, transparency in reporting prevents misinterpretation. Always state the size and properties of the test set (number of documents, token count, average document length), the evaluation protocol (sliding window parameters, chunking rules, which aggregation rule was used), and provide uncertainty estimates (standard errors or confidence intervals). These details allow readers to judge the reliability and practical significance of reported results and facilitate reproducibility.
