Chapter 9: Mixture-of-Experts (MoE) Architectures and Routing

Introduction

Mixture-of-Experts (MoE) models are a class of neural network architectures that aim to increase model capacity while keeping computation and memory costs manageable at inference and training time. The core idea is simple and powerful: replace a single dense transformation with a collection of specialized sub-networks (the "experts") and a routing mechanism (the "gate") that chooses which experts process each input. Because only a small subset of experts are active for any input, the model can scale to many more parameters than would be feasible if every parameter had to be applied to every token. This chapter explains how MoE layers are structured, how gating and routing decisions are made, how sparsity yields efficiency, and the sources and consequences of routing variability. We then examine the delicate issue of computing likelihoods consistently in MoE models and finish with practical trade-offs in memory, communication, and implementation when deploying MoE in distributed systems.

# MoE layer structure: experts and gating/routing networks

An MoE layer replaces a single monolithic transformation (for example, a feedforward or linear layer in a transformer block) with two main components: a set of experts and a gating network that routes inputs to experts. Formally, let the input to the MoE layer be a batch of token representations organized as a matrix $X \in \mathbb{R}^{N \times d}$, where $N$ is the number of items (tokens or positions) in the batch and $d$ is the representation dimensionality. The MoE layer contains $E$ experts, each implementing a function $f_e: \mathbb{R}^{d} \to \mathbb{R}^{d'}$ for $e = 1,\dots,E$. Typically, each expert is itself a small neural subnetwork, frequently a two-layer feedforward network with nonlinearity, parameterized independently for each expert. The output dimensionality $d'$ usually matches $d$ so that the layer can be plugged into existing models, but this can vary.

The gating network is another neural function $g: \mathbb{R}^{d} \to \mathbb{R}^{E}$ that, given an input vector $x$, produces a vector of routing logits $g(x) \in \mathbb{R}^{E}$. These logits are transformed into routing weights via a softmax or related operation to yield a probability distribution over experts for each input. The gating network is usually much smaller than the experts and often implemented as a single linear projection followed by optional normalization and temperature scaling. For a token $x_i$, the gate computes logits $l_i = W_g x_i + b_g$ where $W_g \in \mathbb{R}^{E \times d}$ and $b_g \in \mathbb{R}^{E}$, and then converts $l_i$ to scores.

There are different design choices for the gating output. In a dense gating design, the gate produces a full probability distribution over experts and the outputs of all experts are combined via a weighted sum. In a sparse gating design, the gate selects a small subset of experts for each input (often just one or two) and routes the input only to them; the other experts are not evaluated for that input. Sparse gating is the common choice for modern large-scale MoE models because it preserves activation sparsity and computational efficiency while allowing the total number of expert parameters to grow with $E$.

The MoE layer then computes outputs by applying the selected experts to each input and combining the expert outputs according to the gating weights. If a single expert is selected for $x_i$, the output is simply $y_i = f_{e^*}(x_i)$ where $e^*$ is the chosen expert, possibly scaled by a gating weight. If multiple experts contribute, the output is a weighted sum. In batched implementations, routing maps inputs to experts and forms per-expert input buffers; each expert processes its assigned inputs in a minibatch, and the expert outputs are returned and scattered back to their original positions in $X$.

# Top-k gating, load balancing, and auxiliary losses

Top-k gating is the most widely used sparse gating mechanism in MoE layers. For each input $x_i$, the gate computes logits $l_i \in \mathbb{R}^{E}$ and the top-$k$ experts with the largest logits are selected. Common choices are $k=1$ (top-1) or $k=2$ (top-2). Once the top-$k$ logits are identified, they are converted into normalized weights by applying softmax to just those $k$ entries, producing weights $w_{i,e}$ for the selected experts. Only the selected experts receive and process $x_i$, and the final output for $x_i$ is the weighted sum of the outputs from the selected experts: $y_i = \sum_{e \in \text{TopK}(l_i)} w_{i,e} f_e(x_i)$.

While top-k gating implements sparsity and reduces computation, it introduces a significant practical challenge: load imbalance. If the gating network routes most inputs to a small subset of experts, those experts become hotspots—receiving far more traffic than others—causing inefficient use of parameters and hardware. Load imbalance increases per-step computation on the overloaded devices, causes queuing and straggling in distributed settings, and limits effective model capacity because many experts remain underutilized.

To address this, training typically adds auxiliary losses that encourage balanced use of experts. Two commonly used measures are the load vector and the importance vector. The importance of an expert is the summed gating probability across the batch: Importance$_e = \sum_{i} p_{i,e}$ where $p_{i,e}$ is the final softmax weight given by the gate for input $i$ and expert $e$. The load is the count (or expected count) of tokens routed to an expert: Load$_e = \sum_i \mathbb{I}[e \in \text{TopK}(l_i)]$ or in probabilistic formulations $\sum_i p^{\text{route}}_{i,e}$ where $p^{\text{route}}$ might be the probability that $e$ is selected in the stochastic gating scheme.

The auxiliary balancing loss commonly used is proportional to the coefficient of variation (or squared coefficient) of these quantities, pushing the distribution of tokens across experts toward uniformity. A typical auxiliary loss looks like $\lambda \cdot E \cdot \sum_e \text{Importance}_e^2$ with an appropriate normalization so that the penalty is minimized when importance is uniform. Another variant combines importance and load to capture both expected weight and raw count. The hyperparameter $\lambda$ controls the trade-off between encouraging balanced expert usage and preserving the primary task objective. If $\lambda$ is too large, the gate may be forced to route uniformly regardless of specialization, harming model performance. If $\lambda$ is too small, imbalance ensues. Choosing $\lambda$ and the exact form of the auxiliary loss often requires empirical tuning.

Beyond global balancing losses, other techniques help mitigate imbalance. Noise can be added to the logits before determining top-k (a technique called noisy gating), which increases exploration and reduces deterministic routing patterns early in training. Capacity constraints per expert are also used: each expert has a maximum number of tokens it can accept per minibatch; excess tokens are either dropped, sent to a backup expert, or redistributed. Capacity-aware routing, which considers both gate scores and current per-expert capacity, helps prevent catastrophic overloads and keeps the computational footprint bounded.

# Sparse activation: per-token expert selection and efficiency

Sparse activation is the defining property that makes MoE attractive for scaling. When only a few experts are activated per token, the effective computation per token remains small even as total model parameters grow linearly with the number of experts. Intuitively, for a batch of $N$ tokens with $k$ experts selected per token, the total number of expert evaluations is $Nk$ rather than $NE$, so compute scales with $k$ rather than $E$. If $k \ll E$, then very large $E$ (and thus many parameters) are affordable.

Practically, sparse activation is implemented by sending tokens to the subset of experts that the gate selects and computing expert forward passes only on those token subsets. Efficient implementation bundles all tokens assigned to the same expert into a contiguous mini-batch so the expert can be evaluated in one call. This reduces framework overhead and benefits from vectorization on accelerators. The scatter-and-gather pattern—scatter inputs to per-expert buffers, execute expert networks, and gather outputs back—dominates the runtime structure of MoE layers.

Sparsity also affects memory usage. Each expert's parameters must be stored in memory, and as $E$ grows, total parameter memory increases. However, because only a subset of expert activations are computed, activation memory remains proportional to $Nk$ times activation size rather than $NE$. This trade-off permits very large models where parameter memory is larger than computing all experts would allow, as long as parameter storage capacity (model parallelism, device memory) is available.

There are two angles of efficiency to consider: compute efficiency and hardware-utilization efficiency. Compute efficiency refers to the total number of floating-point operations. Sparse routing reduces FLOPs by a factor of about $E/k$ compared to a dense layer that applied all experts. Hardware-utilization efficiency refers to how well the hardware executes the operations without idle time or overhead. If token distribution among experts is highly imbalanced, some devices will be idle while others are overloaded, lowering utilization. Moreover, the scatter/gather communication between devices (or between host and devices) can incur overhead that outweighs savings in FLOPs if not carefully engineered. Thus, practical implementations must balance topological design, batching strategies, and routing constraints to realize theoretical computational savings.

# Routing variability across parameter updates and its effects

Routing variability refers to changes in how tokens are assigned to experts over the course of training or across parameter updates. Several sources contribute to this variability: parameter updates in the gating network itself, parameter updates in experts that affect their specialization and thus downstream gating behavior, stochastic elements like injected noise in gating logits, and input distribution shifts across batches.

At a fine scale, gating networks produce logits $l_i = W_g x_i + b_g$. As $W_g$ and $b_g$ are updated by gradient descent, logits for the same input representation can shift, leading to different top-k selections. Additionally, because input representations $x_i$ come from earlier layers that themselves change during training, even fixed gating parameters will see changing inputs and thus varying routing decisions. This dynamic is amplified in deep models: early training often exhibits high routing churn as different experts specialize and the gate explores assignments, while later training may settle into more stable routing patterns.

Routing variability has several concrete effects. First, it complicates gradient flow and credit assignment. If a token is routed to different experts across updates, the gradients for a particular expert are noisier and the expert's specialization may form more slowly. Second, variability interacts with load-balancing mechanisms: if the gate frequently moves tokens from one expert to another, balancing losses must adapt, and the benefit of balancing regularizers can change over time. Third, it affects determinism and reproducibility: different shuffles of data, different random seeds, or slight perturbations to model weights can change routing, yielding different per-token computation paths and possibly divergent model states.

From an optimization viewpoint, routing variability can be both beneficial and detrimental. Early exploratory variability helps experts find niches: small amounts of noise in gating logits encourage tokens to visit different experts so those experts can train on diverse examples and specialize. This exploration reduces the risk of dead experts that never receive gradient signal. On the other hand, excessive variability can prevent experts from specializing enough to be useful, since each expert sees too many different examples in quick succession and cannot accumulate a consistent gradient direction. Hence, practical systems use a combination of noise injection for exploration and auxiliary balancing losses plus training schedules that reduce noise or encourage stability once sufficient exploration has occurred.

Routing variability also impacts evaluation and debugging. Because the path taken by a token through an MoE network may change unpredictably across checkpoints, comparing per-token likelihoods, attribution, or intermediate activations between checkpoints requires care: some differences may be due to routing changes rather than learned representation changes. This complicates analysis that assumes a fixed computational graph per input.

# Computing likelihoods in MoE: consistency concerns

Computing likelihoods in models with stochastic or discrete routing raises conceptual and practical issues. For standard deterministic neural networks, the likelihood of a model under parameters $\theta$ for data point $x$ is well-defined: it is the output of the final softmax given the deterministic forward pass. In MoE with sparse, deterministic top-k gating, one may think the forward pass defines a deterministic computation graph and thus likelihoods are straightforward. However, two complications create consistency concerns.

First, if gating is stochastic (for example, if routing is sampled from a softmax distribution at training time or if noise is added to logits before top-k selection), then the model is a mixture model where the output distribution is a marginal over gating choices. Formally, if $z$ denotes the routing assignment and $p_\theta(y \mid x, z)$ is the output conditioned on routing $z$, then the overall predictive distribution is $p_\theta(y \mid x) = \sum_z p_\theta(y \mid x, z) p_\theta(z \mid x)$. If training uses samples of $z$ and maximizes likelihood estimates based on those samples, the estimated likelihood can be a biased or high-variance estimator of the true marginal likelihood. Correct computation of likelihoods for evaluation or for methods that rely on probability estimates must therefore marginalize over routing, which can be impractical when the space of routes is large.

Second, even with deterministic top-k gating at inference, the gate parameters and gating computations can be conditioned on random seeds, dropout, or temperature annealing schedules. If the gating involves heuristics like capacity constraints that drop excess tokens or reroute them deterministically based on order-of-arrival, the effective model used for generation or evaluation may differ from one used during training. These discrepancies can produce inconsistent likelihoods: the training objective optimized may not correspond exactly to the evaluation-time likelihood if the routing mechanism differs.

A practical approach to likelihood computation is to treat the gating decisions as part of the model's deterministic computation graph at evaluation time and compute conditional likelihoods accordingly. That is, fix the gate behavior (for example, deterministic top-k without added noise) and compute $p_\theta(y \mid x, z^*)$ where $z^*$ is the gate-determined routing. This gives a well-defined likelihood but corresponds to a conditional model that does not marginalize over alternative routings. If the gating is intended to be deterministic at inference, and stochastic only during training for exploration, reporting conditional likelihoods under deterministic routing is reasonable. However, one must be explicit about this, because these conditional likelihoods can differ from the marginal likelihood under stochastic gating.

When exact marginal likelihood is required (for example, for proper Bayesian model comparison or for likelihood-based calibration across models with different routing randomness), one must either sum over routing assignments or approximate the marginal by importance sampling, variational approximations, or by designing gates that produce low-variance marginal estimators. In many large-scale MoE deployments, the marginal is intractable and researchers accept conditional likelihoods with careful documentation of gating details.

Finally, consider the effect of routing variability on per-token likelihoods across checkpoints. If small parameter updates flip routing for a token, the computed likelihood for that token under the updated model could change discontinuously because the token now traverses different experts. Such discontinuities complicate training diagnostics that rely on smooth likelihood landscapes and can make likelihood comparisons across models or checkpoints nontrivial.

# Memory, communication, and implementation trade-offs

Deploying MoE architectures at scale requires thoughtful design choices about how to partition experts, where to place expert parameters, and how to manage the communication that arises from routing. The main resource trade-offs involve memory (where parameters and activations live), communication volume and latency (moving activations to experts across devices), and computational balance (so each device is neither idle nor overloaded).

Memory trade-offs primarily concern expert parameter placement. One strategy is to colocate a subset of experts on each device (expert sharding). If there are $E$ experts and $D$ devices, a natural choice is $E/D$ experts per device. A token routed to an expert on device $j$ must be communicated to device $j$, the expert computes its output, and the output must be communicated back. This scatter/gather across devices is the principal communication cost. If experts are duplicated across devices (replication), communication can be reduced at the cost of extra memory for storing replicated expert parameters. Replication helps when a small number of experts are very popular and would otherwise become communication bottlenecks; providing local copies lets many devices compute the expert locally, reducing cross-device transfers. However, replication increases parameter memory and complicates synchronization of expert parameters across replicas for consistent updates.

Communication costs scale with the number of tokens $N$ and with the per-token expert input and output sizes. For each token routed remotely, the activation vector of size $d$ must be sent to the expert's device and the result of size $d$ must be returned, so communication volume is approximately $2Nk d$ (ignoring protocol overhead) per layer per forward pass. In pipelined or multi-layer MoE architectures, these costs accumulate. Techniques to reduce communication include: compressing activations (quantization, reduced-precision transfers), batching routed tokens to amortize per-transfer overhead, and co-locating experts to reduce cross-device transfers.

Another major trade-off is selecting the granularity of model parallelism. Parameter parallelism maps slices of each expert across devices; expert sharding assigns whole experts to devices. Parameter sharding reduces redundant parameter memory but makes expert computation involve more collective communication during the forward pass. Expert sharding simplifies per-expert computation but means that different experts' parameters live on different devices, increasing the potential for communication. Choosing between these modes depends on device memory capacity, network topology, and the expected routing patterns.

Capacity constraints per expert also affect system behavior. Enforcing a hard limit on the number of tokens an expert can accept per batch stabilizes per-step compute and memory but requires strategies for handling overflow. Common overflow strategies include dropping tokens (which biases training), routing overflow tokens to a fallback expert (which can create hotspots), or keeping an overflow queue across microbatches (which complicates stateless training semantics). Capacity-aware gating—where the gate takes into account both score and current load—reduces overflow but requires synchronizing load information across devices, adding communication.

Latency and throughput are also influenced by the choice of $k$ and the batch size. Increasing $k$ raises per-token compute and communication proportionally, while increasing batch size improves amortization of communication overhead and makes expert batching more efficient. For low-latency inference use-cases, the scatter/gather pattern may introduce unacceptable latency unless experts are colocated or the network is extremely fast.

Implementation complexity is nontrivial. Efficient MoE requires custom kernels and communication primitives. Naive implementations that iterate over tokens and call expert networks individually will be orders of magnitude slower than vectorized implementations that batch tokens per expert. Framework-level support for dynamic sparse dispatch, efficient all-to-all collectives, and memory management across devices greatly simplifies implementation. Many research codebases implement MoE using an all-to-all collective that redistributes token embeddings so that each device receives the tokens assigned to its local experts, then runs local expert computations, and finally all-to-alls back to restore original ordering. While all-to-all is convenient and expressive, it can be costly on certain network topologies and scales poorly without high-bandwidth interconnects.

When designing an MoE system, practitioners must therefore balance these factors: how many experts to use given device memory (more experts increases parameter memory but can be split across devices); where to place experts with respect to computation and communication costs; whether to replicate popular experts; how to set capacity constraints and manage overflows; and how to schedule and batch computations to maximize hardware utilization. There is no one-size-fits-all solution; the optimal design depends on the hardware cluster (memory per device, interconnect bandwidth, latency), the expected traffic patterns (sequence lengths, batch sizes, distribution of gate outputs), and the application constraints (throughput vs. latency, reproducibility, and model maintenance).

Conclusion

Mixture-of-Experts layers provide a compelling avenue for scaling model capacity by separating the concerns of parameter size and per-token computation. The architecture relies on a gating network to route tokens to a small subset of expert sub-networks, enabling models with very large numbers of parameters but modest per-token compute. Top-k gating and auxiliary balancing losses are central to making MoE training practical, but they interact with routing variability driven by changing parameters and stochasticity. Sparse activation brings efficiency potential, but only if implementation challenges related to load balancing, memory placement, and communication are addressed. Finally, computing likelihoods in MoE involves careful definitions: conditional likelihoods under fixed routing are straightforward, but marginal likelihoods over stochastic routing are costly to obtain and may be required depending on the application. Understanding these interlocking aspects—architecture, routing, variability, likelihood semantics, and systems trade-offs—is essential for both using MoE models effectively and for interpreting research that explores their behavior.
