# Introduction

Running reinforcement learning (RL) at large scale with large language models (LLMs) is as much an engineering challenge as it is an algorithmic one. The algorithms — policy-gradient methods, actor-critic variants, and on-policy techniques like Proximal Policy Optimization (PPO) — provide the mathematical backbone, but practical success depends critically on the infrastructure that generates rollouts, batches experiences, stores checkpoints, and coordinates distributed computation. This chapter explains the operational building blocks that make large-scale RL with LLMs feasible and stable: how to generate and manage rollouts; how to batch and minibatch data for gradient updates; how to handle partial or multi-turn episodes; differences between inference and training engines and why likelihood recomputation matters; how to make checkpointing and reproducibility robust; and how to diagnose and mitigate communication and memory bottlenecks in distributed systems.

Throughout, assume the RL setting typical for LLM fine-tuning: a policy parameterized by a neural network $\pi_\theta(a\mid s)$ that produces tokens (actions) conditional on context (state), a reward model $r(s,a)$ or scalar reward per episode, and an update rule such as PPO that uses on-policy rollouts to compute gradients. Much of the discussion applies to other on-policy methods or to off-policy methods that still require large numbers of actor-generated sequences.

# Rollout generation pipelines and query sets

Rollouts are the raw data for on-policy RL: sequences of states, actions, and rewards produced by the current policy. In the LLM setting a rollout is typically a conversation or prompt-response sequence in which the model generates one or more tokens or utterances conditioned on prior tokens and possibly external context. Designing the rollout generation pipeline requires addressing sampling strategy, diversity, environment interface, caching, and quality control.

First, clarify the notion of a query set versus a rollout. A query set is a collection of prompts or contexts that you issue to the policy to obtain responses. It can be static (the same prompts reused each epoch) or dynamic (sampled from a distribution, replay buffer, or collected from live traffic). Rollouts are the actual sequences returned by the model for each query; they include model outputs, logits (for later likelihood computation), and any metadata such as sampling temperature, top-k/top-p settings, or prompt IDs.

A critical design choice is whether your rollout pipeline is on-policy or quasi-on-policy. True on-policy requires that gradients are computed using trajectories sampled from the current policy; when rollouts are generated by a slightly older policy, importance weights or trust-region constraints (as in PPO) must correct the distributional shift. In practice, many systems generate rollouts asynchronously: multiple actor machines sample from versions of the model that lag the current learner. This increases throughput but introduces bias that must be controlled. PPO is robust to small shifts because it clips ratios, but you should track the average "KL drift" between the policy used to generate rollouts and the policy being updated.

Practical pipelines include components for: generating tokens (the actor code), collecting and storing logits and token-level meta-data, computing per-episode rewards (which may involve post-processing, human feedback models, or reward models), and exporting data to the learner. To scale, separate the actor fleet (many copies of the model generating rollouts) from the learner (which performs expensive backprop). Use compact, portable formats for rollouts — store prompt IDs, token sequences, and compressed logits if possible. If you will recompute likelihoods later, storing raw tokens and RNG seeds may be enough; if not, store the logits at generation time.

Query-set design matters for learning signal. Static evaluation sets measure progress but can lead to overfitting. Randomized or curriculum-based query selection can prioritize difficult or underperforming prompts. Importance sampling strategies can adjust the sampling distribution to emphasize rare but important cases. Finally, instrument your rollout pipeline to record throughput, latency, drop rates, reward distribution, and the policy-version ID used for each rollout; these signals are essential for diagnosing drift, stale data, or actor failures.

# Batching, splitting into mini-batches, and epoch-based updates

Once rollouts arrive at the learner they must be organized into batches for gradient computation. Batch design influences computational efficiency, variance of gradient estimates, and memory usage. The standard pattern in large-scale RL is to accumulate a collection of trajectories into a "batch" (sometimes called a batch of transitions or rollouts) and perform several training passes (epochs) over this batch, each time splitting the data into mini-batches for stochastic gradient descent.

Let the collected batch contain $N$ transitions (or token-level timesteps) indexed by $t$. Many RL objectives operate at the trajectory or timestep level. For example, the PPO surrogate objective for a timestep $t$ involves importance ratios
$$
r_t(\theta) = \frac{\pi_\theta(a_t\mid s_t)}{\pi_{\theta_{\text{old}}}(a_t\mid s_t)}
$$
and an advantage estimate $\hat{A}_t$. The mini-batch SGD update computes gradients of the clipped surrogate
$$
L^{\text{PPO}}_t(\theta) = -\min\big(r_t(\theta)\hat{A}_t, \ \text{clip}(r_t(\theta), 1-\epsilon, 1+\epsilon)\hat{A}_t\big).
$$

Key considerations in batching:

- Batch size and mini-batch size: Large batches reduce gradient noise and leverage hardware throughput, but excessively large batches can slow update frequency and lead to poorer generalization. For LLMs, token-level batching is common: count each generated token as a timestep and aggregate many tokens across episodes so that each SGD step processes millions of tokens. Mini-batches are subdivisions that fit device memory and allow multiple gradient steps per data pass.
  
- Epochs per batch: On-policy methods often perform several epochs over the collected data to improve sample efficiency. If you perform $E$ epochs over the same batch, ensure the policy used to evaluate importance ratios is $\theta_{\text{old}}$ (the policy that generated the batch) and that you recompute ratios as needed. Too many epochs increase the effective on-policy bias because the policy drifts further from $\theta_{\text{old}}$ between gradient updates; PPO clipping helps but monitor KL and clip fraction.

- Shuffling: Randomly shuffle transitions before splitting into mini-batches to reduce correlation and improve gradient variance. For sequence data where contiguous timesteps matter (e.g., for advantage estimation), you may shuffle at the episode level rather than the token level.

- Microbatching and gradient accumulation: If a mini-batch is still too large for GPU memory, apply microbatching: split a mini-batch further and accumulate gradients across microbatches before performing the optimizer step. This trades increased communication and longer iteration time for the ability to use larger effective batch sizes.

- Token vs sequence batching: Batching by tokens (packing multiple sequences into fixed-length tensors) maximizes device utilization for Transformers, but you must handle variable-length episodes, padding, and masks. Efficient padding and packing strategies reduce wasted computation.

Monitoring statistics like average gradient norm, fraction of clipped ratios (in PPO), and epoch-to-epoch change in loss helps set batching hyperparameters. In practical systems, tune the number of epochs $E$, mini-batch size, and learning rate schedule together; many teams scale learning rate roughly with the square root of batch size or use linear scaling rules depending on optimizer behavior.

# Partial rollouts and multi-turn episode handling

LLMs are commonly used in multi-turn interactions (dialogue) where an episode can span several model responses and user turns. Handling partial rollouts — sequences that are truncated because of time, compute constraints, or because the user interrupted the session — introduces special considerations for credit assignment and advantage estimation.

A partial rollout is a trajectory fragment that does not include a terminal reward or reaches an imposed truncation point. If you truncate an episode at time $T$, you cannot compute an exact return $G_t = \sum_{k=t}^{\infty}\gamma^{k-t} r_k$ for earlier timesteps without either estimating the tail value or discarding the fragment. A common approach is to use bootstrapping: append an estimate of the value function at the truncated final state $s_T$, $V_\phi(s_T)$, and compute Generalized Advantage Estimation (GAE) using the truncated sequence plus the bootstrapped tail. The GAE formula becomes
$$
\delta_t = r_t + \gamma V_\phi(s_{t+1}) - V_\phi(s_t),
$$
$$
\hat{A}_t = \sum_{l=0}^{L-1} (\gamma\lambda)^l \delta_{t+l},
$$
where for truncated sequences you include the bootstrap $V_\phi(s_T)$ in the computation for the last $\delta$.

When multi-turn episodes are broken across rollouts — say each actor produces only one model response per invocation — you should preserve contextual continuity by storing and passing the conversation history. Two practical patterns are (1) long-lived actor state: actors maintain conversation state and produce multiple responses sequentially, producing rollouts that are full episodes; and (2) short-lived partial-rollout actors: each actor invocation returns a single response with context and the learner or a central coordinator stitches multiple responses into an episode. The second approach is more scalable as it simplifies actor statelessness, but it requires careful handling of partial fragments and bootstrapped value estimates.

Reward shaping and delayed rewards are further complications. If the reward is only available at the end of an episode (e.g., human satisfaction measured after several turns), intermediate timesteps must attribute credit. Use reward shaping carefully to avoid introducing bias; prefer using learning signals like GAE with a value function trained to predict returns so that bootstrapping can propagate delayed rewards backward across partial rollouts.

Finally, partial rollouts complicate logging and evaluation: clearly mark truncated episodes and record whether a value bootstrap was used. During debugging, compare learning curves computed with and without bootstrapping to detect bias introduced by inaccurate value estimates.

# Inference engines vs training engines: likelihood recomputation and precision

A critical distinction in production RL is between inference engines (used on the actor fleet to generate rollouts) and training engines (used on the learner to recompute likelihoods and backpropagate). Inference engines are optimized for low-latency, high-throughput generation; training engines are optimized for gradient computation and memory efficiency. Discrepancies between them can create subtle bugs and instability.

One common necessity is likelihood recomputation. Many RL algorithms require the probability under the policy that generated each action, $\pi_{\theta_{\text{old}}}(a_t\mid s_t)$. If the actor recorded logits when generating the rollout, you could reuse that stored likelihood. However, storing logits for every token across millions of rollouts is expensive. The alternative is to recompute the likelihoods on the learner by running the model in a training engine to evaluate $\pi_{\theta_{\text{old}}}(a_t\mid s_t)$ given the saved tokens and contexts. Recomputing is cheaper in storage but sensitive to mismatch: the model used to recompute must be bitwise equivalent (same tokenization, same implementation of softmax/logit processing, same numerical precision) as the one used by the actor, otherwise computed importance ratios will be incorrect.

Precision differences are a frequent source of mismatch. Actors often run inference with mixed precision (e.g., FP16 or BFLOAT16) or quantized weights to accelerate sampling and reduce memory. Training engines, to save memory and increase throughput, may use different mixed precision settings or gradient accumulation rules. Low precision can change logits slightly; when exponentiated in a softmax, small logit shifts can produce non-trivial differences in likelihoods, especially when probabilities are sharply peaked. To avoid inconsistent importance ratios, do one of the following:

- Store per-token logits on the actors if storage permits. This makes recomputation unnecessary and ensures ratios use the exact generated logits.
- Standardize precision: run inference on actors with the same precision and library configuration as the learner's likelihood recomputation. This might mean using the training engine (or a bitwise-identical inference build) on the actors, trading some throughput for consistency.
- Compute and store log-probabilities immediately on the actors using the same code path that your learner will use (e.g., same tokenizer and stable-log-softmax implementation), then store compact float16 log-probs rather than full logits.

Another subtle issue is in sampling stochasticity. If actors sample actions with a certain RNG (e.g., top-p sampling), recomputing likelihoods must assume the same sampling support when computing the denominator of importance ratios; typically you recompute the exact probability of the sampled token under the policy, so only the logits matter, not the sampling algorithm. Nonetheless, ensure the tokenization path and special tokens are identical between inference and recompute code paths.

For algorithms that rely on action probabilities at both behavior and evaluation time (e.g., off-policy importance sampling), numerical consistency across engines is even more crucial. In practice, engineering teams enforce strict binary compatibility between actor and learner builds for likelihood-critical components, or choose to accept small numeric drift while monitoring its effect on KL and gradient stability.

# Checkpointing, reproducibility, and deterministic vs non-deterministic ops

Checkpointing and reproducibility are fundamental for debugging, experimentation, and safe deployment. Checkpoints should capture not only model weights but also optimizer state, learning rate scheduler state, RNG states for all relevant libraries (Python, CUDA, any environment RNGs), the exact commit/version of code, and metadata about the rollout batch and policy versions used.

Optimizer state: For momentum-based or adaptive optimizers (Adam, AdamW), optimizer slots (moment estimates, variance estimators) influence subsequent updates. Restoring only weights without optimizer state changes optimization dynamics and makes results non-reproducible. For very large models, saving full optimizer state may be expensive; strategies include periodic full checkpointing plus more frequent lightweight weight-only checkpoints, or storing optimizer state sharded across devices.

Determinism: GPUs and deep learning libraries include many non-deterministic primitives (optimized convolution kernels, asynchronous reductions, atomic updates). Non-deterministic ops can produce different outputs even with the same seed. For scientific reproducibility, set deterministic flags (for example, in PyTorch by setting cudnn.deterministic = True and cudnn.benchmark = False) and use deterministic kernels where available. Be aware that enforcing determinism can significantly slow training and in some cases is not fully achievable across all ops. For production stability, require reproducibility for critical components (e.g., unit tests and small-scale experiments) while accepting some nondeterminism at scale, as long as results are statistically stable.

RNG state management: Save RNG states to checkpoints so that replaying rollouts or resuming experiments produces comparable sequences. For distributed systems, each worker or actor should have deterministic, reproducible seeding that depends on its actor ID and a base seed. Ensure that checkpointing includes the RNG state for the learner and, if necessary, for actors in long-lived actor setups.

Atomic checkpointing and consistency: Large distributed checkpoints involve writing many files (sharded model weights, optimizer shards). Ensure checkpoints are written atomically or with versioned directories so that a partial write does not corrupt downstream resumes. A common pattern is: write new shard files with a temporary name, then move them into place and update a pointer file (e.g., "latest") atomically. Also save accompanying metadata (commit hash, hyperparameters, exact code version). During recovery, validate that all shards are present and checksummed.

Testing reproducibility: Implement small-scale deterministic runs that can be reproduced exactly on demand. Use these to verify that optimizer and RNG state saving/restoring works, that likelihood recomputation yields the same numbers, and to profile non-deterministic ops. For production runs, provide reproducibility windows: ability to replay an episode, regenerate an important rollout, or reproduce a training step for debugging.

# Communication and memory bottlenecks in distributed RL

Large-scale RL with LLMs typically separates actors (generating rollouts) and learners (updating the model). This architecture introduces communication and memory bottlenecks that must be engineered out.

Actors-to-learner bandwidth: Actors emit a steady stream of rollouts that must be transmitted to learners or to centralized storage. Each rollout can be large (many tokens, logits), so network bandwidth can be the limiting factor. Compress rollout data aggressively: store token IDs as 16-bit or 8-bit where possible, quantize logits, or transmit only selected statistics. Use batching at the transport level: aggregate many rollouts before sending and use high-throughput protocols (gRPC, zeroMQ with binary frames, or custom TCP-based protocols). For high-throughput fleets, use distributed storage (object stores with high ingress rates) rather than direct streaming to a single learner.

Learner-to-actors model sync: Learners periodically send updated model parameters to actors. With very large models, parameter sync is expensive. Common patterns include:

- Periodic snapshotting: send full model snapshots at relatively low frequency and let actors continue using slightly stale policies.
- Delta updates: send only parameter deltas or low-rank adapters to reduce bandwidth.
- Model serving: host a centralized inference service rather than pushing weights to actors; actors send prompts and receive generated tokens. This reduces actor complexity but increases inference service load.

Distributed training internals: On the learner side, distributed training uses model-parallelism (pipeline, tensor or expert parallelism) plus data-parallel SGD with AllReduce. Communication bottlenecks arise during gradient synchronization (AllReduce) where latency and bandwidth of the fabric determine step time. Overlap communication and computation where possible: gradient accumulation reduces frequency of AllReduce at the cost of increased local memory. Use fused AllReduce implementations and optimized NCCL primitives.

Memory bottlenecks: LLM training consumes vast memory for activations, optimizer state, and model parameters. To fit in available hardware, use techniques such as gradient checkpointing (recompute activations during backward pass), activation offloading, optimizer state sharding (ZeRO), and mixed precision. Each technique trades memory for compute or communication: ZeRO stage 3 reduces memory by partitioning optimizer state across devices but increases inter-node communication. Profile memory across all components (model, optimizer, activations, temporary tensors) and use a combination of methods tuned to your hardware.

Concurrency and contention: For actor fleets, contention on central queues or replay buffers can become a bottleneck. Use partitioned queues, hierarchical collectors, or gossip-based aggregations so that no single collector becomes saturated. For learners feeding multiple consumers (e.g., evaluation jobs), design backpressure mechanisms that prevent overload.

Latency sensitivity: For on-policy RL, timeliness of data matters. If actors produce rollouts much faster than the learner consumes them, the dataset may become dominated by trajectories generated under older policies; implement TTLs (time-to-live) or policy-version checks to discard overly stale rollouts. Conversely, if the learner is too slow, actor fleets may idle; dynamically scale actor count to match learner throughput, or provision extra learner capacity.

Monitoring and instrumentation: Track network utilization, queue depths, shard write times, GPU memory pressure, AllReduce times, and end-to-end sample-to-update latency. These metrics indicate where bottlenecks occur and inform optimizations such as increasing batch size, altering epoch counts, or modifying communication patterns.

# Conclusion

Successfully training LLMs with RL at scale requires careful orchestration of rollout generation, batching, partial-episode handling, numerical consistency between inference and training, robust checkpointing, and tightly engineered distributed communication and memory management. The algorithmic choices (e.g., PPO hyperparameters, advantage estimation) interact tightly with infrastructure choices (batch sizes, epoch counts, precision), so treat these as co-design problems rather than independent knobs. Instrumentation, deterministic testing at small scale, and incremental deployment (from local dev to pilot fleet to full production) are essential practices that prevent subtle bugs from scaling into costly failures. With these practical considerations in place, researchers and engineers can focus on improving reward models and policies, confident that the infrastructure will deliver reliable, reproducible training signals.
