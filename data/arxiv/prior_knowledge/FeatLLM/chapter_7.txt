Introduction

Transformer-based large language models (LLMs) are the dominant paradigm for contemporary natural language processing. They power applications ranging from search and question-answering to code generation and conversational assistants. This chapter explains the architecture and training of transformer LLMs, why scale and pretraining produce surprising capabilities, how inference behaves in practice (context windows and decoding controls), the practical choices you face when accessing models via APIs vs. fine-tuning them, and the fundamental limitations you must manage (hallucination, memorization, and biases). The material assumes familiarity with basic linear algebra and probability, but every key idea is developed with intuition and formulas where helpful.

# Transformer architecture: attention, positional encodings, layers

The transformer is a neural network architecture built around the attention mechanism. It was introduced to replace recurrence and convolution for sequence modeling by allowing the model to learn relationships between any pair of positions in the input directly. The core building block is the self-attention layer.

Self-attention operates on a sequence of token embeddings. Each token is projected into three vectors: a query $q$, a key $k$, and a value $v$. Let $Q$, $K$, and $V$ be the matrices whose rows are the queries, keys, and values for all tokens in the sequence. The attention output is computed as
$${\rm Attention}(Q,K,V) = {\rm softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right) V.$$
Here $d_k$ is the dimension of the keys (a scaling factor that stabilizes gradients), and the softmax is applied row-wise to produce attention weights for each query over all keys. Intuitively, the dot product $QK^\top$ measures compatibility between queries and keys (how relevant each key is to each query), the softmax turns those scores into normalized weights, and multiplying by $V$ produces a weighted combination of values. The result is that each output token is a learned mixture of all input token values, allowing the model to integrate contextual information from anywhere in the input.

Transformers typically use multi-head attention: several independent attention computations (heads) with different linear projections, whose outputs are concatenated and linearly mixed. This allows the model to capture different kinds of relations (e.g., short-range syntactic vs. long-range semantic) in parallel. If there are $h$ heads, each head projects into a lower-dimensional space and computes attention independently; the outputs are then combined.

Feed-forward sublayers follow attention. Each transformer block usually contains a multi-head self-attention layer followed by a position-wise feed-forward network (FFN), typically a two-layer MLP applied independently to each position. Residual connections and layer normalization around each sublayer stabilize training and improve gradient flow. A standard transformer block looks like:

1. LayerNorm
2. Multi-head self-attention + residual
3. LayerNorm
4. Feed-forward network + residual

Stacking many such blocks (dozens to hundreds in LLMs) yields deep contextual representations.

Positional encodings. Attention is permutation-invariant by itself: it treats the sequence as a set unless position information is introduced. Transformers inject position information into token embeddings so they can recognize order. Two common approaches are fixed sinusoidal encodings and learned positional embeddings. The sinusoidal scheme (used in the original transformer paper) adds for position $p$ and dimension $i$ the components
\[
\text{PE}(p,2i) = \sin\!\left(\frac{p}{10000^{2i/d_{\text{model}}}}\right),\qquad
\text{PE}(p,2i+1) = \cos\!\left(\frac{p}{10000^{2i/d_{\text{model}}}}\right).
\]
These functions let the model infer relative positions via linear operations. Learned positional embeddings instead allocate a vector per position and learn them together with the rest of the model, which often works slightly better in practice for large models. Recent variants also include relative positional encodings, which directly represent distances between tokens; these can be more effective for long sequences.

Complexity considerations. The attention operation requires forming the $QK^\top$ matrix, which has size $n\times n$ for a sequence length $n$. Thus the time and memory cost of full self-attention scale as $O(n^2 d)$ (more precisely, $O(n^2)$ in tokens times the per-element computation), which becomes the primary bottleneck for very long contexts. Many research efforts focus on approximations or sparsifications to reduce this quadratic cost.

# Pretraining objectives and data sources

Pretraining is the process of fitting transformer parameters on a very large corpus using one or more self-supervised objectives so that the model learns general linguistic, semantic, and world knowledge. The choice of objective and data has a large influence on the model’s downstream capabilities.

Common pretraining objectives include:

- Autoregressive next-token prediction (causal language modeling). The model is trained to predict the next token in a sequence given previous tokens, maximizing
\[
\sum_{t=1}^{T} \log P(x_t \mid x_{1:t-1}).
\]
This is the objective used by GPT-style models. It is simple, scales well with data, and directly aligns with generation tasks.

- Masked language modeling (MLM). Used by BERT and many bidirectional models, MLM randomly masks some tokens and trains the model to predict the masked tokens given surrounding context. The objective looks like
\[
\sum_{t \in \mathcal{M}} \log P(x_t \mid x_{1:T \setminus \mathcal{M}}),
\]
where $\mathcal{M}$ are masked positions. MLM produces strong bidirectional representations that are useful for classification and encoding tasks.

- Denoising objectives. More general denoising pretraining corrupts the input (deletions, replacements, shuffling) and trains the model to reconstruct the original. This includes SpanBERT-style masking and models like T5 which use a sequence-to-sequence denoising objective. Denoising is flexible and supports generation and understanding tasks.

- Prefix or mixture objectives. Some models combine autoregressive and encoder-decoder objectives, or train with multiple tasks to encourage both generation quality and strong representations.

Data sources. Pretraining datasets are large and diverse, typically comprising:

- Web text (crawled pages, filtered). Common sources are Common Crawl-based corpora and filtered web scrapes. These provide enormous breadth but require preprocessing to remove low-quality and duplicate content.

- Books and encyclopedias. Books and curated encyclopedias like Wikipedia provide high-quality, coherent long-form content that helps models learn discourse and facts.

- Code repositories. Public code from places like GitHub is included in many modern LLMs intended to support code generation and reasoning about algorithms.

- Dialogues, forums, and QA data. Optional datasets of conversations and Q&A can be included to better tune interactive and conversational behavior.

- Licensed and proprietary text. Some models use paywalled or specially licensed text to improve coverage in domains not common on public web text.

Data preprocessing and filtering matter. Raw web crawls contain noise, duplications, and personally identifiable information. Deduplication, language detection, quality filtering, and privacy-safe handling are essential steps. The mixture of sources and the volume of data shape what the model "knows" and which styles it can reproduce.

Scale interacts with objective and data. Larger models trained on more diverse and higher-quality data tend to acquire broader and deeper capabilities. However, more data and capacity also increase the chance the model memorizes specific training examples, which has implications for privacy and for controlling outputs.

# Capabilities arising from scale and pretraining

One of the most striking empirical findings is that increasing model size (parameters), dataset size, and compute often yields substantial qualitative changes in behavior. Many capabilities emerge or improve nonlinearly as you scale.

Knowledge: Large models store a surprising amount of factual and encyclopedic knowledge in their parameters. Given appropriate prompts, they can recall dates, definitions, and domain facts learned from pretraining data. This emergent factual recall enables answering many information-seeking queries without external retrieval, especially for common knowledge.

Language fluency and coherence: Pretraining on massive corpora gives models an ability to generate fluent, coherent text across many genres and styles. They learn syntax, idioms, and stylistic conventions, enabling applications like summarization, creative writing, and translation.

Few-shot and in-context learning: A distinctive capability of large autoregressive LLMs is in-context learning: when given a prompt containing task instructions and a few examples, the model can often generalize to new inputs without parameter updates. This enables few-shot and zero-shot use cases where the model adapts behavior during inference by conditioning on examples or instructions.

Reasoning and chain-of-thought: As scale increases, models sometimes perform multi-step reasoning better. Prompting techniques like chain-of-thought (where the model is asked to produce intermediate reasoning steps) can elicit more systematic problem-solving for arithmetic, logic, and commonsense reasoning tasks. These are not guaranteed or perfect, but scale plus the right prompting often improves performance.

Cross-domain skills: Larger models trained on diverse data gain competence in many domains (programming, scientific writing, casual conversation). They can produce code, debug, interpret mathematical expressions, and mimic specialized registers given appropriate prompts.

Robustness and generalization: Scale tends to improve robustness to distributional shifts encountered at inference time, although not uniformly. Larger models are generally better at adapting to new tasks from prompts and at avoiding simple errors, but they still fail on unfamiliar or adversarial inputs.

It is important to emphasize that these capabilities arise from statistical pattern learning over huge datasets; models do not have grounded understanding or sensory experience. Their strengths are practical and empirical: if similar patterns existed in the training data, the model can often replicate or interpolate them.

# Context window (prompt length) and its implications

The context window or prompt length is the maximum number of tokens a model can attend to in a single forward pass. For an LLM, the input is a sequence of tokens (prompt plus possibly previously generated tokens) of length $n$, and the attention mechanism considers interactions across all $n$ positions.

Practically, context length determines the kinds of tasks the model can handle in one interaction. Shorter contexts limit the size of documents you can summarize or the amount of conversation history you can maintain. Longer context windows enable summarizing long documents, multi-document synthesis, coding with large files, and maintaining extended conversations without losing earlier context.

Computational and memory costs scale with the square of context length for standard full attention: time and memory are approximately $O(n^2 d)$, where $d$ is the model dimension. Doubling the context length increases attention cost roughly fourfold. This makes very long contexts expensive and motivates architectural and algorithmic innovations to extend context affordably.

Context window also affects latency and pricing in API usage: longer prompts and longer responses consume more tokens, increasing API costs and inference time.

Strategies to manage limited context:

- Truncation or sliding windows. For streaming inputs, you can keep a sliding window of the most recent tokens. This discards older context but keeps computation bounded.

- Retrieval-augmented generation (RAG). Instead of putting large external documents into the context, you store documents in an index and retrieve relevant passages for each query. This allows a small context window to be used effectively for large knowledge bases.

- Summarization and compression. Pre-summarize long content into compact representations that fit within the context window, or iteratively summarize segments and combine summaries.

- Sparse or structured attention. Research models replace dense $n\times n$ attention with sparse patterns (local windows, global tokens) or approximations that reduce complexity, enabling longer effective context lengths for a given compute budget.

- Memory mechanisms and retrieval memories. Some proposals augment transformers with external memory modules that store compressed representations across interactions, enabling longer-term persistence beyond the immediate context window.

From a user and system perspective, understanding context limits is essential: always account for both prompt tokens and expected generated tokens, and use techniques like RAG or chunking when dealing with large documents.

# Temperature, top-p (nucleus) sampling, and decoding parameters

At inference time, a probabilistic language model defines a distribution $P(x_t \mid x_{1:t-1})$ over possible next tokens. Decoding is the procedure for converting these probabilities into a concrete output sequence. The choice of decoding algorithm has a large effect on diversity, quality, and determinism.

Temperature. Temperature $T>0$ rescales the logits before the softmax:
\[
P_T(x_t \mid x_{1:t-1}) \propto \exp\!\left(\frac{\log p(x_t \mid x_{1:t-1})}{T}\right).
\]
Equivalently, if $z_i$ are logits, probabilities become $\mathrm{softmax}(z/T)$. Lower temperature ($T<1$) sharpens the distribution, making high-probability tokens even more likely and yielding more deterministic, conservative outputs. $T=0$ is often implemented as greedy decoding (always pick the highest-probability token). Higher temperature ($T>1$) flattens probabilities and increases randomness and diversity.

Top-k and Top-p (nucleus) sampling. Top-k sampling restricts choices to the $k$ tokens with highest probability and samples uniformly from that set after re-normalization. Top-p (nucleus) sampling includes the smallest set of tokens whose cumulative probability is at least $p$ and samples from that set. Top-p is adaptive: it uses fewer tokens when the distribution is peaked and more when it is flat. These methods prevent sampling from very low-probability tokens that are likely to be incoherent, balancing creativity and safety.

Greedy and beam search. Greedy decoding picks the single most probable token at each step; it is fast but can lead to repetitive or suboptimal global sequences because local decisions don't account for future benefits. Beam search maintains $B$ best partial hypotheses at each step and selects the best complete sequence according to model score. Beam search is used primarily in tasks where maximizing the sequence probability aligns with quality (e.g., machine translation) but can produce generic or overly safe outputs when applied to open-ended generation.

Typical practical settings. For open-ended creative text, moderate temperatures (e.g., $T=0.7$) and top-p (e.g., $p=0.9$) are commonly used to balance diversity and coherence. For instruction-following or tasks requiring reliability (summaries, code), lower temperature (e.g., $T\le 0.2$) and even greedy decoding may be preferable. It helps to tune these parameters empirically for your use case.

Other decoding controls. Additional controls include repetition penalties, length penalties, and constraining token sets (e.g., forbidding certain tokens). These help avoid pathological behaviors like loops or irrelevant verbosity.

Understanding the interaction between probability calibration and decoding is important: a poorly calibrated model with overconfident probabilities can still produce low-quality outputs when beam search or greedy decoding is applied, and sampling-based methods may mask calibration issues by injecting randomness.

# API access models vs. fine-tuning access

When deploying or using LLMs, you typically choose between using a hosted API (inference-only) or obtaining model weights to fine-tune locally or in a managed environment. Each approach has trade-offs in cost, flexibility, latency, customization, and safety.

API access (hosted inference). Using a model via an API is the most common path for many applications. The provider hosts and manages the model, offering endpoints for generation, embeddings, and other services. Advantages include immediate access, no infrastructure management, automatic updates and safety filters, and often lower upfront cost. APIs typically support prompt-based usage, including few-shot and instruction prompts, and may offer specialized endpoints for chat, streaming completions, or embeddings.

Constraints of API access include limited ability to change model weights, constraints on prompt length, privacy considerations (sending user data to an external service), and per-token costs. Providers may offer options like instruction-tuned variants or specialized models.

Fine-tuning and model weights. Fine-tuning means updating model parameters on a domain-specific dataset to adapt behavior. Access to model weights enables fine-tuning and advanced customization: you can teach the model domain conventions, fix consistent output formatting, integrate proprietary data, or greatly improve efficiency for a narrow task. In addition to full fine-tuning, parameter-efficient techniques like adapters, LoRA (Low-Rank Adaptation), and prefix tuning allow you to adapt large models with far fewer trainable parameters and less compute.

Fine-tuning considerations: you need compute resources (often GPUs/TPUs), expertise in training, and careful dataset preparation. Overfitting, catastrophic forgetting, and degradation of general capabilities are risks if fine-tuning is not done properly. Fine-tuning also raises data governance issues: if the training data contains private information, you may increase the chance the model will reproduce it.

Hybrid approaches. Many workflows combine API usage and fine-tuning. For example, you might start with prompt engineering and retrieval augmentation using an API, then shift to fine-tuning a model (or an adapter) if latency, costs, or control requirements warrant it. Embeddings APIs provide a mechanism to build retrieval systems powering the model without changing its weights.

Versioning and reproducibility. With APIs, the provider controls model versions, which may change behavior over time. Fine-tuning and self-hosting give you deterministic control over model versions but require management of deployments and updates.

Privacy and data residency. If user data cannot be sent to third-party services, local fine-tuning or on-premise inference might be required. Some API providers offer enterprise contracts or opt-outs for data retention to address privacy concerns.

Cost and inference latency. Hosted APIs charge per token and offer high throughput via optimized inference infrastructure. Fine-tuning and self-hosting incur different cost structures: there are upfront model hosting and scaling costs and potentially lower per-inference marginal cost if you can amortize infrastructure.

In summary: use APIs for rapid development, broad capabilities without infrastructure burden, and tasks where customization needs are modest; use fine-tuning or local hosting when you require deep customization, control over data and model behavior, or need to avoid external data transfer.

# Limitations: hallucinations, memorization, and distributional biases

Despite impressive capabilities, transformer LLMs possess important limitations you must understand and mitigate.

Hallucinations. Hallucination refers to confident but incorrect or fabricated outputs. Since generative LLMs predict plausible continuations given training statistics, they can produce factual assertions unsupported by evidence. Hallucinations are particularly problematic in high-stakes contexts (medical, legal, scientific) where misinformation has consequences. Hallucination sources include gaps in training data, model overconfidence, and the fact that probability-optimal text may be plausible-sounding but false.

Mitigations include retrieval-augmented generation (where the model conditions on retrieved supporting documents), grounding outputs with citations and provenance, calibration and uncertainty estimation, post-generation verification by rule-based systems or fact-checking models, and human-in-the-loop validation.

Memorization and privacy. Large-scale models can memorize verbatim fragments from training data, including personal data or copyrighted text. Empirical studies show that with enough capacity and repetition, rare or unique sequences can be memorized and sometimes extracted by adversarial queries. This creates privacy risks and potential copyright infringement.

Mitigation strategies include rigorous data filtering, deduplication, differential privacy training techniques (which limit the influence of any single example on model parameters), monitoring for extraction attacks, limiting output length, and establishing policies about the types of data included in pretraining.

Distributional biases and fairness. Models inherit biases present in training data. These biases manifest as stereotypes, offensive language, or systematic underperformance on examples from marginalized groups. Because LLMs learn statistical correlations from large web datasets, they can perpetuate and amplify harmful patterns.

Mitigation requires multi-pronged approaches: curating and balancing datasets, applying bias-detection tools, using fine-tuning and reinforcement learning from human feedback (RLHF) to align outputs with safety norms, implementing content filters, and providing transparency about limitations. However, no mitigation is perfect: models can still reflect subtle and context-dependent biases.

Calibration and overconfidence. Language models can be poorly calibrated: their internal probabilities do not reliably reflect real-world correctness. A model may assign high probability to a false statement. Calibration techniques (temperature scaling, training with uncertainty objectives) and explicit uncertainty estimation (predicting a confidence score or offering multiple candidate answers) can help, but calibration remains an active area of research.

Vulnerability to adversarial prompts and distributional shift. Models can be manipulated by prompt engineering or adversarial inputs to produce undesired content. They also degrade when inputs are far from the training distribution. Robustness techniques, input sanitization, and careful prompt design can reduce but not eliminate these risks.

Compute and environmental costs. Training very large models consumes significant compute, energy, and resources. This has environmental and economic consequences and affects the sustainability and accessibility of large-scale model development.

Evaluation difficulties. Evaluating LLM outputs can be challenging: automatic metrics (BLEU, ROUGE, perplexity) do not always correlate with human judgments for open-ended tasks. Human evaluation, though more reliable, is expensive and subjective.

In practice, deploying LLMs responsibly means combining technical mitigations (retrieval, fine-tuning, filters), organizational policies (user disclosures, human oversight), and continuous monitoring. For research and applied work, always treat model outputs as probabilistic and potentially incorrect. Design pipelines that verify critical outputs, log interactions for auditing, and provide users with clear guidance about model reliability.

Closing remarks

Transformer-based LLMs are powerful tools that arise from the combination of attention-driven architectures, large-scale pretraining on diverse corpora, and scaling of compute and parameters. Their attention mechanism and layered structure let them model complex language patterns, and pretraining objectives endow them with broad capabilities. However, practical deployment requires attention to context window constraints, careful selection of decoding parameters, and a considered choice between API usage and fine-tuning. Most importantly, awareness of their limitations—hallucination, memorization, and bias—is essential for safe and effective use. Understanding these technical and practical aspects equips you to read current research, design experiments, and build applications that responsibly harness LLM capabilities.
