# Introduction

Large pretrained models, particularly large language models and foundation vision models, have shown remarkable capabilities across many tasks. However, fine-tuning these models by updating every parameter is often impractical: models can contain billions or trillions of parameters, making full fine-tuning expensive in terms of computation, memory, storage, and time. Moreover, updating the full model for every downstream task requires storing a separate full copy of the model per task.

Parameter-efficient fine-tuning (PEFT) methods address these problems by introducing only a small number of trainable parameters while keeping the pretrained parameters largely frozen. The goal is to adapt the model’s behavior for a new task with minimal additional storage and compute, often making it feasible to deploy many task-specific variants of a single base model. This chapter introduces the motivation behind PEFT, describes the principal families of methods (adapters, prefix tuning, prompt tuning, low-rank adaptation, IA3), explains when PEFT is a good choice relative to in-context learning and full fine-tuning, examines computation and memory trade-offs, and discusses how evaluation differs when you use tuning versus inference-only approaches.

# Motivation for parameter-efficient tuning

The fundamental motivation for parameter-efficient tuning stems from practical limits and organizational needs. Consider a pretrained model with $N$ parameters, where $N$ may be in the hundreds of millions to trillions. Updating all $N$ parameters for each downstream task is costly in several dimensions.

First, there is the training compute and memory cost. Gradient-based optimization requires storing parameter gradients and typically optimizer state (e.g., momentum, second-moment estimates) for every parameter. For large $N$, this increases GPU memory requirements and decreases throughput. Second, for storage and deployment, holding a separate full-weight checkpoint for each task multiplies storage costs by the number of tasks. Third, organizations often want to adapt a single model for many tasks, and shipping many full-weight models to production is operationally burdensome.

Parameter-efficient methods reduce the number of trainable parameters from $N$ to a much smaller number $M \ll N$, often by introducing task-specific modules or modifying a small subset of parameters while freezing the rest. This yields a set of benefits. Training becomes faster and requires less memory because the optimizer only maintains states for $M$ parameters. Storage per task shrinks to the size of the added parameters rather than the full model. And because the pretrained backbone remains unchanged, many task-specific adapters can be applied interchangeably at inference time, easing deployment.

Beyond engineering, there are empirical and safety motivations. When the upstream pretraining is extensive and the model already encodes useful representations, only a small, targeted change may be necessary to steer outputs toward a new task. Freezing the backbone reduces catastrophic forgetting of pretraining knowledge and can preserve broad generalization capabilities. Moreover, in sensitive domains, freezing the pretrained model and only storing small task-specific adapters can simplify auditing and provenance tracking.

Finally, PEFT creates an enabling technology for low-resource settings. If you have limited labeled data, a small number of trainable parameters can reduce overfitting compared to updating the entire network. This is analogous to classical practices such as linear probing, where a single linear classifier on top of frozen features often yields good performance with modest data.

# Adapters, prefix tuning, and prompt tuning

Three widely used families of PEFT methods are adapters, prefix tuning, and prompt tuning. They differ in how they introduce trainable capacity and where that capacity sits relative to the pretrained model architecture.

Adapters

Adapters insert small, task-specific layers into the pretrained model at one or more locations (typically between transformer sublayers or after attention/MLP blocks). A common adapter design is a two-layer bottleneck: given an intermediate layer activation $x \in \mathbb{R}^d$, the adapter computes

x' = x + U \phi(V x),

where $V \in \mathbb{R}^{r \times d}$ is a down-projection, $U \in \mathbb{R}^{d \times r}$ is an up-projection, $r \ll d$ is the bottleneck rank, and $\phi$ is a nonlinearity such as ReLU or GELU. The residual connection preserves the pretrained behavior when the adapter parameters are initialized near zero.

Adapters are powerful because they can be inserted at many depths of the model, allowing task-specific transformations of the representations at multiple scales. Because $r$ is small, the number of added parameters per adapter is $dr + rd = 2dr$ (plus any bias terms), which is tiny relative to $d^2$ in full layers. Training only the adapters keeps the core model weights frozen and reduces optimizer state size. Empirically, adapters often match full fine-tuning performance when enough adapters are placed and $r$ is chosen appropriately.

Prefix Tuning

Prefix tuning adapts a model by adding learned "virtual" key and value vectors to the transformer attention mechanism. For a given attention layer that computes queries $Q$, keys $K$, and values $V$ from token embeddings, prefix tuning prepends (for each head) learned prefix matrices $K_p$ and $V_p$ that are concatenated with the original $K$ and $V$ along the sequence dimension. During attention, the model attends to both original tokens and these virtual prefix tokens, which act as a persistent, learned context that conditions the model’s behavior.

Formally, if the original attention has keys $K \in \mathbb{R}^{T \times d_k}$ and values $V \in \mathbb{R}^{T \times d_v}$ for sequence length $T$, a prefix of length $L$ adds $K_p \in \mathbb{R}^{L \times d_k}$ and $V_p \in \mathbb{R}^{L \times d_v}$. Only $K_p$ and $V_p$ are trainable. Intuitively, the prefix functions like a fixed prompt that the model sees on every attention call, steering outputs in task-specific ways. Prefix tuning is particularly well suited to decoder-only models for conditional generation tasks.

Prompt Tuning

Prompt tuning trains only a set of input token embeddings that are prepended to the text input. Unlike prefix tuning, which modifies internal attention with learned key/value pairs, prompt tuning simply learns $L$ embedding vectors $E_p \in \mathbb{R}^{L \times d}$ that are combined with the normal token embeddings at the model input. During training, the base model is frozen and only $E_p$ is updated.

Prompt tuning’s simplicity is attractive: storage per task is a small $L \times d$ matrix. However, because it operates only at the input layer, it may need longer or more expressive prompts to match adapters or prefix tuning, especially for complex tasks. Prompt tuning is particularly effective when the model has strong in-context learning abilities and the task can be expressed via conditioning.

Comparison and trade-offs

Adapters operate throughout the network and can directly modify intermediate representations, often achieving higher performance for classification and structured tasks. Prefix tuning modifies attention behavior layer-by-layer but via virtual tokens; it is powerful for generation problems where conditioning is beneficial. Prompt tuning is simplest and smallest but may be less expressive, particularly on tasks that require deeper representational changes.

Design choices such as how many layers to insert adapters into, how many prefix tokens to use, and whether to tie parameters across layers affect the parameter count, performance, and computation. Initialization matters: adapters are often initialized so that they are near-zero at first, preserving pretrained behavior and ensuring stable fine-tuning.

# Low-Rank Adaptation (LoRA) and IA3 basics

Low-Rank Adaptation (LoRA) and IA3 are methods that change a subset of existing weight matrices instead of adding new modules. They exploit the observation that many useful updates live in a low-dimensional subspace.

LoRA

LoRA applies a low-rank decomposition to the parameter update of certain weight matrices while keeping the original weights frozen. Suppose a pretrained linear layer has weight $W_0 \in \mathbb{R}^{d \times k}$ and computes $Wx$ for input $x$. In LoRA, the modified computation becomes

W x = W_0 x + \Delta W x,  where  \Delta W = BA,

with $B \in \mathbb{R}^{d \times r}$ and $A \in \mathbb{R}^{r \times k}$ and $r \ll \min(d,k)$. Only $A$ and $B$ are trained; $W_0$ is frozen. The number of added parameters is $r(d + k)$, and inference computes $W_0 x + B(Ax)$. Because $r$ is small, this is efficient in storage and computation.

There are useful practical variants: one may only apply LoRA to attention projection matrices (e.g., query, key, value, or output projections), or to feed-forward matrices. LoRA is attractive because it directly modifies the linear maps the model uses, often producing strong performance with tiny $r$. It is also easy to merge the LoRA update into $W_0$ for inference if desired: after training, compute $W = W_0 + BA$ and discard $A,B$ as a single merged weight (though this loses the ability to keep a single frozen backbone and many small task adapters at runtime).

IA3 (Inverse Adapters for Attention and Activation Affine scaling)

IA3 takes a different approach: instead of adding new parameters or rank-decomposed updates, it introduces small per-feature scaling vectors that modulate activations. The core idea is to multiply certain intermediate activations by learned scaling vectors. For example, in a transformer MLP layer producing activations $h$ (dimension $d$), IA3 inserts a learnable vector $s \in \mathbb{R}^d$ and computes

h' = h \odot s,

where $\odot$ denotes elementwise multiplication. Similarly, IA3 can apply scaling to attention outputs per head or across channels. Because these are elementwise parameters, the number of added parameters equals the activation dimension per chosen layer, which can be much smaller than adding full matrices.

IA3 is very parameter-efficient: adding only a few scaling vectors across many layers often yields good adaptation. It is conceptually simple and avoids increasing the rank of weight matrices or changing attention mechanics. However, its expressivity is constrained by the per-feature, multiplicative form.

Comparison

LoRA provides a flexible and expressive change by adding a controlled low-rank additive update to key weight matrices. IA3 provides extremely compact multiplicative modulation of activations. Adapters and LoRA are additive—introducing new pathways—while IA3 is multiplicative. The right choice depends on task complexity, resource constraints, and whether it is desirable to merge updates into the frozen weights after training.

# When to fine-tune vs. when to use in-context learning

In-context learning (ICL) refers to conditioning the model at inference time with example input-output pairs (prompts) rather than updating any model parameters. The model uses the prompt to produce task-appropriate outputs. Deciding between parameter-efficient fine-tuning and in-context learning hinges on several considerations: task permanence, latency, data availability, sample efficiency, privacy, and robustness.

If the task demands repeated, low-latency inference in production, PEFT usually wins. In-context learning requires sending the prompt (which may include several examples) with every request; this increases latency and token-compute per request. Moreover, long prompts affect cost linearly. If you have many repeated calls, investing in a small adapter or LoRA module that permanently encodes the task eliminates prompt overhead.

When only a handful of examples are available and you want to try different tasks rapidly without training, ICL is convenient: it requires no training and can be tried instantly. For some tasks—particularly those where the model already exhibits strong in-context capabilities—ICL may achieve competitive performance without any parameter changes.

Data availability matters. If you have access to a moderate labeled dataset (even a few hundred examples), PEFT typically gives superior and more stable performance because the model parameters can adapt to the task distribution. Fine-tuning is also more sample-efficient than standard full fine-tuning because fewer parameters are updated, but it still benefits from labeled data. Conversely, if you have zero labeled examples and the task is easily specified through instructions and examples, ICL is the only option unless you perform unsupervised or self-supervised adaptation.

Privacy and compliance constraints often favor PEFT. In-context learning requires sending full examples to the model provider for each inference, which may be unacceptable. A locally stored adapter or merged weights avoids repeated data transmission and can be audited. Similarly, for on-device or offline inference without internet access, PEFT (with merged weights) is necessary.

Robustness and reproducibility also weigh in. Model outputs with ICL may be sensitive to prompt phrasing, example ordering, and random seeds; this variability can be undesirable in production. PEFT yields deterministic model checkpoints whose behavior is fixed, aiding reproducibility and enabling standard validation and monitoring.

Finally, cost and compute trade-offs: for occasional tasks with small throughput, ICL’s absence of training can be cheaper. But for high-volume applications, the amortized cost of training a small adapter and storing it locally is often lower than the cumulative cost of long prompts and repeated inference.

# Computation and memory considerations

Understanding the computational and memory profile of PEFT methods is critical for designing efficient training and deployment pipelines. Key factors include the number of trainable parameters, optimizer state, gradient storage, forward/backward compute, and inference-time overhead.

Trainable parameter count and optimizer state. When training, memory usage for parameters usually increases by at least a factor of two compared to inference: you must store the model parameters and their gradients, plus optimizer states (e.g., first and second moments for Adam). If you train only $M$ parameters, the optimizer state scales with $M$ rather than $N$. For example, with Adam, you might store 2 additional vectors of size $M$ (first and second moments), so optimizer memory is roughly $3M$ parameters (parameters + two moment estimates). This is a major saving when $M \ll N$. For LoRA with rank $r$ applied to several matrices, $M = r \sum (d_i + k_i)$ across targeted layers.

Backward computation and activations. Gradient computation requires storing activations needed for backpropagation. If you freeze most of the model, you can sometimes avoid storing activations for frozen layers by using forward recomputation (checkpointing) strategies or by using specialized libraries that only compute gradients for trainable parameters. However, in practice, frameworks will often still need to store activations unless you explicitly use gradient checkpointing or custom kernels that skip backward for frozen modules. Some PEFT methods (e.g., adapters inserted deep into the network) will require storing activations at those locations, but this is typically small compared to storing activations for the entire model.

Compute overhead during training. Training only the added modules reduces computation because fewer gradient calculations are needed, but the forward pass of the entire model still runs. For LoRA, the low-rank updates add extra matmuls of size $r$ which are cheap when $r$ is small. Adapters introduce additional computation inside layers, proportional to the bottleneck rank. Prefix and prompt tuning add small per-token computations for the learned embeddings or attention prefixes. In summary, PEFT methods reduce GPU memory and optimizer cost significantly while incurring small additional forward compute.

Inference-time considerations. Some PEFT methods can be merged into the base weights post-training (e.g., LoRA’s $BA$ can be added to $W_0$), after which inference cost equals the original model. Adapters generally remain as separate modules but incur only small extra compute, roughly proportional to $2dr$ per adapter layer. Prefix tuning and prompt tuning increase sequence length or attention keys/values; this can increase inference latency and memory linearly with the prefix length. IA3’s multiplicative scalings incur negligible cost and are trivial to apply at runtime.

Storage and deployment. Storing PEFT adapters or LoRA matrices requires storing only $M$ parameters per task. This enables shipping many task-specific modules that can be loaded and applied to a frozen backbone at runtime. If you merge LoRA into the backbone to remove runtime composition, you must store a full merged model per task, losing the storage advantage. Therefore, the operational choice depends on whether you can keep a central backbone and dynamically load small modules.

Hardware and implementation considerations. Efficient use of GPUs or TPUs requires kernel support for small matrix multiplications and fused operations. Some frameworks and inference engines optimize for merged weights; others support on-the-fly composition (e.g., applying LoRA updates during forward passes). When doing many small matmuls (as with adapters across many layers), vectorized or fused implementations reduce overhead. Consideration of mixed-precision training (e.g., FP16) and stable initialization are also important to avoid numerical issues.

# Evaluation differences between tuning and inference-only approaches

Evaluating models adapted via PEFT differs in subtle but important ways from evaluating models used via in-context learning or elsefully trained approaches. Proper evaluation ensures fair comparisons and reliable conclusions.

Task splits and lookahead. When evaluating fine-tuning methods, ensure strict separation between training and evaluation data. For PEFT especially, if you tune on a small validation set or perform multiple rounds of hyperparameter search, you can inadvertently leak information into the tuned parameters. For in-context learning, the template examples constitute a kind of tuning at inference time; ensure that examples used for prompts are not drawn from the evaluation set.

Prompt selection and hyperparameters. In-context methods are highly sensitive to prompt wording, example ordering, and the number of examples. Fair evaluation requires searching over prompt formulations and reporting either the best prompt (with costs noted) or averaging over many prompts. For PEFT, you must report the tuning data size, initialization, learning rate, number of steps, and any hyperparameter search, because performance depends on these choices.

Compute and latency accounting. Compare methods on equal footing: for a given compute budget, how do methods perform? In-context learning has zero training cost but higher per-query cost; PEFT has training cost and small inference overhead. Report both total training FLOPs, per-inference FLOPs, and observed latency. When reporting storage or deployment costs, include whether adapters are kept separate or merged.

Robustness and variance. PEFT methods often yield more stable outputs than ICL across runs and prompts. Report variance across random seeds and, for ICL, across prompt samplings. Calibration and reliability metrics (e.g., expected calibration error) can differ between tuned and inference-only approaches: a tuned classifier may be overconfident if the tuning data is small; ICL outputs may be erratic. Include such diagnostics.

Ablations and baselines. Compare PEFT against strong baselines: full fine-tuning (if feasible), linear probes, and ICL with well-tuned prompts. Also compare different PEFT variants (adapter sizes, LoRA rank $r$, prefix length $L$, IA3 placements) to understand the trade-offs of parameter count vs performance. Report the point at which additional parameters no longer yield meaningful gains.

Real-world constraints. When evaluating for deployment, include metrics important in practice: memory footprint, model loading time, compatibility with existing serving infrastructure, privacy considerations, and maintainability. A method that marginally improves accuracy but doubles inference latency might be undesirable in production.

Interpretability and failure modes. PEFT can hide undesirable behavior; because the backbone remains frozen, some failure modes of the pretrained model persist, and adapters may only partially correct them. Evaluate out-of-distribution robustness, adversarial susceptibility, and behavior on safety-critical inputs. For ICL, examine sensitivity to prompt distribution shifts.

In summary, evaluation must measure not only task accuracy but also compute, memory, latency, robustness, reproducibility, and operational costs. Only with these comprehensive metrics can one decide whether a PEFT method is appropriate for a given application.

# Conclusion

Parameter-efficient fine-tuning methods provide practical and empirically robust ways to adapt large pretrained models with small additional parameter budgets. Adapters, prefix/prompt tuning, LoRA, and IA3 each offer different trade-offs in expressivity, storage, compute, and deployment complexity. Understanding when to use these methods versus in-context learning or full fine-tuning depends on task frequency, data availability, latency and privacy requirements, and resource constraints. Careful attention to computation and memory implications and a rigorous, comprehensive evaluation protocol are essential for selecting and deploying the right approach in research and production.
