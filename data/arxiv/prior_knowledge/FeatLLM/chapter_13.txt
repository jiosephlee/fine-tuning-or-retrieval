Introduction

Experimental design is the backbone of empirical machine learning research. A well-designed experiment allows you to draw reliable conclusions about whether a particular modeling choice, architectural change, training procedure, or dataset preprocessing step actually improves performance, and by how much. Poor experimental design leads to misleading claims, irreproducible results, and wasted effort. In this chapter we develop a set of practical principles and protocols for designing experiments, selecting hyperparameters, performing ablation studies, reporting results with appropriate measures of uncertainty, measuring computational costs, and making work reproducible. We also discuss how to choose meaningful baselines to compare against. The goal is to enable you to read, replicate, and perform rigorous empirical work in machine learning.

# Train/validation/test splits and k-fold cross-validation

At the center of experimental design is the idea of splitting available data into separate sets for training, validation (or development), and testing. The training set is used to fit model parameters. The validation set is used to tune hyperparameters, select model checkpoints, and make design decisions. The test set is reserved for the final evaluation and must not influence any decision that could bias the reported performance. When this separation is respected, the test set gives an honest estimate of how the model will perform on truly unseen data.

A common simple split is the "train/validation/test" split with fractions such as 80/10/10 or 70/15/15 depending on dataset size. However, fixed splits can be inefficient or unstable when data is limited. K-fold cross-validation offers a more robust alternative: partition the data into $k$ approximately equal folds, train $k$ models each time using $k-1$ folds for training and the remaining fold for validation, and average the performance across folds. Cross-validation reduces variance in performance estimates and maximizes training data utilization because each example serves as validation exactly once. The typical choices are $k=5$ or $k=10$. In practice, for large datasets the additional computational cost of cross-validation may not be justified; for small datasets cross-validation is highly recommended.

It is important to distinguish between cross-validation for model selection and the final test evaluation. If you use cross-validation to select hyperparameters, you still need a separate held-out test set that was never used during any fold's validation. One correct protocol is nested cross-validation: an outer loop partitions the data into outer train/test folds to estimate generalization, and an inner loop performs cross-validation on the outer training portion to select hyperparameters. Nested cross-validation controls for the optimistic bias introduced by using the same data for tuning and evaluation, though it can be computationally expensive.

When designing splits, take care with data that have temporal, grouped, or correlated structure. For time series, random splitting can leak future information into the past—use time-based splits where the training set precedes the validation and test sets chronologically. For grouped data (for example, multiple samples from the same user, patient, or experiment), ensure that groups are kept intact across splits so that the model is not tested on examples that are highly similar to those in training. Similarly, for spatial or hierarchical data ensure that cross-validation folds respect the data-generating dependencies to avoid artificially inflated performance.

Stratification helps ensure that class proportions are preserved across splits in classification tasks, which reduces sampling variance for imbalanced datasets. When using stratified k-fold cross-validation, maintain similar class distributions within each fold. However, stratification must be combined with group or time constraints carefully: for grouped data, prefer grouped stratified splits that preserve both group integrity and approximate class balances.

# Hyperparameter tuning protocols and preventing leakage

Hyperparameter tuning is the process of selecting model architecture parameters and training settings that are not learned through gradient descent—learning rate schedules, regularization strengths, dropout rates, embedding sizes, optimizer choice, and so on. The validation set should be the only source of feedback for hyperparameter selection. If the test set is used even indirectly for tuning, the test performance becomes an optimistically biased estimate of generalization and invalidates statistical inference.

A safe hyperparameter tuning protocol begins by reserving a test set that is never touched until the very final evaluation. The remaining training data can be split into a training set used for fitting and a validation set used for tuning. For more robust selection, use cross-validation on the training+validation portion (or nested cross-validation as described earlier). Automated hyperparameter search methods—grid search, random search, Bayesian optimization, population-based training—are permissible as long as they only use validation feedback. When using these methods, record the hyperparameter configuration corresponding to the best validation performance and then evaluate that single configuration on the held-out test set.

Hyperparameter leakage happens when information from the test set leaks into the tuning process. This leakage can be subtle. Examples include: (1) repeatedly evaluating the test set and choosing the model that performed best on it; (2) using test-set performance to design new features or preprocessing steps; (3) debugging models on the test set and adjusting hyperparameters there. Any practice where the test set informs model design breaks the independence assumption required for proper evaluation.

Another common source of leakage is data preprocessing performed before the split. For example, performing feature normalization (computing global mean and variance) on the entire dataset before splitting uses information from test examples to affect training. Instead, compute normalization parameters on the training set only and apply them to validation/test sets. This applies to any data-driven preprocessing operations: imputation, feature selection, dimensionality reduction (PCA), vocabulary construction for NLP models, label smoothing calibration, and so on. When using cross-validation or nested procedures, compute such preprocessing within each fold using only data available to that fold's training set.

Hyperparameter search complexity and implicit multiple comparisons must be noted when reporting results. Performing hundreds or thousands of trials increases the chance of selecting a configuration that overfits by luck to the validation set. To account for this, one can use nested validation to estimate generalization error after search, or report both the validation and test performance with awareness that hyperparameter search magnifies variance. If computational resources are limited, consider simple, robust tuning strategies: random search often outperforms grid search by covering the space more broadly; successively halving or bandit-based methods can cut down wasted evaluation time.

Finally, maintain an explicit record of all hyperparameter trials, random seeds, and the validation metrics that informed selection. This audit trail supports reproducibility and helps diagnose whether performance gains are real or the result of excessive tuning overfitting the validation set.

# Ablation studies to isolate component contributions

An ablation study systematically removes or modifies components of a model or an experimental pipeline to determine each component's contribution to the overall result. Ablations are essential for scientific claims: when authors claim that a new architecture or loss term causes improvement, ablations are the way to test that claim. A good ablation study isolates variables so that changes in performance can be attributed to specific modifications.

The baseline for an ablation study is a reference model that includes all components being proposed. Then individual components are removed one at a time (single ablations) while holding everything else constant, and the performance of each ablated model is compared to the full model. Single ablations reveal the marginal contribution of each component. Interaction effects, where two components together produce non-additive effects, require paired or combinatorial ablations: disable combinations of components to see whether their effects add, multiply, or interfere. For $n$ components, exhaustive combinatorial ablation requires $2^n$ runs and becomes infeasible for large $n$, so plan which interactions are plausible and prioritize those.

When performing ablations, control all other variables strictly: use the same training schedule, random seed distribution or multiple seeds, hyperparameters, data splits, and preprocessing. If a component changes the number of parameters or runtime, consider parameter-matched baselines—e.g., scale a baseline model to have a similar parameter count or FLOPs—so that improvements are not merely from undercontrolled capacity differences. When architectural changes alter optimization dynamics, tuning the baseline's optimizer hyperparameters fairly is important so that improvements are not the result of neglecting baseline tuning.

There are different kinds of ablations. Functional ablations remove an entire module (for example, remove an attention mechanism), structural ablations replace a module with a simpler one (replace a fancy regularizer with standard weight decay), and hyperparameter ablations sweep the values of a critical hyperparameter to show the sensitivity and stability of results. Present results visually (curves, bar charts, or tables) that make clear the relative contributions and any trade-offs, such as accuracy versus latency. Also include negative ablations—changes that were attempted but did not help—as they provide valuable information about what does not work.

Finally, ablation studies should be reproducible and comprehensive enough to support the central claims. If a paper credits a new regularizer with improvements, show an ablation where the regularizer is removed but everything else remains identical. If a paper proposes a training curriculum, ablate the curriculum by using a standard training schedule. Transparently reporting ablation methodology and outcomes strengthens the causal interpretation of empirical results.

# Reporting averages, variances, and statistical significance

Single-number performance reports are incomplete; we need measures of variability and tests of significance to interpret whether observed differences are credible or likely due to chance. Sources of variability include random initialization, stochastic optimization, data sampling for splits, and non-determinism in hardware or parallel training. To capture this variability, run each experimental condition multiple times with different random seeds and report summary statistics such as the mean, standard deviation, and confidence intervals of the metric of interest.

A recommended practice is to report the mean and standard error of the mean (SEM) across independent runs. If you perform $m$ independent runs yielding metric values $x_1, \dots, x_m$, report the sample mean $\bar{x} = \frac{1}{m} \sum_{i=1}^m x_i$ and the sample standard deviation $s = \sqrt{\frac{1}{m-1}\sum_{i=1}^m (x_i - \bar{x})^2}$. The SEM is $s/\sqrt{m}$ and a $95\%$ confidence interval for the mean can be approximated by $\bar{x} \pm 1.96\cdot \text{SEM}$ assuming approximate normality. For non-normal distributions or small $m$, use bootstrap confidence intervals or report the full distribution of results.

When comparing two methods, hypothesis testing can help determine whether an observed difference is statistically significant. Paired tests are more powerful when applicable: if both methods are evaluated on the same test folds or same random seeds, a paired t-test or Wilcoxon signed-rank test can exploit the dependency structure. For unpaired comparisons, use an unpaired t-test or appropriate nonparametric test. However, be cautious: statistical significance does not imply practical significance. For large datasets, tiny improvements can be statistically significant yet irrelevant in practice.

Multiple comparisons pose another concern. If you test many models, hyperparameter settings, or datasets, the chance of obtaining a statistically significant result by random chance increases. Correct for multiple comparisons using procedures such as the Bonferroni correction or the Benjamini-Hochberg false discovery rate control when reporting many p-values. Better yet, reduce the number of arbitrary tests and pre-register hypotheses or primary metrics when possible.

For complex metrics, consider plotting full performance distributions, such as boxplots, violin plots, or empirical cumulative distribution functions (ECDFs), which convey skewness, outliers, and multimodality. When improvements are heterogeneous across data subgroups, provide per-subgroup statistics (for example, performance by class, by input length, or by difficulty). Always report the number of independent runs and seeds used; one or two runs are rarely sufficient to make strong claims.

Finally, be transparent about metric selection. If multiple evaluation metrics exist (accuracy, F1, AUC, precision, recall), clearly state which metric is primary for claims and why. When secondary metrics are reported, avoid cherry-picking the metric that shows your method in the best light. Documenting the full set of metrics and their variability paints a complete and honest picture of model behavior.

# Measuring runtime, cost, and inference latency

Beyond accuracy, practical machine learning systems are judged by computational and economic costs: training time, inference latency, memory usage, energy consumption, and monetary cost of compute resources. Reporting these measures is essential when claiming efficiency improvements or real-time applicability.

Define precisely what you measure. Training time can mean wall-clock time to converge to a specified validation performance, time per epoch, or time per optimization step. Inference latency can be measured as the average time to produce a single prediction, or as tail latencies such as the 95th percentile latency. Distinguish between throughput (predictions per second) and latency (time per prediction). Memory measurements should indicate peak memory usage for training and inference separately.

Hardware specifications must be reported in detail. Document CPU and GPU model numbers, number of cores, clock speeds, available RAM, interconnects, and software stack versions (BLAS libraries, CUDA/cuDNN versions, framework versions). Small hardware differences can produce large performance variations. When using cloud resources, indicate instance types and any accelerator configurations. If you use mixed-precision training, note that it can significantly change performance and memory usage.

When measuring runtime, control and report batch sizes and other batching strategies because these directly affect throughput and latency. For example, GPUs are often more efficient with larger batch sizes; reporting latency at batch size 1 is important for interactive applications. Warm-up effects (JIT compilation, caching) can distort measurements; discard initial iterations and report stable-state metrics. For multi-process or distributed training, report the scaling behavior and communication overheads (for example, how throughput changes as the number of workers increases).

Monetary cost is increasingly relevant. Report the total compute cost in terms of GPU-hours or cloud dollars used for training and inference estimates. For reproducibility, report the total amount of floating point operations (FLOPs) or system-level metrics like power consumption if available. Energy consumption can be measured with power meters or estimated using provider billing and hardware TDP, and it provides an environmental perspective on model choices.

When claiming improved efficiency, compare against cost-matched baselines where possible. For instance, if your model achieves higher accuracy with fewer FLOPs, show the baseline model scaled down to the same FLOPs to ensure the improvement is not simply due to having higher compute. Present trade-off curves (e.g., accuracy vs. latency or accuracy vs. FLOPs) rather than a single point, which allows readers to evaluate the method under different operating constraints.

# Reproducibility practices and code/data reporting

Reproducibility is the ability for others to duplicate your results given your code and data. It is a scientific imperative because reproducible results can be validated, extended, and built upon. Achieving reproducibility requires attention to documentation, code release, data accessibility, and deterministic experiment setup.

First, release code with clear instructions for installation and usage. Include environment specifications (operating system, package versions, Python version, CUDA/cuDNN versions) and dependency files (for example, a requirements.txt or environment.yml). Containerization using Docker or Conda environments helps others reproduce the environment precisely. Provide scripts to reproduce each experiment, including training, evaluation, and ablation runs, and set sensible defaults.

Second, make datasets accessible or provide precise instructions for dataset preparation. If data cannot be shared due to privacy or licensing, provide detailed preprocessing scripts, exact versions of data sources, and sample synthetic data that demonstrates pipeline behavior. For preprocessed datasets or tokenizers, include the exact artifacts or the transformations applied and record any filtering or augmentation decisions.

Third, set and report random seeds and the sources of randomness. While deterministic execution is sometimes impossible due to nondeterministic GPU operations, make seeds for all randomness (initialization, data shuffling, augmentation sampling) explicit and provide a reproducible seed-setting mechanism. If exact determinism cannot be achieved, document the expected nondeterminism and show that it does not materially affect conclusions by reporting variance across runs.

Fourth, document hyperparameters, training procedures, and early stopping criteria in full. Provide the exact command lines or configuration files used for each experiment. If a configuration was selected from many runs, disclose the search procedure and the chosen configuration that was finally evaluated. Where possible, publish model checkpoints and logs (training curves, validation metrics per epoch) so that others can verify progress and detect anomalies.

Fifth, adopt best practices in software engineering: modular code, unit tests for critical components, continuous integration, and code commenting. Well-structured code increases other researchers' ability to understand and reuse methods. Encourage community reproduction by providing small-scale examples that run quickly and produce interpretable outputs.

Finally, when releasing results, include a reproducibility checklist in the paper or supplemental materials: code availability, dataset links, hyperparameter tables, number of seeds, hardware used, and evaluation scripts. Journals and conferences increasingly require or encourage such checklists, and adhering to them enhances the impact and reliability of your work.

# Choosing meaningful baselines

Baselines anchor claims in context. A new method is only interesting if it improves upon reasonable alternatives under fair conditions. Choosing meaningful baselines means selecting methods that represent the current state-of-the-art, simpler but competitive approaches, and cost-matched variants that control for confounding factors such as parameter count or compute.

Start with simple, well-established baselines. For supervised learning, this might include logistic regression, random forests, or simple neural networks when appropriate. These baselines serve as sanity checks: if a complex model cannot beat a simple baseline, re-examine experimental setup and claims. Include strong, well-tuned baselines rather than underperforming implementations. A common pitfall is to compare a new method against a poorly tuned baseline and claim superiority; this undermines credibility.

Include state-of-the-art methods and those that are most conceptually related. If you propose a new regularizer, compare against other regularizers; if you introduce a new architecture, compare against architectures of similar capacity or recent leading models. When applicable, include ablations of the baseline to show whether your improvements could be recovered by better tuning or small modifications. Parameter-matched baselines are particularly valuable: scale the baseline to have similar parameter count, FLOPs, or training time to rule out trivial capacity or compute benefits.

Describe baseline implementations thoroughly. When you reimplement published baselines, note all deviations and justify them. If you use publicly available implementations, cite their versions and any configuration changes. If reproducibility is a goal, provide the exact code used for baseline runs.

When proposing a method that trades off accuracy for efficiency, compare against baselines operating at similar resource budgets. For example, if your method reduces inference latency, compare to other low-latency models or the same model with quantization or pruning. Present performance-versus-resource curves for both your method and baselines so that users can choose an operating point appropriate to their constraints.

Finally, be honest about negative or mixed results. If your method improves on some datasets but underperforms others, report those observations. Contextualize your baselines: a method that beats baselines on a synthetic or toy dataset may not generalize to more realistic settings. Claim improvements only where they are consistently supported by rigorous evaluation.

# Conclusion

Designing rigorous experiments in machine learning requires careful control of data splits, strict separation between tuning and testing, systematic ablation studies, transparent reporting of variability and significance, comprehensive measurement of computational costs, rigorous reproducibility practices, and thoughtful selection of baselines. Applying these principles protects against common pitfalls like data leakage, selective reporting, and unfair comparisons. As you progress in research, make experimental rigor a priority: it is the path to credible, useful, and lasting contributions to the field.
