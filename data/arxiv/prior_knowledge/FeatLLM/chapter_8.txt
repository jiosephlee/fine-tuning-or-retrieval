# Introduction

Large language models (LLMs) have demonstrated an impressive ability to perform a wide range of tasks without any parameter updates, simply by conditioning on a text prompt that describes the task and provides examples. This capability is commonly called in-context learning: the model interprets the prompt and adapts its behavior "on the fly" to produce appropriate outputs. Prompt engineering is the practice of designing and arranging these prompts so the model reliably produces the desired behavior. Together, in-context learning and prompt engineering form a practical workflow for getting useful behavior from LLMs in research and applications, often without the expense or complexity of fine-tuning.

This chapter explains the principles of in-context learning, shows concrete prompting patterns, and dives into engineering choices that materially affect model performance. You will learn how to write effective task descriptions, how to select and order few-shot examples, how to prompt for chain-of-thought reasoning, how to control stochasticity via sampling parameters, how to manage limited context length, and how to recognize and mitigate common failure modes. Each section aims to develop intuition, give illustrative examples, and present practical techniques you can apply when reading papers or building systems with LLMs.

# In-context learning concept and examples

In-context learning means using the model's conditioning mechanism—the sequence of tokens in the prompt—to specify a task and examples so that the model's next-token prediction yields task-appropriate outputs. Crucially, the model's weights remain fixed; adaptation happens through the prompt itself. Practically, a typical in-context prompt might include an instruction, several examples mapping inputs to outputs, and a new input for which the model is asked to produce an output.

Consider a few simple examples to make this concrete. For a classification task, the prompt might be:

"Classify sentiment.
Example 1: 'I love this movie.' -> Positive
Example 2: 'It was awful.' -> Negative
Input: 'The plot was predictable.' ->"

When the LLM continues this prompt, it should produce "Negative". For machine translation, the prompt can contain bilingual pairs:

"Translate English to French.
English: 'Good morning.' -> French: 'Bonjour.'
English: 'How are you?' -> French: 'Comment ça va ?'
English: 'See you later.' -> French:"

The model should output "À plus tard." or a similar translation. For arithmetic, few-shot examples can help the model identify the pattern and apply it:

"Add numbers.
2 + 3 = 5
4 + 7 = 11
15 + 9 ="

The model should output "24". In each example, the model infers the mapping from examples and continues appropriately for the new input.

In-context learning can also encode transformations that aren't simple mappings: code generation given a docstring, semantic parsing, summarization, question answering when paired with a short context, or even multi-step reasoning when you craft the prompt skillfully. Modern LLMs can pick up on subtle patterns in examples and generalize to novel inputs because their pretraining implicitly encodes a wealth of tasks and reasoning heuristics that can be triggered by contextual cues.

# Designing prompts: task description, examples, format instructions

A good prompt usually has three components: a clear task description, representative examples (if using few-shot), and explicit format instructions telling the model how to produce outputs. Each component carries distinct roles.

The task description sets the high-level intent. It should be explicit about the objective and any constraints. For example, "Summarize the following paragraph in one sentence, preserving factual details" gives the model both the operation (summarize) and a constraint (one sentence, factual). Keep descriptions concise but unambiguous. Overly long or vague descriptions risk confusing the model or diluting the signal from examples; overly terse descriptions may not sufficiently constrain behavior.

Examples provide the model with a pattern to follow. When including examples for in-context learning, include the input and the desired output in a consistent format. Examples should be representative of the variety of cases you expect the model to handle; cover edge cases and typical instances you'd like it to learn. For complex tasks, showing the intermediate steps in example outputs (structured examples) can teach the model to produce similar internal structure at inference time. Examples are also how you communicate style—formal vs. informal tone, brevity vs. verbosity, numeric precision, and so on.

Format instructions specify the shape of the output. For instance, "Answer with a single word: 'Yes' or 'No'." or "Return a JSON object with fields 'summary' and 'keywords'." Explicit format constraints reduce ambiguity and make post-processing easier. When you require strict formatting (e.g., machine parsable), state it clearly and use examples that demonstrate exactly the format you require.

A few practical points about these three components: put the task description first to set context, then examples to exemplify behavior, then the new input to signal the model to continue. Use separators (like blank lines or delimiters such as "----") to make the structure visually and token-wise distinct. Keep the prompt consistent: identical punctuation, spacing, and labeling across examples helps the model generalize the pattern. Finally, when you need the model to produce outputs that will be parsed by downstream code, prefer strongly typed instructions (e.g., "Return valid JSON" and include a JSON example) rather than leaving format implicit.

# Few-shot example selection and ordering effects

Choosing which examples to place in the prompt and in what order significantly influences performance. Example selection involves deciding which instances to demonstrate; ordering effects encompass how the sequence of examples affects the model's attention and pattern extraction. Both selection and ordering exploit how the model uses context as an implicit "training set."

There are several principles for selecting examples. Representativeness means examples should cover the diversity of inputs the model will encounter: typical cases, important edge cases, and the distribution of labels or outputs. Avoid showing only one narrow slice of the distribution if you expect variety. Demonstrating edge cases is particularly valuable when they differ from the majority; the model can over-generalize from only common examples.

Another useful selection strategy is similarity-based selection. For a given query input, you can retrieve nearest neighbors from a labeled corpus (using embedding similarity or other distance metrics) and use those as in-context examples. This approach, often called retrieval-augmented prompting, gives the model examples most relevant to the current input, improving performance in many tasks, especially ones sensitive to local context (e.g., entity-specific QA or code completion).

Diversity-based selection is helpful when the model must handle several different patterns. You can choose examples that maximize coverage across subtypes of the task or different label classes. If the task has rare but important cases, include them intentionally, even if they are not nearest neighbors.

Ordering of examples also matters because models can exhibit primacy and recency biases: they may attend more strongly to examples presented at the beginning or the end of the context. Empirically, the most recent examples often carry disproportionate weight for many transformer-based models because of attention patterns and the autoregressive generation process. Therefore, when using retrieval-based examples, you might place the most similar examples nearer the test query (i.e., later in the prompt) to leverage recency bias.

There are additional ordering strategies: curriculum ordering (arrange examples from easy to hard) can help the model infer the underlying rule progressively. Conversely, clustering similar examples together can help the model extract the pattern for each cluster separately. When using few-shot chain-of-thought examples (explained below), ordering influences whether the model learns to produce step-by-step reasoning: similar solved examples placed before the unsolved query encourage replication of the reasoning style.

Finally, because the number of examples you can include is limited by the context window, there is a trade-off: more examples provide more information but reduce the space available for the new input and the model's internal attention resources. Use selection algorithms (nearest-neighbor retrieval, clustering, or mixed strategies) to choose the most informative subset of examples for each query.

# Chain-of-thought and structured prompting for improved reasoning

Chain-of-thought (CoT) prompting refers to providing or eliciting intermediate reasoning steps in the model's output rather than asking only for the final answer. The core insight is that many reasoning tasks are easier if the model is guided to produce and follow explicit stepwise logical or arithmetic steps. CoT examples show the model not just the mapping from input to output, but the derivation that leads from one to the other.

For example, instead of a simple arithmetic prompt:

"Q: If there are 12 apples and each basket holds 4, how many baskets are needed?
A:"

A chain-of-thought example would be:

"Q: If there are 12 apples and each basket holds 4, how many baskets are needed?
A: 12 divided by 4 is 3, so 3 baskets are needed."

Providing CoT examples can dramatically improve performance on multi-step reasoning tasks, including arithmetic word problems, symbolic reasoning, and multi-hop question answering. The model learns not only the final response format but also how to structure intermediate steps, which can help it avoid common mistakes like misapplying operators or ignoring constraints.

Structured prompting generalizes the CoT idea: it means designing prompts that enforce or encourage a particular internal structure in the output. This can include labeled steps ("Step 1:", "Step 2:"), structured intermediate representations (logical forms, equations, lists), or templates that the model fills in. For example, for a complex extraction task, you might instruct the model to first "Identify entities", then "Determine relations", and finally "Return triples". Structured prompts reduce ambiguity and make it easier to verify and post-process outputs.

There are several advanced techniques related to CoT. Few-shot CoT provides several examples with explicit reasoning chains; zero-shot CoT uses an instruction like "Let's think step by step" in a zero-shot setting to elicit a chain of thought without example chains. Self-consistency is another technique: sample multiple CoT reasoning traces for the same prompt, compute the final answers from each trace, and choose the most frequent final answer. This reduces sensitivity to the variability in any single sampled chain.

However, CoT prompts increase token consumption because you must include detailed reasoning in each example. They can also increase the chance of the model producing incorrect but convincing reasoning (so-called "hallucinated rationales") that nevertheless leads to a correct or incorrect final answer; therefore, verification strategies (discussed later) are often necessary. Despite these caveats, CoT and structured prompting are among the most powerful tools for eliciting complex reasoning behavior from LLMs.

# Controlling LLM stochasticity: temperature and sampling strategies

LLMs are probabilistic next-token predictors. How you sample from their output distribution strongly affects creativity, determinism, and reliability. The two main controls are temperature and the sampling strategy (greedy, top-k, nucleus/top-p, beam search).

Temperature, typically denoted $T$, rescales the model's logits before applying the softmax. If the model produces logits $z_i$ for token $i$, the probability of token $i$ under temperature $T$ is

p(i) = softmax(z_i / T),

so lower $T$ (< 1) sharpens the distribution, making high-probability tokens even more dominant; $T \rightarrow 0$ approaches greedy decoding. Higher $T$ (> 1) flattens the distribution, increasing randomness. For tasks that require consistent, repeatable outputs—such as code generation, JSON output, or multiple-choice classification—use low temperature (e.g., $T=0$ or near-zero) to reduce variability. For creative tasks (story generation, brainstorming) a higher temperature can produce more diverse outputs.

Top-k sampling restricts output choices to the $k$ tokens with the highest probabilities, sampling proportionally within those. This prevents extremely unlikely tokens from being chosen but can lead to truncating useful tail probability mass if $k$ is too small. Nucleus or top-p sampling selects the smallest set of tokens whose cumulative probability mass is at least $p$, then samples proportionally among that set. Nucleus sampling adapts dynamically to the shape of the distribution and often yields higher-quality diverse outputs than fixed top-k.

Beam search keeps multiple candidate continuations (beams) and iteratively expands them, selecting the most probable sequences under the model. Beam search tends to produce more probable, less diverse outputs and is commonly used when you want the single most likely completion. However, beam search can produce pathological repetitions or generic outputs unless combined with length normalization, coverage penalties, or other heuristics.

Practical rules of thumb: for deterministic tasks and evaluation, set $T$ very low (often $0$ or $0.2$) and use greedy decoding or beam search. For exploration and creativity, use $T$ in the range $0.7$–$1.2$ with nucleus sampling ($p$ around $0.8$–$0.95$). When using chain-of-thought reasoning, sampling with a moderate temperature and applying self-consistency (sampling multiple chains and aggregating final answers) often outperforms a single greedy CoT trace.

Also consider seeding and reproducibility: random seeds control sampling reproducibility when temperature is nonzero. For production systems where determinism is required, freeze the seed or use greedy decoding. For research where you want to estimate uncertainty, run multiple stochastic samples and consider the distribution of outputs.

# Prompt length trade-offs and context management

LLMs have a finite context window: inputs beyond this window are truncated or otherwise inaccessible to the attention mechanism. Prompt length decisions therefore trade off the number and richness of included examples, the length of the new input, and any additional context like external documents or tool outputs.

If you require many or long examples (for example, chain-of-thought examples), you may run into the context limit. A larger number of examples improves in-context learning generally, but returns diminish and eventually reverse when the prompt becomes too long and the model's attention becomes diluted or must truncate the input. Organize prompts to prioritize the most relevant information: task description and the most informative examples, with the new query placed in a location where recency bias helps (often near or right before the expected output).

Context management strategies include chunking long external documents into smaller segments and retrieving only the most relevant chunks for each query. Retrieval-augmented generation (RAG) combines a separate retrieval system (e.g., vector similarity search using embeddings) with the LLM: retrieve the top-k relevant passages and include them in the prompt. This reduces the need to place entire corpora in the context window while still grounding the model's responses.

Another approach is progressive prompting: use multiple model calls where an earlier call extracts salient facts or intermediate representations, which are then fed into a second call with the actual task prompt. This two-step approach reduces average prompt length per call and can improve reliability (for example, first use a model to find named entities, then use those entities in a constrained generation step).

When context capacity is the chief constraint, careful example compression helps. Shorten examples by removing redundancy, using concise phrasing, or substituting placeholders. You can also encode examples in more compact structured forms (table-like representations or bullet points) that are still easy for the model to interpret. In extreme cases, you can distill many examples into a few "meta-examples" that capture the core pattern.

Finally, be mindful of tokenization: some tokens (e.g., certain whitespace patterns or non-ASCII characters) can expand the token count unexpectedly. Use consistent formatting and test the token length of prompts using the target model's tokenizer to ensure you stay within the window.

# Failure modes and mitigation techniques

While powerful, in-context learning and prompt engineering come with notable failure modes. Understanding them helps you design prompts and systems that are safer and more robust.

Hallucinations: LLMs can produce plausible-sounding but factually incorrect statements. Because LLMs approximate distributions of text rather than verify ground truth, they may invent facts when prompts lack sufficient grounding. Mitigation includes grounding outputs with retrieved documents (RAG), asking the model to cite sources explicitly, and verifying outputs with external knowledge bases or symbolic solvers. Calibration and fact-checking components are critical for high-stakes applications.

Brittleness and sensitivity: Small changes to wording, punctuation, or example ordering can lead to large performance shifts. This sensitivity makes prompt engineering brittle. Mitigation techniques include prompt ensembling (averaging outputs over multiple prompts), few-shot example selection strategies (nearest neighbors or curated sets), and automated prompt-search methods that test many candidate prompts and choose the best empirically.

Over-reliance on spurious correlations: The model may pick an unintended shortcut from few-shot examples (e.g., basing the answer on superficial token cues). Preventing this requires careful example design to avoid leaking unintended signals, and including counterexamples that discourage shortcut strategies. Adversarial testing—crafting inputs that expose spurious correlations—helps identify and fix these problems.

Inconsistent reasoning or false chains: With chain-of-thought prompting, the model can produce detailed but incorrect reasoning chains that look convincing. Self-consistency (sampling multiple chains and selecting the majority final answer) is one mitigation. Another is symbolic verification: when the chain produces a calculable result, re-check it with a deterministic calculator or rule-based verifier. For tasks that admit formal checks (e.g., arithmetic, logic), post-validate the answer.

Context contamination and prompt injection: When the prompt includes content provided by untrusted users (e.g., in a web app), malicious content could manipulate instructions or inject harmful directives. To mitigate this, separate trusted instructions from untrusted user inputs, sanitize or escape user content, and use model-controlled affordances like instruction-guard rails or policy filters. Keep system-level instructions in a protected portion of the context that is not concatenated with arbitrary user text.

Mode collapse and repetition: Greedy or poorly tuned decoding can cause repetitive outputs or collapse to generic responses. Use sampling strategies, length penalties, or diverse decoding methods to prevent repetition. Reward-based preferences or constrained decoding (e.g., forbidding immediate token repetition) can reduce pathological loops.

Scaling law mismatches and distributional shift: Performance observed in one setting (e.g., on certain datasets) may not generalize to others, especially when inputs differ from pretraining distributions. Address by collecting and testing on representative evaluation data, using retrieval of context-specific examples, and adapting prompts per domain.

Evaluation challenges: Because outputs can be highly variable, simple automatic metrics like BLEU or accuracy may misrepresent model performance when prompts encourage multiple valid outputs. Use human evaluation, structured output constraints (e.g., exact JSON), or task-specific validators to get accurate performance assessments.

Robust mitigation often combines multiple strategies: grounding with retrieval, explicit verification stages, conservative decoding for high-stakes outputs, diverse prompting to reduce brittleness, and human-in-the-loop checks for quality control.

# Practical checklist and best practices

Summarizing practical steps you can use when designing prompts and applying in-context learning:

1. Start with a clear, concise task description and explicit format instructions. Make desired output format unambiguous and demonstrate it in examples.

2. Choose examples that are representative and, when possible, similar to the query (use retrieval). Include edge cases you care about.

3. If the task requires multi-step reasoning, provide chain-of-thought examples or use zero-shot CoT prompting. For reliability, use self-consistency (sample multiple chains) and validate obvious computations.

4. Control randomness: use low temperature and greedy decoding for deterministic tasks; use top-p sampling with moderate temperature for creative tasks. Seed pseudo-random generators when reproducibility matters.

5. Manage context: use retrieval to include only relevant context, chunk long documents, and compress or shorten examples where necessary.

6. Test prompt sensitivity: vary wording and example order, run prompt-ensembles, and check for brittle behavior. Automate prompt search if scaling up.

7. Add verification: where possible, check outputs against ground truth, use symbolic solvers, or run fact-checking retrieval steps.

8. Harden against injection: keep system instructions separate and sanitize inputs.

9. Monitor and log outputs, especially in production, to catch drifts, hallucinations, or new failure modes as they arise.

# Conclusion

In-context learning and prompt engineering are powerful, practical techniques for leveraging LLMs without changing model parameters. Successful use combines clear task descriptions, carefully chosen and ordered examples, structured prompting to elicit reasoning, sampling strategies tuned to the use case, and sensible context management to stay within token limits. Be aware of the common failure modes—hallucinations, brittleness, and logical inconsistencies—and apply mitigation strategies like retrieval grounding, self-consistency, verification, and prompt ensembling. Mastery of these skills lets researchers and practitioners extract more reliable, interpretable, and effective behavior from LLMs across a wide array of tasks.
