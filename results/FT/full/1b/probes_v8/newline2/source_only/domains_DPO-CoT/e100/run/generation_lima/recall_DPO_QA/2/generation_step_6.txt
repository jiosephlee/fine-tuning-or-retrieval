# A database supports a read committed (RC) transactional model.  A
# transaction either commits completely or rolls back entirely.  There
# is no in-between.  There is no such thing as a nearly-committed record.
# 

# You can think of a "write path" as the series of steps taken to
# modify a row in the database.  They are:
#   1.  Input data to the database engine.
#   2.  Perform any necessary metadata changes to prepare to modify
#       the row.
#   3.  Modify the physical data in the database.
#   4.  Perform any necessary cleanup before the row modification.
#       This could be deleting or overwriting input data.
#   5.  Update the system table that keeps track of all the
#       currently visible rows.
#   6.  Update any archive tables that link to this table.
#   7.  Update any indexes that the system table contains an unique
#       or primary key link to this row.
#   8.  Update any other tables that this table links to via an
#          index the system table contains an Unique/Key to this row.
#       For example, if this row links to a many-to-one column, a
#       separate index on that column must exist for each many-to-one
#       column value in the table.
#   9.  Update any other indexes that this row links to.
#      In some databases, this can be a very expensive operation.
#      Some databases share access to multiple readers via index
#      updates, so they are kept in a read-only copy of the database
#      while this update is taking place.  This database feature
#      protects the single-point-of-failure transactional model in
#      favor of the optimize-for-performance many readers strategy.
#      This feature delays updating any indexes with a copy of the
#      old value for this row until after the update.  This can be
#      either a rough estimate or a precise computed value, depending
#      on the database implementation.
#   10. Update the system table with the visible update result.
#      This causes any monitoring or logging mechanisms to update
#      their views of the record.
#   11. Remove any indexes that this row uses as its index keys.
#      Destroying indexes that are no longer needed is useful for
#      preserving index tree structures in the case of clustered
#      indexes.
#   12. Update the appropriate index keys in the index trees for
#      each index this row uses.
#      Destroying or updating index keys causes logging and
#      monitoring mechanisms to update their views of the record.

# It seems like a lot of steps, but many of them are common to multiple
# rows, so they are grouped together in separate steps.

# update delay, and because indexes are so important, step 12 is
# included in this description of the write path.
